# [Metrics] Add vllm:kv_token_slots gauge

[Upstream PR](https://github.com/vllm-project/vllm/pull/64112) · state: open · merged: False

## Original PR description

Adds a per-engine Prometheus gauge, `vllm:kv_token_slots{kv_group,kind}`, for how the token slots in the KV cache blocks of running and loading requests are used: filled, tail slack in each request's last block, and slots reserved for lookahead and speculative tokens.

## Overview

KV cache memory is allocated in whole blocks. A request's last block is usually only partly filled, and blocks allocated for lookahead slots and speculative tokens hold no KV yet. `vllm:kv_cache_usage_perc` counts whole blocks, so this internal fragmentation is invisible. It grows with the block size: with `block_size=128` (common on TPU) or 256, each request wastes up to 127 or 255 slots in its last block.

This PR exports, per KV cache group:

| `kind` | Meaning |
|---|---|
| `filled` | computed tokens still held, including the tokens scheduled this step (tokens in null blocks a sliding window released are excluded) |
| `tail_slack` | unused slots in each request's last computed block |
| `reserved` | slots in blocks allocated past them (lookahead and speculative tokens) |

`tail_slack / (filled + tail_slack)` is the fraction of held KV memory lost to partial blocks.

## Claims

- `vllm:kv_token_slots` reports the three kinds above for running requests and every request in `kv_holding_waiting` (async loads in flight, and finished loads not yet admitted), per token KV cache group. Mamba and cross-attention groups have no token slots and are skipped.
- `filled` counts only blocks still held: tokens in null blocks (released by a sliding window, including blocks nulled in the middle of a request) are excluded.
- No behavior change: `KVCacheManager.get_token_slots()` only reads the block tables and the requests' computed tokens.
- It's computed in `make_stats()`, i.e. only with `log_stats`. The cost is one pass over the running and KV-holding waiting requests per KV cache group per step.

## Validation

New unit test `test_stats_report_kv_token_slots` in `tests/v1/core/test_scheduler.py` (mock async KV connector, `block_size=16`):
- an async-loading request with 32 claimed tokens (2 full blocks) and a running request with 40 tokens (3 blocks) give `filled=72`, `tail_slack=8`, `reserved=0`;
- after the load finishes but before the request is admitted (still in `kv_holding_waiting`), its blocks are still counted;
- allocating a 16-token lookahead past the computed tokens gives `reserved=16`;
- replacing a block in the middle of the block table with the null block removes its 16 slots from `filled`.

The finished-load and null-block cases each fail on the previous revision.

New logger test `test_kv_token_slots_gauge` in `tests/v1/metrics/test_histogram_buckets.py`: `PrometheusStatLogger.record(..., engine_idx=1)` with two KV cache groups sets each `{kv_group, kind}` series for engine 1, and creates none for engine 0.

```bash
pytest tests/v1/core/test_scheduler.py -k kv_token_slots
pytest tests/v1/metrics/test_histogram_buckets.py -k kv_token_slots
pytest tests/v1/core/test_scheduler.py tests/v1/core/test_prefix_caching.py \
       tests/v1/core/test_kv_cache_utils.py tests/v1/metrics/test_histogram_buckets.py
```

All new tests are `cpu_test` (module-level marker), so they run in CI. The last command gives 560 passed; the 63 failures are the same ones that fail on unmodified `main` in my CPU-only environment (missing GPU / multimodal dependencies). `ruff check`, `ruff format` and `mypy` (1.20.2, as in pre-commit) are clean.

End-to-end on GKE, on the previous revision of this PR. Qwen2.5-7B-Instruct uses full attention (no null blocks), so the null-block change doesn't affect these numbers; including finished-but-not-admitted loads can only add the few requests in that state. vllm-torchtpu pins vLLM v0.32.0, so I cherry-picked the commit onto `v0.32.0` (one import-line conflict, no code change) and deployed it with stock vllm-torchtpu `main`, which has no plugin copy of this gauge. Setup: TPU v5e, Qwen2.5-7B-Instruct, P/D via llm-d with `TPUConnector` + Raiden, `block_size=128`, 109 KV blocks (13,952 token slots) per engine, no speculative decoding. A load job overloaded the single decode engine with shared-prefix and unique ~600-token prompts; the gauge was read once a second for 300 s:

| Engine | Samples (non-zero) | `filled` max | `tail_slack` max | `reserved` max | Running requests max |
|---|---|---|---|---|---|
| prefill | 281 (35) | 3,675 | 190 | 0 | 5 |
| decode | 280 (186) | 13,344 | 1,603 | 0 | 18 |

- In every sample, `filled + tail_slack + reserved` is a whole number of 128-token blocks, and whenever requests are running `tail_slack` stays below 127 × running requests. Decode's `filled` peaks at 13,344 of its 13,952 slots while `vllm:kv_cache_usage_perc` reaches 100%.
- At peak, decode loses up to 1,603 slots (~12.5 blocks, 11% of the pool) to partly filled last blocks.
- `reserved` stays 0: without speculative decoding or lookahead nothing is allocated past the computed tokens (tokens scheduled this step already count as computed). The unit test covers the non-zero case.

## Details

- **Where:** `KVCacheManager.get_token_slots(requests)` next to the block tables it reads; `Scheduler.make_stats()` passes `running` plus all of `kv_holding_waiting` (requests without blocks are skipped); the new `SchedulerStats.kv_token_slots` carries a list of `KVTokenSlots(kv_group, filled, tail_slack, reserved)`; `PrometheusStatLogger` sets the gauge.
- **Released blocks:** `filled` subtracts the null blocks actually present among the computed blocks, rather than the manager's skip rule. Blocks can still be held for in-flight tokens after the skip point, and some managers null blocks in the middle of a request.
- **Shared prefix blocks** count once per request holding them, like the per-request view of the scheduler. This measures slot use from the requests' point of view, not unique physical blocks.
- **Loading requests:** their computed tokens include the tokens being loaded, so those count as `filled` while the load is in flight.
- **Labels:** `kv_group` is the KV cache group index; the series appear after the first stats update.
- **Always registered:** token slots exist with or without a KV connector, so unlike connector-only metrics (e.g. `vllm:kv_load_failed_tokens`, registered only with `kv_transfer_config`) the gauge isn't gated.
- **Rust frontend:** its `SchedulerStats` decoder ignores unknown fields, so it is unaffected. It doesn't export this gauge yet.
- This is part of the same HBM KV cache observability effort as #64026 (`vllm:kv_load_failed_tokens`) and #64093 (`vllm:kv_admission_reserved_blocks`).
