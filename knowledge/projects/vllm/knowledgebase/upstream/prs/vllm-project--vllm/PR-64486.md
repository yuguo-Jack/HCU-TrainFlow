# [Mooncake] Move KV through a transfer backend and support TENT

[Upstream PR](https://github.com/vllm-project/vllm/pull/64486) · state: open · merged: False

## Original PR description

## Purpose

The Mooncake P2P KV connector reaches the Mooncake Transfer Engine directly: the worker creates the engine, registers memory, submits one synchronous batch per request and reads back a single status. That leaves no place to choose another engine and no place for an outcome per range.

This PR puts a backend interface between the connector and the engine, and adds a TENT (Transfer Engine NEXT) implementation behind it. TENT settles one task at a time on its own progress thread and can cancel what it started, which the connector can use without changing how it schedules blocks.

The interface half, with the Transfer Engine behind it and no behaviour change, is split out as #64363 so it can be reviewed and merged on its own; this PR contains both halves. No open PR adds a TENT backend to this connector.

## Part 1 — the backend interface (also in #64363)

`mooncake/transfer/` holds the interface: `rpc_port`, `register_regions`, `unregister_regions`, `transfer`, `shutdown`, and one event per range carrying `COMPLETED`, `FAILED`, `CANCELED` or `IN_FLIGHT`. `mooncake_connector.py` keeps its call sites but no longer names the engine, `TransferEngine` injection in tests goes through one factory, and `transfer/te.py` keeps the existing thread pools and semantics.

## Part 2 — TENT

- `transfer_engine: "tent"` in `kv_connector_extra_config` selects TENT; `"te"` (the default) selects the Transfer Engine. `MC_USE_TENT` and `MC_USE_TEV1` are honoured, and a configuration that contradicts them raises instead of silently preferring one.
- `transfer/tent_config.py` generates the TENT configuration: `p2p` metadata, only the configured transport installed, `device_name` as the RDMA whitelist, and a metrics port of `9100 + device_index` so ranks on one host do not collide. An optional `tent_config` mapping is merged over it.
- `transfer/tent.py` submits a request as one batch. Ranges contiguous on both sides are folded into one task up to 1 MiB, so a request of many small blocks does not pay one Python object per block, while the caller still gets one event per range. The wait polls the aggregated batch status and reads the per-task list only once the batch reports terminal.
- `shutdown` cancels outstanding tasks, drains, then closes the segments. A batch is freed only after every task settled, so the KV memory behind it cannot be released under a running transfer.
- Request metadata carries the engine kind and a wire version, so a Transfer Engine peer and a TENT peer are rejected with a clear error instead of failing inside the engine.
- An engine call that fails, a task the engine cancels, and a submission refused during shutdown are reported as failed ranges instead of an exception, so the sender decrements its request, marks the blocks failed and returns them for rescheduling. Only the requests that own a failed range are reported; the rest of the batch keeps its data.
- A range is failed only when TENT confirms the batch stopped. When it cannot — the engine refuses to cancel the batch, or its status cannot be read — the ranges are reported as in flight, the request keeps its blocks reserved and is dropped rather than rescheduled, and the worker refuses further transfers instead of reusing memory the engine may still be writing. The requests are named in the reply, so the decode side keeps them reserved too: no completion, no failure, and no block reported invalid by any peer of that request, even when a different peer answers later.

## Configuration

```json
{
  "kv_connector": "MooncakeConnector",
  "kv_role": "kv_producer",
  "kv_connector_extra_config": {
    "transfer_engine": "tent",
    "mooncake_protocol": "rdma",
    "device_name": "mlx5_0",
    "transfer_timeout_s": 60
  }
}
```

`transfer_timeout_s` bounds a transfer's wait for the engine (default 60, `0` waits forever). `tent_config` is deep-merged into the configuration vLLM generates, and `MC_USE_TENT` or `MC_USE_TEV1` selects `"tent"` when `transfer_engine` is unset.

## Testing

Two hosts, 8×H20 each, one `mlx5_0` HCA per host on the same fabric, Mooncake built from source with `-DUSE_TENT=ON` (and `-DUSE_CUDA=ON` for the GPU-memory rows), the `tent` module on `PYTHONPATH`. Both engines ran with stock parameters: TENT at its default `transports/rdma` block size and lane count, and no `MC_*` environment variable set for either engine. The measured path is one NIC and one host-to-host link.

What the numbers say:

- Per-range cost is what separates the two paths. The Transfer Engine takes the whole descriptor list in one call, while TENT builds one `tent.Request` per range: 815 µs for 1024 ranges, measured on the same host. Folding removes that cost wherever it applies.
- Reading one status per task had the same shape of cost, so a batch that reports `COMPLETED` now settles every range from that single status and only reads the per-task list when something failed. Together the two changes took the folding-disabled case from 5.61 ms to 3.76 ms against 3.22 ms for the same transfer driven through the engine directly.
- Given the same descriptor list and a larger payload, the two are level: 128 MiB runs at 7.04 ms on the Transfer Engine and 7.28 ms on TENT.
- Folding only applies when consecutive ranges are contiguous at both ends. The heterogeneous-TP shape is strided and cannot fold, which is where the widest gap sits (6.80 ms versus 2.16 ms).
- Concurrency degrades inside the engine, not in the adapter: the same 1024-range transfer driven directly through TENT measures 3.22 ms at one thread and 6.76 ms at ten, without any vLLM code in the path. The adapter tracks those numbers (2.42 ms and 7.68 ms when folded). The connector default is `num_workers = 10`, the worst shape measured here.
- At 400 MiB the pattern holds with the scale: folded TENT is level at one thread (21.66 ms against 21.90 ms) and 1.5× behind at eight (16.72 ms against 11.24 ms), while without folding it is 2.2× and 2.4× behind. Per-range cost is amortized by the larger transfer, so the gap narrows with payload size instead of widening.
- At 1 GiB both engines submit the same 1024 tasks; TENT is ahead at one thread (48.36 ms against 58.08 ms) and 1.8× behind at eight (51.58 ms against 29.25 ms). The single-thread advantage is the engine, the eight-thread deficit is the engine's task dispatch under contention.
- The strided shape is the widest gap at every size, and it is the shape heterogeneous TP produces: 2.5× behind at one thread and 1.9× at eight at 400 MiB, 3.1× at one thread at 32 MiB. No folding is possible there, so every range pays the Python construction cost and lands in the engine as its own task.
- Block size moves the other way: with 1 MiB ranges at eight threads, TENT is ahead of the Transfer Engine (17.34 ms against 19.71 ms), because both submit the same small descriptor list and TENT's request construction no longer dominates.

### End to end

One prefill and one decode process, each on its own host, connected by `examples/disaggregated/mooncake_connector/mooncake_connector_proxy.py`, model Qwen2.5-0.5B, RDMA, `num_workers = 2`. Both processes select the same engine, then `vllm bench serve` sends random prompts through the proxy. One run per engine:

| workload | engine | request throughput | output throughput | mean TTFT | median TTFT | p99 TTFT | mean TPOT |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 64 prompts, 1024 in / 128 out, concurrency 8 | TENT | 10.61 req/s | 1358 tok/s | 526 ms | 58 ms | 3839 ms | 1.73 ms |
| 64 prompts, 1024 in / 128 out, concurrency 8 | Transfer Engine | 10.45 req/s | 1337 tok/s | 540 ms | 61 ms | 3937 ms | 1.71 ms |
| 16 prompts, 8192 in / 128 out, concurrency 4 | TENT | 3.02 req/s | 387 tok/s | 1090 ms | 161 ms | 3842 ms | 1.63 ms |
| 16 prompts, 8192 in / 128 out, concurrency 4 | Transfer Engine | 2.91 req/s | 372 tok/s | 1151 ms | 157 ms | 4069 ms | 1.58 ms |

The two engines are indistinguishable at this scale: every difference sits inside the run-to-run spread of a single measurement, and neither engine moves the tail. A 0.5B model on H20 spends well under a millisecond per request in KV transfer against a prefill of tens to hundreds of milliseconds, so this table shows that the TENT path does not regress serving, and nothing about which engine is faster on the wire. The throughput tables above are where the transport moves data.

### Byte exactness

Every row above is verified by the receiving process after the transfer, block by block, over host memory and over GPU memory, and all runs report 0 mismatches. Two further checks cover the transport itself: 1 GiB payloads in the same shapes, and 256 MiB written then read back with sha256 comparison on both ends (`-DUSE_CUDA=ON` build for the GPU-memory case).

### Per-rank engines and metrics

Eight worker processes on one host, one engine each, ports `9100 + index`: every endpoint answers `GET /metrics` with HTTP 200. `TentMetrics` is a process-wide singleton, so one engine per process is the shape that gives each rank its own endpoint; more than one engine in a process shares the first one's port.

### Failure behaviour

A peer whose segment is gone before the transfer is submitted fails it: `transfer` returns immediately with `FAILED` for every range. Measured by killing the receiving process before the producer starts, for both RDMA and TCP.

A peer that disappears while a transfer is in flight is not reported as a failure: an 8 GiB RDMA write and an 8 GiB RDMA read both returned `COMPLETED` after the receiver exited 0 s and 0.15 s into the transfer. TENT settles a task on the sender side, and this adapter passes neither a deadline nor a notification to it, so there is no remote acknowledgement to lose. What the adapter does bound is its own wait: after `transfer_timeout_s` (60 s by default, `0` waits forever) it stops waiting, and the batch is reported as failed only if TENT confirms it stopped. Liveness of a request keeps relying on the connector's existing timeout and abort path rather than on the engine, and this PR does not claim delivery confirmation from TENT.

Model evaluation does not apply: this changes the transport path, not the model.

## Limits

- TENT requires a Mooncake build with `-DUSE_TENT=ON`. Wheels do not ship the `tent` module yet, so `transfer_engine: "tent"` fails at startup with the build instructions. Without a selection the connector uses the Transfer Engine as before.
- GPU memory needs that build to have `-DUSE_CUDA=ON` as well. Without it, registering a CUDA tensor crashes inside TENT's page prefaulting instead of reporting an error.
- `main` has the push direction only; the pull connector is not merged, so this PR covers the push path.
- TENT priority, deadlines and notifications are not used, because the connector has no source for per-request urgency today.
- At the shape the connector produces today — many small ranges, often not contiguous at both ends — TENT is slower than the Transfer Engine, and slower still with more than two concurrent transfers. This PR makes TENT selectable and correct at the range level; it does not make it faster at that shape.
- TENT's TCP transport is the RPC-based compatibility path; this PR targets RDMA. The high-performance transport upstream (`hp_tcp`) does not cover GPU memory in this release, and enabling it alongside `tcp` leaves the engine unavailable, which the startup check reports instead of running degraded.
