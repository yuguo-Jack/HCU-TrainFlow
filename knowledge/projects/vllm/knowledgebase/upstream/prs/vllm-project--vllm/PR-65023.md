# [Bugfix][Quantization] Quark: match exclude entries that name parameters

[Upstream PR](https://github.com/vllm-project/vllm/pull/65023) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Quark checkpoints may list excluded layers in `quantization_config.exclude` by parameter name (`<module>.weight`). vLLM matches excludes against module names, so those layers are built quantized and their unquantized weights fail to load. This PR maps such entries to module names when `QuarkConfig` is built. Related: #52649 (closed, model-side workaround for a different case).

## Claims

- Fixes loading `amd/Qwen3.8-27B-Quark-AWQ-MXFP4` with `--speculative-config '{"method":"mtp",...}'`. Before, the BF16 MTP head was built as MXFP4 and loading stopped with `AssertionError: self.data.shape == loaded_weight.shape`. With this PR it serves with MTP-3 on vLLM main (MI350P): GSM8K equals main without MTP, and the mean acceptance length is 3.4.
- Exclude entries ending in `.weight` / `.bias` now exclude their module. For fused layers (`qkv_proj`, `gate_up_proj`), the layer is excluded when all its shards are.
- `re:` patterns and entries that already name modules behave as before, and layers that are not excluded are still quantized.
- All three readers of the exclude list see module names: `QuarkConfig.get_quant_method_target`, `get_quark_ocp_mx_group_size`, and the Quark branch of `is_shared_expert_quant_fse_compatible`.

## Details

**Root cause.** The checkpoint keeps its MTP head in BF16. It lists the head by parameter name, next to entries that are module names or regexes:

```
"lm_head", "model.visual.blocks.0.attn.qkv", ..., "mtp.fc.weight",
"mtp.layers.0.self_attn.{q,k,v,o}_proj.weight", "mtp.layers.0.mlp.{gate,up,down}_proj.weight", ...
```

`should_ignore_layer` → `find_matching_patterns` → `is_equal_or_regex_match` compares each entry with the layer's module prefix, by exact equality or by `re:` regex. Fused layers are expanded through `packed_modules_mapping`, so `mtp.layers.0.self_attn.qkv_proj` is compared as `q_proj`, `k_proj` and `v_proj`. `mtp.layers.0.self_attn.q_proj.weight` never equals `mtp.layers.0.self_attn.q_proj`, so no MTP layer is excluded and the BF16 tensors do not fit the FP4 parameters.

**Why in `QuarkConfig.__init__`.** Three places read `quant_config["exclude"]` (listed under Claims), so mapping once at construction fixes all of them. It also runs before `apply_vllm_mapper`, so a model's rename mapper sees module names. `QuarkConfig` keeps a shallow copy of the config dict with the mapped list, and the checkpoint's own dict is not modified.

**Why not in the model.** `qwen3_5_mtp.py` already has format-specific workarounds: it forces `mtp.fc` unquantized for `modelopt_fp4`, and it turns off MTP quantization when a GPTQ `dynamic` config has a `-:...mtp...` entry. A third, Quark-specific branch there would fix only this model. Any Quark export that names excluded parameters, whatever the model or layer, has the same problem. The checkpoint already marks these layers as unquantized, so the Quark config should read the entries the way they are written.

**Limitations.**
- Only entries ending in `.weight` or `.bias` that are not `re:` patterns change.
- MoE `check_children` matches by prefix, so it handled `...experts.0.down_proj.weight` before and still does.
- Unchanged: `layer_quant_config` keys, the KV-cache config and online-quantization targets, none of which reads `exclude`.
- Not covered:
  - `DeepseekV4FP8Config.from_config` (V4 and V4.1) copies the raw Quark `exclude` into FP8 `ignored_layers` without building a `QuarkConfig`.
  - `models/inkling/amd/moe.py` checks for fused expert parameter names (`experts.w13_weight`). Those end in `_weight`, so this PR leaves them alone.

**Not a duplicate.** I searched open and closed PRs and issues for `quark exclude`, `quark mtp` and the assertion text, and found no PR that maps parameter-named Quark excludes to modules.
- #52649 (closed) bypassed Quark quantization in `qwen3_5_mtp.py` for MTP heads missing from `exclude`. It was closed in favour of a fix on the Quark side.
- #53248 (open) changes the shared-expert FSE check to use `should_ignore_layer`. It reads the same list, so it benefits from this PR and does not conflict with it.
- #61770 (open) remaps MTP layer indices (`mtp.layers.0` → `mtp.layers.48`) for Qwen4Exp, which is a different problem.
