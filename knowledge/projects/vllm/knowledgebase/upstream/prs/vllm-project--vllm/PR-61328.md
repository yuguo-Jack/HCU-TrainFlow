# [Frontend] Let an unset `--tool-strict-level` fall back to the tool parser's default

[Upstream PR](https://github.com/vllm-project/vllm/pull/61328) · state: closed · merged: True

## Original PR description



## Overview

An unset `--tool-strict-level` now falls back to the tool parser's default level, while an explicit value, `auto` included, always wins. Both frontends resolve the level the same way, and the Rust frontend gains the per-parser default that #56403 added on the Python side for `glm47`.

## Claims

- Resolution on both frontends: explicit `--tool-strict-level` > the tool parser's default level > `auto`.
- `--tool-strict-level auto` now overrides a parser default. Before, it could not be told apart from an unset option, so it left GLM-4.7 at `function`.
- Rust: `ToolParser::default_tool_strict_level` / `UnifiedParser::default_tool_strict_level` (default `Auto`; `CombinedParser` forwards its tool parser's), and `glm47` defaults to `Function` like its Python counterpart. Rust `glm47` therefore now constrains non-strict `tool_choice="auto"` requests by default.
- No change when the option is unset, except that Rust `glm47` now follows Python.

- Python: the new `test_glm47_default_level_applies_only_when_the_level_is_unset` goes through `ParserManager.get_parser` and fails for both cases without the Python change. Locally, 29 tests in these files fail identically on `main` and on this branch because my environment has xgrammar 0.2.2 instead of the pinned 0.2.8 (missing `mimo` / `deepseek_v4_1` builtins); everything else passes. `tests/entrypoints/launchers/test_cli_args.py` was not runnable in my environment, so CLI parsing was checked directly: unset → `None`, `function`/`auto` parse, unknown values are rejected.
- Render check with `zai-org/GLM-4.7` (engine-free render servers, one non-strict tool), whether the request gets a grammar:

  | Server | `tool_choice="auto"` | `tool_choice="required"` |
  | --- | --- | --- |
  | `vllm-rs render`, `glm47`, unset | grammar | grammar |
  | `vllm-rs render`, `glm47`, `--tool-strict-level auto` | none | grammar |
  | `vllm-rs render`, `glm47`, `--tool-strict-level function` | grammar | grammar |
  | `vllm-rs render`, `qwen3_coder`, unset | none | grammar |
  | `vllm launch render`, `glm47`, unset | grammar | grammar |
  | `vllm launch render`, `glm47`, `--tool-strict-level auto` | none | grammar |

- Not run: GPU serving or model evaluation. The change only selects which existing grammar a request gets.

## Details

- Python: `FrontendArgs.tool_strict_level` defaults to `None` and is passed through the serving layers as `str | None`. `Parser.tool_strict_level` is `None` when unset, and `_apply_structural_tag` falls back to `ToolParser.default_tool_strict_level`, which is now `AUTO` by default instead of `None`.
- Rust: the CLI and bootstrap JSON arg (`vllm serve` forwards only non-default args, so an unset option arrives absent) are `Option<ToolStrictLevel>`, as are `ChatRequestProcessor`, `NewChatOutputProcessorOptions`, and the server/render configs. `DefaultChatOutputProcessor` resolves the level once the parser is chosen, mirroring the Python fallback.
- At `function`, Rust `glm47` uses the xgrammar `glm_4_7` builtin with broad arguments, while Python uses its shallow argument tag (#56403). That difference predates this PR; this PR only aligns when the level applies.
- Not a duplicate: no open PR touches `--tool-strict-level` resolution or Rust parser default levels (searched open PRs for `tool-strict-level`).
