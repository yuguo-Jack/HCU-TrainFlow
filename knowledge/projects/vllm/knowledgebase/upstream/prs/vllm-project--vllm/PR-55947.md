# [Feature][Spec Decode] Add Uno shared-model drafting with a draft-only LoRA adapter (Model Runner V2)

[Upstream PR](https://github.com/vllm-project/vllm/pull/55947) · state: open · merged: False

## Original PR description

**TL;DR.** Speculative decoding with no separate draft model: the target model drafts its own candidates through a small LoRA adapter, and vLLM's native rejection sampler verifies them. Measured against plain vLLM on the same card, same client and same serving shape: **2.1 to 2.4x single-stream on a GB10 and 1.7 to 1.9x on an RTX 3090** with this implementation, and **2.6x on an H100** with our earlier Model Runner V1 build of the same design, which this implementation beats in every cell measured side by side. It stays ahead under load (1.1 to 1.6x at four and sixteen streams on the GB10; 2.2x at eight streams and 1.7x at 32 on the H100). Output is lossless: greedy tokens match plain wherever plain reproduces itself, sampled-distribution tests pass, GSM8K is within one answer of plain. Uno stays out of vLLM's core files: outside its own modules the PR adds a two-line hook call in the V2 model runner, a five-line request check, and configuration. Tested on NVIDIA Ampere, Hopper (FlashAttention 2 and 3) and Blackwell, single GPU and tensor parallel, and on an AMD Radeon AI PRO R9700 (ROCm, TRITON_ATTN). The reference SGLang implementation lands within 3% of the H100 build at every concurrency.

## Purpose

Adds native Uno self-drafting through `speculative_config.method="uno"` for Model Runner V2. One target model
produces `K` draft candidates per request from one base-weight seed row and `K-1` noise rows routed through the Uno
adapter; verification uses the native MRV2 rejection sampler. This follows the MRV2 direction agreed in
[RFC #55267](https://github.com/vllm-project/vllm/issues/55267). The earlier revision of this PR targeted Model Runner V1; this revision replaces it. Current head: reworked on 2026-10-11 so Uno stays out of vLLM's core files, on main at `ff440c7805`, then extended to AMD ROCm in Uno's own files; see the revision history below.

The change includes:

- A native MRV2 speculator that shares the target model, attention layers and KV cache with the drafter and applies the
  adapter only to noise rows, through the LoRA manager's public adapter-mapping call.
- Fused draft-input preparation in one kernel; the prompt length and the request count are runtime values, so it compiles once.
- Native request state, Gumbel sampling, verification, async scheduling and draft CUDA graphs; K lookahead KV slots
  with correct ownership at full acceptance, block boundaries, preemption and prefix-cache reuse. Near a request's length
  or context limit, the scheduler's existing per-request spec-token cap and lookahead cap apply; Uno adds no scheduler code.
- Startup and request validation (fail-closed for KV transfer, KV-sharing fast prefill, which would wrap the shared target and draft layers incorrectly and hand verification wrong prompt logits, pipeline/data/context parallelism, unsupported attention layouts, request-specific LoRA; tensor parallelism is supported and the draft uses the target's degree), a Qwen3-8B recipe ([the Uno docs page](https://github.com/brntech/vllm/blob/uno-core-upstream/docs/features/speculative_decoding/uno.md)), CPU regression tests and end-to-end model tests.

`scheduler.py`, `async_scheduler.py`, `sched/output.py` and `warmup.py` are unchanged. AMD support adds no line outside Uno's own files.

**Platforms.** Uno runs on NVIDIA GPUs with the `FLASH_ATTN` or `TRITON_ATTN` attention backend, and on AMD ROCm GPUs with `--attention-config '{"backend":"TRITON_ATTN"}'`. It restricts the attention backend, not the card: it admits exactly the backends its tests run, and any other attention backend (FlashInfer included), or on ROCm an unset backend, is refused when the config is validated, before weights load. A backend must also pass the capability checks Uno already had (native draft decode metadata updates; graph support for draft graphs), and `load_model` re-checks the backend each layer built. On ROCm, Uno has been tested on the Radeon AI PRO R9700 (gfx1201); `TRITON_ATTN` on NVIDIA on one RTX 3090 (sm_86).

Initial scope is NVIDIA GPUs (single GPU and tensor parallel) and AMD ROCm GPUs (tested single-GPU on the Radeon AI PRO R9700), text-only decoder models with one homogeneous full-attention KV group, the attention backends above, Model Runner V2 with async scheduling. A draft decode graph is captured only when some `cudagraph_capture_sizes` entry is at most `max_num_seqs * K`. The documented adapter is the original [`s-sahoo/uno-qwen3-8B`](https://huggingface.co/s-sahoo/uno-qwen3-8B) for `Qwen/Qwen3-8B`.

Uno is introduced in [Unlocking Lossless Speedups in LLMs via Discrete Diffusion](https://arxiv.org/abs/2609.04010); the method and adapter are credited to its authors. Development was assisted by AI tools, disclosed in the commit
trailers. A ready-to-run container of this revision is published at [github.com/brntech/vllm-uno](https://github.com/brntech/vllm-uno) (release v0.2.0, image `ghcr.io/brntech/vllm-uno:0.2.0`).

## Test Result

### Throughput over plain vLLM

Every ratio is Uno divided by plain vLLM measured on the same card with the same client, model, precision and serving shape, in output tokens per second. GB10 and RTX 3090 figures are medians of three measured repeats after one warm-up; the H100 study reports mean per-prompt throughput at one stream and means of three warm batches at eight and 32 streams.

| Card | Workload | 1 stream | 4 / 8 streams | 16 / 32 streams |
|---|---|---:|---:|---:|
| H100, earlier optimized MRV1 build (Qwen3-8B bf16, controlled, prefix caching off) | math | **2.58x** | 2.20x (8) | 1.74x (32) |
| GB10, this line at `49ffe316bb` (Qwen3-8B bf16, production shape) | short chat | **2.36x** | 1.31x (4) | 1.14x (16) |
| GB10 | long prompts | **2.21x** | 1.44x (4) | 1.15x (16) |
| GB10 | mixed | **2.06x** | 1.58x (4) | 1.12x (16) |
| RTX 3090, head `5da19391` (Qwen3-8B bf16, production shape) | short chat | **1.65x** | 1.18x (4) | 0.74x (16) |
| RTX 3090 | long prompts | **1.71x** | 1.13x (4) | 0.77x (16) |
| RTX 3090 | mixed | **1.85x** | 1.46x (4) | 0.72x (16) |

The H100 row is our earlier optimized Model Runner V1 implementation of the same design, measured in
[the study that IFM cites](https://doi.org/10.5281/zenodo.22652610) (single-prompt operating points on the same card: math 375 tokens/s, code 306, prose 212). The GB10 rows are this MRV2 line at `49ffe316bb` and the RTX 3090 rows head `5da19391`, both under one identical production shape (K=8, async scheduling, ctx 4096, `max_num_seqs` 16, 2048 batched tokens, 2 GiB KV, prefix caching, 128 output tokens). On the same GB10, with the optimized MRV1 release measured as a third arm, MRV2 exceeded it in all nine cells, by 1.03 to 1.31x. Uno is ahead wherever the card has compute headroom to verify drafts in: at four streams on every card, at sixteen on the GB10, at 32 on the H100. The reference SGLang implementation, measured on the same H100 against the same plain server, lands at 2.60x / 2.24x / 1.79x, within 3% of the H100 build at every concurrency.

### First-token latency

At head `5da19391`, same card, same client, median of three repeats: single-stream steady first token Uno 28.0 / 28.2 / 30.5 ms against plain 26.8 / 26.8 / 29.1 ms (short / mixed / long). The draft-input kernel takes the prompt length and the request count as runtime values, so it never recompiles for a new length or batch size. Since the rework there is no startup warmup of the draft sampler, so the first request compiles its sampler kernels.

### Lossless output

**Greedy exact-token matrix.** Seven K=1/K=8 cases (eager, CUDA graphs, prefix caching, dual-stream LoRA) compare Uno's greedy tokens with the plain engine's, each with a same-arm plain-vs-plain control. A first divergence is excused only where the plain engine's own top two raw logits are one bfloat16 step apart at that position, at most one prompt per batch, and every excused position is printed. Each case prints an instrument receipt (card, compute capability, graph mode, attention version, control coordinates, tie positions). At the current head the matrix also asserts that the attention implementation built is the requested backend's. RTX 3090, `TRITON_ATTN`: 7/7, every batch exact in tokens and text, no tie excused. RTX 3090, `FLASH_ATTN`: 7/7, exact except one excused tie in each of two cases (raw-logit gaps 0 and one bfloat16 step, at positions earlier rounds also met). R9700, `TRITON_ATTN`: 7/7, exact, no tie excused. Earlier heads: 7/7 on the GB10 and on the H100 under both FlashAttention 3 and 2.

**Context limit.** A nightly test serves four concurrent requests to `max_model_len` at K=8 and audits every draft KV slot against the limit and the request's block-table row; all four finish at exactly `max_model_len` with tokens and text equal to the plain engine's, and no draft row writes a slot at or past the limit.

**Sampled output.** Sampled-distribution permutation tests (256 samples for each of three prefixes, 16 tokens) pass for both Uno arms and for the independent plain-repeat control; raw greedy matches are 7/8 for both Uno arms against plain and 7/8 for plain against itself on a same-server repeat. GSM8K-128 (five-shot, temperature zero): plain 119/128, Uno MRV2 118/128, optimized MRV1 117/128.

### Request features under speculative decoding

Structured output (valid JSON from a `json_schema` request), logprobs, repetition and presence penalties and `ignore_eos` are all served with Uno drafting active. Min-p and logit bias are refused at admission by vLLM's general spec-decode guard, the same one EAGLE-3 hits. A request-specific LoRA adapter is refused before it is queued; a request can never select Uno's own adapter, including through a prebuilt `EngineCoreRequest` (a nightly test checks both, with exact outputs and the engine serving on).

### Continuous batching under KV pressure

The survivor test pins a 69-block KV pool, admits a seed request, two long peers and an abort peer, and asserts that a long peer is preempted while still generating and that its tokens after resumption equal its solo run. The pool is sized to force the crossing even when one long peer stalls at its admission footprint. It passed on the GB10, the H100 NVL (FlashAttention 3 and 2) and, at the current head, the RTX 3090 and the R9700. The test records the preemption at the scheduler's own event, resolves requests by the scheduler's internal ids, and writes its receipt to a file, so a non-firing run fails with a trace instead of skipping.

## Not in this patch

Three optimisations are left out to keep changes to vLLM's core files minimal. Each would first need a small generic hook, and can follow as a separate PR if wanted:

- **Early length-tail policy:** stop drafting on a step that may be a request's last, saving `K` lookahead KV rows near its length or context limit. Needs a per-request "next draft width" that a speculator can set.
- **Startup draft warmup:** compile the draft sampler's kernels at startup instead of on the first request. Needs a speculator warmup hook beside the existing dummy-propose warmup.
- **Cached LoRA metadata:** reuse precomputed adapter mappings for the draft rows instead of rebuilding them every step. Needs a public way to reuse a LoRA mapping.

Together they are worth about 2% at 16 concurrent requests on an RTX 3090 (Qwen3-8B, K=8, 16 greedy chats × 256 tokens, 3 repeats: 710.7 vs 726.2 tokens/s); single-stream is unchanged within noise (103.6 vs 104.4).

## Revision history

**2026-10-11, AMD ROCm.** Uno runs on AMD ROCm GPUs with `TRITON_ATTN` (tested on the Radeon AI PRO R9700, gfx1201), and on NVIDIA with `TRITON_ATTN` as well as `FLASH_ATTN`. It admits exactly the attention backends its tests run: any other backend, FlashInfer included, and an unset backend on ROCm, are refused when the config is validated, before weights load. Only Uno's own files change; the core footprint is unchanged. The greedy matrix asserts the attention implementation it built, and the survivor test no longer holds its in-process engine across the runner exit (only ROCm's teardown memory wait caught that reference).

**2026-10-11, rework.** Uno now stays out of vLLM's core files. `scheduler.py`, `async_scheduler.py`, `sched/output.py` and `warmup.py` are back to main; the V2 model runner change is a two-line call to a generic `set_lora_manager` speculator hook (a no-op on `BaseSpeculator`), and Uno's serving checks moved next to the method. Dropped: the early length-tail policy (the scheduler's existing per-request cap and lookahead cap keep the context limit correct, checked by a new nightly test that audits every draft KV slot), the startup draft warmup (the draft-input kernel takes the request count as a runtime value instead), and the cached LoRA-metadata restore (draft rows use the LoRA manager's public mapping call). A request-specific LoRA adapter is refused in the input processor, and no request can select Uno's own adapter. The greedy matrix counts ties in bfloat16 steps of the raw logits. The Uno CI job triggers on spec-decode paths only; the longer end-to-end tests run nightly.

**2026-10-10, merge of main `ff440c7805`.** Conflict resolved in the V2 model runner: #60754 moved the drafter hidden-state helper to `spec_decode.utils.get_drafter_hidden_states` and renamed `dp_sync` to `dp_sync_state`; Uno's proposal path and `propose()` follow both.
