# [Bugfix][KV Offload] Emit self-describing offload events for Mamba checkpoints

[Upstream PR](https://github.com/vllm-project/vllm/pull/62538) · state: closed · merged: False

## Original PR description



## Overview

With `self_describing_kv_events` on, the offloading connector publishes offloaded Mamba/SSM checkpoints as `block_size=0` placeholders. This PR emits real `BlockStored` events for them, describing only the block that holds the recurrent state, so KV-aware routers can see where a hybrid prefix is reusable.

Fixes #62510. Follow-up to #51243, which left Mamba groups on the placeholder.

## Claims

- An offloaded Mamba checkpoint, whether a complete chunk or a partial recurrent tail, produces a `BlockStored` event with:
  - one hash, at the state boundary;
  - its parent hash;
  - the tokens of that block;
  - the group's block size;
  - `group_idx` and `kv_cache_spec_kind="mamba"`.
- `BlockRemoved` for that key sends a removal for the same single hash. This needed no new code.
- Sliding-window and chunked-local attention groups still emit the placeholder. Full-attention events are unchanged.
- No scheduler logic changes. The diff is limited to `OffloadingEventsTracker` (+40/−14 lines in `events.py`), plus tests and one docs sentence.

## Validation

**End to end, before and after, on an L4.** I ran `Qwen/Qwen3.5-4B` with prefix caching on, which puts Mamba in align mode with 528-token blocks, and the CPU `OffloadingConnector`. I sent a ~5.9k-token prompt and a fork of it, then read every event back through the publisher's replay socket. Both runs use base `aa3564ceef`; the patched run adds this diff on top.

| CPU `BlockStored`, Mamba groups 0–2 | `main` | this PR |
|---|---|---|
| `kv_cache_spec_kind` | `None` | `mamba` |
| `block_size` | `0` | `528` |
| `block_hashes` / `token_ids` | 1 / 0 | 1 / 528 |
| `parent_block_hash` | `None` | set |
| tracker "emitting a placeholder payload" warning | logged | not logged |

In both runs, the Mamba event's hash equals the attention group's (group 3) hash for the same 528-token block. That is the boundary where the engine actually holds SSM state. The 11 full-attention CPU events are the same set in both runs, and the GPU events have the same counts and shapes.

## Details

**Root cause.** `get_sliding_window_size_in_chunks` returns `1` for `MambaSpec`. Each of the tracker's `record_*` methods bailed out on `sliding_window_size_in_chunks is not None`, so no metadata was ever captured for Mamba groups, and `_take_stored_event` fell back to `_placeholder_stored`.

**Fix.** A Mamba group is identified by the `kv_cache_spec_kind` already stored on `GroupOffloadConfig.kv_event_group_spec`. Only the other windowed groups now take the placeholder path. In `_build_event_metadata` and `_record_partial_tail`, a Mamba entry is trimmed to the final block, reusing the existing `resolve_block_hashes` view. That gives one hash, its parent and that block's tokens.

**Why only the final block.** A Mamba chunk holds a single recurrent state, valid only at the chunk's end. Announcing every block hash in the chunk, the way full-attention events do, would claim reuse at positions where no state exists. That is the overestimation #62510 reports. The partial-tail event uses the same shape as `BlockPool`'s GPU partial-block event: one hash, its parent and that hash block's tokens.

**Changed test.** `test_partial_tail_store_uses_attention_and_recurrent_cow_sources` asserted the old placeholder for the recurrent group. It now asserts the new event. The recurrent event's hash is the attention event's last hash, and its parent is the attention event's second-to-last hash.

**Known limitation.** `_sliding_window_lookup` doesn't take a request context, so it can't backfill metadata. A Mamba checkpoint promoted from a secondary tier that this process never stored or saw as a hit (for example after a restart) still gets a placeholder. This is the same caveat the docs already describe for promotions.

**Not a duplicate.** #62510 has no comments, no assignee and no linked PR. Keyword searches found no open PR touching `offloading/events.py`. #62159 changes GPU-side reuse events in `kv_cache_manager.py`, and #57789 adds publisher snapshots; neither overlaps.
