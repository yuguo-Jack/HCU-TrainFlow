# [Bugfix][Frontend] Allow opt-in prompt id reuse without a KV connector

[Upstream PR](https://github.com/vllm-project/vllm/pull/62333) · state: open · merged: False

## Original PR description

Fixes #62307.

## Why

The earlier connector gate closed the prompt-substitution hole by rejecting every connector-less request, but that also rejected valid aggregated deployments. Routers such as llm-d-router forward the original `messages` together with `prompt_token_ids` even when no KV transfer connector is configured, so those requests need the engine to ignore the forwarded ids and render the messages rather than return HTTP 400.

Deployments that intentionally trust a pre-rendered prompt still need a way to reuse the ids without a connector. This PR makes that an explicit server opt-in instead of an implicit consequence of attaching an arbitrary id list.

## What changed

- On a server without a KV connector, the default path now consumes `prompt_token_ids` and any accompanying `prompt_features`, then renders `messages` through the normal chat path. Ignored ids do not trigger shape or vocabulary errors, and no half-forwarded payload remains in `kv_transfer_params`.
- New `--enable-prompt-token-ids` flag preserves direct id reuse without a connector for trusted deployments. The flag is wired through `ModelConfig`, `EngineArgs`, CLI parsing, and model-config construction. A configured KV connector keeps the existing behavior without needing the new flag.
- Both `preprocess_chat` and the Harmony branch continue through the same `_reused_prompt_token_ids` helper, so the default and opt-in policies apply consistently.
- The disaggregated-prefill documentation now describes the aggregated default, the explicit opt-in, and the trust requirement for ids that must match the tokenizer and rendered prompt.

`prompt_features` itself is being implemented separately in open PR #64721. This PR does not claim multimodal-feature support; it consumes the paired keys on the default render path so the behavior remains compatible with that work.

## Tests

Red-green evidence on the previous implementation:

- `test_chat_kv_transfer_prompt_token_ids_ignored_without_kv_connector` and `test_chat_kv_transfer_prompt_token_ids_opt_in_without_kv_connector` both failed with the old connector-required `VLLMValidationError`: 2 failed, 223 deselected.
- `test_enable_prompt_token_ids_cli` failed because `EngineArgs` had no `enable_prompt_token_ids` field.
- After the implementation, the focused default, opt-in, CLI, connector, validation, echo, non-text, and direct Harmony reuse cases all pass.

Final verification on merge head `814c4d6fa7b58ce2321ff20ed9de4939f957a24d`:

- 317 passed, 26 deselected: 200 serving-chat unit tests and 117 EngineArgs tests. This includes the 26 focused cases.
- `ruff check`, `ruff format`, the oldest-supported-Python MyPy hook, and `git diff --check` passed.
- The other touched-file hooks that ran in the pre-commit pass also passed, including typos and markdownlint.

The two real GPT-OSS serving classes and the separate `TestServingChatWithHarmony` class were excluded from the local unit run because their external serving or slow initialization paths did not complete in this environment. The direct Harmony reuse tests are included in the 317 passing tests. `test_multi_node_world_size_includes_pcp` was also excluded after the same PCP/model-runner failure reproduced on an independent pristine `HEAD` source tree, confirming it is not introduced by this PR.

Validation used a Linux CPU container and the real renderer implementations with test doubles. No GPU, real model-serving, or hosted integration result is claimed.

I agree with the bug in #62307  but I don't think `kv_transfer_config` is the right approach. [llm-d-router#3706](https://github.com/llm-d/llm-d-router/pull/3706) forwards `prompt_token_ids` from the EPP on aggregated deployments too. Those have no KV connector which means every forwarded request would get a 400.

Two changes would cover both cases:
- Without a connector, ignore the IDs and render `messages` instead of returning a 400. This is similar that what we do for `echo` and non-text content. That closes the hole and router requests still work.
- Add an opt-in flag for deployments that want the IDs honored without a connector. `--enable-prompt-token-ids` was already suggested on #55770.

#64721 sends `prompt_features` through this same helper, so whatever we pick needs to cover that as well.
