# [Bugfix][Kernel] Register int8 scaled_mm as a custom op

[Upstream PR](https://github.com/vllm-project/vllm/pull/57331) · state: closed · merged: True

## Original PR description

### What is wrong

`TritonInt8ScaledMMLinearKernel.apply_weights` calls `triton_scaled_mm` directly at line 134. That function is plain Python. It picks a tile shape from `triton.next_power_of_2(M)`, does some reshapes and asserts, then launches a Triton kernel.

There is no custom op wrapper around it, so dynamo and inductor trace straight into all of that. The fp8 block scaled path a few lines below in the same file does have one, registered as `w8a8_triton_block_scaled_mm_func`. So fp8 is opaque to the compiler and int8 is not.

### What it costs

Measured on gfx1151 (Radeon 8060S, Strix Halo), vLLM 0.28.0 built for ROCm 7.2. One linear layer at the fused gate_up shape N=34816 K=5120, one token of decode so M=1:

```
eager, called directly              1.321 ms    134.9 GB/s
torch.compile, called directly     38.072 ms      4.7 GB/s
torch.compile, through a custom op  1.314 ms    135.6 GB/s
```

End to end on a Qwen3.5 27B model quantized to int8 w8a8 with AMD Quark. Same server flags both runs, default cudagraph mode, the patch is the only difference:

```
                  single stream    4 concurrent
before             2.17 tok/s        8.40 tok/s
after              5.15 tok/s       19.37 tok/s
```

Three runs each way. Before: 59.10, 59.09, 59.11 seconds. After: 24.88, 24.86, 24.88 seconds.

The same model in bf16 is not affected either way, 4.10 tok/s compiled against 4.04 eager, so this is specific to the int8 path.

No setting recovers it. `--enforce-eager` is the only mitigation and it still lands at 5.02 tok/s, below the patched number, and it turns off compilation for the rest of the model.

### The fix

Register `int8_scaled_mm_func` with a fake impl and call that from `apply_weights`. This mirrors what `w8a8_triton_block_scaled_mm_func` already does a few lines below.

Output is unchanged. `torch.allclose` against the unpatched kernel passes at rtol 1e-2 atol 1e-2, and generation on the 27B model reads the same as before.

### Testing notes

I only have gfx1151, so that is the only hardware this was measured on. On CUDA the cutlass int8 kernel is normally picked ahead of the Triton one, so fewer users reach this path there and I could not measure it. The change is platform neutral. It adds a wrapper and does not touch the kernel or the tile selection.

This is int8 w8a8 only. AWQ, GPTQ and compressed-tensors W4A16 go through Marlin, `awq_triton` or `wNa16` and are untouched.

### Repro without a large model

```python
import torch
from vllm.model_executor.layers.quantization.compressed_tensors.triton_scaled_mm import triton_scaled_mm

N, K = 34816, 5120
w = torch.randint(-127, 127, (K, N), dtype=torch.int8, device="cuda")
ws = torch.rand(N, 1, dtype=torch.float32, device="cuda")
x = torch.randint(-127, 127, (1, K), dtype=torch.int8, device="cuda")
xs = torch.rand(1, 1, dtype=torch.float32, device="cuda")

c = torch.compile(triton_scaled_mm, dynamic=True, fullgraph=True)
c(x, w, xs, ws, torch.bfloat16, None)
```

Time the compiled call against the plain one. On gfx1151 the compiled one is about 29 times slower.

- afierka-intel · comment · 2026-10-13T10:13:54Z · [source](https://github.com/vllm-project/vllm/pull/57331#issuecomment-6143294731)

Same fix as #61259 (which I'm closing in favour of this PR), with XPU evidence that this change is needed there too. On Intel XPU the failure is not a perf cliff but a startup crash.

**XPU startup crash fixed by this change.** On XPU the int8 linear kernel list is Triton-only and `VLLM_TRITON_USE_TD` is auto-on. With the inline `triton_scaled_mm` call, `vllm serve` for an INT8 W8A8 compressed-tensors model dies in `profile_run`:

```
AssertionError: cannot extract sympy expressions from TreeSpec(...)
```

Dynamo traces the launch inline, the graph then contains the tensor-descriptor allocator setup (`set_alloc_*` attributes plus an `invoke_leaf_function` node carrying an input `TreeSpec`), and `split_module` in `split_graph` cannot handle it. An opaque custom op keeps all of that out of the graph.

Setup: Intel Arc Pro B60 (1 card), `vllm/vllm-openai-xpu:nightly` (vLLM 0.31.1rc1.dev23, torch 2.14.0+xpu, triton 3.8.0), `RedHatAI/Meta-Llama-3.1-8B-Instruct-quantized.w8a8`, `vllm serve ... --max-model-len 4096 --kv-cache-memory-bytes 4G`, default compile.

| Tree | Result |
|---|---|
| `main` @ e0317b28ce | crash in `split_graph`, `TreeSpec` assertion |
| `main` + an opaque `triton_scaled_mm` op (same change as here, op named `triton_scaled_mm_func`) | server starts, `/v1/completions` returns text, no `TreeSpec` |

**Perf (same card, random 512 in / 128 out, 100 prompts, concurrency 32, 3 runs after warmup, seed 42, median output tok/s):**

| Config | inline call (`main`) | opaque op |
|---|---|---|
| compile, `VLLM_TRITON_USE_TD=0` (the only setting where `main` starts) | 16.4 | 26.3 |
| `--enforce-eager`, `VLLM_TRITON_USE_TD=1` | 125.6 | 126.0 |
| compile, `VLLM_TRITON_USE_TD=1` (default on XPU) | does not start | 129.1 (200 prompts) |

So the op costs nothing in eager and helps compiled, in line with the ROCm numbers in the description.

**Tests I'd like to contribute** (I can push them to this PR if you give me access, or open a follow-up PR on top once this merges), written against `triton_scaled_mm_func` and trivially renamed to `int8_scaled_mm_func`:
- the op under `torch.compile(fullgraph=True)`, bit-exact against the eager launch;
- `TritonInt8ScaledMMLinearKernel.apply_weights` under compile, checking the compiled graph contains the opaque op. These 8 cases fail on `main` (graph has no custom op) and pass with the op;
- the fake impl against the real op's output shape/dtype under `FakeTensorMode`;
- a recorder that asserts the TD kernel path was actually launched (guards against silent fallback);
- a Buildkite step running `tests/kernels/quantization/test_triton_scaled_mm.py` on Intel GPU (today only the directory-wide CUDA/AMD shards touch it).

Branch with the commits: https://github.com/afierka-intel/vllm/tree/afierka/xpu-int8-scaled-mm-td-compile

Caveat: one model, one card, and only the Llama arm has accuracy checks (gsm8k, TD on = TD off).

Also worth noting for the description: CUDA selects the Cutlass int8 kernel first, but `--linear-backend triton` filters the list down to the Triton kernel, so this path is reachable on CUDA with that override.
