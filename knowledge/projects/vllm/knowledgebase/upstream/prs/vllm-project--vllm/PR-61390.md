# [Bugfix][KV Offload] Treat an already-published fs block as stored

[Upstream PR](https://github.com/vllm-project/vllm/pull/61390) · state: closed · merged: True

## Original PR description

## Overview

The `fs` secondary tier fails a whole store job with `EEXIST` when another writer has already
published the same block. Related to #61373 (the second, write-side bug in that report).

## Claims

- A store job that loses the publish race on a content-addressed block is reported successful
  instead of being counted as a `cascade_job_failure`.
- The same guard is applied in both implementations of the primitive, the Python `_store_block`
  and the `fs_io_C` one, so behaviour does not depend on whether the extension is built.
- Nothing else changes: the bytes on disk, and every other errno, behave as before.

## Validation

- New unit test `test_store_accepts_block_published_by_another_writer` in
  `tests/v1/kv_offload/tiering/test_fs_tier.py`: it stores a block, then hides it from the
  existence check and fails the publish with `EEXIST`, which is what losing the race looks like.
  It asserts the job result is a success, that no temp file is left behind, and that the
  published bytes are untouched. Without the guard `_store_block` raises and the job is reported
  failed. The injected `EEXIST` is unavoidable here, since `rename(2)` on a local POSIX
  filesystem replaces the destination and never reports it; the test follows the patching style
  already used in that file.
- pre-commit hooks on the changed files: `ruff check`, `ruff format` and `clang-format` are
  clean.
- Not a model-affecting change: this path only decides whether an already-present KV block file
  counts as a store failure, so there are no eval numbers to report.
- Not duplicating an existing PR: I searched the open PRs for `61373 in:body`, for `fs_io`, and
  for fs-tier store keywords, and found nothing covering this.

## Details

Root cause: `_store_block` writes the block to a temp file and publishes it with `rename(2)`. It
skips the write entirely when the destination already exists, but that check and the rename are
not atomic, and with several engine instances sharing one `root_dir` the window between them is
routinely lost. POSIX `rename` would replace the destination silently, but several shared
filesystems (the report is on 3FS over FUSE) return `EEXIST` instead, and that error propagated
out of `batch_store_block` and failed the batch at the first such block.

Block file names are the content hash, so a destination that exists already holds these bytes:
there is nothing left to do and the store has succeeded. Both implementations now drop the temp
file and return success for `EEXIST` from the publish step only. Every other errno still fails
the job, and the `O_EXCL` temp-file open is deliberately left outside the guard so a genuine
temp-path collision remains an error rather than a silently skipped block.

I did not touch the promotion symptom that #61373 leads with, since I could not establish it from
the code. One thing worth noting for whoever picks that up: the two metrics quoted in the report,
`chunk_queries` and `lookup_async_delay_seconds`, are both recorded when an async lookup resolves
to a miss as well as to a hit (`_observe_resolved_lookup` in
`vllm/v1/kv_offload/tiering/metrics.py`), so they do not on their own show that the block was
found. `chunk_hits` is the one that separates the two cases.

- sivabreddy · comment · 2026-10-26T05:53:15Z · [source](https://github.com/vllm-project/vllm/pull/61390#issuecomment-6409248693)

As offered earlier, I ran this fix on the setup where I saw the `EEXIST`: two vLLM instances on two hosts, one shared `fs` tier `root_dir` on a 3FS FUSE mount. Thanks again @shreyanshj10. The rename case is handled, but on 3FS the failing steps are two others in `_store_block`, so the store jobs still fail. Details below.

**Setup:** per-commit wheels one commit apart, `fa2881ed1` (parent) and `1757f6720` (this PR); Llama-3.1-8B, block size 64, `TieringOffloadingSpec` with CPU 10 GiB + one `fs` tier; `PYTHONHASHSEED=123` on both; 3-4 rounds × 16 new prompts of ~8.66K tokens, each prompt sent to both instances at the same moment; a new `root_dir` per run.

| Run (C++ store path) | `[Errno 17] File exists` store failures (A / B) |
|---|---|
| `fa2881ed1`, round 1 / round 2 | 8 / 11, 7 / 14 |
| `1757f6720`, round 1 / round 2 | 9 / 12, 10 / 16 |

No request errors and the same output on both instances in all runs; the second instance loads the first one's blocks from the `fs` tier. A failed store only means that block is not written.

**Which step fails.** On this mount `rename()` onto an existing file replaces it (checked directly), so the case of this PR does not occur. With the Python store path (I hid `vllm.fs_io_C`), the error names the failing path: 14 × the block folder (`.../<3 hex>/<2 hex>_g0`), 3 × the temp file (`...bin_<n>.tmp`), 0 × the final `.bin`. The Python path also showed some `ENOENT` when the temp file was opened in a just-created folder.

**1. Parent-folder creation (main cause).** Both instances create the same new folder. On 3FS, `mkdir()` then returns `EEXIST` while the folder is not yet visible on that host, so `std::filesystem::create_directories` / `os.makedirs(exist_ok=True)` fail. Only the folder step, two hosts, the same 3,000 new folders at the same time: 107 and 882 × `EEXIST` from `create_directories` (0 with one host); after `mkdir()` returned `EEXIST`, `stat()` gave `ENOENT` in 82 of 276 and 606 of 2,732 cases. With a small `os.makedirs` wrapper that waits 50 ms and retries when the folder exists but is not visible (Python path, this PR's build), the store failures went from 9 / 16 to 0 / 0 (14 and 35 retries, all fine at the first retry).

**2. Same temp-file names in both instances (less often).** `_get_tmp_suffix()` uses `random.randint(...)` from the global `random`, which `set_random_seed()` seeds with the model seed (default 0). With the default seed, both instances drew the same suffixes: all 30 temp suffixes logged on one host were also used on the other; with `--seed 0` / `--seed 1`, none were shared. So two instances that store the same block at the same moment can open the same temp file with `O_EXCL`.

**Possible fixes (not tested as code changes):** (a) when the parent-folder step returns `EEXIST` (or the following `open()` returns `ENOENT`), retry after a short wait instead of failing the job; (b) make the temp suffix independent of the model seed (for example from `os.urandom`, or with the PID/host in it).

Should I open a new issue for these two, or is a follow-up PR preferred? I can run a fix on the same setup.
