# [Rust Frontend] Support return_prompt_text

[Upstream PR](https://github.com/vllm-project/vllm/pull/64526) · state: closed · merged: True

## Original PR description

## Overview

Support `return_prompt_text` on chat completions in the Rust frontend (vllm-project/vllm#42052): the response carries `prompt_text`, the prompt string the chat template produced, on non-streaming responses and on the first stream chunk. The Rust frontend rejected `return_prompt_text: true` with a 400 placeholder from vllm-project/vllm#62434, whose TODO this resolves.

## Claims

| Request | Python | Rust before | Rust after |
|---|---|---|---|
| `return_prompt_text` unset or `false` | `prompt_text: null` (non-streaming; first chunk) | same | same |
| `true`, a renderer that produces text (HF templates, DeepSeek V3.2) | rendered prompt string | 400 | rendered prompt string |
| `true`, multimodal content | rendered string, placeholders not expanded | 400 | same as Python |
| `true`, a renderer that produces token IDs (Harmony and others) | `null` | 400 | `null` |

- Streaming puts it on the first chunk only; later chunks omit the key, as they already do for `prompt_token_ids`.
- The prompt string is copied only for requests that ask for it.

- `routes::tests::chat_return_prompt_text_reports_the_rendered_prompt`: a streaming and a non-streaming request through the router and a mock engine; each returns the fake renderer's `"user: hello\nassistant:"`, and in the stream it appears on the first chunk only.
- `chat_stream_and_collect_preserve_prompt_and_sample_logprobs` (vllm-chat): the stream and `collect_message` both carry the rendered text when requested; `chat_streams_text_events` pins `None` when it is not.
- `non_stream_chat_image_url_reaches_engine_mm_features` also sets `return_prompt_text` and checks for the rendered text with one unexpanded image placeholder.
- Red-green: without the stream-level fill, the route and chat tests fail; with the text captured after placeholder expansion, the multimodal case fails; with the first chunk dropping the text, the streaming test fails.
- The `validate_request_compat_rejects_return_prompt_text` unit test goes away with the placeholder.

## Details

**Layering.** The value is produced by rendering, which belongs to `vllm-chat`, so `ChatRequestProcessor::prepare_text_request` takes it from the `RenderedPrompt` before `finalize_rendered_prompt` expands media placeholders, and only when `ChatRequest::return_prompt_text` is set. It is request metadata, so it reaches the server on `ChatEventStream` (`prompt_text()` and `take_prompt_text()`, next to `request_id()`), set by `ChatLlm::chat`; the chat events and output processors are unchanged. `collect_message` copies it into `CollectedAssistantMessage`, and the streaming route takes it once for the first chunk. `prepare` now returns a named `PreparedChatRequest` instead of a tuple so it can carry the text; the render route takes only `text_request` from it. `vllm-server` only lowers the DTO flag and fills the existing `prompt_text` response fields.

**Differences from Python.**

- With a renderer that produces token IDs, Python reports a detokenized prompt only as a side effect of `echo=true` without `return_token_ids` (`needs_detokenization`), and not at all on its Harmony path. Rust reports `null`: that is an echo implementation detail, not the `return_prompt_text` contract.
- With `truncate_prompt_tokens` and left truncation, Python may report text already pre-trimmed by its character-length guard (a tokenizer performance bound); Rust reports the full rendered prompt.

Not a duplicate: no open PR implements `return_prompt_text` in the Rust frontend (searched open PRs for `return_prompt_text`). AI assistance (Claude Code) was used to prepare this change; the human submitter reviewed every changed line.
