# [Bugfix] Package the SM90 DeepGEMM mHC register lifetime fix

[Upstream PR](https://github.com/vllm-project/vllm/pull/59129) · state: open · merged: False

## Original PR description

## Purpose

Package the SM90 mHC prenorm GEMM register-lifetime fix from [deepseek-ai/DeepGEMM#448](https://github.com/deepseek-ai/DeepGEMM/pull/448), authored by jason (leevan). In a multi-stage K loop, the next iteration can overwrite register A operands before the previous asynchronous WGMMA has finished. Repeated calls with identical inputs can therefore produce different outputs. The upstream fix waits immediately after committing the WGMMA batch.

This integrates that existing fix into vLLM's packaged JIT header until the pinned DeepGEMM dependency contains it; it is not a new kernel implementation. DeepGEMM #448 is currently open. Remove the temporary integration once the dependency pin includes the fix.

This correctness change was split out of [vLLM #58986](https://github.com/vllm-project/vllm/pull/58986), which now contains only the H20 block-FP8 MoE tuning. This branch starts from main `07f1ba2ec66776650a490630ddfa9e3c92713c33` and does not depend on that performance PR. The corresponding v0.30 backport remains [mengziheng/vllm#3](https://github.com/mengziheng/vllm/pull/3). There is no throughput improvement claim for this correctness repair.

## Changes

- Generate a patched header during CMake configuration and install it without modifying a supplied `DEEPGEMM_SRC_DIR`. Exclude the original header from the directory install to prevent a same-timestamp overwrite.
- Use the same helper in the standalone DeepGEMM installer. Recognized patched input is idempotent; unrecognized source fails without overwriting the destination.
- Extend the existing mHC suite with six SM90 regressions: 256/512/1024 tokens, different split-K counts, default and side streams, independent FP32 references and exact repeatability. Skip when DeepGEMM is unavailable.

## Validation

The following GPU results were recorded on H20/v0.30 before this PR split. The main test path is `tests/kernels/mhc/test_mhc_kernels.py`; the v0.30 suite used `tests/kernels/test_mhc_kernels.py`.

```bash
.venv/bin/python -m pytest tests/kernels/test_mhc_kernels.py \
  -k 'sm90_mhc_prenorm_preserves_register_operands or test_mhc_fused_post_pre' -v
.venv/bin/python -m pytest tests/kernels/test_mhc_kernels.py \
  -k sm90_mhc_prenorm_preserves_register_operands -v
```

- The pinned original header fails the new regression; the fixed header passes all six cases. The final test including its DeepGEMM availability guard returned **6 passed, 212 deselected**.
- The broader selection returned **17 passed, 9 skipped, 1 failed**. The existing H=7168/M=128 BF16 reference case fails with both original and repaired headers. No tolerance was loosened; this is not a full-suite pass.
- A fresh-process audit of the complete mHC operation covers 12 shape/seed groups with five repeats each. Repaired results are exactly repeatable; the original produces inconsistent results at 256/512 tokens. This does not establish whole-model token determinism.
- An installation fixture using the actual CMake integration verified installed bytes equal the upstream fix, repeated configure/install preserves it, and supplied source content remains unchanged. Standalone idempotence and rejection of unknown input without destination overwrite also passed. A full wheel build was not performed.

Fresh local checks for this split:

```bash

git diff --check 07f1ba2ec66776650a490630ddfa9e3c92713c33 HEAD
```

All applicable pre-commit checks pass. The three integration/helper files are byte-identical to the previously tested implementation, and the new regression's AST is identical. A local helper check again passed original-to-fixed conversion, idempotence, source preservation and unknown-input rejection. GPU tests were not rerun on this latest-main branch; these checks establish split equivalence, not a full main-wheel or full-model validation.

### Model evaluation

Historical validation uses the same GLM-5.3-Flash checkpoint on 4×H20, TP4, FP8 weights/BF16 activations and MTP3, with v0.30 native extensions and the patched JIT header. The corrected control without the MoE tuning and the corrected candidate with the tuning each score **121/128** on a GSM8K first-128, five-shot raw-completion diagnostic (greedy, concurrency 8, output cap 768). Each has 128 successful requests and no truncation. Only 39/128 output texts match exactly; each arm uniquely answers three questions correctly. This subset is not an accuracy-improvement claim or proof of full-model equivalence.

The corrected control completed **1,152/1,152** measured serving requests successfully; all three recorded control/candidate blocks completed **3,456/3,456** in total. The corrected candidate also passed six context-retrieval checks at 511/2047/2048/2049/4097/8193 tokens. Full serving settings, paired measurements and limitations remain in [#58986](https://github.com/vllm-project/vllm/pull/58986). Those performance differences belong to the MoE tuning, with this fix present in both arms.

B200, production traffic, long soak tests and full-model serving on latest main were not validated.
