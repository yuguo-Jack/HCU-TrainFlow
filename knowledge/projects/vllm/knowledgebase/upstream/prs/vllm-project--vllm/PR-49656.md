# [Bugfix][CPU] Fix LoRA no-op row aliasing in PunicaWrapperCPU

[Upstream PR](https://github.com/vllm-project/vllm/pull/49656) · state: open · merged: False

## Original PR description



# Purpose

Fixes #48421-adjacent bug: on CPU, bgmv_shrink/bgmv_expand/bgmv_expand_slice (vllm/lora/ops/torch_ops/lora_ops.py) gather lora_b_weights[lora_indices_tensor] directly, including for rows whose index is -1 ("no LoRA active for this token"). There's no dedicated null slot, so -1 triggers ordinary negative indexing and silently aliases the last real adapter slot (lora_b_weights[max_loras - 1]). With the common max_loras=1 case, that's the one loaded adapter's own slot — so any batch mixing base-model-only requests with adapter-targeted requests can have the adapter's LoRA delta silently added into base-model rows' output.

Note on #48421: I found vllm-project/vllm#48421 open against the same underlying bug while doing the required duplicate-work check. That PR is correct but fixes it by clamping the index to 0 and zeroing the result afterward (masked_fill) — the full shrink/expand GEMM still runs on every no-op row. This PR instead masks out invalid rows before the gather + einsum, so no-op rows cost nothing (and a batch with zero active LoRA rows returns immediately without any GEMM at all). It also fuses add_shrink's per-slice Python loop across lora_a slices into a single batched op in PunicaWrapperCPU, removing the existing # TODO fuse these kernels — a related but separate gap in the same code path, not covered by #48421. Happy to defer to #48421 for the minimal fix if maintainers prefer the smaller diff; opening this as an alternative given the additional performance benefit and the unaddressed fusion TODO.

- abrudner · comment · 2026-10-23T16:31:51Z · [source](https://github.com/vllm-project/vllm/pull/49656#issuecomment-6369728630)

**Update: this PR is now a CPU LoRA performance change.** It skips compute for no-LoRA rows in the torch bgmv ops and groups multi-slice `add_shrink` into one GEMM per active adapter: up to ~4.7x faster `add_lora_linear` in the decode path with LoRA tokens, and near-zero cost for batches with no LoRA tokens.

#48421 has since merged the minimal fix for the `-1` aliasing bug this PR originally targeted, so, as suggested on #48421, I've rebased onto it and kept the title for continuity. The correctness fix and its regression test now come from #48421; this PR changes only how the work is done. The description above predates this; the current scope is:

**1. Skip no-LoRA rows instead of computing and masking them** (`vllm/lora/ops/torch_ops/lora_ops.py`)

#48421 clamps the index to 0, runs the gather + einsum for every row, then zeroes the `-1` rows. The gather materializes a per-token copy of the LoRA weights, so base-model tokens pay the full LoRA cost. The CPU decode path also has no `no_lora` early return (prefill does), so a decode batch with no LoRA tokens still runs shrink/expand in every LoRA layer.

This PR selects only valid rows before the gather + einsum in `bgmv_shrink` / `bgmv_expand` / `bgmv_expand_slice`, and returns immediately when no row has an active adapter. Semantics match #48421 and the Triton kernels: no-LoRA rows are left untouched (including under `add_inputs=False`). When every row is valid, the original code path runs unchanged.

**2. Group `add_shrink` by LoRA** (`vllm/lora/punica_wrapper/punica_cpu.py`)

Replaces the per-slice loop (`# TODO fuse these kernels`) for multi-slice layers (e.g. packed qkv) with one GEMM per active LoRA against its concatenated A slices, with tokens sorted by LoRA. This avoids per-token weight copies entirely for shrink, which dominate cost as the batch grows. Single-slice layers keep the existing path.

**3. Benchmark** — `benchmarks/kernels/cpu/benchmark_cpu_lora.py` times `PunicaWrapperCPU.add_lora_linear` (shrink + expand) in the decode path across batch sizes and LoRA/base-model token mixes.

`torch.compile` note: the CPU platform sets `CompilationMode.NONE` whenever LoRA is enabled (`vllm/platforms/cpu.py`), so the data-dependent shapes here don't introduce graph breaks.

### Not a duplicate

#48421 (merged) fixed the correctness bug with clamp + mask; this PR keeps its semantics and its regression test (`test_torch_ops_bgmv_skips_no_lora_tokens`) and changes only how the work is done. My original aliasing tests were dropped as redundant with that test. No other open PR touches `PunicaWrapperCPU` or the torch bgmv ops. #47951 (open) skips the whole LoRA layer path in eager mode when a batch has no active adapter, but only wires that up for the GPU/XPU wrappers; it would be complementary here (layer-level skip for all-base-model batches) and doesn't cover mixed batches or the shrink grouping.
