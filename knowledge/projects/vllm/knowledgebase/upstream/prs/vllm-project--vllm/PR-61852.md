# [Bugfix][Frontend] Keep the parser's tool call IDs in batch derender

[Upstream PR](https://github.com/vllm-project/vllm/pull/61852) · state: closed · merged: True

## Original PR description

## Overview

Batch `/v1/chat/completions/derender` now keeps the parser's tool call IDs, the same as `/v1/chat/completions` and streaming derender. Part of #42729.

## Claims

- Batch derender uses `tc.id or make_tool_call_id()` in place of a bare `random_uuid()`. Default IDs get their `chatcmpl-tool-` prefix back and Kimi K2 style `functions.<name>:<idx>` IDs come through unchanged.
- The batch parity test compares tool call ID formats as well as names and arguments. It also gives derender the engine's `finish_reason` instead of the coupled one, so derender has to apply the `tool_calls` rewrite itself.

## Validation

New unit tests in `test_derender.py`. Both fail on `main` and pass with this change:

- `test_derender_chat_tool_call_id_matches_chat_completion`: real hermes parser, checks the ID starts with `chatcmpl-tool-`.
- `test_derender_chat_keeps_parser_tool_call_id`: a stub parser returns `functions.get_weather:1` and the test checks it's kept.

```bash
pytest tests/entrypoints/scale_out/derender/test_derender.py -v
pytest tests/entrypoints/scale_out/derender/test_derender_parity.py -v
```

No model eval. The change only affects tool call IDs, not generated text.

## Details

Batch derender threw away the ID the parser had already built. Chat templates for Kimi-style models reference these IDs in multi-turn history, so a bare UUID breaks follow up turns. It also meant batch and streaming derender returned different IDs for the same tokens.

The parity test missed this because `_tool_sig` only looks at names and arguments. It also fed derender the coupled server's `finish_reason` which already had the `tool_calls` rewrite applied, so derender never had to work it out. #59324 shares `resolve_finish_reason()` between chat and derender, so the test can now pass the engine's value.

The current batch tool cases use a named `tool_choice` which never rewrites to `tool_calls`. So the `finish_reason` change mostly guards future auto tool cases.

This matters for #56851 too. The planned `parse_context` carries `history_tool_call_cnt` for Kimi IDs and that field does nothing while batch derender overwrites the IDs.
