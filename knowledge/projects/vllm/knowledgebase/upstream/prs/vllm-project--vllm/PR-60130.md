# [KV Offload] SimpleCPUOffload: one host buffer per rank, opt-in HugeTLB pages

## Overview

**Functionality**
- `SimpleCPUOffloadConnector` allocates each rank's CPU KV caches as views into one host mapping of `cpu_bytes_to_use_per_rank` bytes, pinned with a single `cudaHostRegister`.
- The new `cpu_hugepage_block_size` key (`"1GB"` or `"2MB"`) backs that mapping with explicit HugeTLB pages; without it, ordinary pages are used.
- The mapping prefers the GPU's NUMA node.
- A HugeTLB pool or container hugetlb limit that's too small fails at startup with an error naming the shortfall, never falling back to 4 KiB pages.
- The mapping is excluded from `fork()` (`MADV_DONTFORK`), so child processes can't make pinned pages copy-on-write.

```json
{"kv_connector": "SimpleCPUOffloadConnector", "kv_role": "kv_both",
 "kv_connector_extra_config": {"cpu_bytes_to_use_per_rank": 137438953472,
                               "cpu_hugepage_block_size": "1GB"}}
```

**Performance implications**
- In `vllm serve` (TP=2, 64 GiB per rank, ordinary pages), engine init takes 19.0 s vs 20.2 s before.
- With 1 GiB pages, pinning 128 GiB takes 0.19 s instead of 2.5 s on ordinary pages.
- GPU↔CPU copy bandwidth is unchanged at about 42 GB/s.

**Known limitations**
- On CUDA, a single registration of 512 GiB or more fails (#51081), so a per-rank buffer must stay below that; ROCm accepts 520 GiB.
- Each rank needs `ceil(cpu_bytes_to_use_per_rank / page size)` HugeTLB pages, reserved on the host and, on Kubernetes, requested as `hugepages-<size>`.
- Up-front population needs Linux 5.14+ for HugeTLB pages; ordinary pages fall back to first touch on older kernels.

Related: #45693 (same key name for `OffloadingConnector`), #58852, #59430, #51081.
