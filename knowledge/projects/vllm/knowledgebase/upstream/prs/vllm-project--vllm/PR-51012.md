# [Models] Deprecate `torch.compile` for Qwen3.5 models

[Upstream PR](https://github.com/vllm-project/vllm/pull/51012) · state: closed · merged: True

## Original PR description




## Overview

Qwen3.5 dropped `@support_torch_compile` in favor of breakable CUDA graphs (`VLLM_USE_BREAKABLE_CUDAGRAPH`, auto-enabled in `vllm/config/vllm.py`). An isolation experiment (same old code, compile vs breakable cudagraph) showed the removal alone cost **+45 ~ 64% decode-step and +22 ~ 39% prefill latency**. This change recovers the lost inductor fusions with explicit fused kernels, ending **5~11% faster than the torch.compile baseline** on decode and at parity on prefill.

## Claims

- End-to-end serving (`vllm bench serve`, up to 128 concurrent requests): decode ITL **-3.0% ~ -8.8%**, prefill TTFT **-7.0% ~ -8.9%** vs the torch.compile baseline (9B + 35B-A3B).
- Isolated forward latency (`vllm bench latency`): decode step **-4.9% ~ -10.7%**, MTP decode **-17% ~ -38%**, prefill at parity.
- Greedy decoding output is **token-identical** to the torch.compile baseline (TP1 and TP2).

## Validation

Environment: 1x NVIDIA GB200 (SM100, aarch64) per run, bf16, real weights (`Qwen/Qwen3.5-9B` dense, `Qwen/Qwen3.5-35B-A3B` MoE). Baseline = pre-removal commit (`44e88ae582^`) with default `VLLM_COMPILE`; "old+breakable" = same commit with `VLLM_USE_BREAKABLE_CUDAGRAPH=1`; "this PR" = HEAD with all fusions. Note: newer vLLM defaults prefix caching ON, which alone inflated TTFT by ~17-20% in an unnormalized run — both trees below use identical serving flags to avoid that artifact.

### End-to-end serving (vllm serve + vllm bench serve, random dataset)

**CustomOp CPU-dispatch failures (Kimi K3 lane + Mamba kernels lane) — root cause fixed in ab554877bd**

Both lanes failed the same way: a CPU-tensor CustomOp test dispatched to a CUDA-only op (`_C::silu_and_mul` in `test_sharded_sequence_parallel_mlp_matches_replicated`, `vllm::fla_rms_norm_gated` in `test_output_projection_norms_per_head_and_flattens`). Root cause: `VllmConfig.__post_init__` auto-enables breakable cudagraphs for breakable-by-default archs by setting `VLLM_USE_BREAKABLE_CUDAGRAPH=1` process-wide. With Qwen3.5 breakable-by-default on CUDA (this PR), every test creating a Qwen3.5 config (12 files go through `create_vllm_config("Qwen/Qwen3.5-0.8B")`) leaks it; later bare `VllmConfig()`s in the same pytest process then resolve to compilation mode NONE → custom_ops "all". Specific to this PR — on main Qwen3.5 isn't breakable-by-default, so the leak never fires there.

Fix at the two test-infra funnels instead of per-test pins: `create_vllm_config` snapshots/restores the env var around `VllmConfig` construction (created configs unchanged, process stays clean), and the `default_vllm_config` fixture pins it off. Verified on B300: full K3 lane 421 passed / 0 failed; mamba polluter+victim pair 25 passed.

The process-wide env propagation itself is load-bearing for spawned workers, so changing that mechanism is left to upstream.

**HiSparse failures (upstream, resolved)**: the V1 attention shards failed on `test_hisparse_*` due to the #58305 compact-KV-row regression, which failed on plain main too; fixed by #64238 (merged, now included via merge from main).
