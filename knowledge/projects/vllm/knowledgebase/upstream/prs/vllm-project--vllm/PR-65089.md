# [Attention] Opt in to startup sizing of the FlashInfer workspace

[Upstream PR](https://github.com/vllm-project/vllm/pull/65089) · state: open · merged: False

## Original PR description

## Overview

Opt-in startup sizing of the native FlashInfer attention workspace so a smaller reservation can become KV cache under the same `gpu_memory_utilization`. Fixes the integration requested in #63399. Default behavior is unchanged when the opt-in is off.

This is not a duplicate of #46883 (draft lifecycle rewrite that reserves FlashInfer's per-plan workspace and changes worker profiling) or #40383 (grow the buffer to avoid overflow). Those PRs are still open and take different approaches. This change only shrinks, only when asked, and only when FlashInfer reports a range upper bound.

## Claims

- `VLLM_FLASHINFER_WORKSPACE_AUTO_SIZE=1` asks FlashInfer `workspace_size_upper_bound` (flashinfer-ai/flashinfer#5236) for the prefill and decode service range, then allocates that buffer before memory profiling and CUDA graph capture.
- Unset, allocation is the existing path: 394 MiB, grown for the prefill head footprint, never shrunk.
- An explicit `VLLM_FLASHINFER_WORKSPACE_BUFFER_SIZE`, including a value equal to 394 MiB, disables auto-shrink. The prefill floor can still grow a too-small explicit value, matching today's overflow guard.
- Unsupported routes (DCP, speculative decode, sinks, ALiBi, multimodal prefix, quantized KV, non-causal attention, batch-invariant mode, a fixed `kv_cache_memory_bytes`) keep native allocation and log the reason.
- Startup logs configured bytes, selected bytes, source (`explicit` / `flashinfer` / `configured`), any fallback, and the resulting KV token capacity.

## Validation

Policy tests, CPU only:

```bash
.venv/bin/python -m pytest tests/v1/attention/test_flashinfer_workspace_autosize.py -q --noconftest
```

10 passed. They cover: default path does not shrink; explicit 394 MiB wins and does not query; the #63399 study shape (512 tokens, 12 query heads, ~21.2 MiB bound) selects 32 MiB; a missing upper bound and unsupported routes keep 394 MiB; the prefill floor is not undercut; an int-workspace bound above the wrapper's 8 MiB scratch falls back; the reserved buffer is reused and not grown after profiling.

`ruff check` and `ruff format --check` passed on the touched files.

No end-to-end model run. The pinned `flashinfer-python==0.7.2.post1` does not ship `workspace_size_upper_bound` (flashinfer#5236 is closed and unmerged), so enabling the flag on today's pin logs a fallback and keeps the native reservation. The +21% KV / 5–6% batch-completion numbers in #63399 are the author's measurements, not reproduced here.

## Details

FlashInfer often reserves ~394 MiB at startup. That reservation is counted in non-KV memory, so shrinking it before profiling raises KV capacity at the same utilization. The author's SM89 FA2 run (Qwen2.5-1.5B, 65% budget) went from 62,208 to 75,440 tokens and improved a 4×16K batch, with a slower first request. That latency tradeoff is why this is opt-in.

vLLM does not reimplement the scheduler arithmetic. It passes geometry and limits and adopts the bound only when it is smaller than the native reservation after a 9/8 margin, MiB rounding, a 32 MiB floor, and the existing prefill head-footprint floor. The buffer is allocated before `determine_available_memory` profiles and is reused for capture and replay.

AI assistance was used to implement this change. A human should review every line and rerun the #63399 workload on a GPU with a FlashInfer build that provides `workspace_size_upper_bound` before treating the capacity gain as verified.

### Open questions

- flashinfer#5236 is closed and unmerged, so the shrink path cannot succeed on the current pin. Should vLLM wait for that API, or is a temporary host-side port acceptable?
- #46883 also wants the workspace reserved before KV sizing through a different helper; these should be reconciled before both land.
- Explicit sizes still grow to the prefill floor. A hard cap is #40383's scope.
- The 9/8 margin, 32 MiB floor, and MiB rounding come from the #63399 study, not from FlashInfer.
- No GPU serving or accuracy run was possible in the authoring environment.
