# [Bugfix][MRV2] Release the allocator cache between adaptive verification profile shapes

[Upstream PR](https://github.com/vllm-project/vllm/pull/64280) · state: open · merged: False

## Original PR description

## Overview

Fixes #64275. With adaptive verification enabled, startup can run out of GPU memory in the cost-profiling loop of `capture_model()`, which runs after the KV cache is allocated. The loop profiles shapes in ascending size and keeps the allocator cache until it finishes, so the cache grows to the sum of all shapes. This PR releases the cache whenever the profiled batch changes, so the cache holds at most one shape at a time.

## Claims

- DeepSeek-V4.1-Flash on 4x MI355X at `--gpu-memory-utilization 0.95` now starts and serves. On main, it aborts with `HSA_STATUS_ERROR_OUT_OF_RESOURCES`.
- KV cache size and startup time are unchanged. Fixed-K and no-speculation paths are untouched.

## Details

**Root cause.** `batches_to_profile()` yields every captured size, then the eager tail sizes, in ascending order, with five replays each. Each larger shape needs bigger blocks than any cached one, so the cache grows by about one shape per size until the device is full. The final failing allocation belongs to the HIP runtime, so PyTorch's free-and-retry cannot help. #61509 empties the cache only after the loop.

**Why release on batch change.**
- It bounds the cache to one shape without changing profile order or KV sizing. That shape (at most 2.5 GiB here) fits in the activation headroom that KV sizing already reserves.
- The release happens outside the timed region.
- Comparing the whole batch keeps the release correct if profiling gains more axes, as in #62960.
- Profiling in descending order also starts, but it leaves less margin and relies on allocator block splitting.

**Not a duplicate.**
- #61509 and #63154 (merged) release memory only after the loop.
- #63431 (merged) and #56182 change only the pre-KV pass.
- #63410 conflicts on one line, but not semantically.

**Limitations.**
- Validated on ROCm only. The change is platform-neutral (`torch.accelerator.empty_cache()`).
- The reproduction sets `VLLM_ADAPTIVE_VERIFICATION_PROFILE_CONTEXT_LEN=4096` to avoid a separate ROCm fault at the default of 8192.

> **Question**: Did we consider iterating through the batch sizes in reverse order as an alternative fix (descending in size)? Might be less intrusive vs running `torch.accelerator.empty_cache()`

Good question, yes, I tested descending order. It also starts at 0.95, but the minimum free memory during profiling was 1.06 GiB vs 2.30 GiB with this PR (the smaller shapes fragment the large cached blocks), and it relies on the allocator splitting those blocks rather than explicitly bounding the cache. Releasing on batch change also stays correct if profile batches gain more axes (e.g. #62960), where "descending" isn't well defined. The cost is ~57 empty_cache() calls at startup with no measurable effect on startup time.
