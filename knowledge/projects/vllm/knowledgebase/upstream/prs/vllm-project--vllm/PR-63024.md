# [LoRA][MoE] Expert LoRA for FlashInfer TRTLLM NVFP4 experts

[Upstream PR](https://github.com/vllm-project/vllm/pull/63024) · state: open · merged: False

## Original PR description

## Overview

Add expert LoRA to the fused FlashInfer TRTLLM MoE kernel for NVFP4 (W4A4) experts with per-token activation scales (`TrtLlmNvFp4LoRAExperts`). This is the NVFP4 sibling of #61979 (MXFP4) and reuses the same `_TrtLlmLoRAExpertsBase` flow and the same routed FlashInfer API (`trtllm_fp4_block_scale_routed_moe` with `gemm1_lora_delta`).

## Claims

- NVFP4 MoE models with per-token FC1 activation scales (`kNvfp4DynamicToken`: ModelOpt `moe.activation='nvfp4_per_token'`, or online `nvfp4_per_token` quantization) can serve expert LoRA adapters on `moe_backend="flashinfer_trtllm"`. On main this raises `kernel does not support LoRA`.
- Opt-in: `moe_backend="auto"` selects the same backend as before (Marlin when LoRA is enabled). NVFP4 with static input scales plus expert LoRA is rejected with an explicit reason (`kernel does not support quantization scheme ...`), because the kernel then returns the FC1 activation as packed FP4 without its block scales (see Details).
- The non-LoRA `TrtLlmNvFp4ExpertsModular` is unchanged in behavior: its kernel arguments move into `TrtLlmNvFp4ExpertsBase._routed_moe_kwargs`, which both classes use.

## Details

Design. `TrtLlmNvFp4LoRAExperts(TrtLlmNvFp4ExpertsBase, _TrtLlmLoRAExpertsBase)`: the NVFP4 base comes first in the MRO, so `expects_unquantized_inputs` (per-token: the experts quantize the input themselves), `process_weights_after_loading` (`g1_scale_c`, folded clamp/beta) and the kernel arguments come from the existing NVFP4 experts. The `_TrtLlmLoRAExpertsBase` flow is unchanged: the gate/up delta is computed by punica on the unquantized input and passed as `gemm1_lora_delta`; the down delta is computed from the BF16 FC1 activation the kernel returns; the base finalize and the delta reduction run in one pass. Per-expert deltas already arrive as `[up | gate]`; fused 3D adapters are flipped from the checkpoint `[gate | up]` order.

Why per-token only. With static global input scales and `gemm1_lora_delta`, FlashInfer 0.7.2 returns the FC1 activation as `uint8` with `I / 2` columns, i.e. packed FP4 without block scales (observed on GB300). The down delta cannot be computed from it, the same situation as MXFP8 activations in #61979. With per-token scales the activation comes back as BF16 with `I` columns.

Limitations, each rejected rather than computed wrong:

- Gated SiLU only; other activations (`SWIGLUOAI_UNINTERLEAVE`, `SITU`, non-gated) are not enabled for the LoRA class (untested).
- Llama4 routing (router weight applied on the input) is rejected: the LoRA finalize weights the output again.
- DP, all2all and EPLB are rejected, as for `TrtLlmMxfp4LoRAExperts`: the inherited no-LoRA fast path reads the local batch's adapter flag.
- `fully_sharded_loras` is rejected for all TRTLLM LoRA experts (BF16, MXFP4, NVFP4) through a new `FusedMoEConfig.is_lora_fully_sharded` / `_supports_fully_sharded_lora()` check: the shared flow computes the W13 delta with `add_inputs=False`, which the fully sharded punica path asserts against. With an explicit `flashinfer_trtllm` this raises at selection; BF16 `auto` falls back to Triton.
- With LoRA enabled, the NVFP4 and MXFP4 oracles try only the LoRA experts class, so the error names the unsupported feature (quantization scheme, routing) instead of the last candidate's generic reason.
- When the MoE layer has no LoRA context (adapters only on attention), the TRTLLM LoRA experts run the base path, like `TritonExperts`, instead of asserting.
- FlashInfer 0.7.2 has no tile-192 kernel for this dtype with the LoRA-delta epilogue, but advertises 192 as a candidate tile (flashinfer-ai/flashinfer#8272). The default tactic picks 192 once a launch averages more than 192 tokens per local expert, and autotuning tries it whenever it is a candidate, so an earlier head of this PR failed at warmup with the default `max_num_batched_tokens`. LoRA launches are therefore split to at most `192 * local_num_experts // top_k` tokens (the unfinalized outputs are concatenated, so the w2 delta and finalize are unchanged) and run outside FlashInfer autotuning, so the heuristic never reaches 192. No-LoRA launches are still autotuned. Both can go once FlashInfer ships the kernel or filters the tile.
- Launches above the TRTLLM NVFP4 launch limit (`_get_chunk_size()`) are split instead of raising.

Also fixed on the way, since this PR is the first fused-3D path whose intermediate gets padded at TP 1: `FusedMoE3DWithLoRA._slice_w13_b` returned early at TP 1 (and under EP, where the MoE TP size is 1), so a fused 3D `[gate | up]` adapter was copied unpadded into the padded buffer and the up half was misaligned. The early return is removed; `tests/lora/test_moe_lora_ep_load.py` covers TP 1 with padding. CI: `tests/lora/test_trtllm_nvfp4_lora_moe.py` and `tests/lora/test_trtllm_mxfp4_lora_moe.py` are added to the B200 kernels job.
