# [ROCm][Kimi-K3][Perf] Cut gfx942 MXFP4-to-int4 requant time under pure TP

[Upstream PR](https://github.com/vllm-project/vllm/pull/64004) · state: closed · merged: True

## Original PR description

## Overview

Cut the gfx942 Kimi-K3 MXFP4-to-int4 MoE requant (`--quantization-config '{"moe":{"weight":"int4_per_group_32"}}'`, added in #51274) from ~19 min to 25 s under pure TP8. TP8 server startup drops from 22.5 min to 3.5 min. The converted weights are byte-identical.


## Validation

**End to end:** 8x MI325X (gfx942), ROCm 10.0, Kimi-K3 with the DSpark draft. The checkpoint was in the page cache for all startup numbers. Before and after use the same base; only `mxfp4.py` differs.

```bash
VLLM_USE_V2_MODEL_RUNNER=1 VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MOE=1 VLLM_ROCM_USE_AITER_MLA=1 \
vllm serve moonshotai/Kimi-K3 --trust-remote-code --language-model-only -tp 8 [--enable-expert-parallel] \
  --max-model-len 16384 --max-num-seqs 4 --reasoning-parser kimi_k3 \
  --quantization-config '{"moe":{"weight":"int4_per_group_32"}}' \
  --compilation-config '{"cudagraph_mode":"FULL_AND_PIECEWISE"}' \
  --speculative-config '{"method":"dspark","model":"Inferact/Kimi-K3-DSpark","num_speculative_tokens":7,"attention_backend":"TRITON_MLA","draft_sample_method":"probabilistic","rejection_sample_method":"block"}'
```

| Config | Requant before | Requant after | Startup to `/health` before | Startup to `/health` after | KV cache before | KV cache after |
|---|---|---|---|---|---|---|
| TP8 | 19 min 15 s | 25 s | 1348 s | 210 s | 27.37 GiB | 28.21 GiB |
| EP8 | 4 min 38 s | 24 s | 431 s | 181 s | 22.57 GiB | 23.41 GiB |

The requant is the time between `Loading weights took` and `Online quantization as part of model loading` on rank 0.

**Accuracy** (GSM8K, 5-shot, `lm_eval --model local-completions`, with the fix):
- TP8: 0.988 ± 0.007 on 250 questions.
- EP8: 1.000 on 100 questions.

The weights are byte-identical to the current code (see below), so I didn't rerun accuracy on the baseline.

**Per-layer microbenchmark:** one full Kimi-K3 MoE layer (w13 + w2), per-rank shapes with `routed_expert_hidden_size` 3584, run under `max_split_size_mb:20` like `gpu_worker.load_model`. Times are the median of 7 runs, alternating before and after. The old code's first run in a fresh process is faster (1.94 s TP8, 0.85 s EP8); its `hipFree` cost grows as the process maps more memory.

| EP8 (112 experts, w13 6144 x 3584) | 3.07 s | 0.30 s | 3.43 GiB | 2.89 GiB | 5.66 GiB | 4.56 GiB | 32 | 4 | yes |

**New test:** `tests/kernels/quantization/test_k3_gfx942_int4_requant.py`. It runs on gfx942 only and is picked up by the existing "(MI300) Quantization Kernels" step. It checks that the output does not depend on chunking, and that no device memory is allocated after the first chunk on the Kimi-K3 TP8 w2 shape under `load_model`'s allocator settings. It passes 4/4 with the fix and fails before it. Against the refactor-only parent (9acd4b58ba), every chunk allocates:

```
E       assert [1724, 1737, ...76, 1789, ...] == [1724, 1724, ...24, 1724, ...]
1 failed, 3 passed
```

Against the first revision of this PR (3bdfe8097f), the shorter last chunk allocates:

```
E       assert [90, 90, 90, 90, 111] == [90, 90, 90, 90, 90]
1 failed, 3 passed
```

For those runs the test loaded `mxfp4.py` from each commit. On the parent I appended `_K3_INT4_CONVERT_CHUNK_VALUES` only so the test's `monkeypatch.setattr` resolves; the old code ignores it.

`tests/models/kimi_k3/test_gfx942_int4.py` and `tests/quantization/test_quantization_config_args.py` still pass.

## Details

**Root cause.** `_setup_kernel_k3_situ_gfx942` converted 8 experts per chunk and called `torch.accelerator.empty_cache()` after every chunk. Pure TP keeps all 896 experts per rank at 1/tp width, so TP8 ran 112 chunks per weight where EP8 runs 14, for the same bytes. That is 20,608 chunks over 92 MoE layers.

Every `empty_cache()` hands the chunk's temporaries back to the driver, and the next chunk allocates them again. In a live TP8 server, a native py-spy profile of the requant showed 92% of the time in `emptyCache -> release_block -> hipFree` (HSA `munmap`/`ioctl`) and about 5% in `hipMalloc`. The conversion kernels themselves barely appeared. That worked out to about 56 ms per chunk.

**Fix.**
- Size each chunk by unpacked values instead of experts, using `_K3_INT4_CONVERT_CHUNK_VALUES = 1 << 27`. TP8 and EP8 both run 19 chunks per w13 and 10 per w2.
- Drop the per-chunk `empty_cache()`, so later chunks reuse the cached temporaries. The cache is still emptied once per converted weight.
- Keep every chunk the same shape by shifting the last chunk back to overlap the previous one. Under `max_split_size_mb:20`, a cached block of 20 MiB or more is only reused for a request less than 20 MiB smaller, so a shorter last chunk would allocate a second set of temporaries. The overlapping experts are recomputed to identical values, which costs less than one chunk per weight.
- The output can't depend on chunk size: `per_1x32_i4_quant`, `shuffle_weight` and `shuffle_scale_for_int4` all work per expert along the leading dimension. The new test checks this explicitly.

**Tradeoffs.** The TP8 per-layer peak grows (allocated 1.56 to 2.89 GiB, reserved 1.85 to 4.56 GiB), because the old TP chunks were tiny. The EP8 peak shrinks (allocated 3.43 to 2.89 GiB, reserved 5.66 to 4.56 GiB). Both stay below the old EP8 peak, which already fit.
