# [ROCm][Perf] Skip the seq_lens D2H sync in the AITER sparse MLA metadata key

[Upstream PR](https://github.com/vllm-project/vllm/pull/58710) · state: open · merged: False

## Original PR description

## Purpose

This is the ROCm counterpart of #58684, which has the background.

On every build of `ROCM_AITER_MLA_SPARSE` with persistent metadata (the default for DeepSeek-V3.2 and GLM-5.x sparse MLA), `seq_lens[:num_reqs].cpu()` runs, decode steps included. That is a blocking D2H copy, and under async scheduling it stalls the CPU until the GPU catches up. The copy only feeds the cache key that decides whether to re-run `get_mla_metadata_v1`, which was added in #42982. The metadata itself is already built on device from `paged_kv_indptr`.

The key only looks at seq_lens and context lens clamped to `index_topk`, so exact values usually aren't needed. This PR builds the key from `seq_lens_cpu_upper_bound` whenever that gives the same key:
- **No spec decode:** the upper bound is exact, so it's always used.
- **Spec decode:** the bound can overshoot by up to `num_speculative_tokens`. It's used once every request's `context_ub - num_speculative_tokens >= index_topk`. Past that point both lens clamp to `index_topk`, so the key is identical to the exact one. That's the steady state for long-context decode, the same regime #42982 targeted.
- **Otherwise:** it falls back to the current D2H copy.

Unlike #58684, no device fixup is needed, since AITER already plans on device.

Not changed here:
- The `synchronize()` after a metadata recompute (#47404) is untouched. The fast path never recomputes, since the key stays the same.
- Batches with any short-context request under spec decode still sync.

**Not a duplicate:** I searched open PRs for this backend. #58354 edits the same `build()` (it drops dead ops) but doesn't touch this sync. Whichever lands second needs a trivial rebase.

## Test Plan

- `pytest tests/kernels/attention/test_rocm_aiter_mla_sparse_metadata_sync.py`. The new `test_persistent_metadata_key_from_upper_bound` checks three cases: no spec decode, spec decode with saturated contexts, and spec decode with short contexts. In each it checks whether the D2H copy runs, and that the key equals the one built from exact seq_lens.
- **Needs validation on ROCm hardware.** I don't have MI300/MI355 access. The test module is ROCm-only, so I ran it on CPU with the platform guards removed and `np_to_pinned_tensor` / `triton.next_power_of_2` stubbed. It would be great if someone with ROCm hardware could run the test file, GSM8K, and an async + MTP serving bench (e.g. GLM-5.x or DeepSeek-V3.2) against main.

## Test Result

On CPU with the guards stripped: 7 passed. With the upper-bound path disabled, the two "no sync" cases fail, as expected.

No hardware numbers yet (see above).
