# [Bugfix][ROCm] Let ROCM_ATTN share the BLHNC KV cache layout

[Upstream PR](https://github.com/vllm-project/vllm/pull/63069) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

On ROCm, GLM-5.3-Flash with a DFlash2 drafter fails at startup. The model's indexer needs the BLHNC KV cache layout, but `ROCM_ATTN`, the drafter's backend, declares only LHBNC and LBHNC. This PR lets `ROCM_ATTN` declare BLHNC too.

Related:
- #61761: DFlash2 performance on ROCm.
- #61433 (draft, paused until the aiter pin bump) ranks `ROCM_ATTN` below the unified backends for spec decode, so auto-selection would stop picking it for the drafter. Until then, main auto-selects `ROCM_ATTN` for the drafter and fails at startup. An explicit `"attention_backend": "ROCM_ATTN"` fails in both cases. The two PRs do not depend on each other.

## Claims

- `amd/GLM-5.3-Flash-Quark-MXFP4` with `incoai/GLM-5.3-Flash-DFlash2` starts and serves on ROCm. On main, startup fails with:
  ```
  ValueError: No KV cache layout satisfies every supported set: [['BLHNC'], ['LBNHC', 'LBHNC', 'BLHNC'], ['LHBNC', 'LBHNC']].
  ```
- `ROCM_ATTN` gives correct output in every layout it declares, BLHNC included. It is checked against SDPA by a new test.

## Validation

**Startup and serving.** MI355X, TP2, breakable CUDA graphs with `max_cudagraph_capture_size` 2048. Output tok/s (acceptance length):

| drafter backend | c=1 | c=16 | c=64 |
|---|---|---|---|
| `TRITON_ATTN` (workaround on main) | 398.8 (4.62) | 2135.5 (4.40) | 4608.1 (4.63) |
| `ROCM_ATTN` (this PR) | 412.9 (4.85) | 2238.5 (4.74) | 4400.6 (4.51) |

- This PR is about starting, not speed. In step time (TPOT × acceptance length), `ROCM_ATTN` is about 2% slower at c=64 (60.2 vs 58.9 ms). That agrees with #61433.
- GSM8K with the `ROCM_ATTN` drafter is 0.9704. That run also had the KDA patches from #63071 and #63072 applied.

**Test.** `tests/v1/attention/test_rocm_attn_kv_cache_layouts.py`: 24 passed on MI355X.
- The cases are every declared layout × block size 16/128 × causal/non-causal (DFlash) × bf16/fp8 cache. Each runs the backend's own cache writer and attention, and compares the output to SDPA.
- On main the test does not fail; it just has no BLHNC cases, because it is parametrized over the layouts the backend declares. The startup error above is the reproducer.
- To check that the test can catch errors, I flipped causality and zeroed one cache block. All 24 cases failed.

## Details

**Root cause.** Since #57169 the GLM-5.3-Flash indexer requires the block-outermost BLHNC layout. The worker intersects the layouts of all attention groups. With a DFlash2 drafter on `ROCM_ATTN`, the intersection is empty.

**Why BLHNC is safe for `ROCM_ATTN`.** BLHNC differs from the LBHNC layout, which is already supported, only in the block stride.
- The Triton fallbacks (`context_attention_fwd`, `kernel_paged_attention_2d`) take every cache stride from the tensor.
- The native HIP kernels stay gated on `has_native_kv_cache_layout`, which needs a packed block stride. So BLHNC always runs the Triton path.

**Test design.** The shared backend harness lays the cache out per KV head. `ROCM_ATTN` binds K and V as two head groups, so the new test drives the backend's own writer and attention on a per-layer view in each layout.
