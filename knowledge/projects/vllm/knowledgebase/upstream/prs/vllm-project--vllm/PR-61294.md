# [Bugfix] Merge supported KV cache layouts across pipeline stages instead of asserting they match

[Upstream PR](https://github.com/vllm-project/vllm/pull/61294) · state: open · merged: False

## Original PR description

## Overview

With pipeline parallelism, a model whose stages use different attention backends fails at startup. `resolve_kv_cache_layout` asserts that every worker reports the same list of supported KV cache layouts, but PP stages hold different layers, so their lists can differ. This PR makes the engine core merge the worker lists with the same rule `get_supported_kv_cache_layouts` already uses for the backends of one worker.

This addresses failure 1 ("PP2 on SM100") of #60791. Failures 2-5 in that issue are not touched here.

## Claims

- `vllm serve` of a 10-layer MiniMax-M3-MXFP8 with `--pipeline-parallel-size 2` on B200 now starts, picks `LBHNC`, and answers requests. Before, it died in `_initialize_kv_caches` with `AssertionError: Workers disagree on supported KV cache layouts`.
- When all workers report the same list (one GPU, TP only, PP with equal stages), the result is the same as before.
- If no layout is supported by every worker, the existing `ValueError` is still raised.
- New unit test `test_pipeline_stages_resolve_a_layout_every_stage_supports`. It fails on the old code with the bug's assertion.

## Validation

Layers 0-2 are dense and layers 3-9 are sparse. I cannot show it is tensor-identical to the reporter's cut.

```python
# Cut MiniMax-M3-MXFP8 to its first 10 decoder layers (+ vision tower), as the report describes.
import json, re, glob, os, shutil, sys
from safetensors import safe_open
from safetensors.torch import save_file
src = glob.glob("$HF_HOME/hub/models--MiniMaxAI--MiniMax-M3-MXFP8/snapshots/*")[0]
dst = "/tmp/m3-10layer"
os.makedirs(dst, exist_ok=True)
N = 10
for f in os.listdir(src):
    if f.endswith(".safetensors") or f == "model.safetensors.index.json": continue
    shutil.copy(os.path.realpath(os.path.join(src, f)), os.path.join(dst, f))
def trunc(o):
    if isinstance(o, dict): return {k: trunc(v) for k, v in o.items()}
    if isinstance(o, list) and len(o) == 60 and all(isinstance(x, int) for x in o): return o[:N]
    return o
cfg = json.load(open(os.path.join(dst, "config.json")))
cfg["text_config"] = trunc(cfg["text_config"]); cfg["text_config"]["num_hidden_layers"] = N
q = cfg["quantization_config"]
q["ignored_layers"] = [x for x in q["ignored_layers"] if not (m := re.search(r"layers\.(\d+)\.", x)) or int(m.group(1)) < N]
json.dump(cfg, open(os.path.join(dst, "config.json"), "w"), indent=2)
wm = {}
for shard in sorted(glob.glob(src + "/*.safetensors")):
    out = {}
    with safe_open(shard, "pt") as f:
        for k in f.keys():
            m = re.search(r"language_model\.model\.layers\.(\d+)\.", k)
            if m and int(m.group(1)) >= N: continue
            out[k] = f.get_tensor(k)
    name = os.path.basename(shard)
    save_file(out, os.path.join(dst, name), metadata={"format": "pt"})
    for k in out: wm[k] = name
    print(name, len(out), flush=True)
json.dump({"metadata": {}, "weight_map": wm}, open(os.path.join(dst, "model.safetensors.index.json"), "w"))
```

## Details

Root cause: each worker reports the layouts that all of its own attention backends support (`WorkerBase.get_supported_kv_cache_layouts`). `resolve_kv_cache_layout` then asserted that all reports are equal, because "all ranks run the same backends". With PP, each stage builds only its own layers. For this model with PP2:

- PP0 holds layers 0-4. Layers 0-2 use FlashInfer, which supports only `(LBHNC, BLHNC)` on SM100, so PP0 reports `['LBHNC', 'BLHNC']`.
- PP1 holds layers 5-9, which are all sparse. `MINIMAX_M3_SPARSE` and `MINIMAX_M3_SPARSE_INDEXER` declare no layout set, so PP1 reports the default list of six layouts.

The two lists differ, but they share `LBHNC` and `BLHNC`. With PP=1 the model works, because one worker sees all backends and intersects their sets. A debug run that printed each stage's backends confirmed this.

Fix: the merge code in `get_supported_kv_cache_layouts` moves into a helper, `_merge_supported_layouts`, and `resolve_kv_cache_layout` now uses the helper on the worker reports.

- Identical lists keep their order, so setups where all workers agree are unchanged.
- Otherwise, the candidates are the layouts that appear in every list, and the layout that the most lists put first wins.
- A worker that reports the default list (no backend declares a set) does not vote, in the same way that a backend that declares nothing does not vote inside one worker. Without this rule, an all-sparse stage would vote for `LBNHC`, and PP could pick a different layout from PP=1. The second case of the new test covers this.
- If no layout is in every list, the code still raises `ValueError: No KV cache layout satisfies every supported set`.

Tradeoff: the removed assertion also caught TP ranks of one stage that report different lists, for example after one rank picked a different backend by mistake. Those lists are now merged like PP stages. The chosen layout is still one that every worker supports. A per-stage check could be added back, but the engine core would then need to know which worker is in which stage, and this fix does not need that.

Limitations: only failure 1 of the issue is fixed. Validation used B200 with FLASHINFER and `VLLM_USE_V2_MODEL_RUNNER=1`, not GB200.
