# [ROCm][Tests] Un-skip AITER MXFP4 padding-matrix and token-padding tests

[Upstream PR](https://github.com/vllm-project/vllm/pull/62996) · state: closed · merged: True

## Original PR description

## Summary

Follow-up to #59333/#59334, which left `test_aiter_moe_padding_matrix_mxfp4` and `test_aiter_moe_token_padding_garbage_rows_mxfp4` as skip stubs pending gfx950 hardware access and MXFP4 quant-config plumbing (#60886). Tracked as item "4d-2" in the #54966 progress table (https://github.com/vllm-project/vllm/issues/54966#issuecomment-6129972192). We're on an MI355X (gfx950) now, so this is unblocked.

Un-skips both tests in `tests/kernels/moe/test_modular_kernel_combinations.py`, routing them through `AiterMxfp4Experts` and parametrizing over both AITER-supported MXFP4 schemes (W4A16, W4A4).

Overlaps textually with #62907 (also touches `test_aiter_moe_padding_matrix`, for an unrelated AITER v0.1.26 `ck_moe_stage2` regression, and moves this file's CI home to a new gfx950-native `:amd: (MI355) FusedMoE Layer Kernels` job). Built off current `main` without waiting for it; will rebase once it merges, same as #59334 did on #59333. Until then these MXFP4 tests run on MI300 (gfx942) alongside the file's existing `AiterMxfp4Experts` coverage -- no separate Buildkite change needed.

### New AITER MXFP4 gaps found on hardware

Discovered while widening these tests' padded shapes; documenting following the same pattern as #60886/#62907. Both are AITER-side gaps worth a follow-up issue upstream -- worked around here via shape choice, not by catching the failure.

- **W4A16's CK-Tile stage2 kernel raises `NotImplementedError`** whenever the physical intermediate width isn't a multiple of 256 (it mis-indexes scales otherwise). The file's existing 128-aligned padding constants aren't sufficient for MXFP4; added separate 256-aligned `_PADDING_N_UNPADDED_MXFP4`/`_PADDING_N_PADDED_MXFP4`.
- **W4A4's stage1 (gate/up) GEMM silently produces NaN/Inf**, not a raise, whenever the physical hidden width isn't a multiple of 256 -- confirmed via a standalone hardware sweep (K=768/1024 finite, K=896/1152 NaN). Added separate 256-aligned `_PADDING_K_UNPADDED_MXFP4`/`_PADDING_K_PADDED_MXFP4` (used for both MXFP4 schemes for simplicity, though only W4A4 is empirically affected).

### Addressed review feedback

- Replaced a hard `assert config.fe_supports_quant_scheme()` with `pytest.skip(...)` in both new tests -- `AiterMxfp4Experts` is gfx950-only, so this previously hard-failed instead of skipping on non-gfx950 CI (e.g. gfx1250).
- Added a cosine-similarity check alongside the existing magnitude-ratio guard in the mxfp4 accuracy check: the guard alone can't catch a sign-flipped (same-magnitude) output, and cosine similarity alone can't catch a uniform-magnitude one (it's scale-invariant) -- together they cover both failure modes. Calibrated on gfx950: correct runs score 0.79-0.99 across all padding modes, corrupted output scores <=0.01 or negative.
- Merged `_aiter_token_padding_worker_mxfp4` into the existing fp8 `_aiter_token_padding_worker` (the two were near-total duplicates) instead of keeping a parallel copy.
- Merged `_aiter_padding_matrix_worker_mxfp4` into the existing fp8 `_aiter_padding_matrix_worker` the same way, slicing the packed uint8/block-scale weights directly (new `_slice_unpadded_mxfp4_weights`) and reusing `reference_moe_impl` instead of dequantizing and calling `torch_experts` separately -- the same pattern the fp8 worker already used via `_slice_unpadded_weights`.

## Test plan

```
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MOE=1 pytest -q tests/kernels/moe/test_modular_kernel_combinations.py -k mxfp4
```
16 passed on an MI355X, AITER v0.1.26 (14 new parametrizations from this PR -- 8 `test_aiter_moe_padding_matrix_mxfp4` + 6 `test_aiter_moe_token_padding_garbage_rows_mxfp4` -- plus 2 pre-existing `test_modular_kernel_combinations_singlegpu` mxfp4 cases also matched by `-k mxfp4`, unaffected by this PR).

Timing for just the 14 new parametrizations (`--durations=0`): 279.14s (0:04:39) total, 16.30s-35.91s each.

Full-file regression (no `-k` filter): 85 passed, 4 skipped, 6 failed -- same 6 failures reproduce identically on unmodified `main` (pre-existing AITER v0.1.26 `ck_moe_stage2_fwd` regression that #62907 is already tracking), confirmed unrelated by stash-and-rerun.

The W4A4 comparisons here and in `_aiter_token_padding_worker_mxfp4` can accept badly corrupted nonzero outputs. As the preceding comments note, the reference signal is smaller than `atol=0.1`: reference values of ±0.01 and completely sign-reversed results pass every element of `check_accuracy`, and their identical mean absolute magnitudes also pass the new guard. Thus the guard rejects zero output but does not establish padding correctness or real-row accuracy. Use an error criterion normalized to the reference signal, calibrated on gfx950 for W4A4 quantization error, in both workers so grossly incorrect nonzero results fail.
