# [ROCm][Perf][MLA] Fuse the decode W_UK absorb, q concat + fp8 quant and head pad via AITER

[Upstream PR](https://github.com/vllm-project/vllm/pull/64560) · state: open · merged: False

## Original PR description



## Overview

On ROCm with AITER MLA and an fp8 KV cache, each MLA decode layer builds the asm decode query in three launches: the bf16 W_UK absorb `torch.bmm`, the q concat + static fp8 quant, and the `repeat_interleave` head pad to the asm kernel's 16 heads. This PR replaces them with one AITER Triton kernel, `fused_bf16_bmm_cat_quant_pad_mla` (ROCm/aiter#7171), when AITER ships a tuned config for the layer's shape.

Depends on ROCm/aiter#7171. Without it, the tuned-config check returns false and the existing path runs unchanged.

## Claims

- Kimi-K2.6-MXFP4, TP8, MI355X: output throughput **+3.2% to +7.1%**, mean TPOT **−2.8% to −6.2%** across 1k/1k (concurrency 16/64/128) and 1k/8k (concurrency 64).
- Decode query prep: 61 × (5.66 + 4.55 + 5.32) µs → 61 × 4.58 µs per decode step, **947 µs → 279 µs**, two fewer launches per layer.
- Accuracy unchanged within stderr (GSM8K 5-shot, GPQA diamond CoT 0-shot).

## Details

**Where it plugs in.** The fused call sits in the decode branch of `MLAAttention.forward_impl`. That branch runs inside the opaque attention custom op, so deciding per step from the attention metadata is safe under `torch.compile` and CUDA graphs. It runs only when every one of these holds:

- AITER MLA is enabled.
- W_UK takes the bf16 `torch.bmm` path: not the AITER fp4/fp8 BMMs, not AMX, and `q_pad_num_heads` unset.
- The KV cache is fp8 and the impl takes a quantized query.
- There is no DCP.
- AITER has a tuned config for (heads, `kv_lora_rank`, `qk_nope_head_dim`). This is checked per shape at M=128, like `_triton_gemm_config_is_tuned`'s other callers, so the shape's tuned large-M (`any`) config is used above the largest bucket.

**Head padding comes from the backend.** The asm decode's head count depends on the step: Gluon decode/verify and the DCP routes read the unpadded query. A new `MLAAttentionImpl.decode_query_padded_num_heads()` returns `None` by default. `AiterMLAImpl` returns the asm head count only when that step pads by repeating heads (`get_mla_padded_q`'s divisor case). `_forward_mqa` now also accepts a query that arrives at that count; `get_mla_padded_q` returns it unchanged, and `get_mla_unpadded_o` (`[:, ::2]`) unpads it as before.

**Numerics.** The kernel computes what the unfused path does: the fp32 accumulator is rounded to bf16, multiplied by `1 / q_scale`, clamped to vLLM's `get_fp8_min_max()` bound and cast to vLLM's fp8 dtype. Each head is then written twice, matching `repeat_interleave`.

**Limitations.**
- Tuned configs exist only for gfx950. On other archs the check returns false.
- CI: the MI355 "V1 Attention" step runs `test_mla_backends.py` with `VLLM_ROCM_USE_AITER=1`. The new test skips there until vLLM's ROCm image pins an AITER that includes the kernel.

**Related work.**
- #55230 fuses decode RoPE + MLA KV-cache write + fp8 query assembly through AITER's HIP `fused_qk_rope_concat_and_cache_mla`, also in this decode branch. Both PRs replace the q concat + fp8 quant, so they can't both run that op as written. This PR instead removes the W_UK BMM and the head pad with it (−668 µs per decode step here; #55230 reports −0.29 ms for its two launches). Folding RoPE and the KV write into this kernel would combine the two as a follow-up.
- #36573 (draft) fuses the AITER fp4/fp8 BMM variants with RoPE behind an env flag. This PR covers the default bf16 W_UK path and the head padding.
- Duplicate check: searched open PRs for fused BMM / W_UK / decode query / head pad / concat+quant on MLA and ROCm. Only the two above overlap, and neither covers the bf16 W_UK BMM or the head pad.
