# [CPU] Support FP16 in the GDN attention kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/60051) · state: open · merged: False

## Original PR description

CPU gated delta net was BF16-only on the AVX-512 path. This adds an FP16 tinygemm conv specialization and accepts float16 query, key, value, and beta in the chunked gated delta rule.



## Overview

On x86 CPUs that load the AVX-512BF16 `_C` extension, CPU GDN can run with float16 activations. The causal-conv tinygemm gains an `at::Half` specialization, and `chunk_gated_delta_rule_cpu` accepts float16 query, key, value, and beta. `cpu_gdn_attention_core` accepts BF16 or FP16 and still rejects other dtypes.

## Claims

- The width-4 causal conv tinygemm (prefill, varlen, decode update, and multi-token update) executes for float16 weights and activations when `vllm._C` is loaded. That is the extension built with AVX-512BF16, selected at runtime by `torch.cpu._is_avx512_bf16_supported()`.
- `chunk_gated_delta_rule_cpu` accepts a uniform float16 dtype for query, key, value, and beta. The gate `g` stays float32. Recurrent state may still be float16, bfloat16, or float32.
- ARM BF16 builds do not get an FP16 conv specialization. Float16 there still falls through to the scalar tinygemm stub.

## Validation

Validated on an fp16 supported machine after rebuilding `_C` with the unpacked float16 chunk GEMM: `46 passed, 129 deselected` in 94s (`pytest tests/kernels/mamba/cpu/test_cpu_gdn_ops.py -k "fp16_activations or conv_cpp"`). That is the four `test_chunk_gated_delta_rule_cpu_fp16_activations` cases plus the conv cases for both dtypes, all within `atol=1e-2`. That host is not this pod.

`tests/kernels/mamba/cpu/test_cpu_gdn_ops.py` is already on the Intel CPU kernel shard in `.buildkite/hardware_tests/cpu.yaml`. The cases named `fp16-representative` vary only the recurrent state; activations stay bfloat16, so they do not exercise this change. This branch adds:

- `test_chunk_gated_delta_rule_cpu_fp16_activations` for float16 query, key, value, and beta.
- `dtype=torch.float16` on `test_conv_cpp_matches_torch`, `test_conv_cpp_no_worse_than_torch_vs_fp32`, and `test_conv_cpp_weight_packed_matches_torch`. Float16 is skipped unless AVX-512BF16 is present, so ARM BF16 CI does not call the missing specialization.

```bash
pytest tests/kernels/mamba/cpu/test_cpu_gdn_ops.py -k "fp16_activations or conv_cpp"
```

## Details

`AT_DISPATCH_REDUCED_FLOATING_TYPES` already instantiated the conv and chunked GDN kernels for `Half` and `BFloat16`. `tinygemm_kernel` specialized only `at::BFloat16` under `CPU_CAPABILITY_AVX512` (`__AVX512F__ && __AVX512BF16__ && __AMX_BF16__` in `gemm.h`); float16 hit the scalar stub. `chunk_gated_delta_rule_cpu` required `kBFloat16` for query, key, value, and beta. Decode update and `fused_gdn_gating_cpu` were already dispatched on reduced floating types. The chunked AVX-512 `pack_vnni2` stored the float32 state with `_mm512_cvtne2ps_pbh` into a `scalar_t` buffer. For float16 that is a bfloat16 bit pattern, so the same helper now uses `vcvtps2ph` (`_mm512_cvtps_ph`, AVX-512F) when `scalar_t` is `at::Half`. The bfloat16 path still uses `cvtne2ps_pbh`. That store is not sufficient. `cpublas::brgemm` for `at::Half` with `is_vnni=true` is the oneDNN fp16 ukernel, whose B layout is not the BF16 VNNI pack this file writes, and this build's OpenBLAS has no half GEMM. Float16 chunk GEMMs therefore take the existing unpacked `blas_gemm` branches, and the half overload calls `gemm_no_downcast_stub` so the product accumulates in fp32. Bfloat16 stays on brgemm.

The float16 tinygemm keeps the BF16 packing: 32 fp16 values in VNNI pairs, weight laid out as `[K/2, BLOCK_N, 2]`. `causal_conv1d_weight_pack` copies those pairs as opaque 32-bit words for both reduced dtypes. Each pair is split with `_mm512_cvtusepi32_epi16` and converted with `_mm512_cvtph_ps`, then accumulated with `_mm512_fmadd_ps`. A signed pack would saturate every negative fp16. The dot is an fp32 product of converted fp16 values, with the same `K == 4` and block-N of 32 or 64 limits as the BF16 kernel. The kernel body is a copy of the BF16 tinygemm so the `vdpbf16ps` path stays unchanged. The chunk follow-up is in `fla.cpp` and `blas_gemm.h`. Tests are in `tests/kernels/mamba/cpu/test_cpu_gdn_ops.py`. No model runner, scheduler, or KV-cache manager changes, and no new GPU sync.

The compile guard requires the AMX-BF16 flags because that is how `conv.cpp` is built into `_C`. The FP16 kernel does not execute AMX tile instructions. `_C_AVX512` and `_C_AVX2` do not contain `conv.cpp`; those CPUs stay on the torch conv path, as before.
