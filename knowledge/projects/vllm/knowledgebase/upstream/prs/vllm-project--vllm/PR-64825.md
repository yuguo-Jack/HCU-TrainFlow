# [Perf] Capture prefill-sized CUDA graphs by default for Qwen3.5

[Upstream PR](https://github.com/vllm-project/vllm/pull/64825) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Since #51012 deprecated `torch.compile` for Qwen3.5-family models (Qwen3.5 / Qwen3.6 / Qwen3.8, dense and MoE), they run on breakable CUDA graphs on NVIDIA. A step above the largest captured size therefore has no compiled fallback: it runs fully eager and launches every op from Python. For other models, such a step still runs the torch.compile graph.

The default capture ceiling is 512 tokens on Hopper and other non-Blackwell GPUs, and 1024 on data-center Blackwell (`default_max_graph_size` in `VllmConfig._set_cudagraph_sizes`). As a result, on H100/H200 a single 1k-token prefill of a Qwen3.5-family model runs eagerly. #51012 measured prefill at parity on GB200, where the 1024 ceiling covers such a prefill, so this case was not covered there.

This PR changes the default only for these architectures, and only when the user has not set capture sizes. It also captures every 64 tokens above the ceiling up to 2048, clamped by `max_num_batched_tokens`. Users can already do this themselves with `cudagraph_capture_sizes`; this PR changes the default, which is what most deployments run.

## Claims

- **`Qwen/Qwen3.6-35B-A3B-FP8`, H200 TP1:** TTFT at concurrency 1 drops from 88.5 to 36.4 ms (−59%). TTFT p99 at concurrency 32 drops from 1087 to 554 ms (−49%). Output throughput rises 4.7% at concurrency 1 and 4.6% at concurrency 32.
- **Cost:** CUDA graph capture takes +7 s on Qwen3.6-35B-A3B (16 → 23 s) and +12 s on Qwen3.8-27B (13 → 25 s). The graph pool grows by 0.3 GiB (0.54 → 0.85 GiB) and 0.5 GiB (0.91 → 1.43 GiB) respectively. The KV cache shrinks by 0.8% (2,561,170 → 2,540,690 tokens) and 0.5% (889,287 → 885,191 tokens).
- **`Qwen/Qwen3.8-27B-FP8`:** TTFT −11.5% at concurrency 1 and −5.7% at concurrency 8. Throughput is unchanged. Median TPOT at concurrency 8 is +0.9% on average: +0.1% in one run and +1.7% in the other, while the three main runs are within 0.2% of each other. This is a real padding cost (see Details).
- **No change** for other architectures, for explicit `cudagraph_capture_sizes` / `max_cudagraph_capture_size`, or when the ceiling is lowered by a small `max_num_seqs`.

### Tests

`pytest tests/compile/test_config.py` on this branch rebased onto main `67d677bde`: 99 passed.

The new tests are `test_breakable_cudagraph_default_adds_prefill_capture_sizes` (5 cases), `test_breakable_cudagraph_prefill_capture_sizes_by_platform_and_mode` (4 cases) and `test_breakable_cudagraph_keeps_explicit_capture_size`. They cover:

- the extra grid for a Qwen3.5 architecture, and on data center Blackwell, where it starts above the 1024 ceiling;
- MTP (`num_speculative_tokens=2`): the uniform decode sizes stay within the ceiling and the grid is still added;
- clamping by `max_num_batched_tokens`;
- no change without breakable CUDA graphs, with `cudagraph_mode=FULL` (no piecewise graphs), or off CUDA;
- no change with a small `max_num_seqs`;
- no change for another breakable architecture (DeepSeek-V4.1);
- no change with an explicit `max_cudagraph_capture_size`.

Without the change, the cases that expect an extra grid fail and the rest pass.

## Details

- **Why it helps MoE most.** Qwen3.6-35B-A3B has 3B active parameters, so a 1k-token prefill is mostly launch overhead once it runs eagerly. The dense 27B prefill is mostly GPU work, so it gains less.
- **The TPOT cost on the dense model.** At concurrency 8, a step that mixes one prefill chunk with decodes (e.g. 1031 tokens) is now padded to the next captured size (1088). On a GPU-bound model those extra tokens cost compute, which shows up as +0.9% TPOT. A 128/256-token grid doubled that cost, which is why the grid is every 64 tokens.
- **Why only Qwen3.5.** Other architectures on breakable CUDA graphs by default (DeepSeek-V4.x, GLM-5-Next, Kimi, ...) were not measured. DeepSeek-V4.1 also sizes its decoder-replay graphs and input buffers from `max_cudagraph_capture_size`, so raising it there needs its own validation. Adding an architecture is a one-line change.
- **Platform and MTP.** The default applies on CUDA only, matching where Qwen3.5 moves to breakable CUDA graphs. With MTP, it is covered by the unit test above, but end-to-end serving with MTP was not measured.
- **Documentation.** The `max_cudagraph_capture_size` docstring documents the new default.
- **Relation to #63406.** #63406 separates prefill and decode capture sizes. On model runner V2, which these runs use, it deprecates `cudagraph_capture_sizes` / `max_cudagraph_capture_size` in favor of `max_prefill_cudagraph_capture_tokens` / `prefill_cudagraph_capture_token_sizes`. It raises the prefill default to 8192 tokens on SM100 only; other GPUs keep main's 512-token ceiling. So the Hopper case above stays open with or without it.
  - **Merge order.** If #63406 lands first, I will rebase this onto its prefill fields as a per-architecture default prefill grid. The rule stays the same: Qwen3.5 architectures, no explicit setting, 64-token steps up to 2048.
  - **Data relevant to #63406's padding concern.** On H200, extending Qwen3.5 prefill graphs to 8192 tokens made the dense 27B model's TTFT at concurrency 32 13% worse (the "Other capture grids measured" table above). A 2048 cap with 64-token steps avoids that.
