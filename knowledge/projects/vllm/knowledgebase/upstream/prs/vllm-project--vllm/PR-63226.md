# [ROCm] Enable the custom all-reduce on MI200 (gfx90a)

[Upstream PR](https://github.com/vllm-project/vllm/pull/63226) · state: open · merged: False

## Original PR description



## Overview

Enables vLLM's custom all-reduce on MI200 (gfx90a) by default. Today `RocmPlatform.use_custom_allreduce()` returns True only on gfx94x/gfx95x, so `ParallelConfig` turns it off on MI200 and every TP all-reduce goes through RCCL. On gfx90a, CUDA-graph capture copies inputs into the pre-registered buffer instead of IPC-registering the graph's buffers, which avoids the corruption reported in #61109. `VLLM_ROCM_CUSTOM_AR_GFX90A=0` falls back to RCCL. Split out of the discussion on #61109, whose one-island MI210 mode this overlaps (its two-island TP=8 path is unaffected).

## Claims

- On a fully XGMI-connected MI250X node, the custom all-reduce with copy-in is 1.2-3.7x faster than RCCL for all-reduces up to 1 MiB at TP=2/4/8 (2.1-3.5x at 64 KiB) and matches it bit for bit.
- With copy-in under capture, a TP8 x PP6 MoE model on MI250X with `FULL_DECODE_ONLY` graphs gives correct output (30/30 probe prompts, gsm8k 0.98) and +47% throughput per GPU over graphs with RCCL in ROCm's default environment.
- At TP=4, RCCL is faster from about 4 MiB, so on gfx90a the custom all-reduce is limited to 4 MiB there; TP=2 and TP=8 keep the 8 MiB default.
- AITER's all-reduce and QuickAllReduce keep their own CDNA3+ gates and stay off on gfx90a. Nothing changes on other architectures.

## Details

**Why copy-in.** Under graph capture, `CustomAllreduce.capture()` IPC-registers the addresses of the graph's input buffers so replays reduce in place. On gfx90a that path gave fluent but wrong text in the model above, and #61109 reports wrong sums on MI210 in the TP=2 x PP=2 graph test. Copying the input into the pre-registered buffer, as eager mode does (and as the cuMem graph-pool path already does), fixed it. `CudaCommunicator` therefore constructs `CustomAllreduce` with `register_graph_buffers=False` on gfx90a. The cost is one device-to-device copy of the input per all-reduce. We don't know the root cause of the registered-buffer corruption; this avoids the path rather than fixing it.

**Maximum size.** 4 MiB at TP=4 on gfx90a, and the default 8 MiB otherwise; inputs at or above the limit go to RCCL. We swept 64 KiB to 64 MiB on MI250X. The size at which RCCL catches up with copy-in:

| config | crossover |
|---|---|
| TP=2 | 6-28 MiB, depending on the pair of GCDs |
| TP=4 | 3-4 MiB |
| TP=8 | 8-12 MiB |

TP=4 matches the MI210 number reported in #61109 (about 3 MB). Between 4 and 8 MiB, copy-in at TP=4 takes 13-27% longer than RCCL, so `GFX90A_CUSTOM_ALL_REDUCE_MAX_SIZES` limits it to 4 MiB there, the way `CUSTOM_ALL_REDUCE_MAX_SIZES` does per world size on CUDA. A single limit for all of gfx90a would give up 1.35-1.6x at TP=8 in the same range.

**RCCL's scratch gap.** In ROCm's default environment, RCCL on gfx90a pays about 180 us per call: ROCr allocates its kernels' scratch for each dispatch and frees it afterwards. `HSA_SCRATCH_SINGLE_LIMIT=268435456 HSA_NO_SCRATCH_RECLAIM=1` keeps the scratch resident. vLLM's ROCm base images set `HSA_NO_SCRATCH_RECLAIM=1`. The microbenchmark above sets both variables; without them the custom kernel stays ahead to 16-64 MiB. The end-to-end run did not set them, so part of its +47% is that gap.

**Not tested.** MI210, including TP=2 across XGMI islands (the `world_size == 2` path that skips the fully-connected check).

**Changes.**
- `vllm/envs.py`: `VLLM_ROCM_CUSTOM_AR_GFX90A`, default on.
- `vllm/platforms/rocm.py`: `use_custom_allreduce()` returns True on gfx90a unless the variable is `0`.
- `vllm/distributed/device_communicators/cuda_communicator.py`: `register_graph_buffers=False` on gfx90a.
- `vllm/distributed/device_communicators/all_reduce_utils.py`, `custom_all_reduce.py`: the 4 MiB limit at TP=4 on gfx90a.
- `tests/platforms/test_rocm_custom_allreduce.py`: the platform gate.
