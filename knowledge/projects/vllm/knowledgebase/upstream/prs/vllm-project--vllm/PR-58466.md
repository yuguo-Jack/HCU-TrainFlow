## Original PR description

### Benchmarks: adaptive verification with and without batch-sharded sampling

**Setup.** 4x GB200, TP4 + expert parallel, vLLM `main` @ 13058faa49 + this PR.
`deepseek-ai/DeepSeek-V4-Flash-DSpark`, `--speculative-config '{"method":"dspark","num_speculative_tokens":7,"draft_sample_method":"probabilistic","enable_adaptive_verification":true}'`,
`--max-num-seqs 256 --max-model-len 32768 --block-size 256 --kv-cache-dtype fp8 --moe-backend deep_gemm --enable-expert-parallel --no-enable-prefix-caching --kernel-config.enable_flashinfer_autotune=False`,
`--compilation-config '{"max_cudagraph_capture_size": 2048}'` (so 256 requests x 8 tokens stay under CUDA graphs; the default 1024 falls back to eager above 128 requests).
Both arms have adaptive verification enabled; the sharded arm adds `--enable-batch-sharded-sampling`.

**Client.** `vllm-bench` (Rust), SPEED-Bench `throughput_2k` (all categories), 2048 output tokens, temperature 1.0, no top-p/top-k, `--num-warmups <conc>`, prompts = 8x concurrency (min 32, max 1024).

**Method.** 4 server boots in ABBA order (shard, base, base, shard), 2 full concurrency sweeps per boot, so n=4 per cell; a throwaway warmup run at conc 256 after each boot absorbs first-request JIT. Each boot was checked for the "Batch-sharded sampling enabled" log line count (4 for shard, 0 for base). Delta = shard vs base; negative ITL/TPOT/TTFT is better, positive tok/s is better.

**Result: no regression.** Throughput, TPOT and TTFT are flat within run-to-run noise at every concurrency (tok/s sd is 0.2-2.5% per cell; TTFT sd 1-3%). Median ITL, the lowest-noise metric here (sd 0.01 ms per cell through conc 64), is at parity through 128 and 1.55% better with sharding at 256. Acceptance length matches between arms at every concurrency, i.e. the sharded verify is distribution-equivalent under adaptive verification.
