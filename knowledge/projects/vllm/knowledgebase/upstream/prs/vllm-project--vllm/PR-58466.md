# [Sampling] Add adaptive verification support to batch-sharded sampling

[Upstream PR](https://github.com/vllm-project/vllm/pull/58466) · state: closed · merged: True

## Original PR description

## Context
Batch-sharded sampling does not currently support adaptive verification: https://github.com/vllm-project/vllm/blob/7e3d55956577605838e9babcba84dce354b0b78c/vllm/config/vllm.py#L3144-L3157

Batch sharding sizes its `all_to_all_single` splits and buffers from host-side per-request logit counts (`cu_num_logits_np`). Under adaptive verification, the per-request split of the draft budget is decided on device, so `cu_num_logits_np` only holds the scheduled counts (an upper bound), while the device `cu_num_logits` holds the admitted counts. Once the budget binds, the shard plan built on the host no longer matches the rows placed on device.

## This PR
When the draft budget binds, `reallocate_drafts` copies the per-request admitted draft counts to the host (async D2H on adaptive verification's copy stream). `shard_sampler_inputs` waits on that copy and builds the shard plan from the exact admitted counts, so the lm_head GEMM (`compute_logits_local`), the all-to-all, and the sampler run only on the rows that are actually verified. When the budget does not bind, the host counts are already exact and nothing is copied. The copy is only enabled when batch-sharded sampling is on (`copy_admitted_drafts_to_host`).

Also: the local draft count now follows the admitted budget, so with a budget of 0 every rank runs the same sampler as the replicated path.

### Tradeoff
The alternative is to keep the host's scheduled counts and pad each rank's segment up to them, which avoids any host wait but runs the GEMM, all-to-all, and sampler on the padded rows too. This PR instead adds a host wait in `sample()` on the admitted counts. It blocks the CPU only (the base model forward is already queued behind it), but it limits CPU run-ahead: the CPU cannot launch step N's sampling until the GPU has started step N. That costs ~0.05 ms per step at concurrency 1 on DeepSeek-V4-Flash. The cost shrinks as the forward gets longer, so it matters least for large models at high concurrency, which are the cases batch-sharded sampling targets.

## Benchmarks

**Setup.** 4x GB200, TP4 + EP, vLLM `main` @ 7e3d559565 + this PR. `deepseek-ai/DeepSeek-V4-Flash-DSpark`, `--speculative-config '{"method":"dspark","num_speculative_tokens":7,"draft_sample_method":"probabilistic","enable_adaptive_verification":true}'`, `--max-num-seqs 256 --max-model-len 32768 --block-size 256 --kv-cache-dtype fp8 --moe-backend deep_gemm --enable-expert-parallel --no-enable-prefix-caching --kernel-config.enable_flashinfer_autotune=False --compilation-config '{"max_cudagraph_capture_size": 2048}'`. Both arms use adaptive verification; the sharded arm adds `--enable-batch-sharded-sampling`.

**Client.** `vllm-bench`, SPEED-Bench `throughput_2k` with placeholder prompts removed (905 prompts), max 2048 output tokens with natural EOS, temperature 1.0, `--num-warmups <conc>`, prompts = 8x concurrency (min 32, max 1024).

**Method.** Adaptive verification profiles its cost curves at every boot, and boot-to-boot differences in the curves moved median ITL by up to ~10% at some concurrencies, which swamped the effect. So the curves were saved from the first boot and loaded on every later boot (a benchmark-only patch, not part of this PR), and both arms make identical admission decisions. 4 boots in ABBA order, 2 sweeps per boot. One base boot was excluded for anomalously slow tail steps (−9 to −17% tok/s, with median ITL and acceptance normal), so n=2 for base and n=4 for sharded. Negative ITL/TPOT/TTFT is better.

**Result.** With the cost curves pinned, median ITL is consistent across boots (0.1–0.4% sd), and sharded sampling lowers it by 0.3–1.2% from concurrency 16 upward, growing with concurrency. At concurrency 1 it is +0.05 ms (+0.6%) on every run, which is the cost of the host wait. End-to-end throughput and TPOT are flat within run-to-run noise (tok/s sd 0.8–2.7%), because the median step improves while end-to-end time is dominated by slow prefill-heavy steps that sampling barely affects. Acceptance length matches at every concurrency.

I wasn't expecting to see an improvement in tok/s or TPOT, but rather to not regress it for the batch-sharded sampling cases. The main benefit of batch-sharded sampling is reducing the maximum target logits allocations by a factor of TP size from `B x (K + 1) x V => B x (K + 1) x V / P`.

### Block verification, top-p 0.95

Same setup and method as above, with `"rejection_sample_method":"block"` added to the speculative config and `--top-p 0.95` on the client, at concurrency 64-256. Cost curves pinned across boots; 4 boots in ABBA order, 2 sweeps per boot, n=4 per arm. Negative ITL/TPOT/TTFT is better.

Median ITL improves by 1.7-2.7%, about twice the gain with standard rejection sampling. Throughput and TPOT are flat at concurrency 64-128 (tok/s sd 0.7-2.5%) and improve at 256. Acceptance length matches at every concurrency. This optimization is more worthwhile when the sampling operations are more expensive.
