# [Bugfix][Mamba] Warm up the SSD kernels on a prefill-sized sequence

[Upstream PR](https://github.com/vllm-project/vllm/pull/60800) · state: open · merged: False

## Original PR description

### Purpose

Warm up the Mamba2 SSD Triton kernels on up to 32 chunks instead of one, so the autotuned tile suits real prefills. Extends the warmup added in #39822. Related: #60801 (tensor-descriptor path for the same kernels), whose reproducible results depend on this fix. No other PR does this (searched open and merged PRs for SSD, warmup and autotune; #48363 warms other kernels).

The Mamba2 SSD Triton kernels are autotuned on their first call: the one-chunk `MambaMixer2._warmup_ssd_kernels` during the profile run. The autotune keys have no sequence-length term, so that pick is reused for every later prefill (and cached on disk with `TRITON_CACHE_AUTOTUNING=1`). On one chunk many tiles tie within noise; on a real prefill the grid is `nchunks` times larger and tiles differ by multiples. Which tile wins the tie is random per start, so a start can lock in a slow one.

This PR warms up on `clamp(projected_states.shape[0] // chunk_size, 1, 32)` chunks. The profile run has `max_num_batched_tokens` rows, so Nemotron-3-Nano-4B (chunk size 256) warms up on 32 chunks by default.

### Results

Nemotron-3-Nano-4B-BF16, TP=1. Each sample is a fresh server start; picks are scored against a timing of all tiles at 4x2048.

| GPU | warmup | starts with a state / scan tile >1.05x slower than best |
| --- | --- | --- |
| H200 | 1 chunk (before) | 24/30 (up to 1.55x) / 4/30 (up to 1.45x) |
| H200 | 32 chunks | 0/30 / 0/30 |
| B200 | 1 chunk (before) | 28/30 (up to 1.61x) / 12/30 (up to 1.53x) |
| B200 | 32 chunks | 0/30 / 0/30 |
| Arc Pro B70 | 1 chunk (before) | bad tile in 10/12 emulated starts (9/12 over 1.5x) |
| Arc Pro B70 | 32 chunks | 0/12 |
| Arc Pro B60, Falcon-H1-0.5B / Ultra TP=8 shape | 1 chunk (before) | scan: 10/10 (up to 1.43x) / 6/10 (up to 1.34x) |
| Arc Pro B60, Falcon-H1-0.5B / Ultra TP=8 shape | 32 chunks | 0/10 / 0/10 |

Nemotron-3-Nano-4B on B60 is unaffected (0/23 before, 0/20 after). `vllm bench latency --output-len 1`, 4 x 2048, mean of fresh starts, before -> after:

| GPU | latency |
| --- | --- |
| H200 | -2.0% |
| B200 | -6.1% |
| Arc Pro B70 | 658-835 ms -> 641-648 ms (-11.1% mean, 7 starts, none slower) |

Autotune time per start (sum of the "Triton autotuning finished after" times), before -> after:

| GPU | 1 chunk | 32 chunks |
| --- | --- | --- |
| H200 (32 starts) | 49.1 s | 50.1 s |
| B200 (32 starts) | 48.5 s | 52.5 s |
| Arc Pro B70 (9 starts, median, compiled kernels cached) | 26.4 s | 22.2 s |

B200 grows with the number of chunks (48.3 s at 1, 49.2 s at 4, 51.2 s at 16, 52.4 s at 32); H200 stays flat. KV-cache memory is unchanged. With 8 chunks there are already no slow picks on H200 and B200 (4 chunks: 1/12 on H200).

Reproduce: start the server (or `vllm bench latency --model nvidia/NVIDIA-Nemotron-3-Nano-4B-BF16 --input-len 2048 --output-len 1 --batch-size 4 --max-model-len 2304 --no-enable-prefix-caching --seed 42`) with `TRITON_PRINT_AUTOTUNING=1` and fresh `TRITON_CACHE_DIR` and `VLLM_CACHE_ROOT`; the picked tile of each SSD kernel is printed.

Tests: `tests/kernels/mamba/test_mamba_ssm_ssd.py` passes (H200, B200, Arc Pro B60). gsm8k 5-shot (first 250 problems), before vs after: H200 0.868 vs 0.868, B200 0.864 vs 0.868 (stderr about 0.02).

### Notes

- A Triton cache from an older start keeps its old picks until it is cleared.
- Not covered: other Mamba2 models and chunk sizes, other Triton versions, ROCm.
- AI assistance (Claude) was used for parts of this change and the measurements.
