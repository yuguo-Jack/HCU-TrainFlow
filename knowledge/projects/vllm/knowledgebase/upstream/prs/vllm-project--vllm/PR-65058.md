# [Bugfix][Kernel] Fix two block-FP8 linear crashes on SM12x

[Upstream PR](https://github.com/vllm-project/vllm/pull/65058) · state: open · merged: False

## Original PR description



## Overview

Fixes two crashes that stop `--quantization fp8_per_block` from serving on SM12x. The CUTLASS block-FP8 kernel is picked for shapes it cannot run, and a NaN in CUDA-graph padding rows makes DeepGEMM trap. Related: #49783, #56290, #41427.

## Claims

- `google/gemma-4-26B-A4B-it --quantization fp8_per_block` starts and serves on SM120 with default kernels.
- Block-FP8 models whose linears use DeepGEMM (e.g. `Qwen/Qwen3-0.6B`) no longer crash on the first padded batch under torch.compile + CUDA graphs.
- Nothing else changes: only the shapes CUTLASS fails on move to another kernel, and native scales change only for groups that contain NaN. Greedy output is byte-identical.

## Validation

RTX PRO 6000 Blackwell (SM 12.0), main `b8c04dd` nightly wheel, default kernels, no env vars.

```bash
vllm serve google/gemma-4-26B-A4B-it --load-format dummy --quantization fp8_per_block \
  --language-model-only --max-model-len 4096 --gpu-memory-utilization 0.43
```

## Details

**Fix 1: CUTLASS shape gate.**
- `CutlassFp8BlockScaledMMKernel.can_implement` does not check shape. On SM12x it gets every layer that DeepGEMM (N % 64, K % 128) and B12x (N, K % 128) decline.
- The SM120 CUTLASS blockwise GEMM returns `Invalid status` when N or K is not a multiple of 128. The existing `test_block_fp8.py -k cutlass_matmul` (N = 576) fails 5/5 on this GPU, and Gemma 4's shared-MLP `down_proj` has K = 2112.
- "A is not packed" is only the first check to trip. With a contiguous A, the kernel still returns `Invalid status` for K = 2112 and N = 2880.
- The gate is SM12x-only because only the SM120 kernel has this limit (see Other platforms). Declined layers fall through to the next kernel in the list, Marlin.

**Fix 2: NaN-safe native group quant.**
- Under torch.compile, `QuantFP8` runs `_quantize_group_native`. Its `abs().max()` propagates NaN; the CUDA kernel's `fmaxf` skips it.
- Rows padded for CUDA graphs can hold stale memory. Their outputs are discarded, but one NaN there gives a NaN scale.
- DeepGEMM's `pack_fp32_into_ue8m0` then traps. A coredump shows `DG_TRAP_ONLY_DEVICE_ASSERT((values[j].x & 0x807fffffu) == 0)`.
- On main, Qwen3-0.6B serves in each of these setups:
  - `cudagraph_mode NONE`
  - `mode 0` with FULL graphs
  - `+quant_fp8`
  - prompts of exactly a capture size (8 tokens, so no padded rows); a 5-token prompt after them crashes.
- `MatcherQuantFP8` calls `QuantFP8`, so the fusion patterns pick up the change.

**Other platforms.**
- **Fix 1.** In CUTLASS v4.7.1, the SM120 blockwise mainloop's `can_implement` requires M, N and K to be divisible by the scale and tile sizes (`sm120_mma_tma_blockwise_scaling.hpp`). With vLLM's SM120 configs, that means N % 128 == 0 and K % 128 == 0 for every M.
  - The SM90 and SM100 mainloops only check TMA alignment, and `test_w8a8_block_fp8_cutlass_matmul` (N = 576) runs on H100 in CI.
  - So the gate leaves those archs alone. Applying it there would send such shapes to Marlin whenever DeepGEMM is off.
- **Fix 2** runs on every platform under torch.compile, and only groups that contain NaN get a different scale.
  - SM100: DeepGEMM packs fp32 scales to UE8M0 with the same `smxx_layout.cuh` kernel, so it likely crashes the same way (not measured).
  - SM90: DeepGEMM keeps fp32 scales (`FLOAT32_CEIL_UE8M0`), so the fix only removes NaN scales from rows that are thrown away.
- **Cost.** Inductor still emits one kernel for `_quantize_group_native`, and its time is unchanged within noise. Measured for M = 1 to 4096 and K = 2816 and 7168; for example, at M = 4096, K = 7168 it is 65.2-65.7 µs on main and 64.1-64.6 µs with the fix.

**Limitations.**
- Only SM120 was measured.
- Not covered:
  - The CUTLASS GEMM itself.
  - NaN in the per-token and per-tensor native paths (#41427).
  - The uninitialized TMA padding in the CUDA path behind #49783 and #56290.
