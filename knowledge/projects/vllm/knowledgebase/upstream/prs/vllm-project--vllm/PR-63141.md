# [Bugfix][Spec Decode] Fail fast when a PP MTP drafter has no input embedding

[Upstream PR](https://github.com/vllm-project/vllm/pull/63141) · state: open · merged: False

## Original PR description



## Overview

Under pipeline parallelism, `DeepSeekMTP` and `DeepseekV32MTP` now raise at load time when the draft checkpoint has no input embedding, instead of drafting from an uninitialised `embed_tokens`. The error names the tensor to add. Fixes #63128 (option (a) from the issue).

## Claims

- With PP > 1 and a draft-only MTP checkpoint without `embed_tokens`, loading fails with:
  `The MTP draft checkpoint has no input embedding. Under pipeline parallelism the drafter cannot share the target model's embed_tokens, so add them to the draft checkpoint as 'model.layers.<N>.embed_tokens.weight'.`
  Before, the load succeeded and acceptance silently collapsed (~0.2 instead of ~0.78 in the issue).
- No change when the embedding is loaded, under the layer-local name (`model.layers.<N>.embed_tokens.weight`) or the top-level one (`model.embed_tokens.weight`, #46994).
- No change without PP: the proposer shares the target's embedding there.
- No change for partial weight reloads (`disable_mtp_completeness_check()`), which skip the check like the existing MTP layer completeness check.

## Validation

```bash
pytest tests/model_executor/model_loader/test_mtp_validation.py
```

- 4 new tests: missing under PP raises, loaded under PP passes, missing without PP passes, and the check follows `disable_mtp_completeness_check()`. All 5 tests in the file pass.
- The GPU e2e test `tests/v1/e2e/spec_decode/test_mtp_parallel_load.py::test_deepseek_mtp_load_inline[pp2]` uses the separate draft `luccafong/deepseek_mtp_draft_random`. I checked its safetensors header: it contains both `model.embed_tokens.weight` and `model.layers.10.embed_tokens.weight`, so it still loads.
- `pre-commit run` on the changed files passes (including mypy).

Validated on CPU only; I did not run a PP > 1 MTP model end to end. The new tests run in CI under the existing `model_executor` step.

## Details

**Root cause:** `_maybe_share_embeddings` in the V1 proposer shares the target's embedding only when `get_pp_group().world_size == 1`. The V2 `maybe_share_target_embed` also returns early for drafters without `has_own_embed_tokens`. So under PP, the MTP drafter's `embed_tokens` must come from the draft checkpoint. When it doesn't, nothing reports it: the `loaded_weights` check counts the embedding as initialised because `UnquantizedEmbeddingMethod` has `process_weights_after_loading`.

**Fix:** a helper `validate_mtp_embed_tokens_loaded()` next to the existing scoped completeness flag in `model_loader/mtp_validation.py`, called at the end of `load_weights` in `DeepSeekMTP` and both `DeepseekV32MTP` variants (NVIDIA, AMD). Those cover the DeepSeek-V3/V3.2 and GLM-5 (`glm_moe_dsa`) MTP heads named in the issue; `Dots3NoteMTP` inherits it.

**Notes for reviewers:**

- I put the check in the loaders rather than the proposer because only `load_weights` knows which tensors came from the checkpoint, and it covers both model runners.
- Option (b) from the issue (loading the target checkpoint's embedding into the drafter under PP) would avoid the manual step, but #57171 tried that for `glm5next` and was closed. Happy to follow up if you'd prefer it.
- Other MTP heads may have the same gap under PP. I kept this to the classes named in the issue; I can extend the helper to others in a follow-up.
