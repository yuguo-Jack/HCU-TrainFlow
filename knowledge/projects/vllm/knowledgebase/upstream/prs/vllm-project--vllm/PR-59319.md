# [Bugfix][Attention] Skip the FlashMLA sparse bf16 prefill workspace on the fp8 mixed-batch path

[Upstream PR](https://github.com/vllm-project/vllm/pull/59319) · state: open · merged: False

## Original PR description

## Purpose

`FlashMLASparseImpl.__init__` reserves the bf16 prefill KV workspace (`5 * max_model_len * head_size * 2` bytes) for every quantized DS-MLA cache. Only the separate prefill/decode path reads it: the mixed-batch path, which the builder selects below `MIN_HEADS_FOR_BF16_PREFILL` heads per rank (`fp8_use_mixed_batch`), runs the fp8 decode kernel over the whole batch and never touches it. The reservation still comes out of the KV cache budget.

At long context the buffer is not small. The note in `get_prefill_workspace_size` sizes it at ~900 MB for `max_model_len=163840` and calls it free because it sits under the MoE workspace; at `max_model_len=786432` and `head_size=576` it is 4.22 GiB per rank.

The three buffers added in #57575 (padded query, padded output, output; 1.19 GiB at `max_num_batched_tokens=8192` with 16 heads padded to 64) stay reserved on both paths. The mixed-batch path does not read them on main today, but #60220 stages the mixed-batch kernel's q and out in them, and it unpacks them from the end of `workspace_specs`. The first revision of this PR dropped them too; with #60220 applied that fails on the first forward.

Measured on `Inferact/GLM-5.3-NVFP4`, TP4 + DCP4 (16 heads per rank, mixed-batch path), `fp8_ds_mla`, `--max-model-len 786432 --max-num-batched-tokens 8192 --gpu-memory-utilization 0.945`, MTP 3, 4x H200, nightly `af7f9488c`:

| | before | first revision (all prefill buffers skipped) |
|---|---:|---:|
| `Model loading took` (per rank) | 116.55 GiB | 111.15 GiB |
| GPU KV cache size | 913,664 tokens | 1,045,248 tokens |

The current revision keeps the 1.19 GiB of #57575 buffers, so it should free 4.22 of those 5.40 GiB per rank, roughly 1.016M KV tokens on this config. I have not re-measured it on the serving config.

Changes:

- `FlashMLASparseImpl._use_fp8_mixed_batch(num_heads, use_hisparse, pcp_dcp_kv_gather)` holds the condition; the metadata builder and the impl both call it, so the two cannot drift.
- The impl computes `pcp_dcp_kv_gather` and `fp8_use_mixed_batch` up front and appends the `max_model_len`-sized prefill buffer (and the PCP+DCP gather buffer) only when the separate path is selected. The `max_num_batched_tokens` buffers are appended on both paths.
- `forward_mqa` asserts `attn_metadata.fp8_use_mixed_batch == self.fp8_use_mixed_batch` before dispatching on the fp8 cache. If the two ever disagreed, the separate path would fail on unpacking `get_simultaneous(*self.workspace_specs)`; the assert names the cause instead.
- The dead `assert vllm_config is not None` is gone (`get_current_vllm_config()` raises rather than returning `None`).

Freeing this reservation also removes slack that was quietly covering an unprofiled transient in the DCP top-k merge of the sparse indexer; that one is filed as #59317 (fix in #59367). Our measurements above keep the default cudagraph memory estimate, which leaves enough headroom for it.

Not a duplicate: `gh pr list --state open --search` for "flashmla sparse workspace", "mixed batch prefill workspace" and "prefill workspace mixed batch sparse" turns up no PR that gates this reservation. #57575 (merged) moved the reservation before KV cache sizing, which is what made the cost visible; #56902 (merged) releases stale views after workspace growth; #42856 (open) lowers the multiplier on SM120 only; #60220 (open) reuses the `max_num_batched_tokens` buffers on the mixed-batch path, which this revision keeps.
