# [ROCm][Qwen4Exp] Support HC and MoE sequence parallelism on ROCm

[Upstream PR](https://github.com/vllm-project/vllm/pull/61471) · state: closed · merged: True

## Original PR description

Ports Qwen4Exp GR/PLE and MoE sequence parallelism from #56322 to ROCm. Until now `--enable-hc-sp` was CUDA-only, and on ROCm every DP>1 + EP + TP>1 Qwen4Exp config failed at startup with `NotImplementedError`, because those configs turn on MoE SP.

The AMD model runs under `torch.compile`, and vLLM drops Dynamo guards. The `num_tokens % tp` padding branch in the SP helpers was therefore traced once at the profiling size and reused for every batch, returning the wrong rows for other token counts. While compiling, both helpers now go through custom ops whose fake implementations use `cdiv`. Eager callers, which includes every CUDA user, run the same code as before.

For the same reason the AMD path does not shard `forward_context.is_padding`. Dynamo applies that assignment only after the graph runs, so the opaque `moe_forward` op would still read the old mask. Routers then use a prefix of the full-batch mask, which never marks a real local token as padding. This only reduces padding skipping, and the compiled Qwen3-Next MoE SP path already behaves this way.

The decode cost comes from collectives. ROCm has no custom all-gather or reduce-scatter yet, so SP falls back to RCCL: in graph-replayed microbenchmarks, all-gather plus reduce-scatter is 2.95x slower than the custom all-reduce at 32 tokens and 1.15x at 8K. That also limits the prefill gain. Wiring the AITER custom all-gather and reduce-scatter into the TP communicator is left for a follow-up.

- Port the SP changes from #56322 to the AMD Qwen4Exp model, MTP drafter and PLE layer
- Relax the CUDA-only gates for `--enable-hc-sp` and MoE SP to CUDA or ROCm
- Route `sp_shard` and `sp_reduce_scatter` through opaque custom ops while compiling; the eager path is unchanged
- Skip the ETP reduction in the pinned PLE lookup when SP reduce-scatters instead
- Run `test_tpsp.py` on ROCm, add a compiled SP ops test, and cover the AMD MTP path in `test_config.py`
- Add an MI355 Qwen4 Exp SP step to `test-amd.yaml` and the `models_distributed.yaml` mirror

All runs on MI355 (gfx950) with Qwen/Qwen3.8-Flash-Next-FP8, MRV2, FULL_AND_PIECEWISE cudagraphs.

**Accuracy with SP** (GSM8K, all 1319 questions, chat, greedy, thinking off, ±0.46% stderr):

| Config | GSM8K |
|---|---|
| TP2 baseline | 97.04 |
| TP2 + `--enable-hc-sp` (pinned FP8 PLE) | 97.12 |
| TP2 + `--enable-hc-sp`, device PLE | 97.19 |
| TP4 + `--enable-hc-sp` | 97.12 |
| DP2/TP2/EP4 MoE SP (runs 1 / 2) | 97.04 / 97.27 |
| DP2/TP2/EP4 MoE SP, ETP=4 (`embedding_across_dp`) | 97.04 |
| TP2 + MTP3, without / with SP | 97.19 / 96.97 |

MTP draft acceptance is identical with and without SP (0.8552). Teacher-forced logprobs, with each request scored at batch size 1 with a unique `cache_salt`, move less with SP (mean \|Δ\| 0.065-0.077) than when relaunching the same server (0.119) or switching TP2 to TP4 (0.137). Errors don't cluster at the shard boundary, the padded row, or odd lengths.

**Performance with SP** (TP2, prefix caching off, `vllm bench serve` random dataset, median of 3, spread < 1%):

| | SP off | SP on | Δ |
|---|---|---|---|
| 8K prefill TTFT (C2) | 1096 ms | 1085 ms | +1.1% |
| 16K prefill TTFT (C2) | 2144 ms | 2105 ms | +1.8% |
| Decode TPOT (C32) | 17.71 ms | 19.64 ms | -10.9% |

**No regression with SP off** (main and this PR served concurrently on separate GPUs, alternating every run; `vllm bench serve` median of 5, `lm_eval` GSM8K 5-shot chat median of 3):

| Config | Speed, PR vs main | GSM8K main → PR |
|---|---|---|
| TP2 | within ±0.5% on all workloads | 96.74 → 96.74 |
| TP2 + MTP3 | within ±0.5% | 96.89 → 96.74 |
| DP4/TP1/EP4 | within ±1% | 96.82 → 96.66 |

Workloads were 8K/16K prefill (C2), decode at C1 and C32, and 1K in / 1K out at C64. The few prefill gaps that did not overlap flipped sign when the two builds swapped GPUs, so they come from the GPU pairs.
