# [Bugfix][Anthropic] Map vLLM error types to Anthropic error.type vocabulary

[Upstream PR](https://github.com/vllm-project/vllm/pull/62294) · state: open · merged: False

## Original PR description

## Overview

Part of #57997. `translate_error_response()` now maps vLLM's internal error types to Anthropic's documented `error.type` vocabulary (e.g. `not_found_error`, `invalid_request_error`, `api_error`) instead of copying names like `NotFoundError`.

The validation-envelope half of #57997 is already covered by open PR #58023, so this PR intentionally does not touch that path.

## Claims

- Unknown model on `/v1/messages` returns `{"type":"error","error":{"type":"not_found_error",...}}` while keeping HTTP 404.
- Other statuses map to Anthropic types: 400/422 -> `invalid_request_error`, 401 -> `authentication_error`, 403 -> `permission_error`, 404 -> `not_found_error`, 413 -> `request_too_large`, 429 -> `rate_limit_error`, 5xx -> `api_error`, 529 -> `overloaded_error`.
- HTTP status code and message are preserved.

```json
{"type":"error","error":{"type":"not_found_error","message":"The model `does-not-exist` does not exist. Valid aliases: Qwen3.5-4B."}}

```

Control: the same validation error on `/v1/messages` still uses the existing OpenAI-shaped envelope (`HTTP 400`), confirming this PR only changes `error.type` translation.

## Details

Root cause: `translate_error_response()` copied `ErrorResponse.error.type` verbatim. vLLM builds that field from internal exception class names (`NotFoundError`, `BadRequestError`, `InternalServerError`, ...), but Anthropic SDKs dispatch on the snake_case values defined by the Anthropic API.

Approach: derive the Anthropic type from the HTTP status code, which `create_error_response()` already sets consistently, and fall back to `api_error` for 5xx / `invalid_request_error` for other 4xx. This also normalizes `GracefulHTTPError`, whose type is currently an HTTP phrase (e.g. `"Bad Request"`).

Tradeoff: status-based mapping is intentionally coarse. Anthropic's public API distinguishes `request_too_large` (413) and `overloaded_error` (529), which the mapping handles explicitly. Other 4xx statuses collapse to `invalid_request_error`, matching Anthropic's client-facing behavior.

## Not duplicating existing work

- #58023 covers the validation-envelope half (`RequestValidationError` handling) and is still open; this PR does not modify it.
- #43380 adds a `VLLMValidationError -> invalid_request_error` branch at 400 for the two endpoints; this PR generalizes the mapping in `translate_error_response()` for all statuses, including 404/429/5xx.
- #59968 fixes authentication-middleware envelopes; that path does not go through `translate_error_response()`.
