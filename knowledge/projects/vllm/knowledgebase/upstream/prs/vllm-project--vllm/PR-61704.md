# Revert "[Build] Update deep_gemm git tag for locality_domain update (#61491)"

[Upstream PR](https://github.com/vllm-project/vllm/pull/61704) · state: closed · merged: False

## Original PR description

Reverts #61491 (`ded7ae35e56f8304f8232fadd890804929527247`). Clean `git revert`; no later commits on `main` touch these files.

## Why

The postmerge `:docker: Build image` step on main fails to compile DeepGEMM's `_C_extension` ([Buildkite #94919](https://buildkite.com/vllm/ci/builds/94919#01a13bf4-d805-4e28-a1c7-bd524ab84ad7)):

```
csrc/utils/torch_compat.hpp:50:23: error: call of overloaded 'bitwise_and(const torch::stable::Tensor&, torch::stable::Tensor)' is ambiguous
  candidate: deep_gemm::torch_compat::bitwise_and(const Tensor&, const Tensor&)
  candidate: torch::stable::bitwise_and(const Tensor&, const Tensor&)   // torch/csrc/stable/ops.h:1170
```

The same error repeats for `bitwise_or`, `bitwise_left_shift`, `bitwise_right_shift` and `floor_divide`. The new DeepGEMM tag builds as a `TORCH_STABLE_LIBRARY` extension with its own compat helpers. torch 2.14, which main now installs, ships these ops in `torch/csrc/stable/ops.h`. Because the arguments are `torch::stable::Tensor`, the compiler also finds the torch versions, and the unqualified calls become ambiguous.

The PR's own CI ([#94667](https://buildkite.com/vllm/ci/builds/94667)) passed only because the whole `csrc-build` stage was a Docker cache hit from a torch 2.13 build. DeepGEMM was never compiled against torch 2.14 there.

## Re-landing

Fix the vLLM DeepGEMM fork so the internal calls in `torch_compat.hpp` are fully qualified (e.g. `torch_compat::bitwise_and(...)`), or drop those helpers when torch already provides them. Then bump the tag again.
