# [ROCm] Rank TRITON_ATTN above unified attention on gfx950 until the aiter pin has the #62606 fix

[Upstream PR](https://github.com/vllm-project/vllm/pull/62813) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

On gfx950, `TRITON_ATTN` now ranks right above `ROCM_AITER_UNIFIED_ATTN` in ROCm attention auto-selection, for every model. This is a temporary workaround for #62606: unified attention gives wrong output on gfx950 for some KV cache sizes, and vLLM's aiter pin (v0.1.26) does not have the fix (ROCm/aiter#6661, released in aiter v0.1.27). Other GPUs are unchanged.

Related:
- #62606: the unified attention bug on gfx950.
- #61433 (draft, paused): ranks unified attention above `ROCM_ATTN` for spec decode and hybrid models, for performance. It removes this rule after the pin bump.

## Claims

- On gfx950, runs that do not get `ROCM_ATTN` (KV connector runs, encoder-decoder models, layers `ROCM_ATTN` cannot serve) select `TRITON_ATTN` instead of unified attention. This avoids the wrong output from #62606 until the aiter pin includes ROCm/aiter#6661.
- Nothing else changes. `ROCM_ATTN` stays first, `ROCM_AITER_FA` stays first when `VLLM_ROCM_USE_AITER=1`, and unified attention still works when selected with `--attention-backend`.

Resulting order of the three backends on gfx950:

| | main | this PR |
| --- | --- | --- |
| default | `ROCM_ATTN` > unified > `TRITON_ATTN` | `ROCM_ATTN` > `TRITON_ATTN` > unified |
| with a KV connector (`ROCM_ATTN` excluded) | unified > `TRITON_ATTN` | `TRITON_ATTN` > unified |

## Details

**Root cause.** On gfx950, unified attention gives wrong output when a layer's KV cache is 2–4 GiB (#62606). Requests whose KV sits in blocks past 2 GiB get attention output unrelated to their context. With prefix caching on (the default), a server reaches those blocks once about 2 GiB per layer has been allocated in total. The fix is in aiter (ROCm/aiter#6661), so vLLM gets it only with a pin bump.

**Change.** A self-contained step at the end of `_get_backend_priorities`, so that it is easy to revert:

```python
# TODO(#62606): remove once the aiter pin includes ROCm/aiter#6661.
# ROCM_AITER_UNIFIED_ATTN gives wrong output on gfx950 for some KV cache
# sizes, so rank TRITON_ATTN right above it there.
unified = AttentionBackendEnum.ROCM_AITER_UNIFIED_ATTN
if on_gfx950() and unified in backends:
    backends.remove(AttentionBackendEnum.TRITON_ATTN)
    backends.insert(backends.index(unified), AttentionBackendEnum.TRITON_ATTN)
```

**Tradeoff.** Where this applies, unified attention with aiter v0.1.27 is faster than `TRITON_ATTN`, mostly at long context:
- Qwen3-32B + EAGLE3: 3928 vs 3553 tok/s at 1k c64, and 856 vs 557 at 8k c16.
- Qwen3-Next-80B-A3B + MTP: 403 vs 207 tok/s at 64k c8.

With the current v0.1.26 pin, unified attention is not correct for every KV cache size, so `TRITON_ATTN` is the safe choice until the pin bump. #61433 restores the order after it.

**History.** An earlier version of this PR also ranked `ROCM_ATTN` last for spec decode and hybrid models, because its Triton fallback had two accuracy bugs. Both are now fixed on main:
- The sliding-window NaN (#62828) no longer occurs since #60767.
- #63268 fixed the unwritten output heads on gfx942.

What remained was a performance change, which belongs in #61433, so it was dropped from this PR.
