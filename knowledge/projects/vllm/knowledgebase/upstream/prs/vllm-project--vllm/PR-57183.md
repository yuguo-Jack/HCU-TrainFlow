# [Feature][Core] Warn when estimated decode coverage exceeds CUDA graph capture size

[Upstream PR](https://github.com/vllm-project/vllm/pull/57183) · state: closed · merged: False

## Original PR description

## Purpose

Add an early warning when estimated decode-token coverage exceeds the CUDA graph capture limit. This is a usability and observability improvement, not a kernel bugfix.

CUDA graphs can be enabled while a decode batch is too large for the captured graphs. In that case, execution can fall back to eager kernel launches without a clear explanation of the performance cost. With speculative decoding, each resident request contributes multiple verification tokens, making it easy to overlook the mismatch between request capacity and graph-token coverage.

Diagnosing such a slowdown can require checking configuration, investigating cache behavior, comparing speculative and ordinary decoding, and profiling graph dispatch. A startup warning could point users directly to the capture limit and save substantial debugging time. This PR makes that risk visible without changing execution behavior.

## Change

After cache initialization and warmup, estimate short-request residency using the resolved cache pool and supported cache-group requirements:

```text
q = uniform_decode_query_len
blocks/request = Σ Mamba(1 + num_speculative_blocks)
               + Σ full-attention ceil(q / block_size)
residents = min((num_blocks - 1) // blocks_per_request,
                max_num_seqs, max_num_batched_tokens // q)
decode_coverage = residents × q
```

Warn once if this estimate exceeds the resolved capture cap. The message includes the estimated residency, query width, block accounting and capture limit, and recommends checking observed batch sizes and available memory before increasing `--max-cudagraph-capture-size`.

As a purely hypothetical example, 200 resident requests with five speculative tokens each need 1,200 verification tokens. A 1,024-token capture limit would not cover that batch. All numeric examples and regression fixtures in this PR are synthetic; no deployment measurements are included.

The warning and its limitations are documented in `docs/configuration/optimization.md`.

## Scope and related work

This is a short, unshared-request estimate, not a guaranteed peak. Prompt length, prefix sharing, dynamic speculation and alignment can change actual occupancy. Unsupported layouts are skipped. The warning does not change scheduling, allocation, capture sizes or model outputs, and does not detect every compatibility gap below the scalar cap.

Related upstream draft: vllm-project/vllm#51509 inspects graph-compatible shapes against configured scheduler limits and dynamic speculative widths. This PR estimates residency from the resolved physical cache pool rather than assuming every configured request slot can be resident. That avoids recommending capture coverage for request counts the cache cannot support under the stated assumptions. It deliberately does not replace the existing proposal's compatibility or dynamic-width checks; the two approaches could be combined. This is submitted as a cache-accounting alternative for maintainer review, with the overlap explicitly acknowledged.
