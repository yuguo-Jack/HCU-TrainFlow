# [Bugfix][Attention] Fix Triton MLA decode int32 overflow and logits workspace accounting

[Upstream PR](https://github.com/vllm-project/vllm/pull/61938) · state: closed · merged: True

## Original PR description

Triton MLA models crash at their default context length on MI355: `vllm serve` with default settings for Kimi-Linear-48B-A3B-Instruct, LongCat-Flash-Lite-FP8 and DeepSeek-V2-Lite-Chat dies with `Memory access fault by GPU ... Write access to a read-only page` during CUDA graph capture. Two bugs are involved, and the second only shows up once the first is fixed:

1. **int32 overflow in the decode kernels.** The split-KV logits offset `cur_batch * stride_mid_ob` is computed in int32. At ≥ 128K context, `_compute_num_kv_splits` picks 512 splits on MI355 (2 × 256 CUs), so with 32 heads one request's logits span 32 × 512 × 513 = 8.4M floats. From batch row 256 onward the offset passes 2^31, and FULL graph capture runs batches up to 512.
2. **The logits workspace is not counted by memory profiling.** #46819 reserves the worst-case logits workspace (32 GiB for LongCat at defaults: 1024 seqs × 32 heads × 512 splits × 513 × fp32) when the metadata builder is created, which happens after profiling. The KV cache is then sized as if that memory were free, and its allocation OOMs (`Tried to allocate 164.67 GiB`, 157.84 GiB free).

To resolve the above, this PR modifies:
- `triton_decode_attention.py`: compute `cur_batch * stride_mid_ob` in int64 at the six logits offsets (stage 1 normal/grouped stores and stage 2 loads), following #47671.
- `MLAAttentionImpl.reserve_profiling_workspace()`: a no-op hook called from the MLA profiling branch, next to the existing `kv_b_proj` scratch simulation.
- `TritonMLAImpl` overrides the hook to reserve the logits workspace at its upper bound (`max_num_seqs × max_decode_query_len`) during profiling. The builder keeps its reservation, which becomes a no-op.
- `test_triton_decode_attention.py`: a regression test whose logits exceed 2^31 elements, for the grouped (MLA) and normal kernels.

<details>
<summary>Why decode got faster</summary>

A rocprofv3 trace of the same LongCat decode workload (128 × 2048-token prompts, 256 output tokens, 32K context) shows all of the difference in `_fwd_grouped_kernel_stage1`: 6062 → 5230 ms (−13.7%), with identical grids and register counts. Every other kernel is within ±0.5%. In the stage-1 variants I inspected, the int32 offset lowers the logits stores to scalar `buffer_store_dword`, while the int64 base produces vectorized `global_store_dwordx3`. The kernel microbenchmark is neutral at long sequences (30 shapes, H 16–128, 4K–128K context: median 1.000×, range 0.990–1.005×, run-to-run drift ≤ 0.8%) and 15–17% faster at 512 splits with batch ≥ 128.

</details>

<details>
<summary>Design notes</summary>

- **Effect on KV cache size:** the KV cache now excludes the logits workspace. LongCat at 32K goes from 164.67 to 162.91 GiB (`main` over-commits there too, but its slack absorbs it). At 320K it is 134.86 GiB, where `main` cannot start.
- **Upper bound:** the profiling hook has no builder, so it sizes rows as `max_num_seqs × max_decode_query_len`. That matches the builder's `reorder_batch_threshold` except with DCP on a backend without varlen support, where the builder uses 1 and the profiled reservation is larger than needed.
- **Why the profiling forward:** the impl is built at model load, but the decode metadata builder only exists after profiling. Reserving in the profiling run follows the existing MLA `kv_b_proj` simulation and the sparse-indexer reservations, and avoids touching the worker's profiling code.
- **History:** #33529 made split counts up to 2 × compute units reachable, and #46819 moved the logits into a workspace reserved after profiling. #47671 fixed the same overflow class for page offsets in these kernels.
- **Duplicate check:** no open PR or issue covers this. #46728 (NVIDIA shared-memory OOR) and #57094 (NaN on empty `seq_len`) touch the same kernels for different bugs.

</details>
