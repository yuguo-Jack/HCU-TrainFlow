# [Bugfix][KVConnector] Fix MoRI-IO WRITE-mode requests stranded in WAITING_FOR_REMOTE_KVS

[Upstream PR](https://github.com/vllm-project/vllm/pull/57705) · state: closed · merged: True

## Original PR description

## Purpose

In MoRI-IO WRITE (push) mode, decode requests can get stuck in `WAITING_FOR_REMOTE_KVS` forever when decode is overloaded. The engine stays healthy and keeps serving new requests, so this shows up as a benchmark that never finishes rather than as an error. At 1024 in / 1024 out, 128 requests at concurrency 64, with decode limited to 20 running requests, runs on `main` stall before all requests finish.

This PR fixes two causes. A third cause, decode preemption, is fixed by #53250. This PR used to include the same change, but it has been removed in favour of that PR.

### 1. Prefill gives up on a deferred write without telling decode

In push mode the proxy sends each request to prefill and decode at the same time. Prefill computes the KV cache and then waits for decode to allocate blocks and send their IDs. If decode is busy, the request can wait in decode's queue for longer than `defer_timeout` (60 s). On `main`, prefill then frees its blocks and drops the write, but never tells decode. When decode later admits the request, it waits for KV that will never arrive.

Now, when a deferred write times out:

- Prefill marks the transfer as finished under the lock, so a late block allocation from decode is ignored and no write can start. If the allocation arrived just before the timeout, the write goes ahead as normal.
- Prefill sends `write_failed` to every decode DP rank. Prefill never received the allocation, so it cannot know which rank owns the request. Ranks that do not own it ignore the message, and decode keeps only a bounded number of unmatched failures.
- Prefill then releases its blocks, even if sending a notification failed. This is safe because no write was ever issued.
- Decode reports the request as a failed KV load. It is then failed or recomputed according to `kv_load_failure_policy`. Because no write was issued, decode can free its blocks straight away.

The prefill scheduler no longer has its own WRITE-mode timeout that freed blocks on its own. Only the worker releases them, after the transfer is marked finished.

### 2. A full local prefix-cache hit sent an empty block list

When decode already had the whole prompt in its prefix cache, it sent prefill an empty block list. Prefill rejects that with `MoRIIOError("block_notify_list cannot be empty")` and keeps its blocks. Decode now sends a release message instead, so prefill frees them.

### Related PRs

- #53250 stops a preempted decode request from waiting for a second push. Under the overload above, decode preemption also strands requests, so this PR relies on #53250 to fully fix the hang. With `kv_load_failure_policy=recompute`, #53250 is also what lets a failed request recompute locally.
- #58962 adds a receive timeout on decode for when prefill dies mid-transfer. In that case decode cannot know whether a write is still in flight, so it keeps the blocks. The two PRs cover different failures: this one handles a live prefill that never started the write, and #58962 handles a prefill that cannot send anything.

- akshayv · comment · 2026-09-21T17:48:45Z · [source](https://github.com/vllm-project/vllm/pull/57705#issuecomment-5764975339)

Addressed in `a87a3e8`.

The WRITE timeout lifecycle is now:
1. Re-check remote allocation under the wrapper lock (an allocation racing the timeout wins and proceeds normally).
2. Mark the transfer terminal.
3. Send a structured `write_failed` notification to decode.
4. Only after that notification succeeds, ACK the producer scheduler so source blocks can be released.

Decode reports the notification through the existing `KVConnectorTransferResults.failed_recving` path, which releases `WAITING_FOR_REMOTE_KVS` and uses the configured failure policy (recompute by default). The scheduler-side deadline no longer independently reaps WRITE transfers; READ keeps its existing watchdog.

I also added regression coverage for terminal-before-release ordering, the allocation/timeout race, rejecting a late allocation, failure propagation, and ensuring WRITE is not scheduler-reaped. Focused/adjacent MoRI-IO tests pass (46 total), pre-commit passes, and the normal GPU WRITE path completes 64/64 with no engine errors.

- akshayv · comment · 2026-10-02T08:22:48Z · [source](https://github.com/vllm-project/vllm/pull/57705#issuecomment-5948104382)

Thanks for the review, @simondanielsson. I've pushed fbc4b2928, which addresses your comments:

- I removed the `do_remote_prefill` change, since #53250 makes the same fix.
- `write_failed` is now sent to every decode DP rank, as you suggested in your inline comment.

On the timeout fix not being fully reliable: you're right that a message can always be lost if decode crashes. But the bug this PR fixes is not caused by a lost message. When decode is overloaded, it can admit a request more than `defer_timeout` after prefill finished. Decode then sends its block IDs late, not never. On `main`, prefill has already dropped the write and freed its blocks by then, and it never tells decode. So decode waits forever even though no message was lost.

`write_failed` uses the same ZMQ connection as the block IDs and `write_done`, so it is no less reliable than the messages push mode already depends on.

I also think this fix and #58962 are both needed, because they handle different failures:

- **This PR:** prefill is alive but timed out before it started writing. Prefill knows no write was issued, so decode can free its blocks immediately and fail or recompute the request.
- **#58962:** prefill died or lost its connection mid-transfer. Decode cannot know whether a write is still on its way, so it has to keep the blocks.

With only #58962, an overloaded decode would fail these requests after its own timeout but keep their blocks until restart, even though nothing will ever write to them. If `write_failed` is ever lost, #58962's timeout still fails the request.

I've also updated the PR description to match. Note that this PR now relies on #53250: under the same load, decode preemption still leaves requests stuck until that PR lands.

A note on scope: I found a separate, pre-existing issue that this PR deliberately leaves alone. On `main`, `_release_write_prefill_blocks` computes the release port from the global `remote_dp_rank` and always uses `remote_host`. It does not apply the per-pod host and local-rank handling that the `remote_blocks` notify uses. On a Wide-EP multi-pod deployment, a release for a prefill rank on a child pod can therefore go to the wrong host and port, and prefill holds those blocks until its deferred-write timeout. This PR now routes the full-prefix-hit case through the same helper, so that case shares the limitation. I would rather fix it in a follow-up with its own test than widen this PR.
