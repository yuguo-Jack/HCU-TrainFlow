# [Distributed] Allow one pipeline stage per vLLM instance

[Upstream PR](https://github.com/vllm-project/vllm/pull/63898) · state: open · merged: False

## Original PR description

Stacked on #63897 (its two commits are included here; review only the last commit).



## Overview

Part of #63818 (RFC: pluggable PP transport), Phase 2. Stacked on the `--pp-group-cls` PR (its two commits are included; review only the last commit). Adds `--pipeline-stage-rank k`: a vLLM instance runs only stage `k` of `--pipeline-parallel-size` stages, with the other stages in other instances, connected by the plugin's PP group and driven by a plugin executor.

## Claims

- `ParallelConfig.pipeline_stage_rank` / `--pipeline-stage-rank`: the instance's `torch.distributed` world covers its own stage only (`world_size` excludes PP), `initialize_model_parallel` lays out the groups with one stage, the PP group comes from `--pp-group-cls` (required with this option) and reports stage `k` of N, and `ModelConfig.get_layers_start_end_indices` uses `k`. Unset (default), nothing changes.
- `EngineArgs._check_feature_supported` resolves an executor given by import path (`--distributed-executor-backend pkg.mod.Cls`) before reading `supports_pp`; until now any qualname was rejected with PP > 1 even if the class declares `supports_pp = True`.
- With only these, a plugin runs each stage as its own process (on any host) with replicas per stage, without touching the model runner or the scheduler: stage 0 sends each step's `SchedulerOutput` (unchanged) to one replica per downstream stage, and each downstream replica runs the stock worker / V2 model runner on it. Results below.

It did not reproduce in 15 later kills and its logs were overwritten, so the cause is unknown; it is in the plugin's failover path or in this change, not yet determined.

## Details

- Why a stage index in the config rather than only in the plugin: the layer range is computed in core code (`get_pp_indices` via the PP group, and `ModelConfig.get_layers_start_end_indices` from the config, used by spec-decode heads and connectors), and the torch world size must not include stages that are not in this process. Everything else (how stages find each other, routing, replicas) stays in the plugin.
- What did not need to change: the model runner and the scheduler. A downstream stage runs a normal `EngineCore` (its scheduler unused) and executes the `SchedulerOutput`s it receives, so its runner state (requests, block tables) follows stage 0's scheduler exactly; KV block ids are stage 0's (`--num-gpu-blocks-override` equal on all stages). Warmup/profiling runs of a stage alone have no PP peers; the plugin makes such steps local.
- The executor is supplied by `--distributed-executor-backend` (the plugin subclasses `MultiprocExecutor` for its own stage's TP workers). Tensor parallelism within a stage works (validated TP=2).
- Limitations: DP with `--pipeline-stage-rank` is not validated. In-tree executors (`mp`, `ray`) do not support the option; it is meant for plugin executors.
- Not a duplicate: searched open PRs for "pipeline stage rank", "#63818"; existing PP PRs change model partitioning or MRV2 PP scheduling.

- yanyinglin · comment · 2026-10-28T04:46:42Z · [source](https://github.com/vllm-project/vllm/pull/63898#issuecomment-6460903824)

Correction to my previous comment: the PP=2 x TP=2 failover failure was a plugin bug and is fixed (no change to this PR). While the downstream stage had no live replica, the plugin's stage 0 kept launching steps that nobody downstream would run; their sampled tokens never arrived, and with TP=2 stage 0's in-group broadcast of those tokens blocked both ranks. The plugin now waits for a live replica before launching a step.

Re-run, 32 streaming clients, 3 kills each: stage 1 (TP=2) restarted in place with no spare: 32/32 in-flight requests completed every time, 0 tokens lost, the largest gap ~28 s (the restart; stock vLLM under a restart loop loses all 32 and is down ~60 s). With a spare, stages on three hosts, one TP rank of the active replica killed: 32/32, largest gap 0.2-2.1 s. Greedy runs with a kill (6): 0 tokens off the argmax. PP=2 without TP: 32 further kills, 4,832/4,832 requests, 0 errors, 0 off-argmax.

One trade-off changed the two-host numbers I posted: between hosts the plugin now waits for incoming data on the CPU instead of letting a CUDA stream wait on a flag that a Python thread releases, because the latter deadlocked against a first Triton kernel load (GIL held while waiting for the device) in a cross-host failover. Cost at PP=2 across two hosts: TPOT 34.2 vs 28.9 ms at C=1, 46.0 vs 41.9 ms at C=32. Same-host hops are unaffected (their waits are released by the sender's GPU).
