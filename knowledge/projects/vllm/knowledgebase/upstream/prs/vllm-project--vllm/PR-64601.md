# [Perf][Rust Frontend] Accept decoded images over NIXL in gRPC

[Upstream PR](https://github.com/vllm-project/vllm/pull/64601) · state: open · merged: False

## Original PR description



## Overview

Adds `MediaItem.nixl_ref` to the vllm-rs gRPC API: a client that already decoded an image sends a NIXL descriptor of its pixels, and vllm-rs reads them with a one-sided NIXL READ instead of decoding the file again. Each turn of a computer-use agent re-sends its screenshot history, and vllm-rs decodes every screenshot again on the request path, even when the prefix cache holds its KV. Opt-in: cargo feature `nixl-media` and `--enable-grpc-nixl-media`.

RFC: #64600

## Claims

- An agent turn with 8 screenshots, 7 of them prefix-cached, gets 21% lower TTFT on Qwen3.8-27B, and 9-19% lower under load up to 90% of capacity.
- vllm-rs uses 12% less CPU per request and serves 8-9% more requests per second on 8 cores.
- Model output does not change: answers match `data_uri` request for request.

## Validation

All runs use vllm-rs with Qwen3.8-27B (BF16) on 1 x GB200, with prefix caching on, and every request succeeded. They were measured on base `274a5e19a1`, the newest commit with an aarch64 engine wheel at the time; the commits in this PR make the same changes on current `main`.

The three image sources compared:

- `data_uri`: the encoded image file, base64-encoded in the request.
- `raw_bytes`: the encoded image file as raw bytes.
- `nixl_ref`: pixels that the client already decoded; vllm-rs reads them over NIXL (this PR).

**End to end** (vllm-rs and the vLLM engine; 64 output tokens per request). Time to first token (TTFT), mean, in milliseconds. "Change" compares `nixl_ref` with `data_uri`.

| Workload | Load | `data_uri` (ms) | `raw_bytes` (ms) | `nixl_ref` (ms) | Change |
|---|---|---:|---:|---:|---:|
| Agent turn | 1 request at a time | 426 | 403 | 337 | -21% |
| Agent turn | 1.2 req/s (25% of capacity) | 450 | 421 | 366 | -19% |
| Agent turn | 2.4 req/s (50% of capacity) | 564 | 519 | 477 | -15% |
| Agent turn | 3.4 req/s (75% of capacity) | 589 | 576 | 534 | -9% |
| Agent turn | 4.1 req/s (90% of capacity) | 634 | 633 | 565 | -11% |
| 1 x 1080p PNG | 1 request at a time | 144 | 141 | 141 | -2% |
| 1 x 1024 px JPEG | 1 request at a time | 150 | 149 | 148 | -1% |

An agent turn is one turn of a computer-use agent: 8 x 1080p PNG screenshots per request, of which the first 7 are already in the prefix cache (14,144 cached tokens per request in every column). Rates are open-loop Poisson arrivals. Capacity is about 4.6 req/s for all three sources, because the GPU is the bottleneck.

**vllm-rs alone** (no GPU: 4 x `vllm-mock-engine`, which returns the first token at once, and vllm-rs pinned to 8 Grace CPU cores; 1080p PNG). Here TTFT is the time vllm-rs itself takes to accept, preprocess, and forward a request.

| Metric | `data_uri` | `raw_bytes` | `nixl_ref` | Change |
|---|---:|---:|---:|---:|
| TTFT, 8 images, 1 request at a time (ms) | 260 | 238 | 183 | -30% |
| vllm-rs CPU time per request, 1 image (ms) | 47.1 | 44.0 | 41.3 | -12% |
| Peak throughput, 1 image (req/s) | 130.7 | 137.5 | 141.9 | +9% |

## Details

- **Pixels, not `pixel_values`:** vllm-rs keeps resize, normalization, and patchify, so model preprocessing stays in one place.
- **Pull:** a one-sided READ, like the NIXL KV connector's pull mode, so a client only registers memory and sends a descriptor.
- **Trusted peers only:** the server connects to the agent a request names; `docs/usage/security.md` states the trust model and the source build (the wheel's vllm-rs does not include `nixl-media`). `vllm serve` passes the flag to vllm-rs.
- **Contained failures:** NIXL 1.5.1 can report a failed transfer while its READ still lands, so that buffer is never freed (bounded at 1 GiB).
- **Limits:** peak throughput on one GPU does not change, and normalization and the `pixel_values` send still take about 70% of vllm-rs CPU per image.

`vllm-proto` goes to 0.7.0: a new `oneof` variant breaks Rust callers that match on `Source`. No open PR or issue adds a NIXL image source to vllm-rs; #63160 and #57789 also bump `vllm-proto` to 0.7.0, so whichever merges second takes the next version.
