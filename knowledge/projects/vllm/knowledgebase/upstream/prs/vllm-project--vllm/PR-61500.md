# [Bugfix][NIXL] Re-handshake with a pull peer after a failed read

[Upstream PR](https://github.com/vllm-project/vllm/pull/61500) · state: open · merged: False

## Original PR description

## Overview

With NIXL 1.5.0, a pull that fails with `NIXL_ERR_REMOTE_DISCONNECT` leaves the UCX endpoint to that prefill worker failed for good, so every later read between the two workers fails until one side restarts or the peer is evicted. The decode worker releases a failed peer only when `check_remote_metadata` reports its metadata missing, which it never does here. This releases a peer once two requests to it fail with no completed read in between, so the existing drain, backoff and re-handshake path builds a fresh connection.

Related: #55471 (added the invalid-peer path and the metadata check), #61238 (invalidates peers whose READ has stalled; touches the same lines), #61499 (keeps the engine up through these failures with HiSparse).

## Claims

- When two requests to a pull peer fail with recorded transport failures and no completed read in between, the peer is released once its reads drain, and the next read to it re-handshakes. A completed read resets the count, so a single failed request keeps the peer.
- A release that repeats within 60 s backs off from 1 s to 60 s before the next re-handshake, as for invalidated metadata today; reads to the peer fail fast meanwhile.
- KV lease expiry and reads rejected while a peer drains are not transport failures and do not count. Push mode is unchanged.

## Details

Path of the failure on main, decode side, pull mode:

1. A decode worker reads a request's KV from a prefill worker. The UCX error callback fires for that endpoint (`nixlUcxEp::err_cb`, `src/plugins/ucx/ucx_utils.cpp` in NIXL 1.5.0) and moves it from `CONNECTED` to `FAILED`. Nothing moves it back; only `loadRemoteConnInfo`, run when the remote agent's metadata is added, creates a `CONNECTED` endpoint.
2. Every later read posted on a `FAILED` endpoint returns `NIXL_ERR_REMOTE_DISCONNECT` (`nixlUcxEp::read` and `postSgl` call `checkTxState`). The request fails, and `_handle_failed_transfer` records the remote engine in `_failed_remote_engines`.
3. `_cleanup_remote_engines` calls `check_remote_metadata` on the peer's agents without descriptors. `nixlAgent::checkRemoteMD` then only checks that the remote section exists locally, which it does, so the peer is kept.
4. The next request routed to that prefill worker reads over the same `FAILED` endpoint and fails at step 2.

The change drops the metadata check in step 3. `_failed_reqs_by_engine` replaces `_failed_remote_engines` and holds, per peer, the requests that failed since its last completed read; `_cleanup_remote_engines` marks a peer invalid once it holds `_PEER_FAILED_REQS_BEFORE_RELEASE` (2) of them. The release path keeps its logic: reads to the peer are rejected until in-flight reads drain, its agents are removed, and the next read re-handshakes.

Why two failed requests: an invalidated peer rejects every new read while its reads drain, so releasing on one failure would cost a few seconds of recomputes for an error that might not repeat. A failed endpoint fails every later read (101 requests in the trace above), so on a dead connection the second failure arrives with the next read, at the cost of one more failed request. Requests count once however many of their transfers fail. There is no NIXL call that reports endpoint health, so one failure cannot tell the two cases apart.

Not a duplicate. Open PRs found with `gh pr list --repo vllm-project/vllm --state open --search` for "check_remote_metadata", "nixl remote disconnect", "nixl rehandshake" and "nixl invalid peer": #61238 invalidates a peer whose READ stays in `PROC` past a timeout, which never records a failed transfer; #60279 handles stale P2P tiering registrations. Neither releases a peer after failed reads.

Thanks @NickLucche. I think we should preserve the confirmed-missing-metadata recovery path from #55471: once NIXL has dropped the local peer metadata, the cached connector state is already stale, so waiting for a second failed request does not add confidence.

#61500 addresses an additional case: the metadata still exists, but the underlying connection is unusable. I would handle that as a separate recovery trigger, reusing the existing drain, cleanup, backoff and re-handshake logic. For that case, I agree that the two-request threshold needs more evidence. This would extend recovery coverage without delaying the already-confirmed invalidation case, and we should retain the existing missing-metadata regression tests.
