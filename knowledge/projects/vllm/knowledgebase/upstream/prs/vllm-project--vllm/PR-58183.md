# [Feature][Core] Add opt-in multi-worker CUDA process checkpoint sleep

[Upstream PR](https://github.com/vllm-project/vllm/pull/58183) · state: open · merged: False

## Original PR description

## Purpose

Ordinary level-1 sleep releases weights and KV allocations but can leave CUDA process state resident. Add an **opt-in `ProcessCheckpointExecutor`** that checkpoints dedicated workers after ordinary sleep and restores their original CUDA state before wake. The focus is reclaiming physical GPU memory while retaining captured graphs, not reducing sleep/wake latency.

The default executor is unchanged. The implementation uses a persistent external Python helper and the official `cuCheckpointProcessLock`, `cuCheckpointProcessCheckpoint`, `cuCheckpointProcessRestore`, and `cuCheckpointProcessUnlock` APIs. It locks all ranks before checkpointing any rank, and restores all ranks before unlocking any rank. It reuses existing NCCL suspend/resume and FlashInfer workspace preparation/restoration hooks. No C++ extension, new HTTP endpoint, allocator replacement, or graph recapture is added.

### Relationship to existing work

This is a related, alternative integration focused on **multi-worker sleep/wake**, not a claim that process checkpointing itself is new:

- #56373 already proposes process-state offload on the existing sleep/wake contract. Its documented scope is a single-GPU `uni` executor. This proposal instead uses dedicated multiprocess workers at TP=1/2/4, coordinates driver transitions across ranks, and validates NCCL P2P plus restorable FlashInfer workspaces. These proposals overlap in motivation; the integration should be consolidated with maintainers before merging overlapping functionality.
- #37921/#37925 and RFC #34303 propose C-extension bindings and separate suspend/resume interfaces. This change uses a Python helper and the existing sleep/wake executor interface.
- #57899 destroys graphs and recaptures after wake. This proposal restores the original graphs and does not modify that PR.

### Scope and restrictions

- Linux; single-node TP=1, 2, or 4; level-1 sleep only. Level 0 remains a scheduler pause. Pipeline/data/context parallelism and external cache transfer are rejected.
- Tested on four H20 GPUs, driver **580.126.09**, PyTorch **2.13.0+cu130**, NCCL **2.29.7**, and FlashInfer **0.6.18.post1**. All GPU vLLM validation used `VLLM_USE_V2_MODEL_RUNNER=1`; other worker versions and dependency combinations are not established by these results.
- For TP>1, retain NCCL P2P/CUMEM with `enable_nccl_comm_suspend=True`, but disable NCCL NVLS, SHM/IB, custom all-reduce, symmetric-memory paths, and FlashInfer PCIe IPC. Use FlashInfer `trtllm`; the full configuration is documented in `docs/features/sleep_mode.md`.
- Disabling standalone FlashInfer all-reduce does not disable its compiler fusion. The workspace restrictions apply to both paths. Default NVLS allocations prevented checkpoint in the tested setup; FlashInfer `mnnvl` failed during multicast reconstruction after restore.
- Level-1 sleep still discards KV contents. A partial wake restores the **whole CUDA process** before the requested allocation tags. If weights remain asleep after a KV-only wake, another sleep follows the parent's no-op semantics; wake the remaining weights before another full checkpoint cycle.
- Driver/helper and worker operations have bounded waits. A failed transition terminates the workers rather than continuing with partially restored ranks. Host backup memory and sufficient GPU capacity for restore are required.

### Physical memory and latency

Memory figures use 1 GB = 2^30 bytes. At each checkpoint, worker GPU process records disappeared and all four devices returned to the observed **0.00390625 GB/device** test baseline. This does not attribute the baseline to a particular resource or claim an absolute zero device reading.

After ordinary sleep and communication preparation, driver checkpoint returned an additional **0.880–2.202 GB/device** across the tested configurations. This is a measured stage difference, not an attribution entirely to GraphExec.

Selected steady-state means (cycles 2–20), in seconds:

| Model / TP | Matched ordinary sleep / wake | Checkpoint sleep / wake | Additional driver-stage memory returned per device (GB) |
|---|---|---|---|
| Qwen3-8B / 1 | 0.350 / 0.678 | 1.281 / 1.553 | 1.794 |
| Qwen3-8B / 2 | 0.351 / 0.830 | 1.649 / 2.122 | 1.069 |
| Qwen3-8B / 4 | 0.388 / 1.139 | 2.620 / 3.262 | 1.040 |
| Qwen3-30B-A3B-Instruct-2507 / 4, fixed warmup | 0.796 / 1.679 | 3.972 / 5.373 | 1.271 |
| Qwen3-32B / 4 | 0.700 / 1.363 | 3.547 / 4.769 | 1.106 |

First-cycle costs are higher: 30B TP1 first sleep was **23.480 s**, versus **2.598 s** steady state. The feature trades additional sleep/wake time and host memory for lower sleeping GPU residency.

### Normal inference cost

Qwen3-8B, BF16/default compilation and scheduling, 128 input tokens, batches 1/8/32, 1/64 output tokens, 20 measurements per workload. Each series used independent default-communication baselines before and after the candidate and complete warmup. Relative mean end-to-end latency after checkpoint restoration:

| TP | Batch 1, output 1 / 64 | Batch 8, output 1 / 64 | Batch 32, output 1 / 64 |
|---|---|---|---|
| 2 | +3.15% / -3.71% | +1.20% / -3.20% | +0.44% / -2.22% |
| 4 | +5.55% / -4.63% | +2.82% / -3.32% | +3.82% / -2.77% |

Earlier series showed single-request/one-token increases of 6.94% and 12.90%. The lower long-output means are observations, not evidence that checkpointing accelerates inference. Disabling FlashInfer and its fusion entirely while retaining NCCL P2P increased TP4 64-token latency by 8.40–16.72%; retaining the restorable `trtllm` path matters. These measurements do not establish lossless performance or extrapolate to other models/workloads.

### Lifecycle and remaining gaps

Five real 0.6B TP2 scenarios passed: normal repeated/partial sleep-wake and asleep shutdown, worker death, injected restore failure, and injected NCCL suspend/resume failures. Before external container cleanup, no owned live/zombie worker/helper or GPU process remained. Host shared-memory/resource-tracker warnings remain; this is not an audit of every host resource.

HTTP serving, in-flight request draining/concurrent sleep-wake, real out-of-memory restoration, expert/multinode parallelism, other hardware/drivers, and switching models inside a checkpointed worker are not independently validated. The cause of the first-versus-subsequent output difference is not resolved. A checkpointed worker cannot run another model until restored.

AI assistance (Codex, including an independent adversarial evaluator) was used for implementation, validation, and this description. These are local validation results, not upstream CI results. This PR proposes an explicitly enabled experimental executor, not a replacement for default sleep behavior.

- AlanFokCo · comment · 2026-10-09T12:59:19Z · [source](https://github.com/vllm-project/vllm/pull/58183#issuecomment-6081375073)


Update on the driver-580 multicast restore failure documented in `sleep_mode.md`: NVIDIA has confirmed the root cause, and there is a fix boundary.

**Root cause (confirmed by NVIDIA)**

In ai-dynamo/snapshot#510, NVIDIA reported that the r580 user-mode driver (UMD) has a pre-existing bug in multicast restore (`RestoreMulticastDevices` fails with `CUDA_ERROR_INVALID_DEVICE`) that should be fixed in r595 UMD and above, and that keeping the r580 kernel-mode driver (KMD) is fine. Our results on UMD 610.57.04 and 615.71.09 are consistent with that.

**Validation on a 4x H20 host (580.126.09 KMD retained, newer UMDs via LD_LIBRARY_PATH)**

Whole-process checkpoint/restore of a live vLLM engine (vllm 0.30.1rc1.dev0+g6f75cc7d5d, Qwen3.8-27B BF16) with the *default* communication stack — dispatch order FLASHINFER(trtllm)/CUSTOM/SYMM_MEM/PYNCCL, `fuse_allreduce_rms` pass enabled, NCCL NVLS (NVLink SHARP) at its default — passes 20/20 freeze/restore rounds at:

- TP2 and TP4 on UMD 610.57.04
- TP2 on UMD 615.71.09

CUDA graph identity is preserved across every round (constant capture count, zero recaptures, identical graph-exec handle sets), and per-rank GPU memory returns to within +2 MiB of baseline with no growth across rounds. So in this whole-process checkpoint setup (live engine, no sleep stage), the default multicast-carrying configuration no longer blocks checkpoint on the two >=595 UMD builds we tested. (One intermittent freeze at round 2 of a TP2 run on 610.57.04 did not reproduce on rerun; details in the linked issue comment.)

**Why the restrictive config in the docs works on 580**

Attribution from the checkpoint state files: a stock TP>=2 vLLM worker on NVSwitch-class hardware holds up to three multicast groups —

1. 98 MiB per rank from `CustomAllreduce.__init__` unconditionally calling `_init_mnnvl_buffer` (6 x 16 MiB stages + 2 MiB signal area, via `torch._symmetric_memory` rendezvous); only `disable_custom_all_reduce=True` removes it;
2. 66 MiB (TP2) / 34 MiB (TP4) per rank when `VLLM_ALLREDUCE_USE_SYMM_MEM` is on;
3. 2 MiB per rank when `NCCL_NVLS_ENABLE=1`.

The documented TP>=2 configuration (`disable_custom_all_reduce=True`, NVLS off, symm-mem off) eliminates all three, which is exactly why it survives the 580 defect: with zero multicast groups, the broken restore path is never exercised. Cells that leave any one of them enabled fail at round-1 restore on 580 (12/12 matrix cells).

**Implications for this PR**

- The driver-580 restrictions trace to a driver bug that NVIDIA reports as fixed in 595 and above — not a fundamental limitation. This executor's combined sleep-then-checkpoint flow has not yet been validated on a >=595 UMD, so the restrictions should stay until that is done; the multicast-related ones are the candidates to lift first.
- One operational requirement we verified twice: the host-side tooling driving the checkpoint must not stay on the 580 UMD while the worker processes run a newer one — a 580 CLI against 615 workers hangs at freeze. Both sides on 615.71.09 pass.
- Caveat: FlashInfer's `mnnvl` all-reduce backend specifically was not in our test matrix (ours used `trtllm`), so I can't claim it is covered.

If useful, I can run this PR's full sleep+checkpoint flow (ordinary level-1 sleep first, then driver checkpoint) with the relaxed comm config on the 610 UMD to see whether the restrictions can be lifted on >=595, and report back here.

Evidence details and matrix are in the linked issue comments; happy to share raw logs.

Follow-up on the relaxation question raised above — we have now run this executor's full sleep-then-checkpoint flow at UMD 610.57.04 (applied to both the engine processes and the checkpoint controller; KMD stays 580.126.09), 4×H20 96 GiB, Qwen3.8-27B BF16, TP2, gpu-memory-utilization 0.60, 20 rounds planned per configuration:

- **Stock restriction set (as this PR requires): PASS 20/20.** sleep median 2.95 s, wake median 3.57 s; GPU memory while asleep 4 MiB per GPU; CUDA graph captures constant at 13366 with zero recaptures and identical graph-exec handle sets across all rounds. Token-level comparison stays informational: 17/20 rounds bitwise-match, and the 3 flips match our no-checkpoint TP2 baseline (3/20) — reduction-order noise, not restore perturbation.
- **Restrictions lifted (full default communication stack: CustomAllreduce MNNVL + SYMM_MEM + NVLS), via a relaxed test variant of the executor that skips the restriction check: FAILS at round 1.** The Lock op succeeds on both ranks (~0 s), then the Checkpoint (freeze) op on rank 0 hangs past the 30 s controller deadline (control_start 07:11:38 → control_failed 07:12:08 in the executor's event log).
- **Restrictions lifted + `enable_nccl_comm_suspend` (NCCL 2.29.7; the executor's suspend/resume validation RPCs passed): same freeze hang at the same op.** NCCL suspend does not tear down the CustomAllreduce MNNVL multicast group (the 98 MiB group created unconditionally via `torch._symmetric_memory`), so freeze still runs into a live multicast object.

Conclusion: the communication restriction set is still required even at UMD 610. This is not the 580 restore-side defect (`RestoreMulticastDevices`, reported fixed in 595+) — on this shimless path the freeze/Checkpoint call itself cannot proceed while the target process holds live multicast groups (the same freeze-side hang we previously recorded on 580 with live multicast and no teardown, so this is not a 610 regression). Relaxing the restrictions by UMD version alone is therefore not viable. What lets multicast survive the cycle in the ai-dynamo/snapshot stack is cuInterpose tearing multicast down before freeze (`PrepareMulticast`) and reconstructing it at restore; a shimless executor would need an equivalent teardown step before relaxation can be revisited.

I will update the `sleep_mode.md` note and the executor code comment in this PR (which currently say the restrictions can be revisited at UMD >= 595) to record this negative result instead.
