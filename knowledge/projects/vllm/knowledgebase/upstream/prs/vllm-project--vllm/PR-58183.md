## Overview

Add a default-off `CUDACheckpointExecutor` that checkpoints CUDA worker state after level-1 sleep and restores the original CUDA graphs before waking allocation tags. This reduces sleeping GPU residency at the cost of host memory and extra sleep/wake latency.

Related to #48311, which tracks this PR under Performance: reclaiming GPU-resident process state during sleep while preserving captured CUDA graphs. This PR addresses that specific optimization, rather than the full sleep/wake/drain lifecycle roadmap.

## Claims

- Dedicated workers and an external driver helper preserve original CUDA graph executables without recapture. Partial wake restores the whole CUDA state before the selected allocator tags; KV contents retain ordinary level-1 semantics.
- Driver operations run concurrently within each stage, with all-worker barriers between Lock, Checkpoint, Restore and Unlock. Incomplete responses, failed ranks and timeouts stop the executor; it never resumes service with a partially restored rank set.
- With NCCL communicator suspension, both GPU peer-to-peer and legacy shared-memory transports are accepted. NVLS, NCCL CUDA host-memory allocation and the other documented unsupported resources remain restricted. Upgrading the user-mode driver alone does not qualify them.
- The former `ProcessCheckpointExecutor` import remains an alias. Single-node tensor parallelism is accepted without a hardcoded 1/2/4 whitelist; only those sizes have been GPU-tested. The default executor is unchanged.

## Details

Configuration, deadlines and limitations are documented in `docs/features/sleep_mode.md`. The helper and workers must load compatible user-mode driver libraries. A driver stage has a 30-second response deadline, in addition to each Lock call's driver timeout. Shutdown terminates worker/helper processes without restoring their GPU state.

This increment also fixes a post-merge startup failure: Step5 sparse attention still imported `is_quantized_kv_cache` from `torch_utils` after it moved to `kv_cache_interface`. Importing the model registry could therefore fail even for Qwen; the corrected import was verified by the model runs above.

There is useful common ground with #62570: draining, resource preparation/restoration hooks, transition guards and failure handling. Its current prepare flow discards KV and rejects an already-sleeping engine, while this executor first offloads weights and supports partial tag wake. Shared lifecycle integration remains a maintainer discussion, not an already-implemented compatibility claim. #62570 delegates checkpointing to an external orchestrator; this PR directly invokes the CUDA driver and does not integrate CRIU or container migration. No second public checkpoint API is added here.

Earlier ai-dynamo/snapshot testing showed that newer user-mode drivers plus cuInterpose can restore multicast resources; that path also tears resources down before checkpoint and rebuilds them afterwards. Our native NVLS probes still timed out during Checkpoint on both 580 and 610, so those results do not justify removing the NVLS guard. NCCL's `ncclMemPersist` tracking also does not release NVLS allocations during communicator suspension. Likewise, PageBroker storage/operator results are not claimed as this executor's memory or latency behavior.

#56373 overlaps in process-state offload and needs consolidation with maintainers before merging overlapping integrations. #57899 destroys graphs and lazily recaptures them and remains a separate approach. TP8, actual InfiniBand, unsupported multicast resources, other driver/library combinations and full native-extension rebuilding are not established by this validation.

Update on the driver-580 multicast restore failure documented in `sleep_mode.md`: NVIDIA has confirmed the root cause, and there is a fix boundary.

**Root cause (confirmed by NVIDIA)**

In ai-dynamo/snapshot#510, NVIDIA reported that the r580 user-mode driver (UMD) has a pre-existing bug in multicast restore (`RestoreMulticastDevices` fails with `CUDA_ERROR_INVALID_DEVICE`) that should be fixed in r595 UMD and above, and that keeping the r580 kernel-mode driver (KMD) is fine. Our results on UMD 610.57.04 and 615.71.09 are consistent with that.

**Validation on a 4x H20 host (580.126.09 KMD retained, newer UMDs via LD_LIBRARY_PATH)**

Whole-process checkpoint/restore of a live vLLM engine (vllm 0.30.1rc1.dev0+g6f75cc7d5d, Qwen3.8-27B BF16) with the *default* communication stack — dispatch order FLASHINFER(trtllm)/CUSTOM/SYMM_MEM/PYNCCL, `fuse_allreduce_rms` pass enabled, NCCL NVLS (NVLink SHARP) at its default — passes 20/20 freeze/restore rounds at:

- TP2 and TP4 on UMD 610.57.04
- TP2 on UMD 615.71.09

CUDA graph identity is preserved across every round (constant capture count, zero recaptures, identical graph-exec handle sets), and per-rank GPU memory returns to within +2 MiB of baseline with no growth across rounds. So in this whole-process checkpoint setup (live engine, no sleep stage), the default multicast-carrying configuration no longer blocks checkpoint on the two >=595 UMD builds we tested. (One intermittent freeze at round 2 of a TP2 run on 610.57.04 did not reproduce on rerun; details in the linked issue comment.)

**Why the restrictive config in the docs works on 580**

Attribution from the checkpoint state files: a stock TP>=2 vLLM worker on NVSwitch-class hardware holds up to three multicast groups —

1. 98 MiB per rank from `CustomAllreduce.__init__` unconditionally calling `_init_mnnvl_buffer` (6 x 16 MiB stages + 2 MiB signal area, via `torch._symmetric_memory` rendezvous); only `disable_custom_all_reduce=True` removes it;
2. 66 MiB (TP2) / 34 MiB (TP4) per rank when `VLLM_ALLREDUCE_USE_SYMM_MEM` is on;
3. 2 MiB per rank when `NCCL_NVLS_ENABLE=1`.

The documented TP>=2 configuration (`disable_custom_all_reduce=True`, NVLS off, symm-mem off) eliminates all three, which is exactly why it survives the 580 defect: with zero multicast groups, the broken restore path is never exercised. Cells that leave any one of them enabled fail at round-1 restore on 580 (12/12 matrix cells).

**Implications for this PR**

- The driver-580 restrictions trace to a driver bug that NVIDIA reports as fixed in 595 and above — not a fundamental limitation. This executor's combined sleep-then-checkpoint flow has not yet been validated on a >=595 UMD, so the restrictions should stay until that is done; the multicast-related ones are the candidates to lift first.
- One operational requirement we verified twice: the host-side tooling driving the checkpoint must not stay on the 580 UMD while the worker processes run a newer one — a 580 CLI against 615 workers hangs at freeze. Both sides on 615.71.09 pass.
- Caveat: FlashInfer's `mnnvl` all-reduce backend specifically was not in our test matrix (ours used `trtllm`), so I can't claim it is covered.

The later follow-up below performed that combined sleep+checkpoint experiment; it failed with relaxed communication restrictions. The preceding results and statements describe the earlier investigation, not the current validation status.

Evidence details and matrix are in the linked issue comments; happy to share raw logs.
