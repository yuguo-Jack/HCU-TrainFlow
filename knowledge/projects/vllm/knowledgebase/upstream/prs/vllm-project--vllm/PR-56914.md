# [Frontend] Report time to first content token in per-request metrics

[Upstream PR](https://github.com/vllm-project/vllm/pull/56914) · state: open · merged: False

## Original PR description

## Summary

Adds the optional `time_to_first_content_token_ms` field to the existing `PerRequestMetrics` response object for Chat Completions, Completions, and Responses.

## Motivation

`time_to_first_token_ms` is the time to the first generated output token. For reasoning models, that output may be reasoning or parser control output rather than visible final-answer content.

Existing usage counts and aggregate `mean_itl_ms` cannot reliably reconstruct the content boundary: mean ITL is an average, and one engine output batch can contain multiple tokens. Reporting the observed boundary directly lets clients measure the delay before final-answer content becomes available without duplicating the aggregate metrics schema.

## Behavior

- With a response parser, the new field measures from scheduling until the first engine output batch in which the parser emits final-answer content.
- Timing has engine output-batch resolution.
- Without a response parser, it equals `time_to_first_token_ms`.
- It is `null` when the parser emits no final content or the boundary cannot be determined.
- Chat Completions streaming reports metrics only on the final usage chunk, which requires `stream_options.include_usage` or `--enable-force-include-usage`.
- Responses streaming reports metrics only on `response.completed`.
- Existing suppression for `n > 1` and non-attributable multi-generation Responses workflows is unchanged.
- The field is emitted only when `--enable-per-request-metrics` is enabled, so existing default response shapes remain unchanged.

## Implementation

- Extends the shared `PerRequestMetrics` model and builder with the optional timestamp.
- Records the first content-bearing parser delta without changing the user-visible parsed response.
- Reuses the existing parser path; Harmony receives a small state-snapshot helper so timing classification does not mutate response parsing state.
- Keeps the existing aggregate metrics and feature flag.

## Validation

Current branch, after rebasing onto `main`:

- `pre-commit` on all changed documentation and test files: passed.
- `pytest tests/entrypoints/openai/responses/test_protocol.py -q`: 7 passed.
- Focused Chat serving metrics tests: 2 passed.
- A100 E2E with `Qwen/Qwen2.5-1.5B-Instruct` and no response parser: passed; `time_to_first_content_token_ms == time_to_first_token_ms`.
- A100 E2E with `Qwen/Qwen3-0.6B`, `--reasoning-parser qwen3`, and a thinking-token budget: passed; `time_to_first_content_token_ms > time_to_first_token_ms`.
- Existing endpoint coverage verifies Responses propagation, disabled behavior, streaming placement, and suppression rules.

The Qwen3 assertion is consolidated into the existing mixed-request E2E, replacing the mock-heavy parser test without adding a duplicate model request.

## Why this is not duplicate work

- #46768 introduced aggregate per-request metrics.
- #55084 added those aggregate metrics to Responses.
- This PR adds the one content-boundary timestamp that aggregate counts and averages cannot reliably derive.

Addresses #54829.

- nickharris808 · comment · 2026-10-07T02:59:45Z · [source](https://github.com/vllm-project/vllm/pull/56914#issuecomment-6029985904)

On the question of calculating these values from existing metrics: category boundaries add information, while some derived fields are indeed redundant once those boundaries are available.

A method-level fixture executed [`build_per_request_timing_metrics` and `OutputTokenMetricsTracker`](https://github.com/xinnywinne/vllm/blob/015d1c9b46ae4650a80e54030236a956d6997602/vllm/entrypoints/generate/base/serving.py#L54) at head `015d1c9b` with two synthetic histories. Both have schedule time 10, first output at 11, last output at 14, two reasoning tokens, two content tokens, and no unclassified tokens. Each timestamp is one engine-output batch:

| History | Reasoning batches | Content batches | Content TTFT | Content generation span |
|---|---|---|---:|---:|
| A | 11, 12 | 13, 14 | 3000 ms | 1000 ms |
| B | 11, 11.5 | 13.5, 14 | 3500 ms | 500 ms |

The aggregate builder returns identical values for both: TTFT 1000 ms, generation time 3000 ms, mean ITL 1000 ms, and overall throughput 1 token/s. Final usage/category counts are also identical. Thus those aggregate fields plus counts cannot recover content TTFT or the category generation span, even with a simple reasoning-then-content sequence.

Conversely, once a category's `token_count` and positive first-to-last generation span are provided, the current tracker computes its mean ITL as `span_ms / (count - 1)` and throughput as `(count - 1) * 1000 / span_ms`. A client can calculate those two fields. This supports considering a smaller category surface of count, TTFT, and span rather than treating every derived field as independently necessary.

Client-observed streaming arrival times could estimate delivery timing, but they are a different clock from this engine-batch attribution, and non-streaming responses do not expose that history.

Scope: Python 3.12.13; extracted upstream timing functions/classes and the native `TokenPhaseCounts` dataclass, synthetic timestamps/classifications, and simple constructor shims for output models. This check did not execute parsers, validate endpoint serialization, run HTTP/GPU/model integration, or establish a need for the whole proposed API. It addresses only what the existing aggregate values can identify.
