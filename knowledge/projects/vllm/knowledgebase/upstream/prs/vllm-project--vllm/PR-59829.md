# [BugFix][DiffusionGemma][CPU] Copy async output snapshots instead of aliasing reused buffers

[Upstream PR](https://github.com/vllm-project/vllm/pull/59829) · state: closed · merged: True

## Original PR description



## Overview

Fixes #59828

## Claims

With async scheduling, the V2 model runner snapshots each step's sampled tokens and counts with `async_copy_to_np()`. It reads them after the next step starts. On GPU, `.to("cpu")` copies into new memory. On CPU it returns the same tensor, and the snapshot aliases the sampler's buffers. DiffusionGemma reuses those buffers on every step, and the next step overwrites the snapshot before it is read.

This is latent on `main`. CPU forces sync scheduling, which reads each output before the next step runs. I found it while testing DiffusionGemma structured reads on CPU with async scheduling enabled, after https://github.com/vllm-project/vllm/pull/59107. Every read returned a phantom first token, overwritten tokens and one logprob row too few.

### Changes in this PR

- `async_copy_to_np()` passes `copy=True`. A CPU snapshot now owns its memory. GPU behavior does not change. The device-to-host copy already allocates.
- Add a regression test to `tests/v1/worker/test_gpu_model_runner_v2.py`, next to the other V2 model runner tests, instead of a new file. It snapshots a CPU tensor, overwrites the tensor and checks that the snapshot keeps its values.

I checked the other snapshots in `AsyncOutput`. Logprobs, sampling masks and prompt logprobs also alias on CPU. They are safe because their producers allocate new tensors on every step. I left them as is.

No open issue or PR covers this. I searched for `async_copy_to_np`, CPU async aliasing and overwritten sampled tokens. https://github.com/vllm-project/vllm/pull/58082 edits the code next to `async_copy_to_np()` but does not change it.

I used Claude Code to help with this PR. I reviewed every changed line and ran the tests below.

## Validation

Hardware: 22 vCPU Intel Xeon Platinum 8481C, Ubuntu 22.04, PyTorch 2.13.0+cpu. vLLM built from source for CPU at e006d761a5, with the real `google/diffusiongemma-26B-A4B-it` checkpoint in BF16. Unit tests also on macOS (Apple Silicon).

**Unit tests:**

```bash
pytest -v tests/v1/worker/test_gpu_model_runner_v2.py tests/distributed/aux_output_connector/test_store.py tests/v1/spec_decode/test_adaptive_verification.py
```

**End to end:**

1. Sync path, the default on CPU. Run greedy generation with `Qwen/Qwen3-0.6B` and a DiffusionGemma structured read (32-token canvas on a 64-token server). Run on `main`, with this PR, and on `main` again for the noise floor. Compare tokens, logprobs and throughput.
2. Async path. Enable async scheduling on CPU with a local change to `CpuPlatform.check_and_update_config()`. Send the same DiffusionGemma read 10 times with a batch of 1 and 10 times with a batch of 4. Compare each read with sync.

## Test Result

Before (`main`, async on CPU), the read's tokens are overwritten. The issue has the details and the `collect_env.py` output.

```text
sync   tokens[:8] [45518, 45518, 107, 148436, 148436, 236787, 11262, 1]   logprob rows 32
async  tokens[:8] [45518, 1, 1, 1, 1, 148436, 236787, 11262]              logprob rows 31
```

After:

- Unit tests: 90 passed. The new test fails on `main` with `assert [1, 1, 1, 1] == [0, 0, 0, 0]`.
- Async: 50/50 reads match sync, up from 0/50. No snapshot changes before it is read, even with the reader delayed by 50 ms.
- Sync: [layer 3 results: tokens and logprobs before and after for both models, throughput against the noise floor]

## Details

On CPU, .to("cpu") returns the same tensor, and with async scheduling the next step overwrites the sampled-token snapshot before it is read. That corrupted every DiffusionGemma read I tested (linked in the issue).

This PR copies in `async_copy_to_np()`, the one place sampler outputs cross the async boundary. GPU behavior does not change. CPU pays one small copy per step. main is unaffected today because CPU forces sync scheduling. Logprob snapshots still alias but stay safe because their producers allocate new tensors.

LGTM. Confirmed this only affects GPU->CPU.

As a follow-up, step N+1's `_sampled.zero_()` isn't formally ordered after step N's pending GPU-to-CPU copy of the same buffer. In theory the whole forward pass runs in between, but it's missing an ordered edge. DiffusionGemma's sampler reuses `_sampled` and `_num_sampled` every step so they are worth an audit.

Nit (optional): this monkeypatch might have been working around the same issue and might be removable now:

[tests/distributed/aux_output_connector/test_store.py](https://github.com/vllm-project/vllm/blob/main/tests/distributed/aux_output_connector/test_store.py#L250-L252)

```
    monkeypatch.setattr(
        async_utils, "async_copy_to_np", lambda tensor: tensor.numpy().copy()
    )
```
