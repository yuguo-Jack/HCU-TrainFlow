# [MRV2] Cover speculative KV writes in output readiness

[Upstream PR](https://github.com/vllm-project/vllm/pull/60637) · state: closed · merged: False

## Original PR description

## Overview

Make MRV2 output readiness cover speculative post-sampling KV writes before an opted-in connector can publish or reuse the affected blocks. This extracts the step-readiness fix and its capability from #58968, independently of its FULL-context and MultiConnector ownership changes.

Rebased onto main `bfa7e5b7afe40ebe48288801a2baf5c1135cd881`. This remains an independent child of closed #58968.

## Claims

- Retain early D2H submission, then extend the same output-ready event after draft and post-forward work ordered on the main stream.
- Apply this only with a speculator and `requires_full_step_completion=True`; the base/no-op default is false, disabled wrappers opt out, and MoRI opts in for READ only.
- Compose the capability with `any()` in MultiConnector without changing its ownership algorithm in this PR.

```text
submit early D2H -> draft / post-forward -> copy stream waits on main stream
-> re-record output-ready event -> output may become scheduler-visible
```

## Details

`AsyncOutput` records its copy event before `postprocess_sampled()` and `speculator.propose()`. Waiting for that event previously did not cover subsequent KV writes. Out-of-band RDMA cannot inherit the ordering of a later local GPU kernel, so output-triggered block reuse/source handoff needs that later completion boundary.

The capability is deliberately isolated here in response to the interface concern on #58968. It limits the behavior change to opted-in connectors. A runner-only condition based on active `kv_connector_output` would remove the API extension but broaden the readiness delay to all speculative KV connectors; a connector-local blocking wait could lose CPU/GPU overlap. Neither alternative's performance equivalence has been established. The necessity of this particular interface remains an explicit review point.

This is not #48464's MRV1 lifecycle API or #60544's hybrid WRITE transport. It does not replace producer ACK retention (#56465), transfer draining, or multi-owner release accounting. Only writes ordered on the main stream are covered.

**Merge impact:** reversible code change; opted-in speculative MRV2 output readiness. There is no new host synchronization between target and draft, but delaying readiness/shared-copy-stream work can affect overlap and needs measurement.

#60808's pre-forward READ barrier does not cover draft writes after sampling. #60867 extends hybrid READ to more groups/speculative methods; this PR does not claim hardware coverage for those new layouts. The output-readiness capability remains an explicit maintainer design-review point.
