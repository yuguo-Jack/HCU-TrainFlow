# [Test] Add fused-MoE-LoRA non-adapter neutrality regression test (refs #49063)

[Upstream PR](https://github.com/vllm-project/vllm/pull/49084) · state: open · merged: False

## Original PR description

## Purpose

Adds a regression test for the property behind #49063: on a fused-MoE-LoRA model, a request that carries **no adapter** must receive an **exactly-zero** LoRA contribution — enabling LoRA must be numerically neutral for non-adapter requests.

This is a **test-only** change. #49063 (reported against v0.24.0: `enable_lora=True` perturbed non-adapter greedy output into a repetition loop) **no longer reproduces on current `main`** — see the reproduction posted on the issue. This PR is not a fix; it guards the fixed behavior so it doesn't silently regress.

## What it does

The fused MoE-LoRA Triton kernel enforces neutrality by skipping any token whose adapter is disabled (`adapter_enabled[lora_id] == 0`) or absent (`lora_id < 0`). The new `test_fused_moe_lora_kernel_disabled_adapter_is_neutral` drives that contract directly:

- disables a subset of adapters, then asserts **disabled-adapter tokens get a zero delta** (`add_inputs=False`, so the output holds only the LoRA delta), and
- asserts **enabled-adapter tokens still match the pytorch reference** — so the test is not trivially satisfied by all-zeros and fails if the skip guard is removed.

`use_fused_moe_lora_kernel` gains an optional `adapter_enabled` argument (defaulting to the existing all-ones behavior, so no existing caller changes).

## Why this is not duplicate work

- No existing test asserts non-adapter neutrality; the existing suite covers kernel numerics (all-adapters-active) and multi-adapter routing, not the "adapter disabled ⇒ zero" property.
- A **kernel-level** test is used deliberately: every *model-level* MoE-LoRA test (`test_qwen3moe_tp.py`, `test_qwen36_moe_lora.py`) uses a 30B–35B model and is `skip`ped or `--ignore`d in CI (see `.buildkite/test_areas/lora.yaml`). `test_fused_moe_lora_kernel.py` is one of the few MoE-LoRA tests that actually runs in the LoRA CI step, so this is the level where the guard has effect.

Guards restored; no runtime code is changed by this PR.
