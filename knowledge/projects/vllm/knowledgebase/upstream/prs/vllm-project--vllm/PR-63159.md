# [Bugfix][Kernel] Tune off-grid max-token FlashInfer autotune with per-op buckets

[Upstream PR](https://github.com/vllm-project/vllm/pull/63159) · state: open · merged: False

## Original PR description

## Overview

When `--max-num-batched-tokens` is not on FlashInfer's hybrid bucket grid (e.g. 21504), the FlashInfer autotune warmup stores the full-size profile under a key that serving never looks up, so M in 16385..21504 runs the op's default tactic. This PR tunes that pass with each op's own buckets.

## Claims

- With an off-grid max M, serving finds a tuned config for the largest batch sizes instead of falling back to the default tactic (the `No tuned config covers ...` warnings for the CuTe DSL NVFP4 MoE and `fp4_gemm` at M=21504 go away).
- On-grid maxima (8192, 16384, ...), bounded (deferred MoE) passes and drafter-widened passes behave as before.

## Validation

- `tests/model_executor/test_flashinfer_autotune_warmup.py`: 83 passed on this branch and with it merged into current main (a0544b13f); main alone: 78 passed. The new tests cover the off-grid case with a patched mapper, and check the on-grid / off-grid split against FlashInfer's real `map_to_hybrid_bucket_uncapped` (16384 and 2560 keep the override, 21504 and 3000 do not).
- Runtime check on 4x SM107 GPUs, Qwen3-VL-235B NVFP4, `--max-num-batched-tokens 21504` (3 runs each): without this change every rank logs `No tuned config covers` at M=21504 for the CuTe DSL MoE and two `fp4_gemm` shapes; with it, the autotune cache holds 32768 entries for all three ops and the warnings are gone. The FlashInfer autotune phase took a median of 234 s per rank with this change and 237 s without (12 ranks each), so tuning with per-op buckets does not lengthen warmup here.
- These runs also carried a FlashInfer autotuner patch that only matters when a lookup falls above the largest tuned bucket, which no longer happens with this change. They are therefore not a strict standalone A/B of this PR, and no end-to-end throughput number is claimed for it.

## Details

FlashInfer's AutoTuner stores each profile under the bucket of the active mapper. Inside `autotune(tuning_buckets=...)` that is the override, but capture and serving look tactics up with the op's own mapper. The CuTe DSL MoE, `mm_fp4` and other GEMMs use `map_to_hybrid_bucket_uncapped`, which rounds an off-grid M up past the hybrid grid: with a max of 21504 the full-size profile is stored under 21504, while every M in 16385..21504 maps to 32768 at run time.

When the full-size pass's M is off the grid (`map_to_hybrid_bucket_uncapped(M) != M`), the pass runs without a bucket override, so each op tunes and keys with its own buckets. `map_to_hybrid_bucket_uncapped` is exposed through a lazy wrapper in `vllm/utils/flashinfer.py`; it exists in the pinned FlashInfer version.

Limitation: a drafter-widened pass (`max_tuning_tokens > num_tokens`) keeps the override, so an off-grid drafter-widened max can still miss the top bucket.

AI assistance (Claude, via Claude Code) was used to write parts of this change, the tests and the validation scripts. I reviewed every change and ran the validation above.
