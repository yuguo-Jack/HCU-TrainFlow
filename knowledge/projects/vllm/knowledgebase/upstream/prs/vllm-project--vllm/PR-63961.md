# [Rust Frontend] Return 404 for a missing LoRA adapter path like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/63961) · state: closed · merged: True

## Original PR description

## Overview

`POST /v1/load_lora_adapter` with a local path that does not exist returns 404 `NotFoundError` on the Python frontend: the engine's worker manager raises `LoRAAdapterNotFoundError` on `FileNotFoundError`, and `create_error_response` maps every `VLLMNotFoundError` to 404 (vllm-project/vllm#11727 added the check and `test_dynamic_lora_not_found`). The Rust frontend answers the same request with 400 `"Local LoRA adapter path must exist and be accessible."`, because its runtime path guard (`validate_lora_path_access`, vllm-project/vllm#43778 and vllm-project/vllm#53756) folds every `canonicalize` failure into one `InvalidPath` error. A client that tells "no such adapter" from "bad request" by status code, and `tests/entrypoints/serve/lora/test_lora_adapters.py::test_dynamic_lora_not_found` (which expects `openai.NotFoundError`), see a different answer. This PR makes the guard distinguish a missing path and maps it to 404.

## Claims

- A local adapter path that does not exist returns 404 `NotFoundError` with `param: null` and the message `No adapter found for <path>` (the tail of Python's `Loading lora <name> failed: No adapter found for <path>`), like Python.
- gRPC `LoadLora` returns `NOT_FOUND` for the same case.
- Other `canonicalize` failures, such as a permission error, keep the existing 400.

- `lora::tests::lora_path_reports_missing_paths_as_not_found`: a missing path under a configured prefix yields `NotFound` with the requested path.
- `routes::lora::tests::load_lora_reports_missing_adapter_path_as_not_found` and `grpc::control::tests::load_lora_reports_missing_adapter_path_as_not_found`: the HTTP mapping is 404 and the gRPC mapping is `NOT_FOUND`.
- `error::tests::error_response_names_error_class_and_status_code`: the new variant serializes as `{"message":"No adapter found for /not/an/adapter","type":"NotFoundError","param":null,"code":404}`.
- Red-green: with the `NotFound` kind check, the HTTP arm, or the gRPC arm reverted, the matching test fails.
- There is no request-level test: reaching the `NotFound` branch through either endpoint needs `VLLM_RUNTIME_LORA_ALLOWED_PATH_PREFIXES` set in the test process, which no server test mutates (`std::env::set_var` is `unsafe` under edition 2024). The Python `test_dynamic_lora_not_found` (run with `VLLM_RUNTIME_LORA_ALLOWED_PATH_PREFIXES=/`) covers the endpoint.

## Details

- The path guard reports a `canonicalize` failure of kind `NotFound` as a new `LoraPathAccessError::NotFound { lora_path }`, displayed as `No adapter found for <path>`. Other failures keep the existing 400.
- HTTP maps it to 404 `NotFoundError` with `param: null`, like Python, through a new `ApiError::NotFound { message }` (the existing `ModelNotFound` has a fixed model message and `param: "model"`). gRPC `LoadLora` maps it to `NOT_FOUND`.

Ownership and layering: the guard in `vllm-server` is the code that reads the filesystem for a runtime-loaded path, so it is the only place that can tell a missing path from an inaccessible one; the transports only map the typed error to their status codes.

Unchanged: local paths without `VLLM_RUNTIME_LORA_ALLOWED_PATH_PREFIXES` are still rejected with 400 before any filesystem access (the Rust-only guard), and an existing path outside the configured prefixes still gets 400; a missing path now gets 404 whether or not it is under a prefix, as `canonicalize` runs before the prefix check. A missing Hugging Face repo id still reaches the engine, whose `LoRAAdapterNotFoundError` arrives as a failed utility call and maps to 500; Python matches the exception text to return 404 there. That case is left out, as it needs an engine error contract rather than a frontend check.

Python test: `tests/entrypoints/serve/lora/test_lora_adapters.py::test_dynamic_lora_not_found`.

Not a duplicate: no open PR changes how the Rust frontend reports a missing LoRA adapter path.
