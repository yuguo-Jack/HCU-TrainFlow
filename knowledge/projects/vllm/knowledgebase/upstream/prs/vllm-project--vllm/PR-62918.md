# [Bugfix][Gemma4] Wire Gemma-4 MoE layers into EPLB

[Upstream PR](https://github.com/vllm-project/vllm/pull/62918) · state: open · merged: False

## Original PR description

## Purpose

`--enable-eplb` has no effect on Gemma-4 MoE models (for example `google/gemma-4-26B-A4B-it`). The server starts, but EPLB logs `avg_tokens=0.00, max_tokens=0, balancedness=0.0000` at every step and never rearranges experts.

There are three causes:

1. `Gemma4DecoderLayer` builds its MoE layer without `enable_eplb` or `num_redundant_experts`, so the router has no `EplbLayerState` and records no expert load.
2. `Gemma4ForCausalLM` reports `num_physical_experts = num_local_physical_experts = num_experts` and `num_redundant_experts = 0`, so EPLB sees every expert as local to every rank.
3. Gemma-4 checkpoints store experts as fused `[num_experts, ...]` tensors. The fused branch of `RoutedExperts.load_weights` loads only the logical experts, so with `num_redundant_experts > 0` the redundant physical experts would keep uninitialized weights.

This PR:

- passes `enable_eplb` and `num_redundant_experts` from the parallel config to Gemma-4's `FusedMoEFactory`, as `qwen3_moe.py` does;
- takes the physical and local expert counts from the first MoE layer's `moe_config`;
- in the fused branch of `RoutedExperts.load_weights`, also loads each redundant physical expert `i` from logical expert `i % num_logical_experts`. This matches `EplbState.build_initial_global_physical_to_logical_map`. When there are no redundant experts the list is unchanged.

No existing issue or PR covers this.

## Test Plan

Gemma-4-26B-A4B-it, EP=4 (DP=4, TP=1, DeepEP high-throughput) on 4xH100, `--enable-eplb --eplb-config '{"window_size": 40, "step_interval": 40, "num_redundant_experts": 16, "log_balancedness": true}'`.

- Before: EPLB logs zero load at every step.
- After: EPLB logs nonzero load and rearranges experts.
- Accuracy with EPLB (GSM8K, HellaSwag, MMLU, chat template) matches the run without EPLB, which shows that the redundant copies hold the right weights.

The runs used vLLM v0.31.0 with an equivalent patch, since the cluster image is v0.31.0. The patched code paths are the same on main.

## Test Result

Before (v0.31.0 unpatched), every step:

```
EPLB step: ... avg_tokens=0.00, max_tokens=0, balancedness=0.0000
```

After (patched, 16 redundant experts), load is recorded and EPLB rearranges experts (6 rearrangements during a short prefill run, no errors):

```
EPLB step: 20 for model gemma-4-26B-A4B-it: avg_tokens=3194880.00, max_tokens=3704524, balancedness=0.8624, steps until the next rearrangement: 20
Rearranging experts (async mode) ...
```

Accuracy, EPLB with 16 redundant experts minus no EPLB, same questions, 3 runs each (EPLB rearranged experts 125-140 times per run):

| Task | No EPLB | EPLB - no EPLB (points, mean of 3 runs) | Per run |
|---|---|---|---|
| GSM8K strict-match (1319) | 86.88 | +0.03 | +0.15, +0.00, -0.08 |
| HellaSwag (10042) | 56.50 | -0.01 | -0.05, +0.06, -0.05 |
| MMLU (13849) | 46.27 | +0.04 | +0.01, +0.04, +0.08 |
