# [XPU] Enable XPU eplb

[Upstream PR](https://github.com/vllm-project/vllm/pull/44987) · state: closed · merged: True

## Original PR description

Enable XPU eplb and add TorchDistXCCLStagedEplbCommunicator for this.
Torch_xccl and torch_gloo can both be used on XPU.
```
model=Qwen/Qwen3-30B-A3B
VLLM_ALLOW_LONG_MAX_MODEL_LEN=1 VLLM_WORKER_MULTIPROC_METHOD=spawn  python3 -m vllm.entrypoints.openai.api_server --model $model --enforce-eager --port 30088 --trust-remote-code --gpu-memory-util=0.9 --no-enable-prefix-caching --max-num-batched-tokens=8192 --no-enable-log-requests --max-model-len=8192 --block-size 64  -tp=4 \
 --enable_expert_parallel --enable_eplb --eplb-config '{"num_redundant_experts":32, "step_interval":200, "log_balancedness":true, "communicator":"torch_xccl", "use_async":false}'

lm_eval --model local-completions --tasks gsm8k --model_args "model=$model,base_url=http://localhost:30088/v1/completions,max_gen_toks=1024,num_concurrent=64,timeout=9999999" --limit 100
```

For torch.Event:
CpuGpuEvent uses torch.Event() but does not depend on the blocking parameter. Cross-thread synchronization is handled entirely by threading.Event (self._recorded): the waiting thread blocks on the CPU side until record() is confirmed to have been called, after which self._event.wait(stream) is invoked.
self._event.wait(stream) is a device-side stream wait — it makes the stream wait for the event, not the CPU. The blocking parameter is irrelevant here, as it only controls whether the CPU busy-waits during event.synchronize(). Therefore, the correctness of CpuGpuEvent is unaffected by the blocking bug in torch.Event.

For torch.Stream:
- Stream creation: torch.Stream is a generic accelerator stream API introduced in PyTorch 2.3+. Internally it maps to torch.cuda.Stream on CUDA and torch.xpu.Stream on XPU. No risk.
- stream.synchronize(): Identical semantics to torch.cuda.Stream.synchronize(). No risk.
- device_stream(stream) context manager: Uses torch.accelerator.current_stream() / torch.accelerator.set_stream(), which are platform-agnostic APIs supported on both CUDA and XPU. No risk.

In summary, replacing torch.cuda.Stream/torch.cuda.Event with torch.Stream/torch.Event in the EPLB code carries no correctness risk for the current usage patterns.
