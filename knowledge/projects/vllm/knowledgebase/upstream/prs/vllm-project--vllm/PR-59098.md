# [Bugfix] Fix lost KV context caused by wrong batch order in sort_batch_req_ids.

[Upstream PR](https://github.com/vllm-project/vllm/pull/59098) · state: open · merged: False

## Original PR description


<!-- markdownlint-disable -->

## Overview

Fix KV-cache context loss under Model Runner V2, originally observed with `ROCM_AITER_FA`.

`sort_batch_req_ids` previously sorted requests without considering their already-computed context. A request continuing a prompt (an extend) could therefore appear after a fresh prefill and be misclassified as a prefill, causing its cached context to be ignored.

This PR makes sorting context-aware and protects the prefill boundary even when request ordering cannot be made ideal.

Related: #56624 and #58013.

## Claims

- Prevents requests with existing KV context from being classified as fresh prefills by `split_decodes_prefills_and_extends`, regardless of batch order.
- Accounts for cached context when sorting requests, using the request's state slot rather than its position in the current batch.
- Handles padded speculative-draft rows, including context-less one-token prompts.
- Changes shared host-side Python logic; no GPU kernels or launch configurations are modified.

## Validation

**Correctness**

- `pytest tests/v1/worker/test_gpu_batch_ordering.py -v`: **19 passed, 0 skipped** (6 newly added tests).
- Relevant suites: **214 passed** on the PR branch versus **208 passed** on the merge-base. One unrelated gated-model failure occurred on both revisions.
- A separate nine-scenario splitter probe reproduced **four incorrect classifications** on the base implementation; all four were corrected by the PR.
- Mutation checks confirmed that removing the splitter clamp fails three relevant tests, and replacing state-slot indexing with batch-position indexing fails the dedicated sort-key regression test.
- On MI350 with `ROCM_AITER_FA` and MRv2, @engint-cerebras independently reported improved prompt-logprob agreement with the unchunked reference: **1.23 → 0.015** for a GPT-OSS-120B chunked-prefill case, and **1.82 → 0.11** for a prefix-cache-reuse case. See their review comment for the full methodology and additional models.

**Performance and CUDA impact**

Focused host-side microbenchmarks comparing the merge-base with this PR (`decode_query_len=4`, 1,024 requests, µs per call):

| Workload | AMD EPYC base → PR | H200 host base → PR |
|---|---:|---:|
| Decode-only sorting | 50.46 → 57.88 (+14.7%) | 93.19 → 108.38 (+16.3%) |
| Mixed sorting | 91.92 → 122.37 (+33.1%) | 185.95 → 250.84 (+34.9%) |
| Mixed splitting | 20.75 → 29.45 (+41.9%) | 45.22 → 64.92 (+43.6%) |

The changes add measurable **host-side** overhead, but no reliably measurable end-to-end regression was observed in the tested H200 configurations. Decode-only batches bypass the splitter's added work, though they still incur sorting overhead.

The sorter runs on CUDA Model Runner V2. The updated splitter is also CUDA-reachable through FlashAttention with decode context parallelism (DCP), but was not called in the tested single-GPU CUDA FlashAttention path. No CUDA kernels were modified.

## Details

**`vllm/v1/worker/gpu/model_runner.py`**

`sort_batch_req_ids` receives `num_computed_tokens` and `req_id_to_index` and uses cached-context information to distinguish extends from fresh prefills. Drafted rows avoid unnecessary context lookups. The state array is accessed by **state slot**, not batch position.

**`vllm/v1/attention/backends/utils.py`**

`split_decodes_prefills_and_extends` moves the prefill boundary after the final request carrying context:

```python
has_context = (seq_lens != query_lens) & (query_lens > 0)
context_rows = torch.nonzero(has_context).flatten()
if context_rows.numel() > 0:
    first_prefill = max(first_prefill, int(context_rows[-1]) + 1)
```

This additional protection is needed because the scheduler can pad a context-less one-token prompt with placeholder drafts. Such rows can remain ahead of context-bearing requests, so sorting alone cannot guarantee a safe prefill boundary. Thanks @okorzh-amd for identifying this case.

**Scope of CUDA validation:** The H200 testing covered the shared sorting path and confirmed the DCP splitter call path, but did not perform a full DCP correctness comparison or individually exercise every downstream CUDA backend consuming the reordered batch.

**One consequence worth stating explicitly, since it contradicts something in my original

|---|---|---|
| original commit | 0 | 1,909 |

So it is a real change on meaningful batches, and I went looking for a key that avoided it. There
isn't one, because the two callers want contradictory things:

```
batch: decode4(drafted, context) | extend4096(context) | fresh4(NO context),  decode_query_len = 4

cp_utils, decode_threshold=1     ->  extend4096 survives only if fresh4 is LAST
require_uniform, threshold=4     ->  fresh4 counts as a decode only if ADJACENT to decode4
```

`fresh4` cannot be both. The module already says which should win, in the opening docstring of

what your ordering produces, so the `num_decodes` movement is a second documented bug being fixed
rather than collateral. The PR description now says this instead of the incorrect claim.

**On (2), the assertion.** Added in the same commit rather than as a follow-up, since this is the

- it excludes zero-length rows, so padded batches cannot trip it;

It immediately earned its place: it fired on an existing test of mine that deliberately feeds a

the useful signal — the sort key always satisfies the precondition it now enforces.

**Also added** a regression test at `decode_threshold=1`. The existing tests only covered the

Potential nit, but benchmarking this with 1024 requests on my laptop shows the equivalent of half a kernel launch of additional overhead, so it's not that bad.

numpy functionality could be a noticeable perf improvement on small models/high concurrency.

```
def sort_batch_req_ids(
    num_tokens_per_req: dict[str, int],
    draft_tokens: dict[str, list[int]],
    decode_query_len: int,
    num_computed_tokens: np.ndarray | None = None,
    req_id_to_index: dict[str, int] | None = None,
) -> list[str]:
    # Order verification/decode -> short_extend -> extend -> prefill.
    # (keep the PR's explanatory comment here)
    req_ids = list(num_tokens_per_req)
    n = len(req_ids)
    num = np.fromiter(num_tokens_per_req.values(), dtype=np.int32, count=n)
    no_draft = np.fromiter((not draft_tokens.get(r) for r in req_ids), dtype=bool, count=n)
    # np.lexsort sorts by the LAST key first, so this list is in reverse priority:
    # no_draft, then (fresh prefill), then num != decode_query_len, then num.
    keys = [num, num != decode_query_len, no_draft]
    if num_computed_tokens is not None and req_id_to_index is not None:
        rows = np.fromiter(map(req_id_to_index.__getitem__, req_ids), dtype=np.intp, count=n)
        keys.insert(2, (num > 1) & (num_computed_tokens[rows] == 0))
    return [req_ids[i] for i in np.lexsort(keys)]
```

Alternatively as a minimal change to this, casting separately:
```
def key(r: str) -> tuple[bool, bool, bool, int]:
    num = num_tokens_per_req[r]
    no_context = (
        num > 1
        and num_computed_tokens is not None
        and req_id_to_index is not None
        and bool(num_computed_tokens[req_id_to_index[r]] == 0)
    )
    return (not draft_tokens.get(r), no_context, num != decode_query_len, num)
```

Currently, the boolean operation mixing python and numpy booleans can be significant if GPU compute load is light.
