## Overview

Fixes silent KV-cache context loss under Model Runner V2: `split_decodes_prefills_and_extends` assumed every request
with computed context precedes every fresh prompt, which MRV2 does not guarantee, so a context-bearing request could be
classified as a prefill and attended without its KV cache. Adopts the order-independent splitter from #63542 (@qli88)
in place of the clamp this PR previously carried, adds a guard for an all-decode case neither handles, and reverts the
batch-ordering change that is no longer needed. Related: #56624, #58013, #63542, #63676.

## Claims

- Removes the ordering assumption entirely: the split is now correct for **any** batch order, verified against an
  independent contract oracle over an exhaustive permutation sweep plus 16,000 randomized batches (0 mismatches;
  `main` disagrees on 88/174 permutations and ~2,100/4,000 random batches).
- Fixes a **second, previously unreported defect on the NVIDIA DCP path** that the clamp in the earlier revision of
  this PR could not reach: an all-decode batch arriving with an over-estimated `max_query_len` made
  `run_split_fa2_dcp_context_attention` skip both of its flash-attention calls, dropping context for every row.
- Fixes the numeric symptom on `ROCM_AITER_FA`: on unpatched code the backend diverges from the SDPA baseline by up to
  **3.90625 absolute** (60.5% of elements, 0.01 tolerance); with this PR it matches.
- Divides the extend context workspace among extends that actually carry context, so interleaved fresh prompts no
  longer inflate the chunk count (#63542).
- **Net −8 lines of source** while fixing strictly more: `vllm/v1/worker/gpu/model_runner.py` is reverted to
  byte-identical with `main`.
- Gives the DCP caller (`vllm/v1/worker/cp_utils.py`) its first direct test coverage, on a path upstream CUDA CI
  actually executes.

## Details

**Root cause.** MRV2 guarantees only that decodes lead. `split_decodes_prefills_and_extends` additionally assumed the
extends precede the fresh prompts, and the prefill region is attended without reading the KV cache, so a
context-bearing request landing there silently loses its history. Sorting cannot fix this in general: the scheduler
pads a context-less one-token prompt with placeholder draft rows, and `compact_batch` requires drafted rows to stay at
the front, so they can sit ahead of context-bearing requests with no legal ordering that separates them. Thanks
@okorzh-amd for identifying that case.

**Why #63542's rewrite rather than this PR's clamp.** The clamp sat after the function's two early returns, so there
were inputs it could not reach. The rewrite removes those early returns and computes the boundary directly. That
difference is load-bearing, not cosmetic — see the DCP defect below.

**The guard added on top of #63542.** `max_query_len` is an upper bound, not the batch's true maximum
(`InputBatch.max_query_len` is documented as "longest query the batch MAY contain"; under adaptive verification the
model runner sets it from the pre-compaction estimate while `compact_batch` only shrinks the draft component). A batch
whose rows all ended up at `query_len == 1` can therefore arrive with `max_query_len > decode_threshold`, skip the
uniform-decode early return, and reach the boundary scan, where `argmin` over an all-true mask returns 0 and reports
zero decodes.

```python
is_decode = query_lens <= decode_threshold
if bool(is_decode.all()):
    return num_reqs, 0, 0, num_tokens, 0, 0
```

<details>
<summary>The DCP defect this closes</summary>

`split_decodes_prefills_and_extends` has two production callers, not one: `rocm_aiter_fa.py` and
`vllm/v1/worker/cp_utils.py` (`split_dcp_context_queries`, the NVIDIA decode-context-parallel path). The second is why
this is not a ROCm-local change.

On the batch above, `main` takes the `not torch.any(is_prefill_or_extend)` early return and yields
`(0, 0, 0, 0, 0, 0)`. `split_dcp_context_queries` passes those zeros on; `should_split_fa2_dcp_context_attention` arms
because `num_context_prefill_reqs (0) < num_prefills`; and `run_split_fa2_dcp_context_attention` then skips **both**
flash-attention calls because both token counts are zero. `dcp_context_out` stays zeroed and `context_lse` stays at its
`-inf` fill, so `merge_attn_states` drops the context contribution for every row.

Reachable on DCP > 1 + FA2 + adaptive verification with a reduced draft budget. The previous clamp could not fix it;
#63542's rewrite avoids the catastrophic path but still reports zero decodes; the guard returns the correct split.

</details>

**Why this is not duplicating an existing PR.** #63542 and this PR overlap on the `utils.py` hunk, which @whx-sjtu and
@okorzh-amd both raised. Rather than keep two clamps for one job, this PR now *carries* #63542's rewrite and workspace
fix, with credit to @qli88, and adds only what that PR does not have: the all-decode guard, a regression test for the
DCP defect it fixes incidentally and without coverage, and the merged test suite. **If the maintainers prefer, I will
close this PR and move the guard and tests over to #63542 instead** — what matters is that exactly one of us keeps the
splitter change. @qli88 @tjtanaa, your call. For #63676/#63675, per that PR's own description the fix commit reduces to
deleting the `mrv2-batch-order` entry from `known_defects.py` once either real fix lands; worth confirming this PR
clears that entry's unit and engine tests.

**Related defects, filed separately rather than folded in.** #60487 (`extend_forward` applies the attention sink once
per context chunk rather than once per merged result — affects every context-bearing extend row on `main` today and is
independent of this change), and `should_split_fa2_dcp_context_attention` deciding from region widths rather than
actual per-row context, which is correct with this PR's counts but whose premise is worth revisiting.

I kept the `num > 1` guard exactly as you wrote it. It is load-bearing: dropping it and simply
putting `no_context` first also zeroes the drops, but moves the decode boundary on roughly three

**One consequence worth stating explicitly, since it contradicts something in my original
description.** Your ordering does change `num_decodes`, and my claim that it was untouched was
wrong. Splitting the drift by whether the batch contains a decode at all — the only case where a
"uniform decode run" means anything:

| key | batches with ≥1 decode | batches with no decode |
|---|---|---|
| original commit | 0 | 1,909 |
| your ordering | **2,115** | 2,161 |

So it is a real change on meaningful batches, and I went looking for a key that avoided it. There
isn't one, because the two callers want contradictory things:

```
batch: decode4(drafted, context) | extend4096(context) | fresh4(NO context),  decode_query_len = 4

cp_utils, decode_threshold=1     ->  extend4096 survives only if fresh4 is LAST
require_uniform, threshold=4     ->  fresh4 counts as a decode only if ADJACENT to decode4
```

`fresh4` cannot be both. The module already says which should win, in the opening docstring of
`tests/v1/worker/test_gpu_batch_ordering.py`: *"a prompt chunk of exactly `decode_query_len` tokens
has a decode batch's shape, and must not be classified as a uniform decode batch."* That is exactly
what your ordering produces, so the `num_decodes` movement is a second documented bug being fixed
rather than collateral. The PR description now says this instead of the incorrect claim.

**On (2), the assertion.** Added in the same commit rather than as a follow-up, since this is the
PR that makes the precondition true. Two small deviations from your wording:

- it excludes zero-length rows, so padded batches cannot trip it;

def sort_batch_req_ids(
    num_tokens_per_req: dict[str, int],
    draft_tokens: dict[str, list[int]],
    decode_query_len: int,
    num_computed_tokens: np.ndarray | None = None,
    req_id_to_index: dict[str, int] | None = None,
) -> list[str]:
    # Order verification/decode -> short_extend -> extend -> prefill.
    # (keep the PR's explanatory comment here)
    req_ids = list(num_tokens_per_req)
    n = len(req_ids)
    num = np.fromiter(num_tokens_per_req.values(), dtype=np.int32, count=n)
    no_draft = np.fromiter((not draft_tokens.get(r) for r in req_ids), dtype=bool, count=n)
    # np.lexsort sorts by the LAST key first, so this list is in reverse priority:
    # no_draft, then (fresh prefill), then num != decode_query_len, then num.
    keys = [num, num != decode_query_len, no_draft]
    if num_computed_tokens is not None and req_id_to_index is not None:
        rows = np.fromiter(map(req_id_to_index.__getitem__, req_ids), dtype=np.intp, count=n)
        keys.insert(2, (num > 1) & (num_computed_tokens[rows] == 0))
    return [req_ids[i] for i in np.lexsort(keys)]
```

```
def key(r: str) -> tuple[bool, bool, bool, int]:
    num = num_tokens_per_req[r]
    no_context = (
        num > 1
        and num_computed_tokens is not None
        and req_id_to_index is not None
        and bool(num_computed_tokens[req_id_to_index[r]] == 0)
    )
