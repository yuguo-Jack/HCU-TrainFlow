# [Bugfix][Responses API] Execute parallel built-in tool calls

[Upstream PR](https://github.com/vllm-project/vllm/pull/57808) · state: open · merged: False

## Original PR description

## Purpose

Fixes #57791.

The non-Harmony Responses API path previously inspected and executed only the
last response item after a generation turn. When a parser emitted multiple
server-managed built-in tool calls, every earlier call was silently skipped.

This change:

- tracks the start of each generation turn and executes every trailing built-in
  call from that turn in model output order;
- keeps historical calls and calls from completed generations outside the
  execution boundary;
- rejects turns that mix server-managed built-ins with client-managed
  functions instead of silently leaving a built-in call unexecuted;
- rejects duplicate `call_id` values before any tool is dispatched, preventing
  output-correlation ambiguity after a side effect has already occurred;
- passes the current call explicitly to local `Tool` implementations;
- correlates tool outputs with their originating calls by `call_id` rather than
  list adjacency.

Execution is intentionally sequential. This preserves deterministic ordering
for stateful tool sessions and retains the existing fail-fast behavior for
runtime tool errors.

This PR is now stacked on #55540. The current vLLM base still has a malformed
JSON retry defect that can abort the loop before a later valid call executes.
With #55540 underneath this change, malformed JSON produces a retry item for
that call and processing continues to subsequent valid calls. The only
additional commit to review is `38d829ae8`.

## Test coverage

The unit coverage includes:

- browser/Python calls in both model-output orders;
- multiple calls sharing one tool session;
- generation-boundary isolation and no historical replay;
- mixed built-in/client-managed turns;
- duplicate `call_id` rejection before any dispatch;
- fail-fast behavior after a runtime tool error;
- local Python tool dispatch using each explicit call;
- final `McpCall` pairing by `call_id`;
- an invalid-JSON call followed by a valid call in the same turn.
