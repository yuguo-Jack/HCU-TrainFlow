# [Bugfix][Kernel] Mask out-of-range page-table loads in Triton unified attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/61028) · state: open · merged: False

## Original PR description



## Overview

Mask the compact page-table load in `kernel_unified_attention` so lanes whose page index is past `cdiv(seq_len, BLOCK_SIZE)` do not read beyond the block-table row. One hunk, no launch or selection change.

## Claims

- Fixes an out-of-bounds global read of `block_tables` when `TILE_SIZE > BLOCK_SIZE` (for example the 32-token 2D/prefill tile with 16-token pages). Compute Sanitizer on current main reports 30 invalid reads at this load; 0 after the patch.
- No numerical change: those lanes are already excluded from the K/V loads by `tile_mask`.

## Validation

All on one H100 80GB HBM3 (SM90), `vllm/vllm-openai:v0.31.0` image (torch 2.13.0+cu130, Triton 3.7.1), with `triton_unified_attention.py` from main `ba77c4c130` (identical to the file at current main) overlaid:

| Check | Unpatched main | Patched |
|---|---|---|
| `compute-sanitizer --tool memcheck`, B1, context 1025, block 16, compact block table, forced 2D path | 30 invalid `__global__` reads, all at the page-table load | 0 |
| same, 3D decode path (tile 16) | 0 | 0 |
| same, B4, 2D and 3D | not run | 0 / 0 |
| `pytest tests/kernels/attention/test_triton_unified_attention.py::test_triton_unified_attn` (main test file) | not run | 768 passed in 99 s |

The same masked load was also in a guarded Triton source used for Qwen3-8B-AWQ serving runs on vLLM 0.31.0 (default compilation, exact greedy-token parity vs FLASH_ATTN). Its overhead in an incomplete-page microbenchmark (six GQA shapes, context 1025, permuted pages, 100-call CUDA graphs) was 0.50% median vs the unmasked source.

Reproducer, probe script, raw sanitizer logs, and pytest log: https://github.com/ToukoUrsin/vllm-triton-decode-tile64-evidence (section 3, `bench/sanitizer/`, `results/rerun-2026-10-10/`).

## Details

Root cause: the tile loop computes `seq_offset = j * TILE_SIZE + offs_t` and loads `block_tables_ptr + block_table_offset + seq_offset // BLOCK_SIZE` for every lane before any mask. When the last tile extends past the last page and `TILE_SIZE > BLOCK_SIZE`, some lanes index one or more entries past `cdiv(seq_len, BLOCK_SIZE)`. With a block table whose row width is exactly the page count (as in the kernel tests), that reads past the allocation for the last row; in serving, rows are padded to the per-request maximum, so the stray read usually lands in padding, but it can still run off the end of the tensor for the last row. The fix applies the page-count predicate to the load and supplies `0` for masked lanes; the `USE_TD` scalar load is unchanged because `BLOCK_SIZE % TILE_SIZE == 0` keeps it in range.

Tradeoff: one extra integer compare per lane per tile on the page-table load.

CI coverage: no new test. The read does not change outputs, so it is only observable under a memory checker; the existing kernel test exercises the patched line.
