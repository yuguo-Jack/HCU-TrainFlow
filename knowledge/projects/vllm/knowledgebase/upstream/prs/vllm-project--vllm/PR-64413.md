# [Bugfix] Keep the Hub ID visible when loading HF tokenizers from the local snapshot

[Upstream PR](https://github.com/vllm-project/vllm/pull/64413) · state: closed · merged: False

## Original PR description

## Overview

Since #60825 loads HF tokenizers from a local snapshot directory (v0.32.0 and main; v0.28.0 is not affected), `deepseek-ai/deepseek-coder-*`, `deepseek-ai/DeepSeek-R1-Distill-Llama-*` and `stepfun-ai/step-3.7-*` get the wrong tokenizer class and lose every space: "key 96727 value 4922" encodes as "key96727value4922". This PR passes the Hub ID to transformers again, through the config `get_tokenizer` already reuses.

## Claims

- Fixes the tokenization, and so the outputs, of deepseek-coder and DeepSeek-R1-Distill-Llama checkpoints (verified on deepseek-coder-1.3b-base, deepseek-coder-6.7b-base and DeepSeek-R1-Distill-Llama-8B).
- Restores transformers' Hub-ID matching (`MODEL_IDS_TO_TOKENIZERS_BACKEND`) for all of its nine patterns; the other seven (e.g. umt5-small, blip2, donut) were not checked for wrong output.
- No change for other checkpoints (Qwen2.5 and Llama-3.2 tokenize identically before and after).

## Details

Root cause, in two parts:

1. `resolve_tokenizer_args` rewrites the tokenizer name in `hf` mode to `get_non_weight_snapshot_path(...)`, a local snapshot directory. `get_tokenizer` then loads the config from that directory and passes it to `AutoTokenizer`, so the config's `_name_or_path` is the directory, not the Hub ID.
2. transformers corrects a few checkpoints whose Hub `tokenizer_class` is wrong by matching their Hub ID against `MODEL_IDS_TO_TOKENIZERS_BACKEND` (fnmatch on `config._name_or_path`). deepseek-coder declares `LlamaTokenizerFast` over a byte-level BPE vocabulary; with the ID matched, transformers uses `TokenizersBackend`; with a directory, nothing matches and the declared class is used, which drops every `Ġ` (the byte-level space).

`AutoTokenizer.from_pretrained` on the same directory with the Hub ID as `config._name_or_path` returns the right class, so the fix sets that on a copy of the config when the name was rewritten (`tokenizer_mode == "hf"` and the loaded path differs from the requested name). The copy keeps the cached config unchanged.

Alternatives considered: loading from the Hub ID instead of the snapshot would bring back the per-load Hub requests that #60825 removed (9 to 2 per tokenizer load); forcing `TokenizersBackend` in vLLM for these models would duplicate transformers' list.

Not checked: #60825 also loads processors (`get_processor`) from the snapshot; whether any processor depends on the Hub ID the same way was not tested here.

Found while running the same checkpoints on vLLM 0.28.0 and 0.32.0; the two disagreed on unquantized accuracy (239 against 0), and the tokenizer was the difference (model config and rotary embedding identical in both).
