# [Bugfix][KV Connector] NIXL: tile whole kernel rows of smaller-block KV cache groups

[Upstream PR](https://github.com/vllm-project/vllm/pull/64067) · state: open · merged: False

## Original PR description



## Overview

Fixes #63997. With HMA attention groups of different block sizes (Gemma 4), `NixlConnector` fails at startup in `register_kv_caches` with "KV cache view cannot be partitioned into NIXL regions". This registers the affected views as dense NIXL pages and rejects peers whose geometry can't read them.

Related: #59586 fixes the same mismatch for MLA kernel rows. This PR covers non-MLA attention and leaves the MLA path alone.

## Claims

- Gemma 4 style layouts (non-MLA attention groups with equal page bytes but different block sizes) register with NIXL instead of failing the assertion.
- Each whole logical row of the smaller-block group is addressed as `ratio` dense pages, so kernel block ids `ratio*b ... ratio*b + ratio - 1` cover logical row `b` byte for byte.
- A peer with a different TP size, block size or physical-per-logical ratio is rejected at handshake with a clear `NotImplementedError` instead of transferring the wrong bytes.

## Validation

New test `test_whole_kernel_rows_of_a_smaller_block_group_tile_into_nixl_pages` in `tests/v1/kv_connector/unit/test_nixl_desc_geometry.py`. Two attention groups of 32 and 16 tokens share one multi-layer allocation, and the backend supports only 16-token kernel blocks.

| | `main` | this PR |

| registration | `AssertionError: KV cache view cannot be partitioned into NIXL regions: layer=whole.0, cache_nbytes=4096, num_blocks=8, block_stride=1024, physical_page_size=512` | 3 regions, `block_len == block_stride == page // 2`, 8 blocks each, descriptors tile the allocation |
| peer with the same geometry | n/a | accepted |

## Details

**Root cause.** `NixlConnectorWorker` sets `block_size` to the LCM of the transfer groups' block sizes and, in `_sync_block_size_with_kernel`, picks one kernel block size for all backends. The resulting `_physical_blocks_per_logical_kv_block` applies to every layer. The model runner instead picks a kernel block size per group (`prepare_kernel_block_sizes`). A group whose own block size the backend already supports keeps whole rows (`[NB, page]`), while NIXL expects `[NB * ratio, page / ratio]`. In the issue, `num_blocks=42182` (2 × 21091) meets `block_stride=262144` (2 × 131072), and no region split fits.

**Flow.**
1. P and D start with the same config. Each worker calls `register_kv_caches`.
2. For a whole-row layer, NIXL computes `num_blocks = logical * ratio` with the view's full-row stride, and the region math raises. Startup fails on both sides.
3. With this PR, the row is registered as `ratio` dense pages. `_logical_to_kernel_block_ids` expands the scheduler's logical block ids as before, and each expanded id now maps to one page of the right logical row on both P and D.
4. At handshake, each side compares TP, block size and ratio with its peer. With dense pages in use, any difference is rejected.

**Why dense pages and not a per-group ratio.** The single ratio also drives block id expansion, descriptor ids, prefix-cache zeroing and the `physical_blocks_per_logical_kv_block` handshake field. A per-group ratio would change the handshake contract and most of those paths. Dense pages leave all of that unchanged, because every transfer already moves all `ratio` pages of a logical block.

**Limitations.**
- The pages split a row at byte offsets, not at heads or tokens. Heterogeneous TP and heterogeneous block sizes need head or token aligned slices, so those configurations are rejected rather than supported.
- Only contiguous views are handled. Non-contiguous whole-row layouts, such as block-outermost packing, still hit the original assertion.
- MLA is excluded; #59586 handles it.
