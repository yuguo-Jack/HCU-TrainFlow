# [ROCm][DSv4.1] Enable prefix-cache SWA replay on gfx942

[Upstream PR](https://github.com/vllm-project/vllm/pull/65249) · state: open · merged: False

## Original PR description

## Overview

Enable prefix-cache SWA replay on CDNA3 (gfx942). #64094 enabled it on CDNA4 only. The change is the CDNA check in the DSv4.1 attention layer and the comment in `amd/model.py` that describes it.

`--swa-bounded-replay` is on by default, so after this PR every gfx942 DSv4.1 server with model runner V2 and prefix caching replays the window on hits. `--no-swa-bounded-replay` turns it off.

## Claims

- gfx942 runs the same bounded replay as gfx950: the scheduler rewinds a hit by the 128-token window, and the shared metadata and `combine_topk_swa_indices` kernels bound each gather at `replay_start`. None of that is arch-specific; only the CDNA check kept it off.
- Prefix hits recall planted codes as well as cold misses, and a per-layer log shows every hit gathering from `replay_start`.
- With prefix caching on in both arms, this PR serves a shared-prefix workload at 1.6–1.7× the request throughput of main, with 4–5× lower median TTFT. A single repeated prompt hits 5–9 ms slower, which is the window being recomputed.
- RULER NIAH at 131072 and GSM8K are unchanged.

## Validation

MI325X TP4, `--monokernel` unless noted, prefix caching on in both arms. "main" is image `0.33.0rc1.dev484+g76c6f3f2a`; "this PR" is the same image with only this PR's gate change applied to its `attention.py`. Both arms ran side by side with the same KV cache size. `VLLM_ROCM_USE_AITER_TRITON_SPARSE_MLA` is gfx950-only and ignored on gfx942, so it plays no part here.

### Throughput with shared prefixes

Many requests that start with the same long prefix. `vllm bench serve --dataset-name prefix_repetition`: 256 prefixes of 32768 tokens, each used 4 times with a different 256-token suffix, 1024 prompts.

| concurrency | req/s, main / this PR | median TTFT, main / this PR | median TPOT, main / this PR |
| --- | --- | --- | --- |
| 8 | 1.49 / 2.39 | 2489 / 572 ms | 16.2 / 9.1 ms |
| 32 | 1.67 / 2.90 | 3608 / 765 ms | 114 / 45 ms |
| 64 | 1.72 / 2.99 | 2181 / 437 ms | 244 / 88 ms |

TPOT is not flat because decode shares each step with prefill chunks, and main prefills about twice as many prompt tokens (below). The decode kernels are the same in both arms.

Both gains come from hits. The prefix cache hit rate is about 50% on main and 76% with this PR. Main misses the second use of each prefix: one 32768-token prefix sent four times in a row, each with a new 256-token suffix, hits 0, 0, 32768 and 32768 tokens on main, and 0, 32768, 32768 and 32768 with this PR. Two hits out of four uses on main and three with this PR give the 50% and 76%. With a suffix shorter than the window (64 tokens), main also hits from the second use.

### Cost on a single repeated prompt

TTFT of an exact repeat, served from the prefix cache. This PR recomputes the 128-token window on every hit; main does not.

| prompt | hit TTFT, main / this PR |
| --- | --- |
| 4096 | 28 / 37 ms |
| 32768 | 40 / 49 ms |
| 65536 | 54 / 59 ms |

### Recall on cache hits

Checks that a hit gives the same answers as a cold run. The prompt hides three codes (23, 320 and 2400 tokens from the end) and asks for them back. Each case runs cold, then again so it hits the cache. gfx942 prefill is not bit-stable above 512 tokens, so cold runs also miss codes sometimes; each case is 8 trials, each under its own `cache_salt`, and the two columns should match, not be 8/8.

| prompt | tokens from cache | cold, all 3 codes | cache hit, all 3 codes |
| --- | --- | --- | --- |
| 4096, repeated | 4032 | 8/8 | 8/8 |
| 4096 cached, then sent with 512 more | 4096 | 4/8 | 7/8 |
| 16384 cached, then 4096 more, across a prefill chunk | 16384 | 3/8 | 3/8 |
| 32768 cached, then 1 more | 32768 | 6/8 | 8/8 |
| 65536 cached, then 1 more | 65536 | 7/8 | 6/8 |
| 8 different 8191-token prompts, sent all at once, cold and then as hits | — | 6/8 | 6/8 |
| multi-turn: a 16000-token turn 1, then turn 2 adds its 256 generated tokens | 16192 | 8/8 | 8/8 |
| same, with DSpark k=6 | 16192 | 8/8 | 8/8 |
| 4096, repeated, without `--monokernel` | 4032 | 8/8 | 8/8 |
| 32768 cached, then 1 more, without `--monokernel` | 32768 | 5/8 | 5/8 |
| control: 4064, repeated, with the window not rebuilt | 4032 | 8/8 | 1/8 |
| 4096 / 8191 / 16384 / 32768, repeated, on a full cache (below) | 4032–32704 | 31/32 | 32/32 |

The control row breaks the replay on purpose, and the hits fail, so the probe catches a broken replay. With 8 trials it cannot show that hits are exactly as good as cold runs; small differences would not show up.

The full-cache row ran with the KV cache cut to 701,257 tokens (`--kv-cache-memory-bytes 3500000000`) while 9–10 random 16384-token requests ran in the background. About 7.5M prompt tokens went through the cache during the probe, and every hit was still served from it.

### Accuracy

| task | main | this PR |
| --- | --- | --- |
| RULER niah_single_1, 131072 tokens | 1.0 | 1.0 |
| RULER niah_single_2, 131072 tokens | 1.0 | 1.0 |

5-shot GSM8K strict-match with this PR is 0.9227 ± 0.0074 on the image and 0.9181 ± 0.0076 on upstream main `3a228c1fe`, against 0.9196 published with prefix caching off. GSM8K was not run on main with prefix caching on.

### CI

`test_prefix_cache_replays_the_swa_window` now expects CDNA3 to replay, and CDNA2 to stay off. It mocks the platform and the CDNA version, so it checks the gate, not gfx942 hardware. The `replay_start` clamp is covered by `test_builder_replay_start_bounds_prefill_window_and_gather`, which runs on the GPU. Both are in `tests/v1/attention`, which the optional AMD MI300 "V1 Attention" job runs.
