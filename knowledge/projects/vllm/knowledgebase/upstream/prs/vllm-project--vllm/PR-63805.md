# [RL] Add Connex weight transfer backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/63805) · state: open · merged: False

## Original PR description



## Overview

Registers a `connex` backend in vLLM's pluggable weight-transfer API (worker and trainer side) as a thin, lazily imported re-export of the engine maintained in [Connex](https://github.com/HeterInfra/connex), following the `modelexpress` backend. The `WeightTransferEngine` docstring lists RDMA as a TODO; this provides one RDMA option without adding a dependency to vLLM.

**Not a duplicate:** searched open PRs and issues for "weight transfer backend", "weight sync RDMA", "RL elastic rollout". Related but different: #52152 (shared-disk backend), #61083 (`sparse_disk` backend), #62557 (per-update source ranks for NCCL), #57374 (XPU torch.distributed), #44994 (fast EP scaling). None adds an RDMA pull backend or handles engines joining or failing during an update.

## Claims

- New `--weight-transfer-config '{"backend": "connex"}'`, documented in `docs/training/weight_transfer/connex.md`.
- Engines pull each version with one-sided RDMA reads; no communicator group, so engines can join, leave or restart between updates without anyone re-initializing.
- Engines that finished pulling serve later pullers (tree fan-out), so the trainer NIC does not serve every engine.
- A source dying mid-transfer is survived: the reader switches source and other engines are unaffected.
- Cross-node transfer is faster than NCCL broadcast over IPoIB sockets in our setup (caveat below); on a single host NCCL is faster.

## Validation

- `pytest tests/distributed/test_weight_transfer.py`: 114 passed, 23 skipped (skips need 2 GPUs or Ray workers) on an A40 host, main d0d681e4. pre-commit on the changed files passes; `ruff check` / `ruff format` (v0.14.0) and `typos` clean. Full `pre-commit run --all-files` not yet run.
- End to end through the real entry point (`vllm serve` + `HTTPVLLMWeightSyncClient` + `WeightTransferTrainerFactory`): Qwen2.5-0.5B-Instruct, three versions (original, perturbed, original); greedy outputs match the baseline after versions 1 and 3 and differ after version 2. Run on vLLM 0.32.0 and on main.
- GRPO loop with two `vllm serve` engines, one killed mid-rollout and a new one joining two steps later: all 256 rollouts complete, each generated by a single weight version, the joining engine pulls the latest version before serving.

The new unit tests run in CI (they mock the Connex module); the RDMA paths need Connex and RDMA NICs, which CI lacks, so they were validated outside CI as above.

Timings below were measured on vLLM 0.32.0 and not re-run on d0d681e4 (A40, InfiniBand 100 Gb).

## Details

- `vllm/distributed/weight_transfer/connex_engine.py`: re-exports `ConnexWeightTransferEngine`, `ConnexTrainerWeightTransferEngine` and their info dataclasses from `connex.rl.vllm_backend`; raises `ImportError` with an install hint on `ModuleNotFoundError` for Connex only.
- `factory.py`: lazy registration of `connex` in both factories (imported only when selected).
- `receive_weights` loads through `model.load_weights` inside the layerwise reload lifecycle, as the NCCL backend does. Reads are idempotent byte ranges, which is what makes source switching safe.
- Docs page plus a row in the backend table; registry tests (lazy import on both factories, missing-package error).

Open point: the install hint currently points at the Connex GitHub repository; publishing the package to PyPI before merge is probably preferable.

- yanyinglin · comment · 2026-11-02T02:33:42Z · [source](https://github.com/vllm-project/vllm/pull/63805#issuecomment-6567676547)

Thanks for the careful questions. Short answers first, then details. All numbers below are from single runs on A40 GPUs with 100 Gb InfiniBand, on GPUs shared with other tenants, so please read them as indicative.

**Advantage**

1. What only Connex handles, compared with `sharded_rdt` and `nccl_m2n`: a rollout pool whose membership changes while training runs. Both of those backends assume a fixed set of participants known at init (`nccl_m2n` builds one communicator over trainer and workers, and every rank takes part in every reshard; `sharded_rdt` needs the workers to be Ray actors with NIXL). With Connex, an engine that joins later pulls the current version from the trainer or from engines that already hold it, with no group to rebuild; an engine that dies mid-pull does not block the round; and a receiver whose source dies mid-read switches to another source and continues. In a churn run (3.09 GB, three receivers starting 0.5 s apart), one receiver exited while another was reading from it; the reader switched to the trainer and finished in 0.354 s, against 0.32 to 0.42 s in rounds without a failure. A GRPO run with an engine killed during rollouts and a new one joining two steps later completed 256/256 rollouts, with exactly one weight version per step. The other side of this: `sharded_rdt` and `nccl_m2n` move only each worker's slice and handle sharded trainers, and Connex does neither today (see concern 2).

2. When all replicas pull at once, peer fan-out does not help in our current implementation. Fan-out is per finished copy, so receivers that start together all read from the trainer, and peers only serve engines that start later; chunk-level relaying is not implemented. That is the setup of the cross-node numbers below. On the comparison: we have not run NCCL over IB verbs, RDT or M2N on the same hardware. What we measured, transfer only, all receivers starting together, warm rounds:

   | weights | receivers | NCCL broadcast over IPoIB | Connex (connex-rs over IB) |
   |---|---|---|---|
   | 0.99 GB | 3 on 2 nodes | 0.611 s | 0.394 s |
   | 3.09 GB | 3 on 2 nodes | 1.949 s | 1.192 s |
   | 16.06 GB | 2 | 5.821 s | 3.334 s |

   The NCCL column is NCCL over IPoIB sockets (`NCCL_IB_DISABLE=1`), because NCCL over IB verbs failed at the first collective in that pod image. So this is **not** a comparison with NCCL over IB verbs, and I would expect NCCL over verbs to close most or all of that gap. On one node NCCL is clearly faster: 0.051 s vs 0.21 s for 0.99 GB, since NCCL uses the PCIe peer path and connex-rs reads go through the NIC. End to end through this API on one host (one engine, `send_weights()` warm), the `nccl` backend took 0.097 / 0.201 / 0.798 s and `connex` 0.299 / 0.613 / 2.149 s for 0.5B / 1.5B / 8B models. I am happy to run a same-hardware comparison against `nccl` over IB verbs, `sharded_rdt` and `nccl_m2n` if that would help the review; I have not done it yet.

**Concerns**

1. Memory. The trainer side packs the weights into a registered arena and keeps `buffers` of them (default 2, so the trainer can publish version v+1 while engines still read v); `buffers=1` halves that, and we had to use it for the 8B model next to the trainer's model on one A40. Each worker keeps one full-model-sized arena, which also lets it serve as a source for peers. The worker arena is allocated lazily at the first pull, after vLLM has sized the KV cache, so it does not shrink the KV cache; instead it has to fit in the memory vLLM leaves outside `gpu_memory_utilization`, and it can fail with OOM if that headroom is too small. I have not measured peak memory on either side; I can add that measurement. Freeing the worker arena after the load (at the cost of no longer serving peers) is a possible option.

2. Yes, today each TP rank pulls the whole model and loads it only after the pull completes (`load_weights` does the sharding). Per-rank slice pulls and layer-wise pipelining are not implemented. Both would fit the design (the pull is chunked one-sided reads against a manifest), but I have no timeline, and for large TP/EP deployments `sharded_rdt` and `nccl_m2n` are the better fit today.

**Target scenarios**

1. What we have run: Qwen2.5-0.5B and 1.5B and Llama-3-8B sized weights (synthetic for the transfer benchmark), up to three receivers on up to three nodes, TP=1 engines, and a GRPO loop on Qwen2.5-0.5B-Instruct with two rollout engines in which one engine was killed and a new one joined. The target is rollout pools that scale or get preempted (spot or shared-cluster capacity), where the pool membership is not fixed between steps.
2. Large multi-GPU MoE models such as DeepSeek-V4 are effectively out of scope for this backend today: pulling the full model per rank with no slicing does not scale to that size, and we have not tested multi-node engines or expert parallelism.
