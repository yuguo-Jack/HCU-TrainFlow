# [Core][Spec Decode] Give the DFlash/DSpark drafter's KV its own block pool

[Upstream PR](https://github.com/vllm-project/vllm/pull/64611) · state: open · merged: False

## Original PR description

## Purpose

**Stacked on #64109 (DFlash/DSpark drafter KV backs only its tail) and #64628 (`--max-num-inflight-kv-loads`)**, and builds on #63416 (NIXL pairs KV regions by layer, now merged). The branch merges #64109 and #64628; the rest of the diff is this PR.

This PR adds `--draft-kv-pool`, which gives a DFlash or DSpark drafter's sliding-window KV its own block pool.

With the hybrid KV cache manager every group draws from one pool, and every block is as large as the widest group's. A drafter group of a few sliding-window layers therefore pays a target-sized block for each of its blocks. RFC #59117 measures what this costs on a GDN target with a 5-layer DFlash drafter: 3-11x less KV capacity.

In its own pool, a drafter block is as large as the drafter's layers. The pool is sized for the window each request keeps under #64109.

## Changes

**Config:** `--draft-kv-pool` and `--draft-kv-pool-cache-fraction` (default 0.5).

**Planning** (`kv_cache_planning.py`):
- `get_global_kv_cache_groups` groups the drafter's `DFlashSlidingWindowSpec` layers on their own, in pool 1 (`KVCacheGroupSpec.pool_id`).
- The pool holds the null block plus `(max_num_seqs + max_num_inflight_kv_loads) × (1 + cache_fraction)` requests at their admission cap. An async KV load holds drafter blocks without counting toward `max_num_seqs`, and #64628 caps those loads, so this bounds every request that holds drafter blocks. A KV consumer with the pool must therefore set `--max-num-inflight-kv-loads`; startup fails without it. The pool is sized from the specs alone, so every worker and the scheduler agree on it.
- `get_kv_cache_configs` sets the pool's bytes aside on each worker that holds the drafter, and plans the shared pool in the memory left.
- The pool is laid out after the shared pool, in the same backing allocation (`KVCacheTensor.pool_id`, `KVCacheConfig.pool_num_blocks`).
- A PP stage without the drafter keeps all its memory for the shared pool.

**Scheduler** (coordinator, KV cache manager, scheduler):
- Each pool's groups take blocks from their own `BlockPool`. Block frees already route to the block's own pool.
- Admission, the watermark and the async-load reservation are checked per pool, so running out of drafter blocks blocks admission on its own.
- Copy-on-write copies carry their pool.
- `get_kv_cache_usage` reports the fullest pool.
- Drafter blocks are never zeroed: the pool holds one precision, so it doesn't count toward a mixed-precision cache either.

**Model Runner V2:**
- Block copies run per pool.
- Dummy contexts and warmup take block IDs from each group's own pool.
- The block zeroer skips pool groups. Otherwise, when the target needs zeroing (Mamba layers or mixed precisions), it checks the drafter's layers against the shared pool's block count and fails at startup.

**NIXL:**
- A pool's regions carry the pool's block count. #63416 already reads a peer's per-region counts.
- A contiguous page view counts as block-major when private pools share the backing. Without this, registration fails with "KV cache view cannot be partitioned into NIXL regions".
- With Mamba layers, registration resets every region to the shared pool's kernel-block count; a private pool's regions now keep their own.

**KV transfers need nothing else.** Under #64109 a transfer moves the drafter's window on both sides, and #63416 pairs regions by layer. So a peer with the pool can pull from, or push to, a peer without it, as long as the drafter is its own cache group there (the hybrid manager).

**Refused for now:**
- other KV connectors;
- Model Runner V1;
- `--disable-hybrid-kv-cache-manager`;
- the extensible KV cache: it is turned off by default with the pool, and an explicit request is an error. It sizes the cache after warmup, and the pool sits after the shared pool at an offset fixed at planning;
- HiSparse;
- a custom `KVCacheConfigBuilder` placement;
- NIXL with a host transfer buffer.

**Not a duplicate:** RFC #59117 has a proof of concept with a worker-owned ring for the draft KV. No open PR implements a drafter pool; #64109 is the only PR that links the RFC. This PR's pool is managed by the scheduler instead: drafter blocks are prefix-cached and transferred like any other group's.

New tests:
- **Planning:**
  - the drafter goes to pool 1, sized as above, after the shared pool, which gets the memory left;
  - PP stages agree on the pool's size, and a stage without the drafter holds no pool;
  - EAGLE, Model Runner V1, no hybrid manager, another connector, and a NIXL consumer without `--max-num-inflight-kv-loads` are refused;
  - the pool counts `--max-num-inflight-kv-loads` loads on top of `max_num_seqs`;
  - the extensible KV cache stays off with the pool, and an explicit request is refused.
- **Allocation:** drafter blocks come from the pool; an empty pool blocks admission while the shared pool has room; reservations are checked per pool.
- **Worker:** a block copy applies only to the pool it names. With a Mamba target, the zeroer sees only the shared pool's groups; on the code without the fix, it also gets the drafter's layer.
- **NIXL:**
  - pool regions sit at the pool's offset with the pool's block count, for BLHNC and LBHNC. On the code without this PR's NIXL change, registration raises;
  - on an MLA + GDN hybrid, the drafter's pool region keeps its pool's block count while the other regions take the shared pool's. With the old reset it got the shared pool's 16 blocks instead of 6.
