# [CI] Split (B200) MoE Refactor DP Integration TEMPORARY into per-checkpoint jobs

[Upstream PR](https://github.com/vllm-project/vllm/pull/58777) · state: closed · merged: False

## Original PR description

## What

`(B200) MoE Refactor DP Integration TEMPORARY` runs 13 GSM8K configs in one serial job, and pytest alone takes about 40 minutes. This PR splits its config list into one list per Qwen3-30B-A3B checkpoint, and gives each list its own named job. The configs, the test file and the device settings do not change.

## Old

```text
:nvidia: (B200) MoE Refactor DP Integration TEMPORARY
  key moe-refactor-integration-test-b200-dp-temporary
  --config-list-file=.../moe-refactor-dp-ep/config-b200.txt   (13 configs)
```

## New

Old key `moe-refactor-integration-test-b200-dp-temporary` → five keys `moe-refactor-integration-test-b200-dp-temporary-<suffix>`:

| Job label suffix | key suffix | list (`moe-refactor-dp-ep/`) | configs (`Qwen3-30B-A3B-…`) |
|---|---|---|---|
| `Qwen3 NvFp4 CT` | `-nvfp4-ct` | `config-b200-nvfp4-ct.txt` | `NvFp4-CT-fi-cutedsl-deepep-ll`, `NvFp4-CT-fi-cutlass` |
| `Qwen3 NvFp4 ModelOpt` | `-nvfp4-modelopt` | `config-b200-nvfp4-modelopt.txt` | `NvFp4-ModelOpt-fi-cutedsl-deepep-ll`, `NvFp4-ModelOpt-fi-trtllm`, `NvFp4-ModelOpt-fi-cutlass` |
| `Qwen3 Fp8 AutoFp8` | `-fp8-autofp8` | `config-b200-fp8-autofp8.txt` | `Fp8-AutoFp8-deepgemm-deepep-ht`, `Fp8-AutoFp8-deepgemm-deepep-ll`, `Fp8-AutoFp8-deepgemm` |
| `Qwen3 Fp8 CT Block` | `-fp8-ct-block` | `config-b200-fp8-ct-block.txt` | `Fp8-CT-Block-deepgemm-deepep-ht`, `Fp8-CT-Block-deepgemm-deepep-ll`, `Fp8-CT-Block-deepgemm` |
| `Qwen3 BF16` | `-bf16` | `config-b200-bf16.txt` | `BF16-triton`, `BF16-moonep` |

Each config appears in exactly one list, and together the five lists hold exactly the 13 entries of the old `config-b200.txt`. The old list is deleted, because this job was its only consumer.

## Notes

- **The jobs are grouped by checkpoint, not by duration.** Each list holds one quantized checkpoint, so each job downloads its weights once. The Fp8 configs alone come to about 20 minutes of pytest, and the NvFp4 configs to about 18, so neither quantization format fits in one job with headroom.
- **Each job keeps the old `device`, `num_devices`, `optional`, and its lack of trigger paths.** The one new setting is `timeout_in_minutes: 60`. The old job had no timeout, and on main build [90771](https://buildkite.com/vllm/ci/builds/90771) it ran for 3h10m while four DeepEP LL configs each waited out the 2400s server-startup limit from #57361. A 60-minute timeout still leaves room for one slow startup.
- **`BF16-moonep` skips on every run.** The image doesn't include the `moonep` package. The config stays in the BF16 list unchanged.
- **Out of scope:** `Llama-4-Scout-Fp8-ModelOpt-triton.yaml` sits in the same directory, but no list on `main` includes it. This PR leaves it alone.

## Expected runtime and overhead

These are **predictions**, built from per-config times (`_bk;t=` log timestamps) on six green scheduled main builds: [90589](https://buildkite.com/vllm/ci/builds/90589), [90830](https://buildkite.com/vllm/ci/builds/90830), [90897](https://buildkite.com/vllm/ci/builds/90897), [91049](https://buildkite.com/vllm/ci/builds/91049), [91173](https://buildkite.com/vllm/ci/builds/91173) and [91191](https://buildkite.com/vllm/ci/builds/91191). Pytest is the sum of each config's worst time across those runs, plus about 0.2m of collection. Overhead is the old job's typical wall-minus-pytest (0.7–1.0m in four runs, 2.4–2.7m in two).

| Job | pytest | running wall | non-pytest overhead | main overhead cause |
|---|---|---|---|---|
| Qwen3 Fp8 AutoFp8 | ~12.0m | ~13m | ~1m | job start and checkout before pytest (~0.7m); rest unattributed |
| Qwen3 NvFp4 ModelOpt | ~11.3m | ~12.3m | ~1m | same |
| Qwen3 Fp8 CT Block | ~9.1m | ~10.1m | ~1m | same |
| Qwen3 NvFp4 CT | ~7.6m | ~8.6m | ~1m | same |
| Qwen3 BF16 | ~2.9m | ~3.9m | ~1m | same |

- **Baseline:** one job, 40.5–43.1m running wall (39.7–40.9m pytest).
- **After:** about 48m in total, so roughly **+5 to +7 extra worker-minutes** against the baseline range. That is four more copies of the per-job overhead and of pytest collection. If every job hit the worst overhead seen (2.7m), it would be about +15m. Both are inside the 20-minute budget.
- **Slowest job:** Fp8 AutoFp8, at ~12m pytest (~13m wall). The critical path falls from ~41m to ~13m.
- **Why five jobs:** splitting only by quantization format leaves Fp8 at about 20m and NvFp4 at about 18m. Splitting each format by checkpoint (CT vs. AutoFp8/ModelOpt) is the smallest correlated split that brings every job to about 12m or less. BF16 is a separate checkpoint, so it gets its own job.

Validation will follow as a PR comment from a scoped build of the five new keys.
