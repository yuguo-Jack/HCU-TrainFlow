# [Frontend][Mistral] Forward response_format to mistral-common chat templating

[Upstream PR](https://github.com/vllm-project/vllm/pull/63812) · state: closed · merged: True

## Original PR description



## Overview

Forward the OpenAI `response_format` to mistral-common so v15 tokenizers that declare a `json_schema` model setting render it into `[MODEL_SETTINGS]`. The Mistral tokenizer now forwards extra chat-template kwargs instead of special-casing `reasoning_effort` behind a version check.

Related: #63797 opens the same feature. This PR is a smaller implementation of it: no conversion helper and no version guard (see Details).

## Claims

- `json_object` and `json_schema` (with a schema) requests on Mistral models render the schema into `[MODEL_SETTINGS]`. Other formats are dropped, as before.
- `MistralTokenizer.apply_chat_template` forwards its remaining kwargs (`reasoning_effort`, `response_format`, ...) to `MistralCommonBackend`, which forwards them to `ChatCompletionRequest.from_openai`. That function ignores fields it does not know, so tokenizers without these settings render exactly as before.
- `/tokenize` accepts `response_format` for chat requests, so the rendered prompt can be inspected.

## Validation

Rendered with an internal v15 tokenizer whose `model_settings_builder` declares `json_schema`, through `ChatCompletionRequest.build_chat_params` → `MistralRenderer` → `MistralTokenizer`, with `reasoning_effort="high"`:

| `response_format` | `[MODEL_SETTINGS]` |
| --- | --- |
| `json_schema` (strict or not) | `{"json_schema": <schema>, "reasoning_effort": "high"}` |
| `json_object` | `{"json_schema": {"anyOf": [{"type": "object"}, {"type": "array"}]}, "reasoning_effort": "high"}` |
| `text`, `structural_tag`, none | `{"reasoning_effort": "high"}` |

With `mistralai/Mistral-Small-4-119B-2603`, whose tokenizer has no `json_schema` setting, the prompt is unchanged for every format.

```
pytest tests/tokenizers_/test_mistral.py tests/renderers/test_mistral.py  # 66 passed, 2 skipped
```

`tests/entrypoints/serve/tokenize/test_serving_tokenization.py` was not run locally (`orjson` is missing from my environment); it runs in CI.

## Details

- No conversion helper: the OpenAI `response_format` dump (`by_alias=True`) already matches mistral-common's `ResponseFormat`, because `JsonSchema.custom_schema` has the alias `schema`. The renderer only drops formats mistral-common rejects: `structural_tag`, and `json_schema` without a schema.
- No version guard: removing the `self.version >= 15` filter lets mistral-common decide what each tokenizer supports. The tokenizer keeps its explicit transformers arguments and pops them out of `kwargs`, so they are not passed twice.
- Tests replace the pre-v15 omission test with a forwarding test, and add a test that calls the real tokenizer with the renderer's kwargs.

### [P2] Keep schema forwarding compatible with the declared mistral-common minimum

At `4a015ab05125`, `requirements/common.txt` still admits `mistral_common[image]>=1.11.6`. In that real package, `ResponseFormat.type` accepts only `text` and `json_object`, and its nested model forbids the `json_schema` field. This is a known request field with an unsupported value/shape, so `ChatCompletionRequest.from_openai` does **not** drop it as an unknown kwarg. The newly forwarded schema fails validation before encoding; the previous tokenizer path omitted this kwarg.

This reproduces with the official 1.11.6 package, without downloading a model or tokenizer:

```python
from mistral_common.protocol.instruct.request import ChatCompletionRequest

ChatCompletionRequest.from_openai(
    messages=[{"role": "user", "content": "Return JSON"}],
    response_format={
        "type": "json_schema",
        "json_schema": {"name": "answer", "schema": {"type": "object"}, "strict": True},
    },
)
```

It raises two validation errors: `response_format.type` expects `text` or `json_object`, and `response_format.json_schema` is an extra field. Omitting the format or using `json_object` both pass.

I also checked the exact renderer helper, ChatParams, tokenizer methods and Transformers 5.16.1 forwarding method in isolation. With the same new-renderer kwargs, the parent tokenizer reaches the encoding boundary for all three formats; the head reaches it for `text` and `json_object`, while `json_schema` raises the real 1.11.6 constructor error. That check uses AST-isolated source, represents OpenAIBaseModel with Pydantic BaseModel for these valid known fields, and stops at a post-constructor encoding sentinel. It is not a full vLLM/server or real-tokenization test, and establishes no HTTP status or model result.

Could forwarding preserve compatibility with the admitted older package, or could the dependency floor be raised to a version that actually supports this request shape? A regression against the supported minimum would catch the difference between ignoring unknown kwargs and rejecting a known field's unsupported value.
