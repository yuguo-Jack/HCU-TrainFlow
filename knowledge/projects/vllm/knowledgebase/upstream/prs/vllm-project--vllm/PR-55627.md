## Purpose

Second half of the split of this PR: #57539 adds the exact-replay SSD step and its metadata; this PR wires them into the Mamba2 backend. Tracked in #55524.

Under `VLLM_BATCH_INVARIANT=1`, a Mamba2 layer should produce the same bits for a token whether it is computed in prefill, in a chunked-prefill continuation or in decode. Today prefill runs the chunked scan and decode the single-token update, which round differently, so a token's logprob depends on how the scheduler split the sequence. That defeats the purpose of the mode for RL, where a trainer rescores the rollout through prefill.

With this PR, in batch-invariant mode:

- The SSM state is kept in fp32 and the layer state gains three per-sequence buffers with the inputs of the current partial chunk (x, dt, B), through the shared state shape and dtype calculators, so every model built on `MambaMixer2` gets it without per-model changes.
- The Mamba2 attention metadata builder produces the replay metadata for the prefill and decode rows of each step, and the mixer runs the replayed step from #57539 instead of the chunked scan and the single-token update.
- Unsupported settings are rejected at startup: prefix caching on the Mamba2 layers, PP > 1, speculative decoding, micro-batching, KV connectors and the non-Triton mamba backend. Tensor parallelism works; the gated RMSNorm's TP path for a single group reduces per-rank means in fp32, because batch-invariant mode overrides `mean` but not `sum` (#54993 touches the same lines).
- The Mamba2 layers run outside CUDA graphs in this mode; #55905 brings them back.

Default mode is untouched. Costs: each decode step runs the chunked-scan kernels over the partial chunk instead of the single-token update, the per-layer state grows from two tensors to five (about 43 MiB per sequence for a 27-layer, 32-head model at chunk size 256), and decode throughput on small models drops to roughly a tenth. #55905 recovers most of that, and #55895 pins the kernels' tiles so the bits also match across processes.

Not a duplicate: #54993 aligns the scheduler's chunking and replays the generated history through the SSU kernel on recovery, so it gives decode == recompute while decode stays on SSU. This PR gives decode == single-shot prefill.
