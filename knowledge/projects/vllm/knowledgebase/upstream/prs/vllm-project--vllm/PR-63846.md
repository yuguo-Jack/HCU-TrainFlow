# [Bugfix][Spec Decode] Lower max_model_len to the draft's before model config hooks

[Upstream PR](https://github.com/vllm-project/vllm/pull/63846) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #63844. On the V2 model runner, a hybrid Mamba/GDN target with prefix caching off and a drafter whose `max_model_len` is shorter fails config validation with `--mamba-block-size can only be set with --enable-prefix-caching`, a flag the user never set. This moves `_limit_max_model_len_to_draft()` (added in #63251) ahead of `try_verify_and_update_config()`, so the model config hooks see the lowered `max_model_len`.
## Claims

- The config from #63844 builds on the V2 runner: `max_model_len` is lowered to the draft's 1024 (as #63251 intends) and `mamba_block_size` follows it, instead of raising.
- V1 runner behavior is unchanged (`max_model_len` stays 4096).
- No other `tests/config` result changes.

## Details

`VllmConfig.__post_init__` ran `try_verify_and_update_config()` first and `_limit_max_model_len_to_draft()` later. For hybrid models with prefix caching off, the hook in `HybridAttentionMambaModelConfig` sets `cache_config.mamba_block_size = model_config.max_model_len` (4096). The draft limit then lowers `max_model_len` to 1024, and `validate_mamba_block_size` reads `mamba_block_size != max_model_len` as "the user set `--mamba-block-size`" and raises. Any other hook deriving a value from `max_model_len` also saw the stale value.

Running the draft limit before the hooks fixes this at the source instead of patching `mamba_block_size` afterwards. Its inputs (`use_v2_model_runner`, the draft config, `draft_shares_target_positions()`) are not changed by the model config hooks. The only hook that writes `max_model_len` (EmbeddingGemma2) caps it at 8192, which still composes with a lower draft limit. The check stays after the submodel-config early return, as before.

**Limitation / possible follow-up.** The root fragility is in `validate_mamba_block_size`: it infers "the user passed `--mamba-block-size`" from `mamba_block_size != max_model_len`, so any change to either value after the hybrid hook ran makes it fire on a value the hook set itself. #52045 works around the same validator firing from a different trigger (CPU MLA disabling prefix caching after the hook ran). A sturdier fix would record whether `mamba_block_size` was user-set and validate only that, but it touches how `CacheConfig` tracks explicit arguments, so I kept this PR to the ordering fix. Happy to do that as a separate PR if maintainers prefer it.
