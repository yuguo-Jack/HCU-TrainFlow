# [Kernel] EFC-style epilogues for the CuTe DSL Lamport TP all-reduce

[Upstream PR](https://github.com/vllm-project/vllm/pull/59561) · state: open · merged: False

## Original PR description



## Overview

Generalizes the consumer kernel of the CuTe DSL Lamport TP all-reduce (FlashInfer's `kernel_ll`, vendored for DSV4.1 in #58586) into one kernel whose epilogue is a Python function, modeled on CUTLASS's [Blackwell EFC example](https://github.com/NVIDIA/cutlass/tree/main/examples/python/CuTeDSL/cute/blackwell/efc). Draft for design feedback: no serving path calls it yet.

## Claims

- An all-reduce epilogue is now a short Python function, not a kernel template. `epilogues.py` has residual RMSNorm, Gemma RMSNorm, DSV4.1 mHC + RMSNorm, and RMSNorm or mHC followed by NVFP4, static FP8 or per-token-group FP8 (FP32 or UE8M0 scales).
- The generated kernels are bit-identical to the hand-written ones they generalize, and as fast:
  - residual RMSNorm and Gemma RMSNorm vs FlashInfer's `_LamportResidualRMSNormDeviceKernel`;
  - mHC + RMSNorm vs `_LamportMHCDeviceKernel` from #58586.
- Fused quant outputs are bit-identical to `scaled_fp4_quant`, `scaled_fp8_quant` and `per_token_group_quant_fp8`. Fusing saves 1.0–2.3 µs per boundary vs the all-reduce followed by the separate quant kernel, at M = 1–16 (TP4 GB300, hidden 5120).
- All epilogues share one Lamport mailbox, so each one works after both the plain publish and the MoE finalize publish.

## Details

**Writing an epilogue.** An epilogue is `fn(cfg, *params)`. Each parameter's annotation says how the kernel indexes that tensor:

| kind | tensor | interface |
|---|---|---|
| `Row` | [M, hidden]; reads BF16, writes BF16 / FP8 / packed E2M1 | `.load()`, `.store(v)` |
| `Streams` | [M, S, hidden] | `len(x)`, `x[s]` is a `Row` |
| `Weight` | [hidden] | `.load()` |
| `PerToken` | [M, *shape] FP32 | `x[i, ...]` is a per-token scalar |
| `DeviceScalar` / `Scalar` | one-element FP32 tensor / host float | `.load()` / the value |
| `GroupScale` subclasses (`NVFP4Scale`, `Group128Scale`) | one value per token and group; row-major or the NVFP4 128×4 layout | `.store(v)` |

`cfg` provides `accum()` (the FP32 cross-rank sum), `round(x, dtype)`, `row_sum`, `group_max`, `rsqrt`, `rcp_approx`, `where`, `maximum`/`minimum`/`clamp`, `abs` and `ue8m0_ceil`. For example:

```python
def mhc_rmsnorm_nvfp4(cfg, residual: Streams, post: PerToken, comb: PerToken, pre: PerToken,
                      weight: Weight, eps: Scalar, global_scale: DeviceScalar,
                      residual_out: Streams, q: Row, sf: NVFP4Scale):
    prenorm = mhc_post_pre(cfg, residual, post, comb, pre, residual_out)
    y = cfg.round(rms_norm(cfg, prenorm, weight, eps), torch.bfloat16)
    nvfp4_quant(cfg, y, global_scale, q, sf)
```

**Three phases.** As in EFC, the function runs three ways:
- an analysis pass with dummy values, which records which tensors and hc streams are read and written and counts the row reductions to size shared memory;
- device code generation, on each thread's 8-element fragments of the token row;
- a torch reference on [M, hidden] tensors.

**How this differs from the GEMM EFC.**
- One CTA cluster owns a whole token row, so an epilogue can reduce over the row (block plus DSMEM cluster sum, reusing FlashInfer's `_group_leader_block_sum`). It can also reduce over aligned groups of 16–256 elements with warp shuffles.
- Every load is hoisted ahead of the consumer's `griddepcontrol.wait`, as the hand-written kernels do. This is safe because the publish kernel waits on its own predecessor before it triggers the consumer.
- Rounding is explicit (`cfg.round`), so an epilogue states where the unfused path returns BF16. That is what lets the fused results match the unfused ops bit for bit.

**Duplicate check.**
- #59258 wires FlashInfer's fixed-pattern CuTe AR + RMSNorm into the compile pass, with static FP8 coming from flashinfer-ai/flashinfer#5533. That PR adds graph-level dispatch; this one generates epilogues at the kernel level, covering patterns FlashInfer has no template for (mHC, NVFP4, per-group FP8, Gemma). They are complementary: that backend could dispatch to these epilogues.
- #51942 and #42597 use FlashInfer's fixed TRT-LLM fused all-reduce patterns.
- #58586 provides the protocol and the publish kernels reused here.

**Size.** About 1.9k lines (high complexity). The trade is that each new fusion costs about 10 lines of epilogue instead of a new consumer kernel; #58586's consumer alone is about 330 lines.

**Open before un-drafting.**
- The publish kernels and PTX primitives are imported from `vllm.models.deepseek_v41.nvidia.ops.cute_dsl`, which pulls in the DSV4.1 model package. Move them here and have DSV4.1 import them; `AllReduceMHC` can then become `ar.bind(mhc_rmsnorm)`, deleting `_LamportMHCDeviceKernel`.
- Current scope: one rank lane, BF16 transport, hidden a multiple of 8, M up to the mailbox capacity (the low-latency regime), single-node NVLink multicast.
- Scale layouts are row-major or NVFP4 128×4; DeepGEMM's MN-major FP8 scale layout is not done.
- Static and group FP8 cost 0.35–0.6 µs more than plain RMSNorm. The cost is an IEEE division per element, needed to match vLLM's `x / scale` bit for bit; multiplying by a reciprocal would be cheaper but not bit-exact.
- No model wiring yet: the follow-up is to call these from #59258's backend or from the model files, then run evals.
