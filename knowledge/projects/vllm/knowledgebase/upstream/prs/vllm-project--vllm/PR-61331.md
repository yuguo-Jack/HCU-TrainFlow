# [Perf] Use CUTLASS for small-M per-tensor FP8 GEMMs on SM12x

[Upstream PR](https://github.com/vllm-project/vllm/pull/61331) · state: closed · merged: False

## Original PR description

## Overview

On SM12x (RTX 50xx, RTX PRO 6000, GB10), per-tensor FP8 linears run through `FlashInferFP8ScaledMMLinearKernel` → FlashInfer `bmm_fp8`. For most decode-sized GEMMs, `bmm_fp8` picks a cuBLASLt split-K kernel built for Ada (`sm89_xmma…32x64x64`) that needs a memset before the GEMM. This PR sends GEMMs with M ≤ 32 to vLLM's own CUTLASS sm120 `cutlass_scaled_mm`, inside the existing `vllm::bmm_fp8` op. Larger M still uses `bmm_fp8`.

Related: #59770, #61007 (GB10 slowdown and hang in the `bmm_fp8` path; not measured here), #48210 / #57209 (pin `bmm_fp8` to cuBLAS on sm_12x; complementary), flashinfer-ai/flashinfer#6312.

## Claims

- Decode TPOT on RTX 5090 drops 4–11 % on three NVIDIA FP8/NVFP4 checkpoints (table below; across all runs the range is −3.3 to −10.7 %).
- Mean NLL changes by +0.02 to +0.09 %. This is below a 0.3 % threshold fixed before the runs and is not statistically significant. It is not an equivalence proof.
- The new branch is enabled only when the SM12x and kernel-support conditions in the gate hold. Everything else keeps the current path, including GEMMs with M > 32 on SM12x.

<details><summary>Accuracy</summary>

- Setup: `prompt_logprobs` NLL of 96 wikitext-2 documents (63 932 tokens). The server ran with `--max-num-batched-tokens 16 --no-enable-prefix-caching`, so every GEMM has M ≤ 16.
- Baseline: two cuBLAS server launches, which agree to ≤ 1e-4 nats/token per document.
- Result: four CUTLASS runs have mean NLL +0.024 / +0.058 / +0.058 / +0.085 % above the baseline mean. A test paired by document (n = 96) gives t ≤ 1.3.
- With `--max-num-batched-tokens 96` (M ≤ 96, two launches per arm), the difference is +0.055 %.
- Decision rule, written before the runs: CUTLASS is worse if both CUTLASS launches are above both baseline launches, the relative difference is above max(0.3 %, baseline spread), and the paired t is above 3. Here the first condition holds, and the other two do not. This is a difference-detection test on one model and one text set, not an equivalence test.
- With 16-token chunks, per-document NLL differs between CUTLASS launches by up to 0.04 nats/token. With 96-token chunks, two CUTLASS launches are bit-identical. The cause is not identified.
</details>

## Details

- **Why M ≤ 32.** In the sweep on Qwen3.8 shapes, 32 is the largest M up to which CUTLASS beats cuBLASLt by more than 3 % (full FP8 GEMM time) at every tested size, both with FlashInfer's autotuner and with cuBLASLt's default algorithms. At 48–64 it only ties with the default algorithms. The CUTLASS kernel itself is not always faster at M = 32: with the autotuner on, the two kernels are within 1.6 %, and the gain comes from the removed memsets. flashinfer-ai/flashinfer#6148 changes how tuned cuBLASLt tactics are replayed, so the threshold is chosen to hold in both modes rather than to capture the 72–96 gains seen under today's autotuner. Other models' shapes were checked only at decode (M = 1).
- **Design.**
  - The branch lives inside `vllm::bmm_fp8` (new `cutlass_max_m` argument, default 0), so each GEMM is still one custom op. An earlier version wrapped `bmm_fp8` in a second op and cost about 25 µs of host time per GEMM at eager prefill.
  - The op picks the branch from the concrete M it receives. Under CUDA graphs that M is the padded capture size, so each captured size records its own kernel and replays it.
- **Gating** (`_use_sm12x_small_m_dispatch`, covered by the selection test):
  - SM12x family (includes sm_121);
  - bf16/fp16 output;
  - N and K multiples of 16;
  - `cutlass_fp8_supported()`;
  - not `VLLM_BATCH_INVARIANT`, because picking the kernel by M would make results depend on batch size.

  Otherwise `cutlass_max_m` stays 0 and the op runs `bmm_fp8` unchanged. The op asserts the call is unbatched. To opt out, select another linear kernel with `--kernel-config '{"linear_backend": ...}'`.
- **Scope.** Per-tensor FP8 checkpoints that select `FlashInferFP8ScaledMMLinearKernel` on SM12x: ModelOpt FP8 (including mixed NVFP4), `fp8` static per-tensor, and compressed-tensors W8A8 static per-tensor. Block-FP8 and per-token paths are untouched.
- **Limitations.**
  - Measured on one RTX 5090 (600 W) with torch 2.13 cu130 and FlashInfer 0.7.0.post1. The host is CPU-bound at prefill, so prefill numbers are GPU time, not TTFT.
  - Performance on other SM12x GPUs (GB10, RTX PRO 6000) is not verified. flashinfer-ai/flashinfer#6312 reports kernel parity at M = 1 on RTX PRO 6000, so the gain there may come only from the removed memsets.
  - Batch decode at 17–32 sequences is covered by the M = 32 sweep point and the tests, not by an end-to-end run (the server used `--max-num-seqs 16`).
  - Bias is still added outside the op, as before.
- **Why not a duplicate.**
  - #48210 / #57209 choose the `bmm_fp8` backend. This PR changes which kernel runs for M ≤ 32 and keeps their backend for larger M.
  - #45912 (disable FlashInfer on sm_12x) and #53400 (prefer CUTLASS on SM100 for every M) were closed. This PR dispatches by M because CUTLASS loses at large M.
