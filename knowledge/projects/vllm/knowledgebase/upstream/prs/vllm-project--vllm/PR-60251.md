# [Frontend] Report stop_reason on /inference/v1/generate and pass it through derender

[Upstream PR](https://github.com/vllm-project/vllm/pull/60251) · state: closed · merged: True

## Original PR description

## Overview

Expose the engine's `stop_reason` (matched stop string or stop token id) on `/inference/v1/generate` responses in both frontends, and pass it through the derender endpoints so they match `/v1/chat/completions` and `/v1/completions`. Continues #47313 (@hhk7734, co-authored) and closes the `stop_reason` gap in #57052.

## Claims

- `GenerateChoiceBase` / `GenerateStreamChoiceBase` gain `stop_reason: int | str | None`, so every `output_mode` (tokens and text, batch and streaming) carries it. Python fills it from `output.stop_reason`.
- The Rust generate route reports the same field from `FinishReason::as_stop_reason` on streamed and collected outputs.
- `/v1/chat/completions/derender` and `/v1/completions/derender` (batch and streaming, plain and parser paths) carry the generate value through instead of always returning `null`.
- No wire change for existing fields; `stop_reason` is additive with a `None` default.

Not run: a live render → generate → derender A/B against a coupled server. @Yunzez's comparison on #57052 is the reference for that.

## Details

- **Why a new PR.** #47313 was opened in July against the pre-`output_mode` protocol and its author asked for it to be continued (https://github.com/vllm-project/vllm/pull/47313#issuecomment-5924760857). The original commit is cherry-picked with authorship intact; the rebase moved the field onto the shared base classes introduced by #58588, which is why text mode gets it too.
- **Why derender needs it.** Derender builds its choices from the generate response and had no source for `stop_reason`, so it was `null` on every response (#57052, confirmed by an independent fuzzing run). With the field on the wire, derender passes it through in all five choice constructions. The batch stop pass in #59510 can then read it instead of re-deriving the match; whichever of the two lands second rebases.
- **Streaming nulls.** The Python stream chunk emits `"stop_reason": null` on non-final chunks, the same way it already emits `finish_reason: null`. The Rust stream struct is `skip_serializing_none` and omits it, matching how it treats its other optional fields.
- **Related, not duplicated.** #51904 adds stop-string *support* to the Rust generate route; this PR only surfaces the engine's `stop_reason` and doesn't change stop handling.

Duplicate-work check: searched open PRs for `stop_reason generate`, `47313 in:body`, `57052 in:body`; the only hits are #47313 (superseded by this PR with its author's agreement) and #59510 (consumer of this field, not a producer).
