# [Core] SubGPU pipelining: run micro-batches on green-context SM pools (Model Runner V2)

[Upstream PR](https://github.com/vllm-project/vllm/pull/65637) · state: open · merged: False

## Original PR description

## Overview

Add SubGPU pipelining, an experimental, opt-in decode mode (`--subgpu-pipelining`, Model Runner V2) that overlaps the two halves of
a transformer layer on one GPU: the attention of one micro-batch runs on one CUDA green-context SM pool while the rest of the layer
of the other micro-batch runs on the complementary pool, swapping at every layer. It reuses the V2 runner's micro-batching
(`UBatchRunner`, the DBO runtime) and moves the hand-off points from the all-to-all to the attention boundary.

## Claims

- On one B200 standing in for one rank of an EP-64 GPT-OSS-120B deployment (36 layers, fp8 KV cache, MXFP4 experts, 64 sequences
  per GPU, FULL CUDA graphs, emulated dispatch / combine), the decode step is 5.5% shorter than the temporal step at 32K context and
  17% shorter at 64K; against the same micro-batching on the whole GPU (DBO-style, no pools) 18% and 29%. The V1-runner
  prototype of the same change measured -8..-10% / -19..-21% against temporal and -18..-20% / -29..-31% against DBO-style.
- With the mode off nothing changes: the micro-batching code paths are the existing ones and the temporal step of the patched
  build equals the unpatched build's within node-to-node variation.
- Size: about 330 added lines under `vllm/` (143 of them the new green-context pool module), the rest in `UBatchRunner`, the
  single-rank dispatch decision, the config / CLI options and the gpt-oss stage placement; plus two test files and a section in
  `docs/design/dbo.md`.

## Validation

- Unit tests: `pytest tests/test_config.py tests/v1/worker/test_subgpu_pipelining.py -k subgpu` (config validation, two
  micro-batches, V2 runner selection, the single-rank dispatch decision against a real `CudaGraphManager`, the micro-batches
  running on the pools with a two-stage toy model, the DBO baseline schedule, single-rank forward contexts without DP metadata).
  The pool tests need a GPU with green-context support and `cuda-bindings`; they skip only on `CUDA_ERROR_NOT_SUPPORTED`.
- Decode benchmark, graph replay, ms per step (mean of 200 replays after 8 warm-up steps), GPT-OSS-120B as above, nightly image of
  the base commit, Model Runner V2, two-CTA fp8 decode attention kernel (see the kernel dependency under Details):

  | kv | temporal | DBO-style (no pools) | SubGPU 64 / 84 SMs | vs temporal | vs DBO-style |
  |---|---|---|---|---|---|
  | 32768 | 12.64 | 14.52 | 11.95 | -5.5% | -17.7% |
  | 65536 | 18.62 | 21.64 | 15.40 | -17.3% | -28.8% |

  The V1-runner prototype on vLLM 0.27.1 (same model and harness, another node) measured 12.76 / 14.31 / 11.50 (-9.9% / -19.6%) at kv
  32768 and 18.94 / 21.58 / 14.90 (-21.3% / -31.0%) at kv 65536: temporal and DBO-style agree within node spread, the SubGPU step
  is about 0.5 ms slower here at both context lengths (a fixed per-step amount, not yet attributed).
  With the shipped one-CTA decode kernel the same build measures +5.5% / +8.1% against temporal (the kernel dependency below).
- Not validated: accuracy with real weights (the kernels are unchanged and only their scheduling differs, so outputs should be
  identical; an end-to-end check is still to do); DP > 1 with pools (the DP handshake path is unchanged and builds the runner, but
  no multi-rank run was made); models other than gpt-oss.

## Details

**Motivation.** The two halves of a long-context decode step bottleneck on different resources: dense attention streams the KV
cache (HBM-bound, tensor cores idle), the rest of the layer (projections, norms, routing, MoE GEMMs, dispatch / combine) is bound by
tensor throughput or launch latency (HBM idle). Run back to back on all SMs the GPU uses one resource at a time.

**Design.**
- Runtime: `UBatchRunner` (the V2 micro-batching) is reused unchanged in its threading, hand-off and capture protocol. Under the
  `subgpu` schedule it owns a `GreenContextPools` object: the attention pool's stream is the micro-batches' compute stream, their
  capture stream and their replay stream; the rest pool has one stream per micro-batch, passed to `make_ubatch_contexts` as that
  micro-batch's comm stream, so one micro-batch's all-to-all does not block the other's GEMMs. DBO's SM reservation
  (`create_sm_control_context`) is replaced by a no-op: the pools partition the SMs.
- Pools: `vllm/v1/worker/gpu/green_context_pools.py` splits one container green context into the attention pool (default 64 SMs)
  and the rest pool (84) with the `cuda.bindings` driver API; the pools must be disjoint, which `torch.cuda.green_contexts` in the
  pinned torch cannot express (`GreenContext(num_sms)` contexts may share SMs; `SMPartition.split` is only in later releases).
- Placement: models call `dbo_subgpu_ensure_attn()` / `dbo_subgpu_ensure_rest()` (idempotent, no-ops outside a SubGPU
  micro-batch and under the `dbo` baseline schedule). gpt-oss runs only its full-attention kernels on the attention pool; QKV, RoPE,
  the KV write, o_proj, the sliding-window layers and the MoE stay on the rest pool, which measured better than moving the whole
  attention block. Micro-batches start on the attention pool and end on it, the stream the graph is captured on.
- CUDA graphs: the FULL graph of a micro-batched batch is captured on the attention pool's stream (`UBatchRunner.capture_stream`)
  and replayed on it (`run_fullgraph` wraps the replay in `UBatchRunner.pool_stream()`, which orders the caller's stream before
  and after). Capturing green-context streams needs CUDA 13.4 or later.
- Single rank: DBO is only built with more than one DP rank because the micro-batching decision is a DP handshake. With
  `--subgpu-pipelining` the runner is built on one rank too, and `dispatch_cg_and_sync_dp` decides locally: a batch above the DBO
  token thresholds takes the micro-batched FULL graph when one is captured, otherwise it runs whole (an eager two-pool step has
  nothing to gain, so the single-rank path never runs eager micro-batches). The micro-batched graph candidates come from the
  existing `_maybe_ubatch_twin`. Single-rank micro-batches carry no DP metadata in their forward contexts, like a whole batch's.
- Runner selection: micro-batching currently selects Model Runner V1 unless `VLLM_USE_V2_MODEL_RUNNER` is set (DBO on V2 is still
  gated). This mode exists only in V2, so `--subgpu-pipelining` is the opt-in: the gate is skipped for it and Model Runner V1 lists
  it as unsupported. The DBO unsupported-feature texts name "SubGPU pipelining" in that case.
- Places that must know that two micro-batches are live checked `enable_dbo`; they now check `use_ubatching`, which also covers
  `ubatch_size > 1`: the workspace manager's per-micro-batch slots (`gpu_worker.py`), the shared-expert output buffers of
  `MoERunner`, and the Qwen4Exp PLE/QSA and Step5 MegaMoE guards. The no-EP modular prepare/finalize declares `supports_dbo()`:
  it has no communication to hand off, so the modular kernel's DBO assert does not apply to it.
- Baseline: `--subgpu-schedule dbo` runs the same micro-batching on the whole GPU without pools or stage switches.

**Trade-offs and limitations.**
- Kernel dependency: the gain needs a decode attention kernel that saturates HBM from a partial pool. The shipped trtllm-gen fp8
  decode kernel runs one CTA per SM and needs about 140 SMs to saturate HBM; a two-CTAs-per-SM export of the same kernel reaches
  it from 76-80 SMs. The measurements overlay that export on FlashInfer's cubins; it has to land in FlashInfer (selected by the
  pool's SM count) before this mode helps out of the box. With the shipped kernel the mode is slower than temporal (measured: +5%
  / +8% at kv 32K / 64K).
- Regime: the gain is a long-context, dense-attention effect. At 64 sequences per GPU it loses 6-8% at kv <= 8K; a per-step on /
  off policy is not implemented. On sparse-attention MoE models whose decode step is SM-bound rather than HBM-bound the mode does
  not help (measured on a 128-expert sparse-attention model: no bandwidth phase to pair against).
- Communication: real expert-parallel dispatch / combine (DeepEP) was emulated, not run.
- Scope: Model Runner V2 only (the V1 runner is deprecated); DP > 1 with pools and multi-node runs are untested; CUDA only
  (`cuda-bindings` required; the pool module raises on other platforms).

**Not a duplicate.** No open PR or RFC uses CUDA green contexts to split SMs between attention and the rest of the layer (GitHub
search for "green context" and "SM partition", 2026-11). `vllm/distributed/localization.py` uses green contexts for
locality-domain MoE on multi-domain GPUs, a different purpose. DBO overlaps communication with compute on the whole GPU; this
reuses its runtime for a different overlap.
