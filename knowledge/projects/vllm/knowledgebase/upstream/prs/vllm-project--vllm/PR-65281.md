# [Model Loader] Direct reload: lay the checkpoint out where a relocated weight now starts

[Upstream PR](https://github.com/vllm-project/vllm/pull/65281) · state: closed · merged: True

## Original PR description

## Purpose

With `VLLM_RELOAD_MODE=direct`, a weight that post-load processing moves into another storage at an offset is reloaded into the wrong place.

`record_checkpoint_layout` records each weight's `storage_offset` before post-load processing. On a reload, `begin_direct_reload` views the weight back to that layout in the storage the weight lives in **now**. If post-load processing moved the weight into a different storage (e.g. `set_` into a fused buffer), the recorded offset belongs to the old storage. The new checkpoint is then written over the neighbouring weight, and the moved weight itself keeps its old bytes.

Example: on ROCm, `prepare_compressor_gemm_fusion` in DeepSeek-V4 does `indexer_weight.set_(fused_weight[main_size:])`. On a reload, the indexer compressor weight was written over the main compressor rows. DeepSeek-V4-Pro GSM8K after reloading the original weights dropped from 0.96 to 0.885.

## Fix

Also record the storage's `data_ptr`. If the weight's storage has changed by reload time, use its current `storage_offset()` instead of the recorded one. Only `reload/direct.py` changes (+4/−1).

## Test Plan

- New `test_reload_into_weight_moved_to_an_offset`. The toy model's post-load processing moves `proj.weight` into a new buffer at an offset. A reload must match a fresh cold start and keep every address.
- `tests/model_executor/model_loader/test_direct_reload.py` on GB300, run with this PR and with main's `direct.py`.
- DeepSeek-V4-Pro (heterogeneous, TP8, CUDA graphs, compressor GEMM fusion on) on MI355X with `VLLM_RELOAD_MODE=direct`: cold GSM8K (400, 5-shot), then reload original → perturbed → original, plus a `data_ptr` report. This also needs a separate fix for a `KeyError` in the DeepSeek-V4 ROCm preshuffle scales (stacked on #64692).
