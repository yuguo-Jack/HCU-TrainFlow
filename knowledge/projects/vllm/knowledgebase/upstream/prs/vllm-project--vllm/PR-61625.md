# [Perf][Scheduler] Remove redundant pad_spec_decode guard (fix #55798)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61625) · state: open · merged: False

## Original PR description

## Background

Fixes #55798.

The `pad_spec_decode` condition in the Scheduler had an overly conservative guard clause.

## Problem

The original condition (from the issue report) was:
```python
and (scheduled_running_reqs and not prefill_scheduled)
```

This prevented spec decode padding for the **very first decode request** — when no other requests are running yet, `scheduled_running_reqs` is empty, so the guard evaluates to False and padding is skipped.

The condition was later relaxed to `scheduled_running_reqs or num_computed_tokens > 0`, which partially addressed the issue — but as this PR shows, the entire guard is actually **dead logic**.

## Analysis

When both `not prefill_scheduled` and `num_new_tokens == 1` hold:
- This is a **pure decode batch** (no prefill requests are scheduled)
- For any decode request, prefill must have already completed
- Therefore `num_computed_tokens >= num_prompt_tokens > 0` is **always true**

The entire clause `scheduled_running_reqs or num_computed_tokens > 0` can never evaluate to False when reached. It is redundant defensive code.

## Solution

Removed the redundant guard. The remaining conditions are sufficient:

```python
if (
    (self.num_spec_tokens > 0 and self.dynamic_sd_lookup is None)
    and self.num_sampled_tokens_per_step > 0
    and num_new_tokens == 1
    and not prefill_scheduled
):
```

## Why this matters

- Simplifies the condition — makes the intent clearer
- The first decode request in a batch can now consistently benefit from spec decode padding + CUDA graph mode
- This aligns with the original intent described in #55798

## Testing
- Python syntax verified on the modified file
- This is a pure logic simplification — the removed guard was always True when reached
- No behavior change for any existing code path
