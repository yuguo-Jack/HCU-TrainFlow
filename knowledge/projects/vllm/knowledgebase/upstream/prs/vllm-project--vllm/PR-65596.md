# [Model][Perf] Gemma 4: torch.compile for the native vision tower

## Overview

Make `compile_mm_encoder` apply to Gemma 4's native vision tower (#65431) by compiling each `Gemma4VisionEncoderLayer`, as Qwen3-VL does for its vision blocks.

**Stacked on #65431 and #65591** (H100 fixes, which this PR's tests need on NVIDIA). Only the last commit (`[Model][Perf] Gemma 4: torch.compile for the native vision tower`) is new; please review that commit. I will rebase once they land.

## Claims

- With `compile_mm_encoder`, the Gemma 4 31B vision tower runs 35–63% faster than eager on H100 (bf16, FLASH_ATTN), across 1–4 images and 70–1120 soft tokens per image.
- Served end to end, median TTFT of image requests drops 10–20% (`vllm bench serve`, 1–4 images per request, 280 or 1120 soft tokens per image).
- Inductor fuses the tower's unfused elementwise ops (RMSNorm, GELU, residual adds): 2,234 → 587 kernels and 2.4–2.5× less DRAM traffic per forward (ncu).
- Compiled outputs match transformers within the same tolerance as eager (tower test parametrized over compile).

**Tower latency.** `google/gemma-4-31B-it` vision config (27 layers, hidden 1152, head_dim 72), random bf16 weights, FLASH_ATTN. Median of 20 runs after 5 warmup:

|---|---|---|---|
| 1 × 70 | 30.3 ms | 12.1 ms | -60% |
| 1 × 280 | 29.7 ms | 11.1 ms | -63% |
| 4 × 280 | 74.0 ms | 37.9 ms | -49% |
| 1 × 1120 | 92.8 ms | 59.0 ms | -36% |
| 4 × 1120 | 353.9 ms | 228.9 ms | -35% |

**Where the time goes (ncu).** One tower forward, same setup, `ncu --metrics gpu__time_duration,dram__bytes_{read,write},sm__pipe_tensor_op_hmma_cycles_active`. ncu serializes kernels at base clocks, so absolute times are higher than above; compare the ratios.

| kernel class | kernels | 1 × 280 GPU ms | 1 × 280 DRAM GB | 4 × 1120 GPU ms | 4 × 1120 DRAM GB |
|---|---|---|---|---|---|
| eager: elementwise/reduce/copy | 1,882 | 16.2 | 14.2 | 182.5 | 374.3 |
| compiled: fused Triton (+ leftover aten) | 235 | 2.8 | 3.8 | 39.9 | 85.1 |
| GEMM (both) | 190 | 5.3 | 3.1 | 69.1 | 76.6 |
| FA3 varlen attention (both) | 54 | 2.9 | 0.5 | 116.0 | 12.5 |
| RoPE (both) | 108 | 0.7 | 0.6 | 9.9 | 15.1 |
| **total, eager → compiled** | 2,234 → 587 | 25.2 → 11.8 | 18.4 → 7.9 | 377.5 → 235.2 | 478.5 → 189.5 |

Compile leaves GEMM, attention and RoPE unchanged and replaces ~70 elementwise kernels per layer with 8 fused ones. At 1 × 280, torch.profiler at normal clocks shows 18.1 ms of kernels in a 29.7 ms eager forward; the rest is launch gaps. Compile removes both (9.8 ms of kernels, 11.1 ms wall). At 4 × 1120 the tower is GPU-bound and the gain is all kernel time. After compile, FA3 attention (head_dim 72) is half the large-input time.

## Details

- `@support_torch_compile(enable_if=should_torch_compile_mm_encoder)` goes on `Gemma4VisionEncoderLayer` rather than `Gemma4VisionModel`. The model's forward takes `encoder_metadata: Mapping`, which cannot be marked dynamic, and the packed-sequence metadata (`cu_seqlens`, `max_seqlen`, RoPE positions) is built on the host anyway. Keeping it outside the compiled region avoids graph breaks.
- `compile_mm_encoder`'s docstring now lists Gemma 4.
- **Compile cache:** in a real engine, the cache key includes the full `hf_config` (via `ModelConfig.compute_hash`) and, when `compile_mm_encoder` is set, `MultiModalConfig.compute_hash()`, which includes `mm_encoder_attn_backend`. Different towers or ViT backends therefore get different artifacts. The unit test builds the tower without a model config, so it uses `disable_vllm_compile_cache`.

**Not a duplicate:** no open PR compiles the Gemma 4 vision tower. #65431 adds the native tower that this PR compiles.
