# [Bugfix][KV Offload] Drain unfetched P2P stores before cache reset

[Upstream PR](https://github.com/vllm-project/vllm/pull/63988) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fix cache reset on P2P prefill nodes when store jobs are waiting for a decoder to fetch their KV blocks.

Fixes #63948.

## Claims

- Queued stores report failure and release their primary-tier pins during reset.
- Late fetches fail promptly without reading released slots or leaving stale session bindings.
- Active transfers keep their pins until completion, and fresh symmetric lookup rounds remain usable after reset.

## Validation

Tested on WSL Ubuntu 24.04 with Python 3.12, PyTorch 2.14.0+cu132, NIXL 1.5.1/UCX, and an RTX 3050 8 GB.

The OPT-125m test waits for an active cascade with an absent decoder, calls `LLM.reset_prefix_cache(reset_connector=True)`, and checks that the next request has zero cached tokens and identical greedy output. Unit tests cover queued stores, mid-drain fetches, symmetric lookup rounds, active transfer pins, and abort acknowledgements. Pre-commit checks pass for the changed files.

Without the fix, the issue's producer-reset reproducer fails at `assert not self._jobs` in `TieringOffloadingManager.reset_cache()`; with the fix, both unbound and session-bound stores drain successfully, as confirmed in the issue author's PR feedback.

## Details

A prefill node can finish storing KV before its decoder sends a fetch. These jobs hold primary-tier slots but are not counted as active transfers, so waiting only for transfers leaves jobs behind when the parent resets its cache.

Drain fails unbound stores through the existing expiry path and withdraws queued session supply once. Fetches received during polling are rejected without binding their request IDs. In-flight writes retain their pins until the transport reports completion.

Withdrawn symmetric lookup rounds retain enough state to reject a late fetch without invalidating a fresh round under the same request ID. Aborted rounds use the existing acknowledgement path to avoid duplicate terminal messages.

This addresses producer stores waiting for decoder demand. Related #61667 covers consumer write quarantine. No duplicate fix was found when opening this PR. AI assistance was used for review, and validation.

- liranschour · comment · 2026-10-29T10:14:56Z · [source](https://github.com/vllm-project/vllm/pull/63988#discussion_r4411092358)

File: `vllm/v1/kv_offload/tiering/p2p/manager.py` · line None

**A fetch that arrives mid-drain gets failed but stays half-bound.** `drain_stores()` runs on every pass of the loop, and `_poll_once()` runs right after it. If a decoder `FetchMsg` for a new id X comes in while an in-flight write keeps the loop running, `_poll_once` binds X to the session. On the next pass, `drain_stores` finalizes X's demand-only round as failed (inflight == 0). X is still in `_kv_to_session`, though: the clear on L669 happened before the loop. After the reset, the prefiller's `submit_store` for X goes through the bound fast path into a fresh round with `demand_received=False`. The blocks then sit in `available` and hold primary slots until `_STORE_TIMEOUT_S`.

Could the withdrawal happen once, before the loop, with the late fetch rejected through `_reaped_stores` (or with re-binding blocked) for the length of the drain?

- liranschour · comment · 2026-10-29T10:14:56Z · [source](https://github.com/vllm-project/vllm/pull/63988#discussion_r4411092367)

File: `vllm/v1/kv_offload/tiering/p2p/session/server.py` · line None

**Symmetric (lookup-supplied) rounds can turn into a 30 s stall.** For a round whose supply came from a `LookupResp` HIT and whose `FetchMsg` hasn't arrived yet, this finalizes the round. No `TransferDoneMsg` goes out, because `_finalize_outbound` only sends when `req.demand_received`. The later `FetchMsg` then creates a new round without `lookup_supplied` and parks its demand PD-style. That id was never in `_kv_to_session`, so it isn't in `_reaped_stores` either, and the consumer waits out its 30 s load timeout instead of failing in one round trip.

Also, `_finalize_outbound` defaults to `send_done=True`, while `_finalize_cancelled` (L985) passes `send_done=(kv_request_id, round_key) not in self._pending_aborts`. When an abort for this round is parked, the consumer gets a `TransferDoneMsg(success=False)` here and then an `AbortAckMsg` from `drain_pending_aborts`, i.e. two terminal messages for one round. Should this follow the same `_pending_aborts` rule?

- liranschour · comment · 2026-10-29T10:14:56Z · [source](https://github.com/vllm-project/vllm/pull/63988#discussion_r4411092373)

File: `vllm/v1/kv_offload/tiering/p2p/manager.py` · line None

Every bound id gets marked reaped, symmetric multi-round ids included. For `_REAPED_ID_RETENTION_S` after any reset, a later round's `FetchMsg` for such an id hits the `_reaped_stores` check in `_poll_once` and is rejected via `finish_request`, even when a post-reset `LookupMsg` HIT just pinned fresh blocks for it. The consumer then recomputes KV the producer actually holds.

If that's intentional, a comment would help. Otherwise, could this be limited to ids that actually had rounds withdrawn?

- liranschour · comment · 2026-10-29T10:14:56Z · [source](https://github.com/vllm-project/vllm/pull/63988#discussion_r4411092380)

This is the consumer-side mirror of what this PR fixes for the producer, so it may be worth a follow-up issue.
