# [Core] Add cache-aware admission ordering

[Upstream PR](https://github.com/vllm-project/vllm/pull/54625) · state: closed · merged: True

## Original PR description

## Purpose

Within a bounded look-ahead window over the waiting queue, admit requests whose prefix is
already resident in the KV cache ahead of requests that would have to compute theirs.

The problem is an interaction between strict FCFS admission and prefix caching: a cold
request admitted first allocates blocks, and under pressure that allocation evicts blocks
which a request further back in the queue still needs. The eviction turns a would-be cache
hit into recomputation, and the deeper the shared prefix, the more expensive the loss.
Looking a bounded distance ahead lets the scheduler admit the resident request first, so
the cold request's allocation no longer destroys reuse that was about to be collected.

Two new scheduler options, both off by default:

| Flag | Default | Meaning |
| --- | --- | --- |
| `--cache-aware-admission-window N` | 0 | Look-ahead depth over the waiting queue; 0 admits strictly in arrival order |
| `--cache-aware-admission-threshold F` | 0.0 | KV cache usage below which the window is not applied |

Deliberate limits on scope:

- Reordering is confined to the window, and within it to the slots held by plain
  `WAITING` requests with nothing computed. A request in a blocked status
  (`WAITING_FOR_REMOTE_KVS` and friends) or one already partially computed keeps its exact
  position, and nothing is moved past it. This is a reordering among peers, not a change
  in priority.
- It requires the `fcfs` policy. Positional reordering is meaningless in a priority heap —
  `PriorityRequestQueue.prepend_request` re-inserts by priority and ignores position — and
  it would also fight the user's explicit priorities. Under `priority` the feature is
  disabled at construction.
- It requires prefix caching, and is skipped on steps that defer prefill anyway.
- The threshold exists so operators can confine reordering to periods where there are
  evictions worth avoiding. It defaults to 0.0 (always apply) so that setting only the
  window has a visible effect rather than silently doing nothing on a roomy cache.

Scoring uses a new `KVCacheManager.get_num_cached_tokens`, which probes the cache without
taking references, allocating blocks, or emitting events, so it is safe to call for a
request that may not be scheduled. `get_computed_blocks` is unsuitable for this: it emits
`BlockStored` events under `kv_cache_report_mode="full"`, which would publish phantom
events for requests that were only scored.

Cost is one prefix-cache lookup per request in the window per step, plus one linear pass
over the waiting queue when the order actually changes.

## Why this is not duplicating an existing PR

**#53571** (SLO-aware scheduling policy) is the closest existing work and deserves an
explicit comparison, since it also reorders waiting requests. It is keyed on TTFT targets
and prompt length, to stop short prompts queueing behind long prefills; this is keyed on
resident prefix length, to stop cold admissions evicting reusable blocks. Different
signal, different objective, and they could coexist.

The implementations diverge deliberately. #53571 adds a new `SchedulingPolicy` value,
which makes it mutually exclusive with `priority`. This is a bounded per-step re-sort
behind its own flag, so it composes with whatever policy is in force rather than replacing
it. If maintainers would prefer these unified under one policy mechanism, I am glad to
adapt.

Other adjacent open PRs, none overlapping:

- **#54327** (bounded prefix-aware filesystem cache eviction) concerns the KV-offload
  filesystem tier, not admission order.
- **#53772** and **#54348** rework promotion of blocked `skipped_waiting` requests. This
  PR pins non-`WAITING` requests in place, so it composes; the status filter is covered by
  the tests.
- **#45558** (priority-based preemption at `max_num_seqs`) preempts running requests; this
  never preempts.

## Serving results

Kimi-K3 FP4, 8x MI355X, a single engine with DCP=8, replaying an agentic-coding trace.
Interactivity is per-user output speed at the 90th percentile; higher is better.

### 1. Window in isolation (cadence held constant)

The claim attributable to *this* PR. Both arms pin `prefill_schedule_interval=29` and
`sched_stats=1`; the only difference is the admission window. Concurrency 52, 3628s and
3625s, same day a few hours apart.

| `cache_aware_admission_window` | p90 interactivity | tok/s/GPU | server prefix-cache hit |
| --- | --- | --- | --- |
| 0 | 12.56 | 7,983 | 90.7% |
| 16 | 12.80 (+1.96%) | 8,339 (+4.47%) | 91.5% (+0.8pp) |

A repeat at `window=16` under the identical configuration gives 12.77 and 8,459 tok/s/GPU,
so the direction reproduces. The gain is small and the arms are not repeated enough to put
a tight interval on it; I would describe it as a low-single-digit improvement in both
metrics, with the prefix-cache hit rate moving the way the mechanism predicts — that last
point is what makes the other two deltas credible rather than coincidental.

### 1b. Window in isolation, offload OFF, current nightly

A second measurement on a current nightly (`76c6f3f2`), under a deliberately
stripped-down configuration. Two differences from the table above matter and are not
incidental:

- **KV offload is OFF** (`offload=none`). The measurements above run with KV offload
  (LMCache in the deployed configuration). Offload changes how KV pressure builds, and
  this PR's threshold is defined against KV-cache usage — so the two setups do not
  exercise the window the same way.
- **The cadence option is ABSENT, not held constant.** `prefill_schedule_interval` is
  unset in both arms, so the only non-default scheduler flag in the treated arm is this
  PR's own.

`threshold=0.0`, so the window is always active. Kimi-K3 FP4, 8× MI355X, DCP=8,
`max_num_seqs = 2 × concurrency`, agentic-coding trace, 2029 s per arm.

| concurrency | `cache_aware_admission_window` | p90 interactivity | tok/s/GPU | server prefix-cache hit |
| --- | --- | --- | --- | --- |
| 44 | 0 | 15.15 | 10,818 | 94.7% |
| 44 | 16 | 15.53 (+2.53%) | 10,821 (+0.03%) | 94.6% |
| 48 | 0 | 11.50 | 10,384 | 94.2% |
| 48 | 16 | 12.07 (+4.95%) | 10,279 (−1.01%) | 94.2% |

Two control arms run hours apart under identical settings agree to **0.11% on throughput
and 0.19% on p90**, so the interactivity gains are 13–26× the run-to-run noise while the
throughput deltas sit near it.

The interactivity gain is larger at the higher concurrency, where the waiting queue is
deeper (p90 depth 39 at conc 48 versus 34 at conc 44) and there is more for the window to
reorder. **Without offload the prefix-cache hit rate is already ~94%**, leaving little
headroom for the mechanism to improve it — which is likely why it is unchanged here,
against +0.8pp in the offload configuration above.

**Window size matters more than the earlier table suggests.** At `window=64` on this
same configuration, conc 44 loses 12.9% of throughput and 8.6% of p90 interactivity,
with prefix-cache hit falling 94.5% → 93.8% — the mechanism's own target metric
moving backwards. At `window=32` the gain is about half that of 16 (+1.38% p90). Size
the window to the *typical* queue burst, not the maximum, and verify rather than
assume.

### 2. Across concurrency, deployed configuration

The configuration actually deployed enables this PR's window together with
`prefill_schedule_interval` from #54627, against a baseline with both absent. These
figures are for the two options together, not for this change in isolation. LMCache KV
offload, 3600s measured window.

| concurrency | window / interval | baseline p90 interactivity | with both options |
| --- | --- | --- | --- |
| 44 | 64 / 33 | 11.94 | 17.28 (+44.7%) |
| 48 | 64 / 33 | 11.32 | 16.33 (+44.3%) |
| 52 | 64 / 33 | 10.98 | 13.27 (+20.8%) |

Throughput over the same runs is close to unchanged, as expected for a change that
reorders admission rather than removing work: 9,617 to 9,390 tok/s/GPU at concurrency 44
(−2.4%), 10,537 to 10,103 at 48 (−4.1%), and 8,001 to 8,409 at 52 (+5.1%).

### 2b. How the benefit tracks with concurrency

Same two options, measured across the concurrency range rather than at one point.
Each concurrency runs in its own published configuration -- concurrency 44 and 48 use
DCP8 with KV offload and no speculative decoding, 14 and 1 use DCP1 with MTP -- so this
is the benefit in each deployment as it is actually run, not one configuration swept
across load.

| concurrency | baseline | with both options |
| --- | --- | --- |
| 48 | 11.32 | 16.33 (+44.3%) |
| 44 | 11.94 | 17.28 (+44.7%) |
| 14 | 46.65 | 46.79 (+0.3%) |
| 1 | 121.47 | 121.95 (+0.4%) |

The benefit is concentrated at high concurrency and disappears at low concurrency, which
is what both mechanisms predict. Admission ordering only matters when there is a waiting
queue to reorder, and a prefill cadence only matters when prefill and decode are
contending for the same steps. At concurrency 1 and 14 the queue is shallow or empty and
there is little for either option to act on, so the deltas sit at a few tenths of a
percent -- within run-to-run noise, and reported here to show the absence of an effect
rather than to claim one.

### 3. Window sizing

A same-day sweep varying **only** the window, with the prefill cadence and threshold
pinned across all three arms. Concurrency 52, ~3600s per arm.

| `cache_aware_admission_window` | p90 interactivity | tok/s/GPU | prefix-cache hit |
| --- | --- | --- | --- |
| 16 | 13.08 | 8,298 | 96.93% |
| 64 | 13.01 | 8,349 | 96.92% |
| 128 | 13.13 | 8,317 | 97.02% |

**The size is immaterial over an 8x range.** p90 spans 13.01-13.13 and throughput
8,298-8,349 — about 1%, inside run-to-run noise on this workload, with no monotonic
trend.

The mechanism explains why. Admission reorders scale 1,220 to 1,581 going from window 16
to 64 and then saturate: 128 gives 1,584, i.e. 0.2% more. This trace's waiting queue
averages about 20 deep and peaks near 70, so a window of 64 already spans it and widening
further has nothing left to reorder.

That also answers the cost question directly: since a larger window buys nothing
measurable, there is no reason to run one. Prefer the smallest window that spans the usual
queue depth. Combined with the threshold defaulting to 0.5, the per-step probe is bounded
both by width and by only running under pressure.

### Input-length coverage

ISL is a property of the agentic workload, not a knob. The trace is replayed
request-for-request, so ISL arrives as a heavy-tailed distribution and every run sweeps
that distribution rather than sitting at one length. Reporting a single "ISL"
number for an agentic trace would be misleading: the mean is roughly 120k tokens, but it
is pulled there by the tail, and the median request is only about 84k.

Per-run distributions, showing what each measurement actually covers:

| run | n | ISL mean | p50 | p75 | p90 | p95 |
| --- | --- | --- | --- | --- | --- | --- |
| conc 44 baseline | 2,462 | 117,173 | 84,644 | 135,675 | 241,476 | 340,419 |
| conc 44 both options | 2,377 | 118,084 | 84,302 | 136,698 | 245,376 | 343,461 |
| conc 48 baseline | 2,567 | 122,854 | 83,905 | 140,551 | 253,786 | 374,550 |
| conc 48 both options | 2,400 | 125,888 | 84,096 | 142,877 | 259,991 | 469,672 |

Three things follow from this that matter for reading the results above:

1. **Coverage.** Each arm spans roughly 84k at the median to 250k at p90, with the top 5%
   reaching 340k-470k. So the reported deltas are already integrated over a 3-5x span of
   input length, not measured at one point on it.
2. **Fairness.** The distributions are closely matched between the arms being compared —
   medians agree within 0.9% and p90s within 2.5% — so the A/B is not confounded by one
   arm drawing easier requests.
3. **Where the options should act.** Admission ordering and prefill cadence matter most
   where prefill work is large relative to a decode step, which is the upper half of this
   distribution. A fixed-ISL sweep at, say, 8k would sit far below the median and would
   not exercise the mechanism this PR targets.

Output lengths are short and similarly matched (median 278-301 tokens, p90 1,738-1,845),
which is what makes interactivity the metric of interest here rather than throughput.

If a fixed-ISL sweep would still be useful, that is a different experiment — synthetic
fixed-length requests rather than trace replay — and I am happy to run it; ISL is simply
not an independent variable in the measurement above.

An earlier revision of this section reported results against the `vllm-simple` KV offload
backend. That backend is no longer what we run.

No accuracy eval was run. Neither the model computation nor sampling is touched; the
change affects only the order in which waiting requests are admitted. Batch composition
does change, as with any scheduling change, so outputs are not bit-identical. I am happy
to run `tests/evals` or a gsm8k pass if reviewers would like that confirmed.
