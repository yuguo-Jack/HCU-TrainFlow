# [ROCm][Perf][GLM-5.3-Flash] MonoKernel: read and write the mxfp4_mla KV cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/62655) · state: open · merged: False

## Original PR description



## Overview

Lets the GLM-5.3-Flash MonoKernel (#61662) run with `--kv-cache-dtype mxfp4_mla` (#60321) instead of refusing it, so one server gets the MonoKernel's decode path and MXFP4's KV capacity (272 bytes per token against 1,024 for bf16).

**Stacked on #61662 and #60321**, neither of which has landed, so the diff against main includes both. This PR's own change is the last commit, 4d6094b088 (+211 / −32, 6 files). The commit before it merges #60321 into #61662 and keeps both sides of two conflicts (the CPU test list and `model.py`). I'll rebase when either lands. It stays a draft until the pending GPU validation below is done.

## Claims

- **Feature:** `--monokernel` accepts `--kv-cache-dtype mxfp4_mla` on GLM-5.3-Flash. Before this, the config refused it and every step ran vLLM's layers.
- **Same cache bytes as vLLM's path:** the launch writes each MLA row bit-identically to `store_mxfp4_mla`, and reads it back to the same bf16 values as #60321's Triton read path. A server can therefore switch between the MonoKernel and vLLM's layers step by step on one cache.
- **No change for a bf16 cache:** the new code is behind a compile-time flag.
- **No speed or accuracy claim yet:** see Pending.

## Details

Only the two stages of the sparse-attention launch that touch the MLA latent cache change. Everything between them (q_b, the indexer, top-2048 selection, the MFMAs, W_UV, o_proj) is unchanged.

| Stage | bf16 cache | `mxfp4_mla` cache |
|---|---|---|
| `cache` (writes the step's row) | each of 512 threads stores its bf16 value | the threads quantize the row and store 64 dwords of E2M1 codes and 16 E8M0 scale bytes |
| `split` (loads 64 selected rows into LDS) | 16 bytes a lane | one dword of codes and one scale byte a lane, unpacked to the same bf16 tile with `v_cvt_scalef32_pk_bf16_fp4` |

- **Write.** One 32-value group is one half-wave. The scale is `ceil_pow2(absmax / 6)` computed from the bit pattern, and an all-zero group gets 2^0. Codes round to the nearest E2M1 magnitude, with ties to even as `store_mxfp4_mla` and AITER's `per_1x32_f4_quant` do. Nibbles are packed with DPP shuffles; every 8th lane stores a dword, and each group's first lane stores its scale byte.
- **Read.** Eight latent values are one dword of codes and one scale byte. The converter multiplies by `2^(e − 127)` exactly, so the MFMAs see the same bf16 values as with #60321's Triton path.
- **Refusals.** `mxfp4_mla` joins the accepted KV dtypes. Binding checks the MLA cache's dtype and row width (272 or 512 bytes) against the configured dtype, and the op checks the dtype again at each launch, so a mismatched cache falls back to vLLM's layers rather than being misread.
- **bf16 path.** The only shared edit is the cache-row address, rewritten from `(blk · KVE + off · 512) · 2` to `blk · KVE · 2 + off · 1024`, which is the same value.
- **Tradeoffs.** The split stage loads 5 bytes a lane instead of 16 and adds 4 conversions per row; the write adds a 5-step reduction and 7 compares per value. Neither is measured yet (see Pending).
- **Note on #60321.** Its store-kernel comments say a value on a midpoint rounds down. On gfx950 the kernel rounds ties to even, as AITER does (0.75 → 1.0 and 3.5 → 4.0, but 0.25 → 0 and 2.5 → 2.0). This PR matches the behavior, and I'll correct those comments in #60321.
- **Related.** An FP8 (`fp8_e4m3`) KV cache for the same two stages is in progress separately. Both touch the same lines; when both exist, the build flag should become a KV-format choice.
