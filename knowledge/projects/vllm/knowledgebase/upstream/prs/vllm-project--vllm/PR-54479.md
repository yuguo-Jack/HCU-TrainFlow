# [V1] Fix KV cache capacity discrepancy between cold and warm starts under torch.compile (#54383)

[Upstream PR](https://github.com/vllm-project/vllm/pull/54479) · state: open · merged: False

## Original PR description

### Purpose
Resolves #54383.

### Root Cause
When booting under `torch.compile` on a cold start, JIT compilation occurs during `model_runner.profile_run()` inside `Worker.determine_available_memory()`. Transient compiler scratchpads and Triton workspace inflate the peak activation snapshot, permanently reducing the allocated KV cache pool by ~5% (e.g. 5,408 tokens on Qwen3-32B AWQ) compared to subsequent warm boots.

### Solution
- Under `torch.compile` (`compilation_config.mode != CompilationMode.NONE`), trigger an initial compilation pass ahead of memory profiling.
- Purge compiler scratchpad buffers via `gc.collect()`, `torch.accelerator.empty_cache()`, and `torch.accelerator.synchronize()`.
- Added unit tests in `tests/v1/worker/test_gpu_worker.py` parameterized over `CompilationMode` to verify that warmup execution and accelerator cleanup fire strictly when compilation is enabled and are skipped in eager mode.

### Scope Clarification
This change strictly isolates the cold-start profiling memory inflation under `torch.compile`. It does not touch memory pooling logic, startup plan persistence, or allocator split limits.

### Community Impact & Reproduction
Verified with independent reproduction on dual RTX 4090s (@vitalyrodnenko in #54383) and A100-80GB, restoring 100% cold/warm KV cache token parity.

### Testing
- `uvx ruff check`: 0 errors, 0 warnings.
- `uvx ruff format --check`: clean formatting.
- Unit tests: CPU-first simulation in `tests/v1/worker/test_gpu_worker.py::test_compilation_warmup_before_memory_profiling`.

**Reproduced the deficit, but the fix OOMs on memory-tight configs — I think it double-counts the weights**

Thanks for digging into this @bandham-manikanta — the diagnosis matches what I'd independently concluded, and the cold-boot deficit reproduces cleanly here (4th shape: 5,161 → 5,428 blocks, 4.9%).

But testing the patch on a tighter memory config, **every boot OOMs before the server comes up**. Setup: vLLM 0.28.0, Qwen3-32B-AWQ, TP=2 on 2×RTX 4090 (23.52 GiB usable each), `--gpu-memory-utilization 0.85 --max-model-len 8192`.

| | KV budget/GPU |
|---|---|
| unpatched (warm) | 10.60 GiB |
| patched | **19.69 GiB** |
| inflation | **+9.09 GiB** |
| model weights ÷ TP=2 (18.00 ÷ 2) | **9.00 GiB** |

The inflation equals the per-GPU weight share to ~1%, on all three shapes I tried (19.69 / 19.39 / 19.74 GiB). Requested KV 19.7 + weights 9.0 + overheads ~1.9 ≈ 30.6 GiB on a 23.5 GiB card, so the OOM is forced.

**Suspected cause:** `self.init_snapshot` is captured in `init_device()` *before* `load_model()`, so `init_snapshot.free_memory` means "free memory before the weights exist" — which is why `memory_profiling(self.init_snapshot, weights_memory=...)` subtracts the weights explicitly. The patch re-captures `self.init_snapshot` inside `determine_available_memory()`, i.e. *after* the weights are resident, so the baseline already excludes them and they get subtracted a second time.

**One diagnostic that might be useful:** under the patch, cold and warm compute *bit-identical* budgets (19.69/19.69, 19.39/19.39, 19.74/19.74), so parity is achieved — but the deficit being fixed is only ~0.52 GiB/GPU here, while both numbers moved by ~9 GiB. A fix for a 0.5 GiB accounting error moving things by 18× that seems worth a second look. I'd gently suggest the same reading applies to the "+15.7% cold / +13.2% warm capacity gained" in the PR description: on an 80 GB A100 with a 4B model there's enough headroom that a ~9 GiB over-estimate fits and reads as extra capacity rather than a crash.

**Caveat:** I applied the patch to 0.28.0 via a source-level overlay at the same anchor, not to `main`. If `init_snapshot`'s semantics differ on `main`, this analysis may not carry over.
