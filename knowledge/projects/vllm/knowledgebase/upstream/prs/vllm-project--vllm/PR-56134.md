# [Feature] Switch EP groups between prefill and decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/56134) · state: open · merged: False

## Original PR description

Related to #56133 and #43807.

Adds opt-in switching of a running EP group between prefill and decode. The router stops new assignments; vLLM drains accepted work and retained KV, commits the role on every core, then publishes readiness at the next epoch. Workers, weights, communicators, and CUDA graphs stay resident while other groups keep serving.

The initial scope is NIXL pull transfer, one Python frontend, and internal DP load balancing. EP membership and the communication backend remain fixed.

## Tests

- Final revision `69e0448`: 66 control, frontend, and CLI tests passed. The Python 3.11 readiness regression fails before the fix and passes after it.
- GPU prototype: 6 H100 80GB GPUs, three EP2 groups, OLMoE, DeepSeek-V2-Lite, and Qwen3-30B-A3B. All 60 switches and 3,060 requests passed with matching reference outputs and unchanged process, graph, and communication identities. Held-KV timeout recovery and stale-epoch rejection passed.

[Validation and commands](https://github.com/Etelis/vllm/blob/ff89426a0d23b0d5509e50d0bfa69a36d0174459/VALIDATION.md) distinguish the final checks from the GPU build, which includes a separate unmerged Triton MoE fix. EP16 and multi-node operation remain untested.

- ev-shindin · comment · 2026-09-15T12:59:32Z · [source](https://github.com/vllm-project/vllm/pull/56134#issuecomment-5680569158)

Read through this while working out whether our engine-side role switching could sit inside `commit_pd_role` — I think it can, and the design half of that is on #56133. Two code-level notes.

### Where the internal-DP-LB scope boundary shows up

The RFC scopes the first increment to internal DP load balancing, so this is confirmation rather than a defect report — but the failure mode is specific enough to be worth recording, since it is the line our own deployment falls on (`data_parallel_external_lb`, DP=32 across four pods):

- with external LB the client is `DPAsyncMPClient`, which does not override `call_utility_all_async`, so it inherits the `AsyncMPClient` version returning a single-element list;
- `PDRoleState` is constructed with `parallel_config.data_parallel_size`, the global rank count;
- `_check_ranks` requires `len(statuses) == self.num_engines`, so it compares 1 against 32 and raises `"Engine ranks disagree on the serving role or epoch"`.

Only `DPLBAsyncMPClient` overrides it with the `asyncio.gather` version. **I have read this rather than run it**, so worth confirming before acting on it.

If it does hold, a guard that fails the transition with an explicit "external DP load balancing is not supported" would be kinder than the ranks-disagree error, which reads like a consensus failure rather than a scope one.

Lifting it later looks like more than an override, and the choice may be worth recording in the RFC: with several frontends each owning a subset of ranks, a role change is a fleet action rather than a single-frontend transaction, and the epoch currently lives in one process. Sizing `PDRoleState` from the locally managed rank count and gathering over `core_engines` makes each frontend internally consistent, but then nothing owns the group-wide epoch — which is precisely the thing the router is being asked to trust.

### Two engine-side changes that would compose with this

We have the reconfiguration half the RFC lists as follow-up: a replica that rebuilds its MoE all2all buffer in place, weights untouched, both role buffers resident so switching back allocates nothing. Our switch would naturally be the body of `commit_pd_role`.

It is two self-contained changes, and **neither touches a file this PR touches**:

1. rebuilding a fused-MoE kernel around resident weights (180 lines, across the FP8 and unquantized methods);
2. switching the all2all backend of a live engine in place (867 lines, one new module).

Both rebase cleanly on current main as of today. Happy to open them against this PR or after it, whichever you prefer — and happy to help with the rebase this PR is flagged for, since we have just taken our own branches across the same window.

On the EP16/multi-node validation the RFC lists as outstanding: we have run switching on GLM-5.2-FP8 at EP=16 across two 8xH200 nodes, with all 16 ranks and 75 MoE layers rebuilt in both directions and no in-flight request lost. Glad to re-run it against a build of this PR if that would help close that gap.
