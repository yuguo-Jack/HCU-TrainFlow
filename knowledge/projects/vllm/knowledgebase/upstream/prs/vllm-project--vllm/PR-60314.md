# Support data-parallel multimodal encoder for Gemma-4

[Upstream PR](https://github.com/vllm-project/vllm/pull/60314) · state: open · merged: False

## Original PR description

## Overview
Enables data-parallel multimodal encoder mode (`--mm-encoder-tp-mode data`) for Gemma-4 by setting `supports_encoder_tp_data = True` on `Gemma4ForConditionalGeneration` and implementing eager-mode data-parallel ViT execution (`_dp_execute_and_gather`).
- Eliminates redundant replication of the vision encoder across TP ranks in eager mode (`--enforce-eager`).
- Partitions multimodal items across TP ranks using load-balanced assignment, reduces dynamic token lengths across ranks, and scatters gathered embeddings to preserve original sequence order.

🔴 With encoder CUDA graphs on, data TP mode and TP>1, eager fallbacks can deadlock the TP group. Each rank issues a second all-gather that the other ranks may not match. `EncoderCudaGraphManager.execute` already shards items across ranks, then each rank calls `encoder_eager_forward` on its local shard for graph misses. That fallback now reaches `_process_image_input`/`_process_video_input`, which do their own `_dp_execute_and_gather` with `tensor_model_parallel_all_gather`. Fix: make the eager path used by the manager run locally, e.g. call the `*_local` variants from `encoder_eager_forward`, and keep DP dispatch only for the non-cudagraph `embed_multimodal` path.

<details>
<summary>Why this was flagged</summary>

`EncoderCudaGraphManager` sets `use_dp` when `mm_encoder_tp_mode == "data"` and `tensor_parallel_size > 1` (vllm/v1/worker/encoder_cudagraph.py:176-180). It shards items per rank (`_dp_shard`, 705) and then runs `_execute_local` on the local subset. For any batch whose token budget is None, `_execute_local` calls `self.model.encoder_eager_forward(batch_mm_kwargs)` (encoder_cudagraph.py:524). That is `Gemma4ForConditionalGeneration.encoder_eager_forward` (gemma4_mm.py:2178-2192), which now dispatches to `_process_image_input`/`_process_video_input`. Because `self.use_data_parallel` is true there (1409/1593), it calls `_dp_execute_and_gather`, which runs `tensor_model_parallel_all_gather` (1373). Only the ranks that hit an eager fallback, and only as many times as they have such batches, enter this collective, so the TP group hangs or mismatches collectives. On base, `supports_encoder_tp_data` was unset, so data mode was not used for Gemma-4 and the eager forward ran purely locally.

**Verification:** Trigger: encoder CUDA graphs enabled, `--mm-encoder-tp-mode data`, TP>1, and a per-rank batch whose tokens exceed the largest captured budget. This PR sets `supports_encoder_tp_data = True` (gemma4_mm.py:1036). Only ranks whose local batch misses a graph issue this extra all-gather. The other ranks go straight to `_dp_gather`'s all-gather (encoder_cudagraph.py:652).

</details>

🔴 With tower/connector LoRA on, data TP mode and TP>1, Gemma-4 image and video embeddings get the wrong adapter weights or a LoRA shape error. Base never takes this path. Fix: when `_enable_mm_lora` is set, skip the DP path and use the `*_local` path. Otherwise, rebuild the tower and connector mappings for the local subset on each rank. <details>

Nothing in the diff checks `_enable_mm_lora` before taking the DP path.

**Verification:** The runner builds the TOWER mapping over every item in `mm_kwargs` order, in gpu_model_runner.py:3012-3041. `meta_args` in lora_kernel_metadata.py:197-199 returns `self.token_lora_mapping[:token_nums]`.
