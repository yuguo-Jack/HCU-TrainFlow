## Original PR description

# [Bugfix] Honor generation controls in the DeepSeek V4.1 tokenizer

## Purpose

The independent `deepseek_v41` tokenizer currently ignores
`add_generation_prompt` and `continue_final_message`. This produces identical
prompts with the generation prompt enabled or disabled, and leaves EOS at the
end of an assistant prefix even when continuation was requested.

This change forwards the controls to the V4.1 encoder and:

- suppresses only the final generation cue, preserving historical separators;
- opens a fresh assistant turn after a completed assistant message;
- supports system-only generation;
- removes only the final assistant EOS for continuation;
- keeps a partial reasoning-only assistant message inside its thinking block;
- rejects continuation without a final assistant message.

Continuation takes precedence over the generation prompt. This also handles
`ChatCompletionRequest(continue_final_message=True)` where the default
`add_generation_prompt=True` remains in the renderer kwargs. The request schema
already rejects callers that explicitly set both fields to true.

The reference fixture files are unchanged. Both fixtures end in a completed
assistant message, so the test now checks their exact reference encoding with
`add_generation_prompt=False`, and separately checks the new generation cue.

### Related Work And Scope

Related: #46256 and #46257. The existing open PR #46257, by @fank, fixes the
older `deepseek_v4` encoder; it does not modify the independent `deepseek_v41`
wrapper or encoder. This proposal is limited to V4.1 and follows the generation
control semantics discussed there. It does not claim to resolve the V4/V3.2
parts of #46256, and should not auto-close that issue.

Open-PR searches and the issue discussion were checked on 2026-09-21. This
follow-up changes only the independent V4.1 implementation, not the files in
#46257; its scope is also explained in the
[issue discussion](https://github.com/vllm-project/vllm/issues/46256#issuecomment-5756372341).

No NIXL, scheduling, DSpark, Triton, or CUDA code changes. This is not a claimed
fix for H20 worker deadlocks or production garbage output.

### Model Smoke Evaluation

An isolated H20 TP8 server loaded the real DeepSeek-V4.1-Flash model using the
unmodified nightly above. Baseline and patched tokenizers rendered the same
five synthetic conversations to token IDs; those IDs were sent serially to
`/v1/completions`. No live tokenizer modules were replaced.

Generation settings: `temperature=0`, `seed=2026`, `max_tokens=128`,
`stream=false`, `skip_special_tokens=false`. All 10 requests returned HTTP 200;
all five patched cases contained the expected answer fragment.

| Case | Baseline output | Patched output |
| --- | --- | --- |
| Normal user math question | `323` | `323` (prompt IDs unchanged) |
| Continue assistant `The result is ` | Raw BOS marker, then `# 17 * 19 = 323.` | `323.` |
| Fresh turn after completed assistant | Raw BOS marker and unrelated `#sustainable agriculture#`, then the answer | `The capital of France is Paris.` |
| System-only `Reply exactly OK.` | Empty text | `OK` |
| Continue partial reasoning `17 * 19 = 17 * (20 - 1) = ` | Generated `# Invalid Request` text after a raw BOS marker | `340 - 17 = 323.</think>323` |

The baseline "Invalid Request" was generated model text, not an HTTP error.
This is a narrow prompt-control smoke evaluation, not a broad accuracy
benchmark or full patched `/v1/chat/completions` integration test. No
throughput or production-output correctness claim is made from these samples.
