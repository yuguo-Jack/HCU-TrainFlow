# [Feature][Frontend] Accept text-based file / input_file content parts

[Upstream PR](https://github.com/vllm-project/vllm/pull/62676) · state: closed · merged: False

## Original PR description



## Overview

Fixes #46562. The server now accepts the OpenAI `file` content part (Chat Completions) and the `input_file` content part (Responses) when they carry an inline text file. The file is decoded and added to the prompt as text. Before this change, both part types failed with `Unsupported chat content part type: 'file'`.

## Claims

- `/v1/chat/completions` accepts `{"type": "file", "file": {"file_data": ..., "filename": ...}}` and `/v1/responses` accepts `{"type": "input_file", "file_data": ..., "filename": ...}`, as long as the data is a UTF-8 text file sent inline.
- `file_data` can be a base64 data URL (`data:text/plain;base64,...`) or raw base64. For raw base64, or a data URL with the generic `application/octet-stream` type, the media type is guessed from `filename` with `mimetypes`. An explicit specific data URL type (e.g. `application/pdf`) is never overridden by the filename. A fixed set of common text extensions (`.md`, `.markdown`, `.yaml`, `.yml`, `.csv`, `.tsv`, `.toml`, `.rst`, `.log`, `.txt`, `.json`, `.xml`) is always accepted, so the result does not depend on the server's mime tables. The global `mimetypes` registry is left unchanged. The accepted media types are `text/*`, `application/json`, `application/xml`, `application/yaml` and `application/x-yaml`.
- The file text becomes an ordinary text part. Text-only models work, `has_non_text_content` stays `False` (no media connector is created, and `kv_transfer_params.prompt_token_ids` is kept), and the other file fields (`file_data`, `file_id`, `file_url`, `filename`) never reach the chat template.
- The following inputs are rejected with a `VLLMValidationError` (HTTP 400) and a specific message, not the generic one: `file_id`, `file_url`, a missing `file_data`, non-text media types such as PDF, an unknown media type, non-base64 data URLs, invalid base64, and non-UTF-8 data.
- File text goes through the same reserved `<prompt_embeds>` placeholder check as other text parts.
- No new dependencies. The code uses `pybase64`, which vLLM already depends on, and the stdlib `mimetypes`.

## Validation

Unit tests added to `tests/renderers/chat_utils/test_text_only.py`:

- `test_parse_chat_messages_file_part[string|openai]`: a Chat `file` data URL placed between text parts. Checks that order is kept, that `mm_data is None`, and that `has_non_text_content` is `False`.
- `test_parse_chat_messages_input_file_part`: a Responses `input_file` with raw base64 and `filename="notes.txt"` (non-ASCII UTF-8). Checks that the rendered part is exactly `{"type": "text", "text": "File: notes.txt\n..."}`, so no file fields leak.
- `test_parse_chat_messages_file_part_text_extension`: `README.md` and `config.yml` as raw base64, and `notes.md` as an `application/octet-stream` data URL. Covers extensions `mimetypes` may not know.
- `test_parse_chat_messages_rejects_unsupported_file`: 5 representative rejection cases (`file_id`, missing `file_data`, PDF via filename, invalid base64, non-UTF-8), each for both `file` and `input_file`.
- `test_parse_chat_messages_rejects_placeholder_in_file`: placeholder rejection when `enable_prompt_embeds` is on.

## Details

**Why this is not a duplicate of #57774.** #57774 is open and labelled `needs-rebase`, with no activity since 2026-09-29. On it, @DarkLight1337 raised concerns about supporting arbitrary file types (maintenance and security); this PR answers that by accepting only UTF-8 text files sent inline, adding no parsers or dependencies, and rejecting everything else with a 400. It edits `vllm/entrypoints/chat_utils.py`, which no longer exists on `main` (the code moved to `vllm/renderers/chat_utils/chat_message.py`). It covers only Chat Completions, and it adds server-side PDF/DOCX extraction through pymupdf/pypdf. This PR targets the current layout, covers both Chat `file` and Responses `input_file`, adds no dependencies, and limits scope to text files. Everything else gets a clear 400. Scope proposed in https://github.com/vllm-project/vllm/issues/46562#issuecomment-6273441151. The issue author, @lazydog2, handed the issue over on 2026-10-20: "I'm not currently working on this issue and would be happy for you to pick it up".

**Design.**
- Both part types are registered in `MM_PARSER_MAP` and added to `_TEXT_CONTENT_PART_TYPES`, but not to `TEXT_PART_TYPES`. They have their own branch in `parse_chat_message_content_part`, so the generic text branch's `_collect_extra_fields` cannot copy `file_data` (the whole base64 payload), `filename`, `file_id` or `file_url` into the template dict.
- Presentation: if `filename` is given, the text is prefixed with a `File: <filename>` line. Otherwise the raw text is used. This is the simplest choice that still tells the model what it is reading. It follows no particular model's template and is easy to change if reviewers want something else (e.g. no header, or XML-style tags).
- Data URL parsing follows `MediaConnector._load_data_url` (RFC 2397, base64 only, and media type parameters such as `charset` are ignored). Decoding is strict UTF-8.
- `file_id` (no Files API) and `file_url` (no server-side fetch, which also avoids new SSRF surface) are rejected on purpose.

**Limitations.**
- For raw base64 or `application/octet-stream` data with an extension outside the fixed set, acceptance still depends on `mimetypes.guess_type(filename)`, so it can vary by platform. A data URL with an explicit media type always works.
- No size limit beyond the existing request and `max_model_len` limits.
- The Harmony (GPT-OSS) Responses path (`flatten_input_text_content`) and the Rust frontend are not changed.
