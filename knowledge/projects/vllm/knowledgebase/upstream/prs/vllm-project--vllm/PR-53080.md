# [Bugfix] Separate target and draft scheduling budgets

[Upstream PR](https://github.com/vllm-project/vllm/pull/53080) · state: closed · merged: False

## Original PR description

## Purpose

This PR aims to fix #52922. The idea is simply to track target and draft token budgets separately, since these two stages may process different numbers of tokens for the same request.

Given that the number of draft input tokens varies across current speculative methods, we try to describe the draft input layout in a somehow unified manner:

```text
[target_segment][includes_bonus_as_anchor?][mask * num_parallel_drafting_tokens]
```

Here, `target_segment` can contain all target-derived inputs, or all except first input, or last valid input, or none. `includes_bonus_as_anchor` indicates whether the bonus token from target is reused as the anchor token of draft. `num_parallel_drafting_tokens` is the number of method-specific input tokens used to predict multiple draft tokens in parallel, e.g., mask tokens.

Take MTP/EAGLE3/DFlash/DSpark/P-EAGLE/PARD as examples, with `Q=num_target_tokens` and `K=num_speculative_tokens`:

* MTP/EAGLE3 use all target-derived inputs except the first one, followed by the target bonus as the draft anchor, thereby forming what is known as "shifted input". The two parts contain `Q` input slots in total, so draft input cost is `C(Q)=Q`. Later autoregressive steps process one token per request only and do not exceed the step-0 batch size.
* DFlash/DSpark do not include target segment in their main query forward. Their input contains the bonus/anchor followed by a fixed-size parallel block. DFlash therefore uses `K+1` slots. DSpark uses `K` slots when the anchor predicts the first draft token, and `K+1` otherwise. Their target-derived context/kv precomputation runs as a separate stage bounded by the target budget.
* P-EAGLE/PARD add `K-1` parallel drafting tokens to their base layouts. P-EAGLE uses all target-derived inputs except the first one plus the bonus anchor, giving `C(Q)=Q+K-1`. PARD keeps full target segment plus the bonus anchor, giving `C(Q)=Q+K`.

- CarrotSwordsman · comment · 2026-08-27T12:25:38Z · [source](https://github.com/vllm-project/vllm/pull/53080#issuecomment-5439106098)

Coming over from #52922, where I argued the combined accounting was intentional. **I was wrong for `dspark`, and your PR body is what corrects it:**

> DFlash/DSpark do not include target segment in their main query forward. [...] Their target-derived context/kv precomputation runs as a separate stage bounded by the target budget.

That is exactly the condition I flagged as invalidating my reasoning — I inferred a shared forward from the config-layer docs and never traced the DSpark runner path. With `target_segment="none"`, the draft forward genuinely does not carry target tokens, so charging target tokens against the draft cost is over-restrictive. Apologies for the noise.

Since this is WIP and open to feedback, I re-derived `DraftInputLayout` standalone and checked the budget arithmetic. Sharing what held up and two things worth a look.

**1. The arithmetic is sound — no layout can overrun `draft_budget`.**

For every method in your table (`K=7`) and `draft_budget ∈ {1, 2, 8, 16, 64, 128, 8192}`, scheduling the full granted `request_token_budget` never exceeds `draft_budget`. The growing layouts are also *exactly* tight, not merely safe:

| layout | `get_cost(Q)` | `minimum_cost` | granted | resulting cost |
|---|---|---|---|---|
| `mtp` / `eagle3` | `Q` | 1 | `min(tb, db)` | `= db` |
| `draft_model` | `Q+1` | 2 | `min(tb, db-1)` | `= db` |
| PARD | `Q+K` | `K+1` | `min(tb, db-K)` | `= db` |
| P-EAGLE | `Q+K-1` | `K` | `min(tb, db-K+1)` | `= db` |

The `1 + remaining_draft_budget` correction in `_get_request_token_budget` is what makes the first three land exactly on the boundary — worth keeping the comment there, it is easy to "simplify" wrongly later.

**2. It also resolves the CUDA-graph worry I raised on the issue.** Since `draft_budget` is independently initialized to `max_num_batched_tokens`, both forwards stay bounded by that same value, so `_set_cudagraph_sizes` remains valid even though `_set_max_num_scheduled_tokens` no longer reserves `scheduled_token_delta`. On the issue's example (`mnbt=16`, `K=4`, two 8-token prefills):

```
old: admits [8, 2] -> 10 of 16 target tokens
new: admits [8, 8] -> 16 of 16 target tokens, draft batch = 8 <= 16
```

Might be worth stating that invariant explicitly in the PR description, since removing the reservation is the part a reviewer will look at hardest.

**3. Constant-cost layouts gain an implicit concurrency cap that is invisible to `max_num_seqs`.**

For `target_segment="none"`, `get_cost` is constant per request, so at most `max_num_batched_tokens // cost` requests can draft in a step regardless of `max_num_seqs`:

| method | cost/req (K=7) | mnbt=64 | mnbt=128 | mnbt=2048 |
|---|---|---|---|---|
| `dflash` | 8 | 8 | 16 | 256 |
| `dspark` (anchor=T) | 7 | 9 | 18 | 292 |
| `dspark` (anchor=F) | 8 | 8 | 16 | 256 |

Your serve config (`mnbt=128`, `K=7`, `max_num_seqs=16`) sits just above the line at 18. But e.g. `mnbt=64` with `K=7` silently caps drafting at 9 while `max_num_seqs=16` suggests 16. The existing `max_num_scheduled_tokens < 8192` warning would not catch it. A one-off warning when `mnbt // minimum_cost < max_num_seqs` for non-growing layouts would make that visible.

**4. The benchmark is a throughput/latency trade, not a pure win** — worth saying so before a maintainer asks:

| | without | with | Δ |
|---|---|---|---|
| Output throughput | 2970.07 tok/s | 3557.05 tok/s | **+19.8%** |
| Duration | 706.10 s | 589.58 s | **-16.5%** |
| Mean TTFT | 354249 ms | 296654 ms | **-16.3%** |
| Mean TPOT | 2.88 ms | 4.23 ms | **+46.9%** |
| Mean ITL | 9.18 ms | 13.40 ms | **+46.0%** |
| Acceptance rate | 31.51% | 31.24% | ~flat |

At `--max-concurrency 4096` with `max_num_seqs=16` this is a fully saturated queue, so larger batches trading per-token latency for throughput is expected, and flat acceptance rate is the important signal that draft quality is unaffected. Still, framing it as the trade it is — plus maybe one low-concurrency run to show TPOT is not regressed when the queue is not saturated — would make it much harder to push back on.

Happy to help verify further if useful; I have a single H20 available, though the config above wants TP=2.
