# [ROCm][MoRIIO] Fix WRITE prefill-block release routing under Wide-EP

[Upstream PR](https://github.com/vllm-project/vllm/pull/58435) · state: open · merged: False

## Original PR description

## Purpose

`MoRIIOConnectorScheduler._release_write_prefill_blocks` frees the producer's
deferred KV blocks when a request finishes with `do_remote_prefill` still set —
i.e. it was aborted before `update_state_after_alloc` ever ran.

It addressed the producer with the **raw global** `remote_dp_rank` and
`remote_host`:

```python
target_port = remote_notify_port + get_port_offset(remote_dp_rank, tp_index)
self._send_transfer_release(transfer_id, remote_host, target_port)
```

The notify path in `update_state_after_alloc` resolves the same destination
differently — it folds the rank to its pod-local value and looks up the owning
pod's host:

```python
_remote_dp_rank_for_port = fold_local_rank(remote_dp_rank, _dp_local)
_pod_idx = pod_index(remote_dp_rank, _dp_local)
_notify_host = _remote_hosts[_pod_idx]
```

Under multi-pod Wide-EP the two disagree for every rank on a child pod. At
DP=16 / `dp_local=8`, half the ranks are misrouted:

| rank | notify (correct) | release (before) |
| --- | --- | --- |
| 0–7 | `10.0.0.10:61005`–`61012` | same — match |
| 8 | `10.0.0.11:61005` | `10.0.0.10:61013` |
| 12 | `10.0.0.11:61009` | `10.0.0.10:61017` |
| 15 | `10.0.0.11:61012` | `10.0.0.10:61020` |

A pod binds notify sockets only for its **local** ranks, so both pods listen on
`61005`–`61012`. The release for ranks 8–15 targets `61013`–`61020`, which
nothing binds — so it is **dropped**, not misdelivered. Since this release is
the only thing that frees those blocks (no timeout, no GC, no retry), each
occurrence strands one request's worth of prefill KV for the lifetime of the
process, silently.

Single-pod deployments are unaffected: the modulus is a no-op and there is one
host, so both paths already agreed.

## Why it went unnoticed

`_release_write_prefill_blocks` predates multi-pod support. `fold_local_rank`
and `pod_index` were introduced later, when Wide-EP multi-pod landed, and
applied to the notify path. The release function was pre-existing code that had
always been correct, and nothing in it flagged that its assumptions had changed.

It is also hard to hit in testing: the trigger is an abort *before* scheduling,
so a benchmark where every request completes never executes the path at all.

## Changes

- Reuse the notify path's per-pod resolution in the release path. Both helpers
  were already imported.
- Raise the two early-return guards from `warning` to `error` and include the
  transfer id and DP rank. Each of those returns leaks blocks with no other
  reclaim path, so the leak should at least be attributable. (Deliberately not
  converted to exceptions — that would change behaviour in a path that
  currently degrades gracefully.)

## Test Plan

New: `tests/v1/kv_connector/unit/test_moriio_write_release_routing.py`

Follows `test_moriio_routing.py`'s convention of binding the unbound method to
a lightweight stand-in. Covers:

- master-pod ranks (0–7) unchanged; child-pod ranks (8–15) reach the owning pod
  at the folded offset
- the property directly: for all 16 ranks, release target == notify target
- every release lands on a port a pod actually binds
- single-pod and the `dp_local == 0` external-DP sentinel are byte-identical to
  before the change
- degenerate inputs: missing `remote_hosts`, host list shorter than the pod
  index, non-numeric `dp_local`
- TP fan-out at `tp_size=2`
- both leak guards: nothing sent, error logged naming the request, transfer id
  and rank

## Test Result

Run inside a ROCm vLLM image on an MI355X node.

Against the **unpatched** connector, the suite fails exactly where expected:

```
22 failed, 29 passed
```

The 22 failures are the child-pod ranks, their bound-port assertions, the
all-16-rank parity property, TP fan-out, and the two guards. The 29 passes are
the master-pod ranks, single-pod and the sentinel — the cases that should not
be affected.

With the fix applied:

```
97 passed
```

Full MoRIIO suite, no regressions:

```
159 passed, 25 skipped in 80.23s
```

Can we use this PR as an opportunity to factorize the computation in a helper function used on the notify path, release path, eager handshake, and write finalize?

Something along the lines of:
```
def resolve_pod_notify_target(
    dp_rank: int, tp_rank: int, dp_local: int,
    base_notify_port: int, default_host: str, pod_hosts: list[str],
) -> tuple[str, int]:
    """(host, notify_port) for a remote (dp_rank, tp_rank) under multi-pod Wide-EP."""
    host = default_host
    if dp_local > 0 and pod_hosts:
        idx = pod_index(dp_rank, dp_local)
        if 0 <= idx < len(pod_hosts):
            host = pod_hosts[idx]
    port = base_notify_port + get_port_offset(fold_local_rank(dp_rank, dp_local), tp_rank)
    return host, port
```
