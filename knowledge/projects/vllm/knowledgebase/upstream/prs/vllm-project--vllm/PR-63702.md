# [KV Connector] Add pause mode "migrate" for KV-preserving request handoff

[Upstream PR](https://github.com/vllm-project/vllm/pull/63702) · state: open · merged: False

## Original PR description

## Overview

Add `pause_generation(mode="migrate")`. An engine being retired hands its in-flight requests to other engines together with their KV cache, instead of aborting them (the next engine recomputes the prompt and every generated token) or draining them, which keeps the whole instance, every GPU of a large DEP group, allocated until its longest generation ends. The NIXL connector supports it in pull mode, including hybrid recurrent models with MTP on Model Runner V2.

Motivation: KV-preserving decode scale-down. The [DeepInfer deployment Q&A](https://github.com/deepseek-ai/DeepInfer/blob/main/doc/inference_deployment_qa.md) describes this shutdown path: "a decode engine (CE) enters a grace period (1 min) after receiving a shutdown notice; any requests still unfinished, along with their KV cache, are forwarded in one shot to other CEs to continue decoding." The grace period lets short requests finish, and the forward keeps the long tail from holding the instance, although DeepInfer also writes decode-time KV to a shared 3FS cache. This PR is the engine side of that forward and the vLLM part of [ai-dynamo/dynamo#17073](https://github.com/ai-dynamo/dynamo/issues/17073), which covers the orchestrator side (retirement trigger, target selection, continuation). The same primitive helps RL rollouts: when only a few long-tail requests remain, `mode="migrate"` can consolidate them onto a few engines and release the rest for training or the next rollout batch.

## Claims

- **Pause mode `"migrate"`.** Once no scheduled step is in flight, every request finishes as `FINISHED_MIGRATED`, reported as `finish_reason="abort"`, and its final output carries the connector's `kv_transfer_params` (and `ec_transfer_params`). The pause completes when the exported blocks are released. New requests are rejected with a retryable error (HTTP 503) until resume, as with `abort` and `wait`.
- **NIXL pull export.** A migrated request is exported like a finished remote prefill, under the producer lease that consumer heartbeats renew, so any `NixlConnector` instance continues it through the existing remote-prefill path and recomputes only the last token. A consumer never loads more tokens than the producer reports in `remote_num_tokens`; without this cap a boundary on a block edge trips `_apply_prefix_caching`'s block-count assertion.
- **Hybrid models with MTP.** MRV2 (`mamba_cache_mode="none"`) applies the accepted speculative offset to recurrent and convolution state lazily; a blocking `prepare_migration` worker RPC commits it before transfer. MRV1 and align mode are rejected before anything is paused; a runtime failure in that RPC aborts every request (no `kv_transfer_params`) and fails the pause, since the state may be partially committed.
- **Validated end to end** with one prefill and three decode instances on H200:
  - GLM-5.3-Flash-NVFP4 ([`RedHatAI/GLM-5.3-Flash-NVFP4`](https://huggingface.co/RedHatAI/GLM-5.3-Flash-NVFP4); hybrid KDA, MTP3), TP2 and DEP2: 16/16 requests continued from transferred KV in every run, with non-zero MTP acceptance; GSM8K with requests migrated mid-answer: 0.9166 → 0.9212 (TP2), 0.9174 → 0.9166 (DEP2).
  - DeepSeek-V4.1-Flash ([`deepseek-ai/DeepSeek-V4.1-Flash-1017`](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017); DEP4, DSpark with 3 speculative tokens), two nodes: 16/16 in each of five runs, one across nodes.
- **Against reloading from a KV cache**, on identical contexts with 16 requests continued at once (target TTFT median):

| Cache the resubmitted request reloads from | Generated before handoff | migrate | reload |
|---|---|---|---|
| Shared Mooncake store holding the decode KV (DeepSeek-V4.1-Flash) | 2.5K–3.8K | 257–405 ms | 724–770 ms |
| | 5.1K–7.5K | 316–331 ms | 586–641 ms |
| Ideal prompt-only cache (GLM-5.3-Flash-NVFP4) | 1.6K–2.5K | 301–312 ms | 844–852 ms |
| | 5.2K–7.6K | 346–352 ms | 1,817–1,915 ms |

Existing pause modes and P/D behavior are unchanged.

## Usage

1. Pause the source: `AsyncLLM.pause_generation(mode="migrate")`, or `POST /pause?mode=migrate` with `VLLM_SERVER_DEV_MODE=1`.
2. Each request finishes with `finish_reason="abort"`, its tokens so far, and `kv_transfer_params`.
3. As soon as a response arrives, continue it on another instance via `/inference/v1/generate` (`--enable-scale-out`) with the prompt plus the generated tokens, the remaining `max_tokens` and the returned `kv_transfer_params`. Do not wait for the pause call first.
4. The pause call returns once every exported block has been read or its lease (`kv_lease_duration`) has expired.

## Validation

Setup: one prefill and three decode instances, two GPUs each (GLM-5.3-Flash-NVFP4: TP2, or DEP2) or four (DeepSeek-V4.1-Flash: DEP4), where DEP*n* is data parallel *n* with expert parallelism, MRV2, `NixlConnector` (`kv_both`). GLM runs with prefix caching off and `VLLM_SSM_CONV_STATE_LAYOUT=DS`; DeepSeek-V4.1-Flash keeps prefix caching on and adds `MooncakeStoreConnector` through `MultiConnector`. The GPU runs used this change ported onto `fa75d3456`, the newest build on the test machines, without the later review fixes (preflight check, runtime abort, `ec_transfer_params`), none of which changes the path exercised.

The abort + full-recompute arm on GLM reached the first token after 260–7,217 ms, varying widely between runs (some runs include first-time Triton JIT compilation on the targets). Against a no-KV recompute of the same context on the same target (TP2), the first continuation token matched for 47 of 48 migrated requests and for 46 of 48 requests decoded in place without migration; later tokens diverge in both, since vLLM is not batch invariant.

**KV-cache comparison.** The Mooncake arm runs `MultiConnector` (NIXL + `MooncakeStoreConnector`, `save_decode_cache: true` on the source) within one node; store replay resumes at a 64-token block boundary, one block earlier for Eagle-family drafters such as DSpark, so it recomputes 64–128 tokens per request versus one for migration. Saving decode KV had no measurable decode cost (TPOT 10.2–10.3 ms vs 10.3–10.4 ms without). The prompt-only arm prefills the prompt on P again before the continuation (not counted) and recomputes the generated tokens. First continuation tokens agreed across arms (15–16 of 16 per run).

## Design notes

- The export runs from an idle-state callback, so no step is in flight; `_notify_idle_state_callbacks` stops once a callback creates work (blocks waiting to be read), and `_process_input_queue` re-checks `has_work()` instead of blocking.
- A request still receiving remote KV finishes as aborted and is not exported.
- No new public finish reason: `FinishReason` is mirrored by the Rust frontend, so `kv_transfer_params` distinguishes a migrated request from a client abort.
- The pause waits for the exported blocks to be released, which tells the orchestrator when the source can be shut down.

## Limitations

- NIXL pull mode only; other connectors return `kv_transfer_params: null` (resubmit without KV). Also not exported: requests that never ran or are still receiving remote KV, host-buffer KV caches, and multi-module MTP with prefill backoff > 1.
- Speculative recurrent-state migration needs MRV2 and `mamba_cache_mode="none"` (decode instances without prefix caching).
- **Stale `kv_transfer_params`.** As in any NIXL pull transfer, the consumer reads the source's blocks without validating them first. The source frees them after the first read, or when the lease expires without a heartbeat; a late or repeated read can then return another request's KV once the source has resumed, and `kv_load_failure_policy` does not detect it. Use each set once, resubmit a failed continuation without it, and resume the source only after every continuation has produced its first token. Validating reads against the source is a follow-up for the NIXL connector.
- Generated tokens become prompt tokens on the target, so penalties and structured-output state restart there, as with a plain resubmission.
- Validated with up to DEP4 instances, none spanning nodes; no pre-copy.
- Read source outputs through `AsyncLLM` or non-streaming `/inference/v1/generate` with `n=1`.

No open PR or issue implements request-level migration; #62570 extends the pause lifecycle for checkpoint/restore, not handoff.

| Generated before handoff | migrate | abort + reload from the pool |
|---|---|---|
| 2.5K–3.8K | 257–405 ms | 724–770 ms |
| 5.1K–7.5K | 316–331 ms | 586–641 ms |

Even with the decode KV in the pool, a resubmitted request recomputes its last 64–128 tokens: the pool keeps only full 64-token blocks, so the partly filled last block is recomputed, and with a speculative drafter vLLM steps back one more block. Migration hands over the KV up to the last token, so the target recomputes only that token.

For hybrid models the pool cannot hold the decode-time state today: the KV cache manager keeps Mamba states only at prefill checkpoints (retaining decode checkpoints is #50551), so a resubmitted request resumes at its prompt's last checkpoint and recomputes every generated token. The "prompt-only cache" rows (GLM-5.3-Flash-NVFP4: 844–852 / 1,817–1,915 ms vs 301–312 / 346–352 ms for migration) are the best case of that path.

I'd expect plain GQA models to keep a gap too, though I haven't measured it. Even at a 100% block hit the replay recomputes the last, partially filled block (the pool stores whole blocks only, and the last token is always recomputed for its logits), plus one more block with an Eagle-family drafter. If the resubmission is routed through a prefill instance, it also adds P's pool load and tail compute and a second transfer of the whole context from P to the decode instance; the store-replay numbers above are the cheaper variant, loading straight into the decode instance.

- qianlihuang · comment · 2026-10-27T08:59:03Z · [source](https://github.com/vllm-project/vllm/pull/63702#issuecomment-6437724281)

A follow-up on scale: a DEP64 decode instance at ~20 requests per rank holds ~1.3K in-flight requests. With abort + resubmit in a P/D deployment, all of them hit the prefill pool at once. That is a transient spike that also delays new requests' prefills: with a prompt-only cache every generated token is recomputed, and with decode offload P still loads each context from the pool and recomputes its tail. Then each full context is transferred again from P to a decode instance. Migration skips the prefill pool: it moves the KV once, from the retiring instance to the targets, and each target computes one token per request.

Rough transfer cost for that case (estimates; the runs in the description hand off 16 requests at a time):

- Volume: at DeepSeek-V4.1's ~2.3 KB of KV per token, 1.3K requests of 128K tokens are ~0.38 TB, about 6 GB per source rank.
- Time: a DEP64 instance fills most of an NVL72, so the targets are in other racks and each rank's scale-out NIC sets the pace: ~0.12 s at 400 Gb/s, ~0.06 s at 800 Gb/s.
- Caveats: models with more KV per token take proportionally longer. Where the targets' EP all-to-all also uses the scale-out network (e.g. 8-GPU nodes), migration competes with it, so the orchestrator should migrate in waves.
