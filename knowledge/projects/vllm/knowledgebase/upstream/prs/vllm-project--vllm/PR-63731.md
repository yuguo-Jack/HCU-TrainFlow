# [Bugfix][Responses] Route browser.* to web-search streaming events instead of MCP

[Upstream PR](https://github.com/vllm-project/vllm/pull/63731) · state: open · merged: False

## Original PR description



## Overview

Fixes #52443. Supersedes #52444 (abandoned with unresolved merge conflicts).
Excludes `browser.*` recipients from `is_mcp_tool_by_namespace()` so built-in browser searches emit only web-search streaming events and do not incorrectly emit duplicate MCP lifecycle events.

## Claims

- Eliminates spurious `response.mcp_call.*` events when streaming tool calls with `browser.*` recipients in the Responses API (`/v1/responses`).
- Preserves full web-search lifecycle events (`response.web_search_call.*`).
- Adds regression test coverage in `tests/entrypoints/openai/responses/test_serving_responses.py`.
- Removes obsolete `# TODO: Fix browser emitted as MCP calls` from `vllm/entrypoints/openai/responses/serving.py`.

## Details

In the Harmony Responses API streaming path, `is_mcp_tool_by_namespace()` acts as the inverse of `is_function_recipient()` to route non-function tool calls to MCP event builders. However, built-in browser tools (prefixed with `browser.`) have their own dedicated lifecycle handled by `emit_tool_action_events()`. Because `is_mcp_tool_by_namespace()` did not check for `browser.` prefixes, every browser call was initially emitted as an MCP call, resulting in dual lifecycle events.

This PR adds an explicit guard for `recipient.startswith("browser.")` in `is_mcp_tool_by_namespace()`.
