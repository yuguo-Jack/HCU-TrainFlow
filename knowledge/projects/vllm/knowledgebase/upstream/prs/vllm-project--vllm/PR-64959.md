# [Model] Add LiquidAI LFM3 (Lfm3ForCausalLM)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64959) · state: open · merged: False

## Original PR description



## Overview

Add native support for [LiquidAI/LFM3-1.7B](https://huggingface.co/LiquidAI/LFM3-1.7B) (`Lfm3ForCausalLM`), step 2 of #64645.

Depends on #64647 by @abhijithneilabraham (width-7 `causal_conv1d`). That commit is included here unchanged, with its original authorship, so this branch runs and CI can exercise the model. It can be dropped on rebase once #64647 merges.

## Claims

- New `vllm/model_executor/models/lfm3.py`: the 24-layer hybrid (13 short-conv, 6 full-attention, 5 sliding-window attention with window 256), QK RMSNorm, a per-head sigmoid attention output gate, sandwich norms and tied embeddings.
- Reuses `ShortConv` (width 7), `Lfm2MLP`, the LFM2 weight mapper and the existing `proportional` RoPE. No changes to core components.
- Registered in the model registry and test registry, added to `HYBRID_MODELS` in `test_hybrid.py`, and documented in `supported_models.md`.
- Serving works with the existing parsers: `--reasoning-parser qwen3 --tool-call-parser qwen3_coder --enable-auto-tool-choice`.

## Details

- **RoPE:** the checkpoint config says `rope_type: default` for full attention with `partial_rotary_factor: 0.5`. The reference implementation keeps the full-head frequency progression for the rotated dimensions and zero-pads the tail, using NeoX pairing over all 128 dims. This is not vLLM's standard partial rotary (`rotary_dim=64`), so full-attention layers select the existing `proportional` RoPE (`Gemma4RotaryEmbedding`), which implements exactly this layout. Sliding layers use full rotary with theta 1e4.
- **Config:** transformers does not ship `Lfm3Config` yet (huggingface/transformers#50036 is open), so `trust_remote_code=True` is needed for the config. Execution uses the native model.
- **Duplicates:** no other LFM3 model PR is open. #64647 is only the kernel dependency.
- **Not validated yet:** TP/PP, quantization, LoRA, speculative decoding and prefix-caching reuse.

- hungho77 · comment · 2026-11-02T07:56:55Z · [source](https://github.com/vllm-project/vllm/pull/64959#issuecomment-6572023825)

The description lists quantization and LoRA as not validated yet. I had an LFM3 port of my own that is nearly identical to this PR, so I ran those checks on it, plus IFEval, on a different GPU. The results are below in case they help review.

**Scope.** These numbers come from my own branch, not from this PR's head. The model code differs from `lfm3.py` here in only a few places:
- I don't set `ignore_unexpected_prefixes` for a tied `lm_head`.
- I don't pass `num_spec` to `short_conv_state_shape`, the same as `lfm2.py`.
- I map to `proportional` RoPE only when `partial_rotary_factor < 1`, and raise for a partial factor with a non-default `rope_type`.

None of these touches the quantized or LoRA code paths. The kernel is #64647's change plus a width guard (suggested there).

**Environment:** RTX 4070 Ti SUPER (sm_89, 16 GB), torch 2.14.0+cu130, transformers 5.22.1, Triton 3.8.0, base `3d23773f10`. Server: `vllm serve ... --trust-remote-code --max-model-len 32768 --reasoning-parser deepseek_r1`.

**Tests on this GPU:** `test_causal_conv1d.py` 324 passed, the registry/init tests 3 passed, and `test_hybrid.py -k LFM3` passed.

### GSM8K 5-shot and the generation config

| `--generation-config` | `tests/evals/gsm8k/gsm8k_eval.py`, 5-shot, greedy, 256 tokens, 1319 questions |
|---|---|
| default (`auto`) | 46.2% |
| `vllm` | 41.7% |

The default 46.2% agrees with the 45.87% in the description. The checkpoint's `generation_config.json` sets `repetition_penalty: 1.1`, and with the default `--generation-config auto` the server merges it into every request, which makes up the difference. I ran the other evals with `--generation-config vllm`, so the card's sampling settings below are the only ones applied.

I also sent the first 200 questions through Transformers greedy, with the repetition penalty removed. Transformers and vLLM both scored 39.0%, and 166 of the 200 extracted answers were the same.

### Accuracy, BF16 and Liquid's quantized checkpoints

The card's settings are thinking on. GSM8K uses temperature 1.0, top_p 0.95 and top_k 20. IFEval uses lm-eval 0.4.13 `local-chat-completions` at temperature 0.6, top_p 0.95 and `max_gen_toks` 16384.

| Checkpoint | Kernel on sm_89 | GSM8K, 0-shot chat, 1319 questions | IFEval prompt strict / prompt loose / inst strict / inst loose |
|---|---|---|---|
| LFM3-1.7B (BF16) | — | 87.2 | 95.38 / 96.67 / 96.16 / 97.24 |
| LFM3-1.7B-FP8 (compressed-tensors, 128×128 blocks) | `MarlinFP8ScaledMMLinearKernel` | 86.1 | 93.90 / 96.30 / 95.08 / 96.76 |
| LFM3-1.7B-NVFP4 (ModelOpt) | `MarlinNvFp4LinearKernel` | 86.3 | 94.45 / 94.82 / 95.08 / 95.44 |

The model card gives 96.66 for IFEval.

**Loading.** Both quantized checkpoints load with no LFM3-specific code:
- Their ignore and exclude lists name the conv layers `conv.*`. Those names still match `short_conv` after the weight mapper is applied.
- The conv projections, `gate_proj` and `lm_head` stay BF16, as the model cards state.
- NVFP4 also leaves attention unquantized.

sm_89 runs both checkpoints through the weight-only Marlin kernels, so the native W8A8 block-FP8 and W4A4 NVFP4 paths on Hopper and Blackwell are not covered here.

### LoRA

The adapters are rank 8 and use the checkpoint's own module names:
- **Attention:** `q/k/v/o_proj` and `gate_proj`.
- **Conv:** `conv.in_proj` and `conv.out_proj`.
- **MLP:** `w1/w2/w3`.

Each run used 32 greedy tokens.

| Check | BF16 | FP8 | NVFP4 |
|---|---|---|---|
| Zero-B adapter gives output identical to the base model | yes | yes | yes |
| Random adapter changes the output | yes | yes | yes |
| Adapter nonzero only on `conv.in_proj`/`conv.out_proj` changes the output | yes | yes | yes |
| Adapter nonzero only on `gate_proj` changes the output | yes | yes | no token flipped (see below) |

The conv-only and gate-only adapters target the two places where an adapter could be silently dropped: the `.conv.` → `.short_conv.` rename and the single-slice `in_proj` packing.

**NVFP4 gate-only.** The gate-only adapter flipped no token on NVFP4, but it is applied. Its `gate_proj` is a `ColumnParallelLinearWithLoRA`, and it shifts the logprobs by about as much as on BF16 (mean 0.02, max 0.11).

**Mixed batches.** I mixed base, zero-adapter and random-adapter requests in one batch. Compared with separate runs, the only differences were divergences at near-ties, where each token was in the other's top 5. That is expected without batch invariance.

Once this PR merges, I can follow up with a CI test for the quantized checkpoints and LoRA, if that would be useful.
