# [Bugfix] Use one stage in Triton MLA decode on GPUs with <128 KiB shared memory

[Upstream PR](https://github.com/vllm-project/vllm/pull/60173) · state: open · merged: False

## Original PR description

## Purpose

Fixes #60172.

On sm_120 GPUs (RTX PRO 6000, RTX 5090), `TRITON_MLA` is the only MLA backend, and the first decode fails with:

```text
out of resource: shared memory, Required: 102400, Hardware limit: 101376
```

`_decode_grouped_att_m_fwd` launches the MLA shape (`BLOCK_DMODEL=512`, `BLOCK_DPE=64`, `BLOCK_N=32`, `BLOCK_H=16`) with `num_stages=2`, which needs 102,400 bytes. These GPUs allow 101,376 bytes per block. The existing one-stage fallback only triggers when `BLOCK_DMODEL >= 1024`, so MLA (latent width 512) never gets it.

This PR also uses one stage when the device's `max_shared_mem` is below 128 KiB. It reads the value from the Triton driver, cached per device. GPUs with large shared memory (Hopper, datacenter Blackwell) keep two stages, so their behavior is unchanged.

## Test Plan

- The standalone reproduction in #60172 (`decode_attention_fwd`, `is_mla=True`, Lk=576, 32 heads, FP8 KV cache, page size 16, 1,000-token sequences) on an RTX PRO 6000 Blackwell Workstation Edition (CC 12.0), comparing the output against a PyTorch reference.
- End to end: `sarvamai/sarvam-105b-fp8` on 2x RTX PRO 6000, TP=2, `--kv-cache-dtype fp8`, vLLM 0.31.0. Chat completions and streaming.

## Test Result

- Without the change: `OutOfResources: shared memory, Required: 102400, Hardware limit: 101376`.
- With it: the kernel runs, with max abs error 8.2e-4 against the reference (reference absmax 0.27). The full model serves correctly with `--enforce-eager`.
- These runs used vLLM 0.31.0 with the same one-stage condition applied. This file is identical on current main.
- Not tested: CUDA-graph mode, and sm_86/sm_89 (which share the 101,376-byte limit).
- `ruff check` and `ruff format --check` pass.

- gitbisector · comment · 2026-10-09T23:04:30Z · [source](https://github.com/vllm-project/vllm/pull/60173#issuecomment-6090757106)

Verified on GB10 (sm_121, 101376 B, triton 3.7.1) with the reproducer from #60172: `Required: 102400` before, passes after (max abs err 3.4e-3 vs torch reference). One refinement: only the fp8-KV MLA tile (`BLOCK_DMODEL=512 + BLOCK_DPE=64`) overflows at two stages (102400 B); bf16 KV needs 63488 and is ~4% faster at two stages (1.090 vs 1.138 ms, B=32 H=32 seq=4096). Adding `k_buffer.element_size() == 1 and BLOCK_DMODEL + BLOCK_DPE > 512` to the `< 128 KiB` gate keeps bf16-KV MLA decode at two stages. LGTM either way.
