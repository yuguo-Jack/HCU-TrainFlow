# [Metrics] Add num_requests_prefilling/decoding Prometheus gauges

[Upstream PR](https://github.com/vllm-project/vllm/pull/39456) · state: closed · merged: False

## Original PR description

## Purpose

Expose prefill vs decode request count breakdown as Prometheus gauges.

The scheduler already classifies requests as prefill vs decode internally (`request.num_computed_tokens < request.num_prompt_tokens`), but this was never surfaced to the `/metrics` endpoint. Operators currently only see `num_requests_running` (total) and `num_requests_waiting`, making it impossible to distinguish prefill-heavy vs decode-heavy load from metrics alone.

New gauges:
- `vllm:num_requests_prefilling` — requests currently in prefill phase
- `vllm:num_requests_decoding` — requests currently in decode phase

**Files changed:**

| File | Change |
|------|--------|
| `vllm/v1/metrics/stats.py` | Add `num_prefilling_reqs` / `num_decoding_reqs` fields to `SchedulerStats` |
| [vllm/v1/core/sched/scheduler.py](cci:7://file:///Users/yqu161/workplace/vllm/vllm/v1/core/sched/scheduler.py:0:0-0:0) | Compute prefill/decode counts in [make_stats()](cci:1://file:///Users/yqu161/workplace/vllm/vllm/v1/core/sched/scheduler.py:1935:4-1976:9) |
| `vllm/v1/metrics/loggers.py` | Register Prometheus gauges + DP aggregation |
| `tests/entrypoints/serve/instrumentator/test_metrics.py` | Add new gauges to `EXPECTED_METRICS_V1` |

Invariant: `prefilling + decoding == running` (both derived from the same `self.running` set in a single scheduler call).

**Use cases:**
- Correlate TPOT spikes with prefill bursts (the most common cause of TPOT spikes produces zero preemptions, so `num_preemptions_total` alone is insufficient)
- Tune `--max-num-batched-tokens` and `--max-num-partial-prefills` based onobserved prefill/decode concurrency
- Enable P/D-aware routing and autoscaling in external gateways

I think the sentiment of this PR is interesting. We lack real insight into the reason scheduling decisions are made:
- how many requests are truly waiting vs waiting for kv transfer to finish

I think that in practice reporting explicitly the number of requests in prefill phase vs decode phase is unlikely to be useful though, since in practice for normal sized requests (e.g. 5000 ISL), we will only have 1 or 2 requests prefilling in the batch at any given time. Additionally, since these are gauges, its also unlikely to be be captured by prometheus, since the prometheus probes are typically on the order of 5-15s intervals and will miss quick spikes

I wonder if there is a better way to capture the information you are looking for. For example, it might be better to have a counter of the number of batches with N+ tokens where `N=some big number`. This will:
- a) be easier to measure in grafana (since it will be a counter you can measure over intervals)
- b) wont require peeking into the scheduler data structures, which is bug prone

- chinmay29 · comment · 2026-04-10T01:10:42Z · [source](https://github.com/vllm-project/vllm/pull/39456#issuecomment-4219116278)

Thanks for the detailed review, you’re right on both issues.

The current gauge logic is incorrect: by the time `make_stats()` runs, `_update_after_schedule()` has already advanced `num_computed_tokens`, so it would underreport prefilling requests. And the preempted/resumed case also makes `num_computed_tokens < num_prompt_tokens` a poor proxy for what is conceptually still context/prefill work in the current step.

I still think the motivating problem is real though: I was trying to get visibility into when context/prefill work is interfering with decode and causing TPOT spikes. I agree now that request-phase gauges are not the right metric for that.

A better follow-up seems to be a batch-level metric derived from `SchedulerOutput`, using the existing context vs generation split for the current iteration rather than peeking at mutated scheduler state. Concretely, I’m thinking of replacing these gauges with a Prometheus-friendly mixed-batch metric, e.g. context tokens scheduled in iterations that also contain generation work, potentially as a histogram or a thresholded counter for “batches with >= N context tokens”.

That should:
- avoid the timing/preemption bugs you pointed out
- be much easier to reason about in Grafana over intervals
- map more directly to the TPOT question than counting “prefilling requests”

If that direction sounds reasonable, I’m happy to rework the PR accordingly.
