# [Bugfix] Fix GPTQ checkpoint loading for PLaMo3

[Upstream PR](https://github.com/vllm-project/vllm/pull/62836) · state: closed · merged: True

## Original PR description



## Overview

Fix GPTQ checkpoint loading for PLaMo3, broken since #54809, by building its `lm_head` as most models do: store `quant_config` on `Plamo3ForCausalLM`, pass it to `lm_head`, and name the head `maybe_prefix(prefix, "lm_head")`.

## Claims

- GPTQ PLaMo3 checkpoints load again. They previously failed with `ValueError: There is no module or parameter named '...g_idx'`.
- PLaMo3's head is named `lm_head`, its state-dict name, instead of `.lm_head`, so quant config entries that name it exactly (e.g. compressed-tensors `ignore` / `targets: ["lm_head"]`) now match it.
- No change for BF16 checkpoints or for GPTQ with `lm_head: false`. Nested prefixes (e.g. `draft_model.lm_head`) are unchanged.

## Validation

Reproducer: `vllm serve` any PLaMo3 checkpoint quantized by GPTQModel, which writes `.g_idx` even with `desc_act=False`. We ran a PLaMo3 31B GPTQ checkpoint (internal) on 1x A100 with the nightly image at 042ab03 (`plamo3.py` is unchanged on current main):

| | Result |
|---|---|
| Before | Engine init fails with the `g_idx` `ValueError` |
| After | Serves; chat and completion requests return correct answers |

Head name matching, run on this branch:

| prefix | `should_ignore_layer(ignore=["lm_head"])` | `find_matched_target(targets=["Linear", "lm_head"])` |
|---|---|---|
| `.lm_head` (before) | `False` | `None` |
| `lm_head` (after) | `True` | `"lm_head"` |

On this branch:

- `pytest tests/model_executor/test_plamo3.py`: 1 passed (CPU-only host). This existing test does not build `Plamo3ForCausalLM` through `__init__`, so it does not cover this change.
- `pre-commit run --hook-stage manual --from-ref upstream/main --to-ref HEAD`: all hooks pass, including mypy.

## Details

**GPTQ loading.** Since #54809, GPTQ layers no longer register `g_idx`, and checkpoint `.g_idx` tensors are dropped by `QuantizationConfig.get_checkpoint_weight_mapper()`. `AutoWeightsLoader` takes this mapper from the first module, among the model and its direct children, that has a `quant_config` attribute. PLaMo3 set none, so the lookup stopped at `lm_head`, which `ParallelLMHead` gives `quant_config=None`, and the `.g_idx` tensors had nowhere to go. Storing `quant_config` on `Plamo3ForCausalLM` fixes the lookup. Passing it to `lm_head` too matches most models (e.g. Qwen3, Llama), and lets a head that the checkpoint quantizes get its quant method instead of always being unquantized (not tested, as we have no such PLaMo3 checkpoint).

**Head name.** `ParallelLMHead`'s `prefix` is the layer's full name in the state dict. `f"{prefix}.lm_head"` gave `.lm_head` for a top-level model, which matches no checkpoint key. Now that `lm_head` receives the quant config, quant methods look the head up by this name, so exact entries for `lm_head` would miss it. Weight loading is unaffected, since it resolves parameters by module path, and the online lm_head copies only carry the prefix over. The PLaMo3 checkpoints we know of do not quantize the head, so this does not change how they load.

No accuracy evaluation: the change only lets the loader drop `.g_idx` and renames the head, so it does not alter compute for any checkpoint that loads. No new test: CI has no GPTQ PLaMo3 checkpoint, a unit test for the loader lookup would need heavy stubbing, and checking the head name alone is trivial. No duplicate: among open PRs mentioning PLaMo3, `g_idx`, or `lm_head` quantization, only #45535 edits `plamo3.py`, and it passes `quant_config` to `embed_tokens` only, which neither the loader lookup (model and direct children) nor `lm_head` depends on. AI assistance (Claude Code) was used; the submitter reviewed all changes and ran the tests.
