# [Perf][Core] Reserve step budget for waiting requests with cached KV

[Upstream PR](https://github.com/vllm-project/vllm/pull/65339) · state: open · merged: False

## Original PR description

````markdown
## Overview

A chunked prefill that is already on the running list spends the whole per-step
token budget on every step, so the waiting loop only runs once that prefill
finishes. A queued request whose KV is already cached (prefix cache or a KV
connector's async load) needs only the tokens the cache did not serve, yet it
waits for the entire prefill. This reserves the budget the waiting queue needs
to be admitted, and lets the running loop use only the remainder.

Found while investigating LMCache/LMCache#5440; the fix is independent of
LMCache: any chunked prefill on the running list starves the waiting queue, so
plain prefix caching is affected as well.

## Claims

- A queued cache-hit request is admitted mid-prefill instead of after it: on
  1x A100-PCIE with Qwen3-14B + LMCache MP, 4 requests whose 39,497-token prefix
  is resident plus 4 cold 14,465-token requests, the hit requests' TTFT drops
  13.95 s -> 5.00 s (-64%).
- Group wall is unchanged: 14.769 s -> 14.813 s (+0.3%, same run). The budget
  comes out of the running prefill's step, and every queued request is capped
  at one fair share so the running batch keeps its own share.
- No new configuration, env var or default. The scheduler change is
  27 added lines (+27/-2).

## Details

Root cause: `Scheduler._schedule()` serves `self.running` first and only then
enters the waiting loop. A running chunked prefill asks for `token_budget`
every step, so `token_budget` reaches 0 and the waiting loop is skipped until
the prefill ends. `--scheduling-policy priority` cannot help: it reorders the
waiting queue only and cannot preempt a running chunk.

Fix: before the running loop, compute

```python
reserved_budget = 0
num_active_reqs = len(self.running) + self.num_waiting_for_streaming_input
reservation_queues = (
    (self.waiting, self.kv_holding_waiting)
    if self._pause_state == PauseState.UNPAUSED
    else (self.kv_holding_waiting,)
)
num_reservable_reqs = sum(len(queue) for queue in reservation_queues)
if num_reservable_reqs > 0 and num_active_reqs < self.max_num_active_reqs:
    fair_share = input_budget // (num_running + num_reservable_reqs)
    for request in itertools.chain(*reservation_queues):
        remaining = max(
            0, request.num_tokens_with_spec - request.num_computed_tokens
        )
        reserved_budget += min(remaining, fair_share)
    reserved_budget = min(reserved_budget, token_budget)
```

then gate the running loop with `token_budget > reserved_budget` and cap its
per-step chunk with `token_budget - reserved_budget`.

Four details matter:

- The per-request charge is `min(tokens left, one share)`. A request that has
  already computed part of its prompt is charged only its uncached tail. A
  freshly arrived request has `num_computed_tokens == 0`, so a cache hit and a
  cold request look identical until the waiting loop probes the prefix cache
  / connector; one share is the probe quantum. The cap also stops one long
  queued prompt from reserving the whole step.
- `kv_holding_waiting` is counted as well: a request moves there the moment its
  async KV load starts. While the load is in flight (`WAITING_FOR_REMOTE_KVS`)
  it is still charged one share, which also keeps the waiting loop running so
  the finished load can be promoted; after some tokens are computed the charge
  drops to the uncached tail.
- The reservation is skipped when the waiting loop cannot admit anything
  because of the active-request cap: budget reserved in that state can only
  throttle the running batch (measured: 16% wall). The check reuses the loop's
  own admission condition instead of duplicating it.
- Under `PAUSED_NEW` the loop only drains `kv_holding_waiting`, so only that
  queue is charged. Charging queued cold requests there would throttle the
  running prefill for a request the loop cannot admit (unit test:
  `..._reserves_nothing_when_paused_new`).

Duplicate-work check: no open/closed PR or issue matches this behavior (search
terms: "reserved budget", "waiting queue chunked prefill starves", "kv cache
hit waiting scheduler"). The closest open PRs are #56455 (bounded prefill
admission), #63458 (adaptive token-budget scheduler example), #58837
(prefix-cache admission risk), #61741 (long-prefill chunking), #64927
(time-bounded prefill hold), #64379 (linear-time async KV load admission) and
#53772 (promoting parked skipped_waiting requests); none reserves step token
budget for the waiting queue in `_schedule`.

Tradeoffs / limitations (please note before merging):

- Requests queued but not yet admissible are charged one share for nothing.
  The active-request gate covers the `max_num_seqs` case exactly (negative
  control: +16% wall without it, stock-level with it). A nearly full block pool
  is still charged: gating on `get_num_free_blocks() == 0` would only catch the
  completely empty pool and would couple the scheduler to KV manager internals
  (the scheduler tests stub `kv_cache_manager`), so that residual is left out.
  With the gate the blocked-queue control costs at most +0.6% wall, and the
  cache-hit workload shows no cost (14.813 s vs 14.769 s).
- An in-flight async KV load (`WAITING_FOR_REMOTE_KVS`) is charged one share
  per step even though it cannot be admitted until the load completes; that
  charge is also what keeps the waiting loop running so the load can be
  promoted. Lowering it to a single token would save budget but delay
  promotion by a step.
- No accuracy evaluation was run: the patch changes which requests share a
  step, not what is computed for a token. Recommend a GSM8K sanity run if
  maintainers consider chunk-composition changes accuracy-relevant.
- Validation is on one GPU / one model / one connector workload; the numbers
  above are from outside CI (needs 2x80GB-class GPU memory for the 39k prefix
  plus LMCache). CI coverage for the scheduler behavior itself is the five
  unit tests, which the `cpu_test` step runs (`pytest -m cpu_test v1/core` in
  `.buildkite/test_areas/misc.yaml`).
````
