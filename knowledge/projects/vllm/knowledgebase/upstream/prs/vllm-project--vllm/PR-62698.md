# [Perf][MRV2] Parallelize staged writes across 1024-element chunks

[Upstream PR](https://github.com/vllm-project/vllm/pull/62698) · state: closed · merged: True

## Original PR description



## Overview

`_apply_write_kernel` (MRV2 `StagedWriteTensor` / `FusedStagedWriter`) runs one program per staged write and loops over 1024-element chunks, so writing an admitted long prompt into its `all_token_ids` row runs on a single SM. This PR launches one program per chunk instead. It also removes per-block checks from `BlockPool.get_new_blocks` when neither prefix caching nor a metrics collector is enabled.

## Claims

- Long staged writes are 31x faster at 128K tokens (76 -> 2.5 us) and 120x faster at 855K tokens (443 -> 3.7 us) on GB200. Small writes (decode steps, block tables) do not regress.
- In DEP decode, every admission ran this copy on the admitting rank right before its forward, which made that rank the straggler for the step. With this PR, admitting a request adds ~10 us of rank skew instead of ~200 us.
- `get_new_blocks` + `free_blocks` for 4000 blocks without prefix caching: 616 -> 528 us.

## Validation

**Kernel microbenchmark**, GB200, FlashInfer CUPTI, int32, old kernel copied into the script, outputs checked equal before timing:

| writes | old (us) | new (us) | speedup |
| --- | ---: | ---: | ---: |
| 256 x 1 token (decode step) | 2.82 | 2.30 | 1.2x |
| 256 x 8 (block table) | 2.78 | 2.32 | 1.2x |
| 1 x 8K | 7.04 | 2.24 | 3.1x |
| 1 x 32K | 20.94 | 2.18 | 9.6x |
| 1 x 128K | 76.32 | 2.46 | 31.0x |
| 1 x 855K | 443.42 | 3.71 | 119.5x |
| 1 x 128K + 63 x 1 token | 75.20 | 5.94 | 12.7x |

**Serving context** (DeepSeek V4.1 Flash, P/D decode instance, DEP, 128K-token prompts, GB200; measured on our internal branch, which runs the same kernel): at DEP32 BS64, the admitting rank was the last to reach the first MoE in 90 of 98 steps, 252 us behind the median rank (46 us in steps with no admission). With this change at DEP8 BS64, the last rank trails the median by 73 us when a rank admits vs 63 us when none does.

**BlockPool**: in-process CPU microbenchmark, 4000 blocks, `enable_caching=False`, no metrics collector, NUMA-pinned on GB200 Grace, best of 5 x 200: 616 us (current code path) -> 528 us.

The existing `test_staged_write_inflight` already covers multi-chunk and mixed-length writes on the `StagedWriteTensor` path. The new `test_block_tables_fused_write_spans_multiple_chunks` covers a fused write longer than one chunk.

## Details

- Grid dim 1 is `cdiv(max_write_len, 1024)`. Programs past the end of a shorter write are fully masked. Each `StagedWriteTensor` records its longest staged write as it stages, so launching adds O(1) host work. Computing the max from `cu_lens` at apply time would cost ~40 us per 1024 writes on Grace. The bytes written are unchanged, and no new sync is added.
- Tradeoff: in a batch with one long write and many short ones, the short writes launch programs that exit immediately (1 x 128K + 63 x 1: 5.9 us vs 2.5 us for 1 x 128K alone). This is still far below the old 75 us.
- `get_new_blocks`: blocks popped from the free queue always have `ref_cnt == 0`, so the no-caching, no-metrics path sets `ref_cnt = 1` directly. The caching and metrics paths are unchanged.
- Duplicate check: #62018 fuses separate staged-write calls into fewer launches, and #51334 / #59908 reduce the host-side staging cost. None of them changes how the kernel parallelizes a single long write, so they are complementary to this PR.
