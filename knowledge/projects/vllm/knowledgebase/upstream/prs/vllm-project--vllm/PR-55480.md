# [Bugfix][CPU] Use CPU fallback for Mamba batch_memcpy without Triton

[Upstream PR](https://github.com/vllm-project/vllm/pull/55480) · state: open · merged: False

## Original PR description

## Purpose

Fixes #46693.

On macOS/CPU, hybrid Mamba models such as Qwen3.5 crash in `mamba_utils.batch_memcpy` when Triton is unavailable. `batch_memcpy` always launched `@triton.jit batch_memcpy_kernel` with `[grid]` syntax. Without Triton that name is a dummy Python function, so the launch raises `TypeError: 'function' object is not subscriptable`.

`CPUModelRunner` later monkeypatches `batch_memcpy_kernel` to `cpu_triton_utils.batch_memcpy_kernel`, but that is too late and is skipped when the GPU runner path is used (as in the issue traceback). This PR makes `batch_memcpy` itself fall back to the existing CPU `_batch_memcpy_impl` (`ctypes.memmove`) when `HAS_TRITON` is false or the kernel is not launchable. The GPU/Triton launch path is unchanged when Triton is available.

The same issue also reports that `python -m vllm.collect_env` crashes on macOS because `get_pkg_version()` asserts `get_platform() == "linux"`. That helper now returns `None` off Linux so IGC/XPU package queries stay Linux-only without aborting the report.

## Why this is not a duplicate

- No open PR references #46693.
- #46697 (`[Bugfix] Add CPU fallback for mamba batch memcpy`) attempted a similar fix but is **closed** (merge conflicts). That PR inlined a new `ctypes.memmove` loop; this one reuses the existing `cpu_triton_utils._batch_memcpy_impl` and does not depend on the `CPUModelRunner` monkeypatch.
- #48354 only fixes the `collect_env` non-Linux assert. This PR bundles that small onboarding crash with the actual serving crash from #46693.
- #54505 is a broader CPU mamba prefix-caching wrapper change and does not touch `batch_memcpy`.

AI assistance was used to prepare this patch. I reviewed the changed lines and ran the tests below.
