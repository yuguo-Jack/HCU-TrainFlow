# [ROCm][Build][3/5] Speed up ROCm build: split the skinny GEMMs per kernel family and trim torch headers

[Upstream PR](https://github.com/vllm-project/vllm/pull/62718) · state: open · merged: False

## Disclosure

AI assistance was used. The changes were reviewed and tested manually.

## Overview

**Splits `csrc/rocm/skinny_gemms.cu` on one item - the kernel family (#15830 landed the file, #33762, #34304 and #40687 added kernels).**

`csrc/rocm/skinny_gemms.cu` holds four unrelated kernel families (LLMM1, wvSplitK, wvSplitKrc, wvSplitKQ) whose device code generation was serialized on one core (~58 s). Move the kernels to a header, give each family its own translation unit, and stop pulling `<torch/all.h>` into kernel headers.

`main` already contains #62475, so this PR is a single commit on top of it. Part of a 5-PR series with #62716 (paged attention), #62717 (topk softplus-sqrt), #63364 (int4 skinny GEMM) and #63365 (fused MUSE-Spark op); the gain is joint, see *Validation*.

The single-arch rows are `pip install -e .` on MI350 (gfx950); the 9-arch row is the `setup.py bdist_wheel` described under *Validation*. All cold builds:

| build | `main` | this PR | All 5 PRs (#62921) |
|---|---|---|---|
| `MAX_JOBS=16`, gfx950 only | 107 s | 110 s | 87 s |
| `MAX_JOBS=64`, gfx950 only | 85 s | 85 s | 50 s |
| `MAX_JOBS=64`, 9 archs | 1263 s | 1248 s | 472 s |

## Claims

- Splits the skinny GEMM launchers per kernel family, so the four families and the int4 GEMM compile in parallel instead of on one core; the largest unit drops from 58.3 s to 43.4 s.
- Trims `<torch/all.h>` from the launcher units: `rocm/quickreduce/custom_quickreduce.cu` goes from 30.4 s to 20.1 s.
- The skinny GEMMs stop being a straggler, which is what lets the attention and topk gains of the series show up in the wall clock.
- Nothing about what runs changes: 528 of the 534 launcher-body lines are byte-identical to the old file, no numerics change.

- The kernels and launchers are unchanged: 528 of the 534 launcher-body lines are byte-identical to the old file, and the 6 remaining lines are the two includes moved into `wvSplitKQ` plus the four workspace-pool constants moved into `wvSplitKrc`. No numerics change.
- The skinny GEMMs stop being a straggler, which is what lets the series' attention and topk gains show up in the wall clock.

### Why five PRs

The two builds are bound by different things, so no single change moves both.

**Why the three single-arch PRs are all needed.** At 1 arch (`gfx950`, `MAX_JOBS=64`, `main` = 85 s) three groups take turns setting the wall, in this order:

1. topk softplus-sqrt (#62717) - 74.5 s, a single unit
2. paged attention (#62716) - 71.6 s, the slowest of 12 units
3. other skinny GEMMs (#62718) - 40.9 s, a single unit

#62717 takes (1) to 7.4 s, #62716 takes (2) to 31.1 s and #62718 stops (3) from becoming the next tail; with all three the tail moves to `selective_scan_fwd` (37.7 s) and the build goes from 85 s to 49 s. Drop any one of them and a ~70 s unit is back at the top, so the single-arch win needs all three.

**Why that is not enough at 9 archs.** A 9-arch build multiplies every unit's time by ~9, and the tail becomes two files that none of the first three touch: `csrc/rocm/skinny_gemms_int4.cu` at 1232 s and `csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu` at 478 s. All three merged take the 9-arch build from 1263 s to only 1253 s. #63364 splits the first (its tail drops to 448 s) and #63365 the second (to 171 s), which is what reaches 472 s.

The `skinny_gemms_int4.cu` tail is invisible in a `gfx950` build because that file **only emits its kernels for RDNA (that is part of the 9-arch build)**:

https://github.com/vllm-project/vllm/blob/f4edf9f0f078ae67392510aafd1871288948a3c3/csrc/rocm/skinny_gemms_int4.cu#L17-L19
https://github.com/vllm-project/vllm/blob/f4edf9f0f078ae67392510aafd1871288948a3c3/csrc/rocm/skinny_gemms_int4.cu#L568-L579

`csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu` fails differently: it has no arch guard, so a `gfx950` build compiles it for real - it is just 25 s there against 478 s across nine archs, which is why a single-arch profile ranks it as irrelevant (#63365).

## Details

Four kernel families with no code in common shared one translation unit, so `LLMM1` waited for `wvSplitKQ`'s device code generation and vice versa; the file was the second slowest unit of a ROCm build and became the slowest one as soon as the paged attention units were split.

The kernels and their shared helpers move to `csrc/rocm/skinny_gemms.cuh`, and `skinny_gemms_{llmm1,wvsplitk,wvsplitkrc,wvsplitkq}.cu` each keep one host launcher. The five file-scope helpers (`get_lds_size`, `on_gfx1x`, `on_gfx12`, `on_gfx1151`, `mindiv`) become `inline` so the header can be included by several units, and CMake gains a single `VLLM_SKINNY_SRC` list used by the extension sources, by the `_rocm_C_skinny` object library and by the existing gfx1250 exclusion (which used to name the two files three times).

`<torch/all.h>` drags autograd, nn and jit into every kernel unit, and the header also included `rocm/dispatch_utils.h` - which includes `<torch/all.h>` itself - without using any of its FP8 dispatch macros. `skinny_gemms.cuh` now uses `<torch/types.h>` and no longer includes `dispatch_utils.h`; `skinny_gemms_wvsplitkq.cu` includes `dispatch_utils.h` (for `VLLM_DISPATCH_FP8_TYPES`) and `quantization/w8a8/fp8/common.cuh` (for `is_fp8_ocp()`) itself, and `custom_quickreduce.cu` switches to `<torch/types.h>`.

**Diagnostics change (the only one).** The arch-`#else` stubs in the header now `__builtin_trap()` instead of hitting a device `assert` with file/line (the old code `#undef`/`#define`d `NDEBUG` around `<assert.h>` to keep the assert live, which is order-dependent now that the file is a header). Those stubs are never launched - they exist so that the arch-specific `#if` in the launchers has something to call - so the difference only shows up if that invariant is ever violated.

**Naming and references.** The rename is followed through everywhere it leaks out of the build: the `.buildkite` `source_file_dependencies` entries that used to name `csrc/rocm/skinny_gemms.cu` (which would have silently stopped triggering `test_rocm_gemm_rs_ar.py`) now list the new files, and the `TORCH_CHECK` hint, the `vllm/` comments that point at the source (`layers/utils.py`, `v1/worker/utils.py`), the test comment, `torch_bindings.cpp` and `skinny_gemms_int4.cu` now name `skinny_gemms_wvsplitkrc.cu` / `skinny_gemms.cuh`.

**Header hygiene.** `skinny_gemms.cuh` is now included by four units, so the pieces that used to be file-local were made safe for that: SPDX header, `#ifndef` guards around the `__HIP__GFX9__`/`__HIP__GFX1X__`/`__HIP__MI3XX__`/`LDS_SIZE` macros, `#undef LDS_SIZE` at the end of the header (the int4 unit defines its own, different value), `UNREACHABLE_CODE` is `__builtin_trap()` instead of an `#undef`/`#define NDEBUG` dance around `<assert.h>` (which used to depend on include order), and the inline helpers carry a note that their function-local statics are now one object per program rather than one per translation unit. `kWvSlots`/`kWvCaptureSlots` moved next to their only user, and the four launcher units keep a one-line header.

**How the file got this big.** Four PRs added kernels to `csrc/rocm/skinny_gemms.cu` (created by #15830), all in one TU:

| PR | landed | what it added |
|---|---|---|
| #15830 | 2025-04-21 | the file: 11 `__global__` kernels across the llmm1 / wvsplitk / wvsplitkrc / wvsplitkq families, 27 templates |
| #33762 | 2026-02-28 | 3 padded-stride kernel variants |
| #34304 | 2026-03-10 | 1 more kernel variant |
| #40687 | 2026-05-28 | the N=5 arm |

Arch support (#34709 for gfx1x, #40037 for gfx1102/gfx1103) multiplied those kernels by more targets without adding any, and the rest of the history (#33493, #34410, #34100, #40784, #56098, #60721) is tuning, workspace and header work. So 15 kernels ended up in one TU, which is why splitting by family is enough: they barely share code any more.

### Left to do

Follow-ups identified while doing this, deliberately out of scope:

- [ ] Guard the host-only ATen includes and launcher bodies with `__HIP_DEVICE_COMPILE__`: the device pass still parses them (10.5 s of the 43.4 s unit) although the kernels only need `c10::Half`/`BFloat16`/`Float8_e4m3fn`.
- [ ] Split `wvSplitk` by dtype: it is still the largest unit (43.4 s, of which ~32 s is codegen) and the frontend floor per unit is ~20 s, so the trade-off improved but did not disappear.
- [ ] `<torch/all.h>` still comes in via `rocm/dispatch_utils.h` for ~50 other TUs; trimming it there needs a CUDA build check.
- [ ] The `_rocm_C` extension holds `_rocm_C_skinny` as an object library; with the families split, giving each its own target would let `MAX_JOBS` scheduling prioritise the big ones.
- [ ] Not done here on purpose: splitting `skinny_gemms.cuh` into a common header plus per-family kernel headers (the per-unit parse cost is real, ~20 s for the ~2000-line header, but it is unchanged by this PR and the split adds churn).
- [ ] Not done here on purpose: new tests (the existing `test_rocm_skinny_gemms.py` already covers all four families: 2519 passed, 636 skipped) and an execution run on gfx1100/gfx942 - a gfx1250-only configure and a gfx1030 compile were done instead.
