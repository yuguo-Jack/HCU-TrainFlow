# [Attention] Shard MiniMax M3.1's NVFP4 index cache with indexer CP

[Upstream PR](https://github.com/vllm-project/vllm/pull/64631) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Lets MiniMax M3.1's NVFP4 index cache (vllm-project/vllm#64111) be sharded over TP ranks with indexer CP, which vllm-project/vllm#61929 and vllm-project/vllm#63671 support only for FP8. Depends on vllm-project/vllm#63671 (itself on vllm-project/vllm#61929): only 7 commits are new here ([this PR's commits](https://github.com/vllm-project/vllm/pull/64631/files/a76900d6eee737506a7e7d7e2d540a3171c8cbe8..d5a53c38ed44fb5e19494d665abe5f33482a9afb)), and the branch also merges #63671's latest head and main. Like vllm-project/vllm#61929, it needs vllm-project/MSA#46 (`FMHA_SM100_SRC_DIR`) until the MSA pin moves past it.

Not a duplicate: no open PR shards the NVFP4 index cache. vllm-project/vllm#59980 (M3, FP8) and vllm-project/vllm#64448 (ROCm) split decode scoring over a replicated cache, as main's opt-in `indexer_decode_cp` does.

## Claims

- With `--attention-config '{"indexer_kv_dtype":"nvfp4","indexer_cache_sharding":"on"}'` (off by default), each TP rank stores only its rows of every NVFP4 index page: 36 B instead of 72 B per token per sparse layer at TP2, 18 B at TP4. Supported: TP2 and TP4 at `--block-size 128` (256 cannot serve yet, see below), `indexer_prefill_cp='gather'`.
- Decode rounds index-K as the stock Q8KV4 decode indexer does on each arch (to e4m3 on SM100/SM103, exact on SM107), so the sharded CuTe scorer's page scores match the stock kernel's up to FP32 summation order.
- At P256/TP2 with eight-query decode (DSpark k=7), a rank's shard pages are stock NVFP4 pages, so decode scores them with the stock Q8KV4 decode indexer instead. On GB200 and GB300 that makes the per-layer decode indexer 1.35-1.4x faster than with the CuTe scorer at 16 requests and 1.6x faster at 64 (see Validation), and its scores are bitwise identical to the stock scores of the unsharded pages. `VLLM_MINIMAX_M3_ICP_Q8KV4_DECODE=0` keeps the CuTe scorer. Serving cannot reach this path yet, so only kernel tests cover it: at `--block-size 256`, vllm-project/vllm#63671 lets NVFP4 main attention keep 256-token pages, but vllm-project/MSA#46's Q8KV4 prefill accepts only 128-token pages (found by reading the code, not run).
- The gather prefill stages each rank's shard pages to FP8 with the stock NVFP4 prefill's kernel, then all-gathers them.
- End to end on GB300 at TP2 and `--block-size 128` (so the CuTe scorer), one 1-hour agentic run at concurrency 16 per variant: sharding gives 9.8% more KV tokens at the same prefix-cache hit rate, but ITL rises 25% and throughput falls 2%. An MRCR accuracy check is inconclusive: pooled −1.1 points (95% CI −2.2 to +0.1). See Validation.
- With sharding off, behavior is unchanged apart from the shared paths listed under Details.

## Details

- **Motivation:** KV capacity. Without sharding every rank stores the whole NVFP4 index cache; sharded, TP2 halves and TP4 quarters it, and the freed memory goes to KV tokens.
- **Tradeoffs:**
  - The gather prefill all-gathers FP8 rows (128 B rather than 72 B per token), and like the FP8 gather of vllm-project/vllm#61929 it neither chunks nor reserves its per-layer transient. Main's extensible KV cache, on by default with the V2 runner, now leaves less free memory for that transient than the old 0.92 `gpu_memory_utilization` default did.
  - A sharded cache disables the fused MXFP8 QKV epilogue, which writes whole NVFP4 index pages.
  - Sharded prefill ranks pages with MSA's fmha OnlyScore and `sparse_topk_select` instead of the stock Q8KV8 prefill indexer, so its selection can differ from the replicated path at exact ties.
- **Why a second decode scorer:** only at P256/TP2 is a rank's shard a whole stock NVFP4 page, so only there can the stock Q8KV4 decode indexer, which already serves the replicated cache, score it. It needs full eight-query tiles, because the candidate publish reads contiguous `[tokens, heads, columns]` scores. Every other shape keeps the CuTe scorer.
- **Policy:** at TP4, indexer CP yields to the opt-in `indexer_decode_cp`, which keeps a replicated cache. `local_score` prefill and KV connectors (including CPU offload) are not supported with NVFP4 sharding yet. `dspark` is now accepted for sharding.
- **Shared paths:** the C++ insert's `idx_block_size` runs on every M3.1 deployment; the NVFP4 gather kernel now puts pages on grid x, since one sharded staging call can exceed grid y's 65,535 limit, and main's unsharded prefill uses that kernel too; vllm-project/vllm#61929's FP8 scorer epilogue is factored into fold/store helpers shared with the NVFP4 kernel; the Q8KV4 path calls MSA's private `_run_scores`, as main's decode CP does.
