# [SpecDec] Enable adaptive verification for GLM-5.3-Flash KDA

## Overview

Enable adaptive verification (#52228) for `zai-org/GLM-5.3-Flash`: let GLM's CUDA KDA layers and the SM90 sparse MLA builder replay variable-length decode CUDA graphs, following the Kimi-K3 change in #52988.

## Claims

- `enable_adaptive_verification=true` now serves GLM-5.3-Flash with native MTP (K=3), async scheduling and `FULL_AND_PIECEWISE` graphs, even when the device verification schedule differs from the host plan.
- No behavior change for other models, runs or platforms: the GLM KDA backend is selected only when `enable_adaptive_verification` is set, so non-AV GLM runs keep the generic GDN builder and its `update_block_table` metadata reuse. Generic GDN and non-CUDA backend selection are untouched, and the KDA builder keeps `UNIFORM_BATCH` with the existing mixed prefill/decode restrictions.
- Fix a latent host synchronization in the SM90 sparse MLA planner: `plan()` now receives independent pinned metadata snapshots instead of reusable CPU staging buffers.

## Details

Adaptive verification trims each request's verification width on the device, so the host query lengths the scheduler planned may no longer match the device `query_start_loc`. `maybe_create_adaptive_verification_manager` therefore requires two backend opt-ins: accept the host/device mismatch, and report the widest per-request query length a FULL cudagraph can replay. GLM served its KDA layers through the generic GDN backend, which rejects the mismatch, and its `UNIFORM_BATCH` graphs declared no variable-length decode window, so AV could not be enabled.

**KDA** — `Glm5NextLinearAttention.get_attn_backend()` selects `Glm5NextKDAAttentionBackend` on CUDA when `enable_adaptive_verification` is set, and keeps the generic GDN backend otherwise. The subclass is deliberately excluded from `GDNAttentionMetadataBuilder`'s `update_block_table` metadata reuse (`type(self) is GDNAttentionMetadataBuilder`, because KDA checkpoint metadata is per group), so selecting it only for AV leaves the metadata-reuse fast path and the align-mode index precompute unchanged for every other GLM run. The builder inherits all GDN metadata staging unchanged and only adds the two declarations: `supports_device_cpu_query_lens_mismatch() == True` (the recurrent and causal-convolution kernels read device offsets, and `spec_query_start_loc` is already the device tensor for pure decode) and `get_varlen_cudagraph_max_query_len() == num_speculative_tokens + 1`, the width the decode graph is captured at. Non-CUDA platforms keep the generic backend.

**SM90 sparse MLA** — the builder declares the same window since GLM uses this backend on Hopper. The strict `VLLM_GPU_SYNC_CHECK=error` run exposed an unrelated latent sync: `_SM90State.plan()` passed its reusable CPU staging arrays to `plan()` with `non_blocking=True` H2D copies, so the next plan could overwrite a buffer while a copy was in flight. Each replan now passes independent pinned snapshots; the pageable path is unchanged when pinning is unavailable. Snapshot cost is three small pinned tensors per planner refresh, and refreshes are amortized across steps by `_PLAN_SLACK`; PyTorch keeps their storage alive for the async copy.

The bounded decode-graph declarations follow the restriction discussed in #60133. The padded prompt-tail handling fixed by #58434 is already in the base; this PR reuses that behavior.

**Not covered** — the generic GDN backend (e.g. Qwen3-Next) and the `KimiGatedDeltaNetAttention` layers used by Kimi Linear / Alice-AI are intentionally unchanged: their decode paths were not validated here, and enabling the mismatch for every GDN model would be an unsupported claim. Kimi-K3 already has its own KDA declarations (#52988); other KDA layers can opt in with the same two declarations after kernel-level validation.
