# [Core] Let workers report requests whose KV cache was lost

[Upstream PR](https://github.com/vllm-project/vllm/pull/63899) · state: open · merged: False

## Original PR description



## Overview

Part of #63818 (RFC: pluggable PP transport), the "re-prefill" hook. Adds `KVConnectorOutput.lost_kv_req_ids` and `lost_all_kv`, so a worker, connector or executor can report KV that was computed and then lost on some worker (for example a pipeline stage replaced by a replica that does not hold it); the scheduler then recomputes the affected running requests. Independent of the other #63818 PRs (based on main).

## Claims

- With `kv_load_failure_policy=recompute` (and without a KV transfer config) the scheduler preempts the reported running requests with `drop_stale_output=True` (the path `reset_prefix_cache(reset_running_requests=True)` already uses): their in-flight outputs are dropped and they resume with a prefill of all their tokens (with MRV2, as `NewRequestData` carrying all token ids).
- Their blocks (with `lost_all_kv`: all blocks) are evicted from the prefix cache first. Without this the resumed request, or a new request with the same prefix, hits blocks whose KV is missing on that worker, and decodes on a partial context.
- With `kv_load_failure_policy=fail` the requests finish with an error. `KVOutputAggregator` merges both fields across workers.

End to end (with the out-of-process stage PRs of #63818 and the Connex plugin, Llama-3-8B, PP=2 and PP=3, A40, SIGKILL of the active downstream replica under load): 28 kills in total. Under load (14 kills: PP=2 on one host x10, last stage of PP=3 x2, PP=2 with the stages on two hosts x2): 4,448 of 4,448 requests completed, 0 errors, all 32 requests in flight at each kill resumed; the largest gap between two tokens of a request was 0.39-0.71 s per run. During 16-request greedy runs (14 kills): 13 runs completed with 0 tokens off the argmax; in one run (PP=2, one host, 4th kill of a series) all 16 requests hung until the client timeout. It did not reproduce in 15 later kills and its logs were overwritten, so the cause is unknown; it is in the plugin's failover path or in this change, not yet determined. Before the prefix-cache eviction was added, the same kill left 59 tokens off the argmax in 14 of 16 requests, all after the failover point (tokens 82-91), which is how the eviction requirement was found.

## Details

- Why not `invalid_block_ids`: it rewinds a request only to its first invalid block among tokens computed before the current step, keeps the outputs of the current and in-flight steps (with async scheduling / PP several steps are in flight), and under the recompute policy leaves the invalid blocks in the prefix cache. Lost KV needs all three handled.
- Why preemption: it already handles in-flight outputs (stale shares) for async scheduling and PP, and MRV2 resumes preempted requests as new requests with all their tokens, so a worker that never saw the request gets its full context.
- Cost: nothing unless a field is set. On a report, O(running requests) plus an eviction pass over the reported blocks (all blocks for `lost_all_kv`).
- Who sets it: today an executor (the Connex PP executor sets `lost_all_kv` on the first output after it replaced a downstream stage replica). A worker-side connector method can follow if connectors need it; the aggregator already merges the fields.
- Not a duplicate: open PRs on KV load failures (#61769, #53298, #42461) change `invalid_block_ids` handling for connectors; none covers KV lost after it was computed.

With `lost_all_kv=True`, KV-holding waiting requests such as paused streaming sessions retain their block tables and nonzero `num_computed_tokens`. Evicting their prefix-cache hashes does not reset those references, so the next input resumes against KV the replacement worker no longer holds. Recover these requests while preserving their blocked/session state, or finish them with an error under the fail policy.

- copilot-pull-request-reviewer[bot] · comment · 2026-10-27T01:43:36Z · [source](https://github.com/vllm-project/vllm/pull/63899#discussion_r4384313399)

File: `vllm/v1/core/sched/scheduler.py` · line None

Both engine step paths process queued aborts before `update_from_output()`, so a per-request loss report can arrive after its owner has left `running` and its block table has been freed. This comprehension then collects no blocks for that ID, leaving prefix-cache hashes that let later requests reuse missing KV. Retain block identities until in-flight reports are consumed, or conservatively invalidate the cache when a reported owner's blocks can no longer be recovered.

`get_block_ids()` includes HiSparse's separate host pool, but `KVCacheManager.evict_blocks()` interprets every ID in the GPU pool, so a targeted report can evict unrelated GPU blocks or hit the bounds assertion while leaving host-cache entries intact. Confirmed and fixed. `_handle_lost_kv` now also covers requests in `kv_holding_waiting` (when reported by ID, or all of them with `lost_all_kv`). A waiting request that holds computed KV, such as a paused streaming session, has its blocks freed and evicted and `num_computed_tokens` reset to 0, and it moves to the waiting queue in order.
