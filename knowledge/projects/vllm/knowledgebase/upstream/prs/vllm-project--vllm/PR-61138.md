# [Perf][Distributed] Skip movedim+reshape for dim=0 in CudaCommunicator reduce_scatter

[Upstream PR](https://github.com/vllm-project/vllm/pull/61138) · state: open · merged: False

## Original PR description

## Overview

Skip redundant `movedim` + `reshape` tensor view operations when `dim=0` in `cuda_communicator.py`'s `reduce_scatter`.

## Duplicate-work check

Sibling PRs #61136, #61139, #61140 each touch a different function in a different communicator class (`CudaCommunicator.all_gather`, `DeviceCommunicatorBase.all_gather`, `DeviceCommunicatorBase.reduce_scatter`); none overlaps with this diff. `gh pr list --search "movedim"` and `--search "cuda_communicator reduce_scatter"` turned up no other open PR touching this function.

## Performance

Thanks @kunwarshivam for flagging the missing numbers and the call-site question below -- here's what I was able to validate on this host (2x RTX 5090, no access to a larger cluster).

**Isolated microbenchmark** (the exact removed chain -- `movedim(0,0)` + `.contiguous()` on both input and output -- timed with no NCCL call in the region, 2000 reps, warm-started, p10/p90 spread <0.2us across all shapes/devices tested):

| | old (median) | new (median) | delta |
|---|---|---|---|
| reduce_scatter head (input movedim+contiguous) | 1.14-1.35us | 0.13us | ~1.08us |
| reduce_scatter tail (output movedim+contiguous) | 1.14-1.36us | 0.08us | ~1.13us |
| **total** | | | **~2.2us/call** |

**End-to-end** (real NCCL TP=2 on 2x RTX 5090, 100 trials/condition, old/new order alternated, both ranks' times reduced with MAX): the effect is there in direction but mostly inside this host's own call-to-call noise (shared machine, other users' GPU jobs running throughout):

| shape | old median | new median | speedup | old p10-p90 | new p10-p90 |
|---|---|---|---|---|---|
| (2, 4096) | 51.10us | 44.80us | 1.14x | 47-60us | 41-55us |
| (4096, 4096) | 982.78us | 980.21us | 1.003x | 906-1182us | 904-1159us |

**Applicability**: this only saves time in eager execution (prefill, or decode without CUDA graphs). Under CUDA graph capture, a no-op `reshape` on an already-contiguous tensor enqueues no GPU kernel, so captured-graph replay time is unaffected either way.

**Call-site reachability** (answering the second open question): `dim=0` `reduce_scatter` is exercised by the sequence-parallel path in DeepSeek-V2/V3 (`deepseek_v2.py:1401`), Llama4, Qwen3 (MTP/Next MTP), GPT-OSS, and `moe_runner.py`'s PCP path -- this is live production code, not a rarely-hit branch. All current call sites pass an already-contiguous tensor, so the `.contiguous()` safety net you flagged is never exercised as a real copy today; I kept it rather than asserting contiguity, since it's cheap insurance against a future non-contiguous caller.

**Rough extrapolation**: a 60-layer sequence-parallel model doing one `reduce_scatter` per layer during prefill would save on the order of 60 x 2.2us ~= 130us per request from this PR alone.

I don't have 4xGB300 to reproduce this at the scale you offered to help with -- happy to have it independently re-measured there; the isolated-operation numbers above should hold regardless of GPU generation since they're pure CPU-side dispatch overhead.

## Claims

- Eliminates 2 redundant `movedim` + `contiguous` calls per `reduce_scatter(dim=0)` call, measured at ~2.2us/call in isolation (see Performance)

## Validation

- `ruff check` and `ruff format --check`: all passed
- When `dim=0`, `movedim(0, 0)` returns the same tensor — skipping is behavior-preserving
- Isolated and end-to-end microbenchmarks: see Performance section above

## Details

`reduce_scatter` in `cuda_communicator.py` calls `movedim(0, dim)` and `.contiguous()` on both input and output. When `dim=0`, `movedim(0, 0)` is a no-op. Call `.contiguous()` directly and return the output without `movedim` when `dim=0`.

Verified the fast path locally against current main — the input side checks out, and I traced the output side as well since the diff also skips `.contiguous()` on the return:

**Input path (agrees with the PR):** `reduce_scatter` normalizes negative dims at the top (`dim += input_.dim()`), so `dim == 0` also covers the 1-D `dim=-1` case; `movedim(0, 0)` is identity, so `input_.contiguous()` is equivalent to `input_.movedim(0, 0).contiguous()`.

**Return path (worth adding to the PR notes):** with `dim == 0`, `return output` drops the old `output.movedim(0, 0).contiguous()`. I checked all three branches that produce `output` here:
- pynccl: `torch.empty(...)` — dense by construction;
- NVLS symm-mem: `_get_symm_scratch("rs_out", output_shape, ...)` — fresh scratch allocation of exactly `output_shape`;
- batch-invariant (`reduce_scatter_batch_invariant`) — routed around NCCL chunking via reduce + dim-0 narrow, and a first-dim `narrow()` of a contiguous parent is still `is_contiguous()`.

So the fast path is behavior-preserving today. One suggestion (non-blocking): since the dim==0 return no longer has the `.contiguous()` safety net, a short comment stating "outputs from all branches are dense by construction" would protect future branches (e.g., anything returning a strided view like the pooled slices used in `reduce_scatterv_into_output`) from silently losing the guard.

**Two asks per the perf-PR guidance:**
1. Before/after numbers with named GPU/problem size. The claim is host-side overhead (two Python-level view ops per call), so a per-call CPU overhead microbench (e.g., profiler loop outside CUDA-graph capture) is the honest way to show it.
2. Which production call sites hit `reduce_scatter(dim=0)`? The sequence-parallel consumers I traced use dim=0 all-gathers (`all_gather`'s NVLS comment calls this out), while MoE paths use `reduce_scatterv`. Pinning the hot caller would strengthen the motivation.

Happy to run the dim-0 path on 4×GB300 to give you baseline numbers if useful.
