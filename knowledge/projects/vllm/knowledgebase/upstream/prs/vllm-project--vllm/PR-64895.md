# [Bugfix][KV Connector][Mooncake] Coalesce in-flight lease heartbeats

[Upstream PR](https://github.com/vllm-project/vllm/pull/64895) · state: open · merged: False

## Original PR description

## Overview

Coalesce in-flight Mooncake decoder lease heartbeats per producer engine: keep one drain task and at most one latest pending snapshot per remote engine, so a slow bootstrap resolution no longer replays a burst of obsolete renewals.

## Claims

- Bug fix: while a lease renewal is in flight, every scheduler tick used to spawn another send task holding the snapshot captured at that tick. When bootstrap resolution finally completes, all tasks fire concurrently over real sockets, each sending a stale snapshot. Measured on a real-link harness: 15 ticks produced 15 wire frames, with a 9-frame burst within 2.0 ms where each frame carried a different stale snapshot.
- After the fix, the same scenario sends 8 frames: one in-flight send followed by one send of the latest snapshot, then steady cadence. Lease duration, scheduler cadence, wire protocol and public configuration are unchanged.
- Why this is not duplicating an existing PR: duplicate searches (open-PR title sweeps for mooncake heartbeat / lease / coalesce, plus reading the changed-file patches of #64363, #64486, #55763, #55137) found no existing heartbeat-coalescing fix. Nearby lifecycle PRs (#61515, #62657, #62658) address encoder-cache waiters, sender waiters and readiness slots, not lease-heartbeat coalescing.

### Real-link harness (CPU, wire-level)

To validate the changed control plane on real transports without GPUs, a harness runs two `MooncakeConnectorWorker` instances where everything vLLM-side is real — `MooncakeBootstrapServer` HTTP on localhost TCP, worker registration via `httpx`, `zmq.asyncio` ROUTER/DEALER heartbeat sockets over TCP with real asyncio timing — and only the `mooncake-transfer-engine` package is stubbed (memory registration / transfer calls are no-ops; none are on the heartbeat path). Bootstrap `/query` is delayed 8 s by subclassing the bootstrap server; heartbeat frames are counted on the wire by a raw-TCP ZMTP interceptor and cross-checked against the producer-side receive log (identical counts in both runs).

Scenario: `kv_lease_duration=6` (1 s heartbeat interval), 15 scheduler ticks at 1 s cadence through the production entry point `start_load_kv`, tick *i* carrying full snapshot `[xfer-1..xfer-i+1]`.

| | baseline | fixed |
|---|---|---|
| wire heartbeat frames for 15 ticks | 15 | 8 (7 stale sends suppressed) |
| burst at query return | 9 frames in 2.0 ms, each a different stale snapshot (n=1..9) | 2 frames, serialized in 4.6 ms: in-flight snapshot, then the latest snapshot `[xfer-1..xfer-9]` |
| steady state | — | clean 1 s cadence |

Renewals were verified to extend producer-side lease expiry through `_renew_kv_leases` in both runs.

### Not covered

- Native Mooncake RDMA transport and GPU P/D serving E2E were not run; the harness stubs only the engine package, everything else is real.
- No model accuracy evaluation: the change is control-plane only and does not touch token computation.
- Note for maintainers: `tests/v1/kv_connector/mooncake_integration/run_accuracy_test.sh` does not set `kv_lease_duration`, so upstream CI does not currently exercise the lease-heartbeat path at all; adding it to the integration config would close that gap.

## Details

Root cause flow (P = producer, D = decoder):

1. D's scheduler emits metadata with a full pending-transfer snapshot each step; D sends lease heartbeats to P so held KV is not expired (`kv_lease_duration`).
2. The first heartbeat send resolves the P address via bootstrap HTTP `/query`. With a slow bootstrap, that resolution stays pending.
3. Meanwhile each new tick spawns a fresh send task holding that tick's snapshot (the old code created one task per snapshot with no coalescing).
4. When the query returns, all queued tasks proceed concurrently: repeated sockets, duplicate renewals of already-extended transfers, and stale snapshots overwriting newer information on the wire.

The fix keeps, per remote engine, one active drain task and at most one pending snapshot. Because the scheduler emits full snapshots (not incremental deltas), replacing the pending snapshot with the newest one is lossless; new transfer IDs are preserved because the latest snapshot contains them. Tradeoff: renewals are serialized, so under a slow response the newest snapshot waits for the in-flight send to finish (bounded by the existing response timeout); lease headroom under extreme delay should be confirmed in real PD serving. Timeout and error handling are unchanged.
