# [Bugfix] Don't bound beam search's search width by `max_logprobs`

[Upstream PR](https://github.com/vllm-project/vllm/pull/63803) · state: open · merged: False

## Original PR description

# [Bugfix] Don't bound beam search's search width by `max_logprobs`

## Summary

With the default config, `beam_width` above 10 fails:

```
VLLMValidationError: Requested sample logprobs of 40, which is greater than max allowed: 20
```

The caller set `beam_width`, not `logprobs`, and the number 40 appears nowhere in their request. Beam search asks the engine for `2 * beam_width` candidates per step to expand its beams, and that request was validated against `max_logprobs` -- which bounds what a *client* may be returned.

This separates the two: the search request is bounded by the vocabulary size, while what each returned beam carries is trimmed to `max_logprobs`. **`max_logprobs` still caps what you get back; it no longer caps how widely beam search searches.**

> **Independent of #63525.** That PR forwards `extra_args` on the same code path, so the two touch adjacent lines, but neither depends on the other and they can be reviewed and merged in either order. Whichever lands second needs a trivial rebase.

## Motivation

`ModelConfig.max_logprobs` is documented as "Maximum number of log probabilities to **return** when `logprobs` is specified in `SamplingParams`", with a default of 20 inherited from the OpenAI Chat Completions API. It is an API-surface limit, and it appears nowhere except `SamplingParams._validate_logprobs` and one response-side check on returned `top_logprobs`.

It is not, however, irrelevant to beam search, which is what makes this more than a one-line exemption. Every returned beam carries its per-step logprobs, and that mapping held all `2 * beam_width` candidates. Measured on an A10G with `facebook/opt-125m`, `max_logprobs=20`:

| beam_width | entries per step on each returned beam |
|---|---|
| 2 | 4 |
| 5 | 10 |
| 10 | 20 |

So at width 11 a caller really would have received 22 entries per step, which is exactly what the cap forbids. Exempting the request alone would have let returned output grow past the cap.

Hit while benchmarking beam search for generative retrieval, where the beam width is the number of results requested.

## Approach

Mark the engine's request as internal and bound it by the vocabulary size; trim what is stored on each beam.

Two details the trimming has to get right, both of which cost me a review round:

* **The beam's own chosen token is kept even when it ranked below the cap.** A plain "top `cap`" drops it for any beam whose token ranked low, leaving that beam describing a step that does not mention the token it took.
* **Each beam gets a fresh mapping.** Every sibling expanded from one parent previously shared a single candidate dict, so trimming in place would corrupt the siblings.

`max_logprobs` of 0 is legal (`ge=-1`) and means nothing may be returned, so it yields an empty mapping.

### What I did not do

`logprobs_are_internal` is a field on `SamplingParams`. A reviewer argued for a fully separate internal channel that never touches `SamplingParams`, on the grounds that this is a public bypass of a generic validator. I went with the field because `skip_clone` is already an internal-only field in the same struct, set by beam search itself, and because the OpenAI layer builds `SamplingParams` from an explicit field allowlist, so a REST client cannot set it. A direct Python caller still can, which widens only how far the sampler's top-k looks -- what is returned stays capped wherever beams are built.

If maintainers prefer the separate channel, say so and I will do that plumbing instead; I did not want to decide it unilaterally inside someone else's validator.

## Changes

- `vllm/sampling_params.py` -- `logprobs_are_internal` field; `_validate_logprobs` bounds the **sample**-logprobs branch by `get_vocab_size()` when it is set. The prompt-side caps (`prompt_logprobs`, `prompt_logprob_token_ids`) are deliberately untouched.
- `vllm/entrypoints/generate/beam_search/utils.py` -- `trim_step_logprobs()`; `validate_beam_width_logprobs` becomes `validate_beam_width`, reporting only a top-k wider than the vocabulary.
- `vllm/entrypoints/generate/beam_search/offline.py` -- set the flag, trim at the store site.
- `vllm/entrypoints/generate/beam_search/online.py` -- same, at both store sites.
- `tests/v1/sample/test_logprobs.py` -- 3 tests.

Note `validate_beam_width`'s check is reachable only for a small-vocabulary model: `beam_width` is separately capped at `VLLM_MAX_N_SEQUENCES` (16384) by `BeamSearchParams.__post_init__`, so `2 * beam_width` tops out at 32768. A 32k-vocabulary model is within that; `opt-125m` at 50272 is not.

## Test Plan

```
pytest -v tests/v1/sample/test_logprobs.py::test_trim_step_logprobs_keeps_the_beams_own_token \
          tests/v1/sample/test_logprobs.py::test_validate_beam_width_rejects_top_k_wider_than_vocab \
          tests/v1/sample/test_logprobs.py::test_beam_width_is_not_bounded_by_max_logprobs
```

- The trim unit test asserts the worst-ranked beam keeps its own token, that the shared parent mapping is neither mutated nor aliased, and covers `cap` of 0, 1 and above the candidate count. It carries a **negative control** asserting that the naive top-k rule would have failed it.
- The width test runs `beam_width=8` at `max_logprobs=4` -- previously rejected -- and asserts every returned step holds at most 4 entries **and contains the token that beam took**. It also asserts a client's own `logprobs=8` and `prompt_logprobs=8` are still rejected.
- The boundary test drives `validate_beam_width` against a stub config at vocabulary 32000: 16000 silent, 16001 raises.

## Test Result

A10G, vLLM at `c50aca1441`:

```
tests/v1/sample/test_logprobs.py::test_trim_step_logprobs_keeps_the_beams_own_token PASSED
tests/v1/sample/test_logprobs.py::test_validate_beam_width_rejects_top_k_wider_than_vocab PASSED
tests/v1/sample/test_logprobs.py::test_beam_width_is_not_bounded_by_max_logprobs PASSED
```

Before this change, on the same hardware and model at the default `max_logprobs=20`:

```
width=10: OK
width=11: ValueError: beam_width=11 needs 22 internal logprobs per step, which exceeds max_logprobs=20
width=20: ValueError: beam_width=20 needs 40 internal logprobs per step, which exceeds max_logprobs=20
width=64: ValueError: beam_width=64 needs 128 internal logprobs per step, which exceeds max_logprobs=20
```

**Wins:** `beam_width` is no longer limited to 10 by a cap on returned data; the returned cap is still honoured at any width; the per-beam aliasing of one shared candidate dict is fixed as a side effect.

**Cost (honest tradeoff):** this changes behaviour. Requests that used to be rejected now run, which wants a release note. No request that works today changes, though: it only succeeded if `2 * beam_width <= max_logprobs`, and trimming returns the mapping unchanged whenever the candidate count is within the cap. Trimming is also a returned-data change in its own right: at width above 10 a caller now receives capped dicts where previously the request failed outright. I think that is strictly better, but it is a judgement call.

**Not verified:** vLLM's own beam-search suite (`tests/samplers/test_beam_search*.py`) has not been run -- it needs an engine and I have had a single-GPU box. The online path's trimming is exercised by no test here; its beams are built the same way as offline's, but I have not run a server. I would rather flag that than imply coverage I did not produce.
