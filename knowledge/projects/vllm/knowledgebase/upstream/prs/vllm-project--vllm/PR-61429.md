# [Perf][Spec Decode] Faster vocab top-k when flashinfer is unavailable (Triton, aiter topk_plain on ROCm)

[Upstream PR](https://github.com/vllm-project/vllm/pull/61429) · state: open · merged: False

## Original PR description

## Overview

`LogitsProcessor.get_top_k_tokens` is used by the DFlash2 / LiLiCorr candidate heads. Without flashinfer's radix top-k (e.g. on ROCm) it falls back to `torch.topk` over the full vocabulary, which is slow. This PR adds two faster paths:

1. **aiter `topk_plain`.** Used when `VLLM_ROCM_USE_AITER=1` and the installed aiter has the multi-block fix from [ROCm/aiter#6586](https://github.com/ROCm/aiter/pull/6586). vLLM detects that fix by probing for `topk_plain_merge_workspace_size`.
2. **Triton.** An exact two-stage top-k, used otherwise.

`torch.topk` still handles shapes neither path supports. Where flashinfer is available, it keeps priority.

## Claims

- **Triton:** 4.7–9.6× faster than `torch.topk` over a 248,320-column vocabulary with k=16 on MI355X, in bf16 and fp32. Results match a stable descending sort exactly, with ties resolved to the lowest index.
- **aiter `topk_plain`** (with ROCm/aiter#6586):
  - Level with Triton at 32 rows, and 1.4–2.4× faster than Triton from 112 rows up: 11–13× faster than `torch.topk` at 448–1792 rows.
  - At 7 rows it is about 5 µs slower than Triton.
  - Values match a sort exactly. Ties may resolve to any tied index.
- **End to end**, all three paths are within run-to-run noise on Qwen3.8-27B + DFlash2 at concurrency 1–128 (see below). Both target and draft run in full CUDA graphs, with the top-k inside the draft graph. Even `torch.topk` is only 0.4–0.6% of a step here (about 1.05 ms of 181 ms at C=128, which is 896 rows), so the best possible end-to-end gain is about 0.5%, below the noise.

## Details

**Triton algorithm.**
- **Stage 1.** Each program takes one 4096-column chunk of a row. It computes the maxima of the chunk's 16-column groups and keeps the k groups with the largest maxima; any element of the chunk's top k lies in one of those groups. It then selects the chunk's top k from those 16k candidates.
- **Stage 2.** A second kernel merges the per-chunk candidates of each row.
- **Ordering.** Values and indices are packed into order-preserving int64 keys, so one `tl.topk` over the keys orders by value, then by lowest index. NaN orders above +inf, as in `torch.topk`.

**aiter path.**
- **Op.** `rocm_aiter_ops.vocab_top_k` wraps `topk_plain` as the custom op `rocm_aiter_topk_plain`.
- **Supported shapes** (`supports_vocab_top_k`): contiguous 2-D fp16/bf16/fp32 rows with at least 4096 columns, and k ≤ 128. Above k=128, aiter returns fp32 rows of up to 8192 columns unsorted.
- **Index dtype.** It returns int32 ids, which `get_top_k_tokens` already widens to int64. The TP>1 re-selection over `k * tp` gathered values is narrow, so it uses `torch.topk`.
- **Why the aiter fix is required.** Without it, `topk_plain` returns duplicate fp16/bf16 ids once a row is split across several blocks, which is the decode case here. Its multi-block path also cannot be captured in a CUDA graph. The probe keeps such aiter versions on the Triton path.
- **Determinism.** Unlike Triton, aiter does not resolve ties to the lowest index, and the tie choice can depend on the number of rows. With bf16 logits, exact ties in the top 16 are possible. They pick a different but equally scored candidate. Acceptance length is unchanged above.

**Possible follow-up.** Triton is faster up to about 32 rows, which covers concurrency ≤ 4 with 7 draft tokens. A row threshold could send those batches to Triton. It is left out because the end-to-end difference is in the noise.

**Kernel microbenchmark.** Run this with both diffs and the aiter PR applied, and with `VLLM_ROCM_USE_AITER=1`. It times the three `_topk` paths in CUDA graphs and checks that the values match.

```python
import torch

from vllm._aiter_ops import rocm_aiter_ops
from vllm.kernels.triton.topk import triton_topk

V, K, N = 248320, 16, 20
impls = {
    "torch.topk": lambda x: torch.topk(x, K, dim=-1),
    "triton": lambda x: triton_topk(x, K),
    "aiter": lambda x: rocm_aiter_ops.vocab_top_k(x, K),
}
assert rocm_aiter_ops.is_vocab_top_k_enabled()
for dtype in (torch.bfloat16, torch.float32):
    for rows in (7, 32, 112, 448, 1792):
        x = torch.randn(rows, V, device="cuda", dtype=dtype)
        ref = torch.topk(x, K).values
        times = {}
        for name, fn in impls.items():
            assert torch.equal(fn(x)[0], ref)
            g = torch.cuda.CUDAGraph()
            with torch.cuda.graph(g):
                for _ in range(N):
                    fn(x)
            best = float("inf")
            for _ in range(15):
                b = torch.cuda.Event(enable_timing=True)
                e = torch.cuda.Event(enable_timing=True)
                b.record(); g.replay(); e.record(); torch.cuda.synchronize()
                best = min(best, b.elapsed_time(e) * 1e3 / N)
            times[name] = best
        print(rows, dtype, {n: round(t, 1) for n, t in times.items()})
```
