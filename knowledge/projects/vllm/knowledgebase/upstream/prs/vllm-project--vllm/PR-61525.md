# [Frontend] Accept `--reasoning-parser none` as the unset default

[Upstream PR](https://github.com/vllm-project/vllm/pull/61525) · state: closed · merged: True

## Original PR description



## Overview

`vllm serve --reasoning-parser none` (any case) now disables reasoning parsing instead of raising `KeyError`, matching `vllm-rs serve --reasoning-parser none`. Follows the per-launcher parser semantics from #46359.

## Claims

- `--reasoning-parser none` / `None` / `NONE` parses to the unset default (`""`) on every Python entrypoint, instead of failing at engine config with `KeyError: "Reasoning parser 'none' not found. Available parsers: ..."`.
- Under `VLLM_USE_RUST_FRONTEND=1`, the normalized value is the argparse default, so it is not forwarded to the bootstrapped Rust frontend, which keeps its `none` default (#46359).
- Named parsers are unchanged.

## Validation

- `pytest tests/entrypoints/launchers/test_cli_args.py`: 64 passed. The new parametrized test fails on `main` with `assert 'none' == ''` for each `none` spelling.
- CLI → engine config → Rust bootstrap, through the real `make_arg_parser`:

  | `--reasoning-parser` | `EngineArgs` | `StructuredOutputsConfig` | forwarded to Rust frontend |
  |---|---|---|---|
  | `none` | `''` | `''` | not forwarded (Rust keeps `none`) |
  | `NONE` | `''` | `''` | not forwarded |
  | `deepseek_v41` | `deepseek_v41` | `deepseek_v41` | `deepseek_v41` |

- `pre-commit run --files <changed>`: all hooks pass, including mypy for the oldest supported Python.

## Details

**Root cause.** The Rust frontend's `ParserSelection` accepts `auto | none | <name>`, case-insensitively. `vllm-rs serve` defaults to `auto`, and `none` is the only way to turn parsing off. Python's `--reasoning-parser` is a plain string that `ReasoningParserManager` looks up by exact name, so Python has no way to spell "disabled" other than omitting the flag. A launcher that starts some workers with `vllm-rs serve` and others with Python `vllm serve` therefore cannot share one setting that disables the parser. Multi-node hybrid-DP currently has to go through the Python-supervised Rust frontend. We hit this in Dynamo + vLLM disaggregated deployments, which need vLLM's own reasoning parser off: single-node prefill (`vllm-rs serve`) required `none`, while multi-node decode (`VLLM_USE_RUST_FRONTEND=1 vllm serve`) crashed on it.

**Design.** Normalization happens in the `--reasoning-parser` argparse `type`. That single point covers `EngineArgs`, `StructuredOutputsConfig`, `ReasoningConfig`, entrypoints that read `args.reasoning_parser` directly, and the Rust bootstrap, which only forwards non-default args.

**Limitations.**
- `none` means "unset", so model defaults for an unset parser still apply (gpt-oss → `openai_gptoss`). That is what the engine already receives under `vllm-rs serve --reasoning-parser none`, which forwards no parser to Python.
- `--structured-outputs-config '{"reasoning_parser": "none"}'` and programmatic `EngineArgs(reasoning_parser="none")` are not normalized.
- `auto` stays unsupported in Python. Supporting it would mean Python resolving parsers from model IDs, which only Rust does today.

**Not a duplicate.** I searched open vLLM PRs and issues for `reasoning-parser none` and `reasoning parser none` / Rust frontend; none address CLI parsing of `none`.
