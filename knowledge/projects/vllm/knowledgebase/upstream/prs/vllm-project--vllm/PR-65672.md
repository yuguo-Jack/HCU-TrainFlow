# [Bugfix][Mooncake] Make early prefill abort cleanup idempotent

[Upstream PR](https://github.com/vllm-project/vllm/pull/65672) · state: open · merged: False

## Original PR description

## Overview

Make Mooncake prefill abort cleanup idempotent when the producer worker has no send record yet, so one missing record does not stop cleanup of the rest of the batch. This is separate from #50565, which handles a Decode-side stale receive completion after an early abort.

## Claims

- An abort that reaches `record_send_reqs` before a transfer record exists, or after that record was already removed, no longer raises `KeyError`.
- Records that are present keep the existing assertion that `ready` is not set. Cleanup does not cancel or drain an in-flight Mooncake transfer.

## Validation

Rebased onto `main` (`59519ec0ee`). CPU connector tests, using the cached `facebook/opt-125m` config with `HF_HUB_OFFLINE=1`:

```bash
.venv/bin/python -m pytest tests/v1/kv_connector/unit/test_mooncake_connector.py tests/v1/kv_connector/unit/test_mooncake_connector_hma.py -m cpu_test -q
```

Result: **12 passed, 159 deselected**.

`test_prefill_early_abort_cleanup_is_idempotent` builds the abort metadata through the real scheduler (`add_request` → `finish_requests(FINISHED_ABORTED)` → `schedule`) and passes it to the real worker `record_send_reqs`. It covers a missing record, a second cleanup of an existing record, and a batch where the missing id is ahead of an existing one. Each case repeats the same metadata and checks that the aborted records are gone, an unrelated record remains, and `finished_sending` stays empty. No GPU, RDMA, or server run; the change does not alter transfer bytes.

## Details

On the prefill scheduler, a request that finishes for a reason other than `FINISHED_LENGTH_CAPPED` is added to `reqs_not_processed` and is not queued for send. The worker then does `reqs_need_send.pop(transfer_id)`. That record is created only after allocation metadata arrives, so an abort before that point, or a repeated abort after the first pop, raises `KeyError` and skips later ids in the same batch.

`pop(transfer_id, None)` treats a missing record as already removed. If a record is present, it still must not be `ready`. Sending counters are unchanged, and this does not reclaim unknown transfer placeholders or cancel an active transfer.
