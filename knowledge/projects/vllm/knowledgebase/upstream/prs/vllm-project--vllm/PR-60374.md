# [Bugfix][KV Offload][P2P] Report NIXL submission failures and escalate persistent faults to session teardown

[Upstream PR](https://github.com/vllm-project/vllm/pull/60374) · state: closed · merged: True

## Original PR description

## Overview

This PR fixes two P2P data-plane failures and adds a reconnect backoff. Each part is its own commit (the backoff plus a follow-up that counts faults in its log, then a commit addressing review), so they can be reviewed, or split, independently:

1. **Submission failures are reported to the fetching peer** (fixes #60204). A NIXL error raised while submitting a fetch's WRITE escaped to the session dispatcher, so the peer waited its full 30 s load timeout before recomputing.
2. **Persistent NIXL faults end the session** (fixes #60205 together with #60279). A peer with a stale NIXL registration but a healthy control plane failed every WRITE for the rest of the process. This also answers @snadampal's review question on this PR about recovering the peer instead of fast-failing forever.
3. **Reconnect backoff.** A peer that faults again right after each re-handshake backs off before the next reconnect, as the NixlConnector does for invalid peers.

#61500 independently traces the same root cause in NIXL 1.5.0 for the NixlConnector's pull path: after one `REMOTE_DISCONNECT`, the UCX endpoint stays `FAILED` until the remote agent is re-added. Its production numbers show the before/after effect.

Replaces #55553 (closed in favour of this, by @Etelis). Together with #60279 it covers #55181.

## Claims

**Commit 1 (transfer scope)**
- An error from `make_prepped_xfer` / `transfer` takes the existing fail-fast path. The round fails, the peer gets `TransferDoneMsg(success=False)`, the store job fails at once, and the created handle is released.
- `transfer()` returning `"ERR"` (how the bindings report a failed post) is a failed submission. Previously it was ignored and the handle parked inflight.
- `on_fetch` no longer finalizes a round a second time after a failed submission. That raised `KeyError` in the store-first and finish-before-fetch orderings.

**Commit 2 (escalation)**
- `NixlTransport` classifies each NIXL failure in one place:
  - `nixlRemoteDisconnectError` / `nixlNotFoundError` fault the peer at once.
  - A `check_xfer_state` that raises faults the peer at once (commit 5). NIXL's binding raises for every error status (only `SUCCESS` / `IN_PROG` are returned), so a raise is how a failed WRITE is reported, e.g. `nixlBackendError` for a UCX error.
  - Any other failure (a failed submission, or a transfer in state `"ERR"`) is a strike, and 3 consecutive strikes with no success between them fault the peer. Strikes from one `poll()` batch are applied after the batch is classified, so a `DONE` for the peer anywhere in it counts as the success between (commit 5).
  - Only `nixlRemoteDisconnectError` ends a transfer whose state check raised. Any other raise keeps it inflight, because its WRITE may still be landing (#59790 measured bytes landing while the handle raised `nixlNotFoundError`); the peer fault and the drain cap below bound it.
  - The fault is reported through a new `PollResult.peer_fault`.
- After a fault, no new WRITE goes to that peer. Once its inflight WRITEs drain (capped at 10 s), the session sends `DisconnectMsg`. The existing reap then tears down both sides, and the next request re-registers them.
- Every session death records a reason, and the manager's `peer X down (<reason>)` log reports it. Examples: `data plane: NIXL_ERR_REMOTE_DISCONNECT`, `protocol error: …`, `handshake timed out`, `lookup response timed out`, `control connection lost`.

**Commits 3–4 (reconnect backoff)**
- After reaping a session that ended on a data-plane fault, the faulting side records a per-peer backoff. The first fault reconnects at once. A repeat fault within 60 s of the previous wait expiring doubles the wait, from 1 s up to 60 s, as in the NixlConnector (#55471, #61500). Expiry is by time alone: no successful transfer is required, so a peer that is only idle for 60 s starts over at an immediate reconnect. Control-plane deaths don't back off.
- During the wait, outbound connects to the peer are skipped, so lookups fall back to local prefill. An inbound connect from the peer gets `DisconnectMsg` and is closed, so the peer falls back at once instead of waiting for its handshake deadline. There is no protocol change.
- The peer-down log carries a per-peer lifetime count of data-plane faults, e.g. `peer X down (data plane: …); data-plane fault #7; reconnect backoff 8s`. Unlike the backoff it never expires, so a peer that keeps faulting under traffic too sparse to escalate shows up as a rising count rather than as a series of unrelated faults.

## Details

**Root cause (commit 1).** `_submit_transfer` fails fast only when `write_blocks` *returns* `None`. `NixlTransport.write_blocks` caught nothing, so a NIXL error reached `P2PSession._on_message`, which only logs. The dispatcher's disconnect-after-5-errors guard doesn't fire either, because successful messages in between reset its counter.

**Root cause (commit 2).** Only control-plane signals can mark a peer dead: heartbeat, protocol error, handshake, registration, and lookup timeout (#56836). Data-plane failures were never an input. In #60205 the heartbeats and lookups stay healthy while NIXL's endpoints for the peer are stale.

**Flow after a persistent fault (prefiller P writes into decoder D):**
1. D sends `FetchMsg`. P's `write_blocks` fails, or `check_xfer_state` raises in `poll`. The round fails with `TransferDone(False)` and D recomputes.
2. After 3 strikes, or one decisive error, P's `poll(D)` returns `peer_fault`. P's server role stops submitting, so later fetches from D fail fast.
3. Once P's inflight WRITEs to D drain, P sends `DisconnectMsg` and marks the connection dead with reason `data plane: …`.
4. P's manager reaps the session: it fails its jobs and calls `remove_remote_peer(D)`. D receives `DisconnectMsg` and runs the same reap for P.
5. D's next request opens a new connection, `ConnectMsg` goes both ways, and both sides register fresh. The registration generation keeps a late async registration from reviving the old peer.

**Design choice: one death path.** A data-plane fault ends a peer the same way a control-plane fault does. The transport never re-registers a peer in place. The alternative was `remove_remote_peer` after N failures, inside the transport. That tears down only one side: the session still believes the peer is registered, and the peer keeps *our* stale registration. It also cannot work for a restarted peer. Reusing the reap means no new teardown code.

**Tradeoffs and limitations.**
- A `check_xfer_state` that raises with anything but `REMOTE_DISCONNECT` stays inflight, as #59790 established: it isn't provably terminal, and its WRITE may still be landing. It faults the peer at once, so the session's 10 s drain cap bounds how long it can last. The cost is that one failed state check tears down a peer that is otherwise working (a re-handshake, plus the backoff if it repeats). Treating `nixlBackendError` / `nixlCancelledError` as terminal (the UCX request finished with an error) would avoid the drain wait, but needs evidence that NIXL's UCX backend reports a handle's error only once all of its requests are done; left for a follow-up.
- The disconnect waits for inflight WRITEs because D frees their destination blocks on `DisconnectMsg`. The 10 s cap trades that guarantee for not hanging on a stuck transfer, the same exposure a heartbeat death has today.
- The thresholds (3 strikes, 10 s drain, 1→60 s backoff) are conservative constants, not measured values. The backoff uses the NixlConnector's numbers.
- The backoff forgets a peer by time, not by a successful transfer, matching the NixlConnector. Under sparse traffic a persistently broken peer therefore cycles at a 0 s backoff (3 fast-failing requests that recompute locally, plus one re-registration per cycle); the fault count in the log makes that visible. Requiring a success before forgetting would close the gap but needs a transport→manager success signal, and is better done for both connectors together.
- Only the faulting side knows about the backoff. During the wait, the other peer still tries to connect on each new request and is turned away within one round trip; concurrent requests share the pending attempt. A retry-after hint in `DisconnectMsg` would remove that, at the cost of a protocol change.

**Relation to other PRs.**
- #59790 (merged) provides the sibling drain before `TransferDone(False)`; this PR builds on it.
- #60279 (narrowed to `remove_remote_peer` teardown robustness) is complementary. Expect a one-line conflict in `remove_remote_peer` for whichever lands second.
- #61500 (NixlConnector, pull mode) releases a peer after a failed read, with the same backoff. It touches no shared code. That connector's teardown is one-sided because only the decoder holds the remote registration; P2P registers both ways, so here both sides tear down.
- #49632 marks any `check_xfer_state` raise as failed and releases the handle, which can free a handle whose WRITE is still landing. Here such a transfer stays inflight and is bounded by the escalation instead.

Agreed, fixed in 7bb0f96fb5. `poll()` now classifies the whole batch before touching strikes. A `DONE` for the peer anywhere in the batch resets its strikes, then the batch's failures count. `poll()` observes completions, not the order they happened in, so iteration order no longer decides the outcome. `test_success_in_the_same_batch_prevents_the_fault` is your scenario (strikes=2, the `ERR` iterated first, three `DONE`s); it fails on the previous code.

One deliberate edge: a batch with 3 or more failures still faults the peer even when it also holds a `DONE` (`test_batch_of_failures_still_faults_despite_a_success`). Order inside a batch can't be told, and three failures at once is enough on its own.

While checking this I found that with NIXL 1.5.0 a failed WRITE never shows up as the `"ERR"` state. The binding's `getXferStatus` calls `throw_nixl_exception` on every error status, so the failure arrives as an exception (`nixlBackendError` for a UCX error). Those raises are now decisive (see the other thread), so in practice strikes come from failed submissions, and this fix keeps `poll()` consistent with the contract in `data/base.py` for transports that do report `"ERR"`.

Thanks, the symptom is real, but I fixed it differently, because making `NOT_FOUND` terminal reopens the hazard #59790 closed. #59790 measured a 512 MiB WRITE that kept landing after `remove_remote_agent` while its handle raised `nixlNotFoundError` (5/5 runs). If `NOT_FOUND` ends the transfer, the round fails with `TransferDone(False)` and D may reuse the destination blocks while those bytes are still arriving: silent KV corruption for another request. The 10 s drain is what gives such a WRITE time to land, so I'd rather keep it.

What 7bb0f96fb5 does:
- **Log spam:** a state check that keeps raising warns once, then logs at debug (`test_raising_state_check_warns_once`).
- **`NOT_FOUND`:** still faults the peer at once and stays inflight. The session disconnects when the transfer drains or at the 10 s cap (`test_not_found_state_check_keeps_the_transfer`, `test_not_found_in_cancel_keeps_the_transfer`).
- **A related gap this led me to:** the binding raises for every NIXL error status (`getXferStatus` → `throw_nixl_exception`; only `SUCCESS` and `IN_PROG` are returned). So any other raise, most commonly `nixlBackendError` for a UCX transport error, used to cost one strike and stay inflight. Successes to the same peer kept resetting that strike, so the transfer never drained. Its round stalled the consumer for about 40 s (load timeout plus abort-ack timeout), and its pins, handle and session were held for good. Now any raise faults the peer, so it's bounded by the same drain cap (`test_raising_state_check_faults_the_peer_and_keeps_the_transfer`, `test_raise_faults_despite_a_success_in_the_batch`). Only `nixlRemoteDisconnectError` still ends the transfer, as in #59790.

The cost is that one failed state check tears down a peer that is otherwise working: a re-handshake, plus the reconnect backoff if it repeats. The alternatives are a pin leak or a possible corruption, so that seemed the right side to err on. Making `BACKEND` / `CANCELED` terminal (the UCX request finished with an error) is plausible, but I couldn't confirm from NIXL's UCX backend that a handle reports an error only once all of its requests are done. I've left that for a follow-up with evidence.
