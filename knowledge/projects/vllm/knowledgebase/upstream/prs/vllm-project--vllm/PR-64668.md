# [1/2][MRV2] Remove the dependency of MRV2 DBO from MRV1

[Upstream PR](https://github.com/vllm-project/vllm/pull/64668) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->
Removing MRV1 (#63373) from under MRV2 DBO is two PRs:

-> #64668 [1/2][MRV2] Remove the dependency of MRV2 DBO from MRV1
   #64718 [2/2][MRV2] Abort sibling microbatches when one fails

## Overview

Make MRV2 DBO independent of MRV1. MRV2 DBO no longer references anything that #63373 (Remove MRV1) deletes. The DBO helpers that both runners share move unchanged into one runner-agnostic MRV2 module, so a future runner can reuse them as-is.

## Claims

- **No MRV1 code in MRV2 DBO.** `create_ubatch_slices` computes the padded slices itself instead of calling V1's `maybe_create_ubatch_slices` and then clamping the result. Output is unchanged.
- **Shared helpers have one home.** `UBatchSlice`/`UBatchSlices`, the SM control context, `get_num_ubatches` and `check_ubatch_thresholds` move verbatim to `vllm/v1/worker/gpu/ubatch_common.py`, along with the slice computation (`compute_ubatch_slices`). MRV2 and `forward_context` import them from there. `vllm/v1/worker/ubatch_utils.py` re-exports them for the V1 runner, so each symbol still has exactly one definition and V1 code is untouched.
- **Tests no longer depend on V1.** The MRV2 slicing tests pin the same five layouts to explicit values instead of using V1's `split_attn_metadata` as an oracle. The integer-bounds check in `test_ubatch_offsets.py` now covers the shared `compute_ubatch_slices`, with padding. The V1 `UBatchWrapper` test moves unchanged to `tests/v1/worker/test_gpu_ubatch_wrapper.py`, so MRV1 removal can delete it on its own. Only the V1 runner and the V1 test `test_attention_splitting.py` still call V1's `maybe_create_ubatch_slices`.

## Details

**Why move instead of copy:** two copies of `UBatchSlice` would be distinct types, and mypy would reject MRV2 passing its slices into `forward_context`. The SM control code also still receives backend fixes (for example `comm_sms=0` for ROCm DeepEP HT), and a copy would drift.

**Why the module lives in `gpu/` but stays runner-agnostic:** it imports only config, platform and utility modules. `forward_context` and the V1 runner can import it without a cycle, and a later runner can import it directly or take the file as-is.

**Deliberately unchanged:**
- `vllm/v1/worker/ubatching.py` — the `dbo_*` handoff protocol that MoE prepare/finalize, model layers and the workspace call. It holds process-global state, so it must stay a single module, and #63373 keeps it.
- `skip_dp_coordination` in `vllm/v1/worker/dp_utils.py` — a `ContextVar` that elastic EP sets. A copy would be a separate flag that MRV2 never sees set. It is DP coordination, not DBO.
- `maybe_create_ubatch_slices`, `_pad_out_ubatch_slices`, `is_last_ubatch_empty` and `split_attn_metadata` — after this PR only V1 uses them, so they go away with MRV1.

**Interaction with #63373:** both PRs edit the top import block of `vllm/v1/worker/ubatch_utils.py`, so they conflict textually there. #63373 drops the `CommonAttentionMetadata` import, and this PR replaces the block with the re-export. The resolution is to keep the re-export and drop that import together with the three functions #63373 deletes; the simulation above used exactly this. #63373's `test_attention_splitting.py` still imports the functions it deletes; that V1 test needs updating or deleting there, independently of this PR.

**Config gate (unchanged here):** on main, a DBO config with a feature MRV2 lacks (`_get_dbo_unsupported_features`: LoRA, hybrid, PP, CP, pure PIECEWISE, …) silently falls back to MRV1. At #63373's head the same check raises `ValueError`. This PR changes neither behavior.

**Not a duplicate:** open-PR searches for `ubatch_utils` and "model runner V1 DBO" found nothing similar. #63373 removes MRV1 itself and leaves this call, the test oracle and the shared block in place.
