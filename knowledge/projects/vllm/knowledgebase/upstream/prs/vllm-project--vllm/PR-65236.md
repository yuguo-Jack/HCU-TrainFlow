# [Spec Decode] Support draft_lm_head_quantization for DFlash

[Upstream PR](https://github.com/vllm-project/vllm/pull/65236) · state: open · merged: False

## Original PR description

**Purpose**
`draft_lm_head_quantization` gives the drafter an online-quantized copy of the target `lm_head` it shares. Until now only EAGLE and MTP could use it. This PR lets DFlash use it too: `load_dflash_model` applies `quantized_lm_head_copy` the same way `load_eagle_model` does. The target still verifies with its own head, so greedy outputs are unchanged and only the acceptance length can move.
The draft's `lm_head` is large when the vocabulary is large. With Qwen3.6-35B-A3B + DFlash2 (248k vocab) on CPU, it takes about 6 ms of a ~120 ms speculative step. On Xeon without AMX-FP8, `"fp8"` selects `CPUFp8ChannelWiseScaledMMLinearKernel` (AMX, FP8 weights, BF16 activations), which streams half the bytes.

**Test Plan**
- New `dflash-fp8-lm-head` case in `test_v2_speculator_smoke` (`tests/v1/e2e/test_cpu_spec_decode.py`).
- E2E on Xeon 6985P-C (24 cores, 23 OMP threads): Qwen/Qwen3.6-35B-A3B bf16 with incoai/Qwen3.6-35B-A3B-DFlash2 and `num_speculative_tokens=7`. HumanEval, concurrency 1, 20 prompts, 128 output tokens, temperature 0. Runs interleaved bf16/fp8/bf16/fp8.

**Test Result**
`pytest tests/v1/e2e/test_cpu_spec_decode.py -k dflash`: 2 passed.

| Draft lm_head | Median ITL (ms) | Mean TPOT (ms) | Acceptance length |
|---|---|---|---|
| bf16 | 128.81 / 128.27 / 128.39 | 23.42 / 23.29 / 23.33 | 5.58 / 5.60 / 5.58 |
| fp8 | 126.65 / 126.58 / 126.60 | 23.17 / 23.16 / 23.17 | 5.55 / 5.55 / 5.55 |

- gordan12 · comment · 2026-11-03T16:25:55Z · [source](https://github.com/vllm-project/vllm/pull/65236#issuecomment-6609490345)

Read through this. The refactor onto `share_target_lm_head` keeps the old
DFlash sharing condition, and the option reaches the right subclasses:
DFlash2 inherits it (its candidate top-k also goes through the quantized
head, which your DFlash2 AL numbers cover), XPress overrides
`supported_options`, and opting LiLiCorr out is needed since it reinstalls
the target head and requires a `VocabParallelEmbedding`.
`refresh_quantized_lm_heads` in the MRV2 runner covers the DFlash draft too.

Since the new case only runs in the CPU suite, I checked the CUDA path on
1x H200: Qwen/Qwen3-8B + z-lab/Qwen3-8B-DFlash-b16, MRV2,
num_speculative_tokens=15, max_num_seqs=1, greedy, first 64 GSM8K test
questions (chat, no thinking), max_tokens=256, runs interleaved. The fp8
copy picks `CutlassFP8ScaledMMLinearKernel`.

| Draft lm_head | Acceptance length | ms / output token (wall) |
|---|---|---|
| bf16 | 5.790 / 5.790 | 1.198 / 1.197 |
| fp8  | 5.759 / 5.759 | 1.178 / 1.172 |

Greedy outputs are identical across all four runs (64/64), as expected
with the target verifying with its own head. LGTM.
