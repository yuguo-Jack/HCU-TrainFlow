# [Bugfix] reject string file on translation like transcription

[Upstream PR](https://github.com/vllm-project/vllm/pull/55618) · state: closed · merged: True

## Original PR description

## What

The audio transcription request already 422s when `file` is a string (`Expected 'file' to be a file-like object, not 'str'.`). The translation request has the same `file: UploadFile` field and the same stream-option validator, but it never ran that string check.

On `main` at `6865e67`:

```python
# transcription/protocol.py
if isinstance(data.get("file"), str):
    raise HTTPException(
        status_code=HTTPStatus.UNPROCESSABLE_ENTITY,
        detail="Expected 'file' to be a file-like object, not 'str'.",
    )

# translation/protocol.py
# stream options and vllm_xargs only
```

A translation form that sends `file` as text therefore misses the 422 and fails later with a worse error.

## Why

I was comparing the two speech-to-text request validators. Transcription already treated a string `file` as untrusted input. Translation copied the stream-option half of that validator and left the file check out. I added a unit test that calls both `model_validate({"file": "not-a-file.wav"})` and expects the same 422.

## How

Use the same `HTTPException` / `HTTPStatus.UNPROCESSABLE_ENTITY` check at the start of `TranslationRequest.validate_stream_options`.

## Testing

```bash
pytest tests/entrypoints/speech_to_text/test_audio_request_file_type.py -q
```

The parametrized case covers both `TranscriptionRequest` and `TranslationRequest`. The translation case fails on `6865e67` and passes with this patch.
