#  [ROCm][Perf] Quantize to MXFP4 in the FlyDSL QuickReduce + RMSNorm epilogue

[Upstream PR](https://github.com/vllm-project/vllm/pull/61020) · state: open · merged: False

## Original PR description

## Overview

At prefill sizes, the AR + RMSNorm + MXFP4-GEMM fusion (#59483) now takes the MXFP4 activation and its scales from the FlyDSL QuickReduce + RMSNorm kernel instead of launching a separate quant. Stacked on the FlyDSL QuickReduce + RMSNorm PR (#61021, itself on #59478) with #59483 merged in; only the last commit is new. Needs ROCm/aiter#6369 (`QuickAllReduceInt4.allreduce_rmsnorm_mxfp4`), so this stays a draft until an AITER release ships it.

Not a duplicate: searched open PRs for "QuickReduce MXFP4", "allreduce rmsnorm mxfp4" and "flydsl allreduce". #59483 quantizes in the custom all-reduce at decode only, and #56326 fuses a per-token FP8 quant into the custom all-reduce; neither covers the QuickReduce path.

## Claims

- At M ≥ 32 where FlyDSL QuickReduce runs the fused all-reduce, the per-1x32 MXFP4 quant before the GEMM is no longer a separate launch. The FP4 bytes and scales are bitwise equal to `per_1x32_f4_quant_hip(out, shuffle=True)`.
- `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4`, TP8, MI355X, one run per arm: +0.9% geomean output throughput (gains at 10 of 12 points) and −0.6% mean TPOT, with TPOT lower or equal at every point, against the FlyDSL QuickReduce + RMSNorm PR.
- The fused kernel is 1.08–1.18× faster than FlyDSL all-reduce + `rmsnorm2d_fwd_with_add` + `per_1x32_f4_quant_hip` (ROCm/aiter#6369).
- Nothing changes unless `VLLM_ROCM_QUICK_REDUCE_USE_FLYDSL=1` on gfx950.

- `test_prefill_quantizes_in_the_flydsl_quickreduce_kernel` (plain and Gemma norm): the fused op passes FlyDSL's `x_q`/`x_s` straight to `gemm_with_dynamic_quant` and runs neither the unfused AR + RMSNorm nor a quant.
- `test_prefill_falls_back_when_flydsl_quickreduce_does_not_run`: when FlyDSL declines the input, or the one-stage custom all-reduce owns the size, the op keeps #59483's unfused sequence, so no GEMM gets scales in the wrong layout.
- `test_flydsl_int4_should_fused_allreduce_rmsnorm_mxfp4_needs_gfx950_kernel`: the MXFP4 path is offered only where the FlyDSL kernel can quantize, and with the same operand gate as the plain fused path.
- `test_aiter_rms_fallback.py`: its fake QuickReduce gains `should_fused_allreduce_rmsnorm`, which the fused op now calls.

**Kernel evidence.** ROCm/aiter#6369 tests the kernel at TP 2, 4 and 8 on MI355X: `out` and `residual_out` match the plain fused kernel bit for bit, and the FP4 bytes and live scale bytes equal `per_1x32_f4_quant_hip(out, shuffle=True)`.

One run per arm on the same node, each server from empty vLLM, AITER and Triton caches. The AITER build has no Gemma MXFP4 custom-AR kernel, so #59483's decode quant stays off in both arms and the difference is the prefill quant.

## Details

**Before.** #59483 matches `all_reduce → fused_add_rms_norm → gemm_with_dynamic_quant` and moves the MXFP4 activation quant into the all-reduce, but only at decode (M < 32) and only with an AITER build that has the Gemma MXFP4 custom-AR kernel. At M ≥ 32 the fused op runs AR + RMSNorm, then the quant, then the GEMM. With FlyDSL QuickReduce on, that AR + RMSNorm is the FlyDSL kernel and the quant is a separate launch.

**After.** The AITER PR lets the FlyDSL kernel also write the MXFP4 activation and its e8m0 scales on gfx950, in the shuffled layout that both `gemm_a4w4` and the preshuffled GEMM read from M = 32.

- `QuickAllReduce.supports_fused_allreduce_rmsnorm_mxfp4` is true when FlyDSL QuickReduce is active and its kernel can quantize. `should_fused_allreduce_rmsnorm_mxfp4` applies the same operand gate as `should_fused_allreduce_rmsnorm`.
- `QuickAllReduce.fused_allreduce_rmsnorm_mxfp4(...)` allocates the GEMM operands and returns `(out, residual_out, x_q, x_s)`: `x_q` is `float4_e2m1fn_x2`, and `x_s` is `float8_e8m0fnu` in the padded shape AITER's `mxfp4_scale_shape` gives.
- In `rocm_aiter_fused_allreduce_rmsnorm_mxfp4_gemm`, at M ≥ 32 on the non-one-stage path, when FlyDSL accepts the input, the op calls `gemm_with_dynamic_quant(x_q, ..., x_scales=x_s)` and skips the quant. Everything else runs as in #59483.
- `RocmAiterAllReduceFusionPass` registers the MXFP4 GEMM patterns when either quant path is available: the custom-AR Gemma build, or FlyDSL QuickReduce with MXFP4 support. For a FlyDSL-only build, #59483's `mxfp4_fused_ar_rms_stage` returns None, so decode keeps the unfused sequence.

The scale shape comes from AITER, which owns the layout. +86 / −3 non-test lines.

**Limitations and CI gaps**

- **Arms.** The candidate adds #59483 as well as this commit. With no Gemma custom-AR kernel in the AITER build, #59483 by itself only reroutes the M ≥ 32 GEMM through the fused op, so the delta is the prefill quant. The control inherits the arm issue described in #61021.
- **Coverage.** gfx950 only (the MXFP4 epilogue needs it), TP8, one model. TP2/TP4, a second MXFP4 model, GSM8K and NIAH are pending.
- **CI.** The unit tests run in the MI355 "Distributed Features" step. The end-to-end runs need 8× MI355X and the 2.4T checkpoint, so they ran outside CI.
