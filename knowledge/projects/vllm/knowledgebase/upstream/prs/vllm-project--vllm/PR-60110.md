# [ROCm][Perf][Kimi-K3] Fold q_b_proj and W_UK into one GEMM for the MLA decode query

[Upstream PR](https://github.com/vllm-project/vllm/pull/60110) · state: open · merged: False

## Original PR description

## Purpose

On the ROCm/AITER decode path every Kimi-K3 MLA layer spends two launches on the query
projection (M = 56 rows at the InferenceX c14 point, 12 heads per rank at TP8):

| Kernel | What it does | Before (µs) | After (µs) |
|---|---|---|---|
| `hgemm_bf16_t16x32x128x5` | `q_b_proj`: x[56,1536] → q[56,12,192] | 6.76 | – |
| `_batched_gemm_a16wfp4_kernel` | absorb-in BMM: q_nope × W_UK (fp4) → ql_nope[56,12,512] | 5.49 | – |
| `_gemm_a16_w16_kernel` (aiter Triton `gemm_a16w16`) | x[56,1536] × W_fold[1536,6912] → [ql_nope \| q_pe] | – | 9.20 |
| **per layer** |  | **12.25** | **9.20** |

`q_b_proj` and the `W_UK` are consecutive linear maps, so
`ql_nope[h] = x · (W_UK[h] · W_qb_nope[h])ᵀ`. This PR builds once at load, from the bf16
checkpoint weights,

    W_fold[h] = [ W_UK[h] · W_qb_nope[h] ; W_qb_pe[h] ]        # [512 + 64, 1536] per head


**Decode only:** the W_UK absorb exists only on the MQA decode path. Prefill uses the
un-absorbed form and keeps `q_b_proj`, so any step with prefill tokens takes the original path.

**Small M win:** the fold reads 21 MB instead of 7.5 MB and does 2.5x the FLOPs. The save shrinks as M grows and would turn negative at prefill sizes, which this path never sees. 

We do additional 1.9Gb for the extra weight fold for all 93 layers of Kimi k3.

We're actively testing the prefill shape such that it cannot be much worse than non w-fold so that we don't have to pay for extra 1.9Gb.
