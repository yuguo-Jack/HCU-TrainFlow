## Overview

Let DeepSeek-V4.1 Mono decode on gfx950 read and write the 528 B MXFP8 KV record and read the 288 B NVFP4 compressed record. This follow-up depends on [#57523](https://github.com/vllm-project/vllm/pull/57523), which provides the ordinary attention readers and writers.

This is a stacked follow-up, not a replacement for #57523. Its prerequisite commits remain in the GitHub diff until that PR merges. The Mono-only delta is [the comparison against the parent branch](https://github.com/JohnQin-llm/vllm-amd/compare/rocm-dsv41-mxfp8-kv...dsv41-mono-kv-records).

## Claims

- Mono K1 writes 528 B MXFP8 window records, including quantized RoPE dimensions and per-32 scales.
- Mono K2 reads MXFP8 window records with MXFP8 or NVFP4 compressed records. It pads the NVFP4 compressed key list to complete 16-key tiles.
- Kernel build keys include the record format. The gfx942 NVFP4 exclusion remains.
- Keep V4.1 attention partials in FP32 until the chunk merge. V4 keeps BF16 partials.
- Mono supports the 528 B record. With aiter sparse MLA enabled, MXFP8 uses 528 B only when the installed aiter reader declares support; older aiter retains 584 B. NVFP4 aiter dispatch requires gfx950 and installed readers for both 528 B and 288 B records; older packages retain the ordinary fallback. The parent fixes for effective backend selection and consistent P/D layouts are preserved.

The parent uses legacy standalone Mono attention or an FFN-only fallback with the V4.1 record; this follow-up adds Mono attention support for both new formats.

## Details

The compaction merges duplicate writer stores, simplifies data loads/test setup, and removes repeated layout comments. Both record formats remain supported. The cache format is carried from the layer to the Mono runner and compile keys. The MXFP8 writer quantizes all 512 dimensions. The NVFP4 reader uses the gfx950 pair conversion and the per-16 e4m3 scales. Padding keeps each K2 key tile in one format.

BF16 rounding of each unnormalized attention partial added input error that the quantized MoE amplified. V4.1 retains FP32 partials until combination. On identical FFN input, the remaining Mono/reference FFN error is about 0.4%; the existing numerical thresholds are unchanged.

This follow-up includes a cached record-format capability check against the installed aiter reader and regression coverage for record selection. The aiter reader itself is tracked separately in [ROCm/aiter#7242](https://github.com/ROCm/aiter/pull/7242). User-facing format support and installed-reader requirements are documented under Hardware Supported Models.
