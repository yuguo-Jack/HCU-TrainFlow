# [ROCm][Model][MiniMax-M3] Context-parallel sparse lightning indexer (Triton, opt-in)

[Upstream PR](https://github.com/vllm-project/vllm/pull/57832) · state: open · merged: False

## Original PR description

## Purpose

Adds **context-parallel decode scoring** for MiniMax-M3's sparse lightning indexer on ROCm (TP>1, bf16 index cache, opt-in via `--attention-config '{"minimax_m3_indexer_cp": true}'`).

### Problem

MiniMax-M3 selects a sparse set of KV blocks per query token with a lightweight indexer that scores every block in the request's context. Index heads shard like KV heads (`sparse_num_index_heads == num_key_value_heads == 4`), and the index-K cache is a single shared head replicated on every rank. So with TP>1 every rank streams the whole index cache — the same `seq_len/128` blocks — once per decode step, just to score its own head(s). That read is duplicated `world_size` times and at long context and large decode batches it is a large term in the step.

### Solution

Shard the **blocks** instead of duplicating the read. Because each rank owns different index heads, every rank has to score every head on its shard:

1. All-gather the index queries — `heads * 128` bf16 per token (1 KB at M3's 4 heads).
2. Each rank scores **all global heads** on its `1/world_size` round-robin block shard (`block = local * world + rank`).
3. For each head, take the local top-k of the **full** `k` over the shard, pack each candidate into one int64 `(score, global block id)` key, and all-gather the keys — `P * heads * k * 8` bytes per token, independent of context length.
4. Merge per global head, keeping only the heads this rank owns.

Index-cache traffic per rank drops to `1/P`; scoring compute per rank is unchanged (`heads` heads over `1/P` of the blocks). The merge is exact: for a given head, a block in that head's global top-k is necessarily in its own shard's top-k for the same head. Forced init/sink and sliding-window blocks are pinned on both the shard and the merge.

**Default: OFF** (`AttentionConfig.minimax_m3_indexer_cp = False`); nothing enables it automatically. Turning it on is a startup error unless the index cache is bf16 (`indexer_kv_dtype` "auto" or "bf16") — the score kernel reads the cache without a scale; the fp8 path is #57909 — and when the fused decode path (#59653) is also enabled, since that kernel computes indexer top-k itself. It is also a startup error on non-ROCm platforms or with `tensor_parallel_size == 1`.

### CUDA graph capture

Two properties are required for CP to work under `cudagraph_mode=FULL_DECODE_ONLY`.

**CP must be what gets captured.** vLLM v2 records FULL decode graphs with `cudagraph_runtime_mode=NONE` (see `ModelCudaGraphManager.capture`), so a `CUDAGraphMode.FULL` guard never fires. Guarding on `torch.cuda.is_current_stream_capturing()` would record the **non-CP** indexer into the decode graph that is then replayed. The only guard is `torch.compiler.is_compiling()`, because Dynamo tracing cannot capture the collectives. Persistent buffers (in `IndexerCPDecode`) keep the decode path allocation-free so CP is what gets captured.

**Kernel shapes must be capture-stable.** Capture goes through `_dummy_run`, which sets `seq_lens = max_query_len`. Shapes derived from the batch's `max_seq_len` would specialize a one-block context into every decode graph. All kernel shapes come from `max_model_len`, and block counts and strides are runtime arguments rather than `tl.constexpr`. `test_indexer_context_scores_independent_of_shape_bound` asserts scores are identical whether the grid is sized for the batch or for a bound 8x larger.

`--enforce-eager` is not required.

### MiniMax-M3 sparse attention pipeline

| Stage | Backend | Index cache dtype | When selected |
|---|---|---|---|
| Indexer | **Triton** (this PR) | `bf16` | `indexer_kv_dtype=bf16`; no AITER dependency |
| Indexer | AITER (#57909) | `fp8_e4m3` | `indexer_kv_dtype=fp8` |
| Attention | **AITER_SPARSE_PA** | — | `SHUFFLE_KV_CACHE_LAYOUT=1` + `ROCM_AITER_UNIFIED_ATTN` |

## Test Plan

### Hardware and image
8x AMD Instinct MI355X (gfx950). `vllm/vllm-openai-rocm:nightly-rocm100-92044241a02f05de51420d654daf669de20b4691` with this PR's files applied on top of that exact commit.

### Correctness
```
pytest tests/kernels/attention/test_minimax_m3_indexer_cp.py -v
pytest tests/distributed/test_minimax_m3_indexer_cp_tp.py -v
```
The distributed test runs the production CP decode across real TP ranks and compares each rank's top-k with the non-CP decode kernel (`minimax_m3_index_decode`) on the full context, **per global index head**, using M3's config (4 heads, top-16, init 0, local 1) on 32k–82k token contexts. It is parametrized over TP 2/4/8 (TP=8 covers head replication), `query_len` 1/4 (spec-decode verify), and RCCL vs AITER IPC all-gather. It also asserts the four heads select different blocks on ≥90% of rows, so a merge that mixed heads would fail.

Contexts are deliberately long: at top-16 x 128-token blocks plus a forced local block, any prompt under ~2k tokens selects every block, so short-context evals cannot detect a wrong selection.

### AgentX sweep (MXFP4, TP=4, no speculative decoding)

Same node, same image, same PR code in both arms; only the CP switch differs. (These runs used the earlier environment-variable switch; it has since moved to `attention_config.minimax_m3_indexer_cp` with no change to the CP code path.) CP ran first, baseline second, then CP conc=15 was repeated on a fresh server. Every point has 0 failed requests.

| Concurrency | Baseline (tok/s/GPU) | CP (tok/s/GPU) | Throughput | Requests | ITL baseline → CP (ms) | ISL baseline | ISL CP |
|---|---|---|---|---|---|---|---|
| 15 | 12,652 | 12,997 | +2.7% | +1.6% | 16.2 → 14.7 (−9.5%) | 73,900 | 74,737 |
| 15 (repeat) | 12,652 | 13,320 | +5.3% | +3.3% | 16.2 → 13.8 (−14.9%) | 73,900 | 75,319 |
| 20 | 15,245 | 15,957 | +4.7% | +3.9% | 19.3 → 16.9 (−12.2%) | 75,343 | 75,935 |
| 24 | 15,385 | 17,115 | **+11.2%** | +7.7% | 22.7 → 19.7 (−12.9%) | 74,606 | 76,245 |
| 32 | 20,125 | 23,175 | **+15.2%** | +14.4% | 37.6 → 28.6 (−23.9%) | 73,741 | 74,232 |

The gain grows with decode batch size, as expected when the term being divided by `P` is per-sequence index-cache traffic. At concurrency 15 the throughput delta is about the size of run-to-run variation (baseline conc=15 measured 12,936 and 12,652 in two passes); ITL improves at every point. ISL is within 3% across arms with CP's the higher, so the delta is not a shorter-trajectory artifact.

One earlier pass on the same node was discarded: its baseline engine (CP off) exited partway through conc=32 (42% failed requests), and its CP conc=15 point ran at half speed with no errors. Neither reproduced in the pass above, which also logs both servers in full.

**Withdrawn:** the previous version of this PR scored only each rank's own index head on its shard and merged across ranks, which mixes different heads' candidates at TP=4. The AgentX, EAGLE3 and GSM8K results previously reported here were measured on that code and are removed. EAGLE3 has not been re-measured. GSM8K is not repeated because it cannot distinguish a correct selection from a wrong one at its context lengths (see Test Plan); the per-head equivalence test replaces it.

**Hardware note:** these are MI355X numbers; absolute tok/s/GPU is not comparable to the MI350X figures in earlier revisions. Every comparison is baseline vs CP on the same node.

Requesting changes. I don't think this is correct for MiniMax-M3 at TP=4.

`sparse_num_index_heads` is 4, and the indexer shards heads the same way as KV heads. At TP=4 each rank owns one distinct index head. This PR never all-gathers `index_q`. `forward()` scores only `self.num_index_heads`, then all-gathers packed keys and merges them on local head 0.

Those four keys are top-k blocks of four different heads, each scored on a different block residue class. The exact-merge argument (a global winner is in its own shard's top-k) assumes every rank scored the same head. That is not this model.

The MI350X AgentX speedup is on this TP=4 config, and it only reports tok/s. Reading 1/4 of the index cache is faster even when the selected blocks are wrong. GSM8K will not catch it: contexts are short and init/local blocks are forced. Please add a multi-GPU check that the CP top-k matches the non-CP top-k per global head on a long context (tens of thousands of tokens, not GSM8K).

The fix is to replicate the index queries first (all-gather Q; 4 heads * 128 bf16 per token), score every head on this rank's block shard, merge per global head, then write back only the head this rank owns. Please re-measure after that. I would not treat the current +23% as the result.

Please also refuse the env unless `indexer_kv_dtype` is bf16. `select_indexer_impl_cls()` currently enables this for fp8 too, and the score kernel loads fp8 cache with no scale. The fp8 path is #57909. The official recipe uses fp8, so this must not turn on there.

Keeping this default-off. Please don't auto-enable it. It also must not run together with the fused mono decode path (#6047 / #59653), which owns indexer top-k inside the kernel.

You were right that capture needed attention here, though the failure turned out to be the opposite of a missing guard.

An `is_current_stream_capturing()` skip is what this had originally, and it is actively unsafe: vLLM v2 records FULL decode graphs with `cudagraph_runtime_mode=NONE` (see `ModelCudaGraphManager.capture`), so skipping during capture does not fall back for one warmup step — it bakes the **non-CP** indexer into the replayed decode graph and CP silently never runs.

The real bug was shape specialization. `_capture_cudagraphs` goes through `_dummy_run`, which sets `seq_lens` to the query length:

```python
elif dcp_dummy_context_len > 0:
    seq_lens = max_query_len + dcp_dummy_context_len
else:
    seq_lens = max_query_len
```

so at capture `d.max_seq_len` is 4 with 3 draft tokens. The score kernel was sized off the batch, which baked `LOCAL_BLOCKS = GLOBAL_BLOCKS = CHUNK = 1` and a `(batch, 1)` grid into every decode graph. On replay at 79k context each rank scored only block `rank` and the top-k saw one candidate per shard, so the indexer returned the first few blocks plus the forced sink and sliding-window pins regardless of context length. Throughput was down 46%, and output degraded enough to shorten the trace trajectories themselves (ISL 65.7k against the baseline's 79.4k).

Fixed in 9fd6ca3 by taking every kernel shape from `max_model_len` and making the block counts and strides runtime arguments, so nothing shape-dependent can be specialized into a graph again. The per-request causal bound clips the real work at runtime and chunks past the end return immediately. `test_indexer_context_scores_independent_of_shape_bound` locks this in: it asserts the scores are identical whether the grid is sized for the batch or for a bound 8x larger.

With that fixed, CP is a real win once it is not hidden behind EAGLE3's 2.78 acceptance length. AgentX on the Weka trace, TP=4 MXFP4, no spec decode, `FULL_DECODE_ONLY`, baseline and CP back-to-back on the same server config:

| conc | baseline tok/s/GPU | CP tok/s/GPU | throughput | ITL |
|---|---|---|---|---|
| 15 | 12,248 | 13,266 | +8.3% | −20.5% |
| 20 | 13,661 | 16,145 | +18.2% | −20.6% |
| 32 | 17,858 | 21,996 | +23.2% | −28.0% |

On your other suggestion in this file — yes, an all-gather is the right call and that is what it does now. The exchange all-gathers packed `(score, block id)` int64 keys, so the payload is `P * k * 8` bytes per token and does not grow with context.

This investigation and fix were AI-assisted; I have reviewed every changed line and run the benchmarks above myself.

Good catch on the version you reviewed — at that point prefill went through `super().forward()`, and the base Triton impl runs *both* halves, so a mixed batch would have scored the decode tokens twice: once through CP, then again through the non-CP path.

That is no longer the structure. The prefill branch now calls the score and top-k kernels directly:

```python
if index_md.num_prefills > 0:
    p = index_md.prefill
    score = minimax_m3_index_score(iq[nd:], kv, p.block_table, ...)
    prefill_topk = minimax_m3_index_topk(score, p.cu_seqlens_q, ...)
```

so a mixed batch runs CP decode over `iq[:nd]` and prefill over `iq[nd:]` exactly once each, writing into disjoint slices of the shared top-k buffer.

The one remaining `super().forward()` is the decode fallback (Dynamo tracing, or an unbound/empty index cache during the profiling run). It returns immediately, so it also handles both halves in a single call rather than falling through into the prefill branch.

Prefill deliberately stays on the existing non-CP path. Prefill already amortizes the index-cache read across many query tokens, so sharding blocks there would not recover enough traffic to pay for the exchange — CP only targets decode, where each step re-streams the whole cache for a handful of query tokens.
