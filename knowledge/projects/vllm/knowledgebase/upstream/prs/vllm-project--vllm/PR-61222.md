# [Debug] Add native stack dumps for slow worker RPCs

[Upstream PR](https://github.com/vllm-project/vllm/pull/61222) · state: closed · merged: False

## Original PR description

## Overview

A stalled multiprocessing worker can leave only a later collective timeout from another rank. Add an opt-in native timer that dumps the worker's Python thread stacks while a slow `execute_model` or `sample_tokens` RPC is still running, including when the GIL is held.

## Claims

- `VLLM_WORKER_RPC_DUMP_TIMEOUT_S=30` enables one stack dump per slow runtime RPC; the default `0` disables it.
- Cancel the timer in `finally` and preserve RPC results and existing execution timeouts.
- Exclude loading/warmup RPCs and log rank, PID, and thread ID for attribution.

## Validation

**10 tests passed** in `tests/v1/executor/test_multiproc_executor.py`, including real subprocess stack dumping, a native `ctypes.PyDLL` call holding the GIL, cancellation after a fast RPC, loading exclusion, and existing payload-lifetime/exception/timeout behavior.

The current branch's worker, environment definitions, and test file ran with v0.30.0 packaged dependencies in an isolated CPU container. Current upstream logger/formatter files were also overlaid to satisfy the newer worker's logging import; no worker behavior was stubbed. Repository reproduction command:

```bash
.venv/bin/python -m pytest tests/v1/executor/test_multiproc_executor.py -q
pre-commit run --files docs/usage/troubleshooting.md vllm/envs.py vllm/v1/executor/multiproc_executor.py tests/v1/executor/test_multiproc_executor.py
```

All relevant pre-commit hooks and `git diff --check` passed. Existing `v1-executor-worker` CI runs this test directory.

The same diagnostic logic was previously exercised at a five-second threshold in isolated Kimi-K3 serving: 8,192 image/tokenization requests and 126 mixed text requests completed successfully, and the dumps identified real request-time image compiler stacks. That run used the deployed v0.30.0 base; a full serving build of current upstream with this PR has not been qualified.

## Details

`faulthandler.dump_traceback_later()` uses CPython's native watchdog, so it can emit evidence while a C extension holds the GIL. No model-runner or scheduler changes are needed; this applies to multiprocessing workers regardless of runner version.

Duplicate/related-work review on 2026-10-12 included #55700, #54638, #49628, and RFC #56816 (including its comments). #55700 and #54638 use Python monitoring threads, which require the GIL to run their diagnostic; #49628 captures EngineCore stages and stacks. This proposal specifically provides a GIL-independent, RPC-scoped worker dump, with a real native-call regression demonstrating that distinction. It does not implement the broader heartbeat framework in the RFC.

The timer is process-wide and replaces other uses of `dump_traceback_later` in that worker. Concurrent ranks' stderr dumps may interleave. It observes CPU-side RPC duration and cannot detect every GPU stall after an RPC returns. This is a diagnostic feature, not a fix for the underlying stall.
