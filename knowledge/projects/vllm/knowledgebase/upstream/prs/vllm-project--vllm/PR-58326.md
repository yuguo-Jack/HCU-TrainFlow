# [Quantization][MoE] Route compressed-tensors W4A8-INT MoE to WNA16 Marlin on CUDA

[Upstream PR](https://github.com/vllm-project/vllm/pull/58326) · state: closed · merged: False

## Original PR description

## Purpose

Fix `NotImplementedError: W4A8 Int8 MoE is only supported on CPU platforms` when
serving a compressed-tensors checkpoint whose MoE experts are quantized
INT4-weight / INT8-dynamic-activation on CUDA.

CUDA has no native W4A8-INT MoE kernel: such layers currently reach
`CompressedTensorsW4A8Int8MoEMethod`, whose backend oracle
`select_w4a8_int8_moe_backend` is CPU-only and raises on CUDA.

This PR routes those layers to `CompressedTensorsWNA16MoEMethod` on CUDA: the
INT4 weights run on the existing WNA16 Marlin MoE kernel, which quantizes
activations to INT8 per token at runtime. No new kernel is added — it is a
dispatch change inside the existing `_is_dynamic_token_w4a8_int` branch, so the
CPU path is untouched.

INT8 activation quantization is opt-in and requires
`VLLM_MARLIN_INPUT_DTYPE=int8`. When that variable is unset the same weights run
as W4A16, i.e. existing WNA16 behavior is unchanged.

This is not a duplicate: no open PR routes compressed-tensors W4A8-INT MoE to
WNA16 on CUDA; existing W4A8 work covers FP8 (`CompressedTensorsW4A8Fp8MoEMethod`)
and the CPU path only.

## Test Plan

- `VLLM_MARLIN_INPUT_DTYPE` unset → CUDA loads the layer as WNA16/W4A16; no
  `NotImplementedError`.
- `VLLM_MARLIN_INPUT_DTYPE=int8` → same layer loads as WNA16 with INT8
  activations (info log line above appears once).
- CPU (or `current_platform` non-CUDA) selects
  `CompressedTensorsW4A8Int8MoEMethod`.
