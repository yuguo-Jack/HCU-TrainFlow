# [Model] Add LoRA support for PaddleOCR-VL

[Upstream PR](https://github.com/vllm-project/vllm/pull/61811) · state: open · merged: False

## Original PR description

## Purpose

Enable LoRA and multi-LoRA serving for PaddleOCR-VL
(`vllm/model_executor/models/paddleocr_vl.py`). Related to #48019.

Currently `
vllm serve PaddlePaddle/PaddleOCR-VL --enable-lora` accepts
PEFT adapters but they silently never affect inference: the model class
does not implement `SupportsLoRA`, and its `hf_to_vllm_mapper` lacks the
prefix rule for adapters trained against the native transformers class
(`PaddleOCRVLModel.language_model`). Such adapters carry keys like
`model.language_model.layers.N.*`, which the existing rule
`"model." -> "language_model.model."` rewrites to the nonexistent
`language_model.model.language_model.*`, so no module is matched and the
request is served by the base model.

Scope: text-LoRA only (the adapter targets the ERNIE-4.5 language model).
Tower/connector LoRA (`--enable-tower-connector-lora`) is out of scope;
the SigLIP vision tower receives no LoRA injection.

## Changes

1. `PaddleOCRVLForConditionalGeneration` now inherits `SupportsLoRA`.
2. Add mapper rule `"model.language_model." -> "language_model.model."`,
   placed before the generic `"model."` rule (prefix rules are applied
   sequentially; the specific rule must win).
3. Add `packed_modules_mapping` for the fused `qkv_proj` / `gate_up_proj`
   modules (Ernie4.5 follows the Llama layout).
4. Add `embedding_modules` (`embed_tokens` / `lm_head`).
5. Mark LoRA support in `docs/models/supported_models.md`.

## Test Plan

```
vllm serve PaddlePaddle/PaddleOCR-VL \
--enable-lora --max-loras 3 --max-lora-rank 32 \
--lora-modules adapter1=<adapter1-path> adapter2=<adapter2-path> adapter3=<adapter3-path>
```

- `/v1/models` lists base + all 3 adapters; routing via the `model` field.
- base / adapter1 / adapter2 / adapter3 requests on the same image,
  interleaved in one batch: base output byte-identical to no-LoRA
  serving; adapter outputs differ from base and match offline HF+PEFT
  inference on sampled cases.
- Server logs show non-null `lora_id` on adapter requests.

## Test Result

Environment: vLLM v0.31.0 (patched with this PR) + torch 2.13.0+cu130,
serving PaddleOCR-VL with 3 LoRA adapters (rank 32) via
`--enable-lora --max-loras 3 --max-lora-rank 32`.

1. **Adapter loading**: startup logs show `Loaded new LoRA adapter` for
   all 3 adapters; the LoRA compute kernels (`_lora_shrink_kernel`,
   `_lora_expand_kernel`) are JIT-compiled and exercised during
   inference, confirming the LoRA path is taken.
2. **Routing**: `GET /v1/models` lists the base model and all 3 adapters;
   requests are routed by the OpenAI-compatible `model` field.
3. **Base non-regression**: with the same image/prompt, the base route of
   the multi-LoRA server produces byte-identical output to a vanilla
   base-only server (no `--enable-lora`).
4. **LoRA effect**: the same image sent to base vs. each LoRA route yields
   distinct outputs — base returns raw OCR text while each adapter
   returns its task-specific structured JSON.
5. **Offline parity**: 15 images per adapter, compared field-by-field
   against offline HF+PEFT inference baselines:
   - adapter1: 15/15 identical (10 fields)
   - adapter2: 14/15 identical; the single mismatch is a one-character OCR
     ambiguity that also varies across runs of the offline baseline
     itself (unrelated to LoRA adapter loading)
   - adapter3: 15/15 identical
