# [Perf][Compile] Enable norm+quant fusion by default for NVFP4 checkpoints

[Upstream PR](https://github.com/vllm-project/vllm/pull/61783) · state: open · merged: False

## Original PR description



## Overview

#51925 added the FlashInfer add-RMSNorm + NVFP4 quant pattern behind `fuse_norm_quant`, and its reviewer suggested reusing that flag and enabling the fusion by default ([comment](https://github.com/vllm-project/vllm/pull/51925#discussion_r3901128675)). But `enable_norm_fusion` returns False for NVFP4 checkpoints in the default CUDA config, so the pattern only runs when the flag is set by hand. This PR adds the NVFP4 clause that `enable_act_fusion` already has and updates the fusion docs.

## Claims

- `fuse_norm_quant` is on by default for NVFP4 checkpoints (ModelOpt, compressed-tensors, mixed), like `fuse_act_quant`.
- Prefill GPU time drops 5-6% for Qwen3 4B and 3-7% for 0.6B models on an RTX PRO 6000. Retrieval quality and decode speed stay within noise.

## Validation

RTX PRO 6000 Blackwell Server Edition (SM120), CUDA 13.4, torch 2.13.0+cu130, ModelOpt `NVFP4_DEFAULT_CFG` checkpoints. Both arms run main; "on" sets `pass_config.fuse_norm_quant=True`, the default this PR makes. GPU kernel time of one profiled pooling call on 128 sequences:

| Model | 128 × 640 tokens, off → on | 128 × 320 tokens, off → on |
|---|---|---|
| Qwen3-Reranker-4B | 775.1 → 733.0 ms | 365.1 → 343.7 ms |
| Qwen3-Embedding-4B | 774.5 → 734.3 ms | 364.9 → 343.7 ms |
| Qwen3-Reranker-0.6B | 186.9 → 173.6 ms | 87.1 → 83.9 ms |
| Qwen3-Embedding-0.6B | 186.8 → 173.7 ms | 86.8 → 83.9 ms |

The replaced kernels account for the whole difference: for Reranker-4B at 640 tokens, 71 add-RMSNorm Triton kernels and the `cvt_fp16_to_fp4` launches after them (107.0 ms) become 71 FlashInfer `add_rmsnorm_fp4quant` launches (64.7 ms).

Recall@10 on 60 questions each of Ko-StrategyQA and MIRACL-ko stays within eval noise, and decode throughput within run-to-run variation. The fused kernel is not bit-identical, and neither path is consistently closer to BF16 (details below).

- `pytest tests/test_config.py -k test_fusion_pass_op_priority`: passes with the new NVFP4 case.

## Details

**Why only NVFP4.** `enable_norm_fusion` leaves the pass off when RMSNorm and FP8 quant are both native, because Inductor fuses them itself. NVFP4 quant is always the `scaled_fp4_quant` custom op, which Inductor cannot fuse, so only this pass can.

**Scope.** The NVFP4 pattern still needs FlashInfer's `add_rmsnorm_fp4quant` and SM100+, and the all-reduce + RMSNorm fusion (TP > 1) still runs first where it applies. FP8 and unquantized checkpoints are unaffected. Mixed ModelOpt checkpoints also fuse their FP8 layers' norms, as `fuse_act_quant` already does; that kernel matches Inductor's fused one (67.6 vs 68.2 ms on an FP8 Qwen3-Reranker-4B). A cold compile takes about 1.5 s longer.

**Limitations.** Measured on SM120 only. #51925 measured GB200/GB300 prefill (Qwen3-30B-A3B NVFP4, 0.7-1.1% faster); SM100 decode is not measured.

**Duplicate check.** No open PR changes this default. #36413 (open, idle since July) is the earlier attempt that #51925 followed up. #61073 (open) fuses by hand in Llama's model code; this PR covers models left to the compile pass.

Thanks for measuring this. I reran your setup on an RTX PRO 6000 (main 852989f, seven alternating server launches per model, one shared FlashInfer autotune store):

- Decode TPOT: Qwen3-30B-A3B-NVFP4 at concurrency 4 is +0.1%, inside the 1.5% spread between the off launches, so I couldn't reproduce the +1.9%. Qwen3-4B NVFP4 is +0.9% at concurrency 4 and within noise at 1, 16 and 64.

The fused kernel itself is faster at every size; the cost is host-side time per call around the kernel launch, which shows when a prefill runs outside CUDA graphs and is launch-bound.

So flipping the default isn't a clear win yet. I'm moving this to draft for now.
