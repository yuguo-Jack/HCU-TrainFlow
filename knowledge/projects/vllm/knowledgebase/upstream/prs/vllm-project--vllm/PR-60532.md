# [Attention] Decode FlashInfer spec queries with fa2 on pre-SM90 GPUs

[Upstream PR](https://github.com/vllm-project/vllm/pull/60532) · state: open · merged: False

## Original PR description



## Overview

On pre-SM90 GPUs FlashInfer has no XQA or trtllm-gen decode, so speculative decoding verification steps (1 + `num_speculative_tokens` tokens per request) are split off as prefills, and `get_cudagraph_support` reports `UNIFORM_SINGLE_TOKEN_DECODE`, which drops spec decode from `FULL_AND_PIECEWISE` to `PIECEWISE`. FlashInfer's fa2 tensor-core decode already takes uniform multi-token queries (`q_len_per_req`) and keeps them CUDA-graph safe ([flashinfer-ai/flashinfer#3871](https://github.com/flashinfer-ai/flashinfer/pull/3871), in 0.7.0.post1), so this sends uniform verification queries through it and reports `UNIFORM_BATCH` there.

## Claims

- On pre-SM90 GPUs, FlashInfer spec decode runs its verification steps in full CUDA graphs. On SM80 with Qwen3.8-27B NVFP4 and MTP (3 tokens), decode goes from 73.6 to 108.1 tok/s at TP=1 and from 61.0 to 83.1 tok/s at TP=2, with the same greedy output.
- Without speculative decoding nothing changes: same throughput, same tokens and the same KV cache size.
- SM90 and later keep their decode selection and graph support; single-token native decode is planned exactly as before.

## Validation

`test_flashinfer_fa2_spec_decode_correctness` (new, runs on pre-SM90 GPUs and skips elsewhere) checks uniform 4-token queries over three requests against SDPA, eager and under CUDA graph replay, and that the decode was planned with `q_len_per_req=4`. The test harness's `num_speculative_tokens` option built its speculative config as a `SimpleNamespace` that lacks fields the builders now read, so it fails for FlashInfer on every GPU; it now builds a real `SpeculativeConfig`. `test_flashinfer_varlen_cudagraph_capability` mocks a trtllm-gen platform and now also pins the device capability, since the varlen bound is `None` on pre-SM90 GPUs.

Everything below ran on SM80 with the FlashInfer 0.7.0.post1 release wheel that vLLM pins, installed apart from any source build. `pytest tests/v1/attention/test_attention_backends.py tests/v1/attention/test_flashinfer_dcp_spec_reorder.py tests/kernels/attention/test_flashinfer.py -k "flashinfer or FLASHINFER"` gives 149 passed, 53 skipped on this PR and 147 passed, 53 skipped on `main` (`32fbfa15e8`); the two new cases are the difference.

End to end, `main` (`32fbfa15e8`) against `main` + this PR: Qwen3.8-27B NVFP4 weights, NVFP4 KV cache, FlashInfer, batch 1, default compile and CUDA graph settings, 256 greedy tokens, median of three runs after warm-up.

| | `main` | this PR |
| --- | ---: | ---: |
| TP=1, MTP with 3 tokens | 73.6 tok/s (`PIECEWISE`) | 108.1 tok/s (decode `FULL`) |
| TP=1, no spec decode | 57.2 tok/s | 57.5 tok/s |
| TP=2, MTP with 3 tokens | 61.0 tok/s (`PIECEWISE`) | 83.1 tok/s (decode `FULL`) |
| TP=2, no spec decode | 59.0 tok/s | 59.0 tok/s |

Output tokens are identical between the two builds in every row, and MTP accepts the same drafts (684 of 1032 at TP=1, 668 of 1092 at TP=2). KV cache size is unchanged without spec decode and about 0.05 GiB smaller with MTP, which now captures FULL decode graphs.

## Details

- Spec queries count as decodes on pre-SM90 GPUs (`supports_spec_as_decode`), so the reorder threshold becomes 1 + `num_speculative_tokens`. DCP still forces it back to 1.
- `get_cudagraph_support` returns `UNIFORM_BATCH` on pre-SM90 GPUs. DCP and non-causal draft attention stay at `UNIFORM_SINGLE_TOKEN_DECODE`, and `get_varlen_cudagraph_max_query_len` returns `None` there since fa2 has no varlen decode.
- The native decode branch already gets only uniform decodes (`require_uniform=True` sends mixed lengths to prefill). With more than one token per request it plans the wrapper per request with `q_len_per_req`; FULL uniform-decode graphs are captured only up to `max_num_seqs * (1 + num_speculative_tokens)` tokens, so there the token count is exactly requests × query length. Single-token decode keeps planning by token count.
- FlashInfer freezes a CUDA-graph decode wrapper to its batch size and query length, so the wrapper cache is keyed by both.

An earlier attempt ([#50885](https://github.com/vllm-project/vllm/pull/50885)) targeted SM12x and was closed once XQA covered that architecture; it did not cover pre-SM90.
