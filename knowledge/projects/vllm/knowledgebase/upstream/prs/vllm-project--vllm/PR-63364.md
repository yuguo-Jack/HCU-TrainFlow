# [ROCm][Build][4/5] Speed up ROCm build: instantiate the int4 skinny GEMM per output width

## Disclosure

AI assistance was used. The changes were reviewed and tested manually.

## Overview

**Splits the int4 skinny GEMM translation unit on one item - `N_in` (output width, 1-5), from the dispatch tower #40977 landed and #57199 widened.**

`csrc/rocm/skinny_gemms_int4.cu` holds the whole int4 skinny GEMM (`wvSplitK_int4_g`): a single host entry whose macro tower expands per output width `N_in` (1-5) x 2 activation dtypes x 3 group sizes, so all of the op's device code is emitted by one translation unit. On a 9-arch build that unit is the longest compile of the entire build - 1232 s of a 1234 s ninja span, i.e. the build waits on one core while the other 63 job slots sit idle.

This PR instantiates one unit per `N_in` instead: the kernels live in an include-only `skinny_gemms_int4.cuh` whose entry is a `template <int N>`, each unit is two lines (`#include` + `VLLM_SKINNY_INT4_INSTANTIATE(N)`), and a small `skinny_gemms_int4_api.cu` keeps the public symbol and dispatches on `in_b.size(0)`, with `extern template` keeping the device code in the five units.

Same kernels, same dispatch rules, same numerics: the only change is which translation unit generates which `N_in`, plus the runtime forward in the API unit. At 1 arch the file is not the build's tail, so the single-arch wall is unchanged.


The single-arch rows are `pip install -e .` on MI350 (gfx950); the 9-arch row is the `setup.py bdist_wheel` described under *Validation*. All cold builds:

| build | `main` | this PR | All 5 PRs (#62921) |
|---|---|---|---|
| `MAX_JOBS=16`, gfx950 only | 107 s | 109 s | 87 s |
| `MAX_JOBS=64`, gfx950 only | 85 s | 87 s | 50 s |
| `MAX_JOBS=64`, 9 archs | 1263 s | 600 s | 472 s |

## Claims

- 52 % off the 9-arch wheel build (1263 s -> 600 s): the int4 skinny GEMM is the longest compile of that build (1232 s of a 1234 s ninja span) and becomes 6 units of 75-442 s.
- The 9-arch wheel shrinks from 266 MB to 257 MB and the `.o` set from 924 to 928 MB, i.e. no growth in device code.
- Single-arch is ~2 % slower (107 -> 109 s at 16 jobs, 85 -> 87 s at 64), because the file is not that build's tail.
- The op is not re-instantiated or reduced: each lane emits the kernels of one `N_in` for the same 2 dtypes and 3 group sizes.

**Left to do, the one blocker: gfx11/gfx12 runtime check.** `wvSplitK_int4_g` only has kernels for RDNA - the file defines `__HIP__GFX1X__` from `__GFX11__ || __GFX12__` and stubs the kernels out otherwise - and `tests/kernels/quantization/test_rdna_hybrid_w4a16.py::test_hip_skinny_wvSplitK_int4_g` is `skipif(not on_gfx1x())`. On the MI350X host used here the four lane forwards are therefore exercised by the build only (6 lanes, 0 device symbols in the API unit, 408/216/264/264/264 in the kernel units). Needs a gfx1100 or gfx1151 run before this can leave draft.

### Why five PRs

The two builds are bound by different things, so no single change moves both.

**Why the three single-arch PRs are all needed.** At 1 arch (`gfx950`, `MAX_JOBS=64`, `main` = 85 s) three groups take turns setting the wall, in this order:

1. topk softplus-sqrt (#62717) - 74.5 s, a single unit
2. paged attention (#62716) - 71.6 s, the slowest of 12 units
3. other skinny GEMMs (#62718) - 40.9 s, a single unit

#62717 takes (1) to 7.4 s, #62716 takes (2) to 31.1 s and #62718 stops (3) from becoming the next tail; with all three the tail moves to `selective_scan_fwd` (37.7 s) and the build goes from 85 s to 49 s. Drop any one of them and a ~70 s unit is back at the top, so the single-arch win needs all three.

**Why that is not enough at 9 archs.** A 9-arch build multiplies every unit's time by ~9, and the tail becomes two files that none of the first three touch: `csrc/rocm/skinny_gemms_int4.cu` at 1232 s and `csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu` at 478 s. All three merged take the 9-arch build from 1263 s to only 1253 s. #63364 splits the first (its tail drops to 448 s) and #63365 the second (to 171 s), which is what reaches 472 s.

The `skinny_gemms_int4.cu` tail is invisible in a `gfx950` build because that file **only emits its kernels for RDNA (that is part of the 9-arch build)**:

https://github.com/vllm-project/vllm/blob/f4edf9f0f078ae67392510aafd1871288948a3c3/csrc/rocm/skinny_gemms_int4.cu#L17-L19
https://github.com/vllm-project/vllm/blob/f4edf9f0f078ae67392510aafd1871288948a3c3/csrc/rocm/skinny_gemms_int4.cu#L568-L579

`csrc/fused_muse_spark_qknorm_rope_kv_insert_kernel.cu` fails differently: it has no arch guard, so a `gfx950` build compiles it for real - it is just 25 s there against 478 s across nine archs, which is why a single-arch profile ranks it as irrelevant (#63365).

## Details

The `__global__` templates, `mindiv_int4`, the `max_lds_len` / `on_gfx115x_int4()` gating and the macro tower are unchanged; only the entry becomes `template <int N>` and the `N_in` switch moves to the API unit.

`in_b.size(0)` is the same value the entry already used to pick `N_in`, so the forward in `skinny_gemms_int4_api.cu` cannot route an `N_in` to a unit that did not compile it. One deliberate behaviour change: for an `N_in` outside 1-5 the API unit now raises "Unsupported N value" before the tensor checks run, instead of after them; all valid paths are unchanged.

**How the file got this big.** Two PRs built the configuration space, both keeping it in one TU:

| PR | landed | what it added |
|---|---|---|
| #40977 | 2026-07-14 | the op: 2 kernels plus their CDNA stubs, the `N_in` 1-5 dispatch, 2 dtypes x 3 group sizes |
| #56301 | 2026-10-06 | 2 stride-padded kernel variants |

The rest of the history (#54965 for packed zero points, #57199 for speculative batches, #60721 for headers) reworked bodies and host paths without changing the kernel or arm count: 4 kernels (2 of them CDNA stubs) remain, instantiated over the `N_in` x dtype x group-size tuples, which is why splitting by `N_in` into 6 units recovers most of the time.
