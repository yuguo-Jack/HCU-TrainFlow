# [ROCm][MoE] Add AITER MXFP4 W4A16/W4A4 modular-kernel test coverage

[Upstream PR](https://github.com/vllm-project/vllm/pull/60886) · state: open · merged: False

## Original PR description

## Summary

Part of #54966 (item 1): `AiterExperts` already declares production support for the GFX950-only MXFP4 W4A16 (`kMxfp4Static, None`) and W4A4 (`kMxfp4Static, kMxfp4Dynamic`) quant schemes, but neither was exercised through the modular-kernel (`tests/kernels/moe`) prepare/finalize -> fused-experts -> reference-compare test harness. This PR adds that coverage.

- Adds a `weight_dtype` field to `TestMoEQuantConfig`/`Config` (mirrors `FusedMoEQuantConfig.make()`'s own `(quant_dtype, weight_dtype)` split) to represent the asymmetric W4A16 case (mxfp4 weight, unquantized activation) alongside the symmetric W4A4 case.
- Reuses the production MXFP4 oracle directly instead of reimplementing weight-layout conversion: `convert_gpt_oss_weight_to_mxfp4_moe_kernel_format()` and `make_mxfp4_moe_quant_config()` from `vllm/model_executor/layers/fused_moe/oracle/mxfp4.py`.
- Moves `_interleave_gate_up_rows()` out of `test_rocm_aiter_moe.py` into the shared `tests/kernels/moe/utils.py` helper module.

Three gaps were found while validating on MI350/gfx950 hardware and are scoped around rather than fixed here:
- W4A16's heuristic-dispatch kernel only has a `SWIGLUOAI` specialization, not SILU/GELU, despite `AiterExperts._supports_activation()` declaring broader support (https://github.com/ROCm/aiter/issues/2419).
- W4A16 hits the same `topk=1` + `apply_router_weight_on_input` GPU-hang gap as AITER's existing block-scaled FP8 path (https://github.com/ROCm/aiter/issues/2418), just not representable via `config.quant_block_shape` since mxfp4 has no block-shape field.
- W4A16+`SWIGLUOAI` silently computes the wrong thing for bias-free SwiGLU-OAI (~55% sign agreement, ~5x-small magnitude on hardware) instead of raising; only smoke-tested (shape/finite) here until the fix in #59766 lands.

## Test plan

Validated on an MI350/gfx950 host (MXFP4 is unsupported on MI300/gfx942):
- [x] `pytest tests/kernels/moe/test_modular_kernel_combinations.py::test_modular_kernel_combinations_singlegpu -k mxfp4` — both new W4A16 and W4A4 cases pass (note: `AiterExperts` was split into per-scheme subclasses in #60322, so the original `-k "AiterExperts and mxfp4"` filter no longer matches any test id; use `-k mxfp4`)
- [x] Full `test_modular_kernel_combinations_singlegpu` suite — 12 passed, no regressions to existing FP8/unquantized/nvfp4 cases
- [x] `pytest tests/kernels/moe/test_rocm_aiter_moe.py -k mxfp4` — existing W4A16 unit tests still pass after moving `_interleave_gate_up_rows`
- [x] `-k "mxfp4 and GELU"` collects 0 cases (activation gating confirmed)
