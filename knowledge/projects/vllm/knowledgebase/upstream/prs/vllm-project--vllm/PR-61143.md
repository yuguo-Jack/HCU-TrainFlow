# [Benchmark] Add reproducible request cancellation workloads

[Upstream PR](https://github.com/vllm-project/vllm/pull/61143) · state: open · merged: False

## Original PR description

## Overview

Add reproducible client-abandonment workloads to the Python `vllm bench serve` client. This makes it possible to exercise serving when agent branches are discarded or users interrupt generation, while keeping intentional cancellations separate from request failures.

## Claims

- `--cancellation-rate` selects a fraction of requests using `--seed`; `--cancellation-delay` controls how long each selected request runs after client concurrency admission.
- The existing request coroutine is cancelled and its HTTP response context is unwound before the concurrency permit is released. Requests that finish before their deadline keep their normal result.
- Results distinguish `completed`, `failed`, and `cancelled`, with a detailed per-request cancellation list. Cancelled partial outputs are excluded from successful throughput and latency statistics.
- The feature is disabled by default. Readiness checks, warmups, and probes are not cancelled.

## Validation

Focused tests: **65 passed** across:

```bash
python -m pytest tests/benchmarks/test_serve_cancellation.py \
  tests/benchmarks/test_endpoint_request_func_timing.py \
  tests/benchmarks/test_rust_bench_cli_parity.py -q
```

Coverage includes real local HTTP streams for completions/chat/Responses, cancellation before the first token and during streaming, early completion, external cancellation, unrelated timeout propagation, semaphore admission, warmup exclusion, deterministic selection, and result accounting.

The focused suite ran on Python 3.12.15 with the current benchmark source tree mounted into an existing arm64 CPU vLLM container. Its native runtime was `0.31.1rc1.dev23+g43b4aaea3`; this was not a native build of the branch. The run used `--confcutdir=tests/benchmarks` to isolate the benchmark tests. Applicable non-Rust changed-file pre-commit hooks and `git diff --check` passed, including mypy, Python formatting, test tethering, and the Python CLI flag snapshot check. Rust formatting was checked separately with `cargo +1.95.0 fmt --all -- --check` from `rust/` and passed; compiled Rust tests were not run.

Three CLI runs against a local random-weight two-layer GPT-2 CPU server used 16 requests, 16 input tokens, 32 output tokens, and client concurrency 4:

| Cancellation rate | Completed | Cancelled | Failed | Counted output tokens |
| --- | ---: | ---: | ---: | ---: |
| 0 | 16 | 0 | 0 | 512 |
| 0.5 | 8 | 8 | 0 | 256 |
| 1 | 0 | 16 | 0 | 0 |

The enabled runs used a 0.01-second cancellation deadline. These are client-side outcomes; the runs do not establish how many requests had entered engine execution at cancellation. The server had no running or waiting requests afterward and accepted a subsequent completion. This validates the client workflow, not GPU behavior, performance gains, model quality, or server abort/KV reclamation timing.

## Details

Selection uses a separate random generator so it does not consume the RNG used for dataset sampling or request arrivals. The deadline starts after acquiring the client concurrency permit and before invoking the HTTP request function. Connection setup, server queueing, and generation count toward that deadline; client semaphore wait does not.

The helper uses `asyncio.timeout` around the existing request function. Intentional timeout is converted to a cancelled result after response cleanup; cancellation of the benchmark itself still propagates. No inference-engine or scheduler behavior changes.

This differs from #51030, which fails stalled socket reads to keep a benchmark from hanging. Here cancellation is an intentional workload parameter applied to a selected subset of requests, including healthy streams.

Supported backends are `openai`, `vllm`, `openai-chat`, and `openai-responses`. The Rust client's existing parity allowlist marks these settings as Python-only. The documentation explains how to run the workload and interpret its results. Cancelled partial tokens are not available from an interrupted endpoint function, so reported token throughput measures successful output rather than all server work. Detailed cancellation latency includes client cleanup.

- dilberx · comment · 2026-10-30T01:49:27Z · [source](https://github.com/vllm-project/vllm/pull/61143#issuecomment-6512955800)

The scheduling and metrics changes look correct. `len(tasks)` is the request index and `gather` keeps input order, so `cancellations` lines up with the other per-request lists. The request funcs catch `Exception`, so the `CancelledError` from `asyncio.timeout` gets through them.

I checked that the cancel reaches the server with aiohttp 3.14.3 and a local streaming server, using the connector settings from `serve.py`. After the timeout the connection is closed, the server handler gets `CancelledError`, and the next request opens a new connection.

Some small things:

1. `int(len(input_requests) * cancellation_rate)` can round down to 0, e.g. `--num-prompts 10 --cancellation-rate 0.05`, and nothing gets cancelled. A warning there would help.
2. `--cancellation-delay 0` raises even when the rate is 0. The check could run only when `cancellation_rate > 0`.
3. If one request is cancelled and all the others fail, the "All requests failed" warning is skipped.
4. Can `openai-responses` be supported too? It streams the same way as chat.

Needs a rebase as well.
