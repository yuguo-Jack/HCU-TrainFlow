# [Bugfix][Responses API] Fill reasoning summary when reasoning.summary is set

[Upstream PR](https://github.com/vllm-project/vllm/pull/63238) · state: closed · merged: False

## Original PR description



## Overview

Fixes #63184. The Responses API accepts and echoes `reasoning.summary`, but every reasoning item comes back with `summary: []`. With this PR, when `reasoning.summary` (or the deprecated `generate_summary`) is set, each reasoning item's text is mirrored into `summary` as a `summary_text` part, in non-streaming responses and in the stream. Approach proposed in https://github.com/vllm-project/vllm/issues/63184#issuecomment-6354976724.

## Claims

- With `reasoning.summary` set, reasoning items carry `summary=[{"type": "summary_text", "text": <reasoning text>}]` in the non-streaming response, in `response.output_item.done` and in `response.completed`, for both the simple-parser and Harmony paths.
- In streaming, each reasoning item gets `response.reasoning_summary_part.added`, `response.reasoning_summary_text.delta` (one delta with the full text), `response.reasoning_summary_text.done` and `response.reasoning_summary_part.done`, right before its `response.output_item.done`. Sequence numbers stay contiguous.
- Without `reasoning.summary`, output and events are unchanged (`summary: []`, no summary events).

## Details

**Root cause:** `summary=[]` is hard-coded where reasoning items are built (`responses/utils.py`, `responses/harmony.py`, `responses/streaming_events.py`), and `request.reasoning.summary` is never read.

**Fix:**
- `utils.py`: `wants_reasoning_summary(request)` and `fill_reasoning_summary(item)`. The second sets `summary` from the item's `reasoning_text` content and leaves items with an existing summary or no content alone.
- `serving.py`: applied at the two points every path already goes through, instead of threading the request into the five item builders:
  - `responses_full_generator` fills the final `output`, which covers non-streaming, `response.completed`/`response.incomplete` and stored responses;
  - `responses_stream_generator` fills each reasoning `output_item.done` and emits the summary events before it.
- `streaming_events.py`: `emit_reasoning_summary_events`. `protocol.py`: the four summary event types are added to `StreamingResponsesResponse`.

**Design notes:**
- vLLM has no separate summarizer, so the summary is the reasoning text itself. `content` stays the canonical field (#36516), and input conversion already prefers `content` over `summary`, so echoing the items back or using `previous_response_id` doesn't duplicate reasoning in the prompt.
- The summary is sent as one delta when the reasoning item completes rather than per token, so streamed reasoning isn't duplicated token by token.
- The alternative, a 400 for `reasoning.summary`, would break clients such as Codex that send `summary: "auto"` by default.

- sfeng33 · COMMENTED · 2026-11-03T17:50:33Z · [source](https://github.com/vllm-project/vllm/pull/63238#pullrequestreview-5757018568)

Thanks for the PR. I looked at the issue and at how clients use this field, and I am not sure this change is worth taking.

Nothing is broken on main. vLLM accepts `reasoning.summary`, returns 200, and puts the full reasoning text in `content`. Codex sends `summary: "auto"` by default and works fine against vLLM today. It only shows reasoning from the `summary` field unless the user sets `show_raw_agent_reasoning`, so the result is an empty reasoning panel, not a failure. 

vLLM has no summarizer. This PR copies the raw reasoning text into `summary` as is. That gives `auto`, `concise`, and `detailed` the same output, which is not what the field means upstream. It also doubles the reasoning text in every reasoning item and in the stream, and sends the full text as one delta at the end of the reasoning instead of while it streams. A client that renders only the summary still sees nothing until the reasoning finishes. So the upside is small.
