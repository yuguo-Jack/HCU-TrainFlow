# [CI] Enroll four Nightly steps and three AMD mirrors in automatic sharding

[Upstream PR](https://github.com/vllm-project/vllm/pull/64174) · state: closed · merged: True

## Original PR description

## Overview

Enrolls four Nightly steps and three of their AMD mirrors in `automatic_shard`, continuing the earlier enrollment batches (#61999, #62039, #64115). This PR only sets the flag; it changes no tests or commands. A step that fits in one job runs as one job, unchanged, and splits without another CI change once its tests outgrow it.

## Claims

| Step | Planned shards | AMD mirror |
|---|---:|---:|
| `multi-modal-models-extended-pooling` | 3 | 2 |
| `lm-eval-deepseek-v32-tp-8xh200` | 1 | 1 |
| `lm-eval-deepseek-r1-tp-8xh200` | 1 | 1 |
| `lm-eval-hisparse-nightly-4xb200` | 1 | none |

- Each job runs the same tests, environment and timeout as on main. One gsm8k config takes about as long as a whole shard, so the planner keeps the lm-eval steps whole for now.

## Validation

- Planned each step and mirror with ci-infra main's `runtime_shard.plan_step` against main's timings, and rendered each with the pipeline generator as a PR build and in main's OTel mode.
- `/ci run` (98071) on this head, plus a build scoped to the three AMD mirrors it leaves behind the block step (98079): every job passed. Extended Pooling ran its planned 3 shards (mirror: 2) with the same pass and skip counts as main; the lm-eval steps ran as one job each, as on main.

## Details

- **Extended Pooling is back.** An earlier build of this PR failed it on the ColUltraVBERT checkpoint; main fixed that in #64189 and its nightly passes the step again.
- **Cost.** Extended Pooling's machine time rises by about a third: each extra shard repeats job setup and the model loads its test files share. In exchange its wall time halves. It runs nightly, so we keep the shorter wall time.
- **Dropped from this batch.** `lm-eval-humming-b200-act` fails on main from a regression there. It comes back in a later batch once main passes it.
- **Timeouts unchanged (human).** `timeout_in_minutes` stays per job. Fallback-aware timeouts belong in a central timeout setting.
