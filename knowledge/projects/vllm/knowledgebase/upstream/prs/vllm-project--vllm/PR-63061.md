# [Rust Frontend] Serialize unset chat response fields as null like Python

[Upstream PR](https://github.com/vllm-project/vllm/pull/63061) · state: closed · merged: True

## Original PR description

## Overview

Python returns a non-streaming chat completion via `model_dump()`, so every unset optional field is an explicit `null`. The Rust non-streaming chat types already serialize `None` as `null`, but they lack several of Python's fields, so Rust omits keys that Python sends. This PR adds those fields as always-`None`, so a Rust chat response has the same keys as Python's.

## Claims

For a plain non-streaming chat request, the Rust response now includes these keys as `null`, as Python does:

| Object | Keys | Why Rust has no value |
|---|---|---|
| response | `service_tier` | Python never sets it either |
| response | `prompt_text` | Rust rejects `return_prompt_text: true` |
| `choices[]` | `routed_experts` | not wired into the chat route yet |
| `choices[]` | `weight_versions` | Rust rejects `return_weight_versions: true` |
| `choices[].message` | `refusal`, `annotations`, `audio`, `function_call` | never produced |

Streaming is unchanged: Python serializes chunks with `exclude_unset=True`, and the Rust stream types skip `None`.

- The route test `non_stream_chat_returns_json_response` now asserts an explicit `null` for each new key; the expected set comes from Python's `ChatCompletionResponse(...).model_dump()` on the base commit. On the base it fails with ``expected explicit null `service_tier` ``.

## Details

The fields live in the non-streaming chat response DTOs (`routes/openai/chat_completions/types.rs`), which are built only in `collect_chat_completion`. Wire shape is the server crate's concern and no lower crate produces these values, so nothing below `vllm-server` changes; the shared `Usage` type is untouched.

Not covered here: `usage.prompt_tokens_details.multimodal_tokens` (open vllm-project/vllm#60624), and `usage.prompt_tokens_details.created_cache_tokens`, where Python sends the engine's cache-creation count rather than `null`, so the fix is to carry that value in a separate change.

Not a duplicate: no open PR adds these keys to the Rust chat response.
