# [Bugfix] Annotate DFlash draft KV cache groups via the trailing-layer rule

[Upstream PR](https://github.com/vllm-project/vllm/pull/61545) · state: closed · merged: False

## Original PR description



## Overview

Fixes #61443: DFlash drafters' KV cache groups were never annotated `is_eagle_group`, so the EAGLE last-block-drop optimization was silently disabled and consumers fell back to the conservative flag-all path. The positional (trailing-layer) detection rule now covers `method="dflash"`.

## Claims

- With `method="dflash"` and `use_eagle_block_drop()` on, the draft group (e.g. a DFlash2 uniform sliding-window group) is flagged `is_eagle_group` when the draft layers register after the target layers.
- No behavior change for other speculative methods; the exact-partition guard still applies before the positional rule fires.

## Validation

- Reproduced with a CPU-only script derived from the issue's repro (GLM-5.3-Flash-shaped hybrid: MLA + Mamba target, 3-layer DFlash2 SWA drafter, BLHNC layout): before the fix, the "no KV cache group could be identified as the draft model's" warning fired and 0 groups were flagged; after the fix, exactly the draft group is flagged and no warning fires. Mamba groups stay unflagged.
- New regression test `test_dflash_draft_group_annotated_by_trailing_layer_rule` fails on unfixed main and passes with the fix.
- `tests/v1/core/test_kv_cache_planning.py -k "eagle or draft or mtp or trailing or unidentifiable"`: 17 passed.
- Full `tests/v1/core/test_kv_cache_planning.py`: 37 passed, 32 failed — the 32 failures are byte-identical on unmodified `main` (verified via a clean worktree): they construct real `ModelConfig`/`VllmConfig`, which requires HuggingFace Hub network access unavailable in this sandbox. My change adds the 1 extra passing test and introduces no new failures.
- No GPU in this environment, so no end-to-end serving eval; coverage is at the planning layer where the annotation logic lives (CPU-only tests).

## Details

**Root cause.** `_annotate_eagle_groups` has two detection rules. Rule 1 (spec-driven) needs `non_causal_multi_token_decode` on the spec — declared only on `MLAAttentionSpec` (set by Kimi-K3 DSpark drafters). Rule 2 (positional: flag the group holding the last registered layer) was gated by `_uses_trailing_mtp_layers`, which returned true only for `method == "mtp"` or DeepseekV4/V4.1 `dspark`. DFlash drafters register their KV layers after the target layers, but their plain GQA `SlidingWindowSpec` layers carry no marker — so neither rule fired, `is_eagle_group` stayed false everywhere, and `KVCacheCoordinator` fell back to flagging *all* groups (which, for hybrids with Mamba, also sweeps Mamba groups into the drop, where align-mode checkpointing never produces the widened lookup window).

**Design decisions / limitations.**
- Chose the issue's option 1 (extend the trailing-layer rule) over option 2 (a spec marker on drafter SWA layers): the rule already exists, is guarded by the exact-partition check, and the diff stays minimal.
- Deliberately **not** extending to `eagle3`: the existing `test_non_mtp_eagle_hybrid_still_warns` (parametrized with `eagle`/`eagle3`/`dspark`) pins the warn behavior for those methods, and the registration-order invariant for eagle3-aux recipes isn't established by a concrete case. That can be a follow-up (likely via the marker approach).
- Function name `_uses_trailing_mtp_layers` kept as-is (private, docstring updated) to keep the diff small.

**Duplicate check.** No open PR references #61443 (`gh pr list --state open --search "61443 in:body"` empty as of 2026-10-14); the issue timeline shows no linked fix PR and the filer did not state one was coming.
