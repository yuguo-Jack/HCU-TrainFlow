# [Bugfix][Frontend] Keep qwen3/MiMo unclosed last tool parameter only when the call is closed

[Upstream PR](https://github.com/vllm-project/vllm/pull/59882) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #57699. Qwen3-family models sometimes close `</function>` without closing the last `</parameter>`, and the parser drops that last value. This PR keeps the value when the call is closed and still drops it when output stops early, for example at `max_tokens`. MiMo has its own copy of the converter in `vllm/parser/mimo.py` and gets the same fix.

## Claims

- A closed call with an unclosed last parameter now returns that parameter, in streaming and non-streaming. On `main`, non-streaming drops it and streaming ends in unterminated JSON.
- Output that stops before `</function>` behaves as on `main`: the unfinished value is dropped. A cut-off `rm -rf /tmp/build` cannot come back as a complete `{"cmd": "rm -rf /"}`.
- The fix covers every parser built on `qwen3_config` (Qwen3, Seed-OSS, Step3.5, Nemotron-V3) and MiMo.

## Validation

Unit tests: two new parametrized tests in `tests/parser/engine/test_qwen3.py` run against all five parsers built on `qwen3_config`: `Qwen3Parser`, `MiMoParser`, `SeedOssParser`, `Step3p5Parser` and `NemotronV3Parser`. The closed-call test fails on `main` for all five with `{'city': 'Tokyo'}` and passes here. The cut-off test passes on both and guards the safety behavior.

```bash
pytest tests/parser -q   # 6308 passed
pre-commit run --files vllm/parser/qwen3.py vllm/parser/mimo.py tests/parser/engine/test_qwen3.py
pre-commit run mypy-3.12 --hook-stage manual --files vllm/parser/qwen3.py vllm/parser/mimo.py tests/parser/engine/test_qwen3.py
```

`tests/tool_parsers` passes except `test_llama3_json_tool_parser.py`, which also errors on `main` because it needs the gated `meta-llama/Llama-3.2-1B-Instruct` repo.

End to end, CPU only: I generated a tool call with `Qwen/Qwen3.5-0.8B` (greedy, HF transformers) and sent its tokens through `vllm launch render --tool-call-parser qwen3_coder` via `/v1/chat/completions/derender`. That endpoint runs the same parsing code as `vllm serve`. Generation ran outside vLLM because the CPU backend cannot run Qwen3.5 on Apple Silicon.

Model output: `<tool_call>\n<function=run_shell>\n<parameter=cmd>\nrm -rf /tmp/build_cache_old\n</parameter>\n</function>\n</tool_call>`

| Input | `main` | This PR |
|---|---|---|
| Output as generated | correct | correct |
| Cut after `rm -`, `finish_reason=length` | non-stream `{}`, stream `{"cmd": "rm -` | same as `main` |
| `\n</parameter>` removed before `</function>` | non-stream `{}`, stream `{"cmd": "rm -rf /tmp/build_cache_old` | `{"cmd": "rm -rf /tmp/build_cache_old"}` in both modes |

I made the third input by deleting the tag from the real output. #57699 shows a real model emitting this shape (Qwen3.8-27B, BFCL `live_simple_40-17-0`, temperature 0). I did not run an accuracy eval such as BFCL.

## Details

Root cause: `_qwen3_arg_converter` adds the trailing unclosed parameter only when `partial=True`. The final call (`partial=False`) runs on `TOOL_CALL_END`, and the engine emits that event in two cases: when it reads `</function>`, and in `StreamingParserEngine.finish()` when output ends inside an open call. The converter got the same text in both cases, so it could not tell them apart.

Fix: the `(TOOL_ARGS, FUNC_END)` transition now emits `ARG_VALUE_CHUNK` before `TOOL_CALL_END`, the way the `PARAM_START` and `PARAM_END` transitions already do. `</function>` then reaches the converter's input only for a closed call. Each converter strips it and keeps the trailing value when `partial or closed`. The event order matters because `TOOL_CALL_END` runs the final conversion.

Related PRs:
- #57707 targets the same issue by removing the `partial` check. On the setup above, its cut-off case returns `{"cmd": "rm -"}` as valid JSON, and only `finish_reason=length` tells the client the value is incomplete. It also leaves MiMo unchanged.
- #58349, #58418 and #58437 fix the same pattern in MiniMax-M2, GLM-4.7 and DeepSeek, in other files.
- #53739 handles the unterminated streaming JSON for cut-off calls in the engine. This PR leaves that case alone.

Scope: nothing under `vllm/parser/engine/` changes, following `vllm/parser/AGENTS.md`. MiMo is covered by unit tests only; its checkpoints are too large for a local CPU run.
