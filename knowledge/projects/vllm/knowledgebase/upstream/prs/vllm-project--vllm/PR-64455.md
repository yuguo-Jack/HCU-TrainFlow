# [CI][Test] Compare compile-mode logprobs with tolerance on real weights

[Upstream PR](https://github.com/vllm-project/vllm/pull/64455) · state: closed · merged: False

## Original PR description

## Purpose

`compile/fullgraph/test_basic_correctness.py::test_compile_correctness[*-test_setting0]` (granite-3.0-1b-a400m-instruct) fails with `Results for model=... are not the same` on XPU.

Two causes, both in the test harness rather than the compiler:
1. `compare_all_settings` forces `--load-format dummy`. With random weights the distribution is near-uniform (top-5 logprobs ~ -10.7, tied), so the *set* of top-5 tokens is arbitrary and flips between compile modes.
2. With real weights, `generate_close` still compared the rounded top-5 dict by exact equality, although the comment says "only compare if the output is close". bf16 noise alone moves top-5 logprobs by up to ~0.5 against an fp32 HF reference (granite-3.0-1b-a400m, prompt "Hello, my name is": fp32 `-2.593/-2.625/-2.689/-2.78`, bf16 `-2.552/-2.989/-2.989/-3.239`). Observed XPU eager vs `STOCK_TORCH_COMPILE`: `-2.45` vs `-2.66`, `-2.76` vs `-3.10`.

Changes:
- Granite MoE case uses real weights (`--load-format auto`).
- `generate_close` requires the same top-1 token and shared top-5 logprobs within 0.5 (`_assert_top_logprobs_close`). Only this test uses `generate_close`.

Not a duplicate: searched open PRs/issues in vllm-project/vllm for `test_compile_correctness` and `fullgraph test_basic_correctness granite`; none found.

## Test Plan / Result

```
cd tests
ZE_AFFINITY_MASK=4 VLLM_TEST_DEVICE=xpu pytest -q \
  "compile/fullgraph/test_basic_correctness.py::test_compile_correctness[True-test_setting0]" \
  "compile/fullgraph/test_basic_correctness.py::test_compile_correctness[False-test_setting0]"
```
Before: `[True-test_setting0]` fails with `AssertionError: Results for model='ibm-granite/granite-3.0-1b-a400m-instruct' are not the same` (dummy weights: `' cross'` vs `'Ve'` tie flip at -10.79). With real weights and exact compare it fails with `-2.45` vs `-2.66`.
After: `2 passed in 859s` (validated on an XPU box, on a slightly older base than this branch).

Not run: CUDA. The tolerance is a judgement call based on the bf16 spread above; happy to tighten if CUDA data supports it.
