# [Core] Priority scheduling: preempt for a waiting request under KV pressure

[Upstream PR](https://github.com/vllm-project/vllm/pull/63350) · state: closed · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Under `--scheduling-policy priority`, a waiting request never preempts running requests for KV cache blocks, so a high-priority request that finds the KV cache full waits behind running requests of a lower priority: the KV cache case of #40004, which #54530 (`max_num_seqs` only) leaves out. The V0 scheduler had this preemption (`_schedule_priority_preemption`, from #5958, in v0.6.2 to v0.10.2), on its path without chunked prefill only; the V1 port of priority scheduling (#19057) preempts only in the running loop, and V0 was removed in v0.11.0. This adds `--max-priority-preemptions-per-step N`, off by default, to preempt for it in the V1 scheduler, with chunked prefill and asynchronous scheduling.

## Claims

- With `N > 0`, before the running requests are scheduled, the waiting request of the highest priority that the waiting loop can schedule in the step preempts up to `N` running requests of a strictly lower priority when the KV cache lacks room for its whole sequence: in the order the running loop preempts in (the lowest priority, then the latest arrival), as few as make room, and none if `N` would not.
- The room is net of the request's prefix cache hit, counts a block as freed once all of its holders are preempted, and counts the blocks the running decodes take until the preempted requests' blocks are freed. Room is not made for the request again until the waiting loop has tried its allocation.
- Preempted requests take the running loop's path (`_preempt_request`, `preempted_req_ids`) and are not resumed into the blocks that an in-flight prefill of a higher priority still needs.
- Off (the default), scheduling is unchanged: per-step schedules of a replayed workload are byte-identical to main's, and the scheduler tests give main's results.
- A counter, `vllm:num_priority_preemptions`, counts the running requests preempted this way; it is registered only with `N > 0`.
- On an RTX 5060 Ti (the change ported to vLLM v0.32.0): with the KV cache filled by two lower-priority requests, a priority 0 request's time to first token goes from 4,968 to 290 ms (medians); beside 12 closed-loop agent sessions, two calls' TTFT p95 from 6,830 and 7,158 ms to 4,111 and 1,073 ms; beside 24 coding-agent sessions replayed from traces, two voice calls' voice-to-voice p95 from 10,523 to 5,085 ms, the agents' tokens/s changing by +3%.

## Details

- **Before the running loop.** The pass runs at the start of `schedule()`, so a preempted request has nothing scheduled in the step: no budget, block, encoder or prefix-hash state to roll back (the class of bugs in #59907).
- **Which request.** The waiting request of the highest priority, over both waiting queues, that the waiting loop can schedule in the step: not one loading its KV (until the load is done), compiling its grammar, awaiting streaming input or awaiting output from before its preemption, nor one whose LoRA adapter cannot join the running requests' under `max_loras`. A blocked request ahead of it does not turn the preemption off for the requests behind it.
- **Whole-sequence room.** The room needed is the request's whole remaining sequence (as `scheduler_reserve_full_isl`, the default, admits it), net of its local prefix cache hit and with an encoder-decoder model's cross-attention blocks, what in-flight prefills still need (as an async KV load is admitted) and, while requests run, the watermark. Preempting releases the blocks whose every holder is a victim or a deferred free, except those of the request's own prefix cache hit, and a mid-prefill victim's reservation.
- **The decodes' growth.** The room counts the blocks the running decodes take until the victims' blocks are freed: in this step, and with deferred block frees in the next one too. A request that fits after this step's growth preempts nothing.
- **No second round.** Once room is made for a request, no room is made for it again until the waiting loop has tried its allocation, so a request the waiting loop then skips cannot have a victim preempted every other step.
- **No resume between chunks.** With prefix caching, a preempted request's freed blocks stay cached, and stock admission would resume it into them between the chunks of the request it made room for. So while a prefill of a higher priority is in flight, a new or preempted request is admitted only beside what in-flight prefills still need, and a request preempted in a step is not resumed in it.
- **Victim order.** The running loop's own, the lowest priority and then the latest arrival, which spares older work; as few as make room.
- **Costs.** Victims recompute their prefill on resume unless prefix caching keeps their blocks or an offloading connector restores them (the OffloadingConnector keeps a victim's generated tokens only with `offload_prompt_only: false`, as these measurements set it; its default keeps prompts only); lower-priority admissions are conservative while a higher-priority prefill is in flight. Per step with the option on: the first request of each waiting queue (a scan of the queue only when that one cannot be scheduled) and, while a running request has a lower priority than it, its prefix cache lookup, a sort of those running requests and one pass over the in-flight prefills' remaining blocks; when it is short of blocks, a count of the blocks the candidates would release, and only when they would make room and a bound on the decodes' growth (one block per KV cache group a step, without speculative or lookahead tokens) does not settle the fit, a count of that growth. The CPU cost table above gives the time. No room is made while paused, in a step that defers prefills, or while the KV connector has pending block frees (as in the running loop).
- **Not a duplicate.** #54530 and #45561 preempt at `max_num_seqs` only. #40087, and #45558, which #54530 supersedes, also preempt inside the waiting loop after `allocate_slots` fails, one request at a time, rolling back requests already scheduled, and can preempt without making room. #59963 (#59907) changes the running loop's victim choice. V0's `_schedule_priority_preemption` (#5958) ran only without chunked prefill, in a step that scheduled no prefill, and preempted until the request fit, with no cap and even when preempting every lower-priority request would not make room; its victims were recomputed. This pass runs under chunked prefill, preempts at most `N` and only when they make room, and its victims take the running loop's path, so prefix caching or an offloading connector keeps their KV as for the running loop's victims.
- **Open questions.** If #58037 lands, should `vllm:num_priority_preemptions` become a reason of its `vllm:num_preemptions_by_reason` instead? If #53723 lands, should its `preemption_victim` policy order these victims? Should the admission rule count only the in-flight prefills of a higher priority?

<summary>Root cause of the GPU finding behind the admission rule</summary>

- **The per-step cost**, with the same schedules (the CPU cost table under Validation). <summary>Changes since the first revision (e29d6b761)</summary>

- Victims go in the running loop's preemption order, the lowest priority and then the latest arrival, instead of the most blocks first, which made the request with the largest context the first victim at every turn.
