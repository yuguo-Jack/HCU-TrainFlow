# [Bugfix][KV Offload][P2P] Avoid leaking failed IDs for finished requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/64300) · state: closed · merged: True

## Original PR description

## Overview

Finishing a request with a load in flight can permanently put its KV request ID back into `_failed_req_ids` after `on_request_finished()` has removed it. Repeated mid-load cancellations accumulate stale IDs for the lifetime of the process. Reusing an ID on a retry is a secondary symptom: the stale entry suppresses that request's remote lookup.

Extracts **C** from #61667 as [requested in review](https://github.com/vllm-project/vllm/pull/61667#pullrequestreview-5651552184). Refs #61532.

## Claims

- Finished requests do not permanently repopulate the failed-ID set through immediate cancellation failures, already-buffered outcomes or session close.
- Late failures still complete transfer-job cleanup without restoring finished IDs to the failure set.
- Close cleanup and request-ID reuse preserve this distinction; unfinished failures continue to trigger recomputation.

## Details

Carry a default-false request_finished flag on the load state and LoadResult. Finish marks both in-flight loads and already-buffered results. Polling and close omit finished IDs from failure bookkeeping while still returning failed jobs for cleanup. This is independent of deferred slot release.

- liranschour · COMMENTED · 2026-10-29T13:22:46Z · [source](https://github.com/vllm-project/vllm/pull/64300#pullrequestreview-5698372491)

Thanks for splitting this out. I traced the path on current main and the fix is needed, though I think the PR undersells why.

**The bug is real, and it's mainly a leak.** In `on_request_finished`, `_failed_req_ids.discard(kv_request_id)` runs *before* `session.finish_request()`. `client.finish()` then calls `_abort_load()` for every in-flight load, which immediately buffers a `LoadResult(success=False)`. On the next `_poll_once`, `if not lr.success: self._failed_req_ids.add(...)` puts the id straight back. `close()` does the same for finished requests whose AbortAck hasn't arrived (they still have `st.loads`). That `discard` is the only place entries ever leave the set, so every request aborted mid-load (client disconnect, peer death with loads pending) leaves an entry in `_failed_req_ids` for the life of the process. Id reuse is the secondary symptom; the orchestrator contract says `kv_request_id` is unique, although an orchestrator that reuses the client's `X-Request-Id` will hit it on retries.

**Approach looks right.** A per-load / per-`LoadResult` `request_finished` flag is the right granularity. A manager-side "live ids" set would wrongly poison a reused id whose old failure arrives late, and `test_finish_marks_buffered_result_before_request_id_reuse` covers exactly that case.

Requests:

1. **Reframe the description around the leak**: "every mid-load abort permanently adds an entry to `_failed_req_ids`", with reuse as the secondary effect. Otherwise the natural reply is "ids must be unique".
2. **Please drop the `docs/features/kv_offloading_usage.md` change.** It describes internal bookkeeping, not anything the orchestration layer has to do, and it sits above the intro of the "Orchestration-Layer Protocol" section.
3. **The model-based e2e test is heavy for `test_sessions.py`.** It loads SmolLM2 on a GPU and needs a 78-line `p2p_control_peer` fixture used only by this test, in a file that is otherwise unit tests. The parametrized `test_late_failure_preserves_request_finish` plus the manager test already cover the logic. I'd drop it, or move it alongside the other model-based P2P tests.
4. **Add a manager-level regression test**: `on_request_finished` with a load in flight, then `get_finished_jobs()`, then assert `_failed_req_ids` is empty. That locks in the leak fix directly.
5. Nits:
   - `getattr(loads[0], "request_finished", False)` in the tests was only needed to run against the base branch; access the field directly.
   - The `test_failed_load_records_kv_request_id` docstring still says the id "must" be added; that's now only true for unfinished requests.
