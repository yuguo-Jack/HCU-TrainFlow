# [ROCm][Perf] Muse Spark: MXFP4 MoE on native routes and column-sharded at TP prefill, via AITER's two-stage API

[Upstream PR](https://github.com/vllm-project/vllm/pull/64461) · state: open · merged: False

## Original PR description

## Overview

Muse Spark normalizes each expert's output before the top-k weighted sum, so its MoE must return the unweighted per-route outputs `[T, top_k, H]`. On ROCm the MXFP4 experts get them by repeating the normed input `top_k` (8) times and calling AITER `fused_moe` with one route per row, and at TP > 1 every route's partial sums over all `H` columns are then reduce-scattered before the norm.

This PR runs the experts through AITER's two-stage MoE API (ROCm/aiter#7135):

- **Native routes.** One input row per token, on the `[T, top_k]` routes; stage 2 writes each route to its own row (`per_slot`). The kernels are the ones AITER selects for today's repeated-input call (`config_shape`), so the route outputs are bitwise identical.
- **Column-sharded stage 2 at TP prefill.** For eager batches of ≥ 1024 tokens, the MXFP4 stage-1 output and its scales are all-gathered along the intermediate dim and stage 2 runs against this rank's `H / tp` output rows of `w2`. The norm then needs only a `[T, top_k]` sum-of-squares all-reduce and an all-gather of the finalized columns, instead of a `[T, top_k, H]` reduce-scatter.

It replaces #63290 (native routes) and #63263 (column-sharded down projection), which reached into AITER internals (`_fused_moe_impl` with `_metadata_transform` and `_stage2_override`) and could not be combined. With the public API both are one code path. #63290 and #63263 are closed in favour of this PR.

**Dependency.** Needs ROCm/aiter#7135. With an AITER that lacks the API (including the current ROCm images), nothing changes: every batch takes the existing repeated-input path, and the GPU tests of this PR skip.

8×MI355X, Muse Spark Open MXFP4 + DSpark (7 speculative tokens), AMD Day 0 recipe; `main` (`77f58e5304`) vs this PR, same node and arguments, AITER 0.1.26 + the AITER PR for this PR's arms, stock AITER 0.1.26 for the baseline:

- **TP8 + EP8 + DSpark** (recipe default): TTFT −8% at 2k and **−12%** at 8k / 16k / 4 × 8k. Output throughput +10% at c16 and +12% at c32.
- **Accuracy.** GSM8K TP8 0.9492 → 0.9530 (paired McNemar p = 0.47); TP8 + EP8 0.9477 → 0.9477, the same answer on all 1319 questions. TP8 + EP8 greedy outputs (text and every logprob) are identical to the baseline. At TP8 they are identical too with the column-sharded stage 2 off; with it, the sum is rounded once instead of per rank, see Numerics.
- **Memory.** TP8: the second `w2` costs 15.9 GiB per GPU, KV cache −9.1%. TP8 + EP8: KV cache +1.0%, the `[T * top_k, H]` MoE input is gone.
- No core changes, everything is in `vllm/models/muse_spark/amd/`, and no switches: with an AITER that has the API, the native routes are always used (their outputs are identical), and the column-sharded stage 2 at TP > 1 without EP.

## Details

**Native routes.** `staged_fused_moe` calls `fused_moe_stage1` with the native `[T, top_k]` routes, unit weights and `config_shape=(T * top_k, 1)` (`+1` slot under EP, matching today's masked-slot key), then `fused_moe_stage2(per_slot=True)` into the modular kernel's `[T, top_k, H]` output. The pre-expert norm writes one row per token (`fused_rmsnorm_expand(..., 1)`) for those batches. A batch uses it when `supports_stage2_overrides` holds for its config (a lookup, cached per batch size) and, under TP, from 65 tokens up: with 256 experts the native-route sorting does not pay off for smaller TP batches. Under EP every batch size uses it.

**Column-sharded stage 2** (TP > 1, no EP, eager, ≥ 1024 tokens):

- *Weights, at load.* Before the AITER shuffle, one all-to-all turns this rank's `w2[E, H, I/TP]` and its scales into `w2[E, H/TP, I]`, shuffled like the regular `w2` (kept for decode and small batches).
- *Experts.* Between the stages, the MXFP4 stage-1 output and its E8M0 scales are all-gathered along the intermediate dim. Each rank's slice is whole 32-element quant groups and whole scale tiles, so the gathered tensors equal the full-width quantization exactly. `fused_moe_stage2(per_slot=True, w2=..., a2=...)` then gives each route's exact output on this rank's columns.
- *Finalize.* An all-reduce of the per-route sum of squares (`[T, top_k]` fp32), two Triton kernels for the norm and the weighted top-k sum on the local columns, and an all-gather of `[T, H]`. At T = 8192 per layer a 512 MiB reduce-scatter becomes about 136 MiB of all-gathers plus 256 KiB of all-reduce.
- The decision depends only on shapes, the capture state and AITER's tuned configs, so all ranks agree. Graph capture never reaches it (the recipe captures ≤ 512 tokens).

**Numerics.** Native routes: identical. Column-sharded: both paths compute the same products from the same quantized inputs; the baseline rounds each rank's partial sum to BF16 and reduces in BF16 (`VLLM_ROCM_MUSE_MOE_REDUCE_DTYPE=bf16` in the recipe), this path accumulates the full intermediate dim in fp32 and rounds once. The unit test bounds the difference by `2^-8 · (Σ|partial| + |sum|)` with a 2× margin.

**Memory.** Column-sharded: per MXFP4 layer and rank, 256 MiB of FP4 plus 16 MiB of scales, 15.9 GiB over 60 layers at TP8; no extra workspace (the route outputs reuse 1/TP of the output buffer). Native routes: the `[T * top_k, H]` expanded input is no longer allocated (+1% KV cache under EP).

**Fallback.** AITER without the API, configs whose stage 2 is not a FlyDSL MXFP4 kernel, padded / non-SiLU / non-BF16 experts, or TP batches < 65 tokens: the existing repeated-input path, unchanged.

**Complexity.** 746 non-test lines:

- `staged_moe.py` (344): the AITER API calls, the support check, the `w2` reshard and the activation and scale gathers.
- `ops/column_sharded_finalize.py` (199): the two Triton finalize kernels.
- `muse_moe_runner.py` (+199 / −16), `model.py` (+4 / −1): wiring.

Why ROCm/aiter#7135: AITER's public `fused_moe` only returns the top-k sum, but Muse Spark normalizes each route before summing, so today we repeat the input top_k times. That PR splits `fused_moe` into `fused_moe_stage1` / `fused_moe_stage2`, which gives us:
- per-route stage 2 output, so the experts run on the native `[T, top_k]` routes;
- a replaceable stage 2 `w2` and input, which the column-sharded path needs (the gathered stage 1 output times this rank's `w2` rows).

Without it, vLLM would have to call the private `_fused_moe_impl(_stage2_override=...)` hook and re-derive the FlyDSL kernel arguments itself. That couples vLLM to AITER internals that can change in any release: a renamed hook breaks the model at load, and a change in kernel selection or argument layout can silently pick a different kernel or give wrong outputs. The ROCm CI pins one AITER version, so it would not catch this before an image bump. The public API keeps those internals inside AITER.
