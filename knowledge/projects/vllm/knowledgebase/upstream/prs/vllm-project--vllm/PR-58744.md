# [Bugfix][MLA] Gather nvfp4_ds_mla chunked-context KV with the NVFP4 kernel

[Upstream PR](https://github.com/vllm-project/vllm/pull/58744) · state: closed · merged: True

## Original PR description

## Status (2026-10-15)

Reworked after @zyongye's review (thanks — every point was right) and @LucasWilkinson's stu-cao/vllm#2, which proposed the same `seq_starts` change; rebased onto `main` `19b0efce30`. Lucas's kernel-level test (random cache bytes, non-block-aligned starts, bit-exact against the same slots gathered without starts) is included as his commit in `tests/kernels/attention/test_cache.py`. Where this differs from #2: the BF16 workspace hunk is dropped (zyongye's point 1, it was unreachable) and DCP is rejected at startup instead of being left to fail in the generic gather (point 4).

- **`seq_starts` on the NVFP4 gather kernel** instead of a block-table shim. `cp_gather_and_upconvert_nvfp4_kv_cache` gains an optional `seq_starts` like its fp8 twin (`token_offset = out_token - workspace_starts[req] + seq_starts[req]`), and the dense dispatch passes `chunk.starts` exactly as the `fp8_ds_mla` branch does. `shift_block_table_to_starts`, its alignment precondition, the clamp, the per-chunk gather and its CPU test are gone. Other callers are unchanged (the argument defaults to `None`).
- **Dropped the `MLACommonMetadataBuilder` workspace hunk and the `fp8_query` test arm.** `nvfp4_ds_mla` is only accepted by `FlashMLASparseBackend`, whose builder (`SparseMLACommonMetadataBuilder`) allocates its own BF16 workspace and hard-codes a BF16 prefill query, so neither was reachable.
- **DCP is rejected at startup** (`VllmConfig.validate_nvfp4_kv_cache_with_mla`) instead of in the per-layer forward on the first request with context; covered by `tests/test_config.py::test_nvfp4_ds_mla_rejects_decode_context_parallelism`.
- The raw `kv_c_and_k_pe_cache` pass is intentional: the `nvfp4_ds_mla` cache is allocated as `torch.uint8`. The three other gather dispatch sites that still send `nvfp4_ds_mla` to the generic gather (`mla_attention.py` DCP path, `kimi_k3/nvidia/mla.py`, `sparse_mla_attention.py`) are unreachable today and left for a follow-up.

Verification on the rebased head (`dc6aa4ae53`, B300 SM103, from-source build): **17 passed, 0 failed** — `test_mla_prefill_context_nvfp4.py` (1, the `seq_starts` path on real NVFP4 rows), `test_mla_context_chunks.py` (14), `test_config.py::test_nvfp4_ds_mla_rejects_decode_context_parallelism` (2); registered schema `cp_gather_and_upconvert_nvfp4_kv_cache(..., int batch_size, Tensor? seq_starts=None)`; torch 2.14.0+cu130, `TORCH_CUDA_ARCH_LIST=10.3a`. `tests/kernels/attention/test_cache.py -k nvfp4`: 27 passed including `test_cp_gather_and_upconvert_nvfp4_kv_cache_with_seq_starts`.

## Purpose

`--kv-cache-dtype nvfp4_ds_mla` crashes in the MLA chunked-context prefill:

```
mla_attention.py  _compute_prefill_context
_custom_ops.py    gather_and_maybe_dequant_cache
RuntimeError: get_fp8_kv_cache_data_type, csrc/attention/dtype_fp8.cuh:34,
              Unsupported fp8 kv cache data type: nvfp4_ds_mla
```

`MLACommonBaseImpl._compute_prefill_context` gathers each chunk's cached context KV into a BF16 workspace. It has a branch for `fp8_ds_mla`; every other dtype goes to `gather_and_maybe_dequant_cache`, which only knows the fp8 variants. The NVFP4 upconvert kernel added with the `nvfp4_ds_mla` format, `cp_gather_and_upconvert_nvfp4_kv_cache`, is never called here.

Sparse MLA reaches this path through its dense-MHA prefill: a prefill whose total length is `<= index_topk` and that has cached context. In practice:

- **speculative-decoding warm-up**: the dummy batch takes this path, so an engine with `nvfp4_ds_mla` KV and a DFlash draft never finishes starting;
- **chunked prefill splitting a short prompt**: the continuation step has context;
- **prefix-cache hits** on short prompts.

Longer prefills use the sparse FlashMLA kernels, which already handle `nvfp4_ds_mla`.

**Fix:**

- Route `nvfp4_ds_mla` to `cp_gather_and_upconvert_nvfp4_kv_cache`.
- Give that kernel an optional `seq_starts` (csrc + bindings + `_custom_ops`), mirroring `cp_gather_and_upconvert_fp8_kv_cache`: a continuation chunk reads from its context start instead of the request's first token. Without it, every chunk after the first would silently re-read the request's first tokens.
- Reject `nvfp4_ds_mla` with decode context parallelism at config validation; that combination is not validated.

Other dtypes are unaffected. I found no existing issue or PR for this.

- zyongye · comment · 2026-10-14T04:55:35Z · [source](https://github.com/vllm-project/vllm/pull/58744#issuecomment-6161209988)

The core fix looks right. I traced the chunk planner and the NVFP4 kernel and simulated both tests' chunk plans: starts are block-aligned on every reachable path, the shift lands on the right physical slots, and no column that is actually read ever gets clamped. The reference-vs-dequantized-cache test design is nice.

A few things worth addressing:

**1. The workspace hunk looks dead.** `nvfp4_ds_mla` appears in exactly one `supported_kv_cache_dtypes` list — `FlashMLASparseBackend` (`flashmla_sparse.py:142`) — whose builder derives from `SparseMLACommonMetadataBuilder`, not the `MLACommonMetadataBuilder` changed at `mla_attention.py:2446`. The workspace that actually feeds this gather is `sparse_mla_attention.py:217` (`dtype=self.model_config.dtype`). The fp8-prefill-query rationale can't apply either: sparse metadata hardcodes `q_data_type=self.model_config.dtype` (`sparse_mla_attention.py:399`). The same reasoning makes the `fp8_query` arm of the new test a config no backend can produce — and since `_build_prefill_metadata` hardcodes a bf16 workspace, that arm doesn't exercise the hunk either.

**2. Would `seq_starts` on the NVFP4 kernel be simpler than the block-table shim?** `cp_gather_and_upconvert_nvfp4_kv_cache_kernel` computes `token_offset = out_token_id - workspace_starts[req_id]`; a `+ seq_starts[req_id]` plus the arg plumbing would delete `shift_block_table_to_starts`, its alignment precondition, the clamp, the per-chunk gather, *and* the DCP `NotImplementedError` — and match the fp8 twin, which already handles arbitrary (even unaligned) starts via `map_gather_page_task` (`cache_kernels.cu:1229`).

**3. `shift_block_table_to_starts` fails silently.** The "start is a multiple of `block_size`" precondition isn't enforced, and `clamp_` aliases an out-of-range column onto the last block, so a violation yields wrong KV rather than an error. Two unaligned sources already exist in tree: `align_chunk_to_block=current_platform.is_cuda()` (`sparse_mla_attention.py:320`), and DCP, where `chunk.starts` is overwritten with local offsets `cdiv(start, virtual) * local_block_size` (`mla_attention.py:2152`) — kept out only by the new raise in a different method. An assert (or dropping the clamp) would make it loud.

**4. The DCP rejection fails late.** The raise at `mla_attention.py:3076` sits inside the per-layer forward and only fires once a request carries context, so the engine starts, serves context-free prompts, then dies on the first prefix-cache hit. A validator next to `validate_nvfp4_kv_cache_with_mla` (`config/vllm.py:3499`) would reject at startup. It's also untested as written.

Minor:

- The gather dispatch now has four near-identical copies: `mla_attention.py:2959` (fixed here), `mla_attention.py:3106`, `kimi_k3/nvidia/mla.py:940`, `sparse_mla_attention.py:919`. The other three still route `nvfp4_ds_mla` into `gather_and_maybe_dequant_cache`; they're unreachable today by accident (`_is_masked_mha_available` returns False for any quantized cache), not by contract.
- `flashmla_sparse.py:1114` passes `kv_c_and_k_pe_cache.view(torch.uint8)`; the new call passes it raw. This kernel hard-checks for uint8 (`cache_kernels.cu:1880`) while the fp8 one doesn't — either the view there is redundant or this call needs it.
- The shift builds a full `(num_reqs, max_blocks)` int64 index and table copy per continuation chunk, though `plan_mla_context_chunks` guarantees only row 0 can ever shift.
