# [Bugfix][Tool Parser] Olmo3: don't cut at </function_calls> inside a string argument

[Upstream PR](https://github.com/vllm-project/vllm/pull/61633) · state: open · merged: False

## Original PR description

## Overview

Fixes #61632. The Olmo3 tool parser drops the tool call in non-streaming mode when a string argument contains `</function_calls>`. Streaming handles the same output correctly.

## Claims

- Non-streaming `Olmo3PythonicToolParser.extract_tool_calls` no longer treats a `</function_calls>` inside a string argument as the end of the block.
- Streaming and non-streaming now return the same tool calls for this input.
- Behaviour is unchanged for normal output, for output without tags, and for output with an unclosed tag.

## Validation

Added three cases to `tests/tool_parsers/test_olmo3_tool_parser.py`: streaming, non-streaming, and non-streaming with a second parallel call.

```
pytest tests/tool_parsers/test_olmo3_tool_parser.py tests/tool_parsers/test_pythonic_tool_parser.py
41 passed
```

Without the parser change, the two new non-streaming cases fail. The streaming case already passed.

## Details

**Root cause:** the wrapper was stripped with `re.search(r"<function_calls>(.*?)</function_calls>", ...)`. The non-greedy match ends at the first closing tag, even inside a quoted argument. The remaining text is no longer valid Python, so the parser falls back to returning everything as `content`.

**Fix:** `_strip_function_calls_tags` tries each `</function_calls>` in order and keeps the first body that `ast.parse`s once joined into a list (the same newline join as before). If none parses, it falls back to the first closing tag, which is the previous behaviour.

**Not a greedy `(.*)`:** a greedy match would join two separate `<function_calls>` blocks into one unparseable body. Today the first block parses, and this change keeps that.

The newline join is moved into `_to_call_list` unchanged, so the bodies being tried go through exactly the same transformation as the final parse. #60433 and #60436 change that join (newlines inside strings). They are independent of this fix and may need a trivial rebase against it.

Same bug class as #45167 (Hermes, `</tool_call>` inside a JSON string).

Two problems. Tested at e0f2591dc7.

The new `ast.parse` in `_strip_function_calls_tags` runs before the regex check and only catches `SyntaxError`/`ValueError` ([L96-L98](https://github.com/vllm-project/vllm/blob/e0f2591dc71e0a9414951f50f3b682e565f50716/vllm/tool_parsers/olmo3_tool_parser.py#L96-L98)). A deeply nested body like `"<function_calls>f(a=" + "-" * 7000 + "1)</function_calls>"` raises `MemoryError` there and fails the request, while main returns it as content. Could you catch `Exception` there? That fixed it for me.

This also conflicts with #60436. Whichever lands second should check candidates with #60436's `_parse_newline_separated_calls`, otherwise a multi-line call with `</function_calls>` in a string falls back to content in non-streaming. I tried that swap on a merged branch and the olmo3 tests pass.

The new tests also pass when I group the stream into bigger deltas.
