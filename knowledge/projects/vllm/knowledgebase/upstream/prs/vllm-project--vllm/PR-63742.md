# [Perf][Mamba] Use the shared checkpoint exporter for Mamba2 and drop ssd_checkpoint

[Upstream PR](https://github.com/vllm-project/vllm/pull/63742) · state: closed · merged: True

## Original PR description



## Overview

Mamba2 prefill checkpoints now use the shared `MambaPrefillCheckpointExporter` (introduced for GDN/KDA in #60050) instead of their own `ssd_checkpoint.py` kernel, which is deleted. Part of the internal prefill checkpoint work tracked in #52959.

## Claims

- One checkpoint-store kernel for GDN, KDA and Mamba2 instead of two. Diff: +53 / -157 in `vllm/` (including the deleted 118-line file) and +35 / -17 in tests (the Mamba2 test retarget, plus new Mamba2 and wide-state cases in the exporter test).
- Mamba2 checkpoint store time is faster than the removed kernel in 39 of 48 cases, and no TP1/2/4 case is slower. The 3 slower cases are all TP8 (Nano 30B at 1-2 rows, Super at 2 rows), by at most +2.9 µs per step. GDN/KDA are 13-37% faster at 4+ rows on TP1/2. Across 96 cases, 25 are slower than main by at most +15 µs per step, mostly at TP4/8 with 1-2 rows (details and numbers below).
- Stops Mamba2 from writing skipped prefill checkpoints into the null block. Under the default sparse retention a non-final prefill chunk that spans two or more Mamba blocks gets a checkpoint offset but a null destination (by design since #59175, so that the export is masked); the removed kernel had no null check and wrote it into block 0, while the shared kernel skips it (reproduced with `check_mamba2_null_block_write.py`, which runs both kernels on a Super TP1 row whose column is null). Latent: no reader of block 0 was found (details under "Behavior of the swap").

**What "rows" means.** A row is a request in the step that exports a checkpoint: its final prefill chunk spans more than one Mamba block, so the checkpoint falls inside this chunk (`is_mamba_prefill_checkpoint_valid`). Decodes and other prefills add no rows. 1 row is one long prompt finishing in the step; several rows are a burst of mid-length prompts finishing together. A step holds at most about `max_num_batched_tokens / mamba_block_size` rows. Super at TP1 has a 4224-token block, so at most 3 rows at the default 16k budget. The block size is set so an attention page is at least as large as a Mamba page, so it shrinks with TP once the attention KV heads are replicated and the per-rank Mamba state keeps shrinking; higher TP therefore allows more rows per step (not measured here). The kernel only reads 3 conv tokens and one state row per request, so lengths do not affect its time, only the row count does.

## Details

**Why this swap makes sense now.** Before #60050 the two checkpoint-store kernels were not interchangeable: the shared one read each checkpoint's recurrent state from row `i` of the prefill output, while Mamba2's SSD store picked it out of all chunk states through `checkpoint_chunk_idx`. #60050 added `HAS_RECURRENT_ROWS` (`recurrent_rows`) to the shared kernel, which is exactly that selection. Since then the two kernels are basically identical: they differ in launch configuration (block size 1024 vs 256 on main), in the null-block and short-offset masks described under "Behavior of the swap" (the shared kernel already has them), and in how the conv window is addressed (the removed kernel took `x` as `(dim, tokens)`; the shared one takes `raw_qkv` as `(tokens, width)`, and the mixer now passes `x.transpose(0, 1)`). This PR sets the shared kernel's block size to 512 and makes its strides runtime arguments, so Mamba2 can use it without losing time and the duplicate can go.

**Why the kernel changed.** Three changes to `store_cache_checkpoints_kernel`, each measured separately (the callers benchmark's `cx`, `guard` and `wide` arms each take one change out of the shipped kernel; `scratch_mamba_checkpoint_ablation.py` is a replica kernel that toggles one change at a time, with SASS diffs in `out_ablation_sass.log`):

- **Block size 256 -> 512 (one value for all callers).** The removed Mamba2 kernel used 1024-wide blocks, and at 256 the shared kernel was 1.19-1.27x slower than it at 4-6 rows on large states (Super and Nano 4B at TP1), so Mamba2 would have regressed. 512 has a better worst case than 1024: 1024 is slower than the old kernel in 11 of the 24 TP4/TP8 cases, by up to about +12 µs per step, and it is ahead of 512 in only 7 of 48 cases (by 1-6%, mostly TP1/2 at 4+ rows). GDN/KDA share the kernel and get 512 as well. Keeping them at 256 was measured and is worse: with the conv guard below, 44 of 96 GDN/KDA cases were slower than main (up to ratio 1.19, +20 µs per step, both at Qwen3-Next-80B TP8 1 row), against 25 at 512 (up to ratio 1.14). A larger block means fewer programs, so the guard's fixed cost matters less. (The 256 and 1024 figures come from the block-size sweeps `out_sweep_benchmark.log` and `out_sweep_callers.log`, which time 256, 512 and 1024 side by side. `out_sweep_callers.log` is also the source of the GDN/KDA table; `out_sweep_benchmark.log` is a separate run from the Mamba2 table, so its 512 counts differ by a case or two.)
- **Strides as runtime arguments, not `tl.constexpr`.** Specializing the 8 strides costs about 6% on average (`cx/cur` column of the callers benchmark: 0.97-1.20, mean 1.06 over the 144 Mamba2/GDN/KDA shapes), most at 1-2 rows (mean 1.08 and 1.07) and least on large states (TP1 at 4-6 rows: mean 1.015). The SASS has 192 vs 184 static instructions (216 vs 192 at TP8 shapes), with more IADD3/IMAD where runtime strides use LEA, and an identical sequence of global memory ops. On the conv-only Qwen4Exp PLE shape the two are within 2% (`cx/cur` 0.98-1.01).
- **Skip the conv window in programs that don't cover it.** The conv section used to run, fully masked off, in every program. Guarding it on `program_id(1) * BLOCK_SIZE < WIDTH * STATE_LEN` cuts the time by 15-22% on large states in the ablation (for example 14.2 -> 11.1 µs at Super TP1, 6 rows) and is about neutral on small ones (-5% to +3% at Super TP4/TP8 and Nano 30B TP8). In the callers benchmark, removing it (`wide` arm) makes TP1 shapes at 4-6 rows 13-29% slower (mean 22%).

**Tradeoff of the conv guard.** The guard is what makes the Mamba2 swap faster than the removed kernel. Removing it (`wide` arm: the shipped kernel without the guard) measured, by rows (mean over the 12 shapes per model kind; positive means removing it is slower):

| rows | GDN | KDA | Mamba2 |
|---|---|---|---|
| 1 | 0% | +1% | -1% |
| 2 | +6% | +2% | +4% |
| 4 | +10% | +8% | +10% |
| 6 | +14% | +12% | +15% |

So the guard is about neutral on average at 1 row and wins from 2 rows up, by up to about 255 µs per step on TP1/2 (Kimi K3 TP1, 6 rows; Super TP1 at 6 rows about 125 µs). It loses on a few launch-bound shapes: 15 of the 72 1-2 row cases are 3% or more faster without it (13 of them TP4/8), by at most +0.5 µs per layer (+19 µs per step, Super TP8 2 rows). Without it Mamba2 would be slower than the removed kernel at TP1 with 2+ rows (Super TP1 about 1.03x at 2 rows and 1.15x at 6, from the ablation). On GDN/KDA's 1-2 row TP4/8 cases (2.6% slower than main on average) the guard accounts for about 1 point: removing it makes them 1.2% faster, while going back to 256 or to constexpr strides alone makes them 6% and 9% slower. The benchmarks' main kernel predates #63761's int64 cast; the `guard` arm (the shipped kernel with an int32 index) shows the cast is free (-2.4% to +2.0% per case), so the comparisons with main still hold.

**Behavior of the swap.** The shared kernel also skips null destination blocks, which the removed kernel did not check, and for an offset shorter than the conv window it skips the conv window but still stores the recurrent state. The manager would cache such a block as a valid checkpoint, so `export()` now asserts that every nonzero offset covers the conv window, and that `recurrent_rows` has one entry per checkpoint row. Both are host-side checks with no device sync. Neither can fire today: a valid checkpoint's offset is at least `hash_block_size` (`query_start + hash_block_size <= checkpoint_position`), above the 3-token Mamba2 conv window, and every caller sizes recurrent_rows per checkpoint row. The null-block skip is reachable. Under the default sparse retention (`prefix_cache_retention_interval=0`) the manager reserves a checkpoint block only for the chunk that ends the prefill, and leaves the column null for earlier chunks so that the export is masked (#59175, `test_checkpoint_reservation_matches_worker`). An earlier chunk that spans two or more Mamba blocks still gets an offset, and the removed kernel wrote that checkpoint into the null block (block 0); the shared kernel skips it. `check_mamba2_null_block_write.py` reproduces this with Super TP1's geometry (a 12672-token first chunk, checkpoint offset 8448 in column 1): the removed store writes the row's checkpoint into block 0 and the shared exporter leaves it untouched, while a row with a real block is written identically by both. No reader of that write was found: Mamba's decode conv and SSU kernels skip `NULL_BLOCK_ID` rows, and cache groups overlay the same memory, so it also lands in attention's block 0, which only the FA4 restricted-sliding-window gap path assumes is zero (not used by full-attention hybrids such as Nemotron). That needs a prompt longer than the token budget and a budget of at least two Mamba blocks (Super TP1: prompts over 16k tokens at the default budget). The `mamba2` case in `test_checkpoint_exporter.py` covers the skip. Mamba2 passes the pre-conv activations through `x.transpose(0, 1)`, the same view the removed kernel read.

**Considered: keeping main's launch shape for GDN/KDA.** A per-caller option that keeps GDN/KDA on 256-wide blocks without the guard, with only the runtime strides, is the callers benchmark's `wide256` arm. It is slower than main in 69 of 96 GDN/KDA cases (up to 1.04x, +58 µs per step at Kimi K3 TP1 with 6 rows) and gives up the 13-37% gains at 4+ rows on TP1/2. On the 1-2 row TP4/8 cases it would be 0.9% slower than main on average instead of 2.6%. So all callers share 512 and the guard.

**Limitations.** Measured on B200 only; microbenchmarks, not serving. The shared kernel is also used by the ROCm Kimi-K3 KDA exporter (conv half only, `vllm/models/kimi_k3/amd/ops/kda_checkpoint.py`), so the 512 block size and conv guard apply there too; `tests/models/kimi_k3/test_amd_kda_checkpoint.py` covers it but needs gfx950 and was not run. The Qwen4Exp PLE short conv (#61601: conv-only with a token map, one layer) shares the kernel too. It is 2-6% slower than main at 1, 2 and 6 rows and within noise at 4, at most +0.19 µs per step, which comes from the 512 block size (at 256 the shipped kernel is up to 6% faster on that shape); its conv window spans every program, so the guard skips nothing there.

**Related PRs.** No open PR does this swap (searched 2026-10-26: issue #52959 and open PRs that cite it, `ssd_checkpoint`, `store_cache_checkpoints_kernel`, `MambaPrefillCheckpointExporter`, "Mamba2 prefill checkpoint"). #61601 (Qwen4Exp PLE checkpoints) and #61497 (Mamba2 SSD host overhead) are merged, and this PR is rebased on them. #59175 is where the manager leaves a non-final chunk's checkpoint column null for the exporter to skip (see "Behavior of the swap"). Open PRs near this code: #60659 (GDN Triton/FLA and AITER checkpoints) and #61951 (ROCm GLM-5.3-Flash KDA on Triton) add new `export()` callers without changing the exporter, so they pick up these kernel changes; #61501 (opt-in FlashInfer SSD prefill scan, draft) edits `conv_ssm_forward` next to the Mamba2 export but keeps checkpointed prefills on the Triton scan; #61466 (per-layer checkpoint alignment) edits `mamba_mixer2.py`'s imports and spec override; #60888 (checkpoints at or before the initial-state column, draft) changes the scheduler and manager rules, not the exporter, and like #59175 expects checkpoints into null columns to be skipped; #62232 (Mamba2 prefill checkpoints on CPU) adds a CPU path to `store_prefill_checkpoint`, which this PR deletes, and a test to `test_mamba2_checkpoint_state.py`; whichever lands second moves that path into `MambaPrefillCheckpointExporter.export()`, which, like the removed kernel, always launches Triton (Mamba2 checkpoints on CPU are broken on main too, #62153).

- tomeras91 · comment · 2026-11-02T14:27:08Z · [source](https://github.com/vllm-project/vllm/pull/63742#discussion_r4443545461)

File: `vllm/model_executor/layers/mamba/checkpoint.py` · line 288

The description says the shared kernel skips offsets shorter than the conv window, but this term only skips the conv half. The recurrent store below checks only `valid_checkpoint`, so for `0 < checkpoint_offset < STATE_LEN` the block gets the new recurrent state next to a conv window that was never written. This is the same on main for GDN/KDA, and the removed Mamba2 kernel was not better (it read the previous request's tokens), so it's not a regression.

I agree it's not reachable today (offset >= `hash_block_size`). But if it ever becomes reachable (e.g. after the checkpoint placement changes in #60888), a kernel mask is not the right protection anyway: AFAIU the manager still caches that block as a valid checkpoint, so a later prefix hit resumes from bad state with no error, whether we skip half of the store or all of it.

I suggest enforcing the invariant on the host instead, e.g. an assert in `MambaPrefillCheckpointBuilder.build()` that every non-zero offset is at least the conv state length (the offsets are a host list there, so it costs nothing). I'd keep this term in the mask as well, since it also keeps `token_idx` from going negative for the first row.

- tomeras91 · comment · 2026-11-02T14:31:53Z · [source](https://github.com/vllm-project/vllm/pull/63742#discussion_r4443596652)

File: `vllm/model_executor/layers/mamba/mamba_mixer2.py` · line 907

nit: the removed kernel sized its grid from `chunk_idx.numel()`, while the exporter sizes it from `checkpoint_offsets.numel()` and reads `recurrent_rows[seq_idx]` in each program. Both have one entry per prefill row today, but nothing ties them together, and a mismatch would be a silent OOB read. A cheap `assert recurrent_rows.numel() == checkpoint.checkpoint_offsets.numel()` in `export()` (shapes only, no sync) would pin it.

- roikoren755 · comment · 2026-11-03T11:30:42Z · [source](https://github.com/vllm-project/vllm/pull/63742#discussion_r4454078881)

File: `vllm/model_executor/layers/mamba/checkpoint.py` · line 288

Good catch, you're right: `valid_conv` has the `>= STATE_LEN` term but `valid_recurrent` doesn't, so a short offset would store the recurrent state next to a conv window that was never written, and the manager would still cache the block. Agreed that a kernel mask isn't the protection.

I put the check in `export()` rather than `build()`: the conv window differs per caller (3 for Mamba2/GDN, 9 for the Qwen4Exp PLE conv) and only the exporter knows it, while `checkpoint.offsets` is already a host list there, so it's an `all()` over a few ints. I kept the term in the mask for the negative `token_idx` case.

I profiled it in a real Nemotron Nano step that exports a checkpoint in all 23 Mamba layers: about +1.4 µs of host time per `export()` call, and no change in GPU idle time before the store kernel (details in the description). I also fixed the description, which overstated what the kernel skips.
