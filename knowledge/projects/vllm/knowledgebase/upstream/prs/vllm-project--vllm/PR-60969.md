# [Bugfix][Reasoning] Return unfinished K2 Horizon reasoning as reasoning

[Upstream PR](https://github.com/vllm-project/vllm/pull/60969) · state: open · merged: False

## Original PR description



## Overview

When K2 Horizon output has no end-of-thinking token and no tool calls (for example cut off by `max_tokens`), non-streaming returns the thinking text as `content`, while streaming returns it as `reasoning`. This PR makes non-streaming return it as `reasoning`, like streaming and like `DeepSeekR1ReasoningParser`.

## Claims

- A K2 Horizon response cut off during thinking now has the text in `reasoning` and `content: null`, in both streaming and non-streaming mode.
- Outputs with `</ifm|think>` (or the `medium`/`low` end tokens) or with `<ifm|tool_calls>` parse exactly as before.

| Mode | `main` (`reasoning` / `content`) | This PR (`reasoning` / `content`) |
|---|---|---|
| non-streaming | `""` / `"Let me plan the trip. First, check the weather in Hanoi"` | `"Let me plan the trip. First, check the weather in Hanoi"` / `null` |
| streaming | `"Let me plan the trip. First, check the weather in Hanoi"` / `null` | `"Let me plan the trip. First, check the weather in Hanoi"` / `null` |

On `main` the same truncated output lands in `content` or in `reasoning` depending only on whether the client streams. With this PR both modes agree.

Not run end to end on a GPU yet. The check above uses the model's real tokenizer and special tokens, and the parser has no other inputs on this path.

<summary>Reproduction script</summary>

    from huggingface_hub import hf_hub_download
    from transformers import PreTrainedTokenizerFast
    from vllm.entrypoints.openai.chat_completion.protocol import ChatCompletionRequest
    from vllm.reasoning import ReasoningParserManager
    from tests.reasoning.utils import run_reasoning_extraction

    tok = PreTrainedTokenizerFast(tokenizer_file=hf_hub_download("IFM/K2-Horizon-7B", "tokenizer.json"))
    req = ChatCompletionRequest(model="IFM/K2-Horizon-7B", messages=[{"role": "user", "content": "Plan a trip to Hanoi"}], max_tokens=12)
    out = "<ifm|think>Let me plan the trip. First, check the weather in Hanoi"
    pieces = [tok.decode([i]) for i in tok.encode(out, add_special_tokens=False)]
    for streaming in (False, True):
        parser = ReasoningParserManager.get_reasoning_parser("k2_horizon")(tok)
        print(streaming, run_reasoning_extraction(parser, pieces, req, streaming=streaming))

## Details

Root cause: the last line of `_split_model_output` was `return "", output or None`. The streaming path in the same class buffers that text as reasoning, `extract_content_ids` returns no content ids, and there is no streaming fallback that moves it to content. K2 Horizon has no "thinking off" effort (`reasoning_effort` must be `high`, `medium` or `low`), so text before any boundary is always thinking. The line is now `return output, None`.

Not a duplicate: I searched PRs for "k2 horizon" and open PRs for unfinished or non-streaming reasoning. #59627 changes how the implicit reasoning end reaches structured output and does not touch this function. #57768 adds regex timeouts to the K2 Horizon tool parser. The other open PRs about truncated reasoning are for Kimi K3. No issue reports this bug.

Thanks for the check. On the first point: in the serving path the tool parser never receives None. `_extract_tool_calls` passes `content if content is not None else ""` for auto tool choice and `content or ""` for tool_choice="none" (vllm/parser/abstract_parser.py lines 394 and 447). Returning `(output, None)` when the end token is missing is also what `BaseThinkingReasoningParser.extract_reasoning` already does (vllm/reasoning/basic_parsers.py lines 170-171), so this matches the base contract.

On the second point: you are right that streaming holds back a partial `</ifm|think>` tail and never flushes it. That behavior exists on main and this PR does not change the streaming path, so I kept it out of scope. The test covers output with no end tag at all; I can narrow the docstring to say that if reviewers prefer.

Request (`"stream": true` for the streaming rows):

    curl localhost:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{
      "model": "IFM/K2-Horizon-7B",
      "messages": [{"role": "user", "content": "Plan a 3-day trip to Hanoi for a family with two kids."}],
      "max_tokens": 32, "temperature": 0, "seed": 0, "stream": false}'

The chat template ends the prompt with `<ifm|think>\n`, so the output starts inside thinking. With `max_tokens: 32` it stops before `</ifm|think>` (`finish_reason: "length"` in all four runs). This is the usual case of a response cut off by the token limit.

Output text in all four runs: `The user just typed a blank line? The conversation: system says "You are K2...". The user message is empty (just a newline). The user likely`

| | `reasoning` | `content` |
|---|---|---|
| `main`, stream=false | `""` | the text above |
| `main`, stream=true | the text above | `null` |
| this PR, stream=false | the text above | `null` |
| this PR, stream=true | the text above | `null` |

On `main` the same cut-off thinking comes back as `content` without streaming and as `reasoning` with streaming. With this PR both modes return it as `reasoning`, which matches `DeepSeekR1ReasoningParser` when the end token is missing.
