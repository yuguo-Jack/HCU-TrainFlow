# [Quantization] Support ModelOpt INT8_PB_WO (per-block INT8 weight-only) linear layers

[Upstream PR](https://github.com/vllm-project/vllm/pull/65272) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds `INT8_PB_WO` to vLLM's ModelOpt support: per-block (group-wise) INT8 weight-only linear layers with 16-bit activations, named after `FP8_PB_WO`. Each layer stores an int8 `[out, in]` weight and `weight_scale` `[out, in // group_size]`.
- A whole-model `quant_algo: INT8_PB_WO` checkpoint is served by a new `modelopt_int8` quantization method (`ModelOptInt8Config`), the way NVFP4 is served by `modelopt_fp4`.
- `INT8_PB_WO` also works as a per-layer algo inside `MIXED_PRECISION` (`modelopt_mixed`).

ModelOpt deploys its 2-bit GGML IQ formats exactly by expanding each weight into INT8 levels with a group scale over 16 or 32 weights. With this PR, a converted checkpoint can keep every non-GGML layer's ModelOpt entry and tensors as they are (FP8 attention, NVFP4, ...) and add the INT8 layers in ModelOpt terms. Today the only option is to rewrite everything as compressed-tensors, which cannot express ModelOpt's NVFP4 tensors unchanged.

## Claims

- New `modelopt_int8` method and `ModelOptInt8Config`, a sibling of `ModelOptMxFp8Config` under `ModelOptQuantConfigBase`. A checkpoint whose `quant_algo` is `INT8_PB_WO` is routed to it automatically, whether its `config.json` says `quant_method: modelopt` or it only has a legacy `hf_quant_config.json`. Users never need `--quantization`. The FP8 config (`modelopt`) is untouched.
- `group_size` is required. In `MIXED_PRECISION`, each `INT8_PB_WO` layer takes its own `group_size`, so 16 and 32 can coexist, next to FP8 or other ModelOpt layers and unquantized layers.
- A whole-model checkpoint, or an `INT8_PB_WO` layer in `MIXED_PRECISION`, without `group_size` fails at config parsing or model construction. It does not load with scales of a guessed shape.
- No new kernels. Layers are served by the existing mixed-precision (WNA16) kernels through `choose_mp_linear_kernel`. On an RTX PRO 6000 Blackwell (sm_120): group 32 uses Marlin and group 16 uses Humming, with both bf16 and fp16 activations.
- Bug fix: `ExllamaLinearKernel.can_implement` now rejects `group_size` values that are not a multiple of 32. Before, fp16 group-16 layers (here, and the same for GPTQ/compressed-tensors WNA16) were routed to Exllama and silently computed with the wrong group scales.
- An `INT8_PB_WO` entry on routed experts raises `NotImplementedError` instead of loading as another MoE format. MoE support is a follow-up.

## Details

**Checkpoint format** (what the ModelOpt converter emits):
- `<layer>.weight`: int8 `[out, in]`, symmetric, with no zero point and no input scale.
- `<layer>.weight_scale`: `[out, in // group_size]`, and `w[o, i] = weight[o, i] * weight_scale[o, i // group_size]`. The dtype can be bf16, fp16 or fp32. It is cast to the activation dtype at load, because the WNA16 kernels need scales in the activation dtype.
- Config, in `config.json` `quantization_config` (or legacy `hf_quant_config.json`):
  - whole-model: `{"quant_method": "modelopt", "quant_algo": "INT8_PB_WO", "group_size": 32}`, served by `modelopt_int8`;
  - per layer: `{"quant_algo": "MIXED_PRECISION", "quantized_layers": {"model.layers.0.mlp.gate_proj": {"quant_algo": "INT8_PB_WO", "group_size": 16}, "model.layers.0.mlp.down_proj": {"quant_algo": "INT8_PB_WO", "group_size": 32}, "model.layers.0.self_attn.q_proj": {"quant_algo": "FP8"}, ...}}`.
- Fused vLLM modules (`qkv_proj`, `gate_up_proj`) load from their per-shard tensors. Their shards must agree on algo and `group_size`; otherwise loading raises "Mixed ... within fused layer".
- ModelOpt's per-channel INT8 weight-only export (`W8A16`) is out of scope and stays unsupported, as on `main`.

**Design** (follows the existing "one `LINEAR_ALGOS` row + one `resolve()` row" extension seam):
- `ModelOptInt8Config` (`modelopt_int8`) mirrors `ModelOptMxFp8Config`. It owns `LINEAR_ALGOS["INT8_PB_WO"]` and requires `group_size`. It passes `kv_cache_quant_algo` through to `ModelOptKVCacheMethod` and has no FusedMoE method (experts raise). Its minimum capability is SM75 with bf16/fp16 activations: Marlin and Humming both serve int8 weight groups from Turing.
- Registration follows the siblings: the `QuantizationMethods` literal and method-to-config map, the override order in `ModelConfig._verify_quantization`, and the per-method weight size in `vllm/v1/metrics/perf.py`. The legacy `hf_quant_config.json` normalization in `model_arch_config_convertor.py` also maps `INT8_PB_WO` to `modelopt_int8`; it previously raised "Unknown ModelOpt quant algo".
- `resolve()` maps `INT8_PB_WO` to `QuantSpec(weight=kInt8Static, activation=None)` with `CkptCtx(group_size=G)`, after checking that `G` is set.
- `KInt8Static` (new `QuantKeyScheme`) registers the weight as a packed int32 `[out, in // 4]` `PackedvLLMParameter`. Its weight loader converts the checkpoint int8 to uint8b128 (`q ^ 0x80`, i.e. `q + 128`) and views four bytes as one int32 along the input dim. This is the layout compressed-tensors WNA16 hands to the same kernels, so the regular TP/fused loaders work unchanged. The scale is a `GroupQuantScaleParameter`. It starts as NaN, so a layer whose checkpoint lacks INT8 tensors fails at load instead of producing garbage.
- `select_linear_kernel` gets an int8 branch: it builds an `MPLinearLayerConfig` and calls `choose_mp_linear_kernel`, so `--linear-backend` and `VLLM_DISABLED_KERNELS` apply as usual. `MPLinearKernel` gains the `input_quant_key() -> None` default that `MMLinearKernel` already has; `ModelOptLinearMethod` calls it for every kernel.
- Per-layer `group_size` in `MIXED_PRECISION`: `resolve()` asks the sub-config for `layer_group_size(prefix)`. The mixed config serves as its own `INT8_PB_WO` sub-config and answers from the layer's `quantized_layers` entry. That lookup reuses the existing prefix/fused-shard resolution, generalized mechanically from `_resolve_quant_algo` to `_resolve_layer_field(prefix, field)`; `_resolve_quant_algo` keeps its behavior.

**Exllama root cause**: in `csrc/quantization/gptq/q_gemm.cu`, the GEMM and reconstruct kernels advance K by 32 per iteration and only check `k == nextgroup` at those steps. With `group_size=16`, half of each 32-wide chunk uses the previous group's scale. `can_implement` only required `group_size > 0` and dividing K.

**Limitations**:
- `modelopt_int8` is not added to ROCm's or XPU's supported-quantization lists. On ROCm only the optional Conch kernel handles uint8b128 weights (Exllama needs fp16 activations and groups that are a multiple of 32), and neither path is validated here.
- Linear layers only. MoE raises. An embedding listed as `INT8_PB_WO` is not handled (same as other ModelOpt linear algos today).
- In bf16 models the scales are rounded to bf16, because the kernels take scales in the activation dtype. Reproduction of fp16 GGML scales is bit-exact with fp16 activations.
- On Blackwell, group 16 runs on Humming. Group 32 runs on Marlin, which is slow at large batch; users can set `VLLM_DISABLED_KERNELS=MarlinLinearKernel` to move it to Humming as well.

**Duplicate check**: I searched open PRs (`modelopt W8A16`, `ModelOpt INT8`, `modelopt int8 weight-only`, `modelopt GGML`). Related but different: #65165 (online `int8_per_channel_weight_only` for `LinearBase`, W8A8), #65006 (Nemotron-H serving FP8 linears with bf16 activations), and #65003 (Triton kernels for the ModelOpt IQ2/Q8_0 block codecs). None adds ModelOpt INT8 weight-only checkpoint loading.

<summary>Why this was flagged</summary>

In csrc/quantization/gptq/q_gemm.cu, each kernel (for example the 8-bit one near line 530) and reconstruct_exllama_8bit_kernel (around line 683) sets `group = offset_k / groupsize` and `nextgroup = offset_k + groupsize`, where `offset_k = blockIdx.z * BLOCK_KN_SIZE` and BLOCK_KN_SIZE is 128.
