# [Spec Decode] DSpark: sliding-window MLA draft layers

[Upstream PR](https://github.com/vllm-project/vllm/pull/63795) · state: open · merged: False

## Original PR description

## Overview

Extends DSpark speculative decoding with sliding-window MLA draft layers. Draft layers with an attention window now decode through the Triton MLA backend's windowed path, get a dedicated KV cache group, and can be driven by recurrent Markov heads whose state carries across the positions of one proposal.

Not a duplicate: I searched open PRs for DSpark / DCP / sliding-window work. Adjacent but distinct: #62410 (GLM-5.3 MLA DSpark drafts, model-specific enablement), #61464 (DBO with spec + DCP), #56694 / #62958 (Markov walk perf kernels). None cover windowed MLA draft layers, their KV cache layout, or the recurrent-head speculator hook.

## Claims

- Triton MLA backend: sliding-window decode in both kernel stages.
- Non-causal multi-token decode flag on the MLA KV cache spec and a separate KV cache group for windowed MLA draft layers.
- Speculator hook for recurrent Markov heads that carry a state across the positions of one proposal.

## Validation

- `python -m pytest tests/kernels/attention/test_triton_decode_attention.py tests/v1/core/test_kv_cache_planning.py -v` — both extended by this change and wired into CI on CUDA.
- The windowed decode path was exercised end-to-end during bring-up of the spec-decode stack this change originates from.

## Details

- The windowed decode is implemented inside the Triton MLA kernel stages so a windowed draft layer costs no extra launches relative to the full-attention draft path.
- The non-causal multi-token flag distinguishes speculative draft rows from target rows inside the same group, which is what lets windowed drafts share the MLA cache infrastructure instead of growing a parallel layout.
- The recurrent Markov-head hook keeps proposal state out of the per-position interfaces: the speculator owns the state and re-enters the head per position.
