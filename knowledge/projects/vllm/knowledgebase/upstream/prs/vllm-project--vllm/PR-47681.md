# [Bugfix][OpenAI][Anthropic] Merge inline system messages before rendering

[Upstream PR](https://github.com/vllm-project/vllm/pull/47681) · state: open · merged: False

## Original PR description

## What & why

DeepSeek-V4-Flash can render an inline system message as bare content appended to the preceding user span. Its custom encoder uses `system_msg_template = "{content}"`, so a request such as `[user: Q, system: LATESYS, user: Q2]` becomes `<|User|>QLATESYS<|User|>Q2` rather than a structurally distinct system instruction.

A template rendering without an error is therefore not sufficient evidence that preserving an inline system message is safe. This PR uses a safe default: merge text system messages into one leading system message before rendering. The policy applies consistently to both OpenAI Chat Completions and Anthropic Messages, including Anthropic token counting.

## Changes

- Add `--inline-system-messages {merge,preserve}`; `merge` is the default.
- Normalize system messages in `OpenAIServingChat` immediately before rendering, covering both OpenAI and Anthropic requests.
- Remove Anthropic-only template-error detection and endpoint-local message merging.
- Preserve remains available as explicit opt-in for deployments whose model/template behavior is independently validated and where prefix-cache stability is more important.
- Add regressions that show the DeepSeek-V4 renderer welded prompt under `preserve` and the corrected leading-system prompt under `merge`.
- Add an Anthropic conversion regression proving it uses the shared policy.

## Behavior

| Mode | Behavior |
| --- | --- |
| `merge` (default) | Merge text system messages into one leading system message before rendering. |
| `preserve` | Keep system messages at their original positions. Intended only for verified model/template combinations. |

- Blackwellboy · comment · 2026-09-21T12:47:47Z · [source](https://github.com/vllm-project/vllm/pull/47681#issuecomment-5760725564)

Rechecked this against current `main` and the newer related work. Head `3b4eb88daab61ce35526160e462c104e9882ddad` is currently mergeable; the latest `pre-commit` workflow is only failing the authorization pre-run gate, with the actual pre-commit job skipped. CodeRabbit and Read the Docs are green.

Two concrete things still look worth resolving before merge:

1. The structured-content case from @StevenConnors is still real on this head. `_normalize_inline_system_messages()` only selects system messages whose `content` is a `str`, so a list/block-form inline system message is left in place and can still reach a system-first template. The existing Anthropic `_extract_system_text()` path shows how to flatten text blocks without dropping them.

2. There is now an explicit policy conflict with #53501 and #56520. #56520 improves prefix-cache reuse by preserving DeepSeek inline system turns, but the regression in this PR demonstrates why renderability alone is not enough: DeepSeek can render `[user, system, user]` as user content with no distinct system-role marker. #53501 instead re-roles the inline system turn to `user`, which keeps the prompt append-only but intentionally changes role semantics.

Given that, I would avoid treating `supports_inline_system_messages` as equivalent to preserving system semantics. The current `merge` default + explicit `preserve` opt-in is the safer general contract unless maintainers prefer a third explicit policy (for example re-role-to-user / drop) to make the cache-vs-semantics tradeoff operator-controlled.

I don't think a new competing PR is useful here; #47681 is already the right place to settle the shared policy. Once the structured-content case and policy direction are agreed, the remaining mechanical work is small.
