# [ROCm][Perf] Muse Spark: finalize the token-sharded MoE reduction in one reduce-scatter

[Upstream PR](https://github.com/vllm-project/vllm/pull/63254) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

On ROCm under TP, `MuseSparkTopKWeightAndReduce` finalizes the MoE output of a batch of at least 256 tokens in three steps: reduce-scatter, per-rank `fused_post_expert_finalize`, then all-gather. It does this in 1024-token chunks. With `VLLM_ROCM_MUSE_MOE_REDUCE_DTYPE=bf16` (set by every AMD command of the recipe) the chunks bound no memory, so this PR finalizes the whole batch with one reduce-scatter and one all-gather per MoE layer. The all-gather runs in place when no padding is needed.

**Relation to #64461.** #64461 replaces this reduce-scatter for the MXFP4 (AITER) experts at TP prefill (eager batches of >= 1024 tokens): stage 2 runs column-sharded on the gathered MXFP4 intermediate, so those layers no longer reach this path. The two PRs touch different branches of the finalize and merge cleanly in either order. Which one a MoE layer takes under TP (no EP), for batches above 1024 tokens:

| Checkpoint | MoE layers | Experts | Column-sharded stage 2 on (default) | Column-sharded stage 2 off |
|---|---|---|---|---|
| BF16 | all | Triton | this PR | this PR |
| MXFP4 | first and last (BF16) | Triton | this PR | this PR |
| MXFP4 | the others | AITER | #64461 | this PR |

The column-sharded stage 2 is off with `VLLM_ROCM_MUSE_MOE_COLUMN_SHARDED_DOWN=0` (about 9% more KV cache at TP8), or with an AITER without the two-stage API. It does not pay off for the Triton experts: their BF16 intermediate is as wide in bytes as the reduce-scatter it would replace, and a second BF16 `w2` would not fit. This PR changes nothing under TP + EP, or for batches of 1024 tokens or fewer.

## Claims

- Scope: the MoE layers marked "this PR" in the table above. TP + expert parallel is unchanged. The measurements below are on the MXFP4 checkpoint on `main` (without #64461), where every MoE layer takes this path.
- TP8 + DSpark on `main` (`0f6b261910`), recipe plain-TP settings: single-request TTFT drops 7–8% for 2k / 8k / 16k-token prompts and for a burst of four 8k prompts. On an earlier base it was 9–13%.
- Concurrency sweep, random 8k in / 1k out: output throughput +2.0 to +4.0% at c16 and +6.0 to +6.9% at c32. Mean TTFT drops 7–10% and mean TPOT drops 2–5%.
- Finalize alone, 8 GPUs: 14–29% faster above 1024 tokens. Up to 1024 tokens the output is bitwise identical to the base, and so is the output for the fp32 reduce dtype and the unfused-norm path at every size. Above 1024 tokens with the bf16 reduce dtype, RCCL sums the partials in a different order; the error against an fp32 reference is the same.
- The peak extra memory of the finalize goes down or stays within the profile run's footprint (64 MiB per GPU at 8192 tokens). The KV cache size is unchanged.
- Accuracy: GSM8K shows no significant difference (paired p = 0.74 and 0.86). TP8 + EP8 outputs are bitwise identical to the base, because this path is not taken under EP.
- No new flag or environment variable. The change takes effect with `VLLM_ROCM_MUSE_MOE_REDUCE_DTYPE=bf16`; under the default `fp32` the chunks are kept and the output is bitwise identical.

## Details

**Why the chunks exist and why they can go.** `_FINALIZE_CHUNK_ELEMS` bounds the reduce-dtype copy of the per-route output `[T, top_k, H]`: 1 GiB at 8192 tokens with the fp32 default. With the bf16 reduce dtype, `.to()` copies nothing. The chunks then only split one reduce-scatter / all-gather pair into eight (at 8192 tokens), in each of the 62 MoE layers. When the per-route output is already in the reduce dtype, the whole batch is now one chunk. With a real copy (fp32), the chunks are kept.

**Non-TP-divisible batches.** A chunk larger than one default chunk reduce-scatters its TP-divisible prefix. The remaining (< TP) tokens take the existing all-reduce + fused finalize, the path already used below 256 tokens. Padding such a chunk would copy all of it (512 MiB at 8191 tokens). Chunks of up to one default chunk are padded as before (at most 64 MiB, cheaper than an extra all-reduce launch), so the output for batches of up to 1024 tokens is unchanged.

**In-place all-gather.** When a chunk needs no padding, each rank finalizes straight into its rows of the output. Then `torch.distributed.all_gather_into_tensor(out, out_local, group=get_tp_group().device_group)` runs in place (`out_local` is the rank's slice of `out`, the in-place layout NCCL/RCCL support). This replaces gathering into a new `[T, H]` buffer and copying it. vLLM's `tensor_model_parallel_all_gather` has no output argument; on ROCm it calls the same `all_gather_into_tensor` on the same device group (`CudaCommunicator.all_gather` defers to the base class there). The call sits inside the MoE custom op, like the existing reduce-scatter / all-gather calls of this class. `sparse_attn_indexer` and `flashmla_sparse` call `all_gather_into_tensor` directly in the same way, into preallocated buffers on `get_dcp_group().device_group`.

**Scope.** This changes only `vllm/models/muse_spark/amd/muse_moe_runner.py`: +42 / −20 lines, no new helper, flag or env var. The fp32 reduce dtype, the unfused-norm path, batches below 256 tokens and EP (MoE `tp_size == 1`) behave as before.

**Tests.** `test_token_sharded_finalize_chunks_only_a_reduce_dtype_copy` emulates TP2 rank 0 with a 4-token default chunk. It checks three cases:
- a bf16 batch of 11 tokens takes one reduce-scatter of 10 tokens (gathered in place) plus an all-reduce of 1, with the values of the owned, peer and tail rows checked;
- a bf16 batch within one chunk is padded as before;
- fp32 keeps its chunks.

The test lives in `tests/kernels/moe/`, which the AMD MoE kernel CI step runs as a whole directory.

**Limitation.** Above 1024 tokens with the bf16 reduce dtype, TP outputs are not bitwise identical to the base (RCCL reduction order, same error). A follow-up could use AITER's custom reduce-scatter / all-gather for 256–1031 tokens (7–32% faster finalize in our measurements); it is not part of this PR.
