# [ROCm][MoE] Enable MoRI FP4 dispatch for DeepSeek V4.1 a4w4

[Upstream PR](https://github.com/vllm-project/vllm/pull/59852) · state: closed · merged: False

## Original PR description

## Overview

Enable MoRI FP4 dispatch for DeepSeek V4.1 a4w4 (`VLLM_ROCM_USE_AITER_MOE_A4W4_DSV4=1`) and trim MoRI's dispatch output to the valid token count. **Stacked on #59596**, which adds MoRI FP4 dispatch for MXFP4 W4A4 checkpoints. Only the last two commits are new here; this PR will be rebased once #59596 lands.

## Claims

* DeepSeek V4.1 a4w4 under `--all2all-backend mori_*` now dispatches packed FP4 with e8m0 block scales instead of BF16. Before this change, #59596's W4A4-only gate kept it on BF16 dispatch, because this mode runs on a W4A16 quant config with MXFP4 activations in AITER.
* The two copies of the "MoRI dispatches FP4" check (prepare/finalize selection and `AiterExperts.workspace_shapes`) are now a single `FusedMoEConfig.use_mori_fp4_dispatch()`.
* MoRI's dispatch outputs are sliced to `num_dispatchers * max(num_tokens_across_dp)` rows instead of the full `world_size * max_num_tokens` receive buffer, so AITER picks its MoE kernel config for the real M rather than the worst case.
* No accuracy change on DeepSeek-V4.1-Flash DEP2: GSM8K is 0.974 with MoRI FP4 dispatch and trimming, against 0.977 on the default path.
* On MI355X DEP2 agentic-coding traces, output throughput per GPU is 1.8–11.0% higher than allgather/reducescatter at c32–c192. One MoE layer's dispatch+combine takes 1.33–1.49× less time than MoRI BF16 at 384–8,192 tokens/rank.

## Validation

### Unit test

`tests/kernels/moe/test_mori_moe.py` gets an `mxfp4_dsv4` scheme. It builds W4A16 weights in the SEPARATED gate/up layout, sets `use_mxfp4_w4a4_dsv4`, asserts FP4 dispatch is selected, and compares two-rank MoRI against AITER's non-EP path, including CUDA graph replay at m=32. Every case also asserts that the experts receive `2 * m` rows, the trimmed prefix, rather than MoRI's max-sized buffer.

```bash
FLYDSL_RUNTIME_CACHE_DIR=<writable dir> pytest tests/kernels/moe/test_mori_moe.py
```

On 2x MI355X, all 28 cases pass: 7 shapes each for bf16, fp8_token_channel, mxfp4 and mxfp4_dsv4. Without a writable `FLYDSL_RUNTIME_CACHE_DIR`, both MXFP4 schemes fail with a `PermissionError` on AITER's default FlyDSL cache dir in our image. That is unrelated to this change.

### E2E: DeepSeek-V4.1-Flash DEP2 on MI355X

Setup: 1 node, 2 GPUs, `--tensor-parallel-size 1 --data-parallel-size 2 --enable-expert-parallel --moe-backend aiter --kv-cache-dtype fp8 --block-size 128 --max-num-seqs 64 --max-num-batched-tokens 8192`, CUDA graphs on. Validated on a local stack of `main@0cbac6cd13` + #58014 + #59596 + this change.

**Accuracy.** InferenceX GSM8K eval: `lm_eval --model local-chat-completions --apply_chat_template`, 5-shot, all 1319 questions, `max_tokens=16384`, `temperature=0`, `num_concurrent=64`, no speculative decoding.

## Details

* The DSv4.1 a4w4 expert path already sets `q_dtype_a=fp4x2` and forwards `a1q_scale`, so #59596's pre-quantized FP4 handling in `rocm_aiter_fused_experts` applies unchanged. Only the gate needed widening.
* Trimming: the bound comes from `dp_metadata.num_tokens_across_dp_cpu`, so it is known on the host, needs no device sync, and is fixed for a given CUDA graph capture size. Each source rank sends a token at most once, so every valid received row is inside that prefix.
* The e2e gain is modest on EP2. With top-6 over 2 ranks, almost every token goes to both ranks, so dispatch volume is not reduced, and a single xGMI link between the two GPUs (~64 GB/s) carries all traffic. FP4 shrinks dispatch bytes about 3.6×, while combine stays BF16.
* I also tried MoRI's combine quantization on this model (EP2) without wiring it in. `fp8_direct_cast` was about 1.3× faster on combine but lowered accuracy (gsm8k 0.869 vs 0.897 on the repo's `gsm8k_eval.py`). The `fp8_blockwise` and `fp4_blockwise` modes were slower than BF16 combine at EP2. Combine is left BF16. #44323 covers combine dtype selection more broadly.
* Not a duplicate: #59596 only gates on `quant_config.use_mxfp4_w4a4`, and #44323 (MoRI dispatch/combine dtype refactor) has no DSv4.1 a4w4 handling. I'm happy to fold this into #59596 if the author prefers.
