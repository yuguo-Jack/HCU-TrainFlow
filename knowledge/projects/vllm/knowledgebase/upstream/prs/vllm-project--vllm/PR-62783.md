# [Bugfix][Pooling] Keep the JinaVL score token when truncating score prompts

[Upstream PR](https://github.com/vllm-project/vllm/pull/62783) · state: closed · merged: True

## Original PR description

## Overview

`jinaai/jina-reranker-m0` scores the hidden state of a score token (id 100) that `JinaVLForSequenceClassification.post_process_tokens` appends to the prompt. Since #28631, `CrossEncoderIOProcessor` appends it in `get_score_prompt`, before `render` calls `tok_params.apply_post_tokenization`. When `truncate_prompt_tokens` is binding, truncation runs on the prompt that already has the score token. With the default right-side truncation, that cuts the score token off, and `/score` and `/rerank` silently return the classifier output for an ordinary prompt token. This reserves room for the tokens `post_process_tokens` appends: truncation, padding and the length check run with limits reduced by that count, and the tokens are appended afterwards. The reference `compute_score` in the model repo does the same (it truncates to `max_length - 1`, then appends the score token).

## Claims

- With a binding `truncate_prompt_tokens`, jina-reranker-m0 scores match scoring the template truncated to `truncate_prompt_tokens - 1` tokens plus the score token, and the prompt stays within `truncate_prompt_tokens`.
- `truncate_prompt_tokens=-1` on prompts longer than `max_model_len` keeps working: the prompt is truncated to `max_model_len - 1` tokens plus the score token.
- No change for models whose `post_process_tokens` is a no-op (every other cross-encoder). The change stays in `CrossEncoderIOProcessor`, plus a small `reserve_tokens` helper in `vllm/entrypoints/pooling/utils.py`.

## Validation

Real server on `34ac4f96a3` (`jinaai/jina-reranker-m0 --runner pooling --max-model-len 512`, RTX 4090, `--enforce-eager`). `/rerank` with query "What is the capital of France? Please answer briefly and precisely." and two documents (Paris, Berlin). The references are `/pooling` (`task="classify"`) on the explicit template token IDs, truncated, plus the score token.

Short documents (templates of 32 and 34 tokens), `truncate_prompt_tokens=28`:

| | Paris | Berlin |
|---|---|---|
| reference: 27 tokens + score token | 0.9831 | 0.8146 |
| `main` | 0.9857 | 0.9563 |
| this PR | 0.9830 | 0.8142 |

Long documents (templates of 672 and 674 tokens), `truncate_prompt_tokens=-1`:

| | Paris | Berlin |
|---|---|---|
| reference: 511 tokens + score token | 0.9213 | 0.8930 |
| `main` | 0.9380 | 0.9980 |
| this PR | 0.9211 | 0.8914 |

On `main` the irrelevant document scores about as high as the relevant one, or higher. The remaining differences are bf16 noise between batched and single requests.

Tests:

- `pytest tests/entrypoints/pooling/scoring/test_io_processor_unit.py tests/entrypoints/pooling/scoring/test_jina_ranking_io_processor_unit.py`: 27 passed.

## Details

Before #28631, `get_score_prompt` tokenized with truncation, appended the score token, and the serving layer only validated the length. #28631 moved post-tokenization truncation into `render` after `get_score_prompt`, so it now also runs over the appended token.

`render` now shrinks `max_total_tokens`, `truncate_prompt_tokens` and `pad_prompt_tokens` by the number of appended tokens (`reserve_tokens`) (`-1` follows the reduced `max_total_tokens`), tokenizes and truncates with those limits, and then calls `post_process_tokens`. The count is derived once by running `post_process_tokens` on an empty prompt, so the model interface is unchanged. As a side effect, the "maximum context length" in the length error for jina-reranker-m0 reports `max_model_len - 1`, which is the real limit for the template.

An earlier version of this PR appended the token after truncation without reserving room, so the prompt could exceed the limits by one token (thanks to the review for catching that).

Not a duplicate: I found no issue or PR for this (searched "jina-reranker-m0 truncate", "post_process_tokens", "score token truncation rerank", "JinaVL truncate_prompt_tokens"). #55200 validates truncated prompts for the jina-reranker-v3 processor (`JinaRankingIOProcessor`), and #49963 restored `truncate_prompt_tokens` for that processor. Neither touches the JinaVL score token.

AI assistance was used to find this bug, write the fix and the test, and run the validation shown above.

🔴 jina-reranker-m0 requests that ask to be truncated to fit the context (`truncate_prompt_tokens=-1` or a value equal to `max_model_len`) now fail instead of being scored. `apply_post_tokenization` truncates to `max_model_len`, and `post_process_tokens` then appends token 100. The prompt becomes `max_model_len + 1` tokens and skips `_token_len_check`. Fix: reserve one slot for model-appended tokens, so truncation and the length check use `max_model_len - 1` when the model appends a token, as the reference `compute_score` does.

<details>
<summary>Why this was flagged</summary>

A `/score` or `/rerank` request to jina-reranker-m0 has a query+document longer than `max_model_len` and sets `truncate_prompt_tokens=-1`. `_truncation_slice` (vllm/renderers/params.py:493-495) then resolves to `max_truncation_tokens`, which is `max_input_tokens` = `max_model_len` for pooling (params.py:241-242). `render` (io_processor.py:652) truncates to exactly `max_model_len`, and `_token_len_check` passes. Line 657 then appends token 100 via `JinaVLForSequenceClassification.post_process_tokens` (jina_vl.py:150), giving `max_model_len + 1` tokens. `_validate_prompt_len` (vllm/v1/engine/input_processor.py:574-592) rejects it with "longer than the maximum model length". On the base branch, the append ran before truncation and the request returned a result, though a wrong one. The length check in `apply_post_tokenization` cannot catch it because it runs before the append.

**Verification:** At io_processor.py:652, `apply_post_tokenization` truncates to exactly max_model_len, and `_token_len_check` passes because the check is `len(tokens) > max_input_tokens`. The new line 657 then calls `self.model.post_process_tokens(engine_prompt)`, and JinaVL's version (jina_vl.py:148-149) runs `prompt["prompt_token_ids"].append(100)`. The prompt is now max_model_len + 1 tokens.

</details>
