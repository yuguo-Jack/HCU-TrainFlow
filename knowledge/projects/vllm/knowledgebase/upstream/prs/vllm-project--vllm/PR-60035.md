# [Bugfix][Pooling] Make MEAN pooling batch invariant when the flag asks for it

[Upstream PR](https://github.com/vllm-project/vllm/pull/60035) · state: open · merged: False

## Original PR description

## Overview

With `VLLM_BATCH_INVARIANT=1`, MEAN-pooled embeddings are not reproducible: the same request can get
different bits between identical runs and alone versus inside a batch. `MeanPool` sums each sequence
with `index_add_`, which is nondeterministic on GPUs. Under the flag, this PR sums each sequence over
its own rows instead; the default path is unchanged. Related: #38559.

## Claims

- **Bug:** `docs/features/batch_invariance.md` says "Batch invariance ensures that the output of a model
  is deterministic and independent of the batch size or the order of requests in a batch." With MEAN
  pooling on `main` (A40, `intfloat/e5-small`), embedding the same 64 texts five times changed the bits
  of 44 of 64 embeddings (46 of 64 in a second run).
- **Root cause:** `MeanPool.forward` accumulates with `segment_sums.index_add_(0, segment_ids,
  hidden_states)`. On CUDA this is an atomic add, so the order of the additions changes between
  launches, and float addition is not associative. The batch-invariant overrides cover matmul,
  softmax and mean, not this reduction.
- **Fix:** under the flag, `MeanPool` splits `hidden_states` by prompt length and sums each sequence on
  its own (`sum(dim=0, dtype=torch.float32)`), so each sum depends only on that sequence's rows.
- **Cost:** only under the flag. The pooling call launches one reduction per sequence: on the A40 it took
  1.5× the default path for a step of 64 × 512 tokens and up to 7× with 128 short sequences. With
  #38559's `vllm bench serve` command line (multilingual-e5-base, flag on, five runs per side) the two
  sides overlapped: 167.06–179.59 req/s on `main`, 170.41–188.42 req/s with this PR.

## Validation

Commands, output excerpts and the full logs: [this comment](https://github.com/vllm-project/vllm/pull/60035#issuecomment-6012056147). NVIDIA A40 (SM86), vLLM nightly wheel for
`main` `30ab428235` (`0.30.1rc1.dev708+g30ab42823`), torch 2.13.0+cu130.

- `pytest "tests/model_executor/layers/test_pooler_methods.py::TestMeanPool::test_batch_invariant_under_the_flag"`
  (fp32 and bf16): both cases fail on `main` and pass with this PR. The test pools 64 random sequences
  in one batch and checks that three of them pool to the same bits alone.
- End to end, `repro_60035.py` (e5-small): on `main`, 44 of 64 embeddings change across five identical
  runs, and texts 31 and 63 differ from their in-batch embedding. On `main` that second check cannot
  separate position from run-to-run noise. With this PR, all 64 embeddings are identical across the
  five runs, and all three texts match their in-batch embedding.
- `VLLM_GPU_SYNC_CHECK=error`: no sync error on `main` or with this PR; a positive control that adds an
  `.item()` to `MeanPool.forward` raises, so the check covers this code.

The new test is in `TestMeanPool`, which runs in CI's Model Executor job (H200 MIG 35GB, and MI300 for
the AMD mirror), so no new CI wiring is needed.

## Details

- **Why not the earlier `cumsum`:** going back to the pre-#38559 `cumsum` over the batch would be
  reproducible but still position dependent, since each segment's sum is a difference of prefix sums
  over every preceding sequence.
- **A vectorized alternative:** `torch.segment_reduce(hidden_states.float(), "sum", lengths=...)` (three
  launches instead of one per sequence) gave
  identical bits across calls and for three sequences pooled alone versus in a batch, and was 2.0–6.4×
  faster than this PR's loop, but it needs an fp32 copy of the whole step's hidden states. I kept the
  loop; I can switch if that trade is preferred.
- **Not a duplicate:** in late August I searched PRs for `MeanPool`, `mean pooling`,
  `pooler determinism` and `index_add`, and issues for `embedding deterministic`, and repeated it
  on 2026-10-05. On 2026-10-06 I searched issues and PRs created since 2026-10-05 for `MeanPool`,
  `index_add`, `mean pooling`, `embedding deterministic`, `pooling batch invariant` and
  `embedding batch invariance`; the only match is this PR. #59181 (open issue) reports a 1-ulp
  cross-encoder difference on sm_120 that it attributes to the matmul overrides, not pooling.
- **Limitations:** measured on one GPU (A40, SM86): reproducibility with e5-small, serving cost with
  multilingual-e5-base.

The flag-on path launches one reduction per sequence, so its cost grows with the number of sequences in a step: about 1.5× the default path at 64 × 512, and several times it with hundreds of short sequences. A vectorized alternative exists: `torch.segment_reduce(hidden_states.float(), "sum", lengths=...)`, three launches (cast, reduce, divide) instead of one per sequence, gave identical bits across calls and for three sequences pooled alone versus in a batch (`probe_segment_reduce.py`, below), and was 2.0–6.4× faster than this PR's loop at these shapes. It needs an fp32 copy of the whole step's hidden states (about 100 MB for 32768 tokens at hidden size 768), which #38559 avoided by working in chunks, and I have not run the sync check on it, so I kept the loop here. I can switch if you prefer it.

# Embed the same 64 texts five times, then three of them alone. With batch invariance an
# embedding must not change between identical runs or with the text's place in the batch.
import torch

from vllm import LLM

llm = LLM(
    model="intfloat/e5-small",
    runner="pooling",
    enforce_eager=True,
    enable_prefix_caching=False,
    max_model_len=512,
    max_num_seqs=128,
    max_num_batched_tokens=16384,
    seed=0,
)
words = (
    "the quick brown fox jumps over a lazy dog while seven wizards quietly judge "
    "boxing matches near the old harbor at dawn"
).split()
texts = [
    " ".join(words[(j * 7 + i) % len(words)] for j in range(5 + (i * 11) % 120))
    for i in range(64)
]


def embed(batch):
    return [torch.tensor(o.outputs.embedding) for o in llm.embed(batch, use_tqdm=False)]


runs = [embed(texts) for _ in range(5)]
changed = [i for i in range(64) if any(not torch.equal(r[i], runs[0][i]) for r in runs[1:])]
max_delta = max((r[i] - runs[0][i]).abs().max().item() for r in runs[1:] for i in range(64))
print(f"texts whose embedding changed across 5 identical runs: {len(changed)}/64")
print(f"max |delta| across runs: {max_delta:.3e}")
for i in (0, 31, 63):
    same = torch.equal(embed([texts[i]])[0], runs[0][i])
    print(f"text {i} embedded alone vs inside the batch: {'identical' if same else 'DIFFERENT'}")

# VLLM_GPU_SYNC_CHECK=error. Args: arm (main|pr), mode (plain|positive_control). The positive control
# adds a deliberate `.item()` to MeanPool.forward; it MUST fail, otherwise the check is not live.
import os

    VLLM_BATCH_INVARIANT="1", VLLM_GPU_SYNC_CHECK="error", VLLM_ENABLE_V1_MULTIPROCESSING="0"
)

from vllm import LLM
from vllm.model_executor.layers.pooler.seqwise import methods

    _forward = methods.MeanPool.forward

    def forward(self, hidden_states, pooling_metadata):
        hidden_states.sum().item()  # a deliberate GPU->CPU sync
        return _forward(self, hidden_states, pooling_metadata)

    methods.MeanPool.forward = forward
