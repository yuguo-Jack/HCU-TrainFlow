metadata section around the captured DeepSeek V4.1 flash-decode forward.
Each item is its own PR (#63393 stacks on #63296; #63523 stacks on #63393;
#63579 stacks on #63523); this branch stacks them so the combined effect
can be A/B tested before the individual PRs are marked ready. Items 6
and 7 are committed directly on this branch.

| # | PR | Change | Launches removed / step |
|---|----|--------|------------------------|

| 2 | #63307 | One kernel for `make_dummy`, one for grouped block-table zeroing; cumsum replaced by its closed form | 11 + G (19 at G=8) |

All five keep buffer addresses and value contracts for downstream
consumers (attention kernels, cudagraph replay, JIT warmup).

The engram hash/lookup pair stays unfused on purpose (a radix sort and a

## Post-campaign refinements

After the first four-PR e2e runs, a code review of the head turned up
four refinements, each landed on the sub-PR that owns the code and
merged into this branch:

- The SWA index kernels' invalid-path `-1` row-clear now stops at
  `num_valid_tokens` (#63296): the pre-fusion kernel never wrote index
  rows past it, and on decode+chunked-prefill steps the far tail spans
  the chunk's rows, where the full-width clears cost megabytes of dead
  stores per step. The lens zero still covers the full buffer tail.
- The batched SWA flush takes the direct per-group path at a single
  group (#63393): at G=1 the table upload fuses nothing. The batched
  kernel also bounds its row-clear the same way and reads its parameter
  table through `_load_ptr`, restoring the 16-byte vectorization hint.
- The params-table H2D copy runs on change, not per step (#63523):
  every row holds addresses and strides of persistent per-group buffers,
  so the table only differs on reallocation or a group-count change; a
  numpy compare guards the copy and event record.
- The native indexer decode-lens kernel (#63579) moved from one program
  per token to a 256-wide block-strided grid, removing the scalar div/mod
  per CTA.

None of these change output values or buffer contracts; the e2e A/B and
the profiled A/B above both measured the refined build.

The same traces ruled out the other candidates from the kernel-duration
list: the 301 us/step `nvjet` GEMM is the in-graph lm_head streaming
~1.85 GB of bf16 weights at tiny M (weight-bandwidth-bound, an lm_head
dtype change, not a fusion); the engram hash/lookup chain is in-graph
with per-layer embedding tables prefetched on a side stream, so batching
the lookups would serialize work the prefetch currently overlaps; the
two paged-MQA metadata builds cannot merge without breaking CUDA-graph
address stability (deep_gemm returns fresh tensors and the DtoD copies
pin them); and folding the image-sentinel mask polarity saves no
launches because both polarities are consumed.

## Draft-prologue fusions (direct)

The draft graph's FULL-cudagraph prologue spent ~105 us of in-graph GPU
per decode step before the draft layers. Commit `e685707e` cuts ~35 us
of it with three fusions:

- The context-KV precompute ran one `fused_wqa_wkv` GEMM
  ([T,5120]x[5120,1792]) per draft layer and discarded the q_lora half
  of each output. A merged `context_wkv_proj` ([T,5120]x[5120,1536])
  projects all layers' WKV in one GEMM; weight loading duplicates each
  `mtp.{i}.attn.wkv` shard into the merged projection, mirroring the
  DeepSeek V4 dspark implementation that already ships this pattern.
  The 512-wide output sections keep the fp8 block-quant shards
  128-aligned, so quantization is unchanged.
- The per-layer kv_norm RMSNorm now runs inside
  `fused_deepseek_v4_kv_rope_insert`, which takes the norm weight and a
  row-strided KV view so the projection output slice is quantized and
  inserted into the cache directly (V4 still norms outside its dummy-q
  insert). The kernel matches the reference RMSNorm to fp8-code
  granularity; a kernel test covers the reduction-order tolerance.
- Draft layer 0 enters with the 2D embedding through the
  `hc_attn_fn_broadcast` path instead of materializing the [24,20480]
  repeat of the entry hidden states.

The e2e A/B includes this item, and gsm8k, the accuracy gate for the
fused kv_norm, matched within stderr. The expected e2e effect (~35 us on
a 5-10 ms ITL) sits under the +-2% same-build repeat band, so it reports
inside the aggregate; the kernel-level prologue timing from the trace
window is the primary evidence for this item.

## Dummy-path prologue fusion (direct)

Commit `8e0be20c` stages the dummy path's per-step buffer builds into
the decode prologue parameter table as three new kinds (`FILL_I64`,
`ZERO_ROWS`, `DUMMY_BATCH`):

- A DP rank with no tokens still builds a dummy batch every step: the
  `make_dummy` init kernel, the grouped block-table row zeroing, and
  the slot-mapping pad fill each launch separately. They now retire as
  rows of one prologue launch; with the attention phases' megakernel
  that is 4 launches down to 2 on tokenless steps.
- The dummy rows write the shared step buffers (`seq_lens`,
  `query_start_loc`, `positions`) that the attention-phase prologue
  rows read, and one launch gives no inter-CTA ordering, so the early
  bracket never shares a launch with the attention bracket: it flushes
  at the top of `prepare_attn`, before the replay warmup and slot
  padding read those buffers. Paths that populate zeroed rows or run
  outside a single plain decode step (state slots, dummy context, PCP,
  DCP, multi-ubatch, randomized inputs) keep the direct launches.
- The two-range `is_padding` fill in the sample path becomes one
  `_fill_is_padding_kernel` launch.

Buffer contracts hold: staged buffers are byte-identical to the direct
launches, block-table zeroing still clears dirty rows past `num_reqs`,
and the persistent-tensor addresses the CUDA graph capture relies on
are unchanged. CUDA-gated tests in
`tests/v1/worker/test_gpu_dummy_prologue.py` compare staged vs direct
buffer contents; ruff and CPU import checks pass locally, and the GPU
tests are pending a CI run. This item is not yet covered by an e2e A/B
arm.

## Compressed-slot padding-gap fix (direct)

Commit `0b86f03d8` fixes a correctness bug that `550e44226f`
introduced when it moved the compressed slot mapping's `out.fill_(-1)`
into the kernel: the in-kernel tail clear started at the padded
`num_tokens`, but full-CUDA-graph decode keeps `query_start_loc` flat
below the padded token count, so the gap `[qsl[num_rows], num_tokens)`
held the previous step's slot ids. The captured indexer K store
replays over the full padded width and writes through every
non-negative slot, so stale ids in that gap corrupted the indexer K
cache of live requests: the 2026-10-28 e2e run decoded garbage from
the first traffic step (speculative acceptance 0.000, gsm8k
generations running to the length cap, and the run ended in the
`indexSelectSmallIndex` assert after NaN logits).

The tail now reads its start from `qsl[num_rows]` — where the request
programs stop — on device; the host cannot know that value without a
sync, so both launch sites size the tail grid for the widest tail. The
`num_tokens` kernel argument is gone with it, and the draft rebuild is
unchanged (its arange qsl already ends at `num_rows`). A CUDA-gated
regression test seeds a stale `out` buffer and checks the flat-padded
gap clears to PAD.

## CuTe DSL port of the KV rope/insert kernel (direct)

Commit `cad2bcb10` replaces the
`fused_deepseek_v4_qnorm_rope_kv_insert` CUDA C source and its four
registered ops with a CuTe DSL module that exposes the same entry
points under the same positional schemas (follow-ups `993a6fcbb`,
`9f3956550d`). The math carries over with fp32 accumulation, the KV
branch's bf16 double-round before the absmax, the warp shuffle
reduction order, and the exponent-field UE8M0 scales, over both paged
record layouts (V4 584 B/token, V4.1 mxfp8 528 B/token) and the
full-cache bf16/fp8 variants. The six production call sites import the
module at function scope under a `has_cutedsl()` gate and fail closed
with a named RuntimeError when the DSL package is absent. Known gap:
the `.cu` also built for ROCm, so AMD paths that reached these ops now
refuse instead of running; restoring an AMD implementation is follow-up
work.

The e2e rerun after the slot-tail fix above still decoded garbage
(gsm8k exact_match 0.0000), so the kernel went through a value-level
differential against the reference on an H200 pod. The port had four
defects, each invisible to a clean launch because it corrupts values
while running at full speed, and each caught only by the port's own
suite, which had never been executed (216 of 227 tests failed).
`798a6c99f` fixes them:

- `bf16x2_to_fp32x2` returns the low half first. The port unpacked it
  as (high, low) in `_decode_words` and `_apply_kv_norm`, so every bf16
  pair was loaded with its two elements swapped: Q, KV V4 records,
  mxfp8, combined, and both full-cache variants wrote pairwise-swapped
  values.
- The paged kernel's V4-record RoPE store took its per-lane word offset
  as `(dim_base - NOPE_DIM) // 4`. That difference is an element count
  and a uint32 word holds two bf16s, so consecutive rope lanes wrote
  overlapping word ranges (a write race) and the last 12 words of every
  record stayed unwritten. The stride is now `// 2`.
- The bf16 wrapper's unused `q_fp8` stand-in carried a zero head count
  against the head dim the JIT binds across one call's arguments. The
  stand-in now takes the real head count.
- Q-less full-cache launches compiled their warmup fakes with
  `num_heads_q == 0`, and a zero shape mode is not a legal CuTe layout.
  The warmup fake floors the head count at one. The grid never
  dispatches a Q slot when `num_heads_q == 0`, so the stand-in is never
  read.

The rope region now compares with a one-bf16-ULP slack
(`rtol=1e-2, atol=1e-6`, previously ROCm-only): the DSL contracts the
rotation's two fp32 products into an FMA, as nvcc did for the CUDA
original, while torch's reference rounds each product separately.

`0c1bcad95` repairs three test fixtures that predate or overshoot the
fusions. The dspark compressor fixture stubbed `attn` without the
`kv_norm` attributes `_insert_context_kv` has read since the prologue
fusion, so all 32 parametrizations died on the fixture before reaching
any kernel; its oracle now drives the kv-only op with the same norm
arguments, keeping the comparison byte-exact over the glue the dspark
path owns (attribute reads, scale, flags, strided cache binding, graph
replay) while the norm math stays covered by the kernel suite. The
batched decode-indices test poisoned index rows across the whole token
range, past the decode boundary the decode-phase launch clears. The
dummy-prologue test built its scratch with `torch.full(6, ...)`,
passing 6 as the fill value where the shape is a tuple.

The suites pass on an H200 pod in the wheel-build environment: 227
port, 136 compressor, 55 indexer, 3 prologue, 36 swa-visible tests.
The 26 nvfp4 compressor parametrizations that fail there are ptxas
sm_90a environment failures in the image, on a quant path this branch
does not exercise. The e2e rerun with the port fixes is running.

## Cooperative candidate selection on the stock decode path (direct)

Commit `9e2df243a` routes the stock decode branch's candidate-block
selection through `cooperative_topk`. The c16 decode trace showed the
selection spending ~82 us of stream time per step in the `torch.topk`
fallback, nineteen mbtopk and cub launches plus the trailing
`radixSortKVInPlace` of the sorted=True sort, while the main token
top-k on the same step already ran the single-wave `cooperative_topk`
kernel. `select_candidate_blocks_cooperative` existed for the
specialized decode path only, so stock decode on Hopper took the
fallback unconditionally.

The commit moves the cooperative selection (prefix score kernel,
finalize kernel, shape gate) from
`models/deepseek_v41/nvidia/specialized_decode/attention/candidate_topk.py`
into `kernels/attention/dsa/candidate_blocks.py` beside the reference
kernel, deletes the old module, and dispatches from the stock decode
branch when each row carries its own fp32 bounds and
`supports_cooperative_candidates` accepts the shape (at most 64 rows,
k in {512, 1024, 2048}, 16-byte aligned score rows). DeepSelect GPUs,
rows with shared bounds, and every prefill chunk keep the reference
path. Candidate sets match the reference except for fp32 boundary
ties, the contract the specialized path already ships. The specialized
path and its SM100 equivalence tests import from the new location
unchanged.

When the sub-PRs merge, this branch can be fast-forwarded to main and
closed.
