# [Bugfix][FlashInfer] Restrict W4A16 NVFP4 GEMM to SM100/103; fix CuTeDSL autotune op names

[Upstream PR](https://github.com/vllm-project/vllm/pull/56553) · state: open · merged: False

## Original PR description

## Summary

FlashInfer CuTe-DSL W4A16 NVFP4 GEMM correctness/perf fixes:
- Restrict `FlashInferCuteDslNvFp4W4A16LinearKernel` to SM100/103. On SM12x the un-tuned CuTe-DSL W4A16 kernel falls back to its heuristic tactic (several times slower than CUTLASS at prefill), and its autotune JIT-compiles a cubin + CUDA graph per tactic that `empty_cache()` cannot reclaim — accumulating ~7 GiB and OOMing KV-cache allocation on 32 GiB consumer GPUs.
- Fix the CuTe-DSL autotune op-name skip so W4A16 (`bf16_fp4_cute_dsl_[sm100_]gemm`) and W4A4 (`fp4_gemm`) are each skipped under the correct op name.

## Why this is not duplicating an existing PR

No open PR restricts the FlashInfer CuTe-DSL W4A16 GEMM by arch or fixes its autotune op-name skip. Complements the NVFP4-KV work (keeps the CuTe-DSL W4A16 path off SM12x) rather than overlapping it.

## Changes

- `vllm/model_executor/kernels/linear/nvfp4/flashinfer.py`: `is_supported` restricted to SM100/103
- `vllm/model_executor/warmup/kernel_warmup.py`: `_flashinfer_autotune_skip_ops` returns the correct per-backend op names

## Test

On SM120 the CuTe-DSL W4A16 GEMM is no longer selected (consistent with the W4A16 force-path in `init_nvfp4_linear_kernel`); verified the Qwen3.8-27B NVFP4 stack still serves correctly on RTX 5090 after the restriction.

- hclsys · comment · 2026-09-13T12:17:50Z · [source](https://github.com/vllm-project/vllm/pull/56553#issuecomment-5653212285)

Checked this on sm_121 (GB10), since the description's evidence is sm_120 and the restriction covers all of SM12x.

On current main at cc=121, `FlashInferCuteDslNvFp4W4A16LinearKernel.is_supported(121)` returns True — so today the kernel does claim GB10. After your change it goes False, and the `use_a16` + `auto` force-path in `init_nvfp4_linear_kernel` (the `compute_capability in (100, 103)` branch) falls through to `MarlinNvFp4LinearKernel`, which reports `is_supported(121)` → True here. So sm_121 keeps a W4A16 path and this doesn't strand GB10 — that was my one concern with dropping the sm_12x arm.

The autotune-skip rework looks right as well: the two kernels are siblings under `NvFp4LinearKernel` rather than one subclassing the other, so the `if`/`elif` can't shadow each other, and accumulating into a set instead of returning on the first match is what you want for a model carrying both W4A16 and W4A4 layers.

One thing I can't speak to: the ~7 GiB autotune accumulation. GB10 has unified memory, so a 32 GiB KV-cache OOM wouldn't reproduce here the same way, and I haven't measured it. If you'd rather have the prefill CUTLASS-vs-CuTeDSL comparison on sm_121 measured instead of inferred from sm_120, I have the card.
