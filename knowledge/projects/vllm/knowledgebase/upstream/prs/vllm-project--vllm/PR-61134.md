# [Model Loader] Make dummy weight init dtype-aware

[Upstream PR](https://github.com/vllm-project/vllm/pull/61134) · state: closed · merged: True

## Original PR description



## Overview

Make `--load-format dummy` produce non-degenerate quantized weights by picking dummy values per dtype in `initialize_single_dummy_weight`. Today, dummy-loaded MXFP4 MoE experts are entirely zero and FP8 weights are ~98% zero. That skews performance measurements with dummy weights (e.g. MoE routing and kernels see all-zero experts).

Related: #54958 bounds the memory of the FP8 dummy path. It's complementary (how values are generated vs. which values), and this PR keeps that code path intact so the two compose.

## Claims

- uint8 / int8 / `float4_e2m1fn_x2` params (packed FP4, int8 weights and zero points) get deterministic random bytes instead of being left as zeros or uninitialized memory. Every FP4 code is finite.
- E8M0 scales (`float8_e8m0fnu`, or uint8 params named like a scale, e.g. MXFP4 `w13_weight_scale`) get a fixed 2**-7 instead of arbitrary tiny exponents.
- 8-bit floats default to the range ±1 instead of ±1e-3, which mostly underflows in FP8 (E4M3's smallest normal is 2**-6).
- Wider integer params (int32/int64, e.g. `g_idx`) are untouched, since random values could be out-of-range indices. Explicit `low`/`high` and `dummy_weight_value` still take precedence.

## Validation

Weight statistics after `LLM(model, load_format="dummy")` (after `process_weights_after_loading`) on GB200, measured with `llm.apply_model`:

| Model | Param dtype | Zero fraction before | Zero fraction after | Non-finite |
| --- | --- | --- | --- | --- |
| `RedHatAI/gpt-oss-20b` (MXFP4 experts) | uint8 (packed FP4 + scales) | 1.0 | 0.0039 (≈1/256) | 0 |
| `RedHatAI/gpt-oss-20b` | float8_e4m3fn (backend-converted) | 1.0 | 0.0 | 0 |
| `Qwen/Qwen3-30B-A3B-FP8` | float8_e4m3fn | 0.977 | 0.001 | 0 |

Both models generate with finite logprobs before and after.

<summary>Reproduction script</summary>

```python
import sys, torch
from vllm import LLM, SamplingParams

def weight_stats(model):
    stats = {}
    for _, p in model.named_parameters():
        if p.dtype in (torch.bfloat16, torch.float16, torch.float32):
            continue
        s = stats.setdefault(str(p.dtype), [0, 0])
        raw = p.data.view(torch.uint8) if p.dtype in (torch.uint8, torch.int8) else p.data.float()
        s[0] += int((raw == 0).sum()); s[1] += p.numel()
    return {k: round(z / n, 4) for k, (z, n) in stats.items()}

llm = LLM(sys.argv[1], load_format="dummy", enforce_eager=True, max_model_len=1024,
          gpu_memory_utilization=0.5, skip_tokenizer_init=True)
print(llm.apply_model(weight_stats)[0])
print(llm.generate([{"prompt_token_ids": [785, 6722, 315, 9625, 374]}],
                   SamplingParams(max_tokens=8, temperature=0, logprobs=1))[0].outputs[0].logprobs)
```

Run with `VLLM_ALLOW_INSECURE_SERIALIZATION=1`.

## Details

- **Identifying uint8 E8M0 scales by name.** Several quant methods (MXFP4, Quark OCP-MX, ModelOpt MXFP8) store E8M0 scales as uint8, which is indistinguishable from packed weights by dtype. `DummyModelLoader` now passes each tensor's attribute name, and uint8 tensors whose name contains `scale` get the E8M0 fill. Quant methods can still override per param with `dummy_weight_value`.
- **Magnitudes.** 2**-7 keeps dequantized weights small and finite: |FP4| ≤ 6 gives ≤ 0.047; FP8 ±1 gives ≤ 0.008. FP8 weights with float32 scales (dummy ±1e-3) end up around ±1e-3, matching bf16 dummies.
- **ROCm** previously zeroed all integer params for cross-process reproducibility. 8-bit integer params are now filled from the seeded generator, which is also reproducible.
- **Limitation.** GGUF block formats are uint8 with embedded fp16 scales, so random bytes can decode to large or non-finite values. That's no worse than the uninitialized memory they got before.
- **Behavior change.** Benchmarks run with dummy weights on FP8 / MXFP4 / int8 models may shift, because their quantized weights are no longer zero.
