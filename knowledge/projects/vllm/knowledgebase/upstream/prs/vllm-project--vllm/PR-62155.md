# [Bugfix] Reject shape mismatches in ShardedStateLoader instead of partially loading (fixes #61681 mechanism)

[Upstream PR](https://github.com/vllm-project/vllm/pull/62155) · state: open · merged: False

## Original PR description

## Purpose

Fixes the silent wrong-output mechanism behind #61681.

`ShardedStateLoader.load_weights` loads a saved tensor that is smaller than its parameter into a narrowed view of the parameter, and only logs a warning. The code comment says this is for LoRA padding. The rest of the parameter keeps whatever was in memory, and nothing raises.

That happens whenever a `sharded_state` checkpoint is loaded with a different parallel layout than it was saved with. One concrete case is `--mm-encoder-tp-mode`. With `weights` (the default), the vision tower is TP-sharded. With `data`, every rank holds the full tower. A checkpoint saved from a `weights`-mode engine and served with `--mm-encoder-tp-mode data` therefore gets a vision tower that is half real weights and half uninitialized memory. Requests succeed, the text side is fine, and image answers are wrong. That matches #61681.

This PR makes the loader raise a `ValueError` on any shape mismatch, naming the tensor, both shapes, and the likely cause. Tensors larger than the parameter already failed in `copy_`. They now fail with the same clear message.

**Why dropping the narrowing is safe:** LoRA no longer pads parameters (there is no `lora_vocab_padding_size` on main; vocab padding is `DEFAULT_VOCAB_PADDING_SIZE` with or without LoRA). I also checked it directly. Saving a sharded checkpoint without LoRA and loading it with `enable_lora=True` takes zero narrowing paths, and greedy output is identical to `--load-format auto`. That is the same scenario as `test_sharded_state_loader[enable_lora=True]`, run on Qwen3-0.6B at TP=2, v0.31.0.

## Reproduction (before this PR)

Qwen3.8-27B-FP8 (Qwen3-VL vision path, which supports `--mm-encoder-tp-mode data`), TP=2, 2x H20, `vllm/vllm-openai:v0.31.0`.

1. Save with `examples/features/sharded_state/save_sharded_state_offline.py --tensor-parallel-size 2 --mm-encoder-tp-mode weights`.
2. Serve the result with `--load-format sharded_state` and run the color-quadrant script from #61681.

| load with | `loading tensor of shape ...` warnings | result |
|---|---|---|
| `--mm-encoder-tp-mode weights` | 0 | 4/4 correct |
| `--mm-encoder-tp-mode data` | 330, e.g. `loading tensor of shape torch.Size([1728, 1152]) into parameter 'visual.blocks.0.attn.qkv.weight' of shape torch.Size([3456, 1152])` | garbage tokens for a single image; HTTP 500 for 48 images |

With this patch applied to the same build, the `data`-mode server fails at startup instead:

```
ValueError: Shape mismatch for 'visual.blocks.0.attn.proj.weight': the checkpoint has (1152, 576), the model expects (1152, 1152). A sharded_state checkpoint must be loaded with the parallel layout it was saved with (tensor/pipeline parallel size, --mm-encoder-tp-mode, ...). Re-save it with the current configuration or load the original checkpoint with --load-format auto.
```

(For this FP8 checkpoint I had to add the attention `q/k/v/prob_scale` keys to the shards to load it at all, with identical settings. That is a separate round-trip bug, which I'll report in its own issue. It is unrelated to this change.)
