# [ROCm][MiniMax-M3.1] MXFP8 linear on AITER's tuned FlyDSL GEMM

[Upstream PR](https://github.com/vllm-project/vllm/pull/65479) · state: open · merged: False

## Original PR description


**NOTE:** We should wait to merge this one after this AITER PR makes it into a release https://github.com/ROCm/aiter/pull/6060
## Overview
Adds `AiterMxfp8LinearKernel`, an MXFP8 linear kernel for gfx950 that runs AITER's tuned FlyDSL GEMM (`gemm_a8w8_blockscale_bpreshuffle` with 1x32 E8M0 scales). It is placed ahead of `RocmDotScaledMxfp8LinearKernel` (Triton `tl.dot_scaled`) in the ROCm MXFP8 kernel list. It only claims (N, K) shapes that AITER has tuned rows for; all other shapes fall through to Triton unchanged.
AITER configs: ROCm/aiter#6060 and ROCm/aiter#7411.
## Claims
- 1.2-1.9x faster per GEMM than the Triton `dot_scaled` kernel on the MiniMax-M3.1-Flash TP4 MXFP8 shapes at decode/verify sizes (M = 32-512). The rotating-weight micro-benchmark is below.
- In a DSpark3 conc-32 decode profile, the MXFP8 linear kernels drop from 7.46 ms to 4.28 ms per step (261 launches in both).
- No accuracy change: GSM8K is within run-to-run noise.

- Fangzhou-Ai · comment · 2026-11-03T23:42:56Z · [source](https://github.com/vllm-project/vllm/pull/65479#issuecomment-6618364928)

Thanks for this, the per-GEMM numbers look good. One compatibility question with two open MiniMax-M3.1 PRs that feed this GEMM a pre-quantized activation: #65478 (fuses the MXFP8 quant into the post-attention norm and into swiglu) and #65508 (the NVFP4 sparse decode kernel emits the MXFP8 input for `o_proj`).

Both pass a `QuantizedActivation` (row-major `[M, K/32]` E8M0 scales, `kMxfp8Dynamic`) to the linear, and only when the layer's kernel is `RocmDotScaledMxfp8LinearKernel`. With `AiterMxfp8LinearKernel` selected first for these shapes, two things happen:

1. `apply_weights` always calls `mxfp8_e4m3_quantize(x)`, so it cannot take a `QuantizedActivation`.
2. The model-side gate (`_can_fuse_input_norm_mxfp8`) fails, so the fusions silently turn off for qkv, o_proj and the shared/dense gate_up/down in every layer. Each linear then goes back to a separate quant launch.

Could `AiterMxfp8LinearKernel` accept a `QuantizedActivation` the way `RocmDotScaledMxfp8LinearKernel` does? Roughly:
- `input_quant_key()` returning `kMxfp8Dynamic`, and a `supports_quantized_input(layer)` that returns True when the weight is 1 byte per element.
- In `apply_weights`, `qa = as_quantized_activation(x, self.input_quant_key())`. If `qa` is not None, use `qa.data` / `qa.scale` directly, and take the output dtype and shape from `qa.orig_dtype` / `qa.orig_shape`; otherwise quantize as today.

The scale layout needs no change: the row-major E8M0 scales those fusions write are what `gemm_a8w8_blockscale_bpreshuffle` reads here (viewed as `float8_e8m0fnu`). I have this as an untested sketch and can share it if useful. On our side I'll make the model-side gate accept either kernel once the aiter kernel declares it can take quantized input, so the two PRs don't depend on landing order.

#### 1. 🟠 Should fix: Engine startup fails with 'Failed to find a kernel' when --linear-backend=aiter and shape untuned: this PR registers a shape-gated kernel under 'aiter'
`vllm/model_executor/kernels/linear/__init__.py:364`

Adding `AiterMxfp8LinearKernel` to `_LINEAR_BACKEND_KERNEL_MAP['aiter']` makes `_resolve_backend_kernels` narrow the ROCm MXFP8 list to `[AiterMxfp8LinearKernel]` whenever `--linear-backend=aiter` (or `linear_backend_per_quant={'mxfp8': 'aiter'}`) is set. Because the filtered list is non-empty, the fall-back-to-automatic-selection path no longer runs. Any MXFP8 layer this kernel rejects then makes `init_mxfp8_linear_kernel` raise `ValueError('Failed to find a kernel...')` instead of using `RocmDotScaledMxfp8LinearKernel` or emulation. The kernel rejects a layer when its (N, K) is untuned, the default dtype is not bf16, `VLLM_ROCM_MINIMAX_M3_MONO=1` is set, or `VLLM_BATCH_INVARIANT` is set. The default `auto` backend is unaffected.

**Who is affected:** ROCm (gfx950) users serving MXFP8 models with `--linear-backend=aiter` or an `mxfp8: aiter` per-quant override where some layer shapes are untuned or another gate fails.

#### 2. 🟠 Should fix: Model load aborts with AITER exception instead of falling back: this PR's tuned probe catches only ImportError
`vllm/_aiter_ops.py:4432`

`is_mxfp8_bpreshuffle_gemm_tuned` catches only `ImportError`, so any other error from AITER's `get_mxscale_bpreshuffle_config` escapes `can_implement` and `init_mxfp8_linear_kernel` raises instead of falling through to `RocmDotScaledMxfp8LinearKernel`. Examples are a malformed or overridden tuned CSV (pandas/`KeyError`), an unknown arch, or an AITER with a different signature. On a supported host this is unlikely: `is_supported()` already requires a gfx95x GPU with AITER linear enabled, so `get_gfx`/`get_cu_num` succeed, and the default tuned CSV ships with AITER. The `RuntimeError` in the evidence only happens without a GPU. Catching `Exception` (or at least `(AssertionError, ImportError, KeyError, RuntimeError)`) and returning False would make the fallback robust; note the sibling `is_asm_fp4_gemm_tuned` has the same narrow catch.

**Who is affected:** ROCm gfx95x users with AITER linear enabled whose AITER install has a broken or overridden mxscale bpreshuffle tuned CSV, or a mismatched AITER version.

**Related past reviews:** [#46184](https://github.com/vllm-project/vllm/pull/46184) on `vllm/model_executor/layers/fused_moe/experts/flydsl_mxfp8_moe.py`

#### 3. 🟠 Should fix: Weight-cache daemon and IPC loader fail with UnsupportedQuantForIPCError on tuned shapes: this PR precedes RocmDotScaled without setting supports_pre_processed_weights=True
`vllm/model_executor/kernels/linear/mxfp8/aiter.py:20`

`AiterMxfp8LinearKernel` leaves `supports_pre_processed_weights` at the base default `False`, while the `RocmDotScaledMxfp8LinearKernel` it now precedes sets it to `True`. For ModelOpt MXFP8, the quant method's `supports_pre_processed_weights` defers to the kernel's flag. As a result `check_ipc_quant_support` raises `UnsupportedQuantForIPCError` at daemon and loader startup as soon as one layer has an AITER-tuned (N, K). That error is re-raised even with fallback enabled, so the weight cache stops working where it worked before. The kernel's `process_weights_after_loading` only replaces `weight`/`weight_scale`, which the daemon exports already preshuffled, so it can most likely just declare `supports_pre_processed_weights = True`.

**Who is affected:** Users of ModelOpt MXFP8 checkpoints with `--load-format ipc_cache` (weight cache daemon) on gfx950 with AITER linear enabled.

_Checked against the code by an independent pass._

#### 4. 🟠 Should fix: New default-first ROCm MXFP8 kernel has no selection-gating or output-parity tests
`vllm/model_executor/kernels/linear/mxfp8/aiter.py:1`

The PR adds `AiterMxfp8LinearKernel` and puts it first in the ROCm MXFP8 kernel list, but no test references it. The sibling `RocmDotScaledMxfp8LinearKernel` has dequant-reference parity tests in `tests/kernels/quantization/test_rocm_mxfp8_linear.py`. Neither the new kernel's selection gating nor its output parity is tested. Untested selection gating: tuned shapes pick AITER, untuned shapes fall through to `RocmDotScaledMxfp8LinearKernel`, and `VLLM_ROCM_MINIMAX_M3_MONO`, `VLLM_BATCH_INVARIANT`, non-bf16 and `bmm_batch_size` reject it. Untested output parity: `process_weights_after_loading` and `apply_weights` (shuffle layout, scale trim and E8M0 view) against a dequantized-BF16 reference. Add a CPU selection test with `is_mxfp8_bpreshuffle_gemm_tuned` monkeypatched and a gfx950 parity test.

**Who is affected:** ROCm gfx950 users serving MXFP8 checkpoints (e.g. MiniMax-M3.1) whose (N, K) shapes AITER has tuned; a regression in this path would not be caught by CI.
