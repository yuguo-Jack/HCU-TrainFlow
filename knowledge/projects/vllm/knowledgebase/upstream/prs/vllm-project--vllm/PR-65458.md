# [Perf] Bypass the dispatcher for all vLLM custom ops in eager mode

[Upstream PR](https://github.com/vllm-project/vllm/pull/65458) · state: open · merged: False

## Original PR description



## Overview

Make every vLLM custom op skip the PyTorch dispatcher when it runs eagerly, generalizing the FlashInfer-only bypass from #64417 into the default for all ops (attention, MoE, Mamba/GDN, LoRA, quantized GEMMs, RoPE, ViT attention, vLLM IR ops, ...).

## Claims

- Eager decode at batch 1 is 1.5–5.4% faster end to end on B300 (MoE FP8: −2.4 ms/step, ~50 µs/layer), with bit-identical greedy tokens. Compiled + CUDA graph runs are unchanged.
- `direct_register_custom_op` now returns an eager-bypass handle, also exposed as `vllm_ops.<name>`. All 183 `torch.ops.vllm.<name>(...)` call sites outside `vllm/compilation/` use it.
- vLLM IR ops (`rms_norm`, `fused_add_rms_norm`, activations) skip the torch op layer for eager calls even when `ir_enable_torch_wrap` is on. Before this change, uncompiled multimodal encoders (`compile_mm_encoder=False` by default) paid dispatcher cost on every norm.
- The eager check also treats `make_fx`, `FakeTensorMode` and `torch.fx.symbolic_trace` as tracing, not only Dynamo, so fusion-pass patterns still match the ops. This also fixes a latent gap in the #64417 helper.
- A new pre-commit hook rejects new `torch.ops.vllm.<name>(` calls and new `torch.library.custom_op` registrations outside `vllm/compilation/`. The last three `torch.library.custom_op` ops (`safeFusedQuantizeNv`, `modelopt_block_embedding_chunked`, `triton_mx_block_rearrange`) move to `direct_register_custom_op` with unchanged schemas.

## Validation

End to end, B300, `origin/main` vs this PR, back to back on the same GPU. Greedy decoding, 4 prompts × 64 tokens (VLM: 2 image prompts) compared token by token. Timing is the median of 5 runs of batch-1 decode of 128 tokens (`ignore_eos`):

| model | mode | main | this PR | Δ | tokens |
|---|---|--:|--:|--:|---|
| Qwen3-0.6B | eager | 1.312 s | 1.266 s | −3.5% | identical |
| Qwen3-30B-A3B-FP8 | eager | 5.665 s | 5.358 s | −5.4% | identical |
| Qwen2.5-VL-3B-Instruct | eager | 2.043 s | 2.013 s | −1.5% | identical |
| Qwen3-0.6B | compiled | 0.167 s | 0.166 s | −0.5% | identical* |
| Qwen3-30B-A3B-FP8 | compiled | 0.373 s | 0.377 s | +1.1% | identical |
| Qwen2.5-VL-3B-Instruct | compiled | 0.304 s | 0.303 s | −0.5% | identical |

\* In the first run, one of the four Qwen3-0.6B compiled prompts diverged at token 15 on main (cold compile cache). Two reruns each of main and this PR all matched this PR's output, so that divergence is run-to-run variance and unrelated to this change.

Per-call cost (CPU toy op, two tensor args): bare impl 0.75 µs, handle 1.13 µs, `torch.ops.vllm` 2.35 µs. The eager check costs ~150 ns.

Tests (B300):
- `tests/ir`: 45 passed
- `tests/compile/passes`: 514 passed, 275 skipped
- `tests/compile/{test_decorator,test_graph_partition,test_rotary_embedding_compile,test_wrapper}.py`, `tests/kernels/quantization/test_flashinfer_mxfp8_trtllm.py`, `tests/lora/test_punica_ops.py`: 4300 passed
- New `tests/utils_/test_torch_utils.py::test_custom_op_handle_stays_an_op_under_tracing` (CPU): the handle bypasses the dispatcher in eager and stays an op under Dynamo, `make_fx` (real/fake) and `symbolic_trace`. It fails on 3 of 4 tracers with a bare `is_compiling()` check.
- mypy and all pre-commit hooks pass on the changed files.

## Details

- `is_eager_dispatch(args, kwargs)` returns False when Dynamo is compiling, a torch dispatch mode is active (`make_fx`, fake tensors), or any argument has `__torch_function__` (fx Proxy). `is_compiling()` is checked first so Dynamo never traces the C calls.
- The handle is a plain function, so Dynamo inlines it and emits the same `torch.ops.vllm.<name>` node as before. Graphs, fusion passes, piecewise splitting and compile caches see the same ops. Pattern code in `vllm/compilation/` keeps using `torch.ops.vllm.<name>.default` directly.
- `vllm_ops` falls back to `torch.ops.vllm` for names not registered through `direct_register_custom_op`. Every in-tree `vllm_ops` name has a literal registration.
- Tradeoffs: eager calls no longer show up as `vllm::<name>` ranges in torch profiler traces, and monkeypatching `torch.ops.vllm.<name>` no longer intercepts in-tree callers. I updated the one test that did this (`tests/kernels/mhc`) to patch `vllm_ops`. Out-of-tree callers of `torch.ops.vllm.<name>` keep working on the dispatcher path.
- Not validated locally: ROCm (many `rocm_aiter_*` call sites are rewritten mechanically), XPU, CPU and multi-GPU runs. Relying on CI for those.
- No duplicate: searched open PRs for eager bypass, dispatcher overhead, `vllm_ops` and `torch.ops.vllm` eager. Follows #64417.
