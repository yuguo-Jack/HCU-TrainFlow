# [ROCm][DSv4.1] Allocate offloaded Engram tables at their exact size

[Upstream PR](https://github.com/vllm-project/vllm/pull/63009) · state: closed · merged: True

## Original PR description

On ROCm, allocate private CPU-offloaded Engram tables at their exact size instead of through `pin_memory`, which rounds every allocation up to the next power of two. This saves about 28% of the host memory the tables take, with no change in lookup speed.

The rounding comes from PyTorch's pinned host allocator, which rounds requests up to a power of two; `hipHostMalloc` itself allocates the exact size. CUDA goes through the same allocator code, so it is affected the same way; #59849 addresses that with 4 KiB-page registration. This PR keeps ROCm on huge pages, since that matches today's `pin_memory` speed on MI300X. If #59849 merges first, this becomes a one-line change on top of it.

The change sits after the DP shared-memory branch and does not touch config resolution, so the `dp_shared_memory` default and its fallback are unchanged. Setting `use_thp: true` in the recipes gives the same allocation today, but it also turns off DP table sharing, so it is only safe for TP-only deployments.

- ROCm only: private offloaded tables use the existing `use_thp` path (exact-size huge-page allocation registered with the GPU), with `pin_memory` as the fallback if registration fails, as before.
- Host memory for one TP4 rank-layer of DeepSeek-V4.1-Flash tables: 23.6 GiB instead of 33.0 GiB. At the MI300X/MI325X TP4 recipe shape that is about 75 GiB less per node.
- Lookup speed and serving speed are unchanged within noise. CUDA and the DP shared-memory path are unchanged.

Tested on MI300X, AITER v0.1.25. Allocation at the real per-rank sizes (resident anonymous memory, every run identical):

| Shape | Requested | `pin_memory` (main) | this PR |
|---|---|---|---|
| TP4 rank-layer | 23.605 GiB | 33.001 GiB | 23.605 GiB |
| TP2 rank-layer | 47.21 GiB | 66.0 GiB | 47.21 GiB |

Lookup kernel (`ParallelEngramEmbedding.lookup`, TP4-size table, interleaved in one process): huge-page registered vs `pin_memory` is -2.4% to +1.2% for 1 to 1024 tokens, within noise. ROCm's `pin_memory` is already huge-page backed (33.0 GiB of AnonHugePages for the 33 GiB allocation), so the access path is the same.

End to end on a single-GPU DeepSeek-V4.1 proxy (40 layers, 32 experts, dummy weights, two 23.6 GiB offloaded tables, default CUDA graphs), 3 interleaved runs, median [min-max]:

| | main | this PR |
|---|---|---|
| EngineCore host RSS (GiB) | 72.19 [72.19-72.39] | 53.40 [53.40-53.47] |
| decode bs1 (s/call) | 3.715 [3.712-4.306] | 3.701 [3.701-3.701] |
| decode bs64 (s/call) | 7.529 [7.503-7.572] | 7.467 [7.436-7.474] |
| prefill 8x2048 (s/call) | 1.343 [1.338-1.344] | 1.346 [1.346-1.352] |
| model load (s) | 16.00 [15.81-17.04] | 15.34 [11.70-52.58] |

One patched load took 52.6 s on this shared host; the other two were 11.7 and 15.3 s.

Tests: `tests/kernels/test_engram.py` passes (49 passed, 56 skipped). `test_engram_use_thp_lookup_and_fallback` now also runs on ROCm and covers both the default and `use_thp` paths, with and without a registration failure; it passes 10/10 in a loop.
