# [ROCm][Bugfix] Fix AITER shared-expert fusion routing for gate-less MoE (DeepSeek-V2-Lite)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64737) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fix silently wrong MoE routing on ROCm when `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1` is used with softmax-routed models whose fused shared experts have no gate, such as DeepSeek-V2-Lite (any model built on `DeepseekV2MoE` with softmax routing and one expert group). `AiterSharedRoutedFusedMoERouter` (added in #39280 for Qwen3-Next) treated the last router-logit columns as a shared-expert gate for every such model.

## Claims

- Fixes wrong outputs with AITER shared-expert fusion on gate-less models, matching fusion off:
  - DeepSeek-V2-Lite-Chat (on `main`) GSM8K (strict) goes from 0.095 to 0.661 (fusion off 0.656).
  - Mistral-Large-4-1T-A52B, with a local model implementation that builds its MoE layers with `main`'s `DeepseekV2MoE` (see Validation; not the `MistralMoE` of #64534): GSM8K (strict) goes from 0.718 to 0.959 at 5-shot (fusion off 0.957) and from 0.770 to 0.965 at 20-shot (fusion off 0.962), mean of 3 runs each.
- Qwen3-Next (gated shared expert) routing is unchanged: Qwen3-Next-80B-A3B-Instruct with fusion on scores the same before and after this PR (GSM8K flexible-extract 0.952 vs 0.953, fusion off 0.953, 3 runs each), and the gated unit test passes with the same assertions on `main`.
- With the fix, shared-expert fusion becomes usable for such models. On that Mistral Large 4 implementation, median TPOT is 21% lower than fusion off at concurrency 1, 7.5% lower at 8 and 5% lower at 32 (MI325X, TP8). No throughput regression on DeepSeek-V2-Lite-Chat.

## Validation

All runs on MI325X (gfx942), AITER 0.1.26, `VLLM_ROCM_USE_AITER=1`, on a local ROCm build (vLLM 0.32.1rc1.dev361, 83c078d955). "Before" and "after" differ only in the three changed Python files, taken from before and after this change.

Mistral Large 4 is not in `main` yet, so we used a local Mistral Large 4 implementation that is not in `main` or in another PR. It builds every MoE layer (softmax top-4 over 128 routed experts plus one shared expert, no shared-expert gate, no score bias) with `main`'s `DeepseekV2MoE`, the class DeepSeek-V2-Lite uses, which passes `n_shared_experts` and `fuse_shared_experts` to `FusedMoEFactory`. With the flag set, it fuses the shared expert and takes this router. Mistral's working branch #64534 (at `bd4fa26`) instead passes the shared expert to `MistralMoE` as a separate MLP, so `num_fused_shared_experts` is 0, the factory picks `FusedTopKRouter`, and the flag has no effect: as published, #64534 neither hits this bug nor gets the TPOT gain from this PR alone. Fusing its shared expert would be a separate change, and it would need this fix.

## Details

**Root cause.** `create_fused_moe_router` selects `AiterSharedRoutedFusedMoERouter` when `num_fused_shared_experts > 0`, scoring is softmax, there is no `e_score_correction_bias` or custom routing function, grouping is degenerate, and `VLLM_ROCM_USE_AITER=1`, AITER MoE and `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1` are set. The router assumes every such model has a sigmoid shared-expert gate whose logits are appended as the last `num_fused_shared_experts` columns of `router_logits` (true for Qwen3-Next, where `MoERunner` concatenates `gate` and `shared_expert_gate`). For gate-less models, `router_logits` only has routed experts, so the last routed experts are treated as gate logits: they can never be selected, and their sigmoid becomes the shared-expert weight. Shapes stay valid, so nothing crashes.

Affected:
- Mistral Large 4 (128 experts, top-4, 1 shared) when its MoE layers fuse the shared expert, as in the local implementation measured above. Not #64534 as published, which keeps the shared expert unfused.
- DeepSeek-V2-Lite / -Lite-Chat and DeepSeek-Coder-V2-Lite-Instruct (64 experts, top-6, 2 shared, 1 group), measured above.
- The BF16 Mistral-Large-3 checkpoint has the same gate-less softmax routing (128 experts, 1 shared) and takes the same path by code inspection; not measured here.

Not affected: gated shared experts (Qwen3-Next, Qwen3.5), sigmoid routing with a score bias (DeepSeek-V3/R1, Kimi-K2, GLM), and real expert grouping (DeepSeek-V2, V2.5).

**Fix.** `FusedMoEFactory` passes `has_shared_expert_gate=shared_expert_gate is not None` through `create_fused_moe_router` (default `False`). Without a gate, the router runs the softmax top-k over all routed logits directly into the routed columns of `aiter_topK_meta_data`, picked by `dispatch_topk_softmax_func` like the fusion-off `FusedTopKRouter` (`topk_gating` on gfx942/gfx950 up to 4096 tokens, legacy `topk_softmax` otherwise). Both kernels honor the row stride, and `init_aiter_topK_meta_data` pre-fills the shared slots (ids after the routed experts, weight 1.0; per-rank sentinel ids with EP). It stays one kernel launch, plus one `fill_` only when `shared_expert_weight != 1.0`. The gated path is untouched.

**Duplicate check.** No open or merged PR or issue mentions `has_shared_expert_gate` or fixes this; the related hits (#42964, #44651, #53248, #61457) address imports and quantization compatibility, not the routing. #60217 (MoE balanced routing) only touches `base_router.py`.
