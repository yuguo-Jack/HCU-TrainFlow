# [Bugfix] Keep the --tokenizer chat template for multimodal models

[Upstream PR](https://github.com/vllm-project/vllm/pull/61447) · state: open · merged: False

## Original PR description



## Overview

Follow-up to #60825. `get_processor` now renames the processor's tokenizer to the requested repo. The renderer passes its own tokenizer into the multimodal processor, so for a multimodal model with `--tokenizer` different from `--model`, the renderer's tokenizer gets the model's name and chat templates are resolved from the model repo instead of the tokenizer repo.

## Claims

- Multimodal model with `--tokenizer` != `--model`: chat prompts use the tokenizer repo's template again, as before #60825.
- Default case (`--tokenizer` = `--model`): unchanged. The renderer's tokenizer still reports the Hub ID and uses the same template.

## Validation

Repro: `LLM(model="Qwen/Qwen3-VL-2B-Instruct", tokenizer="Qwen/Qwen3-VL-2B-Thinking")`, then `llm.chat([{"role": "user", "content": "What is 2 + 3?"}])`. I compare `output.prompt` with each repo's own `AutoTokenizer.apply_chat_template` result. The two templates differ: the Thinking one ends the generation prompt with `<think>\n`.

1xL4, nightly images, this diff overlaid on `nightly-5555a2d8` (`processor.py` is the same as current main):

## Details

The renamed tokenizer is the renderer's own object, so `resolve_chat_template` then loads the chat template from the model repo's processor. It also depends on ordering: with the same tokenizer object, `resolve_chat_template` returns the Thinking template before `get_processor("Qwen/Qwen3-VL-2B-Instruct", tokenizer=tok)` runs and the Instruct template after it.

The fix only renames a tokenizer whose `name_or_path` is the snapshot `get_processor` just loaded from. A tokenizer from another repo keeps its name. In the default case the renderer's tokenizer still carries that same snapshot path, so it is renamed to the Hub ID as before.

The snapshot path in the table: `HfRenderer` makes a `copy.copy` of the tokenizer, and the cached tokenizer is rebuilt from the object loaded before `get_tokenizer` renamed it. Text-only models already report the snapshot path on main for this reason. It only changes the reported name, so I left it out of this PR.

Not a duplicate: no open or closed PR or issue since #60825 mentions this. Searched for `name_or_path`, `get_processor tokenizer`, chat template with `--tokenizer`, and `60825`.
