# [Perf][Spec Decode] Split-vocabulary Triton argmax for the DSpark greedy draft

[Upstream PR](https://github.com/vllm-project/vllm/pull/57770) · state: closed · merged: True

## Original PR description

## Purpose

Replace the DSpark greedy draft's full-vocabulary `torch.argmax` with a two-stage Triton split-vocabulary reduction. The reduction preserves int64 outputs, first-index ties, and NaN semantics, with a Torch fallback for unsupported inputs. With `num_speculative_tokens=5`, each decode step runs five dependency-chained greedy selections (`_sample_sequential`'s `for i in range(n_spec)` loop), so the per-call saving compounds five-fold per step.

Scope is limited to `draft_sample_method="greedy"`: `self.draft_logits` is allocated only for `draft_sample_method="probabilistic"`, so the `draft_logits is None` branch is exactly the greedy path. The probabilistic path (`gumbel_sample`) already reduces over vocabulary chunks and is unchanged; the draft backbone, non-greedy sampling, and verification are untouched. The generic `DraftModelSpeculator.sample_draft` argmax is left alone — DSpark overrides `_sample_logits` and never reaches it.

Parallelism: the drafter's logits are the all-gathered, padding-narrowed output of `LogitsProcessor` (`ParallelLMHead` + all-gather when `tp_size > 1`), so every TP rank reduces the same full-vocabulary tensor. The comparator is a total order, so the result does not depend on the reduction order or on the split count, and every rank selects the same draft id. The kernel issues no collectives and no host synchronization, so it does not perturb DP/EP lockstep (DP padding is handled in `_run_model`, before sampling) and it is unaffected by sequence parallelism, which is internal to the backbone forward.

CUDA Graph and JIT: the kernels allocate only from the capturing stream's pool and never synchronize with the host, so they are captured with the rest of the DSpark draft step. They specialize on the vocabulary size, row stride, and dtype, which are fixed per deployment; the row count is only a grid dimension. They are therefore compiled once, in the profiling dummy run before capture, and do not JIT during serving.

- [#50843](https://github.com/vllm-project/vllm/pull/50843) bounds tile-local argmax indices in existing sampler kernels.


## Test Result

GB200 ×4, DeepSeek-V4.1-Flash, DEP4; NCCL DMA-BUF disabled. Baseline and candidate differ only in the greedy draft argmax. Serving config: DSpark `num_speculative_tokens=5`, `draft_sample_method=greedy`, synthetic acceptance 6.0, adaptive verification off; Mega MoE (`deep_gemm_mega_moe`); FlashMLA DSV4.1 attention with MXFP4 sparse-logits indexer; fp8 KV cache; max 128 sequences, 16384 max batched tokens, 131072 max model length; Engram embeddings shared across DP; prefix caching disabled; GPU memory utilization 0.9; seed 42.

8192 input / 1024 forced output; `3×concurrency` requests per run; identical prompt IDs and request seeds, temperature=1/top_p=0.95. Same-node baseline then optimized, three measurements per concurrency, each preceded by full-workload warmup.

In situ the logits are still in L2, since the Markov-bias add has just written them. With a hot L2 (CUDA Graph, CUDA events), Torch argmax is ~26 μs across M, while the split argmax is 3.3 / 4.0 / 6.3 / 14.9 μs at M=1 / 8 / 32 / 128. The resulting 5 × 22.6 ≈ 113 μs per-step saving at M=1 matches the ~109 μs ITL P50 drop at concurrency 1.
