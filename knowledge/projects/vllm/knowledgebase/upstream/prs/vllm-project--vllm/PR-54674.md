# [Perf][DSpark] Stack DeepSeek V4 context WKV projections

[Upstream PR](https://github.com/vllm-project/vllm/pull/54674) · state: closed · merged: True

## Original PR description

## Summary

DeepSeek V4 DSpark currently derives each draft layer's context KV by running
that layer's fused `wq_a|wkv` projection and discarding the Q portion. This
launches one projection per draft layer and computes output that the context-KV
path does not consume.

This PR:

- stacks the draft layers' WKV projections into one
  `MergedColumnParallelLinear` and runs it once for the shared target hidden
  states;
- duplicates each checkpoint WKV weight and quantization scale into the
  corresponding merged-linear shard during loading;
- preserves the existing per-layer KV normalization, RoPE/quantization, cache
  insertion, profiling behavior, and in-place weight refresh semantics; and
- adds focused tests for checkpoint shard construction and the single stacked
  projection behavior.

## Relationship to existing work

This is not duplicating an existing open PR. I searched open PRs for
`DeepSeek V4 DSpark WKV`, `DSpark stacked projection`, `context_wkv_proj`, and
`stacked WKV` before submitting.

- #53577 also changes `deepseek_v4/nvidia/dspark.py`, but adds pipeline-parallel
  prefill/context-KV materialization and padded graph-batch safety. It retains
  the per-layer fused WKV projection; this PR only optimizes that projection.
  The changes are functionally independent, although a textual rebase may be
  needed if #53577 lands first.
- #51620 and #51684 fix quantized context-KV projection correctness in other
  DFlash-family model implementations. They do not change the DeepSeek V4
  DSpark path or add this merged projection.

## Performance

### End-to-end engine benchmark

Measured on two independent 2x NVIDIA H20-3e GPU pairs with
DeepSeek-V4-Flash-0731, TP=2, expert parallelism enabled, FP8 KV cache, eager
execution, and 7-token greedy DSpark speculation. Each request used 256 input
tokens and generated exactly 128 output tokens. Prefix caching and
detokenization were disabled.

The benchmark used AB/BA ordering. Each job ran both implementations with two
warmups and 12 measured `LLM.generate()` calls per batch size, giving 24
samples per implementation and batch size. The speedup below is the geometric
mean of the two within-job mean-throughput ratios; the confidence interval is a
20,000-sample bootstrap stratified by job/GPU pair.

| Batch | Baseline output tok/s | Stacked output tok/s | Paired speedup | 95% CI | Median speedup |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 36.07 | 39.01 | 1.082x | 0.883x-1.334x | 1.037x |
| 8 | 121.48 | 126.67 | **1.043x** | **1.002x-1.085x** | 1.035x |
| 16 | 233.62 | 237.97 | 1.019x | 0.979x-1.060x | 1.031x |

Batch 8 reproduced on both GPU pairs (+5.0% and +3.6%). Batch 1 had substantial
request-latency variance, and batch 16 differed across GPU pairs (+5.6% and
-1.7%), so their confidence intervals cross parity. The conservative result is
a roughly 3%-4% median end-to-end throughput improvement, with statistically
positive paired mean throughput at batch 8 in this run.

The periodic speculative-decoding metric reported mean acceptance lengths of
3.371 for baseline and 3.495 for the stacked implementation. Exact output token
digests also varied across repeated greedy requests within the same arm, so
this runtime was not bitwise deterministic. The end-to-end numbers therefore
include the observed speculative trajectory and should not be interpreted as
an isolated GEMM saving; the projection probe below provides that isolation.

This is an offline engine-level benchmark: the timed region includes prefill,
scheduling, DSpark draft/verify, KV-cache operations, and decode inside the
synchronous `LLM.generate()` call. It excludes model loading, HTTP transport,
tokenization, and detokenization.

### Stacked projection probe

A probe attached to the fully loaded TP2 engine validated that all three merged
weight and scale shards exactly matched the original draft-layer WKV parameters
on both ranks. The old and stacked projection outputs had `max_abs_diff=0.0`
for every measured shape.

| Context tokens | Rank 0 speedup | Rank 1 speedup |
| ---: | ---: | ---: |
| 1 | 7.42x | 6.62x |
| 8 | 7.21x | 7.12x |
| 32 | 6.55x | 7.56x |
| 128 | 6.85x | 7.63x |
| 512 | 38.03x | 36.99x |
| 2048 | 2.94x | 2.93x |

Thanks for the review! I ran the longer-output SPEED-Bench tests with both **2K and 4K output lengths**.

### Setup

- **Model and hardware:** DeepSeek-V4-Flash-0731 on 2× H20, TP=2 with EP enabled, FP8 KV cache, eager execution, and prefix caching disabled.
- **Speculative decoding:** DSpark uses 7 speculative tokens with greedy draft sampling.
- **Request parameters:** `temperature=0`, `seed=42`, and `ignore_eos` to enforce the requested output lengths.
- **Dataset:** A fixed, balanced subset of SPEED-Bench `throughput_2k` prompts: 72 prompts at concurrency 8 and 12 at concurrency 1. This is a subset, not the full SPEED-Bench suite.
- **Measurement protocol:** Each configuration was run as three baseline/PR pairs on each of two fixed GPU pairs, alternating execution order, for six paired measurements per configuration. Warmup requests were excluded.

### Serving results

Metric pairs below are shown as **baseline → PR**.

| Output length | Concurrency | Output tok/s | TPOT (ms) | Acceptance length | Paired speedup |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 2,048 | 1 | 24.23 → 24.40 | 41.024 → 40.742 | 3.3174 → 3.3330 | 1.0068× |
| 2,048 | 8 | 171.67 → 171.49 | 43.790 → 43.620 | 3.3547 → 3.3802 | 0.9989× |
| 4,096 | 1 | 26.84 → 26.02 | 37.198 → 38.435 | 3.6667 → 3.5519 | 0.9687× |
| 4,096 | 8 | 186.36 → 186.95 | 40.206 → 40.147 | 3.5982 → 3.5967 | 1.0031× |

Throughput and TPOT are means across the six runs. Acceptance length is pooled as `1 + total accepted draft tokens / total draft steps`. Speedup is the geometric mean of the within-pair throughput ratios.

**These results do not establish a consistent end-to-end speedup.** The node-stratified paired bootstrap 95% intervals are:

| Output length | Concurrency | Paired throughput speedup: 95% interval |
| ---: | ---: | ---: |
| 2,048 | 1 | 0.9761–1.0425 |
| 2,048 | 8 | 0.9869–1.0113 |
| 4,096 | 1 | 0.9191–1.0211 |
| 4,096 | 8 | 0.9902–1.0136 |

All intervals include 1.0. These intervals are conditional on the two tested GPU pairs.

### Acceptance variability and correctness diagnostics

To investigate acceptance variability and correctness separately:

- **Same-process A/A diagnostics:** Even the unchanged baseline produced different output sequences on 3 of 6 repeated prompts on each GPU pair, despite greedy sampling and a fixed seed. Its pooled acceptance length changed by **+8.16%** on one pair and **−7.32%** on the other. This demonstrates repeatability variability in the baseline, although it does not establish the cause of the baseline/PR differences. These diagnostics used raw prompt tokens rather than the chat-templated serving inputs, so their absolute acceptance lengths are not directly comparable to the table.

- **Fixed-input projection correctness:** I captured real context-projection inputs from baseline inference and replayed the original and stacked projections on identical tensors. Across all **30 captured snapshots per rank on both TP ranks**, the projection outputs were **bitwise identical**, with a maximum absolute difference of **0**.

- **Isolated projection performance:** The isolated projection replay showed approximately **2.86–2.99× lower GPU execution time**, using CUPTI with CUDA Graphs and cold L2. This measures the projection only—not the full draft step or serving throughput. The replay harness retained CUPTI initialization until worker exit to avoid a profiler/NCCL-watchdog crash; per-measurement activity flushing and disabling were retained.

The fixed-input checks support the correctness of the changed projection on the captured cases, and the projection-level benefit is clear. However, I would not claim full draft correctness from acceptance lengths alone, or an end-to-end performance gain from these serving results.
