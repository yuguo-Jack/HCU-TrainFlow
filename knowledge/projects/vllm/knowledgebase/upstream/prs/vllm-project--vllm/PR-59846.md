# [Perf][DSv4.1] SM120: decode DeepSeek-V4.1's own KV records with FlashInfer's DSv4.1 sparse MLA

[Upstream PR](https://github.com/vllm-project/vllm/pull/59846) · state: open · merged: False

## Original PR description



## Overview

On SM120/SM121, DeepSeek-V4.1 writes the V4 KV record and decodes it with FlashInfer's V4 sparse MLA kernels, and `--kv-cache-dtype nvfp4_ds_mla` is rejected. FlashInfer's SM120 sparse MLA also decodes V4.1's own records (flashinfer-ai/flashinfer#5197). This PR writes the V4.1 record on SM120 and lets the KV cache option select the matching FlashInfer kernel. It is the base for further SM120 DSv4.1 work.

**Depends on FlashInfer ≥ 0.7.1:** the `fp8_dsv41` / `fp8_dsv41_fp4_ca` formats are in 0.7.1rc2 but not in the pinned 0.7.0.post1, so this needs the FlashInfer pin bump before it merges.

## Claims

- `fp8_ds_mla` on SM120 writes the 528 B V4.1 record (all 512 dims MXFP8) instead of the 584 B V4 record, and decodes it with FlashInfer's `fp8_dsv41` kernels: +8.7% KV tokens at TP4.
- `nvfp4_ds_mla` works on SM120 (previously rejected): MXFP8 sliding window plus an NVFP4 compressed cache, decoded with `fp8_dsv41_fp4_ca`: +31% KV tokens over `fp8_ds_mla`.
- GSM8K accuracy and fixed 8K/1K serving throughput are unchanged.

## Details

- **Record:** `_use_v41_mxfp8_kv_record()` now also returns true on the SM120 family, so the SWA and compressed caches, the indexer page alignment and DSpark all use the V4.1 record there, as on SM100. Its writers (the fused qnorm/RoPE/KV insert and the compressor insert) already handle it on every arch.
- **Kernel selection:** the SM120 layer passes `kv_cache_format` per call from the caches it reads: `fp8_dsv41_fp4_ca` when an `nvfp4_ds_mla` call includes the compressed cache, `fp8_dsv41` otherwise (FlashInfer has no `fp8_dsv41_fp4_ca` kernel without the compressed cache, which the uncompressed layers hit), and `fp8` for the V4 record.
- **Backend:** `DeepseekV4FlashInferMLASparseBackend` accepts `nvfp4_ds_mla` on SM120 only; the SM100 TRTLLM-gen kernels behind the same backend cannot read the NVFP4 compressed cache.
- **No version gate:** the KV cache option alone selects the kernel; older FlashInfer builds without the V4.1 formats are not supported on this path.
- **Related:** #57523 makes the same record switch for gfx950 (a small textual conflict either way). #57292, #56509 and #57028 change SM120 page geometry and are orthogonal. #59342 adds `nvfp4_ds_mla` to the V3.2 `FLASHINFER_MLA_SPARSE` backend on SM10x, a different backend and model.
- **Not a duplicate:** searched open and merged PRs for `fp8_dsv41`, `fp8_dsv41_fp4_ca`, `nvfp4_ds_mla SM120`, `DSv4.1 SM120`, `V4.1 KV record`, `mxfp8 kv record` and FlashInfer DSv4.1 sparse MLA; none switches SM120 to the V4.1 records or wires FlashInfer's V4.1 formats.

- lucifer1004 · comment · 2026-10-17T02:04:21Z · [source](https://github.com/vllm-project/vllm/pull/59846#issuecomment-6228279459)

Rebased onto main (783380af39) and switched to the V4.1 record layout of #61371.

#61371 moved the V4.1 KV cache to FlashMLA's interleaved records: each token's 512 data bytes are followed by its own 16 scale bytes, and the NVFP4 extra cache uses 288 B records. FlashInfer's SM120 `fp8_dsv41` / `fp8_dsv41_fp4_ca` formats read the per-page footer layout. The record size is the same 528 B, so a plain rebase would decode wrong output on SM120 without raising any error.

The new last commit:
- passes FlashInfer's inline-scale formats `fp8_dsv41_inline` / `fp8_dsv41_inline_fp4_ca`, added in flashinfer-ai/flashinfer#6616;
- turns slot ids into whole-cache row indices across the packed blocks (`block * span + slot`, decode and prefill, main and extra cache);
- fails at startup with a clear error when the installed FlashInfer lacks these formats.

DeepSeek-V4.1-Flash chat GSM8K on SM120 TP4 (RTX PRO 6000) with flashinfer-ai/flashinfer#6616:
- 0.946 with the FP8 KV cache, against 0.945 before #61371;
- 0.948 with `nvfp4_ds_mla`, against 0.947.

**This can't merge yet:** main pins `flashinfer-python==0.7.2`, which has no inline formats. It needs a FlashInfer release containing #6616 and the matching pin bump.

Backport datapoint that may be useful for the pin discussion — and one detail that matters for anyone trying to run this PR before the FlashInfer bump lands.

**Environment:** 8× RTX PRO 6000 Max-Q 97.9 GB (SM120, **no NVLink**), TP8, `vllm 0.31.1rc1.dev253+g7d0b4e57a`, `flashinfer-python 0.7.2.post1`, DeepSeek-V4.1-Flash-1017 (NVFP4 MoE), DSpark k=3 (probabilistic/block), `--kv-cache-dtype fp8`.

**Result: both arms fail at engine init in ~75 s on dev253.**

Applying the PR head to dev253: `nvidia/flashinfer_sparse.py` and `utils/flashinfer.py` apply cleanly (offsets −8/−9, one hunk with fuzz 1); `deepseek_v41/attention.py` has one failing hunk that is comment-context only — the functional change (`_use_v41_mxfp8_kv_record()` returning True for SM120) aligns fine by hand.

Both `fp8` and `nvfp4_ds_mla` then die with the same first cause:

```
vllm/models/deepseek_v41/nvidia/flashinfer_sparse.py:672
RuntimeError: DeepSeek-V4.1 on SM120 reads its inline KV records through
FlashInfer's 'fp8_dsv41_inline' cache formats; the installed FlashInfer does not provide them.
```

i.e. `has_flashinfer_sparse_mla_dsv41_inline()` is False. Probe detail on the stock 0.7.2.post1 wheel:

```
inspect.signature(trtllm_batch_decode_sparse_mla_dsv4).parameters['kv_cache_format'].annotation
  -> Literal['fp8', 'nvfp4', 'fp8_dsv41', 'fp8_dsv41_fp4_ca']   # no *_inline variant
```

This matches @xzwgit's pre-#6616 note: the wheel only has the footer-scale formats.

**The part that may be worth flagging in the PR description / review:** on this base it is all-or-nothing, not "nvfp4 only". The `fp8` arm never asks for `nvfp4_ds_mla`, but once `_use_v41_mxfp8_kv_record()` returns True on SM120, `kv_mxfp8` becomes True, which trips the same inline-format probe. So a backport onto an older vLLM gives no partial win to measure — it refuses to start either way.

**Kernel side is already there**, which supports this being purely a pin issue:

```
flashinfer.mla._sparse_mla_sm120._DECODE_DSV4_DISPATCH contains
  (64, 512) (64, 1024) (64, 2048)  -> True on 0.7.2.post1
```

So the SM120 DSv4 decode specializations exist in the published wheel; only the inline-scale format enum is missing (merged in flashinfer#6616 on 2026-10-18, three days after 0.7.2 shipped on 2026-10-15).

Nothing to change on our side — the blocker is exactly the stated FlashInfer dependency. We have a ready harness (8-sample decode medians + 20-prompt exact-match quality gate + corruption probe) and will re-run both arms the day a wheel containing #6616 is published, then report back here.
