# Diagnose NIXL PD handshake loopback (side-channel defaulting to localhost)

[Upstream PR](https://github.com/vllm-project/vllm/pull/59583) · state: open · merged: False

## Original PR description

## Problem

Setting up NIXL-based P/D disaggregation across nodes fails opaquely when the **producer** does not set `VLLM_NIXL_SIDE_CHANNEL_HOST` (its default is `localhost`):

- the producer advertises `localhost:<port>` as its handshake side-channel address,
- the consumer's `_nixl_handshake` connects to that address — **on the consumer's own host** — and reaches the consumer's own ZMQ listener,
- the only visible symptom is:

```
RuntimeError: Remote NIXL agent engine ID mismatch. Expected <producer engine id>, received <consumer's own engine id>
```

which reads like an engine-ID/plumbing bug and sends you digging in entirely the wrong place. (The request may even still succeed via the consumer's recompute fallback, so nothing else points at the handshake.)

## Change

One targeted branch at the mismatch site: when the received engine ID equals **our own** engine ID, the handshake provably looped back — raise a diagnostic that names the actual cause and fix:

```
Remote NIXL agent engine ID mismatch: the handshake reached this instance itself
(expected <producer>, received our own engine ID <self>). The remote instance most
likely advertised an unreachable NIXL side-channel address (the default
VLLM_NIXL_SIDE_CHANNEL_HOST is localhost). Set VLLM_NIXL_SIDE_CHANNEL_HOST on the
remote instance to an address reachable from here.
```

## Verification (two-node DeepSeek-V4.1-Flash P/D, TP8 + TP8, NixlConnector)

1. **Repro** — producer started *without* `VLLM_NIXL_SIDE_CHANNEL_HOST`, request sent through `vllm-router`:
   - before this patch: `Remote NIXL agent engine ID mismatch. Expected f4c0…, received 1a2b…` (both are random per-instance UUIDs; no hint of the real cause);
   - after this patch: the new diagnostic fires in the same failing handshake, naming the environment variable.
2. **Healthy path** — producer restarted *with* `VLLM_NIXL_SIDE_CHANNEL_HOST=<its fabric IP>`: zero engine-ID mismatches, `NIXL compatibility check passed` on every consumer worker, KV transfer proceeds normally (`Transfer plan: local_tp=8, remote_tp=8`). No behavior change outside the loopback case.

This does not change any control flow — only the error message for a case that is currently undiagnosable from the log output alone.
