# [CI][Test] Derive the expected FP8 block scale dtype from the DeepGEMM oracle

[Upstream PR](https://github.com/vllm-project/vllm/pull/62864) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`test_compressed_tensors_fp8_block_enabled[auto]` and `test_modelopt_fp8_pb_wo_checkpoint_setup` hardcode `torch.float32` for the FP8 block scale dtype. On Blackwell-class GPUs DeepGEMM lays the block scales out as UE8M0 exponents packed four-per-`int32`, so both fail there even though the quantization path is correct. The expected layout is device-dependent; mirror the same architecture split rather than hardcoding the Hopper answer.

## Claims

- Both block-FP8 tests pass on Blackwell, and the expectation now tracks the architecture split instead of one fixed value.
- **No behaviour change on Hopper** — `DeepGemmQuantScaleFMT.from_oracle()` returns `FLOAT32_CEIL_UE8M0` there, so the expression evaluates to `torch.float32`, identical to the literal it replaces. Checked directly on H200, not inferred.
- Only the two block-quantized sites change; the other `weight_scale.dtype` assertions in these files are untouched.
- Test-only change.

## Validation

On H200 the oracle value and the resulting expectation were printed, so the equivalence is measured rather than assumed:

```
capability = 90 ; is_device_capability_family(100) = False ; is_device_capability_family(120) = False
from_oracle()        = DeepGemmQuantScaleFMT.FLOAT32_CEIL_UE8M0
expected_scale_dtype = torch.float32
```

## Details

**Root cause.**

1. Block-wise FP8 keeps one scale per 128x128 block. The layout the kernel requires is device-dependent: on Blackwell-class devices DeepGEMM takes UE8M0 exponents packed four-per-`int32`; on Hopper it takes `float32` values rounded up to powers of two.
2. The tests assert a literal `torch.float32`, which encodes the Hopper answer as if it were universal.

**Fix.** The layout is chosen inside `transform_sf_into_required_layout`, which vLLM imports from DeepGEMM — nothing on the vLLM side decides it. `DeepGemmQuantScaleFMT` encodes the same architecture split and is already used for that purpose elsewhere in the quantization stack, so the test mirrors it instead of hardcoding one side. This is deliberately a mirror, not a lookup of the product's own decision: the authoritative rule lives in the dependency.

The alternative is to drop the dtype assertion altogether, on the grounds that the scale layout is DeepGEMM's output contract rather than vLLM's behaviour. That would reduce coverage, so it is offered here as a maintainer's call rather than taken unilaterally.

**Limitations.** Two cases are not covered:

- With `VLLM_USE_DEEP_GEMM_E8M0=0` the oracle resolves to `FLOAT32`, so the expectation follows it and the test would pass in a configuration where the Blackwell path does not accept float32 scales. The default is on, so CI is unaffected.
- The assertion is not bound to the specific kernel that was selected. If a non-DeepGEMM `Fp8BlockScaledMMLinearKernel` subclass is chosen on a Blackwell-class device, it may legitimately keep float32 scales while this expects `int32`. Not observed on the two devices tested; happy to add an `isinstance` guard if preferred.

**Why CI did not catch this.** `.buildkite/test_areas/quantization.yaml` runs `tests/quantization/` on `h200_35gb` (plus ROCm mirrors); on B200 only `test_blackwell_moe.py` runs. No Blackwell runner collects these two files, and on Hopper the literal happens to be correct. The validation above was therefore performed outside CI.

Not a duplicate: searched for `DeepGemmQuantScaleFMT`, and for `weight_scale` together with `dtype`/`int32`; nothing proposes this.
