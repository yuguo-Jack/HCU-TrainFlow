# [ModelOpt] Unify MoE methods onto QuantSpec + ModelOptMoEMethod

[Upstream PR](https://github.com/vllm-project/vllm/pull/55997) · state: open · merged: False

## Original PR description

## Purpose

Unify ModelOpt MoE the same way #49381 unified linear methods.

One factory (`build_moe_method`) and one method class (`ModelOptMoEMethod`).
`resolve()` still builds the QuantSpec. MoE looks up a weight-key scheme in
`MOE_SCHEME_FOR` (not linear `SCHEME_FOR`).

Folds `ModelOptFp8MoEMethod`, `ModelOptNvFp4FusedMoE`, and
`ModelOptMxFp8FusedMoE` into `ModelOptMoEMethod`. Config classes stay split.
Deepseek V4 NVFP4 experts go through the same factory.

Mixed block-FP8 MoE (`FP8_PB_WO` / `FP8_BLOCK_SCALES`) continues to use
`Fp8MoEMethod`.

Rebased onto `main` at `df028dffa`. The unified method preserves routing-sink
forwarding, pre-processed NVFP4 weights, per-token NVFP4 activation overrides,
online NVFP4 weight dequantization, and valid dummy scales. DeepSeek V4.1 and
MuseSpark callers now use the unified method; MuseSpark retains its separate
w1/w3 scale handling.

Related: #55339

## Before this can merge

**1. GPU and accuracy results.** The PR replaces the FP8, NVFP4, W4A16 and MXFP8 MoE serving classes, but the parity table is all "pending". The only run is on a macOS CPU build, and the NVFP4 numerical cases in `test_online.py` are skipped there. Could you fill in the weight/kernel hash, logit delta and GSM8K for the four formats? I'd also like to see:
- a mixed-precision checkpoint with block-FP8 experts (the dispatch was rewritten)
- DeepSeek V4 and V4.1 NVFP4 experts (the callers changed)
- MuseSpark NVFP4, which isn't in the table but whose subclass changed
- at least one real GPU run each for per-token NVFP4 and pre-processed weights, which are only mocked right now

**2. Homogeneous dispatch for block-FP8 algos.** `get_quant_method` on the base config now calls `build_moe_method(self, self.quant_method, ...)`. For a `ModelOptFp8Config` with `quant_method` of `FP8_PB_WO` or `FP8_PER_CHANNEL_PER_TOKEN`, that hits the `algo in LINEAR_ALGOS` branch and raises `NotImplementedError`. `test_build_moe_method_rejects_linear_only_fp8` locks that in. Before, this config always got `ModelOptFp8MoEMethod`, and the mixed-precision path still sends block-FP8 MoE to `Fp8MoEMethod`, so the two paths now disagree. It's possible the old behaviour was silently wrong for block-scaled weights and an explicit error is an improvement. If so, a sentence in the description saying that would help. If anyone served such a checkpoint this way, it should route to `Fp8MoEMethod` like the mixed path does.

**3. `KNvfp4StaticMoE.setup` overwrites the spec.** It sets `method.use_a16` from `quant_config.quant_method` and then builds a new `QuantSpec`, replacing the one `resolve(algo, ...)` produced. So the `algo` argument and the config's `quant_method` are two independent sources of truth. For example, `build_moe_method(cfg, "NVFP4", ...)` with a config whose `quant_method` is `"W4A16_NVFP4"` silently becomes W4A16. The DeepSeek callers are fine today, and the new test covers that case. But it undercuts the idea that `resolve()` is the single decision point. Could `use_a16` come from `spec.activation is None`, with the per-token override applied in `resolve()`?

## Design suggestions (non-blocking)

- **State on an untyped `method`.** Schemes write `use_a16`, `per_token_activation`, `nvfp4_backend`, `experts_cls`, `use_global_sf` and others onto `method` inside `setup`, and the class only partly declares them. A small typed state object returned by `setup()` would make the contract explicit, and a wrong-format access would stop being an `AttributeError` at runtime. Also, `method.quant_config` (an attribute) and `scheme.quant_config(layer, method)` share a name, which is easy to misread.
- **Duplicated tables.** `MOE_ALGOS` repeats the sub-config names that `LINEAR_ALGOS` already has, and its first tuple element doesn't seem to be read. Could it be derived from `LINEAR_ALGOS`? `FUSED_MOE_METHOD_BUILDERS` is empty and only documented by a comment, so I'd drop it until a format needs it.
- **MuseSpark coupling.** The subclass calls `resolve(quant_config.quant_method, quant_config, "")` itself and then reads `self.nvfp4_backend`, which `setup()` sets during `__init__`. That depends on the exact `__init__` side effects. A supported option for separate w1/w3 scales would be less fragile.
- **Shared format math.** The NVFP4 scale handling and dequantization seem to be the same as on the linear side. Shared helpers would mean a fix lands once.
- **Smaller things:**
  - `supports_pre_processed_weights` uses `spec.weight is kNvfp4Static`, where `==` would be safer.
  - The MoE `dequantize_weight` returns a tuple while the linear one returns a tensor, and the default raises with a `QuantKey` repr instead of the usual guidance.
  - I couldn't find where `marlin_input_dtype` is now set. The old homogeneous path set it from `get_marlin_input_dtype(prefix)` when `backend == "marlin"`, and the new path drops that. It may have been dead already, but can you confirm?
  - Is `@register_weight_loader_v2_supported_method` needed on an MoE method? `RoutedExperts.weight_loader` seems to match on the class name instead.

Happy to re-review once the GPU numbers are in. Thanks again for the work here.
