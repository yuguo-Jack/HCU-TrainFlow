# [Bugfix] shm_broadcast: poll the notify socket from busy readers

[Upstream PR](https://github.com/vllm-project/vllm/pull/63165) · state: closed · merged: True

## Original PR description



## Overview

Fixes #63026. A local SHM reader that keeps reading (which is the normal state under load) never touches its `CONFLATE` notify socket, and libzmq queues an internal command for every write notification until it does. Reader memory then grows with every message. This PR polls the notify socket from `SpinCondition.record_read()` at most once per second.

## Claims

- Reader-side memory stays bounded under sustained load. Before this change, every message added ~41 B to the reader's libzmq mailbox. That affects each worker's RPC broadcast reader (2 messages per step) and EngineCore's response readers (one per replying worker; all of them reply when a KV connector is used).
- The SHM data path, notification semantics, idle wake-up and shutdown are unchanged. The added cost is one `poll(timeout=0)` per reader per second.

## Validation

**E2E (GB200, Qwen3-0.6B, TP=2, 128 prompts × 8192 tokens, `ignore_eos`).** Right after `generate()`, before any reader goes idle, the script below calls `getsockopt(ZMQ_EVENTS)` on every local reader's notify socket and records how much heap that frees. The freed heap is the size of the queued backlog.

| process | local readers | upstream backlog | this PR |
|---|---:|---:|---:|
| EngineCore | 2 | 311.6 KiB (~7.8K cmds) | ≈0 (-0.8 KiB, noise) |
| worker 0 | 1 | 300.2 KiB (~7.5K cmds) | ≈0 (-2.2 KiB) |
| worker 1 | 2 | 298.4 KiB (~7.5K cmds) | ≈0 (-5.6 KiB) |

`generate()` took 46.4 s on upstream and 46.5 s with this PR. At this step rate (~5.7 ms), upstream grows by ~23 MiB/h per process, and the backlog is never cleared while the engine stays busy. That is about one command per step rather than two: `sample_tokens` follows `execute_model` within ~3 ms, so the writer's `SNDHWM=1` usually drops its notification on aarch64.

```python
"""E2E check for vllm#63026: notify-socket command backlog under sustained decode.

Runs a TP=2 engine (EngineCore in-process) that never idles for >1s, then
immediately makes libzmq process the queued commands on every local SHM reader
notify socket and reports the freed heap. ~41 B per queued command.
"""

import argparse
import os
import time

os.environ["VLLM_ENABLE_V1_MULTIPROCESSING"] = "0"
os.environ.setdefault("VLLM_WORKER_MULTIPROC_METHOD", "fork")


def heap_in_use() -> int:
    import ctypes
    import re
    import tempfile

    libc = ctypes.CDLL("libc.so.6")
    libc.fopen.restype = ctypes.c_void_p
    libc.fopen.argtypes = [ctypes.c_char_p, ctypes.c_char_p]
    libc.fclose.argtypes = [ctypes.c_void_p]
    libc.malloc_info.argtypes = [ctypes.c_int, ctypes.c_void_p]
    with tempfile.NamedTemporaryFile(suffix=".xml") as f:
        fp = libc.fopen(f.name.encode(), b"w")
        libc.malloc_info(0, fp)
        libc.fclose(fp)
        tail = open(f.name).read()
    tail = tail[tail.rfind("</heap>") :]

    def total(t):
        m = re.search(rf'<total type="{t}" count="\d+" size="(\d+)"', tail)
        return int(m.group(1))

    system = int(re.search(r'<system type="current" size="(\d+)"', tail).group(1))
    return system - total("fast") - total("rest") + total("mmap")


def find_readers(holder, baseline):
    import gc

    from vllm.distributed.device_communicators import shm_broadcast

    if baseline:
        shm_broadcast.SHM_NOTIFY_POLL_INTERVAL_S = float("inf")
    # vLLM gc.freeze()s after startup; frozen objects are hidden from get_objects.
    frozen = gc.get_freeze_count() > 0
    gc.unfreeze()
    holder._issue_63026_readers = [
        o
        for o in gc.get_objects()
        if isinstance(o, shm_broadcast.MessageQueue)
        and getattr(o, "_is_local_reader", False)
    ]
    if frozen:
        gc.freeze()
    return len(holder._issue_63026_readers)


def drain(holder):
    import os

    import zmq

    from vllm.distributed.device_communicators import shm_broadcast

    readers = holder._issue_63026_readers
    before = heap_in_use()
    for mq in readers:
        mq._spin_condition.local_notify_socket.getsockopt(zmq.EVENTS)
    freed = before - heap_in_use()
    return dict(
        pid=os.getpid(),
        readers=len(readers),
        freed_kib=freed / 1024,
        approx_cmds=freed // 41,
        interval=shm_broadcast.SHM_NOTIFY_POLL_INTERVAL_S,
    )


def main():
    p = argparse.ArgumentParser()
    p.add_argument("--model", default="Qwen/Qwen3-0.6B")
    p.add_argument("--tp", type=int, default=2)
    p.add_argument("--num-prompts", type=int, default=128)
    p.add_argument("--max-tokens", type=int, default=8192)
    p.add_argument(
        "--baseline", action="store_true", help="disable the fix (upstream behavior)"
    )
    args = p.parse_args()

    from vllm import LLM, SamplingParams

    llm = LLM(model=args.model, tensor_parallel_size=args.tp)
    executor = llm.llm_engine.engine_core.engine_core.model_executor

    class Main:
        pass

    main_holder = Main()
    print("readers:", find_readers(main_holder, args.baseline),
          llm.collective_rpc(find_readers, args=(args.baseline,)))

    params = SamplingParams(max_tokens=args.max_tokens, ignore_eos=True)
    prompts = [f"Write a long story about number {i}." for i in range(args.num_prompts)]
    t0 = time.monotonic()
    llm.generate(prompts, params, use_tqdm=False)
    elapsed = time.monotonic() - t0

    # Measure before any reader goes idle (>1s) and polls on its own.
    engine = drain(main_holder)
    workers = executor.collective_rpc(drain)

    tag = "baseline" if args.baseline else "fix"
    print(f"\n[{tag}] generate {elapsed:.1f}s, ~{args.max_tokens} decode steps")
    print(f"[{tag}] engine-core: {engine}")
    for w in workers:
        print(f"[{tag}] worker     : {w}")


if __name__ == "__main__":
    main()
```

**Standalone `MessageQueue`.** One writer and one busy reader, aarch64, pyzmq 27.1 / libzmq 4.3.5. The table shows reader heap growth per message.

| writer gap | upstream | poll+recv every 1s (this PR) | `recv(NOBLOCK)` only, every 1s |
|---|---:|---:|---:|
| 5 ms | 42.6 B/msg | 1.3 B/msg | – |
| 2 ms | 21.5 B/msg | 1.1 B/msg | 21.5 B/msg (no effect) |

At a 2 ms gap, about half of the notifications are dropped by the writer's `SNDHWM=1` (see #58917), so fewer commands reach the reader.

## Details

**Root cause.** In libzmq 4.3.5, `ypipe_conflate_t::flush()` returns `reader_awake`, and nothing ever sets that to true. A `CONFLATE` session pipe also gets HWM -1 (unlimited). So for every notification it receives, the reader's I/O thread posts an `activate_read` command to the SUB socket's mailbox. Those commands are only processed when the application calls into the socket. libzmq documents this under `ZMQ_CONFLATE` in `zmq_setsockopt(3)`: "If recv is not called on the inbound socket, the queue and memory will grow with each message received. Use ZMQ_EVENTS to trigger the conflation of the messages." `SpinCondition.wait()` polls only after `busy_loop_s` (1 s) without a read, which never happens while the engine is stepping. The backlog is cleared only after the reader idles for more than 1 s. EngineCore's response readers stay stuck until the next request arrives, and RSS may not come back down even then.

**Why `poll()` and not just `recv()`.** When a message is already in the pipe, `recv(NOBLOCK)` returns it without processing commands, so the backlog keeps growing (last column in the standalone table above). `poll()` goes through `ZMQ_EVENTS`, which processes them.

**Correctness.** Notifications are only wake-up hints; the SHM flags are authoritative. The writer always sets the written flag (with a fence) before it notifies. So if a busy read consumes a notification, the slot it announced is already visible to the next `acquire_read()` check. The socket is only used by the reader thread, the same thread that runs `wait()`. Cancellation goes through a separate socket.

**Interval.** 1 s matches the default `busy_loop_s` and the interval used by vllm-project/vllm-ascend#19140, which is the Ascend-side workaround for the same issue. That patch can be dropped once this lands. At most ~1 s worth of commands can accumulate. I kept the interval as a separate constant instead of reusing `busy_loop_s`, because #52814 would make that window configurable down to ~0.

**Not a duplicate.** #58917 changes the writer's HWM so that notifications are not dropped. It does not touch the reader mailbox, and it would actually remove the incidental rate cap that currently limits this growth. #52814 and #52848 change the busy window and sleep. No open PR services the reader's notify socket.

When the IPC connection is slow to establish (for example on a loaded CI worker), this one-shot enqueue can publish before `reader._spin_condition.local_notify_socket` has joined. `wait_until_ready()` only handshakes the separate `MessageQueue.local_socket` XPUB/SUB channel, while the notify channel uses plain PUB/SUB, so ZeroMQ drops this notification and the following poll times out after 5 seconds even though the implementation is correct. Synchronize the notify channel (or poll an explicit readiness condition) before sending the notification the assertion relies on.
