# [KV Cache] Native simulator

[Upstream PR](https://github.com/vllm-project/vllm/pull/47922) · state: open · merged: False

## Original PR description

## Summary

Adds a simulated forward mode for exercising vLLM scheduling and KV cache behavior without downloading model weights, loading weights into memory, or running a real forward pass.

The mode constructs the real vLLM model on the `meta` device for metadata-only tensors, so vLLM can reuse the model's normal attention metadata and KV-cache specs, including hybrid, full, and sliding-window attention layouts, without materializing model parameters.

KV cache management then runs through the normal vLLM path, using the configured KV memory budget to compute block capacity and cache groups.

During generation, the runner emits caller-provided token IDs via the existing trace replay (`trace_decode_token_ids`, enabled automatically by `--simulate-forward`) while reusing vLLM's normal KV cache management without allocating KV tensors. Chat and completion requests now accept `trace_decode_token_ids` so this also works over HTTP.

Motivated by #43447

## Notes

- `--simulate-forward` is CPU-only.
- `--kv-cache-memory-bytes` controls the simulated KV capacity.
- Model weights are not downloaded or loaded; model config and tokenizer metadata may still be fetched.
- This simulates scheduler/KV-cache behavior, not model quality or kernel execution.
- Doesn't support MLA yet (deepseekv4)
- **Simulated forward uses MRV2, which requires `triton-cpu`**

## Example

1. Start the server:
    ```bash
    vllm serve openai/gpt-oss-120b \
      --simulate-forward \
      --kv-cache-memory-bytes 17179869184 # 16 GiB
    ```

2. Send the first completion request:
    ```bash
    TEXT="$(printf 'repeat this prefix %.0s' {1..300})"

    curl -s http://127.0.0.1:8000/v1/chat/completions \
      -H 'Content-Type: application/json' \
      -d '{
        "model": "openai/gpt-oss-120b",
        "messages": [
          {
            "role": "user",
            "content": "'"$TEXT"'"
          }
        ],
        "trace_decode_token_ids": [501, 502],
        "return_token_ids": true
      }'
    ```

3. Repeat the same request.

4. Check prefix-cache metrics:
    ```bash
    curl -s http://127.0.0.1:8000/metrics \
      | grep -E 'vllm:prefix_cache_(queries|hits)'
    ```

The completion response should contain exactly token IDs `501,502` (`finish_reason: length`), and the repeated request should increase prefix-cache hits.

Example output from this flow:

```text

Using 16.0 GiB simulated KV cache memory for virtual KV cache.
Initialized virtual KV cache with 2 groups and 3640 blocks; skipped KV tensor allocation.

token_ids [501, 502] finish_reason length
prompt_tokens 968
completion_tokens 2

vllm:prefix_cache_queries_total{engine="0",model_name="openai/gpt-oss-120b"} 1936.0
vllm:prefix_cache_hits_total{engine="0",model_name="openai/gpt-oss-120b"} 896.0
```

- ZC502 · comment · 2026-09-28T02:12:19Z · [source](https://github.com/vllm-project/vllm/pull/47922#issuecomment-5862067446)

@sagearc (@LioEinaudi and I) ran the A/B pilot  this PR (head `e59cbe60`). Two concrete findings came out of it:

**1. The request-boundary KV experiment works cleanly (tested with `allenai/Olmo-3-7B-Think`).**
Using the same 14-request trace, we ran 3 fresh runs per arm. The only difference was virtual KV capacity:
```
16 GiB ↔ 2 GiB

self-repeat A/B     PASS / PASS
output control      PASS
first divergence    E13 (seed_replay)
seed replay hits    768/896 vs 0/896
preemptions         0 vs 0
```
E0–E12 were identical across both arms. The first state divergence only appeared when the original seed was replayed, which is exactly the expected boundary behavior.

**2. MoE initialization fails under `simulate_forward`.**
Both `openai/gpt-oss-120b` and `Qwen/Qwen3-235B-A22B` fail during post-load processing:
```
_C::prepack_moe_weight:
attempted to run this operator with Meta tensors,
but there was no fake impl or Meta kernel registered
```
*Environment caveat*: We ran PR-head Python on top of the official `v0.27.0+cpu` wheel native binaries (torch 2.13, prebuilt triton-cpu 3.8.0). Because of this mixed build, we're flagging this as a reproducible environment-specific finding rather than a guaranteed upstream CI failure. However, the call stack (`CPUUnquantizedExperts` → `cpu_prepack_moe_weight`) seems tied to recent MoE prepack additions.
**note:**
With serial request-boundary snapshots, gauges like `kv_cache_usage_perc` return to zero after each request, so prefix-cache retention is the primary observable here. Future runs might need concurrent pressure to surface eviction/preemption dynamics.
I’ve attached the raw canonical evidence, logs, manifests, and checksums in **[sim47922_sage_evidence.zip](https://github.com/user-attachments/files/32715485/sim47922_sage_evidence.zip)**.
As a follow-up, we'd be interested in seeing if this exact evidence contract could be used for paired MRV1 :left_right_arrow: MRV2 KV-behavior regression, assuming we can expose equivalent observables on both sides.
