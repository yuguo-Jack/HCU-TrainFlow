# [Benchmark] Include speculative drafting in bench forward

[Upstream PR](https://github.com/vllm-project/vllm/pull/63622) · state: closed · merged: True

## Original PR description



## Overview

Include the configured MTP, EAGLE, DSpark, or DFlash drafter in `vllm bench forward` timing by default. Add `--exclude-drafter` for target-only timing.

This follows the PP support merged in #63616 and is rebased onto `main`. Open-PR searches for `bench forward` and speculative drafting found no duplicate; the existing speculator CUDA-graph work concerns serving, not this benchmark entry point.

## Claims

- Capture the target forward and real draft proposal, including draft sampling, in the timed CUDA graph. Assume all draft tokens are accepted, with a fixed bonus token; exclude target sampling, rejection sampling, and CPU overhead.
- Reserve draft KV lookahead and restore KV, slot mappings, and block tables for repeatable replays. PP runs the drafter on the last stage.
- Report the timing scope and graph/eager draft-token agreement in JSON; document the default and exclusion option.

## Validation

GB200, dummy weights, greedy drafting:

- `.venv/bin/python -m pytest tests/benchmarks/test_forward_cli.py -k 'drafter and METHOD' -q`, separately for `mtp`, `eagle3`, `dspark`, and `dflash`: **4 passed**. Each checks verification, prefill, and mixed batches with drafting included and excluded (24 cases).
- `.venv/bin/python -m pytest tests/benchmarks/test_forward_cli.py -k 'pcp_query or build_batch or jitter or oversized_verify or profile_summary' -q`: **7 passed**.
- `.venv/bin/python -m pytest tests/benchmarks/test_forward_cli.py::test_bench_forward -q`: **1 passed**, including kernel profiling.
- All pre-commit hooks passed, including mypy and CI test-wiring checks. The benchmark CI job selects the new parametrized test.
- Before-change check: copied the new EAGLE3 test to base `97135395dd` and ran `-k 'drafter and eagle3'`; it failed with `KeyError: 'timing_scope'`. The same test passes on this branch.

Additional full-model CLI checks used `verify=4*4@128:3` and `prefill=128`, three draft tokens, `--iters 3 --samples 2`. All target outputs and draft token IDs matched eager execution exactly:

| Target / drafter | Configuration |
| --- | --- |
| MiMo-7B-Base / MTP | Single GPU |
| Qwen3-1.7B / AngelSlim EAGLE3 | Single GPU, PP=2, DP=2 (DP also checked a mixed batch) |
| Qwen3-8B / z-lab DFlash | Single GPU |
| Qwen3-8B / Qwen3 DSpark | Single GPU; synthetic DSpark config using the DFlash backbone and a Markov head |
| Reduced DeepSeek-V3.2 / MTP | PCP=2, FLASHMLA_SPARSE, fp8_ds_mla; verification, prefill, and mixed batches |

For example, EAGLE3 verification measured 2.393 ms including drafting versus 1.534 ms with `--exclude-drafter`; prefill measured 2.553 ms versus 1.875 ms. These validate the timing scope, not a serving speedup.

```bash
vllm bench forward --model Qwen/Qwen3-1.7B \
  --speculative-config '{"model":"AngelSlim/Qwen3-1.7B_eagle3","method":"eagle3","num_speculative_tokens":3}' \
  --max-model-len 2048 --gpu-memory-utilization 0.3 \
  --case verify=4*4@128:3 --case prefill=128 --iters 3 --samples 2
# Repeat with --exclude-drafter for target-only timing.
# For PP/DP, launch two workers with torchrun and add -pp 2 / -dp 2.
```

Additional DSV4.1-Flash validation used the full cached `deepseek-ai/DeepSeek-V4.1-Flash` checkpoint (revision `2cba9e42aa026125f3ed06c6d98c1db82f7ca027`), including its three-layer DSpark and Engram tables, on 4 GB200 GPUs with TP=4, EP=4, `deep_gemm_mega_moe`, FP8 KV, and `FLASHINFER_MLA_SPARSE_DSV41`. Both dummy and real weights completed verification, prefill, and mixed workloads. Five draft tokens were accepted; target sampling remains excluded. The trace has 43 MegaMoE calls with drafting and 40 without.

Real-weight CUDA graph timing (3 samples × 10 replays, maximum rank time):

| Case | Target + DSpark | Target only | Draft tokens match eager |
| --- | ---: | ---: | --- |
| verify1 | 7.086 ms | 6.230 ms | No |
| verify16 | 12.240 ms | 11.107 ms | Yes |
| prefill1k | 22.983 ms | 22.016 ms | Yes |
| prefill8k | 94.595 ms | 92.537 ms | No |
| mixed | 25.932 ms | 23.915 ms | No |

**This is not a clean numerical validation of DSV4.1.** All ranks produced finite outputs and valid draft IDs; the 16-request verification case matched target and draft eager outputs exactly. However, single-request verification had a 0.985 target graph/eager relative RMS difference, and prefill varied even between eager repeats (about 0.09 at 1K and 0.15 at 8K). The target-only control reproduced these discrepancies. The drafter integration does not introduce the observed target discrepancy, but its underlying cause is not fully resolved. Real-weight sample-median spread with drafting was 0.21–1.36%; these timings establish execution scope, not serving performance or model accuracy.

```bash
torchrun --standalone --nproc-per-node=4 -m vllm.entrypoints.cli.main bench forward \
  --model deepseek-ai/DeepSeek-V4.1-Flash --load-format auto --routing real \
  --tensor-parallel-size 4 --enable-expert-parallel --moe-backend deep_gemm_mega_moe \
  --language-model-only \
  --speculative-config '{"method":"dspark","num_speculative_tokens":5,"enable_adaptive_verification":false}' \
  --attention-config '{"backend":"FLASHINFER_MLA_SPARSE_DSV41","indexer_kv_dtype":"mxfp4","indexer_sparse_logits":true}' \
  --kv-cache-dtype fp8 --disable-flashinfer-autotune \
  --kernel-config.enable_jit_warmup false --kernel-config.enable_cutedsl_warmup false \
  --max-model-len 16384 --max-num-batched-tokens 8192 \
  --gpu-memory-utilization 0.8 --kv-len-jitter 0 \
  --case verify1=6@8192:5 --case 'verify16=16*6@8192:5' \
  --case prefill1k=1024 --case prefill8k=8192 --case 'mixed=1024,8*6@8192:5' \
  --iters 10 --samples 3 --output-json results.json --profile-dir profiles
# Repeat with --exclude-drafter.
```

A separate dummy-weight diagnostic disabled `supports_mhc_overlap` outside the repository: single-request target verification became bit-exact between graph and eager, while 1K prefill still varied. This isolates the small-batch discrepancy to the model’s capture-specific mHC path; the prefill discrepancy remains unresolved. No model code or correctness tolerances were changed.

Additional parallel-layout checks used the same real DSV4.1-Flash checkpoint, DSpark configuration, MegaMoE backend, and four GB200 GPUs:

- **DEP=4 (DP=4, TP=1, EP=4):** all five cases completed with finite target outputs and valid draft IDs on every rank. The 16-request verification case matched target and draft eager outputs exactly on every rank. Single-request verification and prefill retain the target numerical discrepancies described above; the target-only DEP control reproduces them. Prefill draft agreement varies by rank.
- **PP=2, TP=2, EP=2:** model initialization fails with `ValueError: DeepseekV41ForCausalLM does not support dspark with pipeline parallelism`. The shared runner requires `supports_aux_hidden_states_over_pp`, which this model does not implement. This is an underlying model/speculator restriction; no guard was bypassed and no PP timing is claimed for DSV4.1 + DSpark. The Qwen3/EAGLE3 PP checks above remain the PP coverage for this PR.

DEP timing with drafting included (3 samples × 10 replays; each workload is **per DP rank**, with four replicas active):

| Per-rank case | Target + DSpark |
| --- | ---: |
| verify1 | 9.655 ms |
| verify16 | 16.351 ms |
| prefill1k | 29.473 ms |
| prefill8k | 121.820 ms |
| mixed | 32.108 ms |

Repeat the DSV4.1 command above with `--tensor-parallel-size 1 --data-parallel-size 4` for DEP, or `--tensor-parallel-size 2 --pipeline-parallel-size 2` to reproduce the PP restriction. Included-drafter DEP sample-median spread was 0.18–1.42%. The first target-only control had a mixed-case timing outlier (114.238 ms, 18.71% sample-median spread); its trace showed large Engram lookup and elementwise times. Do not infer drafter overhead from that run.

Repeated target-only control (5 samples × 20 replays):

| Per-rank case | Target only | Sample-median spread |
| --- | ---: | ---: |
| verify1 | 8.623 ms | 2.19% |
| verify16 | 15.083 ms | 1.68% |
| prefill1k | 28.555 ms | 0.40% |
| prefill8k | 122.050 ms | 1.35% |
| mixed | 30.928 ms | 0.73% |

The mixed-case outlier did not recur (30.928 ms on repeat). At 8K, included/excluded timing differences are within variability, so these runs do not resolve drafter overhead. Numerical discrepancies persisted in both target-only controls. No serving/model implementation changes were made.

GLM5.3-NVFP4 supplies additional real-weight MTP + PP coverage. On four GB200 GPUs, PP=2 / TP=2 / EP=2 with `VLLM_PP_LAYER_PARTITION=42,36`, three accepted draft tokens, FlashMLA sparse attention and FP8 MLA KV passed exact target graph/eager, full-pipeline/eager, and draft-token agreement for single-request verification, 16-request verification, 1K prefill, and the mixed batch. All outputs were finite. The checkpoint is `nvidia/GLM-5.3-NVFP4`, revision `e3b8f9f2fad29727dfa95e766c5cac18ea1414bf`; it contains a BF16 MTP layer. Automatic backend selection uses TRTLLM NVFP4 target MoE and BF16 MTP MoE, not NVFP4 MegaMoE. Traces confirm three MTP forwards on the last stage.

| GLM case | Including MTP | Target only | Included / excluded sample spread |
| --- | ---: | ---: | ---: |
| 1K prefill | 66.845 ms | 63.538 ms | 0.049% / 0.087% |
| Mixed: 1K prefill + 8 verification requests | 72.095 ms | 68.505 ms | 0.047% / 0.083% |

Each timing uses 3 samples of 10 steady-window microbatches; eight fill and eight drain microbatches are excluded. Both cases show stage 1 overlapping stage 0's next microbatch for all 30 measured microbatches. Clock-correlation uncertainty was at most 0.179 ms. Included/excluded cases were run through the existing `run_case` in the same loaded-model session, with garbage collection disabled during execution and performed between cases. An initial paired attempt failed when old CUDA graphs were collected during a new capture; per-case results from the successful rerun were saved separately.

Limits exposed by this check:

- The default 39/39 split starts the second stage inside a shared sparse-index group and fails verification graph/eager agreement even without MTP. Starting that stage at index-producing layer 42 fixes the verification and mixed-case disagreements without changing model code.
- 8K prefill still has a target graph/eager discrepancy (maximum relative RMS about 0.323 across ranks), also present in the target-only control. Similar 8K disagreement was present in the earlier real-weight GLM PCP run. It is not counted as clean correctness coverage.
- Verification outputs are exact with 42/36, but its included-MTP pipeline latency grows as the faster first stage queues work ahead of the last stage (49–55% sample spread). Those medians are **not** valid steady-state latency estimates. Bounded in-flight work/backpressure remains a PP benchmark issue; this PR does not fix it.

Reproduction uses the benchmark CLI with `--model nvidia/GLM-5.3-NVFP4 --load-format safetensors --routing real --pipeline-parallel-size 2 --tensor-parallel-size 2 --enable-expert-parallel --speculative-config '{"method":"mtp","num_speculative_tokens":3}' --attention-backend FLASHMLA_SPARSE --kv-cache-dtype fp8_ds_mla`, `VLLM_PP_LAYER_PARTITION=42,36`, and cases `verify1=4@8192:3`, `verify16=16*4@8192:3`, `prefill1k=1024`, `prefill8k=8192`, `mixed=1024,8*4@8192:3`. Use max model length 16384, max batched tokens 8192, GPU memory utilization 0.8, KV jitter 0, 10 iterations and 3 samples; disable FlashInfer autotune and kernel JIT/CuTeDSL warmup. Repeat with `--exclude-drafter` for target-only execution.

## Details

The benchmark calls the existing speculator `propose` interface rather than duplicating drafting implementations. Serving and model implementations are unchanged; accuracy evaluation is not applicable to this synthetic timing fixture. Balanced MoE routing still applies only to the target, so representative MoE drafter timing requires real weights.

AI assistance was used to implement and validate this change. Documentation discovery was checked locally, on the GitHub branch, and through web access; search indexes still show the pre-merge documentation.
