# [Bugfix][Docker] Preserve source-built Triton in downstream uv installs

[Upstream PR](https://github.com/vllm-project/vllm/pull/64813) · state: open · merged: False

## Original PR description

## Overview

Fixes #64761 by preserving the installed source-built Triton version in the image's existing uv overrides file. The reported constrained downstream `uv pip install` can then add dependencies while retaining the customized Torch/Triton runtime.

## Claims

- Records the exact installed Triton version after a successful source-wheel installation, alongside the existing NCCL override.
- Resolves the reported constrained downstream installation without changing captured runtime versions or metadata.
- Documents the supported downstream uv installation procedure.

## Validation

Tested on Linux aarch64 using the issue's exact image:
`vllm/vllm-openai@sha256:d8f44d07d74900d0043eebc7e0c2b2d952caf92fb66d4400ef2dd902c5d3dcf0`, Python 3.12.3, uv 0.13.6.

| Check | Result |
| --- | --- |
| Original image, `b12x==1.5.1` dry run with exact Torch/Triton constraints | Failed with the reported Triton 3.9.0 versus 3.8.0 conflict |
| Apply the new override command, repeat the same dry run | Passed |
| Install full reported auxiliary package set with captured runtime constraints | Passed |
| Compare runtime versions and SHA-256 hashes of `METADATA` before/after | Identical |
| Pre-commit on all three changed files; `git diff --check` | Passed |

The full installation command was:

```bash
uv pip install --system --break-system-packages --prerelease=allow \
  --constraint /tmp/runtime-constraints.txt \
  'ray[cgraph]>=2.48.0' runai-model-streamer b12x==1.5.1 \
  fastsafetensors==0.5.0 pytest
```

Constraints captured installed `torch`, `torchvision`, `torchaudio`, `triton`, `cuda-bindings`, `cuda-python`, and all `nvidia-*` distributions. Torch remained `2.16.0.dev20261009+cu134`; Triton remained `3.8.0+git3f6e4113`. The test applied the exact new override command to the published image; it was not a full from-source Docker rebuild. No GPU inference or model evaluation was run: this change concerns dependency resolution and does not change the selected runtime versions.

from importlib.metadata import distribution, distributions

names = {"torch", "torchvision", "torchaudio", "triton", "cuda-bindings", "cuda-python"}

    runtime[name] = {
        "version": dist.version,

    }
print(json.dumps(runtime, indent=2, sort_keys=True))
Path("/tmp/runtime-constraints.txt").write_text(
    "".join(f"{name}=={data['version']}\n" for name, data in runtime.items())
)
Path("/tmp/torch-triton-constraints.txt").write_text(

)

uv --version
uv venv --system-site-packages /tmp/repro/.venv

cat /tmp/runtime-before.json
printf '\nExisting uv overrides:\n'
cat /etc/uv-overrides.txt
set +e

printf '\nUpdated uv overrides:\n'
cat /etc/uv-overrides.txt

## Details

The source Triton installer intentionally uses `--no-deps`, while PyTorch's wheel metadata still requires another Triton version. Constraints cannot replace that transitive requirement. Reusing `UV_OVERRIDE=/etc/uv-overrides.txt` supplies the intentional override for later uv installs without rewriting metadata.

The append is chained to successful installation so installer/checksum/PTXAS failures still fail the Docker layer. `uv pip list --format freeze` supplies a version pin instead of an ephemeral local wheel URL. Builds without source-built Triton keep their current behavior. This does not make wheel metadata dependency-consistent; pip does not read `UV_OVERRIDE`.

Duplicate-work checks: the issue is unassigned with no comments; open PR searches for `64761 in:body` and the affected cu134/Triton area found no matching fix. The Kimi-K3 kernel-selection PR #60470 is unrelated.
