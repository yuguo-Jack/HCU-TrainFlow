# [BugFix] Forward the configured cpu distributed timeout to `cpu_all_reduce_` 

[Upstream PR](https://github.com/vllm-project/vllm/pull/63016) · state: closed · merged: True

## Original PR description



## Overview


#61767 introduced `cpu_all_reduce_` (`vllm/distributed/utils.py`), a low-latency gloo all-reduce for the DP hot path — `ParallelConfig.sync_dp_state` (engine-side DP state sync) and `sync_cudagraph_and_dp_padding` (worker-side DP padding/cudagraph coordination). It replaced `torch.distributed.all_reduce` with raw `group.send`/`group.recv` p2p ops waited on via bare `work.wait()`.

A bare `wait()` never times out: the gloo group's default timeout is not applied to these p2p waits. So since #61767, `--cpu-distributed-timeout-seconds` silently no longer takes effect on the DP sync path — when a DP peer hangs or dies, the surviving ranks block inside the DP sync, where previously they would have raised a timeout error.

## Claims


Now `cpu_all_reduce_` will throw timeout error under defined `-cpu-distributed-timeout-seconds`.


## Validation



**Unit test** : `pytest tests/distributed/test_cpu_all_reduce.py`

`test_cpu_all_reduce_timeout` spawns 2 gloo ranks; rank 1 never joins the all-reduce, and rank 0 calls `cpu_all_reduce_` with `timeout=timedelta(seconds=1)`. It asserts a `RuntimeError("Timed out ...")` is raised and that the call returns in under 3s (measured ~1.0s), i.e. the wait honors the timeout rather than hanging until the peer process exits.

**Manual e2e**: launched a DP=2 deployment, put one DP rank to sleep, and observed the other rank raise the gloo timeout in the DP sync within the configured window instead of hanging.


## Details



Add an optional `timeout: timedelta | None = None` parameter and forward it to every p2p `work.wait(timeout)`:

- `cpu_all_reduce_` — bounds each p2p wait; `None` keeps the previous no-timeout behavior, so other callers are unaffected.
- `GroupCoordinator.cpu_all_reduce_` and `ParallelConfig.sync_dp_state` — pass-through plumbing.
- Both DP call sites now forward the configured `cpu_distributed_timeout`: `DPEngineCoreProc._has_global_unfinished_reqs` (engine DP state sync) and `sync_cudagraph_and_dp_padding` (worker DP sync).

With this, a hung peer surfaces as a `RuntimeError("Timed out ...")` on the surviving ranks within the configured timeout, instead of an indefinite hang.
