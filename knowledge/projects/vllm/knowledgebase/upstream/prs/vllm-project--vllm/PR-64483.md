# [Perf][Multimodal] Add `mm_tensor_ipc="cuda_ipc_pool"`: TP-aware GPU transport

[Upstream PR](https://github.com/vllm-project/vllm/pull/64483) · state: open · merged: False

## Original PR description



## Summary

This PR continues [#49462](https://github.com/vllm-project/vllm/pull/49462),
co-authored by me, @SangChengC (who opened it), and @wendadawen, rebased onto
current main.

Adds `cuda_ipc_pool`, a persistent CUDA IPC pool that sends GPU-preprocessed
multimodal features to TP workers over D2D / P2P without a host round trip.
Unlike `torch_shm`, it supports TP > 1.

For an EPD encoder with TP > 1, `direct_rpc` was previously the only transport.
`auto` therefore kept preprocessing on CPU; explicitly selecting GPU still
copied the output back to host. `cuda_ipc_pool` lets `auto` use GPU
preprocessing and keeps the data on device.

On Qwen3-VL-30B-A3B-Instruct with E TP4, 10 random 1920x1080 images per
request, and concurrency 16, GPU preprocessing + `cuda_ipc_pool` achieves a
2.33x speedup in p50 E-stage latency over CPU + `direct_rpc`; holding
preprocessing on GPU, the transport-path comparison is 2.01x.

## Changes from #49462

- Rename `cuda_ipc` to `cuda_ipc_pool` to distinguish the persistent pool from
  `torch_shm`, which also uses CUDA IPC handles.
- Add a separate `--mm-cuda-ipc-pool-gb` budget; `mm_ipc_gpu_memory_gb`
  remains the frontend decode admission budget.
- Reject PP > 1, DP > 1, TP > 16, `nnodes > 1`, and
  `--api-server-count > 1` during config validation.
- Fix slice leaks on encoder-cache, prefix-cache, and EC hits, duplicate items,
  and queued aborts; disable the processor cache because cached items could
  outlive their slices.
- Let EPD encoder-only instances select GPU preprocessing in `auto` mode.

## How it works

- **Frontend:** allocate one persistent pool and export its CUDA IPC handle
  once. Copy each GPU tensor into a free slice and send only metadata. Pool
  exhaustion falls back to host copy with a rate-limited warning.
- **Engine core:** keep the slice as a lightweight proxy during scheduling and
  metadata broadcast.
- **Workers:** map the pool once, then `proxy.reconstruct()` copies the slice on
  the local GPU (D2D on rank 0, P2P on other ranks).
- **Recycling:** each in-flight slice has one shared-memory flag per TP rank
  and is reclaimed after all flags are set. Request completion covers inputs
  the encoder skips
  (encoder-cache, prefix-cache, and EC hits, duplicates); an undelivered proxy
  releases all flags when dropped.

CPU tensors continue through the normal host-copy path.

## Model evaluation / performance

On Qwen3-VL-30B-A3B-Instruct with E TP4:

- GPU preprocessing + `cuda_ipc_pool` reduces p50 E-stage latency from
  14.02 s to 6.01 s (2.33x) versus CPU + `direct_rpc`.
- Holding preprocessing on GPU, changing `direct_rpc` to `cuda_ipc_pool`
  reduces it from 12.10 s to 6.01 s (2.01x). GPU preprocessing while retaining
  `direct_rpc` gives 1.16x. These are E-stage, not transfer-only, comparisons.

| | CPU + `direct_rpc` | GPU + `direct_rpc` | GPU + `cuda_ipc_pool` | Pool vs CPU RPC | Pool vs GPU RPC |
|---|---|---|---|---|---|
| Mean | 13665.8 ms | 11942.4 ms | 5728.6 ms | 2.39x | 2.08x |
| P50 | 14020.1 ms | 12103.5 ms | 6010.6 ms | 2.33x | 2.01x |
| P90 | 16445.1 ms | 16442.9 ms | 9964.4 ms | 1.65x | 1.65x |

One run per arm: 16 warmup and 96 measured requests, 10 random 1920x1080
images per request, input/output lengths 128/64, concurrency 16, on 8x H20
(NVLink). PD ran TP4 behind `disagg_epd_proxy.py`. The pool arm had no fallback.

E-stage latency covers API-server arrival through the synchronized end of the
ViT forward and excludes the EC save. The same local instrumentation patch was
used for all arms; it takes the latest timestamp across TP ranks and encoder
calls. The patch is not part of this PR.

E-PD / E-P-D results are omitted because no RDMA-capable EC connector was
available. ECExampleConnector over disk or `/dev/shm` introduces storage- or
memory-bandwidth bottlenecks that are not representative of RDMA.

Common E arguments:

```bash
COMMON_ARGS=(
  Qwen/Qwen3-VL-30B-A3B-Instruct
  --tensor-parallel-size 4 --max-num-seqs 32 --max-model-len 32768
  --max-num-batched-tokens 65536 --gpu-memory-utilization 0.35
  --limit-mm-per-prompt '{"image":10,"video":0}'
  --mm-processor-cache-gb 0 --no-enable-prefix-caching
  --ec-transfer-config '{"ec_connector":"ECExampleConnector","ec_role":"ec_producer","ec_connector_extra_config":{"shared_storage_path":"/dev/shm/ec_cache"}}'
)

# CPU + direct_rpc
CUDA_VISIBLE_DEVICES=0,1,2,3 vllm serve "${COMMON_ARGS[@]}" \
  --mm-tensor-ipc direct_rpc

# GPU + direct_rpc
CUDA_VISIBLE_DEVICES=0,1,2,3 vllm serve "${COMMON_ARGS[@]}" \
  --mm-tensor-ipc direct_rpc --mm-processor-device cuda

# GPU + cuda_ipc_pool
CUDA_VISIBLE_DEVICES=0,1,2,3 vllm serve "${COMMON_ARGS[@]}" \
  --mm-tensor-ipc cuda_ipc_pool --mm-cuda-ipc-pool-gb 4
```

## Existing transports and design alternative

`torch_shm` delivers each tensor to the engine-core process and currently
supports only TP1. Extending it to TP > 1 would require another hop to rank 0
and an ordered NCCL collective. We did not implement or benchmark that
alternative. It avoids an explicit pool but adds synchronization and
TP-communicator traffic, while in-flight producer memory still needs bounding.
The pool lets workers read independently, so the transports remain separate.

#51349 adds a paged host shared-memory processor cache and does not overlap
with this GPU transport.

## Files changed

- **Transport:** pool/proxy/recycling, OOB wiring, and worker reconstruction.
- **Configuration:** transport option, independent budget, topology checks,
  and EPD device selection.
- **Lifecycle:** V1/V2 release paths and processor-cache disablement.
- **Tests:** transport, config, cache, and memory-reservation coverage; the P2P
  case runs in the two-GPU Distributed Comm Ops job.

Device selection uses `torch.accelerator` (RFC #30679), not `torch.cuda`.
