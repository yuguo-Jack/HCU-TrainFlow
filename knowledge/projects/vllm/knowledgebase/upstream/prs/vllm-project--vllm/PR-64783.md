# [Attention] Support `fp8_ds_mla` in Triton MLA on Ampere

[Upstream PR](https://github.com/vllm-project/vllm/pull/64783) · state: open · merged: False

## Original PR description

## Overview

Add opt-in `fp8_ds_mla` decode support to `TRITON_MLA` on CUDA SM80+ GPUs,
including NVIDIA A100. This implements the software-dequant path proposed in
#52202 and #59016.

The path reuses the existing 656-byte DeepSeek FP8 cache layout, CUDA cache
writer, prefill upconversion, workspace management, and split-KV reduction.

## Claims

- Decode packed `fp8_ds_mla` cache rows on SM80+ using software E4M3-to-BF16
  conversion in a Triton split-KV kernel.
- Preserve the existing native-FP8 path and its SM89 requirement for plain
  `fp8` / `fp8_e4m3` MLA caches.
- Reduce raw dense MLA cache storage from 1,152 BF16 bytes to 656 packed bytes
  per token (43.1%), while documenting that decode is slower than BF16.
- Add A100 CI selection, kernel correctness coverage, CUDA graph coverage, and
  an `LLM` regression test covering chunked prefill, decode, and prefix reuse.

## Details

The packed cache stores 512 E4M3 bytes, four FP32 group scales, and 64 BF16
RoPE values per token. The new Triton kernel converts 128-value groups to BF16,
accumulates query/key logits with the unchanged RoPE tail, and computes values
in two 256-wide groups before using the existing stage-two reduction.

The implementation is isolated in `triton_fp8_ds_mla.py`; the shared backend
only validates the supported shape/dtype/device and dispatches the opt-in cache
dtype. Supported geometry is intentionally limited to latent rank 512 and RoPE
dimension 64.

This does not duplicate an existing open PR. PR keyword matches #47629 and
#40925 address sparse MLA and generic block-scaled Triton tuning respectively;
neither adds dense packed `fp8_ds_mla` decode on Ampere.

- selimfedakar · comment · 2026-10-31T01:46:20Z · [source](https://github.com/vllm-project/vllm/pull/64783#issuecomment-6537367231)

Thanks for this — I read it closely since it sits right next to the eager-attention KV-view work I've been doing (#64571 / #64572), and the write-up made the cache layout easy to follow. I verified the main-facing claims against current `main` before commenting; no blocking issues from my read, a few confirmations and two robustness questions.

**Verified against `main`:**

- The SM89 guard narrowing (`startswith("fp8")` → `in ("fp8", "fp8_e4m3")`) is correct and necessary: on `main` (`triton_mla.py:203`) any `fp8*` dtype inherits the SM89 gate, so `fp8_ds_mla` would have been blocked on exactly the SM80 GPUs this PR targets. The dedicated SM80 guard added in `__init__` replaces it cleanly, and the native `fp8`/`fp8_e4m3` path keeps its SM89 requirement.
- Moving the `unsqueeze(2)` / `kv_c_cache` / `PAGE_SIZE` lines below the `block_table`/`seq_lens` reassignment is behavior-preserving — the intervening `repeat_interleave` block touches neither `kv_c_cache` nor `PAGE_SIZE`, so the native `decode_attention_fwd` call is unchanged.
- The hardcoded `513` / `512` Mid-layout strides line up with `main`'s `logits_shape = (B, q_num_heads, num_kv_splits, kv_lora_rank + 1)` (`:281`) precisely because the new guard forces `kv_lora_rank == 512`; the workspace is contiguous so the stage-1 write strides match what stage-2 reads back.
- `_dequantize_e4m3` masks the sign bit (`(b & 0x7F) == 0x7F`), so both `0x7F` and `0xFF` map to NaN, and `scale * 256.0` is the 2^(15−7) bias correction for the fp16-bitcast path. Looks right.

**Two non-blocking questions:**

1. `decode_attention_fwd_fp8_ds_mla` asserts `shape[-1] == 656` and `stride(-1) == 1`, but the kernel also reinterprets the same buffer as fp32 (`byte_offset // 4`) and bf16 (`byte_offset // 2`). Those divisions are exact only if the per-token / per-block strides are multiples of 4, which holds for the contiguous 656-byte cache but isn't asserted. Would you add a `stride(1) % 4 == 0` (or contiguity) check so a padded/non-contiguous caller fails loudly instead of misaligning the views silently?

2. The `513` / `512` constants in the stage-1 Mid stores couple the kernel to `kv_lora_rank == 512`. It's safe today given the `__init__` guard, but a short comment there (or deriving the stride from `kv_lora_rank + 1`) would make the coupling explicit if that rank restriction is ever relaxed.

One note on validation: thanks for being explicit that the end-to-end `test_triton_mla_packed_fp8_generation` run is still pending on the rebased commit — the targeted kernel matrix and cache-writer coverage look thorough, and a `/ci run` after approval should close that last gap.
