# [Frontend] Give API workers independent reuseport listeners

[Upstream PR](https://github.com/vllm-project/vllm/pull/58278) · state: open · merged: False

## Original PR description

## Purpose

Multiple API workers inheriting one socket share its accept queue. Give each TCP worker a fresh listener on the same endpoint so SO_REUSEPORT can distribute new connections.

The HTTP launcher adds only 8 lines to supply an optional factory. The process manager uses socket contexts and `nullcontext` to close fresh parent handles after spawn while borrowing the default socket. Production diff: **24 additions / 11 deletions**. No new startup rollback or finalizer reordering; baseline partial-start failure behavior remains. Single-worker, Unix-domain and Rust listener policies are unchanged. Keep-alive requests stay with their accepted connection. Model computation and response formats are unchanged.

Part of #57479; updates the existing PR. Open-PR searches for `57479 in:body` and `reuseport` found no duplicate: #39619 concerns IPv6 utilities, #59521 test flakiness and #52464 DP-engine routing.

Agent catch one thing maybe better:
Why this pr is sometimes slower

Think of 8 checkout counters and a crowd of customers.

Today (shared socket): there is one line, and whichever cashier calls "next" first takes the customer. A fast cashier can grab a whole batch at once, so one counter gets crowded while others sit idle. That is the 503 vs 39 requests per server in the PR.
With [vllm-project/vllm#58278](https://github.com/vllm-project/vllm/pull/58278) (SO_REUSEPORT): there is no line. Each customer goes to a counter picked at random by a hash of their connection. Nobody can grab a batch, but random assignment sometimes sends several customers to the same counter by chance.

Which one is worse depends on how many customers each counter gets:

Many per counter (hundreds): random assignment comes out nearly even, about 10% above average at most. Batch-grabbing can put twice the average on one counter. So [vllm-project/vllm#58278](https://github.com/vllm-project/vllm/pull/58278) wins clearly.
Few per counter (one or two): batch-grabbing barely happens; at most 2 per counter in our test. Random assignment can easily put 3 on one counter. So [vllm-project/vllm#58278](https://github.com/vllm-project/vllm/pull/58278) can be a little slower.

Each Python server renders large responses one at a time, so the total time is set by the busiest server. One extra request there costs about 4.6 s. Our n32 test (32 requests on 32 servers) was the "few per counter" case, which is why it came out about 1–2 s slower.

In one line: [vllm-project/vllm#58278](https://github.com/vllm-project/vllm/pull/58278) stops one server from grabbing too much, at the cost of random clumping. It helps under high load and can lose slightly under low load.

Plan

Keep [vllm-project/vllm#58278](https://github.com/vllm-project/vllm/pull/58278). It fixes a real, large problem under high load and is only +24/−11 lines. Add one sentence to the PR description saying when it helps: many connections per server. Also say that with one or two requests per server it can be slightly slower because of random clumping.
Measure it at our real scale (dp-round12, running). DP8 sends 256 requests to 64 servers, about 4 per server. My prediction is that random and shared will be similar here: a busiest server of about 9–10 vs the measured 7–13. The result will replace the old DP4 numbers in the PR.
The simplest real fix is round-robin, not random. Send request 1 to server 1, request 2 to server 2, and so on. Then no server gets more than one request above the others. The easiest way is for the client to rotate across each server's own port, or to put a least-connections load balancer in front. I'll list this as an open question in the RFC rather than build it now.
It doesn't matter for the RL path. With the compact format each request takes about 0.1 s, so one extra request on a server is invisible. The Rust frontend is a single process and is not affected.
