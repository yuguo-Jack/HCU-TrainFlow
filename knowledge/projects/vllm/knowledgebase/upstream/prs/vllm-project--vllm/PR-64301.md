# [Bugfix] Name the platform in the MXFP4 MoE no-backend error on CUDA

[Upstream PR](https://github.com/vllm-project/vllm/pull/64301) · state: open · merged: False

## Original PR description

## Overview

On CUDA, `quantization="mxfp4"` failed MoE backend selection with a message that
blamed the *deployment configuration* and listed only AMD-only candidates
(AITER / amd-quark `EMULATION`), telling CUDA users to enable ROCm or install
`amd-quark` — neither of which can help. The error now names the platform and
states that no usable MXFP4 MoE backend exists here. Fixes #61854.

## Claims

- The `select_mxfp4_moe_backend()` "no backend" error now names the platform
  (`current_platform.device_type`) instead of implying the user's config is at
  fault.
- The per-backend rejection reasons are preserved, so the message stays
  actionable.
- No behavior change: the same configurations are still rejected; only the
  message improves.

## Validation

Commands run (RTX 4090, CUDA, `.venv` editable install via
`VLLM_USE_PRECOMPILED=1`):

- `python -m ruff check <file>` → All checks passed
- `python -m ruff format --check <file>` → already formatted
- module imports cleanly
- Exercised the exhausted-backend path directly; it now raises
  `quantization="mxfp4" has no usable MoE backend on this platform (cuda) ...`
  instead of the old "supports the deployment configuration" text.

No model-eval needed: this is an error-message-only change with no effect on
model output, accuracy, or serving behavior.

## Details

When the platform has no native MXFP4 MoE kernel the candidate set is AMD-only
by construction, so the previous lead sentence misattributed the cause and the
listed backends were unreachable. The reframed message keeps the candidate list
and per-backend reasons but leads with the real situation and the platform name.
Scope is limited to the general `select_mxfp4_moe_backend()` path from the issue;
`select_deepseek_v4_mxfp4_moe_backend()` carries the same wording and can follow
up if desired.

## Not duplicating an existing PR

Checked `gh pr list --state open --search "61854 in:body"` and the mxfp4/MoE
area: no open PR addresses this error-message issue. (#63349 refactors the MoE
oracle selection but does not change this message; happy to rebase on it.)
