# [Bugfix][MoE] Reuse the FlashInfer CUTLASS MoE workspace across layers

[Upstream PR](https://github.com/vllm-project/vllm/pull/60570) · state: open · merged: False

## Original PR description

## Overview

Reuse the MoE framework's `workspace2` for FlashInfer CUTLASS scratch to avoid large per-call allocations during serving. Addresses [#60471](https://github.com/vllm-project/vllm/issues/60471); this targets a post-startup OOM and does not claim to fix the profiling-time capacity failure in [#47127](https://github.com/vllm-project/vllm/issues/47127).

## Claims

- Reserve CUTLASS scratch during profiling through `workspace_shapes` and reuse the framework's shared allocation.
- Keep scratch disjoint from output; report zero for the unused `workspace13` shape.
- Include gathered DP input, the autotuning minimum and elastic DP limits via `fi_moe_largest_bucket`, with logical dimensions and quantization dtypes matching the kernel.
- Retain compatibility with FlashInfer versions lacking caller-owned CUTLASS workspace support.

## Details

Without caller-owned scratch, FlashInfer allocates and releases large GEMM buffers on each MoE invocation. That transient allocation contributes to memory profiling but must be allocated again during serving, where fragmentation can cause an OOM despite substantial reserved-but-unused memory.

In response to review, `workspace_shapes` now reports CUTLASS scratch in `workspace2`. The framework allocates output storage and scratch simultaneously. `workspace13` reports zero because the backend does not use it; the framework still reserves the output. This removes the separate persistent-resource allocation and lets sequential operations share the framework's scratch storage.

Sizing uses logical hidden/intermediate dimensions, including unpacked NVFP4 K, gated/non-gated N and packed weight dtypes. Size queries are cached. The byte capacity is rounded up to the framework's workspace dtype. Different token counts can produce different scratch offsets after the output reservation; backing storage is shared and captured graph addresses remain stable after locking.

Older FlashInfer versions and size-query failures retain per-call allocation and its original fragmentation risk. Inputs exceeding the profiled capacity follow the framework's normal locked-workspace checks. No scheduler or model-runner changes are required.

This updates the existing PR following review. Draft [#60617](https://github.com/vllm-project/vllm/pull/60617) independently overlaps with the workspace2 approach; no additional PR is being opened. The CUTLASS API comes from [FlashInfer #4057](https://github.com/flashinfer-ai/flashinfer/pull/4057); TRTLLM-gen integration is separate in [#62948](https://github.com/vllm-project/vllm/pull/62948).
