# Use cumem allocator for the KV cache by default

[Upstream PR](https://github.com/vllm-project/vllm/pull/43134) · state: closed · merged: False

## Original PR description

Currently, in order to use MNNVL for KV transfers, users need to set `--enable-cumem-allocator` so the KV cache gets stable physical pages. This PR enables the cumem (CUDA VMM) allocator by default **when a KV Connector is present** and fabric handle support by default (when available and when using cumem) on CUDA and ROCm. 

This PR
  - Uses a `cuMemCreate` probe to check for fabric allocation, because Claude doesn't trust `cuDeviceGetAttribute` as it can report success but then the allocation can later fail when IMEX is improperly configured. This falls back to POSIX file descriptors when fabric handles aren't available.
  - Retains a safety-net fallback: if fabric was probed as available but a real allocation still fails, updates the cache and retries with POSIX FD.

## Code Review

This pull request introduces the `enable_cumem_kv_cache` configuration option, decoupling the CUDA VMM (cumem) allocator from sleep mode and enabling it by default on CUDA and ROCm platforms. It adds a cached fabric handle probe in `csrc/cumem_allocator.cpp` to verify support for `CU_MEM_HANDLE_TYPE_FABRIC` and implements a fallback to POSIX file descriptors. Review feedback identified a critical missing bounds check for the `fabric_support` array in the allocation safety net, which could lead to out-of-bounds memory access. Additionally, a high-severity issue was raised regarding `my_malloc` using an incorrect granularity for fabric handles, which may cause allocation failures on supported systems.

The assumption in this comment that this path is not used for KV cache is incorrect. When `--enable-cumem-kv-cache` is enabled, the KV cache is allocated through the `CuMemAllocator` pool, which routes through `my_malloc`. 

This leads to a significant correctness issue: `my_malloc` calculates `alignedSize` using a granularity that ignores `CU_MEM_HANDLE_TYPE_FABRIC`. On systems where fabric handles are supported (e.g., multi-node NVLink with IMEX), the required granularity is typically much larger (e.g., 512MB) than the standard 2MB granularity. This will cause `cuMemCreate` to fail with `CUDA_ERROR_INVALID_VALUE` in `create_and_map` because the size is not a multiple of the required granularity. The safety net at line 191 does not catch this error code, resulting in a hard failure of the KV cache allocation. `my_malloc` should be updated to use the maximum of all possible granularities if fabric is supported on the device.
