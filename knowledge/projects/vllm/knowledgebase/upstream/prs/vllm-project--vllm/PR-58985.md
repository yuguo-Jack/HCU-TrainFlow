# [Perf][DCP] DeepSeek-V3.2: skip other ranks' top-k slots in FP8 sparse attention on Hopper

[Upstream PR](https://github.com/vllm-project/vllm/pull/58985) · state: open · merged: False

## Original PR description

## Purpose

Fixes #58980. Under DCP, each rank owns about 2048/dcp slots of the indexer's 2048-wide top-k row. `_forward_fp8_kv_mixed_batch` kept the other ranks' slots as `-1` and ran FlashMLA on the full width, so ~(dcp-1)/dcp of every rank's sparse attention went to masked slots, for decode rows and, under DCP, prefill rows alike.

This PR:

- Compacts the rank's slots into a prefix with the existing in-kernel compaction (`compact_valid_to_front`, already used by the trtllm-gen path) and passes their count as `topk_length`.
- Calls FlashMLA with one batch entry per token, since `topk_length` is per batch entry (the layout the DeepSeek-V4 decode path uses). Each call gets a fresh `FlashMLASchedMeta` because the lengths, and so the plan, differ per layer. Tokens are split across calls so that FlashMLA's fp32 split-KV accumulators stay within 256 MiB per call (2048 tokens at 64 heads).
- Neutralizes empty rows by `topk_length == 0` instead of an all-`-1` scan.
- Passes HY V4's attention sink to the new call as well, since its `_fp8_flash_mla_kernel` override is no longer on the DCP path.
- Moves the query head padding into a helper shared by both FP8 wrappers.
- Needs SM90 V3.2 `topk_length` support in FlashMLA (vllm-project/FlashMLA#27). The `GIT_TAG` bump and the two new kernel files in `cmake/external_projects/flashmla.cmake` follow once it merges. That PR now sits on vllm-project/FlashMLA#30, so they go on top of #61371, which moves the pin to that sync. The faster planner in vllm-project/FlashMLA#28 is optional on top.

The attended token set is exactly the same as before; only the kernel's accumulation order changes.

This does not duplicate an open PR: the masked call comes from #46514, written when the SM90 V3.2 kernel did not accept `topk_length`, and no open PR replaces the masking. This stays a draft until vllm-project/FlashMLA#27 merges and #61371 lands; the `GIT_TAG` bump will then point at the merge commit.

## Test Plan

- Unit: `pytest tests/v1/attention/test_sparse_mla_backends.py tests/v1/attention/test_indexer_dcp_localize.py -k "flashmla or FlashMLA or dcp or fp8 or hyv4"`
  - `test_fp8_mixed_batch_dcp_neutralizes_empty_rows` is updated to the new filter return value.
  - New `test_fp8_dcp_topk_length_matches_masked_rows` (GPU) runs `_forward_fp8_kv_mixed_batch` and checks it against the masked call for DCP 2 and 4, KV interleave 1 and 16, and both 64-token blocks and GLM-5.3's 128-token blocks at a 192-row stride (#57169). It covers rows with fewer than top-k candidates, rows the rank owns nothing of, and batches split across several calls.
  - New `test_hyv4_fp8_per_token_kernel_passes_sink` checks that HY V4's sink reaches the new call.
- Accuracy:
  - GSM8K with `tests/evals/gsm8k/gsm8k_eval.py` (1319 questions, 5-shot), without and with MTP (`num_speculative_tokens=3`).
  - Passkey retrieval at 16K-120K tokens.
  - Teacher-forced log-likelihood of 8 natural documents of ~32K tokens.
- Performance, on prompts of random tokens:
  - Decode step time over a 6 s window in which every request is decoding, at 32K and 128K context with 8, 16 and 32 concurrent requests.
  - Prefill wall time of fresh prompts (no prefix-cache hits) with one output token, for 8 x 32K and 2 x 128K prompts.

Setup: 8x H20, vLLM main (a9eafde59, before the rebase onto current main), FlashMLA 0eee43b with the two FlashMLA PRs as they were before vllm-project/FlashMLA#30, DeepSeek-V3.2, `--tensor-parallel-size 8 --decode-context-parallel-size 4 --enable-expert-parallel --kv-cache-dtype fp8_ds_mla --max-num-batched-tokens 16384 --max-num-seqs 64`, CUDA graphs on.

## Test Result

`pre-commit run --files` on the three changed files: all hooks pass.

Since vllm-project/FlashMLA#30 the stock planner takes ~9 us at that size.

| | before | after |
|---|---:|---:|
| GSM8K (5-shot, 1319) | 0.951 | 0.955 |

The per-document NLL differs by at most 0.0017 nats per token, also beyond the first 4K tokens.

GSM8K without MTP, passkey and NLL ran on v0.30.0 with the same backend code; everything else ran on main. The accuracy runs used a FlashMLA build with both FlashMLA PRs; the planner PR's plans are identical, so the outputs are the same as with vllm-project/FlashMLA#27 alone.

- drakosha · comment · 2026-09-29T21:19:37Z · [source](https://github.com/vllm-project/vllm/pull/58985#issuecomment-5899135406)

The masked call came from #46514, written when the SM90 V3.2 kernel did not take `topk_length`, so this is the change we would have wanted. We run that path in production (GLM-5.3, TP4 + DCP4, MTP 3, `fp8_ds_mla`, 4x H200 NVL) and tested the PR on it.

**Kernel.** vllm-project/FlashMLA#27 and #28 cherry-pick cleanly onto vLLM's current pin `0eee43b`. On one H200 NVL we compared the masked call against the compacted call with `topk_length`: a DCP=4 ownership pattern, the tail of each compacted row filled with other valid slots (so a kernel that ignored `topk_length` would diverge), plus a row the rank owns nothing of and a row with under 100 candidates. Max |Δout| is 3.1e-5 and max |Δlse| 1.4e-6 for `h_q` 64 and 128 at every size. Time per call, planning included on the `topk_length` side:

| tokens | h_q=64 | h_q=128 |
|---:|---:|---:|
| 1 | -15% | -11% |
| 8 | -9% | -27% |
| 128 | -44% | -60% |
| 1024 | -59% | -66% |

**End to end.** Nightly `af7f9488c` with this PR and the two FlashMLA PRs, `Inferact/GLM-5.3-NVFP4`, TP4 + DCP4 + EP, MTP 3, `fp8_ds_mla`, `--max-num-batched-tokens 8192`, `--gpu-memory-utilization 0.945`, OffloadingConnector. Main needs two local workarounds to start this model on Hopper, filed as #59306. All three columns are the same image; the masked call is restored behind an env switch, and the middle column caps the per-token chunk at 1024 tokens.

| | masked (before) | this PR, chunk 1024 | this PR as is |
|---|---:|---:|---:|
| decode, 1 request | 109.2 tok/s | 108.8 | 110.8 |
| decode, 8 concurrent | 263.5 tok/s | 280.3 (+6%) | 281.8 (+7%) |
| decode, 32 concurrent | 773.2 tok/s | 826.9 (+7%) | 836.4 (+8%) |
| fresh prefill, 8 x 32K | 4157 tok/s | 5145 (+24%) | 5218 (+26%) |
| fresh prefill, 2 x 128K | 4053 tok/s | 4973 (+23%) | 5064 (+25%) |
| needle at 230K, 3 depths | 3/3 | 3/3 | 3/3 |
| 3 x 544K cold prompts | 3/3, 444 s | 3/3, 371 s | 3/3, 366 s |
| same 3 prompts again, from CPU offload | 3/3, 2.3 s | 3/3, 2.3 s | 3/3, 2.2 s |

One run per point. The prefill gain shows up the same way in all four prefill-bound measurements (both prefill rows, the needle and the cold prompts); the decode differences at 8 and 32 are single samples. That is in line with your H20 numbers, slightly smaller on prefill.

**Chunk size.** In the per-token layout each call allocates split accumulators of `(b + num_sm_parts) * s_q * h_q * d_v * 4` bytes: 1043 MiB at 8192 tokens and 145 MiB at 1024, measured. The 8192 chunk passed our 544K prompts, but on this image the KV cache came out at 914K tokens against 1.2M on our production image, so there was more free memory than we normally run with, and we have lost an engine before to a 2 GiB version of the same allocation (the masked layout at 8192 tokens, fragmented free memory). The 1024 chunk costs nothing measurable in the table above. Bounding the chunk by bytes rather than by the planner's shared-memory limit would make it independent of how much memory is left free.

Separately, and not caused by this PR: on the current pin the masked mixed-batch call allocates the same accumulators again (2 GiB at 8192 tokens, 8 GiB at 32768) because the FlashMLA V4.1 sync dropped the `num_sm_parts > 1` guard that fixed #53413. Filed as #59305.
