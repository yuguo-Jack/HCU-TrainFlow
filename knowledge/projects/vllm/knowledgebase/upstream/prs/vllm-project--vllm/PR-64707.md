# [Bugfix][Spec Decode] Build MRV2 draft attention groups with the allocated kernel block sizes

[Upstream PR](https://github.com/vllm-project/vllm/pull/64707) · state: closed · merged: False

## Original PR description



## Overview

Fixes #64652. In Model Runner V2, the speculator builds its own attention groups. It picked each KV cache group's kernel block size from the drafter's backends alone, so it can disagree with the kernel pages the KV cache was allocated with. When that happens, draft steps 2+ read the wrong KV. This PR passes the runner's `kernel_block_sizes` to the speculator, which is what Model Runner V1 already does for its drafter (`gpu_model_runner.py`, `drafter.initialize_attn_backend(kv_cache_config, kernel_block_sizes)`).

## Claims

- EAGLE draft acceptance after the first position no longer collapses when the drafter shares a KV cache group with target layers that need smaller kernel pages than `--block-size`. On the exact config from #64652 (MiniMax-M3-NVFP4 + EAGLE3, `--block-size 512`), acceptance length goes from 2.11 to 3.09, matching `--block-size 128`.
- Configs where the two choices already agree, including the default backends, are unchanged.
- A new e2e regression test fails on `main` and passes with this change.

## Details

**Root cause**
- Since #37364, the MRV2 speculator calls `init_attn_backend(..., active_layer_names=<draft layers>)` to build metadata only for the groups the drafter uses. #42766 later moved `prepare_kernel_block_sizes` into `init_attn_backend`. So the speculator now votes a kernel block size per group from the drafter's backends only, while the runner votes over all layers and allocates the KV cache with its own result.
- #57169 made each speculator group map its own block tables and KV views from its `kernel_block_size`, so a disagreement between the two now matters.
- In #64652, the EAGLE3 drafter's dense layer shares a KV cache group with MiniMax-M3's sparse attention and indexer layers, whose backends support only 128-token pages. The runner splits 256/512-token blocks into 128-token pages. The speculator's FlashInfer vote keeps 512, so its group has no `kernel_block_size`.
- Draft prefill reuses the target's metadata, which is correct, so position 1 is healthy. Draft decode steps 2+ build metadata through the speculator's groups and read the 128-token pages with an unsplit block table.
- KV writes use flat token slots and stay correct. That is why outputs stay lossless and only acceptance drops.

**Fix.** `init_attn_backend` takes an optional `kernel_block_sizes` and skips the vote when given. `DraftModelSpeculator.set_attn` (with the DFlash and standalone pass-throughs) takes the runner's `self.kernel_block_sizes` and forwards it. The runner's vote already includes the draft layers' backends, so every backend in a group supports the chosen size. `AttentionGroup.create_metadata_builders` still narrows it per backend, the same way it does for the runner's groups.

**CI coverage**
- The test is in `tests/v1/e2e/spec_decode/eagle/test_eagle_correctness.py`. The `-k qwen3_eagle3` filter of the H200 step "Spec Decode Eagle 1: DeepSeek + Qwen" selects it, and that step depends on `vllm/v1/worker/gpu/spec_decode/`.
- It is skipped on SM100, where FlashInfer offers pages up to 1024 tokens for GQA so 128-token blocks are not split, and on non-CUDA platforms.
- It starts two engines with cached models, which adds roughly 3 to 4 minutes to that step.

**Not a duplicate.** No open PR references #64652. #62800 changes FlashInfer's per-layer page vote and padded-page splitting. It does not touch the speculator's separate vote.
