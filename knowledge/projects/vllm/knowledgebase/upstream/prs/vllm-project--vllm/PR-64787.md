# [MoE][DBO] Support DBO with the FlashInfer NVLink two-sided all2all

[Upstream PR](https://github.com/vllm-project/vllm/pull/64787) · state: open · merged: False

## Original PR description



## Overview

Allow `--enable-dbo` with `--all2all-backend=flashinfer_nvlink_two_sided` by running its all2all on the DBO comm stream and keeping the dispatch routing per microbatch.

First slice of #64780. The one-sided backend stays rejected (see Details).

## Claims

- DBO now works with `flashinfer_nvlink_two_sided` (and its `flashinfer_all2allv` alias) on CUDA. Previously the config rejected it.
- Under DBO, dispatch and combine run on the DBO comm stream through `dbo_comm_region`, now shared with the naive DP/EP backend. Without DBO, or during graph capture, the path is unchanged.
- Each microbatch keeps its own `alltoall_info`, so the peer microbatch's dispatch can no longer overwrite the routing that combine needs.

## Validation

Tested commit `5c1d35ff4c` (this PR) on main `e811e502ef`: 2× H200 with NVLink (NV18), driver 570.211.01, PyTorch 2.13.0+cu129, FlashInfer 0.7.0.post1, MRV2 (`VLLM_USE_V2_MODEL_RUNNER=1`).

Model `Qwen/Qwen3-30B-A3B` (BF16), DP2 / EP2 / TP1, `--moe-backend flashinfer_cutlass`, `--enforce-eager`, 64 concurrent greedy completions (48 tokens, `logprobs=1`):

| Run | Result |
| --- | --- |
| DBO on (`--dbo-decode-token-threshold 8 --dbo-prefill-token-threshold 64`) | Served all requests. Per worker, ≥2327 prepare/finalize calls ran inside each of microbatch 0 and 1 with DBO active; 96 ran unsplit |
| DBO on vs DBO off | 59/64 identical token sequences; 2872/2964 (96.9%) common-prefix logprobs bit-identical, p99 \|Δ\| 0.029, max 0.31. The 5 divergences are coherent text at positions 2, 5, 31, 47, 47 |
| DBO off, repeated, vs DBO off | 64/64 identical, max \|Δ\| 0.0 |

DBO-off is deterministic run to run, so the residual difference comes from microbatching, which changes the GEMM shapes. vLLM is not batch-invariant, and in an MoE model a small numeric change can flip a near-tied expert choice. Misrouting would corrupt output in every microbatched step, not leave 97% of logprobs bit-identical. The call counts come from a local probe that counts `prepare`/`finalize` per microbatch; it is not part of this PR.

```bash
vllm serve Qwen/Qwen3-30B-A3B --data-parallel-size 2 --enable-expert-parallel \
  --all2all-backend flashinfer_nvlink_two_sided --moe-backend flashinfer_cutlass \
  --enforce-eager --no-enable-prefix-caching --no-async-scheduling \
  --enable-dbo --dbo-decode-token-threshold 8 --dbo-prefill-token-threshold 64
```

## Details

The FlashInfer two-sided API has no send/receive hook pair, so `supports_async()` stays `False` and the backend follows the synchronous comm-stream pattern the naive DP/EP backend already uses. That helper moves from `naive_dp_ep.py` to `ubatching.dbo_comm_region` unchanged, so both backends share one implementation.

The two microbatches share the manager's workspace. Both issue their kernels on the single DBO comm stream, in the same order on every rank, and `mnnvl_moe_alltoallv*` return freshly allocated tensors, so no output aliases the workspace. Only `alltoall_info` is per microbatch state.

Limitations:

- **Graph capture**: `dbo_comm_region` keeps collectives on the capture stream, so overlap happens only in eager steps, as for the naive backend. With CUDA graphs, DBO stays correct but decode does not overlap.
- **One-sided**: still rejected. Its FlashInfer wrapper returns views into a workspace that FlashInfer caches by geometry, and it raises on a second dispatch before combine. It needs a workspace per microbatch, which the current FlashInfer API does not offer cleanly.
- **Not measured**: performance, CUDA-graph DBO and multi-node MNNVL with this backend.
