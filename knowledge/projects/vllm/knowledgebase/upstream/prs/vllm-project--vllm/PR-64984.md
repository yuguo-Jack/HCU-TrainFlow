# [Bugfix][MM] Keep FlashInfer cu_seqlens halves aligned in Qwen3-VL encoder CUDA graph replay

[Upstream PR](https://github.com/vllm-project/vllm/pull/64984) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

With `mm_encoder_attn_backend=FLASHINFER` and encoder CUDA graphs enabled, Qwen3-VL image replays copy the packed FlashInfer `cu_seqlens` into the capture buffer with `EncoderCudaGraphManager._copy_padded_buffer`. That copy misaligns the q/k/o and v halves of the packed tensor. The vision encoder output then differs between replays of the same image and from eager mode. This registers the existing Qwen2.5-VL helper `_pad_flashinfer_cu_seqlens_buffer` (from #42796) for Qwen3-VL through `EncoderCudaGraphConfig.padding_logics`. SyaOtiLan found the instability and ran the GPU validation below while testing #63809, which adds the same hook for Qwen3-Omni.

## Claims

- Qwen3-VL encoder CUDA graph replays on FLASHINFER keep each half of the packed `cu_seqlens` in its own half of the capture buffer. In the tested cases, replays are identical and match eager mode on the same padded buffers.
- Other attention backends use `_pad_cumulative_seqlens_buffer`, as Qwen2.5-VL does (changed in 3b80be3 after review). It repeats the last offset, so padded entries are zero-length sequences, while the default copy filled them with zeros. The default copy gave no wrong output in the FLASH_ATTN replays of the earlier GPU runs below, and the GPU run of 3b80be3 below shows exact replays on both backends.

## Details

For FlashInfer, `MMEncoderAttention.maybe_recompute_cu_seqlens` returns the q/k/o offsets followed by the v offsets, each half padded to a FlashInfer batch bucket (8, 16, 32 or 64), and `flashinfer_wrapper` splits the tensor at its midpoint. The BF16 and FP8 paths both use this two-half layout, and only BF16 was run on a GPU. Qwen3-VL captures with `cu_seqlens` padded to `max_frames_per_batch` (bucket 16 for 16 frames, 34 entries) and pads image replays to `max_batch_size` (bucket 8 for 2 items, 18 entries). `_copy_padded_buffer` zeroes the capture buffer and copies the 18 entries to its start. The q/k/o half then holds the 9 q/k/o offsets followed by the first 8 v offsets, and the v half holds the last v offset followed by zeros. Offsets count elements of the packed QKV buffer, so a v offset is 3 x tokens x hidden size. For one 196-patch image with an illustrative hidden size of 1152, the first two v offsets are [0, 677376] in eager mode and [677376, 0] after the default copy, so the kernel sees a sequence of negative length. That would explain why replays of the same input differ from each other, since the kernel then reads outside the valid range, but I have not confirmed this inside the kernel.

The fix mirrors the registration Qwen2.5-VL already has for the same key (`cu_seqlens`) and layout. Changing how image replays are padded would touch the shared graph manager and every model that uses it, while the hook keeps the change inside Qwen3-VL. Video replays pad to `max_frames_per_batch`, the same bucket as capture, so they are not affected, and video replays on the base commit were stable in the second run.

This PR and #63809 touch different model files. Both add tests to `tests/v1/cudagraph/test_encoder_cudagraph.py`, and this commit cherry-picks cleanly onto #63809, so they can merge in either order.

Batch size here is the number of sequences in `cu_seqlens`. There are four cases, each run with FLASHINFER and FLASH_ATTN:
- replay batch 2 into capture batch 16, with one image
- replay batch 2 into capture batch 16, with two images of different sizes
- replay batch 9 into capture batch 32
- replay batch 3 into capture batch 8

FlashInfer rounds the batch up to 8, 16, 32 or 64 before packing, so the last case has the same packed length on replay and capture, and the others have a shorter replay tensor.

The metadata is built with `MMEncoderAttention.maybe_recompute_cu_seqlens` on CPU and no attention kernel runs, so these tests need no GPU.
