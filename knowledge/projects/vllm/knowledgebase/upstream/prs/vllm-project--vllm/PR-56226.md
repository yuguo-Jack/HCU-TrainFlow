# [ROCm][Perf] Route softmax MoE top-k, including fused shared-expert sigmoid, through AITER topk_gating

[Upstream PR](https://github.com/vllm-project/vllm/pull/56226) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

On ROCm, softmax MoE routing uses AITER's legacy `topkGatingSoftmax` launcher. This routes `FusedTopKRouter` and the fused-shared-expert router (`VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1`) through `aiter.ops.topk.topk_gating` instead, which keeps selected-mass renormalization in-kernel (ROCm/aiter#4460), has the E=512 `prefill_n` dispatch (ROCm/aiter#5334), and with ROCm/aiter#6306 scores the shared-expert columns with sigmoid in the same launch. `dispatch_topk_softmax_func` decides per launch between `topk_gating` and the legacy `topk_softmax`. This PR makes the selection the default on CDNA3 and CDNA4 (gfx942, gfx950); every other architecture keeps the legacy launcher. gfx950 is the main sweep; gfx942 (MI300-class) was verified more lightly (see the gfx942 section). The blast radius is implicitly limited to Qwens, because based on my search other models won't use the `topk_gating`.

Not a duplicate: searched open PRs for `topk_gating` and `aiter topk softmax`; no other PR routes softmax top-k through `topk_gating`. #57246 fixes the eager `torch.topk` fallback in `fused_topk_bias`, and #55147 fixes the width of the `topk_ids` buffer AITER's kernels write; neither changes which AITER launcher is used.

## Claims

- On the same nightly, with only this PR and ROCm/aiter#6306 added, `topk_gating` is **+0.7% to +1.5% output-throughput geomean per cell** for Flash-Next (E=512, top-10, one shared expert) at TP2 with `VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS` 1 and 0, at three `max-num-batched-tokens` (2048, 4096, 8192), and **+1.3% to +1.9%** for Qwen3-30B-A3B (E=128, top-8) at TP1 in two passes per cell, over the four rows that repeat. Single-stream decode (1k/1k, concurrency 1) is the largest effect: +2.0% to +4.4% in every cell.
- Kernel: for E=512 / top-10 with one shared expert, `topk_gating` is 37–47% faster than `topk_softmax(..., "sigmoid")` at T ≤ 1024 and level at T = 2048–4096 (AITER op test, table below).
- No directional accuracy change: GSM8K on all 9 cells, paired, 134 problems fixed and 126 broken in total (net +8 of 11,871), no cell below p = 0.12. The six cells of the Qwen3-30B rerun are also consistent with noise (no cell below p = 0.39).
- gfx942 (MI300-class): the kernel passes AITER's op test and the vLLM unit tests there with zero routing mismatches, is neutral to slightly positive end to end (+2.0% and +0.45% output-throughput geomean on Qwen3-30B at mbt 4096 and 2048; +1.4% to +4.7% on three Flash-Next-FP8 TP2 rows), and GSM8K is unchanged (no cell below p = 0.16). This is a lighter check than the gfx950 sweep; details below.
- Which launches change: on CDNA3 and CDNA4 (gfx942, gfx950), contiguous gating rows with T ≤ 4096 tokens, and shared experts only with sigmoid scoring and 1, 2, 4 or 8 shared experts. Everything else, and every other GPU architecture, keeps `topk_softmax`. **There is no env var to turn it on/off.**

## Details

**What runs before and after.** Before, every softmax top-k on ROCm with AITER (`FusedTopKRouter`, and the fused-shared-expert router) ran `topk_softmax`, AITER's legacy launcher. After, `dispatch_topk_softmax_func` takes the launch's tensors and shared-expert arguments and returns `rocm_aiter_ops.topk_gating` on CDNA3 and CDNA4 (gfx942, gfx950) when `_aiter_topk_gating_supported` accepts the launch, and `topk_softmax` otherwise (including on every other architecture). `_aiter_topk_gating_supported` accepts contiguous gating rows with at most 4096 tokens; with shared experts it also needs sigmoid scoring, 1, 2, 4 or 8 of them, `topk_weights` and `topk_indices` sharing a row stride, and `topk_weights` wide enough for the shared columns. The shared-expert ids stay as the caller prefilled them, as with the legacy launcher. `_rocm_aiter_topk_gating_impl` is a plain call into `aiter.ops.topk.topk_gating`; the router runs inside the opaque `moe_forward` custom op, so nothing here changes graph capture.

**Why the 4096-token cap.** At E=512 / top-10 the kernel is level with the legacy launcher at T = 2048 and 4096 and was slower at 8K-token prefill chunks in an earlier measurement, so above 4096 the legacy launcher keeps serving. The cap is a named constant in the router, not a magic number.

**Why no env var.** The sweep shows a small positive effect at every shape tested on gfx950 and no reproducible loss, so there is nothing to opt into, and the path is the default under the existing AITER enablement (`VLLM_ROCM_USE_AITER`, `VLLM_ROCM_USE_AITER_MOE`) on gfx942 and gfx950. gfx942 was verified more lightly than gfx950 (see the gfx942 section); the gate is one line (`is_topk_gating_enabled`), so another architecture can be added the same way once it is measured.
