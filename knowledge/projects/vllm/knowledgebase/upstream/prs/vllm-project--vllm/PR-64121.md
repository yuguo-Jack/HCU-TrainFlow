# [ROCm][Perf][GLM-5.3-Flash] MonoKernel: read and write the mxfp4_mla KV cache (on #61662 + #60321)

[Upstream PR](https://github.com/vllm-project/vllm/pull/64121) · state: open · merged: False

## Original PR description

## Overview

Lets the GLM-5.3-Flash MonoKernel (#61662) run with `--kv-cache-dtype mxfp4_mla` (#60321) instead of refusing it. One server then gets the MonoKernel's decode path and MXFP4's KV capacity: 272 bytes per token per sparse-attention layer, against 512 for e4m3 and 1,024 for bf16.

**Stacked on #61662 and #60321**, neither of which has landed, so the diff against main includes both. This PR's own changes are the commits after it: `0e9f2cba22` (read and write the cache, +215 / −40, 9 files), stage tracing (`844f983b60`, `2e29fede12`), and a native scaled-MFMA split that was tried and then removed (`844f983b60`, `44db408d07`, `1848ce41b2`, removed in `a169678b22`; see below), and `f9e677119d`, a fix for #60321's `mxfp4_mla` `do_kv_cache_update` override, which lacked main's new `skip_scale` argument and failed engine startup with any other KV dtype (#60321 now carries the same fix). The commit before `0e9f2cba22` merges #60321's head into #61662's head. `9b53cfbc07` merges #60321's `37b843fc6f`, which moved the `mxfp4_mla` ops into a package, and `ae86a4dc70` points the tests at `vllm.v1.attention.ops.mxfp4_mla.store`; neither merge had conflicts. `ca81241a17` points the MonoKernel's KDA weight packing at main's fused q|k|v `conv1d` (#60991), without which engine startup failed with `no attribute 'q_conv1d'`; #61662 will need the same once it merges a main with #60991. `839e7d12a1` merges #60321's `b7b9232c25`, which resolved a conflict with main in `mla_attention.py`. I'll rebase when either lands.

**Supersedes #62655.** That draft made the same change on #61662 before it was rewritten (files moved to `specialized_decode/`, plus #61662's own e4m3 KV cache). This is the same kernel change ported to the new layout, beside the e4m3 path. #62655 can be closed in favour of this one.

Stays a draft until the performance below is in. The KV accuracy gate is done (below).

## Claims

- **Feature:** `--monokernel` accepts `--kv-cache-dtype mxfp4_mla` on GLM-5.3-Flash. Before this, the config refused it and every step ran vLLM's layers.
- **Same cache bytes as vLLM's path:** the launch quantizes each MLA row as `store_mxfp4_mla` does (E8M0 scale `ceil_pow2(absmax / 6)` per 32 values, E2M1 round to nearest with ties to even, −0 kept), and reads rows back to the same bf16 values as #60321's read path. Prefill (vLLM) and decode (MonoKernel) therefore share one cache.
- **No change for a bf16 or e4m3 cache:** the new code sits behind a compile-time flag. Both caches are uint8, so binding and every launch tell them apart by row width (272 vs 512) and refuse a mismatch.
- **No significant accuracy loss against e4m3 KV:** GSM8K, RULER NIAH to 128K and GPQA-Diamond over six seeds (see KV accuracy gate).
- **No speed claim yet:** see Pending.

## Details

Only the two stages of the sparse-attention launch that touch the MLA latent cache change. Everything between them (q_b, the indexer, top-2048 selection, the MFMAs, W_UV, o_proj) is unchanged.

| Stage | bf16 cache | `mxfp4_mla` cache |
|---|---|---|
| cache write (one CTA a row, one value a thread) | bf16 store | per-32 absmax by xor shuffles, E8M0 scale, E2M1 codes; nibbles packed by shuffles, one dword per 8 lanes, one scale byte per 32 |
| split (64 keys x 8 heads a task) | bf16 MFMAs | rows unpacked to bf16 with `v_cvt_scalef32_pk_bf16_fp4` (E8M0 scale per 32 values), then the same bf16 MFMAs |

**Why there is no native scaled-MFMA split.** A native split was built: QK on `v_mfma_scale_f32_16x16x128_f8f6f4` with FP4 keys and the query as two MXFP8 terms, and PxV with the per-key scales folded into an FP8 P. It was slower, and it fails `test_dsa_layer_mxfp4_kv_cache[2-mixed]` at TP2 (attention check, row 0). It is removed from this PR and kept, unreviewed and without a PR, on [`cursor/glm53-mono-native-split-exp-1ef0`](https://github.com/amd-dlimpus/vllm/tree/cursor/glm53-mono-native-split-exp-1ef0) (`1848ce41b2`, behind `mxfp4_native=True`). Traced TP2 launches (S = rows, µs per launch, `2e29fede12`):

| Split | S=2, 2,049 tokens | S=2, 8K | S=2, 32K | S=4, 2,049 |
|---|---|---|---|---|
| bf16 cache | 126.6 | 127.8 | 133.3 | 188.5 |
| e4m3 cache | 126.9 | 128.9 | 134.9 | 188.4 |
| `mxfp4_mla`, bf16 unpack (this PR) | 126.8 | 127.9 | 133.6 | 187.4 |
| `mxfp4_mla`, native (removed) | 138.2 | 133.1 | 141.3 | 197.0 |

The native split's row phase takes 4x and its QK phase 2.7x as long as the unpack path's. Its PxV re-quantizes P eight times a tile, because the row's scales run along dims, not along the keys PxV reduces over. Per-32-token value scales would fix PxV but change #60321's shared row format, so that is left for a separate change. The unpack path is within 1% of the bf16 and e4m3 caches.

`trace=True` (compile-time, off by default) stamps `s_memrealtime` per CTA at each stage entry and at sub-steps of the top-k selection and the split, for per-stage timing.

`test_dsa_layer_mxfp4_kv_cache` checks the written rows byte for byte against `store_mxfp4_mla` on the reference norm (under 1% of bytes may differ, where the kernel's norm differs from the reference in a last bf16 bit), then the sparse attention over the dequantized cache, the FFN seam, the MoE, and 300 graph replays bit for bit. CPU total: 53 passed, 1 skipped.

**Early timing (not a throughput claim).** One sparse-attention decoder-layer launch, TP4, 2 rows, CUDA graphs:

| Launch | context 512 | context 8K |
|---|---|---|
| FFN only, no attention | 39.0 µs | 39.0 µs |
| sparse attention, bf16 KV | 79.4 µs | 100.8 µs |
| sparse attention, e4m3 KV | 80.3 µs | 101.4 µs |
| sparse attention, `mxfp4_mla` KV | 79.2 µs | 100.1 µs |

The KV dtype moves the launch by about 1%: the latent read is capped at 2,048 rows by `index_topk`. The growth with context doesn't depend on the dtype either. A full sweep (contexts up to 128K, more rows) is pending.

## KV accuracy gate

Quark-MXFP4 weights, TP2 on MI355X, `--monokernel`, 196,608-token context, image `vllm/vllm-openai-rocm:nightly-rocm100-5d35ce3934a7`. The e4m3 and `mxfp4_mla` arms run with `--max-num-seqs 4` and client concurrency 4, so the MonoKernel serves every decode step (it takes steps of up to 4 rows). The native (#64323) and bf16-unpack (`mxfp4d`) arms run at the default `--max-num-seqs 32` and client concurrency 32, so steps exceed 4 rows and go to vLLM's sparse MLA decode. Batch shape changes the outputs, so only arms at the same concurrency are paired.

**GSM8K** (1319 items, greedy, seed 42, paired exact McNemar):

| Pair | Correct | Only the first | Only the second | p |
|---|---|---|---|---|
| e4m3 vs `mxfp4_mla`, C4 (this PR's MonoKernel path) | 1269 vs 1277 | 7 | 15 | 0.134 |
| `mxfp4d` (bf16 unpack) vs native (#64323), C32 | 1274 vs 1282 | 5 | 13 | 0.096 |

**RULER NIAH multikey-2** (50 items each): e4m3 and `mxfp4_mla` at C4 score 50/50 at 32K, 64K and 128K; `mxfp4d` and native at C32 score 50/50 at 32K.

**GPQA-Diamond** (198 questions, official sampling: temperature 1.0, top_p 0.95, 163,840-token cap), e4m3 vs `mxfp4_mla` at C4, six seeds (42-47):

| Seed | e4m3 | `mxfp4_mla` | Only e4m3 | Only `mxfp4_mla` | McNemar p |
|---|---|---|---|---|---|
| 42 | 182 | 178 | 10 | 6 | 0.454 |
| 43 | 182 | 176 | 11 | 5 | 0.210 |
| 44 | 181 | 178 | 9 | 6 | 0.607 |
| 45 | 180 | 182 | 6 | 8 | 0.791 |
| 46 | 178 | 181 | 5 | 8 | 0.581 |
| 47 | 180 | 180 | 6 | 6 | 1.000 |

- **Means:** e4m3 91.16% (SD 0.77) and `mxfp4_mla` 90.49% (SD 1.13); the difference is 0.67 ± 1.80 points.
- **Seed-level test:** paired t over seeds gives t=0.92 with 5 degrees of freedom, p=0.40.
- **Pooled McNemar** (1,188 seed-question pairs): 47 vs 39, p=0.45.
- **Question-clustered** (each seed reuses the same 198 questions, so one value per question):
  - Mean difference 0.67 points with a cluster SE of 0.80; t-test p=0.40.
  - Sign-flip permutation over questions: p=0.46.
  - Cluster bootstrap 95% CI: −0.84 to +2.27 points.
  - Wilcoxon signed-rank: p=0.35.

No arm shows a statistically significant loss against e4m3 KV, and the GPQA-Diamond CI bounds any loss at about 2.3 points. The bf16-unpack and native decode paths are compared in #64323.
