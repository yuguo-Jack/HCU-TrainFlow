# [Bugfix][LoRA] Honor apply_router_weight_on_input in MoE LoRA

[Upstream PR](https://github.com/vllm-project/vllm/pull/62019) · state: open · merged: False

## Original PR description

## Purpose

With `apply_router_weight_on_input` (top-1 routing, e.g. Llama4), `prepare()` multiplies the MoE input by the routing weight and the base GEMMs skip the weight on the output. The MoE LoRA path did not follow that contract, in two places, on every LoRA-capable experts class:

1. **W13 LoRA input missing the weight.** The modular kernel stashed the unscaled `hidden_states` as `lora_ctx.original_hidden_states`, which the W13 LoRA reads (Triton experts on a single rank, quantized TRTLLM path). Fix: stash the input scaled the same way prepare scales it.
2. **W2 LoRA delta weighted a second time.** `apply_w2_lora` always multiplied the delta by `topk_weights` (`add_lora_w2` hardcodes `mul_routed_weight=True`). Fix: `apply_w2_lora(..., mul_routed_weight=...)`; the Triton, Marlin and OAI Triton experts pass `not apply_router_weight_on_input`. Inside, unit weights are used rather than passing `False` to the op, because the op's `mul_routed_weight` also selects the W2 row mapping.

The TRTLLM LoRA experts also passed the weights to FlashInfer's fused MoE finalize, which has no such switch; they now use unit weights when the flag is set (as `DeepGemmExperts` does).

The two errors sit on either side of the activation, so they do not cancel.

## Test Plan

New `tests/lora/test_moe_lora_router_weight_on_input.py`: modular kernel (`MoEPrepareAndFinalizeNoDPEPModular` + `TritonExperts`, BF16) with a real `PunicaWrapperGPU` LoRA context, top-1. With LoRA active, the layer on `(x, w, on_input=True)` must match the layer on `(x * w, ones, on_input=False)`, for both the naive (M=2) and sorted (M=32) LoRA block assignments.

## Test Result

The TRTLLM change is not covered by the new test (needs SM100 + FlashInfer TRTLLM MoE LoRA); it follows the same contract.
