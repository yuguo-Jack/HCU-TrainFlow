# [Bugfix][Frontend] Honor token ID logprob overrides on derender paths

[Upstream PR](https://github.com/vllm-project/vllm/pull/63173) · state: open · merged: False

## Original PR description

## Overview

Fixes #63162: honor the tri-state `return_tokens_as_token_ids` override on both disaggregated derender paths, including generate streaming after merged #63103.

## Claims

- Explicit request true/false overrides the answering server's flag; omitted/null falls back to that server's setting.
- `/render` omits the new context key when null, preserving legacy generate compatibility for default requests. Explicit overrides require an upgraded generate node.
- Full and streaming chat/completion logprobs retain their existing placeholder-byte, decoding and hidden-reasoning contracts; raw tokens and non-derender text behavior remain unchanged.

## Details

The request override was dropped at render serialization, generate used only its server flag, and separate derender always decoded. A nullable `ParseContext` field preserves explicit false; field-level null omission prevents adding an unknown key for older generate nodes. Each answering path resolves the override against its own server default. Placeholder formatting reuses the existing helper; decoded logprobs retain the existing decoder and UTF-8 fallback repair.

The rebase keeps main's streaming processor setup, `_logprob_settings` and `text_mode` behavior. The model regression reuses the module's indirect server fixture, avoiding a nested server while another fixture owns GPU memory. Its Rust capability skip matches the unsupported `/render` route.

Duplicate searches found only this PR and merged #60082/#63103; neither merged feature includes this request-override fix. The affected logprobs docs explain precedence and rolling upgrade behavior. AI assistance was used for implementation, tests, documentation and review preparation.

- claude[bot] · comment · 2026-10-24T04:21:03Z · [source](https://github.com/vllm-project/vllm/pull/63173#discussion_r4365965684)

File: `vllm/entrypoints/scale_out/token_in_token_out/protocol.py` · line None

🔴 During a render-first rolling upgrade, every `output_mode: "derender"` request fails with a 400 on older generate nodes, including requests that never set the flag. The new `return_tokens_as_token_ids` field defaults to `None`, but `/render` always serializes it. Older nodes reject any unknown `parse_context` key in derender mode, including a null value. Fix: omit the field from the `/render` output when it is `None`, for example by building ParseContext with only the explicitly set value. Only requests that actually set the override should then need an upgraded generate node.

<details>
<summary>Why this was flagged</summary>

ServingRender._build_parse_context (vllm/entrypoints/scale_out/render/serving.py:236) always sets `return_tokens_as_token_ids=request.return_tokens_as_token_ids`, which is usually `None`. The `/render` routes return the whole GenerateRequest through `create_json_response` (render/api_router.py:50, :71), so `"return_tokens_as_token_ids": null` appears in every `parse_context`. Older generate nodes parse ParseContext with `extra="allow"`. Their `_check_parse_context_fields` (protocol.py:403) then fails any derender request that has an unknown key. As a result, every derender request routed from an upgraded render node to an older generate node gets a 400, not just ones that use the new override. On the base branch the field is absent and these requests succeed. The doc note in token_in_token_out.md says to upgrade generate nodes first and calls this accepted. It still means a render-first or mixed rollout breaks all derender traffic, and omitting the field when it is null would avoid that cost.

**Verification:** Trigger: render nodes are upgraded before generate nodes, and clients send `output_mode: "derender"`. render/serving.py:236 always sets `return_tokens_as_token_ids`, so every parse_context carries `"return_tokens_as_token_ids": null`. `_check_parse_context_fields` (base protocol.py:402-411) raises, and that becomes a 400. Before this change those requests worked.

</details>
