# [ROCm][Kimi-K3] Enable torch.compile and encoder graph capture for Kimi-K3 Vision Tower

[Upstream PR](https://github.com/vllm-project/vllm/pull/62700) · state: closed · merged: False

## Original PR description

## Summary

This PR enables `torch.compile` and CUDA graph support (`cudagraph_mm_encoder`) for the **MoonshotAI Kimi-K3 Vision Tower** (`MoonViT3dPretrainedModel` + `KimiK25MultiModalProjector`) on AMD ROCm (MI300X/MI350X/MI355X).

### Key Highlights
1. **TorchDynamo compilation with zero graph breaks:**
   - Added `@support_torch_compile(is_encoder=True)` to vision encoder layers and projectors.
   - Registered `packed_qk_rope` custom op with abstract fake implementation, enabling Dynamo tracing with 0 graph breaks.
2. **CUDA graph support (`SupportsEncoderCudaGraph`):**
   - Implemented `SupportsEncoderCudaGraph` for `KimiK3ForConditionalGeneration` on ROCm with configurable token budgets (e.g. `[768, 1040]`).
   - Auto-inferred budgets are capped at 1040 tokens (`get_encoder_cudagraph_budget_range`): above that, graph replay gave no speedup (compute bound) and larger graphs cost KV cache. Inputs above the largest budget use the existing eager path. The shared `EncoderCudaGraphManager` is not modified.
3. **Serving performance: clear gain on the targeted small-image config, neutral elsewhere within run-to-run noise.** Evaluated on AMD MI355X (TP=8), 7-point serving sweep, 3 repetitions per configuration, same base image, same `--gpu-memory-utilization 0.92`:
   - Compile only (B): no measurable change (geomean throughput +0.11% ± 0.72, mean TPOT +0.03% ± 0.87, mean TTFT -0.27% ± 1.25).
   - Compile + encoder CUDA graph (C): on the config this PR targets, 512x512 conc=16, throughput +3.4%, mean TPOT -3.4% and mean TTFT -2.4%, about 3.5 standard errors. Inputs above the largest token budget (1040 here) run the eager encoder (no benefit from graphs there); those points are neutral, so the geomean over the whole sweep is small (throughput +0.94% ± 0.96, mean TPOT -1.13% ± 1.23, mean TTFT -0.16% ± 1.64).
   - No per-point regression clearly outside noise; run-to-run noise is about 0.5-1.5% for throughput, 0.6-2.4% for mean TPOT and 2-7% for median TTFT (see the "Run-to-Run Noise" table below).
   - MMMU: no quality regression for either candidate.
4. **Opt-in:** enabled only via `--compilation-config.compile_mm_encoder` and `cudagraph_mm_encoder`; default eager behavior is not intended to change (see "Scope and Limitations" below).

## Benchmark Results (7-Point Serving Sweep on MI355X, 3 Repetitions)

**Setup.** Configurations A, B and C all use the same base image (`vllm/vllm-openai-rocm:nightly-e68efc685ab1e6f1eda004ced7157e3ca411da2f`; B and C add the changes of this PR), TP=8, `--gpu-memory-utilization 0.92`, on the same dedicated MI355X node. Each configuration was started fresh 3 times, with identical seeds per sweep point, so repetition *i* is paired across configurations. A and B were run in the same interleaved queue (repetitions alternating between configurations); C was run afterwards on the same node (about 10-12 hours later). 96 prompts per point (32 at conc=4, 256 at conc=64). KV cache: A and B 4,253,212 tokens, C 4,225,231 tokens (0.7% less than A because of the encoder graphs).

**Reading the tables.** Cells are mean ± sample stdev over 3 repetitions. Per-point deltas compare the means. GEOMEAN rows are computed per repetition and the deltas are paired per repetition (mean ± stdev of the 3 paired deltas). Seeds are fixed, so the spread reflects run-to-run and server-launch noise on identical request sets, not dataset variance.

| Mean TTFT | 3.39% (8.10%) | 4.05% (7.52%) | 1.32% (2.04%) |
| Median TTFT | 6.96% (16.95%) | 6.53% (10.87%) | 2.38% (3.82%) |
| Mean TPOT | 2.42% (4.31%) | 1.98% (2.99%) | 0.60% (1.01%) |
| Median TPOT | 3.08% (5.92%) | 2.67% (4.50%) | 1.06% (1.88%) |

**What the data supports:**
- B (compile only) is neutral on every metric.
- C (compile + encoder CUDA graph) shows a small gain overall (about one standard deviation of the paired spread).
- The 512x512 conc=16 point is exactly the configuration this PR targets (small images, where encoder kernel-launch overhead dominates and graph capture pays off), and there C improves clearly: throughput +3.4%, mean TPOT -3.4% and mean TTFT -2.4%, about 3.5 standard errors on throughput and on mean TPOT, with all three metrics moving in the same direction.
- Inputs above the largest budget in `encoder_cudagraph_token_budgets` (1040 here) run the eager encoder, because graphs did not improve anything in that regime. This covers large images (e.g. 2048x1600); those points are neutral, as expected, and they are the reason the geomean gain over the whole sweep is small.
- The isolated median-TTFT outlier (B at in=256, +12.6%) is about 2 standard errors with a spread of the same size (± 47 ms) and is within noise.

## Scope and Limitations

- **Shared code.** `vllm/model_executor/layers/rotary_embedding/packed_qk_rope.py` is shared; the new behavior is opt-in and ROCm/Kimi-K3 specific, so the default path is not intended to change. The default path has not been separately benchmarked on main vs this branch, and other models and non-ROCm backends were not tested.
- **Budgets.** Auto-inferred encoder budgets for Kimi-K3 are capped at 1040 tokens; explicit `encoder_cudagraph_token_budgets` are used as given. Inputs above the largest budget use the existing eager path of `EncoderCudaGraphManager`, and steps whose items each fit but together exceed the largest budget are split into several graph replays by the existing packing logic. This sweep does not break down which steps ran graphed vs eager. For auto-inferred budgets the recommended explicit settings are `[768, 1040]` with `encoder_cudagraph_max_vision_items_per_batch: 2`.
- **Statistics.** 3 repetitions per configuration on a single node, with fixed seeds per sweep point: the spread covers run-to-run and server-launch noise, not dataset variance. Differences below roughly 1-2% (throughput, mean TPOT) or 2-7% (median TTFT) are not meaningful.
- **Benchmark scope.** Short runs (96 prompts per point, 32 at conc=4, 256 at conc=64) at `random-output-len 64`, so throughput is prefill/encoder dominated.
