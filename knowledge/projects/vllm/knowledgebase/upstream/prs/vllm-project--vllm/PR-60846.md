# [Kernel] Add opt-in BF16 shared-gate and CUTLASS MoE decode fusions

[Upstream PR](https://github.com/vllm-project/vllm/pull/60846) · state: open · merged: False

## Original PR description

## Overview

Add two opt-in SM120 BF16 decode fusions: the shared-expert scalar projection/sigmoid/scaling chain and CUTLASS FP4 weighted expert reduction. Both preserve the eager path's intermediate BF16 rounding points while removing intermediate tensor traffic and launches.

Related shared-gate work: #43190. The numerical and dispatch differences are documented below; this PR does not claim that the other implementation returns FP32 outputs or is generally incorrect.

## Claims

- `VLLM_FUSE_BF16_SHARED_GATE=1` fuses the Qwen2MoeMLP shared gate, also used by Qwen3-Next. Round the scalar dot-product result to BF16 before sigmoid, and sigmoid to BF16 before scaling the shared output. Restrict integration to a bias-free, unquantized `ReplicatedLinear` gate.
- `VLLM_FUSE_BF16_MOE_REDUCE=1` fuses CUTLASS NVFP4/MXFP4 routing-weight cast, multiplication, top-k reduction, and output write. Preserve BF16 routing-weight and product rounding before FP32 summation; skip multiplication when weights were already applied to inputs.
- Both flags default off. Model dispatch is restricted to contiguous BF16 SM120 inputs, M=1–4 and H=2560; reduction additionally requires topk=1–32. Batch-invariant mode retains the existing paths. FP32 reduction order and sigmoid approximations can still differ, so preserving rounding points is not a bitwise-equivalence guarantee.

## Details

### Relationship to #43190 and intermediate rounding

Both implementations accept BF16 inputs and produce BF16 output. The difference is **when rounding occurs**. In [#43190 at commit 67de337](https://github.com/haofrank/vllm/blob/67de33772e78ac4267900809fc137d4c834c11f7/vllm/model_executor/layers/fused_moe/shared_expert_gate.py#L37-L44), inputs are promoted to FP32, the dot-product result goes directly into sigmoid, and the FP32 sigmoid result multiplies the shared output before the final store. The two eager BF16 materialization points are omitted.

For the BF16 eager reference, `F.linear(x, weight)` returns BF16, sigmoid returns BF16, and multiplication returns BF16. Our fused kernel preserves those rounding points in registers:

```python
gate = tl.sum(x * w, 0).to(tl.bfloat16).to(tl.float32)
scale = (1.0 / (1.0 + tl.exp(-gate))).to(tl.bfloat16).to(tl.float32)
# Store the scaled result to a BF16 output tensor.
```

Casting back to FP32 promotes the rounded value for the next computation; it does not recover the discarded bits. FP32 intermediates can be closer to the real-valued formula, so this is a reference-compatibility distinction rather than a claim of superior model accuracy. Full model evaluation is still required.

There is deliberate overlap in the fused operation. This variant is retained for explicit eager-BF16 intermediate semantics and the measured tiny-token SM120 workload. It uses five 512-feature output tiles per H=2560 row, recomputing the small gate dot product per tile to expose more GPU blocks at M=1–4. #43190 uses one program per row, supports BF16/FP16 and broader token/stride cases, and changes both Qwen2/Qwen3 shared-gate call sites. Here the shared-gate integration is opt-in and confined to the guarded Qwen2MoeMLP path used by Qwen3-Next; no change to Qwen3MoeMLP is claimed. The custom op includes a fake implementation for compiled model execution.

The CUTLASS weighted reduction is a separate operation from #43190. Row unshuffle and shared-expert addition stay separate. #59025 selects a BF16 GEMM backend; #60850 parallelizes CUTLASS FP4 expert-offset setup. Neither is required by these fusions. No scheduler/model-runner change or new host synchronization is introduced.
