# [Kernel] Add opt-in BF16 reduction for CUTLASS FP4 MoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/60846) · state: open · merged: False

## Original PR description

## Purpose

CUTLASS NVFP4/MXFP4 MoE finalization currently casts routing weights, multiplies BF16 expert outputs, sums over top-k, and copies the result into the output buffer. Add an opt-in Triton kernel that performs this chain in one launch and writes the output buffer directly.

- Enable with `VLLM_FUSE_BF16_MOE_REDUCE=1`. Dispatch is limited to contiguous BF16 SM120 decode inputs, `1 <= M <= 4`, hidden size 2560, and `1 <= topk <= 32`; batch-invariant mode retains the existing path.
- Preserve the existing BF16 rounding of routing weights and products before FP32 summation and BF16 output. FP32 reduction ordering can still differ. When weights were applied to the input, skip the weight multiplication.
- Keep row unshuffle and shared-expert addition unchanged.

Duplicate-work check: open PR searches for BF16 shared gates, MoE weighted reduction, and CUTLASS reduction found no PR implementing this CUTLASS finalization change. #43190 addresses the shared-expert sigmoid gate, which is deliberately excluded here. #59025 selects a BF16 GEMM backend and is independent of this reduction.

## Test Plan

```bash
uv run --active --no-project python -m pytest tests/kernels/moe/test_cutlass_moe.py -k bf16_decode_moe_reduce -v
uv run --active --no-project python benchmarks/kernels/benchmark_bf16_moe_reduce.py --m-values 1,4 --json bf16_moe_reduce.json
```

Tests cover masked widths/top-k, FP32 and BF16 routing weights, weights already applied on input, cancellation that exposes intermediate rounding, and CUDA-graph replay after input changes. They extend the existing CUTLASS MoE suite.

For serving validation, compare the same model, request, seed, speculative settings, and autotune tactics with this flag off/on. Evaluate model quality and accepted speculative tokens as well as latency.

## Test Result

The submitting user's original correctness-gated benchmark on an RTX PRO 6000 Blackwell Max-Q (SM120), Torch 2.13.0+cu130, H=2560, topk=10 measured the same reduction kernel as follows. These are medians of seven CUDA-graph batch-average trials with hot data:

| M | Existing chain | Fused reduction | Speedup |
|---|---:|---:|---:|
| 1 | 6.339 us | 1.537 us | 4.125x |
| 4 | 6.533 us | 1.538 us | 4.248x |

In supplied same-machine Qwen3.8-Flash-Next NVFP4 decode profiles, the 48 main-pass reduction chains went from 355.6 us to 71.9 us of summed GPU kernel time. Whole-cycle means were 38.669 ms versus 38.324 ms, but the experiment also enabled a separate shared-gate fusion and had different MTP acceptance and an autotuned projection tactic. This is not an isolated end-to-end gain attributable to this PR.

Local validation: all applicable pre-commit hooks passed on the five changed files, including Ruff, type checks, test tethering, SPDX/import checks and CUDA API policy checks; Python syntax and `git diff --check` also passed. CUDA pytest and model-quality evaluation of this upstream adaptation remain pending: the local development host has no CUDA toolchain/GPU PyTorch environment. The draft must not be treated as a completed model-accuracy validation.
