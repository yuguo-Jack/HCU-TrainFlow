# [Bugfix][Quantization] Keep the online MXFP8 MoE kernel across  weight reloads

[Upstream PR](https://github.com/vllm-project/vllm/pull/62406) · state: open · merged: False

## Original PR description



## Overview

Online MXFP8 MoE (`quantization="mxfp8"`) builds a new MoE kernel on every `reload_weights`, while decode keeps replaying CUDA graphs captured against the startup kernel. After the first reload, decode reads tensors freed with the old kernel and samples sporadic garbage tokens. This keeps the startup kernel on reload and refreshes its quant config in place.

Same class of bug as #61304 (ModelOpt NVFP4 MoE, behind `VLLM_RELOAD_KEEP_MOE_KERNEL`), which uses the same in-place refresh.

## Claims

- After `reload_weights`, online MXFP8 MoE decode with CUDA graphs matches eager prefill again, instead of sampling occasional tokens that prefill scores at logprob -10 to -30.
- Reload still serves the new weights.

## Validation

All results below are on DeepSeek-V4-Flash, TP8 + EP, `FLASHINFER_TRTLLM` MXFP8 MoE, on 8x B300, with **vLLM 0.31.0** plus an equivalent patch that keeps the startup kernel on reload but doesn't refresh the quant config. **This exact diff has not yet been run on `main`. That run is pending, and the PR stays a draft until it's done.**

**Decode vs prefill self-check.** Generate, then re-score the same tokens with `prompt_logprobs`, and compare (KL of decode vs prefill logprobs):

| | fresh server | after reload |
|---|---|---|
| CUDA graphs, unpatched | 0.0027 | 0.0065 (garbage tokens) |
| `enforce_eager`, unpatched | 0.0026 | 0.0027 |
| CUDA graphs, patched | 0.0026 | 0.0028 (0.0025 after 10 reloads) |

**Reload serves the new weights.** Zero layer 2's routed-expert `w2`, then compare two servers:
- **Reloaded:** booted on the base weights, then given the zeroed checkpoint through `reload_weights`.
- **Fresh:** booted directly on the zeroed checkpoint.

| | KL |
|---|---|
| base-model tokens: reloaded server vs base | 0.0065 |
| base-model tokens: fresh-zeroed server vs base | 0.0066 |
| reloaded server's tokens: fresh-zeroed vs reloaded | 0.0026 (two servers on identical weights: ~0.0027) |

**In RL with weight updates every step:** over 60 steps, the trainer-vs-inference logprob KL mean went from 0.0437 to 0.0038.

**CI coverage gap.** `test_online_quantize_reload` covers `mxfp8` reload on a dense model only. Its MoE case (`DeepSeek-V3-debug`) is `xfail` because MXFP8 doesn't support MLA, and the test runs without CUDA-graph replay checks. So CI doesn't exercise this path, and I haven't added a test.

## Details

**Root cause.**
1. `Mxfp8OnlineMoEMethod._setup_kernel` runs from `process_weights_after_loading` on every reload.
2. Layerwise reload copies the re-processed parameters back into their original storage (`_copy_and_restore_kernel_tensors`), so pointers to layer parameters stay valid.
3. `_setup_kernel` then replaces `self.moe_quant_config` and `self.moe_kernel` with new objects. The old kernel is dropped, along with any tensor only it referenced.
4. The CUDA graphs captured at startup still point at those tensors.
5. Eager mode is unaffected, which is how the bug was isolated.

**Fix.** If a kernel already exists, i.e. on a reload:
- Build the new quant config.
- Copy each of its tensors into the matching tensor of the existing quant config.
- Keep the existing kernel.

Layer parameters are refreshed by the layerwise copy as before. The copy raises an error if a quant-config tensor changes shape or dtype, rather than silently serving stale values.

**Overlap with #61304.** `_refresh_moe_quant_config_inplace` is the same helper #61304 adds to `modelopt.py`. If both land, it should move to `fused_moe/config.py` and be shared. Unlike #61304, this applies unconditionally: online quantization exists to requantize on reload, and rebuilding the kernel is never correct under captured graphs.
