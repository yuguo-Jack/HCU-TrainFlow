# [Bugfix] Don't int-sort attention-type names in --kv-cache-dtype-skip-layers for packed KV dtypes

[Upstream PR](https://github.com/vllm-project/vllm/pull/60364) · state: closed · merged: True

## Original PR description



## Overview

`--kv-cache-dtype-skip-layers` accepts layer indices or attention type names like `sliding_window`, but with a `turboquant_*` or `ultraquant_4bit` cache dtype, `create_engine_config` sorts the merged skip list with `key=int` and crashes on any name.

## Claims

- `--kv-cache-dtype turboquant_4bit_nc --kv-cache-dtype-skip-layers sliding_window` (and the same with `ultraquant_4bit`) no longer fails with `ValueError: invalid literal for int() with base 10: 'sliding_window'`.
- Index-only skip lists hold the same layers as before. They are now ordered as strings (`"10"` before `"5"`), so a list with two-digit indices gets a different `CacheConfig` hash once, i.e. one compile-cache miss after upgrading.

## Validation

Reproduced at config level, platform forced to CPU (no kernels involved; I don't have a CUDA box):

```python
EngineArgs(model="facebook/opt-125m", kv_cache_dtype="turboquant_4bit_nc",
           kv_cache_dtype_skip_layers=["sliding_window", "5"]).create_engine_config()
# main:        ValueError: invalid literal for int() with base 10: 'sliding_window'
# this branch: skip list ['0', '1', '10', '11', '5', 'sliding_window']
```

Same result with `ultraquant_4bit`. No test added: per review, the field is typed `list[str]`, so the int sort key shouldn't come back. `pre-commit` passes on the changed file.

End to end, I hit this on ROCm (gfx1201) with a hybrid GDN target and a DFlash2 drafter: TurboQuant gets picked for the target's full-attention layers, and the drafter's sliding-window layers have no TurboQuant backend, so skipping `sliding_window` is the documented way out. With the same fix applied to our ROCm build, the engine gets past config.

## Details

The user's list can hold names, but the merge with TurboQuant's boundary layers (always indices) sorted everything as ints. Now the merged list is sorted as strings. The sort stays because the list is a `CacheConfig.compute_hash()` factor and is built from a set, so without it the order (and the hash) would vary with `PYTHONHASHSEED`. Order doesn't change behaviour, since `Attention` matches entries as strings.

Not a duplicate: no open PR touches this sort. #54599 mentions the `sliding_window` case not working with TurboQuant "for a different reason" but doesn't change it, and #59178 / #60252 / #60023 touch the same flag in other places.

AI assistance (Claude) was used to write this change. I reviewed the diff and ran the reproduction above.
