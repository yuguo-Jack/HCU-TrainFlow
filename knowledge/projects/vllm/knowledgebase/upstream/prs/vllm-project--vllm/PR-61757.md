# [Bugfix][Frontend] Leave the final stop token out of chat derender text

[Upstream PR](https://github.com/vllm-project/vllm/pull/61757) · state: closed · merged: True

## Original PR description



## Overview

Partially fixes #57052: the chat token-stop part (EOS and `stop_token_ids`). Completion derender and stop strings remain open there.

Chat derender now leaves the stop token that finished generation out of the decoded text, the way the engine's detokenizer does. This fixes `test_parity_reasoning` and `test_stream_parity_reasoning` in `(H200 MIG 35GB) Entrypoints Integration (API Server)`, which fail on main because derender returns `...\boxed{391}\n\]<｜end▁of▁sentence｜>` where the coupled server returns `...\boxed{391}\n\]`. Examples: https://buildkite.com/vllm/ci/builds/95020#01a13dbe-64d7-4310-bfe8-807fb58fd14b (batch) and https://buildkite.com/vllm/ci/builds/94727#01a13986-c733-4d38-ad14-feb389277a93 (stream).

## Claims

- Chat derender (batch, plain stream and parser stream) no longer puts the EOS / stop-token text into `content` when `finish_reason` is `stop`. This matches the coupled `/v1/chat/completions` output.
- `include_stop_str_in_output=true` still keeps it, and `ignore_eos` turns off the EOS check, both as in the engine.
- The returned `token_ids` and the ids passed to the parser are unchanged and still include the stop token, as on the coupled path.

## Details

**Root cause.** When generation stops on a stop token, the engine's `IncrementalDetokenizer.update` drops that token before decoding unless `include_stop_str_in_output` is set (`vllm/v1/engine/detokenizer.py`). Derender received the same `token_ids`, including the stop token, and decoded all of them. Without a parser this was hidden, because `skip_special_tokens=True` drops the EOS anyway. With a reasoning or tool parser, derender decodes with `skip_special_tokens=False` so the parser can see its markers, and the EOS text ends up in `content`. Each test fails only on runs whose greedy, 256-token generation ends on EOS rather than at the length limit. On main that is a minority of runs, so it looks like a flake.

**Fix.** `_text_token_ids` follows the engine's `stop_terminated` using the choice's `stop_reason` (passed through since #60251): `finish_reason == "stop"` with a non-string `stop_reason` means a token stopped generation. `None` means EOS and an int means a `stop_token_ids` entry. A string `stop_reason` (stop string) never drops a token, and neither does `include_stop_str_in_output`. As a guard, because `finish_reason` defaults to `"stop"` when a client sends neither field, the last id must actually be that stop token: equal to the int `stop_reason`, or one of the model's EOS ids (tokenizer and `generation_config`) when it is `None`. This applies at the three chat decode sites only; the ids returned to the client and to the parser are untouched.

**Relation to #59510.** #59510 (@pOpO1-9, "Hide stop text on batch derender") proposes similar helpers, aimed mainly at batch derender plus stop strings. It has had no review since Oct 7 and now conflicts with main. This PR is the minimal fix for the chat paths that are failing on main today. Completion derender and stop strings are left to #59510. If a reviewer prefers to land #59510 instead, this can be closed.

Not a duplicate otherwise: I searched open PRs for derender EOS, stop-token and `test_parity_reasoning` fixes; #59510 is the only related one.
