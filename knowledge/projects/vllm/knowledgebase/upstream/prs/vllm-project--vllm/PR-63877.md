# [Bugfix][CI][MoE] Build modular-kernel test weight scales from per_out_ch_quant

[Upstream PR](https://github.com/vllm-project/vllm/pull/63877) · state: closed · merged: False

## Original PR description

## Overview

`WeightTensors.make()` took the weight-scale layout from `per_act_token_quant` instead of `per_out_ch_quant`, so modular-kernel test configs where the two differ were built with the wrong weight scales. This is what made the MI300 MoE Kernels shard 2 test fail on #58570. It was reported as flaky, but it fails deterministically.

## Claims

- Each config now gets the weight-scale layout it declares: "per-tensor weights + per-token activations" gets per-tensor scales (it got per-channel ones), and "per-channel weights + per-tensor activations" gets per-channel ones.
- The AITER padding tests (FP8 from #59333, MXFP4 from #62996) now use `WeightTensors.make()`. Their `_make_padding_matrix_weights()` existed only to work around this and is removed.

## Validation

CI's shard 2 command on MI300X in #58570's CI image ([#97294](https://buildkite.com/vllm/ci/builds/97294#01a17888-b45c-4264-9ea5-8278b7c641b3)):

    cd /vllm-workspace/tests
    pytest -v -s kernels/moe --ignore=kernels/moe/test_modular_oai_triton_moe.py --shard-id=1 --num-shards=5

| Run | `dtype3` |
|---|---|
| As built (#58570 kernel, current harness) | fails, same numbers as CI: 3 elements, `0.037109375` at `(11, 1032)` |
| With this PR | passes |
| #58570's kernel change reverted | passes |

With `main`'s kernel and this PR:
- No AITER: all 5 single-GPU cases pass; `dtype3` passes for 100/100 weight seeds (max diff 0.0024, atol 0.03).
- `VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_MOE=1`: affected single-GPU cases and `test_aiter_moe_padding_matrix`: 14 passed, 8 skipped (existing skips).
- Multi-GPU (DeepEP, MoRI): the 5 affected cases that run pass; the 2 AITER ones hit the existing #57029 skip.

Not run locally: NVIDIA, and the MXFP4 padding tests (MI355/gfx950 only). CI covers both.

## Details

On `main`, the per-token Triton path reads weight scales according to the scale tensor's shape, so the mislabeled config still passed. #58570 makes the kernel follow `per_out_ch_quant`, so it read one scale per expert from the per-channel tensor, and the output was ~25% off. The failure is deterministic: the weights are drawn unseeded in the parent pytest process, so they depend only on the tests that run earlier in the shard. Same shard, same weights, same failure.

Not a duplicate: #58570 changes the kernel, not the test harness, and #59333 worked around the same coupling only inside the padding tests.
