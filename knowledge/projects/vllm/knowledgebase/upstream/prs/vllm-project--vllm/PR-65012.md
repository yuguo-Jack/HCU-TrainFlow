# [Bugfix][Kernel] Check pointer alignment before vectorizing activation kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/65012) · state: open · merged: False

## Original PR description

## Overview

The activation launchers in `csrc/activation_kernels.cu` (`silu_and_mul`, `gelu_and_mul`, `gelu_tanh_and_mul`, `fatrelu_and_mul`, `gelu_fast`, ...) pick the 128/256-bit vector path from the row width alone. A contiguous input or output whose data pointer is not vector-aligned, such as a view at an odd storage offset, passes that check and then fails with `CUDA error: misaligned address`, which leaves the CUDA context unusable. This PR also checks both data pointers and falls back to the existing scalar path when either is unaligned.

## Claims

- Inputs or outputs at an unaligned storage offset now produce correct results instead of a sticky CUDA error, for all ops built on the three launch macros.
- Aligned tensors take the same path as before; aligned timings are unchanged.

## Validation

H100 (SM90) on this commit's base, `5d55ef1590`, and B200 (SM100) on `e0d00e4b8e`, CUDA 13.0, torch 2.14. The patched `activation_kernels.cu` was built on its own and swapped in for the 10 ops served by the three macros. The failure on main also reproduces on an L4 (SM89) for `silu_and_mul`, `gelu_and_mul` and `gelu_tanh_and_mul`.

```bash
pytest tests/kernels/core/test_activation.py -k misaligned_data_ptr
# main:    fails with Xid 13, "Misaligned Address" (H100 at 7 tokens, B200 at 256 tokens, the 256-bit path)
# this PR: passes, included in the run below

pytest tests/kernels/core/test_activation.py
# this PR: 558 passed on H100 and on B200
```

`silu_and_mul`, bf16, `triton.testing.do_bench_cudagraph`, µs:

| GPU, tokens × d | aligned, main | aligned, this PR | unaligned, this PR (scalar path) |
|---|---|---|---|
| H100, 16 × 6912 | 2.29 | 2.29 | 3.43 |
| H100, 2048 × 6912 | 30.14 | 30.14 | 45.56 |
| H100, 2048 × 13824 | 58.18 | 58.17 | 86.47 |
| B200, 16 × 6912 | 2.34 | 2.54 | 4.12 |
| B200, 2048 × 6912 | 16.42 | 16.41 | 34.12 |
| B200, 2048 × 13824 | 46.21 | 46.21 | 74.57 |

Unaligned output equals aligned main's output in all rows. The fix adds only host-side pointer checks. I read the one B200 16-token difference as noise, from a single run.

## Details

- **Root cause.** `LAUNCH_ACTIVATION_GATE_KERNEL`, `LAUNCH_ACTIVATION_GATE_KERNEL_WITH_PARAM` and `LAUNCH_ACTIVATION_KERNEL` set `use_vec = d % vec_size == 0`. The vector loads and stores start at each row's base pointer, so they also need the tensor's data pointer aligned to the vector width (16 bytes, or 32 on the Blackwell 256-bit path). The interleaved `swigluoai_and_mul` kernel in the same file already checks this (`is_16byte_aligned(in_ptr)`).
- **Fix.** A host-side `is_vec_aligned(tensor, support_vec)` check on `input` and `out` in all three macros. Each row starts at a multiple of `d` (or `2 * d`) elements, so with `d % vec_size == 0` an aligned base pointer keeps every row aligned. Nothing changes on device.
- **Test.** `test_activation_misaligned_data_ptr` covers one op per macro (`silu_and_mul`, `fatrelu_and_mul`, `gelu_fast`), with the input or the output shifted by one element, in fp16, bf16 and fp32, at 7 and 256 tokens (the 256-bit path on SM100+), against `forward_native`.
- **Scope.** No current model path is known to produce such tensors (layer outputs and MoE workspaces start at offset 0); this removes a crash for any caller that passes a view, such as custom ops or plugins.
- **No duplicate.** No open issue or PR covers this.
