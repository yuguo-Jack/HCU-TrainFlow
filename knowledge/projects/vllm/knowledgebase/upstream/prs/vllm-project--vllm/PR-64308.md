# [Rust][Benchmark] Record ramp-up runs in the result JSON and filename

[Upstream PR](https://github.com/vllm-project/vllm/pull/64308) · state: closed · merged: True

## Original PR description

## Purpose

Fixes #64226.

With `--ramp-up-strategy`, the Rust `vllm-bench` sends requests on the ramp-up schedule but saves the result as if it were a fixed-rate run: the file is named `<label>-infqps-...json`, and the result JSON has no ramp-up information, so it can't be told apart from a burst run. `--request-rate` given alongside ramp-up is ignored by the schedule but still ends up in the filename and `request_rate`.

This PR matches Python `vllm bench serve`:

- **Filename** (`compute_result_filename`): `<label>-ramp-up-<strategy>-<start>qps-<end>qps[-concurrencyN]-<model>-<dt>.json`.
- **Result JSON** (`build_result_json`): `ramp_up_strategy`, `ramp_up_start_rps`, `ramp_up_end_rps`.
- **`rps_change_events`**: the start rate, then every integer RPS reached, each with the local timestamp of the first request sent at that rate. Python records these in its dispatch generator. Here the schedule is precomputed, so `RequestSchedule::rps_change_offsets` derives them from the per-request `rates` that `compute_schedule` already returned (previously `#[allow(dead_code)]`), offset from the benchmark start.
- **Validation** (`parse_ramp_up`): reject `--request-rate` and `--sweep-request-rate` with ramp-up, and a start RPS above the end RPS, as Python does. Same reasoning as the existing self-timed check in `config.rs`: a rate that never ran shouldn't label the result.

One difference from Python remains: Python parses the ramp-up RPS as `int`, while the Rust CLI takes `f64`, so the JSON has `2.0` where Python has `2`. Both parse to the same number; the filename is identical (`2qps`).

## Not a duplicate

No open issue or PR covers Rust bench ramp-up results or `rps_change_events`. #42427 changes Python ramp-up validation only.

## Test Plan

New tests:
- `config::tests::test_ramp_up_result_filename`: ramp-up config with `--max-concurrency 8` gives `openai-ramp-up-linear-2qps-10qps-concurrency8-model-<dt>.json`.
- `config::tests::test_ramp_up_rejects_request_rate_flags`: `--request-rate` and `--sweep-request-rate` are rejected with ramp-up.
- `config::tests::test_ramp_up_rejects_start_above_end`.
- `output::json::tests::test_insert_ramp_up`: the three ramp-up fields.
- `rate_control::tests::test_rps_change_offsets`: start rate at 0, one step per integer rate, and rates a single request jumps over share its delay.
