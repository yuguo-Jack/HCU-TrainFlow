# Reduce per-call CPU overhead in OperationFuser

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3767) · state: open · merged: False

## Original PR description

# Description

Reduce steady-state Python overhead in `OperationFuser` for fused basic operations with real caller-supplied extra tensors. The fuser now records the fixed parameter and public-extra-input routing at construction, so plan selection checks the flat caller arguments directly. It also delays per-call extra-input slot construction until forward and reuses the `torch.compiler.is_compiling()` result within each call. Static routing metadata lives on the fuser; invocation-specific tensors, contexts, and the selected backward plan remain on the autograd context so overlapping graphs work independently.

This PR keeps the original per-call extra-input and extra-output slot lists. It does not cache mutable tensor-bearing lists across calls.

## Type of change

- [x] Code refactoring

## Changes

- Precompute grad-input source routes in `OperationFuser.__init__` and avoid constructing per-op input collections during fusion plan selection.
- Avoid an extra per-call slot-list construction in `OperationFuser.__call__`; populate slots once in autograd forward.
- Read immutable routing metadata from the fuser in backward, while retaining per-invocation state on `func_ctx`.
- Check compilation state once per call path.
- Cover different backward boundaries with overlapping live autograd graphs; update the internal plan-selection tests for the flat public extra-input argument format.

## CPU benchmark

Paired runs compare `nvidia_origin/main` at `9b7e959fe47137e4bb1abf2294eb145c763f40c2` with this PR.

The benchmark calls 1, 3, or 9 empty basic operations on a 1×16 BF16 CUDA tensor. It supplies **real public extra input tensors** (1, 1, and 3 respectively), with `requires_grad=True`; the 3- and 9-op cases fuse empty triplets. Forward + backward includes `fuser(...)`, `.backward()`, and leaf-grad reset. Each case runs in a fresh Python process, with 5,000 warmups and 3 timed batches of 10,000 iterations; two pre/post passes provide six samples per revision. Values below are medians of those six host wall-time samples in µs/iteration. CUDA is synchronized around each timed batch, not each iteration.

| Basic ops | Public extra tensors | Pre-PR F+B (µs) | Post-PR F+B (µs) | Change |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 71.85 | 68.56 | −3.29 µs (−4.6%) |
| 3 | 1 | 79.52 | 74.34 | −5.19 µs (−6.5%) |
| 9 | 3 | 105.36 | 98.43 | −6.94 µs (−6.6%) |

Pass medians (pre → post, µs) expose run-to-run variation: 1 op: 71.38 → 67.72 and 72.31 → 70.05; 3 ops: 77.37 → 73.76 and 81.22 → 74.67; 9 ops: 105.32 → 95.96 and 108.69 → 100.35.

No-grad forward was measured in one paired pass with the same warmup and timed batch sizes; each entry is the median of three samples:

| Basic ops | Pre-PR forward (µs) | Post-PR forward (µs) | Change |
| ---: | ---: | ---: | ---: |
| 1 | 4.86 | 4.17 | −14.2% |
| 3 | 6.50 | 5.64 | −13.2% |
| 9 | 14.99 | 12.68 | −15.4% |

These are end-to-end host-side timings for the empty-op harness, including PyTorch autograd overhead and a leaf-gradient device copy in F+B. They are not TE GPU kernel timings.
