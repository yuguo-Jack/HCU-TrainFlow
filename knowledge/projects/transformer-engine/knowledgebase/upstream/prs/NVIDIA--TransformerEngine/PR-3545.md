# [PyTorch] Fix distributed BF16 weights and trim NVFP4 saved state in the fused grouped MLP

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3545) · state: closed · merged: True

## Original PR description

# Description

Two fixes for the CuTeDSL fused grouped MLP (`ops.fused.GroupedMLP_CuTeGEMM*`),
both surfaced while running Megatron-Core MoE experts with GTP-sharded weights
and per-module quantization recipes.

1. The op assumed gathered distributed weights were already quantized: forward
   quantized the shards before the gather, and backward read `_columnwise_data`
   or the NVFP4 amax straight off the gathered tensor. That fails for a module
   whose per-module recipe does not create native-quantized params, e.g. MXFP8
   experts under a global NVFP4 recipe, whose BF16 shards gather as BF16.
   Gather first, then quantize whatever is still unquantized with the op's
   per-expert weight quantizers, mirroring `module/linear.py`. Native-quantized
   shards pass through unchanged. The per-expert weight quantizers are saved on
   the forward context and used in backward, so a later forward under a
   different (or no) recipe cannot reset them out from under an earlier
   backward. The quantizer lists are built lazily, only on the discrete-weight
   and distributed-weight paths that consume them.
2. The save path kept NVFP4 rowwise input data and scales that no wgrad path
   reads (the cuDNN grouped kernel, the single-group dense GEMM and the generic
   grouped GEMM fallback all take the columnwise tiles). Prune them as already
   done for MXFP8. Per decoder expert layer of a Nemotron hybrid proxy
   (83k tokens, hidden 3072) this removes ~136 MiB from the ~1.9 GiB saved set
   with unchanged numerics.

The related `Linear` / `GroupedLinear` / `LayerNormLinear` loss of the
`DistributedWeight` subclass under `saved_tensors_hooks` is fixed generically
in `prepare_for_saving` by #3730 and is intentionally not part of this PR.

## Changes

- `ops/fused/grouped_mlp.py`: gather distributed weights before quantizing;
  quantize re-gathered BF16 weights with the per-expert quantizers, built
  lazily and saved on the FC1/FC2 contexts for backward; move the FC2 backward
  re-gather ahead of the NVFP4 amax computation; drop NVFP4 rowwise input data
  and scales from the saved state.
- `tests/pytorch/test_grouped_mlp.py`:
  - `TestGroupedMLPDistributedWeight`: fused grouped MLP with BF16 and MXFP8
    fake distributed weights under per-module MXFP8, optionally inside a global
    NVFP4 autocast, bit-exact against a plain reference up to the fake hooks'
    scales; a pass-through unit check for already-quantized gathered weights;
    and a backward after a second forward under no recipe or NVFP4.
  - `TestGroupedMLPFusedOp.test_nvfp4_saves_columnwise_inputs_only`: exactly
    one FP4 data and one scale tensor saved per quantized input on the fused
    NVFP4 path, for group sizes 1 and 4. The single-group dense path saves a
    `GroupedTensor` wrapper, whose buffers are inspected directly.

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **Second backward loses distributed weights**

When `GroupedLinear` runs under saved-tensor hooks and its output is backpropagated twice with `retain_graph=True`, the first backward clears `ctx.dist_weights` here; the split backward path clears it too. On the second backward, the saved weights unpack as plain tensors, so the distributed-weight path is lost again. Backward can then fail when it tries to use the unsaved gathered weights, or skip distributed gradient finalization. Keep the original weights available for each backward while the graph is retained.

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **Later forwards break earlier backward**

`_quantize_unquantized_weights` reads quantizers from the live `op`, including during backward. If a distributed BF16-weight MLP runs under MXFP8, then runs again without quantization before the first backward, the second forward clears `op._quantizers`. The earlier backward then gets `None` here and fails at `set_usage`. Switching to another quantized recipe can instead supply the wrong weight format.

Save all per-expert weight quantizers on the forward context and use those when quantizing gathered weights in backward.
