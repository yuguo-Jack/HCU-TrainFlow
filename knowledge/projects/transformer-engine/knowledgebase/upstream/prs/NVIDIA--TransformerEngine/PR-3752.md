# Reduce CPU overhead in graph-safe GroupedLinear/GroupedMLP

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3752) · state: open · merged: False

## Original PR description

# Description

Reduce CPU host overhead in graph-safe GroupedLinear and grouped MLP training steps. The measured CUDA kernels and their total durations are unchanged.

## Type of change

- [x] Code refactoring
- [x] Performance improvement

## Changes

- Read Python tensor attributes once in the C++ type converters, including grouped tensor metadata. Keep the newly added optional row-scaled NVFP4 field from `main`.
- Remove unnecessary flattening when wrapping contiguous grouped input, output, and gradient buffers. Flatten only at the point where `split_into_quantized_tensors` slices storage; add coverage for multidimensional contiguous buffers.
- Use the cached device capability and a direct quantizer check in grouped GEMM setup.
- Remove redundant scale reshapes from the native scaled activation path.

## Performance

CPU host step time, forward plus backward, lower is better. `main` is `dd628d3a11`; `PR` is `96dd4c060e`. Values are medians of six 400-step blocks across two interleaved passes (`main`, PR, `main`, PR) on the same GB200/Grace node, pinned to CPU 16. Each process had 60 warmup steps. The workload uses eight experts, 256 tokens per expert, hidden size 128, discrete expert weights, and no bias. BF16 uses BF16 activations and weights without FP8 autocast; MXFP8 uses BF16 activations with the MXFP8 block-scaling recipe. Timings exclude a per-step CUDA synchronization. The fused MXFP8 MLP uses split alignment 256; the other `Sequential` cases use 128.

These measurements predate the merge of `main` into PR head `08008c8445` on 2026-11-02. The merged head has not been remeasured because dlcluster was unreachable.

- zhongbozhu · comment · 2026-10-31T00:20:23Z · [source](https://github.com/NVIDIA/TransformerEngine/pull/3752#discussion_r4429563817)

File: `transformer_engine/pytorch/cpp_extensions/gemm.py` · line 1260

Honestly at this point, I don't think anyone wants to use `use_split_accumulator=False` even for per-tensor recipe. 

Setting `use_split_accumulator=False` was a legacy toggle used back in the delayed scaling days or per-tensor current scaling, and we sometimes tuned it off and trade GEMM-K accumulation precision for more GEMM perf. But I don't think anyone is gonna do that anymore, plus that everyone using fp8 recipe on Hopper uses blockwise and they expect fp32 accumulation precision. 

`use_split_accumulator=False` is also Hopper-only, it's not applicable for Blackwell anymore. 

I would suggest we remove everything about `use_split_accumulator=False` because it delivers more precision by default.

- vthumbe1503 · comment · 2026-11-02T22:01:42Z · [source](https://github.com/NVIDIA/TransformerEngine/pull/3752#discussion_r4448304407)

File: `transformer_engine/pytorch/tensor/storage/grouped_tensor_storage.py` · line 1083

rowwise_data_buffer is essentially the flattened out tensor. in case of weights, rowwise data is already a 1D tensor and so it is a no-op. We are only adding a .flatten() at the start of this file to make sure the data is flattened because this split API demands the inner tensors to be flattened.

Applying .flatten() on an already flattened tensor has negligible CPU overheads.

The reason these changes exist in the first place is to change the expectations GroupedTensor. Now we no longer expect the inner tensors to be of 1D shape. But rather it needs to be contigous. With this restriction, activations no longer need to do reshape(-1) avoiding a lot of CPU overheads with no CPU overheads being added for the weights
