# [CI] Publish PyTorch 2.11 CUDA 13 release wheels

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3311) · state: open · merged: False

## Original PR description

# Description

Add matching PyTorch 2.11/CUDA 13 release wheels for Linux x86_64 and aarch64. The release workflow currently builds only PyTorch 2.8/CUDA 12.9 wheels. Publishing matching wheels lets users download the PyTorch extension instead of needing a local C++/CUDA build.

Also preserve checkout space on runners where `/mnt` shares the root filesystem. Pooling both paths consumes the space needed to clone the source dependencies. The observed v2.20.2 ARM release job failed during CUTLASS checkout with `fatal: write error: No space left on device`.

The install smoke check needs `transformer-engine` and its core wheel from PyPI, and a GitHub release can precede those uploads. This happened for v2.14, v2.14.1, v2.16, and v2.20.2. The check now reports a workflow warning and continues in that case, so upload order cannot stop a release from publishing the new wheels.

Fixes #3310

## Changes

- Add Python 3.12, PyTorch 2.11/CUDA 13 builds for both architectures.
- Add SM100 to the build image architecture list and install the CUDA development packages needed for the build. The PyTorch extension has no CUDA sources, so its Blackwell kernels come from the `transformer_engine_cu13` core wheel.
- Preserve checkout space when `/mnt` shares the root filesystem.
- Keep compiler output visible and fail the job when the build fails or times out.
- Check wheel tags before upload and run install/import smoke checks for the new builds. Skip the smoke check with a workflow warning when PyPI does not have the release packages for the platform.

## Validation

Repository hooks and shell checks found no new problems. Actionlint reported only existing workflow diagnostics. Rerun the hooks with `pre-commit run --all-files`.

A [release matrix run](https://github.com/bvolpato/TransformerEngine/actions/runs/41271222435) used this PR's composite action and the release matrix on `ubuntu-22.04` and `ubuntu-22.04-arm`. It built PyTorch 2.8/CUDA 12.9 and PyTorch 2.11/CUDA 13 wheels from the `v2.21` tag on both architectures. That version is not on PyPI, so the two new builds reported the warning, skipped the smoke check, and still produced wheels with the expected names. An x86_64 PyTorch 2.11/CUDA 13 build from v2.20.2 in the same run installed and imported its wheel. The x86_64 runner also reported that `/mnt` shares the root filesystem, so this layout is no longer specific to ARM. In a [separate run](https://github.com/bvolpato/TransformerEngine/actions/runs/41280270251) of the previous disk pooling steps, the x86_64 job left 32 MiB free on root and still checked out v2.21 with 1.3 GiB left. The ARM runner stopped during checkout with `No space left on device`.

The wheel from that v2.20.2 build also ran on one NVIDIA B200 (driver 580.95.05) with no CUDA toolkit and no system cuDNN on the host. It used PyTorch 2.11.0+cu130 and `transformer_engine_cu13==2.20.2` from PyPI. TE took its no-toolkit loading path, and every loaded CUDA library came from the virtual environment (cuDNN 9.19, cuBLAS 13.1, and NVRTC 13.0). An MXFP8 `Linear` forward and backward pass and an MXFP8 `GroupedLinear` forward pass ran. `test_sanity.py`, `test_quantized_tensor.py`, `tests/pytorch/mxfp8`, `test_grouped_linear.py`, `test_float8_current_scaling_exact.py`, and `test_numerics.py` from the v2.20.2 tag found no failures. `test_numerics.py` needed `NVIDIA_TF32_OVERRIDE=0`: without it, FP32 cases differ from the PyTorch reference because TE selects TF32 for pure FP32 GEMM, and source builds of current `main` show the same differences. The file name that `get_wheel_url()` computes from the PyPI sdist with this PyTorch matches the built asset.

`test_float8_blockwise_gemm_exact.py` skipped every case, so it adds no coverage. GPU execution on GB200 has not been tested, so the aarch64 wheel is validated only through build, install, and import.

The before/after table links to an earlier native ARM run, which predates the PyPI timing change. Its CUDA 12 build required an unchanged retry after an external PPA returned HTTP 503, and its before/after runs used different runner instances. Build time and install time were not benchmarked. The release workflow does not run on PRs, so the `release` event and the asset upload step were not exercised. The `v2.21` tag does not contain this workflow change, so a release event for that tag uses its existing matrix.
