# [PyTorch] Pass canonical layouts to cuDNN grouped GEMM in fused grouped MLP

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3641) · state: open · merged: False

## Original PR description

# Description

Reduce host overhead in the fused MXFP8 grouped MLP (`GroupedMLP_CuTeGEMMGLU`), forward and backward, by passing operands to the cuDNN frontend grouped GEMM wrappers in their natural layouts.

cuDNN frontend `develop` lets the grouped GEMM wrappers take A as `(sum(m), k)`, B as `(num_groups, n, k)`, 1-D probabilities and the packed scale buffers as-is, and return 2-D outputs: NVIDIA/cudnn-frontend#1233 for the forward GLU and quant wrappers, NVIDIA/cudnn-frontend#1422 for the backward dGLU, dgrad (quant) and wgrad wrappers. Today TE builds 3-D/6-D views of every operand on each call, and the frontend maps them back.

## Changes

- **Forward:** when the GLU and quant wrappers advertise `supports_canonical_layouts`, the MXFP8 forward passes canonical A/B/probability/scale operands and consumes the 2-D C/D and packed SFD outputs directly, without per-call view/permute chains.
- **FC2 amax:** FC2 skips its unused output amax when the quant wrapper advertises `supports_optional_amax`.
- **Backward dGLU:** when the dGLU wrapper also advertises `supports_canonical_layouts`, the MXFP8 backward passes:
  - 2-D grad output and activation input;
  - 1-D probabilities and dprob;
  - packed scale buffers as-is;
  - the FC2 column-wise weight as `(num_groups, k, n)` with `b_major="n"`.

  The 2-D dGLU outputs are used directly.
- **Backward FC1 dgrad:** uses the 2-D dGLU outputs, the FC1 column-wise weight with `b_major="n"`, and a 2-D grad input.
- **Backward wgrad:** passes flat scale buffers when the wgrad wrapper supports them.
- **Unchanged:** NVFP4, SReLU, and frontends without these attributes keep the existing path. The forward and backward are gated separately, so a frontend with only NVIDIA/cudnn-frontend#1233 still gets the forward change.
- **Test:** a new test, `test_grouped_mlp_canonical_layouts_match_legacy`, checks that every operand of the FC1 GLU, FC2 quant, FC2 dGLU and FC1 dgrad calls reaches the frontend in its natural layout, and that outputs and gradients are bitwise identical to the legacy views.
- **Docs:** the fused op docstring notes the layout behavior.

**Setup:**
- Hardware and stack: SM100, TE built from this branch (sm_100), cuDNN frontend with NVIDIA/cudnn-frontend#1233 and NVIDIA/cudnn-frontend#1422, CuTeDSL 4.7.1, torch 2.14.0a0.
- Workload: an isolated 4096-row, 8-expert MLP with hidden size 2048 and intermediate size 512, MXFP8 weights, BF16 input and probabilities, `ScaledSwiGLU(glu_interleave_size=32)`, gradients enabled.
- Method: pinned CPU, 300 synchronized samples per process, configurations interleaved over three rounds.

- hwanseoc · comment · 2026-10-15T07:05:21Z · [source](https://github.com/NVIDIA/TransformerEngine/pull/3641#discussion_r4280049469)

Done for the weight views in 76581d8. The typed `(groups, n, k)` view of each weight buffer is now built once and kept on the grouped weight. It is rebuilt only if the buffer's data pointer changes. This covers all four sites: FC1 and FC2 in the forward, and the FC2 dGLU and FC1 dgrad in the backward. Each site drops from two torch ops (1.6 µs) to 0.24 µs.

The remaining `view(dtype=...)` calls are on buffers that are new every step: the quantized activations and the freshly swizzled weight scales. Each costs about 0.6 µs. TE stores quantized data as `uint8` and cuDNN takes the FP8/FP4 dtype, so dropping those needs one of two changes:
- the TE quantizers allocate typed storage, or
- the cuDNN frontend accepts raw `uint8` MXFP8 buffers with a dtype hint.

I can do the cuDNN side as a follow-up.

I think the dtype mismatch causing cpu overhead should've been avoided. In TE mxfp8 tensor, the storage dtype is uint8 with a TE metadata tracking if it's E4M2 or E5M2, I think TE has been doing this for years already.
