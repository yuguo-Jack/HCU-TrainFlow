# [PyTorch] Add SiLUGate fusible op

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3726) · state: open · merged: False

## Original PR description

# Description

First step of #3724, reworked after review: instead of a dedicated `RMSNormGated` op, this adds a small `SiLUGate` basic op, so gated RMSNorm is

    te_ops.Sequential(te_ops.RMSNorm(hidden_size), te_ops.SiLUGate())

`SiLUGate` takes the gate as an extra input and computes `y = x * silu(gate)`. The SiLU part is computed in FP32; `y` and `dx` are returned in the input dtype and `dgate` in the gate's dtype. Output quantization isn't supported, so it returns an unquantized tensor and the next op quantizes. A fused norm+gate kernel can come later as a fused op that only covers the cases the kernel supports.

Refs #3724, NVIDIA/Megatron-LM#6757

## Changes

- `transformer_engine/pytorch/ops/basic/silu_gate.py`: new `SiLUGate` basic op with one extra input (the gate).
- Export it from `transformer_engine.pytorch.ops` and add it to the API docs.
- `tests/pytorch/test_fusible_ops.py`:
  - `test_silu_gate` checks y, dx and dgate against a reference for each dtype and two shapes.
  - `test_rmsnorm_silu_gate` checks `Sequential(RMSNorm, SiLUGate)` end to end (y, dx, dweight, dgate), with zero-centered gamma on and off. The reference rounds the normalized output and its gradient to the input dtype like the op chain does, instead of loosening tolerances.

Tested on an RTX 3090 (SM86), torch 2.13.0+cu130:

    python -m pytest -q tests/pytorch/test_fusible_ops.py -k "silu_gate or rmsnorm"   # 96 passed

I haven't run it on Hopper/Blackwell yet.

This seems like a rather large and bespoke operation to treat as a first-class citizen. How about we separate the RMSNorm and gate logic by just implementing a `SiLUGate` basic op? Then you can reproduce this function with `Sequential(RMSNorm(...), SiLUGate())`. You can easily change to a different norm or a different gating function (if we add more in the future).

Once you have a fused kernel, the right design is to expose it in a fused op. This has several advantages:
- Your fused kernel doesn't need to be fully general. Only enable the fusion for the cases that the kernel supports, and in other cases we fallback to the unfused impl.
- If you only fuse the forward pass or only fuse the backward pass, your implementation only needs to consider that case.

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **BF16 reference skips rounding**

In `test_rmsnorm_silu_gate`, the reference keeps `n_ref` and its gradient in FP64, but the operation chain rounds both to BF16 between `RMSNorm` and `SiLUGate`. With signed gates, positive and negative terms can nearly cancel in the weight gradient. The missing rounding can then push the difference beyond the tolerance, making a correct implementation fail.

Round the reference normalized output and the gradient passed back into the reference normalization to `dtype`, as described in the PR.
