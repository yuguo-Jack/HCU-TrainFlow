# Accept compact MXFP8 scales in single and grouped GEMM preparation

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3519) · state: open · merged: False

## Original PR description

# Description

`general_gemm()` rejects compact, unswizzled MXFP8 scales: a 64×64 tensor with rowwise scales `(64, 2)` or columnwise scales `(2, 64)` fails during GEMM preparation because the swizzle API requires padded storage. Accept exact logical scale shapes and write them directly into padded, swizzled output, filling padding with zeros. Apply this to both single GEMM and list-based `general_grouped_gemm()` preparation while preserving the caller's buffers and unswizzled flag.

Fixes #3518.

## Type of change

- [x] Bug fix (non-breaking change which fixes an issue)

## Changes

- Accept exact compact MXFP8 scale shapes at the checked swizzle boundary. Other consumers retain their existing scale-shape validation.
- Fuse padding into a bounds-checked swizzle kernel, without an intermediate padding allocation or copy. Use a flat CUDA grid so tall scale planes do not hit the 65,535-block limit of a grid's second dimension.
- Batch up to 32 compact tensors per launch. Mixed batches retain the existing optimized kernels for padded tensors.
- Allocate padded destination shapes and correct shared-buffer offsets in the single- and multi-tensor PyTorch helpers.
- Document the C API contract and add common C API and full-binding PyTorch regressions for both orientations, single/grouped GEMM, compact/padded/mixed storage, exact output bytes, input preservation, large batches, tall shapes, and invalid inputs.

The separate `GroupedTensor` API and unchecked attention swizzle contract are unchanged. GEMM regression operands are copied from independently quantized reference planes to isolate swizzle/GEMM behavior. The separate rectangular compact in-place quantization mismatch noted during investigation is outside this fix.

In the issue you mentioned, custom MXFP8Tensor is being created for weight like this.

```
weight = MXFP8Tensor(
    shape=(64, 64),
    dtype=torch.bfloat16,
    device="cuda",
    rowwise_data=empty((64, 64)),
    columnwise_data=empty((64, 64)),
    rowwise_scale_inv=empty((128, 4) if padded else (64, 2)),
    columnwise_scale_inv=empty((4, 128) if padded else (2, 64)),
    fp8_dtype=tex.DType.kFloat8E4M3,
    quantizer=quantizer,
    with_gemm_swizzled_scales=False,
)
```

I see that this is used in Megatron FSDP v2. So I see that you are dealing with weight sharding in FSDP which can be tricky since sharded tensors might not be padded? 


> quantizer itself works great with unpadded scales

I understand quantization works with unpadded scales. So the problem seems to be that GEMMS need swizzled scales padded. 

So 2 solutions can be
1. Pad the compact scales in megatron itself before constructing the MXFP8Tensor shard for the weights. We do something similar in FSD2P. https://github.com/NVIDIA/TransformerEngine/blob/796346c0e0497b1f56a8d36ec76e02db5a6fed47/transformer_engine/pytorch/tensor/mxfp8_tensor.py#L718
2. Or instead of padding and creating a copy for the compact scales.  How about we handle padding directly in the swizzling kernel, to avoid padding performance penalty? We do something similar in grouped swizzling kernel https://github.com/NVIDIA/TransformerEngine/blob/796346c0e0497b1f56a8d36ec76e02db5a6fed47/transformer_engine/common/swizzle/swizzle.cu#L376-L377. Essentially swizzling kernel will be aware that the scales are not padded already. So manually fills them with zeros.


With the current solution, we are silently introducing a performance penalty in the framework by doing the padding, which I am hoping to avoid.
