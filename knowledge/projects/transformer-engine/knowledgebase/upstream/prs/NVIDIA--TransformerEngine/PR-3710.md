# [Common] Support compact unswizzled scales in MXFP8 quantization

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3710) · state: open · merged: False

## Original PR description

# Description

`MXFP8Tensor.quantize_()` accepts caller-provided unswizzled `scale_inv` buffers, including compact ones that hold one scale per block (`(rows, cols/32)` rowwise, `(rows/32, cols)` columnwise) instead of TE's 128x4-padded shape. #3518 asks GEMM to accept such scales too (#3519). The quantize kernels, however, assumed the padded layout, so quantizing into compact buffers wrote outside them or produced wrong scales.

Reproduced on current `main` (`eb3c860`) on B200: the reporter's script prints `256 256` instead of `0 0`. A sweep over 9 shapes × FP32/BF16/FP16 inputs × rowwise/columnwise/both × 1D/2D scaling, plus E5M2, passed 53 of 180 cases. Compact views 1 or 4 bytes past 16-byte alignment raised `cudaErrorMisalignedAddress`. The FP8 data was always correct; the scales were wrong in three kernels:

| Kernel | Used for | Failure with compact scales |
| --- | --- | --- |
| Generic `quantize_mxfp8_kernel` | FP32 input, 2D scaling, columnwise-only, partial tiles | Rowwise stores are bounded by column only and columnwise stores not at all. They write past the buffer when `rows % 64 != 0` and into the next scale row when `cols % 64 != 0`. |
| Staged bidimensional cast (`CastTraitsSwizzle`) | BF16/FP16, rowwise + columnwise | Rowwise scales are flushed in 4- or 8-byte groups, so rows that are not a multiple of four scales long are dropped or misplaced. Columnwise scales are stored for whole 64-column iterations. |
| Register-resident rowwise and bidimensional casts | BF16, `cols % 128 == 0` / `% 256 == 0` | 64- and 128-bit stores fault on views that are not 16-byte aligned. |

So BF16 inputs stay in bounds only for some shapes.

Review of the first commit found that views whose scale rows hold more entries than blocks also fail in the specialized kernels. The register-resident bidimensional kernel faults when columnwise scale rows are not a multiple of 16 bytes long. The rowwise-only kernels reject such rows (register-resident) or leave some of them unwritten (staged).

Fixes #3689

## Changes

- Generic kernel: bound rowwise scale stores by the scale tensor's rows, and columnwise stores by its rows and columns. TE's padded tensors cover every chunk, so their stores are unchanged.
- Kernel selection: use the specialized kernels only when the scale pointers are 16-byte aligned, the rowwise scale stride is a multiple of four, rowwise-only casts write packed scale rows (one entry per block), and, for the staged bidimensional kernel, each columnwise scale row spans whole 64-column iterations. Other layouts use the generic kernel. The register-resident bidimensional kernel also needs columnwise scale rows that are a multiple of 16 bytes long; other row lengths take the staged kernel. TE's padded tensors always qualify, so their kernel selection is unchanged.
- Validation: reject unswizzled scale tensors that are not 2D or hold fewer than one scale per block, which would otherwise leave scales unwritten. GEMM-swizzled scales are not affected.
- Tests: `tests/pytorch/mxfp8/test_mxfp8_quantize_compact_scales.py` and `CompactScalesCastMXFP8TestSuite` in `tests/cpp/operator/test_cast_mxfp8.cu` quantize into compact views, and into views whose scale rows hold more entries than blocks. Canary bytes surround every view, and the views are aligned and unaligned. The tests compare the results byte for byte with TE's padded output. The C++ suite also covers FP16 input and the dbias variant.

GEMM's handling of compact scales (#3519) is unchanged.

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **Later scale rows remain unaligned**

The new `scales_fit_specialized` check tests each buffer's base address, but not the alignment of later columnwise rows. A BF16 input shaped `(64, 256)`, with aligned rowwise scales shaped `(64, 8)` and columnwise scales shaped `(2, 257)`, passes these checks and selects `launch_cast_bidim`. That kernel keeps the 257-byte stride and issues an 8-byte store at the second row's unaligned address. Quantization can therefore still fail on an accepted layout.

Check the columnwise stride against the selected kernel's store alignment, or send these layouts to the generic kernel.

File: `transformer_engine/common/cast/mxfp8/quantize_mxfp8.cuh` · line 856

Confirmed on B200. With BF16 (64, 256) input, (64, 8) rowwise scales and (2, 257) colwise scales, the register-resident bidimensional kernel faults with a misaligned address on the second colwise scale row.

The same check also missed rowwise-only casts into scale rows longer than one entry per block. `launch_cast_rowwise` rejects them, and the staged rowwise kernel leaves some of those rows unwritten, because its threads past the last column return before the scale flush.

Fixed in 097642fcbe1e6c7376fb1a34b100252216d30350:
- The register-resident bidimensional kernel now also requires colwise scale rows that are a multiple of 16 bytes long; other row lengths take the staged kernel.
- Rowwise-only casts into longer scale rows use the generic kernel.

Both the PyTorch and C++ tests now cover longer scale rows.
