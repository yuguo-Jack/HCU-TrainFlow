- greptile-apps[bot] · comment · 2026-10-22T16:31:39Z · [source](https://github.com/NVIDIA/TransformerEngine/pull/3727#discussion_r4350906493)

File: `tests/cpp_distributed/test_comm_gemm.cu` · line None

<a href="#"><img alt="P2" src="https://greptile-static-assets.s3.amazonaws.com/badges/p2.svg?v=9" align="top"></a> **Logging test depends on order**

`LogsStreamIdToStdout` changes a flag that stays cached for the whole process. `unsetenv` does not reset it, so later GEMM tests keep logging after cleanup. If another GEMM test runs first with logging unset, the cached value stays false and this test's stdout check fails.

Run this check in a separate MPI-launched test process so it neither depends on test order nor changes later tests.

- greptile-apps[bot] · comment · 2026-10-23T18:26:30Z · [source](https://github.com/NVIDIA/TransformerEngine/pull/3727#discussion_r4362945567)

File: `tests/cpp_distributed/test_comm_gemm_stream_logging.cu` · line 54

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **Builds without cuBLASMp fail**

The new test calls `nvte_comm_gemm_ctx_create` without checking `nvte_built_with_cublasmp()`. With `NVTE_WITH_CUBLASMP` disabled—the default—the call throws instead of skipping. The QA script launches this test whenever four GPUs are available, so builds without cuBLASMp now fail this suite.

Add the same early skip used by `test_comm_gemm.cu`, before creating the NCCL communicator.

- denera · comment · 2026-10-27T18:49:25Z · [source](https://github.com/NVIDIA/TransformerEngine/pull/3727#discussion_r4392808402)

File: `transformer_engine/common/comm_gemm/comm_gemm.cpp` · line 65

This stream is actually only ever used in `cublasMpCreate` and cuBLASMp itself uses its own internal streams that it does not expose to the user, so there is no real GPU work that ever runs on **this** particular stream we're logging here. I'm not sure how useful that really is.

As far as cuBLASMp goes, the recommendation would be for the user to go through cuBLASMp's own logging and debug variables instead of using TE to log anything.

Userbuffers code is under an entirely different path at `transformer_engine/common/comm_gemm_overlap`. We do have direct access there to the actual compute and comm streams we use in the overlap algorithms themselves. If you want those logged, I would recommend adding similar stream ID logs behind the same env var in that file instead of adding it here.

Also, printed rank here is tensor-parallel rank so a data-parallel run with logging means you get multiples of the same TP rank printed across DP groups. We don't have access to DP rank here but it might help to differentiate with PID or some unique device identifier perhaps?
