<h3>Summary</h3>

Adds a Mixture of Experts guide with diagrams, API links, and PyTorch and JAX examples.
- The guide shows how a router picks experts and balances their workload.
- The guide shows how tokens move into expert blocks and back.
- The guide shows how grouped expert layers build a single-device MoE example.
- The guide shows how experts run across ranks and return results to their source tokens.
- The framework API pages now point to MoE building blocks and explain their call details.

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **Unmasked Padded Receive Slots**

With a fixed receive capacity, unused EP slots and their routing weights are not initialized. This example multiplies every expert output by `recv_w` without first masking invalid slots. If an expert produces nonzero values for padded rows, such as through a bias, garbage-weighted rows are passed to `ep_combine` and can corrupt the MoE output. Mask the padded slots before combine, as the repository's runnable EP example does.

One thing worth mentioning here is introducting scaled_activation 
is equivalent to doing an activation and multiplying expert_output by scales at the end
i.e
`scales * fc2(act(fc1(x))) = fc2(scales*act(fc1(x))`

And in case of bias, fc2 needs a scale_bias=True argument being passed as well. 

i.e
`scales * fc2(act(fc1(x))`
`= scales * (fc2_gemm(act(fc1(x)) + fc2_bias)`
`= fc2_gemm(scales * act(fc1(x))) + scales * fc2_bias`

I know this is an implementation detail. But from the direct looks it is unclear how this grouped op will create expert_out*scales. So mentioning this detail would be useful

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **EP example fails on fallback**

If `GroupedLinear` uses its fallback path—for example, on Hopper with cuBLASLt older than 13.4—this fixed receive capacity breaks the example. Dispatch returns `recv_capacity` rows, but `tokens_per_expert` counts only the rows actually received. The fallback calls `torch.split` with those counts and fails whenever their sum is below capacity, as normally happens with balanced routing.

Use eager receive sizing for this example, or require and explain the versions needed for the native grouped path.
