# [PyTorch] Add the discovered NCCL and cuDNN include dirs to the PyTorch extension build

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3696) · state: open · merged: False

## Original PR description

# Description

Building from source with a CUDA toolkit installed fails while compiling the PyTorch extension when NCCL and/or cuDNN come **only from the `nvidia-*` wheels** that `torch` pulls in, i.e. with no `libnccl-dev` / system cuDNN:

```
transformer_engine/pytorch/csrc/extensions.h:10:10: fatal error: nccl.h: No such file or directory
transformer_engine/common/util/logging.h:15:10: fatal error: nccl.h: No such file or directory
transformer_engine/common/include/transformer_engine/comm_gemm_overlap.h:12:10: fatal error: nccl.h: No such file or directory
```

With NCCL fixed, a machine that also lacks a system cuDNN then fails on `cudnn.h` (`transformer_engine/common/util/logging.h:12`, `transformer_engine/pytorch/csrc/common.h:22`).

`libtransformer_engine.so` itself builds in both cases. CMake's `find_path` hints locate the wheels: `${Python_SITEARCH}/nvidia/nccl` for NCCL, and `common/cmake/cuDNN.cmake:14` for cuDNN. The setuptools extension misses them because, with a toolkit present, `get_cuda_include_dirs()` returns only the toolkit include dir, and NCCL and cuDNN are not part of the toolkit. `build_tools/jax.py` already appends `nccl_include_path()`, added in #2580 for #2331; `build_tools/pytorch.py` does not, and there is no cuDNN equivalent.

Upstream CI does not hit this. In the PyTorch job of `.github/workflows/minimum_versions.yml`, line 27 apt-installs `cudnn9-cuda-12 libnccl-dev libnccl2` in the container, which puts `nccl.h` on the compiler's default include path, and line 45 sets `CUDNN_INCLUDE_PATH=/usr/include/x86_64-linux-gnu`.

Related: #2331, #2580, #2556

## Changes

- `build_tools/pytorch.py`: append `nccl_include_path()` to the PyTorch extension's `include_dirs` (same as `build_tools/jax.py`), and also `cudnn_include_path()`.
- `build_tools/utils.py`: new `cudnn_include_path()`. It checks the same places as `common/cmake/cuDNN.cmake`, in the same order: `CUDNN_INCLUDE_PATH`, `CUDNN_PATH`, the `nvidia.cudnn` wheel, the toolkit include dir. The extension therefore sees the same `cudnn.h` as the core library.

Both lookups return `None`, or a directory that is already searched, when the headers are on the default include path. Behaviour is unchanged there.

## Validation

Both machines were built from `9d9bd9e5` with `NVTE_WITH_NCCL_EP=0`. `build_tools/` is identical on current `main`. I did not rebuild on the current `main` head.

- **Jetson AGX Thor** (CC 11.0, aarch64): JetPack 7.2 (L4T R39.2.0), CUDA 13.2, system cuDNN 9.20, no system NCCL, `torch 2.13.0+cu130` with `nvidia-nccl-cu13 2.29.7`. `NVTE_CUDA_ARCHS=110`.
  - Before: fails on `nccl.h`, after all 113 common-library targets have built.
  - With the NCCL change: the build succeeds. `import transformer_engine.pytorch` works, and a `te.Linear` forward runs under the DelayedScaling, Float8BlockScaling, MXFP8 and NVFP4 recipes.
- **GH200** (CC 9.0, aarch64 SBSA): CUDA 13.2 toolkit, no `libnccl-dev`, NCCL and cuDNN only from the `torch` cu130 wheels.
  - Before: fails on `nccl.h`.
  - With only the NCCL change: fails on `cudnn.h`.
  - With both changes: the build succeeds in 7 min 26 s (`MAX_JOBS=24`, peak RSS 4.0 GB). `import transformer_engine.pytorch` works, and a `te.Linear` forward runs.

At runtime, both machines also needed the toolkit cuBLAS preloaded (`LD_PRELOAD=.../libcublasLt.so.13:.../libcublas.so.13`). The reason: `import torch` first loads the older pip `nvidia-cublas` under the same soname. That is a separate issue and is not addressed here.

Not validated on x86_64.
