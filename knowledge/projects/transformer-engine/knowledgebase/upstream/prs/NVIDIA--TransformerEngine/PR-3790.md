# [PyTorch] Add export_components to MXFP8 tensors

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3790) · state: open · merged: False

## Original PR description

# Description

`MXFP8TensorStorage.export_components()` returns the FP8 values and E8M0 scales of an MXFP8 tensor in a layout that does not depend on how Transformer Engine stores them. It is for integrations that hand MXFP8 weights to another library, for example RL weight sync to an inference engine. Today NeMo RL #3908, Megatron-Bridge #5917, Miles and verl #8129 each build this by hand from `_rowwise_data` and `_rowwise_scale_inv`.

It returns `MXFP8Components(data, scale_inv)`:

- `data` is `_rowwise_data` viewed as `torch.float8_e4m3fn` or `torch.float8_e5m2`, with the tensor's shape.
- `scale_inv` holds E8M0 biased exponents as `torch.uint8`, with shape `(*shape[:-1], shape[-1] // 32)`, without padding or GEMM swizzle.

The values are always a view of the tensor's data, so they change when the tensor is updated in place, for example by an optimizer step. Clone them to keep a snapshot. The scales are a view too, except in two cases:

- they are padded in the last dimension (`K/32` is not a multiple of 4), or
- they are swizzled for GEMM (`optimize_for_gemm=True`).

In those cases they are copied, and the swizzle is undone with one permute in PyTorch, so no new kernel is needed. A tensor without row-scaled data raises `ValueError`. It works the same for quantized parameters and for tensors returned by a quantizer, with no dequantize or requantize.

On #3644 I asked whether a standalone function that also quantizes a BF16 weight first would be preferred. This PR uses a method. I expect the export logic itself would stay the same in a function, but I have not tried that version.

## Changes

- `transformer_engine/pytorch/tensor/storage/mxfp8_tensor_storage.py`: the `MXFP8Components` NamedTuple and `MXFP8TensorStorage.export_components()`. `MXFP8Tensor` inherits it.
- `tests/pytorch/test_quantized_tensor.py`, 22 cases in all:
  - 4 tests on hand-built storages in `TestQuantizedTensor`, which need no MXFP8 kernels: layout, views, empty tensor, and no row-scaled data.
  - 3 tests in `TestMXFP8Tensor`:
    - the export decodes to `dequantize()` exactly for E4M3, E5M2 and 2D quantization;
    - `optimize_for_gemm=True` gives the same export;
    - a `te.Linear` weight from `quantized_model_init` exports correctly after a forward and backward pass, and after a `FusedAdam` step the views exported before the step hold exactly the rowwise quantization of the new FP32 master weights.
  - 2 test helpers:
    - `_swizzle_mxfp8_rowwise_scale_inv` builds the cuBLAS-swizzled scale layout from the kernel's byte-index formula, independently of the code under test;
    - `_decode_mxfp8_components` decodes the exported values and scales in plain PyTorch.
- `docs/features/low_precision_training/mxfp8/mxfp8.rst`: an "Exporting values and scales" section.

Not covered here: column-scaled data, per-expert export from `GroupedTensor`, and the other recipes.

`test_mxfp8_export_components_of_quantized_weight` never updates the weight. It calls `export_components()` only after backward, so it does not check the promise that exported views follow optimizer updates. A change that leaves those views pointing at old weights could pass this test.

Export before an update, run an optimizer step or `weight.copy_()`, and check that the saved views contain the new values and scales.
