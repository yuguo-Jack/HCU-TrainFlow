# Treat total_num_pages as a physical KV cache budget, not the page-table size

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3557) · state: open · merged: False

## Original PR description

**Incremental review:** [Files changed](https://github.com/NVIDIA/TransformerEngine/pull/3557/files) against `main`.

## The problem

The paged KV cache asserts that the physical page budget equals the size of the page table:

```python
assert total_num_pages == self.max_batch_size * max_pages_per_seq
```

Those two quantities are not the same thing. `total_num_pages` is how much KV memory the pool actually owns; `max_batch_size * max_pages_per_seq` is only how many logical page slots the page table can *address*. Requiring equality means a caller that budgets KV bytes — and therefore wants a deliberately smaller physical pool than the page table could address — cannot construct the cache at all, even though nothing downstream needs the pool to be exactly that size:

* the free-page pool is sized from `total_num_pages`
* the page table is shaped from `max_batch_size × max_pages_per_seq`
* they were already independent everywhere else

## The change

Require only that the pool can hold one full-length sequence, which is the weakest condition that keeps the cache usable:

```python
assert total_num_pages >= max_pages_per_seq
```

A caller that overruns the pool still gets the existing, clean capacity error from the cache manager rather than an out-of-pool page index, so this does not turn a capacity mistake into memory corruption.

## Verification

| check | before | after |
|---|---|---|
| construct with an 8-page pool (32 logical slots) | **rejected** | constructs |
| attention output vs the full pool | — | **bitwise identical** |
| KV bytes held | — | **25%** |
| pool smaller than one sequence | rejected | still rejected |

The test covers both directions.

## Not covered

Only the custom-manager path is exercised. Prefix sharing, page offload, cross-process sharing and scheduler preemption are untouched.
