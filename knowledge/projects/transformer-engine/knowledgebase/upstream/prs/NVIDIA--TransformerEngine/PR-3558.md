<a href="#"><img alt="P2" src="https://greptile-static-assets.s3.amazonaws.com/badges/p2.svg?v=9" align="top"></a> **Bootstrap dtype mismatch**

This check only verifies that the tensor matches `buffer.payload_dtype`; it does not verify that the payload fits the group's bootstrap-time `max_token_dtype`. For example, the default BF16 bootstrap and an FP32 `EpBuffer` pass this check, but native dispatch rejects the wider payload while combine has no equivalent width check before forwarding it to NCCL EP. Validating the buffer dtype against the bootstrap maximum would reject this inconsistent configuration before communication starts.

**Knowledge Base Used:** [PyTorch distributed execution](https://app.greptile.com/nvidia-public-github/-/custom-context/knowledge-base/nvidia/transformerengine/-/docs/pytorch-distributed-execution.md)

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **EP buffer tests fail immediately**

`_make_buffer()` now always passes `payload_dtype` to `_make_config()`, but `_make_config()` accepts neither that argument nor `**kwargs`. Every test using `_make_buffer()` therefore raises `TypeError` before dispatch, including existing BF16 tests and the new dtype sweep. Add the argument to `_make_config()` and pass it into `EpConfig` so the requested dtype reaches the buffer.

- greptile-apps[bot] · comment · 2026-10-27T17:54:57Z · [source](https://github.com/NVIDIA/TransformerEngine/pull/3558#discussion_r4392265837)

File: `tests/pytorch/distributed/run_ep.py` · line 577

<a href="#"><img alt="P2" src="https://greptile-static-assets.s3.amazonaws.com/badges/p2.svg?v=9" align="top"></a> **FP32 checks miss lost precision**

The new FP32 round-trip and gradient checks use `atol=5e-2, rtol=5e-2` on inputs near 0.1–0.9. A payload rounded to BF16 and then returned as FP32 passes both numeric checks and the dtype assertions, so this test can miss lost FP32 precision in either direction. Use dtype-specific tolerances with a tight FP32 threshold.

Note: If this suggestion doesn't match your team's coding style, reply to this and let me know. I'll remember it for next time!
