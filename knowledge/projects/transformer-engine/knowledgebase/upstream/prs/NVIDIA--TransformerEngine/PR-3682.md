# [Common] Optimized kernels for swizzling and remove obsolete narrow scaled kernels

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3682) · state: closed · merged: True

## Original PR description

# Description

This [PR](https://github.com/NVIDIA/TransformerEngine/pull/3658) introduced rowwise/colwise swizzling kernels targeted at narrow scale width use-cases. The scope of this PR is to
- Colwise Swizzling: Enable the colwise swizzling optimized kernel(swizzle_columnwise_chunk_kernel) for both narrow scale-width and wide scale-width use-cases. And completely removes the previously existing kernel for narrow scale width kernel. The previously existing kernel for wide scale-width is retained since that is still used for grouped swizzling. Using the kernel in grouped swizzling will be a follow up PR.
- Rowwise swizzling: Enable rowwise swizzling optimized kernel(swizzle_rowwise_full_width_kernel) for narrow scale-width use-cases. For wide scale-width, we fall back to our previosuly existing rowwise scaling kernel which operates on 128*128*N tile where N is vectorization's bit width. Fall back is implemented through shared memory heuristics
  - If scale is sufficiently narrow (smem ~= 128*padded_k <= 17KB), new kernel is better
  - For roughly 17–30 KiB of shared memory, use the full-width kernel for at most 16 row tiles or when the total row tiles exceed the current GPU’s SM count. The SM-count cutoff replaces the previous hard-coded 128-tile threshold. Otherwise use the generic rowwise kernel.
- Optimized row scaling kernel is also extended to be use for NVFP4.
  - Apt unit tests are also added
- 16 byte Alignment requirement for Swizzling kernels
  - Previously existing kernels had the minimum 4 byte alignment requirement. But even that was never checked
  - Now we have kernels for most of the use-cases doing a int4 read/write and hence 16 byte alignment is a must for both input and output scale pointers.

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **Valid columnwise scales become zero**

A batch containing one MXFP8 tensor with both scale buffers and another with only columnwise scales passes the existing checks and selects the columnwise path. But `logical_rowwise = use_rowwise_buffer` uses rowwise dimensions for the first tensor, even though the selected buffer is `columnwise_scale_inv`.

For a 256×128 tensor, this sets `original_k` to 4 instead of 8. The kernel then zeros half its valid columnwise scales, giving GEMM incorrect scales. Derive the limits from the selected buffer, such as with `rowwise && use_rowwise_buffer`.

```suggestion
    const bool logical_rowwise = rowwise && use_rowwise_buffer;
```

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **Valid mixed batches fail**

A valid batch can contain one tensor with both scale buffers and another with only columnwise scales. If any selected buffer is unaligned, this fallback calls `swizzle_scaling_factors` for every tensor. That function rejects tensors with both buffers, so the batch throws instead of returning columnwise scales.

Build descriptors from the batch’s selected buffers and launch the byte-wise kernel directly, rather than applying the single-tensor checks.
