# [JAX] Control MeshResource at API call granularity for Dense APIs

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3747) · state: open · merged: False

## Original PR description

# Description

Previously, we had been relying primarily on a global `MeshResource` for users to inform TE/JAX about their mesh axes names and parallelisms they would like active. For Dense models, this worked well. For MoE models, we needed to add an explicit `MeshResource` argument to the MoE Block APIs for overriding the parallelism mapping for the MoE region. This PR is an extension to apply that same thinking to Dense APIs.

The motivating case for this is pure-EP workloads. With EP+FSDP workloads, we use EP as EP and FSDP as FSDP in the MoE region, but in other pieces of the model EP acts as further FSDP GPUs instead of replicating. This allows use to expand our FSDP domain for things like QKV+O proj instead of replicating on EP GPUs. However, this mapping is currently implemented in `gemm.py` as implicitly encodes this EP->FSDP mapping.
https://github.com/NVIDIA/TransformerEngine/blob/fac8d4a90601e37cc2d6da12bf5ba13d52537d18/transformer_engine/jax/cpp_extensions/gemm.py#L1013

However, when pure EP is used, this logic breaks and the GEMM sharding rules become ambiguous. This results in the incorrect tensor being AG'd by mistake. In this case, the activations are AG'd along EP instead of the weights.

This PR addresses this by supporting explicit MeshResource args (global MeshResource context still works as-is for simpler cases where this nuance isn't needed). As a result, a user can set `MeshResource(fsdp_resource=('fsdp', 'expert'), ...)`  explicitly which will allow those Dense calls to use either `fsdp` or `expert` (or both if both are active) as FSDP for Dense regions. Then the corresponding MoE region will use `MeshResource(fsdp_resource=('fsdp',), ep_resource=('expert',), ...)`
