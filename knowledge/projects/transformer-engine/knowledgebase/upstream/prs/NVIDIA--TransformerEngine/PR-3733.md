# [Common] Don't call CUDA from static destructors at exit

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3733) · state: closed · merged: True

## Original PR description

*This description was written entirely with AI (Claude Code, Claude Opus 5.5).*

# Description

Processes that ran an NVRTC-compiled kernel (norms and softmax since #3156, and others) or captured cuDNN fused attention into a CUDA graph can segfault at exit, after all their work is done. In pytest this turns a passing test file into exit status 139.

Both crashes come from static destructors that call CUDA after `main` returns. The [CUDA Programming Guide, §2.1.6](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html#runtime-initialization) says that "Using any of these interfaces (implicitly or explicitly) during program initiation or termination after main will result in undefined behavior", and it's Mandatory rule CUDA 1.1 (p. 8) in NVIDIA's [CUDA C++ Guidelines v3.0.1](https://docs.nvidia.com/cuda/cuda-for-tegra-appnote/cudaguideV3.0.1.pdf).
- **`rtc::KernelManager`:** its destructor runs `~Kernel`, which unloads modules through `cuda_driver::call` ([rtc.cpp#L73-L92](https://github.com/NVIDIA/TransformerEngine/blob/ec38bcc8daf532120bde266b2b703a2ef7957554/transformer_engine/common/util/rtc.cpp#L73-L92)). `cuda_driver::call` caches driver entry points in function-local statics, which are usually first constructed after the `KernelManager`, when its first kernel is loaded. Statics are destroyed in reverse order of construction, so those caches are already destroyed when `~Kernel` reads them.
- **Fused-attention graph caches:** destroying a cuDNN plan that a CUDA graph retains releases a CUDA user object ([cuda_graph_retention.h#L159-L166](https://github.com/NVIDIA/cudnn-frontend/blob/51a3de73e122aeedafe68070acf3b7ff3970534e/include/cudnn_frontend/utils/cuda_graph_retention.h#L159-L166)), resolved through `get_cuda_symbol()`'s function-local map ([cudnn_frontend_shim.h#L152-L171](https://github.com/NVIDIA/cudnn-frontend/blob/51a3de73e122aeedafe68070acf3b7ff3970534e/include/cudnn_frontend_shim.h#L152-L171)), which can likewise already be destroyed. That's https://github.com/NVIDIA/cudnn-frontend/issues/1486. https://github.com/NVIDIA/cudnn-frontend/pull/1565 keeps that map alive on `develop`, but no release has it yet.

Whether the `KernelManager` case crashes depends on the libstdc++ TE was built with. With GCC 16's, the lookup walks freed nodes and faults. With GCC 13's (the NGC `pytorch:26.09-py3` container), the destroyed map looks empty, so `cuda_driver::call` inserts into it, writing to freed memory, and the process exits 0. With `MALLOC_PERTURB_=165`, both crash.

**Fix:** `KernelManager` and the graph caches are allocated with `new` and never destroyed ([rtc.cpp#L156-L158](https://github.com/NVIDIA/TransformerEngine/blob/ec38bcc8daf532120bde266b2b703a2ef7957554/transformer_engine/common/util/rtc.cpp#L156-L158), [graph_cache.h#L133-L135](https://github.com/NVIDIA/TransformerEngine/blob/ec38bcc8daf532120bde266b2b703a2ef7957554/transformer_engine/common/fused_attn/graph_cache.h#L133-L135)), so their destructors never run. TE already avoids exit-time teardown this way: `TVMFFIConfigCache::create()` (#3137) and the fused-attention debug registry (#2964) are never destroyed, and `HandleManager` never releases its handles (#1389). `cuda_driver::call`'s symbol cache and mutex are also never destroyed ([cuda_driver.h#L43-L46](https://github.com/NVIDIA/TransformerEngine/blob/ec38bcc8daf532120bde266b2b703a2ef7957554/transformer_engine/common/util/cuda_driver.h#L43-L46)), so a lookup never reads a destroyed map.

Both caches only ever insert ([rtc.cpp#L294](https://github.com/NVIDIA/TransformerEngine/blob/ec38bcc8daf532120bde266b2b703a2ef7957554/transformer_engine/common/util/rtc.cpp#L294), [graph_cache.h#L120](https://github.com/NVIDIA/TransformerEngine/blob/ec38bcc8daf532120bde266b2b703a2ef7957554/transformer_engine/common/fused_attn/graph_cache.h#L120)), so nothing changes before exit. The one behavioural difference is that a program that `dlclose`s `libtransformer_engine.so` and keeps running no longer unloads the NVRTC modules or destroys the cached plans.

## Changes

- `transformer_engine/common/util/rtc.cpp`: `KernelManager::instance()` is never destroyed.
- `transformer_engine/common/fused_attn/graph_cache.h`: the fused-attention graph caches are never destroyed.
- `transformer_engine/common/util/cuda_driver.h`: `cuda_driver::call`'s symbol cache and its mutex are never destroyed.
- `tests/cpp/util/CMakeLists.txt`: the util tests run with `MALLOC_PERTURB_=165`, so `ctest` fails a test whose process crashes at exit. `UtilTest.NVRTC` drives `rtc::KernelManager` directly ([test_nvrtc.cpp#L66-L79](https://github.com/NVIDIA/TransformerEngine/blob/ec38bcc8daf532120bde266b2b703a2ef7957554/tests/cpp/util/test_nvrtc.cpp#L66-L79)).

## Testing

On an RTX 4090 (driver 615.71.09) with CUDA 13.4, cuDNN 9.27, cudnn-frontend 1.31.0 (without https://github.com/NVIDIA/cudnn-frontend/pull/1565), PyTorch 2.14.1 and GCC 16, building `main` (c9c92255) with and without this PR. |---|---|---|

| `te.LayerNorm` forward and backward | exit 139 in 5 of 6 | exit 0 in 6 of 6 |
| `DotProductAttention` (cuDNN) captured in a CUDA graph | exit 139 in 6 of 6 | exit 0 in 6 of 6 |

I also tested both commits backported to TE 2.20.2 (https://github.com/NixOS/nixpkgs/pull/577950) on the same 4090, with cudnn-frontend's fix applied to both builds. Without this PR, `test_torch_compile.py` exited 139 in 4 of 4 runs, and 12 of 20 L0 PyTorch test files exited 139 after their tests finished. With it, none did. The test counts and failing tests were the same: `test_numerics.py` tolerance failures, and out-of-memory errors in `test_fused_rope.py` on the 24 GiB card.

I haven't rerun the GB10 since adding the second commit.

LayerNorm makes no guarantee to call the NVRTC kernel. It does by default, but it can switch to cuDNN by setting `NVTE_NORM_FWD_USE_CUDNN=1`/`NVTE_NORM_BWD_USE_CUDNN=1`. We ignore this envvar in certain cases (e.g. MXFP8 LayerNorm) and we may change the defaults in the future. It may be safer to make this test name more descriptive (`test_exit_after_layernorm`).

```suggestion
def test_exit_after_layernorm():
    # MALLOC_PERTURB_ makes glibc overwrite freed memory, so an exit-time destructor that reads an
    # already-destroyed object crashes every time rather than only sometimes.
    env = dict(
        os.environ,
        # Make glibc overwrite freed memory, so an exit-time destructor that reads an
        # already-destroyed object crashes every time rather than only sometimes.
        MALLOC_PERTURB_="165",
        # Disable cuDNN LayerNorm kernel and use NVRTC kernel instead
        NVTE_NORM_FWD_USE_CUDNN="0",
        NVTE_NORM_BWD_USE_CUDNN="0",
    )
    result = subprocess.run(
        [sys.executable, "-c", SCRIPT], env=env, capture_output=True, text=True, timeout=600
    )
    assert result.returncode == 0, f"exit status {result.returncode}\n{result.stderr}"
```
