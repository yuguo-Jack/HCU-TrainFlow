# Fix EP sharding gather logic so activations stay sharded

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3697) · state: open · merged: False

## Original PR description

# Description

Please include a brief summary of the changes, relevant motivation and context.

This change fixes an unintended behavior for EP-only workloads where GEMMs sharded like the following
- activations: `[B("ep"), S, H]`
- weights: `[H, D("ep")]`
will perform an all-gather on the activations. This is not desirable in the EP case as EP computation is intended to be FSDP-style outside of the expert layers, and as a result, we wouldn't expect an activation all-gather.

As a result, if a mesh axis shards both a non-contracting dim of the activations and a non-contracting dim of the weights, we now gather the weights along that axis (as is already done for FSDP). Only the overlapping axes are dropped from compound weight specs, e.g. `("ep", "tp")` -> `"tp"`.

We make an exception for TPSP workloads, since there we expect activations to be gathered on the sequence dimension; TP and TPSP axes are therefore ignored in this gather.

We additionally add tests validating the EP-only behavior, compound weight specs, and that existing TP/TPSP (including collective GEMM) sharding is unchanged.

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **Compound sharding repeats an axis**

With `fsdp_resource="fsdp"` and `tpsp_resource="tpsp"`, a plain GEMM with input specs `(("fsdp", "tpsp"), None)` and `(None, ("fsdp", "tpsp"))` now keeps `"tpsp"` on the weight. The later activation gather compares whole tuples against individual axes, so it leaves `("fsdp", "tpsp")` unchanged. The resulting output spec, `(("fsdp", "tpsp"), "tpsp")`, repeats an axis across dimensions and fails when building `NamedSharding`.

Previously, the whole weight spec was gathered and the output was valid. Remove overlapping axes from compound activation specs too, and add this case to the tests.
