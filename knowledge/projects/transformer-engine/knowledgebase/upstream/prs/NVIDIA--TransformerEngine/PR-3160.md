# [Common][PyTorch] Add strided batched GEMM in BF16/MXFP8

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3160) · state: closed · merged: True

## Original PR description

# Description

This PR adds experimental cuBLASLt-backed strided batched GEMM support and a new fusible PyTorch operation exported as `transformer_engine.pytorch.ops.BatchedLinear`.

The main use case is applying one weight matrix per group without rearranging interleaved activations:

```
[S, B, G, D] @ [G, R, D] -> [S, B, G, R]
```

Both contiguous `[G, ..., D]` and `[..., G, D]` input layouts are supported through explicit leading dimensions and batch strides. MXFP8 scales are packed into the cuBLASLt per-batch layout internally before each GEMM.

## Dependency

This PR depends on #3327 for meta-device deferred initialization in the operation fuser and should be merged after it.

## Changes

- Add an experimental common API for cuBLASLt strided batched GEMM with independent matrix strides.
- Support high-precision and MXFP8 input pairs with high-precision output.
- Add `transformer_engine.pytorch.ops.BatchedLinear` with high-precision and MXFP8 forward and backward computation.
- Support primary MXFP8 weights, bias and `return_bias`, `save_original_input`, custom initialization and RNG tracking, and main-gradient accumulation.
- Add API documentation and PyTorch L0 tests.

### Current limitations

- A and B must both be high precision or both be MXFP8.
- MXFP8 operands must use contiguous `[G, ..., D]` or `[..., G, D]` layouts.
- Output quantization, fused GEMM epilogues, non-MXFP8 recipes, and tensor parallelism are not supported.

- <img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top">&nbsp;**cuBLASLt handle leak on any API failure after partial descriptor creation** `transformer_engine/common/gemm/cublaslt_gemm.cu:1148` <a href="https://github.com/nvidia/transformerengine/blob/7ba6f2a99dc105e121f0becb35769207ba11f6c7/transformer_engine/common/gemm/cublaslt_gemm.cu#L1040-L1148">▶</a>

  `Adesc`, `Bdesc`, `Cdesc`, `Ddesc`, `operationDesc`, and `preference` are created incrementally. If any `NVTE_CHECK_CUBLAS` call after the first `cublasLtMatrixLayoutCreate` throws - for example in `set_strided_batch`, in the MXFP8 `cublasLtMatmulDescSetAttribute` block, in `cublasLtMatmulAlgoGetHeuristic`, or in `cublasLtMatmul` - the already-allocated handles are never passed to their corresponding `Destroy` functions. The cleanup block at the bottom of the function is only reached on the happy path.

  The MXFP8 version checks at the top of the function were correctly moved before descriptor creation, so those specific paths are safe. The leak window is every `NVTE_CHECK_CUBLAS` call from the first descriptor creation onward. Adding RAII wrappers (or a try/catch with a cleanup lambda) to the new function would prevent the problem here.

- <img alt="P2" src="https://greptile-static-assets.s3.amazonaws.com/badges/p2.svg?v=9" align="top">&nbsp;**C\-matrix always aliased to D \- undocumented design restriction** `transformer_engine/pytorch/cpp_extensions/gemm.py:1491` <a href="https://github.com/nvidia/transformerengine/blob/bab9621091e78a4349d0712390654dc24299963d/transformer_engine/pytorch/cpp_extensions/gemm.py#L1412-L1491">▶</a>

  The public C-level API `nvte_cublas_gemm_strided_batched` accepts independent `C`, `ldc`, and `stridec` parameters (useful for a fused `D = A*B + beta*C` with distinct accumulation buffers). This Python wrapper always passes `out` for both C and D, permanently losing that flexibility. A comment in the docstring noting that accumulation is always done in-place (`beta` is applied to `out` itself) would prevent surprises for future callers who discover the separate C parameter in the C++ header.

  Note: If this suggestion doesn't match your team's coding style, reply to this and let me know. I'll remember it for next time!

File: `transformer_engine/common/include/transformer_engine/gemm.h` · line None

This is not a good design for scale swizzling. The root problem is that `NVTETensor` does not actually understand the batch-GEMM-swizzled format. The user is expected to lie and secretly pass in scales in a non-standard format, and TE has no way to check or handle it generically. If you pass in the wrong format, TE can't check and will instead give you silent data corruption. If you pass the tensor to some other function (like dequantization), TE can't check and will give you silent data corruption.

The proper fix is to make `NVTETensor` aware of its swizzling format. Right now it has a bool `with_gemm_swizzled_scales`:
https://github.com/NVIDIA/TransformerEngine/blob/4a3a8a8e8578e96319467d0cc96b9f5db552a7d3/transformer_engine/common/common.h#L301

My first thought is to generalize to an enum so that we can distinguish between compact scales, swizzled for GEMM, swizzled for batched GEMM, and any formats we may add in the future. However, I think it'll be more complicated than that because the swizzle format changes depending on what is the batch dim.

An alternative is to make aspecific implementation for MXFP8. If we can't make the API general, we shouldn't pretend it's general. This API would look something like:
```c++
void nvte_cublas_gemm_strided_batched_mxfp8(
    int transa, int transb, const float *alpha,
    const NVTETensor A_data,  // dtype=fp8e4m3
    const NVTETensor A_scales,  // dtype=fp8e8m0
    ...
)
```
If we go this route, we'll also need to modify the swizzle functions so the output is not an `NVTETensor`.

Logically, the inputs to batched GEMM are 3D tensors, where the 3 dims are interpreted as the batch dim column dim, and row dim. We can figure everything out based on the batch dim and `trans*`:
- Batch dim tells us how to flatten to 3D. `batch_dim=0` means we flatten `[G, ..., D]` to `[G, flat, D]`. `batch_dim=-2` means we flatten `[..., G, D]` to `[flat, G, D]`.
- `trans*` tells us whether the col dim or row dim comes first. `transa=False` and `transb=True` means the last dim is `k`.

So we can make this significantly more logical and less redundant by replacing all of the stride and dim stuff with `batch_dim_a` and `batch_dim_b`.

For comparison, plain GEMM operates on 2D data and we implicitly flatten `[..., D]` to `[flat, D]`. Batched GEMM adds an extra dim, so one extra parameter seems fair.

Agreed, it's not pretty. The root cause is that the MXFP8 quantizer doesn't know about batch layouts. With `batch_dim=-2`, quantizing `[R, G, C]` column-wise would produce 32-row scaling blocks that mix batch entries, so the op quantizes the `[R, G*C]` view and the GEMM has to know about it. Removing the special case would need either a copy to `[G, R, C]`, which defeats the strided kernel, or batch-aware MXFP8 quantization. I'd rather leave the latter for a follow-up. For now the convention applies only to MXFP8 data with `batch_dim=-2`, and it's documented here and in the binding.

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **Short MXFP8 inputs fail**

Row-only MXFP8 inference fails when `batch_size * rows` is not divisible by 32. For example, `BatchedLinear(2, 64, 32)` with input shape `(2, 1, 64)` passes `_validate_mxfp8_dimensions` under `torch.no_grad()`. This call then sends the unchanged shape to `MXFP8Quantizer`, whose `create_tensor` requires the flattened row count to be divisible by 32. Inference raises before GEMM.

Pad row-only inputs before quantizing and keep the logical GEMM shape separate, or explicitly document and check this remaining restriction.
