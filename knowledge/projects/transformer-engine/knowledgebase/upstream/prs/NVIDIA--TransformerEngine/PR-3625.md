# Let the CUDA allocator manage cuBLAS workspaces

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3625) · state: open · merged: False

## Original PR description

# Description

Concurrent GEMMs on independent CUDA streams receive the same cuBLAS workspace from the device/mode cache and can overwrite each other's partial sums. On one H200, two FP32 `NT` GEMMs with a reduction dimension of 16384 produced incorrect results in 35 of 48 calls; separate scratch produced zero mismatches against serial execution.

Replace the Python workspace cache with invocation-local memory owned by PyTorch's CUDA allocator. Ordinary GEMMs allocate a native `DataPtr` in the PyTorch binding, avoiding per-call Python Tensor creation. The list/multistream grouped path uses one allocation with disjoint, 256-byte-aligned workspace slices. Its helper streams join the caller before the owner is released. Eager reuse remains stream-ordered; captured allocations belong to their graph's private pool. No persistent per-stream cache or new device synchronization is added.

Custom recipes and communication overlap retain explicit Tensor workspaces. Existing explicit-workspace callers remain supported; the private bindings additionally accept `None` with size zero to request native allocation. Usable workspace sizes, GEMM dtypes and algorithm selection are unchanged. The grouped-tensor backend is unchanged.

## Changes

- Allocate scratch per invocation in the PyTorch native binding for ordinary and list/multistream grouped GEMMs.
- Remove Linear and BasicLinear's preallocation workaround for globally cached scratch.
- Test eager ownership, temporary-stream cleanup, graph-pool isolation across capture generations, concurrent FP32/BF16 graph replay, grouped GEMM numerics, and compiled opaque-GEMM graph generations. Observe native allocation requests without retaining Tensor references.
- Cover router dgrad NN with `weight[128,4096]`, `grad_output[8192,128]`, output `[8192,4096]`, and reduction 128 against exact analytic references in FP32 and BF16. Preserve NT coverage.
- Include the workspace regression in the PyTorch L0 launcher.

<details>
<summary>Environment, timing and correctness checks</summary>

- One H200, Xeon Platinum 8570, one pinned host thread, default GPU clocks; PyTorch `2.13.0+cu130`, CUDA toolkit 13.0, cuBLASLt runtime 13.5.1, driver 615.71.09, native PyTorch caching allocator.
- Six main/PR process pairs, alternating AB/BA order. Each configuration used 50 timed warmup calls plus setup warmup, then seven batches of 20 calls. Factory measurements used seven batches of 20,000 calls after 1,000 warmup calls. Cyclic GC was disabled during timing.
