- zhongbozhu · comment · 2026-10-28T06:40:46Z · [source](https://github.com/NVIDIA/TransformerEngine/pull/3613#issuecomment-6462510217)

Document the rowwise usage & columnwise usage under fp8 param in this PR:

**Why it matters**
FP8 parameters persist across calls. A forward that does not need columnwise weight data—such as a no_grad() forward—must not disable a parameter’s existing columnwise usage, because subsequent training or recomputation may need it.

The module/op quantizer expresses the current call’s requirements. The parameter’s internal quantizer must preserve previously enabled usages. If these references point to the same object, changing the module/op quantizer also changes the parameter’s configuration. Copying determines whether those updates are independent.

The table below describes the PR snapshot we inspected, with FP8 primary weights and grouped-tensor execution, excluding grouped MLP fusion. c means “this call requires columnwise weight data.”

**TE behavior AFTER this PR**

<table>
  <thead>
    <tr>
      <th>Implementation</th>
      <th>Weight layout</th>
      <th>Quantizer ownership</th>
      <th>Forward handling of columnwise usage</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>Module</td>
      <td>Discrete</td>
      <td>Each MXFP8 parameter typically stores a <strong>copy</strong> of its module quantizer.</td>
      <td>Selects <code>weight._quantizer</code> directly and sets <code>columnwise=True if c else None</code>, then calls <code>quantize_weight()</code>.</td>
    </tr>
    <tr>
      <td>Module</td>
      <td>Single</td>
      <td>At construction, <code>weight.quantizer</code> <strong>shares the module’s first weight quantizer</strong>.</td>
      <td>Sets the parameter quantizer to <code>columnwise=True if c else None</code>, then returns the parameter.</td>
    </tr>
    <tr>
      <td>Op-fuser</td>
      <td>Discrete</td>
      <td>Parameters typically hold <strong>copies</strong>; recipe reset also assigns copies.</td>
      <td>Sets the <strong>op quantizer</strong> to <code>columnwise=c</code>, then the <strong>parameter quantizer</strong> to <code>columnwise=True if c else None</code>, and reuses the parameter.</td>
    </tr>
    <tr>
      <td>Op-fuser</td>
      <td>Single</td>
      <td>Shares the op quantizer at construction; <strong>recipe reset replaces it with a copy</strong>.</td>
      <td>Returns the already-quantized parameter directly, <strong>without updating weight-quantizer usage here</strong>.</td>
    </tr>
  </tbody>
</table>

<p>
  Here, <code>c</code> means this call requires columnwise weight data,
  and <code>None</code> preserves the existing setting.
  Preserving or enabling a quantizer flag does not itself create missing columnwise storage.
</p>

<a href="#"><img alt="P1" src="https://greptile-static-assets.s3.amazonaws.com/badges/p1.svg?v=9" align="top"></a> **FP8 backward fails on Hopper**

On Hopper, a discrete FP8 weight created under `torch.no_grad()` has no transpose buffer. Removing `w.update_usage(...)` means `_get_discrete_weights_for_gemm` now changes only quantizer flags when training later needs input gradients. Those flags do not build the missing buffer. Forward succeeds, but backward calls grouped GEMM with `layout="NN"` and fails because the weight has no columnwise data.

Keep the call that builds required layouts for existing quantized weights.
