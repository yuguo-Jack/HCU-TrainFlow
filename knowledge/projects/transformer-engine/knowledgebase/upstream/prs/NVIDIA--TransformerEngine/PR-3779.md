# [Common]  Add explicit CUDA state lifecycle APIs for in-process restarts

[Upstream PR](https://github.com/NVIDIA/TransformerEngine/pull/3779) · state: open · merged: False

## Original PR description

Add explicit CUDA state lifecycle APIs to prevent reuse of cached TE resources across in-process restarts. Release resources while CUDA remains usable, or invalidate supported native resources after externally managed context loss, and recreate them lazily.

Framework cleanup preserves model tensors and FP8 numerical history. Unsupported framework recovery and unsafe communication/JIT teardown fail explicitly.

## Changes

- Add release/reset APIs, per-device generations, a global atomic notification, and resource registration callbacks.
- Integrate streams/events, library handles, RTC modules, normalization/attention plans, and context-local kernel initialization. Retain handles from finished threads in a reusable ownership pool.
- Invalidate Workspace plans, TMA descriptors, and persistent contents; release current/retired PyTorch workspace allocations and rebuild them on reuse.
- Integrate PyTorch/JAX cleanup, device-scoped tensor caches, FP8 registrations, and CuTeDSL/TVM-FFI executor retirement.
- Integrate communication cleanup and reject unsafe teardown or stale EP buffers.
- Document lifecycle ordering and limitations; add native, frontend, JIT, and two-rank communication tests.

If I understand correctly, most of the complexity of this PR comes from removing this line. The logic:
1. We want to be able to survive past CUDA context restarts, which will invalidate static device variables.
2. TMA descriptors need to live in device memory. If they can't live in static variables, they need to live in a typical `cudaMalloc` buffer.
3. We want device allocations to be handled in the frameworks rather than in the core library.
4. Therefore we modify all of the APIs to accept framework-allocated workspace buffers.
5. We want some workspaces to be persistent across the session (like activation tables), so we need APIs for the frameworks to figure out the lifespan of the workspaces and the frameworks need singleton manager classes to hold persistent buffers.

Is 3 necessary? These workspaces are small and we were already allocating them automatically on the GPU. We could wrap them in a `Resource` that calls `cudaMalloc` during initialization and `cudaFree` during invalidation. This change would be purely internal to TE and would not change kernel behavior.

- timmoon10 · comment · 2026-10-29T23:14:21Z · [source](https://github.com/NVIDIA/TransformerEngine/pull/3779#discussion_r4418869318)

File: `transformer_engine/common/util/cuda_context.h` · line 30

Handling invalidation logic with a mixin class is a nice approach. As I see it, this class has the following contract:
- Class instances register themselves with a global registry with `bind_context`.
- The internal state of a `Resource` can be invalidated at any time. Any time you access a `Resource`, you need to check whether the state is invalidated and reinitialize if needed.

I wonder if we can make this more automatic:
- Class instances automatically register themselves in global registry (https://github.com/NVIDIA/TransformerEngine/pull/3779/changes#r4418682371).
- Have virtual functions for initialization and invalidation.

```c++
class Resource {
 public:
  Resource() {
    auto &state = registry();
    std::lock_guard<std::mutex> lock(state.mutex);
    state.resources.push_back(this);
  }
  void ensure_valid() {
    if (!valid_.load(std::memory_order_acquire)) {
      initialize();
      valid_.store(true, std::memory_order_release);
    }
  }

 private:
  friend void reset();
  virtual void initialize() = 0;
  virtual void invalidate() noexcept = 0;
  std::atomic<bool> valid_{false};
};

void reset() {
  auto &state = registry();
  std::lock_guard<std::mutex> lock(state.mutex);
  for (auto it = state.resources.rbegin(); it != state.resources.rend(); ++it) {
    if (it->valid_.load(std::memory_order_acquire)) {
      it->invalidate();
      it->valid_.store(false, std::memory_order_release);
    }
  }
  state.generate.fetch_add(1, std::memory_order_release);
}
```
The only requirement for subclasses is to implement the virtual methods and to call `ensure_valid()` before accessing state.
