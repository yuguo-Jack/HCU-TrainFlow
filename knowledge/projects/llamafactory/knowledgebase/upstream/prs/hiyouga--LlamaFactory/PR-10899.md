# [data] read dataset_info.json and cloud JSON as UTF-8

[Upstream PR](https://github.com/hiyouga/LlamaFactory/pull/10899) · state: open · merged: False

## Original PR description

# What does this PR do?

`get_dataset_list()` opens `dataset_info.json` with `open(config_path)` and `_read_json_with_fs()` calls `fs.open(path, "r")`, both with no encoding, so both use the platform's default text encoding. On Windows that is a legacy code page, not UTF-8. `webui/common.py` and `webui/components/data.py` already open the same `dataset_info.json` with `encoding="utf-8"`, so the CLI training path is the one that differs.

Measured on Windows 11, Python 3.12, default encoding `cp1254`, by calling the real functions (the same call path `llamafactory-cli train` takes):

```
dataset_info.json (UTF-8) = {"my_data": {"file_name": "数据.json"}}

before: ValueError: Cannot open ...\dataset_info.json due to 'charmap' codec can't decode
        byte 0x8d in position 31: character maps to <undefined>.
after : dataset_name == "数据.json"

read_cloud_json path, a UTF-8 JSON [{"instruction": "你好"}] read through fsspec:
before: 'ä½\xa0å¥½'   (no error, the text is silently corrupted)
after : '你好'
```

`cp1252` fails the same way as `cp1254` on these bytes. Under a GBK default (`cp936`) the first case would not raise: decoding the UTF-8 bytes of `数据.json` as `gbk` succeeds and gives `鏁版嵁.json`, a different file name. I measured that at the codec level (`bytes.decode("gbk")`); I could not run a process under `cp936` here.

The change passes `encoding="utf-8"` at both sites. It only matters when the file contains non-ASCII text: the `data/dataset_info.json` shipped in the repo is pure ASCII, so default setups are unaffected. A user-edited `dataset_info.json` (non-ASCII file names or descriptions) or a non-ASCII cloud dataset on a non-UTF-8 default is what breaks.

I checked the other `open()` calls under `src/` that have no `encoding`: they read binary data (`"rb"`, `Image.open`, `av.open`, `safe_open`) or JSON that `json.dumps()` wrote with the default `ensure_ascii=True` (`SWANLAB_CONFIG`, the v1 checkpoint `metadata.json`, the fsdp2 index files), so they do not depend on the locale and I left them alone.

## Tests

`tests/data/test_parser.py` runs the real functions in a child interpreter whose default encoding is not UTF-8 (`-X utf8=0`, plus `LC_ALL=C` and `PYTHONCOERCECLOCALE=0` for POSIX), so the tests fail without the change on Windows and on Linux alike, instead of only on a machine that happens to have a legacy locale. Non-ASCII text goes through `\u` escapes because a non-ASCII command-line argument cannot be decoded reliably under the C locale.
