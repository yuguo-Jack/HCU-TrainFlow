# test(webui): guard against hardcoded trust_remote_code=True (companion to #10903)

[Upstream PR](https://github.com/hiyouga/LlamaFactory/pull/10904) · state: open · merged: False

## Original PR description

## Summary

Adds a regression test that fails the build if any module under
`src/llamafactory/webui` hardcodes `trust_remote_code=True` again, plus a check that the
new `LLAMAFACTORY_WEBUI_TRUST_REMOTE_CODE` opt-in defaults to **off**.

Companion to the main fix in #10903.

## Finding

## PoC summary

An unauthenticated POST to the Gradio queue join endpoint for the Load-model handler with
`model_path` pointing at an attacker-controlled HF-style repo made `transformers` import and
execute the repo's `configuration_evil.py` inside the server process (marker written on host) —
before any weights load.

## What this test does

- `test_webui_does_not_hardcode_trust_remote_code` — parametrized over every `*.py` under
  `src/llamafactory/webui`, asserts no literal `trust_remote_code=True` argument exists.
- `test_webui_remote_code_gate_defaults_to_disabled` — asserts
  `is_env_enabled("LLAMAFACTORY_WEBUI_TRUST_REMOTE_CODE")` is `False` when the env var is unset.

Run with:

```bash
pytest tests/webui/test_no_hardcoded_trust_remote_code.py
```

## Fix explanation

This test *enforces* the fix from #10903: remote code execution is only reachable through an
explicit server-side opt-in, never through a user-supplied model path. Any future change that
reintroduces a hardcoded `True` will fail CI.
