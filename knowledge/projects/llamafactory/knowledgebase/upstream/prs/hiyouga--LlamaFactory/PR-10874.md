## Original PR description

# PR: Precompute `length` column to support length-grouped batching

> Upstream: https://github.com/hiyouga/LLaMA-Factory (based on v0.9.5)
> Title: `feat(data): precompute length column for efficient group_by_length sampling`

## PR body (copy into the GitHub PR form)

### Motivation

In non-packed SFT/PT training, LLaMA-Factory feeds randomly shuffled batches to the model and the collator pads every sample to the longest sequence **in the batch**. On real-world datasets with long-tailed length distributions this wastes a substantial amount of compute on padding tokens.

Our measurements on the same hardware, same weights, same data (Qwen2.5-14B-Instruct + LoRA, `per_device_train_batch_size=4`, `cutoff_len=1024`, datasets: `norobots`, `oasst1`, EV-charging QA, 1 epoch each):

| layout | effective tokens/step | padding compute overhead | wall clock |
|---|---:|---:|---:|
| random batches, pad to batch-max (current default) | ~835 | ~30% | 83.3 min |
| length-grouped layout (bucketed so similar lengths share a batch) | ~835 | ~0% | 37.0 min |

The full bucketed + varlen-packed layout of our scheduler reaches **2.25x wall-clock speedup (1074 vs 489 tok/s)** and +1.8 pt mean F1 over the padded-batch baseline, with the same model, data, LoRA config and seed. Length grouping is the first and cheapest layer of that gain.

Transformers already ships the machinery for this: `LengthGroupedSampler` groups roughly-equal-length samples into the same batch while keeping some randomness (no curriculum bias). But today it is impractical to use in LLaMA-Factory:

1. The tokenized dataset has no `length` column, so `LengthGroupedSampler` falls back to materializing `len(feature["input_ids"])` for **every sample of the dataset** at startup — slow and memory-hungry;
2. A `length` column added by the user would leak into the collator output and crash `model.forward`.

### What this PR does

1. `SupervisedDatasetProcessor.preprocess_dataset` (non-packed SFT) now emits a precomputed `length` column — the value is already known at tokenization time, so this is essentially free.
2. `PretrainDatasetProcessor.preprocess_dataset` (non-packed PT) does the same.
3. `MultiModalDataCollatorForSeq2Seq.__call__` pops the `length` helper column so it never reaches the model.

With this, length-grouped batching works out of the box:

```bash
# transformers >= 5.0
llamafactory-cli train ... --train_sampling_strategy group_by_length

# transformers 4.x
llamafactory-cli train ... --group_by_length true
```

The `length` column is also persisted by `tokenized_path`, so cached tokenized datasets benefit too.

### Notes

- `LengthGroupedSampler` still shuffles (megabatch-wise), so training randomness is preserved.
- No need to enable this together with `packing`: packed samples are all padded to `cutoff_len` anyway.
- Eval datasets get the same column; it is dropped by the collator, so evaluation is unaffected.
- Works for both map-style datasets (sampler reads `length_column_name="length"` directly) — streaming mode ignores the sampler as before.

### Testing

Verified locally on LLaMA-Factory 0.9.5 / transformers 5.6.0: preprocessing emits the `length` column, `LengthGroupedSampler` consumes it without the slow length-materialization path, and training runs with `--train_sampling_strategy group_by_length`. Existing CPU collator tests still pass.
