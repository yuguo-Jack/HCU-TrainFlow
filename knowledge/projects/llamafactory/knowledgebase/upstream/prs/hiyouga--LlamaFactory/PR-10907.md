# fix: supply Qwen3-VL modality IDs during prediction

[Upstream PR](https://github.com/hiyouga/LlamaFactory/pull/10907) · state: open · merged: False

## Original PR description

## Problem

Qwen3-VL generation uses a collator with `model=None`, so it cannot precompute M-RoPE positions. Its plugin does not supply `mm_token_type_ids`; Transformers 5.8 therefore raises when computing positions for image/video inputs. Fixes #10905.

## Change

For Qwen3-VL collators without an attached model, build missing modality IDs from the **fully padded** input IDs using the processor helper. Retain existing IDs and leave model-attached training, other plugins, and processors without the helper unchanged.

## Tests

```sh
PYTHONPATH=src CUDA_VISIBLE_DEVICES=-1 pytest -q \
  tests/data/test_qwen3_vl_mm_token_types.py \
  tests/data/test_collator.py::test_4d_attention_mask \
  tests/data/test_mm_plugin.py::test_qwen3_vl_plugin
```

24 passed on Python 3.12 / Transformers 5.8.0. The new regression suite changes from 19 failed / 3 passed to 22 passed. It covers image/video/mixed/text IDs, both padding sides, padding to a multiple, dummy images, an older processor interface, Qwen2-VL, and tiny randomly initialized Qwen3-VL prediction/training. Two tiny-model checks also passed on CUDA. Ruff 0.15.5 lint/format and the relevant license checks passed.

## Compatibility

No new dependencies or pretrained weights. Media extraction is mocked in the new unit tests; the existing Qwen3-VL plugin test uses real processor/tokenizer data. Full pretrained-model metrics, the full suite, Linux, and older Python/Transformers were not run. This targets missing prediction IDs; #10397 addresses existing-ID padding/packing separately.

## Independent verification on a single 24 GB GPU

I reproduced the mechanism on `main` and then re-ran it with this patch applied, using the **real Qwen3-VL-2B-Instruct weights** rather than a tiny random model.

**Setup:** RTX 4090 (24 GB), Python 3.11.15, PyTorch 2.7.0+cu128, Transformers 5.8.0, `Qwen/Qwen3-VL-2B-Instruct`.

### 1. Collator output (predict path, `model=None`)

| | batch keys |
|---|---|
| `main` | `attention_mask, image_grid_thw, input_ids, labels, pixel_values` |
| this PR | `attention_mask, image_grid_thw, input_ids, labels, **mm_token_type_ids**, pixel_values` |

With the patch, `mm_token_type_ids` has shape `(1, 464)` and values `{0, 1}` — built from the padded batch, as the PR describes.

### 2. Your test suite, different Python

`PYTHONPATH=src pytest -q tests/data/test_qwen3_vl_mm_token_types.py` → **22 passed** on Python 3.11.15 (you reported 3.12). No failures, no skips.

### 3. End-to-end `do_predict` (the part that was untested)

One synthetic 640×640 image with a red square at pixels `(200,150)-(440,390)`, prompt asking for `[[x1,y1,x2,y2]]` with no unit specified, greedy decoding, `predict_with_generate: true`, `max_new_tokens: 64`. Same model, same prompt, only the patch differs:

| | predicted box | IoU vs ground truth |
|---|---|---|
| `main` | `[[205,242,700,700]]` | **0.600** |
| this PR | `[[277,220,683,620]]` | **0.847** |

IoU is computed in Qwen3-VL's 0–1000 normalised coordinate space. I confirmed that convention empirically rather than assuming it: on a 1600×1200 image with the box at pixels `(1100,800)-(1500,1100)` (normalised `(688,667)-(938,917)`), the model returns `[[666,650,925,915]]` — no value exceeds 1000, so it is not emitting pixel coordinates. Comparing against pixels instead gives 0.14 for both runs and would wrongly suggest the fix does nothing.

The result also reproduces: two runs of the patched build on the same input give the same box.

So supplying the modality IDs does change what `do_predict` actually produces, in the direction the issue reports.

### What this does **not** establish

- One synthetic sample, not a benchmark — no claim about IoU/F1 on real document data, and no statistical significance.
- Greedy decoding only, single image, no video, no batching beyond size 1.
- I did not test the training path, `predict_with_generate: false`, or other VLM plugins.

### Relation to #10397

Worth flagging since both PRs touch the same block in `collator.py`. #10397 (open since April, still `pending`) handles the opposite case: it preserves and pads `mm_token_type_ids` that the processor *already* produced, and carries them through packed RoPE. This PR only fills the case where they are absent.

They look compatible — the `"mm_token_type_ids" not in features` guard still triggers after #10397 lands, since the Qwen3-VL plugin still does not create them on the predict path — but whichever merges second will need a rebase around that block.

### Setup notes

Two things that tripped me up and might be worth adding to the PR description: `do_predict` requires `eval_dataset` (or `val_size`), and a sharegpt dataset needs `{"from","value"}` message keys. Neither is a problem with the change itself.
