# fix: add None check for feature_extractor in Gemma4Plugin audio processing

[Upstream PR](https://github.com/hiyouga/LlamaFactory/pull/10388) · state: open · merged: False

## Original PR description

## Summary

Resolve Gemma4's audio extractor consistently with input validation: prefer `feature_extractor`, then fall back to `audio_processor`. Both `_get_mm_inputs` and the audio token expansion path must use the same resolved component and sampling rate.

The earlier guard that could suggest silently emitting a single token when an extractor is absent has been removed. If neither component exists, the existing `_validate_input` raises `ValueError: Audio feature extractor was not found...` before preprocessing. Single-token output remains intentional only when `expand_mm_tokens=False`.

Normally merged current main `9997aa07`, resolving the test conflict while retaining main's XPU coverage marker. The net contribution is two files; no model definitions, dependencies or training behavior are changed.

## Regression coverage

The existing lightweight test now has ten cases:

- Feature extractor only; audio processor with the feature attribute missing; audio processor with the feature attribute explicitly None; both components present, preferring the feature extractor.
- Enabled/disabled token expansion, selected sampling rate, extractor invocation and unchanged input messages.
- Both components absent or None must raise the existing clear validation error.

These execute the real `process_messages` and `_get_mm_inputs`. Only audio-I/O normalization and the external processor are controlled; no replacement implementation of the plugin is tested.

On unchanged main `9997aa07`, with the production module path verified: **2 failed, 8 passed** (the two enabled-expansion fallback cases fail by calling None). With this PR: **10 passed**, then independently repeated twice after the final edit.

The `getattr` call is placed inside a nested loop (`for message in messages` -> `while AUDIO_PLACEHOLDER in content`), which is inefficient as the `processor` object and its attributes do not change during this process. Consider moving this assignment before the `for message in messages:` loop (around line 743) to avoid redundant lookups.

Additionally, to be consistent with the validation logic in `_validate_input` (lines 158-160), it should also check for `audio_processor` if `feature_extractor` is missing or `None`.

```suggestion
                feature_extractor = getattr(processor, "feature_extractor", None) or getattr(processor, "audio_processor", None)
```

File: `src/llamafactory/data/mm_plugin.py` · line 1099

The `or audio_processor` fallback looks right, but the second half of the change trades a loud failure for a quiet one. When `feature_extractor` is None and `expand_mm_tokens` is True, this now takes the `else` branch and emits a single un-expanded audio placeholder, so the prompt carries the wrong number of audio tokens and the run fails later inside the model with a shape error that points nowhere near here.

If a processor really can arrive without any audio extractor while audio inputs are present, raising with a message that names the missing component would be more useful than silently under-expanding.
