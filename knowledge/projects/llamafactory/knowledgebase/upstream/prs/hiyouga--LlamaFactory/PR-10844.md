# [feat] add biren supa accelerator support

[Upstream PR](https://github.com/hiyouga/LlamaFactory/pull/10844) · state: open · merged: False

## Original PR description

# What does this PR do?

This PR adds **Biren SUPA** (`torch_supa`, a PyTorch `PrivateUse1` backend exposed as `torch.supa` /
device string `supa:<idx>`) as a first-class accelerator in LlamaFactory, and ships the first fused
SUPA operator — a fused RMSNorm kernel plugin for the v1 kernel framework.

Before this PR, SUPA devices could only be driven through the CUDA-masquerading path, which silently
picked unsupported backends (FlashAttention-2, Liger/Triton kernels) and hard-coded `.to("cuda")`
tensor movement. After this PR, device detection, memory/profiling accounting, attention/kernel
selection and the Ray launcher all understand `supa`, and no CUDA-specific code path is taken on a
SUPA machine.


## 1. Device plumbing (v0)

`src/llamafactory/extras/misc.py`
- New `is_torch_supa_available()`: imports `torch_supa` (which registers the `supa` device) and
  checks `torch.supa.is_available()`; cached with `functools.lru_cache`, returns `False` on any
  import/runtime error so non-SUPA environments are unaffected.
- `_is_fp16_available` / `_is_bf16_available` now consider SUPA (`torch.supa.is_bf16_supported()`).
- SUPA branches added to `get_current_device()`, `get_device_name()`, `get_device_count()`,
  `get_current_memory()`, `get_peak_memory()`, `is_accelerator_available()` and `torch_gc()`.

`src/llamafactory/extras/env.py`
- `llamafactory-cli env` now reports `PyTorch version (SUPA)`, SUPA device name, device count and
  total memory, so bug reports from SUPA users carry the right hardware info.

`src/llamafactory/hparams/parser.py`
- `_set_env_vars()`: eagerly imports `torch_supa_ext` so the fused `torch.ops.sudnn.*` operators are
  registered. `torch_supa` is auto-loaded by `import torch`, but `torch_supa_ext` is not — without
  it the eager path is used and training is extremely slow, so a rank-0 warning is emitted instead
  of failing hard.
- `_set_env_vars()`: forces `VLLM_WORKER_MULTIPROC_METHOD=spawn` on SUPA (fork-unsafe device
  handles), mirroring the existing NPU workaround (#7447).
- `_check_extra_dependencies()`: `use_unsloth` now raises a clear error on SUPA instead of failing
  deep inside Unsloth's CUDA kernels.
- `get_train_args()`: `pure_bf16` is accepted when `torch.supa.is_bf16_supported()` is true.

`src/llamafactory/train/callbacks.py`
- `ModuleProfilerCallback._get_accelerator()` returns `torch.supa.Event` / `torch.supa.synchronize`,
  so per-module timing works on SUPA.

`src/llamafactory/train/tuner.py`
- Added `RAY_EXPERIMENTAL_NOSET_SUPA_VISIBLE_DEVICES` to the Ray no-set list, so Ray-managed SUPA
  device visibility is respected like CUDA / Ascend.

## 2. Backend-specific code paths

`src/llamafactory/model/model_utils/attention.py`
- `flash_attn: auto` previously returned early and let Transformers resolve the implementation,
  which on a CUDA-masqueraded SUPA device can select FlashAttention-2 — there is no FA build for
  SUPA. `auto` now pins `sdpa` on SUPA, the fastest supported backend there.

`src/llamafactory/model/model_utils/liger_kernel.py`
- Liger kernels are Triton/CUDA-specific; `enable_liger_kernel` is now skipped with a rank-0 warning
  on SUPA (pointing users at the fused SUPA RMSNorm instead) rather than crashing at compile time.

`src/llamafactory/model/model_utils/checkpointing.py`
- The Unsloth-style offloaded gradient checkpointing moved the CPU-saved hidden states back with a
  hard-coded `.to("cuda")`. The forward now records `ctx.device = hidden_states.device` and the
  backward restores to that device. **This is a general fix** — it also unbreaks
  `use_unsloth_gc` on NPU/XPU, not just SUPA.

## 3. fused RMSNorm kernel

`src/llamafactory/v1/accelerator/helper.py`
- New `DeviceType.SUPA` enum member.

`src/llamafactory/v1/plugins/model_plugins/kernels/ops/rms_norm/supa_rms_norm.py` (new)
- `SupaRMSNormFunction`: an `autograd.Function` whose forward calls the fused
  `torch.ops.sudnn.rms_norm_func` and whose backward is the analytic RMSNorm gradient
  (`grad_input = rrms * ĝ - (rrms³ / H) · x · (ĝ·x)`, `grad_weight = Σ(grad_out * x_norm)`),
  recomputing `rrms` from the saved input instead of keeping extra activations.
- `SupaRMSNormKernel` registered as the `supa_fused_rmsnorm` kernel plugin: per-module monkeypatch
  of `forward`, keeping the original as `_supa_rmsnorm_original_forward` so non-SUPA tensors fall
  back, idempotent via a `_supa_rmsnorm_patched` guard, and a rank-0 summary of how many modules
  were patched.
- Patching is restricted by an explicit **allow-list** of RMSNorm classes that follow the standard
  `y = x * rsqrt(mean(x²)+eps) * weight` convention (Llama/Mistral/Mixtral/Phi3/InternLM2/GLM/
  DeepSeek-V2,V3/Qwen2,2-MoE,2-VL,2.5-VL,3,3-MoE,3-VL). Variants with a different weight convention
  (Gemma's `1 + weight`, gated/residual RMSNorm) are deliberately excluded and keep the eager path,
  so a silent numerical mismatch is impossible — adding a model means verifying the convention and
  appending the class name.
- If `torch_supa_ext` / `torch.ops.sudnn.rms_norm_func` is missing, the plugin warns and returns the
  model untouched.

`src/llamafactory/v1/plugins/model_plugins/kernels/interface.py`
- Registers the new kernel and maps `DeviceType.SUPA → ("supa_fused_rmsnorm",)` in `_AUTO_KERNELS`,
  so `kernel_config.name: auto` enables it on SUPA. It is also reachable from v0 via
  `use_v1_kernels: true`.
