# [data] fix gemma4 tool_extractor reading colons inside string arguments as keys

[Upstream PR](https://github.com/hiyouga/LlamaFactory/pull/10885) · state: open · merged: False

## Original PR description

# What does this PR do?

`Gemma4ToolUtils.tool_extractor` converts the Gemma 4 call syntax to JSON in two regex passes: first `<|"|>...<|"|>` becomes a JSON string, then every bare identifier followed by `:` gets quoted. The second pass also runs inside the strings produced by the first one, so a string argument such as `Hi Tom, Re: the plan` becomes `"Hi Tom, "Re": the plan"`. `json.loads` then fails and the extractor returns the raw text as the arguments string.

This also means `function_formatter` output does not round-trip:

    <|tool_call>call:f{text:<|"|>Dear John, Re: the meeting<|"|>}<tool_call|>
    -> FunctionCall(name='f', arguments='text:<|"|>Dear John, Re: the meeting<|"|>')

The fix does both steps in one left-to-right `re.sub` with alternation. A whole `<|"|>...<|"|>` string is matched first, so its content is never treated as a key. Key quoting outside strings is unchanged.

Tests: `test_gemma4_tool_extractor_colon_in_string` and `test_gemma4_tool_round_trip` in `tests/data/test_formatter.py`. Both fail on main with `JSONDecodeError` and pass with this change. `tests/data/test_formatter.py`: 48 passed. `ruff check` and `ruff format --check` are clean.

- ErenAta16 · COMMENTED · 2026-10-19T12:59:27Z · [source](https://github.com/hiyouga/LlamaFactory/pull/10885#pullrequestreview-5571891430)

Checked this against both versions of `tool_utils.py`, not only the diff. I could not run the pytest module in my environment (the test package imports `trl`), so I loaded `tool_utils.py` from `main` and from your head and called `function_formatter` and `tool_extractor` directly.

Your two scenarios behave as described. On `main` the extractor returns the raw text `body:<|"|>Hi Tom, Re: the plan<|"|>,to:<|"|>tom<|"|>` instead of parsing it, and the dict from `test_gemma4_tool_round_trip` does not come back equal; on this branch both parse back to the original arguments.

To check beyond your cases I swept the round trip with the original arguments as the oracle: every string of up to three characters over `a _ : , { } space " \n \ < | > 1 [ ]` (4,369 strings) placed as `{k: s}`, `{k: {n: s}}` and `{k: [s]}`, plus all pairs of strings up to two characters as `{a: s, b: t}` (74,529 pairs). On `main`, 6 strings per single-string shape fail, for example `,a:` and `,_:`, because the key pass reads them as a key. On this branch 0 fail, and no case that passes on `main` fails here.

Nothing blocking from me. Two observations, both optional:
- `,a:` is the shortest string the sweep found that breaks `main`; it would make a compact extra parametrized case next to the `Re:` example.
- The format itself cannot carry a string that contains the marker `<|"|>`; that is unchanged by this PR and not something it needs to solve.
