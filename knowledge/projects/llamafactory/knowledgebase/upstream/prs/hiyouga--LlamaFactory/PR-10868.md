# enable fp16 in dtype inference on Intel XPU

[Upstream PR](https://github.com/hiyouga/LlamaFactory/pull/10868) · state: open · merged: False

## Original PR description

# [xpu] enable fp16 in dtype inference on Intel XPU

# What does this PR do?

Fixes # (issue)

Makes `infer_optim_dtype()` pick float16 on Intel XPU, as it already does on CUDA and NPU. On an fp16 checkpoint, this makes QLoRA training **3.1× faster** and QLoRA inference **1.35× faster** on XPU, with the same loss curve and byte-identical generations.

`_is_fp16_available` in `extras/misc.py` only checks NPU and CUDA:

```python
_is_fp16_available = is_torch_npu_available() or is_torch_cuda_available()
```

So on XPU, `infer_optim_dtype(torch.float16)` falls through to `torch.float32`, even though XPU supports fp16 (`is_torch_fp16_available_on_device("xpu")` is `True`). The bf16 check on the next line already handles XPU through `is_torch_bf16_gpu_available()`.

The resulting `compute_dtype` becomes bitsandbytes' `bnb_4bit_compute_dtype`. On XPU, 4-bit weights were therefore dequantized and multiplied in fp32 against fp16 activations.

This only happens when LLaMA-Factory infers the dtype itself:
- inference with the default `infer_dtype: auto`, e.g. `llamafactory-cli chat` with `quantization_bit: 4`
- training with neither `bf16` nor `fp16` set

Runs with `bf16: true` are unaffected.

### Changes

- `src/llamafactory/extras/misc.py`: add `or is_torch_xpu_available()` to `_is_fp16_available`

The added condition is only true on XPU, so CUDA and NPU behaviour is unchanged.

### Testing

Intel Arc Pro B60, Python 3.12.13, torch 2.14.0+xpu, transformers 5.8.0, bitsandbytes 0.50.2, peft 0.18.1. Before = `main` (ce9dc9e0), after = this branch. Same card, runs interleaved before/after, 2 reps each.

**QLoRA training:** `facebook/opt-6.7b` (fp16), 4-bit, LoRA r=8 on all linear layers, `alpaca_en_demo`, cutoff 1024, batch 2, 40 steps, no precision flag.

| | bnb compute dtype | Median step time | `train_runtime` | Peak memory | Final loss |
|---|---|---|---|---|---|
| Before, rep 1 | float32 | 2.557 s | 100.2 s | 4.68 GiB | 1.6948 |
| Before, rep 2 | float32 | 2.553 s | 99.3 s | 4.68 GiB | 1.6941 |
| After, rep 1 | **float16** | **0.822 s** | **36.4 s** | 4.61 GiB | 1.6941 |
| After, rep 2 | **float16** | **0.805 s** | **34.6 s** | 4.61 GiB | 1.6954 |

That is 3.1× per step and 2.8× end to end. All 40 steps are finite in every run. The per-step losses of before and after differ by at most 0.022, and the mean loss over 40 steps is 1.796 in both. Peak memory is essentially unchanged, since it's dominated by the model itself.

**QLoRA inference:** `NousResearch/Llama-2-7b-hf` (fp16), `quantization_bit: 4`, HF engine via `ChatModel`, greedy decoding, 4 prompts × 128 new tokens.

| | bnb compute dtype | Throughput (rep 1 / rep 2) |
|---|---|---|
| Before | float32 | 16.2 / 19.0 tok/s |
| After | **float16** | **22.4 / 25.4 tok/s** |

Generated text is byte-identical before and after, for all 4 prompts.

Test suite (`pytest tests/ tests_v1/`) on XPU: 342 passed, 0 failed
