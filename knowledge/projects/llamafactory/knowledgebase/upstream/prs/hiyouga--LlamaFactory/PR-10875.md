# [export] keep exported tokenizer_config loadable with transformers<5

[Upstream PR](https://github.com/hiyouga/LlamaFactory/pull/10875) · state: open · merged: False

## Original PR description

# What does this PR do?

Fixes #10310, related to #10169.

When exporting with transformers>=5, `tokenizer_config.json` can end up with things transformers 4.x can't read, so vLLM builds that still use transformers 4.x fail to load the merged model:

- `tokenizer_class: "TokenizersBackend"`, which happens for models that have no tokenizer mapping in that transformers version, e.g. Qwen3.5 on 5.2: `ValueError: Tokenizer class TokenizersBackend does not exist`
- `extra_special_tokens` saved as a list, e.g. Qwen3 on 5.8: `AttributeError: 'list' object has no attribute 'keys'`

After the tokenizer/processor are saved, `export_model` now restores the base model's `tokenizer_class` (falling back to `PreTrainedTokenizerFast`) and moves a list-valued `extra_special_tokens` to `additional_special_tokens`. This only runs on transformers>=5; configs that are already compatible are left as they are.

This is the export side; #10767 handles list-shaped `extra_special_tokens` when LlamaFactory itself loads a tokenizer on 4.x, and doesn't touch exported files.

The missing `vocab.json`/`merges.txt` from #10169 are expected with v5, which only writes `tokenizer.json`, and fast tokenizers load fine without them. The actual load failure comes from the config.

Tested with tiny random Qwen3 / Qwen3.5 weights plus the real Qwen3-8B / Qwen3.5-0.8B tokenizer files:
- export on transformers 5.2.0 and 5.8.0; before the change, loading the result with transformers 4.57.6 fails with the errors above, and after it, it loads (`Qwen2TokenizerFast`, same ids)
- reloading with transformers 5.x gives identical encodings, special tokens and chat template
- new unit tests in `tests/train/test_export_tokenizer_config.py`; `tests/e2e/test_train.py -k export`, `make quality` and the license check pass
