# Kernel Fusion Include Capture Folder

[Upstream PR](https://github.com/AMD-AGI/TraceLens/pull/1130) · state: closed · merged: True

## Original PR description

## Summary

On graph-capture traces, the orchestrator's prepare step (Steps 3-6) built its tree from the raw trace, while the Step 1 perf report merged the capture folder first. Layers replayed through the graph were invisible to prepare, so kernel fusion detection never saw them. Prepare now builds the same merged tree as the report. Net: 4 files changed, +57/-6.

## Why

| Case | Old | New |
|---|---|---|
| Inference trace with a capture folder | prepare loads the raw trace; replayed layers are missing, so fusion candidates inside them are never found | prepare merges the capture folder, as the report does, and fusion sees the replayed layers |
| Capture merge fails | n/a | prints "Capture merge failed; using the raw trace" and falls back to the old path |
| No capture folder (training, eager, comparative without capture) | raw trace | unchanged |

## What changed

### Python (2 files)

| File | Change |
|---|---|
| `TraceLens/Agent/Analysis/utils/orchestrator_prepare.py` | New `--capture-folder` flag. When set, `merge_capture_trace_into_graph` builds the tree from the capture folder and its `execution_details.json` (written by Step 1), and `TreePerfAnalyzer` wraps it with `rebuild_tree=False`. Falls back to `TreePerfAnalyzer.from_file` when the merge returns nothing. |
| `TraceLens/Agent/Analysis/utils/config_utils.py` | `check_config` emits `capture_folder` for job 1 when the run yaml sets one. |

### Orchestrator (1 file)

| File | Change |
|---|---|
| `TraceLens/Agent/Analysis/skills/analysis-orchestrator/reference.md` | The prepare command takes `[--capture-folder <capture_folder>]`, passed only when `config_utils` printed it. Notes that the call can run for several minutes and should get the longest timeout the runner allows. |

### Tests (1 file)

| File | Change |
|---|---|
| `tests/test_analysis_agent_config_utils.py` | One new parameter, `standalone_capture`: a standalone inference config with a capture folder prints `capture_folder=`. |

## Validation

- **Unit and format.** The targeted tests pass. In the broad suite, the only failures also fail on the clean base (a live-GPU test and JAX import errors). `black` is clean.
- **Regression harness.** Every case without a capture folder is byte-identical to the base. Capture cases differ only in fusion-derived outputs, and every diff is covered by a frozen allowlist that rejects anything not fusion-derived. Prepare's output is byte-identical to an oracle that loads the report's own merged tree.
- **Agent smoke runs.** Full agent runs on two graph-capture inference traces and one eager trace all finished and wrote analysis.md. Prepare merged the capture folder on both graph traces with no failure. The eager trace took the unchanged path.

## Effect on findings

On the graph-capture traces, the fusion detector now finds additional candidates inside the replayed layers (quantize and GEMM-epilogue chains). In the smoke runs none of them cleared the existing pricing gate (2% of E2E), so the rendered report did not change. The eager trace's findings are unchanged.

## Cost

Prepare re-runs the capture merge that Step 1 already did, so prepare time on capture traces grows with the size of the capture. On large captures it can run for several minutes and come close to Claude Code's default 600 s command cap. Runners should set `BASH_MAX_TIMEOUT_MS`. Traces without a capture folder are unaffected.

## Not in this PR

- Persisting the report's merged tree so prepare stops re-merging. This removes the cost above and is the planned follow-up.
- `validate_findings_file(..., "fusion", "standalone")` rejects the empty fusion findings file that the spec requires. This happens on the base too; the empty-file exemption only covers the compute tier.
