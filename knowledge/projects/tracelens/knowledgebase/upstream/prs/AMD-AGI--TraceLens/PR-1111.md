## Original PR description

# Release Notes (10/23)

## Summary

This release merges `staging_agent` into `main` for the TraceLens Agent. It has three
themes. First, the agent can now **run from a YAML run config** that uses the same schema as
`TraceLens_generate_perf_report_from_config`. Second, a new **multi-trace standalone** scope
analyzes several jobs of one workload, such as prefill and decode, in a single report.
Third, **kernel fusion is reworked**: it now reports in the compute tier's shape, every
fusion decision comes from one kernel taxonomy, and fusion now detects candidates on
graph-capture traces. Net: **55 files changed, +6904 / −4108**.

---

## Key Features

### 1. Run the Agent from a YAML Config

(PR #1121, which carries #1094)

- Besides the interactive Step 0 questions, the agent now accepts "run it from config
  `<run.yaml>`". Both front ends produce one config in the schema of the perf report
  wrapper.
- New `utils/config_utils.py` (`check_config`, `add_diff_stats`, and the
  `build` / `check` / `set-diff-stats` CLI). Step 0 adds the job names, the comparison
  target and the agent's required report flags in code, printing every change, and reports
  all shape errors at once before the wrapper's own validation runs.
- Step 1 is now one `TraceLens_generate_perf_report_from_config` call on
  `cache/run_config.yaml`. The per-CLI flag tables `reference.md` used to assemble command
  lines are gone. The wrapper writes `run_config.resolved.yaml` with every flag explicit.
- Carries the wrapper itself from #1094: `TraceLens/Reporting/generate_perf_report_from_config.py`,
  its `setup.py` entry point, `docs/how-to/generate-perf-report-from-config.md`, and
  `tests/test_perf_report_from_config*.py`.

### 2. Multi-Trace Standalone Analysis

(PRs #1141 and #1144; #1141 carries #1126)

- New `multi_trace` scope: two or more jobs of one workload on one platform, for example
  the prefill and decode captures of one vLLM server, analyzed in one run with one
  report. Every compute `impact_score` is a percent of the combined GPU time of all jobs,
  so P1 is the biggest win for the whole workload.
- Each compute P-item carries a `**Phase**` line and `phase=` on its `p_item` marker.
  `validate_report` rule R6 checks the marker phase against the findings.
  `analysis.json` compute tasks bucket by `(phase, operation)` and carry an optional
  `phase`.
- Kernel fusion and system analysis (CPU/idle, multi-kernel) run on the focus job, which is
  the first job in the config. Fusion suppression is keyed by phase, so suppressing a decode
  row leaves the identical prefill row scored.
- From #1126: `TraceLens/Reporting/aggregate_perf_reports.py` and the wrapper's
  `aggregation: {policy}` key write `perf_report_aggregated_csvs/` with a leading `phase`
  column. Under `combine_only_same_phase`, jobs that share a phase are combined.
- #1144 makes the multi-trace YAML a plain wrapper YAML: the `focus_job` key and the
  `--focus-job` prepare flag are removed. `compare_to` may name job 2 instead of repeating
  its paths. In comparative and semantic runs, job 2's platform is rewritten only when it
  has no arch file.
- `category_manifest.json` gains `focus_job`, `focus_csv_dir`, `capture_folder` and
  `gpu_utilization.jobs[<name>] = {phase, ...}`. `perf_report_csv_dir` and model
  identification read `focus_csv_dir`.
- A single graph-replay-only trace now continues to the Step 2 gate and takes the
  deterministic fallback in both modes. The "Trace Feature Detection" abort and the
  `check_gpu_graph_replay` triage check are removed. The fallback judges graph-replay
  coverage per phase.

### 3. Kernel Fusion Aligned with the Compute Tier

(PR #1093)

- Fusion `**Data:**` tables use compute's 10 columns, with one row per launching op and
  args, built from the same perf-report rows and helpers.
- Fusion time is the sum of real kernel time over every instance. Before, it was the first
  instance's time multiplied by `instance_count`, which overstated modules whose instances
  differ in shape.
- The perf-row lookup and compute's double-count suppression both key on `perf_row_key`
  (op name, args, process and thread) instead of the kernel name.
- `analysis.json` gains `fusion_optimizations[]`, sorted on `impact.mid` like compute.
  The fusion `operation` is the bare name, without the severity badge.
- A `—` `op_row` cell (fusion-flagged row) now scores 0 instead of back-filling to
  `pct_e2e × 0.30`.

### 4. Kernel Taxonomy and One Fusion Module

(PRs #1110 and #1124)

- `KernelTaxonomy` in `utils/classify_kernels.py` maps a kernel name to a
  `KernelClass(type, perf_category, covers)`. One rule table replaces two duplicated
  blocks and adds types such as Add+RMSNorm, RMSNorm+Quant, RoPE+KV Store, TopK, Softmax,
  Reduce, LayoutTransform and Convolution.
- New `utils/kernel_fusion.py` gives each fusion decision one owner: `FusionForms`,
  `FusionLabeler`, `FusionCandidateBuilder` and `FusionPricer`. About 700 lines of fusion
  code leave `orchestrator_prepare.py`, and `kernel_fusion_analysis.py` becomes a thin CLI.
- Candidates and metrics carry a deterministic `fusion_kind` and `confidence`. The
  sub-agent writes a `**Kind:**` line per finding, and `analysis.json` carries it as
  `FusionTask.kind`.
- A high-confidence finding suppresses only the ops its fusion removes. For example, an
  `act_mul` finding no longer hides the GEMMs around it, which keep their own findings.
- #1124 memoizes `KernelTaxonomy._match` and `FusionCandidateBuilder._launch`.

### 5. Fusion on Graph-Capture Traces

(PR #1130)

- On graph-capture traces, prepare (Steps 3-6) now builds the same capture-merged tree as
  the Step 1 report, through a new `--capture-folder` flag. Fusion detection can now see
  layers replayed through the graph. If the merge fails, prepare falls back to the raw
  trace.
- Prepare re-runs the capture merge Step 1 already did, so on large captures it can near
  Claude Code's 600 s command cap. Runners should set `BASH_MAX_TIMEOUT_MS`.

### 6. Cleanups

(PRs #1103 and #1109, plus commits `5da43f3e` and `872a32fb`)

- #1103: `analysis.json` compute tasks emit `impact: {mid}` only. The low/high band was
  copied whole from every finding a task touched, so a split finding could put `mid`
  below `low`. Per-finding bands in `analysis.md` are unchanged.
- `5da43f3e`: drops the legacy `peak_hbm_bw_tbs` fallback. A missing `peak_mem_bw_tbs`
  now fails loudly instead of silently assuming 1 TB/s.
- `872a32fb`: the analysis template spells out the fusion P2/P3 detailed-analysis blocks.
- #1109: the fusion data-table tests reuse the shared table header constants instead of
  their own copies (test-only).

### 7. Upstream Syncs

- `main` was merged into `staging_agent` three times: `baaea160` (10/12), `e4c32589`
  (10/15) and `61f0570f` (10/23). The 10/23 merge brings in everything up to `b6fd72dd`
  (#1151), so `staging_agent` now contains all of `main`.
- #1120, #1122 and #1123 were cherry-picked onto `staging_agent` and are already on `main`.
