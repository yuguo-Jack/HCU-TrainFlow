# Remove Incorrect Low and High Per Kernel Impact Estimates from JSON

[Upstream PR](https://github.com/AMD-AGI/TraceLens/pull/1103) · state: closed · merged: True

## Original PR description

Problem. A compute task's impact.mid is the sum of its own rows, but its low/high were copied whole from every finding the task touched. When one finding splits across several Operation tasks, each task
  carried the full band. On Owl, the P1 elementwise finding (0.77 / 0.92 / 1.02) was split four ways, which gave mul a mid of 0.09 under a band of 0.77 / 1.02. So mid fell below low, and summing bands across
  tasks counted the finding four times. This came in with #1044.

  Change. Tasks now emit "impact": {"mid": mid}. Nothing in TraceLens read the task band, and Hyperloom only passed it through into prose fields. The per-finding bands in analysis.md (the p_item and
  detail_estimate markers) are unchanged and are still where low/high come from.
  - analysis_json.py: drop the band from _build_task and delete _sum_optional.
  - candidate_schema.py: Impact keeps only mid.
  - Tests updated to the new key set.

  Sorting, members and prose are unaffected, since ordering already used mid.

  Downstream. Hyperloom reads with impact.get("low"), so it won't break. A follow-up Hyperloom PR removes the now-empty impact_low_e2e_pct / impact_high_e2e_pct fields and bumps the SHA pin.

  Testing. test_analysis_agent_post_processing.py, test_analysis_agent_utils.py, test_analysis_json_surface.py and the fusion golden suite pass (347 tests), and black is clean.
