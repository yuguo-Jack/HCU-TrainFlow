# TL Agent YAML Interface Organization

[Upstream PR](https://github.com/AMD-AGI/TraceLens/pull/1144) · state: closed · merged: True

## Original PR description

## Summary

A multi-trace analysis now runs from the same YAML that `TraceLens_generate_perf_report_from_config`
takes: each job carries its own `phase`, jobs that share a phase are combined, and the first job is
the focus for kernel fusion and system analysis. The agent-only `focus_job` key and the
`--focus-job` prepare flag are gone, because the focus is derived from the config. Comparative and
semantic runs keep job 2's platform when it has an arch file, and `compare_to` can name job 2
instead of repeating its paths. All changes are on the agent side; the wrapper is untouched.

## Why

| Pain point | Old | New |
|---|---|---|
| Multi-trace YAML was not a wrapper YAML | It needed a top-level `focus_job`, which the agent stripped before calling the wrapper, and the agent forced each job's `phase` to its name and injected `aggregation` | The YAML is passed through as written. `check_config` only adds missing agent report flags and rejects one set to `false` |
| Jobs could not share a phase | `phase` had to equal the job name, so two prefill traces were reported as two phases | `phase` is set per job and `combine_only_same_phase` combines jobs that share it |
| Focus job passed by hand | The orchestrator asked for a focus job and passed `--focus-job` to prepare | The focus is `plans[0]`, the first job, in both `config_utils` and prepare |
| Manifest mixed jobs and phases | `gpu_utilization.phases` was keyed by job name, and fusion stamped the job name as its phase | `gpu_utilization.jobs` is keyed by job name and carries each job's `phase`, and fusion stamps the focus job's phase |
| Job 2's platform always rewritten | In comparative and semantic runs, job 2's report always used job 1's platform, even when job 2's platform had its own arch file | Job 2's platform is rewritten only when it has no arch file. `platform2` is always the user's value |
| `compare_to` repeated job 2's paths | Only the `{trace_path, capture_folder}` mapping was accepted | `compare_to: <job 2's name>` is also accepted, and the agent expands it to the mapping the wrapper expects |

## Architecture

```
run.yaml  (or the Step 0 answers)
   │
   ▼
Step 0: config_utils check_config()
   │  scope derived: 1 job = standalone, compare_to = comparative, aggregation = multi_trace
   │  comparative/semantic: compare_to name -> mapping, job 2 platform rewritten only if
   │                        list_platforms() has no arch file for it
   │  multi_trace: adds missing report flags only; focus = plans[0]
   ▼
<output_dir>/cache/run_config.yaml
   │
   ▼
Step 1: TraceLens_generate_perf_report_from_config
   │
   ├──> run_config.resolved.yaml
   ├──> perf_report_<job>_csvs/          (one per job)
   └──> perf_report_aggregated_csvs/     (multi_trace: one row set per phase)
   │
   ▼
Steps 3-6: orchestrator_prepare.py
   │  requires run_config.resolved.yaml; aggregation present = multi_trace
   │  focus_job = plans[0].name
   ▼
category_data/category_manifest.json
   │  focus_job, gpu_utilization.jobs[<name>] = {phase, utilization}
   │
   ├──> kernel_fusion_analysis.py            phase = jobs[focus_job].phase
   ├──> report_utils.load_manifest_categories system analysis on jobs[focus_job]
   └──> triage/checks.py                      idle check on jobs[focus_job]
```

Prepare now stops with `[DIAG:pipeline:STEP1_FAIL] Resolved run config missing` when the wrapper's
resolved config is absent, instead of falling back to a single-trace layout. Every agent run makes
that file in Step 1, so only reports produced outside the wrapper hit this error.

## What changed

### Python (5 files)

| File | Change |
|---|---|
| `TraceLens/Agent/Analysis/utils/config_utils.py` | Derive `multi_trace` from `aggregation`. Multi-trace: require policy `combine_only_same_phase`, check report flags instead of overwriting them, and drop the `focus_job` and phase-equals-name handling. Comparative: expand a `compare_to` name, and rewrite job 2's platform only when `list_platforms()` lacks it. `_shape_errors` takes the whole config. `build --scope multi_trace` writes the aggregation block |
| `TraceLens/Agent/Analysis/utils/orchestrator_prepare.py` | Drop `--focus-job`. Require `run_config.resolved.yaml` and detect multi-trace from its `aggregation`. Write `gpu_utilization.jobs` with each job's `phase` in place of `.phases` |
| `TraceLens/Agent/Analysis/category_analyses/kernel_fusion_analysis.py` | Stamp the focus job's `phase`, not its name |
| `TraceLens/Agent/Analysis/utils/report_utils.py` | Read the focus job's utilization from `.jobs` |
| `TraceLens/Agent/Analysis/triage/checks.py` | Read the focus job's utilization from `.jobs` |

### Orchestrator skill and docs (4 files)

|---|---|

## Test plan

- [x] Agent unit tests: `test_analysis_agent_config_utils.py`, `test_analysis_agent_utils.py`, `test_analysis_agent_triage.py`, `test_analysis_agent_category_utils.py` and `test_reporting_utils.py` (884 passed). `black` and `lint-imports` are clean
- [x] Wrapper and prepare on a three-job inference config (two prefill jobs, one decode job): the aggregated report has exactly the phases `prefill` and `decode`, and prefill kernel time is twice a single job's. The manifest has `focus_job` set to the first job and three `gpu_utilization.jobs` entries with phases
- [x] One agent run per scope on representative traces:
  - [x] Standalone: same change lines and byte-identical report CSVs as before
  - [x] Standalone fallback: graph-under-recorded detection, deterministic report
  - [x] Comparative MI300X against H100 with `compare_to` by name: expanded to the mapping, H100 rewritten for having no arch file, `platform2=H100`, report CSVs byte-identical to before
  - [x] Semantic for having no arch file, diff stats produced
  - [x] Multi-trace: only report flags added, no focus question, Executive Summary gives per-phase times
- [x] Negative checks: prepare without a resolved config exits with `STEP1_FAIL`, `--focus-job` is rejected, and a top-level `focus_job` key is rejected as an unknown key

Kernel fusion's phase-based suppression was not exercised end to end, because the multi-trace input had no fusion candidates. A unit test covers it.
