# TL Agent YAML Interface

[Upstream PR](https://github.com/AMD-AGI/TraceLens/pull/1121) · state: closed · merged: True

## Original PR description

## Summary

The analysis agent can now run from a run YAML ("run it from config `<run.yaml>`") as well as from the interactive questions. Both front ends produce the same config in the schema of the perf report wrapper from #1094, and a new `config_utils` module completes and checks it in Step 0. Step 1 is then one `TraceLens_generate_perf_report_from_config` call instead of per-mode CLI command lines that the orchestrator assembled from prose.

**Depends on #1094.** This branch carries its three commits (`de5daaec..c3e838a8`); review from `c3e838a8`. The changes here are commits `23a05ff7`, `dfa914b7` and `9c397e96`.

## Why

| Pain point | Old | New |
|---|---|---|
| Multi-node support | Inputs came from Step 0 questions and hand-built command lines, sized for one or two traces | A run config with a `jobs` list is the input a multi-node run needs. This PR lays that groundwork; the scopes still take one or two jobs |
| Step 1 assembled in prose | `reference.md` branched on analysis mode and comparison scope, with per-CLI flag suffix tables for `TraceLens_generate_perf_report_pytorch` and `TraceLens_generate_perf_report_pytorch_inference`; the LLM built each command line | One wrapper call on `cache/run_config.yaml` |
| Interactive only | Every run went through the Step 0 questions | YAML mode: the prompt names a config file and the agent asks only the environment questions |
| Wiring left to the LLM | Job names, the comparison target and the agent's required report flags came from prose instructions | `check_config` adds them in code and prints every change |
| Late, one-at-a-time errors | Scope rules (one job vs two, capture folder on both or neither, semantic is inference only) were prose checks | All shape errors are raised together in Step 0, then the wrapper's own validation runs before anything is generated |
| No record of the run | The inputs lived only in the conversation | `cache/run_config.yaml` (agent input) and `run_config.resolved.yaml` (every flag explicit, written by the wrapper) |

## Architecture

### Step 0: two front ends, one config

```
Interactive mode                                 YAML mode
Step 0 answers (scope, mode, trace(s),           user run.yaml
platform(s), capture folder, extension)          ("run it from config <run.yaml>")
        │                                                │
        ▼                                                ▼
config_utils build                               config_utils check
  --scope --analysis_mode --output_dir             --config <run.yaml> [--scope]
  --job k=v,... (per job)  --set k=v               load_run_config()
  _assign_pairs()                                        │
        └──────────────────────┬─────────────────────────┘
                               ▼
              check_config(config, scope) -> AnalysisConfig
                1. shape: platform per job, absolute paths,
                   _shape_errors(scope)          ── ConfigError (all errors at once)
                2. complete:
                     standalone   drop jobs[0].name
                     two jobs     names trace1/trace2, jobs[1].platform := jobs[0]'s
                                  (original kept as platform2)
                     comparative  jobs[0].compare_to := jobs[1] paths
                     all          AGENT_REPORT_FLAGS[analysis_mode]
                3. wrapper: plan_reports(completed)  ── ConfigError
                               │
                ┌──────────────┴──────────────────┐
                ▼                                 ▼
  <output_dir>/cache/run_config.yaml     stdout: change lines (added/set/renamed/removed)
  (Step 1 input)                                 then key=value variables:
                                                 comparison_scope, trace_path, platform,
                                                 output_dir [, comparison_method,
                                                 trace2_path, platform2]  ──► Steps 1-12
```

Scopes map to the wrapper schema as follows. `semantic` is the comparative graph-replay-only case.

| Scope | Jobs | `compare_to` | `capture_folder` | `comparison_method` |
|---|---|---|---|---|
| standalone | 1 | none | optional | n/a |
| comparative | 2 | added to job 1 | both jobs or neither | tracediff |
| semantic | 2, inference only | none | none | semantic |

### Step 1: pre-processing, then one wrapper call

```
cache/run_config.yaml
        │
        ├── comparison_method = semantic only ─────────────────────────────┐
        │                                                                  ▼
        │                          semantic-comparison sub-agent
        │                            ─► semantic/tracediff_output/diff_stats.csv
        │                          config_utils set-diff-stats --config ... --path ...
        │                            add_diff_stats(): jobs[0].precomputed_diff_stats
        │                                                                  │
        ◄──────────────────────────────────────────────────────────────────┘
        ▼
TraceLens_generate_perf_report_from_config --config <output_dir>/cache/run_config.yaml
        │  writes run_config.resolved.yaml, then runs each job in order
        │  non-zero exit or timeout ─► [DIAG:pipeline:STEP1_FAIL], stop
        ▼
perf_report.xlsx + perf_report_csvs/                     (standalone)
perf_report_trace1.xlsx/_csvs/ + perf_report_trace2.xlsx/_csvs/   (two jobs)
        │
        ▼
Step 2 trace-quality gate (skipped when comparison_method = semantic)
        │
        ▼
Steps 3-12 unchanged
```
