# TraceLens Agent Multi-Node Support

[Upstream PR](https://github.com/AMD-AGI/TraceLens/pull/1141) · state: closed · merged: True

## Original PR description

## Summary

The agent gets a fourth scope, `multi_trace` (prose: "multi-trace standalone"). It analyzes two or more named jobs of one workload on one platform, for example the prefill and decode captures of one vLLM server, and writes a single report. Compute findings are ranked together, with every `impact_score` a percent of the combined GPU time of all jobs, and each P-item says which phase it came from. Kernel fusion and system analysis (CPU/idle, multi-kernel) run on one job the user picks, the `focus_job`.

**Includes a merge of #1126** (`0c9af963`, "Aggregate perf reports"). That merge brings `TraceLens/Reporting/aggregate_perf_reports.py` and the wrapper's `aggregation: {policy}` key, which write the combined `perf_report_aggregated_csvs/` with a `phase` column. The agent uses it unchanged. `a52ecebf` is that merge and also carries the feature; `9509e837`, `6ebc1f3b` and `c3e46e97` are prose and README follow-ups. To review the agent side only, diff `origin/staging_agent` against this branch over `TraceLens/Agent/`, `docs/how-to/agent.md`, `tests/test_analysis_agent_*.py` and `tests/test_reporting_utils.py`.

Single-trace and comparative runs are unchanged. Their CSVs have no `phase` column, so every phase lookup returns None and every new field is left out.

## Why

| Pain point | Old | New |
|---|---|---|
| One phase per report | A prefill and a decode capture needed two runs and two reports, with impact scores on different denominators | One run, one report. Every impact is a percent of the combined time, so P1 is the biggest win for the whole workload |
| Where a finding lives | n/a | Each compute P-item carries `**Phase**: <job>` and `phase=` on its marker; R6 validates it |
| Fusion and system analysis across jobs | n/a | Scoped to `focus_job`, with a scope line in the report. Fusion candidates come from one call tree, and idle time summed across separate captures is meaningless |
| Graph-replay-only, one trace | Step 0 aborted in Interactive mode; YAML mode already fell through to the Step 2 gate | Both modes continue to Step 2, which routes to the deterministic fallback. The `default`-mode "Trace Feature Detection" abort and its triage check are gone |
| Several "which CSV dir" maps | `perf_report_csv_dir` and `prepare_model_identification_data` each mapped scope to a directory | Prepare writes `focus_csv_dir` into the manifest; `perf_report_csv_dir` returns it and model identification calls it |

## Architecture

### End to end (`multi_trace` only)

```
run.yaml (or Step 0 answers)
  jobs: [{name: prefill, ...}, {name: decode, ...}]   one platform
  focus_job: decode
        │
        ▼
Step 0  config_utils check|build --scope multi_trace
          _shape_errors: 2+ jobs, one platform, phase == name
          check_config:  focus_job must name a job, then removed
                         jobs[i].phase := name
                         aggregation := {policy: combine_only_same_phase}
          variables:     trace_path / platform / capture_folder of the focus job,
                         comparison_scope=standalone, focus_job=decode
        │
        ▼
Step 1  TraceLens_generate_perf_report_from_config            (wrapper, #1126)
          perf_report_prefill_csvs/   perf_report_decode_csvs/
          perf_report_aggregated_csvs/   rows of every job, leading `phase` column,
                                         percentages over the combined time
          run_config.resolved.yaml
        │
        ▼
Step 2  check_graph_replay_coverage(aggregated unified_perf_summary.csv)
          graph-replay fraction per phase; the worst phase decides
          ── GRAPH_UNDER_RECORDED ─► deterministic fallback for the whole run
        │
        ▼
Steps 3-6  orchestrator_prepare --focus-job decode
          trace1_csv_dir = perf_report_aggregated_csvs/  ─► category CSVs (phase rides along)
          plan_reports(run_config.resolved.yaml) ─► per-job gpu_timeline.csv
                                                  ─► gpu_utilization.phases{prefill, decode}
          focus_csv_dir  = perf_report_decode_csvs/  ─► FusionCandidateBuilder
          Step 5 tree    = focus trace (+ focus capture merge)
          writes category_manifest.json:
            gpu_utilization       combined, plus .phases
            focus_job, focus_csv_dir, capture_folder (null when the merge fell back to raw)
          writes metadata/cpu_idle_metadata.json with the focus job's utilization
        │
        ├─────────────────────────────┐
        ▼                             ▼
Step 7  system (focus only)          Step 8  compute sub-agents (all phases)
  load_manifest_categories prints      build_operation_metrics ─► compute_impact_estimates
  phases[focus_job]; the CPU/Idle      ─► build_category_findings, grouped per phase
  and Multi-Kernel gates read it       ─► category_data/<cat>_metrics.json
  kernel_fusion_analysis stamps                          │
  phase = focus_job on its metrics                       │
        │                                                │
        └──────────────────┬─────────────────────────────┘
                           ▼
Step 8.5  generate_priority_data ─► priority_data.json   (one ranking across phases)
Step 12   analysis.md: Phase field and phase= on compute P-items, combined Total Time
          plus a per-phase sentence, "summed across phases" note on Top Operations,
          scope line on Fusion and System sections
          validate_report ─► _validate_report_priority_consistency:
            R6 marker phase == findings[N-1].phase
        │
        ▼
render_analysis_json(analysis.md)   (post-processing, run by the consumer)
  compute tasks bucket by (phase, operation) and carry task.phase
```

### Combined vs focus: who reads which numbers

```
category_manifest.json
  gpu_utilization.total_time_ms (combined) ──► compute impact denominators, Executive Summary Total Time
  gpu_utilization.phases[focus_job]       ──► load_manifest_categories (Step 7 gates),
                                              triage check_subagent_budget
  focus_csv_dir                           ──► perf_report_csv_dir ─► fusion, model identification
metadata/cpu_idle_metadata.json           ──► cpu-idle-analyzer (focus job)
metadata/<cat>_metadata.json              ──► compute analyzers (combined, unchanged)
```

### Fusion suppression stays in its phase

Fusion's high-confidence op keys suppress the matching compute rows so the same time is not claimed twice. Under `multi_trace` the same kernel and shapes can appear in both phases, so the key gains the phase:

```
kernel_fusion_metrics.json { phase: decode, high_confidence_op_keys: [...] }
        │  _load_fusion_op_keys ─► {(phase, *key)}
        ▼
build_operation_metrics: row matches only when (row.phase, *perf_row_key(...)) is in the set
        ─► decode rows suppressed, the identical prefill rows still scored
```

## Known limitations

- **Joint ranking weights phases by capture length.** A long prefill capture can dominate the P-list. The Executive Summary's per-phase sentence shows each phase's window.
- **Triage, evals and Hyperloom find runs by `perf_report_csvs/`**, which a `multi_trace` run does not write, so they do not see these runs yet. The `analysis.json` change is additive (`phase` is optional), and Hyperloom's task loader does not read it.
