# Kernel Fusion - Compute Tier Alignment

[Upstream PR](https://github.com/AMD-AGI/TraceLens/pull/1093) · state: closed · merged: True

## Original PR description

## Summary

The kernel fusion tier now reports in the same shape as the compute tier. Fusion Data tables use compute's 10 columns and are built from the same perf-report rows and helpers. `analysis.json` gains a `fusion_optimizations[]` tier sorted on the same `impact.mid` key as compute. Two scoring bugs are fixed along the way: fusion time no longer extrapolates from the first instance, and compute now skips fusion-covered rows by op key instead of by kernel name. The fusion Identification now names the module, its caller and the launch path of each op. 21 files, +1994 / -650.

## Why

| Pain point | Old | New |
|---|---|---|
| Fusion tables don't match compute | `Kernel / Type / Duration (us) / Perf model`, one row per kernel, first instance only | Compute's 10 columns, one row per launching op and args, from the same perf-report row |
| Fusion time is overstated | First instance's kernel time × `instance_count`. A module whose instances differ in shape gets every instance scored at the largest shape | Sum of the real kernel time over every instance |
| Wrong perf row | Lookup on kernel name + first input shape, with prefix matching. One GEMM or elementwise kernel serves many ops | Lookup on `perf_row_key`: op name + args + process/thread, the perf report's own grouping |
| Same time counted in both tiers | Compute flagged rows whose kernel name appeared in the first instance of a HIGH candidate, so rows from later instances slipped through | Compute flags a row when its `perf_row_key` is one of the HIGH candidate's op keys |
| No fusion in `analysis.json` | `findings()` walked `tier=compute` only; a test asserted the fusion key was absent | `fusion_optimizations[]`, same task shape as compute, sorted on `impact.mid` |
| Fusion `operation` carried the severity badge | `"🔴 P1: Unfused Attention"`, the raw heading | `"Unfused Attention"`, the bare name, like compute |
| Identification didn't say where the kernels came from | Described the kernel sequence only | Names the module, its parent and call site, and the launch path of each op |
| `—` op_row cells inflated compute | A `—` cell (fusion-flagged row) back-filled to `pct_e2e × 0.30` | A `—` cell scores 0. The back-fill only runs when a block has no op_row marker at all |

## Before and after

All samples are illustrative: shapes are symbolic, kernel names and launcher paths are placeholders, and bandwidth peaks are written as `<peak>`. The example is a vision attention module with two shape variants (120 large instances and 60 small ones), which is exactly the case the old time extrapolation got wrong.

```markdown
**Identification:** The `Attention` module repeats 180 times inside the encoder layers. Each call launches a GEMM, then a softmax, then a second GEMM, and none of these kernels is a fused attention kernel.

**Data:**
```

```markdown
<!-- reasoning-candidate tier=fusion rank=1 -->
#### 🔴 P1: Unfused Attention

**Identification:** The `Attention` module runs 180 times, called from its parent `EncoderLayer` at `model/encoder.py(NNN): forward`. The batched matrix multiplies and the attention-mask add are launched from `model/attention.py(NNN): forward`, and the softmax is launched from `torch/nn/functional.py(NNN): softmax`. This candidate was surfaced because each instance runs a GEMM → softmax → GEMM kernel sequence with no fused attention kernel anywhere in the module subtree.
```

What changed:
- **Heading** loses the `(ms, instances)` suffix, matching compute headings.
- **Identification** names the module and its caller, then the launch path of each op from the Data rows. That tells a reader where a fused kernel would plug in.
- **Group time** is 250.81 ms (the Time column summed), not 370.53 ms. The old number took the first, large-shape instance and multiplied it by all 180. The impact mid drops from 19.97 to 13.52 as a result.
- **Softmax** turns out to be two thirds of the group. The old table showed it only as "Perf model: No".
- **Labels** are Identification / Data / Resolution / Impact estimate. Fusion blocks have no Reasoning for Slowdown, because the reason is always the same: intermediates round-trip through HBM between separate kernels.
- **`detail_estimate`** carries `mid` (compute and fusion alike).


### `kernel_fusion_metrics.json` (internal sidecar, never in `analysis.json`)

**Before**

```json
"impact_estimates": [
  {"operation": "<Module>", "confidence": "high", "affected_gpu_kernels": ["gemm_kernel_A...", "..."], ...}
],
"high_confidence_kernel_map": {"gemm_kernel_A...": "<Module>", "softmax_fwd_kernel...": "<Module>"}
```

**After**

```json
"impact_estimates": [
  {
    "operation": "<Module>", "confidence": "high", "time_ms": 250.805, ...,
    "rows": [{"operation": "aten::bmm", "args": "...", "kernel_path": "...", "kernel_name": "...",
              "time_ms": "40.460", "pct_e2e": "4.45", "count": 120, "flops_per_byte": "62.46",
              "efficiency": "49.39% of <peak> TB/s", "bound": "memory-bound"}, ...],
    "op_keys": [["aten::bmm", "((H, S, D), (H, D, S))", "('c10::BFloat16', 'c10::BFloat16')",
                 "(<strides>)", "('', '')", "<process>", "<label>", "<thread>"], ...]
  }
],
"high_confidence_op_keys": [ ...op_keys of every HIGH estimate... ]
```

`op_keys` is kept on every estimate, and only the HIGH ones are flattened into `high_confidence_op_keys`, which is the only list compute reads. `affected_gpu_kernels` had no reader in TraceLens, TraceLens-internal, Hyperloom or the prompts, so it is dropped.

## Downstream compatibility (Hyperloom)

No Hyperloom change is needed.
- Hyperloom's reader (`_analysis_json.load_report_tasks`) reads `compute_optimizations[].members[]` only. Every field it reads is still there with the same meaning. The new `fusion_optimizations` key is ignored.
- Hyperloom does not parse the fusion section of `analysis.md`. Its prompts refer to the `## Kernel Fusion Opportunities` heading, which is unchanged.
- The removed kernel map and `affected_gpu_kernels`, and the new `op_keys`, live only in `kernel_fusion_metrics.json`, which Hyperloom does not read.
