# Allow for multiple capture traces to merge with graph root

[Upstream PR](https://github.com/AMD-AGI/TraceLens/pull/1158) · state: closed · merged: True

## Original PR description

### Summary

This PR improves graph capture merge support for speculative decoding traces. It fixes batch size resolution for both vLLM and SGLang EAGLE spec-decode, enabling the merge code to select the correct capture trace for each graph replay root.

### Background

The graph capture merge code previously assumed a 1:1 relationship: each execution root corresponds to a single capture trace file at a single batch size and mode (FULL or PIECEWISE). This held for standard decode and prefill workloads.

In speculative decoding, this assumption breaks. A single execution root can replay multiple CUDA graphs from different capture sources. The merge code needs to load multiple capture files per execution root and match each graph root to the right capture root.

Additionally, four phases replay CUDA graphs with different batch size semantics. The merge code needs to map from the replay annotation's batch size to the correct capture trace's `batch_size` key.

**vLLM — Before**

| Phase | Replay annotation | What merge passed to lookup | Capture `batch_size` formula | Match? |
|-------|------------------|-----------------------------|------------------------------|--------|
| Target verify | `execute_{bs}_context_{c}_generation_{g}` | `ann.batch_size` = requests × (num_spec_tokens + 1) | requests × (num_spec_tokens + 1) | Yes |
| Drafter decode | `sample_{bs}_context_{c}_generation_{g}` | `ann.context_requests + ann.generation_requests` = requests | requests × 1 | Yes |
| Drafter prefill | `sample_{bs}_context_{c}_generation_{g}` | `ann.context_requests + ann.generation_requests` = requests | requests × (num_spec_tokens + 1) | **No** |

The drafter prefill batch size was incorrect. The batch size is the total number of sequences in the forward pass.

**vLLM — After**

| Phase | What merge passes to lookup | Capture `batch_size` formula | Match? |
|-------|-----------------------------|------------------------------|--------|
| Target verify | `ann.batch_size` = requests × (num_spec_tokens + 1) | requests × (num_spec_tokens + 1) | Yes |
| Drafter decode | `ann.context_requests + ann.generation_requests` = requests | requests × 1 | Yes |
| Drafter prefill | `ann.batch_size` = requests × (num_spec_tokens + 1) | requests × (num_spec_tokens + 1) | **Yes** |

`spec_decode_batch_sizes()` now returns both candidates `(requests, ann.batch_size)` for vLLM `sample_` roots. With prefill being `requests` and decodde being `ann.batch_size`

**SGLang — Before**

| Phase | Replay annotation | What merge passed to lookup | Capture `batch_size` formula | Match? |
|-------|------------------|-----------------------------|------------------------------|--------|
| Target verify | `step[VERIFY bs=N]` | `ann.context_requests + ann.generation_requests` = requests | `request_bs × (num_spec_tokens + 1)` | **No** |
| Drafter decode | `draft` (borrows from nearest verify) | `ann.context_requests + ann.generation_requests` = requests | `request_bs × 1` | Yes |
| Drafter extend | `draft_extend` (borrows from nearest verify) | `ann.context_requests + ann.generation_requests` = requests | `request_bs × (num_spec_tokens + 1)` | **No** |

SGLang annotations only carry request counts. Target and drafter_extend captures are indexed by token count `request_bs × (num_spec_tokens + 1)`, creating a unit mismatch. `request_bs` is available in SGLang capture metadata but was not used.

**SGLang — After**

| Phase | What merge passes to lookup | Capture `batch_size` formula | Match? |
|-------|-----------------------------|------------------------------|--------|
| Target verify | requests → `request_bs_map` → `request_bs × (num_spec_tokens + 1)` | `request_bs × (num_spec_tokens + 1)` | **Yes** |
| Drafter decode | requests → `request_bs_map` → `request_bs × 1` | `request_bs × 1` | Yes |
| Drafter extend | requests → `request_bs_map` → `request_bs × (num_spec_tokens + 1)` | `request_bs × (num_spec_tokens + 1)` | **Yes** |

The ideal fix would be to multiply the request count by `(num_spec_tokens + 1)` to get the token-level batch size. But `num_spec_tokens` is not available — it's not in the replay annotations or capture metadata.

Instead, `load_capture_folder()` builds a `request_bs_map` per role from the `execution_details.json` capture metadata. This only happens for SGLang. Each capture entry has both `request_bs` and `batch_size`. The relationship `batch_size = request_bs × (num_spec_tokens + 1)` is baked into these values, so the map implicitly encodes the multiplier without needing to know `num_spec_tokens`.

The merge loop then converts: replay annotation says `requests=4` → find closest `request_bs` in map (4) → use corresponding `batch_size` (24 for target, 4 for drafter, 24 for drafter_extend) → look up capture key `target_24_FULL`.

### Implementation

**`TraceLens/TraceUtils/utils/annotation_utils.py`**

`spec_decode_batch_sizes()` now returns a tuple of candidate batch sizes per root. For vLLM `sample_` roots, it returns both the decode batch size (`context_requests + generation_requests`) and the prefill batch size (`batch_size` from the annotation). For SGLang/ATOM roots and target roots, it returns a single-element tuple with the request count.

**`TraceLens/Trace2Tree/trace_capture_merge_experimental.py`**

- `load_capture_folder()` stores a list of file paths per key instead of a single path. Returns a third value `request_bs_map` for SGLang batch size conversion (see above).

- New `_load_all_capture_sources()` loads all capture files for a role across multiple batch sizes and both FULL/PIECEWISE modes.

- **Capture-to-graph root matching** uses a three-tier strategy:
  1. **1:N broadcast** (preserved from before): if a capture source has exactly 1 capture root, it's broadcast to all graph roots. This is the common case for FULL captures where the entire graph is captured as a single root.
  2. **1:1 positional** (preserved from before): if a capture source has exactly as many capture roots as graph roots, they're paired positionally. This is the common case for PIECEWISE captures where each segment maps to one graph root.
  3. **Dispatch-count matching** (new fallback): `_match_graph_roots_to_captures()` pools all capture roots from all loaded sources and matches each graph root to the capture root whose dispatch count is closest to the graph root's kernel count. This handles the mixed FULL/PIECEWISE case where no single source has the right root count.

- The merge loop converts request counts to token-level batch sizes via `request_bs_map` before calling `find_closest_batch_size`. Two-step lookup: find closest `request_bs` in the map, then use the corresponding `batch_size` for the capture key. Only applies to SGLang captures (detected by filename pattern).

**`TraceLens/Reporting/generate_perf_report_pytorch_inference.py`**

- `classify_graph_capture_trace()` catches `EOFError`/`OSError` when loading capture traces, skipping corrupted gzip files with a warning.
### Tests

Verified on a split decode iteration from a Llama 3.1-8B EAGLE3 trace (`num_speculative_tokens=3`, `CONC=1`):

**Before:**
Drafter prefill (`sample_30`, batch size 1):
  - Graph root 0 (7 kernels) — PIECEWISE capture has 7 dispatches, but entire root skipped
  - Graph root 1 (6 kernels) — PIECEWISE capture has 6 dispatches, but entire root skipped
  - Graph root 2 (23 kernels) — only in FULL capture, not in PIECEWISE
  - Graph root 3 (23 kernels) — only in FULL capture, not in PIECEWISE

Drafter decode (`sample_4`, batch size 1):
  - Graph root 0 (31 kernels, bs=4) — FULL capture at bs=4, but code looked up bs=1
  - Graph root 1 (23 kernels, bs=1) — FULL capture at bs=1, but entire root skipped since PIECEWISE attempted
  - Graph root 2 (23 kernels, bs=1) — FULL capture at bs=1, but entire root skipped since PIECEWISE attempted

**After:**
Drafter prefill (`sample_30`, candidate batch sizes: {1, 32}):
  - Graph root 0 (7 kernels) → PIECEWISE capture root 0 (7 dispatches)
  - Graph root 1 (6 kernels) → PIECEWISE capture root 1 (6 dispatches)
  - Graph root 2 (23 kernels) → FULL capture at bs=1 (23 dispatches)
  - Graph root 3 (23 kernels) → FULL capture at bs=1 (23 dispatches)

Drafter decode (`sample_4`, candidate batch sizes: {1, 4}):
  - Graph root 0 (31 kernels) → FULL capture at bs=4 (31 dispatches)
  - Graph root 1 (23 kernels) → FULL capture at bs=1 (23 dispatches)
  - Graph root 2 (23 kernels) → FULL capture at bs=1 (23 dispatches)

Also verified no regression on vLLM Qwen 3-14B EAGLE3 trace:
  - Drafter decode (`sample_128`, 2 graph roots, candidate batch sizes: {32}):
    - Graph root 0 (25 kernels, bs=32) → FULL capture at bs=32 (25 dispatches)
    - Graph root 1 (25 kernels, bs=32) → same FULL capture (broadcast)
  - Prefill runs in eager mode (bs=128 exceeds max-cudagraph-capture-size=32), no graph roots to merge

Thanks Kyle,
It is a good idea to use the number of kernels, but I am afraid it might make it less robust. Some examples:

Can you check all unit tests as well?

1. Off-by-one counts get dropped. xdit_flux has 994 capture dispatches against 993 kernels per graph launch. SGLang draft_extend has 22 against 23. The old code merged both through its alignment step. The new code merges neither. For xdit_flux that changes the op categories, which is why its two regression tests fail.

2. One miss drops the whole root. If one launch in a root can't be matched, the launches that did match are thrown away too. Merging the matched launches and leaving the rest unmerged would keep the good data.

3. Ties are broken arbitrarily. When several capture roots have the same count, the first candidate wins: PIECEWISE before FULL, then the smaller batch size. In the vLLM runs two different files offered a 25-kernel root. The output didn't change here, but it could elsewhere.
