# feat(orchestrator): analytical roofline augmentation for unmodeled kernels

[Upstream PR](https://github.com/AMD-AGI/TraceLens/pull/1179) · state: closed · merged: True

## Original PR description

Builds on the introspected roofline merged in #1178 (quant precision, MoE, and attention), which is what models the custom attention/MoE ops that this feature attaches to findings.

## Problem

The analysis orchestrator roofline-models a kernel only when the trace carries its **Input Dims** (`record_shapes=True`) **and** PerfModel has a formula for it. A model's custom kernels — a bespoke attention or fused-MoE — otherwise surface as `estimate_method: "heuristic"`: ranked by E2E GPU-time share, with **no bound classification and no roofline floor**.

This bites hard when a capture is taken **without shapes** — e.g. to dodge a profiler fault on a large-context run. The dominant kernels (often attention + MoE, the bulk of GPU time) come back "unmodeled" and the report can say nothing quantitative about them.

## What this adds

A **deterministic** pipeline step that fills the gap using the *analytical* model-explorer roofline (#1178), which derives op shapes from the **model config** and so needs no trace shapes. It is a script, not an agent task — it writes its results into the structured findings data and the report simply renders them.

- **`roofline_augment.py`** — runs the roofline projection at the trace's runtime regime (decode/prefill, batch, context), maps the **dominant unmodeled kernel of each roofline category** (Attention, MoE, …) by kernel name, and:
  - writes `metadata/roofline_augmentation.json` with each kernel's `bound` (memory/compute), `arithmetic_intensity`, per-GPU `roofline_us_per_gpu`, an `achieved` block (**measured** kernel time vs the config-derived FLOPs/bytes → achieved TFLOP/s · GB/s · % of the bound's ceiling), and a pre-rendered Markdown `note`; and
  - **deterministically merges an additive `roofline` block onto the matching `priority_data.json::findings[]` entry** (`merge_into_priority_data`), matched by kernel name in a member's `operation`. It leaves every existing field untouched — `bound_type`, `efficiency_pct`, `estimate_method` — so nothing reclassifies the finding or trips the efficiency-anomaly check.
- **`roofline_cli.run_projection()`** — factored out of `main()` so the CLI and the augmentation share one spec-build + project path (no behavior change to the CLI).
- **reference.md** — new deterministic **Step 10.5** (runs after Step 8.5, which regenerates `priority_data.json`) + a Step 12 note to render `finding.roofline.note` verbatim and qualify any residual "no perf model" wording so the report is not self-contradictory.

### Design choices
- **Deterministic, data-driven:** the roofline lives in `priority_data.json`; the report renders it. No agent computes or interprets it.
- **Purely additive merge:** existing fields are untouched; verified that `validate_subagent_outputs` still passes (time + priority PASS) on real orchestrator output.
- **Name-based classification:** a projection GEMM launched from an attention module stays **GEMM**, not Attention — matching on the module chain would mis-map it.
- **Dominant-only:** only the single highest-GPU-time unmodeled kernel per category is augmented (the one surfaced as a top finding).
- **Honest achieved %:** it assumes every invocation ran the projected phase shape — reliable for a single-phase capture, skewed for a mixed-regime (e.g. agentic) one; the note states this. A fully reliable per-op efficiency still needs per-invocation trace shapes.

## Example (Inkling-MXFP4, decode, vLLM TP8)
```
other/rank1 → Attention MEMORY_BOUND  AI=8.0    ~1.71 ms/GPU   achieved 1.3% of memory bandwidth
other/rank2 → MoE       COMPUTE_BOUND AI=608.4  ~0.12 ms/GPU   achieved 0.9% of compute peak
```
— exactly the two kernels the trace left unmodeled, now with a bound + roofline floor + achieved throughput, merged into `priority_data.json`.

## Tests
- `classify_kernel` (name-based; projection GEMM → GEMM)
- `summarize_projection` (AI / bound / per-GPU floor / per-invocation FLOPs-bytes)
- `achieved_from_measurement` (memory- and compute-bound ceilings, missing measurement)
- `augment` picks the dominant unmodeled kernel per category and skips trace-modeled ops
- `merge_into_priority_data` is additive (annotates the matching finding, leaves others and all existing fields untouched)
- `report_notes` round-trip

## Limitations / follow-ups
- Needs the model source + regime as inputs (not auto-derived from the trace yet). A natural follow-up is to read batch/context/phase from the trace metadata and the checkpoint from `model_info.json`.
- Name-based mapping relies on recognizable kernel-name tokens; unusual custom-kernel names may need markers added.

### Update: achieved-vs-roofline throughput + wording reconciliation (400434b)

This closes the loop asked about — *using ModelUtils-derived shapes with the roofline models the main reports use* — by adding the **measured** side of the roofline, not just the analytical bound:

- `achieved_from_measurement()` combines each kernel's **trace measured time + invocation count** with the **config-derived** per-invocation FLOPs/bytes to report achieved **TFLOP/s · GB/s** and **% of the bound's ceiling** (compute peak for compute-bound, memory BW for memory-bound). `summarize_projection` now carries the dominant op's per-invocation FLOPs/bytes for this.
- The injected note is reworded so an augmented kernel is no longer called wholly "unmodeled": *"no Input Dims in the trace, so shapes come from the model config and are costed with the same PerfModel roofline used elsewhere."* reference.md Step 12 now also instructs qualifying any residual "no performance model" text in the finding, so the report isn't self-contradictory.

**Honest caveat (encoded in the note):** the achieved % assumes every invocation ran the projected phase shape. That's reliable for a single-phase capture; for a **mixed-regime** capture (e.g. an agentic prefill+decode replay) it skews — on the Inkling example the attention kernel reads ~1.3% of memory BW *because* its measured time is dominated by 64k-prefill attention while the projection used decode shapes. The note states this. The fully-reliable per-op efficiency still needs per-invocation trace shapes (`record_shapes=True`); this provides the best honest estimate when they're absent.

+1 test (`achieved_from_measurement` across both ceilings + missing measurement); 80 pass in the two suites.
