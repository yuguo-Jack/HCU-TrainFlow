# fix(grpo): apply max_length bound when re-encoding samples for policy update

[Upstream PR](https://github.com/modelscope/ms-swift/pull/10510) · state: open · merged: False

## Original PR description

Fixes #10504

## Root cause

When re-encoding rollout samples for the policy-update stage, `GRPOTrainer` wraps the re-encode in `self._template_context(template)` without a `max_length` (swift/rlhf_trainers/grpo_trainer.py:723 and :2085 before this change). `_template_context` then sets `template.max_length = None`, so `encode_sample` re-encodes the raw messages with truncation fully disabled. As a result the training-side sequences can far exceed `max_length + max_completion_length` (in the repro: 1342 tokens vs. the 640 bound), and OOM occurs no matter how small `max_length` is.

## Fix

- Add `GRPOTrainer._train_encode_max_length(template)` returning `template.max_length + self.max_completion_length` (swift/rlhf_trainers/grpo_trainer.py:706).
- Pass that bound via `self._template_context(template, max_length=...)` at both training-side re-encode sites (policy-update `_prepare_batch_inputs` path and `_generate_and_split`-adjacent chunk re-encode), so truncation matches rollout: with `truncation_strategy='left'`, the completion tokens are kept as the suffix and the prompt head is truncated — identical to rollout-side truncation.
