# PR information

<!-- No existing GitHub issue tracks this; a descriptive issue can be opened before submission if preferred. -->

`glm4_5`/`glm4_7`/`glm5_1`, `flint`, `ling3`, `spark2_5` and `seed_oss` render non-string tool arguments
with `json.dumps` (mirroring their chat templates' `tojson` filter), so an integer reaches the wire as
`3` and a boolean as `false`, while strings are written raw. Their parsers returned every
`<arg_value>`/`<parameter>` text as a stripped string, so a format/parse round-trip changed
`{'retries': 3}` into `{'retries': '3'}` and `{'dry_run': False}` into `{'dry_run': 'false'}`.
`swift deploy` / inference engines and GRPO rollout parsing consume `get_toolcall` output, so tools
received wrongly-typed arguments (e.g. an `integer` field holding `"3"`).

This gives these templates the same schema-aware discrimination `xing4_0`/`minicpm5` already use
(`supports_tool_schema = True`, `get_toolcall(response, tools)`):

- a shared `BaseAgentTemplate._is_string_param` helper keeps the raw text when the declared type
  includes `'string'`; a bare `null` on a `["string", "null"]` parameter still decodes to JSON null;
- every other value is decoded with the existing `_parse_json` (with the `json.loads('null')`-vs-failure
  distinction), so integers, booleans, numbers, arrays, objects and null round-trip exactly;
- without a schema the literal decoding still applies, matching `xing4_0`/`minicpm5` semantics.

Related open PRs, different templates (no file overlap beyond `base.py`): #10462 fixes the opposite
direction for `hy_v3`/`minimax_*` (they over-decode string-typed values), #10267 covers
`qwen3_coder`/`qwen3_5`. Together the three PRs make all unquoted-wire templates schema-aware.
