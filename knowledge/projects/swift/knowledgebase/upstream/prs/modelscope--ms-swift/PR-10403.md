## What & Why

The `margin` column is already wired through the data pipeline
(`template/template_inputs.py:81`, `template/base.py::_rlhf_encode`,
`template/base.py::_rlhf_data_collator`), and `RewardTrainer` already
consumes it (`reward_trainer.py:43-53`). However, `DPOTrainer.dpo_loss`
never read `margin`, and `concatenated_forward` forwarded it straight into
`model(**batch)`, which raises `TypeError: ... unexpected keyword argument
'margin'` as soon as a dataset with a `margin` field is used for DPO.

This PR adds support for per-pair margin in the `sigmoid` DPO loss:

- `concatenated_forward`: pop `margin` from `batch` before the model
  forward pass (fixes the crash), and propagate it through
  `output['margin']`. Margin is skipped (with a `UserWarning`) under
  sequence packing, since `cu_seqlens`-based pairing no longer aligns 1:1
  with the per-row margin tensor.
- `dpo_loss`: new optional `margin: Optional[torch.FloatTensor] = None`
  argument. For `loss_type == 'sigmoid'` and `reference_free == False`,
  the loss becomes:

  ```python
  L = -logsigmoid(beta * logits - margin)
  ```

  (margin in reward space, consistent with `RewardTrainer`'s
  `-logsigmoid(r_chosen - r_rejected - margin)`). Behavior is unchanged
  when `margin` is `None` (the default), so existing DPO runs without a
  `margin` column are fully backward compatible. `reference_free=True` or
  non-`sigmoid` loss types emit a `UserWarning` and ignore margin (not
  supported for those paths).
- `get_batch_loss_metrics`: passes `model_output.get('margin')` into
  `dpo_loss`.

No changes to the data pipeline are required — users can add a `margin`
field (a float, in reward-space units) directly to their chosen/rejected
DPO samples, e.g.:

```json
{"messages": [...], "rejected_response": "...", "margin": 2.0}
```

### Design notes

- Margin is applied **outside** the sigmoid, in reward space
  (`beta * logits - margin`), not inside as a logit-space constant like
  SimPO's `gamma` (`cpo_trainer.py:32`). This keeps the unit consistent
  with the `rewards/margins` metric already logged by `DPOTrainer`
  (`dpo_trainer.py:432-433`) and with `RewardTrainer`'s margin convention.
- Only the `sigmoid` loss type is supported for now; other loss types
  (`ipo`, `hinge`, `bco_pair`, etc.) are unaffected and margin is silently
  not applied to them (mixed `loss_type` lists still work as before for
  the non-sigmoid components).
- Packing mode is explicitly guarded against (margin is dropped with a
  warning) because a single packed row may contain multiple
  chosen/rejected pairs, breaking the 1:1 alignment with the per-sample
  margin tensor.

## Experiment results

Verified the loss formula numerically matches the intended semantics
(only pairs with non-zero margin get a larger loss; others unaffected):

```
beta = 0.1, delta = [2.0, 0.5, 1.0], margin = [2.0, 0.0, 0.0]
L_plain  mean = 0.636998
L_margin mean = 1.088611
ΔL per sample = [1.354839, 0.0, 0.0]
```
