# fix(template): preserve assistant reasoning on Qwen3.5/3.6 tool-call turns (#10255)

[Upstream PR](https://github.com/modelscope/ms-swift/pull/10259) · state: open · merged: False

## Original PR description

## Summary

Fixes #10255. The qwen3_5 swift backend dropped the assistant's `<think>...</think>` reasoning whenever the same assistant turn also carried `tool_calls`. The official `chat_template.jinja` (used by vLLM / transformers at inference) keeps it, so swift-trained models never saw "think, then call a tool" while being served in exactly that format — the train/infer mismatch behind #9234 (`</think><|im_end|>` / empty `<tool_call>` after SFT on Qwen3.5/3.6-35B-A3B).

## Root cause (from the issue report, confirmed on `main` @ dbc395ff02)

Two narrow mismatches with the jinja:

1. `swift/agent_template/qwen3_coder.py` — `Qwen3_5AgentTemplate._add_tool_call_prefix` used `pre_message['content']` only to decide on the `\n\n` separator and dropped the reasoning entirely. After the tool-call rebuild, the merged assistant turn had no `<think>` block at all.

2. `swift/template/base.py` — `_remove_history_thinking` and `_add_non_thinking_prefix` called `get_last_user_round(messages)` with the default `include_tool=True`. The official jinja uses the last **user** message as the boundary for stripping historical reasoning. With `tool` messages counted as a boundary, reasoning in the current agent round (which has tool messages between the user prompt and the assistant turn) was misclassified as history and stripped. `get_last_user_round` already accepts `include_tool` (from #9923); these two callers just needed to pass `include_tool=False`.

## Changes

- `swift/agent_template/qwen3_coder.py` — `_add_tool_call_prefix` now always preserves the preceding assistant content (so the `<think>` block survives the tool-call rebuild) and inserts the `\n\n` separator only when the effective (post-think) content is non-empty.
- `swift/template/base.py` — `_remove_history_thinking` and `_add_non_thinking_prefix` now pass `include_tool=False` to `get_last_user_round`, matching the official jinja boundary on the last user message.
- `tests/general/test_qwen3_5_agent_template.py` — new regression tests, CPU-only (no weights / tokenizer needed). Covers the three reasoning shapes (pure think, think + post-text, no think), the no-pre / non-assistant / empty-content edge cases, the `include_tool=False` boundary on `get_last_user_round`, and a static guard so a future refactor of the two call sites cannot silently regress.

## Verification

Ran a standalone verifier (`/tmp/verify_10255.py`) that exercises the new logic with hardcoded inputs against the patched source files. 18/18 checks pass, including a regression comparison that confirms the OLD behavior reproduces #10255 (drops reasoning) while the NEW behavior preserves it. The pytest suite itself runs in CI on this branch (this env doesn't have the heavy `swift` import chain satisfied).

## Related

- #10255 (this fix)
- #9234 (the user-visible symptom — same train/infer mismatch)
- #9923 (added `include_tool` to `get_last_user_round`; my fix uses it correctly)

- RerankerGuo · comment · 2026-10-07T10:13:03Z · [source](https://github.com/modelscope/ms-swift/pull/10259#issuecomment-6035785013)

You're right — that's a real regression, and it is fixed in `0d75a91a`.

## Root cause

`_add_tool_call_prefix` (Qwen3.5/3.6) re-emits the preceding assistant content — reasoning included — before `<tool_call>`. But `_preprocess_tool_call` only replaced the `tool_call` block: the original assistant message stayed in the list as its own turn, and the merged turn carried the same content again. Every tool-call round therefore rendered the assistant content twice. On the #10255 repro the reasoning is in *both* copies, which matches your "all 9 mismatches contain the reasoning twice" table exactly.

Reproduced locally against `_preprocess_tool_call` before touching anything:

```
BEFORE the fix, AFTER _preprocess_tool_call:
  assistant: '<think>I should check the weather.</think>\nLet me look it up.'          <- 1st
  assistant: '<think>I should check the weather.</think>\nLet me look it up.\n\n<tool_call>...' <- 2nd (duplicate)
```

## The fix

A generic `_tool_call_prefix_absorbs_content(pre_message)` hook (`swift/agent_template/base.py`, default `False`). `Qwen3_5AgentTemplate` opts in **only when the prefix actually re-emits the content** — assistant role, non-empty string content — so the hook's answer can't drift from its own branch conditions. When set, `_preprocess_tool_call` replaces `[pre_message, tool_call...]` as one message and carries the pre_message's `loss`/`loss_scale` over when the tool_call block doesn't set them:

```
AFTER the fix:
  assistant: 'PHEreasoning</think>\nLet me look it up.\n\n<tool_call>\n<function=get_weather>...'   <- single turn
```

Templates whose prefix emits only a separator or channel token (DeepSeek v4, Kimi K3 — same hook) keep the preceding message as its own turn; a test pins that they're unaffected, along with `qwen3_coder`.

## Why this should also beat base on your table

Base renders reasoning and tool_call as **two** assistant turns; the official jinja emits one turn. Folding them into one removes that structural difference, which is what the 2 base-side mismatches in `last_round` were. The separator logic itself is unchanged (only when effective post-think text is non-empty).

- RerankerGuo · comment · 2026-10-26T15:57:39Z · [source](https://github.com/modelscope/ms-swift/pull/10259#issuecomment-6420631995)

Thanks for the thorough re-verification — 13/13 on `last_round` and the closed alternative confirms the approach.

On the two remaining `all` mismatches: I agree they don't call for a change in this PR. They come from the `preserve_thinking` default (swift keeps past-turn reasoning in the encoded history), which is deliberate: in training, retaining earlier rounds' reasoning is what teaches the model *not* to re-derive it, whereas the official jinja is inference-oriented and strips it. As you showed, that behavior is identical on v4.5.3, so it predates this PR and this PR neither worsens nor masks it — `all` stays at the 11/13 baseline while the regression on the current turn is fixed.

Changing that default would alter rendering for every Qwen3.5/3.6 user, so if the mismatch ever needs reconciling it should be a separate, maintainer-endorsed change to the `preserve_thinking` semantics rather than a rider on this fix. Happy to open a tracking issue if the maintainers want one.
