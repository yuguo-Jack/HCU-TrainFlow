# PR information

<!-- Link the related issue. REQUIRED for first-time contributors. See CONTRIBUTING.md. -->
Refs #6467 — the tool-schema padding issue; the `List(Json())` forcing added for it in #10125 only reaches the parent process, and this PR makes it apply inside spawned `Dataset.map` workers too.

**Summary of the problem**

`RowPreprocessor` forces the `messages` / `tools` columns to `List(Json())` before they are written to
Arrow (`_patch_arrow_writer`), so heterogeneous tool schemas survive preprocessing, the Arrow cache and
`concatenate_datasets` verbatim, and pyarrow does not pad the fields a row never defined with `null`
(#10125, issue #6467).

The forcing was installed by patching `datasets.arrow_writer.ArrowWriter` **in the parent process**,
around `dataset.map`. However, `Dataset.map` performs the writes inside worker processes:
`datasets>=4.8` spawns a worker pool whenever `num_proc is not None` (including `num_proc=1`), and on
Windows/macOS those workers are freshly spawned interpreters that never see a patch made in the parent.
In them the batches are re-encoded with whatever types pyarrow infers from the input features, so:

1. tool schemas are stored as structs aligned across rows, and every field a tool never defined is read
   back as `null` — the exact corruption `_normalize_tools`/`remove_arrow_padding` exist to clean (the
   #6467 regression path);
2. two datasets preprocessed separately get mutually incompatible struct schemas and
   `concatenate_datasets` raises;
3. the output column is no longer `List(Json())`, so the cached dataset loses the schema guarantee that
   downstream code relies on.

On Linux CI (fork start method) the workers inherit the parent's patch, which is why this went unnoticed
there.

**The fix**

- `_patch_arrow_writer` (a scoped context manager) becomes `_install_arrow_writer_patch` (idempotent,
  install-once per process), and it is now installed from `_mapped_preprocess` — the wrapper function
  that `__call__` passes to `dataset.map` — so the patch exists in every process that writes, spawned or
  not. Subclasses that override `batched_preprocess` (e.g. `KTOPreprocessor`) are covered because the
  wrapper, not the override, is what gets mapped.
- `_new_init` only rewrites the types of columns the dataset already has, works on a copy, and skips
  writers whose caller fixed the features (`update_features=False`, e.g. hub dataset builders) — it no
  longer mutates a caller's `Features` object and no longer invents columns.
- A new `ArrowWriter._build_schema` patch re-asserts the canonical features **after** `datasets`' own
  inference (`update_features=True` lets inferred features win), drops keys the rows never contain, and
  rebuilds the affected schema fields and metadata, so `write_table` casts each batch to the canonical
  schema exactly like `Dataset.cast_column` would.

The patch only touches the columns we own; on Linux the current forcing already applied, and the added
`_build_schema` re-assertion finds the features already canonical there, so Linux behavior is unchanged.

Note for the reviewer: `swift/dataset/preprocessor/core.py` has a one-line textual overlap with the open
PR #10484 (`with self._patch_arrow_writer(), safe_ddp_context(None, True):`, which that PR wraps with
its thread-limiter `partial`). The two changes are semantically compatible and trivially mergeable: the
installer is idempotent and runs inside the mapped wrapper, so wrapping the map function with
`_preprocess_in_worker` still installs the patch in every worker.

## Experiment results

Environment: Windows 10 (spawn start method), Python 3.11.0, fresh venv with the repo pins —
`datasets==4.8.4` (pin `>=4.0,<4.8.5`), `transformers==5.22.1`, `torch==2.15.0`, `peft==0.20.0`,
`accelerate==1.15.0`. Clean `main` = 680df5c67; the fix tree differs only by this patch.

Red on clean `main`:

```
python -m pytest tests/general/test_tool_schema_padding.py -q
  6 failed, 13 passed, 9 subtests passed
python -m pytest tests/general/test_serialized_messages.py -q
  2 failed, 5 passed, 2 subtests passed
```

(The failing set on unpatched `main` varies between runs - 4 to 6 tests of the file - depending on
which process wins the write of each batch during worker spawn; every run fails all three new
`TestSeparatePreprocessingStaysConcatenatable` tests plus the existing padding-path tests, and every
run passes all 19 with the patch. The failing set above is from the run these numbers come from.)

`test_batched_cast_does_not_drop_tool_fields` shows the value corruption directly: a tool that never
defined a `query` parameter is read back with `'query': None` padded into its JSON schema;
`test_concatenating_datasets_keeps_both_tool_schemas` fails because two separately preprocessed datasets
carry incompatible struct schemas; `test_jsonl_normalizes_serialized_openai_tool_calls` fails on the
same padding path for serialized OpenAI tool calls.

Green with this PR:

```
python -m pytest tests/general/test_tool_schema_padding.py -q
  19 passed, 9 subtests passed          (16 existing + 3 new regression tests)
python -m pytest tests/general/test_serialized_messages.py -q
  7 passed, 2 subtests passed
```

A new test class, `TestSeparatePreprocessingStaysConcatenatable`, is added to
`tests/general/test_tool_schema_padding.py`; it preprocesses with `num_proc=2` so the pool path (and
thus the regression) is exercised on every platform. On clean `main` it fails (3 failed); with the
patch it passes.

No-regression: `tests/loss_scale` + `tests/utils` outcomes are identical to clean `main` (the 18
failing/skipped-environment cases fail identically before and after), and a per-file sweep of all 47
`tests/general` files produces identical outcomes on both sides except the two files repaired above.

Manual checks (same environment): jsonl → preprocess → Arrow cache roundtrip keeps tool values verbatim
with no padded nulls; a query/response dataset without a `messages` input column yields
`List(Json(decode=True))` messages with verbatim values; `KTOPreprocessor` (which overrides
`batched_preprocess`) behaves the same.
