# PR information

Fixes #10360

When GKD switches from an off-policy batch to an online vLLM rollout, PEFT's adapter-placement helper can cast FP32 trainable LoRA parameters to the BF16 base-model dtype. AdamW has already initialized FP32 state for those same Parameter objects, so its next step fails with a dtype mismatch.

Align the adapter to the base layer's **device only** during Swift's LoRA merge/unmerge. This avoids changing the trainable parameter dtype after optimizer state exists. Skip redundant same-device module conversion so the optimizer's Parameter objects remain intact, including when PyTorch's overwrite-on-conversion flag is enabled. The device lookup follows PEFT's special cases for MultiheadAttention, quantized `qweight` layers and parameter-targeting `ParamWrapper`; meta adapters are skipped as before. `BufferDict` support is optional for older compatible PEFT versions.

AI assistance: An AI coding assistant helped prepare this change and description. The submitting human should review every changed line and confirm the behavior before checking the accountability items below.

## Experiment results

- Before the patch, a standalone PEFT LoRA + two-step AdamW reproducer shows `FP32 parameter / FP32 optimizer state → BF16 parameter / FP32 state`, the same Parameter identity, and `RuntimeError: expected dtype float for end but got dtype c10::BFloat16`.
- With the patch, PEFT 0.20.0 and PyTorch 2.12.1 on CPU show `FP32 / FP32 → FP32 / FP32`; the same Parameter object remains attached to the optimizer and the second AdamW step succeeds, including with `overwrite_module_params_on_conversion=True`.
- `pre-commit run --all-files`: passed all configured hooks.
- A GPU platform run with ms-swift 4.5.3, GKD `--lmbda 0.5`, PEFT LoRA, BF16, colocate vLLM and `adamw_torch` completed all `4/4` steps and saved a LoRA checkpoint. Its 39 non-path training flags matched the pre-fix run, which failed after `1/4` steps. Sanitized output:

  ```text
  before fix: global_step/max_steps: 1/4
  before fix: RuntimeError: expected dtype float for `end` but got dtype c10::BFloat16
  after fix:  global_step/max_steps: 4/4, train_loss: 0.2442
  after fix:  checkpoint-4 saved; main process return code: 0
  ```

- The training log does not record each stochastic online/offline choice. The standalone reproducer in #10360 exercises the merge/unmerge path directly; the GPU run is an end-to-end regression check.
- The community branch is based on the locally fetched `origin/main` and changes only `swift/rlhf_trainers/utils.py`.
- GRPO LoRA GPU regression: not run.
