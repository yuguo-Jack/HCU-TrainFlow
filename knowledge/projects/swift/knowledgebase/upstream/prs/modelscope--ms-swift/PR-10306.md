[Upstream PR](https://github.com/modelscope/ms-swift/pull/10306) · state: closed · merged: True

## Original PR description

…OmniJev

Non-generative `decision` task_type: a single forward pass scores every option into calibrated per-option probabilities. transformers backend only.

- model: ScoringModelLoader + JEV/Clef/OmniJev heads; OmniJev two-stage cached branch forward over the hybrid Qwen3.5 backbone + media compose
- template: decision encode/collate (train right- / infer left-padding)
- dataset: unified user schema, per-model preprocessor subclasses
- loss: ScoringLoss + JEV/Clef/OmniJev heads (masked soft-CE + ordinal RPS)
- trainer: ScoringTrainer re-activates and saves the fp32 head under LoRA
- examples/train/decision/{jev,clef,omnijev}.sh + dataset plugin + data
- tests/test_align: four-stage alignment harness vs each official oracle

Aligned to each official inference path: encoding byte-exact, head math <=1e-7, full forward within bf16 tolerance, loss+grad vs re-derived formula.

**`num_items_in_batch` is not the question count, so the training loss scale is silently off**

HF computes it as the number of `labels.ne(-100)` entries in the accumulation window (with a `[..., 1:]` shift for CausalLM). decision labels are a `[total_q, max_opt]` probability matrix padded with 0.0, so it equals Σ(n_options−1): measured 5/2/1 for 6/3/2-option rows (ga=1), and the same scalar for both micro-batches of a step (ga=2: 6, then 7). Per-question weights are uniform, but the window loss is scaled by 1/mean(n_options−1) with step-to-step variation (measured 1/5 vs 1/1; up to 1/15 for 16-option tasks) — reported loss/grad_norm are not the documented per-question mean, and since `compute_loss_func` is set HF no longer divides by ga, so this is the only normalization. The comment at `decision_trainer.py:79-88` ("total question count") doesn't match the framework.

Suggestion: override `_get_num_items_in_batch` in `ScoringTrainer` (return Σ`labels.shape[0]` of the window), or normalize by `per_question.numel()`; add a ga>1 test asserting the denominator == #questions — the align tests currently only pass `num_items_in_batch=None`.

JevVerbalizerHead 工作原理：该头是一种轻量级 verbalizer 打分头，不引入额外的神经网络层，而是直接复用底座 CausalLM 的 lm_logits。它在每个问题 prompt 的最后一个 token 位置读取 lm_logits，做 log_softmax 后，按 kind 从中抽取对应 verbalizer token 的 log-probability。三种 kind 对应 24 个固定 verbalizer token：
noul（2 个）：false, true
score（6 个）：0, 1, 2, 3, 4, 5
choice（16 个）：A … P
每个 verbalizer token 拥有一个可训练的 fp32 bias 标量（共 24 个），再加上 3 个 per-kind 温度参数。前向计算为 z = (log_prob + bias) / temperature，随后在问题自己的选项集上做 softmax。from_tokenizer 构建路径会从 tokenizer 解析这 24 个 token id，bias 零初始化、温度单位初始化，使其可以直接从随机状态开始与 LoRA adapter 联合训练。

swift/model/models/decision.py里面：
1、GenericDecisionLoader.get_model — 加载底座模型 + 构建头 + 挂载
2、ScoringModelLoader.attach_scoring_head — 把头挂到模型上并劫持 forward
