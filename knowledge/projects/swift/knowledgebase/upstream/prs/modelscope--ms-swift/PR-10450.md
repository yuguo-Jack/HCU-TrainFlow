# PR information

Follow-up to #10337. No separate issue: found through code analysis and a constructed reproduction of the existing GRPO caller.

Padded GRPO with batch size greater than one and more than one completion token passes `logits[:, -(logits_to_keep + 1):-1, :]` to `selective_log_softmax`. The excluded tokens leave gaps between batches, so the helper's `reshape` copies the entire B×T×V slice before chunking. Reducing `chunk_size` does not remove that allocation.

Use a view when the leading dimensions can be flattened without copying; otherwise compute the batch slices separately with the same chunked helper. Keep the existing packed path, output shapes, masking, temperature and gradient semantics. Add allocation and forward/backward regressions to the existing test suite.

Duplicate check: reviewed all open PR titles and file lists, recent closed PRs and helper history. #10439 changes the adjacent entropy helper with a similar layout strategy; it does not change selective log-softmax or remove this copy.

AI assistance: OpenAI Codex assisted with investigation, implementation and validation.

## Experiment results

- `python -m unittest discover -s tests/general -p test_selective_log_softmax.py -v`: 10 tests passed. Against the unchanged helper, the new allocation test fails in all four dtype/layout subcases; the value/gradient test passes.
- CPU check using the imported `GRPOTrainer._get_logps_via_local_forward` with constructed differentiable logits (`B=2`, `T=1024`, `V=4096`): the original helper clones a 32 MiB FP32 / 16 MiB BF16 logits buffer; the fix produces no floating-point clone. Output and input gradients are bit-identical. The packed `B=1` control has no such clone before or after.
- Independent CPU comparison: 540 dtype/layout/index/temperature/chunk combinations and 1,080 weighted backward passes match the original helper; packed reduction call counts are unchanged.
- `pre-commit run --all-files`, `git diff --check` and `python -m pip check`: passed.

These are CPU allocation and correctness checks with PyTorch 2.14.0, not full training, CUDA peak-memory, throughput or OOM results. The existing allocation for `temperature != 1` is unchanged.
