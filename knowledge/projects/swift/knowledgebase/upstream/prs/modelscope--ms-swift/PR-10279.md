# fix(ui): use the last assistant turn when marking a toolbench observation

[Upstream PR](https://github.com/modelscope/ms-swift/pull/10279) · state: open · merged: False

## Original PR description

## Problem

`LLMInfer.send_message` looks for the assistant turn backwards but never stops at the first
hit:

```python
response = ''
i = len(infer_request.messages) - 1
for i in range(len(infer_request.messages) - 1, -1, -1):
    if infer_request.messages[i]['role'] == 'assistant':
        response = infer_request.messages[i]['content']
agent_type = cls.agent_type(response)
if i != len(infer_request.messages) - 1 and agent_type == 'toolbench':
    infer_request.messages[i + 1]['role'] = 'tool'
```

So `i` always ends at `0` and `response` holds the **first** assistant turn of the conversation
instead of the one that was just streamed. Executing those lines verbatim on a toolbench turn
`[system, user, assistant(...Action Input: ...), user(observation)]`:

```
before: [('system', 'sys'), ('tool', 'What is the weather in Berlin?'),
         ('assistant', '...Action Input: ...'), ('user', 'sunny')]
after:  [('system', 'sys'), ('user', 'What is the weather in Berlin?'),
         ('assistant', '...Action Input: ...'), ('tool', 'sunny')]
```

Two consequences:
- the agent type is classified from the wrong turn, so a toolbench conversation whose earlier
  turns are plain chat is never recognised (`response` = `'hello'` → `agent_type` is `None`);
- `messages[i + 1]` is `messages[1]`, i.e. the **user question**, which is relabelled `'tool'`
  — and when the assistant turn is already the last message, the assistant message itself is
  relabelled `'tool'`.

## Fix

Move the scan into `mark_toolbench_observation` and stop at the last assistant turn, so the
message that actually follows that turn is the one that becomes the tool response. Behaviour is
otherwise unchanged (a conversation with no assistant turn, or one that ends on an assistant
turn, is left alone).

## Verification

`tests/llm/test_llm_infer.py` — CPU only, no gradio server, calls the classmethod directly:
- the observation after a toolbench turn becomes a `tool` response;
- only the **last** assistant turn is classified (earlier turns do not confuse it);
- only the message right after that turn is relabelled;
- a conversation ending on an assistant turn is untouched (this is the case that used to
  relabel the assistant message itself);
- ReAct turns, conversations without an assistant turn and an empty conversation are untouched.

Each case was also checked against the genuine `agent_type` / `mark_toolbench_observation`
source extracted from this file.
