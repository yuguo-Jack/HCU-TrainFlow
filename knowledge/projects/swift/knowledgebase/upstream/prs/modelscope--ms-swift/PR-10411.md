# PR information

Fixes #10410

## Problem

GRPO on a multimodal model with `--use_liger_kernel true` and `--deepspeed zero3` hangs in the first training step when the ranks hold a mix of text-only and image samples. Nothing is raised; with the default `ddp_timeout` the job just stays blocked.

## Root cause

The Liger path in `compute_loss` goes through `_forward_redirection`, so the DeepSpeed engine runs the template's pre-forward hook first. For multimodal templates the hook (`Template.pre_forward_hook` -> `_post_encode`) replaces `input_ids`/`pixel_values` with `inputs_embeds`, and text-only samples run the vision encoder on a dummy image, so every rank calls the vision encoder once.

The redirected callable was `lambda *_, **__: self.compute_liger_loss(unwrapped_model, model_inputs, grpo_batch)`. It drops the hook's kwargs, and `_get_last_hidden_state` then calls the inner model with the original `model_inputs`, which still contain `pixel_values`. Ranks holding images run the vision encoder a second time, the ranks issue different ZeRO-3 parameter all-gathers, and training deadlocks. Without ZeRO-3 it does not hang, but image samples still pay for a second vision-encoder pass.

This form came from #9406 (the `KeyError: 'input_ids'` fix) and is unchanged on `main`.

## Change

Only `swift/rlhf_trainers/grpo_trainer.py` changes (+16/-3), plus one CPU test.

- `compute_loss` (Liger path): the redirected function now receives the hook's kwargs. When they contain `inputs_embeds`, it passes them to `compute_liger_loss` together with the original `input_ids`, which is still needed to select the completion tokens. Otherwise (text-only models, or templates whose `_post_encode` does not produce `inputs_embeds`) it keeps the previous behavior.
- `_get_last_hidden_state` (multimodal branch): drops `input_ids` when `inputs_embeds` is present, since the model accepts only one of them.

`_forward_redirection` is kept, so ZeRO-3 still gathers the backbone and `lm_head` parameters inside the engine's forward. After the change the inner model gets the same kwargs as the non-Liger path (`model(**inputs)` through the same hook).

## Experiment results

The run that hung, repeated with the fix. Qwen3.8-27B (model_type `qwen3_5`, template `qwen3_8`), LoRA rank 128, 4 training GPUs (H100, ZeRO-3 + Liger) and a `swift rollout` server (vLLM, TP4), async generation, 16K max length. Each step mixes 8 text-only prompts and 8 prompts with 2 images (64 completions).

| 4.5.3 | Hangs in step 1 (twice). With `--ddp_timeout 7200`, all ranks abort at the same `_ALLGATHER_BASE` (SeqNum 76799): ranks 1 and 3 on the vision `patch_embed` weight (442,368 -> 1,769,472 elements), ranks 0 and 2 on a 24-byte object gather | - |
| `main` (5c7f3ae) + this PR | 3/3 steps completed | 44.25 GiB |

The second row installs a wheel built from this branch, with no other patch. Environment: PyTorch 2.11, Transformers 5.13.0, DeepSpeed 0.18.9, vLLM 0.24.0, Liger Kernel 0.8.2.

CPU regression test:

```bash
python -m unittest tests/train/test_grpo_liger_mllm_forward.py
# Ran 1 test ... OK (2 subtests: with and without an image)
pytest tests/train/test_grpo_liger_mllm_forward.py tests/train/test_grpo_reward_metrics.py -q
# 5 passed, 2 subtests passed
pre-commit run --files swift/rlhf_trainers/grpo_trainer.py tests/train/test_grpo_liger_mllm_forward.py
# all hooks passed
```

`tests/train/test_grpo_liger_mllm_forward.py` calls the real `GRPOTrainer.compute_loss`, `_ForwardRedirection`, `_get_last_hidden_state` and `Template.pre_forward_hook` with a toy multimodal model whose `_post_encode` follows `Qwen2VLTemplate` (dummy image for text-only samples). It checks that the vision encoder runs once per forward with and without an image, and that the inner model receives `inputs_embeds` only. On `main` both cases fail (the image case calls the vision encoder twice). It is a `unittest.TestCase`, so `tests/run.py` picks it up; it runs on CPU in a few seconds.

Not tested: FSDP, sequence parallel, eval-time Liger loss, and models other than Qwen3.8-27B on GPU.

Scope:

- Covered: templates whose `_post_encode` produces `inputs_embeds`, such as Qwen2-VL / Qwen2.5-VL / Qwen3.5 through `Qwen2VLTemplate._post_encode`.
- Not covered: `Qwen3VLTemplate._post_encode` returns the inputs unchanged, so Qwen3-VL keeps the previous behavior, and its vision encoder still runs only on the ranks with images (on the non-Liger path as well).
- Not changed: `gkd_trainer.py` uses the same `lambda *_, **__:` pattern for its Liger loss (student and teacher). I did not touch it because I have not tested multimodal GKD.
