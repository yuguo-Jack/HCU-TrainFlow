# fix(megatron): Fix gradient norms and expert DP routing for legacy MCore

# PR information

Legacy MCore can omit expert gradients or overcount TP replicas when computing the gradient norm, changing gradient clipping. With EP=1 and ETP!=TP, expert gradients can also use the wrong DP group and cause expert replicas to diverge.

This PR backports:

- [Megatron-LM#5916](https://github.com/NVIDIA/Megatron-LM/pull/5916) (MCore 0.19): use ETP for expert duplicate filtering, preserve `allreduce` on FP32 main parameters, fix expert DP routing before DDP wrapping, and restore expert shard metadata for GPU TE and MindSpeed linear layers. Column weights/biases and row weights are shards; row biases are replicas.
- [Megatron-LM#3213](https://github.com/NVIDIA/Megatron-LM/pull/3213) (MCore 0.17): count ordinary `duplicated` TE parameters once.
- Native TP metadata repair for embedding/column/row weights when checkpoint loading skips initialization, preserving partition dimensions and stride.

The patches in `swift/megatron/init.py` are idempotent and reapplied after MindSpeed repatching. Filtering is capability-gated; metadata fixes apply below their respective upstream versions.

Related: [mcore-bridge#229](https://github.com/modelscope/mcore-bridge/issues/229), [mcore-bridge#231](https://github.com/modelscope/mcore-bridge/pull/231).

## Validation

**Compatibility tests:** MCore 0.16.0: 14 passed in both GPU and NPU environments. Official 0.19 source: 12 passed, two legacy-only tests skipped. Repository pre-commit checks passed.

### H20: 300-step comparison with upstream MCore

Compared unpatched MCore 0.16.0, MCore 0.16.0 plus this PR, and official [`core_v0.19.0` source](https://github.com/NVIDIA/Megatron-LM/tree/core_v0.19.0) (reports version 0.19.1 and uses native fixes).

All variants shared the H20-3e container, PyTorch 2.9.0+cu130, TE 2.9.0 and mcore-bridge snapshot; the upstream comparison switched MCore source in that environment.

- Model/data: Qwen3-30B-A3B-Instruct-2507, **two layers**, full embedding/output and all 128 experts; `alpaca-gpt4-data-zh`, first 512 records.
- Training: BF16 full parameters, 300 optimizer steps per variant/topology, micro/global batch=1/8, length=128, seed/data_seed=42, PP=CP=1, SP enabled, grouped GEMM/alltoall, distributed AdamW, LR=1e-5, clip=1, full recomputation and unfused attention.
- Initial parameter and all actual input/label hashes matched across corresponding ranks. All runs completed 300 updates with finite loss/norm and exit code 0. The two-device patched/upstream pair used separate H20 pairs; others used the same devices sequentially.

Loss MAE compares matching optimizer steps:

| TP / EP / ETP | Unpatched vs upstream | Backport vs upstream | MAE reduction |
|---|---:|---:|---:|
| 2 / 1 / 2 | 0.00844809 | 0.00213341 | 3.96x |
| 4 / 1 / 2 | 0.45497113 | 0.00229694 | 198.08x |
| 2 / 2 / 2 | 0.00823119 | 0.00238547 | 3.45x |
| 2 / 4 / 1 | 0.00850320 | 0.00223996 | 3.80x |

The independent norm reference uses module layouts and optimizer gradient shards, not the repaired TP flags:

- Three unpatched cases had maximum norm errors of 16.8–17.4%, with actual post-clipping norms reaching 1.202–1.211 for a threshold of 1. Backport/upstream norm errors were below 2.6e-7 and post-clipping errors below 6.6e-7.
- For `(TP,EP,ETP)=(4,1,2)`, wrong DP routing caused expert replica weight differences up to 0.0009765625 at sampled positions; both repaired variants had zero sampled spread. A reference norm is not reported for the incorrectly synchronized baseline.

TE 2.9.0 already marks expert shards here. The other three baselines expose missing embedding/output TP metadata, so the improvements cover the combined fixes, not solely expert filtering.

### Ascend 910B3: independent norm and clipping checks

Before/after BF16 training with reduced-layer Qwen3 MoE, all 128 experts, MCore 0.16.0 and ETP=1 produced:

| Training | Original norm relative error | Patched max error | Original actual norm after clipping |
|---|---:|---:|---:|
| Full parameters | 5.785–10.128% | 1.675e-7 | 1.061403–1.112694 |
| LoRA | 25.105–27.618% | 1.287e-7 | 1.335198–1.381556 |

With clip=1, patched actual norms were approximately 1; initial parameter and input/label hashes matched.

Three-step ETP=2 full-parameter checks covered `(2,1,2),(4,1,2),(2,2,2)` on H20 and Ascend/MindSpeed. Patched norm errors were below 1.1e-7 on GPU and 1.6e-7 on NPU, with finite gradients and actual updates.

On NPU `(2,1,2)`, adding expert shard metadata to the earlier backport reduced the norm error from 1.0222% to 5.830e-8 and restored post-clipping norms from 1.00754–1.01033 to approximately 1. GPU TE already supplied these flags.

### Full 48-layer LoRA: 200-step GPU/NPU comparison

Four H20-3e GPUs and four Ascend 910B3 NPUs each completed 200 LoRA steps on full BF16 Qwen3-30B-A3B-Instruct-2507 and `alpaca-gpt4-data-zh`.

Configuration: MCore 0.16.0, TP=2/EP=4/ETP=1, PP=CP=1, micro/global batch=4/8, length=128, LoRA rank/alpha=8/16, dropout=0, LR=1e-5 and clip=1. Effective targets were explicitly matched: `linear_qkv`, `linear_fc1`, `linear_fc2`; the separate NPU `all-linear` discovery issue is outside this PR.

Weights, tokenizer, data, initial parameters and all actual input/label hashes matched. **Loss MAE: 0.00519383; maximum absolute difference: 0.03110123.**

### Scope

Cross-version MAE includes other MCore changes; deterministic execution and repeated-run noise were not controlled. The 300-step model has two layers and repeats 512 records; the three-step runs only check correctness. These results do not establish bitwise or downstream-quality equivalence. High-version MCore was tested on GPU only. Expert LoRA remains limited to ETP=1. FP8, arbitrary custom process groups, checkpoint save/resume and performance were not validated.

File: `tests/megatron/test_expert_parallel_compat.py` · line None

On MCore 0.19, the native predicate uses the supplied ordinary TP group unless `expert_tp_group` is explicitly provided. Swift intentionally leaves that implementation untouched, so mocking the global ETP getter does not affect this assertion: it returns False. Pass the expert group explicitly in this cross-version test; any test of the backport's global fallback should be limited to the legacy implementation.

- copilot-pull-request-reviewer[bot] · comment · 2026-10-15T07:12:36Z · [source](https://github.com/modelscope/ms-swift/pull/10364#discussion_r4280107251)

File: `tests/megatron/test_expert_parallel_compat.py` · line 76

On MCore 0.19, the native TP-attribute copier does not copy `allreduce`; upstream provides a separate metadata-copy helper for it. Swift correctly skips its legacy copier shim on that version, so this test raises AttributeError even though the shim is not needed. Skip this shim-specific test on non-legacy versions rather than skipping the whole suite, which would also remove coverage of native pass-through behavior.

- addsubmuldiv · comment · 2026-10-26T12:29:52Z · [source](https://github.com/modelscope/ms-swift/pull/10364#discussion_r4377204780)

File: `swift/megatron/init.py` · line 149

Yes, when ETP=1, each expert TP group contains a single member, whose group-local rank is 0. Returning True is intentional: this predicate filters tensor-parallel replicas, and there are none within a singleton expert TP group. Distinct experts across EP ranks must still contribute to the gradient norm.

For ETP>1, partitioned parameters are retained by the preceding tensor_model_parallel check, while replicated parameters are counted only on expert TP rank 0. Therefore, the same logic handles both cases.
