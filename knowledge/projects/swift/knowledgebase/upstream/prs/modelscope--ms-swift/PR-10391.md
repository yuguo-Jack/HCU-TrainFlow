<!-- Add the related issue before submission. Required for first-time contributors. -->

Collecting training performance traces currently requires users to integrate profiler setup and lifecycle handling into their training code. This PR adds a built-in `profiler` callback for the Transformers and Megatron-SWIFT backends. Users can capture a selected training window with `--callbacks profiler` and environment variables. The callback is included in the standard pip package and requires no external script or trainer source changes.

### Changes

- Add shared profiling configuration and session management in `swift/utils/profiler.py`, with backend-specific adapters in `swift/callbacks/profiler.py` and `swift/megatron/callbacks/profiler.py`. Register both adapters as the built-in `profiler` callback in their respective callback mappings.
- Replace the external example script with packaged modules so the feature works with a standard pip installation. Existing users can remove `--external_plugins examples/custom/profiler.py` while keeping `--callbacks profiler` and their `SWIFT_PROFILER_*` settings.
- Use `torch.profiler` for CUDA and `torch_npu.profiler` for Ascend NPU. Device selection can follow the training arguments automatically or be configured explicitly; CPU tracing is available for debugging.
- Configure the first recorded step, warmup, active steps, output directory, and selected global ranks through `SWIFT_PROFILER_*` environment variables. Invalid configuration raises a descriptive error.
- Collect one window per selected process, then close the profiler while training continues. Use backend training-step counters rather than gradient accumulation microbatches.
- Save traces and `config.json` under separate directories for each collection window, global rank, and run, using hostname, process ID, and timestamp to avoid collisions.
- Handle normal training completion and profiler start/step errors, with best-effort cleanup at interpreter exit. Skip windows already missed when resuming from a checkpoint instead of silently shifting them.
- Update bilingual profiling documentation, callback parameter references, READMEs, training guides, and Megatron quick starts to describe the built-in callback and migration from the external example.
- Add tests for collection timing, built-in callback registration and adapters, configuration validation, rank filtering, resume behavior, cleanup, dependency isolation, CPU trace export, and integration with a real Transformers training loop.

### Usage

Set the collection window in an existing training environment:

```bash
export SWIFT_PROFILER_DEVICE=auto
export SWIFT_PROFILER_START_STEP=1000
export SWIFT_PROFILER_WARMUP_STEPS=1
export SWIFT_PROFILER_ACTIVE_STEPS=3
export SWIFT_PROFILER_OUTPUT_DIR=output/profiling
export SWIFT_PROFILER_RANKS=all
```
Append these arguments to an existing `swift sft/pt/rlhf` or `megatron sft/pt/rlhf` training command:

```bash
--callbacks profiler
```
Keep the existing model, dataset, parallelism, and training arguments. If other callbacks are already configured, append `profiler` to the callback list and keep any external plugins required by those callbacks.

This example warms up at step 999, records steps 1000–1002, and stops profiling after step 1002. Training continues afterward. These are one-based training updates/iterations, not individual microbatches.

### Profiling configuration

The example above sets the following environment variables. The example values override the callback defaults.

| Environment variable | Example value | Default | Meaning |
| --- | --- | --- | --- |
| `SWIFT_PROFILER_DEVICE` | `auto` | `auto` | Select the profiling device. `auto` follows the device in the training arguments when available; otherwise, it detects an available NPU or CUDA device. Explicit options are `npu`, `cuda`, and `cpu` for debugging. This setting does not change the training device. |
| `SWIFT_PROFILER_START_STEP` | `1000` | `1000` | The first **actively recorded** training step, numbered from 1. Must be at least 1. Steps follow the backend's training-update/iteration counter rather than individual gradient accumulation microbatches. |
| `SWIFT_PROFILER_WARMUP_STEPS` | `1` | `0` | Number of profiler warmup steps immediately before START_STEP. Warmup steps are not part of the active trace window. Must be nonnegative and smaller than START_STEP. In this example, step 999 is the warmup step. |
| `SWIFT_PROFILER_ACTIVE_STEPS` | `3` | `1` | Number of consecutive training steps to record. Must be at least 1. This example records steps 1000, 1001, and 1002 in one collection window. |
| `SWIFT_PROFILER_OUTPUT_DIR` | `output/profiling` | `<training output_dir>/profiling` | Root directory for profiling artifacts. Relative paths are resolved against the training process's working directory. An unset or empty value uses the default. |
| `SWIFT_PROFILER_RANKS` | `all` | `all` | Select the distributed processes that collect traces: `all`, a single global rank such as `0`, or comma-separated global ranks such as `0,1,8,9`. These are global ranks, not per-node local ranks. |

Additional NPU analysis settings:

| Environment variable | Default | Meaning |
| --- | --- | --- |
| `SWIFT_PROFILER_NPU_ASYNC_MODE` | `false` | Enable asynchronous analysis when automatic analysis is enabled. |
| `SWIFT_PROFILER_NPU_ANALYSE_FLAG` | `true` | Enable automatic analysis. Set to `false` to retain raw data for offline analysis. |

`SWIFT_PROFILER_NPU_ANALYSE_FLAG=false` takes precedence: automatic analysis is disabled regardless of `SWIFT_PROFILER_NPU_ASYNC_MODE`. When automatic analysis is enabled, `SWIFT_PROFILER_NPU_ASYNC_MODE=false` uses synchronous analysis (the default), while `true` enables asynchronous analysis.

The example produces this collection sequence:

```text
Steps 1–998:   normal training, profiler inactive
Step 999:      profiler warmup
Steps 1000–1002: active recording
After step 1002: profiler stops; training continues
```

Each selected process records one window per training run. Multiple active steps share the same run directory. Repeating the training command with the same START_STEP and output root creates a new `<hostname>_<pid>_<timestamp>` subdirectory under the same step/rank directory, rather than overwriting the previous run.

If a resumed checkpoint has already passed the warmup start, the entire window is skipped. With this example, the profiler must start before step 999 executes; choose a future START_STEP when that point has already passed.

### Implemented scope

| Training backend | CUDA GPU | Ascend NPU |
| --- | --- | --- |
| Default Transformers backend | `torch.profiler` callback | `torch_npu.profiler` callback |
| Megatron-SWIFT | `torch.profiler` callback | `torch_npu.profiler` callback |

This table describes the implemented adapters and profiler routing.

- `SWIFT_PROFILER_RANKS` accepts `all` or comma-separated **global** ranks. Each selected process collects independently, without additional distributed barriers.
- NPU profiling supports `Level0`, `Level1` (default), and `Level2`. Shape recording and memory-event collection default to enabled; call stacks default to disabled.
- The default backend does not require Megatron/MindSpeed. The CUDA path does not require importing `torch_npu`.
- Only training processes that enable the callback are profiled. Separate rollout services are outside the collection scope. Custom/Ray launchers must forward the callback selection and environment settings to training workers.
- Checkpoint resumption uses absolute step counters. If the window's warmup start has passed, collection is skipped and a future START_STEP is required.
- Early termination may produce a partial trace; warmup-only runs or forced termination cannot guarantee export. Detailed collection adds runtime overhead, and GPU/NPU trace formats and analysis tools remain backend-specific.

### Output

```text
output/profiling/
└── profile_step_1000/
    └── rank_<global_rank>/
        └── <hostname>_<pid>_<timestamp>/
            ├── config.json
            └── ... profiler-generated files
```
`config.json` records the requested settings, training backend, device, global rank, PyTorch version, and planned active-step interval. The profiler exports its native trace files; actual completion should be checked in the trace and the `completed_window_steps` log, which includes warmup.

## Experiment results

The PR adds `tests/general/test_profiler.py`. The test suite covers:

- Exact target-step activation, warmup, multi-step collection, and no restart after the window.
- Transformers and Megatron callback signatures, including gradient accumulation substeps.
- Rank filtering, missed resume windows, early completion, and exception cleanup.
- Device routing and avoiding unnecessary Megatron or torch_npu imports.
- Invalid settings, environment-variable parsing, and defaults.
- A real CPU trace that includes only the requested active training steps.
- A real Transformers training loop using the built-in callback factory, including gradient accumulation.
- Built-in registration without starting a profiler or importing optional Megatron/NPU dependencies.
