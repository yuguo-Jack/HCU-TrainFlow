# PR information

Fixes #10382

Two related additions to `swift eval`, both aimed at the same friction: checking a checkpoint you just trained should not require standing up a server.

### 1. `--eval_offline` — evaluate in-process instead of deploying

`swift eval` is deploy-first: unless `--eval_url` points at a service you started yourself, it spawns a server subprocess (`eval.py:25`) and evaluates over HTTP. Every run pays a full engine startup (loading weights, capturing CUDA graphs) just to talk to itself over localhost, and it needs a free port.

The pieces for an in-process path already exist: `swift/pipelines/eval/utils.py:54` registers a `swift_custom` ModelAPI (`EvalModel`) that runs `TransformersEngine` directly on a swift model object. Its only caller today is the training loop (`swift/trainers/mixin.py:1238`, `eval_use_evalscope`); `swift eval` never used it. `--eval_offline` hands the model object to that same engine, so both paths run the same evaluation implementation — this one just skips the deploy.

Scope is the `Native` backend; `OpenCompass` and `VLMEvalKit` are wired to an `api_base` URL (`eval.py:144-149`), so they keep requiring a deployed service. Requesting them with `--eval_offline` raises instead of silently falling back.

### 2. `--eval_ckpts` — sweep several checkpoints in one run

Evaluating N checkpoints used to mean N full server startups. With the in-process engine nothing is deployed per checkpoint, so a sweep becomes cheap — one command, one process, one aggregated report at the end:

```bash
swift eval \
  --model Qwen/Qwen2.5-VL-7B-Instruct \
  --eval_backend Native --eval_offline true \
  --eval_ckpts 'output/run1/v0-*/checkpoint-*' \
  --eval_dataset gsm8k --eval_limit 20
```

```
| checkpoint   | gsm8k |
|--------------|-------|
| checkpoint-2 | 0.4   |
| checkpoint-4 | 0.6 ✅ |
```

Each entry is either a LoRA adapter directory (detected via `adapter_config.json`, evaluated on top of `--model`) or a full model directory. Globs are expanded and results are ordered by checkpoint. `eval_ckpts` requires `eval_offline`, since sweeping deployed servers is exactly what this is trying to avoid.

### Also fixed

`list_eval_dataset` (`swift/arguments/eval_args.py:85`) always called `OpenCompassBackendManager.list_datasets()`, so `swift eval` failed with `ModuleNotFoundError: No module named 'opencompass'` unless opencompass was installed — even for the Native backend. The VLMEvalKit entry was already guarded by `try/except ImportError`; this gives the OpenCompass entry the same guard.

## Experiment results

Offline, single checkpoint:

```bash
swift eval --model /path/to/qwen2.5-0.5b --eval_backend Native \
  --eval_offline true --eval_dataset gsm8k --eval_limit 5
```

```
Model        Dataset   Metric     Subset   Num   Score
qwen2.5-0.5b GSM8K     Accuracy ↑ main     5     40%
```

The report comes back with `eval_type: swift_custom` and `api_url: null`, i.e. no service was deployed and nothing was called over HTTP.

Checkpoint sweep over two LoRA checkpoints of the same run (real output, table above): 0.4 and 0.6, with the best one marked.

Tests: `tests/general/test_eval_offline.py` covers the backend guard.
