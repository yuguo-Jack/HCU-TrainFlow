# PR information

Fixes #8317

`wrap_model()` in `swift/megatron/utils/megatron_lm_utils.py` always built DDP and Megatron-FSDP inside a one-shot `torch.cuda.Stream()`. DDP keeps the AccumulateGrad nodes it creates during init, so they stay bound to that side stream while backward runs on the current stream. With torch 2.10 this prints on every run: "The AccumulateGrad node's stream does not match the stream of the node that produced the incoming gradient ... ensure that DDP initialization is performed under the same stream as subsequent forwards." Cached allocator blocks owned by the side stream also cannot be reused by later current-stream allocations.

This ports NVIDIA/Megatron-LM#6885 ("Fix one-shot stream causing FSDP memory leaks"), which made the same change in Megatron-LM's `build_model` and `_ddp_wrap`:

- When `config.cuda_graph_impl == 'none'` (the default, eager), DDP and Megatron-FSDP are built on the current stream and both `wait_stream` calls are skipped.
- For `local`, `transformer_engine` and `full_iteration`, the dedicated side stream and both waits are kept exactly as before.

Upstream's extra `full_iteration -> get_shared_capture_stream()` branch is not ported, because ms-swift's trainer has no full-iteration CUDA graph capture.

This is a warning and memory fix, not a numerics change: in the runs below the logged loss and grad_norm are identical to main at every step (as logged, 8 decimal places).

## Experiment results

`megatron sft`, Qwen2.5-3B-Instruct full SFT, mbs 4, gbs 16, max_length 512, 30 iters, seed 42; torch 2.10.0+cu128, Transformer Engine 2.16.0, megatron-core 0.18.2, mcore-bridge 1.6.5, transformers 5.22.1. main = 680df5c, fix = f420292. DP=2 on 2x RTX PRO 6000 (`--attention_backend unfused` on both arms, since TE has no fused backend for these inputs on sm_120), interleaved ABBA, 4 runs per arm, medians. Memory values are rank 0.

| DP=2 | AccumulateGrad warnings per run | loss and grad_norm vs main | peak reserved during wrap | reserved after wrap | training peak reserved | step time |
|---|---|---|---|---|---|---|
| DDP main | 2 (one per rank), 4/4 runs | | 23.10 GiB | 23.10 GiB | 37.17 GiB | 783 ms |
| DDP fix | 0, 4/4 runs | identical, 30/30 steps, 4/4 runs | 23.10 GiB | 23.10 GiB | 37.17 GiB | 774 ms |
| Megatron-FSDP main | 0 | | 20.43 GiB | 14.44 GiB | 35.58 GiB | 934 ms |
| Megatron-FSDP fix | 0 | identical, 30/30 steps, 4/4 runs | 17.40 GiB | 14.98 GiB | 35.55 GiB | 928 ms |

- The DDP warning goes from one per rank to zero.
- Megatron-FSDP: peak reserved during wrap drops by 3.04 GiB (14.9%) on both ranks. Reserved right after wrap is 0.54 GiB higher, because blocks stay cached for the current stream instead of the side stream. Training peak reserved is essentially unchanged (rank 0 35.58 to 35.55 GiB, rank 1 35.72 to 35.73 GiB).
- Step time differences (1.1% DDP, 0.6% FSDP) are within run-to-run spread, so I do not claim a speedup.
- On 1x H200 (DP=1, fused attention) logged losses are also identical over 30 steps for DDP and Megatron-FSDP, and the DDP warning goes from 1 to 0.

It mocks the stream APIs, `mpu`, DDP and Megatron-FSDP and checks two things: eager mode uses the current stream with no side stream and no waits, and `local`, `transformer_engine` and `full_iteration` keep the side stream and both waits.
- In the GPU env: 2 passed with the fix; on main the eager test fails (2 failing subtests) and the CUDA graph test passes.
