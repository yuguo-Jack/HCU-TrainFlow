# PR information

vLLM streaming response conversion recreated `previous_texts` on every engine result. The reasoning parser therefore received cumulative token IDs together with an empty text prefix, so text-delimited parsers could not recognize delimiters spanning multiple deltas. The wrapper also treated a parser return value of `None` as a reason to emit the original delta, even though vLLM uses `None` while buffering a possible delimiter.

This change keeps one text history per choice beside the existing token cursor for the lifetime of each request, in both async and synchronous streaming paths. The state remains local to the request, so concurrent requests cannot share it. When the parser buffers a delta, Swift now suppresses that delta instead of leaking the delimiter into `content`. The existing raw-text fallback on parser exceptions and the path without a reasoning parser are unchanged.

This response conversion runs after vLLM has returned sampled token IDs. The change does not modify sampling parameters, logits, token IDs, or stopping behavior.

## Experiment results

- The exact vLLM v0.11.0 Granite parser correctly reconstructed a five-delta response whose reasoning and response delimiters cross packet boundaries: `reasoning_content == "Compute 2+2. "` and `content == "4"`.
- All 13 streaming boundary cases from vLLM v0.11.0's official Granite parser tests passed through Swift's response wrapper.
- Focused regression checks passed for two choices delivered in reverse output order, two interleaved concurrent requests, the no-parser path, parser-exception fallback, token cursor advancement, and per-choice accumulated text.
- `uvx pre-commit run --files swift/infer_engine/vllm_engine.py`: all hooks passed.
- `python3 -m py_compile swift/infer_engine/vllm_engine.py` and `git diff --check`: passed.

The focused validation harness is outside this production-only diff.
