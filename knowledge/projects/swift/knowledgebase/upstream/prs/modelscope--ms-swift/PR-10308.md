# PR information

## What this fixes

`scale_rewards` and `kl_in_reward` exist on both backends, but only the transformers side resolves them from `advantage_estimator`:

| | file:line | behaviour |
|---|---|---|
| correct | `swift/arguments/rlhf_args.py:370-391` (`RLHFArguments._init_grpo`) | resolves both from `advantage_estimator` |
| wrong | `swift/megatron/arguments/megatron_args.py:152,156` | hardcodes `'group'` / `False`; `_init_grpo` never binds them |

Their defaults are documented as **tied to `advantage_estimator`**, in three places — including the Megatron command-line reference itself:

- `swift/rlhf_trainers/args_mixin.py:315-321` — *"The default value is tied to `advantage_estimator`: 'group' for 'grpo', 'none' for 'rloo', and 'batch' for 'reinforce_plus_plus'."*
- `swift/rlhf_trainers/args_mixin.py:350-353` — same for `kl_in_reward`.
- **`docs/source_en/Megatron-SWIFT/Command-line-parameters.md:426`** (and the zh twin `docs/source/Megatron-SWIFT/Command-line-parameters.md:403`) — *"The default value is bound to `advantage_estimator`: `grpo` corresponds to `group`, `rloo` corresponds to `none`, and `reinforce_plus_plus` corresponds to `batch`."*

So the Megatron **code** contradicts the Megatron **documentation** and its transformers twin.

## Consequence

`examples/train/grpo/internal/rloo.sh` passes `--advantage_estimator rloo --kl_in_reward true` and **no `--scale_rewards`**, relying on the documented tie-in. On the Megatron backend that silently trained a different algorithm than on transformers:

- `kl_in_reward=False` kept KL as a separate loss term instead of folding the KL penalty into the reward (`swift/rl_core/advantage.py:56-57` vs the loss term at `swift/megatron/trainers/grpo_trainer.py:1007`).
- `scale_rewards='group'` divided the RLOO leave-one-out advantages by the intra-group standard deviation (`advantage.py:85-86`) — which is precisely what RLOO's baseline does not do, and which the RLOO PR body documents as required.

`--advantage_estimator reinforce_plus_plus` likewise received group- instead of batch-level normalisation. No warning, no error; the run starts and produces different gradients.

## Evidence

Executed on CPU against the real argument dataclasses of both backends and the real shared `swift/rl_core/advantage.py` (only the Megatron runtime bootstrap and the CUDA-only `transformer-engine` import are stubbed):

```
advantage_estimator    backend    scale_rewards  kl_in_reward
grpo                   HF         group          False
grpo                   Megatron   group          False
rloo                   HF         none           True
rloo                   Megatron   group          False        <-- divergence
reinforce_plus_plus    HF         batch          True
reinforce_plus_plus    Megatron   group          False        <-- divergence
```

With identical rewards, the two settings give different advantages for the same input:

```
HF  (rloo -> scale_rewards=none,  kl_in_reward=True ): rewards=[0.98, -0.02, 0.98, -0.02, 0.18, 0.88]
                                                       advantages=[1.0, -1.0, 1.0, -1.0, -0.7, 0.7]
MG  (rloo -> scale_rewards=group, kl_in_reward=False): rewards=[1.0, 0.0, 1.0, 0.0, 0.2, 0.9]
                                                       advantages=[1.414014, -1.414014, 1.414014, -1.414014, -1.413928, 1.413928]
```

After this change the same script prints, for the Megatron backend:

```
rloo                   Megatron   none           True
reinforce_plus_plus    Megatron   batch          True
```

## Sibling call-site regression matrix

Run against the pristine tree and this change; the differences are only the cases that should change:

| case | before | after | verdict |
| --- | --- | --- | --- |
| default grpo | `group / False` | `group / False` | unchanged |
| explicit `--scale_rewards none` / `batch` / `gdpo` | as given | as given | unchanged |
| `--loss_type real` | `none / False` | `none / False` | unchanged (REAL forcing still wins) |
| `--kl_in_reward true` (explicit) | `group / True` | `none / True` | now equals HF |
| `--kl_in_reward false` (explicit) | `group / False` | `none / False` | now equals HF |
| `--loss_type real --advantage_estimator rloo` | `none / False` | `none / True` | now equals HF |
| `--advantage_estimator rloo` (defaults only) | `group / False` | `none / True` | **fixed** |
| `--advantage_estimator reinforce_plus_plus` | `group / False` | `batch / True` | **fixed** |

An explicitly supplied value is never overwritten (the `is None` guards), and the only consumers of the two fields are the Megatron GRPO trainers, so non-GRPO `rlhf_type`s — which never enter `_init_grpo` — are unaffected.

## History

The tie-in landed on the transformers side with the RLOO PR #6325 and the REINFORCE++ PR #6385. The Megatron GRPO support PR #6826 added the two fields with hardcoded GRPO defaults and never copied the resolution; `grep -rn 'kl_in_reward' swift/megatron/` returns only the field, the three trainer reads, and now this resolution. The block added here is a literal mirror of `RLHFArguments._init_grpo`.
