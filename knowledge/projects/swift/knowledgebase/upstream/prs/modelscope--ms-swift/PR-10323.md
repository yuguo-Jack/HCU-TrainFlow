# fix(dpo): keep EXO smoothing local to its loss

# PR information

With `loss_type=['sigmoid', 'exo_pair']`, matching `loss_weights`, and the default `label_smoothing=0`, EXO changes the trainer's smoothing to `1e-3`. This also changes sigmoid's objective: reordering the same weighted loss components, repeating a batch, or evaluating before the first training batch produces different losses and policy gradients.

Keep EXO's positive smoothing fallback local to the EXO calculation. Standalone EXO retains its existing formula for both default and explicit smoothing. Add regression tests through the actual `get_batch_loss_metrics` and model-forward paths, plus a binary reverse-KL reference for EXO values and gradients.

This issue was found through AI-assisted source review and reproduced with randomly initialized tiny GPT-2 models on CPU; it was not observed in a production training run.

## Experiment results

- New regression tests on unchanged upstream: 3 failed, 2 passed. After the fix: all 5 passed.
- New tests plus `tests/utils/test_dpo_precompute.py`: 8 passed, 2 subtests passed.
- In the mixed-loss reproduction, changing component order before the fix changes loss by `4.0031e-5` and the largest policy-gradient element by `3.4730e-4`. After the fix, reordered and repeated calls have exactly equal losses and gradients.
- `tests/test_align/test_rlhf_loss.py`: both upstream and patched source report 11 passed / 31 subtests passed and the same 2 failures; `_PaddingFreeDPOStub.args` is missing `tuner_backend` before the tested loss path is reached.
- Pinned repository `pre-commit` hooks passed for both changed files; `git diff --check` passed.

Validation used CPU FP64, Python 3.13, PyTorch 2.14.0, Transformers 5.17.0 and TRL 0.29.1. No full training benchmark or GPU run was performed.
