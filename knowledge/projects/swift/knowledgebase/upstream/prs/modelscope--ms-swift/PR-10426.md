# fix(grpo): preserve SP state during async server rollout

# PR information

Related issue: none.

HF GRPO can hang when asynchronous server rollout temporarily disables sequence parallelism in the training process. This change keeps remote requests from modifying the training process's SP state, while preserving overlap between generation and training.

## Trigger

The affected configuration is:

| Setting | Value |
| --- | --- |
| Inference backend | `use_vllm=True`, `vllm_mode=server` |
| Generation scheduling | `async_generate=True` |
| Training sequence parallelism | `sequence_parallel_size > 1` |
| Timing | A background server request overlaps with a training or scoring forward |

This overlap is part of the existing asynchronous execution path. In [`_fast_infer()`](https://github.com/modelscope/ms-swift/blob/484e836d691a52fd8c1723137ee3d64c6e066683/swift/rlhf_trainers/rollout_mixin.py#L1187-L1234), the trainer waits for the previous rollout, retrieves its cached results, and submits the next rollout before continuing to process those previous results. The earlier `_wait_queue()` therefore does not prevent the newly submitted request from overlapping with model computation.

Whether a run hits the failure depends on when the request and model computation overlap. It does not require an invalid input or a multi-turn scheduler.

## Cause of the hang

[`async_generate_rollout()`](https://github.com/modelscope/ms-swift/blob/484e836d691a52fd8c1723137ee3d64c6e066683/swift/rlhf_trainers/rollout_mixin.py#L1642-L1669) submits the following path to a background thread:

```text
_infer_single_or_multi_turn()
  -> _rollout()
  -> _server_rollout()
  -> _engine_infer()
  -> vllm_client.infer()
```

Before this change, `_engine_infer()` enters `_disable_sp_context()` before selecting the server or local inference branch. That context saves the current state, sets `sequence_parallel.world_size = 1`, and replaces `sequence_parallel.extra_kwargs` with an empty dictionary for the duration of inference.

The `sequence_parallel` object is a process-global singleton. Its attributes are shared by the background rollout thread and the training thread. The remote request therefore changes the attention dispatch seen by concurrent training.

Only the main rank calls `_engine_infer()` in [the server path](https://github.com/modelscope/ms-swift/blob/484e836d691a52fd8c1723137ee3d64c6e066683/swift/rlhf_trainers/rollout_mixin.py#L1275-L1297). For a two-rank SP group, an overlapping forward can consequently take these different branches:

| | Rank 0 | Rank 1 |
| --- | --- | --- |
| SP size observed during the request | 1 | 2 |
| Attention dispatch | Local attention | Sequence-parallel attention |
| Collective participation | Skips the SP all-to-all operations | Enters all-to-all and waits for rank 0 |

[`DistributedAttention.forward()`](https://github.com/modelscope/ms-swift/blob/484e836d691a52fd8c1723137ee3d64c6e066683/swift/sequence_parallel/ulysses.py#L111-L122) explicitly returns the local attention result when `world_size == 1`. The other rank still enters the collective path, so the distributed computation cannot complete and eventually reaches a communication timeout.

Restoring `world_size` when the HTTP request finishes cannot undo a forward that already took the wrong branch.

## The same context can overwrite newer batch metadata

The context also saves a copy of `extra_kwargs` and restores it in `finally`. While the request is pending, the training thread can write the current batch's `input_ids` or position metadata through `sequence_parallel.prepare_inputs()`. When the background context exits, it replaces those values with the snapshot taken before the request.

The sequence is:

1. The background request saves the old batch's SP metadata and clears it.
2. The main thread prepares a new batch and writes its metadata.
3. The request finishes and restores the old snapshot, discarding the new metadata.

This is another consequence of the same shared-state race. Keeping SP changes out of remote inference addresses both the attention-dispatch mismatch and the stale-state restoration.

## Change

Move `_disable_sp_context()` from the outer inference context into the existing local `self.engine.infer()` branch.

- **Server inference:** serialize the requests and call `vllm_client.infer()` without changing local SP state. The model inference runs in the external server.
- **Local inference:** retain the existing SP disable/restore context around `self.engine.infer()`, including restoration when inference raises.
- **Asynchronous scheduling:** keep the background request and training overlap. No lock or additional wait is introduced.
- **Profiling and response handling:** retain the existing profiling context and output conversion.

The change is limited to `swift/rlhf_trainers/rollout_mixin.py`: **3 insertions and 2 deletions**. It reuses the existing backend branch and adds no configuration option or dependency.
