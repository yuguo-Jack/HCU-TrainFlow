# PR information

Fixes #10405. The other half of that issue, the chunked-loss rescaling, was fixed independently in #10397.

`compute_advantages_dynamic` is the advantage path used when the number of completions per prompt varies (multi-turn, `dynamic_num_samples`). It has no `'gdpo'` branch: with `scale_rewards='gdpo'` it reaches `prompt_stds = None`, so gdpo silently behaves like `'none'`:
- the per-reward-function normalization is skipped;
- the weighted reward sum is only mean-centered within each prompt;
- the final batch normalization is also skipped.

The fixed-group path, `compute_advantages`, implements gdpo. This PR adds the same computation to the dynamic path, on the request-deduplicated rows:
1. normalize each reward function within its prompt group, NaN-aware (`nanmean` / `nanstd`, NaN results → 0);
2. sum with `reward_weights`;
3. normalize the sum over the batch.

The result is then mapped back to the original rows like the other modes.

## Experiment results

New `tests/train/test_grpo_dynamic_advantages.py`:
- `test_dynamic_gdpo_matches_fixed_group_gdpo`: with equal group sizes and no repeated requests (one NaN reward), the dynamic path equals `compute_advantages(..., scale_rewards='gdpo')`. This fails on `main` and passes with this change.
- `test_dynamic_gdpo_maps_repeated_requests_back`: a repeated `request_id` (a multi-turn request with two rows) gets the same advantage as its first row and does not change the others.

Local environment note: importing `swift` fails here because of an unrelated pyarrow/NumPy version conflict. I therefore ran both tests by loading `swift/rl_core/advantage.py` directly, with `swift.utils.nanstd` reimplemented as in `swift/utils/torch_utils.py`: both pass with this change, and the first fails on `main`. I have not run a GPU training job.
