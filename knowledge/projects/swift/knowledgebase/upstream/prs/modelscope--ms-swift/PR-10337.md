# PR information

Fixes #10357

`swift` imports `selective_log_softmax` from `trl.trainer.utils`. TRL's version loops over the leading dimension of `logits` "to reduce peak mem consumption". That is fine when the leading dimension is a batch dimension, but under `padding_free`/packing swift flattens the logits to `[total_nnz, vocab_size]` (`grpo_trainer.py:1591`), so the loop degenerates to one iteration per token — thousands of small `log_softmax` + `gather` launches per call instead of a few dozen.

This adds a chunked implementation in `swift/rlhf_trainers/utils.py`: the flattened rows are processed `chunk_size` at a time. Peak memory is still bounded by the chunk size, which was the point of the original loop, but the work gets batched again. The three call sites in `grpo_trainer.py` (sequence-parallel / padding_free / default) and the two in `rlhf_mixin.py` (DPO/CPO/KTO/ORPO) switch to it.

**Correctness**, checked against the naive `gather(logits.log_softmax(-1), ...)`:
- bf16/fp16 are bit-for-bit identical (`torch.equal`) across 2-D and 3-D shapes, `chunk_size` 1/3/1024/10^6, top-K indices, `temperature`, `row_mask`, and gradients. bf16 is what training actually uses.
- fp32/fp64 keep TRL's `x - logsumexp(x)` form, so results can differ in the last bit; asserted within `rtol=atol=1e-6`.

`chunk_size=1024` is close to optimal (2.6 ms vs 2.4 ms at 16384 on the 8192x152064 case), so the default is left alone.

## Experiment results

Measured on an H200 (torch 2.9.1+cu130, bf16), output asserted bit-identical in every case:

| rows | vocab | TRL loop | chunked | speedup |
|---|---|---|---|---|
| 1024 | 32768 | 22.9 ms | 0.1 ms | 328x |
| 4096 | 32768 | 89.7 ms | 0.3 ms | 345x |
| 8192 | 32768 | 129.6 ms | 0.5 ms | 238x |
| 2048 | 152064 | 64.0 ms | 0.7 ms | 95x |
| 8192 | 152064 | 255.9 ms | 2.6 ms | 97x |

The win is almost entirely launch overhead, which is why it is far larger on GPU than the ~5x measured on CPU.

Tests: `tests/general/test_selective_log_softmax.py`, 7 cases, no GPU or model needed.

- rrrxxx0510 · comment · 2026-10-17T13:36:35Z · [source](https://github.com/modelscope/ms-swift/pull/10337#issuecomment-6234525521)

Thanks for the catch on the top-k regression — that was a real one, and you are right that backward compatibility matters here.

The bug was in the `float32`/`float64` branch: I reshaped the per-row `logsumexp` values to the shape of the gathered result, which only holds when `K == 1`. For `index` of shape `(..., K)` (the top-k case) the element counts do not match and it fails outright. It now broadcasts with `unsqueeze(-1)`, as the original implementation does.

My tests only covered top-k under bf16, which takes the other branch — that is why I missed it. I extended `test_topk_index` to cover both precision branches with `K` in {1, 4}, checking the shape and (for fp32) the values within 1e-6. I also confirmed the test actually catches this: reverting just that line makes it fail on `float32, k=4` specifically.

Everything is squashed into a single commit now, so it is one clean diff to review.
