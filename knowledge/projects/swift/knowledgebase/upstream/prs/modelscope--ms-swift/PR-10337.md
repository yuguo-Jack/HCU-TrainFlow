# perf(rlhf): chunk selective_log_softmax instead of looping per token

[Upstream PR](https://github.com/modelscope/ms-swift/pull/10337) · state: open · merged: False

## Original PR description

`selective_log_softmax` currently comes from `trl.trainer.utils`. TRL's version loops over the leading dimension of `logits`, with a comment saying this is to reduce peak memory. That's fine when the leading dimension is a batch dimension, but under `padding_free`/packing swift flattens the logits to `[total_nnz, vocab_size]` (`grpo_trainer.py:1591`) — so the loop becomes one iteration per token, thousands of small `log_softmax` + `gather` launches per call instead of a few dozen.

This adds a chunked version in `swift/rlhf_trainers/utils.py`: the flattened rows are processed `chunk_size` at a time. Peak memory is still bounded by the chunk size, which was the point of the original loop, but the work gets batched again. The three call sites in `grpo_trainer.py` (sequence-parallel / padding_free / default) and the two in `rlhf_mixin.py` (DPO/CPO/KTO/ORPO) switch to it.

**Correctness**, checked against the naive `gather(logits.log_softmax(-1), ...)`:
- bf16/fp16 are bit-for-bit identical (`torch.equal`) across 2-D and 3-D shapes, `chunk_size` 1/3/1024/10^6, top-K indices, `temperature`, `row_mask`, and gradients. bf16 is what training actually uses.
- fp32/fp64 keep TRL's `x - logsumexp(x)` form, so results can differ in the last bit; asserted within `rtol=atol=1e-6`.

**Measured** on CPU (torch 2.8.0, 8 threads, bf16) — output asserted identical in every row:

| rows | vocab | TRL loop | chunked | speedup |
|---|---|---|---|---|
| 1024 | 32768 | 39.4 ms | 8.1 ms | 4.9x |
| 4096 | 32768 | 160.5 ms | 32.2 ms | 5.0x |
| 8192 | 32768 | 320.3 ms | 64.2 ms | 5.0x |
| 2048 | 152064 | 343.2 ms | 63.0 ms | 5.4x |

The gain comes from collapsing thousands of small kernel launches into a few chunked ones, so it isn't CPU-specific. GPU numbers to follow.

**One tradeoff**: recent TRL has a fused-kernel fast path (`_fused_logprob_entropy`) that only activates when the optional `trl-loss` package is installed, and this change bypasses it. swift pins `trl>=0.15,<1.0` and that path is recent, so most installs hit the loop today. If you'd rather keep it, I can make the local version delegate to TRL whenever the fused kernel is available.

Tests: `tests/general/test_selective_log_softmax.py`, 7 cases, no model or GPU needed.

GPU numbers are in — measured on an H200 (torch 2.9.1+cu130, bf16), output asserted bit-identical in every case:

| rows | vocab | TRL loop | chunked | speedup |
|---|---|---|---|---|
| 1024 | 32768 | 22.9 ms | 0.1 ms | 328x |
| 4096 | 32768 | 89.7 ms | 0.3 ms | 345x |
| 8192 | 32768 | 129.6 ms | 0.5 ms | 238x |
| 2048 | 152064 | 64.0 ms | 0.7 ms | 95x |
| 8192 | 152064 | 255.9 ms | 2.6 ms | 97x |

`rows=8192` is roughly 8 sequences x 1024 completion tokens, and this runs 2-3 times per training step (policy / old / ref). The win is almost entirely launch overhead, which is why it is much larger on GPU than the ~5x I measured on CPU.

I also swept `chunk_size` at rows=8192 / vocab=152064: 256 -> 2.9 ms, 1024 (the default) -> 2.6 ms, 16384 -> 2.4 ms. Left the default alone since it is already in the flat region.

Everything else in the description is unchanged: bf16/fp16 stay bit-for-bit identical, fp32/fp64 keep TRL's `x - logsumexp(x)` form.
