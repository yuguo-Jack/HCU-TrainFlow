# PR information

Related issue: none.

This reduces avoidable work in the vLLM rollout path: intermediate response construction, inference requests for empty server partitions, repeated adapter discovery, repeated prompt encoding within an async batch, and client-side JSON parsing.

I keep the changes in three production files:

- **Return final outputs for non-streaming generation.** Swift consumes intermediate async outputs and discards them, while the synchronous path retains only finished outputs. I extend the existing `FINAL_ONLY` condition to non-streaming requests, including the `n == 1` requests used by async GRPO. The existing streaming behavior, `n > 1` handling, and compatibility guard remain in place.
- **Skip empty HTTP partitions.** The client currently posts empty partitions to independent rollout servers. The server replaces an empty partition with a placeholder prompt, generates a response using the supplied generation limit, and discards it. I return immediately for empty input and submit HTTP requests only for populated partitions. Result ordering and error propagation are preserved. This does not skip workers or collective participation inside a distributed engine.
- **Resolve the rollout adapter once per async batch.** Each request currently queries `list_loras()`, which enters vLLM's utility RPC path. I resolve the adapter before scheduling the batch and mark it resolved for those requests, including when no adapter is loaded. The next batch queries again, so adapter loading and removal remain visible. Explicit adapter requests and direct `infer_async()` calls retain their behavior.
- **Encode repeated text prompts once per async GRPO batch.** Requests of the same protocol type with matching encoding inputs share an in-flight encoding future. The grouping uses the same dataclass conversion as `Template.encode`, preserving field order and encoding options. UUID and `data_dict` are passthrough metadata for the standard template: they are excluded from the grouping key and restored independently for each request, with the original dataclass normalization. Only duplicate requests need entries in the shared-encoding map. Each receives its own deep copy of the encoded inputs before hooks and generation; all generation requests and sampling settings are retained. The cache belongs only to the current batch. This targets ordinary text requests using the standard Swift template and loss scaling with deterministic fast tokenization; multimodal/tool requests, custom templates, Jinja rendering, and tokenizer dropout retain independent encoding. Synchronous inference is unchanged. A canceled waiter does not cancel its siblings' encoding, and generation can begin while other prompts are still being encoded.
- **Parse rollout JSON directly into the protocol models.** A reused Pydantic `TypeAdapter` validates response bytes into `List[RolloutOutput]`, avoiding the initial `response.json()` object tree on the normal path. If that validation fails, I retain the existing per-item parser for older servers returning chat responses directly, including mixed response lists.

These are localized changes to output handling, request dispatch, and repeated CPU encoding. They preserve the response fields used by training, including exact token IDs, logprobs, completion text, finish reasons, and router metadata.

## Experiment results

Local checks exercised the source methods and the actual edited HTTP client:

- Empty partitions no longer make HTTP calls. A separate check of the server method confirmed that those calls previously dispatched placeholder generation and discarded its output.
- Async LoRA discovery runs once per nonempty batch, whether the adapter is loaded or absent. Checks also cover explicit adapters, synchronous/asynchronous `list_loras()` implementations, loading/removal between batches, direct single-request calls, and RPC errors.
- Direct JSON validation produces the same protocol data for standard and compact logprobs, Unicode text, token IDs, prompt metadata, and NumPy router metadata. The synthetic long-response parsing workload was faster with direct validation. Legacy and mixed response lists still use the fallback.
- The final-only output check preserves the final payload across length, stop, and abort termination, while eliminating intermediate response construction.
- With the real local Qwen3 template and tokenizer, 32 prompts repeated eight times require 32 encoding calls instead of 256 in the async path. The substitute generation backend still receives 256 requests with matching inputs, order, UUIDs, seeds, and hook effects. The CPU dispatch workload, including input grouping and copying, was faster after the change. These checks also cover cancellation, overlapping batches, batch-local cache lifetime, metadata normalization and isolation, requests with slots fields, async truncation/options, and unchanged synchronous behavior. Valid tool calls without a `content` field retain their original path, and local passthrough metadata need not be pickleable.
