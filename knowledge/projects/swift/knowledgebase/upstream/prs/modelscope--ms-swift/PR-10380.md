# PR information

Fixes #10379

`_get_inputs_embeds_hf`（`swift/template/base.py:2450`）处理一个没有任何图像的 batch 时，会造一张 32×32 的黑图、过一遍图像处理器、再跑一整遍视觉塔，最后 `inputs_embeds + image_embeds.mean() * 0.` —— 也就是加零。这么做的唯一目的是把视觉塔留在 autograd 图里。

视觉塔冻结时（`freeze_vit=True`，**默认值**）没有图需要留，而且 `patch_frozen_module`（#10214）已经负责把冻结的塔排除在计算图之外。于是图像处理器那次调用和整遍视觉塔前向都是白跑的，每个无图像的 batch 都要付一次。

改动是加一句判断：只有「在算梯度且视觉塔里有参数需要梯度」时才走原来的路径，否则直接返回。视觉塔需要训练时（`freeze_vit=False`）行为完全不变。

## Experiment results

`Qwen2.5-VL-3B-Instruct`，12 条纯文本样本，batch size 2，6 步，H200。base 与改动后**交替跑、各两轮**（共享卡上单次对比不可信）：

| | 第 1 轮 | 第 2 轮 | 平均 |
|---|---|---|---|
| 改动前 | 14.37 s | 15.16 s | 14.77 s |
| 改动后 | 12.53 s | 11.99 s | **12.26 s** |

无图像的 batch **快约 17%**。四轮 `train_loss` 完全一致（0.2094），每步 `token_acc` 序列也一致（0.8846 → 0.9399 → 1.0），说明省掉的确实不参与计算。

50/50 图文混合、batch size 2 时端到端收益约 4%——因为只有「整批都没有图像」才走这条路径，收益随无图像 batch 的占比线性变化。

峰值显存不变（7.38 GiB）。

- ErenAta16 · COMMENTED · 2026-10-19T13:30:54Z · [source](https://github.com/modelscope/ms-swift/pull/10380#pullrequestreview-5572286420)

Blocking until there is evidence: as written this removes the dummy vision forward in the case it was added for.

The description says the dummy image "only exists so that the vision tower stays in the autograd graph". That is not what the maintainers recorded when the code was added. In #5938, hjh0119 answers: "Add a dummy image to prevent deepspeed zero3 from hanging when training on a mixed multimodal/text dataset." #9639 spells out the mechanism for another template: under ZeRO the parameters are sharded and only all-gathered when a computation touches them, so a rank that skips the vision tower while another rank runs it leaves the second rank waiting inside an all-gather.

With this change that situation comes back in two ways:
1. A frozen tower (the default `freeze_vit=True`) under ZeRO-3. The new condition needs a vision parameter with `requires_grad`, so a frozen tower skips the forward on text-only batches. ZeRO-3 shards frozen parameters too (LoRA with ZeRO-3 is the usual example), so a rank that does run the tower for an image batch waits for the rank that skipped it. #10214 keeps the tower out of the autograd graph, but it does not change which ranks take part in the all-gather.
2. Evaluation and generation. `torch.is_grad_enabled()` is False under `no_grad`, so on a text-only batch the early return is taken even when the tower is trainable, while a rank with images still runs the tower.

I could not reproduce either. I only have one small GPU, and the measurements in the description are from a single H200, where there is no other rank to wait for. So this is a request for evidence, not a proven regression: a 2-GPU ZeRO-3 run with `freeze_vit=True` where one rank receives a text-only batch and the other one with images, before and after the change, and the same through the evaluation loop.

If it does hang, this file already has an idiom for "parameters are sharded": `get_default_device_map` in `swift/model/utils.py` checks `is_deepspeed_zero3_enabled() or os.environ.get('ACCELERATE_USE_FSDP', 'False').lower() == 'true'`. Keeping the dummy forward whenever that holds, and skipping only otherwise, would keep the single-GPU and DDP speed-up and leave the sharded cases as they are:

```python
sharded = is_deepspeed_zero3_enabled() or os.environ.get('ACCELERATE_USE_FSDP', 'False').lower() == 'true'
if not sharded and not (torch.is_grad_enabled() and any(p.requires_grad for p in visual.parameters())):
    return inputs_embeds
```

(`is_deepspeed_zero3_enabled` is already imported in `base.py`.)

Optional: #9104 describes a hang of the same family for a trainable tower under ZeRO-2 (a different template); the grad clause in your condition already keeps the dummy for training there. The helper is also shared by the glm, llava and qwen templates, so if the change stays in the shared function, the evidence should cover at least one template of each.
