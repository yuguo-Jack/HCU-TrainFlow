# PR information

Related issue: none.

Ray Megatron weight synchronization can fail with `pidfd_getfd: Operation not permitted` when `expandable_segments:True` is enabled in a restricted container. [PyTorch's CUDA allocator](https://github.com/pytorch/pytorch/blob/v2.13.0/c10/cuda/CUDACachingAllocator.cpp) uses that syscall to import expandable allocations into another process.

Allocate the IPC transfer buffers with expandable segments temporarily disabled. Restore the allocator's configuration and effective expandable flag immediately after allocation, including on failure. Apply the same scope to the adapter's persistent buffer and to the sender used by standalone rollout actors after NCCL receive. Weight export and transfer run after restoration, and the existing buffer reuse, shared-memory path and secondary-rank behavior are preserved.

This lets training keep its expandable allocator for fragmentation control instead of disabling it globally. No new configuration is introduced. The helper uses PyTorch allocator internals, with a fallback for the older setter API; other accelerator and allocator backends bypass it. The setting is process-wide, and the scope encloses only buffer allocation.

AI assistance (Codex) was used to prepare the implementation, tests and reproducer.

## Experiment results

Experiment base: `modelscope/ms-swift@eed35f1a67ec9e72eeb93a9ac442cf89a4447daf`. The branch is rebased onto `d907e329cf27391cd21ae19a7cb0b3c07dc46173`; the affected modules are unchanged between these bases.

- `python -m pytest tests/megatron/test_ray_cuda_ipc.py -q`: **27 passed**, locally and in the GPU runtime. The unchanged implementation fails 8 of 19 behavior cases; 11 pass. Eight tests of the new helper's older-setter fallback are excluded from that baseline comparison. Coverage includes allocator restoration after allocation/export failures, buffer reuse, SHM and secondary-rank bypasses, other backends, and omitted flags or trailing separators in the last configuration string.
- `pre-commit run --all-files`: **all hooks passed**.
- A real two-process CUDA IPC reproducer fails on the unchanged sender with `pidfd_getfd: Operation not permitted`. The candidate imports every byte correctly through ordinary storage and restores the complete allocator settings for normal, empty and trailing configuration strings.
- Native `VllmServer`/`RayVllmEngine` checks use a locally generated two-layer BF16 Llama: sender and rollout on one H200 for colocation, then on separate H200s through the native NCCL checkpoint engine and rollout-side IPC sender. Each route completes three full-weight / adapter-only cycles. Changed base weights and nonzero LoRA weights match HF/PEFT greedy-token controls and change generated outputs. The colocated persistent buffer is reused, allocator settings are restored, and all GPU resources are released. No CUDA or NCCL teardown errors were found in the final driver/worker logs.

GPU checks used PyTorch **2.13.0+cu130**, Ray **2.59.0** and vLLM **0.32.0**. These are single-host TP=1 transport/loading checks, not Megatron optimizer or full-GRPO training runs. The exact candidate modules are loaded from an isolated directory without modifying installed Swift.

No isolated throughput or full-GRPO peak-memory reduction is claimed. The change preserves the configured training allocator while making its IPC buffers importable.
