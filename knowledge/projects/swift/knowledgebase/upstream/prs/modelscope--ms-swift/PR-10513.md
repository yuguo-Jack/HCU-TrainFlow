# PR information

Related issue: N/A

Ascend NPU training became slower after upgrading from ms-swift 4.5.3 / Megatron Core 0.16 / MindSpeed to main / Megatron Core 0.18 / MegatronAdaptor + TransformerEngineNPU. This PR reduces gradient-processing and non-fused MoE permutation overhead while preserving the existing training configuration, including `moe_permute_fusion=false`.

The changes are limited to two areas:

- **Gradient norm and scale/clip:** keep finiteness reductions and tensor scale factors on the device, avoiding per-parameter Python scalar reads. Eligible in-place scaling uses a batched kernel, with a fallback for other layouts and overlapping views.
- **Non-fused MoE permutation:** cast the boolean routing mask to FP32 before stable `argsort`, avoiding the slow NPU boolean-sort fallback. The mask contains only 0/1, which FP32 represents exactly. Token order, probability dtype, and the fixed output shape are preserved. CPU/CUDA, fused, padded, and aligned cases delegate to the original function.

Both patches install after MegatronAdaptor and update cached MCore references, with API signature checks and idempotent installation. Weighted SwiGLU, unpermutation, garbage collection, LoRA coverage, and training flags retain their existing behavior. The MoE implementation is 41 lines, including installation and fallback handling. This PR changes code and tests only.

## Experiment results

### Qwen3-Omni: unchanged non-fused configuration

Full-parameter language-model training on 16 Ascend A3 NPU devices: Qwen3-Omni-30B-A3B-Instruct, BF16, TP=1, EP=8, PP=2, global batch=8, micro batch=1, packing/max length=1024, full recomputation, frozen vision/aligner, and `moe_permute_fusion=false`. Runs share the same fixed mixed text/image dataset and seed/data_seed=42. GC remains unchanged; no profiler, evaluation, or checkpoint saving is enabled.

Each configuration runs for 100 steps. Steps 1–20 are warmup; each measured step synchronizes NPU execution at its boundaries, and its reported duration is the maximum across ranks.

| Configuration in the upgraded stack | Mean, steps 21–100 | Median |
|---|---:|---:|
| Gradient patch only | 1.6784 s/step | 1.6491 s/step |
| Gradient + FP32 permutation patch | 0.9951 s/step | 0.9692 s/step |

Adding the permutation optimization reduces mean step duration by **40.7%** with the fusion flag kept false. Parameter name/shape signatures and the first four microbatch input hashes match on all 16 ranks; all loss/grad_norm values are finite. Call counts verify that the non-fused optimization branch is exercised.

Earlier 100-step reference runs under the same full-parameter configuration measured **1.0164 s/step** for the old stack and **1.7832 s/step** for the upgraded stack with original gradient functions. These references and the ablation above are separate rounds: they show recovery toward the old-stack performance, rather than establishing a precise paired cross-version improvement percentage or confidence interval.

An initial permutation-only ablation attempt overlapped another user's training and was excluded. The accepted replacement was monitored for foreign NPU processes throughout execution.

### Qwen3.5: gradient-path benefit

A separate 8-NPU Qwen3.5-35B-A3B LoRA comparison uses BF16, `USE_MCORE_GDN=0`, TP=1, EP=8, global batch=32, micro batch=2, max length=1024, and rank=8/alpha=32 with all 330 `all-linear` LoRA modules in both groups. The fixed dataset contains 1,500 Chinese Alpaca examples, with seed/data_seed=42. Each group runs 40 steps, measuring the last 20 with the same synchronized maximum-rank method.

Original TENPU gradient functions average **3.8901 s/step**, versus **3.1479 s/step** with the gradient patch: **19.1%** less time. A repeat after sharing the gradient helpers measures **3.1992 s/step**. Parameter/input signatures match and loss/grad_norm remain finite. This configuration has `moe_permute_fusion=true`, so the FP32 sorting optimization is bypassed and the existing fused permutation path is retained.

Environment: torch 2.10.0, torch_npu 2.10.0.post7, CANN 9.2, Megatron Core 0.18.2.

### Why FP32 sorting is retained

An 8-NPU Omni LoRA check keeps `fusion=false` and compares a backport of the old `masked_select` algorithm against FP32 sorting. Each runs 20 steps, measuring the last 10:

| Implementation | Mean duration | Median |
|---|---:|---:|
| Old `masked_select` algorithm, adapted to the current API | 2.1674 s/step | 2.1157 s/step |
| FP32 stable sorting | 2.1840 s/step | 2.1135 s/step |

The difference is small and the mean/median directions differ; this short test does not show a clear performance winner. FP32 sorting is the smaller algorithmic change to current MCore and retains fixed-shape output. The observed 20-step Loss MAE between these implementations is **0.00078236**, with a maximum absolute difference of **0.00164604**. Operator checks compare exact output, index, and gradient values; these short checks do not establish long-term convergence equivalence.

Weighted SwiGLU is omitted: its additional mean-duration benefit on top of the gradient/permutation patches shrank from **2.69%** to **0.45%** in a reverse-order repeat. No GC policy changes or training-flag changes are included.

Copying before scaling can overflow mixed-dtype outputs: an FP32 source containing `65536`, an FP16 destination, and scale `0.5` produce `inf` instead of `32768`. The direct copy also rejects partially overlapping source/destination views. Copy a scaled temporary into `dst` instead, and add regression cases for mixed dtypes and partial overlap.
