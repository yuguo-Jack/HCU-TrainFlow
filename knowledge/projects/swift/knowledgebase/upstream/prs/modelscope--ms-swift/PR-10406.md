# fix(trainer): checkpoint the NPU RNG state alongside CUDA and MUSA

[Upstream PR](https://github.com/modelscope/ms-swift/pull/10406) · state: closed · merged: True

## Original PR description

## Summary

`SwiftMixin._save_flash_checkpoint` overrides the checkpoint save path and rebuilds the RNG state
dict inline, but that copy only covers `cuda` and `musa`. Upstream
`transformers.Trainer._save_rng_state` also covers XLA, NPU, HPU and MLU, and
`transformers.trainer_utils.set_rng_state_for_device` restores whatever is present under the
`cuda` / `npu` / `musa` keys.

So on Ascend the checkpoint gets no `npu` entry, and `Trainer._load_rng_state` silently skips
restoring the NPU generator. A resumed run therefore continues on a different device random stream
than an uninterrupted one - the same class of problem that the `musa` entry in this override is
already there to avoid. Nothing is logged; only the training result drifts.

## Change

* extract the RNG-state assembly into `SwiftMixin._build_rng_states()` and add the `npu` branch
  (`torch.npu.random.get_rng_state_all()` when distributed, `get_rng_state()` otherwise - exactly
  the calls `set_rng_state_for_device("NPU", torch.npu, ...)` expects on the way back in);
* `_save_flash_checkpoint` now calls the helper, so behaviour is unchanged for CPU/CUDA/MUSA users;
* add `tests/general/test_npu_rng_state.py`: the `npu` entry is written for both the single-process
  and the distributed form, and the key is absent when `torch_npu` is not available.

## Verification

Real Ascend 910B (container `mslizhe` on host 169, torch 2.15.0.dev20260917+cpu,
torch_npu 2.15.0.dev20260917+gitec69335, `torch.npu.is_available() == True`). The patched
`_build_rng_states` was extracted from the pushed file with `ast` and executed next to the upstream
inline block, both on the same machine:

| | upstream keys | patched keys |
| --- | --- | --- |
| `NOT_DISTRIBUTED` | `['cpu', 'numpy', 'python']` | `['cpu', 'npu', 'numpy', 'python']` |
| `DISTRIBUTED` | `['cpu', 'numpy', 'python']` | `['cpu', 'npu', 'numpy', 'python']` |

Round trip through the restore path transformers uses
(`torch.npu.random.set_rng_state_all(checkpoint['npu'])` after advancing the stream): the restored
draw is bit-identical to the uninterrupted run (`torch.equal(...) == True`), and the saved
`npu` entry holds one per-device state on this single-NPU box.

Local: `yapf -d --style setup.cfg`, `flake8` and `isort --check-only` are clean on both files
(ms-swift's pre-commit set). The new test needs the repo's runtime dependencies (it imports
`swift.trainers.mixin`), so it was not executed in a bare CPU venv - the logic was verified on the
NPU machine as described above.

Not tested: an actual interrupted-and-resumed training run, and the HPU/MLU/XLA paths, which this
change does not touch.
