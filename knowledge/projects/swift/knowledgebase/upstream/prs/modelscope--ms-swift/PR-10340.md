# PR information

Fixes #10336

Concurrent checkpoint updates share `last-checkpoint.tmp`, allowing one caller to publish another caller's target or delete its staging link during failure cleanup. Give each update a UUID-based staging path and clean it up only after that caller successfully creates the symlink, while preserving atomic `os.replace` publication and relative link targets.

Document the existing publication-order semantics: the last successful replacement wins, regardless of checkpoint step or save start order.

## Experiment results

- One focused regression test completes a second update while the first updater's staging link is pending, using nested calls to the real helper and real filesystem operations. The overlapping-success case fails against the original implementation and passes with this fix.
- Two subtests cover successful overlapping publication and an injected outer replacement failure, checking the published targets and absence of leftover staging links.
- `python -m pytest tests/utils/test_io_utils.py -q`: **7 passed, 2 subtests passed** (Python 3.12).
- `python -m pre_commit run --files swift/utils/io_utils.py tests/utils/test_io_utils.py`: **passed**.
- `git diff --check`: **passed**.
- Full trainer integration and multi-process checkpoint-saving tests were not run. The regression controls the operation interleaving without threads.
