# PR information

Refs #10483, refs #10312

With `dataset_num_proc > 1`, every `datasets.map` worker keeps one torch intra-op thread per CPU core, so N workers run N x cpu_count threads. Multimodal templates run the CPU ops of the image/video processors (`to(float)`, `sub_`, `div_`, `reshape` on the pixel tensors) inside these workers. With that many threads the cores are oversubscribed, and preprocessing gets slower than with a single process. The docs currently ask users to set `OMP_NUM_THREADS` by hand.

This PR:
- adds `swift.utils.limit_worker_num_threads(num_workers)`. It sets `cpu_count // num_workers` torch threads (affinity-aware), never raises the current value, and does nothing if `OMP_NUM_THREADS` is set explicitly;
- calls it in the `RowPreprocessor` map function when `num_proc > 1`, and in the `IterablePackingDataset` workers (`--streaming --packing`);
- updates the `dataset_num_proc` note in the en/zh docs.

Text-only templates are not affected (the tokenizer does not use torch threads). `num_proc=1` is unchanged.

Note: the map function is now wrapped when `num_proc > 1`, so the datasets fingerprint of these maps changes once. Caches written with `dataset_num_proc > 1` are rebuilt once.

## Experiment results

Environment: 20-CPU container, Python 3.12.3, torch 2.11.0, transformers 5.22.0, datasets 4.8.4. Length pre-pass (`AddLengthPreprocessor`, as run by `--lazy_tokenize false`, `--packing`, `--group_by_length` and `export --to_cached_dataset`). Mean +- std of 3 runs; main and PR runs interleaved.

Qwen3-VL-2B processor, 4000 llava-instruct-mix samples (~640x480 images, 388 tokens on average):

| dataset_num_proc | main | this PR |
|---|---|---|
| 4 | 132.6 +- 1.0 s | 16.8 +- 0.1 s |
| 8 | 133.3 +- 0.2 s | 18.4 +- 1.0 s |
| 16 | 133.9 +- 0.4 s | 26.1 +- 0.3 s |

- Qwen3.5-0.8B processor, num_proc=8: 139.3 +- 1.8 s -> 27.4 +- 0.1 s.
- Text (Qwen2.5-0.5B, alpaca-gpt4-data-en, num_proc=8): 15.06 s vs 15.04 s (unchanged).
- The encoded lengths are identical (md5 of the `lengths` column) in every configuration.
- `cpu_count // num_proc` threads vs 1 thread per worker: 17.6 vs 17.9 s (np=4), 17.7 vs 18.2 s (np=8).

The remaining scaling limit (np=16 slower than np=8) is the per-job dill pickling of the template, addressed in a follow-up PR.
