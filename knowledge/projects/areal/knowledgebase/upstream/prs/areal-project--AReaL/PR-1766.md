# Reduce temporary padding allocations when merging rollout batches

[Upstream PR](https://github.com/areal-project/AReaL/pull/1766) · state: closed · merged: True

## Original PR description

## Description

I noticed that merging uneven rollout batches creates a padded copy of each input, then copies those tensors again into the final batch. With many long responses, that adds a lot of temporary allocation and copying.

I changed larger merges to allocate the final output once and copy each input straight into it. Small groups keep the existing path, since direct copies were slower when grouping four responses locally. The new path starts at 16 inputs and applies to contiguous, gradient-free tensors with the same dtype and device. Other inputs keep the existing behavior, including dtype promotion and gradients.

## Additional Context

I benchmarked grouping and batch assembly with 256 prompts and four responses per prompt, matching the GSM8K example's batch size. These use synthetic response lengths and the fields emitted by `RLVRWorkflow`, with PyTorch 2.9.1 on CPU and eight threads. Timings are medians of three trials.

| Maximum response length | Before | After |
| --- | ---: | ---: |
| 2,048 tokens | 56.54 ms | 46.50 ms |
| 32,768 tokens | 355.83 ms | 210.17 ms |

For the 32K final merge, total tensor allocation fell from 1,341.38 MiB to 672.00 MiB. Peak tensor memory, excluding resident inputs, fell from 767.50 MiB to 672.00 MiB.

I added focused tests for padding, masks, ordering, higher dimensions, mixed dtypes, strided inputs, gradients, and allocation. The allocation test fails on the original code and passes with this change. All 251 selected tests passed, and 240 randomized comparisons matched the original helper exactly.
