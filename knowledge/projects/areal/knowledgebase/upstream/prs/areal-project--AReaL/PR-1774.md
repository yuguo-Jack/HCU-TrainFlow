# fix: stabilize Qwen Flash Next multimodal RL

[Upstream PR](https://github.com/areal-project/AReaL/pull/1774) · state: open · merged: False

## Original PR description

## Description

Follow up on #1750, #1751 and #1756 to make Qwen Flash Next multimodal RL reliable with Arena and colocated SGLang/Megatron execution.

- Preserve original prompt/generated token IDs, multimodal masks and image tensors through proxy exports and context recovery; correctly distinguish generated special IDs from real image placeholders.
- Preserve frozen PLE/vision state and validate sharded visual checkpoints; keep valid rollout groups through Arena transient retries and classify native context-budget/model failures consistently.
- Fix colocated pause handling and remove diagnostic-only batch replay, stable top-k, cache salt and verbose dumps from the production recipe. Retain NUMA placement and the existing model/runtime fixes.

## Related Issue

Follow-up to merged PRs #1750, #1751 and #1756. R3 support from #1496 will be handled separately.

This addresses a generic SGLang multimodal executor issue: StopIteration from a preprocessing thread cannot be propagated into an asyncio Future, so the request can remain pending and retain its reader lock. It is independent of SWE and Qwen.

Moved the implementation to `areal/engine/sglang_mm_executor.py` in [697da6f89](https://github.com/areal-project/AReaL/commit/697da6f89fe060e09ae2c1e10f5b707561841c45), with the reusable entry point `python -m areal.engine.sglang_mm_executor`. The recipe now invokes that command; the old example entry point forwards to it for compatibility. Application remains explicit and checksum-guarded for the validated executor revision, so other multimodal recipes can use it without patching unknown SGLang versions.

The executor tests cover successful calls, exception propagation, releasing the request lock, and processing the next request after an exhausted iterator.
