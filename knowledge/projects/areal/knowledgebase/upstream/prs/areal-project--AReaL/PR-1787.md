# fix(engine): route Megatron residency memory calls through the device platform abstraction

[Upstream PR](https://github.com/areal-project/AReaL/pull/1787) · state: closed · merged: True

## Original PR description

### What

The Megatron weight/optimizer residency adapter and the HF export path called
`torch.cuda.*` memory APIs directly instead of the repo's platform abstraction.
This PR replaces them with `current_platform.synchronize()` /
`current_platform.clear_memory()` — the same calls the rest of the engine layer
already uses (`areal/engine/megatron_engine.py`, `areal/engine/fsdp_engine.py`).

Fixes #1786.

### Why it matters

On a non-CUDA accelerator (Ascend NPU, using the existing `areal/infra/platforms/npu.py`)
the hardcoded calls do not work:

| call | on Ascend 910B4 |
| --- | --- |
| `torch.cuda.synchronize()` | raises `AssertionError: Torch not compiled with CUDA enabled` |
| `torch.cuda.empty_cache()` | returns quietly, does **not** release the NPU allocator cache |

so `release_memory()` / `resume_memory()` / `release_grad_memory()` /
`_offload_*()` abort whenever the Megatron backend is used on NPU, and the
reclamation calls in `MegatronEngine.save()` and `hf_save` never free device memory.

### Changed

* `areal/engine/megatron_utils/weight_residency.py` — 8 `torch.cuda.synchronize()` →
  `current_platform.synchronize()`; the two `synchronize()+gc.collect()+empty_cache()`
  trios → `current_platform.clear_memory()` (which is exactly that trio);
  the now-unused `gc` import is dropped.
* `areal/engine/megatron_engine.py` — `torch.cuda.empty_cache()` in `save()` →
  `current_platform.clear_memory()`.
* `areal/models/mcore/hf_save.py` — 2 × `torch.cuda.empty_cache()` (state-dict sharding
  and the pre-ep_pp-gather reclamation) → `current_platform.clear_memory()`.
* `tests/test_megatron_weight_residency_platform.py` — new regression test asserting
  `release_memory()`/`resume_memory()` go through the platform object.

Diff: 13 changed lines in production code, no signature or config change.

### Risk

Low on CUDA: `CudaPlatform.clear_memory()` is literally
`torch.cuda.synchronize(); gc.collect(); torch.cuda.empty_cache()`, i.e. the trio it
replaces, and `CudaPlatform`/`NPUPlatform` both already expose `synchronize()`.
No behaviour change for CUDA/ROCm users; the only functional difference is on
accelerators whose `torch.cuda` namespace is a stub.

### Verification (Ascend 910B4, real hardware)

Env: `torch 2.15.0.dev20260917+cpu`, `torch_npu 2.15.0.dev20260917+gitec69335`,
`Ascend910B4`, platform resolves to `NPUPlatform` (`current_platform.device_type == "npu"`).

Harness drives the real `areal/engine/megatron_utils/weight_residency.py` on the device
with a stub engine (so the offload bodies short-circuit) and fake MCore DDP buffers
(with a `megatron.core.distributed.DistributedDataParallel` shim, since the container
has no megatron-core install). Same harness, same file, only the module under test
swapped — md5 of the module before: `68c75f78fbb749f216d33725cbc8079e`.

### Not tested

* CUDA regression — no CUDA hardware here; the equivalence argument above is the
  substitute (`CudaPlatform.clear_memory` byte-for-byte the replaced trio).
* End-to-end `MegatronEngine.save()` / `hf_save` execution — those call sites need a
  real Megatron build, a checkpoint and multi-process launch; only the substituted
  call was checked (same call, same platform object) plus the residency methods above.
* Multi-card / distributed residency (`torchrun`), and the AWEX colocate paths, which
  are CUDA-IPC based and out of scope.
