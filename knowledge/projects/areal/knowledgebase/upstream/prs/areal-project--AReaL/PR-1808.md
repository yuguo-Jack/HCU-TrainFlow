# perf: bound R3 routing storage and transport memory

[Upstream PR](https://github.com/areal-project/AReaL/pull/1808) · state: open · merged: False

## Original PR description

## Description

R3 rollout trajectories currently retain dense padded expert IDs, and routing preparation and RPC transport can materialize additional full-size copies. This amplifies memory use when rollout and training share devices. Keep routing packed on CPU, distribute only each pipeline stage's layers, and bound transient transfer buffers before uploading local replay slabs.

- Store actual-token routes in lossless compact integer tensors; keep minibatch reorder/split as shared row views. Preserve legacy dense/cache-only interaction compatibility.
- Distribute only pipeline-specific routing layers through Gloo. Validate collective metadata consistently across ranks and release R3 fetch ownership promptly through the existing RTensor cache API.
- Strip unused routing from advantage/ref/teacher/critic payloads; prepare only local CP/SP token positions and PP/VPP layers for native Megatron replay.
- Add routing memory accounting, dense-layout equivalence tests, transport/lifetime regressions, and an isolated CPU memory probe.
- Apply the existing SGLang token-cache compatibility patch in the AWEX scheduler entry.

Based on `main` at `3b936798`; follows the merged R3 implementation in #1496. Preserves main's unified AWEX adapters, CPU-staged optimizer implementation, and composable advantage pipeline. No workflow, dependency, or public config-schema changes.

## Memory scope and risk areas

An isolated fresh-process actor routing-preparation probe (24 sequences, 92,160 actual tokens, max length 8192, 48 layers, top-10, PP4) measured incremental peak RSS of 1,314,963,456 bytes for dense concat plus reorder copies versus 50,237,440 bytes for packed stage-local input. This earlier probe measured routing preparation after PP distribution, excludes model weights and initial source transfer, and does not imply a 96% reduction in total job memory.

The main review areas are collective ordering/validation, CP/SP padding and permutation equivalence, and R3 tensor lifetime during RPC dispatch. Generic RTensor fetch behavior and the HTTP data endpoints are unchanged from the base branch. A prior revision (`5e243288`) completed 22 training steps of the 64-GPU long-context Flash-Next experiment before it was stopped by user request. That distributed run predates this scope reduction; the revised head has CPU regression coverage only, and multi-node/GPU training has not been repeated.

- yulangz · comment · 2026-10-26T06:41:22Z · [source](https://github.com/areal-project/AReaL/pull/1808#discussion_r4374577748)

This is a placement regression exposed by the 64-GPU run, independent of R3's routing representation. #1613 introduced a separate `AWEX_TRANSFER_RANK_BASE`; the colocated launcher resolves the actual CUDA base from the worker environment, but previously retained the controller's predicted base for transfer ranks.

With 8 nodes and two TP4 servers per node (`sglang:d16t4`, forked colocation), actual worker placement differed from controller enumeration. The 64 scheduler processes consequently registered only 32 distinct transfer ranks, including two rank-zero processes that published different rendezvous ports; initialization timed out with 63/64 and 1/64 clients joined.

The fix derives the transfer base from actual placement while preserving isolated CUDA namespaces and explicit bases for separated workers. Production changes are limited to `sglang_remote.py`; the existing AWEX rank formula and transfer protocol are unchanged. Regression tests cover the eight-node cyclic layout with and without GPU isolation. The previous live run verified 64 unique ranks after this fix.

Keeping this narrow fix in this PR so the reproduced multi-node setup remains runnable. The unrelated TMS and generic RTensor changes have been removed.
