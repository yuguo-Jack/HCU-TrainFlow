# feat(trainer): add opt-in stale rollout token loss masking

[Upstream PR](https://github.com/areal-project/AReaL/pull/1840) · state: closed · merged: True

## Original PR description

This feature is opt-in: `rollout.mask_stale_tokens` defaults to `false`. With the default or an explicit `false`, Trainer keeps the existing actor call and loss behavior. Enable per-token filtering explicitly:

```yaml
rollout:
  max_head_offpolicyness: 1
  mask_stale_tokens: true
```

Only token ages greater than the configured limit are masked; equality is retained. This switch does not alter rollout admission, scheduling, or cancellation.

Expired generated tokens can remain in completed multi-turn rollouts beyond the configured policy-version lag. Apply a next-token-aligned policy-version mask at actor update time, preserving fresh tokens, complete trajectory context, and rollout group membership.

The mask gates policy/distillation loss contributions and Megatron MTP loss. Keep the original reduction denominator, trajectory rewards, PRM scores, GAE boundaries, and advantage normalization semantics. Advantage normalization, when enabled, still includes original generated tokens; this change filters direct training contributions rather than removing trajectory history or changing credit assignment. Report version-filtered token fraction and post-filter version statistics alongside existing pre-filter metrics.

Validation: 252 CPU tests passed, 1 deselected across policy-version masking, diagnostics, MOPD, proximal approximation, rollout controller, staleness management, workflow filtering, and async task runner suites. Full pre-commit checks passed. Multi-node/GPU training and MTP integration were not run.

Opt-in follow-up validation: 150 tests passed across policy-version masking, the real Trainer training-loop toggle/default compatibility, diagnostics, MOPD, and proximal approximation. Full pre-commit checks passed again.

Align the MTP version mask with input-token positions

`policy_version_mask[i]` already describes the next-token target `input_ids[i + 1]`. Here it is passed to MCore as `loss_mask` with `labels=None`. MCore 0.19 shifts the mask once when deriving labels from `input_ids`, then again for the first MTP layer. As a result, the MTP target `input_ids[i + 2]` is gated by the version of `input_ids[i + 3]`.

For example, with tokens `[P0, P1, P2, S0, S1, F0, F1, F2]`, versions `[-1, -1, -1, 0, 0, 3, 3, 3]`, current version 3, and maximum lag 1, the resulting MTP mask still enables the expired target `S1`: its gate uses the fresh version of `F0`. This example does not depend on the pre-existing prompt-boundary alignment issue.

Please generate a separate input-token-aligned version mask for MTP from the raw `versions`, so MCore can shift it together with its targets.

Reference: [MCore label/mask rolling](https://github.com/NVIDIA/Megatron-LM/blob/core_v0.19.0/megatron/core/transformer/multi_token_prediction.py#L807-L857).

Preserve the original MTP normalization denominator

In the reachable `calculate_per_token_loss=False` path, MCore computes `num_tokens` from this same mask and divides the auxiliary MTP loss by that count. Combining the masks therefore changes the denominator as well as the numerator, contrary to the stated requirement to preserve the original normalization.

For example, an original mask `0001111110` gives 6 supervised positions after MTP rolling, while a filtered mask `0000001110` gives 3. With an MTP coefficient of 0.1, each retained term changes from `0.1 / 6` to `0.1 / 3`, doubling its weight. The outer actor reduction retains the original mask and does not compensate for this MTP renormalization.

This path is used by Qwen3.5 with CP=1 in the pinned Bridge implementation; its provider only forces `calculate_per_token_loss=True` for CP>1. This finding is specifically about the False path, not a claim that the True path has the same amplification.

Please retain the original per-layer MTP token counts for normalization and apply the version mask only to the numerator.

References: [MCore normalization](https://github.com/NVIDIA/Megatron-LM/blob/core_v0.19.0/megatron/core/transformer/multi_token_prediction.py#L875-L892), [pinned Qwen3.5 provider](https://github.com/sitabulaixizawaluduo/Megatron-Bridge/blob/5d3268b972d55fe1d08b98b04e8c453467d4e51d/src/megatron/bridge/models/qwen_vl/qwen35_vl_provider.py).

With `rollout.mask_stale_tokens=True` and `enable_mtp_training=False`, `PPOActor._ppo_update` still adds `mtp_version_mask` to the batch.
