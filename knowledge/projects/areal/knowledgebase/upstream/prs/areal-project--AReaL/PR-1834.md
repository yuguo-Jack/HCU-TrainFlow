# fix(engine): restore aiter MoE weight layout after online weight updates

[Upstream PR](https://github.com/areal-project/AReaL/pull/1834) · state: closed · merged: True

## Original PR description

> Follow-up: the `Dockerfile.rocm` PR (branch `rocm-dockerfile`) should merge after this one.

## Description

On ROCm, every MoE model served with aiter returns garbage rollouts after the first online weight
update. This happens on both SGLang and vLLM. This PR restores the correct weight layout after each
update. Dense models and CUDA are not affected.

**Why it breaks.** On ROCm, SGLang and vLLM tile-shuffle unquantized MoE expert weights once, right
after loading, into the layout the aiter fused-MoE kernel expects. AReaL's online weight updates
then write checkpoint-layout tensors straight into those shuffled buffers and never re-run the
post-processing. From the first update on, the experts hold weights in the wrong layout and
generation produces garbage. The training job keeps running, so nothing reports an error.

### Changes

**1. SGLang: `areal/engine/sglang_aiter_moe_layout.py` (new).**
SGLang 0.5.10.post1's `update_weights_from_distributed` and `update_weights_from_tensor` only call
`load_weights`, so every update writes checkpoint rows into the shuffled buffer. This module patches
two SGLang functions in place:

- `FusedMoE._weight_loader_impl` unshuffles the target expert slice, loads it, and reshuffles it.
- `UnquantizedFusedMoEMethod` marks the layer as shuffled once post-processing has run.

Each update therefore leaves the correct layout, including partial updates of a single layer. The
patch is guarded by the sha256 of the original and patched files: it refuses any other SGLang
version, is idempotent, and applies all-or-nothing. Users who install SGLang themselves run
`python -m areal.engine.sglang_aiter_moe_layout` once. The follow-up `Dockerfile.rocm` PR runs it at
image build time.

The patch is not needed for SGLang >= 0.5.21, whose `begin/end_weight_update` session re-runs the
post-processing. It can be deleted when AReaL upgrades SGLang.

**2. SGLang + AWEX: `areal/engine/awex/adapters/sglang_adapter.py`.**
AWEX writes raw bytes straight into parameter storage, bypassing SGLang's weight loader, so the fix
above cannot see it. `_rebuild_derived_weights` now re-applies the aiter shuffle to `w13_weight` and
`w2_weight` of every `UnquantizedFusedMoEMethod` layer. It is a no-op when aiter MoE is not active.

**3. vLLM: `areal/engine/vllm_ext/{vllm_worker_extension,areal_vllm_server}.py`.**
vLLM already ships the right mechanism. Layerwise reload restores each layer, loads it, re-runs
`process_weights_after_loading`, and copies the result back into the original storage, so CUDA
graphs stay valid. AReaL bypassed it by calling `model.load_weights` directly. This PR switches to
it only where the layout actually changes after loading:

- **scope**: `_areal_needs_layerwise_reload()` checks once whether any MoE layer's quant method is
  `UnquantizedFusedMoEMethod` with `unquantized_backend == UnquantizedMoeBackend.AITER`. That is
  the same condition under which vLLM converts the weights to the aiter layout. Every other
  backend, including CUDA's default Triton MoE, keeps the original load path unchanged.
- **disk updates**: `areal_update_weights` calls `model_runner.reload_weights(weights_path=...)`.
- **xccl updates**: the first bucket of a refit opens one layerwise session
  (`initialize_layerwise_reload`). `/areal_continue_generation` closes it through the new
  `areal_finalize_weight_update` RPC.
  - The session must span the whole refit: vLLM re-processes a layer only after all its tensors
    have arrived, and buckets routinely split a layer.
  - Every trainer already calls `continue_generation()` after the last bucket (FSDP, Megatron,
    Archon and the rollout controller), so no trainer change is needed.

## Additional Context

### Validation

All tests ran on one AMD MI308X (gfx942) with real Qwen3-30B-A3B weights, TP=1, aiter on and CUDA
graphs on. Every update re-sends the identical checkpoint, so a correct engine must reproduce the
reference prompt logprobs. Each value below is the max |Δ logprob| against that reference. aiter
MoE is not bitwise deterministic, so the healthy bound is max(3 × run-to-run noise, 1.0).

**SGLang 0.5.10.post1** (`update_weights_from_tensor`: a full update, then layer-0 experts only,
then a full update again):

| Build | noise | full | partial | full |
|---|---|---|---|---|
| unpatched (`lmsysorg/sglang:v0.5.10.post1-rocm720-mi30x`) | 0.47 | 25.2 | 25.6 | 27.9 |
| with this PR's patch | 0.20 | 0.14 | 0.26 | 0.46 |

**vLLM 0.19.1**: the test drives the real `VLLMWorkerExtension`. xccl refits are sent in buckets of
100 tensors, which split layers. The NCCL broadcast is replaced by a local copy of the same tensor.

| AReaL | noise | disk | xccl refit 1 | xccl refit 2 |
|---|---|---|---|---|
| main `18f5271f` | 0.49 | 24.1 | 30.0 | 22.6 |
| this PR | 0.33 | 0.25 | 0.12 | 0.12 |

With `VLLM_ROCM_USE_AITER=0`, the unpatched paths are output-identical to the baseline. This
confirms that the corruption comes from the aiter shuffle.

**vLLM scope check.** A random-weight 2-layer, 8-expert Qwen3-MoE checks which path runs. The
engine reloads the identical checkpoint, and 24 greedy tokens are compared with the reference.

| AReaL | aiter | MoE backend | layerwise path | disk reload | 2-bucket xccl refit |
|---|---|---|---|---|---|
| main `18f5271f` | on | AITER | n/a | tokens differ | n/a |
| this PR | on | AITER | yes | identical | identical |
| this PR | off | TRITON | no (original path) | identical | identical |

**End-to-end RL training.** I ran one training job with this PR's engine code on Qwen3-30B-A3B,
using FSDP2, vLLM 0.19.1, aiter MoE, CUDA graphs and real xccl weight updates. It completed 4 of 4
steps with exit code 0, finite loss and live gradients. The mean train-vs-rollout logprob
difference was 0.030, and 0.16% of tokens differed by more than ln 2. On every refit the layerwise
session ran in the required order:

1. first bucket arrives;
2. `initialize_layerwise_reload`;
3. all buckets load;
4. `/areal_continue_generation` calls `areal_finalize_weight_update`;
5. `finalize_layerwise_reload`;
6. generation resumes.

### What this does and does not cover

- **Covered**: the weight layout of unquantized MoE with aiter on ROCm after online updates. This
  covers SGLang (distributed/tensor updates and AWEX) and vLLM (disk and xccl), on a 30B MoE model.
- **Not covered**:
  - FSDP + xccl weight updates of MoE experts under transformers 5. That is a separate,
    backend-generic bug that also affects CUDA. transformers 5 fuses the experts into
    `experts.gate_up_proj` / `experts.down_proj`, and the SGLang and vLLM loaders silently skip
    those names, so the rollout keeps its initial experts. It surfaced in the end-to-end run above
    and needs its own fix;
  - quantized MoE;
  - TP > 1;
  - GPUs other than MI308X (gfx942);
  - upstream AMD CI. AReaL has no AMD runners, and this PR does not register one.
- **CUDA behaviour is unchanged**:
  - the SGLang patch and the AWEX reshuffle only act when aiter MoE is active;
  - the vLLM change is gated on the aiter MoE backend, so CUDA keeps the original load path.
- **Possibly affected on CUDA, left out of scope**: vLLM also changes the weight layout after
  loading for the `FLASHINFER_TRTLLM` unquantized MoE backend and for online quantization. The
  original load path likely has the same problem there. It was not tested, so this PR does not
  change those paths; widening the gate to them would be a one-line change.
