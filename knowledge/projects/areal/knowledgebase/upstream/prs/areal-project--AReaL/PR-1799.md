# fix(engine): align MindSpeed MoE fusion and dispatcher settings

[Upstream PR](https://github.com/areal-project/AReaL/pull/1799) · state: closed · merged: True

## Original PR description

## Description

On NPU, MindSpeed patch registration and model construction could use different MoE fusion and dispatcher settings, leaving fusion disabled in the model despite an enabled MindSpeed setting. Use `mindspeed.moe_permute_fusion` and `mindspeed.moe_token_dispatcher_type` consistently across both bridge backends, synchronizing the fusion alias before provider validation and patch registration.

Reject non-`alltoall` NPU dispatchers early and warn about ignored non-default Megatron settings. Preserve CUDA Megatron Bridge's existing `alltoall` override and CUDA mbridge's dispatcher selection. Update configuration help and correct tau2's `moe_zero_memory` spelling to `level1`.

## Additional Context

Validation: 156 tests passed across `tests/test_megatron_bridge_config.py`, `tests/test_mindspeed_args_patch.py`, and `tests/test_megatron_loss_normalization.py`. Real Qwen3/Qwen3.5 providers passed 12 fusion-transition and stale-alias checks. Four-NPU MoE-block tests confirmed fused forward/backward kernel execution, BF16-routing output/gradient agreement, and exact recovery after disabling fusion. CLI references were regenerated; the full documentation build was not run.

Enabling an existing MindSpeed fusion setting now changes model execution. The dependency's fused path still downcasts FP32 routing probabilities to BF16: the FP32-routing output comparison failed the probe's `rtol=0.01, atol=0.001` tolerance, while gradients passed. This PR does not fix that dtype behavior or claim full-model numerical/performance qualification. MindSpeed all-to-all overlap also disables its unfused NPU fast-ops path; that dependency interaction is outside this configuration fix.
