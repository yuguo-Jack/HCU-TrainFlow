## Description

Moreover, it provides an example of how VLLM environment variables should be set properly so that tensor parallelism can be applied successfully using VLLM on Ascned NPUs.

## Code Review

This pull request introduces a `memory_efficient_load` option for FSDP to reduce peak GPU memory usage during model initialization, which is particularly useful for large models. The core logic involves creating the model on the CPU, loading weights on rank 0, and then broadcasting them. A critical security vulnerability has been identified: the use of `torch.load` without `weights_only=True` in the underlying weight-loading logic can lead to arbitrary code execution if a malicious checkpoint is provided. It is strongly recommended to update the weight-loading utilities to use `weights_only=True` or prefer the `safetensors` format to mitigate this risk. Additionally, minor issues were found in the new example files related to script robustness and configuration consistency.

![security-high](https://www.gstatic.com/codereviewagent/security-high-priority.svg) ![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The call to `get_state_dict_from_repo_id_or_path` on line 297 introduces a potential insecure deserialization vulnerability. This utility function (defined in `areal/utils/save_load.py`) uses `torch.load` to process `.bin` files without setting `weights_only=True`. Since `torch.load` uses the `pickle` module internally, it is susceptible to arbitrary code execution if a malicious model checkpoint is loaded. An attacker who can influence the `self.config.path` (e.g., via CLI overrides) could achieve remote code execution (RCE). It is recommended to update the utility function to use `weights_only=True` or prefer the `safetensors` format for loading weights.

The `allocation_mode` `vllm:d4p1t1+d4p1t1` appears to be syntactically incorrect, as the part after `+` should specify a role (e.g., `fsdp`). Assuming it's a typo for a two-role allocation, it would allocate 8 GPUs in total (4 for each role), which contradicts `n_gpus_per_node: 16` on line 11. The value from the accompanying shell script, `vllm:d1t8+fsdp:d1t8`, is consistent with 16 GPUs and seems more appropriate. To avoid confusion and potential errors, it's best to correct this in the YAML file.

```yaml
allocation_mode: vllm:d1t8+fsdp:d1t8
```
