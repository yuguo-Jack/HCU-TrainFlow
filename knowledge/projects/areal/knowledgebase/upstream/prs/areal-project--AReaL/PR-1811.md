# feat: add Qwen3.8-27B Arena RL training

[Upstream PR](https://github.com/areal-project/AReaL/pull/1811) · state: closed · merged: True

## Original PR description

## Description

Add a standalone Qwen3.8-27B Arena RL training recipe with separate actor and rollout runtimes, Slurm submission, and verified source snapshots. Update shared Arena reward attribution and rollout metrics to reflect the results of consumed training attempts.

- Pin published reward and Harness bindings per task and validate them on recovery. Training uses the top-level reward score; component scores are recorded as telemetry.
- Give retained invalid model responses and verified model execution failures zero reward while distinguishing infrastructure failures. Add opt-in strict Qwen3 Coder tool parsing, preserving permissive recovery by default.
- Compute quality metrics over rollout attempts dequeued for batch assembly, including rejected attempts; exclude completed work still pending in the prefetch queue.
- Add the 27B entry points and runnable recipe. Submission verifies source/profile snapshots, symlinks, and recovery prerequisites.

Shared reward attribution, response validation, and metric changes also apply to Qwen3.8 Flash Next. Its model kernels, R3 switches, training parallelism, and runtime dependencies are unchanged. Reward mapping remains opt-in, and tool-parser recovery remains enabled by default.

- sitabulaixizawaluduo · comment · 2026-10-27T06:33:15Z · [source](https://github.com/areal-project/AReaL/pull/1811#discussion_r4385759187)

After the modification here, has the existing reward metric changed from the reward generated on the output side to the actual reward consumed during training? Would this cause duplication with the existing task_reward metric? If my understanding is incorrect, please correct me.

- dingzhiqiang · comment · 2026-10-27T06:43:14Z · [source](https://github.com/areal-project/AReaL/pull/1811#discussion_r4385820064)

File: `areal/infra/workflow_executor.py` · line 1509

Yes, the timing changed: `rollout/reward` is now buffered per rollout and included when the batch collector dequeues that result, so completed but still-prefetched rollouts do not enter the current metric window. The value is still the terminal exported interaction reward. It includes dequeued attempts rejected by `should_accept_fn` when they produced a reward; “consumed” here means inspected during batch collection, not necessarily used for an optimizer update.

`task_reward` is logged separately by the PPO actor over sequences in the accepted training batch (`original_rewards` when present, otherwise `rewards`). The two metrics can have the same value in an unfiltered one-to-one batch, so the overlap you noticed is real in that case. With filtering or grouped trajectories, `rollout/reward` still includes dequeued rejected attempts, while `task_reward` covers only accepted training rows; reward processing can also make their values differ. `rollout/reward_sample_count` exposes the rollout denominator. This PR intentionally changes the step window for `rollout/reward`; it does not redefine the actor metric.

- dingzhiqiang · comment · 2026-10-27T09:27:10Z · [source](https://github.com/areal-project/AReaL/pull/1811#discussion_r4387018008)

File: `areal/experimental/openai/proxy/proxy_rollout_server.py` · line 1129

Good catch. For native Anthropic streaming, `InvalidToolCallError` occurs before the SSE response starts, but the broad setup handler was turning it into HTTP 500. In 3c3d53d8 I let that error reach the existing HTTP 422 `invalid_request_error` handler with `x-should-retry: false`, and applied the same session retry guard to `/v1/messages` and `/v1/chat/completions`. Once invalid tool JSON is recorded, a retry through either endpoint returns 422 without starting another generation. This preserves the existing `invalid_tool_json` rollout failure classification and reward handling; no reward logic changed. I added regression coverage for streaming and non-streaming Anthropic requests plus a cross-endpoint retry. The proxy server suite passed (60 tests), as did full pre-commit.
