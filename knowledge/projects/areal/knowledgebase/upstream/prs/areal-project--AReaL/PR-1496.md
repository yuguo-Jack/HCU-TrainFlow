# feat(engine): add native R3 router replay

[Upstream PR](https://github.com/areal-project/AReaL/pull/1496) · state: closed · merged: True

## Original PR description

## Description

This PR adds native R3 (Rollout Routing Replay) support for SGLang rollout + Megatron
MoE actor training. R3 records rollout-time MoE expert choices, transports them through
the rollout/workflow/trainer path, validates and packs them into Megatron token order,
then drives Megatron-Core native `RouterReplay` during recompute-logp and PPO updates.

Main changes:

- Add Megatron router replay config, discovery, validation, layout conversion,
  side-channel transport, and replay orchestration under `areal/engine/r3`.
- Wire routed-expert tensors through RLVR, OpenAI proxy interactions, remote inference,
  and v2 inference service / data proxy paths.
- Add safe fallback behavior for invalid routing: forward-only compute-logp falls back to
  the live router; training update records live router choices for forward and replays
  those recorded choices for backward recompute.
- Add Moonlight MoE and guarded Qwen4Exp Flash Next support (all-MoE
  `WRAPPER_THD`, zigzag CP, native replay). Reject unsupported vLLM routed experts,
  non-Megatron/non-MoE actors, tree training, other VLM paths, padded Megatron
  training, and fused MoE router replay.
- Repair CP reassembly for chunked forward logprobs.
- Add R3 documentation in `r3/README.md`, link it from `README.md` and `CLAUDE.md`, and
  add Moonlight math examples under `examples/r3`.

## Metrics, Definitions, Sources, and Meaning

The metric set is motivated by PR1207 review feedback and by R3's core failure mode:
rollout and training may compute different token logprobs because the rollout engine and
training engine route MoE tokens to different experts. The metrics cover two dimensions:
rollout/train logprob drift and replay execution health.

Rollout/training mismatch metrics are emitted during actor recompute-logp as
`compute_logp/r3/*`:

- `compute_logp/r3/enabled`: `1.0` when the batch carries R3 side-channel tensors,
  otherwise `0.0`; confirms whether the comparison is running on an R3 batch.
- `compute_logp/r3/n_valid_tokens`: number of valid loss tokens used as the denominator
  for token-level mismatch statistics.
- `compute_logp/r3/rollout_train_logp_abs_diff/{avg,max,min}`: absolute difference
  between Megatron recompute logprob and SGLang rollout logprob; directly measures policy
  mismatch.
- `compute_logp/r3/rollout_train_logp_sq_diff/{avg,max,min}`: squared logprob
  difference; emphasizes large drift and outliers.
- `compute_logp/r3/rollout_train_k3_kl/{avg,max,min}`: Taylor KL estimate
  `exp(delta) - 1 - delta`, where `delta = train_logp - rollout_logp`; summarizes
  rollout/train distribution drift.
- `compute_logp/r3/rollout_train_extreme_frac_tau2/{avg,max,min}`: fraction of valid
  tokens with `abs(delta) > log(2)`; catches severe 2x probability-ratio outliers.
- `compute_logp/r3/rollout_train_extreme_frac_tau5/{avg,max,min}`: fraction of valid
  tokens with `abs(delta) > log(5)`; catches very large tail mismatches.

Replay execution counters are emitted as `r3/*` from the Megatron engine and can appear
with trainer prefixes such as `ppo_actor/update/r3/*`:

- `r3/enabled`: `1.0` when native Megatron replay was active for the call.
- `r3/batches_with_side_channel`: number of batches that carried routed-expert tensors.
- `r3/samples_total`: number of sequences covered by R3 side-channel accounting.
- `r3/routing_valid_samples`: sequences whose rollout routing passed preprocessing
  validation.
- `r3/routing_invalid_samples`: sequences rejected by preprocessing validation.
- `r3/routing_valid_fraction`: `routing_valid_samples / samples_total`; healthy runs
  should be close to `1.0`.
- `r3/logical_microbatches`: Megatron logical micro-batches processed for the call.
- `r3/router_stage_microbatches`: micro-batches on pipeline stages with local MoE
  routers.
- `r3/replayed_microbatches`: micro-batches that replayed rollout routing.
- `r3/skipped_microbatches`: micro-batches where routing was not safe to replay.
- `r3/invalid_samples`: invalid samples that caused replay skips.
- `r3/mode_replay_microbatches`: micro-batches run in native replay mode.
- `r3/mode_record_microbatches`: training micro-batches that used native record fallback
  because rollout routing was invalid.
- `r3/mode_live_microbatches`: forward-only micro-batches that used the live router.
- `r3/mode_no_router_microbatches`: micro-batches on stages without local MoE routers.
- `r3/replay_fraction_active`: `mode_replay_microbatches / router_stage_microbatches`;
  healthy R3 runs should be near `1.0`.
- `r3/skip_fraction_active`: `skipped_microbatches / router_stage_microbatches`; healthy
  R3 runs should be near `0.0`.
- `r3/tokens_real`: real packed tokens seen by Megatron.
- `r3/tokens_padded`: tokens after Megatron packing/padding.
- `r3/tokens_padding`: padding tokens introduced by packing/alignment.
- `r3/replay_real_tokens`: real tokens in replayed micro-batches.
- `r3/record_real_tokens`: real tokens in record-fallback micro-batches.
- `r3/live_real_tokens`: real tokens in live-router fallback micro-batches.
- `r3/no_router_real_tokens`: real tokens on stages without local MoE routers.

Sparse skip reason counters such as `r3/skip_invalid_sample`,
`r3/skip_zero_routing_for_real_token`, and
`r3/skip_missing_final_token_routing_without_replacement` are emitted only when the
specific fallback path happens.

## Examples

New examples are added under `examples/r3`:

- `examples/r3/gsm8k_rlvr.py` and `examples/r3/gsm8k_rlvr_moonlight.yaml`: single-turn
  GSM8K RLVR with `RLVRWorkflow`.
- `examples/r3/gsm8k_multiturn.py` and
  `examples/r3/gsm8k_multiturn_moonlight.yaml`: GSM8K multi-turn correction loop through
  the agentic `ArealOpenAI` path, exported as interaction trajectories.

Both configs use local 8-GPU split execution with 4 rollout GPUs and 4 actor GPUs:

```bash
rollout.backend=sglang:d1p1t4
actor.backend='megatron:(attn:d1p1t4|ffn:d1p1t1e4)'
```

R3-on:

```bash
export MOONLIGHT_MODEL_PATH=/workspace/models/Moonlight-16B-A3B-Instruct
export GSM8K_DATA_PATH=/storage/openpsi/data/gsm8k

python -m examples.r3.gsm8k_rlvr --config examples/r3/gsm8k_rlvr_moonlight.yaml
python -m examples.r3.gsm8k_multiturn --config examples/r3/gsm8k_multiturn_moonlight.yaml
```

R3-off comparison:

```bash
python -m examples.r3.gsm8k_rlvr \
  --config examples/r3/gsm8k_rlvr_moonlight.yaml \
  trial_name=no-r3 \
  rollout.return_routed_experts=false \
  actor.megatron.enable_router_replay=false

python -m examples.r3.gsm8k_multiturn \
  --config examples/r3/gsm8k_multiturn_moonlight.yaml \
  trial_name=no-r3 \
  rollout.return_routed_experts=false \
  actor.megatron.enable_router_replay=false
```

Performance follow-up on R3 head `8f3e0d3904376496974b8c0f014d0dd11870dd76`, focusing on the long-context Qwen3.8 Flash Next workload in #1774.

With the target recipe's `recompute_logprob=false` and `reuse_train_logp`, R3 does not force an additional actor logprob forward; overhead instead comes from capture/readback, serialization/transport, layout preparation and replay kernels. The [R3 paper](https://arxiv.org/html/2510.11370v1) describes no added computational overhead, but that does not measure this implementation's long-context data movement.

The route payload alone can be calculated exactly: `tokens × 48 layers × topk 10 × 4 bytes` for int32. Excluding framing and the one-row alignment difference:

| Sequence length | Raw int32 | Base64 int32 | Proposed binary int16 |
| --- | ---: | ---: | ---: |
| 16 Ki tokens | 30 MiB | 40 MiB | 15 MiB |
| 32 Ki tokens | 60 MiB | 80 MiB | 30 MiB |
| 128 Ki tokens | 240 MiB | 320 MiB | 120 MiB |
| 256 Ki tokens | 480 MiB | 640 MiB | 240 MiB |

These are byte costs, **not measured latency or throughput losses**. Twelve maximum-length trajectories already contain 5.625 GiB of raw int32 routes before padding/copies.

I would prioritize these optimizations:

1. **Prepare only the rank's required routes before H2D, and avoid GPU-to-Python metadata synchronization.** [engine.py:1814–1819](https://github.com/areal-project/AReaL/blob/8f3e0d3904376496974b8c0f014d0dd11870dd76/areal/engine/megatron_engine.py#L1814-L1819) transfers the complete `[B,S,48,10]` tensor to every rank, then [layout.py:184–196](https://github.com/areal-project/AReaL/blob/8f3e0d3904376496974b8c0f014d0dd11870dd76/areal/engine/r3/layout.py#L184-L196) packs, CP/SP-slices and finally selects local PP layers. For balanced PP4/CP2/TP8+SP, local int32 route elements are 1/64 of the full tensor, before the int64 index conversion; this is a theoretical data-volume reduction, not a 64× speedup. Build the routing layout from the original CPU microbatch metadata, select local layers/tokens, and transfer contiguous pinned slabs once. Currently cu-seqlens are moved to GPU and converted back with `.tolist()` in the layout hot path. Retain exactly the same padding, CP zigzag order and SP ordering.

Prompt tokens still need replay because they affect attention/recurrent state.
