# feat(engine): train Qwen3.5 PointerHead decision models on Megatron

[Upstream PR](https://github.com/areal-project/AReaL/pull/1810) · state: open · merged: False

## Original PR description

## Description

Add supervised training for a Qwen3.5 decision model on the Megatron-Bridge backend inspired by [kev](https://github.com/jaredpalmer/kev). The model does not generate answer tokens. It reads a state and one question, and the loss points at one of that question's options. A stock Qwen3.5 checkpoint is loaded through the existing bridge. On the last pipeline stage the vocabulary head is replaced by an fp32 `PointerHead` (`q` and `k`, each `hidden → decision_head_dim`, default 256). The trunk can be full-weight or LoRA-tuned, including Gated DeltaNet projections. The pointer head stays dense, stays trainable, and is saved and loaded as `head.pt` next to the Hugging Face adapter.

This stays on the SFT trainer. `actor.is_decision_model` selects a decision engine instead of token logprobs. GRPO, PPO, the critic, and vLLM rollout are unchanged.

### Architecture

One question is one causal row: state, instruction, options, then a decide token. Qwen's existing special tokens mark those spans (`<|fim_prefix|>`, `<|fim_middle|>`, `<|box_start|>`, `<|box_end|>`, `<|fim_suffix|>`), shown below as `<state>`, `<q>`, `<opt>`, `</opt>`, and `<decide>`. The hybrid trunk (full attention plus Gated DeltaNet) runs as a normal Megatron-Bridge Qwen3.5 model. `PointerHead` replaces `output_layer` only where `post_process` is true and returns `[tokens, 2 * dp]` in fp32, not vocabulary logits.

The loss does not classify a fixed number of choices. For each packed row it takes the hidden state at `<decide>` and the hidden state at each `</opt>`: z_j = k(h_j) · q(h) / sqrt(dp)

`z` is a distribution over however many options that question has. Hard labels use cross-entropy. A soft `target` uses soft cross-entropy. At most one extra term is added: label smoothing, Brier, focal, or an ordinal ranked-probability score on `score` questions. The loss weight is the number of `<decide>` positions. Rows inserted so every rank has the same number of micro-batches have no `<decide>` token and are skipped. Accuracy and loss are tracked per question.
`PointerHead` is attached in the pre-wrap hook, before LoRA and before DDP builds its buckets. LoRA then freezes non-adapter trunk weights, and the hook turns `requires_grad` back on for the head. The head is never a LoRA target. Its parameters stay fp32, so DDP gives them their own gradient bucket. When tensor parallel is greater than 1, the head is sequence-parallel: the forward gathers the full sequence, and `finalize_model_grads` all-reduces the head gradients.
Gated DeltaNet layers do not expose `linear_qkv` / `linear_fc1`. Their mixer is one fused `in_proj`. `patch_qwen35_hybrid_lora_specs` splits that into `PTNorm` plus `ColumnParallelLinear`, and replaces `out_proj` with `RowParallelLinear`, when the target list names those modules. Presets are `all`, `dense`, `attn`, and `qv`. `all` and `attn` include the mixer; `dense` and `qv` do not. After the split, `in_proj` is still one adapter on the concatenated `[q, k, v, z, b, a]` matrix. Hugging Face can wrap `in_proj_qkv`, `in_proj_z`, `in_proj_a`, and `in_proj_b` as four independent adapters. Those checkpoints are not interchangeable: Megatron-Bridge's PEFT export copies one down-projection onto all four names. `docs/qwen35-gdn-lora.md` records that gap. Full fine-tuning does not need the unfuse.
On Ascend, MindSpeed's GDN conv and delta-rule kernels were copying `cu_seqlens` to the host on every layer. The packed and context-parallel paths now keep a host list and reuse it, including after a batch is moved to device. That cache is used by any packed Qwen3.5 GDN run, not only decision training.
### Integration
The decision path is a branch on the existing SFT and Megatron stack, not a second trainer.
| Piece | Components Touched |
| --- | --- |
| Config | `TrainEngineConfig`: `is_decision_model`, `decision_head_dim`, `lora_targets_preset`, `ord_w`, `label_smoothing`, `brier_w`, `focal_gamma` |
| Data | `areal/dataset/decision.py`, registered in `areal/dataset/__init__.py`. `type: decision` selects it. `type: sft` also selects it when the path is a decision JSONL, a suite directory, or contains `decision` |
| Engine | `MegatronLMEngine` builds `DecisionEngine` when `is_decision_model` is set, otherwise the normal `LMEngine`. The pre-wrap hook attaches the head, applies bridge LoRA, then unfreezes the head. Save and load read and write `head.pt` (or a raw `pointer_head.pt`) on the last stage and broadcast it across tensor- and context-parallel ranks |
| Forward | The last stage still goes through AReaL's packed unpad and, when context parallel is on, reassembly. The decision branch passes that `[tokens, 2 * dp]` tensor to the loss. It does not call `gather_logprobs_entropy` |
| Loss | `DecisionEngine.train_lm` / `eval_batch` pass `compute_packed_decision_loss`. The engine does not own the formula |
| Launch | `examples/decision/train_decision.py` is a normal `SFTTrainer` entry. `qwen3_5_decision_sft.yaml` is the 8-NPU `megatron:d4p1t2` template. `run_npu_poc.sh` is the single-NPU recipe. `run_npu_parallel.sh` selects `single`, `dp2`, `dp4`, `tp2`, `tp4`, `cp2`, `cp4`, or `d4t2` |

**Pipeline parallel is not supported.** Qwen3.5 ties the input embedding to the language-model head, and Megatron's tied-embedding path assumes that head is a vocabulary projection. With pipeline size 1 the tie stays on one rank, so data, tensor, and context parallel train. With pipeline size greater than 1, rank 0 owns the embedding and the last rank owns `PointerHead`. Megatron still reads `output_layer.weight` on that last rank:
1. On load, `_broadcast_shared_embeddings` builds the receive buffer with `empty_like(output_layer.weight)`. `PointerHead` only has `q` and `k`, so initialize raises `AttributeError`.
2. On the first step, `GPTModel.shared_embedding_or_output_weight` returns `self.output_layer.weight`, and `finalize_model_grads` all-reduces that tensor with the stage-0 embedding gradient. The same missing attribute aborts the step.
> A temporary vocabulary-sized `weight` gets past the load broadcast and has to be removed before the optimizer is built, so the forward hits the missing attribute anyway. Leaving it in place would register a tied vocabulary matrix the decision loss never uses. Untying the embedding is a model-construction change: stage 0 allocates that matrix as a shared weight, and a head-only patch cannot turn the tie off after the pipeline modules exist. `run_npu_parallel.sh` exits when the parsed pipeline size is greater than 1.

### Data
We write JSONL. Each line is one state and one or more questions. A question is `choice` (label is an option key), `noul` (label is a boolean, encoded as no/yes), or `score` (label is a 0-based level on an ordered scale). An optional `target` is a distribution over those options. The loss trains against the distribution when target is present, and against the single option otherwise. We use it when no single option is the whole answer. A case can be unknowable, or the annotators can split.

A record with three questions becomes three training rows. Each row is the state tokens plus that one question. On the train split, choice questions are shuffled and, with the default probabilities, sometimes rewritten with a "none of the above" answer, a "none" distractor, or an irrelevant extra option. `noul` and `score` are not rewritten. Validation is encoded as written. `n_per_source` and `max_records` take a deterministic slice of a frozen suite for smoke runs.
The loader, not the JSONL, builds the columns the loss reads. Each column has the same length as `input_ids`.
| Column | What it stores |
| --- | --- |
| `input_ids` | The row: `<state> … <q> … <opt> … </opt> … <decide>` |
| `token_roles` | `0` everywhere else, `1` at each `</opt>` in option order, `2` at `<decide>`. These are the only positions the loss scores |
| `choice_label` | `-1` except at `<decide>`, where it is the 0-based option index after shuffle and insertion. `"label": "billing"` is not written as an index in the file |
| `question_type` | `-1` except at `<decide>`: `0` choice, `1` noul, `2` score. The ordinal term runs only for `score` |
| `soft_target` | `-1.0` means "no soft label". When `target` is present, each `</opt>` holds that option's probability and the loss uses those values instead of hard cross-entropy |


A two-option hard question, options encoded as billing then shipping:
| Token | `token_roles` | `choice_label` | `question_type` | `soft_target` |
| --- | --- | --- | --- | --- |
| state, instruction, option text | `0` | `-1` | `-1` | `-1.0` |
| `</opt>` billing | `1` | `-1` | `-1` | `-1.0` |
| `</opt>` shipping | `1` | `-1` | `-1` | `-1.0` |
| `<decide>` | `2` | `0` | `0` | `-1.0` |

With `"target": {"billing": 0.7, "shipping": 0.3}`, the two `</opt>` `soft_target` values become `0.7` and `0.3`. `<decide>` still holds `choice_label = 0`.
AReaL's existing packer concatenates rows. `cu_seqlens` marks row boundaries. Alignment padding is role `0` and is ignored. The loss walks each span, gathers `</opt>` and `<decide>`, and averages the question losses.

#### Soft targets

`target` in the JSONL is a distribution over the question's options, for a case where one hard label is not the whole answer (annotators split, or the case is unknowable). A hard `label` is still required. Keys match option names for `choice`, `"false"` / `"true"` for `noul`, and `"0"`, `"1"`, … for `score`. Missing keys count as 0, then the vector is normalized.

The loader writes that distribution into `soft_target`, aligned with `input_ids`. `-1.0` means there is no soft label at that token. With `target` present, each `</opt>` holds that option's probability and every other position stays `-1.0`. Without `target`, the whole column is `-1.0` and the loss uses `choice_label`.

For `"label": "billing"` and `"target": {"billing": 0.7, "shipping": 0.3}`, the two `</opt>` positions store `0.7` and `0.3`. The packed loss gathers those `</opt>` values into `t` and, because every entry is non-negative, uses soft cross-entropy `-sum(t * log_softmax(z))`. Label smoothing, Brier, focal, and the ordinal term are not added. `choice_label` at `<decide>` is still the hard index `0`, and accuracy still compares `argmax(z)` with that index.

Choice questions that carry `target` are only shuffled. Inserting or dropping an option would change which probability belongs to which option.
