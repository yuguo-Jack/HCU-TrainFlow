## Description

Adds a validator for prepared datasets, a walkthrough for building them locally, and regression tests for the image helpers.

`python -m areal.dataset.validate` takes a JSONL file or a directory written by `Dataset.save_to_disk()`, checks every record against the `text-rl` or `tokenized-sft` contract, and reports diagnostics with exit codes 0/1/2. It runs on CPU and downloads nothing.

The English and Chinese customization pages now cover `Dataset.from_list()`, `save_to_disk()`, `get_custom_dataset()`, `DatasetDict` splits, and the validator itself. Every snippet was executed, so the output shown is what you get.

`tests/test_image_utils.py` covers Base64 encoding and batch padding. `areal/utils/image.py` gains docstrings describing the behaviour those tests pin down; signatures and behaviour are unchanged.

## Additional Context

### Design note

**Profile boundaries.** Both profiles describe *supported subsets* of what AReaL consumes today, not a universal schema. `text-rl` covers records `RLVRWorkflow` can prompt from; `tokenized-sft` covers records `train_lm` can consume directly. Anything outside them — remote downloads, tokenization, multimodal rows, tool-call conversations, DPO pairs — is out of scope, and the CLI rejects rather than guesses. Extra columns are always allowed, because the loader forwards the whole row to the reward function. `--require-field` checks presence only and never inspects the value, leaving reward-specific semantics to the caller.

**Report format.** Human output is one greppable summary line followed by diagnostics:

```text
checked=3 valid=3 invalid=0
line 2: messages[0].role [unsupported_role] unsupported role 'tool'; expected one of: assistant, system, user
```

`--report PATH` writes the same data as JSON: `profile`, `source`, `split`, `checked`, `valid`, `invalid`, `diagnostics_truncated`, and a `diagnostics` array of `{location, field, code, message}`. `location` is `line <n>` (1-based, JSONL) or `row <n>` (0-based, saved datasets). Diagnostic codes are module-level constants and treated as public API, so tests assert on them rather than on prose.

**Exit codes.** `0` when every scanned record is valid; `1` when at least one record is invalid or the input held no records; `2` for usage errors, unreadable input, or an unwritable report target. Code 2 also covers `--max-length` outside the `tokenized-sft` profile, `--split` on a JSONL file, a `DatasetDict` without `--split`, and an unknown split — each naming the problem and the valid alternatives.

**Diagnostic truncation.** `--max-errors` (default 20) caps how many diagnostics are *retained*. The scan always runs to the end of the input, so `checked` and `invalid` stay accurate, and `diagnostics_truncated` records that detail was suppressed. A record with several problems counts once toward `invalid`.

**JSONL memory behaviour.** JSONL input is streamed line by line over the file handle; nothing is buffered, so memory is constant regardless of file size. Malformed lines are reported with their 1-based line number and the scan continues. Blank lines are skipped and do not count toward `checked`. Saved datasets are iterated row by row through the Arrow-backed `Dataset`.

### Notes for reviewers

- `get_custom_dataset(path=..., type=...)` logs `dataset_config is not provided`. That is the existing branch taken when no config object is passed. The walkthrough mentions it so readers don't wonder; a real training config sets `train_dataset.path` / `.type` and never hits it.
- The unavailable-split `ValueError` is wrapped by the loader, so the requested and available splits appear inside a longer message. The walkthrough asserts on substrings, which the acceptance criteria allow.
- Boolean `loss_mask` values are valid input but cannot be mixed with integer masks inside one saved table, since Arrow assigns a single type per column. Unit tests cover boolean masks directly; the saved-dataset fixtures use homogeneous integer masks.
- Test speed: importing `areal` pulls torch and ray, so each `python -m` subprocess costs ~5 s. Only four cases exercise the real process boundary; the rest drive `main()` in-process, which took the file from 95 s to 26 s without losing coverage.

### Scope check

`areal/api/cli_args.py`, the launchers, and the public configuration are unchanged, and no dependencies were added. Loader behaviour and the image helper signatures are as before. This needs no GPU or multi-node run, and none was performed.
