# fix(trainer): make optimizer-minibatch M2PO selection opt-in

[Upstream PR](https://github.com/areal-project/AReaL/pull/1732) · state: open · merged: False

## Original PR description

## Description

Add an opt-in M2PO path that selects one mask per optimizer minibatch before the engine splits it into microbatches. The default remains per-engine-microbatch selection, so the recommended `examples/math/gsm8k_m2po.yaml` with `fsdp:d4p1t1` retains its existing behavior.

```yaml
actor:
  m2_threshold: 0.04
  m2po_optimizer_minibatch: true  # default: false; requires DP1
  prox_logp_method: recompute    # recompute or metrics
```

Both the supported-scope validation and mask preparation are gated by the new option. Opting in requires a threshold, DP size 1, and cached proximal log-probabilities. Unsupported opt-in configurations fail before training; the default path keeps its existing loss callback and engine weights.

The prepared mask travels as `m2_loss_mask`, separate from the original `loss_mask`. The regular and pure-MOPD losses consume it, while FSDP excludes it from model kwargs and preserves it in the loss context.

Related to #1730. Addresses the review about breaking the shipped DP4 example.

## Scope and relation to #1546

The opt-in path preserves the current unsplit implementation's retained-token mean (`K`). It does not change the objective to the original-token denominator (`N`) in the paper formula and #1546. That normalization contract still needs agreement before merging. Selection across DP ranks is not implemented. Direct loss calls without a prepared mask retain local selection.

- dajiaohuang · comment · 2026-10-27T16:18:12Z · [source](https://github.com/areal-project/AReaL/pull/1732#issuecomment-6447264770)

I found a gap between the split-equivalence test helper and the actor's actual reduction path. `_loss_and_gradient` calls `grpo_loss_fn` without `loss_step`, so it falls back to `TokenMean` constructed from the already-filtered mask and exercises retained-count (`K`) normalization. In `PPOActor._ppo_update`, however, the actor passes a prepared `loss_step`; for `token_mean`, `prepare_policy_gradient_batch` binds `TokenMean` to the original `loss_mask` before the M2PO mask is applied. The PR then changes the engine callback weight to the retained `m2_loss_mask` count. That pairs a local numerator divided by original microbatch count `n_j` with outer weight `k_j`; when `k_j/n_j` differs across engine microbatches, the actor's split execution need not match its unsplit execution. The mocked actor test checks dispatch/weights but does not exercise this real `loss_step` + callback aggregation combination.

Could the regression exercise the same prepared `loss_step` and engine weighting used by `PPOActor`, and assert both the intended `N`/`K` objective and split-vs-unsplit gradients? That would also make explicit which denominator/weight pairing this opt-in path promises. This is based on the code and synthetic test path only; I did not run training or access real model/data/hardware.
