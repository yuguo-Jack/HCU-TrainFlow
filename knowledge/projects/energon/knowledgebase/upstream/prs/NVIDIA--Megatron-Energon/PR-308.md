# perf(parquet): shuffle by row group and stream rows sequentially

[Upstream PR](https://github.com/NVIDIA/Megatron-Energon/pull/308) · state: open · merged: False

## Original PR description

## Summary

Parquet random access has to decode a whole row group to return one row. Reading row by row through `reader[i]`, as the other formats do, therefore decoded each row group once for every row in it. This PR makes Parquet read sequentially per slice and shuffle at row-group granularity.

### Row-group shuffling
- When training, every row group is a slice. Row groups are spread across ranks and workers and visited in random order, and the rows within a row group are read sequentially.
- With a filter index (or `serial` read order), slices are whole files.
- New `parquet_read_order` option on recipes, dataset loaders and the Parquet factories:
  - `row_group_shuffled` (default)
  - `serial`: dataset order, no shuffling, a single stream, for data that is already shuffled
- `max_samples_per_sequence` does not split Parquet slices further, because starting a slice mid row group would decode the rows before it.

### Streaming slices
- New optional `SequentialSampleReader` protocol with `iter_slice(start, stop)`.
- `DatasetSampler` keeps one stream per active slice next to its `SliceState` and samples between them as before. Streams are not part of the saved state, so the checkpoint format is unchanged.
- Readers without `iter_slice` (tar, jsonl, binidx) are unaffected.
- `TranslatedIndexReader.iter_slice` streams the underlying range and skips filtered-out rows.

### Parquet reader
- `iter_slice` reads with `iter_batches` (256 rows per batch, no threads), so rows are decoded incrementally and each row once per epoch. Memory per active slice is bounded by the batch.
- Each stream owns its file handle.
- Random access (`reader[i]`) decodes the row's row group, located by bisection.
- `ParquetFileEntry.row_group_rows` is collected from the footers and is now required.

- Copilot · comment · 2026-10-15T13:36:37Z · [source](https://github.com/NVIDIA/Megatron-Energon/pull/308#discussion_r4283648370)

File: `src/megatron/energon/flavors/base_indexed_dataset.py` · line None

The new row-group shards still pass through generic sub-slicing with `self.max_samples_per_sequence`. A value of `1` makes `Sharder.shard_workers` ignore shard boundaries and create single-row slices; other small limits split large groups into independently shuffled fragments. This defeats `row_group_shuffled` and can repeatedly decode whole groups when the working set exceeds the cache. Preserve row-group shuffle boundaries or reject incompatible limits specifically for Parquet, without changing other formats, and test a non-None sequence limit.

- Copilot · comment · 2026-10-15T13:36:38Z · [source](https://github.com/NVIDIA/Megatron-Energon/pull/308#discussion_r4283648553)

File: `src/megatron/energon/flavors/parquet/reader.py` · line None

`ParquetFileEntry.row_group_rows` defaults to an empty list, and the existing parser test accepts version-1 layouts without this field. Passing such a layout to the exported `IParquetReader` now raises `RuntimeError` for every valid row, whereas the previous reader obtained group sizes from the footer. Populate missing group sizes lazily before looking up the row.

- Copilot · comment · 2026-10-15T13:36:38Z · [source](https://github.com/NVIDIA/Megatron-Energon/pull/308#discussion_r4283648638)

File: `src/megatron/energon/flavors/parquet/reader.py` · line None

Limiting the least-recently-used cache to the number of parallel iterators can evict a row group that is still being consumed. With two iterators, read from A, finish B, then start C: B remains more recently used than A, so inserting C evicts A. Reading A's next sequential row decodes it again. This undermines the intended decode-once behavior even without sequence sub-slicing. Make eviction account for active versus exhausted slices, and add a regression test for this transition.

- Copilot · comment · 2026-10-15T13:36:38Z · [source](https://github.com/NVIDIA/Megatron-Energon/pull/308#discussion_r4283648711)

File: `tests/test_parquet_dataset.py` · line None

`ds.build()` produces one finite epoch; `training=True` does not add the repetition wrapper used by the training pipeline. The 25th `next(iterator)` therefore raises `StopIteration`, so this test always fails. Iterate the built dataset twice to check serial ordering across two epochs.

- Copilot · comment · 2026-10-16T13:04:12Z · [source](https://github.com/NVIDIA/Megatron-Energon/pull/308#discussion_r4294945574)

File: `src/megatron/energon/flavors/common/dataset_sampler.py` · line None

After checkpoint restoration or restarting iteration mid-epoch, the resume branch restores active slice probabilities but never reopens their streams. These slots remain `None`, so every remaining row in those slices uses random access and decodes an entire Parquet row group per sample. Initialize each active stream at its saved `current` position. Add a resumed-iteration decode-count assertion, since the existing restore test checks order but misses this performance regression.

- Copilot · comment · 2026-10-16T13:04:13Z · [source](https://github.com/NVIDIA/Megatron-Energon/pull/308#discussion_r4294945637)

File: `src/megatron/energon/flavors/parquet/reader.py` · line 161

These streaming handles are not registered in `_parquet_cache`, which is all `IParquetReader.close()` closes. After partial consumption, retaining the iterator and calling `dataset.close()` therefore leaves its active Parquet files open: `DatasetSampler.close()` only delegates to the reader. This violates the resource-release contract in `base_dataset.py:245–251`. Track active streams or their handles and release them during explicit cleanup, keeping closure idempotent and allowing subsequent iteration to reopen resources.
