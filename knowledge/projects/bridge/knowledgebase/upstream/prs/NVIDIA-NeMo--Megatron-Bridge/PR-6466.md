# ci(skyrl): add weekly SkyRL Megatron model-parity e2e

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6466) · state: open · merged: False

## Original PR description

## What

A weekly (plus `workflow_dispatch`) job that runs [SkyRL](https://github.com/NovaSky-AI/SkyRL)'s Megatron model-parity test against this repo's checkout and its `3rdparty/Megatron-LM` submodule. It follows the existing NeMo-RL and verl weekly suites:

- `.github/workflows/skyrl-e2e-weekly.yml`: one job on `nemo-ci-gcp-gpu-x8`. It pins a SkyRL SHA and the digest of SkyRL's Megatron CI image, mounts both checkouts, and sends a Slack alert on failure.
- `.github/workflows/skyrl_ci/run_megatron_models.sh`: puts the Bridge and MCore checkouts first on `PYTHONPATH` and checks the imports, then runs the selected rows.
- `.github/workflows/skyrl_ci/README.md`: what the test checks, why these rows were picked, the environment and how the checkout is injected, and runner requirements.

## Why

SkyRL uses Megatron-Bridge for HF -> Megatron loading and for Megatron -> HF weight sync into vLLM after every training step. `test_logprobs_matching_roundtrip` compares Megatron logprobs with vLLM after the HF -> Megatron load, then syncs the exported weights back into vLLM and checks the logprobs again. It does this across TP, PP, CP and EP layouts. Bugs in the conversion mappings and in the TP/EP gathers during export usually don't raise. They show up as logprob drift, which this test catches and conversion tests that compare logits against HF at a single layout can miss.

Rows run (all use bridges that ship here; SkyRL only re-roots `model.language_model.*` for Qwen3.5):

| Row | Model | Layout |
| --- | --- | --- |
| `qwen3-moe_tp2_ep2` | tiny random Qwen3-MoE | TP2 EP2 |
| `qwen3-moe_pp2_cp2` | tiny random Qwen3-MoE | PP2 CP2 |
| `qwen3.5-0.8b-dense_tp2` | Qwen3.5-0.8B | TP2 |
| `qwen3.5-35b-a3b_h100_tp4_ep4` | Qwen3.5-35B-A3B | TP4 EP4 |
| `nemotron3.5-lightning_tp4_ep4_h100` | Nemotron-3.5-Lightning-30B-A3B | TP4 EP4 |

Rows not run, because they would test SkyRL-carried code or need SM100: GLM-5.3-Flash, Kimi K2.5 INT4 QAT, FP8/MXFP8. The README explains each.

## How the checkout is injected

As in `nemo_rl_ci`: the checkouts go first on `PYTHONPATH`, and `SKYRL_PYTHONPATH_EXPORT=1` makes SkyRL's test fixtures forward it into Ray worker runtime envs. Before the tests run, the script imports `megatron.bridge` and `megatron.core` in the driver and in a Ray worker, and requires both to resolve under the mounted roots. All other packages come from SkyRL's `uv.lock` at the pinned SHA.

## Status: draft, for discussion

Opened as a draft to agree on the approach with maintainers before it lands (it adds a CI workflow).

Checked locally (CPU only, Bridge `main` @ `b53e66c4` with Megatron-LM submodule `1e3c0c62`, SkyRL @ `a1e34dbf`):

- The script's import check passes. `megatron.bridge` and `megatron.core` resolve to the mounted checkout in the driver **and** in a Ray worker started through the uv runtime-env hook.
- Under that injection, SkyRL's Megatron worker, model bridges, weight-sync sources and runtime patches all import against Bridge `main`, and the two patches that modify Bridge code apply cleanly. That covers the 193 commits since SkyRL's current pin (`8e7077c6`).
