# fix(model): keep router expert_bias in FP32 when building builder-backed configs

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6731) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Builder-backed configs now keep MoE router `expert_bias`, and parameters a module lists in `_keep_in_float32_parameter_names`, in FP32 through the mixed-precision wrap. This covers `AutoBridge.get_model()`, training setup (including PEFT) and `build_and_load_model()`. The provider path already does this.

Bridge called Megatron Core's builder (`builder.build_distributed_models()`) in three places, and the builder applies `mixed_precision_wrapper` directly (`unimodal_build_distributed_models` → `_wrap_with_mp_wrapper`). With the default `Float16Module`:
- A router `expert_bias` loaded before the wrap is cast to bf16. MCore's `_maintain_float32_expert_bias()` then casts it back to FP32, so the dtype looks right but the values are rounded: `[1.0001, 1.0002]` becomes `[1.0, 1.0]`.
- Parameters listed in `_keep_in_float32_parameter_names` stay in the model dtype.

The provider path (`provide_distributed_model()`) wraps through `_apply_mixed_precision_wrapper`, which snapshots both before the cast and restores them afterwards.

Weights are loaded before the wrap in two places:
- **`AutoBridge.get_model(load_weights=True)`**: the HF weights load in a pre-wrap hook. I found this while GPU-verifying the K-EXAONE and Step-3.5-Flash migration (#6693). On a layer-selected Step-3.5-Flash checkpoint at EP4, main's provider-built model and the builder-built model differed in memory only in the 12 `expert_bias` buffers.
- **PEFT training** (raised in review of #6671): `_create_peft_pre_wrap_hook()` loads the base checkpoint in a pre-wrap hook. `_build_distributed_model()` then called the builder with its bare `Float16Module`, so every PEFT run on a builder-backed family with router expert bias started from rounded biases.

Full fine-tuning and `load_megatron_model()` load the Megatron checkpoint after the wrap, and the router switches back to FP32 before loading, so their biases were exact. `build_and_load_model()` now uses the same helper for consistency.

The in-repo conversion tools pass `mixed_precision_wrapper=None` and were not affected: the `convert.sh` backends, `import_ckpt`, `compare.py`, VLM generation and adapter export.

# Changelog

- New `build_distributed_models(model_config, pg_collection, **kwargs)` in `model_provider.py`:
  - Builds a builder-backed config through its `ModelBuilder`.
  - Applies `mixed_precision_wrapper` through `_apply_mixed_precision_wrapper`, one stage at a time. The wrapper is `Float16Module` when omitted, or the callable the caller passes. `None` still skips wrapping.
- `AutoBridge.get_model()`, `training/setup.py::_build_distributed_model()` and `training/model_load_save.py::build_and_load_model()` build through it. No public signature changes.
- Tests. Each writes nonzero FP32 router biases (1.0001, 1.0002, …) in a pre-wrap hook and compares exactly (`rtol=0, atol=0`):
  - `test_get_model_wrapper_keeps_float32_router_tensors[default|custom|none]` (`test_auto_bridge.py`):
    - Builds a tiny bf16 MoE config through the real Megatron Core GPT builder on CPU.
    - Also keeps the router weight in FP32 through `_keep_in_float32_parameter_names`, as MiniMax-M3 does.
    - Covers the default wrapper, a user-supplied wrapper, and `None`.
  - `test_builder_path_keeps_float32_router_bias_loaded_before_wrap` (`test_setup.py`):
    - Runs `_build_distributed_model()` with a pre-wrap hook that writes the biases, standing in for the PEFT base-checkpoint load.
    - Builds through the real builder and helper. DDP is skipped because it needs CUDA and comes after the restore.
  - `test_load_mbridge_saved_model_config`: updated for the helper's call.
- `docs/bridge-guide.md`: notes the wrapper default and the FP32 behavior.

# Affected families

These bridges on main (2d8f43edb) set both `USE_MODEL_CONFIG_FOR_CONVERSION = True` and `moe_router_enable_expert_bias=True`:

| Bridge | HF architecture | `expert_bias` rounded on main with the default wrapper |
|---|---|---|
| `BailingMoeV2Bridge` | `BailingMoeV2ForCausalLM` | yes |
| `BeamBridge` | `BeamForCausalLM` | yes. `BeamTopKRouter` keeps only its weight and linear bias in FP32 (`keep_in_fp32`) |
| `Ernie45Bridge` | `Ernie4_5_MoeForCausalLM` | yes |
| `ExaoneMoeBridge` | `ExaoneMoeForCausalLM` (K-EXAONE) | yes |
| `GLM45Bridge` | `Glm4MoeForCausalLM` | yes (reproduced on CPU) |
| `HYV3Bridge` | `HYV3ForCausalLM` | yes |
| `MiniMaxM2Bridge` | `MiniMaxM2ForCausalLM` | yes |
| `NemotronHBridge` | `NemotronHForCausalLM` | yes, for MoE checkpoints. Dense Nemotron-H has no router |
| `SarvamMoEBridge` | `SarvamMoEForCausalLM` | yes |
| `Step35Bridge` | `Step3p5ForCausalLM` | yes, when `use_moe_router_bias` is set |
| `MuseSparkBridge`, `MuseSparkTextBridge` | `MuseSparkForConditionalGeneration`, `MuseSparkForCausalLM` | no. `MuseSparkRouter._apply` already restores its FP32 `expert_bias` after every cast |

Two open migrations add more families with router expert bias: #6671 (GLM-5) and #6672 (DeepSeek-V4). Both get this fix once they merge main.

No builder-backed family on main sets `_keep_in_float32_parameter_names`. MiniMax-M3, MiniMax-M3-VL and Kimi K3 do, but they still build through providers. On the builder path those parameters would end up in bf16, not just rounded, so this change covers them before those families migrate.

# Verification

CPU (Mac, Megatron Core a2965235, transformers 5.20.2).

**`AutoBridge.get_model()`**:
- Tiny bf16 configs (a Llama with MoE overrides, and GLM-4.5 mapped by `GLM45Bridge`) are built with a pre-wrap hook that writes the FP32 router tensors.
- The comparison is `provide_distributed_model()` from the same HF config with the same hook.

| Path | `expert_bias` exact FP32 (main → this PR) | FP32-marked router weight (main → this PR) |
|---|---|---|
| `get_model()`, default wrapper | 0/2 → 2/2 | 0/2, left in bf16 → 2/2 |
| `get_model(mixed_precision_wrapper=Float16Module)` | 0/2 → 2/2 | 0/2, left in bf16 → 2/2 |
| `get_model(mixed_precision_wrapper=None)` (no wrap) | 2/2 → 2/2 | 2/2 → 2/2 |
| `provide_distributed_model()` | 2/2 → 2/2 | 2/2 → 2/2 |

**Training setup** (`_build_distributed_model()`, tiny bf16 MoE builder config, biases written in a pre-wrap hook as the PEFT base load does):

| Tree | Router `expert_bias` after the build (both routers) |
|---|---|
| main 2d8f43edb | `[1.0000, 1.0000, 1.0000, 1.0000]`, FP32 dtype |
| this PR | `[1.0001, 1.0002, 1.0003, 1.0004]` |

**Unit tests** (main → this PR, same environment):
- Files: `test_auto_bridge.py`, `test_model_instantiation.py`, `test_setup.py`, `test_setup_restart_hooks.py`, `test_model_load_save.py`, `test_optimizer_distribution.py`, `test_runtime_callbacks.py`, `test_gtp.py` and `test_modelopt_setup.py`. Also the hybrid builder, Sarvam, LLaDA-1.5, MiniMax-M3, Muse Glimmer, Beam, Nemotron-H, GLM-4.5, Llama, Step-3.5, GPU conversion launcher, MIMO provider and orchestrator, compare-mask, generation and VLM tests.
- Result: 1505 → 1509 passed, 25 → 25 failed, 7 skipped. The only outcome changes are the 4 new cases.
- Of the 25 failures, 17 come from this environment: no CUDA, no APEX, Transformer Engine stubbed, emerging optimizers not installed.
- The other 8 are a break on main itself. #6642's Sarvam and LLaDA-1.5 `test_load_builds_on_requested_device` tests fake the built model as `[object()]`. #6645, merged four minutes earlier, sets `model_chunk.model_config` on each loaded chunk.
- The new and updated tests fail on main: the `get_model()` cases have 4 of 4 bias values rounded, and `test_setup.py` cannot import the helper.
- pre-commit 3.6.0 is clean.

**GPU**: not rerun for this change. The H100 runs in #6693 passed this same wrapping to `get_model()` explicitly:

```python
get_model(
    ...,
    mixed_precision_wrapper=lambda config, module: _apply_mixed_precision_wrapper([module], config, Float16Module)[0],
)
```

The builder model's logits were bitwise equal to main's provider-built model for K-EXAONE 236B, K-EXAONE 2.0 and Step-3.5-Flash. CI runs the new tests on its GPU runners.

# Not in this PR

Code outside Bridge that calls `model_config.get_builder_cls()(model_config).build_distributed_models()` directly still gets Megatron Core's bare wrapper. Those callers should use `build_distributed_models()` or `AutoBridge.get_model()`.
