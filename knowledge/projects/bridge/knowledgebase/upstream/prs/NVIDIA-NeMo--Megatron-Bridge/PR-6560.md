# docs(model-card): note Omni H100 SFT runs with the default CUDA allocator

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6560) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Documents in the Nemotron-3-Nano-Omni model card that the H100 SFT item was verified with PyTorch's default CUDA allocator, and that enabling expandable segments makes the run fail after the step-50 checkpoint save. Follow-up to NVBug 6900704. Supersedes #6553 with a card-only change.

# Changelog

- `examples/model_verification_cards/nemotron-3-nano-omni-30b-a3b-reasoning/card.yaml`: the `sft.H100` expected result now states that the run uses PyTorch's default CUDA allocator (expandable segments off), and that with expandable segments enabled, rank 0 runs out of memory on the step after the step-50 checkpoint save on 80 GB H100s.
- Regenerated `docs/_static/model-verification/catalog-v1.json`, `docs/models/nemotron/nemotron-3-omni.md`, and its Fern mirror.

## Why

The Omni SFT recipe inherits `expandable_segments:True` from `COMMON_RECIPE_ENV_VARS`, but `scripts/training/run_recipe.py` applies recipe environment defaults after CUDA initializes, so the card's `train.sh` command runs with PyTorch's default allocator. A run that exports the recipe's declared value before launch reserves about 5 GiB more on rank 0 and runs out of memory on step 51, right after the step-50 save; with the default allocator, all 100 steps pass. QA verified both results and now runs this model's training card items with expandable segments off.
