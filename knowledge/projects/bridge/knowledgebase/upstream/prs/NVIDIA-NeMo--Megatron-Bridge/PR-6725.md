# feat(model): enable full-iteration CUDA graphs for Qwen3-VL text and Qwen3.5-VL images

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6725) · state: open · merged: False

## Original PR description

# What does this PR do ?

Lets Qwen3-VL and Qwen3.5-VL train with Megatron Core's full-iteration CUDA graphs (`model.cuda_graph_impl=full_iteration`): text-only for both, and with real image data for Qwen3.5-VL through an opt-in static vision path (the static path rejects deepstack visual features, which Qwen3-VL uses). It also fixes a hang at exit of full-iteration runs whose cause is in Bridge main's end-of-training cleanup: the optimizer's full-iteration gradient-conversion graphs kept the training graph alive, so `torch.distributed.destroy_process_group()` never returned. Without a full-iteration graph and without `model.vision_static_shapes`, training behaves as before, apart from `dataset.prefetch_factor` now reaching Energon when it is set (see Risks). This revision is rebased onto main and works with main's builder-backed Qwen3.5-VL model config (see "Rebase onto main").

# Changelog

- **fix(model)** `qwen3_vl_step._pad_and_pack_qwen3_vl_step`: compute `max_seqlen` as `target_len` instead of `seqlens_in_batch.max().item()` (the same value by construction). The `.item()` is a device-to-host sync that makes a full-iteration capture fail and costs one sync per microbatch in eager runs.
- **feat(training)** `ConfigContainer.validate()`: allow `rerun_state_machine.check_for_nan_in_loss` and `ddp.check_for_nan_in_grad` with a full-iteration graph when Megatron Core provides deferred result validation (`RerunStateMachine.capture_deferred_validations` / `run_deferred_validations`), `rerun_mode="disabled"`, and neither the spiky-loss nor the large-gradient check is on. This is not only a relaxation: with a full-iteration graph, `validate()` now also rejects, at config time and with a message naming the enabled checks, three kinds of combinations that it used to accept and that then failed later, at capture, or were unsupported at replay: `ddp.check_for_nan_in_grad` on a Megatron Core without deferred result validation, any of the four checks (`check_for_nan_in_loss`, `check_for_spiky_loss`, `ddp.check_for_nan_in_grad`, `ddp.check_for_large_grads`) with a `rerun_mode` other than `"disabled"`, and `check_for_spiky_loss` or `ddp.check_for_large_grads` at all. `check_for_nan_in_loss` without deferred result validation stays rejected, as today.
- **feat(data)** Energon: hand the existing `dataset.prefetch_factor` to Energon's `get_savable_loader` (it was ignored for Energon datasets). `None` keeps Energon's default; sample order and saved loader state do not depend on it.
- **feat(model)** Qwen3.5-VL: opt-in static vision shapes (`model.vision_static_shapes`, default off), the data contract and model path that a full-iteration graph can capture:
  - new `models/qwen_vl/static_vision.py`: a CPU batch converter that runs in the dataloader worker (MRoPE position ids equal to `get_rope_index`, vision position-embedding gather indices and weights, vision rotary ids, static per-image `cu_seqlens` with a trailing padding segment, a scatter index with unique dummy slots), an over-cap image downscale, host FLOP statistics, and the config validation;
  - `Qwen3VLVisionModel.forward_static`: per-image THD vision attention with static `cu_seqlens` and a Python-int `max_seqlen`, 2D vision RoPE, padded rows zeroed before the merger;
  - `Qwen3VLModel`: `static_vision_inputs` replace the host-side reorganize/scatter with an `index_copy` into unique slots. The model reads `vision_static_shapes` and `vision_patch_cap` at construction with its other construction settings: from the builder-backed model config when the builder passes one, otherwise from the provider's language config;
  - model config: `vision_static_shapes`, `vision_patch_cap`, `vision_max_images` and `vision_over_cap_policy` are outer fields of the builder-backed `Qwen35VLModelConfig` (which the Qwen3.5-VL recipes build with AutoBridge), next to the other vision-encoder settings, and fields of the Qwen3.5-VL providers;
  - step, train loop (FLOP statistics outside the graph), mock VLM collate and HF Energon task encoder hooks. The step checks a static batch against the length it pads to, `state.cfg.model.seq_length`. The task encoder's `static_vision` defaults to `None` at class level, so an encoder created without `__init__` takes the default vision path;
  - `ConfigContainer.validate()`: with `model.vision_static_shapes` off, a static layout left on the dataset config (`dataset.static_vision` or `dataset.task_encoder.static_vision`, for example from a saved static config reused with the flag flipped) is rejected; the default vision path does not read static batches and would drop their images silently;
  - docs: `docs/training/cuda-graphs.md` (NaN checks with full-iteration graphs; the static vision path, how to enable it, and the configs that carry its settings).
- **fix(training)** `train._delete_cuda_graphs`: also release the optimizers' full-iteration gradient-conversion graphs. With an eager optimizer step, Megatron Core's distributed optimizer (and its layer-wise mixed-precision optimizer) replays the gradient conversion as a CUDA graph in the training graph's memory pool (`_cudagraphed_grad_copy`, a `FullIterationGradCopy`), and that object keeps a reference to the training graph. `_delete_cuda_graphs` cleared `FullCudaGraphWrapper`'s graphs, the optimizer CUDA graph and the TE and local graphs, but not these, so the training graph and its captured NCCL work outlived the cleanup and `destroy_process_group()` at the end of `pretrain()` never returned. The training loop now passes its optimizer, and each chained optimizer's `FullIterationGradCopy` is reset to its initial state, the way Megatron Core resets it when the training graph changes.

## Why

With full-iteration graphs the whole forward-backward iteration is captured once and replayed, so nothing in the step may read device values on the host. For Qwen3-VL that rules out: the `.item()` above, the loss NaN check (Bridge rejected it outright), and the whole dynamic vision path, which reads `image_grid_thw` on the host to build MRoPE ids, vision rotary/position-embedding indices and attention boundaries, and scatters the vision embeddings with a boolean mask. Text-only runs only need the first two; image runs need the static vision path, whose shapes are fixed for the whole run and whose host work happens in the dataloader worker.

The static path also changes what the vision tower computes compared with today's per-layer Transformer Engine vision graphs: it attends per image and applies the 2D vision RoPE, as the eager path and Hugging Face do. The per-layer vision graphs attend over the padded cap (their padding mask is ignored) and their captured callables drop the rotary embedding (see Risks).

The exit hang (commit 5) is independent of the other commits: the cleanup gap is in Bridge main's code, which commits 1-4 do not touch. With the current Megatron Core pin, a multi-rank full-iteration run whose optimizer builds the gradient-conversion graph hangs in the final `destroy_process_group()` that `pretrain()` runs. Megatron Core skips that graph only with a graphed optimizer step (`optimizer_cuda_graph`), CPU offload, or its precision-aware no-FP8 path. Note that Bridge's `MixedPrecisionConfig` copies its default `fp8_recipe` into the optimizer config even for BF16 runs, so BF16 runs with the precision-aware optimizer still build the graph; this PR's own BF16 smoke did and hung without commit 5. The hang was reproduced on this branch without commit 5, not separately on main, whose cleanup code is identical.

## Reading guide (5 commits, one concern each; each commit builds and passes its own tests)

1. `fix(model): compute the Qwen3-VL step max_seqlen without a host sync` - one line plus a test that packs a batch with `Tensor.item()` disabled.
2. `feat(training): allow NaN checks with full-iteration CUDA graphs through deferred validation` - `ConfigContainer._validate_full_iteration_result_validation`, the capability check `utils.cuda_graph.supports_deferred_result_validation`, and two tests (one per branch; the one that needs the capability is skipped when the installed Megatron Core lacks it).
3. `feat(data): pass dataset.prefetch_factor to the Energon loader` - datamodule plumbing, validation, tests.
4. `feat(model): add opt-in static vision shapes for Qwen3.5-VL full-iteration CUDA graphs` - start with `static_vision.py` (`build_static_vision_batch`, `configure_static_vision`). Then read `vision_model.forward_static`, `model._static_vision_pre_process` and `_init_static_vision`, the step, the data hooks, and the config fields in `qwen35_vl_config.py`. Everything outside `static_vision.py` is a branch taken only when `model.vision_static_shapes` is on, with three exceptions: the config check that rejects a static layout without the flag, the four config fields (default off), and the task encoder's class-level `static_vision = None`.
5. `fix(training): release the full-iteration grad-copy graphs before teardown` - `_release_full_iteration_grad_copies` and its call in `_delete_cuda_graphs`, a test that no reference to the training graph or to a conversion graph survives the cleanup (and that the copies are back in their initial state), and a check that the training loop passes its optimizer.

## Results

All performance numbers in this section were measured on an earlier version of this change (a staged Megatron Core, NaN checks off unless stated) and were not re-measured on this branch; the run on this branch is the single-node smoke under Tests.

Qwen3.5-VL 397B-A17B on 64 GB300 GPUs, real DataComp images (Energon, padding mask on), 16 microbatches per rank, steps 31-80 on the same nodes; full-iteration graph + static vision vs the production per-layer graphs (TE `[attn, moe]` + vision TE graphs), with the MoE layers running a sync-free megakernel backend that is not part of Megatron Core main yet. Measured on an earlier version of this change, with a staged Megatron Core and the NaN checks off in both arms:

| metric | full-iteration + static vision vs per-layer graphs |
|---|---|
| step time | -0.5% (95% CI -0.7% .. -0.2%) |
| peak allocated memory | -9% |
| peak reserved memory | +1.5% |
| FLOPs per step | identical |

The full-iteration arm does more vision work than the per-layer arm (per-image attention, 2D vision RoPE, MRoPE, and the recompute that per-layer graphs skip), so this is parity while computing the vision encoder correctly.

- Same model cut to 4 layers on 8 GB200 nodes: -7% to -10% step time vs the per-layer graphs (2 to 16 microbatches per rank).
- Text-only at 397B (no images, so no static vision): about +2% step time vs the per-layer graphs. The per-layer graphs skip the MRoPE computation (see Risks), and that work accounts for the difference by estimate, so the two are at parity for equal work.
- `dataset.prefetch_factor` (commit 3): on one GB200 node with real images and 16 microbatches per rank, the full-iteration step time dropped 21.5%, because the graph reads all microbatches before the replay and Energon's default read-ahead left most of them to be produced on demand.
- Numerics: the static vision tower is bitwise equal to the eager per-image path in the forward pass. In the backward pass (deterministic attention), the gradients other than the position-embedding gradient are bitwise equal in the single-image cases and within about 1e-5 relative in the three-image case; the position-embedding gradient is bitwise equal except for a very elongated image, where it is within about 3e-3 relative (its bf16 reduction order depends on the number of gathered indices). MRoPE ids, position embedding, rotary and the scatter are bitwise equal to the device/eager computations. With deterministic attention, full-iteration replay is bitwise equal to eager static execution for all 30 iterations of an 8-node run (lm loss, MTP loss, grad norm).
- NaN checks under the full-iteration graph (commit 2) captured and replayed with both checks on, at no measurable step-time cost and with values identical to the checks-off run.

- **Text-only and real DataComp images with static vision.** The image runs used the HF Energon task encoder, with the padding mask on and `dataset.prefetch_factor=16`.
  - The full-iteration graph is captured once per rank and then replayed in every iteration from the fourth on.
  - lm loss, MTP loss, grad norm and load-balancing loss are identical to eager execution at printed precision for all 15 iterations, with the NaN checks on and off.
  - The exact fp32 lm loss and grad norm are bitwise equal between the eager and graph runs.
  - Step time vs eager at this size: -55% with static vision, -8% text-only.
- **Static vision through main's recipe path.** AutoBridge builds `Qwen35VLModelConfig`. With `model.vision_static_shapes=true`, the configuration validates (the static layout is derived from the builder config), the graph captures and replays, and the run exits normally.
  - With the recipe's mock VLM data, graph and eager runs are bitwise equal through iteration 12. After that, the losses differ by at most 5.5e-4 relative and the grad norm by at most 4.2e-3 relative.
  - Two eager runs of that configuration differ in the same way, at the same iteration. With the load-balancing loss off, graph and eager runs are bitwise equal for all 15 iterations.
  - The likely cause is the mock collate, which emits no padding mask, so padding tokens reach the router. Nothing in this PR touches that path.
  - The provider path (`to_megatron_provider`) still enables static vision and is bitwise equal to the builder path through iteration 12.
- **Exit (commit 5).** Every full-iteration run exits right after training, on every rank. The same text-only run on commit 4 alone trains all iterations and then hangs in the final `destroy_process_group()` on every rank.
- The default dynamic vision path was smoke-tested on the previous base (15/15 iterations). On this base it is covered by the unit tests and the CPU check above.

## Risks

- **Opt-in.** Nothing changes unless `model.vision_static_shapes=true` (commit 4) or a full-iteration graph is used (commits 2 and 5). Commit 1 changes no value; commit 3 changes nothing unless `dataset.prefetch_factor` is set for an Energon dataset. Two config-time checks are new and can reject configurations that `validate()` accepted before: the full-iteration result-validation combinations listed in the changelog (commit 2), which used to fail later, at capture, or were unsupported at replay, and a static layout on the dataset config without `model.vision_static_shapes` (commit 4).
- **Config.** `Qwen35VLModelConfig` gains four fields, all default off, and saved run configs now include them.
- **Teardown (commit 5).** It resets the four attributes of `FullIterationGradCopy` that Megatron Core itself resets when the training graph changes; its test compares the reset copies with a fresh instance, so a renamed attribute in Megatron Core shows up there. It only drops references at the end of training; nothing runs differently during training.
- **Over-cap images.** An image whose patch count exceeds its budget (`(vision_patch_cap - 4) / vision_max_images`) is downscaled before the processor runs (default, aspect ratio kept) or rejected (`vision_over_cap_policy=error`); a microbatch with more images than `vision_max_images` is rejected. Pick the cap from the measured patch counts of your data (DataComp at `max_pixels=200704` and micro-batch size 1 peaks below the default budget of a 1024 cap).
- **Recompute runs under full-iteration graphs.** Per-layer TE graphs skip activation recompute inside their captured modules; a full-iteration graph runs it, including the vision encoder's inherited recompute. `model.recompute_granularity=null` removes it when memory allows.
- **Known issues of the per-layer graphs** (not changed here; they matter when comparing against them): per-layer TE graphs drop the MRoPE position ids and the vision RoPE inputs at replay, which a separate Megatron-LM PR addresses ("Capture mrope, yarn and vision RoPE inputs in TE per-layer CUDA graphs"). The per-layer vision graphs also ignore their padding mask. Losses of the static path therefore differ from today's per-layer vision graphs by design.
- **Scope.** The static path needs PP=1, CP=1, no sequence parallelism, no packing (in-batch, Energon or global batch), `rerun_mode="disabled"`, images only (no video), and a vision encoder without deepstack features (Qwen3.5-VL); config validation names each violation, and a vision encoder with deepstack features is rejected when the model is built. It hooks the mock VLM SFT collate and the HF Energon task encoder.
- **MoE.** A full-iteration graph also needs the MoE layers to run without device-to-host syncs (for the native dispatcher: drop-and-pad routing). This PR does not change the MoE layers.

## How to enable

```bash
uv run python scripts/training/run_recipe.py --recipe <qwen3.5-vl recipe> \
  model.cuda_graph_impl=full_iteration "model.cuda_graph_modules=[]" \
  model.vision_cuda_graph_impl=none "model.vision_cuda_graph_scope=[]" \
  model.vision_static_shapes=true model.vision_patch_cap=1024 model.vision_max_images=1 \
  dataset.pad_to_max_length=true dataset.prefetch_factor=16
```

The Qwen3.5-VL recipes build `Qwen35VLModelConfig` with AutoBridge, and the static vision settings are fields of that config (and of the Qwen3.5-VL providers), so these overrides apply as written. NaN checks can stay on (`rerun_state_machine.check_for_nan_in_loss=true`, `ddp.check_for_nan_in_grad=true`) with a Megatron Core that has deferred result validation. The MoE layers must be capture-safe as well (see Risks). Recipe defaults are not changed.
