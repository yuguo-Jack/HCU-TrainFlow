# [sync][training] fix: preserve checkpoint FLOP counter precision

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6415) · state: closed · merged: True

## Original PR description

## What does this PR do?

Preserve cumulative FLOP metadata when saving a training checkpoint. The finalizer currently overwrites `TrainState`'s float64 counter with float32: for example, 16,777,217 becomes 16,777,216 before the train-state sidecar is saved and later restored on resume.

Use float64 in that finalizer, matching `TrainState.state_dict()` and MCore's train-state serialization from NVIDIA/Megatron-LM#7516. The regression extends the existing global-save test over both RNG-save settings, a small value, the float32 precision boundary, and a value above the int64 range. Expected precision is float64, not arbitrary integer precision.

## Supported path and ownership

Public recipe training -> `save_checkpoint_and_time` -> checkpoint manager -> `save_checkpoint` -> `train_state_finalize_fn` -> `train_state.pt` and latest-state metadata -> resume. Bridge owns this callback; updating the MCore pin does not replace it. Only the callback dtype and its regression test change.

Recorded Bridge base: `7feb75ef9410bcda80427499ce4ab44907043b61`.
Pinned MCore: `e0c5e18673bf4d4fd89cf87c4f1afbe521fe297f`.
Upstream MCore main inspected: `e30d863a6d82a3c45f2d71355dc73fbf5610967b`.

Both-repository, all-state duplicate searches covered the counter/finalizer symbols, float64 checkpoint metadata and FLOP precision. Core PR 6807 changes upstream sidecar handling; Bridge PR 6227 changes runtime FLOP calculation, PR 3506 safe loading, PR 2817 EMA callbacks, and issue 3267 iteration snapshot ordering. They do not repair this dtype overwrite.
