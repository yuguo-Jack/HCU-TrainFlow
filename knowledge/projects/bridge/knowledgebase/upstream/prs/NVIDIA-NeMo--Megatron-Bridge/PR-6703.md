# test: batch Qwen VL recipe smoke tests

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6703) · state: open · merged: False

## Original PR description

# What does this PR do ?

The Qwen VL launcher starts five separate distributed pytest sessions. Each later session repeats startup and collection before it reaches its first test.

Run the same modules in one session on H100 and GB200, with the Qwen3.5 modules first. Only the two launchers change.

**Before/after evidence**

| Metric | Before | After | Evidence |
| --- | --- | --- | --- |
| Distributed pytest launches for the same modules | 5 | 1 | Launcher logs |
| Launcher time | 983 and 1,131 seconds | 854 and 900 seconds | Two matched pairs on B200, started together, with different GPU and CPU placement |
| Peak GPU memory | 68,940 MiB | 69,854 MiB | `nvidia-smi` sampled every 5 seconds |
| Peak GPU memory with 81,000 MiB free | 68,938 MiB | 69,852 MiB | A separate process held the rest of each GPU to approximate H100 capacity |

The matched pairs show 129 and 231 seconds saved, or about 13% and 20%. Two earlier pairs on `270264f20` showed about 130 seconds saved, or about 12.6%. These times vary with other work on the machine. H100 and GB200 CI times were not measured.

**Why the Qwen3.5 modules run first**

Process group memory stays on the GPU across tests until the process exits, so GPU use grows through a session. In these runs the growth was about 2.3 GB per test. One session in the original module order reached 87,038 MiB on B200. With 81,000 MiB free it still completed, but the samples showed only about 530 MiB of headroom. The largest models now run before most of the growth, which keeps the peak close to the baseline and leaves about 11 GB of headroom.

`destroy_model_parallel()` does not release this memory. A probe with no model showed 11,944 MiB in use before and after it, and 1,744 MiB after `torch.distributed.destroy_process_group()` on the groups. A launcher run that also destroyed the groups at each teardown confirmed the cause: GPU use stopped growing by about 2.3 GB per test, and the peak fell to 60,574 MiB in the new order and 55,160 MiB in the original order. The root cause is tracked in NVIDIA/Megatron-LM#6897, with a fix proposed in NVIDIA/Megatron-LM#7029. After that fix reaches this repository, this growth should stop and the module order should no longer affect the peak.

# GitHub Actions CI

See the [CI section](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/main/CONTRIBUTING.md#-running-github-ci) in the Contributing doc for how to trigger the CI. A Nvidia developer will need to approve and trigger the CI for external contributors.

Validation ran on NVIDIA B200 GPUs on x86-64, with this PR merged onto main at `00e3730dd`, which includes Megatron-Core `ba495158`. Each launcher used two GPUs, 40 pinned CPU cores to match the CI `--cpus=40` limit, `HF_HUB_OFFLINE=1`, and an environment built from `uv.lock`. Only the GPU indices in the launchers changed. This environment is not the CI container image.

The complete launcher completed on this head with staged release assets in the matched runs above, including with the 81,000 MiB limit. It also completed with #6702, #6704, and #6705 merged, in both conditions.

Not validated: H100 and GB200 runners, and the CI container image. GPU memory use on those GPUs can differ from B200, and the 81,000 MiB limit only approximates H100 capacity. The H100 and GB200 launchers are identical, and only the H100 path ran. Upstream CI remains pending.
