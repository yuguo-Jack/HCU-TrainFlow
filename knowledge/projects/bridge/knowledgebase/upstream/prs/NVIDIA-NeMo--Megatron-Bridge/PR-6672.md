# refactor(model): build DeepSeek-V4 from a builder-backed hybrid MLA model config

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6672) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves **DeepSeek-V4** (`DeepSeekV4Bridge`: DeepSeek-V4-Flash, DeepSeek-V4-Pro and their base checkpoints) onto the builder-backed `ModelConfig` / `ModelBuilder` path for recipes and checkpoint conversion. It builds on `BridgeHybridMLAModelConfig` from the GLM-5 PR (#6671, now merged). Part of MB-1857.

# Changelog

- **`DeepSeekV4Bridge`**: `MODEL_CONFIG_CLASS = DeepSeekV4ModelConfig` and `USE_MODEL_CONFIG_FOR_CONVERSION = True`. `provider_bridge()` is replaced by `hf_config_to_model_config_kwargs()`, and `hf_config_to_provider_kwargs()` reuses those kwargs.
  - `DeepSeekV4ModelConfig` (`deepseek/deepseek_v4_config.py`) is a `BridgeHybridMLAModelConfig`, because `DeepSeekV4HybridModelProvider` combines `HybridModelProvider` with an MLA provider and adds nothing to their construction or finalization. The shared `BridgeHybridModelBuilder` resolves the bridge's named Transformer Engine stack-spec factory as the provider does.
  - DeepSeek-V4 specifics are unchanged: the `W`/`C`/`H` + `E` hybrid pattern with one `WE` MTP depth, per-layer CSA compression ratios, hash routing, hyper-connections, YaRN with separate compressed-KV RoPE base, and FP8/MXFP4 import and export.
  - The `HybridModelProvider` default `attention_backend=flash` is set explicitly.
- **`DeepSeekV4TransformerConfig`** declares `cp_partition_mode`. `dsv4_step` reads it for contiguous CP partitioning, and the packed SFT/PEFT recipes set it. Megatron Core declares it only on its dev pin, so the strict builder config needs it on the main pin. On the dev pin the declaration is the same field with the same default.
- **Unread attributes removed**: the bridge no longer sets `norm_topk_prob`, and three MXFP8 recipes no longer set `mtp_eval_in_bf16`. Neither Megatron Core's main nor dev pin declares or reads them, and no Bridge code reads them. The strict builder config rejects undeclared names.
- **Recipes**: the DeepSeek-V4 library recipes (6 GB200, 2 GB300, 5 H100) and the 2 hardware-agnostic packed recipes built on them use `get_model_config()`. The 6 perf recipes build on these.
- `set_deepseek_v4_pipeline_model_parallel_layout()` accepts either config type.
- **Skills**: the `adding-model-support` skill adds DeepSeek-V4 to the hybrid MLA guidance.
- **Tests**:
  - Bridge: builder vs provider parity for a native `DeepseekV4Config` with Flash's architecture (with and without MTP, tied embeddings; raw and finalized at PP1 and PP2 with the recipes' layout). It also covers the hardware-gated fusions, the hybrid pattern, `cp_partition_mode` overrides, and round trips with a pipeline layout.
  - The DeepSeek-V4 recipe tests build strict `DeepSeekV4ModelConfig`s from Flash's and Pro's architectures, and the provider API raises.

## Behavior changes

- **Checkpoint format.** `convert.sh import` / `AutoBridge.import_ckpt` now write builder-format DeepSeek-V4 checkpoints (`_target_: ...DeepSeekV4ModelConfig`). Bridge versions before this PR cannot load them. This PR loads checkpoints that `main` wrote.
- `apply_overrides_and_finalize()`'s automatic DeepSeek-V4 pipeline layout for PP > 1 stays a provider-path feature. Builder users call `set_deepseek_v4_pipeline_model_parallel_layout()`, as the recipes do.

## Related PRs

- **#6248** adds a runner hook (`_pipeline_model_parallel_layout_builder`) and pipe-segment validation to `DeepSeekV4HybridModelProvider`. Since the recipes now build `DeepSeekV4ModelConfig`, those belong on the config. The PRs merge cleanly, and #6248's unit tests pass on the merged tree, but its hook would cover only the provider path.

## NeMo RL

- **Provider path unchanged.** `to_megatron_provider()` returns the same `DeepSeekV4HybridModelProvider` fields as `main` (see Verification), without the unread `norm_topk_prob` attribute. It now logs the builder-deprecation `FutureWarning`.
- **Checkpoint-format caveat**, as in #6609: NeMo RL's `megatron_bridge` pretrained-checkpoint loader calls `.provide()` and cannot load builder-format checkpoints.

Pre-existing on `main` and unchanged here (both fail identically):

- Import at PP2 fails with `Number of decoder layers 4 must match num_layers 8`. `generate_pipeline_layout()` builds a GPT-style layout of logical layers, but the hybrid model has two physical layers per logical layer.
- `convert.sh export` fails with `v_head_dim must be greater than qk_pos_emb_head_dim`. It rebuilds the Hugging Face config from the checkpoint, and `head_dim` comes back as 64. The exports above start from the source config instead.
