# fix(recipe): pin Qwen3.5 text Base revisions and set the GB200 NVLink domain

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6697) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Pins the Hugging Face Base revisions in the Qwen3.5 text pretrain recipes and gives the 35B-A3B GB200 recipe the HybridEP NVLink-domain settings it was missing.

# Changelog

- `qwen35_text_9b_pretrain_8gpu_gb200_bf16_config` and `qwen35_text_35b_a3b_pretrain_8gpu_gb200_bf16_config` load the Base model's config and tokenizer at fixed revisions (`Qwen/Qwen3.5-9B-Base@68c46c4`, `Qwen/Qwen3.5-35B-A3B-Base@0f08130`) instead of Hub `main`, as the long-context recipe already does for its model.
- `qwen35_text_35b_a3b_pretrain_8gpu_gb200_bf16_config` sets `NUM_OF_HYBRID_EP_RANKS_PER_NVLINK_DOMAIN=8`, `NVLINK_DOMAIN_SIZE=72` and `USE_MNNVL=1`, the values the other eight-GPU GB200 MoE recipes (Nemotron 3 Nano, Qwen3-30B-A3B) carry. Its EP8 group spans two four-GPU GB200 nodes in one NVL72 domain.
- Two unit tests in `tests/unit_tests/recipes/qwen/test_qwen35_text_recipes.py` cover the pinned revisions and the environment. Both fail on main.

# Evidence

Same-allocation A/B on 8x GB200 (two nodes in one NVL72 rack) at Bridge `0652ea797`: the 35B-A3B recipe warm-started from the imported Base checkpoint with natural routing, RedPajama2 re-encoded with the Qwen3.5 tokenizer, GBS 512, sequence length 4096. Four 20-step arms ran back to back in one Slurm allocation with a kept Triton cache, alternating the recipe on main (A) and the recipe with the three variables (B). Only the three variables differ.

| Arm | Mean step time, steps 11-20 | Model TFLOP/s/GPU |
|---|---|---|
| A, first | 24,659.9 ms | 239.0 |
| B, first | 24,426.8 ms | 241.9 |
| A, second | 24,783.0 ms | 238.1 |
| B, second | 24,450.0 ms | 241.3 |

B is faster in both pairs (0.9 % and 1.3 %): 1.1 % pooled, 24,438 ms against 24,721 ms. LM loss, MTP loss and grad norm are bit-identical in float32 across all four arms at every step (LM loss 2.134386 at step 20); only the logged load-balancing-loss metric differs, by one float32 ULP at a few steps. Peak allocated memory is unchanged (133.7 GB on rank 0).

An earlier version of this description reported 13 % (28,284 ms against 24,487 ms). Those two runs landed on different racks, and identical runs differ by up to 13 % in step time between GB200 racks, so the same-allocation result replaces it.

# Additional Information

- The 35B-A3B recipe stays slower per token than the Qwen3-30B-A3B GB200 recipe because it runs MBS 1. MBS 2 with `moe_act` recompute runs out of memory when the CUDA graphs are captured, so a larger micro-batch is left for a separate change.
- The dynamic-CP SFT recipe in the same file also loads the 35B-A3B Base without a revision; this PR leaves it unchanged.
