# [data] fix: Stop forwarding packed chat templates

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6078) · state: open · merged: False

## Original PR description

## What changed

Offline-packed chat datasets now consume the preparation-only `chat_template` option before constructing the runtime packed dataset.

## Supported trigger and impact

A GPT SFT configuration using offline packing with a custom `dataset_kwargs["chat_template"]` fails when reusing an existing packed cache. The same failure affects non-producer ranks during a distributed first build, because only rank zero runs tokenization.

The surviving option is forwarded through `build_gpt_sft_split` and the packed Parquet/packed dataset constructors into `GPTSFTDataset.__init__`, whose closed signature rejects it with `TypeError`. This can prevent training from starting after packing has already completed.

## Root cause and fix

`tokenize_dataset` consumes `chat_template` during preparation, but cache-hit builders and non-producer ranks do not execute that mutation. `build_gpt_sft_split` now removes the option specifically when constructing an offline-packed dataset. Raw dataset behavior is unchanged.

The regression test creates a supported multi-source chat configuration, simulates an existing builder-managed packed artifact, and asserts that the final packed constructor does not receive the preparation-only key.

- claude[bot] · comment · 2026-09-12T08:41:54Z · [source](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6078#issuecomment-5644804708)

Light review, LGTM.

The fix is correct and well-scoped. During offline-packing preparation (packing/offline.py line 159), chat_template is popped and applied to the tokenizer on rank 0. But on the final load (_build_datasets, packed_sequence_size greater than 0), the packed parquet path forwards options into GPTSFTPackedParquetDataset then the parent GPTSFTDataset init, which has no chat_template parameter, so an un-stripped chat_template would raise TypeError. Popping it under the not-packing guard prevents that leak. The added unit test asserts the constructor never sees chat_template, which pins the regression well.

Minor observations (non-blocking):
- The legacy npy packed path (GPTSFTPackedDataset, packing/gpt_sft.py line 56) also forwards kwargs to the same parent, so it had the identical leak and is now equally fixed, but only covered indirectly. Since npy is deprecated, no new test is required.
- The pop is intentionally gated to the packing branch; the non-packing branch still forwards dataset_kwargs verbatim, matching the design that chat_template is a preparation-only knob.

Suggested test cases:
- tests/unit_tests/data/builders/test_gpt_sft_builder.py::test_cached_offline_packing_does_not_forward_chat_template (added in this PR, verify it passes)
- Consider an analogous case for the legacy npy packed path (GPTSFTPackedDataset) confirming chat_template is not forwarded, if npy support is still exercised.

No perf tests impacted.
