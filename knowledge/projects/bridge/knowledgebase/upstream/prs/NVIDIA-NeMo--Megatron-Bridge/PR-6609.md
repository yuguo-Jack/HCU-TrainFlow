# refactor(model): build Nemotron-H from a builder-backed hybrid model config

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6609) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves **Nemotron-H** onto the builder-backed `ModelConfig` / `ModelBuilder` path, for recipes and checkpoint conversion. That covers Nemotron-3 Nano 4B, Nano 30B-A3B, Super 120B-A12B, Ultra 550B-A55B and Nemotron-3.5 Lightning. The PR also adds the shared `HybridModel` config that the migration needs. Follows GPT-OSS (#6551) and the other family migrations.

# Changelog

- **`BridgeHybridModelConfig` + `BridgeHybridModelBuilder`** (`models/hybrid/`): the `HybridModel` counterpart of `BridgeGPTModelConfig`.
  - Flat overrides are strict and route to the nested transformer config. Serialization and builder resolution work as in `BridgeGPTModelConfig`.
  - `transformer_config_class` is a class variable, so a family that also needs MLA can subclass the config with an MLA transformer config.
  - It keeps the `HybridModelProvider` contract:
    - `mamba_chunk_size` is a declared field.
    - `finalize()` appends `mtp_hybrid_override_pattern` once per MTP depth and derives `num_layers` from the pattern.
    - The deprecated `hybrid_override_pattern` moves to `hybrid_layer_pattern`.
  - The builder resolves `hybrid_stack_spec` the way the provider does: a `ModuleSpec`, a factory with 0 or 1 arguments, or Bridge's default selection, which includes the ModelOpt layer-norm remap. It falls back to Megatron Core's selection for `wide_residual`. It also applies `attention_backend=local` and a non-default chunk size.
  - The two spec helpers moved to `hybrid_builder.py`, and the provider reuses them unchanged.
  - Beam and Muse Spark Open subclass the new config and drop their copies of `get_builder_cls()`, `as_dict()` and `from_dict()`. Muse Glimmer is unchanged: it derives from Megatron Core's `HybridModelConfig`, and the training `isinstance` branches would change its path.
- **`NemotronHBridge`**: opts in with `MODEL_CONFIG_CLASS = BridgeHybridModelConfig` and converts through the builder (`USE_MODEL_CONFIG_FOR_CONVERSION = True`).
  - `provider_bridge()` is replaced by `hf_config_to_model_config_kwargs()`, and `hf_config_to_provider_kwargs()` reuses the same kwargs.
  - The provider defaults that differ from the builder config's are now set explicitly: `normalization`, `apply_rope_fusion`, `attention_backend=flash`, `bias_dropout_fusion`, the dropouts, `add_bias_linear` and `num_attention_heads`.
  - MTP, the layer pattern and the MoE settings are unchanged.
  - The shared `provider_bridge()` now keeps a `position_embedding_type` that the bridge's kwargs select, so Nemotron-H keeps `"none"`. Every other bridge on that path passes `rope`, `yarn` or nothing, so they are unaffected.
- **Recipes**: every library and perf recipe under `nemotronh` calls `get_model_config()`.
  - The H100 Nano pretrain and Nano 4B recipes no longer construct `HybridModelProvider(...)` by hand. Nano pretrain keeps `vocab_size=None`.
  - The dense 4B resets the MoE fields that transformers' native `NemotronHConfig` fills with defaults.
  - The Lightning recipes record `hf_model_id` / `hf_model_revision` in `extra_checkpoint_metadata`.
  - The `keep_mtp_spec_in_bf16` lines are removed. Nothing read them: Megatron Core reads `keep_mtp_in_bf16`.
- **Tests**:
  - Shared hybrid config: strict overrides, serialization, MTP pattern merge, `num_layers` and stack-spec resolution.
  - Bridge: builder/provider parity across dense, MoE, MTP (repeated and not), `layers_block_type`, chunk 256 and native configs.
  - Recipes: every Nemotron-H library and perf recipe is built against a real `BridgeHybridModelConfig`.
  - Shared bridge: `provider_bridge()` position-embedding selection.
  - Overrides: the runner's six parallelism keys and the example scripts' path on the Nano recipe, `model.hf_model_id=` on Super, flat/nested precedence on the CLI and in YAML, and unknown fields.
  - HF provenance: the Super recipe's sidecar and adapter export source, the Super-VL text-only config through serialization and reconstruction, and `from_auto_config()` on builder configs.
- **Skills**: `adding-model-support` points `HybridModel` families at the shared config.
- **Flat overrides of builder configs** (`training/utils/omegaconf_utils.py`): a flat key for a transformer setting, such as `model.tensor_model_parallel_size=2`, is routed to `model.transformer.tensor_model_parallel_size`. This covers CLI overrides and YAML files, `process_config_with_overrides()` and the example scripts that call `parse_hydra_overrides()` directly.
  - Fields the model config declares itself stay outer, for example `model.mamba_chunk_size` and `model.seq_length`. Unknown fields still raise `OverridesError`.
  - The provider fields `model.hf_model_id` and `model.hf_model_revision` go to `model.extra_checkpoint_metadata`, where builder configs record them. The text-only Super VL card passes `model.hf_model_id=`.
  - Precedence: CLI overrides apply after the YAML file and in order, so the last one wins whichever spelling it uses. Within a YAML file, a flat key wins over its nested spelling.
  - `run_recipe.py -tp/-pp/-cp/-vp/-ep/-etp`, the Nemotron-3 Slurm examples and the other builder-backed families (GPT-OSS, Qwen2/3, ...) get the same routing.
- **HF provenance of builder configs**:
  - `get_hf_source_from_model_config()` (`training/utils/checkpoint_utils.py`) reads the source id and revision from `extra_checkpoint_metadata`, or from the provider fields.
  - HF sidecar export, PEFT adapter export, HF pretrained initialization, `also_save_hf_checkpoint` validation and `AutoBridge.from_auto_config()` use it. A replacement source still gets no revision.
  - `BridgeHybridModelConfig` and `BridgeGPTModelConfig` declare `hf_model_text_only`, and `AutoBridge.get_model_config()` sets it for a text-only source, so a restored config reopens the language projection. Muse Spark Open inherits the field instead of declaring its own.

## Behavior changes

- **Checkpoint format.** `convert.sh import` / `AutoBridge.import_ckpt` now write builder-format checkpoints (`_target_: ...BridgeHybridModelConfig`). Bridge versions before this PR cannot load them.
- **Recipe construction.** The Nano 30B pretrain and Nano 4B recipes now read `config.json` at build time, from the Hub or the cache, like the other AutoBridge recipes.

## NeMo RL

- **Provider path unchanged.** NeMo RL builds through `to_megatron_provider()`. It sets `hybrid_stack_spec` / `mamba_stack_spec` behind `hasattr`, and reads `hybrid_layer_pattern`, `experimental_attention_variant` and `multi_latent_attention` with `getattr`.
  - All provider fields are unchanged (see Verification), and no provider field declaration changed.
  - `hybrid_stack_spec` resolves as before, and `mamba_stack_spec` exists on neither `main` nor this branch.
  - The one new effect: `to_megatron_provider()` now logs the builder-deprecation `FutureWarning` for Nemotron-H, as for the other migrated families.
- **Checkpoint-format caveat.** NeMo RL's `checkpointing.pretrained_checkpoint` loader (format `megatron_bridge`) cannot load builder-format checkpoints today. It calls `.provide()` and `register_pre_wrap_hook()`, which `BridgeHybridModelConfig` lacks. Not affected: checkpoints imported before this change, and NeMo RL's own HF conversion. The fix belongs in NeMo RL.
- **Nightly.** NeMo RL's nightly for this family, `tests/test_suites/llm/grpo-nano-v2-12b-1n8g-megatron.sh`, was not run for this PR.

# Additional Information

- Part of the incremental provider → builder migration.
- **#5265 (Nemotron-H Puzzle).** `NemotronHPuzzleBridge` subclasses `NemotronHBridge` and sets its per-layer MoE fields only in `provider_bridge()`. It would inherit this PR's opt-in, so conversion and `get_model_config()` would silently drop those fields. It must either opt out (`MODEL_CONFIG_CLASS = None`, `USE_MODEL_CONFIG_FOR_CONVERSION = False`) or map the fields in `hf_config_to_model_config_kwargs()`. Its `super().provider_bridge()` call still works. There are no new textual conflicts; #5265 already conflicts with `main`.
- Other open PRs on these files:
  - #6095 (draft) conflicts in the `provider_bridge()` region that this PR replaces.
  - #6565 and #6373 each have a one-line import conflict in a test file.
  - #4890 re-adds the local-attention block in `hybrid_provider.py`.
  - #5406 replaces the `parse_hydra_overrides()` call in `process_config_with_overrides()` with its own helper. Merged as is after this PR, it would bypass the flat-override routing, so the routing would need to move into that helper.
  - The sibling migration PRs (#6592, #6593, #6594, #6598, #6552) merge cleanly, and the `provider_bridge()` change gives them the same result as `main`.
