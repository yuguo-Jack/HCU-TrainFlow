# perf(recipe): default GB200 and VRNVL72 MoE perf recipes to NCCL EP and grouped tensors

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6373) · state: open · merged: False

## Original PR description

# What does this PR do ?

This PR moves MoE perf recipes on GB200 and VRNVL72 from the HybridEP flex dispatcher to NCCL EP, with `moe_use_grouped_tensor=True`. It follows #6171 (GB300) and #6261 (GPT-OSS 120B GB200 MXFP8). The VRNVL72 switch is there to measure NCCL EP's impact on that platform.

# Changelog

Every switched recipe calls `_enable_ncclep` and sets `moe_use_grouped_tensor=True`. Its inline environment sets `NCCL_EP_HT_EM_PULL_PUSH=1` in place of the HybridEP topology names. `NVTE_ALLOW_NONDETERMINISTIC_ALGO=0` stays on the DeepSeek recipes. Parallelism, precision, recompute, CUDA graph mode and comm overlap are unchanged.

## GB200: 14 recipes

| Family | Recipes |
|---|---|
| DeepSeek V3, 256 GPUs | BF16, MXFP8, NVFP4, MXFP8 large-scale |
| DeepSeek V4 Flash, 128 GPUs | MXFP8 |
| Nemotron 3 Super, 64 GPUs | BF16, MXFP8, NVFP4 |
| Nemotron 3.5 Lightning, 8 GPUs | BF16, MXFP8 |
| Qwen3 235B-A22B, 256 GPUs | BF16, MXFP8, NVFP4, MXFP8 large-scale |

- Each switched recipe applies the NCCL EP overlay itself; none inherits it from a HybridEP sibling. Where a switched recipe and a HybridEP recipe derive from the same parent:
  - DeepSeek V3 NVFP4 builds on a new shared HybridEP base, `_build_deepseek_v3_gb200_bf16`.
  - DeepSeek V4 Flash: the GB300 recipe now builds on the new HybridEP base `_build_deepseek_v4_flash_gb200_fp8mx` instead of the GB200 recipe. GB300 and the B300 recipe derived from it keep HybridEP; the VRNVL72 recipe switches explicitly (below).
  - Nemotron 3.5 Lightning BF16 still derives from the Nemotron 3 Nano BF16 recipe, which stays on HybridEP, and switches explicitly.
  - The MXFP8 large-scale proxies inherit the switch from their 256-GPU MXFP8 recipes; only their environment changes.
- Nemotron 3 Ultra MXFP8 and NVFP4 now run NCCL EP through `main` (#6228, #6468), so this PR no longer changes them.

## VRNVL72: 27 recipes

| Family | Recipes |
|---|---|
| DeepSeek V3 | 128 and 256 GPUs: BF16, MXFP8, NVFP4. 64-GPU and 4-GPU proxies: MXFP8, NVFP4 |
| DeepSeek V4 Flash, 128 GPUs | MXFP8 |
| GPT-OSS 120B, 64 GPUs | MXFP8 |
| Nemotron 3 Super, 64 GPUs | BF16, MXFP8, NVFP4 |
| Nemotron 3.5 Lightning, 8 GPUs | BF16, MXFP8 |
| Qwen3 235B-A22B, 256 GPUs | BF16, MXFP8, NVFP4 |
| Qwen3 30B-A3B, 8 GPUs | BF16, MXFP8, NVFP4 |
| Qwen3.5-VL | 35B on 8 GPUs and 397B on 64 GPUs: BF16, MXFP8 |

- The overlay is applied in the VRNVL72 recipes themselves; the GB300 recipes and the shared HybridEP builders they start from are unchanged.
  - In the 128-GPU DeepSeek V3 MXFP8 recipe the switch comes after `_enable_deepseek_full_iteration`, which would otherwise select HybridEP again.
  - The DeepSeek V3 proxies inherit the switch from their 256-GPU parents and restate the same environment.
- The Qwen3.5-VL 35B and 397B MXFP8 recipes drop HybridEP-only settings that NCCL EP does not read: `moe_permute_fusion_into_hybridep`, `moe_hybridep_num_sms_preprocessing`, and the 397B recipe's HybridEP dispatch and preprocessing chunk sizes. Their dispatch-backward/expert-wgrad overlap stays.
- Not switched, and identical to `main`:
  - Recipes outside the tracked VRNVL72 benchmarks stay on HybridEP: GPT-OSS 20B, Kimi K2, Nemotron 3 Nano, the FP8-CS recipes (DeepSeek V3 and Qwen3.5-VL) and Qwen3.5-VL 122B.
  - GPT-OSS 120B BF16 stays on `alltoall`, like its GB300 recipe.
  - Nemotron 3 Ultra MXFP8 and NVFP4 were already on NCCL EP.

# Scope

- **GB200:**
  - When this PR was opened, nemo-ci benchmarked 22 GB200 MoE recipes, all on HybridEP. `main` has since moved Nemotron 3 Ultra MXFP8 and NVFP4 to NCCL EP, and this PR switches 14 more.
  - DeepSeek V4 Flash MXFP8 is switched without GB300 precedent; #6171 removed its GB300 switch as unverified.
  - Left on HybridEP, although their GB300 counterparts run NCCL EP: Kimi K2 MXFP8, Nemotron 3 Nano BF16/MXFP8, and Qwen3 30B-A3B 8-GPU BF16/MXFP8 and 32-GPU BF16.
  - GPT-OSS 120B BF16 stays on `alltoall`, as on GB300.
  - GB200 recipes without a nemo-ci benchmark are not touched.
  - `deepseek_v3_pretrain_256gpu_gb200_fp8mx_partial_cg_dev_config` stays on HybridEP deliberately: it offloads `expert_fc1` with EP overlap, and MCore rejects that combination under `ncclep`.
- **VRNVL72:**
  - Only the tracked benchmarks switch; the rest stay identical to `main`.
  - Some switched recipes have no NCCL EP counterpart on GB200 or GB300: Qwen3 30B-A3B NVFP4, Qwen3.5-VL 35B MXFP8, and Qwen3.5-VL 397B BF16 and MXFP8.
  - DeepSeek V4 Flash's only NCCL EP run so far, on GB200, hit the determinism error below.
  - SM budgets come from the HybridEP recipes. Megatron-Core routes `moe_hybridep_num_sms` to `moe_flex_dispatcher_num_sms`, which NCCL EP uses: 32 SMs for most recipes and 16 for Nemotron 3.5 Lightning.

# DeepSeek determinism setting

- In nemo-ci, DeepSeek V4 Flash GB200 on NCCL EP failed in the first backward pass with TE's `Deterministic execution was requested (NVTE_ALLOW_NONDETERMINISTIC_ALGO=0 …), but the scale gradient (dprob) is accumulated with nondeterministic atomics` error.
- **Correction to an earlier version of this description: the error is not specific to NCCL EP.**
  - TE raises it in the op-fuser fused grouped MLP (`ops/fused/grouped_mlp.py`) for routed experts whenever `NVTE_ALLOW_NONDETERMINISTIC_ALGO=0` is set and the cuDNN frontend has no deterministic dactivation.
  - Megatron-Core passes the routing probabilities into that MLP the same way for HybridEP and NCCL EP.
  - The check arrived with TE #3407 (2026-09-04), so the recipe's HybridEP golden most likely ran on an older container.
- Any DeepSeek recipe that uses the op fuser and pins `=0` can therefore hit this error on a recent container, whatever its dispatcher. That includes `main`'s GB200 HybridEP DeepSeek V3 MXFP8/NVFP4 recipes. On `main`, the GB300 DeepSeek V3 recipes no longer pin the setting, apart from the dedicated deterministic recipe.
- **This PR keeps `NVTE_ALLOW_NONDETERMINISTIC_ALGO=0` on the GB200 and VRNVL72 DeepSeek recipes, as on `main`**, so the dispatcher stays the only difference from the HybridEP baselines.
- On a container where TE raises this error, the DeepSeek recipes that use the op-fuser grouped MLP fail in the first backward pass on either dispatcher:
  - GB200: DeepSeek V3 MXFP8, NVFP4 and MXFP8 large-scale, and DeepSeek V4 Flash.
  - VRNVL72: DeepSeek V3 128-GPU MXFP8, 256-GPU MXFP8 and NVFP4, the four proxies, and DeepSeek V4 Flash.
- On VRNVL72, the Nemotron 3.5 Lightning recipe notes that the Rubin image lacks TE #3273 (2026-08-31), which would put it before this check. That is unverified.

  - The functional test `test_perf_config_integration.py` was updated but could not run locally, because it also needs HF configs.
- All 29 VRNVL72 NCCL EP recipes build offline and pass Megatron-Core's NCCL EP constraints:
  - none uses drop-and-pad;
  - the static-capacity recipes have the op fuser, grouped GEMM and `NVTE_CUTEDSL_FUSED_GROUPED_MLP=1`;
  - none combines A2A overlap with `expert_fc1` offload.
  - Rubin reports compute capability 10.7, which Bridge's NCCL EP hardware check accepts.
- nemo-ci GB200 runs so far. These used the container's Megatron-LM, not Bridge's pin.
  - **Nemotron 3.5 Lightning, 8 GPUs, ran on NCCL EP.**
    - BF16: 841.4 vs 791 TFLOP/s/GPU, +6.4%. That exceeds the ±5% gate, so the golden needs a refresh.
    - MXFP8: 896.7 vs 877.3, +2.2%.
  - **No data yet for the 64–256-GPU runs:** DeepSeek V3 BF16/MXFP8/NVFP4, Qwen3 235B BF16/MXFP8/NVFP4 and Nemotron 3 Super MXFP8/NVFP4.
    - They failed before training, at the TCPStore rendezvous. One or two nodes were still in nemo-ci's per-node ntrace install, which compiles a CUPTI backend and waits up to 900 s, longer than the 600 s store timeout.
    - The missing ranks never reached Bridge code, so this is unrelated to the change.
  - **DeepSeek V4 Flash:** the determinism error above.
  - **Dropped from this PR after measurement on NCCL EP:**
    - GPT-OSS 120B BF16 measured 543.6 vs 581 TFLOP/s/GPU (−6.3%) against its `alltoall` golden.
    - Qwen3 30B-A3B 8-GPU measured +2.4% (BF16) and +1.9% (MXFP8).
- Nothing has run on VRNVL72 yet.
