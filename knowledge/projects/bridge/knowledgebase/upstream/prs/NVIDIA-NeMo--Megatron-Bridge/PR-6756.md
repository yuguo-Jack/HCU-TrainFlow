# fix(model): compute multimodal RoPE angles elementwise instead of with a matmul

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6756) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Computes the RoPE angles with an elementwise product instead of a K = 1 matmul in six rope modules, so they stay exact when TF32 is allowed for fp32 matmuls.

Currently, these modules compute the angles `position * inv_freq` as an fp32 matmul with K = 1. Although technically correct, cuBLAS can run this matmul, under certain conditions, in TF32. That is allowed, for instance, by default in NVIDIA containers such as `nvcr.io/nvidia/nemo:26.04` (`TORCH_ALLOW_TF32_CUBLAS_OVERRIDE=1`), or whenever `torch.backends.cuda.matmul.allow_tf32 = True` or `torch.set_float32_matmul_precision("high")`. TF32 keeps only 11 significant bits, so positions above 2048 become multiples of 2, 4, ..., every `inv_freq` value carries errors, and the angles in the fast channels end up off by radians.

Whether the TF32 kernel is used depends on the problem shape, a cuBLAS heuristic, so the same model can be exact at one sequence length or batch size and wrong at another. On B300 (cuBLAS 13.4), the Qwen3-VL rope module, which Qwen3.5 also uses, runs in TF32 whenever seq_len is above a few hundred and bs · seq_len is at most 10,922 tokens with Qwen3-VL's 64 frequencies, or 21,845 with Qwen3.5's 32.

A standalone repro and the measured cuBLAS heuristic are in NVIDIA/Megatron-LM#8842; Megatron-core's own `MultimodalRotaryEmbedding` (used here by Qwen2.5-VL and GLM-4.5V) gets the same fix in NVIDIA/Megatron-LM#8843.

```python
# before (Qwen3-VL)
inv_freq_expanded = self.inv_freq[None, None, :, None].expand(3, seq.shape[1], -1, 1)
seq_expanded = seq[:, :, None, :].float()
freqs = (inv_freq_expanded @ seq_expanded).transpose(2, 3)
# after
freqs = seq[..., None] * self.inv_freq
```

Elementwise computation in the latter means we reach torch kernels, and not cublas. Output is bit identical to the current code with TF32 off. It is also faster (not the aim of this PR): the Qwen3-VL rope forward with the Qwen3.5 config on B300 takes 47.0 µs instead of 56.2 µs at 32,768 positions, and 46.7 µs instead of 63.8 µs at 131,072.

# Changelog

- `models/qwen_vl/modelling_qwen3_vl/rope.py`, `Qwen3VLMultimodalRotaryEmbedding` (Qwen3-VL, Qwen3.5-VL, and the Qwen2.5-Omni / Qwen3-Omni thinkers): the change above.
- `models/ernie_vl/modeling_ernie45_vl/model.py`, `ErnieMultimodalRotaryEmbedding` (ERNIE-4.5-VL): same change. It subclasses Megatron-core's `MultimodalRotaryEmbedding` but overrides `forward`, so the Megatron-LM fix does not reach it.
- `models/exaone/exaone45/modelling_exaone45/rope.py`, `Exaone45MultimodalRotaryEmbedding` (EXAONE 4.5): same change.
- `diffusion/models/common/nemotron_labs_diffusion_attention.py` (`Ministral3RotaryEmbedding`, Nemotron-labs diffusion) and the vendored HF modeling code in `models/bailing/modeling_bailing_moe_v2.py` and `models/qwen3_asr/hf_qwen3_asr/modeling_qwen3_asr.py`: the line from [huggingface/transformers#49265](https://github.com/huggingface/transformers/pull/49265), `freqs = position_ids[..., None].float() * self.inv_freq.to(device=x.device, dtype=torch.float)`.
- New tests `test_qwen3_vl_rope_angles_exact_when_tf32_allowed` (Qwen3-VL rope module with the Qwen3.5 config, 32 frequencies) and `test_angles_exact_when_tf32_allowed` (ERNIE-4.5-VL, 64 frequencies): each runs the module with TF32 allowed and not allowed, compares with an fp64 reference, and requires both outputs to be identical.

Test results:
| `TORCH_ALLOW_TF32_CUBLAS_OVERRIDE` | this PR | current `main` |
|---|---|---|
| 1 (container default) | 58 passed | new tests fail at Qwen3-VL 4,096 / 16,384 / 21,845 and ERNIE 4,096 / 10,922, plus the existing `test_qwen3_vl_text_rotary_embedding` (see note); the other 52 pass |
| 0 | 58 passed | same 5 new-test failures |

I also ran all six modules directly on B300 at 2,048 to 80,000 positions. With TF32 allowed, the current code is wrong in each of them for some of these sizes (up to 41 rad in the angles, or 2.0 in cos/sin); with this PR each returns the same bits with TF32 on or off.

Only measured on B300. On GPUs where cuBLAS picks the exact (i.e. non-TF32) kernel for these shapes, the new tests would also pass on current `main`.

Note: in the container default (override 1), the existing HF-parity test `test_qwen3_vl_text_rotary_embedding` also fails on current `main` on B300, and passes with this PR. Its positions are below 1,024, so the error there comes from TF32 rounding `inv_freq`, which is enough to exceed the test 1e-4 tolerance.
