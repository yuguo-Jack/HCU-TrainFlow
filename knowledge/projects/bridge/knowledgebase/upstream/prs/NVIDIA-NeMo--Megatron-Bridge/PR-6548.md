# fix(recipe): use HybridEP and TileLang DSA in GLM-5.2 H100 recipes

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6548) · state: open · merged: False

## Original PR description

# What does this PR do ?

Makes the four GLM-5.2 H100 library recipes run on H100 in containers built from `docker/Dockerfile.ci`: they switch from DeepEP to the HybridEP MoE dispatcher and from the cuDNN DSA backend to the TileLang DSA kernels.

# Changelog

- `glm52_pretrain_416gpu_h100_bf16_config`, `glm52_sft_416gpu_h100_bf16_config`, `glm52_sft_608gpu_h100_bf16_200k_config` and `glm52_peft_208gpu_h100_bf16_config`:
  - `moe_flex_dispatcher_backend`: `deepep` → `hybridep`, with `NUM_OF_HYBRID_EP_RANKS_PER_NVLINK_DOMAIN=8`, `NVLINK_DOMAIN_SIZE=8` and `USE_MNNVL=0`. These are the H100 HybridEP settings the performance launcher and the Nemotron-3 H100 recipes already use.
  - `dsa_kernel_backend`: `cudnn` → `tilelang`.
  - `dist.distributed_timeout_minutes`: default (10) → 120.
  - Launch the library SFT recipe as `glm52_h100_sft_config`. The bare name `glm52_sft_416gpu_h100_bf16_config` selects the same-named benchmark recipe, which this PR doesn't change.
- The module docstring covers three runtime notes: the long first step, that `TMPDIR` must allow executing files (TileLang compiles its kernels there), and that deterministic mode is not bit-exact with TileLang.
- Unit tests assert the dispatcher, its environment variables, the DSA backend and the timeout.

**Why**

- The cuDNN DSA backend runs FlashMLA, which `docker/Dockerfile.ci` builds without sm_90 kernels (`FLASH_MLA_DISABLE_SM90=1`). On H100 the first forward pass fails with `no kernel image is available for execution on the device`.
- DeepEP's own internode test (`tests/test_internode.py`, 2 nodes) timed out with `DeepEP error: timeout (dispatch CPU)` on the two InfiniBand H100 clusters I tested with current containers, with and without NCCL network-plugin overrides. I haven't found the root cause. HybridEP's own 2-node test passes on the same clusters.
- HybridEP and TileLang compile their kernels in every process during the first step, one pipeline stage after another.
  - With 11 stages, the longest single wait was about 30 minutes, or about 50 on a busy cluster. Each extra stage adds about 2.5 minutes (4.5 on a busy cluster).
  - That comes to about 35 and 50 minutes for these recipes' 13 and 19 stages, or 60 and 85 on a busy cluster, so the 10-minute default kills step 1.
  - The 120-minute timeout applies to every collective for the whole run, so a real hang after step 1 also takes up to two hours to surface.
  - `dist.distributed_timeout_seconds_after_init` could lower it after the first step. None of the runs below exercised it, so this PR doesn't set it.

Routing, losses, optimizer and data are unchanged; only the MoE token transport and the attention kernels change. TileLang's DSA backward kernels accumulate with floating-point atomics, and Megatron-Core's determinism manifest exempts them. Even with `--deterministic`, gradients can differ between identical runs, and so can every loss after the first step. Exact-match comparisons therefore won't hold beyond a resumed run's first step.

**Validation** (H100 80GB, a 26.10 NeMo Framework container build)

Kernel parity, TileLang backend against Megatron-Core's native reference:

- Megatron-Core `8442db19`, 1 GPU: `test_fused_absorbed_mla_dsa_matches_native[*-tilelang]`, 8/8 pass. These cases use sequence lengths 1024 and 2048 with index top-k 2048, so every causal key is selected.
- Megatron-Core `ce852bfb`, 1 GPU: the same helper (`run_absorbed_mla_dsa_parity`) at sequence length 4096, where top-k 2048 actually drops keys, 4/4 pass (dense and sparse indexer loss, with and without per-token loss).
- Megatron-Core `ce852bfb`, 4 GPUs: `test_dsa_backend_tp_sp_parity.py -k tilelang`, 5/5 pass on every rank. These cover packed THD sequences with all-gather CP2, TP2 with sequence parallelism, index top-k 64, and the shared-indexer and skip-layer variants. The tests are marked flaky only because their cuDNN variants fail in CI.
- Megatron-Core `ce852bfb`, 1 GPU: `test_dsa_tilelang_kernels.py`, 37 passed.

End to end on 352 H100s (44 nodes × 8, InfiniBand) with Megatron-Core `8442db19`:

- **Setup.** `8442db19` is two pins before `main`'s `ce852bfb`. The 13 Megatron-Core commits in between don't touch DSA attention or MoE dispatch. They do include NVIDIA/Megatron-LM#8142 (embedding weight-gradient accumulation into `main_grad`), NVIDIA/Megatron-LM#8180 (deterministic-mode NCCL settings) and NVIDIA/Megatron-LM#6981 (GPT dataset loss-mask caching). This run was not repeated at `ce852bfb`.
- **Command.** The H100 pretrain command from the earlier GLM-5.2 verification card (100 steps, `--deterministic`, sequence length 2048, PP11, EP32, GBS 1024) on this branch's pretrain recipe, launched with `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` as in #6295. The run predates two details of the final commit: it passed `model.dsa_kernel_backend=tilelang` on the command line, and its timeout was 90 minutes.
- **Health.** 100/100 steps; every loss and grad norm finite; 0 skipped and 0 NaN iterations; no errors. TileLang and HybridEP compiled their kernels on all 352 ranks.
- **Reference comparison.** The same command with the unfused PyTorch DSA path (`dsa_kernel_backend=none`, which needs CP2 to fit) is a reference implementation. Over steps 1–5 the two runs agree within 0.06% on LM loss, 0.4% on grad norm and 0.04% on MTP loss.
- **Early loss spike.** Both runs then go through the same spike: LM loss 33.2 vs 32.6 at step 7 and 44.8 vs 47.4 at step 10. It appeared in every run of this from-scratch command that I have step-by-step logs for, including earlier runs with the all-to-all dispatcher and the cuDNN backend.
- **Divergence after the spike.** The runs recover and drift apart: step 100 is 6.199 with TileLang and 6.621 with the unfused path. These sit on either side of the card's earlier record (13.159 → 6.385), so the end-of-run loss can't distinguish implementations at this horizon.
- **Speed.** Steps 91–100 averaged 35.0 s/step, about 12% slower than the card's earlier record (31.2 s/step with DeepEP and the cuDNN backend on an older container). Steps 2–5 averaged 22.2 s; step time rises after the spike in both runs, most likely because routing becomes imbalanced. TFLOP/s/GPU isn't comparable between the two stacks.
- **Memory and first step.** Peak PyTorch-allocated memory was 56.5 GB; that figure excludes NCCL, HybridEP and TileLang buffers. Step 1 took about 49 minutes, almost all of it kernel compilation.

Checks on this commit with Megatron-Core `ce852bfb` (one H100 node):

- `tests/unit_tests/recipes/test_glm5_recipes.py` and `tests/unit_tests/recipes/test_glm5_perf_recipes.py`: 30 passed. The updated H100 tests fail against the recipes on `main` (8 failures).
- All four recipes build with the real GLM-5.2 provider and pass `finalize()`, which includes Megatron-Core's TileLang dependency check.
- `pre-commit run --all-files` passes.

**Not covered yet**

- No end-to-end runs of the SFT, 200K SFT and PEFT recipes, or of the pretrain recipe's native 416-GPU layout (PP13, sequence length 4096).
- When a TileLang hook declines a layout, Megatron-Core silently falls back to the unfused PyTorch path and logs the decline only at DEBUG (`megatron.core.transformer.experimental_attention_variant.dsa_kernels`). Enable that logger for the first SFT, 200K SFT and PEFT runs.
  - At 200K the fallback cannot fit and would fail with an out-of-memory error; at 2K it would only be slower.
  - The TileLang indexer's memory use at 200K is untested.
- The H100 benchmark recipes in `perf_recipes/glm_moe_dsa/h100/glm5.py` still use DeepEP and the cuDNN DSA backend.
- Building FlashMLA with sm_90 kernels in `docker/Dockerfile.ci` would bring back the cuDNN DSA backend on H100; that would be a separate change.
