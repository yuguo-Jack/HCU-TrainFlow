# feat(quant): export quantized GatedDeltaNet input projections to HF

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6714) · state: closed · merged: True

## Original PR description

# What does this PR do ?

`save_hf_pretrained_modelopt` / `export_hf_weights_modelopt` (#6657, #5812) now export a quantized GatedDeltaNet `in_proj` (Qwen3.5 / Qwen3.6) instead of raising `NotImplementedError` for `GDNLinearMappingSeparate`. The output matches ModelOpt's `export_mcore_gpt_to_hf` bit for bit.

Part of #4804 (PR 4 of its plan, the Qwen3.6-35B-A3B pilot); tracked as OMNIML-5977.

# Changelog

- `in_proj_qkv` and `in_proj_z` are exported packed with their scales. Their rows come from the mapping's own split (`split_gdn_linear_weights` + `_split_gdn_grouped_to_separate`) applied to row indices, so the scales follow the same TP layout as the weights.
- `in_proj_b` and `in_proj_a` (the beta / alpha gates) are written in BF16 and listed in `quantization_config.ignore`. Megatron fuses them into the one quantized `in_proj`, so a recipe can't exclude them with a quantizer pattern; ModelOpt's exporter keeps them in BF16 the same way.
- The ModelOpt export hook passes outputs whose export spec is explicitly `None` through unchanged, instead of failing.

# Tests

- Unit: the GDN state selection recovers every HF row of a Megatron `in_proj` built with `merge_gdn_linear_weights` at TP1 and TP2, and leaves the gates unquantized; the export hook passes unquantized outputs through. Both fail without this change.
- Functional (L0, 2 GPUs): `test_modelopt_hf_export.py` adds a toy Qwen3.5 (one GatedDeltaNet and one full-attention layer) in NVFP4: TP2 and PP2 write the TP1 checkpoint bit for bit, and `ignore` lists exactly the embedding, LM head, `conv1d`, `in_proj_a` and `in_proj_b`. The export script keeps `conv1d` unquantized, as ModelOpt's recipes do.

Run in `nvcr.io/nvidian/nemo:26.10.rc9` with this branch overlaid:

- With nvidia-modelopt 0.48.0rc1 (this repo's pin): `tests/unit_tests/models/test_modelopt_utils.py` (78 passed) and `test_modelopt_hf_export.py` (4 passed, including the new Qwen3.5 case).
- With ModelOpt main: ModelOpt's `tests/gpu_megatron/torch/export/test_quantized_mbridge_export.py` (NVIDIA/Model-Optimizer#3066) extended to a tiny Qwen3.5-VL-MoE with every linear layer quantized, NVFP4 and FP8: the bridge export at TP2 matches `export_mcore_gpt_to_hf` at TP1 bit for bit (weights, scales, `config.json`, `quantization_config`; FP8 `input_scale` within 2% at TP2). Once this merges, I'll bump ModelOpt CI's Megatron-Bridge commit and switch that test's Qwen3.5-VL case from NVFP4 MLP-only to full NVFP4.

Not covered here: KV-cache export (waits for the nvidia-modelopt 0.49.0rc0 pin), Qwen3-Next's `GDNLinearMapping`, and Mamba (`MambaInProjMapping`, OMNIML-5978).

- mxinO · comment · 2026-10-28T22:23:10Z · [source](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6714#issuecomment-6482190589)

Why do we leave the alpha/beta projections in BF16 here? ModelOpt fake-quantizes the entire fused Megatron `in_proj`, including those rows and their input, but export writes the raw gate weights and marks them unquantized. That seems to introduce a fake-quant/inference mismatch. I see the existing ModelOpt exporter does the same, but could we clarify the reason?

- kevalmorabia97 · comment · 2026-10-29T08:28:21Z · [source](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6714#issuecomment-6491782324)

Good catch. The gates stay in BF16 so the exported checkpoint matches what ModelOpt produces for HF PTQ and what serving expects:

- ModelOpt's recipes disable `*linear_attn.in_proj_a*` / `*linear_attn.in_proj_b*` (`default_disabled_quantizers.yaml`, NVIDIA/Model-Optimizer#1381 and #1687), and the published `nvidia/Qwen3.6-35B-A3B-NVFP4-QAD` lists them in `exclude_modules`. vLLM fuses them into one `in_proj_ba` with only 2 × `linear_num_value_heads` rows (64 for Qwen3.6-35B-A3B, fewer per TP rank). That's too narrow for the FP4 kernel tiles (#1687 hit `size_n ... not divisible by tile_n_size = 64`), and it's 0.5% of `in_proj`, so quantizing it gains nothing.
- Megatron fuses all six sections behind one `weight_quantizer`, so a quantizer pattern can't exclude the gates there. Both `export_mcore_gpt_to_hf` and this PR drop them at export instead.

You're right that this leaves a mismatch: Megatron fake-quantizes those rows, and the export doesn't. Its effect is limited:

- Calibration is unaffected. Max calibration collects amax with quantization off, and the `in_proj` input amax is shared, so `in_proj_qkv` / `in_proj_z` get the same `input_scale` either way.
- The deployed gates are more precise than what was simulated. So a Megatron-side fake-quant eval is slightly pessimistic, and QAT trains these rows under noise that the export then removes. Neither should cost accuracy.

The proper fix is for ModelOpt's Megatron GDN support to leave those rows unquantized during fake quant, so simulation matches export. That's a ModelOpt change, so I'll track it there as a follow-up rather than in this PR.
