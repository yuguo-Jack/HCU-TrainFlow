# fix(recipe): resync native DeepSeek V4 pipeline layout after overrides

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6248) · state: open · merged: False

## Original PR description

## What does this PR do?

DeepSeek V4's native Hybrid provider materializes its pipe-separated layer pattern and flexible pipeline layout before the shared recipe runner applies CLI topology overrides. Because the provider does not implement the runner's layout-builder hook, overriding PP or VP can leave the old segmentation attached to the new topology.

Register that mutating hook on `DeepSeekV4ModelConfig`, which the DSv4 recipes build since #6672, and on `DeepSeekV4HybridModelProvider`. Both call shared helpers in `deepseek_v4_hybrid_provider.py` that reuse `set_deepseek_v4_pipeline_model_parallel_layout`. The runner now rebuilds the native attention/MoE segments, keeps the MTP suffix, and places embedding and loss stages for the requested topology.

The hook updates `hybrid_layer_pattern` in place as well as PP/VP and `pipeline_model_parallel_layout`. It strips the prior pipe separators and redistributes logical attention/MoE pairs with that helper's default split (even, except that the first stage grows to hold the hash-routed MoE layers, per #6689), so a topology override intentionally replaces any recipe-specific uneven allocation. The MTP suffix is preserved. If the CLI explicitly sets `model.pipeline_model_parallel_layout`, the shared runner skips this hook; the caller must also supply consistent native pattern segmentation.

Paths that change PP/VP without the hook are now rejected instead of building part of the model. MCore selects pipe segment `vp_stage * PP + pp_rank` and only checks that the segment count divides by PP, so stale segments build part of the decoder without an error: on a 43-block Flash-shaped pattern, PP4 segments used at PP1 build 22 of 86 layers, and PP8 segments used at PP4 build 46 of 86. The builder config's `validate()` and the provider's `finalize()` now require a `|`-segmented pattern to have one segment per PP x VP stage and an explicit layout to place the same number of decoder layers on each stage as the matching segment. Patterns without `|` keep MCore's even split. This covers an explicit CLI layout, Python code that edits PP/VP on a recipe, and the two DSv4 functional tests, which set PP=1 on PP4 recipes and now rebuild the segments first. The DSv4 example README describes the override behavior.

## Validation

- Added regression coverage for a Flash-shaped 43-block pattern changing from an uneven PP8 allocation to PP1, PP4, and PP4/VP4 through the actual public runner synchronization function. It checks layer order, stage counts, MTP suffix, and embedding/loss placement.
- A supplemental CPU proof of the production provider/layout/runner function bodies reproduces all three original failures and passes all three candidate cases, plus two deepcopy checks.
- Repository pre-commit hooks and `git diff --check` pass.
- Fresh native pytest passed all 12 layout tests on one GB300 using the normal repository conftest and production imports (Bridge `c3a0b3e28a9d`, MCore `58f5e938bdf3`; Torch `2.13.0a0+8145d630e8.nv26.06`, CUDA 13.3, Transformer Engine `2.17.0+2e559f06`). All setup, call, and teardown phases passed, with no skips or xfails. The earlier CPU-only import attempt was blocked by unavailable `triton`.
- The shared GPU job and all native steps completed with exit 0; the final evidence audit passed, including unchanged source and dependency snapshots before and after execution. Retained stderr contains only the previously identified Torch weakref shutdown UTF-8 cleanup traces after successful tests. This validates the layout/configuration tests, not model execution across the tested topologies or CI parity.

- Follow-up: 18 layout tests pass in the NeMo container with the pinned MCore (with the recipe, runner, and hardware-recipe suites: 110 passed), both on this branch and merged with current main and its newer MCore pin. The five new rejection tests fail on the previous head ("DID NOT RAISE"). The two functional tests need the DSv4 toy checkpoint and were not run locally; CI runs them.

- Rework for #6672 (`55cb15e`): merged current main and moved the hook and segment check onto the builder config. New unit tests run the runner sync function on a `DeepSeekV4ModelConfig` from `get_model_config()` at PP1, PP8 and PP4/VP2, and check stale segments, a disagreeing list layout and a command-line layout string. Ruff passes. The GB300 results above predate this rework; it is covered by CI only.

This is independent of the older non-Hybrid proposal #5457 and the legacy inference lifecycle fix #5985: it connects the native Hybrid provider to the shared training recipe runner's existing override contract.

## Scope

Only DSv4 config- and provider-owned topology synchronization and validation, the DSv4 example README, and tests change. This does not establish support for every PP/VP combination or change numerical kernels, dependencies, checkpoint formats, or recipe defaults.
