# fix(peft): reject nonzero warmup initialization for LoRA+

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6464) · state: closed · merged: True

## Original PR description

Reject nonzero `SchedulerConfig.lr_warmup_init` when matching LoRA+ adapter-name overrides produce different A/B learning-rate bounds. Previously, a requested ratio of 16 became 1, 12.54, 14.64 and 15.52 during warmup. The guard raises before optimizer construction and directs callers to zero warmup initialization or ratio 1.

The check combines matching name patterns using MCore's override merger and inherits omitted bounds from the optimizer defaults. It covers unilateral overrides, tuple names and names accompanied by attributes. It compares representative adapter names without inspecting rank-local parameters; attribute/predicate-only rules and module-specific name patterns are outside this check. Only the guard and regression tests change.

Validation:
- All 98 focused optimizer tests pass and cover supported configurations, alternate factories, equivalent named overrides, inherited bounds, broad/shared patterns and native conflict handling.
- In the same runtime environment, all three reported forms bypass the previous guard and reproduce incorrect warmup rates; the updated guard rejects them before construction.
- Ten real-model cases per version exercise a two-layer GPT with 8 A/8 B tensors. Supported controls run 12 training steps with finite losses/gradients/weights, unchanged frozen weights and Adam-reference comparisons. Direct adapter/optimizer/scheduler state restoration is compared with uninterrupted execution.
- All-file pre-commit, diff checks and targeted type checking pass.

Separately, sparse versus explicit overrides with equal effective bounds expose a pre-existing MCore optimizer-state restore collision on unchanged source. This change does not fix that restore behavior. Full checkpoint-manager integration and explicit scheduler overrides are outside the validation scope.

- svcnvidia-nemo-ci · comment · 2026-10-14T22:34:19Z · [source](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6464#discussion_r4277011479)

File: `src/megatron/bridge/training/optim.py` · line None

**Blocking — compare effective bounds rather than optional dictionary entries.**

**Failure:** With `optimizer_config.lr=3e-4`, `min_lr=3e-5`, and nonzero warmup initialization, a provider returning the following overrides now raises the LoRA+ `ValueError`:

```python
{
    ParamKey(name="*.linear_in.weight"):
        ParamGroupOverride(max_lr=3e-4, min_lr=3e-5),
    ParamKey(name="*.linear_out.weight"):
        ParamGroupOverride(max_lr=3e-4),
}
```

Both groups have the same effective bounds: the omitted B minimum inherits the base minimum. The comparison instead sees `3e-5 != None`. The [provider contract](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/a08e9ac219e96c937db714c3d55b94bfba7d3ae6/src/megatron/bridge/training/config.py#L217-L230) permits per-group overrides, and [_get_scheduler](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/a08e9ac219e96c937db714c3d55b94bfba7d3ae6/src/megatron/bridge/training/optim.py#L556-L561) supplies the base maximum/minimum. Equal effective rates should reach optimizer construction, not be classified as an unsupported LoRA+ split. Omitting one maximum while explicitly setting the other to the base maximum has the same problem.

**Correction:** In `setup_optimizer`, resolve absent bounds against the scheduler defaults before comparing. Replace the comparison expression at this line with:

```python
and (
    lora_a.get("max_lr", optimizer_config.lr)
    != lora_b.get("max_lr", optimizer_config.lr)
    or lora_a.get("min_lr", optimizer_config.min_lr)
    != lora_b.get("min_lr", optimizer_config.min_lr)
)
```

The invariant is that omission of a bound must not itself create an A/B difference. This suggested replacement is based on source reasoning, not execution; verify it against the pinned MCore implementation before adopting it.

**Preservation:** Keep rejection before every optimizer factory for complete helper overrides with ratios `0.5` or `16` and nonzero initialization, and for explicitly different minimum rates. Keep ratio `1`, zero initialization, missing canonical keys, and attribute-qualified keys accepted. The [helper](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/a08e9ac219e96c937db714c3d55b94bfba7d3ae6/src/megatron/bridge/peft/lora.py#L75-L81) explicitly emits both fields, including minimum `0.0` when the base minimum is `None`, so these existing helper cases retain their current comparisons.

**Acceptance:** Add a proposed regression using the [existing mocked setup](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/a08e9ac219e96c937db714c3d55b94bfba7d3ae6/tests/unit_tests/training/test_optim.py#L1040-L1068): pass the mapping above with `initial_lr=3e-5`; expect no exception and one optimizer/scheduler construction. Also test an omitted maximum against an explicit base maximum. Retain the existing rejection tests' assertions that neither factory nor scheduler runs, the supported-combinations construction assertions, and the distinct-minimum rejection case.

- kamran-nvidia · comment · 2026-10-20T17:40:23Z · [source](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6464#discussion_r4328210539)

File: `src/megatron/bridge/training/optim.py` · line None

This only looks up the two exact `ParamKey(name=...)` keys, so equivalent LoRA+ setups slip through. Also, `ParamKey.matches` ORs name, attr and predicate, so adding `attr=` makes a key broader, not narrower. I ran these through the real `_get_param_groups` + `OptimizerParamScheduler` (init 3e-5, 4 warmup steps), and the guard lets all of them through:

- a B-only `*.linear_out.weight` override: ratio 1 → 257 → 303 → 323 → 333
- the name+attr keys from the test: ratio 1 → 9.9 → 10
- the helper's output re-keyed with tuple names: 1 → 12.54 → 14.64 → 15.52, i.e. the original bug

Could we match on key names instead of exact keys? Something like:

```python
def _effective_lr_bounds(param_name):
    override = combine_param_group_overrides([
        o for k, o in config_overrides.items()
        if any(fnmatch(param_name, n) for n in ((k.name,) if isinstance(k.name, str) else k.name))
    ])
    return override.get("max_lr", optimizer_config.lr), override.get("min_lr", optimizer_config.min_lr)
```

Then compare `"adapter.linear_in.weight"` against `"adapter.linear_out.weight"`. It only depends on config, so every rank still fails the same way.
