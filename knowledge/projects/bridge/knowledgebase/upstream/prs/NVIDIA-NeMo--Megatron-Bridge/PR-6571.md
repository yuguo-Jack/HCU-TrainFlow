# fix(docker): restore NeMo-FW directory traversal permissions (r0.7.0)

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6571) · state: closed · merged: True

## Original PR description

# What does this PR do?

Restore directory traversal permissions in the NeMo Framework image so unprivileged container extraction can access `/opt/NeMo-FW/stubs`.

`COPY --chmod=644` gives the copied stub directories mode `0644`. The preceding file copy also creates `/opt/NeMo-FW` with mode `0644`, so fixing only the stubs subtree still leaves it inaccessible.

# Changelog

- Copy the stubs without applying a file-only mode to directories.
- Set `/opt/NeMo-FW` and all stub directories to `0755`.
- Set regular stub files to `0644`, preserving their non-executable mode.

Primary area: `area:build`.

# GitHub Actions CI

Local validation:

- `uv run pre-commit run --all-files` passed inside the existing Framework container.
- `.github/scripts/test_docker_dependency_layers.sh` passed with the branch's pinned MCore lockfile supplied to the isolated container.
- A minimal Docker build using the changed copy/permission block verified directory mode `0755`, stub file mode `0644`, and successful traversal and file reads as UID/GID `65534`.
- The same access check failed with `Permission denied` for both the original block and a stubs-only permission repair, confirming the parent-directory fix is necessary.
- `git diff --check` passed.

A full Framework image rebuild and Enroot/Pyxis end-to-end launch were not run locally.

# Additional Information

A filesystem scan of the affected RC5 amd64 image found exactly three directories with no execute bits: `/opt/NeMo-FW`, `/opt/NeMo-FW/stubs`, and `/opt/NeMo-FW/stubs/lightning`. This patch repairs all three without changing permissions elsewhere.

Release-branch counterpart of #6570, targeting `r0.7.0` for the NeMo 26.10 image line.
