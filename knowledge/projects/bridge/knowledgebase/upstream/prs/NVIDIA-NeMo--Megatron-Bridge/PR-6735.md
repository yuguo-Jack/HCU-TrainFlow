# feat(quant): support Mamba projection ModelOpt export

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6735) · state: closed · merged: True

## Original PR description

## What does this PR do?

Support quantized Mamba projections in ModelOpt export and repeated refits. Mamba `in_proj` gathers its fused components across TP separately, so its row-based quantizer state must follow the same order as the exported weights.

## Changelog

- Reorder `in_proj` quantizer state using the existing Mamba weight mapping geometry and ModelOpt state transforms.
- Validate component geometry across TP while capturing current layout and amax values on every refit.
- Cover both `in_proj` and the existing row-parallel `out_proj` path, including FP8 and NVFP4.

## Validation

- Exporter unit tests: 88 passed.
- Native tiny Nemotron-H FP8 and NVFP4 export (initial qualification): 2 passed; TP1 output matches TP2 and PP2 bit for bit.
- NVFP4 `in_proj`/`out_proj` weights and scales match ModelOpt offline export.
- Full pre-commit checks passed. Initial strict mypy comparison has no added diagnostics relative to main (39 existing baseline diagnostics remain).

FP8 offline bit parity remains deferred until the dependency contains NVIDIA/Model-Optimizer#3005.

- kevalmorabia97 · COMMENTED · 2026-10-30T11:05:13Z · [source](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6735#pullrequestreview-5711343949)

Thanks, following `MambaInProjMapping`'s component-wise gather for the quantizer state looks right to me, and the unit test that checks it against the real `megatron_to_hf` is a good guard. I found no correctness issues at 53918325b. I have one doc gap and two suggestions to simplify:

1. **Docs still list Mamba as unsupported.** `docs/modelopt/quantization.md` says models with "Mamba layers" fall back to ModelOpt's Megatron exporter at TP=1. With this PR, Nemotron-H exports through `save_hf_pretrained_modelopt` at any TP / PP, so that example should go (KV-cache quantization still applies).
2. **`_plan_spec` covers only Mamba, and the refit path already handles geometry.** On every refit, `_capture_source_state` re-reads `mamba_layout` and `_transform_source_state` recomputes the row indices from it, so the exported weights and scales already follow the current geometry. The extra plan check only rejects a config change that the live module can't undergo without being rebuilt, and a rebuild creates a new plan anyway. QKV (heads vs. groups) and GDN can also change row meaning at the same row count, and their layouts aren't part of the plan check. I'd drop `_plan_spec` and the last block of `test_mamba_projection_plan_recaptures_weight_and_input_amax`, so `local_quantization_specs` keeps one value type. If you want the guard, store the full `_SourceState` for every task instead.
3. **Test overlap.** `test_reused_plan_recaptures_mutable_quantizer_state` already covers amax recapture on a reused plan, and `out_proj` is a plain `RowParallelMapping`, so the new plan test could keep only `in_proj`. In the functional test, FP8 has a single per-tensor scale with no row structure, so the `nemotron_h` FP8 TP2 / PP2 case mostly repeats `qwen3` FP8 TP2. The NVFP4 case is the one that exercises the row reordering. Dropping the FP8 case would save three torchrun exports per CI run.

Follow-up real-quant export/refit adapters:

- Fused QKV + gate (`QKVGMapping`, used by Step models).
- Concatenated QKV (`ConcatenatedQKVMapping`, used by several text and vision bridges).

Each needs quantizer-state transforms that follow its existing weight mapping, with TP/PP and repeated-refit coverage. These are follow-ups to the Mamba projection support in this PR.
