# refactor(model): build MiniMax-M3 from builder-backed model configs

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6739) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves **MiniMax-M3** (`MiniMaxM3Bridge`, the full vision-language checkpoint `MiniMaxM3SparseForConditionalGeneration`) from `MiniMaxM3VLModelProvider` / `MiniMaxM3ModelProvider` to builder-backed `ModelConfig` + `ModelBuilder` classes, for recipes and checkpoint conversion, and switches the two H100 text recipes to `get_model_config()`. The language model sits on `BridgeGPTModelConfig` with MiniMax-M3's custom router; the vision-language builder builds the existing `MiniMaxM3VLModel`.

# Changelog

- **Configs** (new, `minimax_m3/minimax_m3_config.py`):
  - `MiniMaxM3ModelConfig(BridgeGPTModelConfig)`: the sparse-MoE language model, built by `MiniMaxM3ModelBuilder`. The text recipes use it.
  - `MiniMaxM3VLModelConfig(MiniMaxM3ModelConfig)`: the complete model, built by `MiniMaxM3VLModelBuilder`. `MiniMaxM3VLModel` reads the vision config, the image and video token IDs, the projector shape, `spatial_merge_size` and the Lightning Indexer layout from the config it is built with, so `MiniMaxM3VLTransformerConfig` declares them. The outer config holds `hf_config_dict` (export), `temporal_patch_size`, the freeze options and `scatter_embedding_sequence_parallel=False`, with the provider's defaults.
  - `MiniMaxM3VLModelConfig.to_text_config()` returns the language-model config, as `MiniMaxM3VLModelProvider.to_text_provider()` returns the text provider.
  - The vision config is saved with its own `to_dict()` and restored with `from_dict()`. Field-by-field serialization keeps only declared fields, and with `trust_remote_code=True` every shape attribute of MiniMax-M3's vision config is undeclared (it loads as a generic `PretrainedConfig`).
- **Builders** (new, `minimax_m3/minimax_m3_builder.py`):
  - `MiniMaxM3ModelBuilder` builds the GPT language model through `GPTModelBuilder` and promotes the router weights to FP32, as the provider's pre-wrap hook does.
  - `MiniMaxM3VLModelBuilder` builds `MiniMaxM3VLModel` in the provider's order (vision tower and projectors, then the language model from `MiniMaxM3ModelBuilder`) and freezes the requested modules. Checkpoint conversion builds without `Float16Module`, which casts a provider-built model, so the builder casts the vision tower and projectors to `params_dtype` itself.
- **FP32 tensors**: the router weights and expert biases and the vision patch embedding are now also marked with Megatron Core's `mark_keep_in_fp32`, so `Float16Module` leaves them in FP32. Bridge's `build_distributed_models()` (#6731), which `AutoBridge.get_model()`, training and `load_megatron_model()` use, already restores these tensors after the cast; the marks also cover the VL builder's conversion cast and callers of a builder's own `build_distributed_models()`. The two compose: the tensors stay exact either way (tests below). Provider results are unchanged.
- **Bridge**: `MODEL_CONFIG_CLASS = MiniMaxM3VLModelConfig`, `USE_MODEL_CONFIG_FOR_CONVERSION = True`.
  - The `provider_bridge()` assignments move to `hf_config_to_model_config_kwargs()`, plus the two provider defaults the builder config does not share (`masked_softmax_fusion`, `rope_scaling_factor`). `hf_config_to_provider_kwargs()` returns the same kwargs with the provider's layer spec, `partial(minimax_m3_block_spec, use_transformer_engine=HAVE_TE)`, so the deprecated providers are unchanged; `provider_bridge()` is the base implementation.
  - `minimax_m3_block_spec` accepts a builder config. Without `use_transformer_engine` it uses the backend the transformer config selects, as Megatron Core's default GPT spec does.
  - `megatron_to_hf_config()` accepts the providers and the builder configs.
- **`MiniMaxM3VLModel`** takes keyword-only `build_language_model` and `pg_collection` arguments from the builder; providers pass neither. It reads the tie-embeddings flag from the built language model.
- **Recipes**: `minimax_m3_pretrain_256gpu_h100_bf16_config` and `minimax_m3_sft_128gpu_h100_bf16_config` build their model with `get_model_config().to_text_config()`.
- **Docs and skill**: the MiniMax-M3 example README names the text model config. `adding-model-support/llm-patterns.md` notes how to keep FP32 parameters on the builder path.
- **Tests**:
  - Builder configs and builders (`test_minimax_m3_builder.py`): the mapping without the provider path, builder vs provider on every shared field and in `megatron_to_hf_config()`, provider kwargs vs builder kwargs, the text config vs the text provider, flat overrides, `run_config.yaml` round trips for the native and the remote-code vision config, the block spec with a builder config, the FP32 router tensors under `Float16Module`'s conversion and through a distributed build (#6731's `build_distributed_models()` and the builder's own, with weights loaded before the wrap), and the builders: language-model factory and process groups, the vision cast with the FP32 patch embedding, stage flags, freezing and config rejection.
  - `MiniMaxM3VLModel`: the builder's language-model factory and process groups, the tie flag, and the patch embedding under `Float16Module`'s conversion.
  - Recipes: the stub now returns a real, strict `MiniMaxM3VLModelConfig` (so a recipe assigning an undeclared field fails) and fails on `to_megatron_provider()`. The shared offline recipe stub gains `to_text_config()`.

# Behavior notes

- **Checkpoint format:** `AutoBridge.import_ckpt` and `convert.sh import` now write builder-format checkpoints. `main` cannot load them, because the new config classes do not exist there. This branch loads `main`'s provider checkpoints (GPU results below). NeMo RL's `megatron_bridge` checkpoint loader cannot read builder-format checkpoints yet; that applies to every migrated family.
- **Layer spec:** builder configs name `minimax_m3_block_spec` itself and pick the Transformer Engine or local backend from `transformer_impl`; providers keep `partial(minimax_m3_block_spec, use_transformer_engine=HAVE_TE)`. With Transformer Engine installed and the default `transformer_impl`, both resolve to the same decoder spec.
- **Deprecation warning:** `provider_bridge()` and `to_megatron_provider()` now emit the builder deprecation `FutureWarning`, as every migrated family does. The text and VLM generation examples that configure a provider keep working.
- **Vision config in `run_config.yaml`:** builder checkpoints store it in Hugging Face's own `to_dict()` form, so a reload keeps every attribute. Provider checkpoints, unchanged here, save it field by field; with remote code it reloads without its shape attributes, and the local vision tower then falls back to defaults that happen to equal the released checkpoint's values.
- The text configs keep the vision-language config's `scatter_embedding_sequence_parallel=False`, as the text providers did. Megatron Core's `GPTModel` scatters the embeddings itself in that case, so the recipes' TP2 + sequence-parallel layout trains the same on both trees (GPU table).
