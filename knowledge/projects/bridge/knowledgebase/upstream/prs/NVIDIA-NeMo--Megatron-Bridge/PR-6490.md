# build(deps): support Transformers 5.20

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6490) · state: closed · merged: True

## Original PR description

## What
- Widen the supported Transformers range to `>=5.15,<5.21` and lock Transformers 5.20.0. The lock was regenerated with uv 0.7.2 (the `Dockerfile.ci` version), so it stays at lockfile revision 2.
- Extend two exact-release gates from #6471 that would otherwise break under the 5.20.0 lock:
  - **Nemotron 3.5 Super VL:** HF 5.20.0 still cannot load the audio-free processor natively, exactly like 5.19.0: the legacy `_downsample_factor` field is read-only, and an audio feature extractor is required. Keep using the Bridge processor adapter on 5.20.0. The verified releases now live in `_PROCESSOR_ADAPTER_RELEASES`, so the adapter's real-load tests run on the locked version instead of skipping.
  - **MiniMax M3:** vision RoPE outputs are bitwise identical between 5.19.0 and 5.20.0 (FP32/BF16/FP16, head dims 8 and 80). The unit test's native buffer-rounding branch therefore now includes 5.20.0. Without this, `test_hf_vision_rope_dtype_conversion_matches_version_contract` fails on 5.20.0.
- Support native Super VL on Transformers 5.18.0 as well. HF 5.18.0 ships the same `nemotron_h_omni` code as 5.19.0 (the module is byte-identical), and plain `AutoProcessor` fails there in the same way. The native floor drops from 5.19.0 to 5.18.0, and the adapter covers 5.18.0 through 5.20.0. The only HF `nemotron_h` change between 5.18.0 and 5.19.0 adds MoE `router_logits` outputs, which Bridge does not read.
- Read `partial_rotary_factor` from `rope_parameters` on Transformers 5.20.0, which no longer exposes it as a config attribute (details under the compatibility review). The new `partial_rotary_factor_from_hf` helper in `models/conversion/transformers_compat.py` sits next to the existing `rope_theta_from_hf`. It reads the attribute on older releases and `rope_parameters["partial_rotary_factor"]` on 5.20.0. The generic HF-to-Megatron config mapping and the GLM-4.5V bridge use it. The vendored Bailing MoE V2 attention gets the same fallback inline, because that file has to stay standalone.
- Remove the `find_spec("transformers.models.muse_spark")` skip guard from the Muse Spark Open conversion test. 5.20.0 ships the module, so a broken Muse Spark setup now fails CI instead of skipping silently.
- Update the MiniMax M3 and Super VL docs and their nightly fern pages to match.

## Lockfile delta
```
Updated transformers v5.19.0 -> v5.20.0
```
No other package moved. The locked tokenizers 0.23.3 and huggingface-hub 1.33.0 satisfy Transformers 5.20.0's requirements (`tokenizers>=0.23.1,<0.24.0`, `huggingface-hub>=1.31.0,<3.0`).

## Compatibility review (5.19.0 to 5.20.0)
- All 247 `transformers` imports in `src/`, `tests/`, `examples/` and `scripts/` resolve on 5.20.0 wherever they resolve on 5.19.0. 5.20.0 additionally provides `transformers.models.muse_spark`.
- Bridge uses none of the APIs removed in 5.20.0. These include the deprecated `Cache` methods (`get_max_cache_shape`, `max_cache_len`, `max_batch_size`), the GLUE/SQuAD data helpers, `DataCollatorForWholeWordMask`/`DataCollatorForSOP`, and some `modeling_utils`/`masking_utils` internals.
- The remaining Transformers version gates are minimum-version checks, or the MiniMax M3 correction that applies only to 5.17.0. None is affected by 5.20.0.
- **Config change: `partial_rotary_factor`.** 5.20.0 drops the `partial_rotary_factor` attribute from nearly every HF config class that had one, and from Bridge's vendored `BailingMoeV2Config`. The value now lives only in `config.rope_parameters["partial_rotary_factor"]`.
  - The first full CI run caught this. `L1_Launch_models_glm_vl` failed on H100 and GB200 with `AttributeError: 'Glm4vMoeTextConfig' object has no attribute 'partial_rotary_factor'`.
  - The generic config mapping failed silently. It checks `hasattr(hf_config, "partial_rotary_factor")`, which is false on 5.20.0. As a result, GLM-4.5, GLM-4.7-Flash, Qwen3-Next, MiMo-V2-Flash and Bailing fell back to full rotary (`rotary_percent=1.0`), and so did the vendored Bailing attention.
  - The existing unit tests used mocked configs, so they did not catch it.
- A comparison of the serialized keys of every default HF config between 5.19.0 and 5.20.0, including text, vision and audio sub-configs, found no other removed field that Bridge reads. `rope_scaling` is unchanged, and `rope_theta` already lived only in `rope_parameters` on 5.19.0, where `rope_theta_from_hf` handles it.

## Validation
These are CPU-only results on macOS, with GPU-only packages stubbed. Both runs used full `megatron.bridge` imports against the pinned MCore, the same code, and Transformers 5.19.0 and 5.20.0 respectively. Tests covered: `tests/unit_tests/models/nemotron_omni`, `tests/unit_tests/models/minimax_m3`, `tests/unit_tests/models/muse_spark_open`, and `tests/unit_tests/utils/test_tokenizers_compat.py`.

| Transformers | Passed | Skipped (GPU / two-rank) | Environment-only failures |
|---|---|---|---|
| 5.19.0 | 247 | 10 | 2 |
| 5.20.0 | 247 | 10 | 2 |

The two environment-only failures are identical on both versions: `librosa` is not installed, and CUDA is unavailable. Before the gate fix, the MiniMax test failed on 5.20.0, and the Super VL adapter tests would have been skipped there.

After the 5.18.0 change, `tests/unit_tests/models/nemotron_omni` and `tests/unit_tests/models/minimax_m3` give identical results on 5.18.0, 5.19.0 and 5.20.0: 227 passed, 10 skipped, and the same two environment-only failures. This includes the adapter's real-load tests on each version.

After merging `main`, which brings in #6492 and the MCore bump from #6484, the same set gives 250 passed and 10 skipped on 5.20.0, with the same two environment-only failures.

A standalone processor check used the synthetic Super VL processor files from `test_native_processor.py`. Plain `AutoProcessor` fails identically on 5.18.0, 5.19.0 and 5.20.0. The adapter loads the processor, handles image and video inputs, and saves and reloads with bitwise-identical outputs on all three versions.

For the `partial_rotary_factor` fix, the new regression tests build real HF config classes instead of mocks:
- `Qwen2Config`, through the generic mapping;
- `Glm4MoeConfig` (GLM-4.5);
- `Glm4vMoeTextConfig` (GLM-4.5V);
- the Bailing attention's rotary dimension.

On 5.20.0 none of these configs has a `partial_rotary_factor` attribute, so all four tests would fail against the old code. The suite below gives 202 passed and 10 skipped on each of 5.18.0, 5.19.0 and 5.20.0:
- `tests/unit_tests/models/test_model_bridge.py`
- `tests/unit_tests/models/glm`
- `tests/unit_tests/models/glm_vl`
- `tests/unit_tests/models/bailing`
- `tests/unit_tests/models/mimo_v2_flash`
- `tests/unit_tests/models/qwen/test_qwen3_next_bridge.py`

`uv lock --check` and `pre-commit run --all-files` pass.

## CI
The run on 449f7b452 ([38829381289](https://github.com/NVIDIA-NeMo/Megatron-Bridge/actions/runs/38829381289)) had 134 passing jobs. Its only failures were `L1_Launch_models_glm_vl` on H100 and GB200, caused by the `partial_rotary_factor` change above. e9e58a676 fixes it, and CI was re-triggered on that commit, superseding the earlier run before its last jobs finished.

## Muse Spark Open
5.20.0 ships `transformers.models.muse_spark`. The text-only export fix for 5.20.0 landed separately in #6492, and this branch picks it up through the merge of `main`. With the skip guard removed, all four Muse Spark Open conversion tests run: the TP2, PP2 and EP2 round-trips and the text-only export logits check.

In the run on 449f7b452, `L0_Launch_models_muse_spark_open` reported 4 passed and 0 skipped on both H100 and GB200. Muse Spark Open has no L1 or L2 launchers. The 51 Muse Spark unit tests that CI collects also pass locally on 5.20.0, with none skipped.
