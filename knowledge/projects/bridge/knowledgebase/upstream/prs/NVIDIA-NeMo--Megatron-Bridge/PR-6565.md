# feat(quant)!: write ModelOpt quantizer sidecars for fake-quant HF export

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6565) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Save ModelOpt fake-quantized models to Hugging Face with their quantizer ranges and settings (`quantizer_state.pth` + versioned `quant_recipe.yaml`), and register the ModelOpt amax mappings by default (removes `ENABLE_BRIDGE_QUANT_MAPPING`).

# Changelog

- **Breaking:** `ENABLE_BRIDGE_QUANT_MAPPING` is removed. The amax mappings (`*.weight_quantizer._amax`, `*.input_quantizer._amax`, `k/v_bmm_quantizer._amax`) are always registered. They are resolved by lookups but kept out of `registry.mappings`, so registries rebuilt from another registry's mappings do not duplicate them. Before, saving a quantized model without the variable crashed with `'NoneType' object has no attribute 'param_weight'`; NeMo-RL's `os.environ["ENABLE_BRIDGE_QUANT_MAPPING"] = "1"` becomes a no-op.
- **Breaking:** `save_hf_pretrained` / `save_hf_weights` of a quantized model write `quantizer_state.pth` (tensors of the enabled quantizers, original precision) and `quant_recipe.yaml` (`format: modelopt_quantizer_recipe`, `version: 1`, one `get_modelopt_state(properties_only=True)` per HF quantizer name, each written out in full without YAML anchors so editing one entry never changes another) instead of `modelopt_weights.pt` (amax only, no settings; nothing in either repo read it). No sidecars are written when no quantizer is enabled, e.g. weight-only formats after `mtq.fold_weight`, and sidecars left in the directory by an earlier export are removed. `weight_dtype` casts the weights only; the ranges keep their precision.
- `MegatronModelBridge.build_modelopt_quantizer_recipe` names each enabled quantizer through the same amax mappings and q/k/v, gate/up and per-expert fan-out as the exported ranges. Export fails on an enabled quantizer without an HF name or with tensors other than `_amax` (e.g. AWQ pre-quant scales), and on a disabled quantizer that still rotates or scales its input (e.g. the query rotation of `NVFP4_KV_ROTATE_CFG`, or an AWQ W4A16 input scale), instead of dropping them.
- `PackedExpertAmaxMapping`: grouped-MoE input-quantizer amax for HF checkpoints that pack all experts into one tensor (Qwen3.5/3.6 `experts.gate_up_proj` → `experts.gate_up_proj_input_quantizer`, max over EP ranks). Without it, building tasks for a quantized Qwen3.5-MoE failed with "No mapping found ... experts.linear_fc1.input_quantizer._amax".
- Fix: `AmaxFanoutMapping` kept only the first tensor of the EP gather, so at EP > 1 the gate/up input amax of other ranks' SequentialMLP experts was dropped (found exporting Qwen3-30B-A3B at EP2).
- Fix: `build_conversion_tasks` attaches the model config to modules without one, including ModelOpt quantizers; it is kept out of the recipe so exporting the same model twice works.
- Docs: `docs/modelopt/quantization.md` (fake-quantized Hugging Face export).

Uses only ModelOpt APIs present in the pinned 0.48.0rc1. The consumer is ModelOpt's vLLM fake-quant serving (NVIDIA/Model-Optimizer#2888 reads the versioned recipe) and `export_quantized_megatron_to_hf.py --vllm_fakequant_export` (NVIDIA/Model-Optimizer#2889).

# Testing

- **New functional test** `tests/functional_tests/test_groups/quantization/test_fakequant_hf_export.py` (L0, 2 GPUs, ~8 min): a toy Qwen3-MoE is quantized with real ModelOpt (NVFP4 inputs, FP8 KV cache), each range is pinned to a value derived from its global layer, kind and expert, and the model is exported at TP1, TP2, PP2, EP2 (SequentialMLP) and EP2 (grouped GEMM). Every HF quantizer name, range (fp32) and recipe entry is checked against those values, plus: no quantizer tensors in the safetensors, no `modelopt_weights.pt`, and an enabled quantizer without an HF name or with a `_pre_quant_scale`, or a disabled query quantizer that still rotates, fails the export. The exports use `weight_dtype=torch.bfloat16`, so the fp32 range check also covers the weight cast. A folded INT8 weight-only export writes no sidecars and its weights are bitwise equal to ModelOpt's own fold of the source weights. The EP2 SequentialMLP case fails without the fan-out fix. Its `torch.distributed.run` workers run under `coverage run --parallel-mode`, like `test_quantization_workflow.py`, so CI measures the export code they run; before, only the pytest process was measured (`model_bridge.py` 17% in that job, 55% with the workers).
- Unit (no mocks): HF-name resolution through real registries (q/k/v fan-out, KV BMM, per-expert, packed experts) and the sidecar writer on real files. The mock-based `save_hf_weights` sidecar test is replaced by the functional test; `test_save_hf_weights_no_sidecar_when_not_quantized` checks that a plain export removes stale sidecars.
- Unit: `build_modelopt_quantizer_recipe` with real ModelOpt quantizers: HF names (incl. q/k fan-out), the attached model config left out, plain disabled quantizers skipped, all three rejections, and ranks that disagree.
- `tests/unit_tests/models` (quant_mapping, model_bridge, modelopt_utils, auto_bridge, mapping_registry, nemotronh, param_mapping): 518 passed.
- Rebased on main (Megatron-LM ebab48fc): the unit tests above and the new functional test pass again.
- End to end with ModelOpt (NVIDIA/Model-Optimizer#2889), scoring 64 CNN/DailyMail test articles with the per-token negative log-likelihood (NLL):
  - NVIDIA-Nemotron-Nano-9B-v2 NVFP4 W4A4 + FP8 KV: TP1, TP2 and PP2 exports bitwise identical; vLLM fake-quant NLL 2.3467 vs 2.3465 in Megatron.
  - Qwen3.6-35B-A3B (GB300; NVFP4 MoE with packed experts, FP8 attention and GatedDeltaNet projections, constant-amax FP8 KV): EP4, TP2×EP2 and PP2×EP2 exports bitwise identical (1,045 tensors, 390 ranges, 410 recipe entries); vision and MTP weights bitwise equal to the source; ranges loaded in vLLM equal the Megatron ones and each quantizer group matches Megatron within ±0.004 NLL.
  - An internal quantization format whose KV quantizers use a custom `backend` with `backend_extra_args`: both are kept in `quant_recipe.yaml` and restored by vLLM.
- Earlier runs: tiny Qwen3, Qwen3-MoE, Nemotron-H and Qwen3.5-VL-MoE exports at TP2 / EP2 / PP2 are bitwise identical to 1 GPU; Qwen3-0.6B NVFP4 W4A4 + FP8 KV served with vLLM fake quant matches the old exporter's checkpoint exactly (8/8 greedy generations); Qwen3-30B-A3B NVFP4 exports at EP2 and PP2 are identical (18,867 tensors, 18,720 ranges) and serve correctly with vLLM at TP2.
