# feat(model)!: pass a padding mask to Qwen3-VL MoE layers and run the vision merger on graph-padded rows

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6496) · state: open · merged: False

## Original PR description

feat(model)!: pass a padding mask to Qwen3-VL MoE layers and run the vision merger on graph-padded rows

# What does this PR do ?

Speeds up Qwen3-VL training in two independent parts. They touch disjoint files and can be reviewed one at a time.

- **Part 1 (commits 1-2): run the vision patch merger on the CUDA-graph-padded rows.** With vision CUDA graphs, the Qwen3-VL vision patch merger now runs on the fixed-size padded rows instead of on the real patch count, so Transformer Engine's cuDNN LayerNorm builds the merger's `patch_norm` plan once instead of once per new patch count. Outputs and gradients are unchanged. Qwen3.5-VL 35B-A3B pretraining gains +3.3% (native MoE) and +3.5% (MoE megakernel) steady-state throughput, and a 150-step job finishes in 12% / 16% less wall time.
- **Part 2 (commits 3-4): pass a padding mask to the MoE layers.** Adds an opt-in `return_padding_mask` option to the generic HF Energon task encoder and passes the resulting mask through the Qwen3-VL forward step to the model. The MoE layers then keep padding tokens out of the router statistics, and dropless HybridEP stops dispatching them. With native MoE, same-batch throughput rises by 12.8% on Qwen3.5-VL 35B-A3B and by 12.1% on 397B-A17B.

**Breaking change (part 2).** `qwen3_vl_step.get_batch()` now returns seven values instead of six. The seventh is the padding mask, which is `None` unless the dataset emits one. The title therefore carries `!`, and the PR needs the `breaking-change` label (see Risks).

## Part 1: run the vision patch merger on the CUDA-graph-padded rows

### Problem

With vision CUDA graphs on (`vision_cuda_graph_impl="transformer_engine"`, training), `Qwen3VLVisionModel.forward` pads the patch sequence to `max_vision_cuda_graph_seq_length` for the vision transformer block. It used to remove the padding again before the patch merger, so the merger ran on the real patch count, which changes from micro batch to micro batch.

With `NVTE_NORM_FWD_USE_CUDNN=1` and `NVTE_NORM_BWD_USE_CUDNN=1`, Transformer Engine builds and compiles a cuDNN norm plan for every row count it has not seen yet. The merger's `patch_norm` therefore rebuilt its plans whenever a micro batch brought a new patch count:

- such a micro batch spent an order of magnitude longer in the vision forward and backward than one with a known count;
- the other ranks waited for it at the next collective;
- new counts keep appearing throughout training, and the plan cache starts empty again after every restart.

Recipes that combine vision CUDA graphs with these flags are affected, for example the 8-GPU GB300 MXFP8 pretrain recipe for Qwen3.5-VL 35B-A3B (#6413).

### Mechanism

In the padded branch only:

1. Cut the padded rows to whole merged tokens: `hidden_states[: seq_len - seq_len % spatial_merge_size**2]`. The merger now sees the same row count for every micro batch.
2. Zero the padded rows (`masked_fill`) and run the merger.
3. Keep the first `original_seq_len // spatial_merge_size**2` merged tokens. The deepstack features are cut the same way as before.

### Why the result is unchanged

- `patch_norm` acts per row, and `linear_fc1` / `linear_fc2` act per merged token. The vision tower runs without sequence parallelism. Padded rows therefore cannot change the real merged tokens.
- Every image or frame contributes a multiple of `spatial_merge_size**2` patches, and its merge groups are contiguous. The padding thus starts on a merged-token boundary, and the kept merged tokens are exactly those of the old path.
- The dropped merged tokens get zero gradient, but their input rows still enter the merger's weight gradients as `0 * row`. A non-finite padded row would make those gradients NaN. Zeroing the padded rows first rules that out, and it is bitwise neutral for finite rows.
- Cutting to whole merged tokens keeps caps that are not a multiple of `spatial_merge_size**2` working.

### Alternative considered

Turning the cuDNN norm flags off also removes the stalls, but it has three costs:

- the vision step becomes 22% slower;
- stall-free training steps become about 1% slower, because the language model's norms lose the cuDNN kernels;
- numerics change.

This PR keeps the flags.

## Part 2: pass a padding mask to Qwen3-VL MoE layers for padded batches

### Problem

Padded (unpacked) Qwen3-VL batches from the generic HF Energon task encoder reach the language model without a padding mask. Every MoE layer therefore routes each padding token like a real one:

- the token is dispatched to its experts, computed and combined;
- it counts in the router's auxiliary-loss, z-loss and expert-bias statistics.

In a padded vision-language pretraining benchmark, about 94% of the routed rows were padding.

### Mechanism

Megatron-LM's MoE layers already accept a batch-first boolean `padding_mask`, where True marks padding. With it:

- the router excludes padding from its auxiliary-loss, z-loss and expert-bias statistics;
- dropless HybridEP removes padding rows before dispatch. The other dispatchers keep their routes, and only the statistics change.

This PR produces the mask in the data pipeline and passes it through the Qwen3-VL step, as #6188 did for unpacked GPT SFT batches:

1. The encoder derives the mask from the collate function's 2D `attention_mask`.
2. The step moves the mask to the device and pads it with True wherever it pads the batch.
3. The step passes the mask to the model for padded batches only. With in-batch packing (THD layout), a `[B, S]` mask does not apply, so none is passed.
4. Under sequence parallelism, later pipeline stages receive sequence-parallel activations, so the step scatters the mask the same way for them. On the first stage, the model already scatters the mask together with its embeddings.

The option is off by default because it changes training statistics (see Correctness and numerics).

## Correctness and numerics

### Part 1 (vision merger)

- **Real vision encoder, deterministic attention.** We ran the Qwen3.5-VL 35B-A3B vision encoder on seven real image micro batches. The vision output, the input gradient and all parameter gradients are bitwise identical to the old path.
- **More input kinds.** A second check, also with deterministic attention, compared the old path with the new path both with and without the zeroing. It covered images, videos, a mixed image-and-video micro batch, a long video, two caps that are not a multiple of 4, and a patch count equal to the cap. All results are bitwise identical, and peak memory is unchanged.
- **Recipe environment.** With the cuDNN norm flags on and the default non-deterministic attention backward:
  - the vision output, the gradient into the merger and all merger weight gradients are bitwise identical;
  - the other encoder gradients differ from the old path about as much as two runs of the old path differ from each other.
- **397B-A17B recipe shape.** One image per micro batch, with a cap that is not a multiple of 4. Results are bitwise identical with and without the cuDNN norm flags (deterministic attention).
- **Non-finite padding.** We wrote NaN into the padded rows after the vision blocks:
  - merging them without the zeroing makes the merger's weight gradients NaN;
  - with the zeroing, every gradient is finite and bitwise equal to the clean run.
- **Training smoke.** We ran a 4-layer 35B-A3B smoke with the MoE megakernel backend and commit 1 alone, two runs per side.
  - Steps 1 and 2: the LM loss, MTP loss, load-balancing loss and grad norm are identical.
  - Later steps: the two sides differ about as much as two runs of the unchanged code differ from each other.

### Part 2 (padding mask)

- **First steps.** In 4-layer smoke runs at the 35B and 397B shapes, the LM loss was bit-identical with and without the mask at steps 1 and 2. This held for native MoE and for the MoE megakernel.
- **Later steps.** The runs then drift apart slightly, as expected, because padding no longer counts in the router statistics. In the full-size throughput runs, the late-window loss differences between mask and no mask had mixed signs. They stayed within the run-to-run spread of repeated native runs. A long-horizon comparison of mask and no mask was not run.
- **Load-balancing weight.** With per-token loss, Megatron-LM scales the auxiliary loss by the number of tokens it counts. Without the mask, that count includes padding, so in heavily padded batches the load-balancing loss carries correspondingly more weight relative to the language-model loss. With the mask, only real tokens count.
- **Opt-in.** Because the option changes training statistics, it is off by default, and this PR does not enable it in any recipe.

## Performance

### Part 1 (vision merger)

Setup:

- Qwen3.5-VL 35B-A3B, 8 GB300 GPUs (EP4), with the recipe environment (cuDNN norm flags on).
- Same data and batch size. Each arm ran against a matched control submitted at the same time.
- The two runs of a pair differ only in the vision model. Both also used part 2's MoE padding mask.
- The runs used commit 1 alone. The zeroing of commit 2 came later; it is bitwise neutral for finite rows, and in isolated vision timing it changed nothing within noise.

| MoE backend | Throughput, steps 101-150 | Throughput, steps 11-150 | Wall time, whole 150-step job |
|---|---|---|---|
| native (HybridEP) | +3.3% | +6.6% | -12% |
| MoE megakernel (Mixture-of-Kittens: NVIDIA/Megatron-LM#8210 plus the follow-ups under Related) | +3.5% | +10.1% | -16% |

- **Early steps and restarts.** The gain is largest early in a run, when many patch counts are still new, and it recurs after every restart.
- **4-layer smoke.** The stalls dominate this smoke, and steps 2 to 30 took 82% less time.
- **Configurations without the cuDNN norm flags.** These have no stall to remove. The 397B-A17B configuration we measured does not set the flags. Its vision forward and backward already took as long for a new patch count as for a known one, so we did not run it end to end.

### Part 2 (padding mask)

Setup: same data and batch size, native MoE with HybridEP, and the recipes' `[attn, moe_router, moe_preprocess]` TE CUDA graphs. Each row compares runs with and without the mask:

| Model and setup | Throughput | Peak memory |
|---|---|---|
| Qwen3.5-VL 35B-A3B, 8-GPU GB300 MXFP8 recipe as written, 8 GB300 GPUs (EP4), steps 101-150 | +12.8% | -14% |
| same, with the shared-expert gate off in both arms | +11.9% | -13% |
| Qwen3.5-VL 397B-A17B, 64 GB300 GPUs (EP32), forced load balancing, shared-expert gate off in both arms, steps 31-80 | +12.1% | -2% |

- **35B.** The arms of each pair ran concurrently. For the first pair, the 95% confidence interval of the step-time change is -11.6% to -11.0%.
- **397B.** The two arms ran one after another, so this is a single sequential pair.

With the Mixture-of-Kittens MoE backend (NVIDIA/Megatron-LM#8210), the Megatron-LM PR *feat(moe): Qwen3.5 support and speedups for the MoK megakernel backend* (link to be added) consumes the same mask in its commits 4 and 7. In the same experiments, that backend's throughput was 47% higher with the mask at 35B and 26% higher at 397B. Each arm ran at its own tuned megakernel launch settings, so these two figures are not the effect of the mask alone. With the mask, fewer communication SMs are optimal.

## Risks and follow-ups

### Part 1 (vision merger)

- **Extra merger work.** The merger now also processes the padded rows, up to the cap. This cost is included in the throughput numbers above. In isolated vision timing, the cost for a repeated patch count was unchanged within noise.
- **Scope.** Only the padded branch changes, and only in which rows enter the merger. The vision transformer blocks and their attention are untouched.
- **Follow-ups.** None required.

### Part 2 (padding mask)

- **`get_batch` return value (breaking).** `get_batch` now returns seven values instead of six. Within the repository, its only caller is the shared body of `forward_step` and `forward_step_modelopt`. External code that unpacks it needs an update. Per CONTRIBUTING, a function-signature change takes `!` in the title and the `breaking-change` label, so this PR is not auto-merged even with green CI.
- **Changed statistics when enabled.** With the option on, the router statistics exclude padding. Enabling it by default in the Qwen3.5-VL recipes is left for a follow-up that needs model-owner sign-off on that change.
- **Scope.** Only `HFEnergonTaskEncoderConfig` gains the option. That is the config `--dataset energon` builds for recipes without their own Energon dataset, such as the GB300 Qwen3.5-VL recipes. Recipes that use `QwenVLEnergonTaskEncoderConfig` are unchanged.
- **Not run end to end: SP, PP > 1, CP > 1.** Unit tests with stubs cover the sequence-parallel scatter on later pipeline stages. With CP, `get_batch_on_this_cp_rank` shards the mask along with the labels and the loss mask.
- **TE CUDA graphs with the `moe_router` scope.** Megatron-LM reserves the `padding_mask` graph input during the eager warm-up steps, so `cuda_graph_warmup_steps` must stay above 0. The default is 3.
- **Docs next to the GPT SFT section.** The new section says that the Qwen3-VL path works with `moe_router`-scoped graphs, unlike the GPT SFT path above it. The GPT SFT section is unchanged, because Bridge's GPT step still rejects router-scoped graphs when a padding mask is present.
