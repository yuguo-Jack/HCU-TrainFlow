# perf(ckpt): use set lookups for HF state dict keys during import

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6489) · state: closed · merged: True

## Original PR description

# What does this PR do ?

`StateDict` membership checks scanned the full key list on every call, so per-key loops during HF import (`state[k]`, `k in state`) were quadratic in the number of checkpoint keys. This switches them to set lookups.

# Changelog

- `StateDict._get_key_set()`: a set over `source.get_all_keys()`, used by `__getitem__`, `__contains__`, `get`, list access and exact-key `_match_keys`. Both in-tree sources return a cached list, so the set is built once; it is rebuilt only when the source hands back a different list (the Kimi K2.5-VL / K3 bridges temporarily wrap `get_all_keys` with virtual keys during `build_conversion_tasks`).
- `SafeTensorsStateSource.load_tensors`: cache each shard's key set next to its reused `safe_open` handle instead of rebuilding `set(f.keys())` per call. Dropped together with the handle in `_invalidate_handle`, so the retry path still re-reads a replaced shard (covered by the existing `test_retry_refreshes_incomplete_shard`).
- Test: `test_membership_follows_wrapped_get_all_keys` checks membership before, during and after wrapping `get_all_keys`. Passes on main, fails on a build-once cache, passes here.

# Benchmark

Synthetic checkpoints with real key names and one-element tensors, so this measures lookup overhead only, not end-to-end import time. CPU, `StateDict(SafeTensorsStateSource(path))`, keys warmed first.

| Checkpoint shape | Keys / shards | per-key `state[k]` loop | `k in state` loop |
|---|---|---|---|
| DeepSeek-V3 | 94,370 / 163 | 223.2s -> 12.6s | 106.5s -> 0.07s |
| Qwen3-235B-A22B | 73,229 / 118 | 110.8s -> 9.0s | 58.8s -> 0.04s |
