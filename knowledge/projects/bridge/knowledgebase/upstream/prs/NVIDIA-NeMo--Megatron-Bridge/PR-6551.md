# refactor(model): build GPT-OSS from a builder-backed model config

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6551) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves **GPT-OSS** onto the builder-backed `ModelConfig` / `ModelBuilder` path, for recipes and checkpoint conversion, following Muse Glimmer and the families migrated in #6365, #6379, #6383, #6392 and #6401.

# Changelog

- **`GPTOSSBridge`**:
  - `provider_bridge()` is replaced by `hf_config_to_model_config_kwargs()`, and the provider path reuses the same kwargs.
  - The kwargs carry the GPT-OSS specifics: `quick_gelu` with a 7.0 clamp and GLU offset, learnable softmax (sinks), alternating sliding-window attention, and the released YaRN settings.
  - Fields whose builder-config default differs from the provider's (`masked_softmax_fusion`, `rope_scaling_factor`) are set explicitly.
  - Opts in with `MODEL_CONFIG_CLASS = BridgeGPTModelConfig` and converts through the builder (`USE_MODEL_CONFIG_FOR_CONVERSION = True`).
- **Shared `provider_bridge()`**: for non-MLA providers, an explicit `position_embedding_type="yarn"` in the bridge's kwargs is now honored instead of being overwritten from the HF `rope_scaling`. GPT-OSS always uses YaRN, and its removed override used to restore it, so without this a GPT-OSS config lacking `rope_scaling` would build plain RoPE on the deprecated provider path. Only GPT-OSS sets YaRN explicitly; the shared mapping sets it exactly when HF `rope_scaling` is YaRN, so other families are unaffected and MLA providers still use `"rope"`.
- **Recipes**: the H100 recipes use `get_model_config()` (6 call sites). The compatibility aliases in `recipes/gpt_oss/gpt_oss.py` and all GPT-OSS perf recipes build on these.
- **Tests**:
  - Bridge: builder mapping, provider/builder parity, and `megatron_to_hf_config()` from a builder config.
  - Recipes: a strict test builds every GPT-OSS library recipe (15) and perf recipe (25) against a real `BridgeGPTModelConfig` made from `GptOssConfig`. The perf recipes set many model fields, and the shared offline recipe fixture accepts any attribute, so this is what catches a field the builder config does not declare.

File: `src/megatron/bridge/models/gpt_oss/gpt_oss_bridge.py` · line 135

**Blocking: Preserve YaRN on the inherited provider path**

**Failure:** For a GPT-OSS config whose `rope_scaling` is absent, `None`, or `{}`, `to_megatron_provider(load_weights=False)` now returns `position_embedding_type="rope"`, whereas the builder returns `"yarn"`. This delegation supplies the correct kwargs, but [the inherited provider constructor](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/b0c7ee8b83e8a0bc5d0c12fbb9d04f522fa14347/src/megatron/bridge/models/conversion/model_bridge.py#L940-L954) subsequently overwrites that field based solely on HF `rope_scaling`. [The removed override](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/a7eaa195b8c0e60e9f631413181f3ace3801a697/src/megatron/bridge/models/gpt_oss/gpt_oss_bridge.py#L87-L96) restored YaRN after that step. Consequently, legacy model construction silently selects different positional embeddings; [the provider passes this field directly to GPTModel](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/b0c7ee8b83e8a0bc5d0c12fbb9d04f522fa14347/src/megatron/bridge/models/gpt_provider.py#L294-L308).

**Correction:** Keep the inherited compatibility API, but make its final selection honor explicit YaRN kwargs for non-MLA providers. A small suggested replacement for the condition at the shared constructor's line 951 is:

```python
if not is_mla_provider and (
    provider_kwargs.get("position_embedding_type") == "yarn"
    or rope_type == "yarn"
):
```

Leave the existing assignments and MLA-parameter application unchanged. This restores GPT-OSS provider/builder parity without selecting `position_embedding_type="yarn"` for MLA models.

**Preservation and acceptance:** Extend the new parity test with proposed cases for missing/`None`/empty `rope_scaling`, plus explicit HF YaRN. Each must produce `"yarn"` on both GPT-OSS paths, retaining factor `32.0` and original context `4096`. The existing `mock_pretrained` fixture already omits `rope_scaling`, so asserting its provider's positional type is also a minimal regression check. Retain ordinary non-MLA RoPE when neither kwargs nor HF selects YaRN; retain Qwen3 HF-YaRN selection and explicit parameters; retain Llama linear scaling (`position_embedding_type="rope"`, interpolation factor `8.0` in `test_provider_bridge_preserves_linear_rope_scaling`). Using the existing DeepSeek V3 fixture, additionally check that MLA HF-YaRN still yields positional type `"rope"` with `rotary_scaling_factor == 40`.

These are source-derived checks, not executed results; verify the suggested condition before adopting it.
