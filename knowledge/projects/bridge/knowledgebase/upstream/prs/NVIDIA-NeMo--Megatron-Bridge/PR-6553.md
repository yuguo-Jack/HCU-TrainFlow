# fix(recipe): flag ignored recipe allocator settings and pin Omni H100 SFT allocator

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6553) · state: closed · merged: False

## Original PR description

# What does this PR do ?

Warns when a recipe's CUDA allocator setting is applied too late to take effect, and pins the Nemotron-3-Nano-Omni 8-GPU H100 SFT recipe to the allocator its verified run used. Follow-up to NVBug 6900704.

# Changelog

- `apply_environment_variables` (`training/config.py`) warns once on rank 0 when it applies a non-default recipe allocator setting after CUDA initialization and the launch environment sets no allocator variable. `PYTORCH_CUDA_ALLOC_CONF` and `PYTORCH_ALLOC_CONF` count as one setting, and `expandable_segments:False` (PyTorch's default) never warns.
- New keyword-only `warn_on_ignored_allocator_settings` (default `True`) on `apply_environment_variables` and `recipe_runner.apply_runtime_environment`. `bootstrap_recipe_environment` passes `False`, since the restarted interpreter applies the setting.
- `nemotron_omni_cord_v2_sft_8gpu_h100_bf16_config` declares `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:False`.
- `docs/recipe-usage.md` and its fern nightly mirror explain when allocator settings apply and how to pass one through `train.sh --env`, and fix the `COMMON_RECIPE_ENV_VARS` count (five, not seven). The `environment_utils.py` docstring now allows per-recipe overrides.
- Unit tests for the warning conditions, the bootstrap path, flag forwarding, and the Omni recipe value.

## Why

PyTorch reads `PYTORCH_CUDA_ALLOC_CONF` only when CUDA initializes, and importing the training stack already initializes CUDA. `scripts/training/run_recipe.py` restarts the interpreter with the recipe environment only for benchmark recipes and recipes that declare an import-time NVTE variable. For other library recipes launched through `train.sh`, and for Python `pretrain`/`finetune` runs, the `expandable_segments:True` inherited from `COMMON_RECIPE_ENV_VARS` arrives after CUDA is up and silently does nothing. The perf launcher, and anything that exports the variable first, do apply it. So the same recipe and arguments ran with different allocators depending on the launcher.

NVBug 6900704 came from exactly this. The Omni `sft.H100` card item was verified through `train.sh`, with the default allocator. A suite that exported the recipe's declared `expandable_segments:True` saw rank 0 reserve about 5 GiB more and run out of memory on the step after the step-50 checkpoint save. With the default allocator, all 100 steps pass.

## Behavior notes

- Apart from the Omni SFT recipe on launchers that apply recipe env before CUDA starts, no run's effective allocator changes. `train.sh` runs of that recipe already used the default allocator.
- Most hardware recipes inherit `expandable_segments:True` and run in-process under `train.sh`, so those runs will now log the warning once. That is intended: the declared setting has never applied on this path. Whether recipes should drop it, or `train.sh` should start applying it, is a separate decision; applying it would change the allocator for every library recipe and needs card re-verification.
- The Omni PEFT and long-context SFT recipes still declare the common default. They were also verified through `train.sh` and could be pinned the same way in a follow-up.
