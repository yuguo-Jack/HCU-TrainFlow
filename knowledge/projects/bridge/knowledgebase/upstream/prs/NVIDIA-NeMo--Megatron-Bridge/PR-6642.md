# refactor(model): build Sarvam MoE and LLaDA-1.5 from builder-backed model configs

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6642) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves **Sarvam MoE** (Sarvam 30B-A3B) and **LLaDA-1.5** onto the builder-backed `ModelConfig` / `ModelBuilder` path for checkpoint conversion, following #6379, #6383, #6551 and #6552.

# Changelog

- **`SarvamMoEBridge`**:
  - `provider_bridge()` is replaced by `hf_config_to_model_config_kwargs()`. The provider path reuses the same kwargs and still builds `SarvamMoEModelProvider`, now registered as the bridge's `PROVIDER_CLASS`.
  - The kwargs carry every `SarvamMoEModelProvider` default (MoE routing, recompute, fusions and so on) plus the fields whose builder default differs (`masked_softmax_fusion`, `rope_scaling_factor`, `position_embedding_type`).
  - `moe_router_num_groups` and `moe_router_group_topk` stay unset, as on the provider. The checkpoint config sets `n_group = topk_group = 1`, which the shared mapping would otherwise turn into group-limited routing.
  - The builder keeps no `transformer_layer_spec`. Megatron Core's default MoE spec is the decoder block spec the provider uses, and it honors the dense first layer.
  - Opts in with `MODEL_CONFIG_CLASS = SarvamMoEModelConfig` and `USE_MODEL_CONFIG_FOR_CONVERSION = True`.
- **`SarvamMoEModelConfig`** (new, `sarvam_config.py`): a `BridgeGPTModelConfig` whose `finalize()` applies the provider's PP=2/4/8 layouts for the 19-layer decoder (#3041). Without them the builder path fails at PP=2/4/8: Megatron Core asserts that the layer count divides the pipeline size. That includes the PP=2 round trip in `examples/models/sarvam`. The layout helper moved here and the provider reuses it.
- **`LLaDA15Bridge`**:
  - Same change: builder kwargs, provider path delegating to them, opts in with `BridgeGPTModelConfig`.
  - The bidirectional layer spec is public as `llada15_layer_spec` and accepts either config.
  - `examples/models/llada/llada15/convert_llada15_hf_to_megatron.py` now builds through `AutoBridge.get_model()` instead of the deprecated `to_megatron_model()`. `convert.sh` cannot resolve LLaDA because its bridge lives in the diffusion package, so this script is the family's conversion entry point.
- **LLaDA-1.5 checkpoint loading fix**: provider checkpoints serialized the spec as the private `_llada15_layer_spec`. Since #4008 the config loader rejects private targets, so `load_megatron_model()` failed on every LLaDA-1.5 checkpoint, including the README flow (`convert_llada15_hf_to_megatron.py`, then `inference_dllm.py` / `run_llada15_chat.py`). The old name now aliases the public one and is allowlisted, as for Gemma 4 (#5482) and ERNIE 4.5 (#6552).
- **`BridgeGPTModelConfig.as_dict()`** (separate commit): `finalize()` parses `pipeline_model_parallel_layout` into a `PipelineParallelLayerLayout`, which the saved `run_config.yaml` could not restore, so any builder checkpoint saved with a layout failed to reload. The layout is now saved as given, as on the provider path. Sarvam MoE imports at PP=2/4/8 rely on this.
- `sarvam/common.py`: `get_common_config()` takes the HF config instead of the pretrained wrapper. The MLA bridge's call site changes by one line; its provider is unchanged.
- **Tests**:
  - Sarvam MoE: builder mapping; parity among the builder config, the provider and a reconstruction of the pre-migration provider (fp32/bf16/fp16 sources), raw and finalized at PP=1/2/4/8; builder default spec vs provider spec; YaRN on both paths.
  - `SarvamMoEModelConfig`: layouts and `run_config.yaml` round trip at PP=1/2.
  - LLaDA-1.5: the same parity over 10 config variants; layer spec on both paths; `run_config.yaml` round trip; the legacy private target resolves.
  - Load/save: a builder checkpoint keeps a finalized pipeline layout. It fails without the `as_dict()` fix.
  - CPU import, then GPU load: for each family's restored config, `build_and_load_model()` builds where the load asks, whatever `use_cpu_initialization` the import saved. The CPU-import, GPU-load case fails without #6594's fix, which this branch has from `main`.
  - The existing Sarvam tests moved from `Mock()` HF configs to namespaces, because the shared mapping reads every attribute a `Mock` invents.

# Behavior notes

- **YaRN:** a YaRN-scaled Sarvam MoE config now maps to `"yarn"` on both paths, which the HF modeling code also applies. `main` ignored `rope_scaling` here. No published Sarvam MoE checkpoint uses YaRN.
- **Checkpoint format:** `AutoBridge.import_ckpt` now writes builder-format checkpoints for both families. So do `convert.sh import` for Sarvam MoE and the conversion example for LLaDA-1.5. Bridge versions before this PR cannot load them, because `SarvamMoEModelConfig` and `llada15_layer_spec` do not exist there. This PR loads `main`'s provider checkpoints. NeMo RL's `megatron_bridge` checkpoint loader cannot read builder-format checkpoints yet; that applies to every migrated family.

# Additional Information

- Part of the incremental provider → builder migration (MB-1857). `SarvamMLABridge` is not part of this PR; it needs a shared MLA config first.
- Neither family has training recipes. Open PR #4810 adds Sarvam recipes on `to_megatron_provider()`; after this PR they can use `get_model_config()`.
- No open PR touches the Sarvam MoE or LLaDA-1.5 bridges. #6609 also edits `models/gpt/model_config.py`, in a different hunk.
- `AutoBridge.import_ckpt()` saves `use_cpu_initialization=True` in the checkpoint's config. #6594, now on this branch from `main`, clears the flag when a GPU load is requested, so the model builds on the GPU. The new tests cover this for both families.
- Pre-existing on `main`, not changed here: Sarvam MoE export writes `"n_group": null` and `"topk_group": null` to `config.json`, because the reverse mapping exports the Megatron values, which the provider never set. The HF modeling code then fails in the router (`view()` with `None`), so exported Sarvam MoE checkpoints do not run in Transformers. This needs a separate fix in the bridge's `megatron_to_hf_config()`.
