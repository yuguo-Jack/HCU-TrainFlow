# refactor(model): finish the Llama and OLMoE builder migrations

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6594) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Finishes the two partly migrated families on the builder-backed `ModelConfig` / `ModelBuilder` path. Llama checkpoint conversion now goes through `ModelBuilder`, and the OLMoE recipes build from `get_model_config()`.

# Changelog

- **`LlamaBridge`** sets `USE_MODEL_CONFIG_FOR_CONVERSION = True`. `AutoBridge.import_ckpt`, `export_adapter_ckpt`, `scripts/conversion` (`convert.sh` import, export and roundtrip) and `compare.py` now build Llama from its `BridgeGPTModelConfig` instead of `GPTModelProvider`.
  - Llama opted into `MODEL_CONFIG_CLASS` in #5132. That was a month before #5479 added the conversion flag, which defaults to `False`; #5479 also pinned Llama to `False` in `test_gpt_model_config.py`. Neither #5132, #5479 nor #6305 gives a technical reason to keep it off.
  - Unchanged: `examples/conversion/hf_megatron_roundtrip*.py`, `hf_to_megatron_generate_text.py` and multi-GPU `export_adapter.py` still use the provider. `export_ckpt` rebuilds the model from the checkpoint's own `run_config.yaml`, so checkpoints imported on `main` still load through the provider.
- **OLMoE recipes** (`olmoe_7b_{pretrain,sft,peft}`) no longer construct `OlMoEModelProvider` directly. They build from `AutoBridge.from_hf_pretrained("allenai/OLMoE-1B-7B-0125").get_model_config()` with the same parallelism and recompute settings. `OlMoEBridge` already opted in with #6383.
  - The 0125 config reproduces every `OlMoEModelProvider` default; both are fp32. With 0924 only `bf16`/`params_dtype` would differ, and the recipes' `MixedPrecisionConfig` overrides those anyway. The SFT/PEFT tokenizer stays `allenai/OLMoE-1B-7B-0924`.
- **Llama RoPE fix** (the commit from #6597):
  - `position_embedding_type` uses `setdefault`, so YaRN-scaled checkpoints keep `"yarn"` in `get_model_config()`.
  - llama3 RoPE settings that Megatron Core cannot apply now raise a `ValueError` on both paths instead of converting silently. Megatron Core takes only the factor and fixes `low_freq_factor`, `high_freq_factor` and `original_max_position_embeddings` at 1.0, 4.0 and 8192, the values all official Llama 3.1/3.2/3.3 checkpoints use.
- **`load_megatron_model()` CPU-init fix** (`2e58f1a4e`): a CPU import saves `use_cpu_initialization: true` in the checkpoint's config, and the loader overrode it only for provider checkpoints. So a GPU load of a builder checkpoint built the model on CPU.
  - This failed the first CI run in `L0_Launch_converter` and `gb200_L0_Launch_converter` (`test_gpu_checkpoint_export`: Llama-3.2-1B imported on CPU, exported on two GPUs with TP2), with `No backend type associated with device type cpu` in the tensor-parallel `all_gather`.
  - The loader now clears the flag for builder configs unless CPU init is requested, matching the provider path. A unit test covers it.
- **Tests**:
  - Llama:
    - The conversion flag is set.
    - The builder's default layer spec equals the provider's.
    - `import_ckpt` on a Llama 3.2-style checkpoint builds through `get_model()` with llama3 ×32 RoPE scaling and tied embeddings.
    - `test_model_config_is_opt_in_per_family` now asserts the flag for Llama and Qwen3.
    - From #6597: the YaRN mapping, YaRN parity between builder and provider, YaRN export, and the llama3 guard on both paths.
  - OLMoE recipes:
    - The test fakes patch `AutoBridge` and make the provider API raise.
    - A strict test builds every recipe on a real `BridgeGPTModelConfig` from the 0125 architecture.
    - A parity test compares each recipe's model config with the previous `OlMoEModelProvider` settings, field by field.

# Verification

CPU checks first (torch 2.14.1, transformers 5.20.2, Megatron Core 89b28875 from this branch's pin). The GPU results are in the next section.

**Llama config parity** on the real HF configs of Llama 2 7B, CodeLlama 7B, Llama 3 8B/70B, 3.1 8B/70B, 3.2 1B/3B and 3.3 70B:
- `get_model_config()` matches the provider on all 383 shared fields.
- `megatron_to_hf_config()` output is identical, including llama3 RoPE scaling (factor 8 and 32) and tied embeddings.
- The builder's default layer spec matches the provider's.

**Llama conversion on tiny random checkpoints.** I ran `AutoBridge.import_ckpt` with the flag off (the `main` behavior) and on, then load, forward and `save_hf_pretrained`. These runs use Megatron Core's local layer spec on CPU.

| Logits, provider vs builder | bitwise-identical | bitwise-identical | bitwise-identical | bitwise-identical | bitwise-identical |

| Export vs source HF weights, both paths | bit-exact | bit-exact | bit-exact | bit-exact | bit-exact |

Dropping RoPE scaling moves these logits by 8e-5 (llama3) and 5e-3 (linear), so the comparison does see the scaling.

**YaRN and the llama3 guard, after merging #6597.** I ran a tiny random YaRN Llama (factor 4, original length 32768) through `AutoBridge.import_ckpt` with the flag off and on.
- The Megatron checkpoints are identical, and logits are bitwise-identical between the two paths.
- Logits vs HF: max abs diff 1.8e-7 on both paths. The same weights with plain RoPE differ from YaRN by 2.3e-3, so a dropped YaRN would show.
- Both exports are bit-exact against the source weights and keep the YaRN `rope_parameters`.
- A llama3 config with `low_freq_factor=2.0` raises `ValueError` on both paths.

**OLMoE recipes.** I ran `ConfigContainer.validate()` on all three recipes and on `main`'s provider-built versions.
- Model config: all 384 shared fields match.
- Every other section matches too: `train`, `optimizer`, `scheduler`, `dataset`, `tokenizer`, `checkpoint`, `ddp`, `mixed_precision`, `comm_overlap` and `peft`.
- For this check I disabled the precision-aware optimizer on both sides, because the CPU environment has no TE FusedAdam.

**Unit tests:** 903 passed, 1 skipped, 2 failed.
- Files: `models/llama`, `models/olmoe`, `test_gpt_model_config.py`, `test_olmoe_recipes.py`, `test_llama_recipes.py`, `test_llama_perf_recipes.py`, `test_all_recipe_factories.py`, `test_auto_bridge.py`, `test_adapter_export.py`, `test_compare_mask_handling.py`, `test_gpu_backend.py`, `test_vlm_generation.py` and `test_autobridge_registration_matrix.py`.

- The new tests fail with the flag off.
- After merging #6597: 363 passed, 1 skipped, 2 failed across `models/llama`, `test_gpt_model_config.py`, `test_llama_recipes.py`, `test_olmoe_recipes.py` and `test_auto_bridge.py`. The 2 failures are the same `test_save_hf_pretrained_truncates_vocab_padding` cases.

- The three export directions are: `main`'s checkpoint with this branch's code, this branch's checkpoint with its own code, and this branch's checkpoint with `main`'s code. Each is bit-exact against the source HF weights, with the same RoPE values in `config.json`.
- Logits: every run matches HF's next token with cosine ≥ 0.99. Converted from HF, `main` (provider) and this branch (builder) give bitwise-equal logits. This branch also gives bitwise-equal logits from `main`'s checkpoint and from its own.
- Not from this PR: for 70B at TP8 with 9,216 tokens, models loaded from a checkpoint differ from models converted straight from HF by up to 0.75 in logits that reach 35, with the same argmax; both pass every gate. `main` shows the same gap with its own checkpoint, and `main`'s and this branch's code give bitwise-equal logits from the same checkpoint. The gap comes from NCCL's NVLS all-reduce: with NVLS off (NCCL pinned to Ring), the two load paths give bitwise-equal logits. TP4/PP2 and the smaller models show no gap.
- LoRA: a random rank-8 adapter on Llama 3 8B exports identically through `export_adapter_ckpt` on `main` (provider) and on this branch (builder): 448 tensors and the same `adapter_config.json`.
- CI's L0 converter job also runs Llama 3.2 1B through `convert.sh` import, export and roundtrip at TP2 and PP2.

**YaRN** (`NousResearch/Yarn-Llama-2-7b-64k`, YaRN ×16, 6,144-token prompt):
- On `main`, `get_model_config()` builds plain RoPE: wrong next token, 69.8% argmax agreement with HF, cosine 0.729.
- With the fix from #6597, the builder is bitwise equal to the provider, which matches HF (99.5% argmax agreement, cosine 0.9997). transformers 5.20.2 gives the same picture.

**`load_megatron_model()` CPU-init fix** (`2e58f1a4e`). Llama 3.2 1B imported on CPU, then exported on GPU at TP2, with the commands from `test_gpu_checkpoint_export`:

| Export code | CPU import from `main` | CPU import from this branch |
|---|---|---|
| `main` (`4aa119666`) | bit-exact | fails: `No backend type associated with device type cpu` |
| before the fix (`057662bd4`) | not run | fails with the same error as CI |
| this branch (`2e58f1a4e`) | bit-exact | bit-exact |

- The two CPU imports are bitwise identical. Both save `use_cpu_initialization: true`; only this branch writes a builder `run_config.yaml`.
- `compare.py` from the CPU imports: `main` and this branch both match HF's next token with cosine 0.999955. Before the fix, the model is built on CPU and the forward pass fails.
- Bridge versions without this fix, including current `main`, cannot load a CPU-imported builder checkpoint on GPU. Import on GPU, or use a version with this fix.

**OLMoE recipes:**
- With real Transformer Engine and `runtime_config_update()`, all three recipes (pretrain, SFT, PEFT) match `main` on all 384 shared model fields, and every other section is identical. Unlike the CPU check above, the precision-aware optimizer stays on.
- 20 pretraining iterations with `run_recipe.py --deterministic`, mock data, global batch 64 and EP 8: this branch and a repeat of `main` match `main` bitwise at every iteration, for lm loss (11.2413 → 6.8080), load-balancing losses and grad norm.

# Additional Information

- Part of the incremental provider → builder migration. With this PR, Llama and OLMoE are fully migrated.
- The provider path already built YaRN through the shared `provider_bridge()`, but `get_model_config()` overwrote it with plain RoPE. So turning on the conversion flag alone would have dropped YaRN on conversion. This PR therefore includes the fix from #6597: `setdefault` for `position_embedding_type`, and a `ValueError` for llama3 RoPE settings Megatron Core cannot apply. #6597 carries the same commit on its own; whichever merges first, the other's RoPE diff becomes a no-op.
