# fix(ckpt): coordinate synchronous torch_dist saves on a gloo group

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6477) · state: open · merged: False

## Original PR description

# What does this PR do ?

Fixes NVBug 6900704. Synchronous `torch_dist` checkpoint saves now let torch DCP exchange its save plans and write results over a gloo process group instead of the default NCCL group. As a result, the coordinating rank no longer keeps NCCL point-to-point buffers to every other rank after the first save. Those buffers took 2.6 GiB on rank 0 of an 8-GPU H100 node.

# Changelog

- `src/megatron/bridge/training/checkpointing.py`:
  - `_dcp_save_coordination_group()` creates one world-size gloo group, collectively, on the first save. It does this only when `dist.use_gloo_process_groups` is enabled, the job has more than one rank, and the default group is not already gloo. The group uses the default group's post-initialization timeout, and it is recreated if the default process group changes.
  - `_GlooCoordinatedTorchDistSaveShardedStrategy` runs MCore's synchronous `TorchDistSaveShardedStrategy.save()` but passes that group to `torch.distributed.checkpoint.save()`. The written checkpoint is unchanged.
  - `save_checkpoint` uses this strategy for synchronous MCore distributed-checkpoint saves.
  - Unchanged: async (nvrx) saves, `fsdp_dtensor` saves, conversion code that supplies its own strategy, and runs with `dist.use_gloo_process_groups=False`.
- `tests/unit_tests/training/test_checkpointing.py`: new tests cover:
  - when the gloo group is used, and which timeout it gets;
  - reuse of the group across saves, and recreation when the default group changes;
  - a real single-rank save whose DCP call, planner, writer, and checkpoint metadata match MCore's own save, and that reloads;
  - strategy selection in `save_checkpoint` for sync and async saves, with and without fully parallel save.
- `docs/training/checkpointing.md` and its nightly Fern mirror: a new "Save Coordination" section.

# Additional Information

- Related to NVBug 6900704.

**Problem.** MCore's `TorchDistSaveShardedStrategy.save()` calls `torch.distributed.checkpoint.save()` without a process group, so DCP coordinates on the default NCCL group. There, DCP's `gather_object` and `scatter_object_list` run as point-to-point operations, and after the first save the coordinator rank keeps NCCL buffers for a connection to every other rank for the rest of the run.

On one 8xH100 node with `nemotron_omni_cord_v2_sft_8gpu_h100_bf16_config`:
- Rank 0's non-PyTorch memory grows from 7.04 to 9.67 GiB at the first save, and measured ranks 1 and 7 grow from 7.04 to 7.42 GiB.
- With `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` set before launch, GPU 0 already uses about 80,400 of 81,559 MiB (nvidia-smi) before any save.
- So the step right after the step-50 save runs out of memory on rank 0.

**Verification.**
- Unit tests: `tests/unit_tests/training/test_checkpointing.py` and `tests/unit_tests/training/test_model_load_save.py`: 362 passed, 1 pre-existing skip.
- In-process memory: same container, same tree with and without this change, 4 steps with saves at steps 2 and 4.
  - Without the change: rank 0's non-PyTorch memory goes from 7.04 to 9.67 GiB at the first save. `gather_object` on NCCL adds 2.19 GiB and `scatter_object_list` adds 0.44 GiB.
  - With the change: ranks 0, 1, and 7 stay at 7.04 GiB across both saves.
  - Device memory on GPU 0 after the next step: 75.33 GiB with the change, 77.96 GiB without.
- End to end on 1x8 H100: the model verification card's `sft.H100` command (100 steps, saves at 50 and 100), with `expandable_segments:True` set before launch.
  - Before: the step-50 save completes, then step 51 runs out of memory on rank 0 (78.98 of 79.11 GiB in use).
  - After, training: all 100 steps complete. LM loss goes from 1.2788 to 0.0369, with no skipped or NaN iterations.
  - After, checkpoints: the step-50 and step-100 checkpoints are complete. The step-50 checkpoint has the same DCP metadata (6,808 entries; keys, shapes, dtypes, chunks) as the step-50 checkpoint of the run without the change.
  - After, resume: a fresh-process resume from step 50 reproduces the step-51 loss exactly and reaches step 100. Loading the step-100 checkpoint and training one more step also works.
- On 2 nodes (16 GPUs), saves at steps 2 and 4 complete with the gloo group spanning both nodes.

**Follow-up.** MCore's `TorchDistSaveShardedStrategy` could accept a process group for both its sync and async paths, so Bridge can drop this override.
