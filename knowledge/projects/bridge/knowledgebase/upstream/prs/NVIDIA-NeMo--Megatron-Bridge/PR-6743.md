# refactor(model): build Step-3.7-Flash from a builder-backed model config

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6743) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves **Step-3.7-Flash** (`Step37Bridge`, the Step-3.5 text decoder plus a Perception-Encoder G/14 vision tower) from `Step37ModelProvider` to a builder-backed `ModelConfig` + `ModelBuilder`, for recipes and checkpoint conversion, and switches its recipes to `get_model_config()`. Part of the provider → builder migration (MB-1857).

# Changelog

- **`Step37ModelConfig`** (new, `stepfun/step37_config.py`): subclasses `Step35ModelConfig`, so its language half is the Step-3.5 builder config from #6693 (`Step35TransformerConfig`).
  - The vision-language settings are outer fields with the provider's names and defaults: the Hugging Face `vision_config`, `image_token_id`, `understand_projector_stride`, `projector_bias`, `language_max_sequence_length` and the three freeze options. `position_embedding_type` defaults to `"rope"`, as on the provider.
  - `as_dict()`/`from_dict()` serialize the vision config the way provider checkpoints do. The Step-3.7 vision configs set their shape (`width`, `layers`, ...) in `__init__` instead of declaring dataclass fields, so Megatron Core's field-by-field form would reload a default 47-layer tower.
- **`Step37ModelBuilder`** (new, `stepfun/step37_builder.py`): subclasses the GPT builder and builds the existing `Step37Model`, so checkpoint keys and the bridge's registered target stay the same. It resolves the decoder spec as `provide()` does (no MTP block, as before), applies the freeze options, and casts the vision tower and the projector to `params_dtype`: they are torch modules created in FP32, which the provider path casts through `Float16Module`, but builder conversion runs without that wrapper.
- **`Step37Model`** takes an optional `model_config`. A builder passes its outer config, which owns the construction settings (image token ID, projector bias, vocabulary and RoPE options) that a provider carries on the language config.
- **Bridge**: `MODEL_CONFIG_CLASS = Step37ModelConfig`, `USE_MODEL_CONFIG_FOR_CONVERSION = True`; the `provider_bridge()` override is gone.
  - `hf_config_to_model_config_kwargs()` starts from `Step35Bridge`'s kwargs for `text_config` and adds the vision-language fields. Where the Step-3.7 provider set a field differently, it is set as the provider set it: `use_qk_norm`, `tie_word_embeddings` and `use_head_wise_attn_gate` default to Step-3.7's values (the Step-3.7 `text_config` omits them), `attention_output_gate` keeps the checkpoint's value instead of Step-3.5's fallback for older Megatron Core, `layer_types` keeps only the main decoder's entries, and the position embedding stays `"rope"`.
  - `hf_config_to_provider_kwargs()` returns the same kwargs plus the provider-only `attention_other_setting`, so the deprecated provider path keeps every provider field (checked field by field, see below).
- **Step-3.5 decoder layer on Megatron Core dev** (`step35_bridge.py`, `step35_provider.py`): Step-3.7 needs Megatron Core dev (native head-wise gate, `rotary_base_per_layer`). There, each attention layer builds its own rotary embedding and reads `position_embedding_type`, `rope_scaling`, `rope_scaling_factor` and `rotary_scaling_factor` from its layer config. A provider carries them; a builder config keeps them on the outer GPT config, so on `main` a builder-built Step-3.5 model fails there with `AttributeError` (and the new Step-3.7 builder would too). For builder configs, `build_step35_layer_spec` now passes them to each `Step35DecoderLayer` as a spec param, and the layer copies them onto its private config copy. Providers are unchanged, and the Megatron Core main pin has no per-layer rotary embedding, so the copies are unused there.
- **Recipes**: both Step-3.7 recipes build their model with `AutoBridge.from_hf_pretrained(...).get_model_config()`.
- **Tests**:
  - Bridge: the builder mapping without the provider path (with and without native head-wise gate support), the Step-3.7 defaults that differ from the Step-3.5 text mapping, HF flags overriding them, builder vs provider on every shared field, and a serialization round trip that keeps the vision config.
  - Builder: arguments passed to `Step37Model`, the vision and projector cast, later pipeline stages, decoder spec resolution, and invalid configs.
  - Step-3.5: builder configs pass the RoPE settings to every decoder layer (including the MTP layer), providers pass none, and the layer applies them to its own config copy only.
  - Recipes (`test_step37_recipes.py`, new): both recipes build a real, strict `Step37ModelConfig` and the stub rejects `to_megatron_provider()`. The Flickr8k recipe stub now provides `get_model_config()`.

# Behavior notes

- **Checkpoint format:** `AutoBridge.import_ckpt` and `convert.sh import` now write builder-format checkpoints for Step-3.7. `main` cannot load them (no `Step37ModelConfig` there); this branch loads `main`'s provider checkpoints.
- **`moe_layers_enum=None` (synthetic only):** without the Step-3.5 MoE schedule the provider keeps `GPTModelProvider`'s `default_layer_spec`, which `provide()` then calls with `vp_stage` and fails. The builder falls back to `get_step37_text_layer_spec`, as `provide()` intends. Released configs always carry `moe_layers_enum`.

# Not changed (follow-ups)

- **MTP layers:** Step-3.7 keeps `mtp_num_layers` from the checkpoint (3) but builds no MTP block, on `main` and here. A strict export (the CLI default) therefore fails on both trees with `54 tensors from the original checkpoint were not written`, and on Megatron Core dev the GPT post-processing still runs the MTP loss, so inference needs `disable_mtp_for_inference()` (as `compare.py` does). Only the smoke recipe sets `mtp_num_layers=0`; the 64-GPU SFT recipe keeps 3, so on Megatron Core dev its training takes the same MTP-loss path (from reading the code; not run). Building the MTP block would also need the unmerged Step-3.5 MTP fixes (layer index at PP>1, per-layer RoPE base).
- **RoPE scaling:** Hugging Face applies the `text_config`'s llama3-style `rope_scaling` (factor 2, original 131072, high-frequency factor 32) to the full-attention layers (`yarn_only_types: ["full_attention"]`). Neither path maps it, so those layers use unscaled RoPE in Megatron, and the gap grows with position. Megatron Core's llama3 scaling hard-codes Llama 3.1's frequency factors and original length (1, 4, 8192), so it cannot express these settings as is.
- **Docs:** `examples/models/stepfun/step37/slurm_pretrain.sh` launches `--recipe step37_flickr8k_sft_smoke_config`, which does not exist (`step37_sft_flickr8k_smoke_config`). The README's `./scripts/switch_mcore.sh dev` selects `.dev.commit` 4a4de865, which lacks `megatron.training.models.hybrid.resolve_hybrid_stack_spec` that Bridge main imports; these checks used dev HEAD c4220af3a.
