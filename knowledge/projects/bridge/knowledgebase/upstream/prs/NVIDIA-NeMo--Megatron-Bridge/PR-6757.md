# fix(training): read pinned tokenizer revisions from the cache when offline

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6757) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Fixes offline runs of recipes that pin a Hugging Face tokenizer revision. With `huggingface_hub` 2.0–2.1, tokenizer setup tried to reach the Hub and failed with `OfflineModeIsEnabled`, even though the snapshot was already in the cache.

# Changelog

- `_resolve_hf_tokenizer_revision` now passes `local_files_only=HF_HUB_OFFLINE` to `snapshot_download`, as `models/hf_pretrained/state.py` already does for model snapshots. Online behaviour is unchanged.
- New unit test: `local_files_only` follows `HF_HUB_OFFLINE`.

# Root cause

When `revision` is a full commit hash, `huggingface_hub` 2.0.0–2.1.1 skips its guarded `repo_info` lookup. It then calls `list_repo_tree` outside the `try` block, so with `HF_HUB_OFFLINE=1` it raises `OfflineModeIsEnabled` instead of falling back to the cache. 2.2.0 moved that call inside the `try`.

Bridge's locked version (2.4.0) is not affected, but environments that ship 2.0–2.1 are. In those environments, offline runs of recipes that set `hf_tokenizer_kwargs={"revision": ...}` fail at tokenizer setup. The Qwen3.5 text pretrain recipes are one example.

# Testing

- `tests/unit_tests/training/test_tokenizer.py`: 18 passed. The new test fails on `main` with `KeyError: 'local_files_only'`.
- Direct reproduction against a cache that holds only `refs/` and `snapshots/`, with `HF_HUB_OFFLINE=1` and a full-commit revision:
  - `huggingface_hub` 2.1.1 raises `OfflineModeIsEnabled` without `local_files_only` and succeeds with it.
  - `huggingface_hub` 2.4.0 succeeds either way.
- `pre-commit run --all-files` is clean.
