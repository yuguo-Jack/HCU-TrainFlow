# fix(data): bound packed Parquet shard readers

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6087) · state: closed · merged: False

## Original PR description

## Summary

Bound packed-Parquet shard readers per DataLoader worker with an eight-entry LRU.

## Trigger and impact

Training from a supported packed-Parquet glob or directory with enough shards and persistent workers causes each worker to retain every visited `ParquetFile`. Descriptor usage grows with shard count until training fails with `Too many open files`.

## Root cause

`GPTSFTPackedParquetDataset._ensure_reader()` cached every opened shard in `_parquet_files`. Row-group cache eviction did not close shard readers; cleanup happened only at dataset teardown.

## Fix

Keep an eight-reader LRU per worker. Cache hits refresh recency; misses evict and close only the least-recently-used reader. This bounds resource retention while preserving recent-shard and row-group reuse.

- claude[bot] · comment · 2026-09-13T10:38:48Z · [source](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6087#issuecomment-5652757655)

Light review - LGTM with one minor note

The LRU bounding of the open-Parquet reader cache is correct:
- Cache hit pops and re-inserts to mark most-recently-used (parquet.py:305-307).
- Miss at capacity evicts the oldest insertion-ordered entry (parquet.py:309-315).
- The materialized row-group table cache is independent of the reader handle, so eviction cannot invalidate it. No correctness regression.

Minor:
- The eviction path (parquet.py:312-315) closes handle then pf without the best-effort try/except that close() uses (parquet.py:352-363). On the local-file path handle is None (safe), but on the MSC seekable path pf wraps handle, so closing handle first could make pf.close() raise and propagate up through getitem during iteration. Consider guarding it to match close().
- The _ensure_reader docstring no longer reflects the new bounded-LRU behavior; a one-line update would help.

Suggested test cases
- tests/unit_tests/data/packing/test_parquet.py::TestPackedParquetDatasetMultiFile::test_persistent_workers_bound_open_shard_readers
- tests/unit_tests/data/packing/test_parquet.py::TestPackedParquetDatasetMultiFile::test_reader_cache_is_bounded_and_reuses_recent_shards

No perf tests impacted.

I also ran into the issue that was supposed to be fixed in this PR. It has been closed for no apparent reason—are there no plans for a fix?

Beyond the exhaustion of file descriptors, a single reader can leave behind memory roughly the size of the file. Since this is outside the Arrow memory pool, it doesn't show up in `pa.total_allocated_bytes()`. As a result, the `DataLoader` worker may be killed during prolonged SFT.
