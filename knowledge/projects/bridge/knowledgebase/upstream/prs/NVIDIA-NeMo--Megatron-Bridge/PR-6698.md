# fix(ckpt): keep per-group LR overrides when restoring scheduler bounds on resume

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6698) · state: open · merged: False

## Original PR description

# What does this PR do ?

With `scheduler.override_opt_param_scheduler`, resuming from a checkpoint reset every optimizer parameter group's `max_lr` / `min_lr` to `optimizer.lr` / `min_lr`. Groups that get their own learning rate from `optimizer_config_override_provider` lost it on every resume. This PR keeps those groups' bounds.

# Changelog

- `_restore_scheduler_runtime_overrides` (added in #6209) runs after the checkpoint's optimizer state replaces the param groups and sets each group's LR bounds from the config. Default groups take `optimizer.lr` / `min_lr`, and decoupled-LR groups take the decoupled bounds; both are unchanged by this PR. Groups with their own LR override (`default_config=False`) now get back the bounds they were built with. Those bounds are snapshotted before the optimizer state is loaded.
- If the param groups change during the load (their number, or which of them follow the default LR schedule), it warns and falls back to the previous behavior.
- Unit tests: a two-group optimizer keeps its override group's bounds across the restore; through `_load_checkpoint_from_path`, an override group whose bounds the checkpoint load made stale gets its built bounds back; the fallback when the group count or layout changes. With the snapshot not passed to the restore, or with a count-only guard, the new cases fail.

Found with LSQ scale learning (https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6699), where the scale group runs at its own learning rate on top of `optimizer.lr = 0`. On resume the scale group's `max_lr` dropped from 1e-4 to 0, so the scales stopped training. The iteration-10 and iteration-20 checkpoints of a Qwen3-1.7B run resumed at iteration 10 had byte-identical scales.

The fix is correct: `default_config` is False in Megatron-LM's `_get_param_groups` exactly when a group's override carries an LR key, each group's `max_lr`/`min_lr` is set at build time, and the snapshot is taken before the checkpoint's groups replace them. The helpers and tests are in the right files, next to `_restore_scheduler_runtime_overrides` and its existing tests.

Needs action:
- [ ] Add a test through `_load_checkpoint_from_path`, or at least one asserting the snapshot is taken before the load and passed to the restore. No test covers the call site, so dropping the `built_lr_bounds` argument would still pass (inline).
- [ ] Tighten the group-change guard from "same count" to "same count and same `default_config` flags per index"; otherwise a reordered or changed set of override groups with equal count silently gets the wrong bounds (inline).

No action needed:
- A group with only an `lr_mult` override has `default_config=False`, but its built bounds equal the config's, so restoring them changes nothing.
- A changed provider LR on resume is honored, since the snapshot comes from the current config.
- The Qwen3-1.7B resume check in the description (iteration-3 loss and grad norm matching the uninterrupted run) is a good real-run validation.
