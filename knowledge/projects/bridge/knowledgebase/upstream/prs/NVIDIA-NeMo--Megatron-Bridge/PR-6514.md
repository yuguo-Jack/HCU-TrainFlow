# fix(checkpoint): align release optimizer indices with shard order

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6514) · state: closed · merged: False

## Original PR description

DeepSeek-V4 pretraining on `r0.7.0` completes training but fails when saving distributed optimizer state: the checkpoint lookup can select a different parameter's tensors in mixed FP32/BF16 groups. This blocks the unrelated recipe cherry-pick #6497 on both [H100](https://github.com/NVIDIA-NeMo/Megatron-Bridge/actions/runs/38929440133/job/117117199682) and [GB200](https://github.com/NVIDIA-NeMo/Megatron-Bridge/actions/runs/38929440133/job/117117198957).

The release's MCore pin `e0c5e186` constructs checkpoint indices in gradient-buffer order, while its optimizer stores native FP32 shards before BF16-derived shards. [Megatron-LM #7336](https://github.com/NVIDIA/Megatron-LM/pull/7336) fixes that ordering upstream. This release-only adaptation rebuilds the lookup immediately after optimizer construction, before checkpoint loading, using the final shard order. It covers nested optimizer chains and excludes stub/FSDP instances. It preserves the MCore pin, optimizer state, and all existing checkpoint tests.

Cause: **1. Megatron LM bug**, already fixed upstream; not caused by #6497. The relevant DeepSeek test/recipe, optimizer setup, and MCore pin are unchanged between #6497 and its release base.

Validation against the exact release MCore pin:
- Disabling only the new correction reproduces four failures: mixed unequal-sized parameters select the wrong shape, and equal-sized parameters select the wrong values, in both ordinary and precision-aware accessor paths.
- With correction: **71 passed, 6 GPU-only cases skipped**, including existing optimizer tests and new save/restore identity checks for mixed/homogeneous dtypes, multiple/empty groups, nested chains, and stub/FSDP exclusions.
- All-file pre-commit, diff checks, and independent review passed.
- CPU tests exercise real MCore index construction and checkpoint get/set methods; precision-aware storage uses a CPU test double. Full TE/distributed execution is not established locally. Existing L0 DeepSeek jobs on H100/GB200 will validate the failing save path. A separate upstream DP-tail-padding fix is not included and may require follow-up if CI exposes it.
