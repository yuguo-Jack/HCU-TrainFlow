# refactor(model): build Nemotron Omni and Super VL from a builder-backed model config

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6710) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves the **Nemotron Omni** bridges (`NemotronOmniBridge` for Nemotron-3 Nano and Super Omni, `Nemotron35SuperVLBridge` for Nemotron 3.5 Super VL, and the bridge for checkpoints with the historical `NemotronH_Nano_VL_V2` label) from `NemotronOmniModelProvider` to a builder-backed `ModelConfig` + `ModelBuilder`, for recipes and checkpoint conversion, and switches the Omni and Super VL recipes to `get_model_config()`. The language model sits on the shared `BridgeHybridModelConfig` (#6609); the builder builds the existing `NemotronOmniModel`, including the RADIO vision encoder and the Parakeet sound encoder.

# Changelog

- **`NemotronOmniModelConfig`** (new, `nemotron_omni/nemotron_omni_config.py`): subclasses `BridgeHybridModelConfig`, so the language half is the Nemotron-H hybrid config. The media settings are fields of the outer config with the provider's names and defaults: `image_token_index`, the RADIO options, vision recompute, the temporal video embedder, sound (`has_sound`, `sound_config`, ...), `vision_dp_over_cp` and the five freeze options. `finalize()` runs the provider's validation (dynamic resolution, a positive image token, and a sound token plus `sound_config` when sound is enabled).
- **`NemotronOmniModelBuilder`** (new, `nemotron_omni/nemotron_omni_builder.py`): subclasses `BridgeHybridModelBuilder` and builds `NemotronOmniModel` with the same arguments as `NemotronOmniModelProvider.provide()`. The vision, projector and sound config derivations moved from provider methods into helpers in this module; the provider methods now call them, so the two paths share one implementation.
  - It casts the vision and sound encoders to `params_dtype`. The Hugging Face Parakeet sound encoder is created in FP32; on the provider path `Float16Module` casts it with the rest of the model, but builder conversion runs without that wrapper and would otherwise save FP32 sound weights.
  - It passes `model_config.transformer` as the language config (as MCore's `HybridModelBuilder` does), and passes its process groups to the model; the provider let the model fall back to the global ones, which are the same groups in standard runs.
- **`NemotronOmniModel`** takes an optional `model_config` and reads `logit_dtype` from it, as `Qwen3VLModel` does in #6695. Providers do not pass it.
- **Bridges**: `NemotronOmniBridge`, `Nemotron35SuperVLBridge` (inherited) and the V2-label alias set `MODEL_CONFIG_CLASS = NemotronOmniModelConfig` and `USE_MODEL_CONFIG_FOR_CONVERSION = True`.
  - The `provider_bridge()` assignments move to `hf_config_to_model_config_kwargs()`. It also sets the `NemotronOmniModelProvider` defaults that differ from the builder config's, with `setdefault` so a value mapped from the Hugging Face config still wins, as it did on the provider.
  - `hf_config_to_provider_kwargs()` returns the same kwargs plus the provider-only fields, so the deprecated provider path keeps every provider field. `NemotronOmniBridge.provider_bridge()` is now the base implementation (it skips `NemotronVLBridge`'s routing of the V2 label); `Nemotron35SuperVLBridge` no longer overrides it.
  - The V2-label alias maps MoE configs like the canonical bridge and rejects dense configs on both paths; `NemotronVLBridge._legacy_omni_bridge()` holds the shared routing.
  - `NemotronOmniLlavaBridge` (deprecated, unregistered) builds `NemotronOmniLlavaModel` through its provider, so it opts out: `MODEL_CONFIG_CLASS = None`, `USE_MODEL_CONFIG_FOR_CONVERSION = False`, and the base `hf_config_to_model_config_kwargs()` restored. Its provider kwargs come from the Omni mapping.
- **Recipes**: the 7 Nemotron Omni H100 recipes and the 8 Super VL recipes (3 H100, 4 GB200, and the GB300 MXFP8 recipe from #6614) build their model with `get_model_config()`. They share `_nemotron_omni_base()` and `_nemotron_35_super_vl_base()`, which are the only call sites that change. The GB300 recipe's NCCL EP field check is unchanged; its docstring now names the model config.
- **Docs and skill**: the Super VL page says "model config options" for the freeze flags (Markdown and fern). `adding-model-support/vlm-patterns.md` lists Nemotron Omni as the HybridModel VLM reference.
- **Tests**:
  - Config and builder (`test_nemotron_omni_builder.py`): `run_config` round trip, media defaults equal to the provider's, rejection of provider-only fields, `finalize()` validation, and the builder vs the provider for Nano and Super VL: every argument passed to `NemotronOmniModel`, including the language, vision and projector configs field by field and the sound projector. Also the encoder cast, freezing, and media placement on the first pipeline stage.
  - Bridges: the builder mapping without the provider path, builder vs provider on every shared field (raw and finalized) and in `megatron_to_hf_config()` for Nano, Nano without sound, Super VL and the V2 label; the V2 routing and dense rejection; Super VL's two MTP depths; the LLaVA bridge staying on its provider.
  - `NemotronOmniModel` reads `logit_dtype` from `model_config`.
  - Recipes: the stubs now return a real, strict `NemotronOmniModelConfig` (so a recipe assigning an undeclared field fails) and fail on `to_megatron_provider()`. The GB300 recipe test checks its changed fields against the builder config. The L1 functional recipe test builds a tiny `NemotronOmniModelConfig` and shrinks RADIO through the builder's vision-config helper, instead of a tiny provider subclass.

# Behavior notes

- **Provider-only fields.** The builder config does not declare seven provider fields that the expanded-sequence model never reads: `vision_model_type`, `language_model_type`, `tokenizer_type`, `img_start_token_id` and `img_end_token_id` (used only by the LLaVA provider), `nemotron_omni_contract` (guards provider checkpoints against the LLaVA layout; a builder checkpoint names its class instead), and `scatter_embedding_sequence_parallel`. `keep_mtp_spec_in_bf16` is dropped as for Nemotron-H. The provider path still sets all of them.
- **Checkpoint format:** `AutoBridge.import_ckpt` and `convert.sh import` now write builder-format checkpoints for these models. `main` cannot load them, because `NemotronOmniModelConfig` does not exist there. This branch loads `main`'s provider checkpoints (verified on GPU below). NeMo RL's `megatron_bridge` checkpoint loader cannot read builder-format checkpoints yet; that applies to every migrated family.
- **Mamba `A_log` and `D` are stored in FP32.** Builder imports keep the dtypes Megatron Core creates them in, as the Nemotron-H builder on `main` already does; the provider's `Float16Module` stored them in BF16. The values are equal, every other tensor is identical, and the exports from either checkpoint are byte-identical.
- **Deprecation warning:** `NemotronOmniBridge.provider_bridge()` and `to_megatron_provider()` now emit the builder deprecation `FutureWarning`, as every migrated family does. MegatronMIMO conversion and the Nano Omni inference examples still build through the provider and keep working.
- Two pre-existing builder-path behaviors, not specific to this family: `load_model_config()` normalizes the deprecated `moe_hybridep_num_sms` alias only for provider configs, so the four GB200/GB300 Super VL recipes reload with `moe_hybridep_num_sms=32` instead of `null` (the effective flex-dispatcher SM count is the same). `AutoBridge.get_model()` with its default wrapper rounds the router's FP32 `expert_bias` to BF16, which the provider path's wrapper preserves.

mamba_ssm's SSD scan kernels choose their Triton block sizes by benchmarking in each process, so the logits of an input longer than one 128-token chunk can differ in the last bits between two runs of the same tree. The logits rows use Triton's persistent autotune cache (`TRITON_CACHE_AUTOTUNING=1`): a first run on `main` tunes the kernels and every compared run reuses those configs. Without the cache, Super VL's image and video logits, and Nano's in-memory run on `main`, differed from other runs of the same tree. Loaded in one process, which tunes once, the provider-built and builder-built Super VL models give bitwise-equal logits in either order.

**Config parity on CPU** (Megatron Core `3ddfe0fe`, transformers 5.20.2). Inputs: the published Nano Omni config at the recipe pin (`24e67ea0`) with and without its sound config, the published Super VL config (`fb0ee0bc`) as the remote-code `llm_config` and through Transformers' native `text_config`, three internal Super Omni configs, two internal Nano Omni configs with the V2 label, and seven unit-test mocks (16 cases). The real configs were rebuilt from `config.json` without running repository code.
