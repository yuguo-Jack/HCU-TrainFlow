# feat(training): run the dynamic CP example on Megatron-Core main with DCP v2

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6670) · state: closed · merged: False

## Original PR description

## What

Move the dynamic context parallel (DCP) example, docs, validation messages and tests onto the Megatron-Core `main` pin and DCP v2, and make the example run on mock data with a measured speedup over static CP. DCP v2 parts 1/4 to 3/4 are already in the pinned `main` commit, so no pin bump is needed, and nothing in this change asks for the `dev` pin.

## Changes

- **Packing demo** (`dynamic_context_parallel.py`) rewritten to the v2 scheduler API: valid group sizes of the `dp x cp` pool, the smallest group per sample (`dcp_gpus_needed` no longer exists on `main`, so the old demo could not run), the new `--cp-group-sizes` option, and the scheduler's estimated per-rank work.
- **Qwen3.5 example** (`qwen35_35b_a3b_dynamic_cp.py`): `--tiny-model` is now a full-attention MoE model that scales with the GPU count, without the recipe's MTP layer. It cycles its generated dataset and neither saves nor resumes checkpoints. `--static-cp` runs the static baseline on the same packing path.
- **Validation** rejects dynamic CP on models with Gated DeltaNet/KDA layers or multi-token prediction, with an explanation (see below).
- **Cleanup**: dev-only route prebuild removed from the packing glue; dev-pin skip gates and stand-in configs removed from the tests (so those tests always run); docs, README and the Fern copy updated (the two doc pages stay identical).

## Why the example needed more than a rewording

Running the existing example on `main` showed two gaps in Megatron-Core's DCP v2 that this change guards against instead of hiding:

1. **Gated DeltaNet**: GDN fixes its CP size at construction from the static CP group, so a bin placed on a smaller runtime group fails in the first forward pass (`GDN: cu_seqlens_q[-1]=4020 does not match total_sequence_length=8040`). MCore `dev` has explicit handling for this; `main` does not yet.
2. **Multi-token prediction**: under dynamic CP the MTP token roll (`_roll_tensor_packed_seq`) hangs. Reproduced at 2 and 4 GPUs; stack dumps show some ranks parked in that roll while others wait in a MoE all-to-all, and the NCCL watchdog eventually aborts the job. Static CP with MTP works, and dynamic CP without MTP works.

Both would otherwise surface as a hang or a cryptic error deep in the first step, so `ConfigContainer.validate` now raises a clear error. The full Qwen3.5-35B-A3B recipe is therefore rejected under dynamic CP until Megatron-Core supports runtime groups for both; the mock-data example is the supported way to run DCP meanwhile.

The example also had two usability defects found while measuring: a finite `single` loader raised `StopIteration` at the end of an epoch (the mock data now uses the `cyclic` loader), and a finished run's checkpoint in the default directory was picked up by the next run (a changed model failed with a state-dict `KeyError`; the same model would resume from the saved iteration, which breaks back-to-back dynamic-versus-static comparisons). Mock runs no longer save or resume checkpoints.

## Measurements

Four GB200 GPUs in one node, NeMo 26.10 rc5 container, Megatron-Core `main` pin, `--tiny-model` mock data. The first 12 steps are dropped as warm-up. Both modes process identical global batches in the same order and reach the same loss (final losses agree to four decimals).

| Topology | Global batch | Static CP median step | Dynamic CP median step | Static / dynamic total time |
|---|---|---|---|---|
| DP2 x CP2 | 32 | 702 ms | 638 ms | 0.89 |
| CP4 | 32 | 771 ms | 645 ms | 1.10 |
| CP4 | 128 | 2.82 s | 2.10 to 2.15 s | 1.31 to 1.46 |

The first two rows are single 40-step runs. The last row is two runs in opposite order (dynamic first, then static first), over steps 13 to 37 and 13 to 30.

Dynamic CP wins where static CP is expensive (one CP4 group, larger batch). With CP2 replicas on one NVLink domain the tiny model is dominated by per-step overhead and dynamic CP is slightly slower. The speedup also depends on the length mix: this mock stream has many samples that fit one rank. Step times vary because each step draws a different length mix and each newly seen packed shape pays a one-time kernel setup cost, so totals over the same steps are the fair comparison.

## Testing

- Unit tests: 694 pass across `test_config.py`, `test_global_batch_packing.py`, `test_gpt_step.py` and `tests/unit_tests/recipes/qwen`, including new tests for the GDN and MTP guards. 4 tests fail identically on an unmodified `main` copy in the same environment (DeepEP is unsupported on GB200 for the flex dispatcher, and Inductor needs a writable Triton cache directory); they are unrelated.
- End to end on 4 GPUs: dynamic and static runs complete with matching loss. The packing demo runs on `main`, including `--cp-group-sizes`.
- `ruff` 0.9.9 check and format are clean on the changed files.

## Not covered / follow-ups

- GDN and MTP under dynamic CP need Megatron-Core support; the two gaps above are worth reporting upstream.
- Bridge still requires a power-of-two `dp x cp` pool and `dist.use_decentralized_pg=False`; Megatron-Core's group-size helper handles other pool sizes, but I could not run a non-power-of-two pool here.
- Pipeline parallelism and VPP with dynamic CP are not exercised.
- I ran everything on a single 4-GPU node; the full 8-GPU recipe was not run.
