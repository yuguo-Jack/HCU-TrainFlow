# fix(recipe): enable sequence parallelism in Qwen3.5-VL recipes that train with TP > 1

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6541) · state: closed · merged: False

## Original PR description

# What does this PR do ?

Enable sequence parallelism in the Qwen3.5-VL recipes that train the language model with TP > 1, so the GatedDeltaNet `out_norm` weight gets the full gradient on every TP rank (fixes #6533).

The `out_norm` weight is replicated on every TP rank, but the value heads it scales are split across them, so each rank's backward only gives the partial gradient of its own heads. Megatron-Core sums that gradient across TP ranks only on the sequence-parallel path. With TP > 1 and sequence parallelism off, each rank applies a different partial gradient and the replicated copies drift apart. The loss and the global grad norm do not show it. #6533 has the measurements: relative error of the `out_norm` gradient against a float64 reference is 0.72 at TP=2 with SP off (the 4B SFT recipe) and 6.2e-3 with SP on (bf16 noise floor 4.5e-3).

The root fix is in Megatron-Core: NVIDIA/Megatron-LM#7613. It is not merged yet, so the pinned `3rdparty/Megatron-LM` cannot be bumped to a fixed commit yet. Until then, turning on sequence parallelism in these recipes is what makes them train correctly. It is also the usual setting with TP > 1, and the MoE Qwen3.5-VL recipes with TP = 2 already use it. Once the Megatron-Core fix is in the pinned submodule, sequence parallelism here is a performance choice again.

- `recipes/qwen_vl/h100/qwen35_vl.py`: `sequence_parallel = True` in `qwen35_vl_4b_sft_2gpu_h100_bf16_config` (TP2), `qwen35_vl_9b_sft_4gpu_h100_bf16_config` (TP4), `qwen35_vl_27b_sft_16gpu_h100_bf16_config` (TP4) and `qwen35_vl_27b_pretrain_16gpu_h100_bf16_mock_config` (TP4).

- Not changed: `qwen35_vl_9b_pretrain_4gpu_h100_bf16_mock_config` freezes the language model, and the PEFT recipes (for example the 27B TP2 LoRA recipe) do not train `out_norm`.
