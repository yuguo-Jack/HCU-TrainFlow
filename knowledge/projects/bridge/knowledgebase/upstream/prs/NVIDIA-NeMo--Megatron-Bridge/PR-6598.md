# refactor(model): build Qwen3-Next and Qwen3.5 from builder-backed model configs

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6598) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves the gated delta net (GDN) Qwen family onto the builder-backed `ModelConfig` / `ModelBuilder` path, for recipes and checkpoint conversion: **Qwen3-Next** (80B-A3B) and the **Qwen3.5 text bridges** (dense and MoE, which also serve Qwen3.6 27B and 35B-A3B). Follows Qwen3 dense (#6365), GPT-OSS (#6551) and the Qwen3 MoE draft (#6592).

# Changelog

- **`Qwen3NextBridge`, `Qwen35Bridge`, `Qwen35MoEBridge`**:
  - `provider_bridge()` is replaced by `hf_config_to_model_config_kwargs()`, and `hf_config_to_provider_kwargs()` reuses the same kwargs. All three opt in with `MODEL_CONFIG_CLASS = BridgeGPTModelConfig` and convert through the builder (`USE_MODEL_CONFIG_FOR_CONVERSION = True`).
  - The builder config leaves `transformer_layer_spec` unset: Megatron Core's GPT builder builds the hybrid GDN block from `experimental_attention_variant`. The provider path keeps `get_transformer_block_with_experimental_attention_variant_spec`.
  - Fields whose builder default differs from the provider's (`masked_softmax_fusion`, `rope_scaling_factor`, `position_embedding_type`) are set explicitly. MTP keeps `mtp_loss_scaling_factor=0.1` when the checkpoint declares MTP layers.
  - The Qwen3.5 LM settings move into `_qwen35_common_config_kwargs()` and `_qwen35_moe_config_kwargs()`. `_apply_qwen35_common_config()` and `_apply_qwen35_moe_config()` still apply them to providers, so the VL bridges, which stay on providers, are unchanged.
- **Recipes**: the Qwen3-Next H100 recipes and the Qwen3.5 GB200 text recipes call `get_model_config()` (6 call sites). The Qwen3.5 recipes still extract `text_config` from the multimodal checkpoint config. The Qwen3-Next perf recipes build on the pretrain recipe.
- **Tests**:
  - Bridge tests: builder mapping, provider/builder parity on every shared field (tied fp16, YaRN, explicit layer types, no MTP, and a text config extracted from a multimodal config), and the builder's GDN block-spec selection.
  - New `recipes/qwen/test_qwen3_next_recipes.py` and `recipes/qwen/test_qwen35_text_recipes.py` build every Qwen3-Next library and perf recipe and every Qwen3.5 text recipe against a real `BridgeGPTModelConfig`, with the provider API rejected.
  - `test_qwen35_text_long_context.py` reads the GDN fields from the nested transformer config.

## Behavior changes

- The Qwen3.5 text providers no longer carry `bos_token_id` / `eos_token_id`. Neither is a provider or model config field, and nothing reads them.
- YaRN-scaled configs now map to YaRN on both paths; `main` forced `"rope"` for these bridges. The base `provider_bridge()` selects YaRN once the override is gone, and the builder matches it. No released Qwen3-Next, Qwen3.5 or Qwen3.6 checkpoint uses YaRN.
- `qwen35_text_35b_a3b_sft_8gpu_gb200_bf16_dynamic_cp_config` sets `dynamic_context_parallel`, which only the Megatron Core dev pin declares. On the main pin the recipe now raises `AttributeError` at construction instead of failing `ConfigContainer.validate`; it needs the dev pin either way.

## NeMo RL

- NeMo RL builds through `to_megatron_provider()` and reads `multi_latent_attention`, `hybrid_layer_pattern` and `experimental_attention_variant` with `getattr`. All provider fields are unchanged (see Verification).
- **Checkpoint-format caveat:** with `USE_MODEL_CONFIG_FOR_CONVERSION = True`, `convert.sh import` / `AutoBridge.import_ckpt` now write builder-format checkpoints for Qwen3-Next and Qwen3.5/3.6 text checkpoints. NeMo RL's `checkpointing.pretrained_checkpoint` loader (format `megatron_bridge`) can't load those today: it calls `.provide()` and `register_pre_wrap_hook()`, which `BridgeGPTModelConfig` lacks. Not affected: checkpoints imported before this change, VL imports, NeMo RL's own HF conversion, and NeMo RL's export of its own checkpoints. The fix belongs in NeMo RL.
- NeMo RL's Qwen3.5 nightlies (`grpo-qwen3.5-9b-1n8g-megatron.sh` and the 35B-A3B and 397B runs) use the multimodal checkpoints, so they go through the VL bridges, which this PR leaves on providers. There is no Qwen3-Next nightly.

Pre-existing, identical on `main`, not addressed here:
- Round trips are not bit-exact for the GDN `A_log` and `linear_attn.norm.weight` of Qwen3.5 (fp32 in the source, bf16 in Megatron, zero-centered `w−1` mapping), or for `linear_attn.norm.weight` of Qwen3-Next (bf16 weights below 0.5 lose a bit).
- The Qwen3-Next bridge maps no MTP, so import and export drop its 1553 `mtp.*` tensors.
- Tied-embedding Qwen3.5 checkpoints with MTP (0.8B, 2B) can't be saved at PP > 1: Megatron Core's sharded state dict asserts on the MTP stage's output layer.
- compare.py can't run GDN text models: both the static inference context and `InferenceMode` hit GDN asserts. The logits above come from the same forward without `InferenceMode`.
