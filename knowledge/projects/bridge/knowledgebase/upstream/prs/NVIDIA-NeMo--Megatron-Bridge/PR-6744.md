## Original PR description

# What does this PR do?

Fix grouped weight export for Nemotron Omni and Super 3.5. Their custom flat exporter currently prevents AutoBridge's grouped ModelOpt export from running.

# Changelog

- Move the media customization into the existing weight-event hook, shared by flat and grouped export.
- Preserve conversion-task boundaries, checkpoint-only media buffers, required-video recovery, and precedence for trained video weights. Keep the grouped-export validation unchanged.
- Cover both model families, flat/grouped parity, recovered versus trained video weights, and existing pipeline/MIMO ownership behavior.

# Validation

- 25 focused native export tests passed, with no skipped tests.
- All pre-commit hooks passed.
- Local aggregate review found no remaining issues. Strict mypy still reports the same 41 target-file diagnostics as the unchanged parent; this change introduces none.

This validates the export correction; it does not establish full-model training or convergence.

- kevalmorabia97 · DISMISSED · 2026-11-02T20:01:29Z · [source](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6744#pullrequestreview-5742563019)

Thanks, moving the media handling into `_stream_weight_events_megatron_to_hf` is the right place: flat and grouped export now share one implementation, and the grouped-export guard can stay as it is. I checked:

- The new test fails on main with the guard's `NotImplementedError` for both bridges and passes here. Flat and grouped exports match in names, values and order, including the recovered and the trained video weight.
- `tests/unit_tests/models/nemotron_omni`, `test_auto_bridge.py` and `test_model_bridge.py` on nemo 26.10.rc9 (CPU): 438 passed. The one failure and one error need a GPU / a newer ModelOpt and fail the same way on main.
- Group order is the same on every rank: the passthrough groups depend only on the source checkpoint, and grouped export always runs with `current_pp_stage_only=False`.

Two non-blocking notes:

1. `export_hf_weight_groups_modelopt`'s docstring says it yields "One tuple per conversion task". Omni now also yields one group per source-only tensor after the tasks. NeMo-RL #3945 only relies on the order being identical across ranks, so it's fine there, but a line in the docstring would keep a caller from pairing groups with `plan.conversion_tasks`.
2. `KimiK3Bridge` overrides `stream_weights_megatron_to_hf` with the same passthrough pattern, so grouped ModelOpt export still rejects it. The same move would fix it; a follow-up is fine.

LGTM.
