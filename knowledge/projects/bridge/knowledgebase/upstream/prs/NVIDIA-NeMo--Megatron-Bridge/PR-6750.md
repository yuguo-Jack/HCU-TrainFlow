# refactor(model): build Kimi K3 and Sarvam MLA from a builder-backed GPT MLA model config

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6750) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Adds **`BridgeGPTMLAModelConfig`**, the GPT-side builder config for Multi-Latent Attention (the counterpart of `MLAModelProvider`, and the sibling of #6671's `BridgeHybridMLAModelConfig`), and moves **Kimi K3** (`KimiK3Bridge`) and **Sarvam MLA** (`SarvamMLABridge`, `sarvamai/sarvam-105b`) from providers to builder-backed model configs, for `get_model_config()` and checkpoint conversion. Part of the provider → builder migration (MB-1857: MB-1927, MB-1928). Neither model has a library or benchmark recipe on `main`, so no recipe changes.

# Changelog

- **`BridgeGPTMLAModelConfig`** (`gpt/model_config.py`): `MLAModelConfigMixin` on `BridgeGPTModelConfig`, nesting an `MLATransformerConfig`. As on the hybrid side, `rotary_base` and `rotary_percent` are stored and serialized only on the transformer config that MLA attention reads; the outer names are constructor arguments and views of the nested values, and the GPT builder passes those values to `GPTModel`.
- **Shared mapping** (`model_bridge.py`): for MLA configs, a `rope_scaling` of type `"deepseek_yarn"` (DeepSeek's YaRN, the name Sarvam MLA checkpoints use) maps to the MLA YaRN fields like `"yarn"`. Before, the MLA branch warned and fell back to no scaling. Non-MLA configs are unchanged.
- **`get_deepseek_decoder_block_spec`** (`deepseek/attention.py`) builds from a builder config's nested transformer config, so the GPT builder can use it (Sarvam MLA's spec: no query norm without a query LoRA).
- **Kimi K3**:
  - `KimiK3ModelConfig` + `KimiK3TransformerConfig` (new, `kimi/kimi_k3_config.py`): the transformer config declares the fields the KDA, MLA and AttnRes layers read (`kimi_kda_layers`, `kimi_linear_*`, `kimi_kda_gate_lower_bound`, `kimi_attn_res_block_size`) and keeps the provider's `variable_seq_lengths=True`. The standard GPT builder builds it.
  - Bridge: `MODEL_CONFIG_CLASS = KimiK3ModelConfig`, `USE_MODEL_CONFIG_FOR_CONVERSION = True`. `hf_config_to_model_config_kwargs()` maps `text_config` as `provider_bridge()` configured the provider, and `hf_config_to_provider_kwargs()` returns the same kwargs. The thin `provider_bridge()` override stays only to keep `position_embedding_type="none"`: the base path sets `"rope"` on every MLA provider. `mapping_registry()` reads the layer count from `hf_config` instead of a value cached by `provider_bridge()`.
  - `build_kimi_k3_spec` builds from a builder config's nested transformer config.
- **Sarvam MLA**: `MODEL_CONFIG_CLASS = BridgeGPTMLAModelConfig`, `USE_MODEL_CONFIG_FOR_CONVERSION = True`, and `SarvamMLAModelProvider` is registered on the bridge, so the base `provider_bridge()` builds it from the same kwargs; the override is gone. The kwargs set every value the provider set.
- Both bridges keep the provider values where an MLA provider (`MLATransformerConfig` + `GPTModelProvider`) inherits Megatron Core's defaults instead of `GPTModelProvider`'s: `deallocate_pipeline_outputs=False`, and for Sarvam MLA also `cross_entropy_loss_fusion`, `gradient_accumulation_fusion` and `masked_softmax_fusion` (`False`). `rope_scaling_factor` stays 1.0 (builder default 8.0, unused).
- **Tests**: the GPT MLA config (rotary storage and serialization, conflicting values, round trip, CLI overrides, builder arguments, bridge mapping); `deepseek_yarn` mapped for MLA configs only; both bridges' builder mapping without the provider path, builder vs provider on every shared field, round trips, the specs reading the nested transformer config. The Sarvam MLA tests use `SimpleNamespace` configs shaped like the remote `SarvamMLAConfig` instead of `Mock()`, which the shared mapping cannot read.
- **Skill**: `adding-model-support` points GPT MLA families at `BridgeGPTMLAModelConfig`.

# Behavior notes

- **Checkpoint format:** `AutoBridge.import_ckpt` and `convert.sh import` now write builder-format checkpoints for both models. `main` cannot load them (no builder config classes there); this branch loads `main`'s provider checkpoints.
- **Sarvam MLA YaRN:** the settings now come from the checkpoint's `rope_scaling` instead of fixed provider defaults. For `sarvam-105b` they are the same values (factor 40, original 4096, beta 32/1, mscale 1.0/1.0); `rotary_scaling_factor` is now `40.0` (the remote config class casts it) instead of `40`. A checkpoint with other YaRN values now gets them on both paths.
- The deprecated provider path (`to_megatron_provider()`) keeps every provider field and emits the usual `FutureWarning`.

# Not changed (follow-ups)

- **`sarvamai/sarvam-105b` on transformers 5.20:** its remote `SarvamMLAConfig.convert_rope_params_to_dict()` calls `validate_rope(ignore_keys=...)`, which transformers 5.20.2 (the version `uv.lock` pins) no longer accepts, so `AutoConfig` cannot load the published config there, on `main` as on this branch.
- **#6429** (draft) adds a Kimi K3 recipe with `to_megatron_provider()`; it can switch to `get_model_config()` once this merges. Every model field it sets is declared on `KimiK3ModelConfig`.
- Kimi-K2.5-VL (MB-1929) has a Kimi K2 MLA backbone and gets its own VL builder on top of this config in a stacked PR.
