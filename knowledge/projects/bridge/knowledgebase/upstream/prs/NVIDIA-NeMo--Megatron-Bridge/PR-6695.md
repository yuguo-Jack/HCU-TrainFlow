# refactor(model): build Qwen3.5-VL from a builder-backed model config

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6695) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves the **Qwen3.5-VL and Qwen3.6-VL** bridges (`Qwen35VLBridge`, `Qwen35VLMoEBridge`) from `Qwen35VLModelProvider` / `Qwen35VLMoEModelProvider` to a builder-backed `ModelConfig` + `ModelBuilder`, for recipes and checkpoint conversion, and switches their recipes to `get_model_config()`. It is the first vision-language bridge on the builder path; the VLM migrations that follow (Gemma 4 VL, GLM-4.5V, Nemotron Omni) can reuse the pattern.

# Changelog

- **`Qwen35VLModelConfig`** (new, `qwen_vl/qwen35_vl_config.py`), one class for dense and MoE:
  - Subclasses `BridgeGPTModelConfig`. Its language half is the Qwen3.5 text bridges' builder config (#6598).
  - The vision-language settings live on the outer config: the Hugging Face vision config, token IDs, vision geometry, `language_max_sequence_length`, freeze options, and the vision encoder's recompute and CUDA graph settings. `modality_keys` and `special_token_ids` match the providers.
  - `Qwen35VLTransformerConfig` declares only the fields that `Qwen3VLModel` and `Qwen3VLSelfAttention` read from the config they are built with: `apply_rotary_pos_emb_in_fp32`, `spatial_merge_size`, `vision_dp_when_cp`.
  - `finalize()` enables `calculate_per_token_loss` under context parallelism, as the providers do.
  - `vision_config` stays the Hugging Face config object, as on the providers. FLOPs, the training step and the vision encoder read it by attribute. It round-trips through `run_config.yaml` (tested).
- **`Qwen35VLModelBuilder`** (new, `qwen_vl/qwen35_vl_builder.py`): subclasses the GPT builder and builds the existing `Qwen3VLModel`, so checkpoint keys and the bridges' registered target stay the same. It resolves the hybrid GDN block spec and the MTP spec, patches standard attention with `Qwen3VLSelfAttention`, and applies the freeze options, as the providers' `provide()` does.
  - It also casts the vision encoder to `params_dtype`. `get_vision_model_config()` leaves the encoder in fp32. On the provider path, `Float16Module` casts it with the rest of the model, but builder conversion runs without that wrapper and would otherwise save fp32 vision weights.
- **`Qwen3VLModel`** takes an optional `model_config`. A builder passes its outer config, which owns the construction settings (token IDs, vocabulary padding, RoPE, vision encoder options) that a provider carries on the language config. Providers do not pass it, so Qwen3-VL and Qwen2.5-VL are unchanged.
- **Bridges**: `MODEL_CONFIG_CLASS = Qwen35VLModelConfig` and `USE_MODEL_CONFIG_FOR_CONVERSION = True`.
  - `hf_config_to_model_config_kwargs()` starts from the text bridge's kwargs for `text_config` and adds the vision-language fields. It also sets the three provider defaults the text kwargs differ on (`attention_softmax_in_fp32=True`, `bias_activation_fusion=True`, `autocast_dtype=None`).
  - `hf_config_to_provider_kwargs()` returns the same kwargs, so the deprecated provider path keeps every provider field.
  - `Qwen35TokenClassificationBridge` subclasses `Qwen35VLBridge` but stays on its provider. It sets `MODEL_CONFIG_CLASS = None` and `USE_MODEL_CONFIG_FOR_CONVERSION = False` and restores the base `hf_config_to_model_config_kwargs()`, as `DiffusionGemmaBridge` does for `hf_config_to_model_config()`. Its provider kwargs come from the Qwen3.5-VL mapping.
  - The now-unused `_apply_qwen35_common_config()` / `_apply_qwen35_moe_config()` are removed from the text bridge module.
- **Recipes**: the 33 Qwen3.5-VL library recipes (13 dense, 20 MoE) build their model with `AutoBridge.from_hf_pretrained(...).get_model_config()`; the private `_qwen35_vl_provider()` helper is gone. The 51 Qwen3.5-VL benchmark recipes in `perf_recipes/` build on them.
- **`qwen3_vl_step`** reads `seq_length` from `state.cfg.model`: a builder-built model's `config` is its transformer config, which has no `seq_length`. (#6354 makes the same change.)
- **GB200 35B-A3B MXFP8 perf recipe** now enables the TE RNG tracker for the CUDA graphs it turns on after `_benchmark_common()`, as `_enable_partial_cuda_graphs()` does. See Behavior notes.
- **Skill**: `adding-model-support/vlm-patterns.md` describes how to migrate a provider-based VLM. One sentence in `examples/models/qwen/qwen35_vl/README.md` changes from providers to the model config.
- **Tests**:
  - Builder config (`test_qwen35_vl_builder.py`): defaults, routing of flat overrides and rejection of undeclared names, `finalize()`, and a `run_config.yaml` round trip through `load_model_config()`.
  - Builder: the arguments it passes to `Qwen3VLModel` (configs, specs and attention patching), stage flags from the process groups, the vision encoder cast, freezing, and invalid configs.
  - Bridges: the builder mapping without the provider path, tied embeddings from the top-level config, and builder vs provider on every shared field. The token-classification bridge stays on its provider without a deprecation warning, and `test_gpt_model_config.py` checks that it exposes no builder mapping.
  - `Qwen3VLModel` reads its construction settings from `model_config` (CPU, mocked submodules).
  - Recipes: every library recipe builds a real, strict `Qwen35VLModelConfig`, so assigning an undeclared field fails. The recipe stubs now fail on `to_megatron_provider()`.

# Behavior notes

- **Undeclared provider attributes:** the providers lose three attributes that the old `provider_bridge()` set without declaring them: `head_dim`, `hf_text_config` and, for MoE, `audio_token_id`. Nothing reads them, and `kv_channels` already carries the head dimension.
- **Checkpoint format:** `AutoBridge.import_ckpt` and `convert.sh import` now write builder-format checkpoints for Qwen3.5/3.6-VL. `main` cannot load them, because `Qwen35VLModelConfig` does not exist there. This branch loads `main`'s provider checkpoints. NeMo RL's `megatron_bridge` checkpoint loader cannot read builder-format checkpoints yet; that applies to every migrated family.
- **Checks the providers skipped:** Megatron Core's `GPTModelConfig.finalize()` asserts that CUDA graphs use the TE RNG tracker and that virtual pipeline stages hold equal layer counts. `GPTModelProvider.provide()` makes the same checks, but the Qwen3.5-VL providers override `provide()`, so these recipes never hit them on `main`:
  - `qwen35_vl_35b_a3b_pretrain_8gpu_gb200_fp8mx_config` turns CUDA graphs on after `_benchmark_common()` has set the RNG trackers from the then-disabled graphs. It now enables both trackers, as `_enable_partial_cuda_graphs()` does.
  - The five 397B-A17B B200 and H100 benchmark recipes (60 layers, PP=8, VP=4) now fail in `ConfigContainer.validate()`. On `main` they already fail when the model is built: Megatron Core asserts `num_layers=60 should be divisible by pipeline_model_parallel_size=8`. This PR leaves their layout alone.

# Verification

**GPU parity on the published checkpoints.** Each model ran on one GB200 node (4 GPUs) in the NeMo 26.10 rc4 container, with Megatron Core `ed9c2c8c` for both trees and `NVTE_ALLOW_NONDETERMINISTIC_ALGO=0`. The runs compare `main` (97f10edd1, providers) with this branch at 99311a553; the last commit changes only the token-classification bridge. Conversion goes through `convert.sh`'s GPU import and export backends, and the logits come from `compare.py`'s forward.

- **Checkpoints.** `main` and this branch import each model with its first listed layout. Every `.distcp` shard and every other file is byte-identical except `run_config.yaml` (provider vs builder config) and DCP's `.metadata`, whose only differing field is `storage_meta` (the checkpoint path and a per-save UUID). Loaded tensor by tensor, the two checkpoints have the same keys, dtypes, shapes and values.
- **Exports.** This branch exporting its own checkpoint, this branch exporting `main`'s checkpoint, and this branch at each other layout all write the same bytes as `main` exporting its own checkpoint. Against the published safetensors, both trees differ in the same tensors, as `main` already does: the Qwen3.5 checkpoints store GDN `A_log` and `linear_attn.norm.weight` in fp32, and Megatron keeps them in bf16 (36 tensors for 0.8B and 2B, 96 for 27B, 60 for 35B-A3B). Qwen3.6-35B-A3B round-trips bit-exact.
- **Logits.** One image prompt (380–382 tokens, 364 of them image tokens) and one text prompt. `main` twice, this branch on its own checkpoint, this branch on `main`'s checkpoint, and both trees loading the HF weights directly all produce bit-identical logits, with the same next token as HF. Cosine is computed in float64 over the last-token logits.
- **Generation** (Qwen3.5-2B, `hf_to_megatron_generate_vlm.py`, image prompt, 48 greedy tokens): the same five configurations produce identical text.
- **Deterministic SFT smoke.** Two library recipes, each starting from `main`'s imported checkpoint on mock image conversations: `qwen35_vl_2b_sft_1gpu_h100_bf16_config` (full SFT, DP4, GBS 16) and `qwen35_vl_35b_a3b_peft_4gpu_h100_bf16_config` (LoRA, TP2×EP4, GBS 8). Each ran for 10 steps at sequence length 1024, twice on `main` and twice on this branch. Lm loss and grad norm are bitwise-identical at every step across all four runs (2B: 7.112 → 4.283; 35B-A3B: 6.892 → 4.439). The runs use `apply_determinism_overrides()` plus the torch GDN kernels with the pre-gated-delta-rule fusion off, which Megatron Core requires in deterministic mode.
- `main` cannot load this branch's checkpoints (see Behavior notes).

**Config parity on CPU** (Megatron Core `ed9c2c8c`, transformers 5.20.2). Inputs: all 21 published Qwen3.5/3.6-VL configs (Qwen3.5 0.8B, 2B, 4B, 9B and their -Base variants, 27B, 35B-A3B, 122B-A10B and 397B-A17B with -Base and -FP8 variants where published, Qwen3.6 27B and 35B-A3B with -FP8):
