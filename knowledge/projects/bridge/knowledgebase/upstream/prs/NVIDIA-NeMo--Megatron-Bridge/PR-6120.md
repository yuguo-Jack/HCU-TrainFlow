# feat(gemma4): allow CP > 1 on the dense model by building its layer spec with TE

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6120) · state: open · merged: False

## Original PR description

> [!IMPORTANT]
> **Depends on [NVIDIA/TransformerEngine#3527](https://github.com/NVIDIA/TransformerEngine/pull/3527).
> Please do not merge before that lands.**
>
> Without the TE change this is a regression in error quality rather than a fix: the provider
> stops rejecting CP > 1 early with a clear message, and the run instead fails later inside
> attention with "no backend is available", which says nothing about Gemma 4 or context
> parallelism. Details below.

## Problem

`Gemma4DenseProvider` rejects context parallelism outright:

```
NotImplementedError: Gemma4DenseProvider currently supports CP=1 only: its layer spec uses
the local DotProductAttention, which does not implement context parallelism.
```

The cause is that `get_gemma4_layer_spec()` hardcodes `LocalSpecProvider()`, whose
`core_attention()` is the non-TE `DotProductAttention`, and that module asserts
`context_parallel_size == 1`. The MoE path already supports TE through
`gemma4_block_spec(use_transformer_engine=...)`; the dense path simply had no equivalent.

## Change

- `get_gemma4_layer_spec()` takes `use_transformer_engine` (default `False`, so existing callers
  are unaffected). When `True` it builds from `get_backend("transformer_engine")`.
- `Gemma4DenseProvider` passes `use_transformer_engine=HAVE_TE`, matching the convention other
  providers in this repo already use.
- The CP guard now fires only when TE is unavailable, and its message says so.

Notably this needs **no** Gemma-4-specific core attention. `Gemma4TEDotProductAttention` exists to
set the per-layer window from the MoE-only `interleaved_attn_pattern`; the dense provider uses
`window_attn_skip_freq` instead, and MCore's own `TEDotProductAttention` already applies that per
layer (`is_layer_window_attention`). Using the MoE class here raises `AttributeError` on
`interleaved_attn_pattern`, and duplicating the rule would risk it drifting from
`Gemma4DenseSelfAttention`, which derives the same sliding-vs-global distinction to pick
`global_kv_channels`.

## Why it depends on the TE PR

Gemma 4 global layers use symmetric `head_dim=512`. No backend in released TE serves that head dim
together with context parallelism, so with stock TE this change lets model construction succeed
and then fails in the forward pass instead. TE#3527 adds the backend that makes the configuration
actually runnable.

## Verification

With TE#3527 applied, a 6-layer Gemma 4 dense model (5 sliding layers at `head_dim` 256 on
FlashAttention, 1 global layer at 512) trains under context parallelism on B200 and matches its
CP=1 result to **9.7e-05** on the loss and **2.4e-02** on total gradient norm, with identical data
and seeds and gradients reduced across the CP group.

Per-parameter localisation shows the global layer's deviation is *below* the average of the other
layers (0.59x), i.e. the residual gradient-norm difference is ordinary bf16 accumulation rather
than anything specific to that layer.

Tests: the CP rejection test now patches `HAVE_TE` to `False` and asserts the TE-specific message,
so the guard stays pinned for environments without TE. Two new spec tests assert that the default
path does *not* use TE attention and that `use_transformer_engine=True` does. Asserting on module
identity is deliberate: a spec that silently fell back to local attention would still build, and
would fail only once CP was switched on.
