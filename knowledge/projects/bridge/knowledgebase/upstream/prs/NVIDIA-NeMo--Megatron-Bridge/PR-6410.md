# fix(training): keep the direct HF tokenizer fields through __post_init__

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6410) · state: open · merged: False

## Original PR description

## Description

`TokenizerConfig(trust_remote_code=True)` comes back with `trust_remote_code=False`. So do `tokenizer_hf_no_use_fast` and `tokenizer_hf_no_include_special_tokens`, which are the three fields the deprecation warning two lines further down tells people to use instead of `hf_tokenizer_kwargs`.

`src/megatron/bridge/training/tokenizers/config.py:83-97`:

```python
        # HuggingFace tokenizer kwargs
        self.tokenizer_hf_no_use_fast = not self.hf_tokenizer_kwargs.get("use_fast", True)
        self.tokenizer_hf_no_include_special_tokens = not self.hf_tokenizer_kwargs.get("include_special_tokens", True)
        self.trust_remote_code = self.hf_tokenizer_kwargs.get("trust_remote_code", False)
        if self.hf_tokenizer_kwargs:
            warn_rank_0(
                "`hf_tokenizer_kwargs` is deprecated and will be removed soon. "
                "Please, use `tokenizer_hf_no_use_fast` / `tokenizer_hf_no_include_special_tokens` / "
                "`trust_remote_code` arguments directly instead."
            )
```

The three assignments sit outside the `if self.hf_tokenizer_kwargs:` guard, and the dict defaults to empty, so every construction rewrites them from the `.get` fallbacks. `build_tokenizer` then hands MCore a config in which those three are the fallbacks whatever the caller asked for, and `megatron/core/tokenizers/utils/build_tokenizer.py` turns them straight into `use_fast`, `trust_remote_code` and `include_special_tokens` for `AutoTokenizer.from_pretrained`.

Measured. The child `__post_init__` is the real file on `main` and the parent dataclass is the real source text of `megatron.training.config.TokenizerConfig`, lifted out with `ast` because importing it pulls all of `megatron.core` (python 3.12 and torch, neither of which I have here):

```
  asked trust_remote_code                        True -> got False
  asked tokenizer_hf_no_use_fast                 True -> got False
  asked tokenizer_hf_no_include_special_tokens   True -> got False
  asked tokenizer_sentencepiece_legacy           True -> got True
  hf_tokenizer_kwargs=None -> AttributeError: 'NoneType' object has no attribute 'get'
```

The fourth line is the control. `tokenizer_sentencepiece_legacy` had the same clobber and lost it in #5998, and `test_config_success` has asserted since then that it survives construction. The hf trio was left behind.

`include_special_tokens` is the quiet one, since it changes text to id conversion with nothing in the logs. `use_fast` silently swaps the slow tokenizer for the fast one. `trust_remote_code` turns into a confusing transformers-side failure for a repo with custom tokenizer code, and on the Megatron-LM checkpoint path it also makes the guard at `model_load_save.py:236-240` unreachable, since the value it inspects has already been forced to False.

Also reachable from `mlm_compat/arguments.py:53-66`, which copies every matching field out of a checkpoint's saved argparse namespace into `TokenizerConfig(**kw_args)` and so loses whatever the checkpoint recorded for those three.

### The change

Read a key only when the deprecated dict actually carries it, which is what `_resolve_hf_tokenizer_revision` in `tokenizers/tokenizer.py:112-119` already does:

```python
    if "use_fast" in hf_tokenizer_kwargs:
        resolved_config.tokenizer_hf_no_use_fast = not hf_tokenizer_kwargs["use_fast"]
```

Moving the reads inside the existing guard also stops `hf_tokenizer_kwargs=None`, which the annotation at `config.py:47` allows, from reaching `.get`. `tokenizer.py:90` already normalises that with `config.hf_tokenizer_kwargs or {}`.

After:

```
  asked trust_remote_code                        True -> got True
  asked tokenizer_hf_no_use_fast                 True -> got True
  asked tokenizer_hf_no_include_special_tokens   True -> got True
  asked tokenizer_sentencepiece_legacy           True -> got True
  hf_tokenizer_kwargs=None -> ok

deprecated dict still wins when it carries the key:
  use_fast=False in dict         -> tokenizer_hf_no_use_fast   = True
  trust_remote_code=True in dict -> trust_remote_code          = True
  include_special_tokens absent  -> no_include_special_tokens  = True
```

## Tests

Three cases in `TestTokenizerConfig` in `tests/unit_tests/training/test_config.py`, beside the `test_config_success` that already pins the sentencepiece sibling: the direct fields survive, a key the deprecated dict supplies still wins while one it omits leaves the field alone, and `None` is accepted. The first fails on `main` on all three asserts, the third raises `AttributeError` there.

`test_config_success` keeps passing unchanged, since it exercises the non-empty-dict path.
