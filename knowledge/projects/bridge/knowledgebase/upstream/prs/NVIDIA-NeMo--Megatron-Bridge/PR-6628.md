# fix(ckpt): preserve ModelOpt tied-weight metadata and DDP/Float16 load results

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6628) · state: closed · merged: True

## Original PR description

## Summary

Fix two independent downstream compatibility issues: preserve the deployment quantization specification of tied output weights when their input embedding is the only conversion task, and restore checkpoint loading through native DDP/Float16 wrappers.

Without an explicit output-head specification, an MLP-only recipe can correctly leave the embedding BF16 while the canonical deployment configuration incorrectly treats the tied head as quantized. vLLM then ties that head to the BF16 embedding, causing its native FP4 weight processing to fail a shape assertion.

## Changes

- Resolve tied HF output aliases through the existing Bridge mapping registry.
- Copy the source export specification, including explicit unquantized `None`, before ModelOpt builds the canonical configuration.
- Reject missing source specifications and conflicting alias specifications.
- Preserve conversion tasks and exported tensors; the public AutoBridge method signature is unchanged. The plan helper gains one optional keyword-only argument.
- Add W4A4/W4A16 tied/untied, remote-owner, and alias-consistency regressions.
- Preserve checkpoint load results through delegating DDP/Float16 wrappers without bypassing FSDP adapters.
- Keep checkpoint test mocks consistent with native scalar/list unwrapping.

## Why the checkpoint-loading fix is needed

This is a general checkpoint-loader regression, independent of ModelOpt export or quantization. It is included so adopting the newer Bridge revision does not break existing NeMo-RL value-worker initialization; the tied-weight export fix itself does not depend on it.

Upstream [#6469 (`e97a67ac`)](https://github.com/NVIDIA-NeMo/Megatron-Bridge/commit/e97a67acbf1b7a8ae0a0e0f26c60fa9548e19bfe), merged October 21, changed full checkpoint loading to pass the original wrapped models into `_load_model_state_dict`. This was necessary for MFSDP V2's load adapter to refresh compute weights, but it also exposed a different behavior in native DDP and Float16 wrappers:

1. Strict loading raises because a checkpoint key is missing or unexpected.
2. Bridge's existing compatibility fallback retries with `strict=False` and inspects the returned `missing_keys` and `unexpected_keys`.
3. Native [DDP](https://github.com/NVIDIA/Megatron-LM/blob/ede2c586cf70dd452f93b9726b31cbedc8df0dd0/megatron/core/distributed/data_parallel_base.py#L90-L96) and [Float16Module](https://github.com/NVIDIA/Megatron-LM/blob/ede2c586cf70dd452f93b9726b31cbedc8df0dd0/megatron/core/transformer/module.py#L613-L616) delegate loading to the nested model without returning its result. The retry can therefore load successfully but return `None`, causing a secondary `AttributeError` at `load_return.missing_keys`.

A concrete nonquantized reproducer is NeMo-RL's maintained value-worker initialization. Its [fresh scalar value head is intentionally omitted](https://github.com/NVIDIA-NeMo/RL/blob/ddb67f3289a9d4772a153b08612d564c63ead615/nemo_rl/models/value/workers/megatron_value_worker.py#L102-L151) when loading a base-model checkpoint; a training resume instead restores the trained head. In [existing downstream CI](https://github.com/NVIDIA-NeMo/RL/actions/runs/39892904967/job/120287486009), the initial missing `output_layer.weight` error reached this fallback and then crashed on `None.missing_keys`. This is not solely a synthetic missing-key test or a quantization-specific failure.

The fix selectively unwraps native DDP/Float16 wrappers before loading, retaining the underlying incompatible-key result. FSDP adapters remain wrapped so their load-time prefixing and weight refresh still run. This restores the existing fallback policy, including warnings for non-extra-state mismatches; it does not add permission to ignore additional missing weights or change checkpoint serialization, saving, optimizer state, or RNG handling.

Older Bridge revisions passed unwrapped models on this path and avoided the defect. Successful strict loads, successful direct non-strict loads, and the already-unwrapped model-only loading path also did not trigger this return-value crash. Therefore, earlier successful training is consistent with this being a recently exposed, conditional regression—not evidence that every load or every training run was affected.
