# feat(quant): export quantized fused-projection mappings through ModelOpt

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6767) · state: closed · merged: True

## Original PR description

# What does this PR do ?

`save_hf_pretrained_modelopt` can now export quantized weights under every mapping that splits or regroups a fused Megatron weight by whole rows. Until now, any quantized weight under such a mapping, other than the plain QKV, gated MLP, separate GatedDeltaNet and Mamba mappings, failed at every parallelism, e.g.:

```
ModelOpt export metadata capture failed: NotImplementedError: ModelOpt real-quant export does not support ConcatenatedQKVMapping topology
```

| Mapping | Used by | HF outputs |
|---|---|---|
| `ConcatenatedQKVMapping` | Bailing MoE V2 (Ling 2.0), Sarvam MoE; Qwen3-VL / Qwen3.5-VL, Exaone 4.5, Ernie 4.5-VL, Nemotron-VL vision attention | one `[Q|K|V]` tensor |
| `QKVGMapping` | Step 3.5, Step 3.7 | `q/k/v/g_proj`, in both of the mapping's gate layouts |
| `GDNLinearMapping` | Qwen3-Next | `in_proj_qkvz`; `in_proj_ba` stays unquantized, as `in_proj_b` / `in_proj_a` already do |
| QKV-style mappings with their own row layout: `MiMoV2FlashQKVMapping`, `BeamQKVGateMapping`, `MuseGlimmerQKVGMapping`, GLM-5.3's KDA `_ColumnParallelConcatMapping`, and subclasses of the supported mappings that override `megatron_to_hf` | MiMo-V2-Flash, Beam, Muse Glimmer / Spark, GLM-5.3 | the mapping's own outputs |

# Changelog

- `ConcatenatedQKVMapping` and `QKVGMapping` reuse `QKVMapping`'s attention layout and tensor-parallel type. The rows of the gathered ModelOpt state are selected with the same `split_qkv_weights` / `split_qkvg_weights` the mapping applies to the weight. In `QKVGMapping`'s `attention_output_gate` layout, each head's gate row is repeated across the head dimension, and the gate takes one row per head, as the weight conversion does.
- Any other mapping, and any subclass of a supported mapping that overrides `megatron_to_hf`, has its rows traced when the export plan is built: the mapping's own `megatron_to_hf` runs once on a tensor that labels each element of the local weight with its (row, column) in the TP-merged weight. Its outputs show which merged rows land in each HF tensor, including mappings that regroup TP shards section by section. The labels go through the mapping's TP collectives on its own pipeline stage only (`skip_pp_broadcast`), and the rows reach the other stages with the plan's existing metadata sync.
- Tracing fails the export plan, as before, when a mapping does not copy whole rows (it transposes, slices columns or combines rows), or needs another Megatron weight to produce its output. The custom-row-layout rejections are removed, since tracing covers those mappings. `AutoMapping` with `permute_dims` is still rejected.
- `docs/modelopt/quantization.md`: the fallback note no longer lists fused QKV-gate projections as unsupported.

# Tests

- `tests/unit_tests/models/test_modelopt_utils.py` (123 passed):
  - FP8 with per-row scales and NVFP4, at TP 1 and 2: `ConcatenatedQKVMapping` (with and without the output gate) and `QKVGMapping` (both gate layouts) export each weight and its scales bit-identical to ModelOpt's packing of the same HF weight.
  - Traced mappings, through the full plan and export path: `MiMoV2FlashQKVMapping`, `BeamQKVGateMapping`, `MuseGlimmerQKVGMapping`, `GDNLinearMapping` and GLM-5.3's `_ColumnParallelConcatMapping` at TP 1, and the MiMo, `GDNLinearMapping` and GLM-5.3 mappings at TP 2 on two gloo ranks. Every quantized output is bit-identical to ModelOpt's packing of that HF tensor with per-row FP8 scales, and `in_proj_ba` is written unquantized and listed in `ignore`. Reversing the traced rows, or dropping the TP row offset, fails these tests.
  - Mappings that return nothing, transpose, slice columns or add rows are rejected.
- `tests/functional_tests/test_groups/quantization/test_modelopt_hf_export.py`: three new toy NVFP4 cases, each bit-identical at TP=2 to the single-GPU export: Bailing MoE V2 (dense layers, `attention.query_key_value`), Step 3.5 (dense, `g_proj` in the `attention_output_gate` layout) and Qwen3-Next (`in_proj_qkvz` packed, `in_proj_ba` BF16). Each fails on `main` with the unsupported-topology error. All 8 cases in the file pass.
- Dequantizing the toys' exported NVFP4 Step 3.5 `q/k/g_proj` and Qwen3-Next `in_proj_qkvz` gives the source weights to within NVFP4 error (cosine similarity 0.995).
- Ran on 2× RTX 6000 Ada in `nvcr.io/nvidian/nemo:26.10.rc9` with `nvidia-modelopt==0.48.0rc1` and the pinned Megatron-LM.

ModelOpt's own Megatron exporter does not support these models, so there is no reference checkpoint to compare a real export with, and no vLLM run yet. vLLM builds Step 3.5's `g_proj` as a `ColumnParallelLinear` with the model's `quant_config`, so it takes a quantized gate.

**Correction:** All members of each mapping's TP group must agree whether to trace before entering mapping collectives. Replace the eligibility block at lines 887–889 with:

```python
if not _traces_rows(task.mapping):
    continue
source = local_specs.get(task.global_param_name)
quantized = _all_gather_objects(
    source is not None and source.state is not None,
    task.mapping.tp_group,
)
if any(quantized) and not all(quantized):
    trace_error = trace_error or (
        f"Inconsistent ModelOpt quantization across TP for {task.global_param_name}"
    )
    continue

    continue
```

Keep the subsequent tracing/error envelope so every rank reaches the WORLD error synchronization. This suggested change is source-reviewed, not executed; verify it before adopting it.
