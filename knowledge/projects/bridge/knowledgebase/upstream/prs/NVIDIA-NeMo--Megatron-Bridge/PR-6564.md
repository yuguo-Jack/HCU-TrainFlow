# feat(recipe): add 256-GPU DeepSeek V3 MXFP8 MFSDP v2 NCCL EP recipe

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6564) · state: open · merged: False

## Original PR description

# What does this PR do ?

Add a 256-GPU DeepSeek V3 MXFP8 MFSDP v2 HSDP benchmark using NCCL EP and Bridge's standard v2 validation.

# Changelog

- Export and register `deepseek_v3_pretrain_256gpu_gb300_fp8mx_hsdp_mfsdpv2_config` with EP=64, four optimizer instances, GBS=1024, and MBS=1.
- Use dense `optim_grads_params` with outer `optim`, and expert `optim_grads_params` with outer `no_shard`. Dense ZeRO-3 matches the existing Bridge v2 validator.
- Select NCCL EP with its pull/push environment setting and extend the existing NCCL EP recipe test coverage.
- Retain full-iteration CUDA graphs and fused grouped experts. Disable communication settings owned by v2, MoE overlap, and delayed weight-gradient computation.

# Additional Information

**Core comparison:** [NVIDIA/Megatron-LM#8355](https://github.com/NVIDIA/Megatron-LM/pull/8355) groups MXFP8 weights by row width to avoid excessive layout padding. The GBS=1024 dense ZeRO-3 NCCL EP configuration completed three finite warmup iterations without the fix, then ran out of memory during full-iteration graph capture on step 4. The log contains 256 capture-start messages and no completions. The failing `allocate_partial_grad_buffer()` call requested 15.75 GiB, with only 6.03 GiB free on one reported rank. The matched configuration with the fix completed capture and all 100 iterations. The fix is required for the tested full-iteration-graph configuration; this does not establish that every possible configuration needs it. Both variants use Core `60547a3f419bd8027bb6ffb91793c2fa99ad97ed` and the same pre-existing kwargs-aware fused-expert hook change. This PR does not change the Core submodule pin, shared validation code, or shared configuration tests.

**GBS=512 / GA=2 follow-up without the fix:** Reducing only global batch size to 512 (MBS=1, training DP=256) also failed during full-iteration graph capture on step 4. The three completed warmup steps had finite LM losses **11.89582, 11.89472, 10.51192** and gradient norms **24.326, 24.337, 109.583**, with zero skipped/NaN counters. There were **256 capture-start messages and zero completions**, so there is no replay or steady-state throughput result. The same gradient-buffer allocation requested **15.75 GiB**, with **8.53 GiB free** in the first OOM report; PyTorch held **253.39 GiB**, including **54.59 GiB in private pools**. The job ended FAILED (143:0) after distributed abort. Changing GBS alone did not remove the need for the fix in either tested configuration. The default recipe remains GBS=1024.

**HybridEP follow-up at GBS=512 / GA=2 without the fix:** Switching only the dispatcher to HybridEP and adding its GB300 topology settings, while retaining dense/expert ZeRO-3, also failed during step 4 full-iteration graph capture. The resolved-config comparison verified only the backend, four backend environment settings, and output path changed. Three warmup steps completed with finite LM losses **11.89582, 11.89471, 10.51057** and gradient norms **24.326, 24.338, 109.924**, with zero skipped/NaN counters. The log has **256 capture-start messages and zero completions** (markers lack rank IDs). The same `allocate_partial_grad_buffer()` allocation requested **15.75 GiB**, with **9.24 GiB free** in the first OOM report. Job 1171742 ended FAILED (143:0); there is no successful replay or steady-state throughput result. Replacing NCCL EP with HybridEP was insufficient for this no-padding configuration. This is distinct from the earlier successful HybridEP run with the padding fix and dense ZeRO-2.

**HybridEP without CUDA graphs, GBS=512 / GA=2, without the padding fix:** A follow-up changed only `model.cuda_graph_impl` from `full_iteration` to `none` (plus the output path), retaining the prior HybridEP configuration and sources. Preflight and actual-config comparisons verified this isolation. Job 1175214 completed **34 contiguous finite iterations**, with zero skipped/NaN counters and no logged CUDA OOM or training graph capture/replay, before Slurm terminated it at the **35-minute time limit**. It did not complete the 100-step target. As a partial-run measurement, **steps 11–34 averaged 50.9875 model TFLOP/s/GPU at 42.0414 seconds/step**; steps 21–34 averaged 50.9071 at 42.1171 seconds/step. There is no steps 51–100 result. LM loss went from 11.89582 to 8.114134; all recorded gradient norms were finite. Rank 0's logged allocator peaks through step 2 were 238.43 GB allocated / 284.58 GB reserved (decimal GB; not an all-rank or full-run peak). Eager execution passed the prior capture-failure point for the observed 34 steps, but this is not a completed 100-step validation or an isolated speed comparison against a successful graph-enabled run. The logs do not establish the cause of the low eager throughput.

**Current NCCL EP result:** Full DeepSeek V3 (61 layers plus MTP), 256 GB300 GPUs, sequence length 4096, GBS=1024, MBS=1, MXFP8, EP=64, four optimizer instances, and the dense/expert sharding described above:

- Steps 51–100 averaged **843.228 model TFLOP/s/GPU** at **5.0517 seconds/step**, excluding warmup and capture. The throughput range was 839.8–845.1.
- All 100 contiguous iterations had finite LM loss and gradient norms, with zero skipped/NaN counters. LM loss went from **11.89503 to 3.542798**; steps 51–100 went from **6.382897 to 3.542798**.
- Gradient norms ranged from **0.458 to 166.501** across the run, with the maximum on warmup step 3. Steps 11–100 ranged from **0.458 to 13.307**; steps 51–100 ranged from **1.376 to 5.153**. The post-warmup loss trend declined.
- The log contains **256 capture-start and 256 capture-completion messages**, followed by replay through step 100.
- Rank 0's logged peak through step 4 was **211.74 GB allocated / 231.99 GB reserved**, using decimal GB. This is limited logger coverage, not a measured all-rank or full-run peak.
- The job and all Slurm steps exited **COMPLETED, 0:0**, with no logged forced termination or shutdown timeout under the 180-second cleanup grace.

**Earlier baseline:** A 100-step, 256-GPU HybridEP run with dense ZeRO-2 and the padding fix averaged 942.8 model TFLOP/s/GPU at 4.5182 s/step over its final 50 steps. The current recipe is about 10.6% lower in measured throughput, but both the dispatcher and dense sharding changed, so this is not an isolated NCCL EP comparison. The earlier run exceeded a 30-second worker shutdown grace; the current run completed with a 180-second grace.

All runs use mock data and forced balanced routing. They test bounded numerical stability and throughput, not real-data convergence or production routing performance. Model TFLOP/s is a modeled throughput estimate, not a hardware utilization percentage; this is not a claim of globally optimal performance. Cluster launchers, account settings, and local paths are excluded from this source change.
