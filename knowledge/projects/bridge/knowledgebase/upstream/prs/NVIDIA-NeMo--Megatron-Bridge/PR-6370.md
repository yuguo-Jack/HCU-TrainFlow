# refactor(model)!: remove retired model support

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6370) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Remove retired model implementations, registrations, recipes, examples, and current support documentation while preserving shared infrastructure used by supported successors. Delete the deprecation module and its path/name/shape blacklist, so compatible checkpoints are not rejected because of a directory name or fine-tune suffix.

Primary area: `area:model`. This is a breaking change for the removed model APIs and recipes.

# Changelog

- Remove DeepSeek V2/V2 Lite, Gemma 1/2, Llama 2, Mistral 7B and Small 3 24B, Nemotron-4 340B, Llama Nemotron, Nemotron Nano v2 text/VL, and Nemotron H v1 (4B/8B/47B/56B) dedicated support.
- Remove H-v1 library/H100 recipes, nine performance factories across H100/B200/B300/GB200/GB300, public exports, and benchmark selectors. Retain all successor recipe settings.
- Preserve DeepSeek V3/V4 attention and MLA code, Gemma 3/4 helpers, Llama mappings, Mistral NeMo/Ministral infrastructure, and Nemotron 3/3.5/Omni components. Shared architecture-compatible derivatives remain loadable; removed dedicated architectures fail normal registration lookup.
- Keep the historical V2 architecture alias for MoE Nano Omni checkpoints with canonical provider metadata. Its local compatibility provider continues to reject dense V2 configurations.
- Delete `models/_deprecation.py` and every caller. Add regressions for supported checkpoints under misleading local directory names and a Nemotron 3 fine-tune with a `v2` suffix.
- Update current model tables, navigation, examples, and skills. Preserve historical release snapshots and media fixture URLs used by supported VLMs. Eight unlisted Fern pages contain removal notices so previews using trusted-main navigation still resolve.

- kamran-nvidia · comment · 2026-10-09T20:24:59Z · [source](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6370#discussion_r4234254939)

File: `src/megatron/bridge/models/_deprecation.py` · line None

I'm a bit worried about these name checks now that they raise instead of warn. They match substrings anywhere in the load path, and a name hit here wins before the shape check, so a supported checkpoint can get rejected just because of a folder name. Tried a few with the real HF configs (transformers 5.17):

- Mistral-Nemo-Base-2407 in `/models/mistral-7b-comparison/nemo` -> `ValueError: Support for Mistral 7B and Mistral Small 3 24B has been removed...`
- Llama-3.1-8B-Instruct in `/data/nemotron-sft/Llama-3.1-8B-Instruct` -> rejected as Llama Nemotron
- a Nemotron 3 Nano fine-tune named `my-org/nemotron-nano-30b-a3b-sft-v2` -> rejected as Nano v2

`supports()` / `can_handle()` also return False for these.

It doesn't really work the other way either. The comment on L45 assumes the serialized `_name_or_path` survives, but `AutoConfig.from_pretrained` overwrites it with the local path, so `Llama-3.1-Nemotron-Nano-8B-v1` copied to e.g. `/ckpts/reasoning-8b` goes straight through. Not a big deal since it's plain Llama 3.1 underneath, but the joined identifier isn't buying us much.

Could we only raise on what's actually in the config (archs + shape signatures) and keep the name matching as a warning, ideally against the repo id / basename rather than the whole path? A couple of tests with supported models under misleading paths would be nice too.
