# refactor(model): build GLM-5 from a builder-backed hybrid MLA model config

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6671) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves **GLM-5** (`GLM5Bridge`: GLM-5, 5.1, 5.2 and 5.3) onto the builder-backed `ModelConfig` / `ModelBuilder` path for recipes and checkpoint conversion. It adds the shared config this needs: `BridgeHybridMLAModelConfig`, a `BridgeHybridModelConfig` whose nested transformer config is an `MLATransformerConfig`. DeepSeek-V4 moves onto it in a stacked follow-up PR. Follows the Nemotron-H (#6609), Qwen3-Next/Qwen3.5 (#6598) and Gemma 4 (#6612) migrations. Part of MB-1857.

# Changelog

- **`BridgeHybridMLAModelConfig`** (`models/hybrid/model_config.py`): the builder counterpart of the hybrid MLA providers.
  - Megatron Core's `MLATransformerConfig` declares `rotary_base` and `rotary_percent`, and so does the Hybrid model config. MLA and DSA attention read the nested values. With one owner per field, `rope_theta` would reach only the outer config, so GLM-5.2 (`rope_theta=8e6`) would build with the MLA default of 10000.
  - `MLAModelConfigMixin` (`models/common/base.py`) makes the outer names `InitVar` constructor arguments whose descriptors read and write the nested values, so only the transformer config stores, serializes and receives overrides of them. A constructor value that conflicts with a non-default nested value raises before it is copied; a saved config that still carries both is checked the same way.
- **Shared mapping** (`models/conversion/model_bridge.py`): the MLA rope fields are selected when the bridge's model config nests an MLA transformer config, not only for `MLAModelProvider` registrations. `hf_config_to_model_config_kwargs()` emits them as flat kwargs with `position_embedding_type="rope"`, as `provider_bridge()` does for MLA providers. No other bridge changes: only this family sets an MLA model config.
- **`GLM5Bridge`**: `MODEL_CONFIG_CLASS = GLM5ModelConfig` and `USE_MODEL_CONFIG_FOR_CONVERSION = True`. `provider_bridge()` is replaced by `hf_config_to_model_config_kwargs()`, and `hf_config_to_provider_kwargs()` reuses those kwargs.
  - `GLM5ModelConfig` (`glm_moe_dsa/glm5_config.py`) validates and finalizes like `GLM5ModelProvider`. `validate_glm_hybrid_pattern()` checks the layout and training settings without changing the config; it checks the split that finalization will set, so a pattern without `|` stays valid for PP > 1. `finalize_glm_hybrid_pattern()` then places DSA-aligned pipeline boundaries in `hybrid_layer_pattern`, enables sequence parallelism for TP > 1, and derives the MTP pattern and MoE schedule. Both classes call both.
  - `GLM5ModelBuilder` builds every stage from `glm_hybrid_stack_spec()`, as the provider's `_resolve_hybrid_stack_spec()` does.
  - `attention_backend=flash` and `bias_dropout_fusion=True`, the `HybridModelProvider` defaults the builder config does not share, are set explicitly.
- **Recipes**: the GLM-5 library recipes (8 GB200, 4 H100, plus 2 aliases) and the 4 GLM-5.1/5.2 perf recipes use `get_model_config()`.
- **`BridgeHybridModelConfig.validate()`** checks the config without changing it, and `finalize()` runs it before its updates; `GLM5ModelConfig.validate()` adds GLM's checks.
- **`fix(ckpt)`**: `BridgeHybridModelConfig.as_dict()` persists a finalized pipeline layout as given. Without it, any hybrid builder checkpoint saved with a layout cannot be reloaded; this is the hybrid counterpart of #6642's GPT fix.
- **Tests**:
  - The MLA hybrid config: rotary settings stored and serialized only on the nested config, constructor values that match, conflict or fill a default, YAML and CLI overrides of the nested value, save/load (including an edited and a conflicting saved config), finalize, and the MLA rope mapping without an MLA provider.
  - GLM-5 bridge: builder vs provider parity for GLM-5.2 and GLM-5.1 architectures (raw and finalized at PP1, TP2, PP4), the GLM stack spec, the round trip, `validate()` leaving the config unchanged, and the provider and builder rejecting the same layouts and settings.
  - GLM-5 recipe tests build strict `GLM5ModelConfig`s from GLM-5.2's architecture, and the provider API raises.
  - Hybrid layout persistence.
- **Docs and skills**: the GLM-5 pages no longer say `get_model_config()` is unsupported. The `adding-model-support` skill points hybrid MLA families at the new config, with GLM-5 as the reference.

## Behavior changes

- **Checkpoint format.** `convert.sh import` / `AutoBridge.import_ckpt` now write builder-format GLM-5 checkpoints (`_target_: ...GLM5ModelConfig`). Bridge versions before this PR cannot load them. This PR loads checkpoints that `main` wrote.

## Merge order

- Merge after #6731. GLM-5's routers use expert bias, and #6731 keeps a pretrained `expert_bias` in FP32 when a builder-backed config is wrapped for mixed precision (`get_model()` and PEFT training).

## NeMo RL

- **Provider path unchanged.** `to_megatron_provider()` returns the same `GLM5ModelProvider` fields as `main` (see Verification). It now logs the builder-deprecation `FutureWarning`, as for the other migrated families.
- **Checkpoint-format caveat**, as in #6609: NeMo RL's `megatron_bridge` pretrained-checkpoint loader calls `.provide()` and cannot load builder-format checkpoints. Checkpoints imported before this change and NeMo RL's own HF conversion are not affected.
