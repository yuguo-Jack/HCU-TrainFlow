# fix(training): make dynamic CP usable on the MCore dev pin (r0.7.0)

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6579) · state: closed · merged: False

## Original PR description

# What does this PR do ?

Make dynamic context parallelism usable on the 26.10 release branch. The PR bumps r0.7.0's Megatron-Core dev pin to a revision this branch can import, and on the release pin it reports the dev-pin requirement instead of a bare unknown-field error.

# Changelog

- **`build: bump MCore dev to ff4fbc9f`**: changes `.dev.commit` from `4a4de865` to `ff4fbc9f3`, the MCore `dev` head after the full main-to-dev sync in NVIDIA/Megatron-LM#7960.
  - On `4a4de865` (2026-09-09), `import megatron.bridge` fails on this branch. `models/glm_moe_dsa/glm5_hybrid.py` imports `megatron.core.transformer.experimental_attention_variant.dsa_layer_config`, which that revision lacks.
  - A static audit of the 1548 Megatron-LM imports in this branch's `src/` finds 29 that don't resolve on `4a4de865`. 11 of them are module-level imports in 6 files: `glm5_hybrid`, `initialize`, `setup`, `train`, `checkpointing` and `megatron_mimo_provider`. Guarding the GLM import alone would not help.
  - On `ff4fbc9f3`, every import that resolves on the release pin (`core_r0.20.0` @ `5038673`) also resolves (0 missing), and `default_dynamic_cp` is registered.
  - The release pin itself (`.main.commit`, submodule) is unchanged.
- **`fix(training): name the MCore dev pin in dynamic CP field errors`**: the same change as the `main` PR #6578.
  - The release pin doesn't declare `dynamic_context_parallel` or `min_dynamic_context_parallel_size`. Assigning either now appends the dev-pin hint to the bare `AttributeError` from `BridgeGPTModelConfig`'s field guard:
    `Neither BridgeGPTModelConfig nor TransformerConfig declares a field named 'dynamic_context_parallel'. Dynamic context parallelism needs the Megatron-Core dev pin: ./scripts/switch_mcore.sh dev && uv sync.`
  - `global_batch_packing.py` imports the same hint constant.
  - The dynamic-CP docs now say where the error is reported.
  - New unit test (skipped on pins that declare the fields).

# Known limitations on the new dev pin (not fixed here)

- **GDN models fail at setup:** MCore `dev` commit `6e8ff3ecd` (part of #7960) made `TransformerConfig.__post_init__` non-idempotent for GDN, KDA and hybrid configs.
  - The first call fills in `linear_cp_mode='chunkwise'` and `linear_cp_layout='zigzag'`. The second call raises `linear_cp_mode='chunkwise' requires linear_cp_layout='contiguous'`.
  - Bridge finalizes model configs more than once, so GDN models, including the Qwen3.5 dynamic-CP reference recipe, still fail at setup on the `dev` pin. Dense models are unaffected.
  - This needs an MCore `dev` fix, then a re-pin.
- **Missing release-pin commits:** `ff4fbc9f3` lacks a few `core_r0.20.0` commits, including the MoE aux-loss token-count fix under CUDA-graph capture (NVIDIA/Megatron-LM#8217). Users who switch to the dev pin run without it.
- **Expected dev-lane failures:** a few unit tests use stubs that lack new `dev` config fields (`linear_cp_mode`, `mtp_loss_type`, `num_key_heads`), and two GB300 Nemotron perf recipes hit a dev-only NCCL-EP validation. All of them fail identically without this PR.
