# feat(quant): stream KV-cache scales in ModelOpt refits

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6726) · state: open · merged: False

## Original PR description

# What does this PR do ?

Extend the existing ModelOpt online weight-export stream to carry current Q/K/V attention scales and canonical KV-cache metadata for native inference refits.

## Merge dependency

**Do not merge until [ModelOpt #3121](https://github.com/NVIDIA/Model-Optimizer/pull/3121) is merged and Bridge uses a compatible published ModelOpt version.**

- ModelOpt #3121 is required for stateless constant-amax FP8/NVFP4 KV-scale capture. The underlying functional KV API from [ModelOpt #2981](https://github.com/NVIDIA/Model-Optimizer/pull/2981) is already merged.
- A ModelOpt release or RC containing both changes must be available, and Bridge's ModelOpt dependency and lockfile must be updated before this PR merges. The current `0.48.0rc1` pin is insufficient.
- Re-run the KV export tests with that published dependency and require the KV cases to run without skips. Source-installed qualification does not verify the published dependency combination.

# Changelog

- Support symmetric FP8 and NVFP4 KV-only export plans, as well as KV scales alongside quantized weights.
- Capture local scales once during per-stream preparation and emit them once on the owning QKV task's first converted output, including renamed outputs. An absent, disabled or constant-amax Q quantizer exports scale one; calibrated Q uses the TP maximum across local heads. K/V scales must still agree across TP, and online FP8 scales are not clamped to one.
- Reject rotations and pre-quant scaling even on disabled attention quantizers. Validate the supported FP8/block-16 NVFP4 layouts and reject enabled custom backends during planning and plan reuse. Offline KV-cache saving remains unsupported.
- Document the online usage, consumer responsibilities, and ModelOpt prerequisites.

```python
plan = bridge.build_hf_modelopt_export_plan(model)
quantization_config = plan.quantization_config

for name, tensor in bridge.export_hf_weights_modelopt(model, export_plan=plan):
    refit_engine.replace_weight(name, tensor)
```

Every distributed rank must build the plan and fully consume each stream in the same order. The consumer owns native cache storage and attention/CUDA-graph refresh; this PR does not introduce a new tensor transport or quantization implementation.

- kevalmorabia97 · COMMENTED · 2026-10-30T05:22:48Z · [source](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6726#pullrequestreview-5708396003)

Thanks, reusing the existing QKV conversion group and the plan / prepare split fits the online exporter well. I have one correctness concern, one robustness concern and one about cost:

1. **Q scales at TP > 1.** ModelOpt's max calibration syncs only `k_bmm_quantizer` / `v_bmm_quantizer` amax across TP (`model_calib.py`, the "KV Cache Quantization" block); `q_bmm_quantizer` keeps a per-rank amax over its local heads. With an enabled Q quantizer (FP8 attention) and TP > 1, `torch.equal` across the TP shards fails and the stream raises "Inconsistent ModelOpt Q/K/V scales across TP". Deployment needs one per-layer `q_scale`, so either take the max across TP here or sync Q in ModelOpt's calibration as well. A TP2 case with Q enabled would cover it. The PR body says TP > 1 is not qualified yet, but this one fails deterministically.

2. **A renamed `q_proj` would skip the scales without an error.** `_KVExportHook.__call__` emits the scales only when `hf_name == f"{hf_parent}.q_proj.weight"`. That name is checked after `maybe_modify_converted_hf_weight`, which bridges override. I found no current bridge that renames `q_proj` there. If one did, no scales would be emitted, yet `quantization_config` would still declare the KV cache, so the engine would silently use scale 1. Could the hook trigger on the QKV task's own output (e.g. its first one), or raise when the task finishes without emitting scales?

3. **Per-layer synchronization on every refit.** `scales()` runs, per attention layer and per stream:
   - a PP `broadcast_obj_from_pp_rank`;
   - a TP `all_gather_object`;
   - a PP tensor broadcast;
   - a TP gather;
   - a host sync in `bool(torch.all(...))`.

   With PP and TP > 1, that is up to 5 synchronizations per layer, including 2 pickled object collectives, so roughly 320 per refit for a 64-layer model. `prepare_modelopt_export_tasks` already runs one world-wide error collective per stream. Capturing and validating all local scales there would leave each layer with only the tensor collectives it needs. Since K/V are already TP-synced at calibration, the TP equality gather could go as well, once (1) is resolved.

Not for this PR: offline `save_hf_pretrained_modelopt()` still rejects KV quantizers in `check_exportable_quantizers`. Enabling it is the next step for quantized HF export, and these hooks look reusable for it, so it would be good to keep `_KVExportHook` independent of the streaming-only paths.
