# fix(data): register Super VL processor to the Nemotron Omni collator

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6711) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Registers the Nemotron 3.5 Super VL processor type (`NemotronH_Omni_Reasoning_V3Processor`) to the Nemotron Omni expanded-sequence collator, so mock VLM, direct-HF SFT, and generic HF Energon datasets built from a Super VL processor resolve a collator.

# Changelog

- `data/collators/registry.py`: map `NemotronH_Omni_Reasoning_V3Processor` to `nemotron_omni_expanded_collate_fn` with `always_use_model_collate=True`, the same spec as Nano Omni. Super VL reuses the Nemotron Omni model and `nemotron_omni_step`, so text-only rows also need the model-owned collator.
- `data/builders/direct_hf_sft.py`: reject the `last_turn` and `full` chat loss modes for processors that always use the Nemotron Omni collator (Nano Omni and Super VL). That collator builds assistant-only loss masks, so these modes were silently ignored before.
- `data/energon/hf_task_encoder.py`: carry `imgs_sizes`, `num_frames` and `media_token_validity_mask` through `HFEnergonBatch`. The generic HF Energon encoder dropped them, so the model fell back to its fixed-image path. Audio fields are still carried only by the Nemotron Omni encoder.
- Tests: registry resolution and `always_use_model_collate` for both Omni processor names; the direct-HF builder keeps text-only Super VL rows on the model collator and rejects prompt-completion preprocessing and non-assistant loss modes; the mock VLM builder dispatches a Super VL processor to the Omni collator; the generic HF Energon encoder keeps image sizes, frame counts and the media mask for a Super VL processor with two differently sized images.

Before this change, building `MockVLMSFTDatasetConfig(hf_processor_path=<Super VL>, trust_remote_code=True)` and running SFT failed on main with `ValueError: No VLM collate function is registered for processor type 'NemotronH_Omni_Reasoning_V3Processor'`. The Super VL recipes worked only because the Nemotron Omni Energon task encoder passes the collator explicitly.

Notes:
- The Super VL checkpoint's remote-code processor and the native Transformers (5.18+) processor have the same class name. On the pinned Transformers 5.20.2, the native processor cannot load an audio-free checkpoint through `AutoProcessor`, so the dataset builders only see the remote-code class.
- Bridge's `Nemotron35VLProcessor` loading adapter is deliberately not registered. No dataset builder creates it (they all use `AutoProcessor`). The Omni collator also does not yet accept native-processor image outputs (packed 2-D `pixel_values` plus `image_grid_hw`), so that class keeps the explicit registry error.

Testing:
- The new test cases fail without the change and pass with it: 5 for the registration and 5 for the review fixes. 236 passed across `test_model_collators.py`, `test_direct_hf_sft.py`, `test_mock_vlm_sft.py`, `test_imports.py`, `test_nemotron_omni_task_encoder.py`, `test_hf_task_encoder.py` and `test_energon_builder.py` (CPU, Transformers 5.20.2). pre-commit passes.
- GPU (H100): a truncated-layer Super VL SFT smoke with `MockVLMSFTDatasetConfig` and the `nemotron_35_super_vl_sft_64gpu_h100_bf16_config` recipe failed with the error above. With the same registration applied in the test harness, it trained 10 iterations and was identical run to run.

**Blocking — Do not silently replace the configured chat loss policy**

**Failure:** Use a Super VL processor with text-only `user → assistant → user → assistant` data and `ChatSFTPreprocessingConfig(loss_mode="last_turn")` or `"full"`. This flag now sends [build_direct_hf_sft_split](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/8ea2a6402561545db02bd25d373d3e8573ac5a10/src/megatron/bridge/data/builders/direct_hf_sft.py#L366-L386) through the mandatory-model branch, which neither forwards nor validates `loss_mode` for Omni. The [Omni collator](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/8ea2a6402561545db02bd25d373d3e8573ac5a10/src/megatron/bridge/models/nemotron_omni/data/collate_fn.py#L1123-L1138) always builds assistant-only masks. Thus `last_turn` still trains earlier assistant answers, and `full` masks user text. Before registration, text-only Super VL rows reached the shared text collator with the requested policy. The [configuration contract](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/8ea2a6402561545db02bd25d373d3e8573ac5a10/src/megatron/bridge/data/sft_processing.py#L45-L60) requires those policies to differ; an unsupported policy must fail explicitly rather than silently change supervision.

**Correction:** Since the existing Omni collator supports only assistant loss, the smallest correction is to reject other modes in the non-DeepSeek mandatory-model branch. Suggested replacement for the `else` at [lines 378–379](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/8ea2a6402561545db02bd25d373d3e8573ac5a10/src/megatron/bridge/data/builders/direct_hf_sft.py#L373-L381):
```python
        else:
            if config.preprocessing.loss_mode != "assistant":
                raise ValueError(
                    "Nemotron Omni direct-HF collation supports only assistant chat loss."
                )
            selected_collate = None
```
This branch currently serves the two Omni processor names. The invariant is that automatic collator selection must honor the requested loss policy or reject it. This suggestion is source-reviewed, not executed; verify before adopting.

**Preservation / acceptance:** Proposed regression: for each Omni processor name, build a split with each of `last_turn` and `full`; expect the explicit error above before collation. With `assistant`, retain the model-owned collator selection asserted by `test_builder_keeps_text_shaped_nemotron_omni_data_on_model_collator`, and retain prompt-completion rejection. Keep DeepSeek’s `test_builder_forwards_chat_loss_mode_to_model_collator` assertion that the partial contains the requested mode. Ordinary text/Qwen text-only rows must still use the shared collator with their configured mode, while an explicit `collate_impl` must continue bypassing automatic selection.

**Blocking — Preserve Omni geometry through generic HF-Energon batching**

**Failure:** Build `HFEnergonTaskEncoderConfig` with a remote-code Super VL processor and batch a conversation containing an image. This registration now lets [HFTaskEncoder resolve the Omni collator](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/8ea2a6402561545db02bd25d373d3e8573ac5a10/src/megatron/bridge/data/energon/hf_task_encoder.py#L126-L130), whose [_pack_dynamic_images](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/8ea2a6402561545db02bd25d373d3e8573ac5a10/src/megatron/bridge/models/nemotron_omni/data/collate_fn.py#L766-L792) produces packed patches together with `imgs_sizes` and `num_frames`. The canonical collator also emits `media_token_validity_mask`. However, [HFTaskEncoder batching](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/8ea2a6402561545db02bd25d373d3e8573ac5a10/src/megatron/bridge/data/energon/hf_task_encoder.py#L208-L241) discards all three fields. Only packed pixels survive. Consequently [NemotronOmniModel._encode_images](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/8ea2a6402561545db02bd25d373d3e8573ac5a10/src/megatron/bridge/models/nemotron_omni/modeling_nemotron_omni.py#L608-L669) receives no sizes and selects its fixed-image fallback instead of the required dynamic-resolution/per-image-boundary path. Generic encoder construction succeeds, but its image batch violates the model contract.

**Correction:** Preserve these canonical image fields in both the batch dataclass and its construction. A minimal suggested patch is to add to [HFEnergonBatch](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/8ea2a6402561545db02bd25d373d3e8573ac5a10/src/megatron/bridge/data/energon/hf_task_encoder.py#L50-L69):
```python
    imgs_sizes: torch.Tensor | None = None
    num_frames: torch.Tensor | None = None
    media_token_validity_mask: torch.Tensor | None = None
```
and add to `_collate_batch_kwargs`’s `batch_kwargs` construction:
```python
            imgs_sizes=collated.get("imgs_sizes"),
            num_frames=collated.get("num_frames"),
            media_token_validity_mask=collated.get("media_token_validity_mask"),
```
Declaring the fields is necessary because `encode_batch()` serializes dataclass fields, not arbitrary attributes. The invariant is that packed Omni pixels retain their geometry and media-ownership metadata through `batch()` and `encode_batch()`. The existing [Nemotron-specific batch initializer](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/8ea2a6402561545db02bd25d373d3e8573ac5a10/src/megatron/bridge/data/energon/nemotron_omni_task_encoder.py#L88-L115) already extracts and restores these fields, so its behavior must remain intact. This patch is a static suggestion; verify before adopting.

**Preservation / acceptance:** Proposed regression: use a processor stub with the new class name that returns a 32×32 RGB image and one expanded image placeholder. Through generic `HFTaskEncoder`, assert encoded pixels have shape `(1, 4, 768)`, `imgs_sizes == [[32, 32]]`, `num_frames == [1]`, and the media-validity tensor exactly matches the collator output. Add two differently sized images to check distinct boundaries; statically verify that the model receives non-null sizes and enters its dynamic-resolution branch. Retain generic text batching, `test_visual_inputs_passthrough`’s three-image assertion, explicit collator overrides, and the Nemotron-specific encoder’s geometry and legacy `visual_tensors` behavior. Mock/Direct-HF dispatch must remain unchanged. These checks were not executed.
