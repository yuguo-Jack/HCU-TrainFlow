# refactor(model): build EXAONE 4.5 from a builder-backed model config

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6742) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves **EXAONE 4.5** (33B vision-language) onto the builder-backed `ModelConfig` / `ModelBuilder` path, for recipes and checkpoint conversion. It follows EXAONE 4.0 (#6401) and the VL builder migrations (#6695, #6709, #6710).

The builder builds the same `Exaone45Model` that `Exaone45ModelProvider.provide()` builds, so checkpoint keys, weight mappings and the model's forward are unchanged.

# Changelog

- **`Exaone45ModelConfig`** (`exaone45_config.py`), a `BridgeGPTModelConfig` with the vision-language fields on the outer config:
  - `vision_config`, the Hugging Face vision config, as on the provider.
  - The token IDs, `spatial_merge_size`, and the four freeze options (`freeze_mtp_model` included).
  - `language_max_sequence_length` replaces the provider's `hf_text_config`. `provide()` read that config only for `max_position_embeddings`.
  - Defaults `position_embedding_type="rope"` and `scatter_embedding_sequence_parallel=False`, as the provider does.
  - The nested transformer config is Bridge's plain `TransformerConfig`: everything the model reads beyond Megatron Core's fields is an outer construction setting.
- **`Exaone45ModelBuilder`** (`exaone45_builder.py`):
  - Builds `Exaone45Model` from the nested transformer config, resolving `transformer_layer_spec` as the GPT builder does. An unset spec selects the EXAONE Post-LN layer spec.
  - Casts the vision encoder to `params_dtype`. `get_vision_model_config()` creates it in fp32; the provider path relies on `Float16Module` for the cast, but builder conversion builds without that wrapper.
  - Applies the freeze options as `provide()` does.
- **`Exaone45Model`** takes an optional keyword `model_config`. When given, the token IDs and GPT construction settings (vocabulary size, RoPE settings, logit dtype, weight tying, maximum sequence length) come from it. The provider path passes nothing and is unchanged.
- **`Exaone45Bridge`**:
  - `provider_bridge()` is replaced by `hf_config_to_model_config_kwargs()`. The language-model fields start from the EXAONE 4.0 bridge's builder kwargs for `text_config`, which is an `Exaone4Config`.
  - It then adds main's EXAONE 4.5 fields: weight tying from the top-level config, hybrid sliding-window attention, RoPE (any `factor` enables scaling, as before), MTP, the vision config and the token IDs.
  - Where the EXAONE 4.0 mapping differs from the EXAONE 4.5 provider, the provider's values are kept: `autocast_dtype` unset, softmax in fp32, and the RoPE, bias-activation, bias-dropout and gradient-accumulation fusions off.
  - The provider path uses the same kwargs plus `hf_text_config`, which `provide()` still reads.
  - Opts in with `MODEL_CONFIG_CLASS = Exaone45ModelConfig` and `USE_MODEL_CONFIG_FOR_CONVERSION = True`.
- **Recipes**: the EXAONE 4.5 SFT and PEFT recipes use `get_model_config()`.
- **Tests**:
  - Bridge: the builder mapping without the provider path, provider/builder parity on five configs, and a serialization round trip.
  - Builder: construction inputs, stage flags, layer-spec resolution, freeze, the vision cast, and the MTP spec. One test builds both paths with the language and vision modules recorded and checks they receive identical inputs.
  - Recipes: both recipes build against a real strict model config, with the provider API rejected.

# Additional Information

- Part of the incremental provider → builder migration.
- Known issues on `main`, not changed here (follow-ups):
  - No VLM collator is registered for `Exaone4_5_Processor`. Multimodal SFT data, including the recipes' default CORD-v2 dataset, fails at dataset build with "No VLM collate function is registered".
  - EXAONE 4.5 training with MTP, which the recipes keep from the checkpoint, fails at the first step. Megatron Core's `GPTModel._postprocess` passes the MTP block `input_ids` and `position_ids`. `Exaone45Model` feeds its language model `decoder_input` instead, so the MTP block asserts (`multi_token_prediction.py`: `assert input_ids is not None and position_ids is not None`). Inference scripts avoid this by disabling MTP.
- The EXAONE functional tests are L2 (`L2_Launch_models_exaone.sh`); they passed on both trees on GPU (see above).
