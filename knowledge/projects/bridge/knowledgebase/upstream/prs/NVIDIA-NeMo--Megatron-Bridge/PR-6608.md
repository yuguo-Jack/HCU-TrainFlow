# fix(model): make repeated TransformerConfig.finalize idempotent for linear CP fields

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6608) · state: closed · merged: False

## Original PR description

## What

Make `TransformerConfig.finalize()` (and the MLA and heterogeneous variants) idempotent for `linear_cp_mode` / `linear_cp_layout` on Megatron-Core pins that derive those fields in `__post_init__`.

## Why

On the MCore dev pin (`ff4fbc9f3`, includes #7960), `__post_init__` fills an unset `linear_cp_mode` / `linear_cp_layout` with defaults (`chunkwise` / `zigzag` for GDN, KDA and hybrid models) and records whether the caller set them (`_linear_cp_mode_was_default`, `_linear_cp_layout_explicit`). A second pass cannot tell those defaults from user input:

- it raises `linear_cp_mode='chunkwise' requires linear_cp_layout='contiguous'`, and
- it flips `_linear_cp_layout_explicit` from `False` to `True`, which MCore reads later (`hybrid_block`, `mamba_layer_config`, `multi_token_prediction`) to choose the CP layout, so even configs that do not raise silently change behavior.

Bridge finalizes model configs more than once, and `finalize()` is documented as safe to call repeatedly, so GDN recipes (including the Qwen3.5 dynamic-CP recipe) fail at setup on the dev pin.

## How

A shared helper, `_run_mcore_post_init`, is used by all three `finalize()` methods. It remembers which of the two fields were `None` going into MCore's post-init and restores them to `None` before the next pass, unless the caller changed them in between. Explicit values and explicit-but-invalid combinations behave as before, and pins that do not define these fields are unaffected (nothing is recorded).

This is a Bridge-side workaround. Making MCore's `__post_init__` idempotent remains the proper fix.

## Testing

- Unit tests (`tests/unit_tests/models/test_transformer_config.py`): 72 pass, including 7 new tests per config class (plain, MLA, heterogeneous). They use a stand-in for the dev post-init, so they run on any MCore pin.
- Reproduced on real MCore dev `ff4fbc9f3`: with unmodified `main`, finalize #2 on the Qwen3.5 dynamic-CP recipe's GDN model config raises the error above; with this change, finalizes #1-#3 succeed with identical state.
- End to end: `examples/training_features/long_context/qwen35_35b_a3b_dynamic_cp.py --tiny-model` on 2 GPUs (dev MCore plus this change, NeMo 26.10 rc5 container) completes 5/5 iterations, finite losses, 0 skipped and 0 NaN iterations. This shows stability only, not convergence.
- `ruff` 0.9.9 (check, isort, format) clean on the changed files.

## Notes

- The proper fix is proposed in NVIDIA/Megatron-LM#8423 (`dev`); this change is compatible with it and can be dropped once Bridge moves to a `dev` commit that includes it.
- The NeMo 26.10 rc5 image itself ships the main/release MCore pin, which has no `default_dynamic_cp` scheduler, so the dynamic-CP recipe cannot run there regardless of this change (Bridge's validation reports this). It needs the dev pin.
- The current `.dev.commit` predates `linear_cp_layout`; this change matters once the dev pin moves to a commit that includes #7960.
- The full 8-GPU recipe (converted checkpoint plus CoderForge data) was not run.
