# feat(data): feed offline packed rows to global-batch packing and dynamic CP

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6778) · state: open · merged: False

## Original PR description

## Summary

Lets **offline packed data feed global-batch packing and dynamic context parallelism (DCP)**. Until now the two were mutually exclusive, so DCP (#6682) only ran on online, unpacked samples. With both `enable_offline_packing` and `enable_global_batch_packing` set, each offline packed row yields one unpacked sample per sequence it holds. Megatron-Core's scheduler then re-bins those sequences and, under DCP, picks a CP group for each bin. The global batch counts packed rows, as in the original Megatron-LM agentic SFT example's `offline_dynamic_cp` mode.

**Stacked on #6682** (mock dataset, recipe): review the commits from `feat(data): feed offline packed rows…` on. Draft until #6682 and NVIDIA/Megatron-LM#7048 land.

## Megatron-Core pin: NVIDIA/Megatron-LM#7048 (temporary, do not merge as is)

As in #6682, `3rdparty/Megatron-LM` / `.main.commit` point to the head of **NVIDIA/Megatron-LM#7048** ("[DCP V2 4/4] Propagate runtime dynamic CP through hybrid model layers"). Without it, a dynamic-CP bin on a group smaller than the base CP fails in Qwen3.5's Gated DeltaNet layers.

- This branch pins **`f1aa086`**, #7048's current head. It is main's pin `e0a4bfed` plus #7048 (35 ahead, 0 behind), with an unchanged MCore `pyproject.toml`, so `uv.lock` matches main.
- The earlier #7048 head `e3165e9`, which #6682 still pins, lacks MCore changes that Bridge main now needs (for example `OptimizerConfig.validate`).
- Re-pin to main's commit once #7048 merges.

**Result (Qwen3.5-35B-A3B, one 4×GB200 node, NeMo 26.10, mock mixed-length data, 200 steps):**

| Packing | Static CP4 tokens/s | Dynamic CP tokens/s |
| --- | ---: | ---: |
| Online, 32 samples/step | 12,157 | 13,301 |
| Offline, eight 64K rows/step | **14,450** | 12,463 |

Offline packing with DCP works end to end on both mock and real data. But on offline rows, **static CP4 is the fastest setup (+18.9% over online static, +8.6% over online DCP), and DCP is 13.8% slower than static on identical rows**. Details under [Validation](#validation).

## Changes

| Area | Change |
| --- | --- |
| Packed GPT-SFT data | `GPTSFTPackedDataset` (`.npy` and, by inheritance, Parquet) gets a global-batch collate that splits each row into one scheduler sample per sequence. Each sample keeps its in-sequence next-token labels and the row's loss mask. Alignment padding written by offline packing (zero-loss EOS tails) is stripped and replaced by the global-batch alignment multiple, `2 x dp x cp` under DCP, so rows prepared with any `pad_seq_to_mult` work. |
| Builder | Passes `enable_global_batch_packing`, the alignment multiple and `fold_alignment_padding` to the packed dataset classes. |
| Validation | `GPTSFTDatasetConfig` and `ConfigContainer` accept offline + global-batch packing; global-batch stays exclusive with in-batch and Energon packing. `pad_cu_seqlens` (a CUDA-graph feature) is rejected with global-batch packing. The bin-capacity check also covers `packed_sequence_size`. |

## Validation

All performance runs: `nvcr.io/nvidia/nemo:26.10`, MCore `e3165e9` (the #7048 head at the time, as in #6682), on this branch before its latest merge of main. On the current head (main merged, MCore `f1aa086`), the unit tests and a 30-step smoke run of the offline DCP recipe were repeated: the same 579 passed / 1 skipped / 1 failed (the DeepEP-on-GB200 test below), and 30 steps with no skipped iterations, finite losses (12.83 to 12.82), grad norms 68-70, and steady 39-54 s steps.

### Mock data, 4-GPU recipe

Full 40-layer Qwen3.5-35B-A3B + MTP1, TP1/PP1/base CP4/EP4, MXFP8, CPU optimizer offload, HybridEP, full recompute. 200 steps, steps 1-10 excluded; tokens/s from `compare_runs.py`:

| Packing | Mode | Mean s/step | Runtime tokens/s | Median model TFLOP/s per GPU |
| --- | --- | ---: | ---: | ---: |
| Online, GBS 32 samples | Static CP4 | 55.98 | 12,157 | 96 |
| Online, GBS 32 samples | Dynamic CP | 51.16 | 13,301 | 106 |
| Offline, GBS 8 rows | Static CP4 | 36.27 | 14,450 | 113 |
| Offline, GBS 8 rows | Dynamic CP | 42.05 | 12,463 | 101 |

**Correctness:**
- Offline DCP and offline static start from the same rows: step 1 LM loss 12.83670 vs 12.83668, grad norm 70.11 vs 70.08.
- Losses and gradients stay finite with no skipped steps.
- The online DCP run on this branch reproduces #6682's online run: identical step-1/2 losses, 13,301 vs 13,069 tokens/s.

**Why offline DCP is slower than offline static:**
- First-fit decreasing fills rows to a mean 100.0% of 64K, so each step carries a nearly constant 524K tokens (stdev 1.2K, against 682K ± 93K online).
- Static CP4 (order-preserving `dp_balanced`) keeps those rows as 8 full CP4 bins.
- DCP re-bins the same sequences into 9.05 microbatches per step, against 8.00 for static, at the same per-rank critical path (both simulated with Megatron-Core's own schedulers on the run's lengths). Online it is the reverse, 11.3 against 13.7, which is where DCP gains.
- Measured on identical rows, DCP is −13.8% (95% bootstrap −16.5% to −10.9%; wins 8 of 190 paired steps).
- After its longer warmup (each new group size compiles on first use; about 40 steps), DCP is −9.7% over steps 41-200, close to the microbatch ratio.
- The original example reported offline DCP 14,925 vs online DCP 14,342 tokens/s on its own data, but did not measure offline static.

### Real data, 8-GPU CoderForge recipe (GPT-SFT offline packed Parquet)

`qwen35_text_35b_a3b_sft_8gpu_gb200_bf16_dynamic_cp_config` with `dataset.enable_offline_packing=true`:
- the first 4,000 SWE-Rebench trajectories, packed into 32K rows (`pad_seq_to_mult` 8) by the GPT-SFT builder
- random init, global batch 64 rows, 2×4 GB200 in one NVL72 rack, 12 steps, steps 5-12 reported

This exercises the new `GPTSFTPackedDataset` collate with DP2 × CP4:

| Configuration | Median step | Median TFLOP/s per GPU |
| --- | ---: | ---: |
| Online DCP (#6682 table, 64 trajectories/step) | 79 s | 100 |
| Online static CP4 (#6682 table) | 75 s | 106 |
| Offline DCP, 64 rows/step | 68 s | 116 |
| Offline static CP4, same rows | 61 s | 127 |

- Offline runs avoid the online loader stalls, because data is pre-tokenized: the online runs had 200-280 s steps while lazily tokenizing.
- About nine in ten trajectories exceed the 32K cap, so DCP has no short sequences to exploit, and static wins in both modes.

## Notes

- Making DCP keep pre-packed full rows as CP4 bins would be a Megatron-Core scheduler change, not part of this PR.
- `train.global_batch_size` counts packed rows with offline packing, so equal GBS does not mean equal work. `compare_runs.py` compares such runs by tokens per second.
