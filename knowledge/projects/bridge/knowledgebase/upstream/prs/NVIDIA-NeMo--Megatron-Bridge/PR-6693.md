# refactor(model): build K-EXAONE and Step-3.5-Flash from builder-backed model configs

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6693) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves **K-EXAONE** (236B-A23B, 2.0 750B-A37B) and **Step-3.5-Flash** onto the builder-backed `ModelConfig` / `ModelBuilder` path, for recipes and checkpoint conversion, following Qwen3 MoE (#6592), Mistral (#6593) and Ling MoE V2 + EXAONE 4.0 (#6401).

Both families build on the standard GPT builder through a thin `BridgeGPTModelConfig` subclass. Each subclass names a `TransformerConfig` subclass that declares the per-layer fields their custom decoder layers read.

# Changelog

- **Builder checkpoints with a pipeline layout** (cherry-pick of b9c846ff3 from #6642, unchanged):
  - `BridgeGPTModelConfig.as_dict()` saves the layout as given, so `run_config.yaml` reloads.
  - Without it, the three K-EXAONE 2.0 recipes, which set a layout, write a `run_config.yaml` that `load_model_config()` cannot reload.
  - Whichever of #6642 and this PR merges first, the other gets the identical hunk.
- **`ExaoneMoeBridge`**:
  - `provider_bridge()` is replaced by `hf_config_to_model_config_kwargs()`, and the provider path reuses the same kwargs.
  - The schedule validation and every mapped value are unchanged.
  - The `ExaoneMoeModelProvider` defaults that differ from the builder config's are set explicitly. Examples: RMSNorm, alltoall, the router settings, fp32 softmax, and no gradient-accumulation fusion.
  - `ExaoneMoeModelConfig` + `ExaoneMoeTransformerConfig` declare `layer_types`, `sliding_windows`, `swiglu_limits`, `mtp_layer_types` and `mtp_sliding_windows`.
  - `dtype_from_hf()` keeps accepting configs that carry only `dtype`, as before.
  - Opts in with `MODEL_CONFIG_CLASS = ExaoneMoeModelConfig` and `USE_MODEL_CONFIG_FOR_CONVERSION = True`.
- **`Step35Bridge`**:
  - Same move to `hf_config_to_model_config_kwargs()`.
  - Fields whose builder-config default differs from the provider's are set explicitly: `position_embedding_type`, `masked_softmax_fusion`, `rope_scaling`, `rope_scaling_factor`.
  - `Step35ModelConfig` + `Step35TransformerConfig` declare the layer types, the RoPE fractions and bases, the sliding-attention shape, the routed and shared SwiGLU limits, and `head_wise_attn_gate`.
  - `Step35ModelProvider` now declares `rotary_percents`, `swiglu_limits` and `swiglu_limits_shared`. The old `provider_bridge()` set them as undeclared attributes, which the shared provider path drops.
  - Opts in with `MODEL_CONFIG_CLASS = Step35ModelConfig` and `USE_MODEL_CONFIG_FOR_CONVERSION = True`.
  - `Step37Bridge` stays on providers. It reuses `build_step35_layer_spec` and the Step-3.5 provider; its provider fields are unchanged.
- **Layer specs** (`build_exaone_moe_layer_spec`, `build_step35_layer_spec`) accept a builder config as well as a provider:
  - They read the nested transformer config. EXAONE's dense-MTP spec copies that config instead of the builder config, whose shallow copy would share and mutate it.
  - With MTP, the GPT builder passes the block spec's `layer_specs[-1]` to `get_gpt_mtp_block_spec`. At the pinned Megatron Core, that function accepts a bare layer spec only when its module is `TransformerLayer` itself (Megatron Core `dev` accepts subclasses).
  - Both families' MTP layers use their own decoder layer class, so building with MTP failed with `ValueError: Invalid spec`. For builder configs, `layer_specs[-1]` now returns a one-layer block spec holding the same MTP layer spec. The provider path is unchanged.
- **Recipes**: the six K-EXAONE H100 recipes and the Step-3.5 pretrain recipe use `get_model_config()`.
- **Tests**:
  - Bridges: the builder mapping without the provider path, provider/builder parity on four K-EXAONE and one Step-3.5 config, and the builder-path decoder and MTP specs built through the GPT builder's `mtp_block_spec`. Also: config serialization round trips, and the exported MTP counts from a builder config.
  - The Step-3.5 tests of the old `provider_bridge()` overrides now test the kwargs.
  - Recipes: every K-EXAONE recipe, and the Step-3.5 recipe, is built against a real strict model config, with the provider API rejected.
- **Docs**: the Step-3.5 example README describes the config fields instead of `provider_bridge`. The adding-model-support skill notes the per-layer-field and MTP layer-spec pattern.
