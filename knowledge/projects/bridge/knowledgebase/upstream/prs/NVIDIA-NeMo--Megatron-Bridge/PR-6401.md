# refactor(model): build Ling MoE V2 and EXAONE 4.0 from builder-backed model configs

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6401) · state: open · merged: False

## Original PR description

# What does this PR do ?

Moves **Ling MoE V2 (Bailing)** and **EXAONE 4.0** onto the builder-backed `ModelConfig` / `ModelBuilder` path, for recipes and checkpoint conversion, following Muse Glimmer.

# Changelog

- **`BailingMoeV2Bridge`**: `provider_bridge()` is replaced by `hf_config_to_model_config_kwargs()`, and the provider path reuses the same kwargs. The builder config leaves `transformer_layer_spec` unset because MCore's builder default for MoE models is already `get_gpt_decoder_block_spec`, which honors the dense-first `moe_layer_freq`. The deprecated provider path keeps its explicit decoder block spec in `hf_config_to_provider_kwargs()`. `USE_MODEL_CONFIG_FOR_CONVERSION = True`.
- **`Exaone4Bridge`**: same kwargs migration. The builder config carries the Post-LN `exaone4_layer_spec`, which does not read its config. `USE_MODEL_CONFIG_FOR_CONVERSION = True`. The EXAONE 4.0 recipes use `get_model_config()`.
- **EXAONE 4.0 llama3 RoPE scaling — one intentional behavior change**:
  - **Before:** the bridge stored `low_freq_factor`, `high_freq_factor` and `original_max_position_embeddings` as undeclared attributes on the provider. Megatron Core never reads them: `RotaryEmbedding` calls `_apply_scaling(inv_freq, factor=rope_scaling_factor)` with fixed 1 / 4 / 8192. They were only echoed back on export, and a strict builder config cannot carry undeclared fields.
  - **Now:** only `rope_scaling` and `rope_scaling_factor` are mapped. Export writes Megatron Core's fixed values (as `LlamaBridge` does), and a warning is logged when a checkpoint's values differ from what Megatron applies.
  - **Impact:** EXAONE 4.0 checkpoints use exactly 1 / 4 / 8192, so their behavior is unchanged.
- **Tests**:
  - Bailing: builder mapping and provider/builder parity, with and without QKV bias.
  - EXAONE: builder mapping, parity, export of RoPE values from a builder config, and the non-default-value warning.
  - New strict recipe test for the three EXAONE 4.0 recipes.

# Verification

Each family was validated separately on tiny random-weight checkpoints (single GB200 node, NeMo 26.10 container; Bailing uses the HF modeling code vendored in this repo, EXAONE uses transformers 5.15).

**Conversion paths:**
- `scripts/conversion` GPU import at TP2 and export.
- `AutoBridge.import_ckpt` / `export_ckpt`.
- Load + forward as in `compare.py`.
- `roundtrip_checkpoint`.

Each was run on this branch and on `main`.

| Check | Ling MoE V2 (grouped sigmoid routing, dense-first) | EXAONE 4.0 (Post-LN, llama3 RoPE, tied embeddings) |
|---|---|---|
| Provider fields, `main` vs this branch | identical (incl. QKV bias) | identical (llama3 and no scaling) |
| `get_model_config()` vs provider | 0 diffs (17 / 18 on `main`) | 0 diffs (10 / 9 on `main`) |
| Export vs source HF weights (GPU TP2, CPU, and from a `main`-imported checkpoint) | bit-exact except expert-bias dtype (see below) | bit-exact |
| Logits: this branch vs `main`, and this branch on a `main`-imported checkpoint | bitwise-identical | bitwise-identical |
| `roundtrip_checkpoint` TP2 | pass | pass |
| Unit tests (family run) | 6 passed | 15 passed |

**Regression:** 11 Bailing/EXAONE recipe factories and 312 tests (1 skipped) across `models/bailing`, `models/exaone`, the EXAONE 4.0 recipe test, `test_auto_bridge.py`, `test_gpt_model_config.py`, the AutoBridge registration matrix, `conversion/` and `doc_consistency`.

**Lint:** `ruff check` and `ruff format --check` are clean (ruff 0.16.7; `pre-commit` itself not run).

**Pre-existing, identical on `main`; not changed by this PR:**

- **Expert-bias export dtype (Ling MoE V2):** a bf16 source exports the router expert bias as fp32 because Megatron keeps it in fp32. Values are identical after a cast.
- **Ling MoE V2 vs HF logits:** cosine about 0.97 for the tiny model, and `main` gives the same value. The HF-side value varies slightly between runs while the Megatron logits are bit-identical.
- **EXAONE 4.0 vs HF (transformers 5.15) logits:** cosine about 0.73, on `main` too. It persists with all-global attention and with no RoPE scaling, so it is structural rather than RoPE- or sliding-window-related.
- **EXAONE 4.0 unsupported shapes:** the bridge maps tied embeddings only (no `lm_head` mapping), and HF's hybrid sliding-window attention (global layers without RoPE) is not modeled.

These are worth separate investigation against real checkpoints.
