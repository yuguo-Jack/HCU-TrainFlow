# refactor(model): build Ling MoE V2 and EXAONE 4.0 from builder-backed model configs

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6401) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves **Ling MoE V2 (Bailing)** and **EXAONE 4.0** onto the builder-backed `ModelConfig` / `ModelBuilder` path, for recipes and checkpoint conversion, following Muse Glimmer.

# Changelog

- **Opt-in after #6305**: `MODEL_CONFIG_CLASS` now defaults to `None`, so each migrated bridge sets `MODEL_CONFIG_CLASS = BridgeGPTModelConfig` next to `USE_MODEL_CONFIG_FOR_CONVERSION = True` (as Qwen3 and Llama do), and its tests assert it.
- **`BailingMoeV2Bridge`**: `provider_bridge()` is replaced by `hf_config_to_model_config_kwargs()`, and the provider path reuses the same kwargs. The builder config leaves `transformer_layer_spec` unset because MCore's builder default for MoE models is already `get_gpt_decoder_block_spec`, which honors the dense-first `moe_layer_freq`. The deprecated provider path keeps its explicit decoder block spec in `hf_config_to_provider_kwargs()`. `USE_MODEL_CONFIG_FOR_CONVERSION = True`.
- **`Exaone4Bridge`**: same kwargs migration. The builder config carries the Post-LN `exaone4_layer_spec`, which does not read its config. `USE_MODEL_CONFIG_FOR_CONVERSION = True`. The EXAONE 4.0 recipes use `get_model_config()`.
- **EXAONE 4.0 llama3 RoPE scaling — one intentional behavior change**:
  - **Before:** the bridge stored `low_freq_factor`, `high_freq_factor` and `original_max_position_embeddings` as undeclared attributes on the provider. Megatron Core never reads them: `RotaryEmbedding` calls `_apply_scaling(inv_freq, factor=rope_scaling_factor)` with fixed 1 / 4 / 8192. They were only echoed back on export, and a strict builder config cannot carry undeclared fields.
  - **Now:** only `rope_scaling` and `rope_scaling_factor` are mapped. Export writes Megatron Core's fixed values (as `LlamaBridge` does), and a warning is logged when a checkpoint's values differ from what Megatron applies.
  - **Impact:** EXAONE 4.0 checkpoints use exactly 1 / 4 / 8192, so their behavior is unchanged.
- **Tests**:
  - Bailing: builder mapping and provider/builder parity, with and without QKV bias.
  - EXAONE: builder mapping, parity, export of RoPE values from a builder config, and the non-default-value warning.
  - New strict recipe test for the three EXAONE 4.0 recipes.

**Tied embeddings with PP > 1 lose the conversion tie flag**

Enabling the builder path here puts `share_embeddings_and_output_weights` on the outer `BridgeGPTModelConfig`, while the runtime model's `.config` is only the nested `TransformerConfig`. [`build_conversion_tasks()`](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/e0d514ef1cf6b5b3f4863004ea6e355daa33b7e8/src/megatron/bridge/models/conversion/model_bridge.py#L2195) reads the nested config, and `_share_embeddings_and_output_weights()` defaults the missing field to `False`.

For tied EXAONE at PP > 1, the last pipeline stage materializes `output_layer.weight`. It is consequently no longer filtered from conversion, but EXAONE's mapping registry has no mapping for this parameter, so conversion fails. The post-import shared-embedding broadcast also reads the missing flag and is skipped. Previously the provider's `.config` carried the flag. PP=1 avoids allocating the duplicate output parameter, so the reported TP2 checks do not cover this case.

Could we fix tie-flag resolution in the shared conversion helpers and add a tied EXAONE PP2 import/export test, including output-stage weights and synchronization? The same issue is noted on #6379, so one shared fix should cover both. HF initialization for training via `load_hf_weights()` also reaches this path.

This is separate from the pre-existing EXAONE architecture/parity limitations listed in the PR. The finding is based on pinned source inspection and source-level probes; I have not run a distributed checkpoint reproduction.

Thanks, confirmed. A tied tiny EXAONE 4.0 at PP=2 through the builder path fails on this branch with `ValueError: No mapping found for the following Megatron parameter(s): output_layer.weight`.

With it, the last-stage `output_layer.weight` equals the HF `embed_tokens`, and the export reproduces all 46 HF tensors exactly with no `lm_head.weight`. #6460 adds a tied PP=2 builder-path functional test (Qwen3, since its toy checkpoint is tied and already in L0).
