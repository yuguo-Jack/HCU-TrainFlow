# refactor(model): build Gemma 4 text models with ModelBuilder

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6612) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves the Gemma 4 text models onto the builder-backed `ModelConfig` / `ModelBuilder` path. `get_model_config()` now returns a `Gemma4DenseModelConfig` for E2B, E4B and 31B, or a `Gemma4ModelConfig` for 26B-A4B. Their builders construct the same model as the legacy providers. Gemma 4 VL and DiffusionGemma stay on providers for now; they can build on these configs later.

# Changelog

- **New `gemma4_config.py` and `gemma4_builder.py`.** Both Gemma 4 providers override `provide()`, so the generic `BridgeGPTModelConfig` / `GPTModelBuilder` cannot build them. Each variant gets its own config and builder:
  - `Gemma4DenseModelBuilder` builds `GPTModel` with the Gemma 4 dense layer spec. It then installs dual RoPE, the per-layer embeddings, shared-KV wiring, the dense checkpoint load aliases and the logit softcap, in the same order as `Gemma4DenseProvider.provide()`. Like the provider, it supports PP=1 and CP=1 only.
  - `Gemma4ModelBuilder` builds through `GPTModelBuilder` with the sliding RoPE base. It then swaps in Gemma 3's scaled embedding, Gemma 4's dual RoPE, the softcapped output layer and K=V tying, like `Gemma4ModelProvider.provide()`. `Gemma4ModelConfig.rotary_base` holds the (sliding, global) pair.
  - The Gemma 4 decoder fields live on Bridge transformer configs, `Gemma4DenseTransformerConfig` and `Gemma4TransformerConfig`, because the Gemma 4 layers read them from the `TransformerConfig` they are built with. Their `finalize()` keeps the provider checks: double-wide MLP marks the dist-checkpoint heterogeneous, and the MoE config rejects the execution modes its custom forward bypasses (`validate_gemma4_moe_orchestration`, moved from the provider).
- **`Gemma4Bridge`** sets `MODEL_CONFIG_CLASS` and `USE_MODEL_CONFIG_FOR_CONVERSION = True`, so `import_ckpt` and `compare.py` build `Gemma4ForCausalLM` checkpoints through the builder.
  - Both paths share the dense and MoE kwargs (`_dense_config_kwargs`, `_moe_config_kwargs`). The provider class defaults that the HF config does not carry moved to `_GEMMA4_DENSE_DEFAULTS` and `_GEMMA4_MOE_DEFAULTS`.
  - Two `GPTModelProvider` defaults differ from the builder config's, `masked_softmax_fusion` and `rope_scaling_factor`. The builder config pins the provider values, so both paths build the same model.
  - `megatron_to_hf_config()` accepts builder configs.
- **`Gemma4VLBridge`** handles the published `Gemma4ForConditionalGeneration` checkpoints. In `GEMMA4_CONVERSION_MODE=text`, `get_model_config()` returns the text builder config built from `text_config`. Outside text mode it raises `ModelConfigNotSupportedError`. Conversion stays on providers (`USE_MODEL_CONFIG_FOR_CONVERSION = False`), because the VL models still build through them.
- **`DiffusionGemmaBridge`** opts out (`MODEL_CONFIG_CLASS = None`) and restores the base `hf_config_to_model_config`, so it keeps rejecting `get_model_config()` instead of inheriting the Gemma 4 text config.
- **E4B recipe:** `gemma4_e4b_pretrain_2gpu_h100_bf16_config` builds `cfg.model` from `get_model_config()` in text mode.
- **Dense layer dtype fix** in `modeling_gemma4.py`: the per-layer-embedding linears (`per_layer_input_gate`, `per_layer_projection`) and the `layer_scalar` buffer are now created in `params_dtype`, like the Megatron modules around them and the MoE layer.
  - They used to be fp32. The builder conversion path (`import_ckpt`, `compare.py`) builds without `Float16Module`, so E2B and E4B failed there with a bf16/fp32 dtype mismatch. `main`'s provider fails the same way when built without the wrapper.
  - Wrapped models are unchanged, since `Float16Module` already cast these to bf16.
- **Docs:** the Gemma 4 README describes the new configs and builders and lists the new test file.
- **Tests:**
  - New `test_gemma4_builder.py` covers:
    - config types and fields;
    - field-by-field parity with the providers, and export parity;
    - the `as_dict` / `from_dict` round trip and `run_config.yaml` reload;
    - VL and DiffusionGemma routing;
    - dense and MoE builder construction (mocked `GPTModel`);
    - layer-spec delegation and the `finalize()` checks.
  - The Gemma 4 recipe tests fake `get_model_config()` and assert a `Gemma4DenseModelConfig`.

# Verification

I compared `main` (e97a67acb) and this branch in the same container (NeMo 26.10 rc5) on one 8-GPU H100 node, with Megatron Core 89b28875 from `main`'s pin.

**Config parity** on the published E2B, E4B, 31B and 26B-A4B configs, plus a dense and a MoE toy config:
- The legacy providers are identical on `main` and this branch, raw and after `finalize()`. This holds for both `Gemma4Bridge` and `Gemma4VLBridge` in text mode.
- The builder config matches the provider on every shared field (390 for MoE, 396 for dense) except `transformer_layer_spec`. Neither dense path reads that field. For MoE it is the same `gemma4_block_spec`, behind a function instead of a `partial`.

**Forward parity** with the HF weights loaded. For each model I compared every Megatron tensor (shape, dtype and bytes) and the logits for two prompts. Every comparison below is identical: no tensor differs, and the logits are bitwise-identical.

| Model | Parallelism | Tensors per rank | `main` provider vs branch builder | `main` vs branch provider | `main` provider vs branch builder without `Float16Module` |
|---|---|---|---|---|---|
| E2B-it | 1 GPU | 496 | identical | identical | identical |
| E4B-it | 1 GPU | 594 | identical | identical | identical |
| 26B-A4B-it | EP2 | 4683 | identical | identical | identical |
| 31B-it | TP2 | 663 | identical | identical | identical |

The last column builds the model without `Float16Module`, the way `import_ckpt` and `compare.py` build it. Before the dtype fix, E2B and E4B failed that way with `expected mat1 and mat2 to have the same dtype ... BFloat16 != float`, on `main`'s provider too.

**Unit tests** with real Transformer Engine on the same node, over `tests/unit_tests/models/{gemma,gemma_vl,diffusion_gemma}`, `test_gemma4_checkpoint_vocab.py` and `test_logit_dtype_wrapper_propagation.py`: 606 passed and 1 skipped on this branch, against 572 passed and 1 skipped on `main`. The 34 extra tests are the new builder tests.

**Rerunning** in a second job:
- **Functional test** `test_gemma4_conversion.py`, which no CI launcher runs. Its auto-config round trip imports a dense toy model through the builder and exports it again.
  - In the first job, the functional conftest's GitHub test-data download took over 20 minutes from the cluster. The branch run timed out before its first test finished. The rerun skips that download; these tests don't use the data.
  - On `main`, the TP=2 conversion and the auto-config round trip passed. The PP=2 case failed with `Gemma4DenseProvider currently supports PP=1 only`, an existing limitation that the builder keeps.
- **E4B recipe training** for 20 mock-data steps, `main` (provider) against this branch (builder), comparing loss, grad norm and params norm at every step.
  - As shipped (2 GPUs, TP=2, sequence length 4096), the recipe ran out of memory in its first forward step on 80 GB H100s, on `main` exactly as on this branch.
  - The rerun uses all 8 GPUs (TP=2, DP=4) at sequence length 2048, with the determinism overrides on.

**Unit tests on CPU** (macOS, Transformer Engine stubbed): 618 passed, 6 failed across `tests/unit_tests/models/{gemma,gemma_vl,diffusion_gemma}`, `test_gemma4_recipe.py` and `test_gemma4_checkpoint_vocab.py`. The 6 failures need real Transformer Engine or GPU dist-checkpointing, and they fail the same way on `main` in that environment.
