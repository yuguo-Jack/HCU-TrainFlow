## Original PR description

# What does this PR do ?

Moves **Qwen2/Qwen2.5** and **MiMo** onto the builder-backed `ModelConfig` / `ModelBuilder` path, for recipes and checkpoint conversion, following Muse Glimmer and #6365 (Qwen3).

**Builds on #6365 (merged).** It reuses #6365's `TransformerConfig` YaRN fields, without which Qwen2.5 YaRN checkpoints could not convert through the builder. Rebased onto `main` after #6365's squash-merge, so the PR now contains only the Qwen2 and MiMo commits.

# Changelog

- **Opt-in after #6305**: `MODEL_CONFIG_CLASS` now defaults to `None`, so each migrated bridge sets `MODEL_CONFIG_CLASS = BridgeGPTModelConfig` next to `USE_MODEL_CONFIG_FOR_CONVERSION = True` (as Qwen3 and Llama do), and its tests assert it.
- **`test_gpt_model_config.py`**: #6305's `test_unmigrated_bridge_keeps_provider_without_warning` used Qwen2 as its unmigrated example. It now opts a local `Qwen2Bridge` subclass out with `MODEL_CONFIG_CLASS = None`, keeping the check that an unmigrated family stays on the provider path without a `FutureWarning`.
- **`Qwen2Bridge`**: `provider_bridge()` is replaced by `hf_config_to_model_config_kwargs()`, and the provider path reuses the same kwargs (`hf_config_to_provider_kwargs`). Provider-implied defaults are explicit (`masked_softmax_fusion`, `rope_scaling=False`, `rope_scaling_factor=1.0`, `position_embedding_type` via `setdefault("rope")` so YaRN is preserved). `USE_MODEL_CONFIG_FOR_CONVERSION = True`.
- **`MimoBridge`** (subclasses `Qwen2Bridge`): extends the Qwen2 kwargs with `qk_layernorm=False`, `add_qkv_bias=True`, and MTP depth (`mtp_num_layers`, `mtp_loss_scaling_factor=0.1`) instead of overriding `provider_bridge()`. It inherits the conversion flag.
- **Recipes**: all 30 Qwen2/2.5 H100 recipes use `get_model_config()`.
- **Tests**:
  - New `test_qwen2_bridge.py`; Qwen2 had no bridge unit tests. It covers the direct builder mapping, provider/builder parity (tied, fp16, YaRN), and the YaRN transformer fields plus HF export.
  - A strict recipe test runs every Qwen2/2.5 recipe against a real `BridgeGPTModelConfig`.
  - MiMo tests cover the builder MTP mapping and provider parity.

**Tied embeddings with PP > 1 lose the conversion tie flag**

Enabling the builder path here changes where `share_embeddings_and_output_weights` lives: it is on the outer `BridgeGPTModelConfig`, while the runtime model's `.config` is only the nested `TransformerConfig`. However, [`build_conversion_tasks()`](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/4903e5c0027a13bd0cf226ce81f815ab39f826ee/src/megatron/bridge/models/conversion/model_bridge.py#L2195) reads that nested config, and `_share_embeddings_and_output_weights()` defaults the missing field to `False`.

For a tied Qwen2/2.5 checkpoint at PP > 1, the last pipeline stage materializes `output_layer.weight`. Conversion therefore keeps that parameter and requests `lm_head.weight`, which is absent from a deduplicated tied HF checkpoint. The post-import embedding broadcast reads the same missing flag and is also skipped. The provider path retained the flag in `.config`. PP=1 avoids the duplicate output parameter, so TP2-only checks do not cover this case.

Could we make the shared conversion helpers resolve the tie flag from the runtime model or outer model config, and add a tied-checkpoint PP2 import/export regression that checks the output-stage weights and synchronization? This also affects HF initialization for training through `load_hf_weights()`.

This finding is based on the pinned builder/conversion code and source-level probes; I have not run a distributed checkpoint reproduction.

Thanks, confirmed. A tied tiny Qwen2 at PP=2 through the builder path fails on this branch with `ValueError: Hugging Face checkpoint is missing mapped parameter(s): output_layer.weight -> lm_head.weight`. Tied Qwen3 fails the same way on current `main`, since #6365 moved Qwen3 conversion to the builder.

The shared fix is in #6460: `_share_embeddings_and_output_weights()` now takes the unwrapped model. It keeps reading `model.config` when the config declares the flag, so the provider path and VLM wrappers are unchanged, and otherwise falls back to the flag Megatron Core stores on the built language model. With it, tied Qwen2 at PP=2 has a last-stage `output_layer.weight` equal to the HF `embed_tokens`, and the export reproduces all 50 HF tensors exactly with no `lm_head.weight`. #6460 also adds a tied PP=2 builder-path functional test (Qwen3, L0). I'll rebase this PR onto it once it merges.
