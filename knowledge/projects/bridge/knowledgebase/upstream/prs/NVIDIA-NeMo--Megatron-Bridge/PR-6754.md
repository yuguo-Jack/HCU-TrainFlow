# fix(ckpt): allow repository config targets in AutoBridge.from_auto_config

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6754) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Fixes `convert.sh export` for checkpoints whose run config restores a config class from the model repository's code, such as Kimi-K2.5-VL's vision config. These exports failed even with `--trust-remote-code`, because `AutoBridge.from_auto_config()` reloads the run config before anything allows `transformers_modules.` targets. It now allows them when `trust_remote_code=True`, as `AutoBridge.load_megatron_model()` already does.

# Changelog

- **`AutoBridge.from_auto_config()`**: with `trust_remote_code=True`, adds `transformers_modules.` to the instantiate allowlist before `load_model_config()` reads the checkpoint's run config. The remote-code warning now comes before that load. Without `trust_remote_code`, nothing changes: a run config with such a target still fails the allowlist.
- **Unit test** (`test_auto_bridge.py`): a Kimi-K2.5-VL provider run config whose `vision_config` names a `transformers_modules.<dir>.<hash>.configuration_*` class, the form these checkpoints store, fails without `trust_remote_code` and loads with it. On `main`, the trusted call fails too. A fixture removes the prefix from the allowlist for the test and restores it afterwards.

# Root cause

Both export backends, `scripts/conversion/gpu_backend.py` and `scripts/conversion/cpu_backend.py`, call `AutoBridge.from_auto_config(megatron_path, reference, trust_remote_code=...)` to build the exported Hugging Face config from the checkpoint, and only then load the weights through `load_megatron_model()`. Kimi-K2.5-VL's provider keeps the repository's `KimiK25VisionConfig`, so its `run_config.yaml` contains

```yaml
vision_config:
  _target_: transformers_modules.<checkpoint dir>.<hash>.configuration_kimi_k25.KimiK25VisionConfig
```

`load_model_config()` in `from_auto_config()` rejected that target:

```text
InstantiationException: Instantiation of 'transformers_modules.<checkpoint dir>.<hash>.configuration_kimi_k25.KimiK25VisionConfig' is not allowed because it is not in the allowlist.
```

`load_megatron_model()` adds the prefix when the bridge trusts remote code, but `from_auto_config()` runs first.

Other run-config readers checked:

- `cpu_backend.export_checkpoint` calls the same `from_auto_config()`, so this change fixes it too. Its `export_ckpt()` loads through `load_megatron_model()`, which already allowed the prefix.
- `AutoBridge.export_ckpt()` and `AutoBridge.load_megatron_model()` already allowed it.
- `gpu_backend._maybe_restore_pipeline_layout()` reads the run config with `yaml.safe_load`, without instantiating targets.

# Verification

**GPU** (8× H100, NeMo 26.10.rc9 container with transformers 5.17.0 and Transformer Engine 2.20.2, Megatron Core 902feb8e; `main` = 32d7094ed). The checkpoint is `moonshotai/Kimi-K2.5` @4d01dfe0 reduced to layers 0-3 (one dense layer and three MoE layers with all 384 INT4 experts) plus the full vision tower and projector, 10,760 tensors. `main`'s GPU backend imported it at EP8 and at PP2×EP4; conversion runs the checkpoint's repository code. Each export runs `gpu_backend.export_checkpoint()` with `trust_remote_code=True`, as `convert.sh export --trust-remote-code` does.

| Check | Result |
|---|---|
| `AutoBridge.from_auto_config(checkpoint, reference, trust_remote_code=True)` on `main` | `InstantiationException` on the vision config's `transformers_modules.` target |
| The same call on this branch | Loads; `vision_config` is the repository's `KimiK25VisionConfig` |
| The same call with `trust_remote_code=False` on this branch | `InstantiationException`, as before |
| GPU export at EP8 on `main` | Fails on every rank: `export_checkpoint()` → `from_auto_config()` → `load_model_config()` raises the `InstantiationException` |
| GPU export at EP8 and at PP2×EP4 on this branch | Both succeed, in about 2 minutes each. Both are bit-exact against the source on all 10,760 tensors: the INT4 experts re-quantize to the source's packed weights, scales and shapes. Both are byte-identical (25 files, `config.json` included) to exports of the same checkpoints that `main` wrote with the prefix allowed by hand |

**Unit tests** (CPU, transformers 5.20.2, Megatron Core 902feb8e):

- The new test passes. On `main` it fails at the trusted call, with the `InstantiationException` above raised from `load_model_config()` in `from_auto_config()`.
- `tests/unit_tests/models/test_auto_bridge.py`, `tests/unit_tests/conversion/launcher`, `tests/unit_tests/utils/test_instantiate_utils.py`, `tests/unit_tests/training/test_model_load_save.py` and `tests/unit_tests/models/kimi_vl`: 555 pass. The two cases of `test_save_hf_pretrained_truncates_vocab_padding` fail in my local environment on `main` and on this branch alike, because it lacks APEX's CUDA extension.
- The new test still sees the untrusted failure when an earlier test in the same process has already allowed the prefix, and later tests see the allowlist as it was.
- `pre-commit run --all-files` is clean.

# Not changed

- `examples/conversion/compare_text_generation.py` also calls `load_model_config()` without allowing the prefix. It compares text generation for language models; the providers that keep Hugging Face sub-configs in their run configs are vision-language and audio providers.
- `load_megatron_mimo_model()` has no remote-code option. The models with MIMO conversion support (Nemotron Omni and Nemotron 3.5 Super VL) keep only plain settings in their providers, no repository config classes.
