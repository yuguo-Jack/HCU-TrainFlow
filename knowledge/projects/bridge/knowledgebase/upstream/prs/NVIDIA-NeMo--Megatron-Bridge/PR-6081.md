# [model] fix: Preserve token classification AutoBridge dispatch

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6081) · state: open · merged: False

## Original PR description

## Summary

Token-classification configs can validly advertise both `AutoModelForTokenClassification` and `AutoModelForCausalLM` remote implementations. AutoBridge selected the token-classification Hugging Face wrapper, but its validation and bridge lookup unconditionally preferred the causal `auto_map` entry. That paired the token wrapper with the causal bridge and `lm_head` mappings instead of the registered token-classification bridge and `score` mappings.

This change keeps token-classification dispatch on its declared, registered architecture while preserving the existing causal `auto_map` behavior for other architectures. Both validation and runtime bridge selection use the same narrow guard. Related task-head support context: #5211.

## User impact

A supported trusted-remote token classifier with both task entries could fail conversion/provider construction or use the wrong head mappings. The fix preserves `score.weight` and `score.bias` mapping for that configuration.

**Light review — LGTM**

The fix correctly closes a misrouting bug: a `*ForTokenClassification` model whose `auto_map` also exports `AutoModelForCausalLM` (a common multitask config) previously matched the causal-LM entry and was routed down the causal-LM bridge path. The new `_get_architecture_class_name_via_auto_map` guard returns `None` for token-classification architectures so resolution falls through to the correct token-classification bridge. Both call sites (`_causal_lm_architecture` and `_validate_config`) are updated consistently, and the added test exercises the exact scenario (bridge selects `PreTrainedTokenClassification`, `score.weight`/`score.bias` mappings present).

Minor observation (non-blocking): the helper name is generic but only special-cases `ForTokenClassification`. A `*ForMaskedLM` architecture whose `auto_map` also contains `AutoModelForCausalLM` would still be misrouted the same way. If that combination is possible for supported masked-LM models, consider generalizing the guard or documenting why it is token-classification-only.

**Suggested test cases:**
- test_token_classification_config_with_multitask_auto_map_uses_task_bridge (added — covers the fix)
- A negative/regression case asserting a pure causal-LM `auto_map` (no `ForTokenClassification` architecture) still resolves to the causal-LM class name via `auto_map`, guarding against over-broad `None` returns.

No perf tests impacted.
