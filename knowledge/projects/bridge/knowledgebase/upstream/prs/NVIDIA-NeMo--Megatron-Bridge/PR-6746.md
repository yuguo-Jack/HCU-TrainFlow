# feat(recipe): add DeepSeek V4 Pro BF16 GB300 performance recipe

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6746) · state: open · merged: False

## Original PR description

# What does this PR do?

Add a full DeepSeek V4 Pro BF16 performance recipe for 256 GB300 GPUs. It preserves the existing MXFP8 workload and optimizer settings, with eager execution and selective recompute that fit sustained training.

# Changelog

- Export `deepseek_v4_pro_pretrain_256gpu_gb300_bf16_config`, sharing workload construction with the existing MXFP8 factory. The existing factory's behavior is unchanged.
- Disable quantized compute and parameter gathering, CUDA graphs, and activation offloading. Recompute MLA up-projection, mHC, and the complete MoE block.
- Preserve the full model, sequence length 4096, GBS 4096, MBS 1, PP4/VPP4/EP64, canonical forced routing, FP32 master weights, and BF16 Adam moments/main gradients.
- Add configuration and effective-precision tests using the strict builder-backed model config. Describe usage and scope in the recipe docstring.

# Validation

## Best validated performance: full-iteration CUDA graphs on Core dev

The primary comparison is the best validated configuration for each precision: **MXFP8 985.615 vs BF16 710.9375 model TFLOP/s/GPU** (**38.6% higher throughput**, **27.9% shorter step time** for MXFP8). BF16 needed additional whole-MoE recompute to fit graph capture; MXFP8 did not. This compares the best configurations tested, not an isolated precision-only change or an exhaustive tuning search.

| Configuration | Selective recompute modules | Mean s/step | Mean model TFLOP/s/GPU | Peak allocated GB | Minimum sampled free GiB | Job |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| **Best validated MXFP8** | `mla_up_proj,mhc` | **21.44775** | **985.615** | 238.94 | 13.91 | 3552249 |
| **Best validated BF16** | `mla_up_proj,mhc,moe` | **29.73475** | **710.9375** | 172.16 | 77.99 | 3555265 |
| Reference: MXFP8 with BF16's additional recompute | `mla_up_proj,mhc,moe` | 24.82700 | 851.450 | 176.37 | 74.79 | 3555265 |

Each successful case completed 50 updates on all 256 GB300 GPUs: three warmup updates followed by 47 captured/replayed updates, finite losses/gradients, no skipped updates, verified optimizer dtypes, and clean per-case exit. Timings are native logger means over steps 11–50; free memory is the minimum of 1 Hz device samples. BF16 with the original `mla_up_proj,mhc` settings completed warmup but OOMed during capture, motivating the additional MoE recompute. The successful MXFP8 case in job 3552249 remains valid despite that job's later BF16 failure.

All cases use full Pro, sequence length 4096, GBS 4096, MBS 1, TP1/CP1/PP4/VPP4/EP64, activation offload for `core_attn,attn_proj`, and full-iteration forward/backward CUDA graphs (`optimizer_cuda_graph=False`). Both allocations used 64 nodes in four NVLink domains of 16 nodes each, with EP64 within a domain. The best MXFP8 and BF16 measurements used different allocations; the 851.45 reference and BF16 ran sequentially in the same allocation. FP32 master weights and BF16 Adam moments/main gradients were retained.

**Source scope:** these graph experiments used Core **dev `c4220af3a62e851585afdac6f5aa7496163afdaf`**, Bridge base `bf58509537dbaad2c3c2519504822088e75ed52c`, and local Bridge changes to enable the BF16 graph configuration, initialize the dev DSA metric tracker before capture, and release the optimizer's retained gradient-copy graph before shutdown. Runtime: NeMo 26.10.rc10, TE 2.20.2+44f31bbe, CUDA 13.4, cuDNN 9.26, frontend 1.29.1. These experimental changes are **not included in this PR**, whose BF16 recipe still uses eager execution. The validated BF16 graph run explicitly adds `moe` to the recompute modules.

**Main-branch code check (2026-11-01):** Core main `037b883c9e7996b361943d27342ebd9757a5417a` has [full-iteration graph capture/replay](https://github.com/NVIDIA/Megatron-LM/blob/037b883c9e7996b361943d27342ebd9757a5417a/megatron/core/full_cuda_graph.py#L303-L349), but [rejects mHC recompute combined with fine-grained activation offloading](https://github.com/NVIDIA/Megatron-LM/blob/037b883c9e7996b361943d27342ebd9757a5417a/megatron/core/transformer/transformer_config.py#L3086-L3110). That guard also exists in Bridge main's pinned Core `902feb8eea1839d60b312cb7b6ec3b2b0724cc6d`. Thus generic full-iteration graph support on main does not establish compatibility of this exact DeepSeek V4 configuration; these graph results are dev validation, not a main runtime pass.

The eager comparison below is historical evidence for the PR's eager configuration, not the headline MXFP8-versus-BF16 performance ranking. Graph results are consistent with CUDA graphs helping MXFP8 substantially, but kernel profiling has not established how much of the gain is attributable to quantization/launch overhead. Synthetic data, random initialization, and forced routing make these performance checks, not convergence or strict numerical-parity validation. Evaluation/checkpoint peaks and other hardware remain untested.

## Eager configuration validation for this PR

Both full-model cases completed 50 optimizer updates on all 256 GB300 GPUs, with finite losses/gradients, no skipped updates, and initialized optimizer state. Native warmed metrics use steps 11–50. Device headroom is the minimum of 1 Hz samples across all nodes.

**Measured performance (256 GB300, mean over steps 11–50):** BF16 achieved **42.1110 s/step and 502.06 model TFLOP/s/GPU**; matched MXFP8 achieved **49.0875 s/step and 430.71 model TFLOP/s/GPU**. BF16 step time was **14.21% shorter** in this eager/whole-MoE-recompute configuration. The cause of the performance gap has not been established with kernel profiling.

| Mode | s/step | Model TFLOP/s/GPU | Peak allocated GB (GiB) | Peak reserved GB (GiB) | Minimum sampled free GiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| Matched MXFP8 | 49.0875 | 430.71 | 230.97 (215.11) | 233.09 (217.08) | 49.16 |
| BF16 | 42.1110 | 502.06 | 227.25 (211.64) | 230.12 (214.32) | 52.09 |

These full-model measurements used the pre-rebase candidate `2e98d3426a13e02cc94c1c67d9a7fcdd32118765`, on Bridge base `cc1df94a058dfddc860f37644632597ecb4798fe` and Core `5de526f232464e1b1ff1d6645fe2c4aaf01bc0d8`. Runtime: NeMo 26.10.rc10, TE 2.20.2+44f31bbe, CUDA 13.4, cuDNN 9.26, frontend 1.29.1. Full-model performance has not been remeasured on the newer builder/Core revisions in current main.

The measured MXFP8 baseline uses the same eager/no-offload/whole-MoE settings as BF16. The canonical graph/offload combination is rejected by the tested Core mHC guard; eager MLA+mHC recompute alone OOMed at iteration 2, prompting whole-MoE recompute. This comparison does not represent the unchanged public MXFP8 recipe defaults. Synthetic data, random initialization, and canonical forced routing were retained. That eager experiment did not validate convergence, strict numerical parity, CUDA graphs, evaluation/checkpoint peaks, or other hardware; the separate dev graph validation is recorded above.

Latest-main checks: 27 focused unit tests and full `pre-commit run --all-files` passed with no formatting changes. The separate four-GPU reduced-model smoke passed four updates per mode on every rank, with finite loss/gradients, no skipped updates, and verified FP32 master/BF16 Adam state. This checks candidate `bf58509537dbaad2c3c2519504822088e75ed52c`, rebased onto Bridge `270264f20`, with Core `902feb8eea1839d60b312cb7b6ec3b2b0724cc6d`. A workstation strict-mypy attempt could not resolve the training dependencies and does not constitute a type-check pass.
