# fix(build): cap PyNvVideoCodec RTSP redirects on r0.7.0

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6655) · state: closed · merged: True

## Original PR description

## Summary

Backport FFmpeg's RTSP redirect limit (upstream commit f5d4fd186c68913240c4f6e9cda98443e1518b34) to the FFmpeg 9.0.1 library bundled in PyNvVideoCodec 2.2.3. This addresses CVE-2026-107696 without removing PyNvVideoCodec or changing its library ABI.

The final-image build uses the source archive included in the pinned wheel, verifies its SHA-256, applies the upstream patch, and rebuilds `libavformat.so` with the wheel's configuration. It checks that the rebuilt library exports the same symbols before replacing all three installed aliases. The build fails if the wheel or ABI changes unexpectedly.

## Validation

- Rebuilt the x86_64 wheel's FFmpeg library in the NVIDIA PyTorch 26.09 base container; the rebuilt library loaded successfully.
- Compared all 2,326 exported symbols with the original wheel: identical.
- A local RTSP server returning repeated 302 responses produced a bounded error after nine responses (`Too many RTSP redirects`).
- Confirmed that the x86_64 and aarch64 wheels contain the same FFmpeg source archive hash and configuration flags. An arm64 smoke build under QEMU rebuilt the patched library and loaded it successfully; the full NeMo image build remains to be validated in CI.
- `bash -n` and repository pre-commit hooks passed.

## Scan note

This is a source patch backport to FFmpeg 9.0.1. Version-based scanners may continue to report CVE-2026-107696 until PyNvVideoCodec publishes a wheel with a patched FFmpeg release or the scanner accepts evidence of this backport.

**Non-blocking — retain an executable regression for the redirect limit.** There is no accompanying test of this new security behavior. The [export comparison](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/c413c4237ec0513a3b10f52987b28910606661ce/docker/common/patch_pynvvideocodec_ffmpeg.sh#L47-L56) cannot distinguish bounded from unbounded RTSP redirects. The inspected [CI image build](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/c413c4237ec0513a3b10f52987b28910606661ce/.github/workflows/cicd-main.yml#L532-L554) builds Dockerfile.ci, not the changed final image, and [generic import checking excludes PyNvVideoCodec](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/c413c4237ec0513a3b10f52987b28910606661ce/docker/common/import_check_skip.txt#L20-L21). Thus those checks can pass without exercising this limit; the PR's manual reproduction is not retained as a regression.

Add a CPU-only integration harness, invoked by the patched-image validation path, that loads the installed package's actual libavformat directly and calls `avformat_open_input` against a loopback RTSP fixture. Direct loading avoids requiring the NVIDIA driver merely to import PyNvVideoCodec. Give the harness a timeout so an unbounded loop fails safely. No production behavior change is requested: preserve permitted redirects and direct connections, rather than satisfying the test by rejecting all 3xx responses.

Proposed acceptance checks: an endpoint replying to every OPTIONS request with `302` and a Location pointing back to itself must produce nine redirect responses, then a negative open result with `Too many RTSP redirects`, without a tenth redirect request. A chain of eight redirects ending at a valid RTSP fixture must open successfully, as must that fixture without redirects. Run these checks for both supported wheel architectures. These are proposed tests, not executed results; the exact harness implementation needs verification against the wheel's available headers/API, which are not mounted here.
