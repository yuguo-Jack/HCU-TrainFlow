# fix(ckpt): copy the source tokenizer and processor files on HF export

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6724) · state: closed · merged: True

## Original PR description

# What does this PR do ?

`save_hf_pretrained` (and `save_hf_pretrained_modelopt`) now copy the source checkpoint's tokenizer and processor files instead of re-serializing them with `save_pretrained`.

Under transformers 5, re-serializing changes these files. Exporting Qwen3.6-35B-A3B (and Qwen3.5-0.8B) gave, compared with the source:

- `tokenizer.json` with different content (`pre_tokenizer`, `decoder`, `model`), and `tokenizer_config.json` without `added_tokens_decoder`;
- `preprocessor_config.json` switched from `Qwen2VLImageProcessorFast` to the slow `Qwen2VLImageProcessor`, plus a new `processor_config.json`;
- no `vocab.json`, `merges.txt` or `video_preprocessor_config.json`.

ModelOpt's Megatron exporter copies these files unchanged, so this also makes the bridge export match it (found while comparing the two on Qwen3.6-35B-A3B).

# Changelog

- `PreTrainedBase.save_artifacts` copies the source's files for each tokenizer / processor artifact that was loaded from the source and is unchanged since, instead of calling `save_pretrained` on it. The copied files include the tokenizer's own `vocab_files_names` and named chat templates (`additional_chat_templates/*.jinja`), at their relative paths. Hub sources (pinned revision, offline cache) go through the existing `_copy_custom_modeling_files`.
- Edits are detected from a cheap snapshot taken when the lazy property loads the artifact:
  - tokenizer: token count, added tokens, special tokens, chat template, padding / truncation side, `model_max_length`, and a fast tokenizer's normalizer, pre-tokenizer, post-processor and decoder;
  - processor: its config, chat template and tokenizer.
- These artifacts are still saved with `save_pretrained`:
  - one assigned to the wrapper (`model.tokenizer = ...`);
  - one edited in place (`add_special_tokens`, `pad_token = ...`, a new `chat_template`, a backend normalizer, ...);
  - one loaded with arguments that change it (`model_max_length`, `padding_side`, `subfolder`, ...). Only download / model-loading arguments (`revision`, `cache_dir`, `token`, `torch_dtype`, `device_map`, ...) keep the copy;
  - one whose source has none of its files.

  Their saved files win over another artifact's source copies.
- Docs: `docs/bridge-guide.md` notes the copy and when it falls back to `save_pretrained`.

One visible difference: `PreTrainedCausalLM` sets `pad_token = eos_token` when the source tokenizer has none; that change was saved before and now isn't, so the export's tokenizer matches the source.

# Tests

- New unit tests in `tests/unit_tests/models/hf_pretrained/test_base.py`:
  - unchanged source artifacts are copied and not re-serialized;
  - a replaced processor's saved files win over the tokenizer's source copies;
  - an artifact the source has no files for is still saved;
  - with a real `PreTrainedCausalLM` tokenizer: unedited or only used for encoding, it is copied verbatim; after `add_special_tokens`, a new `chat_template`, a backend normalizer edit, a load-time `model_max_length` override or the setter, it is re-serialized and keeps the change. The two in-place edit cases fail on the first commit of this PR, and the normalizer and load-argument cases on its second;
  - named chat templates are copied and reload under their names (fails on the second commit).
- `tests/unit_tests/models/hf_pretrained`, `test_auto_bridge.py`, `training/test_checkpointing.py`: 957 passed, 1 skipped (`nvcr.io/nvidian/nemo:26.10.rc9`).
- `PreTrainedCausalLM("Qwen/Qwen3.5-0.8B").save_artifacts(...)` against the source snapshot: before, 3 files missing, 1 extra and 4 differing; now only `config.json` differs. With an edited chat template, the tokenizer files are re-saved and the processor files still match the source.
