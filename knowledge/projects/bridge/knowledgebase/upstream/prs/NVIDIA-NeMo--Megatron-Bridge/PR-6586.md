[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6586) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Makes the BAGEL card's `pretrain_fsdp` leaf runnable from the card: it loaded `work/model-verification/bagel/seed42-mcore-init`, which nothing published produces, so it now starts from a fresh seed-42 init.

# Changelog

- `examples/model_verification_cards/bagel/card.yaml`: `pretrain_fsdp` uses `checkpoint.load=null checkpoint.load_optim=false checkpoint.load_rng=false dataset.dataloader_load=null`, as the `pretrain` leaf does.
- `docs/models/bagel/bagel.md`, `docs/fern/.../bagel.mdx`, `docs/_static/model-verification/catalog-v1.json`: regenerated.
- `tests/unit_tests/doc_consistency/test_verification_card_published_commands.py`: new check that every non-null `checkpoint.load` / `dataset.dataloader_load` in a card is written by a command in the same card, plus a regression case.

# Additional Information

- **Root cause:** the leaf resumed from an init checkpoint created out of band; no card item, README or doc writes it and the item has no `depends_on`.
- **Regression?** No. The reference has been there since the card landed in #5605.
- **Verification:** the fixed command ran 30/30 steps on 4x8 H100 (nemo:26.04 at Bridge `fd8ab826`, the card's `pretrain` pin, plus the pin's `uv.lock` versions of transformers/energon/av), with finite losses and 0 skipped/NaN iterations. The new test fails on the old card and passes on the fixed card in the NeMo container.
- **Not included:** the card metrics are unchanged. The card-default pin `8d1c3a12` cannot run BAGEL because its Megatron-LM submodule lacks `megatron.core.models.bagel`; that is a separate issue.
- **NVBug:** 6964570.

- svcnvidia-nemo-ci · comment · 2026-10-21T03:51:16Z · [source](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6586#discussion_r4332855939)

File: `tests/unit_tests/doc_consistency/test_verification_card_published_commands.py` · line None

**[P2] Count `--megatron-path` as a producer only for imports**

**Failure:** Put these two commands in the same synthetic card, with no import or checkpoint-save command:
```bash
./scripts/conversion/convert.sh export --megatron-path work/unproduced --hf-path work/hf
./scripts/training/train.sh checkpoint.load=work/unproduced
```
The new check passes because the export's `--megatron-path` enters `produced`. But export **reads** that path and writes `--hf-path`; the [export backend](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/560ffe748ccbc36e4494a0071c4de208afe16e9c/scripts/conversion/gpu_backend.py#L359-L365) explicitly raises when the source is missing. The check should reject this unproduced load rather than letting another reader satisfy it.

**Correction:** In this function's producer branch, retain `--megatron-path` only for `convert.sh import`. A small suggested replacement for the current `if name in producers` block is:
```python
if name in producers:
    if name == "--megatron-path" and not (
        len(tokens) > 1
        and Path(tokens[0]).name == "convert.sh"
        and tokens[1] == "import"
    ):
        continue
    produced.setdefault(card, set()).add(value.rstrip("/"))
```
This restores the invariant that an input-only conversion argument cannot establish a writer. This suggestion is source-reasoned, not executed; verify it before adopting it.

**Preservation and acceptance:** Add proposed fixtures asserting that export-only source plus matching `checkpoint.load` raises, while import output plus matching load passes for both the output root and its `iter_0000000` child. Retain export's `--hf-path` as an output and the existing training-save producers. Also retain the current unproduced-load rejection, accept BAGEL's `checkpoint.load=null` / `dataset.dataloader_load=null`, and verify that an import in a different card cannot satisfy the load.
