# refactor(model): build Kimi-K2.5-VL from a builder-backed model config

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6751) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves **Kimi-K2.5-VL** (`KimiK25VLBridge`, `moonshotai/Kimi-K2.5`) from `KimiK25VLModelProvider` to a builder-backed **`KimiK25VLModelConfig`** on `BridgeGPTMLAModelConfig`, for `get_model_config()` and checkpoint conversion, and switches its SFT recipe to `get_model_config()`. Part of the provider → builder migration (MB-1857: MB-1929).

Stacked on #6750 (`BridgeGPTMLAModelConfig`, Kimi K3, Sarvam MLA); review only the last commit.

# Changelog

- **`KimiK25VLModelConfig`** (new, `kimi_vl/kimi_k25_vl_config.py`): a `BridgeGPTMLAModelConfig` whose outer fields are the provider's vision-language fields, with the provider's names and defaults: `vision_config`, `hf_model_path`, `trust_remote_code`, the token IDs, the freeze options, and `scatter_embedding_sequence_parallel=False`. The remote `KimiK25VisionConfig` keeps its settings as attributes its dataclass does not declare, so the config serializes it as provider checkpoints do and restores it with the config class's own `from_dict()`.
- **`KimiK25VLModelBuilder`** (new, `kimi_vl/kimi_k25_vl_builder.py`): builds the existing `KimiK25VLModel` (same checkpoint keys, same registered target) from the GPT builder's language model and its process groups, and applies the freeze options. Conversion builds without `Float16Module`, so the builder casts the Hugging Face vision tower and projector to `params_dtype`, as that wrapper does on the provider path (tensors marked to stay in FP32 stay in FP32).
- **`KimiK25VLModel`**: optional keyword arguments for a builder: the model config that holds the vision-language settings, a language-model factory and the process groups. It now captures the pad and ignore token IDs at construction, as it already did the media placeholder ID. The provider path builds the same model as before.
- **Bridge**: `MODEL_CONFIG_CLASS = KimiK25VLModelConfig`, `USE_MODEL_CONFIG_FOR_CONVERSION = True`. `hf_config_to_model_config_kwargs()` maps the Kimi K2 text config and sets every value the old `provider_bridge()` set, plus `deallocate_pipeline_outputs=False` and `rope_scaling_factor=1.0`, where the builder config's defaults differ from the provider's. `hf_config_to_provider_kwargs()` returns the same kwargs plus the provider's decoder block spec. A thin `provider_bridge()` keeps the source's path, remote-code trust and generation config on the deprecated provider. The INT4 import and export hooks and the virtual-key `build_conversion_tasks()` override are unchanged.
- **Remote-code trust on the builder path** (`model_bridge.py`, `auto_bridge.py`): `KimiK25VLModel` loads its vision tower and projector from the checkpoint's code, and `get_model_config()` hands the bridge only the Hugging Face config. `AutoBridge` now sets its `trust_remote_code` on the model bridge, as it sets `export_weight_dtype`, and the Kimi bridge records it and the config's `name_or_path` on the model config. Other bridges ignore the attribute.
- **Recipe**: `kimi_k25_vl_sft_512gpu_h100_bf16_config` (and its `kimi_k25_vl_sft_config` alias) uses `AutoBridge.from_hf_pretrained("moonshotai/Kimi-K2.5", trust_remote_code=True).get_model_config()`.
- **Tests**: the builder mapping without the provider path, builder vs provider on every shared field, `trust_remote_code` through `AutoBridge`, the provider's source settings; config defaults vs the provider, `as_dict()`/`from_dict()` and `run_config.yaml` round trips that keep the vision config's attributes, flat overrides; the builder's construction, dtype cast, stage flags, freezing and type check; the model's builder inputs and its sequence-parallel process group; the recipe tests' `AutoBridge` stub now serves a real model config and rejects `to_megatron_provider()`.
- **Docs and skill**: the model page and the example README describe the model config; `adding-model-support` covers restoring remote-code configs and models that load code from the checkpoint.

# Behavior notes

- **Checkpoint format:** `AutoBridge.import_ckpt` and `convert.sh import` now write builder-format checkpoints. `main` cannot load them (no builder config class there); this branch loads `main`'s provider checkpoints.
- **Pipeline parallelism with virtual stages and no layout:** like every builder-backed GPT config, `GPTModelConfig.finalize()` requires equal model chunks per stage; 61 layers cannot be split evenly into PP4 × VP2 chunks, so that combination now fails at finalize; the provider did not check it there. The recipe's layouts are unaffected.
- The deprecated provider (`to_megatron_provider()`) keeps every field and emits the usual `FutureWarning`. It no longer gets the undeclared `async_tensor_model_parallel_allreduce` attribute, which nothing reads.
- `generation_config` stays a provider field: nothing reads it, and the builder config is built from the Hugging Face config alone.

# Verification

**CPU parity** (transformers 5.20.2, Megatron Core 902feb8e; the remote config classes replaced by hand-written mirrors, so no repository code runs; `main` = 58382ddf9):

- 11 Hugging Face configs: `moonshotai/Kimi-K2.5` @4d01dfe0 in bf16, fp32 and fp16; truncated to 4 layers, with two dense layers, without `rope_scaling`, with a different YaRN, without the optional token and scaling fields, and with a smaller vision config; the functional test's toy config; the unit tests' config.
- The deprecated provider vs `main`, raw and finalized for 9 layouts (no parallelism, TP2+SP, PP2, PP2×VP2, PP4×VP2 with and without the recipe's layout, EP8, TP2+SP×EP8×ETP1, PP16 with the recipe's layout): every field, the vision config, the generation config, the decoder and MTP specs and the exported HF config identical; only the undeclared attribute above is gone.
- Builder config vs `main`'s provider, raw and finalized for the same layouts: identical on all 432 shared fields, with identical vision config, decoder and MTP specs and exported HF config. The only difference is the PP×VP check above (PP4×VP2 without a layout). `KimiK25VLModelConfig.from_dict(as_dict())` restores every field, including non-default vision settings.
- `AutoBridge.from_hf_pretrained(..., trust_remote_code=True)`, the same without trust, and `AutoBridge.from_hf_config()`: provider vs `main` identical; the builder config carries the same `hf_model_path` and `trust_remote_code` as the provider and records the source in `extra_checkpoint_metadata`.
- Recipe `kimi_k25_vl_sft_512gpu_h100_bf16_config` and its alias, `main` (provider) vs branch (builder): 432 shared model fields identical as built, after `runtime_config_update()` at 512 GPUs, after CLI overrides through `run_recipe.py`'s path (PP4 × VP2 with the layout re-derived, TP4, EP16, freeze options, sequence length 8192), and after validating the overridden config at 1,024 GPUs; every other section, the layout builder, the vision config and the FLOPs identical.
- Unit tests: `tests/unit_tests/models/kimi_vl`, `tests/unit_tests/recipes/kimi_vl` and the Kimi conversion-task test pass (125). The recipe-factory and perf-recipe sweeps, recipe metadata, Slurm examples, collators, `test_auto_bridge.py`, `test_model_bridge.py`, the registration matrix and mixed precision (1,213 tests): no outcome changed versus `main`. `pre-commit` clean.

**GPU** (H100, NeMo 26.10.rc9 container: torch 2.14.0a0, transformers 5.17.0, Transformer Engine 2.20.2, flash-attn 2.8.3; both trees on Megatron Core 902feb8e; `main` 58382ddf9 vs this branch). Checkpoint: `moonshotai/Kimi-K2.5` @4d01dfe0 reduced to layers 0-3 (one dense layer and three MoE layers with all 384 INT4 experts), with the full vision tower and projector (10,760 tensors), loaded with its repository code. The SFT smoke uses the same layers with the first 64 experts.

The vision tower is frozen in the compared smoke because its flash-attention backward is not deterministic (`KimiK25VLModel` sets MoonViT's `use_deterministic_attn=False` on both trees): with it trainable, two `main` runs already differ from step 3 by about 1e-3 relative, and `main` vs branch differ by the same amount after identical steps 1-2. The exports ran with `transformers_modules.` added to the instantiate allowlist on both trees; without it, the GPU export backend fails on `main` and on this branch alike (see follow-ups). The exported `config.json` matches between the trees; against the source, transformers 5.17 rewrites the nested configs (`rope_scaling` as `rope_parameters`, the text config's `model_type` as `deepseek_v3`, legacy generation keys dropped).

# Not changed (follow-ups)

- **Pre-existing, `main`:** `convert.sh export` (`gpu_backend.export_checkpoint`) cannot export a Kimi-K2.5-VL checkpoint. `AutoBridge.from_auto_config()` reloads the checkpoint's run config before `transformers_modules.` targets are allowed, so the remote `vision_config` fails the instantiate allowlist, even with `--trust-remote-code`. `AutoBridge.load_megatron_model()` allows the prefix when it trusts remote code; `from_auto_config()` does not.
- `examples/conversion/hf_to_megatron_generate_vlm.py` and `examples/conversion/hf_megatron_roundtrip_multi_gpu.py` (used by `L1_Launch_models_kimi_k25_vl.sh`) still build through the deprecated provider path, which keeps working; moving them to `get_model()` is a separate change.
