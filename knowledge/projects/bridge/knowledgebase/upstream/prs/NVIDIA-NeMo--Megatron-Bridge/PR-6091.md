# fix(recipe): rescale global_batch_size to 768 for NemotronH-56B 256-GPU BF16

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6091) · state: closed · merged: False

## Original PR description

# What does this PR do ?

Rescales `global_batch_size` from 192 to 768 in the 256-GPU BF16 NemotronH-56B recipes (`b200` and `gb300`), matching their FP8-CS counterpart recipes and satisfying DP=128 batch divisibility.

# Changelog

- Wrapped `nemotronh_56b_pretrain_64gpu_b200_fp8cs_config()` in `nemotronh_56b_pretrain_256gpu_b200_bf16_config` with `_with_global_batch_size(..., 768)`.
- Wrapped `nemotronh_56b_pretrain_64gpu_gb300_fp8cs_config()` in `nemotronh_56b_pretrain_256gpu_gb300_bf16_config` with `_with_global_batch_size(..., 768)`.
- Added unit tests in `tests/unit_tests/recipes/test_nemotronh_56b_perf_recipes.py` verifying `global_batch_size == 768` and batch divisibility at DP=128.

# Runtime validation status

The GBS change resolves the DP=128 batch-divisibility failure. A separate retest on Bridge `ea5dded83078` with the equivalent GBS=768 change and MCore `f6c33bde4cdc` reported that B200 BF16 still runs out of GPU memory during a Mamba chunk-state allocation, before the first iteration completes or CUDA-graph capture starts ([details](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6091#issuecomment-5763717719)). This PR has not been shown to make the 256-GPU BF16 workload runnable end to end. The reported 64-GPU FP8-CS control completed 30 steps; it does not validate the BF16 preset.

The retest confirmed `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` was active. Rank 6 failed a 512 MiB Mamba chunk-state allocation with 119 MiB free; its exit-time peaks were 172.4454 GiB allocated and 173.4551 GiB reserved. The 953.90 MiB reserved-but-unallocated figure means the diagnostic alone cannot distinguish raw capacity from fragmentation or allocation-reuse constraints. Any memory change still requires a 256-GPU BF16 run through steady-state steps. No memory or convergence settings are changed here.

Here is the full OOM diagnostic for rank 6:
```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 512.00 MiB. GPU 6 has a total capacity of 178.35 GiB of which 119.00 MiB is free. Including non-PyTorch memory, this process has 178.21 GiB memory in use. Of the allocated memory 172.45 GiB is allocated by PyTorch, and 953.90 MiB is reserved by PyTorch but unallocated.
```
The failing allocation is in `mamba_ssm/ops/triton/ssd_chunk_state.py:826`, in `_chunk_state_fwd`.
Immediately preceding the exception, the same rank reported an expandable-segment mapping failure requesting **20 MiB**, with **19 MiB free**. These figures and the exception’s 119 MiB free are separate observations during the failure sequence.
Rank 6’s recorded allocator peaks were:
- Allocated: **185,161,845,248 bytes (172.4454 GiB)**
- Reserved: **186,245,971,968 bytes (173.4551 GiB)**

Those are high-water marks reported at process exit, not a time-resolved memory snapshot. The exception above provides the memory figures at the failed allocation.
This points to severe capacity pressure even with expandable segments enabled. However, the 953.90 MiB reserved-but-unallocated exceeds the requested allocation, so these figures alone do not rule out fragmentation or allocation-reuse constraints. I would avoid attributing the failure exclusively to either cause without an allocator snapshot.
No recomputation or parallelism candidate has been validated yet; the batch-divisibility fix remains independently supported.
