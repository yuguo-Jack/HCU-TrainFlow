# refactor(model): build Gemma 4 VL from builder-backed model configs

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6709) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Moves the **Gemma 4 VL** bridge (`Gemma4VLBridge`: 26B-A4B MoE, 31B, E4B and E2B) from its providers to builder-backed `ModelConfig` + `ModelBuilder`, for recipes and checkpoint conversion, and switches the Gemma 4 VL recipes to `get_model_config()`. The builders build the existing `Gemma4VLModel`, so checkpoint keys, the bridge's registered target and the deprecated providers stay the same. GLM-4.5V, planned alongside, was dropped from the migration on 2026-10-28; `GLM45VBridge` and its recipes are unchanged.

# Changelog

- **Gemma 4 VL configs** (new, `gemma_vl/gemma4_vl_config.py`): `Gemma4VLModelConfig` (MoE) subclasses the text `Gemma4ModelConfig`, and `Gemma4DenseVLModelConfig` (dense) subclasses `Gemma4DenseModelConfig` (#6612).
  - `Gemma4VLModel` reads the Hugging Face vision, text and audio configs and the image and audio token IDs from the config it is built with, during construction and in `forward()`. Their transformer configs (`Gemma4VLTransformerConfig`, `Gemma4DenseVLTransformerConfig`) declare those fields. The outer configs hold `vision_soft_tokens_per_image`, the BOS/EOS and video token IDs, and the freeze options.
  - The MoE config does not scatter embeddings for sequence parallelism (`Gemma4VLModel` scatters after merging image features), as `Gemma4VLModelProvider` does.
  - `as_dict()` serializes the Hugging Face sub-configs the way provider checkpoints do (`_ConfigContainerBase._convert_value_to_dict()`). Megatron Core's `ModelConfig.as_dict()` reads every field of a nested dataclass, and Transformers' `Gemma4TextConfig` raises on its per-layer attributes (`num_key_value_heads` …), so `run_config.yaml` could not be written otherwise.
- **Gemma 4 VL builders** (new, `gemma_vl/gemma4_vl_builder.py`): `Gemma4VLModelBuilder` and `Gemma4DenseVLModelBuilder` subclass the Gemma 4 text builders. They construct `Gemma4VLModel` as the providers' `provide()` does: the Hugging Face vision (and audio) encoders first, then the language model from the text builder, then the freeze options.
- **`Gemma4VLModel`** takes two keyword-only arguments that builders pass: `build_language_model` (in place of the provider's `provide_language_model()`) and `pg_collection` (in place of the provider's `_pg_collection`, for context-parallel slicing and sequence-parallel scattering). The tied-embedding flag is read from the built language model. Providers pass neither, so the provider path is unchanged.
- **Bridge**: `Gemma4VLBridge` sets `MODEL_CONFIG_CLASS` and `USE_MODEL_CONFIG_FOR_CONVERSION = True`.
  - `hf_config_to_model_config_kwargs()` starts from the Gemma 4 text bridge's kwargs for `text_config` and adds the vision-language fields. Where the text kwargs differ, it keeps the values the VL providers have always used: for MoE, the checkpoint's dtype (the text model pins bf16) and no embedding scatter; for dense, `scatter_embedding_sequence_parallel=True`, which the dense VL provider copied from the text provider (the dense language model does not read it).
  - `hf_config_to_provider_kwargs()` returns the same kwargs, so the deprecated providers keep every field; `provider_bridge()` only dispatches between the dense, MoE and text-mode providers.
  - `GEMMA4_CONVERSION_MODE=text` still returns the Gemma 4 text builder configs. `Gemma4Bridge` (text) moves its builder kwargs into `_text_model_config_kwargs()` / `_build_model_config()` for the VL bridge to reuse, and its text-mode MoE provider maps the text config through the base provider kwargs, so the VL bridge's override does not intercept it.
  - `DiffusionGemmaBridge` subclasses `Gemma4VLBridge` and stays on its provider: it restores the base `hf_config_to_model_config_kwargs()` as well as `hf_config_to_model_config()`, and maps its provider kwargs through `Gemma4VLBridge`'s mapping.
- **Recipes**: the Gemma 4 VL 26B-A4B SFT and PEFT recipes build their model with `AutoBridge.from_hf_pretrained(...).get_model_config()`.
- **Docs**: `examples/models/gemma/gemma4/README.md` lists the VL configs and builders; `adding-model-support/vlm-patterns.md` notes how to build an HF-encoder wrapper from a builder config.
- **Tests**:
  - `test_gemma4_vl_builder.py` (new): config types and field placement, builder vs provider on every shared field, export config vs provider, flat-override routing and rejection of undeclared names, a `run_config.yaml` round trip through `load_model_config()`, what the builders pass to the model (configs, language-model factory bound to the text builder, process groups, stage flags), freezing, and invalid configs.
  - `test_gemma4_vl_modeling.py`: `Gemma4VLModel` built with a language-model factory and process groups, and its forward using those process groups.
  - Recipes: the recipe stubs serve `get_model_config()` and fail on `to_megatron_provider()`; a new test builds both recipes from a real Gemma 4 MoE config through a builder-only `AutoBridge`.
  - `test_gemma4_builder.py`: the VL bridge's text mode converts through the builder (both families); the old "rejects builder configs outside text mode" test is replaced by the VL builder tests.

# Behavior notes

- **Checkpoint format:** `AutoBridge.import_ckpt` and `convert.sh import` now write builder-format checkpoints for Gemma 4 VL. `main` cannot load them (`Gemma4VLModelConfig` and `Gemma4DenseVLModelConfig` do not exist there). This branch loads `main`'s provider checkpoints. NeMo RL's `megatron_bridge` checkpoint loader cannot read builder-format checkpoints yet; that applies to every migrated family.
- **`GEMMA4_CONVERSION_MODE=text` conversion** now goes through the Gemma 4 text builders (verified equivalent to the text providers in #6612) instead of the text providers.
- **Unchanged limitation (both paths):** the Hugging Face config serializer drops Gemma 4's per-layer settings (`global_head_dim`, `num_global_key_value_heads` live in neither dataclass fields nor instance attributes), so a `text_config` reloaded from `run_config.yaml` falls back to the default global head size. The published checkpoints use the defaults, and the Megatron model is rebuilt from its own fields.
