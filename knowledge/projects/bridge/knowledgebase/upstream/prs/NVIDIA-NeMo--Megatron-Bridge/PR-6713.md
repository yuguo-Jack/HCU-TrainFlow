# fix(model): make full recompute work for Gemma 4 E2B and E4B

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6713) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Fixes full activation recompute (`recompute_granularity="full"`) for the Gemma 4 models with per-layer embeddings, E2B and E4B. For these models `_gemma4_checkpointed_forward` in `modeling_gemma4.py` replaces Megatron Core's recompute helper, and it had two bugs:

1. **Crash at the first step.** The (local, global) RoPE tuple went to `tensor_parallel.checkpoint` as one argument: `TypeError: save_for_backward can only save variables, but argument 4 is of type tuple`. The helper now unpacks the pair into two tensor arguments and repacks it inside `custom_forward`, as Megatron Core's `recompute.checkpointed_forward` does, in both the `tensor_parallel.checkpoint` and `te_checkpoint` branches.
2. **Wrong gradients once the crash is fixed.** E2B and E4B share K/V across layers (E2B: layers 15-34 reuse the K/V of layers 13 and 14; E4B: 24-41 reuse 22 and 23). The source attention stores its K/V on the module and the shared layers read it from there. A checkpointed chunk runs its forward without autograd, so a shared layer recomputed in a later chunk than its source got K/V without history, and its gradient never reached the source layers or anything before them. The helper now passes the stored K/V between chunks as checkpoint inputs and outputs, so autograd links the shared layers to their sources, as in the HF implementation.

Gemma 4 26B-A4B and 31B have no per-layer embeddings and no shared K/V. They use Megatron Core's own helper and are not affected.

# Changelog

- `_gemma4_checkpointed_forward` passes the RoPE pair as two tensor arguments and repacks it inside `custom_forward`.
- `_gemma4_checkpointed_forward` passes the K/V stored by each shared-KV source layer between recompute chunks as checkpoint inputs and outputs.
- CPU unit tests in `tests/unit_tests/models/gemma/test_gemma4_modeling.py` for both fixes.

# Testing

- The new CPU unit tests run the helper through Megatron Core's real `CheckpointFunction` and compare outputs and every gradient with a no-recompute reference:
  - dual and single RoPE, through the `tensor_parallel.checkpoint` and `te_checkpoint` branches;
  - two K/V sources and three shared layers under uniform 1, uniform 2, block 3 and the `te_checkpoint` branch.

  6 of these fail on main; with only the RoPE change, the 4 shared-KV cases fail.
- GPU (H100, NeMo 26.10 container, Megatron Core a2965235): E2B SFT with the Gemma 4 VL 26B-A4B recipe, TP1 and DP4 on 4 GPUs, 10 steps, GBS 8, sequence length 1024, deterministic, all from the same imported checkpoint.

| Run | Result |
|---|---|
| main, the recipe's full uniform recompute | `TypeError` at step 1 |
| RoPE change only, uniform 1 | Trains, but step-1 grad norm is 212.2 against 255.9 without recompute; loss differs from step 3 |
| This PR: uniform 1 (twice), uniform 4, block 20 | lm loss and grad norm bitwise equal to no recompute at all 10 steps (loss 9.018 → 4.666) |
| This PR vs main, recompute off | Bitwise equal |

Peak allocated memory on rank 0 after 2 iterations: 58.3 GB without recompute, 51.2 GB with uniform 1. Carrying the shared K/V adds about 0.02 GB.

- TE checkpoint branch (taken when `fp8`/`fp4` is set): same E2B setup with `bf16_with_fp8_current_scaling_mixed`. With this PR, full uniform recompute (twice) and block recompute of 20 layers are bitwise equal to no recompute in loss and grad norm at all 10 steps, through TE's own checkpoint. On main the run completes but has the same gradient loss (step-1 grad norm 212.2 against 255.9). The dense Gemma 4 layers use Megatron Core's local modules, so this covers the checkpoint path, not FP8 numerics.
