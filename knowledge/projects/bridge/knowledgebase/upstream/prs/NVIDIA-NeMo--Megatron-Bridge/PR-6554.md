# fix(recipe): compile Inductor kernels in-process for Nemotron 3 Ultra H100 SFT

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6554) · state: closed · merged: False

## Original PR description

# What does this PR do ?

Make the Nemotron 3 Ultra H100 full-SFT recipe compile Inductor kernels in the training process (`TORCHINDUCTOR_COMPILE_THREADS=1`), so its first training step cannot deadlock in Inductor's pool of forked compile workers, and make `run_recipe.py` apply that setting before Inductor is imported.

# Changelog

- `nemotron_3_ultra_sft_384gpu_h100_bf16_openmathinstruct2_packed_config`: set `TORCHINDUCTOR_COMPILE_THREADS=1` in the recipe environment.
- `scripts/training/run_recipe.py`:
  - Add `TORCHINDUCTOR_COMPILE_THREADS` to `IMPORT_TIME_RECIPE_ENV_VARS`. Inductor reads it once, when `torch._inductor.config` is imported, and `run_recipe.py`'s own imports already load that module (with the default of 32 threads) before the recipe environment is applied. A recipe that declares it now triggers the existing one-time re-exec.
  - Decide whether the caller set an import-time variable from the environment recorded when the script starts, before its imports. The same imports load vLLM (through nvidia-modelopt's quantization plugins), whose `env_override` sets `TORCHINDUCTOR_COMPILE_THREADS=1` after Inductor has read it. The old `name not in os.environ` check took that for a caller setting and skipped the re-exec, so the recipe value never reached Inductor. Before re-executing, a value set after startup is dropped so the recipe value is exported, and the re-exec is logged with the variables that triggered it. A value the caller sets at launch still wins.
- Tests: parametrize the bootstrap tests over all import-time variables; cover a variable set by a library after startup and the re-exec log line; check that the startup environment is recorded before the script's first non-standard-library import; pin the recipe value.
- Docs: describe the import-time variables, the re-exec, and how to choose a different value in `docs/recipe-usage.md` and its Fern copy; explain the setting in the Nemotron 3 Ultra example README.

# Why

NVBug 6674155: after #6376, release QA still saw this recipe hang in its first training step on 48 nodes.

- **Inductor compile-worker deadlock.** Inductor compiles through a fork-based worker pool. After 60 s idle the pool shuts down (`quiesce_async_compile_pool`), and the next compile forks a new one. On Python 3.12 before 3.12.8 (and 3.13.0), a worker forked while the old executor's management thread holds its shutdown lock inherits the held lock; when the old executor is garbage-collected in the child, its weakref callback blocks on that lock and the compile job never returns (pytorch/pytorch#200848; fixed by python/cpython#125599 in 3.12.8 and 3.13.1). The containers ship Python 3.12.3.
- **Why this recipe.** During the twelve-stage first step each rank compiles in bursts minutes apart, so its pool quiesces and re-forks many times. In QA's hung run, one rank waited forever for a compile result while one of its 32 forked workers was blocked in `concurrent/futures/process.py` (`weakref_cb` → `with shutdown_lock:`); its expert-parallel group and then the whole pipeline stalled behind it.
- **Why the recipe value needed the launcher change.** Without it, the recipe value would be applied after Inductor has fixed its thread count, and vLLM's own `TORCHINDUCTOR_COMPILE_THREADS=1` would hide that from the bootstrap check. In the release container, a dry run of this recipe through `run_recipe.py` ends with Inductor's `compile_threads` at 32 on main and at 1 with this PR.

# Verification

- [x] 48 nodes (384 H100s), recipe defaults with `TORCHINDUCTOR_COMPILE_THREADS=1` exported at launch: two QA runs completed all 100 steps. A 10-step run of ours matched the losses of the default-pool runs (lm 0.381 → 0.308, no skipped or NaN iterations), started no compile-worker processes, and took 1,827 s for the first step, compared with 1,835-1,850 s with the default pool.
- [x] Dry runs of this recipe through `scripts/training/run_recipe.py` in the release container, with a startup hook that prints the PID, the bootstrap marker and the variable when each interpreter starts, and Inductor's `compile_threads` at exit:
  - main: no re-exec, `compile_threads` 32;
  - this PR, variable unset at launch: one re-exec (same PID, marker set, variable 1 from the start), `compile_threads` 1, and the re-exec is logged;
  - this PR with `env_vars.TORCHINDUCTOR_COMPILE_THREADS=2`: one re-exec, `compile_threads` 2, so the recipe value rather than vLLM's reaches Inductor;
  - this PR with `TORCHINDUCTOR_COMPILE_THREADS=4` set at launch: no re-exec, `compile_threads` 4.
- [x] 48-node run (384 H100s) of the card's SFT command through `run_recipe.py` from this commit, with nothing exported at launch (100 steps, weights-only final checkpoint), in the release container:

  - all 100 steps completed: lm loss 0.381 → 0.233, no skipped or NaN iterations, steps 1-10 within 2.1e-4 (relative) of the earlier runs, first step 1,826 s;

# Additional Information

- Related to NVBug 6674155; follow-up to #6376.
- Side effect for this recipe: because it now re-executes, its whole recipe environment is exported before Python starts, so `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` (noted in #6376) now takes effect even when the launcher does not export it.
- The re-exec runs `run_recipe.py` itself, so a wrapper script that imports `run_recipe.py` and calls `main()` is replaced for this recipe, as it already is for benchmark recipes and for recipes that declare an NVTE import-time variable.
- In this container, a recipe that re-executes for another reason starts its re-executed process with vLLM's `TORCHINDUCTOR_COMPILE_THREADS=1`, which the bootstrap exports with the rest of the environment, so it already compiles in-process on main and with this PR. A dry run of `nemotron_3_ultra_pretrain_256gpu_gb200_bf16_ep16_config`, which declares `NVTE_CUTEDSL_FUSED_GROUPED_MLP`, ends with `compile_threads` 1; benchmark recipes always re-execute the same way. Library recipes that do not re-execute keep the default 32-worker pool. Setting the variable for every recipe while the containers ship an affected Python would make this consistent, but it would re-execute every recipe, so I left it for a follow-up.
- Other recipes have not shown this hang. The general fix belongs upstream: a defensive fix in PyTorch, or Python 3.12.8 or later in the container. `TORCHINDUCTOR_QUIESCE_ASYNC_COMPILE_POOL=0` also avoids the re-fork, but it keeps 32 idle compile workers per rank.
- Please cherry-pick to r0.7.0 (#6376 was cherry-picked in #6423).
