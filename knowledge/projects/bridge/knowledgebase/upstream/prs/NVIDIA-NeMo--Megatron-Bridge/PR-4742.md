# test(functional): add MoE performance recipe proxies

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/4742) · state: open · merged: False

## Original PR description

## What does this PR do?

Adds reduced, model-specific L0 functional proxies for the production Qwen3 30B-A3B, DeepSeek V3, and GPT-OSS 120B performance recipes. These model families were implicated by the same downstream Blackwell MXFP8 grouped-MLP failure, but their production HybridEP and TE op-fuser paths were not exercised by Bridge PR CI.

This PR is intentionally stacked on #4679 and should be retargeted to main after that PR merges.

## Coverage

Each model has its own test module and launcher, matching the existing L0 functional-test structure. Every launcher performs one direct torchrun invocation so failures and runner allocation are isolated by model.

- Qwen3 30B-A3B
  - H100 FP8 current-scaling proxy on the supported x8 runner
  - GB200 MXFP8 proxy from the production 8-GPU constructor, reduced to EP4 for the supported x4 GB200 runner
- DeepSeek V3 GB200 MXFP8
  - production 256-GPU constructor reduced to two decoder layers, 16 experts, PP2, and EP2 on x4
  - retains MTP, a production-style pipeline layout, HybridEP, TE op-fuser, and full-iteration graphs
- GPT-OSS 120B GB200 MXFP8
  - production 64-GPU constructor reduced to two layers and EP4 on x4
  - retains the 120B width, 128 experts, top-4 routing, alternating sliding attention, HybridEP, TE op-fuser, and full-iteration graphs

All proxies assert natural routing, grouped GEMM, discrete expert weights, precision, overlap behavior, and recipe-specific graph settings before training.

## Why this matrix

A Qwen-only proxy guards the shared grouped-MLP operator path, but not DeepSeek MTP/pipeline assembly or the GPT-OSS 120B provider and expert topology. Existing DeepSeek PP1/FSDP and GPT-OSS 20B EP1 tests do not represent those production paths.

Other downstream failures were intentionally kept in their appropriate layers: Llama packed-recipe construction already has dedicated recipe unit regression and packed-LoRA functional coverage; evaluator, performance-threshold, golden-data, and infrastructure failures do not justify additional model GPU jobs.

## Validation

- Ruff lint and format checks pass for all three model modules
- shell syntax checks pass for all four launchers
- project-container collection: 4 functional tests collected across 3 modules
- targeted recipe unit tests: 32 passed
- Qwen3, DeepSeek V3, and GPT-OSS 120B production constructors instantiated with simulated GB200 capability; all x4 proxy topology and path assertions passed
- H100 Qwen x8 runtime passed on the prior SHA before the GB200 runner-only adjustment

Full GB200 training validation is delegated to this PR functional CI.

## CI resource note

The GB200 proxies use separate x4 L0 jobs, matching the only existing explicit GB200 multi-GPU runner size in the repository. The H100 Qwen proxy remains an x8 L0 job because that pool is configured and the runtime test has passed.
