# fix(torchtitan): bound DeepSeek compile at routed experts

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1216) · state: closed · merged: True

## Original PR description

## Summary
Selective compile changes from https://github.com/AMD-AGI/Primus/pull/962 increased memory usage and caused regression on DSv3 BF16. This PR proposed following changes

- compile DeepSeek TransformerBlocks as whole graphs with graph breaks enabled
- keep `GroupedExperts.forward` eager as the explicit EP/FSDP boundary
- compile inside activation-checkpoint wrappers so checkpointed MoE blocks stay compiled
- preserve TorchTitan's scalar-output capture for dynamic token-choice MoE shapes
- avoid the BF16 HBM regression from separately compiled MoE children while preserving finite FP8 training
- add regression coverage for the unified compile boundary, patch rebinding, and a real-compile checkpoint-wrapped MoE block

## Root cause
The regression is caused by the selective compilation policy. Stock v26.7 used whole-TransformerBlock compilation and completed BF16 successfully, but the v26.7 stack also broke when the newer selective compilation changes were applied.

The selective policy left the outer MoE TransformerBlock eager while compiling attention, norms, routing, shared experts, and grouped-MM as separate full graphs. Those boundaries prevent Inductor from scheduling and releasing intermediates across the complete block. Outputs from the separately compiled children remain live while eager MoE routing, expert-parallel communication, and FSDP hooks execute. The resulting higher live-tensor set leaves insufficient contiguous HBM for the compiled cross-entropy backward allocation, causing the BF16 OOM. This also explains why changing allocator settings could mask the crash but did not restore memory usage or throughput.

Using unrestricted whole-block compilation is not sufficient: it recovers BF16 memory efficiency, but can capture routed-expert EP/FSDP behavior in the graph and produced non-finite FP8 training.

## How the fix works
The new policy restores one compile region around each complete TransformerBlock with `fullgraph=False`, allowing Dynamo and Inductor to optimize across attention, routing, shared-expert, residual, and normalization operations instead of creating many isolated compiled children.

Before compiling the blocks, it:

1. preserves TorchTitan v0.2.2's `torch._dynamo.config.capture_scalar_outputs = True` setup so scalar values used by dynamic token-choice MoE shapes do not create unintended graph breaks;
2. wraps `GroupedExperts.forward` with `torch.compiler.disable(..., recursive=False)` to create one deliberate graph break exactly at the routed-expert boundary.

When activation checkpointing is enabled, TorchTitan wraps each block in a `CheckpointWrapper` before `apply_compile`. Compiling the wrapper (`Compile(AC(block))`) puts the `GroupedExperts` and FSDP graph breaks inside the checkpoint body, and Dynamo then runs the whole checkpointed MoE block eagerly. The policy therefore compiles the wrapped block instead (`AC(Compile(block))`), keeping the wrapper outermost.

This means:

- computation surrounding the routed experts remains in the larger block-level compiled regions, with or without activation checkpointing;
- `GroupedExperts.forward` itself runs eagerly. Because the disable is `recursive=False`, Dynamo still traces the functions it calls: Primus-Turbo grouped GEMMs stay opaque custom ops, while the surrounding glue (SiLU×mul, casts, group offsets) and the autograd backward are compiled. EP dispatch/combine hooks stay in the compiled block (intentional; see Validation);
- BF16 no longer retains the excessive intermediates introduced by per-submodule compilation;
- FP8 avoids capturing the grouped-expert compute that previously led to NaNs;
- dynamic scalar outputs do not introduce additional breaks beyond the intended boundary.

The wrapper is marked and installed idempotently, and both TorchTitan aliases of `apply_compile` are rebound because DeepSeek imports the function by value. The result is one precision-independent policy rather than separate BF16 and FP8 branches.

## Validation

8x MI355X, `rocm/primus:v26.8` (torch 2.14.0+rocm10.1, Primus-Turbo 0.5.1), TorchTitan v0.2.2:

```bash
./runner/primus-cli direct -- train pretrain \
  --config examples/torchtitan/configs/MI355X/deepseek_v3_16b-{BF16,FP8}-pretrain.yaml \
  --training.steps 50 --debug.seed 42
```

* unit tests: `tests/unit_tests/backends/torchtitan/test_dsv3_v022_perf_patch.py` 10 passed, including a GPU real-compile test that applies TorchTitan's full activation checkpointing to a tiny DeepSeek-V3 and asserts the MoE router is captured in a compiled graph (it fails on the previous wrapper-level compile)
* DeepSeek-V3-16B BF16: 50/50 finite steps, 264.90 GiB peak, 28,776 harmonic-mean tok/s/GPU (steps 11-50)
* DeepSeek-V3-16B FP8: 50/50 finite steps, 268.72 GiB peak, 33,632 harmonic-mean tok/s/GPU (steps 11-50)
* stock v26.7 BF16 reference: 277.76 GiB peak, 30,194 tok/s/GPU
* previous selective-submodule policy: BF16 OOM at local_batch_size 13 on v26.8, and also broke when applied to the v26.7 stack
* numerics: 3-step BF16 run (seed 42, local_batch_size 2) matches `--compile.enable False` to ~1e-4 in loss and grad norm

Rerun at `872bcc91` (with the checkpoint fix, same command and image, a second MI355X node): BF16 28,529 harmonic-mean / 29,089 median tok/s/GPU, 264.9 GiB; FP8 33,865 / 34,134, 268.7 GiB; all steps finite.

Compile boundary: only `GroupedExperts.forward` is eager; EP dispatch/combine hooks stay in the compiled block. Making the whole experts call eager was tested and rejected: BF16 OOM at step 4 (+17.4 GiB) and FP8 -7.4% tok/s/GPU, with matching losses.

### Activation checkpointing

The DeepSeek-671B recipes enable full activation checkpointing with compile. DeepSeek-V3-16B with `--activation_checkpoint.mode full`, 20 steps, seed 42, 8x MI355X (`primus_ci_655d58f_20261026`, torch 2.16), median tok/s/GPU over steps 4-20:

| Precision | Compile `CheckpointWrapper` (before) | Compile inside wrapper (this PR) | Peak HBM (before → this PR) |
|---|---|---|---|
| BF16 | 17,879 | 19,858 (+11%) | 63.8 → 62.5 GiB |
| FP8 | 17,097 | 25,757 (+51%) | 94.4 → 96.3 GiB |

Losses match at step 20 (BF16 2.4670 vs 2.4671, FP8 2.3443 vs 2.3444) and all steps are finite. Dynamo logs confirm the cause: compiling the wrapper traces only `CheckpointWrapper.forward` for MoE layers (graph break on FSDP's `torch._dynamo.disable` hook inside `torch.utils.checkpoint`), while compiling inside the wrapper traces `TransformerBlock.forward`, `MoE.forward`, token dispatch, and the grouped-MM glue.

### gate-workaround-removal-on-runtime-version-detection
_When a downstream patch/monkey-patch exists to work around a bug in an external dependency (compiler, runtime, driver, ISA), and that bug is fixed in a specific upstream version, the removal of the workaround must be gated on a runtime detection of the dependency's version — not removed unconditionally nor left permanently in place. This preserves correctness on both old and new versions of the dependency within the same codebase._

**Findings:**
- The whole-block-compile workaround exists only because specific torch.compile/inductor versions produce NaNs (FP8) and HBM regressions when expert-parallel dispatch/combine and FSDP hooks are captured in one graph. The patch is applied unconditionally (`condition=lambda ctx: _is_deepseek_model(ctx) and _compile_enabled(ctx)`); add a runtime guard that queries the actual installed versions (e.g. `torch.__version__` / `torch.version.hip` or `importlib.metadata.version('torch')`) and skips the patch on versions where the inductor MoE-graph bug is fixed, so fixed-runtime users do not pay the forced graph break.
- The patch module is keyed to TorchTitan v0.2.2 by filename/docstring only ('dsv3_v022_perf_patches', 'TorchTitan v0.2.2 DeepSeek memory patch'), which is a build-time/naming assumption rather than a runtime check. Resolve the installed TorchTitan version at runtime (e.g. `importlib.metadata.version('torchtitan')` or `torchtitan.__version__`) and apply `_apply_unified_compile` only for the version range whose `apply_compile` has the problematic behavior; otherwise defer to upstream `apply_compile`.
- `_apply_unified_compile` replaces `_apply_selective_compile` unconditionally, silently changing behavior for users on runtimes where the old selective boundary was the only safe policy. Keep both strategies and dispatch between them based on the detected runtime version (e.g. `if torch_version < FIXED_IN: _apply_selective_compile else: _apply_unified_compile`), and log which branch was taken with the detected version string.
- The `torch.compiler.disable(GroupedExperts.forward, recursive=False)` graph break is a compensating hack for the inductor EP/FSDP capture bug. Gate the monkey-patch of `moe_module.GroupedExperts.forward` on the same runtime version check so that on a fixed torch/inductor the method is left untouched instead of permanently mutating the class attribute.
- Add unit tests that stub the runtime version query to assert both branches: patch applied (buggy version) and patch skipped (fixed version), rather than only asserting that `_apply_unified_compile` is bound.
- `_apply_selective_compile` remains in the module but is no longer referenced by the patch; either delete it or wire it into the version-gated dispatch so the retained code path is reachable and tested.

## Architecture Concerns

_These findings come from architecture principles distilled from the repo's PR lineage — patterns that caused PRs to be rejected or significantly reworked._

### gate-workaround-removal-on-runtime-version-detection
_When a downstream patch/monkey-patch exists to work around a bug in an external dependency (compiler, runtime, driver, ISA), and that bug is fixed in a specific upstream version, the removal of the workaround must be gated on a runtime detection of the dependency's version — not removed unconditionally nor left permanently in place. This preserves correctness on both old and new versions of the dependency within the same codebase._

**Findings:**
- The patch module is explicitly scoped to TorchTitan v0.2.2 (`dsv3_v022_perf_patches.py`) and its own docstring notes that part of the compensated behavior is 'already handled in the DeepSeek configs on main', yet `patch_whole_block_compile`'s condition is only `_is_deepseek_model(ctx) and _compile_enabled(ctx)`. Add a runtime version probe (e.g. `importlib.metadata.version('torchtitan')` / `torchtitan.__version__`) and gate installation on `version < (0, 2, 3)` (or whatever release carries the upstream fix) so the monkey-patch stops overriding `apply_compile` once users install a TorchTitan that no longer needs it.
- The retained workaround (keeping `GroupedExperts.forward` behind `torch.compiler.disable`) exists because inductor/Dynamo silently produces FP8 NaNs when EP dispatch/combine and FSDP hooks land in one graph. That is a PyTorch-side bug, so the `torch.compiler.disable` wrapping should be conditional on a runtime `torch.__version__` (parsed from the installed runtime, not a build constant or env var) below the release where the capture bug is fixed; otherwise users on fixed PyTorch permanently eat the graph break and its throughput/HBM cost.
