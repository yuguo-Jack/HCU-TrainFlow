# fix(runner): stop MoE hangs on hosts with amdgpu DRM older than 3.64

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1301) · state: closed · merged: True

## Original PR description

## Summary

With the new UTD CI image (`primus_ci_f77fef4_20261022`, ROCm 10.2), every MoE model hangs on its first training step on MI300X hosts that run the ROCm 6.3 amdgpu-dkms driver, while `rocm/primus:v26.8` trains fine on the same node. The run prints nothing after the first attention call until the idle timeout kills it. The GPUs sit at 0% and all ranks are blocked in the kernel in `ioctl(/dev/dri/renderD*, DRM_IOCTL_SYNCOBJ_TIMELINE_WAIT)`. Dense models are not affected.

This PR adds a launch hook that keeps HIP memory pools off virtual-memory mappings, but only on hosts whose driver needs it. It also makes the `expandable_segments` check fail fast instead of hanging.

## Root cause

Native stack of every rank (py-spy and rocgdb):

```
MoE layer -> PrimusTurboDeepEPTokenDispatcher.dispatch_postprocess
  -> primus_turbo moe_permute -> permute_preprocessing (moe_permute_hip.cpp)
    -> get_temp_storage_layout -> hipMallocAsync
      -> HIP memory pool grows via virtual memory -> hsa_amd_vmem_set_access -> hsaKmtMemoryVaMap
        -> DRM_IOCTL_SYNCOBJ_TIMELINE_WAIT  (never returns)
```

- **Runtime/driver mismatch:** since June 2026 ([rocm-systems `b58362f`](https://github.com/ROCm/rocm-systems/commit/b58362f60ff4f0b2b31a32a2a368db6bffdd5883)), ROCm userspace appends timeline fields to every `DRM_AMDGPU_GEM_VA` map and then waits on that timeline point with no timeout. amdgpu added those fields in DRM 3.64 (Linux 6.16; 6.15 reports 3.63 without them). Older drivers accept the larger struct, ignore the fields, and never signal, so the wait blocks forever. tw044 reports DRM 3.59. Upstream issue: [ROCm/rocm-systems#9820](https://github.com/ROCm/rocm-systems/issues/9820). The fix, [#9821](https://github.com/ROCm/rocm-systems/pull/9821), is approved but not merged.
- **Why MoE, and why only now:** the runtime bug is also in v26.8; a standalone `hipMallocAsync` hangs on both images. What changed is primus-turbo. In 0.5.1 (v26.8), `DeepEPTokenDispatcher` let `moe_permute` pick its backend, and BF16 got Triton, which never calls `hipMallocAsync`. In 0.6.1, the dispatcher forces `permute_backend=BackendType.TURBO`, whose workspace comes from `hipMallocAsync`. HIP backs those pools with virtual-memory mappings by default (`HIP_MEM_POOL_USE_VM=1`).

## Changes

- **`runner/helpers/hooks/05_check_amdgpu_vm_timeline.py` (new):** reads the host's amdgpu DRM version with `DRM_IOCTL_VERSION` (stdlib only). Below 3.64 it emits `env.HIP_MEM_POOL_USE_VM=0`, so HIP pools use plain allocations. That is the same path HIP takes on systems without virtual-memory support. A user-set value is kept, with a warning if it isn't `0` on an old driver. Any probe failure skips the check rather than aborting the launch. The hook runs per node, so mixed clusters get the right setting on each host.
- **`runner/helpers/hooks/05_check_expandable_segments.py`:** when `expandable_segments:True` is requested, it makes one expandable allocation in a child process and fails the launch if that doesn't finish within 60 s. PyTorch maps expandable segments through the same driver path directly, so `HIP_MEM_POOL_USE_VM` can't help. On an old driver this turns a silent hang (which `rocm_arg_validation.py` invites by recommending the setting for turbo grouped GEMM) into a clear error. Because it tests a real allocation, it stops failing on its own once ROCm ships the fix.
- **`docs/03-configuration-reference/environment-variables.md`:** documents `HIP_MEM_POOL_USE_VM`.

## Impact

- **DRM 3.64 and newer (e.g. MI355X):** no environment change. The new hook prints one INFO line with the driver version and takes about 0.03 s. The expandable-segments check adds about 1.5 s, and only when the setting is requested.
- **DRM older than 3.64:** `HIP_MEM_POOL_USE_VM=0` for every model on that host. Only HIP stream-ordered pools are affected: Primus Turbo, TE, rocBLAS and RCCL pool allocations. PyTorch's default caching allocator, DeepEP buffers and regular RCCL buffers are unchanged. A value set in a config's `env:` block still wins, because the runtime applies it after the hooks.

## Testing

On MI300X (tw044, amdgpu-dkms 6.10.5, DRM 3.59) with `primus_ci_f77fef4_20261022`, 3 iterations, through `primus-cli`:

| Run | Without fix | With fix |
|---|---|---|
| DeepSeek-V2-Lite BF16 (MoE) | hangs | trains. Iteration 3: 18.1 s, 298.9 TFLOP/s/GPU (v26.8: 19.3 s, 280.5). Losses match v26.8 exactly (1.160263E+01, 1.160258E+01, 1.151913E+01) |
| Qwen3-30B-A3B BF16 (MoE) | hangs (same ioctl) | trains. Iteration 3: 12.0 s, 250.5 TFLOP/s/GPU |
| Llama 3.1 8B BF16 (dense) | trains | trains with the hook active, 491.3 TFLOP/s/GPU |
| `expandable_segments:True` | hangs | launch fails after about 62 s with an explanatory error |

## Follow-ups

- We can remove `05_check_amdgpu_vm_timeline.py` once our images include [rocm-systems#9821](https://github.com/ROCm/rocm-systems/pull/9821). But it's no harm to keep it.
