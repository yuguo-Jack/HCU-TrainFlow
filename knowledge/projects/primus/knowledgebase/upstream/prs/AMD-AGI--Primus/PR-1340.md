# fix(mega_moe): run MegaMoE on Megatron-LM core_v0.19.2 with PrimusTopKRouter

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1340) · state: closed · merged: True

## Original PR description

## Summary

Since the Megatron-LM core_v0.19.2 bump (#1321), `--use_turbo_mega_moe True` fails to build the model, and once that
is fixed MegaMoE silently routes with Megatron's `TopKRouter` instead of `PrimusTopKRouter`.

`PrimusTurboMegaMoELayer`:

- Accepts the `name` argument that `TransformerLayer` now passes (previously a `TypeError`).
- Builds shared experts from the new builder (`functools.partial`) the way `MoELayer` does; a `ModuleSpec` still works.
- Swaps in `PrimusTopKRouter` itself (`mega_moe_router()`, honouring `disable_primus_topk_router`). The router patch
  only swaps it in `MoELayer.__init__`, which MegaMoE replaces; its spec hook does not reach the GPT decoder spec.
  Megatron's router has no `even` force-load-balancing mode and draws random logits instead, so the lm loss at step
  10 was 8.79 instead of 5.56. With that router the run without MegaMoE reaches the same 8.79, so MegaMoE's numerics
  are not the cause.
- Accepts the extra arguments that Megatron-LM main passes (`hash_moe_layer_threshold`, `input_ids`,
  `packed_seq_params`) and forwards them to the router only when they are set. Checked against main's signatures in
  unit tests, not run end to end.

`megatron.moe.primus_topk_router`:

- `primus_topk_router_for()` holds the swap rule, and MegaMoE uses the same helper.
- The spec-builder wrappers also handle the core_v0.19 partial spec.
- The log no longer claims the `MoESubmodules()` default was patched.

`MoELayer` behaviour is unchanged.

Tests: `test_mega_moe.py` is updated for the partial spec, but it needs 8 gfx950 GPUs and never runs in CI (gfx942).
Two new tests that need no GPU (`backends/megatron/patches/test_topk_router_patches.py`,
`backends/megatron/test_mega_moe_layer_build.py`) cover the swap rule, the patch on the core_v0.19 spec, and how
MegaMoE is built and calls its router. On 8x MI355X `test_mega_moe.py` passes unmodified, all 14 tests (below).

## Results

DeepSeek-V3 proxy (EP4, 128 experts, top-8, GBS 64), Primus-Turbo `main` ff4898e4:

- 4x MI455X: `amdprimus/amdprimus:tas-20261019`, `run_deepseek_v3_proxy_mi455x.sh` defaults.
- 4x MI355X: `rocm/primus:v26.8` + FlyDSL 0.3.4.1 + aiter 0.1.24.post1, same arguments except attention on aiter and
  no hipBLASLt tuning file (the FlyDSL MLA kernels and the tuning file are gfx1250-only).

Correctness, 10 iterations, same on both GPUs:

| | lm loss, step 10 | grad norm, step 1 |
| --- | --: | --: |
| `main`, MegaMoE | TypeError | |
| `main` + the first two changes, MegaMoE (`TopKRouter`) | 8.79 | 3.444 |
| `disable_primus_topk_router: true`, with or without MegaMoE | 8.79 | 3.444 |
| this branch, with or without MegaMoE | 5.5630 | 3.810 |

With and without MegaMoE, loss and grad norms agree at every step (bitwise on MI455X, within run-to-run noise on
MI355X), so 8.79 comes from Megatron's random routing, not from MegaMoE. Without MegaMoE this branch matches `main`.

Speed, ms/iter, mean of iterations 21-40 of 40:

| routing | MI455X: without -> with MegaMoE | MI355X: without -> with MegaMoE |
| --- | --: | --: |
| `even` (default) | 1100.3 -> 1000.6 (1.100x) | 2366.0 -> 1660.5 (1.425x) |
| random (`disable_primus_topk_router: true`) | 1115.3 -> 1044.0 (1.068x) | 2394.3\* -> 1687.6 (1.419x) |

`even` puts each token's 8 experts on one rank, MegaMoE's best case. MegaMoE gains more on MI355X because the EP
all-to-all it removes is slower there (629 vs 144 ms/iter left uncovered by compute).

\* Excluding one 36 s stall: under random routing the gfx950 FlyDSL grouped GEMM recompiles for every new per-rank
token count (about 35 s each), a Primus-Turbo issue, not this PR. MegaMoE has no such stalls.

Before the bump (505e55e0), MegaMoE needs none of this and matches AMD-AGI/Primus-Turbo#582 on MI455X (+9.7% TFLOP/s/GPU;
#582: +9.8%).

Tests:

- `test_mega_moe.py` on 8x MI355X (EP8, unmodified): all 14 pass, mxfp8 included. On 4x MI455X (EP4, guards lifted)
  the 4 bf16 cases pass; mxfp8 stops at a FlyDSL link error in Primus-Turbo, outside this PR. bf16 cosine against
  Megatron's `MoELayer` on both: forward >= 0.99998, input gradient >= 0.9994, expert weight gradients >= 0.9988,
  router and shared expert >= 0.99999.
- The two new CPU tests pass (17); on `main` they fail.

<details><summary>Nits and less certain findings (3)</summary>

**1. Router swap rule duplicated with divergent logic and global `get_args()` dependency** (`primus/backends/megatron/core/extensions/mega_moe.py:86`)

`mega_moe_router` copies the `TopKRouter`→`PrimusTopKRouter` rename rule and the `disable_primus_topk_router` check from `patched_moelayer_init` in `topk_router_patches.py`. A future change to the rule (a new router class, the deprecated MoE path) has to be made in both places. Consider sharing one helper. `get_args()` is reached only for routers named `TopKRouter`, and the layer already needed initialised args through `mega_moe_precision()`, so this adds no new construction requirement.

**Who is affected:** Maintainers changing the PrimusTopKRouter swap rule; there is no runtime impact for users of MegaMoE.

_Checked against the code by an independent pass._

**2. Comments wrongly claim the reference `MoELayer` uses `PrimusTopKRouter`** (`tests/unit_tests/megatron/moe/test_mega_moe.py:190-210`)

The retained comment 'mega layer reuses the same router/shared-expert submodules' in `_build_layers` is now only half true. MegaMoE receives the same `submodules`, but `mega_moe_router` turns `TopKRouter` into `PrimusTopKRouter`, while the unpatched reference `MoELayer` keeps plain `TopKRouter`. Parity therefore rests on `_create_args` turning off the PrimusTopKRouter-only branches (`enable_primus_turbo=False`, `router_logit_softcapping=None`, `moe_router_force_load_balancing=False`). The comment could say so. The new docstring and the new test comment are accurate: in a patched run, `MoELayer` still gets `PrimusTopKRouter` on v0.19.

**Who is affected:** Readers and maintainers of the MegaMoE parity test only; there is no runtime effect.

_Checked against the code by an independent pass._

**3. New pure-Python router and shared-expert logic lacks CPU unit tests** (`tests/unit_tests/megatron/moe/test_mega_moe.py:190-210`)

The new `mega_moe_router` and shared-experts dispatch are pure Python, but they are only exercised by `test_mega_moe.py`. That file skips at module level unless the GPU is gfx950, and its parity tests need 8 GPUs. Only the default `TopKRouter` -> `PrimusTopKRouter` swap is asserted. The `disable_primus_topk_router` opt-out, the passthrough for non-`TopKRouter` routers, the `ModuleSpec` vs builder-callable branch not taken by the pinned Megatron, and the `name + '.shared_experts'` propagation are untested. Consider small CPU tests, e.g. `mega_moe_router(TopKRouter) is PrimusTopKRouter` with a stubbed `get_args`.

**Who is affected:** Maintainers only: regressions in the opt-out or the version-dispatch branches would go unnoticed on CI runners without 8 gfx950 GPUs.

_Checked against the code by an independent pass._
