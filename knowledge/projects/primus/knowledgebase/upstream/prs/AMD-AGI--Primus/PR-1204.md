# fix(diffusion): keep Flux sensitive layers out of FP8 and MXFP4

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1204) · state: open · merged: False

## Original PR description

## What this fixes

`sensitive_layers_enabled` is meant to keep the first and last Flux layers
out of the main low-precision format. On `main` it did not, in two ways:

- **TransformerEngine spec, FP8 and MXFP4.** Megatron keeps a first/last
  layer in bf16 by handing it `nullcontext()` from `get_fp8_context` /
  `get_fp4_context` (Primus's MXFP4 version does the same). That cannot switch
  off an autocast that is already active, and `Flux.get_fp8_context()` wrapped
  the whole transformer in one FP8 or FP4 context. So the sensitive layers ran
  quantized like every other layer. The recompute path already entered one
  context per layer, but inside the outer one.
- **Local spec, FP8.** `get_flux_layer_spec` chose a separate backend for the
  sensitive layers only under FP4. Under FP8 the sensitive backend stayed
  `None`, so the first/last layers were built from the Float8 linears.
- **Local spec, explicit backend.** The sensitive backend was chosen only
  while picking a default backend. A backend passed to `get_flux_layer_spec`,
  or to `Flux(backend=...)`, built the sensitive layers with the same
  quantized linears as the rest, under FP8 and MXFP4 alike. The trainer
  always passes `None`, so this affects callers of the API only.

Local-spec MXFP4 with the default backend was already correct and is
unchanged.

## Changes

**Per-layer contexts on the TE spec (`54e0c11`).** When `first_last_layers_bf16`
is set on the TE spec with FP8 or FP4, `Flux.get_fp8_context()` returns
`nullcontext()` and `DiffusionTransformerBlock` enters each layer's own
context in the non-recompute loop. This is what Megatron's `TransformerBlock`
does for every recipe but delayed scaling. Two helpers in
`diffusion_transformer_block.py` carry the logic:
`uses_per_layer_quantization_context(config)` and
`layer_quantization_context(config, layer_number)`.

**Config rejections on the TE spec (`54e0c11`).** `FluxConfig.validate` now
rejects two combinations the TE spec cannot honour:

- `sensitive_layer_precision` other than `bf16`. Megatron can only switch a
  first/last layer's quantization off. On an MXFP4 run, `tw_fp8` also turns
  `fp8` on, and `Flux.get_fp8_context()` prefers FP8, so the whole model ran in
  FP8 instead of MXFP4. The error points to `bf16`, or to
  `transformer_impl: local` with FP4.
- The `stack`, `double_stack`, `single_stack` and `full_dit` compile
  strategies. They call the layers directly and would bypass the per-layer
  contexts. `per_block` and `whole_model` go through the block and are allowed.
  This check applies whenever per-layer contexts are in use, including when
  Megatron's `first_last_layers_bf16` is set directly rather than through
  `sensitive_layers_enabled` (`0c82536`).

**bf16 linears for FP8 sensitive layers on the local spec (`08c4ae2`).** The
FP8 branch of `get_flux_layer_spec` now uses `PrimusTurboLocalSpecProvider`
for the sensitive layers when `sensitive_layer_precision` is `bf16`. With
`tw_fp8` they stay on the Float8 backend.

**Sensitive backend independent of the main backend (`b5663f6`).**
`_sensitive_layer_backend(config)` resolves the sensitive layers' backend from
the config alone, after the main backend is known, so the same mapping applies
whether the main backend was passed in or picked by default:

| run | `sensitive_layer_precision` | sensitive layers |
|---|---|---|
| local, FP4 | `bf16` | `PrimusTurboLocalSpecProvider` |
| local, FP4 | `tw_fp8` | `PrimusTurboFloat8LocalSpecProvider` |
| local, FP8 | `bf16` | `PrimusTurboLocalSpecProvider` |
| local, FP8 | `tw_fp8` | the main backend |
| TE spec | any | the main backend; per-layer contexts keep them in bf16 |

## Points worth a reviewer's attention

**Dropping the outer context has no other effect.** The only work done on
autocast exit is TE's amax reduction in `FP8GlobalStateManager.autocast_exit`,
which runs for delayed scaling only. Delayed scaling is already rejected with
bf16 first/last layers. Primus-Turbo's MXFP4 autocast exits through the same
TE function.

**Runs without sensitive layers are untouched.** They keep the model-level
context, and every compile strategy still builds for them.

## Blast radius

- Only Flux runs with `sensitive_layers_enabled` and FP8 or FP4 change
  behaviour, plus callers that pass their own backend with sensitive layers on
  the local spec.
- Configs that now fail validation, all on the TE spec with FP8 or FP4:
  `sensitive_layer_precision: tw_fp8`, and the four stack compile strategies
  with bf16 first/last layers. Both used to run with the sensitive layers
  quantized anyway.
- The helpers live in `DiffusionTransformerBlock`, which on `main` only Flux
  uses, and they only switch on with `first_last_layers_bf16`.

## Testing

New file `tests/unit_tests/backends/megatron/diffusion/test_flux_sensitive_layers.py`:

- when contexts are entered per layer (TE vs local, FP8 vs MXFP4, with and
  without sensitive layers);
- the model-level context stepping aside for FP8 and MXFP4;
- the block loop's enter/run order with a fake context, for FP8 and MXFP4;
- the config rejections, and the strategies that still build;
- local spec: the first and last layers' qkv linear is `ColumnParallelLinear`,
  the middle ones `Float8ColumnParallelLinear`, and all Float8 without
  sensitive layers;
- local spec with an explicit FP8 or MXFP4 backend: the edge layers are still
  `ColumnParallelLinear` and only the middle ones use the backend's linear;
- GPU, TE spec: a forward pre-hook on every TE linear records whether FP8 is
  enabled in each layer, with and without full recompute. With sensitive
  layers the edge layers see bf16 and the middle ones FP8.

Against `main`, the tests that check the fix fail. The GPU test sees FP8 in
every layer, and the local-spec test sees Float8 linears at the edges. The
guards (no sensitive layers, allowed strategies) pass on both. The
explicit-backend test fails on the PR's previous head and passes now:


The test that sets `first_last_layers_bf16` directly fails in all four

## Limitations

- There is no GPU test with real MXFP4 GEMMs. MXFP4 is covered at the level of
  context selection and the block loop.
- On the local spec, `tw_fp8` sensitive layers use the run's `fp8_recipe`. They
  are tensorwise only if that recipe is tensorwise.

**3. `whole_model` compile may graph-break on per-layer quantization contexts inside compiled forward** (`primus/backends/megatron/core/models/diffusion/flux/model.py:671`)

With `torch_compile_strategy='whole_model'`, returning `nullcontext` moves the per-layer fp8/fp4 context enter/exit, which mutates TE global state, inside the compiled `Flux.forward`. The `get_fp8_context` docstring says the model-level context exists to avoid exactly this, so it risks graph breaks or failures with `torch_compile_fullgraph=True`. The validator allows this combination, but no test calls `torch.compile`, so add a compiled test or reject `whole_model` here.

_An independent check of the code found this probably does not apply: In repo/ and head/, Flux.forward's whole_model/per_block branch wraps self.transformer in `with self.get_fp8_context():`, and _compile_whole_model does `self.forward = torch.compile(self.forward)`, so TE autocast state was already mutated inside the compiled graph before this PR; under per_block the new per-layer context sits in the eager loop outside the compiled layer.forward. The cited docstring line about graph breaks refers to the local spec, which never enters an autocast, and the defaults…_

**4. Local-spec Flux sensitive layers silently stay MXFP4/Float8 when precision is unrecognised** (`primus/backends/megatron/core/models/diffusion/flux/layer_spec.py:494-512`)

`_sensitive_layer_backend` returns None, so `sensitive_layers_*` has no effect on the local spec, in three cases. They are: a `sensitive_layer_precision` other than `bf16`/`tw_fp8` (e.g. the reserved `'mxfp8'` or a typo), no Primus-Turbo local linears, or `tw_fp8` in an FP8 run. The new `_validate_sensitive_layers_on_te_spec` returns early for `transformer_impl='local'`, so nothing warns. The unrecognised-precision case is not new: the base also handled only `tw_fp8`/`bf16` and otherwise left `sensitive_backend` None. The FP8 + `tw_fp8` case is documented in the new docstring, since those layers already run Float8; consider validating `sensitive_layer_precision` in `BaseDiffusionConfig`.

**Origin:** pre-existing

**Who is affected:** Flux runs with `transformer_impl: local` and `sensitive_layers_enabled` whose precision value is neither `bf16` nor `tw_fp8`, or that lack Primus-Turbo local linears.

_Checked against the code by an independent pass._

**5. Recompute and non-recompute runs could diverge on sensitive-layer bf16: context selection duplicated** (`primus/backends/megatron/core/transformer/diffusion_transformer_block.py:38`)

`layer_quantization_context` repeats the fp8/fp4/nullcontext selection that is already inlined in `_checkpointed_forward_with_conditioning` (with its own local `get_fp8_context`/`get_fp4_context` imports). The recompute path could call the helper when `use_inner_quantization_context` is set, so the two copies cannot drift in future. The two paths behave the same today. Delayed scaling with `first_last_layers_bf16` is rejected in `BaseDiffusionConfig`. Fp8-over-fp4 precedence is the same in both copies and is documented in `Flux` as mirroring Megatron.

**Who is affected:** Maintainers editing the quantization-context logic in `DiffusionTransformerBlock`; no runtime behaviour differs today.

_Checked against the code by an independent pass._

**6. Misspelt `torch_compile_strategy` gets misleading stack-runner error: validator allowlist runs before name check** (`primus/backends/megatron/core/models/diffusion/flux/config.py:299`)

`_validate_sensitive_layers_on_te_spec` treats any `transformer_impl` other than `'local'` as TE, and its error messages hardcode `transformer_impl='transformer_engine'`. `uses_per_layer_quantization_context` likewise returns True for any non-local impl. The strategy check is an allowlist that runs in `FluxConfig.__post_init__`, before `Flux.__init__` validates strategy names (and only when compile is enabled). So a misspelt `torch_compile_strategy` with fp8/fp4 and `first_last_layers_bf16` gets the 'stack runners bypass the per-layer quantization contexts' error instead of 'Invalid torch_compile_strategy'. Only error wording is affected (the config is rejected either way), and Flux code paths only distinguish `local` from `transformer_engine`.

**Who is affected:** Users on the TE spec who enable fp8/fp4 with sensitive layers and either misspell `torch_compile_strategy` or set a non-TE, non-local `transformer_impl`.

_Checked against the code by an independent pass._

**7. Fourth hand-copied per-layer FP8/FP4 context helper with a different index convention** (`primus/backends/megatron/core/transformer/diffusion_transformer_block.py:38`)

The new `layer_quantization_context` in `diffusion_transformer_block.py` repeats the per-layer FP8/FP4 context selection already written as `_layer_fp8_context` in `glm5_next_block.py`, `kimi_k3_block.py` and `deepseek_v4_block.py`. The helper takes a 1-based `layer_number` and passes `layer_number - 1`; the block methods take a 0-based `global_idx`. It also checks `fp8` before `fp4`, which is equivalent only because the two cannot both be set. A shared helper with one index convention would keep this selection in one place.

**Who is affected:** Maintainers only; no runtime behaviour differs between the copies.

_Checked against the code by an independent pass._
