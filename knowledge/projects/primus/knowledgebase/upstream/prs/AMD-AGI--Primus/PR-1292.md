# fix(megatron): store the Turbo FP8 weight cache in the op's padded layout

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1292) · state: open · merged: False

## Original PR description

## Summary

With more than one micro-batch, `PrimusTurboGroupedLinear.prepare_weights` quantizes the expert weights to FP8 on the first micro-batch and reuses that cache for the rest of the step. Turbo passes a pre-quantized weight to the kernel as-is. Turbo's tensorwise `grouped_mlp_fp8` and `grouped_gemm_fp8` pad the weight's K dimension (and N for fc2 and the grouped GEMM `b` operand) to 128 when they quantize a bf16 weight themselves. When the shape isn't 128-aligned, the unpadded cache no longer matches the padded activation, and GPT-OSS 120B tensorwise FP8 (hidden 2880) fails with:

```
K mismatch a=2944 b=2880
```

This PR builds the cache in the consuming op's layout, so it is padded once per step and reused by every micro-batch:

- **`_TURBO_FP8_WEIGHT_PAD`** (`primus_turbo.py`): a table keyed by (Turbo op, weight role, scaling granularity). It records the `pad_align_last` / `pad_align_penultimate` arguments Turbo passes to `QuantizedTensor.quantize` for bf16 weights. The comment above it says which Turbo files to keep it in sync with and when to update it.
- **`_turbo_fp8_weight_pad`**: looks up the table and drops any dimension that is already aligned.
- **`_maybe_create_quantized_weight_buffers`**: with pad arguments, it quantizes with them and builds the transposed buffer from the padded tensor. Without them it takes the existing `create_quantized_weight` path unchanged.
- **`prepare_weights(x, turbo_op, weight_role)`**: the fused-MLP path in `experts.py` passes `("grouped_mlp", "fc1")` and `("grouped_mlp", "fc2")`. The non-fused path keeps the default `("grouped_gemm", "b")`.

**Unchanged:**
- **Other recipes:** Turbo doesn't pad MXFP8, blockwise or rowwise weights (the MX quantizer pads its storage itself), so they have no table entries and keep today's cache.
- **Aligned models:** for example DeepSeek-V2-Lite (fc1 `[E, 2816, 2048]`, fc2 `[E, 2048, 1408]`) gets no pad arguments and keeps today's cache.
- **Older Turbo:** on builds whose `quantize` has no pad arguments, the ops don't pad weights either, so nothing changes.
- **One micro-batch:** there's no cache, so nothing changes.

This replaces the workaround of disabling the cache for shapes that aren't 128-aligned. That workaround also turned the cache off for MXFP8, which doesn't need it.

## Results

MI355X, 8 GPUs, `utd/ci:primus_ci_2d288e9_20261020`, GPT-OSS 120B proxy config without recompute, several micro-batches, 10 iterations. All runs include the cross-entropy `overwrite_input` change from #1286 with `TORCH_DIST_USE_NCCL2=0`.

| Run | tokens/s/GPU (harmonic mean) | Peak allocated | Loss at iteration 10 |
|---|---|---|---|
| Tensorwise FP8, main | fails: `K mismatch a=2944 b=2880`\* | | |
| Tensorwise FP8, cache disabled (workaround) | 34,560 | 263.3 GB | 11.57 |
| Tensorwise FP8, this PR | **34,701** | 263.5 GB | 11.57 |
| MXFP8, main | 27,019 | 269.11 GB | 11.5611 |
| MXFP8, this PR | 26,900 | 269.11 GB | 11.5612 |

\* Observed on this image with the image's bundled Primus (recompute config) and with a Primus tree whose `primus_turbo.py` and `experts.py` are identical to main (configs with and without recompute). The failure is independent of recompute.

- **Tensorwise FP8:** trains with the cache on, at the same speed, memory and loss as disabling the cache.
- **MXFP8:** unchanged. Peak memory is identical to the byte, the loss curves match to about 1e-5, and throughput is within run-to-run noise (iterations 3–10 are within 0.5%).

## Testing

- **New tests:** `tests/unit_tests/backends/megatron/test_turbo_fp8_weight_cache_pad.py` covers:
  - **Table lookups:** GPT-OSS fc1 and fc2 and the grouped GEMM `b` operand get pad arguments; DeepSeek-V2-Lite's aligned shapes get none; MXFP8, blockwise and rowwise get none; Turbo builds without pad support get none.
  - **`prepare_weights` with a real `PrimusTurboQuantConfig`:** tensorwise caches have the padded shapes; the MXFP8 cache is byte-identical to `create_quantized_weight`.
  - **GPU check against real Turbo:** for `grouped_mlp_fp8` and `grouped_gemm_fp8`, on aligned and unaligned shapes, the padded cache gives bit-identical output and gradients (`atol=0`) to Turbo quantizing the bf16 weight itself.
- **Updated:** `test_grouped_mlp.py`, for the new `prepare_weights` arguments.
- **Unit test result:** `test_turbo_fp8_weight_cache_pad.py`, `test_grouped_mlp.py` and `test_primus_turbo_wgrad_accum.py` give 42 passed on the image above.
- **Negative check:** a standalone script using main's unpadded cache on an unaligned shape reproduces Turbo's `K mismatch a=256 b=192`.
- **Lint:** `pre-commit run` on the changed files passes.

## Note

`_maybe_create_quantized_weight_buffers`'s fallback for Turbo builds without `create_quantized_weight` reads `quant_config.granularity`, but `PrimusTurboQuantConfig` keeps it on `.data()`. That path is never reached on current Turbo, so this PR leaves it as is. The new padded path uses `quant_config.data()`.
