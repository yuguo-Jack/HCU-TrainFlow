# feat(mega_moe): accept MiniMax-M3's swigluoai (quick_geglu) activation

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1243) · state: closed · merged: True

## Original PR description

## Summary

Two fixes so MiniMax-M3 can train on MegaMoE (`use_turbo_mega_moe`) with the same loss as the DeepEP path.

**1. MegaMoE accepts `swigluoai`.** MegaMoE asserted `activation_func == SiLU`, so MiniMax-M3, whose experts use `swigluoai` (Megatron `quick_geglu` + `glu_linear_offset=1.0` + `activation_func_clamp_value=7.0`), was rejected at model build. The config's gated activation is now mapped onto Primus-Turbo's `GLUActivation` (Primus-Turbo #538) and passed to stage2 of both the bf16 and mxfp8 experts. SiLU keeps the kernel default, so DeepSeek numerics are unchanged.

**2. Force "even" load balancing is applied in the router even when DeepEP is on.** `PrimusTopKRouter` skipped `_force_even_routing` whenever `moe_enable_deepep` was set and left "even" to the DeepEP dispatcher. That dispatcher gathers the round-robin slots' weights from the router's scores, which are zero everywhere except each token's real top-k, so most routed slots got weight 0 and the MoE output collapsed towards the shared expert. MegaMoE replaces the dispatcher, so it instead routed on upstream's random logits. The two paths therefore trained differently under the same config. The router now always does the remap; DeepEP then reads the carried top-k weights at the same slots, and MegaMoE's top-k picks exactly those slots. This also corrects the DeepEP path on its own for any config using `moe_router_force_load_balancing_type: even` (the default).

## Test plan

Container `tasimage/primus:pr-1236` (primus-turbo 0.5.1.dev24, torch 2.12 / ROCm 7.15), 1 x 8 MI355X.

**Router unit test** (`tests/unit_tests/backends/megatron/test_router_force_even_routing.py`): 2 passed; the DeepEP case fails without fix 2.

**MegaMoE parity vs Megatron `MoELayer`** (`tests/unit_tests/megatron/moe/test_mega_moe.py`, EP8, 256 experts, top-8, 4 GA steps): 4 passed.

| mxfp8 | silu | 0.997325 / 0.997544 | 0.997620 |

**End-to-end MiniMax-M3** (`dev/minimax_m3` + these two commits; `minimax_m3_8layer-BF16-pretrain.yaml` as shipped, EP8, force "even" balancing, mock data, 10 iters):

## Performance

Same runs as above (with fix 2, so all three route identically). MiniMax-M3 8-layer proxy (3 dense + 5 MoE/MSA layers, 128 experts, top-4, hidden 6144), 1 node x 8 MI355X, TP1 / PP1 / EP8 / DP8, seq 4096, MBS 1, GBS 64, BF16, full recompute. Numbers are Megatron's running averages over iterations 3-10, rank 7. Iterations 1-2 are excluded: they include one-time kernel JIT compilation.

| MoE path | ms/iter | TFLOP/s/GPU | tokens/s/GPU | speedup | max allocated (GB) |
| --- | --- | --- | --- | --- | --- |
| TEGroupedMLP + DeepEP (baseline) | 2265.1 | 347.0 | 14,467 | 1.00x | 113.7 |
| MegaMoE bf16 | 1787.9 | 439.6 | 18,328 | **1.27x** | 119.4 |
| MegaMoE mxfp8 | 1799.3 | 436.9 | 18,212 | 1.26x | 123.0 |

- MegaMoE bf16 cuts step time by 21% (1.27x tokens/s) with matching loss.
- MegaMoE uses ~5.7 GB more peak memory per GPU than the baseline (bf16).
- mxfp8 experts are no faster than bf16 on this proxy and use ~3.6 GB more peak memory. Likely causes, not profiled: at MBS 1 the expert GEMMs may be too small for fp8 to pay off, and the op keeps an mxfp8 copy of the expert weights.
- The baseline uses DeepEP, sync-free MoE stage 1 and fused permute, as in the shipped config. Force "even" balancing keeps per-expert token counts constant for both paths, so this is a throughput comparison, not a real-routing one.

## Known issue (not addressed here)

With `moe_router_force_load_balancing: false` (real routing) the M3 proxy's non-MegaMoE baseline fails on the first forward with `HIPBLASLT Error: 6` in TE's expert GEMM (TEGroupedMLP with DeepEP or alltoall, and SequentialMLP alike). MegaMoE trains fine in that setting.

- Copilot · comment · 2026-10-10T02:50:03Z · [source](https://github.com/AMD-AGI/Primus/pull/1243#discussion_r4236111974)

File: `primus/backends/megatron/core/transformer/moe/router.py` · line 131

This newly applies the remap to DeepEP even when `moe_expert_capacity_factor` is enabled, but capacity dropping has already zeroed routes before this point. `_force_even_routing` moves the surviving weights to new experts; Primus-Turbo's DeepEP dispatcher only converts zero weights to `-1` and explicitly relies on the caller to enforce capacity, so the remapped destination experts can exceed the configured capacity (for example, when only one route survives per token, the first round-robin slot targets only every `topk`-th expert). Apply capacity dropping after the even remap, or reject the `even` + capacity combination.
