# [WIP] perf(megatron): MegaMoE fusions, Triton router, fewer grad syncs for DSv3 on MI455X

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1358) · state: closed · merged: False

## Original PR description

## Summary

Faster DeepSeek-V3 MoE training on gfx1250 (MI455X). Changes that reach every model take effect on gfx1250 only (`primus.core.utils.gpu_arch.is_gfx1250()`) and keep gradients and updates bit for bit. Everything else is opt-in or limited to the MI455X example. The MegaMoE and fused-norm features use the companion Primus-Turbo PR (AMD-AGI/Primus-Turbo from `lhzhang333:dev/lhz/dsv3_mega_e2e_opt_merge`); with an older Primus-Turbo they fall back.

## Changes

- **MegaMoE**
  - MegaMoE also runs at EP 1 (a single GPU); it used to require EP > 1.
  - Expert wgrads accumulate into `main_grad` (`turbo_mega_moe_wgrad_accum_fusion`).
  - The shared expert runs while the dispatch prologue's host sync waits.
  - The fused residual RMSNorm gets a MoE mode (`PRIMUS_FUSED_RESIDUAL_NORM_MOE`).
  - First-write grad ownership is kept across micro-batches.
- **Router**
  - Opt-in Triton FP32 router GEMMs (`moe_router_triton_gemm`).
  - `spread` forced-balance routing.
  - On gfx1250, the expert bias is applied instead of using Primus-Turbo's fused router, which ignores it.
  - No materialized zero gradients for TE's fused router.
- **Gradients and optimizer (gfx1250)**
  - One pass for the NaN check and the DP scaling.
  - Fatal NaN/Inf checks with one host sync per step (`defer_nan_check`).
  - 1/DP applied at the backward's seed (`prescale_backward_by_dp`).
  - Clipping by contiguous runs, and a Triton param-remainder Adam that applies the clip coefficient itself (`fold_clip_into_adam`).
- **MI455X DeepSeek-V3 example**: new yaml and launcher defaults, README updated.

## Testing

- Unit tests of the changed modules pass on MI455X.
- 4× MI455X against main (Primus db5fe1fd + Primus-Turbo ff4898e4); numerics stay within run-to-run noise:
  - DeepSeek-V3 proxy with MegaMoE: 1004.3 → 917.2 ms/iter (−8.7%).
  - DeepSeek-V3 proxy with the example's defaults: 1101.1 → 1051.1 ms/iter (−4.5%).
  - gpt-oss 20B: unchanged speed, loss and grad norm bitwise identical.
  - Llama 3.1 8B: unchanged.

An older Turbo, which the code itself anticipates, lacks `PrecisionType`/`FLYDSL`, and its `get_grouped_gemm_backend(cls)` takes no precision argument. _An independent check of the code found this probably does not apply: CI's pinned Primus-Turbo d04ffd9 `core/backend.py` defines `PrecisionType`, `BackendType.FLYDSL` and `get_grouped_gemm_backend(cls, precision)`, so the import and call work on the supported Turbo. **13. Forced-balanced routing leaves some experts a slot short, and bad `spread` configs fail at first forward** (`primus/backends/megatron/core/transformer/moe/router.py:37-56`)

The new `force_balanced_slots` docstring says both modes give every expert exactly `num_tokens * topk / num_experts` slots. That holds only when `num_tokens * topk` is a multiple of `num_experts`, and for `spread` only when `num_tokens` is a multiple of `num_experts // topk`; otherwise some experts get one slot fewer (T=6,k=2,E=8 gives 1/2). **18. Fused residual-norm fallback drops the carried MLP output, producing wrong layer activations** (`primus/backends/megatron/core/extensions/fused_residual_rmsnorm.py:566-571`)

If `_do_fused_forward` raises after it has consumed `layer._v2_carry`, the except handler in `_fused_layer_forward` falls back to `_orig_layer_forward` without re-adding the carry. That layer then runs on the previous layer's post-attention residual and loses that layer's MLP output, so its activations are wrong for that call. The gap and the handler are unchanged from the base. This PR widens the carry to `(routed, shared, residual)` and adds the MoE-split `layer.mlp(..., split_shared_output=True)` call as another place that can raise. Re-apply the carry (as `_drain_carry_into_hidden_states` does) before the fallback.

**Origin:** pre-existing

**Who is affected:** Runs with fused residual RMSNorm V2 enabled where the fused forward hits an unexpected runtime exception after consuming a carry (e.g. MegaMoE layers with shared experts in MoE mode).

_Checked against the code by an independent pass._

**19. `--defer_nan_check null` on the CLI enables the deferred NaN check on every architecture** (`primus/backends/megatron/patches/deferred_nan_check_patches.py:60`)

**20. `--turbo_mega_moe_wgrad_accum_fusion null` on the CLI forces main_grad accumulation even with fusion disabled** (`primus/backends/megatron/core/extensions/mega_moe.py:110`)

**1. 🟠 Should fix: Stale deferred clip coefficient can double-clip a later step: this PR never resets pending coefficients**

`defer()` leaves the coefficient on the params, and only `take()`/`apply_eagerly()` clear it. Nothing resets it if a clip is never followed by that optimizer's `step()` (e.g. an exception between clip and step that is caught while training continues). If the next clip then takes the eager path, `apply_eagerly` would also apply the stale coefficient. A skipped step (`found_inf`) returns before clipping, and `_remainder_step` either takes every deferred param or falls back to TE, which calls `apply_eagerly`. Clearing pending coefficients at clip entry would make this robust.

**Who is affected:** Only gfx1250 runs with `fold_clip_into_adam` whose training loop survives an exception raised between gradient clipping and the optimizer step.

_Checked against the code by an independent pass._

Each buffer's own order (router, then shared; fc1, then fc2) is unchanged, so param-gather and grad-reduce chaining are not disturbed. Only with EP=1, where both share one buffer, could the reordering trigger Megatron's 'already dispatched' warning and lose some overlap. It also needs a Primus-Turbo that provides `prefetch_fused_mega_moe_dispatch`, which the CI pin lacks.

**Who is affected:** MegaMoE runs with a shared expert, EP=1, overlap_param_gather on, and a Primus-Turbo that provides the gfx1250 dispatch prefetch.
