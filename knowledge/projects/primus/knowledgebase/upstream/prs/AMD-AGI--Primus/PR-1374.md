# feat(release-docs): document CI images before publishing, one family at a time, install last

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1374) · state: open · merged: False

## Original PR description

## Summary

Reworks the `release-docs-update` skill and `tools/release_docs/` so the release documentation can be written
**before the images are published**, from the CI images that passed QA, and for **one image family at a time**.
It also scripts the bare-metal validation the skill described but never automated, and fixes the install-script
problems that validation found for v26.9.

## What changes

**Documenting CI images under their release tag**
- `probe_image.py --image <CI tag> --publish-as <release tag> [--expect-digest] [--write-dockerfile]`: the snapshot
  and the release notes use the release tag (a retag keeps image ID, build date and size). The release Dockerfile
  is written from the copy baked into the image (`/workspace/.manifest/`); an existing file that differs is never
  overwritten.
- `preflight.py` works from the snapshots: no docker, no published image and no committed Dockerfile needed. It
  takes a `--family` scope and resolves each family's previous build commit.

**One family at a time**
- `--family` for `bump_version.py`, `collect_changes.py` and `release_notes.py render|rotate`.
- `rotate --family` merges one family's image block, delta table and Highlights subsection into an existing
  release section; `--highlights` writes the Highlights, and the previous release's Highlights now move into
  that release's section automatically (this was a hand edit).
- `bump_version.py --scope docs|install`, so the install scripts move in the install phase. A link into the
  other family's page waits for that family's run. Statements about what an image lacks ("ships no Primus") are
  held, because rewriting them for a new release can make them false.

**Phase order and bare-metal validation**
- `SKILL.md` / `reference.md`: install scripts and the bare-metal check come last; Gate A does not block them;
  Gate B before the PR. The install phase follows the release Dockerfile: a check the Dockerfile does not make
  only warns, and divergences are recorded in `install_parity_rules.json`.
- New `validate_baremetal.sh`: fresh install into a base folder (clean environment, free space checked, warnings
  collected), installed packages diffed against the image snapshot, then a few configs trained for a few steps
  with `tools/perf/run_batch.sh` in direct mode. Every cache, `TMPDIR` and source build stays under the base.
- The management email is internal mail: one file per family under the gitignored `output/release-docs/<version>/`;
  `tools/release_docs/announcements/` is removed (the v26.8 email is kept in `reference.md` as the model).

**Install-script fixes found by the bare-metal validation (v26.9 images)**
- `tools/installation/setup.sh`: the flydsl capability check warns instead of stopping the install. The
  Dockerfile makes no such check, and the image ships the same flydsl.
- `tools/installation-jax/setup.sh`: TensorFlow's LLVM archive. The image copies a frozen archive from a private
  registry, and no public copy matches TensorFlow's pinned sha256 (GitHub's gzip varies). `tf_source` now
  re-gzips GitHub's tar the ways `git archive` does and, as a last resort, fetches the pinned LLVM commit, builds
  the archive with `git archive` and re-pins `LLVM_SHA256` in the temporary TensorFlow checkout (logged). The source
  stays pinned by the commit id. Recorded as the documented divergence `LLVM_ARCHIVE`.
- `tools/installation-jax/env.sh`: `SRC_DIR` defaults to `$PRIMUS_JAX_BASE/build`; the TensorFlow build filled a
  123 GB `/tmp`.

## Testing

- `python tools/release_docs/golden_replay.py`: bump, install parity and the SHA check pass, plus a new **rotation
  replay**. The v26.8 release section and Highlights, fed back to `rotate` on the page as it was before v26.8,
  give the shipped page exactly, for both families at once and one family at a time; a re-run changes nothing.
  Breaking the Highlights move makes it fail.
- `release_notes.py check`, `check_links.py`, `install_parity.py --check` and
  `tools/ci/check_version_consistency.py` pass.
- Used end to end for the v26.9 docs (the follow-up PR): the probes ran on the CI images that passed QA, and
  `validate_baremetal.sh` installed and trained the v26.9 PyTorch and JAX stacks on MI300X and MI355X.
