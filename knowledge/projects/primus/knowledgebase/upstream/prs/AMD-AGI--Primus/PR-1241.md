# perf(moe): defer forward and backward gathers to Turbo MXFP4 quantization

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1241) · state: closed · merged: True

## Original PR description

MoE routing currently materializes BF16 expert-ordered activations and output gradients immediately before Turbo MXFP4 quantization. Pass the original source and routing map to the paired quantizer instead, preserving expert output combination and input-gradient reduction.

Requires [Primus-Turbo #546](https://github.com/AMD-AGI/Primus-Turbo/pull/546). CI pins the paired argument-based handoff implementation at `8f19706aa1c656b11a146eb00db32a6c2b46822d`.

Enable through Megatron training arguments declared in `primus_turbo.yaml`:

```yaml
moe_permute_quant_fusion: true
moe_backward_permute_quant_fusion: true
moe_skip_identity_sort: true
```

Both fusion arguments default false. The patch validates TP1/EP1 all-to-all dispatch, fused Turbo MXFP4 experts, and compatible padding/probability settings. Lazy permutation is scoped to the configured dispatcher's MXFP4 execution; generic permutation calls and empty inputs retain eager behavior. The backward choice travels through an explicit Turbo handoff argument. The implementation no longer reads the former fusion, topology, or identity-sort environment variables; downstream launchers must populate training arguments.

Validation:
- 18 CPU configuration/scope tests passed, including incompatible topology, defaults despite legacy environment variables, forward-only/bidirectional selection, and scope restoration after exceptions.
- Current `mlperf-training/dev` recipe passes the new checks with its MI355X TP1/EP1 launcher settings and the new arguments enabled.
- Python syntax, Black/isort formatting, and diff checks passed.
- Paired GPU integration tests were updated for explicit arguments and empty-input fallback, but skipped locally because the isolated test container had no GPU. Fresh paired GPU correctness, profiling, and convergence validation remain pending.

Historical profiles of the original implementation showed 24 forward and 24 backward gather launches removed per step and 11.08–11.18 ms of net target-kernel savings. The estimated 72.48 GB/rank/step is logical avoided intermediate traffic, not measured HBM traffic. Those measurements do not validate the revised PR heads. The measured backward workload is gfx950 GPT-OSS with BF16 activations, 32 experts, top-4 routing, hidden width 2880, and at most 32768 source tokens.

Preserve the existing empty-input fast path here. With fusion enabled, an empty BF16 input and a positive `num_out_tokens` enters the lazy branch, where it launches zero-sized Triton grids and returns a nonempty expanded placeholder; the normal custom op instead returns an empty clone and empty maps before considering `num_out_tokens`. - Copilot · comment · 2026-10-09T17:12:36Z · [source](https://github.com/AMD-AGI/Primus/pull/1241#discussion_r4232666206)

File: `primus/backends/transformer_engine/pytorch/permutation.py` · line 1074

This handoff does not currently preserve eager permutation semantics if the source is modified before the quantizer consumes it. `inp.detach()` shares storage/version with `inp`, while the companion seam registration validates only the placeholder; thus an in-place source update changes the gathered values instead of raising as the new documentation promises (the eager path has already copied them). Store and validate the source version/signature in the paired seam before quantization.

- Copilot · comment · 2026-10-09T17:22:34Z · [source](https://github.com/AMD-AGI/Primus/pull/1241#discussion_r4232746184)

File: `primus/backends/transformer_engine/pytorch/permutation.py` · line None

This eligibility check cannot establish that the next consumer is Turbo, while the Megatron patch installs this function process-wide. Any other matching permutation call under these flags receives the zero-stride placeholder; an ordinary PyTorch consumer never invokes Turbo's lookup helper, so it reads the uninitialized repeated row instead of raising the documented missing-handoff error. Scope the lazy path to an explicit Turbo-owned call site/consumer token, or use a wrapper that rejects ordinary tensor operations until Turbo claims it.

- Copilot · comment · 2026-10-10T19:59:24Z · [source](https://github.com/AMD-AGI/Primus/pull/1241#discussion_r4239014582)

File: `primus/backends/transformer_engine/pytorch/permutation.py` · line 959

The lazy path only verifies `inp.is_cuda`. A direct caller can pass CPU tensors (or differently shaped/device tensors) for `probs` or `routing_map`, still satisfy this predicate, and then hand their host/mismatched pointers to the Triton kernel in `make_row_id_map_with_dest2src`. Unlike the eager custom op, this can fail inside the GPU launch or access invalid probability coordinates. Require both metadata tensors to be 2-D, CUDA, colocated with `inp`, and shape-compatible before selecting the lazy path.
