- `examples/megatron/configs/MI325X/llama3.1_70B-FP8-pretrain.yaml:6`: 🟠 Should fix **[PR Pundit]**
    Expandable segments (PYTORCH_HIP_ALLOC_CONF=expandable_segments:True) are added only to the MI325X llama3.1/3.3 70B BF16 configs. The FP8 siblings (llama3.1_70B-FP8, llama3.3_70B-FP8) were not updated, nor was qwen2.5_72B-BF16, even though they have the identical env block with GPU_MAX_HW_QUEUES: 4. The MI300X/MI355X zaya1 configs were not updated either. On MI300X (same gfx942), #1307 set the variable on all four llama 70B configs, BF16 and FP8. docs/02-user-guide/megatron-lm-training.md:41 specifically names 'Llama 70B FP8 on 8 GPUs' on MI300X/MI325X as the fragmentation-OOM case, so the variants that most need it are left out. As a result, BF16 and FP8 runs of the same model use different allocators and go through different preflight checks, which makes memory/perf comparisons misleading. Either update the FP8 configs too, or explain why only these four configs need the setting.
    **Evidence (verified by running it):** Ran sed on all MI325X *70B* configs: only the BF16 files have the variable. grep shows the MI300X llama3.1/3.3 70B BF16 and FP8 configs all set PYTORCH_HIP_ALLOC_CONF.
- `examples/megatron/configs/MI325X/zaya1_8B-BF16-pretrain.yaml:21-27`: 🟠 Should fix **[PR Pundit]**
    The micro_batch_size tuning comments are stale. The BF16 comment says 216 is 'the largest multiple of 8 that completes on MI325X with rocm/primus:v26.8', peaking at 249/256 GB, and that 224 OOMs. The FP8 comment (around line 26-33) says the same for 184, peaking at 245 GB, with 192 OOM. These numbers were measured on v26.8 without expandable segments. This PR targets v26.9 and switches the allocator to expandable segments, which changes peak reserved memory and fragmentation. Either the batch sizes were not re-tuned (a larger MBS may now fit), or they were re-tuned and the comments were not updated. Re-measure and update the numbers, or state the conditions under which they were measured. The model-support-matrix doc repeats the v26.8 claim.
    **Evidence (verified by running it):** Read the head file. The comment is unchanged by the diff, and grep shows 'v26.8' is still present. The PR title says v26.9.
- `primus/core/runtime/train_runtime.py:363-366`: 🔵 Minor **[PR Pundit]**
    TrainRuntime._apply_config_env writes env: values into os.environ unconditionally. Baking PYTORCH_HIP_ALLOC_CONF into these configs therefore silently replaces any allocator config the user or image already exported, instead of merging with it. Lost settings include max_split_size_mb, garbage_collection_threshold, and expandable_segments:False used as an old-driver workaround. The only signal is a '[Primus:Runtime] env override' print, and the only way to keep one's own value is to edit the yaml.
    **Evidence:** Read primus/core/runtime/train_runtime.py:319-379: os.environ[str(key)] = resolved, with no check for an existing value.
- `docs/02-user-guide/megatron-lm-training.md:41`: 🔵 Minor **[PR Pundit]**
    The user guide tells MI325X users to pass PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True manually via --env, container options, or runner/.primus.yaml, and says a host export has no effect. The configs now set PYTORCH_HIP_ALLOC_CONF themselves through the yaml env: block, and the docs were not updated. A user following the docs ends up setting two different allocator variables. Exporting PYTORCH_CUDA_ALLOC_CONF=expandable_segments:False to opt out would conflict with the HIP variable baked into the config, and the hook would report an error. Docs and configs should agree on one variable and mechanism.
    **Evidence:** grep expandable in docs/ shows the PYTORCH_CUDA_ALLOC_CONF recommendation. The hook error message mentions another env var overriding with False.

File: `examples/megatron/configs/MI325X/llama3.1_70B-BF16-pretrain.yaml` · line 10

🟠 Should fix **[PR Pundit]**

Setting expandable_segments:True triggers runner hook 05_check_expandable_segments.py (added in #1301/#1302) on every run. The hook exits 1 and aborts the launch in two cases: when expandable segments are not effective (e.g. on an older image such as v26.8, or a PyTorch build without ROCm support), or when the probe allocation hangs/times out on hosts with amdgpu DRM < 3.64 under ROCm 10.x (ROCm/rocm-systems#9820). These four recipes previously ran on such MI325X hosts; zaya1 is the MoE case that commit targeted. Users cannot opt out from outside the yaml: _apply_config_env sets os.environ unconditionally and the hook does os.environ.update(_config_env(argv)), so exporting expandable_segments:False does not help. The configs are not version-gated. Neither the PR nor the configs document the host driver/image requirement, or that users can opt out by removing the line (and lowering micro_batch_size for zaya1).

**Evidence (verified by running it):** Loaded the hook module from head/ and called _config_env plus _requests_expandable_segments on each changed config: all return True, so the hook's GPU checks and probe run. Read the hook's code paths that return 1.
