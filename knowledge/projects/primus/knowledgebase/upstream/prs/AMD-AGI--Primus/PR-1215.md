# fix(megatron): disable Triton recompiles for zebra Llama KDA 1B

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1215) · state: closed · merged: True

## Original PR description

## Summary

Zebra Llama KDA 1B BF16 NaNs on MI355X at iteration 1. Megatron raises on a NaN local grad norm in bucket #0 before the data-parallel reduce-scatter. The recipe is unchanged: micro-batch 9, global batch 72, sequence 8192, Transformer Engine spec, Triton forward and backward, gate fused in the kernel.

Two Triton patches recompile that backward, and training completes again when both are off:

- `megatron.fla.kda_safe_autotune` drops `num_stages > 2` from the FLA KDA intra-chunk autotune space. On Triton 3.6 / ROCm 7.2 the `num_stages=4` candidates fail to compile.
- `triton.buffer_store_war` recompiles any kernel whose AMDGCN has a `buffer_store_dwordx4` VGPR hazard, using `AMDGCN_USE_BUFFER_OPS=0`.

Which of the two recompiles produces the NaN was not isolated. Both were disabled together, and that run trained.

## Fix

Both patches stay on by default. This recipe turns them off through the top-level `env:` block, which Primus applies before either patch runs:

- `PRIMUS_FLA_KDA_SAFE_AUTOTUNE=0`
- `PRIMUS_TRITON_BUFFER_STORE_WAR=0`

`0`, `false`, `no`, and `off` skip the patch and log that it was disabled. Other configs keep the patches.

## Test plan

- [x] `zebra_llama_kda_1B_BF16-pretrain.yaml` on 8x MI355X trains past iteration 1 with no NaN grad norm
- [ ] Confirm the log contains `disabled by PRIMUS_FLA_KDA_SAFE_AUTOTUNE` and `disabled by PRIMUS_TRITON_BUFFER_STORE_WAR`
- [ ] Spot-check another ROCm recipe still applies both patches when these variables are unset

## Architecture Concerns

_These findings come from architecture principles distilled from the repo's PR lineage — patterns that caused PRs to be rejected or significantly reworked._

### gate-workaround-removal-on-runtime-version-detection
_When a downstream patch/monkey-patch exists to work around a bug in an external dependency (compiler, runtime, driver, ISA), and that bug is fixed in a specific upstream version, the removal of the workaround must be gated on a runtime detection of the dependency's version — not removed unconditionally nor left permanently in place. This preserves correctness on both old and new versions of the dependency within the same codebase._

**Findings:**
- `patch_triton_buffer_store_war` is a workaround for a Triton/LLVM buffer-store codegen bug, but the new kill-switch is purely an env var (`PRIMUS_TRITON_BUFFER_STORE_WAR`). Add a runtime capability/version query — e.g. read the installed `triton.__version__` (and/or the ROCm/LLVM backend version via `torch.version.hip`) and auto-skip the patch only when the version is >= the release that fixed the store WAR bug — instead of relying on the operator to set an env var.
- Same for `_should_narrow_kda_autotune`: `PRIMUS_FLA_KDA_SAFE_AUTOTUNE` is an env override, not version detection. Query the installed `fla` package version (and ROCm version) at runtime and narrow the autotune space only on versions where the bad configs are known to miscompile; let the env var act as a manual override of that decision, not as the sole gate.
- Document and encode the exact upstream fix thresholds in code (e.g. `_TRITON_BUFOPS_FIXED_IN = (3, 4, 0)`, `_FLA_KDA_FIXED_IN = (...)`) and compare them against the runtime-resolved versions in the patch-dispatch predicate, so the workaround self-disables on fixed stacks and self-enables on buggy ones without manual config edits.
- `examples/megatron/configs/MI355X/zebra_llama_kda_1B_BF16-pretrain.yaml` disables both workarounds unconditionally for every user of that recipe. Anyone running this config on an older Triton/fla build will silently hit the original store-WAR / autotune bug. Either drop the env block once runtime version gating exists, or have the loader emit a hard warning/error when the workaround is force-disabled on a runtime version known to be buggy.
- The YAML comment states the KDA backward NaNs on MI355X when the kernels are recompiled — capture that as a runtime condition (GPU arch via `torch.cuda.get_device_properties().gcnArchName` combined with the compiler/fla version) in the patch predicate rather than baking the disable into one hardware-specific config file; otherwise the same NaN path reappears in every other MI355X recipe.
