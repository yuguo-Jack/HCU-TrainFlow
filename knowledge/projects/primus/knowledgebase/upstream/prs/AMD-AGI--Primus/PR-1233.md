# feat(torchtitan): add opt-in Triton fused AdamW with a device-sized grid

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1233) · state: open · merged: False

## Original PR description

## Summary

Adds an opt-in Triton AdamW for the TorchTitan backend (`optimizer.use_triton_fused_adam: true`).

TorchTitan builds `torch.optim.AdamW(fused=True)`, whose ATen `multi_tensor_apply` launches are capped at 320 workgroups. AdamW is a 4-read / 3-write streaming kernel, so its throughput is set by how many memory requests are in flight; a fixed 320-workgroup grid cannot hide HBM latency on MI455X (gfx1250, 256 CUs) and is not optimal on MI355X (gfx950) either.

`TritonFusedAdamW` subclasses `torch.optim.AdamW` and runs device-sized Triton kernels instead:

- Large tensors get one grid-stride launch each with direct addressing and an architecture-dependent grid, capped by the tensor size: 2 workgroups per CU on gfx950 / gfx942 (512 on MI355X), 16 on gfx1250 (4096 on MI455X). These come from grid sweeps on Llama 3.1 8B shapes; gfx942 is assumed to match gfx950 and has not been measured.
- Tensors below 4M elements (16-byte aligned) are batched into one launch per dtype combination through a cached chunk -> tensor table. Batches are launched while the host is still walking the parameters, per-parameter kernel inputs are cached across steps, and step counts are tracked on the host, so many-small-tensor models are not bound by host overhead.

## Changes

- `primus/core/kernels/triton_adam.py`: backend-neutral per-tensor and batched Adam/AdamW kernels (FP32 math, any float param/grad dtype) and the per-architecture default grid (`workgroups_per_cu`).
- `primus/backends/torchtitan/components/optimizer/triton_adamw.py`: `TritonFusedAdamW`.
  - Keeps `torch.optim.AdamW`'s state layout (per-parameter CPU `step`, `exp_avg`, `exp_avg_sq`), so DCP checkpoints are interchangeable with the stock optimizer. Loading a checkpoint from `fused=True` (device `step`) moves `step` back to the host.
  - Step counts are kept on the host (one per group plus the parameters that differ, e.g. missing gradients) and written into the `step` tensors by `state_dict()` and before the stock or functional torch step runs; `load_state_dict()` rebuilds them. Reading `optimizer.state` directly between steps therefore shows stale `step` values.
  - FSDP2 `DTensor` parameters are updated through their local shards.
  - Group options the kernels do not implement (amsgrad, maximize, capturable, differentiable, tensor hyper-parameters) and `closure` use the stock step; individual tensors the kernels cannot take are updated by torch's functional Adam in the same step.
- `primus/backends/torchtitan/patches/triton_fused_adamw_patches.py`: wraps `OptimizersContainer.__init__` (train specs capture `build_optimizers` at registration time) to build `TritonFusedAdamW` for `AdamW`. Enabled by `optimizer.use_triton_fused_adam` (default `false`, documented in `torchtitan-parameters.md`).
- `benchmark/kernel/optimizer/bench_fused_adamw.py`: Llama 3.1 8B shapes, `--split` to emulate many small tensors; torch fused vs TE `FusedAdam` vs Triton over a grid sweep. Documented in `benchmark/kernel/README.md`.

The kernels module is shared on purpose: the Megatron variant in #1190 is stacked on this PR and uses it.

## Testing

All MI455X results below come from one MI455X A0 sample (gfx1250, `REV_ID 0x00`, `amdprimus/amdprimus:gfx1250-20260910`). Its measured copy bandwidth is about 4.6-6.6 TB/s, so absolute step times will differ on B0; the comparisons are within the same machine.

- `pytest tests/unit_tests/core/kernels tests/unit_tests/backends/torchtitan/test_triton_fused_adamw.py tests/unit_tests/backends/torchtitan/test_config_utils.py` on MI455X at `aac6cd49`: all pass (matches `torch.optim.AdamW(fused=True)` in FP32 / BF16, state-dict round trips in both directions, step counts with missing gradients and a `closure` step, DCP `get_optimizer_state_dict` / `set_optimizer_state_dict` round trip, single-rank DTensor shards, group and per-tensor fallbacks, patch wiring, JobConfig flag, per-architecture grid).
- Microbenchmark on MI455X at `aac6cd49` (FP32 states, step time, median of 10; runs agree within 2%; default grid 4096):

  | Shapes | torch fused (TorchTitan default) | TE `FusedAdam` | Triton (this PR) |
  |---|---|---|---|
  | Llama 3.1 8B, 32 layers (291 tensors) | 24.78 ms | 21.15 ms | 17.62 ms (1.41x) |
  | 8 layers, `--split 64` (3729 tensors) | 14.63 ms | 18.49 ms | 10.03 ms (1.46x) |

- End-to-end TorchTitan Llama 3.1 8B (`8B_flex`, 1 GPU, `local_batch_size` 4, `seq_len` 8192, compile on, mock data, 20 steps; Primus-Turbo converters off so the optimizer is the only difference), flag off vs on on MI455X:
  - The patch is applied (`OptimizersContainer` builds `TritonFusedAdamW`) and both runs complete.
  - Loss matches at step 1, within 1.5e-6 at step 2 and ~1e-5 through step 6, then the runs drift apart as expected for a chaotic early-training phase (final loss 4.04 vs 3.90, same trend).
  - Throughput 3005 vs 3015 tokens/s: on this machine a step takes ~11 s, so the optimizer saving is below run-to-run noise.
- MI355X (gfx950, `rocm/primus:v26.7`, TE 2.17 with the custom Adam kernel), measured before the per-architecture grid change (default was 4096); medians of 3:
  - Grid sweep on Llama 3.1 8B (291 tensors): 256 = 39.12 ms, 512 = 39.68 / 39.84 ms, 768 = 39.94-40.52 ms, 1024-4096 = 41.7-42.8 ms. The new gfx950 default is 512.

    | Shapes | torch fused | TE `FusedAdam` | Triton, grid 512 (new default) | Triton, grid 4096 (old default) |
    |---|---|---|---|---|
    | Llama 3.1 8B, 32 layers (291 tensors) | 52.83 ms | 40.36 ms | 39.84 ms (1.33x) | 41.82 ms (1.26x) |
    | 8 layers, `--split 64` (3729 tensors) | 23.48 ms | 23.03 ms | 17.78 ms (1.32x) | 17.87 ms (1.31x) |

  - Unit tests: 18 passed.
  - End-to-end TorchTitan Llama 3.1 8B (1 GPU, `local_batch_size` 4, `seq_len` 8192, 20 steps, Primus-Turbo on, `debug.seed=42`): 21,490 -> 21,634 tokens/s (+0.67%); loss identical at step 1 and within 3e-4 through step 6 (final 2.435 vs 2.463). The patch log line is present.
- MI355X re-run at `33a508d7` (before the host-side step counts) (per-architecture grid; `default_grid_size` returns 512 on gfx950), medians of 3: Llama 3.1 8B torch fused 53.01 ms -> Triton 40.38 ms (1.31x, TE 39.89 ms); 3729 tensors 23.51 -> 17.54 ms (1.34x, TE 22.80 ms). Unit tests pass.
- MI355X at `aac6cd49`, medians of 3: unit tests pass; Llama 3.1 8B torch fused 52.89 ms -> Triton 39.64 ms (1.33x, TE 40.31 ms); 3729 tensors 23.93 -> 17.85 ms (1.34x, TE 23.03 ms). All within 2% of `33a508d7`: on MI355X the step is GPU-bound, so the host-side step counts do not change it.
