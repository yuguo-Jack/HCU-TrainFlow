# fix(glm5_next): run packed KDA and DSA under context parallel

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1265) · state: closed · merged: True

## Original PR description

## Summary

GLM-5.3-Flash KDA and DSA rejected packed sequences, so `--qkv-format thd --allgather-cp` could not run with context parallel. This adds that path and keeps FLA's context-parallel kernels inside MI300X's 64 KB of LDS.

- **KDA** (`kimi_delta_attention.py`). With context parallel off, each packed sample runs as its own unpadded forward. With context parallel on, the layer builds an FLA `cp_context` from the global `cu_seqlens` and passes it to the causal conv and `chunk_kda`. Packed sequences force the FLA conv so the conv state resets at each sample boundary. The local shard length times the context-parallel size must equal the global length, which is the contiguous allgather layout, not zigzag.
- **DSA** (`dsa_attention.py`). Same split. Context parallel off walks the packed samples one by one. Context parallel on allgathers the indexer inputs without gradients and the KV latent with gradients, runs the kpool indexer on the full sequence, then slices the indices back to the local shard. Sparse MLA reads the gathered latent rather than the local shard.
- **FLA shared memory** (`kda_kernels/_fla/__init__.py`). `fla_chunk_kda` forwards `cu_seqlens` and `cp_context`. Before the context-parallel kernels launch, Triton autotune configs are clamped to `num_stages=1` and `BV=32`. The unclamped configs request 80 KB of shared memory; gfx942 provides 64 KB, and the first full-model step died in `merge_fwd_bwd_kernel` with `OutOfResources`.

`tests/unit_tests/backends/megatron/glm5_next/run_one_layer_thd_cp.py` compares one packed layer at CP=1 against the contiguous CP=2 shard for both DSA and KDA.

## Test plan

- [x] One-layer packed THD: DSA and KDA CP=2 match CP=1 on tiny shapes (`run_one_layer_thd_cp.py`, CP=2 vs a CP=1 reference).
- [x] Full GLM-5.3-Flash trainer on 64 MI300X GPUs, TP=1, PP=8, CP=8, EP=8 folded onto the same 8 GPUs per stage, `--qkv-format thd --allgather-cp`, global packed budget 32768. HF load from `hf-iter-281`, SFT on the verified HIP-kernel set. The FLA clamp logged on the context-parallel ranks, and 258 optimizer steps completed (`outcome=NORMAL`) with finite loss and grad norm. Step 0 loss 0.119, grad norm 0.679. No `OutOfResources` after the clamp.
- [ ] Reviewer: re-run the one-layer script at CP=1 and CP=2 for `--kind dsa` and `--kind kda` on a MI300X node.

### issue_comments

- yuankaichen-amd · comment · 2026-10-18T18:08:08Z · [source](https://github.com/AMD-AGI/Primus/pull/1265#issuecomment-6253326504)

Pushed a follow-up commit: the FLA CP LDS clamp now queries the device's actual shared memory (`triton.runtime.driver.active.utils.get_device_properties(device)["max_shared_mem"]`) instead of assuming 64 KB everywhere.

- gfx942 (MI300X, 64 KB LDS): unchanged behavior, still narrows to the safe `num_stages<=1, BV<=32` configs. Verified against a live container: `max_shared_mem=65536`, clamp applies, same configs as before (`[(1, {'BV': 32})]`, `[(1, {})]`, `[(1, {}), (1, {})]`).
- gfx950 (MI350X/MI355X, 160 KB LDS): the clamp becomes a no-op and FLA's own, richer default autotune space is left untouched, since 160 KB comfortably fits the 80 KB worst case. Verified by simulating a 160 KB budget on the same container: config counts stayed at FLA's defaults (12/6/2) instead of being narrowed to 1/1/2.

No MI350X/MI355X hardware was available to confirm the real `max_shared_mem` value triton reports there, so that number is from the existing `PRIMUS_DSA_BWD_*` comments in this codebase, not directly measured in this PR. Flagging for a reviewer with gfx950 access to double check.
