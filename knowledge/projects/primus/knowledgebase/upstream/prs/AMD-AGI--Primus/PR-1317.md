# feat(specforge): take online capture settings from the recipe

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1317) · state: closed · merged: True

## Original PR description

## Summary
- Online SGLang capture reads `model.draft_model_config` and `model.target_model_path` from the SpecForge Hydra file, or from a Hydra override, instead of always using the Qwen3.5-4B draft layer ids.
- A relative `draft_model_config` is resolved against the SpecForge checkout. An explicit `capture_layer_ids` / `CAPTURE_LAYER_IDS` value still wins. A Hydra file that exists but cannot be parsed logs a warning instead of failing silently.
- `--skip-tokenizer-init` stays on by default and can be turned off with `specforge_online.skip_tokenizer_init` or `SKIP_TOKENIZER_INIT`.

## Test plan
- [x] Ran the online launch helpers locally (the module is `pytest.mark.skip` in CI): Qwen layer ids still win when the recipe has no draft file, an explicit layer override still wins, an absolute recipe draft and `target_model_path` are picked up, a draft path relative to the SpecForge checkout is picked up, and `skip_tokenizer_init: false` removes `--skip-tokenizer-init`.

🟠 Should fix **[PR Pundit]**

_model_field_from_specforge_config checks a relative specforge_config with Path(raw).is_file() against Primus's working directory only. resolve_specforge_root also returns None for relative configs. SpecForge itself resolves paths after chdir into its checkout, and the sibling draft helper does resolve against root. So a relative specforge_config (e.g. configs/muse.yaml or configs/m.yaml with specforge_root set) is silently ignored, and whether it is read depends on the launch directory. target_model_path then falls back to TARGET_MODEL or the default, and capture layer ids fall back to the Qwen example, with no warning. That is exactly the mis-capture the PR is meant to fix. Relative config paths should also be resolved against resolve_specforge_root(params).

**Evidence (verified by running it):** Probe on head: params with specforge_root=<root> and specforge_config='configs/muse.yaml' (draft ids [1,16,30], target /models/muse). online_settings returned capture_layer_ids (1,8,15,22,29) and target_model_path 'Qwen/Qwen3.5-4B'. With the absolute path it returned (1,16,30).

🟠 Should fix **[PR Pundit]**

_existing_draft_config tries a relative draft_model_config against the process cwd (Path(raw).is_file()) before specforge_root / raw. This contradicts its own docstring ('Relative paths are resolved against the SpecForge checkout'). It also contradicts SpecForge's behaviour, since SpecForge runs with cwd=specforge root, and stack_preflight, which resolves relative drafts against root only. A same-named or stale file under the launch cwd (e.g. a Primus checkout's configs/<name>.json) shadows the real draft. SGLang then captures the wrong aux layers while the trainer uses the root-relative draft. Relative paths should be resolved against root first, or only against root.

**Evidence (verified by running it):** Probe: created /tmp/shadow/configs/muse.json with ids [9,9] and changed into /tmp/shadow. online_settings returned (9,9) instead of the root draft's (1,16,30).

File: `primus/backends/specforge/online_launch.py` · line 104

🟠 Should fix **[PR Pundit]**

The Hydra YAML is read with plain yaml.safe_load of a single file, so Hydra/OmegaConf semantics are lost. `defaults:` composition and config groups are ignored: a model.* value (draft_model_config / target_model_path) inherited from a base config is missed, with a silent fallback to the Qwen target and layer ids. specforge_overrides are also not merged for target. `${...}` interpolations are returned verbatim, so e.g. '${oc.env:TM,/x}' becomes target_model_path and is passed to `sglang --model-path` and to the model.target_model_path= override, which SpecForge would otherwise resolve itself. An interpolated draft path also goes unresolved and falls back to the Qwen ids. Non-scalar values are str()'d. The broad `except Exception` downgrades malformed recipes to a warning plus silent fallback. The docstring does not say composition is unsupported, so only a flat single-file model section is honoured. Fix: skip or reject values containing '${' and dict/list values, or compose with OmegaConf.

**Evidence (verified by running it):** Probe: child.yaml with `defaults: [base]` gives Qwen ids. interp.yaml with draft_model_config: ${paths.d} gives Qwen ids, and its target_model_path came back as the literal '${oc.env:TM,/x}'.

🔵 Minor **[PR Pundit]**

The Hydra YAML is read and parsed from disk separately for draft_model_config and target_model_path on every online_settings call. online_settings is called repeatedly: by the supervisor, in preflight and in run_online.
