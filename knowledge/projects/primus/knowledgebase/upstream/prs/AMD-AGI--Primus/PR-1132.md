## Original PR description

# WAN 2.1 / 2.2 video DiT training on Megatron-Core

## What this adds

End-to-end training support for the WAN video diffusion transformer on Megatron-Core:
- the model, built on `TransformerLayer` and `DiffusionTransformerBlock` as Flux is;
- the pre-encoded data path;
- the trainer and flow-matching scheduler;
- three runnable example configs;
- an HF→Primus checkpoint conversion CLI.

Along the way it fixes defects outside WAN that WAN surfaced. It also adds unit coverage for the invariants the new code depends on, including a forward-parity check against diffusers.

**Validation:**
- WAN 2.1 T2V 1.3B was trained on a pre-encoded PusaV1 dataset in three precision arms: TransformerEngine, Primus-Turbo local bf16, and MXFP4. The arms differ only in their precision block, so they can be diffed against each other.
- FP8 on the local spec was checked with short runs. Tensorwise scaling under Megatron-FSDP and delayed scaling under DDP both train without NaNs, and the run log confirms that the Float8 linears were built.
- The move to `TransformerLayer` (second review round) was checked by training pre- and post-migration code from the same pretrained weights, in bf16 and MXFP4. The first-step loss is identical and the curves stay within run-to-run noise.
- The MXFP4 recipe now runs the forward GEMMs in bf16 and the backward in MXFP4 (third review round). From the same pretrained weights its first-step loss is identical to the bf16 recipe's, and its gradients differ, as an MXFP4 backward should. With `deterministic_mode` on, two runs of each spec give identical losses and gradient norms.

## Points worth a reviewer's attention

**The DiT is built on `TransformerLayer` and `DiffusionTransformerBlock` (`4da7b2b`).**
- Each WAN block is a `WanLayer(TransformerLayer)`. It holds WAN's AdaLN modulation and `scale_shift_table`, builds `self_attention`, `cross_attention` and `mlp` from `TransformerLayerSubmodules`, and returns `(hidden_states, context)`, as Flux's `MMDiTLayer` does.
- `get_wan_layer_spec` returns `TransformerBlockSubmodules`, so backend resolution and sensitive-layer precision use the same per-layer-spec mechanism as Flux.
- **Recompute:** it follows Megatron's `recompute_method`, `recompute_num_layers` and `recompute_layer_ids`. A test checks that recompute changes neither output nor gradients, and that the configured number of layers is actually checkpointed, in bf16 and, on gfx950, under MXFP4 through `te_checkpoint`. `WanConfig` rejects `recompute_granularity: selective`, which the WAN layer doesn't implement, and a uniform `recompute_num_layers` that doesn't divide the depth (`9f92c3d`).
- **FSDP sharding:** Megatron-FSDP's default unit list (`[TransformerLayer]`) matches the blocks by real inheritance. This replaces the earlier virtual-subclass registration.
- **Key layout:** block keys are `decoder.layers.N.{self_attention, cross_attention, mlp, pre_cross_attn_layernorm, scale_shift_table}`. The block is named `decoder`, as in Megatron-Bridge's WAN, because `transformer.` / `transformer_2.` already prefix the backbones in the diffusers layout.
- **Converter:** it maps diffusers `blocks.N` onto this layout from one rename table and one fused-group table.

**RoPE on the TransformerEngine path (`820d645`).**
- The problem: at the pinned Megatron-LM, the fused thd rotary branch does not forward `rotary_interleaved`. TE therefore rotated WAN's interleaved angle layout as if it were half-split.
- The fix: q and k are now rotated in SBHD before packing, on both paths. The SBHD fused kernel honours `rotary_interleaved`, so the TE path keeps TE's fused rotary.
- The test: it compares every rotary call on the real 7×30×52 token grid against an exact pairwise rotation.

**One YAML key drives two backends' attention kernel selection (`a0c5551`, `164a21d`).**
- WAN's sequence length is not divisible by 64. That puts both Primus-Turbo and TE's ROCm CK backend in the same corner: the kernel families that serve non-padded shapes accumulate dQ through atomics. With the fp32 atomic accumulator off there is no ASM backward to dispatch to, and both fall through to `ck_tile` without reporting it.
- The `attn_atomic_fp32` key (default on) sets `PRIMUS_TURBO_ATTN_V3_ATOMIC_FP32` and `NVTE_CK_IS_V3_ATOMIC_FP32` together. It also forces `NVTE_CK_USES_BWD_V3` on, so a launcher cannot quietly undo the atomics.
- The opt-out is the YAML key rather than the environment variable, on purpose. `base_env.sh` exports `${PRIMUS_TURBO_ATTN_V3_ATOMIC_FP32:-0}` and the release image pins `NVTE_CK_IS_V3_ATOMIC_FP32=0`, so every launched run arrives with both already at `0`. Reading them back could not tell a deliberate choice from that blanket default.
- Atomic accumulation is order-dependent whether the accumulator is fp32 or bf16, so `attn_atomic_fp32` doesn't make the backward deterministic (`9f92c3d`).
- **For a deterministic run**, set `deterministic_mode: true` and `use_flash_attn: false` in the YAML and export `PRIMUS_DETERMINISTIC=1`, which sets the environment Megatron's and Primus's checks require. `deterministic_mode` reaches `PrimusTurboLocalAttention` on the dense and the thd path, and TE's attention through `WanConfig`.
  - On the local spec, aiter's deterministic backward allocates a dQ workspace that grows with the square of the sequence length, so it needs a small micro-batch at WAN's sequence lengths.

**The forward step runs without autocast (`918383b`).**
- The batch is already cast to the compute dtype and the parameters are held at `params_dtype`, so autocast had no GEMM left to cast.
- What it did do was apply its fp32 policy to `layer_norm` and `rms_norm`, which is the whole of the block's norm path. The widened outputs were saved for backward twice and recomputed under recompute.
- The norms still accumulate mean and variance in fp32 inside ATen.
- A regression test pins that the model is called outside autocast.

**Packed thd attention on the local spec (`5dca19e`, `7b02c87`).**
- `PrimusTurboLocalAttention` used to ignore `packed_seq_params`. A thd packing is now served by Turbo's `flash_attn_varlen_func`.
- It is off by default and selected by the `local_thd_attention` model key.
- `WanConfig` rejects the key unless `transformer_impl: local`, since the TE path always packs. The trainer rejects it together with `enable_turbo_attention_float8`, since Turbo has no fp8 varlen kernel.
- The varlen kernel is imported only if the Primus-Turbo build has it. Without it the local spec still imports and serves the dense path, and only a thd call raises (`a220be1`).
- A uniform-resolution batch gains nothing from packing. The path exists for mixed-resolution batches, which first need per-sample token counts from the data path.
- The trainer logs which attention path and kernel a run takes.

**MXFP4 reduction-axis alignment (`3e34c70`, `a6bce97`).** Each of M, K and N is the reduction axis of one of a linear's three FP4 GEMMs, and each is padded only when it breaks a kernel constraint:
- AITER's FP4 dispatcher needs every reduction axis to be a multiple of 16.
- `quantize_mxfp4_dual` needs its input's last dimension to be a multiple of the 32-wide MX block, which applies to K and N.
- When `cdiv(d, 128)` is odd, the shuffled colwise scale buffer has blocks with no FP4 data behind them. The Turbo build WAN MXFP4 was first trained on left them unwritten, and the wgrad GEMM summed whatever memory held. Turbo 0.4.1 builds write every scale entry and give bit-identical gradients without the padding. It stays as a guard for older builds.

Axes that already conform are not copied; WAN's dimensions at an even micro-batch size pass through unpadded. Tests run forward and backward at shapes padded on each axis, bit for bit against explicitly zero-padded operands. The same work stops conflating dtypes: `grad_input` comes back in the input's dtype and `grad_weight` in the weight's, and a test pins both.

**The MXFP4 recipe runs a bf16 forward and an MXFP4 backward (`28e616b`).**
- The new model key `mxfp4_forward_precision: bf16` routes the MXFP4 local linears through a new autograd function. Its forward is the bf16 GEMM of the unquantized operands. It also quantizes the activation and the weight, padded as the pure path pads them, and keeps their colwise FP4 copies for dgrad and wgrad.
- Those backward copies use a Hadamard rotation on every operand and 1×32 weight blocks. The pure MXFP4 path keeps its recipe, so other models are unaffected.
- Why: in longer fine-tunes, the quantized forward GEMMs are where pure MXFP4 drifts from bf16. With the forward in bf16, the loss stays on bf16's, while the backward keeps MXFP4's GEMMs.
- `wan2.1_t2v_1.3b_pretrain_pusa_local_spec_mxfp4.yaml` is renamed to `..._mxfp4_bwd.yaml` and sets the key.
- `WanConfig` and the linears reject it together with `mxfp4_backward_precision: fp8`. The trainer forwards it and logs the resulting precision. Flux's trainer doesn't forward it, so Flux always runs the MXFP4 forward.
- Tests:
  - the output equals `F.linear` exactly;
  - wgrad is bit-identical to the pure path's, since its operands carry the same flags;
  - dgrad is quantized but close to the bf16 gradient;
  - the module routes to the new function, and the default is unchanged.

**Run-to-run reproducibility.** The attention backward is the source of run-to-run variation, in bf16 and in MXFP4, so neither is reproducible step for step unless `deterministic_mode` is on. Stochastic rounding of the MXFP4 gradients, off by default, would add its own.

**Precision is forwarded, not assumed (`3d11232`, `06ca4b5`, `2a2ba87`, `4e0bfe3`).**
- **Forwarding:** the config builder passes the MXFP4 recipe string through unchanged, so the AITER preshuffle check runs. It also forwards the FP8 keys that the Primus-Turbo Float8 local linears read, with grad-accum fusion off as those linears require.
- **`WanConfig.validate()`:**
  - rejects `fp4` or `fp8` on the TE path, where the WAN forward never enters an FP8/FP4 autocast and the run would silently train in bf16;
  - rejects `sensitive_layers_enabled` without `fp4`, since only the MXFP4 backend builds the first and last blocks at another precision.
- **Missing providers:** if `fp4` or `fp8` is set but the matching Primus-Turbo provider fails to import, backend selection raises instead of building bf16 linears. The same holds for the provider that `sensitive_layer_precision` names, and an unknown `sensitive_layer_precision` also raises.
- **Delayed FP8 scaling:** the trainer rejects it with Megatron-FSDP `optim_grads_params`. The delayed-scaling update seeds weight amaxes before the first step, when that sharding leaves the weights empty, so the run failed on step 1. The error names tensorwise as the way out.
- **Logging:** the log states the requested linear precision and the linear classes actually built.
- **Model numerics (`303a6c5`):** the trainer now forwards `layernorm_epsilon` from the model YAML into `WanConfig`; before, an override was silently replaced by the default. The WAN block has no dropout, as in diffusers, so `WanConfig` rejects a nonzero `hidden_dropout` or `attention_dropout` rather than ignoring it.

**The training noise and timesteps (`78d074b`, `a6bce97`, `4e0bfe3`).**
- Noise is mixed in fp32 at the sigma the model is conditioned on, then cast.
- Training timesteps are drawn from 1..N, so the base sigma covers {1/N, …, 1}, as in DiffSynth and the scheduler's own weight table: sigma 0 is never drawn and sigma 1 is trained.
- The configured `scheduler_sigma_min` / `scheduler_sigma_max` bound the noise that training applies, and the inherited inference schedule spans the same range. Under the static shift the inference endpoints are always the pre-shift values of the schedule's ends, so the default range isn't shifted twice at the low-noise end either (`9f92c3d`).
- A static shift that isn't positive is rejected: 0 makes the last sigma `0 / 0`, and a negative shift puts a pole inside the schedule (`7b4081b`).
- The trainer rejects `out_channels != in_channels`, since the step regresses `noise - latents`, which has the latents' channels. `WanConfig` still accepts it, because image-to-video models (36 → 16 channels) are valid for inference (`7b4081b`).

**WAN 2.2 per-expert windows follow the router (`ea209e6`, `02fa79a`, `a6bce97`).**
- The router compares the post-shift conditioning timestep against `boundary_ratio * N`. The per-expert training window was being applied to the raw index, so the two disagreed whenever `shift != 1`.
- The window edges now come from the router's own comparison, so a window at `boundary_ratio` splits exactly where routing does. A window whose top edge is 1 includes t = N.
- The scheduler settings live on `WanConfig`, so a window that holds no integer timestep is rejected when the config is built.
- A per-expert `stage` requires `num_transformers: 1`, because the stage rewrites the subfolder the dual-expert model loads its high-noise expert from.

**Each data-parallel rank draws its own noise and timesteps (`21f1cf9`).**
- Megatron seeds every data-parallel rank alike unless `data_parallel_random_init` is set, which `trainer_base.yaml` turns off. So every rank drew the same noise and timesteps, and a step trained on one micro-batch's worth of distinct timesteps however many ranks it ran on.
- The WAN forward step now reseeds on its first call with `seed + 100 * dp_rank`, as Flux does.
- Multi-GPU WAN runs therefore draw different noise than before this commit.
- A resumed run restarts the draw sequence; #1258 tracks the fix.
- Seeding from the global sample index, which would make an N-node run comparable step for step with a one-node run, is left for the multi-node work.

**Fences that land with it:**
- `context_parallel_size != 1` is rejected, since nothing splits the video sequence across context-parallel ranks (`39f10b6`).
- The dual-expert `Wan2_2` model is rejected above one data-parallel rank (`2c32faf`). It routes each micro-batch on its own rank, so under Megatron-FSDP two ranks that route differently would issue different collective sequences.
- `Wan2_2` is also rejected with Megatron-FSDP, torch FSDP2 or `overlap_grad_reduce` (`2a2ba87`). A step that routes no sample to an expert leaves it without gradients, and each of those asserts on such a step. On one data-parallel rank they have nothing to shard or overlap.
- WAN 2.2 A14B trains as per-expert jobs instead: `num_transformers: 1` with `stage: high_noise` or `low_noise`.

## Blast radius

These commits reach outside WAN and deserve the closest look:

- **`3e34c70` and `a6bce97`** change the MXFP4 local spec for every model that uses it:
  - the padding is a no-op for axes that already conform, which covers every Flux and Llama shape;
  - the dtype handling in the backward changes for all callers.
- **`93198f7`** reads the AITER preshuffle gate from Turbo's `BackendChoice`. On Primus-Turbo 0.4.x the old check was always false, so every MXFP4 local-spec model failed at init.
- **`fc22fb7`** makes the TE hipBLASLt GEMM workspace size configurable through `PRIMUS_TE_GEMM_WORKSPACE_MIB`. Unset, the patch does nothing.
- **`5dca19e`** adds the thd branch to `PrimusTurboLocalAttention`. Non-thd calls take the same dense path as before, which a test pins. **`a220be1`** keeps the module importable on Primus-Turbo builds without the varlen kernel, as on `main`.
- **`9f92c3d`** passes Megatron's `deterministic_mode` to `PrimusTurboLocalAttention`'s kernels, which hard-coded `deterministic=False` on `main`. Flux's local spec uses the same attention, so with `deterministic_mode` set its attention backward becomes deterministic too. Runs that leave it off, the default, are unchanged. It also adds `"wan"` to `DiffusionTransformerBlock`'s list of models that must pass `timestep_emb`.
- **`28e616b`** adds the bf16-forward mode to the MXFP4 local linears. It is off by default, so the MXFP4 path of every other model is unchanged. In the existing MXFP4 test file, `_pin_fp4_aiter` now pins the backend through `set_gemm_backend`, which writes the table entries Primus-Turbo 0.4's GEMM dispatcher reads. The guard tests' Megatron-args setup moved into a helper that the new tests share.
- **`87d6139`** exposes two Energon shuffle knobs whose defaults match Energon's own.
- **`diffusion_model.yaml`** declares `attention_backend: auto`, Megatron's own default, so configs can override it.

Everything else is confined to WAN's model, data, scheduler and trainer, or to new files. `compute_flow_matching_loss`, which Flux uses, is unchanged; WAN uses the new `compute_weighted_flow_matching_loss`. Its masked mean divides by the mask total after broadcasting, replacing it with 1 only when it is exactly zero (`7b4081b`). The earlier `clamp(min=1.0)` also raised a soft-mask total below 1 to 1, which under-weighted those elements. #1200 makes the Flux helper do the same; the two PRs touch the same file, so whichever merges second needs a small rebase.

## Testing

139 new test functions: 17 new files, plus additions to three existing ones (`test_synthetic_datasets.py`, `test_loss_computation.py`, `test_primus_turbo_mxfp4_local.py`). No existing test was removed; the one existing helper that changed is `_pin_fp4_aiter`, described under Blast radius.

They cover:
- **MXFP4:** the FP4 reduction-axis alignment against the kernels' constraints, padded forward and backward against explicit zero padding, and the bf16-forward mode against `F.linear` and the pure MXFP4 wgrad.
- **Loss and scheduler:** the weighted flow-matching loss and its masked mean, the timestep range and the fp32 noise mix, the sigma range, and the per-expert windows against routing.
- **Model:** RoPE against an exact rotation on every path, recompute against the plain forward in bf16 and MXFP4, the layer spec's state-dict keys against the converter's key table, dual-expert routing and reassembly, and Wan2_2 gradient sync with real backbones through steps that skip an expert.
- **Attention and the forward step:** the `attn_atomic_fp32` environment plumbing, `deterministic_mode` reaching the kernels and a bit-for-bit repeatable backward, packed thd attention against dense, the forward step running outside autocast, and the absent validation path.
- **Config and trainer:** precision and numerics forwarding and rejections, per-rank RNG seeding, and the workspace-size parsing.
- **Checkpoints:** path resolution, torch-shard loading in both the converter and the training loader, and the rejection of a key repeated across shards.
- **Parity:** a one-forward check of a two-block model against diffusers, on the TE path and both local paths.

## Limitations

- Training reads pre-encoded latents only. The raw-video and encoder path was removed until something wires it in (`842d994`).
- There is no validation schedule yet, so the trainer requires `eval_iters: 0` (`e4fd329`).
- The WAN 2.2 TI2V-5B preset sets the backbone shape only. Image conditioning is not wired and will follow in a separate PR.
- FP8 and MXFP4 run on the local spec only.
- TP, PP and CP are fixed at 1.
- Building `WanTransformer3D` needs Megatron's parallel state initialized, as other Megatron-Core models do, so a standalone script that builds it must initialize that first. The checkpoint converter works on state dicts and doesn't need it.
- The dual-expert `Wan2_2` model runs on one data-parallel rank, with plain DDP and no `overlap_grad_reduce`. Train A14B as per-expert `stage` jobs (`2c32faf`, `2a2ba87`).
- The logged training loss is one data-parallel rank's value, as it is for Flux. #1386 tracks logging the data-parallel mean for both.

- The example configs are launched with `primus-cli` and carry their recipe-specific environment in a top-level `env:` block:
