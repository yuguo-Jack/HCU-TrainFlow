# feat(tools/perf): report why a run failed, from the rank that failed; guard TRAIN_STEPS; keep downloads out of the checkout

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1293) · state: closed · merged: True

## Original PR description

## Why

Release agents debug failed perf runs from `results.csv` and the batch summary. In the v26.9 release batches those often pointed the wrong way:

- `failure_detail` named the first traceback in the log. For the rc1 Megatron-Bridge failures that was an ImportError a Primus patch logs when it is skipped, not the AssertionError that stopped the run.
- The run log only has local rank 0's console (torchrun `--local-ranks-filter`). When another rank failed first, its error was lost and the result said only "launcher exited with code 1".
- An NCCL error was reported by its first line ("unhandled cuda error"). That hid the real cause, e.g. RCCL failing to allocate GPU memory, and sent people to change the NIC.
- The multi-node runner retried every failure up to 6 times, including config errors that fail the same way each time.
- `TRAIN_STEPS` broke the Megatron-Bridge recipes: with their 50-step warmup, `TRAIN_STEPS=20` fails Megatron's `lr_warmup_steps < lr_decay_steps` assertion on every rank.
- Hugging Face downloads went into `<checkout>/data` (62 GB for Qwen3-32B), which filled a 90 GB home quota.

## What changes

**Failure reports**
- `failure_detail` is now the exception that stopped the run. That's the root of the traceback chain printed before `[Primus] Error:`, past Primus's `Training execution failed` wrapper and torchrun's `ChildFailedError`. Primus `[Patch]` messages and other ranks' lines are ignored. A bare `AssertionError` gets its failed assert and location.
- After a failed run, the runner finds the rank torchrun names as the root cause and copies that rank's ERROR records from this run into the log, as a "Failing Rank Output" section. The records come from its Primus log, `<workspace>/…/logs/<module>/rank-N/error.log`. The extractor reads that section first. `FAILING_RANK_OUTPUT=0` turns this off.
- RCCL's `Failed to CUDA calloc/malloc N bytes` is classified as `oom`, unless the output shows a GPU fault first. NCCL errors keep NCCL's `Last error:` line, which usually names what failed, e.g. `Call to ibv_modify_qp failed with 110 Connection timed out, on dev rdma4:1`.
