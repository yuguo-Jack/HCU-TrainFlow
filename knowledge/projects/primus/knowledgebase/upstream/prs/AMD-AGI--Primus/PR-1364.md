# feat(minimax-m3): MiniMax-M3 proxy pretraining on MI455X (gfx1250)

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1364) · state: open · merged: False

## Original PR description

## Summary

MiniMax-M3 BF16 proxy pretraining on MI455X (gfx1250) with the Megatron backend, on Megatron-LM core_v0.19.2.

- **gfx1250 MSA kernels.** Wave32 WMMA versions of the FlyDSL MSA forward, backward (dQ, dK/dV) and the indexer's block max (`minimax_m3/flydsl/msa_w32.py`, `msa_token_fwd_w32.py`, `msa_token_bwd_w32.py`, and a wave32 builder in `index_block_max.py`). The originals use MFMA, `permlane32` and `ds_read_tr16`, which gfx1250 does not have, and failed at compile with `Cannot select: permlane32.swap`. gfx950 keeps the MFMA kernels; only the dispatch changed.
- **Megatron-core 0.19.** `MinimaxSparseAttention` takes the `name=` that 0.19's `TransformerLayer` passes, and the fused Adam clip patch takes 0.19's `group=` in its reduce-max and reads `get_grads_for_grad_norm`. Without these, building an M3 model and the first optimizer step raise a `TypeError` on this base.
- **Fused Adam clip patch builds again.** No hard-coded `-std=c++17`: torch 2.14's headers need C++20, and the patch logged the build error and training ran without it.
- **`megatron.optimizer.te_l2norm_large_tensor` patch.** TE's `multi_tensor_l2norm` reads out of bounds when a multi-tensor call has a tensor of 2^31 or more elements. The Primus-Turbo grouped GEMM keeps a layer's experts in one weight (4.8e9 elements on one GPU), so the first step faulted or ran with a wrong grad norm. The patch splits such tensors into 2^30-element views for the norm.
- **Example.** `examples/megatron/configs/MI455X/minimax_m3-BF16-pretrain.yaml`, `examples/megatron/models/minimax-m3/run_minimax_m3_mi455x.sh` and its README. Defaults: Primus's HIP fused Adam with in-kernel clipping and BF16 writeback, no per-step NaN check. The four-GPU baseline is EP4 with 8 layers and GBS 32 (8 micro-batches per rank, as in the MI355X 8-layer config).

#### 2. 🟠 Should fix: Single-optimizer runs clip MTP params with the main-model norm: this PR adds the MTP guard only to the chained path
`primus/backends/megatron/patches/te_patches/fused_adam_clip_patches.py:616`

The new MTP separate-grad-norm-group guard exists only in `_chained_step_with_device_clip`. With a single optimizer, `MegatronOptimizer.step` calls `patched_clip_grad_norm`, which computes the main norm (MTP excluded by Megatron's getter) and lets FusedAdam clip every param, MTP included, with it. Megatron-core 0.19 instead clips MTP params with their own group norm, and nothing raises here. Add the `has_grad_norm_group` check to `patched_clip_grad_norm`. The skip-threshold part does not apply: in 0.19 only `ChainedOptimizer.step` honours `grad_norm_skip_threshold`.

**Who is affected:** Users who set `PRIMUS_FUSED_ADAM_CLIP=1` with MTP enabled on a model whose optimizer is not chained (for example, a dense model with one model chunk).
