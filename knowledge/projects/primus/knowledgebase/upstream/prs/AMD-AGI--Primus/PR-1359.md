# [WIP] perf(mega_moe): wgrad into main_grad, faster wgrad and GEMM tiles for DSv3 on MI455X

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1359) · state: closed · merged: False

## Original PR description

# Description

Faster BF16 Mega MoE training on gfx1250 (MI455X) for DeepSeek-V3. Only the gfx1250 BF16 Mega MoE path changes; the kernel changes are bit-identical and the wgrad accumulation is opt-in. Companion Primus PR: AMD-AGI/Primus from `lhzhang333:dev/lhz/dsv3_opt_merge`. It checks for the new argument and keeps DDP's separate add without it, so either PR can go in first.

## Type of change

- [x] New feature (non-breaking change which adds functionality)

## Changes

- Expert wgrads accumulate into `main_grad` in the wgrad epilogue (`fuse_wgrad_accum_pattern="megatron"` on the staged ops); weights the kernel cannot serve keep the ordinary gradient. Also fixes `_vk_launch` running a freshly compiled variant twice.
- Faster variable-K wgrads at DeepSeek-V3 shapes: a three-buffer ring (`tile_k` 64), the XDL arbitration stall off on the ring, and dW2 super-tile height 14.
- Mega GEMM tile scheduling options of `dispatch_gemm_nt_gfx1250` / `gemm_combine_nt_gfx1250` (`issue_first`, `lds_cosched`, `wmma_b2b`), on by default.

## Testing

On MI455X (`amdprimus/amdprimus:tas-20261019`):
- New and extended tests: `test_mega_bf16_gfx1250_variable_k_accum.py`, staged wgrad accumulation in `test_mega_bf16_gfx1250_fused_moe.py`, scheduling bit-identity in the dispatch-GEMM and GEMM-combine tests. The single-GPU Mega suites pass (80 tests).
- 4-GPU EP suite (`test_mega_bf16_gfx1250_fused_moe_ep.py`): 5 passed.
- With the companion Primus PR, DeepSeek-V3 proxy on 4× MI455X with MegaMoE: 1003.1 → 933.8 ms/iter (−6.9%) vs main.

**5. Older Primus-Turbo builds fail to import: this PR added unguarded `PrecisionType`/backend imports** (`primus/backends/megatron/core/extensions/primus_turbo.py:70`)

The new module-level `from primus_turbo.pytorch.core.backend import BackendType, GlobalBackendManager, PrecisionType` and the `get_grouped_gemm_backend(PrecisionType.BF16_FP16_FP32)` call have no guard. On the v26.2/v26.3 Turbo builds there is no `PrecisionType`, no `FLYDSL` member and no precision argument, so importing `primus_turbo.py` fails and every Turbo-enabled run breaks; the `getattr(choice, 'backend', choice)` fallback is unreachable. Wrap these in try/except like the other newer-Turbo symbols and treat missing symbols as "not pinned".

_An independent check of the code found this probably does not apply: The base `primus_turbo.py` already imports `ENV_GEMM_BACKEND` from `primus_turbo.common.constants` unguarded, and the installed old 0.2.0+45fe919 build has no `primus_turbo/common`; the base `primus_turbo_mxfp4_local.py` already imports `PrecisionType` unguarded. The CI pin d04ffd9 defines `PrecisionType`, `BackendType.FLYDSL` and `get_grouped_gemm_backend(precision)`, so the pinned build imports and runs the new code._

**6. Clipping change for all gfx1250 Megatron jobs is hard to review and bisect: this PR bundles it** (`primus/backends/megatron/patches/clip_grad_coalesced_scale_patches.py:146`)

Besides the MegaMoE wgrad-into-`main_grad` change, the PR adds a gfx1250-only gradient-clipping replacement (`clip_grad_coalesced_scale_patches.py`), an opt-in Triton FP32 router GEMM (`moe_router_triton_gemm`) and launcher tuning in `run_deepseek_v3_proxy_mi455x.sh`. The clip patch is auto-discovered and installs for every Megatron job on gfx1250, MoE or not. It replaces the upstream clip only when gradients can be merged into contiguous runs, and otherwise falls back to the upstream function. Consider splitting the PR, or at least naming the clip patch in the title and description, so it can be reviewed and bisected on its own.

**Who is affected:** Reviewers, and anyone bisecting gradient-clipping behaviour on gfx1250 Megatron runs.

**7. Layered router backward wrappers may crash: this PR's Triton forward skips dtype attrs and `bias`** (`primus/backends/megatron/patches/moe_patches/router_triton_gemm_patches.py:47-56`)

On the Triton path, the patched forward saves only `(inp, weight)` and never sets `ctx.router_dtype`, `ctx.input_dtype` or `ctx.weight_dtype`. A backward wrapper layered on top, such as the `moe_router_bwd_bf16` patch at the same priority 50, would hit AttributeError or a tuple-unpack error. Keep the upstream contract: set the dtype attributes and save `bias`.

_An independent check of the code found this probably does not apply: `patch_router_triton_gemm` reads `get_args(ctx).moe_router_bwd_bf16` and returns before patching whenever it is set, regardless of patch order, so `_router_backward_bf16` / `_uses_bf16_router_backward` never wrap the Triton forward. Megatron's original backward is only called when `ctx_.primus_triton` is False, i.e. after `orig_forward` populated ctx, and both patches are priority 50 with bf16 registered first (index 74 vs 75)._

**8. Requesting both router options silently drops Triton GEMM: this PR warns-and-skips instead of erroring** (`primus/backends/megatron/patches/moe_patches/router_triton_gemm_patches.py:36-42`)

With both `moe_router_triton_gemm` and `moe_router_bwd_bf16` set, the Triton patch only logs a warning and is not installed, so an explicitly requested option is dropped at runtime. The exclusion is not order-dependent: the check reads `args.moe_router_bwd_bf16`, not the bf16 patch's flag, so the Triton forward is never installed alongside the bf16 backward. The yaml and docs document the pair as not used together; rejecting it during argument validation would make the conflict fail fast instead of a rank-0 warning.

**Who is affected:** Users who enable both router options in one config.

**9. Strided or cross-device router inputs could give wrong results: `supported()` skips weight-device and K-stride checks** (`primus/backends/megatron/core/extensions/_triton/router_gemm.py:256-272`)

`supported()` checks `inp.is_cuda` but not that `weight` is on CUDA and on the same device as `inp`. It also does not check unit stride along K, which the kernels assume since only `stride(0)` is passed. Direct callers with strided inputs or mismatched devices would get wrong results instead of falling back, so add these checks or assertions in the wrappers.

_An independent check of the code found this probably does not apply: `supported()` already requires `weight.is_contiguous()`, and the only caller (router_triton_gemm_patches.py) passes `inp.reshape(...).contiguous()` and `grad_output....float().contiguous()`, so the K stride is always 1. Megatron's router weight and input live on the same GPU; a CPU or foreign pointer would make Triton raise rather than compute silently wrong results._

**10. Models with 48/96/160 experts silently miss Triton router GEMM: this PR's docs omit the power-of-two requirement** (`docs/03-configuration-reference/megatron-parameters.md:602`)

The `moe_router_triton_gemm` row in megatron-parameters.md says the kernels take '16-256 experts'. `router_gemm.supported()` also requires a power-of-two expert count (`n & (n - 1) == 0`). Models with, for example, 48, 96 or 160 experts therefore keep Megatron's path although the docs suggest they qualify. Say 'a power-of-two expert count from 16 to 256'.

**Who is affected:** Users who enable `moe_router_triton_gemm` on a model whose expert count is not a power of two and expect the Triton path.
