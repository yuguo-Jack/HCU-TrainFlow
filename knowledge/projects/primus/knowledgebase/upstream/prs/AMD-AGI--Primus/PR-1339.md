# [draft] feat(megatron): add MiniMax-M3.1-Flash and fix M3's FlyDSL MSA import on rocm/primus:v26.8

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1339) · state: open · merged: False

## Original PR description

## Summary

**Fix: M3's FlyDSL MSA kernels fail to import on `rocm/primus:v26.8`.** #1275 moved their `buffer_ops` import to Primus-Turbo's vendored `primus_turbo.flydsl.utils.buffer_ops`, which Turbo builds that ship FlyDSL 0.2.x do not have; v26.8 has Turbo 0.5.1.dev7 with FlyDSL 0.2.4. So the default `msa_backend: flydsl` raised `ImportError` there. `flydsl/_buffer_ops.py` uses the vendored module when present and otherwise FlyDSL 0.2.x's `flydsl.expr.buffer_ops`. DeepSeek-V4 `flydsl_v1` and Kimi-K3 `_flydsl_v1` use the same import and are left for a follow-up.

**Feature: [MiniMax-M3.1-Flash](https://huggingface.co/MiniMaxAI/MiniMax-M3.1-Flash).** It keeps M3's shapes (~428B total / ~23B active; its `config.json` and `configuration_minimax_m3_vl.py` match M3's apart from the values below), so `minimax_m3.1_flash.yaml` extends `minimax_m3.yaml` and overrides only:
- MSA in all 60 layers. M3 runs dense attention in layers 1-3; their MLPs stay dense in both models, so `moe_layer_freq` is unchanged.
- `rope_theta` 1e7 instead of 5e6.
- No MTP; speculative decoding moves to the separate DSpark draft model.

The two sparse patterns are `1`, `moe_freq_type`'s "every layer", so they follow `num_layers` and a reduced-depth proxy overrides only `moe_layer_freq`. The release's QAT formats (MXFP8 linears, NVFP4 experts) and DSpark are recorded as unmapped.

MI355X examples: full-size BF16 and FP8, and `minimax_m3.1_flash_8layer-BF16-pretrain.yaml`, an 8-layer single-node proxy (3 dense-MLP + 5 MoE layers, all MSA, EP=8), since the full model does not fit on one node. The support matrix is updated.

## Results

1x MI355X node (8 GPUs), `rocm/primus:v26.8` (`sha256:79629b5e5ba4…`), 8-layer proxies, seq 4096, GBS 64, mock data, `msa_backend: flydsl`, 20 iterations, averages over iterations 3-20. Every run exited 0 with no NaN or skipped iterations.

| Proxy | ms/iter | TFLOP/s/GPU | tokens/s/GPU | Memory/GPU | lm loss, iter 1 -> 20 |
|---|---|---|---|---|---|
| M3 BF16 | 2059 | 422 | 15,916 | 148.4 GB | 13.43 -> 3.06 |
| M3 FP8 (`--fp8 hybrid`) | 1974 | 440 | 16,597 | 157.6 GB | 13.42 -> 3.18 |
| M3.1-Flash BF16 | 2144 | 404 | 15,286 | 148.6 GB | 13.43 -> 4.20 |
| M3.1-Flash FP8 (`--fp8 hybrid`) | 2024 | 428 | 16,192 | 157.6 GB | 13.42 -> 4.33 |

- The M3.1-Flash proxy has 11,797,248 more parameters per rank than M3's, which is exactly three MSA indexers, so layers 1-3 do run MSA.
- M3.1-Flash is ~4% slower per step because those three layers run the MSA kernels instead of dense flash attention at 4K.
- Loss values are on mock data and are not comparable across the two models.

**1. Full-size examples ship EP=8, which their own sizing note says OOMs** (`examples/megatron/configs/MI355X/minimax_m3.1_flash-BF16-pretrain.yaml:108`)

The full-depth `minimax_m3.1_flash-BF16/FP8-pretrain.yaml` examples ship `expert_model_parallel_size: 8` with PP off. Their own SIZING comment calls that shape an OOM (~129 GB of bf16 weights per rank), and says EP=32 needs the precision-aware optimizer block, which is left commented out. So the examples need edits before a full-depth run, as the comment instructs ('set expert_model_parallel_size to the world size'). This copies the existing `minimax_m3-*-pretrain.yaml` convention. Consider marking EP=8 explicitly as a placeholder, or reading EP from an env var.

**Who is affected:** Users who launch the full-depth M3.1-Flash BF16/FP8 examples unmodified without first following the SIZING comment's instruction to set EP to the world size.

_Verified by running it._

**Related past reviews:** [#1024](https://github.com/AMD-AGI/Primus/pull/1024) on `primus/backends/megatron/core/models/hybrid/kimi_delta_attention.py`

**2. DeepEP CU count tuned for EP8 while sizing guidance demands EP≥32** (`examples/megatron/configs/MI355X/minimax_m3.1_flash-BF16-pretrain.yaml:157`)

The shipped `expert_model_parallel_size: 8` with `turbo_deepep_num_cu: 80` is consistent with the comment's EP8 recommendation. The SIZING comment says EP=8 OOMs for the full model and tells users to set EP to the world size (≥32). Users who follow that and change only EP keep 80 CUs, while the comment recommends 32 for ep16-64, so DeepEP is likely mistuned (performance, not correctness). Add a note next to `expert_model_parallel_size` that `turbo_deepep_num_cu` should change with EP; this applies to both the BF16 and FP8 configs.

**Who is affected:** Users running the full `minimax_m3.1_flash` BF16/FP8 configs who raise EP to ≥32 as the SIZING comment instructs.

**3. Broad `except ImportError` in buffer_ops shim masks real import failures** (`primus/backends/megatron/core/transformer/minimax_m3/flydsl/_buffer_ops.py:15`)

`except ImportError` in `_buffer_ops.py` also catches failures raised inside an existing `primus_turbo.flydsl.utils` (broken build, missing transitive dependency), not just its absence, and then tries `flydsl.expr.buffer_ops`. On FlyDSL 0.3 the last line of the error becomes `cannot import name 'buffer_ops' from 'flydsl.expr'`. The original Turbo error is still printed above it through implicit exception chaining, but there is no hint to upgrade Primus-Turbo or pin `flydsl<0.3`. Catching `ModuleNotFoundError` and checking `e.name`, or re-raising with an explicit message when both imports fail, would make this clearer.

**Who is affected:** Users running `msa_backend: flydsl` with a Primus-Turbo build whose vendored `flydsl.utils` fails to import; they get a confusing, though still chained, error message.

_Verified by running it._

**4. Import fallback shim has no unit test** (`primus/backends/megatron/core/transformer/minimax_m3/flydsl/_buffer_ops.py:1`)

The new `_buffer_ops` shim prefers `primus_turbo.flydsl.utils.buffer_ops` and falls back to `flydsl.expr.buffer_ops` on `ImportError`, but no test covers that fallback order. Its importers are `index_block_max`, `msa_token_fwd` and `msa_token_bwd`. They are exercised only by the four `test_minimax_m3_flydsl_*` modules (attention, bwd, fwd, indexer). All four call `importorskip("flydsl")` and are skipped unless the GPU is gfx950, so a given machine exercises at most the one branch it has installed. A small CPU test that stubs `sys.modules` with `monkeypatch.setitem` could check three cases: the Turbo copy is preferred, the FlyDSL 0.2 copy is used when Turbo lacks it, and an `ImportError` is raised when both are missing.

**Who is affected:** Maintainers changing the shim or bumping Primus-Turbo or FlyDSL; a broken fallback branch would only show up on a gfx950 machine that has that specific FlyDSL/Turbo combination.

_Verified by running it._

**5. DeepSeek-V4 flydsl_v1 kernels keep the unguarded buffer_ops import** (`primus/backends/megatron/core/transformer/v4_attention_kernels/_flydsl_v1/dsa_fwd_v4_flydsl_kernel.py:56`)

The new FlyDSL 0.2/0.3 `buffer_ops` shim lives privately in `minimax_m3/flydsl/_buffer_ops.py`, and only the three M3 kernels use it. The DeepSeek-V4 `flydsl_v1` kernels (`_flydsl_v1/dsa_fwd_v4_flydsl_kernel.py:56`, `_flydsl_v1/dsa_bwd_dq_flydsl_kernel.py:56`) and the deprecated v0 kernels keep the unguarded `from primus_turbo.flydsl.utils import buffer_ops`. This is pre-existing and unchanged by this PR. On a Primus-Turbo without the vendored module (e.g. rocm/primus:v26.8), selecting `flydsl_v1` still fails at import. `load_flydsl_attention_backends` wraps that failure in an ImportError that blames the `flydsl` package, though the original error text is included. Consider moving the shim to a shared module and using it in the V4 kernels too, or noting that the fix covers only M3.

**Who is affected:** DeepSeek-V4 users who set `use_v4_attention_backend`/`use_v4_csa_attention_backend: flydsl_v1` on a Primus-Turbo build without `primus_turbo.flydsl.utils` (such as rocm/primus:v26.8).

_Verified by running it._

**6. mbs=1 justification cites eager backend while config runs flydsl** (`examples/megatron/configs/MI355X/minimax_m3.1_flash_8layer-BF16-pretrain.yaml:61`)

**8. Int sparse-freq tests only exercise freq=1 and overclaim preset coverage** (`tests/unit_tests/backends/megatron/test_minimax_m3_flops.py:122`)

The new int-frequency tests (`test_int_sparse_freq_charges_every_layer`, `test_layer_pattern_from_an_int_follows_num_layers`) only use `sparse_attention_freq=1`. With 1, `i % 1 == 0` holds for every layer, so they cannot tell Megatron's 'every Nth layer' meaning apart from 'any int means all layers'. Adding an N>1 case, e.g. `2` -> `(1,0)*4`, would pin the int semantics. The test name `..._charges_every_layer` should then say it covers N=1 only. The M3.1-Flash preset itself is already loaded end-to-end by the parametrized `test_preset_builds_the_real_config`.

**Who is affected:** Test coverage only: a regression in int-N (N>1) handling of `sparse_attention_freq` would not be caught; no runtime impact.

_Verified by running it._

**9. Preset test skips `sparse_disable_index_value`; layer comment misplaced** (`tests/unit_tests/backends/megatron/test_minimax_m3_config.py:313`)

The parametrized preset test checks `sparse_layer_pattern` but not `sparse_disable_index_value`, so a preset that overrides only one of the two would still pass. Add `assert config.sparse_disable_index_value == sparse_pattern`. Also move the comment 'both models keep dense MLPs in layers 1-3' from the MSA-pattern assert to the `moe_layer_freq` assert, where it belongs.

**Who is affected:** Maintainers relying on `test_preset_builds_the_real_config` to catch a `minimax_m3.1_flash.yaml` that forgets to override `sparse_disable_index_value`; no runtime effect, since nothing outside the config class reads the field.

_Verified by running it._

**10. `moe_layer_freq` assertion pins the raw string, not the layer layout** (`tests/unit_tests/backends/megatron/test_minimax_m3_config.py:317`)

`assert config.moe_layer_freq == "([0]*3+[1]*57)"` compares the unparsed YAML spelling. An equivalent spelling would break the test, and the per-layer MoE layout is never actually checked. Compare against the expanded list, for example via `moe_freq_type(...)`.

**Who is affected:** Only maintainers of `test_minimax_m3_config.py`; an equivalent rewrite of the preset's `moe_layer_freq` would fail the test while a wrong layout of the same spelling cannot be caught.

_Verified by running it._

**11. Separate RoPE length env var and overstated RoPE cache cost** (`examples/megatron/configs/MI355X/minimax_m3.1_flash-BF16-pretrain.yaml:63`)

In all three new M3.1-Flash examples, `max_position_embeddings` reads `PRIMUS_MAX_POSITION_EMBEDDINGS` (default 4096) and is not tied to `PRIMUS_SEQ_LENGTH`. Raising only `PRIMUS_SEQ_LENGTH` above 4096 aborts at startup on Megatron's `max_position_embeddings >= seq_length` assertion; it does not leave a short RoPE cache. The comment saying the preset's 1048576 'materialises the RoPE cache' and costs 'tens of GB' is inaccurate. Megatron builds RoPE each forward from the actual input length, so `max_position_embeddings` does not size any cache. Default it to `${PRIMUS_SEQ_LENGTH}` (or document the coupling) and fix the comment; the same lines were copied from the existing `minimax_m3-*` examples.

**Who is affected:** Users of the new minimax_m3.1_flash example configs who set PRIMUS_SEQ_LENGTH > 4096 without also setting PRIMUS_MAX_POSITION_EMBEDDINGS get an immediate argument-validation failure.

**12. Proxy architecture defined in example overrides instead of a preset** (`examples/megatron/configs/MI355X/minimax_m3.1_flash_8layer-BF16-pretrain.yaml:67`)

The 8-layer proxy sets `num_layers: 8` and `moe_layer_freq: "([0]*3+[1]*5)"` in the example `overrides` rather than in a preset extending `minimax_m3.1_flash.yaml`. The values agree (8 entries for 8 layers). `test_example_configs.py` does load this example (YAML and preset merge), but no test builds its Megatron transformer config. A future edit that changes one value without the other would therefore only fail at model build. Optionally add a `minimax_m3.1_flash_8layer.yaml` preset covered by the preset test in `test_minimax_m3_config.py`, as done for `qwen3_235B_A22B_4layer.yaml`.

**Who is affected:** Maintainers editing the 8-layer MI355X proxy example; there is no runtime bug in the shipped values.

**Related past reviews:** [#1155](https://github.com/AMD-AGI/Primus/pull/1155) on `examples/megatron/configs/MI455X/qwen3_235B_A22B-BF16-lora-sft-1gpu-proxy.yaml`
