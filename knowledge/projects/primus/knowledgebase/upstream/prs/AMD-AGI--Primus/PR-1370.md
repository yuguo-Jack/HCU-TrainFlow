# fix(megatron): finish the core_v0.19.2 port (PP schedules, V schedule, FSDP, config args)

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1370) · state: open · merged: False

## Original PR description

## Summary

Follow-up to #1321 (Megatron-LM `core_v0.19.2`).

### PP schedules and V schedule

- `get_forward_backward_func` replacements and wrappers take `pp_size`, `vp_size`, `schedule_pg_collection`.
- `LinearWithGradAccumulationAndAsyncCommunication.forward` takes `tp_group`, `gtp_remat_size`.
- `backward_step` no longer takes `model_type` (PrimusPipe handler, zero-bubble runtime).
- V schedule:
  - `get_batch_on_this_tp_rank` keeps labels / loss_mask on PP rank 0, which also runs the loss chunk;
  - the stage predicates are rebound in every module that imports them.
- Zero-bubble (`patch_zero_bubble`):
  - `DataLoaderStore` builds the batch with the 0.19 `get_batch_on_this_tp_rank` / `get_batch_on_this_cp_rank` (the old call raised `TypeError` on the first batch);
  - the runtime takes `force_all_reduce` and rejects it as unsupported (`save_wgrads_interval`).

### Other API changes

- zbpp optimizer: `get_grads_for_grad_norm`.
- MLA: `MultiLatentAttention(pp_layer_offset, name)`.
- GLM-5 next: `setup_model_and_optimizer(model_type, model_provider_func, ...)`.
- Experts: `group_offload` for fine-grained activation offloading.
- DeepSeek-V4 / MiniMax-M3 indexer loss logging: `MoEMetricsTracker.report`.
- Per-head Muon: `megatron.core.optimizer.get_megatron_optimizer` and `TensorParallelMuon`.
- Torch FSDP2: `megatron.training.utils.common_utils`.
- Checkpoint convert: `megatron.legacy` removed.
- The fused AdamW clip patch's `get_grads_for_grad_norm` rename is left to #1364.

### Megatron-FSDP

- Dense models with `ddp_average_in_collective` fall back to the data-parallel group where 0.19 has no expert data-parallel group (the GDN 1B FSDP configs failed to start). MoE models are not affected.

### Config args

- `trainer_base.yaml`:
  - renamed to the 0.19 names `use_gloo_process_groups`, `fp4_param_gather`, `muon_nesterov`;
  - dropped `scatter_gather_tensors_in_pipeline`.
- `language_model.yaml`: dropped `tiktoken_special_tokens`.
- MI355X MLPerf GPT-OSS recipes (`gpt_oss_20B-FP8-mlperf`, `FP8-turbo-attn`, `MXFP4-deosc`): dropped `moe_deepep_num_sms` / `moe_hybridep_num_sms`. They are unused with the alltoall dispatcher, and 0.19 rejects the two set to different values.
- `docs/03-configuration-reference/megatron-parameters.md` follows the renames.

### CI

- The core, Megatron and TorchTitan test steps drop `--maxfail=1` when `PRIMUS_CI_FULL=1`.

**4. 🟠 Should fix: Hybrid-FSDP MoE without `expt_dp` silently reduces expert grads over the dense DP group**

The patched `get_dp_group` falls back to the dense DP group whenever the expert group is None, without checking that the model is dense. For non-hybrid MoE this cannot be reached: `MegatronFSDP` raises `ValueError` when the model has expert parameters but `get_fsdp_group(is_expert_parallel=True)` is None. It is reachable only for hybrid FSDP where `hybrid_fsdp_expt_group` is None but `expt_fsdp_group` is set, i.e. a `pg_collection` without `expt_dp`; upstream marks that path "not been tested yet". There, expert grads would be scaled and reduced over the dense group instead of erroring. Gating on `num_moe_experts is None` would make the intent explicit; the stub tests cover only `use_hybrid_fsdp=False`.

**Who is affected:** Only MoE runs with Megatron-FSDP HSDP (num_distributed_optimizer_instances > 1) that pass a pg_collection lacking `expt_dp`.
