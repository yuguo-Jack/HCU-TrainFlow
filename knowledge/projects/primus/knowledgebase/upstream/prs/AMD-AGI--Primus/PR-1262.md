# fix(hybrid): point the Zebra converter wrappers at a KDA checkpoint

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1262) · state: open · merged: False

## Original PR description

## What

Points the `convert_zebra_llama_to_hf.sh` wrapper, and the eval and chat helpers that follow it, at a KDA checkpoint instead of a Mamba2 one.

## Why

`convert_zebra_llama_to_hf.py` targets the KDA + MLA architecture implemented by `modeling_zebra_llama.py`. That model's layer stack is built from exactly three block types:

```python
if t == "kda":
    self.layers.append(KDALayer(config))
elif t == "attention":
    self.layers.append(MLAAttentionLayer(config, i))
elif t == "mlp":
    self.layers.append(MLPLayer(config))
```

There is no Mamba or GDN mixer in the file. Those architectures are served by `convert_mamba_hybrid_to_fla_hf.py` and `convert_gdn_hybrid_to_fla_hf.py`, and `docs/04-technical-guides/hybrid-models/README.md` already describes this script as the KDA/hybrid converter and documents it with `zebra_llama_kda_1B`.

The shipped wrapper nevertheless pointed it at `output/zebra_llama_mamba_1B_BF16-pretrain/iter_0020000`, a Mamba2 + MLA run, so running it as shipped fed Mamba weights to a KDA model definition. The key comparison reports the resulting missing, extra and shape-mismatched keys, so this is not silent, but the converter still writes weights, a `config.json` and a model card describing the output as KDA. The wrapper also contradicted the documented example.

## Changes

- `convert_zebra_llama_to_hf.sh` converts `zebra_llama_kda_1B_BF16-pretrain/iter_0028000` into `output/zebra_llama_kda_1B_hf_iter_0028000`, matching the hybrid-models guide, and gains a comment naming the converters for Mamba2 and GDN.
- `run_zebra_eval.sh` and the `chat_zebra_llama.py` default follow the same directory, so convert, evaluate and chat remain a working sequence.
- `modeling_zebra_llama.py`: the module docstring claimed a Mamba mixer and a "Megatron-shaped simplified implementation (not the full SSM scan)" that the file does not contain. It now describes the KDA, MLA and MLP stack, names the converters for the other mixers, and records why the `mamba_*` config fields are kept.

## Note on the Copilot finding in #1167

Copilot reported that the converter "writes an incorrect architecture description (KDA) into the generated HF README for Mamba+MLA Zebra checkpoints," and suggested deriving the description from the mixer. That diagnosis is inverted: the `KDA` string is correct for every checkpoint this converter can legitimately produce, because the paired model only builds KDA blocks. The defect is upstream of it, in the wrapper that supplied a Mamba checkpoint, which is what this PR fixes. Deriving `arch_desc` from the mixer would have papered over the mismatch by making the model card describe weights the model cannot represent.

## Validation

- no references to the old `zebra_mamba_1B_hybrid_hf` output remain; all four call sites now name one directory
- `zebra_llama_kda_1B_BF16-pretrain.yaml` exists for both MI355X and MI300X
- `bash -n` on both wrappers, `py_compile` and `black --check` on both Python files
- no functional change to the converter or the model
