# fix(sft): align the unpacked SFT loss mask with the shifted labels

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1351) · state: open · merged: False

## Original PR description

## What

`tokenize_formatted_sft_sample` (the unpacked SFT path, the default when sequence packing is off) shifts `labels` to next-token targets (`labels[i] = input_ids[i+1]`), but leaves `loss_mask` on **input** positions. The SFT loss is `CE(logits[i], labels[i]) * loss_mask[i]`, so the mask is off by one:

- the **first response token is never a target**;
- the **token after the response is**. With no EOS appended, that token is the pad id.

For tokenizers without a pad token, pad falls back to EOS, which hides the bug (Mistral, SmolLM3). Models with a **dedicated pad token** are trained to emit it after every answer: phi-4 (`<|dummy_85|>`) and granite-4.1 (`<|pad|>`).

This PR shifts the mask to label positions (`loss_mask[i] = supervised[i+1]`, last position 0) in both branches of the function. The packed path (`packing.py`) already does this, and so does Megatron-Bridge (`loss_mask = item["loss_mask"][1:]`).

## How it was found

We ran a convergence check that fine-tunes from the released checkpoint on alpaca-cleaned (Alpaca formatter, packing off, seq 1024, global batch 16). It compares the iteration-1 loss with the mean loss of the same model in `transformers` on the same alpaca prompts, scoring only the response tokens.

| Model | Pad token | Iteration-1 / reference |
|---|---|---|
| Mistral-7B-v0.3 | none (falls back to EOS) | 0.94–1.03 |
| SmolLM3-3B-Base | none (falls back to EOS) | 1.05–1.14 |
| phi-4 | `<|dummy_85|>` | 1.18–1.28 |
| granite-4.1-3b | `<|pad|>` | 1.23–1.28 |

The ranges cover runs at 1, 2, 4 and 8 GPUs. The loss curves themselves fall normally, so nothing else looked wrong.

## Tests

`test_tokenize_formatted_sft_sample_targets_exactly_the_response_tokens`, for both `bridge_compat_inline_bos` settings, with a tokenizer whose pad id differs from EOS:

- the scored targets (`labels[loss_mask == 1]`) are exactly the response tokens, in order, plus the appended EOS on the Bridge-compatible path;
- the pad id is never a target;
- the last position is masked.

Before the fix the test reads `[response[1:]..., pad]`; after it, `[response...]`.

`pytest tests/unit_tests/backends/megatron/test_sft_abstractions.py tests/unit_tests/backends/megatron/test_sft_dataset_offline.py tests/unit_tests/backends/megatron/test_messages_format.py`: 17 passed (CPU).

## Stop token

The default unpacked path now appends a supervised EOS after a supervised response, as the `bridge_compat_inline_bos` path already does, so every tokenizer learns to stop. Before, only tokenizers whose pad resolved to EOS trained a stop token, and only by accident of the misaligned mask. The packed default path (`packing._tokenize_no_pad`) still appends no EOS. That predates this PR and is left for a follow-up.

## Follow-up

We will re-run the phi-4 and granite fine-tuning checks with this change and post the iteration-1 ratios here.
