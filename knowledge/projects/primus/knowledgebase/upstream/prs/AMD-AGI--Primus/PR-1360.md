# perf(megatron): Triton router and MegaMoE wgrad fusion for DSv3 on MI455X

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1360) · state: closed · merged: False

## Original PR description

## Summary

Faster DeepSeek-V3 training on MI455X (gfx1250). No default path of another model changes: the router GEMMs are opt-in, the MegaMoE wgrad fusion applies to bf16 MegaMoE experts under Megatron DDP, and the example changes stay in the MI455X DeepSeek-V3 example, which now runs MegaMoE by default. The MegaMoE wgrad fusion uses the companion Primus-Turbo PR (AMD-AGI/Primus-Turbo from `lhzhang333:dev/lhz/dsv3_opt_merge`); with an older Primus-Turbo, Primus keeps DDP's separate add. Two fixes reach other setups that were broken: grouped-linear wgrad fusion with a backend that cannot accumulate, and NUMA binding on a subset of the GPUs.

## Changes

- **Router**: opt-in Triton GEMMs for the FP32 router (`moe_router_triton_gemm`), as accurate as Megatron's FP32 path; unsupported shapes keep Megatron's path.
- **MegaMoE**: bf16 expert wgrads accumulate into `main_grad` (`turbo_mega_moe_wgrad_accum_fusion`; null follows `gradient_accumulation_fusion`). Off under Megatron-FSDP, which clears `grad_added_to_main_grad` before every backward, and for mxfp8 experts, whose stages keep DDP's add.
- **Grouped linear**: the wgrad fusion of `PrimusTurboGroupedLinear` stays on only where the BF16 wgrad backend can add into `main_grad` (no backend set, or Triton / hipBLASLt). A grouped GEMM pinned to FlyDSL or CK, or auto-tuned, keeps DDP's add: a pinned backend raises rather than fall back, and auto-tune in Primus-Turbo builds so far tunes the accumulating wgrad on `main_grad` itself.
- **Runner**: `numa_bind.sh` binds each rank to the NUMA node of the GPU it uses (`HIP_VISIBLE_DEVICES` / `ROCR_VISIBLE_DEVICES` mapped), and runs unbound when the node is unknown instead of failing.
- **MI455X DeepSeek-V3 example**:
  - `gradient_accumulation_fusion`, Triton router GEMMs, routing on TE's fused kernels with the expert bias, no dataloader attention mask, NUMA binding and 4 hardware queues;
  - MegaMoE by default: the launcher's `USE_TURBO_MEGA_MOE=auto` turns it on when the Primus-Turbo in use has the gfx1250 MegaMoE kernels (the image's predates them, so its runs keep the token dispatcher);
  - README updated.

## Testing

- Unit tests of the changed modules pass on MI455X.
- 4× MI455X against main (Primus db5fe1fd + Primus-Turbo ff4898e4); ms/iter is Primus's average over iterations 3–10, the mean of 2 runs alternating with main (3 for Llama); loss and grad norms within run-to-run noise:
  - DeepSeek-V3 proxy with MegaMoE (the example's new default): 995.2 → 929.2 ms/iter (−6.6%), +7.1% throughput.
  - DeepSeek-V3 proxy without MegaMoE: 1094.8 → 1060.8 ms/iter (−3.1%), +3.2% throughput.
  - gpt-oss 20B and Llama 3.1 8B: same speed (2104.2 → 2103.2 and 1053.4 → 1050.9 ms/iter); gpt-oss loss and grad norm bitwise identical (lm loss 11.50698 at iteration 10 and the grad norms of iterations 1–10, in all 4 runs).
- With the image's Primus-Turbo, the example's default run keeps the token dispatcher and finishes.

**1. 🟠 Should fix: Stale clip plan could scale non-gradient memory: this PR keys the plan cache without stride or contiguity**

`contiguous_runs()` keys `_PLANS` on `(data_ptr, numel, dtype, device)` only. On a cache hit, `_runs` checks only that each run fits in its storage; it does not re-check contiguity. A non-contiguous view at a cached address with the same `numel` therefore reuses the old run: a stride-2 `buf[0:20:2]` gets the cached 20-element run, while a fresh `_plan` returns `()`. In the patched clip path the gradients are contiguous DDP-buffer views, so this case does not arise today. Adding `g.is_contiguous()` (or the stride) to the key would make the cache robust.

**Who is affected:** Only a caller that passes a non-contiguous gradient at the same address and size as an earlier contiguous one; Megatron DDP/`decoupled_grad` training on gfx1250 does not do this.

_Checked against the code by an independent pass._

**2. 🟠 Should fix: bf16 MegaMoE expert grads could be double-added by DDP: this PR enables wgrad fusion by default**

With `turbo_mega_moe_wgrad_accum_fusion: null` and `gradient_accumulation_fusion: true`, bf16 MegaMoE experts pass `fuse_wgrad_accum_pattern="megatron"` whenever Turbo's staged ops accept it.
