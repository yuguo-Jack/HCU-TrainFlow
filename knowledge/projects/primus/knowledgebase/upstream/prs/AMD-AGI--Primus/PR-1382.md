# fix(primus_turbo): import Primus-Turbo after its envs refactor

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1382) · state: open · merged: False

## Original PR description

## Summary

Primus-Turbo main (AMD-AGI/Primus-Turbo#605) removed `primus_turbo.common.constants`. `primus/backends/megatron/core/extensions/primus_turbo.py` imported the names of the GEMM backend variables from it, so with that Primus-Turbo (e.g. a `TURBO_DIR` checkout of its main) every Turbo extension fails to import, and a run that asks for one stops with "PrimusTurbo attention was requested, but primus_turbo is not importable". The image's Primus-Turbo predates #605, so CI does not see it.

## Changes

- `turbo_gemm_backend` / `turbo_grouped_gemm_backend` are published through `primus_turbo.common.envs.set_env()` when Primus-Turbo has it: since #605 Primus-Turbo caches each variable at its first read, and `set_env()` also drops that cached value. Older Primus-Turbo keeps the plain `os.environ` write.
- `tests/unit_tests/backends/megatron/test_primus_turbo_backend_env.py`: reads each backend once, then checks that `GlobalBackendManager` sees the value Primus publishes (a plain `os.environ` write fails this on Primus-Turbo since #605), that `default` publishes nothing, and that Primus uses `envs.set_env()` when Primus-Turbo has it (skipped on older Primus-Turbo, as in CI).

## Testing

On MI455X (`amdprimus/amdprimus:tas-20261019`):

- DeepSeek-V3 proxy with Primus-Turbo main (c145c458), which failed to start before:
  - 4 GPUs, with and without MegaMoE (2 runs each).
  - 1 GPU (EP1, where the experts run the grouped GEMM): with `bf16:flydsl` the forward and the wgrad run on the FlyDSL grouped GEMM kernels (profiler trace); with `TURBO_GROUPED_GEMM_BACKEND=default` they run on the Triton ones.
- With the image's Primus-Turbo (21588d59, no `primus_turbo.common.envs`) the import falls back to `os.environ`. The 1-GPU proxy's lm loss and grad norms match `main` at every iteration (20 iterations, 2 runs each).
- Llama 3.1 8B (4 layers, 1 GPU, `--use_turbo_gemm True`): `--turbo_gemm_backend triton` takes effect with Primus-Turbo main too. With the image's Primus-Turbo, lm loss and grad norms match `main` at every iteration.
- Unit tests that import the Turbo extension (8 files): 36 passed, 10 skipped (gfx950-only and 8-GPU cases) on this branch with Primus-Turbo main and with the image's, the same as `main` with the image's. On `main`, Primus-Turbo main makes them fail at collection.
- The new test passes with Primus-Turbo main (c145c458), ff4898e4 and the image's 21588d59 (the `set_env` case is skipped on the last two). With a plain `os.environ` write instead, three of its cases fail on Primus-Turbo main.

#### 1. 🟠 Should fix: CI never runs the new `set_env` path: this PR targets Turbo #605 but pinned commit lacks `common.envs`
`.github/workflows/ci.yaml:50`

CI pins `PRIMUS_TURBO_COMMIT` d04ffd9b, which has `primus_turbo/common/constants.py` but no `common/envs.py`; the rocm/primus image's Turbo 0.2.0 has no `primus_turbo.common` at all. So every tested environment takes the `os.environ` fallback, and the new `set_env` path for post-#605 Turbo (the reason for this PR) is not exercised. The fallback behaves exactly like the base code, so nothing regresses at the current pin; this is a coverage gap. Bump the pin to a commit containing Primus-Turbo#605 when it lands, or add a unit test that covers the `set_env` import path.

**Who is affected:** Only maintainers relying on CI to validate the post-#605 Primus-Turbo path; users on the pinned Turbo see base behaviour.

**2. Turbo backend state may leak across tests: `monkeypatch.delenv` doesn't clear post-#605 Turbo's env cache** (`tests/unit_tests/backends/megatron/test_native_fp8_layout.py:112`)

`test_native_fp8_layout.py`, `test_primus_turbo_mxfp4_local.py` and `test_flux_mxfp4_local_spec.py` clear `PRIMUS_TURBO_GEMM_BACKEND` via `monkeypatch.delenv`. With post-#605 Turbo, a cached value survives the delenv, and conftest has no `envs.reset_cache()`, so backend state leaks across tests. The empty-value workaround and the `fp8_training.md:378` docs are now stale; add a `reset_cache` fixture or use `set_env(..., None)` when `envs` exists.

_An independent check of the code found this probably does not apply: The diff only changes primus_turbo.py; CI pins Primus-Turbo d04ffd9, whose primus_turbo.common.constants the base already imports, and the installed primus_turbo has no common package, so the post-#605 cache cannot be checked here. The fixtures delenv only an empty value, which the candidate itself says post-#605 Turbo reads as None (same as unset), and the MXFP4 fixture monkeypatches GlobalBackendManager._gemm_backend directly, so no backend state leaks through them._

**3. Turbo auto-tuning can stay off despite `use_turbo_autotune=True`: auto-tune env write still bypasses `set_env`** (`primus/backends/megatron/patches/args/rocm_arg_validation.py:161`)

`validate_args_on_rocm` still writes `os.environ['PRIMUS_TURBO_AUTO_TUNE']='1'` directly, while this PR moves the GEMM-backend writes to Turbo's `set_env`. With upstream Primus-Turbo after #605, `envs.PRIMUS_TURBO_AUTO_TUNE` is cached at first read, so this write is ignored if Turbo already read the variable in the same process. On the training path this runs during `validate_args`, before any Turbo dispatch; on the pinned Turbo (`d04ffd9`, no `envs.py`) the variable is read from `os.environ` on every call. Routing this write through `_set_turbo_env` would make the migration consistent. `PRIMUS_TURBO_ODC_GDA_PIPE` is read by the C++ kernel via `getenv`, so `set_env` would not change anything there.

**Origin:** latent

**Who is affected:** Only `use_turbo_autotune=True` runs on a Turbo build with `envs.py`, in a process where Turbo read `PRIMUS_TURBO_AUTO_TUNE` before Megatron argument validation.

_Checked against the code by an independent pass._

**4. A typo in the hard-coded GEMM env-var names would silently drop backend selection on old Turbo** (`primus/backends/megatron/core/extensions/primus_turbo.py:238`)

The PR replaces the library constants with the literals `"PRIMUS_TURBO_GEMM_BACKEND"` and `"PRIMUS_TURBO_GROUPED_GEMM_BACKEND"`, each used once. Both match the values in `primus_turbo.common.constants` at the CI pin. New Primus-Turbo's `envs.set_env` takes the variable name string and rejects undeclared names through `_check_declared`, so a misspelt name errors there. Only the `os.environ` fallback, used with older Turbo, would silently write a misspelt name. Optionally, have the fallback import `ENV_GEMM_BACKEND`/`ENV_GROUPED_GEMM_BACKEND` from `primus_turbo.common.constants`, as #997 did.

**Who is affected:** Nobody today: the literals are correct. It only matters for a future edit to these strings on the old-Turbo fallback path.

_Checked against the code by an independent pass._

**5. Style: new `set_env` compat import placed mid-module, away from the other Turbo compat imports** (`primus/backends/megatron/core/extensions/primus_turbo.py:223`)

The `try: from primus_turbo.common.envs import set_env` block sits after `_bridge_activation_grad`. The other Turbo compat try/except imports are grouped at lines ~45-68, and this import runs at module load anyway. Move it next to them, where the removed `common.constants` import was.

**Who is affected:** Readers and maintainers of `primus_turbo.py`; there is no runtime effect.
