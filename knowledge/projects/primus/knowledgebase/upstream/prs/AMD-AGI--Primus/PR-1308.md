# refactor(megatron): build Primus model families from one registry

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1308) · state: open · merged: False

## Original PR description

## Summary

Adding a Megatron model family to Primus meant three edits that had nothing family-specific in them: a new branch in `get_model_provider`, another in `MegatronPretrainTrainer.train()`, and a `<family>_builders.py` that repeated the config construction, the config-class check, spec resolution, the GPTModel-style constructor arguments and `model_provider` of every other family. Kimi K3, GLM5-Next, DeepSeek-V4 and ZAYA1 each carried their own copy, and Inkling (#1256) was added the same way while this PR was open.

This PR replaces the branches with a registry and the copies with one builder. A new family is now one `MODEL_FAMILIES` entry plus its own config, spec and model code:

```python
"kimi_k3": ModelFamily(
    package="primus.backends.megatron.core.models.kimi_k3",
    config_class="kimi_k3_transformer_config:KimiK3TransformerConfig",
    model_class="kimi_k3_model:KimiK3Model",
    decoder_spec="kimi_k3_layer_specs:get_kimi_k3_runtime_decoder_spec",
    model_kwargs="kimi_k3_builders:kimi_k3_model_kwargs",
    check_model="kimi_k3_builders:check_kimi_k3_model",
),
```

A family whose model does not take GPTModel-style arguments names its own builder instead, and still gets the shared provider, wiring and schema check:

```python
"inkling": ModelFamily(
    package="primus.backends.megatron.core.models.inkling",
    builder="inkling_builders:inkling_builder",
    config_class="inkling_transformer_config:InklingTransformerConfig",
),
```

No model changes: every family builds the same modules with the same arguments as before (see Results).

## Changes

- **`core/models/registry.py` (new):** `MODEL_FAMILIES` maps each `model_type` to its config class, model class, decoder spec, training entrypoint (`pretrain_gpt`, or for `mamba` `pretrain_hybrid` with `pretrain_mamba` as `legacy_training` for Megatron-LM before core 0.19, where `pretrain_mamba.py` became a bare forwarder) and optional hooks: `prepare_args` (before the config is built), `model_kwargs` (extra constructor arguments) and `check_model` (after construction). References are `"module:attr"` literals resolved on first use, so importing the table imports no model code. Upstream `gpt` and `mamba` entries name Megatron's own builders. A Primus entry may also name its own `builder` (Inkling); it still names its `config_class` so `schema_check` covers its keys.
- **`core/models/builder.py` (new):** one `build_model` and one `model_provider` for the Primus-owned families.
  - `build_model` runs `prepare_args`, builds the config, asserts that `core_transformer_config_from_args` kept the family's config class and that `use_legacy_models` is off, honors `args.spec`, and passes the common constructor arguments. It refuses families that name their own builder.
  - `model_provider` matches Megatron's, including the OOM observer that dumps a memory snapshot under `record_memory_history`, but leaves out its ModelOpt builder swap, which would replace the Primus model with a GPT one. Unlike Megatron's, the OOM snapshot keeps `memory_snapshot_path`'s directory and prefixes only the file name (`snapshots/oom_rank-3_memory.pickle`, not `oom_rank-3_snapshots/memory.pickle`).
  - `family_model_provider(builder)` gives each family package a `model_provider` whose `model_builder` defaults to that family's builder.
- **Family builders:** each keeps only its own logic as hooks:
  - DeepSeek-V4: the sink-attention and Turbo DeepEP args plumbing (same order, still before the config is built) and its RoPE arguments.
  - ZAYA1: the data-parallel-only, MLA and RoPE checks, with their messages.
  - Kimi K3: the latent MoE width report and assertion.
  - GLM5-Next: no hooks.
  - Inkling: keeps `inkling_builder` unchanged. `InklingModel` takes `decoder_spec` rather than `transformer_layer_spec` and swallows unknown arguments, and `build_inkling_model` is shared with the converter and the meta-device tests, so it is not folded into `build_model`.

  `<family>_builder` and `model_provider` stay importable and callable as before: `<family>_builders.model_provider(pre_process=..., post_process=...)` still builds that family when `model_builder` is omitted or `None`.
- **`import_utils.get_model_provider`:** looks the family up and binds the Primus `model_provider` to the family's own builder if it names one, else to `build_model`. Upstream families keep the cross-version `lazy_import` fallback (`model_provider` + builder, else the bare provider). An unregistered `model_type` raises and lists the registered ones.
- **Trainers:** `MegatronPretrainTrainer.train()` gets `forward_step` and the datasets provider from the family's training entrypoint (`_get_training_components`). The seven-way if/elif chain is gone (one `GPT_TRAINING` constant now names the default entrypoint), and the `is_distributed = True` fix for the TP > 1 dataset deadlock is kept with its explanation. `setup_model_only` and the SFT trainer call `get_model_provider(model_type=...)` uniformly.
- **`schema_check`:** reads the `model_type` to config-class map from the registry's AST instead of parsing `get_model_provider`'s `if` branches and following each builder's `core_transformer_config_from_args(config_class=...)` call.
- **Log tags:** family logs are tagged with the `model_type` (`[Primus:kimi_k3]`, `[Primus:deepseek_v4]`, `[Primus:glm5_next]`, `[Primus:zaya1]`, `[Primus:inkling]`), the same value the YAML sets.

### Behavior changes

- DeepSeek-V4 and GLM5-Next now also fail fast if `core_transformer_config_from_args` swapped their config class (`multi_latent_attention` or `heterogeneous_layers_config_path` set). Kimi K3 and ZAYA1 already did. Every DeepSeek-V4 and GLM5-Next config leaves both unset.
- `get_model_provider` raises `ValueError` on an unregistered `model_type` instead of building `gpt`, so a misspelt family (`kimi-k3`) no longer trains a different model. The diffusion trainers, whose `model_type: diffusion_model` is not registered, set their own `model_provider` and still get their `forward_step` and datasets provider through the `gpt` training entrypoint.
- With `record_memory_history` on, Primus families now also dump a memory snapshot on OOM, as `gpt` and `mamba` runs already did. Inkling's old provider ignored `record_memory_history` entirely; it now records memory history like the other families.
- Log tags change from `[Primus:Kimi-K3]`, `[Primus:DeepSeek-V4]`, `[Primus:GLM5-Next]`, `[Primus:ZAYA1]` and `[Primus:Inkling]` to the `model_type` form above. Nothing in the repo matches on the old text.

## Results

## Testing

- **New tests:** `tests/unit_tests/backends/megatron/test_model_registry.py`:
  - every registry entry is a literal that `schema_check` can read, and `schema_check` returns the registered config classes;
  - every entry is upstream, Primus with its own builder, or built by the shared builder; every Primus family's references resolve, its `<family>_builder` name points at the shared builder or at the builder its entry names, and its `model_provider` defaults to that builder (omitted, `None`, or overridden);
  - `get_model_provider` wiring for shared-built families, families with their own builder (Inkling) and upstream families (with and without a builder module), and the `ValueError` for unregistered values;
  - every `model_type` string the Megatron backend compares against (patch gates, trainers) is a registered family or `diffusion_model`, so a renamed family cannot silently disable its patches;
  - `build_model`'s hook order, `args.spec` override, given config, and the config-class, legacy-model and own-builder assertions (`gpt`, `inkling`);
  - `model_provider` forwarding, memory-history recording and the OOM snapshot, with and without a directory in `memory_snapshot_path`;
  - family packages that need a GPU to import (DeepSeek-V4, GLM5-Next) skip on GPU-less runners instead of failing.
- **Updated tests:** the trainer, SFT trainer, ZAYA1 and Inkling wiring and `schema_check` tests now assert the registry contract; the `schema_check` fixture is a fake registry instead of a fake `get_model_provider`. The pretrain trainer tests now cover `_get_training_components`: `mamba` takes both components from `pretrain_hybrid` (core 0.19+) or `pretrain_mamba` (older) with `is_distributed` set, a missing entrypoint names every candidate, and GPT-trained families (`gpt`, `kimi_k3`, `inkling`, `diffusion_model`, unset) use the overridable methods.
- **Unit tests:** the affected suites (registry, `schema_check`, `import_utils`, pretrain / SFT trainer, diffusion, ZAYA1, DeepSeek-V4 attention and DeepEP dispatcher, Kimi K3, GLM5-Next, Inkling) pass on MI300X after merging `main` with Megatron-LM core_v0.19.2 (4b4acac9): 575 passed, 57 skipped. The registry change was first checked on MI355X.
- **End to end:** the runs in Results, plus Kimi K3 rerun from the rebased branch (846,762,160 parameters, iteration-1 loss 12.34732, within noise).
- **Lint:** `pre-commit run` on the changed files passes.

**7. Config validation uses bare asserts; isinstance check newly enforced with misleading message** (`primus/backends/megatron/core/models/builder.py:31`)

`build_model` validates the config class, `use_legacy_models` and the family kind with `assert`, which `python -O` strips. The `isinstance(config, config_class)` check is newly applied to `deepseek_v4` and `glm5_next`, and its message always blames `multi_latent_attention`/`heterogeneous_layers_config_path`. Consider raising explicit exceptions and making the message accurate.

**Related past reviews:** [#947](https://github.com/AMD-AGI/Primus/pull/947) on `primus/backends/megatron/patches/kimi_k3_flops_patches.py`

**8. Primus families now go through overridable GPT dataset and forward hooks** (`primus/backends/megatron/megatron_pretrain_trainer.py:135`)

`deepseek_v4`, `kimi_k3`, `glm5_next` and `zaya1` previously imported `pretrain_gpt` components directly and always set `is_distributed=True`. They now route through `self.get_forward_step()`/`get_datasets_provider()`, so a subclass override can silently replace their data path and leave `is_distributed` False, risking the TP>1 deadlock. Confirm this is intended, or keep the direct path for these families.

**9. Registry references are inconsistently resolved and never validated** (`primus/backends/megatron/core/models/registry.py:9`)

The docstring says every reference is a `module:attribute` string relative to `package`, but `training` is a bare absolute module and the upstream builder path is split by hand in `import_utils`. A ref with no `:` or an empty ref fails with obscure errors, and nothing enforces 'builder XOR config_class+model_class' at definition time. Validate entries in `__post_init__` and route all refs through `resolve()`.

**Related past reviews:** [#440](https://github.com/AMD-AGI/Primus/pull/440) on `primus/backends/megatron/training/mlflow_artifacts.py`

**10. Internal registry hook functions added to public __all__ lists** (`primus/backends/megatron/core/models/kimi_k3/kimi_k3_builders.py:25`)

The per-family `__all__` lists now export hook functions such as `prepare_deepseek_v4_args`, `kimi_k3_model_kwargs`, `check_kimi_k3_model` and `zaya1_model_kwargs`. The registry reaches them by string reference, so exporting them only widens the public surface.

_Verified by running it._

**12. Stdlib importlib imported locally inside a method** (`primus/backends/megatron/megatron_pretrain_trainer.py:130`)

`_get_training_components` does a function-local `import importlib`. As a stdlib module it carries no import cost or cycle risk, so it belongs with the module's top-level imports.

`"pretrain_gpt"` is both the `ModelFamily.training` default and the value `_get_training_components` compares against to pick the overridable path. Renaming one copy would silently send GPT-like families down the other branch. Define a single constant in `registry.py` and use it in both places.

**1. 🟠 Should fix: Unregistered model_type falls back to GPT in one lookup but raises in another**

`get_model_family()` silently falls back to the `gpt` family for an unknown `model_type`, while `get_model_provider()` repeats the lookup inline and raises `ValueError`. A typo such as `kimi-k3` therefore gets `pretrain_gpt` training components without error, and a subclass that supplies its own `model_provider` will train with GPT components silently. Put one lookup policy in `registry.py` (e.g. `get_model_family(model_type, strict=...)`) and have both callers use it.
