# [CP] perf(megatron): tune MI300X GPT-OSS-20B and Llama 70B pretrain configs (#1329)

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1332) · state: closed · merged: True

## Original PR description

Tuned on one 8x MI300X node with the primus_ci_655d58f_20261026 image. Tokens/s/GPU over 20 iterations, before = the release/v26.9 configs:

  config              before   after
  gpt_oss_20B  BF16    11497   13730
  gpt_oss_20B  FP8     12232   14797
  llama3.1_70B BF16      799     805
  llama3.1_70B FP8       OOM    1184
  llama3.3_70B BF16        -     804
  llama3.3_70B FP8         -    1186

GPT-OSS-20B (BF16 and FP8):
- Run the Turbo grouped GEMM on hipBLASLt; the default Triton backend is slower on MI300X.
- Enable TE fused cross entropy, RoPE fusion, Turbo RMSNorm and gradient accumulation fusion.
- Enable the fused activation-with-probs on sync-free stage 2; stage 3 itself OOMs on 192 GB.
- Raise turbo_deepep_num_cu from 64 to 160.

Llama 3.1 / 3.3 70B (BF16 and FP8):
- Comment out PYTORCH_HIP_ALLOC_CONF=expandable_segments:True, which cannot run on hosts with older amdgpu drivers.
- Use TE attention instead of Turbo attention.
- FP8: MBS 1, GBS 48, recompute 72 layers. Without expandable segments MBS 3 OOMs and MBS 2 leaves under 1 GB of device memory free.
- Carry over the release/v26.9 settings from #1307 that main lacked: GPU_MAX_HW_QUEUES=4, 20 iterations, BF16 MBS 2 / GBS 16 / recompute 76, and fused cross entropy for llama3.3.

🟠 Should fix **[PR Pundit]**

PYTORCH_HIP_ALLOC_CONF=expandable_segments:True is commented out in all four MI300X llama 70B configs, and no reason is given in the YAML (perf regression? driver hang? probe failure?). The new MBS comments depend on this change. It forces the FP8 configs from MBS=3 down to MBS=1, a large per-step efficiency loss. The project's own runner hook (runner/helpers/hooks/05_check_expandable_segments.py) and rocm_arg_validation both treat expandable segments as the recommended setting. The reason should be documented in a comment, or the line deleted; otherwise this is a regression dressed as tuning.

**Evidence:** diff of the 4 llama files; read 05_check_expandable_segments.py and warn_turbo_grouped_gemm_without_expandable_segments in rocm_arg_validation.py

🔵 Minor **[PR Pundit]**

The comment "stage 3's fused activation; stage 3 itself OOMs on MI300X" is misleading. It explains where the flag comes from, not why it is safe or faster here. use_turbo_fused_act_with_probs is an independent flag, used here with stage 2, that stage 3 merely auto-enables. It requires glu_linear_offset == 0, no activation_func_fp8_input_store, and a gated silu/gelu activation; otherwise PrimusGroupedMLP raises at runtime. Real GPT-OSS uses a clamped swiglu with an offset, so a more faithful preset would break it. Under fp8: hybrid with sync-free stage 2, moe_router_padding_for_quantization is auto-set True, so the fused kernel receives padded tokens_per_expert and probs. This combination is untested, and the MI355X sibling does not enable it. Both BF16 and FP8 configs are affected.

**Evidence:** Read primus/backends/megatron/core/transformer/experts.py:179-203.
