# fix(configs): fix JAX v26.9 OOMs (MI300X wan2.1_1.3b, MI355X mixtral_8x7B fp8) and tune MI300X flux_dev

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1337) · state: closed · merged: True

## Original PR description

## Summary

Config-only fixes for the v26.9 JAX image (`utd/ci:jax_ci_314ee8c_20261026_maxdiffusion`). Two configs ran out of memory and one ran below its throughput target.

| Config | Before | After | Target |
|---|---|---|---|
| MI300X `maxdiffusion/wan2.1_1.3b-pretrain` | OOM at step 0 | 7.90 frames/s/device | 5.7 |
| MI300X `maxdiffusion/flux_dev-pretrain` | 5.21 images/s/device | 6.00 images/s/device | 5.3 |
| MI355X `maxtext/mixtral_8x7B-fp8-pretrain` | OOM (needs 285.9 GB, pool is 276.5 GB) | ~267 GB estimated, same tokens/s/device | — |

## Changes

### MI300X `wan2.1_1.3b-pretrain.yaml`

- **`remat_policy: CUSTOM`** keeps the attention inputs and outputs: Q/K/V, `attn_output`, and `context`, which is TransformerEngine's checkpoint name for the fused-attention output and softmax stats. Without remat, the 720x1280x85 step needs ~223 GiB. XLA's own rematerialization only gets it to 186 GiB, against a 173 GiB limit. With this policy, the 79,200-token attention is never recomputed; only projections, norms and the FFN are.
- **`NVTE_CK_IS_V3_ATOMIC_FP32: "1"`** (fp32 dQ atomics). On gfx942 the bf16-atomic v3 attention-backward kernels have no padded-sequence variant. WAN's 79,200-token sequence isn't a multiple of the kernel tile, so it silently fell back to the generic CK-tile kernel. In a profile that kernel took ~70% of GPU time at ~230 TFLOP/s. The fp32-atomic `a32 psskddv` kernel covers this case, and the step drops from 14.8 s to 10.75 s. fp32 dQ accumulation is also more accurate. FLUX keeps `"0"`: its 1,536-token sequence is tile-aligned, and fp32 atomics measured 1.7% slower there.

### MI300X `flux_dev-pretrain.yaml`

- **`reuse_example_batch: True`**. A profile shows the train step's GPU work takes 1.33 s with or without reuse. Without it, every step adds a 239 ms gap with all GPUs idle:
  - MaxDiffusion's synthetic iterator generates ~540 MB of fp32 data on GPU 0, copies it to the host with `np.array`, and re-shards it back onto the GPUs.
  - `FluxTrainer` fetches each batch synchronously between steps (`WanTrainer` hides the same cost behind a prefetch thread).

  This is the setting MaxText's benchmarking guide recommends, and its GPU model configs ship with it on. Note that the number is not directly comparable with older FLUX results, which included the gap.

### MI355X `mixtral_8x7B-fp8-pretrain.yaml`

- **`per_device_batch_size: 11 → 10`** (global batch 88 → 80). Since the MaxText v26.9 bump (#1316), the batch-11 fp8 step compiles to 285.9 GB against the 276.5 GB pool (0.96 × 288 GB). Each sequence of batch costs ~21 GB, almost all of it activations saved for the backward pass. At the same shape, the OCP `fp8` path needs ~12 GB more than `nanoo_fp8`, which points at the v26.9 rewrite of the fp8 ops. Restoring batch 11 would need a MaxText change.

  Alternatives evaluated, at batch 11 unless noted:

  | Option | Memory, MI355X estimate | Throughput (MI300X proxy) |
  |---|---|---|
  | **Batch 10 (this PR)** | ~267 GB | +0.6% (within noise) |
  | Recompute Q/K/V (`remat_policy: custom`) | ~269 GB | −0.3% to −1.7% |
  | Offload `out_proj` to host | ~274 GB | −6.1% |
  | `num_vocab_tiling: 4` | ~285 GB | doesn't fit |

## Validation

All runs used the image above on 8x MI300X (`tw045`) through `tools/perf/run_batch.sh`.

- **wan2.1_1.3b / flux_dev:** the exact configs in this PR, run in catalog mode for 20 steps. Throughput is the harmonic mean over 16 post-warmup steps; run-to-run variation within each run was under 0.6%. No XLA rematerialization or allocator warnings.
- **mixtral_8x7B fp8:** I had no MI355X access, so this was validated on MI300X in two ways:
  - **Memory:** XLA's compile-time estimate for the exact MI355X config, with XLA's memory limit matched to MI355X (`XLA_FLAGS_APPEND=--xla_gpu_memory_limit_slop_factor=142`). The proxy reads 283.2 GB for the original config against 285.9 GB measured on MI355X, so I add ~2.7 GB to proxy numbers. This PR's config reads 264.9 GB.
  - **Throughput:** a 12-layer Mixtral-8x7B (`nanoo_fp8`, expert parallelism 8) at the real batch sizes. Batch 11: 17,029 tokens/s/device. Batch 10: 17,129 tokens/s/device.

**1. MI300X wan2.1_14b keeps a16 atomics and no remat, unlike fixed 1.3B config** (`examples/maxdiffusion/configs/MI300X/wan2.1_14b-pretrain.yaml:56`)

The PR switches MI300X `wan2.1_1.3b` to `NVTE_CK_IS_V3_ATOMIC_FP32: "1"` because gfx942 lacks a padded-seqlen a16 v3 backward kernel for the 79200-token sequence. The sibling MI300X `wan2.1_14b-pretrain.yaml` still sets `"0"`. It has the same 720x1280x85 synthetic shape, `cudnn_flash_te` attention and CK flags, so by the PR's own reasoning it may hit the slower generic backward fallback. Consider applying the same setting there for consistency; this is pre-existing and not measured for 14B. The remat concern does not apply: the 14B model yaml already sets `remat_policy: "FULL"`, unlike the 1.3B model's `"NONE"`.

**Who is affected:** Users running the MI300X wan2.1_14b MaxDiffusion example may see slower backward steps; no OOM follows from this.

**2. Cached example batch changes the benchmark methodology for MI300X flux_dev** (`examples/maxdiffusion/configs/MI300X/flux_dev-pretrain.yaml:100`)

`reuse_example_batch: True` makes `FluxTrainer` (via `load_next_batch`) reuse the first synthetic batch, so the ~13% per-step synthetic-batch generation cost drops out of MI300X/MI325X `flux_dev` timings. The MI355X `flux_dev` config and the model default (`False`) still regenerate every step. MI300X/MI325X and MI355X perf numbers therefore differ in method, and MI300X numbers are not comparable with runs before this PR. The data is synthetic random either way and the PR comment documents why; consider applying the same setting to MI355X or noting the methodology change in the perf results.

**Who is affected:** People comparing `tools/perf` `flux_dev` throughput between MI300X/MI325X (which run this file) and MI355X, or against earlier MI300X runs.

**3. Python-style `True` instead of lowercase YAML boolean** (`examples/maxdiffusion/configs/MI300X/flux_dev-pretrain.yaml:100`)

The new `reuse_example_batch: True` uses capitalized `True`, while the surrounding overrides use lowercase (`enable_profiler: false`). Use `true` for consistency.

**Who is affected:** Only readers of the MI300X `flux_dev-pretrain.yaml` config; no runtime effect.

**Related past reviews:** [#315](https://github.com/AMD-AGI/Primus/pull/315) on `examples/maxtext/configs/MI300X/grok1-pretrain.yaml`
