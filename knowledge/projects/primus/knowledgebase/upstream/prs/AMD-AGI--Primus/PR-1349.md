# [CP] perf(configs): tune MI355X FLUX.1-dev (JAX) and Mixtral 8x7B / DeepSeek-V2-Lite BF16 (Megatron); add FP8 MoE models to the perf catalog (#1348)

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1349) · state: closed · merged: True

## Original PR description

Cherry-pick of #1348 into `release/v26.9`. Config-only.

## Changes

- **MI355X `maxdiffusion/flux_dev-pretrain`:** `reuse_example_batch: True`. MaxDiffusion's synthetic data loader stalls every GPU between steps; this is the same fix #1338 made for MI300X (5.21 → 6.00 images/s/device there).
- **MI355X `megatron/mixtral_8x7B_v0.1-BF16-pretrain`:** `use_turbo_grouped_gemm: true` + `use_turbo_fused_act_with_probs: true`, and `turbo_deepep_num_cu: 64 → 160`.
- **MI355X `megatron/deepseek_v2_lite-BF16-pretrain`:** `turbo_deepep_num_cu: 64 → 160`.
- **`tools/perf/configs.yaml`:** adds `deepseek_v2_lite-FP8` and `mixtral_8x7B_v0.1-FP8` to the MI300X, MI325X and MI355X Megatron catalogs.

## Validation

Measured on an 8x MI300X proxy with `primus_ci_59003fd_20261028` on this branch's Megatron-LM: 16-layer Mixtral and 14-layer DeepSeek-V2-Lite at the MI355X micro-batch sizes, repeated runs.

| Config | Change | Peak memory |
|---|---|---|
| Mixtral 8x7B BF16 | +2.4% tokens/s/GPU | −0.8 GB |
| DeepSeek-V2-Lite BF16 | +2.1–2.4% tokens/s/GPU | +0.6 GB |

**3. FLUX MI355X throughput not comparable to earlier results: `reuse_example_batch` drops data generation from timing** (`examples/maxdiffusion/configs/MI355X/flux_dev-pretrain.yaml:92`)

The rationale cites figures measured on MI300X at batch 8 (~13% of step time), not on MI355X at batch 14, and those numbers will go stale in a config comment. `reuse_example_batch: True` also removes data generation and the host round-trip from the timed loop. That is a methodology change that makes throughput incomparable with earlier MI355X FLUX catalog results and makes the loss meaningless, so call it out explicitly and move the measurements to the PR body.

_An independent check of the code found this probably does not apply: The base `repo/examples/maxdiffusion/configs/MI300X/flux_dev-pretrain.yaml:95-100` already sets `reuse_example_batch: True` with the same rationale, added deliberately in #1338; the new MI355X comment labels the ~13% figure as measured on MI300X at batch 8. With `dataset_type: synthetic` the batches are random either way, so the loss was never meaningful; skipping data generation is the documented intent of the setting, not a hidden methodology change._

**4. Sync-free MoE comment misstates valid stages and recommends stage 2 while config uses stage 1** (`examples/megatron/configs/MI355X/mixtral_8x7B_v0.1-BF16-pretrain.yaml:94`)

The comment 'sync-free moe support stage 1-2' is wrong, since the validator accepts stages 0-3 (`if stage > 3 or stage < 0`). Its 'stage 2 is recommended' advice also contradicts `turbo_sync_free_moe_stage: 1`, now that turbo grouped GEMM (the prerequisite for stage 2) is enabled. Either switch to stage 2 or document why stage 1 is faster, in both the Mixtral and deepseek_v2_lite BF16 configs.

_An independent check of the code found this probably does not apply: At the base, `repo/examples/megatron/configs/MI355X/{mixtral_8x7B_v0.1,deepseek_v2_lite}-BF16-pretrain.yaml` already carry the same comment and `turbo_sync_free_moe_stage: 1` (64 example configs share the text), and the DeepSeek config already had `use_turbo_grouped_gemm: true`. The PR only flips grouped GEMM and fused act for Mixtral; `rocm_arg_validation.py` accepts 0-3 and requires grouped GEMM only for stage >1, so stage 1 stays valid and choosing it is a tuning choice, not a defect._

**5. Capitalised `True` boolean mixes with lowercase booleans in the FLUX config (style)** (`examples/maxdiffusion/configs/MI355X/flux_dev-pretrain.yaml:97`)

`reuse_example_batch: True` is capitalised, while the rest of the file uses lowercase booleans such as `enable_profiler: false`. Use lowercase `true` for consistency.

_An independent check of the code found this probably does not apply: YAML parses `True` and `true` as the same boolean, and the base MI300X sibling config already has `reuse_example_batch: True` at line 100. The maxdiffusion model presets (`flux_dev.yaml`, `wan2.1_*.yaml`) write `reuse_example_batch: False` and MaxText examples use capitalised booleans, so the PR follows the established convention for this key._

**Related past reviews:** [#315](https://github.com/AMD-AGI/Primus/pull/315) on `examples/maxtext/configs/MI300X/grok1-pretrain.yaml`

**6. Docs still recommend 64 or 80 CUs for ep8 after this PR set ~160 on MI355X** (`docs/06-developer-guide/backend-patch-notes.md:104`)

This PR changes the ep8 `turbo_deepep_num_cu` guidance to ~160 CUs on MI355X, but only in two configs. `docs/06-developer-guide/backend-patch-notes.md:104` and `docs/04-technical-guides/performance-tuning.md:102` still recommend '64 or 80 for ep8'. So do the other MI355X MoE configs, including `deepseek_v2_lite-FP8-pretrain.yaml`, which already sets `160` under the old comment. Consider noting in the docs that the ep8 value depends on the GPU (~160 on MI355X). Note that '32 for ep16-64' is enforced, not advice: `rocm_arg_validation.py` asserts `turbo_deepep_num_cu <= 32` when ep >= 16.

**Who is affected:** Users tuning DeepEP from the docs or the config comments on MI355X at ep8.

_Checked against the code by an independent pass._

**Related past reviews:** [#824](https://github.com/AMD-AGI/Primus/pull/824) on `production_docs/02-user-guide/training-recipes.md`

**7. MoE BF16 launches abort with `PRIMUS_EP>=16`: hard-coded `turbo_deepep_num_cu: 160` exceeds the 32 limit** (`examples/megatron/configs/MI355X/deepseek_v2_lite-BF16-pretrain.yaml:89`)

Both MI355X MoE BF16 configs fix `turbo_deepep_num_cu: 160` while `expert_model_parallel_size` is `${PRIMUS_EP:8}`. With `PRIMUS_EP>=16` and the default `TURBO` dispatch backend, the `turbo_deepep_num_cu <= 32` assertion in `rocm_arg_validation` fires at startup. The base value of 64 failed the same check, so this PR does not change when it fires. The assertion message and the config comment both name the fix. The value can be overridden on the CLI (`--turbo_deepep_num_cu 32`), and an env placeholder such as `${PRIMUS_TURBO_DEEPEP_NUM_CU:160}` would make it more convenient.

**Origin:** pre-existing

**Who is affected:** Users who run the MI355X deepseek_v2_lite or mixtral_8x7B BF16 example with PRIMUS_EP>=16 and the default TURBO DeepEP backend.

_Checked against the code by an independent pass._

**8. Mixtral 8x7B runs mislabelled in logs and W&B: configs reuse the 8x22B experiment name** (`examples/megatron/configs/MI355X/mixtral_8x7B_v0.1-BF16-pretrain.yaml:3`)

The `exp_name` default is `${PRIMUS_EXP_NAME:mixtral_8x22B_v0.1-pretrain}`, a copy-paste of the 8x22B name, and the BF16 config uses `wandb_project` 'Primus_DeepSeek_Pretrain'. Perf-suite logs and W&B runs are mislabelled, and BF16/FP8 runs may collide on output directories unless `PRIMUS_EXP_NAME` is set per run. Fix the default names.

**1. 🟠 Should fix: Mixtral 8x7B BF16 runs log an expandable-segments warning: this PR enabled turbo grouped GEMM without the allocator env**

Mixtral 8x7B BF16 now enables `use_turbo_grouped_gemm: true` but the recipe has no `env:` block setting `PYTORCH_HIP_ALLOC_CONF=expandable_segments:True`. As a result, `warn_turbo_grouped_gemm_without_expandable_segments` logs a rank-0 warning on every run unless the user exports the env. The warning says the stacked expert weights can raise peak reserved memory; no OOM at mbs 4 / seq 4096 has been shown. Most other MI355X grouped-GEMM recipes also omit the env. Consider adding it to the recipe's `env:` block if the extra memory headroom matters.

**Who is affected:** Users launching the MI355X Mixtral 8x7B BF16 example without exporting an allocator config.

_Checked against the code by an independent pass._

**2. 🟠 Should fix: Catalog understates Mixtral FP8 throughput: this PR lists untuned FP8 recipes beside tuned BF16**

The newly listed `mixtral_8x7B_v0.1-FP8` configs are much less tuned than their BF16 siblings. On MI355X the BF16 config (tuned in this PR) uses `use_turbo_grouped_gemm`, `use_turbo_fused_act_with_probs`, DeepEP with `turbo_deepep_num_cu: 160`, sync-free MoE and mbs 4 / gbs 256. On MI300X/MI325X the Mixtral FP8 configs have no Turbo/DeepEP block at all, while the BF16 siblings use DeepEP. The newly listed `deepseek_v2_lite-FP8` configs match their BF16 siblings' Turbo/DeepEP settings and are not affected.

**Who is affected:** Readers of the tools/perf report who compare the FP8 and BF16 Mixtral 8x7B rows on MI300X/MI325X/MI355X.
