# perf(mi355x): tune GPT-OSS 20B and DeepSeek V2 Lite pretrain configs

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1252) · state: closed · merged: True

## Original PR description

### Summary

Based on PR: https://github.com/AMD-AGI/Primus/pull/1247
Replaces the MI355X Megatron pretrain configs for GPT-OSS 20B and DeepSeek V2 Lite (FP8 and BF16) with tuned settings. With the real model vocab from #1249, stock vs tuned on the same node:

| Config | Stock tok/s/GPU | Tuned tok/s/GPU | Change | Peak HBM stock -> tuned |
| --- | --- | --- | --- | --- |
| gpt_oss_20B-FP8 | 30570 | 45754 | **+49.7%** | 277.9 GB (96.5%) -> 257.4 GB (89.4%) |
| gpt_oss_20B-BF16 | 30634 | 34353 | **+12.1%** | 266.7 GB (92.6%) -> 209.5 GB (72.8%) |
| deepseek_v2_lite-FP8 | 45963 | 52466 | **+14.1%** | 240.8 GB (83.6%) -> 237.9 GB (82.6%) |
| deepseek_v2_lite-BF16 (MLA on in both) | 41210 | 42309 | **+2.7%** | 257.7 GB (89.5%) -> 257.1 GB (89.3%) |

It also fixes the Turbo fused grouped MLP skipping DDP param-gather hooks, which silently trained on stale expert weights whenever expert data parallelism exceeds one. See "Fix" under Changes.

`deepseek_v2_lite-BF16` shipped with MLA off. This PR turns MLA on, which is the model's real attention. Against the previous MLA-off config (43761 tok/s/GPU, 91.8%), the new config is 3.3% slower, but that comparison is across two different architectures.

### Changes

**gpt_oss_20B-FP8-pretrain.yaml**
- `sink_sliding_window: 128` on even layers (the gpt-oss default). The old comment said the backend did not support it; it runs correctly on v26.8.
- Turbo grouped GEMM with the fused grouped MLP and fused activation (`moe_router_dtype: fp32`), fused QK RMSNorm+RoPE.
- Turbo DeepEP (160 CUs, no comm stream, `moe_shared_expert_overlap: false`), sync-free MoE stage 1, `turbo_fp8_permute`.
- `fp8_recipe: tensorwise` (required by `turbo_fp8_permute`).
- `ddp_num_buckets: 24`, `ddp_average_in_collective: true`.
- FlyDSL dense GEMM: `use_turbo_gemm: true`, `turbo_gemm_backend: "fp8:flydsl,fp4:flydsl,other:hipblaslt"`. The first run in a fresh container spends ~10 min compiling kernels; later runs reuse the cache.
- `env: PYTORCH_CUDA_ALLOC_CONF: "expandable_segments:True"` (faster and 1 point lower peak with the real vocab).
- `micro_batch_size: 12`, `global_batch_size: 96` (were 10 and 80; still one micro-batch per step). +2.9%, using the headroom the FP8 path frees.

**gpt_oss_20B-BF16-pretrain.yaml**
- `sink_sliding_window: 128` on even layers, fused QK RMSNorm+RoPE.
- Turbo DeepEP (`use_turbo_deepep: true`, 160 CUs, no comm stream, `moe_router_dtype: fp32`) replaces Megatron's all-to-all dispatcher, with `overlap_moe_expert_parallel_comm: false` (was `true`; DeepEP cannot run with it). Together: +6.1% and 49 GB less peak memory.
- `ddp_num_buckets: 24`, `ddp_average_in_collective: true`.
- Keeps TE cross-entropy and expandable segments from #1249.

**deepseek_v2_lite-FP8-pretrain.yaml**
- `fp8: hybrid` (was `e4m3`).
- Fused grouped MLP, fused activation, `turbo_fp8_permute`.
- `turbo_deepep_num_cu: 160` (was 64).
- `turbo_sync_free_moe_stage: 1` (was 2). Stage 2 sizes DeepEP's dispatch buffers for the worst case, which at MBS 14 costs more than the CPU sync it removes (~2% slower).
- `ddp_num_buckets: 24`, `ddp_average_in_collective: true`.

**deepseek_v2_lite-BF16-pretrain.yaml**
- `multi_latent_attention: true`, `apply_rope_fusion: false` (rope fusion is not supported with MLA).
- Turbo grouped GEMM on the FlyDSL backend with fused activation, replacing legacy grouped GEMM (+2.6% on its own).

**tests/trainer/test_megatron_trainer.py**: comment only. `test_turbo_grouped_gemm` described legacy grouped GEMM as the config default, which is no longer true.

**Fix: fused grouped MLP skipped DDP param-gather hooks** (`primus/backends/megatron/core/transformer/experts.py`, raised in review)
- The fused grouped MLP (`turbo_fused_grouped_gemm`) never calls `linear_fc1`/`linear_fc2`.forward. With `overlap_param_gather`, it therefore skipped their DDP forward-pre-hooks, which wait for the distributed optimizer to all-gather the expert weights. Whenever expert data parallelism exceeds one (multi-node, or EP < GPUs per node), the op read partly stale weights. Nothing errors and no NaNs appear; the loss just drifts. This also affects `qwen3_30B_A3B-FP8-pretrain.yaml` on `main`.
- `_prepare_fused_grouped_mlp_weights` now runs both linears' forward-pre-hooks before `prepare_weights()`, the same way the fused dense MLP does. A new unit test in `tests/unit_tests/backends/megatron/test_grouped_mlp.py` checks the order.
- DeepSeek V2 Lite FP8, 1 node, EP=4 (expert DP 2), 20 iterations:

| Run | lm loss @ iter 20 |
| --- | --- |
| overlap_param_gather on, before fix | 5.194 (diverges from iter 3) |
| overlap_param_gather on, with fix | 4.958 |
| overlap_param_gather off (reference) | 4.956 |

- 1-node EP=8 throughput is unchanged (tok/s/GPU before -> after): GPT-OSS 20B FP8 44586 -> 44523 (micro-batch 10), DeepSeek V2 Lite FP8 52466 -> 52541, Qwen3 30B A3B FP8 39570 -> 39543. Memory is the same, and the iteration-20 loss matches within noise. The BF16 configs do not use this path.

Measured and not adopted (NaN checks were kept on throughout):
- `check_for_nan_in_loss_and_grad: false`: +4.7% on GPT-OSS FP8 but -26% on BF16, and it removes a safety check.
- `grad_reduce_in_bf16`: at most +2%, lowers precision, and pushes GPT-OSS BF16 to 99.4% HBM.
- `gradient_accumulation_fusion`: -1% to -8% on GPT-OSS, flat on DeepSeek.
- `turbo_grouped_gemm_without_padding`: no effect in BF16 (padding only applies to FP8/FP4); in FP8 it needs sync-free stage 0 and gave no gain there.
- FlyDSL dense GEMM and Turbo RMSNorm on DeepSeek: about -1%. FlyDSL grouped GEMM backend on DeepSeek FP8: no change.
- GPT-OSS BF16 on DeepEP: sync-free stage 1 (+0.1%) and Turbo grouped GEMM on FlyDSL with the fused activation (+0.2%) are within noise. Micro-batch 10 was -1.0% at 87.4% HBM; micro-batch 12 was +0.8% at 99.7%.
- GPT-OSS FP8 micro-batch 14: +3.7%, but at 99.1% HBM.

### Loss (mock data, 20 iterations)

No NaN or skipped iterations in any run. The first-iteration loss matches ln(vocab) (12.30 for GPT-OSS, 11.60 for DeepSeek), confirming the real vocab is in use.

| Config | Stock iter 20 | Tuned iter 20 |
| --- | --- | --- |
| gpt_oss_20B-FP8 | 11.551 | 10.807 |
| gpt_oss_20B-BF16 | 11.411 | 10.695 |
| deepseek_v2_lite-FP8 | 4.574 | 4.555 |
| deepseek_v2_lite-BF16 (MLA on in both) | 4.453 | 4.445 |

DeepSeek tuned matches stock. GPT-OSS BF16 on DeepEP matches the previous all-to-all config to four decimals (10.6955). GPT-OSS FP8 now uses global batch 96 instead of 80, so its curve is not directly comparable with stock. GPT-OSS tuned decreases faster in both precisions; the sliding window is the shared change and alters the attention pattern, so this is not a like-for-like numerical comparison. A longer run on real data would be the right check of training quality.

### Notes for reviewers

- `gpt_oss_20B-FP8` changes `global_batch_size` from 80 to 96 along with micro-batch 12, so it is a small training hyperparameter change, not only a performance one.
- `tools/perf/configs.yaml` tracks `deepseek_v2_lite-BF16`, `gpt_oss_20B-BF16` and `gpt_oss_20B-FP8` on MI355X; their perf baselines will step up after this merges.
- `examples/megatron/guides/moe_package/start_training_dsv2_lite.sh` passes `--use_turbo_grouped_gemm False --moe_use_legacy_grouped_gemm True` on the command line, so it keeps the legacy grouped GEMM path but now runs with MLA on.

- Copilot · comment · 2026-10-14T18:39:08Z · [source](https://github.com/AMD-AGI/Primus/pull/1252#discussion_r4274801824)

File: `examples/megatron/configs/MI355X/gpt_oss_20B-FP8-pretrain.yaml` · line 37

Both this recipe and `deepseek_v2_lite-FP8-pretrain.yaml` enable fused grouped MLP while keeping `overlap_param_gather: true`. In `PrimusGroupedMLP._forward_with_turbo_fused_grouped_mlp()`, the direct `linear_fc1.prepare_weights()` and `linear_fc2.prepare_weights()` calls bypass the child modules' DDP forward-pre-hooks. When expert data parallelism exceeds one, weights can therefore be consumed or quantized before their parameter all-gather completes. Run those hooks before preparing weights, as the fused dense MLP implementation does, or disable both `turbo_fused_grouped_gemm` and its dependent `turbo_fp8_permute` in both recipes until synchronization is supported. The reported single-node EP=8 runs do not exercise this case.
