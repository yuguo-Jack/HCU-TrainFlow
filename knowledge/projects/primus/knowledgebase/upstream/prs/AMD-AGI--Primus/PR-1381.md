# fix(megatron): drop the shared expert from the GPT-OSS presets

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1381) · state: open · merged: False

## Original PR description

# Description

GPT-OSS has no shared expert, but the `gpt_oss_20B` and `gpt_oss_120B` Megatron presets set `moe_shared_expert_intermediate_size: 2880`. None of the MI300X, MI325X, MI355X or MI455X `gpt_oss_*` examples override it, so they all train an extra 2880-wide SwiGLU expert in every layer. For GPT-OSS-20B that adds about 0.6B parameters and 14% more compute per token compared with the published model and the competitor baseline ([AIMA-340](https://amd-hub.atlassian.net/browse/AIMA-340)).

This PR aligns both presets with the MLPerf GPT-OSS-20B recipe in `examples/mlperf/gpt_oss_20b`. That recipe overrides these fields explicitly, and its values match the Megatron-Bridge GPT-OSS bridge and the Megatron-LM GPT-OSS-20B test case:

| Field | Before | After |
|---|---|---|
| `moe_shared_expert_intermediate_size` | 2880 | null |
| `moe_shared_expert_overlap` | true (from `deepseek_v2_base.yaml`) | false |
| `ffn_hidden_size` | 10944 | 2880 |
| `rotary_base` | 10000 | 150000 |
| `moe_router_pre_softmax` | true | false |
| `moe_router_topk_scaling_factor` | 1.0 | null |
| `moe_router_load_balancing_type` | seq_aux_loss | none |
| `moe_aux_loss_coeff` | 0.001 | 0.0 |

Every layer is MoE, so `ffn_hidden_size` is never read. It is set to 2880 so the preset agrees with the HF config and the projection's built-in GPT-OSS spec. GPT-OSS-120B has the same architecture apart from depth and expert count, so it gets the same fix.

Megatron only counts shared-expert FLOPs when the shared expert exists. The reported TFLOP/s/GPU for these examples will therefore drop while tokens/s goes up. Compare against older runs with tokens/s, or re-baseline.

Out of scope: `qk_layernorm` (inherited as true, and the MLPerf recipe keeps it), RoPE versus YaRN, and linear-layer biases still differ from the published model. They are left as the MLPerf recipe has them.

## Validation

- Resolved 13 experiments through `PrimusParser` (module config, model preset and overrides) at `main` and with this change, then compared the model fields:

#### 1. 🟠 Should fix: README still promises a 2880 shared expert on MI455X runs: this PR removed it from the presets without doc updates
`examples/megatron/models/gpt-oss/README.md:331`

The README still says the presets add a shared expert (`moe_shared_expert_intermediate_size: 2880`) and that the MI455X yamls keep it for comparability with the gfx1250 runbook. The MI455X yamls don't override it, so that comparability is silently gone. Other sections (lines 115-116, 123, 173), the throughput/TFLOP/s/loss tables and the hipBLASLt tuning file also assume the shared expert; update them, or keep the shared expert as an explicit override in the MI455X yamls.

**Who is affected:** Anyone following the MI455X GPT-OSS runbook (examples/megatron/models/gpt-oss) with the gpt_oss_20B/120B MI455X yamls.

**4. Re-adding a shared expert to GPT-OSS presets would still pass CI: drift test never compares its width** (`tests/unit_tests/core/projection/test_projection_model_specs.py:83`)

No regression test pins this fix. `_MEGATRON_FIELD_MAP` in `test_projection_model_specs.py` does not compare `moe_shared_expert_intermediate_size`, although `ModelSpec` exposes it (`num_shared_experts * moe_ffn_hidden_size`, 0 for gpt-oss). That is why the base presets' 2880 shared expert passed the drift test. Adding the key to the map, with the preset's `None` treated as 0, would fail on the base and pass on head. Reading only the leaf preset is a documented, deliberate choice and was not the cause; `ModelSpec` has no `rotary_base` field, so the map cannot compare it.

**Origin:** pre-existing

**Who is affected:** Maintainers relying on the projection drift test to catch future shared-expert regressions in the gpt-oss Megatron presets.

_Checked against the code by an independent pass._

**5. Resuming from old GPT-OSS checkpoints fails on unexpected shared_experts keys: this PR removed the shared expert** (`primus/configs/models/megatron/gpt_oss_120B.yaml:31`)

Removing the shared expert changes the parameter set, so checkpoints from the old presets contain `shared_experts.*` weights. Those runs will fail strict load/resume on unexpected keys or silently drop capacity. Add a compatibility note to the PR description or changelog.

_Not independently checked: treat as a lead._

**6. MLPerf example yamls now duplicate preset values, risking future drift** (`examples/megatron/configs/MI355X/gpt_oss_20B-FP8-mlperf-pretrain.yaml:154`)

Now that the `gpt_oss_20B` preset drops the shared expert and sets `ffn_hidden_size: 2880`, `rotary_base: 150000`, `moe_router_load_balancing_type: none` and `moe_router_topk_scaling_factor: null`, the mlperf yamls restate the same values. Those yamls are `examples/megatron/configs/MI355X/gpt_oss_20B-FP8-mlperf-pretrain.yaml` and `examples/mlperf/gpt_oss_20b/configs/MI355/*.yaml`. They could be trimmed as an optional follow-up. `moe_shared_expert_overlap: false` in the MI300X/MI355X/MI455X yamls is not a workaround for the shared expert: it is already the default in `language_model.yaml`. The overrides predate this PR, match the new preset values, and are harmless. They still matter when `PRIMUS_MODEL` points at another preset.

**Origin:** pre-existing

**Who is affected:** Maintainers of the GPT-OSS example and mlperf yamls; no runtime effect in any configuration.

**7. Uncommented `ffn_hidden_size` 2880 invites a revert that would skew projection's FSDP estimate** (`primus/configs/models/megatron/gpt_oss_20B.yaml:11`)

Both presets change `ffn_hidden_size` from 10944 to 2880 with no comment. Megatron never builds a dense MLP for GPT-OSS because every layer is MoE (`moe_layer_freq: 1`), and `model_specs._gpt_oss` documents the same choice. The value is not entirely unused, though: the performance projection's FSDP all-gather estimate (`projection.py`) reads `ffn_hidden_size` for every layer. Add a one-line comment like the one in `model_specs.py` so nobody 'fixes' it back.

**Who is affected:** Maintainers editing the GPT-OSS Megatron presets; training is unaffected.

**2. 🟠 Should fix: Custom configs on GPT-OSS presets train with no MoE balancing loss: this PR sets load balancing to none**

The GPT-OSS presets now set `moe_router_load_balancing_type: none` and `moe_aux_loss_coeff: 0.0`, replacing the inherited `seq_aux_loss`/0.001; HF gpt-oss trains with `router_aux_loss_coef` 0.9. The shipped Megatron examples and `test_gpt_oss_20B_sink_attention` are not affected: they all set `moe_router_force_load_balancing: true`, which randomises the router logits, and the MLPerf yamls already set these values. Only a user config built on `gpt_oss_20B.yaml`/`gpt_oss_120B.yaml` without forced balancing would train with no balancing loss and no expert bias. Consider keeping a non-zero aux loss in the presets and letting the MLPerf yaml override it.

**Who is affected:** Users who write their own real-routing pretraining config on the gpt_oss_20B/120B Megatron presets without overriding the balancing settings.
