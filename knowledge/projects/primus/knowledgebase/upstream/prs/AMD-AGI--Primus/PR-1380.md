# perf(megatron): Triton router and MegaMoE wgrad fusion for DSv3 on MI455X

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1380) · state: open · merged: False

## Original PR description

## Summary

Faster DeepSeek-V3 training on MI455X (gfx1250). No default path of another model changes: the router GEMMs are opt-in, the MegaMoE wgrad fusion applies to bf16 MegaMoE experts under Megatron DDP, and the example changes stay in the MI455X DeepSeek-V3 example. The MegaMoE wgrad fusion uses the companion Primus-Turbo PR (AMD-AGI/Primus-Turbo from `lhzhang333:dev/lhz/dsv3_opt_merge`); with an older Primus-Turbo, Primus keeps DDP's separate add. Two fixes reach other setups that were broken: grouped-linear wgrad fusion with a backend that cannot accumulate, and NUMA binding on a subset of the GPUs.

## Changes

- **Router**: opt-in Triton GEMMs for the FP32 router (`moe_router_triton_gemm`), as accurate as Megatron's FP32 path; unsupported shapes keep Megatron's path.
- **MegaMoE**: bf16 expert wgrads accumulate into `main_grad` (`turbo_mega_moe_wgrad_accum_fusion`; null follows `gradient_accumulation_fusion`). Off under Megatron-FSDP, which clears `grad_added_to_main_grad` before every backward, and for mxfp8 experts, whose stages keep DDP's add.
- **Grouped linear**: the wgrad fusion of `PrimusTurboGroupedLinear` stays on only where the BF16 wgrad backend can add into `main_grad` (no backend set, or Triton / hipBLASLt). A grouped GEMM pinned to FlyDSL or CK, or auto-tuned, keeps DDP's add: a pinned backend raises rather than fall back, and auto-tune in Primus-Turbo builds so far tunes the accumulating wgrad on `main_grad` itself.
- **Runner**: `numa_bind.sh` binds each rank to the NUMA node of the GPU it uses (`HIP_VISIBLE_DEVICES` / `ROCR_VISIBLE_DEVICES` mapped), and runs unbound when the node is unknown instead of failing.
- **MI455X DeepSeek-V3 example**:
  - `gradient_accumulation_fusion`, Triton router GEMMs, routing on TE's fused kernels with the expert bias, no dataloader attention mask, NUMA binding and 4 hardware queues;
  - MegaMoE (the yaml's default since #1365) only where it can run: the launcher's `USE_TURBO_MEGA_MOE=auto` keeps it on when the Primus-Turbo in use has the gfx1250 MegaMoE kernels (the image's predates them, so its runs keep the token dispatcher);
  - README updated.

## Testing

- Unit tests of the changed modules pass on MI455X.
- DeepSeek-V3 proxy on 4× MI455X against main (Primus 1b077e2f + Primus-Turbo c145c458), both sides with the fix that lets Primus import that Primus-Turbo (separate PR from `dev/lhz/primus_turbo_envs_compat`); ms/iter is Primus's average over iterations 3–10, the mean of 2 runs alternating with main; loss and grad norms within run-to-run noise:
  - with MegaMoE (the example's default): 1001.4 → 934.2 ms/iter (−6.7%), +7.2% throughput.
  - without MegaMoE: 1047.1 → 1014.1 ms/iter (−3.2%), +3.3% throughput.
- gpt-oss 20B and Llama 3.1 8B on 4× MI455X, measured before the merge of main (against Primus db5fe1fd + Primus-Turbo ff4898e4; 2 and 3 runs per side): same speed (2104.2 → 2103.2 and 1053.4 → 1050.9 ms/iter); gpt-oss loss and grad norm bitwise identical (lm loss 11.50698 at iteration 10 and the grad norms of iterations 1–10, in all 4 runs).
- With the image's Primus-Turbo, the example's default run keeps the token dispatcher and finishes.

**1. 🟠 Should fix: Zero-padded visible GPU ids leave ranks unbound or wrongly bound: this PR indexes arrays with raw strings**

The `VISIBLE` regex accepts zero-padded ids, which bash reads as octal in `VISIBLE_IDS[$GPU]` / `BUS_ID[$GPU]`. `08` or `09` print a `value too great for base` error and leave the rank unbound; the script has no `set -e`, so the rank still launches. An id like `010` would index GPU 8 and bind to the wrong node. When `LOCAL_RANK` exceeds the visible list, `GPU=${VISIBLE_IDS[$GPU]:-$GPU}` falls back to the raw index (the base behaviour), though such a rank has no device anyway. Using `10#` and leaving out-of-range ranks unbound would make this exact.

**Who is affected:** Users who pass `--numa` to `primus-cli direct` in torchrun mode and set zero-padded `HIP_/CUDA_/ROCR_VISIBLE_DEVICES` ids, or more ranks than visible GPUs.

_Checked against the code by an independent pass._

**2. 🟠 Should fix: An early failed arch probe silently pins generic kernels on gfx1250: this PR caches `''`**

`gfx_arch()` is `lru_cache`d, including its `''` failure result, and reads `current_device()` on first call. A first call before CUDA init or after a transient error would pin the generic (non-gfx1250) router launch configs and backward for the process, with no log; logging or not caching `''` would be cleaner. The callers in the tree only call it inside `router_gemm.forward`/`backward` and the wgrad bridge backward, during training after device setup, so no current path caches a wrong value. The fallback is the portable path: a slower and slightly less precise run, not a failure. The base `_is_gfx1250` was already `lru_cache`d and cached `False` on failure, so the wgrad-bridge add is not newly exposed.

**Who is affected:** Only code that first calls `gfx_arch()` before CUDA/device setup or during a transient driver error on MI455X; no such caller exists today.

**3. 🟠 Should fix: Wgrad may overwrite instead of accumulate with FlyDSL: this PR's gate returns True on errors**
