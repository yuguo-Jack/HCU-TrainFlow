# feat(diffusion): Add AMDB Mochi-1 benchmark support

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1345) · state: closed · merged: True

## Original PR description

## Summary

Add **Mochi-1** video generation model support for AMDiffusionBenchmark within the Primus diffusion backend.

This PR introduces the Mochi-1 AsymmDiT architecture and integrates it with the shared AMDB training, dataset, and checkpoint loading infrastructure.

## Changes

### Mochi-1 model implementation
- Add the Mochi-1 AsymmDiT architecture and required model components.
- Implement model integration using the existing `GenAIModel` interface.
- Reuse `utils/hf_load.py` for Hugging Face checkpoint loading.
- Integrate the new model with the existing Primus configuration and registration system.

### AMDB integration
- Use `AMDBBenchmarkTrainer`, extending `FSDP2Trainer`.
- Include the shared AMDB dataset loading and checkpoint download path.
- Reuse existing training step handling, batch management, and gradient-norm logic.
- Integrate logging and parameter counting through existing Primus utilities.

## Reused Components

- `trainers/base.py`
- `models/interface.py`
- `argument_builder.py`
- `registry.py`
- `utils/hf_load.py`
- `utils/log.py`
- `utils/train_utils.py`
- Existing diffusion checkpoint preparation infrastructure.

## Validation

- [x] End-to-end mochi video benchmark training.

**14. Cached-latent runs over-report throughput: cached loader drops even-batch sampler and resume offset** (`primus/backends/diffusion/trainers/benchmark.py:82`)

`_cache_encoded_batches` is on by default (`cache_latents=True`) and rebuilds the loader with a plain `DistributedSampler(num_replicas=1)`. That discards `EvenSizeBatchSampler` (5 cached samples at batch 4 yield sizes [4, 1]) while FPS/TFLOPS still use `per_device_train_batch_size`, so throughput is over-reported. It also drops `ContiguousDistributedSampler`'s `set_offset` resume path and changes shuffling; keep the original sampler when building the cached loader.

_An independent check of the code found this probably does not apply: The cache is filled by iterating the base loader, which uses EvenSizeBatchSampler under dataloader_even_batches=True and pads the tail to full batches; so the cached count is a multiple of per_device_train_batch_size and the rebuilt loader (drop_last=False) yields only full batches. ContiguousDistributedSampler/set_offset exist only when mlperf_enable is set, and train() skips _cache_encoded_batches when mlperf_enabled, so no resume path is lost._

**Related past reviews:** [#977](https://github.com/AMD-AGI/Primus/pull/977) on `primus/backends/diffusion/trainers/base.py`

**15. Partial latent caching aborts per rank, so ranks can diverge or hang at the timing barrier** (`primus/backends/diffusion/trainers/benchmark.py:65-75`)

When `encode` returns None mid-loader, `_cache_encoded_batches` returns silently, leaving the loader partly consumed and discarding encoded batches. Each rank decides on its own, so ranks can diverge, or hang at the timing barrier if one raises 'produced no samples'; encoders also stay on GPU. Agree on the decision collectively, and add `dataloader_drop_last` to the `BENCHMARK_TRAINER` defaults since the code reads it.

_An independent check of the code found this probably does not apply: The only encode_batch provider is the Mochi adapter, which calls MochiTrainPipeline.encode_batch; that always returns a dict of latents/text_hidden/text_mask or raises, so the `encoded is None` branch is dead and the rank-divergence and GPU-retention consequences cannot occur. DistributedSampler pads each rank's shard, so no rank on a non-empty dataset produces zero samples, and the missing dataloader_drop_last key falls back to False via args.get._

**16. Future FSDP2 wrapping fixes will miss the benchmark trainer: this PR copies `_apply_fsdp2`** (`primus/backends/diffusion/trainers/benchmark.py:126`)

`AMDBBenchmarkTrainer._apply_fsdp2` matches `FSDP2Trainer._apply_fsdp2` except for about 20 lines adding frozen-module casting and a pure-low-precision path. Later fixes to the base wrapping logic will silently miss the benchmark trainer. Expose those additions as options or hooks on the base method, for example a `pure_low_precision` argument.

**Who is affected:** Maintainers of the diffusion FSDP2 wrapping logic; every Mochi-1 benchmark run uses the copied method.

_Checked against the code by an independent pass._

**17. Two near-identical checkpoint loaders to maintain: this PR adds `checkpoint_io` instead of extending `train_utils`** (`primus/backends/diffusion/utils/checkpoint_io.py:18`)

`checkpoint_io.load_state_dict` largely re-implements `train_utils.load_state_dict` / `load_state_dict_from_folder`: the same five extensions and the same safetensors/`torch.load` dispatch. Its additions are directory handling in one entry point, a `FileNotFoundError` on an empty folder, and unwrapping of a nested `state_dict`/`model`/`module` dict. Folding these into the existing helper, for example as an unwrap option, would avoid two loaders drifting apart. The `torch.load` call omits `weights_only`, but on the torch versions Primus ships (>= 2.6, which defaults to `weights_only=True`) both loaders behave the same, so they have not diverged in safety.

**Who is affected:** Maintainers only; Mochi-1 checkpoint loading through `load_matching` works as intended.

_Checked against the code by an independent pass._

**19. Blank dataset path fails instead of using the mochi-1 default: amdb dataset config lacks `model_name`** (`primus/backends/diffusion/data/benchmark.py:255`)

The per-model default in `download._DATASETS` is therefore dead in the training path. This matters only when `dataset_path` is blank and the prepare hook did not run. **20. `BENCHMARK_DENOISER_ONLY=1` still reads the VAE checkpoint and fails opaquely on raw batches** (`primus/backends/diffusion/models/registrations/mochi.py:68`)

`BENCHMARK_DENOISER_ONLY=1` changes the model structure (encoder and text encoder become `nn.Identity`) through an env var rather than a config option. A non-empty `encoder.autoencoder` is still loaded into Identity via `load_matching` with `strict=False`, wasting a full checkpoint read and logging a misleading message, and raw batches then fail opaquely in `encode_batch`. Make it a config option and skip checkpoint loads and raw batches when it is set.

**Who is affected:** Users running Mochi-1 with `BENCHMARK_DENOISER_ONLY=1`, especially if they also set `VAE_CHECKPOINT` or feed raw video batches.

_Checked against the code by an independent pass._

**21. Default `num_frames=9` is not a 6k+1 Mochi VAE shape, so the latent frame count is unclear** (`primus/configs/models/diffusion/benchmark_mochi_1.yaml:6`)

The synthetic-sample comment says '/4' and '2 frames', which makes the shape and FLOPs label misleading. Use a canonical count such as 7 or 13, and remove the 'UNet convolutions' reference.

Line 7 of the MI300X, MI325X and MI355X Mochi configs says MIOpen FAST mode picks 'slower VAE and UNet convolutions'. Mochi-1 has no UNet: its denoiser is the `AsymmDiTJoint` DiT. Its convolutions are the VAE encoder's `Conv3d` layers and the DiT's `nn.Conv2d` patch embedder (`layers.py`). Replace 'VAE and UNet convolutions' with e.g. 'VAE and patch-embedding convolutions'.

**Who is affected:** Readers of the Mochi-1 benchmark configs; there is no runtime effect.

**27. Constant VAE stats are copied host-to-device on every micro-batch in the timed loop** (`primus/backends/diffusion/models/mochi/train_pipeline.py:117`)

`MochiTrainPipeline.compute_loss` re-copies the CPU `STATS['mean']`/`STATS['std']` tensors to the device on every micro-batch with `.to(device=device, dtype=torch.float32)`. These 12-element constants never change. The cost is two tiny host-to-device copies per micro-batch inside the timed loop, small next to a DiT step. Caching them once per device (or registering them as buffers) avoids the redundant transfers.

**Who is affected:** Every Mochi-1 benchmark post-training run, as a negligible per-step overhead.

_Checked against the code by an independent pass._

**28. Clip-grad-norm test cannot catch regressions from this PR: it tests unchanged behavior** (`tests/unit_tests/backends/diffusion/test_benchmark_workloads.py:195`)

The PR's comment in `_clip_grad_norm` documents this dependency, so a test pinning the early return is deliberate coverage of behaviour the new feature relies on, not a defect._
