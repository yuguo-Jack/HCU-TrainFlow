<details><summary>Nits and less certain findings (8)</summary>

**2. Pad alignment imported from private Turbo symbol with silent fallback** (`primus/backends/megatron/core/extensions/primus_turbo.py:426`)

`_TURBO_FP8_PAD_ALIGN` comes from Turbo's private `grouped_mlp_fp8._FP8_PAD_ALIGN` and silently falls back to 128. The `grouped_gemm`/`b` entry reuses that constant even though `grouped_gemm_fp8` hardcodes its own 128, and `ModuleNotFoundError` in the except tuple is redundant. A Turbo bump that changes or renames these values would drift silently; warn on fallback and drop the redundant exception.

_Verified by running it._

**3. Padded branch duplicates TENSORWISE quantize recipe instead of using helper** (`primus/backends/megatron/core/extensions/primus_turbo.py:501`)

When `weight_pad` is set, the code calls `QuantizedTensor.quantize` directly with `ScalingRecipe()`, `axis=-1` and a manual transpose, bypassing `create_quantized_weight`. If Turbo changes the weight recipe, aligned and unaligned models would silently diverge. Route the pad args through the shared helper, or factor out a single recipe source.

**Related past reviews:** [#1024](https://github.com/AMD-AGI/Primus/pull/1024) on `primus/backends/megatron/core/models/hybrid/kimi_delta_attention.py`

**4. Whole test file skipped without GPU, including pure lookup-logic tests** (`tests/unit_tests/backends/megatron/test_turbo_fp8_weight_cache_pad.py:13`)

The module-level `skip_if_no_cuda()` skips the table/alignment tests too (e.g. `test_tensorwise_pads_only_unaligned_dims`), so none of the new coverage runs on CPU runners. The autouse fixture also forces `_turbo_quantize_supports_padding` to True, so real capability detection is never exercised. Split out the logic tests where possible.

_Verified by running it._

**5. Padding-support probe only inspects quantize signature, not op behavior** (`primus/backends/megatron/core/extensions/primus_turbo.py:460`)

`_turbo_quantize_supports_padding` checks only for `pad_align_last` in `quantize`'s signature. It does not check `pad_align_penultimate`, returns False for a `**kwargs` signature, and assumes the ops pad whenever quantize accepts the args. If a build's quantizer and ops disagree, the cache layout mismatches the activation in the other direction.

**6. Padded colwise transpose cache is effectively dead and untested** (`primus/backends/megatron/core/extensions/primus_turbo.py:509-517`)

The padded branch builds `quantized_weight_rowwise.transpose(-2, -1)` when a transpose cache is requested. However, `prepare_weights` disables that cache under current scaling, and the TENSORWISE ops reportedly ignore `data_t`. The branch is dead, or it wastes a full FP8 copy, and every test passes `disable_parameter_transpose_cache=True`.

**7. Table tests compare alignment against the module's own constant** (`tests/unit_tests/backends/megatron/test_turbo_fp8_weight_cache_pad.py:20`)

`ALIGN = pt._TURBO_FP8_PAD_ALIGN` makes the table tests self-referential, so a wrong or fallback alignment would still pass. Meanwhile the `prepare_weights` cases hard-code 256, which implicitly assumes 128. Assert against Turbo's own constant or hard-code 128 consistently.

**8. prepare_weights cache test skips regression cases and checks too little** (`tests/unit_tests/backends/megatron/test_turbo_fp8_weight_cache_pad.py:102`)

`_skip_without_padding_turbo()` runs for every parametrization, so the aligned and MXFP8 'unchanged' checks are lost on older Turbo builds. The MXFP8 case compares against the same `create_quantized_weight` that `prepare_weights` calls. The TENSORWISE cases check only `qdata.shape`, not data, the zero pad region or `scale_inv`, and there is no `grouped_gemm`/`b` case.

**9. End-to-end tests bypass prepare_weights and skip micro-batch reuse** (`tests/unit_tests/backends/megatron/test_turbo_fp8_weight_cache_pad.py:133-214`)

The equality tests build the cache via private `_turbo_fp8_weight_pad`/`_maybe_create_quantized_weight_buffers`, bypassing `prepare_weights` and `_bridge_weight_grad`. As a result, the production `(op, role)` wiring, wgrad routing and `is_first_microbatch=False` reuse are untested. The `rtol=0, atol=0` gradient comparisons may also be flaky if the wgrad kernel is nondeterministic.

**1. 🟠 Should fix: Unvalidated free-form op/role strings silently skip or mis-apply weight padding**

`_turbo_fp8_weight_pad` looks up `(op, role, granularity)` with `.get(..., {})`, and the op/role names are bare strings repeated in `_TURBO_FP8_WEIGHT_PAD`, the `prepare_weights` defaults and `experts.py`. A typo, a rename, or a new caller that forgets to pass them silently gets no padding or the wrong padding. That reintroduces the K-mismatch, and it only shows up with more than one micro-batch on unaligned models. Define the names once as constants or a `Literal`, and raise when an `(op, role)` pair is unknown.

_Verified by running it._
