# fix(diffusion): average the masked flow-matching loss over elements

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1200) · state: open · merged: False

## Original PR description

## fix(diffusion): average the masked flow-matching loss over elements

### Summary

`compute_flow_matching_loss` returns the wrong value whenever a `loss_mask` is
passed that does not already have the loss's full shape:

- A `[B]` (per-sample) mask, even all ones, returns **C·H·W times** the
  per-element mean that the docstring describes and the unmasked branch
  returns.
- A spatial `[B, 1, H, W]` mask is off by **C**.
- A mask that keeps nothing returns **NaN**, which then reaches the gradients
  and the weights.

This PR counts the mask after broadcasting, so a masked loss is the mean over
the loss elements the mask covers.

### Root cause

```python
if loss_mask.dim() == 1 and loss_per_element.dim() > 1:
    loss_mask = loss_mask.view(B, 1, 1, 1)
loss = (loss_per_element * loss_mask).sum() / loss_mask.sum()
```

The multiplication broadcasts the `[B, 1, 1, 1]` mask across C, H and W, so
the numerator sums every element of every kept sample. `loss_mask.sum()` is
taken on the unbroadcast tensor, so it counts each kept sample once rather
than each kept element. The result is a per-sample sum, exactly E = C·H·W
times the mean, for 0/1 masks and soft weights alike. In general, the error
factor is the number of loss elements each mask entry is broadcast over.

### Fix

```python
loss_mask = loss_mask.to(dtype=loss_per_element.dtype, device=loss_per_element.device)
loss_mask = loss_mask.expand_as(loss_per_element)
count = loss_mask.sum()
loss = (loss_per_element * loss_mask).sum() / torch.where(count > 0, count, torch.ones_like(count))
```

- `expand_as` makes the count match the numerator. It is a view, so it adds
  no copy, and it traces cleanly under `torch.compile` (`_compiled_loss_fn`
  wraps this function).
- The cast to the loss's dtype matters because the forward step casts the
  whole batch, mask included, to the compute dtype (bf16), and bf16 cannot
  count large element totals exactly.
- Replacing a zero total with 1 makes an all-zero mask return 0 instead of
  `0 / 0`, so a fully padded micro-batch contributes nothing instead of NaN.
  Only an exact zero is replaced: soft weights can total less than 1, and that
  total is still the right denominator.

Unmasked calls and full-shape masks give the same result as before.

### Why the mask matters

A loss mask lets a micro-batch keep a fixed shape while some of its contents
do not count toward the loss:

- **Padding samples:** the last partial batch, uneven data-parallel shards,
  or static shapes for CUDA graphs and `torch.compile`. This needs a `[B]`
  mask.
- **Dropping bad samples on the fly**, and **per-sample weights**. Also `[B]`
  masks.
- **Padding inside a sample:** resolution or aspect-ratio buckets, or videos
  padded to a common frame count. This needs a spatial or per-frame mask.

### Impact

Latent today. `DiffusionPretrainTrainer` passes `batch.get("loss_mask")` to
this function, but no Flux task encoder puts a `loss_mask` in the batch, so
current runs take the unmasked branch and their loss is unchanged by this PR.
The bug would become live as soon as padding or packing adds a mask.

#1132, still open, adds a WAN helper, `compute_weighted_flow_matching_loss`,
that already counts its mask after broadcasting; this PR fixes the Flux one.
The two PRs edit the same file, so whichever merges second needs a small
rebase.

### Evidence

**What the helper returns.** Flux latents at 256 px (`[4, 16, 32, 32]`), with
each mask checked against an independently computed masked mean:

| mask | current / true mean | fixed / true mean |
|---|---|---|
| none | 1 | 1 |
| `[B]` all ones | 16384 | 1 |
| `[B]` 2 real + 2 padding | 16384 | 1 |
| `[B]` soft weights | 16384 | 1 |
| `[B, 1, H, W]` spatial | 16 | 1 |
| `[B, C, H, W]` full shape | 1 | 1 |
| `[B]` all padding | NaN | returns 0 |

The gradient carries the same factor.

**Training.** The model is the real `FluxConfig.flux_535m()`, trained for 400
steps with the Flux recipes' AdamW settings and `clip_grad: 1.0`. Every 10th
micro-batch is half padding. "Probe" is the per-element loss on a fixed
evaluation set:

| run | probe loss at step 400 |
|---|---|
| reference: padded steps just drop the padding slots, no mask | 1.728 |
| padded, `[B]` mask, fixed helper | 1.728 |
| padded, `[B]` mask on padded steps, current helper | 1.723 |
| same, with gradient clipping off (reference with clipping off: 1.726) | 1.966 |
| one all-padding micro-batch, current helper | NaN from that step on |

- **The fixed helper is correct.** It reproduces the reference run to within
  run-to-run noise: the maximum weight difference is 7.6e-7, against 4.8e-7
  between two identical reference runs.
- **With the current helper:**
  - The logged loss and gradient norm are 16384x too large, and gradient
    clipping fires on every masked step.
  - With clipping on, that hides the effect on training: the gap from the
    reference is within noise.
  - With clipping off, training stalls: the inflated steps swamp Adam's
    second-moment estimate.
  - A single all-padding micro-batch turns the loss, then the weights, into
    NaN.

### Tests

New `TestFlowMatchingLossMask` in
`tests/unit_tests/backends/megatron/diffusion/training/test_loss_computation.py`.
It compares each case against an explicitly computed masked mean:

- An all-ones `[B]` mask equals the unmasked loss.
- A `[B]` mask with padding equals the loss of the real samples alone.
- Soft `[B]` weights give the weighted element mean.
- A spatial `[B, 1, H, W]` mask counts every channel.
- A full-shape mask gives the mean over kept elements.
- A soft mask whose total is below 1 is not rescaled: one kept element
  weighted 0.5 gives that element's own loss.
- An all-zero mask gives a loss of 0 and a zero gradient, not NaN.
- A bf16 mask counts exactly.
