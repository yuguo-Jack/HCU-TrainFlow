# [CP] fix(torchtitan): compile inside checkpoint wrappers for DeepSeek blocks (#1216)

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1320) · state: closed · merged: True

## Original PR description

Cherry-pick of 872bcc91 from #1216 onto `release/v26.9`. The rest of #1216 is already on this branch via #1277.

## Problem
TorchTitan applies activation checkpointing before `apply_compile`, so with checkpointing enabled `_apply_unified_compile` compiled the `CheckpointWrapper` itself. The `GroupedExperts` and FSDP graph breaks then sit inside the checkpoint body, and Dynamo runs the whole checkpointed MoE block eagerly. This affects the DeepSeek-671B recipes, which enable full activation checkpointing with compile.

## Fix
For checkpoint-wrapped blocks, compile the wrapped block (`AC(Compile(block))`) and keep the wrapper outermost. Unwrapped blocks are compiled as before, so runs without activation checkpointing are unchanged.

## Validation
- `tests/unit_tests/backends/torchtitan/test_dsv3_v022_perf_patch.py`: 10 passed on this branch (`rocm/primus:v26.8`, MI355X). The new `test_unified_compile_compiles_checkpoint_wrapped_moe_block` is a GPU real-compile test that applies TorchTitan's full activation checkpointing to a tiny DeepSeek-V3 and asserts the MoE router is captured in a compiled graph; it fails without this fix.
- DeepSeek-V3-16B, `--activation_checkpoint.mode full`, 8x MI355X, 20 steps, seed 42, median tok/s/GPU (steps 4-20):

| Precision | Before | After | Peak HBM (before → after) |
|---|---|---|---|
| BF16 | 17,879 | 19,858 (+11%) | 63.8 → 62.5 GiB |
| FP8 | 17,097 | 25,757 (+51%) | 94.4 → 96.3 GiB |

  Losses match at step 20 and all steps are finite.
- Without activation checkpointing (MI355X 16B configs, 50 steps, `rocm/primus:v26.8`): BF16 28,529 and FP8 33,865 harmonic-mean tok/s/GPU, matching the #1216 numbers.

- `primus/backends/torchtitan/patches/dsv3_v022_perf_patches.py:80-87`: 🔴 Blocking **[PR Pundit]**
    Compiling inside the CheckpointWrapper (AC(compile(block)) instead of compile(AC(block))) changes the DCP/model state-dict FQNs of every AC-wrapped block, dense and MoE alike, from 'layers.N.<param>' to 'layers.N._orig_mod.<param>' (e.g. layers.N._orig_mod.attention.wq.weight). CheckpointWrapper's state_dict hook strips only '_checkpoint_wrapped_module.'. DCP's _get_fqns/get_model_state_dict normalizes '_orig_mod' only when the OptimizedModule is the outer module, which was the pre-PR case. Here '_orig_mod' is reached via CheckpointWrapper.__getattr__ forwarding, so the prefix is not skipped. TorchTitan saves and loads model and optimizer state through get_model_state_dict (components/checkpoint.py:66-68). Consequences: DCP checkpoints saved before this PR, or by runs without AC, fail to load with missing keys; runs with and without AC are no longer checkpoint-compatible; FQN-based mapping such as state_dict adapters for HF import/export breaks.
    **Evidence (verified by running it):** CPU probe on head with checkpoint_wrapper(block) and the eager backend. Old order (compile around the wrapper): get_model_state_dict keys were ['layers.0.lin.weight', 'layers.0.lin.bias']. After _apply_unified_compile: ['layers.0._orig_mod.lin.weight', ...]. The unwrapped block in the same model still gives 'layers.1.lin.weight'. set_model_state_dict(new, old_sd, strict=True) raised RuntimeError with missing '..._checkpoint_wrapped_module._orig_mod.lin.weight' and unexpected '..._checkpoint_wrapped_module.lin.weight'. Read _get_fqns source to confirm the cause.
