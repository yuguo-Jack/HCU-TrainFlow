# Scope ZeRO-3 __params_to_release cache per coordinator and trace

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8883) · state: open · merged: False

## Original PR description

## Summary

`PartitionedParameterCoordinator.__params_to_release` (`deepspeed/runtime/zero/partitioned_param_coordinator.py`) was decorated with `@functools.lru_cache(maxsize=None)` on an instance method. Because `@functools.lru_cache` attaches a single unbounded cache dictionary to the function object on the class and keys entries by `(self, submodule_to_release, step_id)`, this caused three related bugs in ZeRO-3:

1. **Permanent memory leak across engine lifecycles**: Every call to `__params_to_release` during `ZeRoTraceMode.COMPLETE` stored strong references to `self` (`PartitionedParameterCoordinator`) and `submodule_to_release` (`torch.nn.Module`) in the class-level `lru_cache`, preventing garbage collection of the coordinator, submodules, and their ZeRO-3 parameter partitions even after `engine.destroy()` and deleting all user references.
2. **Stale release decisions after trace invalidation**: When `_invalidate_trace()` / `_clear_trace_structures()` cleared `__submodule_order` and re-recorded a new execution trace (for example under dynamic control flow or MoE routing changes), the class-level `lru_cache` was never cleared. If the same `(self, submodule_to_release, step_id)` occurred in the new trace, `__params_to_release` returned the stale release set computed from the old `__submodule_order`, either releasing parameters still needed within `max_reuse_distance_in_numel` or retaining parameters that should be partitioned.
3. **In-place cache corruption during activation checkpointing backward**: In `release_sub_module()`, the backward path executed `params_to_release.update(recompute_params)` directly on the mutable `set` returned by the cache, permanently mutating the cached release set for subsequent forward passes at the same `(submodule, step_id)`.

## Fix

- Replace `@functools.lru_cache(maxsize=None)` on `__params_to_release` with a per-instance `self.__params_to_release_cache: Dict[Tuple[int, int], FrozenSet[int]]` keyed by `(submodule_to_release.ds_id, step_id)`.
- Clear `self.__params_to_release_cache` in `_clear_trace_structures()` alongside `__submodule_order`, `__step_id_module_fetched_for`, and `__param_queue`.
- Return `FrozenSet[int]` from `__params_to_release` and replace `params_to_release.update(recompute_params)` with `params_to_release = params_to_release | recompute_params` in `release_sub_module()`.

## Sibling Execution Paths Checked

- **ZeRO Stage 1 (`DeepSpeedZeroOptimizer`) and ZeRO Stage 2 (`DeepSpeedZeroOptimizer` / `stage_1_and_2.py`)**: Parameters are not partitioned across submodules and do not use `PartitionedParameterCoordinator` or submodule release traces.
- **ZeRO Stage 3 / ZeRO-Infinity (`DeepSpeedZeroOptimizer_Stage3`, `DeepSpeedZeRoOffload`, `PartitionedParameterCoordinator`)**: All share `PartitionedParameterCoordinator.release_sub_module` and `_clear_trace_structures`, covered by this fix.

## Validation & Benchmarks

- **Hardware**: Raspberry Pi 5 Model B (Broadcom BCM2712, 4-core ARM Cortex-A76 aarch64, 16 GB RAM, CPU-only accelerator), Linux 6.12, Python 3.13.5, PyTorch 2.14.0+cpu.
- **Compatibility Matrix Validated**:
  - ZeRO Stage 3 + FP32 / BF16 on CPU (`gloo` single-rank `DistributedTest`)
  - Forward/backward submodule release with and without `ds_recompute_parameters` (activation checkpointing recompute path)
  - Dynamic trace invalidation (`_clear_trace_structures()`) followed by trace re-recording
- **Memory Leak Benchmark** (20 sequential coordinator lifecycles over a 4-layer `Linear(1024, 1024)` model, `gc.collect()` after each lifecycle):
  - **Before (`@functools.lru_cache(maxsize=None)`)**: 20/20 `PartitionedParameterCoordinator` instances and 80/80 `Linear` submodules retained in memory (`__params_to_release.cache_info().currsize == 80`; RSS grew from 249.6 MB to 888.0 MB, **+638.4 MB leaked**).
  - **After (per-instance `__params_to_release_cache` + `FrozenSet[int]`)**: 0/20 coordinators and 0/80 submodules retained after `gc.collect()` (**0.0 MB leaked**).
- **Tests**:
  ```bash
  pytest tests/unit/runtime/zero/test_zero_params_to_release_cache.py
  ```
  All 3 engine-level `TestZero3CoordinatorCacheLifecycle` tests (`test_release_sub_module_follows_retraced_order`, `test_backward_recompute_release_does_not_mutate_cached_forward_release`, and `test_engine_coordinator_released_after_complete_trace`) pass.
