# Add vocabulary-parallel fused linear cross entropy

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8792) · state: closed · merged: True

## Original PR description

Follow-up to #8173.

## Motivation

After #8173, a vocabulary-parallel LM head still materializes `[tokens, vocab / tp]` logits on every rank. Its CE backward also keeps FP32 softmax buffers of the same size. For long sequences and large vocabularies, this is the largest activation in the step. For example, at 256K vocab, TP2, and 16K tokens, the loss path alone peaks at about 28 GiB per rank.

Existing fused linear CE kernels do not cover this case. Liger's FLCE is not TP-aware (linkedin/Liger-Kernel#826, linkedin/Liger-Kernel#868). PyTorch's `F.linear_cross_entropy` chunks only over the batch dimension and takes no process group.

## What

`deepspeed.sequence.linear_cross_entropy.vocab_parallel_linear_cross_entropy(hidden, weight, target, bias=None, tp_group=None, sp_group=None, vocab_start_index=None, vocab_end_index=None, ignore_index=-100, reduction="mean", chunk_size=None)` (`reduction` is `"none"`, `"sum"` or `"mean"`)

- It replaces `head(hidden)` plus the vocab-parallel CE, taking `weight`/`bias` from `VocabParallelLinear`. Uneven shards are supported.
- **Forward** walks over token chunks. Each chunk computes `h @ W_localᵀ` straight into FP32 and runs one MAX all-reduce plus one SUM all-reduce (sum-exp and target logit packed together). Only the per-token max and sum-exp are kept.
- **Backward** walks over local vocabulary blocks and recomputes each block's logits, with the max subtracted in the GEMM epilogue. Each `dW` block then comes from one GEMM over all tokens. `dh` is accumulated in FP32 and all-reduced over TP, matching the column-parallel head's backward. Backward needs no other collectives.
- No FP32 copy of `dW` is held, and backward is an ordinary autograd backward. The cost is one extra logits GEMM.
- By default, each FP32 logits block is about the size of `hidden`. `chunk_size` trades memory for speed.

## Validation

`tests/unit/v1/sequence_parallelism/test_vocab_parallel_linear_cross_entropy.py` has 24 tests. Values and gradients are checked against `F.linear` + `F.cross_entropy` on the full vocabulary. Coverage:
- `none`/`sum`/`mean` reduction with a non-uniform upstream gradient, with and without bias, and forced chunking;
- all tokens ignored, a frozen weight, and input validation;
- an FP16 product that overflows before a cancelling bias, as `F.linear` handles it;
- FP16 with a 65536 loss scale, and BF16 activations with FP32 parameters under autocast;
- BF16 gradients summed over many chunks and vocabulary blocks;
- TP=2 with uneven vocab shards, in FP32 and BF16, with default and forced chunking.

Ran on Intel Arc Pro B70 (XPU, XCCL): 30 passed. `test_vocab_parallel_cross_entropy.py` still passes (18 passed).

### Memory and time

Measured on 1× Intel Arc Pro B70, single-rank shard, H=4096, BF16. Peak is fwd+bwd and excludes inputs, but includes `dW`/`dh`. The baseline is `head.weight` logits followed by `vocab_parallel_cross_entropy`.

| Vocab / TP | Tokens | Baseline | This PR | Time (baseline → this PR) | torch `linear_cross_entropy` (no TP, reference) |
|---|---|---|---|---|---|
| 128K / TP8 | 8K | 1757 MiB | 569 MiB | 38.9 → 44.0 ms | 269 MiB, 30.3 ms |
| 128K / TP8 | 16K | 3508 MiB | 1008 MiB | 78.1 → 84.1 ms | 412 MiB, 59.7 ms |
| 128K / TP2 | 8K | 7014 MiB | 945 MiB | 158.8 → 173.5 ms | 698 MiB, 124.1 ms |
| 128K / TP2 | 16K | 14028 MiB | 1385 MiB | 316.8 → 331.4 ms | 892 MiB, 229.2 ms |
| 256K / TP2 | 8K | 14336 MiB | 1472 MiB | 314.2 → 370.3 ms | 1222 MiB, 372.2 ms |
| 256K / TP2 | 16K | 28672 MiB | 1921 MiB | 633.6 → 678.9 ms | 1416 MiB, 503.7 ms |

Peak memory drops by 3–15×, and time is 4–18% higher because backward recomputes the logits. The first design computed gradients during forward and accumulated `dW` in FP32 over token chunks. That needed an FP32 `dW` buffer plus a cast copy, which came to about 3× the size of `dW`: 3.6 GiB peak at 256K / TP2.

## Follow-ups

- [ ] Integration path. HF computes logits before `loss_function`, so the existing loss hook cannot intercept them. The options are to patch the CausalLM forward behind `vocab_parallel_ce_backend: "fused_linear"`, or to document the functional API only.
- [ ] End-to-end TP training test with `VocabParallelLinear` and `SimpleModel`, plus multi-rank e2e memory numbers.
- [ ] Interaction with ZeRO-2/3 gradient hooks on the LM-head weight.
- [ ] Close the remaining speed gap to `torch.linear_cross_entropy`, e.g. by fusing the softmax-gradient elementwise ops.

## Limitations

- The fused FP32-output GEMMs (`out_dtype=torch.float32`) are used where the backend supports them, such as XPU. Other backends, such as CPU, fall back to unfused ops.
- Under `torch.autocast`, the GEMMs run in the autocast dtype, as `F.linear` would.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  All-reduce hidden gradients before narrowing to fp16**

When FP16 is used with TP and loss scaling makes the per-shard input-gradient partials exceed 65504, this narrows each rank's FP32 accumulator before the SUM. For example, with a 65536 loss scale, two equal-probability classes on different TP ranks, and weights of 8, the ranks produce opposing FP32 partials whose correct sum is zero, but they become `+inf` and `-inf` here and the all-reduce returns NaN. Sum the FP32 partials before converting to `hidden.dtype` so cancellation across vocabulary shards remains finite.

- jinyouzhi · comment · 2026-10-14T14:14:21Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8792#discussion_r4271932066)

Addressed in 8582e19c9 without a new accelerator interface. Instead of attempting a GEMM and treating any exception as "unsupported" (which could misclassify an OOM), `_has_mixed_gemm(device_type)` now asks the PyTorch dispatcher whether the device registers kernels for `aten::mm.dtype`, `aten::addmm.dtype` and `aten::addmm.dtype_out`. No computation or allocation happens, and the result is cached per device type.

- Upstream registers these ops for CUDA (incl. ROCm) and XPU; CPU returns False and takes the upcast path.
- PyTorch < 2.8 (ops absent) or a build without the `torch._C` query helpers falls back to the upcast path, so the result stays correct.
- The fast path is now only taken for fp16/bf16 inputs with an fp32 output, matching the kernels' dtype contract. This also removes the old behavior where an fp64 input could permanently disable the fast path for a device.
- No try/except around the GEMM anymore, so real failures (e.g. OOM) propagate.
