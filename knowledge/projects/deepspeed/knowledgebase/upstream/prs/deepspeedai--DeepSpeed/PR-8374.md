# Add coalesced full gradient access

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8374) · state: open · merged: False

## Original PR description

Add `safe_get_full_model_grads` for model-wide gradient access after `backward` and before `step`. ZeRO-1/2 uses one coalesced reduction per data-parallel group when supported by the backend, with per-parameter reductions as the fallback. ZeRO-3 uses the existing accessor. AutoTP/AutoEP shards remain local.

The coalesced path shares fragment assembly with `safe_get_full_grad`, including the upstream BF16 fixes: contribute only the owned fragment and prefer FP32 accumulation over the low-precision staging gradient. Parameters owned by another rank still contribute zero buffers to the collective.

Fixes #7644. The open-PR search for #7644 returns this PR.

Synced with upstream `0eb3a8bcc` and resolved the conflicts. `.github` matches upstream exactly; the PR diff contains the utility export, implementation, API documentation, and tensor-fragment tests under `tests/unit/v1/zero`.

Covers ZeRO-1/2 FP32 against an ordinary PyTorch model, BF16 with FP32 accumulation on ZeRO-1/2/3, ZeRO-2 CPU optimizer offload and noncontiguous gradients, remote-owned parameters, fallback, and separate groups.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Keep unmapped ZeRO parameters in the collective**

With ZeRO-1/2, `_init_lp_to_hp_mapping` deliberately leaves `_hp_mapping` as `None` on ranks whose optimizer partition does not overlap a parameter. Skipping those parameters means different ranks build different coalesced buffer lists, so a normal multi-rank model can hang/fail in the collective or return `None` instead of the remotely owned gradient. Managed parameters with a `None` mapping must still enqueue a correctly shaped zero buffer, while only truly unmanaged parameters should be omitted.
