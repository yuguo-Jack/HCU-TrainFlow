# Link ZeRO-1/2 fragments at their round-robin offsets

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8637) · state: open · merged: False

## Original PR description

With `round_robin_gradients`, ZeRO-1/2 lay the flat buffer out in round-robin order, but `_link_all_hp_params` only passed those offsets to `link_hp_params` when there was alignment padding (#8277). Without padding the mapping is summed up in `bit16_groups` order, so after the first reordered parameter everything points at a neighbour's slice. `safe_get_full_fp32_param`, `safe_get_full_grad` and the rest of the fragment API hand back another parameter's data, and universal checkpoints mislabel the fragments. Training itself is fine, it only touches the flat partitions.

I ran into it while working on #8609. On 2×H20, ZeRO-2, six layers:

- `safe_get_full_fp32_param(p)` vs `p`: 0 without round robin, 5.9e-1 with it, 0 with this change.
- A universal checkpoint saved without round robin and resumed with it (Adam, fp32) was 2.4 off after two steps. With this change it's bit-identical, and so are the other two combinations.

The fix just always passes the round-robin offsets. The existing fragment tests only check that the getters return something, which is probably why this has been around since tensor fragments came to ZeRO-2 (#2727). The new `TestTensorFragmentValues` compares them against a plain PyTorch copy of the model on the same batch; the round-robin cases fail on master and pass here.

Also ran `test_zero_tensor_fragment.py`, `test_stage2_flatten_on_gpu.py`, `test_muon_checkpoint.py`, the AutoEP grad parity and unit tests, and the fp32 cases of `test_universal_checkpoint.py`: 328 passed, 33 skipped.


## Environment

NVIDIA H20-3e, driver 580.105.08, Python 3.11.15, torch 2.9.1+cu128; the runs above used 2 GPUs.
