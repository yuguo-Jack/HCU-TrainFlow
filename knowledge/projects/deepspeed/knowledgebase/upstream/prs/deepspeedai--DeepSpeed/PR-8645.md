# Add an opt-in fused Triton RMSNorm for Llama-style Hugging Face models

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8645) · state: closed · merged: True

## Original PR description

## Summary

Adds `deepspeed/ops/triton_ops/fused_rms_norm.py`:

- `fused_rms_norm(hidden, weight, eps)`: Triton forward and backward kernels for the RMSNorm expression that Llama-style Hugging Face models share, `weight * (x.float() * rsqrt(mean(x.float()**2) + eps)).to(x.dtype)`.
- `replace_rms_norm(model) -> int`: an explicit, opt-in installer that runs the kernels in place of the forward of each supported RMSNorm module (the RMSNorm classes of Llama, Mistral, Mixtral, Phi-3, Qwen2, Qwen2-MoE, Qwen3, Qwen3-MoE, DeepSeek-V2 and DeepSeek-V3) and returns how many modules it replaced. For inputs the kernels do not take, a replaced module runs its own eager forward.

Nothing changes unless `replace_rms_norm` (or `fused_rms_norm`) is called. In the AutoEP Qwen3-30B-A3B training setup described under Performance, it cut the median step time by **9.0%**, with peak memory unchanged.

## Module copying and checkpoints

The installer uses a class descriptor and a per-instance opt-in marker, rather than storing a bound `forward` method on each module. The dispatcher is process-wide, but instances not explicitly selected keep their original eager forward and remain eligible for a later opt-in.

Shallow/deep copies and `torch.nn.DataParallel` replicas retain their live opt-in and bind to their own receiver, weights and epsilon. HF module classes, Parameters and state-dict keys are unchanged. Full-model `torch.save(model, ...)` / `torch.load(..., weights_only=False)` clears the opt-in: the marker serializes as `False`, not as an enabled flag. The loaded model remains eager until `replace_rms_norm(model)` is called again, even when another instance has already installed the class dispatcher in the loading process. Legacy boolean markers also cannot enable the new dispatcher. The original class/instance-patch guards, idempotence and unsupported-input fallback are preserved.

This follow-up preserves the earlier master merge and receiver-binding fix; it does not include the narrow-row scheduling changes from #8664.

## Semantics

The kernels keep the eager order: FP32 variance and normalization, one rounding of the normalized value to the input dtype, then the multiply by the weight (gamma). The backward rounds where eager autograd rounds: `grad_out * weight` is rounded to the input dtype before use, and the gamma-gradient product `grad_out * normalized` is rounded to the input dtype before its FP32 column sum. Results are still not bitwise identical to eager, because the FP32 reductions sum in a different order.

## Which modules are replaced

Instances of the exact classes listed in `SUPPORTED_RMS_NORM_CLASSES` that still run their class's own `forward` and are at most 2048 wide.

The list is explicit because a class name ending in `RMSNorm`, a 1-D `weight` and a float `variance_epsilon` do not determine the math. In transformers 5.17, 140 `*RMSNorm` classes pass that rule, and 8 of them multiply by the weight *before* the cast: `GptOssRMSNorm`, `Olmo2RMSNorm`, `Olmo3RMSNorm`, `FlexOlmoRMSNorm`, `OlmoHybridRMSNorm`, `HeliumRMSNorm`, `AfmoeRMSNorm` and `OpenAIPrivacyFilterRMSNorm`. `Olmo2RMSNorm` changed order between releases: it casts before gamma in 4.51.3 and after gamma in 5.17. The kernels would run on those modules without error and silently change their numerics, so falling back to eager cannot catch this; the selection has to. The installer therefore:

- replaces only exact instances of the listed classes. CPU tests hold the currently listed classes to the kernels' expression using `torch.equal` (which does not distinguish signed zero), so a class that changes its cast order upstream fails CI. Adding a class also requires updating the collection-safe class-name metadata in the tests;
- leaves subclasses alone, as well as modules whose `forward` was patched or wrapped on the class or on the instance, whether by another kernel installer or by an earlier call (so a second call replaces nothing). A wrapper made with `functools.wraps` carries the original's name, so it is recognized by the `__wrapped__` attribute that `functools.wraps` sets;
- leaves norms wider than 2048 eager, because the kernels hold a whole row in one block.

On Qwen3-30B-A3B it replaces all 193 RMSNorm modules: `input_layernorm`, `post_attention_layernorm`, `q_norm` and `k_norm` in each of the 48 layers, plus the final norm. On Qwen3-235B-A22B (hidden size 4096) it replaces the 188 128-wide `q_norm` and `k_norm` modules and leaves the 189 4096-wide norms eager.

## Where the kernels run

| | |
|---|---|
| Kernels | Input and weight are bfloat16 or float16 CUDA tensors of the same dtype, and Triton is available on CUDA (not ROCm). |
| Everything else | The module runs its class's own eager forward, so the result is exactly eager's, and a warning is logged once. This includes CPU tensors, float32 inputs and float32 weights under autocast, so the installer can run before the model moves to the GPU. |
| Layout | Any leading shape. Non-contiguous inputs and weights are copied before the kernels run. The kernels' output and input gradient are contiguous, whereas eager follows the input and upstream-gradient strides. |
| Autograd | First-order gradients for input and weight; `eps` is a constant. On the kernel path, double backward raises (`once_differentiable`) instead of silently dropping this op's second derivative. `torch.compile` and `torch.func` transforms are not covered. |
| `fused_rms_norm` | Applies the kernels directly and raises on unsupported inputs instead of falling back. |

## Correctness evidence

Three separate questions, each with its own evidence.

### 1. Does the operator compute the expression? (unit tests, random inputs)

The reference is the eager expression in the same dtype. The metric is the distance in units in the last place (ULP), computed from ordered bit patterns:

- forward: max ≤ 2 ULP, and ≥ 99% of elements within 1 ULP
- input and gamma gradients: max ≤ 8 ULP, and ≥ 95% within 1 ULP (≤ 16 ULP and ≥ 90% at input scales of 1e-4 and 1e4)

Coverage: bfloat16 and float16; widths 128, 130, 256 and 2048, plus an empty input; head-major non-contiguous input; strided weight; and the installer on every listed class, against that class's own eager forward, with a non-default epsilon and the head-major upstream gradient that attention produces. Every random input comes from a seeded generator.

### 2. Does it hold on real training tensors? (frozen replay, Qwen3-30B-A3B)

21 RMSNorm boundaries were captured from one eager Qwen3-30B-A3B training step (48 layers, EP16, sequence length 1024): all four norm kinds at layers 0, 11, 23, 35 and 47, plus the final norm, with the real inputs, gamma, epsilon, upstream gradients and strides. The eager replay reproduces the captured outputs exactly (relative L2 of 0 in all 21 cases). Fused against eager, on one H100:

| | Result |
|---|---|
| Gamma gradient | Bitwise identical in 20 of 21 cases; one element differs in the remaining case |
| Input gradient | 15–136 differing elements per case (out of 0.5M–4.2M), relative L2 ≤ 5e-5 |
| Forward | 0–14 differing elements per case |
| Elements outside \|a − b\| ≤ 2⁻⁶ + 2⁻⁶·\|b\| (BF16 policy) | 0 in every case |

The forward differences come from the FP32 summation order of the variance, which a `torch.compile`d RMSNorm does not reproduce either. No replay was run for the other listed classes; for them, the evidence is the unit tests above plus each class computing the same expression bitwise.

### 3. What does it do to a short training run? (sensitivity, not equivalence)

These are paired 24-step runs in the setup described under Performance, with 4 repeats per arm:

- step 0: mean loss differs by about 4e-4 (forward rounding)
- step 1: 17.100 eager vs 17.044 fused (−0.056), where eager repeats agree to within 0.004
- max |Δ mean loss| over the 24 steps: fused 0.058; eager vs eager 0.013–0.019

A control changes only the eager RMSNorm's variance reduction, computing it in FP64 before the usual FP32 steps, which gives a more accurate eager norm. It moved step 1 by +0.043 and reached a max |Δ| of 0.049. So a 0.02 threshold on short-run loss also rejects a more accurate eager norm: ULP-level changes in the norm move the first AdamW steps by more than 0.02, and the threshold cannot decide on its own whether a kernel is correct. Runs this short cannot establish long-run training equivalence, and this PR does not claim it.

## Performance

Measured setup, identical in both arms except for the RMSNorm implementation:

- Qwen3-30B-A3B, 48 layers, sequence length 8192, micro-batch 1 per GPU
- AutoEP with the DeepEP backend, EP16 on 2 nodes × 8 H100 80GB, with both arms on the same allocation
- BF16, ZeRO stage 1 with FP32 gradient accumulation, AdamW, reentrant activation checkpointing, Python GC disabled during training
- a fixed routing schedule (identical route histograms in both arms); HF router logits on, so both arms also build the zero-coefficient load-balancing loss
- both arms include two changes that are not part of this PR: the DeepEP cached-dispatch layout fix (#8636) and the opt-in fused AutoEP row weighting (#8644)
- 24 steps, of which the first 12 are excluded; step time is the synchronized training step, taking the maximum across ranks
- one discarded preflight run per arm, then 4 runs per arm in ABBA BAAB order

| | Median step (ms) | Per-repeat medians (ms) |
|---|---|---|
| Eager RMSNorm | 1934.3 | 1881.2, 1910.7, 1977.1, 1958.0 |
| Fused RMSNorm | 1760.4 | 1814.3, 1706.5, 1693.1, 1869.3 |

That is −174 ms (−9.0%). All four paired repeats are faster (−3.6%, −10.7%, −14.4%, −4.5%), and the 95% t-interval over those four deltas is [−16.5%, −0.1%]. Peak memory is unchanged (58.3 GiB allocated, 71.2 GiB reserved). An earlier screen on a different allocation, run before the gamma-gradient rounding fix, measured −8.96%.

Scope: one model, one parallel configuration and one sequence length, on H100. The interval is wide, so read this as "about 9% in this configuration", not as a general speedup. Not measured: the other listed model families, other widths, sequence lengths or EP sizes, other GPUs, ZeRO-3, `torch.compile`, and non-reentrant checkpointing.

The measured kernels are byte-identical to this PR's. Since those runs, the installer covers more classes and is stricter about which modules it takes (it still replaces the same 193 modules on this model), replaced modules fall back to eager for inputs the kernels do not take, `fused_rms_norm` copies a non-contiguous weight first (a no-op for the contiguous weights measured), and the backward became `once_differentiable` (first-order gradients unchanged). On supported inputs a replaced module still makes one input check per call and then runs the same kernels.

The receiver-binding and checkpoint opt-in follow-ups change only module dispatch and checkpoint behavior, not the kernels, autograd or direct operator implementation. The existing performance and replay evidence is reused; there is no new timing or full E2E run, and the historical percentage is not an independently retimed measurement of the new dispatcher.

Thank you for the optimization! The performance improvement is clear.

I found one small compatibility issue: `replace_rms_norm()` stores a bound method directly in each instance’s `forward` attribute. This works for direct calls, but introduces two following issues:
- **Shallow copies retain the original receiver.** The copied module’s `forward.__self__` still points to the original module, so calling it uses the original module’s parameters. This affects `nn.DataParallel`, which shallow-copies the instance dictionary when creating replicas for example (though I don't think many people use `nn.DataParallel` these days).
- **Full-model serialization fails on reload.** Saving weights with `torch.save(model.state_dict(), ...)` is unaffected. However, `torch.save(model, ...)` succeeds while `torch.load(..., weights_only=False)` fails. Pickle tries to restore the bound method by looking up `_fused_module_forward` on the restored module, but the method was installed under the name `forward`, so that lookup raises `AttributeError`.

I opened a [PR](https://github.com/yh0903/DeepSpeed/pull/2) to show a different approach, but we don't need to stick to it.
I don't think the above are the major use cases. As long as we can raise a proper error or warning, the current approach would also be good.

This boolean opt-in marker is serialized by full-model `torch.save`. In a fresh process where any other instance of this HF class has already installed the process-wide dispatcher, loading this checkpoint immediately activates fusion for the loaded module (and a subsequent installer call returns 0), despite the documented guarantee that a loaded model remains eager until explicitly reinstalled. Make the serialized form of the marker opt out (or otherwise exclude it from pickling), and cover loading after the dispatcher has already been installed.
