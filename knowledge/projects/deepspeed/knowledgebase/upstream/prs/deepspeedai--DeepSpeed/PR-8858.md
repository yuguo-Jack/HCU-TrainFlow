# [Muon] CPU offload: pin the momentum and overlap the host writeback

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8858) · state: open · merged: False

## Original PR description

Speeds up Muon under ZeRO CPU optimizer offload (ZeRO-1/2/3) without changing results: the momentum now honors `offload_optimizer.pin_memory`, and the host writeback of each update overlaps the next orthogonalization. Part of the roadmap in #8463.

## Motivation

With CPU offload, Newton–Schulz runs on the accelerator, so every step copies each Muon gradient and momentum to the device and the update and momentum back. Every other buffer that crosses PCIe on this path is pinned when `pin_memory` is set; the Muon momentum was not:

- ZeRO-1/2 allocated it with `torch.zeros_like`, ZeRO-3 with `torch.zeros` (`unpinned_fp32_buffer_momentum`).
- Loading a checkpoint replaces optimizer state with freshly allocated pageable tensors, so even a pinned momentum would lose the pin on resume.

This is the same per-step data flow as #7939, which added Muon CPU offload to ZeRO-1/2 and was closed because the offload path was too slow (cc @delock). That design is now on master; this PR targets its two costs, the pageable momentum copies and the serialized writeback.

Pageable copies ran at ~10 GB/s here versus ~43 GB/s H2D / ~57 GB/s D2H pinned. The writeback was also strictly serialized with the next batch's gather and Newton–Schulz.

## Changes

- **Pin the momentum** (`stage_1_and_2.py`, `stage3.py`): allocate it with `pin_empty(_like)` when `offload_optimizer.pin_memory` is set, and re-pin it at the point of use if it is not pinned (after a checkpoint load). ZeRO-3 momentum that the NVMe swapper manages is left to the swapper; the `save_muon_momentum_buffer_in_memory` copy is pinned.
- **Overlap the writeback** (`zero/utils.py: OverlappedHostWriteback`): the update and momentum of batch *i* (ZeRO-1/2) or parameter *i* (ZeRO-3) are copied to the host on a side stream after batch *i+1* has been queued, so the D2H overlaps the next gather and Newton–Schulz. Dependencies are enforced with host-side `Event.synchronize()` rather than a cross-stream wait, since on XPU a stream waiting on another stream's event serialized the two queues (0 overlap in a trace). Sources stay referenced until their copy completes (at most one batch computed and one in flight), and the copies are drained before the host reads them (end of the update, and before an NVMe swap-out). Synchronized devices (CPU accelerator) copy inline as before.

The update math is untouched; results are bitwise identical to master.

## Tradeoffs

- Pinned host memory grows by the momentum size (4 B per Muon parameter per rank; 14.5 GB for Qwen3-4B on one rank), only when the user opted into `pin_memory`.
- Device memory: one more batch of local update/momentum slices can be alive while its copy is in flight (bounded by the existing Muon gather budget). Peak memory is reported below.

### Performance

Qwen3-4B shapes (randomly initialized, 36 layers, 4.02B parameters of which 3.63B Muon), seq 2048, micro-batch 1, bf16, gradient checkpointing, gradient clipping 1.0, `offload_optimizer: {device: cpu, pin_memory: true}`, 1 GPU, one socket (48 cores, `numactl -C 48-95 -m 1`). Per run: mean of steps 2–6; 3 runs per cell. "Muon apply" is `_apply_muon_updates_cpu_offload` (gather, Newton–Schulz, writeback), timed with device synchronization.

| ZeRO | Code | Iteration (s), runs | Iteration mean | Muon apply mean | Peak device memory |
|---|---|---|---|---|---|
| 2 | master | 8.51 / 8.52 / 8.60 | 8.54 | 5.13 s | 12.09 GiB |
| 2 | this PR | 5.57 / 5.77 / 5.70 | **5.68 (−33%)** | 2.35 s (−54%) | 12.09 GiB |
| 3 | master | 7.66 / 7.65 / 7.64 | 7.65 | 3.79 s | 19.88 GiB |
| 3 | this PR | 6.27 / 6.30 / 6.27 | **6.28 (−18%)** | 2.22 s (−41%) | 20.11 GiB (+0.23) |

Breakdown of the two changes (same setup, this PR's code with one change disabled; 3 runs per cell). *Pin only* forces the writeback synchronous; *overlap only* leaves the Muon momentum pageable while every other offload buffer stays pinned. The momentum pin status was checked in every run.

|---|---|---|---|---|---|

| 3 | both (this PR) | | 6.28 (−18%) | 2.22 s (−41%) | 20.11 GiB |

Pinning is the larger effect. The overlap adds a further 0.47 s (ZeRO-2) and 0.35 s (ZeRO-3) of Muon apply on top of pinning. Under ZeRO-2 that shows up in the iteration time (5.94 → 5.68 s). Under ZeRO-3 the iteration mean does not move (6.28 s in both); the gain is within this setup's iteration noise. The +0.23 GiB ZeRO-3 peak comes from the overlap (the in-flight parameter), not from pinning.

Correctness of the overlap: in the same process, the Muon apply was run twice on identical host state, once with the writeback forced synchronous and once overlapped, and the resulting gradients and momentum were compared with `torch.equal` (ZeRO-2 and ZeRO-3, 4 layers). They are bitwise equal on every step after the first. On the first step two *synchronous* runs already differ from each other by the same amount (max 4.9e-4 in one gradient tensor), so that is first-call nondeterminism of the existing path, not the overlap. Losses are not bitwise reproducible across separate processes on master either (they differ from step 1 on), so cross-run loss equality is not used as evidence; the trajectories of master and this PR stay within master's own run-to-run spread.
