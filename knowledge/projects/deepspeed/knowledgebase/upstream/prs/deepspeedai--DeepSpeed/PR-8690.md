- jinyouzhi · COMMENTED · 2026-10-30T15:32:42Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8690#pullrequestreview-5714641076)

Requesting changes based on actual two-GPU validation: the patch regresses non-reentrant checkpointing and does not resolve the frozen-weight/reentrant retention reported on #8481.

**Validation setup**

- 2 x NVIDIA L20 (46,068 MiB each), driver 580.173.02, PyTorch 2.14.1+cu130, CUDA 13.0, NCCL, Python 3.10.22.
- Compared pristine current master `27360990020b0619b744e5fc5e6e4d6e9de3fb79` against the exact diff of this PR at `145e00d309727be081be1700eea8d92eb618d1bf` applied to that master. This is a patch-on-current-master comparison, not a checkout of the PR's historical base.
- Standalone FP32 ZeRO-3 training: three blocks of `tanh(base(x) + 0.1 * B(A(x)))`, width 128, rank-8 adapters, base weights either frozen or trainable, sequential or twice-shared blocks, four optimizer steps. Persistence threshold, prefetch bucket size and maximum reuse distance were all zero; communication overlap disabled. Each case checks loss, input gradients, DP-averaged parameter gradients and parameter updates against an independent unsharded model using the same inputs and SGD updates.
- Ten completed configurations per implementation: sequential with no/reentrant/non-reentrant checkpointing, frozen and trainable base; shared blocks with no/non-reentrant checkpointing, frozen and trainable base. All completed configurations pass the numerical checks, but that does **not** imply correct parameter lifetime. Shared-block reentrant execution separately hit a pre-existing duplicate-parameter assertion in gradient reduction on master, so it is not counted as a passing case or attributed to this PR.

**1. New non-reentrant regression (inline finding)**

| After each of four backwards | Master | This patch |
|---|---|---|
| Sequential block's base-linear `ds_grads_remaining` | 0, 0, 0, 0 | 1, 2, 3, 4 |
| Twice-shared block's base-linear counter | 0, 0, 0, 0 | 2, 4, 6, 8 |
| Sequential post-submodule-backward callbacks per step, including root | 13 | 1 |
| Shared post-submodule-backward callbacks per step, including root | 25 | 1 |

Both ranks reproduce this, with frozen and trainable base weights. The missing callbacks retain gathered layer parameters until later/root cleanup instead of releasing them layer by layer. This independently confirms the earlier counter-drift concern in this PR's discussion.

**2. The #8481 frozen-weight/reentrant retention remains**

A larger sequential model (12 blocks, width 2048, frozen base plus trainable rank-8 adapters, CPU parameter offload without pinned memory, same zero persistence/reuse/prefetch settings) makes the residency difference measurable. Three steps per mode; both ranks agree:

| Implementation / checkpoint | Maximum AVAILABLE parameter storage observed at backward hook boundaries | First-step PyTorch peak allocated |
|---|---:|---:|
| Master / reentrant | 192.06 MiB | 2321.00 MiB |
| Patch / reentrant | 192.06 MiB | 2321.00 MiB |
| Master / non-reentrant | 16.06 MiB | 2147.44 MiB |
| Patch / non-reentrant | 193.50 MiB | 2324.07 MiB |

In master's reentrant trace, frozen weights retain root module id 0 in `ds_active_sub_modules`: after successive blocks finish backward, resident frozen weights grow 16 -> 32 -> ... -> 192 MiB, and are released at root cleanup. Applying this patch leaves that behavior unchanged. Thus the original symptom can occur even when the child-linear counters are zero; removing their reset is not a sufficient fix for this frozen-weight case. This reproduces in-backward parameter accumulation, **not** an unbounded cross-step leak or an actual OOM in the small reproduction. Losses, gradients and updates still match the dense reference over these three steps.

Please fix the checkpoint graph/invocation lifetime accounting and add repeated-step on-device regression coverage that checks parameter residency during backward, not only end-of-backward counters or numerical parity. Frozen parameters attributed to a recompute owner also need a matching timely release.

Scope: synthetic adapter modules, not a full PEFT/TRL/Qwen or Wan run; FP32 only in these tests. No claim is made about BF16 convergence or every checkpoint topology. Validation harness and raw rank-local traces were retained. This review and the validation harness were prepared with GitHub Copilot CLI assistance.

`ds_grads_remaining` is module-local hook state, but `hasattr` can succeed through an attribute-delegating wrapper. In that case this hook does not initialize the wrapper's own counter, and the later `+= 1` starts from the wrapped child's count, coupling two modules and delaying or suppressing their post-backward releases. Check `module.__dict__` here, as the adjacent `pre_bwd_fn`/`post_bwd_fn` guards do.

This issue also appears on line 421 of the same file.

- jinyouzhi · comment · 2026-10-30T15:32:42Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8690#discussion_r4425377301)

File: `deepspeed/runtime/zero/parameter_offload.py` · line 419

[P1] Do not keep one lifetime counter across checkpoint recomputation graphs

Initializing this counter only once introduces a reproducible regression with `checkpoint(..., use_reentrant=False)`. Recomputation executes input wrappers whose setup increments `ds_grads_remaining`, but those recompute-graph wrappers do not all receive a matching backward. With the reset removed, a sequential linear ends successive optimizer steps at 1, 2, 3, 4; a linear used in two checkpointed branches ends at 2, 4, 6, 8. The `== 0` release condition is then never reached for those layers. On 2 L20s, master executes 13 post-backward callbacks per sequential-model step, while this patch executes only the root callback; in the larger CPU-offloaded case, maximum AVAILABLE parameter storage increases from 16.06 MiB to 193.50 MiB under non-reentrant checkpointing. Gradients still match, so loss/gradient-only tests miss this regression. Counter ownership needs to follow the relevant forward/backward invocation or graph, excluding unmatched recompute registrations, rather than persisting all increments across optimizer steps. Please cover repeated non-reentrant backwards and layerwise parameter release in the regression test.
