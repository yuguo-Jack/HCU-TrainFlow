# Fix out-of-bounds row access in inference v2 layer_norm/rms_norm kernels for hidden sizes <= 128

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8886) · state: open · merged: False

## Original PR description

Fixes #8831

## Problem

For `elems_per_row <= 128` the inference v2 norm launchers pack several rows into one 256-thread block, but the kernels have no row bound. When `rows` is larger than the rows per block and not a multiple of it, the last, partially filled block loads and stores rows past the end of every input and output. Reachable through `CUDARMSNorm` with a small `channels`, e.g. the per-head Q/K RMSNorm of EXAONE4 / EXAONE 4.5 (head_size 64 or 128, rows = tokens * heads).

## Fix

- Pass `rows` to the `rms_norm`, `pre_rms_norm`, `fused_ln` and `fused_residual_ln` kernels.
- Derive the row index from the expression already used for `block_offset`, and mask the global loads and stores of rows past the end.
- Threads past the end still take part in the block reductions, so the grid and block shape stay the same. In-bounds outputs are bitwise unchanged.

Same change as #8830 makes for the v1 kernels in `csrc/transformer/inference`.

## Tests

- Every kernel output in `test_rms_norm.py`, `test_post_ln.py`, `test_pre_ln.py` and the new `test_ln.py` (`CUDAFPLN` had no test in-tree) is allocated in front of 256 canary rows. A write past the last row fails under plain pytest, without compute-sanitizer.
- One sub-block shape per threads-per-row dispatch (1, 2, 4, 8, 16), each with one row more than fits in a block, in fp32, fp16 and bf16.
- `assert_rows_independent`: each row of a batched launch must match the same row run alone, within the dtype tolerance. The generic bf16 tolerance (rtol 0.48) is loose enough to accept a row normalized with its neighbour's statistics, so the norm tests use (3e-2, 1e-2) for bf16, measured with a 5x margin over all five kernels and the existing large shapes. No global tolerance change.

## Compatibility matrix

- **Validated:** inference v2 core ops on CUDA; fp16 and bf16 for 8-128 channels (sub-block schedule) and the existing 1024-14432 channel shapes; fp32 for 4-64 channels and the large shapes.
- **Not validated:** ROCm builds, pre-sm_80 GPUs, end-to-end inference v2 model runs (e.g. EXAONE4 through the ragged engine).
- **Not applicable:** ZeRO stage, offload, training parallelism. Inference-only kernels.

## Not a duplicate

No open PR references #8831. #8830 (OOB rows), #8743 (`rows == 0`) and #8827 (fp32 65-128 channels launches no kernel) change only the v1 kernels under `csrc/transformer/inference/csrc/`. The v1 kernels, the v2 rms and layer norm kernels, and the other v2 kernels under `kernels/{core_ops,ragged_ops}` were checked; only the v1 and v2 norm kernels pack rows per block this way.

<details>
<summary>Related v2 defects not fixed here (same on master)</summary>

- fp32 with 65-128 channels: `threads_per_group == 32` falls through the sub-block dispatch and no kernel is launched (v2 sibling of #8827). The LN tests skip that cell with an explicit reason.
- `rows == 0` divides by zero in all four v2 launchers (v2 sibling of #8743).
- `rms_norm.cpp` has no `dim() == 2` or contiguity check; `layer_norm.cpp` flattens 3-D inputs, so the two bindings disagree.
- `block_offset` is `int` in all four kernels and overflows past 2^31 elements. The new `row` index adds no overflow of its own.
- `csrc/quantization/quantize.cu` (`cached_quantization`) uses the same row packing with bounded stores but unbounded loads.
- `get_dtypes()` in the v2 test utils caches the first caller's filtered list, so under the directory-level CI invocation later callers lose fp32 (found by the Codex review here). Split out into its own PR so this one stays a kernel fix.

</details>
