## Summary

MiniMax-M3's stock transformers attention builds a dense `[batch, 64, S, S]` mask in its 57 sparse layers (32 GiB at
16,384 tokens), so the full 426B model stops at 14,336 tokens per GPU on 4 nodes of 8 H200. This PR adds a
replacement for those layers whose memory and time grow linearly with the sequence length:

- `deepspeed.models.minimax_m3_vl.replace_attention(model)` swaps it in before `deepspeed.initialize`. Parameter names
  and state-dict keys do not change.
- Two implementations of the same attention: Triton kernels adapted from flash-linear-attention (default for bf16 and
  fp16 on an accelerator that runs Triton), and plain PyTorch (CPU, float32, or shapes the kernels do not take).
- An optional sequence split over a process group (`set_context_parallel_group`), for 65,536 tokens per sequence.
- The indexer's block scores in one Triton kernel (`index_block_max`, same `kernel` choice): one layer's selection for
  16,384 queries over 65,536 keys takes 2.8-5.7 ms instead of 60.5 ms on one H200, with exact float32 products. On
  the full model (4 nodes, DeepSpeed study tree with CPU binding) 114.9 s per step with the old indexer (which ran in
  bf16 under the engine's autocast, the bug fixed here) to 102.0 s with the kernel.
- On the full model, 4 nodes of 8 H200, 65,536 tokens per sequence: 218.3 s per step with the PyTorch path, 130.9 s
  with the Triton kernels (1.67x), the same peak GPU memory, and losses within 0.003.

## Problem

In each of MiniMax-M3's 57 sparse layers, a lightning indexer picks, for each query and key-value head, 16 blocks of
128 keys (2,048 keys per query). On its eager and SDPA paths, transformers' `MiniMaxM3VLAttention`:

- scores every query against every key as float32 `[batch, 4, S, S]` in the indexer;
- expands the selected blocks into a dense additive mask `[batch, 64, S, S]` (`build_block_mask`): 32 GiB in bf16
  at S = 16,384;
- runs dense attention under that mask, so time also grows with S squared.

On 4 nodes of 8 H200 the full model trained at 14,336 tokens and failed at 16,384 on the mask allocation.

Existing kernels, checked on H200 before writing this one:

| Candidate | Finding |
|---|---|
| MiniMax-AI/MSA (official) | forward only (prefill, paged decode), needs compute capability 10.0; H200 is 9.0 |
| fla `ParallelNSAFunction` (fla 0.5.2) | right shapes; its backward fails with "CUDA error: an illegal instruction" under Triton 3.4.0 |
| fla main (`1fe52b5d`) | forward and backward work, but the backward does not take queries that are the last part of a longer key sequence (needed for the sequence split), and a block selected by every query sets the dK/dV time |
| tilelang `example_tilelang_nsa_bwd.py` (0.1.14) | its block-mask kernel does not skip padded block ids (`-1`), and writes the mask by slot while `bwd_dkv` reads it by block id |

## The change

| File | What |
|---|---|
| `deepspeed/models/minimax_m3_vl/selected_attention.py` (new) | Triton forward, dQ and dK/dV kernels, adapted from fla `fla/ops/nsa/parallel.py` and `fla/ops/utils/csr.py` at `1fe52b5d` (MIT). Changes from fla: (1) the backward also takes queries that are the last `TQ` of `TK` keys; (2) the softmax scale multiplies the float32 scores instead of rounding `q * scale` to bf16 (output error 2.2-2.4e-3 instead of 2.7-3.4e-3); (3) a key block's list of selecting queries is split over programs of at most 1,024 queries that add float32 partial sums atomically, so block 0 (chosen by every query) no longer sets the dK/dV time; (4) only the fixed-count, equal-length path. `selected_attention_supported()` says which shapes it takes: query heads per key-value head, head dim and block size powers of 2 of at least 16 |
| `deepspeed/models/minimax_m3_vl/block_sparse_attention.py` (new) | the same attention in plain PyTorch with its own backward: per chunk of query rows, gather the selected blocks, float32 scores and softmax, save only the float32 log-sum-exp; the backward recomputes the probabilities and adds dK / dV in float32 buffers |
| `deepspeed/models/minimax_m3_vl/attention.py` (new) | `DeepSpeedMiniMaxM3VLAttention` keeps the source module's parameters and attribute names and changes only `forward`: projections, QK-norms and partial rotary as in transformers, then the indexer run `index_query_chunk` rows at a time (same selection, `[batch, 4, 2048, S]` scores instead of `[batch, 4, S, S]`), then the attention. `kernel="auto"` (default), `"triton"` or `"torch"`. Decoding with a cache and calls with an attention mask run the stock forward unchanged (a warning is logged once for the mask case). With `set_context_parallel_group(group)`, each rank holds consecutive equal chunks of one sequence; the 4 key-value heads and the indexer key are all-gathered, and their gradients reduce-scattered back. `DeepSpeedMiniMaxM3VLDenseAttention` does the same for the 3 dense layers (`replace_attention(..., dense=True)`) |
| `deepspeed/models/minimax_m3_vl/index_kernel.py` (new) | `index_block_max(q, keys, positions, block_size)`: each query's maximum score per key block, causal by position, `-inf` for a block with no visible key. A program takes 128 queries of one index head and 8 key blocks; `tl.dot` on the bf16/fp16 inputs with float32 accumulation (exact products, as the float32 matmul), mask, block maximum, store; blocks after every query of the tile are stored as `-inf` without computing. Output `[batch, heads, queries, blocks]` float32 (128 MiB at 16,384 x 512 x 4 heads) instead of the 2 GiB of float32 scores per 2,048-query chunk. `select_blocks(..., use_kernel=True)` uses it for all local queries at once when the inputs are bf16/fp16 on an accelerator with Triton (`kernel` other than `"torch"`); otherwise the float32 matmul runs, with autocast disabled so it stays float32 under the engine's bf16 `torch_autocast` |
| `deepspeed/models/minimax_m3_vl/__init__.py`, `deepspeed/models/__init__.py` (new) | exports. `import deepspeed` does not import `deepspeed.models`. `deepspeed/models/__init__.py` is byte-identical to #8659's |
| `docs/code-docs/source/models/minimax_m3_vl.rst` (new), `docs/code-docs/source/index.rst` | API page; the index entry is identical to #8659's |

| `test_key_gradients_summed_over_every_query_keep_float32_accuracy` (torch, triton) | bf16 accumulation of dK / dV when all 8,192 queries select block 0 (must stay within 1e-2 of float32; an autograd gather fails at 3.9e-2) |
| `test_replacement_matches_transformers_model`, CPU | a replaced model that differs from transformers: loss to 1e-5 and every parameter gradient to 1e-4 against the stock SDPA path; the indexer gets no gradient, as in transformers |
| `test_replace_keeps_names_and_runs_stock_forward_with_cache_or_mask`, CPU | renamed parameters, replaced dense layers, or a wrong cache / padded-batch path |
| `TestMiniMaxM3AttentionZeroStage3` (2 ranks) | the replaced layer or the no-grad indexer running on unfetched ZeRO-3 parameters |
| `test_auto_kernel_runs_triton_for_bf16_on_gpu` | `kernel="auto"` silently taking the slow path for bf16 on a GPU (attention and, since 2026-10-13, the indexer kernel: 2 calls each). With MiniMax-M3's 16 blocks of 128 keys this happens for sequences of 257 to 1,920 tokens, the lengths with 3, 5-7 or 9-15 blocks. Fixed by rounding the range up to a power of 2 and masking the extra columns |
| `TestMiniMaxM3AttentionContextParallel` (2 ranks; torch, triton) | wrong gathered keys, wrong global positions in the indexer or the attention, or wrong reduce-scattered key/value gradients: a sequence split over 2 ranks against the whole sequence on one |
| `test_index_block_max_matches_reference` (queries from position 0 and 700; 1,000 keys, blocks of 128) | the indexer kernel against masked float32 scores reduced per block: a wrong mask, a wrong last partial block, or blocks in the future of a later rank's queries not set to `-inf` |
| `test_index_kernel_selects_the_float32_blocks` | the kernel path changing the selection beyond near-ties (at most 0.1% of slots against the float32 path, 2,048 tokens), and that the kernel ran (call count), so the test cannot compare the float32 path with itself |
| `test_block_selection_ignores_autocast`, CUDA | the indexer's float32 scores turning into bf16 under the engine's bf16 autocast (`torch_autocast`): found in a 4-node MiniMax-M3 profile, where the score matmul, the mask and the block maxima ran in bf16 (3,648 bf16 GEMMs and bf16 max reductions per step on one rank). `select_blocks` now computes the scores with autocast disabled. 2,048 tokens, 128 blocks per query, 3 selected; fails without the fix |
