# Recover legacy Torch checkpoints in zero_to_fp32

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8901) · state: open · merged: False

## Original PR description

Valid ZeRO checkpoints saved with `"checkpoint": {"checkpoint_serialization": false}` fail in `zero_to_fp32` because `parse_optim_states` unconditionally passes `mmap=True` to `torch.load`, which rejects legacy Torch serialization.

Select mmap per optimizer shard using the standard-library ZIP detector. ZIP checkpoints retain the existing mmap path; legacy checkpoints use regular CPU loading. No source checkpoint rewrite, API/configuration change, or broad exception fallback is added. Legacy files cannot be memory-mapped and may require substantially more host memory; no speed or peak-memory improvement is claimed.

The regression writes real files with `TorchCheckpointEngine` for ZeRO-1/2/3 and legacy, ZIP, and mixed-shard serialization. Public eager/lazy recovery and indexed, sharded FP32 export must exactly match the original small tensors, including uneven partition padding.

Validation: one Apple M3 CPU (8 cores), 16 GiB RAM, macOS 15.1 arm64; Python 3.12.14, torch 2.14.1, DeepSpeed source `fb5e960b` (0.19.9+fb5e960b). `DS_ACCELERATOR=cpu`, CPU/Gloo; no GPU/accelerator driver used.

```bash
DS_ACCELERATOR=cpu OMP_NUM_THREADS=1 PYTHONPATH=.:tests python -m pytest \
  tests/unit/checkpoint/test_convert_checkpoint.py -k 'not TestCheckpointConvert' \
  tests/unit/utils/test_get_optim_files.py --torch_ver=2.14 -q
pre-commit run --files deepspeed/utils/zero_to_fp32.py tests/unit/checkpoint/test_convert_checkpoint.py
```

- Unchanged source: the new nine cases give 6 legacy/mixed failures with the mmap-format error and 3 ZIP passes. Patched source: the above suite gives **23 passed**, including all nine new cases. All applicable changed-file pre-commit hooks passed.
- Supplemental local two-process CPU/Gloo experiment: actual training for two steps, save and recover, ZeRO-1/2/3 × legacy/ZIP = **6 configurations passed**. Eager/lazy recovery is bitwise equal to the saved parameters; FP32/FP16/BF16 sharded exports equal the reference cast to the requested dtype. Unchanged converter fails all 3 legacy checkpoints and passes the 3 ZIP controls on those same files.
- Both recovery scripts copied by `save_checkpoint` (`zero_to_fp32.py` and `zero_to_torch.py`) pass on legacy and ZIP ZeRO-3 checkpoints: **4 CLI checks**.

This restores compatibility with an existing serialization option. #6658 introduced mmap-based recovery; open #8376 concerns tied safetensors, #8378 frozen-parameter dtype, #8530 debug mode, #8681 ZeRO-0, and #6655 parallel conversion; none addresses this legacy-load failure. `zero_to_torch` delegates to this converter and benefits from the same fix. The universal converter and runtime Torch loader use ordinary `torch.load` and do not share this unconditional-mmap defect.

Scope: local CPU/offline conversion with two DP shards and FP32 training masters. GPU training, offload, MoE/TP/PP and other accelerators were not validated. No training arithmetic or convergence change is introduced. AI assistance was used for investigation, implementation, testing and review.

The human submitter reviewed every changed line, ran the relevant tests, and confirmed the DCO signoff.


Local recheck on 2026-10-28, unchanged head `5e8d9e1f`: Apple M3/macOS ARM64, Python 3.12.13, torch 2.14.1, CPU; the conversion and optimizer-file suites above report **23 passed, 7 deselected**, and all applicable changed-file pre-commit hooks pass. No additional GPU validation is claimed.
