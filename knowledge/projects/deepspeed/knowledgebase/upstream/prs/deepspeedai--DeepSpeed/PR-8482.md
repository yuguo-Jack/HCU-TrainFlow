- jinyouzhi · COMMENTED · 2026-10-30T15:46:37Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8482#pullrequestreview-5714831065)

I reproduced two blocking lifecycle regressions on actual devices. This independently confirms the earlier discussion: this patch is not yet a reliable fix for #8481.

**Setup and comparison:** 2 x NVIDIA L20 (46,068 MiB each), driver 580.173.02, PyTorch 2.14.1+cu130, CUDA 13.0, NCCL, Python 3.10.22. Compared pristine current master `27360990020b0619b744e5fc5e6e4d6e9de3fb79` with the exact current PR diff at `2bf581f22af70a6f6b99f2610147bb211a0b6f53` applied to that master, not the PR's historical base.

The standalone FP32 ZeRO-3 model has three blocks of `tanh(base(x) + 0.1 * B(A(x)))`, hidden width 128, rank-8 adapters, frozen or trainable base weights. Parameter persistence, maximum reuse distance and prefetch bucket size are zero; overlap is disabled. A dense unsharded reference checks loss, input gradients, DP-averaged parameter gradients and SGD updates.

**Findings:**

1. With ordinary sequential `use_reentrant=True` checkpointing, frozen base weights and gradient-requiring inputs, both ranks fail in the first backward with `AttributeError: 'Linear' object has no attribute 'ds_grads_remaining'` at `PostBackwardFunctionModule.backward`. The same configuration passes on master. The graph-task guard skips initialization during recomputation but does not stop that autograd node from running backward. The callback is also initialized only inside the guard, so initializing the module counter alone would not fully repair the lifecycle contract.
2. When each block is also called once on a discarded branch before its used call, the PR leaves the base-linear counter at **1, 2, 3, 4** over four optimizer steps, versus **0, 0, 0, 0** on master. This reproduces on both ranks, for frozen and trainable base weights, with no checkpointing and with non-reentrant checkpointing. Per-step post-submodule-backward callbacks fall from **13 on master to only the root callback (1)** with the patch. Gradients and updates still match the dense reference, so numerical-only checks miss the parameter-release failure. Root/later cleanup can hide it at the end of backward; this evidence is suppressed layerwise release, not a claim of an unbounded cross-step GPU-memory leak.

Control coverage: eight configurations with all branches contributing to loss (sequential/shared blocks x frozen/trainable base x no/non-reentrant checkpointing) pass four-step loss/gradient/update checks with the patch. That does not cover the failing reentrant and discarded-branch cases above. Please add on-device repeated-step regression tests for these cases and verify timely parameter release inside backward, not only end-of-step numerical parity.

Scope is synthetic adapter modules, not a full PEFT/Qwen/Wan training run; FP32 only. This review does not claim that every #8481 topology has been reproduced or fixed. Harness, logs and rank-local counter/release traces were retained. Prepared with GitHub Copilot CLI assistance.

[P1] Preserve valid backward state for reentrant recomputation

On 2 L20s, a plain sequential ZeRO-3 model with frozen base weights plus trainable low-rank adapters and `checkpoint(..., use_reentrant=True)` fails on its first backward on both ranks: `AttributeError: 'Linear' object has no attribute 'ds_grads_remaining'`. Master passes the same case. The initial checkpoint forward runs without grad; the recomputation runs with an active graph-task ID, so this condition skips the counter and `ctx.post_backward_function` initialization even though the resulting wrapper node later executes `backward()`. That method unconditionally accesses the counter and may access the missing callback. Please make initialization/increment/decrement/callback ownership consistent with whether the node participates in backward; simply initializing the module counter elsewhere does not address the missing callback. This is the runtime failure anticipated in the earlier review thread.

[P1] Do not carry unmatched forward registrations across optimizer steps

Together with deleting the reset in `_post_backward_module_hook`, this one-time initialization leaves permanent increments from calls whose outputs never reach the loss. Reproduction: call each block once on `x * 0.3` and discard the result, then call it on `x` for the actual loss. On both L20 ranks, each base-linear counter ends successive backwards at 1, 2, 3, 4 (master: 0, 0, 0, 0); layer post-backward release callbacks disappear, leaving only the root callback. This occurs with no checkpointing as well as `use_reentrant=False`, and with frozen or trainable base weights, so the new graph-task guard does not prevent it. Numerical parity still passes while gathered parameters lose timely layerwise release. Counter accounting needs a graph/invocation lifetime and handling for branches not traversed by backward, rather than a counter that persists indefinitely.
