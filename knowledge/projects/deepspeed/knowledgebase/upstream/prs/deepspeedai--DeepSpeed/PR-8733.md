# Add an opt-in fused gate+up grouped GEMM for AutoEP experts

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8733) · state: closed · merged: True

## Original PR description

AutoEP's grouped experts run the gate (`w1`) and up (`w3`) projections of the same routed rows as two grouped GEMMs. In the backward pass, they compute two input-gradient GEMMs and add the two BF16 results. This adds an opt-in `expert_parallel.gate_up_impl="fused"`, which runs both projections as one `torch._grouped_mm` over the two weights, concatenated on each call.

### Change

- `GroupedExperts(gate_up_impl="fused")` concatenates `w1` and `w3` per call and runs one grouped GEMM with `2 * hidden_dim` output columns.
  - The backward pass therefore has one input-gradient GEMM, which accumulates both projections in FP32, and no separate addition.
- The activation reads the two halves of the packed output in place:
  - `swiglu` uses a new Triton kernel, `swiglu_packed`, with the same FP32 math as the existing `swiglu` kernel.
  - The other registered forms (`geglu_tanh`, `swiglu_clamped`, `swiglu_oai`) run their eager expression on views of the halves.
  - New forms can register a `packed_fused_fn`.
- The parameters keep their separate `w1`/`w3` layout. Checkpoints, universal checkpoints, expert tensor parallelism and optimizer state, including Muon's per-expert treatment, are unchanged.
- The default, `"separate"`, keeps the existing path.
- `"fused"` is rejected rather than ignored when the experts would not run `torch._grouped_mm`:
  - `use_grouped_mm=false`, at config validation and in `GroupedExperts`;
  - devices that select the Triton grouped GEMM, unless `disable_triton_grouped_mm=true`.
- Docs: `autoep.rst` and the config reference.

### Numerical and autograd contract

The forward expression and parameter-gradient semantics are unchanged. Exact output/weight-gradient equality is an observation in the tested H100 cases, not a guarantee across GEMM shapes, implementations or hardware. The input gradient can differ because it is accumulated in one FP32 GEMM rather than as two rounded BF16 results added. The FP64 regression now uses the same represented BF16 weights as the tested paths, rather than the original pre-quantization FP32 weights; its existing relative-L2 bound (fused error <= 1.05 * separate error) is unchanged. This is not a universal accuracy-improvement or bitwise-equivalence claim.

Cross-GEMM output and parameter-gradient assertions now use the existing grouped-GEMM BF16 policy (`rtol=0.02`, `atol=0.02 * max(abs(reference))`) rather than zero tolerance. The skewed/empty-expert forward and smooth-form parameter gradients use the independent FP64 reference. Clamped-form parameter gradients use an independent dense BF16 reference, because rounding a projection across a clamp boundary changes its derivative discontinuously; the bound is not enlarged to absorb those discontinuities. The input-gradient relative-L2 comparison is unchanged. The multi-step test uses the same policy for comparisons across algorithms, while saved/reloaded parameters, optimizer momentum tensors and parameter-group configuration must still match exactly. Exact parity checks between the two implementations of the same elementwise SwiGLU kernel remain unchanged.

The packed SwiGLU Triton path has first-order gradients only: `create_graph=True` raises rather than silently dropping its second derivative. Forward and backward select the input's CUDA device and its current stream, restoring the caller's current device. The eager expressions for the other activation forms and the default separate path are unchanged.

### Tests

- CPU, `TestFusedGateUp` in `tests/unit/v1/moe/test_autoep_expert_activation.py`:
  - packed versus separate halves for every registered form, forward and backward;
  - only `swiglu` has a packed kernel;
  - the default is unchanged;
  - unsupported settings are rejected (bad value, `use_grouped_mm=false`, Triton grouped GEMM path), at config validation and in `GroupedExperts`;
  - the config reaches the replaced experts, whose parameters remain `w1`, `w2`, `w3`.
- Earlier GPU evidence, on one H100 (305 passed): `test_swiglu_triton.py`, `test_autoep_expert_activation.py` and `test_autoep_unit.py`.
  - `swiglu_packed` matches the existing `swiglu` kernel's values exactly, forward and backward (`rtol=0`, `atol=0`, not a signed-zero bit-pattern assertion). Covered: FP32/FP16/BF16, odd widths, 3-D inputs, empty inputs, non-contiguous input, and an odd last dimension (rejected).
  - The fused path joins `test_grouped_gemm_paths_match_the_for_loop` for every form.
  - New `test_matches_separate_with_skewed_and_empty_experts`, for every form, with an empty expert and unaligned rows:
    - output and `w1`/`w2`/`w3` gradients match exactly in the tested shapes;
    - the original relative-L2 FP64 error comparison is retained with the corrected represented-weight reference described above.
  - Not part of this change: the 2 failures are `TestMiniMaxM3Block::test_replaced_block_matches_hf_block`. That preset requires Transformers >= 5.15.0, and the image has 5.12.0.
- The shipped `GroupedExperts`, one H100, Qwen3-30B-A3B per-rank expert shape (131,072 routed rows, hidden 2048, expert hidden 768, 16 local experts, BF16):

  | Per call (ms) | Forward, no grad | Forward | Backward | Total |
  |---|---:|---:|---:|---:|
  | `"separate"` | 2.149 | 2.292 | 4.857 | 9.298 |
  | `"fused"` | 2.224 | 2.236 | 4.321 | 8.781 |

  Output and all weight gradients matched exactly; the input gradient differed by 2.9e-3 relative.
- End to end, Qwen3-30B-A3B on 8 H100s:
  - Setup: expert parallel size 8, micro-batch 4, 16 accumulation steps, sequence length 4096, DeepEP, reentrant activation checkpointing, BF16 parameters and Adam state, 30 steps with 10 warmup.
  - Measured with an equivalent benchmark patch on our benchmark base: the same concatenation and the same packed SwiGLU kernel.
  - Separate 22,018.8 / 22,018.5 ms against fused 21,601.2 / 21,608.4 ms, in two pairs in the same job: **-414 ms (-1.9%)**.
  - Step-1 loss identical. Later losses agree within same-arm repeat noise.
  - Peak allocated memory unchanged; reserved memory about 0.4 GB higher.

### Review follow-up validation

- Current-master targeted validation on NVIDIA H100 80GB HBM3, torch 2.10/CUDA 13.0, Triton 3.6.0 and transformers 5.12.0: **83 passed, 0 skipped** (the full 63-case SwiGLU file plus 20 `TestFusedGateUp` cases). The SwiGLU file also passed **63/63 with no skips under `pytest --forked`**. Cross-device cases used two GPUs; the lifecycle cases use the actual native grouped GEMM.
- With only the same new tests applied to the prior runtime, all four focused guards fail as intended: both FP16/BF16 cross-device cases reproduce Triton's inaccessible-pointer error, and both FP32/BF16 higher-order cases fail because `create_graph=True` was not rejected. This verifies the actual root causes, not an unrelated collection or test-API failure.
- Regressions cover strided packed inputs and upstream gradients, two-device/current-stream selection and caller restoration, explicit higher-order rejection, the corrected FP64 reference, and two SGD updates with two accumulation micro-batches per step. All four activations run with and without reentrant recomputation; a model/optimizer state-dict round trip between updates keeps the separate `w1`/`w2`/`w3` names and shapes and checks the next update against the independent separate path.
- The SwiGLU test file imports its runtime in the worker, not during collection, so its Triton driver probe is deferred until after `pytest --forked` starts the worker.
- The follow-up changes launch-device selection and unsupported-autograd handling, not the GEMM implementation, kernel arithmetic, launch configuration, default or parameter layout. The earlier local and E2E performance evidence is reused without retiming; the historical percentages are not new measurements of these guards.
