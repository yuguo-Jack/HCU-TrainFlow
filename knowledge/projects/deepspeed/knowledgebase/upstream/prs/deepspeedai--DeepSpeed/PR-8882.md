# Strip ANSI color codes before parsing FAILED lines in cpu-multi-triage

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8882) · state: closed · merged: True

## Original PR description

Fixes #8881.

The `Extract the failing test files` step in `cpu-multi-triage.yml` greps the nightly log for `FAILED unit/...`, but the nightly pytest runs with `--color=yes`, so every summary line carries ANSI sequences between `FAILED` and the path:

```
\x1b[31mFAILED\x1b[0m unit/checkpoint/test_convert_checkpoint.py::TestCheckpointConvert::...
```

The pattern never matched, `failing-tests.txt` stayed empty, and the job exited 1 ("no FAILED test files found in the nightly log") — see the 10-21 triage run: https://github.com/deepspeedai/DeepSpeed/actions/runs/39548955267. As a result no issue was auto-opened for the first `test`-class nightly failure, and the `nightly-cpu-multi-last-green` tag stopped advancing.

Strip the escape codes in the pipeline before grepping, keeping the colored log intact for humans reading the Actions UI:

```diff
           gh run view "$NIGHTLY_RUN_ID" --log \
+            | sed 's/\x1b\[[0-9;]*m//g' \
             | grep -oE 'FAILED unit/[^[:space:]]*\.py' | sort -u \
```

I asked agent to reproduce in local, and here are the summary from it:

Since **gh 2.92.0**, `gh run view --log` always passes logs through `asciisanitizer` (`copyLogWithLinePrefix` in `pkg/cmd/run/view/view.go`), with no TTY check. That rewrites the ESC byte as the two literal characters `^[`. The failed triage job ran on the `ubuntu-24.04` image 20261012.334, which ships **gh 2.102.0**. A local gh of 2.91 or older still prints raw ESC, which would explain why the filter worked for you.

I replayed this step against the 10-21 nightly log (run 39543136857) with gh 2.102.0:
- The log has 0 raw ESC bytes and 4486 literal `^[`, e.g. `^[[31mFAILED^[[0m unit/checkpoint/test_convert_checkpoint.py::...`
- master: no files
- this PR: no files, so the step still exits 1
- stripping both forms: `tests/unit/checkpoint/test_convert_checkpoint.py`

```suggestion
            | sed -E 's/(\x1b|\^\[)\[[0-9;]*m//g' \
```

This handles raw ESC, `^[` and uncolored lines, so it works with any gh version. It's worth noting why in the comment above the pipeline, so nobody simplifies it back later.

Looks like agent is not happy with the changes in the `nightly-triage.yml`. Here are the summary: 

 `cpu-torch-multi-latest` runs pytest on the GitHub runner from `tests/`, but `modal-torch-latest` runs it on a remote Modal/AWS machine from the repo root, and `ci/torch_latest.py` relays the output into the job log. A failure there looks like this (from nightly [38548415627](https://github.com/deepspeedai/DeepSpeed/actions/runs/38548415627); `\x0a` is an escaped newline):

```
[sandbox:run pytest] \x0a[gw0]\x1b[36m [  1%] \x1b[0m\x1b[31mFAILED\x1b[0m tests/unit/v1/zero/test_zero_hook_count_regression.py::TestHookCountRegression::test_training_step_succeeds_after_fix[3]
```

Two things in that line keep the copied pipeline from matching:

1. **The color codes are plain text.** The relay passes every line through `_single_line()`, which writes non-printable characters as escape text, so ESC arrives in the log as the four characters `\x1b`, with no ESC byte left for gh to rewrite as `^[`. In the sed pattern, `\x1b` is the ESC byte and `\^\[` is gh's `^[`, so neither matches; `\\x1b` (a backslash followed by `x1b`) does.
2. **Paths start with `tests/`.** The grep needs `FAILED tests/unit/v1/`, and the last `sed` should only drop `FAILED ` (adding `tests/` again gives `tests/tests/...`). The existing comment about the working directory being `tests/` doesn't apply to this nightly.

On three earlier nightlies whose logs contain pytest failures (38548415627, 37606328579, 37295959814), this step's script with the current PR exits 1 with "no FAILED test files found" on all three; with the suggestion below it lists 9, 10 and 5 files, matching an independent parse of the same logs. Those runs were classified `timeout`, so triage never reached this step for them, but a `test`-class run relays pytest output the same way.

```suggestion
          # The nightly runs pytest from the repo root, so failures read
          # "FAILED tests/unit/v1/...". ci/torch_latest.py relays that output
          # with ESC written as the literal text "\x1b"; also strip the raw ESC
          # byte and gh's "^[" in case output ever reaches the log unescaped.
          gh run view "$NIGHTLY_RUN_ID" --log \
            | sed -E 's/(\x1b|\^\[|\\x1b)\[[0-9;]*m//g' \
            | grep -oE 'FAILED tests/unit/v1/[^[:space:]]*\.py' | sort -u \
            | sed 's|^FAILED ||' > failing-tests.txt
```
