# Check that converting through an affine map writes every element once

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8975) · state: open · merged: False

## Original PR description

Conversion trusts a map further than it checks it.

- `rebuild` (what `ds_to_universal` calls on convert) runs only `validate()`. That checks each rank's element count and where pieces write in the shard, from metadata, but it never looks at the source side. So a map can pass it while two ranks claim the same block of the parameter and no rank holds another.
  - `rebuild` then returns whatever `torch.empty` left in the elements nobody holds.
  - It also lets one rank's block overwrite the other's with no comparison.
- `extract` (what the AutoTP restore path calls) runs no check at all.
- A destination that wraps past the end of a shard row is not a box, so `validate()` cannot place it. #8922 made `validate_coverage()` complete for such destinations, but conversion does not call `validate_coverage()`, because that check walks elements in Python.

Reproduction on `master`:
1. Take two ranks with shards of 4 elements each, for an `(8,)` parameter.
2. Point rank 1's piece at source offset 0 instead of 4.
3. `validate()` passes. `rebuild` returns rank 1's values in elements 0–3 and uninitialised memory in 4–7, with no error.

How often this happens:
- I fuzzed the in-tree constructors (contiguous split, replicated, segmented, block gather). Each case is a random 2-D shape, TP 2–4 with uneven widths, and one offset or stride of one piece corrupted.
- On `master`, **671 of 2,334 corrupted maps converted without an error and produced a wrong tensor**. With this change, none do: each one is refused or still round-trips exactly.
- Every map that passes `validate_coverage()` round-trips exactly on both (801 of 801).
- With the stricter oracle from @0z5a's review (shards built from the uncorrupted map, then rebuilt through the corrupted one; 2,000 cases): master converts 421 silently wrong, this PR none.
- One limit: a corruption that leaves a *valid but different* layout, for example two equal-shaped pieces swapping destinations, passes every map check, because the map is self-consistent and disagrees only with the memory it describes. Catching that takes a runtime digest of the data, not a check on the map.

## Changes

- **`rebuild`**
  - Records who wrote each element of the full tensor (nobody, a single holder, or a replica), one byte per element, and refuses:
    - an element no piece writes;
    - an element written by two pieces unless both are replicas, whichever rank is visited first;
    - replicas that disagree on any element. That includes replicas cut at different boundaries on different ranks. Before, only a piece starting exactly where an earlier one started was compared, so the rest of the replica overwrote it unchecked.
  - Also tracks the shard addresses it reads on each rank, so a destination collision is refused for any stride.
- **`extract`**
  - Runs `rebuild`'s metadata check for its own rank: `validate()` restricted to one rank, through a new `_validate_rank`.
  - Uses the same shard-address mask, so a restored shard never holds uninitialised memory.
- **Both, through `_validate_rank` (and so `validate()`)**
  - Refuse a piece whose source or destination view reaches one address twice within itself.
  - Such a view loses a shard value, and which value survives depends on the device.
  - The check is metadata only: taking the axes that move in order of stride, each stride must clear what the axes before it reach. Every in-tree layout satisfies it.
  - A zero stride now raises a `ValueError` instead of torch's own `RuntimeError`.
- **No change for valid maps.** Error types and messages follow the existing ones (`ValueError`, "twice", "uncovered", "different data"), plus "itself" for the new check.

Cost:
- One byte per element of the full tensor and one per shard element, with vectorised tensor ops and no per-element Python.
- `rebuild` already materialises the full tensor, so the fp32 states that `ds_to_universal` converts need at most a quarter more memory, for the duration of one parameter's conversion.

- jinyouzhi · comment · 2026-11-01T16:39:08Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8975#issuecomment-6560800854)

Thanks, the mask approach is a clean way to make conversion fail closed without per-element Python. Since this was not run on GPU, I ran it on two machines:
- 8x NVIDIA L20 (torch 2.14.1+cu130): test_affine_shard_map / test_affine_transfer_plan / test_zero_affine / test_autoep_affine / test_autoep_affine_universal, 283 passed. On CUDA, rebuild of a 4096x4096 fp32 TP8 column split takes 1.2 ms and 8 extracts take 0.9 ms, so the mask syncs are negligible.
- 8x Intel Arc Pro B70: the same files, 283 passed. extract on a 4096-piece rank takes ~0.04 s, so the added `_validate_rank` is cheap.

Two gaps against the "every element once" contract:

**1. A source view that overlaps itself is still silently wrong.** `covered` only records *that* an element was written, so a single piece whose source strides alias elements writes one element twice and loses a shard value, while the mask ends up all-True:

```python
m = ParamAffineMap((6,), {0: (4,), 1: (3,)}, {
    0: [AffinePiece((2, 2), 0, (1, 1), 0, (2, 1), [0])],   # source addresses 0,1,1,2
    1: [AffinePiece((3,), 3, (1,), 0, (1,), [1])]})
m.validate()  # passes
m.rebuild({0: torch.tensor([9., 8, 7, 6]), 1: torch.tensor([1., 2, 3])})
# CPU:  [9, 7, 6, 1, 2, 3], shard value 8 is dropped, no error
# CUDA: [9, 8, 6, 1, 2, 3], shard value 7 is dropped instead
```
Which value survives the aliased write depends on the device, so the same checkpoint converts to different tensors on CPU and GPU.
With stride 0 torch raises its own `RuntimeError` (internal overlap), but (1, 1) is "too hard" for torch's overlap check and passes. A metadata check that the source view does not overlap itself (sort non-degenerate axes by stride, require each stride >= the span of the inner axes) would close this and give a `ValueError` for the stride-0 case too; the in-tree builders are row-major, so it should not refuse any valid map.

**2. Single-holder vs replica overlap depends on piece order.** The single-holder check only looks at the piece being written now, not at who wrote first:

```python
p = lambda loc: AffinePiece((4,), 0, (1,), 0, (1,), loc)
shapes = {0: (4,), 1: (4,)}
ParamAffineMap((4,), shapes, {0: [p([0, 1])], 1: [p([1])]}).rebuild(...)   # refused
ParamAffineMap((4,), shapes, {1: [p([1])], 0: [p([0, 1])]}).rebuild(...)   # accepted
```
The same map is refused or accepted depending on `pieces_by_rank` order. Keeping a second mask of elements written by multi-holder pieces, and requiring an overlap to be replica-on-replica (`len(piece.locations) > 1 and shared[seen].all()`), would make it order-independent.
