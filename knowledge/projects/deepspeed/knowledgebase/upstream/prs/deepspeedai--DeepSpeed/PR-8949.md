# ZeRO-1/2: preserve gradients across request boundaries until step

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8949) · state: closed · merged: True

## Original PR description

Additionally to https://github.com/deepspeedai/DeepSpeed/pull/8749 another precision issue

Porting this from @seanbell's https://github.com/Snowflake-AI-Research/Arctic-Platform/pull/371


**An accumulation boundary is not necessarily an optimizer step.** A caller can finish several requests with `engine.set_gradient_accumulation_boundary(True)` while delaying `engine.step()` until all requests have contributed. ZeRO-1/2 must retain every request's gradients until that update and must not carry a previous update's gradients into the next one.

This fixes both non-offloaded and CPU-offloaded optimizer paths in `deepspeed/runtime/zero/stage_1_and_2.py`, without changing configuration defaults or adding an application-side workaround.

## Root Cause And Fix

- Non-offloaded optimizers cleared `all_grad_tensors` at every boundary, discarding earlier requests before `step()`. Retain the accumulated tensors until the existing step cleanup. When the separate `param.grad_accum` tensor is cumulative, keep the existing reread behavior so reentrant checkpoint phases do not double-count gradients.
- CPU-offloaded optimizers with FP32 master weights skipped refreshing the persistent host accumulator on a step's first backward when that backward was also a boundary. A subsequent request could then add the previous step's stored gradients. Track each parameter's participation in the current update window instead of relying on the global `micro_step_id`. A first non-boundary contribution refreshes the host accumulator; a first boundary contribution uses only the existing optimizer-partition copy. If another backward follows before `step()`, recover the previous locally owned partition fragment in the accumulation dtype, then allocate or refresh the auxiliary host accumulator. Never reuse a prior update's sum.

**A single-backward update needs no auxiliary allocation or copy.** `_offload_partition_only_param_ids` records FP32-master parameters whose current sum lives only in the optimizer partition. Explicit finalization leaves those already-current gradients intact. `step()` clears both participation sets before either a successful update or an overflow return. Multiple backwards still need an auxiliary accumulator once the second contribution arrives; this change does not claim a speedup for that workload.

**Low-precision masters use a shared buffer instead of the separate FP32-master accumulator.** Their CPU accumulator is a view of the optimizer partition's gradient buffer. On a parameter's first use at a boundary, the existing boundary copy initializes that shared buffer directly, so a second host copy is unnecessary. Register the view and the parameter's participation even when skipping the extra copy; later backwards accumulate into the current window and explicit finalization can restore the shared gradient. A first non-boundary use still initializes the accumulator through the offload helper.

These changes address the [stale-gradient first-use review](https://github.com/deepspeedai/DeepSpeed/pull/8949#discussion_r4419121849), the [low-precision boundary-handling clarification](https://github.com/deepspeedai/DeepSpeed/pull/8949#discussion_r4419154211), and the subsequent single-backward allocation/copy concern. The code names `first_use` and `boundary` explicitly and distinguishes shared-buffer accumulation from the lazily allocated FP32-master accumulator.

**This complements DeepSpeed [#8749](https://github.com/deepspeedai/DeepSpeed/pull/8749), rather than replacing its precision fix.** #8749 preserves FP32 partition gradients, including CPU offload. The remaining defect concerns the lifetime of accumulated gradients when model and accumulation dtypes match. [Arctic-Platform #371](https://github.com/Snowflake-AI-Research/Arctic-Platform/pull/371) motivated the native DeepSpeed repair; AP-specific hooks are not needed by this change.

## Regression Coverage

The existing `tests/unit/v1/zero/test_zero2_offload_multi_backward.py` now includes a 16-case, two-rank integration matrix:

**Each case checks independently derived gradients and actual parameter updates.** Two independent linear projections exercise partition ownership; analytical input-column sums supply the gradient reference and ordinary PyTorch SGD supplies the update reference. Binary-exact fixture values allow zero-tolerance assertions without loosening numerical thresholds.

Eight successive update windows cover a multi-call request, a zero-loss request followed by useful work, consecutive single-call requests, mixed request lengths, a boundary-first request followed by a multi-backward request, a fresh single backward after earlier updates, and two conditional-participation windows. Each projection is absent from the first backward of one window, then contributes repeatedly after having participated in the preceding update. The integration tests compare actual consecutive-single-backward updates; a separate storage regression checks the resource contract.

The existing gradient-safety suite also checks first use after another parameter's backward, with FP32 and BF16 master buffers and boundary/non-boundary first contributions. It checks the summed gradient and actual Adam update against an independent PyTorch optimizer, including a boundary-only overflow after an earlier update has allocated the auxiliary buffer. Additional controls check repeated finalization, partial partition ownership, BF16 accumulation rounding, pending pageable-source copies, and no additional storage or copy for consecutive single-boundary updates. These storage-level tests bypass the ZeRO constructor; they do not claim CPUAdam integration coverage for BF16 master weights.

## Compatibility And Remaining Validation

**The CPU runs validate optimizer-placement logic, not physical GPU optimizer placement or GPU-to-CPU transfers.** The regression is also enabled on hosts with at least two CUDA devices, but GPU execution remains required before claiming on-device coverage. FP16, CPUAdam integration with low-precision master weights, NVMe offload, vendor accelerators, and tensor/pipeline/expert/sequence parallelism were not validated by the new matrix. BF16 master-buffer behavior was validated only in the gradient-safety fixture described above.

Static sibling inspection found that ZeRO-3 refreshes the first microstep's partition buffer and that the BF16 optimizer retains accumulation until its update or explicit zeroing. This PR changes neither implementation. Conditional participation after the first microstep was not validated for ZeRO-3; the inspected code is not evidence that every sibling accumulation case is correct.

Full-model convergence, throughput, and peak-memory measurements were not performed. Only the fixture's auxiliary-allocation and copy-count reductions above are established. GPU transfer cost and performance for repeated-backward workloads remain unmeasured.
