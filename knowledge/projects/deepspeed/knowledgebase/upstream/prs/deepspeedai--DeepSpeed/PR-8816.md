# Use C++20 for NPU op builders on torch 2.12+

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8816) · state: closed · merged: True

## Original PR description

On PyTorch 2.12+, `torch.utils.cpp_extension` builds extensions with `-std=c++20`, but the NPU op builders still append `-std=c++17`, which overrides torch's own flag. This is the NPU counterpart of the XPU fix in #8803.

This PR adds `cpp_standard()` to the NPU builder and uses it in both `NPUOpBuilder.cxx_args` and `AsyncIOBuilder.cxx_args`. The rule is the same one introduced in #8803: C++20 on torch >= 2.12, C++17 otherwise. Scope is NPU only.

CANN officially supports C++20, so the toolchain side is covered:
https://www.hiascend.com/document/detail/en/CANNCommunityEdition/latest/programug/Ascendcopdevg/docs/en/guide/technical_appendix/cpp_standard_support/overview.md

## Testing

Ascend 910B, CANN 8.5.1, with a fresh `TORCH_EXTENSIONS_DIR` for each build. I tested the NPU CPUAdam op, which is the one that actually JIT-compiles through `NPUOpBuilder.cxx_args`:

- **torch 2.12.0 + torch_npu 2.12.0**: C++20 is selected and the op builds against the torch 2.12 headers; results match `torch.optim.AdamW` within the same tolerance used in `tests/unit/ops/adam/test_cpu_adam.py`.
- **torch 2.10.0 + torch_npu 2.10.0**: the default C++17 path is unchanged; a forced C++20 build also compiles and is bitwise-identical to the C++17 build.
- `AsyncIOBuilder` wasn't exercised (no libaio on the test machine; same caveat as #8803).
