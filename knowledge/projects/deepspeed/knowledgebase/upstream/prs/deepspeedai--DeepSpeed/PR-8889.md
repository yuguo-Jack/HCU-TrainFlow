# [BUG] Fix universal checkpoint resume device/dtype mismatch for fused/capturable optimizers (#8884)

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8889) · state: open · merged: False

## Original PR description

### Summary of Changes
This PR fixes a `RuntimeError` occurring when resuming from a universal checkpoint (`load_universal: true`) with client optimizers that use PyTorch's `fused=True` or `capturable=True` (e.g., `AdamW`), where state steps were incorrectly restored on CPU instead of the parameter's target device as a float32 tensor.

- **Step Normalization**: Added `_normalize_step_tensor` and `_normalize_step_for_all_param_groups` to ZeRO optimizers to align restored steps with PyTorch's parameter policy.
- **ZeRO Stage 1/2 & 3 Support**: Updated both `load_hp_checkpoint_state_from_checkpoint_dir` (base optimizer) and `load_hp_checkpoint_state_from_checkpoint_dir_stage3` to normalize step tensors properly after restoring parameter groups and states.

### Testing & Verification
- Added comprehensive unit tests in `tests/unit/checkpoint/test_universal_checkpoint.py` validating normalization and successful execution of engine steps after universal checkpoint resume for both stage 1/2 and stage 3.
- All pre-commit checks and unit tests passed cleanly.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Preserve scalar steps for built-in Adam optimizers**

When a universal checkpoint is resumed with built-in `FusedAdam` (the default DeepSpeed Adam) or `DeepSpeedCPUAdam` (ZeRO-Offload), the saved `step` is a Python integer, but this branch always replaces it with a float32 tensor because those parameter groups have neither `fused` nor `capturable`. Both optimizers then pass `state['step']` to C++ kernels whose signatures take `int`/`size_t` (`csrc/adam/fused_adam_frontend.cpp` and `csrc/adam/cpu_adam_impl.cpp`), so the first post-resume optimizer step receives an incompatible tensor and fails; preserve scalar steps for these optimizer siblings or restrict this conversion to PyTorch tensor-step optimizers.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Skip capturable AdamW cases on the CPU accelerator**

When these tests run with `DS_ACCELERATOR=cpu`, `CPU_Accelerator.is_available()` returns `True`, so the `(False, True)` (`capturable`) parametrization passes this guard in both new loader tests. Each test then runs `torch.optim.AdamW(..., capturable=True)` on a CPU parameter, which PyTorch rejects at `step()` because CPU is not a capturable device, causing CPU-only test runs to fail rather than skip; gate this case on the accelerator device type/support instead of availability.
