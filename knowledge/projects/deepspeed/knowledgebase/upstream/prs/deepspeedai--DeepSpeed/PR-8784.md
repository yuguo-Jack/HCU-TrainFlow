# [Draft] Support HiFloat8 training for Dense Linear and AutoEP on NPU

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8784) · state: open · merged: False

## Original PR description

## Summary

Add opt-in BF16 + HiFloat8 training for selected Dense Linear modules and AutoEP grouped experts on Ascend NPU, using `torchao_npu` for policy, conversion, quantization and GEMM autograd.

Related architecture discussion: [RFC #8777](https://github.com/deepspeedai/DeepSpeed/issues/8777).

## Implementation

- Add a validated `hifloat8` configuration with module patterns, a size threshold and optional selection-count checks. Numerical settings are optional: AO supplies the established `15/15/224` per-tensor recipe; explicit overrides remain supported.
- Probe the requested native kernels before conversion. Reuse one AO policy for ordinary Linear layers and selected `GroupedExperts`, preserving Parameter identity and optimizer/checkpoint integration.
- Keep selection, AutoEP dispatch/padding, expert activation, communication and ZeRO lifecycle in DeepSpeed. Delegate both BF16 and HiFloat8 NPU grouped GEMMs to AO through `trans_b=True` with native `[E,N,K]` weights.
- Retain CPU/CUDA expert dispatch and lazy AO imports. The NPU BF16 grouped path also requires the paired AO implementation.
- Include Qwen3.5 wrapper/text-config support and source-model routing compatibility, plus device-side NPU permutation-index generation for at least 64 source/expert groups. Smaller NPU groups retain the CPU reference path.

```json
{
  "bf16": {"enabled": true},
  "zero_optimization": {"stage": 2},
  "hifloat8": {
    "enabled": true,
    "backend": "torchao_npu",
    "module_name_patterns": ["*.experts", "*.shared_experts.*_proj"],
    "min_numel": 65536
  }
}
```

AutoEP topology is configured separately. `compute_dtype`, when supplied, controls pre-quantization staging and GEMM output; actual GEMM operands remain HiFloat8, and accumulator precision is kernel-owned.

## Validation

Ascend950PR, CANN 9.1.0, PyTorch/TorchNPU 2.11.0, torchao 0.18.0:

- **90 DeepSpeed NPU tests passed**; paired AO tests: **85 passed, 1 empty-Dense native-quantizer skip**.
- Covered selection/configuration errors, Parameter/state compatibility, Dense/grouped forward and gradients, uneven/empty experts and native weight layouts.
- DP2 / ZeRO-2 / gradient accumulation 2: checkpoint at step 2, resume through step 4; subsequent losses, parameters and optimizer state match exactly. Experts are replicated in this lifecycle test.
- Qwen3.5-35B-A3B text-only, EP4 / ZeRO-2: two matched 30-step pairs verify the minimal configuration against the previous explicit recipe. Every rank matches inputs, losses, gradient norms and final trainable BF16 parameters exactly. All 40 layers execute; only layers 0/39 routed/shared experts are trainable, with 12 tensors/rank.

Latest step-P50 changes were **+7.85% and −0.01%**, with identical native call counts and peak NPU allocation. No stable throughput improvement is established; a third comparison failed in a baseline HCCL barrier before DeepSpeed/AO initialization.

## Draft review scope

Review the configuration/backend boundary and whether the Qwen3.5 compatibility and permutation changes should be submitted separately. The current backend is specifically AO/NPU; a generic accelerator-provider interface remains an RFC proposal.

The integration rejects ZeRO-3, AutoTP, Pipeline parallelism and custom model-parallel units. Multi-node, EP8, CUDA hardware regression, full-parameter convergence and framework-wide offload/compile remain separate validation gates.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Restrict FP16 outputs in BF16-only HiFloat8 training**

When `hifloat8.config.compute_dtype` is set to the documented `"float16"` value, this accepts the policy even though HiFloat8 initialization requires a BF16 model. The tutorial states that GEMM results use the selected working dtype, and `_run_experts_npu` returns that result unchanged, so selected Dense/GroupedExperts modules emit FP16 into BF16 residual paths; FP16 plus BF16 promotes to FP32, after which the next ordinary BF16 linear fails on mismatched matrix dtypes. Reject FP16 here or cast converted module outputs back to their input dtype.
