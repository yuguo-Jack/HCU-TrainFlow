# Guard the deprecated tensor model parallel mpu fallbacks

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8801) · state: open · merged: False

## Original PR description

## What's wrong

The three `bwc_tensor_model_parallel_*` helpers in `deepspeed/utils/bwc.py` probe an `mpu` object for successive API spellings, but the final `else` branch calls the deprecated Megatron names unconditionally:

```python
if hasattr(mpu, 'get_tensor_model_parallel_rank'):
    return mpu.get_tensor_model_parallel_rank()
elif hasattr(mpu, 'get_slice_parallel_rank'):
    return mpu.get_slice_parallel_rank()
else:
    return mpu.get_model_parallel_rank()   # assumed to exist
```

An mpu that partitions along a different dimension implements none of the three. `deepspeed/runtime/sequence_parallel/parallel_state_sp.py` exposes only `get_sequence_*` functions, so pairing Ulysses sequence parallelism with ZeRO stage 0 makes `BF16_Optimizer.get_grads_for_norm()` (`bf16_optimizer.py:561`) raise:

```
AttributeError: module 'deepspeed.runtime.sequence_parallel.parallel_state_sp'
has no attribute 'get_model_parallel_rank'
```

That is issue #7833. The same unguarded fallthrough exists in all three helpers (`bwc.py:42`, `:60`, `:78`).

## Fix

Guard the deprecated call and fall back to the values each helper already returns for `mpu=None` — rank `0`, world size `1`, group `None`. Semantically that is correct: an mpu with no tensor model parallel API is not splitting tensors, which is rank 0 of a group of one. It also matches the shape of `bwc_pipeline_parallel_world_size()` just below, which already defaults rather than assuming.

The two supported spellings are still preferred in order, so existing tensor parallel setups take exactly the same path as before.

Note this keeps all three probes. Collapsing them to a single `hasattr(mpu, 'get_model_parallel_rank')` check — as sketched in the issue thread — would silently drop support for `get_tensor_model_parallel_rank` and `get_slice_parallel_rank` and break current Megatron and pipeline-parallel users.

## Not a duplicate

`gh pr list --state open --search "7833 in:body"` and keyword searches for `bwc_tensor_model_parallel`, `get_model_parallel_rank`, and `Ulysses stage 0` return no open PR. In the issue thread @tohtana confirmed "the master branch still doesn't have such a check" and asked for a PR, also noting the world-size helper has the same problem; @nathon-lee asked whether to proceed and the thread went quiet without a PR being opened. @amadhan882 did the original diagnosis and traced it to this line — credit for the root cause is theirs. Happy to close this in favour of their PR if either would rather carry it themselves.

## Testing

New `tests/unit/utils/test_bwc.py` covers all three helpers against four mpu shapes: the current spelling, the slice spelling, the deprecated spelling, and a sequence-parallel-only stub standing in for `parallel_state_sp`. These are plain module-level tests with no dist init, so they run on CPU.

```
$ pytest tests/unit/utils/test_bwc.py -q
15 passed in 5.00s
```

I confirmed the tests fail without the source change — reverting `bwc.py` to master reproduces the reported error at the same lines, while the nine tests covering the supported spellings keep passing:

```
AttributeError: 'SequenceParallelMPU' object has no attribute 'get_model_parallel_world_size'
deepspeed/utils/bwc.py:60: AttributeError
3 failed, 12 passed
```

No new failures in the surrounding suites. `tests/unit/utils/` plus `tests/unit/runtime/test_ds_config_dict.py` report 15 failures both before and after this change; all are environment-related (`deepspeed_shm_comm` JIT load needs `ninja`, plus one unrelated assertion in `test_pin_memory_tracker`), and the count is unchanged.

**Environment:** CPU-only, 2 cores, no accelerator (`get_accelerator()` resolves to `cpu`, `torch.cuda.is_available()` is `False`). torch 2.14.1+cu130, Python 3.12.3, DeepSpeed 0.19.8 at a20acd1.

## Validation gaps, stated plainly

I have no GPU available, so I did not run the multi-GPU Ulysses + stage 0 configuration from the issue end to end. What is verified is the unit-level contract of the three helpers.

Compatibility matrix:

| Cell | Status |
|---|---|
| mpu spellings: current / slice / deprecated / none | validated on CPU |
| ZeRO stage 0 (BF16_Optimizer) + Ulysses, multi-GPU | **not validated** — no accelerator |
| ZeRO 1/2/3, offload, pipeline parallel | **not validated**; untouched code paths, unchanged return values for any mpu exposing a tensor parallel API |

The change affects neither numerics nor memory: for every mpu that previously returned successfully, the returned value is identical. The only behavioural difference is on the path that previously raised `AttributeError`, so there are no convergence, throughput, or peak-memory results to report.

Reviewers who can run the issue's 2-GPU repro would be confirming the last mile here.

For an MPU that actually has the sequence-only shape required to reach this fallback, a ZeRO-0 BF16 step still fails immediately afterward: `BF16_Optimizer.step()` passes `self.mpu` to `get_global_norm_of_tensors()` (`bf16_optimizer.py:390-392`), whose nonempty-gradient path unconditionally calls `mpu.get_model_parallel_group()` (`runtime/utils.py:954-958`).
