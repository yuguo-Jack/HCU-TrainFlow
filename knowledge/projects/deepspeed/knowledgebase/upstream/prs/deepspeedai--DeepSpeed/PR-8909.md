# Fix performance regression caused by comms logger and bug in comms_logger.enabled

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8909) · state: closed · merged: True

## Original PR description

Fixes #8797. With comms logging on, every collective re-read the full history of its timer, so ZeRO-3 step time grew every step and each logged latency was the sum of all earlier calls. Separately, `"comms_logger": {"enabled": false}` turned logging on.

### Root causes
1. **Timer history is never cleared (regression from #7714, v0.18.3).** Logged latencies are cumulative, which changed the original intent. 
2. **The section's `enabled` field is ignored (since #2012).**

### Changes

**`deepspeed/utils/timer.py`**
- `Timer` holds one start/stop event pair, created once and recorded again for each interval, plus a running total and count. It no longer keeps a list of every event pair.
- `elapsed()` returns the latest start/stop interval.
- New `elapsed_total()` returns the sum of all intervals since the last reset.
- `mean()` returns the plain average since the last reset. It used to be a 10% trimmed mean over the stored records.
- Each interval is measured once, when first needed: on a read or at the next `start()`. So `stop()` never waits for the device.
- Reading a timer that is still running stops it, with no automatic restart.
- `SynchronizedWallClockTimer.log()` prints `elapsed_total()`, so every existing log line is unchanged.
- Cleanups:
  - Removed the now-unused `CudaEventTimer`.
  - Added `NoopTimer.elapsed_total()`.
  - `psutil` is imported only when `ThroughputTimer` monitors memory.

**`deepspeed/comm/config.py`, `deepspeed/comm/comm.py`**
- `comms_logger_enabled` now comes from the section's `enabled` field. A missing section is parsed with its defaults, the same way the `compile` section is.
- Inlined `_configure_using_config_file` into `deepspeed.comm.configure()`.
- Removed an outdated comment ("'elapsed' resets events") and the unused `timer_summary` global.
- Removed the `config` argument of `deepspeed.init_distributed()`;

### Related PRs

- **#8798** (open, same issue) caps each timer's history at 1,024 records. That changes the shared timer contract: for example, pipeline iteration time under-reports when `steps_per_print` is above 1024. Logged latencies also stay cumulative, and steps stay much slower than without logging. This PR fixes the cause instead. Its config change addresses the same bug as #8798's.
