# Keep the tensors a model names for fp32 in fp32 in init_inference

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8864) · state: open · merged: False

## Original PR description

Fixes #3177

## Problem
transformers loads the tensors a model lists in `_keep_in_fp32_modules` (under fp16) and
`_keep_in_fp32_modules_strict` (under fp16 and bf16) in fp32, because they overflow or lose precision in
half precision. T5/MT5/UMT5/LongT5/SwitchTransformers list their `wo` projection
(huggingface/transformers#20683, added in Dec 2022 for exactly the FlanT5-XL fp16 case), and 17 MoE
model files (DeepSeek-V3, GLM-4.5, ...) list the routing bias `e_score_correction_bias` under both dtypes.

`InferenceEngine._convert_to_dtype` (`deepspeed/inference/engine.py:521-524`) then calls
`self.module.half()` / `self.module.bfloat16()` on the whole model and casts those tensors with everything
else. With `mp_size=1` and no kernel injection (the reporter's call) nothing else in `init_inference`
touches the model, so this cast is the entire difference from Hugging Face.

Impact: silent-wrong-result. Who reaches it / triggered by: anyone calling
`deepspeed.init_inference(model, dtype=torch.float16)` (fp16 is also the config's default `dtype`) or
`dtype=torch.bfloat16` on a transformers model with one of those lists, e.g. the script in #3177. What is
observed: generations that differ from the same model run in transformers, with no warning or error.

Measured here on CPU with `google/flan-t5-base` loaded with `dtype=torch.float16` (transformers 5.17.0,
torch 2.14.0+cpu; the CPU accelerator's fp16 gate was bypassed in the script so the cast path runs), on
the two sentences from the issue, greedy, `max_length=32`:

```
upstream/master:
wo dtype after init_inference: torch.float16
HF: ['Verbal punishment is a form of punishment that is used to punish a child for a crime.', 'I am .']
DS: ['a slap on the head', "I am n't doing it right"]
identical: False

this PR:
wo dtype after init_inference: torch.float32
DS: ['Verbal punishment is a form of punishment that is used to punish a child for a crime.', 'I am .']
identical: True
```

The `.half()` line dates from the 2021 inference release (ed3de0c2), before transformers introduced the
lists, so this is drift rather than a decision. The training side gained `keep_in_fp32_pattern` for the
same lists in #8699 (ZeRO-3); the inference engine was left out.

## Fix
Before casting, collect the fp32 tensors whose full names match the model's lists (reusing
`keep_in_fp32_pattern(module, "auto", dtype)` from #8699, which applies the strict list under bf16 and both
lists under fp16, the way transformers does), cast the module, and put those tensors back. A listed tensor
that arrives in a lower precision is upcast, as transformers' loader and #8699 do. The kept tensors are
the ones transformers already runs with under fp16, and the HF forward passes already cast activations to
the weight dtype for them, so the module ends in the state transformers itself produces. Kernel injection
and AutoTP run after this point and are unchanged.

## Testing
New `tests/unit/inference/test_inference_keep_in_fp32.py`: a toy module with both lists, parametrized over
fp16/bf16 (fp16 skips where the accelerator lacks it), plus a real `T5ForConditionalGeneration` built from
a tiny config under fp16.

Negative control (revert only `deepspeed/inference/engine.py` to `upstream/master`, keep the new test), on
`test_init_inference_keeps_listed_tensors_in_fp32[dtype1]` (bf16, the one this CPU can run):

```
FAILED ...test_init_inference_keeps_listed_tensors_in_fp32[dtype1] - AssertionError
1 failed
```
Restored: `1 passed`. The fp16 cases pass with the fix and fail without it when the fp16 gate is bypassed
locally; on CPU CI they skip and will run on the GPU jobs. `test_inference_config.py`: 9 passed, 1
pre-existing failure (`test_cuda_graph_with_kernel_inject_raises` fails identically on unmodified
`upstream/master` because this CPU has no fp16).

Execution hardware: CPU only (no GPU available to me), torch 2.14.0+cpu. `pre-commit run --files` clean
on both changed files.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Avoid duplicating all retained weights during the cast**

When a T5 model has already been loaded in fp16 on an accelerator (with its many `wo` matrices left in fp32), `keep` retains every fp32 storage while `self.module.half()` allocates and installs a half copy of every one; none of those temporary copies is released until `_restore_fp32_tensors` runs after the whole cast. Peak memory is therefore the final mixed-precision model plus an extra fp16 copy of all protected matrices, which can OOM large T5 variants even when the final model fits. Cast nonmatching tensors selectively, and validate peak memory on a representative model.
