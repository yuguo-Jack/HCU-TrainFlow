## Summary

With the optimizer offloaded to the CPU, ZeRO-3's step makes three passes over every CPU sub-group:

1. multiply every fp32 gradient by the clipping factor in place (`grad.mul_`), even when the factor is 1;
2. run `DeepSpeedCPUAdam` (reads gradients, parameters and both moments; writes parameters and both moments);
3. cast the updated fp32 parameters to bf16 into the pinned staging buffers and copy them to the device.

This PR folds 1 and 3 into 2: the CPU Adam kernel multiplies each gradient by the factor as it loads it, and writes
the bf16 copy of each updated piece into a pinned staging buffer, which is copied to the device while the next piece
is updated. The parameters after training are bitwise equal to the three-pass path.

## Measured

GLM-5.2, real weights, PG-19 rows of 65,536 tokens, fp32 Adam states, CPU optimizer offload, each sequence over 2 GPUs.

| Setup | Without this PR | With this PR | Same losses |
|---|---|---|---|
| 1 node x 8 H200, first 8 layers, 20% of the optimizer on the GPU: clip factor fused | 15.95 s per step, optimizer step 5.01-5.29 s | 15.01 s, optimizer step 4.25-4.33 s | yes |
| the same, clip factor and bf16 copy fused (2 runs) | 15.95 s | 14.61-14.67 s (-8.0 to -8.4%) | yes |
| 8 nodes x 8 H200, all 78 layers, 10% on the GPU, one job on the same nodes | 147.16 s | 143.61 s (-2.4%) | yes (to the printed digits until step 8, then one bf16 step, as between repeated runs) |

Profile (one step, rank 1): the separate `aten::mul_` pass took 824 ms of a 6.70 s step on 2 nodes before;
with this PR it is 1.2 ms in an 8-node step, and no separate cast pass remains after the backward.
Memory: no new buffers (the staging buffers belong to the copy-back PR).

This change was also in the DeepSpeed tree of our MiniMax-M3 and GLM-5.2 runs against Megatron-LM (real weights,
65,536-token sequences, 80-95% of the optimizer on the CPU): MiniMax-M3 on 4 nodes 85.24 s per step vs 119.35 s for
Megatron-LM (one job on the same nodes); GLM-5.2 first 38 layers on 4 nodes 62.03 vs 63.73 s (one job on the same nodes);
GLM-5.2 all 78 layers on 8 nodes 130.58 vs 135.56 s (separate jobs on 7 of the same 8 nodes). On one node, master plus this
PR, the copy-back PR and the two model PRs (#8658, #8659) gives the same loss at every step as that tree.

- 0z5a · COMMENTED · 2026-10-18T15:05:08Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8841#pullrequestreview-5563587542)

Thanks for this. Most of it checks out: the clip factor comes from the same folding-aware `scaled_global_grad_norm` (partition group → MP reduce → `_autoep_expert_parallel_group`), overflow returns before the sub-group loop, `IncrementStep` is idempotent across pieces, pieces are aligned to `SIMD_WIDTH*8`, and the bf16 store is RNE with NaN→0x7fc0 like torch. The new kernel tests pass bitwise on AVX-512 for me. Small thing: the first commit is #8840's head, so "Builds on #TODO" should read #8840.

One blocking issue and a few should-fix items below.

**1. [blocking] Params with no gradient this step diverge from the unfused path** — [`stage3.py:3022-3024`](https://github.com/deepspeedai/DeepSpeed/blob/5f663c08e5ad46d0088e379c55a8b900633e6360/deepspeed/runtime/zero/stage3.py#L3022-L3024)

Skipping the in-place `unscale_and_clip_grads` has two side effects:

- In offload mode a sub-group's fp32 grad buffer isn't zeroed between steps, and `_finalize_offload_gradient_accumulation` only refreshes params reduced in this window. On master, `unscale_and_clip_grads` rescales that stale region in place every step; on the fused path it keeps its raw loss-scaled, unclipped value and is only multiplied by the current factor. Repro on the CPU accelerator (1 rank, fp32 model, `offload_optimizer: {device: cpu, pin_memory: false}`, `gradient_clipping: 1e-3`, a layer used only on step 0, 3 steps): every parameter is bitwise equal between the fused and unfused paths except the unused layer, which differs by up to 5.9e-3. Under AutoEP this is any expert that receives no tokens in a step.
- After `step()`, `safe_get_full_grad` now returns unscaled, unclipped grads (0.221 vs 2.97e-4 in the same repro).

Options: take the fused path only when every param of the sub-group was reduced this window (e.g. check against `_offload_boundary_param_ids`), or zero the non-reduced regions in `_finalize_offload_gradient_accumulation`. The second would also fix an existing master issue where those stale grads are applied by the step but left out of the norm. Either way, a regression test with a conditionally-unused layer would lock it in.

**2. [should-fix] Scope is wider than the description** — [`stage3.py:3103`](https://github.com/deepspeedai/DeepSpeed/blob/5f663c08e5ad46d0088e379c55a8b900633e6360/deepspeed/runtime/zero/stage3.py#L3103)

The description says fp16 and `pin_memory: false` keep the current path, but `_grad_scale_for_cpu_adam` has no dtype or pin gate: DeepSpeed's own fp16 (dynamic loss scale) and `pin_memory: false` both take the fused grad-scale path (the repro above is `pin_memory: false`). Only the copy-back half is bf16 + pinned. Could you either gate it, or update the description and add an fp16 case with a forced overflow showing the step and the loss-scale update are skipped and nothing is written?

**3. [should-fix] `step_pieces` bypasses `Optimizer.step`** — [`cpu_adam.py:194`](https://github.com/deepspeedai/DeepSpeed/blob/5f663c08e5ad46d0088e379c55a8b900633e6360/deepspeed/ops/adam/cpu_adam.py#L194)

It doesn't go through torch's wrapped `Optimizer.step`, so step pre/post hooks don't run, the profiler loses the `Optimizer.step#DeepSpeedCPUAdam.step` range, and `_opt_called` is never set. A torch LR scheduler built on the basic optimizer then warns that `lr_scheduler.step()` was called before `optimizer.step()`, and with ratio 1.0 + bf16 + pinned `optimizer.step()` is never called at all. Could this go through a `step(..., pieces=...)` overload, or run the hooks and mark the step manually?

**4. [should-fix] Copy-back test fails on the CPU accelerator** — [`test_zero.py:2098`](https://github.com/deepspeedai/DeepSpeed/blob/5f663c08e5ad46d0088e379c55a8b900633e6360/tests/unit/v1/zero/test_zero.py#L2098)

With 2 CPU ranks the destination is never on a device, so `assert calls, "no sub-group took the fused copy-back path"` fails. It needs a skip when `get_accelerator().device_name() == "cpu"` (same issue as in #8840). `TestZero3CpuAdamGradScale` is fine on CPU.

**5. [question] ARM** — [`cpu_adam_impl.cpp:274`](https://github.com/deepspeedai/DeepSpeed/blob/5f663c08e5ad46d0088e379c55a8b900633e6360/csrc/adam/cpu_adam_impl.cpp#L274)

On SVE builds (Grace) `adam_copy_supported()` is false, so only the grad-scale half runs, via the new `svmul_f32_x`. The description lists ARM as unvalidated. I have a GH200 and can run `test_cpu_adam_grad_scale_matches_scaling_in_place` and `test_cpu_adam_step_pieces_matches_step` there if that helps.

**6. [nit]** `src.is_pinned()` here vs `accelerator.is_pinned(src)` in #8840, and the staging allocation duplicates `_copy_through_pinned_staging`; a shared helper would keep them in sync. Also `_optimizer_step(..., grad_scale=...)` is now always passed by keyword while SuperOffload's override keeps the old signature. That's safe today only because SuperOffload overrides `step()`; passing it only when not `None` would be more robust.

- st-bang97 · comment · 2026-10-18T09:47:41Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8841#issuecomment-6248409601)

Hi @pengdurice,

It's great to see this PR addressing CPU optimizer overhead, as it closely aligns with our work on ReplayOpt and ReFlow (#8719).

Our research focuses on the memory bandwidth bottlenecks of CPU-offloaded optimizers. In ReplayOpt, accepted to IEEE Computer Architecture Letters (CAL), we explored reducing the critical-path overhead of optimizer-state updates. Building on this work, ReFlow further reduces memory traffic through register-resident SIMD fusion and overlaps CPU optimizer execution with GPU computation through decoupled scheduling.

In particular, ReFlow already implements the two main optimizations in this PR: fusing gradient scaling/clipping into CPU SIMD kernels and directly generating FP16/BF16 parameters without a separate conversion pass.

There are also opportunities for further optimization. For configurations using BF16 gradient accumulation, or without gradient accumulation, gradients can be transferred to the CPU in BF16 and promoted to FP32 only within SIMD registers during the optimizer update. This reduces not only PCIe traffic but also gradient-related CPU memory traffic, which is especially beneficial for memory-bandwidth-bound CPU optimizers. The in-register conversion is relatively inexpensive and avoids a separate FP32 conversion pass.

With these optimizations and asynchronous scheduling, ReFlow achieves up to 4.0× higher training throughput than ZeRO-Infinity on a single B200 and 1.86× on four B200 GPUs.

I originally implemented these optimizations in separate ReFlow kernels to minimize regression risks and preserve the stability of the existing DeepSpeed CPU optimizer path. However, since this PR is addressing the same underlying bottlenecks, I think this could be a good opportunity to incorporate ReFlow's non-asynchronous optimizations into the default CPU-offload path, while keeping asynchronous execution optional.

Would you be willing to review my PR (#8719) and share your thoughts on this direction? I'd greatly appreciate your feedback and would be happy to help with the integration and validation.

The ReFlow paper has also been accepted to ASPLOS 2027 and is expected to be publicly available soon. I'd be happy to share a copy directly if it would help with reviewing the design and evaluation.

Thank you for your time and consideration!
