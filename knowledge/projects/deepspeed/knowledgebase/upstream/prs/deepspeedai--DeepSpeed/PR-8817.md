# Add RVV vectorized FP32 kernel to CPU Adam

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8817) · state: open · merged: False

## Original PR description

## Description

On riscv64 hosts with the RISC-V Vector (RVV 1.0) extension, DeepSpeed CPU Adam currently falls back to the scalar `Step_1` tail because neither the op builder's `simd_width()` nor the kernel dispatch recognizes the V extension. This PR adds an RVV FP32 tier to CPU Adam, mirroring the existing SVE backend, so RVV-capable CPUs get a ~4x single-core speedup on the optimizer step.

- `csrc/includes/rvv.h`: an RVV 1.0 FP32 Adam kernel. The hot loop processes one `m4` block per iteration — at VLEN=128 each block covers a full 64-byte cache line per stream — and runs entirely at the loop-invariant vlmax; a single `vsetvl` truncates the trailing block, so any tensor length is covered with no scalar tail. The arithmetic order matches the scalar and SVE kernels, keeping every tier within the existing test tolerance. Scalar hyperparameters ride the vf-form intrinsics, so only epsilon occupies a vector register.
- `cpu_adam.h` / `cpu_adam_impl.cpp`: `Step_RVV` dispatch alongside `Step_AVX` and `Step_SVE`; only the FP32 param/FP32 state pair is vectorized, other dtype pairs keep the scalar path (same policy as SVE).
- `op_builder/builder.py`: detect the V extension from the `/proc/cpuinfo` isa line with a per-character token test (a substring test misreads `rv64imafdcvh` as having V), build with `-D__RVV__ -march=rv64gcv` on riscv64, and normalize py-cpuinfo's `RISCV_64` arch string so the riscv64 branch actually fires. Hosts without V are unaffected (`rv64gc`).
- `docs/_tutorials/zero-offload.md`: document the automatic RVV tier.

- zhangjian29 · comment · 2026-10-14T01:13:47Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8817#issuecomment-6158659021)

Follow-up to the P1 on the bare `v` case: addressed in 43b1f40df.

The probe now reads **AT_HWCAP from `/proc/self/auxv`** and treats the `COMPAT_HWCAP_ISA_V` bit (`1 << ('V' - 'A')`, per `arch/riscv/include/uapi/asm/hwcap.h`) as the decision signal. That is the interface the kernel's own vector documentation prescribes — "To get the availability of V in an ELF program, please read the COMPAT_HWCAP_ISA_V bit of ELF_HWCAP in the auxiliary vector" ([Documentation/arch/riscv/vector.rst](https://www.kernel.org/doc/html/next/riscv/vector.html)) — and it reflects the extension set the kernel's ISA parsing accepted rather than echoing the devicetree string, so an unversioned C906/D1 `rv64imafdcv` no longer enables the vector path by itself.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Reject pre-1.0 V extensions before enabling RVV**

On a RISC-V system whose ISA line advertises a draft vector version such as `rv64imafdcv0p7`, this one-character check still returns true and `cpu_arch()` replaces the advertised ISA with `-march=rv64gcv`, which targets ratified V 1.0. The resulting op can execute 1.0 encodings that the CPU does not support instead of retaining the previous scalar `rv64gc` path, so parse and reject explicit V versions below 1.0 (or use an OS capability probe) before defining `__RVV__`.

- Copilot · comment · 2026-10-13T17:17:37Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8817#discussion_r4261773436)

File: `op_builder/builder.py` · line None

A bare `v` in `/proc/cpuinfo` does not identify ratified RVV 1.0. For example, T-Head C906/Allwinner D1 systems report an unversioned `rv64imafdcv` while implementing incompatible RVV 0.7.1, so this returns `True` and `cpu_arch()` builds every CPU op with `-march=rv64gcv`; loading/running those ops can then execute unsupported 1.0 encodings. Detect the kernel-advertised ratified V capability (for example, RISC-V HWCAP/hwprobe) rather than interpreting an unversioned ISA token as 1.0, while retaining an appropriate fallback for older kernels.
