# Keep single-rank barrier() free of torch's device_id warning

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8779) · state: open · merged: False

## Original PR description

Fixes #8775.

### Problem
Since #8269 (0.19.7), a single-rank job initializes the process group without a bound device so that `new_group()` stays lazy (#8248). torch's `barrier()` then has neither `device_ids` nor `group.bound_device_id`, and warns on every call:

    UserWarning: barrier(): using the device under current context. You can specify `device_id` in `init_process_group` to mute this warning.

This hits any single-GPU job: Lightning as reported, and also DeepSpeed's own `dist.barrier()` calls (a single-GPU ZeRO-3 `deepspeed.initialize` plus one step prints it 3 times). Suites that run with warnings as errors fail on it.

Binding a device in any form brings #8248 back: `new_group()` inherits `default_pg.bound_device_id` and calls `eager_connect_single_device`. Setting `bound_device_id` after init does the same.

### Change
When DeepSpeed creates the process group without a device and the world has a single rank, ignore exactly that torch message. With one rank there is no peer that could pick a different device, which is the hang the warning is about. Multi-rank jobs are unchanged: on CUDA the device is still bound, and on other accelerators the warning stays visible. The condition uses `torch.distributed.get_world_size()` after init, so a wrong `WORLD_SIZE` cannot hide the warning in a multi-rank job.

### Verification
WSL2 Ubuntu, RTX 5060 Ti (sm_120), driver 596.49, torch 2.14.1+cu130, NCCL 2.30.7. Single rank, `-W error::UserWarning`, `barrier()` then 64 `new_group([0])` (8 of them used for an `all_reduce`):

| | `barrier()` | 64 × `new_group([0])` |
|---|---|---|
| 0.19.6 | OK | fails at the 40th: `Cuda failure 600 'device not ready'` in `eager_connect_single_device` (#8248) |
| master | raises the UserWarning | OK |
| this PR | OK | OK |

On this machine #8248 looks like a cap on live NCCL communicators per process. Without a bound device, actually using 40 single-rank groups fails the same way. Binding makes every `new_group()` count toward that cap, so keeping it unbound for a single rank is still right.

### Tests
- `test_barrier_device_warning`: with `torch.distributed` stand-ins, the message is hidden after a single-rank init and stays visible for two ranks.
- `TestSingleRankDeviceId::test_barrier_does_not_warn`: real single-rank NCCL init and `barrier()` with that warning set to error. It fails on master and passes with this change.
- `pytest tests/unit/comm/test_dist.py` on 1× RTX 5060 Ti: 19 passed, 26 skipped (multi-GPU / MPS).
- `pre-commit run --files` on both files passes.

### Trade-offs
- Python warning filters are process-wide, so the filter also covers `barrier()` calls made outside DeepSpeed in the same process. That is the point for the Lightning case, but it means a user who wants to see this message after a single-rank DeepSpeed init has to add their own filter after `init_distributed`.
- torch still logs `ProcessGroupNCCL.cpp: Guessing device ID based on global rank...` from C++ before the first collective. It is not a Python warning, so it does not fail warnings-as-errors runs, and this change does not touch it.
- I only have one GPU, so the multi-rank CUDA path was checked by reading the code and with a 2-process gloo run (no filter added on either rank), not on multiple GPUs.
