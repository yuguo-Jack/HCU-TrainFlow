# Reuse continuous rollout graphs and release captured resources on shutdown

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/9009) · state: open · merged: False

## Original PR description

## Summary

Keep the continuous-decode graph alive across RL rollout rounds, and add an explicit way to release it.

| Change | Before | After |
| --- | --- | --- |
| Graph signature | Includes `prompt_len` and every parameter's `(data_ptr, _version)`. | Keeps the decode batch size, cache length, device and dtype, plus each parameter's address, device, dtype, shape and strides. Captured kernels read parameters through the address and layout fixed at capture, so in-place value updates are replayed correctly. Replacing a parameter, or changing its layout at the same address (for example `transpose_()`), triggers a recapture. |
| Width changes | Every new prompt width recaptures, even when `continuous_cache_capacity` pins the cache length. | With a pinned capacity, one graph serves all widths that fit. The capacity check still runs on every call. |
| Rebuild order | The new static cache and graph pool are allocated while the old state is still alive. | Drop the old state before allocating its replacement, avoiding overlapping ownership of both states. |
| `HybridEngineRollout.shutdown()` | No API; the state lives until the rollout object is collected. | Synchronizes and releases the graph and static cache. The rollout stays usable and recaptures on the next graph call. |

`shutdown()` implements the existing `RolloutEngine.shutdown()` lifecycle hook. It matters for TP>1: in the NCCL reproducer below, a persistent graph holding captured collectives makes `destroy_process_group()` hang in `ProcessGroupNCCL.shutdown()`. Call `shutdown()` on each rank before destroying the process group. The docs describe reuse and release.

## Why dropping `_version` is safe

- With bf16, DeepSpeed's optimizer writes updated weights through flat buffers that the parameters view via `.data`, which does not bump `param._version`. On master, single-width bf16 rollouts already reused the graph after `engine.step()`, and the replayed outputs changed with the weights. The version check gave no protection there.
- On paths where a plain torch optimizer updates parameters in place (for example fp32 ZeRO-0), `_version` changes on every step, so master recaptured on every rollout round.
- The cases where storage really moves (AutoTP gather/partition or a `.data =` swap) change `data_ptr`, which stays in the signature.
- A same-address layout change also invalidates the captured kernels. Shape and strides are in the signature, so this recaptures too. This also covers `param.data = param.data.t()`, which keeps both `data_ptr` and `_version` and was therefore missed by the old signature.

## Related work / scope

- Depends on #9008 for TP>1 continuous graph. Without it, TP>1 continuous graph fails at the KV copy before this code matters. The two PRs touch neighbouring lines in `_get_continuous_graph_state`; whichever merges second needs a trivial rebase. TP2 results below use #9008 + this PR.
- Builds on #8732 (persistent continuous graph), reusing its existing fixed-capacity setting rather than adding another configuration option.
- #8853 only measures graph capture and keeps the version check. Its `test_continuous_graph_first_call_benchmark_on_cuda` asserts `capture.call_count == 2` because an in-place SGD step currently forces a recapture. With this PR that step reuses the graph, so whichever of the two merges second needs that expectation changed to 1 (and the benchmark's post-update number no longer includes a recapture). #8786 buckets prefill and does not change graph reuse or release.
- Not covered: ZeRO-3, offload, HybridEngine kernel injection, LoRA fuse/unfuse inside rollout.

**RL loop on L20.** Qwen3-0.6B, TP1, 8 prompts, 4 slots, 32 new tokens, greedy, 6 rounds. Each round does a graph rollout, then a real `engine.backward()` + `engine.step()` with AdamW (lr 1e-4). Times are wall-clock per rollout, including prefill.

After the layout fix, the patched fp32 TP1, bf16 TP1 and fp32 TP2×DP2 runs were repeated: still 1 capture, the same per-round token-match rates and the same `shutdown()` release. Optimizer steps do not change parameter shape or strides.

These are exploratory short runs, not a controlled end-to-end speedup claim. In particular the two fp32 rows use different prompt schedules and cache capacities. No long-run convergence or training-throughput claim is made.

**Correctness against plain eager generation.**

- **fp32:** every round is token-identical in the TP1 master and patched runs, and in the patched TP2×DP2 run (with #9008).
- **bf16, TP1:** rounds 4–6 differ from plain eager after training steps. The per-round token-match rates are the same on master and this PR (0.9961 / 0.8984 / 0.9336). This is consistent with precision-sensitive generation, but does not prove the root cause or bitwise equivalence of the two graph runs.
- **bf16, TP2×DP2:** the patched run also differs from eager (minimum match 0.5742 / 0.9805 / 0.9883 / 0.8047). There is no matched unpatched TP2×DP2 run in this experiment, so this cell is **not validated for token-exact correctness**.

**Tiny Llama fp32 runs:**

- ZeRO-2, widths 16/24: 1 capture, token-identical on every round.
