# Fix ZeRO-3 external parameter discovery for resident weights

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8875) · state: open · merged: False

## Original PR description

Fixes #8874

## Problem

ZeRO-3 currently discovers a parameter accessed outside its owning module only when it is `NOT_AVAILABLE`. A resident weight can therefore be missing from the recorded external dependencies. If it is subsequently partitioned, the same access registers a new dependency after the trace is complete. Checkpoint recomputation then fails because the parameter fetch queue no longer matches the module's dependencies.

I encountered this during full LoRA checkpoint resume using Hugging Face [PEFT](https://github.com/huggingface/peft) and [TRL](https://github.com/huggingface/trl), with gradient accumulation and reentrant activation checkpointing. It also reproduces with a small PyTorch adapter and DeepSpeed alone, without either library, on master `68faa67c`.

## Change

Discover eager external parameter accesses independently of residency, while leaving the existing condition for actually gathering a parameter unchanged. Accesses from the parameter's own module and the separate DeepCompile eager-fallback path retain their behavior.

For ZenFlow, use the existing active-consumer set in the forward and backward hooks so that nested consumers share the compute layout and only the last consumer restores the storage layout. A parameter discovered after the consumer's pre-hook must not receive an unmatched post-hook transpose.

This does not lower the persistence threshold, remove trace checks, or invalidate the trace on every step. Production changes are confined to `parameter_offload.py`; regression tests use three existing test files. The getter is specific to ZeRO-3; ZeRO-1/2 do not use this offload path.

## Validation

Hardware: main1 H100 host, 1 GPU for the ZenFlow tests, 2 GPUs for the resume regression, and 4 for the earlier real-model check. The cloud exposes the device name as `CUDA GPU`, compute capability 9.0, with 81,559 MiB per device. Driver 535.161.08, PyTorch 2.13.0+cu129, CUDA runtime 12.9, nvcc 12.8. DeepSpeed was built from `68faa67c` without prebuilt ops; existing tests may JIT the operators they use.

- The new CPU getter regression fails for external access on unmodified master; both cases pass with the fix.
- The real two-rank checkpoint regression fails on unmodified master with the same adapter/base fetch-queue mismatch. All eight patched cases pass, with no errors or skips on either rank. They cover parameter offload none/CPU, persistent/non-persistent adapters, and reentrant/non-reentrant checkpointing, all with GA 4.
- The regression saves a checkpoint, creates a new engine, and restores optimizer and scheduler state. It checks each microstep's loss and the weights after both optimizer updates against a non-checkpointed plain PyTorch reference.
- All eight resume cases were rerun after the ZenFlow follow-up and still pass on both ranks. The CPU getter and eager-fallback/guard checks also pass: eight cases, without errors or skips.
- Six real-engine ZenFlow cases pass against plain PyTorch: persistent/non-persistent matrices, with no external access, a metadata-only access, or an external access followed by the owning Linear. They check loss, transposed storage values, and weights after three optimizer updates using FP32, synchronous CPU optimizer offload, and the warmup phase. The nested-owner case fails in backward with the previous ZenFlow hooks; a metadata-only control also passes there. The existing BF16 ZeRO-3 ZenFlow selective-update training test passes as well.
- The standalone issue reproducer fails on the original and completes full resume on the patched source.
- The existing attribute-delegating wrapper and dangling external-parameter training tests pass. Six existing CPU eager-fallback/guard checks also pass.
- Before the ZenFlow follow-up, the original 27B checkpoint resumed from global step 2 to 6 and completed two evaluations with stock PEFT 0.21.2 and `stage3_param_persistence_threshold=1000000`. This used BF16 base weights, FP32 LoRA, GA 4, reentrant checkpointing, and TRL fused NLL, with Liger and ZenFlow disabled. No PEFT source or training setting was changed to make it pass. The 27B run was not repeated for the ZenFlow-only follow-up.
- All applicable project pre-commit hooks pass for the four changed files.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Keep ZenFlow transposes symmetric during registration**

With ZeRO-3 ZenFlow enabled, a resident 2-D weight first touched externally inside a consumer's `forward` (such as the added LoRA dtype lookup) is inserted into that consumer's external set here after `pre_sub_module_forward_function()` already enumerated the set. `post_sub_module_forward_function()` then sees the new weight and applies its ZenFlow `.t()` (`parameter_offload.py:562-565`) without the matching pre-transpose, leaving the parameter in the compute layout when partitioning/optimizer code expects ZenFlow's transposed storage layout; this can silently corrupt the next update or forward. Snapshot the pre-hook set or otherwise make the registration's transpose accounting symmetric, and cover this configuration.

AGENTS.md reference: [AGENTS.md:L19-L19](https://github.com/deepspeedai/DeepSpeed/blob/0380e42e27fcd2cd41a1268bd76e9e5e99a1e911/AGENTS.md#L19-L19)
