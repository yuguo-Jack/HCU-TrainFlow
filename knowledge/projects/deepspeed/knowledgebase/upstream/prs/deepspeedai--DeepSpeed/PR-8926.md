# Add a v1 multi-rank CPU suite (manual dispatch first)

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8926) · state: closed · merged: True

## Original PR description

## What

Adds `cpu-torch-latest-v1-multirank`, a CPU suite for the **`tests/unit/v1`** multi-rank tests — the one gap left between the existing CPU workflows:

| Workflow | Covers |
|---|---|
| `cpu-torch-latest` | all of `unit/` at `world_size == 1` (the device gate skips higher ranks) |
| `cpu-torch-multi-latest` (nightly) | multi-rank for the non-v1 half + the `sequential` marker |
| **`cpu-torch-latest-v1-multirank` (this PR)** | **v1 multi-rank** (`world_size` 2-4) |

Mechanically it is the same recipe the nightly suite uses: `LOCAL_SIZE=4` lets the per-device gate admit the multi-rank tests, and `DS_MULTIRANK_ONLY=1` deselects everything else, so the job spends its time on v1 multi-rank tests only.

## Selection

Test selection reuses the existing Modal diff-based picker (`ci/tests_fetcher.py`): the new `WORKFLOWS` entry scopes the suite to `tests/unit/v1`, so a PR only runs the v1 files it could affect. The `collect-tests` job writes `ci/.test_selection/test_list.txt` and the test job consumes it; `mode=none` skips the run entirely. No test lists are maintained by hand.

## Rollout: manual dispatch first

The trigger is `workflow_dispatch` only, deliberately. This suite has never run in CI, and putting an unvalidated ~1 h suite in front of every pull request (or into branch protection) before it has a green run would block PRs. Once it is green across a few real PRs, `pull_request:` goes back into the `on:` block and the check can be registered.

## Harness changes this suite needs (included here)

The v1 multi-rank tests rely on two fixes that used to live on the work-in-progress #8381 branch; they are part of this PR so the first run can be green:

- `tests/unit/v1/zero/test_zero_autocast.py`: the DDP `device_ids` capability probe — without it, all 24 DDP autocast variants fail on CPU with `ValueError: DistributedDataParallel device_ids and output_device arguments ...`. The fp16 parity variants are **skipped** when the accelerator reports no fp16 support (`is_fp16_supported()` false) rather than widening the tolerance, so no assertion is relaxed.
- `tests/unit/common.py`: shm-segment key isolation/cleanup, JIT warm-up with stale-baton cleanup, per-rank faulthandler, and master-port uniquification — without them, concurrent pools share shm segments and can corrupt data or wedge.

Verified on CPU, 2 ranks: bf16 ZeRO-3 passes, fp16 variants skip when fp16 is unavailable, and no `/dev/shm` segments are left behind.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Persist shm keys until cached pools are torn down**

In the checked `cpu-torch-latest.yml` and new v1 workflow, `pytest --forked` can run classes with `reuse_dist_env=True` (for example `TestMuonPartialModelTraining`); `_close_pool(..., force=False)` skips this block, and the forked test process exits without calling `_remove_shm_segments`, while a forced close uses a fresh instance with no `_master_port`. Because `get_master_port` now gives each forked item a different shm key, every such item leaves a new ~66 MiB file per rank instead of reusing the prior name, so long CPU suites can exhaust `/dev/shm`; persist the port with the cached pool and remove it when that pool is actually terminated, or disable reuse under `--forked`.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Cancel rank watchdogs after successful runs**

In non-forked xdist runs such as the checked `amd-mi200.yml`, a `reuse_dist_env=True` worker returns to `_pool_cache` after `_dist_run`, but this process-global timer remains armed. If that pool is idle for `exec_timeout` (600 seconds by default) while other tests run, `exit=True` kills a healthy rank; `multiprocessing.Pool` can replace it with an uninitialized process, and the next cache hit supplies `master_port=None`, causing the reused distributed test to fail or hang. Cancel the watchdog in a `finally` block before a successful worker is returned to the pool.
