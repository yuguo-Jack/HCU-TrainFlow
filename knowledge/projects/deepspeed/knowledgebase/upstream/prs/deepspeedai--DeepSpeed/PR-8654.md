# Release each BF16 gradient once immediate_grad_update has accumulated it

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8654) · state: closed · merged: True

## Original PR description

## Summary

With `bf16.immediate_grad_update`, `BF16_Optimizer` accumulates each completed BF16 parameter gradient in the configured accumulation buffer (FP32 in the measured configuration). Previously it retained the BF16 `param.grad` beside that buffer until the optimizer step. The hook now releases the consumed gradient with `param.grad = None`. With the option disabled, accumulation still happens in the backward epilogue; its default remains unchanged.

For folded AutoEP+AutoTP (TP>1), the BF16 hook also applies folding correction before accumulation. A correction marker left on the parameter after `param.grad` becomes `None` cannot be cleared by the engine's boundary reducer, which skips missing gradients; a later backward could therefore miss correction. The hook now clears that marker when it consumes and releases the corresponding BF16 gradient.

This branch includes current upstream `master`, which removed graph harvesting in #8579. The release hook no longer accesses that removed attribute. It also fixes the BF16 gradient-reconstruction issue exposed by releasing `param.grad`: each rank contributes only its optimizer-owned fragment, even though BF16 keeps a full accumulation buffer on every rank. BF16's mapping indexes its full parameter list rather than ZeRO's local fragment list.

## Why

In a Qwen3-30B-A3B AutoEP training workload (S8192, EP16, 48 layers, 16 NVIDIA H100 GPUs, ZeRO Stage 1, FP32 gradient accumulation), an allocator trace locates peak allocation at the end of backward, when BF16 gradients occupy 6.7 GB per rank beside the accumulation buffers.

## Results (16 NVIDIA H100 80GB HBM3)

Same allocation, four mirrored repeats per arm:

| | epilogue accumulation | immediate accumulation + BF16 grad release |
| --- | --- | --- |
| peak allocated | 54.439 GB | 50.434 GB |
| peak reserved | 57.481 GB | 56.762 GB |
| median step | 2654.2 ms | 2615.6 ms (-1.45%; 95% CI crosses zero) |

This A/B comparison changes the **accumulation mode together with BF16 gradient release**. It does not isolate the speedup or memory effect of the single `param.grad = None` assignment. Step-0 losses match; the maximum cross-arm loss difference across 24 steps is 0.0091, versus 0.0072-0.0085 within an arm. Peak allocation falls by about 4.0 GB, less than the 6.7 GB of freed BF16 gradients because the peak moves to another point in backward.

## Numerical contract

After backward, `param.grad` **may be `None`** with immediate accumulation. In that case `deepspeed.utils.safe_get_full_grad(param)` reconstructs the accumulation buffer from owned fragments **before `engine.step()`** (FP32 when FP32 accumulation is configured). All participating DP ranks must call this collective getter in the same order. Reduction uses the accumulation buffers via `get_grads_for_reduction`; norm, clipping and the optimizer step use them via `get_grads_for_norm` and the FP32 partitions.

## Testing Done

- Current-master targeted run on an 8-GPU NVIDIA H100 80GB HBM3 node (two GPU ranks used): **18 passed, 0 skipped**, with torch 2.10/CUDA 13.0. This includes two owned-fragment getter unit cases, four split/unsplit BF16 Stage-1 and ZeRO Stage-2 training cases (GAS=1/2, two optimizer steps, independent gradient/norm/clipping/SGD references), the release-vs-epilogue comparison, five folding/checkpoint cases, and six multiple-model/shared-loss cases.
- The focused TP2 lifecycle test uses a controlled doubled expert gradient and an independent non-folded reference. GAS=1 and GAS=2 each run two optimizer steps; GAS=2 also exercises reentrant activation checkpointing. The obsolete graph-harvesting case was removed together with upstream's feature.
- The earlier marker-cleanup negative control is retained as evidence: removing only the cleanup makes GAS=1 fail at the **second step's first micro-batch** and GAS=2 at the **first step's second micro-batch**. That evidence predates the upstream synchronization; it is not a new E2E run.
- With only the owned-fragment slicing removed, the full-buffer getter unit case and both BF16 Stage-1 training cases fail as expected; the fragment-local unit case and both ZeRO Stage-2 cases still pass. This isolates the duplicate-contribution defect without changing the release hook or optimizer math.
- All PR-changed files pass changed-files pre-commit checks.
- Published-head checks: DCO and test collection passed. The full DeepSpeedAI GPU CI job was skipped; the targeted H100 execution above is the device-validation evidence.

## Dependencies and scope

The non-immediate folded path's separate GAS>1 marker behavior is not changed; the two-micro-batch regression compares against a non-folded reference instead. Full folded-MoE BF16 Stage-1 integration has a separate pre-existing empty non-expert norm issue on non-zero TP ranks; the focused TP2 test isolates the gradient-lifecycle contract and does not claim full folded-MoE E2E acceptance. The `FP16_Optimizer` MoE grad-norm fix (#8635) has merged upstream and is inherited from `master`, not included as a separate change in this PR. No default-option change or full E2E rerun is part of this follow-up.

Hi @yh0903,
Thank you for the important fix! I think the overall direction seems good, but we need to fix these before merging.

**Access to graph_harvesting**: #8579 removed BF16_Optimizer.graph_harvesting, so the new if not self.graph_harvesting: check raises AttributeError after merging with current master.

**Correctness of safe_get_full_grad**: It is very nice that `safe_get_full_grad` now returns the correct dtype as defined in its contract. However, this exposes a *pre-existing* bug in BF16 gradient reconstruction.
For example, consider a four-element parameter whose FP32 master weights are split between two ranks: rank 0 owns the first two elements, and rank 1 owns the last two. The BF16 parameter and its full gradient accumulation buffer are still present on both ranks. After DP averaging, both gradient buffers contain [5.5, 11, 16.5, 22].
To reconstruct the gradient, each rank should contribute only its owned elements. Instead, get_full_hp_grad() contributes the entire buffer from each rank and sums them, returning [11, 22, 33, 44]—twice the correct gradient. This duplicate contribution does not occur when the parameter fits entirely within one rank’s optimizer partition, because only that rank contributes.

I also wonder if `immediate_grad_update` could be true as default. It was introduced with default `false`, #7018 changed it `true`, and #6979 changed it back to `false`. Given the goal of #6979, I think the change might be unintented.

- Copilot · comment · 2026-09-29T17:15:48Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8654#discussion_r4136297882)

File: `deepspeed/runtime/bf16_optimizer.py` · line None

When graph harvesting is enabled with gradient accumulation, this leaves the correction marker set after the first non-boundary micro-batch. `backward_prologue()` zeroes `param.grad` but does not reset the marker, while the engine clears it only at the accumulation boundary; consequently the next micro-batch reaches `_update_hp_grad()` with a fresh gradient marked as already corrected and skips folding correction. The graph-harvesting test exercises only one hook invocation, so it does not cover this case. The marker must be reset for each fresh gradient while still remaining visible to the boundary reducer, with a graph-harvesting GAS>1 regression test.
