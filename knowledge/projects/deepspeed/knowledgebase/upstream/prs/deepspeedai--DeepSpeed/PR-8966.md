## Original PR description

## Calibrate affine transfer links per path

Stacked on #8809 only for its docs page (`affine-transfer.rst`); the module itself needs nothing beyond master. Until #8809 merges, please review only the last commit ("Calibrate affine transfer links per path, including fan-out and fan-in").

### Why
A replica policy or cost model choosing between plans (#8252, #8935/#8936) needs link costs measured on the machine it runs on. Executor measurements show that round count and receiver sharing dominate sync time, so per-pair numbers are not enough on their own; this PR also measures 1→N and N→1.

### What
`deepspeed/checkpoint/affine_transfer_calibration.py`:
- `calibrate_links(sizes, repeats, warmup, path_of, fan_width)`: collective over the default group. Returns the same raw samples on every process, with no aggregation, for:
  - `local` copy;
  - `peer` (each ordered pair alone);
  - `concurrent` (all processes, every shift);
  - `fan_out` (1→N);
  - `fan_in` (N→1, receiver contention).
  
  Sizes run from 4 KiB to 256 MiB by default.
- Each message is labelled by `path_of(from_process, to_process)`. `default_path_of` gives `local`/`peer`; `node_path_of(n)` gives `intra_node`/`inter_node`; any callable works.
- `fit_links(calibration)`: per-path `alpha + bytes / bandwidth`, fitted to the per-size medians.

It measures only. It does not plan, select replicas, or change the planner or executor.

### Example (one node, 8 devices, default sizes)
| pattern | B70 xccl: alpha (µs) / GB/s | L20 nccl (PCIe): alpha (µs) / GB/s |
|---|---|---|
| local | 73 / 359 | 16 / 1534* |
| peer | 301 / 28.2 | 72 / 25.3 |
| concurrent | 389 / 7.7 | 85 / 23.4 |
| fan_out (7 peers) | 531 / 3.4 | 141 / 3.6 |
| fan_in (7 peers) | 670 / 2.6 | 56 / 3.8 |
| run time | 88 s | 34 s |

\* poor linear fit (max relative error 0.77); small copies are cache-resident.

### Tests
`tests/unit/checkpoint/test_affine_transfer_calibration.py`:
- fit on synthetic data;
- schema and argument checks;
- 4-rank runs checking completeness, sample counts, and fan path direction with an asymmetric `path_of`.

6 passed on 4× B70 (xccl) and on 4× L20 (nccl, together with the #8809 executor tests: 61 passed). Mutation checks: flipping the fan_in label direction fails the test.

### Follow-ups
- Accept a process group.
- Sampled pairs for large worlds.
- Multi-node runs.
- Joining the samples to a plan's messages (analysis PR, stacked on this one and #8809).

- 0z5a · COMMENTED · 2026-11-01T17:04:52Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8966#pullrequestreview-5729264157)

Read the last commit (`3cfa4153`), as asked. The measurement design is careful: the barrier and synchronize brackets keep collectives out of timed regions, the pair sweep isolates each link, and the fans separate sender and receiver sharing. On CPU (gloo, 4 ranks), the calibration tests pass together with #8967's and the executor's (62).

A few thoughts, mostly about feeding a cost model directly:

- **Per-process send and receive capacity.** A model of the form t = max over processes of max(sent / send_capacity, received / receive_capacity) needs each process's aggregate send and receive capacity. `fit_links` gives per-path link costs; the fan fits use the peers' times, and the roots' times, which carry the aggregate, stay only in the raw result. Computing `bytes * len(peers) / root_seconds` from the raw fan entries is a few lines. On CPU it gives a per-root figure for each direction. Having `fit_links` fit those per process (or per root) as `send` and `receive` would let #8967's `ProcessReport.sent_bytes` / `received_bytes` be priced directly.
- **Fan peers.** The peers are `root + 1 … root + fan_width`, so with `fan_width` below the processes per node every fan stays within a node. If receive capacity differs across nodes, a way to choose the peers (a `fan_peers(root)` hook, or a stride) would let the fans cover it.
- **Defaults at scale.** With the default `fan_width = world - 1`, each process can allocate `(1 + world) * max(sizes)`, about 16 GiB at 64 ranks and 256 MiB, and the pair sweep is O(world²) barriers per size. The docstring says so, but a default capped at the processes per node, or a check against free memory, might save someone a surprise.
- **Process group.** Calibration always uses the default group, while the executor runs on whatever group `TransferEndpoints` names. An optional `group` argument would let it measure the group the executor will actually use, e.g. an external trainer–rollout group, with the same rank numbering the analysis report uses.

- jinyouzhi · comment · 2026-11-02T06:34:42Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8966#issuecomment-6570758482)

@Achyuthan-S @0z5a Thanks both. I agree with the direction: a list of fan widths and a fitted root time (per-process `send` / `receive`). Before we key the fits by width alone, here is fan-in data at four widths on 8x B70 (PCIe, xccl, 256 MiB, median of 10). It shows that on a PCIe tree, *which* senders feed a receiver matters more than *how many*.

**Topology.** Four PCIe switches, each with two cards behind one Gen5 x16 root port, and two switches per socket: {0,1} {2,3} on socket 0 and {4,5} {6,7} on socket 1 (assuming ranks follow PCI address order). GH200 over Slingshot is a Clos, so every sender set looks alike there, which fits your flat incast.

**Pair bandwidth, GB/s (row = sender, column = receiver):**

```
from\to   0     1     2     3  |  4     5     6     7
0         -    8.3   7.9   8.3 | 27.3  27.5  27.6  27.8
1        6.0    -    5.5   3.6 | 27.4  27.5  27.4  27.5
2       53.9  53.7    -   53.6 | 14.5  14.6  14.6  14.6
3       53.6  53.5  53.8    -  | 14.6  14.6  14.6  14.6
4       27.4  27.3  27.4  27.3 |  -   14.4  14.3  14.4
5       27.3  27.3  27.4  27.4 | 25.2   -   25.3  25.3
6       27.6  27.7  27.0  27.3 |  8.8   8.7   -    8.6
7       27.5  27.8  27.3  27.4 | 42.8  42.9  43.0   -
```

These are stable across runs. Cross-socket traffic sits near 27 GB/s. Within a socket, bandwidth depends on the sender and the direction (2→0 is 54, 0→2 is 7.9, on the same switches), which the tree alone does not predict.

**Fan-in root aggregate (`k * bytes / root_seconds`), GB/s, by width:**

| width | min ~ max over roots | spread |
|---|---|---|
| 1 | 7.0 ~ 53.9 | 7.7x |
| 2 | 12.6 ~ 55.2 | 4.4x |
| 4 | 18.7 ~ 37.3 | 2.0x |
| 7 | 16.4 ~ 23.6 | 1.4x |

Three cases explain most of it:
- **`0 <- [1, 2]` = 12.6:** the root waits for the slowest sender (1→0 at 6.0), so the aggregate is about 2 × 6.
- **`1 <- [2, 3]` = 55.2:** two 54 GB/s senders reach only about 55 together, so a receive-side limit binds.
- **`3 <- [4, 5, 6, 7]` = 27.9:** four 27 GB/s senders together still get about 28, because the shared bottleneck is the cross-socket link, not the receiver.

So the finish time looks like `max(slowest sender's bytes / pair bandwidth, bytes through a shared link / that link's capacity)`. Both terms depend on the sender set. A single fit per width would average 12.6 and 55.2 at width 2, and a single receive capacity per process would miss the shared cross-socket link.

**Proposal for this PR:**
1. **Width list and root fit:** keep both as you describe. They are right for Clos and other uniform fabrics.
2. **Per-pair fit:** add an optional per-pair entry in `fit_links`, keyed by `(from, to)` and fitted from the existing pair sweep, so no new measurement. It captures sender and direction asymmetry, which a path-class fit hides (the 28 GB/s peer fit here is the median of 3.6–54).
3. **Choosing fan peers:** add a `fan_peers(root, width)` hook (0z5a's suggestion). The fan fits are keyed by the peer set, or by the peers' path classes, not by width alone. That way a fan can target "same switch", "same socket" or "cross socket" senders and measure the shared-link capacity directly. The raw entries already record `peers`.
4. **Docs:** state that width-keyed fits assume a uniform fabric, and include this table as the counterexample.

On 0z5a's other points:
- I'll add the optional `group` argument, with ranks numbered as in the analysis report.
- I'll cap the default `fan_width` at the processes per node and document the memory needed.

@Achyuthan-S Please push your width-list and root-fit commit. I'll add the per-pair fit and the `fan_peers` hook on top so they don't conflict. Raw JSON for all four widths is available if you want to check the fits.

Your B70 table is a great counterexample. It fits the same form once every shared resource is a term, not only the endpoints: a fan finishes when the busiest resource it crosses does, i.e. the max over each sender's link, the receiver, and any shared link such as your cross-socket hop, of the bytes through it over its capacity. Your three cases are one of each:
- `0 <- [1, 2]` is bound by the 1→0 link;
- `1 <- [2, 3]` by the receiver;
- `3 <- [4..7]` by the cross-socket link.

So your per-pair fit and `fan_peers` are what calibrate those resources. I kept the width as the only key here so your peer-set keys can replace it without a conflict.
