# Add a nightly multi-rank CPU suite

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8806) · state: open · merged: False

## Original PR description

## What

Adds the `world_size` axis to CI, which the current suite does not cover:

| File | Purpose |
|---|---|
| `.github/workflows/cpu-torch-multi-latest.yml` | Nightly + manual dispatch: runs the multi-rank CPU tests on a 4-vCPU runner |
| `.github/workflows/cpu-multi-triage.yml` | Routes its outcome through the existing `ci/nightly_classify.sh` / `ci/nightly_report.sh` protocol |
| `tests/conftest.py` | The `DS_MULTIRANK_ONLY` collection hook the workflow selects with (required) |
| `.github/workflows/TEST_SELECTION.md` | Registration of the new nightly |

## Why

`cpu-torch-latest` advertises a single device, so the per-device gate in
`tests/unit/common.py` skips **every `world_size > 1` test** on that runner. The
multi-rank path is therefore only exercised on GPU machines, and issues that show up
there only in a multi-rank configuration go unnoticed.

A recent example: PR #8638 changed the overflow semantics so that non-finite
group norms force an optimizer step to be skipped, bypassing
`bf16.check_grad_overflow: False`. `TestZeROBFloat16::test_ignore_grad_overflow` is
`world_size = 2`, so it is collected and *skipped* by the CPU CI and by any run with
one device; it fails as soon as two ranks execute. Reported as issue #8805.

## Why a nightly rather than a pre-merge check

The selection is cheap to state and expensive to run (measured in #8381, 4-vCPU
runner):

| Run | Wall time |
|---|---|
| This suite: non-v1 multi-rank half | 68-89 min |
| This suite: `sequential`-marked phase | 13-16 min |
| Longest current pre-merge job (`cpu-torch-latest`) | 39-43 min |
| Longest merge-queue job (`modal-torch-latest`) | 64-71 min |

Putting it in the pre-merge path would roughly triple the critical path of every PR,
and a single wedged rank would block the merge queue (the suite's known hang — the
shm op segfaulting on hosts without AVX512 — is fixed by #8701, but the suite is the
most expensive one to re-run).

## What it runs

- `LOCAL_SIZE=4` so the gate admits `world_size <= 4`; `DS_MULTIRANK_ONLY=1` deselects
  the single-rank tests that `cpu-torch-latest` already guards.
- Non-v1 half, `timeout 120m`, plus a `sequential`-marked phase, `timeout 25m` (the
  parallel phase deselects those by default, so they would otherwise never run here).
- Same preset/install/HF-predownload steps as `cpu-torch-latest`, so both runs agree on
  the environment.
- On failure the last step prints `DS_CI_FAILURE_CLASS=timeout|test` for triage; a run
  that dies before that step is reported as unclassified rather than guessed.

Triage is a separate workflow with its own issue titles and its own
`nightly-cpu-multi-last-green` tag, so `nightly-last-green` keeps meaning "the last
revision the full GPU suite verified" and the modal issue dedupe is untouched.

## Validation

- Workflow YAML parses; `pre-commit` clean.
- Timings above come from the real runs of this configuration in #8381.
- Not yet run as `cpu-torch-multi-latest`: GitHub only exposes `workflow_dispatch` for
  workflows present on the default branch, so the first manual dispatch has to happen
  after this merges. Happy to run it then and follow up with the numbers.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Emit only the runtime failure sentinel**

When a test or setup failure reaches this `always()` step, GitHub Actions places the entire multiline `run:` script in the job log before its runtime output, so the log already contains this literal timeout sentinel (and the later test sentinel). `ci/nightly_classify.sh` greps that log and takes `head -1`, therefore it routes every such failure as `timeout` even when the executed branch emitted `test` or emitted no sentinel; the CPU nightly's regression and unknown reports never run correctly. Move emission into a helper whose invocation does not contain the alternate sentinel literals, or make the classifier parse a uniquely anchored runtime-only record.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Fix extraction of pytest failure paths**

When any normal `test_*.py` fails, this matcher finds nothing: GNU grep 3.11 `--help` says `-E` selects “extended regular expressions” and exits 1 when no line is selected, and in that syntax `\t` inside this bracket expression excludes the literal letter `t`, so matching stops before the filename's `.py`. The report job consequently aborts without calling `nightly_report.sh`; even a hypothetical match is converted by the next line to `tests/FAILED unit/...` instead of `tests/unit/...`. Use `[[:space:]]` and replace the leading `FAILED ` with `tests/`.
