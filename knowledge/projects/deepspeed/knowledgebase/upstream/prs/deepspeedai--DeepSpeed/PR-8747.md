# AutoEP: do not slice DeepEP buffers that already hold exactly the arrived rows

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8747) · state: closed · merged: True

## Original PR description

## Summary

Avoid redundant prefix slices of DeepEP's received-row and routing-weight buffers when their lengths already equal `handle.num_expanded_tokens`.

A fresh dispatch synchronizes for exact counts and normally returns exact-size buffers. `received[:arrived]` then changes no values, but records a `SliceBackward` in checkpoint recomputation. Its backward zero-fills a buffer-sized gradient and copies the real gradient into it.

With 16,384 tokens per rank, top-8 routing and hidden size 2,048, a BF16 buffer holding 131,072 expanded rows is 512 MiB. A redundant slice of that buffer adds a 512 MiB fill and copy per layer/micro-batch. A motivating profile measured about 128 ms of BF16 fills and 304 ms of device-to-device copies per step; not every copy is attributed to this slice.

## Change and scope

- Check rows and weights independently. Exact-size buffers bypass the slice; overallocated buffers retain the original prefix slicing and zero padding gradients. Missing routing weights remain supported.
- Keep `handle.num_expanded_tokens` as the host-side row count; add no device-to-host synchronization.
- Preserve `score_apply="pre"` / `"post"`, routing-weight gradients, and the rows passed to experts and combine.
- This is a local autograd-graph optimization on the DeepEP route. It changes neither communication volume nor transport settings and introduces no overlap, new kernel or configuration flag. The collective and EP=1 paths are unchanged.

## Correctness and tests

The CPU regression is consolidated in `tests/unit/module_inject/test_auto_ep_comm.py`:

- 24 BF16 subcases: zero/nonzero arrivals, independent exact/padded row and weight capacities, missing weights, and pre/post weighting.
- Outputs and full-buffer gradients match an independently constructed always-sliced eager reference under `torch.equal`; all padding row and weight gradients remain zero.
- A nonlinear expert makes the two weighting boundaries observably different.
- The profiler checks the specific redundant `aten::slice_backward` work: zero events for exact-size buffers, and one event for each buffer that still requires trimming. This pins the allocation/copy regression directly rather than using tensor identity as a proxy.

Results:

- CPU, torch 2.14: the affected comm suite has **50 passed**, including all 24 new subcases.
- Negative control with the old unconditional slices: **16 of the 24 subcases fail the SliceBackward-count check**; the 8 cases that genuinely require all slices pass. Forward/gradient assertions do not fail.
- Existing accepted H100 validation: **263 passed, 1 skipped**, covering real DeepEP parity, AutoEP comm and AutoEP unit suites. The skip is MiniMax-M3 router-logit capture, which needs Transformers >=5.15.0; that environment uses 5.12.0.
- Changed-files `pre-commit` checks passed.

The H100 run used the actual original PR runtime. The initial review follow-up changed only tests and documentation. The later master synchronization below preserves the same slice-optimization delta while inheriting upstream replay support; it is not presented as a fresh GPU qualification of the merged tree. No GPU suite or full benchmark was restarted.

## End-to-end evidence

Qwen3-30B-A3B training on 8 H100s:

- EP8, micro-batch 4, 16 accumulation steps, sequence length 4,096, reentrant checkpointing, DeepEP configured with 36 SMs.
- 30 steps, 10 warmup, two repeats per arm in one allocation, order base/change/change/base.
- Both arms also use fused gate+up, backward weight-gradient overlap and recomputed-combine skip. They differ only in whether redundant whole-buffer slices are skipped.

| | Run medians (ms) | Mean of run medians (ms) |
|---|---|---:|
| Always slice | 19,873.6 / 19,898.3 | 19,886.0 |
| Skip exact-size slices | 19,553.4 / 19,547.3 | 19,550.3 |

The saving is approximately **336 ms / 1.69%**. Losses agree within same-arm repeat noise; peak allocated memory is unchanged. A real-DeepEP 8-GPU check before timing matched the existing route within DeepEP's arrival-order noise.

The benchmark prototype skipped both slices when both buffers were exact-size, as they were in this workload. The product implementation checks them independently; mixed capacities are covered by the new CPU regression, not by additional performance measurements.

These measurements cover one model, hardware type and training configuration. No universal speedup or long-run convergence result is claimed. Routing weights in SwiGLU are a separate optimization and are not included in the reported 1.69% saving.
