# [AffineIR] Affine storage maps for live ZeRO parameters and optimizer states

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8885) · state: closed · merged: True

## Original PR description

## Summary

Describes, as affine maps in global ranks, where a live ZeRO engine stores each element of a parameter and its optimizer states, so `plan_transfer` can read from or write into training storage directly (e.g. training → rollout weight sync) without gathering full parameters first.

- `zero_affine.py`
  - `zero_param_storage_affine_map`: low-precision replicas under ZeRO-0/1/2 (DP or expert-DP group), `ds_tensor` partitions under ZeRO-3, padding excluded.
  - `zero_optimizer_storage_affine_maps`: fp32 master + optimizer states (ZeRO-1/2, bf16 optimizer, ZeRO-3).
  - `zero_param_storage_shard` / `zero_optimizer_storage_shard`: flat views of ZeRO's own buffers matching the maps.
  - `autotp_storage_affine_maps`: AutoTP layout × ZeRO storage, one all-gather over the TP group.
- `affine.py`: `nest_affine_maps` composes a layout map (TP/EP shard placement) with per-shard storage maps. A process's stored run of an N-D shard is described as at most `2·ndim−1` N-D boxes in the parameter's own shape, so plans stay small (row-parallel shards are not cut per row).
- `affine_transfer.py`: `plan_transfer` accepts an N-D piece in a 1-D (flat) shard only when the piece is dense there; every other rank mismatch is still refused.
- `affine_ir_spec.md`: phase-2 section on layout vs storage maps.
- Fix `test_convert_checkpoint` `stat().size` → `st_size` (from #8515).

No change to ZeRO, AutoTP or the executor. Offloaded optimizer states raise `NotImplementedError`; MiCS / hpZ are not covered.

## Tests

- `tests/unit/checkpoint/test_zero_affine.py`, `test_affine_transfer_plan.py`: ZeRO-0/1/2/3 param + optimizer maps checked against ZeRO's own buffers (bitwise rebuild), AutoTP nest, N-D box count, flat-shard acceptance/refusal.
  - ≤2 ranks: Intel Arc B70 (XPU) ×2, pass. >2 ranks: CPU (gloo), pass.
- End-to-end (deepspeedai/DeepSpeedExamples#1021): Qwen3-8B, 8× NVIDIA L20, AutoTP-2 training engine → AutoTP-4 rollout engine via `autotp_storage_affine_maps` + `plan_transfer` + executor (#8809), ZeRO-2 and ZeRO-3, weights bitwise equal after every sync. Plans are built once and reused.

| Qwen3-8B, 8×L20 | ZeRO-2 gather | ZeRO-2 affine `lowest` | ZeRO-2 affine `balanced` | ZeRO-3 gather | ZeRO-3 affine |
|---|---|---|---|---|---|
| maps + plan (once) | - | 0.63 + 0.57 s | 0.70 + 0.70 s | - | 0.82 + 0.60 s |
| first sync | 1.01 s | 1.16 s | 0.48 s | 1.71 s | 1.18 s |
| repeated syncs | 0.78-0.82 s | 1.05-1.35 s | 0.49-0.55 s | 1.22-1.28 s | 0.45-0.74 s |
| device memory added | 3.48 GB | 0.30 GB | 0.16 GB | 3.48 GB | 0.66 GB |
| sent / local copy | - | 35.2 / 5.0 GB | 15.1 / 25.1 GB | - | 34.0 / 6.3 GB |
| executor rounds | - | 96 | 41 | - | 32 |

Each map has 3,192 pieces on both sides; before N-D boxes (one piece per stored row) the same ZeRO-3 maps had 592k source / 2.36M target pieces and planning took 207 s. Under ZeRO-2 every DP rank holds a replica: `lowest` is the planner's default holder choice, `balanced` is a `replica_selector` in the example (local copy first, else the least-loaded holder).

Thanks @jinyouzhi, I went through the `plan_transfer` relaxation. From the planner side it is safe and I'm happy with it as written.

**Why the invariant from #8624 still holds.** For a flat shard, a piece's local footprint becomes the run `[dest_offset, dest_offset + numel)`. `_shards_tile` still checks that the runs of one rank are pairwise disjoint and add up to the shard size. So two pieces still cannot write the same shard address, and a hole is still caught. The dense check (dest strides must equal the box's own row-major strides) refuses everything that is not one run. The source side keeps its existing check against the logical row-major strides. Nothing beyond a dense run is newly accepted.

I added adversarial cases locally against 42bafc57 and all of them behave as expected:
- refused: two flat pieces whose runs overlap, a hole in the shard, a run past the end of the shard, transposed / padded / gapped dest strides, a 1-D piece describing a matrix, a 2-D shard of a 3-D parameter;
- planned and checked element by element: flat storage on the **target** side (a ZeRO cut inside a row on the write side), flat storage on both sides (40 random TP×ZeRO-3 → TP×ZeRO-3 relayouts with partitions that start mid-row), ZeRO-2 replicas with a random `replica_selector`, and one map that mixes `(numel,)` and N-D shards across ranks;
- Qwen3-8B dense shapes (254 matrices), TP2×ZeRO-3 DP4 → TP4×ZeRO-3 DP2 through `nest_affine_maps`: 2,032 pieces per side, maps + plans in 0.28 s on a laptop CPU.

**Executor (#8809).** No change is needed for flat segments. Segments on the flat side carry the piece's own row-major strides. `_validate_buffers` already bounds the reach of those strides, and `_region` already adds the buffer's own storage offset. The shards that `zero_param_storage_shard` / `zero_optimizer_storage_shard` return are packed views, which is what `_flat` requires. I cherry-picked #8809 onto 42bafc57. The only conflict is in docs. On CPU (gloo, 4 ranks) the executor, planner and ZeRO-map tests pass together, apart from the four `TestAutoTPStorageMaps` cases in 1 below.

Three small requests:

1. **`TestAutoTPStorageMaps` fails on CPU because of the test, not the code.** With `DS_ACCELERATOR=cpu` (4 ranks, gloo), all four cases fail at the planned-copy check. I reproduced this on two machines. `_all_shards` gathers `shard.detach().cpu()`. On CPU that is the view itself, so the unpickled bias keeps its storage offset into the flat buffer (72 elements in the first case). `torch.as_strided(..., segment.source_offset)` then counts from the start of the storage and reads the weight's bytes. On XPU, `.cpu()` makes a fresh copy, which hides this. Gathering `shard.detach().cpu().clone()`, or adding `storage_offset()` the way the executor's `_region` does, makes all 27 tests in the file pass on CPU.
2. **A target-side flat test.** `test_a_flat_shard_holds_a_dense_box_of_a_matrix` covers flat storage only as the source. A restore or reverse sync writes into ZeRO storage, so a case with a flat target cut inside a row would pin the write direction. I can push mine if that helps.
3. **Mixed shard ranks in one map.** `_normalized` now lets one map have `(numel,)` shards on some ranks and N-D shards on others. That plans correctly in my test. If it is intended, a one-line test would document it. If not, it is cheap to refuse.

3. Mixing flat and N-D shards in one map is intended: for example, ranks that keep a ZeRO flat partition next to ranks that hold an unpartitioned shard. `[flat_and_matrix_shards]` documents it.

On replica selection: I agree the planner should not hard-code a hardware cost model (links, contention, topology), because costs depend on the machine and on the goal. But the planner is the right place to *apply* one: given a pluggable cost or policy, it sees every request and can balance and split globally, which a per-request selector cannot. Concretely:
- **The default.** Lowest-rank is the worst policy we measured. Local-first, then fewest assigned bytes, needs no hardware information, stays deterministic, and roughly halved the ZeRO-2 sync time (0.49 s vs 1.05–1.35 s).
- **The interface.** A per-request selector cannot balance load (it sees one request at a time, so results depend on call order) and cannot split a region across holders. A batch form, where the selector receives every request and returns an assignment that may split regions while the planner checks the split tiles exactly, would let external policies do both.

It is not strictly necessary to achieve the absolute optimum right away; my view is that we should provide as much room as possible for the cost model to perform optimizations, while avoiding premature optimization. Happy to open a separate issue for this if you think it's worth discussing. 


- jinyouzhi · comment · 2026-10-26T15:02:03Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8885#issuecomment-6419331329)

And I want share some follow-up ideas for the planner from #8623, which I hit while building storage maps. @0z5a Could you have a look on it? Thanks!

| Check | Current approach | Geometric problem | Better algorithm |
|---|---|---|---|
| `_shards_tile`: a rank's pieces don't overlap in shard addresses | Pairwise, O(n²) | Box disjointness detection | Sweep line with an active set. In 1-D, sort and compare neighbours: O(n log n) |
| `_validate_holders`: one rank's logical boxes don't overlap, and the declared holders are correct | O(n²), plus n × ranks coverage sums | Disjointness detection plus box deduplication | Group by box in a hash map, so each rank's coverage query becomes a key lookup |
| `_sources`: distinct source regions don't overlap | O(R²) | Same as above | Sweep line |
| `_covers_union`: target pieces cover the whole parameter | Subtract box by box; fragments can grow exponentially | Klee's measure problem (volume of a union of boxes) | Deduplicate, verify disjointness, then compare the summed volume: O(n log n) |
| Source × target intersection | All S×T pairs | Red–blue box intersection reporting | Sweep line with an interval tree: O((S+T) log + K), where K is the number of segments produced |

**Structural fast paths**
- **Grid layouts** (TP/EP, each axis cut independently): merge breakpoints per axis. Each intersection is the product of per-axis interval overlaps, O(Σ per-axis breakpoints + K), with no general-purpose data structure needed.
- **ZeRO flat fragments**: in N-D they become full rows plus partial rows at each end. A sweep sorted on axis 0 is close to linear.

- 0z5a · comment · 2026-10-28T09:37:42Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8885#issuecomment-6465577586)

Thanks @jinyouzhi, and sorry for the slow reply.

**Planner complexity.** Your table matches the code, and one point makes it more than a speed question: each of these checks is guarded by `PlanBudget.max_pair_checks` (2^18 by default), so the default budget is also a scale limit. A parameter with more than 512 non-empty pieces on one side fails `_validate_holders`, which for a ZeRO-3 parameter means more than 512 ranks, and fewer when partitions are cut mid-row. `plan_transfer` also refuses more than 2^18 source × target pairs. A caller can raise the budget, but then pays the quadratic cost in Python.

The order I'd take them in:
1. `_validate_holders`: group by box in a hash map. It is the check that binds first, and the change is local.
2. Source × target: the grid fast path for TP/EP, and a sort on axis 0 for ZeRO flat fragments (full rows plus partial ends). A general interval tree can wait until a layout needs it.
3. `_covers_union`: dedupe, check disjointness, compare volumes. Target boxes that overlap without being equal need a decision: keep the current subtraction as their fallback, or refuse them. Either way a test should pin it.
4. `_shards_tile` and `_sources`: sort and compare neighbours. These are small in practice, since a rank holds only a few pieces of one parameter.

On the shared `affine_geometry.py` you proposed on Slack: +1 from the planner side, and I'm happy for you to take it. Two requests. Keep the pure move separate from the algorithmic changes, so the move can be reviewed as a no-op. And for each new check, use the current implementation as the oracle on randomized maps (the adversarial cases from my earlier comment included), plus a planning-time curve over the rank count. I'll review the planner side.

**Replica selection.** Thanks for the clarification; I had read `lowest` / `balanced` / `first` as the proposal. I agree with the batch form:
- the planner hands the policy every request with its validated candidates;
- the policy returns an assignment that may split a region;
- the planner checks that each request's parts tile it exactly and use only validated holders.

That keeps the policy pluggable, which is what I meant earlier, and gives it the global view. The default can be your local-first, then fewest-assigned-bytes rule, which is deterministic and needs no hardware information.

@Achyuthan-S I can open the issue with a strawman of that interface this week, so it is agreed before you pick up the policy in mid-November.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Write through the resident persistent ZeRO-3 tensor**

When a ZeRO-3 target parameter is persistent and has already been gathered, which is its normal state after the first forward, the coordinator never releases it and execution reads resident full `param.data`. This accessor nevertheless returns only `ds_tensor`; transfer-plan writes update the hidden partition but not the resident tensor, so subsequent rollout forwards silently keep using stale values, commonly for biases and normalization weights. The writable endpoint must update or describe resident data, or force a partition/regather.
