# ZeRO: apply the clip coefficient at full precision to bf16/fp16 gradients

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8970) · state: open · merged: False

## Original PR description

## Summary

With `bf16_master_weights_and_gradients` (or the fp16 equivalent), ZeRO's `unscale_and_clip_grads` scales the gradient partitions in place with `grad.mul_(1. / combined_scale)`, where `combined_scale` is a 0-dim fp32 device tensor. Elementwise ops cast a 0-dim device tensor to the other operand's dtype, so the clip coefficient is rounded to bf16 before the multiply: up to 0.39% off (2^-8). With a gradient norm of 1.0033 and `gradient_clipping: 1.0`, about a quarter of the clipped bf16 gradients differ from an fp32 multiply. A Python float or a CPU scalar is applied at full precision, and so is any scale on fp32 partitions, so the default configurations are unaffected.

- Add `deepspeed.runtime.utils.scale_grads_`. For a gradient of lower precision than a tensor scale, it multiplies in the scale's dtype in chunks of 2^24 elements, so the temporary stays bounded and there is no host sync (the reason #5632 moved the clip to `torch.clamp`). Otherwise it is `grad.mul_(scale)`.
- Use it in ZeRO-1/2 and ZeRO-3 `unscale_and_clip_grads`. ZenFlow's ZeRO-3 path scales fp32 CPU `overlap_grad` buffers and is unchanged.

## Test plan

- [x] `tests/unit/v1/zero/test_clip_scale_precision.py` (new; 1x H200): the helper with bf16/fp16 gradients (chunked) and fp32 gradients, plus ZeRO-1/2 and ZeRO-3 `unscale_and_clip_grads` with bf16/fp16 partitions compared bitwise with an fp32 multiply. All 7 pass with the change. On master, the ZeRO-1/2 and ZeRO-3 cases fail their equality assertions (the helper cases fail on the missing function).
- [x] The CPU-only and single-GPU tests in `tests/unit/v1/zero/test_invalid_grad_norm.py` and `tests/unit/runtime/test_runtime_utils.py` pass.
- [x] End to end (8x H200): one ZeRO-2 step with `bf16_master_weights_and_gradients` and forced clipping, for two models, now matches an fp32 reference clip coefficient. It was 0.30-0.33% low before.

Read at `d6849627`.

The bf16/fp16 rounding this targets doesn't reproduce on the CPU accelerator. There a 0-dim CPU tensor is applied as a full-precision scalar, so `bf16_grad.mul_(fp32_scale)` already matches an fp32 multiply on master. As a result, the new file run against master on CPU gives 3 failed / 4 passed. The 3 failures are the helper tests, which fail because `scale_grads_` doesn't exist there; the four `unscale_and_clip_grads` cases pass. So I couldn't check the fix itself, and those four tests only guard it on GPU runners, not on a CPU suite.

What I could check is the side effect Codex raised, and it holds for ZeRO-3. I ran a real 3-step loop with plain `bf16: {enabled: true}` (fp32 master partitions), forced clipping, and recorded what reaches `scale_grads_`:

- ZeRO-3: fp32 gradient partitions with an **fp64** scale, because the norm is computed in `get_norm_dtype()`. They now take the chunked fp64 path. After 3 steps, 286 of 4680 final weights differ from master, by about 1 ulp.
- ZeRO-2, with and without optimizer offload: the scale arrives as fp32, so the plain `mul_` path runs and the weights are bitwise equal to master.

So the default ZeRO-3 configuration is not unaffected: its result changes slightly, and each 2^24-element chunk needs a 128 MiB fp64 temporary plus extra passes over the partition.

Restricting the chunked path to bf16/fp16 gradients and multiplying in fp32 fixes this. I tried it:

```python
if not torch.is_tensor(scale) or grad.dtype not in (torch.bfloat16, torch.float16) or not grad.is_contiguous():
    return grad.mul_(scale)
for chunk in grad.view(-1).split(_SCALE_CHUNK_NUMEL):
    chunk.copy_(chunk.float().mul_(scale))
```

With that change, the ZeRO-3 run above is bitwise equal to master, and your 7 tests still pass. A case with fp32 gradients and an fp64 scale, asserting equality with `grad.mul_(scale)`, would cover the default path, since the current fp32 test uses an fp32 scale.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Keep fp32 partitions out of the fp64 promotion path**

When gradient clipping is enabled on an accelerator reporting fp64 support, `get_norm_dtype()` in `deepspeed/runtime/zero/utils.py:59-63` makes the normal ZeRO norm and `combined_scale` double precision. Consequently this predicate also promotes the default fp32 master-gradient partitions (`4 < 8`), so ZeRO 1/2/3 now allocate up to a 128 MiB fp64 temporary per chunk and execute an fp64 conversion/multiply/copy on every clipped step instead of the previous fp32 `mul_`; this can substantially slow or OOM otherwise-default training. Limit the promotion to bf16/fp16 gradients or cap its compute dtype at fp32; the added fp32-scale test does not exercise this production dtype.
