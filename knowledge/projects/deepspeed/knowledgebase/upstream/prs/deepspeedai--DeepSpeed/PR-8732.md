# Enable CUDA Graph for continuous rollouts

## Summary

Enable experimental CUDA Graph decode replay for greedy Hybrid Engine rollouts that use
`SamplingConfig.continuous_batch_size`.

- Keep a fixed-capacity physical slot layout for each captured graph.
- Preallocate static decode inputs, additive causal masks, position IDs, write positions, and
  `DeepSpeedStaticCache` rows.
- Refill retired physical slots with prefetched requests while masking inactive rows, so replay always uses stable
  tensor addresses and a fixed batch shape.
- Reuse a captured graph across matching rollout calls. Rebuild it when the model parameter storage/version, device,
  dtype, batch capacity, prompt width, or cache shape changes.
- Use a preallocated four-dimensional additive mask during capture, avoiding Transformers mask-construction
  operations that are not CUDA-graph-safe while preserving the model's configured attention implementation.
- Preserve generated-token attention masks across decode steps and clear
  retired rows before reuse.
- Preserve the existing upstream continuous-batching behavior for aligned decode fronts, cache trimming, legacy prefill,                     repetition penalty, and statistics.

## Requirements and limitations

CUDA Graph capture currently requires CUDA inputs, greedy decoding, one sample per prompt, equal padded prompt
widths, `align_decode_fronts=False`, and `enable_cache_trimming=False`. The graph path rejects aligned decode fronts
and cache trimming explicitly because those modes move cache rows or columns, whereas a captured graph requires fixed
physical addresses.

Models that explicitly report no cache-class support remain rejected. Models with unknown support use the legacy
prefill path and should be validated against eager generation before production use.

On an NVIDIA RTX A4500 with PyTorch 2.9.1+cu128 and Transformers 4.57.1, locally initialized small GPT-2 and Llama
models produced token-identical eager and CUDA Graph outputs. Two different GPT-2 prompts reused one capture
(`capture_count=1`).

The same validation ran with public `openai-community/gpt2` pretrained weights in FP16. Two fixed-length,
left-padded prompts with seeds 1234 and 1235 produced token-identical eager and CUDA Graph outputs, including
attention masks, while reusing one capture (`capture_count=1`).

## Performance

The former synthetic continuous-rollout sample included graph capture in every rollout and is not representative of
the reused steady-state path. Production benchmarking should report both first-call latency, which includes capture,
and steady-state reuse separately.

For a local sanity check on the RTX A4500, a randomly initialized medium GPT-2 model with BF16 disabled, batch size
1, prompt length 32, response length 32, two warmup calls, and five steady-state measurements produced:

| Mode | Median latency | Throughput |
| --- | ---: | ---: |
| Eager | 250.88 ms | 127.55 tokens/s |
| CUDA Graph reuse | 31.45 ms | 1,017.62 tokens/s |

This is a local synthetic sanity check, not a production-model result. Production-model measurements should use fixed
prompts and report first-call and steady-state results independently.

## Required changes

### 1. Keep `static_cache_position` alive for the graph's lifetime (correctness)

In `_get_continuous_graph_state`, `static_cache_position` is created locally, passed into `_capture_continuous_graph`, but never stored in `_ContinuousGraphState`. After the function returns, the tensor is freed and its block returns to the caching allocator, while the captured kernels retain its device pointer.

This works today for GPT-2/Llama only because the captured region happens not to read `cache_position` (position_ids and the 4-D mask are passed explicitly, and `DeepSpeedStaticCache.update` uses `_write_position`). Other model families read `cache_position` inside forward (mask construction, `crop()`, slicing), so a replay after that block is reused would read clobbered memory — a silent-corruption risk. The CUDA-graph contract is that every graph-referenced tensor outlives the graph; the other five static tensors already do.

Suggested fix (one field):

```python
@dataclass
class _ContinuousGraphState:
    ...
    static_cache_position: torch.Tensor
```

plus passing it through in `_get_continuous_graph_state`.

### 2. Route the capture check through the accelerator abstraction (convention)

In `deepspeed/utils/static_cache.py`:

```python
is_capturing = (get_accelerator().device_name() == "cuda"
                and torch.cuda.is_current_stream_capturing())  #ignore-cuda
```

The bypass itself is right (the `.any()` → `bool()` sync is not capturable), but per project conventions device-specific behavior should go through the accelerator abstraction rather than an `#ignore-cuda` escape in shared code. Suggested shape:

```python
# abstract_accelerator.py
def is_current_stream_capturing(self) -> bool:
    return False  # safe default: backends without graph capture never bypass

# cuda_accelerator.py
def is_current_stream_capturing(self) -> bool:
    return torch.cuda.is_current_stream_capturing()
```

and `static_cache.py` becomes `is_capturing = get_accelerator().is_current_stream_capturing()`. This also removes the `device_name()` string check and the marker, gives CPU the correct answer by construction, and leaves a one-line override for other graph-capable backends later.

## Suggested follow-ups (non-blocking, happy to see as follow-up PRs)

- **First-call cost & graph pooling with prompt-length bucketing**: the performance table reports steady-state after warmup, but the signature includes `parameter._version`, so in an RL loop every post-training rollout pays a full first call (cache allocation + 3 warmup forwards + capture) — worth quantifying separately (capture vs. allocation split). Related: the graph state is single-slot today, so alternating prompt widths (A→B→A) recapture on every call. Bucketing prompt lengths (padding to a bucket boundary; with `continuous_cache_capacity` pinned, the graph shape depends only on `(max_batch_size, max_cache_len)`) combined with a small per-bucket graph pool would amortize captures across varying widths without creating too many graphs.
- **Batch the EOS check**: `_is_eos` calls `.item()` per active request per step (inherited from the eager path); one batched D2H per step would keep more CPU-side prep overlapped with replay.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Avoid overwriting refilled rows during fixed-batch replay**

When one request reaches EOS while another survives and a pending request refills the freed slot, the loop prefills the new row and then leaves its write position at zero here. Because the captured forward still executes every physical row, that newly admitted row writes the dummy token's KV at column 0, replacing its just-copied prompt KV; for unpadded or right-padded prompts whose first mask entry is attended, subsequent decoding reads corrupted cache and can return different tokens. Use a masked scratch position for rows outside `decode_ids` or perform the refill after replay.
