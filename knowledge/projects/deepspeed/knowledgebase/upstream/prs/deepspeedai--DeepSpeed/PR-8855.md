# Expect AutoTP to keep a row-parallel output head tied to the embedding

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8855) · state: open · merged: False

## Original PR description

## Summary

Fixes a stale test expectation. `TestTiedOutputHead::test_row_parallel_tied_head_is_refused[False/True]` in `tests/unit/v1/moe/test_autoep_autotp_sharded_attention.py` fails on master:

```
AssertionError: AutoTP sharded an output head whose weight is tied to the input embedding
```

The test (added in #8670) expects AutoTP to refuse a row-parallel output head whose weight is tied to the input embedding. Since 3c6a5ca95 ("[AutoTP] Support tied embeddings for row-parallel…"), AutoTP supports this case: it replaces the embedding with a `HiddenParallelEmbedding` that shares the head's sharded weight. The two changes landed a day apart, so the expectation was already stale when #8670 merged.

Change (test only, no runtime code modified):
- Rename the test to `test_row_parallel_tied_head_keeps_the_tie`.
- With and without `zero.Init`, check after `deepspeed.initialize` that the embedding is a `HiddenParallelEmbedding` and `lm_head.weight is embed_tokens.weight`.

The original concern of the test still holds: under `zero.Init` AutoTP gathers the partitioned head weight into a new parameter, and if the embedding kept the old one the two would train as separate copies. The identity check catches that. Numerical training parity of a tied row-parallel head is already covered by `TestTiedRowParallelOutputHeadTraining` in `tests/unit/v1/autotp/test_autotp_training.py`.

## Related work

No open PR fixes this test. #8829 and #8848 both list these two failures as pre-existing and leave them unchanged. I searched open PRs touching `TestTiedOutputHead` and tied/vocab-parallel output heads.
