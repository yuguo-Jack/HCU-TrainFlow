# Fix BF16 AutoEP folding: avoid BF16 round-trip in FP32 accumulation

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8989) · state: closed · merged: False

## Original PR description

## Summary

`_update_hp_grad` in `BF16_Optimizer` applies AutoEP folding correction to `lp.grad` (BF16). The correction helper (`reduce_autoep_folding_gradient`) internally promotes to FP32 for the TP all-reduce, but copies the result **back to the BF16 grad buffer** before returning. The caller then casts this rounded BF16 value to FP32 for accumulation:

```
BF16 local grad -> FP32 TP reduction -> BF16 writeback -> FP32 accumulation
                                         ^^^^^^^^^^^^
                                         unnecessary precision loss
```

This introduces an avoidable BF16 rounding boundary between the FP32 reduction and FP32 accumulation, causing numerical divergence in router gradients, master weights, and Adam moments under AutoEP+AutoTP folding (reported as grad norm 0.78 vs 7.91 on a 65k-token sequence).

## Fix

Promote `lp.grad` to FP32 **before** passing it to the folding correction, so the TP reduction operates directly on the FP32 staging tensor. The corrected FP32 result then feeds into the high-precision accumulation buffer without a BF16 round-trip.

When AutoEP folding is not active, the original cast-and-accumulate path is unchanged.

Fixes #8913

## Test plan

- This fix is a single-file change to the accumulation path in `bf16_optimizer.py`
- The folding correction logic in `auto_ep_folding.py` is unchanged; it already handles FP32 inputs correctly via its existing `dtype != torch.float32` branch
- Validation requires a multi-rank AutoEP+AutoTP setup (TP2/EP2); the reporter's reproduction guidance in #8913 describes the tensor comparison methodology

So the fp32 reduction itself is fixed here. The two cases that still fail are `test_hp_buffer_keeps_fp32_reduction` with `clear_lp_grads=False`. After `_update_hp_grad`, the parameter is marked corrected, but `lp.grad` still holds the local, pre-reduction gradient, because the corrected fp32 value only goes into the hp buffer. `backward_epilogue` uses `clear_lp_grads=False` by default, so after backward, anything that reads `param.grad` sees the uncorrected value, and consuming that gradient a second time skips the correction. #8920 copies the corrected value back into `lp.grad` for this reason, and only promotes when `grad_acc_dtype` is fp32.

Since #8920 covers the same issue and has the tests, it may be simplest to consolidate there.
