# Add deepspeed.models.glm_moe_dsa: TileLang sparse attention for GLM-5.2

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8659) · state: open · merged: False

## Original PR description

# Add `deepspeed.models.glm_moe_dsa`: TileLang sparse attention for training GLM-5.2

**Part of:** #8672 (Q4 2026 roadmap), "Enable training of large scale models": "Test and verify support of SOTA
models" (PoC @pengdurice). Sibling: #8658 (MiniMax-M3).

## Summary

* GLM-5.2 cannot train past 16,384 tokens per GPU with the stock transformers attention. Its indexer
  scores and its attention mask are both dense `seq x seq` tensors.
* This PR adds TileLang kernels that attend only to the 2,048 keys the indexer selects for each query,
  with a backward pass, and a replacement attention module that uses them. One call,
  `deepspeed.models.glm_moe_dsa.replace_attention(model)`, swaps it in.
* With it, the full 78-layer GLM-5.2 (743.4B parameters) trains at 65,536 tokens per GPU on 8 nodes of
  8 H200. On an 8-layer cut of the model at 16,384 tokens, 10 training steps give the same loss as the
  stock path and run 2.7 times faster.
* It adds a new folder, `deepspeed/models/<family>/`, for training code that belongs to one model
  family.

## Why a `deepspeed/models/` folder

Some models need changes that only make sense for that model: a kernel for its attention, a
replacement module, a fix for its layout. Other training stacks keep this code in one folder per model
family, for example `torchtitan/models/<model>/`, Megatron-Bridge's `src/megatron/bridge/models/<family>/`,
and THUDM/slime's `slime_plugins/models/glm5/`. DeepSpeed has no such place on the training side.
The inference side has `deepspeed/inference/v2/model_implementations/<family>/`, and AutoEP keeps one
preset file per model in `deepspeed/module_inject/auto_ep_presets/`.

The convention this PR starts:

* One package per family in `deepspeed/models/`, named after the model's folder in
  `transformers.models`. Here that is `glm_moe_dsa`. A reader goes from a Hugging Face model to its
  DeepSpeed code without a lookup table.
* A family package holds whatever that family needs: kernels, modules, or plain PyTorch. Here it holds
  the TileLang kernels in `kernels/` and the replacement module in `attention.py`.
* A family package exposes the function to call on a built model before `deepspeed.initialize`. Here
  that is `replace_attention`.
* `import deepspeed` does not import `deepspeed.models`. A family's optional dependency (here TileLang)
  is needed only by users of that family.

The MiniMax-M3 sparse-attention PR adds a second family, `deepspeed/models/minimax_m3_vl/`. Both PRs
add the same `deepspeed/models/__init__.py` and the same docs index entry, byte for byte, so they merge
in either order without conflicts.

## Problem

GLM-5.2 (transformers `glm_moe_dsa`, DeepSeek Sparse Attention) cannot train at long sequence lengths
on the stock transformers path, whatever DeepSpeed does about parameters and optimizer state:

* `GlmMoeDsaIndexer.forward` scores every query against every key as a dense float32
  `[batch, 32 index heads, S, S]` tensor before the top-k. That is 34 GB at S = 16,384 and 137 GB at
  S = 32,768, for each layer, before the relu copy and the head-weighted sum.
* `GlmMoeDsaAttention.forward` then turns the top-k indices into a dense `[batch, 1, S, S]` additive
  mask. It calls the attention interface with per-head K and V expanded from the 512-wide latent
  (`expand_kv`). So the attention is dense too, quadratic in S, and cannot use the absorbed form.
* Registering another attention function through `AttentionInterface` does not help. By the time the
  interface is called, the module has already expanded K and V and built the mask.

THUDM/slime trains GLM-5 in Megatron with TileLang kernels that do two things:

1. compute the indexer logits in blocks of query rows and take a hard top-k;
2. run attention in the absorbed multi-head latent attention form over the selected latent keys only,
   with a fused backward.

Depending on slime or Megatron for these kernels is not an option, so this PR adapts them into
DeepSpeed.

## The change

**`deepspeed/models/__init__.py`** (new): the package docstring that states the convention above. It
imports nothing.

**`deepspeed/models/glm_moe_dsa/kernels/`** (new): the kernels. They are adapted from the
`deepseek_v32` examples in tile-ai/tilelang (MIT), by way of the GLM-5 plugin in THUDM/slime
(Apache-2.0). The kernel bodies are the same. The Megatron, context-parallel and sequence-parallel
code is removed, and the latent width is a parameter instead of a constant. Importing this package
imports TileLang.

| file | what it holds |
|---|---|
| `sparse_mla_fwd.py` | forward kernel: online softmax over the gathered top-k latent keys, `-1` indices masked; returns the output and the log-sum-exp |
| `sparse_mla_bwd.py` | backward: preprocess (delta), the `dq` kernel and the atomically accumulated `dkv` kernel, postprocess |
| `sparse_mla.py` | `sparse_mla(q, kv, indices, scale, d_v)`: the `torch.autograd.Function` around the two |
| `indexer_fwd.py` | lightning indexer logits for a block of query rows, `[rows, keys]` float32, `-inf` outside each row's window |
| `indexer.py` | `select_topk(...)`: runs the indexer in blocks of 8,192 query rows (2 GiB of logits per block at 65,536 keys), takes the top-k per block, pads rows with fewer keys with `-1`; `@torch.no_grad()` |

Shapes are token-major: `q [tokens, heads, 512 + 64]`, `kv [tokens, 1, 512 + 64]`, and
`indices [tokens, 1, topk]` int32 with `-1` for unused slots. `topk` must be a multiple of 64.

**`deepspeed/models/glm_moe_dsa/attention.py`** (new): `DeepSpeedGlmMoeDsaAttention(source)` and
`replace_attention(model, index_block_rows=8192, warm_up=True)`.

* The replacement keeps the source module's parameters and attribute names (`q_a_proj`,
  `q_a_layernorm`, `q_b_proj`, `kv_a_proj_with_mqa`, `kv_a_layernorm`, `kv_b_proj`, `o_proj`,
  `indexer`). State-dict keys, parameter-freezing patterns and AutoTP name patterns do not change.
  Only `forward` is different.
* Forward, step by step:
  1. The no-rope part of the query is absorbed into the latent with this head's slice of
     `kv_b_proj.weight`: `q_nope . (W_kc kv) == (W_kc^T q_nope) . kv`.
  2. Rotary embedding is applied interleaved, as in the model.
  3. The indexer selects the top-k positions. The scores are the same as in transformers:
     `sum_h w_h relu(scale q_h . k)`. The scale is folded into the weights, which is exact because
     relu is positively homogeneous.
  4. `sparse_mla` attends over the selected latent keys.
  5. The other slice of `kv_b_proj.weight` maps the output back to value space before `o_proj`.

  Layers of type `"shared"` reuse `prev_topk_indices` from the previous full layer, as the stock
  module does.
* The module reads `kv_b_proj.weight` as a tensor and never calls `kv_b_proj`, so ZeRO-3 gets no
  forward hook for that weight. The module registers the weight with
  `deepspeed.zero.register_external_parameter`. ZeRO-3 then gathers it for this module's forward and
  backward and releases it afterwards.
* The indexer is not trained. A hard top-k has no gradient, and transformers does the same (its
  indexer forward is `@torch.no_grad()`). Under ZeRO-3, users freeze the indexer parameters, as they
  already must on the stock path.
* Training only:
  * no key-value cache;
  * no padding mask: every sequence in the batch is one full causal sequence;
  * attention dropout must be 0.
* Replace every DSA attention layer of a model, or none. The stock module encodes the earliest rows'
  missing keys through its causal mask, and this one through `-1`, so a shared layer must receive
  indices from a layer of its own kind.
* Constructor checks:
  * `kv_lora_rank` and `qk_rope_head_dim` are powers of two;
  * `index_topk % 64 == 0`;
  * the head count is at most 64 or a multiple of 64;
  * the index head count divides 128.
* `replace_attention` checks for TileLang first and raises `ImportError` with the install command.
* Kernel warm-up. With `warm_up=True` (the default), when the backward kernel uses 128 threads (head
  blocks under 64 heads, for example with the heads split over tensor-parallel ranks), each attention module
  launches every kernel once, forward and backward, on a 128-token input with the model's head counts, head
  dims and top-k, at its first forward and on that forward's device. It runs without autograd, so activation
  checkpointing's recomputation saves the same tensors as the first forward.
  * Why: the 128-thread backward kernel spills registers, so its first launch makes the CUDA driver reserve
    local memory outside PyTorch's allocator, and the driver keeps it. Without the warm-up that launch
    happens in the first backward of training, when the allocator's cache can hold the rest of the device.
    On the full 78-layer GLM-5.2 at 65,536 tokens per GPU on 64 H200s it failed there with
    `CUDA_ERROR_OUT_OF_MEMORY` on 3 of the 64 GPUs.
  * The 256-thread kernel (64-head blocks: GLM-5.2's 64 heads on one GPU) does not spill, so it gets no
    warm-up. Measured on one H200, 64 heads, 32,768 tokens, memory used outside PyTorch's allocator around
    the first backward launch:

    | Backward kernel | First training-length launch, no warm-up | 128-token warm-up launch | Training-length launch after the warm-up |
    |---|---|---|---|
    | 128 threads | +0.469 GiB | +0.467 GiB | +0.000 GiB |
    | 256 threads (64-head blocks) | +0.002 GiB | not run | |

  * `kernels/sparse_mla_bwd.py` `backward_threads(heads_per_kv_group)` picks the thread count for both the
    kernel and the warm-up decision, so the two cannot disagree.
  * The forward and indexer kernels take the sequence length at run time, so the warm-up builds the kernels
    training uses. The backward kernel takes the batch size and both sequence lengths at compile time, so
    training's first backward still compiles its own backward kernel; what the warm-up launch provides is the
    local-memory reservation, which covers the training-length launch (table).

**`docs/code-docs/source/models/glm_moe_dsa.rst`** (new) and an entry in
**`docs/code-docs/source/index.rst`** that lists every page in `models/`: usage, requirements, limits,
and the API reference.

**`tests/unit/v1/models/test_glm_moe_dsa.py`** (new): see Tests.

Rebased on master (`5f266e26d`, 2026-10-15). All review points of the first round:

| Review point | Change |
|---|---|
| Kernels adapted from TileLang / THUDM carry only DeepSpeed's header | The three kernel files carry the upstream copyright (`Copyright (c) Tile-AI.`) and `SPDX-License-Identifier: Apache-2.0 AND MIT`, and point to a new TileLang section in `THIRD_PARTY_NOTICES.md` (files, TileLang source paths and revisions, the slime revision they came through, the full MIT text). `scripts/check-license.py` accepts the expression. `setup.py` now lists `THIRD_PARTY_NOTICES.md` in `license_files`; before, the notice was in neither the sdist nor the wheel (checked by building both). |
| `output_attentions=True` returns `attentions=()` | Raises `NotImplementedError`: the kernels never form attention weights. |
| Padding and packed-sequence masks are ignored | A padding mask, a packed-sequence mask or position ids that restart raise `NotImplementedError`. No mask and eager attention's full causal mask are accepted. The check waits for the GPU, so it runs once per model forward, not once per layer. |
| Widths 1 and 2 pass validation | `kv_lora_rank` and `qk_rope_head_dim` must be powers of two of at least 4 (the backward kernel splits the width into groups of 4). |
| The warm-up runs on GPU 0 in every process | It runs at the module's first forward, on the input's device. |
| The warm-up's backward kernel is compiled for 128 tokens | Correct: see the kernel warm-up bullet above. The warm-up now runs only for the 128-thread backward kernel, the one whose first launch reserves local memory. |

Two additions from running GLM-5.2 at scale:

* **256-thread backward kernel for 64-head blocks** (128 threads otherwise, as in tile-ai/tilelang#2592): 3.09x
  faster per kernel at GLM-5.2's shapes on an H200, 34-40% more tokens per second in training.
* **Sequence split (context parallel).** `deepspeed.models.glm_moe_dsa.set_context_parallel_group(group)`: every
  rank of the group holds a contiguous slice of each sequence with global positions; the latent keys and the
  indexer keys are all-gathered over the group and their gradients reduce-scattered back; the indexer's causal
  bounds use global positions. GLM-5.2's first 38 layers at 65,536 tokens on 4 nodes x 8 H200, each sequence
  over 2 GPUs, ZeRO-3 + AutoEP: 96.4 s per step, 9.44% MFU, losses within 0.03 and the step-1 gradient norm within
  0.02% of the same run on an earlier tree.

### Full GLM-5.2, all 78 layers, 8 nodes x 8 H200, 65,536 tokens per GPU

Setup:

* Model: config-only build of GLM-5.2 with all 78 layers. 743.4B parameters, 724.8B of them in 75 MoE
  layers of 256 experts (top-8). 21 layers run the indexer, 57 reuse its selection.
* Parallelism: AutoEP expert parallel 16 (4 expert groups of 2 nodes), TP 1, ZeRO-3 with
  `leaf_module` on the AutoEP layer.
* Memory: optimizer state offloaded to host memory. Activation checkpointing with the checkpointed
  layer inputs in host memory (`checkpoint_in_cpu`). bf16 master weights and optimizer states.
* Data: micro-batch 1, which is one 65,536-token PG-19 book per GPU. Tiled loss (16 shards). Indexer

* Steps: 1 warm-up + 3 measured, learning rate 1e-6.

### GLM-5.2 cut to 8 layers, 2 nodes x 8 H200, ZeRO-3 + AutoEP

Setup:

* Model: config-only build of GLM-5.2 cut to 8 of 78 layers. 5 MoE layers with 256 experts, top-8.
  The indexer schedule keeps both modes: layers 0, 1, 2 and 6 run the indexer; layers 3, 4, 5 and 7
  reuse the selection. 52.5B parameters, of which 48.3B are expert weights.
* Parallelism and memory: expert parallel 16, TP 1, ZeRO-3 with `leaf_module` on the AutoEP layer,
  bf16 master weights and optimizer states, Hugging Face gradient checkpointing.
* Data: micro-batch 1 per GPU. Tiled loss (16 shards) for the 154,880-token vocabulary. Real text:
  PG-19 books re-tokenized with the GLM-5.2 tokenizer, one book per row. Indexer frozen.
* Steps: 10 (3 warm-up + 7 measured).
* Versions: torch 2.8.0+cu126, transformers 5.15.1, tilelang 0.1.14.
* Throughput is tokens per second over all 16 GPUs.

| attention | seq | s / step | tokens / s (16 GPUs) | step peak allocated | peak reserved |
|---|---|---|---|---|---|
| DSA kernels | 16,384 | 4.65 | 56,429 | 54.6 GiB | 67.0 GiB |
| DSA kernels | 32,768 | 9.26 | 56,621 | 73.6 GiB | 91.5 GiB |
| DSA kernels | 65,536 | 18.46 | 56,798 | 112.0 GiB | 133.4 GiB |
| stock SDPA (memory-efficient kernel, dense top-k mask), second run | 16,384 | 12.70 | 20,645 | 71.6 GiB | 93.7 GiB |

## Tests

| `test_indexer_logits_and_selection_match_reference` (8 and 32 index heads) | the logits against the float32 formula, with `-inf` exactly on the future keys. `select_topk` returns the reference top-k on every row where the k-th and (k+1)-th scores are apart, the right number of valid slots on the early rows, and never a future key |

| `test_indexer_selection_at_glm52_sizes` | 32 index heads, 16,384 tokens (two 8,192-row blocks in `select_topk`), top-k 2048: exactly k distinct causal keys per row, each scoring at least the k-th best float32 score minus a rounding allowance, so no better key was left out |
| `test_replacement_matches_transformers_module` | on a small `GlmMoeDsaConfig`, the replacement's selection overlaps the stock indexer's on more than 90 % of slots (the two differ at ties). | `TestDsaAttentionZeroStage3` (2 ranks, ZeRO-3, `torch_adam`) | the loss and the gradient of `kv_b_proj.weight`, the weight read directly, match a single-process run of the same replaced model. Without the external-parameter registration the weight is a 0-element placeholder in the forward |

  `Apache-2.0 AND MIT`), and update `scripts/check-license.py` if needed to

I also found some issues in the code:

  `attentions=()` after replacement. Can we explicitly reject or warn if it's unsupported?

  reject unsupported padding/packing masks?
- **Dimensions:** Widths 1 and 2 pass validation but violate the backward
  kernel's requirement (it must be mulltiple of four). The results might be incorrect.

I have a question about warmup. Backward kernels are precompiled for a specific sequence length (128 tokens), but the precompiled kernel won't be used for the actual training. I still agree that it is still useful to avoid OOM, though.
