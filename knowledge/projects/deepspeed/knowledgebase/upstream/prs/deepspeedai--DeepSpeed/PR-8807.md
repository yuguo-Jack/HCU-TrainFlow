# Speed up import deepspeed by deferring heavy imports and import-time work

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8807) · state: open · merged: False

## Original PR description

## Related issues

Several issues complain about the import time behavior: huggingface/transformers#26308, huggingface/trl#3351, huggingface/transformers#37755, huggingface/accelerate#1963

## Summary

On master, `import deepspeed` takes about 5.5 s with GPU persistence mode on and about 12 s with it off. It imports
`transformers`, `torch._dynamo`/`torch._inductor`, `triton`, `sympy`, `setuptools` and the FastGen engine, calls
`torch.compile` 6 times, and probes every op builder with compiler subprocesses. None of that is needed to import the
package. This PR moves each of them to first use.

With this PR, `python -c "import deepspeed"` takes 1.8 s with persistence mode on, and DeepSpeed's own part of the
import is 0.19 s. Without persistence mode, the GPU query that stays at import still takes several seconds (see "What
still runs at import, and why").

Apart from a few unused top-level re-exports (see Compatibility notes), nothing is removed: the work runs when the
feature that needs it is used.

## Import time with this PR

| Stage | Time |
|---|---|
| `import torch` | 1.15 s |
| GPU query (accelerator auto-detect, NVML) | 0.12 s |
| DeepSpeed's own import (torch and NVML already loaded) | 0.19 s |
| Cold `import deepspeed` | 1.47 s |
| `python -c "import deepspeed"` (startup, import and exit) | 1.77 s |

The import loads 1,607 modules (415 of them `deepspeed.*`), none from `transformers`, `torch._dynamo`,
`torch._inductor`, `triton`, `sympy`, `setuptools` or FastGen. It makes no `torch.compile` call, starts no
subprocesses, runs no full garbage collection, and does not initialize CUDA. Accelerator auto-detect queries NVML
twice, and not at all with `DS_ACCELERATOR=cuda`.

## Changes
### 1. Heavy third-party imports moved to first use

- **transformers** (`linear/context_manager.py`): imported inside `deepspeed.linear.Init`, its only user.
  Importing it cost 1.05 s.
- **sympy** (`compile/custom_ops/all_to_all.py`): `FloorDiv` is imported inside the fake-tensor shape function that
  uses it. `torch.utils._sympy` imports sympy (420 modules, 0.26 s).
- **triton**: `deepspeed.HAS_TRITON` is computed on first access (module `__getattr__`) by the shared
  `deepspeed.ops.triton_ops._triton.is_triton_available()`. `ds_transformer.py` imports the Triton attention and MLP
  only when `use_triton` is set, and `moe/ep_kernels.py` reuses the shared check instead of its own `import triton`.
  Internal code still reads `deepspeed.HAS_TRITON`, so `deepspeed.HAS_TRITON = False` still disables DeepSpeed's
  Triton kernels.
- **distutils/setuptools** (`op_builder/builder.py`): imported inside `has_function()`, the only user. On Python
  3.12 `distutils` comes from setuptools.
- **cpuinfo** (`ops/adam/cpu_adam.py`, `ops/lion/cpu_lion.py`): imported in the `DeepSpeedCPUAdam` and
  `DeepSpeedCPULion` constructors, its only users. Importing py-cpuinfo starts two subprocesses (`file -b <python>`
  and `uname -p`).

### 2. No torch compiler stack at import

- **`compiled_autograd`** (`runtime/compiler.py`): imported on first use. It imported `torch._dynamo` at module
  level.
- **`compiler.lazy_disable`** (`runtime/compiler.py`): `torch.compiler.disable` imports `torch._dynamo` when the
  decorator is applied, which for 5 functions happened at import (`partitioned_param_coordinator.py` 4x,
  `activation_checkpointing.checkpointing.checkpoint`). `lazy_disable` uses `torch._disable_dynamo`, which imports
  dynamo on the first call and returns a function dynamo still skips. torch caches that function from 2.4 on, so
  older torch keeps `compiler.disable`.
- **DeepCompile** (`runtime/engine.py`): `backend`, `init_z1_and_2`, `init_z3`, `init_sp` and `init_tp` are imported
  inside the engine methods that use them. `compile/backend.py` imports `torch._dynamo` and `torch._inductor`.
- **MoE gating helpers** (`moe/sharded_moe.py`): `_capacity`, `_top_idx` and `_one_hot_to_float` are no longer
  wrapped in `@jit_script_compat` (`torch.compile` since #7840). `_top_idx` and `_one_hot_to_float` are inlined as
  `torch.topk` and `F.one_hot(...).float()`, and `_capacity` clamps with `torch.maximum` instead of a Python `if`.
  The compile gave no measurable speedup, made the first gating call compile for ~28 s, and `torch.jit.trace` (used
  by the TorchScript-based ONNX exporter) could not trace the helpers. With the `if`, a traced gate would also keep
  the capacity of the token count it was traced with.
- **Muon** (`runtime/engine.py`, `runtime/zero/stage3.py`, `runtime/zero/stage_1_and_2.py`,
  `runtime/zero/utils.py`): `MuonWithAuxAdam` and `muon_update` are imported where they are used, because the module
  calls `torch.compile` 3 times when imported (`@compiler.compile()`). `is_zero_supported_optimizer()` adds
  `MuonWithAuxAdam` to `ZERO_SUPPORTED_OPTIMIZERS` on first use.

### 3. Import-time work moved to first use

- **Op builder compatibility probes** (#7452): the probing loop moved unchanged from `git_version_info.py` into a
  lazy `deepspeed.ops.__compatible_ops__` (module `__getattr__`). It runs on first read and is cached, so edits to
  the dict persist. The probes start ~17 subprocesses (`gcc` test compiles, `nvcc -V`) and query the GPUs. The
  values are the same as before; the readers are `build_shm_op()` at `init_distributed()` and test `skipif` markers.
- **Quantization device check** (`inference/quantization/utils.py`): the module-level
  `get_accelerator().is_available()` now runs in `dequantize()`, where the device is needed. It queried the GPUs on
  every import, even with `DS_ACCELERATOR` set.
- **DeepCompile custom ops** (`compile/util.py`, `runtime/engine.py`): `autosp::all_to_all` and the three
  `autotp::*_tp_region` ops are registered when the AutoSP or AutoTP compile path is imported, which every user of
  the ops already does (`passes/sp_compile.py`, `passes/tp_compile.py`).

### 4. Lazy re-exports

- **FastGen** (`deepspeed/inference/__init__.py`): `RaggedInferenceEngineConfig`, `DeepSpeedTPConfig`,
  `InferenceEngineV2`, `build_hf_engine` and `build_engine_from_ds_checkpoint` resolve on first access (module
  `__getattr__`). `from deepspeed.inference import build_hf_engine, InferenceEngineV2` (as in DeepSpeed-MII) works as
  before. FastGen is 174 modules, and without them the import no longer triggers a full garbage collection.

### 5. Cleanup

- `deepspeed/__init__.py`: removed unused imports: `sys`, `types`, `ADAM_OPTIMIZER`, `LAMB_OPTIMIZER`,
  `add_tuning_arguments`, `revert_transformer_layer`, `domino` and `is_compile_supported`.

## What still runs at import, and why

### `import torch` (1.15 s, ~78% of the cold import)

DeepSpeed is built on torch: `deepspeed/__init__.py` exposes torch types in its API, and most modules subclass
`torch.nn.Module`, `torch.optim.Optimizer` or `torch.autograd.Function`, or use torch dtypes, when they are defined.
Deferring torch would mean making every public name of the package lazy, and any real use of DeepSpeed imports torch
anyway. The cost belongs to torch.

### GPU query, accelerator auto-detect (0.12 s; several seconds without GPU persistence mode)

`get_accelerator()` picks the backend (CUDA/ROCm, XPU, NPU, HPU, MPS, MLU, SDAA, SUPA or CPU) on its first call. On
NVIDIA it calls `torch.cuda.device_count()`, which with `PYTORCH_NVML_BASED_CUDA_CHECK=1` (set by
`deepspeed/__init__.py`) asks NVML instead of creating a CUDA context, so the import stays fork-safe. It is kept
because:

- **The import needs the accelerator in 11 places** (91 calls). The op builder registry binds every
  `deepspeed.ops.op_builder.*Builder` name to the current accelerator's class (80 calls). The others are type
  annotations (`Event`, `Stream`), default arguments (`device_name()`, `get_compile_backend()`), module-level
  aliases, and the autocast decorators of the ZeRO-3 linear layer, which need the device type when the class is
  defined.
- **Deferring the registry alone does not remove the query.** A prototype that resolves builder names on first
  access (module `__getattr__`) saved 9 ms, but the query still ran during the import: 19 module-level
  `from deepspeed.ops.op_builder import XBuilder` statements and the 10 other sites call `get_accelerator()`.
  Removing all of them touches ~25 files, including a decorator that resolves the device on first call. That is a
  separate change.
- **There is already an opt-out.** `DS_ACCELERATOR=cuda` skips the detection: with this PR the import then makes no
  device query (master: 10). `CUDA_Accelerator()` still calls `pynvml.nvmlInit()` when nvidia-ml-py is installed
  (~0.06 s).
