# Replay AutoEP's DeepEP dispatch layout in non-reentrant checkpoint recompute

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8731) · state: closed · merged: True

## Original PR description

With `comm_backend="deepep"`, a non-reentrant checkpoint that recomputes a fresh dispatch can silently corrupt AutoEP gradients. Pure reentrant checkpointing (without a nested non-reentrant region) and the collective backend are unaffected by the original layout defect.

DeepEP's received row order depends on arrival timing (unless its deterministic receive order is enabled). A non-reentrant checkpoint keeps the forward pass's autograd nodes, and with them the forward's dispatch handle, while replacing the activations they saved with recomputed ones. The recompute dispatched afresh, so the experts' recomputed activations came back in a new arrival order, while combine's backward still scattered gradient rows in the forward's order. A reentrant recompute builds a new graph whose nodes use the recomputed handle, so it stays consistent. This is the failure noted at the end of #8636.

### Change

- Each `AutoEPMoELayer` keeps a `DeepEPCheckpointReplay` record of its forward dispatch handles. Every fresh grad-enabled dispatch records its handle, including graph-building forwards of inner non-reentrant checkpoints during an outer reentrant checkpoint's backward. Only an actual cached-handle replay skips recording.
- Dispatches inside backward reuse the sole live forward graph's handle through DeepEP's cached path (`ElasticBuffer.dispatch(..., handle=..., topk_weights=..., do_expand=handle.do_expand)`). If no live handle exists, the dispatch is fresh. A device-side assertion checks that the recomputed routing equals the handle's.
- Lifetime and matching:
  - A record is owned by the autograd node of the combine that used its handle. It lives exactly as long as the graph that needs it, and is never part of a reference cycle, so it is still freed when Python GC is disabled.
  - A recompute is matched to its forward by requiring exactly one live forward graph. An earlier replay does not exclude a retained graph, which may run backward again. This holds when each micro-batch runs backward and releases its graph before the layer's next forward, as sequential gradient accumulation does.
  - If a recompute could belong to more than one live forward, it raises an error naming reentrant checkpointing as the alternative, rather than guessing.
- A reentrant checkpoint's first pass records nothing because it runs without grad. Its graph-building recompute records fresh dispatches when needed by a nested non-reentrant region; the standalone reentrant path still dispatches afresh and remains self-consistent.
- Docs: `autoep.rst` describes the checkpointing behavior and its constraint.

With PyTorch's default early stop, a non-reentrant recompute now also ends once the expert activations are restored, so it no longer repeats the combine, unless something after the combine in the checkpointed region saves activations (such as shared experts).

### Tests

- CPU, `TestCheckpointRecomputeLayout` in `tests/unit/module_inject/test_auto_ep_comm.py`.
  - Uses a buffer that follows DeepEP's dispatch/combine contract but gives every fresh dispatch a new arrival order.
  - Integer-valued data makes every sum exact, so reordering alone cannot change a result, while mismatched rows do.
  - Expert, gate and input gradients over three micro-batches match no-checkpoint exactly under both checkpoint modes (`rtol=atol=0`, not a signed-zero bit-pattern assertion).
  - Non-reentrant replays on the cached handle and stops before the combine.
  - Also covered: `retain_graph` backward twice on one graph; rejection after interleaving a retained graph with a new forward of identical routing; nested non-reentrant/reentrant checkpoints with trainable or frozen inputs; a discarded plain forward with GC disabled; and no-grad/discarded checkpoint forwards followed by a successful checkpoint backward. Tests assert observable gradients and errors, not private weak-reference containers. Changed routing remains rejected.
  - The current comm file passes all 62 tests; three configuration-helper cases also pass. The preceding runtime reproduces both nested gradient failures and the missing retained-graph rejection.
- H100, `test_autoep_deepep_parity.py`, uniform and skewed routing, 256 rows per rank.
  - Compares ordinary and nested non-reentrant checkpoints with reentrant, retaining relative L2 error below 1e-2 for the input gradient and every parameter gradient.
  - Checks that ordinary non-reentrant early stop runs one combine per layer; nested non-reentrant/reentrant runs two forward combines and three layer forwards.
  - Real DeepEP also checks retained-graph interleaving is rejected on every rank.
  - The existing comparison's absolute tolerances (gradient `atol=5e-2`, parameter delta `atol=5e-4` at `lr=1e-4`) exceed this model's gradients and first Adam updates, so they cannot detect the defect. On current master, `test_cleanup_matches_legacy_preparation[True-False]` passes even though the gradients are wrong.
- Earlier validation on 4 H100s with DeepEP: the full parity file plus the CPU file gave 78 passed, 0 skipped. With the original replay fix removed, the then-new test failed for both routings, with input-gradient relative L2 error of 0.96 (uniform) and 0.99 (skewed).
- Current AI-review follow-up on 4 NVIDIA H100 80GB HBM3 GPUs, torch 2.10/CUDA 13.0, Triton 3.6.0, transformers 5.12.0 and DeepEP v2: **6 passed, 0 skipped**. This includes uniform/skewed ordinary and nested checkpoint gradient parity, plus retained-graph interleaving rejection on every rank.
- With the preceding replay runtime and the same corrected integration tests, both nested cases fail: input-gradient relative L2 error is **0.956 / 0.973**, versus the unchanged **1e-2** threshold. The missing retained-graph rejection is independently reproduced by the deterministic CPU oracle; its unsafe real-DeepEP negative control stalled and was stopped rather than used as successful validation.
- Final CPU validation under `pytest --forked`: **65 passed** (62 comm/replay cases plus 3 configuration-helper cases). The original AI-review runtime fails the frozen/trainable nested gradient subcases and incorrectly accepts retained-graph interleaving. The current implementation passes the discarded/no-grad and GC-disabled lifetime cases without inspecting private storage.
- End to end, Qwen3-30B-A3B on 8 H100s (EP8, MB4/GA16, S4096):
  - Step losses with non-reentrant plus this change matched reentrant to within 5.3e-4 over 30 steps.
  - Non-reentrant was 0.7% slower than reentrant there. It skips the recomputed combines, but the remaining DeepEP calls spent longer waiting for peer ranks.
  - This PR is a correctness fix and makes no performance claim.

The review follow-up changes replay recording/matching and the associated tests only. Existing end-to-end evidence is retained; no benchmark was restarted. All PR commits carry `Signed-off-by`; the automated sign-off finding cited a SHA outside the actual PR commit list.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Record fresh graph-building dispatches during nested backward**

When a non-reentrant checkpoint around this layer is nested inside a reentrant checkpoint, the inner checkpoint's graph-building forward runs during the outer checkpoint's backward, so `_in_backward()` classifies it as a recompute. The outer forward ran without grad, so there is no handle to replay, but this classification also suppresses recording the fresh handle; when the inner checkpoint later recomputes, it dispatches afresh and restores expert activations in a different layout from the handle retained by the inner forward, silently corrupting gradients. Fresh grad-enabled dispatches need to be recorded even when they occur inside a backward; only an actual handle replay should skip recording.
