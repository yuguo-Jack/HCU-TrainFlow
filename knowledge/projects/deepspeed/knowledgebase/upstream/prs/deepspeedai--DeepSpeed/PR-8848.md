**Part of:** #8672 (Q4 2026 roadmap), "Mixture-of-Expert (MoE) Training Scaling and Kernel Development": "AutoEP Performance Optimization & Parallel Folding (AutoEP + AutoTP)" (PoC @tohtana @pengdurice). Follows #8670.

## Problem

#8670 makes `ds_to_universal` refuse a folded ZeRO-3 checkpoint: "Universal checkpoint conversion of an AutoEP +
AutoTP folded ZeRO-3 checkpoint is not supported yet. Load it with the same topology." So a folded run can only resume
with the same TP size, EP size and number of GPUs.

Three things stood in the way: two in the conversion, one in the load.

1. **File keys.** The AutoEP expert step of the ZeRO-3 conversion keyed checkpoint files by the ZeRO data-parallel rank
   alone (`_zero3_rank_from_file`). ZeRO-3 files are named `zero_pp_rank_{dp}_mp_rank_{tp}`. Under folding the files of
   different TP ranks share a data-parallel rank, so they collided. That is why #8670 refused.
2. **The TP merge's strict check.** `_merge_tp_slice_files` asserts that every pattern in AutoTP's universal info was
   used. AutoTP lists the AutoEP expert weights (`experts.w1/w2/w3`) among `tp_replicated_parameter_patterns`. Those
   weights are merged by the AutoEP step, not by the TP merge, so their patterns are never used and the assertion
   fails.
3. **The layout check on load.** `_load_checkpoint` compares the folding layout recorded in the model-states file with
   the runtime's (`_validate_autoep_folding_checkpoint_metadata`). This rejects any other TP size, EP size or an
   unfolded runtime, although a universal load re-cuts every tensor for the runtime's layout.

## Change

- `deepspeed/checkpoint/ds_to_universal.py`:
  - The AutoEP ZeRO-3 files are keyed by (TP rank, DP rank), with `_zero3_tp_dp_ranks_from_file`, which the dense
    merge already uses. `_zero3_rank_from_file` is no longer used and is removed, along with the folding refusal.
  - `_merge_tp_slice_files` no longer counts a pattern as unused when it only matches parameters excluded from this
    merge. The ZeRO-3 path now passes the AutoEP expert names as excluded; the ZeRO-1/2 path already did.
  - The expert reassembly itself is unchanged. It already uses each file's EP rank and ZeRO partition rank. Under
    folding each expert slice exists on exactly one rank, and the existing duplicate and completeness checks still
    apply.
- `deepspeed/runtime/engine.py` `_load_checkpoint`: skip the folding-layout check when `checkpoint.load_universal` is
  set. Rigid loads keep it.
- Loading tensors needs no change. For each parameter, `load_hp_checkpoint_state` in `stage3.py` cuts the EP slice,
  then the TP shard, then the ZeRO partition in the parameter's own group (dense data-parallel or expert
  data-parallel). That is what folding needs.
- Docs: `docs/code-docs/source/autoep.rst` and `docs/_pages/config-json.md`.
- Tests, in `tests/unit/v1/moe/test_autoep_autotp_sharded_attention.py`:
  - `TestZero3FoldedCheckpoint` no longer expects the conversion to be refused.
  - New `TestZero3FoldedUniversalCheckpoint`. A distributed fixture trains a folded TP 2 x EP 2 run on 4 ranks for one
    AdamW step, saves, converts, and records every parameter and both Adam states at full size, then the losses and
    parameters of the next step. Each target layout loads the universal checkpoint and must restore every recorded
    tensor exactly. Targets with the source's 2 data-parallel groups read the same batches, so they must also repeat
    the next step. Targets: the same layout, EP 4, TP 4, 8 ranks with TP 4, and AutoEP without AutoTP; each in fp32
    and bf16.

ZeRO-1/2 conversion of folded checkpoints is not covered: it stores experts in per-expert files, one per TP rank,
and is still refused in `autoep_universal.py` (`resolve_expert_ckpt_path`).

## Further checks (not part of the PR's tests)

A wider version of the new test: 7 target layouts. Besides the 5 above: 8 ranks with TP 2 x EP 4, and AutoEP EP 4
without AutoTP. Run in fp32 and bf16, with the optimizer-offload PR for folding applied, and in 3 offload
combinations: saved and loaded without offload, saved and loaded with offload, saved without and loaded with offload.
All 42 loads restore every parameter and both Adam states exactly. Every target with the source's 2 data-parallel
groups repeats the next step: losses equal, and parameters within 1e-4 relative, leaving out the attention key bias.
In bf16 only the same layout repeats it.

The key bias is left out of the next-step comparison because its true gradient is zero. Its computed gradient is
rounding noise that another layout adds up in another order, and AdamW turns that noise into steps of about lr
(observed differences 6e-4 to 1.5e-3 relative).

**4. [question] Experts are published as TP-replicated in the AutoTP UC metadata** — [`ds_to_universal.py:608-611`](https://github.com/deepspeedai/DeepSpeed/blob/9362efc52a983830845a2048e1ff562fbbdf4cd5/deepspeed/checkpoint/ds_to_universal.py#L608-L611)

Under folding, `collect_autotp_universal_checkpoint_info` publishes `...experts.w[123]` as TP-replicated with a `replicated_map` over the EP-local shape, but TP peers hold different experts (with TP=EP=2 the groups coincide). Filtering those patterns out of the strict check works for this converter, but the metadata itself stays wrong. Would it be cleaner to skip AutoEP expert params when collecting AutoTP UC info? Anything that later plans from `AFFINE_MAP` in UC info (e.g. the shard-to-shard planner / executor) would otherwise trust a wrong map.

**5. [nit] `k_proj.bias` exclusion** — [`test_autoep_autotp_sharded_attention.py:577`](https://github.com/deepspeedai/DeepSpeed/blob/9362efc52a983830845a2048e1ff562fbbdf4cd5/tests/unit/v1/moe/test_autoep_autotp_sharded_attention.py#L577)

The key bias only has a zero true gradient on its non-rotary half. With `partial_rotary_factor=0.5` the rotary half is rotated by position-dependent RoPE; in fp64 on this tiny GLM-4-MoE I get max |grad| ≈ 1e-4 on the rotary dims (same order as `q_proj.bias`) vs ≈ 4e-11 on the pass-through dims. Could you exclude only `[..., int(head_dim * partial_rotary_factor):]` of each head instead of dropping the whole tensor?

**6. [nit] Fallback partition values** — [`ds_to_universal.py:870-871`](https://github.com/deepspeedai/DeepSpeed/blob/9362efc52a983830845a2048e1ff562fbbdf4cd5/deepspeed/checkpoint/ds_to_universal.py#L870-L871)

If `ds_zero_partition_groups` were missing, this falls back to the dense DP size / rank, which is wrong for expert sub-groups (partitioned over EDP). Every partition-native AutoEP ZeRO-3 checkpoint writes it, so raising here seems safer than guessing.
