# feat(comm): one-shot P2P custom all-reduce for TP=2 inference

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8997) · state: open · merged: False

## Original PR description

## Summary

Adds a latency-optimized one-shot all-reduce for P2P-capable CUDA pairs (TP=2), filling the existing `deepspeed.comm.inference_all_reduce` hook — the same slot the CPU backend fills with shm+AVX. **Split out of #8602**: this is a generic comm-layer optimization with zero dependency on segment-KI; any AutoTP TP=2 workload benefits, including plain `HF generate` whose decode steps all-reduce small hidden-state tensors through the TP-wrapped linears.

### How it works
- `csrc/inference/custom_ar.cu`: one-shot P2P kernel over CUDA IPC buffers (2x4MB, sequence-numbered flags)
- `deepspeed/comm/custom_ar.py`: topology gating — world==2, P2P capable, bounded-spin handshake probe; **symmetric verdict** via `all_reduce(MIN)` so a unidirectional fabric fault disables the fast path on both ranks (prevents the peer-spin hang)
- `op_builder/custom_ar.py` (`DS_BUILD_CUSTOM_AR`): built through the standard op-builder path like every other op (wheel-prebuildable), initialized next to the shm op in `TorchBackend`, mirroring `build_shm_op`
- `layers.py`: `RowParallel` routes no-grad small-message decode through `inference_all_reduce` (falls back to NCCL unchanged); inference mode uses reduce-scatter+all-gather
- Fallbacks are safe and logged: non-CUDA, world≠2, no P2P, oversized (>4MB), or build failure → NCCL

## Not a duplicate

Split from #8602 (segment-KI), which remains the umbrella PR. No other open PR implements a CUDA fast path for the `inference_all_reduce` hook (CPU shm path is `ShareMemCommBuilder`, untouched here).

## Tests

`tests/unit/comm/test_custom_ar.py` — routing contract (4 tests, CPU-runnable):
- not-ready before initialize; initialize() no-ops without a process group
- payload gate is zero when not ready (no message can ever qualify)

Run: `pytest tests/unit/comm/test_custom_ar.py tests/unit/comm/ -q` → 38 passed, 28 skipped on CPU (local, Python 3.11, CPU only).

**On-device validation**: the kernel + handshake path was exercised on 2x GPU (AutoDL, see #8602 commit `4bcc86b82` verification) through the ZeRO-3→arena→TP2 rollout e2e. A dedicated 2-GPU parity test (custom_ar vs NCCL all-reduce) is planned as follow-up; reviewer may request hardware specifics from #8602's logs.

## Compatibility matrix

Validated: CPU (comm unit suite), CUDA TP=2 (via #8602 e2e). Not validated: XPU/HPU/NPU (code routes through `get_accelerator()` and falls back; only `can_device_access_peer` is CUDA-specific, marked `#ignore-cuda`). ZeRO/offload unaffected (inference-path only).

- jinyouzhi · comment · 2026-11-04T11:10:18Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8997#issuecomment-6629125799)

I ran this PR on real hardware and found three issues that stop the fast path from working in a normal DeepSpeed setup, plus a gap in the test.

**Setup:** 8× NVIDIA L20 (PCIe, P2P on all tested pairs), torch 2.14.1+cu130, head `a2fb1038`. I called `dist.inference_all_reduce` on bf16 messages of 8 KB and 512 KB and compared the result with `dist.all_reduce`. Each latency is the average of 200 back-to-back calls followed by a sync. The harness and diff are at the end.

### 1. With DeepSpeed's default process group, the fast path never turns on and every call gets slower
On CUDA, `deepspeed.init_distributed()` creates an NCCL-only group. The verdict tensors in `initialize()` (`deepspeed/comm/custom_collective.py:66`, `op_builder/custom_collective.py:106`) are CPU tensors, so `all_reduce` raises `No backend type associated with device type cpu`. `inference_all_reduce` swallows the error. Because `_state["failed"]` is only set on the `return False` paths, the next call runs `_build()` and the failing collective again.

| world=2, TP2 | inited | `_build()` calls | 8 KB / 512 KB |
|---|---|---|---|
| route disabled (NCCL baseline, same code) | – | – | 52–56 / 48–55 µs |
| PR, NCCL-only group (default) | False | 422 (one per call) | **212 / 173 µs** |
| PR, `cpu:gloo,cuda:nccl` | True | 1 | 31–32 / 38–55 µs |

`RowParallel` now sends every no-grad forward through `inference_all_reduce`. That means the extra cost also hits AutoTP no-grad forwards during training, such as eval or HybridEngine rollout, not just `init_inference`.

### 2. `can_device_access_peer(dev, 1 - dev)` assumes the pair is on devices {0, 1}
- **8 ranks as 4×TP2 on `cpu:gloo,cuda:nccl`:** only {0,1} initializes. On ranks 2–7, `1 - dev` is negative, so the call raises. The error is swallowed and retried on every call, giving 388–456 µs. On the NCCL-only group, no pair initializes, at 194–282 µs.
- **Group {1,2} with rank 0 idle:** rank 1 checks device 0, passes, and enters `all_gather_object`. Rank 2 raises and falls back to NCCL, so the job **hangs** (killed after 240 s).

### 3. `ready()` checks only the world size, not the group
I initialized on {0,1}/{2,3}, then called `inference_all_reduce` on {0,2}/{1,3}. The second call passes `custom_collective_ready(2)` and reduces through the IPC buffers mapped to the old peer. The result is **silently wrong** (max abs error vs `all_reduce` = 5.22), and then the job **hangs**. Any process that uses `inference_all_reduce` on two different 2-rank groups can hit this.

### 4. The parity test never runs the kernel in CI
On CUDA, `DistributedTest` initializes with backend `nccl`. Issue 1 applies, so `ready` is always False and `TestCustomARTwoDeviceParity` only checks the NCCL fallback. It would help to assert `ready` when the pair reports P2P, so a fast path that silently stays off fails the test.

### 5. The PR description is out of date
- Files are now `custom_collective.*`, not `custom_ar.*`.
- The reduce-scatter + all-gather inference-mode path has been removed.
- Initialization is now lazy in `inference_all_reduce`, not in `TorchBackend.__init__`.
- Tests are now in `test_custom_collective.py`, and the 2-GPU parity test is already included rather than planned as a follow-up.

### Suggested fix (tested on the same machine)
- Run the verdict `all_reduce` on a device tensor. This works on both NCCL-only and gloo+nccl groups.
- Set `failed` before the first collective step and clear it only on success, so a swallowed exception does not retry on every call.
- Exchange `(hostname, device)` inside the group and check `can_device_access_peer(dev, peer_dev)`. Agree on the result before `create_buffers`.
- Wrap `connect()` and agree on its result.
- Record the group's ranks at init and require them in `custom_collective_ready(..., group=group)`.

| Case | PR head | With fix |
|---|---|---|
| NCCL-only, w2 | not inited, 212 / 173 µs | inited, 30–50 / 38–46 µs, err 0 |
| NCCL-only, w8 (4×TP2) | none inited, 194–282 µs | all inited, 28–32 / 38–39 µs, err 0 |
| gloo+nccl, w8 (4×TP2) | only {0,1} inited, others 388–456 µs | all inited, 31–40 / 38–39 µs, err 0 |
| gloo+nccl, init {0,1},{2,3} → reduce {0,2},{1,3} | wrong result (err 5.22), then hang | err 0 (second group falls back to NCCL) |
| gloo+nccl, group {1,2}, rank 0 idle | hang | err 0, 34–36 µs |

With the fix, `_build()` runs once per rank in every case. The fix also passes the cross and mixed cases on an NCCL-only group.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Initialize custom AR only after selecting the local device**

In the normal `deepspeed.initialize()` flow, `TorchBackend` is constructed before `DeepSpeedEngine._set_distributed_vars()` calls `set_device(self.local_rank)`. Consequently, both TP ranks can allocate and handshake these CUDA IPC buffers on the default device 0, mark the path ready, and then have rank 1 launch the kernels on device 1 later; the stored pointers belong to mappings created on device 0, which can cause illegal memory accesses instead of the promised NCCL fallback. Move initialization after device binding or explicitly bind/validate the intended local device before allocating.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Avoid unaligned 16-byte loads from contiguous views**

A contiguous CUDA tensor does not guarantee that its `data_ptr()` is 16-byte aligned; for example, a contiguous slice with a one-element storage offset can qualify for this path. Casting such a pointer to `uint4*` makes the copy loop issue alignment-sensitive 16-byte loads, which can fault or copy incorrect data. Gate the vectorized path on pointer alignment or copy an unaligned prefix/scalar payload before using `uint4`.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Check topology before JIT-loading the custom op**

This initialization is invoked for every distributed `TorchBackend`, while `_build()` runs before the backend checks whether the world size is two. Consequently, a default CUDA installation without the prebuilt extension performs an expensive JIT compile even for single-rank jobs, larger data-parallel jobs, and training runs that can never use this TP=2 inference path. Perform the cheap world/topology eligibility checks before loading the extension to avoid regressing startup for unrelated workloads.
