# Fix double-transpose crash loading fused QKV checkpoints (megatron_v2)

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8873) · state: open · merged: False

## Original PR description

Fixes #3038

## Problem

When `GPTNEOXContainer.load_params` loads a checkpoint, it reads the fused
`query_key_value` weight through `maybe_copy(..., qkv=True, megatron_v2=True,
split_qkv=False)` in `deepspeed/module_inject/policy.py`, which runs this:

```python
if qkv and megatron_v2:
    tmp = _transpose(transpose(tmp), heads=heads, mp_replace=mp_replace).contiguous()
    if weight_quantizer.q_int8:
        tmp = transpose(tmp)
dst = mp_replace.copy(dst, weight_quantizer.quantize(tmp if weight_quantizer.q_int8 else \
                                transpose(tmp)), int8=weight_quantizer.q_int8)
```

On the non-int8 (fp16/bf16) path `tmp` is already back in the orientation
`ReplaceWithTensorSlicing.copy()` expects after the `_transpose(transpose(tmp), ...)`
head-reorder, but the last line applies `transpose(tmp)` once more when `q_int8`
is False. The tensor arrives one transpose too many and `copy()` raises a
shape-mismatch `RuntimeError` for every `mp_size`, including 1 (no tensor-parallel
split at all).

This regressed in fd1449c7 ("Port Reza's INT8-quantization fix to container
architecture", #2725): it fixed the int8 orientation and left the non-int8 path
with the extra transpose. `git log` on this block since then shows no deliberate
change to the non-int8 branch.

Impact: crash-on-valid-input

- **Who reaches this**: anyone calling `deepspeed.init_inference(model,
  replace_with_kernel_inject=True, checkpoint=<checkpoints.json>)` on a GPT-NeoX
  model, i.e. the documented meta-tensor checkpoint-loading workflow
  (`replace_module.py:418` -> `load_checkpoint.py:171` -> `GPTNEOXContainer.load_params`).
  The issue's `--use_kernel --use_meta_tensor --checkpoint_path` run is exactly this.
  `GPTNEOXLayerPolicy` is the only policy that reaches this branch: GPT-J loads q/k/v
  through `maybe_copy_qkv`, and BLOOM is not `megatron_v2`.
- **How it is triggered**: loading the checkpoint in fp16 or bf16, i.e. without
  int8 quantization. The first `attn_qkvw` copy of the first layer fails. Without
  `checkpoint=` the weights come from the HF module and this code is not used,
  which is why the issue's plain `from_pretrained` run works.
- **What they observe**: `init_inference()` raises `RuntimeError: The size of
  tensor a (...) must match the size of tensor b (...) at non-singleton dimension 1`
  from `ReplaceWithTensorSlicing.copy()` before the engine exists. The reporter's
  traceback goes through the same chain (`GPTNEOXContainer.load_params` ->
  `maybe_copy` -> `copy`); the exact sizes differ because the surrounding code has
  been refactored since 2023.

## Fix

Move the transpose out of the `if weight_quantizer.q_int8:` guard so it always
runs after the head-reorder. The int8 branch is unchanged: it already applied
that transpose unconditionally on its own path, and tracing both branches shows
the sequence of transforms applied to `tmp` when `q_int8` is True is identical
before and after. One production line.

## Testing

New `tests/unit/module_inject/test_gptneox_qkv_checkpoint_load.py` calls
`maybe_copy` directly with synthetic fp16 tensors shaped like
`DeepSpeedSelfAttention.attn_qkvw`'s allocation. No GPU, no CUDA op, no HF model.
One test loads at `mp_size` 1, 2 and 4 and checks the shape. The other checks the
values at `mp_size=1`: the loaded tensor must equal what
`MegatronContainer.transpose()` produces from the same weight when no checkpoint
is used (`_align_qkv_transposed(W.t())`), so the fix gives the same layout as the
path that already works, not just a tensor of the right size.

```
python -m pytest -q tests/unit/module_inject/test_gptneox_qkv_checkpoint_load.py::test_fused_qkv_megatron_v2_checkpoint_load_does_not_crash tests/unit/module_inject/test_gptneox_qkv_checkpoint_load.py::test_fused_qkv_megatron_v2_checkpoint_load_matches_injection_layout
2 passed
```

Negative control: with only `deepspeed/module_inject/policy.py` reverted to
`master` (`b39bf260`) and the new tests kept, both fail:

```
RuntimeError: The size of tensor a (768) must match the size of tensor b (256) at non-singleton dimension 1
2 failed
```

Issue-scale check on `master` (`0eb3a8bc`) with GPT-NeoX-20B's own shape
(`hidden_size=6144`, `num_attention_heads=64`), calling `maybe_copy` the way
`GPTNEOXContainer.load_params` does: `mp_size=1` raises `The size of tensor a
(18432) must match the size of tensor b (6144)`, `mp_size=4` raises `(4608) ...
(6144)`; with this change both load and `attn_qkvw` has the expected shape
(`(6144, 18432)` and `(6144, 4608)`).

Execution hardware: CPU only (no GPU available to me), 1 host, torch 2.14.0+cpu,
Python 3.12. `pre-commit run --files` (yapf, flake8, codespell, license and
torch-dist checks) clean on both changed files.

Compatibility matrix: validated by execution for the kernel-injection load path
in fp16 with `mp_size` 1/2/4 on CPU (shape) and `mp_size` 1 (values), and `mp_size` 1/4 at 20B scale (the
check above). Not validated by execution: bf16 (same code path, dtype-independent
shape logic), int8 (traced only, see above), and a real GPU `init_inference` run on
GPT-NeoX. ZeRO stage, offload and training parallelism do not apply, this
is inference-only weight loading. Sibling paths checked and unaffected:
`maybe_copy_qkv` (separate q/k/v, no `megatron_v2` reorder), the `split_qkv=True`
branch, and the 1-D bias branch of `maybe_copy`.

Not a duplicate: `gh pr list --repo deepspeedai/DeepSpeed --state open --search "3038 in:body"`
returns nothing, nor does a search for `maybe_copy` / `megatron_v2` /
`module_inject/policy.py` in open PR bodies. The issue's comments mention #3103
(meta-tensor loading), which is a separate defect this change does not touch.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Preserve local Q/K/V layout for tensor-parallel loads**

When loading a non-int8 GPT-NeoX checkpoint with `mp_size > 1`, this only makes the tensor's shape acceptable: `_transpose` has already divided `heads` by `mp_size`, after which `ReplaceWithTensorSlicing.copy()` takes one contiguous column range. For head-interleaved NeoX weights that range is not `[local Q, local K, local V]`; it differs from the working non-checkpoint path (`MegatronContainer.transpose()` plus `attention_qkv_mp()`'s `strided_copy`), so each rank receives mixed head/QKV columns and inference silently uses wrong weights. The MP=2/4 test checks only shape, so compare values against that established path or reorder after partitioning.
