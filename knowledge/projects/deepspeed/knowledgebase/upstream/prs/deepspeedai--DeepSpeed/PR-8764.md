# Round to nearest in NPUQuantizer, matching the CUDA quantizer

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8764) · state: open · merged: False

## Original PR description

On Ascend NPUs, ZeRO++ quantized weights and gradients carry twice the quantization error of CUDA, biased toward zero, and int4 qgZ gradients come back about a third too small.

`NPUQuantizer._quantize_groups` truncates `x * scale`. The CUDA kernel rounds half to even (`__float2int_rn`, before the `(int8_t)` cast), and `test_quantize.py` checks it against `torch.round`.

Fix: `trunc_()` to `round_()`, plus the docstring. The new CPU test, at the path the docstring already cites, checks int8 `quantize` and int4 `swizzle_quant` against that reference. It fails on master and passes here.

Before to after, on CPU:
- int8: L1 error 1.99x to 1.00x the reference, mean error -0.50 to 0.00 steps
- int4 qgZ sum (2 nodes x 2 devices) as a fraction of the exact sum: 0.67 to 1.00
- upstream `test_float_quantize` (int8 symmetric) on `NPUQuantizer`: 30 of 60 fail, then all pass

Verified on Ascend 910B4 by @VenusTZZ: qgZ int4 mean reconstruction error 0.1198 to 0.0506.

Thanks for the fix — this is correct. The truncation was my misreading in #8627: the CUDA kernel goes through `conversion::to<int32_t>` (`__float2int_rn`, round half to even), not a C-style cast, so this now matches both the kernel and the `torch.round` reference in `test_quantize.py`.

Verified on Ascend 910B4 (CANN 8.5.1, torch_npu 2.10.0.post7):

  | Check | trunc (before) | round (this PR) |
  | --- | --- | --- |
  | qgZ int4 reconstruction, mean err (on device) | 0.1198 | 0.0506 |
  | qgZ int4 reconstruction, max err (on device) | 0.3511 | 0.2349 |
  | 2-node × 2-device qgZ sum / exact sum (CPU sim) | 0.845 | 0.995 |
  | This test (int4 + int8) | — | 2/2 pass |
  | Per-group numpy-oracle round-trip suite (on device) | — | all pass |

One small suggestion on the test: `test_quantize.py` already covers this contract across both hardware backends — `QuantizerBuilder().load()` resolves to `NPUQuantizer` on NPU (the path your 60/60 run exercised) and to the CUDA kernel on CUDA, both validated against the same `torch.round` reference.

It might be cleaner to reuse it directly instead of adding a separate NPU-specific file, so the reference logic stays consolidated in one place. The int4 `swizzle_quant` coverage is great new coverage and worth keeping — and since it’s pure torch as well, it can fit into the existing test file without needing an NPU-specific variant.
