# Restore the data sampler's own RNG when resuming from a checkpoint

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8788) · state: open · merged: False

## Original PR description

Fixes #8787

## The bug

`DeepSpeedDataSampler` makes all of its random choices with `self.np_rng`, a `np.random.default_rng(seed)` created in `__init__`. Its checkpoint state didn't include that generator, though. `state_dict()` saved `np.random.get_state()`, numpy's global RNG, and `load_state_dict()` restored that one.

After a resume, `self.np_rng` started over from the seed. Cluster sampling, the per-batch shuffle and the cluster reshuffle all repeated the choices from the beginning of training, so the batches stopped matching an uninterrupted run. On top of that, loading rolled numpy's global RNG back to its state at save time.

## The fix

`state_dict()` now saves `self.np_rng.bit_generator.state`, and `load_state_dict()` restores it.

Checkpoints written before this change only have the global state, which is a tuple rather than a dict. For those, `load_state_dict()` does what it did before: it restores the global RNG and logs a warning that sampling after the resume won't match an uninterrupted run. There's nothing in those checkpoints to restore the sampler's generator from, so that's the best it can do. Old checkpoints still load without errors.

## Testing

I added three tests to `tests/unit/runtime/test_data_efficiency.py`.

- `TestCurriculumCheckpointResume` is the end-to-end one. It trains a `SimpleModel` for 16 steps with curriculum learning on. Then it trains 8 steps, calls `save_checkpoint()`, calls `load_checkpoint()` on a fresh engine, and trains 8 more. Every step has to train on the same batch, and the losses have to match exactly. Since 16 steps of 2 from 20 samples crosses the epoch boundary after the resume, the cluster reshuffle is covered too.
- `test_data_sampler_resumes_where_it_left_off` does the same thing on the sampler alone, in a single process with `barrier` and `broadcast` stubbed. It also reseeds numpy's global RNG between saving and loading, to show the result no longer depends on it.
- `test_data_sampler_loads_checkpoints_from_before_the_rng_fix` loads a state in the old tuple format and checks that it still restores the global RNG.

I ran these on an Apple M4 (macOS 26.6, torch 2.14.0, world size 1):

| | with this PR | on master |
| --- | --- | --- |
| `TestCurriculumCheckpointResume`, `mps` | passes | fails: step 9 trained on a different batch |
| `TestCurriculumCheckpointResume`, `cpu` | passes | fails: step 9 trained on a different batch |
| `test_data_sampler_resumes_where_it_left_off` | passes | fails: 14 of 15 batches after the resume differ |

The rest of the file passes, except the two multi-process `TestDataEfficiency` cases, which need 2 GPUs and skip on this machine. I don't have CUDA hardware, so nothing has run on a GPU yet. The new end-to-end test only needs one device in fp32, so CI should be able to run it as is. `pre-commit` is clean.
