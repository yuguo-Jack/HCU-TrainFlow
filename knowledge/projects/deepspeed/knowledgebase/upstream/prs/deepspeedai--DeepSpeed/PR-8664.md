# Fused RMSNorm: multi-row programs and a one-pass backward for narrow norms

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8664) · state: open · merged: False

## Original PR description

## Summary

Builds on the opt-in fused RMSNorm implementation merged in deepspeedai/DeepSpeed#8645. This branch has been rebased onto current upstream `master`: the PR diff contains only narrow-row scheduling/backward changes, boundary tests and documentation, not the former parent commits.

The merged parent's per-instance opt-in, checkpoint opt-out, copy/DataParallel behavior, eager fallback and collection-safe CUDA test framework are preserved.

The parent fused RMSNorm kernels run one row per program. For the 128-wide query and key norms of models like Qwen3, that leaves most of each program idle. The backward also reads `hidden` and the incoming gradient twice, once in the dx kernel and once in the weight-gradient partial kernel.

For norms at most 128 wide, this change:

- runs up to 4096 elements per program in the forward (32 rows at width 128), with smaller power-of-two row tiles for short inputs;
- uses one backward kernel that reads each row once and writes both the input gradient and the per-block weight-gradient partials, which are then summed as before.

Wider norms, including the hidden-size norms, keep the existing row kernels unchanged.

The short-input cap addresses the Codex review in this existing PR, rather than opening a duplicate optimization PR. Both passes use `min(max_rows_per_tile, next_power_of_2(n_rows))`; a single width-128 or width-one row uses `BLOCK_M=1`, not 32 or 256 padded rows. Filled tiles keep their original scheduling. AI assistance was used for this follow-up, with author review before submission.

## Numerics

The expression and its rounding points are the same as the parent row kernels'. Multi-row scheduling can change the FP32 reduction order for variance, `grad_rstd`, and weight-gradient partials. The unchanged ULP limits against eager still apply; **bitwise equality with eager is not claimed**. Identical fused runs give repeatable input and weight gradients at widths 128 and 2048, which is a separate determinism property.

At width one and `eps > 0`, the pre-gamma input derivative is `eps / (x**2 + eps)**(3/2)`, not strictly zero. A tiny epsilon can make that value hard to distinguish from low-precision cancellation. The dedicated width-one test uses `eps=0.25` and an FP64 reference so the nonzero gradient is measurable, without relaxing the existing ULP thresholds.

## Tests

The existing `test_fused_rms_norm.py` forward/backward test gains narrow shapes:

- many rows with a partial last block: `(4099, 128)`;
- the head-major query-norm shape: `(2, 300, 32, 128)`;
- width 96 with masked columns, and widths 64 and 16 at the scheduling boundary;
- widths 7 and 15 with masked columns and partial last blocks, under the same forward/dx/dgamma ULP thresholds.

A width-one test checks the nonzero input derivative against FP64 and forward/gradient parity with eager. The repeated-run test checks fused input and weight gradients at widths 128 and 2048. Existing tests cover head-major non-contiguous inputs, transposed incoming gradients, and non-contiguous weights.

The first width outside the narrow cutoff, 129, is additionally checked in BF16/FP16 under the unchanged wide-path accuracy contract. The shape, FP64 width-one and determinism cases now run inside the merged parent's `DistributedTest` CUDA class, with Triton imports and availability checks deferred to execution.

Earlier validation passed the six BF16/FP16 sub-16 and width-one cases on one NVIDIA H100 80GB HBM3 (torch 2.10/CUDA 13.0, Triton 3.6).

This includes the narrow numerical/masked-width/FP64/determinism tests and the merged parent's guards, copying, checkpoint loading/reinstallation and two-GPU DataParallel training.

The wide kernel implementations and parent dispatch/checkpoint logic are also unchanged by AST comparison.

## Performance

**Incremental local effect of this PR:** measured on one H100, Qwen3-30B-A3B attention layer under reentrant checkpointing (forward, recompute and backward), with fused RoPE already enabled in both arms.

| Sequence | Q/K norm time | Attention-layer time |
|---|---|---|
| 8192 | 0.73 → 0.33 ms | 7.80 → 7.52 ms |
| 16384 | 1.40 → 0.45 ms | 23.66 → 22.89 ms |

**Combined E2E effect:** Qwen3-30B-A3B training with AutoEP, 16x H100, expert parallel 16, 48 layers, one sequence per GPU, activation checkpointing. The "after" arm adds **both this narrow-row RMSNorm change and fused RoPE (deepspeedai/DeepSpeed#8663)** on an otherwise identical stack, in the same allocation. The total change cannot be attributed to this PR alone:

| Sequence | Before | After | Change |
|---|---|---|---|
| 8192 | 1714 ms | 1654 ms | −3.5% |
| 16384 | 3632 ms | 3511 ms | −3.3% |

- The 8192 result separates cleanly: both "after" runs are below both "before" runs.
- The 16384 run ranges overlap, so its −3.3% result is **indicative**, not a confirmed independent speedup.
- Peak allocated memory did not increase at either length (50.434 GB at 8192; 57.161 GB at 16384). Peak reserved memory decreased slightly.
- Final-step losses differed by at most 0.0023 in these paired runs (within-arm run-to-run spread: 0.0016–0.0068). This is a **final-step observation, not a bound across all steps**.

The narrow kernel arithmetic and filled-tile scheduling used by these measured workloads are unchanged; only underfilled short inputs use the smaller row tile. Rebase/conflict resolution preserves the merged parent rather than reinstating the former instance-bound forward or serialized opt-in behavior. The performance numbers above are reused historical measurements, not a retiming of the rebased stack or the short-row follow-up.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Cap narrow tiles for short inputs**

When the flattened input has fewer rows than this fixed `block_m` (for example a short decoding batch with fewer than 32 width-128 Q/K rows), the narrow kernels still instantiate all 4096 tile elements. A one-row width-128 call therefore does 32 padded rows of lane work, and a one-row width-1 call does 256 padded rows, whereas the previous row kernel used one padded row and the same single program; the extra arithmetic and register state can turn this optimization into a substantial regression for supported short inputs. Keep the row kernel for underfilled tiles or derive a smaller power-of-two `BLOCK_M` from `n_rows`.
