# Fix memory leak and NULL-deref in shm_initialize

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8565) · state: closed · merged: True

## Original PR description

## Summary
Two related bugs in `shm_initialize()` (`csrc/cpu/comm/shm.cpp`), both found via static analysis and manually verified against the real code before fixing.

### 1. Memory leak (CWE-401)
```c
workspace_buf = (struct allreduce_workspace*)malloc(sizeof(struct allreduce_workspace));
snprintf(shm_name, NAME_BUF_SIZE, "%s_%d", shm_name_prefix, rank);
shared_create(&allreduce_buffer, shm_name, workspace_buf, sizeof(struct allreduce_workspace));
workspace_buf = (struct allreduce_workspace*)allreduce_buffer.bytes;  // original pointer overwritten here
```
`shared_create()` only reads `workspace_buf`'s contents (via a `write()` call that seeds the shared-memory segment) — it never stores or frees the pointer it's given. Once `workspace_buf` is reassigned to `allreduce_buffer.bytes`, the original `malloc()`'d block is unreachable for the rest of the process. Verified by reading `shared_create()`'s implementation directly and confirming there is no `free()` call anywhere in `shm.cpp`.

**Fix:** free the original buffer right after `shared_create()` returns (its contents have already been copied out at that point), before `workspace_buf` is repointed at the shared mapping.

### 2. NULL pointer dereference on unchecked calloc (CWE-476)
```c
workspace = (struct allreduce_workspace**)calloc(size, sizeof(struct allreduce_workspace*));
symmetric_buffer[0] = (char**)calloc(size, sizeof(char*));
symmetric_buffer[1] = (char**)calloc(size, sizeof(char*));
distributed_buffer[0] = (char**)calloc(size, sizeof(char*));
distributed_buffer[1] = (char**)calloc(size, sizeof(char*));
// (no NULL check anywhere)
```
All five are dereferenced unconditionally in the loop immediately after (`workspace[i] = ...`, `workspace[i]->buffer`, `symmetric_buffer[*][i] = ...`, etc.). `calloc()` can return `NULL` under memory pressure; any of these failing would then be a NULL-pointer write. Verified there is no existing check on any of these five variables anywhere in the file.

**Fix:** a single guard checking all five allocations before the loop uses any of them, matching this file's existing fail-and-return style (`shared_create()`'s own printf-then-return error handling).

I ran this against `89ca1a04` in a clean `gcc:13` container, compiling `SharedData`, `shared_open()` and `shared_create()` from `shm.cpp:42-85` verbatim plus the real `allreduce_workspace` struct.

The guard covers the five `calloc()`s at `:375-379`, which ask for 320 bytes in total at world size 8. The `malloc()` on this line asks for one `allreduce_workspace`, measured at 69206024 bytes, and it is still unchecked. That is the allocation here that fails under memory pressure.

It escapes the guard because a NULL from `:362` never reaches a NULL dereference. It goes into `shared_create()`:

```
write(d, NULL, 69206024) -> -1 errno=14 (Bad address)
nbytes = write(...) assigned -> 18446744073709551615 ; truthy in `if (nbytes = write(...))`
shared_open's shm_open -> d=4, so it takes the SUCCESS branch
mmap(NULL, 18446744073709551615) -> 0xffffffffffffffff (MAP_FAILED) errno=12
```

The assignment inside the `if` at `:73` turns -1 into `(size_t)-1`, which is truthy, so `shared_open()` runs with that length. Its `shm_open()` succeeds, since the segment was just created, so `:57` assigns `data->bytes = bytes` unconditionally and stores `MAP_FAILED`. `descriptor` is a live fd, so the `descriptor == -1` sentinel never fires. Driving both arms through the real functions, only `workspace_buf` forced to NULL, `:371` writes through `(void*)-1` and the process takes SIGSEGV; the malloc-succeeds arm exits 0.

Pre-existing, and your diff does not introduce it, but it is the same CWE-476 in this function, 13 lines above the guard. One edit: check `workspace_buf` straight after this line and bail the way the new guard does.

Not checked: I did not build the extension or call `shm_initialize()` itself, and the second arm forces the NULL rather than exhausting memory.
