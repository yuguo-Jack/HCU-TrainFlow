# Set TORCHINDUCTOR_COMPILE_THREADS=1 in modal CI sandbox to stop 300s test timeouts

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8914) · state: closed · merged: True

## Original PR description

## Description

Since #8902 (Python 3.10 -> 3.12 sandbox bump) landed on 10-25, `modal-torch-latest` merge-queue runs hit repeated `DS_CI_FAILURE_CLASS=timeout: no test progress for 300 seconds` (9 occurrences 10-25..10-26 across pr-8478/8647/8642/8800/8882 and the nightly master run). In every case the watchdog fires while workers are inside `tests/unit/v1/compile/test_compile_zero.py` at 95%+ progress.

Root cause: torch 2.10.0's Inductor `SubprocPool.shutdown()` (`torch/_inductor/compile_worker/subproc_pool.py`) waits up to `process.wait(300)` for its nested compile-worker pool when tasks are still in flight at process exit — [pytorch/pytorch#162199](https://github.com/pytorch/pytorch/issues/162199), fixed by [pytorch/pytorch#184038](https://github.com/pytorch/pytorch/pull/184038), first released in torch 2.13. Each `test_compile_zero` case spawns fresh rank processes (`DistributedTest, world_size=2, non_daemonic_procs=True`), so nearly every case pays a fixed ~300s at exit (~310s total per case vs ~20-90s before the sandbox bump). When these cases are the last ones running, the whole-suite 300s no-output watchdog kills pytest.

This PR sets `TORCHINDUCTOR_COMPILE_THREADS=1` in the Modal sandbox env: serial compile never creates the worker pool, so the shutdown race cannot occur. The variable should be removed when `MODAL_TORCH_PRESET` moves to >= 2.13.

### Why this does not duplicate an existing PR or issue
Checked open PRs for `TORCHINDUCTOR_COMPILE_THREADS`, `inductor timeout`, and `300 seconds timeout` in PR bodies — no existing PR addresses this.

### Test commands run and results (AI-assisted investigation; local reproduction)

Local CPU reproduction (no GPU available locally), torch installed from the cpu wheel index:

| Env | Experiment | Result |
|---|---|---|
| py3.12.15 + torch 2.10.0+cpu | `AsyncCompile.process_pool()` + in-flight task, then `shutdown_compile_workers()` | `TimeoutExpired` after exactly **300.0s** (wall 305.8–309.0s) — matches CI's ~310s/case signature |
| py3.10.22 + torch 2.10.0+cpu | same | identical 300.0s hang — rules out Python version as the switch |
| py3.12.15 + torch 2.10.0+cpu, `TORCHINDUCTOR_COMPILE_THREADS=1` | `process_pool()` unreachable (assert threads>1); cold `torch.compile` shutdown | shutdown **0.00s**; compile 16.7–19.7s vs 17.2–24.5s with default threads (no regression) |
| py3.12.15 + torch 2.13.0+cpu | same race as row 1 | shutdown returned in **2.5s** (confirms upstream fix; long-term option) |

Hardware: local CPU-only workstation (8 cores). CI-side confirmation is implicit in the modal-torch-latest run for this PR: expected effect is `test_compile_zero` cases dropping from ~310s to ~20s in `--durations` output and no further `timeout: no test progress for 300 seconds`.
