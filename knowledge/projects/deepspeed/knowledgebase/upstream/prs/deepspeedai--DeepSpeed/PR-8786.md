# perf(rollout): select generation and prefill buckets with a tunable cost model

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8786) · state: open · merged: False

## Original PR description

## Summary

Closes #8785. Related tracking: [#8197](https://github.com/deepspeedai/DeepSpeed/issues/8197), [#8462](https://github.com/deepspeedai/DeepSpeed/issues/8462).

**Performance follow-up to [#8497](https://github.com/deepspeedai/DeepSpeed/pull/8497).** Aligned CB avoids padding on long-tail prompts, but one prefill Forward per request is expensive for short prompts. A padding-ratio threshold cannot distinguish **128/4** from **512/16**, despite identical ratios and different fastest baselines.

This change adds **one opt-in automatic policy** that compares ordinary no-CB generation with aligned CB using **DP-selected prefill buckets**. For 1×512 + 31×16, the selected buckets are `[1,512]` and `[31,16]`, reducing prefill Forwards from 32 to 2.

**Auto is disabled by default.** Existing manual modes and positional configuration arguments are preserved.

```python
cfg = HybridEngineRolloutConfig(adaptive_prefill=True)
rollout = HybridEngineRollout(engine, tokenizer, cfg)
sampling = SamplingConfig(max_new_tokens=16, temperature=0, continuous_batch_size=32)
```

## Selection and configuration

A length-sorted **O(n²)-time / O(n)-space DP** minimizes the additive estimated cost of contiguous buckets. It explores one batch, singleton batches and intermediate partitions without running the GPU for candidate evaluation. Each bucket uses ordinary left padding and a 2D attention mask; **no varlen kernel is needed**. Model geometry is read once per plan.

```text
C(B,L) = fixed + token × B×L + attention × estimated_attention_GFLOPs
         + kv × estimated_KV_MiB
attention_GFLOPs = 4 × B × L² × layers × query_heads × head_dim / 1e9
KV_MiB = 2 × B × L × layers × KV_heads × head_dim × element_bytes / 2^20
```

| Parameter | Default | Meaning |
| --- | ---: | --- |
| `prefill_fixed_cost_ms` | 25.0 | Fixed milliseconds per prefill Forward |
| `prefill_token_cost_ms` | 0.1 | Milliseconds per padded token position; projection/MLP term |
| `prefill_attention_cost_ms` | 0.01 | Milliseconds per estimated attention GFLOP |
| `prefill_kv_cost_ms` | 0.04 | Milliseconds per MiB of KV copied into the CB cache |
| `continuous_decode_cost_ms` | 10.0 | Additional CB milliseconds per remaining Decode step |
| `prefill_max_tokens` | 65536 | Maximum padded token positions per prefill Forward; `None` removes this limit |

All cost coefficients must be finite and non-negative. **These are starting estimates, not universal GPU constants**; calibrate them for the model, device, precision and attention backend. Head dimension, query/KV heads, layers and parameter element size are read automatically. The DP is optimal for the configured estimates, not guaranteed globally optimal measured latency.

Ordinary generation is eligible when every row fits `continuous_batch_size`, the physical input fits the prefill/context limits, and neither explicit static capacity nor trimming is requested. Its estimated cost omits CB cache-copy traffic; CB adds `continuous_decode_cost_ms × (max_new_tokens - 1)`. The first output token comes from Prefill.

For CB, **every admission/refill replans the newly admitted requests**. Effective KV spans are copied into the existing right-aligned cache; surviving rows retain their layout. The policy does not change caller configuration or active-row bounds. Disabling Auto restores manual selection. Model/OOM errors propagate without trying another path.

## Correctness

- Apply repetition penalty from the first token using **original padded history**, even when bucket model inputs are trimmed.
- Preserve generated PAD-valued tokens through the first EOS, excluding structural padding after termination.
- Include route planning and result normalization in end-to-end profiling; count **productive output tokens** and retain active/configured capacity fields.
- Resolve HF's effective generation configuration before rejecting unsupported processors/output modes, including legacy model-config refresh; preserve explicit generation-config overrides. Auto requires single-process greedy rollout, one sample per prompt and cache-class support; existing CUDA Graph/shared-prefill restrictions remain.

## Experiments

Related work: [TurboTransformers, §5 (PPoPP 2021)](https://arxiv.org/html/2010.05680) already uses length sorting, profiled batch costs and an O(n²) DP to partition variable-length inference requests. [DynaPipe, §4](https://arxiv.org/html/2311.10418) applies cost-based DP partitioning to training micro-batches. This PR applies that established scheduling approach to HybridEngine rollout, with ordinary-generation comparison, refill planning and existing aligned-cache semantics; it makes no claim of a new DP algorithm.

**Single GPU; Qwen/Qwen2.5-3B-Instruct; FP32 / SDPA; PyTorch 2.9.1+cu128; Transformers 4.57.1.** Each candidate receives **one warmup and five interleaved timed runs**, 32 requests and 16 output tokens per request. CB capacity is 32; trimming is disabled, cache capacity unset, TF32 disabled. The default cost coefficients above are unchanged across workloads.

| Workload | Effective prompt lengths | Reason |
| --- | --- | --- |
| Short, similar | 20..13 repeated four times | Normal workload shape from #8497 |
| Long tail | 1×512 + 31×16 | Long-tail workload from #8497 |
| Short tail | 1×20 + 31×1 | Counterexample to ratio-only routing |
| Moderate tail | 1×128 + 31×4 | Same padding ratio as 512/16, different best legacy path |
| Spread | 16, 32, …, 512 | General distribution with intermediate buckets |

Inputs repeat non-special token ID 14990. #8497 did not publish complete short-prompt sequences, so that case reconstructs its documented shape. Every timed response matches independent single-request eager generation; each workload produces **512 effective output tokens**.

GPU-synchronized wall-clock timing includes the full `generate()` call, including Auto planning and normalization. Model loading and oracle work are outside timing; profiling is disabled during timed runs. All reported E2E values are **arithmetic means of five runs**.

**All five workloads meet the 5% acceptance tolerance.** Auto chooses ordinary generation for both short cases; their small timing differences are not claimed as a kernel speedup. Relative to the fastest legacy baseline, mean latency falls by **50.06%** for 1×512 + 31×16, **29.27%** for 1×128 + 31×4, **15.10%** for 16, 32, …, 512. These improvements come from fewer prefill Forwards and reduced padded work.

## Validation and limits

A separate microbenchmark measures **planner overhead**, without model Prefill: for 128/256 requests of 65,536 tokens, CPU DP takes **0.48/1.82 ms** on average with the default per-bucket token limit. It still checks all 8,256/32,896 candidate segments; over-limit segments skip cost evaluation. For 32 requests, DP takes 0.089 ms at length512 and 0.040 ms at length65,536 (0.078 ms with no token limit). GPU mask validation/length extraction for 32×65,536 takes 0.83 ms separately. Measurements use ten repeated timing samples after warmup. **These are not 64k model Prefill timings or the complete Auto-path overhead.**

**The original validation passed 105 related rollout/cache tests**, including independent exhaustive partition comparisons for DP, device-backed tiny-Qwen tests for grouped prefill and refill, both cache APIs, effective generation-config/legacy refresh, repetition history, EOS/PAD masks, capacity bounds and external-wall-time checks for profiling. Existing tests cover retirement, compaction and trimming. Independent mixed-bucket checks also exercised live-survivor refill and trimming on/off against padded per-request HF generation.

One pre-existing native shared-prefill extension test is excluded because the host has no CUDA compiler; **all added tests ran**. Changed-file pre-commit and `git diff --check` pass. Repeated local review ended with **no actionable findings**.

```sh
python -m pytest -q \
  tests/unit/runtime/rollout/test_hybrid_engine_rollout.py \
  tests/unit/runtime/rollout/test_continuous_batching.py \
  tests/unit/runtime/rollout/test_rollout_interface.py \
  tests/unit/utils/test_static_cache.py \
  -k 'not native_repeat_kv_cache_fp16_reverse_copy'
```

The prefill token limit does **not** bound allocated decode KV memory. A single prompt over that limit raises an explicit error; there is no chunked prefill. **64k prompts require a model context limit covering prompt plus output budget, sufficient KV capacity and temporary memory.** The measured checkpoint is configured for 32k. Planner/position-limit boundaries are tested; real 64k inference performance is not claimed.

Performance evidence uses unsharded HF models behind `HybridEngineRollout`; the additional calibrated and real-question checks are listed below. Other model/device configurations, FP16, native kernel injection, ZeRO/TP training integration and production arrival/EOS distributions remain unmeasured. Controlled performance runs do not exercise staggered EOS or trimming; those have correctness coverage.

No new dependency, kernel, online learner or trimming redesign. Related foundation: [#8368](https://github.com/deepspeedai/DeepSpeed/pull/8368); profiling: [#8494](https://github.com/deepspeedai/DeepSpeed/pull/8494).

Thanks @delock. Prefill's share of rollout E2E depends on the checkpoint and task, including the prompt and response distributions. There is no single task-independent “typical” RL length.

**Motivation:** prompt lengths vary within a batch. Too few buckets waste padded computation; too many repeatedly pay per-forward/kernel-launch overhead. Cost-based DP balances these costs. The same calibrated policy adapts across successive batches, compares eligible no-CB with CB, and replans new admissions within CB. Coefficients are adjustable for the model, GPU, precision, and backend.

| Output tokens/request | No-CB Prefill / E2E | Fastest manual baseline | Auto mean | Auto choice |
| --- | ---: | ---: | ---: | --- |
| 128 | 29.2% | Aligned CB: 6.450 s | **5.666 s** | Bucketed CB |
| 512 | 8.25% | No-CB: 23.270 s | **23.067 s** | No-CB |

Here E2E covers the complete generation call, excluding tokenization, loading, reward computation, and training updates.

Thanks @nathon-lee for the [independent smoke test](https://github.com/deepspeedai/DeepSpeed/pull/8786#issuecomment-6095074656). I agree that **the default coefficients are starting estimates, not portable deployment settings**. Users enabling Auto should calibrate for their **model, GPU, precision and attention backend**, and for the prompt-length/batch-size range they actually use. Auto remains disabled by default.

**Recommended calibration:** choose a small set of feasible (batch size, prompt length) pairs covering the deployment's short, typical and long prompts, together with small and typical batches. For example, a workload spanning 128–8192 input tokens should include representative points around 128, 512, 2048 and 8192, subject to memory and model context limits. Fit once, save the coefficients, and validate on separate mixed-length batches with representative generation lengths. Compare Auto against all available manual paths and report the worst regression before enabling it.

**Why exact DP is practical here:** for per-group batches around 128–256 requests, there are only 8,256–32,896 candidate segments. The O(n²) DP can therefore compute the **exact optimum for the calibrated cost model over length-sorted contiguous partitions**, rather than requiring heuristic search. Here n is the number of requests, not the number of tokens. A small n makes exact solving practical; prediction of measured GPU latency still depends on calibration.

**Calibration is deployment setup work:** run the supplied script during deployment preparation or warmup, save the coefficients in `costs.json`, and have the application load them once when constructing `HybridEngineRolloutConfig`. Calibration and fitting do not run inside generation requests. Runtime reuses the saved coefficients and performs only batch-length extraction and route planning. The same configuration can be reused across tasks whose lengths and batch sizes are covered by calibration; changing tasks alone does not require recalibration.

The current script's built-in calibration grid reaches only **768 input tokens**. Those measurements do **not** establish long-context accuracy; longer deployments need an expanded grid. At present this means changing the `shapes` list in `calibrate()`; there is no automatic workload-range discovery.

There were also two distinct causes of the reported regressions:
- **Wrong route selection:** fixed estimates transferred poorly to the tiny model. Configuration-specific calibration keeps that model on ordinary generation in the measured sweep.
- **Unnecessary routing overhead:** per-request mask validation added 128 device scalar reads, and DP ran even when ordinary batching could be selected directly. [Commit 359b3d5](https://github.com/deepspeedai/DeepSpeed/commit/359b3d5002f8af11e1565ebf59c67b93b1af77cd) batches validation/length extraction, skips DP using a cost lower bound or the exact uniform-length estimate, delays per-row request construction, and reuses generation configuration and result normalization. The 128-short-request case now has the same seven scalar reads as ordinary generation and no DP call.

The separate calibrated sweep reports **Auto E2E / fastest manual baseline E2E** (ordinary, equal-width CB or aligned CB):
