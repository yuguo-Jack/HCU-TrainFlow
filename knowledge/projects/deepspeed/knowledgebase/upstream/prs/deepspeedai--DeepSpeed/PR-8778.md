# Add AWS capacity fallback for torch-latest

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8778) · state: closed · merged: True

## Original PR description

`torch-latest` check on Modal often fails due to the lack of GPU capacity. 
So this PR adds an AWS capacity fallback for the `torch-latest` check on Modal.

The workflow now tries Modal first and falls back to AWS capacity if the two-GPU Sandbox cannot be started within the bounded startup window.
The fallback tries G7.12 Spot capacity in a fixed three-region order.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Split the prepare script before calling SendCommand**

With the default `MODAL_TRANSFORMERS_SOURCE=git`, `build_aws_scripts()` makes this single `commands` value roughly 4.5–5 KB (even a minimal run identity is over 4,096 characters). The [SendCommand API](https://docs.aws.amazon.com/systems-manager/latest/APIReference/API_SendCommand.html#systemsmanager-SendCommand-request-Parameters) specifies “Maximum length of 4096” for each parameter value, so AWS rejects the prepare submission with `ValidationException` and no fallback test can run after Modal times out. Split or upload the script, and make `FakeAwsCli` enforce the provider bound.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Emit the SSM output tail used by nightly triage**

On a scheduled full-suite AWS fallback, verbose pytest output will exceed SSM's inline response limit before the final failure summary, but this function prints only the inline fields after completion. The [GetCommandInvocation API](https://docs.aws.amazon.com/systems-manager/latest/APIReference/API_GetCommandInvocation.html#systemsmanager-GetCommandInvocation-response-StandardOutputContent) defines these as the first 24,000 stdout characters (and first 8,000 stderr characters), while `.github/workflows/nightly-triage.yml:186-191` searches the GitHub log for the final `FAILED unit/v1/...` lines; those lines will be absent, so the report job fails and maintainers get no failure details. Surface a sanitized tail from the S3 output and model the documented truncation in the fake.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Classify the AWS execution deadline as a timeout**

When the test SSM invocation remains `Pending`/`InProgress` for more than `AWS_TEST_TIMEOUT_SECONDS` while still producing output, the no-progress watchdog never returns 124; `wait_for_ssm_command()` instead raises its controller-bound error, which lands here and emits `DS_CI_FAILURE_CLASS=test`. Nightly triage then treats a 50-minute execution timeout as a real regression and tries to extract `FAILED` lines even though pytest produced no result, so the test-phase deadline should emit the timeout sentinel and return `EXIT_TIMEOUT`.
