# AutoEP: opt-in routing weights inside the expert activation

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8748) · state: open · merged: False

## Original PR description

Stacked on deepspeedai/DeepSpeed#8739 (backward weight-gradient overlap), which is reviewed first. This child keeps activation weighting as a separate opt-in and must not land before the parent. It remains Draft until the parent merges, as requested by the submitting human. Child-only diff: https://github.com/yh0903/DeepSpeed/compare/b016772c3...ac87d34ba

The DeepEP route applies each received row's routing weight to the expert output: one more pass over `[rows, hidden]` in forward, and in backward a pass that also reduces each row's weight gradient. The down projection is linear and bias-free, so scaling its input inside the activation (`h = act(gate, up) * weight`) is the same mathematical function. Evaluation order and intermediate rounding change, including for FP32; BF16/FP16 activation values are rounded once after the FP32 weighted product, rather than after post-expert weighting. No bitwise-equivalence claim is made. NeMo AutoModel applies its routing probabilities at this mathematical boundary.

This adds `expert_parallel.row_weighting_impl="activation"`.

### Change

- `swiglu_triton.swiglu_weighted(gate, up, weights)`: fused Triton kernels.
  - Forward computes `silu(gate) * up * weight` in FP32 and rounds once.
  - Backward, one program per row, returns the gate and up gradients and the row's FP32 weight gradient from the same pass.
  - Off the accelerator, or without Triton, it uses the same expression in plain PyTorch.
- `ExpertActivation` gains an optional `weighted_fused_fn`, registered for `swiglu`.
  - `apply_expert_activation(..., row_weights=...)` uses it when available.
  - Otherwise it computes the form in FP32, multiplies, and rounds once.
- Separate and packed gate+up have weighted forward/backward callbacks. They share the same weighted kernel arithmetic with explicit row strides; the packed path reads projection halves in place and writes one packed gradient, avoiding half copies.
- `GroupedExperts.forward` and all three expert paths (for-loop, `torch._grouped_mm`, Triton grouped GEMM) take optional `row_weights`. The for-loop path splits them per expert and ignores padding rows.
- The fused native grouped-GEMM and parent's deferred-weight-gradient path also take `row_weights`. dX and the FP32 router-weight gradient return through the expert backward immediately; only parameter-gradient GEMMs enter the slot, so async combine receives both token and routing-score gradients.
- With `"activation"`, the DeepEP route hands the received weights to the experts and does not weight their output afterwards.
- Rejected rather than ignored:
  - `score_apply` resolving to `"pre"`, checked at layer construction;
  - `comm_backend` other than `"deepep"`;
  - `autoep_size=1`.
- Defaults are unchanged.
- Shape/dtype/device mismatches are rejected before kernel launch. Weighted Triton kernels select the input device/current stream and restore the caller; they are first-order only and explicitly reject `create_graph=True`.
- Docs: `autoep.rst` and the config reference.

### Tests

- Triton (GPU):
  - Forward and gate/up gradients against the FP32 reference, for FP32/FP16/BF16 and even/uneven shapes.
  - The weight gradient within FP32 summation order.
  - Empty input; validation of the weights.
- CPU:
  - For every registered activation, the weighted activation equals the form's FP32 product rounded once under value comparison, without claiming signed-zero bit-pattern equivalence.
  - The for-loop experts with row weights equal post-expert weighting (output, input and weight gradients), including an empty expert and padding rows.
- GPU: the `torch._grouped_mm` and Triton grouped GEMM paths take row weights like the for-loop path, for every activation.
- Config and layer: `"activation"` is rejected without DeepEP, with `autoep_size=1`, and when `score_apply` resolves to `"pre"`. The DeepEP route hands the weights to the experts and does not call the row weighting.
- GPU, `test_row_weighting_in_activation_matches_eager`, 4 GPUs with DeepEP:
  - grouped GEMM (fused kernel) and for-loop paths; uniform and skewed routing; reentrant checkpointing;
  - identical routes;
  - output, input and every parameter gradient within 2e-2 relative L2 of eager.
- GPU suites (DeepEP parity, comm, unit, SwiGLU Triton, expert activation): 394 passed, 1 skipped, 2 failed.
  - Both failures are `TestMiniMaxM3Block::test_replaced_block_matches_hf_block`, and the skip is MiniMax-M3 router-logit capture. Both need Transformers >= 5.15.0; the image has 5.12.0.
- End to end, Qwen3-30B-A3B on 8 H100s, measured with an equivalent benchmark patch on our benchmark base (routing weight inside the fused SwiGLU).
  - Setup: expert parallel size 8, micro-batch 4, 16 accumulation steps, sequence length 4096, DeepEP with 36 SMs, reentrant checkpointing, 30 steps with 10 warmup.
  - The base also had fused gate+up, the backward weight-gradient overlap, the recomputed-combine skip, and the whole-buffer slice fix.
  - One job, order base, change, change, base:

    | | Run medians | Mean |
    |---|---|---:|
    | Separate row weighting | 19,553.4 / 19,547.3 ms | 19,550.3 ms |
    | **Weight inside the SwiGLU** | 18,863.4 / 18,866.8 ms | **18,865.1 ms (-3.50%)** |

  - A real-DeepEP check on 8 GPUs before the timing: output 1.2e-3, input gradient 1.6e-3, router gradient 4.3e-3, expert gradients up to 4.3e-3 relative L2 against the separate weighting.
  - Losses agree within same-arm repeat noise; allocated memory unchanged.

### Ordered review follow-up

- This child inherits the parent/master integration, including actual ZeRO-stage forwarding, checkpoint-layout replay, exact-size slice behavior and failure-safe async event/carveout handling. It does not duplicate those changes.
- The published mathematical contract is not a bitwise contract. Existing weighted-kernel and model-gradient tolerances remain unchanged; near-zero Adam updates are not used as the only correctness criterion.
- On CPU, weighted scalar/reference, metadata and deferral checks pass, including all four activations, FP32/BF16, separate/packed projections and router gradients. The combined comm/replay suite passes **68/68 under `pytest --forked`** on Apple M4 Pro/torch 2.14.1.
- New targeted acceptance on an 8x NVIDIA H100 80GB HBM3 host (distributed cases use four ranks), driver 580.159.04, torch 2.10.0.2/CUDA 13.0, Triton 3.6.0 and transformers 5.12.0: **85 passed, 0 skipped**. This includes all old weighted-kernel shapes/dtypes, packed/unpacked and standalone-gradient equivalence, device/higher-order contracts, all four activation forms, and real eager-vs-activation-vs-overlap comparisons at ZeRO 1/2 with separate/fused gate+up and uniform/skewed routing.
- The model-level comparisons retain the existing 2e-2 relative-L2 bound and inspect every trainable accumulated gradient before clipping. Dropping only the custom backward's row-weight gradient reproduces all eight direct-gradient failures and all six route/checkpoint subcase failures on CPU, confirming that the router path is not silently omitted.
- The existing 394-passed/1-skipped/2-version-related-failure GPU suite and 3.5% E2E prototype evidence are reused. No fresh throughput or convergence sweep was run; the historical percentage is not a retiming of this integrated child.

Validation limits: real DeepEP supports BF16 rows here; direct weighted kernels cover FP32/FP16/BF16 and FP32 weights. Overlap requires the parent's native grouped-GEMM and ZeRO 1/2 scope. No fresh offload, expert-TP, multi-node or non-CUDA-device matrix is claimed.

AI assistance was used for review, conflict integration and tests. The submitting human reviewed the exact child-only diff before signoff; this is an update of the existing PR, not a new duplicate feature.
