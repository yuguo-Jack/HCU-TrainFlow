# Cap CPU accelerator memory at the cgroup limit of the process

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8930) · state: closed · merged: True

## Original PR description

**Issue**

`CPU_Accelerator.total_memory()` and `available_memory()` return host RAM from `psutil.virtual_memory()`. In a container or a Kubernetes pod, the process can use only its cgroup limit. Callers that plan memory from these values on the CPU accelerator include ZeRO 1/2 flattening (`stage_1_and_2.py:451`) and the autotuner. Fixes #8929.

Related: #1891 asks for cgroup-aware CPU memory limits. #3458 (Docker), #2632 and #2788 (Slurm) report processes killed by a cgroup limit without a message.

**Fix**

Only the CPU accelerator, its tests and its docs change.

- `total_memory()` returns the smallest memory limit from the process cgroup up to the root, capped at host RAM.
- `available_memory()` returns the smallest free headroom over every limited cgroup on that path. A parent limit also counts the usage of its other children, so each limited level is checked. Usage excludes the inactive page cache, which the kernel can reclaim.
- The cgroup mount point and mount root come from `/proc/self/mountinfo`. When several mounts match, the one whose root contains the process cgroup is used. This supports mounts that expose a subtree, cgroup v1 co-mounts such as `cpu,memory`, and delegated subtrees mounted before the main mount.
- On by default, as asked in review. `RESPECT_CGROUP_MEMORY_BY_DEFAULT = True` is the one line that sets the default. `DS_CPU_RESPECT_CGROUP_MEMORY=0` turns it off, `=1` turns it on. `export_envs()` returns the variable, so the launcher forwards it to every node.
- The accelerator setup guide documents the variable. `abstract_accelerator.py` does not change.

**How to test**

Needs Docker with cgroup v2. Save the first script from the collapsed sections at the end as `check_cgroup_memory.sh`. One command installs `master` (before) and this branch (after) in the same container with 1 GiB. It prints `total_memory()` and `available_memory()` from three cgroups with `DS_CPU_RESPECT_CGROUP_MEMORY` unset, and once more with `=0`.

```sh
sh check_cgroup_memory.sh "git+https://github.com/deepspeedai/DeepSpeed@master" \
                          "git+https://github.com/prabhkodes/DeepSpeed@cpu-accelerator-cgroup-memory"
```

Output (Ubuntu 24.04 VM, kernel 6.8, 3.8 GiB, cgroup v2, Docker 29.1 with the systemd driver):

```
        process cgroup (container limit 1 GiB)                         total   available
before  A. container root                                          3904 MiB    2773 MiB
before  B. child cgroup, limit 256 MiB                             3904 MiB    2774 MiB
before  C. child 600 MiB; parent 800 MiB, sibling uses 500         3904 MiB    2685 MiB
after   A. container root                                          1024 MiB     342 MiB
after   B. child cgroup, limit 256 MiB                              256 MiB      90 MiB
after   C. child 600 MiB; parent 800 MiB, sibling uses 500          600 MiB     129 MiB
after   A. container root, DS_CPU_RESPECT_CGROUP_MEMORY=0          3904 MiB    2755 MiB
```

Before, every case reports the host. After, `total` is the limit of each case. In C, `available` is the free headroom of the 800 MiB parent, which the 500 MiB sibling also uses. In A, the container's 1 GiB also holds that sibling. With `=0`, the values are host RAM again.

On a cgroup v1 host, the second script, `check_cgroup_v1.sh`, runs the same cases with the same arguments. Same VM booted with `systemd.unified_cgroup_hierarchy=0`, Docker 29.1 with the cgroupfs driver and its default host cgroup namespace:

```

before  A. container root                                          3904 MiB    2850 MiB
before  B. child cgroup, limit 256 MiB                             3904 MiB    2814 MiB
before  C. child 600 MiB; parent 800 MiB, sibling uses 500         3904 MiB    2781 MiB

after   B. child cgroup, limit 256 MiB                              256 MiB      89 MiB
after   C. child 600 MiB; parent 800 MiB, sibling uses 500          600 MiB     129 MiB
```

<summary>check_cgroup_memory.sh (cgroup v2)</summary>

```sh
#!/bin/sh
# Before/after check of DeepSpeed's CPU accelerator memory values inside cgroups. Needs Docker with cgroup v2.
#   sh check_cgroup_memory.sh <before pip spec> <after pip spec>
# Example:
#   sh check_cgroup_memory.sh "git+https://github.com/deepspeedai/DeepSpeed@master" \
#                             "git+https://github.com/prabhkodes/DeepSpeed@cpu-accelerator-cgroup-memory"
# A pip spec can also be a source tarball in the directory given as SRC_DIR (mounted at /src).
# IMG replaces the python:3.12-slim image, e.g. with one that has torch installed.
set -eu
docker run --rm -i --privileged --cgroupns=private --memory=1g ${EXTRA_DOCKER_ARGS:-} ${SRC_DIR:+-v "$SRC_DIR:/src:ro"} \
  -e BEFORE="${1:?before spec}" -e AFTER="${2:?after spec}" "${IMG:-python:3.12-slim}" sh -s <<'INNER'
set -e
export DEBIAN_FRONTEND=noninteractive
apt-get -qq update >/dev/null 2>&1 && apt-get -qq install -y git >/dev/null 2>&1
pip install -q torch --index-url https://download.pytorch.org/whl/cpu >/dev/null 2>&1
pip install -q psutil numpy pydantic packaging py-cpuinfo tqdm hjson msgpack ninja einops >/dev/null 2>&1
cat > /tmp/probe.py <<'PY'
from deepspeed.accelerator import get_accelerator
a = get_accelerator()
print(f"{a.total_memory() >> 20:>7} MiB {a.available_memory() >> 20:>7} MiB")
PY
cat > /tmp/hold.py <<'PY'
import time
b = b"\x01" * (500 << 20)
time.sleep(3600)
PY
C=/sys/fs/cgroup
mkdir -p $C/init; for p in $(cat $C/cgroup.procs); do echo $p > $C/init/cgroup.procs 2>/dev/null || true; done
echo "+memory" > $C/cgroup.subtree_control
mkdir -p $C/nested; echo $((256 << 20)) > $C/nested/memory.max
mkdir -p $C/shared; echo $((800 << 20)) > $C/shared/memory.max; echo 0 > $C/shared/memory.swap.max
echo "+memory" > $C/shared/cgroup.subtree_control
mkdir -p $C/shared/sibling $C/shared/me; echo $((600 << 20)) > $C/shared/me/memory.max
sh -c "echo \$\$ > $C/shared/sibling/cgroup.procs; echo -1000 > /proc/self/oom_score_adj; exec python /tmp/hold.py" &
sleep 3
# run <version> <label> <cgroup> [VAR=value]: the probe runs with the flag unset unless given.
run() {
  printf "%-7s %-56s" "$1" "$2"
  sh -c "echo \$\$ > $C/$3/cgroup.procs; DS_ACCELERATOR=cpu ${4:-} exec python /tmp/probe.py 2>/dev/null"
}
printf "%-7s %-56s %11s %11s\n" "" "process cgroup (container limit 1 GiB)" "total" "available"
for v in before after; do
  if [ $v = before ]; then spec=$BEFORE; else spec=$AFTER; fi
  DS_BUILD_OPS=0 pip install -q --no-deps --force-reinstall "$spec" >/dev/null 2>&1
  run $v "A. container root" init
  run $v "B. child cgroup, limit 256 MiB" nested
  run $v "C. child 600 MiB; parent 800 MiB, sibling uses 500" shared/me
done
run after "A. container root, DS_CPU_RESPECT_CGROUP_MEMORY=0" init DS_CPU_RESPECT_CGROUP_MEMORY=0
INNER
```

```sh
#!/bin/sh
# Before/after check of DeepSpeed's CPU accelerator memory values on a cgroup v1 host. Run as root on the host.
# Docker's default on cgroup v1 is the host cgroup namespace: /proc/self/cgroup shows the host path of the
# container, and the cgroup mount inside the container starts at the container's own cgroup.
#   sh check_cgroup_v1.sh <before pip spec> <after pip spec>
# Example:
#   sh check_cgroup_v1.sh "git+https://github.com/deepspeedai/DeepSpeed@master" \
#                         "git+https://github.com/prabhkodes/DeepSpeed@cpu-accelerator-cgroup-memory"
# A pip spec can also be a source tarball in the directory given as SRC_DIR (mounted at /src).
# IMG replaces the python:3.12-slim image, e.g. with one that has torch installed.
set -eu
[ "$(stat -fc %T /sys/fs/cgroup)" = tmpfs ] || { echo "needs a cgroup v1 host" >&2; exit 1; }
docker run --rm -i --privileged --memory=1g ${SRC_DIR:+-v "$SRC_DIR:/src:ro"} \
  -e BEFORE="${1:?before spec}" -e AFTER="${2:?after spec}" "${IMG:-python:3.12-slim}" sh -s <<'INNER'
set -e
export DEBIAN_FRONTEND=noninteractive
apt-get -qq update >/dev/null 2>&1 && apt-get -qq install -y git >/dev/null 2>&1
pip install -q torch --index-url https://download.pytorch.org/whl/cpu >/dev/null 2>&1
pip install -q psutil numpy pydantic packaging py-cpuinfo tqdm hjson msgpack ninja einops >/dev/null 2>&1
cat > /tmp/probe.py <<'PY'
from deepspeed.accelerator import get_accelerator
a = get_accelerator()
print(f"{a.total_memory() >> 20:>7} MiB {a.available_memory() >> 20:>7} MiB")
PY
cat > /tmp/hold.py <<'PY'
import time
b = b"\x01" * (500 << 20)
time.sleep(3600)
PY
C=/sys/fs/cgroup/memory
mkdir -p $C/nested; echo $((256 << 20)) > $C/nested/memory.limit_in_bytes
mkdir -p $C/shared/sibling $C/shared/me
echo $((800 << 20)) > $C/shared/memory.limit_in_bytes
echo $((600 << 20)) > $C/shared/me/memory.limit_in_bytes
sh -c "echo \$\$ > $C/shared/sibling/cgroup.procs; echo -1000 > /proc/self/oom_score_adj; exec python /tmp/hold.py" &
sleep 3
# run <version> <label> <cgroup under the container> [VAR=value]: the probe runs with the flag unset unless given.
run() {
  printf "%-7s %-56s" "$1" "$2"
  sh -c "echo \$\$ > $C/$3/cgroup.procs; DS_ACCELERATOR=cpu ${4:-} exec python /tmp/probe.py 2>/dev/null"
}
printf "%-7s %-56s %11s %11s\n" "" "process cgroup (container limit 1 GiB)" "total" "available"
for v in before after; do
  if [ $v = before ]; then spec=$BEFORE; else spec=$AFTER; fi
  DS_BUILD_OPS=0 pip install -q --no-deps --force-reinstall "$spec" >/dev/null 2>&1
  run $v "A. container root" .
  run $v "B. child cgroup, limit 256 MiB" nested
  run $v "C. child 600 MiB; parent 800 MiB, sibling uses 500" shared/me
done
run after "A. container root, DS_CPU_RESPECT_CGROUP_MEMORY=0" . DS_CPU_RESPECT_CGROUP_MEMORY=0
# The files the CPU accelerator reads, as seen from cgroup C.
sh -c "echo \$\$ > $C/shared/me/cgroup.procs
  echo '### /proc/self/cgroup'; cat /proc/self/cgroup
  echo '### /proc/self/mountinfo (cgroup lines)'; grep -E ' - cgroup2? ' /proc/self/mountinfo
  for d in $C/shared/me $C/shared $C; do
    echo \"### \$d\"
    for f in memory.limit_in_bytes memory.usage_in_bytes; do echo \"\$f \$(cat \$d/\$f)\"; done
    grep -E '^total_inactive_file ' \$d/memory.stat
  done
  echo '### /sys/fs/cgroup/unified'; ls /sys/fs/cgroup/unified | tr '\n' ' '; echo"
INNER
```

**Precedent.** The same walk is already in production elsewhere. Rust's `std::thread::available_parallelism` takes the smallest `cpu.max` from the process cgroup up to the mount ([`quota_v2`](https://github.com/rust-lang/rust/blob/41089d07a0a2afc16adfe28a760d94d73d7298a4/library/std/src/sys/thread/unix.rs#L908-L953)). The JDK fixed limits on parent nested cgroups in [JDK-8322420](https://bugs.openjdk.org/browse/JDK-8322420) (2024) and the hierarchical memory limit in [JDK-8370572](https://bugs.openjdk.org/browse/JDK-8370572) (2025). Go 1.25 finds the process cgroup through `/proc/self/cgroup` and `/proc/self/mountinfo` ([`cgroup_linux.go`](https://github.com/golang/go/blob/63313a0fc5b68d86399a64e323113667d8aa7823/src/runtime/cgroup_linux.go#L11-L24)), reading the leaf only. vLLM's CPU-quota reader walks the hierarchy ([`_cgroup_cpu_limit`](https://github.com/vllm-project/vllm/blob/ed6b8f4cd2b47e4240e7ff5feb5105444245b0c2/vllm/utils/torch_utils.py#L180-L231)); vllm-project/vllm#64104 adds the same for memory. The same fix for OpenObserve merged on 2026-10-28 (openobserve/openobserve#15906).

Two things worth settling before merge:

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Compute headroom at every finite ancestor**

When the process cgroup has the smallest (or tied) `memory.max` but a larger-limit ancestor is nearly full because sibling cgroups consume it, this selects the child and reads only the child's usage. For example, an empty 1 GiB child under a 2 GiB parent with 1.9 GiB in siblings is reported as roughly 1 GiB available although the parent can accept only roughly 0.1 GiB; callers such as ZeRO sizing in `deepspeed/runtime/zero/stage_1_and_2.py:451` can therefore still allocate past the enforced cgroup headroom and be OOM-killed. Keep the smallest limit for total capacity, but compute the minimum remaining headroom across every finite ancestor.
