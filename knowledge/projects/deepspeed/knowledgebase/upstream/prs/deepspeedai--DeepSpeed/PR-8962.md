# Fix AutoTP multi-query GPTBigCode training at TP > 1

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8962) · state: open · merged: False

## Original PR description

Fixes #8961.

## Scope

This PR fixes the two defects that block AutoTP multi-query GPTBigCode at TP > 1: empty attention
shards and non-contiguous K/V gradients. The regression test compares against a single-device
reference with gradient clipping disabled. This PR does not make the default gradient-clipping
path equivalent to single-device training. The global norm counts the replicated K/V rows once
per TP rank, so with the default `gradient_clipping: 1.0` the clip coefficient still differs
whenever clipping activates. That is a separate pre-existing issue tracked in
#<GRAD_CLIP_ISSUE>.

## Background

GPTBigCode's fused `c_attn` stores the query rows followed by the whole shared K/V block, and `_bigcode_type_transpose` shards only the query rows. With transformers 5.x, `GPTBigCodeConfig(multi_query=True)` exposes `num_key_value_heads=1`, and `AutoTPMeta.from_model_config` uses that as the head count for `get_shard_size`. At TP=2 the query rows and `c_proj` input columns become `[32, 0]`, so rank 1 holds the K/V block but no query rows:

```text
rank 0: c_attn.weight=(48, 32)  attn.c_proj.weight=(32, 32)  num_heads=4
rank 1: c_attn.weight=(16, 32)  attn.c_proj.weight=(32, 0)   num_heads=0
```

The failure point depends on the stack:

- NPU: `cannot reshape tensor of 0 elements into shape [-1, 0]` in backward, then `repeats must be not zero` in the SDPA fallback.
- CUDA 5.20.2: `Number of heads in key/value must divide number of heads in query` in the SDPA forward; rank 0 blocks in the `c_proj` forward all-reduce.

| transformers | `num_key_value_heads` | Result before this PR |
|---|---|---|
| 4.44.2 | absent -> attention heads | no empty shard |
| 5.19.0, 5.20.2 | 1 | empty query shard at TP > 1 |

Separately, the K/V gradient all-reduce added in #8928 passes a `narrow()` view of the fused `c_attn` gradient to the collective. torch_npu returns that gradient in a transposed, non-contiguous layout, while CUDA returns a contiguous `[out, in]` gradient. NCCL and HCCL both reject non-contiguous collective inputs, so NPU fails with `Tensors must be contiguous` even with transformers 4.44.2, where no empty shard exists. On NPU the failed backward is followed by a teardown hang; the primary failure occurs earlier.

| Backend | transformers 4.44.2 | transformers 5.x |
|---|---|---|
| CUDA / NCCL | passes on master | empty query shard; no non-contiguous gradient |
| NPU / HCCL | non-contiguous K/V gradient | empty query shard and non-contiguous K/V gradient |

## Change

**Defect A: shard replicated-K/V layouts by query heads**

- `fusedqkv_utils.py`: add `replicates_kv_block`, which detects `bigcodetype` class names derived from `FUSED_QKV_TYPE_DICT`.
- `auto_tp.py`: for replicated-KV layouts, use `num_attention_heads` as the effective shard count; keep key/value head attributes whole and recompute `num_key_value_groups` from the local query shard. Derive the group count from `kv_heads`, falling back to `num_key_value_heads`, and reject a module that publishes the group count but neither head count instead of silently keeping a model-wide value. Leave `tp_meta` unchanged when an explicit `partition_config` is present, so custom config / HF `tp_plan` keeps ownership of the layout.
- `auto_tp.py`: `AutoTP.set_tensor_parallel_config` calls `_validate_replicated_kv_tp_width` to reject `tp > attention head count`, after the custom partition config / HF `tp_plan` / heuristic choice has been made, so training and inference share the check. An explicit `partition_config` is skipped and owns its layout.
- `engine.py`: keep only the warning for non-replicated layouts whose TP width exceeds the key/value head count. The replicated-KV rejection is not in `engine.py`; it runs from the shared AutoTP path above.

**Defect B: make the K/V gradient collective backend-safe**

- `layers.py`: when the K/V slice is non-contiguous, stage a contiguous copy for `all_reduce` and copy the result back into the view autograd consumes. Empty K/V blocks are skipped on every rank.

## Test

- `TestGPTBigCodeMultiQueryTraining`: TP=2 and TP=4 are separate tests. Each checks the shard shapes, that the K/V gradient hook runs, gradients against the single-device model, four SGD steps (`atol=1e-5`), identical K/V rows across ranks, and that the published `c_attn` affine map matches the local shard.
- `TestGPTBigCodeMultiQueryInference`: TP=2 forward logits match the unsharded model; `tp > query heads` is rejected before replacement.
- Unit tests cover the attribute gate, `tp > query heads` rejection from the shared AutoTP path in both training and inference branches, the explicit `partition_config` exemption and its `tp_meta` guard, the `num_key_value_groups` derivation/error paths, and the non-contiguous staging path.

The training comparisons above use `gradient_clipping: 0.0`; the default-clipping gap is described under Scope and Not covered.

## Not covered

- **Gradient clipping.** The global norm counts the replicated K/V rows once per TP rank. At TP=2 the `c_attn` norm is 1.414× the single-device value; subtracting one extra K/V copy reproduces it exactly. With the default `gradient_clipping: 1.0`, the TP=2 regression test still diverges: the maximum loss difference is 0.034327 (0.79% relative) at step 3, while the same test passes with clipping disabled. The clipping code is unchanged here and is tracked in #<GRAD_CLIP_ISSUE>.
- **Precision beyond fp32.** bf16, fp16, and autocast are follow-up; this PR is validated in fp32 only.
- **Non-contiguous path on CUDA.** The staging branch runs end-to-end on NPU. CUDA returns a contiguous gradient, so it is covered by a synthetic unit test only.
- **Non-MQA GPTBigCode.** `multi_query=False` is unchanged; its forward failure under AutoTP is pre-existing and noted in #8927's Related section.
- **Mixed replicated-KV layouts.** The `tp_meta` adjustment applies to the whole AutoTP instance, which assumes one replicated-KV layout per model (as GPTBigCode has). A model mixing GPTBigCode blocks with another fused layout would need per-block metadata.
- **Inference.** Forward and illegal-TP rejection are covered; `generate` and a past-KV-cache run are not covered.
