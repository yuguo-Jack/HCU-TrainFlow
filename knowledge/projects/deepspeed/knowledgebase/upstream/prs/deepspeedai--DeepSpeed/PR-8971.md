# Log Train/Samples/train_loss to monitors again

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8971) · state: open · merged: False

## Original PR description

Restore the `Train/Samples/train_loss` monitor event that `DeepSpeedEngine` stopped writing to TensorBoard, WandB, CSV and Comet in v0.18.3.

## What breaks

Since #7665 (PyTorch-compatible backward API, first released in v0.18.3), a run with any monitor backend enabled only gets `Train/Samples/lr` (and `loss_scale` with fp16). The training loss is never written, although `docs/_pages/config-json.md` and `docs/code-docs/source/monitor.rst` still list `Train/Samples/train_loss` as logged by default. `PipelineEngine` is not affected because it writes its own loss event in `train_batch()`.

Reproduce: enable `csv_monitor` (or `tensorboard`), train a few steps with `engine.backward(loss)` and `engine.step()`, and look for `Train_Samples_train_loss.csv`. It is missing on current master. The write is present in `engine.backward()` up to v0.18.2 and absent from v0.18.3 on (checked in the released sources).

## Root cause

#7665 moved the backward prologue into output hooks and removed the block in `engine.backward()` that summed `loss.mean().detach()` into `self.losses` and wrote the event at the accumulation boundary. `self.losses` is still reset in `_take_model_step()`, but nothing writes to it anymore.

## Fix

- `engine.backward()`: when the monitor is enabled, add the gradient-accumulation-scaled loss to `self.losses` after `loss.backward()` and the backward epilogue succeed. The sum is kept in fp32 so bf16/fp16 losses do not drift over many micro-batches, and a backward that raises does not leave its loss in the next event.
- `engine.step()`: at the accumulation boundary, write `("Train/Samples/train_loss", self.losses.item(), self.global_samples)` on rank 0 right before `_take_model_step()`, which resets the sum and advances `global_samples`.

This keeps the value and x-axis of the v0.18.2 event (mean micro-batch loss of the step, at the pre-step `global_samples`). Writing it in `step()` instead of `backward()` also covers `managed_gradient_accumulation=false`, where the boundary is only known inside `step()`. Nothing runs when the monitor is disabled, and the only added sync is one `.item()` per optimizer step on rank 0 with a monitor enabled, which matches the old behavior.

Sibling paths checked: `PipelineEngine` calls `super().backward()` and `_take_model_step()` directly and never `DeepSpeedEngine.step()` (it raises), so it accumulates and resets `self.losses` but does not write a second event. `DeepSpeedHybridEngine` inherits the fixed path.

## Tests

New `TestMonitorTrainLoss` in `tests/unit/monitor/test_monitor.py` trains `SimpleModel` with the CSV monitor (GA=256, 2 optimizer steps) and checks one event per optimizer step equal to the mean of the micro-batch losses returned by forward. Cases: managed GA fp32, unmanaged GA fp32, managed GA bf16 with ZeRO-1 (skipped where bf16 is unsupported). The bf16 case also fails if the sum is kept in bf16.

Hardware: CPU only, AMD EPYC Genoa (4 vCPU), `DS_ACCELERATOR=cpu`, torch 2.15.0+cpu, Python 3.11.14, pytest 8.3.5. No GPU runs.

```
cd tests && DS_ACCELERATOR=cpu pytest --forked -q unit/monitor/test_monitor.py -k TrainLoss
```

- master (ba0d63c): 3 failed, `AssertionError: Train/Samples/train_loss was not written to the monitor`
- this PR: 3 passed (also 3 repeated runs, all passed)

Extra local check, not committed: the same loop with both `csv_monitor` and `tensorboard` across ZeRO 0 fp32, ZeRO 1/2/3 bf16 and ZeRO 2 fp32 (10 cases), comparing the logged values against the forward losses: all passed. Not validated: fp16 with dynamic loss scaling, CPU/NVMe offload, multi-rank runs, WandB and Comet (they receive the same event list through `MonitorMaster`).

## Not covered

Users who call `loss.backward()` directly instead of `engine.backward(loss)` still get no `train_loss` event, because the engine never sees the loss value on that path. That path did not exist before #7665, so this is not a regression, but the docs could say that `train_loss` is logged for `engine.backward()`. Happy to add that line or to log from the output hook if you prefer.

**<sub><sub>![P2 Badge](https://img.shields.io/badge/P2-yellow?style=flat)</sub></sub>  Normalize the monitored loss in fp32 before accumulation**

For native fp16 losses with gradient accumulation, this conversion happens too late: `gas_scaled_loss` was already divided by the accumulation factor in fp16. For example, an fp16 loss of `1e-5` with `gradient_accumulation_steps=1024` rounds to zero during that division, so the new monitor records `train_loss=0` despite nonzero micro-batch losses and a successful backward. Summing in fp32 cannot recover that value. Preserve a detached fp32 copy of the original loss before normalization, respect `scale_wrt_gas`, and accumulate that copy for monitoring.

Useful? React with 👍 / 👎.
