# ZeRO-3: partition parameters of modules added after initialization

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/9002) · state: open · merged: False

## Original PR description

## Summary

Modules attached after `deepspeed.initialize` (for example inference modules or frozen copies created by PEFT `modules_to_save` wrappers) are constructed outside `deepspeed.zero.Init`, so their parameters remain full and unsharded. `partition_all_parameters()` then failed at the first optimizer step, and the new parameters were never gathered by the forward hooks.

This adds `DeepSpeedZeRoOffload.partition_pending_parameters()`:

- Detects new modules in the ZeRO-3 forward prologue and converts their parameters to ZeRO parameters in place.
- Also detects parameters attached directly to already-registered modules before that module's forward hooks run, instead of waiting for the optimizer-step fallback.
- Registers hooks on new modules while skipping already-registered children, so repeated forwards do not duplicate hooks.
- Excludes descendants of existing ZeRO leaf modules from hook registration, preserving the leaf boundary (important for MoE and granularity-selected leaves) while still converting genuinely new parameters owned by the leaf.
- Refreshes the persistence policy and invalidates the coordinator trace when parameters are added.
- Refreshes the engine's parameter-name registry, including names changed by wrapping existing modules, so checkpoint save/load includes late parameters and no longer fails on the one-time name snapshot.

### Trainable late parameters

ZeRO-3 builds its FP16 partitions, FP32 master weights, gradient buffers, and reduction hooks from the optimizer groups at initialization and has no incremental enrollment path. Silently warning users to add a late parameter to the optimizer left its gradient unreduced and the adapter incorrectly stepped. This change rejects late trainable parameters with an explicit error that points to creating adapters before `deepspeed.initialize()` (or inside `deepspeed.zero.Init`) and notes that frozen late parameters are supported.

This targets the frozen/inference side of the PEFT `modules_to_save` workflow in #7669 and makes the trainable limitation explicit.

## Testing

- `tests/unit/runtime/zero/test_zero3_late_parameter_partition.py` covers:
  - a late-attached frozen module and a frozen `modules_to_save`-style wrapper,
  - direct parameters attached to already-registered modules during forward and during the optimizer-step fallback,
  - repeated forwards without duplicate hooks,
  - exclusion of existing leaf descendants from hook registration,
  - explicit rejection of trainable late parameters,
  - a checkpoint save/load round trip for a late frozen parameter.
- Manually validated with `torchrun --nproc_per_node=2`, checking shard sizes for a frozen wrapper and a direct parameter.
- `pre-commit` passes (flake8 run separately under Python 3.12).

Fixes #7669

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Keep hooks out of configured ZeRO leaf descendants**

When an existing model contains a configured ZeRO-3 leaf (including MoE leaves or modules selected by `stage3_module_granularity_threshold`), initial hook setup intentionally stops recursion at that leaf, so its pre-existing descendants have no `ds_id`. This loop consequently registers per-child hooks on the first forward even when nothing was added; rank-dependent expert execution then enters the coordinator trace below the leaf, defeating the leaf boundary and causing cross-rank trace mismatches. Exclude descendants of existing ZeRO leaves from the new-module set while still converting genuinely new parameters owned by the leaf.

When a pending parameter requires gradients, as the trainable copy in a `modules_to_save` wrapper does, Stage 3 has already built its FP16 groups, FP32 partition buffers, and gradient-reduction hooks from the original optimizer parameters. There is no Stage-3 add path that rebuilds those structures, so adding the parameter to the underlying optimizer as this warning instructs leaves its gradient unreduced and the adapter is not correctly stepped (and may fail once its data is partitioned). The wrapper test only checks sharding after `step()` rather than observing a weight update; either fully enroll late trainable parameters or reject them explicitly.
