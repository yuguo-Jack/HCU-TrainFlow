# Avoid `O(W^2)` linear scans in `ProcessTopology` and `PipelineParallelGrid`

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8888) · state: open · merged: False

## Original PR description

## Motivation

In `deepspeed/runtime/pipe/topology.py`, several methods on `ProcessTopology` and `PipelineParallelGrid` performed repeated linear scans over all `W` ranks (`world_size`), leading to $O(W^2)$ overhead when initializing pipeline-parallel topologies and building checkpoint rank representations on large multi-node clusters:

1. **`ProcessTopology.get_coord(rank)` & `get_rank_repr(rank)`:**
   - `get_coord(rank)` linearly scanned `self.mapping.items()` (`O(W)` per lookup), and `get_rank_repr(rank)` invoked `self.get_coord(rank=rank)` inside the `for ax in axes:` loop on every axis.
2. **`ProcessTopology.__init__` & `get_axis_comm_lists(axis)`:**
   - `__init__` constructed `key = {axis: coord[self.axes.index(axis)] for axis in self.axes}` before `self.ProcessCoord(**key)` even though `self.ProcessCoord` is a `namedtuple` whose fields already match `self.axes` (`self.ProcessCoord(*coord)`).
   - `get_axis_comm_lists(axis)` similarly evaluated `{a: coord[other_axes.index(a)] for a in other_axes}` and `self.get_dim(axis)` inside the cartesian product loop instead of `dict(zip(other_axes, coord))`.
3. **`PipelineParallelGrid._build_p2p_groups()`:**
   - Iterated `for rank in range(self.world_size): for l in comm_lists: if rank in l: idx = l.index(rank)` ($O(W^2)$ across all ranks) and called `self._topo.get_axis_comm_lists('pipe')` a second time even though `self.pipe_groups` computes the exact same list.
   - Because `comm_lists` partitions `0 .. world_size - 1`, `p2p_lists` can be populated in a single $O(W)$ pass over `comm_lists`.

## Changes

- Maintain `self.rank_to_coord` in `ProcessTopology.__init__()` and construct `self.ProcessCoord(*coord)` directly.
- Use $O(1)$ `self.rank_to_coord[rank]` lookup in `ProcessTopology.get_coord(rank)` (verifying `self.mapping.get(coord) == rank` and refreshing `self.rank_to_coord[rank]` if `self.mapping` was modified after construction) and hoist `coord = self.get_coord(rank=rank)` outside the axis loop in `get_rank_repr()`.
- Use `dict(zip(other_axes, coord))` in `get_axis_comm_lists()`.
- Reuse `self.pipe_groups` and populate `p2p_lists` in a single $O(W)$ pass in `PipelineParallelGrid._build_p2p_groups()`.
- Add tests in `tests/unit/runtime/pipe/test_topology.py` covering `PipelineParallelGrid` `pipe_groups`/`p2p_groups` construction (including 4-stage wrap-around and remapped topologies) in `TestDistributedTopology.test_grid_pipe_data` as well as invalid-rank `ValueError` and remapped-coordinate refresh in `test_topology_remapped_mapping`.

### Micro-benchmark (4,096-rank 3D topology: `dims=[32, 32, 4]`)

- **Before (`master`)**: `1,114.22 ms`
- **After (this PR)**: `21.08 ms` (**52.9x speedup**)

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Invalidate reverse lookups when mapping is remapped**

When a caller or subclass remaps `mapping` after construction (for example, swaps two coordinates to define a non-row-major rank layout), this early return still yields the original coordinate for every cached rank, so the fallback scan is never reached. `get_rank()` and `get_axis_comm_lists()` then use the modified mapping while `PipelineParallelGrid.get_stage_id()` and `get_data_parallel_id()` use the stale result, which can assign stage/DP identities inconsistent with the communication groups; verify that the cached coordinate still maps to `rank` and refresh it before returning.
