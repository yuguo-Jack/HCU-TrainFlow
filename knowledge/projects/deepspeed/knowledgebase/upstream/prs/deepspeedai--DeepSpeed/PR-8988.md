# Fix zero.Init: respect explicit dtype in tensor constructors

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8988) · state: open · merged: False

## Original PR description

## Summary

`zero_wrapper_for_fp_tensor_constructor` unconditionally casts every floating-point tensor to the target dtype (e.g. bf16), even when the caller explicitly passes `dtype=torch.float`. This corrupts RoPE `inv_freq` computation in ~200+ transformer models that use:

```python
torch.arange(0, dim, 2, dtype=torch.float) 
```

Under ZeRO-3, `inv_freq` is computed in bf16, causing positional encoding errors up to **117 radians** at position 65k (vs 0.003 rad in fp32).

## Fix

Skip the cast when `kwargs['dtype']` is explicitly set, in both:
- `zero_wrapper_for_fp_tensor_constructor` (wraps `torch.empty`, `torch.zeros`, `torch.ones`, `torch.arange`, etc.)
- `get_new_tensor_fn_for_dtype` (wraps `torch.Tensor.__new__`)

If no dtype is passed (or `dtype=None`), behavior is unchanged: the tensor is cast to the target dtype as before.

Fixes #8948

## Test plan

- Added `TestZeroWrapperDtypeRespected` and `TestNewTensorDtypeRespected` covering:
  - Explicit `dtype=torch.float32` preserved across `empty`, `zeros`, `ones`, `randn`, `arange`, `full`
  - No-dtype calls still cast to target bf16
  - End-to-end RoPE `inv_freq` pattern stays float32

```bash
pytest tests/unit/runtime/zero/test_zero_init_dtype.py -v
```

With bf16 ZeRO-3 and no parameter offload, a module combining a default-dtype parameter with one created using `torch.ones(..., dtype=torch.float32)` now gets bf16 and fp32 shards. `Init._post_init_method()` does not recast parameters, and `DeepSpeedEngine._cast_module_mixed_precision()` skips already-partitioned parameters, so `deepspeed.initialize()` aborts at the single-dtype assertion in `deepspeed/runtime/zero/utils.py`'s `defragment()`. Preserve explicit precision for intermediate tensors and buffers such as `inv_freq`, but separately convert model parameters to the context dtype before partitioning so previously working models with mixed constructor styles can still train.
