# [AutoEP] Plan expert transfers from the live runtime placement

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8800) · state: open · merged: False

## Original PR description

## Summary

#8623 plans shard-to-shard copies between two `ParamAffineMap`s. Today, though, the only AutoEP maps come from checkpoint metadata, so nothing at runtime can feed the planner. This PR closes that gap: it builds the source map from the placement the live `AutoEPMoELayer` actually holds, and builds the target map from a target placement descriptor. Both maps then go straight to `plan_transfer`.

```
AutoEP runtime placement -> source / target ParamAffineMap -> plan_transfer (#8623) -> copy descriptors
```

Related: #8252 (§8.4 AutoEP expert placement), #8230, #8544.

## Changes

- `AutoEPMoELayer.expert_affine_maps()` returns the affine maps of the live `w1`/`w2`/`w3`.
  - Map ranks are EP-local ranks. The docstring explains how to translate them with `dist.get_global_rank(self.ep_group, rank)`.
  - Each shard is the unpartitioned packed `[local_experts, ...]` tensor. ZeRO-3/EDP fragments stay outside the map, and the shape comes from `ds_shape`.
  - No collectives.
- `AutoEPMoELayer.plan_expert_transfer(target_placement, limits=None, *, replica_selector=None)` returns one `TransferPlan` per expert parameter.
  - It only plans: it moves no data, swaps no parameters and migrates no optimizer state.
- `autoep_affine.plan_autoep_placement_transfer(source_placement, target_placement, logical_shape, ...)` is the layer-independent form. Both placements go through the existing `autoep_placement_to_affine_map`, so no second placement→map conversion is introduced.
- The live placement must match how `repack_expert_weights` actually packed the weights; today that is contiguous and uniform. A descriptor that disagrees raises `NotImplementedError`, rather than producing a map that addresses shards the weights do not have.
  - A placement the descriptor can express is not necessarily one the runtime can execute. The target placement is only used for planning.

## Not in scope

- Executing plans or transporting data (see the executor work in 0z5a/DeepSpeed#1), parameter swap, optimizer-state migration.
- Placement generation/versioning: the runtime does not change placement after construction yet.
- Runtime support for non-uniform placements.

## Tests

`tests/unit/v1/moe/test_autoep_unit.py` adds three tests:
- `test_live_expert_maps_address_the_packed_runtime_weights`: for each rank, the map's shard shape and contents match the real packed `w1/w2/w3`. The reference is the full tensor from `repack_expert_weights(ep_size=1)`, which does not depend on any affine map.
- `test_plan_expert_transfer_moves_live_shards_into_target_packed_order`:
  - The source is EP=2. The target has 3 ranks with reordered, uneven, empty and replicated placements.
  - Executing the plan on the live shards reproduces the target shards in target packed order, and every target element is written exactly once.
  - Planning is checked to never call `rebuild`/`extract`.
- `test_live_expert_maps_reject_a_placement_the_weights_do_not_have`: a mismatched descriptor and a mismatched logical shape both raise.

Results:
- `test_autoep_unit.py`, `test_autoep_affine.py`, `test_autoep_affine_universal.py`, `test_affine_transfer_plan.py`: 354 passed, 6 skipped.
- Swapping in a wrong live placement makes the new tests fail.
- Hardware: Intel Arc Pro B70; these are single-process unit tests.
