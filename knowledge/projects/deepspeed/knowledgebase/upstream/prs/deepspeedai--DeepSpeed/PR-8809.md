# [checkpoint] Execute affine transfer plans with bounded peer staging

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8809) · state: closed · merged: True

## Original PR description

The merged #8623 planner describes affine shard copies. This PR executes those plans directly into existing frozen target shards with bounded peer staging, without reconstructing the full logical tensor.

Refs #8230, #8252 and 0z5a/DeepSpeed#1. This is the executor portion of that work; #8800 supplies live AutoEP metadata separately. The diff is limited to **4 files, 1014 added lines**: executor, contract tests, a new API documentation page and its toctree entry. Historical benchmark drivers and evidence remain in the fork and are linked below.

`execute_transfer` / `execute_transfers` accept explicit source and target rank bindings, preserve strided regions and storage offsets, and collectively reject invalid buffers, aliases or request-order disagreement before writes. Shared plans reuse their schedule within a call. On accelerators that are not synchronized with the host (`is_synchronized_device()` is false), work handles order the caller stream and drain every 32 rounds and before return; on synchronized devices such as CPU each handle is waited immediately.

Review fixes, first round: valid scalar plans now execute; the unrelated `new_group(timeout=...)` changes are removed, preserving the existing CCL interface.

Review fixes, second round: stream ordering is gated on `is_synchronized_device()` rather than the device type; the multi-rank tests are no longer confined to CUDA and rely on the harness's device-count gate before launch; the disjoint-endpoint case uses 2 or 4 ranks so it fits the two-GPU PR runners and the four-rank CPU nightly; the documentation moved from the AutoEP page to an *Affine Shard Transfers* page under Checkpointing API, and records that the staging arena and `StagingBudget` belong to the current torch point-to-point transport.

**Transport assumption worth documenting: staging is not inherent to affine transfer**

The executor hands the transport one contiguous tensor per peer per round, so strided regions are packed through an arena. A future GPUDirect-RDMA path would instead want the per-round `(offset, length)` pairs as a scatter/gather list over registered memory — i.e. the arena copy is the copy such a transport exists to remove, and it also needs registration lifetime this API has no place for. No code required now: please note in the module docstring (and `autoep.rst`) that the arena and `StagingBudget` are artifacts of the current torch-P2P transport, and that the wire contract is expected to change when a zero-copy path lands.

- 0z5a · comment · 2026-10-26T17:43:47Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8809#issuecomment-6423197759)

Pushed 99aef488 with one more fix, found while wiring the executor into an RL trainer↔engine weight-update group.

**The bug.** RL frameworks build that group outside the default world. Each trainer or engine process keeps its own default group (world size 1 at TP=1) and joins a separate two-process group created with `_new_process_group_helper` on its own store, which is how slime, SGLang and vLLM set it up. torch's rank bookkeeping for such a group maps every member's default-world rank 0 to group rank 0, so `dist.get_rank(group)` returned 0 on both ends. The preflight then refused the whole batch:

```
[transfer] rank 0 rejected the batch: target location 0 is not owned by this process
AffineTransferExecutionError: a rank rejected the transfer batch before it began; no data moved
```

**The fix.** When a group is passed, `execute_transfers` now reads the rank and size from the group itself (`group.rank()` / `group.size()`). The default-group path is unchanged.

**The test.** `tests/unit/checkpoint/test_affine_transfer_executor_external_group.py` reproduces the setup on CPU: two processes, each with a world-size-1 default group, joined by an externally created gloo group. It fails on ba9e8b65 with the error above and passes on 99aef488. With `DS_ACCELERATOR=cpu`, the existing executor tests and the new one pass together (50/50). The test has to create the group with `torch.distributed` directly, so I added it to the `check-torchdist` exclusion next to `tests/unit/comm/test_dist.py`. If you'd rather keep that list fixed, I can move the reproduction under `tests/unit/comm/` instead.

With the fix, the executor also syncs a full Qwen3-8B (399 tensors, 16.4 GB) between two GPU hosts over NCCL into a running vLLM engine's parameters, through exactly such a group, bitwise-checked after every sync.

The CPU multi-rank runs now cover the synchronized branch: forcing the other branch there makes them fail.

One caveat for other accelerators. `Work.block_current_stream()` orders the device stream only on backends that override it. `WorkNCCL` and `WorkXCCL` both implement it as `synchronize()`; I checked this at the torch 2.12.1 and 2.14.1 tags and the torch-xpu-ops commits they pin. The base `Work` implementation instead uses a CUDA stream baton. Forcing this branch on CPU/gloo shows what happens on a non-synchronized accelerator whose backend does not override the method: the two-rank cases fail at the first round with `RuntimeError: Failed to create StreamBlock`, and the four-rank case stalled instead of failing. I did not find such an override for HCCL or CNCL. This PR has not been validated on those devices, and before this change they took the `wait()` path.
