## Summary

With `offload_optimizer.device: cpu`, ZeRO-3 copies each sub-group's updated float32 master partition back to the
device from host memory that is never pinned, even with `pin_memory: true` (the default since #8207). This PR copies
it through two fixed-size pinned buffers instead, with the same values.

- Qwen2.5-32B, 8 H200, whole optimizer on the CPU: 11.96 s to 10.35 s per step (-13.5%), same peak memory.
- MiniMax-M3 (all 60 layers, 4 nodes x 8 H200, 65% of the optimizer on the CPU): 126.9 s to 123.9 s per step.
- Extra host memory: a fixed 256 MiB of pinned memory per rank (bf16).

## Duplicate check

Searched issues and PRs on 2026-10-13 ("offload pinned fp32 partition", "zero3 offload pin_memory copy",
"fp32_partitioned_groups_flat", "offload ratio pinned", "pageable offload"). Related, not duplicates: #8207 (merged:
pinned the ZeRO-3 gradient offload buffers, default `pin_memory: true`; master partitions unchanged), #8256 (merged:
routes pin sites through `get_accelerator().pin_memory()`; this PR uses the same accelerator calls), #8618 (closed:
a CPU-offload benchmark).

Sibling path: ZeRO-1/2 does not have the defect. It pins the float32 partition and casts into a pinned bf16 buffer
of the partition's size before a `non_blocking` copy (`stage_1_and_2.py` lines 546-558 and 2841-2844).

## Root cause

`_create_fp32_partitions` (`stage3.py`) builds each CPU master partition with `.to('cpu', dtype=...)` and
`.clone().detach()`, which is pageable memory whatever `pin_memory` says. After the CPU optimizer step,
`_reassign_or_swap_out_partitioned_parameters` runs `fp16_flat.data.copy_(fp32_flat.data)`: a blocking copy from CPU
float32 to device bf16. For a blocking copy with a dtype change, PyTorch converts on the CPU into a new pageable bf16
tensor of the whole partition, copies it from pageable memory and synchronizes.

Found in a profile (MiniMax-M3, first 8 layers, 8 H200, 75% of the optimizer on the CPU, rank 0): 13 bare
`aten::copy_` host-to-device copies of 576 MiB per step from pageable memory, at 3-7 GB/s, 1,648 ms per step.

## The change (`deepspeed/runtime/zero/stage3.py`, 49 added, 2 removed lines)

| Where | What |
|---|---|
| `_reassign_or_swap_out_partitioned_parameters` | uses the new copy when `offload_optimizer.pin_memory` is true, the source is on the CPU and not pinned (`get_accelerator().is_pinned`), and the destination is on the device; every other case keeps `dst.copy_(src)` |
| new `_copy_through_pinned_staging(dst, src)` | two pinned buffers of 2**26 elements in `dst`'s dtype (`get_accelerator().pin_empty`, created on first use). Per piece: wait for the previous copy out of this buffer (an event), cast the piece into the buffer on the CPU, `copy_(..., non_blocking=True)` to the device, record an event. Before returning, wait for the last piece |
| `__init__`, `_unpin_offload_buffers` | the buffer size and state; release of the buffers (matters under `DS_PIN_MEMORY_BACKEND=native`) |

Design notes:
- **Why not pin the master partitions, as ZeRO-1/2 does:** a `non_blocking` copy from pinned float32 into a bf16
  tensor converts on the device and needs a float32 device temporary of the sub-group's size. Avoiding that needs a
  pinned bf16 buffer of each partition's size, as ZeRO-1/2 keeps. Either way pinned host memory would grow with the
  model, and PyTorch's pinned allocator rounds each allocation up to a power of two. The two buffers here have a fixed
  size; 2**26 is a power of two, so nothing is rounded up.
- **Same values:** the CPU cast is the one the blocking copy did before (round to nearest even), so the device
  partition is bitwise the same.
- **Stream order:** the pieces are copied on the current stream, and an event guards each buffer's reuse. The final
  wait keeps what callers had before: the partition is on the device when the function returns. The next forward's
  parameter all-gathers run on their own stream, and it does not wait for the main stream.
- **Host synchronization:** at most one piece-sized wait per buffer reuse and one at the end. The old path blocked
  for the whole copy.

## Tests

New: `TestZero3OffloadPinnedCopyBack` in `tests/unit/v1/zero/test_zero.py` (2 ranks, `ratio` 1.0 and 0.5,
`sub_group_size` 20,000 so partial offload has sub-groups on both sides).
- It trains 3 steps with `pin_memory: false` (direct copy) and with `pin_memory: true`, and requires the gathered
  parameters to be bitwise equal.
- It also requires that only the pinned run used the staging buffers. Otherwise the test would compare the direct
  copy with itself.
- The piece size is set to 1,000 elements, so each step refills both buffers many times.

The test is in `tests/unit/v1` so that PR CI selects it. With this diff, the `modal-torch-latest` selector
