# SuperOffload: checkpoint the CPU Adam state, fix unused parameters and rollbacks, speculate with clipping

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8972) · state: open · merged: False

## Original PR description

## Summary

SuperOffload has several bugs that change the training result without an error, mostly in the path that runs the CPU
Adam step during backward and undoes it in `step()`. This PR fixes them. 

## Fixes

Before → after, against ZeRO-3 CPU offload on GH200 (base `c6291b7e1`):

1. Checkpoints had no Adam state (it lives in the CPU worker process). It is now saved in the ZeRO-3 layout. 
2. A sub-group with an unused param never stepped, and a param without a gradient reused an old one. 
3. Gradient accumulation lost the gradients of earlier micro-steps.
4. Undoing a step with an inf/nan gradient set the weights to 0, and undoing a finite step could make `exp_avg_sq`
   negative (nan in the next step).
5. The worker ignored `adam_w_mode`, `bias_correction` and `fp32_optimizer_states`, and failed with bf16 master
   weights. Up to 1.4e-1 off, or `RuntimeError`
6. Under fp16, the step during backward used the loss-scaled gradient.
7. The worker kept the initial `betas`, `eps` and `weight_decay` (only `lr` was sent).
8. With `gradient_clipping` > 0 (the default is 1.0), no CPU step overlapped backward. Now it does; `step()` undoes and
   redoes those steps when clipping triggers or the fp16 loss scale changes.
9. With the decoupled checkpoint engine, the next backward could change the state while it was being written.
   `save_checkpoint` now commits the save first.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Disable speculative rollback for zero Adam betas**

With SuperOffload configured with a valid Adam beta of 0 (for example `betas=[0, 0.999]`) and a speculative step later being undone because clipping triggers, another gradient arrives, or another group overflows, this gate still enables speculation. `adamw_rollback_inplace` reconstructs `exp_avg`/`exp_avg_sq` by dividing by `beta1`/`beta2`, so rollback writes NaNs into the worker state and the next update corrupts the weights; include nonzero betas in the eligibility check (and re-evaluate it if schedules change them).

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Preserve FP32 moments when loading BF16-master checkpoints**

When `bf16_master_weights_and_grads=true` and `bf16_optimizer_states=false`, the worker checkpoint contains FP32 moments, but `super().load_state_dict()` first loads them through PyTorch against the BF16 flat parameter and casts floating optimizer state to that parameter dtype. Passing the popped state through here therefore leaves a worker configured for FP32 optimizer states holding BF16 moments, silently changing resumed updates; cast `exp_avg` and `exp_avg_sq` back to FP32 before `set_state` or restore the worker state without the generic parameter-dtype cast.
