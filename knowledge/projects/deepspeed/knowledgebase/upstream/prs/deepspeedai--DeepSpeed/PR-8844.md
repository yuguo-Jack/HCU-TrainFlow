## Problem

`ds_to_universal` converts a ZeRO-3 AutoEP checkpoint in two parts. The dense parameters go through the usual
extract-and-merge path, which reads one optimizer file per worker and writes fragments to `tmp/`. The routed experts
go through `_consolidate_zero3_autoep_expert_states`, which first loads **every** rank's optimizer file into one dict
(`optim_states_by_rank`) and then keeps a copy of every expert fragment in memory until all of them are merged.

Together those files hold every optimizer state of the model: fp32 (or bf16) master weights plus both Adam moments.
For a large MoE model that is more than one host has:

| Model | Parameters | Optimizer state, fp32 master + fp32 Adam (12 B/param) | bf16 master + bf16 Adam (6 B/param) |
|---|---|---|---|
| MiniMax-M3 | 426.2B | 4.65 TiB | 2.33 TiB |
| GLM-5.2 | 743.4B | 8.11 TiB | 4.06 TiB |

The H200 nodes this was found on have 2 TiB of host memory, so the conversion cannot finish for either model.

## Change

`_consolidate_zero3_autoep_expert_states` reads one rank's optimizer file at a time. Each expert fragment it finds is
written to `<output>/tmp/autoep_expert_fragments/` (one file per parameter, optimizer state, EP rank and partition
rank) and the rank's file is released before the next one is read. The merge then loads, for one parameter and one
state at a time, only that parameter's fragments. Peak host memory becomes one optimizer file plus one full expert
tensor, instead of all optimizer files.

The checks are unchanged: missing ranks, duplicate or missing expert-data-parallel partitions, shape mismatches and
placement disagreements raise the same errors. The temporary fragments live under `<output>/tmp`, which the converter
already uses for the dense fragments and removes at the end.

4.65 TiB in total, more than the 2 TiB of the H200 hosts this was found on); after, one rank's file plus one
parameter's fragments.
