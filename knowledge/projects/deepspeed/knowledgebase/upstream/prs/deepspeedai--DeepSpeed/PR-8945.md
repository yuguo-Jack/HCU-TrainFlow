# [VocabTP] vocab_parallel_ce support fused LM-head projection + loss for the HF forward

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8945) · state: closed · merged: True

## Original PR description

## Motivation

`vocab_parallel_lm_head` (#8173 follow-ups) keeps the output vocabulary sharded, but each rank still
materializes `[tokens, vocab / tp]` logits (plus their FP32 copies in the loss). #8792 added
`vocab_parallel_linear_cross_entropy`, which fuses the projection into the loss, but its docs state it is
"not yet wired into the HuggingFace forward or the `vocab_parallel_lm_head` configuration". This PR does
that wiring, so HF `Trainer` / plain `deepspeed.initialize` users get it via config only. Tracked in the
#8790 plan.

**Not a duplicate:** searched open PRs/issues for `fused_linear`, `linear_cross_entropy`, `vocab_parallel_ce_backend`;
the only related work is #8540 (Liger CE on logits, does not fuse the projection) and #8792 (the kernel itself).
Liger's own FLCE has no TP support.

## What changes

- `tensor_parallel.vocab_parallel_ce_backend` accepts `"fused_linear"`.
- `VocabParallelLinear.forward`: when the installed fused loss is armed (training forward with `labels`), the
  head returns a `[..., 0]` placeholder and hands its input to the loss instead of projecting it.
- `VocabParallelLinearCausalLMLoss` (installed as `model.loss_function`): HF label shift, `ignore_index`,
  `num_items_in_batch`; falls back to the logits-based vocab-parallel loss when nothing was captured
  (eval mode, no labels).
- Explicit rejections: ZeRO-3 (head params freed before the loss runs), DeepCompile `autotp` pass, and
  models that soft-cap / rescale logits after the head (`final_logit_softcapping`, `logit_scale`, `logits_scaling`).
- `vocab_parallel_linear_cross_entropy` now drops `ignore_index` tokens before the projection (prompt/padding
  tokens cost no GEMMs or collectives); the range check and the compacted length share one host sync.
- Default chunk size keeps the FP32 logits chunk near the hidden-state size **but at least 256 tokens**. Without
  the floor, 4,096 valid tokens were split into 85 chunks of ~49 rows (narrow GEMMs, 170 tiny all-reduces):
  on L20 the op took 128 ms vs 47 ms at 256 rows (+150 MiB); larger chunks gave no further gain.
- Docs: `docs/_tutorials/autotp-training.md` — new backend, HF `Trainer` usage, measurements, limitations,
  and the incompatibility of any vocab-parallel backend with callers that compute their own loss from
  logits / `lm_head.weight` (`Trainer(label_smoothing_factor=...)`, TRL ≥ 1.15 `SFTTrainer`/`GRPOTrainer`
  fused LM head).

## Downstream HF usage

No HF code change needed. `transformers` `Trainer` reads `tensor_parallel.autotp_size`
(`trainer.py` `get_tp_size`) and `integrations/deepspeed.py` calls
`deepspeed.tp_model_init(model, tp_size, dtype, config=...)` before `deepspeed.initialize`; Accelerate
(`accelerator.py`, deepspeed ≥ 0.16.4) does the same. Verified end-to-end with `Trainer` + the config below:

```json
"tensor_parallel": {"autotp_size": 2, "vocab_parallel_lm_head": true, "vocab_parallel_ce_backend": "fused_linear"}
```

## Results

Qwen2.5-0.5B (151,936 vocab, tied), HF `Trainer` (transformers 5.17.0, accelerate 1.15.0), TP=2, ZeRO-1, BF16,
gradient checkpointing, micro-batch 4 × 2,048 tokens, 50 % prompt-masked, 20 steps (mean of steps 6–20).

softcap (any cap, including 1.0) and ZeRO-3; non-finite activations at ignored positions affect neither loss nor
gradients; many-token BF16 parity on the accelerator.

Compatibility combos verified on TP=2: unit tests with ZeRO-0, FP32, Llama/Gemma3, tied and untied heads, eval and
no-label forwards; HF `Trainer` end-to-end with ZeRO-1, BF16 and FP32, gradient checkpointing on/off, 512–8,192
tokens per micro-batch (B70), and the four-backend `Trainer` comparison above on L20. ZeRO-3 and DeepCompile
`autotp` are rejected.

**Non-blocking: diagnostic warning for the unconsumed-capture case.**

The capture protocol assumes "training mode + labels ⇒ the forward must call `model.loss_function`". When a caller violates this (e.g. `Trainer(label_smoothing_factor=...)`, or a custom loop that reads `outputs.logits` and computes its own loss), the head has already returned empty logits and the failure surfaces far away (a `Dimension out of range` / NaN inside the caller's code), which is hard to attribute to the config.

Detecting "taken but never popped" in `disarm_capture` is nearly free and has no false positives — in a conforming forward the pair always occurs together, so `capture.hidden is not None` at the post-hook is the exact signature of a violation. Suggested:

```python
def disarm_capture(module, args, output):
    if capture.hidden is not None:
        logger.warning("vocab_parallel_ce_backend='fused_linear': labels were passed but the "
                        "installed loss never consumed the LM-head capture; outputs.logits is "
                        "empty (vocabulary dim 0). Compute the loss via model.loss_function or "
                        "use the 'torch' backend.")
    capture.reset()
```

No behavior change — it just moves the failure from an obscure error downstream to the root cause identified at the offending forward.

**Non-blocking: test for the all-ignored batch (`num_valid == 0`).**

A micro-batch where every label is `ignore_index` (e.g. a fully-masked prompt batch) currently passes safely thanks to three implicit guards scattered across two functions: the outer `max(1, ...)` in `_default_chunk_rows`, the empty `range` loop in the kernel, and `clamp(min=1)` on the mean path. Nothing pins this boundary down today, and it is the easiest thing to silently break when the compaction/chunking logic is refactored (e.g. nesting the `max(1, ...)` inside the `min` would yield `chunk_size=0` and crash in `range(0, 0, 0)`).

A small test — all-`-100` target → loss == 0, all-zero `reduction="none"` output, backward succeeds — would lock in the contract.
