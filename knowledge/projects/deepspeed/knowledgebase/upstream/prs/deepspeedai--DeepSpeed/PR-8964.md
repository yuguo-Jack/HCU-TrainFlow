# ZeRO-1/2: keep every request's gradients until the optimizer step

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8964) · state: open · merged: False

## Original PR description

Supersedes #8949. A caller can finish several requests with `engine.set_gradient_accumulation_boundary(True)` and call `engine.step()` only after all of them have contributed. ZeRO-1/2 must keep every request's gradients until that update, and must not carry the previous update into the next one.

This replaces the lazy auxiliary-buffer approach in #8949. That approach is cheaper for a single backward, but it can keep a stale host sum when a parameter is unused for a whole window, and it can drop an earlier ZeRO-2 request when a parameter misses the boundary backward. The accumulator here is the buffer the optimizer already owns.

## Root cause

- Non-offload ZeRO cleared `all_grad_tensors` at every boundary, so earlier requests were gone before `step()`.
- CPU offload treated the first backward of a new window as a refresh of the persistent host buffer only in some cases. A later request could add the previous window's values. `reset_cpu_buffers` did not zero that buffer.
- ZenFlow wrote each backward into whichever overlap buffer the current index selected. With the automatic update interval that index flips every backward, so one window was split across both buffers.

## Fix

- CPU offload adds each owned fragment into `single_partition_of_fp32_groups[i].grad` through one synchronous staging buffer. That partition gradient is the only persistent host accumulator. It is zeroed after the step consumes it, after overflow, and when `zero_grad()` discards the window.
- Non-offload ZeRO keeps reduced gradients until `step()`. Reentrant checkpoint phases still reread the cumulative `grad_accum` tensor and commit the backward once.
- Norm and overflow are recorded for every reduced parameter, including parameters that miss the boundary backward. Compact FP32 partitions are mirrored on every backward and zeroed with the window.
- ZenFlow accumulates in `partition.grad` and copies that sum into the selected overlap buffer at submit time. `reset_cpu_buffers` still zeros only the overlap buffer whose optimizer step has finished.
- `engine.zero_grad()` also clears the optimizer's retained window, including finalized `averaged_gradients`.

No config key changes. Clients do not need unmanaged gradient accumulation.

## Tradeoff against #8949

#8949 avoids an auxiliary allocation and a second copy when an update is a single backward. This change does not. Every offload backward does a synchronous staging copy and a host add, including the single-backward case. There is no second per-parameter accumulator: the existing FP32 partition gradient is reused. ZenFlow CPU offload holds one extra partition-sized host buffer so the window sum does not follow the overlap index.

ZeRO-3 was inspected and not changed. Its partitions accumulate in `__param_id_to_grad_partition`, and the optimizer offload copy stays deferred to the boundary. The standalone BF16 optimizer was inspected and not changed. It clears both low-precision and FP32 gradients in `zero_grad()`.

Open PRs checked on October 31, 2026: #8949 is the same bug with the lazy design this replaces. #8728 clears unowned offload scratch for low-precision masters. #8920 preserves FP32 folded gradients through FP32 accumulation. Neither is this request-lifetime fix. Follow-up coverage remains in #8957 and is not required to land this.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Avoid duplicating every ZeRO-1 gradient snapshot**

When `use_grad_accum_attribute` is enabled (notably ZeRO-1 with a higher-precision accumulation dtype), this branch clones `latest` into `_current_backward_grads` and then clones it again while constructing `all_grad_tensors`; with completed requests it additionally clones the full accumulated snapshot. Because `param.grad_accum` also remains live until the next forward, an ordinary backward can retain multiple full, unpartitioned gradient copies per rank, causing large-model jobs to OOM and defeating ZeRO's memory-saving purpose. Keep a single cumulative snapshot and avoid materializing duplicate per-request copies.
