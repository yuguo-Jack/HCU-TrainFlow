# Fix out-of-bounds row access in inference layer_norm/rms_norm kernels for hidden sizes <= 128

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8830) · state: open · merged: False

## Original PR description

Fixes #8828

## Summary
For hidden sizes <= 128 the inference norm launchers pack `256 / threadsPerGroup` rows into one thread block, but the kernels had no row bound. When `rows` is larger than that and not a multiple of it, the last block read its inputs and wrote its outputs for rows past the end of the tensors (e.g. fp32 hidden 64 or fp16/bf16 hidden 128 with 17 or 33 rows; see #8828).

This PR passes `rows` to `fused_ln`, `fused_residual_ln` (used by both residual launchers) and `rms_norm` / `pre_rms_norm`, computes the row index from the same expression the kernels already use for `block_offset`, and masks the global loads and stores of rows past the end. Those threads still take part in the reductions (masked loads return zeros), so the warp/block reductions are unchanged; there is no early return. Launch shapes (grid/block) are unchanged, and the launch macros just pass `rows` through.

## Why this is not a duplicate
- #8828 is the issue for this bug; no open PR addresses it (checked `gh pr list --search "8828 in:body"` and searches for the launcher names).
- #8827 (fp32 hidden 65-128 launched no kernel) adds the missing 32-thread branch and launches it one row per block; it does not touch the other branches. #8743 (rows == 0) adds an early return in the same launchers. Both touch the same files, so whichever merges second may need a trivial rebase. #8827 currently launches its 32-thread branch one row per block because the kernels had no row bound; with this PR merged that branch could use the default multi-row launch, but it does not have to change.

## Tests
Hardware: 1x NVIDIA GeForce RTX 5080 Laptop GPU (sm_120), driver 595.99.02, CUDA 12.8, torch 2.11.0+cu128, Python 3.12.3. `transformer_inference` JIT-built separately for master and this branch (`TORCH_CUDA_ARCH_LIST=12.0`, `MAX_JOBS=4`).

Test changes (`tests/unit/ops/transformer/inference/`):
- `test_layer_norm.py`, `test_rms_norm.py`: `seq_len` `[1, 128]` -> `[1, 17, 33, 128]` and `channels` gains `32, 64` in all five parametrizations, so fp32/fp16/bf16 at 4-, 8- and 16-thread sizes run with partially filled blocks.
- `test_layer_norm.py`: new `test_layer_norm_residual_cuda` calling the CUDA residual bindings directly (`_layer_norm_residual`, `layer_norm_residual_store_pre_ln_res`) for rows 17/33 at fp32 32/64, fp16 64/128 and bf16 128, since `LayerNormOp.layer_norm_residual*` are PyTorch implementations.

Commands (from `tests/`): `pytest -m inference_ops unit/ops/transformer/inference/test_layer_norm.py` and `... test_rms_norm.py`.

The 8 failures on master are `test_layer_norm_residual_cuda[store_pre_ln_res=True]` at exactly the partially filled shapes (fp32 32 / rows 33, fp32 64 / rows 17 and 33, fp16 64 / rows 33, fp16 and bf16 128 / rows 17 and 33): the overrun of the normalized output lands in the adjacent `res_output`. The other new cases (including all of `test_rms_norm.py`) pass on master too even though they overrun, because the stray accesses happen to hit unused memory; the memcheck table below is what shows the overrun.

On a normal pytest run, these added RMS shapes and the analogous base layer-norm shapes do not detect the defect being fixed: the tests only compare values inside the returned logical tensors, while the surplus groups write after those tensors, so the parent implementation passes all of these RMS cases unless it happens to corrupt another allocation (the reported baseline is 360/360). Consequently `fused_ln`, `rms_norm`, or `pre_rms_norm` can lose its `valid_row` guard while CI remains green; use a canary/guard allocation or a sanitizer-backed regression that reliably fails on the old kernels instead of only broadening the parameter matrix.

Agreed. The new seq_len/channels cases pass on master under plain pytest; only compute-sanitizer memcheck catches the overrun, and memcheck isn't part of the default CI.

I've added canary tests that fail under plain pytest:
- New tests: `test_layer_norm_no_write_past_last_row` and `test_rms_norm_no_write_past_last_row`.
- Helper: `run_with_output_canaries` in `inference_test_utils.py`.
- Coverage: all five bindings (`layer_norm`, `_layer_norm_residual`, `layer_norm_residual_store_pre_ln_res`, `rms_norm`, `pre_rms_norm`), rows 17 and 33, at fp32 hidden 32/64 and fp16/bf16 hidden 64/128.
- How it works:
  - The outputs are allocated inside the bindings, so the helper uses a private `torch.cuda.MemPool` to place each output directly in front of a caller-owned canary tensor filled with a finite sentinel (1000.0).
  - It asserts that the layout holds, and then that the canary is unchanged after the call.
  - The tests skip when `MemPool` isn't available.

Results:
- Master (unguarded kernels): 40 failed / 10 passed in each of 20 runs. The 10 passes are rows 17 at the 8-thread sizes (fp32 32, fp16 64), which fit in one 32-row block and don't overrun.
