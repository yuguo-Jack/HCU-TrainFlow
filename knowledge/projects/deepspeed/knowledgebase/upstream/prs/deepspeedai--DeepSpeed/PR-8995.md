# Fix quantized storage of nontrainable weights in ZeRO-3

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8995) · state: open · merged: False

## Original PR description

Fixes #8990

## Summary

The change has three parts:

1. **Fix three device-agnostic defects in the `zero_quantized_nontrainable_weights` path** (int8 storage of frozen weights, used by LoRA + ZeRO-3).
   - Quantize the partition only after the real weights have been copied in. Previously the code quantized an uninitialized buffer and then overwrote it with a dtype-cast copy of fp16/bf16 weights, truncating values in (-1, 1) to zero in the int8 storage. The model silently output zeros and the loss never moved.
   - Assign the quantizer on the `Init` class so the no-gather handles used on single-rank runs can dequantize (`AttributeError: type object 'Init' has no attribute 'quantizer_module'`).
   - In coalesced buckets whose params carry their own quantized storage, dequantize each param with its own scale and re-quantize the bucket uniformly. A flat dequantize with concatenated per-param scales computes a wrong `elems_per_group` whenever group counts differ (silent on CUDA, divisibility assertion on NPU). Also cast the fetched weights to `param.dtype`, not the int8 storage dtype. The per-param dequantize stays in the fp16 wire dtype because a quantized bucket may mix parameter dtypes, and fully padded partitions are zeroed before the bucket re-quantize so uninitialized padding cannot feed the shared group scale.

2. **Reject CPU parameter offload with this flag at init**, because the quantizer runs on the accelerator and the partition would not stay on the CPU. NVMe parameter offload is left unquantized with a warning.

3. **Extend `NPUQuantizer` to the int4/asymmetric contract and round half to even**, matching the CUDA kernel (`__float2int_rn`). `quantize` now packs int4 two per byte; `dequantize` accepts N-D packed inputs and asymmetric params; the reference test in `tests/unit/ops/quantizer/test_quantize.py` covers int8/int4, symmetric/asymmetric. Production hpZ/qgZ continue to use symmetric int8. The half-to-even change is adapted from #8764 (author: vineethsaivs).

## Motivation

`zero_quantized_nontrainable_weights` is the option that makes LoRA fine-tuning cheap in ZeRO-3: frozen base weights are stored as int8 and dequantized on fetch. On master the option is effectively unusable:

- Frozen weights are all zeros in storage, with a scale derived from uninitialized memory. Training runs, the loss is `mean(label**2)`, and gradients are zero -- no error is raised. On NPU the same path later fails even harder: a second fetch leaks int8 storage into matmul and raises `Tensor mat2 not implemented for DT_INT8`.
- Single-rank runs crash immediately.
- Multi-parameter buckets either corrupt values or assert, depending on backend.

The rounding change addresses a separate but related accuracy issue in the same quantizer: truncation biases int4 qgZ gradients low (sum ~0.85 of the exact value in a 2x2 CPU simulation), while the CUDA kernel rounds.

- Every case is marked `inference_ops`, so `pytest.ini` deselects them when the command is run verbatim; use `-m "inference_ops or not inference_ops"`.
- The file is device-agnostic and collects on NPU. `NPUQuantizer.quantize` now covers int4 (two per byte) and asymmetric scale+zero point, so the full 242-case matrix runs on NPU as well as CUDA.
- The new rounding cases use the accelerator-resolved `QuantizerBuilder` (`quantize` for int8, `swizzle_quant` for int4), so they run against CUDA or NPU without importing a platform module.
- CUDA's reciprocal scale differs from the torch reference by 1-2 ULP. The test compares scales with a small tolerance and checks the dequantized output bitwise against the kernel's own params; a truncate-vs-round change still changes `q` and fails.

- All quantized runs: 310/310 int8 partitions on 0.6B and 1.7B, 398/398 on 4B, 98.8% non-zero on both devices.
- Init-allocated savings (quantized vs control): GPU 306 / 819 / 1,918 MiB, NPU 295 / 763 / 1,889 MiB. The frozen storage itself halves at every size, and the byte counts are identical across devices.
- Training peak is lower with quantization in every GPU run. On NPU the 1.7B peak is 218 MiB higher (6,207 vs 5,989) because peak includes the fp16 all-gather buffers and bucket re-quantize transients; treat peak as workload-dependent, and init-allocated/storage as the stable savings.
- 0.6B checkpoint (8 steps): GPU replay 8.1402, NPU replay 8.1354 (step 7 repeats step 5); both ALL PASS. Frozen storage is zeroed before the load, so the continuation proves restoration.
- The coalesced-bucket re-quantize path runs repeatedly (quantize counter +9 per step on 0.6B, +42 per step on 1.7B).

The NPU also ran the same three models with pretrained weights: init allocated 1,307 / 1,600, 1,845 / 2,608 and 2,952 / 4,840 MiB, identical frozen storage, and losses 0.932 -> 0.021 / 0.863 -> 0.001 / 0.718 -> 0.003 (control 0.934 -> 0.015 / 0.883 -> 0.000 / 0.705 -> 0.001). The storage and memory numbers agree with the random-init runs within 1-8 MiB.

### Not tested

- Pretrained weights on GPU: the GPU real-model runs use random-init weights. Storage and memory metrics match the NPU pretrained-weight runs; loss values are not comparable to a pretrained model.
- bf16 and fp32 storage: not validated. `stage3.quantize_nontrainable_params()` still asserts fp16, so the post-init bf16 workflow remains out of scope.
- NVMe parameter offload: not exercised by the regression test; quantization is skipped with a warning.
- Padding: the in-repo test does not construct partial or fully padded partitions; those audit fixes are validated by inspection and the end-to-end runs, not by a targeted regression case.
- `stage3.quantize_nontrainable_params()` (the post-init re-quantize workflow) is not exercised by the in-repo test.
- hpZ `ds_secondary_tensor` (`_partition_param_sec`) has no targeted quantization test; the hpZ suites cover the primary path.
- Full `save_checkpoint`/`load_checkpoint` round trip is covered by the external Qwen3 script; the in-repo test uses `load_module_state_dict(..., fetch_z3_params=True)`.
- Cross-world-size checkpoint loading, TP/PP, and accelerators other than A100 and 910B4.

## Offload behavior

- CPU parameter offload + `zero_quantized_nontrainable_weights`: rejected at init with `NotImplementedError`; the in-repo regression test covers this path. The quantizer runs on the accelerator, so the partition would not stay on the CPU.
- NVMe parameter offload: quantization is skipped and a warning is emitted; frozen partitions keep their unquantized dtype. This combination is not exercised by the regression test.

## Compatibility and risk

- No API, config, or checkpoint format change.
- `zero_quantized_nontrainable_weights` users on CUDA get correct storage instead of zeros; single-rank and multi-param buckets start working.
- hpZ (`zero_quantized_weights`), autocast communication and the general fetch path are unchanged when the flag is off; the regression suites above pass.
- CPU offload with the flag now fails early instead of silently moving the storage to the accelerator; NVMe offload skips quantization with a warning.
- Existing quantized checkpoints: storage produced by the old code was all zeros and unusable, so no compatible checkpoint exists to preserve.
