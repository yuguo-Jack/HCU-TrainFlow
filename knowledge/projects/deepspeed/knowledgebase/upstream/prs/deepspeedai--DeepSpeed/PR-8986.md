# ZeRO-3 CPU offload: fix the step() device memory regression from #8840

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8986) · state: closed · merged: False

## Original PR description

## Summary

#8840 copies each pinned CPU master partition to the device in float32 and casts it there. It moves the whole sub-group at once, so with `offload_optimizer.pin_memory: true` (the default) `step()` needs a float32 device temporary of a whole sub-group: up to 3.73 GiB at the default `sub_group_size` of 1e9. The description of #8840 says the copy goes in pieces of 2**26 elements (0.25 GiB); the merged code does not. No release has #8840 yet.

This PR copies in pieces of 2**26 elements, in order on one stream, so each piece reuses the memory of the previous one. ZeRO-1/2 cast on the host into a pinned 16-bit buffer and have no device temporary; SuperOffload and ZenFlow's overlap step copy the masters their own way.

No open issue or PR covers this.

## Fixes

Before → after, 1 GH200, bf16, ZeRO-3 with `offload_optimizer: {device: cpu, pin_memory: true}`, base `1a956270f`. Device memory that `step()` takes on top of what is allocated before it:

1. 1.0B parameters, default `sub_group_size` (one sub-group of 1007M elements): 3.75 → 0.25 GiB.
2. 134M parameters: 0.50 → 0.25 GiB.

The step time does not change (1.0B: 0.178 → 0.178 s; copy-back 12.7 → 12.8 ms).

Read at `8e6295a1`. This looks right to me: the pieces are views of the pinned buffer, so `non_blocking` still applies, and since they run in order on one stream, the allocator can reuse each piece's temporary for the next one.

Your test skips on the CPU accelerator, so I checked the chunking directly. I called `_copy_pinned_master_to_device` with `PINNED_MASTER_COPY_NUMEL` patched to 1000, a no-op event (the CPU accelerator has none) and an fp32 source of 0, 1, 999, 1000, 2000 and 2500 elements: the bf16 destination equals `src.to(torch.bfloat16)` every time, tails and the empty case included. I can't check the device-memory numbers here. A small test along those lines, with the constant patched down, would let the CPU job cover the tail logic too.
