## Original PR description

# ZeRO-3: reuse the weight partition as the master copy when it already has the master dtype

## Summary

`DeepSpeedZeroOptimizer_Stage3._create_fp32_partitions` has a branch that uses a sub-group's weight partition as its
master copy when the two would be identical (same dtype, on the device). Its check compared
`tensor.device == self.device`, where `self.device` is a string such as `"cuda:0"`
(`get_accelerator().current_device_name()`). A `torch.device` never equals a string, so the branch never ran, and
ZeRO-3 kept a second copy of every partition. This PR compares with `torch.device(self.device)`.

The branch now runs in these ZeRO-3 runs without optimizer offload:

| Run | Config | Device memory saved per rank |
|---|---|---|
| Plain fp32 | no `bf16`, `fp16` or `torch_autocast` section | 4 bytes per parameter in the rank's partition |
| fp32 model under torch autocast | `torch_autocast` enabled, no `bf16` / `fp16` section | 4 bytes per parameter in the rank's partition |
| bf16 master weights | `"bf16": {"enabled": true, "bf16_master_weights_and_grads": true}` | 2 bytes per parameter in the rank's partition |

Runs with `"bf16": {"enabled": true}` and fp32 master weights are not affected: their partitions are bf16 and the
master copy is fp32, so the branch does not apply with or without this PR. Runs with optimizer offload or NVMe are not
affected either: those branches come first.

In these runs the master and the weight partition are the same tensor, so `offload_states` / `reload_states` must not
move them apart. This PR makes those sub-groups move with `lp_params` (details below).

## Duplicate check

Searched open pull requests on 2026-11-01 ("master copy stage3", "fp32_partitioned_groups_flat",
"torch.device self.device", "offload_states alias", "master weights autocast zero3"). None changes this comparison or
`offload_states`. #8892 also edits `stage3.py`, but only the restore of fp32 masters from a checkpoint.

## The change

`deepspeed/runtime/zero/stage3.py`:

| Where | What |
|---|---|
| `_create_fp32_partitions` | Compare with `torch.device(self.device)`. Record the sub-groups whose master is the weight partition in `aliased_fp32_sub_groups`. |
| `offload_states` / `reload_states`, `hp_params` | Move only the masters that have their own storage (`_fp32_partitions_with_own_storage`). An aliased master moves with `lp_params`; moving it alone would split it from the weights. |
| `offload_states` / `reload_states`, `lp_params` | After `lp_param_buffer` moves, point each aliased master at its slice of the moved buffer again (`_point_aliased_fp32_partitions_at_lp_buffer`). The master stays the tensor the optimizer holds. |
| `offload_states`, `hp_params` without `lp_params` | Log a warning once: the aliased sub-groups stay on the device, so the call frees no memory for them. The DeepSpeed logger prints only warnings by default, so an info log would not show. |

`docs/code-docs/source/zero3.rst`: the `hp_params` entry says that, in these runs, the fp32 copies move only with
`lp_params`.

## Behaviour changes

1. **Memory.** As in the Summary table.
2. **`offload_states` with `hp_params` alone** frees no device memory for aliased sub-groups (the warning and the docs
   say so). With `lp_params` in the same call, or with `include=None`, the weights and their masters move together.
3. **`GatheredParameters` edits now persist in these runs.** A weight edit under
   `deepspeed.zero.GatheredParameters(..., modifier_rank=...)` writes into the weight partition, which is now the
   master. So the next `step()` updates the edited value. Before this PR, `step()` copied the separate master back
   over the edit, unless `refresh_fp32_params()` was called. This is intended: there is no second copy to restore
   from. Runs with bf16 / fp16 weights and fp32 masters keep the old behaviour. `refresh_fp32_params()` still works;
   for an aliased sub-group it copies the partition onto itself.

## Measured

CPU offload. The fix was tested in a DeepSpeed study tree before this branch existed.

## Tests

New tests, all with 2 ranks and ZeRO-3 without optimizer offload:

| Test | What it checks |
|---|---|
| `TestZero3AutocastSharesMasterWeights` (`test_zero.py`) | torch autocast (bf16), fp32 weights: every master partition is the weight partition itself; 2 training steps run. |
| `TestZero3Fp32SharesMasterWeights` (`test_zero.py`) | Plain fp32: every master partition is the weight partition; 3 steps match `torch.optim.Adam` on an unsharded copy (losses and final weights, rtol 1e-5, atol 1e-6, gradient clipping off). |
| `TestOffloadStatesZero3AliasedMaster` (`test_offload_states.py`; fp32 and autocast, `pin_memory` False / True) | Offload and reload `[lp_params]`, `[hp_params]`, `[lp_params]`, `[hp_params, lp_params]`, then all states, with a step before each. After each round trip the weights are bitwise unchanged and each master is still the weight partition inside `lp_param_buffer`; offloading `lp_params` frees at least the weights' bytes. At the end the weights equal those of a run without offloading, bitwise. The autocast case skips on accelerators without bf16. |

On master the first two fail at `assert master is model_partition`, and the third fails at its first check that the
master is the weight partition.

- 0z5a · COMMENTED · 2026-10-18T15:05:07Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8842#pullrequestreview-5563587468)

The fix itself is right: `torch.device == str` was always False, so the alias branch was dead. But that dead branch was also what kept hp and lp storage separate everywhere, and `offload_states` / `reload_states` rely on that. Turning it on breaks the offload round trip, and it now also fires for plain fp32 ZeRO-3, not only autocast / bf16-master runs.

**1. [blocking] `offload_states` / `reload_states` desync the weights once the partitions alias** — [`stage3.py:1162`](https://github.com/deepspeedai/DeepSpeed/blob/1409708dc4688bea5f035c1de545f365132225b7/deepspeed/runtime/zero/stage3.py#L1162), [`stage3.py:3881`](https://github.com/deepspeedai/DeepSpeed/blob/1409708dc4688bea5f035c1de545f365132225b7/deepspeed/runtime/zero/stage3.py#L3881), [`stage3.py:3948`](https://github.com/deepspeedai/DeepSpeed/blob/1409708dc4688bea5f035c1de545f365132225b7/deepspeed/runtime/zero/stage3.py#L3948)

Once `fp32_partitioned_groups_flat[i] is fp16_partitioned_groups_flat[i]`, offloading `hp_params` rebinds `.data` of the shared tensor while the `ds_tensor`s still point into `lp_param_buffer`. After the next `step()` they get repointed to the new storage, `lp_param_buffer` goes stale, and a later `lp_params` offload/reload restores stale weights.

Repro on the CPU accelerator (1 rank, plain fp32 `nn.Sequential`, Adam, ZeRO-3, no optimizer offload): step → offload/reload `[hp_params]` → step → offload/reload `[lp_params]`. On this branch the module weights change by up to 1e-2 across the `lp_params` round trip and no longer share storage with `lp_param_buffer`; on the merge base the same sequence is exact.

Also, while aliased, offloading `lp_params` can't free device memory (the master still references the old storage), and after a reload the two lists are separate tensors again, so the saving silently disappears. `TestDynamicOffloadStatesZero3` only runs bf16, where nothing aliases, so it doesn't catch this. Suggest moving hp and lp together for aliased groups (and re-aliasing after reload), plus an fp32 / autocast parametrization of that test.

**2. [should-fix] This now applies to every plain fp32 ZeRO-3 run** — [`stage3.py:1162`](https://github.com/deepspeedai/DeepSpeed/blob/1409708dc4688bea5f035c1de545f365132225b7/deepspeed/runtime/zero/stage3.py#L1162)

The branch also fires without any bf16 / fp16 / autocast section, but the summary lists only autocast with an fp32 model and bf16 master weights, so reviewers may read plain fp32 runs as untouched. Please call that out, and add a numerical parity test (aliased vs. a forced copy over a few steps) in addition to the identity check in `TestZero3AutocastSharesMasterWeights`.

**3. [question] `GatheredParameters` edits now persist in fp32 runs**

With the alias, weight edits under `GatheredParameters(..., modifier_rank=0)` now go straight into the master copy in fp32 runs. On master the next `step()` overwrote them unless `refresh_fp32_params()` was called (in my check the weight mean is -0.011 on master vs. 0.500 kept here); bf16 runs keep the old behaviour. Is that intended? If so it deserves a note. Related: with #8843 the fp32 sub-groups from `keep_in_fp32_modules` will alias too, and #8843 still allows `hp_params` offload for mixed dtypes, which is the half that breaks the alias.
