# fix: inference norm missing threadsPerGroup==32 dispatch + ROCm 7.2.2 bf16 ABI

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8906) · state: closed · merged: False

## Original PR description

## What

Two independent fixes to the v1 inference norm kernels.

**1. Missing `threadsPerGroup==32` dispatch (layer_norm.cu, rms_norm.cu)**

`launch_fused_ln`, `launch_fused_residual_ln`, `launch_fused_residual_ln_store_pre_ln_res`, and `launch_rms_norm` all dispatch on `threadsPerGroup` with branches for {1, 2, 4, 8, 16} only. For `float32` inputs with `elems_per_row` in [65, 128], `T_per_load=4` gives `threadsPerGroup=32`, which falls through every branch — no kernel is launched and the output tensor holds uninitialized memory (silent numerical corruption).

Reproduced on MI350X (gfx950, ROCm 7.2.2): errors of 3–8 units for H=80–128 with `dtype=float32`.  
Fix: add `else if (threadsPerGroup == 32)` to all four dispatch tables.

Real-world trigger: per-head Q/K RMSNorm in EXAONE 4/4.5 with head_size 64 or 128 (related to #8886).

**2. ROCm 7.2.2 bf16 ABI build failure (conversion_utils.h)**

`conversion_utils.h` includes `cuda_bf16.h` guarded only by `BF16_AVAILABLE`. Hipify translates this to `hip_bf16.h` in `conversion_utils_hip.h`. When `op_builder` compiles `.cpp` files with plain `g++` and `-DBF16_AVAILABLE -D__HIP_PLATFORM_AMD__`, it pulls in `amd_hip_bf16.h`, which on ROCm 7.2.2 requires Clang-only builtins (`__builtin_elementwise_fma`, `__builtin_elementwise_ceil`, etc.) and a `__bf16` vector ABI not available under `g++`, causing the entire `inference_core_ops` extension to fail to build.

Fix: add `&& !defined(__HIP_PLATFORM_AMD__)` to match the identical pattern already in `ds_kernel_utils.h` (which has a comment explaining exactly this problem). Hipify will propagate the guard correctly to the generated `_hip.h` file.

## Test

Repro script for fix 1: verified H=80–128 (float32) produce zero error after the fix on gfx950.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Keep bfloat definitions available to HIP device compilation**

On a ROCm build of an op that leaves `enable_bf16` enabled, such as `QuantizerBuilder` or `FPQuantizerBuilder`, hipcc itself defines `__HIP_PLATFORM_AMD__`, so this condition removes the bfloat header from device translation units too. `conversion_utils.h` nevertheless compiles its `BF16_AVAILABLE` specializations using `__nv_bfloat16`, `__nv_bfloat162`, and their intrinsics; `ds_kernel_utils.h` only forward-declares the scalar type, and these builders include conversion/reduction before any bfloat definition, so they now fail to compile. Distinguish host-only g++ from hipcc or provide the definition before this header.
