# [Hybrid Engine] Enable XPU graph capture behind the explicit opt-in

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/9007) · state: open · merged: False

## Original PR description

Follow-up to #8980. Wire the XPU accelerator into the explicit graph-capture opt-in that #8980 introduces.

## Background

`XPU_Accelerator` currently stubs the graph interfaces: `create_graph()` returns `None`, capture is a no-op context, and replay does nothing, so HybridEngine always runs eager on XPU. Upstream PyTorch ships XPU stream capture since 2.11 (`torch.xpu.XPUGraph`, the `torch.xpu.graph` capture context, and `torch.xpu.is_current_stream_capturing()`), so the capability exists but was never connected. Note #8980 does not regress XPU — it opts XPU out of a path that was never functional — this PR turns the real support on.

## Change

- `create_graph()` returns `torch.xpu.XPUGraph()` when available (`None` otherwise, preserving eager on older torch).
- `capture_to_graph()` delegates to `torch.xpu.graph(graph, pool, stream)`; `replay_graph()` to `graph.replay()`.
- `is_current_stream_capturing()` delegates to `torch.xpu.is_current_stream_capturing()`.
- `is_graph_capture_supported()` returns `torch.xpu.is_available() and hasattr(torch.xpu, 'is_current_stream_capturing')`. Both checks are required: torch builds without an XPU backend stub `torch.xpu` with dummy types where the query exists but raises when called, and pre-2.11 builds expose no query at all — either way XPU stays opted out and keeps the eager fallback.
- Contract test in `tests/unit/accelerator/test_accelerator_graph.py`: the opt-in matches torch.xpu's actual capture capability (runs green on any accelerator; pins both a hardcoded-`True` regression and a forgotten opt-in).

## Testing

Hardware: Intel Arc Pro B60 ×2 (single card used), torch 2.15.0+xpu, Python 3.12.16, transformers 5.22.1, Ubuntu 26.10. Branch under test: this PR stacked on #8980 (ec6fc5de).

- `DS_ACCELERATOR=xpu pytest tests/unit/accelerator/test_accelerator_graph.py -v` — 3 passed, 1 skipped (the eager-fallback test skips by design once XPU returns a real graph). `test_graph_capture_replay_roundtrip` exercises real XPUGraph capture → replay on device, including the in-capture `is_current_stream_capturing()` query.
- `DS_ACCELERATOR=xpu pytest tests/unit/runtime/rollout/test_hybrid_engine_rollout.py -q` — 50 passed.
- `tests/unit/hybrid_engine/test_he_graph.py` skips module-level on XPU: `InferenceBuilder` (transformer inference kernels) is not implemented for XPU — pre-existing on master, unrelated to this change.
- CPU-only machine (torch 2.12.1+cpu): same accelerator suite 3 passed, 1 skipped; dummy-type `torch.xpu` correctly stays opted out.
- Rollout micro-benchmark (card 0, GPT-2 small 124M bf16, 8 prompts × 64 new tokens, continuous_batch_size=4, greedy): eager 466 tok/s vs graph capture 2109 tok/s — **4.53×**. Outputs: prompts identical; 22/512 response tokens differ in 2/8 rows with first divergence at new-token 31/35, consistent with bf16 numerics cascade rather than a logic error. Note: running against transformers 5.22 additionally required stacking #8852 (`DeepSpeedStaticCache.get_query_offset`) in the validation tree; that fix is independent of and not included in this PR.
