# [rl] Run Verifiers groups in rollout workers (12/14)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5511) · state: open · merged: False

## Original PR description

**TLDR:** Verifiers groups now run in rollout worker processes, like native groups, so the controller receives finished groups only. At ~62 Verifiers calls/s on 8 x H100, the controller's CPU drops from 13.9 to 3.9 s per training step and its GC from 0.78 to 0.12 s.

**Problem**
1. **Native groups run in worker processes.** The controller sends a group to a worker and gets one `RolloutGroup` back.
2. **Verifiers groups run in the controller.** `VerifiersRollouter` calls `EnvClient.run` once per rollout in the controller process.
3. **What comes back.** Each call returns the whole episode (token ids, masks and logprobs per turn), which the controller decodes and converts.
4. **How much.** 64 prompts x 16 samples, 512 tokens: the env client's reply decoding held the controller's GIL 4.6% of the time (all threads: 20.2%) in a 60 s profile.

**Solution**
1. `VerifiersRolloutWorker`, a `RolloutWorker` subclass, owns the env client, `run_group`, `_run_single_rollout` and the trace conversion.
2. `VerifiersRollouter.setup_async` starts the EnvServer, then spawns the workers with a config that carries its address (`Rollouter.setup_async(worker_config=...)`).
3. One shared EnvServer; each worker opens its own client to it.
4. No in-controller mode: `VerifiersRollouter.Config` drops its pool overrides and gets native's 4 workers x 4 threads. `Config.worker` must stay None.
5. A cancelled group stops on its worker (PR 11), which cancels each `EnvClient.run` and waits for every rollout's release.
6. Unchanged: the controller code, generators, router, recipes and native rollouts.

```text
before   controller: EnvClient.run per rollout; env server --episode--> controller (decode, convert) -> batcher
after    controller --run_group--> rollout worker (same call as native)
         worker: EnvClient.run per rollout; env server --episode--> worker (decode, convert)
         worker --finished RolloutGroup--> controller -> batcher
```

**Results**
Numerics: bitwise vs main. Verifiers DAPO-Math training samples are byte-identical on CPU with each group run by `VerifiersRolloutWorker.run_group`. On real Monarch processes (2 rollout workers), the rollouts equal the in-process run field by field; their pickle bytes differ only because objects unpickled from Monarch share references differently.

This stack on Verifiers 0.4.0 (its top PR, one 5-step run): 3.6 s controller CPU per step. GC and loop lags need timers this stack doesn't carry (an earlier run of the same changes on 0.4.0: 0.11 s GC per step, no lags).

You may ask:
- Why subclass `RolloutWorker`? `spawn_rollout_workers` takes a `RolloutWorker.Config`, and the subclass reuses `rubric`, `advantage` and `score_group`. Cost: the inherited `message_env` and `token_env` are unused.
- Why a `worker_config` keyword? The worker config needs the env server's address, known only after `start()`.
- Why one shared EnvServer? One per worker multiplies Verifiers' `serve.max_concurrent` and sandbox pools by the worker count, and leaves orphan server processes when the mesh stops.
- Why drop the in-controller mode? With model calls over HTTP, it only kept the trace stream on the controller.

NOTE:
- Each `EnvClient` decodes one reply at a time, so `worker_pool_size` sets how many traces decode in parallel. Recipes at 3+ nodes likely need 8 or more (not measured).
- Cancelling a Verifiers group doesn't stop runs already queued on its env server (~45 s of new rollouts at shutdown, on main too). A mid-training cancel trigger needs that fixed first.
- A sibling cancelled inside `acquire_rollout` can leak one unit of router load if its `acquire` lands after `release_groups`.
- A cancelled Verifiers rollout has no trace ids, so its held KV and folded metadata wait for the group's `release_groups`.
- Verifiers' failed-rollout warnings now print from the worker processes, and the rubric's reward classes must import there (today: `RewardFromVerifiers`).
- A worker never closes its `EnvClient` (process exit does).
- GPU: one 5-step run at `worker_pool_size=4`; 8 workers and the 8k-token recipe were not run.

A general comment:

A theme in this stack is on how to manage the the serialization cost. We should look into the lazy deserialization pattern, so we can bundle passthrough fields into a lazy object, and only deserialize them when we have to. 

Monarch already has zero-copy optimization on pickling bytes, and potentially could do more. So this is a area we could make it quite optimal.
