# Support HF generation tags in HFBackendTokenizer chat templates

[Upstream PR](https://github.com/pytorch/torchtitan/pull/4992) · state: closed · merged: True

## Original PR description

> _Drafted by Claude (AI) for @egeboy35._
>
> Some HF chat templates wrap assistant turns in `{% generation %} ... {% endgeneration %}` (SmolLM3-3B and LFM2.5-1.2B `chat_template.jinja`, TRL's `*_training.jinja`). transformers registers that tag to build assistant masks. torchtitan's Jinja environment does not, so `HFBackendTokenizer` raises `TemplateSyntaxError` while auto-loading such a tokenizer directory.
>
> Per review, the change is now confined to `experiments/transformers_modeling_backend/tokenizer.py`. `HFBackendTokenizer.set_chat_template` rewrites the tags into `{% with %}` / `{% endwith %}`, keeping the `-`/`+` whitespace-control markers, and then calls `super().set_chat_template()`. `torchtitan/components/tokenizer.py` is untouched. A with-block also scopes a `{% set %}` inside it to the block, as transformers does.
>
> Test Plan:
>
> Run locally without torch (torch cannot be imported on this machine). The real `components/tokenizer.py` and this file were loaded with only `tokenizers` and `torchtitan.config` stubbed. SmolLM3-3B, LFM2.5-1.2B and the two TRL training templates render identically to transformers with `add_generation_prompt` False and True, also with every tag rewritten as `{%- generation -%}`, `{%+ generation %}`, `{%generation%}` and similar forms. Templates without the tag (Llama-3.2, Qwen3, OLMo-3, LFM2, Seed-Coder) are unchanged by the rewrite and render exactly as on main. The new test fails on main with `TemplateSyntaxError` and passes with this change. `pre-commit run --files` passes on both files (lychee skipped). pyrefly, run separately, reports the same errors as on main.
>

### Correctness

- **The override is reached on auto-load.** `HuggingFaceTokenizer.__init__` calls `self.set_chat_template(...)` (`torchtitan/components/tokenizer.py:164,166`). Because that call goes through `self`, Python uses the subclass override, including during `super().__init__()`. So the case that failed before, auto-loading a tokenizer directory whose `chat_template.jinja` has these tags, is the one this fixes.
- **The regex matches only what it should.** `(\{%[-+]?\s*)(end)?generation(\s*[-+]?%\})` needs `generation` to be the only word in the tag. It will not touch `{% set generation = ... %}`, `{{ generation }}`, or `{% generation_foo %}`. It also keeps the `-`/`+` whitespace markers, so `trim_blocks`/`lstrip_blocks` behave as in the original template. Because `\s` includes newlines, tags split across lines are handled too.
- **`{% with %}` is a sound replacement.** Jinja accepts `{% with %}` with no assignments. Like transformers' `AssistantTracker` (which parses the body into a `CallBlock`), it scopes any `{% set %}` inside the block to that block. Without mask tracking, output should match transformers.
- **No assistant-mask dependency in torchtitan.** I found no code in torchtitan that reads `return_assistant_tokens_mask` or masks produced from generation tags. The chat dataset builds its masks separately (`test_chat_dataset.py:344`), so treating the tag as a no-op loses nothing.
- **The test's import will work in CPU CI.** Importing `...transformers_modeling_backend.tokenizer` runs the package `__init__`, which imports `transformers` through `model.py`. That's fine: `transformers` is in `requirements-dev.txt`, and `test_embedding.py:151` already imports from this package the same way.

### Nits / suggestions

1. **Make the test assert actual output** (`tests/unit_tests/cpu/test_tokenizer.py:539-562`). Right now it only checks `render(tagged) == render(untagged)`, so a template that renders wrongly in both forms would still pass. One extra `assertEqual` against the literal expected string would fix that, e.g. `"<|im_start|>user\n...<|im_end|>\n<|im_start|>assistant\n...<|im_end|>\n"` built from `SAMPLE_MESSAGES`. Optionally, also cover one whitespace-control variant such as `{%- endgeneration -%}`, since keeping those markers is the subtle part of the regex.
2. **Point to where the tag comes from** (`tokenizer.py:38-39`). Naming the upstream source in the comment would help future readers check behaviour, e.g. `# See transformers.utils.chat_template_utils.AssistantTracker`.
3. **Core `HuggingFaceTokenizer` still fails on these templates.** That is the scope agreed in review, but it means SmolLM3 / LFM2.5 / TRL `*_training.jinja` templates still raise `TemplateSyntaxError` through the base tokenizer, e.g. in core SFT. Please confirm that limit is intended. A short TODO here or a follow-up issue would keep it from being forgotten.
4. **Clean up the commit message.** It names a local script that isn't in the repo (`C:/Users/egeme/Desktop/pytorch/.venv/Scripts/python.exe verify_a1.py`). Please trim that when squashing.
5. **Edge case, no action needed:** tags inside a `{% raw %}` block would also be rewritten. No real template does this.

### Re-check of the new test

I traced the expected string through the base Jinja env (`trim_blocks=True`, `lstrip_blocks=True`, `components/tokenizer.py:75-76`):
- `{{ msg.role }}\n{% if ... %}`: the `\n` comes after a variable expression, not a block tag, so `trim_blocks` keeps it.
- `{% if ... %}{%- generation %}`: nothing comes before the `-`, so it strips nothing. `<|im_end|>\n{% endgeneration %}`: `trim_blocks` only removes the newline *after* a block tag, so the `\n` stays.
- The result is exactly `"<|im_start|>user\nHello<|im_end|>\n<|im_start|>assistant\nHi there<|im_end|>\n"`, matching `SAMPLE_MESSAGES` (`test_tokenizer.py:30-33`). Both assertions should pass.
- `tok.apply_chat_template` runs after the `TemporaryDirectory` is removed. That is fine because both the template and the tokenizer are loaded into memory in `__init__`.

A one-line `subTest` over `{%generation%}` / `{%- endgeneration -%}` would lock in the `[-+]?\s*` handling in the regex, which is the subtle part.
