# [pipeline] Make loss-count ownership explicit

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5327) · state: open · merged: False

## Original PR description

Prepared with AI assistance.

Loss normalization belongs to stages that evaluate the objective. Require
denominators on those owners, and discard unused denominators on other ranks
before device conversion or optimizer-step mutation. Preserve existing RL,
TorchFT and direct engine callers instead of requiring an unrelated API change.
Routing denominators remain globally reduced on every MoE stage.

Keep token-seen and auxiliary metric collectives on all ranks; reduce and log
loss/count metrics only on owners. Non-owners retain the existing explicit
loss sentinel. No throughput improvement is claimed for the smaller payload.

<details><summary>Details</summary>

### What I checked and found safe
- **Collective consistency:** the `dp` and `loss` meshes are both per PP stage (`parallelism_context.py:339,387`), so every rank in a collective makes the same `owns_loss` decision. The payload is smaller on non-owners, but within each mesh it is the same everywhere. Moving the `ntokens_seen` `dist_sum` ahead of the loss reductions keeps the same order on all peers.
- **CUDA graphs:** `None` is a pytree node with no leaves, so `CUDAGraphInputSpec` sees a stable structure on non-owners (always `None`) and on owners (always a tensor).
- **Loss kwargs on non-last stages:** only loss functions read `global_loss_token_counts` (`loss.py`, `MTPLoss`, `dapo`, `ChunkedLossWrapper`), and the PP schedule never calls them on non-last stages.
- **GraphTrainer GraphPP** asserts that every rank holds both the first and last stage, so its `torch.Tensor`-typed overrides never receive `None`.
- **Logging:** non-owners now log `-1.0` for train and validation loss. Before, they logged `dist_sum(-1 sentinel)`, which scaled with the DP/CP size, so this is cleaner.

### Issues
1. **Validator zero-token check (inline):** under PP only loss owners raise this error. Non-owners go back to training and block on the next PP or FSDP communication until the job is torn down.
2. **Callsite audit (inline on engine):** `experiments/torchft/trainer.py:390-416` still passes local loss counts named as global on non-owners, and the engine silently drops them. Either update the FT copy and remove the override, or explain why the compatibility shim should stay. Separately, `not pp_enabled or engine.pp_has_last_stage` can be just `engine.pp_has_last_stage` in both the trainer and the engine.
3. **MTP.md (nit):** the new text is trainer and collective detail inside a model doc, and the line wrap is off.

### Tests
- The CPU tests are heavily mocked but cover the owner/non-owner × DP × should_log combinations. The engine test case `(pp_enabled=False, last_stage=False)` is a state that can't occur, because the engine forces `pp_has_last_stage=True` without PP.
- I did not run the tests or lint.

On the value question from the earlier review: the PR now states it claims no throughput gain, so the case for merging rests on semantic clarity. With +304/-70 lines, mostly tests, that's a maintainer call.

- claude[bot] · comment · 2026-11-01T05:58:57Z · [source](https://github.com/pytorch/torchtitan/pull/5327#discussion_r4434584188)

File: `torchtitan/components/validator.py` · line 468

This failure path is no longer SPMD under PP. On the base branch every PP stage built `total_global_valid_tokens` from the same per-DP-rank data, so all ranks raised this `ValueError` together. Now only loss owners raise it. Non-owners log `-1.0`, return to `train()`, and block on the next PP P2P or FSDP collective until the job is torn down (NCCL timeout, or the torchrun agent killing the group). Under PP, rank 0 is a non-owner, and that is the rank whose logs people usually read, so the actual error is easy to miss.

This is an edge case (fully masked validation labels), but it is the "careful to not hang in collective due to non-SPMD behavior" concern from the earlier review. Some options:
- keep the per-step DP count reduction on every rank, which is a scalar and cheap, and do the zero check everywhere; or
- accept the asymmetry and add a comment saying non-owners can't detect this case.
