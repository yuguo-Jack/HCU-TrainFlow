# [checkpoint] Trim the HF save map to written tensors

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5582) · state: closed · merged: True

## Original PR description

HF saves give consolidation `fqn_to_index_mapping`, copied from `model.safetensors.index.json`, as the tensors to write. Each listed name that `to_hf` does not write (quantization scales, MTP weights, unused vision towers or layers) gets a `{"shape": [], "dtype": ""}` header entry that makes its file unreadable.

## Fix

`BaseStateDictAdapter.fqn_to_index_mapping_for_save(hf_fqns)` keeps the entries in `hf_fqns` and logs a warning for the rest. `CheckpointManager.dcp_save` passes the global keys from the `Metadata` that `dcp.save` returns, since a PP or EP rank's `to_hf` holds only its own tensors. The two conversion scripts pass their state dict. `TorchCheckpointingManager` is unchanged because `torch_checkpointing` already trims and logs unwritten entries. This replaces the DeepSeek V3, Kimi K3 and gpt-oss filters and the tied `lm_head.weight` pops from #3764, and keeps the `_packed` and `_blocks` renames.

If `to_hf` loses a weight by mistake, the export is now valid but incomplete. The warning names only the first 20 skipped entries, so such a loss usually shows as a higher skipped count. The writer still gets the full index, because before the save no rank knows the other ranks' tensors, so the pickled index copy in each rank's save plan grows from 17.6 to 36.4 MiB for Kimi K3.

## Testing

- `pytest tests/unit_tests/cpu` on x86 Linux with nightly CPU torch passes. The new `test_hf_save_skips_index_entries_the_model_does_not_write` fails on `main` with `SafetensorError` (`unknown variant`).
- HF saves through `last_save_in_hf` and `convert_to_hf.py` with the released Llama-3.1-8B, Qwen3.5-0.8B, Qwen3.6-35B-A3B, Kimi-K3 and gpt-oss-20b indexes leave unreadable files on `main` and none here, each holding exactly the `to_hf` tensors. With the DeepSeek V3.1-Base index, which `main` already filtered, the files are byte-identical to `main`. Two-rank PP and EP saves hold every tensor.
- `SKIP=lychee-link-checker pre-commit run --all-files` passes.

### Answering @tianyu-l's question: where does `mtp.*` come from?

The base class adds it. `StateDictAdapter.__init__` (`torchtitan/models/base/state_dict_adapter.py:155-172`) copies every `weight_map` entry from `<hf_assets_path>/model.safetensors.index.json` into `fqn_to_index_mapping` and never checks the entries against the model config:

```python
if hf_safetensors_indx:
    self.fqn_to_index_mapping = {}
    for hf_key, raw_indx in hf_safetensors_indx["weight_map"].items():
        ...
        self.fqn_to_index_mapping[hf_key] = int(indx)
```

So the mapping holds whatever the released index lists. The released Qwen3.5/3.6/3.8 indexes list the MTP head (`mtp.*`), even though torchtitan's `Qwen35Model` has none. `dcp.py:290-347` then passes this mapping to `HuggingFaceStorageWriter` and `consolidate_safetensors_files_on_every_rank`. Consolidation treats the mapping as the list of tensors to write, so each name that `to_hf` never produced gets an empty `{"shape": [], "dtype": ""}` header entry, and the file can't be opened afterwards. You're right that a model without MTP should never have these names in the mapping. The issue is that nothing removes them after the base class copies the released index.

Other adapters already work around the same thing in their own `__init__`:
- `deepseek_v3/state_dict_adapter.py:46-64` drops the FP8 `weight_scale_inv` entries and MTP layer 61 when the config has no MTP (#5065)
- `gpt_oss/state_dict_adapter.py:53-60` renames quantized names to unquantized ones
- `kimi_k3/state_dict_adapter.py:129-143` drops `weight_scale` and, for text-only configs, the vision tower and projector

This PR follows the same per-adapter pattern, so it is consistent with the existing code.

- `transformers` ignores `mtp.*` when loading Qwen3.5 (`_keys_to_ignore_on_load_unexpected`), so leaving them out of the export loses nothing for HF users.

### Possible follow-up (not blocking)

This is the fourth adapter that hand-filters the released index (DeepSeek V3, gpt-oss, Kimi K3, now Qwen3.5). A general fix would build the save mapping from the keys `to_hf` actually returns, e.g. filter `fqn_to_index_mapping` to `state_dict.keys()` in `dcp.py` right after `self.sd_adapter.to_hf(state_dict)`. That would cover any future released index listing tensors the model doesn't have, and the per-adapter filters would no longer be needed.

It touches shared checkpoint code that every model's HF save uses, though, so it belongs in a separate PR. The targeted fix here is fine to land as is.

### Answering from first principles: is a missing MTP head a model bug?

Yes, you read it right. The official Qwen3.5/3.6/3.8 checkpoints ship an MTP module (`mtp.*`). torchtitan's `Qwen35Model` doesn't implement it, and the READMEs say so on purpose (`torchtitan/models/qwen3_6/README.md:22`, `qwen3_8/README.md:29`: "Released MTP weights are not imported or exported because this model path currently trains only the primary next-token decoder").

I don't think that makes it a model bug that this PR should fix. There are really two separate questions.

**1. Should `Qwen35Model` have MTP?**

MTP is an add-on to the model, not part of the next-token path:
- It is used only as an extra training loss, or as a draft head for speculative decoding at inference.
- The next-token logits don't depend on it.
- HF `transformers` makes the same choice. Its reference Qwen3.5 implementation has no MTP module and ignores `mtp.*` on load (`_keys_to_ignore_on_load_unexpected`).

So a Qwen3.5 model without MTP is a complete next-token model and matches HF's own reference. Adding MTP would be a feature, not a fix:
- It would mean extra training loss and maybe a speculative-decoding draft head for RL rollouts.
- It could reuse `deepseek_v3/mtp.py`.
- It is worth tracking separately.

**2. Should the HF save write tensors the model doesn't have?**

No, and this stays true even if (1) is done. MTP would be optional, like DeepSeek V3's `mtp_layers`. With it turned off, the released index would still list `mtp.*` and the save would still break.

The rule should be: the save map must equal the set of keys `to_hf` returns. Today the base `StateDictAdapter.__init__` copies an outside file (the released `model.safetensors.index.json`) into `fqn_to_index_mapping` as the list of tensors to write. That breaks whenever the index and the model config disagree, for whatever reason:
- unused heads such as MTP
- FP8 `weight_scale_inv` entries
- vision towers in a text-only config
- fewer layers in a debug or truncated config

That's why four adapters now filter the index by hand: DeepSeek V3 (#5065), gpt-oss, Kimi K3, and this PR.

So the root cause sits in the checkpoint layer, not in the Qwen model. This PR adds a fourth patch for the same problem. The patch is correct, but it doesn't fix the cause.

### Recommendation

Fix it once at the point where the mapping is used, and drop the per-model filters. Wherever `to_hf(state_dict)` runs before an HF save:
- `torchtitan/components/checkpoint/dcp.py`, in the `last_save_in_hf` path
- `scripts/checkpoint_conversion/convert_to_hf.py:55-60`
- `scripts/checkpoint_conversion/convert_ema_to_hf.py:193-198`

trim the mapping to what is actually being written:

```python
hf_state_dict = sd_adapter.to_hf(state_dict)
fqn_to_index_mapping = {
    k: v for k, v in sd_adapter.fqn_to_index_mapping.items() if k in hf_state_dict
}
```

It's best to put this in one shared helper so the three callsites can't drift apart. Two optional additions:
- **Logging:** log the dropped names at info level, so a user can see that `mtp.*` was left out on purpose.
- **Missing names:** names that `to_hf` writes but the index doesn't list already need handling. Check how consolidation treats them, so the helper doesn't break that.

With this in place, the hand filters in the DeepSeek V3, Kimi K3 and Qwen3.5 adapters can go. gpt-oss renames entries rather than dropping them, so its filter probably stays.

This touches shared checkpoint code, so per the repo rules it should be tested on HF saves for several models, at least DeepSeek V3, Kimi K3, Qwen3.5 and Llama3.

### Side note on dropping MTP from exports

With either fix, an exported torchtitan checkpoint has no MTP weights. vLLM's MTP speculative decoding then won't work on it. Copying the original MTP weights through unchanged isn't a good answer either: once the trunk is fine-tuned they no longer match it. So "no MTP in the export" is the honest result until (1) is built. It should be documented as such, not hidden in an adapter.

### Verdict
- The fix in this PR works.
- From first principles, the cleaner change is a shared filter in the save path rather than a fourth per-model one. I'd suggest the PR author make that change instead.
- Whether to add MTP to Qwen3.5 is a separate feature decision.
