# [scripts] download_hf_assets: copy asset_types and raise a readable unknown-asset error

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5621) · state: closed · merged: True

## Original PR description

In `scripts/download_hf_assets.py`, `download_hf_assets()` has two problems on the unknown-asset path.

1. It appends `"additional_patterns"` to the caller's `asset_types` list. A caller that reuses the list, for example looping over several repos with the same `asset_types=["tokenizer"]` and `additional_patterns=["*.txt"]`, gets `ValueError: Unknown asset type additional_patterns` on the second call, because the first call left `["tokenizer", "additional_patterns"]` behind.
2. The unknown-asset `ValueError` is built from three positional arguments, so `str(e)` (and the CLI traceback) is a tuple repr with literal `\n` escapes:

```
ValueError: ('Unknown asset type tokenizers. Available uses: --assets tokenizer safetensors index config \n', "Or specify exact patterns to download. Example: --additional_patterns '*.safetensors' README.md '*.json' \n", 'Or use --all to download all files')
```

The fix copies `asset_types` before the function appends to it (a `str` is still wrapped in a list as before), and joins the error into one message:

```
ValueError: Unknown asset type tokenizers. Available uses: --assets tokenizer safetensors index config
Or specify exact patterns to download. Example: --additional_patterns '*.safetensors' README.md '*.json'
Or use --all to download all files
```

Which files get downloaded does not change.

Tests, in `tests/unit_tests/cpu/scripts/test_download_hf_assets.py`:
- `test_unknown_asset_type` now checks that the exception has one argument and checks the full text. The old `assertIn` passed against the tuple repr, which is why this went unnoticed.
- New `test_reused_asset_types_list_is_not_mutated` calls the function twice with the same list and checks the list is unchanged and both calls download the same files.

Both fail on main and pass with this change. The other 11 tests in the file pass, and so does all of `tests/unit_tests/cpu/scripts` (40 tests), on Windows with Python 3.11 and torch 2.16.0.dev20261024+cpu. `pre-commit run` on the two changed files passes flake8, ufmt, pydoclint, codespell and pyrefly. The lychee hook needs `/bin/bash`, so it did not run on Windows. I did not run anything on Linux or GPU; the change only touches this script and its test.

This looks good to merge. Both fixes are small, correct, and limited to the script, and the tests cover the bugs that were actually reported.

**`scripts/download_hf_assets.py:91`, copying `asset_types`**
- `list(asset_types)` makes a shallow copy, which is enough here because the list holds strings. The `str` case is handled the same way as before.
- The function still treats `"additional_patterns"` as an asset type (lines 113-114) and checks it in the per-type warning loop (lines 142-154). So the `Warning: No matching files found for asset_type 'additional_patterns'` message still appears when it should.
- Optional: a cleaner fix would stop appending to `asset_types` and keep the warning-loop keys in a separate local list. That would remove the pseudo-asset-type workaround that caused the bug. The copy is fine for this PR.

**`scripts/download_hf_assets.py:102-108`, the error message**
- The `ValueError` now gets one string, so `str(e)` gives the readable multi-line text. This also drops the trailing spaces before each `\n`, which is a good change.
- Small wording nit, not new in this PR: "Available uses: --assets ..." reads oddly. "Available asset types: ..." would be clearer, but changing it is optional.

**Tests**
- `test_unknown_asset_type` now asserts `len(args) == 1`. That is the right regression check: the old `assertIn` also passed on the tuple repr, which is why the bug went unnoticed.
- `test_reused_asset_types_list_is_not_mutated` checks two things: the caller's list is unchanged, and both calls download the same files. The second check matters because it shows the second call no longer raises.
