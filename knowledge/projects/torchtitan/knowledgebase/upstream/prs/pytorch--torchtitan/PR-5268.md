# [rl] FSDP generator: sync weights one FSDP module at a time

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5268) · state: closed · merged: True

## Original PR description

**TLDR:** On main, a weight sync holds two copies of the generator's weights, so the first sync OOMs unless the second copy fits in the ~6 GiB that vLLM leaves free on an H100. This PR syncs one FSDP module at a time: Qwen3.5-35B-A3B at TP1 needs 1.6 GiB extra instead of its 64.6 GiB state dict, and the KV cache keeps its size.

**Problem**
1. With FSDP, each weight has a sharded buffer, which `load_state_dict` writes, and an unsharded buffer, which forward and CUDA graphs read.
2. Between syncs, only the unsharded buffers stay allocated.
3. A sync re-allocates all sharded buffers (`prepare_for_state_dict_load`) before `load_state_dict`, so both sets are resident.
4. With generator FSDP degree 1 (TP-only or 1-GPU generators), the sharded set is a whole second copy of the local model.
5. vLLM fills GPU memory up to `gpu_memory_limit` (default 0.9) at startup, leaving a sync about 6 GiB on a 95 GiB H100.
6. Qwen3.5-9B at TP1 needs 16.7 GiB and OOMs at the first sync.

**Solution**
1. `VLLMModelWrapper.load_state_dict` (overriding `nn.Module`'s, keyed like `self.model`) keeps one `load_state_dict` call. For each group of modules sharded together (e.g. `[norm, lm_head]`), it adds a temporary pre-hook on the first module, which calls `prepare_for_state_dict_load` for that group, and a post-hook on the last, which calls `prepare_for_forward`.
2. `prepare_for_state_dict_load` no longer skips groups that already read as sharded: FSDP's own load pre-hook reshards a module that owns parameters (e.g. `tok_embeddings`) before ours runs.
3. The generator's pull calls `model.load_state_dict(model_sd)`.
4. Both prepare methods take one `FSDPModule` and act on its FSDP group; `__init__` loops over the FSDP modules for the initial unshard.

```text
before:  re-allocate ALL sharded -> load_state_dict -> unshard + free ALL           peak: 2x weights
after:   load_state_dict, per FSDP group: re-allocate -> copy -> unshard + free     peak: weights + ~1 group
```
With tied embeddings, the `[tok_embeddings, norm, lm_head]` group stays allocated for the whole load.

**Results**
```text
H100 (95 GiB), bf16, gpu_memory_limit 0.9: extra GPU memory during one sync
main = the state dict size; this PR = measured peak
Qwen3.5-35B-A3B, TP1     64.6 -> 1.6 GiB     (5.9 GiB free)    sync 1.3 s
Qwen3.5-9B, TP1          16.7 -> 1.9 GiB     (6.1 GiB free)    sync 0.37 s   main OOM observed
Qwen3.5-9B, TP2           8.3 -> 0.95 GiB    (5.7 GiB free)    sync 0.2-0.24 s
Qwen3.5-4B, TP1, tied     9.0 -> 1.4 GiB     (6.1 GiB free)    sync 0.2 s
```
- Greedy decode under FULL CUDA graphs is identical across syncs of the same weights. A perturbed `norm.weight` changes it, and undoing that restores it.
- RL runs, H100:
  - Qwen3.5-4B-Base, 2 GPUs, generator TP1, 8 steps: trainer-generator logprob diff mean 5.6e-5 at step 8.
  - `rl_grpo_qwen3_moe_debug_varlen` (generator DP=2, so a real FSDP all-gather inside the load; CUDA graphs off), 5 steps: per-step max logprob diff 0.009-0.059, main 0.007-0.058; pull 0.60 s, main 0.62 s.
  - `rl_dapo_qwen3_4b_math_8k`, 8 GPUs, 109 steps (then stopped by an unrelated host OOM kill): mean reward 0.17 over steps 1-10 and 0.35 over steps 91-109; 0.2 s per sync.

You may ask:
- Why per FSDP group, not per module? `fully_shard([norm, lm_head])` gives both one FSDP state; unsharding after `norm` would all-gather `lm_head` before it loads.
- Why hooks, not one `load_state_dict` per FSDP module? That call also loads the nested FSDP modules, whose sharded buffers are still freed.
- Why not leave room for the second copy, by lowering `gpu_memory_limit` or reserving it during vLLM's memory profiling? It comes out of the KV cache. Reserving it at profiling, on one H100:
  ```text
  Qwen3.5-9B TP1          KV cache 67.81 -> 51.44 GiB (1.23M -> 0.93M tokens)
  Qwen3.5-35B-A3B TP1     engine fails to start (OOM during memory profiling)
  ```

NOTE: results above are from an earlier main (`49c4cff1f`); the 9B and 35B probes were re-run on this branch (below).

- felipemello1 · comment · 2026-10-11T04:01:08Z · [source](https://github.com/pytorch/torchtitan/pull/5268#issuecomment-6105244701)

reply by claude: All comments are addressed. Summary of the changes:

- **`model.load_state_dict(model_sd)`:** `VLLMModelWrapper` now overrides `load_state_dict`. Keys are those of `self.model` (no `model.` prefix). `strict=True` is fixed: with `strict=False`, a missing param would end up with uninitialized memory.
- **Why per FSDP group:** modules from one `fully_shard` call, e.g. `[norm, lm_head]`, share one FSDP state. Unsharding right after `norm` would all-gather `lm_head` before it loads. The docstring now draws when each group is allocated and freed.
- **Why hooks:** calling `load_state_dict` per module would also load its nested modules while their buffers are still freed. The hooks run inside one call, right before and after each group. Added a comment.
- **One module:** `prepare_for_state_dict_load` / `prepare_for_forward` take one `module: FSDPModule` (they call `_get_fsdp_state()` and `unshard()`). `__init__` loops over the FSDP modules.
- **Tests:** CPU unit tests, a new CPU FSDP2 regression test, 2-GPU bitwise parity, and the 9B / 35B-A3B engine probes all pass.
- **Red CI:** "1 GPU Integration (Fake PG)" fails on the SFT loss golden. That's main: the recent in-place WGRAD change updated `real_pg/a10g/sft.txt` but not `fake_pg/a10g/sft.txt`. Not from this PR.
