# [graph_trainer] Trace compact DeepEP and overlap the shared experts with the dispatch wait

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5315) · state: open · merged: False

## Original PR description

## Summary

Following the review of #5263: express the shared-expert / DeepEP-dispatch overlap as a GraphTrainer
graph pass instead of an eager callback. That needs a prerequisite, which is most of this diff: the compact
DeepEP training path has to be traceable by GraphTrainer at all. Today `memory_policy.py` already lists
`deepep.dispatch`, but the ops have no fake kernels, the backward runs DeepEP directly, and the combine
relies on an eager-only stream wait.

## What changes

`torchtitan/distributed/deepep/deepep.py` (eager behavior preserved):
- every `deepep::` op gets a fake kernel; the received row count is an unbacked size (`new_dynamic_size()`),
  the same way the all-to-all path exposes data-dependent counts;
- the backward communications become ops (`dispatch_bwd`, `combine_bwd`) with fake kernels, so a traced joint
  graph contains them instead of running DeepEP on fake tensors;
- `combine` waits for its own communication (the dispatcher synchronized right after it anyway), which a
  traced graph needs because `sync_combine()` was never part of the graph;
- the handle cache is only touched inside op implementations; `setup_context` keeps the handle_id tensor;
- optional split of the compact dispatch into `launch_dispatch` + `wait_dispatch` (DeepEP v2.5
  `defer_epilogue`): `DeepEPTokenDispatcher.Config.split_dispatch_launch_wait`, default off. Eager runs them
  back to back; `_permute_tokens` uses `shape[0]` instead of `len()` so it traces with an unbacked size;
- `EPBuffer` / `ElasticBuffer` import compatibility (DeepEP v2.5 renamed the buffer); the DeepEP GPU test
  patches whichever class the installed DeepEP has.

`torchtitan/experiments/graph_trainer`:
- `compile.deepep_dispatch_overlap` and `deepep_overlap_pass`: for each forward `wait_dispatch`, every node in
  the window up to the combine's consumer that does not depend on the wait, has no side effect and is
  computable from pre-launch values (in the common MoE layout: the shared-expert FFN) is scheduled between
  the launch and the wait. Forward only, stable topological sort, no node added or changed. Independent of
  `ep_overlap`: DeepEP has one communication buffer, so the second in-flight exchange that chunking needs is
  not available, which is why this only sinks waits.
- memory policy lists the new ops as communication ops, `annotate_moe_ep_regions` covers the DeepEP
  dispatcher, test recipe `graph_trainer_deepseek_v3_debugmodel_deepep`, CPU unit tests for the pass, README.

## Validation (8 x H200 141GB, one node, torch 2.16.0.dev20261009+cu132, public DeepEP 2.5, NCCL 2.32.3)

- `tests/unit_tests/gpu/distributed/test_deepep_activation_checkpoint.py`: 2 passed (eager saved and
  replayed communication with the new backward ops).
- `experiments/graph_trainer/tests/test_deepep_overlap_pass.py`: 3 passed (CPU).
- `pre-commit run --files <changed>`: all hooks pass, no hook edits.
- GraphTrainer traces and trains the compact DeepEP path: `deepseek_v3_debugmodel` and the 16B flavor,
  EP8, FSDP8, default memory policy, 20-30 steps, synthetic packed inputs, deterministic mode.
- Pass ON vs OFF is bitwise identical: loss, grad_norm and final weights on all 8 ranks, 30 steps, in all
  four arms of an ABBA sequence; 26 MoE layers x 24 nodes moved (shared-expert mm/silu/mul/cat/split/...).
- DeepSeek-V3 16B (dim 2048, 64 experts top-6, 2 shared experts), EP8, 8192 tokens per rank,
  same-allocation ABBA, median over steps 6-30 of the per-step max-rank wall time:

  | arm | step ms |
  | --- | ---: |
  | OFF A1 | 1029.26 |
  | ON B1 | 1017.35 |
  | ON B2 | 1018.12 |
  | OFF A2 | 1030.13 |

  ON is 1.16% faster (both neighbour pairs -1.16% / -1.17%, arm repeats within 0.08%); peak memory
  unchanged (28.7 GiB). A profiler trace shows the shared-expert GEMMs inside the `wait_dispatch` host
  spans only with the pass; the GPU is already ~95% busy there from queue run-ahead, which bounds the gain.
  The debug model (256 tokens per rank) shows no measurable difference, consistent with #5263.
- For reference, the eager callback of #5263 on the same 16B / EP8 / 8192-token configuration (SelectiveAC,
  one OFF/ON pair, 30 steps) measures 910.5 -> 895.0 ms, -1.7%, bitwise identical; the two approaches hide the
  same window, so the gain is bounded the same way.

Not validated: multi-node, TP > 1 with EP, FP8 dispatch, CUDA graphs (the compact path has a host sync),
`ep_overlap` chunking composed with this pass, convergence on real data. Upstream GPU CI pins an older
DeepEP, so the v2.5-only split path is exercised only by the recipe above.

## Open questions

- Is the compact (data-dependent shape) DeepEP path acceptable in GraphTrainer graphs, or should GraphTrainer
  stay with HybridEP? The traceability part stands on its own even without the pass.
- Should the launch/wait split stay a dispatcher config, or be implied by GraphTrainer?
- Should the pass live in `ep_overlap_pass.py` as a single-chunk mode instead of its own module?

Supersedes the eager approach of #5263 if accepted.
