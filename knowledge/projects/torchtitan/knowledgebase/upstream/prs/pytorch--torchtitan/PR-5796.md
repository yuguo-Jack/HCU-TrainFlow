# [tests] Regenerate the real-PG SFT goldens after #5757

## Why
The Real PG integration suite (`8 GPU Integration (Real PG - full suite - features)`) and the ROCm integration suite have failed the `sft` loss check on main since #5757 (`899480301`; `a87db08ea` before it passed):

```
[sft] AssertionError: 7.889825820922852 != 7.887711524963379 : loss mismatch at step 1   # A10G
[sft] AssertionError: 7.890093803405762 != 7.887524604797363 : loss mismatch at step 1   # MI350X
```

#5757 renders `bos_token`/`eos_token` in Hugging Face chat templates, an intended change to the SFT token stream. It regenerated `tests/assets/losses/fake_pg/a10g/sft.txt` but not the real-PG A10G and MI350X goldens.

## What changed
- `tests/assets/losses/real_pg/a10g/sft.txt` and `tests/assets/losses/real_pg/mi350x/sft.txt`: steps 1-10 regenerated; headers unchanged.

## Numerics
The new values are the full-precision TensorBoard metrics of the failing main runs' baseline training (the same values `loss_compare.py --export-result` writes), read with `scripts/loss_compare.py`'s own extraction from the uploaded `integration-8gpu-features-outputs` artifacts:
- A10G: run 41746280593 (`e6ca6d861`). Step 1 matches the log's baseline (7.889825820922852, grad_norm 4.189799785614014).
- MI350X: the ROCm run on `73c4ebdac`. Step 1 matches the log's baseline (7.890093803405762, grad_norm 4.189815998077393).

The commits between #5757 and those runs (#5572, #5787, #5776, #5774, #5779, #5741, #5786) do not change SFT numerics.

## Testing
- CI: Real PG (`ciflow/real-pg`) and ROCm (`ciflow/rocm`) integration suites.
- A manual `export_results` run of the integration workflow for `sft` on main (run 41760303504) exported a real-PG A10G golden identical to this one.
- `Multi-GPU Unit Tests` fails here with the `_VisionEncoder ... named_preserve_dtype_params` error that is also on main; #5795 fixes it.

This PR was AI-assisted.
