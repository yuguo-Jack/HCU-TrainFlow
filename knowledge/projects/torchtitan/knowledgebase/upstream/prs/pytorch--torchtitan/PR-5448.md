# [Muse Spark Open] Bridge multi-turn prompts in the renderer

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5448) · state: closed · merged: True

## Original PR description

## Summary

`MuseSparkRenderer.bridge_to_next_turn` returned `None`, so multi-turn clients (the Verifiers train client) re-rendered every agent turn from parsed messages. Parsing is lossy: it strips whitespace, merges reasoning channels and re-serializes tool arguments. After a non-canonical completion, the re-rendered prompt no longer starts with the sampled tokens, and the trainer's sample builder starts a new sample that repeats the whole history.

This PR implements the bridge. It keeps the previous prompt and completion verbatim and renders only the new tool and user messages plus the generation prompt, piece by piece as `render` does. For a canonical completion the result equals the full re-render. It returns `None`, so the caller re-renders, when:

- there is no previous turn, or the tail contains an assistant message;
- the completion did not close its turn with `<|eot|>` (a truncated completion is re-rendered rather than closed with a synthesized `<|eot|>`);
- the tool results do not match the completion's tool calls one to one. Muse Spark tool calls carry no ids, so results are matched to calls in order, and a result's own `name`, when given, must agree.

`render`-side behavior is unchanged.

## Evidence

On a 131k-context multi-turn SWE agent run (Verifiers + OpenCode, 3 steps), each rollout produced about 9 training samples that repeated the history (~385k tokens per rollout). Two 3-step runs of the same config, before and after the bridge:

| | step 1 | step 2 | step 3 |
|---|---|---|---|
| training samples, before | 312 | 291 | 264 |
| training samples, after | 64 | 100 | 76 |
| trainer fwd/bwd (s), before | 110 | 86 | 62 |
| trainer fwd/bwd (s), after | 58 | 33 | 16.9 |

The rollouts differ between the two runs, so the per-step numbers are indicative; the sample count drop is the direct effect.

## Tests

- `tests/unit_tests/cpu/models/muse_spark/test_renderer.py`, 4 new tests:
  - a canonical completion bridged with a tool result equals the full render;
  - two tool results plus a user message equal the full render;
  - a completion with extra spaces in its reasoning is kept verbatim, while the full re-render drops the spaces and no longer extends the sampled turn;
  - fallbacks to `None`: no previous turn, truncated completion, more tool results than calls, tool name disagrees with the call, assistant in the tail.
- The first three fail without the change. The file passes: 10 passed, 3 xfailed (the existing review-item xfails).
- The same 4 tests also pass with the `Muse-Spark-1.2-816B-A42B-open` checkpoint tokenizer.
- `pre-commit` on the touched files; pyrefly reports 0 errors in `renderer.py`.
