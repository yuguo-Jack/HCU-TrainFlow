# [dsv4] Apply the published swiglu_limit in the Flash and Pro flavors

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5646) · state: closed · merged: True

## Original PR description

DeepSeek-V4-Flash and DeepSeek-V4-Pro both publish `swiglu_limit: 10.0` ([Flash config](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/blob/main/config.json), [Pro config](https://huggingface.co/deepseek-ai/DeepSeek-V4-Pro/blob/main/config.json)). The reference inference code builds both the routed experts and the shared expert with it (`Expert.forward` in [inference/model.py](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/blob/main/inference/model.py)), clamping the up projection to `[-limit, limit]` and the gate to `max=limit` before `silu(gate) * up`. Hugging Face transformers does the same in `DeepseekV4MLP` and `DeepseekV4Experts._apply_gate`.

The `deepseek_v4_flash` and `deepseek_v4_pro` flavors use plain `SwiGLU` for both, so a model loaded from those checkpoints computes a different MoE output whenever a gate or up activation passes 10. This PR adds `LimitedSwiGLU` and uses it for the routed experts and shared expert of every MoE layer in both flavors. The MTP block deep-copies the last layer, so it gets it too. `debugmodel` is unchanged.

`LimitedSwiGLU` is a separate class rather than a `SwiGLU` subclass or a `ClampedSwiGLU` option. `ClampedSwiGLU` is the GPT-OSS formula (`gate * sigmoid(alpha * gate) * (up + 1)`), and the bundled `fused_swiglu` override targets `SwiGLU.Config` and does not clamp, so it must not match. `dist_moe` already raises a `TypeError` for activations it does not support, so these flavors now raise there instead of running it without the clamp.

Reproducer: it builds the V4-Flash shared expert from the flavor and compares it with transformers' `DeepseekV4MLP`, with the same random weights, on 64 random tokens scaled by `std`.

```python
import torch
from transformers.models.deepseek_v4.configuration_deepseek_v4 import DeepseekV4Config
from transformers.models.deepseek_v4.modeling_deepseek_v4 import DeepseekV4MLP
import torchtitan.models.deepseek_v4.flavors as v4
from torchtitan.config.parallelism import ParallelismConfig

torch.manual_seed(0)
cfg = v4.build_model_config("deepseek_v4_flash", parallelism=ParallelismConfig(), seq_len=4096)
shared = cfg.layers[3].feed_forward.shared_experts.build()
hf = DeepseekV4MLP(DeepseekV4Config(hidden_size=4096, moe_intermediate_size=2048))
for p in hf.parameters():
    torch.nn.init.normal_(p, std=0.02)
shared.load_state_dict({"w13.weight": torch.stack((hf.gate_proj.weight, hf.up_proj.weight)),
                        "w2.weight": hf.down_proj.weight})
for std in (1.0, 4.0, 8.0, 16.0):
    x = torch.randn(64, 4096) * std
    with torch.no_grad():
        gate, up, expected, actual = hf.gate_proj(x), hf.up_proj(x), hf(x), shared(x)
    print(std, gate.abs().max().item(), up.abs().max().item(),
          (actual - expected).abs().max().item(),
          ((actual - expected).norm() / expected.norm()).item())
```

The bug is real. V4-Flash and V4-Pro publish `swiglu_limit: 10.0`, the reference code clamps both the routed and shared experts, and today these flavors use plain `SwiGLU`, so loaded checkpoints compute the wrong output. The wiring in `flavors.py` is correct: MoE layers only, routed and shared experts, MTP inherits it, and `debugmodel` is unchanged. My concerns are about where the clamp lives, not whether it should be added.

---

### Q1: Should this be folded into the existing `SwiGLU`?

**I'd say yes.** V4's formula is plain SwiGLU with its inputs clamped first: `silu(clamp(gate, max=L)) * clamp(up, -L, L)`. An optional field on `SwiGLU.Config` covers it:

```python
class SwiGLU(BinaryActivationFn):
    @dataclass(kw_only=True, slots=True)
    class Config(BinaryActivationFn.Config):
        limit: float | None = None  # validated finite and > 0 when set

    def _activation_fn(self, gate, up):
        if self.limit is not None:
            gate = gate.clamp(max=self.limit)
            up = up.clamp(min=-self.limit, max=self.limit)
        return F.silu(gate) * up
```

The `if` resolves at trace time, so the `fused_binary_activation` compiled region still gets one static graph per config. The default `None` leaves every existing user (llama3, qwen3, dsv3, kimi_k2_7, ...) bit-identical.

`ClampedSwiGLU` should stay a separate class. Its formula, `gate * sigmoid(alpha * gate) * (up + 1)`, is a different function, not SwiGLU plus a clamp. Once `SwiGLU` can clamp, the name `ClampedSwiGLU` gets confusing; renaming it to something like `GptOssSwiGLU` could be a follow-up.

**Catch to handle in the same PR:** the PR description gives "`fused_swiglu` must not match" as the reason for a separate class. That risk is real: `fused_swiglu` targets `SwiGLU.Config` with `exact=True`, and `derive()` silently drops fields the target lacks (`torchtitan/config/override.py:251`, "fields only on `source` -> dropped"). With a `limit` on `SwiGLU.Config`, `--override ...fused_swiglu` would quietly turn V4's clamped activation back into a plain one, which is the same silent mismatch this PR fixes. Either:
- (a) add `limit` to `FusedSwiGLU.Config` and clamp in the Triton forward and backward kernels (`torchtitan_recipes/overrides/fused_swiglu.py:315`). This is easy: zero `grad_gate` where `gate > L` and `grad_up` where `|up| > L`. Or
- (b) make `fused_swiglu` raise `ValueError` when `cfg.limit is not None`.

I'd do (b) now and (a) later if someone needs it.

### Q2: Does it work with DistMoE, and what's the best UX?

**It does not work today, but it fails loudly rather than silently.** `_replace_routed_experts` (`torchtitan/config/transform/dist_moe.py:48-60`) accepts only `SwiGLU.Config` (mapped to `"swiglu"`) and `ClampedSwiGLU.Config` (mapped to `"swiglu_clamped"`). Anything else, including `LimitedSwiGLU`, raises `TypeError`.

You can't express V4's clamp through DistMoE's existing clamping mode. `"swiglu_clamped"` passes `swiglu_alpha`/`swiglu_limit` to the annex kernel, which implements the GPT-OSS formula (`ClampedSwiGLU` maps 1:1 to it). Setting `alpha=1` still leaves the `(up + 1)` term, so the result would be wrong. Supporting V4 needs a kernel change in `meta-pytorch/dist_moe`: the cleanest version is an optional `swiglu_limit` on the plain `"swiglu"` mode.

**The UX I'd suggest, which matches what you described:**
1. `SwiGLU.Config(limit=...)` is the single source of truth, as in Q1.
2. The DistMoE transform reads the limit from the source activation instead of owning its own setting, the same way it already treats `ClampedSwiGLU`:
   ```python
   if isinstance(source.activation_fn, SwiGLU.Config):
       activation = "swiglu"
       swiglu_alpha = None
       swiglu_limit = source.activation_fn.limit  # None -> unclamped
   ```
   This needs `DistMoeRoutedExperts.Config.__post_init__` (`routed_experts.py:88-90`) to allow `swiglu_limit` with `"swiglu"`, and `_resolve_context_config` (`runtime.py:443`) to forward it.
3. **Until the annex kernel supports a limit on plain SwiGLU**, the transform must raise when `limit is not None`. Folding the clamp into `SwiGLU` turns today's `TypeError` into a silent drop, because `isinstance(..., SwiGLU.Config)` would match and the limit would be ignored. That makes this guard a correctness requirement if you take the Q1 route, not an optional nicety.

Users would then turn on DistMoE or `fused_swiglu` with the V4 flavors and no extra flags, and either get the right numerics or a clear error.

### Other notes
- **Missing wiring test.** The new test covers the activation alone. Add a flavor-level assertion that for `deepseek_v4_flash`/`deepseek_v4_pro`, every MoE layer's `routed_experts.activation_fn` and `shared_experts.activation_fn` use the limit (including the MTP layer), and that `debugmodel` and dense layers are unchanged. That would catch a regression if `_make_v4_moe_config` is refactored.
- **Small style point** (`flavors.py:429-434`): mutating `activation_fn` after the configs are built works, but `gpt_oss/flavors.py:206` sets it inline. Passing the activation config straight into the builders, or setting it once with a local `activation_fn = ...`, would read more directly. This is minor.
- **Checkpoints:** the change adds no parameters, so the state dict adapter is unaffected.
- **Numerics:** the HF reproducer is convincing for the forward pass. Per CLAUDE.md this is a computation change, so a short V4 forward/backward (or debug-model run with the limit forced on) would be good before landing. `debugmodel` itself stays bit-identical.
