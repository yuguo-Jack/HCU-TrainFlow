# [rl] Split the generator into service, engine loop, dispatch and vLLM engine

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5317) · state: open · merged: False

## Original PR description

Stacked on #5316.

## Why

`torchtitan/rl/generator/generator.py` (1860 lines) mixed three concerns in one class:

- calls into vLLM (`EngineArgs`, `render_cmpl` + `add_request`, `step`, `SamplingParams`, `RequestOutput` parsing, prefix-cache reset, teardown);
- request dispatch across data-parallel replicas and fan-in of results to rank 0;
- the engine thread and its SPMD loop (queue, rank 0's decision, broadcast, step bursts, load coalescing).

That makes each part hard to read in isolation, and gives a second inference engine (e.g. SGLang) no clear place to plug in. This PR splits the file along those lines. It changes no config and no behavior.

## What changed

| File | Contents |
| --- | --- |
| `generator/generator.py` | `VLLMGenerator`, the service: config, setup and endpoints (457 lines) |
| `generator/engine_loop.py` | `EngineThread` (the engine thread and its event loop) and `EngineLoop` (queue, decide -> broadcast -> apply, load coalescing, policy version, per-group cache-salt pins) |
| `generator/dispatch.py` | `RequestDispatcher` and the rank-0 completion metrics |
| `generator/types.py` | `SamplingConfig`, `EngineRequest`, `FinishedRequest`, `RequestMetricsInputs`. No vLLM import. |
| `generator/vllm/engine.py` | `VLLMEngine`, holding every vLLM call, plus `build_engine_args` / `setup_vllm` / `build_stat_loggers` |
| `generator/vllm/config.py` | `VLLMCudaGraphConfig` |

Only `generator/vllm/` imports vLLM. `engine_loop.py`, `dispatch.py` and `types.py` see the engine only through `VLLMEngine`'s methods (`add_requests`, `step`, `has_unfinished_requests`, `load_prefetched_model_state_dict`, `shutdown`), which take and return engine-agnostic types.

The dispatcher now receives `FinishedRequest`s instead of vLLM `RequestOutput`s. Rank 0 builds each `Completion` from the fanned-in results. Peer replicas used to send a `Completion` with a placeholder `min_policy_version` that rank 0 overwrote; they now send their `FinishedRequest`s plus the policy version installed when those finished.

`SamplingConfig`, `VLLMCudaGraphConfig` and `add_extra_vllm_engine_args` move with their code, and every caller is updated: recipes, the controller, rollout, the verifiers example and `generate.py`. `VLLMGenerator.Config` is unchanged, so recipes and CLI overrides keep working.

## Not in this PR

- vLLM-specific config fields (`cuda_graph`, `extra_vllm_engine_args`, `vllm_stat_logger`, ...) still sit on `VLLMGenerator.Config`. Grouping them under an engine sub-config would change config paths, so that is left for when a second engine lands.
- `generate.py` and the GPU parity test still build their own `EngineArgs` rather than using `build_engine_args`.

## Testing

- `pre-commit run --all-files` is clean (pyrefly: 0 errors).
- RL CPU unit tests: 433 passed, the same as #5316 and main. The one failure, `test_rollout_worker.py::test_delta_prompts_rebuild_the_full_prompt_samples`, also fails on main. `test_engine_loop.py` now drives `EngineLoop` directly with a fake engine, and `VLLMEngine`'s admission, salting, rejection and KV-reset tests no longer go through the loop.
- Every RL recipe builds, except a hardware-gated MXFP8 recipe.
- GPU: the local GPUs were unavailable while I made this change, so end-to-end generator coverage comes from CI's RL GPU and integration jobs (bitwise parity, uneven decode, alphabet sort).
