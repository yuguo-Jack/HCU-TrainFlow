# [rl] Split the generator into service, engine loop, dispatcher and engine; add GenerationEngine

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5317) · state: closed · merged: True

## Original PR description

Stacked on #5316.

## Why

`torchtitan/rl/generator/generator.py` (1860 lines) mixed three concerns in one class, `VLLMGenerator`:

- calls into vLLM (`EngineArgs`, `render_cmpl` + `add_request`, `step`, `SamplingParams`, `RequestOutput` parsing, prefix-cache reset, teardown);
- request dispatch across data-parallel replicas and fan-in of results to rank 0;
- the engine thread and its SPMD loop (queue, rank 0's decision, broadcast, step bursts, load coalescing).

That makes each part hard to read in isolation and ties the generator to vLLM. This PR splits the file along those lines and puts the inference engine behind an interface, so a second engine (e.g. SGLang) can be added as another `GenerationEngine` without touching the generator, the engine loop or the dispatcher.

## What changed

**Generator split**

| File | Contents |
| --- | --- |
| `generator/generator.py` | `Generator` (was `VLLMGenerator`), the service: config, setup and endpoints |
| `generator/engine_loop.py` | `EngineLoopThread` (the thread and event loop the engine lives on) and `EngineLoop` (queue, decide -> broadcast -> apply, load coalescing, policy version, per-group cache-salt pins) |
| `generator/dispatcher.py` | `RequestDispatcher` and the rank-0 completion metrics |
| `generator/types.py` | `SamplingConfig`, `EngineRequest`, `FinishedRequest`, `RequestMetricsInputs` |
| `generator/engine.py` | `GenerationEngine`, the engine interface |
| `generator/vllm/engine.py` | `VLLMEngine`, holding every vLLM call |
| `generator/vllm/config.py` | `VLLMCudaGraphConfig` |

The dispatcher now receives engine-agnostic `FinishedRequest`s instead of vLLM `RequestOutput`s, and rank 0 builds each `Completion`. Peer replicas used to send a `Completion` with a placeholder `min_policy_version` that rank 0 overwrote; they now send their `FinishedRequest`s plus the policy version installed when those finished.

**Engine interface**

- `VLLMGenerator` -> `Generator`, `VLLMGeneratorActor` -> `GeneratorActor`.
- `GenerationEngine` (`generator/engine.py`) is the interface the engine loop and the generator call: `add_requests`, `step`, `has_unfinished_requests`, `load_prefetched_model_state_dict`, `shutdown`, `prefetched_model_state_dict`, and the data-parallel layout. Its docstring lists the build arguments every engine accepts.
- `VLLMEngine` implements it. vLLM setup, `EngineArgs` and the stat logger are private `VLLMEngine` methods, and the engine is built from its config on the engine loop thread.
- Only `generator/vllm/` imports vLLM; `generator.py` imports the default engine config lazily.

**Monarch README**

`actors/monarch/README.md` lists the Monarch adapters and the Monarch use that still lives outside them (provisioning in `train.py`, spawning in the controller and rollouter, `InterGeneratorRouter` as an `Actor`, and the RDMA microbatch), with the planned path to confine it to `actors/monarch/`.

## User-facing changes

- `VLLMGenerator` -> `Generator`, `VLLMGeneratorActor` -> `GeneratorActor`.
- vLLM-only settings move from `Generator.Config` to `VLLMEngine.Config`, selected by the new `Generator.Config.engine` (default `VLLMEngine.Config()`):

  | Before | After |
  | --- | --- |
  | `generator.cuda_graph` | `generator.engine.cuda_graph` |
  | `generator.extra_vllm_engine_args` | `generator.engine.extra_engine_args` |
  | `generator.vllm_stat_logger` | `generator.engine.stat_logger` |
  | `generator.session_kv_holder` | `generator.engine.session_kv_holder` |

  Engine-agnostic settings stay on `Generator.Config` and are passed to the engine's build: `model_dtype`, `gpu_memory_limit`, `max_num_batched_tokens`, `checkpointer`, `dist_moe_runtime`, `debug`. Every recipe and test is updated. Only Python configs change: the CLI has no per-field overrides, and `--override` targets override functions, not config paths.
- `SamplingConfig` moves to `torchtitan.rl.generator.types`, `VLLMCudaGraphConfig` to `torchtitan.rl.generator.vllm.config`, and `add_extra_vllm_engine_args` to `torchtitan.rl.generator.vllm.engine`; every caller is updated.

## Execution order

The per-iteration sequence is unchanged: decide, broadcast, stamp versions, admit, step burst, fan-in, load. The differences:

- The engine's process-wide setup (`register_to_vllm`, the model runner env var, the batch-invariant logprob patch) now runs on the engine loop thread inside the engine build, after `set_batch_invariance` and the determinism flags. vLLM reads neither at import time.
- `RequestOutput` -> `FinishedRequest` conversion happens in `VLLMEngine.step` on every rank, not only TP rank 0 (a small list copy on the other ranks; the n=1 check now fires on every rank instead of only rank 0).
- A model state dict load sets the policy version after the optional prefix-cache reset rather than before; both run synchronously on the engine loop thread, and nothing reads the version in between.
- `generate`'s `stop_token_ids` assert runs before the closed/not-started guard (error path only).
- Session KV release (#5220) runs through the engine loop as a `SessionReleaseMessage`, applied on every rank in the next decision; vLLM priority scheduling (#5257) passes `group_id` as the priority and rank 0's `arrival_time` to every rank, as on main. Because `session_kv_holder` is vLLM-only, its check against `reset_kv_cache_on_model_state_dict_load` now fails when the engine is built rather than when `Generator.Config` is constructed.

## Testing

- RL CPU unit tests: 492 passed, 8 skipped (rebased on `dc9ea005e`). `test_engine_loop.py` drives `EngineLoop` directly with a fake engine; `VLLMEngine`'s admission, salting, rejection, step, shutdown and KV-reset tests use a fake `LLMEngine`; the engine kwargs test builds `VLLMEngine` through `Config.build(...)` with vLLM mocked; the `generate` endpoint and the DP fan-in's min/max versions have their own tests.
- `pre-commit run --all-files`: clean for the changed files (see #5316 for the unrelated local `kda.py` pyrefly errors).
- Every RL recipe builds, except a hardware-gated MXFP8 recipe.
- GPU A/B against main (2x GB300, Qwen3 debug model with random init and a deterministic varying reward):
  - on-policy, batch-invariant: all 65 non-timing metrics are bitwise identical to main, and identical run to run;
  - async (`target_offpolicy_steps=3`): within main's own run-to-run variation.
- After the rebase onto `dc9ea005e`, CI's multi-GPU RL suites pass locally under torchrun: bitwise parity Varlen 3/3, Flex 3/3, Qwen3.5 4/4, and the 4-GPU uneven decode test 1/1.

Thanks @felipemello1! I checked both points against the full stack: this PR plus #5391 on top (`15b4d8702`), compared with main (`7db578e15`, which includes #5316).

**1. Runs on main vs this stack**

Both use the real recipes on the same host (GB300), with one change made identically on both commits: only 2 GPUs were free, so each run used a TP=1 trainer and one TP=1 generator (model configs rebuilt for that layout). Everything else is the recipe as checked in.

*Alphabet sort* (`rl_grpo_qwen3_0_6b_varlen`, Qwen3-0.6B, multi-turn, 10 steps, `target_offpolicy_steps=3`):

| | main | this stack |
| --- | --- | --- |
| validation reward, step 0 -> 10 | 0.179 -> 0.301 | 0.179 -> 0.286 |
| rollout reward, mean of steps 1-10 | 0.288 | 0.286 |
| policy age per step | 0,1,2,3,3,3,3,3,3,3 | 0,1,2,3,3,3,3,3,3,3 |
| wall time | 234 s | 231 s |

*DAPO math* (`rl_dapo_qwen3_4b_math_8k`, Qwen3-4B-Base, 50 steps):

| | main | this stack |
| --- | --- | --- |
| rollout reward, mean of steps 1-10 / 21-30 / 41-50 | 0.180 / 0.249 / 0.238 | 0.184 / 0.240 / 0.241 |
| response length, same windows | 1032 / 1260 / 1408 | 1036 / 1285 / 1549 |
| grad norm, same windows | 0.169 / 0.137 / 0.128 | 0.167 / 0.138 / 0.125 |
| AIME validation reward, step 0 -> 50 | 0.167 -> 0.133 | 0.133 -> 0.133 |
| wall time | 1189 s | 1197 s |

The async loop is not deterministic, so per-step values differ; the curves track each other. Earlier, a 2-GPU deterministic run (batch-invariant, on-policy, random-init Qwen3 debug model) was bitwise identical to main on every training metric (loss, grad norm, rewards, entropy, trainer-vs-generator logprobs, policy age); only time-to-first-token latency differed.

*vLLM logs.* After normalizing actor names, progress bars and throughput samples, every engine line matches: the full `Initializing a V1 LLM engine ... with config:` line, KV cache size, CUDA graph capture, model loading memory, and warnings. Neither branch logged an error. The DAPO pair first differed in two places, and both came from noise in that first main run:

- KV cache size: 1,733,824 vs 1,733,680 tokens (20 MiB more non-torch memory at startup on this stack).
- AIME step-0 validation: 5/30 vs 4/30 problems (greedy, but 8K-token answers decoded in one batch without batch invariance, plus Math-Verify timeouts that score zero).

Two more startup + step-0 validation runs per commit, alternating main and this stack, all matched this stack's numbers exactly: 9.42 GiB consumed, 1,733,680 KV cache tokens, 0.133 validation, and identical vLLM engine lines.

**2. Verbatim check**

For every function and method in the old files, I compared `ast.unparse` of its body (formatting-insensitive, docstrings removed) with its new home. I also diffed comment lines. Code that moved without a matching function name (the `EngineArgs` block, the request admission loop) was compared as statement blocks after variable renames.

- Identical: 23 functions in the generator split, 10 in the provisioning move, 10 in the router split, and 36 in the controller and rollouter. The `EngineArgs` block (now `VLLMEngine._build_engine_args`) and the admission loop (now `VLLMEngine.add_requests`) are also identical apart from variable renames.
- The rest differ only in the intended ways:
  - renames (`VLLMGenerator` -> `Generator`, `_RequestMetricsInputs` -> `RequestMetricsInputs`, the `extra_engine_args` field);
  - delegation to the engine, the engine loop and the actor system;
  - peers fanning in `FinishedRequest`s plus the policy version, with rank 0 building each `Completion` from the same values;
  - `ServiceHandle` replacing the `flatten("rank").slice(rank=0)` calls;
  - the router's private methods made public;
  - `num_generators` read from config instead of the mesh count.
- Visible but behavior-neutral: the log line "vLLM rejected request" is now "Engine rejected request", the trace span `vllm_init` is now `engine_init`, and the engine thread is named `engine-loop` instead of `vllm-engine`.
- Dropped comments are either reworded in their new location or described the old placeholder-`min_policy_version` fan-in, which no longer exists.

No changes were needed. I'll do 3 (restructuring the comments and docstrings) as a follow-up PR.
