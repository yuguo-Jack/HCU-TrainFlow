# [rl] One scoring step and one metrics step for every RL loss; add DPPOLoss

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5474) · state: open · merged: False

## Original PR description

**TLDR:** The RL losses now share one function that scores the sampled tokens and one that logs the metrics every loss logs, so a loss file holds only its own per-token loss. `DAPOLoss` and `GRPOLoss` run the same ops in the same order (bitwise unchanged vs main), and `DPPOLoss` is the second loss built on the two functions.

**Problem**
1. `DAPOLoss.__call__` does everything inline: temperature, trainer logprobs, the non-finite mask, the ratio, the PPO clip and 7 metrics (`trainer/losses/dapo.py:73-167`).
2. Each new loss copies that code. The open DPPO, IPO and score-centering PRs each carry a copy and import DAPO's private `_normalize` and `_MAX_LOG_RATIO`.
3. Each loss lists its inputs as keyword-only arguments, and the trainer passes every input to every loss (`TrainingMicrobatch.loss_kwargs`).
4. So an input added for one loss crashes the others. The policy-age-0 metric PR adds `is_policy_age_0`, and DPPO, IPO and score centering would fail with `TypeError` once those PRs land.

**Solution**
1. `losses/common.py` adds `score_tokens(logits, labels, **loss_inputs)`. It runs DAPO's first steps unchanged: divide by the temperature, trainer logprobs and entropy, drop tokens with a non-finite generator logprob, ratio. It returns them as a `ScoredTokens`.
2. `policy_metrics(tokens, own_sums, ...)` adds the 5 metrics every loss logs and divides every sum by `global_loss_token_counts`.
3. Each loss takes `**loss_inputs` and passes them to `score_tokens`. A new input is one keyword argument with a default there, and no loss signature changes. An unknown key still raises.
4. `DAPOLoss` keeps its config, ops and op order. `GRPOLoss` is untouched, apart from a TODO for Dr. GRPO.
5. `DPPOLoss` (https://arxiv.org/abs/2602.04879) drops a token once `sign(A) * (p - p_gen) > 0.2`, and trains the others with `-A * detach(min(p / p_gen, 5)) * log p`. It is the standalone DPPO PR's loss, already reviewed twice there, rebuilt on the two functions: 120 lines instead of 157.

```text
before:  DAPOLoss = temperature + logprobs + mask + ratio | PPO clip     | 7 metrics
         DPPOLoss = temperature + logprobs + mask + ratio | trust region | 7 metrics   (a copy)
after:   score_tokens ──> DAPOLoss: PPO clip     ──> policy_metrics
                      └─> DPPOLoss: trust region ──> policy_metrics
```

**Results**
```text
Numerics: bitwise identical for DAPOLoss and GRPOLoss (output, logits grad, every metric):
          the same torch ops on the same tensors, in the same order. Only the metric dict's key order changes.
          main vs this PR, torch.equal, CPU and CUDA (H100)                                    16/16 cases equal
Lines:    dapo.py 167 -> 97; new common.py 177; DPPOLoss 120 (157 as a standalone copy)
```

You may ask:
- Why `**loss_inputs` instead of named arguments on each loss? Named arguments on every loss are what let one loss's new input crash the others. `score_tokens` keeps the named, typed list, in one place.
- Why not a base class with one `__call__` and a per-loss hook? Each loss's `__call__` shows its whole computation in ~25 lines; a hook would hide half of it in the base class.
- Why not Dr. GRPO's fixed normalizer too? It changes every GRPO recipe's gradient scale (~10x smaller in an earlier 2xH100 smoke run) and the RL CI loss reference. No recipe asks for it yet, so it's a TODO for an opt-in field that divides by a config constant.
- Why no binary-KL DPPO? The paper finds it on par with binary TV. It's a TODO in the code.

NOTE: `DPPOLoss`'s `loss/mean` is the REINFORCE surrogate `-A * w * log p`, so it can't be compared with `DAPOLoss`'s on the same dashboard. No recipe uses `DPPOLoss` yet.
