# [rl] FULL CUDA graphs for linear-attention generators at DP>1

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5490) · state: open · merged: False

## Original PR description

**TLDR:** At generator DP>1, linear-attention models (GDN, KDA layers) now keep FULL CUDA graphs instead of falling back to FULL_DECODE_ONLY, so prefill steps replay a graph instead of running eager. Qwen3.5-35B-A3B, EP = DP = 4 on GB300: output tokens per second 1.55x / 2.02x at 64 / 256 sequences per engine. Not bitwise when another DP rank prefills; the generator-vs-trainer logprob gap is unchanged. No linear-attention recipe on main captures graphs at DP>1 yet.

**Problem**
1. At DP>1, our linear-attention metadata builder tells vLLM it can only graph uniform (decode-only) batches, so vLLM turns FULL into FULL_DECODE_ONLY.
2. FULL_DECODE_ONLY has no graph for a step with prefill tokens, so that step runs eager.
3. vLLM runs every DP rank in the same graph mode, so when one rank prefills, the other ranks' decode steps run eager too.
4. **Who hits it.** The generator allows DP>1 only to supply EP ranks (`Generator.Config.__post_init__`), so every EP generator does.
5. **Cost.** An eager 2048-token prefill step takes 271 ms (median), ~27 ms of it GPU work (profiled); replayed, 20 ms (GB300, Dist-MoE).

**Solution**
1. The builder reports full graph support at DP>1. Micro-batching and dual-batch overlap still report uniform-only.
2. That alone crashes: vLLM pads a decoding or idle DP rank to the busiest rank's token count, then looks up a decode graph of that size, and no decode graph is that large.
3. `TorchTitanCudagraphDispatcher.dispatch` now uses the decode graphs up to the largest one captured (`max_decode_capture_size`), and the mixed-batch graph above it, as a prefilling rank does.
4. **Batch-invariant runs keep main's behavior (TODO):** uniform-only support at DP>1, and decode batches on the decode kernels. The packed kernels don't match the decode kernels bitwise (check below).
5. Unchanged: FULL_DECODE_ONLY, NONE, ubatching / DBO, the decode graphs, and every recipe.

```text
one step at DP = 4: rank 0 prefills a 2048-token chunk, ranks 1-3 decode 64 sequences
main:     synced mode NONE -> 4 ranks eager, unpadded
this PR:  synced mode FULL -> 4 ranks replay 2048-token graphs
          ranks 1-3: uniform decode, 2048 > largest decode graph -> mixed graph
```

**Results**
```text
GB300, Qwen3.5-35B-A3B-Base, 4 vLLM engines (EP = DP = 4) with the generator's engine settings (FULL, 2048-token
chunks), on main plus the Dist-MoE inference PRs (not on main yet); GSM8K prompts, 256 output tokens, temperature 1;
warm pass, wall clock; main and this PR back to back.

                                           seq/engine   main        this PR
Dist-MoE EP 4, DP 4   prefill, slowest engine   64      0.90 s  ->  0.08 s
                                                256     5.04 s  ->  0.68 s
                      output tok/s, 4 engines   64      10.4k   ->  16.2k    1.55x
                                                256     16.2k   ->  32.7k    2.02x
                      decode step (median)      64      9.1 ms  ->  9.0 ms
                      engine 0 prefills, 1-3 decode padded to 2048 (3 steps)   865-924 -> 59-62 ms
stock EP 1, DP 4      output tok/s, 4 engines   64      6.95k   ->  7.92k    1.14x
                                                256     13.9k   ->  19.1k    1.38x
graph capture at init   Dist-MoE 16 -> 26 s, 0.16 -> 0.40 GiB; stock 13 -> 19 s, 0.19 -> 0.68 GiB
```
- Engine 0 joins 6 steps late, so it prefills while its peers decode. Every DP-synced step on every engine replayed a FULL graph.
- Stock EP 1, DP 4: every engine holds every expert. The generator rejects this config; it shows the effect without Dist-MoE.
- H100, DP2 x TP2 x EP4, a Terminal-Bench-shaped multi-turn replay with a capturable MoE dispatcher not on main: wall time 445 -> 246 s (-45%); KV blocks -2.0%.
- Both runs bounded the decode graphs by `max_num_seqs`. That routes the same batches whenever `max_num_seqs` is a capture size: true on GB300 (256), not checked for the H100 run.

**Numerics:** not bitwise when another DP rank's load changes. On steps where another rank prefills past the largest decode graph, a decoding rank's tokens run through the mixed graph's prefill kernels.
```text
mean |trainer - generator| logprob, GB300, 256 seqs/engine (trainer: Dist-MoE EP 4 + FSDP 4)
Dist-MoE   main 1.690e-2 | this PR 1.629e-2
stock      main 1.769e-2 | this PR 1.767e-2
across 6 main / PR pairs, this PR is lower in 4 and higher in 2 (largest gap 6.6%)

H100, TP1, a decoding rank's mean |dlogprob| when its peer injects 1,500-token prompts, vs no injection
this PR (mixed graph) 0.0058 | main's FULL_DECODE_ONLY (eager vs graphed) 0.0073 | FULL run twice 0
```

**Batch-invariant check** (Qwen3.5-0.8B-Base, GB300, 8 seeded requests, each compared with the same requests alone at DP = 1):
```text
                                                     requests that differ               max |d|
DP = 2, guard removed, padded by a prefilling peer   6 of 8, from the 1st padded step   6.9e-2
DP = 1, mixed with long prefills (main's path)       4 of 8, from the 1st mixed step    4.1e-2
```
Main's DP = 1 mixed steps already break bitwise output. Without the guard, every step where a peer prefills would break it too.

You may ask:
- Why not fall back to eager above the largest decode graph? By then vLLM has settled on FULL for every rank and re-dispatches with only FULL allowed (`valid_modes={FULL}`), so "no graph" is an AssertionError, not an eager step.
- Why the largest captured decode graph and not `max_num_seqs`? Capture sizes can skip `max_num_seqs` (a user list, or sequence parallelism dropping sizes that aren't TP multiples). A decode batch in that gap would run eager, and one eager rank makes every DP rank eager.

NOTE:
- **DP = 1, normal mode:** a decode batch in a capture-size gap now replays the mixed graph instead of running eager, on the kernels a mixed step already uses.
- **Not run:** KDA at DP>1 (no recipe); stock MoE at EP 4; batch-invariant mode end to end; a full RL job.

**Follow up**
- [ ] With a capturable MoE generator on main: flip the 35B Terminal-Bench recipe to FULL and add a DP2 GDN case to `test_generator_uneven_decode.py`.
- [ ] Batch-invariant GDN/KDA: make the packed kernels with cached state match the decode kernels bitwise, then drop both batch-invariant clauses (the TODO in `linear_attention.py`).

**Test plan**
```
pytest tests/rl/unit_tests/gpu/test_gdn_graph_metadata.py   # 9 passed (runs on CPU too)
pytest tests/rl/unit_tests/gpu/test_gdn_cudagraph.py        # 4 passed, GB300, Qwen3.5-0.8B-Base, regular + batch-invariant
pytest tests/rl/unit_tests/cpu                              # 497 passed, 9 skipped
```
Each change, reverted alone, fails a test: the DP>1 support level, the largest-decode-graph bound (vs `max_num_seqs`), the batch-invariant support guard, and the dispatcher's batch-invariant clause.
