## Agent details

Written with Claude Code: the analysis, measurements and test plan below.

**TLDR:** At generator DP>1, linear-attention models (GDN, KDA layers) now keep FULL CUDA graphs instead of falling back to FULL_DECODE_ONLY, so prefill and mixed steps replay a graph instead of running eager. Qwen3.5-35B-A3B at DP 2 x EP 2 (GB300): one prefill 0.68 s -> 39-157 ms (2k-16k tokens); at EP = DP = 4, output tokens per second 1.55x / 2.02x at 64 / 256 sequences per engine (earlier measurement). No recipe runs this today: the one hybrid DP>1 recipe uses eager mode because its MoE dispatcher can't be captured; once it moves to Dist-MoE, this PR lets it run FULL instead of FULL_DECODE_ONLY.

```text
one step at DP = 2: rank 0 prefills a 16k-token chunk, rank 1 decodes 24 sequences
main:     linear attention reports uniform-only at DP>1 -> mode FULL_DECODE_ONLY -> both ranks eager
this PR:  full support -> mode FULL -> both ranks replay the 16384-token mixed graph (rank 1 padded to it)
```

```python

# after
```

**Problem**
1. At DP>1, the linear-attention metadata builder tells vLLM it can only graph uniform (decode-only) batches, so vLLM turns FULL into FULL_DECODE_ONLY.
2. FULL_DECODE_ONLY has no graph for a step with prefill tokens, so that step runs eager.
3. vLLM runs every DP rank in the same graph mode, so when one rank prefills, the other ranks' decodes run eager too.
4. **Who hits it:** the generator allows DP>1 only to supply EP ranks (`Generator.Config.__post_init__`), so any EP generator of a hybrid model in FULL mode. Today that is no recipe: `rl_grpo_qwen35_35b_a3b_terminal_bench` (generator DP 2 x EP 4) runs `mode="NONE"` because its all-to-all MoE dispatcher copies split sizes to the host, which graph capture rejects (`torchtitan_recipes/rl/verifiers_terminal_bench.py:299-306, 413`).
5. **Cost:** an eager prefill takes ~0.68 s at any size from 2k to 16k tokens (flat, so host-bound), vs 39-157 ms replayed (Results).

**Solution**
1. The builder reports full CUDA-graph support at DP>1. Micro-batching and dual-batch overlap still report uniform-only.
2. Padded decode ranks need no new code: position 1's dispatcher already replays the mixed graph for a decode batch above the largest decode graph.
3. **Batch-invariant runs keep uniform-only support at DP>1 (TODO):** the packed kernels with cached state don't match the decode kernels bitwise (measured for GDN; KDA assumed).
4. Unchanged: DP = 1, FULL_DECODE_ONLY and NONE modes, ubatching / DBO, the decode graphs, every recipe.

**Verdict: Approve.** The PR relaxes one condition that position 1's dispatcher made unnecessary, it is well measured, and the remaining item is optional test trimming.

**What this PR does.** At DP>1, `TorchTitanLinearAttentionMetadataBuilder.get_cudagraph_support` now reports `ALWAYS` instead of `UNIFORM_BATCH`, so vLLM keeps FULL mode for GDN/KDA models and no longer downgrades to FULL_DECODE_ONLY. Steps that contain prefill tokens on any DP rank now replay a mixed graph instead of running eager. Batch-invariant mode, ubatching and DBO still report uniform-only. DP>1 now behaves the same as DP=1, where FULL already captures mixed graphs, and position 1's dispatcher already sends DP-padded decode batches to the mixed graph.

**Example.**
```text
Qwen3.5 MoE, DP=2, cuda_graph.mode="FULL"
step: rank 0 prefills a 1500-token chunk, rank 1 decodes 3 seqs (or is idle)
base (pos. 1): UNIFORM_BATCH -> resolved mode FULL_DECODE_ONLY -> both ranks NONE (eager)
this PR:       ALWAYS        -> mode FULL -> both ranks replay the >=1500-token mixed graph
               (rank 1 padded; an idle rank's dummy batch also padded)
batch_invariant=True at DP=2: unchanged (FULL_DECODE_ONLY), so bitwise parity is kept
```

<details><summary>Details</summary>

- **Gate.** The problem is real on the base branch: the eager prefill is host-bound at about 0.68 s. The fix is in the layer that owns it: the builder's support level was the only thing forcing FULL_DECODE_ONLY, and the reason for it (padded decode ranks) is now handled by `TorchTitanCudagraphDispatcher.dispatch`. No recipe uses this today. The consumer is named (`rl_grpo_qwen35_35b_a3b_terminal_bench` after it moves to Dist-MoE), and the change removes a restriction rather than adding a knob, so it passes.
- **Batch-invariant ordering.** `get_cudagraph_support` reads a process-global flag. `Generator.__init__` calls `set_batch_invariance` (`generator.py:217`) before it builds the engine, and the engine uses `external_launcher`, so vLLM's workers run in the same process and see the flag when the cudagraph mode is resolved.
- **Two batch-invariant clauses.** When batch-invariant mode is on at DP>1, the mode resolves to FULL_DECODE_ONLY, so the dispatcher clause in `worker.py:83` (FULL only) never runs there. It still matters at DP=1. The TODO that refers to both clauses is accurate.
- **CI split.** Giving each test its own torchrun launch follows the file's rule that each engine frees its GPU memory only at process exit.
- **New GPU test.** It fails on the base branch (no FULL non-uniform record), so it guards this change. It also covers the idle-rank dummy batch through the packed path, which no other test covers.
- **Cost.** Per rank, about 1.7 GiB more graph memory and about 40 s more capture time at max_num_batched_tokens 16384. This is the same cost DP=1 FULL already pays, and it is documented.

</details>

Not verified: KDA at DP>1, including the idle rank's dummy batch going through the KDA packed path in a mixed graph. This needs a GPU run, and no test or recipe covers it.
