# Fix tuple assignment in spmd_types.py

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5283) · state: open · merged: False

## Original PR description

normalize_partition_spec in torchtitan/distributed/spmd_types.py overwrote entries[dim] instead of accumulating into it, so when two mesh axes independently shard the same tensor dimension (a supported configuration, e.g. PartitionSpec((DP, CP))), only the last axis survived and the other was silently dropped from the synthesized spec used by the shard-order validator.

Fix

Changed entries[dim] = (MeshAxisName(axis_name),) to entries[dim] = entries[dim] + (MeshAxisName(axis_name),) so all axes sharding a given dim are preserved, in order.

Test plan

Isolated the function’s logic with stub types (the real spmd_types package is internal/unavailable) and confirmed: before the fix, two axes (dp, cp) both sharding dim 0 collapsed to (('cp',), ()) — dp lost; after the fix, (('dp', 'cp'), ()) — both preserved in insertion order. Verified the patched file parses correctly.

**Summary:** The change makes sense as a local fix. Accumulating is better than overwriting, because the old code silently dropped every axis except the last. Before merging, though, I think we need to settle whether this code path can actually be reached, and what shard order it should produce. The PR also has no test.

---

#### 1. The example in the description never reaches this code

`_normalize_partition_spec` only runs for a side that has **no** `partition_spec` (`torchtitan/distributed/spmd_types.py:344-347`). If a layout is written as `PartitionSpec((DP, CP))`, its spec is used directly and never goes through this function. So the case this change affects is narrower than the description says: a `SpmdType` with no `partition_spec` whose `local_type` has two or more axes with `S(d)` on the **same** dim, e.g. `SpmdType({DP: S(0), CP: S(0), TP: R})`.

In that case the old code does go wrong. For example:
- `src = SpmdType({DP: V, CP: V, TP: R}, partition_spec=PartitionSpec((DP, CP), None))`
- `dst = SpmdType({DP: S(0), CP: S(0), TP: <changed>})`

The old code builds `dst_spec = ((CP,), ())`, compares it with `((DP, CP), None)`, and wrongly raises "changes shard order". With this PR it builds `((DP, CP), ())` and the check passes.

**Please check whether `spmd_types` accepts such a layout at all.** If `SpmdType` rejects (or normalizes away) several axes with `S(d)` on the same dim when there is no `partition_spec`, then this code can't be reached and the fix changes nothing. In that case an explicit check with a clear error would be more honest than silently building a spec.

#### 2. The synthesized order comes from dict insertion order

With this fix, the order of axes in `entries[dim]` is whatever order they were inserted into `layout.local_type` (via `_per_axis_types`). The validator then treats that order as meaningful: it checks `dst_axes == src_axes + (changed_axis,)`, and `test_partition_spec_order_controls_state_shard` shows that `(DP, CP)` and `(CP, DP)` put different global slices on each rank.

So `{DP: S(0), CP: S(0)}` and `{CP: S(0), DP: S(0)}` would now build different specs, and one of them could be wrongly rejected (or wrongly accepted) against an explicit `PartitionSpec`. If `spmd_types` defines a canonical order for multiple shards on one dim with no spec (for example, mesh axis order), build the spec in that order. If it doesn't define one, the shard order is ambiguous, and raising a `ValueError` that asks for an explicit `partition_spec` is probably the right contract.

#### 3. Update the comment at line 336-337

```python
# 3) If one side has no PartitionSpec, synthesize the simple
# one-axis-per-dim form from its S(dim) local types.
```
This says the author assumed one axis per dim. If multiple axes per dim are now supported, the comment should say so and state which order is used. If they're not supported, that assumption should be enforced in code rather than only stated in a comment.

#### 4. Missing unit test

The CLAUDE.md rules require CPU unit tests. `tests/unit_tests/cpu/test_parallelism_context.py::TestSpmdLayout` already tests `spmd_validate_redistributions` (`test_rejects_partition_spec_reorder_redistribute`, `test_rejects_multi_axis_redistribute`). Please add a case next to them that pairs an explicit `PartitionSpec((DP, CP), None)` with a no-spec layout `{DP: S(0), CP: S(0), ...}`. It should fail on `main` and pass with this PR, and it should also pin down the expected behavior when the insertion order is reversed (`{CP: S(0), DP: S(0)}`).

The test in the description used stub types instead of the real `spmd_types` package, so it doesn't show how real `SpmdType` objects behave. A unit test in the repo would cover that.

#### 5. Nit
`entries[dim] += (MeshAxisName(axis_name),)` is equivalent and a bit shorter. It's safe here because the elements are tuples, so `[()] * ndim` doesn't share anything mutable.

---

**Recommendation:** The direction is right, but please (a) confirm with `spmd_types` that multiple axes with `S(d)` on the same dim and no spec can happen, (b) choose a deterministic order or raise an error if the order is ambiguous, (c) update the step-3 comment, and (d) add a unit test. cc @tianyu-l. @pianpwk can probably answer (a) and (b) quickly, since the TODO in this function is theirs.
