## Agent details

Written with Claude Code: the analysis, measurements and test plan below.

**TLDR:** The Muse Spark debug recipe as shipped fails at the first backward with `CheckpointError`. Cause: norms of different layers share one compiled region but differ in a float, `gain_center`. Compiled code now reads `gain_center` from an fp32 CPU scalar tensor. Training is bitwise identical to main wherever main runs, with the same kernel time and one fewer graph.

```text
forward:    layer 0 norm -> graph A (gain_center=0.707 baked in)
            layer 1 norm -> guard fails -> graph B (gain_center is an input, a CPU scalar)
recompute:  layer 0 norm -> graph B (checked first; its guards accept any gain_center)
            B saves [cpu scalar, rstd, ...], A saved [rstd, ...]  -> CheckpointError
```

**Problem**
1. `post_attention_norm` (region `muse_spark_rmsnorm`) and `post_ffn_norm` (region `muse_spark_input_scaled_rmsnorm`) use `gain_center = 1/sqrt(2 (layer_id + 1))`: a different float in each layer.
2. Dynamo bakes the first float into the graph. Layer 1's value fails that guard, so Dynamo recompiles the region with the float as a graph input.
3. Activation remat recomputes layer 0 in backward. Dynamo checks the newest graph first, and it accepts layer 0's value.
4. That graph saves one more tensor, the CPU scalar. `torch.utils.checkpoint` sees different saved tensors than in forward and raises.
5. CI misses it: the Muse Spark integration tests turn on SPMD typechecking, which empties `local_compile.regions` (`torchtitan_recipes/tests/__init__.py:30`).

Pure PyTorch repro:
```python
import torch
import torch.nn as nn
import torch.nn.functional as F
from torch.utils.checkpoint import checkpoint


class Norm(nn.Module):
    def __init__(self, dim, gain_center):
        super().__init__()
        self.weight = nn.Parameter(torch.randn(dim) * 0.1)
        self.gain_center = gain_center  # torch.tensor(gain_center) -> OK

    @torch.compile(fullgraph=True)
    def forward(self, x):
        return F.rms_norm((self.weight + self.gain_center) * x, (x.shape[-1],), None, 1e-6)


a, b = Norm(256, 0.7071).cuda(), Norm(256, 0.5).cuda()
x = torch.randn(64, 256, device="cuda", requires_grad=True)
checkpoint(lambda t: b(a(t)), x, use_reentrant=False).sum().backward()  # CheckpointError
```

**Solution**
1. `MuseSparkRMSNorm` keeps an fp32 CPU scalar tensor copy of `gain_center`.
2. Under `torch.compiler.is_compiling()`, `_get_effective_weight` reads the tensor. Every graph of the region then takes it as an input and saves the same tensors, so whichever graph the recompute picks matches the forward.
3. Eager keeps the float: SPMD typechecking rejects an untyped tensor.
4. The input-scaled norm still recompiles once when the routed-token count changes between layers. That recompile is now harmless.
5. A TODO links the upstream PyTorch issue (closed with a clearer error; recompute still picks the newest graph).

You may ask:
- **Why not `dynamic=True` on the regions?** It fixes the error but makes the token dim symbolic too. Forward is 2.1-2.5x slower at T=16384 (rmsnorm, D=4096: 83 -> 183 µs), and 15-28 µs slower than this PR at T=64.
- **Why not `dynamic=False`, one graph per gain_center, like eps?** The debug model's 8 gains each run in two input-scaled norms (post-FFN and MoE output): 16 graphs, against that region's limit of 8. Static shapes would also recompile for every routed-token count.
- **Why not a buffer, or the tensor in eager too?** An untyped tensor fails SPMD typechecking in eager (`SpmdTypeError: args[1] missing axis mesh_cp`). So a buffer would not remove the branch, and it needs re-init after the meta-device build.
- **`eps` also differs between norms. Same bug?** No. `rms_norm` takes `eps` as a Python float, so each value gets its own graph and dispatch is exact. Checked with eps 1e-5 and 1e-8 norms under checkpoint.

**Test plan**
- New GPU test `test_norm_region_under_activation_checkpoint`: two layers' post norms under `torch.utils.checkpoint`, for both regions (the input-scaled case also changes the token count). It raises `CheckpointError` on main, and passes here, bitwise equal to the run without checkpoint.
- Bisect on main: the `muse_spark_input_scaled_rmsnorm` region alone raises `CheckpointError`; each other region alone trains.
- Muse Spark GPU tests: 9 passed. Muse Spark + MoE CPU tests: 105 passed; 2 `test_dist_moe` topology failures also fail on main.
- Pre-commit clean. Pyrefly: the same 2 `torch_checkpointing` errors as main.

This works around a PyTorch problem, not a Muse Spark one. With non-reentrant `torch.utils.checkpoint`, the recompute can land on a different Dynamo cache entry than the original forward used, because the newest entry is checked first and automatic dynamic makes it accept earlier inputs. If that entry saves a different set of tensors, checkpoint raises. Any `local_compile` region under remat that recompiles partway through the forward is exposed to this. The comment explains the mechanism, but there's no TODO or upstream issue, so nobody will know when the tensor copy and the `is_compiling()` branch can go (CLAUDE.md principle 3).

Fix: file a pytorch/pytorch issue with the 15-line repro from the description, then add a line like:
```python
        # TODO(pytorch/pytorch#NNNN): drop the tensor copy once checkpoint recompute
        # replays the forward's compiled graph.
```
