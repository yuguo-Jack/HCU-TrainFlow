# [graph_trainer] Reduce SimpleFSDP gradients in reduce_dtype, as FSDP2 does

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5171) · state: closed · merged: True

## Original PR description

Stack from [ghstack](https://github.com/ezyang/ghstack/tree/0.12.0) (oldest at bottom):
* __->__ #5171

This fixes a numerics mismatch between eager FSDP2 and SimpleFSDP (GraphTrainer).

pytorch/pytorch#194434 ("[FSDP2] Separate sharded and unsharded gradient dtypes", 38d3f6fd0d6e, in the 2026-10-02 nightly) changes the dtype of FSDP2's unsharded-parameter gradients when `grad_dtype` is not specified: they now default to `reduce_dtype` instead of `param_dtype`. With torchtitan's mixed-precision policy, that is fp32 instead of bf16.

This changes the backward all-reduce of TP-replicated parameters (typed R on TP, e.g. sequence-parallel norm weights and the MoE router gate): eager FSDP2 now sums the per-TP-rank partial gradients in fp32 and reduce-scatters the fp32 sum. SimpleFSDP also sums them in fp32, but the sum is rounded back down to bf16 to match the dtype of SimpleFSDP's unsharded weight, a bf16 autograd intermediate, before the reduce-scatter. The router gate's `grad_weight`, which `HiMidLoLinear` computes in fp32, is rounded the same way. As a result the dense Llama3/Qwen3 and the Qwen3 MoE numerics tests diverge from eager at step 2, and are xfailed in #5110 and #5133.

This PR adds a custom autograd Function that runs SimpleFSDP's gradient reductions the way FSDP2 does. All of those tests match eager bitwise again, and their xfails are removed.

## Backward, before and after

Both sides use torchtitan's default mixed-precision settings:

| Field | Value | Source |
|---|---|---|
| master (sharded) param dtype | fp32 | |
| `param_dtype` | bf16 | `training.mixed_precision_param` |
| `reduce_dtype` | fp32 | `training.mixed_precision_reduce` |
| `grad_dtype` on the param | unset | |

### Issue 1: R-on-TP parameters (e.g. sequence-parallel norm weights)

Each TP rank computes a partial gradient (over its tokens), which must be summed over TP before the FSDP reduce-scatter.

```
Eager FSDP2
  compute -> wgrad bf16
  -> LEAF .grad: unsharded param, grad_dtype = reduce_dtype       -> fp32
     ---- autograd ends; FSDP2 post-backward ----
  -> TP all-reduce (fp32) -> reduce-scatter (fp32)

SimpleFSDP on main
  compute -> wgrad bf16
  -> spmd.convert(I -> R) bwd: cast fp32, TP all-reduce (fp32)
  -> autograd casts to the bf16 all-gathered weight's dtype       <- rounds the TP sum
  -> redistribute bwd: cast fp32, reduce-scatter (fp32)

SimpleFSDP, this PR
  compute -> wgrad bf16
  -> output grad dtype declared fp32                              -> cast up (exact)
  -> _UnshardAndReduceGradFunction bwd: TP all-reduce (fp32), reduce-scatter (fp32)
```

### Issue 2: MoE router gate (HiMidLoLinear, also R on TP)

`HiMidLoLinear`'s backward computes `grad_weight` in fp32 by design.

```
Eager FSDP2
  HiMidLo bwd -> grad_weight fp32
  -> LEAF .grad: grad_dtype = reduce_dtype                        -> kept fp32
     ---- autograd ends; FSDP2 post-backward ----
  -> TP all-reduce (fp32) -> reduce-scatter (fp32)

SimpleFSDP on main
  HiMidLo bwd -> grad_weight fp32
  -> autograd casts to convert output's dtype (bf16)              <- issue 2
  -> convert bwd: cast fp32, TP all-reduce (fp32)
  -> autograd casts to the bf16 all-gathered weight's dtype       <- issue 1
  -> redistribute bwd: cast fp32, reduce-scatter (fp32)

SimpleFSDP, this PR
  HiMidLo bwd -> grad_weight fp32
  -> output grad dtype declared fp32                              -> kept fp32
  -> _UnshardAndReduceGradFunction bwd: TP all-reduce (fp32), reduce-scatter (fp32)
```

For every other parameter, the bf16 wgrad reaches the reduce-scatter with no reduction in between, and the bf16 -> fp32 cast is exact wherever it happens, so those gradients already matched eager.

## Fix

`_UnshardAndReduceGradFunction` covers one parameter's unshard and gradient reduction:

- **Forward:** wrap the TP/EP-local shard as a DTensor on the DP mesh, cast to `param_dtype`, all-gather (no-op for DDP), and return the unsharded weight. Same ops as before.
- **Output gradient dtype:** `ctx.set_output_grad_dtype(reduce_dtype)`, the same value FSDP2 gives its unsharded parameter's `grad_dtype`. An fp32 gradient flowing in is kept, and a bf16 one is cast up exactly.
- **Backward:** all-reduce (P -> I) over the non-DP axes where the parameter is R, then Partial -> the DP placements (reduce-scatter for FSDP, all-reduce for DDP, both for HSDP), all in `reduce_dtype`, in one node with no bf16 intermediate.

Both branches of `ReplicateComputation.replicate_compute` (with and without TP/EP axes) use it, replacing the `redistribute -> to_local -> spmd.convert` chain.

Dynamo cannot trace `ctx.set_output_grad_dtype` yet, so the call is skipped under `torch.compile`. GraphTrainer traces with `make_fx` and is unaffected; only the SimpleFSDP unit tests that use `torch.compile(backend="aot_eager")` take this path, and none uses mixed precision. The guard can go once the Dynamo support (pytorch PR, https://github.com/pytorch/pytorch/pull/200311) is in the nightly.

**Compared to #5106**, which all-gathers R parameters in fp32 so the TP sum stays fp32:
- the all-gather stays in bf16, so there are no extra fp32 all-gather buckets (#5106: 15 -> 28 in the Llama3 debug model);
- it also fixes issue 2, which #5106 cannot reach because the router's rounding happens before the TP sum.

## Test plan

- `test_numerics.py`: the five tests above pass. The strict xfails from #5110 and #5133 are removed, and the MoE test now uses the bitwise `run_loss_compare` instead of `run_loss_compare_close`.

  - `test_tp_reduced_grad_stays_in_reduce_dtype`: per-TP-rank grads 1 and 2**-9 (exact in bf16, but their sum is not) must reach the reduce-scatter as 1 + 2**-9.
