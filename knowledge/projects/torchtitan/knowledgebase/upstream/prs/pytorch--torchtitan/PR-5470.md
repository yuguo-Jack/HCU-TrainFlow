# [tokenizer] Preserve non-special added tokens

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5470) · state: closed · merged: True

## Original PR description

`_infer_special_tokens` reads `special=False` from `added_tokens_decoder`, then passes every token to `add_special_tokens`. That call marks the ordinary added tokens special too, so default decoding drops them.

This affects Qwen3's reasoning and tool-call delimiters. I changed the registration call to `add_tokens`, which keeps each `AddedToken.special` flag. True special tokens such as EOS are still filtered. The change does not alter token IDs, model parameters, or checkpoint keys.

Reproducer (downloads only two tokenizer files):

```python
import torchtitan
from huggingface_hub import model_info, snapshot_download
from tokenizers import Tokenizer
from torchtitan.components.tokenizer import HuggingFaceTokenizer

repo_id = "Qwen/Qwen3-0.6B"
revision = model_info(repo_id).sha
path = snapshot_download(
    repo_id,
    revision=revision,
    allow_patterns=["tokenizer.json", "tokenizer_config.json"],
)
reference = Tokenizer.from_file(f"{path}/tokenizer.json")
wrapped = HuggingFaceTokenizer(tokenizer_path=path)
print("torchtitan:", torchtitan.__file__)
print("revision:", revision)
for text in (
    "<think>reason</think>answer<|im_end|>",
    '<tool_call>{"name":"f"}</tool_call><|im_end|>',
):
    ids = reference.encode(text).ids
    print("reference:", reference.decode(ids))
    print("wrapped:", wrapped.decode(ids))
```

Observed on Qwen3 tokenizer revision `c1899de289a04d12100db370d81485cdf75e47ca`:

| Decoded content | Before | After / reference |
|---|---|---|
| Reasoning + answer | `reasonanswer` | `<think>reason</think>answer` |
| Tool call | `{"name":"f"}` | `<tool_call>{"name":"f"}</tool_call>` |

The new offline CPU regression uses a small WordLevel tokenizer and checks that encoding IDs stay the same, non-special added tokens survive decoding, EOS is still filtered, and `skip_special_tokens=False` still preserves both token kinds. It fails on main with `'hello world' != 'hello <domain> world'` and passes with the fix.

Test plan:

### Summary

The fix is correct and small, and I'd approve it with the nits below. In the Python binding, `Tokenizer.add_special_tokens` sets `special=True` on every `AddedToken` it receives. It also adds the content to the added vocabulary's special-token set, and `decode(skip_special_tokens=True)` uses that set to decide what to drop. `add_tokens` leaves the per-token flag alone. True specials still get registered, because `_process_special_token` defaults to `special=True` for plain-string top-level keys and for dict entries with no `special` field (`tokenizer.py:338`, `tokenizer.py:342`). After this change, `decode` matches the reference `tokenizers` and `transformers` behavior for Qwen3-style `<think>` and `<tool_call>` delimiters.

The PR doesn't change token IDs, model parameters or checkpoint keys, so the checkpoint-compatibility concern in CLAUDE.md doesn't apply.

### Blast radius

The only behavior change is in `HuggingFaceTokenizer.decode` when `skip_special_tokens` is left at its default (`True` in `tokenizers`). Every caller inside the repo already passes `skip_special_tokens=False`:
- `components/data/text_datasets.py:217`
- `models/muse_spark/renderer.py:799`
- `models/muse_glimmer/renderer.py:723`
- `components/renderer.py:143` (defaults to `False`)

In-repo training and rendering paths therefore don't change. Only external callers that rely on the default are affected, and they now get output that matches HF.

`MultiModalTokenizer.__init__` (`tokenizer.py:564`) looks tokens up by content via `get_added_tokens_decoder()`, which doesn't depend on the special flag, so it's unaffected.

### Comments

1. **The `.special` assertions probably don't catch the regression; the decode assertions do** (`test_tokenizer.py:154-156`). If I remember the Rust `AddedVocabulary::add_tokens` correctly, a token whose content is already in the added vocabulary is skipped when the map is updated. The old call would still have put it into the special-token set, though. If that's right, on `main` `get_added_tokens_decoder()[id].special` would still report `False` for `<domain>` while decode drops it anyway. That would also explain why the existing `_compare_tokenizers` check on `.special` (`test_tokenizer.py:280-288`) never caught this bug. Your PR says the test fails on `main` on the decode assertion, which fits this. Nothing needs to change, but a short comment that the decode check is the real regression guard would stop someone "simplifying" the test down to the flag checks.

2. **Naming is now slightly stale (nit).** `_process_special_token` and `_infer_special_tokens` now also handle ordinary added tokens. You updated the docstrings, which is enough for this PR, but the method docstring at `tokenizer.py:290` still says "Process a special token". A one-word tweak there ("Process a configured added token") would keep it consistent. I wouldn't rename the methods in this PR.

3. **Comment wording (nit)** at `tokenizer.py:389`: `# add_special_tokens would mark ordinary added tokens as special too.` explains why the code doesn't use something, which is useful. Something like `# add_tokens keeps each AddedToken.special flag; add_special_tokens would force special=True on all of them.` would say what the current code relies on.

4. **Edge case (no action needed).** If a token appears both as a plain-string top-level key (forced `special=True` by the fallback at `tokenizer.py:342`) and in `added_tokens_decoder` with `special: false`, both `AddedToken`s go into the same `add_tokens` call. I don't know of any real config shaped like that, and the old code made it special anyway, so this PR doesn't make it worse.

### Tests

The new offline WordLevel test covers the important properties: encode IDs are unchanged, a non-special added token survives default decode, EOS is still dropped, and `skip_special_tokens=False` keeps both. It needs no network or GPU, which suits a CPU unit test. As noted above, I couldn't run it here.

**Verdict:** LGTM once the nits are addressed (all optional). This is a correct root-cause fix, not a band-aid.
