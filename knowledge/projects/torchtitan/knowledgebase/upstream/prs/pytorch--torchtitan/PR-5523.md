# [moe][perf] DeepEP at EP > 1: send each token once per rank (3/3)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5523) · state: open · merged: False

## Original PR description

**TLDR:** At EP > 1 with DeepEP, the generator sends each token once per rank instead of once per expert, and the Triton routed-experts kernels read its routes: H100, Qwen3.5-35B-A3B experts, routed experts take 0.71-0.82x the time of DeepEP expand + stock GEMMs at EP = 4, 0.54-0.73x at EP = 8, CUDA-graph safe. The H100 DeepEP recipe (`search_r1`) turns it on for the generator.

**Stack** (3 PRs, merge bottom-up; this PR is in **bold**)

| # | PR | Independent? | Needs (stack positions) |
|---|---|---|---|
| 1 | Triton grouped GEMMs for the no-grad expert MLP, any dispatcher | yes | — |
| 2 | Triton routed experts: kernels read the routes, no dispatch | no | 1 |
| **3** | **DeepEP at EP > 1: send each token once per rank** | **no** | **2** |

**Problem**
1. **Today.** The generator's DeepEP dispatch uses the expand layout: one row per (token, local expert), so a token with 3 experts on a rank is copied 3 times.
2. **Then.** The rows go through the grouped GEMMs, each row is multiplied by its score in PyTorch, and DeepEP's combine sums them.
3. **Better layout.** DeepEP's compact layout sends one row per (token, rank) with the token's local expert ids, and the Triton routed-experts kernels already sort routes themselves.
4. **Gap.** TorchTitan uses compact only with a host sync (training), which CUDA graphs can't capture.

**Solution**
1. **Transport.** `deepep.dispatch_routes` / `combine_routes`: the compact layout without the host sync, inference only.
2. **Buffer.** Worst case EP x T rows; rows past the received count get id -1.
3. **Experts.** With DeepEP's inference dispatcher (`cuda_graph_compatible=True`), EP > 1 and grad off, `TritonRoutedExperts.forward` runs dispatch -> `triton_routed_experts_op(..., ep_size)` -> combine (DeepEP's ids are already local).
4. **Recipe.** `rl_grpo_qwen3_30b_a3b_deepep_search_r1_perf` applies the override to the generator only, in its own call (one `OverrideConfig` rejects overrides of nested nodes).
5. **Gate.** `TritonRoutedExperts` also accepts `fused_swiglu`'s activation (same SwiGLU math, not bitwise), which that recipe applies to both models. With both overrides, stack positions 1's and 2's paths run instead of the stock path too.
6. **Unchanged.** Training, DeepEP expand without the override, every other dispatcher.

```text
before:  dispatch (expand: row per token x expert) -> grouped GEMMs -> x scores -> combine
after:   dispatch (compact: row per token x rank)  -> [route sort + w13/SwiGLU + w2 + fp32 combine] -> combine
```
