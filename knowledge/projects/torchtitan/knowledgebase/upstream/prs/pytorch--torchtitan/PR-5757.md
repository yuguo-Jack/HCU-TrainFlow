# [tokenizer] Pass bos and eos into Hugging Face chat templates

## Why

`HuggingFaceTokenizer.apply_chat_template` rendered with `messages` and the caller's kwargs only. Jinja's default Undefined becomes an empty string, so a template that prints `{{ bos_token }}` or `{{ eos_token }}` dropped both. Default recipes use `HuggingFaceTokenizer`, not the experiment subclass that already passed those strings.

`encode(..., add_bos=True)` only prepends BOS. It does not put EOS between turns. `ChatProcessor` calls `encode` that way on the rendered string, then appends one EOS if the last id is not already EOS.

**Example.** Asset template in `tests/assets/tokenizer` (`bos_token` is `<|begin_of_text|>`, `eos_token` is `<|end_of_text|>`), messages `user/hi` then `assistant/yo`:

```text
before: user\nhiassistant\nyo
after:  <|begin_of_text|>user\nhi<|end_of_text|>assistant\nyo<|end_of_text|>
```

Same text, `encode(..., add_bos=True, add_eos=False)` on that asset tokenizer:

```text
before: [2002, 117, 115, 101, 114, 104, 105, 97, 115, 115, 105, 115, 116, 97, 110, 116, 121, 111]
        one BOS (2002) prepended; no EOS id
after:  [2002, 117, 115, 101, 114, 104, 105, 2003, 97, 115, 115, 105, 115, 116, 97, 110, 116, 121, 111, 2003]
        BOS once; EOS (2003) after each turn
```

## What changed

- `HuggingFaceTokenizer.apply_chat_template` passes `bos_token` and `eos_token` via `setdefault`. Caller kwargs win. A missing token is `""`, so Jinja does not see Undefined.
- `HuggingFaceTokenizer.encode` sets `add_bos=False` when the text already starts with `bos_token`, so `ChatProcessor`'s `add_bos=True` does not insert a second BOS.
- `HFBackendTokenizer.apply_chat_template` and `encode` are deleted. They repeated the base `setdefault` and the BOS prefix check. `__init__` still repairs eos when `eos_id` was left unset, and `set_chat_template` still rewrites `{% generation %}` tags.
- `encode`'s `add_bos` docstring says the prepend is skipped when the text already starts with `bos_token`.
- `DefaultRenderer`'s error no longer names `bos_token` as a variable this tokenizer omits. It names the rest of the special-token map (`pad_token`, `unk_token`, ...).
- `tests/unit_tests/cpu/components/data/test_chat_dataset.py` still expects the corrected render. `TestHuggingFaceTokenizerChatTemplateTokens` is gone (`test_shifted_by_one` already checks that string and one BOS id). `TestHFBackendTokenizerChatLabels` is `TestChatTemplateSpecialTokens` on `HuggingFaceTokenizer` and still checks answer-only labels.

## Alternatives considered

- Point every recipe at `HFBackendTokenizer`. That subclass also rewrites `{% generation %}` tags and repairs eos when bos and eos are the same string. Default SFT should not depend on the experiment tokenizer for variables the base tokenizer already knows.
- Leave the two overrides on `HFBackendTokenizer`. No. After the base change they only ran the same `setdefault` and prefix check a second time.
- Inject the strings in `BaseTokenizer.apply_chat_template`. The base class has no `bos_token` or `eos_token`.
- Splice BOS/EOS inside `ChatProcessor` after rendering. The template already says where they go, and any other `apply_chat_template` caller would still drop them.

## User-facing changes

This changes SFT chat strings for every recipe that uses `HuggingFaceTokenizer` and a template that references `bos_token` / `eos_token`. Templates that do not reference those names are unchanged, because the extra kwargs are unused. `encode` changes only when the text already starts with `bos_token`.

| Before | After |
| --- | --- |
| `{{ bos_token }}` / `{{ eos_token }}` render as empty strings | They render this tokenizer's BOS and EOS strings (`""` if unset) |
| `encode(rendered, add_bos=True)` prepends BOS even when the template already wrote it | One BOS id |
| EOS shows up only if the caller appends it (ChatProcessor appends one at the end) | EOS is present wherever the template writes `{{ eos_token }}`, including between turns |
| Caller-supplied `bos_token=` / `eos_token=` | Still win |

## Numerics

Not bitwise-identical. Chat token ids change for those templates, so SFT loss on the same rows will not match the base commit `4759738106a6f198a4dd41c78d2a754be5d0b2c4`. No GPU loss comparison. No golden loss files to regenerate: this does not change the model forward, only the chat strings fed to it. Pretraining text that does not start with `bos_token` encodes as before.

## Testing
