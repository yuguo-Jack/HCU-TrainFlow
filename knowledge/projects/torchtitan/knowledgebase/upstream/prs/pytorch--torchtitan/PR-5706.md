## Agent details

Written with Claude Code: the analysis, measurements and test plan below.

**TLDR:** The CP-16 LoRA SFT recipe moves from Ulysses flex on FA4 (256-token blocks) to Ulysses `varlen`, pinned to FA4. The Muse Ulysses CP transform now maps the varlen global and sliding-window layers. Attention kernel time per 128k step drops by 16% on one document and by 25-30% when the 128k tokens hold 4-8 documents (the recipe packs up to 8). Step time was not measured. The shared 816B builder still defaults to flex, so the Dist-MoE scale recipes keep it.

```text
CP-16 LoRA SFT, one rank (8 q / 1 kv heads, the full sequence after the Ulysses all-to-all)
main:     global + window layers -> flex, FA4 backend, 256-token block mask
this PR:  global layers          -> varlen, FA4 (cuDNN is slower here, Results)
          window layers          -> varlen, FA4 with its native 2048 window
```

```python
# before
config = _muse_spark_816b_a42b(seq_len=seq_len, parallelism=...)
...
for _, inner_attention, _, _ in config.model.traverse(FlexInnerAttention.Config):
    inner_attention.kernel_options = {"BACKEND": "FLASH"}
    inner_attention.block_size = 256
# after
config = _muse_spark_816b_a42b(seq_len=seq_len, parallelism=..., attn_backend="varlen")
...
for _, inner_attention, _, _ in config.model.traverse(VarlenInnerAttention.Config):
    inner_attention.sdpa_backends = [SDPBackend.FLASH_ATTENTION]
```

**Problem**
1. **Layers.** The 816B model has 16 global and 46 sliding-window (2048) layers: head dim 64, 128 q / 16 kv heads.
2. **Flex only.** The shared 816B builder, `_muse_spark_816b_a42b`, hard-codes `attn_backend="flex"`. The CP-16 LoRA SFT recipe then puts every flex layer on its FA4 backend with 256-token blocks.
3. **Window layers.** Flex passes the window to FA4 as a 256-token block mask plus a mask function on the partial blocks. Varlen hands the window to FA4 directly. At the recipe's per-rank shape, flex's window layers take 1.7x varlen's time (Results).

**Solution**
1. `_muse_spark_816b_a42b` takes `attn_backend` (default `"flex"`, so other callers don't change). The CP-16 LoRA recipe passes `"varlen"`.
2. The Muse Ulysses transform maps `VarlenInnerAttention` and `SlidingWindowVarlenInnerAttention` to their Ulysses versions. The transform matches exact types (`config/transform/context_parallel.py:60-64`), so both entries are needed.
3. The CP-16 LoRA recipe pins its varlen layers to FA4. torch's default order puts the global layers on cuDNN, which is 1% slower than flex on one 128k document and 13% slower than FA4.
4. The recipe's flex FA4 loop goes away. With varlen decoder layers it would only reach the vision encoder, which this text-only recipe skips (`dataset_modalities` is empty).
5. Unchanged: the builder's default, the Dist-MoE scale recipes, the debug recipes and every RL recipe.

You may ask: why not keep flex on FA4 for every Muse recipe? It's one backend, but the window layers, 46 of 62, take 1.7x longer on it.
You may ask: why not varlen in the Dist-MoE scale recipes too? Three things block it today:
- Their C4 loader sets no `max_num_documents`. Under CUDA graphs, validation raises for any varlen layer without it (`config/validation.py:111-118`).
- Their CP is K/V all-gather. Varlen K/V all-gather is untested on Muse.
- `_use_flex_flash_attention` raises on any non-flex layer (`torchtitan_recipes/models/muse_spark.py:223`).

NOTE: kernel times only. Not run: the CP-16 LoRA recipe itself (16 GPUs), its step time and its loss curve.

**Follow up**
- [ ] CP-16 LoRA SFT, a few steps on 16 GPUs: loss and step time, main vs this PR.
- [ ] Varlen K/V all-gather CP for the Dist-MoE scale recipes: a document cap on their loader and a step-time comparison against flex.

**Test plan**
- New CPU test `test_cp16_lora_recipe_uses_ulysses_varlen` builds the CP-16 recipe and checks that every decoder layer is Ulysses varlen. It fails on main.
- Built every Muse recipe and ran `validate_model_training_config` (it runs `validate_context_parallel`): all pass, except the MXFP8 debug recipe, which needs a torchao nightly to build (an import error, same on main). Only the CP-16 LoRA recipe changes: 16 global + 46 window layers move from Ulysses flex to Ulysses varlen.
- 2-GPU debug-model training, flex vs varlen, TP 2 + EP 2 + SP and Ulysses CP 2 + EP 2, 16k and 32k tokens, 3 steps. Losses are within 1e-4, and step-1 grads differ by the same rel L2 as swapping one flex kernel for another (numbers above). Activation checkpointing was off: with it on, the TP 2 layout fails in backward on main too.
- 2-GPU run of the recipe's path: Ulysses CP 2, varlen pinned to FA4, `max_num_documents` 8, deterministic, 6 steps, CUDA graphs on vs off. Loss and grad norm are bitwise equal at every step, including the 3 replays on new microbatches; the graphs run logs "Recorded CUDA graph forward_backward" on each rank.
- CPU: `tests/unit_tests/cpu/recipes`, `tests/rl/unit_tests/cpu`: same failures as main, all others pass. pre-commit passes, pyrefly included.
