# [rl] generator: run on vLLM main as well as the current pin

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5498) · state: open · merged: False

## Original PR description

**TLDR:** The RL generator fails at startup on vLLM main, which is 1,920 commits past our pin. Five small fixes make it run on vLLM main and keep it running on the current pin.

**Problem**
1. **Coupling.** The generator subclasses vLLM's model runner, worker and attention impl, and it reads scheduler internals.
2. **Removed APIs.** vLLM main removed five things the generator touches:
   - `PassConfig.enable_sp`;
   - `GPUModelRunner._pad_for_sequence_parallelism`;
   - `FlashAttentionMetadata.use_cascade`;
   - `Scheduler.skipped_waiting`;
   - the `PretrainedConfig` re-export in `vllm.transformers_utils.config`.
3. **Every start fails,** in this order:
   - `ImportError: cannot import name 'PretrainedConfig'`;
   - then `ValidationError ... PassConfig ... enable_sp: Unexpected keyword argument`;
   - then `AttributeError: 'FlashAttentionMetadata' object has no attribute 'use_cascade'` on the first forward.
4. **One silent break.**
   - vLLM main never calls `_pad_for_sequence_parallelism`, so eager steps of an EP + TP generator are no longer padded to a multiple of TP.
   - The MoE layer needs a TP-divisible token count when EP splits tokens over TP (`moe.py:795`), so a 3-token decode at TP 4 breaks.
   - CI runs this layout eager at TP4 EP4 (`rl_grpo_moe_debug_tp4_ep4`).

**Solution** (each fix runs on both vLLM versions)
1. **Drop the generator's dense sequence-parallel knob** (`InferenceParallelismConfig.enable_sequence_parallel`) and its `PassConfig`. No recipe sets the knob on a generator, and vLLM main no longer has the pass.
2. **Pad expert-parallel steps to a multiple of TP** in the existing `_determine_batch_execution_and_padding` override, after vLLM's own padding.
   - CUDA-graph sizes are already multiples of TP, so only eager steps change.
   - The dead `_pad_for_sequence_parallelism` override is deleted.
3. **Import `PreTrainedConfig` from transformers.** It's the class name in transformers 5.19.0, which both venvs use, and vLLM main imports it from there itself.
4. **Drop the cascade assert.** Cascade attention is off by default on the pin and gone on main.
5. **Count waiting requests with `Scheduler.get_request_counts()`.** It exists on both versions and includes each version's extra waiting queue.

Unchanged: CUDA-graph capture sizes, the expert-parallel capture-size filter, and the V1 runner.

Files after the generator split: the capture-size config is in `generator/vllm/config.py`, its call in `generator/vllm/engine.py`; `generate.py` and `test_bitwise_parity.py` drop the same argument.

**Results**
```text
CPU tests (tests/rl/unit_tests/cpu)        before                  this PR
vLLM pin  (9f03b510c)                      464 passed              464 passed
vLLM main (19b0efce30)                     455 passed, 9 failed    464 passed

Qwen3.5-0.8B generate, greedy, 1x H100     before                  this PR
vLLM pin                                   12 tokens, correct      same text
vLLM main                                  ImportError at start    same text as the pin

test_generator_uneven_decode.py (3 decode tokens, TP4 EP4, eager, 4x H100)
vLLM pin                                   runs in CI              passed (30 s)
vLLM main                                  ImportError at start    passed (220 s)
vLLM main, this PR minus the padding       -                       fails: all 4 ranks SIGABRT in the final barrier after ~6 min

RL smoke, Qwen3.5 debugmodel, trainer 1 + generator 1 GPU, FULL graphs, 3 steps
vLLM pin                                   -                       exit 0, logprob diff max 0.0102
vLLM main                                  ImportError at start    exit 0, logprob diff max 0.0106
```
- vLLM main was built from source for H100 against the same torch nightly.
- The padding unit test covers 3 cases: eager with DP 2, without EP, DP 1.
- Deleted: one dense-SP test, and the NONE-mode test (it only checked that "NONE" maps to `CUDAGraphMode.NONE`).
- The CPU counts above were taken with 2 more tests: the NONE-mode test and a fourth padding case.

You may ask:
- **Why not keep the dense-SP knob and pad for it too?** No recipe uses it. It would also need its own capture-size filter, which vLLM used to provide.
- **Why not pass the padded count into vLLM?** vLLM decides whether a batch is uniform decode from `num_tokens`. A decode batch whose request count isn't a multiple of TP would lose its decode graph.
- **Why not keep pulling the config class through vLLM?** That re-export is exactly what broke.

NOTE:
- Landing order: the CPU KV offload and session-KV metrics PRs still read `Scheduler.skipped_waiting` in `session_kv_holder.py`. Whichever lands second switches that read to `Scheduler.get_request_counts()`, as fix 5 does.
- `tests/rl/unit_tests/cpu/test_dapo_math.py` fails to collect (`math_verify` not installed), before and after.
- DP > 1 padding (rounding `num_tokens_across_dp`) is covered by the unit test only. The GPU runs use DP 1.
- vLLM's optional `cudagraph_metrics` stats don't count the TP rounding (off by default; correctness unaffected).
- Not run: the Dist-MoE path, which also asserts `num_tokens % tp == 0` (`model_wrapper.py`). Its package isn't installed here.

**Test plan**
```bash
# CPU, both vLLM versions
python -m pytest tests/rl/unit_tests/cpu -q
# 4 GPUs: 3 decode tokens at TP 4 + EP 4, the case the padding in fix 2 serves
torchrun --nproc-per-node=4 -m pytest tests/rl/unit_tests/gpu/test_generator_uneven_decode.py -v
```
