# [perf] Tied RoPE cache

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5583) · state: closed · merged: True

## Original PR description

I previously proposed this optimization in [PR #4111](https://github.com/pytorch/torchtitan/pull/4111), but it stalled due to concerns about fragility and pipeline parallelism (PP). I’d like to revisit it with a more minimal implementation.

The tying now happens at the same location as the embedding tying. Since each model part is a separate decoder, this approach also works naturally with PP.

## Motivation

At long sequence lengths and with deep models, RoPE caches can easily consume several GB of memory per rank. This optimization avoids materializing multiple identical RoPE caches, reducing memory overhead without changing the underlying computation.

**Summary:** I recommend this approach over the Decoder-owned `rope`. It handles mixed RoPE configs such as deepseek-v4's without extra work, needs no changes to any `Attention` constructor or to PP stage building, and leaves checkpoints unchanged. The cost is that the sharing is implicit and only saves memory after init, not at peak init. A few small follow-ups are below.

### How the PR works

1. `Decoder.init_states()` runs `super().init_states()`. Each `RoPE._init_self_buffers()` rebuilds its own cache, so there are N copies again.
2. `_tie_rope_caches()` then groups `RoPE` modules by `(type, config)` and points every module in a group at the group's first cache. The extra copies are freed.

Why this is correct:
- **`to_empty` breaks sharing.** `nn.Module._apply` builds a new buffer for each module. So the call in `__init__` does nothing on the trainer's meta-device path; the call after `init_states` is the one that matters. The code comment says this, and `test_caches_are_shared_after_to_empty_and_init_states` covers it.
- **Checkpoints and numerics are unaffected.** `cache` is registered `persistent=False`, so state_dict and DCP are untouched. Nothing writes to the cache in place, so sharing it can't change results.
- **PP works.** `_split_module` deep-copies the whole Decoder for each stage, and `training_engine.py:412-414` runs `to_empty()` and `init_weights()` on each `model_part`. Each stage therefore shares caches among its own layers. With interleaved schedules, several stages on one rank each keep a copy, which matches the overhead the alternative accepts.
- **SPMD annotations survive.** `_preserve_buffer_spmd_types` restores each module's annotation before tying, and the shared tensor is the representative's already-annotated one. All RoPE caches use the same `rope_cache_sharding_config()` (replicate), so the placements agree.
- **The vLLM generator path is covered.** `rl/generator/vllm/model_wrapper.py:390-402` also runs `to_empty()` then `init_weights()`. Tying happens before CUDA graph capture, so captured graphs see one stable address.

### Issues and suggestions

**1. The "wrong indentation" at `decoder.py:250` is a `for ... else`, not a bug.** The `else:` belongs to the inner `for rep in representatives:` loop and runs only when no match triggers `break`. The code is correct, but this review comment shows it reads like a mistake. Suggested rewrite:
```python
representatives: list[RoPE] = []
for module in self.modules():
    if not isinstance(module, RoPE):
        continue
    rep = next(
        (r for r in representatives
         if type(r) is type(module) and r.config == module.config),
        None,
    )
    if rep is None:
        representatives.append(module)
    else:
        module.cache = rep.cache
```
A dict keyed by config won't work here: `Config` is a `slots=True` dataclass with `eq=True` and not frozen, so it can't be hashed. A linear scan over a handful of representatives is fine.
[Fix this →](https://claude.ai/code?q=In%20torchtitan%2Fmodels%2Fcommon%2Fdecoder.py%20on%20branch%20f14-tied-rope%2C%20rewrite%20Decoder._tie_rope_caches%20to%20avoid%20the%20for%2Felse%20construct%3A%20use%20next(...)%20over%20representatives%20matching%20type%20and%20config%2C%20append%20if%20None%20else%20assign%20module.cache%20%3D%20rep.cache.&repo=pytorch/torchtitan)

**2. Peak memory during init doesn't go down, only steady-state memory.** `to_empty()` still allocates N caches, and each `_init_self_buffers` allocates a new one before the old one is freed. Tying only frees the copies after that. The freed blocks stay in the caching allocator and get reused for activations, so the stated motivation (GBs per rank) still holds. But a setup that OOMs while materializing the caches is not helped. Please say this in the PR description. The Decoder-owned design doesn't have this limitation (see below).

**3. Sharing is lost after any later `_apply`.** A future `model.to(device)` or dtype cast after `init_states` would quietly bring back N copies. That costs memory but never correctness. I found no such call in core today (only the two `to_empty → init_weights` sites). One line in the docstring stating that sharing only holds after `init_states` would make this explicit.

**4. Add a deepseek_v4 test.** The PR's main advantage is mixed configs, but the test only uses llama3 with a manually changed `theta`. deepseek_v4 is the real case:
- the flavors build both `rope` and `rope_compress` (`flavors.py:759-766`, chosen by `cr > 1` at `:535`);
- RoPE modules also sit inside `Compressor` and `Indexer` (`compressor.py:91, 218`), not just `attention.rope`.

A CPU test with the dsv4 debug flavor should check that there are exactly 2 distinct cache tensors and that compressor and indexer RoPEs share with the matching attention group. That would show the claim that answers @Mystri's objection.

**5. Back it with numbers.** CLAUDE.md asks for identical loss under `seed=42` and `deterministic=True`, plus a before/after memory figure. For scale: `ComplexRoPE` stores `max_context_length × dim/2` complex64 values. With llama3-8B (`dim=128`) at 128K context that is 64 MiB per layer, about 2 GiB over 32 layers. At 1M context it is 512 MiB per layer.

**6. Minor: some configs won't group.** Configs compare all fields, including `sharding_config` and `param_init`. Two RoPEs that are numerically identical but differ in those fields stay separate. That only misses a saving and is not a bug. Today every caller uses `rope_cache_sharding_config()`, so they match.

### Comparison with a Decoder-owned `rope` passed into `Attention`

| | **This PR (tie by config)** | **Decoder-owned `rope`** |
|---|---|---|
| Mixed configs (dsv4 `rope` / `rope_compress`) | ✅ Grouped by config, 2 caches | ❌ Needs a keyed registry, `Decoder.ropes[key]`, plus routing; this rebuilds the same dedup by hand |
| RoPE inside sub-modules (dsv4 `Compressor` / `Indexer`) | ✅ Found through `self.modules()` | ❌ The shared module must be passed down through Attention → Compressor/Indexer constructors |
| Code touched | 25 lines in `Decoder` | Every attention constructor (llama3, qwen3, qwen3_5 including its own RoPE subclass, gpt_oss, dsv3 MLA, dsv4 attn/compressor/indexer, kimi_k3, muse, vision encoders), each `flavors.py`, and the config `build()` flow |
| Config system fit | ✅ `Config.build()` stays self-contained | ⚠️ Passing a live module into constructors bypasses the "config builds its children" pattern |
| PP | ✅ Works as is (each stage is a deep-copied Decoder) | ⚠️ `_split_module` sets non-kept attributes to `None`; `rope` must be kept on every stage, plus custom PP such as kimi_k3's |
| Peak init memory | ⚠️ N caches allocated during init, then freed | ✅ Only one cache is ever allocated |
| Explicitness | ⚠️ Implicit; sharing is lost after a later `_apply` | ✅ Ownership is visible in the module tree |
| Module tree | Unchanged | Either a submodule registered under many parents, which wrappers like AC, compile and `ShardingConfig` would visit repeatedly, or an unregistered reference |
| Checkpoints | Unaffected (non-persistent) | Unaffected (non-persistent) |

**Recommendation:** @Mystri's point decides it. dsv4 has at least 2 RoPE configs per model, and several RoPE consumers per layer. A Decoder-owned design would need a keyed, multi-level registry to support that, which is a hand-written version of what `_tie_rope_caches` already does, plus a much larger set of changes. The alternative's real advantages are lower peak init memory and clearer ownership. Neither seems worth the cross-model churn and PP changes. I'd go ahead with this PR after:
- the `for/else` rewrite (#1);
- the docstring notes (#2, #3);
- a dsv4 unit test (#4);
- loss and memory numbers (#5).

If peak init memory becomes a problem later, it can be fixed here without changing the design. For example, `RoPE._init_self_buffers` could reuse a cache already built for an equal config during the same `init_states` pass, so the N copies are never created.
