# Report Math-Verify scoring failures (#5741)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5741) · state: closed · merged: True

## Original PR description

Summary:

Why:
Math-Verify currently assigns zero reward both when an answer is wrong and when its scoring worker times out, dies, or returns malformed output. Warnings alone cannot show in training-step metrics whether zero rewards reflect model quality or verifier health.

How:
Make `MathVerifyPool.score()` return a structured result with `scored`, `timed_out`, `worker_died`, and `invalid_output` status, and update every caller to consume that single API. Invalid worker output now follows the same kill/wait cleanup path instead of leaking the worker through `ValueError`. `RewardMathVerify` records typed counters under the dedicated `math_verify/...` namespace on each rollout turn. The Verifiers adapter explicitly extracts the numeric score where its reward API requires a float.

Differential Revision: D129127439

**Verdict: Approve -- please address the items below before merging.** Reporting timeouts and worker deaths separately from wrong answers is a real gap on `main`, resolved by an existing TODO there. The fix is in the right place: only the DAPO example changes, and core is untouched. The remaining items are small, local edits.

**What this PR does.** Today `MathVerifyPool._score_in_worker` returns 0.0 for a wrong answer, a timeout, or a dead worker alike, and only a log warning tells them apart. The PR returns a `MathVerifyResult(score, status)` instead. `RewardMathVerify` then appends two `Sum` counters to the rollout's last turn, and the existing turn-metric fold in `compute_rollout_metrics` sums them per step. Healthy scores emit zeros.

**Example.**
```
# a step with 64 rollouts; one hits the 60 s timeout
before: rollout_reward/component/RewardMathVerify/mean drops; timeout only in logs
after:  reward/math_verify_timeout/sum = 1.0
        reward/math_verify_worker_death/sum = 0.0
```

### Must fix
1. `torchtitan/rl/examples/dapo_math/rubric.py:55-59` -- The counter keys start with `reward/`. `Controller._log_reward_delta` will therefore print them under "Validation reward (pre / post)", and they read like reward components. Rename them, e.g. `math_verify/timeouts` and `math_verify/worker_deaths`.
2. `torchtitan/rl/examples/dapo_math/math_verify_pool.py:83-93` -- `score()` is now a forwarder with one caller (verifiers `data.py:39`), and its docstring is stale. Make `score()` return the result and drop `score_with_outcome`.

### Should consider
- `math_verify_pool.py:38-43` -- Use `Literal[...]` instead of an unused `StrEnum`. This also removes the new `__init__.py` exports.
- `tests/rl/unit_tests/cpu/test_dapo_math.py:198-205` -- The timeout test duplicates `test_math_verify_pool_replaces_a_killed_process`. Fold it into that test.
- `tests/rl/unit_tests/cpu/test_dapo_math.py:246-257` -- This re-tests the generic turn-metric fold, which `test_metrics.py` already covers. Drop it.

### Questions
- The verifiers taskset (`torchtitan/rl/examples/verifiers/dapo_math/data.py`) uses the same pool and still drops the status, so its zero rewards stay ambiguous. Is that intended for this PR, or a follow-up?

<details><summary>Details</summary>

- Turn metrics bypass the `rollout`/`validation` prefix in `compute_rollout_metrics`. Validation rollouts therefore emit these counters under the same key as training. Post-training validation logs at `step=num_training_steps`, the same step as the last training log, so the backend gets two values for one key and step. The `generator/*` turn metrics already have this problem, and fixing it means changing core `compute_rollout_metrics`, so it is out of scope here. It is worth a follow-up if these counters are read near the end of a run.
- Checked in `_score_in_worker`: the worker-death branch now skips `kill()` and only calls `wait()`. That is safe because EOF on stdout means the process is exiting. The timeout branch logs exit code -9, as before.
- Rollouts short-circuited by `truncation_reward` / `error_reward`, or with no turns, emit no counters. That is correct, since nothing was scored.

</details>
