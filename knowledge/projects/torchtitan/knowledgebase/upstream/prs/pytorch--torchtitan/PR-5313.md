# [train] Require one device for a seed checkpoint

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5313) · state: closed · merged: True

## Original PR description

## Summary (human-written)
A seed checkpoint has to be written from one rank, but `main()` asserted `int(os.environ["WORLD_SIZE"]) == 1`. Pure fake mode never sets that variable, so the assert raises `KeyError`, and `python -O` removes it, so an 8-rank launch can save a sharded init and still log "Created seed checkpoint". `checkpointer=None` and `load_only=True` also skip the write and log success. The launch check now raises `ValueError` from `trainer.engine.parallelism_context.world_size`, and `Trainer.Config.__post_init__` rejects a checkpointer that will not save. Seed recipes set `create_seed_checkpoint` after the config is built and leave `override.imports` empty, so `ConfigLoader.load` runs `__post_init__` again after launch options and `apply_overrides` runs it again after replacements.

## Why

A seed checkpoint has to be written from one rank. `main()` used to assert `int(os.environ["WORLD_SIZE"]) == 1`. Pure fake never sets `WORLD_SIZE`, so that assert raises `KeyError`. Under `python -O` the assert is removed, so an 8-rank launch can save a sharded init and still log "Created seed checkpoint". `checkpointer=None` and `checkpointer.load_only=True` also skip the write (`_should_save` returns false) and still log success.

**Example.**

```text
# torchrun --nproc_per_node=8, python -O, create_seed_checkpoint=True
# before: assert removed, sharded checkpoint, "Created seed checkpoint"
# after:  ValueError: ... Got world size 8.

# create_seed_checkpoint=True, checkpointer.load_only=True
# before: nothing saved, "Created seed checkpoint"
# after:  ValueError: create_seed_checkpoint requires a checkpointer with load_only=False.
```

## What changed

- `main()` reads `trainer.engine.parallelism_context.world_size` and raises `ValueError` unless it is 1. The helper and the `is_initialized()` branch are gone. World size 1 already means every parallelism degree is 1.
- `Trainer.Config.__post_init__` rejects a missing checkpointer and `load_only=True` when `create_seed_checkpoint` is set.
- `Configurable.Config.__post_init__` is a no-op, so every config can be re-entered. `ConfigLoader.load` calls it after the recipe and launch options. `apply_overrides` calls it after replacements. `Trainer.__init__` does not. Seed recipes assign the flag and set no imports (`tests/integration_tests/features.py`, the checkpoint compat generator), so the loader is the call that sees them. The RL controller, `rl/generate.py`, precompile, and torchft already call `apply_overrides`, so they revalidate there.
- `torchtitan/config/transform/README.md` names those two calls.
- Deleted `tests/unit_tests/cpu/test_seed_checkpoint_launch.py`. The checkpointer rule is still covered by re-entering `__post_init__`. Two new tests lock the loader call and the `apply_overrides` call. No distributed monkeypatch.
- `HFTransformerModel.Config.__post_init__` forwards leftover kwargs to `PretrainedConfig.__post_init__`. `Configurable.Config.__post_init__` is ahead of `PretrainedConfig` in that MRO and takes no extra arguments, so `attn_implementation` raised `TypeError` while collecting `tests/unit_tests/cpu/recipes/test_debug_config_defaults.py`.

## Alternatives considered

- Revalidating only in `Trainer.__init__` misses the RL controller, which applies overrides and never builds a `Trainer`.
- Revalidating only in `apply_overrides` misses the seed recipes. They assign the flag and leave `override.imports` empty, and every caller skips `apply_overrides` in that case.

## Numerics / performance

No training math changes. A rejected launch does not save. A one-rank launch with a saving checkpointer still calls `save_checkpoint(last_step=True)`. Kimi's optimizer alignment runs again on load; when the layouts already match it returns the same optimizer. No GPU loss comparison.

## Testing

`tests/unit_tests/cpu/config/test_override.py` (including `test_revalidates_after_assignment`) and `test_load_revalidates_recipe_assignments` passed locally: 39 passed. `test_seed_checkpoint_requires_a_saving_checkpointer` still calls `__post_init__()` for `checkpointer=None`, `load_only=True`, and a normal checkpointer. This machine cannot collect that file: `module 'spmd_types' has no attribute 'rules'`, then NumPy 2.2.6 vs bottleneck. The loader tests that import a recipe hit the same `spmd_types` error inside `_load_config`, before the new call. No seed-checkpoint launch was run here. CPU `build-test` job 125731353312 failed that collection with the `attn_implementation` `TypeError`. This machine still cannot import that test (`spmd_types.rules`). A local MRO replica of the same call raises on the base method and returns the kwargs once the subclass forwards them.

## Known issues

Pure-fake seed checkpoint is not a workflow this needs. `validate_fake_pg_compatibility` already rejects `create_seed_checkpoint` unless the integration test sets `use_real_pg`. `scripts/loss_compare.py` starts the seed run under `torchrun` with one GPU. `parallelism_context.world_size` is `NGPU` in fake mode and the torchrun world size otherwise. A `Trainer` or `FaultTolerantTrainer` built in-process, without `ConfigLoader` and without override imports, does not re-enter `__post_init__`. `FaultTolerantTrainer` copies `__init__` and does not add its own call.

### On @tianyu-l's latest comment (`torchtitan/config/configurable.py:49`)
**Mistaken. Keep the method.** The docs section you linked describes a hook that you write yourself. It doesn't describe a default that `@dataclass` adds. The docs say: "The generated `__init__()` code will call a method named `__post_init__()`, if `__post_init__()` is defined on the class." CPython does the same thing: `_process_class` computes `has_post_init = hasattr(cls, _POST_INIT_NAME)` and adds the call to `__init__` only when that is true. It never adds the attribute. So for a config that defines no `__post_init__`, anywhere in its MRO, the new calls fail with `AttributeError`:

```python
@dataclass(kw_only=True, slots=True)
class Root(Configurable.Config):          # e.g. Root/ParentComponent in test_override.py
    child: ComponentA.Config
apply_overrides(OverrideConfig(), Root(...))
# without the base no-op: AttributeError at config_root.__post_init__()  (override.py:507)
# with it: no-op
```

The two new unconditional calls (`override.py:507`, `loader.py:56`) accept any `Configurable.Config` root, so the base class is the right place for a default. The alternative is `getattr(config_root, "__post_init__", None)` at each call site, which is worse. Defining it on the base also means every subclass's generated `__init__` now calls a method. When the subclass has no override, that method is an empty function, so the cost is negligible. No in-repo `__post_init__` calls `super().__post_init__()` (I grepped), so subclasses with their own method don't change.
