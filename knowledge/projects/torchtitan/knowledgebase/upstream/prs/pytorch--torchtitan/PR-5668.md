# [rl] generator: fused GDN gate kernel in the packed path (1/7)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5668) · state: closed · merged: True

## Original PR description

**TLDR:** The GDN packed path (prefill and mixed steps) computed the decay gate with 6 small PyTorch kernels. It now uses Attention Gym's fused kernel with `fastmath=False`: 1 kernel, same bits. -7 to -22 us per GDN layer per packed step (0.4-1.1 ms per step at 27B TP1, 48 GDN layers; estimate).

```python
# before: 6 PyTorch kernels
decay = gate_transform(a, A_log.float(), dt_bias.float(), kind="softplus", impl="reference")
# after: 1 Triton kernel
decay = gate_transform(a, A_log.float(), dt_bias.float(), kind="softplus", fastmath=False, impl="fused")
```

**Problem**
1. `VLLMInnerGDN._forward_gdn` runs in every GDN layer on every packed step.
2. It computes the decay gate `-exp(A_log) * softplus(a + dt_bias)` with `impl="reference"`: 6 small PyTorch kernels.
3. Their cost is what the fused kernel saves: 7-22 us per GDN layer (below).

**Solution**
1. `impl="fused"` runs Attention Gym's Triton gate kernel: 1 launch.
2. `fastmath=False` uses libdevice `exp`/`log1p` and `F.softplus`'s threshold, so the bits match the FP32 gate. It is explicit because the default is `True` (off by up to 3.8e-6).
3. Batch-invariant decode steps call the same function, so they run the fused gate too, with the same bits.
4. Unchanged: other decode steps (the decode kernel computes the gate itself), the trainer.

**Results**
Numerics: bitwise identical to main in all 80 cells (output, recurrent and conv state). Gate vs the trainer's FP32 expression, every finite bf16 value x 7 parameter sets: 0 of 296.6M differ.

```text

```

**Test plan**
`TestBitwiseParityQwen35DebugVarlen` (2 GPUs, run in CI) fails with `fastmath=True` (trainer vs vLLM prefill, max delta 3.1e-3) and passes with this PR. GB300: `TORCHTITAN_QWEN3_5_0_8B_HF_PATH=<Qwen3.5-0.8B-Base> pytest tests/rl/unit_tests/gpu/test_gdn_cudagraph.py tests/rl/unit_tests/gpu/test_gdn_graph_metadata.py`, 9 passed.

**Stack** (land in order): 1/7 fused gate -> 2/7 metadata reuse -> 3/7 no output memset/copy -> 4/7 decode routing -> 5/7 fused input projections -> 6/7 float32 gate parameters -> 7/7 split compiled per grad mode.

**Verdict: Approve** -- one argument changes, and it swaps 6 PyTorch kernels for 1 Triton kernel while keeping the gate bitwise equal to the trainer's FP32 expression. No must-fix items. A maintainer still needs to review, since this touches the RL generator.

**What this PR does.** In `VLLMInnerGDN._forward_gdn`, the decay gate now uses Attention Gym's fused kernel (`impl="fused"`) instead of the PyTorch reference path. It passes `fastmath=False` so the kernel uses libdevice `exp`/`log1p` and the softplus threshold, which gives the same bits as the trainer. The packed path (prefill and mixed steps) and batch-invariant decode both go through `_forward_gdn`. Regular decode computes the gate inside `recurrent_gdn_decode` and is unchanged.

**Example.**
```python
# trainer, torchtitan/models/common/attention/gdn.py:391
g = -torch.exp(A_log.float()) * F.softplus(a.float() + dt_bias)
# generator, before: same math as 6 eager kernels
gate_transform(a, A_log.float(), dt_bias.float(), kind="softplus", impl="reference")
# generator, after: 1 Triton kernel, same bits
gate_transform(..., kind="softplus", fastmath=False, impl="fused")
# fastmath=True (the default) would differ from g by up to ~4e-6 and break
# trainer/generator bitwise parity in batch-invariant mode
```

<details><summary>Details</summary>

- Gate: the problem is real (6 eager kernels per GDN layer per packed step), the fix is in the right layer (choosing an existing upstream kernel), and nothing new is added (no knobs, no helpers).
- Batch invariance: the gate is elementwise, so the fused kernel's tiling can't make the result depend on batch composition. Batch-invariant decode (`gdn.py:262`) reaches the fused gate through `_forward_gdn`, as the description says.
- The test's reference expression adds `a.float() + dt_bias` with bf16 `dt_bias`, which matches the trainer exactly (`gdn.py:391`), so the comparison is against the right target.
- `gate_transform` comes from the private `attn_gym.linear._delta_rule.gate` module. That predates this PR, and `torchtitan/models/common/attn_gym.py` already has a TODO for it.

</details>

Not verified: that `gate_transform` accepts `fastmath` in the pinned `attn-gym==0.0.17`, the perf numbers, and the bitwise claims (all need a GPU). I relied on the author's GB300 runs for these.
