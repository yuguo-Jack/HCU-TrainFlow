# [rl] vLLM watermark passthrough + preemption metrics (1/5)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5216) · state: closed · merged: False

## Original PR description

**TLDR:** Adds `VLLMGenerator.Config.watermark` and two preemption signals: a per-request `generator/num_preemptions` metric, and a per-engine stdout line with each stat interval's preemptions and re-prefilled tokens. In a standalone H100 vLLM repro with a full KV cache, `watermark=0.03` cut preemptions from 346 to 18 per 1k steps and raised generated tok/s 11%. The default is unchanged. GB300 is unmeasured.

**Problem**
1. **KV fills first.** When a generator's KV cache fills before `max_num_seqs`, vLLM still admits a waiting request each time one finishes, because it fits at that moment.
2. **Preemption.** The next running request that needs a new KV block finds none free, so vLLM preempts the newest running request: it frees its KV and prefills it again later.
3. **Churn.** This repeats every few steps: in an H100 repro, 27% of decode steps became mixed recompute + decode steps.
4. **Hidden.** vLLM's stat line never prints `Preemptions:`, because `LoggingStatLogger.log()` resets the count before it checks it (`vllm/v1/metrics/loggers.py:241,284`). Its prompt throughput also skips re-prefilled tokens. So we can't see whether our runs hit this, or what it costs.
5. **Cost.** ~7 ms of a 57.3 ms decode step (12%) on H100. A 35B-A3B GB300 run has ~14 ms of 84 ms per step unexplained once its engines fill, which fits the same churn but is unmeasured.

**Solution**
1. **The idea.** vLLM's `watermark` keeps a fraction of KV blocks free when it admits waiting requests, so running requests grow into it and far fewer get preempted.
2. **Passthrough.** `VLLMGenerator.Config.watermark: float | None = None` reaches `EngineArgs` in `VLLMGenerator` and in `generate.py`.
3. **Per request.** `generator/num_preemptions` (mean and max over the completions logged at that step) reads vLLM's per-request `RequestStateStats.num_preemptions`. That counter is correct; only the stat line drops it.
4. **Per engine.** `VllmPreemptionStatLogger`, a vLLM stat logger that `VLLMGenerator` registers on TP rank 0, prints right before vLLM's stat line:
   ```text
   Engine 000: Preemptions: 12, Re-prefilled tokens: 254310
   ```
   Re-prefilled tokens are the tokens resumed requests compute again: vLLM's per-step `preempted_queries - preempted_hits - preempted_requests`.
5. **Unchanged.** `None` leaves the kwarg out, so vLLM keeps its default (0.0, no reserve) and no recipe changes behavior.

**Results**
```text
H100, FA3, vLLM 9f03b510c serving its own Qwen3.5-9B-Base (not the TorchTitan model), with the generator's engine settings.
50 GiB KV, max_num_seqs 400, 1,400 requests (256-token prompts, 400-9,000 output tokens), 200-900 s window with requests waiting, one seed.

                                   watermark 0   ->  0.03
running requests                        309      ->   306
preemptions per 1k steps                346      ->    18
mixed recompute + decode steps         26.9%     ->  4.7%
decode step                            57.3 ms   ->  51.1 ms
generated tok/s                        5,394     ->  5,998   (+11%)
excess ms/step over a fit to steps
where the KV cache never filled          7.0     ->   1.5
```

```text
CPU, vLLM 9f03b510c's real Scheduler and AsyncScheduler + OutputProcessor, 24 requests of 132-428 tokens, 85 blocks of 16 tokens.

                                          sync      async
preemptions, scheduler's own count          48         50   (49 resumes)
preemptions, logged                         48         50
re-prefilled tokens, scheduled - expected 2,952      2,992   (expected = prompt + output - 1 per request)
re-prefilled tokens, logged               2,952      2,992
```

You may ask:
- Why not lower `max_num_seqs`? It also works (288: +12%, 256: +10%), but the running count where KV fills moves with response lengths (253-337 within one run), so a fixed cap gives up concurrency when responses are short.
- Why not fix vLLM's own stat line? That means monkeypatching its private `_update_stats`, and its line would still have no re-prefilled tokens. An upstream fix for the count is open; the TODO drops our count once it lands.
- Why stdout and not TensorBoard for the per-engine numbers? Generator metrics reach the controller only on completions, which are per request. A per-step engine total needs a new path to the controller (TODO).
- Why not use `VllmOtelStatLogger`? It already exports `vllm.preempted_requests`, but it is off by default and needs an exporter env var.
- Why not default to 0.03? It reserves ~3% of concurrency, and no TitanRL run has measured the gain yet.
- Why `None` and not `0.0`? Unset follows vLLM's default instead of pinning today's value. vLLM rejects `watermark=None`, so unset leaves the kwarg out (tested).

NOTE:
- GB300 may differ: it graphs mixed batches and runs MoE + FA4 with 1,152-token KV blocks. The H100 repro ran mixed steps eagerly, because vLLM's GDN backend downgrades FULL graphs to decode-only.
- With `reset_kv_cache_on_weight_sync=True` (required by `batch_invariant`), each weight sync preempts every running request. There, preemptions > 0 is not by itself a reason to raise `watermark`.
- Re-prefilled tokens over-count a resume that is preempted again mid-prefill. Hybrid (GDN) models split resumes longer than one block, so it happens there: +4% in a CPU probe with 16-token blocks. Resumes that finish are exact.
- Needs a vLLM nightly from 2026-09-01 or later, when `RequestStateStats.num_preemptions` landed. This applies to every run, not only runs that set `watermark`.
- Not run: GPU or end-to-end RL with this branch. CPU tests only. The registration line has no CPU test; check the first GPU run's stdout for `Re-prefilled tokens`.

**Follow up**
- [ ] Report the per-engine preemptions and re-prefilled tokens per training step in TensorBoard. Needs a path from the generators' engine stats to the controller. TODO in `VllmPreemptionStatLogger`.
- [ ] Drop `Preemptions` from our line once the open upstream vLLM fix merges. TODO in `VllmPreemptionStatLogger`.

**Test plan**
```text
pytest tests/rl/unit_tests/cpu   # 515 passed, 8 skipped (main: 511 passed, 8 skipped)
```
- `test_watermark_reaches_engine_args[None|0.03]`: unset leaves `watermark` out of the engine kwargs; set passes the value. It fails if the code always passes `watermark`.
- `test_metric_timing_math_and_prefix_override`: `num_preemptions` reaches the aggregated metrics.
- `test_logs_the_schedulers_preemptions_and_reprefilled_tokens[Scheduler|AsyncScheduler]`: drives vLLM's real scheduler and `OutputProcessor` like `LLMEngine.step`, with a pool small enough to preempt. The logged line must equal the scheduler's preempted request ids and the tokens it scheduled beyond prompt + output - 1 per request. It fails if the line drops `- preempted_requests`, counts resumes instead of preemptions, or does not reset after logging.
