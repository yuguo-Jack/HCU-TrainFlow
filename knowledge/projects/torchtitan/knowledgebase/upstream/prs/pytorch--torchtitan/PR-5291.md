# [rl] Build and pack training batches in their own process

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5291) · state: closed · merged: True

## Original PR description

**TLDR:** On a busy controller the batcher waits on the GIL: one batch takes 3.7-5.4 s instead of 0.2 s (CPU benchmark). This PR moves building and packing into their own process (`BatcherActor`). Under the same load a batch then takes 0.61-0.70 s with the RDMA fast path on (trainer ranks read from the batcher's process), and 2.0-4.5 s by value (the default; the controller still unpickles each batch under its GIL).

**Problem**
1. **One GIL.** `_batcher_loop` builds training samples and packs microbatches inside the controller process.
2. **Busy loop.** On large runs, the controller's event loop holds that GIL most of the time, serving rollouts.
3. **Build and pack wait.** `build_from_group` and `add_training_samples` run in `asyncio.to_thread`; each time that thread gives up the GIL (e.g. every torch op in the packer), it waits up to 5 ms (`sys.getswitchinterval()`) to get it back.
4. **How much.** A batch is thousands of small torch ops: 0.2 s alone, 3.7-5.4 s next to a busy loop.
5. **At scale.** On a 10-node agentic run, the trainer idled 54% of each step: the batcher took 100-180 s per batch vs 80 s of forward/backward.

**Solution**
1. **Own GIL.** Build and pack in a separate process, as the router already does.
2. **`BatcherActor`** (`torchtitan/rl/actors/monarch/batcher.py`): a thin Monarch wrapper over `Batcher`, like `VLLMGeneratorActor`, spawned by `setup_async` on a one-process mesh on the controller host. The new `Batcher.add_group(rollout_group=...)` builds the group's training samples and packs them. It returns each finished batch by value or, with `rdma_min_tensor_bytes` set, as `MonarchRDMAMicrobatch`es whose tensors it keeps (the RDMA PR's code, unchanged).
3. **Release.** After `forward_backward`, in a `finally`, the trainer loop calls `batcher.maybe_release_oldest_batch.broadcast()` (a no-op by value). Not awaited: awaited, it waited p50 255 ms behind an in-flight pack. Batches train in order through the one-batch queue.
4. **Config:** `Batcher.Config` now owns `training_sample_builder` (moved from `AsyncLoopConfig`) next to `rdma_min_tensor_bytes`; the controller reads neither.
5. **Unchanged:** packing, `TrainingSampleBuilder`, the batch order, the one-batch queue, and the trainer side (it reads as before, now from the batcher's process).

```text
before (controller process, one GIL)
  event loop thread:  serve rollouts, ...                                     <- holds the GIL most of the time
  to_thread worker:   build_from_group, add_training_samples, then register  <- every torch op: release, wait up to 5 ms

after
  controller:       await batcher.add_group.call_one(rollout_group=group)          <- pickle a group, unpickle the batch
                    await trainer.forward_backward.call(packed.microbatches, ...)   <- by value, or MonarchRDMAMicrobatches
                    batcher.maybe_release_oldest_batch.broadcast()                   <- a no-op by value
  batcher process:  build_from_group + add_training_samples (+ register buffers on the fast path; its own GIL)
  trainer ranks:    by value: the column arrives in the call; fast path: read it from the batcher process
```

**Results**

Wall time per batch. CPU benchmark, one host, torch 2.15 nightly, torchmonarch 0.6.0: 8 groups x 8 rollouts x 8 turns -> 1 batch of 32 microbatches, dp 4; a task on the controller's event loop burns CPU for <load> of every 10 ms. "main" built on the event loop; main now builds in `asyncio.to_thread` (not re-measured):
```text
                 main (in the controller)   this PR, by value (default)   this PR, fast path
loop idle        0.23-0.25 s                not measured                  0.35-0.36 s
loop 50% busy    0.39-0.41 s                not measured                  0.36-0.45 s
loop 100% busy   3.7-5.4 s                  2.0-4.5 s                     0.61-0.70 s
```
On an idle loop it costs ~0.1 s more per batch, for pickling the groups and registering buffers.

You may ask:
- **Why not a `ProcessPoolExecutor`?** Its pipe moves the batch in 64 KB reads, each one a GIL handoff: 26 s at 100% load.
- **Why `async` endpoints?** Monarch rejects mixing sync and async endpoints, and the release awaits the buffer drops. They stay plain `@endpoint`, so groups are processed one at a time, in arrival order.
- **Why FIFO release, not keyed by step?** The batcher doesn't know a batch's step when it packs it, and batches train in order. A lost broadcast holds one extra batch; it never frees an unread one.
- **Why not `sys.setswitchinterval(0.0005)`?** It cuts the busy-loop time 4x (3.2 -> 0.75 s), but it's process-wide: the event loop gets preempted 10x more often.
- **Why not fewer torch ops in the packer?** The cost is still ops x 5 ms, and it grows with the microbatch count.
- **Why not move rollout serving out of the controller?** It removes the load at its source but is a larger change; the batcher should stay off the controller's GIL either way.

NOTE:
- **BC-breaking:** `async_loop.training_sample_builder` -> `async_loop.batcher.training_sample_builder`. Old configs fail loudly (`TypeError` at construction, `AttributeError` on access).
- **The input side remains:** sending a group pickles it on the event loop: 0.02 s for 8 rollouts x 8 turns, 0.04-0.07 s for 8 x 40 turns (measured when each turn stored its full prompt; main now stores a delta). Router replay and top-k add per-token data.
- **Memory (fast path):** the batcher holds up to 3 batches (training, queued, one more if `_batcher_loop` is blocked on the queue): ~53 GB at 17.8 GB per batch with router replay, plus transient copies on TCP; the controller holds none. A released batch's memory returns by the batcher's next call.
- **CUDA context (fast path):** moves from the controller into the batcher process, which now registers the buffers (~256 MiB on GPU 0; 0 `[RdmaXcel]` lines in the GPU run vs 152 before). Created at spawn while trainer rank 0 starts on GPU 0: on exclusive-process GPUs one of them fails.
- **Needs Monarch ≥ 0.7** for the fast path (main pins it): its reentrant drop lock lets the batcher keep only the `MonarchRDMAMicrobatch`es. On 0.6 the batcher hangs within its first few steps.
- **Reads don't slow down while the batcher packs:** the owner side of a read needs neither its GIL nor its actor loop (CPU probe, 4 readers, 81.7 MB microbatches: 115 ms per microbatch idle vs 105-117 ms while the batcher spins, packs or registers).
- **Spans:** `training_sample_builder` and `batcher_pack` move to a new `rl_batcher` structured log; the controller logs `batcher_add_group` around the call and sends the step with `broadcast`.
- **Config errors** (e.g. `num_tokens_per_microbatch_per_dp_rank` not a multiple of `max_context_length`) now fail at actor spawn, in the batcher process's traceback.
- **The 10-node run** used a branch whose `TrainingSample`s hold tensors, so many more torch ops per pack (0.1 -> 18 s under this benchmark, vs main's 0.2 -> 3.6-4.1 s). This PR has not run at scale.
- **Not tested:** multiple hosts, the RL GPU CI.

Follow up:
- [ ] Send only the fields the builder reads, or let rollouts reach the batcher directly, if group pickling shows up in `batcher_add_group`.

**Test plan**
- `pytest tests/rl/unit_tests/cpu` (repo root, Monarch 0.7, merged with main): 498 passed, 5 skipped.
- `test_batcher_actor.py`: spawns `BatcherActor` in its own process (TCP), with and without `rdma_min_tensor_bytes=1024`. 5 groups (one untrainable) make batches A and B; after releasing A, B still reads back to the in-process batch, every tensor exact (256-token microbatches: the int64 fields cross by ref, the token counts by value). Unset, both batches come back by value and match. A builder error surfaces at `call_one`.
- GPU, Qwen3-0.6B, H100, batch invariant, lockstep, Monarch 0.7, 5 steps:
  - trainer DP 2 (3 GPUs), RDMA buffers over ibverbs (now `rdma_min_tensor_bytes=1024`): `loss/mean` bitwise equal to main's DP 2 at every step, 0 `[RdmaXcel]` lines. Over TCP, the next PR's head matches too. Both before the merge with main.
  - the whole stack at the previous push (the next PR's head), DP 1 (2 GPUs), `rdma_min_tensor_bytes=1024`: `loss/mean` bitwise equal to the by-value run (earlier push, same config and seed), 0 `[RdmaXcel]` lines, and the `rl_batcher` log written by the actor.
