# [rl] Send only changed elements of the model state dict to generators

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5751) · state: open · merged: False

## Original PR description

## Summary (human-written)
<!-- Write this yourself, not with an AI tool. 2-5 sentences: the problem, why
     this approach, and what you checked yourself. -->

Stacked on https://github.com/pytorch/torchtitan/pull/5659. Depends on https://github.com/meta-pytorch/torchstore/pull/279 (`StateDictDelta`, `put_state_dict_delta`, `get_state_dict_delta`).

## Why
Each generator pulls the full model state dict every version, even though an RL step with a small LR changes only a small fraction of the elements in the transfer dtype. In the Qwen3-0.6B run below, 1.1-1.8% of the bf16 elements change per step, yet every pull reads all 1.5 GB.

**Example.**
```python
config.model_state_dict_delta_max_fraction = 0.05
# trainer push: full put_state_dict + one row per shard with up to 5% (value, index) pairs
# generator pull: scatter rows into the persistent prefetch buffers;
#                 full read only for shards whose row overflowed or that missed a version
```

## What changed
- `Controller.Config.model_state_dict_delta_max_fraction: float | None = None`, validated in `__post_init__`. None keeps today's behavior.
- Trainer: builds a `ts.StateDictDelta` after loading the checkpoint. The push worker thread from #5659 calls `ts.put_state_dict_delta` instead of `ts.put_state_dict`. It compares the live GPU tensors on the push stream against the previous version kept in pinned host memory, then puts the full state dict and the rows.
- Generator: `prefetch_model_state_dict` calls `ts.get_state_dict_delta` into the existing prefetch buffers, which keep the previous version between pulls.
- Tests: constructor arguments; the existing push test is parametrized over the delta path (the put runs in the worker thread on the push stream after it synchronizes).

## Alternatives considered
- Previous version on the accelerator: doubles model memory in the transfer dtype. Host memory keeps GPU cost to chunk temporaries of about 0.2 GB.
- Skipping the full `put_state_dict`: a generator that starts late or misses a version would have nothing to fall back to.

## User-facing changes
| Before | After |
| --- | --- |
| generators always pull the full model state dict | `model_state_dict_delta_max_fraction=f` pulls only changed elements (up to `f` per shard) |

## Numerics
Generator weights are bitwise identical to a full pull. In the e2e run, the generator also did a full pull into a copy on every step and compared the bytes; no tensor mismatched on any step.

## Performance
Qwen3-0.6B (751.6M elements, bf16) on a single host over loopback. The trainer runs on 1 GPU, 2 generators, `max_fraction=0.05`:

| | Full (today) | Delta |
| --- | --- | --- |
| Generator prefetch per version | 0.12-0.18 s | 0.18-0.50 s (scatter 0.12-0.24 s) |
| Bytes read per pull | 1.5 GB | 225 MB rows |
| Trainer push (worker thread) | put only | + stage 0.13-0.24 s |
| Changed elements per version | - | 1.1-1.8% |
| First version | full | full (rows report overflow) |

- On loopback the delta pull is slower, because the scatter costs more than the saved bandwidth. The gain needs a bandwidth-bound path, such as cross-host pulls or many generators sharing trainer egress.
- Extra trainer memory per element at `f=0.05`:
  - pinned host: 2.3 B;
  - GPU: about 0.2 GB of chunk temporaries, which stay reserved on the push stream by the caching allocator.
- The stage numbers above predate the torchstore chunked encode, which takes 33-40 ms for 750M elements on an H100.

## Testing
- `pytest tests/rl/unit_tests/cpu` against the torchstore PR: 488 passed, 9 skipped, 1 failed. The failure, `test_rl_recipes_get_model_defaults[dapo_math]`, also fails without this change (environment).
- E2E run as above: delta vs full bitwise check on every version.

## Known issues / follow-ups
- No metric for the changed fraction yet (TODO in the field docstring).
- Needs a bandwidth-bound run (cross-host, or many generators sharing trainer egress) showing a win, and a recipe that enables it.
- Lands after torchstore#279 (the trainer test patches `ts.put_state_dict_delta` with `create=True` until then).

**What this PR does.** It adds `Controller.Config.model_state_dict_delta_max_fraction`. When the field is set, the trainer builds a `ts.StateDictDelta` after loading the checkpoint, and each push calls `ts.put_state_dict_delta`: a full put plus one row per shard of up to `f` changed (value, index) pairs, diffed against a pinned-host copy of the previous version. Generators call `ts.get_state_dict_delta` into their persistent pinned prefetch buffers. Tensors whose rows overflowed, or that missed a version, are read in full.

**Example.**
```
config.model_state_dict_delta_max_fraction = 0.05
v1: trainer full put + rows (count=-1, overflow) -> generator reads every tensor in full
v2: 1.5% of bf16 elements changed -> rows hold them; generator reads 225 MB of rows,
    scatters them into prefetch buffers, reads nothing in full
before (None): every version, every generator reads the full 1.5 GB
```

### Must fix
1. `torchtitan/rl/trainer/trainer.py:474` -- the delta path drops `direct_rdma=False`. The pull of version N overlaps `optim_step` N+1 (`controller.py:1230`), so full reads must come from a StorageVolume snapshot, not from live GPU tensors. The delta put needs to forward `direct_rdma` (torchstore#279) and pass `False` here. *Unverified* whether torchstore's default already makes this safe.
2. `torchtitan/rl/controller/controller.py:305` -- no recipe or test turns on this knob, the measured result is a regression on loopback, and users have no metric to tune `f` with. Before landing, it needs either a measured win (cross-host or many-generator egress) plus a recipe that enables it, or an explicit maintainer decision to land it ahead of that evidence.
3. Merge order: the new trainer test patches `ts.put_state_dict_delta`, which doesn't exist on `torchstore@main`, and that is what CI installs. This PR can only land after torchstore#279.

### Should consider
- `tests/rl/unit_tests/cpu/test_trainer.py:125` -- fold the new test into the existing full-path test by parametrizing over the delta.
- `torchtitan/rl/trainer/trainer.py:458` -- with the delta set, `_model_buffer_names(...)` is still computed on every push and then ignored, because `StateDictDelta` holds `preserve_dtype_keys` from construction. Skip it on the delta path, or don't pass it at all.
- The "Summary (human-written)" section only has the stacking and dependency links. The author should add a sentence or two in their own words.

### Questions
- Does the delta path work with the colocated SharedMemory transport that `push_model_state_dict`'s docstring describes? If it isn't supported, or isn't useful there (the full put is already a local copy), it should raise in `__post_init__` rather than silently run the slower path.

<details><summary>Details</summary>

- Placement: putting the field on `Controller.Config` makes sense, because it configures both the trainer and the generators, which only the controller spawns. Validation is in `__post_init__`. The generator takes a `bool` derived from it and doesn't need the fraction.
- Ordering invariant: `generator.py:449` documents that a pull overlapping a push leaves the buffers permanently stale. `_trainer_loop` keeps that ordering (each pull waits for its push, and the next push waits for the previous pull). Nothing else enforces it, but torchstore's per-row (epoch, version) catches restarts and missed versions.
- PP: each PP rank publishes a partial state dict under the same key with its own epoch. torchstore#279 tests rows from several publishers at different versions, so this should compose. Not exercised in this repo.
- Memory: the description puts GPU compare temporaries at per-tensor size. They are allocated in the push worker while forward/backward N+1 is running, so they add to peak activation memory when the knob is on. Default-off, so the main path is unaffected.
- Smallest alternative if maintainers want this in now: same diff minus the duplicated test, plus `direct_rdma` forwarded. About +40 lines.

</details>

Not verified: torchstore's `direct_rdma` default; behavior with the SharedMemory transport; GPU runs.

- claude[bot] · comment · 2026-11-03T01:17:34Z · [source](https://github.com/pytorch/torchtitan/pull/5751#discussion_r4449752820)

File: `torchtitan/rl/trainer/trainer.py` · line 470

The delta path loses the explicit `direct_rdma=False` that the full path passes. In torchstore#279, `routing.delta.put_state_dict_delta` calls `state_dict_utils.put_state_dict(store, state_dict, key, transfer_dtype=..., preserve_dtype_keys=...)` with no `direct_rdma`, and `ts.put_state_dict_delta` has no way to pass it.

This matters because of how the controller orders things: the pull of version N is awaited only *after* `optim_step` N+1 (`controller.py:1230`). If the full put registers live GPU tensors, a generator whose row overflowed and does a full read (always the case for version 1) can read weights while the optimizer is changing them. That corrupts the weights silently, and every later delta builds on top of the bad copy. The generator comment at `generator.py:447` ("StorageVolume snapshot so generators do not read live trainer GPU tensors") relies on this snapshot.

*Unverified*: I couldn't check the default of `direct_rdma` in `state_dict_utils.put_state_dict`. If the default is False, this is fine today, but the invariant then depends on a torchstore default. Smallest fix: forward `direct_rdma` through `put_state_dict_delta` in torchstore#279 and pass `direct_rdma=False` here, the same as the full path.
