## Agent details

**TLDR:** When compiled, the MoE router runs scoring and top-k selection in one fused kernel. Its load-balance sums move into a compiled region.
Numerics: rounding only. In one MoE layer, compiling main already moves the output and grads by some rounding. This PR moves them at most half as much (Kimi K3), and about a tenth as much or less for the other 7 models. End to end, step 1 stays within 1.6x of main's own change, except Kimi K3: its loss and 4 changed expert picks (main: 0).
Speed (Qwen3.5-35B-A3B, GB300): the router is 41-63% faster at inference and 49-52% faster in fwd+bwd. The whole MoE layer is 3.4-3.6% faster in fwd+bwd.

```text
before:  gate GEMM -> softmax -> topk (ATen) -> gather + norm -> [T, E] sums (eager)
after:   gate GEMM -> [softmax + argmax rounds] [gather + norm] -> [expert counts + score sums]
                      moe_router_topk region (3 kernels for Qwen3.5)  moe_aux_loss region
```

**Stack** (merge bottom-up): this is PR 1 of 4. PR 3 (group-limited routing with argmax rounds) needs it. PR 2 (shared experts on a side stream) and PR 4 (DeepEP expand-layout training) are independent.

**Problem**
1. The Qwen3.5 router picks 8 of 256 experts per token with `torch.topk`.
2. Inductor can't fuse `topk`: it runs a separate ATen kernel.
3. The load-balance loss sums two `[T, 256]` tensors in eager.
4. **Cost.** Qwen3.5's router takes 691 µs per MoE layer fwd+bwd at 16k tokens, and 30-58 µs at decode.

**Solution**
1. **Argmax rounds.** The compiled router picks the k best experts one at a time: take the highest score, then hide it (`_topk_ids_by_argmax`). The rounds fuse with the softmax. Eager keeps `topk`.
   Example: scores [0.1, 0.9, 0.5, 0.9], k = 2. Pick 1: expert 1 (it ties with expert 3; the lower id wins). Pick 2: expert 3. `topk` makes no promise on ties.
2. **New region `moe_router_topk`** on `_score_and_select_experts`: score, select, gather, normalize, routing map. A region is a function that `local_compile` compiles. With Inductor's `batch_invariant` option, it gives a token the same result at T = 1 to 16k.
3. **Load-balance sums** move into the existing `moe_aux_loss` region.
4. **On by default** for the 8 models on the shared router (GPT-OSS not on ROCm, see NOTE).
5. **Unchanged:** the gate GEMM, the per-expert token counter (`tokens_per_expert_E`), the aux-loss gradient and the collectives stay eager. `forward` returns the same 3 tensors.

**Results**

**Numerics: not bitwise vs main. Every difference is rounding.**
- **Layer:** at most 0.5x main's own compile change for Kimi K3, about 0.1x or less for the other 7 models (table below).
- **Loss:** in every FSDP and TP run, the step-1 loss differs from main by at most 6.6e-5 relative (Kimi K3). Main's own rounding changes (eager vs compiled, or all-to-all vs DeepEP) move it by up to 1.5e-4 (Muse Spark). In the 10-step runs it is identical for Qwen3.5, DeepSeek-V3, DeepSeek-V4 and Kimi K2.5.
- **Bitwise:** regions off vs main (all but Kimi K3); a token's region output at T = 1 to 16k; grads with and without remat (recomputing activations in backward).

Why the numbers move:
1. **Scores.** The compiled softmax or sigmoid rounds differently (fp32). Max |diff| vs main, same experts: Qwen3.5 4.5e-8, DeepSeek-V3 1.2e-7, Kimi K3 2.2e-8.
2. **Expert ids.** A score that moved one rounding step can swap two near-tied experts. One router, T = 1 to 32k: Qwen3.5 0 tokens, DeepSeek-V3 1 of 16k, Kimi K3 2 of 8k and 1 of 32k.
3. **Grads.** The backward of scoring, gather and normalization is compiled too.
4. **Kimi K3, regions off only.** Its quantile router returns its picks unsorted (main: sorted), so `route_norm` adds them in another order: same experts, scores 1.5e-8 apart.

How big. One MoE layer at real size, T = 4096, both regions on, local experts. rel L2 = ||this PR - main|| / ||main||.

You may ask:
- **Why `batch_invariant`?** It keeps the region from adding its own batch-size dependence. Without it, the region gave a token other outputs at small T than at 16k in 4 of 7 runs (with it: 0 of 7). The gate GEMM before it is still not batch-invariant. Cost: up to 3.8 µs per MoE layer at decode, at most 1.9% of the whole layer (Qwen3, DeepEP EP 2, T = 1: 2.1 of 113 µs), within run-to-run noise from 4k tokens. Small, so kept on.
- **Why do the gate, counter and aux loss stay eager?** Gate: traced, its default `inplace_wgrad_accum=True` raises. With it off, compile rounds its fp32 weight grad to bf16 under FSDP2 (fix open: pytorch/pytorch#197381). Counter, aux-loss accumulators, K3's histogram: they update buffers. Remat replays the region, so an update inside would need an `is_recomputing()` guard, and that guard makes Dynamo compile a second graph.
- **Other routers?** DeepSeek-V3: decode 26-33% faster, prefill 1-21%, fwd+bwd 5-8% (its group selection keeps `topk` until stack PR 3). Kimi K3 (top 16 of 896): decode 48-63%, prefill 38-58%, fwd+bwd 13-14%.

**What this PR does.** When `moe_router_topk` is listed, everything in the router after the gate GEMM (score function, top-k, gather, route norm/scale, routing map) runs as one compiled region. That region is built with Inductor's `batch_invariant` option. Under compile, `_select_experts` replaces `torch.topk` with k masked-argmax rounds, which fuse with the softmax. The batch-wise loss's expert counts and the aux-loss score sums move into the `moe_aux_loss` region. `QuantileBalancedTopKRouter` now updates its histogram in eager code after the region, using the cutoff `max(biased scores of unpicked experts)` instead of the (k+1)-th score from `topk`. Every model on the shared router lists the region by default.

**Example.** One token, E = 4, k = 2, biased scores `[0.1, 0.9, 0.5, 0.9]`:
```text
main:     topk(sorted=False) -> {1, 3}, in unspecified order; the ids are kept by remat
this PR:  round 1 argmax -> 1 (tie: lower id wins), mask -> round 2 -> 3  => [1, 3]
          eager (regions off) still calls topk; with remat on, the ids are recomputed in backward
Quantile cutoff: main = 3rd-largest score = 0.5; this PR = max over unpicked {0, 2} = 0.5 (same except on exact ties)
```

Reply from claude: Inductor can't fuse `topk`: it lowers it to a separate ATen kernel. Inside the compiled region, k "pick the max, then hide it" rounds fuse with the scoring into the same kernel, which is where most of the decode speedup comes from. The eager path still runs when regions are off, for example in the batch-invariant RL recipes, so it keeps `topk`. Both pick the same experts except on exact ties, where `topk` makes no promise and the rounds pick the lower id. I added a one-line comment with this trade-off (e75975b5c).
