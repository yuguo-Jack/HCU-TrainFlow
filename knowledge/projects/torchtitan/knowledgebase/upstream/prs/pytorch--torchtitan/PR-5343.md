# [moe][perf] Compile the MoE router and its load-balance sums (3/3)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5343) · state: open · merged: False

## Original PR description

**TLDR:** Under compile, the MoE router picks experts with masked argmax rounds instead of `topk`, and the load-balance sums run in a region; every model on the shared router path turns it on. Qwen3.5 MoE layer fwd+bwd -3.6% at 16k; Kimi K2.5 / Muse Spark router + counts at EP 4 decode 35.9 -> 19.0 / 36.2 -> 19.9 us per layer.

**Stack** (3 PRs, merge bottom-up; this PR is in **bold**)

| # | PR | Independent? | Needs (stack positions) |
|---|---|---|---|
| 1 | Dist-MoE: skip the per-expert token count it doesn't read | yes | — |
| 2 | Shared experts on a side stream in CUDA graphs at inference | yes | — |
| **3** | **Compile the MoE router and its load-balance sums** | **yes** | **—** |

**Problem**
1. **Selection.** `TokenChoiceTopKRouter` picks 8 of 256 experts per token with `torch.topk`.
2. **Not fusable.** Inductor lowers `topk` to an ATen fallback, so a compiled router still runs a 162 us radix-select at 16k.
3. **Loss sums.** The batch-wise load-balance loss sums `[T, 256]` maps and scores in eager: ~190 us of reductions over 16 MB tensors.
4. **Cost.** The router takes 617 us per MoE layer at 16k under CUDA graphs: ~25 ms per 16k microbatch over Qwen3.5's 40 layers.

**Solution**
1. **Argmax rounds.** Under compile, `_select_experts` takes 8 masked argmax rounds (`_topk_ids_by_argmax`) that fuse with the softmax into one kernel; eager keeps `topk`.
2. **Top-k region.** Scoring, selection, gather and normalization after the gate run as the `moe_router_topk` region, compiled with Inductor's `batch_invariant` option (launch configs don't depend on the token count).
3. **Loss sums.** The batch-wise loss's counts and score sums run in the existing `moe_aux_loss` region, called where they ran before (same SPMD typing).
4. **Enabled** in the defaults of Qwen3.5 (3.6, 3.8), the Qwen3 MoE flavors, DeepSeek-V3 (so Kimi K2.5), DeepSeek-V4, GPT-OSS, Kimi K3 and Muse Spark, and so in recipes that extend them (Muse Spark 816B Dist-MoE).
5. **Kimi K3.** `QuantileBalancedTopKRouter` selects with the base `_select_experts` and updates its histogram in eager, after the region (a checkpoint recompute inside it would update it twice).
6. **Unchanged.** Counters, aux-loss injection and collectives stay in eager; ties pick the lower expert id.

```text
before:  gate -> softmax -> topk (ATen) -> gather/norm -> eager [T,E] sums for the loss
after:   gate -> [softmax + 8 argmax rounds + gather/norm] (moe_router_topk) -> [counts], [score sums] (moe_aux_loss)
```

You may ask:
- Why not `triton.decompose_sort_ops`? Slower than ATen topk here (747 vs 579 us).
- Why not include the gate? Tracing it raises with `inplace_wgrad_accum=True`; with the flag off, a compiled region rounds its fp32 weight grad to bf16.

NOTE:
- Not tested: EP>1 training beyond the DeepSeek-V4 run, GraphTrainer (traces the eager topk path), loss curves, H100.
- Not covered: the HF-backend MoE (`transformers_modeling_backend`) swaps in this router but keeps its own region list, so it doesn't compile it. Follow-up.
- The B200 RL Dist-MoE test `rl_grpo_moe_debug_dist_moe_tp2_ep4` is the first CI run of the router region in the vLLM generator (full CUDA graphs). Watch it when B200 CI runs.
- Kimi K3 in eager: ids within a row now come unsorted, so route-norm scores can move by 1 ulp; same experts except on exact ties; histogram unchanged.
- Goldens: 5 integration tests compare losses exactly and change with the new defaults: `qwen3_moe_fsdp+tp+cp+ep_param_groups`, `deepseek_v3_fsdp+ep`, `deepseek_v3_fsdp+cp+pp+ep`, `gpt_oss_fsdp+tp+ep`, `gpt_oss_pp+fsdp+cp+ep+sacop`. This PR refreshes their A10G real-PG goldens (Integration Tests export run). `ciflow/fake-pg` and `rocm` stay red on them until the A10G fake-PG and the MI350X goldens are regenerated (follow-ups).

- felipemello1 · comment · 2026-10-15T01:49:37Z · [source](https://github.com/pytorch/torchtitan/pull/5343#discussion_r4278182922)

File: `torchtitan/models/common/moe.py` · line None

reply from claude:
It's the part of `forward` that traces and doesn't update state:
```
gate (eager) -> [score, top-k, gather, normalize, routing map] -> counts, aux loss (eager)
```
- Gate: raises when traced with `inplace_wgrad_accum=True` (the default); with the flag off, a compiled region rounds its fp32 weight grad to bf16.
- Counts, aux loss: they update buffers. Compiled, `remat.is_recomputing()` is always False, so a recompute pass would count them twice. Their `[T, E]` sums run in `moe_aux_loss`, as the microbatch-wise loss already does.
- Same rule for subclasses: `QuantileBalancedTopKRouter` updates a histogram in `_select_experts`, so it now always runs this step eagerly, with a test (the histogram doubled before: 12 -> 24).

Router, 16k tokens, GB300: 617 us eager -> 579 (region, ATen `topk` inside) -> 437 (argmax rounds) -> 301 (+ aux-loss sums).
Renamed to `moe_router_topk` / `_score_and_select_experts`: it is the router's top-k stage, next to `moe_dispatch` and `moe_combine`.

reply from claude:
Small. It's what the microbatch-wise loss already does: `_microbatch_load_balance_local_stats` runs the same counts in `moe_aux_loss`. Eager casts the `[T, E]` bool map to an fp32 copy, then sums it; compiled reads the map once. H100, per MoE layer:
```
tokens   _expert_counts      _norm_sum_scores_over_tokens (fwd+bwd)
4k       14.7 -> 3.4 us      57.8 -> 9.1 us
16k      31.7 -> 5.5 us      172.3 -> 20.0 us
```
`_expert_counts` alone saves ~1 ms per 16k microbatch over 40 MoE layers. With the score sums, it is the 437 -> 301 us router step in the PR body (GB300). I added the number to its docstring.
