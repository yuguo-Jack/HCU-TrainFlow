## Why

Full-scale pipeline MoE training needs driver-visible free memory for communication and expert buffers allocated outside PyTorch's caching allocator. The 256-GPU MXFP8 factory releases unused startup and first-forward blocks before each stage's first training backward. Other graph workloads preserve their seeded cache, so this once-only policy is opt-in.

Both final full-scale recipes leave per-update cache clearing disabled. That unused option is removed from this PR; update-boundary behavior and FSDP reshard/reduction-stream APIs are unchanged.

**Example.**

```python
ParallelismConfig(
    pipeline_parallel_degree=4,
    pipeline_parallel_empty_cache_before_first_backward=True,
)
# Evaluation does not consume the startup release.
# First training backward: one release per local stage instance.
# Later microbatches and captured replay: no cache release.
```

## What changed

- Add a stage-owned, once-only startup release and retain it when Kimi rebuilds attention-residual stages.
- Keep forward-only evaluation from consuming the startup token.
- Reject the option without PP and in HF Transformers/GraphTrainer pipeline implementations that would otherwise ignore it.
- Preserve upstream's positive layer-count validation and native backward arguments.

No per-update engine branch, FSDP lifetime wrapper, reduction-dtype change or model-kernel change is added.

## Alternatives considered

- Releasing cache before every pipeline action adds allocator work to the hot path.
- An unconditional startup release discards other graph workloads' seeded cache.
- Extra update-boundary policy has no enabled consumer in the final recipes and is not needed here.

## User-facing changes

| Policy | Default | Boundary |
| --- | --- | --- |
| `parallelism.pipeline_parallel_empty_cache_before_first_backward` | `False` | Once per local stage instance, before its first training backward action |

## Numerics

Fresh GPU-0-only validation uses native one-stage `PipelineStage` and `Schedule1F1B`, four microbatches per update, seed 42, and strict deterministic algorithms. FP32 and BF16 runs compare startup release off/on in eager and graph execution against the native eager stage. Loss, gradient norm, all gradients and updated weights match bitwise over five updates, including two warmups, capture and replay.

This is an allocation-policy component check, not real multi-rank PP/VPP acceptance or a full-model throughput claim. Earlier PP2/VPP2 eager/graph checks are historical, not fresh results for this narrowed prefix.
