# [rl] spawn_proc_mesh: roles that share a host mesh get disjoint GPUs

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5269) · state: closed · merged: True

## Original PR description

**TLDR:** With caller-provided host meshes, every role started allocating at GPU 0, so four 1-GPU generators on one 4-GPU host all got `CUDA_VISIBLE_DEVICES=0`. Now roles given the same host mesh get consecutive GPUs, and a layout that doesn't fit fails before anything is spawned.

**Problem**
1. With `host_meshes` set, `spawn_proc_mesh` calls `_spawn_proc_mesh` once per role: the trainer, then each generator.
2. `_spawn_proc_mesh` builds a new `PerHostProvisioner` on every call (`torchtitan/rl/train.py:160`), so every role starts at GPU 0.
3. Roles given the same host mesh get overlapping `CUDA_VISIBLE_DEVICES`.
4. Each vLLM engine reserves 90% of its GPU by default (`gpu_memory_limit`, `torchtitan/rl/generator.py:788`), so a second engine on GPU 0 does not fit.
5. When: only launchers that pass `host_meshes` and put several roles on one mesh. We caught it before a GB300 launch whose launcher gives each host's four 1-GPU generators one host mesh. The single-node path (`host_meshes=None`, used by `main()`) already shares one provisioner and is not affected.

**Solution**
1. `spawn_proc_mesh` builds one `PerHostProvisioner` per host mesh and passes it to `_spawn_proc_mesh`, which used to build its own.
2. Roles on the same host mesh get consecutive GPUs in spawn order: trainer first, then generators.
3. `_check_gpus_per_host` runs before the first spawn: it fails if the roles on one mesh need more than `gpus_per_node` GPUs per host, or if a role's world size doesn't split evenly across its mesh's hosts (moved up from `_spawn_proc_mesh`).
4. Unchanged: a role on its own host mesh still starts at GPU 0, and the single-node path.

```text
2 one-host meshes A, B with 4 GPUs each; trainer 2 GPUs; six 1-GPU generators
HostMeshes(trainer=A, generators=[A, A, B, B, B, B], gpus_per_node=4)
  A: trainer 0,1 | gen0 2 | gen1 3           4 of 4
  B: gen2 0 | gen3 1 | gen4 2 | gen5 3       4 of 4  -> OK
generators=[A, A, A, B, B, B]
  A needs 5 of 4                                     -> fails before anything is spawned
```

**Results**
`CUDA_VISIBLE_DEVICES` per role for the OK layout above (CPU check, fake host meshes):
```
main:     trainer 0,1 | A gens 0, 0 | B gens 0, 0, 0, 0
this PR:  trainer 0,1 | A gens 2, 3 | B gens 0, 1, 2, 3
```
On GB300, an earlier version of this change (same allocation logic) put each host's 4 generators on GPUs 0-3.

You may ask:
- Why key by `id(host_mesh)`? `HostMesh` is unhashable, and its `__eq__` blocks until the mesh is up, so `==` could stall the controller's event loop.
- Why per host mesh, not per physical host? `spawn_proc_mesh` only sees `HostMesh` objects. Two objects over the same host (e.g. two `this_host()` or `slice()` calls) still get separate provisioners, as on main. To pack roles on one host, pass the same object.

NOTE: roles on one host mesh that need more than `gpus_per_node` GPUs per host now fail in `spawn_proc_mesh` before anything is spawned; on main they silently overlapped.

**Test plan**
```
PYTHONPATH=$PWD python -m pytest -q tests/rl/unit_tests/cpu/test_shutdown.py   # 16 passed
```
- `test_spawn_proc_mesh_gives_roles_sharing_a_host_mesh_disjoint_gpus`: the OK layout above; fails on main.
- `test_spawn_proc_mesh_checks_gpus_per_host_before_spawning`: the over-capacity layout and an uneven world size fail, and nothing is spawned; fails on main.

### Answers to @tianyu-l's inline questions

**1. `train.py:160`: does this enable one host serving several roles, e.g. trainer and generator?**
Not really a new capability.
- The single-node path (`host_meshes=None`, used by `main()`) already puts the trainer and every generator on one `this_host()` with one shared `PerHostProvisioner`.
- The 8-GPU RL integration CI runs that path, so co-locating the trainer and generators on one host is already exercised end-to-end, torchstore weight sync included.
- On `main`, the `host_meshes` path just didn't partition GPUs. Passing the same mesh to several roles was accepted, but every role got `CUDA_VISIBLE_DEVICES` starting at 0. That's a silent bug, not an unsupported feature.
- The PR's motivating case (four 1-GPU generators on one host, trainer elsewhere) doesn't co-locate trainer and generator at all.
- One thing torchstore could still hit, though I think it's unlikely: the multi-host trainer and generator on one mesh is new territory. Every proc there sees a local `CUDA_VISIBLE_DEVICES` that doesn't start at 0. The single-node path already does this for generators (e.g. `CUDA_VISIBLE_DEVICES=4`), so any device-index assumptions in torchstore's RDMA transport should already be shaken out.

**2. `train.py:258`: what happens with duplicate keys in the dict comprehension?**
- A later duplicate key overwrites the earlier value. With `[A, A, B]` the comprehension builds three provisioners and keeps two: the second `A` replaces the first.
- That's harmless because nothing has been allocated yet when the dict is built. Each `id` ends up mapped to exactly one instance, and every lookup afterwards returns that same instance. The new test checks this: `mesh_a.visible_devices == ["0,1", "2", "3"]`.
- On the first half of your question: the key is `id(host_mesh)`, the object's identity, not the host. Two different `HostMesh` objects over the same physical host get **separate** provisioners, and both start at GPU 0. The PR description and the `_check_gpus_per_host` docstring both say this. Only roles given the *same object* share GPUs.

### Suggestions (all non-blocking)

1. **Make the dedup explicit (`train.py:256-259`).** Overwriting is correct, but it's exactly what prompted question 2. Something like this would make it obvious:
   ```python
   provisioners: dict[int, PerHostProvisioner] = {}
   for host_mesh in [trainer_host_mesh, *generator_host_meshes]:
       provisioners.setdefault(id(host_mesh), PerHostProvisioner(total_gpus=gpus_per_node))
   ```
   Or just note in the comment that a repeated mesh maps to a single provisioner.

2. **Partially overlapping meshes aren't detected.** Say the trainer gets a 2-host mesh `M` and a generator gets `M.slice(hosts=0)`. These are different objects, so both start at GPU 0 on host 0 and still overlap. That's the same as `main` and the PR documents it under "per host mesh, not per physical host". It's fine to leave, but a `TODO` near the `id()` keying would help the next person debugging an overlap.

3. **Two capacity checks now cover the same thing.** `_check_gpus_per_host` and `PerHostProvisioner.allocate` (`RuntimeError`) both enforce capacity. That's fine: the pre-check is what guarantees nothing gets spawned. But since `_spawn_proc_mesh` now silently relies on the caller having validated divisibility, its docstring could say "caller must have validated with `_check_gpus_per_host`". Otherwise, a future caller that skips the check gets a truncated `role_world_size // nodes` with no error.

4. **Small style points.**
   - The `ValueError` dumps a dict (`{'trainer': 2, 'generator0': 1, ...}`). That's readable enough. Listing only the roles on the over-full mesh, which it already does, is the useful part.
   - `assert len(generator_host_meshes) == num_generators` sits next to the new `ValueError`s but is also user-facing config. Under `CLAUDE.md` it should arguably be a `ValueError` too. It predates this PR, so it's optional here.
