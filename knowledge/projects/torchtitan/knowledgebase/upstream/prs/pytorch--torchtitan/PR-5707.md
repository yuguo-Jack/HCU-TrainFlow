## Agent details

**TLDR:** `ChunkedLossWrapper` now runs the lm_head only on the tokens the loss reads: `loss_mask` in RL, labels != `IGNORE_INDEX` in SFT. It's on by default, and the engine turns it off under accelerator graphs. Loss region: 4.9-6x faster with the RL 35B-A3B head, 8.9x with the SFT 9B head. SFT end to end: +15% tokens/s (0.8B, 128k tokens per step). Peak memory is at or below main's at every loss-token fraction (up to 256k tokens, D 4096); with every token a loss token (pretraining packs) it runs main's code. With the flag off it's bitwise equal to main, and with it on its grads are as close to main as main is to itself with a different chunk count (TP2, CP2).

```text
main:     hidden [T, D] -> N chunks of T/N rows (views)                                  -> lm_head + loss
this PR:  rows = loss tokens first (stable sort of loss_mask, or labels != IGNORE_INDEX)
          hidden [T, D] -> ceil(K*N/T) chunks of <= T/N rows, each gathered in the loop -> lm_head + loss
          grads [K, D] -> one index_copy_ into the [T, D] grad (other tokens: 0)
          T=8, N=4, loss tokens [F T T F F F T F] -> rows [1 2 | 6 0]: K=3 loss tokens + 1 pad, 2 chunks
```


**Problem**
1. `ChunkedLossWrapper` runs the lm_head (`[V, D]`, V = 248k for Qwen3.5) on every token, chunk by chunk.
2. The loss reads only some of them: the policy's responses in RL, the answers in SFT.
3. In multi-turn tool use and few-shot SFT, prompts and tool outputs can be most of the tokens (8-shot GSM8K below: 92%).
4. Cost: Qwen3.5-35B-A3B head, 64k tokens, 16% loss tokens: 420-518 ms fwd+bwd per microbatch, compiled; the loss tokens alone take 70-89 ms.

**Solution**
1. **Loss tokens.** `loss_mask` if the loss gets one (RL), else labels != `IGNORE_INDEX` (SFT). A TODO in the skip says to consider a `loss_mask` in SFT too.
2. **Fewer chunks, never longer.** A stable `argsort` puts the K loss tokens first, in order. They run in `ceil(K*N/T)` chunks of `ceil(K/chunks)` rows, and the first non-loss tokens pad the last chunk (zero loss and grad). With no loss tokens, one row runs, so FSDP still reduce-scatters the lm_head grad.
3. **Main's code when nothing is skipped.** If every token is a loss token (pretraining packs), the skip runs main's path, so memory and numerics match main exactly.
4. **One chunk copy at a time.** Each chunk gathers its rows inside the loop, so no `[K, D]` copy of the hidden states is held. Their grads fill a `[K, D]` buffer, and one `index_copy_` writes it into a zero `[T, D]` grad after the loop.
5. **MTP.** With multiple outputs, they all use one row set: tokens that any output's labels read.
6. **On by default.** `ChunkedLossWrapper.Config.skip_non_loss_tokens=True`, and the RL recipes drop their explicit flag.
   - With accelerator graphs on, `TrainingEngine` turns it off (logged at info), since graphs need a fixed row count. This replaces the earlier config error.
   - GraphTrainer keeps it off: subclass default, `to_graph_trainer_config`, and a config check.
   - `AnswerTokenLoss` (decision recipe) gathers its rows itself with a static shape, so it keeps it off too.
7. **Unchanged:** main's chunk loop, `GradAccumulator`, the decoder-backward bridge, and everything with the flag off (bitwise).

You may ask:
- Why does RL read `loss_mask` and SFT read labels? RL labels are real token ids on every row, so only `loss_mask` marks the response. SFT has no mask and marks the prompt with `IGNORE_INDEX`. 7 of 11 libraries with both SFT and RL use one mask for both; the TODO notes it.
- Why sort instead of `nonzero()`? The sort keeps every chunk the same length, so main's `_chunk_local`, `GradAccumulator` and loop run unchanged, with no special case for the last chunk.
- Why not graphs? The row count changes every microbatch. Keeping the loss outside the graph means splitting the step's fwd/bwd graph at the loss, per microbatch (FSDP hooks, remat and PP cross the split). A fixed row budget gathered with `nonzero_static` is graph-safe, as `AnswerTokenLoss` does, but saves only down to the budget. Both are follow-ups; no RL recipe captures graphs today.
- Why on by default? The skip doesn't change the result of any loss that reads only its loss tokens: CE and MTP CE ignore `IGNORE_INDEX` rows, and DAPO and GRPO read only `loss_mask` tokens. Those are every `loss_fn` used with `ChunkedLossWrapper` in the repo. A loss that reads other tokens (entropy or KL over all tokens) must set it to False; the field docstring says so.

NOTE: one host sync per microbatch (`int(is_loss_token.sum())`). Pretraining with graphs off now pays it too; the measurement above (91.0k vs 92.4k tokens/s) is inside single-run noise.
NOTE: the engine sets the built loss's flag to False under graphs, so a config dump shows True while the run uses False. An info log says so.
NOTE: MFU still counts the lm_head over all tokens, so it reads high with the flag on.
NOTE: goldens. `tests/assets/losses/rl_grpo_cuda.txt` (A10G, bitwise) came from this PR's A10G CI run, when its recipe first ran the skip; max change vs main 3.1e-9 absolute. Two goldens run with graphs off on data with ignored labels, and I updated them from this PR's CI (adb2d13e2): `real_pg/kimi_k3_b200.txt` (multimodal; steps 1-2 bitwise, max loss diff 3.5e-3) and `real_pg/mi350x/sft.txt` (ROCm has no graphs; step 1 bitwise, max loss diff 5e-4). The other real-PG and fake-PG suites passed unchanged: graphs-off pretraining goldens have no ignored labels, so they run main's path.
