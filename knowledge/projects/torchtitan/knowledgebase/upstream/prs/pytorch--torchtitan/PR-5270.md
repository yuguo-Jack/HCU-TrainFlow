# [rl] Verifiers generation server: reject prompts that leave no room for an output token

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5270) · state: closed · merged: True

## Original PR description

**TLDR:** A Verifiers prompt of exactly `max_rollout_tokens` tokens reached vLLM, and vLLM's rejection crashed the generator's engine loop. A Qwen3.5-9B Terminal-Bench run lost a generator this way, and 214 rollouts failed against it in the next 6 minutes. `GenerationServer` now answers that prompt with a 400 before it reaches the generator.

**Problem**
1. On the Verifiers path, each turn's prompt is the whole conversation so far, so it grows over a long rollout.
2. Verifiers' client checks the prompt against the advertised `max_model_len`, but rejects only `len(prompt) > max_model_len` (`renderers/client.py:285`). A prompt of exactly `max_model_len` tokens goes through.
3. vLLM needs room for one output token, so it rejects that prompt (`vllm/v1/engine/input_processor.py:472-480`).
4. The generator admits requests without a per-request guard (`torchtitan/rl/generator.py:1335-1353`), so the rejection ends the engine loop:
   - every other request in flight on that generator fails with the same error, and Verifiers ends those rollouts as `context_length`;
   - every later request to that generator fails with "generator is closed", which the harness retries.

**Solution**
1. `GenerationServer` returns a 400 when `len(prompt_token_ids) >= max_rollout_tokens`, through its existing error-to-400 path.
2. The message starts with "This model's maximum context length is", which Verifiers maps to `OverlongPromptError` (`verifiers/v1/errors.py:102-103`), so the rollout ends as `context_length` and isn't retried (`verifiers/v1/interception/server.py:600-609`).
3. Unchanged: recipes already pass the generator's context length as `max_rollout_tokens` (`torchtitan_recipes/rl/verifiers_terminal_bench.py:139`); the field docstring now says so. The native `TokenEnv` path already stops at `prompt_len >= max_rollout_tokens` (`torchtitan/rl/rollout/environment/token.py:302`).

```text
cap N = max_rollout_tokens = the generator's max_model_len

prompt tokens    before                                   after
N - 1            generator samples 1 token                same
N                reaches vLLM -> engine loop crashes      400 -> rollout ends as context_length
N + 1            Verifiers' pre-flight check stops it     400 (if a client skips the check)
```

**Results**
The new CPU test sends N - 1, N and N + 1 tokens with N = 8: only N - 1 reaches the generator, and Verifiers' `model_error` reads the 400 for N as `OverlongPromptError`. It fails with the server change reverted.

NOTE: not run end to end with the fix.

You may ask:
- Why not fix the renderer's `>`? It's an external package, and the server check also covers clients that skip the pre-flight check.
- Why not advertise `max_model_len = max_rollout_tokens - 1`? `max_model_len` would no longer be the context length, and a client that skips the check would still crash the generator.
- Why not keep the engine loop alive on any rejected request? That's a separate change to the generator. Until then, other requests vLLM rejects (e.g. an empty prompt) still end the loop.

**Test plan**
```bash
pytest tests/rl/unit_tests/cpu/test_verifiers.py   # needs verifiers + renderers; 10 passed
pytest tests/rl/unit_tests/cpu                     # 553 passed; the 2 failures in test_verifiers_terminal_bench.py also fail on main
```
