# [rope][perf] Compile ComplexRoPE in real arithmetic (rope region)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5196) · state: open · merged: False

## Original PR description

NOTE:
- This PR makes `ComplexRoPE` compilable and turns the `rope` region on by default for Llama 3, DeepSeek-V3 (Kimi K2.x inherits it), Muse Spark and Muse Glimmer.
- `rope` replaces the `complex_rope` and `cos_sin_rope` region names. `ComplexRoPE` and `CosSinRoPE` share the name, each with its own compile options, so Qwen3 and GPT-OSS keep their behavior. Configs that list `complex_rope` or `cos_sin_rope` must switch to `rope`; an unknown name raises.
- The overrides are untouched. Muse Spark keeps its Helion RoPE kernel until "[muse_spark][perf] Compile RoPE with the q/k norms; drop the Helion RoPE override" (later in this stack). DeepSeek-V3's fused MLA override keeps doing its own RoPE.
- DeepSeek-V4 turns the region on in "[dsv4][perf] Compile the attention's q norm + RoPE glue (q_norm_rope, partial_rope)".

**TLDR:** Under compile, `ComplexRoPE` rotates in real arithmetic instead of a complex multiply, as the `rope` region, now on by default. The cache rows are gathered as floats, so the gather fuses into the rotation, and bf16 pairs are written as one int32 each, so stores are contiguous. RoPE prefill at 64k vs eager: Llama 3 8B 1126.5 -> 224.3 us, DeepSeek-V3 2589.9 -> 426.5 us. For contiguous q/k it is on par with or faster than the Helion RoPE kernel at 16k-64k. Outputs and grads are bitwise equal to eager for every model measured (GB300).

**Problem**
1. **ComplexRoPE.** `apply_rotary_emb` rotates q/k with `view_as_complex` and a complex multiply.
2. **No complex codegen.** Inductor can't generate kernels for complex tensors.
3. **Fallbacks.** So a compiled `ComplexRoPE` still runs those ops as separate eager kernels.
4. **Cost.** Llama 3 8B's RoPE at 64k tokens (q `[64k, 32, 128]`, k `[64k, 8, 128]`) in eager: 2223.4 us fwd+bwd, 1126.5 us prefill.

**Solution**
1. **Real arithmetic under compile.** Rotate each `(x[2i], x[2i+1])` pair in fp32 with `cos`/`sin`, instead of `view_as_complex` and a complex multiply.
2. **One int32 per bf16 pair.** Write each rotated bf16 pair as one int32, so stores are contiguous.
   - Contiguous inputs are also read that way: a bf16 shifted into the high 16 bits is its exact fp32.
   - Split views, such as DeepSeek-V3's `q_pe`, read their two halves, since an int32 view of a strided tensor is copied first.
   - fp32 and fp16 inputs rotate in fp32, cast each half to the input dtype, and stack.
3. **Float cache gather.** Under compile, `_reshape_cache` gathers rows of the cache's real view `(T, 1, dim)`. A complex gather ran as its own kernel; the float gather fuses into the rotation.
4. **Custom backward.** `_RotatePairs` rotates the grad by the opposite angle, in one kernel. It is required: the int32 bit views have no autograd.
5. **On by default.** `rope` joins the default `local_compile_regions` of Llama 3, DeepSeek-V3, Muse Spark and Muse Glimmer, and replaces `cos_sin_rope` in Qwen3 and GPT-OSS.
6. **Unchanged:** eager, and the overrides that replace RoPE (Helion, fused MLA).

```text
eager:     x -> view_as_complex -> * cache[positions] (complex) -> view_as_real          (unchanged)
compiled:  x, cache[positions] as floats -> rotate in fp32 -> bf16: one int32 per pair    (one kernel)
           backward: the same rotation by -angle
```

**Results**
```text
Numerics (GB300): bitwise identical to eager, outputs and q/k grads, train and no_grad, bf16, for every model below
          (Llama 3 8B, Muse Glimmer 30B, Muse Spark 816B shapes, DeepSeek-V3 671B with strided q_pe / k_pe, Kimi K2.5).
          Not guaranteed by construction: Inductor may contract the real arithmetic into FMAs.
          fp32: within assert_close defaults of eager (test_compiled_matches_eager_complex).
Batch invariant: a full batch and its uneven chunks match bitwise, outputs and grads (3 head layouts, T up to 8192),
          and test_compiled_is_batch_invariant passes. The earlier version's break with a real-view gather does not
          reproduce on this code.
```

You may ask: why not stack per half for bf16 too? With dynamic T the stride-2 stores stop vectorizing at the ragged row tail. Writing each pair as one int32 keeps the stores contiguous for every bf16 input; only contiguous inputs can also be read that way.
You may ask: the int32 view ends the fusion with whatever produced x. Inside the norm + RoPE regions, the normed q/k are written out first. Net it still wins: Muse Spark's q/k region is faster than Helion at every size in the PR that uses it.
You may ask: why keep the cat options (`max_pointwise_cat_inputs=0`, `max_complex_pointwise_cat_inputs=0`) on ComplexRoPE? Only fp32/fp16 inputs still stack, and without the options fp32 prefill is 1.4x slower (Llama 3 shapes, 16k: 122.9 vs 172.4 us). They make CosSinRoPE 1.3-2.6x slower (Qwen3 shapes, 16k-64k), so each class keeps its own decorator under the shared name.
You may ask: why not DeepSeek-V4 here? Turned on alone it goes past the graph limit; its glue PR enables it together with the glue regions.
NOTE: not tested: GraphTrainer (it traces the eager branch), H100, multi-GPU.
NOTE: golden losses: on A10G the compiled rotation is not bitwise equal to eager (on GB300 it is), so this PR refreshes the A10G goldens of the models that compile it, from this PR's CI:
  - Fake PG `llama3.txt`, `deepseek_v3.txt`; Real PG `llama3_pp.txt`, `deepseek_v3_cp_pp.txt`.
  - Losses move by at most 1.5e-4 relative over 10 steps, with no drift. Llama 3 Fake PG is bitwise through step 5.
  - On A10G, compiled still matches eager within `assert_close` (`test_compiled_matches_eager_complex` passes there).
  - Every PR above this one printed the same Fake PG values, so none of them moves these goldens.
  - ROCm mi350x goldens run only on main or with a `ciflow/rocm` tag, and may need a refresh after landing.

### Review: complex RoPE math change

**Verdict:** I found no correctness problems in the math. Below is what I checked, then a few small suggestions. I could only read the code: this runner has no permission to run Python, so I ran nothing on CPU or GPU.

#### What I checked in `_RotatePairs` (`torchtitan/models/common/rope.py:319-365`)

1. **Forward formula.** `real = xr*cos - xi*sin` and `imag = xr*sin + xi*cos` are the same terms as `c10::complex` `(a+bi)(c+di)` with `x` on the left. Floating-point addition is commutative, so the only possible difference from eager is FMA contraction. The PR body already says this.
2. **Inverse.** `sin = -sin` is the same as `rope_cache.conj()`, and it applies to both q and k, as eager does.
3. **Backward.** For `y = R(θ)x`, the input gradient is `R(θ)ᵀ g = R(-θ) g`, so `rotate(grad, cos, -sin)` is right. With `inverse=True` the sign flips twice, which is also right.
   - The rounding points match eager. Eager's backward upcasts with the `type_as` backward, runs the complex-mul VJP in fp32, then rounds once to bf16 in the `.float()` backward. `rotate(grad)` does the same: fp32 math, then one `type_as(x)`.
   - Returning `None` for `cos`/`sin` is fine, since they come from a non-persistent buffer.
4. **Reading a bf16 pair as one int32.** `x.view(int32)` puts `x[2i]` in the low 16 bits.
   - `pairs << 16` gives exactly the fp32 value of `x[2i]`.
   - `pairs & ~0xFFFF` (Python `-65536`, i.e. `0xFFFF0000` as an int32) gives exactly the fp32 value of `x[2i+1]`.
   - Both are exact because a bf16 is the top half of an fp32.
5. **Writing the pair back.** `int16 -> int32` sign-extends, then `& 0xFFFF` strips the sign bits. `imag << 16` shifts the sign extension out. `(low | high).view(bf16)` then puts `real` at `2i` and `imag` at `2i+1`, which is the interleaving eager produces, and the last dim goes back from `H/2` to `H`.
6. **Cache under compile.** `view_as_real(cache).flatten(-2)` has shape `(T, 1, dim)`. `unflatten(-1, (-1, 2))[..., 0/1]` gives `cos`/`sin` of shape `(T, 1, dim/2)`, which broadcasts against `x_real` of shape `(T, N, dim/2)`. Direct callers that pass the complex cache (Kimi / Muse Spark vision encoders, the fused-MLA test) take the `is_complex()` branch and broadcast the same way as eager.
7. **Callers.** Every q/k slice offset is even: DSv3 `q_pe` at 128, `k_pe` at 512; DSv4 rope slice at 448. So the int32 view is valid wherever it is taken.
   - At decode, a `[1, 1, 64]` slice of a wider row reports `is_contiguous()` (strides of size-1 dims are ignored), so it takes the int32-read path. It still works because the strides and offset are even.
   - If a future caller sliced at an odd offset, `view(int32)` would raise; it would not give wrong numbers silently. So relying on the comment is acceptable.
8. **Region config.** `_LOCAL_COMPILE_CALLBACKS` keeps a list per name, so two decorators with different options under `"rope"` is supported. There are no stale `complex_rope` / `cos_sin_rope` region names left in the repo. `HelionComplexRoPE.forward` overrides the compiled `forward`, so Muse Spark's override still wins.

#### Suggestions (all minor)

1. **The branch is `torch.compiler.is_compiling()`, not "the `rope` region is enabled"** (`rope.py:269`, `rope.py:289`).
   - Any enclosing compile now takes the real-arithmetic path: full-model `compile.components=["model"]`, a compiled vision encoder that calls `ComplexRoPE.apply_rotary_emb`, or the later q/k-norm regions that inline RoPE.
   - That is probably what you want, but it changes the code path for existing full-model-compile users of Llama 3 / DSv3 / Kimi, even with `rope` removed from `local_compile_regions`.
   - The numerics in the PR body only cover the region. Please state this in the PR body, and ideally run one full-model-compile loss comparison (Principle 5).
2. **Endianness is implicit.** The comment at `rope.py:345` ("`x[2i]` in the low half") only holds on little-endian hardware. That is true for every CUDA and ROCm target, but saying "(little-endian)" would make the bit layout self-documenting.
3. **The test does not match the bitwise claim.** `test_compiled_matches_eager_complex` uses `assert_close` with default bf16 tolerances, and its comment says results "can differ from eager complex by 1 bf16 ulp in rare elements". The PR body says bitwise for every measured model.
   - Both are defensible, because FMA contraction isn't guaranteed.
   - Consider asserting `rtol=0, atol=0` for the contiguous bf16 case as a regression tripwire, since that is the property the goldens depend on. Or keep it as is and align the comment with the body.
4. **Memory, no action needed.** `ctx.save_for_backward(cos, sin)` saves strided views of the gathered `(T, 1, dim)` fp32 cache. Eager's complex-mul backward also saves the gathered cache, so this is not a regression. The AOT partitioner may also choose to recompute the gather from `positions`.

Overall, the math (forward, inverse, backward, and bit packing) is consistent with eager `ComplexRoPE`, and the design comments in the code explain the non-obvious choices well. The only item I'd push on before landing is suggestion 1.
