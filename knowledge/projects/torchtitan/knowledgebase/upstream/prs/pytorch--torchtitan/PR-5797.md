## Agent details

**TLDR:** The compiled cross-entropy (CE) loss now uses Inductor's fast exp. With bf16 logits, CE forward + backward gets 16-19% faster on a GB300, and the error vs an fp64 reference stays the same. End to end that is about 0.25-0.5% of a training step (estimated from GB300 step times, see Results).

```python
# before
@local_compile("loss", batch_invariant=False)
def cross_entropy_loss(...)
# after
@local_compile("loss", batch_invariant=False, options={"use_fast_math": True})
def cross_entropy_loss(...)
```

**Problem**
1. Every decoder model turns on the `loss` region by default. It compiles `cross_entropy_loss` into one forward kernel (online softmax) and one backward kernel.
2. Both kernels compute `exp` of every logit. Inductor emits the accurate `libdevice.exp` for it.
3. With bf16 logits, that exp, not memory, sets the speed: changing only the exp makes both kernels faster while they move the same bytes.
4. Cost: at DeepSeek-V3 shapes, CE fwd+bwd takes 0.722 ms. Moving the bytes needs only 0.448 ms: the forward reads the 1 GB of bf16 logits, and the backward reads them again and writes dlogits. That is 3 passes at 7.1 TB/s.

**Solution**
1. `use_fast_math=True` makes Inductor emit `tl_math.exp` (the hardware approximate exp) instead of `libdevice.exp`. On CUDA it changes nothing else. On ROCm it also changes `tanh`, which CE doesn't use.
2. The option is set on the `cross_entropy_loss` region only. No global Inductor setting changes.
3. Unchanged: eager, and the two other functions in the `loss` region, `compute_logprobs` and `mse_loss`.

**Numerics**

```text
bf16 logits: not bitwise vs main. The error vs fp64 equals main's region in every digit shown, or is lower
(peaked rows). Main's region was not bitwise vs eager either.
fp32 logits: the dlogits error is 1.3x main's on random rows, 1.9x on peaked rows.

GB300 (CUDA), labels with 5% ignore_index, summed loss, fwd+bwd, one GPU
                                          eager       main region   this PR
bf16 [4096, 129280]   loss error          3.2e-10     7.24e-8       7.24e-8
                      dlogits error       4.32153e-5  4.32153e-5    4.32153e-5
                      elements != eager   0           3,817         36,551      (of 530M)
bf16 [16384, 248320]  loss error          2.21e-8     2.21e-8       2.21e-8
                      dlogits error       3.35856e-5  3.35856e-5    3.35856e-5
                      elements != eager   0           72,375        305,745     (of 4.07G)
bf16 peaked rows      error, target slots 3.16e-3     3.54e-3       3.36e-3
  [4096, 129280]      error, other slots  1.53e-3     1.53e-3       1.53e-3
                      elements != eager   0           26,677        81,914
bf16 TP path (vocab-parallel CE at world size 1)
     [4096, 129280]   dlogits error       4.32153e-5  4.32153e-5    4.32153e-5
fp32 [4096, 129280]   dlogits error       3.83e-9     3.96e-9       5.10e-9     (1.3x)
```

- Errors are relative to an fp64 reference. dlogits error is the relative L2 norm of (dlogits - fp64 dlogits).
- With bf16 logits, the bf16 rounding of dlogits sets the error. The fast exp's worst error is 1.75e-6 relative (GB300, vs fp64), and bf16 rounds at 3.9e-3, so it only changes which elements round differently from eager. Split into target slots and other slots, both errors still match main's region.
- Peaked rows: each target logit is set 15 above its row's max, so p_target is about 1 - 5e-5. There the fast exp is at least as accurate as main's region.
- With p_target about 1 - 3e-7 (target 20 above the max), p_target - 1 cancels in fp32 math, so the target-slot error is large. Main's region and this PR give the same error there (0.63).
- fp32 logits reach CE in Muse Glimmer: its head upcasts the logits for the soft-cap. Its `.float()` then casts dlogits back to bf16, which hides the extra error.

**Results**

```text
GB300, CUDA-graph replay, median of 7 x 20 replays, fwd+bwd per call, torch 2.16.0.dev20261030
shape                                  eager     main region   this PR    delta
bf16 [4096, 129280]   (DeepSeek-V3)    3.930     0.722         0.604      -16%
bf16 [16384, 248320]  (Qwen3.5)        29.324    5.063         4.122      -19%
fp32 [4096, 129280]                    3.046     0.975         0.967      -1% (memory-bound)
```

- Main's region and this PR ran in one process on the same inputs.
- End to end: DeepSeek-V3 runs CE twice per microbatch (main head + MTP head), so this saves ~0.24 ms per microbatch. A DeepSeek-V3 last pipeline stage took 48-68 ms on GB300 in earlier measurements, so that is ~0.35-0.5%. For a Qwen3.5-4B 16k microbatch (~400 ms, estimated) it is ~0.25%.

**Convergence**

The gap between the two runs (mean 0.003) is 50x smaller than main's own step-to-step change (0.18).

```text
Qwen3 0.6B, random init, C4, 500 steps of 16k tokens, 1 GB300 per run, same seed
                                        main      this PR
mean loss, steps 401-500                6.2520    6.2513
gap per step, steps 401-500             mean 0.0033, max 0.013
gap per step, all 500 steps             max 0.047
main's step-to-step change, 401-500     mean 0.18
```

- The runs were not in deterministic mode, and no main-vs-main pair was run. So the gap includes run-to-run noise.

**Loss goldens change**

- CI compares losses and grad norms with the goldens exactly: `assertEqual` on each step (`scripts/loss_compare.py`).
- 21 golden files change: every golden test whose run computes CE in the `loss` region.
  - `fake_pg/a10g` (5): `deepseek_v3`, `gpt_oss`, `llama3`, `muse_glimmer`, `qwen3`.
  - `real_pg/a10g` (8): the same 5, plus `deepseek_v3_cp_pp`, `gpt_oss_pp`, `llama3_pp`.
  - `real_pg/mi350x` (8): the same 8 names. These may not move: that depends on how Triton's AMD backend lowers `exp`.
- They get regenerated in this PR, from its own CI run, before landing. The labels `ciflow/fake-pg`, `ciflow/real-pg` and `ciflow/rocm` start those jobs. Each failing job prints the new values in golden-file format.
- Unchanged: `sft` and `kimi_k3_b200` (SPMD type checking turns local compile regions off), and `rl_grpo_cuda` (it uses `compute_logprobs`).
- On a GB300 (fake PG, 10 steps), Llama 3 moves from step 3, and DeepSeek-V3 from step 1's grad norm. DeepSeek-V3 on main, run twice, is bitwise equal.

You may ask:
- Why not `compute_logprobs` too? The RL loss uses trainer minus generator (vLLM) logprobs. The fast exp would change the trainer's side, and that gap was not measured. A TODO at the function says so.
- Why not `mse_loss`? It has no exp, so the option would do nothing.
- Why not skip the option for fp32 logits? That needs a second compiled function per dtype. It would avoid the larger fp32 error (1.3-1.9x main's), which the bf16 cast in Muse Glimmer's head hides.
- Why not `TORCHINDUCTOR_USE_FAST_MATH=1`? That changes every compiled region (router softmax, RL logprobs, ...). Each would need its own numerics check.
- What about a fused CE kernel? Another open PR adds one for DeepSeek-V3. It matches eager bit for bit, which this PR does not. The two touch different code paths.

**Test plan**
- The benchmark and the convergence pair above.
- `python tests/integration_tests/run_tests.py <out> --test_suite models --test_name llama3_fsdp+tp+cp --execution_mode fake_pg --ngpu 1 --export-numerics` (same for `deepseek_v3_fsdp+ep`), on main and on this branch.
- CPU unit tests can't see this change: the option only changes GPU (Triton) code.

NOTE, not run:
- Other GPUs. Numerics were measured on CUDA (GB300) only, speed too. On GPUs with slower memory the kernels may wait on memory, like the fp32 row above (not slower there).
- TP > 1 timing. Only the accuracy of the TP math was checked, at world size 1.
- The A10G and MI350X golden jobs (see above).

import torch
from torchtitan.components.loss import cross_entropy_loss

T, V = 4096, 129280
x = (torch.randn(T, V, device="cuda", dtype=torch.bfloat16) * 2).requires_grad_()
labels = torch.randint(0, V, (T,), device="cuda")
labels[torch.rand(T, device="cuda") < 0.05] = -100
for options in ({}, {"use_fast_math": True}):
    torch._dynamo.reset()
    ce = torch.compile(cross_entropy_loss.__wrapped__, fullgraph=True, options=options)
    step = lambda: torch.autograd.grad(ce(x, labels, reduction="sum"), x)
