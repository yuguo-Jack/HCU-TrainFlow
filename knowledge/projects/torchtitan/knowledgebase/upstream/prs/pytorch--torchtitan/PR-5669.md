# [rl] generator: reuse linear-attention metadata across KV-cache groups (2/7)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5669) · state: closed · merged: True

## Original PR description

**TLDR:** vLLM built the GDN metadata once per KV-cache group, every step. The builder now implements vLLM's `update_block_table`: one build, and the other groups only re-gather their state slots. Qwen3.5-9B, 256 requests: decode step -4.5%. Bitwise identical.

```text
main:     group 1: build   group 2: build                group 3: build
this PR:  group 1: build   group 2: update_block_table   group 3: update_block_table
```

**Problem**
1. Qwen3.5 has 1 attention and 3 GDN KV-cache groups. The GDN groups differ only in their block tables.
2. Each GDN group still ran `build`, every step.
3. A build costs 300-350 us of host time at 256 requests: ~1 ms per step.

**Solution**
1. `supports_update_block_table = True` makes vLLM's runner call `update_block_table` for the later groups, as for its Mamba builders.
2. The metadata keeps each request's block-table column (`state_block_column`), so the update is one `torch.gather` plus copies into this builder's captured buffers.
3. The runner tells the builder which graph the step replays. After vLLM dispatches, `TorchTitanGPUModelRunner` sets `replays_packed_graph = cudagraph_mode == FULL and not batch_descriptor.uniform` on these builders. A one-token step that replays a packed graph (padded past every decode graph) is built as PACKED, so `update_block_table` restages its query offsets like any packed step's. Eager one-token steps stay SINGLE_TOKEN.
4. "none" mode gathers from a zero column allocated once in `__init__`: slot staging 23-24 us per build vs main's column-0 copy 18-22 us (GB300).
5. Unchanged: kernels and the metadata values they read.

**Results**
Numerics: no kernel change. Greedy tokens bitwise identical in all 6 runs; GDN op bitwise in all 80 cells (this PR vs 1/7).

```text
Qwen3.5-9B-Base TP1, GB300, FULL graphs, 256 requests x 512-token prompts x 1024 new tokens, greedy
f5f3d2900 (main) vs f5f3d2900 + this diff, median of 3 interleaved runs per side
GDN metadata, host ms/step   0.90-1.04 -> 0.42   (1 build of 277 us + 2 updates of 69 us)
decode step, ms              12.73 -> 12.16      -4.5%
mixed step, ms               30.60 -> 30.88      within 2.7-4.3% run-to-run noise
```

NOTE: not run on 27B / 35B-A3B (same group layout) or on KDA, which shares this builder.

NOTE: point 3 of Solution was added after review, first as a `max_num_seqs` rule in the builder, now as the runner's choice (Driss's review). As a SINGLE_TOKEN step, groups 2 and 3 replayed the mixed-batch graph with a previous step's offsets (wrong outputs, no error). That replay needs FULL graphs at DP>1 (#5490), or #5704 at DP=1 when `max_num_seqs` isn't a capture size. Found on our Qwen3.5-35B-A3B DP 4 x EP 4 run branch, which had turned the reuse off instead.

**Test plan**
- `test_update_block_table_matches_build`: align / none x packed / single-token / padded single-token / packed-graph single-token (2 tokens; fails with the old `max_num_seqs` rule).
- `test_runner_tells_builders_the_selected_graph`: FULL packed, FULL decode, eager.
- The eager/FULL engine test (`test_gdn_cudagraph.py`) checks every replayed step's path against `batch_descriptor.uniform`.
- GB300: GDN GPU tests (graph metadata, cudagraph engine, deltanet) 38 passed, also with cold Triton / Attention Gym / inductor caches. RL CPU: 504 passed, the same 2 dapo_math failures as the base.

**Stack** (land in order): 1/7 fused gate -> 2/7 metadata reuse -> 3/7 no output memset/copy -> 4/7 decode routing -> 5/7 fused input projections -> 6/7 float32 gate parameters -> 7/7 split compiled per grad mode.

**What this PR does.** Qwen3.5 has three GDN KV-cache groups that share a `MambaSpec` and differ only in their block tables. Setting `supports_update_block_table = True` means vLLM runs `build` once per step and calls `update_block_table` for the other groups. `build` saves each request's state column in the new `state_block_column` field. `update_block_table` then re-gathers that column from its own group's block table and copies `has_initial_state` (plus the query offsets on the packed path) into its own builder's buffers, which its CUDA graphs captured.

**Example.** Two requests with `seq_lens=[16, 2]` and `block_size=8` in `"align"` mode give `state_block_column=[[1],[0]]`:
```text
group 1  block table [[1,5],[2,6]]  build              -> state_indices [5, 2, 0(null)]
group 2  block table [[3,7],[4,8]]  update_block_table -> state_indices [7, 4, 0(null)]
         (before: a full build per group, ~300 us host time each at 256 requests)
```

**I think the tradeoff is worth it. The PR adds about 46 net source lines in one builder and saves about 0.5-0.6 ms of host time per decode step (-4.5% at 256 requests), with bitwise-identical output. What it really costs is coupling to vLLM's internals, more than the line count.**

<details><summary>Breakdown</summary>

### Complexity added
`linear_attention.py`: +59/-13. Tests: +73.
- **Small, contained code.** It adds one class flag, one metadata field (`state_block_column`), `update_block_table` (~25 lines) and `_stage_state_indices` (~10 lines). `build` also uses `_stage_state_indices`, so the slot-staging code is shared rather than duplicated. Nothing outside this builder changes, and the kernels are untouched.
- **It uses an existing vLLM hook.** `supports_update_block_table` is the path vLLM's own Mamba builders use, so this isn't a new mechanism.
- **The subtle part is CUDA-graph buffer identity.** `update_block_table` must return views into *its own* builder's buffers, with the same extents `build` returns, or replay reads the wrong memory. Two things depend on this:
  - The extent is derived indirectly from `metadata.has_initial_state.shape[0]`, so `build` and `update_block_table` must keep slicing the same way. The new test checks `data_ptr` and extents, which guards this well.
  - Whether the packed path copies the query offsets depends on the execution path.

### Coupling and maintenance risk
1. **Inlined `mamba_get_block_table_tensor`.** The "align" and "none" column logic is now a local copy of vLLM's helper. If vLLM changes how it picks the column (speculative decoding, a new `mamba_cache_mode`), this copy won't follow. A cheaper way to stay in sync: store `seq_lens` in the metadata instead of `state_block_column`, and call the upstream helper in both methods. That keeps vLLM as the source of truth, at the cost of a little arithmetic per group. I haven't checked whether that helper is noticeably heavier than the single-column gather, so this needs measuring.
2. **Runner contract.** Correctness depends on two things in vLLM's runner:
   - It calls `update_block_table` only for groups with the same spec and builder type.
   - It calls `build_for_cudagraph_capture` for every group during capture.

   I couldn't check either against the pinned vLLM source. The bitwise FULL-graph results suggest both hold, but a vLLM upgrade could change them silently.
3. **Shared by KDA.** KDA uses this builder but wasn't benchmarked or run end to end, as the PR notes. The unit test covers the shared code.

### Performance
- **What it saves.** Host time for GDN metadata drops from 0.90-1.04 to 0.42 ms per step: one 277 us build plus two 69 us updates, instead of three builds.
- **Decode gains, mixed doesn't.** Decode step goes from 12.73 to 12.16 ms (-4.5%). Mixed steps show no measurable change, since GPU time dominates there and the run-to-run noise is about 3-4%.
- **How it scales.** The saving per step is roughly `(num_GDN_groups - 1) x (build - update)`. It grows with batch size, because build cost grows with request count, and with more GDN groups. It only shows up end to end when host prep is on the critical path, which is the case here because FULL graphs make GPU replay cheap. At small batch sizes, or if host prep overlaps GPU work, expect less.

### Bottom line
For about 46 lines, with no kernel or numerics change and an existing upstream hook, saving about 4.5% of decode time is a good trade. If you want to cut the maintenance risk, the change I'd consider is (1): replace the inlined column logic with calls to the upstream helper.

</details>
