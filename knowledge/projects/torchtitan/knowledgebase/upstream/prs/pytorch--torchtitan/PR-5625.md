# [optim] Handle device modules without is_initialized() in the first step sync

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5625) · state: closed · merged: True

## Original PR description

## Summary

Since #5450 the first optimizer step calls `device_module.is_initialized()` before `synchronize()`. `device_module` is whatever `torch._utils._get_available_device_type()` reports for the process, and on an Apple Silicon Mac that is `mps`. `torch.mps` has no `is_initialized` (`cuda`, `xpu`, `mtia` and `cpu` all have one), so every training run on a Mac, and the CPU trainer tests, stop at the first optimizer step with

```
AttributeError: module 'torch.mps' has no attribute 'is_initialized'
```

even when the model itself is on CPU. On main, `tests/unit_tests/cpu/components/test_invalid_loss.py` fails all four tests this way on a Mac.

The fix keeps main's guard and skips the `is_initialized()` call when the device module does not provide it. CUDA and XPU behave exactly as on main, so a model on CPU on a GPU host still never creates a device context, which is what the guard is for.

Why `torch.mps` has no `is_initialized`: MPS is not a lazily initialized backend in PyTorch. `is_device_lazy_init_supported()` in `torch/csrc/utils/device_lazy_init.h` covers CUDA, XPU, HPU, MTIA and PrivateUse1 only. The single Metal device is a function-local static created on first use in `MPSDevice::getInstance()`, and there is no primary context whose creation a guard would need to avoid, so the backend has no initialization state to report. Skipping the check for such a module is the intended behaviour, not a workaround.

An earlier revision of this PR replaced the guard with `torch.accelerator.synchronize()` and `torch.accelerator.empty_cache()`. As @tianyu-l showed on a GPU box, that initializes CUDA: the no-argument `synchronize()` resolves the current device index through `torch._C._accelerator_getDeviceIndex`, which calls `maybe_initialize_device` before the sync's own initialized check runs. That revision is gone.

## Test plan

### Why it happens
This is from reading the torch source. Nothing ran in this job because the sandbox blocked the commands that would import torch.

- When you call `torch.accelerator.synchronize()` with no argument, it calls `_get_device_index(None, optional=True)`. That falls back to `torch.accelerator.current_device_index()`, and the C++ binding behind it (`_accelerator_getDeviceIndex`) calls `maybe_initialize_device(...)`. So CUDA gets initialized *before* the "skip if not initialized" check further down ever runs. The docstring's "no op if not initialized" is true for the C++ sync itself, but not for the device index lookup in front of it.
- `torch.accelerator.empty_cache()` returns early when `_accelerator_isAllocatorInitialized()` is false. It doesn't resolve a device index, so I'd expect it to be safe. To confirm on your GPU box:
  ```bash
  python -c "import torch; torch.accelerator.empty_cache(); print(torch.cuda.is_initialized())"   # expect False
  python -c "import torch; torch.accelerator.synchronize(); print(torch.cuda.is_initialized())"   # True (this is the culprit)
  ```

### Suggested fix
Keep the PR's MPS fix, but put the guard back in front of `synchronize()`. MPS has no lazy init and no `torch.mps.is_initialized`, so treat it as always initialized. In `torchtitan/components/optim/optim.py:153-157`:

```python
if self._is_first_step_call:
    # Finish GPU work before freeing cached memory for NCCL buffers.
    # https://github.com/pytorch/torchtitan/issues/5019
    if torch.accelerator.is_available():
        # torch.accelerator.synchronize() lazily initializes devices such as
        # CUDA while resolving the current device index, so skip it when the
        # device was never initialized (e.g. model on CPU). MPS has no lazy
        # init and no is_initialized().
        is_initialized = getattr(device_module, "is_initialized", None)
        if is_initialized is None or is_initialized():
            torch.accelerator.synchronize()
        # No-op when the allocator has not been initialized.
        torch.accelerator.empty_cache()
    self._is_first_step_call = False
```

The `device_module` import has to come back too. The `getattr` here isn't a speculative check: `torch.mps` really doesn't have `is_initialized`, and that is the bug this PR fixes.

**Tests.** With the new parametrization, the uninitialized case is mocked out, which is how this slipped through. Keep a `device_initialized` axis (patch `device_module.is_initialized`) and assert that `synchronize` is **not** called when it's `False`. Add one more case where `device_module` has no `is_initialized` attribute (the MPS case) and check that sync still runs.

Before landing, run the one-liner above (with `synchronize` and `empty_cache` together) on a GPU box with this patch applied and check that it still prints `False`.

### On "why doesn't mps have `is_initialized`?"
The explanation in the PR description is right. MPS doesn't use PyTorch's lazy device init: `is_device_lazy_init_supported()` (`torch/csrc/utils/device_lazy_init.h`) covers only CUDA, XPU, HPU, MTIA and PrivateUse1. The Metal device is a function-local static singleton (`MPSDevice::getInstance()`) with no primary context to avoid creating, so there is no init state to report. Treating "no `is_initialized`" as "nothing to guard" is the right reading of the contract. Adding `torch.mps.is_initialized()` upstream would be a separate PyTorch change, and torchtitan shouldn't wait for it.
