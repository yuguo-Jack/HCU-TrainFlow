# Identify MoE blocks by their MoE child in the load-balancing hook and symm-mem scope

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5715) · state: closed · merged: True

## Original PR description

## Summary (human-written)
This is motivated by two things. 1) post 5345, MoE blocks that aren't transformerblocks (e.g. in any custom defined blocks, etc.) get missed. And 2) as a semantic change that common/moe shouldn't have to know about common/decoder necessarily, or the moe check should not have to know that the moe is part of a transformerblock. This PR fixes it by just checking any block to see if it has moe children, and I've confirmed the new tests fail without the fix.

## Why
Three places decide whether a decoder block is an MoE block, and they disagree:

- `apply_fsdp_to_decoder` reads `transformer_block.feed_forward`;
- `register_moe_load_balancing_hook` (`_iter_moe_layers`) and the `"dense"` scope of `enable_fsdp_symm_mem` read `feed_forward` too, and additionally require the block to be a `torchtitan.models.common.decoder.TransformerBlock`.

So a block that isn't a `TransformerBlock`, or that holds its `MoE` under another name, is mishandled, mostly silently. One such model is in-tree: the transformers modeling backend swaps a torchtitan `MoE` in at `layer.mlp` on HF decoder layers, and calls both `register_moe_load_balancing_hook` and `enable_fsdp_symm_mem`. Its `test_optimizer_hook_updates_expert_bias` fails without this PR, because the hook finds no MoE layers.

**Example.** Take a block, `class MyBlock(nn.Module)`, with `self.mlp = MoE(...)` and `load_balance_coeff` set:

| | on `main` | with this PR |
| --- | --- | --- |
| loss-free balancing | hook finds no MoE layers; `expert_bias` never moves | updated every step, as for `TransformerBlock` |
| `enable_fsdp_symm_mem(model, "dense")` | symm-mem also enabled on the MoE blocks | MoE blocks skipped, as for `TransformerBlock` |
| `apply_fsdp_to_decoder` | `AttributeError: ... no attribute 'feed_forward'` | sharded as an MoE block |

## What changed
All three sites now treat a block as an MoE block when one of its direct children is an `MoE`:

- `torchtitan/models/common/moe/moe.py`: `_iter_moe_layers` drops the `isinstance(transformer_block, TransformerBlock)` check and yields the block's `MoE` children.
- `torchtitan/distributed/fsdp.py`:
  - under `"dense"`, `enable_fsdp_symm_mem` skips FSDP modules that have an `MoE` child, in place of the `TransformerBlock` and `feed_forward` checks;
  - `apply_fsdp_to_decoder` takes the block's `MoE` child in place of `feed_forward`.
- Both drop the now-unused function-local `TransformerBlock` import, so `common/moe` no longer imports `common/decoder`.
- Tests, additions only:
  - `test_fsdp.py`: `_FSDPOutOfTreeBlock`, parametrized into `test_enable_fsdp_symm_mem_scope`, and `test_apply_fsdp_to_decoder_shards_an_moe_held_as_mlp`.
  - `test_optimizer_param_groups.py`: `FakeMlpMoEBlock`, and `test_moe_load_balancing_updates_a_block_with_its_moe_as_mlp`.

For every in-tree model, all three sites select the same modules as before. Built on meta, the 62 flavors under `torchtitan/models` (with an MTP layer where the flavor takes one) hold 1,131 `MoE` modules, each the only `MoE` child of a `TransformerBlock`, at `feed_forward`.

## Alternatives considered
- Keep `feed_forward` as the rule at all three sites (this PR's first commit). That leaves the transformers modeling backend's balancing broken, since its `MoE` sits at `mlp`.
- Make out-of-tree blocks subclass `TransformerBlock`. That drags in its constructor and config, and renaming a block's class or attributes to fit changes checkpoint keys for existing models.
- Leave it as is. An out-of-tree model then has to copy the hook, and the copy drifts from upstream whenever the hook changes.

## Testing
- `pytest tests/unit_tests/cpu/distributed/test_fsdp.py tests/unit_tests/cpu/components/optim/test_optimizer_param_groups.py`: 44 passed.
- Full `tests/unit_tests/cpu`, with and without this PR (base `1e30d69a3`, torch 2.15): results are identical except for 3 of the new cases, which fail without it. The same 8 failures and 11 collection errors, from this environment, occur on both.
- `torchtitan/experiments/transformers_modeling_backend/tests/test_moe_parallelism.py -k test_optimizer_hook_updates_expert_bias` (CPU, needs `transformers`): fails without this PR, passes with it.

File: `torchtitan/distributed/fsdp.py` · line 201

After this change, the same file uses two different rules to decide what counts as an MoE block. Here, and in `_iter_moe_layers`, a block is MoE if any direct child is an `MoE`. `apply_fsdp_to_decoder` (line 396 in this file) still decides with `isinstance(transformer_block.feed_forward, MoE)`.

So the `mlp`-style block in the new load-balancing test (`FakeMlpMoEBlock`) raises `AttributeError` at line 396 if it goes through `apply_fsdp_to_decoder`. A block that has a dense `feed_forward` plus an MoE stored under another name gets sharded as dense, with no expert placements and no `edp_mesh`, while this function treats it as MoE. Neither case exists in-tree today, but the stated goal of this PR is out-of-tree blocks, and that is exactly where the two rules give different answers.

Pick one rule and use it at all three sites:
- **Option A:** go back to commit 1, which checks `feed_forward` only. That matches `apply_fsdp_to_decoder` and the PR description.
- **Option B:** use the children scan in `apply_fsdp_to_decoder` too, e.g. `moe = next((m for m in transformer_block.children() if isinstance(m, MoE)), None)`. Since `apply_fsdp_to_decoder` handles only one MoE per block, it should raise if it finds more than one.

Option B goes further toward the human summary's goal of not depending on block structure.
