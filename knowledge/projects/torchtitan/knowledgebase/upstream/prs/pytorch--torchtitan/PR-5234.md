# [rl] One step-time ratio per loop phase; fwd_bwd no longer counts the optimizer

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5234) · state: open · merged: False

## Original PR description

**TLDR:** Each loop phase gets its own `perf/trainer/step_time_ratio/<phase>`, the checkpoint save becomes its own phase instead of part of `optimizer`, and consecutive `timing/step/total`s now cover the whole loop. On a 2-GPU run, a save step's `timing/step/optimizer` drops from 12.4 s to 0.02 s, the save reads as `timing/step/save_checkpoint`, and `unaccounted` stays under 0.02%.

**Problem**
1. The loop times each phase under `timing/step/<phase>`, and `compute_perf_ratio_metrics` turns them into `perf/trainer/step_time_ratio/*`.
2. `step_time_ratio/fwd_bwd` is (forward_backward + optimizer) / total, and `tokens_per_second_fwd_bwd` divides tokens by the same sum.
3. `Trainer.optim_step` also saves the checkpoint, so `timing/step/optimizer` (and "fwd_bwd") include the save.
4. On a 35B-A3B MoE run, the optimizer phase read 213-257 s on save steps, vs 0.12-0.3 s on the other steps.
5. `timing/step/total` starts after `sync_log_step` and stops before `metrics_log`, so their time belongs to no step. On a 27B run with an earlier controller, wall-clock steps were 0-6 s longer than `timing/step/total`.

**Solution**
1. One ratio per phase: `perf/trainer/step_time_ratio/<phase>` = `timing/step/<phase>` / `timing/step/total`.
2. Each ratio takes its phase's name, which renames three keys:
```text
perf/trainer/step_time_ratio/batch      -> perf/trainer/step_time_ratio/wait_for_training_batch
perf/trainer/step_time_ratio/fwd_bwd    -> perf/trainer/step_time_ratio/forward_backward
  (forward/backward + optimizer)           + perf/trainer/step_time_ratio/optimizer (new)
perf/trainer/tokens_per_second_fwd_bwd  -> perf/trainer/tokens_per_second_forward_backward
  (over forward/backward + optimizer)      (over forward/backward only)
```
3. `timing/step/total` is now the loop period: from the previous step's `metrics_log` to this step's flush. A step can't time its own log, so step `s` reports step `s-1`'s `metrics_log`:
```text
 |<--------------------------------- timing/step/total of step s --------------------------------->|
 log(s-1)  sync_log_step  wait  forward_backward  push wait  optimizer  save_checkpoint  pull wait  flush(s)  log(s) ...
```
4. New phases `sync_log_step`, `metrics_log` and `save_checkpoint`, each with a ratio.
5. The save moves from `Trainer.optim_step` (which drops `last_step`) to a new `Trainer.save_checkpoint(last_step=...)` endpoint, which the controller calls on every trainer rank right after the optimizer.
6. Unchanged: the order optimizer -> save -> pull wait -> push, the other `timing/*` keys, and the formulas of `step_time_ratio/blocking_*`, `unaccounted` and `tokens_per_second_full_step`.

**Results**
```text
Qwen3-0.6B alphabet_sort, 1 trainer H100 + 1 generator H100, 3 steps, checkpoint interval 2 (saves at steps 2 and 3).
Before: this PR's previous head merged with main. After: this update. Separate runs; save times vary with the disk.

seconds                                   before    after
step 2  timing/step/optimizer             12.37     0.019
        timing/step/save_checkpoint       -         16.07
        step_time_ratio/unaccounted       7e-5      1.1e-4
step 3  timing/step/optimizer             8.09      0.033
        timing/step/save_checkpoint       -         12.28
        step_time_ratio/unaccounted       9e-5      1.6e-4
step 1  timing/step/save_checkpoint       -         0.0016   (no save: the endpoint's own cost)
sync_log_step + metrics_log per step      no step   0.009-0.017, now inside the total
```

You may ask:
- What replaces tokens over forward/backward + optimizer? Nothing exactly. The closest is the trainer's `trainer/tokens_per_second` (per device, all tokens), timed from forward/backward start to the optimizer update: no checkpoint save, but it includes the blocking push wait.
- Why an endpoint, instead of `optim_step` returning its save time? The phases are `MetricsTimer.record` context managers, so the controller would have to subtract the save from the optimizer's recorded time afterwards. With the endpoint, each phase is one awaited call, for one extra RPC per step (1.6 ms above).

NOTE:
- Dashboards that read the three old keys need the new names. `timing/step/total` now includes the log calls, so every ratio and `tokens_per_second_full_step` shift a little; `timing/step/optimizer` no longer includes the save.
- New trace spans: `save_checkpoint` on the controller and the trainer. The checkpointer's `checkpoint_save` span now sits under the trainer's `save_checkpoint`, not `optim_step`.
- Step 1 (and the first step after a resume) has no `metrics_log` phase, so it logs no `unaccounted`.
- With async checkpointing, `engine.optim_step` first waits for the previous save's staging, so part of a save still lands in the next step's optimizer phase.
- The profiler step and the `trainer/memory/*` peak stats now run before the save, so a save's memory peak shows up in the next step.

**Test plan**
- `test_compute_perf_ratio_metrics_reads_flushed_means`: the exact output dict, so every phase ratio, `unaccounted` and both tokens/s keys, with no extras.
- `test_step_total_covers_the_save_and_the_previous_metrics_log`: a fake clock. The save is its own phase, step 2's total starts at step 1's log, and `unaccounted` is 0.
- `test_push_then_pull_then_release_after_each_optimizer_step`: the save runs after the optimizer and before the push, with `last_step=True` only on the last step.
- `test_optim_step_advances_profiler_and_reports_aux_loss_metrics`: `optim_step` no longer saves.
- The four fail without this update. `pytest tests/rl/unit_tests/cpu --durations=20` on this branch (main `f2bd97332` merged), torchmonarch 0.7.0: 480 passed, 9 skipped in 36 s; each new test takes under 10 ms.
- GPU: the 2-GPU run above (`rl_grpo_qwen3_0_6b_varlen` with trainer and generator TP 1, `num_training_steps=3`, `checkpointer.interval=2`). Saves at steps 2 and 3 (step 3 is the last step).
