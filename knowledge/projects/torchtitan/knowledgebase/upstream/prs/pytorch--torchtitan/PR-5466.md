# [overrides] Run the fused SwiGLU override on any accelerator

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5466) · state: closed · merged: True

## Original PR description

## Summary (human-written)
<!-- Write this yourself, not with an AI tool. 2-5 sentences: the problem, why
     this approach, and what you checked yourself. -->

This PR generalizes fused_swiglu overrides across accelerator devices ( including cuda).  The overrides kernels are in Triton,  hence has no cuda dependency,   Visually checked  source diffs and manually ran the tests. 

## Why
The DSv3 and Muse Spark recipes enable the bundled `fused_swiglu` override by default. Its two custom ops are registered with `device_types="cuda"`, so on any other accelerator the first forward fails, even though the kernels are plain Triton and compile for other backends.

**Example.**
```
# Intel PVC (XPU), Muse Spark or DSv3 recipe, fused_swiglu on by default
main: first forward -> NotImplementedError: The operator 'torchtitan::silu_and_mul'
      is not currently implemented for the XPU device.
PR:   the op registers for "xpu" and runs.

# Unit tests on XPU
main: 10 passed, 7 skipped ("silu_and_mul op is CUDA-only" / "CUDA required")
PR:   17 passed
```

## What changed
- `torchtitan_recipes/overrides/fused_swiglu.py`: register `torchtitan::silu_and_mul` and its backward for `torchtitan.tools.utils.device_type`, the accelerator core torchtitan already uses for device selection. It falls back to `"cuda"` when no accelerator is present, so CUDA and CPU-only hosts behave as before. The kernels themselves are unchanged.
- `tests/unit_tests/gpu/recipes/test_fused_swiglu.py`, `test_fused_swiglu_override.py`: put tensors on the `torch.accelerator` device instead of `cuda`, and gate the tests on the device type the ops register for. They now run on non-CUDA accelerators, and they skip instead of failing where `torch.accelerator` and `device_type` disagree (e.g. MPS, or an XPU host with no visible tile).

## Alternatives considered
- Drop the override on non-CUDA in the recipes: gives up the fused kernel, which on XPU is up to about 2x faster than the `fused_binary_activation` local compile region (comparison in the PR discussion).
- Register for an explicit list such as `("cuda", "xpu")`: duplicates the accelerator detection core already does, and needs editing for each new backend.

## Numerics
No computation change: the same Triton kernels run, only the device the ops are registered for changes.

## Testing
On Intel PVC (torch 2.16 dev `+xpu`, triton-xpu 3.9):
```
python -m pytest tests/unit_tests/gpu/recipes/test_fused_swiglu.py \
    tests/unit_tests/gpu/recipes/test_fused_swiglu_override.py
17 passed
```
With no XPU tile visible (`ZE_AFFINITY_MASK=99`), `device_type` falls back to `cuda` and the same command gives 10 passed and 7 skipped. That's the mismatch case the new gating handles.

## Known issues / follow-ups
- The change that makes the kernels' row count a runtime argument, which avoids a recompile for every new routed-token count under expert parallelism, has moved to its own PR: #5717.
- Other overrides that still register for `"cuda"` only: `fused_mla`, `higher_precision_rms_norm`, `kimi_attention_residual`. None is enabled by default; they are left for follow-ups.

Overall this looks good. I didn't find any correctness bugs. The motivation is real: `device_types="cuda"` on Triton/Helion code was more restrictive than it needed to be, and the `is_cuda` gate in `helion_rope` silently fell back to the PyTorch path off CUDA while still reporting the override as applied. Most of what follows is about verification, plus a few small nits.

### Correctness checks (no action needed)

- **int64 address arithmetic still holds after dropping `constexpr`.** Now that strides are runtime args, Triton types any stride that fits in 32 bits as `i32`, so overflow was the main thing to rule out. `row_start = tl.program_id(0).to(tl.int64) * BLOCK_M` (`fused_swiglu.py:64`, `:119`) makes `rows` int64, so `rows[:, None] * *_ROW_STRIDE` is promoted to int64 even when the stride is `i32`. The column terms use `i32` but are bounded by `NUM_COLS * col_stride`, which is small. `test_silu_and_mul_uses_int64_row_stride_arithmetic` (stride 8192, row offset past 2^31) covers exactly this case, so passing it on XPU is good evidence.
- **`row_limit` typing.** `row_limit = NUM_ROWS` followed by `row_limit = tl.load(...)` inside `if HAS_OFFSETS:` is fine because `HAS_OFFSETS` is still `constexpr`, so the branch is resolved at compile time.
- **The `_complex_eligible` rewrite** (`helion_rope.py:435`) is equivalent to the old four `is_cuda` checks. `xq.device.type == device_type` together with the chained `xq.device == xk.device == ...` implies that all four tensors are on the accelerator. On a CPU-only host `device_type` falls back to `"cuda"`, so CPU inputs are still ineligible and take the fallback as before.
- **Recompile fix.** Treating `NUM_ROWS` as `constexpr` really did force a recompile for every distinct routed-token count, on CUDA too. Making it and the strides runtime args is the right call. Specialization on `==1` and `%16` keeps the `COL_STRIDE == 1` fast path.

### Suggestions

1. **Show CUDA numerics and perf for the `constexpr` change.** This is the part of the PR that changes behaviour on the battle-tested CUDA path, and the test plan only covers XPU. Per CLAUDE.md ("Protect battle-tested code paths", "Show numerical proof"), please add:
   - A CUDA run of the three test files.
   - A short before/after microbenchmark of `silu_and_mul_forward_kernel` / `_backward_kernel` on CUDA at a representative MoE shape. Losing constant strides can change vectorization or index math. I expect any difference to be in the noise, and a real win once compile time is counted, but it's worth showing.
   - Ideally a 10-step DSv3 or Muse Spark debug run with `seed=42` / `deterministic=True` showing bit-identical loss and grad_norm on CUDA. The math is unchanged, so this should be trivially identical.

2. **Helion configs are tuned for GB200.** `_complex_fwd_config` / `_complex_bwd_config` (`helion_rope.py:220-274`) hard-code configs from a GB200 search: `num_warps=2`, `l2_groupings`, and `load_eviction_policies` of `first`/`last`. Off CUDA these compile, but they may perform worse than the PyTorch fallback. Please either add an XPU fused-vs-fallback timing to the PR description, or add a `# TODO` noting that these configs are CUDA-tuned. Otherwise, enabling the override by default on non-CUDA could end up a perf regression rather than a win.

3. **The tests and the op registration detect the device differently.** The ops register for `torchtitan.tools.utils.device_type`, which comes from `torch._utils._get_available_device_type()` and checks cuda/xpu/mtia/privateuse1 with a fallback to `"cuda"`. The tests gate on `torch.accelerator.is_available()` / `current_accelerator()`, which also covers backends such as MPS. On a host where the two disagree, for example an Apple Silicon dev box, the tests would now run and fail with `NotImplementedError` where they used to skip. A simple way to keep them consistent is to use the same source in the tests, e.g. `from torchtitan.tools.utils import device_type` and skip unless `torch.accelerator.current_accelerator()` has `.type == device_type`. Low priority, since CI has no MPS runners.

Max error against an fp32 reference is the same for both paths (bf16 rounding). On XPU the fused op is about 2x faster at small MoE shapes and 25-35% faster when there are padded rows. - this PR: two compiles (Triton's divisibility-by-16 specialization), then 0.1 ms for every new row count
