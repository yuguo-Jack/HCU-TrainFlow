# [MoE][perf] Cache the EP submesh in BaseEPTokenDispatcher.ep_mesh

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5323) · state: open · merged: False

## Original PR description

#4810 made `BaseEPTokenDispatcher.ep_mesh` a property that slices `spmd_sparse_mesh()["ep"]` on every read, and `DeviceMesh.__getitem__` builds a new submesh each time, about 380 us of CPU. DeepSeek-V3 16B with EP=8 reads it 370-420 times per step, so each step spends 140-160 ms of CPU on slicing, which shows up as GPU idle and longer NCCL waits: throughput drops 7-8% on 2x4 GB200.

This caches the submesh on the dispatcher, keyed on the identity of the sparse mesh it was sliced from, so a newly registered sparse mesh still gets a fresh slice.

## Test plan

`test_ep_mesh_is_sliced_once_per_sparse_mesh` fails on main and passes with this change. Measured on 2x4 GB200 with DeepSeek-V3 16B, EP=8, eager: on main the cache brings throughput from 12,970 to 14,050 tps (+8.3%) and slicing time from 160.6 ms to 0.5 ms per step. The loss comparison with `debug.seed = 42` and `debug.deterministic = True` is still to come (and it's still a draft)

### Review: [MoE][perf] Cache the EP submesh in `BaseEPTokenDispatcher.ep_mesh`

- [x] Gather context (diff, callsites)

**Verdict:** I found no correctness problems. The change is small, keeps the old behavior, and fixes a real regression from #4810. The notes below are suggestions; none of them blocks merging.

### Correctness

- **The cache key holds up.** `spmd_sparse_mesh()` returns `ParallelismContext._global_meshes["spmd_sparse_for_fwdbwd"]` (`torchtitan/distributed/parallelism_context.py:345`). That object is built once in `build_mesh()` and then handed to `set_spmd_meshes` on every `activate_spmd()`. Since the same object comes back each time, checking `is` on it hits the cache every time. If a different mesh is registered, the slice is rebuilt, which the new test covers.
- **EP=1 behaves as before.** When the sparse mesh is `None`, the property still returns `None` and never reads or writes the cache, so a stale submesh can't leak into a non-EP run.
- **Moving `spmd_sparse_mesh()` outside `spmd.no_typecheck()` is fine.** It's just a `getattr` on thread-local storage (`spmd_types.py:86-88`). Only the `mesh["ep"]` slice needs the no-typecheck context, and it still has it.
- **On the `cached_property` thread:** I agree with keeping the current version. With `cached_property`, an early read that returns `None` would turn off EP for good with no error. The current version can't fail that way, and the cost is about 60 ns per read.
- **PP `split_module` deepcopy (`pipeline_parallel.py:613`):** this runs before any forward pass, so the cache is still `None` when the model is copied. Even if a copy did carry a cached submesh, its `_ep_mesh_parent` wouldn't be the live TLS mesh, so it would just slice again. I don't see a problem here.

### Suggestions

1. **Optional: cache at the source instead.** `ParallelismContext` already builds a one-axis EP mesh once: `_single_axis_meshes["ep"] = full_sparse_mesh["ep"]` (`parallelism_context.py:368`). If `set_spmd_meshes` also stored the EP mesh in `_MESH_TLS` (for example behind a `spmd_ep_mesh()` getter in `torchtitan/distributed/spmd_types.py`), the property would become a plain TLS lookup:
   - no mutable cache on each module;
   - other places that slice every time would also benefit, e.g. `decoder.py:199` (`sparse_mesh["ep"].size()`);
   - this matches the "model-agnostic parallelism helpers live in `torchtitan/distributed/`" guidance.

   The cost is changing every `set_spmd_meshes` callsite (tests, `graph_trainer/precompile.py`). It's also worth checking that `full_sparse_mesh["ep"]` and `spmd_sparse_for_fwdbwd["ep"]` give the same group (they should, since both slice the same `ep` axis). Since this PR fixes a regression, landing it as is and doing this as a follow-up seems fine.

2. **Nit: update the cache in one assignment.** `_ep_mesh` and `_ep_mesh_parent` are set separately and the property returns `self._ep_mesh`. If two threads ever saw different sparse meshes, one could get the other's submesh. That doesn't happen today (all reads are on the main thread, as your instrumentation shows), but one tuple removes the window and saves an attribute:
   ```python
   self._ep_mesh_cache: tuple[DeviceMesh, DeviceMesh] | None = None
   ...
   cache = self._ep_mesh_cache
   if cache is None or cache[0] is not mesh:
       with spmd.no_typecheck():
           # weirdly, accessing ep PG hits DeviceMesh internals that expects type annotations
           cache = (mesh, mesh["ep"])
       self._ep_mesh_cache = cache
   return cache[1]
   ```
   [Fix this →](https://claude.ai/code?q=In%20torchtitan%2Fmodels%2Fcommon%2Ftoken_dispatcher.py%20on%20branch%20lonyshchenko%2Fep-mesh-cache%2C%20replace%20the%20two%20cache%20attributes%20_ep_mesh%20and%20_ep_mesh_parent%20in%20BaseEPTokenDispatcher%20with%20a%20single%20_ep_mesh_cache%3A%20tuple%5BDeviceMesh%2C%20DeviceMesh%5D%20%7C%20None%20(parent%2C%20ep_submesh)%20that%20is%20assigned%20atomically%20and%20returned%20from%20a%20local%20variable%20in%20the%20ep_mesh%20property.&repo=pytorch/torchtitan)

3. **Nit: the comment.** `# mesh["ep"] builds a new DeviceMesh on every call, about 0.4 ms of CPU each.` The exact timing will go stale as `DeviceMesh` changes. Something like `# DeviceMesh.__getitem__ builds a new submesh on every call, and ep_mesh is read hundreds of times per step.` explains the reason and will stay accurate.

4. **Test.** The test checks both identity on repeated reads and a fresh slice after a new mesh is registered, and its cleanup is correct. Two small things:
   - The name says "sliced once", but the test checks object identity. Patching `DeviceMesh.__getitem__` with `wraps=` and asserting `call_count == 1` would test exactly what the name claims and catch a cache that rebuilds and happens to return an equal object.
   - Adding `self.assertIsNone(dispatcher.ep_mesh)` before the first `set_spmd_meshes` would also cover the "read before EP is set up" case you described in the `cached_property` reply.

### Validation

- The throughput numbers and the bit-identical loss/grad_norm at seed 42 with `deterministic=True` (EP=4) cover what CLAUDE.md asks for on a non-computation change.
- The runs were eager only. The `ciflow/rl` and `ciflow/fake-pg` jobs (once approved) should show whether a compiled / graph_trainer path that reads `ep_mesh` inside traced code handles the attribute write in the property. I expect it to, since core compiles only `local_compile` functions and not the dispatcher module.

I'd keep the current version rather than switch to `cached_property`. both are equally fast, but with `cached_property` the first read decides the value for good. if anything ever reads `ep_mesh` before `activate_spmd()` sets up the EP mesh, it would cache `None`, and the MoE layers would quietly run without expert parallelism. nothing reads it that early today, but caching per parent mesh rules this out at no extra cost.
