# [MoE][perf] Avoid repeated EP submesh construction

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5323) · state: closed · merged: True

## Original PR description

#4810 made `BaseEPTokenDispatcher.ep_mesh` slice `spmd_sparse_mesh()["ep"]` on every read, and `DeviceMesh.__getitem__` builds a new submesh each time. DeepSeek-V3 16B with EP=8 reads it hundreds of times per step, spending tens to hundreds of milliseconds of CPU per step on mesh slicing while GPU compute stays unchanged.

This removes `ep_mesh` and resolves the existing EP process group through `spmd_mesh_group(MeshAxisName.EP)`, avoiding submesh construction and mutable cache state on every dispatcher module.

## Test plan

- `python -m pytest -q tests/unit_tests/cpu/distributed/test_expert_parallel.py tests/unit_tests/cpu/models/common/test_moe.py`: 36 passed.
- On 2x4 GB200 with DeepSeek-V3 16B and EP=8, the process-group version is within 0.15% of the cached version and 6.2% faster than uncached `main`.
- A deterministic 50-step cache/process-group A/B finished with final loss 5.861 / 5.864. The trajectories were close but not bit-identical.

<details>
<summary>Performance measurements</summary>

DeepSeek-V3 16B, bf16, EP=8, local batch 4, sequence length 4096, forced expert load balance, eager, 2 nodes x 4 GB200.

| implementation | tokens/s, run 1 | tokens/s, run 2 | mean |
|---|---:|---:|---:|
| uncached `main` | 19,388 | 19,389 | 19,388 |
| cached submesh | 20,617 | 20,619 | 20,618 |
| EP process group | 20,579 | 20,596 | 20,588 |

Rank-0 instrumentation records 12,999 `DeviceMesh.__getitem__` calls from `ep_mesh` over 50 steps on uncached `main`, totaling 2.99 seconds. The process-group implementation makes no `DeviceMesh` slices from the token dispatcher. All three arms used the same image, recipe, node pair, and source base.

An independent 2x4 GB200 validation, pinned to the same software base for both arms, measured 19,578 tokens/s without the change and 21,397 with the process-group implementation (+9.3%). The scheduler placed the arms on different node pairs.

</details>

### Review: [MoE][perf] Cache the EP submesh in `BaseEPTokenDispatcher.ep_mesh`

- [x] Gather context (diff, callsites)
- [x] Review the caching logic and the test
- [x] Post review

**Verdict:** I found no correctness problems. The change is small, keeps the old behavior, and fixes a real regression from #4810. The notes below are suggestions; none of them blocks merging.

### Correctness

- **The cache key holds up.** `spmd_sparse_mesh()` returns `ParallelismContext._global_meshes["spmd_sparse_for_fwdbwd"]` (`torchtitan/distributed/parallelism_context.py:345`). That object is built once in `build_mesh()` and then handed to `set_spmd_meshes` on every `activate_spmd()`. Since the same object comes back each time, checking `is` on it hits the cache every time. If a different mesh is registered, the slice is rebuilt, which the new test covers.
- **EP=1 behaves as before.** When the sparse mesh is `None`, the property still returns `None` and never reads or writes the cache, so a stale submesh can't leak into a non-EP run.
- **Moving `spmd_sparse_mesh()` outside `spmd.no_typecheck()` is fine.** It's just a `getattr` on thread-local storage (`spmd_types.py:86-88`). Only the `mesh["ep"]` slice needs the no-typecheck context, and it still has it.
- **On the `cached_property` thread:** I agree with keeping the current version. With `cached_property`, an early read that returns `None` would turn off EP for good with no error. The current version can't fail that way, and the cost is about 60 ns per read.
- **PP `split_module` deepcopy (`pipeline_parallel.py:613`):** this runs before any forward pass, so the cache is still `None` when the model is copied. Even if a copy did carry a cached submesh, its `_ep_mesh_parent` wouldn't be the live TLS mesh, so it would just slice again. I don't see a problem here.

### Suggestions

1. **Optional: cache at the source instead.** `ParallelismContext` already builds a one-axis EP mesh once: `_single_axis_meshes["ep"] = full_sparse_mesh["ep"]` (`parallelism_context.py:368`). If `set_spmd_meshes` also stored the EP mesh in `_MESH_TLS` (for example behind a `spmd_ep_mesh()` getter in `torchtitan/distributed/spmd_types.py`), the property would become a plain TLS lookup:
   - no mutable cache on each module;
   - other places that slice every time would also benefit, e.g. `decoder.py:199` (`sparse_mesh["ep"].size()`);
   - this matches the "model-agnostic parallelism helpers live in `torchtitan/distributed/`" guidance.

   The cost is changing every `set_spmd_meshes` callsite (tests, `graph_trainer/precompile.py`). It's also worth checking that `full_sparse_mesh["ep"]` and `spmd_sparse_for_fwdbwd["ep"]` give the same group (they should, since both slice the same `ep` axis). Since this PR fixes a regression, landing it as is and doing this as a follow-up seems fine.

2. **Nit: update the cache in one assignment.** `_ep_mesh` and `_ep_mesh_parent` are set separately and the property returns `self._ep_mesh`. If two threads ever saw different sparse meshes, one could get the other's submesh. That doesn't happen today (all reads are on the main thread, as your instrumentation shows), but one tuple removes the window and saves an attribute:
   ```python
   self._ep_mesh_cache: tuple[DeviceMesh, DeviceMesh] | None = None
   ...
   cache = self._ep_mesh_cache
   if cache is None or cache[0] is not mesh:
       with spmd.no_typecheck():
           # weirdly, accessing ep PG hits DeviceMesh internals that expects type annotations
           cache = (mesh, mesh["ep"])
       self._ep_mesh_cache = cache
   return cache[1]
   ```
   [Fix this →](https://claude.ai/code?q=In%20torchtitan%2Fmodels%2Fcommon%2Ftoken_dispatcher.py%20on%20branch%20lonyshchenko%2Fep-mesh-cache%2C%20replace%20the%20two%20cache%20attributes%20_ep_mesh%20and%20_ep_mesh_parent%20in%20BaseEPTokenDispatcher%20with%20a%20single%20_ep_mesh_cache%3A%20tuple%5BDeviceMesh%2C%20DeviceMesh%5D%20%7C%20None%20(parent%2C%20ep_submesh)%20that%20is%20assigned%20atomically%20and%20returned%20from%20a%20local%20variable%20in%20the%20ep_mesh%20property.&repo=pytorch/torchtitan)

3. **Nit: the comment.** `# mesh["ep"] builds a new DeviceMesh on every call, about 0.4 ms of CPU each.` The exact timing will go stale as `DeviceMesh` changes. Something like `# DeviceMesh.__getitem__ builds a new submesh on every call, and ep_mesh is read hundreds of times per step.` explains the reason and will stay accurate.

4. **Test.** The test checks both identity on repeated reads and a fresh slice after a new mesh is registered, and its cleanup is correct. Two small things:
   - The name says "sliced once", but the test checks object identity. Patching `DeviceMesh.__getitem__` with `wraps=` and asserting `call_count == 1` would test exactly what the name claims and catch a cache that rebuilds and happens to return an equal object.
   - Adding `self.assertIsNone(dispatcher.ep_mesh)` before the first `set_spmd_meshes` would also cover the "read before EP is set up" case you described in the `cached_property` reply.

### Validation

- The throughput numbers and the bit-identical loss/grad_norm at seed 42 with `deterministic=True` (EP=4) cover what CLAUDE.md asks for on a non-computation change.

- [x] Read the diff (`git diff origin/main...HEAD`)

**Verdict:** The change looks correct, and it's a clear improvement over the cached-submesh version. I found no blocking correctness problems. The one thing I'd still like settled before merge is why the A/B loss is not bit-identical (item 1).

### Correctness

- **The process group is the same one as before.** `_ep_process_group()` enters the registered sparse mesh and calls `spmd_mesh_group("ep")`, which returns `mesh.get_group("ep")` (`torchtitan/distributed/spmd_types.py:118-127`). That is the same PG that `mesh["ep"].get_group()` returned, but without building a submesh. Passing a PG into `spmd.all_to_all` and into the functional `all_to_all_single` matches how `linear.py:272-281` already works with `tp_group`.
- **The EP=1 fallback still behaves the same.** `spmd_mesh_group` also returns `None` when the group size is 1, which the old `ep_mesh` did not. That case can't happen here, because `spmd_sparse_for_fwdbwd` is only registered when `self.ep > 1` (`parallelism_context.py:344`). So "sparse mesh present" and "EP group exists" mean the same thing.
- **`_permute` gets `ep_size` passed in explicitly.** Both overrides (`token_dispatcher.py:517`, `:751`) and both callers were updated, as was the CPU test. The TorchAO EP=1 path now passes `ep_size=1` instead of computing it from `self.ep_mesh`, which is simpler. No other subclass overrides `_permute` (I checked `experiments/` too).
- **Nothing else used `ep_mesh`.** No references to `.ep_mesh` remain in the repo. The graph_trainer annotations (`common_utils.py:412-423`) wrap the exchange helpers by name and never relied on the parameter name, so the `pg` -> `ep_group` rename is safe.

### Items

1. **The loss isn't bit-identical, and the cause isn't explained yet.** CLAUDE.md asks that a non-computation change give identical loss with `seed=42, deterministic=True`. The earlier cache-vs-`main` A/B at EP=4 was bit-identical. The PG-vs-cache A/B at EP=8 on 2x4 ended at 5.861 / 5.864. Nothing in this diff should change numerics: same PG, same splits, same ops. My guess is the 2-node EP=8 setup itself isn't run-to-run deterministic (inter-node a2a or the scheduler's node placement), not this change. Either of these would settle it:
   - run the same arm twice at 2x4 EP=8 to measure the noise floor, or
   - repeat the PG-vs-cache (or PG-vs-`main`) A/B on 1x4 EP=4, where you already showed bit-identical results.

2. **Nit: the assert message is stale.** `token_dispatcher.py:895` and `:1029` say "ExpertParallel._partition_fn() should set it." `_partition_fn` doesn't exist anymore. The sparse mesh is registered by `ParallelismContext.activate_spmd()` -> `set_spmd_meshes`. This PR rewrites those lines, so it's a good time to fix them, e.g. `"EP process group is not set; ParallelismContext.activate_spmd() registers the sparse mesh."`
   [Fix this ->](https://claude.ai/code?q=In%20torchtitan%2Fmodels%2Fcommon%2Fmoe%2Ftoken_dispatcher.py%20on%20branch%20lonyshchenko%2Fep-mesh-cache%2C%20update%20the%20two%20assert%20messages%20in%20DeepEPTokenDispatcher.dispatch%20and%20HybridEPTokenDispatcher.dispatch%20that%20reference%20the%20non-existent%20ExpertParallel._partition_fn()%20to%20say%20the%20EP%20process%20group%20is%20registered%20by%20ParallelismContext.activate_spmd()%20via%20set_spmd_meshes.&repo=pytorch/torchtitan)

3. **Nit: Unicode in a rewritten docstring.** `token_dispatcher.py:366`, "When the EP process group is absent (EP=1), falls back to local dispatch — no", is a rewritten line that still has the em dash. CLAUDE.md asks for ASCII (`--`) in rewritten docstrings.

4. **Optional: `ep_size` is redundant in `_token_count_exchange`.** It now receives `ep_group`, so it could use `ep_group.size()` itself. `_sync_token_count_exchange` and `_permute` still need `ep_size` as a parameter, so leaving it as is for consistency is also fine.

5. **Optional: where `_ep_process_group()` lives.** It's a model-agnostic "PG for an axis of the sparse mesh" helper. If another module needs it later, it belongs in `torchtitan/distributed/spmd_types.py` (e.g. `spmd_sparse_mesh_group(axis_name)`). For a single user, keeping it private here is fine.

- The throughput numbers (+6.2% same node pair, +9.3% independent run) and the zero `DeviceMesh.__getitem__` calls from the dispatcher support the change well.
- I didn't run the unit tests in this job: chained Bash commands need approval here. The PR reports 36 passing CPU tests. `ciflow/fake-pg` and `ciflow/rl` should cover the compile/graph_trainer path that now passes a PG into `all_to_all_single`.

I'd keep the current version rather than switch to `cached_property`. both are equally fast, but with `cached_property` the first read decides the value for good. if anything ever reads `ep_mesh` before `activate_spmd()` sets up the EP mesh, it would cache `None`, and the MoE layers would quietly run without expert parallelism. nothing reads it that early today, but caching per parent mesh rules this out at no extra cost.
