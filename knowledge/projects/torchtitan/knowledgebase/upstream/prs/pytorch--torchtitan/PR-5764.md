## Agent details

**TLDR:** With streamed microbatches, a queued `forward_backward` call now starts its RDMA reads while the previous call waits for the GPU. In a CPU model with dapo_math-like timings, the exposed read time over 6 calls drops from 0.902 s to 0.150 s. End to end the gain is small, an estimated 0.15-0.3 s of a ~97 s dapo_math step, because most calls already run while the trainer waits for generation.

**Numerics:** no change. The engine gets the same calls in the same order. Only the host's wait for the GPU moved.

```text
before:   call k     | launch | GPU wait, event loop blocked |
          call k+1                                           | read 0 (GPU idle) | launch | GPU wait |
this PR:  call k     | launch | GPU wait, event loop free    |
          call k+1            | read 0, read 1               | launch | GPU wait |
```

```python
prefetcher = RDMAMicrobatchPrefetcher(microbatches)  # before: reads start when the engine iterates it
                                                     # now: the first 2 reads start here
async with self._forward_backward_lock:  # new: first in, first out
    result = engine.forward_backward(microbatch_groups=prefetcher)
    await asyncio.to_thread(torch.accelerator.current_stream(engine.device).synchronize)  # new
```

**Problem**
1. With `stream_microbatches`, the controller sends call k+1 while call k runs.
2. Monarch starts queued calls in order. But `Trainer.forward_backward` never awaited, so call k+1's body started only after call k returned.
3. The prefetcher started its reads when the engine first iterated it. So every call's first read was exposed, and the GPU sat idle during it.
4. Cost: ~0.15 s per call for an 82 MB microbatch over TCP (0.5-0.65 GB/s per rank, 4 ranks reading at once).

**Solution**
1. `RDMAMicrobatchPrefetcher` submits its first 2 reads in `__init__`. The new `close()` cancels the reads not started yet, also for a prefetcher that was never iterated.
2. `Trainer.forward_backward` checks the RDMA identities and makes its prefetchers on arrival. Then it takes a first-in, first-out `asyncio.Lock` around the engine calls and the metric collectives.
3. Inside the lock, it waits for the GPU in `asyncio.to_thread`. During that wait, a queued call starts its reads.
4. Busy time (`trainer/tokens_per_second`, TFLOPS, MFU) starts after the lock is taken, so a queued call doesn't count the running call's GPU wait.
5. Unchanged: the engine runs the same calls in the same order.

Most of `trainer.py`'s diff (+88/-66) is re-indentation. With whitespace hidden it is +48/-26.

**Results**

```text
Numerics: no change. The engine gets the same calls in the same order.

CPU model of both behaviors: a real Monarch actor with a fake read and a fake GPU (a 1-thread executor).
Per call: one 0.15 s read, then 3 groups x 0.5 s of GPU, with a host sync between groups. 2 calls in flight, 6 calls.
                            before     this PR
exposed read, 6 calls       0.902 s    0.150 s (call 0 only)
wall time                   10.27 s    9.52 s   (GPU work alone: 9.36 s)
```
- The timings follow dapo_math (Qwen3-4B-Base, 1 GB300 trainer): 505-578 ms of forward/backward per microbatch, vs ~0.15 s per read.
- End to end, only the 1-2 calls after the step's last group add wall time: 0.15-0.3 s per step. This is an estimate, not a measurement.

```text
RL run at the top of this stack: Qwen3-0.6B, 2 GPUs (trainer + generator), streaming + RDMA + lazy preprocessing
+ accelerator graphs + compile, 5 steps, 3-7 calls per step. Time each call waits for its next microbatch:
  each step's first call   37.8 ms mean over 5 calls (155 ms in step 1, 1-13 ms in steps 2-5)
  later calls              1.2 ms mean, 4.2 ms max, over 24 calls
```
- [W&B](https://meta.wandb.io/felipemello/titan_rl/runs/rih5hzpa). Later calls' reads are hidden. Each step's first read is still exposed (NOTE). There is no before column: no run without this PR used this setup.

You may ask:
- Why the lock? Without it, call k+1 would launch its engine work during call k's GPU wait. Ranks could then issue the metric collectives in different orders and hang.
- Why not run the engine on its own thread? It would hide reads that take longer than a microbatch's GPU time. But every engine or CUDA endpoint would then have to run on that thread, because FSDP2 swaps unsharded parameters into the modules during forward. On dapo_math the GPU time (505-578 ms) is far above the read (~0.15 s).

NOTE:
- Still exposed: each step's first call's first read. The controller sends that call only after `optim_step` returns (existing TODO in `controller.py`).
- The read leaks when a microbatch's GPU time is below its read time. Same CPU model with 0.15 s of GPU per group and a 0.2 s read: 0.449 s exposed over 6 calls, vs 0.200 s for call 0 alone.
- Host memory: with 2 calls in flight, a rank holds up to 6 microbatches instead of 4 (~0.5 GB at 82 MB each).
- A split first call (graphs with HSDP or deferred reduction) makes both prefetchers on arrival, so their first reads share the link. No recipe uses that combination today.
- `push_model_state_dict` can now start during a call's GPU wait. It issues no collectives and copies on its own stream.
- The trainer's `forward_backward` trace span now includes a queued call's wait for the lock. The engine's span inside it marks the work.

**Verdict: Approve -- please address the items below before merging.** The design is the smallest one that hides a streamed call's first read. To start its reads early, a queued call has to run while the previous call waits, so the previous call must yield (the `to_thread` sync). The lock then keeps the metric collectives in the same order on every rank. I found no correctness bug. This touches the RL trainer's core call path, so a maintainer still needs to review it.

**What this PR does.** `RDMAMicrobatchPrefetcher` now submits its first 2 reads in `__init__`, and a new `close()` cancels the queued reads. `Trainer.forward_backward` checks the RDMA identities and builds its prefetchers before taking a FIFO `asyncio.Lock`. Inside the lock it runs the engine calls, then waits for the GPU with `asyncio.to_thread(stream.synchronize)`, then reduces the metrics. While call k waits for the GPU, queued call k+1 runs up to the lock, so its first reads overlap call k's GPU work.

**Example.** Streamed step, 2 calls in flight, one RDMA microbatch per group:
```text
before: call 0  engine launch | sync inside dist_sum (loop blocked) | return
        call 1                                                       | read 0 (GPU idle) | engine ...
after:  call 0  engine launch | to_thread(sync), loop free | metrics | return
        call 1                | check ids, read 0 + read 1 | wait for lock -> engine (read 0 already done)
```

<details><summary>Details</summary>

- **Gate.** The problem is real on the base branch: `forward_backward` never awaited, so a queued call started only after the previous call returned, and its first read was always exposed. The measured end-to-end gain on dapo_math is small (0.15-0.3 s of ~97 s). The gain grows when the trainer, not generation, is the bottleneck: each call's first read (~0.15 s) is then exposed. The cost is +48/-26 lines of logic plus one new concurrency invariant (first inline comment).
- **Collective order.** Every collective in `forward_backward` (FSDP inside the engine, `dist_sum`/`dist_max` in the metric reduction) runs while the lock is held. Python 3.12's `asyncio.Lock` doesn't let a new caller take the lock ahead of queued waiters, and Monarch starts queued calls in send order. So every rank issues them in the same order.
- **Push during the GPU wait.** The staging stream's dependency on the optimizer is recorded in `optim_step` (`_mark_model_state_dict_ready_for_staging`), not when the push starts. `stream_context` doesn't stay entered across an `await`. A push that starts during the wait therefore neither waits for call N+1's kernels nor redirects them. The FSDP host state during the wait is the same as between calls, which was already allowed. The PR's claim holds.
- **Busy time.** `forward_backward_start` moved inside the lock, so a queued call doesn't count the running call's GPU wait. The new explicit sync replaces the implicit one in the first `dist_sum(...)` on last-stage ranks, so the measured interval covers the same work.
- **Error path.** `close()` is idempotent (`shutdown` twice is fine). On a failed call, the trainer's `finally` blocks the event loop until the running read finishes; the iterator already did this before the PR. A queued call still runs after a failed one, also as before.
- **Tests.** Both new tests guard real invariants: a queued call reads during the GPU wait, and `close()` cancels the queued reads of a prefetcher that was never iterated. The edits to the existing tests are mechanical: lock attributes, the `current_stream` patch, and recording groups in `side_effect`, because a closed prefetcher can't be iterated again.

</details>

Not verified: GPU behavior of `Stream.synchronize` from a worker thread, and the CPU-device question above.

File: `torchtitan/rl/trainer/trainer.py` · line 354

Before this PR, `forward_backward` never yielded, so no other trainer endpoint could run in the middle of a call. Now every `@concurrent_endpoint` (`optim_step`, `push_model_state_dict`, `sync_log_step`, `close`, ...) can run during the `to_thread` GPU wait. The lock only orders `forward_backward` calls against each other. Today `optim_step` is safe only because the controller exits its `TaskGroup` (`controller.py:1146`) before sending it. Nothing in the trainer enforces that. A future controller change that sends `optim_step` early would step the optimizer on partial gradients and issue its grad-norm collectives in the middle of the metric collectives.

Smallest fix: wrap the body of `optim_step` in `async with self._forward_backward_lock:` (one line plus re-indent; the lock is uncontended today). Then "optimizer after every queued forward_backward" is an invariant the trainer owns. If you'd rather keep relying on the controller, the docstring here or in `system.py` should at least list which endpoints may run during the GPU wait.

- claude[bot] · comment · 2026-11-03T06:40:07Z · [source](https://github.com/pytorch/torchtitan/pull/5764#discussion_r4451621657)

File: `torchtitan/rl/trainer/trainer.py` · line 328

The conclusion is right, but the reason given is indirect. It also depends on event-loop scheduling: after call k-2 releases the lock, call k-1's waiter has been woken but has not yet run. The direct reason is simpler. The step's first call arrives after `optim_step` returns, so it takes an uncontended lock, and `asyncio.Lock.acquire` doesn't yield when the lock is free. That call then runs its engine call before its first `await`. So every later call of the step sees `step_started` set.

```suggestion
        # `step_started` is current here: the step's first call arrives after optim_step returns,
        # takes the free lock without yielding and runs its engine call, so later calls see it set.
```
