# [distmuon] Support tensor-parallel storage layouts

[Upstream PR](https://github.com/pytorch/torchtitan/pull/4353) · state: open · merged: False

## Original PR description

Based on `main` at `09c98e528` after #5183 merged. This PR contains only the two TP/QK-clipping commits.

## Summary

- Generalize DistMuon's optimizer redistribution schedule from one storage mesh axis to multiple axes, allowing DP and TP storage layouts to participate in one optimizer transport plan.
- Support `Shard` and `_StridedShard` storage for whole-matrix, variable-sized per-head block, and expert Muon computation.
- Preserve TP head ownership and redistribute per-head matrices only within the required DP group; skip redistribution when storage already contains complete matrices.
- Preserve the explicit redistribution mesh contract from #5183 for both single-axis and combined DP/TP transport.
- Enable TP layouts in the Kimi K2.5 DistMuon recipe and rebuild layouts/buckets for the final recipe parallelism configuration.
- Keep EP-enabled routed-expert layouts on their actual sparse `edp_shard`/`ep` mesh; TP is declared only for the EP-disabled dense expert layout.
- Make QK clipping represent per-head scales as TP-sharded and data-parallel replicated DTensors, preserving the single packed MAX all-reduce with no per-weight collective.

## Motivation

DistMuon previously assumed that optimizer redistribution operated over one storage mesh axis. Kimi's FSDP+TP parameters instead use multi-axis layouts such as `_StridedShard(0)` over the data-parallel axis together with `Shard(0)` over TP. This prevented the recipe from using TP even though model forward/backward TP was already available.

This change makes optimizer transport operate over the required storage axes while retaining the storage/compute layout contract. With EP enabled, routed experts live on the sparse `(edp_shard, ep)` mesh rather than a mesh containing a named `tp` axis, so their layout preserves EP-first `Shard(0)` ordering without advertising an ignored TP placement. Shared experts and dense attention/MLP parameters still use the dense TP mesh.

QK clipping is updated separately so TP-local attention heads are scaled against the same distributed storage layout.

#5183 supplies isolated DP/EDP child communicators through `build_alternative_fsdp_mesh()`. Custom NCCL options for a combined DP/TP group are configured on its flattened explicit mesh; flattening does not inherit options from the individual axis groups. The four-GPU regression covers both the isolated DP-only head bucket and an explicitly capped combined group.

The rebase also preserves main's newer compute-chunk balancing, source-locality preference, and per-rank region packing. Strided storage mappings and transport-local block-pattern offsets feed that planner rather than restoring the older redistribution builders. The variable-block regression checks complete matrix views and exactly-once coverage without depending on which DP rank the balancer selects.

## Testing

Rebased onto `main` at `09c98e528` on 2026-10-29. Local tests use `tt12` with pinned Python dependencies installed in an isolated validation directory; the shared environment was not changed.

- DistMuon and QK-clipping GPU suite: **19 passed**, including the capped DP/TP regression and inherited CPU-offload/device-staging coverage.
- Combined CPU coverage for FlexShard, optimizer parameter groups, optimizer containers, parallelism context, distributed utilities, and Kimi K2/K3 configuration: **117 passed**. The known FSDP mixed-precision test requiring the newer `param_dtype_override_fn` API was excluded from this `tt12` run.
- The CPU planner tests preserve main's fixed-work balancing and plan-reuse regression.
- The four-GPU numerical test verifies the supplied isolated DP and explicitly configured DP/TP groups, and compares assembled BF16 compute matrices and final updates against an unsharded reference.
- The GPU suite also covers an ordered variable-size BlockShard subgroup starting mid-pattern, preserving the global matrix-block phase.
- Prior four-GPU Kimi debug smoke testing with DP=2, TP=2, EP=2 completed 10 forward/backward and optimizer steps; loss decreased from `7.85023` to `5.49017`. This training run was not repeated for this rebase.
- All source lint/format hooks pass. Pyrefly was run separately and reports the same three PyTorch API errors on this branch and clean `main`, with no additional type errors.

```
 Yes—for this head layout, matching TP-first storage with TP-first compute is the better default.
  TP should retain its heads, and DP should divide the heads within each TP slice.

  On a (dp_shard, tp) mesh, that storage order is represented by:

  (_StridedShard(0, split_factor=tp_size), Shard(0))

  I’d keep both BlockShard declarations and add support for:

  shard_order_by_tensor_dim={0: ("tp", "dp_shard")}

  The planner should then:

  1. Compute head ownership sequentially: split heads over TP, then split each TP-local head range
     over DP. Convert those head ranges into row ranges.

  2. Compare actual storage and compute ownership: use only DP redistribution when TP ownership
     matches; skip redistribution entirely when DP boundaries already align with heads.

  I checked the routes for DP=2, TP=2, two rows per head:

   Heads    Current flattened plan: rows transferred    TP-first plan: rows transferred

   6                                               7                                  2

   8                                               8                                  0

  Merely adding the configuration field would not fix it.
```
