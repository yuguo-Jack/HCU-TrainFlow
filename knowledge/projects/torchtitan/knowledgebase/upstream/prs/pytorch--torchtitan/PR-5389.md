# Fix chunked loss backward for frozen decoder outputs

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5389) · state: closed · merged: True

## Original PR description

## Summary

`ChunkedLossWrapper` returns a detached loss when decoder outputs are frozen, even if the language-model head is trainable. The trainer's `loss.backward()` then raises `RuntimeError: element 0 of tensors does not require grad and does not have a grad_fn`.

Compute `decoder_requires_grad` and `run_backward` once before the chunk loop. Backward runs when decoder outputs require gradients, or when autograd is enabled and the head has trainable parameters. A detached or constant chunk loss still raises, preserving the existing error instead of silently skipping a gradient-accumulator slot. With frozen decoder outputs, `torch.no_grad()` remains forward-only.

The in-tree `LoRATransform(target_modules=["lm_head"])` produces this state: it freezes token embeddings, decoder layers and final normalization, so decoder outputs do not require gradients while the `lm_head` adapters train. Head-only linear probing with a trainable `lm_head` reaches the same path. Decoder LoRA and pipeline parallelism keep decoder outputs that require gradients, so they stay on the existing bridge.

For frozen decoder outputs and a trainable head, head gradients accumulate inside the chunk loop. The returned scalar is a leaf: its backward accumulates only its own gradient. Scaling that scalar afterward does not rescale head gradients, consistent with the existing decoder bridge's treatment of `grad_output`. Chunk sizes and normalization remain unchanged.

The fix makes sense. It addresses two real gaps in `ChunkedLossWrapper.__call__`:
1. **Head-only training.** `pred.requires_grad == False` but `lm_head` is trainable. Before this PR the wrapper skipped per-chunk backward and returned a detached loss, so the trainer's `loss.backward()` raised.
2. **`no_grad` with a grad-requiring `pred`.** The `h_chunks` became `requires_grad=True` leaves, but `chunk_loss` had no graph, so `chunk_loss.backward()` raised.

The ordinary training path behaves the same as before. I have one correctness concern, a few smaller points, and a question about motivation.

---

### 1. A loud failure becomes a silent gradient corruption (please fix)

`torchtitan/components/loss.py:722-732`

```python
if chunk_loss.requires_grad:
    requires_backward = True
    with spmd.no_typecheck():
        chunk_loss.backward()
        if requires_grad:
            ...grad_accumulator.add(h_chunk.grad)
```

This branch used to check `requires_grad` (the decoder output needs a gradient). Now it checks `chunk_loss.requires_grad`. That opens a new case: `requires_grad=True` while `chunk_loss.requires_grad=False`. This can happen if a `loss_fn` returns a constant or detached loss for some chunk, e.g. an early `return torch.zeros(())` when a chunk has no valid tokens. The skipped chunk then never calls `GradAccumulator.add`:

- `GradAccumulator.buffer` starts as `torch.zeros_like` (`loss.py:480`), so the decoder silently gets zero gradients for that chunk.
- Worse, `_next_idx` only advances on `add`. Every later chunk then writes at an offset shifted by one chunk, so the decoder gets **misaligned gradients**. Nothing errors.

On `main` this case fails loudly at `chunk_loss.backward()`. Per the repo's guidance on silent correctness issues in distributed/loss code, I'd keep that invariant enforced. The simplest change keeps the old error for the decoder-grad case:

```python
if requires_grad or chunk_loss.requires_grad:
    requires_backward = True
    with spmd.no_typecheck():
        chunk_loss.backward()  # still raises if requires_grad but no graph
        if requires_grad:
            ...
```

An explicit `ValueError` or `assert` when `requires_grad and not chunk_loss.requires_grad` would also work. `requires_backward` is then only needed on the `not requires_grad` return path.

### 2. The returned leaf loss is a stand-in for differentiability

`loss.py:739`: `total_loss.requires_grad_(requires_backward)` returns a leaf tensor that requires grad. Calling `loss.backward()` on it isn't quite a no-op, as the docstring says (`loss.py:584-585`). It fills `total_loss.grad` with a scalar `1.0` and does nothing else. That's harmless, but:

- Please reword the docstring to say what actually happens, e.g. "lm_head gradients are already accumulated; the returned loss is a grad-requiring leaf so the caller's `backward()` succeeds but propagates nothing."
- Any scaling the caller applies to the loss before `backward()` is ignored for head grads. The existing decoder path has the same property (`_DecoderOutputGradientBackProp.backward` does `del grad_output`), so this is consistent. A one-line comment would still help, so nobody later assumes this leaf carries gradient.

### 3. `torch.is_grad_enabled()` gating: OK

`loss.py:614`: `requires_grad = requires_grad and torch.is_grad_enabled()` is correct and cheap. In-tree, `Validator.validate` runs under `@torch.no_grad()`, so `pred` already won't require grad there. This case is mainly for external callers, which is fine. The mismatch `ValueError` just above still fires under `no_grad` when predictions disagree, which is reasonable.

Per CLAUDE.md ("investigate root cause", "no speculative defensive checks"): **which real config hits head-only training?** All decoder parameters *and* the embedding have to be frozen for `pred.requires_grad` to be `False`. ### Re: `loss.py:620`, what happens when `torch.is_grad_enabled()` is `False` but `decoder_requires_grad` is `True`?

**Short answer:** yes, `run_backward` is `True`, so `chunk_loss.backward()` is called. It then **raises** on the first chunk. It shouldn't run backward. In practice that failure is acceptable, because no in-tree caller can reach this state. This behavior isn't new in this PR; `main` does exactly the same thing.

### Trace

With `pred.requires_grad=True` under `torch.no_grad()`:

1. `decoder_requires_grad = True`, so `run_backward = True`. The `or` short-circuits, so `is_grad_enabled()` is never checked.
2. `chunk.detach().requires_grad_(True)` works under `no_grad`, so every `h_chunk` is a leaf that requires grad.
3. `lm_head(h_chunk)` and `self.loss_fn(...)` run under `no_grad`, so they record no graph. `chunk_loss.requires_grad` is `False` and there is no `grad_fn`.
4. `if run_backward: chunk_loss.backward()` then raises `RuntimeError: element 0 of tensors does not require grad and does not have a grad_fn`.

On `main`, the guard was `if requires_grad:` with `requires_grad = pred[0].requires_grad`, so it fails in the same way. The PR only renamed that flag to `decoder_requires_grad`. It also added the head-only branch, which *is* gated by `is_grad_enabled()`.

### Should it run backward?

No. Under `no_grad` the caller is asking for forward only, and there's no graph to backprop through. Still, I'd leave this as is rather than patch it:

- **No in-tree caller reaches it.** `Validator.validate` (`torchtitan/components/validator.py:145`) is decorated with `@torch.no_grad()`, so the model forward also runs under `no_grad` and `pred.requires_grad` is already `False`. To reach this state, a caller would have to run the decoder forward with grad on, then call the loss under `no_grad`. That's an unusual split.
- **It fails loudly.** It doesn't silently produce wrong gradients, and nothing gets accumulated or misaligned. The `RuntimeError` message is a bit generic, but it points at the cause.
- **There was a fix, and it was removed on request.** An earlier revision of this PR had `requires_grad = requires_grad and torch.is_grad_enabled()`, which made this case forward-only. @anijain2305's review item (2) asked to drop it under "no speculative defensive checks", since no in-tree caller needs it. That matches CLAUDE.md principle 7.

If we ever do want to support it, the right fix is the one-liner the PR used to have:

```python
decoder_requires_grad = pred[0].requires_grad and torch.is_grad_enabled()
```

With that change, the hidden chunks are not marked as requiring grad, there is no `GradAccumulator`, backward is skipped and the loss is returned detached. If we'd rather reject this usage, a clear `ValueError` would also work: "pred requires grad but autograd is disabled; run the model forward under the same grad mode". Either option belongs in a follow-up PR, not this one.

One related point: under `torch.inference_mode()`, `is_grad_enabled()` is also `False`, and the same reasoning applies. Inference-mode decoder outputs can't require grad, so `decoder_requires_grad` is always `False` there. The head-only branch's `is_grad_enabled()` check prevents `requires_grad_` from being called on an inference tensor, so that case is handled correctly.
