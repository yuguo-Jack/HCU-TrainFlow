# [observability] Keep log_trace_span records paired while another thread compiles

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5472) · state: open · merged: False

## Original PR description

**TLDR:** `log_trace_span` skips `_start` while another thread compiles, and its `_end` then logs the time since boot. In one GB300 RL run this broke 413 of each generator's first 482 `generate` spans. Fix: guard with `torch.compiler.is_dynamo_compiling()` instead of `is_compiling()`.

**Problem**
1. Every `log_trace_*` call returns early when `torch.compiler.is_compiling()` is True, so code traced by torch.compile doesn't log.
2. `is_compiling()` reads one process-wide flag. Dynamo holds it True for the whole compile session, so every thread sees True.
3. The RL generator compiles on its engine thread at the first step (vLLM's sampler), while the event loop thread opens `generate` spans.
4. A span opened during that compile skips `_start` and keeps `start_time = 0.0`. Its `_end`, written after the compile, logs `timer() - 0.0` with no `task_name`.
5. Cost: per generator, 413 of the first 482 `generate` calls have an `_end` of ~1.31e9 ms and no `_start`, ~15% of all `generate` spans in the log. Gantt and span analysis read them wrong.

**Solution**
1. `log_trace_span`, `log_trace_instant` and `log_trace_scalar` check `torch.compiler.is_dynamo_compiling()`. It is True only in code Dynamo traces, and False in eager code on every thread.
2. Logging inside a compiled function is still skipped, with no graph break (checked with `fullgraph=True`).

**Results**
```text
GB300 RL run, first wave of generate calls per generator (from the structured logs)
generator A   482 calls   69 with _start + _end,  413 with _end only (~1.31e9 ms, no task_name)
generator B   482 calls   70 with _start + _end,  412 with _end only

CPU repro: thread 1 compiles (backend blocks), thread 2 opens a span, then lets the compile finish
before   records: [generate_end]                  value 2.73e9 ms (devserver uptime)
after    records: [generate_start, generate_end]  value 40 ms
```

You may ask: why not make `__exit__` skip when `__enter__` skipped? The records would pair, but those 413 spans would still be missing. The guard itself is wrong for eager code.

NOTE: non-strict `torch.export` also sets the `is_compiling()` flag, so a `log_trace_*` call inside code it traces now logs once at trace time. No torchtitan call site runs under it today.

**Test plan**
`pytest tests/unit_tests/cpu/observability/ -q`: 140 passed. The new `test_pairs_while_another_thread_compiles` fails on main with only `generate_end` written.
