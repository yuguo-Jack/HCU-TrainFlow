# [CI] Preserve NumPy 1.x support by constraining PyArrow

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5372) · state: closed · merged: True

## Original PR description

Fixes #5365.

PyArrow 26 requires NumPy 2, but its wheel does not declare a NumPy runtime dependency. The datasets dependency therefore permits pip to install PyArrow 26 while retaining NumPy 1.26.4 in PyTorch's CI image, causing TorchTitan's feature test entrypoint to fail during import.

Add `pyarrow <26` to the shared requirements file to preserve NumPy 1.x support. Root requirements, Docker installs, and setuptools-generated wheel metadata already use this file, so the constraint has one owner.

### Verification

- Built the TorchTitan wheel and confirmed its `pyarrow<26` dependency.
- Clean Python 3.12 installed-wheel imports, `Trainer` import, datasets/PyArrow round trips, and dependency checks passed with NumPy 1.26.4 and 2.5.4, using PyArrow 25.0.1.
- Pip rejects an explicit request for PyArrow 26 against the corrected wheel.
- The actual integration-test module starts successfully with `--help` under NumPy 1.26.4.
- `pre-commit run --all-files`: all hooks pass except an existing Pyrefly error at `torchtitan/components/data/multimodal/utils/video.py:114`; the same error was reproduced on untouched main. No unrelated lint edits are included.

Package/startup checks ran on aarch64 with a CPU torch nightly. The original GPU CI job was not rerun.

**Verdict: LGTM.** It's a small, correct fix in the right place.

### What I checked
- **There is only one place to set this.** `requirements.txt` is a symlink to `.ci/docker/requirements.txt`, `pyproject.toml:23` reads it for `dependencies`, and `.ci/docker/common/install_conda.sh:43` pip-installs it in the Docker image. So the wheel metadata, a local `pip install -r`, and the CI image all pick up the pin. Nothing gets duplicated.
- **No conflicting pins.** No other requirements file or workflow pins `pyarrow`. `requirements-dev.txt` lists `numpy` with no version, so pip has no reason to upgrade NumPy to fit PyArrow 26. That is the failure the PR describes.
- **Works with the `datasets` range.** `datasets >= 3.6.0, < 4.8.0` only sets a lower bound on pyarrow, so `< 26` leaves a large compatible range (25.x, for example).
- **Root cause, not a band-aid.** PyArrow 26's wheel doesn't declare NumPy as a dependency, so pip can't detect the mismatch itself. Pinning PyArrow is the right fix, and it's better than pinning NumPy, which would break NumPy 2 users.

### Minor / optional
1. **The pin also applies to NumPy 2 users.** Since it's in the published dependencies, everyone installing torchtitan is held below PyArrow 26, even with NumPy 2. Environment markers can't depend on another package's version, so this trade-off is reasonable. I'd still make the comment say when the pin can go, e.g.:
   ```
   # TODO: Remove once PyTorch CI drops NumPy 1.x coverage. PyArrow 26 requires
   # NumPy 2 but its wheel does not declare a NumPy dependency.
   pyarrow < 26
   ```
   This follows the CLAUDE.md guidance to use a TODO for known limitations, and it explains why pip can't resolve this on its own. Without that, the pin looks redundant.
2. **Comment style.** The new comment uses `;`, which is ASCII. It passes the ASCII-only rule.

### Not verified here
I didn't rerun the GPU integration job. The PR description also says it wasn't rerun, and the `ciflow/docker` label should rebuild the image and confirm the fix.
