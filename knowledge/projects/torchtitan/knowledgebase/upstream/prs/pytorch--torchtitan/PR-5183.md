# [distmuon] Isolate redistribution NCCL communicators

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5183) · state: closed · merged: True

## Original PR description

## Summary

- add an explicit redistribution mesh to FlexShard `BucketConfig`, validated against the inferred storage-mesh axis, ranks, and rank order
- build one storage-shaped redistribution mesh per distinct runtime storage `DeviceMesh` within each DistMuon instance, replacing only `dp_shard` and `edp_shard` groups with resource-independent NCCL children
- attach the same built mesh directly to every matched DistMuon bucket with that storage layout, without a run-wide mesh cache
- build capped meshes with standalone `build_alternative_fsdp_mesh` in `torchtitan/distributed/utils.py`, keeping the existing `Config.build(params=...)` API without extra optimizer context plumbing
- leave the FlexShard DistMuon constructor and planner unchanged
- keep FSDP on its original communicator and configure the Kimi K3 DistMuon recipe to use eight redistribution CTAs

## Why

DistMuon uses all-to-all redistribution. Letting that traffic initialize on the FSDP communicator can create direct peer/channel connection state for the whole group, while reducing channels globally would also constrain FSDP collectives.

The explicit `DeviceMesh` contract follows the parallelism API convention: callers own process-group construction and DistMuon consumes the named mesh axis selected by its storage-to-compute transition. This supports `max_ctas` now and other process-group initialization options later without creating communicators implicitly inside FlexShard.

Optimizer construction retains the normal `Config.build(params=...)` API. The TorchTitan DistMuon wrapper calls the standalone `build_alternative_fsdp_mesh` utility on matched parameters' storage meshes. Adam, AdamW, and custom optimizer constructors remain unchanged; no new `parallelism_context` forwarding is needed in the optimizer container or torchft.

During initialization of each DistMuon instance, TorchTitan constructs one capped redistribution mesh for each distinct runtime storage `DeviceMesh` and explicitly reuses it across matching buckets. This sharing stays within that optimizer instance; there is no run-wide cache. The builder splits only the FSDP shard axes with `split_share=0`, preserves every other storage-mesh axis group, and reconstructs the original storage layout with `DeviceMesh.from_group`. The default `max_nccl_ctas_for_comms` value is `-1`; all values `<= 0` leave communication behavior unchanged.

A positive cap requires NCCL on the FSDP shard axes. Other backends raise `ValueError`; fake warns and keeps the storage groups without modeling the cap. A storage mesh without FSDP shard axes warns that the cap is not applied. The configuration documents the connection-memory savings, fixed communicator overhead, and bandwidth tradeoff, with a TODO identifying this as a temporary workaround pending lower-memory redistribution.

For a 64-rank all-peer group with 12 MiB of measured connection storage per peer/channel pair, reducing 32 channels to 8 changes the fan-out estimate from 23.625 GiB to 5.906 GiB per rank.

I didn't push any code. Two reviewers have pulled this PR in different directions, so the three of you should agree on a direction before it gets rewritten again.

**Short answer:** yes. Only one piece of this PR is NCCL-specific, and it's the piece that's currently in core.

| Piece | Backend-agnostic? | Recommendation |
|---|---|---|
| `BucketConfig.mesh` plus the validation in `_bind_bucket_configs` (`_optimizer_reshard_schedule.py:90-108`) | Yes. It's a plain `DeviceMesh` contract, same idea as FSDP2's `mesh` | **Keep.** It's what @weifengpy asked for, and it would fit well as its own small PR |
| `DistMuon.Config.redistribution_max_ctas` (`optimizer.py:224`) | No | Remove |
| `ParallelismContext.build_redistribution_mesh` (`parallelism_context.py:494-560`): `ProcessGroupNCCL.Options`, `split_share`, the `backend != NCCL` raise, the hard-coded `DP_SHARD`/`EDP_SHARD` | No, and ad hoc | Remove |
| `BaseOptimizer.Config.build_optimizer`, plus passing `parallelism_context` through `OptimizersContainer` and torchft | It only exists to feed the NCCL path | Remove, then use the plain `config.build(params=...)` |

### The problem underneath
What we need, without naming any backend, is: *"optimizer redistribution runs on its own communicator, not FSDP's."* The CTA cap is only how we'd tune that communicator on NCCL. Today the tuning is the API, and the isolation is a side effect of it.

### Proposed shape
1. **FlexShard:** `BucketConfig.mesh` as it is in this PR. No change.
2. **ParallelismContext:** build an optional dedicated optimizer-comm view of the storage meshes **once, when the meshes are built**, next to `full_dense_mesh_for_fsdp` and the sparse mesh. Use the `backend_override` path `unflatten_mesh` already uses (`parallelism_context.py:290-300`), which also accepts per-axis `(backend, Options)` in upstream DeviceMesh.
   - It's PyTorch-native and contains no `if nccl:` branches in our code.
   - The backend options come from config as an opaque per-backend override, or the default options if none are given. So on non-CUDA accelerators you still get isolation without any NCCL knob. The fake backend works the same way `backend_override` already handles it.
   - It's created once per run, which fixes a problem in the current version (below).
3. **Optimizer config:** a backend-neutral switch such as `isolate_redistribution_comm: bool = False`. The TorchTitan `DistMuon` wrapper then looks up the matching mesh with `parallelism_context.get_mesh(...)` by storage layout. There's no more `fnmatch` re-matching to find a parameter's mesh (`optimizer.py:262-275`).
4. **K3 recipe:** turns isolation on and puts the NCCL tuning (`max_ctas=8`) in its own parallelism/backend config. That keeps the NCCL-specific number at the recipe level, where it's a hardware-specific tuning choice, and out of `optimizer.py`.

This also answers @shuhuayu's timing concern: the optimizer config is built before any meshes exist, but `ParallelismContext` already knows the storage layouts before the model is built.

### A problem with the current version worth fixing anyway
`DistMuon.__init__` builds its redistribution meshes per optimizer instance (`optimizer.py:259`, the per-instance dict). `OptimizersContainer` creates one instance per model part, so PP with VPP=2 creates **two** child communicators per FSDP axis. That's the extra roughly 2 GB per process group @weifengpy warned about (the same mistake as `reshard_after_forward=int`). @shuhuayu's last comment notes this. Building them once in `ParallelismContext` at mesh-init time removes it.

### Another option to consider
The memory issue comes from all-to-all opening a connection to every peer. NCCL charges for that per peer per channel, and other backends have their own costs. Redistribution could instead use all-gather or reduce-scatter (ring patterns, no all-peer connection state), at the cost of moving more data. A rough bucketed comparison of throughput versus memory on K3 would show whether the communicator setting is worth exposing at all. Without that data, I'd go with the proposal above.

**Suggested next step:** land `BucketConfig.mesh` as its own PR now, then decide between items 2–4 above and the alternative. If you'd like me to implement this, tag me with the direction you've agreed on.

### 1. `build_redistribution_mesh` (`parallelism_context.py:494`)

**(a) Make it a standalone function: agreed, and it helps more than it looks.** The method never touches `self`. It's also the only reason DistMuon needs a `ParallelismContext`. Once it's a free function, the wrapper calls it on `matched_parameter.device_mesh`, and all of the following can be reverted:
- `parallelism_context` on `DistMuon.__init__`, `Adam.__init__` and `AdamW.__init__` (`optimizer.py:142,180,235`)
- the new `parallelism_context` argument on `OptimizersContainer` and its use in `optim.py:125`
- the torchft passthrough (`experiments/torchft/optimizer.py`)
- the `BaseOptimizer` docstring saying custom optimizers must accept `parallelism_context`

The current version requires every custom `BaseOptimizer` subclass to accept a new constructor kwarg, which breaks user code. That goes away too, and `optimizer_config.build(params=[param_group])` becomes plain again. This resolves your earlier "can just use constructor" comment cleanly.

**(b) Name: agreed that it should mention FSDP, but I'd avoid `build_alternative_fsdp_mesh`.**
- "alternative" doesn't say how it differs.
- "fsdp mesh" suggests FSDP runs on it, and the whole point is that FSDP doesn't.

What the function actually does is take a storage mesh and swap the `dp_shard`/`edp_shard` groups for new `split_group` children with capped CTAs. I'd use the upstream verb, since "split" also tells the reader it allocates new communicators and costs memory:

```python
def split_fsdp_shard_groups(storage_mesh: DeviceMesh, *, max_nccl_ctas: int) -> DeviceMesh:
    """Return a mesh with the storage layout whose dp_shard/edp_shard groups are
    new NCCL communicators (split_share=0, max_ctas capped); other axes keep
    their original groups."""
```

`build_mesh_with_capped_fsdp_shard_groups` would also work if you want something more explicit.

**(c) Location: `fsdp.py` would create an import cycle; I'd use `torchtitan/distributed/utils.py`.** The chain is:

`components/optim/optimizer.py` → `distributed/fsdp.py` → `models.common.moe` (`fsdp.py:26`) → `models/common/moe/moe.py:39` → `models/common/aux_loss.py:37` → `components.optim` → `optimizer.py`

`fsdp.py` is also about applying FSDP to modules, which this function doesn't do. `distributed/utils.py` fits better:
- it already holds backend-specific communicator helpers (`configure_nccl_for_ulysses`, `set_pg_timeouts`)
- it only imports `parallelism_context`, so `MeshAxisName` is still available
- it keeps the code in `torchtitan/distributed/`, as CLAUDE.md asks

The two tests that mock `parallelism_context.build_redistribution_mesh` (`test_dist_muon.py:75`, `test_optimizer_param_groups.py:586-625`) would switch to patching the function.

### 2. `max_nccl_ctas_for_comms` (`optimizer.py:228`)

**Is it a no-op on non-NCCL backends?** Only when it's disabled. Current behavior:

| value | NCCL | fake | other backends (gloo, xccl, …) |
|---|---|---|---|
| `<= 0` | no-op | no-op | no-op |
| `> 0` | split + cap | warns, falls back to the storage group | **`ValueError`** (`parallelism_context.py:529`) |

Raising is the right call; a silent no-op on XPU would hide a missing memory cap. It should be documented on the field, though.

Smaller issues:
- The inline comment says `<0 disables`, but the check is `> 0` (`optimizer.py:239`), so `0` also disables. Either write `<=0 disables`, or reject `0` in `__post_init__`.
- If no matched parameter has a `dp_shard`/`edp_shard` axis, `replaced_group` stays `False` and the knob does nothing without telling anyone. CLAUDE.md asks for a warning when config is skipped like this.
- `for_comms` reads as "all comms", but only DistMuon redistribution is capped and FSDP is untouched. The docstring should say so.

Suggested replacement for the inline comment:

```python
        max_nccl_ctas_for_comms: int = -1
        """Cap NCCL CTAs (channels) for DistMuon redistribution only; ``<= 0`` disables.

        Redistribution is an all-to-all, so NCCL keeps connection buffers for every
        peer on every channel: memory ~ num_peers * num_channels * per-pair size.
        A positive value runs redistribution on new child communicators of the
        ``dp_shard``/``edp_shard`` groups (``split_share=0``) with ``max_ctas``
        set, which reduces the channels and that buffer memory. FSDP collectives
        stay on the original communicators. Each child communicator adds fixed
        workspace memory and fewer channels may lower all-to-all bandwidth.
        Requires NCCL: raises ``ValueError`` on other backends and is ignored
        (with a warning) under the fake backend.

        TODO: Temporary workaround for all-to-all connection memory. Remove once
        redistribution uses a pull-based (symmetric memory) kernel that does not
        need all-peer NCCL connections.
        """
```

The TODO matches @weifengpy's and @fegin's long-term plan.
