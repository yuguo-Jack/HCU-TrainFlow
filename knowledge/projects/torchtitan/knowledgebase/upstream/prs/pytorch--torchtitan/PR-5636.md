# [model] Add an add_model skill documenting the model-port workflow

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5636) · state: open · merged: False

## Original PR description

human notes:
1. this is a skill used to draft a new model support in torchtitan so one can iterate with agents with the draft, 
2. covering model definition, parallelisms, numerical parity, feature and e2e tests,
3. following 1) titan coding styles in naming, comments, file structure, 2) proper reusing existing modules, abstract boundaries. 

## Why

The add_model guidance predates current TorchTitan APIs and needs a concrete validation plan for new model ports. A numerical golden is useful only after the debug recipe is proven repeatable.

## Changes

- Document current flavor/build, recipe, lifecycle, sharding, checkpoint, and shared component APIs.
- Require component and full-model forward parity in evaluation and training, plus gradients for differentiable components and the full training model. Select compatible HF, Megatron, author, SGLang, or vLLM references.
- Keep CPU feature tests, real combined FSDP/TP/EP/PP training, and strict debug goldens. Prove independent repeatability with full-precision loss and grad_norm before golden export and replay.
- Add offline parallelism comparisons with matched global batches and loss normalization, reconstructed gradients before clipping, and global norm scaling checks. Report the matrix evidence in the PR.
- Require PR stacks: model enablement, additional parallelisms and required kernels, then optional performance work. Reuse established attention/remat paths and benchmark matched workloads when requested.
- Require local `pr_review` -> revise -> re-review for every PR until the current version is approved with no open must-fix findings. Re-review affected dependencies before submission; use concise API examples and a compact coverage table.

## Example

A new MoE port first adds its model, FSDP, and reference forward/backward tests.
A later PR adds TP/EP/PP support and the broader numerical comparisons.
A TP run reporting grad_norm 2.0 against a matched baseline of 1.0 requires investigation.
The matrix checks gradients before clipping, so clipping cannot conceal the scaling problem.
Each PR is revised and locally reviewed until it passes; then the reviewed stack is submitted.
A fixed debug recipe still needs exactly matching loss and grad_norm before golden generation.
