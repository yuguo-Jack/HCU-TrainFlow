# [rl] Generator drains itself before a hot_swap=False weight load (7/14)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5503) · state: open · merged: False

**TLDR:** With `hot_swap=False`, the generator now drains itself before a weight load, instead of the router holding back its calls. A caller can then send `generate` straight to a generator (PR 9) without losing the drain.

**Problem**
1. With `hot_swap=False`, `InterGeneratorRouter.pull_model_state_dict` stops routing to a generator, waits until no call it routed there is in flight, then loads.
2. That works only because the router wraps every `generate` call and sees it start and end.
3. A caller that sends `generate` straight to the generator (over HTTP, PR 9) bypasses the router, so the router can't drain.

**Solution**
1. `Generator.load_model_state_dict(version, drain=True)` puts a draining load on the engine loop's queue.
2. The engine loop stops admitting new requests, keeps stepping the admitted ones, and loads once none is left.
3. Requests that arrive meanwhile are admitted right after the load, so they run on the new weights.
4. The router passes `drain=not hot_swap` and drops its per-generator `serving`/`idle` state.
5. Unchanged: `hot_swap=True` loads, routing, and when a load is requested.

**Results**
Numerics: bitwise vs main. With `hot_swap=True` (the default, and every recipe) nothing changes; with `hot_swap=False` a request still waits for the load and runs on the new weights, only where it waits moves.
```text
hot_swap=False, Qwen3-4B-Base native DAPO-Math (8 x 16, 8k tokens), 8 x H100, 5 steps, measured with PR 9 on top
                                   main           this PR
step period, mean / median (s)     57.0 / 53.9    57.4 / 55.3
pull span seen by the caller (s)   46.0 median    45.7 median   (drain + load; the drain moved into the generator)
```

NOTE:
- No recipe sets `hot_swap=False`.
- With `hot_swap=False`, `time_to_first_token_ms` now includes the drain wait.
- A client that leaves while its request is parked still gets it generated after the load (PR 10 fixes this).
- The router's `router_drain_wait` span is gone; the generator's `load_model_state_dict` span covers drain + load.
- All generators still drain in one gather, so a parked request waits about as long as one held in the router did. A new session can now land on a generator still draining while another has finished.
