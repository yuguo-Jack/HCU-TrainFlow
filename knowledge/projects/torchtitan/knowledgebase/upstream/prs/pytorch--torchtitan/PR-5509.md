# [rl] Generator aborts a request whose caller left (10/14)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5509) · state: open · merged: False

## Original PR description

**TLDR:** A `generate` call cancelled after the engine loop took its request (e.g. a Verifiers harness that hit `timeout.rollout` closed its POST) now aborts the request on every rank of its replica and frees its KV, instead of generating it to the end for nobody.

**Problem**
1. **The cancel reaches the generator.** Since PR 9, a caller that leaves closes its HTTP connection, and the server cancels `Generator.generate`.
2. **Queued requests are skipped.** The engine loop drops a request whose caller left while it was still on the queue.
3. **Taken requests run to the end.** `GenerationEngine` has no abort, so a taken request keeps a sequence's KV and decode steps until it ends.
4. **Draining loads too.** With `hot_swap=False`, a request parked by a draining load whose caller left is still generated after the load.

**Solution**
1. **One message.** A `generate` cancelled after the loop took its request puts a `RequestAbortMessage(request_id)` on the queue.
2. **Parked:** rank 0 fails its reply and drops it; it never reaches an engine.
3. **Admitted:** the next decision's `aborted_request_ids` makes every rank call `engine.abort_requests(ids)`; rank 0 fails the reply and frees its DP reservation.
4. **Engine API:** `GenerationEngine.abort_requests(ids)` returns the ids it ran (default `[]`); `VLLMEngine` aborts one id per call, so every TP rank frees blocks in the same order.
5. **Unchanged:** calls that aren't cancelled, requests still on the queue, loads, routing.

```text
caller leaves -> EngineLoop.generate cancelled
  still on the queue        -> the loop skips it                                    (unchanged)
  taken, parked by a drain  -> rank 0 fails it; never admitted after the load       (new)
  admitted                  -> next decision's aborted_request_ids
                               every rank: engine.abort_requests(ids)                (new)
                               the TP rank 0 that ran it reports it -> rank 0 fails the reply
```

**Results**
Numerics: bitwise vs main when no call is cancelled; a cancel removes that request from the batch, so other requests' tokens can differ, as with any load change.
```text
GPU, with PRs 11 and 13 (native rollouts reach this path only through a group cancel or a rollout timeout):
alphabet sort, Qwen3-0.6B, trainer TP2 + one TP4 generator, rollout_timeout_s=0.5 (generate p50/p99 0.25/0.50 s), 5 steps
training steps                            5 of 5, no errors
rollout timeouts (worker log)             568
decisions with aborts                     14; every one aborted more than one request
per TP rank: ids asked / aborted          490 / 300 (the rest had already finished)
TP ranks agreeing on every decision       4 of 4
```

You may ask:
- Why exactly once with DP > 1? vLLM drops a request from its id map inside the `step()` that finishes it, so an abort after the finish (or on a replica that doesn't run it) skips it; finish and abort reports travel on one port from the same sender.
- Why not report aborts through `process_rejected_requests`? It logs one warning per request, and aborts come in bursts.
- Why not keep the partial completion? The caller left, so nobody reads it.

NOTE:
- An aborted admitted request no longer counts toward a draining load, so the load stops waiting for work nobody wants.
- Native rollouts and shutdown cancel a generator call only with PR 11, since a Monarch call runs to completion even when its caller is cancelled. With it, a native shutdown aborted 68 in-flight requests on 6 TP1 generators within 100 ms of post-training validation's start.
- DP > 1 and Verifiers-harness timeouts are tested on CPU only.
- `VLLMEngine.abort_requests` reads vLLM internals (`OutputProcessor.external_req_ids`, `LLMEngine.abort_request`); a CPU test fails if either moves.
- A request that finishes in the same burst its caller leaves resolves normally; its abort is a no-op.
