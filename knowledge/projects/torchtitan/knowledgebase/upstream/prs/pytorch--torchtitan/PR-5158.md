# [kimi_k3][perf] Compile the MLA key/value assembly (mla_kv region)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5158) · state: open · merged: False

## Original PR description

**TLDR:** Kimi K3's MLA k/v assembly becomes the `mla_kv` region: MLA glue 2.63 -> 0.52 ms per MLA layer, ~0.5% of a full-model step (optional, below the 1% bar).

**Problem**
1. **Split.** MLA splits `kv` into k_nope and v.
2. **Broadcast + concat.** The headless rope slice is broadcast to all heads and concatenated into k.
3. **Slow copies.** The concat and the split's backward run as non-vectorized `CatArrayBatchedCopy` kernels.
4. **Cost.** 1.17 + 1.63 ms per MLA layer at 16k (24 of 93 layers are MLA).

**Solution**
1. **Region.** `KimiMLAAttention._assemble_kv` is now the `mla_kv` region; Inductor fuses split, broadcast and concat.
2. **One-kernel grad.** Under a compiled backward, v comes back contiguous, so the region writes kv's gradient in one kernel.
3. **Unchanged.** Eager and `no_grad` keep the view; the remat marker sits on `kv` before the call.

**Results**
```text
Kimi K3 layers 50+51 (one MLA layer of two), 16k tokens, fwd+bwd wall, 1x GB300 (shared), on PR 2
no AC          194.23 -> 192.21 ms  (-1.0%)
SelectiveAC    216.8  -> 213.50 ms
MLA kernels      2.63 ->   0.52 ms per MLA layer (ideal 0.53)
correctness: bitwise vs eager (k, v, kv grad, k_rope grad)
graphs: _assemble_kv 1 per grad mode (2 with no_grad)
```

You may ask:
- Why not always return a contiguous v? An extra copy in eager.
- Why not a ConcatKernel lowering? Slower.

NOTE: not tested: TP (the region runs `spmd.local()` inside), varlen backend in the unit test (uses flex), loss curve.
