## Agent details

Written with Claude Code: the analysis, measurements and test plan below.

**TLDR:** `materialize_mla_kv`, the k/v build shared by DeepSeek-V3 and Kimi K3 MLA, becomes the `mla_kv` local-compile region, which fuses the eager concat kernels. Two DeepSeek-V3 layers at 16k: -2.6% wall, -2.7% under CUDA graphs, -1.07 GB peak (2 layers, no activation remat). Outputs are bitwise; grads are bitwise except k_shared's, a sum over heads in Inductor's order (1 bf16 ulp on 1 of 1,048,576 elements under some configs). `UlyssesMLAAttention` now all-gathers k_shared synchronously, so the region keeps k_shared's grad.

```text
main:     kv -> split -> k_nope, v (a view of kv);  k = cat(k_nope, k_shared on every head)   eager cat; bwd: eager cat
this PR:  region(kv, k_shared) -> k, v (dense when grad is on)                                Triton copies; bwd: one copy + head sum
```

Independent of the PR below it in the stack (no shared files; applies cleanly on main).

**Problem**
1. **Shared k/v build.** `MLAAttention` builds per-head k and v in `materialize_mla_kv`, from packed `kv` `[T, H, 256]` and the shared key `[T, 64]`.
2. **Eager copies.** It splits kv into k_nope and v, broadcasts the shared key to all heads, and concatenates `k = [k_nope, k_shared]` `[T, H, 192]`.
3. **Slow kernels.** Both concats run ATen's generic cat kernel: k's 1552 us vs 189 us at full memory bandwidth (8x), the backward's 1940 vs 302 us (6.4x).
4. **Cost.** 3.55 ms per DeepSeek-V3 layer at 16k, fwd+bwd kernel time (ideal 0.53 ms).

**Solution**
1. **Region.** `materialize_mla_kv` is now the `mla_kv` region. Inductor fuses split, broadcast and concat into one copy kernel, and the backward concat into another.
2. **Dense v when grad is on.** Attention saves v, and a v that views kv keeps all of kv alive. A dense v lets kv go after the forward: -0.54 GB per MLA layer at 16k without activation remat. Under compile the copy is free: it replaces the backward's copy of v's grad.
3. **Ulysses CP.** `UlyssesMLAAttention` all-gathered k_shared with `async_op=True`. A compiled region detaches an unwaited async input, so k_shared's grad came out all zeros under `mla_kv`. The all-gather is now synchronous. The gathered k_shared is `[T, 64]` (2 MB at 16k in bf16); the overlap it loses was not measured.
4. **Enabled** in `DeepSeekV3Model.Config` (Kimi K2.x inherits it) and `KimiK3Model.Config`.
5. **Unchanged:** the function's signature and how both callers call it (`MLAAttention.forward`, also used after the CP all-gather, and `UlyssesMLAAttention.forward`). `no_grad` keeps the view.

**Results**

Decode: not reached in the RL generator, which runs vLLM's native MLA. The exception is batch-invariant mode, whose only MLA configs (the Kimi K3 RL tests) set regions `[]`.

You may ask: why a dense v in eager too? Same memory reason, one code path instead of an eager/compiled fork. Measured 10-19 on the same split + copy, before it moved into `materialize_mla_kv` (2 DeepSeek-V3 layers at 4k): eager +0.2-0.3%, GraphTrainer +0.3-0.8% kernel time.
You may ask: why not a dense v under `no_grad`? Nothing is saved for backward, so it's only a copy: +0.44 ms wall on the 16k prefill (2 layers; two 155 us clones).
You may ask: why not always the view? Same time without activation checkpointing, but +0.54 GB per MLA layer at 16k without activation remat. Under activation remat the forward copy replays: +0.16 ms per layer (0.2%).
NOTE: the region is on in the recipes that keep the model's default regions: `deepseek_v3_671b`, `deepseek_v3_671b_dist_moe_bf16`, `deepseek_v3_671b_dist_moe_mxfp8`, the Kimi K2.x / K3 model configs (debugmodel test recipes), and `rl_grpo_deepseek_v3_debug` (the H100 RL integration test, 4 GPUs: its trainer runs the region, its generator runs vLLM's native MLA). That RL test is the PR's only GPU end-to-end coverage.
NOTE: the region is off in `deepseek_v3_671b_nvfp4_ffn_mxfp8_attn` (regions `["loss"]`), GraphTrainer and SPMD-typechecking configs (regions `[]`), the Kimi K3 RL test configs (`[]`) and the `fused_mla` override (it skips `materialize_mla_kv`). With grad on, these still return a dense v (cost in "You may ask").
NOTE: Ulysses CP: q keeps the packed q/kv buffer alive, so there a dense v adds `[T, H/cp, 128]` per MLA layer instead of saving memory. No recipe uses Ulysses MLA.
NOTE: goldens: the fake-PG A10G DeepSeek-V3 golden is unchanged (bitwise; the region is on there). The real-PG CP+PP goldens (A10G, mi350x) get refreshed if they move. The Kimi K3 B200 golden runs with typechecking, so regions are off there.
NOTE: not tested: varlen DeepSeek-V3 (the 671B recipe's default backend; the region doesn't touch attention), multi-GPU TP and CP, loss curve.


<details><summary>Details</summary>

- Call sites: `MLAAttention.forward` binds `materialize_kv=materialize_mla_kv` at def time. That binding is the `local_compile` wrapper, so the region applies to `MLAAttention`, to the all-gather CP variant (which calls `MLAAttention.forward`), and to `UlyssesMLAAttention`. The `fused_mla` override passes its own `materialize_kv`, so it isn't affected, as the description says.

- Remat: `recompute_needs_tensor(kv_THP, k_shared_TR)` already keeps `kv` for replay, so with remat on, the dense `v` changes time (the description measures +0.16 ms per layer) but not peak memory.
- The test is in the right place (`models/common`, next to the shared function). The Ulysses parametrization adds real coverage: a non-contiguous `kv` taken from a packed q/kv tensor.
- Eager configs (GraphTrainer, RL with regions `[]`) pay the copy of `v` (+0.2-0.8% kernel time) to get the same memory win. I agree with keeping one code path here.

</details>
