# [rl] offload idle session KV to CPU (6/6)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5299) · state: open · merged: False

## Original PR description

not a priority

**TLDR:** opt-in `VLLMSessionKVHolder.Config(cpu_kv_offload=CPUKVOffload.Config(size_gib=16))` turns on vLLM's native CPU KV offload. A multi-turn session whose history left the GPU reloads it instead of recomputing it: 23-26 ms vs 196 ms for an 8k history (Qwen3.5-4B-Base, 1 H100). Ended sessions are evicted first, so a 16 GiB tier keeps a live 32k session that plain LRU loses (40 ms vs 883 ms). Tokens and logprobs are bitwise equal to a run without eviction. Works with TP; DP > 1 is rejected for now: vLLM pins `size_gib` once per DP rank.

**Problem**
1. A multi-turn rollout re-sends its whole history every turn. vLLM skips recomputing it only while it is still in the GPU prefix cache.
2. Between turns (env step, tool call), other requests evict it. The session KV holder protects it, but when memory runs short it drops whole idle sessions, which then recompute.
3. Recompute grows with the history: 196 ms of time to first token (TTFT) for 8k tokens, 882 ms for 32k.
4. vLLM's native CPU offload would fix this, but here:
   - it refuses to start under `expandable_segments:True`, which `RL_ENV_DEFAULTS` sets for every RL process;
   - by default it stores prompt blocks only, so the previous turn's completion is never stored;
   - its LRU fills the CPU tier with finished rollouts, which push out live sessions;
   - with more than one GPU per generator it hangs: each rank runs its own scheduler, which waits for every worker to finish a transfer but sees only its own worker's.

**Solution**
1. A new `Configurable`, `CPUKVOffload` (`torchtitan/rl/generator/vllm/cpu_kv_offload.py`), holds everything offload-specific. The holder owns it:
```
holder = config.session_kv_holder.build()
engine_kwargs.update(holder.engine_kwargs())  # vLLM's OffloadingConnector, offload_prompt_only=False
engine = LLMEngine.from_engine_args(EngineArgs(**engine_kwargs))
holder.attach(engine)                         # CPUKVOffload.attach: the TP fixes in step 4
holder.release(session_ids=[...])             # CPUKVOffload.evict_first: ended sessions' chunks go first
```
2. The controller's default actor system launches generator procs with `expandable_segments:False` (other allocator options kept) and `PYTHONHASHSEED=0` when offload is on. Trainers are unchanged.
3. Evicted first: the ended sessions' chunks that no live session uses (GRPO siblings share their prompt). A session the holder drops from GPU for room keeps its CPU place: that copy is what it reloads. The stall release ignores requests loading from CPU: they wait for the load, not for blocks.
4. With TP > 1, every engine step all-gathers the TP ranks' finished transfers and merges them with vLLM's `KVOutputAggregator`. The TP ranks' schedulers must stay identical: request ids get a counter suffix instead of vLLM's random one, procs share `PYTHONHASHSEED=0`, and each gather raises if the scheduler fingerprints differ. Each scheduler waits for its own TP group only, not DP x TP.
5. Off by default; `hold_gpu_blocks=False` gives offload without the GPU hold. `session_kv_holder` still rejects `reset_kv_cache_on_model_state_dict_load=True` (which `batch_invariant` needs): vLLM can't reset the prefix cache while a request waits on a CPU load either.
6. `VLLMEngine` rejects `cpu_kv_offload` with `data_parallel_degree > 1` when it is built: vLLM gives each DP rank its own `size_gib` region, so DP=2 pins 2 x `size_gib`, and half of it is never written (Results).

**Results**
```
Qwen3.5-4B-Base, VLLMGenerator standalone, 1 H100, TP=1, FULL CUDA graphs, greedy.
4 sessions x 8k prompts -> churn of 2x the 124-block GPU pool -> turn 2 (7,920 reusable tokens):
  no eviction              7,920 cached   TTFT  16.4-16.6 ms
  offload off                  0 cached   TTFT 196-197 ms
  offload on (16 GiB)      7,920 cached   TTFT  22.9-25.9 ms
  offload on + hold        7,920 cached   TTFT  24.1-27.6 ms   (the free floor dropped all 4; reloaded from CPU)
  tokens and logprobs bitwise equal to no eviction; churn took 3.05 s with offload off, 3.07 s on

1 live 32k session, offload on, hold off, 16 GiB CPU tier, ~18 GB of churn stored after it,
each churn rollout released through InterGeneratorRouter:
  base branch (plain LRU)                       0 cached   TTFT 882 ms
  this PR, router releases not forwarded        0 cached   TTFT 883 ms
  this PR                                  32,736 cached   TTFT  40.5 ms   bitwise equal to no eviction (15.5 ms)

TP=2 (2 H100, 4B), 4 x 8k two-turn with churn, all bitwise equal to TP=2 no eviction:
  hold off                     7,920 cached x4   TTFT 22.4-24.3 ms
  hold on                      7,920 cached x4   TTFT 20.4-22.2 ms
  hold on + pull               7,920 cached x4   TTFT 18.8-21.7 ms   (pull between turns; same weights: load_state_dict patched to a no-op)
TP=2 churn loop, 16 sessions x 12 turns, 8 GiB tier:
  Qwen3.5-4B           1,787 steps in sync, 939 CPU hits, the same CPU eviction order on both ranks
  Qwen3-0.6B           4,339 steps in sync (attention-only, 16-token blocks)
  per-step all-gather  +0.5% wall time (prototype, offload off: 30.19 s without the gather, 30.33 s with it)
DP=2, Qwen3.5-35B-A3B-Base, EP=2 (vLLM's default all-to-all), CUDA graphs off, before DP > 1 was rejected:
  7,392 cached x4, bitwise equal to DP=2 no eviction; TTFT 1.1-1.2 s vs 2.1-2.5 s recomputed
```
These were measured before the `CPUKVOffload` refactor, which moved the code without changing it. Rerun after it (TP=1, 1 H100 each):
```
offload on + hold, 4 x 8k     7,920 cached x4   TTFT 23.9-26.1 ms   1.244 GB loaded, 10.89 GB stored (as before)
32k session via the router   32,736 cached      TTFT 44.0 ms
```
Why Solution step 6 rejects DP > 1:
```
Host RAM per generator, size_gib=4, Qwen3-0.6B, 2 H100, vLLM engine build only, every region pinned whole:
             regions      /dev/shm    slots written
TP=1 DP=2    2 x 4 GiB    +8.0 GiB    rank 0: slot 0 of region A; rank 1: slot 1 of region B
TP=2 DP=1    1 x 4 GiB    +4.0 GiB    rank 0: slot 0, rank 1: slot 1, same region
```

You may ask:
- Why name the connector instead of setting `kv_offloading_size`? vLLM's in-process config check then sees it and rejects router replay with offload (`ValueError`). Through `kv_offloading_size` it was accepted, and CPU-restored rows replayed the wrong experts (vLLM 1.0.0.dev20261011, Qwen3-30B-A3B).
- Why merge every step, not once per engine-loop decision? Per decision delays a reload by up to 16 steps (190-260 ms on the 4B), about an 8k recompute; per step costs +0.5%.
- Why a counter suffix on request ids? vLLM reports finished loads by its internal id, whose random suffix differs per rank.
- Why `PYTHONHASHSEED=0`? Without it, the two ranks held the same CPU chunks in a different eviction order, so later evictions could differ.
- Why evict ended sessions first instead of not storing them? Often only the env knows after a turn that it was the last (chess: game over after the move).
- Why reject DP > 1 instead of sharing one region? One `engine_id` per generator would let its DP ranks on one host share one region, but that relies on vLLM's private slot layout (slot = device index % world size); it is a TODO at the check. Dividing `size_gib` by DP fixes the RAM total, but still leaves half of each region unused at DP=2.
- Why not `enable_cumem_allocator=True`? Our worker routes only weights through CuMem, so the KV cache would stay on expandable segments: it would only silence vLLM's check.

NOTE:
- Untested: DeepEP (EP ran only with vLLM's default all-to-all), GB300 (reloads go over NVLink-C2C), Qwen3.5-35B-A3B under RL, RL throughput with offload under memory pressure.
- `expandable_segments:False` may fragment CUDA graph pools and DeepEP buffers; unmeasured. Launchers that build their own actor system must set both env values (vLLM or our init check raises otherwise).
- Private vLLM state, all inside `CPUKVOffload`; rerun the TP=2 two-turn replay after each vLLM bump:
  - `connector_scheduler.manager._policy.evictable_chunks` (`attach` raises if the policy is not `LRUCachePolicy`);
  - the connector's `num_workers` and `_job_counter`;
  - `InputProcessor.assign_request_id` and `Scheduler.update_from_output` (both replaced).
- Weight sync: requests carry a per-version cache salt, so a new-version request can't hit old-version CPU chunks.
- Gaps: a sibling whose first request hasn't reached the generator doesn't protect the shared prompt. TODOs in code: a chunk stored after its release keeps its LRU place; each release rebuilds the live hash set (0.6 ms for 250 Qwen3.5 sessions of 16k tokens, 23 ms with 16-token hash blocks).
- CPU RAM is ~131 KB per token for Qwen3.5-4B; pinning 16 GiB added at most 5 s to init, 64 GiB 15-25 s (H100 host).
