# [rl] vLLM generator: 128-token KV pages when FA4 runs attention

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5489) · state: open · merged: False

## Original PR description

**TLDR:** when FA4 runs attention, TorchTitan's vLLM generator now asks for 128-token KV pages instead of vLLM's default of 16. This applies to every model except head dim 256 (Qwen3.5), which vLLM already gives 128. On GB300, head dim 64 (Muse Spark): batched decode 13-16% faster, cached prefill 9-16% faster; head dim 128 (Qwen3, Llama 3): decode 1-8%, cached prefill 11-13%. Outputs are bitwise identical.

**Problem**
1. FA4 loads paged K/V with TMA (the GPU's bulk-copy unit) only when one page holds exactly one 128-key block (`page_size == tile_n`); other page sizes take a slower gather path.
2. vLLM picks 128-token pages by itself only for FA4's head-dim-256 kernel (Qwen3.5). Every other head dim gets vLLM's default of 16.
3. TorchTitan's vLLM backends subclass vLLM's FlashAttention backends, so they inherit that choice; the generator only overrides the page size below SM90.
4. **Cost:** Muse Spark (head dim 64, 32 q / 4 kv heads per TP-4 rank) decodes and prefills on the gather path. Decode batch 256 x 32k: 1478 us vs 1246 us with 128-token pages.

**Solution**
1. `_FA4PageSize` makes `get_supported_kernel_block_sizes` return `[128]` when `get_cuda_flash_attention_impl()` is `"FA4"`.
2. Both TorchTitan backends (`TorchTitanVarlenInnerAttentionBackend` and the DiffKV one) inherit it.
3. Unchanged: FA3/FA2 keep vLLM's choice, and head dim 256 already got 128.

**Results**
GB300, Muse Spark per TP-4 rank (32 q / 4 kv heads, head dim 64), FA4 4.0.0b34 through torch `varlen_attn_out` (`num_splits=-1`), CUDA-graph replay with cold L2, us, 16 -> 128-token pages:
```
decode   bs64  x 2k            44.2 ->   39.0   (-12%)
decode   bs64  x 32k          434.7 ->  376.0   (-14%)
decode   bs256 x 2k           116.9 ->  109.7    (-6%)
decode   bs256 x 32k         1477.8 -> 1246.4   (-16%)
decode   bs1   x 32k           27.3 ->   30.6   (+12%)
prefill  2048 new on 16k      302.2 ->  272.6   (-10%)
prefill  2048 new on 32k      566.4 ->  515.3    (-9%)
prefill  4 x 512 new on 8k    170.1 ->  143.5   (-16%)
prefill  8192 new on 0        265.4 ->  254.1    (-4%)
```
Head dim 128 (32 q / 8 kv, like Qwen3-8B and Llama 3 8B), same setup, 2 rounds within 1%:
```
decode   bs8   x 32k          187 ->  180    (-4%)
decode   bs64  x 8k           353 ->  324    (-8%)
decode   bs64  x 32k         1325 -> 1233    (-7%)
decode   bs256 x 8k          1234 -> 1223    (-1%)
prefill  2048 new on 32k      812 ->  705   (-13%)
prefill  4 x 512 new on 8k    230 ->  203   (-11%)
```
- Sliding-window layers (2048 tokens) are within +-3% either way; batch 1-8 decode is within noise except bs1 x 32k global (+3 us).
- Bitwise: the same logical KV laid out as 16- or 128-token pages gives identical FA4 outputs (decode and prefill, global and windowed, 5 shapes). Only the load path changes.

You may ask: why not pick the page size per head dim? FA4 on Blackwell uses 128-key tiles at every head dim (`_get_fwd_config` starts every SM100 config at 128 x 128), and its fast path needs page size == key tile, so 128 is right for all of them. One exception: models with different q/k and v head dims (DeepSeek-V3's 192/128) switch to 64-key tiles when decode splits the KV, so split decode there stays on the gather path. Their prefill and unsplit decode still use 128-key tiles, so 128 is still the best single choice.

NOTE: 128-token pages make vLLM's prefix-cache reuse coarser (only full 128-token blocks are shared) and waste up to 127 tokens of KV per sequence. Not measured end to end.
NOTE: hybrid models with linear-attention layers (e.g. Kimi K3) align their attention page size to this value. Untested until the engine smoke below.

**Test plan**
- New `tests/rl/unit_tests/cpu/test_vllm_attention.py`: both backends pick 128 with FA4 and keep 16 with FA3 (4 passed).
- CI lint (pre-commit, all hooks) passes.
- GB300 engine smoke, 16 vs 128-token pages, on the Muse RL recipe and the Kimi K3 debug recipe: `<fill: engine start, KV block count, prefix-cache hit rate, trainer-generator logprob diff>`.
