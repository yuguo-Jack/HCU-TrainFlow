## Agent details

Written with Claude Code: the analysis, measurements and test plan below.

**TLDR:** When FA4 runs attention on SM100/SM103 (GB200/GB300, B200/B300), TorchTitan's vLLM generator now asks for 128-token KV pages instead of vLLM's 16, so FA4 loads K/V with one bulk copy (TMA) instead of a gather. Qwen3-8B TP2 engine (head dim 128): cached prefill -8% to -13%, fresh 16k prefill -3% to -4%; decode +1% to +5% slower at batch 1-8, -3% to +2% from batch 16 up (one noisy cell, below). Attention kernel: prefill -8% to -17%; head dim 64 decode (Muse Spark) -4% to -15% at batch >= 32, but up to +17% (+4 us) at batch 2-8 on some shapes. Outputs are bitwise identical.

```text
main:     16-token pages  -> FA4 gathers K/V page by page
this PR:  128-token pages -> one TMA copy per 128-key tile    (vLLM already does this for FA4 at head dim 256)
```

```python
# before: vLLM's FlashAttention backend default
get_supported_kernel_block_sizes() -> [MultipleOf(16)]      # head dim 256 already gets [128]
# after: TorchTitan's backends, when FA4 runs attention
get_supported_kernel_block_sizes() -> [128]
```

**Problem**
1. On SM100/SM103, FA4 loads paged K/V with TMA (the GPU's bulk-copy unit) only when one page holds exactly one 128-key tile (`page_size == tile_n`); other page sizes take a slower gather path.
2. vLLM picks 128-token pages itself only for FA4's head-dim-256 kernel (Qwen3.5); every other head dim gets 16.
3. TorchTitan's backends subclass vLLM's FlashAttention backends, so they inherit 16.
4. **Cost:** Qwen3-8B TP2, prefill 2048 new tokens on 16k cached: 31.7 ms at 16-token pages vs 29.3 ms at 128.

**Solution**
1. `_FA4PageSize.get_supported_kernel_block_sizes` returns `[128]` when `get_cuda_flash_attention_impl()` is `"FA4"`.
2. Both TorchTitan backends (`TorchTitanVarlenInnerAttentionBackend` and the DiffKV one) inherit it.
3. Unchanged: FA3/FA2 keep vLLM's choice; head dim 256 (Qwen3.5) already had 128. A hybrid model (GDN/KDA) at another head dim, e.g. the head-dim-64 debug model, now rounds its KV block up to a multiple of 128 (was 16) and splits it into 128-token pages.

- Small batches can lose: with split KV, FA4's paged-TMA path is 2-6 us slower per call at batch <= 32 on some shapes (head dim 64 Muse: bs4 x 8k 21.3 -> 25.0 us, +17%; worst across shapes, Llama 3.2 1B's head dim 64 32q/8kv: bs4 x 2k 17.5 -> 22.9 us, +31%). Both page sizes run the same 3 kernels (scheduler, forward, combine), so the loss is inside that path. At 32k context most small batches gain instead.
- In the engine, batch 1-8 is +1-5% slower; at the engine's exact shape (head dim 128, 16q/4kv) the kernel moves only at bs8 (+2.8 us), so the rest of the cause is not measured.
- On the installed FA4 4.0.0b36 wheel, head dim 128 (32q/8kv) shows the same picture: decode bs64 x 8k -3.7%, bs256 x 8k +1.6%, prefill 4 x 512 on 16k -13.7%.
- Training: not touched (generator only).

You may ask: why not pick the page size per head dim? FA4 on SM100/SM103 uses 128-key tiles at every head dim (`_get_fwd_config` starts every SM100 config at 128 x 128), and its fast path needs page size == key tile.
You may ask: why not set `block_size=128` in the engine kwargs, next to FA2's 256 (`engine.py:282-284`)? For hybrid models vLLM aligns the KV block to the linear-attention state (e.g. 1152 tokens) and then splits it into the kernel's supported page sizes (vLLM `platforms/interface.py:895-900` aligns, `v1/worker/utils.py:330-384` splits); only the backend hook makes those pages 128. It is also the rule vLLM itself uses for FA4 at head dim 256.

NOTE: 128-token pages make prefix-cache reuse coarser (whole 128-token blocks) and waste up to 127 KV slots per sequence.
NOTE: Under FA4, an explicit `block_size` in `extra_engine_args` that is not a multiple of 128 now fails at engine init (vLLM rejects the backend's block size). No recipe sets it.
NOTE: SM120 (consumer Blackwell) also reports FA4 and gets 128-token pages, but FA4's SM120 forward is its SM80 kernel, without TMA loads, so it pays the costs without the gain. Not measured.
NOTE: Models with different q/k and v head dims (DeepSeek-V3's 192/128) use 64-key tiles when decode splits the KV, so split decode there stays on the gather path; prefill and unsplit decode still use 128-key tiles.

**What this PR does.** Both TorchTitan vLLM attention backends now get `get_supported_kernel_block_sizes()` from a small mixin. It returns `[128]` when `get_cuda_flash_attention_impl()` is `"FA4"`; otherwise it defers to vLLM's FlashAttention default (`MultipleOf(16)`). Dense models now use 128-token KV pages under FA4. Hybrid models (GDN/KDA) still align their KV block to the linear-attention state, and vLLM then splits it into 128-token kernel pages.

**Example.**

  after:                                                                    -> 128  (one TMA copy per 128-key tile)
Hybrid head dim 64 + GDN, KV block aligned to 1152
  before: split into 16-token pages      after: split into 128-token pages
H100 (FA3) / A100 (FA2, block_size=256 in engine.py): unchanged

### Questions
- RL rollouts often end with a long tail of a few sequences still decoding (bs1-8), which is exactly where the engine numbers show +1-5%. Do you have an end-to-end rollout or `generate.py --benchmark` number on a long-tail workload, to confirm the prefill gains outweigh the small-batch decode loss?

<details><summary>Details</summary>

- Layer: the alternative, `block_size=128` in the engine kwargs, would not fix hybrid models. Their page size comes from the backend's supported kernel sizes after the KV block is aligned to the linear-attention state, so the backend hook is the correct and smallest place.
- MRO: `_FA4PageSize` comes before `FlashAttentionBackend` / `FlashAttentionDiffKVBackend`, so `super()` reaches vLLM's default for FA3/FA2. The parametrized CPU test covers both backends and so guards the mixin order. The `select_common_block_size(1152, ...)` test guards the hybrid split, which depends on vLLM's behavior. Both are cheap CPU tests.
- Process/CUDA init: the hook calls `torch.cuda.get_device_capability()`. The engine runs with `external_launcher` in a process where CUDA is already initialized (`engine.py:283` already calls `has_cuda_capability`), so this adds no fork-after-CUDA-init risk.
- `session_kv_holder.py` and `linear_attention.py` read `kv_cache_spec.block_size` generically, and FA2's forced `block_size=256` never runs under FA4. No other callsite assumes 16-token pages.

</details>

Not verified: the vLLM-side behavior of `get_preferred_block_size` / `select_common_block_size` and the current hook signature (vLLM source not readable here), and the GPU perf and bitwise-parity numbers.
