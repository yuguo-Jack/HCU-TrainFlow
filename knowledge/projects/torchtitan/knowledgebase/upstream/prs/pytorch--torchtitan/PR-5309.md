# [rl] Send each trainer DP rank only its column of the grid

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5309) · state: closed · merged: True

## Original PR description

**TLDR:** The controller called `trainer.forward_backward` on the whole trainer mesh with the step's whole `[num_microbatches][dp_degree]` grid, and each rank kept only its column. Now each trainer DP rank receives only its column. By value (the default), a 2.6 GB step at dp 4 goes from 5.3 to 2.1 s and peak memory per rank from 7.6 to 1.9 GB (CPU Monarch, one host, an earlier version of this PR). With RDMA handles each rank already reads just its column; this shrinks the handle message (41 -> 19 ms per call at dp 2, 1.5 s -> 22 ms with a dp-64 grid sent to 4 ranks on one host), so it matters at high DP.

**Problem**
1. The batcher packs each step as a `[num_microbatches][dp_degree]` grid: `TrainingMicrobatch`es by value, or `MonarchRDMAMicrobatch` handles (~5 KB each) with the fast path.
2. The controller calls `trainer.forward_backward` on the whole trainer mesh with the whole grid.
3. Every rank receives and unpickles every column, then keeps (or reads) only its own.
4. By value, each rank unpickles dp times the bytes it trains on. With handles, at dp 64 that is 14.4 MB per rank and ~1.5 s per call; at dp 2 it is 0.45 MB.

**Solution**
1. The trainer lays its ranks out as `(dp, cp, tp)`, and RL rejects PP, so the ranks at one DP rank are `cp * tp` consecutive ranks.
2. `Controller.setup_async` cuts the trainer mesh into one sub-mesh per DP rank with Monarch's `split`, once. It checks that layout once: each rank reports its DP rank through a new `get_dp_rank` endpoint, and setup raises if a sub-mesh's ranks don't all report its DP rank.
3. `Controller._trainer_loop` sends one call per DP rank, each with its column, and awaits them together. It reads rank 0's metrics as before.
4. `Trainer.forward_backward` takes that column, `microbatches: [num_microbatches]` (by value or handles), instead of the grid.
5. Unchanged: the batcher, the grid, the global loss and routing token counts, the reads, and every other trainer call.

```text
before: trainer[0..3].forward_backward(grid [M][2])               -> each of the 4 ranks receives M x 2 microbatches
after:  trainer[0, 1].forward_backward([row[0] for row in grid])  -> M each
        trainer[2, 3].forward_backward([row[1] for row in grid])  -> M each
```

**Results**

By value, CPU Monarch, one host, 2.6 GB step (an earlier version of this PR; a separate run from the RDMA PR's table):
```text
               per step         peak memory per rank
dp 2 x tp 2    5.0 -> 3.0 s     7.6 -> 3.8 GB
dp 4           5.3 -> 2.1 s     7.6 -> 1.9 GB
```
Handles, CPU Monarch, one host, 4 rank processes, 46 microbatches per DP rank, routed expert ids and top-32 logprobs in `model_kwargs`. Bytes are `len(cloudpickle.dumps(...))` of the grid vs one column; the call is a median of 5 to an endpoint that returns `len()`:
```text
          handles per rank           call to 4 ranks
dp        whole grid -> column       whole grid -> column
2         0.45 MB -> 0.22 MB         41 ms -> 19 ms
8         1.8 MB  -> 0.22 MB         153 ms -> 16 ms
32        7.2 MB  -> 0.22 MB         946 ms -> 20 ms
64        14.4 MB -> 0.22 MB         1475 ms -> 22 ms
```
- Summed over dp 64 x tp 4 ranks: 3.7 GB -> 58 MB per step (computed, not measured).
- These handles carry only TCP contexts; on ibverbs hosts and across hosts each is larger, so these bytes are a lower bound.

GPU, Qwen3-0.6B, H100, batch invariant, lockstep, one TP 1 generator, Monarch 0.7, 5 steps:
- Trainer DP 2 (3 GPUs), TCP, with RDMA buffers (an earlier version of this stack): `loss/mean` bitwise equal to main's DP 2 run at every step.
- The previous push of the whole stack, trainer DP 1 (2 GPUs): `loss/mean` with `rdma_min_tensor_bytes=1024` bitwise equal to a by-value run of an earlier push (same config and seed); `timing/trainer/read_microbatches/max` 147, 17, 10, 12, 15 ms at steps 1-5 (step 1 includes RDMA setup).

CPU mesh check: the controller's real setup and `_trainer_loop` code against real Monarch actor meshes, with a fake trainer that has the real DP-rank lines and a collective spanning DP ranks (an earlier version of this PR, same split and layout check):
- dp 2 x tp 2, dp 4, dp 1 x tp 4, dp 2 x cp 2, and HSDP 2 x 2 x 2 on a 2-level mesh: each rank got exactly its column every step, and rank 0's metrics came from global rank 0.
- With DP as the innermost dimension, the startup check raised.
- When one DP rank's call raised, the step raised within 20 ms and the batch release ran once.

You may ask:
- **Why not one call per rank?** Each column would be pickled `cp * tp` times on the controller's event loop.
- **Why slice by layout instead of asking each rank where it belongs?** A Monarch slice needs consecutive ranks anyway; the startup check turns a layout drift into an error instead of silently wrong gradients.
- **Why scatter handles too?** It's the same code on both paths; a by-value-only scatter would need `forward_backward` to take the grid again (a second signature or a shape branch).
- **Does it make the controller cheaper?** No: pickling 64 columns costs the same as one grid (0.43 vs 0.42 s at dp 64). It cuts what each rank receives and unpickles.

NOTE:
- The `cp * tp` ranks at one DP rank still each receive the same column (the read-once-and-broadcast TODO in `Trainer.forward_backward`).
- The GPU run is DP 2 x TP 1, so one rank sits at each DP rank; the CPU mesh check covers several ranks per DP rank.
- Not tested on more than one host.

**Test plan**
- `pytest tests/rl/unit_tests/cpu` (repo root, Monarch 0.7, merged with main): 498 passed, 5 skipped.
- `test_trainer.py`: `forward_backward` trains a column by value, and a column of `MonarchRDMAMicrobatch`es through the read-ahead prefetcher.
- GPU parity and the CPU mesh check above.
