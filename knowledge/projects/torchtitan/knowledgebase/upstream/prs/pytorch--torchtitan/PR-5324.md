# [ROCm] Add MORI-EP token dispatcher

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5324) · state: open · merged: False

## Original PR description

## Summary

Adds `MoriTokenDispatcher`, an expert-parallel token dispatcher backed by [MORI-EP](https://github.com/ROCm/mori), the AMD counterpart of DeepEP. It follows the structure of the existing DeepEP/HybridEP integration:

- `torchtitan/distributed/mori/mori.py` — `mori_ep::dispatch` / `mori_ep::combine` custom ops (with fake impls and registered backward), receiver-side expert-major layout, op/symmetric-memory construction.
- `MoriTokenDispatcher` in `models/common/token_dispatcher.py`, selected with `TokenDispatcherTransform(dispatcher=MoriTokenDispatcher, num_max_tokens_per_rank=...)`.
- Wired into config validation (requires EP > 1) and `swap_token_dispatcher`, which keeps MORI and sets `pad_multiple` when grouped GEMMs are quantized. Only the config path is tested: the MXFP8/NVFP4 grouped-GEMM kernels are not available on ROCm, so no quantized run was done. All runs below are bf16.
- `deepseek_v3_debugmodel_mori` test recipe.

## Why

On AMD GPUs, MoE training at large EP is dominated by the EP all-to-all. MORI sends each token **once per destination rank** instead of once per routed expert, and sums the per-rank partial outputs on the source rank (the DeepEP contract). It runs GPU-initiated kernels intra-node (XGMI) and over RDMA inter-node.

## Design notes

- **Pure-communication ops, layout in PyTorch.** As in `deepep.py`, the custom ops only move data. The gather into expert-major order (with optional padding) and the score-weighted reduction run in plain PyTorch, so autograd handles the routing-score gradient.
  - Dispatch backward is a MORI combine of the gradients. Passing the received score gradients as combine weights also reduces the routing-score gradients to their source tokens.
  - Combine backward is a MORI dispatch that replays the forward's routing handle.
- **Activation checkpointing.** MORI fills receive slots with atomics and has no deterministic mode. A replayed dispatch could therefore receive rows in a different order than the forward's routing handle records.
  - So the `ep_communication.dispatch` / `ep_communication.combine` regions are **always retained** (`recompute=False`), including under `FullAC`. If a policy asked to recompute them, it logs a warning once.
  - Expert compute and layout around the communication are still recomputed.
  - This also removes the replayed EP communication that `FullAC` otherwise costs.
- **Kernel selection.** The kernel follows the EP group's extent: `IntraNode` when the group fits on a node, `InterNodeV1` otherwise. EP ranks are innermost, so they're consecutive within a node.
- **Fixed per-process op.** One op and one shmem context per process, sized by `num_max_tokens_per_rank` (like DeepEP's `ElasticBuffer`). Buffers are bf16; the symmetric heap is sized by the `MORI_SHMEM_HEAP_SIZE` environment variable.
- **Shmem init.** `_init_shmem` re-implements `mori.shmem.shmem_torch_process_group_init` with a group-local broadcast source. The upstream helper passes a global `src=0`, so it fails for EP groups that don't contain global rank 0. I plan to report and fix this in MORI; once that's released, this can call the upstream helper.

## Requirements / known MORI issues

- MORI with ROCm/mori@28d4973f, the intra-node replay-dispatch fix. With `amd_mori==1.2.3.post1`, the intra-node combine-backward (a replayed dispatch) returns stale data. The tests here used 1.2.3.post1 with that fix applied.
- Inter-node on NICs without IBGDA support needs `MORI_ENABLE_HOST_PROXY=1` (and `MORI_ENABLE_DMABUF_REG=1` on our cluster).
- `InterNodeV1` reads the dispatch weights buffer without a null check, so the combine-backward passes zero weights rather than `None`.
- Not supported: TP/SP on the MoE (as with DeepEP), CUDA graphs (dispatch has a host sync for the received count), non-bf16 dispatch.

## Test plan

- [x] CPU:
  - `test_transforms.py`: the transform fills the MORI buffer fields; quantization swap keeps MORI with `pad_multiple`.
  - `test_config_validation.py`: MORI requires EP > 1.
  - `test_debug_config_defaults.py`: new recipe.
  - The config/quantization/recipe suites (271 tests) and `models/common` (214) pass.
- [x] `pre-commit run` on changed files.
- [x] GPU, `tests/unit_tests/gpu/distributed/test_mori_token_dispatcher.py`: 4× MI355X, ROCm 7.2, torch 2.15 nightly, `amd_mori` 1.2.3.post1 + 28d4973f. **3 passed.**
  - `test_matches_all_to_all`: output and all gradients (input, gate, expert weights) vs `AllToAllTokenDispatcher`, with and without `pad_multiple=32`. The maximum relative norm error is 3.7e-3 (bf16 summation order: MORI sums per-rank partials).
  - `test_ranks_without_received_tokens`: routes every token to EP rank 0's experts. Without the second commit's fix, the dispatch backward of a rank that received no tokens fails with `TypeError` (MORI returns no weight gradients for an empty weights tensor).
  - `test_activation_checkpointing_never_replays_communication`: `FullAC`, `RegionAC([])`, `RegionAC(["*ep_communication"])` and `SelectiveAC` each issue exactly 2 MORI dispatches and 2 combines per forward/backward (no replays), and gradients match the run without AC.
  - The GPU tests ran on a revision before one later change: logging the retained-communication warning once per process instead of once per layer. That change doesn't touch the tested code paths.
- [x] **Cross-node parity**, using this branch's `MoriTokenDispatcher` vs `AllToAllTokenDispatcher` on the same inputs and weights (256 experts, top-8, 4096 tokens/GPU, bf16):
  - **EP16** on 2 nodes × 8 MI355X (`InterNodeV1`): loss within 6e-6, gradients (input, router, expert weights) within 2–4e-3 relative.
  - **EP32** on 4 nodes × 8 MI355X: single layer, loss within 1.2e-5 and gradients within 3.6e-3. With 3 stacked layers, the deeper layers differ more (up to 0.14 on the router gradient) because bf16 differences flip near-tied top-8 choices; the loss stays within 7e-5.
- [x] **End-to-end training parity (bf16, no quantization).** DeepSeek-V3 debug model, EP4 × FSDP on 8 MI355X, region-based full recompute (`RegionAC(save_regions=[])`, equivalent to `FullAC` on current `main`), 100 steps, seed 42, 4 runs per arm.
  - Environment: training on current `main` needs a newer torch than the ROCm 7.2 nightlies provide (the FSDP `MixedPrecisionPolicy` API is missing). So these runs cherry-pick this PR's two commits onto 88759f1f, the commit before #5068, with torch 2.15 ROCm. The MORI code is byte-identical to this branch.
  - Results:

    | | mean loss, steps 76–100 (4 runs) | tokens/s (median, steps 21–100) | peak memory |
    |---|---|---|---|
    | `AllToAllTokenDispatcher` | 2.7624 ± 0.0048 | ~126k | 1.42 GiB |
    | `MoriTokenDispatcher` | 2.7638 ± 0.0061 | ~134k | 1.59–1.71 GiB |

  - Step 1 is identical in both arms (loss 8.04307, grad norm 3.8780). The difference in mean loss is within run-to-run noise.
  - MORI's extra memory is the retained `ep_communication` outputs.
  - **Qwen3 MoE debug model** (64 experts, top-8; the model upstream's `qwen3_moe_deepep` recipe uses), bf16, EP4 × FSDP, same setup, 5 seeds, all-to-all and MORI run back to back on the same node per seed:

    | Seed | All-to-all, mean loss 76–100 | MORI | MORI − all-to-all |
    |---|---|---|---|
    | 1 | 2.8756 | 2.8735 | −0.0021 |
    | 2 | 2.8691 | 2.8692 | +0.0001 |
    | 3 | 2.8448 | 2.8466 | +0.0018 |
    | 4 | 2.8561 | 2.8500 | −0.0060 |
    | 5 | 2.8602 | 2.8592 | −0.0010 |

    - Paired difference: −0.0014 ± 0.0030, mixed sign; step-1 loss matches to 5 decimals for every seed. Throughput ~53k vs ~48k tokens/s.
    - At this model's MoE shape, an isolated layer is equally accurate in both paths against an fp32 reference: relative error ~3.9% from the bf16 expert GEMMs, with the same signed bias for the output and the input, router and expert gradients.
  - On that older base, the then-operator-level `SelectiveAC`/`FullAC` (`torch.utils.checkpoint` with an op save list) replays MORI dispatch and leaks the forward's routing handles. On current `main`, all AC policies are region-based, and the GPU tests above verify they never replay MORI communication.
