# [RL] Checkpoint prompt data state

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5114) · state: closed · merged: True

## Original PR description

## Why

RL prompt consumption currently lives outside the trainer checkpoint, so a resumed job can repeat or skip prompts even when model and optimizer state are restored. The checkpointer also owns the core dataloader as a special case, which makes it difficult to checkpoint controller-owned workflow state atomically.

## What

- let trainers register dataloader and workflow state through `extra_states`
- add configurable `RLDataset` and `RLDataLoader` base classes, plus iterable and map-style checkpointable loaders
- preserve the original iterable behavior of the built-in RL datasets
- mirror controller-owned dataloader state into the trainer checkpoint before each optimizer step
- replay yielded-but-unacknowledged samples before consuming new inputs after resume
- carry group IDs through batching so metric-only groups are acknowledged too
- bound validation with pretraining-style `validation.steps` without requiring map-style data
- update DCP, torch-checkpointing, and TorchFT integrations to use the shared state map

The RL dataloader state is saved in the same checkpoint transaction as the trainer step. Acknowledgement happens only at that transaction boundary, after all consumed groups—including metric-only groups—have been accounted for.

## API notes

- `Rollouter.Config` uses `training_dataloader` and `validation_dataset`
- both dataloaders and datasets are nominal, configurable base classes
- custom streaming, generated, or mixed datasets can implement their cursor/RNG state in an `RLDataset` and use `IterableRLDataLoader`, or provide a custom `RLDataLoader`
- RL trainer endpoints match `TrainingEngine`: `forward_backward()` and `optim_step()`

- tianyu-l · comment · 2026-10-08T23:49:42Z · [source](https://github.com/pytorch/torchtitan/pull/5114#discussion_r4225290862)

File: `torchtitan/rl/components/data.py` · line 141

**what agent said:**

I audited `SingleDatasetConfig` and `GrainDataLoader` against the RL data path. I don't think we can replace `RLDataLoader` with `GrainDataLoader` directly: the pretraining loader checkpoints its consumption cursor and emits collated `TrainingMicrobatch` objects, while RL consumes prompts ahead of the optimizer/checkpoint transaction and therefore needs an explicit acknowledgement ledger plus replay of every unacknowledged prompt.

The missing DP rank/degree is intentional here. This loader lives in the singleton controller; completed samples are partitioned across trainer DP ranks later by the RL batcher. Applying trainer DP sharding at prompt ingestion would change the global prompt stream rather than distribute a per-rank trainer loader.

There is still useful reuse at the dataset/source layer, but today's interfaces do not line up cleanly: pretraining `DatasetConfig.build()` requires a trainer-oriented build context and iteration policy, and `GrainDataLoader` adds batching, collation, tokenizer context, prefetching, and DP sharding. Several RL datasets are also stateful infinite generators. My recommendation is to keep the acknowledgement-aware RL loader in this PR and converge on a shared unbatched Grain dataset-construction layer in a follow-up, rather than make core pretraining abstractions accommodate RL-specific transaction semantics.

- tianyu-l · comment · 2026-10-08T23:49:44Z · [source](https://github.com/pytorch/torchtitan/pull/5114#discussion_r4225291017)

File: `torchtitan/rl/components/data.py` · line 111

Serializing only `_replay` would lose `_pending`, which contains prompts already handed to rollout work but not yet committed at an optimizer/checkpoint boundary. More importantly, after load both runtime buckets must become replayable: restoring old `_pending` entries as pending would strand them because the caller would never receive them again. The checkpoint therefore intentionally stores the union of pending and replay IDs, ordered by the globally increasing ID, and restores the union into `_replay`. For the map-style loader the payload is deterministic random access, so only those IDs need to be stored.

- tianyu-l · comment · 2026-10-08T23:49:46Z · [source](https://github.com/pytorch/torchtitan/pull/5114#discussion_r4225291177)

File: `torchtitan/rl/components/data.py` · line 200

The distinction between `_pending` and `_replay` is runtime-only and should not be recovered exactly. Every unacknowledged item must be yielded again after a restart, including items that were `_pending` at the crash, so load deliberately collapses both collections into an ordered replay queue. Restoring `_pending` as-is would make those samples wait for acknowledgements without ever being reissued.

The full controller state is already serialized as one opaque value by `MirroredState`, so these sample payloads are serialized. Keeping a versioned, explicit state dict inside that value gives us validation and a migration point instead of coupling the checkpoint format to the current container implementation. (`torch` also has `torch.save`, but no `torch.dumps`; if you meant pickle/`torch.save`, that outer serialization is already happening.)
