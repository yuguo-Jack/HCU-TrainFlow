## Why
#5468 made DistMuon's startup planning about 4x slower. For the Kimi K3 non-routed layers on 128 ranks (16 layers, CPU, fake process group), building DistMuon went from 1.8 s to 7.2 s with stacked w13 stored `Shard(1)` (torchtitan's FSDP placement for it), and from 1.6 s to 5.9 s with `Shard(0)`. Every rank runs this planning at startup. Four loops grow with the number of ranks:

- Routing: `_build_region_redistribution_plan` intersects every storage region with every compute chunk of a parameter.
- Placement: `_assign_balanced_compute_regions` scans all storage regions for each chunk, and then takes a min over all ranks for each chunk.
- Validation: `_validate_redistribution_plan` filters the full route list once per participant. Its overlap check only cuts the scan short along dim 0, so it compares every pair when all regions start at row 0, as w13 `Shard(1)` routes do.
- Storage geometry: `_device_mesh_coordinate` finds each participant with a list lookup in the flattened mesh, so it takes ranks^2 steps per parameter.

## What changed
Each change gives the same result as the code it replaces:
- Routing: compute chunks are disjoint row ranges that span every trailing dim (the planner validates this). So each storage region bisects to the chunks whose rows overlap its own, and visits them in their original order.
- Placement: ranks that store none of a chunk differ only in loads and bytes, so a heap gives the best of them. Only ranks that store part of the chunk are compared on locality. When storage holds disjoint row ranges, as with FSDP `Shard(0)`, each chunk bisects to the storage regions it overlaps; otherwise it still scans them all.
- Validation: routes are grouped by participant in one pass. The overlap check sweeps along the dim with the most distinct region starts, not always dim 0.
- Storage geometry: `_device_mesh_coordinates` maps every rank of the mesh to its coordinate in one pass. It replaces the per-participant `_device_mesh_coordinate`.

## Alternatives considered
- Skip `_validate_redistribution_plan` during planning: it is about 1 s of the remaining 2.6 s, but it is the check that stops a malformed plan from silently moving the wrong elements.

## Numerics
None: placements, plans, schedules, Newton-Schulz views and row scales are identical.

## Testing
- Plan identity: dumped every bucket plan, packed schedule, Newton-Schulz view and row scale for the Kimi K3 non-routed layers (fake process group). The 10 configs are 8 ranks x 4 layers, 64 x 8 and 128 x 16, on rank 0 and the last rank, with w13 stored `Shard(1)` and `Shard(0)`. The dumps match before and after this PR in all 10.
- Planning time (DistMuon construction, 128 ranks, 16 layers, CPU, fake process group):

  | | w13 `Shard(1)` | w13 `Shard(0)` |
  | --- | --- | --- |
  | before #5468 | 1.8 s | 1.6 s |
  | main | 7.2 s | 5.9 s |
  | this PR | 2.6 s | 2.2 s |

- The new overlap check agrees with an all-pairs check on 200,000 random region sets (0-3 dims, up to 7 regions; 85,599 of them overlap).
- `pytest tests/unit_tests/gpu/distributed/flex_shard/test_dist_muon.py tests/unit_tests/cpu/distributed/flex_shard`: 21 passed.

## Known issues / follow-ups
- Planning is still slower than before #5468. #5468 builds one region plan per parameter (184 here, against 100 shared plans before), and the remaining time is spread over routing, validation and the packed all-to-all schedule.
