## Why

Kimi K3 uses bounded SiTU-GLU. The shared Dist-MoE transform rejects it, ordinary
1F1B lacks a slot plan, and dynamic pipeline metadata inference can route
uninitialized values through a capacity-bounded backend. Planner overflow also
needs to fail before the optimizer commits an update.

**Example.**

```python
from torchtitan_recipes.tests.models.kimi_k3 import (
    kimi_k3_debugmodel_dist_moe_mxfp8,
)

# Preserve the source SiTU-GLU gate/up bounds. The shared runtime selects
# activation="situ_glu", situ_glu_gate_beta, and situ_glu_up_beta.
config = kimi_k3_debugmodel_dist_moe_mxfp8()
```

## What changed

- Translate SiTU-GLU to the clean public BF16/MXFP8 API. Both TorchTitan and
  native configuration use `situ_glu_gate_beta` / `situ_glu_up_beta`; clamped
  SwiGLU reads upstream's `alpha` / `limit` fields.
- Plan ordinary 1F1B/GPipe slots alongside native multi-stage liveness analysis.
- Register stage metadata contexts for eager PP and GraphPP, keep routing
  suppressed through backward metadata recomputation, and clear/reset before
  real execution or tracing.
- Describe CP-local Kimi carrier boundaries without full-pipeline execution;
  TP-sharded boundaries retain dynamic inference.
- Reuse compatible carriers while preserving independent input-gradient leaves.
- Finish the asynchronous native capacity check before optimizer mutation.
- Add small Kimi BF16/MXFP8 recipes and real-PG B200 integration configurations.
  Moving optional-dependency recipe helpers out of DeepSeek is mechanical.

## Alternatives considered

- Duplicating expert math or dispatch in Kimi would bypass the shared backend.
- Routing setup placeholders can corrupt the planner; metadata needs no expert
  values.
- Checking overflow after optimization commits an invalid update too late.
- A Python quantized-weight cache can make replay use pre-update weights;
  FSDP keeps its existing unshard-lifetime operands, and non-FSDP execution
  prepares live weights on each call.

## User-facing changes

| Before | After |
| --- | --- |
| The transform rejects SiTU-GLU. | Both expert precisions preserve its gate/up bounds through the public API. |
| Ordinary 1F1B has no slot policy; metadata can enter routing. | Slots match live activations; metadata bypasses routing until cleanup. |
| Capacity checks are outside the optimizer boundary. | Overflow raises before parameters or completed-step state change. |

Requires the optional public Dist-MoE package exposing `activation="situ_glu"`,
`situ_glu_gate_beta`, `situ_glu_up_beta`, and `max_num_local_input_tokens`.
Normal TorchTitan imports remain optional-dependency-safe.

## Numerics

Backend kernels are unchanged. Fresh GPU-0-only EP1 probes on this restack:

| Probe | Result |
| --- | --- |
| BF16 SwiGLU and SiTU-GLU versus stock | Output and four gradient families pass at the existing 1e-4 tolerance. |
| MXFP8 SiTU-GLU versus native, saved-factor None and 1.0 | Exact output, input/score gradients, and W13/W2 gradients; native capacity checks pass. |
| Static CP-local carriers versus inferred metadata, three CPU updates | Exact losses, gradient norms, and every parameter gradient. |

Historical validation of the original prefix—not rerun on this one-GPU review—
includes three EP2 numerical tests and five-update FSDP2/EP2 eager/graph parity
for BF16/MXFP8 with NoAC and FullAC. These are shared-backend checks, not full-K3
PP/CP convergence or performance evidence.
