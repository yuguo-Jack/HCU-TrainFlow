# [TorchTitan] Use unquantized GPT-OSS expert names unless loading MXFP4

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5064) · state: open · merged: False

## Original PR description


Summary:
With E experts, D = hidden dim, and F = expert hidden dim, TorchTitan stores
the gate/up projections (D -> F) as `w13.weight [E, 2, F, D]` and the down
projection (F -> D) as `w2.weight [E, D, F]`: output size first, like
nn.Linear. `GptOssStateDictAdapter.to_hf` always emitted the MXFP4 names
`gate_up_proj_blocks` and `down_proj_blocks` in that layout, which is what the
quantized reader dequantizes to. That is only right for a quantized load.
Unquantized GPT-OSS checkpoints (and HF transformers, which computes x @ W)
name these `gate_up_proj [E, D, 2F]` and `down_proj [E, F, D]`, input size
first; `unsloth/gpt-oss-20b-BF16` has `gate_up_proj [32, 2880, 5760]`. So a
bf16 GPT-OSS checkpoint could not be loaded, and `last_save_in_hf` wrote
tensors under MXFP4 names with the wrong layout.

`to_hf` now uses the unquantized names and layout by default, and the
`_blocks` names with the TorchTitan layout when `to_quantized_layout=True`.
`from_hf` with `is_quantized_layout=True` reads only those names, so both
directions share one name map (`from_hf_map` or `from_hf_map_quantized`).
The biases have the same names in both formats.

The released checkpoint's `model.safetensors.index.json` names the MXFP4
tensors, so `fqn_to_index_mapping` maps `X_blocks` to `X` and drops
`X_scales`. HF saves keep the released file sharding.

Test Plan:
```
pytest -q tests/unit_tests/cpu/models/test_state_dict_adapter.py tests/unit_tests/cpu/components/checkpointer/test_checkpoint.py
SKIP=lychee-link-checker pre-commit run --files tests/unit_tests/cpu/models/test_state_dict_adapter.py torchtitan/models/gpt_oss/state_dict_adapter.py
```
87 passed, and pre-commit passes. The GPT-OSS round trip now runs with
the quantized layout off and on. It checks that the quantized expert weights
are the transpose of the unquantized ones, and that `from_hf` with a
mismatched flag leaves the expert weights out.
A new test covers the index remapping. Expert names and shapes were checked
against the `unsloth/gpt-oss-20b-BF16` safetensors headers.

This change was written with the help of an AI assistant.

**Summary:** The fix is correct and the layout table above the class constants is very helpful. I traced every path that reaches the adapter:
- `dcp.py:388-399` (load) passes the same `from_quantized` to `to_hf`, `get_hf_storage_reader`, and `from_hf`, so the two name maps are always used as a matching pair.
- `dcp.py:289` and `torch_checkpointing.py:575` (HF save) call `to_hf(state_dict)` with the default `False`. That matches the unquantized `fqn_to_index_mapping` you build in `__init__`.
- `torch_checkpointing.py:346` already rejects `from_quantized`, and the torchft experiment passes `False`. No other callsites, and nothing under `scripts/` uses this adapter.

If the config flag doesn't match the checkpoint, the load should fail loudly rather than load bad weights. With `False` on the MXFP4 release, `HuggingFaceStorageReader` can't find `gate_up_proj`. With `True` on a bf16 checkpoint, the quantized reader can't find `_blocks`. DCP's default planner raises in both cases.

I have one compatibility concern and a few minor points.

### 1. Old TorchTitan HF saves stop loading (please call this out)

Before this PR, `last_save_in_hf=True` wrote bf16 tensors named `gate_up_proj_blocks` / `down_proj_blocks` in the TorchTitan layout, with no `_scales`. Those checkpoints loaded back fine with `initial_load_in_hf_quantized=False`, because `to_hf` asked for the same `_blocks` names. After this PR, they fail both ways:
- `from_quantized=False` looks for `gate_up_proj`, which doesn't exist.
- `from_quantized=True` uses `QuantizedHuggingFaceStorageReader`, which expects `_scales` tensors.

Those files were never valid HF checkpoints, so breaking them is reasonable. Per the "protect battle-tested code paths" rule, though, please state the break in the PR description. Something like this would do: *"GPT-OSS HF checkpoints saved by TorchTitan before this change use the `_blocks` names in the TorchTitan layout and won't load; rename and transpose the expert weights, or re-export from a DCP checkpoint."* A short conversion snippet would help anyone affected.

### 2. Expert weights are now saved as non-contiguous views (worth checking on a real save)

`state_dict_adapter.py:162-168`: on the unquantized path, both expert weights reach the storage writer as `transpose(1, 2)` views. Previously `w13` was contiguous (the earlier `flatten` copies it) and `w2` went through unchanged. Loading is fine: DCP copies into the view, so the data lands in the storage that `from_hf` transposes back. Saving has no coverage, though: the unit tests only round-trip in memory and never use `HuggingFaceStorageWriter` or the safetensors consolidation. Please run one `last_save_in_hf` on the debug model, ideally with FSDP or EP so the `Shard(0)` DTensor path is exercised. Then confirm the output loads in `transformers` (or at least that the safetensors headers show `[E, D, 2F]` / `[E, F, D]`). If the writer doesn't make tensors contiguous itself, add `.contiguous()` on the save path.

### 3. Minor points

- **Repeated condition.** `state_dict_adapter.py:162-164` and `:201-204` both test `tt_key in (self._W13_WEIGHT_KEY, self._W2_WEIGHT_KEY) and not from_quantized`. A class constant `_EXPERT_WEIGHT_KEYS` would remove the repetition, and the local `expert_weight_keys` at `:92` could use it too.
- **`_scales` filter is broad.** `:55-60` drops every index key ending in `_scales` and strips `_blocks` from every key. That's fine for today's GPT-OSS names, but anchoring both to `.mlp.experts.` would make the intent explicit. Optional.
- **Comment wording.** `:52`, "only HF saves read it": the load path never uses the mapping, so this is accurate. Saying "only `to_hf` saves (`last_save_in_hf`) read it" would point readers to the callsite.
- **Tests.** `test_released_index_maps_to_unquantized_names` is a good addition. One gap: if `to_hf(False)` ever emitted a `_blocks` key, it would be absent from `fqn_to_index_mapping`. You could add a check that every key from `to_hf(state_dict)` is in the remapped mapping when the index holds all expert names.

### 4. On @tianyu-l's earlier question (option 2 in #4996)

I couldn't open the issue comment from this environment, so I can't compare against option 2 directly. On its own terms, this PR's approach of choosing the name map from `from_quantized` costs little: it uses the flag the checkpointer already threads through, and HF saves always produce real bf16 HF checkpoints. If option 2 was "always emit unquantized names and have the quantized reader translate them", that would move this mapping into PyTorch's `QuantizedHuggingFaceStorageReader`. This PR avoids that cross-repo change.

**Verdict:** The change looks good. My main requests are to document the break in (1) and run the real-save check in (2). I didn't run the tests or pre-commit, because this environment doesn't allow Python or `pip` commands.
