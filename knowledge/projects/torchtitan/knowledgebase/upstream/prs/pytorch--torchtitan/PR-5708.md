## Agent details

Written with Claude Code: the analysis, measurements and test plan below.

**TLDR:** DeepEP training now dispatches into DeepEP's expand layout, whose rows are already grouped by expert. That deletes the eager gather before the grouped GEMM, the bf16 `scatter_add_` after it, and their host syncs.
- **Numerics:** not bitwise, but within rounding. A token's expert rows are now summed in fp32 inside DeepEP's combine, instead of by bf16 adds. On one MoE layer of 5 models at EP 2, the change is 0.4-0.6x of the compile yardstick and every weight grad stays bitwise. The generator's output stays bitwise.
- **Memory:** kept for backward stays at base (2-10 MiB per layer below it).
- **Speed:** one MoE layer fwd+bwd at EP 2, default remat: DeepSeek-V3 671B 5-8% faster, Qwen3.5-35B-A3B 18-27% faster.

```text
base:    dispatch (compact) -> gather + sort (host syncs) -> experts -> * scores -> scatter_add_ (bf16) -> combine
this PR: dispatch (expand) ---------------------------------> experts -> * scores -> combine (sums a token's rows in fp32)
```

```python
# before: _dispatch_op_impl
do_expand=cuda_graph_compatible,      # training: compact, then _permute_tokens in eager
# after
do_expand=True,                       # backward-safe: get_buffer sets allow_multiple_reduction=True
do_cpu_sync=not cuda_graph_compatible,
```

**Problem**
1. DeepEP v2's dispatch has two layouts. Compact: one row per received token. Expand: one row per (token, local expert) pick, grouped by expert.
2. Training used compact. `deepep.py` kept expand for inference only, quoting a DeepEP kernel assert ("must not be backward").
3. So `_permute_tokens` expanded and sorted the rows in eager before the grouped GEMM: a boolean-mask gather, an argsort, `repeat_interleave`, `index_select`. The masks and `repeat_interleave` sync with the host.
4. After the experts, `_unpermute_tokens` summed each token's rows with a bf16 `scatter_add_`. It rounds after every add, and it is non-deterministic outside torch's deterministic mode.
5. The generator already used expand, so the trainer's forward and the generator's forward differed.
6. **Cost.** On Qwen3.5 at 16k tokens per rank, removing them saves 2.2 of the layer's 10.8 ms (eager fwd+bwd, no remat).

**Solution**
1. **Expand is backward-safe when combine sums locally.** DeepEP's assert fires only when combine sends expanded rows without summing them first (`deep_ep/impls/combine.cuh:42`, assert at `:69`). With `allow_multiple_reduction=True` (the `ElasticBuffer` default, now passed explicitly in `get_buffer`), combine sums a token's rows on the expert rank first and accepts one score per row.
2. **The dispatch op always passes `do_expand=True`.** `cuda_graph_compatible` now only picks `do_cpu_sync`. Combine's backward re-dispatches with `do_expand=True` too.
3. **Remat keeps one row per received token.** In expand, a token that picked several of this rank's experts arrives as identical rows. Saved-tensor hooks (`_OneRowPerTokenHooks`) keep each token once plus a row-to-token index, and rebuild the rows with a gather in replay, bitwise. Without remat they never run.
4. **Deleted:** `_permute_tokens`, `_unpermute_tokens`, the compact fields of `DispatchState`, and the op's `recv_topk_idx` output.
5. **Unchanged:** `cuda_graph_compatible=True` stays inference-only. Without a host sync, `recv_x` reserves up to `ep_size` times the routed rows: too many to keep for backward. Scores are still applied in `combine_tokens`.

**Numerics: not bitwise; within rounding, and closer to fp64 than base**

Why: only one step changes, the sum of a token's expert rows on each rank.
- Base: a bf16 `scatter_add_`, one rounding per added row.
- This PR: DeepEP's combine, fp32 accumulation, one rounding (`deep_ep/impls/combine_utils.cuh:115-165`).
- Tokens with at most 2 rows on a rank get the same result in both: DeepEP then uses one bf16 add (`combine_utils.cuh:68-70`).
- CPU check of the sum alone (4 ranks x 4 rows per token, bf16 rows), rel L2 vs fp64: base 3.1e-3, this PR 2.4e-3.

You may ask:
- **Why saved-tensor hooks, not the compact layout under remat?** Compact would bring back the gather, its host syncs, and a second `DispatchState` layout. The hooks are torch_remat's API for storing a kept tensor in another form.
- **Why not skip the host sync in training too (`do_cpu_sync=False`)?** `recv_x` and the expert activations would be up to `ep_size` times larger, and autograd keeps them for backward.
- **How do we know combine returns rows to the right tokens?** A new 2-GPU test checks the output and every grad against the all-to-all dispatcher. In the matrix, every weight grad is bitwise vs base on 5 models.
- **And a remat policy that also saves `w13`?** Then `w13` keeps the expand rows itself, on top of the hooks' copy: about +441 MiB per DeepSeek-V3 layer at 16k. Main keeps the same extra rows in that case. No in-tree DeepEP config uses such a policy.

NOTE:
- Not run: multi-node, which uses DeepEP's hybrid kernels. Their combine has the same expand + local-sum branch (`hybrid_combine.cuh:48, 117-119, 305-313`). EP > 2 ran only for Kimi K3 (EP 4, GB300) and in the H100 CI (FSDP 4 x EP 4).
- The hooks are torch_remat's. GraphTrainer's graph-level memory policy doesn't run them, so a traced expand dispatch there would keep one row per pick.
- The hooks read DeepEP's `recv_src_metadata[:, 2:]`, an internal layout. A TODO in the code asks DeepEP to expose the row-to-token map.
