# [rl] Move weight-sync draining from the router into the generator

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5253) · state: open · merged: False

## Original PR description

**Problem:** with `hot_swap=False`, `InterGeneratorRouter` marks every generator SYNCING at once while it drains. Every turn sent during the sync goes to the first generator back, and the sticky strategy re-pins those sessions there for good. #5218 fixes this inside the router (a pinned turn waits for its own generator). This PR is a simpler alternative: take draining out of the router.

**Solution:** drain inside the generator. The engine loop already chooses between admitting requests and applying a pull, and rank 0 already tracks every outstanding generation across DP ranks. With the new `VLLMGenerator.Config.drain_on_weight_sync`, a pending pull:
1. keeps stepping the running requests and holds new ones (it admits nothing),
2. is applied once nothing is running,
3. then the held requests are admitted and run under the new weights.

The router never changes its candidate set anymore, so a session stays on its generator and the re-pinning problem can't happen. Removed from the router: `Config.hot_swap`, `_GeneratorState`, the per-generator `idle` event, `_serving`, `_candidates()`, `_set_state()`. A weight sync is now prefetch, then pull.

**Behavior changes**
- Default (`drain_on_weight_sync=False`, i.e. the old `hot_swap=True`): unchanged. With hot swap on, the removed router code never ran.
- Config: `InterGeneratorRouter.Config.hot_swap=False` becomes `VLLMGenerator.Config.drain_on_weight_sync=True`. No recipe sets `hot_swap=False` today.
- A new session that starts during a sync can land on a generator that is still draining and wait for it, instead of going to the first generator back. Turns of existing sessions wait for their own generator, as in #5218.
- A request that has reached the generator but not started when the pull arrives now runs under the new weights. With the router's drain it would have run under the old ones.
- The router's `router_drain_wait` span is gone. The generator's `pull_model_state_dict` span now covers drain plus apply, and `pull_model_state_dict_copy` is the apply alone.

**Test plan**
- `pytest tests/rl/unit_tests/cpu`: 511 passed, 8 skipped.
- New `test_drain_holds_requests_until_running_ones_finish`: decision-level test. The pull stays pending while a request runs, then is applied, then the held request is admitted.
- New `test_drain_on_weight_sync_finishes_running_requests_before_the_pull`: engine-thread test, run with drain on and off. With drain on, the running request finishes under the old version and the held one runs under the new version. With drain off, the pull lands mid-request.
- Router: removed the 9 drain tests. Added `test_sticky_session_stays_on_its_generator_during_a_pull` and `test_pull_failure_propagates`.
- `pre-commit run` on the changed files, with `pyrefly` skipped (`torchtitan/rl` and tests are in pyrefly's `project-excludes`).
- Not run on GPUs, and not tested with more than one DP rank (the CPU fake engine has a single rank). With DP > 1, the drain relies on rank 0's outstanding-generation tracking, which already covers peer ranks.
