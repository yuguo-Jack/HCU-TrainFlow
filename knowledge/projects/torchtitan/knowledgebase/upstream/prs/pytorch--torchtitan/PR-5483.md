# [rl] Verifiers env server: torch-free workers, smaller glibc footprint

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5483) · state: open · merged: False

## Original PR description

**TLDR:** Verifiers env-server workers no longer load torch, and they give a finished episode's memory back to the OS. Each worker, after it builds the Qwen3.5 renderer, goes from 776 to 341 MB of anonymous memory (RSS 1,163 -> 384 MB): ~7 GB per host for the Terminal-Bench recipes' 16 workers (estimate: 16 x 435 MB).

**Problem**
1. The env server runs its pool workers on the controller host: 16 in the Terminal-Bench recipes. An elastic pool adds a worker for every `multiplex` rollouts in flight.
2. **Torch.** Each worker builds a renderer, whose tokenizer loads through `transformers.AutoTokenizer`. In transformers 5.19 that import pulls in torch: ~435 MB of anonymous memory per worker, never used.
3. **Peak RSS.** Workers render on threads, glibc gives threads their own malloc pools (arenas), and by default it keeps the memory those threads free.
4. **Cost:** 16 x 435 MB = ~7 GB per host from torch alone (estimate). A pool with ~4,400 rollouts in flight at `multiplex=8` would have ~600 workers, ~260 GB (estimate).

**Solution**
1. The worker hook `setup_env_server_worker` (torch-free `worker_setup.py`) now sets `sys.modules["torch"] = None` first. Verifiers runs this hook in every worker before it builds the renderer.
2. `import torch` then raises ImportError, and transformers loads the tokenizer without it. The env-server process already imported torch through torchtitan, so the hook leaves torch alone there.
3. Before it spawns workers, `_run_env_server_process` sets `MALLOC_ARENA_MAX=2`, `MALLOC_MMAP_THRESHOLD_=65536` (every block of 64 KB or more gets its own mmap and goes back to the OS when freed) and `MALLOC_TRIM_THRESHOLD_=0` (free memory at the top of a heap goes back at once). glibc reads them when a worker starts.
4. The arena cap is assigned, not defaulted: the env-server process inherits the controller host's own cap (16 once the per-role arena caps land), and the workers need 2. A launcher's two thresholds still win.
5. Unchanged: the controller, trainer and generators, and the env-server process itself.

**Results**
```text
One worker after building the Qwen3.5 renderer and rendering a prompt.
CPU, real VerifiersEnvServer with 2 pool workers, Qwen/Qwen3.5-27B tokenizer, read from /proc/<pid>.
                       main        this PR
RssAnon (anonymous)    776 MB  ->  341 MB
VmRSS                1,163 MB  ->  384 MB
libtorch_cpu mapped      yes   ->  no
```

```text
The glibc variables. Churn test: 8 threads, 8 episodes of 62k tokens alive at a time, 48 in total.
3-4 runs each, RSS above the 166 MB baseline.
                              glibc default        2 arenas + 64 KB threshold
peak                          +475..506 MB    ->   +184..226 MB
after every episode is freed  +147..306 MB    ->    +33..36 MB
wall time (CPU-bound)         9.6 s           ->   11.4-12.3 s
```
The extra CPU time: blocks of 64 KB or more become mmap/munmap pairs. Workers mostly wait on the model and the sandboxes.

You may ask:
- Why not `USE_TORCH=0`? transformers 5.19 still imports torch with it.
- Why in the `log_setup` hook? It is the only hook Verifiers runs in every worker before the renderer exists. Workers are fresh `spawn` interpreters, so setting `sys.modules` in the env-server process doesn't reach them.
- Why not `malloc_trim(0)` after each episode? The variables match it with no code: after the episodes end, +23..25 MB with a trim per episode vs +23..33 MB with the variables (single thread, 3 runs).
- Why `MALLOC_TRIM_THRESHOLD_` too? The churn numbers came out the same without it, but it costs one line and matches the settings of the long Terminal-Bench runs.

NOTE:
- A worker now fails with ImportError if it imports torch. `datasets.Dataset.map` and `IterableDataset` iteration fail too: they import torch whenever `"torch" in sys.modules`, which the block makes true. Workers build tasks from the request and never load data; the Terminal-Bench taskset is torch-free (tested).
- The DAPO-Math taskset imports torch, so its recipe must keep `num_workers=1`, where the env-server process serves rollouts itself and keeps torch.
- Not run: a GPU RL run. The numbers above were measured before the rebase onto the taskset-alias fix.

Without the block, importing `AutoTokenizer` alone loads torch.
