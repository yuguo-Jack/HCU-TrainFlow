# [profiler] Add always-on CUDA kernel span collection with Cuspy

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5792) · state: open · merged: False

## Original PR description

Stack from [ghstack](https://github.com/ezyang/ghstack/tree/0.15.0) (oldest at bottom):
* __->__ #5792

Add Profiler.Config.kernel_span_ring: every training step, each rank records
every CUDA kernel's GPU start/end time, CUDA graph node id and stream with a
Cuspy observer, files the kernels into training steps, and writes them every
steps_per_file steps (default 100) to a per-rank .npz, deleting the oldest files
written by the run beyond num_steps_retained (default 1000). A slow step can then
be inspected after the fact without having scheduled a profiling window for it.

Kernels are named from the CUDA graph nodes they replay: a graph instantiate
hook records each node's kernel name, launch geometry and graph annotations
(mark_kernels regions, c10d collective metadata) once per graph, and each file
embeds the table for the graphs its steps ran. scripts/kernel_span_ring_to_trace.py
joins kernels to that table and writes a Chrome/Perfetto trace for chosen steps
and ranks.

- KernelSpanRecorder runs from Profiler.step() on the training thread: record
  the step's host end time, flush CUPTI without a device sync, and cut the
  delivered kernels (kept sorted by start time) at the end of every step for
  which a later kernel has arrived. _KernelSpanRing buffers finished steps,
  writes a file every steps_per_file steps and evicts old files.
- Requires accelerator graphs (validated in TrainingEngine.Config) and CUDA
  graph node ids (CUDA 13.1+ driver or cuda-compat). Kineto windowed profiling
  cannot run alongside it; Cuspy windowed profiling can, with graph annotations
  keyed by exec-graph node id.
- Rename _cuspy_unavailable_reasons to cuspy_unavailable_reasons, now used
  from kernel_span_ring.py.

## Cost

4x GB300, FSDP over 4 GPUs, CUDA graphs, cuda-compat 13.1. Baseline and
kernel_span_ring runs alternated, 2 rounds each. Llama 3 8B: seq 8192, 60 steps,
medians over steps 21-60. Qwen3 32B: seq 4096, full activation recompute, 40
steps, medians over steps 16-40. Both runs are GPU-bound. steps_per_file=20
so files are written inside the measured window (5x more often than the
default).

Performance:

| Model (kernels/step) | Round | Step time, baseline | Step time, ring | Change | Tokens/s/GPU, baseline | Tokens/s/GPU, ring |
|---|---|---|---|---|---|---|
| Llama 3 8B (2.3k) | 1 | 377.4 ms | 377.7 ms | +0.1% | 21,802 | 21,662 |
| Llama 3 8B (2.3k) | 2 | 377.7 ms | 382.6 ms | +1.3% | 21,732 | 20,760 |
| Qwen3 32B (5.4k) | 1 | 2,963.0 ms | 2,969.1 ms | +0.2% | 5,528 | 5,514 |
| Qwen3 32B (5.4k) | 2 | 2,963.1 ms | 2,973.5 ms | +0.35% | 5,524 | 5,512 |

Tokens/s is averaged over the logged steps in the window (every 10 steps), so
it is noisier than the median step time.

Memory and disk, per rank:

| Model | GPU peak reserved, baseline -> ring | Host peak RSS, baseline -> ring | Disk per step (steps_per_file=100) | Disk at default retention (1000 steps) |
|---|---|---|---|---|
| Llama 3 8B | 61.33 -> 61.33 GiB | 3.49 -> 3.52 GiB | 81 KB | ~81 MB |
| Qwen3 32B | 145.28 -> 145.28 GiB | 3.66-3.67 -> 3.71 GiB | 188 KB | ~188 MB |

Host RSS was sampled every 2 s from each training process. Disk per step
includes the node table, which is stored once per file (0.6 MB for 8B, 1.5 MB
for 32B).

Time taken:

| Model | Recorder step(), median per step | Recorder step(), max (includes file writes) | Write one 100-step file | Convert 1 step x 4 ranks | Convert 10 steps x 4 ranks |
|---|---|---|---|---|---|
| Llama 3 8B | 2.8-3.5 ms | 12.6-43.0 ms | 3.9 ms (8.1 MB) | 2.3 s (0.6 GB peak) | 4.6 s (0.6 GB peak) |
| Qwen3 32B | 5.3 ms | 24.5-24.9 ms | 8.5 ms (18.8 MB) | 2.7 s (0.6 GB peak) | 8.2 s (0.7 GB peak) |

The recorder runs on the host while it waits on the GPU, so its time is mostly
hidden in GPU-bound steps. File write times are page-cache writes to local disk,
measured by re-saving the run's files. Conversion runs offline, off the
training machines.

Numerics: loss and grad_norm match the baseline for 30 steps of the llama3
debug model (seed 42, deterministic, flex attention, 2 GPUs).
