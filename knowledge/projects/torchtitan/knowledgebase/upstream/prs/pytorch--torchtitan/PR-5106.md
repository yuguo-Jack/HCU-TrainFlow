# [graph_trainer][CI] Keep TP-reduced grads of R parameters in reduce_dtype, as FSDP2 does

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5106) · state: closed · merged: False

## Original PR description

CI is red. This is vibecoded. Need someone from graphtrainer to review

----

**TLDR:** The dense GraphTrainer numerics tests (`test_dense_{llama3,qwen3}_aot_fx_trace_vs_eager`) fail on main since the 2026-10-02 PyTorch nightly. FSDP2 now keeps the TP all-reduced grad of sequence-parallel norm weights in fp32; SimpleFSDP rounds it to bf16. This PR keeps it in fp32, and both tests match eager bitwise again.

**Problem**
1. With TP + sequence parallel, each TP rank computes a partial grad for an RMSNorm weight, so the grad is all-reduced over TP. These parameters are typed `spmd.R` on TP.
2. PyTorch commit 38d3f6fd0d6e ("[FSDP2] Separate sharded and unsharded gradient dtypes") sets `grad_dtype = reduce_dtype` on FSDP2's unsharded parameter. Eager FSDP2 now runs that all-reduce in fp32 and reduce-scatters the fp32 sum. Before, the all-reduce ran in bf16.
3. SimpleFSDP also runs it in fp32 (the backward of `spmd.convert(I -> R)`), but the grad flows into the bf16 all-gathered weight. Autograd casts a grad to its tensor's dtype, so the sum is rounded to bf16 before the reduce-scatter.
4. All 13 norm weight grads of llama3 debugmodel differ from eager after step 1, and the loss diverges at step 2 (CI: 7.7476043701171875 vs 7.747605800628662).

How I found it: torchtitan 6f716feed passed CI with torch dev20261001 and failed with dev20261002, and 38d3f6fd0d6e is the only FSDP2 change between them. Locally, rounding eager FSDP2's TP-reduced grads to bf16 makes it match GraphTrainer bitwise for 20 steps.

**Solution**
1. A parameter with an `R` axis outside DP is all-gathered in its stored dtype (fp32), not `param_dtype`.
2. The existing `spmd.convert` casts it to `param_dtype`. Its backward returns its input's dtype (fp32), so the reduced grad reaches the reduce-scatter unrounded, as in FSDP2.
3. Other parameters are unchanged, and so are forward values: casting before or after the all-gather gives the same bf16 weight.

**Results** (H100, torch dev20261004, both configs with dp_shard=2 tp=2 on 4 GPUs, 20 steps)
```
llama3 dense   mismatch from step 2 -> bitwise equal, all 20 steps
qwen3 dense    mismatch from step 2 -> bitwise equal, all 20 steps
```

You may ask: why not all-reduce over TP after the reduce-scatter, keeping the bf16 all-gather? It sums in a different order than FSDP2, so it is not bitwise.

NOTE:
- R parameters (e.g. norm weights with SP, the MoE router gate) now get their own fp32 all-gather bucket, since bucketing groups by dtype: 15 -> 28 bucketed all-gathers in the llama3 debugmodel graph. These parameters are small; multi-dtype bucketing could merge them back.
- Not run: the 8-GPU tests themselves (I had 4 GPUs) and the 8-GPU H100 `test_moe_qwen3_aot_fx_trace_vs_eager`.

**Test plan**
- `scripts/loss_compare.py --assert-equal --steps=20` on 4-GPU copies of `{llama3,qwen3}_{eager,graph}_numerics` (dp_shard=2): fail on main, pass with this PR.
- `pytest torchtitan/experiments/graph_trainer/tests/test_numerics.py::TestSimpleFSDP`: 16 passed, 2 skipped (need 8 GPUs).
- `test_passes.py`, `test_graph_pp_passes.py`, `test_simple_fsdp.py`, `test_chunked_loss.py`, `test_grad_accumulation.py`: pass.

> I think SimpleFSDP should follow FSDP2 to set unsharded param's grad type to be reduce_dtype, i.e. fp32 by default. cc @pianpwk

looking, I think the annoying part is grad_dtype can only be set on autograd leaf nodes, which is doable in eager FSDP2 because the autograd graph ends at unsharded grad (TP allreduce & FSDP reduce-scatter are manual machinery outside the graph), but with SimpleFSDP those collectives are in the autograd graph. So we can't set grad_dtype here.

I'm exploring writing custom autograd Fn for this, since FSDP2 is also taking the manual approach (rather than say, changing grad behavior for `to_local`), not sure what you think

IIUC now, the difference is:
```
Eager FSDP2
  BWD:  compute -> LEAF .grad (fp32 via grad_dtype)
        ---- autograd ends; FSDP2 post-backward hook, plain code ----
        -> TP all-reduce (fp32) -> reduce-scatter (fp32)

SimpleFSDP
  BWD:  compute -> convert bwd = TP all-reduce (fp32)
        -> engine casts to the bf16, this is based on to_local's FWD dtype, and the downcast causes the numerics mismatch
        -> redistribute bwd: upcast to fp32 again, reduce-scatter -> LEAF .grad
```

the custom AF wouldn't cast down to bf16 here
