# fix softmax collapse with improved ce perf

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5661) · state: closed · merged: True

## Original PR description

This PR does two things for TP cross entropy calculation:

1. use `F.softplus` for ce calculation to address the softmax collapse issue when the model is overconfident

2. move softmax-onehot calculate to fwd pass; as a result, we don't need to redo softmax-related ops in bwd, and buffer movement, which would improve the customized eager TP autograd perf.

It changes numerics for TP > 1 case, since we are using a different implementations of softmax + cross_entropy

The numbers are as follows: (T=16384, V=128256, TP=2)

||old TP ce (eager)| new TP ce (eager)| old TP ce (compile)| new TP ce (compile)|
|---|---|---| ----|----|
|memory | 15.66 GiB | 5.87 GiB | 7.83 GiB | 3.91 GiB |
|time |38.96 ms | 27.11 ms | 13.15 ms | 6.29  ms |

### Summary

The math holds up. `softplus(logsumexp_{j!=t} z_j - z_t)` is an exact rewrite of the NLL. Taking the target out of the sum *before* reducing is the right way to stop the small terms from being absorbed into `exp(0)=1`. Using `-p_nt` for the target-gradient slot once `p_t >= 1/4` avoids the `p_t - 1` cancellation. I traced the edge cases and they are handled:
- ignored rows: no shard owns the target, so `sum_exp` is just the non-target sum and the row gets zero gradient
- `-inf` at the fallback lane 0
- a `-inf` target logit: NLL is `inf` and the gradient is `-1`, same as before
- uneven shards
- `non_target_sumexp` underflowing to 0: NLL is 0 and all gradients are 0, so the result is consistent

There are two things to resolve before merge (CI goldens and compile behavior), plus a few smaller points.

### Blocking / must-address

**1. TP golden numerics will change. Regenerate them and add a convergence proof.**
The integration goldens are produced *with TP* and checked with `--assert-equal`. For example, `tests/assets/losses/fake_pg/a10g/llama3.txt` comes from `llama3_debugmodel_fsdp2_tp2_cp2` (FSDP=2, TP=2, CP=2), and the same holds for the `real_pg/*` and `sft.txt` goldens built from TP configs. This PR changes the loss in the last bits for every TP run, so `loss_compare.py --assert-equal` should start failing in the `ciflow/fake-pg` and real-PG jobs. This is a computation change, so per CLAUDE.md the PR should also include:
- regenerated goldens (fake_pg and real_pg, for every affected arch: a10g, mi350x, ...)
- a loss/grad_norm convergence comparison against `main` on a representative dataset (e.g. C4) with TP>1

**2. Check the in-place mutation of a saved tensor under `torch.compile`.**
Both callers run inside `@local_compile("loss", ...)` regions (`loss.py:52`, `loss.py:409`). Backward now runs `grad_logits.mul_(grad_output)` on a tensor from `save_for_backward` and then returns it (`loss.py:277-278`). In eager mode this works: unpacking happens before the mutation, and the version-counter bump is what makes the second backward raise, as your test expects. Under AOTAutograd, though, mutating a backward-graph input (a saved activation) gets functionalized. That can add a copy (which cancels the memory win) or hit an unsupported-mutation path. Please:
- confirm the T=16384/V=128256 numbers were measured with the `loss` region compiled as well as in eager mode, since the default recipes compile it and Inductor already fused the old `(exp(log_probs) - onehot) * g` backward into one kernel
- add or extend a test that runs the TP CE under `torch.compile` with forward and backward

If compile does object, a non-mutating `return (grad_logits * grad_output).to(ctx.logits_dtype)` still keeps most of the win: it saves only one buffer, does no softmax recompute, and needs no zeros/index_put.

### Non-blocking suggestions

**3. TP and non-TP CE are now numerically different by design.**
The non-TP path (`F.cross_entropy`, `loss.py:80`) still collapses for overconfident targets, and the batch-invariant RL path (`loss.py:467`) does too. Before this PR, TP CE matched `loss_parallel()`/`F.cross_entropy` bit for bit. Now TP=1 vs TP=2 runs no longer match bit for bit, and in the overconfident regime they differ for real. That is fine if it is intended, but:
- say it explicitly in the PR description, since users debug parity between TP=1 and TP>1
- consider whether the non-TP path should get the same fix, either in a follow-up or by routing it through a shared helper, so the two paths don't disagree in exactly the regime this PR targets

**4. `HIGH_PROB_THRESHOLD` is a public module-level name in a shared module.**
`loss.py:92` is generic for `torchtitan/components/loss.py`. Consider `_HIGH_PROB_THRESHOLD` or a class attribute on `_LossParallelCrossEntropy`.

The comment could also be sharper. By Sterbenz, `p_t - 1` is exact for `p_t >= 0.5`; the real issue is that the *absolute* rounding error of `p_t` (~ulp(1)) becomes a large *relative* error in `1 - p_t`. Any threshold in roughly [1/4, 1/2] works, so a short note on why 1/4 was picked would help future readers.

**5. Optional memory win: skip the full fp32 copy of the logits.**
`logits = logits.float()` (`loss.py:155`) followed by `shifted = logits - local_max` creates two `[T, V_local]` fp32 buffers at the same time when the input is bf16. The `compute_logprobs` caller passes raw logits; `cross_entropy_loss` already passes `pred.float()`. Computing `local_max` from the original logits, upcasting it, and then running `shifted = logits - local_max` lets type promotion produce a single fp32 buffer. Gather the target from `shifted`, as you already do. This matters most for the RL path, where logits arrive in bf16.

**6. Using a version-counter error as a feature.**
The test in `test_loss_parallel_cross_entropy_ignored_rows_and_inputs` asserts that a second backward raises `RuntimeError`. That relies on the eager version-counter check, which is an implementation detail and not obviously stable under compile or saved-tensor hooks (CPU offload, AC). I'd either drop that assertion or decorate `backward` with `@once_differentiable`. The latter is also accurate, since the backward is not differentiable, and it documents the contract more explicitly.

There is also a related subtlety. For fp32 inputs, `.to(ctx.logits_dtype)` is a no-op, so the returned gradient *is* the saved buffer. With a leaf input, `logits.grad` aliases that storage. That is harmless today, but worth a one-line comment.

**7. Tests.**
The new fp64-reference test for confident targets is good: targets land on different shards, the margins go past the fp32 collapse point, and it checks the gradient-balance invariant. Some notes:
- Switching the parity test from `torch.equal` to `assert_close` with default tolerances is reasonable, but it would also be useful to compare against an fp64 reference in the parity test, so that "close to loss_parallel" doesn't hide a systematic bias.
- Consider adding an uneven-vocab case (e.g. `vocab_size=1003` with TP=4 on the confident-targets test). With `1003 // 4`, the last shard is already smaller, so this is partly covered. Also add a case where the target sits at local index 0 on a non-owner rank's shard boundary, to exercise the lane-0 rewrite at `loss.py:246-251`.
- I couldn't run the CPU unit tests here because shell permissions for `pytest` aren't granted in this job. Please confirm they pass locally or in CI.

### Nits
- `loss.py:192` comment: "``shifted`` is a fresh buffer" holds because of the subtraction, not because of `.float()`, which returns the same tensor for fp32 inputs. Saying that explicitly would protect the invariant from a future refactor (e.g. switching to `logits.sub_`).
- The docstring now says "This is no longer bitwise identical to `loss_parallel()`". After merge, the comparison to the old implementation won't mean much to readers. Consider describing the property instead, e.g. "matches `loss_parallel()` up to fp32 rounding; differs when the target margin exceeds ~16.6".

Overall the direction is good and the numerics are careful. The main asks are the golden/convergence evidence and a compile check.

There are now two CE implementations, picked by whether we're tracing. Only the `recompute` branch runs on the production path: both callers sit inside `@local_compile("loss")`, and `"loss"` is in every model's default regions. The `else` branch, plus its save/backward halves at L283-291 and L773, runs only when the loss region is not compiled. `.claude/rules/design.md` covers this case: "Debug-only and eager fallback paths don't deserve optimization ... when compiled/kernel paths exist."

What it costs to keep:
- About 25 lines of in-place index/scatter logic (lane-0 rewrite, `-inf` patch, `div_`, mutating a saved tensor in backward), each of which needs its own reasoning and tests.
- A private upstream API, `torch.compiler._is_non_strict_tracing()`, added only to choose between the two branches, with no TODO or upstream issue (CLAUDE.md principle 3).
- The goldens mostly don't cover the code that runs in production. `torchtitan_recipes/tests/__init__.py:30` clears `local_compile.regions` whenever SPMD type checking is on, so those integration configs run the eager branch. The default compiled branch is covered only by the CPU `aot_eager` test.

Smallest fix: drop the gate and the `else` branches, and always use the masked-sum + recompute form (forward L236-240, save L280-282, backward L769-771). That also removes `ctx.recompute`, `row_idx` in forward, and the private API call. In eager the recompute form should cost about what `main` costs today: a few `[T, V_local]` fp32 temporaries and a saved low-precision input instead of saved fp32 `log_probs`. *Unverified*: please re-measure eager, and regenerate any goldens that move.
