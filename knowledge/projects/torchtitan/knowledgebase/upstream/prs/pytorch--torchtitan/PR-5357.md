# fix: preserve global metadata for offloaded ema checkpoints

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5357) · state: closed · merged: True

## Original PR description

## summary

preserve the live parameter's global shape and stride when rebuilding offloaded ema tensors for checkpoint save and load.

for a 5 by 4 parameter sharded over two ranks, the local shards have 3 and 2 rows. inferring the global shape from each local shard produces 6 and 4 rows, which makes the checkpoint planner reject the chunks. using `shape=p.shape` and `stride=p.stride()` also handles empty tail shards and transposed layouts.

the existing cpu rewrap fixture now covers 4, 5 and 1 rows. checkpoint keys, host shadow storage and ema updates stay unchanged.

**Verdict: LGTM. The fix is correct and small.** I have a few optional suggestions on test coverage, listed below.

#### The fix (`torchtitan/components/optim/ema.py:436-443`)

The bug is real. When `shape`/`stride` are left out, `DTensor.from_local` computes the global shape on the assumption that every rank holds the same number of rows. FSDP2 `Shard(0)` splits unevenly when the dimension doesn't divide evenly: a 5-row param splits into 3 and 2 rows. Rank 0 would then work out a global shape of 6 rows and rank 1 a global shape of 4. The resulting chunk metadata is inconsistent across ranks, so DCP's planner rejects the save.

Passing `shape=p.shape, stride=p.stride()` is the right fix:
- `p` is still the live DTensor param. The docstring already relies on this, so reading the spec from it is safe after a resume or a world-size change.
- The pinned shadow comes from `torch.empty_like(local, ...)` at `ema.py:96`, which keeps the local strides. The local layout therefore matches what `p.stride()` describes, transposed params included.
- `load_state_dict` (`ema.py:591-602`) fills the DTensors that `state_dict()` produced, so this fix covers the load path too. No separate change is needed there.
- This is the only `DTensor.from_local` call under `torchtitan/components/`, so no other callsites in this area need the same change.

The non-offload path is unaffected. It holds real DTensors from `t.detach().clone()`.

#### Suggestions (non-blocking)

1. **Also assert the stride in the rewrap test.** Half of the change is `stride=p.stride()`, but `test_rewrap_restores_the_global_shape` only checks `.shape`. Adding `self.assertEqual(rewrapped.stride(), param.stride())` inside the subtest loop would pin it. A transposed case such as `distribute_tensor(global_tensor.t().contiguous().t(), ...)` would cover the transposed-layout claim in the PR description.

2. **The checkpoint scenarios described in the PR are not in the repo.** The description mentions 8 two-rank and 4 four-rank gloo lifecycle scenarios. The in-repo `TestEMACheckpointResharding` class only uses the non-offloaded path and evenly divisible shapes (8×8 and 8×4). Neither CI nor future refactors will catch a regression of this exact bug at `dcp.save`. One cheap test would close that gap: build a 5-row `Shard(0)` param and call `dcp.save({"k": ema._materialize_dtensor(param, param.to_local().clone())})`. Then load it into a plain `torch.zeros(5, 8)` and compare. It needs no pinned memory, so it runs on CPU/gloo. The current fixture only checks metadata, not the DCP planner path that actually failed.

3. **Optional one-line docstring note.** CLAUDE.md asks for comments only on non-obvious points. Why `shape`/`stride` must be passed explicitly qualifies, so a short note in `_materialize_dtensor`'s docstring would fit, e.g. "`shape`/`stride` are passed explicitly because `from_local` cannot infer the global size from an uneven or empty shard."

4. **Nit:** `_sharded_param(self, num_rows=4)` could be annotated as `num_rows: int = 4`.

#### Not verified here
As the author notes, the CUDA-specific parts still need a run on GPU CI: pinned-memory H2D/D2H, stream ordering, and a two-GPU checkpoint save → resume with an uneven-shard param. The diff does not touch the update path (`_update_offloaded`), so I don't expect numerics to change. A debug-llama loss comparison is a low-priority check for this change.
