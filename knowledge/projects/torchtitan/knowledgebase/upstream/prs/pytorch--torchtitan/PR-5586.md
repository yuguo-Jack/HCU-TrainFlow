# [rl] Pin the generator's weight-sync buffers at their exact size

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5586) · state: closed · merged: False

## Original PR description

## TLDR

The generator's pinned weight-sync receive buffers cost 1.74x the bytes they hold: PyTorch's CUDA caching host allocator rounds every pinned block up to a power of two. PyTorch can turn that off above a size (`pinned_max_round_threshold_mb`); this PR sets it to 64 MiB in the generator right before the buffers are allocated, so they are pinned at their exact size.

NOTE: this takes effect for large models, where the rounding decides whether the buffers fit in host memory. Kimi K3's generator at TP 4 needs ~424 GiB of buffers per 4-GPU node at their exact size and ~740 GiB at 1.74x, on hosts with 855 GiB. Small models waste little.

## Problem

1. Each generator rank allocates its weight-sync receive buffers once, at startup (`VLLMModelWrapper.__init__`): one pinned CPU tensor per parameter, shaped like the rank's local shard. Every weight sync reuses them: TorchStore writes the trainer's new weights into them while the generator keeps generating, then `load_prefetched_model_state_dict` copies them to the GPU. They stay resident for the whole run.
2. They are built with `_create_cpu_state_dict(state_dict, pin_memory=True)`, which calls `.pin_memory()` per tensor. PyTorch's CUDA caching host allocator rounds each request up to the next power of two so freed blocks can be reused, and pins the whole rounded block. A 2.297 GiB expert shard takes 4 GiB. These buffers are never freed, so the reuse never helps.
3. Measured on a reduced Kimi K3 generator (8 layers, DP 16 x EP 16, 216 tensors per rank): the buffers hold 24.99 GiB and pin 43.40 GiB (1.74x); process RSS grows by 43.6 GiB; node `MemAvailable` drops by 174 GiB (4 ranks).
4. Full Kimi K3 generator: at TP 1 (DP 64 x EP 64) a rank holds 185.8 GiB of bf16 weights (non-expert 101.3 GiB, replicated at TP 1; routed experts 79.2 GiB; embedding and head 4.4 GiB; vision 0.8 GiB), so the buffers need 743 GiB per 4-GPU node of 855 GiB even at their exact size. At TP 4 (DP 16 x TP 4 x EP 64) they need ~106 GiB per rank, ~424 GiB per node, which fits only without the rounding.

## Solution

1. Right before `_create_cpu_state_dict(..., pin_memory=True)`, the generator sets `pinned_max_round_threshold_mb:64` (two statements in `VLLMModelWrapper.__init__`). The caching host allocator then pins blocks above 64 MiB at their exact size; smaller blocks keep the rounding.
2. The setting is process-wide, so other pinned allocations above 64 MiB in the generator process are exact too. They lose only reuse across differently sized blocks, which allocations made once do not use.
3. Our key goes first and the current allocator settings after it. PyTorch resets `max_split_size_mb`, `roundup_power2_divisions` and `garbage_collection_threshold` to their defaults when a settings call omits them (`c10/core/AllocatorConfig.cpp`, `parseArgs`), so they are re-applied; later keys win, so a threshold the user set in `PYTORCH_CUDA_ALLOC_CONF` still applies.

Unchanged: `_create_cpu_state_dict`, the buffers' keys, shapes, dtypes and placements, TorchStore, and per-sync behavior.

## Results

```text
pin one 1.15 GiB tensor with .pin_memory(), A100, torch 2.15.0.dev20260928
                                          allocator holds   RSS growth
default                                   2.00 GiB          +2.12 GiB
pinned_max_round_threshold_mb:64          1.15 GiB          +1.27 GiB
```

| Per rank, reduced Kimi K3 generator (DP 16 x EP 16, GB300) | Before | Exact-size pinning |
|---|---|---|
| Bytes the buffers hold | 24.99 GiB | 24.99 GiB |
| Pinned through the caching host allocator | 43.40 GiB | 0.03 GiB |
| Process RSS growth | +43.6 GiB | +24.9 GiB |
| Node MemAvailable drop (4 ranks) | 174 GiB | 100 GiB |

NOTE: the Kimi K3 numbers above were measured with this PR's first version, which pinned the buffers as one hand-registered `cudaHostRegister` allocation. That pins the same bytes as this version, but this version has not been run on Kimi K3 yet. A reduced Kimi K3 RL smoke with the first version synced weights normally (generator pull 1.49-1.50 s, trainer/generator logprob gap unchanged).

Full model: with exact-size buffers, generator TP 1 still OOM-killed the hosts right after the checkpoint load (the buffers alone are 743 of 855 GiB per node). Generator TP 4 brings them to ~424 GiB per node; a reduced-layer TP 4 generator and RL smoke passed with exact-size buffers, and the full-model TP 4 run is pending.

NOTE: `pinned_max_round_threshold_mb` is in the PyTorch 2.15 nightlies (checked 20260817 and 20260928). The other pinned options (`pinned_use_cuda_host_register`, `pinned_num_register_threads`, `pinned_reserve_segment_size_mb`) do not stop the rounding.

NOTE: `_create_cpu_state_dict` still copies each DTensor shard to pageable CPU memory before pinning, and discards the copy. That costs startup time, not resident memory; #5485 removes it.

The net change is the 9 lines at `torchtitan/rl/generator/vllm/model_wrapper.py:423-431`. The diagnosis is right: long-lived buffers that are allocated once don't benefit from the caching host allocator's power-of-two rounding, and at Kimi K3 scale that rounding is the difference between fitting in host memory and getting OOM-killed. I don't see a correctness bug. My main concern is how the option is set.

### Why does this call private APIs?

**PyTorch doesn't need to be called at runtime for this; the public contract is the env var.** `pinned_max_round_threshold_mb` is an ordinary key in the allocator config string, the same one `PYTORCH_ALLOC_CONF` / `PYTORCH_CUDA_ALLOC_CONF` carry. PyTorch has no public API to change allocator settings after startup. `torch._C._accelerator_setAllocatorSettings` (and the Python wrapper `torch.cuda.memory._set_allocator_settings`) are private for a reason: the config is a process-global singleton, some keys can't safely change once allocations exist, and every call resets keys it doesn't mention (which is why the PR has to read the settings and re-apply them). The PR has to work around that last behavior, so it depends on two private bindings and on an implementation detail of `parseArgs`. A nightly could change either one without notice.

**torchtitan already has the public path:** `torchtitan/rl/_env.py:16` `RL_ENV_DEFAULTS` sets `PYTORCH_ALLOC_CONF` / `PYTORCH_CUDA_ALLOC_CONF = "expandable_segments:True"` before torch is imported. `train.py`, `generate.py` and the Monarch actor provisioning (`actors/monarch/provisioning.py:32`) all run it, so generator processes get it. The no-private-API version of this PR is:

```python
"PYTORCH_ALLOC_CONF": "expandable_segments:True,pinned_max_round_threshold_mb:64",
"PYTORCH_CUDA_ALLOC_CONF": "expandable_segments:True,pinned_max_round_threshold_mb:64",
```

Trade-offs compared with the PR:
- **Scope:** it also applies to trainer processes. That should be harmless, since pinned blocks over 64 MiB there are also long-lived (DCP staging, offload). The runtime call already affects the whole generator process anyway.
- **User overrides:** `apply_env_defaults` uses `setdefault`, so a user who sets their own `PYTORCH_CUDA_ALLOC_CONF` loses the threshold. That is already true of `expandable_segments` today, and it follows the documented env-var semantics. A NOTE in `_env.py` or the Kimi K3 recipe docs saying large-model generators need this key would cover it.

[Fix this ->](https://claude.ai/code?q=On%20branch%20rl-exact-pinned-weight-sync-buffers%2C%20replace%20the%20torch._C._accelerator_getAllocatorSettings%2F_accelerator_setAllocatorSettings%20calls%20in%20torchtitan%2Frl%2Fgenerator%2Fvllm%2Fmodel_wrapper.py%20(VLLMModelWrapper.__init__%2C%20around%20line%20423)%20by%20adding%20%60pinned_max_round_threshold_mb%3A64%60%20to%20both%20PYTORCH_ALLOC_CONF%20and%20PYTORCH_CUDA_ALLOC_CONF%20in%20RL_ENV_DEFAULTS%20in%20torchtitan%2Frl%2F_env.py%2C%20with%20a%20short%20ASCII%20comment%20explaining%20why%20(caching%20host%20allocator%20power-of-two%20rounding%20of%20long-lived%20pinned%20weight-sync%20buffers).%20Update%20tests%2Frl%2Funit_tests%2Fcpu%2Ftest_runtime_env.py%20if%20needed.&repo=pytorch/torchtitan)

### Who should expose this, in principle?

The mismatch is that a caching allocator, whose policy is built around reuse, is serving a request that is allocated once and never freed. So the right owner is whoever makes that allocation, not a global allocator knob:

1. **`torch.distributed.checkpoint` (DCP).** `_create_cpu_state_dict(pin_memory=True)` is itself private (`torch.distributed.checkpoint._state_dict_utils`), and its whole purpose is long-lived staging buffers. Its `share_memory=True` branch already bypasses the caching allocator with `cudaHostRegister` at the exact size. The pin-only branch should do the same, or take an option for it. That would fix this for every DCP user (async checkpoint staging hits the same 1.74x), and torchtitan would need no allocator configuration at all. This is the upstream fix I'd push for; it fits core principle #1/#3 (fix it upstream instead of working around it locally).
2. **PyTorch core, as a fallback.** Either a public per-allocation way to pin exactly (e.g. `pin_memory()` / `torch.empty(..., pin_memory=True)` taking a no-cache or exact-size hint, or a public `torch.cuda.caching_host_allocator_alloc`-style API), or a public, documented, merge-not-reset runtime setter for allocator settings under `torch.accelerator.memory`. The reset-on-omit behavior you had to work around is the main reason the current setter isn't safe to make public as it stands.
3. **torchtitan's role:** only the env default above, and only until (1) lands.

This PR's first version used a hand-registered slab, so it effectively implemented (1) locally. Moving to the allocator knob was a reasonable simplification, but it swapped a self-contained mechanism for a private global one.

### Smaller points

- **No test now.** The last commit removed both the CPU and GPU tests. With the env-var approach, `tests/rl/unit_tests/cpu/test_runtime_env.py` covers the value for free. If you keep the runtime call, the GPU test that checks a 65 MiB pin stays exactly 65 MiB is worth keeping, because it is what catches a nightly changing the reset semantics or dropping the key.
- **Unknown-key failure.** On a torch build without `pinned_max_round_threshold_mb`, the CUDA config parser rejects unrecognized keys, so generator init fails with an allocator-config error rather than a clear message. That's acceptable because torchtitan already pins nightlies, but it's worth knowing. The env-var route fails the same way, just earlier.
- **Re-applying `expandable_segments` after CUDA allocations exist:** `_accelerator_getAllocatorSettings()` returns the string that includes `expandable_segments:True`, so this re-sets it at runtime with the same value. It's fine today, but it's another behavior that only the private path depends on.
- **The NOTE is model-specific.** The comment at `model_wrapper.py:424-426` hard-codes Kimi K3 node sizes, which will go stale. The general reason (long-lived, allocated once, so rounding only wastes memory) is enough there, and the numbers belong in the PR description.
- **Placement:** the call sits between `maybe_apply_numa_binding` and the allocation, so it does take effect before the buffers are pinned. Any pinned allocation made earlier in `__init__` (for example during `_maybe_initial_load_weights`) still gets rounded. That has no effect on resident memory unless those blocks are kept.

### Summary

The fix works and the measurements are convincing. I'd change how it's delivered: put `pinned_max_round_threshold_mb:64` in `RL_ENV_DEFAULTS` (public, already set before torch is imported, no reset workaround), and open an upstream issue asking DCP's `_create_cpu_state_dict(pin_memory=True)` to pin at the exact size the way its `share_memory` path already does. I didn't run tests or linters; this was a read-only review.
