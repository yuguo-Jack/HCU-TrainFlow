# [muse_spark][perf] Compile RoPE with the q/k norms; drop the Helion RoPE override

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5459) · state: open · merged: False

## Original PR description

**TLDR:** Compile Muse Spark Open's RoPE inside the attention's q/k region and drop the Helion RoPE override: norm + RoPE 6-15% faster than Helion at 16k-128k and 2.7-3.8x faster at decode, outputs bitwise equal to the Helion path.

Land after "[rope][perf] Compile ComplexRoPE in real arithmetic (rope region)". Without it, RoPE's complex multiply runs as separate eager kernels inside this region, while the Helion kernel is already gone.

**Problem**
1. **Override.** The Muse recipes replace `ComplexRoPE` with a Helion kernel (`helion_rope.helion_complex_rope`), an optional dependency.
2. **Two passes.** The q/k norm region (PR 3) writes q and k in bf16, then the Helion kernel reads them back to rotate them.
3. **Cost.** At decode, norm + RoPE take ~35 us per layer with Helion, plus 3 bounds-check kernels per call.

**Solution**
1. **One region.** `_prepare_query_and_key` compiles everything from the qkv projection to attention: per-head norms, query scale, position temperature and RoPE. The region is renamed `muse_spark_attention_qk` (was `muse_spark_attention_qk_norm`).
2. **RoPE in real arithmetic.** With the ComplexRoPE PR, RoPE compiles to pointwise math that reads and writes each bf16 pair as one int32. That view needs the normed q/k in memory, so the region writes them out first, as the Helion path did; the gain is one graph with fewer kernels and a faster rotation, not one memory pass.
3. **Recipes.** The 816B, Dist-MoE and debug recipes drop the Helion RoPE override.
4. **Unchanged.** The math, and the Helion override module (removed in the next PR).

```text
before:  qkv -> [qk norm region] -> q,k bf16 -> Helion RoPE kernel -> attention
after:   qkv -> [qk region: norms, scale, temperature -> q,k bf16 -> RoPE] -> attention
```

Region options:
- `recompile_limit=16`: RoPE and no-RoPE layers share the region: 8 graphs across training, prefill and decode shapes, which is exactly the default limit.
- `batch_invariant=False`: the region runs RMSNorm, like the other norm regions.

You may ask: why not keep Helion inside the region? It works (the region calls it as an opaque op), but the rotation can't fuse with the norms, and decode stays at Helion's ~35 us.
NOTE: in the 2-layer Helion column the Helion op runs inside the same region, so both columns share every other kernel.
NOTE: not tested: TP/EP/CP > 1, the Dist-MoE recipes, loss curves, H100.

**Test plan**
- `pytest tests/unit_tests/gpu/models/muse_spark/test_attention_compile.py`: layers 0 (RoPE) and 3 (position temperature, no RoPE); the compiled region's error against an fp32 run is at most 1.05x eager's, outputs and grads.
- `pytest tests/unit_tests/cpu/recipes/test_muse_spark.py`: the debug recipes still import.
- TODO before un-drafting: `muse_spark_debugmodel` (regions on) for a few training steps and one RL DAPO step, CUDA graphs on, `TORCH_LOGS=recompiles`: report each region's graph count against its limit. No debug-size Muse Spark RL config exists yet: either run one step of `muse_spark_816b_a42b_dapo_math_gb300_config` (256 trainer + 16 generator GPUs), or first write a small debug-model DAPO config. The Muse integration tests can't check this: they turn on SPMD typechecking, which clears every region.
