# Add kv head padding for non-divisible TP 

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5132) · state: open · merged: False

## Original PR description

This PR adds support for `n_kv_head % TP_degree != 0` in GQA case. 

Say there is a fused QKV (q_head=12; k_v_head=6; TP=4), the fused QKV becomes sth like [Wq0, Wq1, ..., Wq11 | Wk0, Wk1, ..., Wk5 | Wv0, Wv1, ..., Wv5] (before regrouping and cat). Through padding, the fused QKV becomes [[Q0 Q1 K0 V0], [Q2 Q3 K1 V1], ...., [Q10 Q11 K5 V5], [PAD PAD PAD PAD], [PAD PAD PAD PAD]].  The padded QKV are further sharded by TP in dim0. In this case, Wo also needs to be padded to be multipliable by QKV output. It is padded from [H, 12D] -> [H, 16D]. 

I do acknowledge that there are other ways to handle this, e.g., by sharding the fused QKV naively and all-gather the weights when needed; or replicate KV heads and only shard q heads. 

It is more computation-efficient for smaller models/smaller k_v_head to do KV head replicate, where the attention computation dominates; you can hide k_v_head gradient updates, tho the implementation would be more invasive. Padding, however, would be easier to implement and the wasted padding computation is acceptable for larger models.

**Summary:** The core math holds up. Padded KV groups go at the end of the `(n_kv_heads, R, head_dim)` `wqkv` layout, and the matching `wo` input columns are zero-initialized. That keeps the `q head -> kv head` mapping intact on every TP rank, and the padded heads get zero output and exactly zero gradients (Q/K/V all come out as zero, and so does `dout` through the zero `wo` columns). The CPU parity test covers this. My main concerns are not in the padding itself. They come from padding **only inside `Decoder.__init__`**, which leaves the rest of the system holding an unpadded config.

### 🔴 Major

**1. The state-dict adapter, FLOPs and nparams are built from the unpadded config, so HF checkpoint I/O breaks.**
`training_engine.py:337-346` builds `adapter_cls(self.model_config, ...)` and `self.model_config.get_nparams_and_flops(...)` from the trainer's config. That config is never padded: `validate_model_training_config` calls `model.pad_attention_heads_for_tp(tp)` and throws the result away (`validation.py:76`). Only `Decoder.self.config` is padded.
- `_split_qkv_linear` / `_merge_qkv_linear` (`protocols/state_dict_adapter.py:236, 276`) work out `num_kv_heads` from the tensor shape. As a result:
  - `to_hf` would emit padded `wq/wk/wv/wo`.
  - Loading a real HF checkpoint (for example Qwen3 with `n_kv_heads=4` at TP=8) fails with a shape mismatch.

  The docstring admits "HF adapters see the padded geometry". In practice, though, this rules out the main fine-tuning use case for padded TP, and the user never gets a clear error saying why.
- The logged model size and the MFU leave out the padded params and FLOPs. Counting real FLOPs for MFU is arguably right, but the nparams log will no longer match the actual parameter count.

**Suggestion:** pad the config once at the trainer level (next to `set_sharding_`), so the model, adapter, FLOPs and RL all see the same geometry. Then make the adapter padding-aware: slice off the padded groups in `to_hf` and zero-pad in `from_hf`. With that in place, HF checkpoints load, and exported checkpoints stay TP-agnostic. If you want to keep it out of scope, at least raise a clear `ValueError` when HF load or save is requested with padded heads.

**2. RL weight sync (`ciflow/rl`).**
Under TP, the trainer builds padded `wqkv`/`wo` parameters. The generator side builds its own config (`rl/model/vllm_registry.py:67` reads `cfg.first_base_attention` for `num_key_value_heads`), and its TP degree may differ, so the generator may pad differently or not at all. Trainer -> generator weight transfer will hit a shape mismatch, or worse, a silent mis-mapping. Please either confirm the RL path is safe or reject the setup explicitly.

**3. "Trains as the unpadded one" doesn't hold for Muon.**
`_adjust_muon_learning_rate` (`distributed/flex_shard/dist_muon.py:1795-1807`) scales LR by `rows/columns` or `max(rows, columns)`. Padding changes `wqkv` rows and `wo` columns, so the effective LR on the *real* heads changes unless Muon splits per head via `compute_sharding_by_fqn`. Zero rows staying zero through Newton-Schulz is true, but the shape-dependent LR scaling is a real numerics change. Please qualify the docstring at `attention.py:1043-1046`, or verify it for the Muon configs.

### 🟡 Design / performance

**4. The overhead can be large when `tp > n_kv_heads`.**
Padding grows `n_heads` by `padded_kv / n_kv`. A few cases:

| Config | Overhead |
|---|---|
| `n_kv=6, TP=4` (the PR's example) | 33% extra QKV/attention/`wo` |
| `n_kv=4, TP=8` (Qwen3 MoE flavors) or `n_kv=8, TP=16` (Llama3) | 2x attention FLOPs, plus 2x `wqkv`/`wo` params and optimizer state |
| `n_kv=2, TP=8` | 4x |

KV-head replication (the vLLM/Megatron approach when `tp % n_kv == 0`) costs nothing in Q compute in that regime. Some options:
- Mention this split in the PR (padding for `n_kv % tp != 0` with `n_kv > tp`, replication for `tp > n_kv`).
- Put the overhead ratio in the warning.
- Possibly raise above some threshold.

**5. Parameter shapes now depend on the TP degree.**
A DCP checkpoint saved at TP=4 (padded to 8 kv) won't load at TP=2 (6 kv). This is documented and you get a warning, but resharding a checkpoint across a different TP degree is a common workflow, so it's a silent break of that ability (CLAUDE.md principle 5). The adapter-level fix in (1) mostly addresses it for HF format. For DCP, call it out in the docs or the PR description.

**6. Validation calls a mutating-style API only for its side effect.**
`model.pad_attention_heads_for_tp(tp)` in `validation.py:76` deep-copies the whole config just to raise early, then discards it. That reads as a bug. Either pad there and keep the result (see 1), or split out a `check_attention_heads_shardable_for_tp` helper.

### 🟢 Minor
- `_log_attention_head_padding` runs once per `Decoder` build on every rank and every PP stage, so the same warning will print N times. Consider logging only on rank 0, or once.
- `pad_attention_heads_for_tp` iterates `self.layers` but writes to `padded.layers[i]`. If a user config shares one layer config object across layers, `deepcopy` keeps the aliasing, and the shared attention gets wrapped repeatedly. That's harmless today because the second wrap pads by 0, but it's fragile. Guarding with `if _tp_shards_attention_heads(padded.layers[i].attention, tp): continue` would avoid it.
- The comment on `_zero_padded_init` relies on `DTensor.new_empty(real_shape)` returning a Replicate DTensor. Nothing tests that with TP or FSDP-sharded DTensors.

### 🟡 Should address

**1. Every `state_dict()` call all-gathers each padded param, and the cache may keep the full gathered tensor alive.**
`PaddedDim.strip` (`attention.py:~986-995`) does `redistribute(Replicate)` -> `narrow` -> `redistribute(Shard)` on every padded `wqkv`/`wo`. This runs on each checkpoint save and on each RL `push_model_state_dict` (every policy update).
- Cost: one all-gather of the full `wqkv` and the full `wo` per layer, per call.
- Retained memory: `BaseStateDictWrapper` (`checkpointer/base.py:128,144`) keeps the first result in `cached_state_dict`. If `Replicate -> Shard` returns a `chunk` view instead of a contiguous copy, each cached local shard keeps its full replicated storage alive. Every rank would then hold unsharded `wqkv` + `wo` for every layer for the rest of the run.

Please check this. If it's a view, a `.contiguous()`/`.clone()` on the local tensor would fix the retained memory. Longer term, a shard-local strip that narrows only the ranks owning the boundary would avoid the all-gather. That could be a TODO.

**2. Placement round-trips under FSDP+TP aren't tested.**
- `strip` maps every `Shard` subclass to plain `Shard` (`attention.py:~990`). For `wqkv` under FSDP+TP, the placements are typically `(_StridedShard(0), Shard(0))`. They become `(Shard(0), Shard(0))` with uneven sizes on both mesh axes. The values are still correct, but DCP save/load of uneven nested `Shard(0)`s is not exercised anywhere.
- `restore_padded_optim_state` then does `redistribute(Replicate -> live.placements)` (`optim/utils.py:185`), which includes `Replicate -> _StridedShard`. Please confirm that DTensor supports this path at the pinned torch version.
- All the DTensor tests (`test_dtensor_state_dict_round_trip`, `test_dtensor_states_hide_padding`) use a **1-rank mesh**. On a 1-rank mesh, every redistribute is a no-op and nothing is uneven. The test comment even says the hook output aliases the params.

Since the PR has `ciflow/fake-pg`, could you add a fake-PG test? Suggested setup: `dp_shard=2, tp=4`, `n_kv=6`, then model + AdamW `state_dict()` -> DCP save -> load at `tp=2` and `tp=1`. That would cover the real code path.

**3. RL generator TP.**
Padding is decided at build time from `spmd_mesh_size("tp")` (`attention.py:1028`). The state-dict exchange is padding-agnostic, so trainer TP and generator TP can differ, which is good. Two things are still open:
- The vLLM wrapper builds `_prefetched_model_state_dict` from `self.model.state_dict()` (`vllm_wrapper.py:364`). With padding, that's the stripped tensor, and for DTensors it now has uneven shards. Can you confirm that torchstore's `put_state_dict`/`get_state_dict` handles uneven `Shard` DTensors?
- If the generator shards through vLLM's own TP without the spmd `tp` mesh, it won't pad. It would then fail the n_kv divisibility requirement on its side. A single RL smoke test with `n_kv % generator_tp != 0` would settle both questions.

### 🟢 Minor / nits

- **FLOPs are inconsistent.** `get_nparams_and_flops` (e.g. `llama3/model.py:94-108`) counts the padded params in `nparams`, and through `6 * active_nparams` in the linear FLOPs, but uses the unpadded `attention.n_heads` for the attention-op FLOPs. MFU therefore counts the padded `wqkv`/`wo` matmuls as useful work but not the padded attention. Pick one convention: subtract padded params, or count padded heads. A one-line note would be enough if this is intentional.
- **Shape-based matching in `_map_padded_optim_state` (`optim/utils.py:217-221`).** It relies on `shape[dim] == num_padded/num_real` to decide whether to convert. That works for Adam/AdamW/SGD. A future optimizer with a non-parameter-shaped 2D state of the same size along `dim` (e.g. a factored or Shampoo-style preconditioner for `wo`) would be silently narrowed. A short comment that only parameter-shaped states are supported would help the next person.
- **Reliance on `getattr(module, "padded_params", {})`.** `OptimizersContainer._padded_params` (`optimizer.py:~106`) depends on this plain attribute set in `_register_padding_hooks`. That's fine, but `nn.Module.__setattr__` stores a dict as a regular attribute, so it won't survive `copy.deepcopy`-free module swaps such as float8/MX `Linear` conversion if those rebuild the module. Please check that a quantized-converter run (e.g. `Float8Linear` swap) keeps `padded_params` and the hooks on `wqkv`/`wo`. If the swap drops them, padding leaks into checkpoints silently.
- **`validate_tp_head_sharding` checks only `first_base_attention`.** That's unchanged from before, but now that padding is per-layer opt-in, a config that mixes `PaddedQKVLinear` and `QKVLinear` layers would only be validated on layer 0. The non-divisible layers would then fail later in `local_map` with a less clear error.
- **`PaddedQKVLinear.Config.validate_tp_degree` is a no-op `pass`.** The rule the docstring describes holds by construction (`heads_per_kv * round_up(n_kv, tp)` is divisible by `tp`), so this is fine. A one-line assert in `__init__` that `num_padded_kv_heads % tp == 0` would document the invariant cheaply.

### Simplifying the optimizer-side padding

- [x] Read the optimizer / EMA padding code in `components/optim/`

- [x] Work out whether they can at least live next to `PaddedQKVLinear`

**Short answer:** yes. The optimizer code can go away completely. Moving it into `attention.py` would not really fix the problem.

### Why `optim/` ends up involved

The optimizer code exists because of one choice: the PR makes **checkpoint shapes differ from parameter shapes**. The params are padded, but the hooks on `wqkv`/`wo` save them unpadded.

Every optimizer state shaped like a param (Adam `exp_avg`/`exp_avg_sq`, EMA copies) then has to apply the same transform, and only the optimizer container can see those states. That is why the PR adds `_padded_params()`, `_flat_state_dict()`, `_restore_padding()`, the `like=` placement plumbing, and the shape-matching in `_map_padded_optim_state`.

Moving those helpers into `attention.py` as e.g. `PaddedQKVLinear.strip_optim_state` wouldn't remove the coupling. `OptimizersContainer.state_dict()` and `load_state_dict()`, and EMA, would still need to find padded modules and call into them. `torch.optim.Optimizer` hooks don't help either: the module can't reach the optimizer, and the hooks see param-id-keyed state, not torchtitan's flat FQN dict.

So the fix is to remove the mismatch, not to move the code.

### Option A (recommended): save the padding in checkpoints and pad from a config value, not the TP mesh

Today, `PaddedQKVLinear.__init__` computes `round_up(n_kv_heads, spmd_mesh_size("tp"))`. That makes param shapes depend on the TP degree, which is why the PR strips padding to keep DCP portable.

Instead, make the padded size an explicit config field, e.g. `PaddedQKVLinear.Config.num_padded_kv_heads: int` (or `pad_kv_heads_to_multiple_of`). Then:

- **Param shapes depend only on the config.** A DCP checkpoint reshards to any TP degree that divides `num_padded_kv_heads`. That includes TP=1, where the padded heads are just inert zeros.
- **No state-dict hooks at all.** Params, Adam states and EMA copies all have the padded shape, so the whole `components/optim/` diff (optimizer.py, utils.py, ema.py) can be reverted. So can `PaddedDim.strip`/`restore`, `_register_padding_hooks` and `module.padded_params`.
- **The round-2 issues go away too:**
  - no all-gather on every `state_dict()` call (checkpoint saves, RL weight pushes);
  - no `_StridedShard -> Shard` conversion or uneven-shard DCP round trips;
  - no `Replicate -> _StridedShard` on optimizer restore;
  - no `padded_params` dict that a float8/MX module swap could drop.
- **HF interop stays at the existing HF boundary.** `_split_qkv_linear` (`protocols/state_dict_adapter.py:232-242`) already redistributes `wqkv` to Replicate and reshapes it to `(num_kv_heads, R, head_dim, ...)`. So `to_hf` only needs `packed[:real_n_kv]`, plus `wo[:, :real_n_heads * head_dim]`. `from_hf` zero-pads the same way. The adapter already reads the real `attn.n_kv_heads` from the config (`llama3/state_dict_adapter.py:81`). This is the one place that truly needs to know about padding, and it already pays for the all-gather.
- **Simpler for RL.** The generator builds from the same config, so it gets the same padded shapes whatever its TP degree. There's nothing to negotiate.
- **Trade-off:** a padded DCP checkpoint can't be loaded directly into an *unpadded* config; it has to go through HF. That's the normal contract for any architecture-config change. `validate_tp_head_sharding` can raise a clear `ValueError` when `tp` doesn't divide `num_padded_kv_heads`, with a hint pointing to the field.

### Option B: keep params unpadded and pad inside `forward`

In this option the stored params are never padded, so params, optimizer state and checkpoints all hold the real shapes with no hooks. Inside the `local_map` body, each rank zero-pads its local shard up to `ceil(n_kv / tp)` groups, a local `F.pad` with no communication.

This works because DTensor's uneven `Shard` rule (`torch.chunk`, e.g. `[2, 2, 2, 0]` for n_kv=6, tp=4) matches the PR's group layout exactly, **as long as the sharded dim counts whole KV groups**. With today's 2D `wqkv` `(n_kv*R*D, H)`, though, DTensor splits by rows: 6RD/4 isn't a multiple of a group. Option B would therefore need the param stored as a 3D `(n_kv, R*D, H)` tensor, and `wo` with a matching head axis. That changes the `Linear` layout, the FSDP+TP composition and checkpoint compat. It's a bigger change than Option A, so I'd only consider it if TP-agnostic *unpadded* DCP checkpoints are a hard requirement.

### Recommendation

Go with **Option A**. It deletes all of the `components/optim/` changes and the param state-dict hooks, keeps everything padding-related in `attention.py` plus a small strip/pad in the HF QKV split/merge, and answers most of my round-2 distributed concerns along the way.

I haven't changed any code, since this is a design call for @ruisizhang123 and you. If you want, I can push Option A to this branch.

You're right about Option A. A fixed padded size has to target the largest TP degree you expect, so every smaller-TP job pays for padding it doesn't need. That undoes the point of padding per TP degree, so I withdraw it. Option B is also out: it would need a 3D `wqkv` layout to get group-aligned uneven shards, which is too invasive.

I agree with generation-only padding. Training can keep requiring `n_kv_heads % tp == 0`, which `validate_tp_head_sharding` already enforces. All the optimizer and EMA complexity exists only because a padded param has an optimizer, and the generator has none.

### What can be deleted

- **All `components/optim/` changes** (`optimizer.py`, `utils.py`, `ema.py`) and their tests can be reverted.
- **The trainer stays unpadded.** Its weight push (`rl/trainer.py:331`) sends real-shaped tensors with no strip step, so the round-2 concern about an all-gather on every `state_dict()` call goes away for the trainer.
- **Training checkpoints stay unpadded,** which removes the questions about uneven DCP `Shard`s and `_StridedShard -> Shard` conversions.

### The config split may be smaller than a full refactor

The generator already rewrites the shared config on its own side:
- `rl/model/vllm_wrapper.py:287-289` deep-copies `model_config`, calls `set_sharding_` with the generator's parallelism, then runs `_replace_vllm_layer_configs`.
- `_replace_vllm_layer_configs` (`vllm_wrapper.py:45`) already replaces each layer's attention config with vLLM-specific versions.

A generator-only step there, "swap `QKVLinear.Config` for `PaddedQKVLinear.Config` when `n_kv_heads % generator_tp != 0`", gives you different trainer and generator models without changing the unified `config.model` that `controller.py:584/601` passes to both. The weight-sync contract still holds, because FQNs match and the module hooks keep the generator's state-dict shapes unpadded. Whether you still want the broader refactor for other reasons is your call, but padding alone doesn't seem to need it.

### What the generator path still needs

1. **Pass padded head counts to vLLM.**
   - `VLLMAttentionWrapper.Config(num_heads=..., num_kv_heads=...)` in `_replace_vllm_layer_configs`, which comes from `get_attention_dimensions`.
   - The HF-shaped dict in `rl/model/vllm_registry.py:87-88`, where vLLM uses `num_attention_heads` and `num_key_value_heads` for TP divisibility checks, FA3 head counts and KV-cache sizing.

   If either one keeps the real counts, vLLM rejects the TP degree or misreads the local head count.
2. **The KV cache becomes the real cost.** In inference, the padded KV heads also take KV-cache memory, roughly `padded_n_kv / n_kv` of it (1.33x for n_kv=6, tp=4). That costs batch size more than it costs FLOPs, so it's worth stating in the warning.
3. **The `restore` hook on every weight pull.**
   - `_prefetched_model_state_dict` is a pinned **CPU** copy (`vllm_wrapper.py:363`).
   - `_pull_model_state_dict` calls `load_state_dict` with it on every sync (`rl/generator.py:1517`).
   - `PaddedDim.restore` calls `redistribute(Replicate)` (`attention.py:1024-1027`), so each sync triggers a collective on CPU DTensors. That probably fails on an NCCL mesh, and at best it's a full all-gather per layer per sync.

   Since the generator never trains, a simpler option is to keep the prefetch buffer for the padded params at the generator's padded local layout and copy only the real rows on load, with no collective. A full-tensor CPU fetch for just `wqkv`/`wo`, narrowed locally, is the fallback. Please test this path with an actual `generator_tp`, since nothing exercises it today.
4. **Skip padding when vLLM's KV replication already applies.** When `generator_tp % n_kv_heads == 0` (e.g. n_kv=4, tp=8), native vLLM replicates KV heads and doesn't pad Q. Padding then doubles the work. It's probably worth padding only when neither number divides the other. That's a later improvement, not a blocker.
5. **Initial checkpoint load on the generator.** The DCP/HF load at generator init uses the same strip/restore hooks, with a GPU template, so it should work. It still needs one test with uneven `Shard`.

### Suggested scope for this PR

- Revert `components/optim/` and the optimizer/EMA tests.
- Keep `PaddedQKVLinear` and its module hooks in `attention.py`.
- Raise a clear `ValueError` if a padded config reaches the trainer. This holds as long as the `validate_tp_head_sharding` path runs for any padded layer, not only `first_base_attention` (an earlier minor note).
- Move the RL wiring (items 1 and 3) into a follow-up. That can land with or after your config change, together with an RL smoke test where `n_kv % generator_tp != 0`.
