# Capture the full training step, optimizer included, in GraphTrainer

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5626) · state: open · merged: False

## Original PR description

This PR lets graph trainer trace gradient clipping and optimizer.step() into the same graph as the forward and backward passes, so optim.enable_accelerator_graph = True replays the whole training step as one graph instead of being rejected.

- claude[bot] · CHANGES_REQUESTED · 2026-11-04T03:47:54Z · [source](https://github.com/pytorch/torchtitan/pull/5626#pullrequestreview-5762942042)

**Verdict: Request changes** -- the PR shows no numerics or perf evidence, doesn't compare against the much smaller two-graph option, and copies `Optim`'s update logic into a second place that #5728 is about to change.

**What this PR does.** In GraphTrainer, setting `optim.enable_accelerator_graph = True` used to raise. Now it traces gradient clipping, the loss/grad-norm finite check, and `optimizers.step()` into the SPMD joint fwd+bwd graph. The graph returns `(loss, grad_norm)` instead of `(loss, *grads)`, and the LR scheduler and EMA still run eagerly afterwards. PP, gradient accumulation, SDC replay, paged stash, precompile artifacts, and optimizer step hooks are all rejected.

**Example.**
```text
# GraphTrainer, SPMD FSDP+TP, 1 microbatch, optim.enable_accelerator_graph = True
main: GraphTrainingEngine.__init__ -> ValueError("Optim CUDA graphs are not supported with GraphTrainer.")
PR:   graph(inputs) = fwd -> loss -> bwd -> clip_grad_norm_ -> assert finite -> optimizers.step()
                      -> (loss, grad_norm)          # grads never land in param.grad
      eager after replay: lr_schedulers.step(); ema.step()
      MoE load balancing / qk_clip / bf16 moments (step hooks) -> ValueError at first trace
```

### Must fix
1. **Description.** The description is one sentence. It has no "Summary (human-written)" section, no problem statement, no testing section, and no numerics. Please add:
   - Numerics: a bitwise loss and grad_norm comparison between `enable_accelerator_graph` on and off, with `seed=42, deterministic=True` (FSDP+TP is enough).
   - Value: a measured benefit (step time and/or peak memory).
   - Alternative: why this design over the smallest option, which is deleting the `ValueError` and letting `Optim` capture its own accelerator graph, as the eager trainer does (two graphs instead of one, about 2 LoC versus +457 net). If the gain is memory (grads die inside the graph) or overlap, the numbers should show it. *Unverified* whether the two-graph option works as-is.
2. `trainer.py:252` -- second copy of `Optim.step`/`Optim._update`. It will drift apart from the original, and #5728 (grad division moving into `optim_step`) would silently change numerics on whichever PR lands second. It also already drops the first-step sync.
3. Validation is spread across four places:
   - `spmd_graph_builder.py:237` -- the precompile check belongs in `Config.__post_init__`.
   - `pipeline.py:756` -- the grad-accum check belongs in the engine, where `num_microbatches` is computed.
   - `traced_optimizer.py:45` -- the PP check can never fire; delete it.

### Should consider
- `trainer.py:250` -- `optim_step` gets the trace span twice on the default path.
- `make_fx_tracer.py:229` -- take only `Sequence[Optimizer]` and always return a list.
- `test_trace_module.py:1319` -- drop the three raise-only tests.
- `optimizer_update` is threaded through about 10 functions, each with `= None`. Making it keyword-required in the private helpers would stop a caller from silently dropping it.

### Questions
- Rather than keeping a copy in `TracedOptimizerUpdate`, should `Optim._update` become traceable (take the parameters, reduce the finite flag with funcol)? That touches core, so it's a maintainer call, but it would remove both copies.
- Does `llama3_fsdp_tp` (now with the flag on) check against golden losses? If not, nothing in CI ties traced-optimizer numerics to the eager optimizer at model scale.

<details><summary>Details</summary>

- Gate: the problem is real (the flag raises on `main`), and the change is in the experiment folder, so it doesn't touch core. What's missing is evidence of value and a comparison with the existing `Optim` graph path.
- Checked and OK:
  - Hooks are registered in `_initialize_optim` before `_initialize_forward_backward`, so the step-hook rejection sees them.
  - Tracing is lazy (at the first step), so it happens after `load_checkpoint`.
  - `accumulate_param_grads_` skips the `[None]` placeholders.
  - The lazily created `Optim._run_update` graph wrapper is never instantiated, so `all_wrappers_warmed_up` isn't blocked.
  - Default `fused=True` AdamW traces the fused op, so no foreach/single-tensor switch is expected on the main path.
- `grad_norm` reaches `optim_step` through a side channel (`record_grad_norm`). It's acceptable inside the experiment, but it relies on `forward_backward` running exactly once per `optim_step`.
</details>

Not verified: GPU numerics, FSDP+TP integration behavior, and whether skipping the first-step `empty_cache` affects peak memory.

This is a second copy of `Optim.step`'s tail, and `TracedOptimizerUpdate.__call__` is a second copy of `Optim._update`. The two copies will drift apart, and you can see it happening already:

- Open PR #5728 moves the gradient division (`grads /= N`, the step's loss-token count) into `optim_step`, right before clipping. Whichever of the two PRs lands second, the traced path will either skip that division or run it twice. Neither case raises an error; only the loss and grad_norm change.
- The `_is_first_step_call` synchronize + `empty_cache` in `Optim.step` (#5019) is already dropped here, without any explanation.

Please coordinate with #5728 so the traced path does the division inside the graph, before `clip_grad_norm_`. Also either restore the first-step sync or explain why the traced path doesn't need it. At minimum, put a comment on each copy that names the eager function it mirrors.
