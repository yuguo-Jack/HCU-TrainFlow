# [Release CI] Sync RL and staged-wheel validation

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5632) · state: closed · merged: True

## Original PR description

## Summary

Sync the release-candidate validation improvements proven on `release/0.4` back to the main-branch template.

- add A10G and B200 RL release-validation suites without allowing RL dependencies to replace the selected Torch release wheels
- align CPU and non-RL GPU validation with TorchAO nightly, matching main CI
- update the CPU smoke test to the current packed-token model API and run full-model backward/optimizer coverage in the A10G core validation
- stage checkpoint helpers, Flux documentation, and synthetic multimodal assets so copied tests exercise the installed TestPyPI wheel successfully
- scope `HF_ASSETS_PATH` to the Qwen3 parity tests so the Qwen3.5 random-weight test does not load an incompatible checkpoint
- resolve test modules from the installed TorchTitan package when validation runs outside the checkout

This intentionally does not port the Torch 2.15 compatibility shim, its EnvServer workaround, or the release-only LoRA test change.

## Source PRs

This combines the final validated state from these `release/0.4` PRs:

- [#5588](https://github.com/pytorch/torchtitan/pull/5588): validate against the Torch 2.15 RC stack
- [#5597](https://github.com/pytorch/torchtitan/pull/5597): add RL suites and update installed-wheel validation (release backport of closed main PR [#5589](https://github.com/pytorch/torchtitan/pull/5589))
- [#5602](https://github.com/pytorch/torchtitan/pull/5602): use TorchAO nightly for CPU validation
- [#5606](https://github.com/pytorch/torchtitan/pull/5606): stage source-test assets for CPU validation
- [#5609](https://github.com/pytorch/torchtitan/pull/5609): use TorchAO nightly for GPU validation
- [#5610](https://github.com/pytorch/torchtitan/pull/5610): fix staged GPU test setup and checkpoint scoping
- [#5614](https://github.com/pytorch/torchtitan/pull/5614): stage installed-wheel test assets for GPU validation

## Why

The main-branch release-validation template still had the pre-0.4 setup: no RL coverage, an obsolete CPU smoke-test API, stable TorchAO versions missing APIs used by the current tests, and incomplete staged-wheel assets. These issues were found and fixed while validating 0.4 RCs. Carrying the validated harness back to main prevents the next release branch from rediscovering the same failures.

Torch 2.15 FlexAttention rejects backward on CPU when its inputs require gradients. The CPU job therefore keeps a real model forward smoke, while the A10G `core` suite runs three full-model FlexAttention backward and AdamW steps before the rest of the GPU tests.

#### Suggestions

**1. A release-specific vLLM hack is going into the main template** (`validate_release_gpu.sh`, the `TORCH_VERSION == "2.15.0" && VLLM_VERSION == "1.0.0.dev20261005+cu132" && PYTORCH_INDEX_URL == ...` block)
The PR description says Torch-2.15-specific workarounds were left out on purpose, but this block is exactly that. It hardcodes a dated nightly wheel URL and a `UV_OVERRIDE`. Once the next release bumps any of those three values, the branch stops running without any warning, and `vllm==${VLLM_VERSION}` may then pull its own torch nightly. The constraint file should catch that as a resolution failure, which is fine, but the hack is still dead weight. Two options:
- Drop the block in main and let the release branch carry it.
- Make it generic: add an optional `VLLM_REQUIREMENT` input (default `vllm==${VLLM_VERSION}`) plus an optional override flag, both set from the workflow, so the script holds no version literals.

[Fix this →](https://claude.ai/code?q=In%20.github%2Fscripts%2Fvalidate_release_gpu.sh%20on%20branch%20codex%2Fsync-release-validation-main%2C%20replace%20the%20hardcoded%20TORCH_VERSION%3D%3D2.15.0%20%2F%20VLLM_VERSION%3D%3D1.0.0.dev20261005%2Bcu132%20vLLM%20wheel-URL%20override%20block%20with%20an%20optional%20VLLM_REQUIREMENT%20env%20var%20(default%20vllm%3D%3D%24VLLM_VERSION)%20and%20an%20optional%20flag%20to%20write%20the%20torch%20UV_OVERRIDE%20file%2C%20so%20the%20script%20has%20no%20release-specific%20literals.&repo=pytorch/torchtitan)

**2. Three back-to-back `if` blocks** on the same condition (`validate_release_gpu.sh`, nvcc / flash-attn-4 / dist_moe install). This can be one `if [[ rl-b200 ]]; then fa4; dist_moe; else nvcc; fi`.

**3. The CPU smoke test lost its backward-pass coverage** (`validate_rc.yaml`, "Run CPU debug-model forward smoke test")
The old test ran 3 AdamW steps and asserted the loss went down. The new one is a single forward pass under `no_grad`, so the CPU RC check no longer covers autograd or the optimizer. If flex attention's backward works on CPU under `force_eager`, I'd keep at least one `loss.backward()` + `optimizer.step()`. If it doesn't, a short comment saying why would help the next reader. Also, `model._get_attention_metadata` is a private API, so this test will break if it gets renamed. That's acceptable for a smoke test, just be aware of it.

**4. CUDA 13.2 wheels in a CUDA 13.0 container** (`validate-rl-b200` job)
`rl-b200` installs cu132 wheels and asserts `torch.version.cuda == "13.2"`, but runs in `nvidia/cuda:13.0.3-cudnn-devel`, and it skips the `nvidia-cuda-nvcc==13.2.*` install that the A10G RL path gets. Minor-version compatibility should cover the runtime, and this passed on `release/0.4`, but anything that JIT-compiles with the system `nvcc` will see 13.0. Is skipping nvcc deliberate? A one-line comment would make that clear.

#### Nits
- In `validate-rl-b200`, `VLLM_VERSION` is passed through `env:` while every other variable is passed inline. Passing it inline next to `VALIDATION_SUITE=...` would match the other jobs.
- For non-RL suites, the only torchao check is `".dev" in torchao.__version__`. That matches main CI, but because torchao nightly isn't pinned, two RC validation runs can test different torchao builds. The version is printed to the log, which helps when tracing a failure.
- The CPU job's `ln -s` into the venv's site-packages will fail if it's re-run in the same venv. That's harmless in a fresh CI runner, but `ln -sfn` would make it idempotent.

Overall the script is careful about keeping the release wheels fixed: `PIP_CONSTRAINT` pins `torch`, `torchvision` and `triton`, `install_release_candidate` installs `torchtitan[rl]`, and the verifiers extra is resolved last. Scoping `HF_ASSETS_PATH` to just the Qwen3 parity classes is also correct.
