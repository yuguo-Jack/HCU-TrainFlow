# Summary

The RL trainer previously cast model parameters to the generator dtype on GPU before TorchStore copied them to CPU. This temporarily materialized another model-sized GPU state dict.

This change allocates a persistent pinned CPU mirror of the complete model state dict, that

- Are staged on the GPU-local NUMA node
- Has parameters directly in the generator transfer dtype

Before each transfer, we copy the complete snapshot into staging before passing it to TorchStore.

This removes the temporary GPU cast copy and gives TorchStore a stable CPU snapshot rather than live trainer tensors.

The change also overlaps both the following transfers with fwd/bwd

- Staging model weights to Titan owned CPU buffer
- Transferring Titan owned CPU buffer to TS owned CPU buffer

### 2. Can the structure be simplified?

Yes. Concrete suggestions, roughly in order of value:

**a. One helper for the "weights are final" sync point.** The `__init__` and `optimizer_step` blocks are the same idea. A tiny method makes that explicit, and the comment answering the DCP question has a natural home:

```python
def _mark_weights_ready_for_staging(self) -> None:
    # Push runs as a concurrent endpoint and may be scheduled after the next
    # fwd/bwd has already enqueued kernels, so record the ordering point here
    # (right after weights are final) instead of at push time.
    if self._staging_stream is not None:
        self._staging_stream.wait_stream(torch.cuda.current_stream(self.engine.device))
```
Call it once at the end of `__init__` (after `load_checkpoint`) and once after `engine.optim_step()`.

**b. Replace the 1 ms polling loop with a thread wait.**
```python
await asyncio.to_thread(staging_complete.synchronize)
```
`Event.synchronize()` releases the GIL, so this is simpler and doesn't wake the actor's event loop 1000×/s. With this, `_stage_*` reduces to: enqueue copies → record event → await. The early-return `None` branch also goes away if you only create the event when the stream exists.

**c. Simplify the dtype selection.** Now that a staging copy always happens, the "`_transfer_dtype` is `None` when equal to the training dtype" optimization in `__init__` no longer saves anything: `copy_` with the same dtype doesn't cast. You can store `gen_dtype` directly and write `dtype = tensor.dtype if name in buffer_names or gen_dtype is None else gen_dtype`. Then update the comment at `trainer.py:114` to match. Optional.

**d. Move NUMA binding out of the staging setup.** `maybe_apply_numa_binding` sets **process-wide** CPU affinity. Hiding it inside `_setup_push_staging_state_dict` is surprising. `graph_trainer/trainer.py:156` calls it once during trainer init, and I'd do the same here at the top of `Trainer.__init__`. That way it also covers EMA's pinned buffers and any other pinned allocation.

**e. Keep the DTensor allocation hack, but document it.** `empty_like(DTensor, device="cpu")` followed by swapping `_local_tensor` for a pinned tensor looks odd. It's needed because `DTensor.from_local` would move the local tensor back to the mesh's device type, and DTensor has no `pin_memory` (EMA hits the same limitation; see the TODO at `ema.py:407`). Add a one-line comment pointing at that limitation so nobody "simplifies" it to `from_local`. Also use `get_local_tensor(staging_tensor)` there. (Minor: the first `empty_like` allocates an unpinned local buffer that is thrown away right after. Harmless, since large untouched mallocs aren't committed.)

**f. (Optional) shared helper.** EMA (`_pin_local` / `_materialize_dtensor`) and this PR both build "pinned CPU local shard behind a DTensor spec". A `pinned_cpu_like(tensor, *, dtype)` in `distributed/utils.py` next to `get_local_tensor` would fit "reuse over duplication". It's fine to defer that to a follow-up.

Putting a–c together, the trainer side becomes roughly:
```python
# __init__
self._staging_state_dict = self._setup_staging_state_dict()
self._staging_stream = (
    torch.cuda.Stream(device=engine.device) if engine.device.type == "cuda" else None
)
self._mark_weights_ready_for_staging()

@sl.log_trace_span("stage_state_dict")
async def _stage_state_dict(self, state_dict):
    stream = self._staging_stream
    with torch.cuda.stream(stream):
        for name, dst in self._staging_state_dict.items():
            get_local_tensor(dst).copy_(get_local_tensor(state_dict[name]), non_blocking=stream is not None)
        if stream is None:
            return
        done = torch.cuda.Event()
        done.record(stream)
    await asyncio.to_thread(done.synchronize)
```

### 1. What keeps staging and the optimizer step in order

There are two hazards. The PR handles each one differently.

**(a) Staging must read the weights *after* optimizer step N has finished writing them. This is GPU-side ordering, done with `wait_stream`.**

```
host:     optim_step N ── mark ── [optimizer_step returns] ── fwd/bwd N+1 enqueued ─┐
                           │                                                         │ push N task starts
compute:  [optim N kernels]│[fwd/bwd N+1 kernels ..........................]         │ (any time after)
                           ▼                                                         ▼
staging:          (waits on point "mark") ─────────────────────── [D2H copies N] → event
```

- `_mark_weights_ready_for_staging()` (`trainer.py:168`) runs right after `engine.optim_step()` (`trainer.py:301`). It calls `staging_stream.wait_stream(current_stream)`.
- `wait_stream` records an event on the compute stream at that exact point and makes the staging stream wait for it. Copies queued on the staging stream later will run after the optim-N kernels, but **not** after anything queued on the compute stream after the mark.
- That's why the mark sits in `optimizer_step` and not in `push_model_state_dict`. The push is a separate `concurrent_endpoint` task (`WeightSyncManager.start_async_push_pull`). It can run after the controller has already sent `forward_backward_steps` N+1. A `wait_stream` at push time would make the copies wait for fwd/bwd N+1 to finish. That's still correct, but the overlap is gone.
- The call in `__init__` (`trainer.py:143`) does the same job for the H2D copies from `load_checkpoint()` before the first push.

**(b) Optimizer step N+1 must not overwrite the weights while the copies for N are still reading them. This is host-side ordering, done by awaiting a task.**

There's no cross-stream GPU wait for this direction. The host enforces it:
1. `_stage_state_dict` doesn't return until `staging_complete.query()` is true, i.e. the D2H copies have actually finished on the GPU (`trainer.py:397`).
2. After that, `push_model_state_dict` awaits `ts.put_state_dict` (`trainer.py:365`).
3. The controller awaits `wait_prev_push()`, which awaits that push task, **before** it calls `optimizer_step` N+1 (`controller.py:1121` → `:1128`).

So by the time the optim N+1 kernels are even queued, the copies for N are done on the GPU and TorchStore has finished reading the pinned buffer. The same chain covers reusing the pinned buffer itself: staging N+1 only starts after push N has returned.

The cost of using host sync for (b) is that the optimizer step can stall on the push. That stall is what `timing/step/blocking_trainer_push_model_state_dict` measures, and it's the same contract `WeightSyncManager` already had before this PR.

One more condition: fwd/bwd N+1 runs during staging N, so this is only safe if fwd/bwd doesn't change anything in `state_dict()`. That's the contract stated at `trainer.py:394`. Today the only persistent buffer that changes, `expert_bias_E`, is updated in the optimizer pre-step hook.

### 2. Do we need a separate stream? Why not a `concurrent.futures.Future` like DCP?

The stream and the Future solve different problems, so one can't replace the other:

| | What it does | DCP | This PR |
|---|---|---|---|
| **Separate stream** | Lets the GPU run the D2H copies alongside fwd/bwd. Copies on the compute stream would queue behind fwd/bwd N+1. | Yes. As I understand it, `DefaultStager` with `use_async_staging` + `use_non_blocking_copy` creates its own CUDA staging stream. I couldn't open the installed torch source in this run to confirm. | `_staging_stream` |
| **Completion handle** | Tells the host the copy is done. | `concurrent.futures.Future` from a 1-worker thread pool that synchronizes the staging stream | The push `asyncio.Task` (awaited by `wait_prev_push`) plus the event poll inside it |

So **yes, we need a separate stream** if we want the overlap; DCP needs one for the same reason. The Future part already has an equivalent here: `WeightSyncManager._trainer_push_task` is our version of `staging_future`, and `wait_prev_push()` is our version of `maybe_wait_for_staging()`. Wrapping the copy in `ThreadPoolExecutor.submit` + `asyncio.wrap_future` would work, but it only moves the wait onto a worker thread (`cudaEventSynchronize` spin-waits there, as discussed earlier) and adds a second async mechanism on top of the asyncio one the actor already uses.

**The real difference from DCP is *where staging starts*, not Future vs. stream.** DCP's `stager.stage()` is called synchronously on the trainer thread inside `save_checkpoint()`, right after the optimizer step. The copies are queued at a point where "current stream state" already means "weights are final". That's why DCP doesn't need a separate mark step. We could do the same:

```python
# optimizer_step
grad_norm = engine.optim_step()
self._staging_complete = self._enqueue_staging()  # wait_stream + copies + event.record, no await

# push_model_state_dict
await self._wait_staging(self._staging_complete)  # poll the event
await ts.put_state_dict(self._staging_state_dict, ...)
```

This puts the `wait_stream` right next to the copies, removes `_mark_weights_ready_for_staging` and the init-time call, and makes the ordering obvious when reading `optimizer_step`. The costs:
- `optimizer_step` pays the CPU time to queue one copy per state-dict entry.
- Staging becomes tied to `optimizer_step`, so a step that isn't followed by a push (e.g. the last step) would stage for nothing unless it's skipped.

I'd lean toward this version because it reads more clearly, but the current code is correct as written.

**Note:** `forward_backward_steps` runs `engine.forward_backward` synchronously inside the coroutine, so the actor's event loop is blocked for the whole fwd/bwd. During that time the GPU copies still run, but the 1 ms poll and any host-side work in `ts.put_state_dict` only get a turn when the loop is free. This doesn't affect correctness. It does mean how much of `put_state_dict` overlaps depends on whether TorchStore/NIXL does its transfer off the event loop. That fits with the Qwen-27B result in the PR description being NIXL-specific.
