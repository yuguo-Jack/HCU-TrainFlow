# [checkpoint] Reseed EMA after a model-only or EMA-excluded load on any backend

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5141) · state: closed · merged: True

## Original PR description

`CheckpointManager` (DCP) reseeds the EMA from the just-loaded weights when the EMA itself was not restored: a model-only load (a seed `step-0` checkpoint, or `initial_load_path` with the default `initial_load_model_only=True`) or `exclude_from_loading=["ema"]`. `docs/checkpoint.md` describes this, and `test_model_only_load_reseeds_ema_from_loaded_weights` / `test_exclude_ema_honored_even_when_data_is_present` pin it. The reseed lives in `CheckpointManager._load_checkpoint`, so `TorchCheckpointingManager` never does it: after those loads its EMA keeps tracking the random initialization the model just discarded, and the EMA's cold-start warning does not fire.

Loading a seed checkpoint, then resuming a step-5 checkpoint with `exclude_from_loading=["ema"]` (CPU, both backends on the same model):

```
CheckpointManager          after loading step-0: EMA==loaded weights True,  EMA==discarded random init False
TorchCheckpointingManager  after loading step-0: EMA==loaded weights False, EMA==discarded random init True
TorchCheckpointingManager  resume step-5 excluding ema: EMA==loaded weights False, EMA==discarded random init True
```

### Change

Move the reseed from `CheckpointManager._load_checkpoint` into `BaseCheckpointManager.load`, right after `_load_checkpoint`, so every backend gets it. The old condition also required `MODEL in states`, to keep TorchFT's per-replica dataloader-only load from reseeding; that load calls `_load_checkpoint` directly rather than `load()`, and inside `load()` the states always include `MODEL` (`model_only` returns it and `Config.__post_init__` rejects it in `exclude_from_loading`), so that check can no longer be false and was removed.

### Test plan

- New `test_model_only_load_reseeds_ema_from_loaded_weights` in `tests/unit_tests/cpu/components/checkpointer/test_torch_checkpointing.py` loads a step-0 checkpoint with an EMA attached and checks the EMA is reseeded. It fails on main.
- New `test_ema_excluded_from_resume_is_reseeded` (step-5 resume with `exclude_from_loading=["ema"]`; fails on main) and `test_full_resume_keeps_restored_ema` (a full resume restores the EMA and does not reseed it).
- `TestBaseCheckpointManagerTracing._manager` builds a `Mock(spec=BaseCheckpointManager)` and sets the instance attributes `load()` reads; it now also sets `states = {}`.
- `test_torch_checkpointing.py` and `test_checkpoint.py` on the rebased branch: 115 passed (CPU, torch nightly, locally). The two `test_hf_load_*` tests fail locally with and without this change because macOS has no `os.O_DIRECT`.
- The comparison above, run on the first commit: both backends report `EMA==loaded weights True` after both loads.
- flake8 (with the hook's plugins) and ufmt (black 22.12.0, usort 1.0.5) pass on the changed files of the latest commit; the first commit also passed pydoclint and codespell.

### Why the change is correct

- **Root cause.** The rule "reseed the EMA if it wasn't restored" doesn't depend on the storage format, but it was implemented in `CheckpointManager._load_checkpoint` (DCP only). Moving it into the shared `load()` path fixes the root cause rather than patching `TorchCheckpointingManager` separately.
- **Order is preserved.** Both backends restore `MODEL` inside `_load_checkpoint`:
  - DCP: `states[MODEL].load_state_dict(...)`
  - torch_checkpointing: the `target.load_state_dict(state_dict[key])` loop at `torch_checkpointing.py:368-370`

  So when `EMA.load_state_dict({})` runs at `base.py:328-329`, the model already holds the loaded weights and the cold-start copies the right tensors.
- **TorchFT is unaffected.** `TorchFTCheckpointManager._load_checkpoint` calls `super()._load_checkpoint(...)` and then `_ft_load`. The reseed now runs after `_ft_load` instead of between the two. `_ft_load` only touches `DATALOADER`, so the order doesn't matter. `_ft_load` calls `super()._load_checkpoint` directly, so it never reaches the reseed. Peer recovery through `ft_manager.set_state_dict_fns` doesn't go through `load()` either, and it carries `EMA` explicitly.
- **No other overrides.** No subclass overrides `load()` (only `CheckpointManager`, `TorchCheckpointingManager` and `TorchFTCheckpointManager` exist), so all three get the behavior.
- **Mock fix makes sense.** `states = {}` in `TestBaseCheckpointManagerTracing._manager` is needed because the new line reads `self.states`. Since `EMA in self.states` is checked first, the condition never touches the `Mock` returned by `_states_to_load`.

### Nit: the `MODEL in states` check can no longer be false
`torchtitan/components/checkpointer/base.py:328`

The old comment explains the `MODEL in states` check: it stopped TorchFT's dataloader-only `_load_checkpoint` call from triggering a reseed. In `load()`, that case can't happen:
- `_states_to_load(model_only=True)` returns `{MODEL: ...}`.
- Otherwise it returns `self.states` minus `exclude_from_loading`, and `MODEL` is rejected from that list at `base.py:603-604`.
- The only subclass override (TorchFT) only pops `DATALOADER`.

So the check is always true here. Per CLAUDE.md principle 7 (no speculative defensive checks), I'd simplify to:

```python
# Reseed EMA from the just-loaded weights if it wasn't itself
# restored (excluded, or a model_only load).
if EMA in self.states and EMA not in states:
    self.states[EMA].load_state_dict({})
```

If you'd rather keep the guard, write it as `assert MODEL in states` so it reads as an invariant, not a branch. Either way, the PR description's sentence about TorchFT "(the old comment's reason for checking `MODEL`)" should be updated, since the check no longer protects anything.

### Tests: two small gaps
