# [HiMidLoLinear] Accumulate LM-head WGRAD into the running fp32 grad in place

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5178) · state: open · merged: False

## Original PR description

## Summary

Ports the WGRAD accumulation optimization from [#5137](https://github.com/pytorch/torchtitan/pull/5137) onto the current `main` branch.

`ChunkedLossWrapper` runs one LM-head backward per chunk. Before this change, every later chunk materializes a full FP32 `grad_weight`, then `AccumulateGrad` adds it to the existing `weight.grad` in a separate kernel. For a Qwen3-8B LM head, that temporary is 2.318 GiB.

For the wide `HiMidLoLinear` path, this change takes the existing FP32 running gradient and folds the next WGRAD into it with `torch.addmm(..., out=running_grad)`. It then returns that buffer for `AccumulateGrad` to reattach. The first chunk, router/narrow path, stacked weights, traced backwards, and gradients narrower than the WGRAD retain the existing behavior.

The read-and-clear logic is shared with `MXFP8Linear` through `can_accumulate_into_weight_grad` and `pop_running_weight_grad`.

## PyTorch dependency

The FSDP path requires the unsharded parameter to retain its unsynchronized FP32 gradient between chunks. This is provided by [pytorch/pytorch#194434](https://github.com/pytorch/pytorch/pull/194434) and its follow-up stack.

The end-to-end benchmark used an isolated PyTorch build at `ccd8044a383a00dc90a696392f0085a56b2b63ee`, the head of [pytorch/pytorch#197701](https://github.com/pytorch/pytorch/pull/197701), which includes #194434 and its follow-up fixes. With a stock PyTorch build, FSDP stores the unsynchronized gradient in an internal accumulator and leaves `lm_head.weight.grad` as `None`, so this optimization does not trigger.

## Loss-path microbenchmark

**The optimized loss path is 1.156x faster at 8192 tokens/device and 1.100x faster at 16384 tokens/device.** It also removes the 2.318 GiB temporary WGRAD allocation.

Single H100 96 GB, BF16 Qwen3-8B LM-head shape, two runs per shape, 5 warmup and 20 measured steps per run. The table reports the combined median of 40 measurements and incremental peak allocated memory.

| Tokens/device | Tokens/chunk | Path | Speedup | Median time | Memory reduction | Incremental peak |
| ---: | ---: | --- | ---: | ---: | ---: | ---: |
| 8192 | 1024 | chunked + local-compiled CE | 1.000x | 105.22 ms | - | 5.98 GiB |
| | | + in-place WGRAD accumulation | **1.156x** | 91.04 ms | **-2.318 GiB (-38.8%)** | 3.66 GiB |
| 16384 | 2048 | chunked + local-compiled CE | 1.000x | 185.01 ms | - | 7.32 GiB |
| | | + in-place WGRAD accumulation | **1.100x** | 168.25 ms | **-2.318 GiB (-31.7%)** | 5.00 GiB |

The optimized path executes one `addmm` for every chunk after the first.

## End-to-end performance

Qwen3-8B (`8.19B` parameters, 36 layers, `H=4096`, `V=151936`) on 8xH100 96 GB with FSDP8, TP1, PP1, BF16, selective activation checkpointing, CUDA graphs, and `T/device=8192`. Both paths use `ChunkedLossWrapper(num_chunks=8)` (1024 tokens/chunk), local-compiled CE, and a local-compiled FP32-to-BF16 split. The baseline disables only this PR's in-place accumulation helper.

The run uses TorchTitan `47ea181315029530a3a84af2164778ba422dc5b7` and the patched PyTorch build described above. Local C4 test data and the test tokenizer supply inputs without changing the model or loss shapes.

Each path ran twice for 50 training steps. The table combines steady-state steps 11-50 from both runs (80 samples/path).

| Path | Speedup | Median TPS/device | Median global TPS | Peak active memory/device | Active memory vs baseline | Peak reserved memory/device |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| chunked + local-compiled CE | 1.000x | 7,798 | 62,385 | 42.68 GiB | - | 48.54 GiB |
| + in-place WGRAD accumulation | **1.012x** | 7,888 | 63,106 | 41.44 GiB | **-1.24 GiB (-2.90%)** | 48.54 GiB |

The optimization improves end-to-end throughput by 1.16%. It removes one 2.318 GiB temporary WGRAD from the loss path; the end-to-end peak active reduction is 1.24 GiB because other allocations overlap the training-step peak. CUDA graph pool reservation is unchanged.

## Numerics and tests

- Both repeated 8-GPU runs produced exactly matching logged loss and `grad_norm` values at all 50 steps between the baseline and optimized paths.
- CPU helper tests: 2 passed.
- Single-GPU accumulation tests: 3 passed; optimized gradients are bitwise equal to the original `AccumulateGrad` path.
- Two-GPU FSDP trigger test: passed with the patched PyTorch stack above; the test confirms that the later chunk uses `addmm`.
- All pre-commit hooks except Pyrefly passed. Local Pyrefly is blocked by the installed PyTorch and `torch-checkpointing` packages being older than current TorchTitan `main`.

The benchmark recipe is local-only and is not included in this PR.
