# [config] Move dtypes into a root-owned PrecisionConfig; FSDP CPU offload into ParallelismConfig

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5776) · state: closed · merged: True

## Original PR description

## Summary (human-written)
<!-- Write this yourself, not with an AI tool. 2-5 sentences: the problem, why
     this approach, and what you checked yourself. -->

Apparently not only trainer cares about precision; generator also cares. This PR moves it out from `TrainingConfig` as a standalone config, owned by core trainer and RL controller, preparing for the next PR.

## Why
The model's dtypes (`training.dtype`, `training.mixed_precision_param`, `training.mixed_precision_reduce`) live on `TrainingConfig`, owned by `TrainingEngine.Config`. In RL they describe the model that both the trainer and the generators run, but only the trainer can see them:
- The generator builds its model with its own `generator.model_dtype` and fabricates a `TrainingConfig()` just to call `model.parallelize(training=...)`.
- `model.parallelize` takes the whole `TrainingConfig`, but reads only those three fields plus `enable_cpu_offload`.

This PR is a mechanical move. #5774 (stacked on top) then makes the generator mirror the trainer's precision from this one config and deletes `generator.model_dtype`.

**Example.**
```python
# before
config.training.dtype = "float32"
config.training.mixed_precision_param = "bfloat16"
config.training.enable_cpu_offload = True
model.parallelize(parallelism_context=..., training=config.training, parallelism=..., ...)

# after
config.precision.dtype = "float32"          # Trainer.Config.precision / Controller.Config.precision
config.precision.param_dtype = "bfloat16"
config.parallelism.fsdp_enable_cpu_offloading = True
model.parallelize(parallelism_context=..., precision=config.precision, parallelism=..., ...)
```

## What changed
- `PrecisionConfig(dtype, param_dtype, reduce_dtype)` in `torchtitan/config/configs.py`. `param_dtype`/`reduce_dtype` match FSDP's `MixedPrecisionPolicy` names.
- Ownership: core `Trainer.Config.precision` and RL `Controller.Config.precision`, not `TrainingEngine.Config`. `TrainingEngine` receives it as a constructor argument, like `model_config`. In RL the controller passes the same object to the trainer (and, in #5774, to the generators).
- `training.enable_cpu_offload` -> `parallelism.fsdp_enable_cpu_offloading`, next to the other `fsdp_*` options, so `model.parallelize` / `_apply_fsdp` take `precision=` and no longer need `training`.
- The Dist-MoE `param_dtype == "bfloat16"` check moves from `TrainingEngine.Config.__post_init__` to `Trainer.Config` and `Controller.Config`, where `precision` is visible (two 5-line copies, both at config time).
- GraphTrainer (experiment): its models read the token budget in `parallelize`, so `GraphTrainingEngine` passes `training` there through its existing kwargs hook.
- Mechanical, skimmable: every `parallelize`/`_apply_fsdp`/`pipeline` signature, recipes, tests, docs (`BF16_OPTIMIZER_STATES.md`, `dist_moe/README.md`, `BITWISE_PARITY.md`, `numerics_debugging` skill).

## Alternatives considered
- Keep the fields in `TrainingConfig` and have the RL controller forward them to the generator: the generator would read the trainer's config, and `parallelize` would still take the whole `TrainingConfig`.
- Put precision on the model config: duplicated on `trainer.model` and `generator.model` with an equality check, and dtype is a per-run choice, not architecture.

## User-facing changes
| Before | After |
| --- | --- |
| `training.dtype` | `precision.dtype` |
| `training.mixed_precision_param` | `precision.param_dtype` |
| `training.mixed_precision_reduce` | `precision.reduce_dtype` |
| `training.enable_cpu_offload` | `parallelism.fsdp_enable_cpu_offloading` |
| RL: `trainer.training.dtype` | `precision.dtype` (on `Controller.Config`) |

## Numerics
No computation change. Loss and grad_norm bitwise identical to main (01586df70), 20 steps, seed 42, deterministic, flex attention, 2 GPUs, GB300, read from TensorBoard:

| Config | Result |
| --- | --- |
| llama3 debugmodel, FSDP 2 (fp32 masters) | bitwise identical |
| llama3 debugmodel, FSDP 2, `reduce_dtype="bfloat16"` | bitwise identical |
| kimi_k3 debugmodel, FSDP 2 (bf16 masters, `dtype="bfloat16"`) | bitwise identical |

PP, `param_dtype="float32"` and FSDP CPU offload configs could not run on this host for main or this PR (a torch nightly pipelining API mismatch, an fp32 backward kernel limit, and a hang in CPU offload), so they rely on CI.

## Testing
- CPU unit suites (`tests/unit_tests/cpu`, `tests/rl/unit_tests/cpu`, graph_trainer and torchft tests touched here): same results as main. The remaining failures also fail on main on this aarch64 host (LoRA, Qwen3.5 MRoPE x3, graph_trainer Dist-MoE recipe tests, autoparallel not installed).
- `test_rl_dist_moe_recipe.py` now also covers the RL `Controller.Config` copy of the Dist-MoE check, the only guard for RL trainers; the core copy stays covered by `test_runtime_config_requires_bfloat16_unsharded_parameters`. `test_cpu_offload_requires_distinct_dp_shard_seeds` covers the renamed offload field.

- `test_generator_dist_moe_mxfp8.py` (CI `rl-b200`) has failed on main since #5691: its fake trainer model is a `SimpleNamespace` without the `named_buffers` the weight-sync helper now reads. This PR gives the fake `named_buffers` so `rl-b200` is green (test-only).
