# [rl] generator: route a mixed step's decode requests to the GDN decode kernel (4/7)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5671) · state: closed · merged: True

## Original PR description

**TLDR:** In a mixed step (prefill chunks plus one-token decode requests), the GDN op ran each decode request through the chunk kernel as its own sequence. Decode requests now take the GDN decode kernel, as vLLM does. Qwen3.5-27B TP1, 256 requests: mixed step -10.9%, batch wall time -4.7%.

```text
main:     prefill chunks + decodes -> chunk kernel (one sequence per decode)
this PR:  prefill chunks           -> chunk kernel (decode tokens: one null-slot sequence)
          decodes                  -> decode kernel, output added
```

**Problem**
1. vLLM puts a mixed step's one-token decode requests first, then the prefill chunks.
2. The GDN op ran every decode request through the chunk kernel as its own one-token sequence.
3. The chunk kernel's cost grows with the number of sequences: 255 decodes + 1 chunk take 867 us per layer at 27B TP1, one 2k prefill 144 us (3/7's numbers).

**Solution**
1. The builder stages the decode slots and vLLM's `prefill_*` offsets and slots (`_stage_decode_split`). The chunk kernel sees the decode tokens as one null-slot sequence.
2. A null slot gives zero output and writes no state, so adding the decode kernel's output to the chunk kernel's is exact.
3. Under graph capture the decode kernel runs on min(max_num_seqs, tokens) rows, since a FULL graph replays with any decode count. Eager runs only the decode requests.
4. Capture and FULL dummy builds always stage the split (`build_for_cudagraph_capture` passes `stage_packed=True`). At DP>1 a rank with requests but no scheduled tokens runs a one-token dummy (`_dummy_run(1)`) that replays the mixed-batch graph at the padded size; added after review.
5. Unchanged: decode-only steps; batch-invariant mode (the plain recurrence over every row).

**Results**
Numerics: not bitwise in mixed steps (decode tokens change kernel). rel L2 vs main: output 1.7e-4 to 8.1e-4, recurrent state 1.4e-3 to 1.6e-3. Other steps bitwise.

```text

step                              27B TP1          27B TP4          35B-A3B TP1      35B-A3B TP2
1 x 2k prefill                    143.8 -> 200.6   111.4 -> 129.5   132.6 -> 171.0   113.7 -> 153.4
16 decodes + 1 chunk, 8k cached   202.3 -> 252.1   153.6 -> 167.2   186.9 -> 216.8   162.1 -> 193.0
61 decodes + 4 chunks             354.8 -> 264.8   149.5 -> 132.8   278.0 -> 202.9   180.2 -> 163.3
128 decodes + 4 chunks            504.1 -> 313.5   204.7 -> 146.7   362.4 -> 234.9   259.1 -> 174.7

End to end, Qwen3.5-27B TP1, GB300, FULL graphs, 512-token prompts x 256 new tokens, greedy, median of 3 interleaved runs,
```

**Verdict: Approve.** Nothing new since the 40bc20838 review. The squashed head bbb4e7e has the reworded autotune comment, and I found no new problems. A maintainer still needs to review.

**What this PR does.** In a packed (mixed) step, vLLM puts the one-token decode requests first. Before this PR, the chunk kernel ran each of them as its own sequence. Now `_stage_decode_split` stages a second set of offsets and slots in which the chunk kernel sees all the decode tokens as one sequence on the null slot. The decode requests then go to `recurrent_gdn_decode`, and its output is added to the chunk kernel's. Both kernels give zero output for null slots, so the add is exact.

**Example.** 2 decode requests, then a 3-token prefill. Slots are 5, 7, 9 and capacity is 4.
```text
before: chunk kernel, cu_seqlens [0,1,2,5,5,5], slots [5,7,9,0,0]   -> 3 sequences
after:  chunk kernel, cu_seqlens [0,2,2,5,5,5], slots [0,0,9,0,0]   -> decode tokens on the null slot
        decode kernel, slots [5,7] (eager) or [5,7,0,0] (FULL capture), output added to rows [:2] or [:4]
```

### Re-checked at HEAD
- `update_block_table` (`linear_attention.py:275-280`) copies `extent + 1 = capacity + 2` query offsets before restaging. That matches the slice `_stage_decode_split` reads, and `state_indices` has already been restaged for this group, so the per-group slots are right.
- Under FULL, `capacity = min(max_num_seqs, num_actual_tokens)`, so `conv_output[:capacity]` stays in bounds. Rows past `num_decodes` are prefill tokens on null slots, so they add zero. This is why the decode output needs its own buffer and an add, rather than writing into `output` directly.
- `num_decodes <= num_reqs <= capacity`, so the `zero_()` slices are well-formed. All the staging is GPU-side, with no host sync.
- The convolution still uses the original `non_spec_*` offsets and slots. KDA reads only `non_spec_*`, and no torchtitan code reads the new `prefill_*` or `decode_*` fields outside the GDN op.

### What I checked
I traced the split by hand. Decode requests come first (`reorder_batch_threshold = 1`).
- `prefill_query_start_loc = clamp(qsl, min=num_decodes)` with `[0] = 0` turns the decode tokens into one sequence `[0, num_decodes)` on null slot `prefill_state_indices[0] = 0`. Requests `1..num_decodes-1` become empty sequences. Prefill requests keep their original index, so `has_initial_state[j]` still lines up.
- Under FULL capture the decode kernel runs on `capacity = min(max_num_seqs, num_actual_tokens) <= num_actual_tokens` rows, so the slice is always in bounds. Rows `>= num_decodes` are prefill tokens on null slots, so they give zero output and the `add_` stays exact. Writing the decode output straight into `output` would clobber those prefill rows, so the separate buffer plus add is needed.
- `update_block_table` restages from its own `state_indices` after copying `capacity + 2` query offsets, which is exactly what `_stage_decode_split` reads. The extended `test_update_block_table_matches_build` covers this.
- `build_for_cudagraph_capture` zeroes the new slot buffers. `prefill_query_start_loc` can keep its values because any valid offsets are fine at capture time.
- Decode-only steps never take this path (the dispatcher routes uniform decode to the `FULL_DECODE_ONLY` keys). The single-token branch and batch-invariant mode are unchanged.
- Lint and CPU CI pass. The RL GPU unit tests were still queued when I checked.

### Requests (non-blocking)
1. **The real-kernel test skips the FULL row count** (`test_gdn_graph_metadata.py:457`). It only runs the eager `num_decodes` rows. The production default (FULL) runs the decode kernel on `capacity` rows, so prefill tokens land on null slots. Only the mocked test covers that today. Please parametrize over capture mode and check that the null slot's state is unchanged.
2. **The "must not autotune" requirement isn't enforced** (`gdn.py:306`). The warmup before a packed capture usually has `num_decodes == 0`, so capture can be the decode kernel's first launch at `capacity` rows. Either pin no-autotune explicitly, or say in the comment which property of the kernel makes this safe.

### Nits
- `test_gdn_graph_metadata.py:501`: the 1e-2 tolerance is 6-12x above the reported error. About 5e-3 would catch more regressions.
- `_stage_decode_split` runs in the builder that KDA shares, so KDA packed steps pay about 5 small launches per group to fill buffers they never read. That's cheap, but a short note in the docstring (or KDA adopting the same split later) would make it clear this is intentional.
- The FULL pure-prefill regression (+57 us per GDN layer at 1 x 2k on 27B TP1, about +1.7 ms per step) is called out in the PR body and has a TODO. Consider filing a tracking issue so the capped-grid fix doesn't get lost after the stack lands.
