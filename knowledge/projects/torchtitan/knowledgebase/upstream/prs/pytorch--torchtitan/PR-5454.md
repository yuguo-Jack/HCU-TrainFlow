# [rl] Verifiers generation server: faster request path, required sampling params (4/14)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5454) · state: open · merged: False

## Original PR description

**TLDR:** Token-id validation is 5.7x faster (~390 -> 68 us per 7k-token prompt) and the response build 1.4x faster with no GC passes. Together they were ~42% of the controller thread's GIL-holding samples at 10 nodes, so its GIL-holding time drops by ~25% (estimated from microbenchmarks, not re-measured). `temperature`, `top_p` and `max_tokens` are now required (the rollouter always sends them).

**Problem**
1. Each generate request type-checks every prompt token in a Python generator expression (~7k tokens in the profiled run).
2. Each response builds one dict and one f-string per completion token.
3. At 10 nodes the controller thread holds the GIL in 94% of samples: (1) is 23.6% of them, (2) 18.0%.
4. (2)'s per-token dicts start a GC pass every ~700 tokens: 61% of the controller's GC time.

**Solution**
1. `_validate_token_ids` checks `set(map(type, token_ids)) <= {int}` and returns the list without a copy.
2. The logprobs content is written as JSON text and spliced into the response dict.
3. `temperature`, `top_p` and `max_tokens` are now required. A missing one used to sample at the defaults (temperature 0.8, 100 tokens); the rollouter always sends all three.
4. Unchanged: the response JSON (the test now asserts the exact payload).

**Results**
```text
Microbenchmark, AMD EPYC 9654, Python 3.12, GC on; us per call, 3 repeats (min-max)
                                   main                          this PR
validate a 7,000-token prompt      385-409                       67-68
response body, 1,000 tokens        721-748, 1 GC pass            507-531, 0 GC passes
response body, 8,000 tokens        5,858-5,884, 11 GC passes     4,263-4,312, 0 GC passes

py-spy --gil, 120 s, controller of a 10-node Qwen3.5-27B SWE RL run (same validation and response code)
share of GIL-holding samples       _validate_token_ids 23.6%, response build 18.0%
expected saving                    23.6% x 83% + 18.0% x 27-30% = ~25% (not re-measured)
```

You may ask: why not orjson? It's a new dependency, and the request decode it would also speed up (13.4%) is smaller than either fix here.

NOTE: a non-finite logprob now fails the client's JSON parse instead of its finiteness check; the request fails either way.

**Test plan**
```bash

```
`test_parse_sampling_config_requires_temperature_top_p_max_tokens` fails on main; `test_validate_token_ids` and the exact-payload assertion pin unchanged behavior.
