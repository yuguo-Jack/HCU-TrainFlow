# [rl] Every generate call goes over HTTP to its generator (10/14)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5506) · state: open · merged: False

## Original PR description

**TLDR:** Every `generate` call now goes over HTTP straight to its generator, so the controller and the router are no longer middle-men for prompts and completions. That matters for two reasons:
1. with many nodes, one process can't carry every byte;
2. agent harnesses expect an HTTP endpoint to plug into.

At ~62 Verifiers calls/s on 8 x H100, the controller's CPU drops from 22.6 to 13.9 s per training step, and its GC from 1.41 to 0.78 s.

```text
before   native     rollout worker --pickle--> router --pickle--> generator
         Verifiers  agent --HTTP--> controller GenerationServer --pickle--> router --pickle--> generator
after    native     rollout worker --acquire/release--> router;  rollout worker --HTTP--> generator
         Verifiers  rollouter --acquire / release_rollout, once per rollout--> router;  agent --HTTP--> generator
```

**Stack** (14 PRs, merge bottom-up; this PR is in **bold**)

PRs 2-7 don't need the HTTP design and can be reviewed now. PRs 8-14 wait on the design discussion on PRs 9 and 10.

**Problem**
1. **Native:** a rollout worker calls `generate` on the router actor, which pickles the prompt and the completion through itself on every call.
2. **Verifiers:** each agent model call goes to an aiohttp `GenerationServer` inside the controller, then to the router, then to the generator.
3. **The controller pays:** that server decodes every request and builds every response on the controller's main thread, and keeps every in-flight prompt in its heap.
4. **How much:** DAPO-Math, 64 prompts x 16 samples, 512-token completions (~62 calls/s): 22.6 s of controller CPU per training step (39% of a core) and 1.4 s of GC.

**Solution**
1. **The generator serves HTTP:** rank 0 of each generator runs `GenerationServer`, bound to `Generator.generate`.
2. **The router places, the caller sends:** `InterGeneratorRouter.acquire(session, group_id)` returns a generator's index and URL and takes one unit of load (a lease); `release(index, group_id)` gives it back.
3. **One client:** `GeneratorClient` serves both paths. Native takes a lease per call (routing unchanged); Verifiers takes one per rollout, returned by `router.release_rollout` with its policy versions and metrics.
4. **Two response formats:** vLLM's token-in response by default, which Verifiers reads unchanged; `"response_format": "torchtitan"` returns raw int32 token ids and float64 logprobs.
5. **Unchanged:** what a training sample contains, weight sync, priority, the prompt-length check, native routing.

**Results**

Numerics: bitwise identical training samples (token, logprob and prompt bytes, policy versions, messages, rewards, advantages, generator metrics). Only the router is faked there; its `release_rollout` -> generator `release_sessions` hop is covered by unit tests.

Step times are within run-to-run noise: one node doesn't bind on the controller, and the high-rate Verifiers runs are bound by the single env server.

You may ask:
- Why not let the router forward the HTTP bodies? Every byte would cross one Python process that also runs weight sync: the controller's problem, moved one process over. A router mesh sharded by session would fix that, as new work; with look-aside, capacity grows with the generators.
- Why not serve vLLM's own HTTP app? Its response build costs ~9 us per completion token (~1 us here), and it drops policy versions and metrics.
- Why float64 logprobs? Every Python float round-trips exactly, -inf and NaN included.
- Why does a Verifiers release go through the router? The lease goes back in the same message even if the caller is cancelled, and `acquire` returns no actor handle (unpickling one per call cost 1.4% of the controller's GIL).

NOTE:
- A Verifiers rollout stays on one generator for its whole episode. main pinned each trace by its own session and re-pinned it off an overloaded generator; native rollouts still re-pin. In a CPU routing sim with one generator at 2x step time, re-pinning was 5-9% faster.
- The HTTP server shares the generator's event loop: engine step p99 +5-13 ms, the agent's slowest-call p99 +0.5-1.4 s (p50 unchanged).
- Each native turn adds one router round trip (`release`); the router's ceiling isn't measured.
- A generator advertises `socket.getfqdn()`. At setup the router checks every URL from its own host. Tested on one host.
- The server is unauthenticated and listens on every interface, like a vLLM server. Core RL now imports aiohttp (already a vLLM dependency).

**Test plan**

New tests in `test_generation_server.py` (both formats, a client that hangs up, the lease, the metrics codec), `test_inter_generator_router.py` (lease, `release_rollout`, URL check) and `test_engine_loop.py` (the server closes after the engine loop).

reply from claude:
- **Body:** rewritten. The flow diagram is in the TLDR, under the two goals: the controller can't stay the middle-man at many nodes, and agent harnesses expect an HTTP endpoint.
- **`_InterGeneratorRouterActorEndpoints`:** added a docstring. Monarch only calls methods marked as endpoints, and the router class stays free of Monarch, like the generator, trainer and batcher. Each method here marks the router method of the same name and calls it via `super()`.
- **The `try`:** its `finally` gives the generator lease back even if `run` raises or the task is cancelled; main had no lease. Added a comment.
- **`base_url`:** added a type hint and a one-line example (`"http://host-3.example.com:41233/v1"`). Verifiers takes an OpenAI-style base URL and keeps one HTTP client per distinct client config. So giving every rollout on a generator the same config shares one connection pool.
- **Session vs trace vs rollout:** added an example to the docstring. A rollout has one trace per agent (the trainable one plus sub-agents), and each trace's id is its session id. So traces `"a1"` and `"b7"` give `session_ids=["a1", "b7"]`. PR 2 released them one call each; here one call releases all of a rollout's sessions, then its lease.
- **`_METRIC_TYPES`:** gone. The codec now sends each metric's attributes and rebuilds any `MetricValue` subclass, so a new metric type with plain-number attributes needs no change here. The test round-trips all 7.
