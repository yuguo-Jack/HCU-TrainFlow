# [rl] Every generate call goes over HTTP to its generator (9/14)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5506) · state: open · merged: False

## Original PR description

**TLDR:** Every `generate` call now goes over HTTP straight to its generator, so the controller and the router no longer carry prompts or completions. At ~62 Verifiers calls/s on 8 x H100, the controller's CPU drops from 22.6 to 13.9 s per training step and its GC from 1.41 to 0.78 s.

**Problem**
1. **Native rollouts.** A rollout worker calls `generate` on the router actor, which forwards it to a generator; the prompt and the completion are pickled through the router on every call.
2. **Verifiers rollouts.** Each agent model call goes to an aiohttp `GenerationServer` inside the controller, then to the router, then to the generator.
3. **The controller pays.** That server decodes every request and builds every response on the controller's main thread, and keeps every in-flight prompt in its heap.
4. **How much.** DAPO-Math, 64 prompts x 16 samples, 512-token completions (~62 calls/s): 22.6 s of controller CPU per training step (39% of a core) and 1.4 s of GC.

**Solution**
1. **The generator serves HTTP.** Rank 0 of each generator runs `GenerationServer`, bound to `Generator.generate`.
2. **The router places, the caller sends.** `InterGeneratorRouter.acquire(session, group_id)` returns a generator's index and URL and takes one unit of load (a lease); `release(index, group_id)` gives it back.
3. **One client.** `GeneratorClient` serves every caller: native takes a lease per call (routing unchanged); Verifiers one per rollout, returned by `router.release_rollout` with its policy versions and metrics.
4. **Two response formats.** Default: vLLM's token-in response, which Verifiers reads unchanged. `"response_format": "torchtitan"`: raw int32 token ids and float64 logprobs.
5. **Unchanged:** what a training sample contains, weight sync, priority, the prompt-length check, native routing.

```text
before   native     rollout worker --pickle--> router --pickle--> generator
         Verifiers  agent --HTTP--> controller GenerationServer --pickle--> router --pickle--> generator
after    native     rollout worker --acquire/release--> router;  rollout worker --HTTP--> generator
         Verifiers  rollouter --acquire / release_rollout, once per rollout--> router;  agent --HTTP--> generator
```

**Results**

Step times are within run-to-run noise: one node doesn't bind on the controller, and the high-rate Verifiers runs are bound by the single env server.

You may ask:
- Why not let the router forward the HTTP bodies? Every byte would cross one Python process that also runs weight sync: the controller's problem, moved one process over.
- Why not serve vLLM's own HTTP app? Its response build costs ~9 us per completion token (~1 us here), and it drops policy versions and metrics.
- Why float64 logprobs? Every Python float round-trips exactly, -inf and NaN included.
- Why does a Verifiers release go through the router? The lease goes back in the same message even if the caller is cancelled, and `acquire` returns no actor handle (unpickling one per call cost 1.4% of the controller's GIL).

NOTE:
- A Verifiers rollout stays on one generator for its whole episode (main routed each trace by its own session); native rollouts still re-pin. In a CPU routing sim with one generator at 2x step time, re-pinning was 5-9% faster.
- Verifiers: metadata of traces nobody popped (retries, sub-agents) is dropped at group end, not at shutdown.
- Verifiers: the metrics prefix travels with each request, so overlapped validation can't log under training's prefix.
- The HTTP server shares the generator's event loop: engine step p99 +5-13 ms and the agent's slowest-call p99 +0.5-1.4 s in every high-rate pair (p50 unchanged); not localized.
- Each native turn adds one router round trip (`release`); the router's ceiling isn't measured.
- Tested on one host; at setup the router checks every generator's URL, so a cross-host address problem fails at start.
- The server is unauthenticated and listens on every interface, like a vLLM server.
- Core RL now imports aiohttp (a vLLM dependency).
- A failed `release_rollout` fails its rollout.
- `Generator.close` stops the engine loop before the server, so handlers fail at once instead of after aiohttp's 60 s.
- Processes log "Unclosed client session" at shutdown (TODO in `http_client.py`).
