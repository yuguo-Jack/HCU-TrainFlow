# [rl] DAPO-Math: score Math-Verify in worker processes with a hard timeout

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5186) · state: closed · merged: True

## Original PR description

**TLDR:** One model answer like `\boxed{2000^{2000^{2000}}}` froze a DAPO-Math rollout worker forever, and the run stopped with no error. Scoring now runs in long-lived worker processes with a hard timeout (60 s default). That answer scores 0 when it fires, other answers keep scoring, and a normal score costs +0.1 to 0.5 ms.

**Problem**
1. **Where scoring runs.** `RewardMathVerify` calls Math-Verify synchronously on the rollout worker's event-loop thread, which monarch runs off the main thread.
2. **The input.** sympy evaluates `2000**(2000**2000)` (`sympy/core/numbers.py:2076`): one C call that never finishes and never releases the GIL.
3. **The freeze.** No other thread in that process runs again, including the event loop that serves every group on that worker.
4. **The earlier fix.** Its thread timeout raises through `PyThreadState_SetAsyncExc`. CPython checks that only between bytecodes, so it never fires here.
5. **Math-Verify's own timeout** uses SIGALRM, which works only on the main thread.
6. **The cost.** Hung groups hold their rollout slots forever, so the trainer starves.

```text
before: event loop -> score_math_response -> sympy pow (holds the GIL)   => whole process stops
after:  event loop -> await pool.score -> pool thread -> pipe -> worker process -> sympy pow
                                          no reply in 60 s => SIGKILL the process, score 0
```

**Solution**
1. **The idea.** Score in a few long-lived worker processes, and kill the one that gets stuck.
2. **`MathVerifyPool`** (new `math_verify_pool.py`) runs `python -I math_verify_pool.py` in each process. It reads JSON lines in and writes one score per line out.
3. **Timeout.** If no score comes back within `timeout_seconds`, the answer scores 0. The process is SIGKILLed, and the next score starts a new one.
4. **Light processes.** `math_verify_pool.py` imports no torchtitan (which loads vLLM), so a process starts in ~0.3 s and uses ~70 MB.
5. **Config.** `RewardMathVerify.Config` gains `timeout_seconds=60.0` and `num_processes=4`. The Verifiers DAPO task had the same hang and now uses the same pool.
6. **Unchanged.** `score_math_response` moves as-is to `math_verify_pool.py`. The vendored `thread_timeout.py` is deleted.

**Results**

CPU repro with `timeout_seconds=5`, reward on a non-main-thread event loop as in a monarch actor; one bad answer, then a normal one 0.2 s later:

```text
answer 2000^{2000^{2000}}, gold 34   frozen >30 s         ->  0.0 at 5.01 s, normal done at 0.58 s
answer (10^{10})!                    loop blocked 12.6 s  ->  0.0 at 5.01 s, normal done at 0.52 s
answer 10^{10^{10}}, gold 34         frozen >20 s         ->  0.0 at 5.01 s, ~77 MB peak before the kill, process replaced
```

The ~0.5 s is mostly starting a second process; in a real monarch actor with warm processes, 8 normal answers took 3 ms.

Normal answers (unique inputs, shared CPU host):

```text
one score                         p50 1.96 -> 2.42 ms
16-answer group, asyncio.gather   p50 91 -> 32 ms (4 processes in parallel; before, the loop was blocked)
first score on a new process      315 ms; ~67 MB RSS per process
```

Why 60 s? The slowest of 3516 real AIME-2026 answers took 0.38 s. Symbolic Omni-MATH golds took up to 3.8 s. A longer limit only costs on answers that hang: each holds one process for the full 60 s.

You may ask:
- Why not keep SIGALRM on inside the worker process? It stops this pow, but Verifiers reported a sympy hang that SIGALRM missed.
- Why not `ProcessPoolExecutor`? Killing a stuck process fails every other in-flight future.
- Why not `multiprocessing` spawn? The child would import `torchtitan.rl` and vLLM: ~9 s and ~1.1 GB per process.
- Why not a new process for every score? That costs ~0.3 s per score.

NOTE:
- `-I` means math-verify must be in the interpreter's own site-packages, not reached through `PYTHONPATH`.
- Linux only: `prctl(PR_SET_PDEATHSIG)` kills a stuck worker process if its parent dies.
- Not run: GPU or end-to-end RL.
