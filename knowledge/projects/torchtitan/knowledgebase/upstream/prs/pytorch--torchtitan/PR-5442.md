# [attention] Flex attention: recompile limit 16, and fail instead of running eager

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5442) · state: closed · merged: True

## Original PR description

**TLDR:** Compiled flex attention now uses `fullgraph=True` and `recompile_limit=16`, in the default compile and in deterministic mode. Today, after 8 graphs, flex silently runs eagerly. Muse Spark needs 10 graphs across training, prefill and decode, so its short-query shapes ran eager flex and CUDA-graph capture failed. With this PR they compile, and a 17th graph raises instead of falling back.

**Problem**
1. **One compiled flex for every layer.** `FlexInnerAttention._compiled_flex_attn` is a single `torch.compile(flex_attention)`, shared by every layer in the process.
2. **Graphs multiply.** Each graph is keyed on the mask kind (sliding window vs global), grad mode, the first static token count, size-1 queries, and Inductor's short-query (decode) kernel.
3. **Muse Spark needs 10.** 2 mask kinds x (train static, train dynamic, no_grad dynamic, no_grad 1 token, no_grad short query).
4. **Silent eager fallback.** Without `fullgraph`, Dynamo logs `hit config.recompile_limit (8)` and runs flex eagerly: slow, and CUDA-graph capture of those shapes fails.
5. **Who hits it.** A process that runs flex at both training and inference shapes, like the Muse 2-layer benchmark. Training-only runs skip the short-query graphs; the RL generator uses vLLM, not flex.

**Solution**
1. **`fullgraph=True`:** flex never runs eagerly. A graph break or the limit raises `FailOnRecompileLimitHit`.
2. **`recompile_limit=16`:** room for 2 mask kinds across training and inference shapes.
3. **Deterministic mode too:** `--debug.deterministic` recompiles flex without autotuning (`distributed/utils.py`); it gets the same two settings.
4. **Unchanged:** kernels, block masks, kernel options.

**Results**
```text
Numerics: bitwise identical wherever main compiled (same graphs, same kernels). Shapes that main
          ran eagerly after the limit now run the compiled kernel.

Muse Spark inner attention, layer 0 (sliding 2048) + layer 1 (global), 128/16 heads x 64,
GB300, CUDA graphs, us; all 9 shapes in one process
mode              T          main           this PR
train fwd+bwd     2k/4k/16k  compiled       compiled (same graphs)
prefill no_grad   2k         603.9          604.0
                  16k        6484.1         6483.4
decode no_grad    1          16.5           16.5
                  8          capture fails  30.9
                  256        40.3           41.1
flex graphs                  8, then eager  10, 0 graph breaks

DeepSeek-V3 16B (one mask kind, no GQA): 5 graphs on main and this PR, all 9 shapes compile.

Forcing more graphs (a new mask_mod per call):
main:     "hit config.recompile_limit (8)", then 24 calls run, 16 of them eagerly
this PR:  FailOnRecompileLimitHit: Hard failure due to fullgraph=True   (on the 17th graph)
```

You may ask: why not reduce the graphs instead? They are real kernel differences (mask kind, grad mode, decode kernel); `dynamic=True` still made 8 and fell back.
NOTE: decode with 17-127 query tokens and 8 query heads per KV head (Muse decode 64) now raises `InductorError` on stock PyTorch: Inductor's flex decode kernel rejects that shape. On main it ran eagerly because the limit was hit first. A separate PyTorch fix makes it compile. Only flex inference hits it.
NOTE: a model with more mask kinds can now hit the limit and crash where it used to run eagerly; that's intended. Not tested: the CP flex subclasses and the FA4 flex backend (they share this compile), multi-GPU, GraphTrainer.

**Test plan**
- `pytest tests/unit_tests/cpu/models/common/test_flex_attention.py tests/unit_tests/cpu/models/common/test_cp_attention.py tests/unit_tests/gpu/models/common/test_varlen_attention.py`: same results on main and this PR (40 pass; 16 fail in both from the local environment).
- TODO before merge: one training step of a Dist-MoE scale recipe (they keep flex, on the FA4 backend). It covers training shapes only.
- TODO before merge: the no_grad graph-limit check (a new mask per call, no_grad, T=256) at the scale recipe's block sizes: (256, 256) global, (256, 128) sliding, FA4 backend. Expected: the error fires only where main silently ran eager.
