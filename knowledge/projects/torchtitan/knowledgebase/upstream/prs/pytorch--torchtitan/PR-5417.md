# [dsv4] HcPost: mix the residual branches (sum over the residual's branch axis)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5417) · state: closed · merged: True

## Original PR description

Fixes #5416.

`HcPost` kept the `dim=2` of DeepSeek-V4's reference `hc_post`. The reference is written for `[B, S, hc, hc, D]`, where `dim=2` is the residual's branch axis. On torchtitan's `[T, hc, hc, D]` product, `dim=2` is the other branch index, so each branch was only scaled by its row sum of `comb` and never mixed with the others.

This PR sums over `dim=1`:

`y[j] = post[j] * x + sum_i comb[i, j] * residual[i]`

That is what the reference and transformers' `DeepseekV4DecoderLayer` (`comb.transpose(-1, -2) @ hidden_states`) compute.

No parameter changes. Checkpoints trained before this fix still load, but they were trained without the mixing.

**Test plan**

`tests/unit_tests/cpu/models/deepseek_v4/test_deepseek_v4_mhc.py` (new) compares `HcPost`, on a non-symmetric `comb`, with:
- the reference `hc_post`, copied verbatim and run on the `[B, S, ...]` layout;
- the closed form `comb^T @ residual`.

```
pytest tests/unit_tests/cpu/models/deepseek_v4/test_deepseek_v4_mhc.py
```

With this change, both tests pass. With the current `HcPost`, both fail, with every element mismatched. `ufmt`, `flake8` and `codespell` pass on the changed files.

**The fix is correct. I recommend landing it**, once there's numerical evidence that it changes training behavior as expected (see the end of this review).

### Correctness

I worked through the index math in `torchtitan/models/deepseek_v4/mhc.py:145-148`:

- `comb.unsqueeze(-1)` has shape `[T, i, j, 1]`, and `residual.unsqueeze(-2)` has shape `[T, i, 1, D]`. The product `P[t, i, j, d] = comb[t, i, j] * residual[t, i, d]`.
- **Old code (`dim=2`, summing over `j`):** `y[i] = post[i]*x + residual[i] * sum_j comb[i, j]`. Each branch is only rescaled by its own row sum, and the branches never mix.
- **New code (`dim=1`, summing over `i`):** `y[j] = post[j]*x + sum_i comb[i, j] * residual[i]`, which is `comb^T @ residual`.
- **Reference (`[B, S, ...]` layout):** the product is `[B, S, i, j, D]`, so the reference's `dim=2` is `i`. The new code matches it, and it also matches the `comb.transpose(-1, -2) @ hidden_states` form the PR description cites from transformers.

The bug was worse than a wrong axis. `HcSplitSinkhorn` makes `comb` close to doubly stochastic, so its row sums are about 1. The old `HcPost` therefore reduced to roughly `post * x + residual`: a plain per-branch residual where `comb` did almost nothing. Two consequences:
1. **Official / HF DeepSeek-V4 weights gave wrong activations** when loaded into torchtitan, since every layer skipped the cross-branch mixing. This matters most for anyone fine-tuning from released weights.
2. **The `comb` parameters were close to dead during training.** That covers `hc_fn` rows `2*hc:`, `hc_base[2*hc:]` and `hc_scale[2]`. Their gradient came only through the row sums, which Sinkhorn pins near 1, so it was close to zero. The PR description notes that older checkpoints were trained without mixing. Worth stating explicitly as well: in those checkpoints the `comb` weights are essentially still at their initial values.

**Parallelism:** `comb` and `residual` use `_hc_branch_placement` (`sharding.py:54`), which shards only on the token axis (CP `S(0)`, or the SP layout) and is `I` on TP. The sum over the `hc_mult` axis stays local under every combination, so no placement or sharding changes are needed.

**Callsites:** `HcPost` is only used in `deepseek_v4/model.py:98` and `:120`, and both pass `(x, residual, post, comb)` as `[T, ...]`. The other `hc_post` hits under `torchtitan/` are only the config wiring in `flavors.py`. MTP blocks go through the same `Block`, so they pick up the fix too.

### Test (`tests/unit_tests/cpu/models/deepseek_v4/test_deepseek_v4_mhc.py`)

- Using a non-symmetric `comb` is the right choice. With a symmetric matrix, `comb @ r` and `comb^T @ r` would be equal and the test couldn't tell them apart.
- I can't call either test redundant: `test_matches_reference` pins the reference implementation, and `test_mixes_the_residual_branches` pins the closed form. Keeping both is fine.
- Nit (optional): `torch.rand` gives a positive, non-normalized `comb`. Building it with `HcSplitSinkhorn` would test with realistic inputs, but the current version already catches the bug, so this isn't needed.
- I could not run the tests in this job because `pytest` needs approval in this sandbox. The math above confirms that both assertions hold for the new code and fail for the old one.

### Suggestions

1. **Optional, efficiency:** the broadcast-then-sum materializes a `[T, hc_mult, hc_mult, D]` fp32 intermediate. That is `hc_mult` (4) times the size of the residual, and the block computes it twice. The same result can be written as:
   ```python
   y = post.unsqueeze(-1) * x.unsqueeze(-2) + comb.transpose(-1, -2) @ residual
   ```
   This avoids the intermediate and states the math directly, so the explanatory comment could get shorter. Two caveats:
   - The result is no longer bitwise identical to the reference, because the reduction order changes.
   - `comb` is fp32 and `residual` may be bf16, and `@` doesn't promote mixed dtypes, so you'd need `residual.float()` or a cast of `comb`.

   Keeping the reference form in this PR and doing the matmul as a follow-up is a reasonable split.
2. **Numerics:** this is a computation change. Per the repo guide, please attach a short loss-curve comparison on a representative dataset (e.g. C4), before vs. after, for the dsv4 debug flavor. An end-to-end parity check against transformers' `DeepseekV4DecoderLayer` (or the reference) would be stronger still, and could serve as a regression test. Nothing under `scripts/` covers DeepSeek-V4 parity today, which is likely how this slipped through.
3. **Nit, pre-existing:** the `HcSplitSinkhorn.forward` docstring says `mixes` is `[B, L, ...]` but returns `[T, ...]`. In practice it receives `[T, ...]`. It could be fixed here since it's next to the change, but it's out of scope.
