# Compile the attention residual and FFN norm (#5740)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5740) · state: open · merged: False

## Original PR description

Summary:

Why:
Qwen3 executes the attention residual add and the following FFN RMSNorm as separate eager kernels. Decode is launch-latency bound, and the issue report measures a 2.9% end-to-end improvement when this seam is compiled together. Compiling the seam changes training numerics, so the optimization must not silently alter the default training path or bypass module-call metadata when disabled.

How:
Add a non-batch-invariant `attention_residual_norm` local compile region that returns both the updated residual and its normalized FFN input. When enabled, pass the norm weight and epsilon into functional RMSNorm so the fullgraph boundary does not trace the parallelized module wrapper. When disabled, retain the original residual add and `self.ffn_norm(x)` module call so GraphTrainer FQN tagging, profiler annotations, and sharding buckets remain unchanged. Keep the region opt-in through `LocalCompileConfig`.

Differential Revision: D129126504

**Verdict: Request changes** -- turning this region on by default changes the main Qwen3 training path. That breaks an existing CPU unit test, probably changes the golden numerics with no explanation, and the region claims batch invariance without evidence.

**What this PR does.** It adds a `local_compile` region, `attention_residual_norm`, to `qwen3/model.py`. The region fuses the post-attention residual add with `ffn_norm` and returns both the updated residual and the FFN input. The region is added to `Qwen3Model.Config`'s default `local_compile.regions`, so it runs in both training and the vLLM generator, which builds from the same model config.

**Example.**
```python
# before (eager): 2+ kernels per layer
x = x + attn_out
ffn_out = self.feed_forward(self.ffn_norm(x))
# after (one Inductor graph when the region is enabled, the Qwen3 default)
x, ffn_input = _attention_residual_norm(x, attn_out, self.ffn_norm)
ffn_out = self.feed_forward(ffn_input)
```
The forward is the same math, but RMSNorm now runs as an Inductor reduction instead of eager `F.rms_norm`. The bits will probably differ (the PR's own test uses `assert_close`, not equality).

`batch_invariant=True` claims that the Inductor-compiled RMSNorm is batch-invariant, and nothing backs that up. Every other RMSNorm-style region in the repo declares `False`: `offset_rmsnorm` (qwen3_5/model.py:89), `gated_rmsnorm` (common/norm.py:35), and `muse_spark_rmsnorm`. In batch-invariant mode the eager reductions go through the `batch_invariant_ops` overrides. A compiled region lowers its own Triton reduction instead, and Inductor picks the reduction config per shape (persistent vs. looped, split reduction when there are few rows, as in decode). If someone enables this region with `DebugConfig(batch_invariant=True)`, nothing raises, and trainer/generator logprob parity can drift without any error.

All in-repo batch-invariant recipes already set `local_compile.regions = []`, so declaring `False` costs nothing:
```suggestion
@local_compile("attention_residual_norm", batch_invariant=False)
```
