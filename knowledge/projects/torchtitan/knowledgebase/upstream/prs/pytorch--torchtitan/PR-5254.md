# [rl][Observability] Count every token in perf/trainer throughput; log controller GC time

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5254) · state: open · merged: False

## Original PR description

**TLDR:** `perf/trainer/tokens_per_second_*` counted only loss tokens (completions), so in a multi-turn RL run the fwd/bwd rate fell 71k -> 35k tok/s while the trainer did the same work. Both now count every non-padding token, and `trainer/tokens_per_second` is no longer logged, so all token throughput lives under `perf/trainer/`. A new `perf/controller/gc_seconds` times the controller's garbage collection.

**Problem**
1. **Numerator.** The controller passes `packed.global_loss_token_counts[0]` to `compute_perf_ratio_metrics`: completion tokens only.
2. **Prompts don't count.** Prompt and env tokens run through forward and backward, but the metric leaves them out.
3. **When.** In multi-turn RL, each turn re-sends an env message of roughly fixed size. As the policy writes shorter replies, completions become a smaller share of each sequence.
4. **How much.** Qwen3.5-4B, FSDP 4, ~51 turns per rollout: completions fell from 64% to 35% of the tokens, and `tokens_per_second_fwd_bwd` fell 71k -> 35k tok/s. fwd/bwd time per step stayed flat once rollouts stopped growing.
5. **Two compute throughputs.** `perf/trainer/tokens_per_second_fwd_bwd` (global, timed on the controller) sits next to `trainer/tokens_per_second` (per GPU, timed on the trainer), in different units.
6. **GC is invisible.** The same trainer-bound run paused the controller 15-32 s per full garbage collection, and no metric showed it.

**Solution**
1. `perf/trainer/tokens_per_second_full_step` and `perf/trainer/tokens_per_second_fwd_bwd` count every non-padding token: `packed.global_routing_token_counts[0]`, which the batcher already sums over microbatches and DP ranks.
2. `trainer/tokens_per_second` (per GPU, padding included, timed on the trainer) is no longer logged.
3. `compute_perf_ratio_metrics(num_global_valid_tokens=...)` becomes `num_global_tokens`, since "valid tokens" means loss tokens elsewhere in the same file.
4. `perf/controller/gc_seconds` (sum and max per step): `GCTimer` times the controller's Python garbage collection through `gc.callbacks` (~0.9 us per collection). `controller/gc/gen{0,1,2}/` splits it by GC generation (collections, seconds and the longest pause, objects collected), outside `perf/` so the console doesn't print it.
5. Unchanged: `trainer/tflops`, `trainer/mfu_percent`, the loss normalization, and every `step_time_ratio`.

**Results** (before this PR, on the run that exposed it)

```text
multi-turn RL, Qwen3.5-4B, FSDP 4, steps 2 -> 69
completion share of tokens            64% -> 35%
perf/.../tokens_per_second_fwd_bwd    71.1k -> 34.8k tok/s    (loss tokens)
  same, every token (derived)         ~111k -> ~99k tok/s     (line above / completion share)
4 x trainer/tokens_per_second         117.8k -> 100.6k tok/s  (padding included; 97k-102k since step 23, when rollouts reached ~33k tokens)
fwd/bwd time per step                 750-910 s since step 23
```

You may ask:
- Why drop `trainer/tokens_per_second` instead of `tokens_per_second_fwd_bwd`? To keep every token throughput in one place, `perf/trainer/`, which the console prints by default. Divide by the trainer GPU count for a per-GPU rate.
- Why do `trainer/tflops` and `trainer/mfu_percent` stay under `trainer/`? They measure hardware use: each trainer rank computes them from its own token count, padding included, since the GPUs compute padding too. Moving them would rename two keys and add them to the console's `perf/` panel, which this fix doesn't need.
- Why `global_routing_token_counts` on a dense model? Its entry 0 is `(~padding_mask).sum()` for every model; only MTP adds entries.

NOTE:
- Dashboards that plot `trainer/tokens_per_second` lose it. Both `perf/trainer/tokens_per_second_*` jump up, since they now count prompt and env tokens (1.6x-2.9x on the run above).
- `trainer/tflops` and `trainer/mfu_percent` still count padding and the trainer's blocking weight-push wait. Both are logged on their own: `train_batch/padding_frac`, `perf/trainer/step_time_ratio/blocking_trainer_push_model_state_dict`.
- GC time during validation or between steps lands in the next step's `gc_seconds`.
