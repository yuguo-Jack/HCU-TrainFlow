# [Loss] Preserve caller FSDP policies across chunked backward

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5563) · state: closed · merged: True

## Original PR description

## why

`ChunkedLossWrapper` runs several head-only backwards before decoder backward. main restores head sync unconditionally on the final chunk, overwriting the caller's FSDP and HSDP accumulation policies. an inner root callback can also reduce earlier decoder gradients before the current microbatch arrives.

pipeline schedules choose their backward policy after the loss runs. the wrapper now follows the schedule's manual-finalization owner from the first head pass, so GPipe, 1F1B and Interleaved1F1B all defer every head microbatch until schedule finalization, the same way PP no-sync already treats every other group on the stage.

## what changed

- keep runtime policy and grouped-forward handling in `torchtitan/distributed/fsdp_lifecycle.py`, shared by loss and validation. the loss loop uses `before_last_forward` and `after_forward` without private FSDP reads.
- save and restore each group's reduction, replica all-reduce and reshard settings and the root's `is_last_backward`, including when a chunk raises.
- keep decoder gradients, prefetched weights and root finalization out of the inner head-only backwards. outside manual finalization, retain pending-gradient detection so a shared norm/head group coalesces its accumulated gradients into one reduction.
- defer head reduction unconditionally under manual pipeline finalization, including the first microbatch. parameter residency stays with the schedule. outside pipelines, preserve the caller's early-reshard policy and the unreduced-gradient lifetime.
- complete partial grouped forwards for training with a frozen decoder and for evaluation cleanup. register root iteration reset after dynamic pipeline metadata inference on success and failure, preserving gradients between normal accumulated schedule steps.
- replace the private-state mock with real FSDP lifecycle observations, including tuple multi-output unshard and reshard behavior.
- regenerate the three A10G pipeline goldens whose head reduction order changes.

GraphTrainer's production path uses SimpleFSDP and keeps its separate reduction owner.

## pipeline numerics and goldens

one reduction per step changes the head's fp32 summation order from `RS(g0) + RS(g1) + ...` to `RS(g0 + g1 + ...)`. with bf16 parameters and fp32 reduction the drift stays around 1e-6 relative, steps 1 and 2 stay bitwise equal, and the first changed step is 4 for `llama3_pp.txt` and 3 for `gpt_oss_pp.txt` and `deepseek_v3_cp_pp.txt`.

`e41cf117e` imports the new A10G values from the "Baseline metrics in import file format" section of the [models job](https://github.com/pytorch/torchtitan/actions/runs/41582312136/job/125739765775) at `636e16d` and keeps the file headers. the [main models job](https://github.com/pytorch/torchtitan/actions/runs/41754606663/job/126327728943) at `73c4ebdac` ran the same `2.16.0.dev20261102+cu132` build and reproduced the previous goldens exactly, so the runner repeats across runs and the only change in the imported values is this reduction order. the models job on the current head is the second same-environment run of the new values.

the MI350X copies of the same three files need a ROCm run. `ciflow/rocm` on this PR would produce them here, otherwise they follow the [#5423](https://github.com/pytorch/torchtitan/pull/5423) refresh pattern, since `integration_test_rocm.yaml` runs these configs on every push to main.

`test_dense_llama3_hsdp_graph_pp_vs_eager` uses eager Interleaved1F1B PP as its baseline with `rtol=1e-4` and `atol=1e-5`. its workflow is path-filtered to `torchtitan/experiments/graph_trainer/**` and won't run on this PR, and the observed drift sits well inside that tolerance, so the next scheduled main run covers it.

## last-stage memory and throughput

four Hopper GPUs on one host (sm_90, 132 SMs, 139.8 GiB each, reported by `nvidia-smi` as `NVIDIA L20X`), PyTorch `2.16.0.dev20261102+cu130` with the CUDA 13.0 `580.95.05` forward-compat user-mode driver on kernel driver `570.172.08`. the host is shared and eight free GPUs weren't available, so the runs use FSDP2 `dp_shard=2` × `pp=2`.

the model is the Llama3 8B shape (32 layers, dim 4096, vocab 128256) with flex attention, `ChunkedLossWrapper`, bf16 parameters, fp32 reduction, one 8192-token sequence per microbatch, eight microbatches per step and accelerator graphs off. each run trains 20 steps and reports the median per-rank throughput and step time after five warmup steps, plus the per-rank `max_active` and `max_reserved` memory over the run. main is `887d89561` (the following main commit only changes SFT goldens), and the PR arm is code-identical to the current head. main and PR alternate order across two repetitions.

| schedule | main tps/GPU | PR tps/GPU | main step | PR step | last-stage peak active | last-stage peak reserved |
| --- | --- | --- | --- | --- | --- | --- |
| 1F1B | 8939, 8951 | 9316, 9354 | 3.666, 3.661 s | 3.518, 3.503 s | 61.49 → 57.80 GiB | 71.66 → 67.95 GiB |
| 1F1B, 2 accumulation steps, `fsdp_defer_gradient_reduction` | 9063, 9066 | 9418, 9425 | 7.231, 7.229 s | 6.959, 6.954 s | 61.49 → 57.80 GiB | 71.67 → 67.95 GiB |
| Interleaved1F1B, 2 stages per rank | 9242, 9259 | 9601, 9623 | 3.546, 3.539 s | 3.413, 3.405 s | 68.90 → 66.47 GiB | 79.12 → 74.56 GiB |
| GPipe | 2286, 2364 | 2251, 2438 | 14.33, 13.86 s | 14.56, 13.44 s | 128.93 → 127.72 GiB | 134.88 → 134.88 GiB |

1F1B and Interleaved1F1B gain about 4% throughput on every rank, and the deferred-accumulation row covers `finalize_gradients=False` across schedule steps with the same result. GPipe keeps all eight microbatches' activations live and runs at 96% of device memory, so its throughput spread is wider than any difference and stays inconclusive. the first-stage ranks peak at 68.75 GiB under 1F1B and 75.27 GiB under Interleaved1F1B in both arms, so the job-wide peak in these two layouts is unchanged and the reduction lands on the output stage. under GPipe the output stage sets the job-wide peak, and it goes from 128.93 to 127.72 GiB with the first stage at 126.53 GiB in both arms.

a 1F1B profiler step on the output-stage rank shows 33 all-gathers and 25 reduce-scatters on main against 17 and 17 with this change, with all-gather time going from 142.1 to 47.8 ms and reduce-scatter time from 98.6 to 90.1 ms. the first-stage rank runs 17 and 17 in both arms.

a six-step 1F1B memory snapshot on the output-stage rank shows where the difference comes from. main's peak holds 3.914 GiB of FSDP collective buffers, exactly the size of two fp32 copies of the 128256 × 4096 head gradient, and this change holds none at its peak. the other allocation categories at the peak stay within 0.4 GiB of each other, including 7.48 GiB from `_fsdp_param.py:alloc_storage` and 13.00 GiB from `_restore_unsharded_grad_dtypes` in both arms. the snapshot covers one profiled step, so its peaks of 54.00 and 50.32 GiB sit below the 20-step maxima with the same 3.68 GiB difference as the table. so in these runs keeping the head unsharded until finalization adds nothing at the peak, and main's per-microbatch head reduction is what places staging buffers on top of the live activations.

losses vary run to run in both arms at this learning rate, so these runs measure memory and speed only. numerics come from the lifecycle scenario and goldens above.

### Part 1 -- The problem, explained simply

**Background: what deferred accumulation is trying to do.** Say one optimizer step uses 3 microbatches (mb0, mb1, mb2). With `defer_fsdp_gradient_reduction`, `TrainingEngine` (`training_engine.py:772-776`) tells the FSDP root:

| | `requires_gradient_sync` | `reshard_after_backward` | `is_last_backward` |
|---|---|---|---|
| mb0, mb1 | False | False | False |
| mb2 | True | True | True |

So each param group should keep its **unsharded** gradients locally through mb0 and mb1, then do **one** reduce-scatter per group during mb2's backward. With HSDP, `set_requires_all_reduce(is_last)` works the same way for the replica all-reduce.

**What `ChunkedLossWrapper` does inside one microbatch.** It splits the sequence into N chunks and runs a separate `chunk_loss.backward()` for each chunk, only through `lm_head`, because the hidden states are detached. After the loop, the decoder backward runs once, as a separate autograd pass.

That gives N+1 backward passes per microbatch, and FSDP treats each one as a full backward.

**Bug A: the wrapper overwrites the caller's settings.** On main, the wrapper does this:
```python
lm_head.set_requires_gradient_sync(False)     # chunks 0..N-2
...
lm_head.set_requires_gradient_sync(True)      # final chunk, unconditionally
...
lm_head.set_reshard_after_backward(True)      # after the loop, unconditionally
```
Example: on mb0 the engine says "don't sync", but the wrapper turns sync on for `lm_head` anyway. So `lm_head` reduce-scatters on every microbatch, and deferral never applies to it. `set_requires_gradient_sync(True)` also turns `all_reduce_grads` back on, which undoes the engine's HSDP `set_requires_all_reduce(False)`. These are mostly wasted collectives. The math is still right, since the sum of reductions equals the reduction of the sum.

**Bug B: an inner chunk backward reduces the decoder too early.** When an autograd pass touches any FSDP module, FSDP's root post-backward callback runs over **every** group in the root context, not just `lm_head`. On mb2 (sync=True), the decoder groups are still holding unsharded grads from mb0 and mb1. So:

```
mb2, chunk-0 backward (lm_head only)
  -> root final callback visits decoder groups
  -> they have pending mb0+mb1 grads and sync=True
  -> reduce-scatter now                         <- reduction #1
mb2, decoder backward
  -> mb2 grads arrive -> reduce-scatter again   <- reduction #2
```
Each decoder group gets reduced twice instead of once, plus an early `is_last_backward` finalize. That matches the "7 reduce-scatters -> 3" numbers in the description.

**Bug C: a grouped `fully_shard([norm, lm_head])` with a frozen decoder.** FSDP fires the group's post-forward, which registers the backward hooks, only after *all* modules in the group have run forward. The chunk loop only calls `lm_head`, so the group never finishes its forward. With a frozen decoder, the inputs don't require grad, so no input-side hook gets registered either. As a result, nothing triggers the group's backward lifecycle.

**The PR's fix:**
1. Save each group's reduce/reshard policy and restore it on exit, including on exceptions, instead of hard-coding `True`.
2. If any group already has pending grads (or HSDP partial state), keep sync off on **all** groups and set `is_last_backward=False` during the chunks. The outer decoder backward's root callback then reduces everything, including `lm_head`, exactly once.
3. For case C, manually call FSDP's `_post_forward` so the output hook gets registered.

### 1. Correctness

**Correct as written**

- **Bug B (decoder reduced too early) is real, and the defer path fixes it.** In each inner `chunk_loss.backward()`, the root final callback calls `post_backward()` on *every* group in `all_states` that isn't already `POST_BACKWARD`. On the last microbatch, that reduce-scatters the decoder's pending mb0+mb1 gradients during chunk 0, and then again in decoder backward. In the defer path, every group has `reduce_grads=False` and `reshard_after_backward=False`, and `is_last_backward=False`. Those callbacks then only accumulate gradients, and decoder backward does a single reduction.
- **Early reshard with pending gradients (my earlier item 3) is safe.** FSDP's own `reduce_grads=False` branch of `post_backward` calls `reshard()` *before* `to_accumulated_grad_if_needed()`. `to_sharded()` only frees all-gather storage, and `_unsharded_param.grad` survives. So the wrapper relies on the same contract FSDP relies on internally, and the new comment at `loss.py:571-572` is accurate. Withdrawn.
- **Bug C (frozen decoder, grouped head) is real on main.** Only chunk 0's logits finish the grouped forward. Chunks 1..N-1 get neither an output pre-backward hook nor an input post-backward hook, because frozen inputs carry no hook. Their `lm_head` gradients sit in `unsharded_param.grad` with nothing to reduce them. Calling `_post_forward` each chunk fixes this. Implicit prefetch indices stay balanced, because each chunk adds one post-forward index and its backward pops one.
- **Exception path.** The `finally` block restores everything the setup touched. The test checks the policies both after a mid-loop failure and after `reset_iter_state()`.

**Needs attention before merge**

**(a) PP: what the wrapper preserves is the previous microbatch's policy.** Under PP, `ChunkedLossWrapper` runs inside the last stage's *forward* step (loss computation). PyTorch pipelining sets the FSDP policy in `backward_maybe_with_nosync`, i.e. *after* the loss. On main, the wrapper force-reduces `lm_head` on every microbatch, so this didn't matter. With this PR, `lm_head`'s reduction follows whatever the previous stage backward or the previous step's finalization left behind. The pending-gradient detection can also switch to the defer path partway through the schedule.

Mathematically it should still be correct, because PP's finalization reduces whatever is pending. But it changes *how* `lm_head` gradients are grouped into reductions, which changes floating-point summation order. My guess is that this explains the DeepSeek-V3 / GPT-OSS **PP** loss/grad-norm failures in the model job. I haven't confirmed it, and it needs a same-environment main-vs-PR rerun. If the comparison there is exact-match, the expected-numerics change needs to be stated and re-baselined. If it's tolerance-based, it's a real bug. Either way, it shouldn't land unexplained.

**(b) Production uses only the grouped layout; the separate layout is test-only.** `torchtitan/distributed/fsdp.py:339-358` always does `fully_shard([norm, lm_head])`, or `[tok_embeddings, norm, lm_head]` with weight tying. The test matrix covers grouped, which is good. The tied 3-module group isn't covered, though: its group pre-forward fires on `tok_embeddings`, whose input is integer token ids, so no input post-backward hook gets registered. Please add a `grouped_tied` variant to the matrix, or at least run the weight-tied model through `fsdp_deferred_gradient_reduction`.

**(c) A pre-existing perf issue that the defer path fixes only some of the time.** With the default `is_last_backward=True`, chunk 0's root callback runs `_finalize_backward()` on *all* states. ### 2. Readability and maintainability

There is room here. In rough order of impact:

**2.1 Drop pending-gradient detection by always isolating the head pass (when `decoder_requires_grad`).**
`defer_to_decoder` exists because the inner callbacks touch non-head groups. Mask those groups *unconditionally* instead:

```python
# decoder_requires_grad: decoder backward follows in this microbatch and owns
# the root finalization. Inner head-only passes must not reduce, reshard or
# finalize any non-head group.
for group in non_head_groups:
    group.reduce_grads = False
    group.reshard_after_backward = False
state_ctx.is_last_backward = False
# head groups: reduce_grads=False until the final chunk, then the caller's policy (unchanged)
```

- In the default plain-FSDP step, non-head groups have no gradients during chunks, so masking them changes nothing numerically. `lm_head` still reduces at the final chunk, overlapped with decoder backward, exactly as on main. The bitwise-identical default is preserved.
- In deferred mode on the last microbatch, decoder groups can't reduce early, so bug B is fixed without the `_post_backward_pending` / `_partial_reduce_output` reads.
- It also fixes (c) for every path, and stops a prefetched last block from being resharded and then re-gathered between chunk 0 and decoder backward.
- It deletes the `None | Callable` yield and the mid-loop `restore_gradient_sync()` call. There is a single path when the decoder is trainable and a single path when it is frozen. The frozen path leaves the other groups and `is_last_backward` alone, since no decoder backward follows.
- **Cost:** with a grouped `[norm, lm_head]` in deferred mode, the last microbatch does one extra small reduce-scatter (norm's mb2 gradient, in decoder backward), so the test would expect `3` instead of `2`. I think that's worth it to drop the two private *reads* that encode FSDP's notion of "pending".

### 3. What belongs in the upstream FSDP API

Listed by how much private state each removes from torchtitan:

1. **A scoped "partial backward" for the root callback.** This is the main one. For example: `with fsdp_root.partial_backward():` or `backward(..., fsdp_partial=True)`. Inside the scope, the root final callback only runs `post_backward` for states whose hooks actually fired, skips `_finalize_backward`, and leaves `post_forward_order` / `_post_forward_indices` alone. Chunked loss, PP's split-backward / zero-bubble, and any multi-pass backward need these semantics. It would remove the `is_last_backward` overwrite and the non-head group masking, and it would fix (c) upstream.
2. **Value-based policy snapshot and restore.**
   ```python
   policy = module.get_fsdp_policy(recurse=False)   # reduce_grads, all_reduce_grads, reshard_after_backward, reshard_after_forward (incl. int / mesh info)
   with module.fsdp_policy(requires_gradient_sync=False, reshard_after_forward=False, reshard_after_backward=False, recurse=False): ...
   ```
   Also decouple `set_requires_gradient_sync` from `all_reduce_grads`, or add a `keep_all_reduce=True` argument. Today `set_requires_gradient_sync(True)` silently undoes `set_requires_all_reduce(False)`, which is the original HSDP part of bug A.
3. **Finishing a partial grouped forward.** Either `FSDPModule.finish_forward(output)`, or make a re-entrant call to one member of a `fully_shard([a, b])` group register the output pre-backward hook on every call. This would replace both the frozen-head workaround here and `post_validate_fsdp_for_cuda_graph`.
4. **A documented contract that `reshard()` keeps unreduced gradients.** FSDP already relies on this internally. Documenting it turns `loss.py:571-572` into a contract instead of an observation.
5. **`has_pending_gradients()` / `has_pending_partial_reduction()`.** Only needed if (1) doesn't land and §2.1 isn't adopted.

Each private access should get a `TODO(<upstream issue link>)` pointing at the item above that replaces it. Please open (1)–(3) as PyTorch issues, since they are the exit path for this code.

The "5 -> 3" comes from whatever FSDP policy the previous microbatch left behind, so the number of head reductions depends on the schedule (GPipe: no change). ### Why PP is different

Under PP, the loss runs inside the last stage's **forward** action. That covers `ChunkedLossWrapper` and its head-only chunk backwards. The FSDP policy for a microbatch's backward is set later: the stage backward turns sync off, and PP turns it back on only when it finalizes at the end of the step. So the "caller's policy" the wrapper snapshots (`fsdp_lifecycle.py:75-85`) is whatever the previous action left behind.

**Example.** One stage holds `decoder` plus the grouped `(norm, lm_head)`, with 1F1B and 3 microbatches. The action order is F0 B0 F1 B1 F2 B2, then finalize. This is the setup behind the 5 -> 3 count, the same shape as `test_chunked_loss_fsdp.py:128-156`.

| action | policy the wrapper sees | main: head group | PR: head group |
|---|---|---|---|
| F0 | sync on (left by last step's finalize) | reduce-scatter mb0 | reduce-scatter mb0 |
| B0 | PP turns sync off | | |
| F1 | sync off (left by B0) | **forces sync on, reduce-scatter mb1** | keeps it off, accumulates locally |
| F2 | sync off (left by B1) | **forces sync on, reduce-scatter mb2** | accumulates locally |
| finalize | PP turns sync on | head group (norm's mb2 grad) + decoder | head group (head mb1+mb2, norm) + decoder |
| **reduce-scatters per step** | | **5** | **3** |

**Why the bits change.** The math is the same, but the order of additions differs. Let `RS` be the reduce-scatter (sum over ranks) and `g_k` the head gradient of microbatch k:

```
main: shard = RS(g0) + RS(g1) + RS(g2)   # sum over ranks, then over microbatches
PR:   shard = RS(g0) + RS(g1 + g2)       # add mb1+mb2 locally first, then over ranks
```

Float addition isn't associative. In fp32, `(1 + 1e8) - 1e8 = 0`, but `1 + (1e8 - 1e8) = 1`. Each step's difference is about 1 ulp (the CPU run in the description saw `2.98e-8`), and the optimizer compounds it. That fits the goldens matching for a few steps and then diverging: step 3 for gpt_oss, step 6 for deepseek_v3. *Unverified:* that the GPU drift comes only from this.

### Should we do it?

The goal, yes. On main, lm_head is the only parameter in a PP stage that reduces every microbatch. Everything else waits for PP finalization, and lm_head is usually the largest single weight (Llama3-8B: 128256 x 4096, about 525M params). But the PR doesn't implement that goal deliberately:

- **The count depends on the schedule.** GPipe runs every forward before any backward, so every forward sees "sync on" and the head still reduces per microbatch. That is why the description's GPipe run is bitwise equal to main. 1F1B reduces at F0 and again at finalize. Interleaved1F1B falls in between, depending on how many last-stage forwards run before its first backward.
- **The policy it "preserves" was never chosen.** Under PP it is the previous action's leftover, so no comment or test can state the intended behavior.
- **The memory cost isn't measured.** Deferring keeps the head's unsharded gradient alive across microbatches on the last stage. It also removes the per-microbatch head all-gather, which is a throughput gain worth measuring.

### Why there's normally one reduce-scatter per step

PyTorch's `PipelineStage` switches its FSDP root to no-sync at the start of every **backward** action (`reduce_grads=False`, `reshard_after_backward=False`, `is_last_backward=False`). The step's finalization then turns sync back on and runs `post_backward` on every group once. So each group reduces once per schedule step. With `defer_fsdp_gradient_reduction`, that becomes once per optimizer step, because `finalize_gradients` is False on earlier accumulation groups (`training_engine.py:782-784`).

### Why lm_head breaks that pattern under chunked loss

The loss runs inside `forward_one_chunk`, and `ChunkedLossWrapper` calls `chunk_loss.backward()` there (`loss.py:819-821`). So lm_head's backward happens **during F0, before B0 has set no-sync**. At that point, FSDP still holds what the previous step's finalization left behind: sync on and reshard on. On step 1 it holds FSDP's defaults, which are the same.

| action | lm_head policy at that moment | main | this PR |
|---|---|---|---|
| F0 | sync on (left by previous finalize) | forces sync on: **RS** | keeps sync on: **RS** |
| B0 | stage sets no-sync | | |
| F1, F2 | no-sync (left by B0, B1) | forces sync on: **RS** each | keeps no-sync: accumulates |
| finalize | stage sets sync on | RS head group + decoder | RS head group + decoder |

At F0, the PR's `defer_reduction` (`fsdp_lifecycle.py:86-101`) comes out False for plain FSDP, for two reasons:
- the `manual_backward_finalization` clause only fires when HSDP replica all-reduce is off;
- nothing is pending yet at the start of the step.

So `before_last_backward` restores `reduce_grads=True`, and the final chunk reduces mb0. Under GPipe, every forward runs before any backward, so every forward sees sync on. That's why GPipe gives the same result as main.

### How to defer it

The stage already sets `set_manual_backward_finalization(True)` in `forward_one_chunk`, before the loss runs. You can see the same call mirrored at `models/kimi_k3/pipeline_parallel/stage.py:178-180`. So the wrapper can already tell at F0 that PP owns finalization. Defer unconditionally in that case:

```python
defer_reduction = state_ctx.manual_backward_finalization or (
    outer_backward_follows
    and any(
        policy.group._post_backward_pending
        or policy.group._partial_reduce_output is not None
        for policy in policies
    )
)
```

   It passed on `e002910` because that revision grouped the reductions exactly like main, and it fails now because the grouping really changed. This is the "head reduces once per step on every schedule" behavior you asked for.
3. **The drift is tiny and starts late.** Steps 1-2 are bitwise equal in all three tests, and the gap stays around 1e-6 relative. My best explanation, *not verified*: the defaults are `mixed_precision_param=bfloat16` and `mixed_precision_reduce=float32`. Summing a few bf16-valued gradients in fp32 is usually exact, so changing the order only changes a few elements. Small fp32 weight differences are also rounded away when the weights are cast to bf16 for the forward, until enough of them accumulate.
4. **The other PP tests have no golden files.** `kimi_k2_5_muon_pp+fsdp+ep`, `qwen3_5_moe_fsdp+tp+ep+pp`, `gpt_oss_pp+fsdp+ep+sacop` and `muse_glimmer_mm_tp+cp+pp+sp` only check that training runs, so they pass whatever the numerics. Muse Glimmer has no FSDP anyway.
