# [CI Fix][GraphTrainer] Stop the Flex bitwise tests from compiling flex per layer

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5547) · state: closed · merged: True

## Original PR description

**TLDR:** Two CI fixes for the GraphTrainer and 8 GPU Integration jobs.
1. Fixes #5366. The Flex eager-vs-trace bitwise tests compiled flex once per layer in the eager reference, and after 8 graphs Dynamo silently ran unfused eager flex. The traced side was correct; the eager reference changed. With this PR the eager reference compiles flex once, like the core and RL trainers, and hitting the recompile limit raises instead of falling back.
2. Fixes PP after #3980. #3980 made PP preprocessing return 4 values, but two callers still unpacked 3, so every PP + CUDA graph integration test and the GraphTrainer PP numerics test fail on main with `ValueError: too many values to unpack (expected 3)`.

## 1. Flex bitwise tests compiled flex per layer (#5366)

**Problem**
1. **The eager reference was annotated.** `_run_steps` called `annotate_graph_trainer_model` for both `Trainer` and `GraphTrainer`. It wraps every submodule's forward with `annotate_fn({"module_fqn": fqn})`. Only GraphTrainer's graph passes read these tags. The core and RL trainers never set them.
2. **Dynamo now guards on the annotation.** pytorch/pytorch#198959 (October 10 nightly, the first failing one) adds an `FX_ANNOTATION` guard. Each layer's `inner_attention` has a different `module_fqn`, so the eager compiled flex compiles once per layer: 8 graphs for Qwen3 debugmodel_moe, all identical.
3. **The graphs carry over between tests.** Dynamo caches them on `flex_attention`'s code object, which outlives the `torch.compile` wrapper rebuilt in `setUp`. Llama3 Flex leaves 6. Qwen3 MoE Flex then passes the limit of 8 at its third layer.
4. **Silent fallback.** Past the limit, Dynamo runs flex eagerly, which is the unfused implementation, so the eager loss changes: `hit config.recompile_limit (8)`, then `eager vs aot_fx_trace: loss mismatch`.

**Solution**
1. **Annotate only GraphTrainer runs.** The eager reference stays unannotated, like the core and RL trainers.
2. **`fullgraph=True` and `recompile_limit=16`** on the test's flex compile, the same settings as #5442. Hitting the limit raises instead of falling back.
3. **`torch._dynamo.reset()` in `setUp`.** Tests no longer share flex graphs.
4. **Unchanged:** the GraphTrainer runs, their annotations, and every assertion.

## 2. PP callers still unpacked 3 values after #3980

**Problem**
1. #3980 made `TrainingEngine._preprocess_microbatch_group` return `(arg_mbs, kwarg_mbs, target_mbs, loss_kwarg_mbs)` under PP.
2. `prepare_for_capture` (PP + CUDA graphs, added by #5241 before #3980 landed) still unpacked 3 values. Every PP test in the 8 GPU features job fails there: 3d, pp_1f1b, pp_dp_tp, pp_looped_zero_bubble, lora, and others. On main, that job passes at #3980's parent `efdde5eda` and fails at #3980 `a4a62b349`.
3. GraphTrainer PP reuses the core preprocessing, and its forward-backward loop also unpacked 3 values, so `test_dense_llama3_hsdp_graph_pp_vs_eager` fails. The GraphTrainer job uses `set -eux`, so it stops there and never reaches `test_bitwise_deterministic.py`.
4. The CPU test for `prepare_for_capture` still fed the old 3-tuple, which hid the mismatch.

**Solution**
1. **`prepare_for_capture`** unpacks 4 values and passes the first microbatch's loss arguments plus `global_loss_token_counts` to schedule initialization. Initialization calls the loss on that microbatch, as the real step does.
2. **GraphTrainer PP** drops the fourth element. GraphTrainer rejects per-microbatch loss arguments earlier, so it is always empty, and both paths now return `(arg_mbs, kwarg_mbs, target_mbs)`, as before #3980.
3. **The CPU test** feeds the PP layout with a per-microbatch loss argument and checks the loss arguments passed to initialization. It fails without the fix with the same `ValueError`.

You may ask: does the core trainer recompile flex per layer too? No. Llama3 1B (16 layers) with flex on the core `Trainer` compiles flex once and never recompiles. Only an annotated eager model recompiles per layer.

NOTE: GraphTrainer's validator runs the annotated model eagerly, so Flex validation on a model with more than 8 layers should hit the same per-layer recompiles. Not covered here.
NOTE: `test_dense_llama3_hsdp_graph_pp_vs_eager` needs 8 GPUs, so I could not run it locally. On the PP=2 reduction, eager PP vs GraphPP misses its grad_norm tolerance (max 1.7e-4) both with this PR and at #3980's parent, so that gap comes from the reduced config, not this PR. The full 8 GPU test passed on main before #3980.
