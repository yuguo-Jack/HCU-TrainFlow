# [SDC] Use int64 digests for portable replay comparisons

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5769) · state: closed · merged: True

## Original PR description

## Summary

SDC replay fails on Ascend when comparing `uint64` digests because the backend does not support comparisons for that dtype. Using `.view(torch.int64)` preserves all 64 bits without changing the hash algorithm. I reviewed the two-file patch and the before/after validation records, including injected gradient mismatches, and confirmed that replay completes normally while still detecting mismatches.

## Why

Fixes #5734.

SDC replay currently compares `uint64` digests, which fails on backends without `uint64` comparison support:

```python
digest = torch.hash_tensor(tensor)
digest != digest  # Before: unsupported uint64 comparison.
digest = digest.view(torch.int64)
digest != digest  # After: compare the same 64-bit hash.
```

## What changed

- Reinterpret tensor hashes with `.view(torch.int64)` and use `int64` for empty/None digests.
- Update the existing tests' dtype assertions, expected complex hashes and batched-comparison inputs.

## Numerics / performance

Single-rank Llama3 debugmodel, 100 optimizer steps, seed 42, strict determinism, and the same initial checkpoint. Compared main `4759738106a6f198a4dd41c78d2a754be5d0b2c4` with replay disabled against this patch with replay enabled at every step.

**Verdict: Approve** -- this is the minimal fix agreed in #5734: all four digest sites now use `int64`, the comment requested there is in place, and the tests are updated to match.

**What this PR does.** SDC replay digests come from `torch.hash_tensor`, which returns `uint64`. They were stacked and compared with `torch.ne` / `torch.equal`, and Ascend has no `uint64` kernel for `ne`. The PR reinterprets each hash with `.view(torch.int64)` in `_hash_tensor` and switches the three zero sentinels (the empty tensor, the None buffer, the None grad) to `int64`. The view is a bit-for-bit reinterpretation: it launches no kernel, adds no collisions, and gives the same equality results. Nothing orders, adds, logs, or saves the digests.

**Example.**
```python
d = _hash_tensor(param)          # before: uint64; after: int64, same 64 bits
torch.ne(torch.stack(ref), torch.stack(cand)).any()
# before on NPU: aclnnNeTensor raises "DT_UINT64 not supported" (a backend error, not a mismatch)
# after: comparison runs; a real mismatch still raises SDCReplayMismatch
```

<details><summary>Details</summary>

- Coverage: `torchtitan/observability/sdc_replayer.py` produces digests only at `:117`, `:122`, `:432`, and `:449`, and all four are now `int64`. This matters because `torch.stack` won't combine `uint64` with `int64`, so one leftover `uint64` site would break comparison on every backend. There are no other in-repo readers of these digests. `_validate_hash_support` (`:346`) still checks only that `hash_tensor` runs, which is correct.
- Tests: the `int64` dtype assertions in `test_empty_tensor_hash_uses_zero_sentinel` and `test_complex_tensor_hash_uses_real_view` are the regression guard against `uint64` coming back. No new test is needed.
- Numerics: the replayer only reads digests and never feeds them into training. That matches the bitwise-identical loss and grad_norm runs in the description.
- Hardware: the fix has no vendor-specific branch, as Principle 9 asks.

</details>
