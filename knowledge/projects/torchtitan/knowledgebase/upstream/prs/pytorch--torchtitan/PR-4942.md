# [RL] Add Terminal-Bench 2.1 experiment via Verifiers (Qwen3.5 9B, 35B-A3B)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/4942) · state: closed · merged: True

## Original PR description

Human Note:
- This PR is using Agent-in-sandbox pattern.
- End to end run verified using coreweave cluster.

## Summary

Adds a Terminal-Bench 2.1 example: the task adapter under `torchtitan/rl/examples/verifiers/terminal_bench`, the recipes in `torchtitan_recipes/rl/verifiers_terminal_bench.py`, using the existing TitanRL/Verifiers bridge. Verifiers runs a Docker-isolated Terminus-2 agent and the Harbor verifier; TitanRL handles rollout grouping, generation, and training. TitanRL's core is unchanged.

This PR contains the whole experiment: the implementation from #4888 (commit `b758984eb`, unchanged), four fixes for rollouts that report `reward=0.000` without the model having failed, and training recipes for Qwen3.5-9B and Qwen3.5-35B-A3B.

- Training and validation tasks are Harbor datasets selected by id (`org/name@ref`), fetched and cached by the `harbor` CLI the way Verifiers does it; the recipe refuses to run if the two are the same dataset. The task-specific XML harness stays inside this experiment.
- Two model sizes share the datasets, sampling, loop and optimizer settings. Each recipe is one self-contained config in `torchtitan_recipes/rl/verifiers_terminal_bench.py`. Both train on `local/tmax@v1` (AI2 TMax, converted by `prepare_tmax.py` into `~/.cache/harbor/local_tmax_v1`) and validate on `terminal-bench/terminal-bench-2-1`.
- Validation over the 89 Terminal-Bench 2.1 tasks runs at the start and end of training, so there is no separate eval-only config.
- Setup, fidelity limits and open dependencies are documented in the experiment README.


## **100-step run (Qwen3.5-9B-Base, TMax-15K, stock Verifiers Terminus-2, lr 1e-6)**

| | step 0 (base) | step 100 |
|---|---|---|
| held-out reward (507 unseen tasks x 8 rollouts) | 0.334 | **0.417** |
| held-out pass@8 | 0.586 | 0.655 |
| training reward (mean over steps 1-50 → 51-100) | 0.344 | 0.393 |

- On held-out tasks, reward goes up by +0.083 +- 0.008 (11 SE) after 100 steps. The step-100 policy is better on 217 tasks and worse on 46.
- Most of the gain is the policy finishing tasks within the 30-turn cap more often, with the same accuracy when it finishes.

The held-out reward is the clearest evidence that training works: the per-step training curve is noisy because each step trains on 16 new tasks.

## Known gaps / follow-ups

- Daytona is not supported by Verifiers 0.3.1. This experiment uses Docker.
- Datasets are fetched by Harbor id into `~/.cache/harbor`. A cluster without access to the Harbor Hub can pre-populate that cache; loading from an arbitrary local path is not supported here.
- The published TB2.1 images do not all ship `tmux`; Harbor's Terminus-2 session installs it at run time, so the task container needs network then, as scoring already does.
- Mainline TitanRL uses GRPO rather than the colleague run's DPPO trust-region loss, uses independent generator replicas rather than one eight-way DP generator, and does not offer the same per-group KV-cache salting or dedicated asynchronous periodic validation.
- Evaluation is greedy pass@1, not the colleague's pass@5. Comparable results need pinned task/image revisions and a live GPU run against the same checkpoint.

## Results

Qwen3.5-9B-Base on TMax-15K, 100 steps, lr 1e-6, 16 tasks x 8 rollouts per step. Both arms use the same seed and task order.

| | this PR (4 patched args) | stock Verifiers Terminus-2 |

| training reward, mean | 0.358 | 0.369 |
| paired on the same 1600 tasks (PR - stock) | -0.010 +- 0.004 | |
| rollouts that hit the 30-turn cap | 49% | 39% |

- **Stock is not worse.** The patched arm hits the turn cap more often because XML rollouts take more turns.
- **Stock generalizes.** On 512 held-out tasks, the step-100 policy scores 0.417 against 0.334 for the base model (+0.083 +- 0.008).
- **Matches prime-rl.** Same model, data, harness and optimizer: the same reward on shared tasks (-0.003 +- 0.011).
- `max_turns=120` never applies under Verifiers' 30-turn cap. `enable_summarize=False` and `model_info` changed nothing observable
