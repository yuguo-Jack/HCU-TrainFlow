# [RL] Enable batch-invariant FlexAttention on ROCm

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5657) · state: open · merged: False

## Original PR description

## Summary

- use compiled FlexAttention for ROCm batch-invariant trainer runs while preserving the existing eager fallback for ordinary deterministic ROCm runs
- allow ROCm batch invariance only when trainer and generator attention layers use FlexAttention
- align vLLM's paged Flex mask with the trainer through a request-independent page lookup and request-ownership mask

## Motivation

TorchTitan currently rejects all ROCm batch-invariant RL configurations and uses eager FlexAttention for deterministic ROCm training. Eager trainer attention cannot match vLLM's compiled paged FlexAttention bit-for-bit.

The original gfx950 compiled-Flex nondeterminism reproduces on the ROCm 7.2 nightly stack. On the tested ROCm 10.0 and 10.1 nightly stacks, the same emitted Triton forward and backward kernels were bitwise stable for 300 iterations.

After enabling compiled trainer FlexAttention, the remaining one-BF16-ULP difference was localized to vLLM's request-indexed `physical_to_logical[request, physical_page]` lookup. Q/K/V and reconstructed KV-cache contents were already identical. The ROCm batch-invariant path instead derives one logical index per physical page and keeps request ownership in an `int64` bitmask.

Standalone generation and the RL engine now share the same process-wide vLLM runtime configuration.

## Running ROCm batch invariance

Use the `rl_grpo_qwen3_0_6b_flex_batch_invariant` recipe as the base and disable vLLM graph replay for the ROCm run:

```python
config = rl_grpo_qwen3_0_6b_flex_batch_invariant()
config.generator = dataclasses.replace(
    config.generator,
    engine=dataclasses.replace(
        config.generator.engine,
        cuda_graph=dataclasses.replace(
            config.generator.engine.cuda_graph,
            mode="NONE",
        ),
    ),
)
```

Launch the wrapper recipe in a ROCm 10.0 environment with a vLLM build compatible with the installed Torch:

```bash
export HIP_VISIBLE_DEVICES=0,1,2,3
export VLLM_BATCH_INVARIANT=1
export HF_ASSETS_PATH=/path/to/Qwen3-0.6B

python3 -m torchtitan.rl.train \
  --module <module-containing-the-wrapper> \
  --config <wrapper-function> \
  --output-dir outputs/rocm_flex_batch_invariant
```

Run at least two optimizer steps and verify that each training line reports `bit_wise/logprob_diff/max: 0`. The second step checks parity after the optimizer update and trainer-to-generator weight transfer.

## Validation

Tested on gfx950 (AMD Instinct MI350X) with Torch `2.16.0.dev20261018+rocm10.0`, Triton `3.9.0+gitfc8d31a5`, and vLLM `0.32.0rc1.dev369+g1b2a66639.rocm100`.

A two-step Qwen3-0.6B TitanRL run on the rebased branch completed with:

```text
Train | Step: 1 ... bit_wise/logprob_diff/max: 0
Train | Step: 2 ... bit_wise/logprob_diff/max: 0
```

Earlier 25-step runs also produced zero maximum logprob difference for Qwen3-0.6B, 1.7B, 4B, and 8B:

- 0.6B: https://forge.coreweave.com/wandb/rissinha-amd/rocm_batch_invariance/runs/mk6j4qvu
- 1.7B: https://forge.coreweave.com/wandb/rissinha-amd/rocm_batch_invariance/runs/dj122pxg
- 4B: https://forge.coreweave.com/wandb/rissinha-amd/rocm_batch_invariance/runs/gsbwh33o
- 8B: https://forge.coreweave.com/wandb/rissinha-amd/rocm_batch_invariance/runs/wbzall1v

Focused CPU tests: `10 passed`.

## Scope

- plain FlexAttention models only; ROCm varlen remains unsupported
- validated on gfx950 with ROCm 10.0 userspace
- the ownership mask supports at most 64 concurrent requests
- ROCm Flex batch invariance currently requires `cuda_graph.mode="NONE"`; graph replay is tracked in #5725

Related: #3960

**Verdict: Request changes** -- the core fix replaces a private vLLM method with an unexplained, boolean-equivalent mask, with no upstream issue. On top of that, the determinism gate switches on `batch_invariant` instead of the ROCm version the PR shows is the real cause.

**What this PR does.** On ROCm it lifts the blanket ban on RL batch invariance when every trainer and generator attention layer uses FlexAttention. In batch-invariant mode the ROCm trainer runs compiled Flex instead of eager (`set_determinism`). On the generator side it monkeypatches vLLM's `FlexAttentionMetadata.get_paged_mask_mod` with a request-independent page lookup plus an int64 ownership bitmask, capped at 64 concurrent requests. Standalone `generate.py` now shares the engine's renamed `configure_runtime`, which is public because a second module now calls it.

**Example.**
```
ROCm, recipe rl_grpo_qwen3_0_6b_flex_batch_invariant
before: Controller.Config -> ValueError "batch_invariant mode is not supported on ROCm"
after:  ROCm 10.x + cuda_graph.mode="NONE"   -> runs, compiled trainer Flex, patched vLLM mask, logprob_diff 0
        ROCm 10.x + default mode="FULL"      -> ValueError, but only inside the generator actor at engine build
        ROCm 7.2                              -> passes validation, runs compiled Flex (nondeterministic per the PR)
        ROCm + varlen (controller)            -> ValueError "requires FlexAttention"
```

### Questions
- Under CUDA graph replay, the patched `mask_mod` closes over fresh tensors (`physical_to_logical.amax`, `physical_request_mask`) computed per build, not persistent buffers. Is that part of why #5725 needs `mode="NONE"`, beyond the recompile-limit failure described there?

<details><summary>Details</summary>

- Correctness of the bitmask mask: given vLLM's `physical_to_logical` (rows filled with -1 and scattered from the valid block-table entries), a shared prefix-cache page always maps to the same logical index, so `amax(dim=0)` plus the ownership bit equals the original `physical_to_logical[q_req, block] >= 0` test. `sum` over distinct powers of two equals OR, and bit 63 doesn't overflow. Nothing asserts that invariant, so if vLLM ever shares a physical block at different logical positions, the mask would be silently wrong.
- `batch_invariant` is only reachable from RL (`Trainer.Config.__post_init__` rejects it for SFT), so the `set_determinism` change only affects ROCm RL trainers.
- Smaller alternative for 1/2: if the page mapping is valid on all hardware, apply it whenever Flex + batch-invariant is on, delete `_configure_rocm_flex_batch_invariance`'s hardware branch, gate `set_determinism`'s eager fallback on the ROCm version, and do all checks in `Controller.Config`. That is roughly -30 lines from the current diff.

</details>

Not verified: the 1-ULP root cause, determinism on ROCm 7.2 vs 10.x, and the graph-replay interaction. These need a GPU run, and I couldn't read vLLM's upstream `get_paged_mask_mod` source in this environment. A maintainer still needs to review, since this touches `torchtitan/distributed/utils.py`.

File: `torchtitan/rl/generator/vllm/batch_invariance.py` · line 99

This replaces vLLM's `FlexAttentionMetadata.get_paged_mask_mod` (a private upstream method) with a full re-implementation. Two problems:

1. **The root cause isn't explained.** The old and new mask_mods return the same booleans for every `(q, kv)` pair; the only difference is the gather `physical_to_logical[q_req, block]` vs. `physical_to_logical[block]` plus a bitmask test. A boolean-identical mask that changes attention output by 1 BF16 ULP points at Inductor/Triton codegen or block-mask construction (full vs. partial blocks) rather than at the lookup itself. Without that explanation we can't tell whether this fix holds up when vLLM or Triton changes, or whether it only hides the problem for the tested shapes. It's also unclear why CUDA Flex batch invariance reaches 0 diff with the upstream mask but ROCm doesn't (this is yuankaichen-amd's unanswered "useful for other hardware?" question).
2. **It's an upstream patch with no TODO or issue.** Per the repo rules, a workaround for a vLLM gap needs a `TODO` with a vLLM issue link, and the fix should be proposed upstream (e.g. a request-independent paged mask in vLLM's Flex backend). If it's correct on all hardware, the simplest torchtitan-side form is to apply it whenever Flex + batch-invariant is on and drop the ROCm-only branch.

At minimum, add the TODO and upstream issue, and put the codegen-level root cause in the PR description.
