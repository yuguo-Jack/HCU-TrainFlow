# [rl] Size the trainer LR schedule from async_loop.num_training_steps

[Upstream PR](https://github.com/pytorch/torchtitan/pull/4939) · state: open · merged: False

## Original PR description

> **Draft: needs a golden regeneration before it can land.** This changes the LR schedule of the config behind the 8-GPU RL loss guard. `tests/assets/losses/rl_grpo_cuda.txt` must be regenerated on the GPU runner (details below). I don't have access to that runner.

## Summary

The RL trainer builds its LR schedulers in `TrainingEngine` from `trainer.lr_scheduler`, with `training_steps=trainer.training.steps`. That value is the schedule horizon whenever `lr_scheduler.total_steps` is `None`.

The RL loop never reads `trainer.training.steps`; it runs `async_loop.num_training_steps` optimizer steps. No RL recipe sets `training.steps`, so the horizon silently stays at the `TrainingConfig` default of 10000, whatever the run length.

For example, `rl_grpo_gpt_oss_20b_varlen` (alphabet-sort) runs 10 RL steps with `warmup_steps=2`, linear decay and `min_lr_factor=0.0`. The LR multiplier before each scheduler step is:

```
before: 0.5000 1.0000 1.0000 0.9999 0.9998 0.9997 0.9996 0.9995 0.9994 0.9993 0.9992
after:  0.5000 1.0000 1.0000 0.8750 0.7500 0.6250 0.5000 0.3750 0.2500 0.1250 0.0000
```

So the configured decay is, in effect, a constant LR. The opposite mismatch is worse: a horizon shorter than the run makes a linear decay keep going below `min_lr_factor`.

## Change

This PR adds `_with_rl_lr_horizon(trainer_config, num_training_steps)` in `rl/controller.py`. `Controller.setup_async` applies it at the one place the trainer actor is spawned.

- If `lr_scheduler.total_steps` is set, the config is returned unchanged. An explicit `total_steps` remains the way to pin a different horizon; the checkpoint resume test recipe already does this.
- Otherwise, the trainer gets a copy (`dataclasses.replace`) with `training.steps = num_training_steps`. The controller's own config, and any dump of it, is not modified.
- If `training.steps` was set explicitly and differs from `num_training_steps`, a `UserWarning` says it is being replaced and points to `lr_scheduler.total_steps`.
- The horizon is logged at INFO when the trainer is spawned.

It is applied at the spawn site so that the horizon comes from the config that is actually running, however it was built or edited (CLI, `replace`, in-place edits). In the RL trainer path, the only reader of `trainer.training.steps` is the LR scheduler build.

**Behaviour changes:**

- **Changed:** only schedules that actually decay, i.e. the alphabet-sort recipes with `warmup_steps=2` and linear decay to `min_lr_factor=0.0`, and configs derived from them.
- **Unchanged:** recipes with `min_lr_factor=1.0` (dapo_math, search_r1, verifiers, and the alphabet-sort recipes with `warmup_steps=0`). Every in-tree recipe has `warmup_steps <= num_training_steps`.
- **Clamping:** a warmup longer than the run is now clamped to the run length by the scheduler's existing clamp, which logs a warning.
- **Resume:** resuming with a different `num_training_steps` now resizes the schedule, unless `total_steps` is pinned.

## Golden regeneration needed (blocking)

The loss guard in `.github/workflows/integration_test_8gpu_rl.yaml` runs `scripts/rl/loss_compare.py --config rl_grpo_qwen3_0_6b_varlen_batch_invariant ... --assert-equal` against `tests/assets/losses/rl_grpo_cuda.txt`. That recipe uses the same schedule shape as the example above (`warmup_steps=2`, linear decay, default `min_lr_factor`), and `loss_compare.py` forces 10 steps.

The LR multiplier is identical for optimizer steps 1–3 and differs from step 4 on (0.9999 before, 0.8750 after). So the recorded losses should differ from step 5 on, and the guard will fail on this change alone.

It needs the workflow's own invocation, with `--export-result` in place of `--import-result ... --assert-equal`:

```
python scripts/rl/loss_compare.py --hf-assets-path $MODEL_PATH \
  --config rl_grpo_qwen3_0_6b_varlen_batch_invariant \
  --export-result tests/assets/losses/rl_grpo_cuda.txt \
  --options='--trainer.parallelism.tensor_parallel_degree 4 --generator.parallelism.tensor_parallel_degree 4 --num_generators 1'
```

I can't run it without the A10G runner. I'd appreciate it if a maintainer could regenerate the file, or tell me how you'd like to handle it: in this PR, or in a stacked PR that lands together with it.

## Test plan

New `tests/rl/unit_tests/cpu/test_controller_lr_horizon.py`. It builds the real `LRSchedulersContainer` the way `TrainingEngine` does and steps it `num_training_steps + 1` times:

- `test_lr_schedule_spans_the_rl_run`: warmup peaks inside the run, the last RL step is below peak, the schedule reaches `min_lr_factor` right after the last step and never goes below it, and the controller's config is unchanged.
- `test_lr_schedule_follows_a_step_count_set_after_construction`: `num_training_steps` is edited in place to 7 and to 30.
- `test_explicit_lr_total_steps_opts_out`
- `test_explicit_training_steps_is_replaced_with_a_warning`
- `test_default_training_steps_is_replaced_without_a_warning`
- `test_setup_async_spawns_the_trainer_with_the_rl_horizon`: runs the real `Controller.setup_async` with the mesh helpers monkeypatched and checks that the trainer is spawned with `training.steps == 7`.

The file sits in `tests/rl/unit_tests/cpu`, so the existing CPU RL workflow picks it up.

Run on Linux x86_64 with Python 3.12, torch 2.14.0+cpu, torchmonarch 0.6.0 and torchstore at main. vLLM was installed without its CUDA dependencies.

```
PYTHONPATH=$PWD pytest -p no:asyncio tests/rl/unit_tests/cpu/test_controller_lr_horizon.py
# this PR:                        6 passed
# controller.py reverted to main: 6 failed

PYTHONPATH=$PWD HF_HUB_OFFLINE=1 pytest -p no:asyncio --continue-on-collection-errors \
  --ignore=tests/rl/unit_tests/cpu/test_muse_glimmer_renderer.py tests/rl/unit_tests/cpu
# this PR: 325 passed, 2 skipped, 1 error
# main:    319 passed, 2 skipped, 1 error
```

Two parts of the suite could not run locally:

- `test_verifiers.py` hits a collection error because the optional `verifiers` package isn't installed here. It fails the same way on main.
- `test_muse_glimmer_renderer.py` was ignored because its tokenizer fixture downloads from the HF Hub, which this machine can't reach.

The GPU integration tests and the loss guard were not run.
