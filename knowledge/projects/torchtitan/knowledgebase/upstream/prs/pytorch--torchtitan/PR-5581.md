# [rl] Muse Spark DAPO-Math GB300: train on FSDP 8 x TP 4 x CP 4 x EP 16 (128 GPUs)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5581) · state: closed · merged: True

## Original PR description

## TLDR

`muse_spark_816b_a42b_dapo_math_gb300_config` now trains on the layout our Muse Spark 816B RL runs use on GB300: FSDP(shard) 8 x TP 4 x CP 4 x EP 16 on 128 GPUs, instead of FSDP(shard) 64 x TP 4 x EP 4 on 256 GPUs. The generator is unchanged.

## Problem

1. With EP 4, each routed expert is FSDP-sharded over 64 ranks. The expert all-gathers (bf16) and reduce-scatters (fp32) cross racks every step, and that traffic, not compute, sets the trainer's step time.
2. The recipe needs 256 trainer GPUs for that.

## Solution

1. Trainer parallelism FSDP 8 x TP 4 x CP 4 x EP 16. EP 16 shrinks the expert FSDP group to 8; CP 4 shards each rollout's tokens over 4 ranks, so per-GPU activations and Dist-MoE scratch scale with context / (TP x CP).
2. The trainer's `ContextParallelTransform` maps `VarlenInnerAttention` to `UlyssesVarlenInnerAttention`. Muse Spark's sliding-window layers are `VarlenInnerAttention` with a window, so the one mapping covers global and windowed layers. The generator keeps plain varlen attention.
3. Dist-MoE device scratch factor 16 (= EP), so the worst case (every token routed to one rank) fits in device memory without host-backed VMM scratch.

Unchanged: the generator (DP 4 x TP 4 x EP 16, Dist-MoE, full CUDA graphs), the 65,536-token context, the loss, the optimizer and the checkpoint loading.

## Results

The layout ran our Muse Spark 816B SWE-rebench RL smoke on GB300 (3 RL steps, 131,072-token context, 4 generators): peak 186 GiB per GPU after the optimizer state, trainer MFU 15% -> 26% -> 28% over the steps, Dist-MoE scratch peaked at 22% of the factor-16 allocation (~3.5x balanced routing), weight sync 11-13 s.

NOTE: this DAPO-Math recipe itself has not been rerun with the new layout; the run above is the SWE workload at twice the context.

NOTE: Dist-MoE exchanges tokens through peer GPU memory, so each EP 16 group (4 GB300 hosts) must share one NVLink domain; the launcher must place the trainer accordingly (the docstring says so).

## Test plan

- New CPU test `test_muse_spark_gb300_recipe_shards_sequences_in_the_trainer_only`: builds the recipe and checks every trainer layer (sliding-window ones included) uses `UlyssesVarlenInnerAttention` with the same windows as the generator's plain varlen layers. Fails without the CP transform.
