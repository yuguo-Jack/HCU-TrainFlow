# Compare SDC replay RNG states exactly

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5702) · state: closed · merged: True

## Original PR description

Fixes https://github.com/pytorch/torchtitan/issues/5701

## Why
Compare CPU and accelerator RNG states byte-for-byte instead of with `torch.hash_tensor`. The hash XOR-reduces the state bytes, and the two counter updates of a single CPU draw cancel under XOR at about half of all generator positions, so a replay that consumes an extra random number can go undetected. Losses, gradients, and buffers still use tensor digests.

## What changed
This bug was existing but not caught by tests since tests did not hit this edge case

## Testing
The existing `cpu_rng` replay test now starts from the RNG position in the repro script, so it fails without this fix. Also added a test for accelerator RNG states. Also pass on my own CI

**Verdict: Approve. Please address the items below before merging.** The fix is right: exact byte comparison is the correct way to check RNG state. What's left is a misstated root cause and a redundant test.

**What this PR does.** `SDCReplayer._signature` stopped hashing the CPU and accelerator RNG states with `torch.hash_tensor`. It now stores them as `bytes` in the signature's `state` tuple and compares them with `!=`, the same way it already handled Python's `random.getstate()`. Losses, buffers and gradients are still hashed on the device.

**Example.** From #5701:
```
torch.manual_seed(0); torch.rand(2)
before = torch.get_rng_state(); torch.rand(1); after = torch.get_rng_state()
hash_tensor(before) == hash_tensor(after) == 40   # different states, same 8-bit digest
# main:  replay that draws one extra torch.rand(1) -> no SDCReplayMismatch
# PR:    bytes(before) != bytes(after)            -> SDCReplayMismatch(signature='rng:cpu')
```

### Must fix
1. PR description and `torchtitan/observability/sdc_replayer.py:392`: they give the wrong reason for the collision. RNG states are `uint8`, and `hash_tensor` XOR-reduces them into a digest with only 8 bits, so any change collides about 1 time in 256. Order-insensitivity has nothing to do with it. Also, the "What changed" section of the description currently explains why the bug was missed instead of describing the change.
2. `tests/unit_tests/cpu/observability/test_sdc_replayer.py:189`: the new test with 8 parametrized cases duplicates the existing `cpu_rng` case. Delete it, and pin the existing test with `fork_rng` + `manual_seed(0); rand(2)`.

### Should consider
- `torchtitan/observability/sdc_replayer.py:414`: drop the `.cpu()` call, which does nothing here, and use `.numpy().tobytes()` instead of `bytes(t.tolist())`.

<details><summary>Details</summary>

- **Gate:** the bug is real on main, and #5701 has a deterministic repro. Fixing it in the replayer is the right layer, because `hash_tensor` only supports the XOR mode. Exact comparison is also cheaper than before: the CPU state is about 5 KB of host-side work, and the old path paid an H2D `.to(digest_device)` copy for every RNG digest. I found no overlapping open PRs.
- **Accelerator test** (`test_signature_detects_accelerator_rng_advancement`): it calls the private `_signature`. I'm fine keeping it, because the accelerator loop can't run on CPU CI any other way, and patching `_accelerator_rng_states` around `run_fwd_bwd` would make `restore()` raise on a CPU device.
- **Diagnostics order:** `_find_signature_mismatch` checks digests before `state`. When both the gradients and the RNG state diverge, it now reports `gradient:*` where it used to report `rng:*`. This is minor and only changes which name appears in the message.
- **Follow-up (pre-existing, not for this PR):** buffers have the same weakness. A `uint8` or `int8` buffer gets an 8-bit digest, and a `bool` buffer gets a single parity bit, so changing two mask elements goes undetected. If any model registers buffers like these, compare them exactly too.

</details>

**Re-review of 1ee993f.**

**Earlier items**
1. Collision cause: **resolved, and my earlier claim was wrong.** The new wording in `sdc_replayer.py:392-394` and in the test comment is the accurate one. A single CPU draw runs `left_--` and `next_++` in the mt19937 state, and `left_ + next_` stays odd. So whenever `next_` is even, both low bytes flip only bit 0, and the two flips cancel in the byte-wise XOR reduction. That is a collision at about half of all positions, including `manual_seed(0); rand(2)` from #5701. My "8-bit digest, 1 in 256" explanation was a much weaker effect and doesn't explain the repro.
2. Redundant parametrized test: **resolved.** It's been deleted, and the existing `cpu_rng` case is now pinned with `fork_rng` + `manual_seed(0); rand(2)`. That also stops the test from depending on what earlier tests did to the RNG.
3. `.cpu()` / `bytes(t.tolist())`: **resolved.** The code now uses `.numpy().tobytes()`.

**Example.**
```
torch.manual_seed(0); torch.rand(2)            # next_ = 2 (even)
before = get_rng_state(); torch.rand(1); after = get_rng_state()
main: hash_tensor(before) == hash_tensor(after)   -> replay passes silently
PR:   before.numpy().tobytes() != after...        -> SDCReplayMismatch('rng:cpu')
```

### Must fix
1. PR description, "What changed": **still open.** It still explains why tests missed the bug instead of describing the change. One sentence would do, e.g. "`_signature` stores CPU/accelerator RNG states as `bytes` in `state` and compares them with `!=`; losses, buffers, and gradients are still hashed."

<details><summary>Details</summary>

- **New commit:** I found no new problems. Storing `bytes` in `_ReplaySignature.state` is safe with `clone()`, which shares `state`, because `bytes` is immutable. If a backend's `get_rng_state_all` ever returned device tensors, `.numpy()` would raise loudly instead of comparing the wrong thing.
- **`test_signature_detects_accelerator_rng_advancement`:** it feeds the colliding CPU states from #5701 through the accelerator loop, so it fails on main. Keeping it is fine, for the reason given in the last review.
- **Diagnostics order (minor, unchanged):** `_find_signature_mismatch` checks digests before `state`. When the gradients and the RNG both diverge, it now reports `gradient:*` first.
- **Follow-up, not for this PR:** `uint8`/`int8`/`bool` buffers still get a digest of 8 bits or less.

</details>

File: `torchtitan/observability/sdc_replayer.py` · line None

This gives the wrong reason for the collision. Order-insensitivity isn't what breaks here, because an RNG advance is not a permutation. `torch.hash_tensor` XOR-reduces the elements after upcasting each one to 64 bits. The RNG states are `uint8` tensors, so each element holds 0..255 and the digest has only 8 bits. Any change to the state then collides about 1 time in 256, which matches the `40 == 40` in #5701. A future reader could look at this comment and decide hashing is fine for other non-permuted state. Suggested wording:

```suggestion
        only when a mismatch is detected. RNG states are compared exactly: they
        are uint8 tensors, so the XOR-reduced tensor hash is only 8 bits wide.
```
