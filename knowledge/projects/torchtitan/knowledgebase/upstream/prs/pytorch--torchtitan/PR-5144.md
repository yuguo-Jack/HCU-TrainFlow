# [checkpoint] Reject incomplete checkpoints before native loads

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5144) · state: closed · merged: True

## Original PR description


Summary:
Fixes #5096.

`BaseCheckpointManager.load` only checked that a user-named checkpoint was a directory before handing it to the backend. Automatic selection (`_find_load_step`) already requires `_is_resumable_checkpoint`, but two user-named sources skipped it:
- an explicit `checkpointer.load_step=N`, and
- a native (non-HF) `checkpointer.initial_load_path`.

For the DCP manager, an interrupted save (no `.metadata`) or a Hugging Face checkpoint in either place went straight into `dcp.load` and failed with an opaque DCP/storage error. `TorchCheckpointingManager._load_checkpoint` already rejects both cases with its own `_is_resumable_checkpoint` check, but the error only says the path "is not a supported torch_checkpointing checkpointer".

`load()` now requires `_is_resumable_checkpoint` for every non-HF load, right before `_load_checkpoint`, and raises a `ValueError` that names the path, says the save never finished or it is a Hugging Face checkpoint, and points at `checkpointer.initial_load_in_hf`. The check lives in the shared `load()` so both backends and every source use the one rule that automatic selection already uses, with the same error. On the automatic path it always passes. Hugging Face loads (`initial_load_in_hf`) are unchanged: their validity rule is different (any `*.safetensors`; single-file checkpoints have no index).

Test Plan:
New tests in `tests/unit_tests/cpu/components/checkpointer/`:
- `test_checkpoint.py::test_explicit_load_step_rejects_non_resumable_checkpoint`: empty and HF-only `step-5/` raise the new `ValueError`; `dcp.load` is never called. Fails on main with `ValueError not raised`.
- `test_checkpoint.py::test_initial_load_path_rejects_non_resumable_checkpoint`: same for an empty and an HF-only `initial_load_path`. Fails on main.
- `test_torch_checkpointing.py::test_explicit_load_step_rejects_incomplete_checkpoint`: same error from the torch_checkpointing backend; backend `load` is never called. On main the backend's own check raises a different message.
- `test_torch_checkpointing.py::test_initial_load_path_rejects_hf_export`: a final HF export as `initial_load_path` is rejected before the backend. On main the backend's own check raises a different message.

`test_initial_load_path_used_when_folder_has_no_valid_checkpoints` loaded from an empty directory; it now writes a `.metadata` file. Every other `initial_load_path` use in the repo sets `initial_load_in_hf=True`, except `scripts/_checkpoint_test_config.py` and `cp_pp_numerical.py`, which load DCP checkpoints that have `.metadata`.

**Verdict: LGTM.** The fix is in the right place and is small. Every non-HF load now checks the same `_is_resumable_checkpoint` rule that automatic selection (`_find_load_step`) already uses, so both backends behave the same. The tests fail on main and pass with the fix, and they also check that the backend load is never called. My comments below are minor cleanups, not blockers.

### Correctness

- **Automatic path:** `_find_load_step` only returns steps that pass `_is_resumable_checkpoint`, so the new check can't reject a checkpoint that was picked automatically. This holds except when a checkpoint is deleted between the scan and the load, and then a clear error is what we want.
- **HF paths (`initial_load_path` with `initial_load_in_hf`, and the `hf_assets_path` fallback):** these are skipped correctly by `from_hf`.
- **`TorchFTCheckpointManager`:** it subclasses `CheckpointManager` and doesn't override `_is_resumable_checkpoint`, so it inherits the `.metadata` rule.
- **Seed checkpoints (`step-0`):** these are DCP saves with `.metadata`, so they still load through `load_step=0` and through `initial_load_path=.../step-0` (`experiments/transformers_modeling_backend/tests/cp_pp_numerical.py:179`).
- **Other callsites:** the PR description says every other `initial_load_path` use sets `initial_load_in_hf=True`. That leaves out two callsites:
  - `scripts/_checkpoint_test_config.py:113`: native load from an env var.
  - `cp_pp_numerical.py`: native seed checkpoint.

  Both point at native DCP checkpoints, so they're unaffected. A load that used to reach the backend and now raises would have failed inside `dcp.load` anyway, so nothing that worked before breaks.

### Suggestions

1. **The `_is_valid_checkpoint` check in `TorchCheckpointingManager._load_checkpoint` can never fail now** (`torchtitan/components/checkpointer/torch_checkpointing.py:352-356`).
   - That method is only called from `BaseCheckpointManager.load`, and only after the new `_is_resumable_checkpoint` check has passed.
   - `_is_resumable_checkpoint` implies `_is_valid_checkpoint`, so this check never fires.
   - Worse, it suggests the wrong rule: it accepts an HF export. Following the "reuse over duplication" guideline, I'd delete it so there is one rule in one place.

   [Fix this →](https://claude.ai/code?q=On%20branch%20pr5144%2C%20remove%20the%20now-unreachable%20%60if%20not%20self._is_valid_checkpoint(checkpoint_id)%3A%20raise%20ValueError(...)%60%20block%20in%20TorchCheckpointingManager._load_checkpoint%20(torchtitan%2Fcomponents%2Fcheckpointer%2Ftorch_checkpointing.py%20~L352-356)%2C%20since%20BaseCheckpointManager.load%20now%20enforces%20_is_resumable_checkpoint%20before%20calling%20_load_checkpoint.%20Also%20update%20the%20TorchCheckpointingManager._is_resumable_checkpoint%20docstring%20to%20no%20longer%20say%20it%20is%20only%20about%20automatic%20loading.&repo=pytorch/torchtitan)

2. **One docstring is out of date** (`torchtitan/components/checkpointer/torch_checkpointing.py:413-417`). The PR updates the base-class docstring for `_is_resumable_checkpoint`. The `TorchCheckpointingManager` version still says "Whether automatic loading may select `checkpoint_dir`" and gives "automatic loading cannot select those exports" as the reason. Now that the method gates every native load, that wording should change too.

3. **The error message could be more specific** (`base.py:319-326`). It's one message for three situations, and the advice doesn't always apply:
   - **`load_step=N` path:** pointing at `checkpointer.initial_load_in_hf` doesn't help here, because a checkpoint in the folder always wins over the `initial_*` settings. What helps is picking another step or deleting the partial `step-N/`.
   - **`TorchCheckpointingManager`:** `initial_load_in_hf` isn't supported yet, so following the advice leads straight to the "does not yet support loading Hugging Face checkpoints" error.

   Splitting the message for the `load_step` and `initial_load_path` cases would fix the first. For the second, you could let the backend supply the advice. This is optional; the current message is already far better than the opaque DCP error it replaces.

4. **Nit: the comment at `base.py:317-318`** explains why the check exists ("only checked to be directories above") instead of what it enforces. Once the earlier code changes, that will be confusing. Something like this would hold up better: `# Every native load needs a finished checkpoint; _find_load_step already filters on this, so only explicit load_step / initial_load_path can fail here.`

### Tests

- The tests cover both backends × {explicit `load_step`, `initial_load_path`} × {empty dir, HF-only dir}, and `subTest` keeps the DCP tests compact.
- Small gap: the torch_checkpointing `load_step` test covers only the empty dir, not an HF export at `step-N`. That's the exact case the old `_is_valid_checkpoint` check let through. Consider adding a subtest with `{MODEL}.safetensors.index.json`, mirroring the DCP test.
- Updating `test_initial_load_path_used_when_folder_has_no_valid_checkpoints` to write `.metadata` is right, because it used to rely on an empty directory being loadable.
