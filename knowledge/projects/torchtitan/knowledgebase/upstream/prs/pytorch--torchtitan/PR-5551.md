# [DeepSeek V3] Fuse general-shape router forward and backward

## Agent details (AI-generated)

Adapted from Yidi Wu (@ydwu4), #5258, revision
a5d8990c5e9b46e3a87007b33de8e03c09fb97b7, with original credit and license
preserved. This is an integration and generalization, not an unmodified port.

Keep the gate native and fuse sigmoid, group-limited top-k, routing weights,
map/usage counts and backward. Preserve NVIDIA's BF16 logit/selected-weight
boundaries and independent BF16 rounding for route and auxiliary score
gradients. Forced round-robin remains an explicit benchmark deviation.

Accept general legal token/expert/top-k/group dimensions with parameterized
Triton kernels. Preserve the tuned CuTe launch for the production geometry.
Match ATen's FP32 reduction order, including output-major upstreams, four
virtual-thread accumulators and unaligned vector tails. Use fresh integer
counts in the general path rather than a shape-dependent shared-counter budget.
Keep padding, remat, rank-local counters, checkpoint parameters and native
auxiliary-loss composition. Required unsupported precision/mesh/device
contracts fail explicitly; supported shapes stay fused.

**Request changes.** Under the MLPerf recipe, the fused router's BF16 backward produces different gradients from the native router, and the production GB300 CuTe kernel never runs in CI. Details are in 7 inline comments.

<details><summary>Review summary</summary>

### Blocking
1. **The override changes numerics** (`fused_dsv3_router.py:324-333`). The recipe uses a BF16 `Linear` gate, `Sigmoid(fp32)` and `routing_weight_dtype=bf16`. In that configuration the native router sums the route and aux gradients into the same `scores_TE` in FP32 and rounds to BF16 once. `_AuxLossInjection` stays in the same autograd graph, so this is how native works today. The fused kernel instead rounds each branch to BF16 separately and uses a different sigmoid-backward op order.
   - Enabling the override therefore changes training gradients.
   - The native fallback path still gives native numerics, so results depend on which path a call takes.
   - Either match native, or make the NVIDIA-style rounding an explicit choice and include a loss comparison against the unfused recipe (CLAUDE.md "Show numerical proof").
2. **Test gaps** (`tests/unit_tests/gpu/test_fused_dsv3_router.py:225`).
   - The CuTe class only runs on SM 10.3; B200 CI is SM 10.0. About 800 lines of inline PTX, DSMEM code and the arrival-counter protocol are never tested continuously, and that is the path production runs use.
   - Every module-level comparison uses a `HiMidLoLinear` gate (FP32 logits). None covers the recipe's BF16 `Linear` setup against the native `DeepSeekV3Router`.
   - Consider landing the Triton path first and the CuTe specialization separately, with a measured end-to-end gain. The current evidence is "prior qualified microbenchmarks".

### Should fix
3. **Recompiles:** `TOKENS` is a `tl.constexpr` in both Triton kernels, so each distinct token count triggers a new JIT compile. Pass bucketed values computed on the host instead (`:168`).
4. **Forward/backward dispatch can disagree.**
   - The backward doesn't check the multiprocessor count, groups or epsilon that the forward checks, so one call can mix the two backends.
   - The CuTe backward flushes subnormals to zero when not deterministic; the Triton backward never does.
   - Decide the backend once in the forward and store it on `ctx` (`:1416`).
5. **Coupling to ATen internals:** `_native_row_sum` and the unsorted-top-k ordering copy ATen implementation details (`Reduce.cuh` heuristics, `gatherTopK` output order), not contracts. That is a lot of code for bitwise parity on an 8-element sum, while the backward already differs from native on purpose (`:85`).

### Nits
- `_with_local_counter_sharding` uses string axis names; use the `DP`/`CP`/`TP` constants.
- `_generic_router_forward` takes `counter` but never uses it, yet the op still declares it mutated.
- Other override tests live under `tests/unit_tests/{cpu,gpu}/recipes/`; move the new tests there.
- `test_whole_override_compiles_without_graph_breaks` calls the eager fused module `native`, which is misleading.
- The imports inside `test_dsv3_mtp1_mlperf_recipe_contract` should be hoisted to module level.
- Typos with missing spaces: "uses256 / top8 / scale2.5" in `FUSED_DSV3.md` and "At128" in the `_native_row_sum` docstring.

I did not run the tests: running pytest in this environment needed an approval I didn't have, and no GPU was available.
</details>

- claude[bot] · comment · 2026-11-01T06:06:51Z · [source](https://github.com/pytorch/torchtitan/pull/5551#discussion_r4434600459)

File: `torchtitan_recipes/overrides/fused_dsv3_router.py` · line 333

**This changes numerics compared with the native router; it is not a drop-in fusion.** This branch is exactly what the MLPerf recipe runs: BF16 `Linear` gate, `Sigmoid(compute_dtype=fp32)` and `routing_weight_dtype=bf16`.

In the native `TokenChoiceTopKRouter.forward`, the gather branch and the aux-loss branch both read the same FP32 `scores_TE`. `_AuxLossInjection` puts the aux gradient into that same autograd graph. Autograd therefore sums both gradients in FP32, runs `SigmoidBackward` as `(g*(1-s))*s`, and the `.to(fp32)` backward rounds to BF16 once.

This kernel does something different. It rounds each branch to BF16 separately, uses `g*s*(1-s)`, and adds the two rounded values. So turning the override on changes the recipe's training gradients. The fallback path (`require_fusion=False`) still gives native numerics, so the gradients also depend on which path a call takes.

The GPU tests don't catch this because they compare against `_MegatronSigmoid` (applied twice), not against the native module.

If matching NVIDIA's numerics is the goal, it should be a visible choice: a native config option, or at least a named flag on this override. Under CLAUDE.md that also needs a loss comparison against the unfused recipe. Otherwise, the BF16 path should match native: sum both branches in FP32 and round once.

`TOKENS` is a `tl.constexpr` here and in `_generic_router_backward_kernel`, so Triton JIT-compiles a new kernel for every distinct token count. That conflicts with the "general token dimensions" claim: any workload whose `T` varies (validation with a different batch, dropless/varlen, RL) recompiles. - claude[bot] · comment · 2026-11-01T06:07:02Z · [source](https://github.com/pytorch/torchtitan/pull/5551#discussion_r4434600790)

File: `torchtitan_recipes/overrides/fused_dsv3_router.py` · line 1422

The backward picks its kernel with different conditions from the forward (`_use_tuned_router`). It doesn't check `multi_processor_count >= 128`, the group/limited/forced shape, or `epsilon`. So a call whose forward ran the Triton kernel (for example on an MIG slice, or with a different epsilon) can run its backward on the CuTe kernel.

The two backends also aren't numerically identical. The CuTe backward flushes subnormal scattered gradients to zero when `not deterministic` (L1001-1006); the Triton backward never does. Make the dispatch decision once in the forward, store it on `ctx`, and either keep the backends' numerics in sync or document the difference.

This function copies ATen's internal `Reduce.cuh` launch heuristics (block width/height, vectorization threshold, four-accumulator folding, output-major split) to get bitwise parity on a sum over `K=8` values. Any upstream change to them breaks parity and means re-deriving this logic.

Is bitwise parity with the unfused **forward** worth that coupling when the backward already differs from native on purpose (see L324)? If the goal is "matches native up to reduction order", plain `tl.sum` plus a tolerance-based test would cut a lot of code. If bitwise parity really is required, add a comment pointing to the exact ATen source revision this mirrors.
