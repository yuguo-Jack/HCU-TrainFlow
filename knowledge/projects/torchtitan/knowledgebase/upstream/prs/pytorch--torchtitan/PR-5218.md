# [rl] drain mode: wait for the pinned generator instead of re-pinning (3/5)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5218) · state: closed · merged: True

## Original PR description

**Problem:** with `hot_swap=False` all generators drain in the same weight sync. Every turn sent while they all drain goes to the first generator back, and the sticky strategy re-pins those sessions there for good.
```
real router, 2 generators, 20 sessions:
turn0 {gen0: 10, gen1: 10} | turn1, during sync {gen0: 19} | turn2, after sync {gen0: 19}
```
**Solution:** a turn whose session is pinned to a draining generator waits for it (`RoutingStrategy.pinned_candidate` + the generator's `serving` event, which replaces the `SERVING`/`SYNCING` enum). New sessions still go to any serving generator. With the default `reset_kv_cache_on_weight_sync=False`, the generator keeps a group's KV across the weight pull, so waiting beats re-prefilling elsewhere.

```
CPU sim on the real router classes, hot_swap=False, main -> this PR
32 generators:                wall 831 s -> 400 s
4 generators, multi-turn:     prefix hit 0.857 -> 0.898
```

NOTE: no recipe sets `hot_swap=False` today.

**Test plan**
`pytest tests/rl/unit_tests/cpu`: 433 passed, 5 skipped (main: 432 passed; the 2 `test_verifiers_terminal_bench.py` failures are on main too). `test_sticky_session_assigns_new_generator_when_sticky_target_is_syncing` asserted the old re-pin; it is now `test_sticky_session_waits_for_its_syncing_generator`.

### Answers to your questions

**1. "During `hot_swap=False`, handles will be in syncing status, where the router will re-route to some available generators instead of waiting?"**

Yes, before this PR. `_pull_one` sets `SYNCING` (`inter_generator.py:297`). `_candidates()` then drops that handle. `StickySessionRoutingStrategy.choose` sees that the pinned handle is not among the candidates, so it falls back to least-loaded and **writes the new choice into `_sessions` for good**.

All pulls start together through `asyncio.gather` (`:311`), so every generator drains at roughly the same time. Turns that arrive during the sync wait on `self._serving`. Whichever generator calls `_set_state(SERVING)` first takes all of them, and they stay re-pinned there. That matches the `{gen0: 19}` numbers in the PR description. Your read is right, and the change makes sense.

**2. "We wouldn't encounter this for `hot_swap=True` because syncing is never set there?"**

Correct. `_set_state` is only called in the `else` branch of `_pull_one`, so with hot swap on, `h.serving` stays set from `__init__` (`:134`). `asyncio.Event.wait()` on a set event returns right away without yielding. For hot swap, the new code adds only a dict lookup per request, and behaviour is unchanged.

### Your inline comments

**`:51` and `:162`, "drop the Enum, check via instance methods": I agree.** As written, the same fact is stored twice (`h.state` and `h.serving`), and `_set_state` has to keep them in sync by hand. The enum has only two values and is private: it is used only in this file and in `test_inter_generator_router.py`. A simpler version:

```python
@dataclass(kw_only=True, slots=True)
class _GeneratorHandle(RoutingCandidate):
    ...
    serving: asyncio.Event = field(default_factory=asyncio.Event)
    """Set while this generator is routable; cleared while it drains for a
    weight sync (only when hot-swap is off)."""

    def is_serving(self) -> bool:
        return self.serving.is_set()

# router
def _candidates(self):
    return [h for h in self._generators if h.is_serving()]

def _set_serving(self, h, serving: bool) -> None:
    h.serving.set() if serving else h.serving.clear()   # or an if/else
    self._refresh_serving_status()
```

This would also update these tests, which use `_GeneratorState` / `h.state`: lines 141, 144, 170, 243, 256, 391–431. They would switch to `_set_serving(h, False)` and `[h.is_serving() for h in ...]`.

### Other findings

**1. The `:195` comment ("the drain is short") is inaccurate, as pzhan9 pointed out.** A drain waits for `h.idle`. That means every in-flight turn on that generator has to finish, and a long-generation turn can take a while. Only after that does the CPU-to-GPU apply run. Also, "the generator keeps the session's KV" holds only for the default `reset_kv_cache_on_weight_sync=False` (`generator.py:822`). It does not hold with `True`, which `batch_invariant` requires (`generator.py:855`).

Waiting is still the right choice in both cases, because it also prevents the pile-up on the first generator back. The comment should give the reason that always holds, for example:

```python
# A turn pinned to a draining generator waits for it rather than re-pinning:
# every generator drains at once, so re-pinning would move all such sessions
# to whichever comes back first; waiting also reuses the session's KV when
# reset_kv_cache_on_weight_sync=False.
```

**2. Race after the wake-up (fine, but worth knowing).** After `pinned.serving.wait()` wakes, the generator could go back to `SYNCING` before the task runs. That would need a second pull to start right away. In that case `choose` still re-pins through the fallback path, so nothing breaks or hangs. A comment isn't needed, but this is why `choose` still has to handle "pinned is not a candidate".

**3. Waiting turns don't reserve load, which is correct.** `_reserve` runs after the wait, so a parked turn doesn't keep `h.idle` cleared and can't stall the drain it is waiting on.

**4. Test (`test_sticky_session_waits_for_its_syncing_generator`).** It checks the three things that matter: the pinned turn blocks, a new session isn't blocked, and the turn lands on `gen0` afterwards. `await asyncio.sleep(0)` followed by `assert not turn.done()` is a somewhat weak check, because one loop tick is enough here. Still, it would catch the old re-pin behaviour, since that version completes in a single tick.

**5. pzhan9's larger suggestion (#5253, move drain into the generator).** Now that the router waits anyway, that refactor looks like the cleaner end state. Doing it as a follow-up seems reasonable; it doesn't need to block this PR in the stack.
