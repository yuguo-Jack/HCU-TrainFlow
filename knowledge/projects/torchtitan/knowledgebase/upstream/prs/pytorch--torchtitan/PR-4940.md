# [rl] Publish a tied weight once per trainer-to-generator weight sync

[Upstream PR](https://github.com/pytorch/torchtitan/pull/4940) · state: open · merged: False

## Original PR description

## Summary

With `enable_weight_tying` (e.g. the Qwen3 flavors used by the RL recipes), `Decoder` registers one `nn.Parameter` as both `tok_embeddings.weight` and `lm_head.weight`. `Trainer.push_model_state_dict` publishes `self.model.state_dict()`, which lists that parameter under both keys, so the tied weight moves twice on every weight sync:

- `ts.put_state_dict(..., direct_rdma=False)` stages every key as its own entry. When a transfer dtype is set, the per-key cast has already turned the two keys into two independent copies before the put.
- Each generator's `ts.get_state_dict` then fetches every stored key, so it fetches the tied vocab x dim tensor twice.

This PR adds `_tied_alias_fqns(model)`, which returns the FQNs that appear in `named_parameters(remove_duplicate=False)` but not in `named_parameters()`. `push_model_state_dict` pops those keys before the cast, so a tied parameter is published once, under its first FQN.

- Detection is by parameter identity. Weights that are not literally the same `Parameter` are never dropped, and untied models are unchanged.
- The helper runs on every push rather than once in `__init__`. FSDP2 re-registers different parameter objects when it switches between its sharded and unsharded states, so identity has to be checked at push time. The cost is two `named_parameters()` walks next to a full-model put.

Expected saving, computed from the shapes rather than measured: one vocab x dim tensor at the transfer dtype per push, and the same again per generator per pull. For Qwen3-0.6B in bf16 that is 151936 x 1024 x 2 B = 311,164,928 B (~297 MiB) each way. I'm not claiming a wall-time number.

## Why the generator still gets both FQNs

- Trainer and generator are built from the same `config.model`. The generator's `Decoder` ties the weights in `__init__` and ties them again in `init_states`.
- `_pull_model_state_dict` → `_get_spmd_state_dict` does the following:
  1. It wraps each tensor of `model.model.state_dict()` as a DTensor view (`DTensor.from_local(..., run_check=False)`, which makes no copy).
  2. It calls `ts.get_state_dict(..., strict=False)`, which fills only the stored keys, in place.
  3. It puts `to_local()` back and runs `load_state_dict(strict=False)`.

  The state-dict tensors share storage with the parameters, so filling `tok_embeddings.weight` updates the single tied parameter behind both FQNs.
- Both FQNs declare the same sharding, so the kept key is filled with the same layout the dropped key would have used.

The contract this relies on is now written in the comment at the pop: if the trainer's model is tied, the generator's model must be tied the same way. Today that holds structurally. A generator that broke the tie would not fail loudly, because the pull is `strict=False`; the alias would simply stop updating. I didn't add a generator-side assertion because I can't exercise the vLLM engine build path here, but I'm happy to add one if you'd like.

## Test plan

New tests in `tests/rl/unit_tests/cpu/test_trainer.py`, which follow the existing `object.__new__(Trainer)` pattern:

- `test_tied_alias_fqns_lists_only_the_repeated_fqn`
- `test_push_model_state_dict_publishes_a_tied_weight_once`: runs the real `push_model_state_dict` with `ts.put_state_dict` mocked and the transfer dtype set to bf16. It then does a receiver round trip: fill only the published keys in place, then `load_state_dict(strict=False)`. It checks that both FQNs equal the trainer's weight.
- `test_push_model_state_dict_publishes_every_untied_weight`

Run on Linux x86_64 with Python 3.12, torch 2.14.0+cpu, torchmonarch 0.6.0 and torchstore at main. vLLM was installed without its CUDA dependencies.

```
PYTHONPATH=$PWD pytest -p no:asyncio tests/rl/unit_tests/cpu/test_trainer.py
# this PR:                                     13 passed
# pop loop replaced by `pass` (helper kept):   1 failed (publishes_a_tied_weight_once), 12 passed

PYTHONPATH=$PWD HF_HUB_OFFLINE=1 pytest -p no:asyncio --continue-on-collection-errors \
  --ignore=tests/rl/unit_tests/cpu/test_muse_glimmer_renderer.py tests/rl/unit_tests/cpu
# this PR: 322 passed, 2 skipped, 1 error
# main:    319 passed, 2 skipped, 1 error
```

Two parts of the suite could not run locally:

- `test_verifiers.py` hits a collection error because the optional `verifiers` package isn't installed here. It fails the same way on main.
- `test_muse_glimmer_renderer.py` was ignored because its tokenizer fixture downloads from the HF Hub, which this machine can't reach.

I also replayed the generator's receive sequence through DTensor views, outside the PR. It ran on 2 gloo CPU ranks with a TP mesh of size 2 and `Shard(0)`, used `from_local(run_check=False)`, an in-place fill of only the published keys at each shard's offset, `dtensor_to_plain_tensor_state_dict`, and `load_state_dict(strict=False)`. Results:

- A tied receiver got both FQNs updated on both ranks.
- An untied control did not get the dropped FQN updated, which confirms the contract above.

torchstore itself was not in that loop, and I did not run an end-to-end GPU weight sync.
