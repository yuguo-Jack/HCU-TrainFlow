# [dsv3][perf] Compile MLA q/k RoPE and q concat as a local region

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5161) · state: closed · merged: True

## Original PR description

**TLDR:** DeepSeek-V3 attention's q split + RoPE + q cat (with k_pe's RoPE) becomes the `mla_qk` region: 16k step -2.1%, bitwise. The key/value build stays main's `materialize_mla_kv` in `MLAAttention`.

**Problem**
1. **q today.** Split, apply RoPE to one part, cat back.
2. **Slow copies.** The cat and its split backward run as non-vectorized `CatArrayBatchedCopy` on `[T, 128, 192]`.
3. **Cost.** The region saves 3.9 ms of a 182 ms 2-layer 16k fwd+bwd step (DSv3 671B layers 2-3, GB300; Results).

**Solution**
1. **Region.** `mla_qk` wraps q's split -> RoPE -> cat and k_pe's RoPE (`_apply_rope_to_q_and_k_pe`); Inductor fuses the cat and the split.
2. **Enabled** in the DSv3 model config, after `rope` (the `rope` region is inlined inside `mla_qk`).
3. **Unchanged.** The key/value build (main's `materialize_mla_kv` in `MLAAttention`) and recipes with the `fused_mla` override, which replace this code.

```text
before:  q: split -> rope -> cat   (eager CatArrayBatchedCopy)     k/v: materialize_mla_kv (main)
after:   q: mla_qk region (split -> rope -> cat fused)             k/v: unchanged
```

**Results**
```text
Numerics: bitwise identical with and without the region, bf16 output and all grads (2 layers, 4k and 16k, GB300).

DSv3 671B layers 2-3 (MoE at one EP8 rank's shapes, 32 experts), flex attention, fwd+bwd wall, 1x GB300 (shared),
median [range] of 3 fresh processes, no AC, the other default regions on in both:
16k            182.44 [181.94-185.04] -> 178.58 [177.11-181.14] ms  (-2.1%)
peak             34.2 -> 34.2 GB

graphs (this stack): _apply_rope_to_q_and_k_pe 4 of 8 (train static T, train dynamic T, no_grad dynamic T,
                     no_grad T=1), shared across attention instances
```

You may ask:
- Why not `fused_mla` everywhere? It is an opt-in Triton override that replaces `forward`, so this region never runs under it; the region is the default for every recipe without it. On the old base, with the k/v build also in the region, `fused_mla` was still faster: 1.6% per attention layer at 16k (45.10 vs 45.85 ms), 2.1% of a 2-layer step (156.24 vs 159.58 ms); not re-run here. Making `fused_mla` the default is the owners' call.
- Why not compile the k/v build too? It is main's `materialize_mla_kv` in `MLAAttention`, which the CP MLA path also calls; its own PR.

NOTE:
- The region turns off pointwise autotuning, as the `rope` region does (kernel time, 671B layer 0: train 0%, prefill +0.2-0.4%).
- Plain cat lowering (`max_pointwise_cat_inputs=0`): with RoPE in real arithmetic, 16k layer fwd+bwd 46.95 -> 45.85 ms, bitwise vs eager; alone, the option is neutral (46.37 ms). Measured on the old base (k/v build also in the region).
- The 16k reps were noisy (per-rep deltas -3.86 / -0.79 / -7.94 ms): another user's jobs ran on other GPUs during reps 2-3.
- Reaches recipes using the stock DSv3 `Attention` (deepseek_v3_671b with flex, Kimi K2.x).
- Not tested: TP/SP (regions are disallowed under SPMD type checking), GraphTrainer, varlen attention, loss curve, H100.

**Test plan**
`pytest tests/unit_tests/cpu/models/deepseek_v3/test_deepseek_v3_mla_compile.py` (fp32, with and without `positions`; fails before, passes after)

Stack: 1 of 3 on top of the RoPE / Muse Spark stack: this PR -> MLA RoPE as int32 pairs -> remove the Helion RoPE override.

@SherlockNoMad FusedMLA is ~2.6% faster than this PR's region at 16k (45.10 vs 46.34 ms per attention fwd+bwd). Two small changes get the region to 45.48 ms. CUDA graphs don't change the picture: one attention layer at these sizes is GPU-bound.

```text
DeepSeek-V3 671B attention (one layer), packed 4k-token docs, bf16, fwd+bwd, 1x GB300, 3 fresh processes
                          T=4k     T=16k    T=16k CUDA graph
eager glue               13.33    52.18    52.26 ms
mla_qk (this PR)         11.84    46.34    46.42
+ real-arithmetic RoPE   11.72    45.85    45.96
+ V as a view of kv      11.62    45.48    45.59
FusedMLA                 11.49    45.10    45.22
all bitwise identical to eager, with and without graphs
```

- **RoPE (0.5 ms):** Inductor can't codegen complex multiply, so `q_pe * freqs_cis` stays an ATen kernel inside the region. Real arithmetic (the `complex_rope` PR, #5196) plus `max_pointwise_cat_inputs=0` (second commit here) fixes it.
- **V (0.3 ms):** a dense V costs a clone and a slower attention fwd; returning the view from a region makes AOTAutograd copy its grad. An `autograd.Function` around two regions returns the view, like FusedMLA. ~35 lines for ~0.6% of the layer, so not in this PR.
- **Left (0.4 ms):** mostly FusedMLA rotating `grad_q` in place, which a compiled region can't do.
- **One or the other:** FusedMLA replaces `Attention.forward` and is opt-in per recipe; without it, every DeepSeek-V3 config gets `mla_qk`.

```python
"""DeepSeek-V3 671B MLA attention, fwd+bwd: eager q/k glue vs the mla_qk region vs FusedMLA,
without and with CUDA graphs.

usage (from the repo root, 1 GPU): PYTHONPATH=. python compare_mla.py 2>/dev/null
(stderr carries flex attention's autotuning log)
"""

import torch
from torch.nn.attention.flex_attention import and_masks

from torchtitan.distributed.local_compile import apply_local_compile
from torchtitan.models.common.attention import (
    create_attention_mask,
    get_causal_mask_mod,
    get_efficient_causal_mask_mod_for_packed_document,
)
from torchtitan.models.deepseek_v3.flavors import build_model_config
from torchtitan_recipes.overrides.fused_mla import fused_mla

DOC_LEN = 4096  # packed documents of 4k tokens
attn_config = build_model_config("671B").layers[3].attention


def build(config):
    torch.manual_seed(0)
    with torch.device("cuda"):
        attn = config.build()
        attn.init_states(buffer_device=torch.device("cuda"))
    return attn.bfloat16()


stock = build(attn_config)
fused = build(fused_mla(attn_config))
fused.load_state_dict(stock.state_dict())


def step(attn, x, mask, positions):
    """One fwd+bwd. Grads are overwritten, not accumulated, so a captured step replays exactly."""
    for p in [x, *attn.parameters()]:
        p.grad = None
    out = attn(x, mask, positions)
    out.float().square().mean().backward()
    return out


def time_ms(fn, iters=10):
    for _ in range(3):
        fn()
    start, end = torch.cuda.Event(enable_timing=True), torch.cuda.Event(enable_timing=True)
    start.record()
    for _ in range(iters):
        fn()
    end.record()
    torch.cuda.synchronize()
    return start.elapsed_time(end) / iters


def capture(attn, x, mask, positions):
    """Warm up on a side stream, then record one fwd+bwd into a CUDA graph."""
    side = torch.cuda.Stream()
    side.wait_stream(torch.cuda.current_stream())
    with torch.cuda.stream(side):
        for _ in range(3):
            step(attn, x, mask, positions)
    torch.cuda.current_stream().wait_stream(side)
    graph = torch.cuda.CUDAGraph()
    with torch.cuda.graph(graph):
        out = step(attn, x, mask, positions)
    return graph, out


def rel_l2(a, b):
    return ((a.float() - b.float()).norm() / b.float().norm()).item()


for num_tokens in (4096, 16384):
    torch._dynamo.reset()  # training runs one T; a second T would recompile flex with a symbolic T
    positions = torch.arange(num_tokens, device="cuda") % DOC_LEN
    mask_mod = and_masks(
        get_causal_mask_mod(), get_efficient_causal_mask_mod_for_packed_document(positions)
    )
    mask = create_attention_mask(
        mask_mod, 1, None, num_tokens, num_tokens, device="cuda", BLOCK_SIZE=128
    )
    x = torch.randn(num_tokens, 7168, device="cuda", dtype=torch.bfloat16, requires_grad=True)

    eager_ms, graph_ms, results = {}, {}, {}
    for name, attn, regions in [
        ("eager-glue", stock, []),
        ("mla_qk", stock, ["mla_qk"]),
        ("FusedMLA", fused, []),
    ]:
        apply_local_compile(regions)
        eager_ms[name] = time_ms(lambda: step(attn, x, mask, positions))
        out = step(attn, x, mask, positions).detach()
        results[name] = (out, x.grad.clone())

        graph, graph_out = capture(attn, x, mask, positions)
        graph_ms[name] = time_ms(graph.replay)
        graph.replay()
        torch.cuda.synchronize()
        replay_match = torch.equal(graph_out, out) and torch.equal(x.grad, results[name][1])
        print(f"T={num_tokens // 1024}k {name}: replay bitwise equal to eager run: {replay_match}")
        del graph, graph_out

    for label, ms in [("no graphs", eager_ms), ("CUDA graph", graph_ms)]:
        row = " | ".join(f"{k} {v:.2f} ms" for k, v in ms.items())
        print(f"T={num_tokens // 1024}k {label:10s} {row}")
    ref_out, ref_grad = results["eager-glue"]
    for name in ("mla_qk", "FusedMLA"):
        out, grad = results[name]
        print(f"       {name} vs eager-glue: out {rel_l2(out, ref_out):.1e}, x.grad {rel_l2(grad, ref_grad):.1e}")
```

### Answers to the inline questions

**1. "Can we remove this code?" (`attention.py:215`, the `if torch.compiler.is_compiling():` branch)**

Yes, I'd make it unconditional:

```python
k_nope, v = torch.split(kv, [self.qk_nope_head_dim, self.v_head_dim], dim=-1)
k = torch.cat([k_nope, k_pe.expand(-1, k_nope.size(1), -1)], dim=-1)
# A strided value view gets a gradient from attention in another layout, which
# the compiled backward copies before using it. A dense value avoids that copy.
return k, v.contiguous()
```

- **Eager cost:** in eager mode this adds one `[T, H, v_head_dim]` clone and loses the strided-view flex fwd that the author measured. That only matters if someone runs the hot path in eager mode, which, as you say, nobody should for performance.
- **Gains:**
  - Eager and compiled return the same `v` strides, so the eager-vs-compiled parity test compares like with like.
  - One fewer `is_compiling()` branch in model code.
  - The same behavior in every other tracing context where `is_compiling()` may be true, such as GraphTrainer, which runs with `local_compile_regions = []`.
- **SPMD type checking:** no impact. Regions are rejected under `debug.spmd_typechecking` (`config/validation.py:140`), so that path is eager. `.contiguous()` inside `spmd.local()` keeps the same local type, and the `assert_type` on `[k, v]` still holds.

**2. "Is this PR 1.5-2% faster but still slower than the Triton kernel, so you are keeping the kernel?"**

From the author's numbers in the thread, the two figures measure different things:

| per attention layer fwd+bwd, 16k, GB300 | ms |
|---|---|
| eager glue (before this PR) | 52.18 |
| `mla_qk` (this PR) | 46.34 (-11% vs eager) |
| + real-arithmetic RoPE (now in this stack) | 45.85 |
| + V as a view of kv (not in this PR) | 45.48 |
| FusedMLA (Triton) | 45.10 |

- **This PR vs eager:** 7.5% faster per step and about 11% faster per attention layer than the eager glue.
- **FusedMLA vs this PR:** FusedMLA is still faster. The "1.5-2%" is FusedMLA's lead over this region at step level on the old base. Per layer it is about 2.6%, dropping to about 1% with the RoPE follow-up in this stack.
- **Both are kept:** FusedMLA replaces `Attention.forward` and is opt-in per recipe. When it is used, `mla_qk` never runs. This PR doesn't remove FusedMLA or change any recipe; it only speeds up the default path every other DSv3/Kimi config takes.
- **Your call:** whether to make FusedMLA the default, or drop it now that the gap is about 1%, is a separate decision for the owners.

---

### Smaller notes (non-blocking)

1. **Cat options only apply to the q region** (`attention.py:168-172`): `_apply_rope_to_q_and_k_pe` sets `max_pointwise_cat_inputs=0`, but `_split_kv_and_build_k`, also under the `mla_qk` name, uses Inductor's default cat lowering. If that's on purpose (the k cat has an `expand`ed input, so pointwise cat may win there), a short comment would stop someone from "fixing" it later. If not, it's worth a quick check of both settings.
2. **What the test doesn't cover** (`test_deepseek_v3_mla_compile.py`): it runs in fp32 on CPU with `positions` set. That means it never reaches:
   - the bf16 path of `_RotatePairs`;
   - `positions=None`, which is a separate graph and counts toward the recompile budget the PR mentions.

   Two cheap additions would help:
   - a `positions=None` case;
   - running the region twice under `torch._dynamo.config.patch(error_on_recompile=True)` with a second `attention` instance, to lock in the "graphs shared across attention instances" claim.

   Neither is required.
3. **Docstring** (`_apply_rope_to_q_and_k_pe`): `Args` doesn't document `positions`.
4. **Callsites:** Kimi K2.x inherits the DSv3 `local_compile_regions` default, so it gets `mla_qk` automatically, as the PR description says. DSv4, Kimi K3 and Muse Glimmer don't use `DeepSeekMLAAttention`. GraphTrainer forces `local_compile_regions = []`. Nothing else needs updating.

I couldn't run the unit test here because the CI sandbox needs approval to run Python, so this review is from reading the code only.
