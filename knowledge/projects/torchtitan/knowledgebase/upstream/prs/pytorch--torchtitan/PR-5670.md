# [rl] generator: no output memset or copy in the GDN inner op (3/7)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5670) · state: closed · merged: True

## Original PR description

**TLDR:** `VLLMInnerGDN.forward` zero-filled its output, then the packed path copied the chunk kernel's result into it. `_forward` now returns the kernel's tensor: no memset, no copy. Per GDN layer: 2048-token packed steps -4 to -16 us (-0.5 to -0.8 ms per step at 27B TP1, 48 GDN layers; estimate), eager prefill -13 to -88 us. Bitwise identical.

```python
# before
output = mixed_qkv.new_zeros(num_tokens, heads, head_v_dim)  # memset
output.copy_(chunk_kernel(...)[0])                           # copy
# after
output = chunk_kernel(...)[0]
```

**Problem**
1. `VLLMInnerGDN.forward` allocated its output with `new_zeros`: one memset per GDN layer per step.
2. The packed path then copied the chunk kernel's result into it: a full read and write of the output.
3. Only rows no kernel writes need zeros: vLLM's profiling run, an empty batch, rows past the batch.

**Solution**
1. `_forward` returns its output: the chunk kernel's tensor on packed steps.
2. Single-token steps allocate with `new_empty`; the decode kernel writes the batch rows.
3. Only the rows no kernel writes are zeroed.
4. Unchanged: kernels and outputs (bitwise).

**Results**
Numerics: bitwise identical to 2/7 in all 80 cells (output, recurrent and conv state).

```text
GDN op per layer, GB300, CUDA graphs, us, median of 3; before = 1/7 + 2/7, after = + this diff, on f04e77ef1
step                     27B TP1          27B TP4          35B-A3B TP1      35B-A3B TP2
1 x 2k prefill           157.6 -> 143.8   116.2 -> 111.4   141.2 -> 132.6   119.6 -> 113.7
255 decodes + 1 chunk    880.4 -> 867.1   317.1 -> 312.6   637.9 -> 628.3   381.3 -> 374.8
8 x 2k prefill (eager)   729.3 -> 641.5   232.9 -> 210.2   567.7 -> 507.0   306.2 -> 277.3
decode batch 1           16.0 -> 14.5     19.0 -> 14.2     16.3 -> 15.5     18.9 -> 14.4
decode batch 256         254.4 -> 254.1   76.5 -> 74.5     177.6 -> 176.1   97.1 -> 96.9
```

You may ask: vLLM's GDN copies into a preallocated output, why not here? vLLM splits piecewise CUDA graphs at this op, so the output must live in the previous piece's buffer. This generator runs NONE, FULL_DECODE_ONLY or FULL (`VLLMCudaGraphConfig.mode`), never piecewise.

**Test plan**
`test_forward_respects_prepared_extent_and_decode_padding` (`new_empty` returns NaN, so a row neither written nor zeroed fails; also the zero early returns). `test_single_token_reused_state_capture` NaN-fills the output before each graph replay, so a null row the decode kernel leaves unwritten fails. GB300 GDN GPU tests: 13 passed.

**Stack** (land in order): 1/7 fused gate -> 2/7 metadata reuse -> 3/7 no output memset/copy -> 4/7 decode routing -> 5/7 fused input projections -> 6/7 float32 gate parameters -> 7/7 split compiled per grad mode.

### Review: looks good, with one question about dtype before landing

The change is right. Each branch of `_forward` now defines every output row:
- **Early returns** (profiling, empty batch) use `new_zeros`.
- **Decode** writes the batch rows; `zero_()` clears the rows past the batch.
- **Packed** gets zeros on null-slot padding rows from the kernel, and `torch.cat` adds zeros for the rows past `num_actual_tokens`.

Under CUDA graphs, FULL bucket padding goes through the metadata, so the `cat` only runs in eager. Your reason for not copying into a preallocated output (no piecewise graph split at this op) holds for the `VLLMCudaGraphConfig.mode` values.

The NaN `new_empty` trick in `test_forward_respects_prepared_extent_and_decode_padding` is a good check. It would catch a row that is neither written nor zeroed, on both the decode and packed paths.

### Question

**1. Removing `.to(output.dtype)` changes the packed path's output dtype contract** (`torchtitan/rl/generator/vllm/gdn.py:367`)

`_forward_gdn` used to cast the kernel output to the `mixed_qkv` dtype. It now returns `recurrent_output[0]` as is:
- **Decode:** still safe. `output[:num_decode_rows] = ...` casts implicitly.
- **Packed:** the kernel's dtype goes straight downstream.
- **Batch-invariant packed path:** this is the case that matters. `recurrent_gdn` runs against the float32 SSM cache. The trainer's wrapper around the same kernel still casts back explicitly: `return out_BTHV.to(q_BTHK.dtype)` in `torchtitan/models/common/attention/gdn.py:140`.
- **What happens if it is float32:** `GatedRMSNorm` returns the input dtype, so `out_proj` would get a float32 activation against bf16 weights. That would likely fail loudly rather than silently, but it would still be a regression on the RL path.

Could you confirm whether the 80 bitwise cells include batch-invariant prefill or chunked steps? `test_single_token_reused_state_capture[batch_invariant=True]` only covers decode.
- If `recurrent_gdn` always returns the dtype of `value`, a short comment there is enough. The trainer-side `.to` then looks like the redundant one.
- Otherwise, keep the cast on the `recurrent_gdn` branch only. It is a no-op when the dtypes already match.

### Nits
- **Eager padding cost** (`gdn.py:302-306`): when SP or model-input rounding pads, `torch.cat` copies the whole output again. That costs about what the old memset plus copy did, so there's no regression, just no saving in that case. It doesn't need a change, but the perf numbers in the description don't cover it.
- **Test lambda** (`test_gdn_graph_metadata.py`): the patched `lambda self, size:` only accepts one positional size. That works for the one call site now. `lambda self, *size, **kwargs: self.new_full(*size, float("nan"), **kwargs)` would keep working if `new_empty` is later called with a dtype or with unpacked sizes. Optional.

### Re-review of d9df8773d: looks good to land, with one test suggestion

Every row of the returned output is still defined on every path:
- **Early returns** (profiling, empty batch): `new_zeros`.
- **Decode**: the kernel writes `[:num_decode_rows]`, and `zero_()` clears the rest. `zero_()` on an empty slice launches nothing, so batches that fill the bucket pay no extra cost.
- **Packed**: null-slot rows are zeroed by the kernel, and the `cat` only runs for eager SP/model-input rounding.

Your earlier replies on dtype, the eager `cat` cost and the lambda settle those points. The downstream consumer uses `reshape` (`models/common/attention/gdn.py:558`), so a non-contiguous kernel output would still be safe. Scoping this to GDN only is right: KDA's `_forward` is wrapped in `@eager_break_during_capture` (`kda.py:210`), which splits the graph there, so it still needs the preallocated output.

### Suggestion

**1. Make the real-kernel test catch decode null-slot rows that are never written** (`tests/rl/unit_tests/gpu/test_gdn_cudagraph.py:257`)

Before this PR, a zero-filled buffer hid any null-slot row the decode kernel didn't write. Now the output comes from `new_empty`, so the PR relies on `recurrent_gdn_decode(out=...)` writing zeros on null-slot rows (slot 0 and `-1`).
- **What checks this today:** `assert not output[len(slots):].count_nonzero()` at line 259 is the only test that covers it with the real kernels.
- **Why that check is weak:** `output` is the graph pool's static buffer, and it is the first allocation in the captured decode branch. That is likely fresh, already-zero memory, so a kernel that skips null rows would probably still pass.
- **The NaN unit test doesn't cover it either:** it mocks `_forward_gdn`, so it never reaches `recurrent_gdn_decode`.
- **The fix:** add one line before `graph.replay()`:

```python
            output.fill_(float("nan"))
            graph.replay()
```

The checks at 258 and 259 then actually verify the decode kernel's null-slot contract, in both `batch_invariant` modes. [Fix this →](https://claude.ai/code?q=In%20tests%2Frl%2Funit_tests%2Fgpu%2Ftest_gdn_cudagraph.py%20on%20branch%20felipemello1%2Fgdn-stack%2F3-no-output-copy%2C%20in%20test_single_token_reused_state_capture%2C%20add%20%60output.fill_(float(%22nan%22))%60%20immediately%20before%20%60graph.replay()%60%20so%20the%20assertions%20verify%20the%20decode%20kernel%20writes%20zeros%20on%20null-slot%20rows%20now%20that%20VLLMInnerGDN._forward%20allocates%20with%20new_empty.&repo=pytorch/torchtitan)
