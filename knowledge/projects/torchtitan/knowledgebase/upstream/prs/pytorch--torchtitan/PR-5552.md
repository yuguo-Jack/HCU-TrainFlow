# [DeepSeek V3] Fuse general-shape sequence loss forward and backward

## Agent details (AI-generated)

Adapted from Yidi Wu (@ydwu4), #5259, revision
25dafa9a6db1e7d5327377a0e28913485e704a1f. Preserve original attribution and
license; this change includes integration and generalization, not just a port.

Keep provided-map/L1 and unbiased top-k objectives distinct. Preserve native
coefficient/token normalization, gradient injection, metric accumulation and
DP-local training ownership. Padding contributes no counts, score sums or
gradients; unbiased selection is independent of biased/group-limited routing.

General fused CUDA kernels support positive T/E and configured top-k, while
the aligned production geometry keeps the tuned CuTe launch. Derive scratch
and native CTA partitioning from shapes and device resources. Explicitly fold
block.y partials in native order, independent of Triton layout; preserve
unaligned score-base offsets and scalar clamp-min's strict boundary derivative.
Temporary normalized scores/maps and partial buffers are not autograd saved
state. Save only original scores, frequencies and an optional padding mask.
The general implementation does not fall back to eager ATen for shape/tails.

**Verdict: changes requested (minor).** The design is sound, but please remove the duplicated CuTe helpers, fix the tuned backward so it uses the same unbiased denominator as its forward, and widen GPU test gating so CI on B200 actually runs most of the new tests. See the 6 inline comments.

<summary>Review details</summary>

### What's good
- Ownership is kept clean. Only the raw objective is fused; coefficient/denominator scaling, `inject()` (including the remat `recompute=False` metric region) and the DP-local context all stay native.
- `metric_name` is resolved before `AuxLoss.__init__`, so the `_group_counts` keys match native (`microbatch_wise_load_balance_loss` / `unbiased_top_k_load_balance_loss`).
- Padding masking in provided-map mode is redundant with the router's `masked_routing_map_TE`, but it gives the same result.
- The composed override (`fused_dsv3_router_and_seqwise_loss`) is a reasonable way around ancestor-claim conflicts. `derive`'s shallow copy is safe because `aux_loss` is reassigned, not mutated.
- The CPU fallback path checks bitwise equality against native for both modes, including tiny/zero unbiased rows.
- Added comments and docs are ASCII-only.

### Inline findings
1. **Duplication** (`fused_dsv3_seqwise_loss.py:332`): about 12 CuTe/PTX helpers plus `launch` are verbatim copies from `fused_dsv3_router.py`, while `select_eight` is already imported from it. Import them instead.
2. **Forward/backward denominator mismatch** (`:776-781`): in unbiased mode the tuned backward uses the abs-sum `row_sum(magnitudes)`. The tuned forward, the generic backward and native all use the plain sum. It only matters for signed scores, but the Function accepts them and no test covers that combination on the tuned path.
3. **CI coverage** (`tests/.../gpu/test_fused_dsv3_seqwise_loss.py:173`): the whole class is gated on sm_103, so on `ciflow/b200` the remat/metric, SPMD typecheck, router composition and compile/CUDA-graph tests never run. Most of them don't depend on the tuned kernel.
4. **One class, two modes** (`:1128`): `top_k is None` switches between objectives, and the fallback calls `UnbiasedTopKLoadBalanceLoss._compute_local_stats(self, ...)` on an instance that isn't a subclass. Two fused subclasses would be cleaner. Not blocking.
5. **Dead sharding hook** (`:1137`): aux-loss configs have no `sharding_config`, so the `V` declaration for `arrival_counter` never takes effect. The GPU test even asserts the counter is `R`.
6. **ATen heuristic mirroring** (`:47`): `_column_reduction_plan` copies `Reduce.cuh`'s `setReduceConfig`. Please cite the upstream function and PyTorch version so a parity break after a PyTorch bump is easy to trace.

### PR description
- It cites "prior matched GB300 microbenchmarks" but gives no numbers. Please include the measured speedup on the 4096x256 production shape (fused vs native forward+backward, ≥10 steps). That's what justifies about 1.3K lines of kernel code in the recipe path.
- The verification section is hard to parse ("Three unchanged main type findings remain attributed…"). Please give a plain list of which tests ran, on which hardware, and the result.

### Not verified
I couldn't run anything: running pytest/python here needs approval, and there are no GPUs. I did not check the bitwise-parity claims (ATen reduction-order emulation, clamp-min boundary derivative, top-k tie-breaking) beyond reading the code. I'm relying on the GPU test matrix described in the PR.

- claude[bot] · comment · 2026-11-01T06:06:51Z · [source](https://github.com/pytorch/torchtitan/pull/5552#discussion_r4434600457)

File: `torchtitan_recipes/overrides/fused_dsv3_seqwise_loss.py` · line 781

**Forward and backward use different unbiased denominators.** In unbiased mode the tuned backward builds its denominator from `row_sum(magnitudes) + 1e-20` (abs-sum). Three other places use the plain sum `scores.sum(-1) + 1e-20`:
- the tuned forward (`forward_kernel`, L723-724: `row_sum(items)`)
- the generic backward (`_generic_seqwise_backward`, which passes `scores` when `UNBIASED`)
- the native `UnbiasedTopKLoadBalanceLoss`

Sigmoid scores are nonnegative, so this doesn't show up today. But `FusedDSv3SeqwiseLossFunction` accepts signed input. Your generic tests even include a `signed` + `unbiased=True` case, and nothing tests that combination on the tuned path. With signed scores at 4096x256 on GB300, this kernel's gradient would not match its own forward. Suggest matching the forward:
```python
norm = row_sum(items) if cutlass.const_expr(unbiased) else row_sum(magnitudes)
```
(then `magnitudes` is only needed when the mode is biased).

**Design nit: one class with two modes.** A single class chooses between two objectives based on `top_k is None`. The fallback reaches into a class it doesn't inherit from: `UnbiasedTopKLoadBalanceLoss._compute_local_stats(self, ...)` is an unbound call on a non-subclass instance. `metric_name` and the `forward` fallback also branch on `top_k`, which goes against the PR's own goal of keeping provided-map and unbiased objectives distinct.

A cleaner split: a shared fused mixin plus
- `FusedMicrobatchWiseLoadBalanceLoss(MicrobatchWiseLoadBalanceLoss)`
- `FusedUnbiasedTopKLoadBalanceLoss(UnbiasedTopKLoadBalanceLoss)`

Each would inherit its native `_compute_local_stats`/`forward` fallback, so the unbound call and the `top_k: int | None` sentinel go away. `metric_name` would still need an override to keep the native metric keys. Not blocking, since this is recipe code.

The bitwise-parity contract therefore depends on PyTorch internals that can change between releases, with no API guarantee.
