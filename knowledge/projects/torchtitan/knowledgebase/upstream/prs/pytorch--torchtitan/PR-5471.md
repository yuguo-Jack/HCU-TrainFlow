# [scripts] Download chat_template.jinja with the tokenizer assets

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5471) · state: closed · merged: True

## Original PR description

`HuggingFaceTokenizer` loads a standalone `chat_template.jinja` from the tokenizer directory first and falls back to the inline `chat_template` in `tokenizer_config.json` (`torchtitan/components/tokenizer.py`, "Models like GPT-OSS use this pattern"). `scripts/download_hf_assets.py --assets tokenizer` doesn't download that file. For `openai/gpt-oss-20b`, the repo has `chat_template.jinja`, `tokenizer.json` and `tokenizer_config.json`, and its `tokenizer_config.json` has no `chat_template` key. A tokenizer downloaded with the script therefore has no chat template, and building chat samples fails with `ValueError: No chat template set. Call set_chat_template() first.`

This adds `chat_template.jinja` to the tokenizer file patterns and to the docstring list. Repos without the file are unaffected; the script only downloads patterns that exist in the repo. For a repo that has both `chat_template.jinja` and an inline `chat_template` in `tokenizer_config.json`, a fresh download now uses the `.jinja` file, which is what the tokenizer already prefers and what `transformers` does.

**Test**
- New `test_tokenizer_includes_standalone_chat_template` in `tests/unit_tests/cpu/scripts/test_download_hf_assets.py`, using the existing mocked `list_repo_files` / `hf_hub_download`. It fails on `main` (2 files downloaded instead of 3) and passes with this change. The file's 12 tests pass.
- ufmt (black 22.12.0, usort 1.0.5) and flake8 with the pre-commit plugins are clean on both files.

**Verdict: LGTM.** This is a small, correct fix for the problem the PR describes.

### Correctness
- `torchtitan/components/tokenizer.py:117,157-166` first looks for `chat_template.jinja` at the top level of `tokenizer_path`, then falls back to `tokenizer_config.json["chat_template"]`. Before this PR, the script never downloaded that file, so repos that keep their template only in the `.jinja` file (e.g. `openai/gpt-oss-20b`) came out with no chat template. This change fixes that.
- `should_download` (`scripts/download_hf_assets.py:115-128`) checks for an exact basename match, so the new entry only matches files named exactly `chat_template.jinja`. Repos without the file are unaffected.
- The new test (`test_tokenizer_includes_standalone_chat_template`) reuses the existing mocks and checks the exact set of downloaded files. That is enough to show the regression.

### Things to be aware of (none block merging)
1. **Effect on repos with both template sources.** If a repo has both `chat_template.jinja` and an inline `chat_template` in `tokenizer_config.json`, the `.jinja` file is now used for a fresh download. This matches what `transformers` does (the standalone file wins) and what our tokenizer already prefers, so I think it's the intended behavior. It is still a quiet change for users who re-download such a repo, and the PR description could mention it in one line.
2. **Templates in subdirectories (existing behavior, not caused by this PR).** Matching is on the basename, so a nested `foo/chat_template.jinja` would also match. `hf_hub_download` keeps the subdirectory, so the tokenizer, which only checks the top level, would not find it. All the other patterns already work this way, so I'm only flagging it. Newer HF repos can also include `additional_chat_templates/*.jinja` files. Those are correctly *not* downloaded, since the tokenizer only reads the default template.
3. **Minor nit.** The filename now appears as a literal in two places: here and in `HuggingFaceTokenizer.CHAT_TEMPLATE_FILE`. Importing the constant into a standalone script would add a dependency on `torchtitan`, so keeping the literal is fine.
