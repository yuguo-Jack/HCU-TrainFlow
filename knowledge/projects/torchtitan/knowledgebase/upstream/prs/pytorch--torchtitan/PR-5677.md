# [distmuon] 4/n Bound optimizer memory ownership and allocation lifetimes

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5677) · state: open · merged: False

## Original PR description

Part **4/n** of the Kimi K3 / Dist-MoE training stack. Based directly on `main`: the review diff contains only the optimizer-memory changes below.

human notes: add a `_persistent_redistribution_buffers` knob for distmuon, by default it is true. when it is false, in eager mode, it can release the memory used for redistribute and compute, freeing memory for fwd/bwd. also deleting some ns intermediate tensors to optimize memory.

## Why

DistMuon keeps optimizer-only exchange and compute scratch alive between updates, although forward/backward does not use those tensors. Both full-scale Kimi K3 recipe builders select transient optimizer scratch while retaining communication resources. This option makes unused workspace available for allocator reuse; no isolated full-recipe peak-memory saving is claimed.

Example:

```python
from dataclasses import replace

dist_muon_config = replace(
    dist_muon_config,
    persistent_redistribution_buffers=False,
)
```

The existing `max_nccl_ctas_for_comms` API and resource-independent NCCL redistribution meshes are inherited from the base, not implemented again here.

## What changed

- In transient mode, skip scratch reservation during construction and checkpoint loading; reserve it before each eager update and release it afterward. Initialized communication streams/events are retained.
- Release Newton-Schulz temporaries after their last use without changing arithmetic, coefficients, or compute dtype.

Persistent scratch remains enabled by default. In transient mode, stream/event context creation is deferred to the first reservation and that context is then reused. Buffer reservation remains allocation-only: this PR adds no synthetic all-to-all or communicator-warmup bookkeeping. Optimizer-state initialization, training-engine startup and accelerator-graph helpers are unchanged from `main`; this PR adds no early-state-initialization option.

The existing once-only cache release before the first `Optim.step()` is inherited from [#5350](https://github.com/pytorch/torchtitan/pull/5350). It addresses the first-update allocation/cache interaction in [#5019](https://github.com/pytorch/torchtitan/issues/5019), not true live-memory exhaustion or every later NCCL allocation.

## Alternatives considered

A process-wide allocator policy would conflate different buffer owners. Recreating communication contexts between updates would unnecessarily discard persistent streams and events. Releasing only optimizer-owned tensor references makes those allocations reusable without rebuilding communication resources.

## User-facing changes

| Before | After |
| --- | --- |
| Redistribution scratch remains allocated between updates. | `persistent_redistribution_buffers=False` allocates optimizer-only scratch only for each eager update and releases it afterward; construction and checkpoint loading skip reservation. |
| Obsolete Newton-Schulz intermediates retain memory until replacement or function exit. | Intermediates are released immediately after their final use, with arithmetic and compute dtype unchanged. |

## Numerics

Newton-Schulz arithmetic, coefficients, operation order, and compute dtype are unchanged; only obsolete tensor references are dropped. The existing coefficient test remains. Real two-rank optimizer/checkpoint tests retain their original reference comparisons while exercising both persistent and transient buffers; the distributed validation below is historical. No standalone throughput improvement is claimed.

**Verdict: Request changes** -- most of the scratch that transient mode frees is allocated on the transfer stream, so forward/backward on the default stream can't reuse it without an allocator OOM retry (a device sync plus `cudaFree`) every step.

**What this PR does.** It adds `DistMuon.Config.persistent_redistribution_buffers` (default `True`). With `False`, construction and checkpoint load skip `reserve_buffers()`. Each `step()` then reserves the slot buffers before `run()` and clears them afterward, while keeping streams and events. Separately, `_zeropower_via_newtonschulz` drops the `gram`, `gram_update` and initial BF16 `result` references after their last use. Arithmetic is unchanged.

**Example.**
```
persistent=True  : [reserve at init] fwd | bwd | step(run) | fwd | bwd | step(run) ...
                   exchange + scratch stay allocated the whole time
persistent=False : init (no reserve)  fwd | bwd | reserve, run, release | fwd ...
  compute_scratch  (caller stream)   -> freed to caller pool   -> fwd/bwd can reuse
  storage_exchange/compute_exchange/storage_scratch
                   (transfer stream) -> freed to transfer pool -> fwd/bwd cannot reuse
                                        unless an allocation fails and the allocator
                                        syncs and cudaFrees all cached blocks
```

<details><summary>Details</summary>

- **Allocator reasoning.** `_BufferSlot.reserve` (L136-162) allocates three of the four buffer kinds under `device_handle.stream(transfer_stream)`. The caching allocator pools free blocks per stream, and the only cross-stream release is `release_cached_blocks()` on a failed allocation. That path synchronizes the device and frees whole segments to the driver. So in steady state, either memory doesn't drop, or every fwd/bwd triggers a retry and every step re-`cudaMalloc`s.
- **Why caller-stream allocation is safe.** Allocation on the caller happens before `context.transfer_stream.wait_stream(caller)` in `run()`. Every redistributed bucket ends with `_release()` -> `caller.wait_event(slot.done)`. So all transfer-stream work is ordered before the caller-side free, and later caller-stream allocations that reuse the block are ordered after it.
- **Newton-Schulz `del`s.** Checked; each one drops the last reference before the next large allocation, and the operation order is unchanged. `del result` in the batched path frees the initial copy after the first iteration rebinds `matrices`, because `matrices` is a view of it. No finding.
- **Consumer.** No in-repo recipe sets `False` at HEAD; the consumer is `torchtitan_recipes` in #5793.

</details>

- claude[bot] · comment · 2026-11-04T07:55:35Z · [source](https://github.com/pytorch/torchtitan/pull/5677#discussion_r4465038569)

File: `torchtitan/distributed/flex_shard/_optimizer_reshard_runtime.py` · line 436

Most of what this releases can't be reused by forward/backward. `_BufferSlot.reserve` (L136-162) allocates `storage_exchange`, `compute_exchange` and `storage_scratch` under `device_handle.stream(transfer_stream)`. The CUDA caching allocator only hands a freed block to later allocations on the stream it was allocated on. So after `release_buffers()`, those blocks sit cached in the transfer stream's pool, and forward/backward on the default stream can't use them. They only become available when an allocation fails and the allocator falls back to `release_cached_blocks()`. That path synchronizes the device, `cudaFree`s every free segment, and counts as an alloc retry. Then the next step's `reserve_buffers` has to `cudaMalloc` them again. Only `compute_scratch` (allocated on the caller stream) can be reused directly.

Consequence: either the knob saves much less than intended, or it saves memory by paying a device sync plus a malloc/free round trip every step, which is exactly what `num_alloc_retries` in the memory monitor flags.

Smallest fix: allocate every slot buffer on the caller/compute stream. That is stream-safe without `record_stream`. `run()` makes the transfer stream wait on the caller before its first redistributed use (`context.transfer_stream.wait_stream(caller)`), and the caller waits on every slot's `done` event before `run()` returns. So by the time the caller-stream free happens, all transfer-stream work on these blocks is already ordered before it. As a side effect this deletes the `transfer_stream` branch in `_BufferSlot.reserve`. *Unverified on GPU*; this is based on allocator semantics, so a `torch.cuda.memory_stats()` reading of reserved bytes and `num_alloc_retries` across steps in both modes would settle it.
