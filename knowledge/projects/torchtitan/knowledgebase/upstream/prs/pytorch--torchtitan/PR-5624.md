# [WIP] [loss] Keep confident-target loss and gradient in _LossParallelCrossEntropy

## Original PR description

## Problem

`_LossParallelCrossEntropy` formed `log_softmax` as `shifted - log(sum exp(shifted))`, with the target's `exp(0) = 1` inside the all-reduced sum. Once the target's margin over the other logits passes ~16.6, the sum rounds to 1 in fp32. The per-token loss and the target gradient `p_t - 1` become exactly 0, while every non-target gradient `p_j` stays nonzero. `compute_logprobs` reuses this Function with `reduction="none"`, so RL per-token logprobs are affected the same way. #5623 has a repro.

## Change

Following Barron et al., "A Fix for Softmax and Cross-Entropy" (arXiv:2610.31642), the NLL is `softplus(logsumexp_{j != t}(z_j) - z_t)`, with the target left out of the sum rather than subtracted from it afterwards.

- **Forward:** the owner shard zeroes the target's exp term before the sum all-reduce. It still uses the same three all-reduces as before: max, non-target sumexp, and target logit.
- **Backward:** still collective-free. `log_softmax` is saved as `z - (z_t + NLL)`, and the owner shard's target slot gets `p_t - 1 = expm1(-NLL)` instead of `exp(log_p_t) - 1`.
- **Memory:** saves the same `log_probs` as before plus the per-token `nll`, and backward no longer allocates a `zeros_like`.

**Numerics notes:**
- Results are no longer bitwise identical to `loss_parallel()`. At ordinary margins they agree within `assert_close`'s default fp32 tolerances, so `test_loss_parallel_cross_entropy_parity` now uses `torch.testing.assert_close` instead of `torch.equal`.
- The non-TP path (`F.cross_entropy`) is unchanged and still has the rounding. TP > 1 and TP = 1 therefore no longer match bitwise for confident targets.

## Convergence check (TP=2)

`scripts/loss_compare.py` with this PR's base (`89e4339`) as the baseline and this PR (`44ae27d`) as the test, both on the same seed checkpoint with seed 42 and deterministic mode.
- **Model and parallelism:** Llama 3 debug model with TP=2 and every other parallelism at 1, so the loss goes through `_LossParallelCrossEntropy`.
- **Data and length:** streamed C4 (`allenai/c4`, `en`), 1,000 steps.
- **Hardware:** 2× A40, torch `2.16.0.dev20261027+cu132`.

- **Loss:** step 1 is bitwise identical. From step 2 the runs differ at about 1e-5, the new formula's different rounding after the first optimizer update. By the end that has grown to the usual run-to-run drift of about 1e-3. There's no sign of a regression, and the slightly lower late loss is within that noise, so it isn't an improvement.
- **Grad norm:** mean 0.5218 → 0.5205 over the 1,000 steps (mean diff −0.0013, largest 0.13).
- **NCCL:** both runs set `NCCL_P2P_DISABLE=1`, because P2P all-reduce hung on that machine's PCIe-connected A40s. It changes only how the GPUs exchange data.
