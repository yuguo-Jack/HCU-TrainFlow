# [rl] Cancel a rollout group on its worker (11/14)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5507) · state: open · merged: False

## Original PR description

**TLDR:** A cancelled rollout group now stops on its rollout worker. Today Monarch runs the worker's `run_group` to the end after the controller cancels it, so at shutdown the in-flight training groups keep generating through post-training validation.

**Problem**
1. **Groups run in worker processes.** The controller sends each group to a rollout worker with `run_group.choose(...)`, a Monarch call.
2. **Monarch doesn't forward a cancel.** The caller returns at once, but the remote `run_group` runs to completion (CPU probe: caller cancelled at 0.3 s, the remote call finished at 2 s).
3. **When.** At shutdown the controller cancels its loops, then runs post-training validation on the same generators; the worker mesh stops only after validation.
4. **What stays held.** A cancelled group also skips `release_groups`, which runs only after `try / except Exception`, so its leases, held KV and cache salts (the group's prefix-cache keys) stay.

**Solution**
1. `RolloutWorkerActor.cancel_group(group_id)` cancels that group's `run_group` task and returns once it ended.
2. `Rollouter.run_group_rollouts` awaits it when its own caller is cancelled (at most 30 s, PR 6's limit), then re-raises; a failing `cancel_group` is logged.
3. `Controller._rollout_loop` calls `release_groups` in a `finally`, and a native rollout releases its routing session in a `finally`.
4. The native group gathers with `return_exceptions=True`, as Verifiers does, so a cancel waits for every sibling's release.
5. Unchanged: no cancel trigger besides shutdown. Verifiers groups still run in the controller here (PR 12 moves them).

**Results**
Numerics: bitwise vs main. Nothing changes unless a group is cancelled, which only shutdown does today.

You may ask:
- Why `cancel_group.call` on every worker? `choose` doesn't report which worker took the group; the others return at once.
- Why not cancel only at the generator? That stops no env work: tool calls and sandboxes keep running until their next model call.

NOTE:
- Monarch starts two concurrent-endpoint calls from one sender in order (monarch `_src/actor/concurrent.py`), so `cancel_group` finds a group whose `run_group` was sent first.
- A sibling cancelled inside `acquire` still sends `release_session` from the same worker, and Monarch starts one sender's calls in order, so `release_groups` frees any lease it never gave back.
- What closes the race: generate results no longer pass through the router (PR 9), and `cancel_group` returns only after every sibling's router calls landed. Left: a sibling cut off inside its final `release_session`; no run hit it.
- Cancelled Verifiers groups are released too, but their env server keeps starting the group's queued runs (~45 s of new training rollouts during post-training validation, on main too). Stopping queued Verifiers runs is a follow-up.
- `asyncio.to_thread` work inside `env.step` keeps running after a cancel, as with `step_timeout_s` today.
- Without PR 10, a request the generator already admitted decodes to its end after its HTTP call closes.
- PR 6's TODO about rollouts that fail at shutdown goes: they are cancelled now.
