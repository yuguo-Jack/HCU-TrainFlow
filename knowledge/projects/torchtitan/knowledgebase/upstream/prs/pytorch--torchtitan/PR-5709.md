**TLDR:** With DeepEP, the expert SwiGLU now multiplies each row by its routing score inside its compiled region (rows x F, fp32), and DeepEP's combine only sums. Before, an eager bf16 multiply ran over w2's output (rows x D), and the default remat kept that output. One MoE layer fwd+bwd, EP 2, compiled, vs PR 4: DeepSeek-V3 671B -12 to -13%, Qwen3.5-35B-A3B -12 to -26%; kept memory under the default remat -63% (DeepSeek-V3) / -58% (Qwen3.5), to 37% / 42% of main's. The shipped DeepEP RL recipes apply `fused_swiglu`, so their forward keeps today's path; the router gradient changes for every DeepEP run, because dispatch backward no longer rounds it to bf16 (Solution 4).

```text
before:  w13 -> activation region -> w2 -> * score (eager, R x D, bf16) -> combine
after:   w13 -> activation region (* score, fp32) -> w2 -> combine (sums only)
```


**Problem**
1. With PR 4, DeepEP's dispatch returns R rows, one per (token, local expert) pick, and one fp32 score per row.
2. `combine_tokens` casts the scores to bf16 and multiplies the expert output (R x D) by them in eager, because DeepEP's combine op only sums rows.
3. That broadcast multiply and its backward (two more multiplies and a row sum) run as separate eager kernels over R x D.
4. Its backward needs w2's output, so autograd keeps an R x D bf16 tensor per layer, and so does the default remat (DeepSeek-V3: 1.75 GiB at 16k tokens per rank, EP 2).
5. When it happens: DeepEP with the stock `SwiGLU`, e.g. the DeepEP test recipe (`torchtitan_recipes/tests/models/qwen3.py:qwen3_moe_deepep`). The shipped DeepEP RL recipes apply `fused_swiglu` (`search_r1.py:316`, `tests/rl/alphabet_sort.py:374`) and are unchanged.

**Solution**
1. **`take_routed_scores(metadata)`** on the dispatchers: the base returns None, so combine still applies the scores (local, all-to-all, TorchAO, HybridEP). DeepEP's returns `recv_scores` and clears it from the state, so `combine_tokens` skips its multiply and no longer pins w2's output for backward (the pin now sits in the multiply's branch).
2. **`BinaryActivationFn.__call__(gate_up, *, offsets, scores=None)`** scales row `r` by `scores[r]` inside the `fused_binary_activation` region, in fp32, and rounds once.
3. **`RoutedExperts`** takes the scores only where `w2(h * s) == s * w2(h)` and the activation accepts `scores`: the activation is exactly `SwiGLU`, w2 has no bias, and there is no output postprocess. `FusedSwiGLU` (a `BinaryActivationFn`, not a `SwiGLU`, `fused_swiglu.py:315`) has no `scores` in its `__call__`; gpt-oss's experts add a w2 bias.
4. **DeepEP's dispatch backward returns the score gradient in fp32,** the dtype of its `topk_weights` input, instead of rounding it to bf16. This applies to every DeepEP run and is separable.
5. **Unchanged:** the DeepEP custom ops, every other dispatcher, and the fallback's forward (other activations, a w2 bias, a postprocess), where combine applies the scores as before.

You may ask:
- **Why only DeepEP?** The all-to-all dispatcher applies the scores on the source rank after the combine all-to-all, so the expert rank never has them. The local dispatcher (EP = 1) could hand its expert-sorted scores over the same way; not done here: it would change every EP = 1 MoE run's numerics and goldens.
- **Why not the `fused_swiglu` recipes?** `FusedSwiGLU`'s Triton op has no score input. The decision row says the DeepEP recipes would gain more by dropping the override (-11 to -24%, compiled) than by fusing the scores into it; that recipe change is a follow-up that needs an RL run.
- **Why fp32 for the multiply?** The scores arrive in fp32; rounding once after the multiply loses less than rounding the scores and the w2 output to bf16 first. Against fp64 (CPU, `R` = 257, compiled region): output 4.44e-3 -> 3.77e-3, score grad 4.63e-3 -> 3.87e-3.
- **Why not make the score gradient bitwise run-to-run?** Default Inductor options would make it row-order independent, at 1.6-1.8x the region's fwd+bwd (230.7 -> 373.8 µs at R = 131k, 377.3 -> 675.6 µs at R = 262k, F = 512): 1.5-3% of a compiled Qwen3.5 layer, for a property deterministic mode already gives.
- **Why clear `recv_scores` instead of passing a flag to combine?** The state then says by itself whether combine still owes the multiply.
- **Why not on w2's input, outside the region?** It still runs as its own eager pass over R x F, in bf16.

NOTE:
- Determinism: the forward stays bitwise under any row order (trainer == generator). Under the region's options, the score gradient's per-row sum depends on the row's position, so outside deterministic mode compiled Qwen3.5's x grad and router grad vary between runs (PR 4 already varies the routed-expert grads). Deterministic mode is bitwise (compiled Qwen3.5, 16k).
- The region compiles separate graphs for `scores` None and a tensor. Where shared and routed experts share an F (Qwen3.5-35B-A3B without TP, F = 512), that F needs about twice the graphs, under the limit of 16.
- MXFP8 / NVFP4 grouped experts can't use the DeepEP dispatcher (`quantization/utils.py:77` raises), so this path doesn't meet them.
- Not run: multi-node, EP > 2 on GB300, non-SwiGLU activations with DeepEP (they take the fallback), an RL run. H100 CI (`ciflow/h100.8`) on the previous head 64a2e7eea (run 41000419452): DeepEP test 4 passed, `qwen3_fsdp+deepep` passed; re-runs on this head.

This gate decides on the activation's exact class. Shared code then checks for one concrete type, and any activation that isn't exactly `SwiGLU` drops to the slower path without saying so. That covers `LimitedSwiGLU` (deepseek_v4), `SiTUGLU` (kimi_k3) and any `SwiGLU` subclass, even though they inherit the same `BinaryActivationFn.__call__` and would accept `scores` with no changes. The only reason for the exclusion is that `FusedSwiGLU` overrides `__call__` and doesn't take `scores`.

Smaller alternative: make `scores` part of the `BinaryActivationFn.__call__` contract. Every subclass takes it, and `FusedSwiGLU` applies it with one eager fp32 multiply on its R x F output. That's still cheaper than the R x D multiply in combine, and it frees w2's output. The gate then shrinks to the two w2-linearity conditions (no w2 bias, no postprocess). The shipped DeepEP RL recipes would get the memory win too. That does change their numerics, so if you want to keep this PR off that path, say so here in a TODO pointing at the follow-up, and keep the exact-type check until then.

The GPU test's `_SwiGLUSubclass` trick also depends on this exact-type check. With the contract above, the "combine applies" arm could use a biased-w2 or postprocess case instead.
