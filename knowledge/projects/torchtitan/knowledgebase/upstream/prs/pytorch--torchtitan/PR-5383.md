# [rl] Generator: vLLM's dense CUDA graph sizes, plus a prefill tail

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5383) · state: open · merged: False

## Original PR description

**TLDR:** The generator's default CUDA graph sizes go from powers of 2 to vLLM's spacing, plus a coarse tail for FULL prefill. 34 running sequences now pad to the 40 graph instead of the 64 graph. On a 4-layer Qwen3.5-35B-A3B, a 64-row decode step takes 2408 us and a 34-row step 2072 us.

**Problem**
1. **Padding.** vLLM runs each step on the smallest captured CUDA graph that fits it, and pads the batch to that size.
2. **Today.** `VLLMCudaGraphConfig` captures powers of 2 up to the cap, plus `max_num_seqs` and the cap.
3. **Agent rollouts.** A generator often runs a few dozen sequences: 34 sequences pad to the 64 graph.
4. **Cost.** 4-layer Qwen3.5-35B-A3B, 2k context, GB300: a 64-row decode step takes 2408 us, a 34-row step 2072 us (+16%).

```
before:  1 2 4 8 16 32 64 128 256 ... 16384                                                 (+ max_num_seqs)
after:   1 2 4 | 8 ... 248 (+8) | 256 ... 1024 (+16) | 1536 ... 4096 (+512) | 6144 ... 16384 (+2048)   (+ max_num_seqs)
```

**Solution**
1. `_default_capture_sizes`: 1, 2, 4, every 8 to 256, every 16 to 1024 (or to `max_num_seqs`, if larger). This is vLLM's own spacing.
2. FULL also graphs prefill, so above that it adds every 512 up to 4096, then every 2048 up to `max_num_batched_tokens`.
3. `max_num_seqs` stays an exact size: with GDN/KDA layers, FULL decode graphs stop at `max_num_seqs`, so a full batch must not pad past it.
4. Unchanged: explicit `capture_sizes`, the cap, and the expert-parallel size filter.

**Results**
```
Numerics: not compared. A step now replays a smaller padded graph, so its GEMMs can pick other tiles (rounding only).

4-layer Qwen3.5-35B-A3B, GB300, TorchTitan V1 runner, FULL graphs, max_num_batched_tokens 16384

decode, 2k context, kernel us per step
B=34          2072   <- this PR pads 34 to 40 (the 40 graph was not timed)
B=64          2408   <- where 34 sequences pad on main

prefill, wall per request (2k-16k new tokens): with the +512/+2048 sizes vs no graph above 1024
median   1.81x -> 1.00x
worst    2.83x -> 1.00x
```

```
graph captures at max_num_seqs 230, max_num_batched_tokens 16384 (counted from the size lists, not measured)
                                    main   this PR
FULL graphs                           16        96
extra decode graphs (GDN/KDA)          9        32

engine init and KV blocks, one recipe:  <FILL IN BEFORE POSTING: before -> after>
```

You may ask:
- Why not stop at 1024, like vLLM's default? Prefill steps above 1024 tokens would run without a graph: 1.8x slower above.
- Why keep `max_num_seqs` as its own size? With GDN/KDA, decode graphs exist only up to `max_num_seqs`. A full batch of e.g. 230 padded to 232 finds no decode graph and runs eager.

NOTE: Not measured: the new prefill sizes vs main's powers of 2 (which also graph 2048 to 16384, with more padding).
