# [rl] Allocate the generator's pinned weight-sync buffers directly, without a staging copy

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5485) · state: open · merged: False

## Original PR description

NOTE: measured on H100 only; needs retesting on Blackwell.

**TLDR:** The generator built its pinned CPU weight-sync buffers by copying every GPU shard to pageable CPU memory first. This PR allocates them pinned directly. For 64 GiB of weights that step drops from 51.4 s to 13.7 s (H100 host), on every generator start.

**Problem**
1. **Buffers.** On each weight sync, the generator prefetches the trainer's weights from TorchStore into pinned CPU buffers, then copies them to the GPU.
2. **Built once.** `VLLMModelWrapper.__init__` builds them with torch's `_create_cpu_state_dict(self.model.state_dict(), pin_memory=True)`.
3. **The waste.** For each DTensor weight, it copies the local shard to pageable CPU memory, allocates a pinned tensor, and drops the copy.
4. **Cost.** 64 GiB of FSDP-sharded bf16 weights: 51.4 s on one H100 host. Qwen3.5-35B-A3B on GB300 (65 GiB per engine, an earlier main): about 50 s per engine, before the first weight sync.

**Solution**
1. `_empty_pinned_like(tensor)` allocates `torch.empty(local_shape, dtype, device="cpu", pin_memory=True)` and wraps it in a DTensor with the weight's spec (mesh, placements, global shape).
2. `__init__` builds the buffers with it, then keeps the existing `_copy_state_dict` that fills them with the model's values (GPU -> pinned, about 0.2 s per 9 GiB), so keys the trainer doesn't publish keep their init value.
3. Unchanged: each buffer's DTensor spec, the NUMA binding before allocation, and every TorchStore call.

**Results**
```
Building the buffers. FSDP-sharded bf16 Linear weights, 1 rank, H100 host, torch 2.15.0.dev20261005
8 GiB      6.5 s -> 1.7 s
64 GiB    51.4 s -> 13.7 s

Standalone VLLMGenerator init, Qwen3.5-4B-Base, TP1, 1x H100, warm compile caches, 9.0 GiB of buffers.
4 runs each on a shared host (load average ~180), measured before the fill copy was added (+0.2 s).
vLLM "Model loading"          12.5 / 11.4 / 11.1 / 10.6 s  ->  4.9 / 3.5 / 7.5 / 5.1 s
VLLMGenerator init (median)   28.0 s  ->  22.2 s
```
End to end, 3 steps of Qwen3-0.6B alphabet sort (trainer and generator on one H100): weight sync works; trainer vs generator logprob diff -0.0018 (main -0.0016); step-0 validation reward 0.190 (main 0.192).

You may ask:
- Why not allocate at the first prefetch? At startup the first prefetch comes right after init, so the cost only moves.
- Why build the DTensor by hand? `DTensor.from_local` moves the local tensor to the mesh's device (the GPU).

NOTE: quantized FSDP weights (e.g. MXFP8) used to get unpinned buffers (the old path treats a tensor subclass as empty); they now get pinned ones. A probe with such a weight loaded the prefetched value exactly, without the fill copy; not run with it.
NOTE: allocating pinned memory still costs 13.7 s per 64 GiB; a TODO in the code suggests a background thread while vLLM profiles memory.

**Test plan**
```bash
CUDA_VISIBLE_DEVICES=0 pytest -q tests/rl/unit_tests/gpu/test_prefetch_buffers.py
CUDA_VISIBLE_DEVICES= pytest -q tests/rl/unit_tests/cpu
```
`test_empty_pinned_like_keeps_spec_without_reading_weights`: a [2, 8] shard of a [4, 8] weight whose storage is freed gets a pinned CPU [2, 8] local tensor with the weight's DTensor spec. The old copying path fails it.
