# [rl] read each trainer rank's microbatches two ahead of training

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5286) · state: closed · merged: True

## Original PR description

**TLDR:** Reads now overlap compute: each trainer rank reads its RDMA microbatches two ahead on a background thread, and the engine trains each one as it arrives. On H100 the loss is bitwise equal to the base at DP 1 and DP 2, and reads after a step's first microbatch wait ≤ 1.1 ms per step in total. Opt-in: it needs the RDMA fast path (`async_loop.batcher.rdma_min_tensor_bytes`) and the new `trainer.training.preprocess_microbatch_groups_lazily=True`.

**Problem**
1. **With the RDMA fast path on, each rank reads its whole column before compute.**
2. **The reads are exposed:** est. ~0.15% of `forward_backward` at 38 B/token, ~2% at 614 B/token, up to ~25% for a fast trainer with a heavy payload and 16 TCP readers.
3. **The whole column sits in host memory.**
4. **The engine needs every microbatch before the first forward:** `TrainingEngine.forward_backward` preprocesses every group up front, so it would drain a prefetcher before training starts.

**Solution**
1. **`TrainingEngine`, opt-in:** with `training.preprocess_microbatch_groups_lazily=True` (default False), each group is preprocessed just before its forward (PP included), by the new `_preprocess_microbatch_group`.
   - Rejected with CUDA graphs on (TODO: several smaller graphs), with SDC replay, and by `GraphTrainer`. The RL controller warns when `rdma_min_tensor_bytes` is set without it.
   - Each model fills its own `aux_loss_denominators` (the aux-denominator PR below), so one group needs no engine patch.
2. **`RDMAMicrobatchPrefetcher`:** `Trainer.forward_backward` passes it as `microbatch_groups` when it gets `MonarchRDMAMicrobatch`es (by value, the column as before).
   - It reads this rank's column on a thread, two ahead, one `asyncio.run` per read, with the actor's context copied in (else Monarch starts a second client). The engine needs only `len()` and one pass.
   - Ending the pass early (e.g. a failed step) cancels the queued reads. A `wait_for_microbatch` span records the read time training didn't hide; the total read time feeds `timing/trainer/read_microbatches/max`.
3. **Unchanged by default:** pretraining, ROCm and by-value RL preprocess up front as on main. With RDMA on but lazy off, the engine drains the prefetcher first: correct, no overlap.

```text
engine, default:  preprocess 0, preprocess 1 | fwd/bwd 0 | fwd/bwd 1
engine, lazy:     preprocess 0 | fwd/bwd 0 | preprocess 1 | fwd/bwd 1

trainer rank:  read thread  | read 0 | read 1, read 2 | read 3  | ...
               main thread  | wait   | train 0        | train 1 | ...
```

**Results**

GPU, Qwen3-0.6B, H100, batch invariant, lockstep, 10 steps, one TP 1 generator, 4,096-token microbatches (0.16 MB each), RDMA and lazy preprocessing on. From an earlier push, before the opt-in flag (not re-run on GPU). "main + engine change" is upstream main plus this PR's engine change, without the RDMA microbatch PR:
```text
                                          trainer DP 1 (2 GPUs)          trainer DP 2 (3 GPUs)
loss/mean, vs main + engine change        bitwise equal at all 10 steps  bitwise equal at all 10 steps
forward_backward, main + engine change    1.393 s                        0.909 s
forward_backward, RDMA microbatch PR      1.414 s                        0.910 s
forward_backward, this stack              1.399 s                        0.932 s
wait_for_microbatch, first read           2.3-3.1 ms per step            2.8-5.1 ms per step
wait_for_microbatch, later reads          0.4-1.1 ms per step in total   0.2-0.7 ms per step in total, per rank
```
- At this size there is little to hide, and the forward_backward rows differ by run-to-run noise (the RDMA microbatch PR row is a separate run). Prefetch pays with heavier per-token payloads (see NOTE).
- At the batcher-process and scatter PRs' heads (which include this PR), trainer DP 2, 5 steps: `loss/mean` bitwise equal to main's DP 2 at every step, over TCP and over ibverbs.
- CPU stress: 1,500 steps x 8 microbatches x 4 ranks of register, read and drop: every field matched, no hang.

You may ask:
- **Does this change pretraining?** No, lazy preprocessing is off by default. With it on, the device holds one group's inputs instead of the step's (an RL step of 46 x 128K tokens: 229 MB -> 5 MB).
- **Why not with SDC replay?** Replay reruns a checked step on the same inputs, so lazily it would preprocess (and count `ntokens_seen`) and read every microbatch again.
- **Why a Python thread if Rust moves the bytes?** A Monarch `Future` does nothing until someone calls `get()` or awaits it, and the actor's loop thread is busy in forward/backward.
- **Why two ahead?** A rank then holds at most 4 microbatches on the host (2 queued, 1 waited on, 1 training). Not tuned.

NOTE:
- **The lazy path costs ~4 ms per microbatch** (pageable inputs and varlen's host sync; +0.77% at 16K tokens, Qwen3-0.6B, H100), about what prefetch hides at 38 B/token. In a repro, pinned inputs plus `max_num_documents` removed it; pinned alone did not.
- **Metrics:** with the fast path, `trainer/tokens_per_second` and MFU now include the reads: each step's first read with lazy preprocessing on, every read with it off. The weight push returns after `forward_backward`, as on main (the RDMA microbatch PR let it finish during the reads).
- **Not tested:** multiple hosts; the RL GPU CI.

**Test plan**
- Repo root, Monarch 0.7, merged with main: `pytest tests/rl/unit_tests/cpu` 497 passed, 5 skipped; `pytest tests/unit_tests/cpu` 1,658 passed; the only failures fail on main too (offline: 3 tokenizer downloads, `test_download_hf_assets`; `test_quantization.py` needs `torchao`).
- `test_trainer.py`: by value, the column goes to the engine as is; with `MonarchRDMAMicrobatch`es, the prefetcher reads it and the read time is reported.
- Engine: lazy and up-front preprocessing (PP included), the flag reaching the body, and the config checks (CUDA graphs, SDC, GraphTrainer).
- `test_rdma_microbatch.py`: the prefetcher yields in order and reads exactly two ahead (fails for a read-ahead of 0, 1 or 100); the read thread sees the caller's context; closing it cancels queued reads.

### On @tianyu-l's comments

**1. `training_engine.py:498`: make lazy preprocessing an explicit config (strongly agree)**

Right now lazy preprocessing turns on for **every** eager run without SDC: pretraining recipes with `disable_cuda_graphs=True`, ROCm (`not cuda_graphs_supported()`), Flux and DeepSeek-V3. The PR's own NOTE says this path costs about 4 ms per microbatch (pageable H2D plus varlen's host sync), and it was not measured on Flux, DSv3 or ROCm. Pretraining gets nothing from it, since its inputs come from a dataloader and are already pinned. That cuts against "protect battle-tested code paths." Suggestions:
- Add `training.preprocess_microbatch_groups_lazily: bool = False`. The docstring should say it exists so RL can overlap the controller -> trainer transfer with forward/backward. Turn it on in the RL recipes, which all set `disable_cuda_graphs=True` already.
- In `__post_init__`, raise `ValueError` if it is set with `disable_cuda_graphs=False` or with `sdc_replayer`. ROCm with `disable_cuda_graphs=False` would then be rejected even though it runs eagerly. That's fine: the user sets the flag explicitly.
- `GraphTrainingEngine` overrides both `_initialize_forward_backward` and `_forward_backward_body`, so it would silently ignore the new flag. It should reject the flag, or at least warn.
- On the RL side, an RDMA run (`rdma_fast_path_threshold` set) with lazy preprocessing off still works, because the engine drains the stream up front. But nothing overlaps, so warn once, per the "silently skips user configuration" rule.
- This also removes the `_preprocess_groups_lazily=False` lines added to about 8 `SimpleNamespace` engine fakes in the tests.

**Why it can't work with SDC replay (your question):** `SDCReplayer.run_fwd_bwd` calls `execute` **twice** on a checked step (`sdc_replayer.py:376`, `_run_checked`). With lazy preprocessing, `execute` iterates over the raw `microbatch_groups`, so the replay would:
- (a) re-run `_preprocess_microbatch_groups`, which **double-counts `ntokens_seen`** (`training_engine.py:613`). That value is checkpointed state.
- (b) iterate `MicrobatchStream` a second time. `__iter__` builds a new pool and **reads every microbatch over RDMA again**, even though the class says it supports only one pass.
- (c) for pretraining, it would also re-run H2D and mask building inside the region being checked.

Banning the combination is right. It would help to say why in the `ValueError` message.

**2. `training_engine.py:670`: add a dedicated `_preprocess_microbatch_group()` (agree)**

The pattern `self._preprocess_microbatch_groups([microbatch_group])` followed by `[prepared_inputs] = prepared_groups` is awkward. The plural method's loop body (lines 597-649) splits cleanly into a singular method that returns one prepared tuple. The plural one becomes `[self._preprocess_microbatch_group(g) for g in groups]`. The `ntokens_seen` accounting would live in the singular method. `GraphTrainingEngine._preprocess_microbatch_groups` overrides the plural method and never runs lazily, so it can stay as is.

**3. `training_engine.py:569`: move the `aux_loss_denominators` fill into `Model.preprocess_inputs()` (agree)**

Benefits:
- It removes `_set_aux_loss_denominators`. That helper detects PP vs non-PP by checking whether the tuple has 3 or 4 elements.
- It removes the `self._global_routing_token_counts` attribute, which exists only to pass state from one call to the next.
- The PP path and `GraphTrainingEngine` get it for free.

The models already write `input_dict["aux_loss_denominators"] = None` as a placeholder, so they would write the real tensor instead. To audit every callsite, the new keyword has to reach:
- `models/base/model.py:52` (signature)
- `common/decoder.py:331`
- `qwen3_5/model.py:557`
- `deepseek_v3/mtp.py:326` (per-depth tensor; it already checks `numel() == len(mtp_layers) + 1`)
- `kimi_k3/model.py:544`
- `kimi_k2_7/model.py:182`
- the `**kwargs` overrides: flux, muse_glimmer, `transformers_modeling_backend`
- `graph_trainer/precompile_main.py:267`, which fills the value by hand

Two caveats:
- `preprocess_inputs` runs under `activate_spmd()`. The value must be set **after** `annotate_input_spmd_types`, so it stays a plain tensor as it is today.
- `forward_backward` always receives `global_routing_token_counts`. The new keyword can therefore be required rather than defaulting to `None`.

This could be its own small PR before this one, since it touches every model.

**4. `rdma_microbatch.py:113`: rename (agree, with one fix)**

The suggested name has a typo: `RMDAMicrobatchStream` should be `RDMA...`. I agree that "stream" is overloaded: CUDA streams appear all through `training_engine.py`. I'd use **`RDMAMicrobatchPrefetcher`**. It names the scope (RDMA) and what it does (reads ahead). Also update:

It is used only there. `_read` could also be a closure, accumulating into a local and assigning `self.read_s` in the `finally`.

### My own findings

1. **The `finally` cleanup only runs when the generator is closed** (`rdma_microbatch.py:148-151`). If forward/backward raises mid-step, the `enumerate(microbatch_groups)` iterator in `_forward_backward_body` stays alive as long as the traceback is referenced. Monarch's actor error handling may keep it, so the `shutdown(cancel_futures=True)` that cancels the queued reads can run late or never.
   - Also, `shutdown()` defaults to `wait=True`, so if the controller is gone, the read already in flight still blocks for up to the 60 s RDMA timeout.
   - The comment "On an error, cancel queued reads" reads as stronger than what happens. Either call `iterator.close()` explicitly from the engine loop, which is awkward in core, or reword the comment to describe the real behavior.
   - The current test (`iterator.close()`) only covers the explicit-close case.
2. **`read_s` accumulates across iterations.** If anything iterates twice (see the SDC point above), the reported `read_microbatches/max` doubles. Renaming the class to a prefetcher and documenting it as one-pass, or raising on a second `__iter__`, would make the contract explicit.
3. **The cross-thread write to `read_s`** is safe today: `pool.shutdown()` in the `finally` joins the worker before `Trainer` reads the value. A comment saying the value is valid only after iteration ends would stop someone from reading it mid-step.
4. **`_step_num_tokens_per_dp_rank` now counts tokens differently** (`rl/trainer.py:269`). It changed from `sum(labels.numel())` to `len(microbatches) * num_tokens_per_microbatch_per_dp_rank`. That matches `Batcher`'s fixed `rows x seq_len` padding (`batcher.py:204`), so the value is the same today. But the by-value path now trusts an invariant it used to compute directly. This is fine; just pointing it out.
5. **The `_ForwardBackwardFn` type is now `list[Any]`.** After the config change, it might be clearer to type it as `Sequence[list[TrainingMicrobatch]] | list[tuple[Any, ...]]`, and to change `forward_backward`'s `microbatch_groups` annotation from `list[...]` to `Sequence`/`Sized & Iterable`. A `MicrobatchStream` is not a `list`.
6. **Test timing:** `test_microbatch_stream_yields_in_order_and_reads_two_ahead` uses sleeps, but a read past the window is structurally impossible, so it can't fail spuriously. 👍

### Summary
- **Blocking:** the opt-in config (#1). It keeps pretraining and ROCm on the code path that has been validated.
- **Cleanups:** #2, #4 and #5 are small refactors worth doing in this PR. #3 touches every model variant and might fit better as a separate PR before this one.
- **Not done:** I didn't run any tests or GPU jobs. This is a read-only review.
