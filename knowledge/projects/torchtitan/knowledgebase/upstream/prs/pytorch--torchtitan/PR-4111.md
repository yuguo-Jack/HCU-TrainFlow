# RoPE cache sharing

[Upstream PR](https://github.com/pytorch/torchtitan/pull/4111) · state: closed · merged: False

## Original PR description

# Summary

When training with long contexts (>128K), the RoPE cache can become substantial, especially for models with many layers.

Currently, in TorchTitan, each layer creates its own RoPE cache even when the RoPE configuration is identical across layers. This results in significant memory duplication.

For example, with:

* Head dimension: 128
* Context length: 128K
* Precision: FP32
* Number of layers: 40

The approximate memory usage is:

```text
128 * 131072 * 32 * 40 / 8 / 10^9 ≈ 2.7 GB
```

By sharing the cache across layers, this can be reduced to:

```text
128 * 131072 * 32 / 8 / 10^9 ≈ 67 MB
```

This PR enables RoPE instances with the same configuration to share the underlying cache.

# How It Works

Previously, calling:

```python
x1 = rope.build()
x2 = rope.build()
```

would create two distinct RoPE objects, each with its own identical cache.

With this PR, building RoPE multiple times from the same configuration returns the same object, allowing the underlying cache to be shared:

```python
x1 = rope.build()
x2 = rope.build()

assert x1 is x2
```

If two independent caches are required, the configuration can be explicitly duplicated:

```python
x1 = dataclasses.replace(rope).build()
x2 = dataclasses.replace(rope).build()
```

This makes RoPE sharing implicit and configuration-driven: layers using the same RoPE configuration automatically share the same instance and cache. If different layers use different RoPE configurations, sharing is automatically disabled.

# Changes

To enable this sharing mechanism, this PR:

* Removes several `dataclasses.replace(rope)` calls that were unnecessarily copying the configuration and preventing sharing.
* Updates some model configurations so that layers can correctly share the same RoPE configuration.
* Adjusts the existing guards that prevent the same module from being parallelized multiple times, since shared RoPE instances can now legitimately appear in multiple layers.

# Notes

The sharing mechanism itself is intentionally simple: **using the same RoPE configuration enables sharing**. No additional model-specific logic is required.

File: `torchtitan/models/common/rope.py` · line 147

Caching by sharing config sounds a bit fragile, as it more-or-less break the modularity benefit brought by the config system.

ChatGPT gives me three alternatives
1. manage class attribute which `.to(device)` doesn't work with
```
import torch
import torch.nn as nn

class MyModule(nn.Module):
    shared = None  # class-level

    def __init__(self, n):
        super().__init__()
        if MyModule.shared is None:
            MyModule.shared = torch.zeros(n)  # created once

    def forward(self, x):
        # ensure it's on the right device if needed
        shared = MyModule.shared.to(x.device)
        return x + shared
```
2. Make it a per-instance buffer but have all instances reference the same underlying storage initially:
```
class MyModule(nn.Module):
    _shared = None
    def __init__(self, n):
        super().__init__()
        if MyModule._shared is None:
            MyModule._shared = torch.zeros(n)
        # instance buffer points at the same tensor object
        self.register_buffer("buf", MyModule._shared)
```
Caveat: if you later call m.to(device) on one instance, PyTorch will typically replace that instance’s buf with a new tensor on the target device—so it may stop being shared across instances.

3. store it outside modules (or in a dedicated “owner” module) and pass it in, rather than making it class-level.
```
class Shared(nn.Module):
    def __init__(self, n):
        super().__init__()
        self.register_buffer("buf", torch.zeros(n))

class MyModule(nn.Module):
    def __init__(self, shared: Shared):
        super().__init__()
        self.shared = shared

    def forward(self, x):
        return x + self.shared.buf
```

We used to have 3, but it is not very modular, and needs extra care when working with PP.

- francesco-bertolotti · comment · 2026-08-13T10:21:40Z · [source](https://github.com/pytorch/torchtitan/pull/4111#discussion_r3774456966)

File: `torchtitan/models/common/rope.py` · line 147

I think the reason PP needs special treatment is that our internal solution ties the cache across different layers. If layer 0 is the one that owns the actual cache, we assume that layer 0 will not be deleted by pipeline parallelism.

With respect to @fegin's solution, I think we still need to make sure that `shared_rope` is not associated with any layer; otherwise, it could get dropped by PP.

One option would be to explicitly disallow tying when PP > 1:

```python
class Decoder(BaseModel):
    @dataclass(kw_only=True, slots=True)
    class Config(BaseModel.Config):
        ...
        def update_from_config(self, *, config, **kwargs) -> None:
            ...
            if self.enable_weight_tying and parallelism.pipeline_parallel_degree > 1:
                raise NotImplementedError(
                    "Weight tying is not supported with Pipeline Parallel."
                )
            if self.enable_rope_tying and parallelism.pipeline_parallel_degree > 1:
                raise NotImplementedError(
                    "Rope tying is not supported with Pipeline Parallel."
                )

    ...
    def __init__(self, config: Config):
        ...
        if self.enable_weight_tying:
            self.tok_embeddings.weight = self.lm_head.weight
        if self.enable_rope_tying:
            self._share_rope_modules()

    def _share_rope_modules():
        # Traverse all rope configs.
        # If two or more have the same config,
        # tie the underlying cache.
```

This is also the approach Torchtitan takes for `weight_tying=True` with PP > 1. The `enable_rope_tying` option isn't strictly necessary; we could simply perform rope tying only when `PP == 1`.

Alternatively, if the PP boundaries are known at `__init__` time, I think we could tie only the model parts that end up on the same rank. That would avoid the issue of a tied layer being deleted later by PP.
