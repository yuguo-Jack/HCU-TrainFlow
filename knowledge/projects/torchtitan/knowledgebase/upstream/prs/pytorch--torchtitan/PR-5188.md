# [rl] DAPO-Math grader: box the gold answer before parsing

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5188) · state: closed · merged: True

## Original PR description

**TLDR:** Math-Verify reads LaTeX only inside a delimiter like `\boxed{}`, and our gold answers are bare. So gold `2\sqrt{3}` was read as 2: the model's `\boxed{2}` scored 1.0 and the right answer 0.0. Now the gold is boxed like the prediction. No change on DAPO-Math (integer golds); ~19% of INTELLECT-3-RL math golds were misread.

**Results**
```text
math-verify 0.9.0, score_math_response(response, gold)   before -> after
gold 2\sqrt{3}, response \boxed{2\sqrt{3}}               0.0 -> 1.0
gold 2\sqrt{3}, response \boxed{2}                       1.0 -> 0.0
gold (1,2),     response \boxed{(1,2)}                   0.0 -> 1.0
gold \pi/4,     response \boxed{\frac{\pi}{4}}           0.0 -> 1.0
```
Today's recipes score the same: every DAPO-Math-17k (12,643) and AIME 2025 (30) gold parses to the same value either way. On 10,805 INTELLECT-3-RL math rows, 949 golds parse to nothing bare and 1,126 to a different value (`3:5` as 3). Counted as `parse(gold)` vs `parse("\\boxed{" + gold + "}")`.

NOTE: an integer gold with a trailing period (`34.`) now reads as the string `34.`, so `\boxed{34}` goes 1.0 -> 0.0. No DAPO-Math-17k or AIME 2025 gold has one.

NOTE: the grader-process PR moves `score_math_response` to `grader.py`; whichever lands second rebases this one line.

You may ask:
- Is this standard? verl (`math_verify.py:59`), NeMo-RL (`math_environment.py:134`) and verifiers (`score.py:103`) box the gold the same way.
- Why not a Math-Verify extraction config? Its LaTeX patterns need a delimiter (`$`, `\(`, `\[`, `\boxed`), so bare LaTeX falls to the number parser, which reads `2\sqrt{3}` as 2.
