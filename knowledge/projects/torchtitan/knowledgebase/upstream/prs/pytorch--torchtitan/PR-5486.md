# [rl] Start the generator model's thread at one CPU thread

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5486) · state: open · merged: False

## Original PR description

**TLDR:** vLLM sets the model's thread to one CPU thread when warmup ends, and torch.compile guards on the thread count, so every compiled region compiles again at the first eager step. Making vLLM's call at model init instead removes the repeat: `OffsetRMSNorm` 13 -> 9 compiles on a 4-layer Qwen3.5-35B-A3B generator, recompiles 24 -> 17 in an RL smoke.

**Problem**
1. The generator compiles its norm, activation, gate and RoPE regions during vLLM's warmup.
2. When warmup ends, vLLM sets torch on the thread that runs the model to one CPU thread, unless `OMP_NUM_THREADS` is set. RL generator processes don't set it, so they start at the host's core count (192 here).
3. torch.compile guards on the thread count (`GLOBAL_STATE changed: num_threads`), so each region compiled at 192 threads compiles again at 1, at the first step that runs eager (FULL_DECODE_ONLY mixed steps, NONE, or steps above the capture cap).
4. Every generator process pays this once: on a 4-layer Qwen3.5-35B-A3B, `OffsetRMSNorm` compiles 13 times instead of 9, four other regions 4 instead of 3.
5. It's headroom, not a crash today: a region raises at its 17th version (`recompile_limit=16`), and a 9B replay already uses 13 of 16 on the worst region.

**Solution**
1. `VLLMModelWrapper.__init__` calls vLLM's own `set_torch_threads_for_runtime` (the call vLLM makes when warmup ends), right after it builds the pinned CPU buffers and before vLLM's first compile.
2. vLLM's later call then finds one thread and changes nothing.
3. Unchanged: the actor thread that copies prefetched weights, and a user-set `OMP_NUM_THREADS` (the function leaves that alone, as before).

**Results**
```
4-layer Qwen3.5-35B-A3B-Base, TP1, H100, FULL_DECODE_ONLY, 7 batches (1-64 prompts x 700 tokens),
TORCH_LOGS=recompiles, A-B-A-B, one process each
                                   before             after
OffsetRMSNorm compiles             13, 13             9, 9
norm, activation, gate, RoPE       4 each             3 each
num_threads guard failures         48, 48             0, 0
"Reducing Torch threads" log       after warmup       at model init
model load (s)                     10.95, 8.19        8.29, 11.57
engine init (s)                    23.6, 20.4         21.2, 23.3
decode step median, 64 prompts     4.38 / 4.12 ms     4.06 / 4.23 ms   (round 1)
                                   4.02 / 4.04 ms     4.07 / 4.39 ms   (round 2)

3-step RL smoke through VLLMGenerator (Qwen3.5 debugmodel, FULL_DECODE_ONLY, 2 GPUs), TORCH_LOGS=recompiles
                                   before   after
recompiles                         24       17
num_threads guard failures         45       0
bit_wise/logprob_diff/max          0.012    0.011    (last of 3 steps)
```
Model load (8-12 s) and engine init (20-24 s) vary run to run by the same amount in both arms.
Decode step medians over all 7 batches and both rounds (14 pairs): the PR is within -0.32/+0.35 ms of base, higher in 10 of 14; the largest gap is 8 prompts, round 2 (2.43 -> 2.71 ms). The table shows only the 64-prompt batch.

You may ask:
- Why not `OMP_NUM_THREADS=1` for the generator process? It also puts the actor thread, which copies prefetched weights into pinned memory, on one thread (a 2 GiB CPU copy takes 12.7 ms at 192 threads, 163.6 ms at 1).
- Why not raise `recompile_limit`? That hides the duplicates instead of removing them.

NOTE: H100 only; compile counts don't depend on the GPU.

**Test plan**
No unit test: the call has no logic.
Harness A-B-A-B and the 3-step RL smoke above (both before and after, `TORCH_LOGS=recompiles`).
Quick check on any generator run: with `TORCH_LOGS=recompiles`, `grep -c 'GLOBAL_STATE changed: num_threads'` on the log is above 0 on main and 0 here.
