## Agent details

Written with Claude Code: the analysis, measurements and test plan below.

**TLDR:** When compiled, DeepSeek-V3's group-limited router picks its groups and experts with argmax rounds (k argmax calls, each masking the previous pick) instead of three `torch.topk` calls. The whole selection then fuses into PR 1's router region. Every test picks the same experts as before; scores move by at most 1.2e-7. The 671B router gets 40-48% faster at decode, 59-76% at prefill and 43% in fwd+bwd, about 1% of a training MoE layer (estimate).

```text
before:  gate -> [sigmoid -> topk(2) per group -> topk(groups) -> topk(experts)] -> counts
                 region      ATen        ATen              ATen
after:   gate -> [sigmoid -> argmax rounds x 3 ................................] -> counts
                 one fused region
```

```python
# before (compiled and eager)
group_scores_TG = scores_TGP.topk(2, dim=-1).values.sum(dim=-1)
# after, when compiled (eager keeps topk)
group_scores_TG = scores_TGP.gather(-1, topk_ids_by_argmax(scores_TGP, 2)).sum(dim=-1)
```

**Problem**
1. **The router region.** PR 1 compiles the MoE router as one region (`moe_router_topk`). It picks experts with argmax rounds, which Inductor fuses with the scoring.
2. **DeepSeek-V3 overrides the selection.** Its group-limited routing (671B: 8 groups of 32 experts, keep 4, top-8) calls `torch.topk` 3 times: top-2 per group, top groups, top experts.
3. **Not fusable.** Inductor runs each `topk` as a separate ATen kernel, so with PR 1 alone the 671B router stays slow.
4. **Cost.** At 16k tokens the router takes 620 µs per MoE layer at prefill and 1073 µs in fwd+bwd. Over the 58 MoE layers that is ~62 ms per 16k-token microbatch fwd+bwd (arithmetic).

**Solution**
1. **Argmax rounds when compiled.** `topk_ids_by_argmax` picks the top-2 experts of each group (their scores are summed), then the kept groups. The final pick calls the base `_select_experts`, which already uses argmax rounds when compiled. Ties go to the lower id.
2. **`topk_ids_by_argmax` becomes public** (exported from `torchtitan.models.common.moe`): it now has two users.
3. **Group checks move to `DeepSeekV3Router.Config.__post_init__`.** A bad config now fails at build time with a `ValueError`, not inside the compiled region. Three checks are new:
   - `num_limited_groups` set without `num_expert_groups` (it used to fall back to ungrouped routing silently),
   - more kept groups than groups,
   - kept groups that hold fewer than `top_k` experts.
   The last two would make argmax rounds repeat ids. No shipped flavor trips them.
4. **Unchanged:** eager runs the same `topk` calls. Every other router is untouched.

**Numerics: same experts; scores and grads differ only by rounding**

Why not bitwise: the picked experts are the same, but argmax rounds return them in descending score order, and `topk(sorted=False)` doesn't. So `route_norm` sums the 8 picked scores in another order.

You may ask:
- **How does this relate to the fused Triton router (PR 5551)?** Both speed up the same step. PR 5551 is a hand-written kernel that recipes opt into; this PR stays on the default path with local compile. In an earlier side-by-side run (one GB300, router fwd+bwd without the aux loss), the Triton router is faster at 4k (139.8 vs 170.2 µs) and this PR is faster at 16k (433.2 vs 451.1 µs).
- **Why gather the top-2 values, not `amax` plus a masked second `amax`?** One selection helper instead of a copied round. The `amax` form was 0.7-2.0 µs faster per call (16k forward: 30.1 vs 32.1 µs, earlier run).

NOTE:
- The compiled path assumes finite scores. With a -inf expert bias, a group's second argmax could repeat its first pick. No shipped bias is -inf.
