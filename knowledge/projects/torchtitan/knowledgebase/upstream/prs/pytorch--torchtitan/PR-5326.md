# [validation] Reuse validation sources and isolate evaluation batches

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5326) · state: open · merged: False

## Original PR description

Retain the validation loader's source, storage clients and prefetch workers,
restarting its initial Grain cursor for each evaluation event. Honor the
configured shuffle policy; fixed-seed rebuilding could also preserve order,
but restart avoids rebuilding the data-provider infrastructure. Close owned
readers/handles on failure or trainer shutdown and restore model modes.

Allow validation's global batch to differ from training while sharing the
model parameters and existing schedule builder. Fresh manual pipeline stage
wrappers isolate metadata and receive buffers, retaining registered forward
contexts, cleanup hooks and cached edge communicators. Independent batches
do not support CSV schedules; GraphTrainer integration is downstream work.

Keep the landed eval-first shared-pool capture ordering and preserve each
microbatch's loss kwargs during training metadata inference. Reject a
requested mesh layout mismatch rather than silently returning no mesh.

Validation-only loss projection and generic graph-warmup configuration are
separate stack changes, not part of this loader/schedule PR.

<details>
<summary>Review summary</summary>

### Scope
This PR contains three changes that are independent of each other:
1. Keeping the validation loader around and adding a `restart()` method to it.
2. Letting validation use a different global batch than training, by building fresh eval `PipelineStage` wrappers and a second schedule.
3. Making `_build_get_mesh_callback` raise instead of returning `None`. Every PP training run goes through this helper.

Please split them. (3) in particular needs its own justification against the upstream `GetMeshCallback` contract.

Following up on @tianyu-l's earlier question: the reason given for (1) is that it avoids rebuilding storage clients and prefetch infrastructure. It also adds new lifecycle state (a retained loader, `restart()` on `BaseDataLoader`, and close ordering). Please measure how much the rebuild actually costs before taking that on. If restart is still wanted, snapshotting `state_dict()` once and calling `load_state_dict()` before each eval reuses the existing checkpoint path, and no new loader API is needed.

### Correctness
- **Dist-MoE + PP** (`validator.py:245`): copying `stage._forward_contexts` onto the eval stages also copies a slot map keyed by `(stage, microbatch)` that only covers `range(train_n)` (`dist_moe/runtime.py:523-530`). When eval runs more microbatches than training, it raises `ValueError: no activation-slot assignment`.
- **Fake PG** (`validator.py:237`): the eval stages are built without the `_static_stage_metadata` that `pipeline_llm` requires on a fake process group.
- **"`None` inherits training"** is wrong when `gradient_accumulation_steps > 1`. The new field counts context rows, while training's `num_tokens_per_train_step` counts tokens, so the units don't match. `FluxValidator` also ignores the field without any warning.
- **`except: self.close()`**: `train.py` already does this teardown. Here it also removes the eval stages' forward-context handles, so a later retry would run PP eval without the Dist-MoE context and get no error.

### Tests
- No test in this PR runs `_build_validation_schedule`.
- The non-PP test sets `_validation_num_microbatches` directly instead of deriving it from `global_batch_size`, so the divisibility math is never exercised.
- A CPU or fake-PG test covering eval vs. training microbatch counts with a registered forward context would have caught the Dist-MoE issue.

### Not verified here
I couldn't run Python in this environment, so I couldn't check the upstream PyTorch APIs from PyTorch#200643 (`register_forward_context`, `_post_metadata_inference_cleanups`), or whether Grain's `set_state` stops the prefetch thread. I also couldn't run the tests. The repo's `/pr-review` skill wasn't available, so the inline comments above are standalone comments rather than one batched review.

**Bug (Dist-MoE + PP):** the forward contexts copied here aren't independent of the microbatch count. `_DistMoeForwardContext` (`models/common/dist_moe/runtime.py:110-122`) looks up `activation_slot_id_by_stage_and_microbatch[(stage_index, microbatch_index)]`, and that map is built from the *training* schedule's liveness for `range(liveness.num_microbatches)` (`runtime.py:523-530`). Once the eval schedule has more microbatches than training, `microbatch_index >= training_n` hits the `KeyError` -> `ValueError("Dist-MoE has no activation-slot assignment ...")` branch. When it has fewer, slots get picked using the training coloring, which happens to work for forward-only eval but nothing guarantees it.

So "share registered forward contexts" only holds when `eval_n <= train_n`. Either check that at construction with a clear `ValueError`, or build an eval-specific context or plan. I'd also add a CPU test that runs `_build_validation_schedule` with a registered context; right now nothing in this PR covers this path.

This docstring, and the "None preserves the training batch" line in `config/README.md`, are wrong whenever `gradient_accumulation_steps > 1`. The training global batch is `num_pp_microbatches * gradient_accumulation_steps * dp * mb` (`trainer.py:185-206`), but `None` gives `num_pp_microbatches * dp * mb` (or `dp * mb` without PP).

Units are also inconsistent: training sizes its step with `training.num_tokens_per_train_step` (tokens), and this new field counts "context rows". A token-based name like `num_tokens_per_step` would match training, and the check at L181-190 would collapse to a single divisibility test against `dp * num_tokens_per_microbatch`.

Also, `FluxValidator.Config` inherits this field, but `FluxValidator` doesn't call `super().__init__` and ignores it silently. Per our config rules it should either warn or reject.
