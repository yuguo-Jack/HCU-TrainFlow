- pzhan9 · comment · 2026-10-19T17:25:06Z · [source](https://github.com/pytorch/torchtitan/pull/5505#issuecomment-6273104807)

This stack's `GenerationServer` related changes mix two separate decisions:

1. change `router` from a reverse proxy to a look-aside load balancer.
2. change the `RollouterWorker` to `Generator` path's from monarch messaging to HTTP, even for the native path (i.e. non-verifiers path).

Change 1 is a valid design, except the obvious trade-offs:
* some small complexity on the client side for releasing the lease. (it could get worse quickly though, if we start to consider generator fault-tolerance, or try to integrate a generation stack with stock router).
* the picked generator is pinned throughout the rollout session. We lose the ability to pick a different generator in the middle of the rollout session, e.g. for load re-balancing, or failover. 
    * this potentially is a **deal break** when we run jobs at scale. 

Change 2 makes sense for Verifiers but is unnecessary for the native path, and it makes the code more convoluted. It should be an easy fix to make the HTTP path opt-in only for the verifier path. Or more generically speaking, for path that needs an HTTP endpoint of the generation stack.

**Nevertheless**, before we commit to the look-aside pattern, I think we should look into the following choice first, and at least demonstrate it is not working, since that would be a much smaller change:

* Move the HTTP server to the router, it is off the controller's GIL.
* Forward opaque bytes inside the router, so there is no repeated serialization inside router.

This is how the topology would look like:

```
  Verifiers agent --HTTP--> router (only HTTP server, loopback on controller host)
  native worker   --Monarch: router.generate(...)--> router
  router --Monarch: generate_raw(body: bytes) -> bytes--> generator rank 0
```

No generator hosts an HTTP server: no aiohttp, sockets, ports or URLs on generators.

I like the reverse proxy because it hides the whole generation stack behind the router, which makes it easier to extend:
  - We keep rebalancing and failover mid-rollout.
  - Elasticity becomes a router (and launcher) change.
  - Swapping in a stock vLLM/sglang stack needs mostly router changes, not rollouter/controller changes (not saying we should integrate stock vllm/sglang. Just using them as an example to show the extensibility).
  
With lookaside, each of these is coupled to the clients.

The trade-offs of using reverse proxy over lookaside are:
  1. Router only has 1 GIL. Fixable with a router mesh, e.g. sharded by session id.
  2. One extra hop each way for the payload (in the current code, extra kernel copies). Fixable, e.g. with RDMABuffer, as on the trainer path. 

Depending on the workload or complexity, this is where lookaside might win.
