# [rl] verifiers: register the local taskset alias in every env-server worker

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5482) · state: open · merged: False

## Original PR description

**TLDR:** On main, every Verifiers env-server pool worker of the Terminal-Bench recipes exits at startup with `ModuleNotFoundError: taskset '...' not found`, so the recipes never run a rollout. This PR registers the local taskset in each worker too, through the per-process hook Verifiers already calls, in a module that doesn't import torch.

**Problem**
1. Our tasksets are local modules, e.g. `torchtitan.rl.examples.verifiers.terminal_bench.taskset`. Verifiers imports a taskset by a plugin ID with no dots.
2. `register_local_taskset_alias` bridges the two: it adds the module to `sys.modules` as `torchtitan_rl_examples_verifiers_terminal_bench_taskset`.
3. `_run_env_server_process` registers that alias only in the env-server process.
4. With more than one worker, Verifiers starts pool workers with `spawn`. A spawned worker starts with an empty `sys.modules`, can't import the taskset, and exits.
5. The broker answers health checks itself, so startup looks fine, but no worker is left to run rollouts. The Terminal-Bench recipes use 16 workers (`StaticPoolConfig(num_workers=16)`). DAPO-Math uses 1 (no pool), so it is not affected.

**Solution**
1. `serve_env(log_setup=...)` is Verifiers' per-process hook: it runs it in the env server and first thing in every pool worker it spawns.
2. New `worker_setup.py` holds `setup_env_server_worker(level, local_taskset_module)`: it sets up logging as before and registers the alias.
3. `register_local_taskset_alias` moves there unchanged (plus a docstring example). Workers unpickle the hook by importing its module, and `data.py` imports torch. `data.py` imports the function back, so its callers don't change.
4. Unchanged: the env-server process still registers the alias before `resolve_env_config`, which imports the taskset before `serve_env` runs the hook.

```text
                         main                   this PR
env-server process       alias registered       alias registered
pool worker (spawned)    no alias               alias registered by log_setup
  import taskset         ModuleNotFoundError    ok, torch still not loaded
```

You may ask:
- Why not `fork`, so workers inherit `sys.modules`? Verifiers' pool hardcodes `spawn`, and the broker already holds a ZMQ context, which is unsafe to fork.
- Why a new module? Every worker imports the hook's module, so it must not import torch: `data.py` does, through grain and `torchtitan.rl.rollout.data`. Loading the trainer's imports takes a worker from 185 MB to 1.3 GB of RAM.

NOTE: not run: the Terminal-Bench recipe end to end (needs Harbor and Docker). The 16-worker pool goes through the same `serve_env` path as the test.

**Test plan**
```
pytest tests/rl/unit_tests/cpu/test_verifiers_terminal_bench.py tests/rl/unit_tests/cpu/test_verifiers_example.py
# 14 passed on Verifiers 0.3.1 and on 0.4.0
pytest tests/rl/unit_tests/cpu   # 532 passed, 3 skipped (Verifiers 0.3.1)
```
- `test_env_server_workers_skip_the_trainer_imports` (in CI) now runs the pickled `log_setup` in a fresh interpreter, resolves the env config by its alias and loads the harness: torch, vLLM and Monarch must stay unloaded. It fails on main with `ModuleNotFoundError` (checked on Verifiers 0.3.1 and 0.4.0).
- Removed `test_worker_process_resolves_the_harness_from_a_fresh_interpreter`: it registered the alias by hand, so it passed while every real worker failed; the test above runs the real hook.
