 ## Summary

Add optional validation CUDA graphs with `validator.enable_cuda_graphs=True`. Training, validation, and optimizer graphs share the existing memory pool. Capturing eval first lets its temporary buffers share storage with training gradients.

- Keep scheduled step 1 eval. After training and optimizer warmup, run eager eval, then captured eval. This allows us to reuse the memory, otherwise we will see memory jump during the warmup.
- Preserve memory reuse through `_CUDAGraphGradientState`.
- Prepare PP metadata outside capture and finish PP/FSDP eval cleanup.
- Wait for checkpoint staging before eval can update model buffers.
- Document tensor lifetimes in cuda_graph.md


## Memory usage

The current design is much simpler than the earlier version. The trainer no longer runs validation twice. The validator holds `capture_allowed=False` until every registered wrapper has warmed up, and its own second pass turns capture back on. I traced the call order: step 1 runs eager eval, step 2 captures eval on the first group and replays the rest, and step 3 captures training and the optimizer. This matches `CUDA_GRAPH.md`. The bit-exact PP+FSDP train/eval GPU test over 10 steps and 4 schedules covers the main risk well.

Below are the remaining concerns, most important first. I only read the code: I could not run Python, pytest or pre-commit in this sandbox, and I could not read the installed torch pipelining source.

---

#### 1. PP stage `has_backward` is not restored after eval prepare (question / possible silent bug)
`torchtitan/distributed/pipeline_parallel.py` `prepare_pipeline_schedule_for_cuda_graph`:
```python
schedule._has_backward = has_backward and not for_eval
try:
    for stage in stages:
        stage.has_backward = schedule._has_backward
    initialize(...)
finally:
    schedule._has_backward = has_backward   # stage.has_backward is NOT restored
```
After the eval `prepare_for_capture` runs, every stage keeps `has_backward=False` while the schedule says `True`.

- **With training capture:** the training `prepare_for_capture` runs before training capture and sets the stages back to `True`. This path is fine.
- **PP + eager training + `validator.enable_cuda_graphs=True`:** `Trainer.Config.__post_init__` allows this setup. Here the next eager `schedule.step()` depends on torch detecting the mode change and re-initializing the stages. If it does not, backward could be skipped or misconfigured with no error.

The GPU test `test_pp_fsdp_train_eval_shared_pool` always captures training, so this path is untested. Please either restore `stage.has_backward` in the `finally` block, or add a PP case with eager training and eval capture (or reject that combination).

#### 2. The single-flag request from the latest review is not addressed
@tianyu-l's approving review said: *"in this PR let's use one flag to determine both training and eval"*. The code still has a separate `validator.enable_cuda_graphs`. `CUDA_GRAPH.md:47-48` still justifies eval-only capture, and the `__post_init__` coupling in `trainer.py:91` still exists. One flag would also remove the eval-only path that causes concern #1, and the "eval-only capture" paragraphs in the doc. The other renames from that review are also still pending:
- `cuda_graph_per_accumulation_group` -> `cuda_graph_per_microbatch_group`. The docstring and doc now say "microbatch group", but the flag name does not.
- `_init_evaluate_fn` / `_evaluate_body` -> `_init_validate_fn` / `_validate_body`.
- `finish_fsdp_eval` -> a CUDA-graph-explicit name.

#### 3. Extra full validation passes at startup
`Validator.should_validate` returns `True` at every step until eval captures. That is at least 2 extra passes (steps 1 and 2) whatever `freq` is. The default is `steps=-1`, which consumes the whole validation dataset, so each pass can be expensive. Each pass also logs a validation metric at a step the user did not schedule. The doc mentions this, but a one-time `logger.info` would help users who see an unexpected eval at step 2. Alternatively, cap the warmup and capture passes at one microbatch group. One group is enough to warm up and capture, though it would mean not reporting a loss for those passes.

#### 4. `maybe_wait_for_staging` only runs when eval graphs are enabled (`trainer.py:503-508`)
The comment says *"Eval can update buffers that checkpoint staging reads"*. That applies to eager eval as well: any buffer written in forward, such as MoE load-balancing counters, races with async staging the same way. Either the wait is needed in both paths, or the comment should explain why capture specifically needs it.

#### 5. `finish_fsdp_eval` and PP `clear_runtime_states` now run on the eager path too
`validator.py:_evaluate_body` calls `finish_fsdp_eval` and `stage.clear_runtime_states()` even when eval graphs are off. Both use private APIs (`_get_fsdp_state`, `_modules_to_run_forward`, `_post_forward`, `_stage`/`_stages`). This is probably correct, since it frees memory the old code held. Still, it changes behavior on the existing eager validation path, which CLAUDE.md asks us to protect. Please confirm that the existing validation integration tests (e.g. `llama3_debugmodel_validation_tp2_cp2_pp2`) still give identical losses.

Two related points:
- The `isinstance(PipelineScheduleSingle) / PipelineScheduleMulti` stage-list logic now appears in both `validator.py` and `pipeline_parallel.py`. A small helper in `pipeline_parallel.py`, e.g. `_get_schedule_stages(schedule)`, would remove the duplication. That follows CLAUDE.md "Reuse over duplication".
- The fsdp.py comment *"Loss can call one grouped module after the root forward ends"* should name the concrete case: `lm_head` called from `ChunkedLossWrapper` with `skip_lm_head=True`, as @tianyu-l asked.

#### 6. Minor
- `training_engine.py:248/272/510`: `_forward_backward_cuda_graph_enabled` is only read on the line right after it is set. Make it a local variable or remove it.
- `validator.py:342`: the validator passes `max_num_documents` and `max_context_length=self.seq_len`, but not `**preprocess_inputs_kwargs` or `global_routing_token_counts` the way training does (`training_engine.py:675-678`). That is probably fine for eval. Just confirm that no model needs `global_routing_token_counts` to keep eval shapes static under capture.
- `cuda_graph.py`: renaming `_CUDAGraphManager` to the public `CUDAGraphManager` / `cuda_graph_manager`, and `run_eager_on_cuda_graph_stream` to private, are API changes. Check for out-of-tree users; `grep` found none in-tree.
- `CUDAGraphManager.teardown()` no longer has the `if not self._initialized: return` guard, and `TrainingEngine.close()` now always calls it. That is fine because teardown only touches Python state. Moving teardown after `checkpointer.close()` also keeps the GraphTrainer stash-free ordering correct. Nice.
- `validate()` now saves and restores each module's `training` flag instead of calling `model.train()`. This is an improvement, since modules that were already in eval mode stay that way. It is still a quiet behavior change worth one line in the PR description.

Response to Claude's review

  1. PP stage flags
  PyTorch sets stage.has_backward at each schedule.step() call. It also
  rebuilds metadata when the mode changes. We did not find a missing
  restoration bug, so we did not add another restoration step.

  2. Flags and names
  Validation now follows training's capture mode. We removed
  validator.enable_cuda_graphs and applied the requested method and
  microbatch-group names. Unsupported validation paths remain eager and warn.

  3. Startup validation
  Step 1 is already part of the normal validation schedule. Capture can add
  validation at step 2 if it is not scheduled. We kept full validation passes
  and their reported losses.

  4. Checkpoint staging
  We removed the validation staging wait. We found no validation writes to
  checkpointed model or optimizer tensors. MoE usage counters are training-
  only and nonpersistent. The existing wait before optimizer updates remains.

  5. Eager cleanup
  We kept cleanup in the shared validation body. We do not claim that eager
  numerical correctness requires it. The grouped-FSDP test now covers the
  actual chunked-loss sequence and subsequent training. Its eager reference
  does not call the cleanup helper.

  6. Other suggestions
  The engine's capture-mode field now supplies the validator's mode, so it is
  no longer a one-use field. Routing token counts serve training-only
  auxiliary losses in the inspected router.
