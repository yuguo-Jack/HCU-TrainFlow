# [rl] RL model defaults in every run: fp32 lm_head, frozen MoE expert bias and router gate

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5271) · state: closed · merged: True

## Original PR description

**TLDR:** `build_rl_model_configs` is called by every RL recipe. It now gives the trainer and generator model configs two defaults: fp32 lm_head logits, and frozen MoE routing (new `FreezeMoERoutingTransform`). A moving expert bias makes the trainer-vs-vLLM logprob gap grow: 0.053 -> 0.157 in 30 steps at lr=0 (Qwen3-30B-A3B with a bias, earlier main). With the bias frozen, the gap stays flat (0.054 -> 0.053). Today only the 3 Kimi K3 debug recipes move a bias, but an RL run on any model that ships one (DeepSeek-V3, Kimi K2.7) would. No recipe's lm_head changes; new recipes can no longer forget the fp32 head.

**Problem**
1. **The trainer moves the expert bias.** Before each optimizer step, a balancing hook updates every MoE layer's `expert_bias_E`. This happens in RL too.
2. **The bias changes which experts win.** It pushes experts close to the top-k cutoff. There, tiny trainer-vs-vLLM numeric differences pick different experts: 3.2% -> 9.0% of tokens per layer after 30 steps at lr=0, with bitwise-correct weight sync. The logprob gap triples.
3. **Who has a moving bias today:** Kimi K3 (quantile balancing), and any checkpoint that ships a bias (DeepSeek-V3, Kimi K2.7). Qwen3 MoE had one until the batch-wise aux loss replaced it.
4. **Balancing is not the RL objective.** 13 of the 16 MoE recipes add a batch-wise aux loss. Its gradient pushes the hidden states toward uniform expert load.
5. **fp32 logits are opt-in.** Each recipe has to remember `LMHeadFP32OutputConverter`.

**Solution**
1. `build_rl_model_configs` applies both defaults to both configs, each behind a flag: `fp32_lm_head=True` and `freeze_moe_routing=True`. Pass False to skip one.
2. `fp32_lm_head` appends `LMHeadFP32OutputConverter`, as the recipes did.
   - The recipes drop 14 converter lines, and 3 wrappers drop their append.
   - Muse Glimmer opts out: its soft-capped head can't be converted yet.
3. `FreezeMoERoutingTransform` sets three fields on every `MoE.Config`:
   - `freeze_expert_bias=True` (new field): the balancing hooks are not registered, so they skip their all-reduce;
   - `router.freeze_gate=True` (new field): the gate gets no gradient and no optimizer state;
   - `router.aux_loss=None`.
4. `LMHeadFP32OutputConverter` changes in two ways:
   - it skips a head that is already converted;
   - it raises on a Linear subclass (e.g. a soft-capped head) instead of dropping its forward.
5. Unchanged: pretraining and SFT, which don't call this function. The new MoE fields default to False.

**Results**
```text
What changes per RL recipe vs main: 43 of 45 recipes build on CPU (MXFP8 and dist_moe need packages),
trainer and generator configs
16 MoE recipes       freeze_expert_bias, router.freeze_gate: False -> True
13 of them           router.aux_loss: BatchWiseLoadBalanceLoss -> None
3 Kimi K3 recipes    quantile-balanced expert bias: moves -> frozen
all recipes          lm_head unchanged (already fp32; Muse Glimmer stays bf16)
```

```text

Real trainer + vLLM actors and weight sync, no RL loop: 30 x (generate -> score -> optimizer_step(lr=0) -> push/pull).

trainer-vs-vLLM logprob abs mean, step 0 -> 29
bias moves     0.053 -> 0.157
bias frozen    0.054 -> 0.053
```

You may ask:
- Why not `load_balance_coeff=None` in the recipes? It deletes a checkpoint's bias (DeepSeek-V3, Kimi K2.7). Kimi K3's quantile balancing keeps its bias anyway.
- Why freeze the gate rather than train it at a lower lr? With the bias frozen and the aux loss off, nothing balances a trainable gate. A lower gate lr is the alternative, left as a TODO in the code. There is no ablation yet.
- Why a transform, not code inside the RL helper? Any recipe can apply it, e.g. for MoE SFT: `transform_model_config_(model, [FreezeMoERoutingTransform()])`.

NOTE:
- GPU: a 3-step RL smoke on 2 H100s (Kimi K3 and Qwen3.5 MoE debug models, random init, forced non-zero advantages). The router gates and expert biases stay bitwise unchanged while the other weights move, and no balancing hook is registered. Not run: the GPU unit tests, a real-checkpoint run, and FSDP+TP+EP.
- The "bias frozen" run used an earlier version of this PR, which still ran the hook but skipped the update. The bias stays at its loaded value either way.
- A checkpoint saved with frozen routing can't resume with `freeze_moe_routing=False`, because the gates have no optimizer state. The other direction works.
- With the bias frozen, nothing resets the router's usage counts. Only the balancing hooks read them (TODO in the code).

**Test plan**
```bash
pytest tests/unit_tests/cpu/config/test_freeze_moe_routing.py tests/rl/unit_tests/cpu/test_model_defaults.py \
  tests/unit_tests/cpu/components/optim/test_optimizer_param_groups.py \
  tests/unit_tests/cpu/models/common/test_hi_mid_lo_linear.py \
  torchtitan/experiments/torchft/tests/test_torchft_optimizer.py
```
- `test_freeze_moe_routing.py` runs one AdamW step on each MoE family's debug flavor, frozen vs not. With the freeze:
  - the gate (and gpt-oss's gate bias) stays unchanged and has no optimizer state;
  - the expert bias stays unchanged;
  - every other parameter still moves.
- `test_model_defaults.py` builds every RL recipe and checks both model configs:
  - fp32 head, except Muse Glimmer;
  - every MoE layer frozen;
  - no aux loss.

  CI's Verifiers pass runs it too, because the first pass can't import the two Verifiers recipe modules. A second test checks that `freeze_moe_routing=False` leaves DeepSeek-V3's routing untouched.
