## Why
After a multi-turn rollout is repinned to another generator, that generator currently recomputes a prefix absent from its local GPU cache. Add an opt-in vLLM Mooncake Store integration so independent generators can reuse KV from shared CPU DRAM.

For example, generator A produces a turn under policy 5. Generator B can load its prompt and completed decode blocks for the next turn. After B loads policy 6, the same prompt misses policy-5 KV; A can still reuse policy 5. Individual weight updates never clear the shared pool.

## What changed
- Configure `MooncakeStoreConnector` through the existing `VLLMEngine.Config.extra_engine_args["kv_transfer_config"]`, using vLLM's native dict or config object. Validate a run/model namespace, `kv_both`, and decode-cache saving; enable stable block hashing. Deployment settings use upstream `MOONCAKE_CONFIG_PATH`.
- Pass the loaded policy version into the engine, salt shared KV by that version, and reject weight updates while requests are running. Configure the existing router with `hot_swap=False`.
- Keep the engine loop stepping asynchronous cache work after final outputs, including when no new requests arrive.
- Add deployment documentation and CPU/GPU regression coverage. Initial support is TP=DP=EP=1 per generator; scale independent replicas with `num_generators`.

Reference: [verl #6373](https://github.com/verl-project/verl/pull/6373) and [vLLM Store documentation](https://docs.vllm.ai/en/latest/features/mooncake_store_connector_usage/). Policy-version namespaces avoid a per-replica global Store reset during asynchronous generator updates.

## Testing
- Devgpu, two H100s, one local Master, two independent generator processes, real RDMA and CPU DRAM: **passed**. Cached tokens: cold 0; cross-generator prompt 496; next turn 544 (512-token prompt plus decode KV); changed weights 0; old-policy replica 496.
- `pytest tests/rl/unit_tests/cpu/test_generator.py tests/rl/unit_tests/cpu/test_engine_loop.py -q`: **101 passed, 1 skipped**. Includes native-config passthrough and validation, background progress beyond one engine-step burst, and loaded-version isolation.
- `pre-commit run --all-files`: non-type checks pass after formatting. Pyrefly reports 40 diagnostics, identical to clean base `ff96670a26c7079bc1b9049f5b6942adf35567c1`; no unrelated auto-edits retained.
- Repository `pr-review` skill used; two independent review lenses, fixes applied and correctness re-reviewed with no unresolved findings. The native-config follow-up was self-reviewed and retested on devgpu.

## Numerics / limitations
Cold vs. shared-cache greedy tokens match; sampled logprobs pass the smoke test tolerance. Trainer loss/grad-norm parity and end-to-end RL performance were not measured. The test is on one host; multi-node performance is unverified. Automatic NIC selection encountered retries before succeeding, so this run provides no bandwidth claim.

Tested with torch `2.15.0+cu132`, vLLM distribution `1.0.0.dev20261005+cu132`, and Mooncake `0.3.13.post1`. This host used DMA-BUF (`WITH_NVIDIA_PEERMEM=0`) and IPv4 worker addresses. Multi-rank scheduler synchronization, session-based Store eviction, the GPU session holder, batch-invariant/reset-on-load configurations, and standalone `generate.py` support remain outside this draft.
