# [moe] Reuse the parameter on HF load instead of re-stacking its expert views

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5587) · state: closed · merged: False

## Original PR description

## TLDR

Loading an HF checkpoint into an MoE model allocated every routed expert on the rank a second time: `from_hf` re-stacked the per-expert views that DCP had just filled in place. This PR returns those views as a strided view of the parameter instead, so the load needs no second copy. It applies to every MoE adapter built on `MoEStateDictAdapter` (DeepSeek-V3, Qwen3-MoE, GPT-OSS, Llama4, Kimi K3).

## Problem

1. `to_hf` exposes a grouped routed-expert parameter as views of it: W13 is unbound into W1/W3, then each is sliced per expert (`_get_local_experts_weights` for DTensors, `torch.split` otherwise).
2. The HF load fills those views in place, so the parameters already hold the loaded values.
3. `from_hf` then `torch.stack`s the experts back into a new tensor, and W1/W3 into another, and `load_state_dict` copies the result into the parameter: a full second copy of every routed expert on the rank, alive until the copy.
4. Loading the first 4 Kimi K3 layers into a one-GPU vLLM generator ran out of GPU memory at 267 GiB allocated, on an 18.4 GiB allocation (one layer's stacked experts).

## Solution

1. `stack_or_view(tensors, dim)` (in `models/base/state_dict_adapter.py`) returns a strided view of the shared storage when the tensors are equal-stride slices of one storage with the same dtype, shape and strides, which they are on the load path; otherwise it stacks. `copy_` of identical memory is a no-op, so `load_state_dict` does nothing for these keys.
2. DTensors are viewed through their local tensors and keep their mesh; shard placements at or after the new dimension move by one. `_StridedShard` is handled separately: it is not a `Shard` subclass in current PyTorch, and missing it rebuilt `(_StridedShard(1), Shard(1))` as `(_StridedShard(0), Shard(1))`, which `copy_` then redistributed to the wrong local size.
3. Used by `_concatenate_expert_weights_dtensor`, `_concatenate_expert_weights` and `_stack_logical_linears` (the W13 fusion).

Unchanged: tensors that are not slices of one storage (offline conversion, independent tensors) are stacked as before; results equal `torch.stack` in value and placement.

## Results

- 4-layer Kimi K3 generator on one GB300: the HF load OOMed before; with this change it loads and generates.
- Full Kimi K3 generator (DP 64 x EP 64, 64 GB300): the HF load finished in 120 s on every rank.

## Test plan

- `StackOrViewTest`: slices of one parameter come back as a view at both levels (experts, then W1/W3); independent tensors are stacked; a DTensor with `(_StridedShard(1), Shard(1))` on a fake 2 x 2 mesh keeps its placements and storage, and `copy_` back succeeds (fails without the `_StridedShard` handling).
- `test_roundtrip_preserves_mtp_expert_placements` (DeepSeek-V3, Shard(0) and Shard(2)) now also asserts the restored experts share the parameter's storage.
- New `test_hf_load_writes_routed_experts_in_place` (Kimi K3 debug model): routed experts restored by `from_hf` share storage with the parameters and hold the values written in place.
- `pytest` over the state-dict adapter tests, Kimi K3, MLA, GPT-OSS, DeepSeek-V3 and Muse Spark model tests: 76 passed, 3 xfailed (GB300 venv). The new checks fail with the call sites reverted to `torch.stack`.
- `pre-commit run --files` on the touched files: clean (Pyrefly skipped locally).
