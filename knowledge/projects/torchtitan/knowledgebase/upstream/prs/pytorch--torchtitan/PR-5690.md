# [rl] generator: let l2norm read GDN query/key as strided views

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5690) · state: closed · merged: True

## Original PR description

**TLDR:** On packed steps (prefill and mixed), the generator's GDN layer copied query and key out of the conv output before `l2norm`, which already reads strided head rows and writes compact ones. The two copies are gone. GDN layer, 2k-token steps: -5.3 to -8.6 us, bitwise.

```text
conv output, one row per token: [ q | k | v ]
main:     q -> copy -> l2norm        k -> copy -> l2norm        v -> copy
this PR:  q view -> l2norm           k view -> l2norm           v -> copy
          (l2norm reads strided rows and writes compact ones)
```

```python
# main
query = mixed_qkv[:, :local_key_dim].contiguous().view(1, num_tokens, heads, head_dim)
# this PR
query = mixed_qkv[:, :local_key_dim].view(1, num_tokens, heads, head_dim)
```

**Problem**
1. On packed steps, `VLLMInnerGDN._split_qkv` splits the conv output `[ q | k | v ]` into query, key and value.
2. It copied query and key into contiguous tensors before `l2norm`.
3. `l2norm` already reads strided head rows and writes compact ones, so the two copies cost 5.3-8.6 us per GDN layer on 2k-token steps for nothing.

**Solution**
1. `VLLMInnerGDN._split_qkv` returns query and key as views of the conv output; `l2norm` reads them in place.
2. Value is still copied: the chunk kernel would copy a strided value itself, and a view is slower there.
3. Unchanged: decode steps in normal mode (they never call `_split_qkv`), the trainer. Independent of the open GDN generator stack.

## Review and discussion

### reviews

- claude[bot] · APPROVED · 2026-10-29T10:10:41Z · [source](https://github.com/pytorch/torchtitan/pull/5690#pullrequestreview-5696018518)

**Verdict: Approve** -- a small, local perf change. It removes two copies that nothing needs, since `l2norm` reads strided query/key directly, and the batch-invariant parity test still covers the path.

**What this PR does.** In `VLLMInnerGDN._split_qkv`, query and key stay as views of the conv output; the old code copied them with `.contiguous()`. `_split_qkv` has one caller, `_forward_gdn`, and it passes both straight to `l2norm` (`gdn.py:323-324`), which writes compact outputs. So every downstream kernel (`paged_chunk_gdn`, `recurrent_gdn`, `chunk_kernel_options`) still gets contiguous query/key. Value is still copied.

**Example.**
```text
conv_output: [T, 2*Dk + Dv], row stride 2*Dk + Dv
main:    q = conv_output[:, :Dk].contiguous().view(1,T,H,K)   # copy T*Dk
         l2norm(q) -> compact q_norm
this PR: q = conv_output[:, :Dk].view(1,T,H,K)                # strides (_, 2*Dk+Dv, K, 1)
         l2norm(q) -> compact q_norm                           # same values, one fewer copy
```
The `.view()` is legal because each head's K elements are still contiguous within a row (last-dim stride 1, head stride K).

### Should consider
- `torchtitan/rl/generator/vllm/gdn.py:180-181` -- the docstring mentions only the chunk kernel, but batch-invariant mode sends value to `recurrent_gdn`. It also doesn't say that callers must apply `l2norm` before using query/key. Wording is in the inline comment.

<details><summary>Details</summary>

- Gate: the problem is real on `main` (two copies per packed step, measured at -5 to -9 us per layer on 2k-token steps). The fix sits in the right layer: the caller stops copying, and nothing changes in shared code or upstream. Net LoC is 0. No new knobs or tests, which is right, because `TestBitwiseParityQwen35DebugVarlen` already runs `_split_qkv` against the trainer's contiguous `l2norm` input.
- Normal-mode decode never reaches `_split_qkv`. Batch-invariant decode does, on `causal_conv1d_decode`'s output, and the same reasoning applies.
- Overlap: this doesn't depend on the open GDN stack (#5668-#5691). None of those PRs edit `_split_qkv` in a way this PR conflicts with, as far as the PR titles show.
- This is RL generator code, not core. A maintainer still needs to review.

</details>

Two small things in this docstring:

1. It only says "the chunk kernel", but `_forward_gdn` sends `value` to `recurrent_gdn` in batch-invariant mode (line 327), not to `paged_chunk_gdn`. Someone reading the docstring later would think that's the only consumer.
2. Returning strided `query`/`key` is only safe because the one caller runs `l2norm` on them before anything else uses them (lines 323-324). That's a contract on the caller, and the docstring is the place to write it down.

Suggested wording:

```suggestion
        Query and key are strided views; the caller must pass them through l2norm,
        which reads strided rows and writes compact ones. Value is copied because
        paged_chunk_gdn would otherwise copy a strided value itself, more slowly.
```
