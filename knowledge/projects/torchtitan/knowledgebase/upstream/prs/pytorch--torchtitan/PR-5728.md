## Agent details

**TLDR:** Every loss now returns its sum over loss tokens. `optim_step` divides all gradients once by N, the step's loss-token count summed over DP ranks. Callers no longer pass N, so they don't need the whole step before the first forward. This lets RL stream microbatches into a step (the PR stacked on this one).

**Numerics:** bitwise vs main for text pretraining, MoE auxiliary losses included. Configs whose N is not a power of two change by rounding. The largest change is SFT's grad norm, +0.16%, which moves it toward an fp32 reference.

```text
main:     N, R = all_reduce_dp(token counts of every microbatch)   # needs the whole step first
          forward_backward(groups, global_loss_token_counts=N, global_routing_token_counts=R)   # loss / N, aux / R
          optim_step()
this PR:  D = R / N   # MoE with an aux loss: the same all-reduce as main. RL: computed on the host.
          forward_backward(groups, aux_loss_denominators=D)   # losses are sums, aux / D; the engine counts N
          optim_step()   # N = all_reduce_dp(local count); grads /= max(N, 1); clip; step
```

**Problem**
1. On main, each loss divides by N, the step's loss-token count over every microbatch and DP rank. Each MoE auxiliary loss divides by R, the step's routed-token count.
2. So the caller needs every microbatch of the step before the first forward.
3. RL generates a step's samples over tens of seconds, and the trainer waits for the last one. On dapo_math (Qwen3-4B, 24 prompts x 16 samples), it then needs 20.6 s before it can send new weights. Streaming cuts this to 1.6 s (measured in the PR stacked on this one).

**Solution**
1. **Sum, then divide once:** `sum_i grad(S_i) / N == sum_i grad(S_i / N)`. FSDP and PP already sum gradients over ranks (`set_gradient_divide_factor(1.0)`, `scale_grads=False`), so 1/N is the only factor.
2. **Losses return sums:** `CrossEntropyLoss`, `MSELoss`, `ChunkedLossWrapper`, `MTPCrossEntropyLoss`, `DAPOLoss`, `AnswerTokenLoss`, and their `/mean` and `/frac` metrics.
3. **The engine counts and divides.** Preprocessing adds each microbatch's `loss_token_count`. `optim_step` sums the count over the `"dp"` mesh, then runs `torch._foreach_div_` on the gradients before clipping. A second `optim_step` without a `forward_backward` raises.
4. **Aux losses divide by D = R / N**, one fp32 value per routing depth. After the divide by N, microbatch m weighs R_m / R, as on main. The core and TorchFT trainers get D from `engine.step_aux_loss_denominators(groups)`: one int64 all-reduce, skipped for models without an aux loss. RL's controller computes D on the host.
5. **Unchanged:** the step order, the logged loss definitions (`global_avg_loss`, `global_max_loss`), and every FSDP, HSDP and PP reduction.

**What changes beyond rounding**
- **MTP depths** divide by the main objective's count, as the DeepSeek-V3 report divides every depth by T (eq. 24). Depth 1's weight on c4_test: 0.9995.
- **TorchFT, async quorum:** the replica hook now sums instead of averaging, and `optim_step` sums N over the same replicas. Otherwise each replica would divide the average by its own N, and the replicas would drift apart. So the loss is the token mean over replicas, not the mean of the replicas' means. Aux losses weigh each replica by its share of the loss tokens, not 1 / replicas.
- **A step with no loss tokens** steps with its aux gradients only, instead of failing the finite-loss check. AdamW still moves the weights. RL's DAPO loss already did this.

You may ask:
- Why not keep a second mode, with N passed before the step? Every caller would pick a mode, and the engine would need guards against mixing them. One path needs none.
- Why divide the gradients instead of scaling the last call's loss? Earlier calls' gradients are already accumulated. One divide before clipping covers all of them.
- Why not weigh aux losses by each microbatch's loss tokens (D = R_m / N_m, no collective)? It moves aux weight between microbatches, vs main: 1.7% on dapo-like steps, 7% SFT-like, 22% agentic with long masked prompts (median per step, CPU simulation with the RL batcher).
