# [graph_trainer] Overlap HybridEP and paging across combined PP graphs

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5542) · state: open · merged: False

## Original PR description

## AI-Generated Details

Prepared with Codex from the author's GraphPP multiplexing design. This is a
new change, not an update of the stale DualPipeV placeholder draft.

Requires the new PyTorch Interleaved1F1BCombined API:
https://github.com/pytorch/pytorch/pull/201439

Multiplex independent forward/backward graphs without EP token chunks. Tag
source ownership explicitly; reuse the eager stack's native request/input
validation, tensor/mutation dependency builder and paging resource ordering.
Ready native launches yield priority to complementary source work, with waits
behind independent compute. Preserve original positional input order as ABI
dependencies, every operation binding and all outputs.

The existing pipeline runtime owns receives, unshards, sends, gradients and
callbacks. Enabling the default-off flag selects non-blocking HybridEP async
operations without dividing per-microbatch capacity. DeepEP and full-graph
Inductor remain outside scope; existing regional attention compilation stays.

Join terminal stash inputs through the existing group_start operation before
backward reload, avoiding calibration/residency input-output aliasing without
clones or schema changes. Explicit whole-step capture scope allows fixed PP
prefetch/residency decisions, with the partial-stage guard retained.

197 affected cases passed (one skip); all three real native/SPMD/PP integration
tests passed, including both strict ten-step PP comparisons with full pipeline
F/B CUDA capture/replay. Twenty-step checkpoint comparisons matched all293
tensors, non-tensor state and loss/gradient-norm values exactly.

Actual pre/post graphs preserve input/output ABI, all operations and paging
queue order, unique requests/keepalives, final-consumer commits and full row
capacity12288. All-rank built-in GPU traces confirm EP/GEMM, page/GEMM and
page/EP intersections; kernel counts are unchanged by EP-only scheduling.

One clean four-GB300 run on the six-layer DeepSeek V3 debug model, hidden256/
routed-intermediate4096, global4096/micro512, DPshard2/TP1/EP2/PP2, two local
stages/four microbatches, capacity4, strict seed42: EP-only56.094 ->52.452ms
(1.0694x throughput). Same-save no-page versus paging:51.836/51.256ms and
4.297/3.988GiB on rank2; reserved savings1.96-7.59% across ranks. Async EP-only
reserve was1.738 ->2.070GiB, not doubled capacity. No OOMs/allocation retries.

Twenty steps, throughput11-20; separate built-in profiles9-10/19-20; page64,
CUDA page factor2.1, no CPU spill. This is local debug-model evidence, not a
production-model, H100/multi-host or globally optimal scheduling claim.
Warmup/cooldown and exhausted complementary work remain unpaired.

Both H100 source/release CI selectors include the real PP test; their YAML/
shell/collection checks passed, but H100 execution has not run. Changed-code
lint passed; the unrelated video typing baseline remains unchanged.
