# [dsv3][perf] MLA RoPE: rotate q's rope dims within the row, as int32 pairs

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5529) · state: open · merged: False

## Original PR description

**TLDR:** In the `mla_qk` region, q's rope dims are rotated within the contiguous q row, read and written as int32 pairs, instead of being split off as a strided view. DeepSeek-V3 and Kimi K2.5 q/k RoPE glue: -30% to -32% prefill, -34% to -36% train, at 89-99.6% of the bandwidth floor, bitwise with eager on GB300.

**Problem**
1. **q today.** `_apply_rope_to_q_and_k_pe` splits q `[T, H, 192]` into `q_nope [.., 128]` and `q_pe [.., 64]`, rotates `q_pe` with `k_pe`, and concatenates back.
2. **A strided view.** `q_pe` is a slice of each row, so the compiled rotation can't view it as int32 pairs: Inductor would copy it first. It reads the two halves with stride-2 loads instead.
3. **Cost.** The region runs at 59-69% of the bandwidth floor: DeepSeek-V3 prefill 64k 1380.0 us (floor 945.7). Helion's kernel in the same place is faster (1326.5 us).

**Solution**
1. **Rotate within the row.** `RoPE.rotate_tail(query, key, positions)` rotates the last `dim` dims of each `query` row and all of `key`, in one RoPE call.
2. **ComplexRoPE fast path.** Under compile, for a contiguous bf16 `query`, `_RotateTail` views the whole row as int32 pairs, rotates the last 32 words with `_RotatePairs.rotate` and concatenates them with q_nope's 64 untouched words. `key` (`k_pe`) uses the same cos/sin rows. The backward is the same rotation by the opposite angle.
3. **`_RotatePairs.rotate`** also accepts pairs already packed as int32 words, so both paths share one rotation formula.
4. **Call site.** `_apply_rope_to_q_and_k_pe` is one line: `return self.rope.rotate_tail(q, k_pe.unsqueeze(1), positions)`.
5. **Unchanged.** Eager, fp32 and non-contiguous q take the split / rotate / cat path, with q's tail and `k_pe` in one RoPE call as before. `k_pe` keeps its existing compiled path.

```text
before:  q [T,H,192] -> split -> q_pe (strided) -> rotate (stride-2 loads, int32 stores) -> cat
after:   q [T,H,192] -> view int32 [T,H,96] -> rotate the last 32 words, copy the first 64 -> view bf16
```

Size vs gain: +77/-14 non-test lines (`rope.py`, `attention.py`) for ~0.3% end to end. On its own that is under our bar; it's here because it closes the last gap to the Helion RoPE override (26-28% faster than Helion in this region), so the next PR can delete it without any model getting slower than Helion.

You may ask:
- Why not rotate `k_pe` the same way? Its output is its own `[T, 1, 64]` tensor, so its stores are already contiguous int32 pairs. The region gets it as a slice of the `[T, 576]` wkv_a output, so reading it as int32 without a copy would mean passing the whole row in. It is 0.3% (DeepSeek-V3) to 0.5% (Kimi) of the region's bytes.
- Why only MLA? Contiguous q/k already take the int32 path in `_RotatePairs.rotate`. DeepSeek-V4's indexer q and its inverse RoPE on `o` also slice the rope dims out of a buffer and could use `rotate_tail` (`o` needs inverse); follow-up, not measured.
- Why a method on `RoPE`, not a helper in `deepseek_v3/attention.py`? The fast path needs ComplexRoPE's cache gather and `_RotatePairs`; a helper there would reach into rope.py's private pieces. The base method keeps `self.rope.rotate_tail` valid for any RoPE (the field is a `RoPE.Config`).

NOTE:
- With `mla_qk` on (the default), the fast path no longer calls the Helion RoPE override's `forward`, so Helion stops reaching DeepSeek-V3 / Kimi from this PR. Its only user is the DeepSeek-V3 MTP integration test; the next PR deletes it.
- Other ComplexRoPE models: `_RotatePairs.rotate` traces the same ops for bf16 (contiguous and split), fp32 and fp16 inputs; the fake-PG goldens of DeepSeek-V3, GPT-OSS, Llama 3, Muse Glimmer and Qwen3 are unchanged (exported at the next PR).
- Reaches every recipe that enables `mla_qk`: DeepSeek-V3 and Kimi K2.x (on by default in the DeepSeek-V3 model config).
- Not tested: TP/SP, loss curve, H100. On A10G (CI) the compiled rotation is not bitwise with eager, so the test uses `assert_close`; on GB300 it is bitwise.

### Review: MLA RoPE int32 tail rotation

I read the full diff against `felipemello1/lcp/dsv3-2-dsv3-mla-qk-region` along with the code around it in `rope.py` and `deepseek_v3/attention.py`. I didn't run the GPU test because this runner has no GPU.

**Overall:** the change is small and correct, and well scoped. The forward and backward of `_RotateTail` match the math of `_RotatePairs`: the backward rotates by `-sin` over the same words, and q_nope's words pass through unchanged in both directions. All three callers of `_reshape_cache` still get one gather, shared between q and k. The fallback path does the same thing as the old `_apply_rope_to_q_and_k_pe`. I found no correctness bugs.

### Points worth addressing

1. **The bitwise test may break on other GPUs** (`test_mla_rope_compile.py:73`)
   - The PR body says bitwise equality is "not guaranteed by construction: Inductor may contract the real arithmetic into FMAs". The test still uses `torch.equal`, and it has only been confirmed on GB300.
   - If A10G CI (or a future Triton or Inductor version) contracts the arithmetic, the test fails even though nothing regressed.
   - The pre-existing compile path's comment says it is "within 1 bf16 ulp of eager".
   - Options:
     - Keep the strict check on q's untouched dims (`[..., :qk_nope_head_dim]` must be exact) and allow 1 ulp on the rotated dims.
     - Or keep it strict and add a comment saying it is intentionally strict, so someone who hits a failure knows it isn't a real bug.

2. **The test can't tell whether the int32 path actually ran.**
   - The `["mla_qk"]` and `["rope"]` runs both compare against eager.
   - If a future change makes `query.is_contiguous()` false at the call site, `rotate_tail` quietly takes the split path. The test still passes and the 30% gain is lost.
   - A cheap check, such as counting `_RotateTail.forward` calls or checking the Inductor output code for an `int32` view of the full row, would make the test catch that.

3. **`_RotatePairs.rotate` picks its behaviour from the input dtype** (`rope.py:379-404`)
   - When `x.dtype == torch.int32`, it reads x as packed bf16 pairs and returns int32. That is an implicit, dtype-driven contract on a function every ComplexRoPE model uses.
   - It's documented in the docstring and only `_RotateTail` uses it. Still, splitting it into a small `_rotate_words(pairs, cos, sin) -> int32` that `rotate` calls for the bf16-contiguous case would make the two entry points explicit.
   - The traced ops for existing callers would stay the same, so the goldens shouldn't move.

4. **The `cos`/`sin` extraction is duplicated** (`rope.py:348-349` vs `apply_rotary_emb`)
   - `ComplexRoPE.rotate_tail` repeats `unflatten(-1, (-1, 2))` → `cache[..., 0], cache[..., 1]`, which `apply_rotary_emb`'s compile branch already does.
   - This is minor, but a tiny `_cos_sin(cache)` helper would keep the two in sync if the cache layout changes.

5. **TP/SP is untested** (the PR body says so)
   - `_apply_rope_to_q_and_k_pe` receives `q` outside the `spmd.local()` block.
   - If `q` can arrive as a DTensor under TP, `x.view(torch.int32)` inside `_RotateTail` needs DTensor support for `aten.view.dtype`. The old split/cat path didn't need that.
   - If `spmd` tensors are always plain local tensors in this region, there's nothing to fix. A one-line comment saying so, or a TP run before landing, would settle it.

### Nits
- `RoPE.rotate_tail` (`rope.py:173`):
  - The docstring has no `Args:` section, unlike `forward`/`_reshape_cache` next to it.
  - It also doesn't say that `inverse` isn't supported. That matters if the DeepSeek-V4 `o` follow-up mentioned in the PR body ends up using it.
- `_RotateTail` docstring: "Needs an even storage offset" is correct. A non-contiguous or odd-offset `grad` would raise in `view(torch.int32)` rather than give wrong values. AOTAutograd makes tangents contiguous, so this is fine in practice.
- New lines stay within flake8's 120-character limit (`rope.py:343` and `rope.py:380` are the longest). I didn't run `pre-commit`.

### Summary
The approach is sound and the speedup is well documented. The things I'd want looked at before merge are (1) whether the strict bitwise test holds on A10G CI, and (2) a check that the fast path actually runs. Points 3–5 are cleanups or open questions, not blockers.
