# [rl] Finish the weight push before forward/backward

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5235) · state: open · merged: False

## Original PR description

**TLDR:** The weight push's reply waited behind `forward_backward`, so the generators' pull started one forward/backward late. The controller now awaits the push before the next `forward_backward`. With the thread-count fix this PR stacks on, the push takes 0.08 s at Qwen3-0.6B, so the wait is cheap.

**Problem**
1. **Background push.** After optimizer N, the controller starts push N -> pull N in the background. It sends forward/backward N+1 as soon as batch N+1 is ready.
2. **One event loop.** The trainer actor runs all endpoints on one asyncio loop, and `forward_backward` never yields it.
3. **Late reply.** If forward/backward N+1 starts while push N runs, push N replies only after forward/backward ends. Its put finished long before, in a worker thread.
4. **Late pull.** Pull N starts on that reply, ~3 s late at Qwen3-0.6B. The loop can then wait for it after optimizer N+1 (`timing/step/blocking_generator_pull_model_state_dict`).
5. **When.** The next batch is ready before the push ends. On the base branch: 3 of 5 steps, push 2.98-3.22 s (put 0.05-0.06 s), loop waits 0.29-0.89 s for the pull.

```text
base:
  controller: | start push N | send fwd/bwd N+1 ...................... | optim N+1 | wait for pull N ~~ |
  trainer:    | push N: stage, put | fwd/bwd N+1 ================ | reply N ^
  pull N:                                                      | pull N -------------------- |

this PR:
  controller: | start push N | wait for batch | await push N | send fwd/bwd N+1 ......... | optim N+1 |
  trainer:    | push N: stage, put, reply ^    | fwd/bwd N+1 ================ |
  pull N:                                      | pull N -------- |
```

**Solution**
1. The controller's existing `await push_task` moves from before `optim_step` to before `forward_backward`, after the wait for the batch.
2. The push still overlaps the wait for the batch, and the pull still overlaps forward/backward.
3. Unchanged: pull N-1 before push N, the trainer's push code, and the metric names. `timing/step/blocking_trainer_push_model_state_dict` is now the part of the push the batch wait didn't hide.

**Why the wait is cheap now.** What the trainer waits for when the batch is ready, with the thread fix:

```text
Qwen3-0.6B, 1 rank, real run (below)              0.08 s    (without the fix: 1.05 s)
microbench, 4 ranks pushing FSDP shards at once, max over ranks:
  Qwen3-0.6B                                      0.06 s    (without the fix: 7.3 s)
  Qwen3.5-9B                                      ~0.42 s   (GPU -> CPU copy estimated at 45 GB/s)
  Qwen3.5-35B-A3B                                 1.14 s    (0.38 s GPU -> CPU + 0.76 s put; without the fix: 13.8 s)
```

An earlier controller-side version of this PR got pushback in review because the push was long. It is now short.

**Results**

Numerics: unchanged; only when the push runs changes.

- In both runs with this PR, every push ended during the 0.7-41 s wait for the next batch, so the loop never waited for it. With a ready batch it would wait for the push: 0.08-0.10 s here.

You may ask:
- Why not run `forward_backward` on its own thread, as this PR's previous version did (kept on the `rl/trainer-compute-thread` branch of my fork)? It hid the push completely, but per-thread state had to follow the work to the new thread: the CUDA device, autograd's multithreading switch, and the profiler, which records CPU ops only on the thread that starts it. Staging was also safe only because the controller sends push N before forward/backward N+1. Awaiting a 0.08 s push needs none of that.
- Why await before forward/backward, not right after starting the push? Both wait the same when the batch is ready. Awaiting late also hides the push behind the batch wait, and keeps the push task, the pull's `after=` and the one-step-late push metric as they are.
- What does it cost? When the batch is ready, the loop waits for the whole push (0.08 s at 0.6B, ~1.1 s at 35B from the microbench). On main that time overlapped forward/backward, but the generators got the new weights one forward/backward later.

NOTE: the branch keeps the compute-thread commits and a revert commit, so earlier review comments keep their anchors. Against its base the diff is 3 files.

**Verdict:** I found no correctness hazard. This PR changes only *when the push replies*. It does not change *when the push runs* relative to forward/backward. The push is still sent and started before `forward_backward` N+1, as on main. So the concern in the earlier CHANGES_REQUESTED review applies to this PR's first version (await the push before fwd/bwd), not to the current diff. Below I check each invariant against the earlier reply, then list the extremal cases and a few small suggestions.

---

### 1. Invariants with the earlier reply

All trainer endpoints are `@concurrent_endpoint`, so the only ordering on the trainer comes from the controller's awaits plus the single asyncio loop. With this PR the controller can now see "push N done" while `forward_backward` N+1 still holds the trainer's loop. Here is what depends on that reply:

| Invariant | Who enforces it | Still holds? |
|---|---|---|
| The GPU->CPU copy of push N is done reading params before optimizer N+1 changes them | `staging_complete.synchronize()` runs before the put, which runs before `on_published` (`trainer.py:416-427`). The controller's `wait_prev_push()` comes before `optim_step` (`controller.py:1160`) | ✅ The reply still comes after the sync |
| Staging stream is ordered after optimizer N | `_mark_model_state_dict_ready_for_staging()` in `optim_step` | ✅ Unchanged |
| Pull N reads a complete policy N | `_generator_pull_and_release_buffer_slots` awaits `push_task`, which is `.call()` over **all** trainer ranks. Each rank replies only after its own put | ✅ The pull still starts after every rank's put |
| Push N+1 doesn't overwrite `_staging_state_dict` or the TorchStore key while pull N reads them | `wait_prev_pull()` comes before `start_async_push_pull` (`controller.py:1190-1195`) | ✅ Unchanged |
| Push N's worker thread is done with `_staging_state_dict` before push N+1 writes it | `on_published` is the last thing in the thread (`trainer.py:425-427`) | ✅ The comment there captures this. Please keep it last |
| Born-fresh rollouts | `release_active_groups` runs after the pull | ✅ Unchanged |

What's new is a short window in which **push N's coroutine is still alive on the trainer** (waiting for `to_thread` to resume after fwd/bwd N+1 ends) while the controller is already moving on. I traced what can run in that window:
- `optim_step` N+1: can't start before fwd/bwd N+1 returns (they share the loop). Push N has no work left after the thread except leaving the span. ✅
- `push_model_state_dict` N+1: needs pull N first. In theory it can land on the loop before push N's coroutine resumes (both are queued behind fwd/bwd). The only shared state is `_staging_state_dict`, and the thread is already done with it. Two `push_model_state_dict` spans may overlap in the trainer trace. This is cosmetic only (spans are per-task through contextvars).
- `model_state_dict` (the local inside push N) now stays alive until after fwd/bwd N+1. On main this was also the case in the slow case. No change in peak memory.

### 2. Extremal cases

1. **Push message runs after `forward_backward` N+1 on the trainer.** This can happen if both messages are queued and the trainer loop is busy. The push then starts after fwd/bwd, as could already happen on main, and simply overlaps less. It's slower but correct. In the real loop the `sync_log_step.call()` await separates the push send from the fwd/bwd send, so the push normally gets to `to_thread` first.
2. **Multi-rank, partial failure.** Say rank 0 replies and rank 1 calls `port.exception(...)`. `.call()` raises `ActorError` and the pull never starts, which matches main. The actor isn't marked failed in either case. ✅ The CPU test uses only 1 proc, so the mesh case (explicit port plus `.call()` collecting replies from N ranks) has no CPU coverage. It's worth a 2-proc variant if that's cheap.
3. **NaN `break` / `packed is None` / last step.** Each of these goes through `wait_inflight_push_pull()` before teardown. ✅
4. **Controller fails while a push thread is in flight** (e.g. `forward_backward` raises `ActorError`). The worker thread can't be cancelled, so it will still call `port.send` after the caller is gone. If that raises, the `except` calls `port.exception`, which will likely also raise. The coroutine then fails out of an explicit-port endpoint, which is an actor fault during teardown. Main has a similar teardown race (its implicit reply also fails). The difference is that the failure now starts in a non-actor thread. Low severity, but worth knowing.
5. **`asyncio.CancelledError` / `BaseException`.** These aren't caught by `except Exception`. With an explicit port, Monarch won't reply for you, so the caller gets no reply from that rank. This only matters at actor stop, but it's a change: before, Monarch's own handler replied.
6. **Undocumented Monarch contract.** `Port.send` from a non-actor thread works today. The CPU test pins this on 0.6.0/0.7.0, which is the right mitigation. Consider a one-line comment at the endpoint pointing at that test, so whoever upgrades Monarch knows what to look for.

### 3. Suggestions (non-blocking)

- **Don't reply twice.** After `on_published` succeeds, the endpoint still runs the span exit and the return. If anything there raises, the code calls `port.exception` on a port that already replied. Depending on Monarch, that either drops silently or raises an unhandled fault, and the fault would exit the controller even though the push succeeded. A small flag avoids this (`monarch_actors/trainer.py:73-77`):
  ```python
  published = False
  def on_published() -> None:
      nonlocal published
      port.send(None)
      published = True
  try:
      await super().push_model_state_dict(on_published=on_published)
  except Exception as e:
      if published:
          raise
      port.exception(ActorError(e))
  ```
  This is low probability. I'd still prefer it, because the failure mode (controller process exit) is out of proportion to the cause. [Fix this ->](https://claude.ai/code?q=In%20torchtitan%2Frl%2Fdistributed%2Fmonarch_actors%2Ftrainer.py%20push_model_state_dict%20(branch%20felipemello1%2Fweight-push%2F2-finish-push-before-forward-backward)%2C%20track%20whether%20port.send(None)%20already%20succeeded%20and%20only%20call%20port.exception(ActorError(e))%20if%20it%20did%20not%3B%20otherwise%20re-raise%2C%20to%20avoid%20double-replying%20on%20the%20response%20port.&repo=pytorch/torchtitan)
- **`on_published: ... | None = None` in `Trainer.push_model_state_dict`.** The only production caller is the actor endpoint, which always passes it. Under the CLAUDE.md rule against speculative defaults, consider making it required. You'd then have to update the existing direct-call unit test (`test_push_model_state_dict_stages_on_dedicated_cuda_stream`) to pass `lambda: None`. Optional.
- **The test depends on timing.** It relies on 0.1 s vs 2 s sleeps and on message order between two `ensure_future`s. The margin is large, so it's probably fine on CI. If it ever flakes, have `forward_backward` block on a `threading.Event` that the test sets after the push reply arrives, instead of sleeping.
- **Perf note for large models.** Pull N now actually overlaps fwd/bwd N+1. Your own data shows one fwd/bwd at 3.36 s vs ~3.02 s next to a 2.57 s pull. For large models where the pull's TCP/host-memory traffic shares a NIC or host with the trainer, that contention could grow. It would be good to call out in `WEIGHT_SYNC.md` that the overlap trades a small fwd/bwd slowdown for removing the pull wait.

### Summary
Under every ordering the controller can now produce, the safety invariants (no torn snapshot, no optimizer write during staging, no overwrite during a pull, born-fresh rollouts) still hold. They depend on `synchronize -> put -> reply` inside the thread and on the controller's existing `wait_prev_push` and `wait_prev_pull` awaits, and this PR leaves all of those alone. The remaining risks are in error and teardown paths (a possible double reply, `CancelledError`, a send after the caller is gone) and the undocumented cross-thread `Port.send`. None of them is a correctness issue on the happy path.

I didn't run the tests. I also couldn't inspect the installed torchmonarch source to confirm what `Port` does on a second send, so suggestion 1 is based on reasoning rather than on Monarch's code.

**Verdict:** I found no correctness issue, and your instinct is right on both points. The await sits before forward/backward because of *how the push replies*, not because of what the push has to finish. And most of what it waits for besides the GPU -> CPU copy is the TorchStore put. There is a simple way to wait for neither, and it is already on this branch (option 4a below).

<details><summary>Details</summary>

### 1. Correctness of the move
Push N is now awaited before forward/backward N+1. That is strictly earlier than before optimizer N+1, so every invariant from the base branch still holds:
- Staging finishes reading the params before optimizer N+1 writes them.
- Pull N-1 finishes before push N starts.
- Pull N starts only after every rank's put, because `push_model_state_dict.call()` (`controller.py:1321`) collects a reply from all ranks.

I also checked the exit and error paths:
- A failing push now raises before forward/backward instead of before the optimizer step.
- `packed is None`, the NaN `break`, and the final `await push_task` all still work. Awaiting a finished task twice is fine.

The tests were updated to match, and no `.md` file or test still claims the push overlaps forward/backward.

### 2. Why before forward/backward and not before the optimizer step
For correctness, only the base branch's await before the optimizer step is needed. The await moved because pull N starts on push N's **reply**. That reply is sent from the trainer actor's event loop (`actors/monarch/trainer.py:68-70`), and `forward_backward` holds that loop. So if forward/backward N+1 starts before push N's put returns, the pull starts late again, wherever the await sits.

As long as the reply goes through the event loop, this PR's placement is the only one that keeps the pull early. Putting it after the wait for the batch is the best version of that placement.

Splitting the push into two endpoints (stage, then put) does not help on its own. The put endpoint's reply would wait behind forward/backward in the same way.

### 3. What the await covers today
These are the steps of `Trainer.push_model_state_dict` (`trainer.py:415-477`):

| Step | Runs on | Needed before optimizer N+1? | Needed before pull N? |
|---|---|---|---|
| `model.state_dict()` and `_stage_model_state_dict`: queue the per-tensor `copy_` into pinned buffers on the staging stream, casting to the generator dtype (the cast runs by default: `training.dtype` is `float32`, `generator.model_dtype` is `bfloat16`) | actor loop (queueing) + GPU | yes | yes |
| `staging_complete.synchronize()` | worker thread | yes | yes |
| `ts.put_state_dict(...)`: a second CPU copy, from the pinned snapshot into TorchStore's StorageVolume (see the TODO at `trainer.py:432`), plus the TCP fallback transport | worker thread | **no** | yes |
| reply | actor loop | -- | yes |

Your microbenchmark of Qwen3.5-35B-A3B gives 0.38 s for GPU -> CPU and 0.76 s for the put. So about two thirds of the wait is the put. That is the "push does more than push" you remembered; the GPU -> CPU copy is the smaller part.

### 4. Ways to wait only for GPU -> CPU
**a) Reply from the worker thread (recommended).** This is commits 3fd5850 and 6f4f4f9 on this branch. tianyu-l approved that version, and it already addresses the earlier review's suggestions. The put's completion reaches the controller without going through the event loop, so:
- You can keep main's await before the optimizer step, and nothing blocks before forward/backward.
- Staging and the put overlap forward/backward, which is what #5107 intended and what tushar00jain asked for.
- The pull still starts right after the put.

The cost is an explicit response port plus an `on_published` callback (about 20 lines). It also relies on Monarch accepting `Port.send` from a non-actor thread, which the CPU test pins.

The PR's "You may ask" section explains why you dropped the compute thread, but not why you dropped this version. It is the simplest option that satisfies both reviewers. I'd reconsider it, or at least say in the description why it was dropped.

**b) TorchStore-owned staging.** This is the TODO at `trainer.py:432`. If the GPU -> CPU copy wrote straight into the StorageVolume buffer, the put would shrink to publishing metadata, and this PR's await would be roughly the GPU -> CPU time. It needs a new TorchStore API, so it is longer term. It also combines with (a).

**c) Quantization later.** Run it on the GPU, on the staging stream, in `_stage_model_state_dict`'s per-tensor loop, as the dtype cast is today. It then counts as part of the GPU -> CPU step and shrinks the bytes for both the copy and the put. If quantization instead runs on the CPU in the worker thread, it adds to this PR's wait. Under (a) it would also compete for the GIL with forward/backward's Python dispatch.

### 5. What this PR costs as it is
It only costs time when batch N+1 is ready before push N ends, that is, when the trainer is the bottleneck. In that case each step waits for the whole push:
- about 0.08 s at Qwen3-0.6B
- about 1.1 s at Qwen3.5-35B-A3B (from your microbenchmark)

For large models where the trainer is the bottleneck, that adds straight to step time. On main that time was hidden behind forward/backward, but the pull started one forward/backward late. `timing/step/blocking_trainer_push_model_state_dict` is the right metric to watch.

### 6. Minor
- `_mark_model_state_dict_ready_for_staging` still records the staging dependency at optimizer time. With this PR, no forward/backward N+1 kernels can be queued before stage N, so the reason in the removed comment no longer applies. I'd keep the call anyway: it is harmless, and (a) needs it again. If you go with (a), restore the sentence you removed.
- tushar00jain's request for changes was against this ordering (push before forward/backward), so the PR still needs his re-review.

I did not run the tests or anything on a GPU; this is from reading the code. There was no `pr-review` skill in this environment, so I posted the review in this comment.
