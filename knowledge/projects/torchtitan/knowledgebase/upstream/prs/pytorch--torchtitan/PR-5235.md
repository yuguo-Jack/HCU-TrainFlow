# [rl] Reply to the weight push from its worker thread, so the pull overlaps forward/backward (1/2)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5235) · state: open · merged: False

## Original PR description

**TLDR:** The weight push now replies as soon as TorchStore has the weights, not after the next forward/backward. The generator pull then overlaps forward/backward. On a local Qwen3-0.6B run, the loop's wait for the pull drops from 0.40-1.00 s to < 0.1 ms on the 3 of 19 steps that waited (0.5% of loop time; the run is generation-bound). (1/2; 2/2 renames the timing keys.)

**Problem**
1. **Background sync.** After optimizer N, the controller starts push N -> pull N in the background (`start_async_push_pull`). When batch N+1 arrives, it sends `forward_backward` N+1 to the same trainer actor.
2. **The data moves in the background.** The push queues its GPU -> CPU copy on a side CUDA stream. A worker thread waits for it and runs the TorchStore put, during forward/backward N+1.
3. **The reply waits for the loop.** The actor runs all endpoints on one asyncio loop, and `forward_backward` holds it until it returns. The push replied from that loop, so only after forward/backward N+1 ended.
4. **The pull starts late.** It starts on that reply, so it can still be running when optimizer N+1 ends. The loop then waits for it (`timing/step/blocking_generator_pull_model_state_dict`).
5. **When.** Whenever batch N+1 arrives before push N's put finishes: 3 of 19 steps below. The loop waited 0.40-1.00 s on each.

```text
main, batch N+1 arrives before push N's put finishes:
  loop:    | forward/backward N+1 ============= | optimizer N+1 | wait for pull N ~~~ |
  push N:  | copy + put, in a thread |    reply ^
  pull N:                                       | pull N ---------------------------- |

this PR:
  loop:    | forward/backward N+1 ============= | optimizer N+1 |
  push N:  | copy + put, in a thread ^ reply
  pull N:                            | pull N --------- |
```

**Solution**
1. **Reply from the thread.** `Trainer.push_model_state_dict` takes an `on_published` callback and calls it in the worker thread right after the put.
2. **How.** The actor's `push_model_state_dict` (in `_TrainerActorEndpoints`) becomes `@concurrent_endpoint(explicit_response_port=True)` and passes `on_published=lambda: port.send(None)`. `Trainer` sees only the callback, so it stays independent of Monarch.
3. **Errors.** Monarch doesn't forward errors from explicit-port endpoints: the actor fails, and Monarch's unhandled-fault hook exits the controller process. The endpoint sends them with `port.exception(ActorError(e))`, so the controller gets an `ActorError`, as on main.
4. **Unchanged.** The loop still awaits push N before optimizer N+1 changes the weights, and pull N before push N+1 overwrites them in TorchStore. New rollouts still start only after the generators hold the new weights.
5. **Side effect.** `timing/weight_sync/trainer_push_model_state_dict` becomes the push's own time. On main it could include the rest of forward/backward N+1.

**Results**

  pulls that started during forward/backward                0 -> 3

  mean of per-step ratios                                   3.0% -> 0.0%

timing/step/forward_backward                                median 3.00 s -> 3.01 s

correctness
trainer/policy_version                                      1..20 in both; all 21 pulls (setup + 1 per step) completed
rollout/max_policy_version                                  trails the trainer by 1-3 -> 1-2 versions

- The 3 overlapped forward/backwards took 3.05, 3.02 and 3.36 s. The 3.36 s one ran beside a 2.57 s pull.
- Loop totals differ (457 vs 369 s) from generation noise (median batch wait 23 s vs 17 s), not this PR.
- Max policy age: 16 here vs 9 on main (a group from version 0 finished at step 17). Ages come from generation time; neither run caps them.
- Both runs: an earlier main with torchmonarch 0.6.0, plus an early draft of 2/2 (renames only; none of the values above change). Keys here use main's names.

You may ask:
- Why not await the push before forward/backward (this PR's first version)? The loop would wait for the rest of the push instead of the pull, and the push is longer (median push 1.21 s vs pull 0.79 s on this PR's run).
- Why not run `forward_backward` in a thread? Same payoff, but compute would leave the actor's thread, and per-thread CUDA/NCCL state (device, stream) would need review. This PR changes one endpoint.
- Why can a non-actor thread reply? A Monarch `Port` keeps its actor instance, and `send` pickles under the GIL, so any thread can call it.

NOTE: that last point is Monarch behavior, not a documented contract. The CPU test checks it on torchmonarch 0.7.0 (main's minimum) and 0.6.0.
NOTE: the trainer's `push_model_state_dict` trace span still ends after forward/backward. The controller's `trainer_push_model_state_dict` span ends at the reply.

**Test plan**

  - A failing push raises `ActorError` in the caller. Without the forwarding, the fault ends the pytest process.

### Review of #5235: replying to the weight push from its worker thread

**Verdict:** I found no correctness hazard. This PR changes only *when the push replies*. It does not change *when the push runs* relative to forward/backward. The push is still sent and started before `forward_backward` N+1, as on main. So the concern in the earlier CHANGES_REQUESTED review applies to this PR's first version (await the push before fwd/bwd), not to the current diff. Below I check each invariant against the earlier reply, then list the extremal cases and a few small suggestions.

---

### 1. Invariants with the earlier reply

All trainer endpoints are `@concurrent_endpoint`, so the only ordering on the trainer comes from the controller's awaits plus the single asyncio loop. With this PR the controller can now see "push N done" while `forward_backward` N+1 still holds the trainer's loop. Here is what depends on that reply:

| Invariant | Who enforces it | Still holds? |
|---|---|---|
| The GPU->CPU copy of push N is done reading params before optimizer N+1 changes them | `staging_complete.synchronize()` runs before the put, which runs before `on_published` (`trainer.py:416-427`). The controller's `wait_prev_push()` comes before `optim_step` (`controller.py:1160`) | ✅ The reply still comes after the sync |
| Staging stream is ordered after optimizer N | `_mark_model_state_dict_ready_for_staging()` in `optim_step` | ✅ Unchanged |
| Pull N reads a complete policy N | `_generator_pull_and_release_buffer_slots` awaits `push_task`, which is `.call()` over **all** trainer ranks. Each rank replies only after its own put | ✅ The pull still starts after every rank's put |
| Push N+1 doesn't overwrite `_staging_state_dict` or the TorchStore key while pull N reads them | `wait_prev_pull()` comes before `start_async_push_pull` (`controller.py:1190-1195`) | ✅ Unchanged |
| Push N's worker thread is done with `_staging_state_dict` before push N+1 writes it | `on_published` is the last thing in the thread (`trainer.py:425-427`) | ✅ The comment there captures this. Please keep it last |
| Born-fresh rollouts | `release_active_groups` runs after the pull | ✅ Unchanged |

What's new is a short window in which **push N's coroutine is still alive on the trainer** (waiting for `to_thread` to resume after fwd/bwd N+1 ends) while the controller is already moving on. I traced what can run in that window:
- `optim_step` N+1: can't start before fwd/bwd N+1 returns (they share the loop). Push N has no work left after the thread except leaving the span. ✅
- `push_model_state_dict` N+1: needs pull N first. In theory it can land on the loop before push N's coroutine resumes (both are queued behind fwd/bwd). The only shared state is `_staging_state_dict`, and the thread is already done with it. Two `push_model_state_dict` spans may overlap in the trainer trace. This is cosmetic only (spans are per-task through contextvars).
- `model_state_dict` (the local inside push N) now stays alive until after fwd/bwd N+1. On main this was also the case in the slow case. No change in peak memory.

### 2. Extremal cases

1. **Push message runs after `forward_backward` N+1 on the trainer.** This can happen if both messages are queued and the trainer loop is busy. The push then starts after fwd/bwd, as could already happen on main, and simply overlaps less. It's slower but correct. In the real loop the `sync_log_step.call()` await separates the push send from the fwd/bwd send, so the push normally gets to `to_thread` first.
2. **Multi-rank, partial failure.** Say rank 0 replies and rank 1 calls `port.exception(...)`. `.call()` raises `ActorError` and the pull never starts, which matches main. The actor isn't marked failed in either case. ✅ The CPU test uses only 1 proc, so the mesh case (explicit port plus `.call()` collecting replies from N ranks) has no CPU coverage. It's worth a 2-proc variant if that's cheap.
3. **NaN `break` / `packed is None` / last step.** Each of these goes through `wait_inflight_push_pull()` before teardown. ✅
4. **Controller fails while a push thread is in flight** (e.g. `forward_backward` raises `ActorError`). The worker thread can't be cancelled, so it will still call `port.send` after the caller is gone. If that raises, the `except` calls `port.exception`, which will likely also raise. The coroutine then fails out of an explicit-port endpoint, which is an actor fault during teardown. Main has a similar teardown race (its implicit reply also fails). The difference is that the failure now starts in a non-actor thread. Low severity, but worth knowing.
5. **`asyncio.CancelledError` / `BaseException`.** These aren't caught by `except Exception`. With an explicit port, Monarch won't reply for you, so the caller gets no reply from that rank. This only matters at actor stop, but it's a change: before, Monarch's own handler replied.
6. **Undocumented Monarch contract.** `Port.send` from a non-actor thread works today. The CPU test pins this on 0.6.0/0.7.0, which is the right mitigation. Consider a one-line comment at the endpoint pointing at that test, so whoever upgrades Monarch knows what to look for.

### 3. Suggestions (non-blocking)

- **Don't reply twice.** After `on_published` succeeds, the endpoint still runs the span exit and the return. If anything there raises, the code calls `port.exception` on a port that already replied. Depending on Monarch, that either drops silently or raises an unhandled fault, and the fault would exit the controller even though the push succeeded. A small flag avoids this (`monarch_actors/trainer.py:73-77`):
  ```python
  published = False
  def on_published() -> None:
      nonlocal published
      port.send(None)
      published = True
  try:
      await super().push_model_state_dict(on_published=on_published)
  except Exception as e:
      if published:
          raise
      port.exception(ActorError(e))
  ```
  This is low probability. I'd still prefer it, because the failure mode (controller process exit) is out of proportion to the cause. [Fix this ->](https://claude.ai/code?q=In%20torchtitan%2Frl%2Fdistributed%2Fmonarch_actors%2Ftrainer.py%20push_model_state_dict%20(branch%20felipemello1%2Fweight-push%2F2-finish-push-before-forward-backward)%2C%20track%20whether%20port.send(None)%20already%20succeeded%20and%20only%20call%20port.exception(ActorError(e))%20if%20it%20did%20not%3B%20otherwise%20re-raise%2C%20to%20avoid%20double-replying%20on%20the%20response%20port.&repo=pytorch/torchtitan)
- **`on_published: ... | None = None` in `Trainer.push_model_state_dict`.** The only production caller is the actor endpoint, which always passes it. Under the CLAUDE.md rule against speculative defaults, consider making it required. You'd then have to update the existing direct-call unit test (`test_push_model_state_dict_stages_on_dedicated_cuda_stream`) to pass `lambda: None`. Optional.
- **The test depends on timing.** It relies on 0.1 s vs 2 s sleeps and on message order between two `ensure_future`s. The margin is large, so it's probably fine on CI. If it ever flakes, have `forward_backward` block on a `threading.Event` that the test sets after the push reply arrives, instead of sleeping.
- **Perf note for large models.** Pull N now actually overlaps fwd/bwd N+1. Your own data shows one fwd/bwd at 3.36 s vs ~3.02 s next to a 2.57 s pull. For large models where the pull's TCP/host-memory traffic shares a NIC or host with the trainer, that contention could grow. It would be good to call out in `WEIGHT_SYNC.md` that the overlap trades a small fwd/bwd slowdown for removing the pull wait.

### Summary
Under every ordering the controller can now produce, the safety invariants (no torn snapshot, no optimizer write during staging, no overwrite during a pull, born-fresh rollouts) still hold. They depend on `synchronize -> put -> reply` inside the thread and on the controller's existing `wait_prev_push` and `wait_prev_pull` awaits, and this PR leaves all of those alone. The remaining risks are in error and teardown paths (a possible double reply, `CancelledError`, a send after the caller is gone) and the undocumented cross-thread `Port.send`. None of them is a correctness issue on the happy path.

I didn't run the tests. I also couldn't inspect the installed torchmonarch source to confirm what `Port` does on a second send, so suggestion 1 is based on reasoning rather than on Monarch's code.
