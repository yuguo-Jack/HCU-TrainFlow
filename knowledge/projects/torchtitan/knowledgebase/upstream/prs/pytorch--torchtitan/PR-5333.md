# [DeepSeek V3] Report LM and MTP pipeline metrics

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5333) · state: open · merged: False

## Original PR description

## Agent details (AI-generated)

Preserve the weighted objective while exporting detached LM, unweighted mean
MTP and combined metrics through plain dictionary pipeline loss results.
Reuse upstream per-microbatch loss kwargs and nested group/microbatch metrics;
do not introduce a duplicate mutable group aggregator or public result class.

Depend on PyTorch #200644's dictionary-result and optional loss_results API.
Require one detached export per loss-owning microbatch and consistent names,
then aggregate normalized contributions over microbatches and loss-owning
DP/CP ranks. Validation selects the LM term for every context row, preserving
the earlier independent batch and sequential projection/release behavior.
GraphTrainer integration remains downstream work.

- claude[bot] · comment · 2026-11-01T06:03:44Z · [source](https://github.com/pytorch/torchtitan/pull/5333#discussion_r4434593963)

File: `torchtitan/distributed/pipeline_parallel.py` · line 463

To answer @tianyu-l's question: this solves an already-solved problem a different way. It isn't a general improvement.

On the base branch, `_scalar_loss_fn` already sends per-microbatch metrics out of the PP schedule through the `loss_metrics` loss kwarg, and `test_schedule_loss_replaces_loss_metrics` covers it. Once `MTPLoss` returns non-empty metrics, those metrics already reach `ForwardBackwardResult.loss_metrics` under PP with no change here or in `training_engine.py`.

This change swaps that working mechanism for pytorch/pytorch#200644. That PR is still **OPEN** (not merged). The switch is also a hard dependency: `training_engine.py:893` and `validator.py:344` raise `RuntimeError` when `loss_results` is missing, and `pp_schedule.step/eval(loss_results=...)` fails with a `TypeError` on any PyTorch build without that kwarg. So every PP run in this stack breaks until #200644 lands and ships in the nightly CI uses.

Suggestion: keep the existing `loss_metrics` kwarg path and limit this PR to what is actually new: `MTPLoss` returning the named terms, trainer logging, and the validation choice. Migrating to the upstream dict API can be a separate follow-up once #200644 has landed, and it should remove the old mechanism in that same follow-up.

- claude[bot] · comment · 2026-11-01T06:03:49Z · [source](https://github.com/pytorch/torchtitan/pull/5333#discussion_r4434594147)

File: `torchtitan/trainer.py` · line 488

This reducer sums every metric over microbatches and the loss mesh, whatever its suffix. The repo already has a suffix contract (`/mean`, `_mean`, `/frac`, `_frac` are additive; `/max` and `/min` are not), enforced in `ChunkedLossWrapper._combine_chunk_metrics` (`components/loss.py:801`) and `rl/controller/metrics.py:combine_microbatch_metrics`. If any loss used with the core `Trainer` returns a `/max` metric, this code silently logs the sum of maxima. It also strips only `_mean`, so `/frac` and other keys pass through under inconsistent names.

Please reuse one shared suffix-aware reducer here instead of adding a third variant that disagrees with the other two. For example, move the microbatch combine and the sum/max loss-mesh reduction from the RL trainer into a shared location and call it from both trainers.

Smaller points:
- `loss_mesh` is already computed at line 423, so line 483 can reuse it instead of calling `get_optional_mesh("loss")` again.
- No unit test covers this block (accumulation across groups, DP/CP reduction, name stripping). The new `test_trainer.py` test only covers the engine-side name check.

File: `torchtitan/models/deepseek_v3/mtp.py` · line 638

Two points:

1. `combined_loss_mean` is `loss.detach()`. Accumulated over microbatches and summed over the loss mesh, that is exactly `global_avg_loss`, which `metrics_processor.log` already reports as `loss_metrics/global_avg_loss`. It is a duplicate series, so drop it.
2. The `len(depth_losses) == 1` special case isn't needed, because `torch.stack(depth_losses).mean()` already returns the single element.

```suggestion
        return loss, {
            "lm_loss_mean": main_loss.detach(),
            "mtp_loss_mean": torch.stack(depth_losses).mean().detach(),
        }
```

- claude[bot] · comment · 2026-11-01T06:03:58Z · [source](https://github.com/pytorch/torchtitan/pull/5333#discussion_r4434594399)

File: `torchtitan/components/validator.py` · line 325

This adds two things to the core validator that shouldn't live here:

1. **A DeepSeek-V3-specific key.** `metrics.get("lm_loss_mean", loss)` (here and at line 369) makes the generic validator aware of one model's metric name. The core rule says not to modify shared infrastructure for a single model's needs. A cleaner design keeps the choice in the loss. For example, `MTPLoss` could return only the LM term in eval/validation mode (the validator already flips `model.eval()`). Alternatively, the recipe could build a validation `loss_fn` that scores `pred[0]` only. Either way the validator stays model-agnostic.
2. **A check that exists only for an experiment.** `isinstance(self.pp_schedule, _PipelineSchedule)` exists only so GraphTrainer's custom runtime can skip `loss_results`. It also means the same MTP model reports `validation_metrics/loss` as the LM term under `Trainer` but as LM + `mtp_scale` * MTP under GraphTrainer, with no warning. If you keep the current approach, emit a warning or reject MTP with a non-native schedule, so the numbers aren't silently incomparable. If you go with (1), this branch disappears.

Also, this changes the reported validation loss for existing MTP runs (it drops the MTP term). That is reasonable, but please call it out in the PR description.
