# [rl] verifiers: route each generation request to its own group's GenerateFn

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5238) · state: closed · merged: False

## Original PR description

**TLDR:** The Verifiers generation server now calls the `GenerateFn` of each request's own rollout group, not the one the last-started group set. No run on main hits the old behavior today: validation runs only before and after training. Periodic or overlapped validation would log validation generator metrics under `generator/`, and the reverse.

**Problem**
1. `VerifiersRollouter.run_group_rollouts` called `GenerationServer.set_generate_fn(generate_fn)` for every group, and the server kept one function.
2. The controller passes training groups a function that logs under `generator/`, and validation groups one that logs under `validation_generator/`.
3. When groups of both kinds run at once, every request uses the function of whichever group started last.
4. That happens with periodic validation (training groups keep generating while the trainer waits) and with overlapped validation.
5. Routing and rollouts don't change, only the metric labels. But a validation pass logged at a training step puts its mislabeled `generator/*` values in that step's row.

**Solution**
1. `GenerationServer.generate_fns` maps group id to `GenerateFn`.
2. `run_group_rollouts` sets its group's entry before the rollouts and removes it in a `finally`, so a rollout that raises doesn't leave it behind.
3. A request whose group has no entry gets a 503 instead of another group's function.
4. Unchanged: group ids. They are already unique among groups that run at once (training >= 0, validation negative).

NOTE:
- Landing order: the "abort a generation when its caller gives up" PR adds a `test_verifiers.py` test that calls `server.set_generate_fn`, which this PR deletes. Whichever lands second switches it to `server.generate_fns[1] = generate_fn`.
- Best landed after "Verifiers: release each finished rollout's routing session": there `gather` waits for every sibling, so a failing rollout no longer pops its group's entry while siblings still generate (they get a 503 here).

**Test plan**
```
pytest tests/rl/unit_tests/cpu/test_verifiers.py
```
- `test_generation_server_uses_each_groups_generate_fn`: a validation group's second request still uses its own function after a training group registers one; an unknown group gets a 503.
- `test_rollouter_registers_the_groups_generate_fn_while_it_runs`: the entry lives while the group's rollouts run, even as another group starts, and is gone after, also when a rollout raises.
