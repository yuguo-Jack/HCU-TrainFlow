# [profiler] add opt-in Cuspy profiling backend

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5525) · state: open · merged: False

## Original PR description

Stack from [ghstack](https://github.com/ezyang/ghstack/tree/0.15.0) (oldest at bottom):
* #5527
* #5526
* #5136
* __->__ #5525

Profiler.Config.cuspy switches CUDA activity collection from Kineto to Cuspy
(PM sampling, environment counters, sync events, graph dependencies, event-node
ids, and optional Perfetto protobuf output). Profiler startup raises a
ValueError if torch or libcupti lacks Cuspy support.

With CUDA graphs on, kernels replayed from graphs do not carry annotations in
the Cuspy trace yet; the next PR in the stack captures graphs with a CUPTI
annotation config to fix that.

### Review: [profiler] add opt-in Cuspy profiling backend

- [x] Read the PR diff (`origin/gh/pianpwk/115/base...HEAD`)
- [x] Read `torchtitan/observability/profiler.py`, the tests and the docs
- [x] Post review

Overall the PR is clean. It's opt-in, and with `cuspy=None` the Kineto path behaves exactly as before: the activities and annotation export are the same, and XPU and Neuron are untouched. The capability probe avoids taking a CUPTI subscription, which is a careful touch. The tests cover the error path, the file naming and the real torch config build. My comments below are mostly small.

#### Worth addressing

1. **CUDA graph annotations are dropped without a warning** (`profiler.py:442-443`). With `cuspy` set, the handler calls `prof.export_chrome_trace(output_file)` and never checks `get_cuda_graph_annotations()`. The PR description says the next PR in the stack fixes this. Until then, someone running Cuspy with CUDA graphs gets a trace without kernel annotations and no explanation. CLAUDE.md asks for a warning whenever a code path silently skips something, and the Kineto branch already logs one in the same situation. A one-time `logger.warning` would match, e.g. "Cuspy traces do not yet carry CUDA graph kernel annotations" whenever `get_cuda_graph_annotations()` returns something. It can be removed in the follow-up PR.
   [Fix this →](https://claude.ai/code?q=In%20torchtitan%2Fobservability%2Fprofiler.py%20trace_handler%20(branch%20gh%2Fpianpwk%2F115%2Fhead)%2C%20when%20cuspy%20is%20not%20None%20and%20get_cuda_graph_annotations()%20is%20non-empty%2C%20emit%20logger.warning%20that%20Cuspy%20traces%20do%20not%20yet%20carry%20CUDA%20graph%20kernel%20annotations.&repo=pytorch/torchtitan)

2. **`trace_format` is never passed to torch** (`profiler.py:436-443`). It only picks the filename suffix (`.pftrace.gz` vs `.json.gz`). Both formats then go through the same `prof.export_chrome_trace(output_file)` call. So pftrace output only works if torch chooses the encoder from the file extension, and gzips after encoding. If that's how it's meant to work, please add a short comment here saying so; a reader expects `trace_format` to reach some torch API. If torch actually needs an explicit argument, or a different export method for pftrace, then right now this would write JSON into a `.pftrace.gz` file. `test_cuspy_activity_and_trace_file` mocks `torch.profiler.profile`, so it can't catch either case.

#### Minor

3. **Redundant failure reason when torch has no Cuspy** (`_cuspy_unavailable_reasons`). If `torch.profiler.CuspyConfig` is missing, the function still goes on to `from torch.profiler._cuspy import cupti_python`. On that same torch build the import fails too, so the error lists a second reason, `No module named 'torch.profiler._cuspy'`. That second line is noise and suggests a package is missing. Return right after the first reason.

4. **Missing cupti-python gets a bare error.** The `ModuleNotFoundError` branch appends `str(error)` and nothing else. The docs already say `pip install cupti-python`; putting that hint in the error message would save users a lookup.

5. **Top-level `import torch._C._profiler`** (`profiler.py:18`). It's only used in the pftrace probe. A local import inside `_cuspy_unavailable_reasons`, next to the other private-module import, would keep the private dependency in one place. Not blocking.

6. **No bounds check on the sampling values.** `CuspyProfilerConfig.__post_init__` checks that the PM fields come with `performance_metrics`, but accepts `pm_sampling_interval_ms <= 0` and `pm_lookback_window_ms < pm_sampling_interval_ms`. These fields are user-facing config, and a `ValueError` here would be clearer than whatever CUPTI returns. Optional; skip it if torch already validates these values with a clear message.

7. **Error message for a missing GPU.** `raise ValueError("profiler.cuspy requires CUDA.")` is correct. Something like "profiler.cuspy is set but no CUDA device is available" would tell the user which config caused it. Nit.

#### Docs

- I agree with @tianyu-l's inline comment. The profiling docs, including this new Cuspy section, would sit better in `torchtitan/observability/README.md`, next to the code they describe. That could be a follow-up.
- The "PyTorch nightly from 2026-09-21 or later" requirement will go stale. Once a release ships, consider pinning to the release version only.

#### Tests

- The tests use `self.assertRaisesRegex` on a multiline string. That works, but `re.escape` would make it robust if a reason ever contains regex metacharacters. Nit.
- `test_cuspy_activity_config` is skipped on builds without Cuspy, so CI only exercises it if a Cuspy-capable nightly is installed. Worth checking that at least one CI job really runs it, or the "torch API changes fail here" guarantee in its docstring doesn't hold.

I didn't run the tests or the linter. My tool permissions in this job blocked running Python, so I couldn't inspect the installed torch's `export_chrome_trace` to settle point 2.
