# [CP] Add Ulysses context parallelism for KDA and GDN

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5590) · state: closed · merged: True

## Original PR description

## Summary

**This Ulysses PR is inspired by the idea in [#4903](https://github.com/pytorch/torchtitan/pull/4903).**

Add opt-in Ulysses context parallelism for KDA and GDN. Ulysses moves CP sharding from tokens to heads with packed all-to-all collectives, so each rank processes a full sequence for a subset of heads. Per-head convolution and gate parameters are sliced locally without changing checkpoint keys.

The existing state-routing backends remain the default. Ulysses requires head counts divisible by `TP * CP`. KDA/GDN can share HeadTail or PTRR token load balancing with AllGatherKV full-attention layers: they restore original token order after the input all-to-all and reapply the shared permutation before the output all-to-all. These reorders are local; the contiguous path is unchanged.

```python
ContextParallelTransform(
    inner_attention_map={
        FlexInnerAttention: AllGatherKVFlexInnerAttention,
        InnerGDN: UlyssesInnerGDN,
    }
)
```

For Kimi, map `InnerKDA` to `UlyssesInnerKDA` alongside its MLA CP mapping.

## Performance

Median step time after 5 warmup steps; lower is better. Throughput change is `(state / Ulysses - 1) * 100%`.

### GB300

BF16, full activation rematerialization. CP=4 results use three 20-step repeats; CP=2 uses only the first 20-step run per backend. Discard the first 5 steps of each run.

| Model | CP | Tokens | State ms | Ulysses ms | Throughput | Peak GiB, state / Ulysses |
|---|---:|---:|---:|---:|---:|---:|
| Kimi K3, 1.46B | 4 | 8K | 896.2 | 983.2 | -8.8% | 11.40 / 11.40 |
| Kimi K3, 1.46B | 4 | 32K | 1061.9 | 1096.0 | -3.1% | 14.30 / 14.40 |
| Qwen3.5-4B | 4 | 8K | 991.9 | 825.9 | +20.1% | 39.74 / 39.73 |
| Qwen3.5-4B | 4 | 32K | 1831.9 | 1960.8 | -6.6% | 39.84 / 39.85 |
| Qwen3.5-35B-A3B text | 2 | 64K (65536) | 13426.3 | 14210.8 | -5.5% | 270.49 / 270.99 |

Kimi 8K was noisy and its backend ordering changed between repeats.

The 35B-A3B run uses two GB300s, TP=EP=1, and replicated parameters (no FSDP), on a fixed synthetic next-token batch. Timings include forward, backward, CP gradient synchronization, clipping, and fused AdamW. Initial weight and input hashes match.

For 35B-A3B, both backends use `PYTORCH_ALLOC_CONF=expandable_segments:True`. Ulysses hit recoverable memory-allocation retries during timed steps near GPU capacity; State did not emit these warnings. The measured difference includes memory pressure and does not isolate CP communication cost.

## Permutation validation

- 86 CPU tests pass, including mixed Kimi K3/Qwen3.5 configuration validation with HeadTail and PTRR.
- A two-GPU BF16 test verifies bitwise-identical outputs, input gradients, and parameter gradients between contiguous and permuted Ulysses KDA/GDN execution. It covers packed document boundaries, non-self-inverse head-tail and arbitrary permutations, and GDN with different Q/K and V head counts. The test is included in the multi-GPU CI lane.
- Ten training steps complete with finite losses and gradient norms for Kimi K3 debug + HeadTail, Kimi K3 debug + PTRR, and Qwen3.5 debug + HeadTail (CP=2, full activation rematerialization, deterministic algorithms).
- Full `pre-commit run --all-files` passes. Existing performance rows above use their original configurations; the added permutation path has not been benchmarked for speed.

@MegaGimen Seqlen IS a variable that will impact the performance and communication amount. Ulysses has a different communication pattern. For a smaller seqlen, while ulysses may have more communication, ulysses doesn't need to do extra metadata computation. But with longer seqlen, the extra communication outweighs the computation saving, hence a worse performance.  For the inter-node experiment, you can see ulysses is always worse because cross-node communication is slower.
