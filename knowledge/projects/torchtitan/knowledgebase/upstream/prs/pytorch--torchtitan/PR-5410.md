# [rl] Default RL trainers to per-group CUDA graph replay

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5410) · state: open · merged: False

## Original PR description

**TLDR:** Turning trainer CUDA graphs on in an RL recipe crashes at step 2, after the model loads and step 1 runs. The RL trainer config now turns on per-group CUDA graph replay whenever graphs are on, and the trainer fails at startup if graphs were turned on after the config was built.

**Problem**
1. **Changing count.** The RL batcher packs a different number of microbatch groups each step (2, 4 and 5 in the run below).
2. **One graph per step.** With trainer graphs on and `training.cuda_graph_per_microbatch_group=False` (the `TrainingConfig` default), one graph captures the whole step.
3. **Crash.** At step 2 the group count changes, and `CUDAGraphInputSpec.flatten` raises `CUDA graph input structure must remain constant across training steps`.
4. **Who hits it.** No recipe today: every RL recipe sets `disable_cuda_graphs=True`. Anyone who turns graphs on does.

**Solution**
1. Per-group replay already exists: `cuda_graph_per_microbatch_group=True` captures one group and replays it once per group.
2. RL `Trainer.Config.__post_init__` sets it to True when `disable_cuda_graphs` is False. Every RL recipe builds this config, so no recipe changes.
3. It runs before the core checks, so per-group's limits still raise at config time (no SDC replay, no deferred FSDP gradient reduction).
4. Backstop: `Trainer.__init__` raises when graphs are on and per-group is off. That happens when a recipe sets `config.trainer.training.disable_cuda_graphs = False` after the build, which skips `__post_init__`.
5. Unchanged: every recipe (graphs stay off), `TrainingEngine`, and pretraining. CPU and ROCm runs stay eager, as before.

**Results**
```text
Qwen3-0.6B AlphabetSort (rl_grpo_qwen3_0_6b_varlen), 1 trainer H100 + 1 generator H100, TP1, 3 steps, max_num_documents=64
graphs on, per-group off (main):   crashes at step 2: "CUDA graph input structure must remain constant"
graphs on, per-group on:           3 steps with 2, 4 and 5 groups, one trainer graph capture, finite loss and grad norm
```
These runs are from an earlier version of this PR that set the flag in every recipe. With this PR, graphs on gives the second row's config; not rerun.

You may ask:
- Why not a default on the `training` field? Every RL recipe passes its own `TrainingConfig(...)`, which replaces a field default, so it would never apply.
- Why not set the flag in every recipe? That is 23 lines that do nothing while graphs are off, and core forbids per-group with graphs off.
- Why set it instead of raising? Both: set it when the config is built, raise if graphs are turned on later. RL never has a fixed group count, so a whole-step graph is never the right choice in RL.
- Why not one graph per distinct group count? That is the TODO in `TrainingConfig`. Each new count costs warmup steps, a capture and graph memory.

NOTE:
- The eager-vs-graph numerics check is still open, so recipes keep trainer graphs off. To turn them on, set `disable_cuda_graphs=False` inside the recipe's `TrainingConfig(...)`.
- Per-group replay does one gradient reduction per group with FSDP/HSDP. Its docstring says it may not be bitwise identical to eager accumulation.
- An RL config with graphs on and SDC replay now fails at config time. Before, it crashed at step 2.

**Test plan**
- `tests/rl/unit_tests/cpu/test_trainer.py`: restored `test_rl_trainer_rejects_whole_step_cuda_graph` (graphs on, per-group off after the build -> `ValueError` at startup).
- Before un-drafting: run that file, and the 3-step run above with `disable_cuda_graphs=False` set in `rl_grpo_qwen3_0_6b_varlen`'s `TrainingConfig(...)`.
