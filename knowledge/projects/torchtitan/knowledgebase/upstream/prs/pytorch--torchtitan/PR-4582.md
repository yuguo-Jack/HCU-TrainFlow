# [BC][loss] Redesign loss abstractions

[Upstream PR](https://github.com/pytorch/torchtitan/pull/4582) · state: closed · merged: True

## Original PR description

## Motivation

The previous loss hierarchy mixed the trainer-facing interface with concrete
single-output behavior:

- `BaseLoss`, `CrossEntropyLoss`, and `MSELoss` described tensor-only inputs,
  while MTP and chunked loss also operate on aligned prediction/label tuples.
- `MTPLoss` inherited from `CrossEntropyLoss` even though it combines several
  cross-entropy objectives.
- `ChunkedLossWrapper` inherited objective behavior even though it changes how
  another loss is executed.

As a result, inheritance did not accurately describe input contracts,
composition, or execution wrapping.

## Design

### `Loss`: a configurable, typed callable abstraction

`Loss` is a generic abstract `Configurable` whose type parameter describes the
shared structure of `pred` and `labels`:

```python
LossInputT = TypeVar("LossInputT", contravariant=True)

class Loss(ABC, Configurable, Generic[LossInputT]):
    @dataclass(kw_only=True, slots=True)
    class Config(Configurable.Config):
        pass

    @abstractmethod
    def __call__(
        self,
        pred: LossInputT,
        labels: LossInputT,
        global_loss_token_counts: torch.Tensor | None = None,
        **loss_inputs: Any,
    ) -> LossResult:
        ...
```

The abstraction inherits directly from `Configurable`; it does not inherit from
the concrete `Function` wrapper because losses do not store and forward to a
configured `fn`.

`CrossEntropyLoss`, `MSELoss`, `DAPOLoss`, and `GRPOLoss` use the tensor input
contract. Policy losses retain their specialized keyword-only inputs.

### `MTPCrossEntropyLoss`: composition instead of inheritance

`MTPCrossEntropyLoss` implements the tuple input contract and owns a
`CrossEntropyLoss`. It applies cross entropy independently to the main and MTP
depth outputs, normalizes each objective by its corresponding token count, and
combines the weighted terms.

The explicit name reflects that this implementation hard-codes cross entropy.

### `ChunkedLossWrapper`: execution wrapping

`ChunkedLossWrapper` accepts either a tensor pair or aligned prediction/label
tuples:

```python
LossInput = torch.Tensor | tuple[torch.Tensor, ...]
```

It preserves that structure while chunking inputs, running `lm_head`, invoking
the configured inner loss, accumulating gradients, and reconnecting decoder
backward. It does not define the wrapped objective.

The resulting relationships are composition:

```text
chunked cross entropy: ChunkedLossWrapper -> CrossEntropyLoss
chunked MTP:           ChunkedLossWrapper -> MTPCrossEntropyLoss -> CrossEntropyLoss
```

## Detailed changes

- Replace `BaseLoss` with `Loss[T]` and nested `Loss.Config`.
- Make cross entropy and MSE implement `Loss[torch.Tensor]` directly.
- Make DAPO and GRPO inherit the tensor loss abstraction; align DAPO's first
  argument name with the shared `pred` contract.
- Rename `MTPLoss` to `MTPCrossEntropyLoss` and use composition rather than
  inheriting from `CrossEntropyLoss`.
- Make `ChunkedLossWrapper` explicitly support tensor and tuple inputs while
  preserving runtime structure validation.
- Update trainer, model, recipe, documentation, and test call sites.

## Validation

The numerical comparisons below used baseline commit `310e2a66e`, the same seed
checkpoint, `--debug.seed=42`, `--debug.deterministic`, disabled CUDA graphs,
and full-precision TensorBoard values for 10 training steps.

| Configuration | GPUs | Maximum loss difference | Maximum grad-norm difference |
| --- | ---: | ---: | ---: |
| MTP + chunked loss | 1 | 0 | 0 |
| MTP + chunked loss, TP=2, CP=2, SP | 4 | 0 | 0 |

Additional validation:

- Loss, CLI-config, graph-trainer, config-manager, and CP-validation tests:
  84 passed, 7 subtests passed.
- Real-process-group `deepseek_v3_mtp_tp+cp`: 10/10 steps passed on 4 GPUs.
- Compiled MTP + chunked loss CPU smoke test using the eager compile backend
  completed forward and backward successfully.
- Latest focused loss tests after the abstraction follow-ups: 41 passed and 14
  subtests passed. One unrelated local LoRA/FlexAttention CPU compile case could
  not load a TorchInductor artifact because of a local shared-library symbol
  mismatch.
