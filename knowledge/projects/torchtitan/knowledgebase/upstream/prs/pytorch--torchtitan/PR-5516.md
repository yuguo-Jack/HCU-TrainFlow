# [moe][perf] Dist-MoE: skip the per-expert token count it doesn't read (1/3)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5516) · state: open · merged: False

## Original PR description

**TLDR:** With Dist-MoE, the MoE no longer sums the routing map into per-expert token counts that Dist-MoE throws away. Qwen3.5-35B-A3B MoE block at decode: 158.2 -> 150.0 us per layer at 64 tokens per GPU (-5.2%). Outputs bitwise identical.

**Stack** (3 PRs, merge bottom-up; this PR is in **bold**)

| # | PR | Independent? | Needs (stack positions) |
|---|---|---|---|
| **1** | **Dist-MoE: skip the per-expert token count it doesn't read** | **yes** | **—** |
| 2 | Shared experts on a side stream in CUDA graphs at inference | yes | — |
| 3 | Compile the MoE router and its load-balance sums | yes | — |

**Problem**
1. `MoE.forward` sums the `(T, E)` routing map into per-expert counts (`routing_map_TE.sum(dim=0)`) and passes them to the routed experts.
2. The stock routed experts read them to dispatch tokens.
3. `DistMoeRoutedExperts.forward` builds its dispatch from the expert ids and deletes the counts.
4. Cost: one reduction per MoE layer for nothing, 6.8-12.0 us per layer at decode.

**Solution**
1. Routed experts gain `count_tokens(routing_map_TE)`: the stock `RoutedExperts` returns the sum, `DistMoeRoutedExperts` returns `None` (its MXFP8 and LoRA variants inherit that).
2. `MoE.forward`, `MuseSparkMoE.forward` and `KimiLatentMoE.forward` call it instead of summing.
3. Under the SPMD typechecker, Dist-MoE still returns the sum: the checker rejects `None` for an input declared as a tensor.
4. Unchanged: the stock routed experts, which still get the sum, and the router's load-balance statistics (`tokens_per_expert_E`, aux loss).

**Results**
```text
Numerics: bitwise identical. The MoE block's output on each of 4 ranks at T = 32 / 64 / 256, before vs after (12/12).

Qwen3.5-35B-A3B MoE block (router + Dist-MoE routed experts + inline shared experts), EP 4 on 4 GB300,
8 layers, CUDA graphs, decode (no grad), min of 2 interleaved processes, us per layer
T per GPU    before    after    delta
32            153.2    146.4    -6.8  (-4.4%)
64            158.2    150.0    -8.2  (-5.2%)
256           177.4    165.4   -12.0  (-6.8%)
```
NOTE: not measured: end to end, prefill, training.

You may ask: why a method, not a flag like `reads_token_counts`? A flag puts a conditional and a copy of the sum at each of the 3 callers; the method keeps the sum in one place.

Follow up: the stock DeepEP and HybridEP dispatchers also discard the count (`token_dispatcher.py:904-906`, `:1037-1039`), so `RoutedExperts.count_tokens` could skip it for them too.

**Test plan**
- `pytest tests/unit_tests/cpu/models/common/test_dist_moe.py -k count_tokens`: Dist-MoE returns `None`, the sum under the typechecker, and the MXFP8 and LoRA variants inherit the hook.
- `pytest tests/unit_tests/cpu/models/common/test_moe.py -k passes_the_count`: `MoE`, `KimiLatentMoE` and `MuseSparkMoE` pass `None` through; fails if a caller sums again.
- CPU MoE suites: `test_moe.py`, `test_dist_moe.py`, `test_aux_loss.py`, `recipes/test_inference_moe.py`, `models/kimi_k3`, `models/muse_spark`. The 2 MXFP8 recipe tests need torchao.
