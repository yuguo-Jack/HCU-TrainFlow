# [DeepSeek V3] Add MTP1 eager pipeline parallelism

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5329) · state: open · merged: False

## Original PR description

Prepared with AI assistance.

Keep model-specific stage ownership in pipeline.py/pipeline_dsv3() and reuse
pipeline_llm for partitioning, parallelization and scheduling. Send only hidden
activations; prepare shifted IDs and masks as rank-local root kwargs. Preserve
the current four-part input/label/model-kwargs/loss-kwargs preprocessing API.

Replicate the canonical token embedding on the last MTP stage. Synchronize its
FSDP/TP shards after init/loading. Reuse native optimizer-owned GradientClipper
for final owner-gradient combination and logical norm selection. Both copies
retain optimizer states and identical updates; count one logical embedding,
clip both. Configure MTPGradientClipper in the MTP recipe rather than placing
MTP-specific pre-update behavior in the training engine.

Coalesce the two training projections through one LM head. Sequential evaluation
projects/releases each objective through the validation-only loss wrapper;
preserve native alignment, objective denominators and detached loss metrics.
GraphTrainer and MTP+PP+CP remain downstream work, not compatibility fallbacks.

- claude[bot] · COMMENTED · 2026-11-01T06:02:31Z · [source](https://github.com/pytorch/torchtitan/pull/5329#pullrequestreview-5726697149)

**Verdict: changes suggested.** The core MTP+PP design looks right, but one correctness gap should be fixed before landing, and part of the scope should be trimmed.

The PP mechanics hold up:
- Only hidden activations cross stage boundaries.
- Shifted IDs are passed as root kwargs.
- `pipeline_llm` is reused rather than duplicated.
- The FSDP `layers` key fix for non-contiguous stage layer IDs (`apply_fsdp_to_mtp_decoder`) is correct.
- `split_group` uses group-local ranks, and `broadcast` uses a global `src`.
- The combine-then-clip arithmetic counts the embedding once in the norm and clips both copies, which is correct.
- Moving gradient finalization out of `TrainingEngine` addresses the earlier intrusiveness concern.

**Must fix**
1. The two embedding copies can silently diverge unless the recipe also sets `MTPGradientClipper`. Gradient combination only happens inside that clipper, and any DSV3 MTP1 + PP config that keeps the default clipper trains the two copies apart with no error. (inline: `pipeline.py`)

**Should fix**
2. `config/validation.py` now imports and `isinstance`-checks `DeepSeekV3Model`. Move that check into `MTPDecoder.pipeline()` / `DeepSeekV3Model.pipeline()`. (inline)
3. Scope: `ChunkedLossWrapper.validation_only`, which touches loss, validator and engine, and `MTPDecoder.coalesce_lm_head` aren't enabled by any recipe and aren't needed for PP stage ownership. Split them out, or wire them into a tested recipe. (inline)
4. The PP integration recipe swaps `ChunkedLossWrapper` for a plain `MTPLoss`, so MTP+PP+`ChunkedLossWrapper` is never tested. Either support and test it, or reject it explicitly. (inline)

**Minor / questions**
- `pipeline_dsv3` rejects the `fake` backend, but the PR carries `ciflow/fake-pg`. What fails under fake PG? If it's only `split_group`, the fake-PG dry-run path could still cover the partitioning.
- Pipeline-only state (`_mtp_pipeline_enabled`, `_mtp_embedding_group`, ...) now sits on the shared `MTPDecoder`, which Kimi K2.7 also inherits. Consider keeping it in the DSV3 subclass.
- The PR shows parity checks but no loss comparison against a non-PP MTP1 run with the same seed and deterministic settings. That curve would back up the gradient-combination claim directly.

- claude[bot] · comment · 2026-11-01T06:02:05Z · [source](https://github.com/pytorch/torchtitan/pull/5329#discussion_r4434590489)

File: `torchtitan/models/deepseek_v3/pipeline.py` · line 152

**Silent divergence if the recipe doesn't set `MTPGradientClipper`.** The embedding gradients only get summed inside `MTPGradientClipper.clip_grad_norm_`. Only `deepseek_v3_debugmodel_mtp` sets that clipper. Any other config that builds `build_model_config(..., num_mtp_layers=1)` and enables PP gets the default `GradientClipper`. In that case:
- the stage-0 copy is updated with only the main-path gradient,
- the last-stage copy is updated with only the MTP-path gradient,
- both copies are still saved under the same `tok_embeddings.weight` FQN, so DCP dedup keeps one of them arbitrarily.

None of this raises an error or prints a warning. The optimizer is built after `pipeline()`, so this function can't easily check it. Possible ways to close the gap:
- Make the training-time combine independent of which clipper the user picks: register it from `_register_optimizer_hooks` (DSV3 already overrides it) as an optimizer step pre-hook. Then `MTPGradientClipper` only has to handle the logical-norm dedup.
- Or raise a `ValueError` from `_register_optimizer_hooks` (or from `validation.py`, see the comment there) when `_mtp_pipeline_enabled` is set and `optim.gradient_clipper` isn't an `MTPGradientClipper`.

Either way, please add a unit test showing that the misconfigured case raises or is handled.
