## Agent details

**TLDR:** Training accelerator graphs (CUDA graphs) now handle several `forward_backward` calls per step, as streamed RL sends. The step's first call replays one graph that allocates the gradients, as today's default mode does. Each later call replays one graph per segment, which adds into them. This one mode replaces the two graph modes. A trainer with one call per step, like the core trainer, replays the same single graph as before.

**Numerics:** graphs vs eager are bitwise given the same calls (one call per step, FSDP on 1 and 2 GPUs, HSDP 2x1, deferred reduction). One exception in RL: with graphs, the RL trainer sends a step's first group as its own call. Under HSDP or deferral that adds one gradient reduction, so there RL with graphs is not bitwise equal to RL without graphs.

```text
segment = the microbatch groups that one graph replay runs
          the step's first call: one segment
          a later call: a segment ends at each gradient reduction
                        (FSDP or PP: each group. HSDP or deferred reduction: the whole call)

step's first call   -> first-segment graph (allocates the gradients in the graph pool)
each later segment  -> the later-segment graph of its length (adds into them)

one call [g0, g1, g2]:            first([g0, g1, g2])             # core trainer: as before
FSDP, calls [g0] then [g1, g2]:   first([g0]) later_1([g1]) later_1([g2])
HSDP, calls [g0] then [g1, g2]:   first([g0]) later_2([g1, g2])
```

**Problem**
1. The default graph mode captures a whole `forward_backward` call as one graph. It needs one call per step and a fixed group count.
2. Streamed RL sends many calls per step (23.3 per step on dapo_math, measured in the stream-microbatches PR of this stack), and RL's group count changes every step with packing. So the RL controller rejects streaming with graphs.
3. The per-group mode (`accelerator_graph_per_microbatch_group=True`) allows changing counts, with two limits:
   - Its gradients live outside the graph pool, so it rejects SDC replay and deferred reduction.
   - Each group is one replay, so HSDP all-reduces once per group.
4. Lazy preprocessing, which lets RDMA reads overlap training, is rejected with any graph.

**Solution**
1. **One mode.** With graphs on, the engine runs `_run_forward_backward_segments`. The step's first call replays the first-segment graph: today's default wrapper, on the same inputs. A later call replays later-segment graphs (`wrap_with_accelerator_graph`), one per segment length.
2. **Capture order.** A later-segment graph records adds into the gradient addresses that the first-segment graph puts back. So it captures only after the first-segment graph has captured. Until then it warms up with `accelerator_graph_manager.capture_allowed = False`.
3. **No later capture in an SDC-checked call.** A capture makes its call's input tensors the graph's inputs, and the call's next replays copy their own inputs into them. An SDC re-run would then read overwritten inputs. So later-segment graphs warm up, without capture, in a call that SDC replay checks.
4. **New gradient tensors.** A later-segment graph that may capture raises a `ValueError` naming any parameter whose gradient tensor changed during the call: a new one, or a replaced one. That tensor would live in the capture, and the next `zero_grad` would drop it.
5. **Lazy preprocessing** preprocesses the step's first call before its replay, and each later segment just before its own.
6. **RL trainer.** The step's first call must keep one group count, and RL's count changes with packing. So with graphs on, `Trainer.forward_backward` sends the step's first group as its own engine call. Under FSDP or PP this adds no reduction.
7. **Deleted:** `accelerator_graph_per_microbatch_group`, the RL streaming + graphs check, and the engine checks for per-group + SDC, per-group + deferral, and lazy preprocessing + graphs.
8. **Unchanged:** SDC replay still allows one replay with graphs, as on main. Lifting it needs its own PR with a green CI run.

You may ask:
- Why not make the step's first segment its first group inside the engine? Then the core trainer's step of N groups becomes N replays. Each graph replay finishes before the next starts, so one group's reduce-scatter can no longer overlap the next group's forward.
- Why does the RL trainer split its first call instead of one first-segment graph per length? Each would keep its own gradient tensors (122 MiB here), and a replay of one would not put back the other's.
- Why block capture instead of running later segments eagerly until the first graph captures? Eager work on the default stream keeps its own memory cache: +1.1 GiB peak reserved at N = 3.

NOTE:
- `muse_spark` leaves the per-group mode for one 8-group graph per step. On its FakePG recipe (above), steady memory and step time are equal. Capture takes 22 s longer, once. During the eager warmup steps, allocated memory peaks 24 GiB higher, with no change in reserved memory. The recipe's author (jinsooihm, the muse_spark open-source PR) should confirm on real hardware.
- No in-repo RL recipe turns graphs on: all 18 trainer `TrainingConfig` blocks in the 5 RL recipe files set `disable_accelerator_graphs=True`. So the RL split only runs when a user turns graphs on.
- HSDP 2x2 (4 GPUs) was not run. dp_shard=2 covers the reduce-scatter inside graphs, and dp_replicate=2 the replica all-reduce.
- With eval graphs, a later-segment length still in warmup blocks eval capture, and with it training capture. No current config has a validator and several calls per step (TODO at the site).

Silent hazard: a parameter that gets no gradient in the first segment but does get one in a later segment. `_AcceleratorGraphGradientState.record()` stores only the grads that are non-None after the first-segment capture. Such a parameter therefore has `.grad is None` when `later_*` captures, and autograd allocates its grad in the pool during that capture. The next `zero_grad(set_to_none=True)` drops the only reference, and nothing puts it back. From then on, each replay writes into pool memory that has been freed and may be reused, while `param.grad` stays `None` and the optimizer skips the parameter. No error is raised.

The old modes couldn't hit this: the whole-call mode used one graph, and per-group used `set_to_none=False`. The docs only require that segments of the *same length* share a gradient set, not that the first segment's set covers the later ones. A cheap guard would be to snapshot `id(p.grad)` for all `requires_grad` parameters before a `later_*` call that will capture (`not graph.captured`), compare after the call, and raise if any `.grad` went from `None` to a tensor.

Reply from claude: The split has to stay without streaming too. Non-streaming RL also changes its group count every step: G = ceil(B / (M * D)) (`batcher.py:671, 698-704`). A whole-call first graph would raise "input structure must remain constant" (`accelerator_graph.py:64-67`) on the first step whose count differs. Under FSDP or PP the split adds no reduction. Under HSDP or deferral it adds one per step. Before this stack, a changing count needed per-group graphs, which all-reduce once per group under HSDP and reject deferral. No in-repo RL recipe turns graphs on: all 18 RL trainer configs in 5 recipe files set `disable_accelerator_graphs=True`.
