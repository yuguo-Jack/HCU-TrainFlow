# [models][fsdp] preserve_dtype_params: keep selected parameters out of mixed-precision casts

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5774) · state: closed · merged: True

## Original PR description

## Summary (human-written)
<!-- Write this yourself, not with an AI tool. 2-5 sentences: the problem, why
     this approach, and what you checked yourself. -->

pytorch/pytorch#196626 added `MixedPrecisionPolicy.param_dtype_override_fn` so FSDP can leave chosen parameters alone.

E.g., for GDN / KDA, the params `A_log` and `dt_bias` should never go through down-casting, during FSDP's pre-all-gather.

This PR is making it configurable.

## Why
FSDP2 mixed precision (`precision.param_dtype="bfloat16"`) casts every fp32 master parameter to bf16 at all-gather. Some parameters are numerically sensitive, and their reference checkpoints store them in float32 on HF:

| Model | Stored as F32 on HF |
| --- | --- |
| Qwen3.5 (0.8B, 27B, 35B-A3B) | GDN `linear_attn.A_log`, GDN gated norm `linear_attn.norm.weight` |
| Kimi-Linear-48B-A3B (KDA) | `A_log`, `dt_bias` |
| DeepSeek-V4-Flash | `hc_*_fn/base/scale`, `attn_sink`, compressor `ape` |

On main the kernels then upcast bf16-rounded values (`gdn.py:480`, `kda.py:128`, `mhc.py:112`). DSV4 even creates its head hc params with `dtype=torch.float32`, and FSDP still rounds them. The same rounding happens when RL publishes weights to generators (`transfer_dtype`) and when a final checkpoint is exported (`export_dtype`). pytorch/pytorch#196626 added `MixedPrecisionPolicy.param_dtype_override_fn` so FSDP can leave chosen parameters alone.

**Example.**
```python
# GDN.Config (component default)
preserve_dtype_params: tuple[str, ...] = ("A_log", "dt_bias")

# fp32 masters, precision.param_dtype="bfloat16"
# before: FSDP all-gathers A_log in bf16; kernel computes exp(A_log.bf16().float())
# after:  A_log is all-gathered and used in fp32; RL sends and the generator uses it in fp32;
#         export_dtype="bfloat16" keeps it fp32, as in the HF release
```

## What changed
- `Module.Config.preserve_dtype_params: tuple[str, ...]`: names of a module's own parameters that bulk casts never lower in precision. Validated at build. `Module.named_preserve_dtype_params()` yields `(fqn, param)` for a module tree, like `named_parameters()`.
- Components whose math always needs it set the default: GDN and KDA (`A_log`, `dt_bias`), DSV4 `HcPre`/`HcHead` (`hc_*`), DSV4 `Compressor` (`ape`). Flavors set it for single instances of generic modules: Qwen3.5's GDN `GatedRMSNorm`, DSV4's `attn_sink` `Linear`.
- FSDP: `mixed_precision_policy(module, ...)` builds the policy with `param_dtype_override_fn` (the wider of the parameter's dtype and `param_dtype`). Every core FSDP site that shards TorchTitan modules uses it (decoder, multimodal encoder, Flux model). Flux's HF T5/CLIP encoders keep their own policy (no TorchTitan modules). The graph_trainer experiment's SimpleFSDP has no per-parameter override, so `GraphTrainerModel.parallelize` raises if a model lists preserved params (none does today). Removes `Decoder._fsdp_param_dtype_override_fn`, added in #5691 with a TODO asking for this. Quantization converters raise on a `Linear` that lists preserved params instead of silently dropping the field.
- RL (on #5776): the generator mirrors the trainer's `Controller.Config.precision` instead of its own `generator.model_dtype` (removed). It builds the model in `precision.dtype`, so buffers and preserved params get the trainer's dtypes. It holds every other parameter in `precision.param_dtype` and computes in it (vLLM `dtype`; the wrapper raises if they differ), so its FSDP casts nothing. The generator model is frozen, and parameters are cast with `torch.utils.swap_tensors`, since `param.data =` leaves a quantized tensor subclass's (MXFP8/NVFP4) inner tensor in the old dtype. vLLM's attention layers are still built in vLLM's model dtype, because vLLM picks their backend from the default dtype. The trainer sends parameters in `param_dtype` (`transfer_dtype`, when it differs from `dtype`), and buffers and preserved params in their own dtype (`preserve_dtype_keys`). The generator's receive buffers are its sharded state dict as is (`cpu_prefetch`), and `gpu_fetch` (#5652) fetches straight into the sharded parameters, so #5652's cast of float32 parameters through model-dtype staging tensors is removed. This generalizes #5691's GDN-only handling. With bf16 masters, GDN `A_log`/`dt_bias` reach the generator in bf16, so `VLLMInnerGDN` casts them at its kernel call on every forward (`.float()`, a no-op for fp32 tensors), as the trainer's GDN does. With fp32 masters this keeps #5691's saving.
- Checkpoint export: `export_state_dict(state_dict, *, dtype, model_parts)` replaces the duplicated cast loops in both checkpointers and both `scripts/checkpoint_conversion/` converters. The converters now cast before `to_hf`, like the in-training export.
- Mechanical, skimmable: test updates for the removed `param_dtype_override_fn` argument, `models/README.md` bullet, reworded KDA TODO.

## Alternatives considered
- Run-level FQN regex list in the training config: puts an architecture property into every recipe, and patterns break across PP splits and renames.
- Class attribute only: can't vary per instance (Qwen3.5 preserves one `GatedRMSNorm`, KDA's stays bf16).
- Tagging `nn.Parameter` objects: tags are lost through `to_empty`, `param.data =` and DTensor re-wrapping.
- Requiring fp32 masters for RL: several GDN/KDA RL recipes train with bf16 masters.
- Keeping `generator.model_dtype` and upcasting preserved params to at least fp32 on the wire and in the generator: a heuristic that guesses the trainer's dtypes. Mirroring the trainer's `precision` makes every dtype match by construction.

FlexShard's `param_dtype_overrides` (an FQN map) can consume `named_preserve_dtype_params` directly once it lands; not wired here.

## User-facing changes
| | Before | After |
| --- | --- | --- |
| Qwen3.5 / DSV4 training, fp32 masters | listed params all-gathered in bf16 | all-gathered and computed in fp32 |
| Kimi K3 training, fp32 masters | KDA `A_log`/`dt_bias` in bf16 | fp32 |
| bf16 masters (`precision.dtype="bfloat16"`) | unchanged | unchanged (params stay bf16) |
| RL generator dtype | `generator.model_dtype` (every recipe: `"bfloat16"`) | `precision.param_dtype` (default `"bfloat16"`); `generator.model_dtype` removed |
| RL generator, fp32 masters | GDN `A_log`/`dt_bias` fp32, values bf16-rounded | all listed params fp32 and unrounded |
| `export_dtype="bfloat16"` | every float tensor bf16 | listed params stay fp32 |
| `convert_to_hf.py --export_dtype bfloat16` | cast after `to_hf`, so adapter-created tensors were cast too (DSV4 `tid2eid`: int64 -> fp32 in `to_hf`, then rounded to bf16) | cast before `to_hf`; `tid2eid` stays fp32 |

## Performance

- Qwen3.5-0.8B, fp32 masters, FSDP 2, seq 4096, GB300, median tokens/s over steps 5-20, three runs each alternating on the same GPUs: base 24.1k / 24.1k / 22.3k, this PR 25.1k / 23.0k / 23.6k (run-to-run noise about 5%). Peak active memory 28.66 GiB in both.
- DeepSeek-V4 debugmodel: 63.6k vs 63.0k tokens/s (concurrent runs on separate GPU pairs, within noise); peak memory identical.

## Known issues / follow-ups
- Not run here: the 8-GPU `rl_grpo_qwen3_5_debug_tp2_batch_invariant` CI config. A 4-GPU variant (trainer DP 1) is not bitwise on base or on this PR.
- Norm weights in general (beyond Qwen3.5's GDN gated norm) are a follow-up after convergence studies.
- RL with bf16 masters: the generator now receives GDN `A_log`/`dt_bias` in bf16, the trainer's dtype, so `VLLMInnerGDN` casts them each step again. That costs the 3-6 us per GDN layer per step that #5691 saved (Qwen3.5-27B / 35B-A3B measurements there); fp32 masters keep the saving.
- Separate issue found while validating: `VarlenInnerAttention` defaults to cuDNN attention first, whose dQ backward is not deterministic under `debug.deterministic=True` on SM100+ (flash is). Numerics above use flex attention for that reason.

- **Callsites.** The only `MixedPrecisionPolicy(` constructions left are in Flux's HF T5/CLIP encoders (they hold no TorchTitan modules), the transformers backend (sets `preserve_dtype_params = ()`) and graph_trainer (now raises). DSV3/DSV4 MTP goes through `apply_fsdp_to_decoder`. MTP layers are attached as `model.mtp_layers`, so `named_modules()` reaches them. `apply_fsdp_to_decoder` builds one policy before any `fully_shard`, and after TP, so the identity set holds the right parameters. No `model_dtype`, `generator_dtype` or `_fsdp_param_dtype_override_fn` references remain anywhere.
- **Explicit-dtype params.** The only parameters created with an explicit dtype are DSV4 `HcHead.hc_base`/`hc_scale`, and they are preserved. So with bf16 masters (`transfer_dtype=None`), no non-preserved parameter is sent in a dtype other than the one the generator swaps to.
- **Generator build in `precision.dtype`.** The trainer also builds under `set_default_dtype(precision.dtype)` (`training_engine.py:375`), so buffer dtypes match by construction. The RoPE cache is computed with `.float()` either way. `GatedRMSNorm` casts its output back to the input dtype, so the fp32 Qwen3.5 gated-norm weight doesn't spread fp32 activations. Only two vLLM layers are built inside the model, `Attention` and `MLAAttention`, and both are now wrapped in `set_default_dtype(model_config.dtype)`.
- **Config transforms.** LoRA copies every dataclass field, so it keeps the list. The MXFP8/Float8 rebuild drops it, and the new `_validate_quantizable_linear` raise covers that.
- **New since caefd10.** The PR is rebased onto #5652: `gpu_fetch` fills sharded params directly, and the staging-tensor cast is gone. `VLLMInnerGDN` now calls `.float()` at its kernel call (a no-op with fp32 masters). `VLLMInnerKDA` already did, at `kda.py:240`. Both are fine under CUDA graphs.

</details>
