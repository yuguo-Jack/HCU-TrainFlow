## Agent details

Written with Claude Code.

**TLDR:** Kimi K2.5 can now start when dp * cp == 1 (data-parallel degree times context-parallel degree), for example with PP only or on one GPU. On main, every such Kimi K2.5 run fails at startup. The PR has two parts. The mesh fix lets PP start. A cleanup drops the attention maxima that QK clip records during shape inference: one extra forward per stage that torch's pipeline schedule runs to learn tensor shapes.

**Numerics**

```text
Kimi K2.5 debug model, PP 2 (1F1B, 2 microbatches of 512 tokens), 2 GB300 GPUs, 3 steps, seed 42, deterministic.
Main cannot start this run, so the reference is main with the QK clip hook registration removed.

                     loss step 1 / 2 / 3        grad norm step 1 / 2 / 3
main, hook removed   8.0913 / 6.6100 / 5.2602   4.2686 / 4.3782 / 4.9129
this PR              bitwise equal              bitwise equal
```

No run clips: the max logit is 0.98-1.57, and QK clip only scales heads above 100. So the hook runs on both stages without changing the run. The 2-GPU tests cover the scaling math.

**Problem**
1. After each optimizer step, QK clip all-reduces each head's max attention logit over the "loss" mesh: the dp * cp ranks that hold the same layers.
2. `register_qk_clip_hook` reads that mesh with `get_mesh("loss")`, which raises `ValueError: Mesh 'loss' is not available` when dp * cp == 1.
3. Under PP, shape inference runs on the first step, and on the first step after each validation.
4. Stages after the first run that forward on uninitialized memory (`torch.empty`). QK clip records its maxima, and the first clip uses them. In the run above without the cleanup, each stage's first clip sees 9 maxima instead of 6.
5. One NaN maximum there makes that head's scale NaN, and its query and key weights stay NaN.

**Solution**
1. `register_qk_clip_hook` uses `get_optional_mesh("loss")`. `qk_clip` skips the all-reduce when the mesh is None.
2. New `register_qk_clip_shape_inference_cleanup`. It clears the recorded maxima after shape inference, through torch's `register_post_metadata_inference_cleanup` hook. `KimiK25Model.pipeline()` registers it. This applies to every PP run, also with dp > 1.
3. Unchanged: the all-reduce when dp * cp > 1, and runs without PP. CI's Kimi PP + FSDP + EP job runs 1 step, so its loss cannot move: QK clip acts after the step.

Known, already on main: TP > 1. With the recipe's TP rejection skipped (TP 2 x EP 2, AdamW), the first clip raises "QK clip scales do not match the MLA weight shape": each rank records only its own heads. The recipes reject TP > 1 at config time, so no recipe run gets there. TODO at the check.

Not tested: PP with dp > 1 end to end, beyond CI's 1-step job.

**Test plan**
- `pytest tests/unit_tests/gpu/models/kimi_k2_7/test_qk_clip.py`: 6 passed on 2 GPUs.
- `test_optimizer_hook_runs_without_loss_mesh` (new) registers the hook for one QK-clip layer on a real single-rank context, then steps. It fails on main with `ValueError: Mesh 'loss' is not available`. With only main's `if reduction_mesh.size() > 1` put back, it fails with `AttributeError`.
- `test_pipeline_shape_inference_maxima_are_dropped` (new) runs a real 2-stage torch schedule on CPU. Without the cleanup it fails with `3 != 2` recorded maxima.

**What this PR does.** QK clip gets its reduction mesh with `get_optional_mesh("loss")`, so it no longer crashes at startup when dp * cp == 1. When there is no mesh, it skips the all-reduce. This matches main's behavior for mesh size 1, because an active `loss` axis always has size > 1. Separately, `KimiK25Model.pipeline()` registers a callback with the PP schedule. After the schedule's shape-inference forward (metadata inference), the callback clears the QK-clip maxima recorded during that forward. So the first clip only sees real microbatches.

**Example.**
```text
PP=2, dp=cp=1, Kimi K2.5 debug model
main:  register_qk_clip_hook -> get_mesh("loss")
       -> ValueError: Mesh 'loss' is not available   (startup)
PR:    reduction_mesh=None; qk_clip uses local maxima only

PP=2, dp=2 (already runs on main), first optimizer step on stage 1
main:  max_attention_logits_H = [garbage from torch.empty input, mb0, mb1]
       -> a NaN/huge maximum gives a NaN/tiny scale -> wq_b / wkv_b rows corrupted
PR:    cleanup after metadata inference -> [mb0, mb1]
```

<details><summary>Details</summary>

- **Gate.** Both problems are real on main. The mesh crash is deterministic for every dp * cp == 1 run. The garbage maxima also affect existing PP + dp > 1 runs, so the cleanup is not just PP-only scaffolding. That makes it reasonable to ship both in one PR. The fix is in the model folder (`models.md`: model-tied PP behavior lives on the model class), and no shared code changes.
- **Ordering invariant.** The cleanup clears *all* recorded maxima on the rank. That is correct only if metadata inference finishes for every local stage before any real microbatch forward, including interleaved and multi-stage-per-rank schedules. Dist-MoE's `context.reset` (`dist_moe/runtime.py:396-403`) depends on the same ordering, so this PR adds no new assumption. Gradient accumulation (several `pp_schedule.step` calls per optimizer step, `training_engine.py:869`) is also fine: shape inference reruns only on the first schedule step, or the first after validation, so the list is already empty from the previous `qk_clip`.
- **Validation.** `pp_schedule.eval` runs in eval mode, so `_process_aux` records nothing there. The re-inference on the next training step is covered by the cleanup.
- **Tests.** Both new tests fail on main / without the fix, so each guards a real regression. They run on CPU/gloo inside the GPU suite, like the existing `QKClipTest` in this file.
- **Equivalence.** `reduction_mesh is not None` vs main's `reduction_mesh.size() > 1`: `get_optional_mesh` returns `None` for inactive (size-1) axes, so the dp * cp > 1 path is unchanged.

</details>

Not verified: torch's `register_post_metadata_inference_cleanup` firing order for `_PipelineScheduleRuntime` / ZBV schedules (I couldn't read the installed torch source; I inferred it from the Dist-MoE usage), and the TP > 1 behavior above.
