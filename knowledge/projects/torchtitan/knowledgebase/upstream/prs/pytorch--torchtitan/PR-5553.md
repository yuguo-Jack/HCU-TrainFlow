## Original PR description

## Agent details (AI-generated)

Adapt Yidi Wu's (@ydwu4) implementation from #5261 at
1acef597590c0a4933ddcf50e7a6769d99aabdfa, preserving copyright/license and
credit for the original kernel design. Extend the override to positive token
and full-vocabulary sizes instead of restricting it to a benchmark shape.
Preserve native warp/register/global softmax reduction order, BF16 forward
and backward rounding, ignored labels, and device bounds assertions.

Only raw cross entropy is fused. Native MTP alignment, independent objective
denominators, coefficient/mean composition, and detached metrics remain
unchanged. Save two FP32 row statistics (32 KiB at 4096 tokens), not FP32
vocabulary activations. Retain proven 32-bit indexing when T*V < 2^31 and
widen larger addresses. Keep native TP/unsupported-layout behavior unless
fusion is required. Do not add owned outputs or a competing loss-result API.

Production kernels retain their existing hot instruction path. General shapes
use actual fused kernel variants, not eager fallback. Original-author branches
are untouched. GraphTrainer is outside scope.

### Review: changes requested

The design fits the codebase. Only the raw CE callback is swapped, and MTP denominators, weighting and metrics stay with native `MTPLoss`. Saving BF16 logits plus `stats[2,T]` instead of FP32 log-softmax output is a clear memory win, and the TP and unsupported-layout fallback matches native `cross_entropy_loss`. Four issues need fixing before merge, plus two nits. Details are in the inline comments.

**Must fix**
1. **Backward launch fails when `T > 65535`.** In `fused_dsv3_mtp_loss.py:370`, tokens are on grid axis 1, and CUDA caps `gridDim.y` at 65535. `supports()` accepts these shapes, so training crashes instead of falling back, even with `require_fusion=False`. This contradicts the "positive T" claim. Swapping the grid axes fixes it.
2. **CI runs none of the GPU tests.** `tests/unit_tests/gpu/test_fused_dsv3_mtp_loss.py:45` skips the whole module unless the GPU is GB300 `(10, 3)`. The `ciflow/b200` runner is `(10, 0)`. The SM80+ scalar-exp path is not tested anywhere. The router and seqwise test files only gate their production-shape tests on GB300.
3. **The 64-bit indexing branch is untested.** The `T*V >= 2**31` path (`_row_stats` / `_backward`) has no test. The largest test shape is about 33.5M elements, and production DSv3 is about 529M. Any small-vocab test that crosses 2^31 also needs `T > 65535`, so it also hits issue 1.
4. **`debug=True` was added to the forward launches (L321, L338).** It was not in #5261. Besides enabling `device_assert`, Triton's debug mode adds int32 overflow sanitization to the hot-loop index math. Please show with SASS or timing that the production-shape instruction path is unchanged, as the PR description claims, or validate labels another way.

**Docs**
- `FUSED_DSV3.md:189` says "Index offsets are 64-bit", but the code widens to int64 only when `T*V >= 2^31`.
- Spaces are missing in several places: `use32KiB at4096`, `are64-bit`, `stay32-bit`, and `values1024` in the comment at `fused_dsv3_mtp_loss.py:129`.

**Nits**
- `VOCAB_SIZE = 129280` (L394) is unused, and so are most of the tuning kwargs on `_ce_forward` / `_ce_backward`.
- `_check` repeats the conditions in `supports()` one by one; it could just call `supports()`.

**Not verified:** bit-parity with ATen depends on internal ATen choices: the warp, register and block thresholds (2048 / 9216), the `_loss_sum` thread-count formula, and whether `.ftz` exp matches native. I couldn't check these without a GPU; the tests are what would catch drift after a PyTorch upgrade, so issue 2 matters doubly. I didn't run any tests: there's no GPU here, and the bash commands I needed weren't approved.

**Bug for the general-shape claim:** `tokens` is on grid axis 1, and CUDA caps `gridDim.y` at 65535. When `T > 65535` (for example `local_batch_size=16, seq_len=8192` with `num_chunks=1`), the launch fails with `invalid argument`. `supports()` still accepts these shapes, so this crashes even with `require_fusion=False` instead of falling back to native.

This grid comes unchanged from #5261, where the shape was fixed at 4096 tokens, but this PR advertises "positive T". The simplest fix is to put tokens on axis 0 (`2^31-1` limit) and vocab blocks on axis 1 (`cdiv(V, 2048)`, which is 64 for DSv3):

```python
compiled = _backward[(tokens, triton.cdiv(vocab, block))](
```
with `row = tl.program_id(0)` / `columns = tl.program_id(1) * BLOCK + ...` in the kernel. If you swap the axes, re-check the hot-path bits and perf, because the CTA rasterization order changes. A test with `T > 65535` and a small V (for example `(65537, 64)`) would catch this. The same test also exercises the `T*V >= 2**31` widening if you choose V so the product crosses `2**31`. Neither branch is covered today.

`debug=True` was not in the original #5261 launch. It was added here so that `device_assert` fires. In Triton, `debug=True` does more than keep `device_assert`: it also turns on integer-overflow sanitization (an assert after each int32 add/mul/sub). In this kernel that includes the `row * VOCAB` and `tile * 4096 + lanes * 4 + vector` index math in the hot float4 loop.

That conflicts with "Production kernels retain their existing hot instruction path" in the description. Could you confirm, with a SASS diff or a timed comparison against the #5261 kernel, that the production-shape forward is unchanged? If it isn't, an alternative is to validate labels without `debug` (for example a cheap trap only on the label load, or masking plus the native `nll_loss` contract). The same applies to `_warp_row_stats` at L321.
