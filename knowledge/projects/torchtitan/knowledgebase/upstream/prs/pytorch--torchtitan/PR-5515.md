# [moe] Raise on token counts not divisible by TP; pad the gpt-oss parity batch

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5515) · state: open · merged: False

## Original PR description

**TLDR:** `TestBitwiseParityGptOssVarlen` hung for 300 s because it fed MoE an odd token count at TP2 + EP2, and MoE needs a count divisible by TP. This PR pads the test batch to a TP multiple, so `test_batch_invariance` passes bitwise, and MoE now raises the same clear error on every rank instead of hanging.

**Problem**
1. **Test input.** `test_batch_invariance` packs 2 prompts into 277 tokens.
2. **Uneven split.** gpt-oss runs EP2 + TP2 without sequence parallelism, so MoE splits the tokens across the TP ranks: 139 and 138.
3. **Equal shards assumed.** After the experts, the `Shard(0) -> Partial` zero-fill sizes its output as `local_rows * 2`: 278 rows on rank 0, 276 on rank 1.
4. **Hang.** The ranks all-reduce different sizes; under pytest they fall out of step and wait for NCCL's 300 s watchdog, with no assertion text.
5. **Only tests hit it.** Real callers pass TP-divisible counts (the trainer packs every microbatch to a fixed token count; vLLM's runner rounds up to a TP multiple), but nothing checked it.

**Solution**
1. **Test:** `_varlen_prefill_logprobs` appends one pad segment to reach a TP multiple. Its labels are `IGNORE_INDEX` and its logprobs are not returned.
2. **MoE:** `_maybe_shard_routed_branch_inputs_across_tp` runs `torch._check(num_tokens % tp_degree == 0)` before the split. Every TP rank sees the same count, so every rank raises before any collective.
3. **Traceable:** the message captures only Python ints, so the check also traces under `torch.compile(fullgraph=True)`.
4. **Unchanged:** inputs whose token count TP already divides, and the sequence-parallel path, whose tokens arrive already sharded.

**Results**
```text
TestBitwiseParityGptOssVarlen::test_batch_invariance, debug model, TP2 + EP2, 2x H100, torch 2.15.0.dev20261005
main:            RuntimeError on both ranks (277 vs 278 / 276 rows), then hang until NCCL's 300 s watchdog
MoE check only:  both ranks raise "... the token count must be divisible by the TP degree (2).", 33 s, no hang
this PR:         0 of 275 shared-token logprobs differ (bsz 2 vs 5)
```

You may ask:
- Why not assert on every rank in the parity tests? The rank-0 asserts run after all collectives, so they don't hang (the class finishes in 32 s); the uneven split did.
- Why not pad inside MoE? Real callers already pass divisible counts, and padding there adds work to every run.
- Why `torch._check` and not `if ...: raise`? An `if` on an unbacked token count fails to trace; `torch._check` turns into a runtime assert.

NOTE:
- Not run: `TestBitwiseParityMoEEP` (4 GPUs). Its token counts (100, 210) are already even.
- `test_trainer_vs_vllm_prefill` in this class failed before the generator softmax-scale fix, which is now on main; not rerun.
