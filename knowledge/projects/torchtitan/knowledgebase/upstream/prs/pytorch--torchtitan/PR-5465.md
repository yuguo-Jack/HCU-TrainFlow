# [dist_moe] Use fast fused SwiGLU mega kernel for inference

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5465) · state: closed · merged: True

## Original PR description

## Summary

Expose the existing fused SwiGLU option in Dist-MoE's MXFP8 mega kernel to the RL generator. This path is designed for inference, but the RL generator today is using the slower path designed for training.

This new path improved Dist-MoE's MXFP8 speedup (against BF16) from 0.9-1.35x to **1.5-1.7x** across a range of real Qwen3-30B-A3B GEMM shapes (see microbenchmarks section).

```
+--------+---------------------------------+---------------------------------+
|        | Trainer                         | Generator                       |
+--------+---------------------------------+---------------------------------+
| Before | 32x32 weight scales             | 32x32 weight scales             |
|        |                                 |                                 |
|        | W13 and W2 are separate kernels | W13 and W2 are separate kernels |
|        | ("staged" pipeline)             | ("staged" pipeline)             |
+--------+---------------------------------+---------------------------------+
| After  | (unchanged)                     | 32x32 weight scales             |
|        |                                 |                                 |
|        |                                 | W13 and W2 are fused into one   |
|        |                                 | kernel ("mega" pipeline)        |
|        |                                 |                                 |
|        |                                 | SwiGLU fused into W13 epilogue  |
+--------+---------------------------------+---------------------------------+
```

The generator can choose from the following pipelines:
- **staged** (default, unchanged): Separate W13 and W2 kernels
- **mega**: Fused W13 + SwiGLU + W2 in 1 mega kernel, but each of these steps runs in a separate warp
- **mega + fused swiglu** (this PR): Same mega kernel, but SwiGLU is fused into the epilogue of W13 so they run in the same warp. For inference only.

All 3 paths match bitwise exactly, so trainer + generator will continue to match numerically as before regardless of which path the generator uses. For an e2e Qwen3-30B-A3B RL workload, "mega + fused swiglu" is the fastest, followed by "staged", then "mega".

## API

```python
from torchtitan.config.transform import apply_transforms
from torchtitan.config.transform.dist_moe import DistMoeTransform
from torchtitan.models.common.dist_moe import _dist_moe as dist_moe, DistMoeRuntime

# Trainer: unchanged (32x32 scales, staged kernels)
config.trainer = apply_transforms(
    config.trainer, [DistMoeTransform(expert_precision="mxfp8")]
)

# Generator: 32x32 scales, Mega kernel with SwiGLU fused into the W13 GEMM
config.generator = apply_transforms(
    config.generator,
    [
        DistMoeTransform(
            expert_precision="mxfp8",
            block_scaled_config=dist_moe.BlockScaledConfig(pipeline="mega"),
            mxfp8_mega_fused_inference=True,
        )
    ],
)
config.generator.dist_moe_runtime = DistMoeRuntime.Config(inference=True)
```

## E2E example: Qwen3-30B-A3B DAPO-Math RL

Setup:

- Model: Qwen3-30B-A3B-Base, DAPO-Math, 8K max response tokens, one 8x B200 node.
- Trainer: FSDP=4 TP=1 EP=4 on 4 GPUs
- Generator: DP=4 TP=1 EP=4 on 4 GPUs, FULL CUDA graphs

Concurrency:

- P = `num_prompts_per_train_step` = 256
- S = `num_samples_per_prompt` = 16
- `target_offpolicy_steps` = 4
- Theoretical concurrency = 256 * 16 * (4+1) = 20,480
- Actual concurrency = ~4,800 (due to KV cache pressures, stragglers etc)
- R = 4,800 * top_k / EP = 4,800 * 8 / 4 = ~9,600 (median)

Results (steps 3-10 of 10-step runs, speedup over BF16):

| metric                       | Before: staged MXFP8 | After: Mega MXFP8 |
|------------------------------|----------------------|-------------------|
| step time                    | 1.06x                | **1.10x**         |
| generator decode step        | 1.06x                | **1.09x**         |
| logprob diff (trainer - gen) | -0.0020              | -0.0021           |

The expert layer is ~10% of the decode step (attention dominates), so the ~1.6x layer speedup shows up as a few percent end to end; numerics match the staged MXFP8 path.

### Responses to tianyu-l's comments

**1. `mxfp8.py:74`, "Inference uses 1x32-block FPROP scales": why?**

1x32 is the standard MX granularity: one scale per 32 elements along K. Training uses 32x32 tiles for a different reason. Under a 32x32 tile, one `qdata` and one scale grid are valid in both the FPROP orientation and the transposed DGRAD orientation. That is why `prepared()` sets `dgrad_data=self.qdata`, so the weight is quantized only once. Inference has no DGRAD, so that reason disappears, and 1x32 is both finer (more accurate) and what a serving stack would use.

The docstring states the result but not this reason. One sentence like the above would answer it.

**2. `dist_moe.py:157`: does Mega require 1x32? Why can't inference use staged?**

From the code:
- **Mega does not require 1x32.** Mega training already runs with 32x32 scales: the training branch of `_prepare_mxfp8_weight` uses the annex default regardless of pipeline.
- **The actual link is in the annex.** Only `prepare_block_scaled_weight(..., inference=True, fuse_swiglu=...)` produces interleaved W13 with fused SwiGLU, and that call also emits 1x32 FPROP-only scales. The `pipeline == "mega"` check exists because, per the PR, only the Mega pipeline uses the interleaved W13 / fused-SwiGLU epilogue. Staged MXFP8 runs SwiGLU as its own kernel.

So `mxfp8_use_inference_weight_format` bundles two independent choices:
- (a) scale granularity: 1x32 vs 32x32
- (b) interleaved W13 + fused SwiGLU (Mega only)

In principle, (a) alone could work with staged, and (b) could work with 32x32 scales. That second combination is vkuzo's proposal, and the author estimates it at 10-20 lines in dist_moe without kernel changes. It would remove the trainer/generator numerics gap described in the PR.

My recommendation: either split the flag along these lines, or at least have the `ValueError` and docstring say this is an annex limitation, not something inherent to Mega. Please also confirm with @sanketpurandare whether the annex can take 32x32 scales together with `fuse_swiglu=True`. If it can, that should probably be the default generator setup, matching the trainer, with 1x32 as an opt-in.

**3. `mxfp8.py:88`: why build a new `BlockScaledConfig` instead of using the module's?**

You're right, and this already happens on main: the training branch calls `dist_moe.BlockScaledConfig()`. This PR adds a second hardcoded `BlockScaledConfig(pipeline="mega")`.

What happens today: the forward pass gets `module.block_scaled_config` (`runtime.py:464`), but weight preparation in `_DistMoeW13ShardedTensor` / `_DistMoeW2ShardedTensor._build_operands` uses whatever is hardcoded. The likely cause is that the sharded wrappers only carry `use_inference_weight_format` and have no access to the module config.

This works today only because `__post_init__` forces `format == MXFP8_E4M3` and `pipeline == "mega"`. It breaks silently if the annex ever makes weight layout depend on `kernel_config` or `fast_math`, or if a format other than E4M3 is allowed.

Since this PR already threads a flag through `__tensor_flatten__`/`_rewrap`, the cleaner fix is to thread the module's `BlockScaledConfig` instead. The format choice (inference vs training) could even be derived from it. That would also replace the bool. [Fix this →](https://claude.ai/code?q=In%20torchtitan%2Fmodels%2Fcommon%2Fdist_moe%2Fmxfp8.py%20on%20branch%20dist-moe-mxfp8-inference%2C%20_prepare_mxfp8_weight%20hardcodes%20dist_moe.BlockScaledConfig()%20and%20BlockScaledConfig(pipeline%3D%22mega%22)%20instead%20of%20using%20MXFP8DistMoeRoutedExperts.block_scaled_config.%20Thread%20the%20module%27s%20block_scaled_config%20into%20_DistMoeMXFP8ShardedTensorBase%20(via%20__init__%2C%20__tensor_flatten__%2C%20__tensor_unflatten__%2C%20_rewrap)%20and%20_dynamic_prepared_weight%2C%20and%20pass%20it%20to%20dist_moe.prepare_block_scaled_weight.&repo=pytorch/torchtitan)

### Other findings

**Mismatched settings fail late or not at all (worth fixing).** `mxfp8_use_inference_weight_format` sits on the transform, while `DistMoeRuntime.Config.inference` sits on the runtime config, and nothing checks the two against each other:
- **Format on, runtime off** (e.g. someone applies the generator transform to a trainer, or to a validation model with a training runtime): the forward pass hands the annex prepared weights with `dgrad_data=None` and an interleaved W13, inside a training context. At best this fails during backward with an annex error that doesn't explain the cause.
- **Format off, runtime on**: this works (it is the current default), so no check is needed there.

Suggestion: add an explicit `ValueError` when the runtime binds a module. `DistMoeRuntime` already reads `module.block_scaled_config` around `runtime.py:449-467`, so it can also check that `getattr(module, "use_inference_weight_format", False)` implies `self.config.inference`. Add a CPU unit test for it. This also covers "users should not turn on this format just to run validation" with an error instead of documentation alone. [Fix this →](https://claude.ai/code?q=On%20branch%20dist-moe-mxfp8-inference%2C%20in%20torchtitan%2Fmodels%2Fcommon%2Fdist_moe%2Fruntime.py%20where%20dist_moe.Config%20is%20built%20from%20a%20module%20(~line%20449)%2C%20raise%20ValueError%20if%20the%20module%20has%20use_inference_weight_format%3DTrue%20but%20self.config.inference%20is%20False%2C%20with%20a%20clear%20message.%20Add%20a%20CPU%20unit%20test%20in%20tests%2Funit_tests%2Fcpu%2Fmodels%2Fcommon%2Ftest_dist_moe.py.&repo=pytorch/torchtitan)

**Minor items:**
- **`mxfp8.py:46`:** the format check in `_DistMoeMXFP8Operands.prepared` raises `RuntimeError`. It guards an internal invariant (operands built in one format, consumed in the other), so per CLAUDE.md it should be an `assert` with the same message.
