# [dist_moe] Use fast fused SwiGLU mega kernel for inference

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5465) · state: open · merged: False

## Original PR description

## Summary

Expose the existing fused SwiGLU option in Dist-MoE's MXFP8 mega kernel to the RL generator. This path is designed for inference, but the RL generator today is using the slower path designed for training. The main benefits are:

- **Faster MXFP8 rollouts:** This path improved the expert layer's MXFP8 speedup (against BF16) from 0.9-1.35x to 1.5-1.7x across a range of real Qwen3-30B-A3B GEMM shapes.

- **Closer match to real inference numerics:** A production MXFP8 inference stack will likely serve with the fastest kernel. Using the same path during RL training minimizes numerical mismatch.

```
+--------+---------------------------------+---------------------------------+
|        | Trainer                         | Generator                       |
+--------+---------------------------------+---------------------------------+
| Before | 32x32 weight scales             | 32x32 weight scales             |
|        |                                 |                                 |
|        | W13 and W2 are separate kernels | W13 and W2 are separate kernels |
|        | ("staged" pipeline)             | ("staged" pipeline)             |
+--------+---------------------------------+---------------------------------+
| After  | (unchanged)                     | 1x32 weight scales              |
|        |                                 |                                 |
|        |                                 | W13 and W2 are fused into one   |
|        |                                 | kernel ("mega" pipeline)        |
|        |                                 |                                 |
|        |                                 | SwiGLU fused into W13 epilogue  |
+--------+---------------------------------+---------------------------------+
```

**Note:** This change introduces a small numerical divergence between the trainer and the generator (32x32 vs 1x32 weight scales). In practice, this has little effect on RL training (see E2E section below). Ideally the trainer should match the generator as closely as possible, but training with 1x32 scales and fused swiglu is currently not supported in DistMoE.

The generator still defaults to `staged` (unchanged). This PR just adds an option for users to choose a faster path.

## API

```python
from torchtitan.config.transform import apply_transforms
from torchtitan.config.transform.dist_moe import DistMoeTransform
from torchtitan.models.common.dist_moe import _dist_moe as dist_moe, DistMoeRuntime

# Trainer: unchanged (32x32 scales, staged kernels)
config.trainer = apply_transforms(
    config.trainer, [DistMoeTransform(expert_precision="mxfp8")]
)

# Generator: 1x32 scales, Mega kernel with SwiGLU fused into the W13 GEMM
config.generator = apply_transforms(
    config.generator,
    [
        DistMoeTransform(
            expert_precision="mxfp8",
            block_scaled_config=dist_moe.BlockScaledConfig(pipeline="mega"),
            mxfp8_use_inference_weight_format=True,
        )
    ],
)
config.generator.dist_moe_runtime = DistMoeRuntime.Config(inference=True)
```

## Dist-MoE microbenchmarks

MXFP8 speedup against BF16 across 1 DistMoE layer:
- Hardware: one B200
- Shapes: derived from Qwen3-30B-A3B at EP4
  - gate/up (W13): `[R, 2048] @ [32, 2048, 1536]`
  - down (W2): `[R, 768] @ [32, 768, 2048]`
  - `R`: number of routed rows per rank
- MXFP8 output error vs bf16 is unchanged (relative error 0.066 for both paths)

| R       | Before: staged MXFP8 (32x32) | After: Mega + fused SwiGLU (1x32) |
|---------|------------------------------|-----------------------------------|
| 512     | 105.2 / 117.3 (0.90x)        | 105.6 / 61.3 (**1.72x**)          |
| 2,048   | 122.9 / 125.6 (0.98x)        | 123.8 / 72.0 (**1.72x**)          |
| 5,120   | 144.8 / 151.1 (0.96x)        | 144.2 / 87.4 (**1.65x**)          |
| 8,192   | 174.1 / 171.4 (1.02x)        | 174.0 / 112.0 (**1.55x**)         |
| 10,240  | 218.4 / 192.9 (1.13x)        | 219.8 / 135.5 (**1.62x**)         |

## E2E example: Qwen3-30B-A3B DAPO-Math RL

Setup:

- Model: Qwen3-30B-A3B-Base, DAPO-Math, 8K max response tokens, one 8x B200 node.
- Trainer: FSDP=4 TP=1 EP=4 on 4 GPUs
- Generator: DP=4 TP=1 EP=4 on 4 GPUs, FULL CUDA graphs

Concurrency:

- P = `num_prompts_per_train_step` = 256
- S = `num_samples_per_prompt` = 16
- `target_offpolicy_steps` = 4
- Theoretical concurrency = 256 * 16 * (4+1) = 20,480
- Actual concurrency = ~4,800 (due to KV cache pressures, stragglers etc)
- R = 4,800 * top_k / EP = 4,800 * 8 / 4 = ~9,600 (median)

Results (steps 3-10 of 10-step runs, speedup over BF16):

| metric                       | Before: staged MXFP8 | After: Mega MXFP8 |
|------------------------------|----------------------|-------------------|
| step time                    | 1.06x                | **1.10x**         |
| generator decode step        | 1.06x                | **1.09x**         |
| logprob diff (trainer - gen) | -0.0020              | -0.0021           |

The expert layer is ~10% of the decode step (attention dominates), so the ~1.6x layer speedup shows up as a few percent end to end; numerics match the staged MXFP8 path.
