# [rl] Fetch generator weights from the StorageVolume into GPU

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5652) · state: closed · merged: True

## Original PR description

Root issue: RL generators prefetch each policy from the StorageVolume into a full pinned CPU copy of the weights before loading it into vLLM. GB300 generator hosts have little CPU memory and OOM on this copy.

Fix: one load path, `VLLMModelWrapper.load_model_state_dict(fetch)`, walks the FSDP groups one at a time (reshard, restore sharded params, `fetch` the group's subset in place, unshard and free; buffers last). Every parameter must be filled. `Generator.Config.model_state_dict_load_mode` picks the fetch:

| `model_state_dict_load_mode` | prefetch | fetch during load | generator host memory |
|---|---|---|---|
| `"cpu_prefetch"` (default, previous behavior) | StorageVolume -> pinned CPU copy, overlaps generation | `copy_` from the pinned copy | +1 full weight copy |
| `"gpu_fetch"` | no-op | TorchStore read straight into the GPU weights | none |

A gloo all-reduce agrees on load failure across generator ranks before rank 0 replies; on a fetch failure every rank still unshards every group (avoids an all-gather hang) and then stops the engine loop. gpu_fetch tradeoff: the transfer runs inside the load while the engine is paused rather than overlapping generation. gpu_fetch rejects quantized parameters at init. Parameters whose dtype differs from the model dtype (float32 GDN `A_log`/`dt_bias`, https://github.com/pytorch/torchtitan/pull/5691) are fetched into model-dtype staging tensors and cast, since the trainer sends the model dtype and torchstore requires matching dtypes. The trainer-side duplicate copy (https://github.com/pytorch/torchtitan/issues/5654) was removed by https://github.com/pytorch/torchtitan/pull/5659.

Requires https://github.com/meta-pytorch/torchstore/pull/252 (merged).

Test plan:
- CPU: `pytest tests/rl/unit_tests/cpu` with no GPU: all pass (gpu_fetch load path covered by `test_vllm_wrapper`/`test_generator`, incl. float32 param staging).
- GPU (GB200): `torchrun --nproc-per-node=2 -m pytest tests/rl/unit_tests/gpu/test_bitwise_parity.py::TestBitwiseParityQwen35DebugVarlen`: 5 passed on both ranks. Trainer vs vLLM prefill and decode are bitwise identical, including a reload through `load_model_state_dict` after CUDA graph replay.
- E2E async RL on GB200 through TorchStore (before merging main):
  - Qwen3 debugmodel, gen TP2, 4 steps: logprob_diff/max 0.0099-0.012 in both modes.
  - Qwen3 8B, gen TP1, 5 syncs: logprob_diff/max 0.21-0.31 in both modes (same as before this PR; untrained weights, not batch invariant).

Generator memory, Qwen3 8B, gen TP1:

| mode | host RSS | GPU growth in sync | sync time |
|---|---|---|---|
| `cpu_prefetch` | 24.7 GiB (16 GiB pinned copy) | +1 GiB on first sync only | 0.48 s, overlapped with generation |
| `gpu_fetch` | 3.8-3.9 GiB | 0 | 1.1-1.2 s, engine paused |

Lines changed: impl +306/-88, tests +436/-100, CI 0.

### tianyu-l's review

2. `model_wrapper.py:599`, naming -- **Correct.** One mode has four names: `fetch_model_state_dict_to_gpu`, `load_*_direct`, `_direct_load_groups`, and `fetch_model_state_dict` (which is really the transport callable). 3. `model_wrapper.py:401`, `other_keys` -- **Correct.** The assert on that line guarantees they are buffers. Rename to `buffer_keys` / `_direct_load_buffer_keys`, and update the docstring.
4. `engine_loop.py:505` -- **Partly correct.** Only the direct path needs the all-reduce before replying, since other ranks may still be reading the snapshot. The staged path has a related gap, though: if one rank's load raises, that rank stops alone, rank 0 replies success, and the next decision broadcast hangs. After (1), run the all-reduce on both paths (it reduces a single integer over gloo) and inline `_load_model_state_dict_direct`, which has one caller.
5. `generator.py:162`, what is the unification? -- It isn't chunked CPU prefetch, and the TODO gives no concrete plan. To overlap a direct fetch with generation, the new weights need somewhere to live while CUDA graphs still read the old ones. That means keeping the sharded buffers allocated: 1/FSDP-degree of the weights in GPU memory, taken from the KV cache, and a full second copy at FSDP 1 (#5268's OOM case). Chunked CPU prefetch would save host memory, but the transfer would still happen during the pause. The author should say what the TODO means, or delete it.
6. `generator.py:163`, first-class paths -- **Correct.** Neither path is better on both axes: 0.52 s overlapped vs 1.2-2.3 s paused, and 24.7 vs 3.8 GiB RSS.
