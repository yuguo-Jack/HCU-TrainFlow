# [lora] shared-outer adapter layout for routed experts

## Why

Grouped LoRA gives every expert its own `A` and `B` (`A [E, L, I]`, `B [E, O, L]`). Serving engines and other trainers lay expert adapters out the other way, "shared-outer": the factor on the model-dimension side of each routed projection is shared across the experts (`A` of W13, which reads the hidden stream; `B` of W2, which writes it) and only the other factor is per expert. A token's low-rank path then reads and writes the hidden stream through one matrix, and the adapter volume no longer scales with the model dimension per expert. SGLang serves both layouts, but its tuned MoE LoRA plans target shared-outer, Megatron-Bridge and miles train it, and it is the one an RL trainer wants to sync every step. The layout is fixed in `_build_grouped_lora_adapters`, so a trainer that needs it has no way to ask for it.

Before: `LoRATransform(rank=8)` on a W13 `[E, 2, F, D]` gives `lora_a [E, 8, D]`, `lora_b [E, 2, F, 8]`; no other shape is reachable.
After: `LoRATransform(rank=8, expert_adapter_layout="shared_outer")` gives `lora_a [8, D]` (shared), `lora_b [E, 2, F, 8]`; for W2, `lora_a [E, 8, F]`, `lora_b [D, 8]` (shared). The default stays `per_expert`.

## What changed

- `LoRATransform.expert_adapter_layout: Literal["per_expert", "shared_outer"] = "per_expert"`. Under `shared_outer`, a grouped target named `w13` gets `shared_factor="lora_a"` and `w2` gets `"lora_b"`; any other grouped projection is refused with `ValueError`.
- `torchtitan/models/common/lora.py`: the grouped LoRA config carries `shared_factor`; the shared factor is built as a plain `Linear` without the expert axis, with the sparse family's replicated placement where the base weight is split by expert (the placement a parameter shared across experts already uses, kept in step under EP by `test_fsdp_moe_sharding`), and the base placement otherwise. `_grouped_mm` applies a shared factor as one dense matmul over the routed rows and a per-expert one as a grouped matmul (`_adapter_matmul`). Dist-MoE materializes `W + scale * B @ A` with the same single `baddbmm` as before; `_adapter_operands` hands it a shared factor as a stride-0 expanded view, so no extra full-size temporary.
- Mechanical: `_create_lora_class` is split into the two `get_lora_*` builders so only the grouped config carries the new field.

## Numerics / performance

Per-expert layout is unchanged: same adapters, same grouped matmuls, same `baddbmm` materialization. The shared-outer layout is new behavior with no golden losses.

## Testing

- `test_shared_outer_adapters_share_the_model_side_factor`: shapes and state-dict keys of both projections, forward equal to a per-expert loop with the shared factor broadcast (bf16 rows, as the grouped matmul casts), gradients reach all four adapters and no base weight. Catches a wrong shared side or a wrong operand order.
- `test_shared_outer_adapters_follow_expert_sharding`: shared factors get the replicated sparse placement, per-expert ones keep the expert placement.
- `test_shared_outer_rejects_a_grouped_projection_outside_the_experts`.
- `test_shared_outer_lora_dist_moe_weight_operands_broadcast_the_shared_factor` (Dist-MoE): effective W13/W2 equal the base plus the broadcast update.
- `TestSharedOuterLoRAExpertParallel.test_shared_factor_stays_replicated_across_ep` (GPU, 4 ranks, EP=2 with FSDP on the Qwen3 MoE test config): the shared factors sit on the sparse mesh, receive gradients with their own placements, and hold one value on every EP rank after an optimizer step; the per-expert factors stay expert-sharded. - HJSang · comment · 2026-11-03T00:31:37Z · [source](https://github.com/pytorch/torchtitan/pull/5738#issuecomment-6592133179)

@tianyu-l thanks for looking. Pointers:

**Serving (SGLang).** The layout was introduced in sgl-project/sglang#21466 and is the only expert-LoRA layout its MoE LoRA path implements: `FusedMoEWithLoRA` (https://github.com/sgl-project/sglang/blob/9eec211b9a/python/sglang/srt/lora/layers.py#L1007) applies the shared factor as one dense step and indexes a per-expert table for the thin factor; the flag's contract is in https://github.com/sgl-project/sglang/blob/9eec211b9a/python/sglang/srt/arg_groups/fields/lora.py#L91 ("w1/w3 lora_A and w2 lora_B are shared across experts"); the two adapter key conventions are documented at https://github.com/sgl-project/sglang/blob/9eec211b9a/python/sglang/srt/lora/lora.py#L125.

**Training (Megatron-Bridge).** `experts_shared_outer_loras` in https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/00e3730dd99181177e731b475b6fdd05a309eaaa/src/megatron/bridge/peft/lora.py#L135 (documented as matching the SGLang contract), implemented by `SharedOuterGroupedExpertAdapter` at https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/00e3730dd99181177e731b475b6fdd05a309eaaa/src/megatron/bridge/peft/utils.py#L2683 next to the per-expert `GroupedExpertLinearAdapter` (L2014).

**What the layout means.** For W13 (reads the hidden stream, `[E, 2F, D]`) the update is `B_e @ A` with one `A [r, D]` for all experts and per-expert `B_e [2F, r]`; for W2 it is `B @ A_e` with per-expert `A_e [r, F]` and one shared `B [D, r]`. The factor on the model-dimension side is shared, the expert-side one is per expert. At the same rank it is a strict subset of per-expert (set every `A_e := A`), so the two are different models, not two encodings of one: an adapter has to be trained in the layout it will be served in. The reasons engines standardised on shared-outer: one dense matmul for the shared step plus a thin per-expert table (no per-expert `A` kernel), adapter volume `r*2D + E*r*3F` instead of `E*r*(2D+3F)` per layer (for a 256-expert, 8192-wide model at rank 32 that is 101M vs 268M parameters per layer, which is also the weight-sync volume in RL), and the shared read-out is trained on every token rather than each expert's ~top_k/E share.

**Consumer.** The RL trainer in radixark/miles uses torchtitan as a training backend and serves adapters through SGLang after every step; today its torchtitan path can only adapt attention on MoE models for this reason, while its Megatron path trains shared-outer expert adapters. The export of these adapters under the HF/SGLang names lives in miles (the same code path it uses for fused q/k/v, which also share one `lora_a`), so nothing in torchtitan needs to export them; this PR is the trainer-side piece.

**Only mode?** I kept `per_expert` as the default so existing users see no numerics change, and because the per-expert code, its tests and the Dist-MoE materialization are already in tree. If you would rather have a single layout, shared-outer is the one every consumer serves, and I am glad to make it the only one in this PR; that removes the knob the review objects to. One asymmetry to be aware of either way: torchtitan's fused w13 shares one `A` across gate and up, while Megatron-Bridge keeps one per branch, so torchtitan -> SGLang export duplicates `A` losslessly, and the reverse direction is exact only when the two branch factors are equal.
