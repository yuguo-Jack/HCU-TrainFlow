# feat: let GroupedLinear declare its FSDP shard dim

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5575) · state: open · merged: False

## Original PR description

Lets GroupedLinear report which dimension FSDP should shard when it cannot shard the group (expert) axis.

linear_param_shard_placements hardcodes Shard(weight.ndim - 2) for stacked weights, which assumes in_features is the last dimension. That holds for the stock [E, N, F, D] layout, but not for a subclass that allocates its weight in a kernel-native order — there the output-feature axis sits elsewhere and the hardcoded index silently shards the wrong dimension. Only the module knows its own layout, so this adds GroupedLinear.fsdp_shard_dim(param_name) and has linear_param_shard_placements ask for it. The default returns the dimension the function already used, so stock placements are unchanged.

Part of https://github.com/pytorch/torchtitan/issues/5545

Test plan
Two CPU unit tests in tests/unit_tests/cpu/distributed/test_fsdp.py:

test_grouped_linear_shard_placements_use_default_shard_dim — stock layouts still resolve to Shard(2) for [E, N, F, D] and Shard(1) for [E, F, D].
test_grouped_linear_subclass_declares_its_own_shard_dim — a subclass that reallocates its weight as [E, D, N, F] and overrides fsdp_shard_dim gets its declared dimension.
No numerics change: the default path produces identical placements.
