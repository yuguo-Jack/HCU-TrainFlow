# [rl] Generator weight-sync buffers: allocate pinned directly, keep attention scales, fail on unpublished keys; one CPU thread at init

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5484) · state: open · merged: False

## Original PR description

**TLDR:** Four generator fixes. The first three are about the pinned CPU buffers that receive weight syncs, which `VLLMModelWrapper.__init__` builds once:
1. **Allocate them pinned directly**, without a staging copy: 64 GiB 51.4 s -> 13.7 s on every generator start (H100 host).
2. **Fill them with the model's values**, so vLLM's attention scales stay 1.0 after a sync instead of 0.0. An FP8 KV cache would divide by 0.
3. **Fail the pull when the trainer didn't publish a generator weight.** Today that weight silently keeps its init value.
4. **Set vLLM's one-CPU-thread runtime at init.** On a 4-layer Qwen3.5-35B-A3B, `OffsetRMSNorm` compiles 13 -> 9 times; in an RL smoke, recompiles go 24 -> 17.

NOTE: measured on H100 only; needs retesting on Blackwell. (Change 4's compile counts don't depend on the GPU.)

**1. Pinned buffers without a staging copy**
1. **Today:** `__init__` builds the buffers with torch's `_create_cpu_state_dict(self.model.state_dict(), pin_memory=True)`.
2. **The waste:** for each DTensor weight, it copies the local shard to pageable CPU memory, allocates a pinned tensor, and drops the copy.
3. **Cost:** 64 GiB of FSDP-sharded bf16 weights take 51.4 s on one H100 host. Qwen3.5-35B-A3B on GB300 (65 GiB per engine, an earlier main) takes about 50 s per engine, before the first weight sync.
4. **This PR:** `_empty_pinned_like(tensor)` allocates `torch.empty(local_shape, dtype, device="cpu", pin_memory=True)` and wraps it in a DTensor with the weight's spec (mesh, placements, global shape).
5. **Unchanged:** each buffer's DTensor spec, the NUMA binding before allocation, and every TorchStore call.
```
Building the buffers. FSDP-sharded bf16 Linear weights, 1 rank, H100 host, torch 2.15.0.dev20261005
8 GiB      6.5 s -> 1.7 s
64 GiB    51.4 s -> 13.7 s

Standalone VLLMGenerator init, Qwen3.5-4B-Base, TP1, 1x H100, warm compile caches, 9.0 GiB of buffers.
4 runs each on a shared host (load average ~180), measured before the fill copy (2) was added (+0.2 s).
vLLM "Model loading"          12.5 / 11.4 / 11.1 / 10.6 s  ->  4.9 / 3.5 / 7.5 / 5.1 s
VLLMGenerator init (median)   28.0 s  ->  22.2 s
```
End to end, 3 steps of Qwen3-0.6B alphabet sort (trainer and generator on one H100): weight sync works; trainer vs generator logprob diff -0.0018 (main -0.0016); step-0 validation reward 0.190 (main 0.192).

NOTE: allocating pinned memory still takes 13.7 s per 64 GiB; the TODO in `__init__` suggests a background thread during vLLM's memory profiling.

**2. vLLM's attention scales keep their init value**
1. vLLM's `Attention` registers 4 scale buffers per layer (`_k_scale`, `_v_scale`, `_q_scale`, `_prob_scale`), and the trainer has none of them.
2. TorchStore fills only the keys the trainer publishes, and the pull loads every key with `strict=True`. So after the first sync, the scales are whatever the buffer held.
3. Only FP8 paths read them, and TorchTitan asserts the FP8 KV cache off, so generation is unchanged today.
4. **This PR:** right after allocating the buffers, `_copy_state_dict` copies the model's values into them, and `_VLLMAttention._init_self_buffers` sets the scales to vLLM's default 1.0 (they are built on meta, and vLLM fills them only after `__init__`).
```
Qwen3.5-4B-Base, 1x H100, in-process vLLM engine. Fill only the trainer's keys, then run main's pull.
32 attention scales after 1 sync (measured on change 2 alone, before change 1):
  main 0.0, main + copy only 0.0, + default scales 1.0 (TP1 and TP2)
greedy decode before vs after the sync: identical in all runs
startup: +0.21 s for 9.02 GiB (the old _create_cpu_state_dict took 10.8-12.8 s)
```

**3. Fail the pull on an unpublished generator weight**
1. The pull fetches only keys that are both published and in the pinned dict, so a generator key the trainer didn't publish keeps its old value, with no error.
2. `load_state_dict(strict=True)` can't see it, because the pinned dict comes from the generator's own model. In RL, the old value is the init: random weights, or zeros for an `expert_bias_E` buffer.
3. Nothing hits this today: 0 unpublished keys across the 32 of 35 alphabet-sort RL recipes that build. But the trainer and generator model configs are separate objects, and the controller compares only their class.
4. **This PR:** `prefetch_model_state_dict` compares the pinned dict's keys with the keys the pull returned, and raises `RuntimeError` naming the first 5. vLLM's attention scales (`.vllm_attn.` keys) are exempt. Keys the trainer publishes but the generator doesn't hold aren't fetched, so they aren't checked.
```text
trainer vs generator keys, 32 RL recipes (meta device, CPU):   unpublished keys 0
same probe, 9 recipes in dapo_math, search_r1, verifiers_dapo_math, verifiers_terminal_bench: 0
  (not built: 3 of 35 alphabet-sort recipes (dist_moe, DeepEP, newer torchao), the DeepEP search_r1
  perf recipe, the Muse Spark GB300 recipe; Terminal-Bench recipes built with Verifiers stubbed)
check cost per pull (1920 keys, CPU):                          0.03 ms
2x H100, trainer 1 GPU + generator 1 GPU, 2 train steps:
  Kimi K3 debug (MoE, 16 expert_bias_E buffers)   3 pulls, no error
  Qwen3-0.6B (tied lm_head.weight)                3 pulls, no error
  trainer drops layers.1.feed_forward.expert_bias_E:
    RuntimeError: The trainer did not publish 1 of the generator's weights (first 5: ['layers.1.feed_forward.expert_bias_E']). Check that the trainer and generator model configs match.
  trainer drops lm_head.weight (tied):
    RuntimeError: The trainer did not publish 1 of the generator's weights (first 5: ['lm_head.weight']). ...
```
The two "trainer drops ..." runs are negative controls: a local edit removed one key from the trainer's staging dict.

**4. One CPU thread from model init**
1. When warmup ends, vLLM sets the thread that runs the model to one CPU thread, unless `OMP_NUM_THREADS` is set. RL generator processes don't set it, so warmup runs at the host's core count (192 here).
2. torch.compile guards on the thread count, so each region compiled during warmup compiles again at the first step that runs eager (FULL_DECODE_ONLY mixed steps, NONE, or steps above the capture cap).
3. It's headroom, not a crash today: a region raises at its 17th version (`recompile_limit=16`), and a 9B replay already uses 13 of 16 on the worst region.
4. **This PR:** `__init__` calls vLLM's own `set_torch_threads_for_runtime` before vLLM's first compile, so vLLM's later call changes nothing. A user-set `OMP_NUM_THREADS` is still left alone.
```
4-layer Qwen3.5-35B-A3B-Base, TP1, H100, FULL_DECODE_ONLY, 7 batches (1-64 prompts x 700 tokens), TORCH_LOGS=recompiles, A-B-A-B
                                   before        after
OffsetRMSNorm compiles             13, 13        9, 9
norm, activation, gate, RoPE       4 each        3 each
num_threads guard failures         48, 48        0, 0
3-step RL smoke (Qwen3.5 debugmodel, FULL_DECODE_ONLY, 2 GPUs): recompiles 24 -> 17, num_threads guard failures 45 -> 0,
  bit_wise/logprob_diff/max 0.012 -> 0.011 (last of 3 steps)
```
Decode step medians, over all 7 batches and both rounds (14 pairs): within -0.32/+0.35 ms of base, higher in 10 of 14. The largest gap is 8 prompts, round 2: 2.43 -> 2.71 ms. Model load (8-12 s) and engine init (20-24 s) vary by the same amount in both arms.

You may ask:
- **Why not load only the keys TorchStore filled?** A generator-only parameter would still be lost: each pull re-allocates the sharded storage without values.
- **Why not `strict=True` in TorchStore?** The routing client doesn't support it: each rank reads only the keys it registered.
- **Why not `OMP_NUM_THREADS=1`?** It also puts the actor thread that copies prefetched weights on one thread: a 2 GiB CPU copy takes 12.7 ms at 192 threads and 163.6 ms at 1.
- **Why not make the 4 scales non-persistent?** That fixes only these 4. Another vLLM attention buffer the trainer doesn't publish would get uninitialized memory on every sync; any other unpublished buffer now raises (3).
- **Why copy every value if unpublished keys now raise (3)?** Only vLLM's attention scales need it, but one `_copy_state_dict` is simpler than picking keys and costs 0.2 s per 9 GiB.
- **Why not check parameters only?** That misses persistent buffers (16 `expert_bias_E` in the Kimi K3 debug model) and the tied `lm_head.weight`.
- **Why not raise `recompile_limit`?** That hides the duplicate compiles instead of removing them.

NOTE: a value vLLM sets after `__init__` (e.g. calibrated FP8 KV scales from a `quant_config`) would still be reset on every sync. That isn't reachable today: the generator builds its attention with `quant_config=None`.
NOTE: quantized FSDP weights (e.g. MXFP8) used to get unpinned buffers (the old path treats a tensor subclass as empty); they now get pinned ones. A probe with such a weight loaded the prefetched value exactly, but without the fill copy (2); not run with it.

**Test plan**

- `test_empty_pinned_like_keeps_spec_without_reading_weights`: the old copying path fails it.
- `test_prefetch_model_state_dict_raises_when_a_weight_is_not_published`: fails on main.
- Scales: a GPU probe, not in this PR (~2 min per run, TP1 and TP2): build one engine, fill only the trainer's keys, run the pull, print the scales.
- The thread change has no unit test (the call has no logic). Quick check on a generator run: with `TORCH_LOGS=recompiles`, `grep -c 'GLOBAL_STATE changed: num_threads'` on the log is above 0 on main and 0 here.
