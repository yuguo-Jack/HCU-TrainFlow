# [rl] keep vLLM attention scales across generator weight syncs

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5484) · state: open · merged: False

## Original PR description

**TLDR:** After the first weight sync, the generator's 32 vLLM attention scales (Qwen3.5-4B) are 0.0 instead of 1.0. Nothing reads them today because the KV cache is bf16, but an FP8 KV cache would divide by 0. This PR keeps every key the trainer doesn't publish at the value it has after model init, for 0.2 s more startup.

**Problem**
1. vLLM's `Attention` registers 4 scale buffers per layer: `_k_scale`, `_v_scale`, `_q_scale`, `_prob_scale`. The trainer has none of them.
2. `VLLMModelWrapper.__init__` allocates the pinned CPU receive buffers with `_create_cpu_state_dict`, which does not copy values: a 0-dim tensor becomes `torch.tensor(0)`.
3. TorchStore fills only the keys the trainer publishes (`get_state_dict(..., strict=False)`).
4. The pull loads every key (`load_state_dict(..., strict=True)`), so after the first sync the scales are 0.0.
5. Only FP8 paths read them, and TorchTitan asserts the FP8 KV cache off, so generation is unchanged today.

**Solution**
1. Right after allocating the receive buffers, copy the model's values into them (`_copy_state_dict`). A pull overwrites only the keys TorchStore wrote.
2. `_VLLMAttention._init_self_buffers` sets the scales to vLLM's default 1.0. Without it, step 1 copies 0.0: the scales are built on meta, and vLLM fills them only after `__init__`.
3. Unchanged: the pull path, the TorchStore get, NUMA binding and pinning, GPU memory.

**Results**
```
Qwen3.5-4B-Base, 1x H100, in-process vLLM engine. Fill only the trainer's keys, then run main's pull.
32 attention scales after 1 sync:
  main               0.0
  main + copy only   0.0
  this PR            1.0
  this PR, TP2       1.0 (2 GPUs)
greedy decode before vs after the sync: identical in all runs
startup: +0.21 s for 9.02 GiB (_create_cpu_state_dict already takes 10.8-12.8 s)
```

You may ask:
- Why not load only the keys TorchStore filled? `ts.get_state_dict` returns them, but a generator-only parameter would still be lost: each pull re-allocates the sharded storage without values. The copy keeps parameters and buffers, and the pull stays one `load_state_dict(strict=True)`.
- Why not make the 4 scales non-persistent? That fixes only these 4. The next generator-only buffer would get `torch.empty` memory on every sync.
- Does this hide a renamed trainer key? A generator key the trainer stops publishing now keeps its init value instead of undefined memory. `strict=True` never caught this, since the receive buffers come from the same model.

NOTE: a value vLLM sets after `__init__` (e.g. calibrated FP8 KV scales from a `quant_config`) would still be reset on every sync. Not reachable today: the generator builds its attention with `quant_config=None`.

**Test plan**
- `pytest tests/rl/unit_tests/cpu`: 496 passed, 9 skipped
- GPU probe (not in this PR), ~2 min per run, at TP1 and TP2: build one engine, fill only the trainer's keys, run the pull, print the scales.
