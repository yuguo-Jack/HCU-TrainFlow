# [dist_muon] 5/n Support CP and TP storage-to-compute layouts

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5678) · state: open · merged: False

## Original PR description

Part **5/n** of the Kimi K3 / Dist-MoE training stack. Based on `shuhuayu/k3-dm-stack-04`: the review diff contains only this feature.

## Why

An optimizer matrix can be physically split across both DP and TP while its
update must operate on complete matrices. On a 2 x 2 `dp_shard / tp` mesh,
`(Shard(0), Shard(1))` gives each rank only a row-and-column fragment. A
single-axis transport cannot reconstruct the full matrix for an `Owned()`
update.

## What changed

- Resolve all active storage-to-compute transport axes and bind their exact
  ordered process group before constructing either packed schedule.
- Map contiguous and strided storage runs to logical compute regions, including
  uneven and empty shards. Preserve the upstream balanced compute-region planner
  and outer expert storage domains.
- Provide `redistribution_mesh_axes()` and `build_transport_mesh()` for callers
  that need an explicit transport mesh. Apply the existing DistMuon CTA cap to
  that actual group without changing FSDP groups or adding a new policy.
- Keep Kimi projection layouts intact and avoid mutating an original recipe's
  optimizer when constructing a parallelism variant.
- Preserve TP-local QK-Clip head scales while allowing FSDP shards to split heads; retain the upstream per-row scaling arithmetic.
- Reject an explicit `BucketConfig.mesh` combined with automatic CTA capping rather than replace the caller-owned communicator.
- Delete the superseded storage-shaped mesh helper and migrate its NCCL
  cap/identity/parity tests to the exact transport builder.

## Example

```text
storage mesh: (dp_shard=2, tp=2)
storage: (Shard(0), Shard(1)) for one matrix
compute: {"dp_shard": Owned(), "tp": Owned()}
before: cannot resolve a multi-axis transport
after: one ordered dp_shard_tp group reconstructs the complete matrix,
       updates it once, and restores the original local storage shards
```

## Alternatives considered

Updating TP fragments independently changes Muon's matrix operation. Flattening
a mesh only after schedule binding can leave schedules on an uncapped or
incorrect process group. Model-side conversions put transport ownership outside
the optimizer.

## User-facing changes

| Before | After |
| --- | --- |
| Transport assumes one changing storage axis. | Exact DP/TP transport supports complete-matrix and whole-expert updates. |
| A separate storage-shaped helper caps only FSDP shard children. | The existing DistMuon cap applies to the actual resolved transport group. |
| Shallow recipe variants can mutate shared nested optimizer config. | Variants replace the nested config without modifying the original. |

An explicit combined `BucketConfig.mesh` must use the joined-axis name and
storage rank order. A device-bound world NCCL group requires PyTorch
`ProcessGroupNCCL.Options.lazy_init` for newly inferred combined groups; otherwise
supply an already-built mesh and disable automatic CTA capping. Ordinary
TorchTitan initialization does not bind the world group to a device.

## Numerics

Newton-Schulz arithmetic and optimizer state/update functions are unchanged.
Historical unmocked two-rank Muon/checkpoint tests preserve their original comparisons: whole-matrix parameters use exact equality, while batched BF16 block directions use the existing tolerance (`atol=2e-2`). Both persistent and transient redistribution buffers were covered; these results are not fresh post-rebase runs.
The new DP/TP tests check exact matrix routing, ownership, storage updates and
CUDA-graph replay using a matrix-dependent cumulative-sum mock; they are routing
coverage, not a claim of a full model's Muon convergence.
