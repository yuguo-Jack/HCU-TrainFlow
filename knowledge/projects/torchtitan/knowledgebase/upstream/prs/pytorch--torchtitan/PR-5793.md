Part **14/n** of the Kimi K3 / Dist-MoE training stack. Stacked on
[#5686](https://github.com/pytorch/torchtitan/pull/5686).

## Why

The preceding changes expose Kimi SiTU-GLU experts and their native Dist-MoE
pipeline lifecycle, but debug recipes do not demonstrate the full-model
parallelism, memory policy, and dependency contract together. Add two public
text-only 93-layer MXFP8 recipes matching validated 4K source workloads:
256 GB300 with PP4/VPP2 and 512 GB200 with PP8/VPP1.

**Example.**

```bash
# After installing the documented native dependencies and tokenizer assets:
python -m torchtitan.train --module torchtitan_recipes.models.kimi_k3 \
  --config kimi_k3_dist_moe_mxfp8_gb300_256
# For the 512-worker launcher, select:
# --config kimi_k3_dist_moe_mxfp8_gb200_512
```

Use the ordinary multi-node launcher; these commands select configurations,
not provision hardware. The guide supplies the process-level NCCL/allocator
settings.

## What changed

| Recipe | PP / VPP / DP / CP / TP / EP | Rows x context | Microbatches / update | Global tokens / update |
| --- | --- | --- | ---: | ---: |
| `kimi_k3_dist_moe_mxfp8_gb300_256` | 4 / 2 / 64 / 1 / 1 / 64 | 1 x 4096 | 32 | 8,388,608 |
| `kimi_k3_dist_moe_mxfp8_gb200_512` | 8 / 1 / 64 / 1 / 1 / 64 | 1 x 4096 | 64 | 16,777,216 |

- Both use Interleaved1F1B, one schedule call per update, CUDA-graph
  forward/backward replay, fixed 32-document metadata, twelve updates, and
  selective profiling on one rank per PP stage.
- Keep FP32 resident parameters, optimizer state, gradient accumulation and
  reduction. Dense/shared and FSDP parameter compute views are BF16; only
  routed-expert GEMMs use fast-math MXFP8 E4M3.
- Select the native Dist-MoE transform before graph configuration validation.
  Preserve eight explicit original-layer chunks, including VPP1 on 512 workers.
- Apply the native PP backward-reshard/current-stream policies through a small
  recipe-specific model subclass. Keep the explicitly fused Attention Gym KDA
  core through a private recipe kernel config, rather than changing core APIs.
- Phase forced expert IDs by EP source so a partial round-robin cycle remains
  balanced. Scores and their gradients stay learned; no tokens are dropped.
- **Mechanical:** move the three existing Kimi DistMuon mesh/alignment/build
  helpers into `torchtitan_recipes.models.dist_muon`; migrate the existing debug
  recipes and GPU-test imports to their shared owner.

The 256-worker policy reshards after forward and backward, keeps two local
chunks available, uses optimizer-only CTA cap 1, and retains selected late KDA
cores/projections and shared-expert projections. The 512-worker policy retains
its one local chunk, uses CTA cap 8, and adds no outer remat saves. Native decoder
backward prefetch remains enabled; neither recipe uses the removed 2/n policy.
Dist-MoE owns expert recomputation with activation factor `None`, scratch
factor `1.0`, and VMM factor `None`. Optimizer steps are not CUDA-graphed.

## Dependencies and unsupported modes

The native Dist-MoE source checked here is public commit
`285763b5a0e01059a62c96b0990754a60a6ed94a`, using
`situ_glu_gate_beta` and `situ_glu_up_beta`.

The reproducible PyTorch source basis is the public memory-policy stack at
[`836e2870159`](https://github.com/shuhuayu/pytorch/tree/836e2870159a81601cff37d8a00b71381e17dab4)
**plus** public cleanup commit
[`f722f226bbc`](https://github.com/pytorch/pytorch/commit/f722f226bbcebd522c6fec3bc463b21df273cb7e)
([#199884](https://github.com/pytorch/pytorch/pull/199884)).
Apply the cleanup commit before building, or use an equivalent revision. Both
factories reject a missing native cleanup API; the 256-worker factory also
rejects missing native backward-reshard/current-stream APIs instead of
silently changing memory policy.

These are **forced-routing performance controls**, not learned-routing
pretraining recommendations. Learned expert choices require a separately
validated scratch budget. Public C4 replaces a deployment-specific source;
tokenizer assets remain user-provided.

## Alternatives considered

- Copying an experimental trainer/communication stack would duplicate native
  integration; these recipes consume the existing model, transform, and engine.
- Replacing the source KDA core with automatic hardware-based selection changes
  the workload; its explicit fused core stays private to the recipes.
- A generic pipeline-policy abstraction is unnecessary for two consumers of
  already-existing native PyTorch APIs.

## Numerics and testing

Fresh retained-parent validation: **178 CPU tests** and **seven existing
GPU-0-only Kimi tests** pass.

```bash
CUDA_VISIBLE_DEVICES='' python -m pytest -q -o addopts= --tb=short \
  tests/unit_tests/cpu/recipes/test_kimi_dist_moe.py \
  tests/unit_tests/cpu/recipes/test_kimi_dist_muon.py \
  tests/unit_tests/cpu/models/kimi_k3 \
  tests/unit_tests/cpu/models/common/test_dist_moe.py \
  tests/unit_tests/cpu/test_trainer.py \
  tests/unit_tests/cpu/distributed/test_activation_remat.py

CUDA_VISIBLE_DEVICES=0 python -m pytest -q -o addopts= --tb=short \
  tests/unit_tests/gpu/models/kimi_k3/test_kimi_k3.py
```

The existing KDA recurrence test passes with its unchanged tolerances for the
recipe's fused core. Five changing-input graph replays match the native fused
core exactly in output and all seven input-gradient families.

The public-equivalent Python schedule source passes its existing cleanup
regression and eight exact one-GPU FP32/BF16 eager/graph probes, with startup
release on/off and five changing-input updates. This verifies Python source/API
equivalence against the installed compiled PyTorch binary, **not a clean
PyTorch build**.

All twelve isolated FakePG/meta PP-coordinate construction checks pass:
four coordinates with two local stages on 256 workers, and eight with one
local stage on 512 workers. These checks verify original layer FQNs and
stage ownership; they do not measure HBM or collective throughput.
All non-type hooks pass. The unchanged type error in
`torchtitan/components/data/multimodal/utils/video.py:114` also reproduces on
the clean upstream base; no new type error was introduced.

## Performance evidence and remaining validation

The source workloads completed twelve updates at **1,079 tokens/s/GPU**
(256 GB300, 255.64 GiB maximum PyTorch reservation) and
**1,009.5 tokens/s/GPU** (512 GB200, 158.41 GiB maximum reservation).
These are historical source-workload results, **not fresh measurements of this
public port or total-device memory**, and not a matched-data convergence test.

Fresh full-scale distributed throughput/memory, learned routing, checkpoint
resume, a clean dependency build, full CI, and maintainer review remain landing
gates.
