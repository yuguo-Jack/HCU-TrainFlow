# [distributed] Isolate FSDP from CP's default-group reuse to prevent a deadlock

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5645) · state: closed · merged: False

## Original PR description

## Bug

`DeviceMesh._init_one_process_group` reuses the default (WORLD) process group -- instead of creating a dedicated communicator -- for any mesh dimension (including one produced by `DeviceMesh._flatten`) whose ranks span every rank, as long as no explicit `backend_override` is given.

FSDP shards parameters on `dp_shard * cp`. When `dp_shard == 1` (a pure-CP configuration, e.g. `cp == world_size`), that flattened axis spans every rank -- and so does CP's own `cp` axis. Both silently collapse onto the same WORLD process group / NCCL communicator. `dp_replicate` (pure DDP spanning the world) and `edp_shard` (EP with no other sparse-region parallelism) have the same failure mode on their own single axis.

FSDP issues its all-gather/reduce-scatter from its own dedicated CUDA streams, while CP's collectives run on the default/compute stream. Nothing orders those two streams against each other, so the two collectives can be enqueued in different host-side orders across ranks. Two collectives sharing one communicator must be posted in the same order by every rank, so a mismatched order deadlocks NCCL instead of merely serializing. Whether the groups collide is config-deterministic, but the deadlock itself is a scheduling race -- which is why it does not reproduce on every run.

## Fix

Give FSDP's shard/replicate axes a dedicated `backend_override` so they never alias the default group:
- `dp_replicate` and `edp_shard` are built directly by `ParallelismContext.build_mesh`'s `unflatten_mesh` closure; give them an explicit override there.
- `dp_shard * cp` is flattened later, inside `resolve_fsdp_mesh`, when passed to `fully_shard` via `DataParallelMeshDims`. Pre-flatten it eagerly there with an explicit override so FSDP2's own (unoverridden) internal flatten just hits the cache we already populated.

The override passed is the mesh's own already-configured backend (`dist.get_backend_config`), so this only changes communicator *identity*, never which backend is used -- real NCCL/Gloo meshes and "fake"-backed test meshes behave the same as before, just with a dedicated communicator.

## Tests

Added `TestFsdpCpCommunicatorIsolation` to `tests/unit_tests/cpu/distributed/test_parallelism_context.py` (CPU/fake-mesh, no GPU needed):
- `test_pure_cp_fsdp_group_is_not_shared_with_cp_group`: `dp_shard=1, cp=4` -- the historically-buggy configuration -- asserts FSDP's shard group and CP's group have different `group_name`s. Fails on `main` with `AssertionError: AssertionError not raised`, confirming the two groups collide today.
- `test_pure_ddp_dp_replicate_group_is_dedicated`: `dp_replicate=4` (pure DDP spanning the world) asserts its group differs from the default group.

Ran the full existing `tests/unit_tests/cpu/distributed/` suite (163 tests) to confirm no regressions.

@fegin This is race condition so it's extremely hard to reproduce. The hang happens since FSDP all-gather is scheduled on a different stream than our CP communication. This cause indeterministic ordering on the GPU kernel execution order. For example, rank0 can execute CP comm first, while rank1 can execute FSDP all-gather since there's no cross-rank order synchronization. 

I added a simple local repro that forces this misalignment in ordering across rank through the host. W/ shared communicator, we reproduce the deadlock issue. W/ separate pg, all ranks can complete.
