# [moe][perf] Gather-based dispatch backward and combine under local compile

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5160) · state: open · merged: False

## Original PR description

**TLDR:** under the `moe_dispatch_combine` region, MoE combine becomes one fused fp32 gather per token and both backwards become gathers: DSv3 16k step -6.4%.

**Problem**
1. **Combine today.** Multiply `[R, D]` expert rows by scores in fp32, then `deterministic_scatter_add` (a sort-based accumulating `index_put`).
2. **Dispatch backward.** Another accumulating `index_put`.
3. **Cost.** ~16 ms per MoE layer at 16k vs ~1.5 ms ideal. Op level: combine 13.47 ms, dispatch 3.39 ms.

**Solution**
1. **Gather-sum.** Under compile, combine sums each token's K rows (score-weighted, fp32, top-k order) in one fused gather kernel.
2. **Backwards are gathers** for both the dispatch gather and the combine.
3. **Row order.** Each token's rows come from the inverse of the expert sort `_local_reorder` already runs: one scatter, stored in the dispatch metadata, returned through AllToAll's `_dispatch` remat region.
4. **Gate.** Eager is unchanged behind `is_compiling()`: the unfused gathers are slower in eager. Eager path is upstream's `_score_and_combine`.
5. **Enabled** in `DeepSeekV3Model.Config.local_compile_regions`.

```text
before:  y[R,D] * score (fp32) --deterministic_scatter_add--> out[T,D]
after:   out[t] = sum_k score[t,k] * y[row(t,k)]   (one fused gather, fp32, top-k order)
```

You may ask:
- Why not compile combine as written? 4.4 vs 1.4 ms op level.
- Why not a plain compiled gather with autograd's backward? Its backward is an `index_put`: 7.4 ms.
- Why not apply scores inside SwiGLU? Under all-to-all EP the scores live on the source rank.

NOTE:
- Reaches every recipe built from the DSv3 model config: deepseek_v3_671b, 16B/236B flavors, Kimi K2.x (inherits the config). Local, AllToAll and TorchAO (EP=1) dispatchers; not Dist-MoE/DeepEP/HybridEP.
- Not tested: multi-GPU EP (the AllToAll combine relies on the combine all-to-all returning rows in sent order), GraphTrainer, CUDA graphs, loss curves, H100.
- The Kimi K3 stack carries a variant of this change; land one.

Rejected:
- scores inside SwiGLU: under all-to-all EP the scores live on the source rank
- gather form in eager: combine 20.7 vs 13.5 ms, dispatch bwd 7.1 vs 3.4 ms, so gated on `is_compiling()`
- real-arithmetic RoPE: ties complex RoPE with ConcatKernel (53.35 vs 53.48 ms per attention module)
- gate/up packed + unbind in a region: 2.26 vs 2.30 ms at 16k, worse at 4k
- RMSNorm, residual adds, unbind stacks: each < 1%

Compile limits hit:
- Per-block compile inlines flex attention and drops its max_autotune options: attention 82 -> 105 ms at 16k. Attention stays outside regions.
- A region returning a strided view (`v = kv[..., 128:]`) gets its grad from flex in another layout; AOTAutograd copies it first (556 us): return v dense under compile (PR 2).
- `torch.topk` is an ATen fallback in Inductor: the router uses masked argmax rounds under compile (PR 4).
- Inductor has no codegen for complex multiply: RoPE's `q_pe * freqs_cis` stays an ATen kernel inside the `mla_qk` region (2 x 212 us at 16k). Real arithmetic (#5196) plus plain cat lowering takes the layer 46.34 -> 45.85 ms (PR 2, second commit).

Not tested: multi-GPU EP, GraphTrainer, CUDA graphs, loss curves, H100, TorchAO/MXFP8, full AC, MTP/loss paths.
