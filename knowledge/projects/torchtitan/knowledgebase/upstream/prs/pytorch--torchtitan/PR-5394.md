# Add optimizer-owned gradient clipping extension point

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5394) · state: open · merged: False

## Original PR description

## Summary

- add a configurable `GradientClipper` interface owned by the optimizer component
- make the default `GradientClipper` preserve the existing `dist_utils.clip_grad_norm_` behavior
- default `Optim.Config.gradient_clipper` to `GradientClipper.Config()` and build it once for the optimizer lifetime
- share clipping dispatch with specialized optimizer update paths

## Motivation

Gradient clipping operates on optimizer-owned mutable gradient state, but there is no scoped component seam for an out-of-tree device backend to provide its own implementation. This change makes that behavior explicit in optimizer configuration without replacing the eager utility process-wide.

For example, on accelerators where op-by-op execution is expensive, a backend can compile the local norm calculation and gradient scaling into a device program, cutting repeated per-step dispatches and temporary allocations.

`local_compile_regions` is not the right extension point because gradient clipping is configured and invoked by the optimizer and operates on global gradient state across model parameters and distributed meshes. Treating it as a model compile region would couple optimizer behavior to model configuration.

Backend-specific implementations remain outside TorchTitan core.

## User story: integrate an out-of-tree device backend

An out-of-tree accelerator backend can supply a gradient clipping implementation that, for example, compiles its local norm and scaling work while retaining the backend-specific distributed behavior it needs. Its integration package supplies a concrete `GradientClipper` component and opts in through optimizer configuration:

```python
config.optim.gradient_clipper = DeviceGradientClipper.Config()
```

The optimizer constructs the configured component once and uses the same dispatch from its standard and specialized update paths. Without an override, the built-in `GradientClipper` retains the existing eager gradient clipping behavior.

## Related work

Open PR #4709, "Make Trainer gradient clipping overridable," addresses the same extensibility need at the former `Trainer.train_step` call site. This PR follows the current ownership boundary by placing the extension point on `Optim`, which owns the gradient state and update paths, and shares it with specialized optimizer paths such as TorchFT.
