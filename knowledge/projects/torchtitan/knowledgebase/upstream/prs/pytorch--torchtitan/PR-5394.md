# Add optimizer-owned gradient clipping extension point

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5394) · state: closed · merged: True

## Original PR description

## Summary

- add a configurable `GradientClipper` interface owned by the optimizer component
- make the default `GradientClipper` preserve the existing `dist_utils.clip_grad_norm_` behavior
- default `Optim.Config.gradient_clipper` to `GradientClipper.Config()` and build it once for the optimizer lifetime
- share clipping dispatch with specialized optimizer update paths

## Motivation

Gradient clipping operates on optimizer-owned mutable gradient state, but there is no scoped component seam for an out-of-tree device backend to provide its own implementation. This change makes that behavior explicit in optimizer configuration without replacing the eager utility process-wide.

For example, on accelerators where op-by-op execution is expensive, a backend can compile the local norm calculation and gradient scaling into a device program, cutting repeated per-step dispatches and temporary allocations.

`local_compile_regions` is not the right extension point because gradient clipping is configured and invoked by the optimizer and operates on global gradient state across model parameters and distributed meshes. Treating it as a model compile region would couple optimizer behavior to model configuration.

Backend-specific implementations remain outside TorchTitan core.

## User story: integrate an out-of-tree device backend

An out-of-tree accelerator backend can supply a gradient clipping implementation that, for example, compiles its local norm and scaling work while retaining the backend-specific distributed behavior it needs. Its integration package supplies a concrete `GradientClipper` component and opts in through optimizer configuration:

```python
config.optim.gradient_clipper = DeviceGradientClipper.Config()
```

The optimizer constructs the configured component once and uses the same dispatch from its standard and specialized update paths. Without an override, the built-in `GradientClipper` retains the existing eager gradient clipping behavior.

## Related work

The PR in its current state (`58030b4`) addresses all three of your last review points:
- the thin `_clip_grad_norm` helper is removed;
- `GradientClipper` now exposes an explicit `clip_grad_norm_` method instead of `__call__`;
- the extra `isinstance`/`ndim` checks are gone.

The default clipper also defaults to `GradientClipper.Config()` and keeps the current eager behavior, as you asked earlier.

### Default behavior
- `GradientClipper.clip_grad_norm_` (`torchtitan/components/optim/optim.py:39-58`) makes the same call as before: `dist_utils.clip_grad_norm_(params, max_norm, foreach=True, pp_mesh=ctx.get_optional_mesh("pp"))`. With no override, the numerics shouldn't change.
- The clipper is built once in `Optim.__init__`, before the CUDA graph wrapper is set up. `_update` calls it, so clipping stays inside the captured region, same as before.
- `gradient_clipper` uses `field(default_factory=GradientClipper.Config)`, and `field` is already imported.

### Callsites
- The only places that used to call `dist_utils.clip_grad_norm_` with `max_norm` were `Optim._update` and `TorchFTOptim._update`. Both now go through `self.gradient_clipper`, and `torchtitan/experiments/torchft/optimizer.py` no longer imports `dist_utils`. The remaining direct callers are tests of the utility itself: `test_distributed_utils.py` and `gpu/.../test_fsdp_moe_sharding.py`.
- Every recipe builds `Optim.Config(...)` or `TorchFTOptim.Config(...)` through the config, so they all get the default clipper. That includes llama3, qwen3, deepseek_v3, flux, muse_glimmer, the RL recipes, torchft and the transformers backend.
- Three tests skip `__init__` with `object.__new__(Optim)`: `test_trainer.py:771`, `test_invalid_loss.py:62` and the new one in `test_optim.py`. All three now set `optim.gradient_clipper`.
- The TorchFT `_optim()` test helper goes through `config.build(...)`, so the existing non-finite step tests get the default clipper.

### Nits (optional, not blocking)
1. **Docstring:** the `clip_grad_norm_` docstring (`optim.py:46-52`) mixes what the default does ("use `foreach=True` and the PP mesh") with what overrides must guarantee (scalar, same value on every rank, keep NaN/Inf, don't reuse the result as scratch). Splitting those would make it clearer what a custom clipper has to honor, which matters because `_update` feeds the norm into the finite check and the CUDA graph output.
2. **Redundant `__init__`:** `GradientClipper.__init__` only does `self.config = config`. That matches the pattern in other `Configurable` classes, so it's fine to keep.

The approval still stands from my side. Before merge, it's worth confirming that CI (`ciflow/fake-pg` plus the CPU unit tests) runs green, since I couldn't run the tests here.
