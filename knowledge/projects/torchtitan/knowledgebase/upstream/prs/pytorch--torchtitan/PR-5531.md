# [rl] Size generator max_num_seqs for every rollout sequence

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5531) · state: open · merged: False

## Original PR description

## Summary

`max_num_seqs` is vLLM's cap on concurrently running sequences per engine. Requests above it wait in vLLM's queue even when the KV cache has room. The controller sized each generator DP rank's cap at the even share, `ceil(rollout_concurrency / (num_generators x dp_degree))`. Sticky routing keeps a session on its generator and DP rank until that rank passes `repin_load_ratio` x the mean load, so ranks regularly run above the even share and queue requests while sibling ranks have free slots.

This PR sets the cap to `min(rollout_concurrency, 512)`. No rank can ever hold more than every in-flight rollout sequence, so the cap no longer binds before the KV budget, and the value does not depend on the routing strategy. The 512 cap is unchanged from main.

For 80 concurrent sequences over 4 generators x DP 4, the cap changes from `ceil(80 / 16) = 5` to 80.

The previous revision multiplied the even share by `repin_load_ratio` for each routing layer (5 -> 12). That value is an upper bound only under extra assumptions: a least-loaded fallback, and no generator draining with `hot_swap=False`. The measurements below show a larger cap costs little, so exact sizing is not worth those assumptions.

## Cost of a larger cap

`max_num_seqs` sizes three things in vLLM:
- per-request buffers, including a host token buffer of `max_num_seqs x max_model_len`;
- the sampler warmup during memory profiling, which comes out of the KV budget;
- CUDA graph capture sizes.

In the default `FULL` mode the capture cap is already `max(max_num_seqs, max_num_batched_tokens)`, so `max_num_seqs` adds one capture size.

Generator startup with Qwen3-0.6B, TP4, `FULL` CUDA graphs, standalone `torchtitan.rl.generate`:

```
max_num_seqs      5        12       48       64       96       512
A100  init       19.3 s   18.0 s   18.5 s   18.4 s   18.6 s   18.6 s
A100  KV cache   70.22    69.81    69.71    69.70    69.61    68.92 GiB
GB300 KV cache   245.91   245.97   245.93   245.91   245.83   245.09 GiB
```

Graph capture took 4-5 s on A100 and 13-18 s on GB300 at every value. GB300 init varied between 33 and 85 s from run to run, with no trend in `max_num_seqs`. A100 at 80 is missing; see below.

## Evidence for headroom

In a multi-turn SWE agent run with 80 sessions over 4 generators x DP 4, all ranks reached the old cap of 5. In 78 of 218 waiting-gauge samples, a sibling rank of the same generator was below the cap. Generator queue time reached 1.4 s mean and 33 s max per call.

A step-1 A/B with similar response lengths raised the cap from 5 to 12:
- queue time mean/max: 1,685 ms / 40 s -> 2 ms / 0.26 s;
- time to first token: 1.88 s -> 0.24 s;
- inter-token latency: 38.7 ms -> 43.7 ms, as busy ranks ran larger batches;
- per-call time: about unchanged (13.8 s vs 13.5 s).

That runtime's sticky routing did not repin, so the A/B shows the cost of a binding cap under skew. It is not an end-to-end throughput result.

## CI failure on the previous revision

The previous revision failed `rl_grpo_checkpoint_resume` on A10G with an illegal memory access.
- **Cause:** a FlashAttention-2 bug, Dao-AILab/flash-attention#3117. FA2 handles paged KV with its split-KV kernel. That kernel's early exit, for a row block with no visible keys, writes `softmax_lse` with the padded layout, which runs out of bounds for varlen + paged KV.
- **How CI reached it:** vLLM's CUDA graph memory profiling runs a dummy batch with `seq_len = 1` for every request, splitting 2048 query tokens across `max_num_seqs` requests. Any dummy request with 65 or more query tokens reaches the early exit.
- **Which phase:** the test's save phase (2 generators x TP2) got `max_num_seqs = 48`, so 2048 / 48 leaves 74 tokens for the last request. Main gives 32 (64 tokens each) and this revision gives 64 (32 each), so neither reaches it.
- **Reproduction on A100** with that generator config: 48 crashes, while 32 and 64 start. FA4 on GB300 starts at every value, including 80.

The bug is not fixed here. On FA2 GPUs, any `max_num_seqs` that leaves a dummy request with 65+ query tokens writes out of bounds during profiling. On main that includes the 8 and 22 values of some CI configs, where the writes land in mapped memory and do not crash.

Re @tianyu-l's question about a proof: the formula is an upper bound, but only under assumptions that neither the code nor the docstring states. The argument should be in the docstring.

Per layer, with N candidates and at most C requests in flight in total: load only grows on admission. `StickySessionRoutingStrategy.choose` (strategies.py) keeps a session on its pinned candidate only while `load_before <= r * mean_before`. Because `mean_before <= (C-1)/N`, the load after admission is at most `floor(r*(C-1)/N) + 1`, which is `<= ceil(r*C/N)` when `r/N <= 1`. The least-loaded fallback admits at `load_before <= mean`, so it stays inside the same bound. Composing the two layers (generator load `L_g <= ~r1*C/G`, then a DP rank `<= ~r2*L_g/D`) gives about `r1*r2*C/(G*D)`, up to rounding. I checked some small cases by hand and the ceil absorbed the rounding. I haven't proven that it always does.

The bound depends on assumptions that can fail:
1. **The mean is taken over the candidates present at that moment, not all N.** With `hot_swap=False`, a draining generator leaves `_candidates()` (inter_generator.py:119). While k generators are out, the others' mean is `C/(G-k)`, so the bound becomes `r*C/(G-k)` and the cap is exceeded. Either say the bound is for the full candidate set, or note it in a TODO next to #5253.
2. **Total in flight <= `rollout_concurrency`.** This needs one in-flight `generate` per rollout, and validation must not overlap training rollouts, since `rollout_concurrency` is `max(...)`, not a sum.
3. **`r/N <= 1`.** `repin_load_ratio=3` with 2 DP ranks breaks the `floor(...)+1 <= ceil(...)` step.

As written, the docstring says a candidate can run that far "before sessions move". That describes the threshold, not a bound on load.
