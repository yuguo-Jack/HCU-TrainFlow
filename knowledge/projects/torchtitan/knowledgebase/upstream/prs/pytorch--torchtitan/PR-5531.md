# [rl] Size generator max_num_seqs for sticky-routing peak load

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5531) · state: open · merged: False

## Original PR description

## Summary

The controller currently sizes each generator DP rank's `max_num_seqs` for a perfectly even share of rollout concurrency. Both routing layers default to sticky sessions with `repin_load_ratio=1.5`, allowing a session's generator and DP rank to stay above the mean in-flight load before routing moves it. A cap at the even share can therefore queue requests inside vLLM while sibling ranks still have available slots.

Size the cap for the configured repin threshold of each routing layer with multiple candidates. For 80 concurrent sequences across 4 generators x 4 DP ranks, this changes the cap from `ceil(80 / 16) = 5` to `ceil(80 x 1.5 x 1.5 / 16) = 12`. Single-candidate layers do not contribute a multiplier; non-sticky routing and sticky routing without a repin threshold retain the previous sizing. The latter has no finite skew bound, so this change does not solve arbitrary imbalance when repinning is disabled. The cap remains at 512, and the KV budget can still limit admission.

This is capacity headroom for the existing routing policy, not a routing-policy change. Better balancing of live sessions across DP ranks is a separate improvement.

## Evidence

In a multi-turn SWE agent run with 80 sessions over 4 generators x DP 4, all ranks reached the old cap of 5; 78 of 218 waiting gauge samples had a sibling rank of the same generator below the cap. Generator queue time reached 1.4 s mean and 33 s max per call.

In a step-1 A/B with similar response lengths (316 versus 311 tokens), increasing the cap from 5 to 12 reduced mean/max queue time from 1,685 ms / 40 s to 2 ms / 0.26 s and time to first token from 1.88 s to 0.24 s. Inter-token latency increased from 38.7 ms to 43.7 ms as busy ranks ran larger batches; total per-call time remained roughly unchanged (13.8 s versus 13.5 s). The benefit established here is removal of long queue waits, not higher end-to-end RL throughput.

The A/B used a Muse Spark runtime where sticky routing did not repin, so it demonstrates the effect of capacity headroom under skew, not a direct performance A/B of upstream's merged repinning behavior.

## Tests

- 75 controller and routing CPU tests passed, including tests for default two-layer sizing, independent routing strategies, single-candidate layers, alternative strategies, and the 512 cap. The local test environment required a process-local compatibility shim for an older TorchStore export; no production code was modified for this.
- `pre-commit run --all-files`: all available hooks passed. The Pyrefly hook could not run because its executable is not installed locally; RL is excluded from this repository's Pyrefly project. CI should validate it.

No GPU throughput or memory-capacity comparison was run for this patch. Larger `max_num_seqs` can change batching and CUDA graph capture sizes, so KV capacity and model-specific memory should be checked in integration runs.
