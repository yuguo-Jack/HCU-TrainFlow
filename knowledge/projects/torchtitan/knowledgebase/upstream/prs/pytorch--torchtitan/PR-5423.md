# [CI Fix] Refresh MI350X goldens for FP32 first-WGRAD accumulation

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5423) · state: closed · merged: True

## Original PR description

ROCm model/SFT numerical checks still use MI350X goldens from before #5399. That change produces the first accumulated WGRAD directly in the parameter's FP32 gradient dtype instead of rounding through BF16, and refreshed the A10G goldens only.

Refresh the nine MI350X Real-PG golden files used by ten integration configurations. Values come from full-precision TensorBoard scalars in [main ROCm CI](https://github.com/pytorch/torchtitan/actions/runs/38753451439), using `torch==2.16.0.dev20261015+rocm10.0`. Preserve the existing ten-step coverage, parallelism/config metadata, and strict loss/gradient-norm equality checks. The two Llama3 configurations sharing one golden produce identical values.

Validation in progress:

- Extracted and checked both metrics for all ten steps in every affected configuration.
- All nine model configurations match bitwise across two independent main CI runs (`38753451439` and `38778179164`), covering both metrics at every step.
- Changed-file pre-commit checks passed. Full-tree pre-commit passed except for 54 existing local Pyrefly dependency/type errors; unrelated automatic edits were reverted.
- A controlled ROCm run restores only the pre-#5399 Linear implementation while pinning the failing nightly. This checks whether the old goldens still pass with the old WGRAD math, separating the computation change from the nightly update: https://github.com/pytorch/torchtitan/actions/runs/38787345295
- Full ROCm verification of the updated goldens is queued: https://github.com/pytorch/torchtitan/actions/runs/38787809162 . Keeping this PR in draft until the control and verification checks finish.
