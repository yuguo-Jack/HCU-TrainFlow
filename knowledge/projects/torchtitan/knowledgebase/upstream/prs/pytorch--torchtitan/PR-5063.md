# [TorchTitan] Tell to_hf and from_hf when an HF load is quantized

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5063) · state: closed · merged: True

## Original PR description


Summary:
An HF load calls `to_hf` on the destination state dict to get the keys to
read. Some quantized checkpoints store a tensor under a different name than
the unquantized checkpoint does: compressed-tensors MXFP4 (Kimi K3) stores
`X.weight_packed` and `X.weight_scale` where the bf16 checkpoint has
`X.weight`. The adapter has no way to tell which one is being read.

This adds keyword-only `to_hf(state_dict, *, to_quantized_layout=False)` and
`from_hf(hf_state_dict, *, is_quantized_layout=False)` to the state dict
adapter protocol, and the DCP load passes its `from_quantized` to both.
`to_quantized_layout` makes `to_hf` return the quantized checkpoint's key
names; only the names change, and no values are quantized. The storage reader
then fills those entries with dequantized tensors, so the dict `from_hf`
receives is in the quantized checkpoint's layout without being quantized, and
`is_quantized_layout` tells `from_hf` to read the names `to_hf` chose instead
of inferring the format from the keys. These are per-call
arguments rather than adapter state because the same adapter also converts
state dicts for HF saves, RL weight sync, and the conversion scripts, which
always want unquantized names.

Every in-tree adapter accepts both arguments:
- DeepSeek V4 and Kimi K2.7 wrap DeepSeek V3 and forward them.
- DeepSeek V3 and GPT-OSS, which already load quantized checkpoints, ignore
  them for now.
- Adapters that cannot load a quantized checkpoint (Flux, Llama 3, Qwen3,
  Qwen3.5, Muse Glimmer, Kimi K3 and the HF transformers backend) raise
  `ValueError`. Before, the base storage reader only logged a warning and
  read the checkpoint as unquantized.

The `torch_checkpointing` HF load path is left alone for now.

Test Plan:
```
pytest -q tests/unit_tests/cpu/components/checkpointer/test_checkpoint.py tests/unit_tests/cpu/models/test_state_dict_adapter.py tests/unit_tests/cpu/components/checkpointer/test_torch_checkpointing.py
SKIP=lychee-link-checker pre-commit run --files <changed files>
```
128 passed, and pre-commit passes. The new
`test_quantized_hf_load_requests_quantized_names` checks that a quantized DCP
load calls `to_hf(..., to_quantized_layout=True)` and
`from_hf(..., is_quantized_layout=True)`. The new
`test_adapters_without_quantized_loads_reject_quantized_layout` checks that the
Flux, Llama 3 and Qwen3 adapters raise for both, and fails if the Flux check
is removed.

### Naming suggestion for the `to_hf` / `from_hf` quantized flag

- [x] Read the diff (`models/base/state_dict_adapter.py`, `components/checkpointer/dcp.py`, the adapter overrides)
- [x] Read the review discussion
- [x] Write up a recommendation

**Recommendation: give both methods the same keyword-only name, and have it describe the HF checkpoint rather than a direction. My pick is `hf_quantized`.**

```python
def to_hf(self, state_dict, *, hf_quantized: bool = False) -> dict[str, Any]: ...
def from_hf(self, hf_state_dict, *, hf_quantized: bool = False) -> dict[str, Any]: ...
```

```python
# dcp.py
hf_state_dict = self.sd_adapter.to_hf(state_dict, hf_quantized=from_quantized)
...
state_dict = self.sd_adapter.from_hf(hf_state_dict, hf_quantized=from_quantized)
```

#### Why one name instead of a `to_*` / `from_*` pair

1. **The flag describes the same thing in both calls.** The method name already gives the direction. The flag only says which layout the HF side uses: a quantized checkpoint (`X.weight_packed` / `X.weight_scale`) or a bf16 one (`X.weight`). A `to_`/`from_` prefix repeats the direction, and on `to_hf` it suggests the method writes quantized values. That reading confused things earlier in this thread, and none of `to_quantized`, `to_quantized_keys` or `from_quantized` avoids it.
2. **The two values must always match, and one name says so.** The current `from_hf` docstring has to explain *"pass the `to_quantized_keys` value that `to_hf` was called with"*. With a shared name, that rule is obvious.
3. **It matches existing naming.** The user-facing config is already `initial_load_in_hf_quantized`, so `hf_quantized` is the same idea. `get_hf_storage_reader(..., from_quantized)` can keep its name, because a *reader* does read *from* the checkpoint, so the direction is accurate there.
4. **It avoids "quantized keys".** @tianyu-l is right that keys aren't quantized; tensors are. @ivy-zhou's point that only the *names* follow the quantized layout, while dequantization happens in the storage reader, belongs in the docstring, which already says it well. Put descriptions in docstrings, not in names (CLAUDE.md).

If you want the name itself to stress "names only", the next best option is `hf_quantized_layout`. It's longer but still direction-neutral. I'd steer away from `*_keys` and from `to_`/`from_` prefixes.

#### Small related nit: make it keyword-only

CLAUDE.md prefers keyword-only arguments after the first positional one. Right now some callers pass the flag positionally, for example `super().from_hf(lm_hf, from_quantized_keys)` and `super().to_hf(lm_titan, to_quantized_keys)` in `kimi_k2_7/state_dict_adapter.py`, and the same pattern appears in DeepSeek V4. Adding `*` to the signatures makes every call site name the flag explicitly. That matters for a bool, and it prevents mistakes if more parameters are added later.

#### Suggested docstrings (ASCII only)

```python
hf_quantized: Whether the HF state dict uses the tensor names of a
    quantized HF checkpoint (e.g. ``weight_packed`` / ``weight_scale``
    instead of ``weight``). Only the names differ; values are never
    quantized here, and on load the storage reader dequantizes them.
    Adapters whose quantized and unquantized checkpoints share names
    can ignore this.
```

I haven't pushed any code changes; this is only a suggestion. If you go with it, the rename affects all 15 files in the PR, plus the test names and the PR description. Mention me if you'd like me to apply it.
