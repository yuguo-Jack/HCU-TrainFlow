# [data] Keep packed token positions across row boundaries

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5756) · state: closed · merged: False

## Original PR description

## Summary (human-written)
<!-- Write this yourself, not with an AI tool. 2-5 sentences: the problem, why
     this approach, and what you checked yourself. -->

## Why

Packed position ids restart at each document start and every `max_context_length` tokens after it. A row can still begin in the middle of that window: a one-token document shifts the concat boundary, or `max_num_documents` ends a row before the window does. Concat-then-split and first-fit then renumbered from the start of the row, and the document-cap iterator always emitted `arange` from 0 for the next slice.

Before, a full row whose real tokens were `[3, 0, 1, 2, 3, 0, 1, 2]` became `[0, 0, 1, 2, 3, 0, 1, 2]`. After, it stays `[3, 0, 1, 2, 3, 0, 1, 2]`. A document-cap row that continues at in-window offset 2 stays `[2, 3, 0, 1]` instead of `[0, 1, 2, 3]`. Rows that already start at 0 are unchanged.

## What changed

- `_packing_output_to_text_sequence` keeps packed positions for real tokens. It still rewrites the padding tail (segment id 0) with `max_context_length`. A real token whose position is 3 is not treated as position 0.
- `_DocumentAwareConcatThenSplitIterator` continues from the source position at the slice start when the sequence has positions, otherwise from `remainder_offset % max_context_length`. The slice is `(arange(n) + base) % max_context_length`, so a slice that crosses the window wraps. `_next_document_chunk_end` still ends a slice on the next explicit position 0.

## Alternatives considered

Do not renumber in the model; the packed tensor is already the position ids.

## User-facing changes

| | Before | After |
| --- | --- | --- |
| Packed row that starts mid-window | First real token forced to position 0 | First real token keeps its in-window offset |
| Packed row that already starts at 0 | Unchanged | Unchanged |
| Padding tail | Positions restart inside `max_context_length` | Same |

No new config or CLI flags.

## Numerics

This changes RoPE positions for packed rows that start mid-window, so loss is not bitwise identical on those batches. Rows that already start at 0 stay the same. No GPU loss run was done.

**Verdict: Request changes** -- There is no bug here on `main`, and this change breaks the rule that every packed row starts at position 0. The varlen and flex mask builders rely on that rule.

**What this PR does.** Today, a packed row that starts partway through a document gets positions that restart at 0 from the row start. This PR keeps the original in-window offset instead, for both concat-then-split and the document-cap iterator.

**Example.** Concat-then-split row 1 from the new test, with `max_context_length=4`:
```
main: positions [0, 0, 1, 2, 3, 0, 1, 2]  -> cu_seqlens [0, 1, 5, 8]  (token 27 is a 1-token segment)
PR:   positions [3, 0, 1, 2, 3, 0, 1, 2]  -> cu_seqlens [1, 5, 8]     (token 27 is in no segment)
```
On `main`, token 27 attends only to itself. Under RoPE, a single token gives the same attention output at position 0 or 3, because RoPE only depends on relative positions. The "wrong" position therefore changes nothing. With the PR, token 27 drops out of the varlen metadata and gets a fully masked row in flex, but its label still counts toward the loss.

### Must fix
1. PR description -- "Summary (human-written)" is empty. The motivation also doesn't hold. Positions within a row's first segment only matter relative to each other, and that segment has no in-row context anyway. `main` already yields segments of at most `max_context_length` that the attention builders handle correctly. The Numerics section credits the loss change to RoPE positions. The actual cause is tokens falling out of the attention metadata.
2. `torchtitan/components/data/packing.py:416` -- Removing the canonicalization leaves the leading tokens outside every varlen sequence and fully masked in flex (inline).
3. `torchtitan/components/data/packing.py:168` -- The same breakage hits the document-cap path, and the wrap also changes how that path chunks a row (inline).
4. `tests/unit_tests/cpu/components/data/test_grain_data.py:2105` -- The new tests assert the broken rows (inline).

### Questions
- Did you see a concrete training problem (loss, throughput, a failing assert) that led to this? If the issue is the 1-token leading fragment in concat-then-split taking up a segment, that's a separate, smaller change to discuss. It must still start every row at 0.

<details><summary>Details</summary>

The rule that a row starts at position 0 is set in `_packing_output_to_text_sequence` (concat-then-split and first-fit) and by `np.arange` in the document-cap iterator. These consumers depend on it:
- `create_varlen_metadata_for_document` (`attention.py:917`): `cu_seqlens` comes from `positions == 0`. With no 0 at index 0, `cu_seqlens[0] > 0` in both the dynamic and fixed-shape (`max_num_documents`) paths. Used by the main varlen attention path, GDN (`gdn.py:334`), KDA (`kda.py:167`), and DSv4 (`deepseek_v4/attention.py:75`).
- `get_efficient_causal_mask_mod_for_packed_document` (`attention.py:809`): `document_id[0] = -1`, and `offsets[-1]` is the `seq_len` fill value, so `kv_idx >= seq_len` masks out every key.
- `get_document_mask_mod` happens to work (doc id -1 matches itself), but the efficient mask is the one the main flex path uses (`attention.py:534`, `:715`).

First-fit is unaffected in practice: `_SplitTextSequenceDocuments` emits chunks that start at 0. Only concat-then-split rows and document-cap continuation rows change.

</details>

This removes the guarantee that every row starts at position 0, and the attention metadata depends on it. Every builder takes `positions == 0` as a segment start (`attention.py:799`, `:827`, `:950`):

- varlen (`create_varlen_metadata_for_document`): for `[3, 0, 1, 2, 3, 0, 1, 2]` you get `doc_starts = [1, 5]`, so `cu_seqlens = [1, 5, 8]`. Token 0 is in no sequence, so its attention output is never written, but its label still counts toward the loss. The fixed-shape `max_num_documents` path also puts 1 in `cu_seqlens[0]`. GDN/KDA (`gdn.py:334`, `kda.py:167`) and DSv4 use the same metadata.
- flex (`get_efficient_causal_mask_mod_for_packed_document`): `document_id[0] = -1`, so it reads `offsets[-1] == seq_len` and token 0 can attend to nothing (a fully masked row).

The `[0, 0, 1, 2, ...]` this hunk removes is what keeps a row's leading fragment valid. Please keep the canonicalization.
