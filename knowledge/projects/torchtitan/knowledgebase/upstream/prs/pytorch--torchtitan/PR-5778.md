# [rl] Select TorchStore's control plane and run the RL loss guard on its service

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5778) · state: open · merged: False

## Original PR description

Stack from [ghstack](https://github.com/ezyang/ghstack/tree/0.18.0) (oldest at bottom):
* __->__ #5778

## Summary (human-written)
TitanRL's Monarch actor system always calls `ts.initialize` with the default and never hands ranks an address so a recipe can't pick TorchStore's new coordinator service. I added a control-plane setting ("monarch" or "service") to the actor system's config because the actor system runs the setup, and whatever `ts.initialize` returns now goes to every trainer and generator client. A new CI job reruns the RL loss guard on a service twin of its recipe against the existing golden so any difference in the synced weights shows up as a loss mismatch, and the controller's close now always stops the meshes and the service even after a failure or a cancellation unless one of those stops hangs. I ran the RL CPU suite on torch 2.15 and 2.16 and without torchmonarch, and the loss guard on an A100 matched the golden on all 10 steps on both control planes.

## Context
- TorchStore's control-plane selection (meta-pytorch/torchstore#253 to meta-pytorch/torchstore#265, meta-pytorch/torchstore#277, and meta-pytorch/torchstore#281) adds `control_plane=` to `ts.initialize` and `address=` to `ts.client`. TorchStore's coordinator service (meta-pytorch/torchstore#282 to meta-pytorch/torchstore#289) adds a "service" control plane whose address `ts.initialize` returns
- The Monarch actor system calls `ts.initialize` without a control plane and sets up every trainer and generator client with no address. So a recipe cannot pick the coordinator service
- CI runs the RL loss guard, which asserts bitwise-equal losses against a committed golden, only on TorchStore's default Monarch control plane. A difference in the weights that "service" syncs would go unnoticed
- CI installs TorchStore main, so this lands only once it has the control-plane selection, the coordinator service, and TorchStore's in-process volume servers. It must be reverted first if any of them is

## Solution
- `MonarchActorSystem.Config` gains `torchstore_control_plane` ("monarch" by default, or "service"), and what `ts.initialize` returns reaches every trainer and generator client. The trainer's and generator's `initialize_torchstore_client` takes a required keyword-only `address`, None on Monarch's control plane
- The controller's close now calls the actor system's `stop` from a `finally`, then closes the metric backends. `stop` shuts the service down even after a failed client setup or a cancel in a mesh stop
- Service twins of two CI recipes change only the control plane. A new 8-GPU RL job reruns the guard on its twin against the existing golden, then runs the other twin as a new `rl_service` suite
- The RL README shows how to select "service" and warns that the coordinator service and the volume servers unpickle each request that passes a JSON hello. So "service" belongs on a trusted network

## Test Plan
- RL CPU unit suite: 537 passed vs 489 at the parent on torch 2.16 dev, 535 vs 487 on 2.15 dev, and 411 vs 407 without `torchmonarch`, where the parent's 30 failures stay
- On 8 x A100 both loss guards match an A100 golden on all 10 steps. They ran on an earlier TorchTitan main before this commit's latest fixes, none of which changes a run that ends normally
- The service guard logs service selection lines and coordinator connects but no Monarch line. The default guard logs Monarch selection lines and no service line
- Not checked: whether another host or job can reach the new job's coordinator service and trainer ranks' volume servers, which listen without authentication, or its container can request `id-token: write`. Both depend on the runners' setup
- TorchTitan's RL CI installs TorchStore main, where 24 of the 50 new cases fail: 22 reject `control_plane` or `address` and 2 need `ts.ControlPlane`. The RL CPU job stays red until TorchStore's control-plane selection lands
```bash
# $PINS holds main's pinned packages and an alias that lets torch's SDPBackend pickle, and $TORCHSTORE is a local TorchStore build with only the control-plane selection for the unit runs and with the coordinator service and the in-process volume servers for the guards
# RL CPU unit suite with GPUs hidden, at the parent and at this commit, in each env
CUDA_VISIBLE_DEVICES= PYTHONPATH=$PINS:$PWD:$TORCHSTORE python -m pytest tests/rl/unit_tests/cpu --strict-markers -q -p no:cacheprovider -rfEs --continue-on-collection-errors
# The new job's script passes shellcheck
python -c "import yaml; print(yaml.safe_load(open('.github/workflows/integration_test_8gpu_rl.yaml'))['jobs']['build-test-service']['with']['script'])" > service_job.sh && shellcheck -s bash service_job.sh
# RL loss guard on 8 x A100 with this change on an earlier TorchTitan main, against an A100 golden exported from TorchTitan main before the control-plane selection: the service variant, then the default
PYTHONPATH=$PINS:$PWD:$TORCHSTORE python scripts/rl/loss_compare.py --hf-assets-path "$MODEL_PATH" --dump-folder rl_loss_guard_service --module torchtitan_recipes.tests.rl.alphabet_sort --config rl_grpo_qwen3_0_6b_varlen_batch_invariant_service --import-result "$GOLDEN" --assert-equal
PYTHONPATH=$PINS:$PWD:$TORCHSTORE python scripts/rl/loss_compare.py --hf-assets-path "$MODEL_PATH" --dump-folder rl_loss_guard --import-result "$GOLDEN" --assert-equal
# Lint, with pyrefly 0.45.1 on PATH
PYTHONPATH=$PINS SKIP=lychee-link-checker pre-commit run --from-ref HEAD~1 --to-ref HEAD
```

BC-breaking: yes, even the default Monarch path needs a TorchStore with the control-plane selection, `initialize_torchstore_client` takes a required keyword-only `address`, `ActorSystem.stop` also stops a rollout worker pool and lets the other processes stop after a first cancel but ends the stops at a second and shuts the service down either way, `ActorSystem.stop_rollout_workers` forgets its pool before it awaits the pool's stop, and even after a cancel `Controller.close` finishes that stop before the metric backends close
