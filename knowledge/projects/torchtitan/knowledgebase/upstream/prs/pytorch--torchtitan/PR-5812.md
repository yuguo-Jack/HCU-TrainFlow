## Why
The RL generator runs only on vLLM today. SGLang's scheduler (radix prefix
cache, overlap scheduling, breakable prefill CUDA graphs, session-referenced
KV, host KV offload) is a strong fit for RL rollouts, especially multi-turn
agentic ones. This PR adds an `SGLangEngine` behind the existing
`GenerationEngine` interface. As with `VLLMEngine`, SGLang runs the trainer's
TorchTitan model and attention kernel; it owns only KV cache management and
scheduling.

**Example.**
```python
# before: vLLM only
generator=Generator.Config(..., engine=VLLMEngine.Config())
# after: pick the engine by config type
generator=Generator.Config(..., engine=SGLangEngine.Config())
```
```
SGLangEngine (every rank, in-process; no tokenizer/detokenizer processes)
  add_requests ----> Scheduler.process_input_requests
  step ------------> one iteration of Scheduler.event_loop_overlap
                       TorchTitan Decoder, attention -> RadixAttention ->
                       trainer's varlen FlashAttention on SGLang's paged KV
  load_model_state_dict -> ModelStateDictLoader (in place, CUDA graphs stay valid)
```

## What changed
- `torchtitan/rl/generator/sglang/` (new):
  - `engine.py`: `SGLangEngine`. It builds SGLang's `Scheduler` in-process per
    TP rank and steps one overlap-loop iteration per `step()`. It also does:
    - request admission and rejection;
    - incremental output collection;
    - model state dict loads, with and without a KV reset (retract, flush,
      continue);
    - policy-version `cache_salt`;
    - session references;
    - seeded sampling.
  - `model_wrapper.py`: the TorchTitan model as an SGLang model class, with
    `_DecoderBody`, the module SGLang's prefill CUDA graphs capture.
  - `attention.py`: `SGLangInnerAttention`, plus a FlashAttention-backend
    subclass that calls the shared `paged_varlen_attention_out`.
  - `registry.py`: model class, config parser and attention backend
    registration.
  - `batch_invariance.py`: the trainer's `compute_logprobs` for returned
    logprobs.
  - `README.md`.
- `inference_model.compute_logits`: the lm_head plus TP gather, now shared by
  the vLLM and SGLang wrappers. For vLLM this is mechanical (the same code,
  moved).
- `torchtitan_recipes/rl/alphabet_sort.py`: new recipe
  `rl_grpo_qwen3_0_6b_varlen_sglang` (generator TP 2 plus trainer TP 2).
  `rl_grpo_qwen3_0_6b_varlen` now builds through a shared helper; its config is
  unchanged (`repr` compared).
- `test_sglang_bitwise_parity.py` (new). `test_model_defaults.py` lists the
  SGLang recipe as needing an optional package.
- Docs: `generator.py` and `torchtitan/rl/README.md` mention the new engine.

Supported: dense softmax attention with the varlen backend (Qwen3, Llama 3),
any TP, decode plus breakable prefill CUDA graphs, batch-invariant mode,
session KV, and CPU KV offload (SGLang HiCache, through `extra_server_args`).
These raise at build: DP > 1, EP / Dist-MoE, SP, flex attention, sliding window,
sinks, MLA and GDN.

Workarounds of SGLang APIs, each with a TODO in code:
- single-iteration loop (mirrors `event_loop_overlap`);
- an in-process output sink replacing the detokenizer and tokenizer sockets;
- a hook to plug a kernel into SGLang's FA metadata;
- skipping SGLang's own aten batch-invariant overrides in deterministic mode;
- registering a model class built at runtime;
- the layer attribute path its prefill graphs use to find attention.

## Numerics
Batch-invariant mode matches the trainer bitwise.

| Check | Hardware | Result |
| --- | --- | --- |
| `test_sglang_bitwise_parity.py`: trainer prefill vs SGLang decode; decode bsz 1 vs 5 with the prompt cached; trainer vs SGLang after an in-place model state dict load of perturbed weights | 2x GB300, SGLang `851642ade` | 3 passed, max delta 0 (a no-op load fails it: delta 19.5) |
| E2E `rl_grpo_qwen3_0_6b_varlen_batch_invariant` with SGLang (1 generator TP 2 + trainer TP 2), 10 steps | 4x GB300 | `logprob_diff/max` = 0 every step |
| Multi-turn workload (192 sessions x 4 turns), batch-invariant, HiCache on vs off | 2x GB300 | identical tokens for every session |

Outside batch-invariant mode, `logprob_diff/max` on the default recipe
(10 steps) is in vLLM's range: SGLang 0.4-18.5, vLLM 0.4-12.4. Across
other runs it varies: SGLang reached 4.9, 7.4 and 11.1; vLLM reached 9.8.

## Performance
Qwen3-0.6B, generator TP 2, 2x GB300. Same `GenerationEngine` calls; temperature
1; fixed-length outputs.

| Workload | vLLM | SGLang |
| --- | --- | --- |
| Decode: 512 requests, 256 in / 1024 out | 18.0 s (29.1k out tok/s) | 10.9 s (48.0k out tok/s) |
| Prefill: 512 requests, 1536 in / 128 out | 4.1-4.6 s | 3.1 s |
| Shared prefix: 512 requests, 1536 in (1280 shared) / 256 out | 4.9 s | 3.7 s |
| Multi-turn: 192 sessions x 4 turns (1024 + 4 x (256 obs + 128 gen)), KV pool 300K tokens | 6.96 s, 21% prefix hits; 6.22 s, 30% with `session_kv_holder` | 6.24 s, 37% |
| Multi-turn, KV pool 450K tokens (fits) | 5.8-6.2 s | 5.5 s |
| Peak GPU memory at `gpu_memory_limit=0.8` | 81.2% | 81.1% |

End to end, `alphabet_sort` (generator TP 2 + trainer TP 2, 4x GB300, 10 steps):
trainer tokens/s over steps 3-9 is 1682 and 1693 for vLLM (two runs), and 1632
and 1758 for SGLang (two runs).

Three engine fixes were needed to get there:
- Breakable prefill CUDA graphs: eager prefill was CPU-bound, at 114 ms of host
  time against 16 ms of GPU time per 16K-token chunk.
- `gc.freeze()` after the build: SGLang's ~1.5M objects made the engine loop's
  `gc.collect()` after each load take 1.2 s.
- KV-pool bookkeeping on SGLang's schedule stream.

## Testing

- Engine checks (local script) at TP 1 and TP 2, each with
  `reset_kv_cache_on_model_state_dict_load` off and on:
  - a too-long prompt is rejected;
  - a mid-generation reload of the same weights leaves outputs identical;
  - reset mode passes 6 of 6 repeats at TP 2.
- `pytest tests/rl/unit_tests/cpu`: 546 passed.
- vLLM `TestBitwiseParityVarlen`: 3 passed (it covers the shared
  `compute_logits`).
- E2E runs as above.

## Known issues / follow-ups
- CI has no SGLang environment, so CI doesn't run `test_sglang_bitwise_parity.py`
  (TODO in the test). An SGLang CI job is a follow-up.
- Upstream SGLang issues for the workarounds above are not filed yet.
- FlashAttention 4 JIT-compiles prefill kernel variants on first use, which
  costs about 6 s of stalls once per run.
- A request whose last batch is in flight during a model state dict load is
  reported at the new policy version (TODO in `load_model_state_dict`).
- In reset mode, requests retracted by a load lose their session reference
  (their next turn recomputes the prefix).
- HiCache costs more than it saves for Qwen3-0.6B, where recompute is cheaper;
  it needs evaluation on larger models.
- Next phase: MoE / EP, DP > 1, GPT-OSS, GDN / MLA, flex attention.

**Verdict: Needs discussion** -- The engine is careful and fits the `GenerationEngine` interface. But adding a second inference engine means maintaining about 10 private SGLang touchpoints, pinned to one SGLang commit, with no CI. The PR's own end-to-end numbers on the in-repo recipe are at parity with vLLM, not ahead. Maintainers need to decide whether that cost is worth taking on now.

**What this PR does.** It adds `SGLangEngine`, a second `GenerationEngine`. On every TP rank it builds SGLang's `Scheduler` in-process and runs one iteration of SGLang's overlap event loop per `step()`. The TorchTitan `Decoder` is plugged in as an SGLang model class, and attention goes through `RadixAttention` into a FlashAttention-backend subclass that calls the trainer's varlen kernel. The lm_head plus TP gather moves into `inference_model.compute_logits`, which both engines now share. It also adds a 4-GPU recipe and a bitwise-parity test that doesn't run in CI.

**Example.**
```python
# before: one engine
Generator.Config(..., engine=VLLMEngine.Config())
# after: pick the engine by config type
Generator.Config(..., engine=SGLangEngine.Config())
#   add_requests -> Scheduler.process_input_requests (no tokenizer/detokenizer procs)
#   step         -> _overlap_event_loop_iteration(scheduler)   # copy of the pinned event_loop_overlap body
#   load         -> ModelStateDictLoader in place; reset mode = pause(retract) + flush_cache + continue
```

### Questions
- **Value end to end.** The alphabet_sort trainer tokens/s is 1682/1693 for vLLM and 1632/1758 for SGLang, which is noise. On the multi-turn benchmark, SGLang takes 6.24 s and vLLM with `session_kv_holder` takes 6.22 s. The large wins (decode 1.65x, prefill 1.3x) are from generator-only microbenchmarks. Which in-repo workload, e.g. long-decode `dapo_math`, shows an end-to-end gain that justifies a second engine?
- **CI and ownership.** Who owns the SGLang environment, and when does the SGLang CI job land? Until it does, ~1.8K lines and the only parity test are unguarded.
- **Priority tie-breaks across TP ranks.** `EngineRequest.arrival_time` exists so that TP ranks with different clocks break priority ties the same way. The SGLang engine never passes it. Does SGLang's priority policy break ties by insertion order only, or does it use rank-local timestamps (e.g. wait-time thresholds) that could make TP ranks schedule differently?

<details><summary>Details</summary>

**Gate.**
- *Problem:* the generator only supports vLLM. The PR measures what SGLang's scheduler adds.
- *Layer:* SGLang lives in its own subpackage, behind the existing interface, selected by config type. Imports are lazy in the recipe, and core never imports SGLang. That matches `direction.md` and the vLLM precedent. `extra_server_args` matches vLLM's `extra_engine_args`, including the owned-key check.
- *One-sided design:* not applicable; this is an engine alternative, not a generator-only optimization.
- The open questions are value and maintenance cost, which is why the verdict is Needs discussion rather than Request changes.

**Checked and fine.**
- `compute_logits` is shared correctly. Inside the vLLM method body, `compute_logits` resolves to the module-level import, not the method.
- `replace_sglang_layer_configs` uses a strict `type(...) is VarlenInnerAttention.Config` check. That rejects sliding-window varlen, flex, MLA, GDN/KDA and linear attention at engine build. GPT-OSS's sinks are never reached because its layer 0 is sliding-window.
- `release_sessions` releases sessions in sorted order, and the releases arrive through the broadcast decision, so all TP ranks agree.
- The `GenerationEngine` threading and TP-collective contract holds: every rank gets the same calls.

**Size.** About 1.3K lines of logic plus a 148-line README. The `compute_logits` move and the recipe helper are mechanical.

Why does the SGLang recipe use generator TP 2 when the vLLM recipe uses TP 4? Qwen3-0.6B (16 query / 8 KV heads) divides by 4, and `SGLangEngine` supports any TP.

The TP change is the only reason for the new `_qwen3_0_6b_varlen_config` helper and the restructuring of `rl_grpo_qwen3_0_6b_varlen`: the generator model's sharding is built from `generator_parallelism`. With TP 4, the recipe could derive from the base recipe, as `rl_grpo_qwen3_0_6b_varlen_no_compile` already does:

```python
def rl_grpo_qwen3_0_6b_varlen_sglang(*, seq_len: int = 2048) -> Controller.Config:
    """... with the SGLang engine (6 GPUs: 4 gen + 2 train)."""
    from torchtitan.rl.generator.sglang.engine import SGLangEngine

    config = rl_grpo_qwen3_0_6b_varlen(seq_len=seq_len)
    config.generator.engine = SGLangEngine.Config()
    return config
```

That drops the helper (about 25 fewer lines) and makes the two recipes differ only by engine. If TP 2 is intentional (e.g. a 4-GPU CI budget), say so in the docstring.
