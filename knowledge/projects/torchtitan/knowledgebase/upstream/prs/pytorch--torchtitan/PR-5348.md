# [scripts] Retain all TensorBoard scalar steps for loss comparisons

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5348) · state: closed · merged: True

## Original PR description

## Summary

Keep every recorded scalar step when extracting loss/grad-norm metrics for numerical comparisons.

TensorBoard's default scalar reservoir keeps only 10,000 events per tag. `extract_scalar_from_tensorboard()` currently uses that default, so comparisons of longer runs silently operate on a sample rather than all recorded steps. Set scalar size guidance to zero, TensorBoard's unlimited-retention setting, while leaving other event types unchanged.

This affects comparison/export tooling only; training computation, models and checkpoint formats are unchanged. Retaining the full scalar series intentionally uses memory proportional to its length.

## Validation

- A real `EventFileWriter` writes 10,001 steps for both loss and grad-norm. The regression checks every extracted step and value, without mocking TensorBoard or extraction.
- Original implementation on current main: **1 failed, 3 passed**, with both tags truncated to 10,000 events.
- Patched full affected file: **4 passed** under WSL/Python 3.12/TensorBoard 2.21.0 after updating the base to `4a4176e97`. Earlier Windows/Python 3.11 runs also passed independently.
- Full repository-pinned `pre-commit run --all-files`: **passed** on that updated base. Python-managed hooks used isolated environments; pinned system Pyrefly used real CPU-nightly Torch and the repository's pinned dependency source revisions. No type suppressions/configuration changes were added. The optional Lychee executable was absent, so its guarded hook did not perform external link validation.
- No GPU integration or end-to-end training run was performed; the test demonstrates exact scalar-series preservation rather than claiming a training-loss result.

**Verdict: LGTM, the fix is correct and small. One suggestion about scope, plus a couple of nits.**

#### Correctness
- `EventAccumulator(event_dir, size_guidance={"scalars": 0})` is the right fix. `EventAccumulator` merges the dict you pass with `DEFAULT_SIZE_GUIDANCE` one key at a time, so other event types keep their defaults, and `0` means unlimited for the scalar reservoir. With the default of 10,000, longer runs get a reservoir *sample*. Steps get dropped silently and `compare_metrics` only sees a subset, which is exactly the kind of silent failure a numerics tool shouldn't have.
- No effect on training, models or checkpoints. Memory grows with the number of logged steps, which is negligible for scalar series.

#### Suggestion: same issue at other callsites (CLAUDE.md principle 6, "Audit all callsites")
The same default-reservoir pattern exists in three other places that compare losses step by step:
- `scripts/rl/loss_compare.py:86`: `EventAccumulator(tb_dir)`
- `scripts/checkpoint_compat_test.py:143`: `EventAccumulator(path)`
- `torchtitan/experiments/graph_trainer/tests/test_numerics.py:232`: `EventAccumulator(rank_event_dirs[0])`

These runs are usually far below 10k steps, so this is not urgent. Still, it would be nice to apply the same `size_guidance={"scalars": 0}` there in this PR (or a follow-up) so the comparison tools don't drift apart. [Fix this →](https://claude.ai/code?q=On%20branch%20codex%2Floss-compare-retain-scalars%2C%20pass%20size_guidance%3D%7B%22scalars%22%3A%200%7D%20to%20EventAccumulator%20in%20scripts%2Frl%2Floss_compare.py%3A86%2C%20scripts%2Fcheckpoint_compat_test.py%3A143%2C%20and%20torchtitan%2Fexperiments%2Fgraph_trainer%2Ftests%2Ftest_numerics.py%3A232%2C%20matching%20scripts%2Floss_compare.py%3A206&repo=pytorch/torchtitan)

#### Test (`tests/unit_tests/cpu/scripts/test_loss_compare.py`)
- It's a good regression test. It writes real events with `EventFileWriter`, uses 10,001 steps (one past the default cap), covers both `TB_TAGS`, and checks the exact `{step: value}` mapping. `assertEqual(values, expected)` already covers the length, so `assertEqual(len(values), num_steps)` is redundant, though it does give a clearer failure message.
- Nit: the TensorBoard imports inside the test method follow the lazy-import style of `loss_compare.py`. That's fine since `tensorboard` is in `requirements.txt`.
- Nit: writing 20k events plus a `Reload()` should take on the order of a second on CPU, which is acceptable for a unit test.
