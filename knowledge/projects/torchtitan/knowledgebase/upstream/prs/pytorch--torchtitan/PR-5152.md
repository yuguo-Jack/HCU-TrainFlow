# Varlen attention backend falls back to CuDNN even when FA is installed.

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5152) · state: open · merged: False

## Original PR description

Pin varlen attention to Flash to avoid cuDNN backward OOM on packed batches

## Problem
When no `sdpa_kernel` priority is set, `torch.nn.attention.varlen.varlen_attn` defaults to `[CUDNN, FLASH]` 

https://github.com/pytorch/pytorch/blob/7f758944c91946d1c7fbe69cc5cf60b1feba873c/torch/nn/attention/varlen.py#L49-L53 

Is there a particular reason for moving away from flash attn? In my tests on GH200 cudnn is far more memory hungry than flash.

Regular SDPA uses a different order (`[FLASH, EFFICIENT, MATH, CUDNN, ...]`). `VarlenInnerAttention` never set a priority, so every causal `(-1, 0)` layer ran on cuDNN. Sliding-window layers were already on Flash, because cuDNN rejects that window.


## Fix
`VarlenInnerAttention` now has a `sdpa_backends = [SDPBackend.FLASH_ATTENTION]` class attribute and runs `varlen_attn` inside `sdpa_kernel(self.sdpa_backends, set_priority=True)`. This mirrors `ScaledDotProductInnerAttention`. The backward reuses the backend chosen in the forward, so it runs on Flash as well.

I recently upgraded PyTorch and noticed that an experiment that was already running close to the memory limit stopped working. Claude helped me identify the cause: the backend had changed from FA3 to cuDNN. Switching back to FA3 immediately resolved the issue.

Initially, I assumed the switch to cuDNN was accidental. However, since you asked about it, I looked into it further. Based on my benchmarks, cuDNN uses less memory than FA3 when document lengths are roughly uniform.

When document lengths are heavily skewed, however, FA3 performs significantly better.

For the benchmarks below, I tested two document-length policies:

**1. Decreasing document lengths**

* 1 document → 16k
* 2 documents → 8k, 8k
* 4 documents → 8k, 4k, 2k, 2k
* ...

**2. Uniform document lengths**

* 1 document → 16k
* 2 documents → 8k, 8k
* 4 documents → 4k, 4k, 4k, 4k
* ...

Under the first policy, FA3 performs significantly better. On a GH200, cuDNN cannot even complete the benchmark.

Under the second policy, cuDNN appears to have a slight memory-efficiency advantage.

Given that natural document lengths tend to be skewed, I think FA3 should be the default backend. What do you think?

The vibed benchmark

```python
import gc
import torch
from torch.nn.attention import SDPBackend, activate_flash_attention_impl, sdpa_kernel
from torch.nn.attention.varlen import varlen_attn

activate_flash_attention_impl("FA3")

S, H, D, MIN = 16384, 32, 128, 8  # total tokens, heads, head dim, min doc length


def doc_lens_decreasing(n):  # sums to S: S/2, S/4, ..., last two equal; floored at MIN
    lens, rem = [], S
    for i in range(n - 1):
        lens.append(min(max(MIN, rem // 2), rem - MIN * (n - 1 - i)))
        rem -= lens[-1]
    return lens + [rem]

def doc_lens_equal(n):
    return [S // n] * n


def rand(*shape):
    return torch.randn(*shape, device="cuda", dtype=torch.bfloat16, requires_grad=True)


def varlen(backend):  # same packed q/k/v and cu_seqlens for both backends; only the kernel differs
    def setup(lens):
        q, k, v = (rand(S, H, D) for _ in range(3))
        cu = torch.tensor([0] + lens, device="cuda").cumsum(0, dtype=torch.int32)

        def fwd():
            with sdpa_kernel([backend], set_priority=True):
                return varlen_attn(q, k, v, cu, cu, max(lens), max(lens), window_size=(-1, 0))
        return fwd
    return setup


fa3, cudnn = varlen(SDPBackend.FLASH_ATTENTION), varlen(SDPBackend.CUDNN_ATTENTION)


def peak_mb(setup, lens):
    fwd = None
    try:
        fwd = setup(lens)
        fwd().sum().backward()  # warmup
        torch.cuda.synchronize(); base = torch.cuda.memory_allocated(); torch.cuda.reset_peak_memory_stats()
        fwd().sum().backward()
        torch.cuda.synchronize()
        return f"{(torch.cuda.max_memory_allocated() - base) / 2**20:.1f}"
    except (torch.OutOfMemoryError, RuntimeError) as e:  # cuDNN/cuda OOM can surface as a plain RuntimeError
        if isinstance(e, RuntimeError) and "out of memory" not in str(e).lower():
            raise
        return "OOM"
    finally:
        fwd = None; gc.collect(); torch.cuda.empty_cache()


print("decreasing doc lens")
print(f"max_seqlen={S} heads={H}\n{'num_docs':>10} {'FA3 MiB':>10} {'cuDNN MiB':>10}")
for n in [1, 2, 4, 8, 16, 32, 128, 512, 1024]:
    print(f"{n:>10} " + " ".join(f"{peak_mb(f, doc_lens_decreasing(n)):>10}" for f in (fa3, cudnn)), flush=True)


print("\n\nequal doc lens")
print(f"max_seqlen={S} heads={H}\n{'num_docs':>10} {'FA3 MiB':>10} {'cuDNN MiB':>10}")
for n in [1, 2, 4, 8, 16, 32, 128, 512, 1024]:
    print(f"{n:>10} " + " ".join(f"{peak_mb(f, doc_lens_equal(n)):>10}" for f in (fa3, cudnn)), flush=True)

```
