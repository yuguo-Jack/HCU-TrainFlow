# [WIP] Balance singleton expert NS compute across E-FSDP ranks

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5633) · state: open · merged: False

## Original PR description

## WIP status

We are evaluating bucket-wide balancing across Owned, Shard and BlockShard workloads, including fixed local work. Upstream #5468 has now merged a general implementation of this approach. We are checking its coverage of this PR's singleton E-FSDP case before proposing any further changes.

## Summary

When an EP-local expert batch contains one expert, `Shard(0)` assigns its entire Newton-Schulz workload to the first E-FSDP rank. Multiple layers in the same bucket can therefore leave the other E-FSDP ranks idle.

Balance these singleton expert tensors within each bucket using the existing deterministic greedy load allocator. The planner estimates NS compute cost and reorders compute-shard ranks per tensor, while preserving complete matrices, storage placements and the existing transport path. Eligible E-FSDP layouts are detected automatically, without new configuration options.

The change is limited to `dist_muon.py` and one new CPU unit test covering balanced ownership, complete matrix shapes, routing and plan-cache separation.

## Validation

- 42 relevant CPU tests passed, including the new test. Changed-file lint/format checks and type checking passed.
- Tested DeepSeek-V4 Flash on 8 Ascend 910B3 devices and 8 NVIDIA H800 GPUs: 23 layers, 4 experts, FSDP8 + EP4 + E-FSDP2, paired-layer buckets, and no CPU swap. On both setups, the original and balanced versions completed 15 steps with identical recorded loss and grad norm, and matching final model and optimizer-state hashes on all ranks.

| Hardware | Original Muon time | Balanced Muon time | Reduction |
| --- | ---: | ---: | ---: |
| Ascend 910B3 | 1296.47 ms | 1140.56 ms | **~12%** |
| NVIDIA H800 | 328.60 ms | 300.86 ms | **8.44%** |

910B3 timing is from the inspected rank-0 profiling region. H800 timing uses CUDA events: the median of steps 6-11, taking the slowest of 8 ranks at each step. These are preliminary Muon optimizer measurements.

**Verdict: Request changes** -- the new balancer runs separately from the existing `Owned` balancer and its cross-bucket loads. It is also turned on by an axis-name check, and the only benchmark is a reduced model where `num_experts == EP`.

**What this PR does.** Take a redistributed `Shard(0)` expert tensor whose group-local batch is a single expert. The PR picks which E-FSDP rank gets shard index 0, the only non-empty compute shard, using the existing LPT helper within each bucket. Ownership varies per tensor. Storage, transport participants, and numerics stay the same.

**Example.** Mesh `(edp_shard=2, ep=4)`, 4 experts, so each EP rank holds 1 expert and the edp group is `{0, 4}`.
```
main: layers.{1,2}.routed_experts.{w13,w2}: Newton-Schulz on rank 0, rank 4 idle
PR:   bucket [l1.w13, l1.w2, l2.w13, l2.w2] -> l1.w13->0, l2.w13->4, l1.w2->4, l2.w2->0
      bucket with one layer [l1.w13, l1.w2] -> w13 always on rank 0, w2 always on rank 4
```

The benchmark used a 23-layer, 4-expert model where `num_experts == EP`. A single local expert with E-FSDP > 1 needs EP equal to the expert count (e.g. EP256 for Flash, EP384 for Kimi). - Smaller design: `_assign_balanced_owner_ranks` treats "singleton redistributed `Shard` compute" layouts as candidates, with cost from `_dtensor_storage_regions(...)[0]`. `_resolve_muon_redistribution_plans` turns the owner into `shard_participants = (owner, *others)` and passes it to `_build_parameter_redistribution_plan`, with the owner in `spec`. - claude[bot] · comment · 2026-11-02T09:35:56Z · [source](https://github.com/pytorch/torchtitan/pull/5633#discussion_r4440798281)

File: `torchtitan/distributed/flex_shard/dist_muon.py` · line 1076

This is a second LPT balancer that ignores the first one. `_resolve_muon_redistribution_plans` already balances `Owned` items with `_assign_balanced_owner_ranks`, carrying `cumulative_loads_by_participants` across buckets. This call starts at `(0,) * len(participants)` in every bucket and ignores any `Owned` load in the same bucket. Two consequences:
- When a bucket has one singleton tensor, or the same uneven w13/w2 pair in every bucket, ties go to partition 0 every time, so `participants[0]` gets the heavier work in every bucket. The 8-12% gain was measured with paired-layer buckets, which hides this. With one layer per bucket I'd expect most of the gain to disappear (*unverified*).
- `Owned` and singleton loads on the same participants never see each other.

A singleton `Shard(0)` batch is really one owner computing the whole group-local tensor. Smallest fix: make these layouts candidates in `_assign_balanced_owner_ranks`, with cost taken from the group-local shape, so both kinds share one balancer and the cumulative loads. Then delete this function.

- claude[bot] · comment · 2026-11-02T09:36:00Z · [source](https://github.com/pytorch/torchtitan/pull/5633#discussion_r4440799130)

File: `torchtitan/distributed/flex_shard/dist_muon.py` · line 1048

This gates the behavior on a hard-coded mesh axis name. Nothing else in `flex_shard/*.py` checks axis names; layouts are resolved from placements and declared `ComputeLayout`s. The imbalance doesn't depend on the axis being called `edp_shard`: any redistributed `Shard(0)` compute whose group-local batch is smaller than the group size has it. If an axis gets renamed, or the same layout runs on another axis, the balancing turns off silently. Drop the name check and keep only the structural conditions (`Shard` compute, a redistribution axis, and the group-local batch size).

File: `torchtitan/distributed/flex_shard/dist_muon.py` · line 1062

Only `local_shape[0] == 1` is handled. The same fixed-coordinate hotspot happens whenever the group-local batch doesn't divide evenly over the participants. For example, 2 local experts over `edp_shard=4` means ranks at shard index 0 and 1 compute every layer while 2 and 3 never do. That's the case the Kimi recipe comment describes ("EP-local expert count is smaller than the edp_shard size"). Is there a reason to stop at 1? Rotating the shard order per tensor would cover any remainder. If you want to keep only the singleton case, say why in a comment.
