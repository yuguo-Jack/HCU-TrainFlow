# [kimi-k3] Add DistMuon support for vision linear weights

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5688) · state: open · merged: False

## Original PR description

## Why

The K3 DistMuon recipe currently leaves the entire vision encoder on AdamW, including its matrix-valued linear weights. Extend the existing recipe so vision Q/K/V projections get per-head Muon updates and the other vision linear weights get whole-matrix updates.

For example, in the debug model:

```text
vision_encoder.layers.0.attn.wq.weight: [512, 256]
main:    AdamW on the packed parameter
this PR: DistMuon on four independent [128, 256] head matrices
head_dim = attention.dim / num_heads, not vision_encoder.dim / num_heads
```

This belongs in the optimizer recipe: existing `BlockShard` and `Owned` layouts already express these matrices. A blanket "all 2D parameters" rule would incorrectly include learned position embeddings and would not preserve Q/K/V head boundaries.

## What changed

- Add explicit vision parameter selection and compute layouts: per-head Q/K/V; whole-matrix attention output, MLP, patch embedding, and multimodal projector weights.
- Keep vision buckets separate from decoder buckets. Vision uses a `dp_shard` FSDP mesh, while CP-enabled decoder parameters use `dp_shard_cp`.
- Keep norms and learned position embeddings on AdamW. The debug recipe changes from 228 Muon + 237 AdamW parameters to 243 Muon + 222 AdamW parameters.
- Add coverage and document the optimizer assignment. Model forward code and parameter/checkpoint layouts are unchanged; optimizer states saved with the old vision AdamW assignment require reinitialization or migration.

## Numerics

Validated on a branch based on `2db551367`, using seed 42 and deterministic algorithms.

| Check | Result |
| --- | --- |
| 10-step `kimi_k3_debugmodel_mm_muon`, FSDP2 + EP2, 2 GB300 GPUs | Loss and gradient norm are bitwise identical to independent seeded repeat runs |
| Debug training loss | Step 1: 7.983359336853027; step 10: 6.552382469177246 |
| Vision update reference | DistMuon update directions match independent per-head/whole-matrix `torch.optim.Muon` within the existing BF16 Newton-Schulz tolerance; AdamW updates match exactly |

The training check uses `scripts/loss_compare.py` with `--metrics=loss,grad_norm --steps=10 --baseline-ngpus=2 --test-ngpus=2`, baseline/test config `tests.integration_tests.b200:kimi_k3_debugmodel_mm_muon`, seed config `tests.integration_tests.b200:kimi_k3_debugmodel_mm`, and `--import-result=<previous-run.txt> --assert-equal`.

This intentionally changes optimizer updates and therefore the post-step-1 golden losses. The 10-step debug run is a smoke/reproducibility check, not real-data convergence evidence.

## Testing

**28 targeted tests passed**, including:

- CPU coverage against actual debug/full model parameters built on meta: every vision linear weight is selected, Q/K/V use the projected head width, embeddings/norms remain AdamW, and buckets do not mix vision/decoder transport groups. Covers CP degree 1 and 2 and a configuration without vision.
- Two-GPU FSDP update comparison, with an FSDP shard boundary that splits a vision head; image/image, image/text, and all-text batches; optimizer `state_dict` save/load followed by further updates.
- Existing Hugging Face state-dict round trip and decoder grouped-linear DistMuon coverage.

CUDA_VISIBLE_DEVICES=0,3 python -m pytest \

The new GPU test is marked `multi_gpu` and selected by the existing GPU unit-test workflow. The existing B200 `kimi_k3_mm_muon` integration recipe already exercises this default optimizer.

`pre-commit run --all-files`: all hooks pass except three pre-existing local Pyrefly errors in the installed `torch_checkpointing` API and PyAV types. The changed recipe type-checks with zero errors; no unrelated lint-generated changes are included.
