# [recipes] Add a Jev-style typed-decision fine-tune recipe for Qwen3

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5569) · state: closed · merged: True

## Original PR description

## Human Note

## Agent Notes

A minimal recipe that fine-tunes a base LM into a Jev-style typed-decision model, with no changes to
torchtitan core. Jev is [TypeSafe's decision model](https://typesafe.ai/blog/introducing-system-one-models-and-jev): given a state and typed questions (`choice`, yes/no
`noul`, ordinal `score`), it returns a probability per option from one forward pass, with no generated
text. Open reimplementations ([Kev](https://github.com/jaredpalmer/kev), [decider](https://github.com/Mapika/decider),
[WebJev](https://github.com/lexmount/WebJev)) all fine-tune Qwen bases; this
recipe uses decider's letter-slot readout, the simplest of them.

`prepare_data.py` turns each question in BEV
([`avbiswas/bev-decision-150K`](https://huggingface.co/datasets/avbiswas/bev-decision-150K)) into a
prompt that lists the options as letters and ends in `Answer:`. `choice` options and `noul`'s Yes/No
order are shuffled with a seeded RNG so the model can't learn letter-position priors; `score` levels
stay ordered. `DecisionLetterProcessor` supervises only the answer-letter token, and each question is
packed as its own varlen document, so questions about the same state can't see each other. At eval
time, the next-token logits restricted to the valid letters give the option distribution.

Rows average ~180 tokens with one supervised token, so `AnswerTokenLoss` gathers the supervised
positions into a fixed-size buffer (static shapes for CUDA graphs, on-device assert on the bound) and
then hands only those rows to `ChunkedLossWrapper.__call__`, which applies `lm_head` and cross-entropy
with its existing FSDP and loss-parallel handling. `qwen3_1_7b_decision` takes an optional
`ParallelismConfig`: FSDP by default, tensor parallelism (with loss parallel), or context parallelism,
for which it applies the Ulysses varlen attention transform. Pipeline parallelism is unsupported
because Qwen3-1.7B ties its embedding and output weights.

## Performance

One GB300, mean of steps 21-80 of an 80-step run: 68.7K -> 105.5K tokens/s (higher is better) from
`AnswerTokenLoss`, a single data reader, 16 prefetched microbatches, no activation recompute and
`max_num_documents=256`, compared with the same recipe using `ChunkedLossWrapper`, default activation recompute and data
loading (16 reader threads, 2 prefetched microbatches), and `max_num_documents=512`.

The same recipe scaled to Qwen3-4B (config not in this PR) on 2 GB300s runs at 51K tokens/s per GPU and
57% MFU. GEMMs take 61% of GPU time, and FSDP communication is almost fully overlapped. Trace
(Meta-internal): https://fburl.com/perfetto/t5n874gy

### 1. What a Jev-style decision model is

A normal LM is used **generatively**: you sample text, then parse an answer out of it. A decision model (Jev, and the open copies Kev, decider and WebJev) is a **classifier built on an LM**. It takes a *state* plus a *typed question* and returns a probability distribution over the options from **one forward pass**. Nothing is generated.

```
            +---------------------------- input ----------------------------+
 state:     | "Pizzagate is real..."  (a comment, a JSON invoice, a scene)  |
 question:  | type=score  "Toxicity band, 0-3?"   options=[0,1,2,3]         |
            +--------------------------------+------------------------------+
                                             |
                                             v
                                  +---------------------+
                                  |  LM (Qwen3 base),   |   one forward pass,
                                  |  causal attention   |   no decode loop
                                  +----------+----------+
                                             |
                                             v
            +---------------------------- output ---------------------------+
            | {"type":"score","score":2.6,"probabilities":                  |
            |   {"0":0.01,"1":0.04,"2":0.28,"3":0.67}}                      |
            +---------------------------------------------------------------+
```

There are three question types:

```
  choice : pick one of N named options     -> {"choice": "22622", "probabilities": {...}}
  noul   : yes/no                          -> {"noul": P(yes)}
  score  : ordinal 0..K                    -> {"score": E[k], "probabilities": {...}}
```

The output is a **calibrated probability**, so what matters is calibration (Brier, ECE) and "how many questions can I answer at <=5% error", not just accuracy. That's why `evaluate.py` fits a temperature.

### 2. The letter-slot readout (what this recipe trains)

The open approaches differ in how they read the distribution out of the LM. This PR uses the simplest one (as in decider). It renders the options as letters and reads the **next-token logits at `Answer:`**, restricted to those letters:

```
 prompt (prepare_data.render):

   Context:
   <state>

   Question (ordered scale): Toxicity band, 0-3?
   Options:
   A) not toxic
   B) mildly
   C) toxic
   D) very toxic
   Answer:                      <- last prompt token
                    \
                     \  next-token logits over full vocab V (~151K)
                      v
      [ ... " A" " B" " C" " D" " E" ... "the" ... ]
              |    |    |    |
              +----+----+----+---- keep only the valid letter ids
                       |
                softmax(logits / T)   (T is fit on calib.jsonl)
                       |
                       v
          P(A)=.01  P(B)=.04  P(C)=.28  P(D)=.67
```

The other readouts mentioned in the PR, for contrast:
```
 letter-slot (this PR)  : reuse the LM head, 1 token per option     <- zero model changes
 pointer head (Kev)     : extra head scores the option spans          <- model change
 shared-state packing   : N questions attend to ONE copy of state     <- needs segment/prefix IDs in core
```

### 3. `DecisionLetterProcessor`: one row -> one document with one supervised token

```
 sample = {"prompt": "...Answer:", "answer": " C"}

 tokenize separately (add_bos=False, add_eos=False):
   prompt ids : p0 p1 p2 ... p(n-1)
   answer id  : a                       (must be exactly 1 token, else ValueError)

 tokens      = [p0  p1  p2  ...  p(n-1)  a]
 input_ids   = [p0  p1  p2  ...  p(n-1)]          (drop the last token)
 labels      = [-100 -100 -100 ... a ]            (IGNORE_INDEX everywhere but the last position)
                                    ^
                                    position of "Answer:" predicts " C"
```

Tokenizing prompt and answer separately is deliberate. At eval time the prompt ends at `Answer:` and the next token is scored, so train and eval see the same token seam.

Packing (core `FirstFitPackingConfig` plus varlen masking) then puts ~180 of these documents into one 32K-token microbatch row:

```
 microbatch row (32K tokens, max_num_documents=256):

  |<-- doc 1 (q1 about state X) -->|<-- doc 2 (q2 about state X) -->|<-- doc 3 ... -->| pad |
   pos 0 ....................... L1  pos 0 ...................... L2  pos 0 ...
   labels: -100 ............... a1   -100 ................... a2      ...     -100
                                ^                              ^
                          supervised                     supervised

  attention: block-diagonal (document mask inferred from positions == 0)
  -> q2 can NOT see q1, even though both repeat the same state X
     (that's the "shared-state packing" follow-up in the PR)
```

The processor **raises** on rows longer than `max_context_length` instead of letting packing split them. A split row would become two documents, one with no supervised token, and that breaks the bound described next.

### 4. `AnswerTokenLoss`: run `lm_head` only where labels exist

Under the normal path, `lm_head` + CE runs on every token, even though ~99% of the labels here are `-100`:

```
 normal path:
   hidden [T=32768, D] --lm_head--> logits [32768, V=151K] --CE--> mostly ignored
                                     ^^^^^^^^^^^^^^^^^^^^^^
                                     ~5 billion logits (~10 GB in bf16), almost all wasted
```

`AnswerTokenLoss` gathers the supervised rows first:

```
 labels_T        : [-100 ... a1 ... -100 ... a2 ... a3 ... -100]   (T = 32768)
 is_supervised_T : [  0  ...  1 ...   0  ...  1 ...  1 ...   0 ]
                                 |            |      |
 nonzero_static(size=S=256, fill=-1)          |      |
 index_S         : [ i1, i2, i3, -1, -1, ..., -1 ]          (static shape S -> CUDA-graph friendly)
 is_valid_S      : [  1,  1,  1,  0,  0, ...,  0 ]
 index_S.clamp(0): [ i1, i2, i3,  0,  0, ...,  0 ]          (padding slots read row 0, harmless)
 labels_S        : [ a1, a2, a3,-100,-100,...,-100]         (padding slots are ignored by CE)

 hidden_TD[index_S] -> [S=256, D] --lm_head--> logits_SV [256, V] --CE(sum)/global_count--> loss
                       ^^^^^^^^^                ^^^^^^^^^^^^^^^^^
                       128x fewer rows than the normal path

 guard: _assert_async(num_supervised <= S). The bound holds because each doc has 1
 supervised token, docs are never split, and packing caps docs/row at 256.
```

It subclasses `ChunkedLossWrapper` only for its trainer wiring. The trainer sees `isinstance(loss_fn, ChunkedLossWrapper)`, sets `model._skip_lm_head = True` and calls `loss_fn.set_lm_head(lm_head)` (`torchtitan/training_engine.py:417-432`). The PR then **overrides `__call__` completely**, so none of the chunking, detach, `GradAccumulator` or FSDP reshard logic runs. Autograd just goes through `lm_head` normally.

### 5. Code review

**Correctness: looks right for the validated config (FSDP, 1 microbatch row).** I checked:
- `max_num_documents` is enforced **per packed row**, and a row is `num_tokens_per_microbatch` (32K) long. So "<= 256 supervised tokens per microbatch" holds (`torchtitan/components/data/packing.py:127-131`).
- Padding slots in the gather are handled correctly: they clamp to index 0 and get the label `IGNORE_INDEX`.
- The normalization is right: `global_loss_token_counts` here equals the number of supervised answer tokens.
- The test `test_answer_token_loss_matches_full_cross_entropy` checks both the loss and grad against full CE, which is the right check.

**Issues / suggestions:**

1. **`AnswerTokenLoss` takes the `ChunkedLossWrapper` contract but none of its parallelism handling** (`qwen3.py:85-133`). `ChunkedLossWrapper.__call__` runs under `spmd.local()`, does the `spmd.mutate_type` on the loss, and handles FSDP reshard and gradient-sync coalescing. This class skips all of that, so it's only validated under FSDP-only. Under TP/loss-parallel (vocab-sharded `lm_head`, spmd type checking) or PP, it's untested and might fail confusingly. It also inherits an unused `num_chunks=8` config field. The PR's TODO already names the real fix: a core hook for "losses that apply lm_head themselves". Until then, I'd at least raise a `ValueError` (or document) that TP/PP aren't supported. [Fix this →](https://claude.ai/code?q=In%20torchtitan_recipes%2Fdecision%2Fqwen3.py%20on%20branch%20drisspg%2Fjev-decision-recipe%2C%20AnswerTokenLoss%20subclasses%20ChunkedLossWrapper%20but%20overrides%20__call__%20and%20skips%20its%20spmd%2FTP%2FFSDP%20handling.%20Document%20in%20the%20docstring%20that%20only%20FSDP%2FDP%20is%20supported%20and%20note%20that%20the%20inherited%20num_chunks%20field%20is%20unused.&repo=pytorch/torchtitan)

2. **The gathered `lm_head` is a reusable optimization, not a decision-specific one.** Any SFT with sparse labels (prompt-masked chat SFT, RL with short completions) wastes the same `[T, V]` compute. If this lands, the gather belongs in core as a mode of `ChunkedLossWrapper` (or as the hook above), not in a recipe file. That follows "reuse over duplication" in CLAUDE.md.

3. **`DecisionLetterProcessor` is ~90% a generic prompt/completion processor.** It differs from `ChatProcessor` only in having no chat template and a 1-token answer. On question 2 in the PR: yes. A core `PromptCompletionProcessor` (prompt masked, completion supervised, optional `max_completion_tokens`) would serve base-model SFT generally. The recipe would then keep only the `len(answer) == 1` check, e.g. as a `post_filter` or a thin subclass.

4. **Over-length rows raise instead of drop** (`qwen3.py:75-79`). That's a deliberate choice, and it's safe today because `prepare_data` filters `state` to 4000 chars (~1K tokens < 2048). But a single bad row kills a run mid-training. `ChatProcessor` returns `None` for the per-sample overflow case (see its `_require_token_prefix` docstring for the reasoning). Returning `None` also keeps the "never split" invariant, so I'd do that plus a warning.

5. **Options are never shuffled** (`prepare_data.py:29-55`). `noul` is always `A) Yes / B) No`, and `choice`/`score` keep the dataset order. The model can learn letter-position priors, and the letter-slot readout is known to be sensitive to them. Consider shuffling `choice` options with a seeded RNG, at least for training. `score` should stay ordered.

6. **The docs don't agree with each other.** The README says "about 3 minutes on 2 GB300"; the PR body says "about 6 minutes". The README results table (0.873 / 0.882 / ...) also differs slightly from the PR table (0.875 / 0.889 / ...). Pick one run.

7. **The README's perf paragraph will go stale.** The quack/CuTeDSL RMSNorm note ("4.8.0 here; other versions silently fall back") depends on the nightly and the environment. I'd drop it, or turn it into a one-line TODO.

8. **Minor items in `evaluate.py`:**
   - It hard-codes `"cuda"`.
   - It loads everything into memory with `open(...)` and never closes the file handles.
   - The `metrics` comment says "longest prefix whose error rate stays within 5%", but the code computes the *largest k* whose cumulative error is <=5%. That's fine, but say that in the comment.
   - Fitting the temperature on part of the *test* split is fine because it's state-disjoint, and the README already says so.

9. **Tests.** The CPU tests are good. The loss-equivalence test in particular is the right one. Not covered: the `_assert_async` path actually firing on CUDA (on CPU it raises a `RuntimeError` synchronously, which is what the test checks), and an integration test. CLAUDE.md asks for a GPU integration test only when parallelism is involved; here that's just FSDP, so this is optional.

### 6. Should it land?

**Recommendation: not as-is. Land the reusable pieces in core and keep the recipe thin, or move it to `experiments/`.**

| piece | where it should go | why |
|---|---|---|
| sparse-label `lm_head` gather (`AnswerTokenLoss`) | **core**, as a `ChunkedLossWrapper` mode or a "loss owns lm_head" hook | not decision-specific; helps any masked SFT/RL; removes the subclass-to-get-wiring workaround |
| prompt/completion processor | **core** `SampleProcessor` | base-model SFT without a chat template is a general need |
| `qwen3_1_7b_decision` config | `torchtitan_recipes/` | it's a recipe |
| `prepare_data.py`, `evaluate.py` (HF `transformers` + `datasets`, BEV-specific, Jev response format) | `torchtitan/experiments/decision/` (or out-of-tree) | dataset- and product-specific tooling; `torchtitan_recipes/` today holds configs, not data/eval pipelines |

On the PR's three questions:
1. **Placement.** A new `torchtitan_recipes/decision/` that ships a data-prep script and an HF eval script is a new precedent for that package. `experiments/` is the more natural home for this whole bundle while it's exploratory.
2. **Core processor.** Yes, see item 3.
3. **What's next.** Shared-state packing (explicit segment/prefix IDs instead of `positions == 0`) is the one with real value beyond Jev: prefix-sharing also helps RL (GRPO groups) and multi-question SFT. I'd scope that as its own RFC. A pointer head and MoE fine-tunes are model/recipe work and can wait until there's a concrete user.

Overall the work is clean and well-validated for a draft: the numbers are convincing, the invariants are documented, and the loss test is the right test. The main question is scope. The two generic wins (sparse `lm_head` and the prompt/completion processor) are worth more to torchtitan than the Jev recipe itself.

### Deep review: no real bugs found

I went through `qwen3.py`, `prepare_data.py`, `evaluate.py` and the tests, and checked them against the core code they rely on (`ChunkedLossWrapper.__call__` and `_DecoderOutputGradientBackProp`, FirstFit packing with `max_sequences_per_bin`, decoder `preprocess_inputs`/CP sharding, and the trainer's lm_head wiring). I found nothing that produces wrong results.

Things I specifically checked that hold up:
- **Supervised-token bound.** Each packed row is one `num_tokens_per_microbatch_per_dp_rank` microbatch, and packing caps it at 256 documents. The processor rejects over-length rows, so a document is never split, and there is one label per document. A CP shard only holds a subset of the row, so its count is lower still.
- **Gather fill slots.** Unused `nonzero_static` slots are `-1`. They read the last row, their label is masked to `IGNORE_INDEX`, and they contribute zero gradient. This stays correct when the last row is itself a real supervised position, because the zero gradients just add to its real one.
- **Gradient path.** `pred[index_S]` stays connected to the decoder graph. The parent detaches only the gathered rows, so `_DecoderOutputGradientBackProp`'s gradient flows back through the index op into the full `[T, D]` hidden state. `loss_kwargs` is empty for this pipeline, so leaving it ungathered doesn't cause a shape mismatch.
- **Label alignment.** `TextSequence` expects pre-shifted labels, and `labels[-1] = answer` puts the target at the `Answer:` position. That matches eval's `logits[:, -1]` read with left padding and cumsum position ids.
- **Data splits.** The calib/eval split is state-disjoint. Option shuffling moves `keys` and `gold` together, so the gold letter, `system_one_answer` and `probs["true"]` stay consistent.
