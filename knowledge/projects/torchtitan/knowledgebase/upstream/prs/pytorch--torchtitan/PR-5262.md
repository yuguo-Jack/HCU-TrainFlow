# Fix dimension handling for batch invariant function

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5262) · state: open · merged: False

## Original PR description

What changed?
In _sum_dim_batch_invariant, dims = tuple(range(input.ndim)) if not dim else tuple(dim) treats dim=[] the same as dim=None. Changed to if dim is None else.

Why?
dim=[] is a valid no-op reduction (PyTorch supports reducing over zero dims as identity). The old check reduced over all dims instead, breaking bit-identical parity with the real aten::sum.dim_IntList op this function overrides.

How did you test it?
Hand-traced both branches with dims=(): the float path’s loop becomes a no-op and returns result * 1; the integer path’s loop is skipped and returns result cast to output_dtype — both correctly identity.

Potential risks
Low — only changes behavior for the previously-mishandled dim=[] case; all other inputs unaffected.

### Summary

I recommend **not merging** this change. Its premise is wrong. In ATen, `sum.dim_IntList` with an empty `dim` list **reduces over all dims**, the same as `dim=None`. It is not an identity/no-op. The current `if not dim` check already matches upstream, so this PR would make the override *diverge* from `aten::sum.dim_IntList`.

### Details

`sum.dim_IntList` builds its reduction mask with `make_dim_mask` (`aten/src/ATen/native/ReduceOpsUtils.h`):

```cpp
static inline DimMask make_dim_mask(OptionalIntArrayRef opt_dims, int64_t ndim, bool allow_empty_dims=false) {
  DimMask mask;
  if (opt_dims.has_value()) {
    auto dims = opt_dims.value();
    if (dims.empty() && !allow_empty_dims) {
      mask = DimMask().flip();   // empty list -> reduce ALL dims
    } else {
      mask = at::dim_list_to_bitset(dims, ndim);
    }
  } else {
    mask = DimMask().flip();     // None -> reduce ALL dims
  }
  return mask;
}
```

`sum` uses the default `allow_empty_dims=false`. So `torch.sum(x, dim=[])` and `torch.ops.aten.sum.dim_IntList(x, [])` both return the full scalar sum. This is a well-known legacy quirk (see pytorch/pytorch#29137). It differs from NumPy, where `axis=()` is an identity. Some newer reductions opt into `allow_empty_dims=true`, but `sum` does not.

After this PR, with batch-invariant mode on:

```python
x = torch.randn(2, 3)
torch.sum(x, dim=[])
# upstream / current code: tensor(<scalar>)   shape ()
# with this PR:            tensor of shape (2, 3)   (identity)
```

So the override would return a different **shape**, not just slightly different numerics. That breaks the drop-in contract the override relies on (`allow_override=True` at `torchtitan/distributed/batch_invariant.py:107`). Any caller that hits the empty-list path, e.g. decompositions or autograd formulas that pass `[]`, would silently get the wrong shape and values.

I wasn't able to run Python in this environment to confirm empirically. You can check quickly with:

```python
import torch
x = torch.arange(6.).reshape(2, 3)
print(torch.ops.aten.sum.dim_IntList(x, []))        # expect tensor(15.)
print(torch.ops.aten.sum.dim_IntList(x, [], True))  # expect tensor([[15.]])
```

### Suggestions

- **Close this PR as is.** The existing `if not dim` is correct.
- If the goal is to make the intent clear, a short comment would help more than a behavior change. For example:
  ```python
  # Match aten: an empty dim list reduces over all dims, like dim=None.
  dims = tuple(range(input.ndim)) if not dim else tuple(dim)
  ```
- If you want to guard against this regression, add a CPU unit test. It should compare `_sum_dim_batch_invariant(x, [])` with `torch.ops.aten.sum.dim_IntList(x, [])` for shape and value, on both the float and integer paths. On CPU the float path needs `batch_invariant_ops`, so the test may need to be GPU-gated or use the integer/float64 path. That test would be more valuable than the PR's hand-traced check, which tested against the wrong expected behavior.
