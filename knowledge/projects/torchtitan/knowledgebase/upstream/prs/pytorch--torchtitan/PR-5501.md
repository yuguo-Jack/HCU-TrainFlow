# [data] Preserve HF streaming state between restore and read

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5501) · state: open · merged: False

## Original PR description


`_HuggingFaceCursorIterator.set_state` loads a cursor into Hugging Face, but HF applies it lazily on the next read. Until then, `get_state` returns the previous dataset position.

The document-aware packer snapshots its source before reading a document. After resuming an unshuffled stream, it can therefore save a stale cursor for a document remainder. A second restart then reads that remainder from the wrong document. I keep the restored bytes until the next read, when HF's live state becomes current.

Minimal reproducer:

```python
import datasets
from torchtitan.components.data.sources import _HuggingFaceCursorIterator


def cursor():
    data = datasets.Dataset.from_dict({"id": list(range(8))})
    return _HuggingFaceCursorIterator(
        data.to_iterable_dataset(), repeat=True, shuffle=False
    )


original, restored, restored_again = cursor(), cursor(), cursor()
try:
    for _ in range(3):
        next(original)
    state = original.get_state()
    restored.set_state(state)
    print("state preserved:", restored.get_state() == state)
    restored_again.set_state(restored.get_state())
    print("direct resume:", next(restored)["id"])
    print("resaved resume:", next(restored_again)["id"])
finally:
    original.close()
    restored.close()
    restored_again.close()
```

Observed with datasets 4.7.0 and Grain 0.2.18:

| Output | Before | After |
|---|---|---|
| State preserved | `False` | `True` |
| Direct resume | `3` | `3` |
| Re-saved resume | `0` | `3` |
| Second packed-loader resume | `[14, 15, 16, 17]` | `[24, 25, 26, 27]` |

The new CPU tests also reproduce two resumes through a real JSONL-backed `GrainDataLoader`, including a training microbatch between the two checkpoints. All six new cases fail before the fix. The fixed loader matches uninterrupted inputs, labels, positions, and padding masks, with prefetch both disabled and enabled.

I audited the source's callers. The change stays inside the shared HF cursor; no callsite changes are needed. The `epoch` and opaque `hf` checkpoint fields are unchanged, as are token processing and model computation.

### Summary

The diagnosis looks right to me. HF `IterableDataset.load_state_dict()` only stores `_starting_state_dict`. The state isn't applied until `__iter__`'s generator body runs, which happens on the first `next()`. Until then, `state_dict()` still returns the old `_state_dict`. `ConcatThenSplit` packing snapshots the source before it reads, so a checkpoint taken right after a restore can save a stale cursor.

The fix is small and stays inside the cursor:
- It holds on to the restored bytes.
- It returns those bytes from `get_state()` until the next read.
- It reuses the original `bytes` object, so the saved state is byte-identical to what was loaded and can't be changed by HF mutating its dict.

No callsites change, and neither does the checkpoint format. That's a good scope for the fix. 👍

### Suggestions

**1. Clear `_pending_hf_state` only after a successful read** (`sources.py:245`)

Right now it is cleared before `next(self._iterator)`. If that read raises something other than `StopIteration` (for example a transient network or IO error from a remote streaming source), the pending state is already gone. Whether HF has applied the restored cursor at that point depends on where the error happened. If a checkpoint is then saved (e.g. by an error handler or a retry loop), it could have the same stale-cursor problem this PR fixes. Clearing after the read closes that gap:

```python
def __next__(self) -> dict[str, Any]:
    try:
        row = next(self._iterator)
    except StopIteration:
        if not self._repeat:
            raise
        ...
        row = next(self._iterator)
    self._pending_hf_state = None
    return row
```

With `repeat=False`, if `StopIteration` comes straight after a restore, the pending bytes stay set. That's correct: they are still the right state to save. This is minor, but it makes the invariant simple: pending bytes are cleared only once HF has actually produced a row.

[Fix this →](https://claude.ai/code?q=In%20torchtitan%2Fcomponents%2Fdata%2Fsources.py%20on%20branch%20fix%2Fr4-torchtitan-streaming-resume%2C%20in%20_HuggingFaceCursorIterator.__next__%2C%20move%20%60self._pending_hf_state%20%3D%20None%60%20so%20it%20runs%20only%20after%20a%20row%20has%20been%20successfully%20read%20(both%20the%20normal%20path%20and%20the%20repeat%2Frollover%20path)%2C%20instead%20of%20before%20next(self._iterator).&repo=pytorch/torchtitan)

**2. Add a TODO pointing at HF upstream** (`sources.py:284-286`)

This works around HF behavior: `state_dict()` after `load_state_dict()` returns stale state until the next read. Per the "investigate root cause / reuse upstream" principle, a TODO linking an upstream `datasets` issue (or opening one) would make it clear the workaround can be removed once HF reports the pending state. Something like:
```python
# TODO: Remove once datasets.IterableDataset.state_dict() reflects a
# loaded-but-unapplied state (<link to upstream issue>).
```

**3. The README addition reads like a changelog entry** (`README.md:521-522`)

"A restored streaming cursor can be checkpointed before its next read" is how resume is expected to work, not a feature users have to think about. The section already says resume needs unchanged code, config, and so on. I'd drop these two lines, or reword them as a plain guarantee (e.g. "Repeated checkpoint/resume cycles are exact, including mid-document packing remainders.").

**4. Test coverage nit**

`test_hf_cursor_state_after_restore` covers `num_consumed` of 4 (mid-epoch) and 20 (second epoch). Adding `num_consumed=16` would cover a restore at the exact end of an epoch, where the first post-restore read hits `StopIteration` and rolls over. That's the one path where clearing the pending state and changing epoch happen together.
