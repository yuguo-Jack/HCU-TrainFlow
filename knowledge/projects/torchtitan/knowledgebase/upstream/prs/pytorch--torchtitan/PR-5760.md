## Agent details

**TLDR:** Adds score centering (https://arxiv.org/abs/2609.20807), an opt-in RL loss that cancels the bias a trainer/generator mismatch adds to the policy gradient. Turn it on with `SamplingConfig.num_topk_logprobs=k` and `ScoreCenteringLoss`. With `k=0` (the default) nothing changes.

```text
vLLM logprobs=k -> Completion [generated, k] -> TrainingSample [loss tokens, k] -> microbatch [loss tokens, k]
                -> TrainingMicrobatch.to_input_dict: scatter to [T, k] on the trainer's device -> ScoreCenteringLoss
```

```python
generator=Generator.Config(sampling=SamplingConfig(..., num_topk_logprobs=32)),
trainer=Trainer.Config(loss=ChunkedLossWrapper.Config(loss_fn=ScoreCenteringLoss.Config(global_vocab_size=...))),
# masked importance sampling instead of the default truncation at 2.0:
ScoreCenteringLoss.Config(ratio_band=(0.2, 5.0), global_vocab_size=...)
```

**Problem**
1. The trainer scores each sampled token with its policy `p`. vLLM sampled it from a slightly different `q` (kernels, quantization, MoE routing, staleness).
2. So each position's expected policy gradient has a term with no reward in it: `E_q[A] * sum_v q_v * grad log p_v`. It pulls `p` toward `q` (paper Eq. 3). Group-mean advantages don't remove it: at later positions `E[A | prefix] != 0`.
3. Each weight sync feeds the pull back into vLLM, so it compounds. Paper, Qwen3-30B-A3B with an INT8 sampler and INT4 KV cache: score centering 30% accuracy, truncated IS 12%, the other methods below 5%. Under a mild FP8 sampler all of them tie (57-58%).
4. The mismatch grows in async TorchTitan runs too. Qwen3.5-35B-A3B with this loss (truncated IS, k=32), bf16 generator, policy age 5-7: the mean `log p - log q` went from -0.003 (step 145) to -0.018 (steps 160-162), and the share of tokens with `p / q > 2` from 0.02% (step 105) to 0.56% (steps 160+).

**Solution**
1. Subtract each position's expected score from the token's score, over vLLM's top-k tokens `H`; the trainer models the tail (paper Eq. 12). The correction is exactly 0 when `p == q`:
   `token_loss = -A * (w(p_y/q_y) * log p_y - sum_H detach(q_v * w(p_v/q_v) - alpha * p_v) * log p_v)`
2. `ScoreCenteringLoss` (`torchtitan/rl/trainer/losses/score_centering.py`). The token weight `w(r)` is truncated (`max_ratio=2.0`, the default and the paper's TIS cap) or masked (`ratio_band=(lo, hi)`, which replaces the cap; the paper's MIS+SC).
3. `compute_topk_logprobs` sits next to `compute_logprobs`, in the same `"loss"` compile region. Under TP it gets the logprobs of the k ids with three all-reduces, without gathering the vocab. In batch-invariant mode it gathers the vocab, like `compute_logprobs`, and vLLM's logprob patch calls the same function, so the trainer's and the generator's top-k logprobs match bitwise.
4. Transport: `SamplingConfig.num_topk_logprobs` -> vLLM `logprobs=k` -> `Completion` -> `RolloutTurn` -> `TrainingSample`, which keeps one row per loss token. `TrainingMicrobatch.to_input_dict` scatters the rows into `[T, k]` on the device (`masked_scatter_`, no host sync).
5. `loss_kwarg_sharding` gives a loss input with trailing dims the labels' token layout plus replicated trailing dims, so CP and SPMD typing accept `[T, k]`. Every model's `preprocess_inputs` uses it; a 1-D loss input gets the same layout as before.

Unchanged: `DAPOLoss` and `GRPOLoss` numerics (their two helpers become public: `MAX_LOG_RATIO`, `normalize`), `_LossParallelCrossEntropy` (its shard code moved to `_local_vocab_shard`, which the top-k path shares; only the error text changed), every recipe, and every path with `num_topk_logprobs=0`, except two things. `log_logprobs` rollout dumps gain two null top-k keys per turn. The Verifiers rollouter pops every trace's generation metadata: main pops only the trainable trace's, so the others stay in the server until `close()`.

You may ask:
- Why not on top of PPO-clip (`DAPOLoss`)? The paper tests score centering only with REINFORCE, truncated IS and masked IS. With a clip, the correction needs per-token clip weights over the whole top-k, an untested combination.
- Why scatter in `to_input_dict`, not in the batcher or the loss? Dense `[T, k]` rows from the batcher would also ship every prompt and padding row. CP and `ChunkedLossWrapper` split loss inputs along T, so the loss must get `[T, k]`.
- Why must the batcher know k? An empty DP bin still needs `[0, k]` rows, so every rank calls the loss with the same arguments.
- Why does `ratio_band` replace `max_ratio`, not a `TruncatedIS.Config | MaskedIS.Config` pair? Each class would be used once, and either way a user sets one field.
- Why Verifiers support in this PR? The at-scale runs used Verifiers rollouts. Verifiers drops extra response fields, so the generation server records each generation's top-k, and `trace_to_rollout_turns` attaches the rows to the node with the same prompt length and completion tokens. A second generation with the same key in one trace gets HTTP 500, since its rows can't be told apart from the first one's.

NOTE:
- The controller raises at startup for `ScoreCenteringLoss` without top-k, and for top-k with any other loss. Validation never asks for the top-k.
- Transport is 8 * k bytes per generated token from vLLM, and per loss token to the trainer (256 B at k=32). The engine raises if vLLM's logprob rows are not `[sampled, top-1, ..., top-k]`.
- In eager the loss saves one more `[T, V_local]` fp32 buffer per chunk for backward than `GRPOLoss`. The `"loss"` region removes it (TODO in the code: one call for the label and the top-k).
- `max_logprobs` now follows `num_topk_logprobs`; setting it in `VLLMEngine.Config.extra_engine_args` raises.
- No CI entry runs `ScoreCenteringLoss` on GPUs yet. A GPU integration config follows once a recipe uses the loss.
- An earlier cut of the same transport and loss trained Qwen3.5-35B-A3B in async multi-turn runs: truncated IS (k=32) and, for 150 steps, `ratio_band=(0.2, 5.0)` (k=128). Generator and trainer top-k mass agreed to ~5e-5 (0.99941 vs 0.99935 at k=32).
