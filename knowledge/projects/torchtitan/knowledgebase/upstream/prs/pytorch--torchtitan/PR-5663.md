# [distributed] Isolate FSDP communicators from WORLD/CP

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5663) · state: open · merged: False

## Original PR description

- Give FSDP `dp_replicate`, `edp_shard`, and flattened `dp_shard * cp` axes dedicated process groups, preserving the configured backend and FSDP2 mesh semantics.
- Add pure-CP/pure-DDP communicator-identity tests and an 82-line manual NCCL ordering probe.
- Four-B300 diagnostic: shared PG 0 / sequence 3 watchdogs; separate communicators complete with exact outputs on all four ranks. This deliberately reverses **host submission order**; completion is measured here, not a general reversed-order guarantee ([NVIDIA contract](https://docs.nvidia.com/deeplearning/nccl/archives/nccl_2307/user-guide/docs/usage/communicators.html#using-multiple-nccl-communicators-concurrently)).
- Continues #5645 under this account; Pei's original commits and authorship are preserved.

**Verdict: Request changes** -- the PR hasn't shown that the bug exists in torchtitan on `main`, and its explanation of the root cause doesn't match how a single NCCL communicator orders work. Isolating the groups could also bring in the cross-communicator ordering risk that the NVIDIA doc warns about.

**What this PR does.** When a mesh axis spans every rank, `DeviceMesh` reuses the WORLD process group instead of creating a new one. This PR passes an explicit `backend_override` so that FSDP's `dp_replicate`, `edp_shard`, and flattened `dp_shard*cp` axes get dedicated process groups. It pre-flattens `dp_shard_cp` under the name FSDP2 will use later, so FSDP2 picks the dedicated group out of the cache. It also adds two CPU tests and a manual NCCL probe script.

**Example.** `cp=4, dp_shard=dp_replicate=tp=pp=1` on 4 GPUs:
```
main: cp axis -> WORLD; FSDP shard axis dp_shard*cp (size 4) -> WORLD   (one communicator)
PR:   cp axis -> WORLD; FSDP shard axis -> new 4-rank PG                (two communicators)
```
The repro deadlocks only because rank 0 is forced to submit A2A->AG on the host while the other ranks submit AG->A2A. Torchtitan never does this, because its host order is the same on every rank. @fegin has run CP8 and CP16 with `dp_shard=1` many times without a hang. The author's answer is that the hang shows up with an *internal* CP implementation that uses P2P.

### Must fix
1. **The problem isn't shown on `main`.** @fegin's question ("what TorchTitan command / parallelisms") is still open: the only reported trigger is an out-of-tree CP. If that CP issues collectives in a rank-dependent host order (from a thread, data-dependent P2P, or lazily created P2P communicators), the fix belongs there. Please give either a torchtitan config that hangs, or an NCCL/flight-recorder trace from the production hang showing the mismatched sequence numbers across ranks.
2. `torchtitan/distributed/parallelism_context.py:95-100` -- the stream-based rationale is incorrect: the stream a collective is issued from doesn't change its host enqueue order, and one communicator serializes its work in launch order (inline).
3. **The fix may just move the hazard.** Once the groups are separate, the GPU order of FSDP and CP kernels really can differ across ranks. The linked NVIDIA doc says that can deadlock unless launch order is consistent or `NCCL_LAUNCH_ORDER_IMPLICIT` is set, and both measured runs set `NCCL_LAUNCH_ORDER_IMPLICIT=1` (inline on the script).
4. `torchtitan/distributed/parallelism_context.py:77-80` -- the `dp_replicate` and `edp_shard` overrides don't address the CP case. The `dp_replicate` one adds a world-size communicator under pure DDP; the `edp_shard` one is a no-op (inline).
5. `torchtitan/distributed/fsdp.py:145-150` -- the fix depends on FSDP2's private flatten naming and on `DeviceMesh` caching by name, with no upstream TODO or issue (inline).
6. `scripts/repro_collective_order.py` -- remove it; it's a probe of documented NCCL behavior with no consumer in the repo (inline).

### Should consider
- `tests/unit_tests/cpu/distributed/test_parallelism_context.py:22-25` -- the test re-derives the FSDP shard group using private FSDP2 helpers (inline).
- `parallelism_context.py:37-44` -- re-sorting `__all__` is unrelated to the fix.

### Questions
- In the production hang, which collectives were at the mismatched sequence number on each rank? Were both on PG 0, and was one of them a P2P op from the internal CP?
- If isolation is still wanted after (1) is answered, should a dedicated FSDP group become an option in FSDP2/DeviceMesh upstream rather than a pre-flatten trick here?

<details><summary>Details</summary>

- Host order within one PG: FSDP2's pre-forward/pre-backward hooks and CP's attention collectives run on the main Python thread in the same program order on every rank. ProcessGroupNCCL launches every op of a PG on that PG's NCCL stream, waiting on the caller's current stream. Issuing from `all_gather_stream` instead of the compute stream changes the dependency, not the sequence number.
- If the change is still wanted after the root cause is established, the smallest version is just the `fsdp.py` pre-flatten with a TODO linking an upstream issue (~10 lines), with no `_FSDP_SINGLE_AXIS_NAMES`, no DDP test, and no script.
- After this PR, CP's `cp` axis still shares WORLD with `loss_mesh` (dp*cp) and grad-norm reductions. That is fine under same-order host submission, and it is the same argument for why the FSDP/CP share is fine as well.

</details>

Not verified: NCCL-internal serialization of one communicator across user streams; DeviceMesh flatten-cache behavior on the pinned torch; no GPU runs. A maintainer still needs to review.

File: `torchtitan/distributed/parallelism_context.py` · line 100

This explanation doesn't follow. The CUDA stream a collective is issued *from* has no effect on its *host* enqueue order. Host order is program order, and in torchtitan that's identical on every rank (FSDP hooks and CP calls run in the same Python sequence everywhere). For a single process group, ProcessGroupNCCL launches every collective on that PG's own NCCL stream, and NCCL serializes the operations of one communicator in launch order. So two collectives on one communicator can't be reordered on the GPU differently per rank. That's why the repro script has to force rank 0 to submit A2A before AG on the host.

If this docstring and the test docstring stay, they will teach a false model of NCCL semantics. Please either show the concrete rank-dependent host ordering that happens in a real run, or restate the rationale. *(unverified: the NCCL-internal serialization detail; a NCCL debug trace from the production hang would settle it.)*
