# [ROCm] Derive set-matrix ROCm version from test-infra

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5794) · state: open · merged: False

## Original PR description

## Summary
- Update `set-matrix.yaml` to take the latest ROCm version from `pytorch/test-infra` `generate_binary_build_matrix` instead of hardcoding `10.0`.
- Keeps a single ROCm matrix entry so expensive 8-GPU jobs do not multiply across every shipped ROCm version.

- claude[bot] · CHANGES_REQUESTED · 2026-11-04T00:53:58Z · [source](https://github.com/pytorch/torchtitan/pull/5794#pullrequestreview-5761657993)

**Verdict: Request changes** -- the new test-infra lookup runs, and can fail, on every `set-matrix` call. That includes the 12 CUDA-only callers and every regular PR, so a ROCm-side problem in test-infra would block all CUDA CI.

**What this PR does.** Before building the matrix, `set-matrix.yaml` now calls `pytorch/test-infra`'s `generate_binary_build_matrix.yml@main`. That call returns the ROCm nightly wheel entries. The workflow picks the highest `gpu_arch_version` from them and uses it instead of the hardcoded `10.0`, both for the ROCm entry and for its `index-url`. CUDA stays hardcoded at `13.2`.

**Example.**
```
# test-infra nightly ROCm list: ["10.0", "10.1"]
before: rocm entry -> gpu-arch-version 10.0, index .../nightly/rocm10.0
after:  rocm entry -> gpu-arch-version 10.1, index .../nightly/rocm10.1   (picked automatically)

# PR touching only CUDA code, workflow calls set-matrix with gpu-arch: cuda
before: no test-infra call; matrix = [cuda]
after:  test-infra call runs; if it returns no ROCm entries -> `set` exits 1 -> CUDA jobs skipped
```

### Must fix
1. The description says what changed but not what broke. Did `rocm10.0` get dropped from the nightly index, or is this preventive? That decides whether automatic tracking is worth a cross-repo `@main` dependency in front of every CI run. A one-line version bump when nightly moves is the alternative to beat.
2. `.github/workflows/set-matrix.yaml:35` -- the lookup isn't gated on whether ROCm is actually selected, and its failure paths (L108-121) `exit 1` regardless (inline).

### Should consider
- `.github/workflows/set-matrix.yaml:51` -- `always() &&` is redundant with `!cancelled()` (inline).

### Questions
- Should ROCm CI track the *latest* nightly ROCm automatically? When test-infra adds a new ROCm version, torchtitan's ROCm CI switches to it at once with no torchtitan commit. Any breakage then shows up as an unexplained red ROCm run instead of on a PR that bumped the version. Maintainers should decide whether that is preferred over an explicit bump.
- CUDA stays hardcoded at `13.2` right next to this. If deriving from test-infra is the right policy, why only for ROCm? If it isn't, the simpler change is bumping `10.0` when needed.

<details><summary>Details</summary>

- Callers: 15 workflows use `set-matrix.yaml`, and 12 of them pass `gpu-arch: cuda`. For those, and for PR events without `gpu-arch: rocm`, the ROCm entry is built and then thrown away, so the lookup does nothing useful but still sits on the critical path.
- The `jq` parse: `unique | sort_by(split(".") | map(tonumber)) | last` is correct for numeric `X.Y` versions. A non-numeric suffix (e.g. `-rc`) would make `tonumber` error, and `set -e` would turn that into the same CUDA-blocking failure. Gating the lookup fixes this case too.
- `.ci/docker/build.sh:38` builds the ROCm image from `rocm/dev-ubuntu-22.04:latest`, so the docker base is already unpinned. Deriving the wheel version doesn't add a pinned-image mismatch, but it does mean nothing in the ROCm toolchain is pinned anymore.

</details>

### inline_comments

- claude[bot] · comment · 2026-11-04T00:53:40Z · [source](https://github.com/pytorch/torchtitan/pull/5794#discussion_r4462294480)

File: `.github/workflows/set-matrix.yaml` · line None

This job only checks `is-experimental`, so it runs for all 15 `set-matrix` callers. That includes the 12 that pass `gpu-arch: cuda` (graph_trainer, RL, release validation, ...) and every ordinary PR, where the final matrix is CUDA-only anyway. It also runs on draft PRs, where `set` is skipped. On top of that, the shell block at L108-121 does `exit 1` whenever the test-infra ROCm list is empty or can't be parsed, without checking whether ROCm was selected. The result: if test-infra stops listing ROCm for nightly, even briefly, or `generate_binary_build_matrix.yml@main` breaks, `set` fails and **all CUDA CI** is skipped on every PR.

Fix: only look up the ROCm version when ROCm will actually be in the matrix. Gate this job on the same condition the step uses (`inputs.gpu-arch != 'cuda'` plus main push / schedule / `gpu-arch == 'rocm'`, and not draft). Then move the `ROCM_BINARY_MATRIX` parsing inside the branch that emits `FULL_MATRIX`, so a CUDA-only run never reads it.
