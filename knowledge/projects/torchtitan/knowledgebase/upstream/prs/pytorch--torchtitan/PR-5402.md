# [rl] Run GRPO on Intel XPU through the stock RL path

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5402) · state: open · merged: False

## Original PR description

Part of the RFC pytorch/torchtitan#5401 (GRPO on Intel XPU).

XPU support decided where each choice is made, no `*_xpu` modules; CUDA behavior unchanged.

- `train.py`: spawned procs get `ZE_AFFINITY_MASK` instead of `CUDA_VISIBLE_DEVICES` when `device_type == "xpu"`.
- `_runtime.py`: skip the `expandable_segments` allocator default on XPU (it invalidates the USM pointers oneCCL registers, so weight-sync transfers read corrupt data); an explicit user value is still honored.
- `generator.py`: on XPU, vLLM runs eager, picks its own attention backend (`AttentionConfig(backend=None)`) and gets no CUDA-graph config.
- `vllm_worker.py` / `vllm_registry.py`: `TorchTitanXPUModelRunner` (TorchTitan runner on vLLM's `XPUModelRunner`) and `TorchTitanXPUWorker` (on vLLM's `XPUWorker`, via `_make_model_runner`), defined and registered only on XPU.
- Tests: device visibility for both devices, the allocator default, the XPU worker and runner (skipped off XPU).

Validated on ALCF Aurora (torch 2.14.0+xpu, oneCCL 2022.1.1, vLLM main, Qwen3-0.6B GRPO, full + LoRA): 18/18 regression (2 nodes x 1/2/4/8/12 tiles, 16 nodes x 4/12 tiles, 1- and 8-node 10-step runs). This branch targets current main, which needs torch nightly while vLLM's XPU support pins torch 2.14, so it was checked line by line against the tested torch-2.14 branch.
