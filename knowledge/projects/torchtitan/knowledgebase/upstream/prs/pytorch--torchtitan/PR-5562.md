# [muse_spark][perf] Split the packed qkv inside the q/k region

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5562) · state: open · merged: False

## Original PR description

**TLDR:** Muse Spark's `muse_spark_attention_qk` region now takes the packed `wqkv` output and splits it itself, so the q and k copies fuse into the norm kernels and the backward writes the packed grad without a cat. One 4-layer unit: decode -0.8% to -1.8% (batch 1-1024), prefill -0.3% to -0.7%, training within noise. Outputs and grads are bitwise identical.

```text
fwd main:     wqkv -> split + 3 copies (eager) -> region(q, k): norm -> RoPE
fwd this PR:  wqkv -> region(qkv): split -> norm -> RoPE, copy v
bwd main:     region bwd -> cat of the q, k, v grads (eager)
bwd this PR:  region bwd writes the packed qkv grad
```

```python
# before (MuseSparkAttention.forward)
query_TNH, key_TKH, value_TKH = self.qkv_linear(x_TD)
query_TNH, key_TKH = self._prepare_query_and_key(query_TNH, key_TKH, positions)
# after
qkv = self.qkv_linear.wqkv(x_TD)
query_TNH, key_TKH, value_TKH = self._prepare_query_key_value(qkv, positions)
```

**Problem**
1. **Packed projection.** `QKVLinear.wqkv` returns q, k and v as one tensor, viewed as `[T, 16 kv heads, 10, 64]`: per kv head, 8 q heads + 1 k + 1 v.
2. **Split in eager.** `QKVLinear.forward` splits it and copies q, k and v out (q's reshape can't be a view; vLLM needs contiguous k and v).
3. **Read again.** `muse_spark_attention_qk` then reads the copied q and k for the norms and RoPE.
4. **Backward.** Autograd cats the three grads back into one packed grad, in eager.
5. **Cost.** Per 4-layer unit: 12 copy kernels and 4 cats. With the q/k norm and RoPE kernels, they take 48 us of a 1.97 ms decode step at batch 1, and 1.94 ms of a 295 ms training step at 16k (kernel time).

**Solution**
1. **Split inside the region.** `MuseSparkAttention` calls `qkv_linear.wqkv(x)` and passes the packed tensor to the region, now `_prepare_query_key_value`, which returns q, k and v.
2. **`QKVLinear.split`.** The split moves out of `QKVLinear.forward` into its own method, with the same `local_map` output types; the region calls it.
3. **What fuses.** The q and k copies fuse into the norm kernels. The cat fuses into the norm-backward kernels, which write the packed grad. v is still copied, now by Inductor.
4. **Unchanged:** `QKVLinear.forward` runs the same ops for Llama 3, Qwen3, GPT-OSS and Muse Glimmer; q, k and v keep their contiguous layouts; the region's options and graph count.
5. **One difference for every caller:** `wqkv` now runs outside `forward`'s `local_map`. That only matters under SPMD type checking (`local_map` is a passthrough otherwise); TP 2 type checks with and without SP pass for Llama 3, Qwen3, Muse Glimmer, GPT-OSS and Muse Spark (Test plan).

You may ask: why not run all of `qkv_linear(x)` inside the region? `wqkv` does the SP all-gather and has its own remat regions, which is why `wo` stays outside too.
You may ask: why not Llama 3, Qwen3 and GPT-OSS too? Their RoPE region is the RoPE module's own forward, which takes q and k. Fusing the split needs a new q/k region in `GQAttention` (split -> norm -> RoPE): a follow-up.
You may ask: why is training flat? The glue saves 0.47 ms, 0.16% of the 295 ms unit, which is below the run-to-run spread (0.7% at 32k).
NOTE: activation checkpointing was off in every GPU run (the TP 2 debug-model layout below fails in backward with it on, on main too); it is covered by the CPU remat checks in the Test plan.
NOTE: not measured: mixed steps (a prefill chunk plus decodes); the split is per token, so they should save what a prefill of the same token count saves.
NOTE: reaches every Muse Spark recipe (the region is on by default): the training recipes and the RL DAPO-math recipe (Dist-MoE experts, so the microseconds carry over, the percentages don't). Not run: loss curve, multi-node training.

**Example.**
```python
# main: split + 3 copies run in eager, then the region reads q and k again

# backward: autograd cats dq, dk, dv into dqkv (eager)

# this PR: the split runs inside the compiled region
qkv = self.qkv_linear.wqkv(x_TD)
```

<details><summary>Details</summary>

What I checked:
- **Callers.** `QKVLinear` is only called through `forward` by `GQAttention`, GPT-OSS and Muse Glimmer, and those paths run the same ops as before. I found no subclass of `QKVLinear` and no hook on `qkv_linear` in RL, experiments or recipes. `QKVLinear` has no `sharding_config` of its own (the colwise sharding is on `wqkv`), so calling `qkv_linear.wqkv` directly still applies the SP input redistribution and keeps the `wqkv.linear` remat region name.
- **`local_map` inside the compiled region.** The region already traced a `local_map` before this PR (`rope._reshape_for_broadcast`), so `split`'s `local_map` there is not new. The region is on by default (`MuseSparkModel.Config.local_compile.regions`), and `muse_spark_mm_fsdp+tp+cp+ep+sp` runs with SPMD typechecking on. That integration test covers type checking + TP + SP with the compiled split.
- **Remat.** v used to come out of `forward` already marked (through `qkv`). It is now produced inside the region from the marked `qkv`, so marking `qkv` alone is enough for q, k and v. The Test plan checks this, including that removing the mark breaks saving `wqkv.linear`.
- **Test.** The updated `test_attention_compile.py` gives the region the packed `qkv` (`(N + 2K) * H` wide, which matches the `[T, K, R, H]` view), so q, k, v and the packed grad are now checked against eager. This is the existing test updated, not a new one.

(Should consider) This docstring sets a rule that nothing enforces: every caller has to mark `qkv` with `remat.recompute_needs_tensor` before calling `split`. The same `wqkv(x)` + mark pair now appears twice, here in `forward` (lines 158-160) and in `MuseSparkAttention.forward` (`model.py:122,127`). Your Test plan shows that leaving the mark out makes saving `wqkv.linear` fail in backward, so a future caller of `split` that forgets it only finds out when remat runs.

One option: give `QKVLinear` a small `project(x)` method that runs `wqkv(x)`, marks the result and returns it. Then `forward` becomes `return self.split(self.project(x))`, Muse Spark calls `self.qkv_linear.project(x_TD)`, and this sentence can be deleted. It has two callers, so it isn't a single-use helper. Not blocking: keeping the docstring is fine if you'd rather not add the method.
