# [RL] Keep varlen RL working on ROCm by deferring backend choice to vLLM

[Upstream PR](https://github.com/pytorch/torchtitan/pull/4866) · state: open · merged: False

## Original PR description

## Problem

`vllm_attention_backend` names `CUSTOM` for every varlen model on every
platform. `CUSTOM` is the generator's own varlen backend -- it computes with the
kernel the trainer computes with, which is what makes one model definition valid
on both sides.

On ROCm it cannot run. `CUSTOM` attends over vLLM's paged KV cache, and torch's
ROCm varlen kernel refuses a page table outright:

```
RuntimeError: [ROCm] mha_varlen_fwd: block_table_ must be nullopt
```

An inherited assert (`FlashAttention version not detected`) fires first, but it
is only a symptom: vLLM detects no flash-attn version on ROCm, and `CUSTOM`
never calls vLLM's flash-attn anyway.

## Fix

Gather each sequence's pages into contiguous rows; the page table is then not
needed. The gathered rows go to the same AOTriton varlen kernel the trainer
runs, so `CUSTOM` keeps its point.

Two details make that work.

**Bottom-right causal.** A decode query sits at the end of its sequence, so the
mask must be aligned per sequence -- `k_len - q_len` differs across a batch that
mixes prefill and decode. AOTriton spells this as
`WindowValue::BottomRightAligned`, which ROCm's `calculate_swa` installs only
when no explicit window is given. `varlen_attn`'s causal branch always sends
`window_size_right=0`, which overwrites the sentinel and degrades the mask to
top-left, so this calls `torch.ops.aten._flash_attention_forward` directly. A
sliding window cannot be combined with bottom-right alignment today, so those
layers raise. Unequal K/V head dims raise for the same reason.

**Fixed-stride rows.** Packing would need the batch's total context length on
the host -- a sync per layer, and unreadable during a CUDA graph capture. Rows
are laid out at a fixed stride instead and `seqused_k` carries the real lengths,
so the kernel never reads the padding. Under capture the stride is the whole
block table; otherwise it is the batch's own longest context.

Also drops `assert not attn_metadata.use_cascade`: vLLM removed the field, so on
current vLLM the assert raises `AttributeError` on every call rather than
checking anything.

## User-facing change

| | before | after |
|---|---|---|
| ROCm varlen RL | `AssertionError` at the first attention call | trains |
| ROCm sliding-window varlen | same `AssertionError` | `NotImplementedError` naming the gap |
| ROCm unequal K/V head dims | same `AssertionError` | `ValueError` naming the gap |
| CUDA | unchanged | unchanged |

## Numerics and cost

8x MI355X (gfx950), ROCm 10.0, torch 2.16.0.dev20261009+rocm10.0,
`rl_grpo_qwen3_0_6b_varlen`, trainer TP=2 / generator TP=4, 10 steps.

| leg | decode_ms | `logprob_diff/max` peak | mean |
|---|---|---|---|
| before (deferring to vLLM's `ROCM_ATTN`) | 212.2 | 11.67 | 3.75 |
| this change | 667.0 | 8.46 | 3.19 |

One run per leg, no fixed seed. Four runs of the gathered path gave peaks of
4.70, 6.64, 6.53 and 8.46, so the spread is about +-2 and the parity numbers
should be read as "no worse", not as an improvement.

Attention itself is ~20us; the rest is the gather, which runs at ~12% of HBM
bandwidth. A fused gather kernel is the obvious follow-up, but it cannot remove
the padding volume -- that needs paged varlen upstream (see the `TODO`).

## Correctness of the mask

Checked against an explicit bottom-right causal reference (`max |err|`, bf16):

| batch | result |
|---|---|
| decode only, `q=[1,1,1] k=[100,256,37]` | 2.4e-03 |
| prefill only, `q=[128,64] k=[128,64]` | 7.0e-03 |
| extend, `q=[64] k=[256]` | 2.9e-03 |
| mixed, `q=[128,1,1] k=[128,256,37]` | 7.5e-03 |
| mixed, fixed stride 512 | 7.8e-03 |

With `varlen_attn`'s `window_size=(-1, 0)` instead of the sentinel, the mixed
cases are off by 3.2 -- that is the degradation this PR works around.

## Testing

`tests/rl/unit_tests/cpu/test_vllm_wrapper.py` covers the gather on CPU: each
sequence comes back verbatim at the offset `cu_seqlens_k` reports, in both
stride regimes and across page sizes; the capture layout keeps one shape across
three different context-length sets; and a strided cache view is read without
materializing the cache.

**What this PR does (at `aeecdda`).** On ROCm, `CUSTOM` now picks a new `AiterVarlenInnerAttentionImpl`. It copies each sequence's paged KV into contiguous rows (`_gather_paged_kv`) and calls `aiter.flash_attn_varlen_func`. While a CUDA graph is being captured, every sequence is padded to the full block-table width so tensor shapes stay fixed. The base impl is split into `_activate_flash_attention_impl` and `_attend` hooks, and the `use_cascade` assert is removed.

**Example.** `rl_grpo_qwen3_0_6b_varlen` on MI355X:
```
main:    CUSTOM -> TorchTitanVarlenInnerAttentionImpl -> AssertionError: FlashAttention version not detected
this PR: CUSTOM -> AiterVarlenInnerAttentionImpl -> gather pages -> aiter varlen
         trainer still: torch varlen_attn -> torch's ROCm flash backend (AOTriton/CK)
```

This is the claim the design depends on, and I can't find support for it in the repo. On ROCm the trainer's `VarlenInnerAttention.forward` (`torchtitan/models/common/attention/attention.py`) calls torch's `varlen_attn`. - claude[bot] · comment · 2026-11-03T20:00:48Z · [source](https://github.com/pytorch/torchtitan/pull/4866#discussion_r4459798576)

File: `torchtitan/rl/generator/vllm/attention.py` · line None

This path makes two device-to-host syncs per attention layer on every forward. `repeat_interleave` has no `output_size`, and `int(starts[-1])` reads the total back to the host. On Qwen3-0.6B that is 56 syncs per forward on every eager step: prefill, batches larger than the capture sizes, and all of `cuda_graph.mode="NONE"`.

`sequence`, `position`, `blocks` and `offsets` depend only on `block_table` and `seqused_k`, and those are the same for every layer. Build the indices once per forward instead: in the metadata builder (`TorchTitanVarlenInnerAttentionMetadataBuilder`), or cached on `attn_metadata`. Take the total from host-side metadata (vLLM keeps `seq_lens` on the CPU too) and pass it as `output_size`. Each layer is then left with only the two index reads `key_cache[blocks, offsets]`.

- claude[bot] · comment · 2026-11-03T20:00:54Z · [source](https://github.com/pytorch/torchtitan/pull/4866#discussion_r4459799531)

File: `torchtitan/rl/generator/vllm/attention.py` · line None

`VLLMCudaGraphConfig.mode` defaults to `"FULL"`, so on ROCm this is the decode path in practice. It copies `num_seqs * max_model_len` K rows and the same number of V rows per layer, and the cost scales with `max_model_len` rather than the live context.

Example: Qwen3-0.6B at generator TP=4 has 2 KV heads x 128 x bf16, i.e. 512 B per token for K. With 256 seqs:
- at the recipe's `seq_len=2048`, each layer allocates ~256 MiB for K and ~256 MiB for V;
- at 32k context, ~4 GiB for K plus ~4 GiB for V per layer, reserved in the graph pool. That likely OOMs a long-context RL run (*unverified*).

Please measure decode throughput and peak memory against the CUDA-side baseline, or against vLLM's `ROCM_ATTN`, at the recipe context length and at a long one. If the cost is real, a Triton gather (vLLM's ROCm AITER FA backend does this with `cp_mha_gather_cache`) or a cap that raises `ValueError` above some `max_model_len` is better than silently moving the whole table.
