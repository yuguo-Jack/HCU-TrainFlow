# [RL] Keep varlen RL working on ROCm by deferring backend choice to vLLM

[Upstream PR](https://github.com/pytorch/torchtitan/pull/4866) · state: open · merged: False

## Original PR description

## Problem

The generator names `CUSTOM` for every attention config that is not flex. `CUSTOM`
is the generator's own varlen backend (`torchtitan/rl/generator/vllm/attention.py`),
and torch's ROCm varlen kernel cannot serve a vLLM generator:

- it rejects `num_splits` -- the same limit `Controller` already cites when it
  refuses batch-invariant mode on ROCm, and
- it rejects a paged KV cache (`mha_varlen_fwd: block_table_ must be nullopt`).

What fails first is neither of those:

```
File "torchtitan/rl/generator/vllm/attention.py", line 158, in forward
    self.vllm_flash_attn_version is not None
AssertionError: FlashAttention version not detected.
```

That assert is inherited from vLLM's `FlashAttentionImpl`, and `CUSTOM` never calls
vLLM's flash-attn -- it computes with `torch.nn.attention.varlen.varlen_attn_out`.
So the assert is a symptom, and deleting it would only surface the two real limits.
The docstring says so, to stop the next reader "fixing" it that way.

## Fix

Return `None` on ROCm -- `AttentionConfig`'s documented "select automatically" --
rather than naming a backend. vLLM's own ROCm dispatch already gates its candidates
on architecture and head size and falls back when they do not hold, so naming one
here would duplicate that and fail where vLLM would have coped. Flex and the CUDA
path are unchanged.

The choice was spelled out twice on `main` -- in `VLLMEngine._build_engine_args` and
again in `generate.py` -- so it now lives in one `vllm_attention_backend()` that both
call.

This means a ROCm generator attends with a different kernel from its trainer, which
departs from running the same kernels on both sides. Log-prob parity therefore
becomes a property to measure rather than one the shared model definition supplies --
see below.

## Verification

8x MI355X (gfx950), ROCm 10.0, torch 2.16.0.dev20261009+rocm10.0, vLLM
0.32.0rc1.dev246, aiter 0.1.26.dev0, `rl_grpo_qwen3_0_6b_varlen`, trainer TP=2 +
generator TP=4. Measured in a dev container, not a released ROCm vLLM image.

### Does it run

| leg | backend selected | steps completed | outcome |
| --- | --- | --- | --- |
| varlen, main | `CUSTOM` | 0 | `AssertionError: FlashAttention version not detected` |
| varlen, this PR | `ROCM_ATTN` x4 ranks | 8 | trains normally |

With `backend=None` vLLM offers `['ROCM_ATTN', 'ROCM_AITER_UNIFIED_ATTN',
'TRITON_ATTN']` and picks `ROCM_ATTN`. Setting `VLLM_ROCM_USE_AITER=1` adds
`ROCM_AITER_FA` to that list, which is the intended composition: the choice stays
vLLM's.

### Log-prob parity against flex as the same-kernel reference

The two stock recipes are not comparable: `rl_grpo_qwen3_0_6b_flex` uses generator
TP=2 and `max_tokens=100`, against TP=4 and 700 for varlen. `bit_wise/logprob_diff/max`
is a max over tokens, so 7x shorter completions shrink it on their own. The flex leg
below is therefore the **varlen** recipe with `attn_backend="flex"` swapped in, so
attention is the only difference. 8 steps, temperature 0.8.

| step | varlen `max` | varlen `mean` | varlen clipped | flex `max` | flex `mean` | flex clipped |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 0.71 | -0.0017 | 0.0043 | 0.60 | -0.0019 | 0.0051 |
| 2 | 1.26 | -0.00060 | 0.0058 | 0.94 | -0.0010 | 0.0047 |
| 3 | 1.43 | -0.0014 | 0.0089 | 3.00 | -0.0027 | 0.011 |
| 4 | 2.56 | -0.0044 | 0.016 | 5.06 | -0.0035 | 0.015 |
| 5 | 2.84 | -0.0044 | 0.023 | 5.75 | -0.020 | 0.021 |
| 6 | 3.73 | -0.010 | 0.026 | 8.31 | -0.019 | 0.025 |
| 7 | 3.68 | -0.0039 | 0.016 | 2.46 | -0.0021 | 0.020 |
| 8 | 6.41 | -0.0080 | 0.026 | 2.92 | -0.0015 | 0.017 |

(`bit_wise/logprob_diff/{max,mean}`, `loss/ratio_clipped_frac`.)

Worst `max` 6.41 (varlen) vs 8.31 (flex); peak clipped fraction 0.026 vs 0.025;
median `|mean|` 0.0042 vs 0.0024. At matched sampling the different-kernel generator
costs nothing measurable -- flex is if anything slightly worse on worst-case `max`.
Both legs grow with step count, so the driver is completion length and training
drift, not the attention backend.

Caveat: one run per leg, temperature 0.8, no fixed seed. The step-to-step swings
(flex 8.31 at step 6, back to 2.46 at step 7) mean this shows the two backends are in
the same band, not that they are equal to within a few percent.

For contrast, the stock flex recipe (`max_tokens=100`) peaks at `max` 1.88 and
clipped 0.0092 -- which is what makes an unmatched varlen-vs-flex table look like a
varlen regression.

### Tests

CPU-only, pinning `current_platform`: flex is platform-independent, non-ROCm varlen
stays `CUSTOM`, ROCm varlen defers with `None`.

## Relationship to flex

Flex becomes attractive on ROCm once a ROCm vLLM image ships with a torch new enough
for `create_block_mask(separate_full_blocks=...)`, which torchtitan's flex mask passes
unconditionally -- then `rl_grpo_*_flex` runs the same kernel family on both sides. On
the measurement above that is an architectural tidiness argument, not a parity one.

This PR is still needed either way. A newer torch does not fix `CUSTOM` on ROCm -- the
`num_splits` and `block_table` limits hold there too -- and varlen-only configs such as
the MoE debug RL recipes have no flex variant.
