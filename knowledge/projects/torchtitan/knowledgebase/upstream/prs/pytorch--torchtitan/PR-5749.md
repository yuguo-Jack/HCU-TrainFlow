Written with Claude Code: the analysis, measurements and test plan below.

**Needs retesting on H100.** All numbers are from GB300, where CPU-GPU copies ran at ~90 GB/s per direction. An earlier H100 run copied at ~32 GB/s (PCIe), so copies would take ~2.8x longer there.

**TLDR:** A new opt-in flag keeps Adam/AdamW's moments in pinned CPU memory between steps. `optimizer.step()` streams them through the GPU in chunks. Updates are bitwise identical to today's.
- Qwen3-4B, FSDP=2, 2 GB300: peak GPU memory 30.7 -> 18.6 GiB per rank, for 22% fewer tokens/s.
- If the freed memory lets a run drop full activation checkpointing, the run gets faster: Qwen3-8B SFT +10.5% tokens/s.

```python
AdamW.Config(pattern=r".*", state_offload=OptimizerStateOffloader.Config())
```

**Problem**
1. **Moments.** Adam keeps `exp_avg` and `exp_avg_sq` for every weight: 8 bytes per parameter in fp32, 4 with `moment_dtype="bfloat16"`.
2. **Resident all step.** They stay in GPU memory (HBM) through forward and backward. Only `optimizer.step()` reads them.
3. **Cost.** Qwen3-4B at FSDP=2: 15.0 GiB of the 30.7 GiB peak per rank.
4. **When it matters.** `rl_grpo_muse_glimmer_30b_search_r1` turns on full activation checkpointing (full AC) only to make room for the moments. Its docstring: they add ~37 GB per GPU at the first step, and default remat then runs out of memory at step 2.
   Estimated per trainer GPU (FSDP=3 x TP=2, fp32): params 17.3 + grads 17.3 + moments 34.6 = 69.2 GiB of an 80 GB H100. Offload frees 31.2 GiB of it.

**Solution**
1. **Idea.** Moments live in pinned CPU buffers between steps. `step()` streams them in chunks (whole parameter shards, ~256 MiB of moments) through two GPU slots into the unchanged fused Adam kernel.
2. **Overlap.** While Adam updates one slot, the other slot stores its previous chunk and loads the next one, on two side streams.
3. **No host wait.** `step()` ends with the compute stream waiting for the last store. `state_dict()` and `load_state_dict()` wait for it before the CPU touches the moments.
4. **Enable.** `state_offload` on `Adam.Config` / `AdamW.Config`. Default `None` keeps today's path.
5. **Unchanged.** Params, grads, clipping, checkpoint keys and values, DTensor sharding, LR metric names.

```text
                warm-up | chunk 0       | chunk 1           | chunk 2
GPU compute:            | Adam 0 in A   | Adam 1 in B       | Adam 2 in A
slot A copies:  load 0  |               | store 0 -> load 2 |
slot B copies:          | load 1        |                   | store 1 -> load 3
```

**Results**

Numerics: bitwise identical to resident moments (loss, grad_norm, params, moments, checkpoints). Why: the same fused AdamW kernel runs on the same values; only where the moments wait between steps changes.

You may ask:
- Why a wrapper instead of chunking inside `Adam`/`AdamW`? Neither class changes. The wrapper narrows their param groups to one chunk per inner `step()`.
- Why two copy streams? One stream (load, update, store in order) was slower: offloaded step alone on one GB300, fp32 155 vs 176 ms, bf16 65 vs 97 ms.
- Why not `training.enable_cpu_offload`? It also moves params and grads, and runs Adam on the CPU.
- Why does `lr_scheduler.py` change? LR metric keys use the optimizer class name. Without it, `lr/AdamW` becomes `lr/OptimizerStateOffloader`.
- Why reject `Optim.enable_accelerator_graph`? `step()` picks chunks on the host, and its first loads wait on events recorded outside the capture. A capture probe on GB300 fails on such a wait.
- Why does torchft reject `state_offload`? Its full saves read `cache_state_dict`, which skips `OptimizerStateOffloader.state_dict()` and its wait for the last stores.
- Why `torch.from_dlpack` on the CPU state? DCP's `DefaultStager` fails on a DTensor whose local tensor starts at a storage offset > 0. The alias starts at 0. The TODO in `_state_like` holds the repro.

NOTE:
- Launch with `torchrun --numa-binding=node`, so the pinned buffers sit on the GPU's NUMA node. An H100 run of an earlier version lost 17% tokens/s without it.
- Host memory: one pinned copy of the moments per rank (Qwen3-4B fp32, FSDP=2: 16.1 GB per rank).
- Fused Adam/AdamW only, params on CUDA. Raises for `training.enable_cpu_offload` and `create_seed_checkpoint` runs.
- Not run: PP, EP, HSDP, MoE, H100, the `search_r1` recipe (8 H100s and a retrieval server), the 4-GPU `full_checkpoint` integration test (run on 2 GPUs).

**What this PR does.** `OptimizerStateOffloader` wraps a fused `Adam`/`AdamW` and shares its `param_groups` and `state`. It keeps `exp_avg`/`exp_avg_sq` in one pinned CPU slab per moment, as parameter-shaped DTensor views. In `step()` it packs params into ~256 MiB chunks. For each chunk it binds GPU slot views as the state, narrows the param groups to that chunk, and calls the unchanged inner `step()`, with loads and stores on two side streams. `lr_scheduler.get_metrics` unwraps it so the `lr/AdamW/*` keys stay the same.

**Example.**
```python
AdamW.Config(pattern=r".*", state_offload=OptimizerStateOffloader.Config())
# Qwen3-4B, FSDP=2, fp32 moments (per the description):
#   before: peak HBM 30.70 GiB/rank, 36182 tok/s/GPU
```

<details><summary>Details</summary>

Checked and found no issue:
- **Stream ordering.** The first load waits on the compute stream, which covers slot memory the caching allocator hands back from pending compute work. A slot is reused only after its `slot_free` event, recorded after the previous store. Each store waits on the compute stream after that chunk's Adam step. The slots are freed only after both side streams are synchronized.
- **State identity.** `cpu_state` puts the original DTensor objects back after each chunk. Slab pointers stay stable through `load_state_dict`, and torchft's `cache_state_dict` references stay valid.
- **`init_optim_state`.** State is allocated eagerly, so it is a no-op, and the `isinstance(optim, (Adam, AdamW))` reset in `utils.py:72` is never reached for the wrapper.
- **bf16 moments.** The `initialize_moments` pre-hook on the inner optimizer runs once per chunk and is a no-op because state already exists. `restore_moment_dtype` is bypassed by the `load_state_dict` override, and the slab dtype is already right.
- **Hooks.** Step hooks are registered on the container (MoE bias, aux loss, qk_clip), so they run once per step, not once per chunk.
- **graph_trainer paged stash.** `skips_step_on_found_inf` returns False for the wrapper, so that path raises a clear `ValueError`. Loud, and an experiment.
- **PP.** Multiple model parts or optimizers each get their own offloader, streams and slabs. They step one after another, so peak HBM is set by the largest single pair of slots.
- **Tests.** Turning offload on in the existing `full_checkpoint` entry, rather than adding a new one, is the right shape. Resident optimizer resume is still covered by the `fsdp2_tp2_pp2` save/load entry, though with type checking off.

</details>

<details><summary>Details</summary>

Checked in the new stream ordering, no issue found:
- **Slot lifetime.** Slots are allocated on the compute stream and dropped when `step()` returns, after `compute.wait_stream(d2h)`. The caching allocator reuses a block only for allocations on its own stream, and every later compute-stream use is ordered after the last store. Every H2D load was already waited on by the compute stream, so the H2D stream needs no join.
- **Next step's loads.** At the top of `step()`, `h2d.wait_stream(compute)` runs, and the compute stream already waited on the previous stores, so a load can't read a slab before the last store into it lands.
- **Host writes in `load_state_dict`.** Syncing D2H is enough. Each store waits on a compute stream that waited on every load, so no load from the last step is still running.
- **Async checkpoint.** `get_flat_optim_state_dict` calls `optim.state_dict()` (`utils.py:98`), which is the wrapper's synced override. `optim_step` calls `maybe_wait_for_staging()` before the next update (`training_engine.py:891`), so background staging of the slabs finishes before new stores start.
- **Hook bypass.** The wrapper's `state_dict()` skips post-hooks registered on the inner optimizer. The only such hook, `_save_host_lr`, exists only under `enable_accelerator_graph`, which offload bans.
- **torchft check.** `TorchFTOptimizersContainer.Config.__post_init__` doesn't shadow a parent check, because `OptimizersContainer.Config` defines none.
- **Several offloaders in one container.** Each one's loads wait on the compute stream, which waits on the previous offloader's last store, so offloaders don't overlap each other. This affects throughput only.

</details>

**Layer**

We think core `components/optim` is the right home for now, with the private-API gaps named in TODOs. The three homes compared:

| | on CPU | where Adam runs | FSDP2 / DTensor | DCP |
|---|---|---|---|---|
| this PR | Adam moments only | GPU, the unchanged fused kernel, 2 streamed slots | yes | yes, same keys |
| torchao `CPUOffloadOptimizer` | param copy, grads, state | CPU | no, "for single GPU training" (its README) | own format |
| FSDP2 `CPUOffloadPolicy` | params, grads, state | CPU | yes | yes |

1. FSDP2: `OffloadPolicy` decides where sharded params live. `torch.optim` creates the optimizer state on the param's device, and FSDP2 never touches it. Its only optimizer hook is `set_post_optim_event`. A state-only policy would mean FSDP2 wrapping `optimizer.step()`, and it would miss params FSDP2 does not shard (this PR handles plain tensors too).
2. torchao: a different algorithm (ZeRO-Offload for one GPU: the update runs on the CPU, no grad clipping). Core torchtitan also can't depend on torchao (principle 3).
3. Other trainers keep this in their own optimizer layer: Megatron-LM `HybridDeviceOptimizer`, DeepSpeed ZeRO-Offload, prime-rl `CPUOffloadOptimizer` (on by default there). Megatron and DeepSpeed run Adam on the CPU. prime-rl moves the whole state to the GPU for each step. None streams moments through two slots into the fused GPU kernel, so there is nothing to reuse yet.
4. Private APIs: PyTorch uses the same ones internally. FSDP2 builds DTensors with the constructor (`_from_local_no_grad`), and DCP's stager pins with `_pin_memory_utils`. Each use here has a TODO:
   - In-place pinning: the TODO links the open PyTorch issue.
   - The DTensor constructor: the TODO at that line names the gap, a public way to build a DTensor whose local tensor stays on the CPU.
   - The DCP stager bug: it has a repro ready and will be linked from the TODO once filed.

If you'd rather have it upstream later, the closest fit is `torch.distributed.optim`, next to `ZeroRedundancyOptimizer`. torchtitan would then keep only the `state_offload` field and its build branch. We'd like to prove it in a recipe here first.

Should consider: these two `synchronize()` calls are a host sync on every step. The CPU can't queue the next step's forward until the last D2H store lands, and they are also the reason accelerator graphs are banned. Both stated reasons can be handled in stream order:
