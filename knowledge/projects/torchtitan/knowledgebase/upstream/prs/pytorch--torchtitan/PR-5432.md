# [muse_spark][perf] Run the fp32-stream RMSNorms on the fused kernel

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5432) · state: open · merged: False

## Original PR description

**TLDR:** Muse Spark's residual-stream RMSNorms now run one fused kernel instead of ~20 small ones, in both the trainer and the generator: 2 layers -7% in training, -5% at prefill, -2 to -4% at decode. The math doesn't change: the norm already computed in fp32, and its error vs fp64 is the same as on main.

**Problem**
1. **fp32 stream.** Muse Spark keeps the residual stream in fp32 (`residual_dtype`), and `attention_norm` / `ffn_norm` read it. The trainer and the generator run the same code.
2. **bf16 weight.** The norm weight is bf16 on both sides (trainer: FSDP mixed precision; generator: `model_dtype="bfloat16"`), so `weight + gain_center` is bf16.
3. **Slow fallback.** `F.rms_norm` uses its fused kernel only when weight and input share a dtype; otherwise it runs pow, mean, rsqrt and muls (~20 kernels fwd+bwd).
4. **Already fp32.** The fallback multiplies the fp32 input by the bf16 weight, which PyTorch promotes to fp32.
5. **Cost.** 1047 us per norm at 4k tokens (ideal 76 us), two per layer.

**Solution**
1. **Cast the weight** to the input dtype in `MuseSparkRMSNorm.forward`, so `F.rms_norm` takes the fused kernel.
2. **Exact cast.** bf16 -> fp32 loses nothing, and `weight + gain_center` still adds in bf16 first, as on main.
3. **Unchanged.** The math: the error vs fp64 is the same before and after, in the trainer and in the generator.

```text
trainer and generator (same norm code)
before:  x fp32 + w bf16      --F.rms_norm--> pow, mean, add, rsqrt, mul, mul ...   (~20 kernels, fp32 math)
after:   x fp32 + w.to(fp32)  --F.rms_norm--> fused rms_norm kernel                (fwd 1, bwd 2, fp32 math)
```

Correctness: not bitwise, but the error vs fp64 is unchanged.
```text
max relative error vs fp64, op level (attention_norm, 4k)   output    input grad   weight grad
bf16 weight, fp32 stream   main                             5.1e-8    5.7e-8       1.7e-3
                           this PR                          5.1e-8    5.7e-8       1.7e-3
fp32 weight                main / this PR (bitwise)         5.1e-8    5.7e-8       2.2e-7
```
2 layers at 4k: the difference from main is about the size of what a 1-ulp change of the input causes (0.9-0.96x), because small differences flip some routing decisions.

You may ask: why not compile the norm instead? That is the separate, optional follow-up: it adds a region and 12 compiled graphs for a 1-5% gain on top of this cast.
You may ask: why not cast the input to bf16 instead? That rounds the fp32 stream before the norm and changes the math, in the trainer and the generator.
NOTE: reaches every Muse Spark recipe (training and the RL trainer/generator). Not tested: loss curve, multi-GPU, the trainer vs generator logprob gap in an RL run.

**Test plan**
No new test: numerics are unchanged (table above). `pre-commit run --files torchtitan/models/muse_spark/model.py`.
