# [rl] Send trainer microbatches over Monarch RDMA by default

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5413) · state: open · merged: False

## Original PR description

**TLDR:** Trainer microbatches now go over Monarch RDMA by default: `async_loop.batcher.rdma_min_tensor_bytes` goes from `None` (by value) to `1024`. On one host, a 1 GiB microbatch takes 0.55 s by RDMA over ibverbs vs 1.9 s by value, and every read was byte-exact. `rdma_min_tensor_bytes=None` keeps the by-value message.

**Problem**
1. The RDMA path for trainer microbatches is opt-in: by default each trainer rank gets its column of the batch inside the `forward_backward` RPC message.
2. By value, the controller pickles every microbatch, Monarch copies it, and the rank unpickles it.
3. That grows with the microbatch: 16 MiB takes 21 ms per call by value vs 8.4 ms by RDMA, and 1 GiB 1.9 s vs 0.55 s (ibverbs, one host).

**Solution**
1. `Batcher.Config.rdma_min_tensor_bytes` defaults to 1024: tensors of at least 1 KiB stay in the batcher as RDMA buffers; smaller ones (token counts) stay in the message.
2. If Monarch has no RDMA backend (`monarch.rdma.get_rdma_backend() == "none"`), the batcher logs one warning and sends by value. Otherwise Monarch uses ibverbs where the host has it, else TCP.
3. The batcher creates the CUDA context that silences Monarch's per-buffer `[RdmaXcel]` log right before its first registration. It used to do it at spawn, where by default it would race trainer rank 0 for GPU 0.
4. The controller no longer warns about RDMA without `preprocess_microbatch_groups_lazily`: it would fire on every default config.
5. Unchanged: `None` is exactly the old by-value path.

**Results**

Stress, one host (H100 devserver, CPU tensors, Monarch 0.7): the owner registers a fresh microbatch with random bytes each step, a reader process reads it, the owner drops the previous one. 5 steps per size, medians of steps 2-5. Every read was byte-exact. Read = reader side, fresh destination included. Call = one actor call, RDMA vs the same microbatch by value:
```text
per microbatch   read, ibverbs   read, TCP   call: ibverbs / TCP / by value
1023 B           0.12 ms         0.19 ms     2.5 / 3.1 / 2.7 ms     (below 1 KiB: by value)
1 KiB            7.8 ms          0.5 ms      11 / 2.9 / 3.2 ms
1 MiB            6.4 ms          1.9 ms      12 / 7.8 / 5.5 ms
16 MiB           3.6 ms          15 ms       8.4 / 19 / 21 ms
256 MiB          83 ms           449 ms      0.17 / 0.49 / 0.56 s
1 GiB            334 ms          1.6 s       0.55 / 1.8 / 1.9 s
```
- 4 readers, 256 MiB each, at once: 81 ms over ibverbs (13 GB/s together), 630 ms over TCP.
- Registering (in the batcher, at pack time) pins memory over ibverbs: 26 ms at 256 MiB, 264 ms at 1 GiB; under 1 ms over TCP.
- Up to 1 MiB, an ibverbs read costs 6-8 ms, a few ms more than by value.

GPU, Qwen3-0.6B, H100, batch invariant, lockstep, trainer DP 1 + one TP 1 generator (2 GPUs), 4,096-token microbatches, 5 steps:
```text
                                    loss/mean, step 5   bit_wise/logprob_diff/max   read_microbatches/max, steps 1-5
None (by value)                     0.00061             0                           -
1024 (default), ibverbs             0.00061             0                           126, 36, 12, 19, 21 ms
1024, TCP                           0.00061             0                           57, 15, 10, 14, 17 ms
```
- `loss/mean` is bitwise equal across the three runs at all 5 steps; 0 `[RdmaXcel]` lines. Step 1 includes RDMA setup.
- TCP = `MONARCH_RDMA_DISABLE_IBVERBS=1 MONARCH_RDMA_ALLOW_TCP_FALLBACK=1`. The `None` run is from an earlier build of this change; `None` runs none of the changed code.
- Measured before rebasing onto the current main, which has since changed only generator files under `torchtitan/rl`.

You may ask:
- **Why not probe ibverbs at startup?** A failed registration leaves Monarch's RDMA manager dead in its process, so a probe needs a child process. Like TorchStore, we only check that Monarch has an RDMA backend.
- **What about a host that lists ibverbs devices it can't use?** It fails at the first batch: set `rdma_min_tensor_bytes=None`, or `MONARCH_RDMA_DISABLE_IBVERBS=1` for TCP in every process (weight sync included). The docstring says so.
- **Why 1 KiB?** Registering one buffer costs 0.4-1 ms (stress above), far more than sending an 8 B token count, and `RDMABuffer` rejects empty tensors.

NOTE:
- The RL GPU CI now takes the RDMA path (ibverbs or TCP, whichever its containers have).
- Every default run now holds ~256 MiB on GPU 0 (trainer rank 0's GPU on one host) for that CUDA context, in the batcher process, until Monarch logs the line once (TODO in `create_cuda_context_to_silence_monarch_log`). The first batch's `batcher_pack` span includes creating it.
- With `preprocess_microbatch_groups_lazily=False` (the default) nothing hides the reads: each rank reads its microbatches one at a time before compute, ~6-8 ms each over ibverbs at small sizes.
- Not tested on more than one host.

**Test plan**
- `pytest tests/rl/unit_tests/cpu` (repo root, Monarch 0.7): 510 passed, 5 skipped.
- `test_rdma_microbatch.py`: the threshold boundary (a 1 KiB tensor goes by RDMA at 1024 and by value at 1025); by value with `None` and with no RDMA backend; the CUDA context created once, at the first batch; 4 rank processes on the default config read their columns byte-exact over real Monarch TCP across 3 released batches, then all read one 42 MiB microbatch.
- `test_batcher_actor.py`: the batcher process on the default config.
- The stress script and GPU runs above.
