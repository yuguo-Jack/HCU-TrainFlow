# [rl][perf] FULL CUDA graphs: separate decode graphs for softmax-attention generators

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5591) · state: closed · merged: False

## Original PR description

**TLDR:** Under FULL CUDA graphs, decode batches of softmax-attention generators now replay graphs captured for decode, not for a prefill of the same token count, at every generator DP size. Qwen3-4B on one GB300, 256 decoding sequences: 12.7 -> 8.0 ms per decode step. Greedy outputs unchanged.

**Problem**
1. `VLLMCudaGraphConfig.mode` defaults to FULL. vLLM's V1 runner then captures one graph per token count and keys it by token count only.
2. It captures that graph with a prefill-shaped dummy batch (`max_query_len = num_tokens`) and replays it for every step of that size, including uniform decode.
3. Attention launch parameters are fixed at capture. At 256 tokens, FA4 replays the launch it chose for a 256-token prefill: 2072 CTAs per layer instead of its persistent 152 (Qwen3-4B).
4. `TorchTitanCudagraphDispatcher` already captures separate decode graphs under FULL, but `TorchTitanGPUModelRunner.load_model` installs it only for linear-attention (GDN/KDA) models.
5. Cost: FA4 decode is 2.2x slower per call at 256 sequences (225 vs 101 us). Qwen3-4B decode step 12.7 ms instead of 8.0 ms. Every dense recipe that runs FULL hits it once a step decodes 64+ sequences.

**Solution**
1. Install `TorchTitanCudagraphDispatcher` for every model, so uniform decode batches dispatch to FULL_DECODE_ONLY-style graphs captured for decode.
2. A uniform decode batch above the largest decode graph replays the mixed graph, as vLLM's own FULL dispatch does. Two cases reach it:
   - DP > 1: vLLM pads a decoding or idle rank to the busiest rank's token count and allows only the DP-synced mode. A decode-graph lookup at that size finds nothing and fails "No matching cudagraph found", so without this rule the dispatcher could only be used at DP = 1. DP > 1 is how the generator gets EP ranks, so that would leave out every EP MoE generator (e.g. the Muse Spark DAPO recipe, FULL at DP = 4).
   - Capture sizes that skip `max_num_seqs`: decode batches between the largest decode graph and `max_num_seqs` used to run eager.
3. Batch-invariant runs of linear-attention models keep those batches on the decode kernels, as on main: the packed kernels in the mixed graph do not match them bitwise.
4. Unchanged: FULL_DECODE_ONLY and NONE, prefill and mixed-batch graphs, every recipe config. Linear-attention models at DP > 1 still run FULL_DECODE_ONLY (their metadata builder reports uniform-only graph support there), so the new rule does not reach them.

You may ask:
- **Why not FULL_DECODE_ONLY?** It drops prefill graphs. It matches this PR on decode (Qwen3-4B B = 256: 7.84 ms), but prefill steps then run eager.
- **Why not switch to vLLM's V2 model runner?** V2 captures decode-only graphs and matches this PR (Qwen3-4B B = 256: 8.07 ms). But TorchTitan's runner is V1-only (SP padding, the GDN/KDA dispatcher), V2 fails at warmup on hybrid models, and V2 skips a DP collective.
- **At DP > 1, can ranks replay different graphs in one step?** Yes. A decoding rank replays its decode graph while a prefilling rank replays the mixed graph of the same size. The only cross-rank contract is that every EP rank passes the same row count to the MoE, and every graph of a DP-synced step has the step's token count (Dist-MoE derives its row count from it, and padded rows are `-1` routes that never leave the rank).

NOTE:
- The speedups above are GB300, TP 1, dense Qwen3 at DP = 1. The DP > 1 path is covered by CPU dispatch tests only so far; the end-to-end check is the B200 RL suite's Dist-MoE recipe (`rl_grpo_moe_debug_dist_moe_tp2_ep4`: generator DP 2 x TP 2 x EP 4, FULL, replicas schedule different request counts), which runs with `ciflow/b200`. Not measured: MoE decode speed at DP > 1, TP > 1, H100.
- One Qwen3-4B B = 256 process read 9.43 ms; the other and two earlier runs read 8.00-8.07 ms.

### 1. Linear-attention models change behavior when batch invariance is off (not mentioned in the PR)

`worker.py:94-97`. On main, every uniform decode batch from a GDN/KDA model under FULL went to `decode_dispatcher`. A decode batch larger than the largest decode graph therefore ran **eager on the decode kernels**.

With this PR, unless batch-invariant mode is on, that batch now replays the **mixed graph with the packed linear-attention kernels**. This happens at DP = 1 when the capture sizes skip `max_num_seqs`.

The PR body says "Batch-invariant runs of linear-attention models keep those batches on the decode kernels, as on main". That implies the other case changed, but the "Unchanged" list does not say so. Please either:
- add a line saying this is intended (packed kernels are numerically fine for decode, just not bitwise equal to the decode kernels), or
- keep linear-attention models on the old routing whenever `has_linear_attention` is set. Then the new rule only affects softmax-attention models, which is the PR's stated scope:
  ```python
  and (num_tokens <= self.max_decode_capture_size or self.has_linear_attention)
  ```
  This also removes the `is_in_batch_invariant_mode()` call from the per-step dispatch path. That path is hot, though the call is cheap.

I lean toward the second option. It matches the title, removes a combination nobody has tested, and makes the docstring shorter.

### 2. Batch-invariant softmax attention is fine
I first worried that sending the same request to a decode graph at B=4 and to the mixed graph at B=6 could change its numerics. It doesn't in batch-invariant mode: `attention.py:248` forces `num_splits=1` there, so the per-row reduction is the same whichever graph is replayed. It would help to say so in one line, since that is the obvious question a reader of `BITWISE_PARITY.md` will ask.

### 3. Where `max_decode_capture_size` is defined
`worker.py:72` sets it only inside `if cudagraph_mode == FULL`. `dispatch` only reads it under the same condition, so this is safe today. It is still an attribute that only exists in one mode. Setting `self.max_decode_capture_size = 0` in `__init__` would be more robust.

### 4. Tests
- `test_full_mode_softmax_attention_decode_dispatch` builds the runner with `object.__new__` and uses `__mro__[1]`. That is brittle, but it follows the existing pattern in this file, so this is not blocking.
- Good: the DP-padded case (`valid_modes={FULL}`, 8 tokens) and the capture-size gap case are both tested, along with the batch-invariant branch.
- Missing: a test for case 1 (linear attention, batch invariance off, above the largest decode graph). Whichever behavior you choose there, a test would pin it down.

### 5. @felipemello1's inline comment (too much text, prefill perf?)
I agree the class docstring has grown long. A suggested shorter version with a diagram:

```python
class TorchTitanCudagraphDispatcher(CudagraphDispatcher):
    """Under FULL, replay decode-captured graphs for uniform decode batches.

    vLLM's FULL mode keys graphs by token count only, and captures each one as
    a prefill (max_query_len == num_tokens). Decode then replays prefill-sized
    kernel launches (FA4: 2056 vs 152 CTAs/layer at 256 decodes) and the wrong
    numerical path for Attention Gym linear attention. We add the native
    FULL_DECODE_ONLY keys alongside the FULL ones:

        uniform decode, n <= max decode graph -> decode graph (FULL_DECODE_ONLY keys)
        uniform decode, n >  max decode graph -> mixed graph   (as vLLM FULL does)
        prefill / mixed batch                 -> mixed graph   (unchanged)

    "n > max decode graph" happens when DP > 1 pads a rank to the busiest
    rank's token count, or when capture sizes skip max_num_seqs. Graphs on
    different DP ranks may differ within a step but always share the step's
    token count, which is all Dist-MoE EP needs.

    Cost: one extra capture per decode batch size.
    """
```

On "how": the mixed graph and the decode graph for the same token count are now separate `BatchDescriptor`s (`uniform=True` vs `False`). Each one is captured with its own batch shape, so FA4 picks its persistent decode launch for the decode graph.

On prefill performance: prefill and mixed batches still dispatch through `super().dispatch` and are unchanged. The only cost is capture: 14 s / 0.26 GiB -> 15 s / 0.28 GiB on Qwen3-4B, per the PR body. It would help to say "prefill/mixed graphs unchanged" in the docstring, as above.

Closing.

Correction to "Why not switch to vLLM's V2 model runner?" above: V2 does not capture decode-only graphs under FULL. Before vLLM 23110a0c9ef8 ("[Bugfix] Capture prefill kernels for mixed FULL graphs", 2026-09-24), V2 captured mixed FULL graphs with `max_query_len` taken from the one-token dummy batch, so decode replayed FA4's decode launch by accident. Our benchmark ran vLLM 9f03b510c (2026-09-14), before that fix, so V2's 8.07 ms came from it. After the fix V2 captures mixed FULL graphs with `max_query_len = num_tokens` like V1; neither runner has separate decode graphs under FULL.
