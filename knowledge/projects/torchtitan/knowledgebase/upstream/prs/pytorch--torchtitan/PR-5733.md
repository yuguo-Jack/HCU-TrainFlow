# [muse_spark] raise the rmsnorm region's recompile limit for RL

## Why

`muse_spark_rmsnorm` is one `local_compile` boundary shared by every residual-stream norm, with `recompile_limit=16` sized for pretraining's 12 graphs. An RL trainer runs the model in more ways: a `no_grad` log-prob pass and a training pass, over micro-batches of varying token counts. On Muse Spark with the `dapo_math` recipe's LoRA setup the first training step dies with `FailOnRecompileLimitHit` in that boundary (fullgraph=True makes the 17th graph a hard failure).

Measured on an 8xH200 box with `TORCH_LOGS=recompiles` over two rollouts (Muse Spark 4-layer slice, TP2/EP2, rank-32 attention LoRA, log-prob and training passes), graphs per boundary:

| boundary | graphs | limit |
|---|---|---|
| `muse_spark_rmsnorm` | 22 | 16 -> 32 |
| `muse_spark_attention_qk` | 8 | 16, unchanged |

The rmsnorm graphs split on: weight present or not, weight width 8192 or 4096 (expert space), FSDP-wrapped or plain module type, input token count, and `requires_grad` of the input (log-prob vs training pass).

## What changed

One line plus its comment: `muse_spark_rmsnorm` compiles with `recompile_limit=32`, following the per-boundary convention (`models/common/rope.py` does the same for DeepSeek-V4 with 32). This replaces the earlier `LocalCompileConfig.recompile_limit` knob from this PR's first revision, which no recipe set.

## Numerics / performance

No numerics change: the same graphs compile, the limit only stops the 17th from raising. With the raised limit the RL run completes two rollouts and two training steps with the regions on.

## Testing

- The measurement run above completes end to end with the limit raised; on the pinned v0.4.0 it fails at the first training step.
- No new test: the failure is a hard error at the first step of any RL run on this model, which cannot come back silently.

- claude[bot] · comment · 2026-11-02T05:55:49Z · [source](https://github.com/pytorch/torchtitan/pull/5733#discussion_r4439317433)

File: `torchtitan/distributed/local_compile.py` · line None

If the field stays, apply the floor in the callers, not inside the override hook. As written, the floor only applies when an out-of-tree `_compile` override remembers to call `self._compile_kwargs(...)`. An override that doesn't silently ignores `recompile_limit`, and that's exactly why the example subclass in the test had to change.

Compute it in `bind_local_compile` and `bind_compile` before calling `config._compile(...)`, and keep `_compile` a `@staticmethod`. Then the hook contract stays the same, and every backend gets the floor.
