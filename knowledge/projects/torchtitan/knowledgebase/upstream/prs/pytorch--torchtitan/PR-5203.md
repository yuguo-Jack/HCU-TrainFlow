# [Draft][KimiK3][Optimizations]Add opt-in joint compilation of chunked projection and cross-entropy

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5203) · state: open · merged: False

## Original PR description

ChunkedLossWrapper currently compiles cross-entropy separately from its LM-head projection. Add opt-in `linear_cross_entropy=True` to include an ordinary TP1 projection in the existing loss compilation region. On GB200, this reduces absolute peak allocation by one chunk-sized BF16 logits buffer in the tested cases, with no consistent throughput improvement.

The wrapper calls an FSDP-registered `Linear.cross_entropy` method. FSDP hooks remain outside the tensor-only compiled region, and the existing chunk loop, normalization, hidden-gradient accumulation and final-chunk synchronization are reused.

```python
config.loss = ChunkedLossWrapper.Config(
    num_chunks=8,
    linear_cross_entropy=True,
    loss_fn=CrossEntropyLoss.Config(global_vocab_size=163840),
)
# Include "loss" in config.model.local_compile_regions.
```

Limited to TP1, one prediction/label pair and an ordinary single-projection Linear. Specialized heads (including HiMidLoLinear) and custom losses are rejected. Default behavior and checkpoint parameter names are preserved.

## GB200 measurements

PyTorch 2.15.0.dev20260928+cu130; hidden 7168, vocabulary 163840, BF16 inputs/parameters. Separate fresh processes, compiled CE in both variants, eight chunks, three initial iterations and ten measured iterations. Peak is absolute PyTorch allocated memory; timing is isolated head/loss forward+backward.

| Local tokens | Separate projection + compiled CE peak | Joint peak | Saved | Time: separate → joint |
|---:|---:|---:|---:|---:|
| 1,024 | 6.7556 GiB | 6.7166 GiB | 40 MiB (0.58%) | 17.12 → 17.12 ms |
| 8,192 | 7.8887 GiB | 7.5762 GiB | 320 MiB (3.96%) | 45.48 → 46.00 ms |
| 32,768 | 11.7737 GiB | 10.5237 GiB | 1,280 MiB (10.62%) | 164.68 → 166.02 ms |

Full-size **two-rank FSDP** at 1,024 local tokens reproduces **40 MiB/rank** savings: 12.1626 → 12.1235 GiB, 47.17 → 47.12 ms on rank 0. Single-GPU eight-chunk graph replay is 16.874 → 16.865 ms.

Absolute peaks matter: subtracting each variant's baseline hides the saving because their retained allocations differ. An allocator probe identifies a 1,280 MiB `Linear._linear` allocation in the separate-projection path at 32,768 tokens, absent in the joint path; the saving persists after full garbage collection. This is evidence of a tensor-lifetime reduction, not proof of a logits-free kernel.

## Validation

- Three CPU test methods pass in the GB200 container with standard imports; eager FP32/BF16 comparisons include ignored labels, strided inputs, inference and bias.
- Actual Inductor CPU compilation matches loss and gradients against separately compiled CE.
- Two-rank GPU tests pass with and without CUDA graph capture/replay, including loss and hidden/weight/bias gradients and an entirely ignored chunk.
- Full-size 1,024-token/eight-chunk single-GPU loss, hidden gradients and head weight gradients are bitwise identical between variants.
- Full-size graph replay outputs are bitwise stable across replays.
- Final formatting/lint checks and targeted Pyrefly pass. Full-project local type checking lacks some training dependencies; it is not claimed as passing.
- GPU execution tested production code at e0e0b2c; the subsequent benchmark-only change adds absolute peak/baseline JSON summaries.

## Draft limitations

Keep this opt-in and in draft pending representative training validation. The 40 MiB/rank saving at the short-sequence point is modest. Full Kimi training, optimizer memory, convergence, TP and specialized heads are not validated. Chunking itself is a separate tradeoff: at 1,024 tokens, the isolated one-chunk control uses less memory and runs faster than eight chunks; at longer sequences chunking substantially lowers peak memory.
