# [rl] Controller GC: freeze the setup heap, fold generator metrics per rollout and group

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5290) · state: closed · merged: True

## Original PR description


**TLDR:** Every full garbage collection in the RL controller walks every object the collector tracks. After setup that's ~1M objects that never die, plus 16 generator-metric records per generation that a Verifiers rollout keeps until it ends. This PR freezes the setup objects out of the collector and folds each rollout's generator metrics into one `Mean` and one `Max` per key. In a local multi-turn run, the longest GC pause drops from 0.98 s to 0.06 s, and GC time from 1.63 to 0.57 s per minute.

**Problem**
1. **Full collections walk the whole heap.** CPython runs one whenever the objects that survived into the oldest generation grow by 25%. It visits every tracked object (dicts, lists, class instances) in the process.
2. **Setup leaves ~1M objects behind.** After setup the controller holds the modules it imported (torch, vLLM, Verifiers), configs, the dataset and actor handles. They live until exit, and each full collection rescans them: 0.4-0.7 s on an H100 host.
3. **Each generation adds 16 metric records.** The generator returns 8 metrics, each as a `Mean` and a `Max` record, so 48 tracked objects. The Verifiers `GenerationServer` keeps all of them until the rollout ends.
4. **The group copies them again.** `compute_rollout_metrics` puts every turn's records into the group's metrics, which live until the step is logged.
5. **Cost:** in an agentic run with ~2,000 rollouts in flight, ~24 turns each, a full collection paused the controller for 4.7-8.6 s, adding up to 12-37 s of GC per step.

```text
                          before                                   after
setup objects (~1M)       rescanned by every full collection      frozen: never scanned again
in-flight rollout         16 records x turns                       16 records
finished group            16 records x turns x rollouts            16 records
```

**Solution**
1. `Controller.run()` calls the new `GarbageCollector.freeze(reason)` before starting its loops: a full collection, then `gc.freeze()`. The setup objects move to a generation the collector never scans.
2. New `metrics.fold(metrics)` merges the `Mean`, `Max`, `Min` and `Sum` records that share a key into one record per type. `MetricsProcessor` reduces the result to the same numbers.
3. `GenerationServer` folds each generation's metrics into the rollout's. `compute_rollout_metrics` folds the turns' generator metrics.
4. Unchanged: every logged value, up to float rounding of the sums.

**Results**
The real loop on 2 H100s: Qwen3-0.6B, trainer on one GPU and one generator on the other. A Verifiers env runs 12-turn episodes of fake tool output, so no sandboxes are needed. 64 rollouts per step, ~320 in flight, 30 steps per arm. The census thread logs per-generation GC time and object counts every 30 s.

```text
                                       main          this PR
GC time                                1.63 s/min    0.57 s/min
longest pause                          0.98 s        0.06 s
full collections (count, mean pause)   7, 0.77 s     10, 0.04 s
objects the collector scans            1.37M         47K
step time                              12.3 s        13.0 s   (run-to-run noise; GC isn't the bottleneck at this scale)
```

You may ask:
- **Why not disable the GC, or raise its thresholds?** Disabling it leaks every reference cycle. Higher thresholds make collections rarer but no shorter, and each one still walks the setup objects.
- **Why freeze in `run()` and not in `train.py`?** Launchers that build the `Controller` themselves call `setup_async()` and `run()` without going through `train.main()`.
- **Why fold, not make `Metric` cheaper (`__slots__`)?** Slots would save one object of the three per record. Folding makes a rollout's record count stop growing with its turns.

NOTE: not run at the ~2,000-rollouts-in-flight scale of the agentic run above, and that run's heap was never inventoried. How much of its 4.7-8.6 s these two changes remove is an estimate.
NOTE: a Verifiers rollout whose episode raises before `pop_generation_metadata` still leaves its metadata in `GenerationServer`. After folding that's ~20 objects per failed rollout.
