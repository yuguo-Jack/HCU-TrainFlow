# [kimi_k3] Add a renderer for K3's XTML chat encoding and a tokenizer.json converter

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5584) · state: open · merged: False

## Original PR description

## TLDR

Adds `KimiK3Renderer` for Kimi K3's XTML chat encoding and `scripts/checkpoint_conversion/convert_kimi_k3_tokenizer.py`, which writes the `tokenizer.json` TorchTitan needs and checks both against the released checkpoint. On the real checkpoint the renderer's token ids equal `apply_chat_template`'s on all 9 conversation settings tested, and the converted tokenizer matches K3's on every test text.

## Problem

1. Kimi K3 marks chat structure with four special tokens (`<|open|>`, `<|close|>`, `<|sep|>`, `<|end_of_msg|>`) around `message`, `think` and `response` tags. The `renderers` package covers Kimi K2 / K2.5, not this encoding, so K3 RL cannot render prompts or parse completions.
2. The checkpoint ships a tiktoken BPE (`tiktoken.model`) with remote tokenizer code. TorchTitan's `HuggingFaceTokenizer` loads `tokenizer.json`, which the release does not include.
3. K3's `apply_chat_template` adds an internal `thinking_effort=max` system message by default; a renderer that only follows the message builder misses it and renders different prompts.

## Solution

1. `torchtitan/models/kimi_k3/renderer.py`: `KimiK3Renderer` implements the `renderers.Renderer` protocol for system, user and assistant messages, mirroring `encoding_k3.build_chat_segments` (markers as special tokens, everything else ordinary text).
   - `KimiK3RendererConfig.thinking` / `thinking_effort` mirror `apply_chat_template`'s arguments; `thinking_effort` defaults to `"max"` like the checkpoint.
   - `render` marks everything after the assistant role header as sampled; stop tokens are `<|end_of_msg|>` and `[EOS]`.
   - `parse_response` splits a completion into reasoning (`think`) and answer (`response`); a completion truncated while thinking keeps its reasoning and has no answer.
   - Select it with `from_renderers(CustomRendererConfig(import_path="torchtitan.models.kimi_k3.renderer.KimiK3Renderer"))`.
2. `scripts/checkpoint_conversion/convert_kimi_k3_tokenizer.py`: converts the BPE with transformers' `TikTokenConverter`, adds the 256 special tokens at K3's ids, saves `tokenizer.json`, then checks the converted ids against K3's tokenizer and `KimiK3Renderer` against `apply_chat_template`.
3. `torchtitan/models/kimi_k3/README.md`: how to produce the tokenizer and select the renderer.

Example: `render([{"role": "user", "content": "2+2?"}])` with the defaults (`thinking=True`, `thinking_effort="max"`); line breaks added. `<|open|>`, `<|close|>`, `<|sep|>` and `<|end_of_msg|>` are single special-token ids, everything else is ordinary BPE text. The first message is the one `apply_chat_template` adds by default (Problem 3).

```text
generation prompt:
<|open|>message role="system" type="thinking-effort"<|sep|>`thinking_effort` guides on how much to think ... Now the system is invoked with `thinking_effort=max`.<|close|>message<|sep|><|end_of_msg|>
<|open|>message role="user"<|sep|>2+2?<|close|>message<|sep|><|end_of_msg|>
<|open|>message role="assistant"<|sep|><|open|>think<|sep|>

completion (sampled by the generator, stops at <|end_of_msg|>):
2 plus 2 is 4.<|close|>think<|sep|><|open|>response<|sep|>\boxed{4}<|close|>response<|sep|><|close|>message<|sep|><|end_of_msg|>

parse_response(completion) -> reasoning_content="2 plus 2 is 4.", content="\boxed{4}"
```

Unchanged: the model, state-dict adapter and existing configs.

## Results

On the released checkpoint (`moonshotai/Kimi-K3`, GB300 venv), the converter reported:

```
tokenizer.json: 163840 tokens (163584 base + 256 special); 9 texts match K3's tokenizer
KimiK3Renderer matches apply_chat_template on 9 conversation settings
```

The 9 settings are thinking with effort `max`, thinking with effort `low`, and non-thinking, each over a single-turn, a system + user, and a multi-turn conversation with a prior assistant turn. The texts cover math, code, Chinese, emoji, whitespace runs and the XTML markers.

We have used this renderer and tokenizer for Kimi K3 RL (DAPO-Math) runs with real weights.

NOTE: tools and tool messages are not supported yet; the renderer raises on them.

`bridge_to_next_turn` keeps the previous prompt and sampled completion ids through `<|end_of_msg|>` and appends only the new messages and the generation prompt. A re-render would rebuild the previous assistant turn from `parse_response`'s stripped text, which can drop or re-tokenize sampled ids, so the next prompt would no longer extend the previous one. A completion cut at the token limit gets the closing markers a re-render of the parsed turn would emit, after its sampled ids. It falls back to a re-render for assistant or tool messages, a cut inside a marker, and a completion stopped at `[EOS]`.

## Test plan

- New `tests/unit_tests/cpu/models/kimi_k3/test_kimi_k3_renderer.py` (8 tests, no checkpoint needed): a byte-level stand-in tokenizer pins the exact rendered layout with and without thinking (including the thinking-effort message), the sampled mask, stop tokens, `parse_response` on a full and a truncated completion, the tools error, and `bridge_to_next_turn`: it equals the full re-render for a canonical completion, keeps a leading `\n` that `parse_response` strips (a re-render drops it), closes a turn cut in the think channel, between channels or in the response channel exactly as a re-render does, and falls back for a cut inside a marker or an assistant message.
- `python -m scripts.checkpoint_conversion.convert_kimi_k3_tokenizer <checkpoint> <out>` on the released checkpoint: output above; the written `tokenizer.json` is byte-identical to the one our K3 runs use.
- `pre-commit run --files` on the touched files: clean (Pyrefly skipped locally).

### Review: do we have to introduce the conversion script?

- [x] Read the diff (renderer, tests, conversion script, README)
- [x] Decide whether `convert_kimi_k3_tokenizer.py` is needed
- [x] Review the renderer

**Short answer:** We need a `tokenizer.json` from somewhere, but not this script in its current form. It does two separate jobs, and neither is specific to K3 in a way that justifies a separate per-model script.

#### Why some conversion is needed

`HuggingFaceTokenizer._load_tokenizer_from_path` (`torchtitan/components/tokenizer.py:191-267`) only loads `tokenizer.json`, or `vocab.{json,txt}` + `merges.txt`. K3 ships only `tiktoken.model` plus remote code, so without a converted file you can't tokenize at all. Adding a `tiktoken.model` path to core isn't a good fit either:
- The pre-tokenizer regex (`pat_str`) and the special-token ids live in the checkpoint's remote Python code.
- Rebuilding BPE merges from tiktoken ranks is what `transformers.TikTokenConverter` does, and core shouldn't depend on transformers or tiktoken (principle 1).

#### Why the current script is the wrong shape

1. **The problem isn't K3-specific.** `torchtitan_recipes/tests/models/kimi_k2_7.py:259` points `kimi_k2_5` at `./assets/hf/Kimi-K2.5`. I believe that release also ships `tiktoken.model` with the same remote `TikTokenTokenizer` (exposing `pat_str` and `special_tokens`), but I haven't checked. If so, that recipe has the same gap with no documented fix. `convert()` (lines 74-113) only reads `type(reference).pat_str`, `reference.special_tokens` and `tiktoken.model`, so nothing in it is K3-specific. A K3-named script would just be copied for K2.5 later (principle 3).
2. **It mixes conversion with a parity test.** `check_renderer()` (lines 116-142) checks `KimiK3Renderer` against `apply_chat_template`. That's a numerical-parity check and belongs next to `scripts/checkpoint_conversion/numerical_tests_kimi_k3.py`, which already depends on `tiktoken`/`transformers` and the remote code. Bundling it means you can't regenerate the tokenizer without also importing the renderer and `renderers` package, and the renderer check gets no visibility as a test.
3. **Placement:** `scripts/checkpoint_conversion/` holds weight converters and parity tests. A tokenizer-asset tool fits better next to `scripts/download_hf_assets.py`.

#### Suggested options (in order of preference)

- **A. Avoid the script entirely.** The PR says the produced `tokenizer.json` is byte-identical to the one our K3 runs already use. If we can host that file (or upstream it to the HF repo), the README becomes "download `tokenizer.json` with `download_hf_assets.py`" and the script goes away. The one-time-conversion caveat could become a short README snippet (~10 lines using `TikTokenConverter`) instead of a maintained script.
- **B. Keep the conversion, but make it generic.** Rename it to something like `scripts/convert_tiktoken_tokenizer.py`, keep only `convert()` plus the id-equality check on `_TEXTS`, and reference it from both the kimi_k2_7 and kimi_k3 READMEs.
- In either case, **move `check_renderer` into `numerical_tests_kimi_k3.py`** (or a separate `--check-renderer` section there). That way the renderer and `apply_chat_template` parity claim in the PR stays reproducible.

#### Other notes on the renderer

- `bridge_to_next_turn` (`renderer.py:230-296`): this addresses your earlier "re-render is not a good idea" comment for the common case. Re-render is now only a fallback (assistant/tools in `new_messages`, a cut inside a marker, or `[EOS]`), so that thread can probably be resolved.
- `renderer.py:291`: `sampled_mask` is `False` for the whole bridged sequence, including `previous_completion_ids`. `render()` marks assistant turns as sampled. Please confirm the `renderers` bridge contract expects the previous completion to be unmasked here. Otherwise multi-turn loss masking would differ between bridged and re-rendered prompts.
- `renderer.py:290`: the previous ids all get `message_indices=-1`, while `message_roles` only covers `new_messages`. That's internally consistent, but worth a one-line docstring note that indices are relative to `new_messages`.
- `convert_kimi_k3_tokenizer.py:141`: `3 * len(_CONVERSATIONS)` hardcodes the length of the `(thinking, effort)` tuple at line 121. If you keep this code, hoist the tuple into a constant and use `len()`.

I didn't run the checkpoint-based script, since there's no checkpoint here. This is a read-only review; I made no code changes.
