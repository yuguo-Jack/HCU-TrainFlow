# Compile Muse Glimmer Softcap

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5630) · state: closed · merged: True

## Original PR description

Adding local compile for softcap layers in MuseGlimmer. This is similar to what MuseSpark is doing [here](https://github.com/pytorch/torchtitan/blob/main/torchtitan/models/muse_spark/model.py#L327).

This idea is that softcap is a memory-bound kernel. The bwd math is sth like this `out = dz * temp * (1 - tanh^2) * (1/temp) * mult`. There are two optimizations you can do for this kernel: (1) cancel `temp * 1/temp` by hand so that it only does two precision rounding instead of four; (2) recompute tanh in the bwd from the saved bf16 logits instead of saving the fp32 tanh output; as a result, we can have less data movement for memory-bound kernel. 

Local compile only solves (2), but (1) is a todo here. 

If executing purely in eager, the code is sth like this:
```python
### FWD
tmp1 = x.to(fp32)
tmp3 = tmp1 * 0.19611613513        # x * mult
tmp5 = tmp3 * 0.05                 # z = x*mult/temp
tmp6 = libdevice.tanh(tmp5)        # y = tanh(z)
tmp8 = tmp6 * 20.0                 # out = temp * y
tl.store(out_ptr0 + x0, tmp6)      # <- extra 4 B/elt write: y, saved for bwd
tl.store(out_ptr1 + x0, tmp8)      #    out

### BWD
tmp0  = tl.load(in_ptr0 + x0)      # g  (fp32)
tmp3  = tl.load(in_ptr1 + x0)      # y  (fp32, saved from fwd)  <- replaces x + the tanh recompute
tmp2  = tmp0 * 20.0                # (a) d(out)/d(tanh) = temp
tmp4  = tmp3 * tmp3
tmp6  = 1.0 - tmp4                 #     tanh'(z) = 1 - y^2
tmp7  = tmp2 * tmp6                #     g * temp * (1 - y^2)
tmp9  = tmp7 * 0.05                # (2) d(z)/d(x*mult) = 1/temp
tmp11 = tmp9 * 0.19611613513       #     d(x*mult)/dx = mult
tl.store(out_ptr0 + x0, tmp11.to(bf16))
```

By applying local compile, the code becomes this:

```python
### FWD
tmp0 = tl.load(x_ptr + x0).to(fp32)    # read x            2 B/elt (bf16)
tmp3 = tmp0 * 0.19611613513            # x * mult
tmp5 = tmp3 * 0.05                     # z = x*mult/temp
tmp6 = libdevice.tanh(tmp5)            # y = tanh(z)       (y is NOT stored)
tmp8 = tmp6 * 20.0                     # out = temp * y
tl.store(out_ptr + x0, tmp8)           # write out         4 B/elt (fp32)

### BWD
tmp0  = tl.load(g_ptr + x0)            # read g            4 B/elt (fp32)
tmp3  = tl.load(x_ptr + x0).to(fp32)   # read x            2 B/elt (bf16, saved)
tmp2  = tmp0 * 20.0                    # (a) d(out)/d(tanh) = temp
tmp6  = tmp3 * 0.19611613513           #     x * mult
tmp8  = tmp6 * 0.05                    # (1) recompute z
tmp9  = libdevice.tanh(tmp8)           #     recompute y = tanh(z)
tmp12 = 1.0 - tmp9 * tmp9              #     tanh'(z) = 1 - y^2
tmp13 = tmp2 * tmp12                   #     g * temp * (1 - y^2)
tmp14 = tmp13 * 0.05                   # (2) d(z)/d(x*mult) = 1/temp
tmp15 = tmp14 * 0.19611613513          #     d(x*mult)/dx = mult
tl.store(dx_ptr + x0, tmp15.to(bf16))  # write dx          2 B/elt (bf16)
```

The change is small and the reasoning holds up. With `.float()` moved inside the compiled region, the compiled backward can save the bf16 logits and recompute `tanh`, so it no longer needs the fp32 `tanh` output. That is the bandwidth win described in the PR body. `batch_invariant=True` is correct because the op is elementwise. I have one real correctness issue (in a comment) and a few suggestions.

### Issues

**1. The TODO copied into `muse_spark/model.py` is wrong for that model** (`torchtitan/models/muse_spark/model.py:327-330`)

`MuseSparkLMHead` subclasses `HiMidLoLinear`. Its `forward` already returns **fp32** (`torch.mm(..., out_dtype=torch.float32)`, `hi_mid_lo_linear.py:87-119`). So `postprocess_logits` there gets fp32 logits, not bf16, and "recompute tanh from the saved bf16 logits" doesn't apply.

For Muse Spark, a recompute-tanh backward would save fp32 input instead of fp32 `tanh` output. That is the same traffic, so the only possible gain is the rounding cancellation in (1). Either reword the TODO to say only that, or drop it from muse_spark and keep the PR to Glimmer.

**2. The region name `"softcap"` is generic and inconsistent with the sibling model** (`muse_glimmer/model.py:229`, `:308`)

Muse Spark names its region `"muse_spark_logit_postprocess"`. The registry is process-wide and keyed by name (`_LOCAL_COMPILE_CALLBACKS`), and it allows several callbacks per name. If another model later registers its own `"softcap"`, enabling it in one model's `local_compile_regions` also compiles the other's function, which is surprising. I'd suggest `"muse_glimmer_logit_postprocess"`, or the shared option in item 3.

### Suggestions

**3. Consider one shared soft-cap function** (CLAUDE.md "Unify Across Models" / "Reuse over duplication")

`SoftCappedLinear.postprocess_logits` and `MuseSparkLMHead.postprocess_logits` do the same math: `temp * tanh(x * mult / temp)`, or `x * mult` when `temp is None`. The only difference is that Glimmer adds a leading `.float()`, which is a no-op on Spark's fp32 input.

A single module-level function in `torchtitan/models/common/`, decorated with `@local_compile("logit_soft_cap", batch_invariant=True)`, could serve both. Each head would call it with `(logits_TV, self.output_multiplier, self.output_soft_cap_temp)`. The future custom `autograd.Function` from the TODO would then live in one place too. This is optional and fine as a follow-up, but it's the natural home for item (1).

**4. Numerics evidence is missing**

This changes computation slightly. Inductor's `libdevice.tanh` can differ by an ULP from eager `aten::tanh`, and fusion can change rounding. CLAUDE.md asks for proof:
- a loss and grad_norm comparison with `seed=42, deterministic=True` (eager vs. `"softcap"` enabled, following `scripts/loss_compare.py`), or a short convergence curve;
- ideally the memory and throughput numbers that motivate the change (peak memory or step time on a Glimmer config, at least 10 steps).

**5. Tests**

There is no test showing the compiled region matches eager. A small CPU unit test would catch future regressions in the region: build `SoftCappedLinear`, call `apply_local_compile(["softcap"])`, and compare forward and backward against `apply_local_compile([])` with a tolerance. Cover both `output_soft_cap_temp=None` and `20.0`.

**6. Style nits**
- The new `postprocess_logits` has no docstring, unlike its Muse Spark counterpart.
- New model tensor code should use shape suffixes (`logits_TV`) per CLAUDE.md.
- The TODO comment sits above the decorator and reads as documenting the forward. Consider moving it into the method docstring.

### Looks good
- Splitting the method so `forward` calls `self.postprocess_logits(super().forward(input))` keeps `Linear.forward` (and its sharding hooks) outside the compiled region, the same as Muse Spark.
- The guards on `self.output_multiplier` and `self.output_soft_cap_temp` are static per model, so they shouldn't cause recompiles. Varying chunk lengths under `ChunkedLossWrapper` will be handled by automatic dynamic shapes after the first recompile.
- Enabling the region by default in `local_compile_regions` is consistent with how `rope` and `fused_binary_activation` are handled. `validation.py:140` already rejects local compile together with `spmd_typechecking`.
