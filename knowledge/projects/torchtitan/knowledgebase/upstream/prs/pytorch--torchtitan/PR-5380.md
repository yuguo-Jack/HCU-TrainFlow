# [moe][perf] EP=1 inference: gather-sum MoE combine region (3/6)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5380) · state: open · merged: False

## Original PR description

**TLDR:** At inference, the EP=1 MoE combine becomes a compiled gather-sum: one Qwen3.5-35B-A3B MoE layer 353 -> 300 us at 34 tokens, 1242 -> 711 us at 4096 tokens. Reference path (Dist-MoE has its own combine), low priority.

**Stack** (6 PRs, merge bottom-up; this PR is in **bold**)

| # | PR | Independent? | Needs (stack positions) |
|---|---|---|---|
| 1 | AllToAll dispatcher: permute and unpermute with gathers | yes | — |
| 2 | Argsort expert ids on the narrowest integer type | yes | — |
| **3** | **EP=1 inference: gather-sum MoE combine region** | **no** | **2** |
| 4 | EP=1 inference: sort-region MoE dispatch | no | 2, 3 |
| 5 | Gather-sum dispatch and combine for training, at any EP | no | 4 |
| 6 | Turn on gather-sum dispatch and combine for DeepSeek-V3 and Kimi | no | 3, 4, 5 |

**Problem**
1. **Combine.** After the experts run, `LocalTokenDispatcher.combine` adds each token's `top_k` expert rows back into that token.
2. **Today.** It calls `deterministic_scatter_add`: a sort, an `index_put_(accumulate=True)` and 2 `_assert_async` checks.
3. **Not needed at inference.** Each token owns exactly `top_k` rows, so a gather and a sum are enough.
4. **Cost.** At 4096 tokens, score multiply + cast + scatter take ~500 us, about 40% of the layer.

```text
today:    rows sorted by expert -> x score -> scatter-add into tokens                 (sort + index_put + 2 asserts)
this PR:  rows sorted by expert -> gather each token's top_k rows -> weighted sum in fp32   (2 kernels)
```

**Solution**
1. Under `no_grad`, `dispatch` keeps the expert-sort order and the unsorted scores in `LocalDispatchMetadata`.
2. New `_gather_weighted_sum`, in a `moe_combine` local-compile region: gather, sum in fp32, round once.
3. Qwen3.5 (and 3.6/3.8, which reuse its list) turns the region on.
4. Unchanged: training (grad on), eager calls and the EP dispatchers keep the scatter-add.

**Results**
```text
Numerics: not bitwise. Today rounds to bf16 after every route; this PR sums in fp32 and rounds once.
          rel L2 vs today: 3.0e-3
          max rel L2 vs fp64, op level (CPU probe of the same combine, stack position 6):
          eager combine 2.34e-3 | gather-sum 1.66e-3 = bf16 rounding floor

one Qwen3.5-35B-A3B MoE layer (ffn_norm + MoE), no_grad, CUDA graph replay, GB300, us per call
T=34     353 -> 300   (49 -> 32 kernels)
T=64     448 -> 385
T=4096  1242 -> 711

4-layer Qwen3.5-35B-A3B generator (vLLM, CUDA graphs, GB300), median kernel time over 15 decode / 9 prefill shapes
decode   -11%
prefill  -26%
```

You may ask:
- Why only `no_grad`? Training needs a backward for the gather; stack position 5 adds it.
- Why not eager too? Unrolled over `top_k` it is ~3 x `top_k` eager kernels; the scatter-add is faster in eager.

NOTE:
- EP=1 here (`LocalTokenDispatcher`), i.e. TP=1 generators: MoE requires EP >= TP (`decoder.py:184-189`).
- At EP>1, decode gains little: AllToAll copies its split sizes to the host, so it runs without CUDA graphs.

**Test plan**
```bash
pytest tests/unit_tests/cpu/models/common/test_token_dispatcher.py tests/unit_tests/cpu/models/qwen3_5/test_offset_rmsnorm.py
```

- felipemello1 · comment · 2026-10-15T01:49:34Z · [source](https://github.com/pytorch/torchtitan/pull/5380#issuecomment-6182532603)

reply from claude:
Today rounds each product to bf16, then adds a token's routes in expert-id order, rounding after each add (I reproduced it bitwise that way). This PR sums in fp32 and rounds once. Error vs a float64 sum, random inputs at Qwen3.5-35B-A3B shapes, H100:
```
today (scatter-add)    rel L2 4.0e-3   43.5% of outputs correctly rounded
this PR (gather-sum)   rel L2 1.7e-3   >99.99%
```
- Match today's dtype: possible, but bitwise needs a per-token sort of the routes plus emulated bf16 casts, and keeps 2.4x the error.
- Trainer vs generator: this PR alone makes them differ in the combine; (7/7) moves compiled training to the same kernel, so they match bitwise again.
- fp32 cost: ~2%, the accumulator stays in registers. 4096 tokens: 77.0 us fp32 vs 75.5 us with bf16 accumulation (today's scatter-add: 717 us).
- Determinism: no atomics; each output is one fixed-order sum of K rows. 20 runs are bitwise equal, and 34 tokens alone give the same bits as inside a 4096-token batch.
- Why today casts before the scatter-add: it came with the bmm -> scatter-add switch (8bc267dea), for bmm's slow backward. bmm summed `rows.float()` and rounded once, like this PR; `scatter_add` needs `src` and `out` in one dtype, and `out` is bf16.
- Inference only: (7/7) adds training.
- EP>1: AllToAll gets its rows back in the same order as EP=1, so it could reuse this combine, but not in this stack:
  - generator: AllToAll reads its split sizes on the host, so EP>1 generators run without CUDA graphs and a decode step is host-bound (30-40 ms per 4-layer step vs 2-5 ms of kernels). A faster combine barely moves it.
  - trainer: this is where it would pay off, as (7/7) does at EP=1 (one MoE layer, fwd+bwd at 32k: 24.1 -> 10.8 ms). It needs (7/7)'s backward inside AllToAll's dispatch and combine, plus an EP=2 parity test. I left a TODO in `AllToAllTokenDispatcher._combine`.

The numerics are now in `_gather_weighted_sum`'s docstring.
