## Agent details

Written with Claude Code: the analysis, measurements and test plan below.

**TLDR:** In plain FULL CUDA-graph mode (TorchTitan's default), decode replays a graph captured for a mixed batch, which freezes `max_seqlen_q = num_tokens`, so FA4 launches tiles for query rows that don't exist. This PR gives every model's decode its own FULL graphs (GDN/KDA models, e.g. Qwen3.5, already had them) and keeps them safe at DP>1. Decode attention at batch 32-1024: -27% (head dim 128) to -43% (head dim 64). Real generator decode step: Qwen3-8B TP2 at 2k context -22% to -30% at batch 128-1024; Qwen3-30B-A3B at DP 2 x EP 2 -20% / -26% at batch 256 / 1024. Outputs are bitwise identical to main; Qwen3-8B's KV cache size is unchanged.

```text
main:     64 decodes -> graph "64 tokens", captured as a mixed batch (max_seqlen_q = 64) -> FA4 grid for 64 queries per sequence
this PR:  64 decodes -> graph "64 decodes" (max_seqlen_q = 1)                           -> FA4 grid for 1 query per sequence
          DP>1, a peer prefills 16k -> this rank is padded to 16k -> graph "16384 tokens" (mixed), as on main
```

**Problem**
1. **One graph for two batch kinds.** In plain FULL mode, vLLM drops the uniform-decode flag from the graph key (`v1/cudagraph_dispatcher.py:302`, vLLM 9f03b51), so 64 one-token decodes and one 64-token prefill replay the same graph.
2. **Captured as the mixed batch.** That graph freezes `max_query_len = num_tokens`, which TorchTitan's attention passes to FA4 as the host int `max_seqlen_q`.
3. **Cost.** FA4 sizes its grid from `max_seqlen_q`: decode attention takes 1.3-2.0x longer from 32 sequences at head dim 64 and from 64 at head dim 128 (GB300).
4. **Already solved for linear attention.** `TorchTitanCudagraphDispatcher` adds decode keys in FULL mode, but the runner installs it only for models with GDN/KDA layers.
5. **DP>1.** vLLM pads a decoding rank to the busiest rank's token count and then allows only FULL (`v1/worker/gpu_model_runner.py:4038-4048`, vLLM 9f03b51); a decode batch above every decode key then asserts (`v1/cudagraph_dispatcher.py:320`).

**Solution**
1. `TorchTitanGPUModelRunner.load_model` installs `TorchTitanCudagraphDispatcher` for every model; decode batches get FULL graphs captured with `max_seqlen_q = 1`.
2. `dispatch`, for a uniform-decode batch in FULL mode:
   ```text
   num_tokens <= max_decode_capture_size          -> decode graph
   larger (DP padding, or a capture-size gap)     -> mixed graph, as in stock FULL
   larger, batch-invariant, eager allowed         -> eager on the decode kernels (GDN/KDA's packed kernels
                                                     in the mixed graph don't match them bitwise)
   ```
3. KV cache: vLLM's graph-memory estimate, which comes out of the KV cache, charges every FULL graph like the second-largest one (`v1/worker/gpu_model_runner.py:6740-6771`, `v1/worker/gpu_worker.py:619-623`). The 11 decode graphs (0.03 GiB) would cost Qwen3-8B TP2 2.6% of its KV tokens, so `TorchTitanGPUModelRunner.initialize_kv_cache` drops the decode keys from the profiling pass. vLLM discards those profiling keys anyway, and the real pass rebuilds them, decode keys included.
4. Unchanged: prefill and mixed graphs, FULL_DECODE_ONLY and eager modes.

You may ask: why not switch TorchTitan to FULL_AND_PIECEWISE? TorchTitan captures with `CompilationMode.NONE` so vLLM's Inductor compile doesn't nest inside local compile, and without piecewise compilation vLLM turns FULL_AND_PIECEWISE into FULL_DECODE_ONLY, which runs prefill and mixed steps eager.
You may ask: why not fix vLLM? Plain FULL is one graph per size by design; decode specialization is what its split modes are for, and those need piecewise compilation. The dispatcher delegates to vLLM's own FULL_DECODE_ONLY dispatcher, so it can go once vLLM offers FULL decode next to FULL mixed graphs.

NOTE: Cost: one more graph per decode batch size up to `max_num_seqs` (11 at 1024), 0.03 GiB in total for Qwen3-8B TP2. Engine init: Qwen3-8B TP2 52-65 s -> 58-68 s; Qwen3-30B-A3B DP2 x EP2 104 -> 141 s (one run each).
NOTE: GDN/KDA models already captured decode graphs on main; the estimate now drops those too, so their KV cache grows a little (Qwen3.5-35B-A3B's 9 decode graphs take 0.12 GiB when captured alone). Qwen3-30B-A3B lost 1.0% of its KV tokens on the previous revision: one rank's weights + non-torch memory read 35.69 GiB vs 34.48 on main (the other rank 34.48 both), and its graph estimate grew only 0.08 GiB.

**What this PR does.** In plain FULL mode, vLLM keys CUDA graphs by token count alone. So N one-token decodes replay the graph captured for an N-token prefill, which has `max_seqlen_q = N` baked in, and FA4 launches tiles for query rows that don't exist. The GDN/KDA-only `TorchTitanCudagraphDispatcher` already captures separate decode keys; this PR installs it for every model. It also bounds decode dispatch by the largest decode graph, which fixes the assert at DP>1 when a decoding rank is padded to a peer's prefill. Finally, it drops the decode keys from vLLM's profiling-time memory estimate so the KV cache doesn't shrink.

**Example.**
```text

  decode dispatcher alone: no key above max_num_seqs -> assert
```

<details><summary>Details</summary>

- **GDN/KDA at DP>1.** I checked whether the new fall-through to the mixed graph lets batch-invariant GDN runs silently use packed kernels for decodes. It can't today: `TorchTitanLinearAttentionMetadataBuilder.get_cudagraph_support` returns `UNIFORM_BATCH` at DP>1 (`linear_attention.py:75-80`), so those models never reach FULL mode at DP>1. That path belongs to PR 2 of the stack.
- **Batch-invariant eager branch.** It applies to every model, not only GDN/KDA. For attention-only models the mixed graph matches decode bitwise (the new GPU test checks this at DP 2), so the branch only costs performance there, and only when there is a capture-size gap at DP=1. That case is rare, so it doesn't justify a per-backend gate.
- **Other modes.** FULL_DECODE_ONLY, NONE and PIECEWISE are unchanged: both `initialize_cudagraph_keys` and `dispatch` branch only on `CUDAGraphMode.FULL`.
- **Test value.** The CPU test covers the bound and the eager branch. The GPU test covers what the CPU test can't: that vLLM's real DP padding reaches `dispatch` with `uniform_decode=True, valid_modes={FULL}`, and that the decode and mixed graphs give bitwise-identical outputs. It earns its CI entry.

This changes vLLM's graph-memory estimate by editing the dispatcher's key set in the middle of `initialize_kv_cache`. It depends on two vLLM internals: (a) the estimate reads `cudagraph_keys` after this call returns, and (b) the real (non-profiling) call re-runs `initialize_cudagraph_keys`. If a vLLM bump breaks (b), decode graphs silently stop being captured and you lose the speedup without any error. If it breaks (a), the KV cache shrinks by about 2.6% and nothing reports it either.

Two cheap fixes:
- Mark this as a `TODO(<vLLM issue>)`: upstream should estimate each graph kind separately instead of charging every FULL graph like the second largest.
- Add an assert or test that the decode keys exist after the real `initialize_kv_cache`. The new GPU test's `any(mode == FULL and uniform ...)` check already covers (b) at DP 2, so a short comment pointing to that test is enough for (b).
