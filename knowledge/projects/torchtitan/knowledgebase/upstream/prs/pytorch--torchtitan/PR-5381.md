# [moe][perf] EP=1 inference: sort-region MoE dispatch (4/6)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5381) · state: open · merged: False

## Original PR description

**TLDR:** At inference, the EP=1 MoE dispatch sorts routes by expert in a compiled region and returns each route's row, so the combine doesn't invert the sort: Qwen3.5-35B-A3B routed experts 117.7 -> 96.6-99.9 us at 34 tokens (-15 to -18%). Reference path (Dist-MoE has its own dispatch), low priority.

**Stack** (6 PRs, merge bottom-up; this PR is in **bold**)

| # | PR | Independent? | Needs (stack positions) |
|---|---|---|---|
| 1 | AllToAll dispatcher: permute and unpermute with gathers | yes | — |
| 2 | Argsort expert ids on the narrowest integer type | yes | — |
| 3 | EP=1 inference: gather-sum MoE combine region | no | 2 |
| **4** | **EP=1 inference: sort-region MoE dispatch** | **no** | **2, 3** |
| 5 | Gather-sum dispatch and combine for training, at any EP | no | 4 |
| 6 | Turn on gather-sum dispatch and combine for DeepSeek-V3 and Kimi | no | 3, 4, 5 |

**Problem**
1. **Dispatch.** Before the grouped GEMM, `LocalTokenDispatcher.dispatch` sorts the `T x top_k` routes by expert id.
2. **Today.** Under `no_grad` it calls `_argsort_expert_ids` (a radix sort on uint8 keys), then gathers tokens and scores in separate kernels.
3. **Decode.** At 34 tokens x top-8 = 272 routes, the radix sort alone takes 13 us.
4. **Extra kernel.** The gather-sum combine then inverts the sort to find each route's row.

```text
today:    expert ids -> argsort -> order -> gather tokens, gather scores        combine: invert the order
this PR:  expert ids -> [pairwise rank + gathers] (moe_dispatch) -> tokens, scores, row of each route
```

**Solution**
1. **Pairwise rank.** A route's row in the stable sort is the count of routes with a smaller key `expert * N + route`: one `(N, N)` compare-and-count, fused with the scatter.
2. New `_sort_routes_and_gather`, in a `moe_dispatch` region, returns the sorted tokens, the sorted scores and each route's row; the combine reads the row.
3. **Size.** O(N^2), so only up to `_MAX_PAIRWISE_RANK_ROUTES = 2048` routes (256 tokens x top-8); above that the region falls back to `_argsort_expert_ids`.
4. Qwen3.5 (and 3.6/3.8, which reuse its list) turns the region on.
5. Unchanged: eager calls (argsort + scatter-add combine), training and the EP dispatchers.

**Results**
```text
Numerics: bitwise identical to stack position 3 (same stable order on the same keys); MoE layer outputs equal at 1-4096 tokens.

Qwen3.5-35B-A3B routed experts (dispatch + grouped GEMMs + combine; no router, norm or shared expert), EP=1, no_grad,
4 layers per CUDA graph, skewed routing, generator compile order (largest first), 1x GB300, us per layer.
before = stack position 3, min of 2 processes (they agree within 1.5 us).
tokens              1        34       64       256      1024     2048     4096
before              66.4     117.7    135.0    191.8    287.2    361.9    476.7
after (process 1)   49.7     96.6     111.9    169.8    274.2    351.1    473.7
after (process 2)   53.9     99.9     115.0    175.3    279.3    356.9    473.8
delta               -19/-25% -15/-18% -15/-17% -9/-11%  -3/-4.5% -1/-3%   -0.6%
```

You may ask:
- Why not a one-hot counting sort? 5 kernels at decode (9.1 vs 5.1 us at 34 tokens), and in the generator's compile order its cumsum is slow at 1024-2048 tokens (dispatch region + counts + offsets: 114 vs 50 us at 2048).
- Why stop at 2048 routes? O(N^2): at 16,384 routes the pairwise rank took 241 us, vs 50-53 us for the whole region with the narrow argsort.
- Why not a hand-written routing kernel? FlashInfer's sorts in one ~4 us launch; the pairwise rank gets to 3 kernels (5.1 us) with 4 lines of torch.

NOTE:
- EP=1 here (`LocalTokenDispatcher`), i.e. TP=1 generators: MoE requires EP >= TP (`decoder.py:184-189`).
- Not run: the vLLM generator end to end; recorded routing (the timing uses skewed synthetic routing).

**Test plan**
```bash
pytest tests/unit_tests/cpu/models/common/test_token_dispatcher.py tests/unit_tests/cpu/models/qwen3_5/test_offset_rmsnorm.py
```
- `test_pairwise_rank_matches_stable_argsort`: compiled, both branches (pairwise rank, and argsort with the threshold forced to -1) give eager's stable order, with duplicate experts within a token.
- 1x GB300, ad-hoc script (not in the PR): compiled dispatch + combine equal eager's stable argsort at T = 4096, 1024, 257, 256, 64, 34, 1 (257 and 256 straddle the 2048-route threshold).
