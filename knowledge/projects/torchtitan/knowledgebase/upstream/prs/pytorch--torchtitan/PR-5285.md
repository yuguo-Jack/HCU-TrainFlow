# [rl] Add an opt-in RDMA fast path for trainer microbatches

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5285) · state: closed · merged: True

## Original PR description

**TLDR:** Adds an opt-in RDMA fast path for trainer microbatches, `async_loop.batcher.rdma_min_tensor_bytes`: the batcher keeps tensors of at least that many bytes as Monarch RDMA buffers, and each trainer rank reads only its own column. A 5.2 GB step at dp 2 x tp 2 goes from 9.1-11.1 s to 3.3-5.1 s (CPU Monarch, one host, TCP), mostly from that column. `None` (the default) keeps main's by-value RPC.

**Problem**
1. **One message per step.** The controller calls `trainer.forward_backward` with the step's whole `[num_microbatches][dp_degree]` grid of `TrainingMicrobatch`, by value.
2. **Every rank gets every column.** Each rank keeps only `row[dp_rank]`, so it unpickles dp_degree times the data it trains on.
3. **Extra per-token fields make it big.** Main's fields are 38 B/token (~1.1 GB per rank for a 29M-token step); router replay plus top-32 logprobs make it 614 B/token.
4. **The run dies.** In a router-replay run (replay is still a draft PR), main's step-3 call took 93-100 s to reach the last of 4 trainer ranks (17.8-19.9 GB each; at most 20.7 s at steps 1-2), and the job died on Monarch's 60 s proc-state timeout.

**Solution**
1. **`MonarchRDMAMicrobatch`** (new `torchtitan/rl/trainer/rdma_microbatch.py`): `register(microbatch, min_bytes=...)` swaps each tensor of at least `min_bytes`, `model_kwargs` included, for an `RDMABuffer` handle; `read()` copies them into fresh tensors with one RDMA action; `drop()` releases them.
2. **Batcher:** registers each batch right after packing (already in `asyncio.to_thread`) and keeps it until `maybe_release_oldest_batch()`. Each handle carries the batch, DP rank and position it was registered for.
3. **Training loop:** no RDMA branch. It passes `packed.microbatches` either way and calls `batcher.maybe_release_oldest_batch()` in a `finally`.
4. **Trainer:** checks each handle's batch, DP rank and position (`ValueError` on a mismatch), reads its column one microbatch at a time, and reports `timing/trainer/read_microbatches/max`.
5. **Unchanged:** with `None` (the default) the grid goes by value, as on main, and the release is a no-op. Packing, the token counts, the loss, the engine, `optim_step` and weight sync are unchanged either way.

```text
default:  controller --forward_backward.call(grid of TrainingMicrobatch)--> every trainer rank
opt-in:   batcher: register each batch after packing
          controller --forward_backward.call(grid of MonarchRDMAMicrobatch, ~0.8 MB)--> every trainer rank
          trainer rank: read its column out of band | train 0 | train 1 | ...
          batcher: drop the oldest batch's buffers after the call returns (or fails)
```

**Results** (all for the opt-in path)

Data path per step: packed batch -> every rank holds its column -> drop.
- CPU Monarch, one host, TCP, 4 rank processes, 131,072-token microbatches; medians of steps 2-5, ranges are separate runs.
- 614 B/token adds routed expert ids and top-32 logprobs in `model_kwargs`.
- From an earlier benchmark copy that buffered every non-empty tensor; at 1 KiB only the 8 B token counts move into the message.
```text
                                     by value      fast path      peak memory per rank
dp 2 x tp 2, 0.64 GB, 38 B/token     1.3 s         1.0 s          2.5 -> 0.2 GB
dp 2 x tp 2, 2.6 GB, 614 B/token     7.5 s         2.5 s          7.5 -> 1.3 GB
dp 2 x tp 2, 5.2 GB, 614 B/token     9.1-11.1 s    3.3-5.1 s      15-18 -> 2.6-3.1 GB
dp 4 x tp 1, 2.6 GB, 614 B/token     4.9 s         1.0 s          7.5 -> 0.7 GB
dp 1 x tp 4, 2.6 GB, 614 B/token     5.0 s         3.8 s          7.5 -> 2.4 GB
```
Most of the gain is the column (each rank reads 1/dp of the step), which the scatter PR later in this stack gets by value too:
```text
2.6 GB step       by value, whole grid    by value, own column    fast path
dp 2 x tp 2       7.5 s                   3.0 s                   2.5 s
dp 4 x tp 1       4.9 s                   2.05 s                  1.0 s
```
- At dp 1 x tp 4 there is no column to save; the fast path still wins (5.0 -> 3.8 s) by skipping the grid's pickle, copy and unpickle.
- The real transport saving needs ibverbs: 25 vs 1.3 GB/s over TCP, reading 256 MiB on one host (CPU probe).
- Router-replay GPU run from Problem 4 (multiple hosts), not a controlled A/B: a later job of the same recipe with an earlier version of this PR (resumed at step 10) trained steps 11-16, but with the proc-state timeout raised to 300 s. So it shows the handles work at this size, not that they alone avoid the timeout.

GPU, Qwen3-0.6B, H100, batch invariant, lockstep, trainer DP 1 + one TP 1 generator (2 GPUs), 4,096-token microbatches, 5 steps, ibverbs:
```text

loss/mean            bitwise equal at all 5 steps
read_microbatches    -                    126, 16, 5, 6, 7 ms at steps 1-5 (step 1 includes RDMA setup)
[RdmaXcel] lines     0                    0
```
The by-value run is from an earlier push (same config and seed). One earlier push read 203 and 102 ms at steps 2 and 4; its rerun and the previous head did not.

You may ask:
- **Why opt-in?** RPC stays the one way to orchestrate. Over TCP most of the saving is the column, which the scatter PR gets by value; the transport saving needs ibverbs, which not every host has.
- **Why no transport switch?** Monarch uses ibverbs where the host has it, else TCP. A host whose ibverbs devices fail doesn't fall back: `MONARCH_RDMA_DISABLE_IBVERBS=1` forces TCP in every process, weight sync included.
- **Why a byte threshold?** An 8 B token count costs more to register (~0.15 ms per buffer) than to send, and `RDMABuffer` rejects empty tensors. At 1 KiB, per-token tensors go out of band from 1,024 tokens up.
- **Why not overlap the reads?** The prefetch PR in this stack does; it needs an opt-in `TrainingEngine` mode.
- **Why not gather the reads?** Microbatch 0 would arrive no sooner than the whole column, and each RDMA action would last as long as the column (3.2 vs 0.17 s at 5.2 GB, dp 2 x tp 2), against its 60 s deadline. Only 0-19% faster (one host, TCP).
- **Why does the batcher own the threshold?** It makes the microbatches and registers right after packing, off the training loop; the batcher-process PR moves this code into its own process unchanged.
- **Why one buffer per tensor, not one per microbatch or column?** Packing costs a controller copy (0.3-0.8 s at 5.2 GB) and twice the step's memory, without cheaper registration; packed reads only tie at ≤16 MiB TCP chunks and are 1.3x slower at Monarch's default 64 MiB.
- **Why not TorchStore?** TitanRL's store only accepts the weight sync's planned keys; a second store needs the deprecated `ControllerStorageVolumes` and cleanup on both sides.
- **Why no checksum of the bytes?** Each batch gets fresh tensors that are never refilled, and is released only after every rank read it (or the step failed, which stops the run), so a read never sees another batch's bytes. The identity check covers a handle read twice or by the wrong rank.

NOTE:
- **CI** integration runs go by value (the default). The fast path is covered by CPU unit tests (faked RDMA, plus 4 ranks over real Monarch TCP), a CPU probe (TCP and ibverbs) and the GPU run above.
- **CUDA context:** without one, Monarch prints `[RdmaXcel] No CUDA context` once per registered buffer. So with the threshold set, the controller makes one current on GPU 0 with the stack limit at 0: ~256 MiB on H100 plus ~100 MiB of host memory, until Monarch logs it once (TODO). On exclusive-process GPUs, the controller and trainer rank 0 race for GPU 0.
- **Contention:** one controller actor serves the TCP reads, so per-rank read speed falls as readers grow. Registering in a thread slows down while the event loop is busy (320 buffers: 19 s vs 0.06 s with the loop held 100%, CPU).
- **Metrics:** with the fast path, `timing/step/forward_backward` includes reading and dropping; registering shows in the `batcher_pack` span; tokens/s and MFU exclude the reads.
- **Memory:** up to 3 registered batches (training, queued, waiting to be queued); by value the same batches are held as tensors.
- **Multiple hosts:** an earlier always-on version ran in all our multi-host runs, but correctness is verified on one host only and multi-host step time is not measured.

Follow up:

- [ ] Read once per DP replica and broadcast (TODO in `Trainer.forward_backward`).
- [ ] Send each DP replica only its column (last PR in this stack).

**Test plan**

- `test_rdma_microbatch.py`: with fake RDMA at `min_bytes=1024`, a `TrainingMicrobatch` round-trips (tensors ≥ 1 KiB become refs, one in `model_kwargs`; smaller and empty ones stay) and `drop` releases every buffer. Unset, the batcher never registers; set, `maybe_release_oldest_batch` frees only the oldest batch.

Overall the design is sound. The call now carries refs, each rank reads only `row[dp_rank]`, the engine call doesn't change, and the drop-ordering trick for the Monarch 0.6 deadlock has a comment explaining it. The PR description is very thorough. Below are the issues I found, most important first. I didn't run the tests here: running Python needed approval in this environment.

---

### 1. Drop is skipped when the call raises (agree with @pzhan9)
`torchtitan/rl/controller.py:1126-1144`: when `forward_backward.call` raises, `ref.drop()` never runs, so the step's buffers leak. In practice the job is probably going down at that point, so the cost is small. Still, `try/finally` is the right shape:
```python
microbatch_refs = await asyncio.to_thread(...)
try:
    fwd_bwd_metrics = self._get_rank_0_value(await self.trainer.forward_backward.call(...))
finally:
    # Drop while `packed` still holds the tensors (Monarch 0.6 deadlock).
    await asyncio.gather(*(ref.drop() for row in microbatch_refs for ref in row))
```
`packed` stays alive through the `finally`, so the deadlock invariant still holds. On the success path, the NaN `break` already runs after the drop, so that path is fine.

### 2. Reads run one microbatch at a time, each with its own thread hop and RDMA action
`torchtitan/rl/trainer.py:273`: `[await asyncio.to_thread(ref.read) for ref in refs]` waits for each microbatch to finish before starting the next. That's one thread handoff and one `submit().get()` round trip per microbatch. Two ways to fix it:
- (a) Take @pzhan9's suggestion: make `read` async with `await action.submit()`, then `asyncio.gather(*(ref.read() for ref in refs))`. This also avoids blocking a worker thread on `.get()`.
- (b) Queue every read for the column into **one** `RDMAAction` and submit once.

(a) is the smaller change, and the next PR (prefetch) needs per-microbatch async reads anyway. One caveat from your own measurements: with the TCP fallback served by one controller actor, many concurrent reads per rank may not be faster than serial ones. Please check the `read_microbatches` span after the change.

### 3. Tiny tensors each get their own RDMA buffer
The batcher (`torchtitan/rl/components/batcher.py:718-733`) gives every microbatch 10 top-level tensors, and all of them get a buffer. Some are very small:
- `loss_token_counts` and `routing_token_counts` have `1 + num_mtp_layers` elements (from `torch.stack` in `get_mtp_token_counts`).
- `temperature` is a `full_like` of a constant.

Each costs ~0.15 ms to register, one GIL handoff, and one `[RdmaXcel] No CUDA context` log line, while carrying only a few bytes. A byte-size threshold in `register` (small tensors go by value, like empty tensors already do) is a cheap win. It also reduces the ~1.6K log lines per step.

On @pzhan9's `_runtime.py` comment: I see the threshold and `MONARCH_RDMA_DISABLE_IBVERBS` as **separate** concerns. The threshold is about per-buffer overhead. The env var is about the ibverbs transport failing on some fabrics, and a threshold can't replace it. Both could exist. If you add the threshold, `MicrobatchRef` is still an accurate name: it is still a ref to a microbatch, with some fields inlined.

### 4. The env default may not reach trainer procs on other hosts
`torchtitan/rl/_runtime.py:40-48`: `apply_env_defaults()` runs when `torchtitan.rl` is imported.
- **Single host:** spawned trainer procs inherit the controller's environment after `setdefault`, so this works.
- **Remote host meshes:** the actor proc has already imported `monarch` before it unpickles anything that imports `torchtitan.rl`, and it doesn't inherit the controller's environment. On those procs the new warning fires and the default may not apply.

The PR already lists multiple hosts as untested. I'd add a sentence to the `RL_ENV_DEFAULTS` comment saying multi-host launchers must export the variable themselves.

### 5. `read()` assumes CPU, and `register()` assumes contiguous tensors
- `queue_read` allocates with `torch.empty(shape, dtype=dtype)`, which is always CPU. That matches what the old unpickled path produced, so it's fine today. A short comment would help, since `_TensorRef` doesn't record the device.
- `tensor.view(-1)` in `_TensorRef.register` raises on non-contiguous tensors. That fails loudly rather than silently, which is good. As @pzhan9 asked, say in the comment that the batcher guarantees contiguity. On main every tensor comes from `torch.tensor(...)`, `full_like`, or `torch.stack`, so this holds.

### 6. Silent fallback for unknown containers in `model_kwargs`
`pytree.tree_map_only` only walks containers pytree knows (dict, list, tuple, namedtuple, registered dataclasses). Suppose a future `model_kwargs` value is a custom object holding tensors. Its tensors are treated as one opaque leaf and pickled by value, with no error and no warning, and the message grows back silently. Today `model_kwargs` is empty on main (nothing in `torchtitan/rl` fills it), so this isn't urgent. A docstring note on `MicrobatchRef.fields` would be enough for now.

### 7. Minor / nits
- `trainer.py:266-270`: I agree with @pzhan9 that the two TODOs could be shorter. The numbers (230 MB/s vs 1 GB/s, 0.15% / 2%) belong in the PR description. In code they will go stale.
- `test_microbatch_ref.py`: `assert len(tensor_refs) == 11` depends on the field count of `TrainingMicrobatch`. Counting `tree_leaves(ref.fields)` that are `_TensorRef` and comparing to the number of non-empty tensors in the input would survive adding a field.
- `test_microbatch_ref.py`: the fake `submit()` returns `SimpleNamespace(get=...)`. If you switch to `await action.submit()` (point 2), make the fake return an awaitable, or the test will stop exercising the real call shape.
- `test_trainer.py`: switching to `dp_rank = 1` plus `other_rank_ref.read.assert_not_called()` is a nice way to prove each rank reads only its own column. 👍

### Things that look correct
- Message shape: the controller still owns `packed` for the whole step, and the tensors outlive the buffers, so the deadlock comment is accurate.
- `_step_compute_start` is now set after the reads, so tokens/s and MFU exclude read time. That matches the description.
- 0-dim tensors: `view(-1)` gives shape `[1]` and `torch.empty(())` restores the 0-dim shape. Bool tensors: `view(torch.uint8)` works because the element sizes match.
- Every caller of `Trainer.forward_backward` has been updated: the controller is the only production caller, and the actor endpoint's type hint changed with it.

**Summary:** one real fix (`try/finally` around drop), one likely performance improvement (no serial thread hop per microbatch), and one small-tensor threshold that would cut both overhead and log spam. The rest are documentation and tests.

**Updated:** this replaces my earlier text here; my other replies on this PR describe earlier versions. Current design, as you proposed:

- `async_loop.rdma_fast_path_threshold: int | None = None`.
