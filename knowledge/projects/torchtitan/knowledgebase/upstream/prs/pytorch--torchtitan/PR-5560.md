# [CI Fix][GraphTrainer] Avoid materializing parameters during FSDP inspection

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5560) · state: closed · merged: True

## Original PR description

## Summary

- Inspect parameter shard placements with SimpleFSDP parametrizations disabled.
- Add a regression test for reapplying data parallel to an already parametrized quantized weight.

## Root cause

The GraphTrainer B200 job fails in `graph_trainer_dist_moe_mxfp8_fsdp_ep_pp` while applying pipeline-stage parallelism: https://github.com/pytorch/torchtitan/actions/runs/39351458272/job/118396337526

`data_parallel()` computes `linear_param_shard_placements(model)` before its module loop skips modules that already have SimpleFSDP. On a reused/shared module that GraphPP has already parametrized, reading `child.weight` during that inspection invokes `ReplicateComputation` and tries to build the MXFP8 compute operands.

This happens during model construction, while the model is still on the `meta` device and before `to_empty(device=...)`. Dist-MoE checks both `weight.is_cuda` and `weight.is_contiguous()` but reports either failure as `ValueError: weight must be contiguous CUDA storage`. Here the failed condition is `weight.is_cuda == False`, not contiguity.

### Regression provenance

pytorch/torchtitan#4867 introduced the unconditional `linear_param_shard_placements(model)` scan that reads parametrized `child.weight`. pytorch/torchtitan#4949 later allowed callers to supply placements explicitly, but retained that scan on the default path.

The workflow installs `dist_moe@main` rather than a pinned revision. The last passing run on October 15 installed `dist_moe@6f0c3d4216`:

https://github.com/pytorch/torchtitan/actions/runs/38663506034

The first failing run on October 16 installed `dist_moe@e3d21b8d2a`:

https://github.com/pytorch/torchtitan/actions/runs/38832949153

Between those revisions, meta-pytorch/dist_moe@fa32967a85 added the valid CUDA/contiguous input contract and exposed the latent GraphTrainer bug. That commit has no associated public GitHub PR.

The Dist-MoE check should not be weakened and the dependency should not be pinned back: parameter-layout inspection should never execute the parameter's compute representation in the first place.

### Fix

Use GraphTrainer's existing `disable_active_parametrization()` context while inspecting shard placements. Inspection now sees the raw sharded parameter instead of materializing its compute representation; actual forward parametrization is unchanged.

An initial attempt to call `.contiguous()` at the Dist-MoE boundary failed with the same error, confirming that the meta device, not storage stride, was the violated contract:

https://github.com/pytorch/torchtitan/actions/runs/39374680382/job/118470042165

### Why `disable_active_parametrization` is needed here

- [x] Read the PR diff and `data_parallel()` call flow
- [x] Find out when parametrization is applied versus when the inspection runs
- [x] Answer the question

**Short answer:** You're right about the modules the current `data_parallel()` call is about to wrap. But `model` can already contain submodules that an **earlier** `data_parallel()` call parametrized. `linear_param_shard_placements(model)` walks `model.modules()`, so it reaches those submodules too. It does this before the `"SimpleFSDP" in mod.__class__.__name__` skip in the loop at `simple_fsdp.py:551`.

**Where an earlier call wraps a submodule first**

`apply_simple_fsdp` in `common_utils.py:609-659` calls `data_parallel()` more than once on the same tree when EP is on:

1. If `experts_shard_dim == 1`, it calls `data_parallel(routed_experts.w13, ...)` and `data_parallel(routed_experts.w2, ...)` (L636-651). Neither call passes `param_shard_placements`. Each call:
   - swaps the module's class for `SimpleFSDPGroupedLinear_N`;
   - turns `weight` into a property that returns `ReplicateComputation(self._parameters["weight"])` (`_register_parametrization`, L211-236).
2. Then it calls `data_parallel(model, ...)` (L653), again with no `param_shard_placements`. This runs `linear_param_shard_placements(model)` (`torchtitan/distributed/fsdp.py:71-100`), which visits every `GroupedLinear`, including the `w13` that was just wrapped. `w13` is stacked (`num_linears == 2`), so the scan reaches `weight = child.weight` at L96.

On a wrapped module, reading `child.weight` doesn't return the stored parameter. It runs `ReplicateComputation._forward`, which does `replicate_compute` (the all-gather) and then `_BuildUnshardedTensorFunction` (L482-506). For an MXFP8 `_ShardedFSDPTensor`, that builds the quantized compute operands. All of this happens during model construction, while the weights are still on `meta`. That's where Dist-MoE's `weight is not CUDA` check fires.

The GraphPP case in the PR description has the same shape: a module that already went through `data_parallel` gets visited again by a later call over an enclosing tree. The unit test you added triggers it the simplest way, by calling `data_parallel(linear, ...)` twice on one module.

**What the context manager changes**

With `_active_parametrization = False`, `ReplicateComputation._forward` returns `x` as is (L479-480). So `child.weight` gives back the stored sharded parameter, and no collective or quantization runs. The placements recorded for those already-wrapped modules are never used, because the loop skips them anyway. Modules that aren't wrapped yet have no parametrization, so the context changes nothing for them.

**A possible cleanup (not a correctness issue)**

The fix would read more directly if the scan just left out already-wrapped modules, for example by filtering `"SimpleFSDP" in type(child).__name__`. However, `linear_param_shard_placements` lives in core `torchtitan/distributed/fsdp.py`, and the root CLAUDE.md says not to add experiment-specific logic to core. Reusing GraphTrainer's existing `disable_active_parametrization()` keeps the fix inside the experiment, so I think the current approach is reasonable. It would help to add a one-line comment above L536, along the lines of "`model` may contain submodules parametrized by an earlier `data_parallel` call (e.g. EP experts); read raw params instead of running `ReplicateComputation`". Without it, the next reader will likely ask the same question.
