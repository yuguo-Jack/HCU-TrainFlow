# Build sharded model configs; separate RL trainer and generator models

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5280) · state: closed · merged: True

## Original PR description

## Why

The RL trainer and generator shared one model config, and each actor re-derived sharding from its own parallelism with a public `set_sharding_()` before building. That forced three workarounds:

- Model configs were built without a parallelism, so sharding was attached afterwards by per-model walkers that mutate a finished tree, and transforms ran before sharding existed.
- `SharedExpertRowParallelLinear` existed only because the shared-expert output layout (TP-Partial vs. reduced) could not be fixed at build time.
- Role-specific settings (e.g. a CUDA-graph-compatible MoE dispatcher for the generator) needed per-actor overrides (`torchtitan_recipes/overrides/moe_token_dispatcher.py`).

This PR builds each model config for a known parallelism, bottom-up, and gives the RL trainer and generator their own model configs.

## What changed

**Sharding is part of model config construction**
- `build_model_config(flavor, *, parallelism)` builds a sharded config; `parallelism` is required so a model config cannot be built without choosing its layout. Each component gets its `sharding_config` where it is constructed; the shared `make_*` factories take `enable_sp`/`enable_ep`. Sequence and expert parallelism are the only settings that change declared layouts; mesh degrees are still resolved at runtime.
- Removed: `BaseModel.Config.set_sharding_()`, the per-model `set_*_sharding_config` walkers, `decoder_sharding.set_*`/`moe_sharding.set_*`/`set_vision_transformer_block_sharding_config`, and the runtime re-shard in the trainers and the vLLM wrapper. Model `sharding.py` files now hold pure constructors returning `ShardingConfig`/`SpmdType` (deleted for llama3 and qwen3, which need none beyond `common/`).
- `SharedExpertRowParallelLinear` is removed: the shared-expert `w2` is chosen at construction -- a `RowParallelLinear` (reduce-scatter) with SP, and a plain `Linear` that keeps its TP-Partial output without SP, so the MoE reduces routed + shared once. `RowParallelLinear` is unchanged and transforms such as async TP apply as-is.
- Transforms and overrides assume the config is already sharded and keep (or explicitly set) the sharding of configs they replace; `apply_transforms` never re-derives sharding.

**RL: one model config per role**
- `Controller.Config.model` is removed; `Trainer.Config.model` and `VLLMGenerator.Config.model` replace it, each built for that role's parallelism (`build_rl_model_configs` builds both from one call). The controller requires the same model class; keeping them otherwise aligned is the recipe's job.
- Per-role differences are model config transforms on one role, e.g. `apply_transforms(config.generator, [TokenDispatcherTransform(DeepEPTokenDispatcher, num_max_tokens_per_rank=..., kwargs={"cuda_graph_compatible": True})])`.
- Transforms take only the model config (`ModelConfigTransformContext` is removed) and `apply_transforms` works on any config that owns a `model`. `TokenDispatcherTransform` takes the EP buffer capacity explicitly: a trainer passes its microbatch / (CP x TP), the generator its per-step token budget / TP.
- `override` moves from `TrainingEngine.Config` to the top-level configs: core `Trainer.Config.override` and a new `Controller.Config.override`, applied to the whole RL tree (both models) before actors spawn. `VLLMGenerator.Config.override` and `moe_token_dispatcher.py` are removed. The CLI `--override` extends the top-level config's `override`.

**Recipes**
- Recipes declare their parallelism before building the model. Base recipes that derived recipes reshape (EP 1 vs. >1, SP on/off) take a `parallelism=` keyword; derived recipes that only change degrees are unchanged.
- Base MoE test recipes that accept an EP parallelism disable CUDA graphs for the stock all-to-all dispatcher (it syncs with the CPU); derived recipes that install a capturable dispatcher (HybridEP non-blocking, Dist-MoE) re-enable them. Every non-RL recipe's final config and runtime model config is unchanged vs. #5277 (checked for all recipes, with the shared-expert class rename normalized).

**Cleanups**
- Sharding constructors are named `*_sharding_config` (e.g. `sharding_config=router_gate_sharding_config()`), so call sites do not read like module configs.
- The vLLM wrapper's FSDP storage transitions are private module functions named for what they do: `_restore_sharded_params` / `_unshard_and_free_sharded_params` (matching the upstream APIs they stand in for).
- `scripts/install_rl_env.sh` installs FA3 from the same `nightly/${cuda}` index as torch (FA3 ships one CUDA 13.0 stable-ABI wheel that every CUDA 13 index serves).

**Fixes found along the way**
- `kimi_k2_7` and `muse_glimmer` `build_model_config` dropped a converter's returned root config (now covered for every model by `test_build_model_config.py`).
- graph_trainer's SDPA test backend swap kept the inner attention's sharding.

## Behavior changes

- Recipes that set the `fused_swiglu` perf override now set it on `Controller.Config.override`, so it applies to both RL models (previously the DeepEP perf recipes applied it to the generator only).
- The RL generator's DeepEP dispatch buffers are sized from its own per-step token budget instead of the trainer's microbatch.
- The routed-expert "sharding does not match expert_parallel_degree" validation is removed along with the runtime re-shard; a mismatched build is caught by SPMD typechecking (`debug.spmd_typechecking`).

## Numerics

Every model flavor's config tree (llama3, qwen3, qwen3_5/6/8, deepseek_v3/v4, gpt_oss, kimi_k2_7, kimi_k3, muse_glimmer, flux) x {SP on, off} x {EP 1, 2} is byte-identical to the tree the previous walkers produced, including every `sharding_config` and parameter initializer.

Bitwise comparison against #5277 with `scripts/loss_compare.py` (seed 42, deterministic, `--metrics loss,grad_norm --assert-equal`, 20 steps, 4x GB300):

| Config | Layout | Result |
| --- | --- | --- |
| Llama 3 debugmodel | FSDP2 TP2, no SP | loss and grad_norm identical |
| DeepSeek V3 debugmodel (MLA, MoE with shared experts) | FSDP2 TP2 EP2, SP | loss and grad_norm identical |
| DeepSeek V3 debugmodel | FSDP2 TP2 EP2, no SP (plain `Linear` shared-expert `w2`) | loss and grad_norm identical |
| Qwen3.5 debugmodel_moe (GDN, sigmoid-gated shared experts) | FSDP2 TP2 EP2, SP | loss and grad_norm identical |
| Qwen3.5 debugmodel_moe | FSDP2 TP2 EP2, no SP | loss and grad_norm identical |
| Kimi K3 multimodal DistMuon (`kimi_k3_mm_muon`) | FSDP2 EP2, seeded from `kimi_k3_debugmodel_mm` | loss identical, both with a shared seed checkpoint and with each commit creating its own |

Beyond loss runs, every recipe in `torchtitan_recipes` and the integration suites was built on both commits: the final configs (models excluded) are identical for every non-RL recipe, and every runtime model config (this PR's built config vs. #5277's config after `set_sharding_(parallelism)`) is identical once the shared-expert class rename is normalized. The only intended differences are the RL changes listed above.

## Testing

- `pre-commit run --all-files` clean (pyrefly 0 errors).
- CPU unit tests (core, RL, graph_trainer passes): all pass except failures that reproduce on #5277: 4 aarch64-only Inductor CPU flex-attention failures, and 2 Dist-MoE tests that need a visible GPU (they pass with one).
- GPU unit tests touched by this change pass on 4x GB300: `test_tensor_parallel_feed_forward`, `test_async_linear`, `test_fsdp_cpu_offload`, `test_fused_swiglu`, `test_fsdp_moe_sharding` (one failure also fails on #5277).
- Every recipe in `torchtitan_recipes` and the integration suites builds, and its model's SP/EP layout matches its parallelism (both RL roles included), except hardware-gated MXFP8/NVFP4/flash recipes on this machine.
