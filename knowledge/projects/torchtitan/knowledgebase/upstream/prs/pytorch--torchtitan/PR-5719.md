# [MoE] Make the token combine one op that backends can override

The MoE token combine multiplies each routed row by its router score in float32, casts it back to the routed dtype, and adds it into the output with `deterministic_scatter_add`. Only the scatter is an op, so a backend with a fused combine kernel cannot replace the whole combine without patching `token_dispatcher.py`. This PR adds a `torchtitan::score_and_scatter_add` op whose only kernel is CompositeImplicitAutograd, with the existing code as its body: every current backend runs the same ATen ops in the same order, and an out of tree backend can register its own fused kernel for the op on its device. The combine, a full MoE layer and the AOT graphs match main bitwise on CPU, and loss and grad norm match main bitwise on GPU with `loss_compare.py --assert-equal`. The sections below are AI-assisted.

## Why

On main, the MoE token combine in `token_dispatcher.py` is three steps: a float32 multiply by the router score, a
cast back to the routed dtype, and `torchtitan::deterministic_scatter_add`. Only the last step is an op. A backend
with a fused combine kernel can register for `deterministic_scatter_add`, but by then the multiply and the cast have
already run, each as a separate pass over the `(N, D)` routed tensor. Out-of-tree backends that have such a kernel,
such as torch-neuronx, can reach it today only by patching `token_dispatcher.py`.

**Example.**

```python
# main: only the scatter is an op
routed_ND = (routed_ND * scores_N.reshape(-1, 1).to(torch.float32)).to(routed_ND.dtype)
out_TD = deterministic_scatter_add(torch.zeros_like(x_TD), idx_N.reshape(-1, 1).expand(-1, D), routed_ND)

# this PR: the whole combine is one op, and its CompositeImplicitAutograd body is the code above
out_TD = score_and_scatter_add(torch.zeros_like(x_TD), routed_ND, scores_N, idx_N)

# an out-of-tree backend replaces it on its own device, with no torchtitan change
lib = torch.library.Library("torchtitan", "IMPL")
lib.impl("score_and_scatter_add", fused_combine, "AutogradPrivateUse1")
```

## What changed

- `torchtitan/ops/scatter_add.py`: new op `torchtitan::score_and_scatter_add(out, routed, scores, token_indices)`.
  Its only kernel is CompositeImplicitAutograd, and its body is the current combine. `out` is the zeros buffer that
  receives the sums. `score_and_scatter_add` is the op itself, so eager and compiled runs both go through it, and a
  backend kernel is reached in both.
- `torchtitan/models/common/moe/token_dispatcher.py` (mechanical): the local, all-to-all and TorchAO dispatchers call
  the op with `torch.zeros_like(x_TD)` as `out`, as they pass it to `deterministic_scatter_add` on main. The
  `_score_and_scatter_add` helper only forwarded to it, so it is removed.
- Not changed: the DeepEP, HybridEP and Dist-MoE combines, which have their own kernels.
- No new config, flag or dependency.

## Alternatives considered

- A Configurable override of the token dispatchers (`torchtitan/config/OVERRIDE.md`): needs no torchtitan change.
  But each backend has to subclass the local, all-to-all and TorchAO dispatchers and copy their combine, every recipe
  has to opt in, and the backend package has to import torchtitan.
- A kernel for `deterministic_scatter_add`: the multiply and the cast run before that op boundary.
- `torch.library.custom_op` with its own autograd: Inductor can no longer fuse the scale and the casts, and DTensor
  needs a sharding rule.

## Performance

- No backend kernel: the op runs the same kernels as main, plus one dispatcher call per MoE layer in eager mode. Peak
  memory was the same in all 6 GPU configs (within 0.02 GiB, previous revision).

  equals main in 256 of 256.
- `pre-commit run --all-files`: all hooks pass.

## Known issues / follow-ups

- The Python dispatcher caches its kernel choice per op and dispatch key. A backend kernel registered after the op
  was already traced under that key in the same process is not used by AOT tracing. Backends should register at
  import, before the first compile.

**What this PR does.** It turns the MoE combine (multiply by the router score in fp32, cast back, deterministic scatter-add) into one `torchtitan::score_and_scatter_add` op. The op's only kernel is CompositeImplicitAutograd, and its body is the current combine code. An out-of-tree backend (torch-neuronx) can then register a fused kernel under its own autograd key. The local, all-to-all and TorchAO dispatchers call the op through a Python wrapper. The wrapper skips the op while compiling.

**Example.**
```python
# Neuron backend registers its fused kernel
lib.impl("score_and_scatter_add", fused_combine, "AutogradPrivateUse1")

model(x)                    # eager: dispatcher -> op -> fused_combine
torch.compile(model)(x)     # compiled: is_compiling() -> reference body; fused_combine never runs
```

<details><summary>Details</summary>

- **Gate.** There is a real problem: on main a backend can only hook `deterministic_scatter_add`, after the fp32 multiply and the cast have already made separate passes over `(N, D)`. Registering a kernel through `torch.library` under the backend's own dispatch key is PyTorch-native, adds no config, flag or dependency, and leaves core unaware of Neuron. So the approach fits torchtitan's rules. The open points are value evidence (above) and making the hook behave the same in eager and compiled runs.
- **Scope.** The DeepEP, HybridEP and Dist-MoE combines are left alone, which is right because they have their own kernels. A backend override therefore covers only the local, all-to-all and TorchAO paths, and the description says so.
- **Remat.** `remat.recompute_needs_tensor(routed_output_RD)` still applies. With a backend kernel, that kernel owns what it saves for backward.
- **Size after the fixes.** About 30 lines in `scatter_add.py` (the schema, the reference body, the `_lib.impl` call), three call-site edits, and one test of about 30 lines. Net LoC goes from +148 to about +40.
</details>
