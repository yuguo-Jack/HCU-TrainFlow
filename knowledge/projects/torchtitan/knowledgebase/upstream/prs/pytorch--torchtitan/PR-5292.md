# [rl] Drain in-flight rollouts during shutdown

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5292) · state: open · merged: False

## Original PR description

**TLDR:** A run that finishes every step, its final validation and its last checkpoint can still exit with code 130 during shutdown, so the job shows as failed. This PR closes the generators before the rollout workers, and waits for in-flight rollouts before stopping the workers. On one 8x H100 node with Monarch 0.7: exit 130 in 2/3 runs before, exit 0 in 3/3 after.

**Problem**
1. Training ends with rollout groups still generating: 6-9 in the runs below.
2. `Controller.run` cancels its rollout loops, but each `run_group` call keeps running on its rollout worker.
3. `Controller.close` stops the rollout workers first (`Rollouter.close`) and closes the generators after.
4. The generator router then replies to a worker that has stopped.
5. Monarch 0.7 treats that undeliverable reply as an unhandled error: it cancels `Controller.close` midway and sends SIGINT. Monarch 0.6.0 drops the reply.
6. The generators, proc meshes and metric backends are never closed, and the job exits 130 after all its work is done.

We also hit it at the end of a 150-step run on 3 GB300 nodes: the step-150 checkpoint and the final validation finished, then the job exited 130.

**Solution**
1. Close the generators first. A closing generator fails its outstanding requests, so each group finishes while its worker is alive.
2. `Rollouter.run_group_rollouts` keeps each `run_group` call in `_inflight_run_group_calls`, shielded from the controller's cancel.
3. `Rollouter.close` waits for them, then stops the worker mesh. It stops waiting after 30 s.
4. `VerifiersRollouter` is unchanged: its rollouts run in the controller process, so it has no workers to drain.

**Results**
```
One 8x H100 node. Qwen3-4B-Base DAPO-Math, TP=2 trainer + six TP=1 generators, target_offpolicy_steps=4,
4K responses, 3 steps, validation off. 3 runs per arm. "in flight" = groups running when Rollouter.close starts.

Monarch 0.7.0.dev20260930   exit 130 in 2/3 -> exit 0 in 3/3   (6 groups in flight, drained in 0.05-0.16 s)
Monarch 0.6.0               exit 0 in 3/3   -> exit 0 in 3/3   (5-7 groups in flight, drained in 0.18-0.30 s)
```
Measured on an earlier main (dd4d4830c) with torch 2.15.0.dev20260926. This branch is that commit rebased onto current main without conflicts; only comments and tests changed since.

You may ask:
- Why not only reorder? 5-7 groups were still running after the generators closed. Stopping their workers right away races their last router replies.
- Why not make the router ignore undeliverable replies? It would also hide real delivery failures during training.
- Why 30 s? It only bounds a group stuck in a slow env step or reward. The drains above took at most 0.3 s.

NOTE:
- The base failure is a race: a router reply has to reach a worker while it stops. It hit 2/3 runs here and 6/7 across all my base runs on Monarch 0.7.
- Each rollout in flight at close now logs `marking ERROR` with a traceback, 23-36 per run above. A TODO in `RolloutWorker` tracks logging it at info.
- If the drain times out, a group can still be mid-call when its worker stops.
