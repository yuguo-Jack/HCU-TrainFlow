# [rl] Generator: cheaper GDN metadata build on single-token steps

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5384) · state: open · merged: False

## Original PR description

**TLDR:** On decode steps (one query token per request), the GDN metadata build skips work the decode kernel never reads. That is host time once per step: on a 4-layer Qwen3.5-35B-A3B, decode steps get 4.6% shorter. A full 40-layer model hides most of it.

**Problem**
1. **Metadata.** Before every step, `TorchTitanLinearAttentionMetadataBuilder.build` fills the GDN buffers: query offsets, state slots, `has_initial_state`.
2. **Today.** It always copies and pads `query_start_loc`, and calls `split_decodes_and_prefills`.
3. **Unused at decode.** When every request has 1 query token, the decode kernel reads the fixed `decode_query_start_loc` instead.
4. **Extra ops.** `has_initial_state` takes 3 ops (computed tokens, compare, copy) where 1 compare is enough.
5. **Cost.** This runs on the host every decode step, outside the CUDA graph.

**Solution**
1. On single-token steps, skip the split (the step has `num_reqs` decodes) and the `query_start_loc` copy and fill.
2. With 1 query token, a request has state to resume only when `seq_len > 1`: one `torch.gt` into the buffer.
3. Still filled: `query_start_loc` on a one-token step padded past `max_num_seqs` tokens. No decode graph is that large, so a DP>1 rank padded to the busiest rank's token count replays the mixed-batch graph, which reads it.
4. Unchanged: multi-token (prefill and mixed) steps.

**Results**
Numerics: unchanged (same values in every buffer the kernels read).
```
4-layer Qwen3.5-35B-A3B, GB300, V1 runner, FULL graphs, median over 15 decode shapes (B 1-128, ctx 2k-32k)
decode wall per step, end to end   1.048 -> 1.000
decode kernel time                 1.010 -> 1.000
```
The saving is host time spent once per step for all GDN layers. A 40-layer step has ~10x the GPU work, so its share is smaller. Not measured at 40 layers.

NOTE:
- Changed after the first review: point 3 of Solution. Without it, a decoding rank at DP>1 would replay the mixed-batch graph with the previous mixed step's offsets (wrong outputs, no error). The guard is off on normal decode steps (at most `max_num_seqs` tokens), so the numbers above still hold. Please re-review.
- `num_decode_tokens` is now `num_reqs` on single-token steps (it was the padded token count). The GDN and KDA layers don't read it; they branch on `execution_path`.

**Test plan**
```
pytest tests/rl/unit_tests/gpu/test_gdn_graph_metadata.py tests/rl/unit_tests/gpu/test_gdn_cudagraph.py
```
`test_full_metadata_and_native_dispatch_variants` checks that a one-token step padded past `max_num_seqs` still writes this step's `query_start_loc`. 2 tests skip without a local Qwen3.5-0.8B checkpoint.
