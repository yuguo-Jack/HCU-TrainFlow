# [rl] Fail the weight pull when the trainer did not publish a generator weight

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5487) · state: open · merged: False

## Original PR description

**TLDR:** A generator weight the trainer didn't publish now fails the first weight pull, naming the keys, instead of silently running at its init value. No recipe hits this today; it guards against the trainer and generator model configs diverging.

**Problem**
1. The generator pulls weights with `strict=False`: TorchStore fetches only the keys that are both published and in the generator's pinned CPU dict.
2. A generator key the trainer didn't publish keeps its old value, with no error.
3. `load_state_dict(strict=True)` can't see it, because the pinned dict comes from the generator's own model.
4. In RL there is no HF load on the generator, so the old value is the init: random weights, or zeros for an `expert_bias_E` buffer, so routing can differ from the trainer's.
5. Nothing hits this today: 0 unpublished keys across 32 RL recipes. But the trainer and generator model configs are separate objects, and the controller compares only their class, so a per-role config change can open the gap.

**Solution**
1. `prefetch_model_state_dict` compares the pinned dict's keys with the keys the pull returned, and raises `RuntimeError` naming the first 5.
2. vLLM's attention scales (`.vllm_attn.` keys) exist only in the generator, so they are exempt.
3. Keys the trainer publishes but the generator doesn't hold (e.g. a vision encoder) aren't fetched, so they aren't checked.
4. Unchanged: the weights, the pinned dict, `load_state_dict`.

<details><summary>Key probe (per recipe)</summary>

```python
config = recipe()
with set_current_vllm_config(VllmConfig()), torch.device("meta"):
    trainer = config.trainer.model.build()
    generator = _replace_vllm_layer_configs(config.generator.model).build()
required = {key for key in generator.state_dict() if ".vllm_attn." not in key}
assert not required - set(trainer.state_dict())
```

Run over every `rl_grpo*` recipe in `torchtitan_recipes/rl/alphabet_sort.py` and `torchtitan_recipes/tests/rl/alphabet_sort.py`: 32 of 35 build (3 need `dist_moe`, DeepEP or a newer torchao).
</details>

You may ask:
- Why not check parameters only? That misses persistent buffers (16 `expert_bias_E` in the Kimi K3 debug model) and the tied `lm_head.weight`.
- Why check on every pull? It costs microseconds, and checking once would need a flag.
- Why not `strict=True` in TorchStore? The routing client doesn't support it: each rank reads only the keys it registered.
