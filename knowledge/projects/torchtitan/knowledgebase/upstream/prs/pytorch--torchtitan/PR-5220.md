# [rl] hold each multi-turn session's KV between its turns (5/5)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5220) · state: closed · merged: True

## Original PR description

**TLDR:** opt-in `VLLMGenerator.Config.session_kv_holder = VLLMSessionKVHolder.Config()`. Between two turns of a multi-turn rollout (a tool call, an env step), the session has no request in vLLM, so any new request can take its cached blocks and the next turn recomputes its history. `VLLMSessionKVHolder` keeps a reference on those blocks until the next turn or the rollout's end; when memory runs short, it lets go of whole idle sessions, oldest first. It also covers hybrid models (Qwen3.5). On vLLM's real KV manager, a next turn after full churn hits 48 of 50 prompt tokens with the hold and 0 without; on GPU the gain under memory pressure is unmeasured, so this is headroom.

```text
turn 1 prefill done  ->  hold the blocks turn 2 would hit (attention + Gated-DeltaNet state)
tool call            ->  held: no other request can take them
turn 2 prefill done  ->  hold the blocks turn 3 would hit, drop turn 1's hold
rollout ends         ->  release: the blocks go back to vLLM's free queue, still cached
```

**Problem**
1. A multi-turn rollout re-sends its whole history every turn. vLLM skips recomputing it only while the history is still cached.
2. When a turn finishes, its blocks become "free but cached", and any new request can take them.
3. For a hybrid model, a continuation also needs the Gated-DeltaNet state saved at the previous prompt's end. vLLM's "align" mode hands that block back to the free pool as soon as decode starts, ~1-3 min before the turn ends.
4. Under load, the turn's next call misses and recomputes its whole history. A CPU probe on vLLM's real KV manager: hold at finish -> 0 tokens hit after churn; hold right after prefill -> full hit.

**Solution**
1. `VLLMSessionKVHolder` (`torchtitan/rl/generator/vllm/session_kv_holder.py`), a `Configurable` built by the generator when `session_kv_holder` is set. The engine loop calls it at admission (`track`), once after each engine step (`after_step`), and when sessions end (`release`):
   - Right after a request's prefill, hold the blocks vLLM's own prefix lookup says a continuation would hit: attention plus the matching GDN state blocks (`block_pool.touch`).
   - The session's next prefill takes a new hold, then drops the old one.
2. Release:
   - when the rollout ends (`release_session`): the router always forwards it to the generator the session is pinned to; without sticky routing, at group end;
   - at group end (`release_groups`);
   - after each step, while fewer blocks than a floor are free, so the next step has room: sessions idle longest first, including those whose next request is still waiting (it references none of its blocks yet, so the cost is at most a recompute); only sessions with a running request are skipped. The holder can't act inside a step, so the floor is derived from the engine, with no config field: vLLM's watermark plus the most blocks the next step can add to running requests, which vLLM schedules before it admits new ones. Per KV cache group: one block per running request (GRPO siblings cross a block boundary together) + `cdiv(max_num_scheduled_tokens, block_size)` (one prefill chunk).
   - after a step where nothing runs and requests wait: with an empty batch vLLM admits the head unless its blocks don't fit, so idle sessions are released, oldest first, until some blocks come back. Without this, held blocks could stall the engine for good: nothing running, `free` above the floor, and the head needing more than `free`.
   - A release only demotes: the blocks return to vLLM's LRU free queue with their hashes, so they stay prefix hits until reused.
3. Releases ride the engine-loop decision that every rank receives, so all TP ranks apply them at the same point.
4. Held blocks count in vLLM's KV usage. Works with any vLLM watermark, since the floor is read from the built engine. Incompatible with `reset_kv_cache_on_model_state_dict_load=True` (config check).
5. Off by default. Without a holder, the forwarded release is a no-op on the generator.

**Results**
```
GB300, 35B-A3B chess self-play, the hold on (an earlier fixed free floor of 0.05, watermark 0.03), steps 2-6:
  sessions held per generator    126-252
  released by the free floor     0
  prefix hit                     93-96%
  KV use                         52-66%
A run without the hold had the same prefix hit (93-96%): with KV use under ~66%, little was evicted either way.

CPU (vLLM KVCacheManager, 1 attention + 3 Mamba align groups):
  next turn hits 48/50 prompt tokens after full churn with the hold, 0 without
  80 blocks, 12 held sessions (7 free), nothing running, a 10-block turn waiting:
    floor rule only (before)  never admitted in 20 steps
    this PR                   admitted after the stall release
```
The GB300 run also used a KV admission gate that is not in this stack, and its releases went to the generator that gate placed the group on.

You may ask:
- Why off by default? With KV use under ~66% the hold changed nothing on GB300 (93-96% prefix hits either way); a run under memory pressure comes first.
- Why hold right after prefill, not when the request finishes? The GDN state block leaves the request when decode starts, and under load a freed block survives ~78 s (estimate) while a turn decodes for ~1-3 min.
- Why always forward a session's release, even without a holder? It saves a flag; the cost is one actor call per rollout (not per turn) to a no-op endpoint.
- How does this relate to vLLM request priority? Priority orders requests in vLLM's queue; the holder protects blocks of sessions that have no request in vLLM (between turns), which priority can't see.

NOTE:
- The hold may take an older duplicate of a block that the request also owns, about one extra block per session while it decodes.
- The holder's constructor raises on partial hash hits and on speculative decoding, since both move the replay point.
- After any re-pin (`repin_load_ratio`, on by default since 4/5, or an LRU eviction), the session's hold on its old generator is freed at group end or by the free floor.
- A turn that doesn't fit in the blocks left above the watermark starts only once the running batch ends (then the stall release admits it).
- Derived floor before the watermark, from vLLM's logged KV size (4 KV cache groups): Qwen3.5-4B (~4,600 blocks, 2,048 batched tokens) 16 blocks + 4 per running request, so 136 blocks (2.9%) at 30 running and 336 (7.3%) at 80; 35B chess on GB300 (8,169 blocks, 8,192 batched tokens) 32 + 4 per running request, so 464-1,168 (5.7-14.3%) at the 108-284 requests it ran. The old fixed default was 5%.
- Hybrid models at TP>1: the holder raises if vLLM turns on partial-block hits. Qwen3.5-4B at TP=2 held fine (6/6's TP=2 run); other sizes are untested.
- Not run on GPU with this branch. The GB300 run used a different router release path and never reached the free floor.

### 1. `evict_until_free()` / `after_step()` (`generator.py:1462-1467`)

**Short answer: both are needed.** These two calls *are* the manual management. vLLM has no "prefill finished" or "about to allocate" callback, so the holder has to poll the scheduler around each `engine.step()`. Each call has one job that only it can do:

| call | when | job | what happens without it |
|---|---|---|---|
| `after_step()` | after every step | (a) **take** the hold for requests whose prefill just finished; (b) note that a request has left; (c) stall release | (a) nothing ever gets held, so the feature does nothing. (c) the engine can deadlock |
| `evict_until_free()` | before every step | **give back** holds when free blocks drop below the floor | held blocks fill the pool and vLLM preempts *running* requests |

**Simple examples** (pool of 100 blocks, watermark 3):

*Why `after_step` runs every step, not once per decision:* request R (session S, hybrid model) finishes its prefill in step k. In "align" mode vLLM releases R's prompt-end GDN state block at step k+1, when decode starts. If the hold were taken only at the next decision, up to 16 steps later (`max_engine_steps_between_decisions`), that block would already be in the free queue and could be reused. So it has to run right after step k. The "request left" bookkeeping (`move_to_end`) makes the release order oldest-idle-first instead of insertion order.

*Why `evict_until_free` is needed:* 30 idle sessions hold 90 blocks and 8 requests are decoding. Held blocks have `ref_cnt > 0`, so vLLM's LRU can't take them back. When the 8 decoders cross a block boundary, `allocate_slots` fails and vLLM **preempts running requests**, which is worse than having no hold at all. The floor (`watermark + one prefill chunk per group + groups x len(running)`) releases the oldest idle sessions *before* `schedule()` runs inside `step()`. The holder can't act during the step.

*Why `after_step` also has the stall release:* 12 idle sessions hold 73 of 80 blocks, so 7 are free. Nothing is running, and a 10-block turn is waiting. With no running requests the floor is only `watermark + chunk`, so the free count can sit above it while still being below what the head of the queue needs. vLLM never admits it and nothing ever changes. `test_a_waiting_turn_gets_room_when_held_sessions_fill_the_pool` covers exactly this case.

**But they could be merged into one call.** Between `after_step()` at the end of step k and `evict_until_free()` before step k+1, the only things that run are `release()`, which only adds free blocks, and `add_request()`, which allocates nothing (allocation happens in `schedule()`). `scheduler.running` also stays the same in between. So running the floor check at the end of `after_step()` gives the same result, and the engine loop shrinks to a single hook:
```python
with torch.no_grad():
    request_outputs = self._engine.step()
if self._session_kv_holder is not None:
    self._session_kv_holder.after_step()  # hold new prefixes, stall release, then evict to the floor
```
That's one call site, the holder owns its own ordering, and the reviewer has one hook to reason about instead of two. Worth doing for readability. [Fix this →](https://claude.ai/code?q=On%20branch%20felipemello1%2Fsession-kv%2F5-hold-session-kv%2C%20fold%20VLLMSessionKVHolder.evict_until_free%20into%20the%20end%20of%20after_step%20in%20torchtitan%2Frl%2Fsession_kv_holder.py%20(make%20it%20private%20_evict_until_free)%20and%20remove%20the%20pre-step%20call%20in%20torchtitan%2Frl%2Fgenerator.py%20engine%20loop%3B%20update%20docstrings%20and%20tests%20in%20tests%2Frl%2Funit_tests%2Fcpu%2Ftest_session_kv_holder.py&repo=pytorch/torchtitan)

**Smaller notes on the two methods:**
- `evict_until_free` builds `running_ids` (a set over all running requests) on every step, even though it usually returns immediately. Compute the floor from `len(self._scheduler.running)` first, and build the set only when an eviction is actually needed (`session_kv_holder.py:135-140`). At the 108-284 running requests from the GB300 run, this is per-step Python on the critical path.
- `after_step` scans all of `_live` every step to find prefill completions and finished requests. That's fine for now. The finished case could also be read from `request_outputs[*].finished` instead of probing `scheduler.requests`, but that would need the external id -> internal id mapping, so it's optional.
- The stall release also fires when the batch drains naturally while requests wait because of `max_num_seqs`. The comment acknowledges this ("one cheap extra release"), so it's OK.

### 2. Default on? (`generator.py:871`)

I'd keep it **off for now** and turn it on in a follow-up:
- The constructor **raises** on speculative decoding and on partial-block hash hits. The PR notes that hybrid models with TP>1 hit the second one. Turning it on by default would make those configs fail at build time unless the default were "on when supported", which brings back a hidden branch.
- The PR says this branch has **not run on GPU**, and the gain under memory pressure is unmeasured. In the GB300 run the prefix hit was the same with and without the hold (93-96%).
- Single-turn workloads get nothing from it but still pay the per-step polling and hold blocks until the rollout ends.

Suggestion: land it off, run one GPU job under memory pressure (KV use above ~85%) on this branch, then turn it on in a follow-up with the numbers.

File: `torchtitan/rl/generator.py` · line None

reply from claude: `release()` only says when a session ends. The two calls handle what happens inside vLLM's steps, where vLLM has no hook, so the holder checks the scheduler around `engine.step()`:
- hold: session S's turn 1 finishes prefill in step k. On hybrid models (Qwen3.5), vLLM frees the prompt-end GDN state block when decode starts at k+1. So the hold has to be taken right after step k, not at the next decision, which can be up to 16 steps later.
- free floor: held blocks fill most of the pool while 8 requests decode. vLLM can't take held blocks back, so when the 8 need new blocks it preempts running requests. The holder releases the oldest idle sessions before that happens.
- stall: nothing runs, 7 blocks are free, and a 10-block turn waits. vLLM never admits it, so the holder releases idle sessions until the turn fits.

As suggested, it's one call now: `after_step()` ends with the free-floor check. Between two steps only `release()` (which frees blocks) and `add_request()` (which allocates nothing) run, so the check gives the same answer, or releases a step earlier.
