# [rl] Scheduler launchers on the Monarch actor system, starting with SLURM

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5572) · state: closed · merged: True

## Original PR description

## Summary (human-written)

This PR adds a slurm launcher, so we can launch a job using multiple hosts. See `rl_grpo_qwen3_0_6b_flex_slurm` for the example of how it is used.

## Why
TitanRL can run on several hosts only through a launcher that builds
`MonarchActorSystem(host_meshes=...)` itself; the in-repo path
(`python -m torchtitan.rl.train`) runs every role on the controller's host. There
is no way to submit a recipe to a cluster scheduler from this repo.

**Example.** Qwen3-0.6B GRPO on two 4-GPU SLURM nodes:
```bash
python -m torchtitan.rl.actors.monarch.launcher.submit \
  --module torchtitan_recipes.rl.alphabet_sort --config rl_grpo_qwen3_0_6b_flex_slurm
```
```
node 0 (mesh trainer):  trainer, TP=2 x FSDP=2      4 GPUs
node 1 (mesh node_0):   generator_0..3, 1 GPU each  4 GPUs
```

## What changed
- **Launch recipes** (`launcher/base.py`): `MonarchControllerWithLauncher` is a
  `Controller` subclass whose `Config` adds `launcher` at the root, so a launch
  recipe is "this RL recipe on this cluster", built with
  `MonarchControllerWithLauncher.Config.from_controller_config(config,
  launcher=...)`. `Controller.Config` and `MonarchActorSystem.Config` have no
  launcher settings.
- **Building the actor system** (`controller.py`): `setup_async` builds it
  through a new `Controller._build_actor_system()`, which builds
  `config.actor_system`. `MonarchControllerWithLauncher` overrides it to acquire
  the planned hosts and build `MonarchActorSystem(host_meshes=...)` from
  `self.config`.
- **Submit**: `launcher/submit.py` plans the layout on the submit host and
  submits. The scheduler runs the unchanged `python -m torchtitan.rl.train` with
  the same arguments; `config.build()` builds `MonarchControllerWithLauncher`.
- **Layout planner** (`MonarchLauncher._layout`): places the trainer, then each
  generator, filling one node before the next. A role using a node or more gets
  whole nodes; smaller roles share nodes; idle GPUs are logged as one warning.
  Table of examples in `torchtitan/rl/actors/monarch/README.md` ("Layout").
- **`SlurmLauncher`** (`launcher/slurm.py`): one Monarch `SlurmJob` in batch
  mode, controller on SLURM's head node. Site settings go in `slurm_args`; flags
  the launcher owns are rejected. JIT caches (Triton, vLLM, FlashInfer) default to
  node-local `/tmp/torchtitan-<uid>`.
- **Example launch recipe** `rl_grpo_qwen3_0_6b_flex_slurm` in
  `alphabet_sort.py`.
- **Removed** `MonarchActorSystem`'s `generator_env` argument (and
  `extra_env` behind it): unused since #4834 removed its only caller.
- Small, mechanical: `Controller.Config.resolve_overrides()` (moved out of
  `Controller.__init__` so `submit` plans from the overridden config);
  `generator_role_names` in `provisioning.py`, shared by the planner and
  `MonarchActorSystem`.

## Alternatives considered
- Launcher on `MonarchActorSystem.Config` (an earlier version of this PR): makes
  every recipe pick its scheduler and adds a second way to pass hosts.
- A separate job entry point passing a pre-built actor system through a
  `train.main` hook and `setup_async(actor_system=...)` (an earlier version of
  this PR): more code, and the hook got the config before overrides were
  applied, so root-level overrides never reached the job.
- Launcher config wrapping `Controller.Config` in a `job` field: `--override`
  needs `override` at the root, so CLI overrides and `--print-config` would change.
- Launcher config loaded separately from the RL recipe (`--launcher module:fn`):
  launches are defined per recipe and cluster in practice, as in fairtitan.

## User-facing changes
| Before | After |
| --- | --- |
| Multi-host only via an out-of-repo launcher passing `host_meshes` | Also `launcher.submit` with a `MonarchControllerWithLauncher.Config` recipe |
| `python -m torchtitan.rl.train` | Unchanged |
| `controller.setup_async(actor_system=...)` | **Removed.** Subclass `Controller` and override `_build_actor_system` |
| `MonarchActorSystem(..., generator_env=...)` | **Removed** (no in-repo caller since #4834) |

## Numerics
No computation change. Without a launcher, `Controller._build_actor_system`
builds `config.actor_system`, as `setup_async` did before.

**What the suggestion changes.** Today a job runs a separate entry point (`launcher/job.py`), which passes a `build_actor_system` callback into `train.main`, which then passes the built system into `Controller.setup_async(actor_system=...)`. The suggestion moves that work into a `Controller` subclass:
```python
# controller.py: replaces the setup_async(actor_system=...) parameter
async def _build_actor_system(self) -> ActorSystem:
    return self.config.actor_system.build()

# launcher/base.py
class <Name>(Controller):
    @dataclass(kw_only=True, slots=True)
    class Config(Controller.Config):
        launcher: MonarchLauncher.Config

    async def _build_actor_system(self) -> MonarchActorSystem:
        layout = Layout.from_env()  # raises unless the job was submitted
        meshes = await self.config.launcher.build().acquire_hosts(layout)
        return self.config.actor_system.build(host_meshes=layout.host_meshes(meshes))
```
`Configurable.__init_subclass__` sets `Config._owner` on a nested `Config` (`torchtitan/config/configurable.py:187`), so `config.build()` in an unchanged `torchtitan.rl.train` builds the subclass.

```python
        smaller roles fill shared nodes in order. Example, 4 GPUs per node:

            trainer 8, generators 1 x4  ->  trainer: 2 nodes | shared_0: generator_0..3
            trainer 2, generators 1 x2  ->  shared_0: trainer, generator_0, generator_1
            trainer 4, generators 3 x2  ->  trainer: 1 node | shared_0: generator_0 | shared_1: generator_1
        """
        ...
        mesh_nodes, role_mesh = {}, {}
        num_shared = free_gpus = 0
        for role, world_size in role_world_sizes.items():
            if world_size >= gpus_per_node:
                if world_size % gpus_per_node:
                    raise ValueError(...)
                mesh_nodes[role] = world_size // gpus_per_node
                role_mesh[role] = role
                continue
            # Start a new shared node when the current one is full.
            if world_size > free_gpus:
                shared = f"shared_{num_shared}"
                mesh_nodes[shared], free_gpus = 1, gpus_per_node
                num_shared += 1
            free_gpus -= world_size
            role_mesh[role] = shared
        idle_gpus = sum(mesh_nodes.values()) * gpus_per_node - sum(role_world_sizes.values())
        if idle_gpus:
            logger.warning(f"{idle_gpus} GPUs stay idle: {role_mesh}")
        return Layout(gpus_per_node=gpus_per_node, mesh_nodes=mesh_nodes, role_mesh=role_mesh)
```

### Review of @tianyu-l's review (`README.md:70`: launcher config inside `Controller.Config`)

**Verdict:** I agree with your point, and the code backs it up. Two things would make the comment easier to act on: (1) a note that the launcher has two halves, a submit half and an in-job half, and only the submit half is a natural fit outside the config tree; (2) a concrete recommendation of option 2, because the codebase already has a seam for it.

#### What the code supports in your comment

1. **The nesting couples a recipe to one scheduler.** The PR has to add `rl_grpo_qwen3_0_6b_flex_slurm` (`alphabet_sort.py`), a copy of `rl_grpo_qwen3_0_6b_flex` that only sets `actor_system.launcher`. Every recipe needs a `_slurm` twin, or users have to edit the recipe, to run on a cluster. The README then tells users to put site settings (account, partition) in their own recipe. Those settings belong to the cluster and the user, not to the training config.
2. **The same recipe can't run through both entry points.** `MonarchActorSystem.provision` raises `"This recipe sets a launcher; submit it with ..."` when it runs outside the job (`system.py`, `provision`). `submit.py::_build_launcher` raises the reverse error when the recipe sets no launcher. So the recipe decides how it gets launched, which is backwards.
3. **Secrets end up in config dumps.** `submit.py::_launcher_settings` prints only env *names* ("values can hold secrets"). Inside the job, though, `Controller.Config.maybe_log` logs `self.to_dict()` (when `print_config` is set) and writes it to `dump_folder` (when `save_config_file` is set). Both include `actor_system.launcher.env` with its values. If the launcher is not in the tree, this can't happen.
4. **The codebase already has the "outside the tree" seam.** `Controller.setup_async(actor_system=...)` is documented as *"An actor system the launcher built, e.g. a `MonarchActorSystem` on hosts it allocated"*. `MonarchActorSystem.__init__(host_meshes=...)` is how the internal MAST and FAIR launchers already plug in (per @pzhan9's reply on `system.py:102`). This PR goes the other way: it adds a second path through the config and a TODO to delete the existing seam. Your option 2 would keep a single path.

#### What the comment leaves out

- **The in-job half.** `MonarchLauncher` does two things:
  - On the submit host: `plan` and `submit`.
  - Inside the job: `in_job` and `acquire_hosts`, called from `provision`.

  The in-job half is the reason the config sits under `actor_system`. Moving the launcher out of the tree needs another way for the job to learn its scheduler. That part is small: the PR already passes the plan to the job through env vars (`LAYOUT_ENV`, `_JOB_STATE_ENV`). The submit side could also export the launcher class. A thin launcher-owned job entry point would then:
  1. call `acquire_hosts`,
  2. build `MonarchActorSystem(config.actor_system, host_meshes=layout.host_meshes(...))`,
  3. call `Controller.setup_async(actor_system=...)`.

  `torchtitan.rl.train` stays unchanged, and `actor_system.launcher` goes away. It also settles @felipemello1's change 2 (`self._host_meshes` stays `None`, which affects felipemello1/torchtitan#412) without extra code, because the hosts would come in through the existing `host_meshes` argument.
- **Why option 2 over option 1.** "Launcher owns `Controller.Config`", e.g. `SlurmLauncher.Config(job=Controller.Config)`, still needs a wrapper recipe per scheduler. Every CLI override would also gain a `--job.` prefix, which breaks the PR's "same arguments as `torchtitan.rl.train`" design. With option 2, submit can still load a separate `Configurable` launcher config through `ConfigLoader`, so no custom argparse is needed, which follows the repo's "use torchtitan's config system" rule. The submit command would be something like `submit --launcher-module my_site --launcher-config slurm_gb300 --module ... --config rl_grpo_qwen3_0_6b_flex`.
- **Planning still needs the training config.** `plan` reads trainer and generator world sizes, `num_generators` and `dump_folder` from the resolved config (`resolve_overrides`). That's fine under option 2: the launcher reads the controller config but doesn't live inside it. Worth saying so the author doesn't read the comment as "the launcher can't see the config".

#### Suggested wording, if you want to make it actionable
> Prefer keeping the launcher out of `Controller.Config`: submit loads the launcher config separately, exports what the job needs (layout, launcher class, job state) through env, and a launcher-owned entry point acquires hosts and passes `MonarchActorSystem(host_meshes=...)` into `Controller.setup_async(actor_system=...)`, which is the seam MAST and FAIR already use. Then any recipe runs on any scheduler unchanged, site settings stay out of recipes, and `launcher.env` values never reach `maybe_log`/`save_config_file`.

`build_actor_system` gets the config before overrides are applied. `config.build()` constructs the `Controller` from `replace(self)`, a shallow copy, and `resolve_overrides()` runs on that copy. `apply_overrides` replaces a node with `setattr(parent, attr, new_cfg)`, and for a root-level node (`actor_system`, `launcher`) the parent is the copy, so the original `config` never sees the replacement.

Failure case: a site override that swaps `actor_system` for a `MonarchActorSystem.Config` subclass, or replaces `launcher`. `submit` applies it, because it calls `config.resolve_overrides()` on the loaded config before planning. Nested nodes (`trainer.model`, ...) aren't affected because `replace` shares them.
