# [rl] Support pipeline parallelism in trainer

[Upstream PR](https://github.com/pytorch/torchtitan/pull/3980) · state: closed · merged: True

## Original PR description

**Depends on pytorch/pytorch#200238**, which adds `step(loss_kwarg_mbs=...)` to pipeline schedules. Every PP run in TorchTitan now passes it, so CI will fail until that change reaches the torch nightly.

## Why

The RL trainer rejected pipeline parallelism for two reasons:

1. TorchStore could not publish a complete model from stage-local state dicts. The routing client from #5061 fixes this: every stage publishes into the same key.
2. The RL loss takes per-token arguments (advantages, generator logprobs, loss mask, temperature) that differ per microbatch, and pipeline schedules passed the same `loss_kwargs` to every microbatch. pytorch/pytorch#200238 adds `loss_kwarg_mbs` for this, so TorchTitan no longer needs an RL-side workaround.

## What changes

- **Engine (shared):** under PP, the engine copies `global_loss_token_counts` into each microbatch's loss arguments and passes them to the schedule as `loss_kwarg_mbs`, instead of raising "not supported with pipeline parallelism yet". It also collects one loss metrics dict per microbatch: the schedule's scalar loss wrapper fills a per-microbatch `loss_metrics` dict, replacing it on each call because the schedule also calls the loss on microbatch 0 while inferring stage metadata. `ForwardBackwardResult.loss_metrics` is now nested like `microbatch_groups` (one list per group, one dict per microbatch). The pretraining trainers do not read these metrics.
- **GraphTrainer:** its traced loss takes one shared set of loss arguments. It overrides `_pp_forward_backward_microbatch_group` to keep passing the shared `loss_kwargs` to its runtime, and its existing rejection of per-microbatch loss arguments now also covers its PP path.
- **RL trainer:**
  - Lifts the PP restriction. Context parallelism still raises, because per-token loss arguments are not sharded along the sequence yet.
  - The batcher returns `TrainerStepBatch.microbatch_groups` (`[num_groups][num_pp_microbatches][dp_degree]`), so each group runs as one pipeline step. The controller sends each DP rank its grouped column; the Monarch actor system now slices the trainer ranks as `(pp, dp, cp, tp)` so a DP rank's slice spans every pipeline stage.
  - Ranks without the last stage return no metrics, and the controller takes the result from a rank that has it. V-style schedules (ZBV, DualPipeV) put the last stage on the first PP rank, so this does not assume a fixed rank.
  - RDMA microbatch transfer (`async_loop.batcher.rdma_min_tensor_bytes`, off by default) keeps the group structure, but is rejected together with PP for now: its prefetcher reads one microbatch per group.
  - Every stage publishes its partial state dict into the single `model_state_dict` key, so generators do not depend on the trainer PP layout.
- **CI:** new 8-GPU integration test `rl_grpo_pp2_interleaved1f1b_fsdp2_gen_tp2`: Qwen3-0.6B, trainer PP=2 with Interleaved1F1B (two stages per rank) x FSDP=2, two TP=2 generators, untied embeddings.

## Test plan

- `tests/unit_tests/cpu/test_trainer.py`, `tests/unit_tests/cpu/test_pipeline_parallel.py`, and GraphTrainer's `test_trace_module.py` and `test_graph_pp_runner.py` pass on the 2026-10-07 CPU nightly with pytorch/pytorch#200238 applied. One GraphPP test fails because the optional `dist_moe` package is not installed, which is unrelated.
- RL CPU unit tests pass locally with vLLM stubbed out (no real vLLM on that host); the per-file failure set matches `main`. The tests that spawn Monarch processes (`test_batcher_actor.py`, the multi-rank RDMA test) time out on that host on `main` too, so CI covers them.
- Not yet run on this version: the 8-GPU integration test. It needs vLLM plus the PyTorch change; CI covers it once #200238 is in the nightly.
- An earlier version of this PR, which used an RL-side workaround instead of the PyTorch change, ran an 8-step deterministic batch-invariant run where PP=2 x FSDP=2 matched no-PP FSDP=2 bit for bit on loss, entropy, and reward, with `logprob_diff/max = 0`. grad_norm differed by 1 ULP at one step. This needs re-running on this version.

We have to pack (`_pack_pipeline_targets`) and unpack these fields to be a tensor and passed as `target` field in PP, to make these field split along the inputs.

I think a better idea is to passing a Tuple or Dictionary as target:
```
  schedule.step(
      token_ids,
      target={
          "labels": labels,
          "generator_logprobs": generator_logprobs,
          "loss_mask": loss_mask,
          "advantages": advantages,
      },
  )
```
PyTorch currently effectively does:

```_split_tensor(target, target_chunk_spec, n_microbatches)```

But _split_tensor() expects a tensor:

```target.size(split_dim)```

A dictionary or tuple has no .size(), so this fails before the schedule runs.
