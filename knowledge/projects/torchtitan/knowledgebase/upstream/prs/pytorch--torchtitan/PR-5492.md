# [rl][Observability] log host memory per process kind

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5492) · state: open · merged: False

## Original PR description

**TLDR:** The controller logs host memory every step, per process role: anonymous memory and process count for the controller, trainer, generators, env-server workers and the rest, plus the cgroup's total. Always on, no knob, like GPU memory. One pass takes ~1.5-2 ms per process (320 ms for 219 processes on a devserver), in a thread that the step loop awaits: about 1% of a GB300 step at ~600 processes (estimate).

**Problem**
1. **Many roles share the controller host:** the controller, the env-server workers, and often trainer ranks and generators.
2. **Only GPU memory is logged.** Nothing tracks host memory.
3. **So an OOM is a guess.** One run's 978 GB controller host went from 17% to 100% used in 40 minutes. We could not tell which role grew: more workers, bigger workers, the controller, or the trainer ranks.

**Solution**
1. `compute_host_memory_metrics()` (`controller/metrics.py`) runs once per step inside the `metrics_log` span, in a thread, so its `/proc` reads don't block the event loop. The training loop awaits it, so its time adds to each step, outside `timing/step/total`.
2. It lists every process in the controller's cgroup v2 (`/proc/self/cgroup`, then `cgroup.procs`). On multi-host jobs, trainer ranks are not the controller's children, so walking its process tree would miss them.
3. A process's role is `TORCHTITAN_RL_ROLE` in its spawn env, and children inherit it. `train.py` sets `trainer` and `generator` on the Monarch procs, and the env server sets `env_server_worker` before it spawns workers. This process is `controller`. Untagged processes, or unknown values, are `other`.
4. Per role, it sums anonymous memory (`Anonymous:` in `/proc/<pid>/smaps_rollup`) and counts the processes. Then it reads the cgroup's `memory.current`. All 5 roles are logged every step, 0 when empty.
5. A process that exits mid-scan, or can't be read, is skipped. Without cgroup v2 it warns once and logs nothing.

**Results**
```text
New keys, per role: host_memory/rss_anon_gib/<role>, host_memory/num_processes/<role>
          and once: host_memory/cgroup_memory_current_gib
Real VerifiersEnvServer with 2 pool workers (CPU): env_server_worker 0.65 GiB, 2 processes
One pass on a devserver (aarch64, 64 KiB pages), 219 processes holding 80 GiB: 320 ms (status's RssAnon would take 16 ms)
```

You may ask:
- Why anonymous memory, not RSS or PSS? Summed RSS counts shared library pages once per process (~380 MB per worker with torch). PSS splits those pages among the processes that map them, so one role's value moves when another role starts or exits.
- Why `smaps_rollup`, not `status`'s `RssAnon`? The kernel counts RSS per CPU, and before Linux 6.16 `status` reads only the shared total, missing up to ~18 MiB per CPU. On GB300 hosts (Linux 6.14, 144 CPUs, 64 KiB pages) it read 5.97 GiB where `smaps_rollup` read 12.13 GiB over 70 processes, and 0 kB for a `sleep` child. A devserver with the same CPUs and page size on Linux 6.16 reads the same from both. `smaps_rollup` walks the page tables, so a pass costs ~20x more (above).
- Why an env var for the role? The trainer and generator procs run the same command (the Monarch bootstrap), so nothing else in `/proc` tells them apart. `train.py` already sets per-role values in the spawn env.
- Why not psutil? It is not a dependency, and the anonymous total is one line of `/proc/<pid>/smaps_rollup`.

NOTE:
- `other` includes the batcher, the generator router and the rollout-worker procs (untagged for now, TODO in the code), Monarch host agents, and the env-server process itself (it tags only what it spawns). With `num_workers=1` the env server serves episodes itself, so they count as `other`.
- Only the controller's own cgroup is scanned. Processes in another cgroup (e.g. per-task cgroups) are missed. On a hybrid cgroup v1/v2 host it logs nothing.
- `memory.current` includes page cache, so it can sit well above the summed anonymous memory.
- One sample per step, at its end: it misses the peak during forward/backward.
- Not run: a GPU RL run. The trainer and generator tags are checked with a fake host mesh; a real single-node Monarch proc carried the tag in its `/proc/<pid>/environ`.
- Results are from the branch before the port to main's file layout. The port moves the code and puts the scan inside the `metrics_log` span; the logic is unchanged.
