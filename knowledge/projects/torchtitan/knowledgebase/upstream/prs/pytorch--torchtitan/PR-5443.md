# [dsv4] MTP: pass one labels tensor per depth to MTPLoss

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5443) · state: closed · merged: False

## Original PR description

DeepSeek-V4 with MTP fails at the first loss computation. This affects `deepseek_v4_mtp_debugmodel` and any config with `n_mtp_layers > 0`:

```
ValueError: MTPLoss expects prediction and labels tuples.
```

`DeepSeekV4Model.forward` returns one prediction per depth, but the model inherits `Decoder.preprocess_inputs`, which returns a single labels tensor. DeepSeek-V3 builds the per-depth inputs in `MTPDecoder.preprocess_inputs`; DeepSeek-V4 had no equivalent. The existing V4 MTP tests check the config and the FSDP wiring, not the training path.

This PR makes DeepSeek-V4 follow the DeepSeek-V3 MTP pattern:
- the body of `MTPDecoder.preprocess_inputs` moves unchanged into `preprocess_mtp_inputs()` in `deepseek_v3/mtp.py`. `MTPDecoder` calls it, and so does `DeepSeekV4Model` when it has MTP layers. The tokens, validity masks and labels of every depth are rolled in one place, before CP sharding, and annotated once;
- `DeepSeekV4Model.forward` takes the prepared token tuple and `mtp_input_valid_masks`, like `MTPDecoder.forward`, and `mtp_forward` no longer rolls.

Without MTP layers, DSv4 still uses `Decoder.preprocess_inputs`.

**Test plan**

New CPU tests in `tests/unit_tests/cpu/models/deepseek_v4/test_deepseek_v4_mtp.py`:
- `preprocess_inputs` returns one token tensor, validity mask and labels tensor per depth. They are shifted inside each packed document, and nothing crosses a document boundary or enters the padding;
- the MTP debug recipe runs `preprocess_inputs`, forward and `MTPLoss` to a finite loss;
- on a one-rank mesh, without mocking the annotation, every per-depth tensor carries the SPMD type of its main counterpart.

All three tests fail on main. With this change, 61 CPU tests pass with torch nightly:
- `tests/unit_tests/cpu/models/deepseek_v4`
- `tests/unit_tests/cpu/models/deepseek_v3`
- `tests/unit_tests/cpu/components/test_loss.py`
- `tests/unit_tests/cpu/components/test_validator.py`

`ufmt`, `flake8`, `codespell` and Pyrefly report nothing new. Not run on GPU or on a multi-rank mesh.

### Review: is this the DSv3 MTP pattern?

Only partly. The PR reuses DSv3's pieces (`roll_mtp_sequence` with the same `positions`/`padding_mask`/`IGNORE_INDEX` arguments, `decoder_input_sharding()["labels"]` for the shifted labels, a `(main, *mtp)` labels tuple for `MTPLoss`). It does not follow DSv3's structure. As a narrow fix for the `MTPLoss expects prediction and labels tuples` crash, I think it's correct.

- [x] Gather context (PR diff, DSv3 `MTPDecoder`, DSv4 `forward`/`mtp_forward`)
- [x] Compare against the DSv3 MTP pattern
- [x] Post review

#### How DSv3 does it (`torchtitan/models/deepseek_v3/mtp.py:248-339`)
`MTPDecoder.preprocess_inputs` handles every per-depth input in one place. For each depth it builds three things from the same roll:
1. `mtp_input_tokens_{depth}` and `mtp_input_valid_mask_{depth}` (`roll_mtp_sequence(tokens, ..., return_valid_mask=True)`)
2. `mtp_labels_{depth}`

It puts them all into `input_dict` and adds their entries to the same `input_shardings`. Then it runs one `_cp_shard` and one `annotate_input_spmd_types` over everything. `forward` receives a `tokens` tuple and `mtp_input_valid_masks`, and does no rolling itself.

#### How this PR does it (`torchtitan/models/deepseek_v4/model.py:279-316`)
- **Labels** are rolled in `preprocess_inputs`, on the raw tensors. Then a separate `annotate_input_spmd_types` call runs on just the MTP labels, after `super().preprocess_inputs()`.
- **Input tokens and the validity mask** are still rolled inside `mtp_forward` (`model.py:392-399`), on tensors that are already annotated.

So the shift for one depth lives in two places, and they only agree because both calls happen to pass the same arguments. The docstring admits this ("`mtp_forward` shifts the MTP input tokens itself; the labels are shifted here the same way"). Today it's correct only because DSv4 rejects CP in `__init__`. DSv3 rolls *before* `_cp_shard` precisely because the roll has to see whole sequences. If DSv4 ever gets CP, the token roll in `forward` would run on CP shards while the labels were rolled on full sequences, and they would silently stop lining up.

#### Suggestions
1. **Match DSv3: move the token roll into `preprocess_inputs` as well.** Build `mtp_input_tokens_{depth}`, `mtp_input_valid_mask_{depth}` and `mtp_labels_{depth}` together, and add them to the same `input_shardings` (input layout for tokens and mask, labels layout for labels). Then annotate everything once, return `(main_tokens, *mtp_tokens)` and `mtp_input_valid_masks`, and drop the `roll_mtp_sequence` call from `mtp_forward`. That makes `forward`'s contract the same as `MTPDecoder.forward` and leaves one place to update when CP support lands. The rolls also run once per step in preprocessing instead of inside the traced forward. [Fix this →](https://claude.ai/code?q=On%20branch%20fix%2Fdsv4-mtp-labels%20in%20torchtitan%2Fmodels%2Fdeepseek_v4%2Fmodel.py%2C%20restructure%20DeepSeekV4Model.preprocess_inputs%20to%20mirror%20MTPDecoder.preprocess_inputs%20in%20torchtitan%2Fmodels%2Fdeepseek_v3%2Fmtp.py%3A248-339%3A%20roll%20tokens%20(with%20valid%20mask)%20and%20labels%20per%20depth%20before%20annotation%2C%20register%20them%20in%20a%20single%20input_shardings%20dict%2C%20call%20annotate_input_spmd_types%20once%2C%20return%20a%20tokens%20tuple%20%2B%20mtp_input_valid_masks%20kwarg%2C%20and%20remove%20the%20roll_mtp_sequence%20call%20from%20mtp_forward%20so%20forward%20consumes%20the%20prepared%20tensors.%20Update%20the%20DSv4%20MTP%20unit%20tests%20accordingly.&repo=pytorch/torchtitan)
   - A further step to consider: `MTPDecoder.preprocess_inputs` is the only DSv3-specific code needed here. It could be moved into a shared helper (e.g. `build_mtp_inputs(input_dict, input_shardings, num_mtp_layers)`) that both models call, so DSv3 and DSv4 don't each carry a copy (CLAUDE.md "Reuse over duplication"). `roll_mtp_sequence`/`MTPLoss` are already imported across models from `deepseek_v3/mtp.py`, so a helper there or in `models/common/` fits.
2. **Signature.** `preprocess_inputs(self, input_dict, **kwargs)` hides the keyword-only contract that `Decoder`/`MTPDecoder` declare, and `kwargs["parallelism_context"]` raises a bare `KeyError` if it's missing. Spell out the parameters as the base class does (`parallelism_context`, `parallelism`, `max_num_documents`, `max_context_length`, `global_routing_token_counts`).
3. **`cast(torch.Tensor, labels)`** is only there because `super()` returns the union type. If you follow suggestion 1 and pop `labels` yourself, the cast goes away.

#### Tests
- `test_preprocess_inputs_returns_one_label_per_depth` and `test_mtp_debugmodel_loss_runs` are good. The packed two-document plus padding case is the right edge case to cover.
- `test_shifted_labels_have_the_labels_layout` can't fail as written. Its own comment says an unannotated tensor also reads as the empty local type on a one-rank mesh, so the assertion passes with or without the annotation. Either assert something that differs on one rank, or drop the test and rely on a multi-rank fake-PG run (`ciflow/fake-pg` is already labeled).
- Nothing here has run on GPU or a multi-rank mesh, so a short loss-convergence check on `deepseek_v4_mtp_debugmodel` would be worth adding to the PR description, as CLAUDE.md asks for computation changes.

**Bottom line:** the fix is correct for the current no-CP DSv4, and it reuses DSv3's helpers. But it splits the per-depth shift between `preprocess_inputs` (labels) and `forward` (tokens and mask), where DSv3 keeps all of it in `preprocess_inputs`. I'd recommend aligning with `MTPDecoder.preprocess_inputs`, ideally through a shared helper, before merging.

Restructured to follow the DSv3 pattern in the second commit:

- The body of `MTPDecoder.preprocess_inputs` moved unchanged into `preprocess_mtp_inputs()` in `deepseek_v3/mtp.py`. `MTPDecoder` calls it, and so does `DeepSeekV4Model` when it has MTP layers. - `preprocess_inputs` spells out the base class's keyword-only parameters, and the `cast` is gone.

On the DSv4 MTP debug model, the predictions, labels and loss for a packed batch with padding are bitwise identical between the first commit and this one.

About `test_shifted_labels_have_the_labels_layout` (now `test_mtp_inputs_have_the_main_layouts`): it does fail without the annotation. It asserts `spmd.has_local_type(...)`, which is False for an unannotated tensor. The comment explains why `get_local_type` alone would not be enough on one rank. I checked this by removing the annotation from the first version, and the test failed. It now covers the per-depth tokens and masks too.
