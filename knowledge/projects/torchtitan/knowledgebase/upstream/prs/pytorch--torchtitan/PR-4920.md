# Add DistMuon support for DeepSeek V4

[Upstream PR](https://github.com/pytorch/torchtitan/pull/4920) · state: open · merged: False

## Original PR description

## Summary

DeepSeek-V4 currently uses an AdamW-only recipe, while TorchTitan already provides `DistMuon` and its distributed optimizer-state redistribution runtime. This PR adds a DeepSeek-V4 mixed optimizer recipe that uses `DistMuon` for matrix parameters and AdamW for the remaining parameters.

The implementation: 

- defines DeepSeek-V4 `ComputeLayout` mappings for attention, shared experts, routed experts, router, HC, compressor, and MTP parameters
- separates routed-expert and non-routed parameters into compatible redistribution buckets
- adapts the parameter layout and bucket partitioning strategy from the torchtitan-npu DeepSeek-V4 DistMuon implementation to the current upstream model structure
- keeps fixed Newton-Schulz coefficients supported and adds an optional per-step coefficient schedule
- exposes `muon_ns_steps` and `muon_ns_coefficients` through Python recipe/config factory arguments
- changes the DeepSeek-V4 integration topology from FSDP+TP+EP to FSDP+EP because `DistMuon` does not yet support TP-produced `_StridedShard` layouts

## Motivation

`DistMuon` cannot treat every matrix as an undifferentiated tensor. It needs the logical matrix boundaries and the intended distributed compute layout in order to run Newton-Schulz on the correct projections and redistribute optimizer state safely. DeepSeek-V4 has different attention, expert, compressor, and MTP parameter structures from the existing Kimi recipe, so the model-specific layouts and bucket boundaries belong in the DeepSeek-V4 recipe.

The Newton-Schulz coefficients remain optimizer-owned behavior. A single coefficient triple is reused for every step, while a tuple of triples selects coefficients per step. DeepSeek-V4 only chooses these values through its Python config factory.

## Test Plan

- `42 passed`: DistMuon coefficient tests, DeepSeek-V4 optimizer/layout tests, DeepSeek-V4 MTP tests, and optimizer parameter-group tests
- 4-device Real-PG smoke on Ascend 910B3, FSDP4 + EP4, 10 steps completed, loss `8.22225 -> 6.86945`
- 8-device Real-PG smoke on Ascend 910B3, FSDP8 + EP4, 10 steps completed, loss `8.23890 -> 6.92734`
- `flake8`, `ufmt`, `pydoclint`, `codespell`, AST, whitespace, and merge-conflict pre-commit hooks passed on the changed files
- local `pyrefly` passed with CPU nightly and pinned upstream dependencies
- NPU smoke used a test-only compatibility adapter, eager execution, TP=PP=1, and no CPU swap

## Limitations

Following the current Kimi DistMuon support boundary, the DeepSeek-V4 recipe currently requires `tensor_parallel_degree=1`. TP support and upstream GPU validation remain follow-up work.

- weifengpy · comment · 2026-10-14T21:35:53Z · [source](https://github.com/pytorch/torchtitan/pull/4920#issuecomment-6179023962)

thanks for the PR! this is indeed a gap. following are from AI review. I care about 1 a lot, as it's numeric correctness and why we do DistMuon

```
 **1. Newton-Schulz should see the same matrix boundaries as the forward**
  
  Kimi runs one Newton-Schulz per logical matrix the forward uses, and splits fused weights with `BlockShard` (RFC #4692, #4840),
  including the no-RoPE/RoPE split inside each head. This recipe only splits `wq_b`, and only per head. File references below are
  in `torchtitan/models/deepseek_v4/`.

  - `attention.wq_b`: the forward splits each head into q_nope and q_rope (`attention.py:377`). Please use `BlockShard(dim=0,
  block_sizes=(head_dim - rope_head_dim, rope_head_dim))` instead of `(head_dim,)`, so each head becomes two matrices.
  - `attention.wkv`: the forward splits it into kv_nope and kv_rope (`attention.py:383`), but it is computed as one matrix
  (`Owned`). Please use the same `(head_dim - rope_head_dim, rope_head_dim)` blocks.
  - `attention.wo_a`: the forward views it as `n_groups` independent matrices (`attention.py:439`), but the block size is the full
  height, so Newton-Schulz runs on all groups stacked together. Please use `(o_lora_rank,)`, as @shuhuayu suggested.
  - `hc_attn_pre.hc_fn` and `hc_ffn_pre.hc_fn`: the output is split into pre (sigmoid), post (2 * sigmoid) and comb (Sinkhorn)
  (`mhc.py:44`). These are three different projections, so please use `(hc_mult, hc_mult, hc_mult * hc_mult)` instead of `Owned`.
  - CSA `attention.compressor.wkv`: the rows are two halves, one for the previous group's overlap candidates and one for the
  current group (`compressor.py:98`). Each half is no-RoPE followed by RoPE (`compressor.py:192`). That is four matrices, so
  please use `(head_dim - rope_head_dim, rope_head_dim)` blocks instead of `Owned`.
  - CSA `attention.compressor.wgate`: the same previous/current halves, so `(head_dim,)` blocks.
  - HCA `attention.compressor_128.*`: not on Muon at all today, as @shuhuayu noted. Its `wkv` should get the no-RoPE/RoPE split,
  and `wgate` is one matrix.

  The other Muon layouts match Kimi: `wq_a`, `wo_b`, the router gate, shared experts, routed experts, the MTP `e_proj`/`h_proj`,
  and `hc_head.hc_fn`. Please also extend the unit test to check these block sizes. Today it only checks `wq_b`.

  **2. Other gaps compared with Kimi**

  - **Seed checkpoints break.** Seed checkpoint creation skips `parallelize`, so DistMuon gets plain tensors and fails with
  `TypeError: DistMuon requires DTensor parameters`. The same path works with the old AdamW optimizer. Kimi has
  `kimi_k2_5_debugmodel_seed_checkpoint`, which swaps in AdamW. Please add the same for DeepSeek-V4.
  - **Muon vs AdamW choices.** Kimi keeps biases, embeddings and degenerate matrices on AdamW, and explains each choice in a
  comment. `compressor.ape` is an additive bias on the gate logits, not a linear map, so it should probably stay on AdamW. Please
  also add a comment explaining why the indexer stays on AdamW.
  - **TP guard.** Kimi K3 only rejects TP when DistMuon is in use. This recipe rejects TP > 1 unconditionally, so DeepSeek-V4
  can't run TP even with AdamW. Please gate it like K3, and keep the existing FSDP+TP+EP integration test with AdamW.
  - **CP.** Kimi K3 declares both `dp_shard` and `dp_shard_cp` in every layout. #5191 fixed exactly this optimizer-init failure.
  This recipe declares only `dp_shard`, so it would fail the same way under CP.
  - **PP.** Kimi has a DistMuon PP+FSDP+EP integration test and documents what PP needs. Is PP expected to work for DeepSeek-V4
  with DistMuon?
  - **Buckets.** Kimi pairs MoE layers into one bucket to amortize collective launches. This recipe uses two buckets per layer,
  about twice as many (87 vs about 45 for flash). Not blocking, but worth matching.
  - **Numerics.** Kimi K3 (#4596) was validated with deterministic runs from a shared seed checkpoint: FSDP4 twice, and FSDP4 vs
  FSDP4+EP4. Could you add a similar comparison? The 10-step smoke runs only show that loss goes down.
  - **Reuse.** `_per_expert_compute_layout` and `_align_dist_muon_expert_compute_layouts` are copied from `kimi_k2_7.py`. Please
  import them as `kimi_k3.py` does; that also picks up the `dp_shard_cp` axis.
```
