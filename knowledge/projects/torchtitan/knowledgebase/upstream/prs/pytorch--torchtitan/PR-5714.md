# [rl] Fix metadata-dependent Q/K normalization in batch-invariant mode

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5714) · state: closed · merged: False

## Original PR description

## Summary

Batch-invariant execution requires identical query/key rows to normalize identically regardless of sequence packing. In Attention Gym 0.0.17, passing `cu_seqlens` to `l2norm` can select different reduction layouts for packed prefill and single-token decode. The resulting FP32 summation-order difference can change BF16 rounding even when the Q/K inputs are identical. This PR uses a consistent normalization layout in the affected learner and generator calls.

## Why this affects GDN

GDN's batch-invariant learner and generator passed `cu_seqlens` into Q/K `l2norm`, exposing this metadata-dependent dispatch. The fix omits metadata from normalization while retaining it for recurrence and state ownership.

KDA uses Attention Gym's `l2norm` too, but its learner and generator already call it without `cu_seqlens`. Full attention and MLA do not use this metadata-dependent L2-normalization call for Q/K. These paths therefore do not trigger this particular normalization-layout switch and do not need this fix.

## Reproduce

Run the regression test added in this PR on the baseline and on the PR branch:

```bash
python -m pytest \
  tests/rl/unit_tests/gpu/test_gdn_cudagraph.py::test_batch_invariant_query_normalization_matches_prefill \
  -q
```

Main needs the added test applied first, with its production code unchanged. The test uses a captured BF16 query and exercises the generator's GDN implementation; it needs one GPU and no model checkpoint.

The following matrix checks both parameterized layouts on both GPU types. Baseline production code is `83abb2c0`, with only the regression test added; the fix is the normalization code published in `12094464`. Each cell shows the maximum absolute decode/prefill Q-normalization gap, main -> fix.

| Key heads / value heads | H200: main -> fix | B200: main -> fix |
| --- | --- | --- |
| 1 / 2 (`one-key-head`) | `0.00048828125 -> 0` (fails -> passes) | `0 -> 0` (passes both) |
| 16 / 16 (`qwen3_5-heads`) | `0 -> 0` (passes both) | `0.00048828125 -> 0` (fails -> passes) |

Both cases reuse the same captured BF16 query, repeated across key heads, and both run on whichever CUDA GPU executes pytest. The rows are not restricted to specific architectures. These results describe this fixed query and pair of packing layouts; a passing cell is not exhaustive coverage of that GPU/head-count combination.

In the failing main cells, component 125 is `-0.12109375` in decode and `-0.12158203125` in prefill. With the fix, all selected query components agree bitwise in every cell. The one-key-head case already agrees on B200 because it does not select the Blackwell decode-specific normalization layout; the 16-head case exercises that path.

## What changed

- Omit sequence metadata from Q/K normalization in batch-invariant GDN. Sequence boundaries and state metadata still reach the recurrence.
- Use the same normalization during learner gradient recomputation, with `autotune=False` to pin normalization backward.
- Add the captured-query regression, extend the existing two-GPU parity test to cross token position 128, and check finite gradients for all five recurrent inputs.

Attention Gym 0.0.17 [selects a decode-specific normalization layout](https://github.com/meta-pytorch/attention-gym/blob/4d3bdcf2ea511f335fcf789d7ca1ff88e325c395/attn_gym/linear/kda/fwd/triton/l2norm_fwd.py#L126-L135) for certain BF16 shapes. Omitting `cu_seqlens` from normalization keeps the layout consistent across prefill and decode. The recurrence still receives the original sequence boundaries.

Ordinary GDN and the separate context-parallel path are unchanged; the GPU checks here use CP=1. Changing backward autotuning alone, as in #5655, does not fix this forward discrepancy.

## Validation

On a small C4 slice, main (`d86c77d6`) and the PR (`89211ec4`) produced bitwise-identical loss and gradient-norm traces over 200 updates at learning rate `2e-6`. FP32 master weights and BF16 model weights also matched at the checked updates. A ten-update control with batch-invariant mode disabled matched exactly.

These runs used earlier revisions and show unchanged training on this workload. The captured-query regression above demonstrates the prefill/decode normalization fix.

**What this PR does.** In batch-invariant mode, the GDN learner forward (`_recurrent_gdn_fwd`), its gradient recompute, and the vLLM generator's `_forward_gdn` now call Q/K `l2norm` without `cu_seqlens`. Attention Gym 0.0.17 uses `cu_seqlens` only to pick a reduction layout, and that layout differs between decode-shaped inputs and packed prefill. `cu_seqlens` still goes to `recurrent_gdn`. The non-batch-invariant paths and CP are unchanged.

**Example.**
```
Same BF16 query row q (128 dims), generator in batch-invariant mode:
  decode : T=3,   cu_seqlens=[0,1,2,3]       -> l2norm(q)[125] = -0.12109375
  prefill: T=313, cu_seqlens=[0,143,247,313], q at row 128
                                             -> l2norm(q)[125] = -0.12158203125
main: decode != prefill (1 BF16 ulp)  ->  generator logprobs depend on batch composition
PR:   l2norm(q) with no metadata in both -> bitwise equal
```

<details><summary>Details</summary>

- Necessity: the problem is real and well reproduced, with a captured query, a stated gap, and pass/fail on H200. Root cause is attn-gym layout selection keyed on `cu_seqlens`. Since `l2norm` is per-row, omitting the metadata is semantically a no-op. Changing it only in batch-invariant mode keeps the non-batch-invariant decode layout, and its perf, intact.
- Learner/generator consistency: both sides now normalize without metadata, so trainer forward and generator stay on the same layout. The recompute in `_chunk_gdn_gradients` also drops `cu_seqlens`, so gradients use the same normalized Q/K as the forward. That part is needed; only the autotune half is out of scope.
- KDA (`kda.py:135`, `rl/generator/vllm/kda.py:270,301`) already calls `l2norm` without metadata, so it needs no change, as the description says. `cp_gdn.py:264` still passes `cu_seqlens`. That only matters if batch-invariant mode + CP is supported for GDN, and the PR explicitly leaves it out of scope.
- The new unit test (73 lines, `object.__new__` plus a monkeypatched `recurrent_gdn`) is the deterministic one-GPU reproducer, and it guards a real silent invariant. The `(16, 16)` case only diverges on Blackwell, per its comment. Keep it if CI has Blackwell; otherwise it adds no coverage.

</details>

`autotune=False` is a second concern: backward run-to-run determinism, not the forward prefill/decode layout this PR fixes. It also hardcodes a different policy from KDA (`kda.py:133`, `autotune = not torch.are_deterministic_algorithms_enabled()`) and from open #5655, which edits these same two lines to use the KDA policy. As written, the two PRs will conflict here and leave GDN and KDA with different rules.

Smallest fix: keep only the `cu_seqlens` removal here, so the recompute normalizes Q/K the same way as the forward, and let #5655 own autotuning. If this PR needs it to land first, use the KDA expression:

```suggestion
        # Match the forward's metadata-free normalization layout.
        autotune = not torch.are_deterministic_algorithms_enabled()
        normalized_q = l2norm(inputs[0], autotune=autotune)
        normalized_k = l2norm(inputs[1], autotune=autotune)
```

This works around Attention Gym behavior: `l2norm` is row-wise, but passing it `cu_seqlens` changes its reduction layout. The fix depends on the no-metadata dispatch staying shape-invariant, which is an internal detail of attn-gym 0.0.17. Per CLAUDE.md principle 3, please add a `TODO` with an attention-gym issue link, here and at `torchtitan/rl/generator/vllm/gdn.py:336`. Upstream, the layout should not depend on metadata in batch-invariant mode, or the batch-invariant path should be exposed as an explicit option. That way the workaround can be removed once upstream changes, and a future attn-gym release that adds shape-based decode dispatch has an obvious place to look.
