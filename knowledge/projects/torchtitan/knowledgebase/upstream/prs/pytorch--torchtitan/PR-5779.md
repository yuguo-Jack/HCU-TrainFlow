# [config] Read max_context_length from the model config

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5779) · state: closed · merged: True

## Original PR description

Stacked on #5774, which is stacked on #5776 (GitHub stack: this PR's base is #5774's branch).

## Summary (human-written)
<!-- Write this yourself, not with an AI tool. 2-5 sentences: the problem, why
     this approach, and what you checked yourself. -->

Right now we have both `model.max_context_length` and `training.max_context_length`. The latter is redundant. This PR consolidates them.

## Why
The context length is set twice: once on the model config (`build_model_config(..., seq_len=...)`) and once as `training.max_context_length`. `validate_model_training_config` then requires the two to be equal, so every recipe repeats the model's value:

```python
model_config = build_model_config("debugmodel", seq_len=2048, parallelism=parallelism)
Trainer.Config(
    model=model_config,
    training=TrainingConfig(
        max_context_length=model_config.max_context_length,  # must equal the model's
        ...
    ),
)
```

The model owns its context length: it sizes the RoPE cache and attention metadata, and RL serves it with vLLM `max_model_len = model.max_context_length`. A second copy in `TrainingConfig` adds nothing but a way to get it wrong.

## What changed
- `max_context_length: int` is declared on `BaseModel.Config` (it was on `Decoder.Config`). `TrainingConfig.max_context_length` and the equality check in `validate_model_training_config` are deleted.
- The trainer, training engine, validator, RL controller (batcher and SP divisibility check), torchft and GraphTrainer read `model.max_context_length`.
- `preprocess_inputs` no longer takes `max_context_length`: the decoder reads `self.config.max_context_length` when it builds attention metadata. The engine, validator and GraphTrainer stop passing it.
- Flux: `MODEL_FLAVORS` entries become `(factory, default_len)`, like the decoders, and `build_model_config` takes `seq_len`. The defaults (768 / 512 / 512) are the `_flux_seq_len(img_size, t5_len)` of the shipped recipes, which still pass it explicitly.
- HF backend (experiment): `load_hf_config` also sets `max_context_length`; its `max_seq_len` (aliased to HF `max_position_embeddings`) is unchanged.
- Two RL recipes set different model and training lengths, so they already failed at RL trainer startup on main (the equality check). They now take the length the deleted training value recorded, and their token budgets are multiples of it:
  - `search_r1.rl_grpo_muse_glimmer_30b_search_r1`: the model is built with `seq_len=4096` (it defaulted to 16384; training was 4096).
  - `alphabet_sort.rl_grpo_qwen3_6_27b_varlen_perf`: `num_tokens_per_microbatch_per_dp_rank = seq_len` (65536). Its 2048 came from the 9B base recipe, while the recipe builds a 65536-length model.
- Mechanical, skimmable: `max_context_length=` removed from every `TrainingConfig(...)` in recipes and tests; `config.training.max_context_length` reads become `config.model.max_context_length`.

## User-facing changes
| Before | After |
| --- | --- |
| `training.max_context_length` | removed; set the model length with `build_model_config(..., seq_len=...)` and read `model.max_context_length` |
| RL: `trainer.training.max_context_length` | `trainer.model.max_context_length` |
| `model.preprocess_inputs(..., max_context_length=...)` | argument removed |
| Flux `build_model_config(flavor, parallelism=...)` | also takes `seq_len` (defaults per flavor) |

## Numerics
No computation change: every value the training path reads is the same number as before. I built every zero-argument recipe in `torchtitan_recipes` (220) on the base commit and on this branch: `model.max_context_length` here equals the old `training.max_context_length` for all of them except the two RL recipes above, which could not run on main.

## Testing
- CPU suites (`tests/unit_tests/cpu`, `tests/rl/unit_tests/cpu`, GraphTrainer, torchft and HF-backend tests): same results as the base commit. The remaining failures also fail there on this aarch64 host (LoRA, Qwen3.5 MRoPE x3).
- Tests that asserted the old field or kwarg are updated; the `TrainingConfig(max_context_length=0)` validation case is deleted with the field. No new tests: the recipe build check above covers the move.
