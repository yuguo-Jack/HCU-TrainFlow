## Agent details

Stacked on #5543 ("[MoE] Apply router scores before W2 projection"). Please review only the top commit.

**TLDR:** With DeepEP, the activation output is multiplied by the router scores before w2, as a separate eager op. This PR moves the multiply into the activation's compiled kernel: fp32 math, one rounding, no extra pass over the `[R, F]` activation (R = rows routed to this rank, F = expert hidden size). Activation plus multiply gets about 3x faster. Today only the debug recipe `qwen3_moe_deepep` takes this path: the DeepEP RL recipes use `fused_swiglu` (NOTE).

```text
multiply after activation:   w13 -> activation -> * scores (eager, bf16) -> w2 -> combine (sum)
multiply inside activation:  w13 -> activation with * scores (fp32)      -> w2 -> combine (sum)
```

**Solution**
1. `BinaryActivationFn.__call__` (base of SwiGLU, LimitedSwiGLU, ClampedSwiGLU, SiTUGLU) takes `scores` (`[R]` or None). The compiled region computes `(hidden * scores[:, None]).to(bf16)`.
2. `RoutedExperts` passes the DeepEP scores, and None for other dispatchers.
3. `FusedSwiGLU` accepts `scores` but keeps the separate bf16 multiply: its Triton kernels take no scores.

**Results** (one production-size MoE layer, EP 2, 2x GB300, arms run back to back)

```text
Numerics: not bitwise. Activation output vs fp64 (R = 4096, F = 768):
          after 2.78e-3 | inside 1.66e-3 | one bf16 rounding 1.66e-3

rel L2 vs main (combine scales), compiled: output / input grad / worst weight grad
             multiply after       multiply inside      yardstick
Qwen3        4.8 / 5.8 / 4.6e-3   5.6 / 6.2 / 4.7e-3   5.3 / 5.6 / 5.0e-3
DeepSeek-V3  3.8 / 4.5 / 4.6e-3   4.4 / 4.8 / 4.7e-3   5.1 / 5.1 / 5.0e-3
Qwen3.5      3.3 / 4.3 / 4.6e-3   3.8 / 4.5 / 4.6e-3   5.3 / 6.1 / 6.0e-3
```

- Bitwise, one layer: reruns, default remat vs no remat, CUDA-graph replay vs the same forward without capture, the new kernel's grad vs no-grad forward (op level), and `fused_swiglu` vs multiply after.
- End to end, `qwen3_moe_deepep` (FSDP 2 x EP 2, 30 steps), worst rel diff in loss / grad norm: inside vs main 1.0e-4 / 2.6e-3, after vs main 3.0e-4 / 1.4e-2.

- Training saves about 2.6-4.2% of the layer's compiled fwd+bwd step (16k tokens per rank, no remat). Layer step times were too noisy to show it (identical code moved 23% between runs).

You may ask: **Why not a compiled multiply in `RoutedExperts`?** A second region is a second kernel: the extra pass this PR removes.

NOTE:
- Dropping `fused_swiglu` from the DeepEP RL recipes would move them here. At 16k tokens per rank that saves activation + multiply time, about 2-4% of the layer's compiled fwd+bwd step with `fused_swiglu`, no remat (Qwen3 0.57 of 13.6 ms, DeepSeek-V3 1.41 of 41.9 ms, Qwen3.5 0.35 of 18.9 ms). That needs an RL run: follow-up.
- The forward stays batch invariant (RL logprob parity unchanged). The backward does not: each row's score gradient depends on its position. Without `debug.deterministic`, router grads differ in the last bits from run to run.
- Only SwiGLU was measured.
- Without compile regions, the fp32 multiply raises peak memory (Qwen3, 16k tokens per rank: +0.44 GiB).

**What this PR does.** With DeepEP, the router-score multiply used to run as a separate eager op after the activation. Now `BinaryActivationFn.__call__` takes an optional `scores=[R]` and does the multiply inside the `fused_binary_activation` compiled region, in fp32, with a single cast to bf16. `RoutedExperts` passes the DeepEP scores and `None` for every other dispatcher. `FusedSwiGLU` takes `scores` but keeps the old bf16 multiply after its Triton op, so that path's math is unchanged.

**Example.** DeepEP, `R` routed rows, fp32 `routed_scores_R`:
```text
before: h = swiglu(gate_up)                       # compiled, bf16 out (round 1)
        h = h * scores.to(bf16)[:, None]          # eager pass, scores round, product rounds
after:  h = swiglu(gate_up, scores=scores)        # one kernel: silu(g)*u*s in fp32, round once
Local/AllToAll dispatchers: scores=None -> same Dynamo graph as before (guarded on None).
fused_swiglu recipes: hidden * scores.to(hidden.dtype) -> same math as before.
```

- claude[bot] · comment · 2026-11-03T07:37:46Z · [source](https://github.com/pytorch/torchtitan/pull/5765#discussion_r4452001351)

File: `torchtitan/models/common/activation.py` · line 64

"Rounds once" isn't true for every subclass. `SiTUGLU._activation_fn` ends with `.to(input_dtype)`, so its hidden is already rounded to bf16 before the score multiply, and the result is rounded again. That makes two roundings, the same as the old multiply-after path. This only matters if someone uses Kimi K3 with DeepEP, but this base-class docstring is the contract. Smallest fix: scope the claim, e.g. "the compiled region multiplies in fp32 and rounds once, unless `_activation_fn` itself casts to a lower dtype (SiTUGLU does)". Or drop SiTUGLU's trailing cast so it returns fp32 and the base does the single cast. That second option changes SiTUGLU's numerics for every caller, so the wording fix is the safer one here.

- felipemello1 · comment · 2026-11-03T07:41:05Z · [source](https://github.com/pytorch/torchtitan/pull/5765#discussion_r4452023314)

File: `torchtitan/models/common/activation.py` · line 64

Reply from claude: Inside the compiled region, SiTUGLU still rounds once. Inductor drops a downcast-upcast pair between fused ops, so SiTUGLU's `.to(input_dtype)` stays in fp32 inside the kernel. The `emulate_precision_casts` comment in `torch/_inductor/config.py` describes this. That knob keeps the casts, and it is off by default (`TORCHINDUCTOR_EMULATE_PRECISION_CASTS=0`). A CPU probe at 599361c31 agrees: compiled SiTUGLU with scores has the error of one bf16 rounding vs fp64. Without compile regions, SiTUGLU's own cast does round first. The docstring scopes the claim to "the compiled region" for that reason.
