# Fix final RL validation logging in W&B

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5648) · state: open · merged: False

## Original PR description

Summary:

RL has two distinct clocks. The optimizer step identifies the model version:
step 0 before training, then steps 1 through 150 in the reference run.
W&B's internal _step identifies a committed logging entry. Once an entry is
committed, W&B expects subsequent entries to advance its internal step.

Previously, WandBLogger passed the optimizer step to wandb.log as W&B's
internal step and committed every call. The observed sequence was:

  Event                  Model version  Old W&B call             Outcome
  Initial validation                 0  step=0, commit=True     Saved: 0.10
  Final training metrics           150  step=150, commit=True   Saved; next step is 151
  Final validation                 150  step=150, commit=True   Rejected as out of order

The final validation really ran: the 150-step DAPO run recorded 5/30 (0.17)
held-out correct answers in the console and rollout records, versus 3/30
(0.10) before training. W&B's latest validation value stayed at 0.10
because the initial validation was its only accepted validation entry.
The dashboard was therefore missing a result, not reporting that final
validation failed or that the model still scored 0.10.

Separate model version from W&B event order. Add an optional step_metric to
the shared WandBLogger; when supplied, it registers that metric with
wandb.define_metric as the axis for other metrics. RL opts in with
trainer/step. Every RL log payload includes trainer/step=<optimizer step>,
but wandb.log no longer receives that value as its internal step.
Committing a log entry can advance W&B's internal _step without advancing
the optimizer step.

The corrected sequence for the same run would be:

  W&B entry 0:    trainer/step=0,   validation=0.10
  W&B entry 150:  trainer/step=150, training metrics
  W&B entry 151:  trainer/step=150, validation=0.17

The last two entries are consecutive W&B events for the same model
version. Both plot at trainer/step=150, so the final validation is kept in
W&B history and its 0.17 becomes the latest validation summary value.
Charts explicitly configured to use W&B's _step should instead use
trainer/step when they need optimizer steps on the x-axis.

Only the RL metrics processor enables this behavior. Console and
TensorBoard retain the actual optimizer step, and other WandBLogger
callers keep explicit-step logging. Existing runs are not backfilled:
the fix prevents this loss of data on future runs.

Test Plan:
- 88 targeted CPU tests passed for RL metrics and WandBLogger.
- Offline W&B smoke check: validation 0.10 at model step 0, training at
  step 150, and validation 0.17 at model step 150; the W&B summary reports
  0.17 at trainer/step=150.
