# [rl] Train the MoE router gate; RL turns off only load balancing

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5730) · state: open · merged: False

## Original PR description

## Summary (human-written)
In a previous PR we froze the router. We shouldn't. In this PR i remove the extra class FreezeMoERoutingTransform and keep things a bit more simple.

## Agent details

**TLDR:** RL recipes train the MoE router gate again. `build_rl_model_configs` now turns off only load balancing (the expert-bias update and the router aux loss), which is what grew the trainer-vs-generator logprob gap. With the gate trainable, the gap stayed flat over 60 steps (Qwen3.5-35B-A3B-Base, 4 layers).

```text
main:     build_rl_model_configs -> FreezeMoERoutingTransform: expert bias frozen, aux loss off, router gate frozen
this PR:  build_rl_model_configs -> expert bias frozen, aux loss off; router gate trains
```

```python
# this PR, in build_rl_model_configs
if disable_moe_load_balancing:
    for model_config in model_configs:
        for _fqn, moe_config, _parent, _attr in model_config.traverse(MoE.Config):
            moe_config.freeze_expert_bias = True
            moe_config.router.aux_loss = None
```

**Problem**
1. **Routing.** An MoE layer picks experts with `topk(score(gate(x)) + expert_bias_E)`. The gate is a linear layer; `expert_bias_E` is a buffer that a load-balancing hook moves after every optimizer step.
2. **The drift.** The moving bias tripled the trainer-vs-generator logprob gap in 30 steps, even at lr=0 (Qwen3-30B-A3B, 8 layers: 0.053 -> 0.157). It pushes experts toward ties, so bf16 noise flips more top-k sets.
3. **Main's fix** turns off the bias update and the aux loss in RL.
4. **It also freezes the gate**, with no measurement behind it, so the gate never learns in RL. A later ablation found that freezing it doesn't change the gap (Results).

**Solution**
1. `build_rl_model_configs(disable_moe_load_balancing=True)` replaces `freeze_moe_routing=True`. On every `MoE.Config` of both roles it sets `freeze_expert_bias=True` and `router.aux_loss=None`. The gate keeps its gradient.
2. `FreezeMoERoutingTransform` and `TokenChoiceTopKRouter.Config.freeze_gate` are removed. `build_rl_model_configs` was the transform's only caller, and the transform was the field's only setter.
3. **Unchanged:** the expert bias still routes, at its loaded value. Dense recipes, pretraining and SFT are untouched.

**Results**

```text
Numerics: dense RL recipes unchanged (no MoE layer). MoE RL recipes differ from main by design: the gate now gets updates.

Gap: mean |trainer logprob - generator logprob| over each step's fresh completion tokens, median of the first 5 -> last 5
steps. 4-layer cuts of the real checkpoints, trainer FSDP2 dp_shard 2 x EP 2 (fp32 master weights), TP1 vLLM generator,
2x H100; per step 8 prompts x 8 samples x 200 tokens, random advantages +-1, AdamW lr 5e-6, then weight sync.
Every arm: no expert bias (these Qwen3/Qwen3.5 flavors have none), no aux loss.

                                   gate frozen (main)          gate trains (this PR)
Qwen3.5-35B-A3B-Base, 60 steps     0.0315 -> 0.0290  -8%       0.0317 -> 0.0312  -1%
  same frozen arm, run again       0.0319 -> 0.0271  -15%
Qwen3-30B-A3B, 20 steps            0.0199 -> 0.0187  -6%       0.0185 -> 0.0190  +3%

gate change ||W - W0|| / ||W0||, last step     0 (frozen)    1.7e-3 (Qwen3.5), 5.3e-4 (Qwen3)
expert load max/mean, first -> last step       Qwen3.5: 18.5 -> 19.2 and 19.5 frozen, 18.5 -> 19.0 trains
                                               Qwen3:   6.6 -> 6.4 frozen, 6.6 -> 6.5 trains
Noise: the two identical frozen runs end 7 points apart (-8% vs -15%).
For scale, a moving expert bias at lr=0 (Qwen3-30B-A3B, 8 layers): 0.053 -> 0.157 in 30 steps.
```

These arms ran on the branch that added the RL defaults, switching the gate freeze and the aux loss. This PR's config is the "gate trains" arm, measured only for these flavors without an expert bias.

You may ask:
- Why not keep the transform and drop only its gate line? A public class for two field flips with one caller; `build_rl_model_configs` already applies `fp32_lm_head` inline.
- Why one flag for the bias and the aux loss? Both are load balancing: the bias update balances without a loss, the aux loss with one. In the same ablation the aux loss moved routing on its own (Qwen3.5 load max/mean 18.6 -> 16.0 with the gate frozen), which the RL loss didn't ask for.
- Why not a lower learning rate for the gate? We found no RL setup with an RL-specific router learning rate, and the gate's relative change was 1.7e-3 over 60 steps at lr 5e-6.
- What balances a trainable gate now? Nothing, as with the frozen gate. Over 60 steps the load drifted the same either way.
- Why remove `freeze_gate` too? Nothing sets it after this PR. A frozen-gate experiment can add it back with its first caller.

NOTE: resuming an MoE RL checkpoint saved since the gate freeze landed (2026-10-12) fails at load: `Missing key in checkpoint state_dict: optimizer.state.layers.0.feed_forward.router.gate.weight.step`, because the frozen gate had no optimizer state. Workaround: set `exclude_from_loading=["optimizer", "lr_scheduler"]` on the resumed recipe's `CheckpointManager.Config` (the checkpointer requires both). It loads the weights and the step, with fresh Adam state and a restarted LR schedule. Both checked on CPU with the default DCP checkpointer: Qwen3 debug MoE saved on main, loaded on this PR.
NOTE: not measured: a trainable gate next to a frozen nonzero expert bias (the Muse Spark 816B recipe, the only MoE RL recipe that loads one from a checkpoint; the DeepSeek-V3 debug recipes start it at zero). The bias doesn't move, so the measured drift mechanism is absent.
NOTE: not run: a reward A/B of frozen vs trained gate. The ablation is 4-layer cuts, 20 and 60 steps, random advantages.
NOTE: not run: a batch-invariant MoE RL run checking that the trained gate reaches the generator bitwise. The trainer pushes its full state dict (no `requires_grad` filter), as main already did for the frozen gate.
