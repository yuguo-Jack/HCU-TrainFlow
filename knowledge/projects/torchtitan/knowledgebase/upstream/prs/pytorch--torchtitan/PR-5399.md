# [Linear] Produce the first WGRAD in the weight's grad_dtype

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5399) · state: closed · merged: True

## Original PR description

Stack from [ghstack](https://github.com/ezyang/ghstack/tree/0.18.0) (oldest at bottom):
* __->__ #5399

FSDP2 sets the unsharded parameter's grad_dtype to the reduce dtype. With
the deferred upcast, it stays fp32 only on a microbatch with gradient sync
disabled and no gradient yet, i.e. the first microbatch of gradient
accumulation. There `_LinearFunction.backward` computed the WGRAD as a bf16
`mm`, and autograd then cast it to fp32: an extra cast kernel and a
full-size bf16 temporary, with the WGRAD rounded to bf16 before the upcast.

Without a running gradient, the backward now reads `weight.grad_dtype` and,
when it differs from the input dtype, computes the WGRAD with
`mm(out_dtype=grad_dtype)` so the GEMM's fp32 accumulator is written
directly. The branch stays because CPU has no `mm(out_dtype=)` kernel, even
when the dtype matches the inputs; grad_dtype None (FSDP deferring the
upcast) keeps the plain `mm`.

MXFP8Linear (`output_dtype=ctx.wgrad_dtype`) and HiMidLoLinear (fp32 WGRAD
in every path) already produce the WGRAD in the gradient's dtype.

Numerics: unchanged without FSDP or with gradient sync on every
microbatch. Under FSDP with an fp32 reduce dtype and gradient
accumulation, the first microbatch's WGRAD is no longer rounded to bf16,
so it is more accurate and not bitwise identical to before.

Test: test_first_wgrad_is_produced_in_grad_dtype checks the Function
returns fp32 and matches `mm(out_dtype=fp32)` bitwise; it fails without
this change.
