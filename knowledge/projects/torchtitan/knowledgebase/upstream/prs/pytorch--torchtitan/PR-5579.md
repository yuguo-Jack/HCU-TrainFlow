# [perf] Avoid unsharding input embeddings when this are untied

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5579) · state: closed · merged: True

## Original PR description

This is one of those optimizations that is likely to make a difference in only a limited number of cases.

However, when computing gradients with respect to the input embeddings, the embedding weights themselves are not needed, so we can avoid gathering them during the backward pass.

The performance impact is likely to be noticeable only when the embedding matrix is very large relative to the rest of the network and the communication medium is slow (e.g., InfiniBand). It could also provide a small memory benefit, since the input embedding matrix no longer needs to be unsharded on each rank while gradients are live.

Regardless, this is a one-line optimization, so I think it's worth taking.

**TPS difference:** 2 nodes, 4 A100s per node, with InfiniBand between nodes.

def llama3_debugmodel_tb_100() -> Trainer.Config:

    config.loss.loss_fn.global_vocab_size = vocab_size

### Review: [perf] Avoid unsharding input embeddings when they are untied

- [x] Read the diff and the surrounding FSDP code
- [x] Check correctness: tied embeddings, PP, TP, the other models and the HF backend
- [x] Post the review

**Summary:** For a plain `Embedding`, the change is correct and the speedup is cheap to get. The backward pass of `aten.embedding` only needs `grad_output` and the token indices, never the weight values. This is the case `FSDPModule.set_unshard_in_backward` was written for. Placing the call only in the untied branch is right: when weights are tied, the shared weight is needed for the `lm_head` backward. TP (vocab-sharded `Shard(0)` weight) is also fine, because the DTensor embedding backward only reads the weight's metadata. Under PP, or with `reshard_after_forward=False`, the weight is still unsharded when backward runs, so the change does nothing there but also does no harm.

My main concern is that the flag covers the whole FSDP unit, not just the embedding weight.

#### 1. The flag covers every parameter in the `tok_embeddings` FSDP group (`torchtitan/distributed/fsdp.py:351-353`)

`set_unshard_in_backward(False)` is only safe if **no** parameter in this FSDP unit is used in backward. `apply_fsdp_to_decoder` is shared by every `Decoder`, and some models put more than an `Embedding` inside `tok_embeddings`:

- **muse_glimmer**: `EmbeddingWithNorm` uses a scaleless `RMSNorm`, so it has no extra parameter. Safe today.
- **muse_spark**: `MuseSparkEmbeddingWithNorm` holds `norm: MuseSparkRMSNorm.Config | None`.
  - The current flavor sets `elementwise_affine=False`, so it is safe today.
  - The config allows a learned norm weight, and `elementwise_affine=True` is already used elsewhere in `muse_spark/flavors.py:323`.
  - If someone turns on the embedding-norm weight, the RMSNorm backward would read the unsharded weight after FSDP freed its storage at reshard-after-forward. The result is either a crash or silently wrong gradients, and nothing in this file would point to the cause.

This is the kind of silent breakage that `CLAUDE.md` asks us to flag. I'd suggest gating the call on the actual invariant, not on "the embeddings are untied", for example:

```python
# Embedding backward needs only grad_output and the indices, not the weight,
# so skip the backward all-gather when the unit holds nothing but embedding
# weights.
embedding_weights = {
    m.weight for m in model.tok_embeddings.modules() if isinstance(m, nn.Embedding)
}
if all(p in embedding_weights for p in model.tok_embeddings.parameters()):
    model.tok_embeddings.set_unshard_in_backward(False)
```

The check above assumes torchtitan's `Embedding` subclasses `nn.Embedding`; adjust the `isinstance` if it doesn't. This keeps the optimization for llama3, qwen3, deepseek, gpt_oss, kimi, muse_glimmer and similar models, and turns it off automatically for any embedding module that carries other learnable state.

[Fix this →](https://claude.ai/code?q=In%20torchtitan%2Fdistributed%2Ffsdp.py%20apply_fsdp_to_decoder%20(branch%20f14-no-embedding-unshard)%2C%20only%20call%20model.tok_embeddings.set_unshard_in_backward(False)%20when%20every%20parameter%20of%20model.tok_embeddings%20is%20an%20embedding%20weight%20(e.g.%20muse_spark%20MuseSparkEmbeddingWithNorm%20can%20hold%20a%20learned%20RMSNorm%20weight%20that%20is%20needed%20in%20backward).%20Update%20the%20comment%20accordingly.&repo=pytorch/torchtitan)

#### 2. This depends on `tok_embeddings` not being recomputed in backward

If `tok_embeddings` were ever wrapped by activation checkpointing (directly or through a future `activation_remat` policy), the recompute would run the forward with freed weights. AC is not applied to `tok_embeddings` today, so this is fine for now. It's worth saying so in the comment so a later AC change doesn't break it silently.

#### 3. Numerics proof is missing

The TPS chart is useful. However, the PR checklist in `CLAUDE.md` asks non-computation changes to show **bit-identical loss and grad_norm** before and after, with `debug.seed=42` and `debug.deterministic=True`, checked through TensorBoard (`scripts/loss_compare.py`). Please add that comparison for at least FSDP-only and FSDP+TP. This change only alters which collectives run, so the results should match exactly.

#### 4. A test would be good

A small GPU or fake-PG test would catch any regression in the "grads are reduce-scattered correctly without a backward all-gather" path in future PyTorch versions. The `ciflow/fake-pg` label is already on the PR. The test could compare `tok_embeddings.weight.grad` with and without the flag, or assert that only one all-gather of the embedding happens per step.

#### 5. Nits

- **Comment wording:** "Embedding weight grads only need the token indices" is slightly incomplete, since they also need `grad_output`. The point is that they don't need the weight values. Suggested wording: `# Embedding backward needs only grad_output and the token indices, not the weight, so skip the backward all-gather.`
- **Optional follow-up:** `torchtitan/experiments/transformers_modeling_backend/parallelize.py:259` has its own untied-embedding `fully_shard` path that could get the same optimization. HF embedding modules vary, though (some carry scale parameters), so the same "only embedding weights" gate would be needed there. It's fine to leave this out of this PR.

### Verdict
The idea is good and correct for a plain `Embedding`. I recommend (1) gating the call on "this unit only holds embedding weights" so muse_spark-style embedding norms can't silently break, and (3) attaching the bitwise loss/grad_norm comparison before merging.

I couldn't open the installed PyTorch FSDP2 source in this sandbox. My reading of `set_unshard_in_backward` relies on its documented contract: it is meant for modules whose parameters are all unused in backward, such as embeddings.
