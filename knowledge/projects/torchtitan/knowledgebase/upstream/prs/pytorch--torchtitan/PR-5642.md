# add rmsnorm kernel override

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5642) · state: closed · merged: True

## Original PR description

This pr introduces an overide RMSNorm kernel that allows higher precision accumulation than the default torch RMSNorm.

By default, it uses FP32 + Kahan to simulate the FP64 accumulation behavior. By setting use_kahan_summation to false, you can use actual FP64 to perform the accumulation. 

It allows config'ed input_dtype and output_dtype to cast the input/output to desired dtype to the kernel. The internal accumulation is still performed as FP32 + Kahan/FP64.

### 🔴 Main issue: for most hidden sizes, the extra precision doesn't happen

The forward kernel splits each row into column blocks of `BLOCK_D = min(next_pow2(D), 8192)` (`_row_block_shape`, L287-290). It then does:

```python
block_sum = tl.sum(x * x, axis=1)          # FP32 tree reduction over up to 8192 elems
if USE_KAHAN:
    sum_sq, compensation = _fast2sum(sum_sq, block_sum + compensation)
else:
    sum_sq += block_sum                    # FP64 add of an FP32 partial
```

The higher-precision part (Kahan or FP64) only applies **between column blocks**. Inside a block, the reduction is a plain FP32 `tl.sum` in both modes, and `x * x` is also FP32 in the FP64 mode.

- **When `D <= 8192` the loop runs once.** That covers Llama3 8B/70B (4096/8192), D=5120, and every QK norm (head_dim 64-256). In that case `sum_sq == block_sum`, a single FP32 tree reduction. Both `use_kahan_summation=True` and `False` give the same accuracy as `F.rms_norm`, which also accumulates in FP32.
- **The "FP64" mode isn't FP64 accumulation.** The squares and the within-block sum are rounded to FP32 before they are promoted.
- **Tests:** only D=12288 (two iterations) can tell the two modes apart. That is why `test_default_is_kahan_not_fp64` and `test_kahan_and_fp64_agree_closely` use 12288. `test_high_precision_accumulation_beats_bf16_torch_norm` uses D=4096, so it compares two FP32-accumulating implementations and passes without showing any benefit.

Suggested fix:
- FP64 mode: convert before squaring, `x64 = x.to(tl.float64); block_sum = tl.sum(x64 * x64, axis=1)`. Better still, keep a per-lane `[BLOCK_T, BLOCK_D]` FP64 accumulator across iterations and reduce it once at the end.
- Kahan mode: use a smaller column tile (e.g. 256-1024) so the loop actually iterates. Keep **per-lane** `sum`/`comp` vectors of shape `[BLOCK_T, BLOCK_D]`, compensate in every iteration, and reduce `sum + comp` across lanes only at the end.
- Tests: add a test where `D <= 8192` and the result is measurably closer to FP64 than `F.rms_norm(x.float())`, for example a large-magnitude FP32 input with D=4096.

### 🟠 `_fast2sum` can be called with its precondition violated (L71-76, L124)

Fast2Sum is only exact when `|a| >= |b|` (more precisely, when `exp(a) >= exp(b)`). The code passes `a = running sum` and `b = block_sum + compensation`. A later block can be larger than everything summed so far: for example, with D=16384 split into two blocks, if outlier channels (common "massive activations" in LLMs) sit in the second half. When that happens the error term `e` is wrong. TwoSum (Knuth) has no precondition, has no branch, and costs about 3 more FLOPs, which is negligible next to the memory traffic:

```python
s = a + b
bp = s - a
e = (a - (s - bp)) + (b - bp)
```

### 🟡 Other notes on precision

- **`tl.rsqrt` in FP32 (Kahan mode) is approximate.** It lowers to `__nv_rsqrtf` (about 2 ulp). Once summation is fixed, this error is larger than anything Kahan saves. If tighter `rstd` matters, consider `1.0 / tl.sqrt_rn(...)` with `div_rn`.
- **"Rounded once to the output dtype" in FP64 mode (docstring L20-21):** please check whether Triton converts FP64 to BF16/FP16 directly or via FP32. Going via FP32 would round twice. Either way, the docstring claim should match what the kernel does.
- **The final `compensation` is never added back** before `rsqrt` (L130). This only affects the last half-ulp, but folding in `sum_sq + compensation` is free.

### 🟡 Design and performance

- **Fusion with neighbouring ops is lost.** The opaque custom op stops Inductor from fusing the norm with the preceding residual add or the following cast/quant. Please include perf numbers (≥10 steps, per CLAUDE.md) against the stock compiled `RMSNorm` so users know the cost.
- **No numerical proof yet.** CLAUDE.md asks for loss and grad_norm curves for a compute change. Please add a loss comparison against stock RMSNorm (e.g. on C4) to the PR description.
- **Subclasses are skipped silently.** `exact=True` means subclasses such as `OffsetRMSNorm` (qwen3_5/3_6/3_8) are not replaced. That matches `fused_swiglu`, but the docstring and `OVERRIDE.md` could say so, so users don't assume qwen3_5 gets the higher-precision norm.
- **Backward saves the full input.** It keeps the original `x` (e.g. FP32 when `input_dtype=bf16`) to re-round later. That trade-off is documented. Under activation checkpointing this costs twice the memory of saving the BF16 copy, which is worth one more sentence.

### 🟢 What looks good

- The `custom_op` setup is solid: fake, autograd, `mark_non_differentiable(rstd)`, `opcheck` coverage, and a `fullgraph=True` compile test.
- The dw reduction is deterministic (fixed chunking plus a torch `sum` instead of atomics). The result depends on the SM count, which is fine.
- `_as_rows` correctly handles stride-0 grads (e.g. from `.sum()`) and row-strided views, and there are tests for both.
- I checked `local_spmd=True` against all three norm sharding configs in `decoder_sharding.py`: each sets `out_src_shardings` and `input`, so `_maybe_wrap_with_local_region` won't assert. In the SP case the weight layout `R` with a sequence-varying input gives a pending-reduce dw, the same as the stock path.

### Nits

- `tests/unit_tests/gpu/recipes/test_triton_rms_norm_override.py:31`: the `_reference` docstring says it returns `(y, dx, dw)`, but it returns `(x, w, y)`.
- `tests/integration_tests/features.py`: the Qwen3 test covers both decoder norms and QK norms, so it is a superset of the Llama3 test. Consider dropping one of the two new 4-GPU jobs to save CI time.
- The integration tests only run the default settings (Kahan, no dtype options). A `use_kahan_summation=False` or `out_dtype="float32"` variant would also exercise the FP64 path end to end through the CLI override kwargs.
- The `TestTritonRMSNormDtypeOptions` config tests are CPU-only but sit under `gpu/` and import Triton at module level. This matches `test_fused_swiglu_override.py`, so it's fine if that's intended.

**Summary:** the plumbing (custom op, override, SPMD local region, tests) is in good shape. However, the kernel doesn't yet deliver the higher-precision accumulation the PR is about, except when D > 8192. I'd fix the per-lane accumulation and switch to TwoSum before merging, then add a loss/perf comparison to the description.

### 🟠 1. Compiler FMA contraction can break the error-free steps (L139-142)

TwoSum is exact only if `s` is exactly the rounded `a + b`. Triton launches with `enable_fp_fusion=True` by default, which lets ptxas merge a multiply and a following add into one FMA. At the first level of the `tl.reduce` tree, each thread combines elements it already holds in registers, and those values come straight from `square = x * x`. The compiler is therefore allowed to turn `s = square_a + square_b` into `fma(x_a, x_a, square_b)`. Then `s` is no longer the rounded `a + b`, and the compensation term is no longer exact.

The effect on accuracy is probably second-order. Still, the comments and docstring promise an exact (product, error) pair and exact TwoSum. That guarantee should come from the code, not from the compiler happening not to fuse. The fix costs almost nothing:

```python
_rms_norm_forward_kernel[grid](..., num_warps=_ROW_KERNEL_NUM_WARPS, enable_fp_fusion=False)
```

`tl.fma` is an explicit FMA, so it is not affected by this flag. Alternatively, dump the PTX/SASS once and confirm that no `fma` feeds into `_two_sum`.

### 🟡 2. `sum_sq * (1.0 / D)` — prefer `sum_sq / D` (L157)

`1.0 / D` is a Python float constexpr. For D that is not a power of two (5120, 7168, 12288, gpt_oss's 2880), the result depends on how Triton types that constant when it meets an FP64 tensor. If it is turned into an FP32 scalar first, it has about 6e-8 relative error, which throws away the precision this PR adds. `sum_sq / D` (an int constexpr promoted to FP64, then a correctly rounded `div.rn.f64`) avoids the question.

The D = 12288 case of `test_rstd_is_correctly_rounded_beyond_fp32_sum` should catch this. If it passes on GPU, this item is only a robustness change.

Related nit: Triton passes Python float arguments such as `eps` as FP32. The difference only matters when `mean(x^2) ~ eps`, but you could note it.

### 🟡 3. Docstring claims slightly overstate the precision

- L26: *"`rstd` ... is correctly rounded"*. `tl.rsqrt` on FP64 lowers to libdevice `__nv_rsqrt`, which can be off by about 1 ulp, so the result is not correctly rounded in FP64. After rounding to FP32 (the stored `rstd`, and Kahan mode) it is correctly rounded except in rare double-rounding cases, which matches the "almost always" wording in the test. Suggest: *"correct to FP64 precision; the stored FP32 copy is almost always correctly rounded."*
- L29: *"the output is rounded once to the output dtype"*. In Kahan mode `y = (x * rstd) * w` rounds twice in FP32 before the final cast. In FP64 mode, check whether Triton's FP64 to BF16/FP16 store goes directly or through FP32. This was raised last time and I could not verify it here.

### 🟡 4. Performance and hardware

- Default Kahan mode now does about 10 FP32 operations per element, plus a reduction over tuples (more registers and shared memory than `tl.sum`). It should still be limited by memory bandwidth, but please measure it.
- **FP64 mode on Blackwell Ultra (GB300/B300):** FP64 throughput there is cut down to roughly 1/64 of FP32 or worse. This repo has GB300 recipes, and with FP64 squares, sums and `x * rstd * w` the norm could become compute-bound. One line in the `use_kahan_summation` docstring ("prefer Kahan on GPUs with reduced FP64 throughput") would help users.
- Please add perf numbers (>= 10 steps, per CLAUDE.md) against the stock compiled `RMSNorm`, plus loss and grad_norm curves. The custom op also stops Inductor from fusing the norm with the residual add and the following cast.

### Nits

- `test_high_precision_accumulation_beats_bf16_torch_norm` (L122-135): with BF16 input and BF16 output, both implementations round once to BF16, so max-abs errors will almost always tie. The test passes but shows nothing. The new rstd test already covers this, so consider deleting it or switching it to `out_dtype=torch.float32`.
- `_resolve_dtypes` (L302-305): an FP64 or other unsupported `x.dtype` with no `input_dtype` raises a bare `KeyError` from `_TRITON_DTYPES[x.dtype]`. Including `x.dtype` in the existing `ValueError` check would make the error clearer.
- `tests/unit_tests/gpu/recipes/test_triton_rms_norm_override.py:31`: the docstring says it returns `(y, dx, dw)`, but it returns `(x, w, y)`.

### Summary

The main accuracy problem is fixed. Both modes now accumulate beyond FP32 at every D, and there is a test that would catch a regression. Before merging, I'd make the error-free steps safe from compiler FMA fusion (`enable_fp_fusion=False`), switch to `/ D`, tighten the two docstring claims, and add the loss and perf numbers to the description. None of these looks like a blocker, provided the GPU unit tests pass.
