# [checkpoint] Write the final model-only save to exports/step-N

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5748) · state: closed · merged: True

## Original PR description


Summary:
Fixes #5054.

With the default `last_save_model_only=True`, the last step writes a
model-only checkpoint to `step-N`, the same name as a resumable checkpoint.
Rerunning the job with a larger `training.steps` auto-selects it, `load()`
asks for the full training state, and the load fails with
`Missing key in checkpoint state_dict: dataloader.version`.

The final model-only save is an export, not a checkpoint training can
resume from, so it now goes to `<folder>/exports/step-N`. Auto-resume only
matches `step-N` directory names, so it never sees exports and resumes from
the newest full checkpoint instead. Nothing has to inspect checkpoint
contents to tell the two apart, and any future export kind written under
`exports/` is excluded the same way.

```
checkpoint/
|-- step-500/          # full checkpoint, resumable
|-- step-1000/         # full checkpoint, resumable
`-- exports/
    `-- step-1200/     # final model-only save (training.steps=1200)
```

Changes:
- `BaseCheckpointManager._create_last_step_id` picks the final save's path.
  A model-only final save goes under `exports/`. Step 0 stays at `step-0`:
  `create_seed_checkpoint` saves through the last-step path, and `load()`
  restores `step-0` as the model-only seed.
- The DCP and torch_checkpointing last-step saves use it, and their
  "Saving a model only checkpoint" log line now prints the destination.
- Flux inference loads the export explicitly. `flux_debugmodel_inference`
  used `exclude_from_loading` for every non-model state so that auto-load
  would pick the newest model-only `step-N`; it now sets `load_only=True`,
  `initial_load_path=<dump_folder>/checkpoint/exports/step-<steps>` and
  `initial_load_model_only=True`. The `_test` variant builds the path from
  `TORCHTITAN_TEST_OUTPUT_DIR`, like the HF round-trip test. `infer.py` now
  raises when no checkpoint loads instead of running on initialized
  weights.
- Updated the HF round-trip integration test path, the checkpointer README
  (layout diagram and how to load an export), and `docs/evaluation.md`.

Not changed:
- Folders written before this change still hold model-only `step-N`
  exports, which auto-resume can still select. The HF clause in
  `_is_valid_checkpoint` is kept so retention does not delete existing HF
  exports at `step-N` as abandoned.
- `keep_latest_k` only counts `step-N` directories, so exports are never
  purged.
- `initial_load_path` is still ignored when the folder holds a loadable
  `step-N` (fault-tolerance restart). Inference pointed at a training folder
  with interval checkpoints would load the newest `step-N`; inference should
  use its own folder. Making `load_only` runs skip that rule could be a
  follow-up.

Test Plan:
New tests in `test_checkpoint.py`:
- `test_auto_resume_skips_final_model_only_export`: full `step-2`, model-only
  final save at step 3. Checks the folder holds `step-2` and
  `exports/step-3`, and that `load()` resumes from `step-2`. Fails on main
  (the final save lands at `step-3`).
- `test_seed_checkpoint_stays_at_step_zero`: a model-only last-step save at
  step 0 is written to `step-0`.

Updated tests that hardcoded `step-N` for the final save
(`test_last_save_model_only_and_initial_load_model_only`, two
torch_checkpointing last-step tests, the HF load-path definition test) and
the Flux inference test's fake engine, which now returns True from
`load_checkpoint()`.

```
pytest tests/unit_tests/cpu/components/checkpointer/ \
  torchtitan/experiments/torchft/tests/test_torchft_checkpoint.py \
  tests/unit_tests/cpu/models/flux \
  tests/unit_tests/cpu/test_integration_test_definitions.py
169 passed
```

ufmt, flake8, pydoclint and codespell pass on the changed files. pyrefly
reports no errors in the changed files. GPU integration tests (HF
round-trip, Flux inference) were not run.

**Verdict: Approve -- please address the items below before merging.** The fix is small and at the right layer: final model-only exports go to a directory that auto-resume never scans, which is what @fegin asked for in #5054 ("we shouldn't resume from it"). One in-repo caller still points at the old path. A maintainer still needs to review, since this touches core checkpointer code.

**What this PR does.** When `last_save_model_only=True` (the default), the final save now goes to `<folder>/exports/step-N` instead of `<folder>/step-N`. `_find_load_step` only lists `step-N` entries directly under `folder`, so it can no longer pick a model-only export and then fail to load the full training state. Seed checkpoints (step 0) stay at `step-0`.

**Example.**
```
interval=2, training.steps=3, last_save_model_only=True (default)
main:  checkpoint/{step-2 (full), step-3 (model-only)}
       rerun with steps=5 -> picks step-3 -> "Missing key ... dataloader.version"
PR:    checkpoint/{step-2 (full), exports/step-3 (model-only)}
       rerun with steps=5 -> resumes from step-2
```

<details><summary>Details</summary>

- Gate: #5054 reproduces on main. The DCP `_is_resumable_checkpoint` only checks for `.metadata`, which model-only DCP saves also have. Another fix would be to read the DCP metadata and require `train_state.*`. That costs a metadata read per step dir on remote storage and needs a separate rule for step 0. A path-based split avoids both and is about +15 LoC in core.
- The `step > 0` special case is needed: `train.py:54` creates the seed checkpoint through `save_checkpoint(last_step=True)` at step 0, and `load()` treats step 0 as model-only. `test_seed_checkpoint_stays_at_step_zero` covers this case, which the PR introduces.
- Audited other callsites: torchft (`_ft_folder`), RL recipes (all set `last_save_model_only=False`), `scripts/_checkpoint_test_config.py` (seed is step 0; resume sets `last_save_model_only=False`), `cp_pp_numerical.py` (`step-0`), and `features.py` HF save/load (interval=10, steps=10, so the final save goes to `exports/step-10`). None need changes beyond those listed above.
- An explicit `load_step=N` that points at the final step now fails with `FileNotFoundError ... step-N` instead of the missing-key error. Both are errors, so this is fine.

- claude[bot] · comment · 2026-11-02T22:28:46Z · [source](https://github.com/pytorch/torchtitan/pull/5748#discussion_r4448556348)

File: `torchtitan/components/checkpointer/README.md` · line None

This instruction only works when the loading job's `checkpointer.folder` has no resumable `step-N`. `load()` ignores `initial_load_path` when the folder already holds one (the fault-tolerance rule at `base.py:311-326`). So a user who follows this from the same job folder, e.g. to fine-tune from the export, silently gets `step-1000` instead of `exports/step-1200`. The PR description says this, but the doc doesn't. Suggest adding: "Run it from a job whose `checkpointer.folder` holds no `step-N`; otherwise the newest `step-N` is loaded and `initial_load_path` is ignored."
