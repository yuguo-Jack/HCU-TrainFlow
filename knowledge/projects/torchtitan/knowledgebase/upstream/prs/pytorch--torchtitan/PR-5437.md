# [moe][perf] Rank small route sets pairwise instead of a one-hot cumsum

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5437) · state: closed · merged: False

## Original PR description

**Bitwise vs main?** Yes. The sort order is unchanged (a stable sort on the same keys), so every output is identical.

**TLDR:** Compiled, the MoE dispatch ranks up to 2048 routes by comparing every pair of routes, in one kernel, instead of a one-hot cumsum. Above that it uses the narrow-argsort PR's narrow-key argsort. Dispatch at decode goes from 5 to 3 kernels, and the slow one-hot cumsum at 1024-2048 tokens goes away. Qwen3.5-35B-A3B MoE layer: 275.4 -> 269.2 us at 34 tokens (~1% of a decode step over 40 layers), 597.3 -> 465.4 us at 2048 tokens.

**Problem**
1. **Counting sort.** Compiled, `_sort_routes` finds each route's row in the expert-sorted order with a one-hot `(N, E)` cumsum when `N * E <= 16384 * 256` (N = tokens x top-8).
2. **Decode.** The cumsum, the offsets scan and the scatter each end a kernel: 5 kernels, 9.1 us at 34 tokens (272 routes), each launch-bound.
3. **Mid sizes.** In the generator's compile order (largest size first), the dynamic cumsum is slow at 1024-2048 tokens: 60 us at 2048 tokens.
4. **Cost.** The dispatch region plus counts and offsets: 18.6 us at 34 tokens, 115 us at 2048.

**Solution**
1. **Pairwise rank.** Give each route the key `expert * N + route`; its row is the number of routes with a smaller key. This is the stable sort, as one `(N, N)` compare-and-count.
2. Inductor fuses that count and the scatter of the sort into one kernel.
3. **Size.** It is O(N^2), so it only runs up to `_MAX_PAIRWISE_RANK_ROUTES = 2048` routes (256 tokens x top-8). Above, `_sort_routes` uses the narrow-argsort PR's narrow-key argsort.
4. The counting-sort dispatch PR's one-hot counting sort is deleted.
5. Unchanged: the order, so every output is bitwise identical; eager keeps the argsort.

**Results**
```text
Dispatch region + per-expert counts + offsets, compiled in the generator's order (16384, 14336 tokens first),
CUDA-graph replay, GB300, us (two runs)
tokens   one-hot cumsum   this PR
34       18.7 / 18.5      14.8 / 14.9
256      24.9 / 28.8      22.0 / 19.4
1024     61.4 / 63.6      43.2 / 43.2
2048     114.4 / 116.2    50.1 / 52.8
dispatch kernels at 34 tokens: 5 (9.1 us) -> 3 (5.1 us)
```
```text
Qwen3.5-35B-A3B MoE layer (ffn_norm + router + shared expert + routed experts), generator config, EP=1, no_grad,
generator compile order, CUDA-graph replay, GB300, min of 3 interleaved processes, us
tokens      1      34     64     256    1024   2048   4096
before    66.6  275.4  333.6  391.3  485.1  597.3  551.3   (with the narrow-argsort PR)
after     62.8  269.2  328.0  384.3  431.4  465.4  550.4
```
- Outputs equal the base run bitwise at every size (the base itself differs from run to run by 1 bf16 ulp in a few elements at T >= 256).

You may ask:
- Why not a hand-written routing kernel? FlashInfer's does the sort in one ~4 us launch; the pairwise rank gets to 3 kernels (5.1 us) with 4 lines of torch that every compiled path shares.
