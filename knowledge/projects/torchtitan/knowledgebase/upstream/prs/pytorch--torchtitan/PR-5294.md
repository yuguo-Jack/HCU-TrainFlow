# [rl] Keep Verifiers env-server workers off the trainer imports

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5294) · state: closed · merged: True

## Original PR description

**TLDR:** Every Verifiers env-server pool worker loaded torch, vLLM and Monarch, and used none of them. One such worker starts in ~13 s, but 112 starting at once on one host contend with each other: on a Terminal-Bench training run (8 generators, 112 workers, 144-CPU GB300 hosts), the last worker came up 31 min after the pool started. With this PR, a worker imports only Verifiers, the taskset and its harness, and the last worker comes up after 8 min. That now overlaps the checkpoint load, so after a resume the generators start serving in ~1.5 min instead of ~20 min. On a dev machine, 112 workers come up in 24-28 s instead of 157-269 s, with 185 MB RSS each instead of 1.3 GB. On main, the in-repo Terminal-Bench recipe's workers can't import its local taskset alias yet (see NOTE), so the gain applies to installed tasksets now, and to that recipe after the follow-up.

**Problem**
1. **Spawn.** `VerifiersEnvServer` starts a broker process, and the broker starts `num_workers` pool workers with multiprocessing `spawn` (verifiers 0.3.1 `serve/pool.py:98,171`). Each worker is a fresh Python process.
2. **Three import paths.** Each worker:
   - re-runs the broker's `__main__`, which is the controller script: `train.py`'s top-level imports load torch, vLLM, Monarch and grain;
   - unpickles `log_setup=_setup_env_server_process`, which imports `env_server.py` and its package, `torchtitan.rl.examples.verifiers`;
   - imports the taskset module, under the same package. The package `__init__.py` re-exports the rollouter and `data.py`, which import torch, Monarch and grain.
3. **Unused.** A worker only serves rollouts over ZMQ and calls the model over HTTP.
4. **Cost.** Each worker takes 1.3 GB RSS (dev machine). 112 such workers starting at once contend on the host: on GB300, the median worker came up 30.5-31.7 min after the pool started (six launches).
5. **Silent.** The broker answers `health` itself with 0 workers ready (verifiers `serve/pool.py:194-197`), so the rollouter's `wait_for_server_startup` (`torchtitan/rl/examples/verifiers/rollouter.py:193`) returns at once. A slow pool never errors; it only idles the generators.

**Solution**
1. `env_server.py`: pass `functools.partial(setup_logging, "INFO")`, Verifiers' own logging setup, as `log_setup`, and delete `_setup_env_server_process`. Unpickling it imports no torchtitan module.
2. `env_server.py`: set `sys.modules["__main__"] = types.ModuleType("__main__")` in the broker right before `serve_env`. Spawn then finds no main module name or file to re-run (stdlib `multiprocessing/spawn.py`, `get_preparation_data`). This covers `train.py`, `python -m` and custom launch scripts alike.
3. `torchtitan/rl/examples/verifiers/__init__.py`: drop the re-exports. The two recipes and one test now import from the defining modules.
4. Unchanged: the controller, generator and rollouter code. The broker still re-runs the controller script once.

```text
pool worker imports        before                                                      after
re-run controller script   train.py: torch, vLLM, Monarch, grain                       skipped
unpickle log_setup         torchtitan.rl.examples.verifiers.* (torch, Monarch, grain)  verifiers
import taskset module      torchtitan.rl.examples.verifiers.* (torch, Monarch, grain)  verifiers + harness
```

**Results**
```text
Terminal-Bench training run, 8 generators, 112 workers, 144-CPU GB300 hosts
                                           before                      this PR
last worker up, after the pool starts      30.7-31.7 min (7 runs)  ->  7.8-8.0 min (2 runs)
generators serving, after a resume         19-22 min (3 runs)      ->  ~1.5 min (2 runs)
```
These runs used an earlier main plus unrelated generator changes, and an installed taskset plugin, which workers can import. One of the before runs used the same image and Python path as the two PR runs, and took 31.2 min.

```text
dev machine (384 CPUs, shared, load 120-200), workers pinned to 144 CPUs, Terminal-Bench env config,
train.py's top-level imports in the main script; seconds from spawn until the last "EnvServer up"
                         earlier main          this PR
112 workers              157 s, 269 s    ->    28 s, 24 s
16 workers               69 s            ->    9 s
RSS per worker           1.3 GB          ->    185 MB
RSS, 112 workers total   146 GB          ->    22 GB (incl. the broker)
```
Measured on an earlier main, where `torchtitan/rl/__init__.py` also imported vLLM. Main has dropped that import, but every worker still re-runs `train.py`'s top-level imports.

You may ask:
- Why not set `CUDA_VISIBLE_DEVICES=""` and `MONARCH_TOKIO_WORKER_THREADS=1` in the broker (2 lines)? That removes the CUDA init and the per-CPU Monarch threads, but only ~1% of each worker's mmap/munmap calls (strace), and each worker still takes ~1.4 GB RSS. Verifiers' subprocess runtime also passes the host env through to task programs.
- Why not a lazy module `__getattr__` to keep `from torchtitan.rl.examples.verifiers import VerifiersRollouter` working? It is a shim, and type checkers would see `Any` for the recipes' `VerifiersRollouter.Config(...)` calls. Three in-repo callers are a small change.
- Why not start the broker as its own CLI process? Bigger change; for spawn, the empty `__main__` does the same.

NOTE: code outside the repo that imports from the package, e.g. `from torchtitan.rl.examples.verifiers import VerifiersRollouter`, must import from the defining module instead: `from torchtitan.rl.examples.verifiers.rollouter import VerifiersRollouter`.

NOTE: on main, pool workers can't resolve the Terminal-Bench recipe's local taskset alias, which `register_local_taskset_alias` registers only in the broker. Every worker exits with `ModuleNotFoundError`, before and after this PR. The dev-machine Results therefore add a 3-line plugin module that makes the alias importable in workers.

NOTE: not run: GPU tests. The GB300 runs used this commit before its rebase onto main.

**Follow up**
- [ ] Register the local taskset alias in each pool worker through `log_setup`. Today no worker of main's Terminal-Bench recipe (16 workers) comes up. Both the hook and `register_local_taskset_alias` must live in a module that imports only Verifiers; the latter is in `data.py` today, which imports grain and torch. The new test catches a `log_setup` that brings torch back.
- [ ] Find the remaining 8 min on GB300. It overlaps the trainer's checkpoint load on the same host, which also runs slower there (212-395 s) than in a run without an env server (28 s), and the workers come up 1-1.5 min after that load ends. Timing the workers alone, and on a fresh start, tells whether to start the pool after the load.
- [ ] Verifiers: spawn pool workers in bounded waves, and dispatch only to workers that are up.

**Test plan**
- `pytest tests/rl/unit_tests/cpu/test_verifiers_terminal_bench.py::test_env_server_workers_skip_the_trainer_imports`: checks that the broker hands spawn an empty `__main__`, and that a fresh interpreter can unpickle `log_setup` and import the taskset without loading torch, vLLM or Monarch. It fails on main; with only the `__main__` fix, the worker still loads torch and Monarch. CI runs it in the Verifiers step of `unit_test_cpu_rl.yaml`, by node id, since two other tests in that file already fail on main. It also passes with `harbor` uninstalled, as in that step.
- `pytest tests/rl/unit_tests/cpu`: 433 passed, 2 failed, 5 skipped. Main b81852f00: 432 passed, the same 2 failed (`'Config' object has no attribute 'train_dataset'`, in `test_verifiers_terminal_bench.py`).
- Startup probe: start `VerifiersEnvServer` with the Terminal-Bench env config and N workers from a script that has `train.py`'s top-level imports, then time every "EnvServer up" line.
