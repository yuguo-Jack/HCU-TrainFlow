# [gpt_oss][perf] Add expert biases with a gather and a one-hot GEMM backward

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5192) · state: open · merged: False

## Original PR description

**TLDR:** GPT-OSS's per-expert bias backward becomes one fp32 GEMM instead of a bf16 scatter-add: 2-layer step at 16k -9.7%, deterministic.

**Problem**
1. **Bias per expert.** Each GPT-OSS expert projection (w13, w2) adds its expert's bias to every routed row.
2. **Expanded in eager.** `repeat_interleave` copies the bias out to all R rows, then adds it.
3. **Scatter in backward.** Autograd sums the R row grads back into the bias with a bf16 scatter-add.
4. **Cost.** The scatter alone is 2.65 ms per 2 layers at 16k tokens.

**Solution**
1. **Gather, don't expand.** Each row reads its expert's bias by index (`add_grouped_bias`).
2. **Bias grad as a GEMM.** `one_hot[E+1, R] @ grad[R, O]`, accumulated in fp32: deterministic.
3. **Region.** `grouped_expert_bias` fuses gather + add, on in `GptOssModel.Config`.
4. **Static width.** w13 and w2 differ, so each gets its own kernel; `recompile_limit=16`.
5. **Single path.** The new form is faster in eager too, so no gate.
6. **Unchanged:** expert weights, routing and the dispatcher.

```text
before:  bias[E,O] --repeat_interleave--> [R,O] --add-->   bwd: bf16 scatter_add over R rows
after:   bias[E,O] --gather(expert_id)--> add   (region)   bwd: one_hot[E+1,R] @ grad  (fp32)
```

**Results**
```text
Numerics: the bias grad is not bitwise (it now accumulates in fp32); its error size vs fp64 was not measured.
          An fp64 CPU test checks fwd, input grad and bias grad against the repeat_interleave reference
          (incl. an empty expert and padding rows), eager and compiled.

one projection, 16 experts, R = 4T, fwd+bwd kernel time, GB300   (ideal = min bytes / bandwidth)
T=16k O=5760   1593 -> 615 us   (new form in eager 868, ideal ~319)
T=16k O=2880    947 -> 305 us   (ideal ~160)
T=4k  O=5760    313 -> 161 us
T=4k  O=2880    173 ->  85 us

GPT-OSS 20b layers 0 (sliding window) + 1 (full attention), native dims, 16 local experts (one EP2 rank),
16k tokens, fwd+bwd wall, 1x GB300 (shared), 1 process, with an unmerged MoE dispatch/combine change applied (indicative)
step   28.46 -> 25.70 ms  (-9.7%)
graphs: grouped_expert_bias 6 (2 widths x static/dynamic rows x grad mode), limit 16
```

You may ask:
- Why not let per-block compile handle it? Inductor lowers the gathered bias's backward to an atomic scatter-add: nondeterministic.
- Why not autograd's own backward for the gather? It's an `index_put`, slower.
- Why not fold the w13 bias into `fused_binary_activation`? ~2%, but it needs an interface change in shared MoE code.

NOTE:
- Not measured under CUDA graphs.
- Not tested: TP=2 (the recipe's TP), multi-GPU EP (TorchAO's padded rows only through the padding-row test), the vLLM generator path, GraphTrainer, the flex backend, 120b, loss curves.

**Test plan**
`pytest tests/unit_tests/cpu/test_gpt_oss_compile.py`
