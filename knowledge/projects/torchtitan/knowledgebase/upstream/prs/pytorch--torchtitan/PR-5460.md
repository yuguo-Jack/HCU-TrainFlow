# [compile][perf] SwiGLU region: write the packed gate/up gradient with one store per half

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5460) · state: open · merged: False

## Original PR description

**TLDR:** The SwiGLU region's backward now writes `grad_gate_up` with one store per half: SwiGLU fwd+bwd -27% on GB300 (T=16k, F=2048: 1440 -> 1048 us), now 1% faster than the hand-written Triton override. Prefill and decode unchanged. Bitwise identical to before.

**Problem**
1. **Packed gradient.** `fused_binary_activation` unbinds `gate_up [..., 2, F]` inside the region, so backward produces one `[..., 2, F]` gradient.
2. **Masked stack.** Inductor writes that gradient as one pointwise kernel over both halves: every element loads its inputs behind a mask and picks a half with `tl.where`.
3. **Cost.** At 8T rows x F=2048 the backward kernel takes 788 us at T=16k, 2.1x its bandwidth floor (377 us).

**Solution**
1. **Region options** `max_pointwise_cat_inputs=0` and `max_complex_pointwise_cat_inputs=0`: Inductor writes each half with its own store. The first alone is not enough: the second, at its default 8, still sends a 2-input cat down the masked path.
2. **Unchanged.** Math, graph count, the forward kernel, and other activations (ClampedSwiGLU is neutral).

**Results**

Who gains: models whose default regions include `fused_binary_activation` and that use SwiGLU or ClampedSwiGLU (Llama 3, Qwen3, Qwen3.5, DeepSeek-V3/V4, Muse Glimmer). Kimi K3's SiTUGLU gets the same lowering but was not measured. Muse Spark: no change today; its recipes run Dist-MoE experts or the fused SwiGLU override, and its default regions don't include this one.

You may ask: why not a hand-written backward (`autograd.Function`)? With the same options it saves another ~2% at 16k (606 vs 620 us kernel time), not worth the extra code.
NOTE: measured on GB300 only; H100 not re-measured. Not tested: multi-GPU, loss curves.
NOTE: `test_swiglu.py::test_gpt_oss_forward_and_backward_match_reference` is flaky on main (unseeded inputs, 1 of 10 runs misses atol by one bf16 step); unrelated.

### In plain terms

SwiGLU takes one tensor `gate_up` with shape `[..., 2, F]`. Think of it as two stacked sheets, "gate" and "up". The code splits the sheets apart and computes `silu(gate) * up`.

In backward, autograd has to produce a gradient for each sheet and stack them back into one `[..., 2, F]` tensor, because `unbind`'s backward is a `stack`/`cat`. Inductor can write that stacked result in one of two ways:

- **Before (default):** one kernel covers the whole output. Every element first asks "am I in the top sheet or the bottom sheet?", loads inputs for both cases behind masks, and keeps one with `tl.where`. That is a lot of wasted memory traffic, which is why the PR measures the kernel at about 2x its bandwidth floor.
- **After (this PR):** Inductor treats the output as two slices. The gate-gradient code writes straight into the top half and the up-gradient code writes straight into the bottom half, with no per-element branching. This is Inductor's `ConcatKernel` path, where each input is realized directly into a view of the output buffer.

The two Inductor settings, `max_pointwise_cat_inputs` and `max_complex_pointwise_cat_inputs`, are the size limits under which Inductor still picks the masked "one kernel" version. Setting both to 0 turns that version off for this region. The PR explains why both are needed: the second limit would still send a 2-input cat down the masked path.

These are `torch.compile(options=...)` settings, so they only affect this one compiled region (`local_compile` passes `**compile_kwargs` straight to `torch.compile`, `local_compile.py:69`). Nothing changes globally.

### Should numerics change? Expected: no

- **The math per element is the same.** Each output element of both gradients still comes from the same pointwise ops on the same inputs (`d_gate = grad * up * silu'(gate)`, `d_up = grad * silu(gate)`). The only change is how the result is written into memory: two slice stores instead of one masked `tl.where` store. Choosing between values with `tl.where` adds no rounding.
- **No reductions are involved.** The region is purely elementwise, so there is no accumulation order that could shift. This also fits `batch_invariant=True`.
- **The forward pass is untouched.** It has no cat, which matches the unchanged prefill/decode timings in the PR.
- **One caveat (theoretical).** Bitwise equality is very likely but not guaranteed by construction. Changing how Inductor lowers code can in principle change fusion, for example whether a bf16 intermediate is stored to memory (and rounded) or kept in fp32 registers, or how a multiply-add gets contracted. The PR's bitwise check (output and grad, bf16 and fp32, F = 512 / 2048 / 14336) is the right evidence here, and it shows no such effect.
- **Same pattern already in the repo.** `ComplexRoPE.forward` uses identical options (`rope.py:190-194`) for the same reason.

So I'd expect the loss and grad_norm to be bitwise identical, as the PR claims.

### Code feedback

The change is small and correct. Some notes, none blocking:

1. **SiTUGLU / Kimi K3 not measured** (`activation.py:212`). The options apply to every `BinaryActivationFn` subclass. SwiGLU and ClampedSwiGLU were benchmarked; SiTUGLU, which upcasts to fp32 and casts back, was not. The PR lists Kimi K3 under "Who gains", which is inferred, not measured. A quick bitwise check and timing for SiTUGLU would back that up, or the claim could be softened.
2. **No regression guard.** If a later PyTorch release renames or changes these Inductor settings, the speedup could quietly disappear (an unknown option key would probably raise an error rather than fail silently). A small GPU test using `torch._inductor.utils.run_and_get_code` could check that the backward kernel stores into two slices and has no masked `tl.where` cat. That is optional, and `rope.py` doesn't have one either, so it could be done for both regions together later.
3. **Comment.** Wording and length are fine (flake8 max line length is 120) and the comments are ASCII only. You could add "(see also `ComplexRoPE`)" so readers know the trick appears in two places and keep them in sync. That is a nit.
4. **Recompiles are unaffected.** The options are fixed per region, so they don't add to the graph count against `recompile_limit=16`. That matches the "10 graphs, same as main" result.
5. **Testing scope.** The PR says it was only measured on GB300, with no multi-GPU runs or loss curves. Since the change should be bitwise neutral, a single-GPU loss comparison with `seed=42, deterministic=True` (per CLAUDE.md, via `scripts/loss_compare.py`) would be enough to confirm it end to end.

**Verdict:** LGTM. It is a low-risk, region-scoped compiler option that has precedent in `rope.py`. Numerics are not expected to change and the PR's bitwise checks support that.
