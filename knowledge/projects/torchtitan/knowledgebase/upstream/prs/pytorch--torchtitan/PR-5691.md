## Agent details

**TLDR:** The generator now holds GDN's `A_log` and `dt_bias` as float32 parameters. The float32 cast the GDN kernels need then happens once per weight load, in `load_state_dict`'s `copy_`, instead of in every GDN layer on every step. GDN layer -3.2 to -5.8 us per step (Qwen3.5-27B TP4, 35B-A3B TP2), bitwise.

```python
# this PR, VLLMModelWrapper.__init__, on the meta model before parallelize
for param in (module.A_log, module.dt_bias):  # every GDN module
    param.data = param.data.float()
    param.requires_grad_(False)
self.model._fsdp_param_dtype_override_fn = lambda param: param.dtype

# Decoder._apply_fsdp (core): forwards FSDP's existing knob; the default None is main's path
param_dtype_override_fn=self._fsdp_param_dtype_override_fn,
```

**Problem**
1. The generator's GDN kernels (Attention Gym's decode, gate and chunk kernels) take `A_log` and `dt_bias` in float32 only.
2. vLLM builds the generator model in bf16, so `VLLMInnerGDN` casts both with `.float()`: 2 casts on decode steps, 4 on packed steps, in every GDN layer, inside the CUDA graphs.

**Solution**
1. **Float32 parameters.** `VLLMModelWrapper` converts every GDN's `A_log` and `dt_bias` to float32 and freezes them: FSDP requires one dtype among the parameters that have a grad.
2. **FSDP keeps each parameter's dtype.** FSDP casts every parameter to `mixed_precision_param` (bf16) when it unshards. `Decoder._fsdp_param_dtype_override_fn` forwards FSDP's `param_dtype_override_fn` through `apply_fsdp_to_decoder`. The generator sets it to `lambda param: param.dtype`; its other parameters are already bf16.
3. **Receive what the trainer sends.** The trainer sends parameters in the generator's dtype and buffers in their own (`rl/trainer/trainer.py:506-514`). The pinned CPU copy that receives them is now built the same way, because torchstore's RDMA transport copies raw bytes and asserts equal dtypes. `load_state_dict` then casts `A_log` and `dt_bias` to float32.
4. **`VLLMInnerGDN`** drops its six `.float()` calls.
5. **Unchanged:** the trainer, the kernels, and every model that doesn't set the attribute (FSDP gets None, as on main).
6. **Changed for non-bf16 generators:** the override applies to every generator model. With `generator.model_dtype="bfloat16"` (the default, and required for batch invariance) nothing changes. With float32 or float16 (allowed outside batch-invariant mode), FSDP used to cast the unsharded weights to bf16 (`TrainingConfig().mixed_precision_param`); now they stay in `model_dtype`.

You may ask:
- Why not keep a float32 copy and refresh it after each load (the first version)? It needed a per-load hook in the wrapper. Float32 parameters need none: the load's own `copy_` casts.
- Why not float32 buffers, which FSDP leaves alone? FSDP turns parameters into DTensors but leaves buffers rank-local. The state dict would hold `A_log` as a local `[heads / TP]` tensor, and the weight sync, which reshards DTensors, breaks at TP > 1 (the parity test failed this way).
- Why a `Decoder` attribute? The generator never calls `fully_shard` (`parallelize` -> `_apply_fsdp` is core), and a `parallelize` argument would change all 6 `_apply_fsdp` implementations. The generator sets `_skip_lm_head` the same way.
- Why not float32 in the trainer too? The trainer would compute with its float32 master values while the generator gets bf16 ones, so trainer-vs-generator parity would stop being bitwise.

NOTE: not tested: weight sync over RDMA (multi-host). The receive dtypes follow from torchstore's dtype assert (`torchstore/transport/monarch_rdma.py`). The parity test now asserts that every receive tensor has the dtype the trainer sends.
NOTE: a generator that loads an HF checkpoint directly gets the same numbers: released Qwen3.5 checkpoints (0.8B-Base, 9B-Base, 27B, 35B-A3B-Base) store `A_log` as F32 with bf16-exact values and `dt_bias` as BF16. A non-bf16-exact float32 `A_log` would now load unrounded.
NOTE: at FSDP degree > 1 (vLLM DP > 1), FSDP all-gathers the mixed dtypes as bytes. Checked on CPU only (FSDP 2 and 4, TP2 x FSDP2, TP4 x FSDP2: float32 after unshard and after a load); the GPU tests below run at FSDP degree 1.

With `model_dtype` set to `float32`/`float16` (allowed outside batch-invariant mode, `controller.py:419`), the behavior does change. On the base, FSDP cast every unsharded weight to `TrainingConfig().mixed_precision_param` (bf16). Now the weights stay in `model_dtype`, so a float32 generator computes in float32 and its unsharded weights take twice the memory.

That is probably the more correct behavior, but the description says "Unchanged: ... every model that doesn't set the attribute", and that doesn't cover it. Either say in the description that the generator now honors `model_dtype` for all models, or limit the override to what this PR needs (`lambda p: torch.float32 if p.dtype == torch.float32 else None`; this still keeps a float32 generator in float32, so describing the change is the simpler fix).
