# [rl] trainer ranks pull their own microbatches by RDMA ref

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5272) · state: closed · merged: False

## Original PR description

**TLDR:** The trainer call used to carry every microbatch of the step to every rank. Now it carries refs: 0.05 MB instead of 17.6 MB in the CPU check below. Each rank reads only its own microbatches, over RDMA, on a background thread, two ahead of training. On GPU the loss is bitwise equal to the base, and reads after a step's first microbatch wait ≤ 1 ms per step in total.

Two commits. The first, `[training_engine] Preprocess microbatch groups lazily without CUDA graphs`, makes `TrainingEngine` move each microbatch group to the GPU just before its forward when CUDA graphs are off. This PR needs it so the engine can consume microbatches as they arrive. The second commit is the change described below.

**Problem**
1. **One message per step.** The controller calls `trainer.forward_backward` with the step's whole `[num_microbatches][dp_degree]` grid of `TrainingMicrobatch`, by value.
2. **Every rank gets every column.** Each rank keeps only `row[dp_rank]`, so it unpickles dp_degree times the data it trains on, and needs ~3x the message in fresh host memory while it does.
3. **Nothing trains until everything has arrived.** Delivery is serial with compute.
4. **Small on main, not with extra per-token fields.** Main's fields are 38 B/token, ~1.1 GB per rank for a 29M-token step. Router replay plus top-32 logprobs make it 614 B/token. In one such run, step 3 sent 17.8 GB to each of 4 ranks, and the job died on Monarch's 60 s proc-state timeout.

```text
before: controller --[pickled grid, all DP columns, all at once]--> every trainer rank
```

**Solution**
1. **The call carries refs; each rank pulls its own microbatches.** AReaL keeps rollout tensors on the producer and sends refs the same way.
2. **`MicrobatchRef`** (new `torchtitan/rl/distributed/microbatch_ref.py`):
   - `register` turns every non-empty tensor of a microbatch, including those inside `model_kwargs`, into a Monarch `RDMABuffer` on the controller;
   - `read` copies them into fresh tensors with one RDMA action;
   - `drop` releases the buffers.
3. **`MicrobatchStream`** is what `Trainer.forward_backward` passes as `microbatch_groups`.
   - It reads this rank's column on a background thread, two microbatches ahead of training.
   - The engine only needs `len()` and one in-order pass, so it trains each microbatch as it arrives.
   - A `wait_for_microbatch` span records read time that training didn't hide.
4. **The controller registers in a thread, calls, then drops.** Registering takes ~0.15 ms per tensor (~0.3 s for 2,200) and would stall the rollouts on its loop. It drops while the step's tensors are still alive.
5. **`RL_ENV_DEFAULTS` adds `MONARCH_RDMA_DISABLE_IBVERBS=1`.** Monarch's ibverbs path fails, with no fallback, on some RoCE hosts and on native InfiniBand. Its TCP fallback is on by default.
6. **Unchanged:** the batcher, the grid, the global token counts, the loss, `optim_step`, weight sync, and the engine. Each rank still picks `row[dp_rank]`, as on main.

```text
after:  controller --[refs, ~0.8 MB per production step]--> every trainer rank
        trainer rank:  read thread  | read 0 | read 1, read 2 | read 3  | ...
                       main thread  | wait   | train 0        | train 1 | ...
        controller: drop the RDMA buffers after the call returns
```

**Results**

GPU, Qwen3-0.6B, H100, batch invariant, lockstep, 10 steps, one TP 1 generator. Base is main `432b95dcf` plus the first commit; this PR adds the second:
```text
                                    trainer DP 1 (2 GPUs)          trainer DP 2 (3 GPUs, each rank reads its own column)
loss/mean                           bitwise equal at all 10 steps  bitwise equal at all 10 steps
timing/step/forward_backward        1.393 -> 1.399 s               0.909 -> 0.932 s
wait_for_microbatch, first read     2.3-3.1 ms per step            2.8-5.1 ms per step
wait_for_microbatch, later reads    0.4-1.1 ms per step in total   0.2-0.7 ms per step in total, per rank
```
Means of steps 2-10, with 4,096-token microbatches (0.16 MB each). Step 1's first read also pays the one-time RDMA setup: 57 ms.

Message size, CPU Monarch check with 4 ranks (dp 2 x tp 2) and 12 microbatches of 4,096 tokens, with routed expert ids `[T, 40, 8]` inside `model_kwargs`:
```text
pickled trainer call     17.6 MB (the grid, by value) -> 0.052 MB (refs)
```

Read time per 81.7 MB microbatch, CPU, Monarch's TCP fallback (`MONARCH_RDMA_DISABLE_IBVERBS=1`), all ranks reading at once:
```text
readers   TCP parallelism 1      MONARCH_RDMA_TCP_FALLBACK_PARALLELISM=4
4         130-170 ms             81-107 ms
8         250-276 ms             162-187 ms
16        348-380 ms             131-239 ms
wait after the first microbatch, 4 readers, 200 ms of compute per microbatch:
  0.0 ms while compute releases the GIL, 0.4-1.3 ms while it holds it
```

Stress, CPU: 1,500 steps x 8 microbatches x 4 ranks of register, read and drop, in this PR's order. Every field matched at every step, with no hang.

You may ask:
- **Why one `forward_backward` call per step, not one per microbatch?** The gradient-accumulation flags for the last microbatch (`set_requires_all_reduce`, `set_is_last_backward`, `set_requires_gradient_sync`) live inside one engine call. Per-microbatch calls would move that state to the controller.
- **Why a Python thread if Rust moves the bytes?** A Monarch `Future` does nothing until someone calls `get()` or awaits it. The actor's loop thread is busy in forward/backward, and `get()` there warns.
- **Why one buffer per tensor, not one packed buffer per microbatch?** Reads are as fast, and packing would cost one controller copy per microbatch.
- **Why read two ahead?** While the engine waits on microbatch i, reads i+1 and i+2 are queued, so a rank holds at most 4 microbatches on the host. Not tuned.
- **Why not TorchStore?** TitanRL's store only accepts the weight sync's planned keys. A second store needs `ControllerStorageVolumes`, which is deprecated, and cleanup on both sides. It is ~10x faster on one host (shared memory), so it's an option if `wait_for_microbatch` ever shows exposed reads.
- **Why not slice the call per DP replica?** That cuts the message by 1/dp but doesn't bound it, and it changes nothing at dp 1.

NOTE:
- **RL now runs on Monarch's TCP fallback by default.** It's a `setdefault`, so a launcher can set `MONARCH_RDMA_DISABLE_IBVERBS=0` where Monarch ibverbs works. Without the default, every RL run on a host with ibverbs hardware would need the variable. On main, single-host weight sync goes through TorchStore shared memory and never touches Monarch RDMA. On hosts where Monarch ibverbs does work, the default also moves TorchStore's cross-host weight sync to TCP.
- **Monarch 0.6 deadlocks in `RDMABuffer.drop()` when the buffer is the last owner of its storage.** The controller drops while the step's tensors are alive, and a comment says why.
- **The TCP fallback is served by one controller actor,** so per-rank read speed falls as readers grow. At TP 4-8, set `MONARCH_RDMA_TCP_FALLBACK_PARALLELISM=4`. That variable is process-wide, so it also affects weight sync.
- **Metrics include new work.** `timing/step/forward_backward` now includes registering and dropping the refs. `trainer/tokens_per_second`, `trainer/tflops` and MFU include each step's first read, which is never hidden.
- **Not tested:**
  - Multiple hosts, TP > 1 on GPU, and large microbatches on GPU with weight sync on. The CPU checks cover DP 2 x TP 2 and 82 MB microbatches.
  - The RL GPU CI: please run it before merging, since its runners may expose ibverbs devices.

Follow up:
- [ ] Read once per DP replica and broadcast within it. The cp * tp ranks of a replica read the same column today (TODO in `Trainer.forward_backward`).
- [ ] Register in `_batcher_loop` a step ahead, so the first read can start during the previous `optim_step` (TODO at the controller call).
- [ ] Read into pinned tensors to make the engine's per-microbatch copy to GPU async (TODO in `MicrobatchRef.read`).

**Test plan**
- `pytest tests/rl/unit_tests/cpu`: 521 passed. The 2 failures also fail on the base in the same environment: `test_rollouter_builds_one_env_per_group_member` and `test_worker_executes_group_without_actor_mesh`.
- New `tests/rl/unit_tests/cpu/test_microbatch_ref.py` (fake RDMA classes):
  - every field round-trips, including a tensor in `model_kwargs`, and an empty tensor goes by value;
  - the stream yields in order and reads exactly two ahead (it fails for a read-ahead of 0, 1 or 100);
  - the read thread sees the caller's context;
  - a read error surfaces at its position;
  - closing the stream cancels queued reads.
- CPU Monarch check (script not in this PR): 4 ranks at dp 2 x tp 2 with the real module. Every field matched, with routed ids in `model_kwargs`, for 40 steps and again for 1,500 steps. It also passed with the RDMA env vars unset, relying on the new default.
- GPU loss parity: the DP 1 and DP 2 runs above.
