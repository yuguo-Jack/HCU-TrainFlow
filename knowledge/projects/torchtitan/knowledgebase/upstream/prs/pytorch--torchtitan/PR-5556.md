### 2. `mla.py:86`: why `_VLLMNativeMLAAttention` overrides anything, and what comment to add

Once item 1 is done, what's left in this class is a workaround for one vLLM behaviour. Here is my understanding; @liangel-02, please confirm it against vLLM:

- vLLM's `MLAAttention.process_weights_after_loading` splits `kv_b_proj.weight` into two decode-time matrices. `W_UK_T` folds the K up-projection into the query, so decode can take the dot product directly against the cached latent. `W_UV` up-projects the latent attention output to `v_head_dim`.
- vLLM stores these as `nn.Parameter`s on the attention layer. That puts them in `state_dict()` as `...vllm_mla.W_UK_T` and `...vllm_mla.W_UV`. The trainer has no such keys, so the generator's `load_state_dict(strict=True)` during weight sync fails. HF adapters with strict key mapping, such as K3, fail the same way.
- `VLLMInnerAttention` (attention.py:393) doesn't need this, because `vllm.Attention` owns no weights. It only has the scale buffers, which are handled by `_exclude_vllm_attn_scales_from_state_dict`. That's the same kind of fix.

Suggested docstring for the class:
```python
class _VLLMNativeMLAAttention(VLLMNativeMLAAttention, Module):
    """vLLM MLA attention that participates in the TorchTitan Module protocol.

    vLLM derives ``W_UK_T``/``W_UV`` from ``kv_b_proj.weight`` in
    ``process_weights_after_loading`` and registers them as parameters. They are
    not model weights (the trainer has no such keys), so they are moved to
    non-persistent buffers to keep the generator's state dict identical to the
    trainer's. For a bf16 ``Linear`` they are views of ``wkv_b.weight``, so weight
    sync's in-place copy updates them without re-deriving.

    TODO: upstream registering these as non-persistent buffers in vLLM, then drop
    this override.
    """
```

**Make the "views" claim a checked invariant, not a comment.** Without the refresh loop, decode is only correct if `W_UK_T` and `W_UV` share storage with `wkv_b.weight`. If that breaks, decode quietly keeps using step-0 weights while prefill uses the new ones, and nothing errors. It would break if, for example:
- vLLM calls `.to(act_dtype)` or `.contiguous()`, or a backend pre-packs the weights;
- `process_weights_after_loading` runs while FSDP holds the sharded param rather than the unsharded storage.

Two concrete asks:
- Right after `super().process_weights_after_loading(...)`, assert that `W_UK_T` and `W_UV` share storage with `kv_b_proj.weight`, with a clear message. CLAUDE.md allows this kind of check because the failure would otherwise be silent.
- Add a CPU test: build the layer, run `process_weights_after_loading`, call `VLLMModelWrapper.load_state_dict` with a *different* `wkv_b`, then check that `W_UK_T` and `W_UV` match the new weight. Run it with the existing `fully_shard` fixture too (test_vllm_wrapper.py:185). The current test at line 351 only checks the initial derivation.

### 3. `mla.py:144`: native TorchTitan latent-space MLA kernel

+1 to having one, the way varlen does for GQA. The order I'd suggest:
1. **This PR:** land the vLLM-native compressed path for plain bf16 `wkv_b`, scoped as described in items 1 and 2. Add a module-level `TODO` in `mla.py` pointing to the follow-up, so the dependency on vLLM's kernel is clearly temporary.
2. **Follow-up:** a TorchTitan `InnerAttention` that takes `(q_THK, kv_c_normed_TL, k_shared_TR)` and does the absorbed latent decode itself, the varlen equivalent for MLA. The generator's `VLLMMLAInnerAttention` would then only handle the paged-cache read and write, the same way `VLLMInnerAttention` does today. If the same kernel ran on both trainer and generator, batch-invariant mode could keep the compressed cache too. That would remove the `is_in_batch_invariant_mode()` branching now in both `registry.py:76` and `model_wrapper.py:89`.

### 4. Related cleanups (small)

- **Duplicated mode check:** `is_in_batch_invariant_mode()` drives the compressed-vs-materialized decision in three places:
  - `vllm_attention_backend`
  - `model_config_to_hf_config_dict` (`kv_lora_rank` keys)
  - `_replace_vllm_layer_configs`

  If any one of them disagrees with the others, the cache gets sized for one layout while the layers use the other. I'd put the decision behind one small predicate used by all three. It should be just `isinstance(..., MLAAttention.Config) and not is_in_batch_invariant_mode()`, with none of the earlier dim or `wkv_b` checks, which matches your earlier comment.
- **Duplicated flex error:** the "MLA + flex unsupported" `ValueError` appears twice, at `registry.py:83` and `model_wrapper.py:107`. Keep one.
- **Scale buffers:** `VLLMMLAInnerAttention.__init__` still sets `ShardingConfig.state_shardings` for the scale buffers after making them non-persistent. That's fine, since buffers still need to be placed on devices. A one-line comment saying so would answer your earlier "why vllm makes them persistent" question at the call site.
