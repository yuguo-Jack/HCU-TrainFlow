# [LoRA] Fix SPMD type checking under tensor parallelism

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5390) · state: closed · merged: True

## Original PR description

## Summary

LoRA under tensor parallelism fails SPMD type checking: on a row-parallel linear, `lora_b` receives a partial sum from `lora_a`, and `_LinearFunction`, which `Linear` uses by default, accepts no partial-sum input; this PR gives `_LinearFunction` the typing rule of a matmul, which is linear in its input.

- `torchtitan/models/common/linear.py`: `_LinearFunction.spmd_typecheck` types the GEMM with `rules.einsum(..., linear_in=(0, 1))` and the bias add as jointly linear, in place of `register_local_autograd_function`.
- `tests/unit_tests/cpu/models/common/test_lora.py`: a two-rank test runs a LoRA feed forward with TP and SP under the type checker, forward and backward.

## Design

- Typing:
  - A sharded contraction gives Partial, and a Partial operand passes through when the other operand is Replicate, as for any matmul.
  - On a row-parallel projection, `lora_a` (sharded on its input dim) gives Partial, `lora_b` (Replicate) keeps it, and `RowParallelLinear` reduces it together with the base output.
  - The bias add is jointly linear, so a Partial output only takes a Partial bias.
  - The stacked dim of a `num_linears > 1` weight is typed as never sharded.
- The computation is unchanged; only the type rule differs.

## Test plan

```

pytest tests/unit_tests/cpu/models/common/test_lora.py                                     # 30 passed
```

`llama3_debugmodel` with TP2, SP, `LoRATransform` and `debug.spmd_typechecking` raises `SpmdTypeError` on main and runs here. `pyrefly check` reports the same errors as main.

### Review: [LoRA] Fix SPMD type checking under tensor parallelism

- [x] Review test

**Verdict: LGTM.** The fix is in the right place and doesn't change any computation. I found no blocking issues, only a few small points below.

#### Why the fix is right
On a row-parallel projection, `lora.py:114-118` feeds `lora_a._linear(...)` straight into `lora_b._linear(...)`. `inplace_wgrad_accum` defaults to `True` (`linear.py:56`), so both calls take `_LinearFunction`. As a local-only function, it couldn't accept the Partial input `lora_b` receives from `lora_a`. A matmul is linear in each operand on its own, and the bias add is linear in both together, so `linear_in=(0, 1)` and `linear_in=((0, 1),)` are the correct rules:
- row-parallel base: `S(-1) x S(1) -> P`
- `lora_a` (weight `S(1)`) gives `P`; `lora_b` (weight `R`) keeps it; `P + P -> P`; then `RowParallelLinear` reduces it
- with a bias, `P + P` is allowed but `P + R` is rejected, which matches the `I -> P` conversion in `RowParallelLinear.forward`

The test also exercises the stacked `"_nk"` path: `make_ffn_config` builds `w13` with `num_linears=2`, so `w13.lora_b` has a 3D weight.

#### Test
@anijain2305's suggestion is already in `c35491f`: the test runs with `enable_sp` both on and off, and calls `spmd.assert_type(x_local / output, residual_activation_placement(...))` at the boundary, so a wrong P/V/I type on the output now fails.

#### Points (all minor / non-blocking)

1. **The bias branch of `spmd_typecheck` is never typechecked by a test** (`linear.py:187-191`). The FFN in the new test has no bias. `test_linear.py:285` covers `RowParallelLinear` with a bias, but that runs under `spmd.no_typecheck()` (`linear.py:351`). Column-parallel with a bias (`R x S(1) -> S(-1)`, plus a `S(-1)` bias) never goes through the new rule. A small case in `test_linear.py` would cover it: `ColumnParallelLinear` with `bias=True`, `num_linears` of 1 and 2, under `typecheck(local=False)`. That would also check the `"_n"` stacked-bias spec.

2. **The `no_typecheck` in `RowParallelLinear` is now stricter than needed for the default path** (`linear.py:349-358`). The TODO there points at the `[V, V, P] -> P` combination for `F.linear`. `_LinearFunction`, the default path, now types this correctly. The suppression still has to stay for `F.linear`, LoRA and the quantized paths, so I'm not asking for a change. It may be worth adding a line to the TODO saying the in-place path already handles this case.

3. **Validated parallelism combinations.** The test plan covers TP2 ± SP. The `...k` / `...n` ellipsis now carries batch-dim shards (e.g. `dp_shard` / CP `S(0)` on the input) through the rule, where the local registration used to handle them. A quick `llama3_debugmodel` run with `dp_shard=2, tp=2` + `LoRATransform` + `debug.spmd_typechecking` would confirm that FSDP and TP together still type cleanly. Per `.claude/rules/distributed.md`, consider all parallelism combinations.

4. **Sibling linear functions** (follow-up, not for this PR). `_HiMidLoLinearFunction` (`hi_mid_lo_linear.py:75`), `_MXFP8LinearFunction` (`mxfp8/linear.py:369`) and `_NVFP4LinearFunction` (`nvfp4/linear.py:327`) still use `register_local_autograd_function`. LoRA adapters are always plain `Linear`, so this PR's case doesn't reach them. A Partial input to any of them would still fail the same way, and the same einsum rule would likely carry over. The existing TODO at `mxfp8/linear.py:366` already tracks removing the local registration across the tree.

5. **PR description nit:** it says `torchtitan/models/common/linear.py`, but the changed file is `torchtitan/models/common/linear/linear.py`.
