# [module] Reject dtype changes to pinned buffers

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5153) · state: open · merged: False

## Original PR description

Whole-model casts can discard complex RoPE components or reduce cache and MoE accumulator precision. Reject incompatible buffer replacements instead of silently overriding the requested cast.

Buffer owners opt in through `_dtype_pinned_buffers: ClassVar[frozenset[str]]`. The sets contain buffer names only. `Module._apply` checks each conversion result against the materialized buffer's current dtype before PyTorch installs it. The conversion runs once. Undeclared buffers retain standard PyTorch behavior, and absent optional buffers are skipped.

Meta placeholders can change dtype. The numerical scripts and affected graph-trainer tests set precision before `to_empty()` and `init_states()`. Initialization rebuilds buffers in their intended dtypes. Kimi also sets its separate vision precision before materialization and checkpoint loading.

The guard does not restore tensors, duplicate dtype declarations, or validate initialization. SPMD annotation preservation remains separate. Device moves and dtype-preserving conversions remain supported.

The guard protects the current dtype, including after checkpoint assignment. It does not repair an already incorrect dtype. Failed conversions can leave earlier parameters or children changed. Functions that mutate inputs in place are outside the guard's contract.

Validation:

- Isolated CPU guard tests: 10 passed, 15 subtests passed, one CUDA test skipped.
- Coverage includes complex values, aliases, optional buffers, inherited pins, meta construction, checkpoint assignment, and SPMD annotations.
- Added a real RoPE rejection test. Retained three script tests with explicit parameter and buffer precision assertions.
- All non-type-check pre-commit hooks pass. Diff checks pass.
- Pyrefly reports the same 15 dependency/API errors as the preceding baseline in the local environment.
- Model-dependent tests remain blocked by missing macOS dependencies. CUDA tests and full checkpoint-backed numerical comparisons were not run.

### Core change: `torchtitan/protocols/module.py:141-153`

I checked these properties and they hold:
- **Children are handled.** `super()._apply(fn, recurse=True)` processes children first, and each torchtitan `Module` child restores its own `_buffers`. Buffers on a plain `nn.Module` still get cast, and the zoo test is designed to catch those.
- **Same-device restores alias the original.** `old.to(buf.device)` returns `old` itself when the device is unchanged, so SPMD annotations survive without a copy. When the device changes, `_preserve_buffer_spmd_types` re-applies the annotations to the new tensor. Buffers from `spmd_distribute_tensor` are plain local tensors, not DTensors, so `.to(device)` is safe.
- **The dtype gate is required.** It is what makes `to_empty()` and device-only moves work, and the inline comment explains this well.
- **Integer and `None` buffers are untouched.** That covers `_sr_seed` (int64), `_rht_sign_vector` (int8), `tid2eid` and the histograms. `nn.Module._apply` never casts them, and the `buf is not None` check handles empty slots.
- **Activations keep their dtype.** `ComplexRoPE` and `CosSinRoPE` both compute with `query.float()` and cast back with `type_as`. The bf16 scores + fp32 `expert_bias_E` add at `moe.py:212/368` promotes to fp32, which is what FSDP2 MP training already does and matches HF's fp32 `e_score_correction_bias`. The `.double()` tests (`test_deepseek_v4_compressor.py`, `test_deepseek_v4_dsa.py`) are unaffected because RoPE already downcasts fp64 queries to fp32.

Comments:

1. **(Semantics) This keeps the dtype the buffer had before the cast, which is not always its canonical dtype.** After `load_state_dict(..., assign=True)` from a checkpoint that stores `e_score_correction_bias` / `expert_bias_E` in bf16, the buffer becomes bf16. A later `model.float()` / `.to(torch.float32)` now leaves it in bf16, where before it was upcast. This is an edge case, but the docstring should say "keeps the buffer's current dtype" so nobody reads it as "restores the canonical dtype". The real canonical-dtype guarantee comes from `init_states`.

2. **(Semantics) The change can silently override an explicit request.** `model._apply(lambda t: t.to(torch.bfloat16))` in `test_graph_pp_passes.py:180` asks for every tensor, buffers included, in bf16, and the buffers now quietly stay fp32. CLAUDE.md asks for a warning "when a code path silently skips user configuration". A warning on every `model.to(bf16)` would be noisy, so I'd treat this as an intended contract rather than skipped config. It should still be stated in the `Module` class docstring, not only in `_apply`, because downstream subclasses inherit it. Agreed that an opt-out can wait until someone needs one.

3. **(Minor perf) `.to(device, dtype)` copies each buffer twice.** For a cross-device cast like `model.to("cuda", torch.bfloat16)`, `nn.Module._apply` first sends a cast copy to the target device, the override throws it away, and then copies `old` across again. `non_blocking` and `memory_format` from the original call are also dropped on the restore path. The buffers are small (RoPE cache up to `max_seq_len x dim`, per-expert vectors), so this is acceptable. A short comment would help.

4. **(Nit) Docstring wording.** "keep each own buffer's dtype" reads awkwardly. Suggested: *"...and to keep this module's own buffers in their current dtype across casts; parameters are still cast."*

| graph_trainer tests, `add_moe_model` skill script | various | Test-only |

Casting before `init_states` is a complete fix wherever it applies. Every `_init_self_buffers` rebuilds its buffer in a hard-coded dtype: `torch.polar` gives complex64 in `rope.py:236`, `.float()` is used in `rope.py:326`, and `dtype=torch.float32` is set for `tokens_per_expert_E` and `expert_bias_E` in `moe.py`. They don't follow the parameter dtype.

So on `main` this is a footgun in debug and numerics scripts, not a live production bug. The cost of the override is real, though:
- It contradicts the documented `nn.Module.to` behavior ("casts floating point parameters **and buffers**"). Every downstream `Module` subclass inherits this silently.
- It overrides an explicit `fn`. `model._apply(lambda t: t.to(bf16))` no longer does what it says.
- It locks in whatever dtype the buffer *currently* has. After `load_state_dict(assign=True)` from a bf16 checkpoint, `model.float()` no longer upcasts `expert_bias_E`.

**A lighter fix:**
1. In `numerical_tests_qwen3_5.py`, move `model.half()` before `init_states`. This is the only real instance, and it matches the Kimi scripts.
2. Optionally, make `numerical_tests_kimi_k3.py:224` re-run `init_states` after the cast, or keep the cast-then-init order.
3. If you want a guardrail, a CPU test can assert the documented pattern: `to_empty` → `.to(bf16)` → `init_states` leaves every buffer in its canonical dtype. That would reuse most of `test_model_buffer_dtypes.py` without changing `nn.Module` semantics.

One addition to the comment: the PR's measurements (24.6 vs 2.3e-3 score spread) are correct for the scenario they test. But no `main` path reaches that scenario except the Qwen3.5 script, so the motivation in the description overstates the impact.

### Comment 2: "Merge this into `_preserve_buffer_spmd_types`, renamed to `_preserve_buffer_types`?"

The readability goal makes sense, but **merging as written would introduce a bug.** `_preserve_buffer_spmd_types` is used in two places:

1. `_apply` (`module.py:145`)
2. `init_states`, around `_init_self_buffers` (`module.py:137-138`)

The dtype logic restores the *old tensor*. It does `self._buffers[name] = old.to(buf.device)`; it does not just cast the dtype back. Inside `init_states`, that means: whenever `_init_self_buffers` rebuilds a buffer in a different dtype from the stale one, the context manager would **throw away the freshly computed buffer and put the stale one back**. Today's workaround order (`to_empty` → `.to(bf16)` → `init_states`) triggers exactly this case, because the stale cache is bf16 and the fresh one is complex64/fp32. And `init_states` is the one place that is *supposed* to set the canonical dtype.

There are two smaller mismatches as well:
- The SPMD context manager walks `self.named_buffers()` (recursive). The dtype logic only touches `self._buffers` (own buffers) and relies on each child `Module` doing its own. A merged version has to pick one scope. Recursive would also catch buffers on plain `nn.Module` children, which changes the behavior again.
- The restore has to run **before** the SPMD re-annotation in `finally`, because that step checks `not spmd.has_local_type(buf)` on the final tensor. The current nesting gets this right; a merged context manager has to keep that order.

If the dtype override stays (see comment 1), I'd suggest a separate `_preserve_buffer_dtypes()` context manager used **only** in `_apply`, nested inside the SPMD one:

```python
def _apply(self, fn, recurse=True):
    with self._preserve_buffer_spmd_types(), self._preserve_buffer_dtypes():
        return super()._apply(fn, recurse=recurse)
```

This keeps `_apply` as short as you were after, and leaves `init_states` free to set dtypes. If they must be merged, add a flag like `_preserve_buffer_types(*, keep_dtype: bool)` that is off in `init_states`. I find that harder to read than two context managers.
