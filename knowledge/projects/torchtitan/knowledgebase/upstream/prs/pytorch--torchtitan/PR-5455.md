# [rl] Trainer MFU over real documents: no padding, attention at each document's length

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5455) · state: open · merged: False

## Original PR description

**TLDR:** RL `trainer/mfu_percent` counted padding as work, and counted every token as attending to `max_context_length` tokens. It now counts only real tokens, each attending to its own document's length. On a 0.6B smoke run, logged MFU drops 1.4-2.1x on the same batches. For a 4B run at a 131k context, we estimate 67% -> ~37%.

**Problem**
1. The RL batcher packs documents into microbatches padded to `num_tokens_per_microbatch_per_dp_rank`.
2. The trainer counts that padded total as trained tokens. Padding was 5-22% in our long-context runs.
3. FLOPs per token come from `get_nparams_and_flops(model, max_context_length)`, so every token attends to `max_context_length` tokens.
4. Packed documents are much shorter: 39-72k of 131k tokens on average in those runs.
5. So `trainer/mfu_percent` and `trainer/tflops` read ~1.8x too high there (estimate, under torchtitan's non-causal convention).

**Solution**
1. Under the non-causal convention, a token that attends to L tokens costs f(L) = intercept + slope * L FLOPs, so a document of length L costs L * f(L).
2. `TrainingEngine` also stores `num_flops_per_token_at_one_token` = f(1). With f(max_context_length), it gives the intercept and the slope.
3. The batcher records `num_real_tokens` = sum(L) and `sum_squared_document_lengths` = sum(L**2) on each `TrainingMicrobatch` at pack time. They are plain ints, so they travel by value in RDMA microbatches too.
4. The trainer sums both over its column and averages them over DP ranks. MFU = (intercept * sum(L) + slope * sum(L**2)) / time / peak.
5. `trainer/tokens_per_second` now counts real tokens, not padded ones.
6. Unchanged: the non-causal convention, the pretraining trainer's metrics, the peak-FLOPS table.

**Results**
```text
Qwen3-0.6B alphabet sort, 2 H100s (trainer TP=1, generator TP=1), max_context_length 2048, 3 steps.
Two separate runs, so the batches differ. The last column applies main's formula to this PR's batches.

step   padding (main / PR)   MFU main run   MFU this PR   main's formula on this PR's batches
1      0.36 / 0.36           1.76%          0.83%         1.78%    (step 1 includes compilation)
2      0.28 / 0.29           5.32%          2.52%         4.82%
3      0.04 / 0.04           6.32%          4.39%         6.03%
```
The documents are short here: their length-weighted mean is 80-265 tokens, against a 2048 context.

You may ask:
- Why average over DP ranks? The controller logs only DP rank 0's `optim_step` metrics. Rank 0 also gets the all-padding bins first, because they have the highest padding-aware workload. With per-rank counts, the logged MFU would be 0 whenever rank 0 got only padding.
- Why not reuse `global_routing_token_counts`? It gives sum(L), but not sum(L**2).
- Why plain ints on the microbatch, not tensors? With `rdma_min_tensor_bytes` set, a tensor that size or larger stays in the batcher until the trainer reads it. Ints always travel in the message, so the trainer reads them without an RDMA read.

NOTE: f(L) is not linear in L for sliding-window layers or DeepSeek-V4's compressed attention, so their MFU stays approximate (TODO in the code). A per-batch FLOPs estimator is in progress in another PR; this moves onto it once it lands.
NOTE: `TrainingEngine` now calls `get_nparams_and_flops` twice, so every trainer, pretraining included, logs "Total parameter count" twice at startup.
NOTE: the 4B estimate is arithmetic from logged run metrics, not a run of this PR.

**Test plan**
- `tests/rl/unit_tests/cpu/test_batcher.py::test_microbatch_counts_real_tokens_and_squared_document_lengths`: lengths 3 and 2, each padded to 4, give 5 and 13; an all-padding bin gives 0 and 0.
- `tests/rl/unit_tests/cpu/test_trainer.py::test_optim_step_counts_each_real_document_at_its_own_length`: MFU equals 3 * f(3) + 2 * f(2) for the Qwen3.5 debug model (full attention plus delta rule), to rel 1e-12.
- `test_forward_backward_accumulates_microbatch_metrics` (both paths): the counts come from `.fields` on the RDMA path, and are averaged over 2 DP ranks when rank 0 got only padding.
- Each new or changed assertion fails on main. These broken variants each fail at least one test: main's per-token FLOPs, no DP mean, the slope off by one, the RDMA path reading attributes, intercept = f(1), and counting padded sample lengths.
- `pytest tests/rl/unit_tests/cpu`: 481 passed, 9 skipped. `pytest tests/unit_tests/cpu`: same failures as main (3 SPMD redistribute tests, plus a torchao import in a venv without torchao).
- pyrefly 0.45.1: 31 errors on main and on this branch, none in `training_engine.py`.
- GPU: the 3-step runs above, with `python -m torchtitan.rl.train` and a local recipe that sets TP=1 on `rl_grpo_qwen3_0_6b_varlen`.
