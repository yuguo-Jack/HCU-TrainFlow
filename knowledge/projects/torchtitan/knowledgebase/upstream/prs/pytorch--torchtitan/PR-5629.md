# [graph_trainer] Offload after the last forward write into the storage

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5629) · state: open · merged: False

## Original PR description

Fixes #5628

`apply_cpu_offload_pass` inserted `ao.offload` right after the offloaded node, but `ao.offload` copies the tensor when it runs. If the forward pass writes into that storage afterwards, e.g. `h.view(-1)[:k].add_(1)`, the CPU copy is stale and backward reloads the pre-write value.

This moves the offload after the last forward write into the node's storage, using `mutation_utils.mutation_deps` to find writes (it follows views back to the base). With no forward writes, the offload stays right after the node, so nothing changes for the usual case. The forward wait was already placed after the last forward user of the storage, including writes, so it still comes after the offload.

Test plan:
- repro from the issue (3-layer model, `sac_and_offload`, view write into an `mm` output): max grad error ~5e3 before, 0 after
- combined with #5622 (written tensor that would otherwise be recomputed, then offloaded): correct only with both fixes
- 0 of 490 offload candidates move on the llama3 and qwen3 MoE debug models
- two new tests in `test_cpu_offload.py`, both fail on main: one checks the offload lands after the write, the other compares gradients to eager under `sac_and_offload`
- `test_cpu_offload`, `test_passes`, `test_remat_metadata`, `test_sac_peak_memory`, `test_numerics`, `test_paged_stash`: 267 passed, 6 skipped (existing skips)
