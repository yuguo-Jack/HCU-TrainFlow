## Agent details

Written with Claude Code: the analysis, measurements and test plan below.

**TLDR:** At inference under CUDA graphs, `MoE.forward` runs the shared experts on a side stream, in parallel with the routed experts. The output stays bitwise identical: 51 of 51 checks over 8 MoE models. Qwen3.5-35B-A3B MoE block, Dist-MoE, EP 2: 2.7-7.4% faster at decode, 1.2-2.5% at prefill.

```text
before:  router -> routed experts (dispatch, GEMMs, combine) -> shared experts -> add
after:   router -> routed experts (dispatch, GEMMs, combine) ---------------> add
                \-> side stream: shared experts -------------------------/
```

```python
# MoE.forward: fork right after the router, join before the add
side_stream = shared_TD = None
if self.shared_experts is not None:
    side_stream = _shared_experts_side_stream(x_TD)  # None unless captured, no grad, no SP
    if side_stream is not None:
        side_stream.wait_stream(torch.accelerator.current_stream(x_TD.device))
        with side_stream:
            shared_TD = self.shared_experts(x_TD)
out_TD = self.routed_experts(...)
if side_stream is not None:
    torch.accelerator.current_stream(x_TD.device).wait_stream(side_stream)
```

**Problem**
1. `MoE.forward` runs the router, then the routed experts, then the shared experts, all on one stream.
2. At decode, Dist-MoE's routed path starts with a chain of small kernels (publish, peer barrier, routing, plan). Most SMs sit idle during it.
3. The shared experts read only `x_TD`, yet they wait for the whole routed path.
4. **Cost.** 7-10 µs per Qwen3.5 MoE block at decode sit on the critical path (the saving below). Over 40 layers that is 0.3-0.4 ms per decode step (arithmetic, not measured end to end).

**Solution**
1. `_shared_experts_side_stream(x_TD)` returns one side stream per device. It returns `None` (run inline) off the accelerator, with grad on, under torch.compile, outside CUDA graph capture, or with sequence parallelism (SP).
2. With a side stream, `MoE.forward` forks right after the router and joins before the shared add.
3. **No collective on the side stream.** Dispatch, combine and the TP all-reduce launch from the main stream. With SP the shared experts would all-gather their input, so they stay inline.
4. **Unchanged:** training, eager forwards, the MoEs that override `forward` (Muse Spark, Kimi K3), and the math.

**Numerics: bitwise identical**

Why: the same kernels run on the same inputs. Only the stream changes, and the main stream waits for the side stream before the add.

- **Stack matrix** (this PR vs PR 1, at this head; script not in this PR): 51 of 51 checks bitwise.
  - The side stream runs in 8 cells: Qwen3.5, DeepSeek-V3, Kimi K2.5 and DeepSeek-V4, in a captured CUDA graph, with DeepEP at EP 2 and with local dispatch at EP 1.

You may ask:
- **Why fork after the router, not before?** Forking before lets the shared GEMMs compete with the router's small kernels. That was slower in every row of an earlier EP 4 run (T = 64: 149.2 vs 145.6 µs).
- **Why no token cap?** vLLM caps the same overlap at 256 tokens per rank (`VLLM_SHARED_EXPERTS_STREAM_TOKEN_THRESHOLD`). Qwen3.5 still gains at T = 16384.
- **Why only captured no-grad forwards?** With grad on, the shared backward would run on the side stream too. In training, PR 5554's overlap measured +1.7% at 4k and -0.8% at 16k (one layer, EP 1). In eager, the stream calls cost more host time than they hide (PR 5554 at decode: +2.6 to +7.1%).
- **How does this relate to PR 5554?** PR 5554 overlaps the shared experts in training and inference. At inference it is bitwise too, but slower than this PR at every T on the bench above (T = 1: -5.3% vs main, this PR -7.4%). This PR goes first for inference; PR 5554 rebases on top for training.

NOTE:
- The gate checks the execution mode, not the backend. Any dispatcher a CUDA graph can capture takes the side stream: Dist-MoE (timed), local dispatch at EP 1 and DeepEP with `cuda_graph_compatible=True` (matrix, bitwise), HybridEP non-blocking (not run). The all-to-all dispatcher at EP > 1 copies its splits to the host, so it can't be captured and stays inline.
- The side stream comes from torch's stream pool, so a stream created elsewhere later can be the same one. That costs overlap, never correctness.
- Not run: a full vLLM engine, captured trainer validation, HybridEP capture.

**Stream and allocator safety (checked, no issue found).** The side stream only reads `x_TD` and the weights. The next layer's fork runs `side.wait_stream(main)` after that add, so reusing the block is ordered. `torch.cuda.graph` creates its capture stream from the pool before capture starts, so creating the side stream lazily inside capture doesn't initialize the pool mid-capture. - The main stream joins the side stream before the add, which is the last use of `shared_TD`.
- The next layer's `side.wait_stream(main)` orders reuse of that block.
- `torch.Stream(device=...)` on CUDA takes a stream from the same pool that `torch.cuda.Stream` uses, so creating it lazily during capture still doesn't initialize the pool mid-capture.

**Device check.** `device_type` comes from `torchtitan.tools.utils` and falls back to `"cuda"` when no accelerator is found. A CPU tensor therefore always takes the early return, whatever the host has.

</details>
