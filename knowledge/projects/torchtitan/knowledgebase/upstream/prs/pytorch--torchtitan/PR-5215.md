# [rl] controller: drop each finished rollout group (full GCs froze the controller)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5215) · state: closed · merged: True

## Original PR description

**TLDR:** one `del` in `Controller._rollout_loop`. Each rollout-loop task held its last finished group for about an hour. With 1,152 such tasks, each full Python GC most likely froze the controller for 7-30 s, and a ~30 s freeze killed a GB300 run (Monarch drops links at its 30 s delivery timeout). With the fix, the same recipe reached step 10 with 1-4 s GCs, where the run without it froze for 25-27 s.

**Problem**
1. The controller runs `max_active_rollout_groups` rollout-loop tasks. Each one keeps its last finished group in its locals (`group`, and `work.rollout_group`) while it waits for its next group, typically ~1.2 h in a 35B chess run (rollout p50 74 min).
2. A finished group holds every turn's full prompt as Python lists of ints. At the fatal freeze, the held groups came to an estimated ~3.4B list entries.
3. CPython's full GC walks every one of them while holding the GIL, so all Python code in the controller process stops: the event loop and its worker threads.
4. **In the GB300 run:**
   - Every engine stopped receiving requests at the same moments, every ~157 finished groups.
   - The fleet-wide request gaps grew smoothly: 6.6, 7.6, 9.3, 11.6, 13.6, 17.1, 18.2, 22.5, 24.9, 27.1, then ~30 s. These are upper bounds (up to ~1 s high). Monarch's stall warnings give lower bounds, e.g. 11.1 s for the 13.6 s gap.
   - At ~30 s the router's links timed out, and the run died in step 11.
   - The pause per held list entry in the run (5.3-8.8 ns) matches the CPU cost of a full GC (5-8 ns).

**Solution**
- `del group, work` after `finalize_work`. Both go, because `work.rollout_group` is the same group.
- Nothing else changes: the group is already handed to the buffer.
- A TODO next to it: the per-token fields of `RolloutTurn` and `TrainingSample` are Python lists, and a full GC walks every entry; a torch tensor may be better.

**Results**
```
CPU simulation of the real rollout and batcher loops, 1,152 tasks, tiny token lists (real object counts):
  live groups:                       1,152 -> 1
  longest event-loop stall:          6.9 s -> 1.2 s
  extrapolated to real size:         ~20-30 s -> ~1-2 s
full GC cost: ~5.2 ns per held list entry

GB300, 35B chess, controller freezes without -> with the fix
(without: fleet-wide request gaps; with: a 1 s slow-GC warning added for the run):
  through step 5:   6.6-9.3 s -> 1.2-2.1 s
  step 10:          24.9-27.1 s -> 2.8-3.6 s
```
- The run without the fix died ~25 min later, in step 11. The run with the fix was stopped ~7 min after step 10 to free its hosts.
- The run with the fix also raised Monarch's timeouts to 300 s and changed generator KV settings (session-KV holding, vLLM watermark). Neither runs in the controller, and step times stayed close (step 10: 1,748 s vs 1,687 s).
- Simulation times come from an x86 host, not the run's ARM (Grace) controller, so read them as an order of magnitude.

NOTE: GC pauses still grow with sequence length, likely from the per-token Python lists in turns and training samples. In the run with the fix, they rose from 1.2-2.1 s to 2.8-3.8 s as mean rollout length went from ~10k to ~22k tokens (steps 1-10). The TODO covers this.

**Test plan**
`pytest tests/rl/unit_tests/cpu` (regression only; no test calls `_rollout_loop`): 511 passed, 8 skipped, same as main. A separate check ran the real `_rollout_loop` and `_batcher_loop` with 16 tasks: main keeps 16 finished groups alive, this PR keeps 1 (the batcher's).
