# [rl] Put GPU weights directly into TorchStore, drop trainer staging buffers

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5659) · state: closed · merged: True

## Original PR description

Fixes https://github.com/pytorch/torchtitan/issues/5654

Root issue: the RL trainer copies its weights into pinned CPU staging buffers, then `ts.put_state_dict(direct_rdma=False)` copies them again into the colocated StorageVolumes. So every trainer host holds two CPU copies of its shard.

Fix: drop the staging buffers. `push_model_state_dict` now puts the live GPU state dict with `transfer_dtype` from a worker thread (`asyncio.to_thread`).
- The worker makes the push stream current and synchronizes it. The current stream is thread-local, so this has to happen inside the worker. Transports that read GPU memory outside stream order (RDMA) then see weights from after the last optimizer step.
- With colocated SharedMemory, TorchStore casts during the D2H copy into StorageVolume memory, so the volume holds the only CPU copy.
- Persistent buffers keep their registered dtype through `preserve_dtype_keys`.
- Push/pull ordering is unchanged: push N is awaited before optimizer step N+1.

Depends on https://github.com/meta-pytorch/torchstore/pull/266, which adds transport-side casting and `preserve_dtype_keys`. torchtitan installs torchstore@main unpinned, so that PR must land first.

Lines: implementation +60/-91, tests +29/-115.

Test plan:
- `pytest tests/rl/unit_tests/cpu --ignore=tests/rl/unit_tests/cpu/test_dapo_math.py`: 482 passed. `test_model_defaults[dapo_math]` and `test_dapo_math.py` collection fail with an environment ImportError (`CallbackArgs`); this is unrelated to the change.
- New `test_push_model_state_dict_puts_on_push_stream_in_worker` checks that the push:
  - runs in a worker thread on the push stream and synchronizes it first;
  - puts live tensors (`data_ptr`s match);
  - passes `transfer_dtype`, and passes `preserve_dtype_keys` with the canonical names of nested buffers, excluding non-persistent buffers.
- Removed the tests for the deleted staging-buffer helpers.

Results (GB200, one client + one local StorageVolume, SharedMemory, 290 fp32 GPU tensors pushed as bf16, median of 5 pushes; old = pinned bf16 staging copy then put):

| fp32 shard | push time old → new | client RSS old → new | extra GPU peak |
|---|---|---|---|
| 4 GiB | 246 → 35 ms | 6.46 → 4.20 GiB | 7 MiB both |
| 16 GiB | 304 → 66 ms | 22.54 → 13.46 GiB | 28 MiB both |

The SHM segments are pinned with `cudaHostRegister`, so the D2H stays a pinned copy. The cast uses one tensor's worth of GPU scratch at a time. Non-SHM transports still materialize a bf16 GPU copy per put batch. Pushed weights match `w.bfloat16()` when read back.

**Verdict: Approve -- please address the items below before merging.** The fix removes a redundant full CPU copy of the trainer shard at the layer that owns it. torchstore#266 merged today, so the new `put_state_dict` kwargs exist.

**What this PR does.** The RL trainer no longer keeps its own pinned CPU mirror of the weights. `push_model_state_dict` hands the live (GPU, possibly DTensor) state dict to `ts.put_state_dict` with `transfer_dtype`, and TorchStore does the cast. Persistent buffers keep their dtype through `preserve_dtype_keys`. The worker thread makes the side stream current and synchronizes it before the put. That way the put sees post-optimizer weights, and casts don't queue behind forward/backward N+1 on the default stream.

**Example.** fp32 training with a bf16 generator, FSDP, colocated volume:
```
before: GPU fp32 --copy_(cast, non_blocking)--> pinned CPU bf16 (trainer) --memcpy--> shm bf16 (volume)
        host holds 2 bf16 copies of the shard
after:  GPU fp32 --TorchStore copy_(cast)--> shm bf16 (volume)
        host holds 1 copy; a `norm.scale` buffer stays fp32 via preserve_dtype_keys
```

- claude[bot] · comment · 2026-10-29T23:57:07Z · [source](https://github.com/pytorch/torchtitan/pull/5659#discussion_r4419123840)

This trades one CPU copy for a different D2H path, and the description has no numbers for it. Before, D2H went GPU -> pinned buffer (fast and async), followed by a CPU memcpy into the volume. Now D2H goes straight into the StorageVolume shm segment. Unless TorchStore registers or pins that segment (*unverified*), this is a pageable D2H copy, which can be much slower. If the push then outlasts forward/backward N+1, `timing/step/blocking_trainer_push_model_state_dict` grows on every step.

Second, for non-SharedMemory transports this docstring says TorchStore makes "a GPU cast copy of each batch". That copy is allocated while forward/backward N+1 is running. Before, the transient was one tensor (`copy_(non_blocking=True)` casts per tensor on the GPU). If a batch is a whole volume's worth of tensors, peak GPU memory during the overlap goes up.

Please add before/after numbers to the description for `timing/weight_sync/trainer_push_model_state_dict`, `blocking_trainer_push_model_state_dict`, trainer host RSS (the claimed win), and `trainer/memory/max_reserved_gib`, on one representative FSDP run.
