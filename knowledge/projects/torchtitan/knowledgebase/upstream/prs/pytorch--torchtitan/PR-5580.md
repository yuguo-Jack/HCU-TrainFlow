# [flux] Shift the sampling schedule by the packed sequence length

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5580) · state: closed · merged: True

## Original PR description

`denoise` computes the timestep shift from `latent_height * latent_width`, the unpacked latent area. The reference Flux sampler and diffusers both use the packed 2x2-patch sequence length:
- [BFL reference](https://github.com/black-forest-labs/flux/blob/802fb4713906133fcbd0d8dc5351620ca4773036/src/flux/cli.py#L254-L255): `get_schedule(opts.num_steps, inp["img"].shape[1], ...)`.
- [diffusers](https://github.com/huggingface/diffusers/blob/1ddaf8f4e7c33afaa7c6c2c3be9e56f2c2a634c8/src/diffusers/pipelines/flux/pipeline_flux.py#L826): `image_seq_len = latents.shape[1]`.

The value we pass is 4x larger, so an N px image is sampled with the schedule meant for 2N px. This affects FluxValidator image generation and `inference/infer.py`. I moved the schedule after `pack_latents` and pass `latents.shape[1]`. I found this by reading and testing the code.

Reproducer: run `denoise` with a stub model that records the timesteps it is given.

```python
import torch
from torchtitan.models.flux.inference import sampling

seen = []
def model(*, img, timesteps, **kwargs):
    seen.append(round(float(timesteps[0]), 3))
    return torch.zeros_like(img)

sampling.denoise(device=torch.device("cpu"), dtype=torch.float32, model=model,
                 img_width=1024, img_height=1024, denoising_steps=50,
                 clip_encodings=torch.zeros(1, 768), t5_encodings=torch.zeros(1, 1, 4096))
print(seen[9], seen[24], seen[39])
```

Timestep at steps 10 / 25 / 40, 50 steps:

| image | before | after | BFL reference and diffusers |
|---|---|---|---|
| 256px | 0.895 / 0.670 / 0.346 | 0.883 / 0.641 / 0.317 | 0.883 / 0.641 / 0.317 |
| 512px | 0.935 / 0.774 / 0.471 | 0.895 / 0.670 / 0.346 | 0.895 / 0.670 / 0.346 |
| 1024px | 0.991 / 0.965 / 0.877 | 0.935 / 0.774 / 0.471 | 0.935 / 0.774 / 0.471 |

The new CPU test checks the timesteps `denoise` feeds the model at 256px and 512px against hard-coded values of the reference schedule, so it also guards the schedule formula and its defaults. It fails on main and passes with the fix. Training, the validation loss and model code are unchanged, but FluxValidator images from existing runs will look different after this change, because they are now sampled with the reference schedule.

**Verdict: LGTM.** The fix is correct and small, and it doesn't touch training.

#### Correctness

- `get_lin_function` defaults to `x1=256, x2=4096`. Those anchors only make sense in packed-token units: a 1024px image gives a 128x128 latent, which packs (2x2 patches) to 64x64 = 4096 tokens, the point where `max_shift` applies. This matches BFL's `get_schedule(..., inp["img"].shape[1])` and diffusers' `calculate_shift(image_seq_len, base_seq_len=256, max_seq_len=4096)`. Before this PR, `latent_height * latent_width` was 4x the packed length, so every resolution got the schedule meant for 2x its side length. The before/after table in the description shows exactly that.
- Moving `get_schedule` below `pack_latents` is the right fix. CFG doubles only the batch dimension, so `latents.shape[1]` is the per-image packed length either way.
- Callsites: `denoise` (`torchtitan/models/flux/inference/sampling.py:205`) is the only caller of `get_schedule`. It's used by `generate_image`, which `FluxValidator` and `inference/infer.py` both call.
- Training is unaffected. `FluxModel` draws training timesteps from plain `torch.rand` (`torchtitan/models/flux/model.py:348`), and validation loss uses fixed stratified timesteps. Neither uses the shifted schedule, so the numerics and loss-equivalence requirements in CLAUDE.md don't apply here. Only sampled images change.

#### Test

- The test fails on main: 256px gives 1024 unpacked positions vs. 256 packed tokens, and `assert_close` catches the gap. It passes with the fix. The parametrized values (256 -> 256, 512 -> 1024) check out with `IMAGE_LATENT_SIZE_RATIO=8` and 2x2 patches.
- Nit (optional): the expected values come from `get_schedule` itself, so the test pins the *argument* but not the formula. You could add one hard-coded anchor, e.g. assert that at 256 packed tokens `mu == base_shift` (0.5), or check one of the reference timesteps from your table (0.883 / 0.641 / 0.317 at 256px, 50 steps). That would guard against someone changing the `x1`/`x2` defaults later. Not blocking.

#### Minor / FYI

- Users should know that FluxValidator images from existing runs will look different after this lands, because they'll now be sampled with the less-shifted, correct schedule. It's worth a line in the PR description or release notes so nobody reads it as a regression.
- `latent_channels` at `sampling.py:180` is unpacked but never used. That was already the case before this PR, so leave it unless you're already touching the line.

I couldn't run the test suite here because the sandbox blocked `pytest`. The review above is based on reading the code and working through the shapes by hand.
