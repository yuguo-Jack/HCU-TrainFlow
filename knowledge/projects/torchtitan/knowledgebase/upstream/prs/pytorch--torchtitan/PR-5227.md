# [fix] wandb: stop dropping validation metrics logged at a training step (1/2)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5227) · state: open · merged: False

## Original PR description

**TLDR:** W&B drops every validation metric logged at a step that training already logged. With the default `log_freq=10` and validator `freq=10`, that is every core validation; in RL, it is the post-training pass and, with the next PR, every periodic pass. `WandBLogger` now accumulates each step's row and pushes it with an explicit `commit()`.

**Problem**
1. `WandBLogger.log` calls `wandb.log(metrics, step=N, commit=True)`, so each step shows up in W&B as soon as it is logged.
2. Once row N is committed, W&B drops every later log to step N.
3. Validation logs after training at the same step, so `validation_metrics/*` never lands.
4. RL's post-training validation logs at the last train step (`Controller.run`), so the same rule drops it.

**Solution**
1. `WandBLogger.log` accumulates into the step's row (W&B's default when `step` is passed).
2. A new `commit()` on the loggers pushes the open row. The trainer calls it after validation.
3. The RL controller calls it at the top of each step and after post-training validation, so that pass joins the last row.
4. Each step still shows up in W&B as soon as its last log lands.

**Results**

Committed rows read back from the offline `.wandb` file (W&B 0.28.1).

1-GPU llama3 debugmodel, `log_freq=5`, validator `freq=5`, measured on an earlier main (losses differ slightly: no fixed seed):
```
main:
{'_step': 1,  'loss_metrics/global_avg_loss': 8.08}
{'_step': 5,  'loss_metrics/global_avg_loss': 5.24}
{'_step': 10, 'loss_metrics/global_avg_loss': 4.11}

this PR:
{'_step': 1,  'loss_metrics/global_avg_loss': 8.08, 'validation_metrics/loss': 7.77}
{'_step': 5,  'loss_metrics/global_avg_loss': 5.22, 'validation_metrics/loss': 4.69}
{'_step': 10, 'loss_metrics/global_avg_loss': 3.99, 'validation_metrics/loss': 4.00}
```

The RL controller's log/commit order with overlapped validation (next PR), replayed through the real `WandBLogger`, 6 steps:
```
main:     6 rows, train/loss only
this PR:  step 1  train/loss, validation/pass_0
          step 3  train/loss, validation/pass_2
          step 6  train/loss, validation/pass_4, validation/final
```

You may ask: why not just drop `commit=True`? Then row N is pushed only when the next logged step arrives, so every row shows up late (up to `log_freq` steps, or one RL step).
You may ask: why not a custom x-axis, `define_metric("*", step_metric="step")`? `_step` would stop matching the training step, which breaks panels of older runs and `WANDB_RESUME_FROM`/`WANDB_FORK_FROM=<run>?_step=N`.

NOTE: `experiments/torchft/trainer.py` has its own loop and doesn't call `commit()`. Its rows are pushed when the next step logs: correct, one logged step late.

**Test plan**
```
pytest tests/unit_tests/cpu/observability/ torchtitan/experiments/torchft/tests/test_torchft_trainer.py tests/rl/unit_tests/cpu/test_metrics.py   # 229 passed (main: 228)
pytest tests/rl/unit_tests/cpu   # 479 passed, 9 skipped, same as main
```
New: `test_wandb_commit_keeps_validation_in_the_training_row`. The next PR's `test_overlapped_validation_runs_beside_training` checks the RL commit order. The RL replay script is not checked in.
