# [qk_clip] Scale MLA rows so FSDP can split a head across ranks

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5737) · state: closed · merged: True

## Original PR description

## Summary (human-written)

with uneven division of head i.e. FSDP rank count doesnt divide the head count into whole numbers, it led to pytorch runtime error; for example with 16 heads and training recipes like FSDP32/64; however, after this fix, the code can handle this uneven count/division without any extra comm; checked the training recipe on AWS Neuron device for moonlight 16B-A3B text tower model with FSDP 64.

On why this approach?
multiplying each row by its head's scale gives the same result with no reshape and no comm also, row-by-row multiplication works however FSDP splits the rows, even mid-head, and the results are bitwise identical wherever the old code worked

## Why

QK-Clip crashes in the first optimizer step when the FSDP shard count does not divide the number of attention heads. `_scale_mla_heads` views each `Shard(0)` MLA weight as `[num_heads, rows_per_head, in_features]`, and DTensor cannot view an unevenly sharded tensor. For example, the Kimi K2.7 recipe's Moonlight 16B-A3B text tower has 16 heads, so it cannot use QK-Clip at FSDP 32 or 64.

**Example.** `moonlight_16b_a3b` text tower, `data_parallel_shard_degree=64`:

```text
main:    step 1 forward and backward pass, then optim_step -> qk_clip -> _scale_mla_heads
         RuntimeError: Cannot unflatten unevenly sharded tensor: output dimension 0 (size 16)
         is not evenly divisible by mesh dimension 0 (size 64).
         Sharding propagation failed for aten.view.default(Spec(f32[3072, 2048](S(0))),
         [16, 192, 2048]) on DeviceMesh((dp_shard=64), ...)
this PR: trains
```

## What changed

`_scale_mla_heads` multiplies the weight by one scale per row. The row scales come from the same `scales_H.pow(exponent)` values as before, so the result is bitwise identical. The replicated `[rows, 1]` scales apply to the `Shard(0)` weight without communication, for even and uneven shards. The shape-suffix legend gets `R` (weight rows).

## Alternatives considered

- Fix the view in DTensor: DTensor rejects an uneven unflatten by design, because a local view cannot express a head that two ranks share.
- Redistribute the weight to an even layout before the view: a collective per weight per step.
- Restore the local head-range arithmetic that #4252 replaced: more code, and DTensor dispatch already handles uneven `Shard(0)`.
- Reject uneven head sharding at config time: it blocks valid FSDP sizes.

## Numerics

Bitwise identical where main runs. On CPU with gloo at 3 and 4 ranks, the new `_scale_mla_heads` equals the main implementation bitwise for every head count that the shard count divides. For uneven head counts it equals a dense reference exactly. Weight scaling adds zero collectives in all cases (`CommDebugMode`).

## Performance

The new code multiplies the `wkv_b` V rows by 1.0, once per optimizer step. QK-Clip takes 0.04 s per step on the Moonlight 16B-A3B text tower (27 layers) at FSDP 64.

## Testing

`test_weight_scaling_is_communication_free` now uses `num_heads = world_size + 1`, so `Shard(0)` splits a head across ranks, and it also checks the clipped values. It catches the regression: it fails on main with the sharding error above.

```bash
pytest tests/unit_tests/gpu/models/kimi_k2_7/test_qk_clip.py
```

Ran this file on CPU (gloo backend, `device_type="cpu"`): 5 passed with this PR. With main's `qk_clip.py`, the extended test fails and the other 4 pass. GPU runs on CI. `pyrefly check torchtitan/models/kimi_k2_7/qk_clip.py`: 0 errors. `pre-commit` hooks pass.

End to end, on AWS Neuron, the Moonlight 16B-A3B text tower trains with this PR at FSDP 64 with QK-Clip and the upstream DistMuon compute layouts: 27 layers, 10 steps, loss 12.41 -> 5.00.

**Verdict: Approve** -- this fixes a real crash on main at its source (a DTensor view that can't represent a head split across ranks) with a smaller, communication-free elementwise multiply, and the result is bitwise identical wherever main already ran.

**What this PR does.** `_scale_mla_heads` used to view each `Shard(0)` MLA weight as `[H, D, I]` and scale slices of it. DTensor rejects that view when `num_heads` isn't a multiple of the shard count. The PR instead builds one scale per row, a replicated `[R, 1]` tensor, and multiplies it into the weight in place. DTensor turns the replicated scales into the local shard by slicing, so this works for even and uneven `Shard(0)` with no collective. The existing comm-free test now uses `world_size + 1` heads and also checks the clipped values.

**Example.** Moonlight 16B-A3B text tower, 16 heads, `wq_b.weight` is `[16*192, 2048]` with `Shard(0)` on `dp_shard=64`:
```text
main:    weight.view(16, 192, 2048)  -> RuntimeError: Cannot unflatten unevenly sharded tensor
this PR: row_scales_R1 = [s_h**alpha]*128 + [s_h]*64 for each head h  -> shape [3072, 1], Replicate
         weight.mul_(row_scales_R1)  -> each rank scales its 48 local rows, 0 collectives
```
Numerics: the per-row values come from the same `scales_H.pow(exp)` calls as before, and the V rows get multiplied by `1.0`, which leaves them bitwise unchanged.

### Should consider

- `tests/unit_tests/gpu/models/kimi_k2_7/test_qk_clip.py:349` -- all heads share one logit, so the value check can't tell if a head got another head's scale. Give each head its own logit.
- `torchtitan/models/kimi_k2_7/qk_clip.py:56-57` (unchanged lines) -- the comment says `_StridedShard` is rejected because it "would pair heads with the wrong rows". That was true for the old view, but a broadcast multiply through DTensor doesn't depend on shard order. Either reword the comment to give the real reason, or confirm that the check is still needed. Under TP, the shape check above it would fail first anyway, because `scales_H` would only cover the local heads.

<details><summary>Details</summary>

- Parallelisms: FSDP gives `(Shard(0),)` and HSDP gives `(Replicate(), Shard(0))`. In both cases `_replicated_scales` creates an all-`Replicate` `[R, 1]` DTensor, and pointwise sharding propagation redistributes it Replicate -> Shard(0) by slicing locally, using the same uneven chunking as the weight. The in-place op keeps the weight's placement. PP and gradient accumulation are unaffected because they only change how many maxima get recorded. TP isn't supported before or after this PR.
- Cost: one full pass over each weight instead of one or two partial passes, plus an `[R, 1]` scale tensor. This runs once per optimizer step, and the description measures 0.04 s per step at FSDP 64.
- Alternatives: the description already compares the realistic options (redistributing before the view, local head-range arithmetic, banning uneven sharding at config time). The row multiply is the smallest of these.
- No overlapping open PRs found for `qk_clip`.

</details>

Now that the V rows get multiplied anyway, `remaining_scale_exponent` never needs to be `None`. The `wkv_b` caller (line 145) can pass `remaining_scale_exponent=0.0`: `x.pow(0.0)` is exactly `1.0` for any `x`, so the result stays bitwise identical. That lets you drop the `| None`, the `ones_like` branch, and the "remaining rows are unchanged when ... `None`" sentence in the docstring.

```suggestion
    row_scales_R1 = torch.cat(
        [
            scales_H.pow(nope_scale_exponent)[:, None].expand(-1, nope_rows_per_head),
            scales_H.pow(remaining_scale_exponent)[:, None].expand(
                -1, rows_per_head - nope_rows_per_head
            ),
        ],
        dim=1,
    ).view(-1, 1)
```

- claude[bot] · comment · 2026-11-02T17:55:26Z · [source](https://github.com/pytorch/torchtitan/pull/5737#discussion_r4445821534)

File: `tests/unit_tests/gpu/models/kimi_k2_7/test_qk_clip.py` · line None

Every head records the same max logit (400, line 335), so all heads get the same scale. The value check catches rows that are offset inside a head, because the NoPE, RoPE, and V rows have different scales. It can't catch a head getting another head's scale, which is the likely bug if this ever goes back to per-rank head-range arithmetic. A distinct logit per head, e.g. `100.0 * torch.arange(2, num_heads + 2)`, with the expected tensor built per head, would cover that and cost nothing extra.
