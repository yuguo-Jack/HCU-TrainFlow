# [qwen3.5] Raise offset_rmsnorm's recompile limit to 16

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5267) · state: closed · merged: True

## Original PR description

**TLDR:** On main, a Qwen3.5 generator with CUDA graphs fails to start: vLLM's profile and capture runs compile the `offset_rmsnorm` region 9 times, past Dynamo's limit of 8. This PR raises the region's limit to 16, as `fused_binary_activation` already does.

**Problem**
1. The region compiles `OffsetRMSNorm.forward(self, x)`, so Dynamo recompiles when the rank or strides of `x`, or the class of `self`, change.
2. Qwen3.5 passes 3 layouts of `x`: rank-2 (block norms), rank-3 and strided rank-3 (q/k norms).
3. With FSDP on the generator, the final norm becomes an `FSDPOffsetRMSNorm`, a 4th case.
4. Each case compiles up to 3 versions (graphs): the first token count, then the token count as dynamic, then a single token (Dynamo specializes sizes 0 and 1).
5. Here that is 9 graphs, one past the limit.

**Solution**
1. `recompile_limit=16` on the region.
2. The count doesn't grow with the number of CUDA graph sizes: vLLM captured 19 sizes here and the region still compiled 9 graphs. Only a new layout or class adds graphs, up to 3 each, so 16 fits 5 cases.

**Results**
```text
Qwen3.5-9B generator, TP1, FULL CUDA graphs, 1x H100, torch 2.15.0.dev20261005
main:     [0/8] torch._dynamo hit config.recompile_limit (8), engine fails to start
this PR:  OffsetRMSNorm.forward compiles 9 graphs, engine starts
```

You may ask: why not compile a free function `(x, weight, eps)`? It would drop the class case but leave 7 of 8 graphs, one layout away from crashing again.

**Test plan**
- The engine above (a local script with `TORCH_LOGS=recompiles`), on an earlier main.
- On this main, with the weight-sync memory fix (separate PR) also applied: Qwen3.5-9B and Qwen3.5-35B-A3B generators at TP1 start with FULL CUDA graphs and pass two weight syncs.
- A 2-GPU Qwen3.5-4B-Base RL run for 8 steps, also with the weight-sync fix, on an earlier main.
