# [graph_trainer] Support runtime-aware graph passes

[Upstream PR](https://github.com/pytorch/torchtitan/pull/4763) · state: open · merged: False

## Original PR description

## Summary

Add an opt-in runtime context for GraphTrainer graph passes.

Most graph passes only need the traced graph and fake example inputs. Some graph optimizations, such as runtime benchmarking and schedule autotuning, also need to evaluate candidate graphs using the live module state and the real batch for the active training step.

This change introduces:

- `GraphPassRuntimeContext`, which carries the live module, current call arguments, and training context.
- Runtime-context propagation from `GraphTrainer` when constructing the graph-pass pipeline.
- Construction-time binding for passes that require runtime state using ordinary callables such as `functools.partial`.

## Motivation

The existing graph-pass interface only exposes the graph and fake example inputs. A pass that needs to benchmark a transformed graph would otherwise have to reconstruct the model and synthesize inputs, which can be expensive and may not accurately represent the active training step.

Providing the original runtime state allows these passes to reuse the model and batch that produced the trace without advancing the data loader or initializing another model.

## Design

Runtime context is provided when the pass pipeline is constructed. Existing graph passes continue to use the unchanged two-argument interface:

```python
pass_fn(gm, example_inputs)
```

A custom pipeline can bind the context only to passes that need it:

```python
functools.partial(pass_fn, runtime_context=runtime_context)
```

The traced result remains a regular pipeline-construction argument, so it does not need to be duplicated in the runtime context. Runtime-aware passes remain ordinary callables, and pass naming, filtering, debugging, and graph validation continue to use the existing execution path.

This avoids signature introspection and keeps `apply_graph_passes` and the pass calling convention unchanged.

## Testing

- Added unit coverage verifying that a pass pipeline can bind runtime context with `functools.partial` and execute it through the existing pass runner.

- qqq6op · comment · 2026-09-18T03:42:57Z · [source](https://github.com/pytorch/torchtitan/pull/4763#discussion_r4043619143)

File: `torchtitan/experiments/graph_trainer/passes.py` · line None

The concrete use case is runtime profiling and autotuning of transformed graph candidates to improve communication-computation overlap.

The pass replaces the GraphModule in the existing TracedResult and uses run_traced() to execute each candidate against the live module and current training batch.

TracedResult provides the state-input metadata, pytree specifications, tensor-subclass layouts, and output reconstruction metadata required by run_traced(). The live module provides the current parameters and buffers, while the call arguments provide the real batch.

Since TracedResult is already available as a pipeline-construction argument, I removed it from GraphPassRuntimeContext in the latest commit. A custom pipeline can bind TracedResult and the runtime context separately using functools.partial.

- qqq6op · comment · 2026-09-21T15:05:14Z · [source](https://github.com/pytorch/torchtitan/pull/4763#discussion_r4063433066)

Yes, the real request is to run transformed candidate graphs inside the pass pipeline for profiling.

The original model forward is not executed. The module is only used by `run_traced()` to obtain the current parameters and buffers; the candidate `GraphModule` is what actually runs.

`example_inputs` contains flattened FakeTensors for both model state and user inputs. Materializing the model-state inputs would require additional parameter-sized allocations, which would be expensive for large models, and the synthetic values would not match the current model state. Randomly materialized user inputs may also produce MoE routing and all-to-all communication patterns that are not representative of real training. Reusing the existing model state and current batch would therefore be more convenient and efficient.

I agree that a callable for running candidate graphs may be a better interface than exposing the raw runtime context. Is that the alternative approach you had in mind?
