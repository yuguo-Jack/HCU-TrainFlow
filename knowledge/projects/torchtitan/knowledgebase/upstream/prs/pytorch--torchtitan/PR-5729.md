## Agent details

**TLDR:** With `async_loop.batcher.stream_microbatches=True`, the trainer starts forward/backward on the first packed microbatches while the step's other groups are still generating. One optimizer step can now span several `forward_backward` calls. On on-policy dapo_math, a streaming build with this PR's packing finished 1.6 s after the step's last group, vs 20.6 s on main. Builds on the engine PR below.

**Numerics:** a streamed step gives the optimizer the same gradients as one call: bitwise on 1 GPU and with PP 2, allclose with HSDP. With the flag off, numerics are the engine PR's.

```text
before:
  generators: [====== 24 groups x 16 samples (long tail) ======]
  trainer:                                                       [fwd/bwd all][opt]
after (stream_microbatches=True):
  batcher:        [batch 1]    [batch 2]      [last batch]
  trainer:          [fwd/bwd]    [fwd/bwd]      [fwd/bwd][grads /= N][opt]
```

```python
# d_k: R / N of the step's batches 1..k (auxiliary-loss denominators, computed on the controller's host)
engine.forward_backward(microbatch_groups=batch_1, aux_loss_denominators=d_1)   # the step's first call: GC, zero_grad
engine.forward_backward(microbatch_groups=batch_2, aux_loss_denominators=d_2)   # adds to the same gradients
engine.forward_backward(microbatch_groups=last, aux_loss_denominators=d_3)      # adds; d_3 is the step's R / N
engine.optim_step()   # grads /= the step's loss tokens over DP; clip; step
```

**Problem**
1. With the engine PR, losses are sums and `optim_step` divides. But every `forward_backward` call still zeroes the gradients, so a step is one call.
2. So the batcher sends a step only after all its groups finish generating.
3. On-policy, the trainer sits idle during generation, then runs every forward/backward back to back.
4. Cost on dapo_math: generation spreads over 92.8 s, then the trainer needs 20.6 s more before it can send new weights.

**Solution**
1. **Engine.** A step is every `forward_backward` call since the last `optim_step`. The first call runs GC and `zero_grad`. Later calls add to the gradients, the loss-token count and `engine.loss`. Every call finishes its own FSDP, HSDP and PP reductions.
2. **Batcher.** After each finished group, first-fit decreasing (FFD) packs the unsent samples into bins. It sends the samples that fill whole microbatch groups (one bin per DP rank, `num_pp_microbatches` deep), packed like any batch. At least `dp_degree x num_pp_microbatches` samples wait for the step's last batch, which packs everything left and has `ends_step=True`.
3. **Controller.** It sends each batch's call while the previous call runs, with at most 2 in flight. The trainer runs them one at a time, in send order: Monarch starts queued calls in order, and `Trainer.forward_backward` never awaits. A `TaskGroup` stops the step as soon as a call fails. At the step's end, the controller divides the summed loss metrics once.
4. **Auxiliary losses.** Each call divides them by R / N of the step's batches sent so far. The last call gets the step's exact ratio. Earlier calls get an estimate (Results).
5. **Unchanged:** with the flag off, the call sequence and numerics are the engine PR's.

**Results**

```text
Numerics: a streamed step gives the optimizer the same gradients as one forward_backward call
          (test_loss_token_count.py, N = 509 loss tokens, not a power of two).

  HSDP 2        gradients allclose   the replicas all-reduce once per call instead of once per step

No RL recipe trains an auxiliary loss today: build_rl_model_configs freezes MoE routing and drops it.
```

- "Streamed" is an earlier build of this PR: the same packing at 1 DP rank and no PP, with one call in flight. "main" is d681f48b4. This PR's final code has not run on dapo_math.
- "Step time outside generation" = step total minus the first-to-last group spread. Step totals swing from 60 to 168 s with the generation tail, so they are not compared.
- Forward/backward per step grows because a microbatch takes 578 ms while the generators share the node, vs 505 ms after generation. Those calls hide behind generation.

```text
Packing cost, CPU replay of this PR's batcher: whole-step packing (main) -> streamed
log-normal lengths (median ~1100 tokens), 24 groups x 16 samples, 8K context, 1-2 DP ranks, 3 seeds:
    padding 0.4-2.4% -> 2.0-4.4%, rows +0-1
64K-context agentic lengths, 96 groups x 26 samples, 16 DP ranks:
    padding 1.2% -> 1.2%, rows 30 -> 30, row imbalance 1.03 -> 1.50 (mean)
```
- Row imbalance = the slowest DP rank's attention work over the ranks' mean. It costs time only when the trainer is the bottleneck.

You may ask:
- Why does a step start at the first call after `optim_step`, with no flag on the last call? `optim_step` already ends the step, and every call finishes its reductions.
- Why not balance the streamed rows here? A balancing packer cuts the 64K row imbalance from 1.50 to 1.105, for about 80 more lines. It moves to its own PR, which must show the gain on GPU.
- Why hold back `dp_degree x num_pp_microbatches` samples? So the step's last batch has at least enough samples for one microbatch group. A bin can still end up empty when the last batch needs more groups. Example, 2 DP ranks, 10-token bins: group 0 `[8, 8, 7, 6, 1]` streams `[8+1] [8]`. With group 1 `[5]`, the last batch packs 3 samples into 4 bins. It happens in 38 of 3000 small random steps and 0 of 200 dapo_math-like steps (CPU, the real batcher). No send rule prevents it, because the last group's size is unknown. The trainer accepts an empty bin: all padding, 0 loss tokens, auxiliary weight 0.

NOTE:
- Streaming rejects SDC replay and whole-step graphs at config time. Per-group graphs, RDMA, MTP and deferred FSDP reduction stream.
- With RDMA, each call's first read is not overlapped yet (TODO at the read site). `timing/trainer/read_microbatches/max` reports the step's total read time: each call reports the running total.
- Engine callers: two `forward_backward` calls without an `optim_step` between them now add up. The core, TorchFT and RL trainers always pair them.
- A streamed step all-reduces HSDP replicas, or reduce-scatters with `fsdp_defer_gradient_reduction`, once per call. No RL recipe streams with either.
- With the flag off:
  - `trainer/tokens_per_second`, `trainer/tflops` and `trainer/mfu_percent` divide by busy time, not by wall time.
  - Non-last PP ranks sync the GPU once per call: 4.8 ms of a 920 ms step (2-GPU PP, 8 calls), within noise.
  - A failed `forward_backward` surfaces as an `ExceptionGroup`.
- Streamed samples are packed in arrival order, so the microbatches depend on which groups finish first.
- A NaN loss in an earlier batch is seen at the step's end, and no optimizer step runs.
- Not run: multi-node, MoE with EP, CP.

**What this PR does.** With `async_loop.batcher.stream_microbatches=True`, the batcher checks the step's unsent samples after each group except the last.
