# [transform] LMHeadFP32OutputConverter to transform

## Original PR description

<sub>Stack created with <a href="https://github.com/github/gh-stack">GitHub Stacks CLI</a> • <a href="https://gh.io/stacks-feedback">Give Feedback 💬</a></sub>

Change `LMHeadFP32OutputConverter` to transform.

It runs after LoRA,
and since `validate_converter_compatibility` is deleted for now since only conflict was between quantization and the deleted `LMHeadFP32OutputConverter`. The conflict will be added once quantization moves to transform.

## RL
`build_rl_model_configs` does not apply the default transforms for `freeze_moe_routing` and `fp32_lm_head` anymore.
There is a separate `apply_rl_transforms(configs, shared_transforms, trainer_transforms, generator_transforms, fp32_lm_head, freeze_moe_routing)` that:
- add `fp32_lm_head` and `freeze_moe_routing` transforms to `shared_transforms` if enabled
- apply `trainer_transforms + shared_transforms` to `trainer.model`
- apply `generator_transforms + shared_transforms` to `generator.model`

This consolidates the transform application to one place, but the recipes must not forget to call this `apply_rl_transforms` function.

reply from claude: Update: Tianyu prefers flags, so `build_rl_model_configs` keeps `fp32_lm_head: bool = True` and `freeze_moe_routing: bool = True`. Inside, it builds one `transforms` list (today `FreezeMoERoutingTransform()` when `freeze_moe_routing`) and applies it to both role configs with `transform_model_config_`. After rebasing, you could append `LMHeadFP32OutputTransform()` to that list under `if fp32_lm_head:` and drop the converter append, so recipes need no `apply_transforms` call for the fp32 head and `search_r1` keeps `fp32_lm_head=False`. Per-role transforms (e.g. the token dispatcher) stay in `apply_transforms(config.trainer / config.generator, ...)`.
