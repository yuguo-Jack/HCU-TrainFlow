## Original PR description

# [MoE] Apply router scores before W2 projection

Supersedes #4095 with a DeepEP-only implementation: router scores are absorbed before W2, and DeepEP combine is one never-replayed remat region.

## Motivation

The original DeepEP path applies router scores to each routed expert output after the W2 projection in `combine_tokens`:

```python
hidden_states = hidden_states * state.permuted_scores.to(
    hidden_states.dtype
).reshape(-1, 1)
```

This multiplication causes the post-W2 `routed_output_RD` to retain for backward. Because W2 is linear, the router score can be applied earlier to the SwiGLU activation, immediately before W2:

```
routed_output_RD
 = W2(h_RF) * routed_score_R # current impl
 = W2(h_RF * routed_score_R) # our proposal
```


See the diagram below:

<img width="4444" height="5508" alt="image" src="https://github.com/user-attachments/assets/6f4e5155-6cfb-455f-925f-8d9165899666" />

### Expected memory gain in full model:
Combine output: `T * D * 2 = 4096 * 7168 * 2 = 56.0 MiB` per layer, `* 58 layers = 3.17 GiB`

W2 output: `(T * top_k) * D * 2 = 4096 * 8 * 7168 * 2 = 448.0 MiB` per layer, `* 58 layers = 25.4 GiB`

Total per GPU: `25.4 + 3.17 = 28.6 GiB`

### Expected recomputation gain in FullAC
check https://github.com/pytorch/torchtitan/pull/5543#issuecomment-6469912261

## Implementation
### Functionalities
- DeepEP dispatch returns per-row router scores explicitly through `DeepEPDispatchMetadata`, rather than storing them in backend state for combine.
- `RoutedExperts` applies those scores to the SwiGLU output before the bias-free W2 projection by default, with no configuration flag. The optimization is DeepEP-only. DeepEP with a W2 bias or `output_postprocess` raises `ValueError` during config validation.
- DeepEP combine becomes a pure unpermute/reduction inside one never-replayed remat region. Remove the redundant W2-output and combine-output retention markers.

### Tests
- Extend the existing DeepEP checkpoint tests with a `_PostW2` reference that applies scores after W2, comparing loss and input/router/expert gradients while preserving checkpoint equivalence and communication replay checks.

### Numerics

Moving router-score multiplication before a bias-free W2 is equivalent in exact
arithmetic but changes BF16 rounding and therefore outputs and gradients. The
original DeepEP path casts the score to the W2-output dtype before multiplying.
This PR preserves that score precision: it casts the score to the hidden dtype
before scaling W2's input, then applies W2. Rounding the scaled input before
W2 still differs from rounding W2's output before applying the score.

### Is this PR worth its complexity? Gain by (remat policy × dispatcher)

**Short answer:** the memory gain is real and large for one combination: **DeepEP + a policy that saves `w2`** (Default or save-all), and only when the user opts in to `absorb_router_scores=True`. For HybridEP the gain is about zero as written. DistMoE is untouched. The rest of the PR is the AllToAll/Local/TorchAO reference paths plus config plumbing. Under **FullAC + DeepEP with the default `absorb=False`**, it looks like the PR makes memory worse.

I got the numbers below by reading the code, not by running it. Sizes are for 671B per GPU: T=4096, top_k=8, D=7168, F=2048, so R = T·top_k = 32768. Per layer, the `w2` output R·D·bf16 is **448 MiB**, the combine output T·D·bf16 is **56 MiB**, and h (the SwiGLU output) R·F·bf16 is 128 MiB.

|---|---|---|---|---|
| **DistMoE** | any | — | **not affected.** `dist_moe.routed_experts` is one opaque `recompute=False` region that owns dispatch, the expert GEMMs, activation storage and combine (`dist_moe/routed_experts.py:224`) | same |
| **DeepEP** | Default (`save *`, recompute `w13`) / save-all | `w2` output pinned as SAVE_OUTPUT by `recompute_needs_tensor` in `combine` (448 MiB). Combine output pinned (56 MiB) | **−448 MiB −56 MiB/layer (~28.6 GiB/GPU).** The real win | `w2` output now held by the mul inside the never-replayed combine region instead of the pin: same 448 MiB. **−56 MiB** from removing the combine-output pin |
| **DeepEP** | Full | nothing resident. - **DistMoE BF16:** scoring follows the fused W2-and-combine operation, so reconstruction includes both computation and communication.

- **DeepEP/HybridEP:** scoring precedes combine communication, so reconstructing the local W2 output can suffice.

You only get it under FullAC (or another policy that doesn't save `w2`), and only with DeepEP when `absorb_router_scores=True` is set explicitly.** Under the Default policy, `main` never runs GEMM 3, so the gain there is memory, not compute.

#### 1. Elementwise ops are not added, they get smaller

Your example leaves out the elementwise ops on the `main` side. With every op written out (R = routed rows, D = model dim, F = expert hidden dim):

| | `main` (score after W2) | PR (score before W2) |
|---|---|---|
| forward | `z = W@h` (GEMM), `y = s*z` (**R×D**) | `a = s*h` (**R×F**), `y = W@a` (GEMM) |
| FullAC replay | `z = W@h` (**GEMM 3**) | `a = s*h` (**R×F**) |
| backward, score grad | `ds = rowsum(g*z)` (**R×D**) | `ds = rowsum(da*h)` (**R×F**) |
| backward, input grad | `dz = s*g` (R×D), `dh = Wᵀ@dz`, `dW = dz@hᵀ` | `da = Wᵀ@g`, `dh = s*da` (R×F), `dW = g@aᵀ` |

Backward has two elementwise ops on each side. The PR's run on R×F tensors instead of R×D. In Mystri's example (D=7168, F=1408) that is 5.1× less memory traffic for each op. The only new op is the replay `a = s*h`, which is one R×F pass. The FullAC replay on `main` does GEMM 3 at the same point.

Rough size of that extra pass: R×F in bf16 is 61614·1408·2 ≈ 165 MiB. A read+write pass is about 0.1–0.2 ms on H800, compared with **1965 µs** for the GEMM it replaces. The PR currently writes `input_RI.float() * scores` (`linear.py`, `GroupedLinear.forward`), which creates an fp32 temporary and roughly doubles that traffic. It is still small next to the GEMM, but type promotion (`(input_RI * scores).to(input_RI.dtype)`) would avoid it.

Routed-expert grouped GEMM FLOPs for one MoE layer and one microbatch:

| | forward | FullAC replay | backward | total |
|---|---|---|---|---|
| `w13` (2·M·D·2F) | 2.49 T | 2.49 T | 4.97 T | 9.95 T |

As a share of the whole MoE layer, the saving is smaller. #### 3. Which (policy, dispatcher) combinations get the compute saving

GEMM 3 only exists when `w2`'s output is not saved:

| policy | `main` | PR, `absorb=True` |
|---|---|---|
| Default (`save *`, recompute `w13`) / save-all / no AC | `z` saved, **no GEMM 3** | no FLOP saving. The gain is memory: `z` (R×D bf16, ~448 MiB/layer at 671B) is no longer retained |
| FullAC | GEMM 3 runs | GEMM 3 is gone (Mystri's trace: 40 → 35 grouped GEMMs over 5 layers) |

Both parts of the PR are needed for the compute win. Absorption removes `ds`'s dependency on `z`, and the never-replayed combine region (`deepep.py`, `_scored_combine` with `recompute=False`) removes the replay's dependency on `z`. With absorption alone, the combine replay would still read `z` and GEMM 3 would stay.

Without this PR, you pick one: save `z` (0 extra FLOPs, +448 MiB/layer) or recompute it (0 MiB, +1 GEMM). With the PR you get 0 MiB and 0 extra FLOPs.

#### 4. Is it worth the complexity?

Points to weigh:
- **The scope is narrow.** DistMoE (the main optimized backend) isn't affected. AllToAll is a reference path. HybridEP gets no gain as written (see the earlier analysis). DeepEP only gets it as an opt-in. So the compute benefit only applies to DeepEP + FullAC + opt-in.
- **The math is cheap, the plumbing isn't.** The math itself is about 10 lines: scale W2's input, skip the multiply in combine. Most of the +1147 lines are the per-dispatcher `absorb_router_scores` flag, auto-resolution, the `swap_token_dispatcher`/transform plumbing, and the stub-based tests.
- **There's no end-to-end number yet.** The trace measures a single GEMM. Before deciding, it would help to see:
  - (a) step time for DeepEP + FullAC, absorb vs. not, on a real-size config;
  - (b) the C4 loss comparison, which is still unchecked. Absorbing rounds `s*h` to bf16 before the GEMM, so results are not bitwise identical to `main`.

If (a) shows a step-time gain in line with the ~4% FLOP estimate, a reduced version seems worth it: absorption always on for DeepEP when valid (no flag), plus the never-replayed combine. That gets the memory win under Default and the GEMM win under FullAC with much less surface. The rest could be dropped or deferred.

<summary>Details: per-op FLOPs and memory traffic, with 671B numbers</summary>

#### Symbols

- `R`: routed rows on this rank (`T * top_k`)
- `D`: model dim
- `F`: expert hidden dim
- `b`: bytes per element (bf16: `b = 2`)
- Tensor shapes: `h, a, da, dh` are R×F; `z, y, g, dz` are R×D; `W` is D×F; `s, ds` have shape R.
- A GEMM costs 2·M·N·K FLOPs. An elementwise multiply costs 1 FLOP per element. A row-wise dot costs about 2 FLOPs per element (multiply + add).

```
fraction      = (2DF + 4D - 5F) / (8DF + 4D)      # R cancels
traffic saved = (6RD - 8RF) * b                    # positive whenever 3D > 4F
```

- `y = s*z` (RD) ↔ `a = s*h` (RF)

<details>
<summary>How the numbers were computed, and caveats</summary>

#### Formula

```
N_blocks  = matmul params in the transformer blocks (routed experts weighted by top_k/E)
N_head    = D·V (lm_head; embeddings untied in every flavor above, so excluded)
A         = model's attention term (quadratic_attention_flops_per_token /
            delta_rule_flops_per_token, already a 6x training number)

FullAC FLOPs/token = 6·(N_blocks + N_head) + A      # repo MFU convention
                   + 2·N_blocks + A/3              # FullAC replays every block's forward
saved/token        = 2·top_k·D·F · L_moe           # the W2 GEMM no longer replayed
e2e                = saved / FullAC FLOPs
```

Why it is capped near 8%: the routed experts contribute `3·top_k·D·F` params per MoE layer, and W2 is 1/3 of that. Under FullAC each routed param costs 8 FLOPs (2 forward + 2 replay + 4 backward), and the PR removes 2 of the 24 per expert row. So `e2e ≈ (routed share of active FLOPs) / 12`. Models where the routed experts dominate the active params come closest. Kimi K2.5 has one dense layer and MLA with 64 heads, and gets the highest share. Qwen3.5-35B has a large vocab relative to its size and GDN/full-attention projections, and gets the lowest.

With the fallback gone, absorption now always runs for DeepEP, including in the two cases where it is wrong. Nothing raises:
- **w2 bias** (gpt_oss, `GptOssGroupedLinear` always creates `self.bias`): this computes `W2(s*h) + b`, but the correct result is `s*(W2 h + b)`. Each expert's bias is now added unscaled, once per routed row.

Both models build with `AllToAllTokenDispatcher`, but `TokenDispatcherTransform(dispatcher=DeepEPTokenDispatcher, ...)` can be applied to any model. On `main` that combination was correct; with this PR it silently gives wrong numerics.

Ban it. `TokenDispatcherTransform` swaps the dispatcher after the `RoutedExperts.Config` is built, so `__post_init__` doesn't see the swap. `GptOssGroupedLinear` adds its bias regardless of `Config.bias`, so the check is simplest at build time in `RoutedExperts.__init__`:

```python
if isinstance(self.token_dispatcher, DeepEPTokenDispatcher) and (

):

    )
```
