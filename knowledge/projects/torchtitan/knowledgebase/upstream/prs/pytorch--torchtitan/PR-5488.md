# [rl] Drop FULL CUDA graph capture sizes above max_model_len

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5488) · state: open · merged: False

## Original PR description

**TLDR:** Under `FULL` CUDA graphs, a generator whose `max_model_len` is below its largest capture size (2048 by default) can crash with an illegal memory access while capturing. The generator now captures only sizes up to `max_model_len`.

**Problem**
1. `FULL` captures a graph for every size up to `max_num_batched_tokens` (2048 by default).
2. vLLM captures a size by running dummy requests as long as the size: a 2048-token capture runs 2048-token requests.
3. Each request's KV block table has room for `max_model_len` tokens. At `max_model_len=1024`, attention reads 128 pages from a 64-page row.
4. On H100 that's an illegal memory access in the first capture warmup (GPT-OSS debug and Qwen3 debug, TP1). A memory checker reports a 16-byte read 65,024 bytes before the KV cache, in the paged-KV load.
5. Only setups with `max_model_len` below the capture cap can hit it. Every shipped recipe is at 2048 or more. The 1024-token CI recipes are in range and read past the block table without faulting: only the last row reads past the end, so whether it faults depends on what lies after it.

**Solution**
1. In `FULL`, the capture cap is now at most `max_model_len`, and sizes above it are dropped (with a warning), in `VLLMCudaGraphConfig.get_vllm_compilation_config`, which now takes `max_model_len`.
2. Explicit `capture_sizes` are filtered the same way; if none is left, it raises.
3. `FULL_DECODE_ONLY` is unchanged: its dummies are one-token requests, which always fit.
4. Cost: on a short-context recipe, a step with more tokens than `max_model_len` (several prompts at once) runs eager.

**Results**
```
H100, TP1, random init, FULL, max_num_seqs 8, max_model_len 1024, 8 prompts x 32 tokens
                          before                                  after
GPT-OSS debug             illegal memory access during capture    runs, sizes up to 1024, decode step 1.63 ms
Qwen3 debug               illegal memory access during capture    runs, sizes up to 1024, decode step 1.58 ms
Qwen3 debug, memcheck     1,056 errors (paged-KV load)            0 errors
```
Recipes with `max_model_len` >= the capture cap get the same sizes as before (checked on 840 settings of mode, `max_num_seqs`, `max_model_len`, budget and expert-SP degree).

You may ask:
- Why not cap the dummy's length inside vLLM? That's vLLM's runner; this is one filter in our config.
- Why not raise, as the linear-attention builder does? It would break the 1024-token CI recipes over a setting they don't care about.

NOTE: measured on H100 only; needs a Blackwell run (the fix removes the oversized dummy, so it shouldn't depend on the attention kernel).

**Test plan**
`pytest tests/rl/unit_tests/cpu/test_generator.py` (new: `test_cuda_graph_full_mode_drops_sizes_above_max_model_len`).
GPU, 1 H100: GPT-OSS debug and Qwen3 debug at `max_model_len` 1024 under FULL, before and after.
