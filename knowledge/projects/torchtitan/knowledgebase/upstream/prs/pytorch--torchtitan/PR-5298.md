# [rl][easy] Require torchmonarch>=0.7.0

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5298) · state: closed · merged: True

## Original PR description

**TLDR:** Require `torchmonarch>=0.7.0` for RL. On 0.6.0, freeing a tensor registered as an `RDMABuffer` can deadlock. In a CPU stress of the trainer-pull batcher, 0.6.0 hung in 3 of 10 runs and 0.7.0 in 0 of 10. CI already installs 0.7.0; the floor makes existing environments upgrade too.

**Problem**
1. In 0.6.0, freeing a registered tensor runs a cleanup callback under a non-reentrant lock.
2. That cleanup can free a second registered tensor on the same thread, whose callback then waits forever for the lock its caller holds.
3. main's own code creates no `RDMABuffer`, and single-host runs sync weights over shared memory, so CI never hits this.
4. Multi-host weight sync can use torchstore's Monarch RDMA transport, which registers buffers. So do the trainer-pull PRs, which carry a workaround for 0.6.0.
5. `.ci/docker/requirements-rl.txt` lists `torchmonarch` with no version. The CI image was rebuilt on Oct 11 and already has 0.7.0, but an existing environment stays on 0.6.0: `uv pip install -r` skips a satisfied requirement (`--dry-run` prints "Would make no changes").

**Solution**
1. `torchmonarch>=0.7.0`. 0.7.0 makes the lock an `RLock` (Monarch commit `8ce01987a`, "Fix self-deadlock in the local-memory cache eviction path").
2. No code changes; main's CI already runs on 0.7.0.

**Results**

Monarch's regression test `test_local_memory_cache_reentrant_eviction`, run standalone with a 5 s join:
```text
0.6.0   still blocked after 5 s (deadlock)
0.7.0   ok
```

Batcher stress from the trainer-pull PRs with their workaround off (each batch freed right after `drop()`): 4 CPU readers, 1,500 steps and 120,000 buffers registered and dropped per run, TCP transport, 10 runs of each version at the same time:
```text
0.6.0   3 of 10 hung; py-spy on all 3: _evict_local_memory re-entered under the lock
0.7.0   0 of 10 hung
```
The race needs load: with 8 and 12 runs at a time, 0.6.0 hung in 0 of 8 and 0.7.0 in 0 of 12.

`pytest tests/rl/unit_tests/cpu` on 0.7.0 (torch 2.16.0.dev20261011, CPU only):
```text
433 passed, 5 skipped, 2 failed
```
The 2 failures are config tests in `test_verifiers_terminal_bench.py` (`'Config' object has no attribute 'train_dataset'`). They don't touch Monarch, and CI doesn't run them.

You may ask: why not `==0.7.0`? The unpinned line already takes the newest release at each image rebuild; `>=` only adds the minimum.

NOTE: this edits `.ci/docker`, so CI needs `ciflow/docker` to build the image (about 15 min) before other jobs can pull it, and `ciflow/rl` for the RL jobs. Rerun any job that started before the image existed.

**Test plan**
```bash
CUDA_VISIBLE_DEVICES= PYTHONPATH=. python -m pytest -q tests/rl/unit_tests/cpu
```
RL CI with `ciflow/docker` and `ciflow/rl`. The regression test and the batcher stress are standalone scripts, not part of this PR.
