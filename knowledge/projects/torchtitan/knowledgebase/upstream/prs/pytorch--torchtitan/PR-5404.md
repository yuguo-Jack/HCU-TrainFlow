# [rl] Default the oneCCL 2022 workarounds on for XPU

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5404) · state: open · merged: False

## Original PR description

Part of the RFC pytorch/torchtitan#5401 (GRPO on Intel XPU).

Contains only the oneCCL workarounds; merge after #5403. On its own, `train.py` builds the storage-volume twin mesh on `this_host()`; once #5403 lands, that call uses the job's trainer hosts (`host_meshes.trainer`) -- a one-line rebase.

Two oneCCL 2022 bugs break weight sync on XPU (filed with standalone C reproducers): uxlfoundation/oneCCL#222 (a cross-node broadcast from a process whose first communicator was an FSDP one moves no data) and uxlfoundation/oneCCL#225 (concurrent communicator creation fails).

- `Controller.Config.storage_volumes_in_own_procs`: TorchStore storage volumes run in a twin of the trainer mesh (same hosts and devices), whose first communicator is a weight-pull one.
- `InterGeneratorRouter.Config.sequential_initial_pull`: the first weight pull runs one generator at a time; later pulls stay concurrent.

Both default to `device_type == "xpu"`, so CUDA is unchanged; they can be removed once oneCCL ships fixes. Validated on ALCF Aurora (torch 2.14.0+xpu, oneCCL 2022.1.1, vLLM main, Qwen3-0.6B GRPO, full + LoRA): 18/18 regression (2 nodes x 1/2/4/8/12 tiles, 16 nodes x 4/12 tiles, 1- and 8-node 10-step runs). This branch targets current main, which needs torch nightly while vLLM's XPU support pins torch 2.14, so it was checked line by line against the tested torch-2.14 branch.
