# perf: keep chunked loss gradient buffers in their native dtype

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5408) · state: closed · merged: True

## Original PR description

## Summary

Keep the chunked-loss hidden-gradient buffers in the hidden-state dtype and pass those buffers directly to decoder backward. On an H100, this reduces peak allocated memory by **128 MiB** for the 16K-token cases and **1,043.983 MiB** for the 128K-token case below.

`GradAccumulator.add()` copies each chunk gradient into a disjoint slice. Each detached hidden-state leaf already receives a gradient in its own dtype. The current FP32 assembly therefore widens every BF16/FP16 chunk and narrows the complete buffer at the end without performing any arithmetic in between. Using the original dtype removes both conversions and their temporary allocations.

The change is confined to `ChunkedLossWrapper`; `GradAccumulator` retains its explicit-dtype contract and zero initialization. LM-head parameter-gradient accumulation, loss computation, and FSDP synchronization remain unchanged. This continues the chunked-loss memory work in #5082.

For BF16/FP16 hidden states with shape `[T, D]`, the assembly buffer uses `2 * T * D` fewer bytes per output. Removing the final FP32-to-hidden-dtype copy eliminates another full-buffer allocation at the handoff. The overall peak depends on the LM-head and loss intermediates.

## H100 measurements

Measured against `10f03e13d6f3ca8fcf08a16620abe3e2670b3101` on one NVIDIA H100 80GB HBM3 with MIG disabled, driver 580.95.05, and PyTorch `2.16.0.dev20261010+cu132`.

All inputs use BF16 and hidden size 4,096. The 16K cases use 16,384 tokens and 8 chunks; the 128K case uses 131,072 tokens and 64 chunks. `Linear` uses vocabulary size 128,256; `HiMidLoLinear` uses 151,936.

<summary>Reproduce the native Linear memory and latency measurements</summary>

Run this from each checkout with the same CUDA runtime. It measures the complete native BF16 LM-head, chunked loss, and backward call. Each run warms up five calls and measures fifteen calls. Set `TOKENS=131072 CHUNKS=64` for the long-context case; set `COMPILE_LOSS=0` for eager cross-entropy.

```bash
CUBLAS_WORKSPACE_CONFIG=:4096:8 PYTHONPATH=. python - <<'PY'
import os
import statistics
import time

import torch
from torchtitan.components.loss import ChunkedLossWrapper
from torchtitan.distributed.local_compile import apply_local_compile
from torchtitan.models.common.linear import Linear

torch.manual_seed(42)
torch.set_num_threads(1)
torch.use_deterministic_algorithms(True)
tokens = int(os.environ.get("TOKENS", "16384"))
chunks = int(os.environ.get("CHUNKS", "8"))
head = Linear.Config(in_features=4096, out_features=128256).build()
head = head.to(device="cuda", dtype=torch.bfloat16)
hidden = torch.randn(tokens, 4096, device="cuda", dtype=torch.bfloat16,
                     requires_grad=True)
labels = torch.randint(128256, (tokens,), device="cuda")
labels[::13] = -100
count = (labels != -100).sum()
loss_fn = ChunkedLossWrapper.Config(num_chunks=chunks).build()
loss_fn.set_lm_head(head)
apply_local_compile(["loss"] if os.environ.get("COMPILE_LOSS", "1") == "1" else [])
samples = []
for iteration in range(20):
    head.zero_grad(set_to_none=True)
    hidden.grad = None
    torch.cuda.synchronize()
    if iteration == 5:
        torch.cuda.reset_peak_memory_stats()
    started = time.perf_counter()
    loss, _ = loss_fn(hidden, labels, count)
    loss.backward()
    torch.cuda.synchronize()
    if iteration >= 5:
        samples.append((time.perf_counter() - started) * 1000)
print({"torch": torch.__version__, "gpu": torch.cuda.get_device_name(),
       "tokens": tokens, "chunks": chunks,
       "median_ms": statistics.median(samples),
       "peak_allocated_GiB": torch.cuda.max_memory_allocated() / 2**30})
PY
```

### Review: does this reduce accumulation precision?

**Short answer: no. There is no case where it reduces precision.** The FP32 buffer was never used for accumulation. It only held copies of data, so removing it doesn't change any result for BF16, FP16 or FP32 hidden states. For FP64 it slightly *improves* precision.

#### Why

1. **`GradAccumulator.add()` copies; it never adds.** Each chunk is written into its own slice of the buffer (`self.buffer[tuple(slices)] = chunk_grad`, `loss.py:497-499`). The slices never overlap and the buffer starts at zero, so no value is ever the sum of two contributions. The class name is misleading: there's no `+=` anywhere.
2. **The per-chunk gradient already has the hidden-state dtype.** Each `h_chunk` is a separate detached leaf (`loss.py:632`). Autograd's `validate_outputs` casts the incoming grad to the leaf's dtype before `AccumulateGrad`, so `h_chunk.grad` is already BF16 for a BF16 hidden state, whatever happened inside the LM head or the loss (for example, an FP32 upcast in CE). Any summing within a chunk happens in autograd, in the leaf dtype, before `GradAccumulator` sees it, and that is the same before and after this PR.
3. **The FP32 detour was a round trip with nothing in between.** It went BF16/FP16 → FP32 (exact) → copy → FP32 → BF16/FP16 (exact, because the values were representable in the original dtype). The result is bit-identical, which matches the PR's exact-match validation.
4. **Multi-output (MTP) doesn't change this.** Each output gets its own leaves and its own accumulator (`loss.py:642-650`), so different outputs never sum into one buffer.
5. **Decoder backward gets the same dtype as before.** Before, `_DecoderOutputGradientBackProp` received `buffer.to(hidden.dtype)`; now it receives a buffer that is already in that dtype. When the hidden state was FP32, `.to()` was a no-op that returned the same buffer, so passing the buffer itself (the same object that is saved on `ctx`) is a path that already ran. The GraphTrainer bridge (`experiments/graph_trainer/chunked_loss.py`) uses the same tensors.
6. **FP64 improves.** Before, FP64 grads were truncated to FP32 and then widened back. Now they stay FP64, as the PR description notes.

The only real accumulation in this path, the LM-head **parameter** gradients across chunks, goes through `param.grad` / FSDP and is unchanged.

#### Other notes
- The diff is correct and small. Reading `hidden_state.dtype` per output is right for MTP outputs with mixed dtypes.
- Nit: the `GradAccumulator` docstring example (`loss.py:463`) still shows `dtype=torch.float32`. Consider changing it to `dtype=hidden_states.dtype` so it matches the only caller. The name `GradAccumulator` also suggests summing, which is probably where the precision worry came from; a one-line note that chunks are written into disjoint slices, not summed, would head off this question in the future. Optional.
- Nit: there's no test that pins the new behaviour. A small CPU test could check that the hidden grad from `ChunkedLossWrapper` with BF16 input is BF16 and bit-identical to the unchunked reference. Existing tests only build `GradAccumulator` with FP32.
- The PR's measurements are single-GPU only. Precision is not affected by TP/CP/FSDP here: with TP, the hidden state is `Replicate` going into the LM head, and with FSDP mixed precision the input cast happens inside the LM head, upstream of the leaf grad. Multi-rank memory numbers haven't been measured.

LGTM on the precision question.
