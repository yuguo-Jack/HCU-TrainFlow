# [glm5] Add GLM-5 model support

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5578) · state: open · merged: False

## Original PR description

## Summary

Adds native GLM-5 model support to TorchTitan, covering GLM-5.2 and GLM-5.3.

GLM-5.3 uses the same base model architecture as GLM-5.2. The implementation
therefore shares one GLM-MoE-DSA model definition while exposing versioned
GLM-5.2 and GLM-5.3 flavors and test recipes. It covers the released base
architecture and smaller debug configurations, including multi-head latent
attention, DeepSeek Sparse Attention with cross-layer index sharing,
dense-to-MoE transitions, and the released NextN multi-token prediction block.

## Main changes

### Model

- Add `torchtitan/models/glm5` with MLA and DSA attention, cross-layer index
  sharing, dense and routed/shared MoE layers, NextN/MTP training,
  declarative sharding, and Hugging Face state-dict conversion.
- Add versioned GLM-5.2 and GLM-5.3 flavors sharing the released base
  architecture.
- Add GLM-5 to the supported-model table and provide test recipes under
  `torchtitan_recipes/tests/models/glm5.py`.

### Shared infrastructure

- Allow declaratively sharded modules to return a primary tensor together
  with auxiliary tuple outputs.
- Redistribute the primary tensor while preserving auxiliary values such as
  DSA routing indices.

### Tests and validation

- Add CPU tests for model and flavor configuration, DSA index sharing,
  sharding contracts, MTP configuration, and Hugging Face state-dict round
  trips.
- Add reduced TorchTitan/Hugging Face numerical validation and versioned
  GLM-5.2/GLM-5.3 checkpoint-mapping coverage.
- Add 8-GPU integration configurations for the base and MTP models.

## Parallelism support

- FSDP2 / HSDP
- Tensor and sequence parallelism
- Context parallelism
- Expert parallelism
- Pipeline parallelism for the base model

The registered integration configurations compose FSDP2, TP, CP, and EP on
eight GPUs. MTP composes with FSDP2, TP, CP, and EP. Pipeline parallelism with
MTP is not included yet.

## Numerical validation

The reduced Hugging Face comparison strictly loads the converted state dict
and compares routing decisions and full-sequence logits:

- Router choices: `159/160` (`99.4%`)
- KL divergence: `4.0183e-05`
- Cosine similarity: `0.99995768`
- Maximum logit difference: `6.2998e-02`
- Top-1 agreement: `100%`

## Testing

- `pre-commit run --all-files`
- GLM CPU unit tests
- Hugging Face numerical parity
- 8-GPU base integration: FSDP2 + TP2 + CP2 + EP2, 10 training steps
- 8-GPU MTP integration: FSDP2 + TP2 + CP2 + EP2, 10 training steps

Both integration configurations completed training with finite and
rank-consistent loss and gradient norm.

**Must fix: `padding_mask` polarity is inverted.** In torchtitan `padding_mask` is True for padding: see `components/data/collators.py:74,98` (real rows get `zeros`), `packing.py:197` (`constant_values=True`), and the docstring at `common/attention/attention.py:932`. This line keeps `allowed` only where `padding_mask` is True, so every real token's row is fully masked and only padding tokens attend.

`to_input_dict` always passes `padding_mask` (`components/data/types.py:82`), so this hits every training step through the standard data pipeline. Attention output for real tokens becomes empty or uniform, but loss stays finite, which is why the 10-step integration runs didn't catch it. `model.py:409-411` / `mtp.py:61-63` build `mtp_padding = ~valid | padding_mask` with the correct (True = pad) convention and then pass it here, so the code is internally inconsistent.

The tests encode the inverted meaning (`test_glm5_dsa.py:41-45` pass `valid` as `padding_mask_T`, `:71` expects index 1 = `False` to be excluded). The HF parity script uses no padding.

```suggestion
        allowed_TT = allowed_TT & ~padding_mask_T[:, None] & ~padding_mask_T[None, :]
```
Also flip the tests, and add one test that feeds a collator-produced microbatch through `get_attention_masks`.
