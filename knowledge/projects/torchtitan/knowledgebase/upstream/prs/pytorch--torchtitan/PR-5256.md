# [rl] keep session KV in an evict-last free-queue tier instead of pinning it (on #5220)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5256) · state: open · merged: False

## Original PR description

**TLDR:** Stacked on #5220. Replaces `SessionKVHolder`'s pinned blocks (an extra block reference plus `session_kv_free_floor`) with a two-tier vLLM free queue: blocks a live session will reuse stay free, but vLLM reuses them only after every other free block. This removes the floor and a latent engine hang. It's the same idea as SGLang's [session-aware radix cache](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/session_radix_cache.mdx#eviction-behavior) ("soft protection, not memory pins").

**Problem with pinning (#5220)**
1. A held block carries an extra reference, so vLLM counts it as used. Admission sees only the unheld free blocks.
2. Holds are released only while free blocks are below `session_kv_free_floor`. vLLM admits a waiting request only if its whole uncached prompt fits in the free blocks (`scheduler_reserve_full_isl=True`), and FCFS stops at the first request that doesn't fit.
3. So a request needing more than the floor is never admitted. Once nothing runs, free blocks stay at or above the floor, nothing is released, and the engine loop steps forever. CPU repro on vLLM's `KVCacheManager`: 100 blocks, floor 10, 8 idle held sessions leave 20 free; a waiting 25-block request is never admitted, and `evict_until_free()` releases nothing.
4. It's latent while the floor covers a max-length request (likely true on GB300) and real for smaller KV caches or long contexts. While other requests run, the same gap stalls admission (headroom = floor - watermark).

**Solution**
1. `_TieredFreeBlockQueue` replaces `BlockPool.free_block_queue` and implements what the pool calls after its init. The ordinary tier is vLLM's original queue; the live tier holds free blocks that live sessions mark. vLLM takes from the ordinary tier first, and from the live tier (oldest first) only once the ordinary tier is empty. Both tiers count as free.
2. `SessionKVHolder` keeps #5220's session bookkeeping, release paths and prefix lookup, but marks blocks instead of referencing them:
   - marks are counted per block, so a shared prefix stays live until its last session ends;
   - each mark records the block's reuse epoch, so a release never unmarks a block vLLM has since reused for other content;
   - blocks no live session marks go to the evict-first end (the session's next turn moved past them, or the session ended).
3. Removes `session_kv_free_floor` and `evict_until_free`. Init rejects KV connectors, models with more than one block pool, and an unexpected queue type.
4. `vllm.kv_cache_usage` no longer includes held blocks, so it means what it means in plain vLLM.

Compared with SGLang: same soft protection. SGLang registers a session's cache when a request finishes (output tokens included); this marks it right after prefill (prompt only), which vLLM's align mode needs for the GDN state block. SGLang evicts referenced nodes with fewer session references first; here any mark counts the same. SGLang returns a closed session's KV to its normal LRU position; here it goes to the evict-first end, since vLLM's queue keeps no timestamps.

NOTE:
- This patches vLLM internals more deeply than #5220 (the free queue itself, not just `touch`/`free_blocks`). The tests drive vLLM's real `KVCacheManager`, so a vLLM bump that changes how `BlockPool` uses its queue should fail them. Long term this belongs in vLLM.
- Not run on GPU. #5220's open question still applies: an A/B with the KV cache under pressure.

**Test plan**
`pytest tests/rl/unit_tests/cpu`: 527 passed, 8 skipped (#5220: 528; this removes its 3 floor tests and adds 2). `tests/rl/unit_tests/cpu/test_session_kv_holder.py` is rewritten, including `test_a_request_larger_than_the_unheld_blocks_is_admitted` (the hang scenario), `test_shared_prefix_stays_held_until_its_last_session_ends`, and a check that every free block sits in exactly one tier. pre-commit is clean (pyrefly hook skipped locally; pyrefly on `session_kv_holder.py`: 0 errors).
