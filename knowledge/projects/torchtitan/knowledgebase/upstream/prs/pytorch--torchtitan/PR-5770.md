# Fix HybridEP activation remat and document EP backend selection

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5770) · state: closed · merged: True

## Original PR description

## Summary (human-written)
<!-- Write this yourself, not with an AI tool. 2-5 sentences: the problem, why
     this approach, and what you checked yourself. -->

1. add proper remat support for HybridEP
2. add moe/README.md as a backend selection guidance

## Why
HybridEP dispatch and combine run outside torch_remat regions. Consequently,
DefaultActivationRematConfig replays both during backward even though its documented
policy retains EP communication. Users also lack a single guide comparing the
supported EP execution paths and their graph, precision, and memory constraints.

**Example.** One forward/backward through a routed-expert layer normally needs
one dispatch and one combine in the forward, plus one call to each primitive
for gradient computation. Activation remat can add another replay of the
forward communication pair:

| Policy | Extra communication before this PR | Extra communication after this PR |
| --- | --- | --- |
| No remat | None | None |
| Default remat | 1 extra dispatch and 1 extra combine | None |
| Full remat | 1 extra dispatch and 1 extra combine | 1 extra dispatch and 1 extra combine |

The default policy now retains the forward communication results for expert
recomputation. Normal forward and gradient communication still run; full remat
continues to replay communication as requested.

## What changed
- Declare HybridEP dispatch/combine regions controlled together by `ep_communication`,
  matching DeepEP. Retain counts and scores consumed outside regions.
- Pass the forward handle through a CPU tensor ID because torch_remat 0.2.2 accepts
  only tensor region outputs. Garbage collection releases cache entries. A CPU
  lookup op keeps autograd setup contexts traceable with FakeTensor/AOT. Upstream
  opaque-output support is tracked in [remat issue #10](https://github.com/meta-pytorch/remat/issues/10).
- Add an EP backend selection guide beside MoE, with configuration examples,
  remat semantics, capacity considerations, and links to public dependency guides.
  No backend is removed or added.
- Mechanically share the existing DeepEP test harness with HybridEP, then check
  communication counts, exact loss/gradients, and graph capture. Run HybridEP tests
  after its existing CI installer.

## Alternatives considered
- Retain the whole MoE call: would also retain expert compute that the default
  policy intends to recompute.
- Return the existing opaque handle from the region: current torch_remat rejects
  it. The tensor-only contract comes from meta-pytorch/remat#2; upstream opaque
  output support would allow removal of the tensor-ID cache.

## User-facing changes
| Before | After |
| --- | --- |
| HybridEP communication replays under default remat | Default/custom saved policies retain it; full remat still replays it |
| Backend constraints scattered across recipes and implementation | `torchtitan/models/common/moe/README.md` describes the available choices |

## Numerics
No changes to routing, expert computation, checkpoint parameter names, or precision.
Against main `ff96670a2`, DeepSeek V3 debug-model training with FSDP2 x EP2 on two
GB300 GPUs produced bitwise-identical TensorBoard loss and grad_norm for all 10
steps, with seed 42 and deterministic execution. Validation used
`scripts/loss_compare.py --steps 10 --no-seed-checkpoint --metrics loss,grad_norm`,
exporting main's metrics and asserting equality on the branch with `--import-result`.

## Testing

<details><summary>Details</summary>

- Lifetime: the cache entry stays alive while any of these references `handle_id`: `DispatchState`, the dispatch node's ctx, or the combine node's ctx. Without remat, `handle_id` is freed after backward frees the graph. Under `no_grad`, it is freed after combine. When remat replays the communication, the replayed dispatch creates its own id, and the replayed nodes' ctx keeps it. Because the region policy is `ep_communication`, dispatch and combine are always both saved or both replayed. A saved dispatch can never be paired with a replayed combine, so a missing `_handle_cache` key isn't reachable.
