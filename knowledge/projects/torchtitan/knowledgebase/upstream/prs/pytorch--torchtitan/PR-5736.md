# added z loss

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5736) · state: open · merged: False

## Original PR description

## Summary

Z loss has become a fairly popular regularization loss used together with Cross Entropy. I already did a PR about this but it stalled for there were major mods coming to the way loss was handled. I do not know if the situation stabilized from https://github.com/pytorch/torchtitan/pull/2576 but here I am re-proposing the same feature.

## Why
Adds an optional z-loss regularizer used by PaLM/OLMo/Trinity) to `CrossEntropyLoss`. To make it observable, the trainer and validator now log the metrics a loss returns (both dropped them before).

```python
CrossEntropyLoss.Config(global_vocab_size=V, z_loss_weight=1e-4)  # None = off (default)
# loss = (sum_t CE_t + w * sum_t lse_t^2) / N
# logs:  ce_loss/mean, z_loss/mean                         (train)
#        validation_metrics/ce_loss/mean, .../z_loss/mean  (validation)
```

## What changed
**z-loss**
- `CrossEntropyLoss.Config.z_loss_weight: float | None`. When set, the loss adds `w * sum lse^2` before token normalization and returns `ce_loss/mean` and `z_loss/mean` (unweighted). When `None`, the path is unchanged.
- `cross_entropy_and_logsumexp` (new, `@local_compile("loss")`): returns `(CE, lse[T])` from one logsumexp. Under TP it uses `_LossParallelCrossEntropy(..., return_lse=True)`.
- `_LossParallelCrossEntropy(return_lse=False)`: optional second output. lse = `local_max + log(sum_exp)` from the existing all-reduces (no extra collective); backward adds `softmax * grad_lse` (still collective-free). `return_lse=False` is unchanged.

**Loss-metric logging**
- `combine_loss_metrics(metrics_list, *, mesh=None)` + `loss_metric_reduce_op(key)` in `loss.py`: one rule set by key suffix (`/mean`, `/frac`, `_mean`, `_frac` → sum; `/max` → max; `/min` → min), applied locally and, with `mesh`, across ranks.
- `ChunkedLossWrapper` now uses it instead of `_combine_chunk_metrics` (mechanical move).
- `Trainer.train_step`: combines loss metrics over microbatches and the loss mesh and logs them. `TODO(#4202)`.
- `Validator`: collects loss metrics on the non-PP path and on the PP path (one `loss_metrics` dict per microbatch via `pp_schedule.eval(loss_kwarg_mbs=...)`, filled by `_scalar_loss_fn`); combines across steps and ranks; divides sum-type keys by the global valid-token count; logs them as `validation_metrics/<key>`.
- LossFunction now types a Loss ((loss, metrics)); the raw mse_loss kernel annotation is fixed accordingly (typing only)

## User-facing changes
| Before | After |
| --- | --- |
| no z-loss | `CrossEntropyLoss.Config(z_loss_weight=...)` |
| loss metrics dropped by trainer and validator | logged (`ce_loss/mean`, `z_loss/mean`, `validation_metrics/...`) |
| — | with z-loss on, `loss_metrics/global_avg_loss` and `validation_metrics/loss` include `w * z`; compare `ce_loss/mean` against runs without z-loss |

<details><summary>Details</summary>

- **Parallelisms.** `lse` is `I@TP` and `V` on dp/cp, so `z = lse.square().sum()` is `P` on dp/cp like `ce`, and summing over the loss mesh (dp x cp, which excludes TP) is correct. - **TP backward.** `backward` now returns 6 grads. The existing 5-arg `apply` callers (`cross_entropy_loss`, `compute_logprobs`) still work because PyTorch trims trailing `None` grads. `grad_lse` is materialized as zeros if unused, so the `assert` holds.
- **MTP.** `MTPCrossEntropyLoss` builds its inner `CrossEntropyLoss` without `z_loss_weight`, so DeepSeek-V3 MTP recipes can't enable z-loss. That's fine until someone needs it.
- **Logging cost.** Each metric key adds one `dist_sum` (an all-reduce plus a D2H sync) on log steps. That is small with two keys. Stacking the keys into one all-reduce per op would avoid it growing with more keys.
</details>

- francesco-bertolotti · comment · 2026-11-02T20:47:29Z · [source](https://github.com/pytorch/torchtitan/pull/5736#issuecomment-6588072083)

> sorry I need to remind myself what z-loss is about

Z-loss is simply a regularization term used to prevent logit explosion:

$$
\mathcal{L} = \text{CE}(z, y) + \alpha (\log Z)^2,
\qquad
\log Z = \text{logsumexp}(z),
\qquad
\alpha \approx 10^{-5}
$$

where $$z$$ is the logit vector.

> Would you use it as a separate loss/regularizer?

I think it could be implemented using `aux_losses`, but I would advise against it.

The main reason is that Z-loss is computed from the log-sum-exp of the logits, which is already required by cross-entropy. Ideally, we should reuse the log-sum-exp computed by CE and derive the Z-loss from that value, rather than computing it twice.

> Would https://github.com/pytorch/torchtitan/pull/4202 be helpful for logging?

Generally speaking, **yes!** I think this is very important for understanding whether training is progressing cleanly or running into issues.

I would probably decouple metric collection from the logging step. Lightweight metrics, such as loss and gradient norm, could be collected every step, while other metrics could be collected less frequently (e.g. every 10 or 100 steps).

For Z-loss specifically, I don't think this approach would be directly suitable. The reason is that `tensor_logging.register_fwd_bwd` is tied to model modules, whereas Z-loss lives on the loss side.

It might be possible to make it work with `tensor_logging.register_fwd_bwd`, but this would require some additional work in https://github.com/pytorch/torchtitan/pull/4202.

Since `LossResult` already supports an extra metrics field, it would make more sense to handle these metrics in the trainer, following the same approach used for the loss itself:

https://github.com/pytorch/torchtitan/blob/4e8b4b88520c636651ace7749b18637e47d2dfe2/torchtitan/components/loss.py#L28

This can be shorter:

if self.z_loss_weight is None:
    loss, metrics = ce, {}
else:
    z = lse.square().sum()
    loss = ce + self.z_loss_weight * z
    metrics = {"ce_loss/mean": ce.detach(), "z_loss/mean": z.detach()}
if global_loss_token_counts is not None:
    loss = loss / global_loss_token_counts
    metrics = {k: v / global_loss_token_counts for k, v in metrics.items()}

This adds a second set of suffix-reduction rules for loss metrics. `ChunkedLossWrapper._combine_chunk_metrics` (`loss.py:942`) already reduces `/mean`, `/frac`, `_mean`, `_frac`, `/max` and `/min`. This block accepts only `/mean` and `/max`, so a loss metric that works inside `ChunkedLossWrapper` (e.g. `x/min` or `x/frac`) would make `train_step` raise on the first log step. The cross-rank step at L459-466 would also need to know about `/min`. Turn `_combine_chunk_metrics` into a module-level function in `loss.py` and use it for both the chunk and microbatch reductions, so there is one rule set.

Also note that metric reduction in core is meant to move to the distributed tensor logging framework (#4202; see the `TODO(#4202)` in `collect_aux_loss_metrics`). Add a matching TODO here so this ad hoc block gets removed when that lands.
