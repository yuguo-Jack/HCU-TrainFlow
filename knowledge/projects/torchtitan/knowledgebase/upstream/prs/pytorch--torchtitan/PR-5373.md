# Sample loss-parallel test data on a CPU generator

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5373) · state: closed · merged: True

## Original PR description

## Summary

`TestLossParallelCrossEntropy` samples its test data with
`torch.Generator(device=self.device_type)`. That errors on accelerators without
a device-side generator.

This change samples on a CPU generator and moves the tensors to
`self.device_type`, in both parity tests in
`tests/unit_tests/cpu/components/test_loss.py`.

The change is test-only. For CPU it is bit-identical, since `torch.Generator()`
and `torch.Generator(device="cpu")` produce the same stream. For CUDA, XPU and
other accelerators the tests still pass but they now see different sampled
values. As the tests are parity tests, they compare two computations on the same
data, so the result does not depend on which values were sampled. There is no
comparison against a stored literal, and the fixed seeds keep runs reproducible.
These tests no longer exercise a device-side generator on any device.

**Verdict: LGTM.** The change is small, only touches tests, and is correct. I found no blocking issues, just a few minor notes below.

### What I checked

1. **Semantics are kept.** Both tests (`test_loss_parallel_cross_entropy_parity` at `test_loss.py:452-461` and `test_vocab_parallel_policy_stats_parity` at `test_loss.py:563-569`) create the global tensors once and then pass them to `distribute_tensor(...)`. Two things make cross-rank consistency safe:
   - Every rank seeds the CPU generator with the same value, so every rank builds the same global tensor, just as it did before.
   - `distribute_tensor` broadcasts from `src_data_rank=0` by default, so the shards would match across ranks even if the data didn't.
2. **Draw order is unchanged.** The `randn` → `randint` → `rand` sequence still uses one generator, so CPU runs are bit-identical to before.
3. **The bf16 case is fine.** `torch.randn(..., dtype=torch.bfloat16, generator=cpu_gen)` works on CPU. The in-place edits after the move (`global_logits[3, vocab_size // 2:] = -torch.inf`, `global_labels[...] = IGNORE_INDEX`) run on the device tensor, which is correct.
4. **Nothing else needs this fix.** I grepped for other `torch.Generator(device=...)` uses:
   - `tests/unit_tests/cpu/models/deepseek_v4/test_deepseek_v4_dsa.py:28` hard-codes `device = torch.device("cpu")`, so it isn't affected.
   - `tests/unit_tests/gpu/...` (`test_sigmoid_gate.py`, `test_dist_moe.py`, `test_moe_aux_loss_compile.py`) are CUDA-only GPU tests. They're outside the scope of this PR.
   
   This PR therefore covers every device-agnostic CPU test that had the problem.

### Minor notes (non-blocking)

- **Bitwise parity now runs on different data on CUDA.** The first test asserts `torch.equal` between `loss_parallel()` and `_LossParallelCrossEntropy`. That parity should not depend on the data, since both paths run the same reductions in the same order. But it is a bitwise check, so the CUDA run now validates new values. The PR description says the tests still pass on CUDA. It would help to state in the description that this was actually run on a CUDA host, and not only on CPU or the fake-PG path, because that is the one place a data-dependent difference could show up.
- **Duplicated comment.** The two-line `# Sample on CPU and move to the test device...` comment appears in both tests. That's fine for test code. A tiny helper such as `_sample_on_cpu(...)` would be overkill for two call sites, so I'd leave it as is.
- **Slightly worse locality.** `torch.randn(T, vocab_size, generator=generator).to(self.device_type)` allocates on the host and then copies. The tensors are at most 128×32003, so the cost is negligible.

There are no Unicode or lint concerns in the added comments; they are ASCII only, as `CLAUDE.md` requires. No numerics validation is needed, since the change only affects tests.
