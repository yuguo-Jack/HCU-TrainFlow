# [dsv4][perf] Compile the mHC Sinkhorn loop with one tensor per entry

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5199) · state: open · merged: False

## Original PR description

**TLDR:** Under compile, run mHC's Sinkhorn loop on one `[T]` tensor per matrix entry so it fuses: 16k step -2.3%, for +42 s of cold compile.

**Problem**
1. **Sinkhorn.** `HcPre` normalizes a `[T, 4, 4]` matrix by rows, then columns, for several steps.
2. **Transposed reads.** Each column sum reads the previous step's output transposed.
3. **One kernel per step.** So compiled, Inductor emits one kernel per normalization step.
4. **Cost.** At 16k, 1.8 ms of the 78.2 ms step (Results).

**Solution**
1. **Per entry.** Under compile, the 16 entries are 16 `[T]` tensors; row and column sums are plain adds.
2. **Fused.** The whole loop becomes a few kernels.
3. **Gate.** `is_compiling()`: the per-entry form is far slower in eager.
4. **Unchanged:** eager keeps the tensor form; the math is bitwise the same in fp64.

```text
eager:     m[T,4,4] -> row norm -> col norm (transposed read) -> ...     (unchanged)
compiled:  m00[T], m01[T], ..., m33[T] -> sums of 4 tensors -> ...       (fuses)
```

**Results**
```text
DeepSeek-V4 Flash layers 4+5, fwd+bwd wall, 1x GB300, FA4, median of fresh processes within 1% of best
measured with #5157's moe_dispatch_combine applied (it sat before this PR in the original stack)
16k   78.23 -> 76.40 ms  (-2.3%)
4k    34.73 -> 32.77 ms  (-5.6%)
cold compile, 2-layer slice, caches off, 1 process   67.3 -> 109.4 s  (+42 s)
correctness: per-entry vs tensor form bitwise in fp64 (new CPU test)
graphs: unchanged (HcPre 3)
```

You may ask: why not 4 row tensors? Slower.
NOTE: trade-off: 2-6% of the 2-layer step vs about 40 s more cold compile per process; warm caches remove it.
NOTE: not yet measured under CUDA graphs. Not tested: loss curve, multi-GPU.

**Test plan**
`pytest tests/unit_tests/cpu/test_deepseek_v4_mhc.py`

Stack: 5 of 7. Branch `felipemello1/lcp/dsv4-5-sinkhorn-per-entry`.
