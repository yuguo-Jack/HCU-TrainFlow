## Agent details

**TLDR:** A recipe that sets `Trainer.Config.tensor_logger` gets 8 statistics (rms, abs_max, kurtosis, ...) of each tensor the model code logs, and of its gradient, every `log_freq` steps. Each statistic covers the whole tensor over all ranks, under FSDP, TP, CP, PP and EP. Unset (the default), loss and grad_norm stay bitwise equal to main wherever main repeats itself bitwise. On llama3 8B (FSDP 4, 4 GB300), a recorded step is 3.7% slower than main, and the other steps are as fast as main.

```text
main:     one value per step for the whole model (loss, grad_norm, lr, aux-loss means)
this PR:  + 8 fields per logged tensor, every log_freq steps, e.g.
            tensor_logger/layers.3.attention.xq.fwd.rms   0.92    forward value
            tensor_logger/layers.3.attention.xq.bwd.rms   1e-05   its gradient

on a recorded step:
  forward    log_fwd_bwd(self, xq=xq_THK): a kernel adds xq's 7 sums + 1 max into its row
  backward   a gradient hook runs the same kernel on xq's gradient
  after      collect(): one SUM and one MAX all-reduce over all ranks -> the published fields
```

```python
# recipe
config.tensor_logger = TensorLogger.Config(log_freq=10)
# GQAttention.__init__
tensor_logger.register_fwd_bwd(self, "xq", "xk", "xv", "head_out")
# GQAttention.forward (head_out is logged after attention)
tensor_logger.log_fwd_bwd(self, xq=xq_THK, xk=xk_THK, xv=xv_THV)
```

A recorded step is a step that is a multiple of `log_freq`. Every other step is an off step.

### Why

1. **Today.** Main publishes one value per step for the whole model: loss, grad_norm, lr and each aux loss's mean. None is per layer.
2. **The gap.** When one layer's activations spike or die, loss and grad_norm move late, and they do not say which layer.
3. **Shards.** A local hook sees only part of a tensor. FSDP and DP split the batch, CP the sequence, TP the heads or hidden size, EP the tokens. Under PP, only one rank (the first rank of the last stage) publishes metrics.
4. **Main already waits for it.** `models/common/aux_loss.py` has a TODO to move its metric reduction onto this logger.
5. **This PR.** Each logged tensor gets a row: 7 sums and 1 max in a buffer built at init. Each rank adds its shard into the row. After backward, a SUM and a MAX all-reduce merge the rows, so each row describes the whole tensor.

### What changed

- `torchtitan/observability/tensor_logger/` (new):
  - `statistics.py`: the custom op `torchtitan::accumulate_tensor_statistics` and its CPU reference kernel.
  - `statistics_triton.py`: the GPU kernel. A device flag makes it exit at once on off steps.
  - `api.py`: `TensorLogger` and its `Config(log_freq)`, plus `register_fwd`, `register_fwd_bwd`, `log_fwd`, `log_fwd_bwd`.
  - `README.md`: how to enable it, the callsite rules, the fields, cost and limits.
- `trainer.py`: the field `tensor_logger: TensorLogger.Config | None = None`, config checks, `maybe_record(step)` around forward and backward, `collect()` into the step's metrics, `close()`.
- Model callsites, a few lines each: the shared `Decoder`, `GQAttention`, `DenseFeedForward` and `MoE`. Models that override those forwards make the same calls: deepseek_v3 (MTP), deepseek_v4, kimi_k2_7, kimi_k3, muse_glimmer, muse_spark, qwen3_5.
- Callsite rules (README): stay outside `local_compile` regions, and never log a partial sum (`log_fwd_bwd` takes no replicated tensor, whose gradient is a partial sum).
- These raise `ValueError` at config time: PP schedules that split the backward (and schedule CSV files), `sdc_replayer`, `GraphTrainer`, `FaultTolerantTrainer`, and a `log_freq` that is not a multiple of `metrics.log_freq`.

You may ask:
- Why calls in `forward`, not module hooks? A hook sees only a module's inputs and outputs, so the logger would depend on each model's submodule names and output tuples (`qkv_linear` returns xq, xk and xv together). A call in `forward` names the tensor where it is made, the same way in every model.
- Why not `full_tensor()` and torch stats on one rank? That gathers every logged activation, MBs per tensor per step. Here each row all-reduces 32 B.
- Why a Triton kernel, not torch ops? A captured graph replays every call on every step. A flag read inside the kernel skips the work with no host sync and no second graph.
- Why register rows in `__init__`? Graph capture needs the buffer at a fixed address, and the all-reduces need the same row order on every rank, before step 1.
- Why float32 sums? Half the memory and all-reduce bytes of float64. `numel` stays exact up to 2^24 elements per row and step, and keeps about 7 significant digits above that.

### Numerics / performance

Numerics: with the logger off or on, loss and grad_norm are bitwise equal to main in every cell where main repeats itself bitwise. The cells that differ are the 4 where two main runs also differ.

Runs compared: main; off = this PR, field unset; on = `log_freq=2`; probe = a test-only logger that logs known tensors and raises on any wrong statistic. A cell is one model x layout x mode. Most cells use flex attention, which repeats bitwise on main. Four cells use varlen attention: one llama3 and one deepseek_v3 cell on purpose, and muse_glimmer multimodal and kimi_k3 by their recipe default.

```text
this PR c6267a626 vs main 6a2292d00 (= base 828961319 except .claude/CLAUDE.md), GB300
10 steps per run (step-time cells 30-40), 61 cells, 236 runs (212 + 24 oracle)
check                                     cells   result
logger off vs main: loss, grad_norm       43      bitwise equal in 39; 4 within main's own noise (1)
logger off vs main: peak memory           43      equal in 38; +512 B in 4 (2); gpt_oss -35 KB, while two
                                                  main runs differ by up to 0.95 GiB on some steps
logger on vs logger off: loss, grad_norm  42      bitwise equal in 40; 2 within noise (1)
probe vs logger off: loss, grad_norm      51      bitwise equal in 48; 3 within noise (1)
logger on: extra peak memory              43      = its 3 buffers, each rounded up to 512 B: 3072 B for
                                                  73 rows (llama3 debug), 2048 B for 35 rows (deepseek_v3
                                                  debug); +512 B more on 2 cells (2); llama3 8B +16 KB for
                                                  13.5 KB of buffers (3)
probe: exact statistics                   55      exact on every recorded step of all 55 runs
1-GPU oracle                              20      8336 step-1 statistics agree with the 1-GPU run (4)

(1) llama3 and deepseek_v3 with varlen attention, gpt_oss, flux: two main runs differ within 10 steps
    (gpt_oss: loss up to 1.2e-3, grad_norm up to 2.3e-2 relative). This PR stays within 2x main's own
    difference, and step-1 loss is bitwise equal.
(2) One allocator block. Two main runs differ by the same 512 B, and the same main commit run from
    another directory is also +512 B.
(3) TensorBoard stores memory as float32 GiB, so near 74 GiB a difference is known to 8 KB.
(4) fp32, same seed weights, and every DP rank gets the 1-GPU batch, so forward fields equal the 1-GPU
    run and gradients are 1/DP of it. Counts exact; abs_mean, rms, abs_max within 1e-3 relative;
    kurtosis within 1e-2 of (kurtosis + 3); zero_frac within 1e-6 (forward) or 1e-4 (gradient).

models:  llama3, deepseek_v3 (+MTP), deepseek_v4, qwen3, qwen3 MoE, qwen3_5, qwen3_6, gpt_oss,
         kimi_k2_7, kimi_k3, muse_glimmer multimodal, muse_spark, flux (logger off only)
layouts: 1 GPU, FSDP 2/4, HSDP 2x2, TP 2 (with and without SP), CP 2, EP 2 (with FSDP or TP),
         PP 2 (1F1B, Interleaved1F1B, GPipe, LoopedBFS), TP2xCP2, TP2xCP2xEP2, PP2xTP2, PP2xTP2xEP2,
         FSDP4xEP2
modes:   default (accelerator graphs, local compile, default remat), eager, full remat, gradient
         accumulation 2/4, graphs per microbatch group, SPMD type checking, validation every 2 steps
         (also with PP)
```

```text
llama3 8B, FSDP 4 on 4 GB300, accelerator graphs on, flex, W&B + TensorBoard on, one run per arm
median step time over steps 4-30          main       this PR
logger off, all steps                     650.3 ms   646.7 ms   -0.6%
logger on (log_freq 2), off steps         649.0 ms   649.5 ms   +0.1%   (odd steps)
logger on (log_freq 2), recorded steps    651.8 ms   676.0 ms   +3.7%   (even steps)
logger on: 385 rows, 3080 extra scalars per recorded step
```

NOTE: In a CPU-bound run, the metric loggers pay for the extra scalars. Example: llama3 debug, eager, FSDP 2, `log_freq=2`, TensorBoard writing 584 extra scalars. Recorded steps took 103.0 vs 85.1 ms on main, and the off step after each took 118.6 vs 86.9 ms. With no metric logger (times from the console tokens/s), recorded steps took 97.7 vs 96.0 ms, and off steps matched main (89.7 vs 89.8 ms).
NOTE: Not run: 8-GPU 3D/4D layouts (the test machine has 4 GPUs, and no CI entry enables the logger on 8 GPUs), multi-node, ROCm. All runs used GB300 GPUs.

### Testing

- `pytest tests/unit_tests/cpu/observability/test_tensor_logger.py`: each forward counts once under Full and Default remat; cadence and derived fields; a parameter passed to `log_fwd_bwd` raises; split-backward and CSV PP schedules, `sdc_replayer` and a bad `log_freq` raise.
- `pytest tests/unit_tests/gpu/observability/test_tensor_logger.py`: the Triton kernel matches the CPU kernel (fp32, bf16); a graph captured on an off step records on replay; every callsite runs once per microbatch for llama3, deepseek_v3, kimi_k3 and muse_glimmer.
- Integration `pp_looped_1f1b`: `llama3_debugmodel_pp4_interleaved_1f1b` now always runs with the probe (real process groups, `log_freq=1`). It fails on a wrong row order across stages, double counts from PP metadata inference, or a wrong MAX.
- Integration `2d_eager_no_sp`: `llama3_debugmodel_tp2_no_sp` now always runs with the logger on (`log_freq=2`) under SPMD type checking. It fails if a logging call or gradient hook breaks SPMD type checking (`register_hook` has no sharding rule).
- `test_ft_rejects_tensor_logger`: FaultTolerantTrainer with `tensor_logger` raises at config time. GraphTrainer raises too, checked by hand (no unit test).
- Stress matrix: the Numerics block above.

**What this PR does.** Adds an opt-in `TensorLogger` (`Trainer.Config.tensor_logger`, default off) that publishes 8 statistics per logged tensor and its gradient every `log_freq` steps. Model modules register row names in `__init__` and log in `forward`; each rank accumulates into fixed per-row buffers via a Triton kernel (a device flag skips off steps inside captured graphs), and `collect()` runs one SUM and one MAX all-reduce on recorded steps. Unsupported combinations (split-backward PP schedules, schedule CSVs, `sdc_replayer`, GraphTrainer, FaultTolerantTrainer, `log_freq` not a multiple of `metrics.log_freq`) raise at config time.

**Example.**
```python
config.tensor_logger = TensorLogger.Config(log_freq=10)
# publishes e.g. tensor_logger/layers.3.attention.xq.fwd.rms = 0.92
#                tensor_logger/layers.3.attention.xq.bwd.rms = 1e-05
```

The probe's `collect()` asserts that every registered row has `observation_count == owners x calls_per_step`, so a dropped call fails the run. All of these pass at this head.

The trade-off: that matrix is not in CI. If maintainers want CI coverage for these four, adding them to the parametrize list with per-model setup is a follow-up.
