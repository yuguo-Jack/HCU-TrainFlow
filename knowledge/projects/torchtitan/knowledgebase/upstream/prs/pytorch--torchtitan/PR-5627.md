# [perf] Move all-gather comm. on the FSDP compute stream

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5627) · state: open · merged: False

## Original PR description

## Context

Hello TorchTitan team,

Over the past few days, I've been investigating CUDA allocation retries that were noticeably slowing down training steps. I traced the issue to memory fragmentation across the multiple CUDA streams used by FSDP.

While looking for a solution, I came across [this PyTorch issue](https://github.com/pytorch/pytorch/issues/147168), which mentions enabling `_set_unshard_async_op(True)`. I tried this approach, and the results were very promising.

However, `_set_unshard_async_op` appears to be a private, undocumented FSDP method, and I'm not familiar enough with FSDP's internals to determine whether enabling it is safe. I'd appreciate some guidance on a few questions:

- **Stability:** Is `_set_unshard_async_op(True)` considered stable, or could enabling it introduce subtle issues or unexpected behavior?
- **Future compatibility:** Is this API likely to change or be removed in future PyTorch versions?
- **Prefetch configuration:** Claude suggested that enabling `_set_unshard_async_op` requires explicitly configuring `set_modules_to_forward_prefetch` and `set_modules_to_backward_prefetch`. In TorchTitan, these are explicitly configured only when `EP > 1`. Is there a specific reason for this conditional configuration, or would it make sense to configure them unconditionally?

To illustrate the change and its potential benefits, I've put together this PR.

## Performance results

In my experiments, enabling `model._set_unshard_async_op(True)` produced the following results:

- **Peak reserved GPU memory:** Decreased from 42.08 GB to 37.62 GB, a reduction of approximately 10.6%.
- **Average throughput:** Decreased slightly from 3,771 to 3,745 tokens/s, a reduction of approximately 0.7%.
- **Identical loss:** Loss remained bit identical with or without `model._set_unshard_async_op(True)` for the first 30 steps.

In addition to addressing the CUDA allocation retries, the reduction in memory usage seems substantial, with only a small throughput trade-off.

I'd love to hear your thoughts on whether this approach is safe and appropriate for TorchTitan, and whether there are any potential pitfalls I should be aware of.

Thanks!

import os

import torch

import torchtitan.components.data
import torchtitan.components.data.text_datasets
import torchtitan.components.loss
import torchtitan.components.optim
import torchtitan.config
import torchtitan.distributed.activation_remat
import torchtitan.models.common
import torchtitan.models.common.config_utils
import torchtitan.models.common.decoder_sharding
import torchtitan.models.llama3
import torchtitan.models.llama3.flavors
import torchtitan.observability.logging
import torchtitan.observability.metrics
import torchtitan.trainer
import torchtitan_recipes.data

# Toggle with UNSHARD_ASYNC=0/1 to compare runs.
unshard_async = os.environ.get("UNSHARD_ASYNC", "1") == "1"

# Few, very wide layers and short sequences: FSDP all-gather buffers are large
# relative to activations, so the per-unit buffer FSDP keeps alive in forward
# without unshard_async is a visible share of peak memory.
seq_len = 2048
dim = 8192
n_layers = 4
n_heads = 64
n_kv_heads = 8
vocab_size = 128256
attn_backend = "varlen"

parallelism = torchtitan.config.ParallelismConfig(
    data_parallel_replicate_degree=1,
    data_parallel_shard_degree=-1,
    fsdp_unshard_async_op=unshard_async,
)

model = torchtitan.models.llama3.Llama3Model.Config(
    max_context_length=seq_len,
    dim=dim,
    vocab_size=vocab_size,
    tok_embeddings=torchtitan.models.common.Embedding.Config(
        num_embeddings=vocab_size,
        embedding_dim=dim,
        param_init=torchtitan.models.llama3.flavors._EMBEDDING_INIT,
        sharding_config=torchtitan.models.common.decoder_sharding.token_embedding_sharding_config(
            enable_sp=parallelism.enable_sequence_parallel
        ),
    ),
    norm=torchtitan.models.common.RMSNorm.Config(
        normalized_shape=dim,
        param_init=torchtitan.models.llama3.flavors._NORM_INIT,
        sharding_config=torchtitan.models.common.decoder_sharding.pre_lm_head_norm_sharding_config(
            enable_sp=parallelism.enable_sequence_parallel
        ),
    ),
    lm_head=torchtitan.models.common.Linear.Config(
        in_features=dim,
        out_features=vocab_size,
        param_init=torchtitan.models.llama3.flavors._output_linear_init(dim),
        sharding_config=torchtitan.models.common.decoder_sharding.lm_head_sharding_config(),
    ),
    layers=torchtitan.models.llama3.flavors._build_llama3_layers(
        n_layers=n_layers,
        dim=dim,
        n_heads=n_heads,
        n_kv_heads=n_kv_heads,
        hidden_dim=torchtitan.models.common.compute_ffn_hidden_dim(
            dim, multiple_of=4096, ffn_dim_multiplier=1.2
        ),
        rope=torchtitan.models.common.ComplexRoPE.Config(
            dim=dim // n_heads,
            max_context_length=seq_len,
            theta=500000,
            scaling="llama",
        ),
        attn_backend=attn_backend,
        enable_sp=parallelism.enable_sequence_parallel,
    ),
)

config = torchtitan.trainer.Trainer.Config(
    parallelism=parallelism,
    dump_folder=f"outputs/llama3_debug_ua{unshard_async}",
    model=model,
    loss=torchtitan.components.loss.ChunkedLossWrapper.Config(
        loss_fn=torchtitan.components.loss.CrossEntropyLoss.Config(
            global_vocab_size=torchtitan.models.common.config_utils.decoder_vocab_size(model),
        ),
    ),
    hf_assets_path="./tests/assets/tokenizer",
    optim=torchtitan.components.optim.Optim.Config(
        optimizer=torchtitan.components.optim.OptimizersContainer.Config(
            optimizers=[
                # Exclude the input/output embeddings from weight decay.
                torchtitan.components.optim.AdamW.Config(
                    pattern=r"(?:tok_embeddings|lm_head)\.",
                    lr=0.0008,
                    betas=(0.9, 0.95),
                    eps=1e-08,
                    weight_decay=0.0,
                ),
                # Everything else: standard AdamW with weight decay.
                torchtitan.components.optim.AdamW.Config(
                    pattern=r".*",
                    lr=0.0008,
                    betas=(0.9, 0.95),
                    eps=1e-08,
                    weight_decay=0.1,
                ),
            ],
        ),
        lr_scheduler=torchtitan.components.optim.LRSchedulersContainer.Config(
            warmup_steps=2,
            decay_ratio=0.8,
            decay_type="linear",
            min_lr_factor=0.0,
        ),
    ),
    training=torchtitan.config.TrainingConfig(
        num_tokens_per_microbatch_per_dp_rank=seq_len,
        max_context_length=seq_len,
        steps=int(os.environ.get("STEPS", "30")),
        disable_cuda_graphs=True,
        enable_cpu_offload=False,
    ),
    dataloader=torchtitan.components.data.GrainDataLoader.Config(
        max_num_documents=torchtitan_recipes.data.c4_document_capacity(seq_len),
        dataset=torchtitan.components.data.ConcatThenSplitPackingConfig(
            dataset=torchtitan.components.data.SingleDatasetConfig(
                source=torchtitan.components.data.HuggingFaceRandomAccessSource.Config(
                    path="json",
                    split="train",
                    load_dataset_kwargs={
                        "data_files": "./tests/assets/c4_test/data.json",
                    },
                ),
                processor=torchtitan.components.data.text_datasets.TextProcessor.Config(),
                post_filters=(lambda sample: sample is not None,),
            ),
        ),
        shuffle=False,
    ),
    activation_remat=torchtitan.distributed.activation_remat.DefaultActivationRematConfig(),
    metrics=torchtitan.observability.metrics.MetricsProcessor.Config(
        enable_tensorboard=True,
        enable_wandb=False,
        log_freq=1,
    ),
    checkpointer=None,
    validator=None,
    debug=torchtitan.config.DebugConfig(
        save_config_file="config.json",
        seed=42,
        deterministic=True,
    ),
)

if __name__ == "__main__":
    # Mirrors torchtitan.train.main(), minus the CLI config loader.
    torchtitan.observability.logging.init_logger()
    trainer = config.build()
    try:
        trainer.train()
    finally:
        trainer.close()
        if torch.distributed.is_initialized():
            torch.distributed.destroy_process_group()

Following up with a concrete scope that I think can land. I put up pytorch/pytorch#202343 to make this public as `FSDPModule.set_unshard_async_op`. The private `_set_unshard_async_op` stays as is, so this PR can call it now with a TODO and switch to the public name once that lands.
I'd scope the knob to what the explicit prefetch chain covers today:
**1. Opt in per recipe, plain decoders only.** Keep the default `False`; no recipe needs to change in this PR. Recipes that enable it later should be plain decoders (llama3, qwen3, gpt_oss, DeepSeek-V3/V4 without MTP). There each FSDP unit runs once per forward in the order `tok_embeddings -> layers -> norm/lm_head`, which is exactly the chain `apply_fsdp_to_decoder` prefetches.
**2. State the scope in the docstring** of `fsdp_unshard_async_op`, e.g. append:
```python
    Supported for decoders whose FSDP units run once per forward in the order
    tok_embeddings -> layers -> norm/lm_head, which is the explicit prefetch
    chain. Raises with MTP layers. Multimodal encoders are not in the chain,
    so their all-gathers do not overlap with compute.
```
**3. Don't drop the knob silently on the MTP path.** `MTPDecoder._apply_fsdp` and DeepSeek-V4's `_apply_fsdp` call `apply_fsdp_to_mtp_decoder`, which never forwards the knob, so DeepSeek-V3, DeepSeek-V4 and Kimi K2.7 ignore it today. Please pass it through and raise only when MTP layers are present: `tok_embeddings` runs twice per forward there, and the chain doesn't cover the second call.
```python
# torchtitan/models/deepseek_v3/mtp.py
def apply_fsdp_to_mtp_decoder(
    ...
    symm_mem_scope: FSDPSymmMemScope = None,
    unshard_async_op: bool = False,
) -> None:
    if unshard_async_op and model.mtp_layers is not None:
        raise ValueError(
            "fsdp_unshard_async_op does not support MTP layers yet: "
            "tok_embeddings runs twice per forward and the forward "
            "prefetch chain does not cover its second call."
        )
    ...
        apply_fsdp_to_decoder(
            ...
            unshard_async_op=unshard_async_op,
        )
```
Both callers then pass `unshard_async_op=parallelism.fsdp_unshard_async_op`. Flux wraps its own units, so its `_apply_fsdp` should reject the knob too:
```python
        if parallelism.fsdp_unshard_async_op:
            raise ValueError("fsdp_unshard_async_op is not supported for Flux.")
```
**4. Keep implicit prefetching when the knob is off.** Making explicit prefetching unconditional changes every EP=1 run, which would need its own loss and throughput validation. I'd restore the early return in `apply_fsdp_to_decoder` with the new condition:
```python
    # Explicit prefetching: D2H syncs in EP break implicit prefetching, and
    # all-gathers issued from the compute stream (unshard_async_op) only
    # overlap with compute if they are issued ahead of time.
    if ep_degree == 1 and not unshard_async_op:
        return
```

Thanks for the review! Addressed all points:

- **Public API:** switched from `_set_unshard_async_op(True)` to `set_unshard_in_current_stream(True)`. This depends on pytorch/pytorch#202343, so runs with the knob on will fail until it lands in a nightly. Docstrings now describe the knob as "all-gathers on the current stream" rather than `async_op`.
- **Opt-in:** `parallelism.fsdp_unshard_async_op` defaults to `False` and no recipe enables it.
- **Docstring scope:** states the supported unit order (`tok_embeddings -> layers -> norm/lm_head`), that it raises for MTP and Flux, and that multimodal encoder all-gathers are not prefetched.
- **MTP:** `apply_fsdp_to_mtp_decoder` takes `unshard_async_op` and forwards it to `apply_fsdp_to_decoder`. It raises `ValueError` when it is set and `mtp_layers` is not `None`. `MTPDecoder._apply_fsdp` and DeepSeek-V4's `_apply_fsdp` pass `parallelism.fsdp_unshard_async_op`. Updated `test_deepseek_v4_mtp.py` for the new argument.
- **Flux:** `_apply_fsdp` raises `ValueError` when the knob is set.
- **Implicit prefetch:** restored the early return as `if ep_degree == 1 and not unshard_async_op: return`, so behavior with the knob off is unchanged from `main`.

Question: should the knob follow the upstream name, i.e. `fsdp_unshard_async_op` -> `fsdp_unshard_in_current_stream`?
