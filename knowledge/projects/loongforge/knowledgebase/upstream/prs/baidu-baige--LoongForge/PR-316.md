# [vla] fix: release loader-cached GPU memory before eval warmup

[Upstream PR](https://github.com/baidu-baige/LoongForge/pull/316) · state: closed · merged: False

## Original PR description

## Change Summary

- **What changed?**
  - Added `_release_loader_cached_memory()` to the standalone eval policy server and
    call it once after `build_model_spec()`, before warmup. It runs
    `torch.cuda.empty_cache()` and logs the resulting reserved-memory drop.
  - Added unit tests covering the CUDA and non-CUDA paths.
- **Which issue or requirement does this address?**
  - Eval factories that build in fp32 and cast to bf16 (pi05, xvla, GR00T-N1.6/N1.7,
    DreamZero) keep the transient fp32 copy and the staged checkpoint tensors in
    PyTorch's caching allocator. For pi0.5 RoboTwin, `nvidia-smi` reported 15.9GB
    after load while the live weights were 8.3GB, which reduced the headroom left
    for co-located GPU simulators.
  - Releasing those blocks drops the pi0.5 load footprint from 15.9GB to 8.7GB,
    freeing ~7GB per card for co-located sims. At the measured ~5.5GB/sim for
    RoboTwin, that is 1-2 more sims per card. Co-location still works without the
    release, but with a lower packing limit and a higher OOM risk.
- **Which modules are affected?**
  - `loongforge/embodied/eval/servers/loongforge_server.py`
  - `loongforge/embodied/eval/unit_tests/test_server_memory_release.py`
  - Applies to every eval model factory; no model-specific code changed.

## Reviewer Notes

- The call happens **before** warmup, so warmup activations repopulate the allocator
  with inference-sized blocks. Releasing after warmup would free those too and force
  a fresh `cudaMalloc` on the first real request.
- `nvidia-smi` after load is ~8.7GB (7.72 GiB live weights + ~0.7 GiB CUDA
  context/workspace), so `vram_model_gb` should be budgeted as ~10GB including
  warmup activations.
- No correctness or steady-state latency change; capacity only.
- Follow-up (not in this PR): `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` for
  long-running multi-process servers; weight tying for the duplicated 0.53B `lm_head`
  in pi0.5 (~1GB bf16).
