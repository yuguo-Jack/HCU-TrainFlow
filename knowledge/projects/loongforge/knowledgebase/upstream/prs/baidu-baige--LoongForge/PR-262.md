# [vla, data] perf: decode LeRobotV2 multi-frame observations in one container open

[Upstream PR](https://github.com/baidu-baige/LoongForge/pull/262) · state: closed · merged: True

## Original PR description

## Change Summary

- **What changed**: `LeRobotV2Dataset._decode_video_frames` now decodes all requested frames in a single container open via the existing batched backend API (`decode_video_frames_by_timestamps`), instead of one `av.open` + `seek` per frame (a list comprehension over `_decode_video_frame`).
- **Which issue it addresses**: redundant per-frame container re-opening in the LeRobot v2.0/v2.1 dataset path. For FastWAM's LIBERO geometry (`num_video_frames=9`, `action_video_freq_ratio=4`, 2 cameras) that is 18 container opens per sample.
- **Which modules are affected**: `loongforge/embodied/data/datasets/lerobot_dataset.py` only. Scope is `LeRobotV2Dataset`; `LeRobotV3Dataset` and `cosmos3/droid_lerobot_dataset.py` are unaffected (they already go through the upstream batched API).

**Bit-identity** (the critical check for a data-pipeline change):

- `max|d| = 0` between the previous per-frame path and the new batched path: 48 samples x 8 episodes x 2 cameras = 528 arrays, overall sha256 equal, including episode-tail clamped duplicate frames.
- Also `max|d| = 0` at frame level for both the `pyav` and `torchcodec` backends, 2 cameras x 3 episodes.

**Performance** (8x A800-80GB):

- Single-process microbenchmark (real LIBERO mp4, 9 frames): **147.8 -> 81.7 ms** per camera sample (**1.81x**).
- End-to-end loader-only A/B (16 workers, batch 16, 60 batches; identical checkout with only the decode call toggled): **185.9 -> 204.7 samples/s (+10.1%)**.
- Smoke: 5 training iterations on this branch (single LIBERO suite, `--lerobotdataset-version v2.1`) — finite loss / grad norm, 0 NaN.

## Reviewer Notes

- This does **not** speed up FastWAM training today: the data pipeline is not the bottleneck (batch-generator ~17.65 ms against a ~1507 ms step, ~1.2% waiting; pipeline capacity 175.5 samples/s vs 85.0 samples/s demand). The value is CPU/IO efficiency (9 fewer container opens per camera per sample, on every rank) and scaling headroom.
- The batched `pyav` path decodes the whole `[min(ts), max(ts)]` window sequentially and selects by nearest timestamp, whereas `torchcodec` jumps to exact frames. That is a pre-existing, deliberate trade-off (see the `stream.thread_count = 1` note in `video_backends.py`), not introduced here.
- `decode_video_frames_by_timestamps` was previously dead code on this path; this change wires it up.
