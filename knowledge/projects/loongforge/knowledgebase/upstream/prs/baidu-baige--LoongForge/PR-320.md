# [vla] fix: save ZeRO optimizer state asynchronously (#308)

[Upstream PR](https://github.com/baidu-baige/LoongForge/pull/320) · state: closed · merged: True

## Original PR description

# fix: save ZeRO optimizer state asynchronously ([issue #308](https://github.com/baidu-baige/LoongForge/issues/308))

## Problem

With `--save-format dcp --async-save`, only the DCP shards are written asynchronously. The ZeRO optimizer state (`zero_optimizer/rank_*.pt`) is still written synchronously, so every save blocks training. In the issue, a 6B FastWAM run blocks for about 162s per save.

## Cause

ZeRO state is rank-local and cannot be resharded, so it is excluded from the DCP state dict and written separately by `torch.save` in `_save_zero_optimizer_state`. `--async-save` only covers `dcp.async_save`. Non-ZeRO optimizer state is already part of DCP and is not affected.

## Solution

Follow `dcp.async_save`: take a CPU snapshot synchronously, then write it in a background thread. Only `loongforge/embodied/distributed/checkpoint.py` is changed.

- `_save_zero_optimizer_state` gains an `async_save` flag. When set, it snapshots the state with `_cpu_snapshot`, submits the write to a single-worker thread pool, and returns a future. When unset, behavior is unchanged.
- `_save_dcp` merges the DCP and ZeRO futures with `_merge_futures` and reuses the existing `flush_pending_save` flow. The merged future completes only after all inputs settle, and handles cancellation. If `dcp.async_save` raises synchronously, it waits for the ZeRO write first. The non-ZeRO path returns `dcp_future` unchanged.
- `resume_meta.json` is still written only after everything is on disk. No new options; checkpoint format unchanged.

Cost: each rank holds an extra CPU copy of its ZeRO state while the save is in flight.

## Test Results

FastWAM DDP + ZeRO-1 (`run_fastwam_sft_ddp_zero1_finetune.sh`), single node with 8 GPUs, bs16, `SAVE_FORMAT=dcp ASYNC_SAVE=1 ZERO_MASTER_PARAM_DTYPE=fp32`, 160 steps with a save every 40 steps, local NVMe. Each checkpoint is 13GB of DCP plus 68GB of `zero_optimizer`. Baseline is the parent commit.

| Checkpoint | Blocking before | Blocking after |
|---|---|---|
| steps_40 | 17.21s | 11.97s |
| steps_80 | 22.15s | 9.92s |
| steps_120 | 15.29s | 8.86s |
| steps_160 | 14.50s | 8.84s |
| Mean | 17.3s | 9.9s |

- Background write takes about 7.7s and step time is 1.37s, both unchanged.
- Peak host memory rises by 68GB per node (386GB to 454GB).
- `rank_*.pt` keys, shapes, and dtypes match the baseline. Resuming from steps_80 works, and the loss difference is within run-to-run noise.
- The remaining blocking comes from the GPU-to-CPU snapshot and DCP staging. Slower storage gives a larger gain.

Other save paths (20 steps each, saving every 10 steps, then resuming):

| Scenario | Result |
|---|---|
| dcp + async + non-ZeRO | Training and resume OK |
| dcp + sync + ZeRO | Training and resume OK; the new snapshot path is not used |
| dcp + async + ZeRO + `--no-save-training-state` | OK; no `zero_optimizer/` written |
| safetensors + `--async-save` + ZeRO | `--async-save` is ignored as expected |
