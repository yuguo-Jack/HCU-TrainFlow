- katsugtgz · comment · 2026-11-04T08:01:40Z · [source](https://github.com/baidu-baige/LoongForge/pull/318#issuecomment-6625779433)

Title fixed. On the smoke test: added one, and it reproduces a real failure. The bump is not the cause.

The `NLTK_DATA` branch of `Encoder.initializer` loads the legacy punkt pickle through a `file:` URL. On nltk 3.10.4 that load fails with `_pickle.UnpicklingError: global 'copy_reg._reconstructor' is forbidden` (`nltk/picklesec.py` rejects the globals used by the legacy pickle). The non-`NLTK_DATA` path still works, because `nltk.load("nltk:tokenizers/punkt/english.pickle")` resolves to the punkt_tab based `PunktTokenizer`.

Measured on Python 3.12, punkt downloaded fresh into a private `NLTK_DATA` dir:

- nltk 3.10.4, `file:` URL into `NLTK_DATA`: `UnpicklingError`
- nltk 3.10.3, same load: `UnpicklingError` (so 3.10.3 has the same failure and this PR does not regress it)
- nltk 3.10.4, `nltk:tokenizers/punkt/english.pickle`: loads as `PunktTokenizer`, sentence split works

Added `tests/test_preprocess_nltk_data_smoke.py`, which mirrors the tool's punkt download and the `NLTK_DATA` load branch. It is red today for the reason above. It skips when nltk refuses the download because the `NLTK_DATA` path is not private: nltk 3.10 `pathsec` rejects world-writable ancestors, so plain CI tmp dirs cannot exercise this code path.

A fix would be to prepend `$NLTK_DATA` to `nltk.data.path` and load the punkt resource the normal way instead of building a `file:` URL to the pickle, or to move to `punkt_tab`. That is a source change outside this dependency bump, so leaving it with you. Suggest keeping the bump: same behavior on 3.10.3 and 3.10.4 for this path, and it clears GHSA-j456-xh4h-cpf2.
