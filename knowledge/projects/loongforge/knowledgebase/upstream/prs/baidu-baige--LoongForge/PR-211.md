# [vla] feat: consolidate LingBot VLA v2 training integration

[Upstream PR](https://github.com/baidu-baige/LoongForge/pull/211) · state: open · merged: False

## Original PR description

## Summary
- Add LingBot VLA v2 fine-tuning on the new tensor wise optimizer.
- New: model integration, dataset/collator, precision policy, config and run script.

## Design notes
- **Compared with FSDP2**: parameters are replicated rather than sharded, so there
  is no per-micro-batch all-gather/reshard. The only parameter traffic is one
  owner-to-replica publish per optimizer step; gradient reduce targets the owner
  only, so non-owners never materialise the full reduced gradient.
- **Compared with torch ZeRO-1** (`ZeroRedundancyOptimizer`): both shard optimizer
  state, but ZeRO-1 allreduces gradients to every rank, although each rank only
  updates the parameters it owns. Here gradients are reduced to the owner only,
  so the gather half of the allreduce is not needed.
- **Whole-tensor ownership**: each tensor is owned by exactly one rank, because
  Muon's Newton-Schulz needs the complete matrix, so gradients cannot be
  reduce-scattered into flat slices. The optimizer state (Muon momentum, AdamW
  moments) and the fp32 masters are sharded 1/N, and the compute replica is bf16
  for most tensors. 
- **One plan for Muon and AdamW**: a single ownership and publish plan covers
  both optimizers and both 2D and 3D (MoE expert) weights. torch's
  `ZeroRedundancyOptimizer` takes one optimizer class per instance, `torch.optim.Muon`
  only accepts 2D parameters, and ZeRO-1's overlap mode needs a functional
  optimizer and a single parameter group, which Muon training cannot meet.
- **Publish overlaps the update**: Muon reports each master as soon as it is
  updated, and a ready bucket is broadcast asynchronously while the remaining
  masters are still being computed. Gradient reduce is likewise bucketed and
  asynchronous.
- **Per-parameter precision**: compute / grad-reduce / param-publish dtypes are
  resolved independently. Non-critical tensors can use bf16 (or fp8 delta) on the
  wire, while MoE router/gate weights and 1-D norms/biases keep fp32, since a
  rounded router weight flips the top-k expert selection instead of merely
  perturbing it.

muon 抽象出来了，这个optimizer 和zero 的区别是 通信方式以及通信时间点（overlap)的区别；它不是zero1，而且在用muon的情况下通信数据类型可定制（更快），量少：

使用muon优化器情况下：
 通信量：torch zero1 的梯度做 allreduce，但每个 rank 只持有部分参数的优化器状态，只能更新自己那部分参数，更新完还要 broadcast，合计约 3Ψ。tensor_wise 的梯度只 reduce 到 owner，合计约 2Ψ。另外，tensor_wise 支持按参数类别设定通信精度：大部分参数可以用 bf16 或 fp8 发布，对精度敏感的 MoE router/gate 和一维 norm/bias 保留 fp32，这是开启低精度通信的前提。 
通信时间：参数 broadcast 和 Muon 计算重叠，owner 更新完一个参数就开始发布。zero1 用 Muon 时只能先做完 step 再统一 broadcast。
