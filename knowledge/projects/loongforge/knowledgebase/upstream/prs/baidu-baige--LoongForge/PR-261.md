# fix(embodied): write the async checkpoint marker early and fix DCP resume

[Upstream PR](https://github.com/baidu-baige/LoongForge/pull/261) · state: closed · merged: True

## Original PR description

Fixes https://github.com/baidu-baige/LoongForge/issues/258

## Summary

- `resume_meta.json` — the marker `get_latest_checkpoint` requires before a checkpoint counts as resumable — was only written when the *next* save started or at exit. It therefore lagged a full `--save-interval` behind the data, so a crash in that window dropped an already-complete checkpoint.
- Add a per-step probe that commits the marker as soon as the async DCP write finishes, mirroring Megatron's `maybe_finalize_async_save(blocking=False)`.
- Also fix `--resume` from a DCP checkpoint, which failed outright for models that register the same parameters under multiple attribute paths.

## Changes

### Async checkpoint marker — `loongforge/embodied/distributed/checkpoint.py`
- New `maybe_finalize_pending_save(ctx, step)`. With no save in flight it returns after one attribute read (zero cost, no communication). Otherwise it resolves `Future.done()` with an `all_reduce(MIN)` and reuses `flush_pending_save`. `done()` is rank-local, so the vote must be unconditional — entering `flush_pending_save` (which runs collectives of its own) on a subset of ranks would deadlock.
- `flush_pending_save` now unwraps `AsyncSaveResponse.upload_completion` when present, so the durable side is the one waited on if torch ever stages asynchronously.
- `step` is informational only — it makes the "finalized" log carry ` at step N`, which distinguishes a probe commit from a save-entry/exit commit.

### Training loop — `loongforge/embodied/train/trainers/base_trainer.py`
- Call the probe once per optimizer step, before `_save_checkpoint()`.

### DCP resume — `loongforge/embodied/distributed/checkpoint.py`
- `_resume_dcp` loaded model weights with `set_state_dict` on the DDP-wrapped module. Its internal fqn remap dedups by object identity and returns only the canonical path, so aliased keys never got the `module.` prefix re-added (4947 missing / 4947 unexpected). Load into the unwrapped module instead. Fixes https://github.com/baidu-baige/LoongForge/issues/260

### Tests
- `tests/embodied/unit/test_async_checkpoint_finalize.py` — 6 cases: no-pending no-op, finalize on completion, idempotence, slow write, failed save aborts and cleans up, `AsyncSaveResponse` waits for upload.

## Not addressed

This PR does **not** fix the pre-existing gloo abort that `--save-format dcp --async-save` hits with the default `--detail-log-interval` — see https://github.com/baidu-baige/LoongForge/issues/259. It reproduces on `0f659d7`, `origin/master` and `upstream/master`, so it is not a regression from this change; until it is fixed, exercising the async-save path needs `--detail-log-interval 0`.

## Test Plan

- **Unit**: `pytest tests/embodied/unit/test_async_checkpoint_finalize.py` → 6 passed.
- **Real training** (FastWAM MoT 6.7B, 4×A800, `--train-iters 1000 --save-interval 500 --save-format dcp --async-save --detail-log-interval 0`):
  - marker for `steps_500` written at **step 645** — 145 steps / 132 s after launch, and **183 s before** the next save entry.
  - same config without the probe: marker written at the next save entry, +500 steps / 261 s.
- **Resume from the probe-committed `steps_500`**: model / optimizer / scheduler / RNG all restored, training continued to step 510. (Resuming from `steps_1000` would not test this — that marker is written by the exit path, not the probe.)
- **Correctness**: `flush_pending_save` still calls `future.result()` before writing the marker, so a mis-reported `done()` can only stall the loop — it can never produce a marker over incomplete data.
- Reproduction of the two fixes requires the `--detail-log-interval 0` workaround described under *Not addressed*.
