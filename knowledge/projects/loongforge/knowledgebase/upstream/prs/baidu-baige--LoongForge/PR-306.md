# [vla, docs] feat: align LingBot-VA RoboTwin/LIBERO train/eval defaults with the evaluated runs

[Upstream PR](https://github.com/baidu-baige/LoongForge/pull/306) · state: closed · merged: True

## Original PR description

## Change Summary

- **What changed?** The default LingBot-VA RoboTwin train/eval recipe now reproduces the evaluated FP32-reduce release (RoboTwin-2.0, 50 tasks: Easy 87.6% / Hard 85.7%).
  - `features.py`: `LINGBOT_FSDP_BF16_REDUCE` defaults to off, because BF16 reduction rounds away small action-head gradients. Adds `LINGBOT_VA_FIXED_MICROBATCH_RNG`, also off by default. When it is off, each rank draws its own timesteps/noise/chunk/window like the community trainer, instead of every rank sharing the hard-coded per-microbatch RNG draw.
  - `modeling_lingbot_va.py`: the per-microbatch reseeding in `_prepare_input_dict` is now behind that switch. Turning it on gives the previous behaviour byte for byte.
  - `run_lingbot_va_robotwin_fsdp_finetune.sh`:
    - initialises from `lingbot-va-base`;
    - 50000 iters, GA 8 (8 GPUs x 1 x 8 = global batch 64);
    - `--set-seed-by-rank`, `--fsdp-unshard-param-dtype bfloat16`, `--no-fsdp-cast-forward-inputs`;
    - spells out the remaining flags of the evaluated run: `--no-batch-drop-last`, `--fsdp-min-param-num`, `--fsdp-reduce-dtype fp32`, `--manual-gc --manual-gc-interval 50`, `--detail-log-interval 20`, `--loss-log-rank=-1`;
    - artifact root is a placeholder.
  - `robotwin_runner.py`: one added line that maps `benchmark.instruction_type` from YAML.
    - Before this, `orchestrator.run` calls `build_argparser().parse_args([])`, so `--instruction-type` could never be set and every run used `unseen`.
    - Other models' YAMLs do not set the key, so they still get `unseen`.
  - LingBot-VA RoboTwin template: sets `instruction_type: seen`. The community client hard-codes `instruction_type = 'seen'` in `evaluation/robotwin/eval_polict_client_openpi.py`.
  - New `examples/embodied/lingbot_va/eval/configs/robotwin/robotwin_50tasks.yaml`: the full 50-task protocol of the released numbers, and now the default of `run_robotwin_eval.sh`. Users only fill paths.
    - seen instructions, start seed 10000, expert check on, 50 episodes per task;
    - the official per-task step limit as `max_steps`, set per task through `sweep`;
    - `task_config: demo_clean` for Easy, `demo_randomized` for Hard.

    The protocol lives in this LingBot-VA config only; the runner change is still the one mapping line. `adjust_bottle.yaml` stays as the one-episode smoke test.
  - Docs: the LingBot-VA quick start (en/zh) is rewritten in the GR00T-N1.7 layout (training preparation, post-training, evaluation preparation, evaluation) and reflects the new defaults. It adds the measured speedup (same node, data and global batch, mean of steps 15-45: RoboTwin 8.98 vs 25.55 s/step = 2.85x, LIBERO 12.49 vs 27.13 s/step = 2.17x), loss/grad-norm curves against the community trainer, the success rates and rollouts of the hardest tasks (`docs/assets/images/lingbot_va/`, every file <= 1 MB). The RoboTwin and LIBERO benchmark pages now list LingBot-VA.
  - New `examples/embodied/lingbot_va/export_eval_checkpoint.py` exports a training DCP into the checkpoint root the policy server loads. On a LIBERO 5000-step DCP, all 839 exported tensors are identical to the evaluated release.
- **Which issue or requirement does this address?** Running the shipped example with its defaults did not reproduce the released RoboTwin numbers.
- **Which modules are affected?**
  - `loongforge/embodied/model/lingbot_va/*`
  - `examples/embodied/lingbot_va/*`
  - one mapping line in `loongforge/embodied/eval/orchestrator/runners/robotwin_runner.py`

## Validation

Results with the default recipe: RoboTwin-2.0 50 tasks x 50 episodes, Easy 87.6% / Hard 85.7% (community-trained 86.1% / 85.1%); LIBERO-Long 10 tasks x 50 episodes, 84.6% (community-trained 77.8%).

## Reviewer Notes

- The recipe was validated end to end before this rebase: 50k-step training followed by the full 50-task Easy and Hard evaluation.
- No GPU smoke was run on this exact commit; the GPUs were busy.
- The evaluated run was 2 nodes x 8 GPUs x GA 4. The script default is 1 node x 8 GPUs x GA 8, which gives the same global batch of 64.
