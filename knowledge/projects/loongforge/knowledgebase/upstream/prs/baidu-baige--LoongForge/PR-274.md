# fix(embodied): align the FastWAM LIBERO eval protocol with the official harness

[Upstream PR](https://github.com/baidu-baige/LoongForge/pull/274) · state: closed · merged: True

## Original PR description

## Change Summary

**What changed?**

*Eval side (main)*
- `examples/embodied/fastwam/eval/configs/libero/*.yaml` (4 files): `sigma_shift` **5.0 -> 1.0** — the official action expert uses shift 1.0 and only the video expert stays at 5.0, while the old comment claimed 5.0 was the official value. Also declare `benchmark.prefer_controller_ee: false` (the official eval reads `obs['robot0_eef_pos']`; the runner defaults to the OSC controller cache) and `benchmark.controller_force_update: false`.
- `eval/orchestrator/runners/libero_runner.py`: new `--env-seed-mode {per_episode,per_task}` (`per_task` = the official semantics: one env per task, seeded once and reused across the 50 trials) and `--controller-force-update`; the runner now logs the effective value of both.
- `eval/orchestrator/config.py`: wire `benchmark.env_seed_mode` / `benchmark.controller_force_update` from the YAML into args.

*Training side (supporting)*
- `train/training_args.py`: new `--sampler-epoch-mode {advance,fixed}`, plus the new module `data/datasets/fastwam/samplers.py`. `fixed` pins the epoch to 0 to reproduce standalone FastWAM's `ResumableEpochSampler`, whose epoch never advances so every epoch reuses one permutation. The default `advance` keeps the existing behaviour bit-identical.
- New `configs/models/embodied/fastwam_aligned.yaml` / `fastwam_aligned_accel.yaml` and `examples/embodied/fastwam/run_fastwam_sft_ddp_zero1_finetune_official_aligned.sh` package the "training-side alignment + acceleration" recipe as a one-shot reproduction.

*Small boundary fix on top of #269*
- `data/datasets/lerobot_dataset.py`: `MultiLeRobotV2Dataset(roots=[])` used to build a silent zero-length dataset (the sampler yields nothing and training does no work). It now raises `ValueError` in the constructor.

**Which issue or requirement does this address?**
While reproducing FastWAM with LoongForge we found several places where the eval protocol disagreed with the official harness (most importantly `sigma_shift`, worth ~3pt). This PR aligns the eval side item by item and packages the aligned training recipe as an example, so that the same weights evaluated in both frameworks agree (TOTAL differs by <= 0.4pt).

**Which modules are affected?**
`loongforge/embodied/eval/` (orchestrator + LIBERO runner), `loongforge/embodied/train/` (training_args), `loongforge/embodied/data/datasets/` (new sampler, lerobot_dataset guard), `examples/embodied/fastwam/`, `configs/models/embodied/`.

## Reviewer Notes

**Known risks / trade-offs**
1. **`libero_runner`'s defaults are deliberately kept legacy.** `--controller-force-update` defaults to `True` (the pre-change behaviour) because the runner is shared by *every* model evaluated on LIBERO, and flipping the default would silently change their first observation. The four FastWAM configs set it to `false` explicitly to match the official eval.
2. **The two new configs carry placeholder machine-specific paths** (`norm_stats_path: /path/to/dataset_stats.json`, `tokenizer_model_id: /path/to/...`); users must fill them in.
3. **The empty-roots guard in `MultiLeRobotV2Dataset`** is a follow-up to the just-merged #269. It is added in the constructor only (there is a single caller, and the message is enough to locate it).

**Note on evaluation variance (for future comparisons)**
Retraining with identical code, data and recipe yields weights whose loss differs by ~0.2%; on `libero_10` that amplifies to **+/-1.6pt** (the evaluation itself is deterministic: rerunning the same weights reproduces all 500 episodes bit-for-bit). So **a single `libero_10` number is not a criterion**; compare changes on `spatial/object/goal` (delta <= 0.6pt here) together with a McNemar test. This matches public practice (the LeRobot docs recommend averaging over >=3 seeds; a 500-episode suite carries a ~+/-2-4pt confidence interval).

**Follow-ups (not in this PR)**
- RoboTwin-side alignment (launch script + `camera_layout` + the `z-score` alias in `normalizer`) is held back until the RoboTwin alignment settles.
- To reduce evaluation variance further, training can be made deterministic (disable `cudnn.benchmark`, enable `torch.use_deterministic_algorithms`) at some throughput cost.

This inherits `--clip-grad 1.0` from the base script, but official FastWAM effectively runs **without** gradient clipping:

1. [`configs/train.yaml#L30`](https://github.com/yuantianyuan01/FastWAM/blob/main/configs/train.yaml#L30) sets `max_grad_norm: 1.0`, and [`trainer.py#L701`](https://github.com/yuantianyuan01/FastWAM/blob/main/src/fastwam/trainer.py#L701) calls `accelerator.clip_grad_norm_(...)`.
2. Training runs under DeepSpeed ([`accelerate_zero1_ds.yaml`](https://github.com/yuantianyuan01/FastWAM/blob/main/scripts/accelerate_configs/accelerate_zero1_ds.yaml)). In that mode `Accelerator.clip_grad_norm_` only returns `engine.get_global_grad_norm()` and ignores `max_norm`; clipping is delegated to DeepSpeed's `gradient_clipping`.
3. [`ds_zero1_config.json`](https://github.com/yuantianyuan01/FastWAM/blob/main/scripts/ds_configs/ds_zero1_config.json) has no `gradient_clipping` key, and DeepSpeed's `GRADIENT_CLIPPING_DEFAULT = 0.` (`deepspeed/runtime/constants.py`). Accelerate's `gradient_clipping: 1.0` kwarg only fills keys set to `"auto"`, so it isn't injected either.

We verified this on the real FastWAM trainer (8 GPUs): `clip_grad=0.0` at runtime, step-1 global grad norm ≈ 19.6, unchanged after the clip call. LF only matched FW bit-for-bit after switching to `--clip-grad 0`.

Since grad norms are ~20–130, `--clip-grad 1.0` fires on every step in LF. Under Adam a per-step global rescale mostly cancels out, which is probably why eval still lands within noise. But it does reweight steps in the moment estimates and is one source of the residual you measured. Please use `--clip-grad 0`.
