# [BREAKING][ray,rollout] feat: add resource_pool_specs and route resource_pool to rollout server

[Upstream PR](https://github.com/verl-project/verl/pull/4515) · state: open · merged: False

## Original PR description

### What does this PR do?

This PR add the resource_pool_specs in config root level, and let each role to select its resource_pool and slot. With this base, this PR route the resource pool to rollout server. This PR contributes a more general resource pool management and support hybrid, colocate, standalone strategies.

RL frameworks share the GPU resources in five levels, and verl resource pool management reflects the complexity of the resource sharing. The five levels are:
1. Single model in single engine. This is the general case for most RL frameworks. For example a policy model resides in a single training engine.
2. Single engine with multiple model instances: Different models share the same engine.
3. Hybrid engine: Different engines share the same process group. verl provides WorkerDict class to manage multiple workers in a single process group.
4. Colocated: Different engines share the same set of GPUs but in different processes group.
5. Standalone: Different engines are on the different sets of GPUs.

A resource pool is a set of GPUs in the ray cluster for a group of processes. So within a process group, the GPU resources are shared by the program and no need to be managed by the framework.

Traditionally, we use one `global_pool` for all the actors, and take an Actor-centric view to other roles. `Hybrid`, `Colocate`, and `Standalone` are the relationship to the actor from a role. If we view the all the roles and resource pools equally, there can be a free configurations for the roles. This PR proposes to add resource pool specs field to the configs.

Resource Pool Specification
---------------------------

A resource pool is a set of GPUs in the ray cluster. The resource pool specification list the resource it provides. And verl needs a list of resource pool specifications to create the resource pools.

```yaml
  # The list of resource pool specifications.
  resource_pool_specs:
    # The resource pool id for roles to be placed on.
    - id: global_pool
      # number of nodes for the pool
      nnodes: 1
      # number of GPUs per node for the pool
      n_gpus_per_node: 8
      # max number of processes in the pool
      max_colocate_count: 1

    - id: reward_model_pool
      nnodes: 1
      n_gpus_per_node: 8
      max_colocate_count: 1
```

With this specification, the resource pools will be created in verl.

```python
    resource_pool_spec = {}
    for spec in config.resource_pool_specs:
        resource_pool_spec[spec.id] = (spec.max_colocate_count, [spec.n_gpus_per_node] * spec.nnodes)

    resource_pool_manager = ResourcePoolManager(resource_pool_spec=resource_pool_spec, mapping=self.mapping)
    resource_pool_manager.create_resource_pool()
```

Role Placement
--------------

RL frameworks schedule multiple roles, and each role is placed on a colocate slot of a resource pool. The role placement is determined by the resource pool id. The role will be placed on the resource pool with the same id. A role needs to be assigned a resource pool id and a colocate slot to be placed on. Due to historical reasons, the actor role is always placed on the global_pool by default, and other roles can be placed on the global_pool or other resource pools.

```yaml
    # resource pool id for rollout
    resource_pool_id: global_pool
    # colocate slot for rollout
    colocate_slot: 0
```

And in the code, the role placement mapping is determined by the resource pool id.

```python
    self.mapping[Role.Critic] = config.critic.resource_pool_id
```

Practices in verl
----------------
Though verl provides a general resource pool managerment scheme, the roles placement is a evolutional process of the concepts. Here is some practices in verl.

1. verl provides SPMD HybridEngine for the actor and rollout roles. The actor and rollout roles are placed on the same worker, then the same process group and the same set of GPUs.
2. verl provides colocate resource pool for rollout and reward model. And it is also noticeable that in some cases, a role colocate with the actor role, but the GPU resources are not allocated from Ray.
3. verl provides standalone resource pool for rollout and reward model.

This logic to infer the `placement` mode is redundant with the `placement` field added to `RolloutConfig` in `verl/workers/config/rollout.py`. For example, `recipe/dapo/main_dapo.py` uses `config.actor_rollout_ref.rollout.placement` to determine `max_colocate_count`. ```

The `ValueError` message is misleading. The `if/elif` chain checks the value of the local `placement` variable, but the error message reports `rollout_config.placement`. This can be very confusing for debugging, as the reported value might not be the one that caused the `else` branch to be taken. For example, this branch can be reached if `placement` is "colocate" but `rollout_config.name` is not "trtllm". The error message should report the actual values that led to the error.

            raise ValueError(f"Invalid rollout placement '{placement}' for rollout type '{rollout_config.name}'")
