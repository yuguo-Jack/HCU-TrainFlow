# [fsdp] fix: preserve FP32 buffers when casting the model to model_dtype

[Upstream PR](https://github.com/verl-project/verl/pull/8189) · state: open · merged: False

## Original PR description

## What does this PR do?

Fixes #8154.

`FSDPEngine._build_module()` ends with a blanket `module.to(torch_dtype)`. `Tensor.to(dtype)` converts registered buffers as well as parameters, so floating-point buffers that the model implementation builds in FP32 are rounded to the model dtype. `RotaryEmbedding.inv_freq` is the visible case: it is constructed in FP32, and rounding it to BF16 is irreversible — a later `buffer_dtype=torch.float32` policy only upcasts the already-rounded values, so the positional encodings (and the resulting per-token log probabilities) change.

This PR casts the floating-point (and complex) **parameters** to `model_dtype` and leaves registered buffers at their construction precision. Integer tensors, meta-initialized parameters and tied `Parameter` identity are unaffected. The helper `verl.utils.torch_dtypes.cast_module_params_to_dtype` is device-agnostic and adds no dependency.

#### Why this is not a duplicate

- Exact issue search: [open PRs mentioning #8154](https://github.com/verl-project/verl/pulls?q=is%3Apr+is%3Aopen+8154+in%3Abody) → no other PR.
- Keyword search: [open PRs mentioning `inv_freq`](https://github.com/verl-project/verl/pulls?q=is%3Apr+is%3Aopen+inv_freq) → no other PR.
- The only related open PR is #7165, which makes the same cast honor Hugging Face `_keep_in_fp32_modules*`. Qwen3 / Qwen3.5 declare neither list, so their RoPE buffers still lose precision through #7165's unchanged "no keep-list" path. This change keeps every registered buffer at its construction precision and is independent of the keep-list mechanism.

## Test Plan

New CPU test: `tests/utils/test_cast_module_params_on_cpu.py` (6 cases; picked up by `cpu_unit_tests.yml` through the `*_on_cpu.py` suffix).

```text
python -m pytest -q tests/utils/test_cast_module_params_on_cpu.py

```

Run on a CPU-only host with `torch 2.10.0+cpu`, through a minimal `verl` package shim (importing the real `verl` package pulls Ray, which is not installed on that host). Standalone check of the underlying mechanism with the same torch build: the old `module.to(torch.bfloat16)` turns the FP32 `inv_freq`-style buffer into BF16 and changes its values (max frequency error `9.77e-05`), while `cast_module_params_to_dtype(module, torch.bfloat16)` leaves the buffer FP32 and bit-identical, casts FP32 parameters to BF16, and leaves integer tensors untouched.

## Not tested

- No end-to-end FSDP forward with a real checkpoint; the log-probability deltas in #8154 were measured by the reporter on a CUDA host and are not re-measured here.
- Not exercised on NPU or CUDA (the change itself is device-agnostic).
