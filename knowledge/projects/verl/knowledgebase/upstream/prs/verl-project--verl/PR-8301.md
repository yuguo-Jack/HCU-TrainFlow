# [hardware, recipe] fix: set --xla_tpu_bf16_emission_mode=PROMOTE_F32 in the TPU GRPO recipes

[Upstream PR](https://github.com/verl-project/verl/pull/8301) · state: closed · merged: False

## Original PR description

<!-- repo: verl-project/verl | head: gutianyu-google:tpu7x-bf16-promote-f32 | base: main -->

### What does this PR do?

Both TPU GRPO recipes (`examples/tpu/grpo/run_qwen3_0_6b_torchtitan.sh`, `run_qwen3_4b_torchtitan.sh`) add `--xla_tpu_bf16_emission_mode=PROMOTE_F32` to `LIBTPU_INIT_ARGS`, with a one-line comment.

On TPU 7x, XLA's default emission mode compiles bf16 transcendental chains (sigmoid, SiLU, tanh-GELU) natively in bf16, rounding at every step; on v6e the same chains are promoted to f32 and rounded once. The difference is in the compiled HLO (reproducible offline with libtpu 0.0.47 and 0.0.50) and its effect on Qwen3 is large: about 1.8x the SiLU error and 5x the logits error against an fp32 reference, greedy GSM8K evaluations inflated by about 8 pp, and a trainer/rollout `ppo_kl` of 0.008-0.010 instead of about 0.0015. With the flag, TPU 7x compiles these chains exactly like v6e; on v6e the flag changes nothing.

Port of jialei777/verl-upstream#78 to the two recipes that exist here.

### Test

CI cannot cover this (TPU 7x hardware). Measured on TPU 7x with the Qwen3-4B recipe (verl `tpu-main` + plugin `8619e2dc`): rollout throughput -0.4%, trainer FFN step time unchanged; a 10-step GRPO run with only this flag (no code patches) matched v6e end to end (step-0 GSM8K 0.5466 vs v6e 0.5504, `ppo_kl` 0.0011-0.0021 vs 0.008-0.010 without the flag); three 250-step chains with the flag land on the v6e and H100 trajectories. On 2 x v6e-4 the recipes run as before (the flag is a no-op there).

### API and Usage Example

No API change. The flag is on by default in both scripts; it only governs XLA-compiled ops (Pallas kernels cast on their own) and is an internal `xla_tpu_*` flag, so it is pinned together with the image's libtpu version.

### Design & Code Changes

- The two `export LIBTPU_INIT_ARGS=...` lines, with a one-line comment.
- Depends on verl-hardware-plugin forwarding the driver's `LIBTPU_INIT_ARGS` to the Ray workers (plugin PR "forward the driver's LIBTPU_INIT_ARGS and XLA_FLAGS to the Ray workers"); without it the recipes' `export` stops at the driver, as it does today for `--xla_tpu_use_enhanced_launch_barrier=false`.
- Rebased on main after #8288; the scripts merge cleanly.
- Review (jialei777): the README section was dropped and the script comment cut to one sentence, so the README stays customer-facing.

Related, found while validating on TPU 7x with this stack (separate PRs): the Dockerfile does not install `orjson`, which verl main imports at platform-registration time, and the 0.6B script's batch (4 prompts x 8 samples, micro batch 8) does not divide over more than 4 trainer chips, so the README's own 2 x `v6e-8` variant fails in `ref_compute_ref_log_prob`.
