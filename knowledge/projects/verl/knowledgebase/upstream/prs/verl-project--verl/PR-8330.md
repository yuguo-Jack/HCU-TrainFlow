# [veomni] feat: expose low-precision ReduceScatter communication

[Upstream PR](https://github.com/verl-project/verl/pull/8330) · state: closed · merged: True

## Original PR description

### What does this PR do?

VeOmni already supports node-local BF16 gradient transport with FP32 accumulation and output, but verl does not expose its configuration. Add the default-off `low_precision_reduce_scatter_comm` option and forward it directly to the pinned VeOmni model builder.

Implements the [assigned low-precision communication scope](https://github.com/verl-project/verl/issues/8186#issuecomment-6332111088) in #8186 using [VeOmni #1167](https://github.com/ByteDance-Seed/VeOmni/pull/1167), which is already included in the pinned dependency.

AI assistance was used for implementation, review, test execution, and PR preparation.

```bash
# PASS
```

The baseline observed 12 native FP32 ReduceScatter calls; the enabled run observed 12 low-precision hooks and 12 BF16 all-to-all calls. Across two optimizer updates with two microbatches per rank, gradient and parameter-update relative L2 and maximum absolute differences were zero.

A separate actor-update benchmark used a 428M-parameter dense Qwen3, sequence length 512, per-rank batch 4 / microbatch 2, eager attention, and no activation checkpointing or compilation. Four independent runs used the same checkpoint and inputs in native–low–low–native order, with 5 warmup and 10 measured steps each. Timing includes zero-grad, forward/backward, optimizer and scheduler steps, with CUDA synchronization; each sample uses the maximum time across ranks.

| Run | Median ms/step | IQR ms | Peak allocated GiB | Peak reserved GiB |
| --- | ---: | ---: | ---: | ---: |
| native-1 | 117.023 | 1.116 | 5.927 | 6.318 |
| low-1 | 130.853 | 3.218 | 5.927 | 6.416 |
| low-2 | 119.163 | 0.762 | 5.927 | 6.416 |
| native-2 | 118.891 | 2.209 | 5.927 | 6.318 |

This workload showed no speedup. The low-precision runs had higher reserved memory and substantial run-to-run timing variation; no bottleneck or stable slowdown percentage is claimed.

GPU environment: PyTorch 2.13.0+cu130, runtime NCCL 2.29.7, Transformers 5.16.1, and VeOmni commit `10a26aca258f91a7af3e698cc0db8c6c51705989`. The isolated environment reused the image's PyTorch/CUDA libraries, so this was not a clean frozen-install validation. GPU results were collected on the earlier implementation, before removing compatibility checks and the forward-only guard. The final tree passed the existing CPU regression tests and hooks; CUDA was not rerun, and forward-only inference was not tested on GPU. The standalone performance harness and raw logs are supporting validation artifacts, not added repository files.

### API and Usage Example

Add these overrides to a VeOmni training command:

```bash
model_engine=veomni \
actor_rollout_ref.actor.veomni.mixed_precision=true \
actor_rollout_ref.actor.veomni.low_precision_reduce_scatter_comm=true
```

The option defaults to `false`. It requires CUDA FSDP2 and mixed precision. The hook only performs gradient communication during backward, so forward-only inference does not execute it. VeOmni retains native communication for ineligible shard groups. Parameter AllGather and HSDP replica AllReduce are unchanged.

### Design & Code Changes

- Add the boolean to the engine dataclass, Hydra configuration, and generated reference configuration.
- Forward the option directly to the pinned VeOmni builder, which validates the configuration and selects eligible shard groups.
- Document usage, requirements, and performance tradeoffs.
