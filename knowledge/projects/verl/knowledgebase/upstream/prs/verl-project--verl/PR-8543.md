# build(deps): update tensordict requirement from !=0.9.0,<=0.10.0,>=0.8.0 to >=0.8.0,!=0.9.0,<=0.15.4

[Upstream PR](https://github.com/verl-project/verl/pull/8543) · state: open · merged: False

## Original PR description

Updates the requirements on [tensordict](https://github.com/pytorch/tensordict) to permit the latest version.
<details>
<summary>Release notes</summary>
<p><em>Sourced from <a href="https://github.com/pytorch/tensordict/releases">tensordict's releases</a>.</em></p>
<blockquote>
<h2>TensorDict v0.15.4</h2>
<h2>Highlights</h2>
<ul>
<li><code>tensordict.nn.functional_vmap</code> calls a module once per set of stacked parameters in one <code>torch.vmap</code> and stacks the outputs (<a href="https://redirect.github.com/pytorch/tensordict/issues/3327">#3327</a>).</li>
<li>Printing an h5 or zarr file in the detailed display, or one row of it such as <code>h5[0]</code>, reads nothing from the file (<a href="https://redirect.github.com/pytorch/tensordict/issues/3375">#3375</a>, <a href="https://redirect.github.com/pytorch/tensordict/issues/3408">#3408</a>).</li>
<li>Fixes for h5 and zarr files, <code>append_memmap</code> after a killed append, saving a consolidated file over an existing one, lazy stacks, and in-place shape ops on views.</li>
<li>1 feature and 19 bug fixes. 5 calls warn ahead of changes in TensorDict 0.17 and 0.18; see &quot;Deprecations&quot; and &quot;Behavior changes&quot; below.</li>
</ul>
<h2>Compatibility</h2>
<ul>
<li>The zarr backend checks its version as the <code>zarr</code> extra does: with zarr 3.0.8 to 3.1.0, <code>to_zarr</code>, <code>from_zarr</code> and <code>PersistentTensorDict(backend=&quot;zarr&quot;)</code> raise an <code>ImportError</code> that names the version and the upgrade command. Before, they ran and warned on every string array. zarr 3.1.1 came out in July 2025 (<a href="https://redirect.github.com/pytorch/tensordict/issues/3364">#3364</a>, fixes <a href="https://redirect.github.com/pytorch/tensordict/issues/3352">#3352</a>).</li>
<li>The <code>parquet</code> and <code>tabular</code> extras need pyarrow 14.0.1 or later, the first release with the fix for CVE-2023-47248, against pyarrow 10 before (<a href="https://redirect.github.com/pytorch/tensordict/issues/3400">#3400</a>).</li>
<li><code>to_h5</code> stores each group's batch size and dim names in a <code>__tensordict__</code> attribute, as zarr stores already do. Older versions of tensordict ignore it, and files without it load as before (<a href="https://redirect.github.com/pytorch/tensordict/issues/3414">#3414</a>).</li>
</ul>
<h2>Features</h2>
<ul>
<li><code>tensordict.nn.functional_vmap(module, params=params, args=(x,))</code> calls <code>module</code> once per set of parameters in <code>params</code>, such as the output of <code>TensorDict.from_modules</code>, and stacks the outputs along the batch dims of <code>params</code>. It takes <code>in_dims</code> for inputs that differ per set, <code>randomness</code>, <code>chunk_size</code>, <code>method</code>, and <code>loop=True</code> to call the module in a Python loop instead of <code>torch.vmap</code> (<a href="https://redirect.github.com/pytorch/tensordict/issues/3327">#3327</a>, fixes <a href="https://redirect.github.com/pytorch/tensordict/issues/2813">#2813</a>).</li>
</ul>
<h2>Performance</h2>
<p>Against 0.15.3, on one core of an NVIDIA Grace CPU with torch 2.15.0, the 177 microbenchmarks of the 0.15.0 notes run 1.009 times as fast on average (geometric mean), and the 446 tests of the benchmark suite 0.997 times. <code>import tensordict</code> takes about as long: 1.375 s against 1.384 s.</p>
<ul>
<li>The detailed print of an h5 or zarr file, and both prints of a view of one such as <code>h5[0]</code>, build the text from the metadata and read no tensor: 2.3 to 3.8 times as fast on that machine. The text is the same as in 0.15.3 (<a href="https://redirect.github.com/pytorch/tensordict/issues/3375">#3375</a>, <a href="https://redirect.github.com/pytorch/tensordict/issues/3408">#3408</a>, <a href="https://redirect.github.com/pytorch/tensordict/issues/3423">#3423</a>, fixes <a href="https://redirect.github.com/pytorch/tensordict/issues/3403">#3403</a>).</li>
</ul>
<p>These calls are slower:</p>
<ul>
<li><code>update(src, keys_to_update=...)</code> with a lazy stack as <code>src</code> and keys deeper than an entry that the tensordict lacks takes 1.17 to 1.20 times as long, and 1.4 to 1.9 times with non-tensor entries in the members. This is the check behind the new FutureWarning of <a href="https://redirect.github.com/pytorch/tensordict/issues/3368">#3368</a>, which goes away with the change in 0.17.</li>
<li><code>consolidate(filename=p)</code> over an existing file of equal or smaller size now writes a new file, so it costs what a save to a new file costs: 1.26 times as long for a small tensordict on that machine, about 2 times for 64 MiB (<a href="https://redirect.github.com/pytorch/tensordict/issues/3421">#3421</a>).</li>
<li><code>from_h5(batch_size=...)</code> and <code>to_h5</code> take 8 to 9% longer, for the stored batch sizes and names of <a href="https://redirect.github.com/pytorch/tensordict/issues/3414">#3414</a>.</li>
<li>Calls that emit one of the new FutureWarnings take a few microseconds longer for the warning.</li>
</ul>
<h2>Bug Fixes</h2>
<h3>h5 and zarr files</h3>
<ul>
<li><code>td[&quot;n&quot;, &quot;m&quot;]</code> on an h5 or zarr file gives the nested group the batch size and names that <code>td[&quot;n&quot;][&quot;m&quot;]</code> gives. Before, h5 gave it the root's batch size and zarr no names, and some writes raised (<a href="https://redirect.github.com/pytorch/tensordict/issues/3417">#3417</a>, fixes <a href="https://redirect.github.com/pytorch/tensordict/issues/3410">#3410</a>).</li>
<li><code>clone(newfile=)</code> copies empty nested tensordicts, and zarr clones store each group's own batch size. Before, the clone raised <code>KeyError</code>, or reopened with the wrong batch size (<a href="https://redirect.github.com/pytorch/tensordict/issues/3416">#3416</a>, fixes <a href="https://redirect.github.com/pytorch/tensordict/issues/3409">#3409</a>, fixes <a href="https://redirect.github.com/pytorch/tensordict/issues/3412">#3412</a>).</li>
<li><code>from_h5</code> and <code>from_zarr</code> load a file or group that holds only strings, with no batch dims for such a group. Before, they raised <code>IndexError</code> (<a href="https://redirect.github.com/pytorch/tensordict/issues/3418">#3418</a>, fixes <a href="https://redirect.github.com/pytorch/tensordict/issues/3411">#3411</a>).</li>
<li><code>from_zarr(auto_batch_size=True)</code> gives one dim name per batch dim, as <code>auto_batch_size_()</code> does. Before, later calls such as <code>to_tensordict()</code> raised <code>ValueError</code> (<a href="https://redirect.github.com/pytorch/tensordict/issues/3419">#3419</a>, fixes <a href="https://redirect.github.com/pytorch/tensordict/issues/3413">#3413</a>).</li>
<li><code>to_h5</code> and <code>to_zarr</code> name the entry and the backend when they can't store a bfloat16 or nested tensor, and say what to do instead (<a href="https://redirect.github.com/pytorch/tensordict/issues/3373">#3373</a>, fixes <a href="https://redirect.github.com/pytorch/tensordict/issues/3265">#3265</a>).</li>
</ul>
<h3>Saving and loading</h3>
<ul>
<li><code>append_memmap</code> after an append that was killed midway finishes or rolls back the killed append, then appends. Before, it raised until you renamed the leftover <code>.meta.json.append.tmp</code> files by hand. A directory saved again since the kill keeps its new data (<a href="https://redirect.github.com/pytorch/tensordict/issues/3376">#3376</a>, <a href="https://redirect.github.com/pytorch/tensordict/issues/3424">#3424</a>).</li>
<li><code>consolidate(filename=p)</code> over an existing file of equal or smaller size saves the right data when a tensordict still maps the old file, or when an older result refreshes its metadata after a newer save. Before, the file loaded without an error and held the wrong data (<a href="https://redirect.github.com/pytorch/tensordict/issues/3421">#3421</a>, fixes <a href="https://redirect.github.com/pytorch/tensordict/issues/3197">#3197</a>).</li>
<li><code>consolidate(return_early=True)</code> on a tensorclass gives back the tensorclass from <code>future.result()</code>, as the eager call does. Before, it gave a plain <code>TensorDict</code> (<a href="https://redirect.github.com/pytorch/tensordict/issues/3365">#3365</a>, fixes <a href="https://redirect.github.com/pytorch/tensordict/issues/3149">#3149</a>).</li>
</ul>
<h3>Keys, set and update</h3>
<ul>
<li><code>update(src, keys_to_update=[(&quot;nested&quot;, &quot;b&quot;)])</code> with a dict source that has tuple keys writes only the listed entries, as a tensordict source does (<a href="https://redirect.github.com/pytorch/tensordict/issues/3361">#3361</a>, fixes <a href="https://redirect.github.com/pytorch/tensordict/issues/3216">#3216</a>).</li>
</ul>
