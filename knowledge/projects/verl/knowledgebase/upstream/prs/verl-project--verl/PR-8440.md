# [trainer, rollout] feat: split shared physical pools for separate async

[Upstream PR](https://github.com/verl-project/verl/pull/8440) · state: closed · merged: False

## Original PR description

### What does this PR do?

V1 `separate_async` configures trainer and standalone rollout pools separately.
On two 8-GPU nodes, that interface cannot describe a rollout pool occupying one
full node and half of the other while leaving the remaining four GPUs to the
trainer. This change adds an opt-in `shared_rollout_gpus` setting: the physical
pool is reserved once and split into disjoint rollout and trainer bundles. For
example, `trainer.nnodes=2 trainer.n_gpus_per_node=8` and
`trainer.v1.separate_async.shared_rollout_gpus=12` assign 12 GPUs to rollout and
4 to training; setting it to 10 yields 10 and 6. Existing configs are unchanged.

Rollout replicas are sliced from the rollout pool. The change validates the
replica layout before allocation and counts trainer GPUs correctly in config
validation and throughput metrics. The initial implementation requires
node-local rollout replicas and rejects hybrid switching and PD disaggregation
with this option.

### Related work

- [#4273](https://github.com/verl-project/verl/pull/4273) provides the underlying
  resource-pool split and [#7993](https://github.com/verl-project/verl/pull/7993)
  lets standalone replicas attach an existing pool; this PR wires those APIs
  into the V1 separate-async trainer.
- [#4515](https://github.com/verl-project/verl/pull/4515) is an open broader
  role/slot configuration proposal, currently based on uniform per-node pool
  sizes. This change is a small, opt-in static split rather than a general
  topology API. See also [RFC #7269](https://github.com/verl-project/verl/issues/7269).
- Search: https://github.com/verl-project/verl/pulls?q=is%3Apr+resource+pool+rollout+trainer

### Test

- Targeted CPU tests: `pytest -q tests/trainer/ppo/v1/test_shared_resource_pool_on_cpu.py tests/trainer/ppo/v1/test_v1_async_alignment_on_cpu.py tests/trainer/ppo/v1/test_separate_async_step_switch_on_cpu.py` — 112 passed.
- Two local Ray nodes advertising 8 synthetic GPU slots each: verified disjoint
  12/4 and 10/6 assignments and node distributions with
  `tests/special_standalone/shared_resource_pool_ray.py`.
- One 8×RTX A6000 host, Qwen2.5-0.5B, FSDP2 and vLLM: completed two training
  steps with 6 rollout / 2 trainer GPUs and 5 rollout / 3 trainer GPUs.
  The 6/2 run returned zero but logged a DataLoader worker-killed traceback
  during shutdown; the 5/3 run with `data.dataloader_num_workers=0` exited
  without that traceback.
- Two Ray nodes on that same host, each exposing four distinct physical GPUs:
  completed two training steps with a 6/2 rollout/trainer split, including
  checkpoint weight transfer between workers on different Ray nodes.
- The test image uses PyTorch 2.11.0+cu130, Ray 2.55.1, Transformers 5.3.0,
  vLLM 0.20.2, and TransferQueue 0.1.11; CI should also exercise the repository's
  pinned environment.
- The available test host has one physical machine. No claim of a real
  multi-host training run or a throughput improvement is made here.
- Ruff 0.15.21, generated-config verification, docs and test-structure checks
  passed. Full pre-commit was not run because its dependencies did not finish
  downloading; its configured Ruff version is 0.12.2.

### API and usage example

```bash
trainer.use_v1=true \
trainer.v1.trainer_mode=separate_async \
trainer.nnodes=2 \
trainer.n_gpus_per_node=8 \
trainer.v1.separate_async.shared_rollout_gpus=12 \
actor_rollout_ref.rollout.nnodes=1 \
actor_rollout_ref.rollout.tensor_model_parallel_size=2
```
