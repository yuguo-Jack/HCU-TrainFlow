# [reward] fix: reject wrong interval brackets and scaled numbers in prime_math

[Upstream PR](https://github.com/verl-project/verl/pull/8347) · state: closed · merged: False

## Original PR description

### What does this PR do?

Fixes #8346.

This PR fixes grading errors in `verl/utils/reward_score/prime_math`, which scores the `numina_*` math rows of Eurus-2-RL-Data. Exactly these behaviors change:

1. **Interval brackets.** An interval with a wrong endpoint bracket no longer gets credit. For example, `[1,2]` now scores 0 against `[1,2)`, and this also applies to brackets inside unions.
2. **Infinite endpoints.** The bracket at an infinite endpoint is ignored, because it does not change the set. So `(0, \infty)` still matches `(0, \infty]`, and `[-\infty, 8]` now matches `(-\infty, 8]`. This also holds with `\left`/`\right` and inside unions, and when only one of the two answers uses `\left`/`\right`. For example, `\left[\frac{3}{2}, +\infty\right]` and `[\frac{3}{2}, +\infty]` now both match row 302's `\left[\frac{3}{2}, +\infty\right)`.
3. **Unicode infinity.** `∞` is read the same as `\infty`, so `(-\infty, 0)` now matches the gold `(-∞, 0)`.
4. **Integers.** An integer gold now needs an exact match: `22501` no longer matches `22500`. Integer literals are compared as Python ints. That includes an optional leading `+` or `-` and a zero fraction such as `22500.0`. It also holds above 2^53, so `9007199254740993`, `+9007199254740993` and `9007199254740993.0` no longer match `9007199254740992`, and `-9007199254740993` no longer matches `-9007199254740992`.
5. **Percentages.** 100x and 1/100x of the gold are only accepted in the direction the `%` sign implies:
   - For a gold of `83\%`, `83`, `0.83` and `83\%` still match, while `8300` and `0.83\%` no longer do.
   - For a gold of `0.25`, `25\%` still matches.
   - A plain number no longer matches 100x or 1/100x of a plain-number gold (`4200` for `42`).

What does not change:

- **Equation answers** are graded exactly as on main. The issue's third finding, gold equations that score 0 when given back, is not addressed here. The issue explains why a simple side-by-side comparison would create new false credits.
- **Decimal golds** keep the existing 1e-4 relative tolerance (reason below). Numbers in other forms, such as `9.007199254740993e15`, still go through the existing float comparison.
- **Pre-existing behavior** that this PR does not touch:
  - A gold left-hand side of at most two characters is dropped (`q = 2` matches `m = 2`).
  - In non-equation golds, everything after `\text{ ` is dropped (`199 \text{ or } 201` matches `199 \text{ or } 200`).
  - Base subscripts are ignored (`1042_8` matches `1042_7`).
  - The MATH normalizer used by `grade_answer` removes `\left`/`\right` by plain substring replacement. That also turns both `\leftarrow` and `\rightarrow` into `arrow`, so a boxed `A \leftarrow B` can still match `A \rightarrow B` through `grade_answer`. This PR does not touch that path; its own `\left`/`\right` removal in `math_equal` keeps both arrows.

The change touches three source files (50 lines added, 3 removed) and adds a CPU test file.

Related open PRs (none of them changes the same behavior):

- #7437 fixes the `timeout_limit` usage in `grader.symbolic_equal`, which is a different function. The two patches apply cleanly together; results are under Test.
- #7607 and #7701 remove `eval()` from `grader.py` (`handle_pi` and the matrix branch). Each applies cleanly on top of this branch.
- #8124 normalizes the boxed fallback in `math_dapo.py`, which is a different scorer.

### API and Usage Example

No public API changes. The signatures of `math_equal` and `compute_score` are unchanged. `include_percentage=True` still enables the percent conversion; the conversion now follows the `%` sign.

```python
from verl.utils.reward_score import default_compute_score

def score(answer, gold):
    return default_compute_score("numina_cn_k12", f"The answer is $\\boxed{{{answer}}}$.", gold)

score("[1,2]", "[1,2)")                       # main: 1.0, this PR: 0.0
score("(0, \\infty)", "(0, \\infty]")         # 1.0 on both
score("2250000", "22500")                     # main: 1.0, this PR: 0.0
score("22501", "22500")                       # main: 1.0, this PR: 0.0
score("8300", "83\\%")                        # main: 1.0, this PR: 0.0
score("0.83", "83\\%")                        # 1.0 on both
```

### Design & Code Changes

`verl/utils/reward_score/prime_math/grader.py`, in `math_equal`:

- **Infinite endpoints.** `_normalize_interval_brackets` runs on both answers before the interval checks:
  - It drops `\left` and `\right`, which only size the brackets. Commands such as `\rightarrow` are kept, and the MATH normalizer already drops `\left`/`\right` in `grade_answer`.
  - It then rewrites `\infty]` as `\infty)` and `[-\infty` as `(-\infty`. The same applies to `∞`.
- **Interval brackets.** When the prediction and the reference both start with `(` or `[`, both end with `)` or `]`, and both contain a comma, they must have the same sequence of bracket characters. If they don't, the function returns False. This check runs before the existing step that strips `[]()` and compares the rest, which is the step that let `[1,2]` match `[1,2)`. Apart from unions, the only interval-shaped gold in this split with inner brackets is a list of points, `(-4, -3), (-3, -4), ...`, and that gold is not affected.
- **Integers.** If no percent conversion applies and both answers are integer literals (optional `+` or `-`, optionally with a zero fraction), they are compared as Python ints. Otherwise, an integer-valued reference is compared with `rel_tol=0`, and a non-integer reference keeps `rel_tol=tolerance` (1e-4).
- **Percentages.** Whether each answer contains `%` is recorded before normalization strips the sign. The candidate list is then `[reference]`, plus `reference / 100` if only the reference carries `%`, or `reference * 100` if only the prediction does.

`verl/utils/reward_score/prime_math/__init__.py`: `_normalize` and `_str_to_int` convert integer literals (optional `+` or `-`, optionally with a zero fraction) with `int()` instead of going through `float`. Above 2^53, the float round trip had turned `9007199254740993` into `9007199254740992`.

`verl/utils/reward_score/prime_math/math_normalize.py`: `_strip_string` replaces `∞` with `\infty` (one line).

**Why the tolerance is kept for decimals.** The 1e-4 tolerance appears intended for floating-point answers. Many decimal golds in this split are rounded values (`-29.2307692`, `3347.333`, `-64.226`, `0.4752`), so exact matching would reject answers that give more digits. The cost is that a last-digit change on a decimal gold with five or more significant digits can still pass (8 golds in this split). Integer golds have no rounding to absorb, so they now get the exact match that `grade_answer` already asks for ("if the ground truth answer is an integer, we require the given answer to be a strict match").

`tests/utils/reward_score/test_prime_math_on_cpu.py`: the 64 cases described under Test. The `cpu_unit_tests` workflow already collects `*_on_cpu.py` files, so no workflow change is needed.
