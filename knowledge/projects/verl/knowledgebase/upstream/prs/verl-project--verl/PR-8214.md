# [trainer, cfg, doc] feat: support custom validation metrics

[Upstream PR](https://github.com/verl-project/verl/pull/8214) · state: closed · merged: False

## Original PR description

### What does this PR do?

Add a config-driven hook, `data.custom_validation_metrics.{path,name}`, that lets users add validation metrics without subclassing the trainer.

Built-in validation metrics are grouped only by `data_source` and use fixed statistics (mean/std/best/worst/maj @N). Metrics split by another per-sample attribute, or metrics that combine several fields, currently require overriding `_val_metrics_update` in a trainer subclass. The new hook is loaded with `load_extern_object`, like `custom_reward_function` and `data.custom_cls`. It covers both the legacy `RayPPOTrainer` and the V1 `PPOTrainer`, and it is disabled by default, so behavior is unchanged unless it is configured.

For both trainers, the new `test_custom_validation_metrics_on_cpu.py` calls the real `_val_metrics_update` and checks that:

- built-in metrics are unchanged and the custom metrics are merged;
- the function receives `data_sources` as a `list` and the exact per-sample `reward_extra_infos` dict;
- a disabled hook produces only the built-in metrics;
- a non-dict return value raises `TypeError`, and a key collision with a built-in metric raises `ValueError`;
- invalid configs (missing `name`, missing file, missing attribute, non-callable object) fail at load time;
- constructing `RayPPOTrainer` or the V1 `PPOTrainer` from a composed `ppo_trainer` config with a wrong function name fails during construction.

No GPU or end-to-end run was done. The change only affects validation-metric post-processing and is a no-op when disabled.

### API and Usage Example

```python
# my_metrics.py
from collections import defaultdict

import numpy as np


def difficulty_metrics(data_sources: list[str], reward_extra_infos: dict[str, list]) -> dict[str, float]:
    acc_by_difficulty = defaultdict(list)
    for difficulty, acc in zip(reward_extra_infos["difficulty"], reward_extra_infos["acc"], strict=True):
        acc_by_difficulty[difficulty].append(acc)
    return {f"val-aux/difficulty/{key}/acc/mean": float(np.mean(vals)) for key, vals in acc_by_difficulty.items()}
```

```bash
python -m verl.trainer.main_ppo ... \
  data.custom_validation_metrics.path=/path/to/my_metrics.py \
  data.custom_validation_metrics.name=difficulty_metrics
```

- `data_sources`: the data source of each validation sample.
- `reward_extra_infos`: the same per-sample dict passed to `process_validation_metrics` (`reward`, `acc` and any extra reward fields).
- The returned dict is merged into the validation metrics, and its keys are used verbatim.

### Design & Code Changes

- `verl/trainer/ppo/metric_utils.py`:
  - `load_custom_validation_metrics_fn(data_config)` returns `None` when `path` is unset, raises `ValueError` if `name` is missing, and raises `TypeError` if the object is not callable.
  - `merge_custom_validation_metrics(...)` calls the function, raises `TypeError` on a non-dict result and `ValueError` on a collision with a built-in key.
- `RayPPOTrainer` and the V1 `PPOTrainer` load the function in `__init__`, so a wrong path or name fails at startup instead of after the first validation rollout. The result is merged at the end of `_val_metrics_update`, which also covers the legacy `_merge_validation_results` path.
- `OneStepOffRayTrainer` and `FullyAsyncRollouter` override `__init__` without calling `RayPPOTrainer.__init__` but still use the inherited `_validate`. Each gets one line that loads the function the same way, so validation keeps working and the option is honored.
- `verl/trainer/config/data/legacy_data.yaml` and the regenerated `_generated_*.yaml`: new `custom_validation_metrics: {path: null, name: null}` next to `custom_cls`.
- `docs/examples/config.rst`: new "Customized Validation Metrics" section.

#### Open questions for reviewers

- Should the function also receive `sample_uids` and `sample_turns` (e.g. for per-prompt metrics such as pass@k)? The current `fn(data_sources=..., reward_extra_infos=...)` signature matches an existing user function; more inputs could be added later as optional keyword arguments.
- Should custom keys be namespaced automatically (e.g. a `val-custom/` prefix) instead of being used verbatim with only a collision check?
- Is `data.*` the right place, or would `trainer.*` be preferred?
