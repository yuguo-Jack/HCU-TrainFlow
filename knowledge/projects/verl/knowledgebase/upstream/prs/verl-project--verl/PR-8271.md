# [hardware, doc] fix: handle unset TPU_WORKER_HOSTNAMES in TPU SFT torchrun mode and sync README

[Upstream PR](https://github.com/verl-project/verl/pull/8271) · state: closed · merged: False

## Original PR description

### What does this PR do?

Fixes two follow-up issues from #8233 in `examples/tpu/sft`:

1. **`examples/tpu/sft/run_qwen3_0_6b_torchtitan.sh`**: Because the script starts with `set -xeuo pipefail`, line 115 (`DEFAULT_MASTER_ADDR="${TPU_WORKER_HOSTNAMES%%,*}"`) aborts with `TPU_WORKER_HOSTNAMES: unbound variable` whenever `TPU_WORKER_HOSTNAMES` is unset (for example on single-host TPU v6e-4 VMs or single-host GKE TPU pods where the webhook does not inject `TPU_WORKER_HOSTNAMES`), before reaching the `127.0.0.1` fallback on line 116 (and even when `MASTER_ADDR` is explicitly provided). Default `TPU_WORKER_HOSTNAMES` to `127.0.0.1` before stripping `,.*`.
2. **`examples/tpu/sft/README.md`**: #8233 changed `run_qwen3_0_6b_torchtitan.sh` to default to `SFT_TRAINER_MODE=torchrun` (was `ray`), so the README's `ray job submit` commands need `SFT_TRAINER_MODE=ray` and the `verl-hardware-plugin` runtime environment (`VERL_PLATFORM=tpu`, `VERL_USE_EXTERNAL_MODULES=verl_hardware_plugin`, matching `examples/tpu/grpo/README.md`).

**Reject the loopback fallback for multi-node runs.**

When `TPU_WORKER_HOSTNAMES` and `MASTER_ADDR` are unset, this assigns `127.0.0.1`. `NNODES_TRAINER` defaults to 2, so workers on other nodes cannot reach the master through their own loopback address, and training fails to rendezvous. Use loopback only for single-node runs. For multi-node runs, require a routable address or exit before launching `torchrun`.
