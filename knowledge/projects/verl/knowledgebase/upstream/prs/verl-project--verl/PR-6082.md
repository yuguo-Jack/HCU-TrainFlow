In verl/utils/tensordict_utils.py, a previous workaround for a tensordict bug was replaced with a runtime version check. - ErenAta16 · COMMENTED · 2026-08-01T22:22:29Z · [source](https://github.com/verl-project/verl/pull/6082#pullrequestreview-4835919309)

Two things about the constraint change, separate from whether 0.12.2 is the right floor.

**The upper bound goes away.** The three declaration sites move from a bounded range to an open one:

```
requirements.txt      tensordict>=0.8.0,<=0.10.0,!=0.9.0  ->  tensordict>=0.12.2
requirements-npu.txt  same
setup.py              same
```

The old constraint was not a lazy pin. It carried an upper cap *and* an explicit `!=0.9.0`, which is what a project writes after a specific release broke it. This PR exists because a tensordict version shipped the `_ragged_idx` problem, so the history says releases in this dependency do break verl, and the change removes the mechanism that contained that.

Concretely, the next tensordict minor lands in every fresh install and every CI run with no change to this repo, and if it regresses nested tensors the failure appears on unrelated PRs first. Given the diff already touches eight workflows to force a version, an upper bound seems more in keeping with how this dependency has actually behaved. `>=0.12.2,<0.13` would keep the fix and keep the containment.

If dropping the cap is deliberate, for instance because the cap was what made this upgrade painful in the first place, that is a reasonable trade, it just belongs in the description rather than being inferred from the diff.

**The version now lives in eleven places.** Three declaration files plus a `pip install --index-url https://pypi.org/simple "tensordict>=0.12.2"` line added to eight workflows. The next bump has to hit all eleven, and a missed workflow fails in a way that looks like a flaky job rather than a stale pin. A constraints file referenced by the workflows, or a single composite action, would leave one place to edit.

Worth a second look at `--index-url` specifically. It *replaces* the index set rather than adding to it, so any workflow that relies on a configured mirror or an internal index loses it for that install. That is most likely to matter in `e2e_ascend.yml` and `e2e_ppo_trainer_megatron_vllm_2_ascend.yml`, where NPU wheels commonly come from somewhere other than pypi.org. `--extra-index-url` would add pypi without displacing whatever is configured, if the intent is just to make sure a recent tensordict is reachable.

Neither is blocking. The upgrade itself is clearly needed.

- peterdsharpe · comment · 2026-10-30T01:04:20Z · [source](https://github.com/verl-project/verl/pull/6082#issuecomment-6512340425)

I maintain `tensordict` and tested this upgrade against `verl`'s CPU test suite (`main` at `2ab3529`) on `tensordict` 0.10.0, 0.14.3, and 0.15.3.

### What upgrading to 0.15.3 gives `verl`

- **Fixes the #7899 / #6851 3D `position_ids` crash path:** `tensordict>=0.12.2` preserves `_ragged_idx` through `consolidate()` and pickling (pytorch/tensordict#1675), so `maybe_fix_3d_position_ids()` can be removed as this PR does.
- **Native jagged `NestedTensor` batch ops (pytorch/tensordict#3113, in 0.15.3):** Indexing, slicing, `chunk`, `split`, and `cat` now work directly on `TensorDict`s holding jagged tensors (for example, `tu.pad_to_divisor` works on jagged batches instead of raising `RuntimeError`, and native `chunk` + `cat` is ~2x faster than unbinding and repacking in Python).
- **Pure-Python wheel (in 0.15+):** 0.15 ships a single `py3-none-any.whl` with no C++ extension, avoiding platform/ABI wheel mismatches on `linux-aarch64`, Ascend, and ROCm.
- **Lower CPU/controller overhead:** On `verl`-shaped batches (128 samples, 8 tensor keys + `NonTensorStack` + `NonTensorData`), key lookups are ~7x faster, shallow copies ~4.5x faster, batch construction ~2.8x faster, and `consolidate()` + pickle ~1.3–1.5x faster than in 0.10.0.

### Four small changes needed in `verl` for 0.14.2+ / 0.15.3

Out of 1,689 CPU tests, only 3 in `tests/test_protocol_v2_on_cpu.py` fail on 0.14.3 and 0.15.3, and `tensordict` emits no deprecation warnings on `verl`'s calls:

1. **Keep rank-0 `NonTensorData` in `concat_tensordict` (`verl/utils/tensordict_utils.py`):**
   Since `tensordict` 0.14.2 (pytorch/tensordict#1786), concatenating `TensorDict`s whose `NonTensorData` values differ returns a per-row `NonTensorStack` instead of keeping only the first input's value. When DP > 1, each rank's `metrics` dict has rank-local memory/MFU numbers, so after `concat_tensordict` in `_compute_old_log_prob`, `tu.get(output, "metrics")["mfu"]` gets a `list` of dicts and raises `TypeError`. Preserving the first input's `NonTensorData` in `concat_tensordict` keeps the existing behavior on all versions:

   ```python
   non_tensor = {k: v.data for k, v in data[0].items() if isinstance(v, NonTensorData)}
   if non_tensor and len(data[0].batch_size) > 0:
       output = concat_tensordict([td.exclude(*non_tensor) for td in data])
       for key, value in non_tensor.items():
           output.set_non_tensor(key, value)
       return output
   ```

   This fixes `test_concat_tensordict`. In `test_chunk_concat`, line 365 calls `torch.cat` directly to test keep-first behavior and should call `tu.concat_tensordict([data1, data2, data3])` instead.

2. **Add `orjson` to `verl`'s dependencies (`pyproject.toml`, `setup.py`):**
   `verl/utils/tracking.py` imports `orjson` without declaring it. `tensordict` 0.15.2 dropped its own `orjson` dependency, so a fresh environment without `sglang` (such as the `cpu` extra) will be missing `orjson` unless `verl` lists it (#8292).

3. **Update `test_contiguous` (`tests/test_protocol_v2_on_cpu.py:1140`):**
   Since `tensordict` 0.14.0 (pytorch/tensordict#1747), `consolidate()` supports non-contiguous tensors directly and no longer raises `RuntimeError`.

4. **Torch floor on older NPU images (`requirements-npu.txt`):**
   `tensordict` 0.15 requires `torch>=2.11` (which `verl`'s `uv` environments on `torch 2.13` satisfy). Environments that pin an older `torch` resolve to `tensordict` 0.14.3 automatically, but `requirements-npu.txt` does not pin `torch`, so running `pip install -r requirements-npu.txt` inside a `torch_npu 2.10` container will pull `tensordict` 0.15.3 and overwrite `torch` with 2.14 from PyPI unless `requirements-npu.txt` caps `tensordict<0.15` (or pins `torch`).

(One minor rebase note on this PR: `collate_variable_batch` in `verl/utils/dataset/dataset_utils.py` already uses `nested_tensor_from_tensor_list`, so that hunk is no longer needed.)
