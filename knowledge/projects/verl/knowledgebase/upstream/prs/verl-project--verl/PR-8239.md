# [hardware, doc] fix: update TPU GRPO examples for Ray TPU_VISIBLE_CHIPS and Qwen3-4B 100-step stability

[Upstream PR](https://github.com/verl-project/verl/pull/8239) · state: closed · merged: True

## Original PR description

### What does this PR do?

Fixes the TPU GRPO examples (`examples/tpu/grpo`) on Ray `< 2.59.0` and ensures the full 100-step Qwen3-4B GRPO training run completes end-to-end without HBM fragmentation/exhaustion:

1. **Remove `RAY_EXPERIMENTAL_NOSET_TPU_VISIBLE_CHIPS=1` from TPU GRPO scripts and `README.md`**:
   - Complementing #8233, remove `RAY_EXPERIMENTAL_NOSET_TPU_VISIBLE_CHIPS=1` from `examples/tpu/grpo/run_qwen3_0_6b_torchtitan.sh`, `examples/tpu/grpo/run_qwen3_4b_torchtitan.sh`, and `examples/tpu/grpo/README.md` so Ray populates `TPU_VISIBLE_CHIPS` per worker on Ray `< 2.59.0`.
2. **Set default `MICRO_BATCH_SIZE=2` in `examples/tpu/grpo/run_qwen3_4b_torchtitan.sh`**:
   - In #8226 (`MICRO_BATCH_SIZE=4`), only 10 steps (`TOTAL_TRAINING_STEPS=10`) were tested and libtpu already logged `RESOURCE_EXHAUSTED ... Fragmentation` allocation retries on the 33.54 GB v6e trainer chips. Over a full 100-step run, `MICRO_BATCH_SIZE=4` eventually hits unrecoverable HBM fragmentation (`tt_jit_gather` / `reduce_scatter_tensor` reservation failure at step 37).
   - Combined with per-micro-batch backward TPU synchronization (`tpu_synchronize(wait=True)` from `verl-hardware-plugin` PR https://github.com/verl-project/verl-hardware-plugin/pull/57, merged as `e5ab532`), setting `MICRO_BATCH_SIZE=2` keeps trainer HBM safely within 33.54 GB across all 100 steps while maintaining the same end-to-end step time (since steps in `separate_async` mode overlap trainer updates with vLLM rollout generation).
3. **Pin `verl-hardware-plugin` commit and update expected step time in `examples/tpu/grpo/README.md`**:
   - Check out commit `e5ab532ae41a582bd2e9183c5deaf2bd8876045f` right after cloning `verl-hardware-plugin`: the current `main`, where https://github.com/verl-project/verl-hardware-plugin/pull/57 landed, so no extra `git fetch` of a PR commit is needed.
   - Update expected Qwen3-4B step time in `README.md` to `20-30 s per step (~25 s average over 100 steps)`.
