# [rollout] fix: make max_num_batched_tokens mutable

[Upstream PR](https://github.com/verl-project/verl/pull/8075) · state: closed · merged: True

## Original PR description

## What does this PR do?

#7632 added a self-heal to `vLLMHttpServer._validate_configs()`. When
`enable_chunked_prefill=False` and `max_num_batched_tokens < max_model_len`, it
raises `max_num_batched_tokens` to `max_model_len`:

```python
self.config.max_num_batched_tokens = self.config.max_model_len
```

`RolloutConfig` is a `BaseConfig`, which freezes every field that isn't listed in
`_mutable_fields`. `max_num_batched_tokens` isn't in that list, so the self-heal
crashes:

```
File "verl/workers/rollout/vllm_rollout/vllm_async_server.py", in _validate_configs
    self.config.max_num_batched_tokens = self.config.max_model_len
File "verl/base_config.py", line 37, in __setattr__
dataclasses.FrozenInstanceError: Field 'max_num_batched_tokens' is frozen and cannot be modified
```

**How to reproduce:** set `rollout.enable_chunked_prefill=False` and leave
`rollout.max_model_len` unset. The model's `max_position_embeddings` then fills in
`max_model_len`, and it's bigger than the default `max_num_batched_tokens=8192`
(for example, Qwen2.5-0.5B-Instruct: 32768). With #7632, the vLLM server dies in
`__init__`. Before #7632, vLLM rejected the config instead.

**Why CI didn't catch it:** #7632 also removed `enable_chunked_prefill=False` from
the example scripts and CI jobs. The only script that still sets it
(the torch profiler example) pins `max_model_len` explicitly, so it never hits this
branch.

## Fix

Add `max_num_batched_tokens` to `RolloutConfig._mutable_fields`, the same way
`max_model_len` is already mutable. `max_model_len` is back-filled a few lines
earlier in the same `_validate_configs()`.

Why this fix rather than one that avoids mutation:
- `self.config` is a private copy. Each server builds it with
  `omega_conf_to_dataclass()` in `__init__` and adjusts it in
  `_validate_configs()` before anything reads it. Nothing else shares the object,
  so the stale-shared-state problem that freezing guards against doesn't apply here.
- The only other option that keeps the field frozen is to keep the adjusted value
  outside the config and pass it only to the vLLM engine args. Then
  `config.max_num_batched_tokens` would report 8192 while vLLM actually runs with
  32768, which is worse than a controlled mutation.
- `dataclasses.replace()` would run `__post_init__` again on the whole rollout
  config just to change one int.

```python
from verl.workers.config.rollout import RolloutConfig


def test_max_num_batched_tokens_raised_when_chunked_prefill_disabled():
    # vLLMHttpServer._validate_configs raises max_num_batched_tokens to max_model_len
    # when chunked prefill is off; that write must not hit the frozen-field guard.
    config = RolloutConfig(name="vllm", enable_chunked_prefill=False, max_num_batched_tokens=8192)
    config.max_model_len = 32768
    config.max_num_batched_tokens = config.max_model_len
    assert config.max_num_batched_tokens == 32768
```
