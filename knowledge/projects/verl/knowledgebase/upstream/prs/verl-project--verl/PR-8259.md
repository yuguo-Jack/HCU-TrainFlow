# [hardware, perf, doc] feat: move the TPU GRPO image to torchtitan ea7fec0f (jax 0.11.1, libtpu 0.0.50) and speed up the Qwen3-4B example

[Upstream PR](https://github.com/verl-project/verl/pull/8259) · state: closed · merged: True

## Original PR description

### What does this PR do?

> Moves the TPU GRPO example (`examples/tpu/grpo`) to `google-pytorch/torchtitan` `ea7fec0f` with that commit's TPU package versions, and points the README at the verl-hardware-plugin commit that supports it (`f5876f75`, the merge of verl-project/verl-hardware-plugin#60: a standalone TPU TorchTitan engine). It also makes the Qwen3-4B example's 100-step run 11% faster with three overlap settings. Only `examples/tpu/grpo/` changes; core verl, including `verl/workers/engine/torchtitan/`, is untouched.

Two commits:

1. `03751db2`: the image and the plugin pin.
   - `Dockerfile`: torchtitan `f880cc73` -> `ea7fec0f`, with the versions of its `torchtitan/experiments/tpu/requirements.txt`: jax/jaxlib 0.10.2 -> 0.11.1, libtpu 0.0.47 -> 0.0.50, torchao 0.17.0 (new). The rest of the stack is unchanged.
   - `README.md`: checks out verl-hardware-plugin `f5876f75` instead of `e5ab532`, which subclasses core's TorchTitan engine and does not import with this torchtitan.
2. `3b0c9a24`: three overlap settings for the Qwen3-4B example (`run_qwen3_4b_torchtitan.sh`, now environment variables), and the README's expected step time.

Related open PRs:
- #8243 also edits this `Dockerfile` and `README.md`, but takes a different direction: Ray 2.59, PyPI `torchtitan` 0.3.0 and a pip-installed plugin. This PR keeps `google-pytorch/torchtitan`, because the TPU engine uses its TPU recipe (SimpleFSDP) and kernels (splash attention), which PyPI `torchtitan` 0.3.0 does not have. Whichever lands second needs a rebase of the shared files.
- #8254 (draft) edits the README's setup steps and the step-time sentence that this PR also changes.
- No open PR changes the torchtitan pin or the Qwen3-4B settings.

- **Trade-off: learning per step and per minute.** Samples are staler with a second queued batch, so reward in steps 11-50 is lower than with the previous settings (0.80 vs 0.86 on this image). Measured against time it is also slightly behind: the 10-step average reward reaches 0.85 after 19.1-19.4 vs 15.8 min of step time, and 0.90 after 22.9-25.0 vs 21.0 min. The 100 steps still finish 4 min sooner, and GSM8K accuracy at step 100 (0.930 and 0.953 vs 0.938) is within the ±0.02 noise of 128 validation samples. `NUM_WARMUP_BATCHES=1` keeps the previous freshness and learning curve. Measured on `main`, the other two settings then still make each step 3-7% faster per generated token.
- `actor/grad_norm` has occasional large clipped spikes with either settings (9,665 and 9,666 on this image; none in the rerun).
- The earlier `8d79e16` torchtitan pin is no longer on a `google-pytorch/torchtitan` branch. The code the plugin engine imports is byte-identical in `8d79e16` and `ea7fec0f`.

### Design & Code Changes

- `examples/tpu/grpo/Dockerfile`:

  | package | before | after |
  |---|---|---|
  | torchtitan (`google-pytorch/torchtitan`) | `f880cc73` | `ea7fec0f` |
  | jax / jaxlib | 0.10.2 | **0.11.1** |
  | libtpu | 0.0.47 | **0.0.50** |
  | torchao | not installed | **0.17.0** (torchtitan's float8 converter needs it) |
  | tokamax | 0.0.14 | 0.0.14 (it requires jax>=0.11, which 0.10.2 did not meet) |
  | spmd_types | 0.2.1 (pinned here) | 0.2.5 (pinned by torchtitan's `requirements.txt`) |

  - `PIP_EXTRA_INDEX_URL` is removed. It sent every pip call to the TorchTPU index as well, but only `torch-tpu` and `tpu-sync-torch` come from there, and `tokamax` 0.0.14 is on PyPI. During one build, the index returned HTTP 404 for one of tokamax's dependencies.
  - Unchanged: Ray 2.56, torch 2.13.0, torch-tpu `0.1.2.dev20261006000518`, tpu-sync-torch `0.0.1.dev20261006025601`, vllm-torchtpu `9faafb17`, vLLM v0.29.0, transformers 5.10.x.
- `examples/tpu/grpo/README.md`:
  - the verl-hardware-plugin checkout described above;
  - the 4B step time changes from "20-30 s (~25 s average)" to "18-27 s (~22 s average over 100 steps)".
- `examples/tpu/grpo/run_qwen3_4b_torchtitan.sh`:

  | setting | env var | before | after | why |
  |---|---|---:|---:|---|
  | `trainer.v1.separate_async.num_warmup_batches` | `NUM_WARMUP_BATCHES` | 1 | **2** | A second queued batch refills freed decode slots at once. With one batch ahead, the rollout's 256 slots average 74% full and the trainer waits for each batch's long tail. |
  | `actor_rollout_ref.rollout.max_num_batched_tokens` | `MAX_NUM_BATCHED_TOKENS` | 1536 (`MAX_MODEL_LEN`) | **4096** | Each weight sync aborts ~230 in-flight rollouts, which re-prefill as partial rollouts. A larger step budget does this in fewer engine steps (restart 3.0 s -> 1.9 s). |
  | `actor_rollout_ref.actor.torchtitan.pad_to_length_bucket` | `PAD_TO_LENGTH_BUCKET` | 1024 | **512** | Late in training the run is trainer-bound and packed micro-batches are ~1,090 tokens, which 1024-token buckets pad to 2,048. 512-token buckets cut `update_actor` time per token by 3-8%. |

**Security Blast Radius**
- _inferred_ — Compromise of the selected image or plugin would inherit the example workload's existing pod authority, including its service account, mounted bucket and host /tmp mounts. The documented bucket grant is objectViewer for the selected bucket, rather than model-specific isolation. These grants and mounts predate this PR; actual deployment permissions depend on the operator's selected account.

**Trust Boundaries and Controls**
- _observed_ — The external plugin remains operator-selected executable code uploaded through the Ray job runtime environment and loaded by the trainer. The new overlap controls are launch-environment values passed as configuration arguments; the PR does not introduce a new remote configuration endpoint or authorization mechanism.

**Resilience and Maintainability Implications**
