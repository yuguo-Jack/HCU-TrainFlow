# [rollout, vllm, perf] feat: add bounded resume admission burst

[Upstream PR](https://github.com/verl-project/verl/pull/8136) · state: open · merged: False

## Original PR description

### What does this PR do?

When tools return during a multi-turn rollout, their continuation requests can
wait behind a large wave of first requests. Add an opt-in router that admits a
bounded number of extra continuation/retry requests while keeping base slots
available to fresh work. vLLM continues to use FCFS.

`ToolAgentLoop` labels requests as fresh, continuation, or retry; partial-rollout
retries refresh that metadata. The router preserves existing sticky,
least-loaded replica routing and records admission counts and wait times.

Queued admissions and release/control RPCs now use separate Ray concurrency
groups. Per-attempt admission IDs make completion idempotent, cancellation
reconciles remote grants, and server removal retires outstanding accounting.
A canceled client retains its slot while backend generation is still running.
Fresh-wave burst defaults to zero, and overdue fresh work stops new burst
admissions. The plugin remains opt-in; no unmeasured backend-pressure
thresholds or automatic tuning are added.

Backend request-priority policies, their configuration fields, SGLang priority
forwarding, and the companion effective-cost admission plugin are removed from
the final diff. The existing explicit vLLM priority path for single-turn
determinism is unchanged. Historical priority experiments remain documented as
evidence for retaining FCFS, without configuration examples for removed APIs.

This updates the existing contribution and replaces closed draft #8135; it does
not introduce a second PR. The earlier duplicate-work checks are recorded at:

uses the capacity-40, fresh-wave-cap-1, resume-cap-20 router below.

An earlier four-GPU study measured 22.459374 seconds for the original FIFO
baseline and 16.035935 seconds after joint engine/router tuning (-28.60%). This
is a historical comparison from a separate measurement batch; it does not
isolate the contribution of burst admission. Full TTFT, queue, utilization,
preemption, prefix-cache, environment, and rejected-case details are recorded
in `docs/advance/agent_loop.rst`.

These are standalone serving measurements, not a full PPO training run or a
validation of live-trainer replica balance. Expert parallel remains excluded
from the production recommendation because output equivalence is unverified.
The serving measurements above predate the lifecycle fixes in this update.
No GPU rerun was performed for these fixes: read-only cluster inspection found
no immediately available idle burst node, and existing jobs were left intact.
The current implementation still needs a same-engine, same-base-capacity
burst-on/off GPU comparison before extending the workload recommendation.

Burst does not help every workload. In the earlier TP8 capacity-40 active-burst
candidate, wall time was 14.081865 seconds versus 12.188314 seconds for the
capacity-64 FIFO cross-check (+15.54%). Its coefficient of variation was 2.20%,
so it was rejected. Capacity changed as well, so this is evidence against that
configuration, not an isolated measurement of burst cost.

### API and Usage Example

Router YAML for the tested single-TP4 workload:

```yaml
router_class: verl.workers.rollout.router.SoftAdmissionRequestLoadBalancer
max_concurrent_requests: 40
fresh_wave_max_resume_burst_requests: 1
max_resume_burst_requests: 20
fresh_max_wait_seconds: 60
```

```yaml
actor_rollout_ref:
  rollout:
    name: vllm
    scheduling_policy: fcfs
    max_num_seqs: 32
    engine_kwargs:
      vllm:
        max_num_batched_tokens: 32768
        async_scheduling: false
    router_config_path: /path/to/request_router.yaml
```

These settings are workload-specific examples, not new defaults. Without the
router configuration, the existing default load balancer is used.

### Design & Code Changes

The base admission capacity is available to every request. Only continuation
and retry requests can use extra burst slots. The burst target is:

```text
min(current_burst_cap,
    ceil(base_capacity * resume_pressure / total_pressure))
```

Pressure includes queued and in-flight requests. The lower fresh-wave cap
defaults to zero while fresh requests remain queued; explicitly measured
configurations can opt into a small cap. The larger cap applies after the
router fresh queue drains, which means admission, not backend completion.
Overdue fresh work stops new burst admissions; existing requests are not
preempted. The threshold does not promise an end-to-end latency bound.

Each backend attempt receives a unique admission ID, separate from the sticky
trajectory ID. Duplicate and stale releases cannot free another attempt.
Client cancellation cancels a queued Ray acquire and reconciles a grant that
completed first. After backend generation starts, cancellation defers release
to backend completion/failure. Server removal clears its grants, and late
completion cannot affect replacement work; the caller remains responsible for
stopping generation on the removed server.

Ray admission and control methods run in separate concurrency groups, with a
lock protecting shared state and thread-safe waiter delivery. Saturating the
admission group therefore leaves release and server-management RPCs runnable.
No polling or extra RPC is added to the successful request path.

Removing `router_config_path` fully restores the default load balancer.
Setting only `max_resume_burst_requests: 0` still retains base admission limits.
No backend queue/KV-cache thresholds are inferred from request counts; tune
and validate the opt-in configuration using full rollout wall time.
