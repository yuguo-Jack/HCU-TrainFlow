# [training_utils] fix: preserve RL-Insight gauge scalar name and step metadata

[Upstream PR](https://github.com/verl-project/verl/pull/8357) · state: closed · merged: False

## Original PR description

### Problem and change

`RLInsightLogger.log(data, step)` currently discards `step` and replaces `/` with `_` in every scalar name before calling `metric_gauge`. A push exporter consequently cannot recover the caller's exact metric name or associate its value with the supplied training step.

Keep the existing flattened gauge name and numeric value, and pass the original name and explicit step through `rl_insight_metric_name` / `rl_insight_step` event labels. Update the logger contract test. This uses the existing gauge keyword-label API and does not require a newer rl-insight `metric_log` API.

For example, `log({'actor/loss': 0.0}, step=7)` emits the same `actor_loss` gauge value, plus original-name and step metadata for an exporter that consumes them. The exporter still needs to map these labels to its own metric-log fields; this patch alone does not change a dashboard or add a storage backend.

### Related work and review scope

Related: #8315. That PR prefers the newer `metric_log` API and leaves the old `metric_gauge` fallback without step metadata; it also adds async weight-sync and rollout-state tracing. This patch targets the existing gauge path, including installs without `metric_log`, and does not add those tracing changes. The approaches overlap on preserving training-step information and should be coordinated rather than both applied blindly. If #8315 is the preferred solution, this can instead be considered as a compatibility follow-up for its legacy gauge fallback.

Duplicate search: https://github.com/verl-project/verl/pulls?q=is%3Apr+is%3Aopen+RLInsightLogger+step

### Validation

- Executed the actual `RLInsightLogger.log` method in a CPU-only AST harness: preserves an unknown original metric name, explicit step and zero value; skips non-scalar input. This avoids importing the GPU training stack.
- Repository commit hooks passed for the patch, including Ruff, formatting, mypy and compilation. Rebasing onto main left the two-file patch unchanged; diff checks passed afterwards.
- The updated `tests/utils/test_rl_insight_logger_on_cpu.py` assertion covers the new call contract. The complete core/GPU suite and a GPU end-to-end run of this metadata extension have not been run.

### Compatibility / limitations

Consumers that turn all gauge labels into time-series dimensions should consume or remove `rl_insight_step` before storage to avoid per-step series cardinality. The labels are metadata for compatible push exporters; no consumer-side stripping is added here. That tradeoff is part of the requested review.

AI assistance was used to implement and validate this patch. Draft pending human review of every changed line and human-run validation under the repository contribution policy. No automatic merge.

# RL-Insight

Online observability for reinforcement learning training. RL-Insight connects training-side metrics, RL state traces, and service dashboards across distributed rollout and optimization workloads.

## Why RL-Insight

RL-Insight focuses on the online observability path that RL training needs most:

  * One-command server startup: install dependencies and start the RL-Insight server with Prometheus, Tempo, and Grafana with `rl-insight server install` and `rl-insight server start`.
  * Trainer and rollout metric aggregation: collect key actor, rollout, and transfer queue metrics in one monitoring view while keeping training-side instrumentation lightweight.
  * CPU and Ascend NPU monitoring: register node_exporter and NPU Exporter endpoints to view hardware metrics in the RL-Insight Grafana dashboards.
  * Grafana dashboards for RL workloads: provide ready-to-use dashboard structure for training metrics, rollout behavior, engine metrics, and RL state timelines.

## Architecture

RL-Insight has two metric sources. Training code reports framework-internal signals through the Python API, and RL subsystems such as rollout engines and transfer queues register their own `/metrics` endpoints through the metric aggregation interface. The RL-Insight server coordinates the training side and manages Prometheus, Tempo, and Grafana so metrics, traces, and subsystem signals converge into unified RL dashboards.

L190: # RL-Insight
L191: 
L192: Online observability for reinforcement learning training. RL-Insight connects training-side metrics, RL state traces, and service dashboards across distributed rollout and optimization workloads.
L193: ## Why RL-Insight
L194: 
L195: RL-Insight focuses on the online observability path that RL training needs most:
L196:   * One-command server startup: install dependencies and start the RL-Insight server with Prometheus, Tempo, and Grafana with `rl-insight server install` and `rl-insight server start`.
L197:   * Trainer and rollout metric aggregation: collect key actor, rollout, and transfer queue metrics in one monitoring view while keeping training-side instrumentation lightweight.
L198:   * CPU and Ascend NPU monitoring: register node_exporter and NPU Exporter endpoints to view hardware metrics in the RL-Insight Grafana dashboards.
L199:   * Grafana dashboards for RL workloads: provide ready-to-use dashboard structure for training metrics, rollout behavior, engine metrics, and RL state timelines.
L200: ## Architecture
L201: 
L202: RL-Insight has two metric sources. Training code reports framework-internal signals through the Python API, and RL subsystems such as rollout engines and transfer queues register their own `/metrics` endpoints through the metric aggregation interface. The RL-Insight server coordinates the training side and manages Prometheus, Tempo, and Grafana so metrics, traces, and subsystem signals converge into unified RL dashboards.

## Training API

`rl_insight/` exports the online monitor public API, so training code can import one module:

API  | Use
--- | ---
`init(project=None, experiment_name=None, config=None)`  | Enable monitoring once per process and attach global labels.
`metric_count(name, amount=1.0, documentation=&quot;&quot;, **labels)`  | Increment a Prometheus counter.
`metric_gauge(name, value, documentation=&quot;&quot;, **labels)`  | Record the latest value for a gauge.
`metric_histogram(name, value, documentation=&quot;&quot;, **labels)`  | Add one sample to a histogram.
`trace_state(state_name, state_lane_id=None, **labels)`  | Record a named RL state interval.
`trace_op(name=None, extra_labels=None, **static_labels)`  | Decorate a synchronous function and emit one duration span per call.
`finish()`  | Reset in-process monitor state.

Configuration can be passed to `insight.init(config=...)` or through environment variables:
    
    insight.init(
        project=&quot;verl&quot;,
        experiment_name=&quot;ppo-smoke-test&quot;,
        config={
            &quot;server&quot;: {
                &quot;namespace&quot;: &quot;rl_insight_monitor&quot;,
                &quot;backend&quot;: &quot;ray&quot;,
                &quot;url&quot;: &quot;http://&lt;server-ip&gt;:18080&quot;,
            },
            &quot;prometheus&quot;: {
                &quot;metrics_report_port&quot;: 9092,
            },
        },
    )

Useful environment variables:

Variable  | Purpose
--- | ---
`RL_INSIGHT_SERVER_URL`  | RL-Insight server URL, for example `http://&lt;server-ip&gt;:18080`.

**Remove `rl_insight_step` from the gauge labels.**

`rl_insight.metric_gauge` treats keyword arguments as Prometheus labels. The PPO loop logs `training/global_step` on every iteration, then increments `self.global_steps`. Each step therefore creates a new time series instead of updating the existing gauge. Long runs can accumulate one series per step.
