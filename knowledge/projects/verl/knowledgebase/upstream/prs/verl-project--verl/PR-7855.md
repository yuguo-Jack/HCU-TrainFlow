# [algo, fsdp, megatron, veomni] feat: add tail-aware top-k KL for on-policy distillation

[Upstream PR](https://github.com/verl-project/verl/pull/7855) · state: closed · merged: True

## Original PR description

### What does this PR do?

Adds a `forward_kl_topk_tail` loss mode for on-policy distillation.

The existing `forward_kl_topk` objective retains only the teacher's top-k terms:

```
L_truncated = Σ_{i∈T} p_i (log p_i − log q_i)
```

Because `T` is truncated, the retained masses `P = Σ_{i∈T} p_i` and `Q = Σ_{i∈T} q_i` are both below 1. The quantity is therefore not a KL and goes negative whenever `Q > P`; the current implementation clamps it with `clamp_min(0)`, which silently discards the gradient carried by those tokens. In our runs the per-token minimum was exactly `0.0` (clamping active) in **415 / 467 training steps (89 %)**.

This PR treats every token outside `T` as one aggregate category:

```
p_tail = 1 − P,  q_tail = 1 − Q
L_tail = Σ_{i∈T} p_i log(p_i / q_i) + p_tail log(p_tail / q_tail)
```

which is the exact KL between the two `K+1`-category distributions: non-negative by construction (no clamp), a lower bound on the full forward KL, and it reuses the existing teacher top-k payload, so teacher compute, schema and network traffic are unchanged.

**The claim of this PR is training efficiency**: at an equal training-step budget, `forward_kl_topk_tail` reaches a higher GSM8K accuracy than `forward_kl_topk`; equivalently, it reaches a given accuracy in fewer steps. It is not a claim about a higher final ceiling — the two curves approach the same asymptote and the gap narrows with longer training, which is the expected shape of faster convergence.

Related in verl: #7239 / #7375 (full-vocabulary OPD), #6676 / #7590 / #7806 (reverse-KL on the student top-k support), #7733 / #7809 (memory/perf work on the existing top-k path) — none of them change the truncated forward-KL objective.

**The objective itself is prior art, and this PR does not claim it as new.** Section 3.3 of the [LFM2 Technical Report](https://arxiv.org/abs/2511.23404v1) optimizes `KL(Bern(P_T) || Bern(P_S)) + P_T * KL(P_T(.|T) || P_S(.|T))`; at temperature 1 that is algebraically the coarse-grained KL written above, and the report states the same lower bound. The aggregate tail bucket is the *ghost token* of [Sparse Logit Sampling](https://aclanthology.org/2025.acl-long.885.pdf). What this PR adds is the integration into the OPD path: the analytic gradient on the out-of-top-k tokens for vocab-parallel (Megatron TP) shards so no rank gathers logits, reuse of the existing `[S, K]` teacher payload with no schema or communication change, the `tail_mass_eps` guard semantics, tests + TP parity, and the efficiency measurement below.

The new coverage asserts: non-negativity; equality against an independent coarse-distribution oracle; autograd gradient equality; analytic sharded-gradient equality with cross-shard teacher IDs; the lower-bound property across K; equality with the full KL when K spans the vocabulary; regular and chunked FSDP paths; invalid clamp/epsilon configuration; and the fused-mass fallback / fail-closed behaviour.

```bash

# [PASS] VP KL divergence correctness verified for test case 0..3
# [PASS] VP tail-aware KL correctness verified for test case 0..3
```

Loss, `student_mass`, `teacher_mass` and `tail_loss` match the FSDP reference, and every vocabulary-shard gradient matches FSDP within `atol=rtol=1e-4`; existing truncated top-k cases do not regress.

Synthetic full-KL benchmark (`examples/on_policy_distillation_trainer/benchmark_tail_kl.py`) — gradient cosine similarity to the true full-KL gradient, and the frequency of negative (clamped) truncated losses:

| K | truncated | tail-aware | negative truncated loss frequency |
|---|---|---|---|
| 8 | 0.303 | 0.455 | 6.25 % → 0 % |
| 16 | 0.327 | 0.561 | 0 % |
| 32 | 0.393 | 0.653 | 0 % |
| 64 | 0.488 | 0.793 | 0 % |

Scalar error relative to the full KL is *not* uniformly better (it is slightly worse), which is expected: tail-aware KL is a lower bound, not a better point estimate. We do not claim otherwise.

Real-model efficiency measurement — student Qwen3-1.7B (FSDP + colocated vLLM rollout) and teacher Qwen3-32B (vLLM TP=2) on 3×RTX A6000, GSM8K, batch 16, identical seed/data/batch/optimizer for both arms, validation on the full 1319-example test set (standard error ≈ ±1.3 pp). The only difference between arms is `loss_mode`; both arms run with `log_prob_min_clamp=null`.

Experiment A (same run, same step grid):

| steps | `forward_kl_topk` | `forward_kl_topk_tail` |
|---|---|---|
| 175 | 0.3177 | **0.3472** |
| 350 | 0.3457 | **0.3616** |

At 175 steps the tail-aware arm already matches what the baseline reaches at 350 steps (0.3472 ≥ 0.3457) — i.e. **≤ 50 % of the training steps for the same accuracy**.

Experiment B (independent seed, earliest phase):

| steps | `forward_kl_topk` | `forward_kl_topk_tail` |
|---|---|---|
| 50 | 0.3412 | **0.4246** |

The leading margin shrinks with training (50 steps +8.34 pp, 175 steps +2.96 pp, 350 steps +1.59 pp), consistent with two curves sharing an asymptote but converging at different rates.

Cost is unchanged: 142.6 vs 143.0 tokens/s, 40.58 vs 40.61 GB peak HBM, and `grad_norm` of the same order, so the efficiency difference is not bought with extra compute. Mechanistically, `loss_min` is exactly `0.0` (clamped) in 415/467 steps for the baseline versus `≈ −1e−7` (finite-precision noise, never clamped) for the tail-aware arm, while the top-k overlap ratio is essentially identical (0.7153 vs 0.7119), i.e. the difference does not come from different token selection.

Caveats: both arms are single-seed, and the measured run-to-run noise for the same arm at the same step is ≈3.3 pp, so Experiment B's margin is ≈2.5× the noise while Experiment A's is of the same order. We report three step budgets rather than only the most favourable one, and multi-seed error bars are in progress.

### API and Usage Example

No API change; it is a new value for an existing config field.

```bash
distillation.distillation_loss.loss_mode=forward_kl_topk_tail
distillation.distillation_loss.topk=16
distillation.distillation_loss.log_prob_min_clamp=null   # required by this mode
distillation.distillation_loss.use_policy_gradient=false  # intended setting
```

`tail_mass_eps` (new, default `1e-6`) is the numerical guard on `q_tail`; it must lie strictly between 0 and 1.

### Design & Code Changes

- `verl/trainer/distillation/tail_kl.py` (new): stable tail-bucket value computation in FP32, plus an analytic, Megatron-independent logit-gradient helper. For `j` inside the teacher top-k `dL/dz_j = q_j − p_j`; for `j` outside, `dL/dz_j = q_j (P − Q) / (1 − Q)`, which every vocabulary shard can apply locally without gathering logits. The helper also matches the derivative of the `q_tail.clamp_min(tail_mass_eps)` guard when it is active.
- `verl/trainer/distillation/losses.py`: registers the mode with `use_topk=True` (so the teacher path requests top-k log-probs as before), dispatches to the FSDP/VeOmni and Megatron backends, keeps `clamp_min(0)` only for the legacy mode, and adds `head_loss`, `tail_loss`, `teacher_tail_mass`, `student_tail_mass` metrics. If a fused engine returns a detached `student_mass` it fails closed instead of silently training with an incomplete gradient.
- `verl/trainer/distillation/fsdp/losses.py`: refactors the existing top-k path without changing legacy behaviour, adds `compute_forward_kl_topk_tail`, and supports both the regular and `use_chunked_topk=True` paths.
- `verl/trainer/distillation/megatron/losses.py`: extends `_VocabParallelKLDivergence` with `include_tail` / `tail_mass_eps`, all-reduces the student top-k mass across TP ranks, and uses the shard-local analytic gradient in backward.
- `verl/workers/config/distillation.py` + config YAMLs: `tail_mass_eps`, validation rules (strictly between 0 and 1; `forward_kl_topk_tail` requires `log_prob_min_clamp=null`), and a warning when combined with `use_policy_gradient=true`. Per-entry log-prob clamping is rejected for this mode because it would change the selected top-k mass and invalidate the coarse-grained KL.
- Tests, benchmark, docs and generated configs as listed in the diff.

**VeOmni backend.** Two notes, neither of which is a defect in VeOmni:

- *Fused-kernel masses — our earlier claim was wrong.* Our first measurement with `model_engine=veomni` + `use_fused_kernels=True` showed `teacher_mass ≈ 2.11e-4`, which we described as the fused kernel's mass outputs being degenerate. Instrumenting the payload showed instead that every teacher top-k log-prob was exactly `-log V` — the *teacher payload* was uniform — and `2.11e-4 = K / V` is the correct mass of that payload. Serving the same teacher directly through vLLM returns a real distribution, and re-running the example with the default `distillation.teacher_models.teacher_model.*` entry instead of the named `+distillation.teacher_models.gsm8k.*` entry delivers a real payload (`Σ exp = 0.0377`). The artefact was in our own configuration, not in the fused kernel.
- *Design limitation (documented).* `chunk_topk_distill` returns `student_mass` / `teacher_mass` with `requires_grad=False` by design, so the tail bucket cannot receive gradient through the fully-fused path. `forward_kl_topk_tail` therefore requires `use_fused_kernels=False` on the VeOmni backend; the fail-closed guard rejects the fused combination rather than silently training with an incomplete gradient.

Two environment-level blockers were also worked around for the measurement: veomni 0.1.11's generated Qwen3 patch passes `cache_position` to `transformers.masking_utils.create_causal_mask`, which the pinned transformers 5.9.0 no longer accepts; and single-GPU VeOmni runs need `actor_rollout_ref.actor.veomni.init_device=cuda` because `fsdp_enabled` is false when `fsdp_size == 1` while the default is `meta`.

**What we actually measured.** In the run we reported, the teacher's top-k log-probs were uniform: every entry was exactly `-log V`, so `Σ_k exp(log p_k) = K / V` — that is, the `2.1099e-4` we reported as "degenerate" is precisely the mass of the payload the loss was handed. The fused kernel computed it correctly; in the same run `student_mass` spans `4e-17 … 0.99999`, as it should.

**Where the uniform payload came from.** Two checks, both pointing away from VeOmni:

1. Serving the same Qwen3-1.7B directly through vLLM with `prompt_logprobs=32` returns a real distribution (`':'` at -1.50, `' is'` at -2.38, `'’s'` at -2.63, …), so the model and the log-prob request path are fine.
2. Re-running the VeOmni example **unchanged except for the teacher entry** — the named `+distillation.teacher_models.gsm8k.*` block replaced with the default `distillation.teacher_models.teacher_model.*` entry — delivers a real payload: first eight log-probs `[-4.40, -5.90, -6.46, -6.59, -6.77, -6.77, -6.96, -6.99]` and `Σ exp = 0.0377` instead of `K / V`.

So the degenerate payload was an artefact of how we had configured the teacher in that run (a named-teacher entry, alongside the three local workarounds for transformers 5.9.0 / FA2 / single-GPU init) — not the fused kernel, and not VeOmni.

One VeOmni limitation **does** apply, and it is a documented design choice: `chunk_topk_distill` returns `student_mass` / `teacher_mass` with `requires_grad=False` (they are reported as metrics; the kernel carries its own analytic backward for the truncated objective). Good question — that branch is easy to misread, and you're right that it is the one place where the mode and the payload disagree. It is for **fused engines**: the non-fused FSDP and Megatron implementations return `tail_loss` themselves and take the `if tail_loss is not None` branch above, whereas a fused engine that computes the existing top-k objective in-kernel (e.g. VeOmni's `chunk_topk_distill`) returns only the head loss plus `student_mass` / `teacher_mass`, so we add the tail bucket here from those masses — no new teacher request, no `[T, V]` logits.

Because the two tails play different roles, and clamping the teacher side to `tail_mass_eps` may be incorrect:

- **Student tail** sits inside a logarithm (`log(q_tail)`) as the denominator. `q_tail = 0` sends both the loss and its gradient to infinity, so `tail_mass_eps` is exactly the bound we want there.
- **Teacher tail** is only a *multiplicative weight*: as `p_tail → 0` the whole term vanishes by continuity (`x log x → 0`). Clamping it to `tail_mass_eps` would inject a spurious `eps · log(eps / q_tail)` contribution for every token whose teacher top-k mass is exactly 1, i.e. it would make the loss depend on the guard rather than on the distributions.

This is not hypothetical: on the FSDP path we measure `actor/distillation/teacher_mass_max` of `1.0000001 … 1.0000005` (fp32 rounding of a top-k mass that is exactly 1), so `p_tail = 1 - mass` is `0` after the `clamp(min=0)`, and the spurious term would be added on those tokens.

So `p_tail` is left unclamped and only the *input of its logarithm* is floored at the dtype minimum, which keeps `log` finite without changing the product (an exact-zero teacher tail still contributes exactly zero). I've expanded the in-code comment to spell this out.

Working through §3.3, its decoupled Top-K objective is the *same* loss at temperature 1:

```
KL(Bern(P_T) || Bern(P_S)) + P_T * KL(P_T(.|T) || P_S(.|T))
  = sum_{i in T} p_i log(p_i / q_i) + (1 - P_T) log((1 - P_T) / (1 - Q_S))
```

which is exactly the expression this PR computes, and the report makes the same lower-bound remark for τ=1 ("it omits the teacher tail where logits are unavailable"). So the objective itself is prior art, and `90bd3548` makes the docs and the PR description say that explicitly instead of only listing it as related work.

What is left here is the integration rather than the objective: the analytic gradient on the out-of-top-k tokens for vocab-parallel (Megatron TP) shards, so no rank gathers logits; reuse of the existing `[S, K]` teacher payload with no schema or communication change; the `tail_mass_eps` guard semantics; and tests, TP parity and an efficiency measurement in verl.
