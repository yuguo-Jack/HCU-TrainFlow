# [ckpt, worker] feat: mori checkpoint engine sharded export (no trainer all-gather)

[Upstream PR](https://github.com/verl-project/verl/pull/8535) · state: closed · merged: False

## Original PR description

### What does this PR do?

This is a follow-up to #8482 (the `mori` checkpoint engine) and builds on it; only the last commit is new. It adds `export: shard`. Each trainer rank sends only its own shards from the training engine's `get_per_tensor_param_shard()`, in bf16 and using the contract in `verl/workers/engine/spec.py`, so the trainer no longer all-gathers every parameter. Rollout workers assemble full tensors from the pieces of all stripes and split packed MoE experts, as the FSDP full export does. Server adapters see the same `(name, full tensor)` stream as before.

On Qwen3-30B-A3B with 2 nodes and FSDP2, a sync takes 0.47 s with shard export, against 0.65 s with the full export and 1.40 s with `nccl` (Results below).

Related: #8395 (sharded_nixl) and the NCCL M2N series (#7432, #7552, #8087, #8088) also avoid the trainer all-gather. This PR reuses the shard-export contract already on main and does not depend on them.

### Design & Code Changes

- `verl/checkpoint_engine/mori_checkpoint_engine.py`:
  - **Stripe contents.** Stripe r carries trainer rank r's local shards. A piece's `TensorMeta` gives the full tensor's shape and dtype, and `chunk_offset` is the piece's byte offset in that tensor. Receivers copy each piece into the full tensor and yield the tensor once it is complete.
  - **Supported engines.** Only engines whose shard export is in HF layout. `BaseEngine` gains `per_tensor_param_shard_is_hf`, which defaults to False. `FSDPEngine` sets it. `VeOmniEngine` resets it, because its fused experts need converter specs. Megatron shards are MCore-named local TP slices, so they are refused.
  - **Supported shards.** Shards must be one flat range of the full tensor, as with FSDP2 `Shard(0)`. Replicated tensors are sent once. `num_chains` must be >= the trainer world size.
  - **Refused.** LoRA, QAT, and specs with `to_hf_chunk` / `hf_slots`. A refusal aborts the sync on every worker.
  - **Bounded memory.** Receivers hold at most `num_slots * bucket_size` plus the largest tensor in partly assembled tensors.
    - A stripe starts a new tensor only if the tensor fits in that budget, or if it is the next incomplete tensor in export order.
    - The check and the reservation happen without yielding to the event loop.
    - This cannot deadlock: every tensor is sent by some rank, and all stripes send in export order.
  - **Completeness.** A sync fails if any tensor is still incomplete when every stripe has ended.
- `verl/workers/engine/base.py`, `fsdp/transformer_impl.py`, `veomni/transformer_impl.py`: the `per_tensor_param_shard_is_hf` declaration.
- `verl/workers/engine_workers.py` and `tests/checkpoint_engine/test_utils.py`: the trainer hands its training engine to `send_weights` when the checkpoint engine sets `consumes_training_engine`. This was hard-coded for `delta_sharded` before; that case is kept.

### Test

- CPU: 14 more tests in `test_mori_checkpoint_engine_on_cpu.py`. A fake trainer cuts each tensor along dim 0 with `torch.chunk`.
  - **Shapes.** Uneven and empty shards, empty and 0-dim tensors, replicated tensors, packed MoE experts, 1-3 rollout nodes.
  - **Bounded memory.** Two cases: one stripe much slower than the others, and ranks with empty shards that start on different tensors which are all larger than the budget. In both, peak assembly memory stays within the bound; the earlier admission rule exceeded it and fails the second case.
  - **Failures.** A tensor left incomplete fails the sync. Each of these is refused:
    - an engine whose shards are not in HF layout (Megatron-like);
    - LoRA;
    - QAT;
    - specs that need a to-HF conversion;
    - a source that is not a training engine.
- GPU: `test_mori_checkpoint_engine` gains an `export="shard"` case: FSDP, Qwen3-8B, 3 syncs compared tensor by tensor.
- **End to end** (verl's V1 separate_async GRPO with a real vLLM rollout, GSM8K, an earlier version of this PR). With 2 nodes and 7B, GSM8K test accuracy after 20 steps was 0.909, against 0.901 with nccl.

- 1 node, 0.5B, 30 steps: test accuracy 0.000 → 0.268 (nccl 0.001 → 0.258).
- 2 nodes, 7B, 20 steps: test accuracy 0.785 → 0.909 (nccl 0.785 → 0.901).

### Results

The setup and the statistic are the same as in #8482: Qwen3-30B-A3B, FSDP2, 2 nodes, and the median of 9 syncs after the first, all from one run on the commit of this PR. The first two syncs of every configuration that transfers weights were compared tensor by tensor on all 8 rollout workers, 16/16 consistent each.

| | seconds per sync (median of 9) |
|---|---|
| floor: the trainer only iterates `get_per_tensor_param_shard()` | 0.296 |
| mori, shard export, 2048 MB, 4 slots | **0.469** |
| mori, full export (#8482) | 0.647 |
| nccl, 2048 MB | 1.403 |

**Bytes on the wire.** Shard export ships bf16, 61 GB for this model, which is what the rollout loads. The full export on main ships fp32, 122 GB.

<details><summary>Earlier runs and a small model</summary>

- Six earlier runs of earlier versions, on 3 node pairs, with 5-7 syncs each, gave shard-export medians of 0.38-0.44 s. Their floors were 0.29-0.43 s; one node pair has a 0.43 s floor.
- Qwen2.5-0.5B, FSDP2: shard export 0.073 s, against 0.117 s for the full export and 0.126 s for nccl.

</details>

### API and Usage Example

```yaml
actor_rollout_ref:
  rollout:
    checkpoint_engine:
      backend: mori
      update_weights_bucket_megabytes: 2048
      engine_kwargs:
        mori:
          num_chains: 8      # >= trainer world size
          num_slots: 4
          export: shard
```
