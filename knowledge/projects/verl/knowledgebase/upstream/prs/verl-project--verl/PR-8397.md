# [rollout, vllm] fix: release the submission-gate barrier when a request lands in the engine, not on its first token

[Upstream PR](https://github.com/verl-project/verl/pull/8397) · state: closed · merged: True

## Original PR description

### What does this PR do?

Before a weight sync, `abort_all_requests()` waits for `_admitting == 0` (no request is between the submission gate and the engine) and only then calls `pause_generation()`. `generate()` decremented `_admitting` only on the request's **first output**, i.e. once it had been scheduled and prefilled. With `len(batch) > max_num_seqs`, most requests sit in vLLM's WAITING queue for seconds, so the pause had to wait until every one of them was scheduled and prefilled, and then aborted them anyway.

On Qwen3-8B (TPU v6e-8, 256 requests vs `max_num_seqs=32`) this cost **5–14 s of pause per weight sync**. The same code path is used on GPU.

The fix: call `AsyncLLM.add_request()` directly and release `_admitting` as soon as it returns. At that point the request is registered in the output processor and has been sent to EngineCore over the same ordered socket that `pause_scheduler` uses, so a later pause still covers it.

### API and Usage Example

### Design & Code Changes

- `vLLMHttpServer._generate_admitted()` calls `engine.add_request(...)` (forwarding `data_parallel_rank`), releases `_admitting`, then drains the per-request collector the same way `AsyncLLM.generate()` does.
- On cancellation or error, it aborts the request in the engine (except on `EngineDeadError`), matching `AsyncLLM.generate()`.
- The test fake engine implements `add_request()` instead of `generate()`.
- `AsyncLLM.add_request(..., data_parallel_rank=...)` is available in vLLM 0.18 (the `setup.py` minimum) through 0.32 (the `pyproject.toml` pin).
