# [algo] fix: clamp the optimal token baseline weight at zero against float32 cancellation

[Upstream PR](https://github.com/verl-project/verl/pull/8444) · state: open · merged: False

## Original PR description

### What does this PR do?

Fixes a float32 rounding bug in the Optimal Token Baseline (OTB) advantage estimators (`compute_optimal_token_baseline_advantage` and `compute_multi_turn_optimal_token_baseline_advantage`) and the W-score variance proxy (`compute_variance_proxy_metrics`) where the per-token score-norm proxy `w_t = 1 - 2 * pi_t + sum_pi_squared` can become negative on confident tokens ($\pi_t(y_t) \approx 1$), making the cumulative path variance $W_t = \sum_{j=1}^t w_j$ non-monotone or negative and pushing per-timestep baselines $B_t = \sum_i G_{t,i} W_{t,i} / (\sum_i W_{t,i} + \epsilon)$ outside $[0, 1]$ on $[0, 1]$-bounded returns.

**Duplicate check (`AGENTS.md`):** Searched issues and PRs in `verl-project/verl` for `optimal_token_baseline`, `OTB`, `sum_pi_squared`, `w_per_timestep`, and `variance_proxy`:
- OTB / `sum_pi_squared` PRs `#8364` (V1 trainer plumbing) and `#8365` (chunked `sum_pi_squared`), and keyword-matched PRs `#7473`, `#8026`, and `#7866`, do not touch `verl/trainer/ppo/core_algos.py` or `verl/trainer/ppo/metric_utils.py`.
- Open PRs `#8386`, `#8421`, and `#8422` touch other algorithms in `verl/trainer/ppo/core_algos.py` and `tests/trainer/ppo/test_core_algos_on_cpu.py`, not the OTB estimators.
- Input-side log-prob precision issue `#8376` and PRs `#8377` / `#8378` address log-probs that round to `0` in float32 in `torch_functional.py` / fused kernels; they do not touch the OTB estimators and do not eliminate negative $w_t$ (even with exact float32 `old_log_probs` and `sum_pi_squared`, `1 - 2 * pi_t + sum_pi_squared` still evaluates `< 0` on confident tokens).

### Design & Code Changes

#### Root Cause

The Optimal Token Baseline (OTB) and `compute_variance_proxy_metrics` compute the per-token score-norm proxy:
$$w_t = \|e_{y_t} - \pi_t\|_2^2 = (1 - \pi_t(y_t))^2 + \sum_{v \neq y_t} \pi_t(v)^2 = 1 - 2\pi_t(y_t) + \sum_v \pi_t(v)^2$$

In exact arithmetic, $w_t = \|e_{y_t} - \pi_t\|_2^2 \ge 0$ everywhere, so the cumulative path variance $W_t = \sum_{j=1}^t w_j$ is non-decreasing and non-negative.

In `verl`, `old_log_probs` ($\log \pi_t(y_t)$) and `sum_pi_squared` ($\sum_v \pi_t(v)^2 = \exp(\operatorname{logsumexp}(2z_t) - 2\operatorname{logsumexp}(z_t))$) are computed upstream in float32 by two separate reduction paths (`logprobs_from_logits` and `calculate_sum_pi_squared_from_logits` in `verl/utils/torch_functional.py`). When a token is confident ($\pi_t(y_t) \approx 1$, so true $w_t \le 2(1 - \pi_t(y_t))^2 < 2\times 10^{-6}$), the final three float32 operations in `(1 - 2 * pi_t) + sum_pi_squared` are exact for inputs in $[1/2, 1]$, so the subtraction cancels the leading $1$ and directly exposes the float32 rounding errors already present in `old_log_probs` and `sum_pi_squared`. Whenever the rounded `sum_pi_squared` lands below `2 * exp(old_log_probs) - 1` (for example, `old_log_probs = 0.0` giving `pi_t = 1.0` (`0x3f800000`) and `sum_pi_squared = 1.0 - 2^-17` (`0x3f7fff80`)), `1 - 2 * pi_t + sum_pi_squared` evaluates to a negative float32 value (`-2^-17 = -7.629e-6`).

This causes three downstream failures:
1. $W_t = \sum_{j=1}^t w_j$ is no longer monotone non-decreasing and can become negative after a confident prefix.
2. In all-confident prompt groups where $\sum_i W_{t,i} < -\epsilon$, adding $\epsilon = 10^{-8}$ makes the negative denominator $\sum_i W_{t,i} + \epsilon$ slightly smaller in magnitude than $\sum_i W_{t,i}$, pushing the baseline $B_t = \sum_i G_{t,i} W_{t,i} / (\sum_i W_{t,i} + \epsilon)$ above $1$ on all-$1$ returns (e.g. `1.000328` in the reproducer below; in constructed CPU examples where rollout IS weights scale $\sum_i \bar{\rho}_{t,i}^2 W_{t,i}$ near $-\epsilon$ or batch-variant group rows have opposite-signed $W_{t,i}$, the denominator cancellation can invert $B_t$ to `-14.29` or `-762.9`).
3. `compute_variance_proxy_metrics` logs a negative `variance_proxy/expected_w` for an expected squared norm.

#### Minimal Reproducer

```python
import numpy as np
import torch
from verl.trainer.ppo.core_algos import get_adv_estimator_fn

# Float32 witness where 1 - 2 * exp(old_log_probs) + sum_pi_squared < 0:
# pi_t = 1.0 (0x3f800000), sum_pi_squared = 1.0 - 2^-17 (0x3f7fff80) -> -2^-17.
old_log_probs = torch.zeros((4, 1), dtype=torch.float32)
sum_pi_squared = torch.full((4, 1), float.fromhex("0x1.ffff00p-1"), dtype=torch.float32)
rewards = torch.ones((4, 1), dtype=torch.float32)
mask = torch.ones((4, 1), dtype=torch.float32)
index = np.array(["g0"] * 4, dtype=object)

adv, ret = get_adv_estimator_fn("optimal_token_baseline")(
    token_level_rewards=rewards,
    response_mask=mask,
    index=index,
    old_log_probs=old_log_probs,
    sum_pi_squared=sum_pi_squared,
)
baseline = (ret - adv)[0, 0].item()
print(f"Baseline for all-1 returns: {baseline:.6f} (expected in [0, 1])")
```

Output before this PR (`1.000328 > 1.0` on all-`1.0` returns) vs. after (`0.000000`, since $W_t = 0$ on the confident tokens and $\epsilon = 10^{-8}$ shrinks the zero-weight baseline to $0$):
```text
# Before:
Baseline for all-1 returns: 1.000328 (expected in [0, 1])

# After:
Baseline for all-1 returns: 0.000000 (expected in [0, 1])
```

#### Fix

Clamp the per-token weight at zero (`.clamp_min(0)`) at all three sites where `1 - 2 * pi_t + sum_pi_squared` is computed:
- `verl/trainer/ppo/core_algos.py`: `compute_optimal_token_baseline_advantage`
- `verl/trainer/ppo/core_algos.py`: `compute_multi_turn_optimal_token_baseline_advantage`
- `verl/trainer/ppo/metric_utils.py`: `compute_variance_proxy_metrics`

With `w_per_timestep >= 0`, $W_t$ is guaranteed non-negative and non-decreasing, the baseline $B_t = \sum_i G_{t,i} W_{t,i} / (\sum_i W_{t,i} + \epsilon)$ stays a weighted mean of the group's returns shrunk toward $0$ by $\epsilon$ (so for returns in $[0, 1]$ it stays in $[0, 1]$), and `variance_proxy/expected_w` is non-negative.

**Scope note (what this clamp does not change):** The clamp fixes the sign of $w_t$ and the range of the baselines; it does not make their values accurate. In a 512-row synthetic test (512 LM-like bfloat16 rows, vocabulary 151,936, $\pi_t(y_t) \in [1 - 9\times 10^{-4}, 1 - 10^{-7}]$, torch log-prob path), on the 339 rows where the computed $w_t$ stays positive, $|w_t - w_{\text{exact}}|$ has median $1.2\times 10^{-6}$ and max $4.3\times 10^{-6}$, so baselines over confident prefixes remain decided by float32 rounding: the largest $|B_t - B_{\text{exact}}|$ is `0.999` both with and without this change (on a row whose float32 weight is positive noise $1.2\times 10^{-6}$ against an exact $3\times 10^{-13}$). On the 163 rows where the clamp fires, the baseline becomes `0` where the exact value is up to `0.998`: 84 of these baselines move closer to the exact value and 79 move farther, and their mean $|B_t - B_{\text{exact}}|$ goes from `0.49` without this change to `0.51` with it. Over all 512 rows, 387 baselines are more than `0.1` from the exact value with this change (386 without it).

**Possible follow-up (not implemented in this PR):** since $(1 - \pi_t(y_t))^2 \le w_t \le 2(1 - \pi_t(y_t))^2$ and $1 - \pi_t(y_t) = -\operatorname{expm1}(\log \pi_t(y_t))$, a weight computed from `old_log_probs` alone, `torch.expm1(old_log_probs).square()`, bounds $w_t$ within a factor of 2 whenever the log-prob is accurate. In the same test, that float32 weight is within a factor of 2 of the exact $w_t$ on 478/512 rows, and all 512 baselines computed from it are within `0.0073` of the exact value (mean `0.0004`).
