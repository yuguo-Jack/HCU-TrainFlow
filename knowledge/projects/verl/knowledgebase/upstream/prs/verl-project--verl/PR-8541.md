# [ckpt, worker] feat: checkpoint engines that take the training engine; close receive streams on failure

[Upstream PR](https://github.com/verl-project/verl/pull/8541) · state: open · merged: False

## Original PR description

### What does this PR do?

Two small, engine-agnostic hooks for checkpoint engines that live outside verl core. They are what remains in core of #8482 / #8535 after the `mori` engine moved to verl-hardware-plugin, as requested in #8482; the engine itself is verl-project/verl-hardware-plugin#116 (sharded export: verl-project/verl-hardware-plugin#117).

1. **`CheckpointEngine.consumes_training_engine`** (default `False`). When a checkpoint engine sets it, `ActorRolloutRefWorker.update_weights` hands its training engine to `send_weights` instead of a generator of full tensors, as it already does for `delta_sharded`. An engine can then send each rank's own shards (`get_per_tensor_param_shard()`) without an all-gather. `BaseEngine.per_tensor_param_shard_is_hf` (default `False`) declares whether those shards are HF-named and cut in HF coordinates; `FSDPEngine` sets it, and `VeOmniEngine` resets it because its fused expert stacks need converter specs.
2. **`CheckpointEngineWorker.update_weights` closes the receive stream when the server adapter raises or is cancelled**, instead of leaving it to garbage collection (the traceback keeps the generator alive). An engine can then tell its peers at once that the sync failed, even when the adapter fails before taking its first tensor, instead of the peers waiting for a timeout.

No behavior changes for the engines in core: none sets `consumes_training_engine`, and closing an abandoned receive stream only runs its cleanup earlier.

### Test

- `tests/checkpoint_engine/test_global_steps_on_cpu.py` (CPU CI), 2 new tests:
  - a checkpoint engine with `consumes_training_engine` receives the training engine itself, and the trainer still offloads afterwards;
  - `CheckpointEngineWorker.update_weights` closes the receive stream when the adapter raises and when it is cancelled, and re-raises.
  - Each fails if its hook is reverted.
- With the `mori` engine from verl-hardware-plugin on this branch: verl's GPU correctness harness (FSDP, vLLM rollout, `CheckpointEngineManager`, Qwen3-8B-Base, 3 syncs compared tensor by tensor) passes for the full and the sharded export, on 8x MI355X.

### API and Usage Example

```python
class MyShardedCheckpointEngine(CheckpointEngine):
    consumes_training_engine = True

    async def send_weights(self, engine, global_steps=None):  # a BaseEngine, not a generator
        if not engine.per_tensor_param_shard_is_hf:
            raise NotImplementedError("needs HF-layout shards")
        shards, _ = engine.get_per_tensor_param_shard()
        ...
```

### Design & Code Changes

- `verl/checkpoint_engine/base.py`: the `consumes_training_engine` class attribute; the `try/except BaseException` around the adapter call in `CheckpointEngineWorker.update_weights`.
- `verl/workers/engine_workers.py`: `delta_sharded` or `consumes_training_engine` → `send_weights(self.actor.engine)`.
- `verl/workers/engine/base.py`, `fsdp/transformer_impl.py`, `veomni/transformer_impl.py`: `per_tensor_param_shard_is_hf`.
- `tests/checkpoint_engine/test_utils.py`: the test trainer worker honours `consumes_training_engine` too.
