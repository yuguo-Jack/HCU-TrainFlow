# [trainer, worker] feat: add V1 PPO mini-batch modes and per-mini-batch balancing

[Upstream PR](https://github.com/verl-project/verl/pull/8201) · state: open · merged: False

## Original PR description

### What does this PR do?

Adds explicit PPO mini-batch modes to the V1 trainer and balances preserved optimizer mini-batches across data-parallel ranks.

- `fixed_rows` is the default and preserves the current verl behavior: each model targets `ppo_mini_batch_size * rollout.n` trajectory rows per optimizer update, and one UID may cross a mini-batch boundary.
- `fixed_count` is opt-in and follows the fixed-count scheduling proposed in #8099: `ppo_mini_batch_size` is a source-prompt/UID count, all trajectories from one UID stay together, and variable-output rollouts can produce variable row counts without changing the intended UID count per update.

Both modes support different actor and critic mini-batch sizes through shared GCD-sized balancing units. The legacy V0 trainer is unchanged; mini-batch construction and per-mini-batch DP balancing in this PR apply only to V1.

### API and Usage Example

```yaml
trainer:
  use_v1: true
  v1:
    # fixed_rows (default) | fixed_count
    mini_batch_mode: fixed_rows
    sampler:
      # false: train only materialized UIDs
      # true: refill zero-trajectory sync groups
      sync_refill_failed_groups: false
```

`fixed_rows` pads the shared train batch to the least common multiple of the DP size and active actor/critic row mini-batch sizes. Each model then performs `padded_rows / its_row_mini_batch_size` optimizer updates per PPO epoch. With `shuffle=true` and `ppo_epochs>1`, V1 falls back to whole-train-batch DP balancing and lets workers reshuffle trajectory rows each epoch, matching current main behavior.

`fixed_count` groups by source UID, pads and balances each shared unit independently, and permits a partial final UID mini-batch when sync failures leave fewer materialized groups. If `R` UIDs produce at least one trajectory, a model performs `ceil(R / ppo_mini_batch_size)` optimizer updates per epoch. `shuffle=true` is supported for one epoch; combining it with `ppo_epochs>1` is rejected because row reshuffling would split UID groups.

### Design & Code Changes

- Add `trainer.v1.mini_batch_mode` with backward-compatible `fixed_rows` as the default and `fixed_count` as an explicit opt-in.
- Keep one V1 controller balancing pipeline: fixed-row mode forms trajectory-row units, while fixed-count mode forms UID units; both use the GCD of active actor and critic mini-batch sizes so their configured sizes may differ.
- Pad fixed-row batches once to shared actor/critic/DP divisibility. Pad each fixed-count unit independently to DP and active static micro-batch divisibility.
- Balance every preserved unit independently across actor DP ranks, then apply static-micro-batch-friendly workload ordering only within each rank's share of that unit.
- Carry controller-owned variable mini-batch layouts through TransferQueue metadata refreshes. Workers consume padded row boundaries while sequence-level loss normalization excludes synthetic rows.
- Preserve padding-aware normalization in the fixed-row multi-epoch shuffle fallback by carrying an explicit padding mask through worker shuffling and aggregating each resulting mini-batch's valid row count across DP ranks.
- Retain `trainer.v1.sampler.sync_refill_failed_groups=false` by default. Enabling it replaces zero-trajectory groups in synchronous sampling; disabling it avoids additional synchronous rollout work and lets fixed-count mode use a partial final mini-batch.
- Update generated configs and V1/PPO/GRPO documentation, and add CPU coverage for both modes, multi-output UID grouping, actor/critic size differences, partial layouts, padding, shuffle fallback, and worker normalization.
- Leave the legacy V0 `RayPPOTrainer` and its whole-batch balancing behavior unchanged.

Thanks for adding the V1 ordering. There is another case worth considering when deciding where the mini-batch boundaries should be established: synthetic padding for multi-trajectory rollouts.

In V0, `RayPPOTrainer._balance_batch()` first balances the **whole batch** across DP ranks, then applies the following ordering to each rank’s **entire partition**, before workers split it into PPO mini-batches:

```python
for idx, partition in enumerate(global_partition_lst):
    partition.sort(key=lambda x: (workload_lst[x], x))
    ordered_partition = partition[::2] + partition[1::2][::-1]
    global_partition_lst[idx] = ordered_partition
```

Consequently, this ordering can change which samples belong to each subsequent mini-batch. This PR uses the same ordering pattern, but only **within each balancing unit**, preserving the mini-batch membership established beforehand.

That distinction matters for the following V1 `separate_async` case:

- `ppo_mini_batch_size=64`, `rollout.n=8`, `shuffle=False`, and no critic.
- Each local trigger samples 64 prompt groups, normally producing 512 trajectories—one global PPO mini-batch.
- If one rollout session produces an additional trajectory, the sampled batch contains **513 real trajectories**.
- `_balance_batch()` pads this to 1024 samples by appending **511 synthetic padding rows**, whose response masks are zero.

With this PR’s current `shuffle=False` path, the two global mini-batches are established before the within-unit ordering:

| Layout | Mini-batch 1: real / padding | Mini-batch 2: real / padding |
|---|---:|---:|
| Current PR | 512 / 0 | 1 / 511 |
| V0-style whole-partition ordering, DP=1 | 256 / 256 | 257 / 255 |

The second row was verified by replaying the trajectory lengths from two affected batches. It is an observed result for these inputs, rather than a general guarantee of the length-ordering heuristic.

The current PR’s ordering cannot redistribute real samples between these two updates. With DP=2, the second mini-batch still contains only one real trajectory globally: one rank receives that trajectory plus padding, while the other receives only padding. Dynamic micro-batching cannot change this composition either, since it operates inside each mini-batch.

Consequently, when training reaches the second PPO mini-batch, its optimizer update receives a loss/gradient contribution from only **one real trajectory globally**; all 511 synthetic padding rows have zero response masks and contribute no loss. With DP=2, that single effective training sample is on only one DP rank, while the other rank has no effective training samples for that update.
