# [trainer] feat: balance every PPO mini-batch across DP ranks, shuffle on the trainer

[Upstream PR](https://github.com/verl-project/verl/pull/8201) · state: open · merged: False

## Original PR description

### What does this PR do?

Balance **every PPO mini-batch** across DP ranks instead of only the whole train batch, and make `actor.shuffle` / `critic.shuffle` orthogonal to DP balancing: if shuffle is enabled, the trainer first shuffles samples into mini-batches, then balances each mini-batch.

Workers split their shard into PPO mini-batches sequentially and synchronize gradients after each one. `_balance_batch` only equalized the per-rank totals of the whole train batch, so individual mini-batches can still be badly imbalanced and every gradient sync waits for the slowest rank. The legacy `keep_minibatch` branch (#3605) aimed at this, but it is never enabled by any caller, uses `ppo_mini_batch_size` without multiplying by `rollout.n`, and its result is undone by the per-partition sort that follows. The v1 trainer accepts `keep_minibatch` but ignores it.

Related: #3605, #3887, #5639, #6025, #8099

### Test

- New CPU unit tests: `tests/utils/test_minibatch_balancing_on_cpu.py`
  - without shuffle, every mini-batch keeps exactly its original samples and each rank's i-th sequential slice comes from mini-batch i;
  - each mini-batch is balanced across ranks;
  - shuffle is seeded/reproducible and keeps mini-batches aligned across ranks;
  - fallback to whole-batch balancing when the mini-batch size does not divide the batch;
  - balancing unit for actor + critic, and the legacy `RayPPOTrainer._balance_batch` end to end;
  - `make_iterator(shuffle_mini_batch_order=True)` keeps mini-batch contents, changes the order per epoch, and is identical for the same seed.
- Existing `tests/test_protocol_on_cpu.py`, `tests/test_protocol_v2_on_cpu.py`, `tests/trainer/ppo/v1/test_trainer_base_on_cpu.py`, `test_v1_async_alignment_on_cpu.py`, `tests/utils/test_seqlen_balancing.py` pass.
- Simulation with the default workload model (`24576·L + L²`), N=512 samples, 4 mini-batches, DP=16, sequence lengths resampled from a real multi-turn agentic run. Metric: `Σ_i max_r W[i][r] / (W_total / DP) - 1`, i.e. extra time spent waiting at the per-mini-batch gradient sync:

  | DP balancing | mean | p90 |
  |---|---|---|
  | whole batch (current) | 42.3% | 48.1% |
  | per mini-batch (this PR) | 0.23% | 0.34% |

- In our internal 4B hybrid-attention RL runs (colocated, CP=4), a similar per-mini-batch balancing cut the ReduceScatter wait in the actor update from ~24 s to ~0.4 s per step on 8 GPUs. GPU e2e numbers on upstream examples are still TODO (this is why the PR is a draft).

### API and Usage Example

No new config. `trainer.balance_batch=True` (default) now balances per mini-batch.

`actor.shuffle` / `critic.shuffle` now mean "randomly assign samples to PPO mini-batches". With `balance_batch`, the trainer applies the shuffle once per step (seeded by `data_loader_seed` and the step); workers no longer shuffle samples, but visit the balanced mini-batches in a new random order every PPO epoch, using the same seed on all DP ranks.

**Behavior change**: with `shuffle=True` and `ppo_epochs > 1`, the mini-batch *composition* is fixed within a step and only the mini-batch *order* changes per epoch. Previously each rank reshuffled its own shard every epoch, which changes composition but also destroys the DP balance and never moves samples across ranks. Random reshuffling and shuffle-once have comparable convergence guarantees for SGD, and randomizing the order per epoch keeps the same samples from always being updated at the most off-policy position. With `balance_batch=False`, or with PrefixGrouper, or in recipes that override `_balance_batch`, workers shuffle exactly as before.

A follow-up for the v1 trainer could re-balance a fresh permutation every epoch, since v1 workers fetch samples from TransferQueue by key and per-epoch layouts would only cost metadata.

### Design & Code Changes

- `verl/utils/seqlen_balancing.py`: add `get_minibatch_balanced_partitions(workload_list, k_partitions, mini_batch_size, shuffle, seed)`. It optionally permutes samples into mini-batches, runs Karmarkar-Karp per mini-batch, and lays out each rank's shard mini-batch by mini-batch, so the i-th sequential mini-batch on every rank comes from the same balanced global mini-batch.
- `verl/trainer/ppo/utils.py`: `get_balance_mini_batch_size` (balancing unit = gcd of the actor and critic global mini-batch sizes, so both are balanced) and `need_minibatch_shuffle`.
- `verl/utils/tensordict_utils.py`: `make_iterator(..., shuffle_mini_batch_order=True)` visits the contiguous mini-batches in a new random order every epoch without changing their contents. `TrainingWorker.train_mini_batch` enables it via `shuffle_mini_batch_order` and then uses the same seed on all DP ranks (instead of `seed + dp_rank`).
- v1 `PPOTrainer._balance_batch`: use the new partitioning; `_update_actor` / `_update_critic` disable the worker-side sample shuffle and request `shuffle_mini_batch_order` when shuffle is enabled.
- Legacy `RayPPOTrainer._balance_batch`: use the new partitioning and mark `batch.meta_info["minibatch_balanced"]`; `_update_actor` / `_update_critic` switch from the sample shuffle to `shuffle_mini_batch_order` only for marked batches. The "smaller micro-batches at both ends" ordering for pipeline parallel now runs inside each rank's share of a mini-batch so mini-batch boundaries are kept. The buggy `keep_minibatch` branch and argument are removed (no callers).
- Config comments and `docs/examples/config.rst` updated for the new `shuffle` semantics.
