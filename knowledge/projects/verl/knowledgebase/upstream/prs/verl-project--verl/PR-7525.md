# [BREAKING][trainer, cfg] fix: derive TransferQueue storage units from node count

[Upstream PR](https://github.com/verl-project/verl/pull/7525) · state: closed · merged: False

## Original PR description

### What does this PR do?

Fixes #7398 by deriving the default number of TransferQueue `SimpleStorage` units from `trainer.nnodes`. When the configured value is null, resolve it to `max(2, 2 * trainer.nnodes)` immediately before TransferQueue initialization; preserve any explicit `num_data_storage_units` override.

The original fixed default reserves eight storage-unit CPUs plus the controller even for a single-node run. This change follows the config's existing recommendation of at least two units per node and reduces the one-node default to two.

### API and Usage Example

The existing explicit override remains unchanged:

```bash
transfer_queue.backend.SimpleStorage.num_data_storage_units=5
```

Leaving the value at null selects `max(2, 2 * trainer.nnodes)`.

TransferQueue checkpoints must be restored with the same storage-unit count used when they were written. A single-node checkpoint written with the previous implicit default of 8 units must be resumed with this explicit override:

```bash
transfer_queue.backend.SimpleStorage.num_data_storage_units=8
```

Preserve the original count explicitly when changing `trainer.nnodes` for a resumed run.

### Design & Code Changes

- Change the SimpleStorage YAML default from 8 to null and regenerate all flattened PPO trainer configs.
- Resolve the node-aware default before printing the runtime config and before `tq.init`.
- Preserve explicit values and add CPU coverage for one-node, multi-node, and override behavior.

### Compatibility

This changes the implicit default: one-node runs use 2 storage units instead of 8, and four-node runs use 8. Explicit values are unchanged. Because storage-unit count is part of TransferQueue checkpoint recovery, users must pass the checkpoint's original count when resuming a checkpoint created under the previous implicit default.
