# [megatron, ckpt] fix: synchronize overlapping parameters before checkpoint save

[Upstream PR](https://github.com/verl-project/verl/pull/8264) · state: open · merged: False

## Original PR description

### What does this PR do?

Fix checkpoint saving in SFT and RL training using the Megatron engine with standard DDP, distributed optimization, and parameter-gather overlap enabled (DP > 1).

After an optimizer step, the updated weights are normally synchronized before the next forward pass. If training saves a checkpoint before that synchronization—for example, at a periodic checkpoint or the end of training—the save can succeed while some model weights are still out of date. **Both native Megatron-Core (MCore) checkpoints and Hugging Face-format exports can be affected**, because both backends read weights from the model. The saved weights may therefore not fully reflect the completed training step or match the saved optimizer state.

This PR completes parameter synchronization before either checkpoint backend reads model weights. FP8/FP4 configurations are excluded. Two-GPU BF16 validation covers both formats, including save/load correctness and training continuation.

#### GPU validation

**Setup:** 2 × H20-141G, Qwen3-1.7B, BF16, standard DistributedOptimizer, DP2 / TP1 / PP1 / CP1, synchronous saving. The final implementation was tested with overlap off/on in two separate runs: HF/Bridge model save/load, and native MCore model-shard save/load with HF export alongside it.

##### Checkpoint correctness

**Goal:** verify that saved and restored model weights include the completed optimizer update.

Train for two steps and save immediately after the optimizer update, without another forward pass. Compute the **expected updated model weights** from the optimizer's FP32 master weights, cast to BF16 in independent tensors. This computation does not synchronize or overwrite the live model.

- **HF export:** compare the saved files elementwise against the expected updated weights converted to HF layout.
- **Post-save model:** compare the in-memory model parameters against the expected updated weights.
- **Fresh-process restore:** call the unchanged `engine.load_checkpoint()` API, then compare restored model parameters against BF16 weights reconstructed from the restored optimizer's FP32 master weights.

**Unpatched baseline (HF/Bridge):** overlap disabled produced correct weights; overlap enabled produced mismatches in both the HF export and the restored model.

**Final fix:** all elementwise comparisons pass:

| --- | --- | ---: | ---: |
| HF/Bridge | Off | 0 | 0 |
| HF/Bridge | On | 0 | 0 |
| Native MCore | Off | 0 | 0 |
| Native MCore | On | 0 | 0 |

Restored-model and post-save model mismatches are zero on both ranks in all four configurations. HF weights were also exported in the native MCore run; native model restore loaded `model/dist_ckpt`, not the HF export, with no HF fallback. The unpatched baseline used HF/Bridge; an unpatched native MCore GPU negative control was not run.

##### Training continuation

**Goal:** verify that saving or resuming a checkpoint does not change subsequent training.

For the fixed implementation, compare three training paths for each backend and overlap setting:

- **A:** train four steps continuously.
- **B:** save at step 2, then continue in the same process.
- **C:** restore B's step-2 checkpoint in a fresh process, then continue.

- **Training metrics:** B matches A's loss, grad_norm, and learning rate exactly for all four steps; C matches A's steps 3–4 exactly.
- **Final states:** at step 4, model, optimizer, scheduler, and RNG hashes match for corresponding ranks across A/B/C.

Both model backends pass with overlap enabled and disabled. The unpatched baseline did not include this continuation comparison.

These experiments validate engine checkpoint save/load and continuation in the BF16 synchronous-save setup above, not a full SFT/RL trainer end-to-end run. Other precision, parallelism, and offload configurations were not tested.

### Design & Code Changes

The distributed optimizer updates the parameter shards owned by each rank. With parameter-gather overlap, publication of the full model weights can be deferred until the next forward pre-hook. Checkpoint writers read model weights directly and do not execute that forward boundary.

#### Save boundary

In `verl/workers/engine/megatron/transformer_impl.py`, call `start_param_sync(force_sync=True)` under `torch.no_grad()` after GPU restoration and before the checkpoint manager reads the model. A synchronization exception prevents that rank from entering checkpoint writing; cross-rank failure recovery is not claimed. Existing barrier, offload, and load logic is unchanged.
#### Eligibility

Synchronize a chunk only when all five conditions hold:

- The chunk is a Megatron `DistributedDataParallel` wrapper.
- `chunk.ddp_config.use_distributed_optimizer` is enabled.
- `chunk.ddp_config.overlap_param_gather` is enabled.
- The effective `self.tf_config.fp8` is disabled.
- The effective `self.tf_config.fp4` is disabled.

FP8/FP4 paths can require optimizer staging before an explicit gather, particularly MXFP8 with shared parameter/gradient buffers. This PR does not implement that lifecycle. Excluded configurations retain their previous save behavior; their checkpoint correctness is not guaranteed by this change. The guard checks effective precision settings; inconsistent quantized gather/reuse overrides and alternative optimizer wrappers are outside the validated setup.

#### Regression tests

`tests/workers/test_megatron_checkpoint_sync_on_cpu.py` covers configuration eligibility, restoration/save ordering, no-grad execution, and failure safety. Distinct mock chunk IDs ensure that synchronizing one chunk twice cannot hide a missed second chunk. The file matches the existing `*_on_cpu.py` discovery; no dependencies or workflow changes are added.

Only the engine save boundary and CPU regression test are changed. GPU validation harnesses and deployment-specific materials are not included.

#### 2. Independent references and comparison targets

1. **Pre-save reference:** read the FP32 master-weight shards owned by each rank, cast them to BF16, and place them at the corresponding offsets in new tensors. 2. **HF export:** convert the independent reference to HF layout with Megatron-Bridge's same naming, QKV, and GLU conversion; read the saved safetensors and check tensor names, shapes, dtypes, and every element. 3. **HF/Bridge restore:** call `engine.load_checkpoint()` in a new process with the HF model backend, then compare complete model parameters and owner shards against restored optimizer master weights. This is the backend used by the historical baseline and the first final-revision run.
4. **Native MCore model restore:** in the second final-revision run, retain HF model initialization and construct the existing public `MegatronCheckpointManager` with `use_dist_checkpointing=True`, save contents `['model', 'hf_model', 'optimizer', 'extra']`, and load contents `['model', 'optimizer', 'extra']`. - ewan0x79 · comment · 2026-10-16T14:05:52Z · [source](https://github.com/verl-project/verl/pull/8264#issuecomment-6217249444)

To clarify the core issue: in the **Megatron engine with standard DDP, DistributedOptimizer, and DP > 1** (reproduced with DP=2 in BF16), `overlap_param_gather=true` can leave non-owner model parameter shards stale after an optimizer update until the next forward pre-hook. **Saving a synchronous checkpoint immediately after the update, before another forward, can therefore persist stale model weights.** The historical unpatched run showed elementwise HF-export mismatches and model/master-weight inconsistency after a fresh-process restore through `engine.load_checkpoint()`. **Correction:** that run used HF/Bridge for model weights, not native MCore model shards; optimizer/scheduler/RNG used MCore storage. This is a **checkpoint model-weight consistency issue**, not file-format corruption.

The updated fix only adds synchronization for DDP chunks with distributed optimization and parameter-gather overlap enabled **and FP8/FP4 disabled in the effective model config**; the load path is unchanged. The final BF16 implementation was validated in separate HF/Bridge and native MCore model-shard runs, each with overlap off/on: HF files, post-save models, and restored models had zero differences from the corresponding master-weight references, and continuous/save-and-continue/fresh-resume trajectories matched. The native-model run loaded MCore model shards without HF fallback. An unpatched native-model-backend GPU negative control has not been run. FP8/FP4 skip the new synchronization and retain their previous save behavior; their checkpoint correctness is not claimed.
