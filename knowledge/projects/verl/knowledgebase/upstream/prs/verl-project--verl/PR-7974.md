# [trainer, ckpt] fix: skip dataloader state restore when resuming at epoch boundary

[Upstream PR](https://github.com/verl-project/verl/pull/7974) · state: open · merged: False

## Original PR description

### What does this PR do?

Fixes #7401. When a checkpoint is saved exactly at an epoch boundary (e.g. `save_freq` is a multiple of `steps_per_epoch`), resuming silently skips the next epoch: the job can exit with status 0 having performed none of the remaining updates, leaving an under-trained model that looks "complete".

**Root cause:** the saved `StatefulDataLoader` state marks the sampler as fully exhausted. On resume, the trainer already advances to the next epoch (`start_epoch = global_step // steps_per_epoch`) and calls `set_epoch()` before iterating; the restored iterator then fast-forwards the *new* epoch's sampler by the whole epoch length (torchdata restores the sampler position via `itertools.islice`), so the new epoch yields 0 batches.

**Fix:** #5725 solved the same bug for `ppo/ray_trainer.py` with a modulo check (`global_steps % steps_per_epoch == 0`). This PR applies the same, already-accepted approach to the remaining affected paths:

- `verl/utils/checkpoint/checkpoint_handler.py` (shared by SFT spmd/ray trainers): new optional `steps_per_epoch` argument; skip restoring the dataloader state when `resume_global_step % steps_per_epoch == 0`. Detection is disabled when the argument is not provided, so existing behavior is unchanged for other callers.
- `verl/trainer/sft_trainer.py` / `verl/trainer/sft_trainer_ray.py`: pass `steps_per_epoch` through.
- `verl/trainer/ppo/v1/trainer_base.py`: same boundary check as `ppo/ray_trainer.py`, using the trainer's own `steps_per_epoch` (consistent with its `current_epoch` computation).

**Relation to #7402 (why this is not a duplicate):** #7402 addresses the same issue but introduces a new on-disk sidecar metadata file (~50 lines plus format versioning and a legacy path), which only protects *newly written* checkpoints and adds a new hard failure (`ValueError`) when resuming with a different `steps_per_epoch` (e.g. different GPU count after preemption). This PR is the minimal fix: no new artifact, works for every existing checkpoint, adds no new failure mode, and also covers `ppo/v1/trainer_base.py`, which #7402 does not touch. Related: #5725, #7402, #7516.

### API and Usage Example

No API changes. `CheckpointHandler` gains an optional keyword argument `steps_per_epoch` (default `None` = detection off, fully backward compatible). No user action is required.

```python
# SFT trainers already wire this up internally; no user-side change.
# For direct CheckpointHandler users who want the protection:
handler = CheckpointHandler(
    engine=engine,
    train_dataloader=train_dataloader,
    default_local_dir=ckpt_dir,
    steps_per_epoch=len(train_dataloader),  # optional; enables epoch-boundary detection
)
```

- flyingdoubleG · comment · 2026-10-25T05:28:22Z · [source](https://github.com/verl-project/verl/pull/7974#issuecomment-6393919528)

I think the V1 part of this change introduces a data-order regression, and V1 already handles the epoch boundary correctly without it.

**Why V1 doesn't need the skip:** `_fetch_one_gen_batch` catches `StopIteration` and calls `iter()` again. On a boundary resume, the first `iter()` applies the saved (exhausted) state and stops immediately. The second `iter()` starts a fresh epoch from the restored sampler. So no epoch is lost.

**Why skipping is harmful for the RL sampler:** `create_rl_sampler` uses torchdata's `RandomSampler` with a `torch.Generator`, and that generator's state is part of `data.pt`. If restore is skipped, the new dataloader starts from the generator's initial state, so the epoch after resume replays epoch 1's permutation exactly. An uninterrupted run would draw a new one. This happens with `data.seed: null` too, because an unseeded `torch.Generator()` starts from a fixed default seed. The SFT path uses `DistributedSampler` with `set_epoch`, which reseeds per epoch, so I believe skipping is fine there; this only concerns the RL samplers.

**GPU check:** main @ 3c6d9b4, V1 trainer, Qwen3-0.6B, 64 GSM8K prompts, batch 32 → 2 steps/epoch, `total_epochs=2`. The checkpoint is saved at step 2 (epoch boundary) and resumed with `resume_mode=auto`. The values below are the first 8 sorted dataset indices of each training batch:

| run | step 3 | step 4 |
|---|---|---|
| uninterrupted | `[4, 6, 9, 10, 11, 12, 13, 14]` | `[0, 1, 2, 3, 5, 7, 8, 15]` |
| resume, main | `[4, 6, 9, 10, 11, 12, 13, 14]` | `[0, 1, 2, 3, 5, 7, 8, 15]` |
| resume, this PR's V1 change | `[0, 1, 3, 4, 5, 6, 13, 14]` (= step 1) | `[2, 7, 8, 9, 10, 11, 12, 15]` (= step 2) |

On main, steps 3–4 run and match the uninterrupted run. With the skip, epoch 2 repeats epoch 1.

The legacy `ray_trainer.py` has the same replay since #5725. A fix that keeps the state is to restore it and then drain the exhausted epoch when `global_steps % steps_per_epoch == 0` (`for _ in dataloader: pass`), so the next `for batch in dataloader` starts a fresh permutation. I have that with a CPU test locally and can open it separately if useful. Given the legacy trainer is deprecated, it may not be worth it, though.

Suggestion: drop the `trainer_base.py` hunk from this PR (or limit the skip to samplers without generator state).
