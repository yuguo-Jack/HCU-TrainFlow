# [fsdp] fix: prevent parameter corruption during FSDP2 CPU offload

[Upstream PR](https://github.com/verl-project/verl/pull/8187) · state: closed · merged: True

## Original PR description

### What does this PR do?

Prevent silent parameter corruption when moving FSDP2 models to CPU with uneven parameter shards.

I identified this issue while debugging Qwen3-Omni training and evaluation failures reported in:

- https://github.com/verl-project/verl-omni/issues/660
- https://github.com/vllm-project/vllm-omni/issues/8039

The observed symptoms included degraded evaluation accuracy in multi-node training. The investigation traced the problem to parameter values changing during CPU offloading, without any forward pass, backward pass, or optimizer update.

This PR uses blocking device-to-CPU transfers in both affected verl paths:

- Runtime offloading through `offload_fsdp2_model_to_cpu`.
- Initialization-time offloading inside `fsdp2_load_full_state_dict`, which reuses the same helper.

This follows the discussion in:
https://github.com/verl-project/verl-omni/pull/741#issuecomment-6139999835

### Root Cause

`model.to("cpu", non_blocking=True)` can leave a device-to-CPU transfer in progress while FSDP2 processes the converted parameter.

For uneven shards, `FSDPModule._apply` calls `FSDPParam.reset_sharded_param`, which may allocate new padded CPU storage and copy the transferred local tensor into it. This CPU copy can read the transfer destination before the asynchronous D2H transfer has completed.

Incorrect values can then persist in the new padded storage. Synchronizing after the entire `model.to()` call returns does not repair values that have already been copied into that storage.

This is not specific to NPU: I reproduced the same failure on CUDA by queuing additional computation before the transfer.

### Design & Code Changes

- Use `model.to("cpu", non_blocking=False)` in `offload_fsdp2_model_to_cpu`, so each transfer completes before FSDP2 can consume its CPU result.
- Route the CPU move in `fsdp2_load_full_state_dict` through that helper with `empty_cache=False`, preserving the initialization path's cache behavior.
- Keep the CPU-to-device helper's `non_blocking=True` argument.
- Update transfer-policy tests to require blocking D2H on both CUDA and NPU.
- Generalize the NPU regression into `test_fsdp2_model_cpu_offload.py`, shared by CUDA and NPU CI. It covers nested FSDP2 modules, large even/uneven weights, and the original small bias vectors.
- Queue warmed-up matrix multiplications on the actual conversion stream and check both default and non-default streams. Change parameter values between trials and check CPU values after synchronization to distinguish persistent corruption from an unfinished transfer.
- Update the CUDA regression so it validates parameter correctness rather than requiring the pinned allocation associated with the previous non-blocking D2H path.

The fix uses existing PyTorch module conversion behavior and does not patch private FSDP2 internals or introduce backend-specific synchronization code.

### Related Work

- https://github.com/verl-project/verl/pull/7347 enabled non-blocking runtime FSDP2 model transfers for performance. This PR changes the D2H policy to restore correctness. The initialization-time asynchronous CPU move predates #7347 and is covered here as well.
- https://github.com/verl-project/verl/pull/8057 addresses pinned-memory allocation configuration. It does not establish transfer completion before FSDP2 reads CPU data.
- https://github.com/verl-project/verl-omni/pull/741 provides a downstream workaround. This PR addresses the shared verl helpers used by downstream callers.

### Performance Considerations

This change prioritizes parameter correctness over asynchronous D2H overlap.

Blocking D2H can increase host-side waiting and may change whether the resulting CPU storage is pinned. Consequently, keeping `non_blocking=True` in the CPU-to-device helper does not guarantee the same H2D overlap or throughput as before.

The performance impact of this broader verl change has not been quantified. The successful downstream training runs are correctness evidence, not a controlled performance comparison.

### API and Usage

No public API or configuration changes are required.

Existing callers of the two affected helpers automatically receive the corrected D2H behavior.
