# [trainer, algo] fix: give GDPO its reward components on the V1 trainer

[Upstream PR](https://github.com/verl-project/verl/pull/8424) · state: open · merged: False

## Original PR description

### What does this PR do?

On the V1 trainer (the `main_ppo` default), `algorithm.adv_estimator=gdpo` fails on the first advantage step. `_compute_advantage` fetches only `uid`, `response_mask`, `rm_scores` and the log-prob/value fields, so the `DataProto` handed to `compute_advantage` has:

- no reward components: v0 puts each `reward_extra_info` key into `non_tensor_batch`, and V1 never does;
- no `prompts` / `attention_mask`, which `compute_gdpo_outcome_advantage` uses to find each response's last token.

The estimator raises `KeyError: 'prompts'`, and past that its `GDPO reward key ... not found in non_tensor_batch` assertion.

This PR fetches the `gdpo_reward_keys` components and gives the estimator what it needs to place them, so V1 GDPO matches v0.

Why this is not a duplicate:

- #5613, #6497 and #7965 change `compute_gdpo_outcome_advantage` in `core_algos.py`. None of them touch the V1 trainer, and on V1 the estimator fails before it reaches their code paths.
- #7473 passes `non_tensor_batch` to estimators in the v0 `ray_trainer.py` only.
- #7497 (CoDaPO) also forwards `reward_extra_info` into the V1 advantage batch, for its own estimator. That covers half of this: GDPO would still raise `KeyError: 'prompts'`, and a colocated reward model writes the components as their own fields rather than in `extra_fields`. Whichever lands first, I will rebase the other onto it.

### Test

New `tests/trainer/ppo/v1/test_gdpo_on_cpu.py` runs `_compute_advantage` against an in-memory TransferQueue and compares the V1 advantages token by token with v0's `compute_advantage` on the same rewards, for both the streaming reward path (`extra_fields`) and a colocated reward model (per-key fields).

```bash
pytest -q tests/trainer/ppo/v1/test_gdpo_on_cpu.py tests/trainer/ppo/v1/test_trainer_base_on_cpu.py tests/trainer/ppo/v1/test_compute_reward_colocate_on_cpu.py
```

- main: both new cases fail with `KeyError: 'key "prompts" not found in TensorDict ...'`.
- this PR: 23 passed.

I have not run GDPO end to end on GPU for this change; the CPU test checks V1 against v0 directly.

### Design & Code Changes

`verl/trainer/ppo/v1/trainer_base.py`:

- `_compute_advantage`: for GDPO, select `extra_fields` (streaming reward path) or the `gdpo_reward_keys` fields (colocated reward model, which writes each reward extra key as its own field), and put the components into `non_tensor_batch`.
- Give the estimator an empty `prompts` and an `attention_mask` covering each full response. GDPO only uses them to find the last response token, so this places each component exactly where v0 does, tool tokens included (they are in v0's attention mask too).
- `_pop_gdpo_rewards`: a small helper that reads the components from either layout. Keys missing from any sample are left out, so the estimator's existing assertion still reports them.

**Apply final-session selection to GDPO normalization.**

`_agent_loop_postprocess` stores every output under `{uid}_{session_id}_{index}` and copies the final output’s reward components to intermediate outputs. V1 then sends GDPO through `compute_advantage_for_multi_trajectories`, whose final-session selection currently applies only to GRPO.

GDPO therefore includes duplicate intermediate rows in `uid`-based normalization. When sessions have different numbers of outputs, this can weight their rewards differently from v0’s one-final-output-per-session behavior. The rows in one session usually share the same reward components, so the issue is altered group statistics, not necessarily different advantages within that session.

Extend the final-output selection and broadcast branch to GDPO, and add a multi-output parity case.
