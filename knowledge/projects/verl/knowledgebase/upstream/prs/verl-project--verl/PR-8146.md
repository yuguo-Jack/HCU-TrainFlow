# [hardware, recipe] feat: DeepSeek-V4-Flash GRPO on ROCm (MI355X) with QAT, FP8 or BF16 training

[Upstream PR](https://github.com/verl-project/verl/pull/8146) · state: closed · merged: True

## Original PR description

### What does this PR do?

Makes DeepSeek-V4-Flash GRPO run end to end on AMD MI355X with an FP8 rollout, and gives it one recipe with three training modes. Follow-up to #7050 (ROCm enablement) and #7455 / #7470 (Megatron-Bridge path). Two commits:

1. **`[docker]` image.** `docker/rocm/Dockerfile.rocm.deepseek-v4` builds the versions the runs were validated with: Transformer Engine 2.18 (ROCm build: Triton grouped GEMM path that avoids a bf16 grouped-GEMM backward hang on gfx950, float-scale blockwise FP8 GEMM), a libhsa-runtime that returns memory under `expandable_segments` on ROCm 7.2.x, Megatron-LM `fd1121b8f` plus the `deepseek-v4-rocm-support` commits (config-driven FP8 fake quantization, FP8-training alignment options, and the `index_select` gather of the unfused CSA sparse attention that upstream introduced with the reworked SBHD path in NVIDIA/Megatron-LM#6400, which this older base predates), Megatron-Bridge 0.5.0 plus a fix that keeps the FP8 weight export on the checkpoint's power-of-two scale grid, and four vLLM 0.26.0 patches applied at build time (NaN guard on the FP8 indexer logits; CuMem wake cache release, vllm#49857; indexer K-cache block-flat layout on gfx950/gfx942, vllm#50455; SwiGLU clamp on the FP8 Triton fused MoE path).
2. **`[recipe]` one script, three modes.** `examples/grpo_trainer/run_deepseek_v4_flash_megatron_rocm.sh`, `TRAIN_MODE=qat|fp8|bf16`. `qat` is BF16 training with Megatron's FP8 fake quantization (weights on 128x128 power-of-two scales, inputs on 1x128 float scales, straight-through estimator) and an FP8 W8A8 vLLM rollout; `fp8` is Transformer Engine blockwise FP8 training with float activation scales; `bf16` is BF16 training with a BF16 rollout. All modes round the KV latent and the indexer q/k the way the rollout's FP8 KV cache and FP8 indexer do. Everything is a transformer-config override; the only environment variables are the two Transformer Engine kernel selectors.

Why the alignment matters: on ROCm, vLLM quantizes FP8 activations with float scales (amax / 448) while Transformer Engine's blockwise recipe uses powers of two, so the same training code that aligns on NVIDIA (DeepGEMM) does not align here. With the rollout's rounding reproduced in training, `training/rollout_probs_diff_mean` at step 1 drops to the BF16-forward level and the train/rollout KL stays flat over 300 steps.

The Megatron-LM and Megatron-Bridge changes live in the author's forks while they are proposed upstream; the Transformer Engine wheel and the libhsa-runtime are published as release assets because no official ROCm package carries those fixes yet.

### Test

DeepSeek-V4-Flash (FP8 checkpoint), 4 nodes x 8 MI355X, ROCm 7.2.3, GRPO/GSPO on DAPO-Math, validated on AIME-2024 every 10 steps:

| Mode | step-1 `rollout_probs_diff_mean` | step-1 `rollout_corr/kl` | 300 steps | AIME-2024 acc |
| --- | --- | --- | --- | --- |
| qat | 0.0096 | 0.0021 | KL 0.0022 -> 0.0029, no NaN/hang | 0.60 -> 0.76 |
| fp8 | 0.0097 | 0.0021 | KL 0.0022 -> 0.0039 | 0.60 -> 0.76 |
| bf16 | 0.0060 | 0.0008 | KL 0.0008 -> 0.0011 | 0.59 -> 0.79 peak |

On the image built from this branch, a 7-layer cut of the model (single node) gives diff / KL of 0.0129 / 0.0068 in `qat` and 0.0130 / 0.0069 in `fp8` over 3 steps, matching the earlier runs. Per step on 32 GPUs: ~490 s (`qat`), ~420 s (`fp8`), ~330 s (`bf16`), of which ~85 s is the weight sync.

### API and Usage Example

```bash
DOCKER_BUILDKIT=1 docker build -f docker/rocm/Dockerfile.rocm.deepseek-v4 -t rocm-verl-dsv4 .
# Ray on every node (commands in the script header), then on the head node:
WK=<wandb key> TRAIN_MODE=qat bash examples/grpo_trainer/run_deepseek_v4_flash_megatron_rocm.sh
TRAIN_MODE=fp8 TOTAL_TRAINING_STEPS=5 bash examples/grpo_trainer/run_deepseek_v4_flash_megatron_rocm.sh trainer.val_before_train=False
```

### Design & Code Changes

- `docker/rocm/Dockerfile.rocm.deepseek-v4`: version pins and build-time patches as described; `docker/rocm/patches/vllm-*.patch` carry the upstream reference in their headers.
- `examples/grpo_trainer/run_deepseek_v4_flash_megatron_rocm.sh`: the recipe; the header documents the modes, the Ray commands and the reference values. The mode only changes a set of `override_transformer_config` keys (`fp8_fake_quant`, `fp8_fake_quant_kv_cache`, `fp8_fake_quant_indexer_qk`, and for `fp8`: `fp8=e4m3 fp8_recipe=blockwise fp8_blockwise_act_pow2_scale=False`), applied to both the actor and the reference policy.

Answering my own question after checking: **yes, this patch also applies on CUDA**, and I'd prefer not to land it in its current form.

- `apply_patch()` runs for every `MLATransformerConfig` model (`hf_to_mcore_config_dpskv3` and `make_megatron_module`), regardless of platform. The new function only checks whether `csa` can be imported, and any recent mcore has that module.
- CUDA reaches the unfused path too. In `fd1121b8f`, `apply_dsa_kernel_fusion` defaults to `False`. In upstream `main`, `use_fused_dsa_kernels(config)` falls back to unfused when the backend is unfused or when FlashMLA / cuDNN CuTe-DSL is missing. All call sites in `csa.py` resolve the name from the module globals, so the replacement is used everywhere.

More importantly, **upstream has already fixed this**. NVIDIA/Megatron-LM#6400 (`a2003d48f`, merged 2026-08-27) changed `unfused_compressed_sparse_attn` to `kv_flat.index_select(0, ...)` with the same rationale. Your fork's base `fd1121b8f` (2026-07-10) predates it. With an mcore that already has the fix, this patch:
- overwrites the upstream implementation with a frozen copy and drops upstream's `attn_sink` shape validation;
- will break (`TypeError`) or silently diverge if upstream later changes the signature or the index semantics (e.g. THD);
- is applied silently, with no log line, so it would be hard to spot during debugging.

Suggestions:
1. Preferred: cherry-pick #6400 into the `deepseek-v4-rocm-support` fork (or rebase onto a newer mcore), point the Dockerfile at it, and drop this verl patch.
2. If it has to stay for now, gate it on the old implementation rather than on the platform, e.g. only patch when `"torch.gather" in inspect.getsource(csa.unfused_compressed_sparse_attn)`, and log when the patch is applied. CUDA users on an old mcore with fusion off would hit the same OOM, so an `is_rocm` check alone isn't the right gate.

The Dockerfile, vLLM patches and recipe are ROCm-only and don't affect CUDA.
