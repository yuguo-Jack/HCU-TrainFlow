# [training_utils] fix: keep confident-label logprobs and gradients in the Triton fused linear cross-entropy

[Upstream PR](https://github.com/verl-project/verl/pull/8378) · state: open · merged: False

## Original PR description

### What does this PR do?

Fixes the Triton fused linear cross-entropy (`verl/utils/kernel/kernels.py`, used with `use_fused_kernels=True`) so a confident label keeps its logprob and gradient. Before this change the forward formed `z_t - (max + log(accu))`, where `accu` sums `exp(z - max)` over every logit, including the label's own 1.0. Once the label's margin over the other logits passed ~16.6 in fp32, `accu` rounded to 1. The logprob and the label's gradient entry `exp_logits * accu_rcp - 1` both became exactly 0, while the other entries stayed nonzero. Part of #8376, which has a repro; the torch log-prob half is #8377.

Following Barron et al., "A Fix for Softmax and Cross-Entropy" (arXiv:2610.31642), the logprob is now `-softplus((max - z_t) + log(accu_other))`. `accu_other` is accumulated with the label's term left out, rather than subtracted from `accu` afterwards.

### API and Usage Example

No change to `linear_cross_entropy` or `LinearCrossEntropy`. The internal `kernels.efficient_entropy_forward` now returns one more tensor, `one_minus_p`, and `kernels.efficient_entropy_backward` takes it. `LinearCrossEntropy` is their only caller in the repo.

### Design & Code Changes

- **Forward mainloop:** also accumulates `accu_other`, the online sum of `exp(z - max)` with the label's term masked out before summing, stored per vocab split like `accu`.
- **Epilogues:** reduce `accu_other` across splits like `accu`. Under TP it rides in the existing all-reduce buffer for `accumulate` and `entropy_b` (now 3 × num_tokens), so there is no extra collective.
- **Host:** computes `logprob = -softplus((max - z_t) + log(accu_other))` and `1 - p_t = -expm1(logprob)` in torch, then applies the none/sum/mean reduction. Subtracting `z_t` from `max` first keeps the rounding at the scale of the margin rather than of the logits. The reduction moved out of the epilogue kernels, along with their `atomic_add` and the mainloop's scalar init store.
- **All five backward kernels:** take `1 - p_t` and use `-(1 - p_t)` for the label entry of `softmax - onehot`. The other entries and the entropy gradient are unchanged. The `d_hidden`/`d_weight`-only kernels are updated the same way but aren't launched by any current backward method, so no test covers them.
- **Entropy:** still uses the full `accu`.
- **TP label-logit buffer:** always zero-initialised now. It used to be `torch.empty` for `reduction="sum"/"mean"`, so non-owner ranks all-reduced uninitialised memory into the label logit.

**Subtract the label logit before adding `log(accumulate_other)`.**

The expression evaluates as `(maximum + torch.log(accumulate_other)) - label_logits`. The first addition yields about the log-sum-exp of the non-label logits, which has the magnitude of those logits. Its rounding error is half an ulp at that magnitude: about 4e-6 for values in [64, 128) and about 3e-5 for values in [512, 1024). This error depends on the logit offset, and it enters `softplus` unchanged.

When the label is the maximum, `maximum - label_logits` is exactly 0. When the two logits are within a factor of 2, Sterbenz's lemma makes their difference exact. Subtracting first removes the offset-dependent rounding at no extra cost. The remaining rounding occurs at the scale of the margin.

The practical effect is small. It matters only for large logit offsets. At typical magnitudes, the existing rounding in `log(accumulate_other)` is comparable or larger. For confident labels, `one_minus_p = -expm1(token_logprobs)` changes very little, because its sensitivity to the log-probability is about `exp(token_logprobs)`.
