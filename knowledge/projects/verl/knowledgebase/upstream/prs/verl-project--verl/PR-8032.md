# [rollout] feat: release LoRA base weights on sleep via lora.resync_base

[Upstream PR](https://github.com/verl-project/verl/pull/8032) · state: open · merged: False

## Original PR description

### What does this PR do?

To avoid main memory OOM when offload, add an opt-in `model.lora.resync_base` flag for LoRA adapter mode (`model.lora.merge=False`). When it is set, the rollout releases the base weights on sleep, and the trainer re-syncs the full base weights before the adapter on every weight update. The refit cost is then similar to `merge=True` (full weights every step), plus the usual adapter load. The flag defaults to `False`, which keeps the current behavior.

- **vLLM**: adapter mode today pins the rollout to level-1 sleep, which offloads the base weights to CPU memory on every sleep and copies them back on wake-up. With `resync_base=True` the rollout sleeps at level 2 and discards them instead, so no rollout replica keeps a CPU copy of the base weights.
- **SGLang**: adapter mode today releases only the kv_cache on sleep, so the base weights stay on GPU through training. With `resync_base=True` sleep releases the weights too. HYBRID mode always launches SGLang with `enable_weights_cpu_backup=True`, so on SGLang this frees the GPU memory the base holds during training but still keeps a CPU copy.

### API and Usage Example

New config key `model.lora.resync_base` (default `False`). It only has an effect when `model.lora.merge=False`, with `rollout.name=vllm` or `rollout.name=sglang`.

```bash
python3 -m verl.trainer.main_ppo \
    actor_rollout_ref.rollout.name=vllm \
    actor_rollout_ref.model.lora_rank=32 \
    actor_rollout_ref.model.lora.merge=False \
    actor_rollout_ref.model.lora.resync_base=True \
    ...  # Megatron sets the rank via actor_rollout_ref.model.lora.rank instead
```

### Design & Code Changes

1. `verl/trainer/config/model/hf_model.yaml`: add `lora.resync_base: False` and regenerate the `_generated_ppo_*_trainer.yaml` files. The key is added to the shared model config, so it also appears under `critic.model.lora`, where it is unused.
2. `verl/workers/engine_workers.py`: `ActorRolloutRefWorker` reads `lora.resync_base` at init. In the colocated (`naive`) `update_weights` path, adapter mode sets `rollout.sleep_level = 2` and runs the base sync on every update instead of only while `base_sync_done` is False. The base sync reuses the existing first-sync path (`get_per_tensor_param(base_sync_done=False)`, then `rollout.update_weights(..., base_sync_done=False)`), which previously ran only once, when the rollout started from a `dummy` load format.
3. `verl/workers/rollout/vllm_rollout/vllm_async_server.py`: `_resolve_sleep_level()` returns 2 instead of 1 for adapter mode when `lora.resync_base` is set. MTP rollout and NPU are still checked first and keep level 1; with `resync_base` they re-sync the base redundantly but stay correct.
4. `verl/workers/rollout/sglang_rollout/`: add `lora_base_kept_on_sleep()` to `utils.py`, which is true in adapter mode unless `lora.resync_base` is set. `SGLangHttpServer.sleep()`, the COLOCATED branch of `wake_up()`, and the initial `ServerAdapter.sleep_level` use it instead of `lora_served_as_adapter()`, so with `resync_base` the server releases `weights` on sleep and `update_weights` resumes them before the base re-sync. Without this, `update_weights` would resume a `weights` tag that sleep never released, which is the `KeyError: 'weights'` from #7289. `enable_lora` and the per-request `lora_path` still follow `lora_served_as_adapter()`.

Nothing changes unless `resync_base=True`; `merge=True` and full-parameter runs are unaffected.
