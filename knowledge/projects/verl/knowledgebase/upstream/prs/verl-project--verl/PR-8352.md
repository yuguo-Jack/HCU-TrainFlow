# [vllm, rollout, perf] refactor: stage LoRA buckets in one host block

[Upstream PR](https://github.com/verl-project/verl/pull/8352) · state: closed · merged: True

## Original PR description

### What does this PR do?

Performance only, no behaviour change.

When a LoRA adapter is synced to vLLM through the bucketed IPC transport (`update_weights_from_ipc` with `peft_config` and `base_sync_done`), every received tensor is cloned one by one on the device, cloned again in `_update_weights`, and then vLLM's `LoRAModel.from_lora_tensors` moves each tensor to host memory in `lora_dtype` and pins it, one tensor at a time. With per-expert MoE LoRA that is tens of thousands of small device allocations, device-to-host copies and pinned allocations per sync.

This PR copies each received bucket into **one** CPU block in vLLM's resolved `lora_dtype` (pinned when vLLM's `is_pin_memory_available()` allows, the same policy vLLM's LoRA loader uses) and hands out views of it. vLLM's per-tensor `.to("cpu", dtype)` and `.pin_memory()` then return the same tensors, so per bucket there is one pinned allocation and each tensor is copied (and cast) straight into its slice, with no extra device buffer. The second clone in `_update_weights` is dropped: its only caller already passes owned copies. If no torch dtype is available from vLLM's LoRA config, the previous per-tensor clone is used.

### Test

Existing tests pass with this change on one GB300 GPU (vLLM main build, torch 2.15 nightly): `tests/utils/test_vllm_weight_name_normalization_on_cpu.py` 28 passed, `tests/workers/rollout/test_vllm_weight_update_utils_on_cpu.py` 5 passed.

Micro-benchmark of the receive-side copy chain on one GB300 GPU: bf16 tensors that are views into one device buffer; "main" = two per-tensor clones + vLLM's per-tensor `.to("cpu", dtype).pin_memory()`, "PR" = the staging code from this PR + the same vLLM calls. Median after warm-up; results `torch.equal`; with the PR all tensors still share one host storage after the vLLM calls.

| bucket | main | this PR | speedup |
|---|---|---|---|
| 4000 tensors (16, 2048), 250 MiB | 165 ms | 35 ms | 4.7x |
| 16000 tensors (16, 1024), 500 MiB | 705 ms | 131 ms | 5.4x |

Limits:
- Receiver side only; the trainer-side gather and the transport itself are unchanged.
- No end-to-end LoRA sync time was measured against a live vLLM engine.
- The gain relies on vLLM not re-copying tensors that are already on CPU, pinned and in `lora_dtype` (true for `from_lora_tensors` today: `.to()` and `.pin_memory()` return the input in that case).

### Design & Code Changes

- `verl/workers/rollout/vllm_rollout/utils.py`: stage each LoRA bucket into one CPU block in `lora_dtype`; drop the redundant clone in `_update_weights`.

**Avoid the full-bucket accelerator allocation.**

The receiver can pass accelerator-resident tensors to `stage_lora_bucket`. `torch.cat` then allocates an additional accelerator tensor for the full bucket before the host copy. A 500 MiB bucket can require roughly 500 MiB of additional accelerator memory and may cause an out-of-memory failure under tight memory.

Copy each tensor directly into its assigned host slice. `copy_` performs the dtype conversion during that copy, so the staging path does not need `flat`.
