# [rollout] remove leftover todo ENV, remove SGLANG_USE_CPU_ENGINE environment 

[Upstream PR](https://github.com/verl-project/verl/pull/8069) · state: closed · merged: True

## Original PR description

## What does this PR do?

Removes the unconditional `SGLANG_USE_CPU_ENGINE=1` set/`del` from `verl/workers/rollout/replica.py::_load_sglang()`, plus the now-unused `import os`.

```diff
 import asyncio
 import logging
-import os
 from abc import ABC, abstractmethod

 def _load_sglang():
-    os.environ["SGLANG_USE_CPU_ENGINE"] = "1"
-
     try:
         import vllm  # noqa: F401
     ...
     from verl.workers.rollout.sglang_rollout.async_sglang_server import SGLangReplica
-
-    del os.environ["SGLANG_USE_CPU_ENGINE"]
     return SGLangReplica
```

The unrelated vLLM-module-mocking block in the same function is left untouched.

## Why?

This flag was added in #3456 (2025-09-16) as a temporary workaround and removed from the code in #3701:

```python
# NOTE: verl driver is cpu only, avoid sglang fp8 quantization import error.
# TODO: remove this once we bump to sglang>=0.5.1
```

Its own removal condition is long met — verl pins `sglang==0.5.20`. Two problems with keeping it:

1. **On CUDA it is a no-op today, but a latent hazard.** Real-CUDA detection dominates, so nothing breaks now — but setting a "CPU" flag on a GPU process relies on sglang never trusting `is_cpu()` at a site CUDA can't override. `cache_move.py` already shows one such site (XPU falls into it); a future one could catch CUDA too.

2. **It breaks the SGLang backend on XPU.** `SGLANG_USE_CPU_ENGINE=1` is an opt-in "run on CPU" declaration. On an Intel XPU host (x86 CPU) it makes sglang's `is_cpu()` return `True`, which triggers an unguarded CPU-only kernel import in sglang (`cache_move.py` → `from sgl_kernel import copy_all_layer_kv_cache_cpu`) that the XPU `sgl_kernel` build does not export:
   ```
   ImportError: cannot import name 'copy_all_layer_kv_cache_cpu' from 'sgl_kernel'
   ```


Upstream sglang declined to shield callers from this flag (sgl-project/sglang#41141, closed not merged): *"For XPU or CUDA, user doesn't have to set up this flag at all."* Since verl is the caller setting it unconditionally, the fix belongs here.

## High-level design / API

No API change. Pure removal of an internal env-var manipulation.

## Test

Because the flag only affects sglang's import + engine launch inside `_load_sglang()`, testing focused there. All on `sglang==0.5.19` (verl pins 0.5.20, one patch up), single A100, tp=1, Qwen2.5-0.5B-Instruct.

**1. Import path, CUDA** — flag removed, `_load_sglang()` imports `SGLangReplica` cleanly:
- GPU visible: OK (`is_cuda=True`, `is_cpu=False`)
- `CUDA_VISIBLE_DEVICES=""` (CPU-only-driver, the scenario the 2025 comment guarded): OK — the original fp8 import error does **not** reproduce.

**2. Real rollout, CUDA** — drove verl's actual path (`_load_sglang()` → `launch_server_process` → real SGLang HTTP server → `/generate`), comparing flag-removed vs flag-restored, interleaved. Warm-run throughput (excluding the one cold first-run, which paid one-time CUDA-graph/autotune/cache costs — `init=41s`, `9.5k tok/s` — on whichever condition ran first):

| condition | warm engine init | warm tok/s | output |
|---|---|---|---|
| flag removed (this PR) | ~35 s | ~13.1k (13087, 13117) | identical, coherent |
| flag restored (current main) | ~35 s | ~13.1k (13167, 13112, 12996) | identical, coherent |

The two conditions are statistically identical when warm. → **no regression on CUDA.** (Single GPU, tp=1, greedy decode, 3488 output tokens/run.)

**3. XPU** — the `ImportError` above reproduced on real B60 hardware and is caused by exactly this flag; removing it clears it.

I do **not** have verl's full CUDA CI / multi-GPU / Megatron matrix locally — please let CI exercise those paths. The change is a strict removal, so risk is bounded to the sglang import/launch path tested above.
