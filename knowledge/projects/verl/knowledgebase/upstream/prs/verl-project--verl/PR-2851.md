## Code Review

This pull request adds pipeline parallelism support for the vLLM ZMQ executor. The changes span across configuration, testing, and core execution logic. The implementation correctly handles model/data parallelism parameter calculations and introduces a mechanism to manage ZMQ socket communication for pipeline stages.

My review identifies two key issues. First, a critical bug in the worker initialization logic where shallow copies of configuration dictionaries are used, which would lead to incorrect worker setup. Second, a high-severity performance issue in the ZMQ executor where a single-threaded pool is used for receiving messages, serializing I/O and negating the benefits of parallel execution. I've provided suggestions to fix both issues.

- gemini-code-assist[bot] · comment · 2025-08-01T00:46:39Z · [source](https://github.com/verl-project/verl/pull/2851#discussion_r2246640335)

File: `verl/workers/rollout/vllm_rollout/vllm_rollout_spmd.py` · line 477

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The `while` loop to populate `all_kwargs` uses a shallow copy by appending `all_kwargs[-1]`. This results in all elements of the list referencing the same dictionary object. Consequently, when a worker modifies its configuration with `all_kwargs[self.rpc_rank]['rank'] = self.rank`, it inadvertently alters the configuration for all other workers in the model-parallel group. This leads to incorrect ranks being passed during worker initialization. To fix this, you should use `deepcopy` to create a unique configuration dictionary for each worker.

```suggestion
            all_kwargs.append(deepcopy(all_kwargs[-1]))
```

- gemini-code-assist[bot] · comment · 2025-08-01T00:46:39Z · [source](https://github.com/verl-project/verl/pull/2851#discussion_r2246640339)

File: `verl/workers/rollout/vllm_rollout/vllm_async_server.py` · line 171

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

Using a `ThreadPoolExecutor` with `max_workers=1` for handling asynchronous `recv` calls from multiple sockets serializes these operations. This creates a significant performance bottleneck, especially with pipeline parallelism where multiple workers produce outputs concurrently. The system will wait for replies in a fixed order (rank order), even if a higher-ranked worker is ready sooner. This negates the benefits of parallel execution.

To improve performance, the number of workers in the thread pool should be increased to allow concurrent receives from all sockets. A value equal to the number of workers (`self.parallel_config.world_size`) would be appropriate. The comment about preserving dequeue sequence seems to be a misunderstanding, as the order of futures in the returned list is based on submission order, not completion order.

```suggestion
        if self.max_concurrent_batches > 1:
            # Using a thread pool to receive from sockets concurrently.
            self.io_thread_pool = ThreadPoolExecutor(
                max_workers=self.parallel_config.world_size,
                thread_name_prefix="zmq_exec_io")
```
