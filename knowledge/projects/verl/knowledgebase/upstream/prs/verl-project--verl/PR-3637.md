## Code Review

This pull request introduces an experimental implementation of SVD-LoRA-GRPO. The core logic is in the new `verl/utils/experimental/svd_lora.py` file, with integrations in FSDP utilities and worker configurations. My review has identified a few critical issues. There's a `TypeError` in `SVDLinear.create_from_weight` that will cause a runtime crash. More importantly, the implementation in `apply_svd_lora` seems to misinterpret the paper by performing SVD on LoRA's A and B matrices separately, instead of on their product `W=BA`. I've also pointed out a high-severity issue in `fsdp_utils.py` where reconstructed weights are not moved to the CPU, and a high-severity maintainability issue regarding the use of a deprecated PyTorch function. Please address these points to ensure the correctness and robustness of this new feature.

- gemini-code-assist[bot] · comment · 2025-09-27T15:53:56Z · [source](https://github.com/verl-project/verl/pull/3637#discussion_r2384224663)

File: `verl/utils/experimental/svd_lora.py` · line 91

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The current implementation in `apply_svd_lora` performs SVD on `lora_A` and `lora_B` weight matrices separately. This appears to contradict the description in the ESSA paper, which states that the LoRA adapter `W = BA` is decomposed. The current approach results in composing two SVD-decomposed layers, `SVDLinear_B(SVDLinear_A(x))`, which is not equivalent to decomposing `W`.

To correctly implement the paper's method, you should iterate over `LoraLayer` modules, compute `W = lora_B.weight @ lora_A.weight`, perform SVD on `W`, and then replace the LoRA forward computation with a new layer that uses the SVD components. This would likely require monkey-patching the `forward` method of the `LoraLayer`.

- gemini-code-assist[bot] · comment · 2025-09-27T15:53:56Z · [source](https://github.com/verl-project/verl/pull/3637#discussion_r2384224664)

File: `verl/utils/experimental/svd_lora.py` · line None

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

`torch.svd` is deprecated and will be removed in a future version of PyTorch. It's recommended to use `torch.linalg.svd` instead. Note that `torch.linalg.svd` returns `U, S, Vh` where `Vh` is the conjugate transpose of `V`. For real matrices, `Vh` is `V.T`. The `_get_svd_weight` method uses `self.V.T`, so you'll need to store `Vh.T` as `self.V` for the reconstruction to be correct.

```suggestion
        U, S, Vh = torch.linalg.svd(weight.to(torch.float32), full_matrices=False)
        V = Vh.T
```

- gemini-code-assist[bot] · comment · 2025-09-27T15:53:56Z · [source](https://github.com/verl-project/verl/pull/3637#discussion_r2384224665)

File: `verl/utils/fsdp_utils.py` · line None

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The reconstructed weight tensor is not moved to the CPU. This is inconsistent with `gather_standard_params` and the original implementation, which both move parameters to the CPU. Leaving the tensor on the GPU can lead to unexpected GPU memory consumption and potential issues if the calling code expects CPU tensors.

Additionally, using `U * sigma` is more efficient for this operation than `U @ torch.diag(sigma)`.

```suggestion
        collected[f"{prefix}.{layer_name}.weight"] = ((U * sigma) @ V.T).cpu()
```
