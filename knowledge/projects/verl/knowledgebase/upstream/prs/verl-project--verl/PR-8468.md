# [trainer, rollout] fix: settle failed validation and cancel remote generation

[Upstream PR](https://github.com/verl-project/verl/pull/8468) · state: open · merged: False

## Original PR description

### What does this PR do?

**Status update: [uni-agent #294](https://github.com/verl-project/uni-agent/pull/294) now implements validation settlement and cancellation in its own integration against unmodified verl. It no longer depends on this PR.**

This PR remains an independent draft proposal; its code and commit history are unchanged. It makes interrupted validation settle with complete denominators: the V1 trainer invokes optional lifecycle hooks, skips empty TQ batches when all observations fail, counts missing reward/acc/score observations as zero, and confirms termination of dispatched Ray generation when the local call is cancelled.

These optional hooks remain a standalone verl proposal. The current uni-agent implementation owns its validation collector and client instead, so there is no required merge order or submodule update between these PRs. Existing agent loop managers without these proposed hooks retain their current path.

### Design & Code Changes

- `PPOTrainer._validate()`: create a unique run ID, invoke optional `begin_validation`, and carry the ID in prompt metadata. Skip failed batches with no trajectories and publish computed metrics before returning to the existing training flow.
- `process_validation_metrics()`: apply existing `expected_acc_counts` to reward and scorer score as well. Missing observations count as zero; `*_success_only` retains conditional statistics. Sources that do not define acc/score do not acquire synthetic metrics.
- `LLMServerClient.generate()`: retain the specific Ray generation reference, cancel it when the caller is cancelled, wait a bounded time for remote acknowledgement, and propagate cancellation. Unrelated requests are not interrupted.
- Add regressions for partial failure, total failure, mixed sources, and two concurrent requests on a real Ray actor: cancelling one terminates it while the other remains active.

- koriyoshi2041 · comment · 2026-10-31T03:52:29Z · [source](https://github.com/verl-project/verl/pull/8468#issuecomment-6538653183)

The bounded wait in `LLMServerClient.generate()` can replace the caller's cancellation with `ray.exceptions.GetTimeoutError`. `ray.cancel()` is best-effort, and if the async actor has not acknowledged it within 5 seconds, `ray.get(..., timeout=5)` takes the uncaught timeout path, so the bare `raise` is never reached. The new test covers prompt acknowledgement but not this timeout boundary.

Could this catch `GetTimeoutError` as well (ideally logging that remote settlement was not confirmed) and then re-raise the original `CancelledError`? That preserves the method's cancellation contract even when remote cleanup is slow.
