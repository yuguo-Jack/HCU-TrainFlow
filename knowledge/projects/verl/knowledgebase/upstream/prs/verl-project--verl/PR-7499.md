# [megatron] fix: don't crash fused forward when labels is None (#5273)

[Upstream PR](https://github.com/verl-project/verl/pull/7499) · state: open · merged: False

## Original PR description

## What

`patch_fused_forward()` monkey-patches `model.forward` to `_fused_GPTModel_forward` whenever `use_fused_kernels=True` (legacy pre-0.18 Megatron-Core mode). That function unconditionally fed `labels` into `linear_cross_entropy(...)`, but `labels` defaults to `None`, and `linear_cross_entropy.forward()` does `len(labels.shape)` unconditionally at `verl/utils/kernel/linear_cross_entropy.py:74` — so any caller invoking the patched forward without labels (e.g. `enable_mtp=False`) crashes with:

```
AttributeError: 'NoneType' object has no attribute 'shape'
```

Fixes #5273.

## Fix

When `labels is None`, `_fused_GPTModel_forward` now skips the fused cross-entropy kernel and instead projects `hidden_states` through the resolved `output_weight` to produce plain logits, mirroring the no-labels branch of the real (unpatched) `GPTModel._postprocess` (verified against `megatron-core==0.16.1` source). The labels-provided path is untouched.

`patch_fused_forward` itself is left unconditional — `verl/workers/engine/megatron/transformer_impl.py`'s `_maybe_enable_fused_kernels` already disables fused kernels whenever MTP is enabled, so the crash isn't really about MTP; it's that the monkey-patched `forward()` is reachable from other call sites without labels. Making the forward itself robust to `labels=None` is the more general fix.

## Testing

No GPU/`megatron-core` available in the environment this was developed in, so:
- `tests/models/test_model_forward_fused.py` (new) — written against the real module, will run in CI.
- A standalone harness that loads the actual, unmodified `model_forward_fused.py` via `importlib` with `megatron.core.*` stubbed out, driving `_fused_GPTModel_forward` directly with fakes: **13/13 checks pass** on the fixed code, and correctly **fails** when run against the pre-fix code (verified via `git stash`).
- `ruff check` / `ruff format --check` pass.

> Returning the logits directly here defeats the original purpose of the fused implementation. [...] this interface expects an output structure, so returning logits directly may cause issues.

That objection is correct, and it applies to #5332, which does `return logits` — a bare `torch.Tensor`, where the labels-provided path returns `CausalLMOutputForPPO`. That inconsistent return type is also what the bot review on #5332 flagged.

This PR does not return a bare tensor. It sets `output.logits` and returns `output`, so the return type is the same on both branches. It additionally:

- gathers across the tensor-parallel region (honouring `runtime_gather_output`, else `output_layer.gather_output`), which #5332 omits;
- transposes `[s, b, v]` -> `[b, s, v]` to match the un-patched `GPTModel._postprocess` contract;
- adds a regression test (#5332 has none).

On the MTP point in that same review: `patch_fused_forward` is deliberately left unconditional here. `_maybe_enable_fused_kernels` in `verl/workers/engine/megatron/transformer_impl.py` already disables fused kernels when MTP is on, so the crash is not really about MTP — it is that the patched `forward()` is reachable from call sites that pass no labels. Making the forward robust to `labels=None` is the narrower fix; supporting MTP under fused mode is a separate piece of work and is not attempted here.

Maintainers: happy either way — land #5332 first and I will rebase this down to just the gather/transpose/return-type correction plus the test, or land this and close #5332 as superseded with credit to @devchilll. I have no preference beyond not duplicating review effort.
