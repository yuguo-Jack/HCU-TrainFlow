# [reward] fix: bound reward model HTTP requests with configurable timeouts

[Upstream PR](https://github.com/verl-project/verl/pull/8527) · state: open · merged: False

## Original PR description

### What does this PR do?

When a discriminative reward backend accepts a connection but never completes its response, `RewardLoopWorker._post_request()` waits indefinitely because it explicitly passes `ClientTimeout(total=None)`. Its timeout retry handler is never reached, so batch reward computation can stall indefinitely.

## Summary

```diff
 HTTP request to the built-in reward model
- no request deadline
+ finite, positive reward.reward_model.request_timeout (default: 300 seconds)
  existing bounded retry policy and exponential backoff
```

The deadline includes connection establishment and reading the response body. Exhausting retries propagates the error. Custom reward functions continue to manage their own HTTP clients.

This is independent of #8015, which repairs the mathematical verifier's shared process pool. It also completes the HTTP timeout behavior noted in the review of #4628; the current main branch still disables that deadline. Searches for open PRs containing `request_timeout`, `_post_request`, and `ClientTimeout` found no overlapping fix on 2026-11-04.

### API and Usage Example

```bash
# Per attempt, not for the entire batch or all retries combined.
reward.reward_model.request_timeout=120.0
```

The value must be finite and positive. The default is 300 seconds. Existing configurations without the new key use that same default.

### Design & Code Changes

- Apply and validate the timeout before the HTTP retry loop.
- Add the configuration field to `RewardModelConfig`, source YAML, and four generated reference configs.
- Document the deadline and its relationship to retries.
- Add CPU tests using an ephemeral local server; no model downloads or GPU are required.

## Merge Danger

**Door:** Two-way.

**Blast Radius:** Reward.

Requests that previously ran longer than five minutes now time out and retry by default. Backends that legitimately need longer requests should raise `reward.reward_model.request_timeout`. With the existing 16-attempt policy, total elapsed time can still substantially exceed one request deadline. Client cancellation/timeout does not guarantee cancellation of inference already running on the backend.
