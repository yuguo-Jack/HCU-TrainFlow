# feat(tools): add local thread pool option for tool execution

[Upstream PR](https://github.com/verl-project/verl/pull/5673) · state: closed · merged: False

## Original PR description

### What does this PR do?

Fixes https://github.com/verl-project/verl/issues/5646

Add a `use_ray_execution_pool` config option to `SandboxFusionTool` that allows users to choose between Ray actor-based execution pool and a local thread pool for tool execution.

**Motivation**: On AMD ROCm platforms (e.g., MI300X/MI308X), Ray actor-based tool calls exhibit significantly higher latency compared to NVIDIA GPUs, due to differences in IPC communication patterns and the HIP compatibility layer. The local thread pool mode bypasses Ray actor serialization overhead using `asyncio.run_in_executor` with a local `threading.Semaphore`, which is effective for single-node training.

**Changes**:
- Add `use_ray_execution_pool` config option (default: `False`) to `SandboxFusionTool`
- Fix `ExecutionWorker.execute()` crash when `enable_global_rate_limit` is set to `False` (null check for `rate_limit_worker`)
- Add AMD platform documentation for tool execution latency optimization

**Related recipe PR**: https://github.com/verl-project/verl-recipe/pull/69

## Code Review

This pull request introduces an option to use a local thread pool for tool execution instead of a Ray actor pool, which is a great optimization for single-node, especially on AMD platforms. The documentation updates are clear and helpful.

My main feedback is a critical issue in the implementation of the local thread pool. The use of `threading.Semaphore` with a blocking `acquire()` call within an `async` function will block the event loop, which can cause severe performance problems. I've suggested a fix to use `asyncio.Semaphore` instead, which is the correct pattern for this scenario.

The bug fix for the `ExecutionWorker` null check is also a good addition.

Using `threading.Semaphore` in an `async` context can lead to blocking the event loop. Since the `execute` method is `async`, it's better to use `asyncio.Semaphore` to ensure non-blocking behavior. This will prevent performance degradation and potential deadlocks.

```suggestion
        self._local_semaphore = asyncio.Semaphore(self.num_workers)
```

The `acquire()` method of `threading.Semaphore` is a blocking call. In an `async` function, this will block the event loop. To correctly handle concurrency limiting in an asynchronous context, you should use `async with` on an `asyncio.Semaphore` (as suggested for line 148). This is the idiomatic and non-blocking way to acquire and release a semaphore in `asyncio`.

```python
            async with self._local_semaphore:
                result = await asyncio.get_running_loop().run_in_executor(
                    None, self.execute_code, instance_id, code, timeout, language
                )
```
