# [ckpt] fix: fail LoRA-only checkpoint load when adapter keys are missing

[Upstream PR](https://github.com/verl-project/verl/pull/8350) · state: closed · merged: False

## Original PR description

### What does this PR do?

`FSDPCheckpointManager.load_checkpoint` loads a LoRA-only checkpoint with `strict=False` (it legitimately lacks the frozen base weights) and already raises on unexpected keys, but never looks at `missing_keys`. If the checkpoint lacks some adapter tensors (e.g. a different `target_modules`, or a truncated/partial save), those tensors silently keep their fresh initialization while the rest of the adapter and the optimizer state are restored, and training resumes from a model that is neither the saved one nor a clean start.

This PR raises a `ValueError` when any missing key is a LoRA/adapter key (same `lora_` / `.adapter_` rule as `is_lora_only_state_dict`). Missing base weights are still accepted.

Scope: the check runs per rank after that rank's `load_state_dict`. Every rank saves the same key set, so a checkpoint that lacks adapter keys (e.g. a different adapter config) fails on every rank. A shard corrupted on only one rank is not handled here: with FSDP1 the ranks may already diverge inside the sharded load, and otherwise only that rank raises. Catching that would need a preflight of expected adapter names plus a collective failure flag, which is left out to keep this change small.
