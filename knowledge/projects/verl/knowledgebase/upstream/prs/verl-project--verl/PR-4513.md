# [vLLM] feat: Adds video input support to vLLM rollout

[Upstream PR](https://github.com/verl-project/verl/pull/4513) · state: open · merged: False

## Original PR description

### What does this PR do?

Ensure video data is passed to vLLM to prevent empty features in vlm mrope calculations

#### Description
This PR modifies the data flow to ensure video data is correctly delivered to vLLM alongside other multi-modal information. This fixes an issue where Qwen3-VL would receive empty video features during mrope calculations.

#### Detailed Changes:

verl/experimental/agent_loop/single_turn_agent_loop.py: Extracted video data from the non-tensor batch, passed it to the server, and preserved it in the output. While the processor is still used to generate prompt IDs, it no longer processes the video data locally; instead, the video is passed directly to the inference backend.

verl/experimental/agent_loop/agent_loop.py: Updated AsyncLLMServerManager.generate to support video_data argument and forward it to the underlying vLLM actor.

verl/workers/rollout/vllm_rollout/vllm_async_server.py: Modified TokensPrompt to include video data within multi_modal_data when passing it to vLLM (alongside the existing image data).

## Code Review

This pull request correctly adds support for passing `video_data` to the vLLM server, which is a crucial step for enabling video modality. The changes plumb the new parameter through `AsyncLLMServerManager`, `SingleTurnAgentLoop`, and into the `vLLMAsyncRollout` worker.

However, I've identified a critical issue in an unchanged part of the code that this PR makes relevant. In `verl/experimental/agent_loop/agent_loop.py`, the `_agent_loop_postprocess` method does not pass video data to the processor when preparing data for training (line 526). This will lead to incorrect RoPE indices for video tokens, as `video_grid_thw` will be missing for the `get_rope_index` call. This could silently corrupt training data. Since this is outside the diff, I'm highlighting it here and strongly recommend fixing it to ensure end-to-end correctness.

I have also added one specific comment regarding the handling of empty lists for media data, which could lead to data being dropped.

- Miku2G · comment · 2025-12-16T12:04:07Z · [source](https://github.com/verl-project/verl/pull/4513#issuecomment-3660186980)

@EchoMinkki 
The Qwen3-VL processor in vLLM requires the input prompt to retain the original video placeholder string `<|vision_start|><|video_pad|><|vision_end|>`. The engine expects to handle the expansion (replacing it with timestamps + multiple video_pad tokens) internally.

Currently, the HuggingFace processor expands these placeholders before the request reaches vLLM. As a result, vLLM cannot find the expected replacement target, triggering the following error: `AssertionError: Failed to apply prompt replacement for mm_items['video'][0]`

I am implementing two fixes to address this:

single_turn_agent_loop.py:

Separate the prompt IDs. We will pass server_prompt_ids (with unexpanded placeholders) to vLLM, while still using the expanded prompt_ids via the processor for the training output/logs.

vllm_async_server.py:

Adjust the max_tokens calculation. Since the unexpanded prompt is significantly shorter, the default calculation might result in an overestimated max_tokens value. I'm adding a check similar to `max_tokens = min(response_length, max_model_len - len(prompt_ids))` to prevent context window overflow.

- Miku2G · comment · 2025-12-17T06:21:24Z · [source](https://github.com/verl-project/verl/pull/4513#issuecomment-3663841946)

@DesertsP 
In this commit, the agent loop now explicitly supports two non-mixed video input formats:                                                                                                                           
   1. Qwen-style video dicts (as documented in verl/utils/dataset/vision_utils.py, where fps/min_frames/max_frames live in the dict). For these, we preprocess via process_video(..., return_video_metadata=True) and normalize to the (frames, metadata) format expected by the downstream HF processor and vLLM.                                                                                                                  
   2. Pre-decoded frames (numpy/torch tensors, optionally wrapped as (frames, metadata) tuples). For these, we keep do_sample_frames=False and pass video_metadata when available. If a list mixes dict-based specs and pre-decoded frames, we now raise a clear ValueError instead of silently producing empty video features.                                                                    
                                                                                                                                                                                                                
  Regarding AsyncLLMServerManager.generate: I intentionally didn’t add a new mm_processor_kwargs / video_kwargs parameter because it would expand a cross-backend RPC/API contract and require plumbing through all rollout server implementations. The official sampling knobs are already carried by the video dict itself, and after preprocessing we pass (frames, metadata), so we don’t need to change the generate signature to address this issue.

The checks `if image_data:` and `if video_data:` will evaluate to `False` if an empty list is passed (e.g., `[]`), which can be a valid value.
```suggestion
        if image_data is not None:
            multi_modal_data["image"] = image_data
        if video_data is not None:
            multi_modal_data["video"] = video_data
```
