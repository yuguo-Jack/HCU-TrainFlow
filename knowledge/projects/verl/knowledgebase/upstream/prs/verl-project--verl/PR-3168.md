# [WIP] DistDataProto: An Easy-to-Use Transparent Distributed Data Layer

[Upstream PR](https://github.com/verl-project/verl/pull/3168) · state: open · merged: False

## Original PR description

### What does this PR do?

A work-in-progress implementation for [volcengine/verl#2847](https://github.com/volcengine/verl/issues/2847) and long sequence training related challenges.

## Overview
We propose **DistDataProto** - a user-friendly, transparent distributed data storage format. This implementation:
- Maintains API compatibility with DataProto
- Replaces storage backend with distributed node-wise storage
- Transmits only metadata and data references during dispatch/collect phases
- Materializes data via P2P communication only when needed
- Implements prefetching to overlap computation and communication delays during mini-batch iterations

## Current Limitations
### Generate Sequences
- Current implementation transmits all data to generation engine for internal scheduling, because of potential bubbles in generation engine if we implement mini-batch prefetching here
- **Discussion Needed**: Optimal batching strategy for generation pipeline

### Advantage Calculation
- UID grouping requirement for algorithms like GRPO
- Current architecture requires modifications to enable prefetching at this stage

## Code Review

This pull request introduces a work-in-progress implementation of DistDataProto, a distributed data layer. The changes are extensive, adding many new files for configuration, worker implementations, and a new distributed data protocol. The core idea is to replace the existing data storage with a distributed, node-wise storage system that uses lazy materialization and prefetching to optimize performance. While the overall direction is promising, I've identified several critical issues related to undefined variables, incorrect attribute access, and in-place configuration modifications that will cause runtime errors or lead to hard-to-debug side effects. There are also some API inconsistencies in the new engine abstraction. Addressing these issues will be crucial for the stability and maintainability of this new data layer.

Modifying the configuration object `self.config` in-place (e.g., `self.config.actor.ppo_mini_batch_size *= ...`) can lead to unexpected side effects. This pattern is repeated for `rollout` and `ref` configs in this class, and also in `CriticWorker` and `RewardModelWorker`. It's a better practice to treat configuration objects as immutable after initialization. Please consider creating deep copies of the relevant config sections for modification or storing the normalized values in new instance attributes to avoid hard-to-debug issues.
