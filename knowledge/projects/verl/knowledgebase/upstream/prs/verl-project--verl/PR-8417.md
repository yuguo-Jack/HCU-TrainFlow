# [veomni, vllm, model] feat: support M3.1-Flash multimodal full-weight RL

[Upstream PR](https://github.com/verl-project/verl/pull/8417) · state: closed · merged: False

## Original PR description

### What does this PR do?

Add M3.1-Flash multimodal input handling and public-checkpoint-layout full-weight export to the **VeOmni training / vLLM rollout** path. This enables the full-parameter M3.1-Flash integration without adding generic LoRA support.

The target checkpoint is **MiniMax-M3.1-Flash**. Its checkpoint config uses `model_type="minimax_m3_vl"` and architecture `MiniMaxM3SparseForConditionalGeneration`; existing `minimax_m3` module/class identifiers are retained for compatibility. They are architecture identifiers, not a claim that a different model version was validated.

Model dimensions and dense/MoE schedules come from config. Export validates EP ownership and streams expert rows; vision/projector and fused dense/expert keys map to the public layout. Image placeholders are collapsed before vLLM expansion, and the expanded inference prompt is checked against the training token sequence.

### Why this is not duplicate work

Searched open [MiniMax PRs](https://github.com/verl-project/verl/pulls?q=is%3Apr+is%3Aopen+MiniMax) and [VeOmni LoRA PRs](https://github.com/verl-project/verl/pulls?q=is%3Apr+is%3Aopen+VeOmni+LoRA) on 2026-10-28. #8353 uses verl-native FSDP2 for a text model; this is the VeOmni multimodal route. [VeOmni #1315](https://github.com/ByteDance-Seed/VeOmni/pull/1315) provides the model but explicitly lacks rollout-layout export. #8307 supplies generic dense LoRA and is not included here; its checkpoint import compatibility pattern is acknowledged.

### Test

- Ported to main `2ab35292039a51175a4b3d3b3b2d76e951a0d3e4`, preserving its newer vLLM admission helper and VeOmni engine changes.
- **30 CPU cases passed again (4.84s)**: tensor-name/shape contracts, image-span normalization, and two-process Gloo expert-row export.
- Public-layout inverse check: all **23,416 public keys / 1,582 native parameters**, with full 60-layer / 128-expert / 32-vision-layer key layout and reduced matrix sizes, round-trip exactly, including shuffled input order. This is a layout check, not full-model allocation or training.
- Scoped Ruff lint/format and `bash -n examples/grpo_trainer/run_minimax_m3_veomni.sh` pass.
- CPU command: `python -m pytest --noconftest -o addopts= -q tests`, with plugin autoload disabled, on an isolated task-owned source snapshot and existing Python 3.12 server packages.
- The helper tests do not import or run the complete Ray/vLLM/VeOmni stack. No new hardware run, standard repository conftest/scheduler run, or full-repository pre-commit is claimed for this port.

### Historical full-model evidence

The experimental stack used the complete **60-layer / 128-expert M3.1-Flash**, with **16 nodes / 256 NPUs**, training EP32/SP1 and rollout EP64. It completed two actor updates and weight synchronizations. Reward was 0.6476563 then 0.7145833; gradient norms were 0.2054841 and 0.2149987. DSpark was disabled.

This is historical evidence from the experimental stack, not a fresh run of this extracted branch. Train/evaluation used the same 500 examples; the driver later exited nonzero and no checkpoint was produced. It does not establish generalization, long-run stability, or an SFT result.

### Dependency and reproduction

The model/base operators originate from VeOmni #1315. A publicly addressable integration source is now available:

```bash
uv pip install --no-deps 'veomni @ git+https://github.com/Li-Jicheng/VeOmni.git@d51ffd7ca60b65be361091c2f3c95828772262ef'
```

Use this only inside a compatible VeOmni/verl environment; --no-deps does not resolve the rest of the stack. This is a fixed integration revision, not a released package. Its source includes #1315, a pinned dense-reference dependency from VeOmni #1337, and expert-LoRA work used by the separate LoRA follow-up; this full-weight PR does not require that generic verl LoRA follow-up.

**Draft acceptance:** this PR intentionally does not replace verl's global VeOmni install pin or claim its current uv.lock resolves this integration. Final dependency selection and lock regeneration/validation remain required before merge. The companion upstream PR is [VeOmni #1380](https://github.com/ByteDance-Seed/VeOmni/pull/1380); the fixed source commit above remains the reproducible integration reference.
