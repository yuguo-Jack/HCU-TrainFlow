# [fsdp, veomni] feat: opt in to FP32 logits before temperature scaling

[Upstream PR](https://github.com/verl-project/verl/pull/8419) · state: closed · merged: False

## Original PR description

### What does this PR do?

When `VERL_POLICY_FP32_LOGITS=1`, upcast logits **before temperature division** in the shared unfused FSDP/VeOmni postprocessing helper. Casting only after low-precision division cannot recover the rounding already introduced.

Unset/0 preserves the existing dtype and unit-temperature no-copy path. The option keeps the lm_head matmul in its original dtype, adds no diagnostic printing, and does not affect fused loss kernels that bypass this helper. FP32 vocabulary tensors use more memory; the option is explicit and off by default.

### Duplicate-work check

Searched [FP32 logits](https://github.com/verl-project/verl/pulls?q=is%3Apr+is%3Aopen+FP32+logits) and [VERL_POLICY_FP32_LOGITS](https://github.com/verl-project/verl/pulls?q=is%3Apr+is%3Aopen+VERL_POLICY_FP32_LOGITS) on 2026-10-28.

- #8004 changes the lm_head projection compute precision and has different model/device constraints; this changes postprocessing only.
- #8026 adds batch-invariant FSDP execution and a sampler logprob formula using unscaled logits. This smaller option applies at the shared helper, including ordinary non-batch-invariant FSDP/VeOmni consumers and their entropy/other uses of the scaled logits. It does not claim the complete sampler formula or batch invariance from #8026.
- #8377 changes numerical stability inside torch logprob calculation; this addresses the earlier temperature-division rounding.

This draft is independent of the MiniMax model/LoRA drafts and has no pending VeOmni source dependency. Maintainer feedback on a typed configuration field versus the opt-in worker environment flag is welcome before merge.

### Historical evidence

On the same archived BF16 training logits, with sampler and norm fixes already enabled, mean absolute probability difference changed from **0.006243378492 to 0.005188585780 (16.8946% lower)** when FP32 postprocessing was added.

The 2026-10-18 experiment used a historical MiniMax-M3 checkpoint with 60 text layers and **8 routed experts**, not full 128-expert M3.1-Flash. All four archived variants shared 64 responses and 54,762 valid response tokens, with image-token correction present throughout. The combined sampler + norm + postprocessing result was 0.014523769978 to 0.005188585780 (64.2752% lower). These are conditional, sequential contributions; they must not be added or attributed entirely to this PR. Sampler mode changes the probability being reported and is not an equivalent change in forward-logit error.

The archived 16-NPU GRPO diagnostic iteration completed rollout, backward and weight synchronization: 64 responses / 56,409 valid response tokens, mean probability difference 0.005803629756, gradient norm 0.054521188140, and exit 0. Its learning rate was 0, so this verifies the execution path, not learning progress. This is archived evidence, not a new hardware run of this port. The 2026-10-24 attempt failed before a complete update and contributes no new metric.

The archived launcher set `VERL_POLICY_FP32_LOGITS=1` and `VERL_POLICY_FP32_HEAD=0`; all 16 training ranks recorded activation on BF16 logits, and the runtime source hashes matched the saved candidate. Historical CPU checks also passed for default behavior, the FP32 numerical oracle, gradients and unit temperature. Rechecking the saved helper against this PR confirms equivalent computation after excluding the one-time diagnostic print and normalizing the disabled environment default.

Historical commands were `bash real_step/run.sh` (the archived configured 16-NPU driver) and the paired postprocessing entry point `run_train_pair.sh` / `train_pair.py`. These are existing experiment artifacts, not commands rerun on the current PR checkout. The contributor asked to use their existing experiments as relevant validation; the five new CPU regressions above were run separately by the assistant.

### Usage and acceptance

Set the non-sensitive flag consistently in **all Ray worker environments** that compute policy/reference probabilities:

```text
VERL_POLICY_FP32_LOGITS=1
```

Only the literal value 1 enables it. A launcher-shell export alone is insufficient if the worker environment does not inherit it. Check vocabulary-tensor peak memory on the intended workload. Fused loss paths need separate treatment.
