# [utils] fix: honor tokenizer.json when AutoTokenizer rebuilds the pre-tokenizer

[Upstream PR](https://github.com/verl-project/verl/pull/8193) · state: open · merged: False

## Original PR description

### What does this PR do?

`hf_tokenizer` now checks that the tokenizer returned by `AutoTokenizer` encodes like the `tokenizer.json` it was loaded from and, on mismatch, loads the file as stored (`PreTrainedTokenizerFast`).

transformers 5 rebuilds some tokenizer classes (e.g. `LlamaTokenizer`) from the class recipe and ignores the pre-tokenizer stored in `tokenizer.json`. For a byte-level BPE vocabulary whose `tokenizer_config.json` names such a class, every space and newline is dropped without any error:

```
"Solve it  step by step.

	x = 3"  ->  "Solveitstepbystep.x=3"
```

Prompts, validation text and decoded responses become run-together text, and no train/rollout consistency check catches it because both sides see the same token ids. Reproduced with transformers 5.5.3, 5.12.0 and 5.17.0.

### Test

`tests/utils/test_hf_tokenizer_on_cpu.py`: a byte-level vocabulary filed under a generic class and under `LlamaTokenizerFast`; ids must equal the raw `tokenizers` encoding and decode back to the text. The Llama case fails without the fix.

### API and Usage Example

No API change. Tokenizers that already reproduce their `tokenizer.json`, and paths without a local `tokenizer.json`, are returned unchanged.
