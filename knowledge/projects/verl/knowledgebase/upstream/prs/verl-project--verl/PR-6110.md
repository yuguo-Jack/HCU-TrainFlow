# [fsdp, training_utils] feat: support per-sample temperature with fused linear cross entropy

[Upstream PR](https://github.com/verl-project/verl/pull/6110) · state: open · merged: False

## Original PR description

## Summary
Currently `use_fused_kernels=True` requires a scalar `temperature`, which blocks RL training setups that need per-sample temperatures (e.g. teacher/distillation mixing, mixed data). This PR makes both fused implementations accept either a Python scalar (unchanged) or a 1-D per-token tensor, without regressing the scalar fast path.

The approach is to pre-scale the hidden states by `1/T` in fp32 before the fused matmul and then run the kernel with `temperature=1.0`. Since softmax and logsumexp are invariant to a constant multiplicative factor on logits, this is mathematically equivalent to the `logits / T -> cross_entropy` baseline and keeps the kernel's memory and compute profile essentially unchanged.

## Changes
- `verl/utils/torch_functional.py`: new `prescale_hidden_by_per_sample_temperature` and `resolve_temperature_for_fused_kernel` helpers.
- `verl/utils/kernel/linear_cross_entropy.py` (Triton): accept `Union[float, Tensor]`, dispatch via helper.
- `verl/utils/experimental/torch_functional.py` (`FusedLinearForPPO`): same dispatch.
- `verl/workers/engine/fsdp/transformer_impl.py`: forward `temperature_rmpad` to the fused kernel when `use_remove_padding=True`; keep scalar-only assertion on the non-remove-padding path.
- `tests/utils/test_linear_cross_entropy.py`: add uniform-tensor-equals-scalar and per-sample-vs-fp32-reference tests (fwd + bwd) for both Triton and PyTorch fused paths. Also fixes a pre-existing `TypeError` when `MAX_TEST_CASES` is set from the shell (stringified int).

## Tests
`pytest tests/utils/test_linear_cross_entropy.py -v`

@ETOgaosion Thanks for the review! I'd like to confirm the intent, since there are a couple of design points hidden here.

The reason temperature is currently Union[float, Tensor] is that the underlying fused kernels (both Triton and the torch path) only accept a scalar temperature and do logits / T internally. To support per-sample temperature without rewriting the kernels, I prescale hidden by 1/T (fp32) only in the tensor-with-many-elements case and call the kernel with temperature=1.0; the scalar case stays on the kernel's native path, which avoids one extra bf16 rounding on hidden and an extra hidden-sized copy.

So unifying to torch.Tensor could mean two different things:

- Unify only the public signature — always take a torch.Tensor, but internally still short-circuit to the native scalar path when it's 1-element/uniform. Keeps the scalar fast path's precision & perf, but an internal branch remains.
- Unify the whole execution path — always prescale hidden and run the kernel at temperature=1.0. Removes all branching, but slightly changes scalar numerics (extra bf16 rounding) and always pays the hidden copy.

Could you clarify which one you're after?

Consequently, `temperature.item()` at line 1011 will raise a `ValueError` because it is only valid for tensors with exactly one element. Since the assertion at line 881 ensures that the temperature is uniform for the padded path, you should extract the scalar value safely (e.g., using `view(-1)[0]`) to satisfy the fused kernel's requirement for a float.

            else:
