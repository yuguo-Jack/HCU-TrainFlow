# [perf, trainer] fix: forward global torch profiler contents/discrete to role tool configs

[Upstream PR](https://github.com/verl-project/verl/pull/8409) · state: closed · merged: False

## Original PR description

### What does this PR do?

`global_profiler.global_tool_config.torch.contents` and `.discrete` were silently ignored. The actor, critic, and ref role configs hardcoded `tool_config.torch.contents: []` and `discrete: false`, instead of interpolating from the global config the way `nsys.discrete` (`actor.yaml` line 221) and every `torch_memory` field already do. Rollout mirrors the actor config, so it inherited the same gap.

The empty contents fall back to `[CPU, CUDA]` activities inside `torch_profile.py` (`verl/utils/profiler/torch_profile.py:200-212`), so listing `cpu`/`cuda` globally appeared to work by coincidence, while `stack` (the `with_stack` flag, `torch_profile.py:231`) was dropped outright — a global setting of `contents=["cpu","cuda","stack"]` produced traces with no call stacks.

This wires the two fields through `${oc.select:global_profiler.global_tool_config.torch.*,default}` in the actor/critic/ref yamls, regenerates the `_generated_*.yaml` reference files, adds a CPU test, and documents the global path.

Found while profiling a training run with `++global_profiler.global_tool_config.torch.contents=["cpu","cuda","stack"]`: the collected trace had kernel/cpu_op activity but no stacks, and stream-level event attribution was impossible.

# before: contents=["cpu","cuda","stack"] stopped at the global layer; workers saw []

    ++global_profiler.global_tool_config.torch.contents='["cpu","cuda","stack"]'
