# [trainer] fix: construct unpadded position IDs with explicit sequence axis

[Upstream PR](https://github.com/verl-project/verl/pull/8408) · state: closed · merged: False

## Original PR description

### What does this PR do?

Fixes the `left_right_2_no_padding()` producer so that unpadded `position_ids` always use the token axis as their jagged dimension.

For an equal-length batch of eight mRoPE samples shaped `(4, 575)`, `as_nested_tensor(..., layout=torch.jagged)` packs the component axis. The subsequent `maybe_fix_3d_position_ids()` metadata assignment makes `index_select_tensor_dict()` fail at `unbind()`:

```text
RuntimeError: split_with_sizes expects split_sizes to sum exactly to 575
(input tensor's size at dimension 1), but got split_sizes=[4, 4, 4, 4, 4, 4, 4, 4]
```

The patch concatenates along the last/token axis, reuses the `cu_seqlens` already calculated for input IDs, and supplies `jagged_dim=position_ids.dim() - 1` to the public PyTorch constructor. This covers ordinary 2D position IDs and 3D multi-component position IDs without an API or configuration change.

### Related work and scope

Related to #6851 and #7899. **This overlaps with the producer-side fix in the open PR #7901.** It is submitted as a focused alternative limited to this construction site, using the existing token offsets and an explicit public `jagged_dim` directly. It does not include #7901's broader serialization, dynamic-batch reconstruction, or consumer-side normalization changes and does not claim to replace that broader work.

Similar-PR search: https://github.com/verl-project/verl/pulls?q=is%3Apr+is%3Aopen+position_ids

### Test

Local validation against base `b65da71c1745b49e80adc218d02782a3df73d047`, on macOS CPU with Python 3.12.12, PyTorch 2.10.0 and TensorDict 0.10.0:

```bash
# With the new tests but before applying the production fix:
python -m pytest tests/utils/test_padding_on_cpu.py -k position_ids_sequence_axis -q --tb=short
# 8 failed, 7 passed, 8 deselected.
# Includes the exact 575/[4]*8 and 580/[4]*8 errors above.

# After applying the fix:
python -m pytest tests/utils/test_padding_on_cpu.py -q --tb=short
# 23 passed.

pre-commit run --files verl/workers/utils/padding.py tests/utils/test_padding_on_cpu.py --show-diff-on-failure
# All hooks passed.
```

The 15 new parameterized cases cover text / 3-component / 4-component positions; equal lengths 575 and 580, unequal lengths, a single sample, and the square-layout corner. They check selected/repeated/reordered sample values, public shape, and token-length offsets. The square mRoPE case also catches a wrong `(8, 4)` output where `(4, 8)` is expected even when no split exception is raised. These tests extend the existing CPU test file collected by the CPU CI workflow.

Additional private-environment validation, reported by the human submitter: on Ascend 910B3 with Qwen3.5-4B GRPO and the older verl checkout `8f8b122195ecf43475679fb6ee0204ee33f387c5`, the same local construction fix allowed both ordinary training and training with a custom actor-operator plugin to finish 250 steps each. The previously reported failure occurred with and without that plugin. These runs validate the local patch on that environment; they are not runs of this latest upstream checkout or of the complete #7901 patch, and their logs are not published here.
