# [reward] fix: prime_code scores every call-based APPS/TACO task 0

[Upstream PR](https://github.com/verl-project/verl/pull/8182) · state: open · merged: False

## Original PR description


### What does this PR do?

Fixes #8174. `prime_code` graded every call-based (function-call) APPS/TACO sample **0, even for a
correct solution**, and additionally gave 0 instead of partial credit under `continuous=True`. Two
defects, two commits:

1. **`testing_util.py` — parse layout (commit 1).** The call-based branch of `run_test` assumed
   LiveCodeBench-style tests: each input is a *string* holding one JSON value per line
   (`inputs.split("\n")` then `json.loads` per line). APPS and TACO publish call-based tests with
   each input already a *list of arguments* (e.g. `"inputs": [[[1,2,3,4,5,6,1], 3]], "outputs": [12]`),
   so `inputs.split` raised `AttributeError: 'list' object has no attribute 'split'` inside the
   grading subprocess. `_temp_run` catches it, appends `-1` for every test, and redirects stderr to
   `os.devnull` first — so nothing is logged and the sample just silently scores 0 (exactly the
   "looks like the model failed" symptom from the issue). Fix: decide **per test case** by whether
   the input is a string. Strings are parsed exactly as before (unchanged behavior for existing
   data); anything else is already the argument list and is used as-is, with inputs/outputs
   JSON-encoded only for the truncated metadata.

2. **`prime_code/__init__.py` — keep `fn_name` in per-sample runs (commit 2).** With
   `continuous=True` (what `default_compute_score` uses for `apps`/`taco`/`codecontests`/`codeforces`),
   the per-sample loop rebuilt each test case as
   `{"inputs": [inputs[i]], "outputs": [outputs[i]]}` — dropping `fn_name`. `run_test` therefore
   dispatched call-based samples to the **standard-input** branch, compared captured stdout against
   the expected return value, and every per-sample run failed with `Wrong Answer` / empty output.
   Consequence on main: call-based problems could only ever score through the all-tests-pass fast
   path; any failing test made the continuous score exactly 0 (e.g. 2/3 passing tests → 0.0). This
   affects **both** test layouts and is independent of the layout bug. Fix: propagate `fn_name` to
   the per-sample test cases when present; standard-input problems are untouched.

### Design & Code Changes

- `verl/utils/reward_score/prime_code/testing_util.py`: in `run_test`'s call-based branch, parse

  expected output as is, JSON-encoding both only for the truncated metadata.
- `verl/utils/reward_score/prime_code/__init__.py`: propagate `fn_name` into the per-sample test
  cases when present.
- `tests/utils/reward_score/test_prime_code_call_based_on_cpu.py`: new CPU test (both layouts x
  correct/wrong, plus the continuous-fraction case).
