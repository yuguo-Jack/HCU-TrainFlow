# [hardware, doc] feat: TPU examples: public-package image, 2-chip GRPO smoke test, DP shard size from TP, SFT torchrun fixes

[Upstream PR](https://github.com/verl-project/verl/pull/8288) · state: closed · merged: True

## Original PR description

### What does this PR do?

Combines three TPU example PRs into one so they can be reviewed and merged together, and builds the TPU image only from public packages. It supersedes #8266, #8271 and #8280. Only `examples/tpu/` changes; no library code.

### Changes

**1. 2-chip GRPO smoke test (from #8266)**

- The Qwen3-0.6B GRPO example now needs 2 chips (2x `v6e-1`) instead of 8 (2x `v6e-4`): one trainer chip and one rollout chip.
- `ray-tpu-v6e4-2slice.yaml` is renamed to `ray-tpu-v6e-2slice.yaml` and defaults to two `v6e-1` slices. Comments give the `v6e-4` / `v6e-8` values.
- `run_qwen3_0_6b_torchtitan.sh` defaults to `N_CHIPS_TRAINER=1 N_CHIPS_ROLLOUT=1` and uses the same trainer and rollout settings as `run_qwen3_4b_torchtitan.sh`.
- `examples/tpu/grpo/README.md`: the 2-chip flow is the default. A new section covers Qwen3-4B on 2x `v6e-4` and 2x `v6e-8`.

**2. DP shard size derived from TP (from #8280)**

- In all three TPU scripts, `DATA_PARALLEL_SHARD_SIZE` defaults to `TOTAL_TRAINER_CHIPS / TENSOR_PARALLEL_SIZE`.
- The default is unchanged at `TENSOR_PARALLEL_SIZE=1` (pure FSDP, still the fastest setting). With `TENSOR_PARALLEL_SIZE>1`, `dp_shard * tp == world_size` now holds without a manual override.
- Removed the outdated warning that TP>1 gives non-finite gradients on TPU. TP support landed in verl-project/verl-hardware-plugin#62 (merged).

**3. SFT `torchrun` fixes (from #8271)**

- `run_qwen3_0_6b_torchtitan.sh` used to abort under `set -u` when `TPU_WORKER_HOSTNAMES` was unset. Now `MASTER_ADDR` falls back to `127.0.0.1` on single-host runs, and multi-host runs exit early with a clear error if no routable master is set.
- `examples/tpu/sft/README.md` is updated for the `torchrun` default. The `ray job submit` examples now pass `SFT_TRAINER_MODE=ray` and the `verl-hardware-plugin` runtime env.

**4. TPU image built only from public packages**

- `examples/tpu/grpo/Dockerfile` no longer uses the authenticated `torch-tpu` registry. `torch-tpu` 0.2.0 and `tpu-sync-torch` come from PyPI.
- vllm-torchtpu (now public) moves to `33ee547b` with vLLM v0.31.0, the first versions that support `torch-tpu` 0.2.0 natively. jax moves to 0.11.2, the vllm-torchtpu pin.
- The `setuptools-scm` pretend-version variable follows vllm-torchtpu's renamed `vllm-torchtpu-core` package.

**Review follow-ups (CodeRabbit comments on #8271 / #8280 / #8288)**

- Multi-host `torchrun` no longer silently falls back to loopback.
- The SFT README commands drop the explicit `DATA_PARALLEL_SHARD_SIZE`, and the README says that any explicit value times `TENSOR_PARALLEL_SIZE` must equal the trainer chip count.
- All three TPU scripts exit early unless `TENSOR_PARALLEL_SIZE` is a positive divisor of the trainer chip count.
- The SFT README documents the `TORCH_TPU_SLICEBUILDER_ADDRESSES` / `TORCH_TPU_TOPOLOGY` environment that `torchrun` needs on a plain TPU VM.

### Dependency

The public image uses `torch-tpu` 0.2.0, which makes the `torch.tpu` device functions internal. verl-project/verl-hardware-plugin#64 (merged) moves the plugin to `torch.accelerator`. `examples/tpu/grpo/README.md` now checks out plugin main `c76de674`, which includes #64 and #63. The previous pin `97e50f48` fails at startup with this image.

The examples retain their existing permissions and improve launch validation. However, applying the renamed deployment in an existing environment can leave the previous cluster running with bucket access. This is a conditional cleanup and ownership risk, not a demonstrated privilege escalation.

**Retained concerns**
- **Low · security · inferred:** The RayCluster is renamed from ray-tpu-v6e4-cluster to ray-tpu-v6e-cluster without a documented legacy-resource transition. In an existing namespace, applying the new manifest leaves the old cluster outside the new lifecycle while it can retain the shared identity and bucket access. Deleting the entire old manifest is not an isolated cleanup operation because it also declares ray-ksa, which the new cluster uses.
