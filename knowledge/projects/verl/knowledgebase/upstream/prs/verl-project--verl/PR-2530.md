![critical](https://www.gstatic.com/codereviewagent/critical.svg)

Executing commands with `shell=True` is a significant security risk, as it can lead to command injection vulnerabilities. The `full_command` string is constructed using f-strings that include user-provided arguments (e.g., `experiment_name`, `conda_env`). A malicious user could inject arbitrary shell commands through these arguments.

To fix this, you should avoid `shell=True`. Instead, construct the command as a list of arguments and pass it to `subprocess.run`. For complex shell operations like `eval` and `| tee`, consider either performing them in Python or using a dedicated wrapper script that accepts sanitized arguments.

The path to the conda executable is hardcoded (`/home/sam/miniconda3/bin/conda`). This makes the sbatch script template non-portable and will cause it to fail for other users or on different machine setups. This hardcoded path appears in multiple places (e.g., line 96 as well).

It's better to assume `conda` is in the user's `$PATH` or to make the conda path a template variable that can be substituted by the launcher script.

```suggestion
    bash -c "eval \"\$(conda shell.bash hook)\"; conda activate ${CONDA_ENV}; cd ${verl_workdir}; \
        ray start --head --node-ip-address=\"$head_node_ip\" --port=$port \
        --dashboard-port=8266 \
        --num-cpus \"${SLURM_CPUS_PER_TASK}\" --num-gpus \"${SLURM_GPUS_PER_NODE}\" --block" &
```

File: `scripts/submit_sbatch.sh` · line None

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

This script is highly non-portable and difficult to maintain due to numerous hardcoded values, including:

*   User-specific paths (e.g., `/home/sam/...`)
*   Fixed SLURM parameters (e.g., `--nodes=8`)
*   A long, hardcoded `python3 -m verl.trainer.main_ppo` command with many fixed hyperparameters.

This script's functionality seems to be superseded by the new `launch_math_rl.py` script, which provides a configurable way to launch jobs. Checking in such a specific, non-reusable script is not a good practice. Consider removing this file and using `launch_math_rl.py` instead. If this is intended as an example, it would be better to document an example invocation of `launch_math_rl.py` in a `README` file.
