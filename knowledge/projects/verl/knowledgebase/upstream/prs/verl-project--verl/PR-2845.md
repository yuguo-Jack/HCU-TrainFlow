# [fsdp, trainer] feat: Run vLLM-based Generative Reward Model with Multi-Workgroup Support

[Upstream PR](https://github.com/verl-project/verl/pull/2845) · state: open · merged: False

## Original PR description

Solve problem #1193 by multiple vllm instance available.

- The core enhancement is **decoupling the resource pool from the WorkerGroup**, allow roles to be assigned to separate WorkerGroups while sharing a single resource pool. Consequently, multiple vLLM rollout engines can be launched without partitioning GPU resources.
- This feature allows users to load a extra vllm instance to compute rewards. By loading custom `reward_preprocess` and `reward_postprocess` functions, users can define custom reward prompts or even integrate a reward function directly with the reward model.
- It is easy to support other rollout engine in reward model, and can be used as a foundation to develop new features like [critic-rl](https://github.com/HKUNLP/critic-rl/tree/main)

## Code Review

This pull request introduces a valuable feature by decoupling resource pools from worker groups, enabling multiple vLLM instances to run concurrently for tasks like reward modeling. The implementation is well-structured, with the new `SharedPoolRayPPOTrainer` and modifications to `RewardModelWorker` forming the core of this enhancement. I have one high-severity concern regarding a potential change in behavior for the critic's learning rate scheduler, which I've detailed in a specific comment. Addressing this will ensure the change is robust and predictable. Overall, this is a great contribution that enhances the framework's flexibility.
