# [fsdp, model] fix: run fused LM heads through FSDP2 hooks

[Upstream PR](https://github.com/verl-project/verl/pull/8096) · state: open · merged: False

## Original PR description

### What does this PR do?

Fixes #8091. With untied embeddings, FSDP2 shards `lm_head` independently, but fused forwards read its weight from the parent. This bypasses the head's unsharding, mixed precision, CPU offload and backward hooks. A two-GPU Qwen3 reproducer fails with mixed Tensor/DTensor operands (Torch), BF16/FP32 operands (Triton), or CPU weights under offload.

Run the fused projection through an FSDP-registered forward method on the existing head. The head keeps its own sharding group and ordinary logits `forward`; backend selection and label preparation remain unchanged. The dense, Qwen2-VL, Qwen3-VL, Qwen3.5 and GLM4V adapters share this entry point.

Related work: closed #7427 instead keeps the fused head in the root FSDP unit. Open #8004 adds an opt-in FP32 head and routes that branch through its head forward, while the default fused path still reads the weight directly. Open #5948 falls back to materialized logits for a sharded Qwen3-VL Torch head; this change retains fused computation and also fixes the default dense and other adapter paths. It does not implement #8090's Triton shape change or #7323's visual-call alignment.

No new user configuration or CLI is required. Existing `use_fused_kernels` configurations use the registered head entry point automatically.

### Design & Code Changes

Register one additional FSDP forward method lazily on independently sharded heads, using PyTorch's public registration API. Keep existing non-FSDP behavior and VLM dtype/DTensor handling inside the projection. Add CPU numerical coverage and the two-GPU regression matrix to the existing distributed test runner.
