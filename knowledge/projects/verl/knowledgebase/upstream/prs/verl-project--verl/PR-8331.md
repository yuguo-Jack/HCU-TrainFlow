# [perf, rollout] feat: fused Triton fast path for FP8_BLOCK weight export in the compressed-tensors quantizer

[Upstream PR](https://github.com/verl-project/verl/pull/8331) · state: closed · merged: False

## Original PR description

### What does this PR do?

With FP8_BLOCK rollout (and FP8 QAT) on the Megatron engine, every weight sync quantizes the exported HF weights through `verl/utils/qat/compressed_tensors.py::_compress_weight`, which goes through compressed-tensors' generic per-tensor path (`calculate_qparams` -> `BaseCompressor.compress` -> `quantize` -> `_process_block`). That path is pure eager torch in compressed-tensors 0.17.0 (the version vLLM pins): per tensor it does ~4 full passes (block amin/amax, `x / scale`, `clamp`, `.to(fp8)`), a transpose-back copy, and ~10 tiny kernels, all launched one by one from Python. For a fine-grained MoE this is launch-bound: Qwen3-30B-A3B exports 18,432 expert tensors of 768x2048 per step.

Measured on 8x H20-3e, Qwen3-30B-A3B-Base, DAPO 2K/8K, 64x8 (`timing_s/update_weights` per step): BF16 4.4 s, FP8_BLOCK rollout / FP8 QAT / FP8 E2E 14.6-15.2 s. The extra ~10 s cancels the FP8 generation speed-up at ~1K-token responses (gen 42 s vs 52 s), so FP8 rollout is net neutral per step in that regime.

Micro-benchmark on one H20 (18,432 synthetic expert tensors, FP8 block 128x128):

| path | total | per tensor |
|---|---|---|
| compressed-tensors eager `_compress_weight` | 5.12 s | 0.278 ms |
| `verl.utils.kernel.fp8_kernel.scaled_fp8_blockwise` (Triton), per tensor | 0.58 s | 0.032 ms |
| same kernel on one stacked `[128*M, N]` tensor per layer/projection (96 launches) | 0.03 s | - |

verl already ships this fused Triton kernel for the FSDP refit path (`verl/utils/fp8_utils.py`); it computes block amax -> fp32 scale -> clamp -> cast in one launch and returns `(fp8 [M, N], scale [ceil(M/128), ceil(N/128)])` with the same "multiply to dequantize" semantics as compressed-tensors' `weight` / `weight_scale`. This PR uses it as a fast path in `_compress_weight` for the FP8 block scheme, so both `CompressedTensorsWeightQuantizer` (new API) and `Fp8ConfigWeightQuantizer` (legacy) benefit, and quantizes packed 3D expert tensors (`experts.gate_up_proj` / `experts.down_proj`, Qwen3.5-style checkpoints) with one launch per layer. Everything else (other schemes, CPU tensors, Triton unavailable, `VERL_FP8_EXPORT_FAST_PATH=0`) keeps the eager path.

Long term this belongs upstream: compressed-tensors is adding Triton kernels (vllm-project/compressed-tensors#766, #804, #812, #875), and we opened vllm-project/compressed-tensors#983 for a fused `calculate_qparams` + `quantize` path and a batched entry point. Until that lands and vLLM moves its `compressed-tensors==0.17.0` pin, verl needs the local fast path.

### Test

Environment: verl main + this patch, compressed-tensors 0.17.0, vLLM 0.29, 8x H20-3e, Qwen3-30B-A3B-Base.

1. Unit test `tests/utils/test_fp8_block_export_fast_path.py` (needs CUDA + Triton, 11 cases, all pass): for shapes `(768, 2048)`, `(2048, 768)`, `(2048, 2048)`, `(1000, 2048)`, `(768, 2000)`, `(64, 64)` the fast path and the eager path (`_compress_weight_eager`) return the same keys, dtypes and shapes; `weight_scale` is bit-identical; the fp8 `weight` differs in at most 1.3e-6 of the elements (0 to 4 elements per 768x2048 tensor) by exactly one fp8 ulp, because the Triton kernel multiplies by the reciprocal scale while compressed-tensors divides. Packed `[E, 2I, H]` / `[E, H, I]` expert tensors give the same per-expert results as the per-expert path, and fall back to it when the per-expert row count is not a multiple of the block rows. `VERL_FP8_EXPORT_FAST_PATH=0`, CPU tensors, non-float8 inputs, 1-D tensors and the MXFP8 scheme all take the eager path.
2. Single-step mismatch, `scripts/rollout_logprob_diff.py` (8 prompts x 4, EP=8, rollout TP=2, R3), FP8_BLOCK rollout: `k3_kl` 0.00361 before / 0.00303 after; the unseeded probe's BF16 control moved from 0.00083 to 0.00069 in the same runs, so this is sampling noise, not a change.

The same drop shows in the FP8 QAT runs (7.0-9.1 s).

### API and Usage Example

No API change. The fast path is used automatically for `rollout.quantization.linear/moe=FP8_BLOCK` (and the legacy `fp8` config) on CUDA when Triton is available; `VERL_FP8_EXPORT_FAST_PATH=0` forces the eager reference path (`VERL_DISABLE_TRITON_FP8=1` additionally switches the kernel wrapper to its torch fallback).

### Design & Code Changes

- `verl/utils/qat/compressed_tensors.py`:
  - `_fp8_block_fast_path_applies(weight, scheme)`: FP8 (`QuantizationType.FLOAT`, 8 bits), symmetric, `BLOCK` strategy with a 2-D `block_structure`, 2-D high-precision CUDA tensor, `scale_dtype` unset or fp32, env var not `0`, Triton available.
  - `_compress_weight` returns `_compress_weight_fp8_block` (one `scaled_fp8_blockwise` launch, scale cast to fp32) when the fast path applies and no `global_scale` is involved; otherwise `_compress_weight_eager`, which is the previous function body unchanged.
  - `_compress_packed_experts_fp8_block` + `_packed_experts_fp8_block_applies`: for a packed `[E, R, C]` tensor whose `R` (and `R/2` for `gate_up_proj`) is a multiple of the block rows, quantize `tensor.reshape(E*R, C)` once and yield per-expert `weight` / `weight_scale` views with the same names as `_unpack_experts`; `CompressedTensorsWeightQuantizer._compress_packed_experts` uses it before the per-expert loop (input global scales are still emitted per module).
- `verl/utils/kernel/fp8_kernel.py`: no change (reuse `scaled_fp8_blockwise`, Hopper+ only; the eager path remains the fallback elsewhere).
- `docs/low_precision/fp8.md`: one paragraph on the refit fast path and the env var.
