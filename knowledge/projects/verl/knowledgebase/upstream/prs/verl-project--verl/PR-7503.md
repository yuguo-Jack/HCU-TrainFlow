# [misc] fix: clone replicated FSDP shard tensors to avoid aliased storage in merged checkpoints (#6259)

[Upstream PR](https://github.com/verl-project/verl/pull/7503) · state: open · merged: False

## Original PR description

### What does this PR do?

Fixes #6259 (merging a 64-GPU FSDP GRPO checkpoint into HF format produced `.safetensors` shards with keys appearing "duplicated" — not reproducible at 32 GPUs).

**Update (see the review thread below for the full discussion with @UgaTheDev):** this PR originally also added a broad `assert_no_aliased_state_dict_tensors()` guard at the `save_pretrained` choke point, with an error message claiming `save_pretrained` "silently drops" tensors that share storage. Review established that claim is inaccurate for the common case (`transformers` clones apart two keys that are *disjoint* views of shared storage; it already raises loudly, upstream, if two keys are the exact same tensor object and not declared tied) and that the guard was stricter than transformers itself in an edge case. That guard and its tests have been **removed**. This PR is now scoped to just the one change that's correct on its own, narrower terms:

`FSDPModelMerger._merge_by_placement()`'s `Replicate` branch returned `tensors[0]` — the raw `_local_tensor` loaded straight from the rank-0 checkpoint file — **unmodified, with no clone**. For parameters FSDP could not shard further (more likely to occur the larger the FSDP world size is), that local tensor can still be a *view* sharing storage with some other tensor materialized from the same checkpoint file. Returning it as-is lets that storage aliasing leak into the merged `state_dict`, so two *unrelated* keys can end up pointing at the same underlying storage — a real hazard independent of exactly how any given `transformers` version happens to handle it at write time, and one that also keeps a (potentially large) shared source buffer alive for the rest of the merge.

I'm not able to independently confirm this aliasing is provably *the* root cause of #6259's exact reported symptom (duplicate keys across shards, specifically) without the reporter's checkpoint — flagging that honestly rather than restating the original PR's confidence. The clone is worth landing regardless: it removes a real storage-sharing hazard between unrelated state_dict keys and reduces peak host memory during merge.

- UgaTheDev · comment · 2026-08-27T06:51:53Z · [source](https://github.com/verl-project/verl/pull/7503#issuecomment-5435423519)

Thanks for digging into #6259 — the aliasing mechanism you describe in the
`_merge_by_placement` comment is real and well explained. FSDP2 packs a param group
into one flat allocation, `torch.save` preserves storage sharing within a file, and
`torch.load` restores it, so the rank-0 `_local_tensor` of a `Replicate()` param
genuinely can come back as a view into a buffer that other params also view. That
`return tensors[0]` propagates into the merged state_dict is a fair thing to fix, and
the 32-vs-64-GPU dependence in the report is consistent with which params end up
replicated rather than sharded.

I ran the branch locally (torch 2.13 / transformers 5.14, plus a read of transformers
4.57.1 source since that is the version in the issue report). A few things came back
that I think are worth resolving before this lands. Happy to be wrong on any of them.

## 1. `save_pretrained` does not silently drop disjoint views

This is my main concern, because it is the premise of the guard and of the error
message. The scenario the tests construct — two distinct keys as *non-overlapping*
views of one storage (`shared_buffer[0:4]` / `shared_buffer[4:8]`) — is handled
explicitly and safely by transformers, on both the reporter's version and current
main.

In 4.57.1, `modeling_utils.py` (the `_find_disjoint` path, called from
`save_pretrained`):

```python
shared_names, disjoint_names = _find_disjoint(shared_ptrs.values(), state_dict)
# Those are actually tensor sharing but disjoint from each other, we can safely clone them
# Reloaded won't have the same property, but it shouldn't matter in any meaningful way.
for name in disjoint_names:
    state_dict[name] = state_dict[name].clone()
```

So disjoint views are cloned, not deduped. And in the fully-identical case (same
tensor under two keys), 4.57.1 deletes a key *only* when it matches the model's
declared `_tied_weights_keys`; anything else reaches
`raise RuntimeError("The weights trying to be saved contained shared tensors ...")`.

I confirmed the same empirically on transformers 5.14 with a small Qwen2 model, by
packing `gate_proj.weight` and `up_proj.weight` into one buffer as disjoint views and
calling `save_pretrained(state_dict=...)`:

```
[DISJOINT views of one storage]  keys written=15/15  missing=[]  wrong_values=[]
[IDENTICAL alias (same tensor)]  RuntimeError: The weights trying to be saved contained
    shared tensors [{'model.layers.0.mlp.gate_proj.weight',
    'model.layers.0.mlp.up_proj.weight'}] which are not properly defined.
```

Nothing was dropped and no values were wrong in the disjoint case; the identical case
already fails loudly upstream. I could not find a version where the tested condition
produces silent key loss.

Two consequences:

- The error message ("`save_pretrained` silently drops all but one tensor per shared
  storage group, so this would produce safetensors shards with missing/duplicated
  weights") tells a future reader something that isn't true of the disjoint case, which
  is the case most likely to trip the guard. Someone hitting this will spend a while
  looking for corruption that isn't there.
- The guard is stricter than transformers: it converts a merge that transformers would
  complete correctly into a hard `RuntimeError`. Since the guard sits at the shared
  choke point, that risk applies to every backend and to any future producer of a
  state_dict, not just the FSDP path this PR fixes.

It would also help to reconcile the root-cause story with the reported symptom. The
issue reports *"不同safetensors包含同一个key"* — the same key appearing in more than one
shard file — and the pasted output is from the reporter's own dedup script ("剔除 N 个
重复Key"). Keys duplicated *across* shards and keys *dropped* are different failures.
If you have a reproduction that ties the aliasing to the reporter's exact output, that
would settle it; if not, it may be worth saying in the PR body that the aliasing is a
plausible-but-unconfirmed cause.

## 2. Tied weights: no false positive on the canonical case

I checked this specifically, since intentionally-aliased input/output embeddings are
the obvious way a guard like this goes wrong. Good news: it holds up, because you put
the call *after* `drop_tied_target_keys`, which pops the alias key. With a real
`Qwen2Config(tie_word_embeddings=True)` model built the same way
`save_hf_model_and_tokenizer` builds it (`init_empty_weights` → `to_empty("cpu")`):

```
[tie=True, embed/lm_head independent tensors]  guard PASSED  (keys after drop: ['model.embed_tokens.weight'])
[tie=True, embed/lm_head same tensor object]   guard PASSED  (keys after drop: ['model.embed_tokens.weight'])
```

So ordinary tied embeddings are safe. Two narrower cases do fire, both arguably
correctly, but worth a line in the docstring so the next person doesn't have to
rediscover them:

- `tie_word_embeddings=False` in the config while the state_dict aliases the two keys
  anyway. `drop_tied_target_keys` returns early on the flag, so the guard raises. This
  is probably the right outcome, but the message should point at the config mismatch.
- The `drop_tied_target_keys` "canonical name absent → promote the alias" branch. When
  the canonical key is missing, nothing is dropped, so an alias pair survives into the
  guard and raises. Also probably correct, but it means the guard's behavior depends on
  a non-obvious branch in a different module.

The cause is the fixture's `monkeypatch.delitem(sys.modules, "torch.distributed.tensor")`.
The first test's `monkeypatch` teardown restores the module into `sys.modules`, the

initialization, which asserts on double registration of the DTensor dispatch impl.

The fixture comment gives the reason for that `delitem` as:

> torch 1.12 (used in some CI/dev environments) has neither `torch.distributed.tensor`
> nor `torch.distributed._tensor`.

I don't think that applies here — `pyproject.toml` pins `torch==2.11.0` in every extra
and declares a floor of `torch>=2.6.0`, so torch 1.12 is not a supported target. The
`torch.distributed._tensor` fallback is being forced for an environment the project
doesn't support, and the forcing is what breaks the test. Note that in the *first*
test the real `torch.distributed.tensor` import succeeds, so `_FakeDTensor`,
`_FakePlacement`, `_FakeShard` and `_FakeReplicate` are never bound by the production
module at all — it uses the real classes, and `_FakeReplicate()` only works as an
argument by duck typing.

## 6. Smaller things

- `tensor.storage()` raises `UserWarning: TypedStorage is deprecated` on every call, so
  a 32B merge emits one warning per key. `tensor.untyped_storage().data_ptr()` is the
  modern form and is also what transformers' own `id_tensor_storage` uses, so it
  matches the semantics you are guarding against. Same for the two `.storage()` calls
  in the tests.
- Once `tensors[0].clone()` is in, the FSDP path can no longer produce an aliased merged
  state_dict at all: `clone()` allocates fresh storage and the shard path goes through
  `torch.cat`. The megatron path still assigns loaded tensors through in places
  (`state_dict[hf_name] = split_tensor[0]` in `megatron_model_merger.py`), so the guard
  isn't dead code there — but it does mean the one-line clone is what actually fixes
  #6259. It might be worth landing the clone plus a short test for it on its own, so the
  fix isn't held up by the questions above.
- The clone has a nice second benefit the PR doesn't mention, which might be a better
  motivation than corruption: returning a small view of a large flat rank-0 buffer keeps
  that whole buffer alive for the rest of the merge. Cloning lets it be freed. For a
  32B model that is a real peak-memory difference, and it's an argument that doesn't
  depend on `save_pretrained`'s dedup behavior at all.

Thanks again for taking this on — the diagnosis of the replicate path is the valuable
part here and I'd like to see it land.
