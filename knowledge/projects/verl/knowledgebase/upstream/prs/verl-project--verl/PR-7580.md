# [rollout, trainer, training_utils, doc] feat: support weighted multi-output agent-loop trajectories

[Upstream PR](https://github.com/verl-project/verl/pull/7580) · state: open · merged: False

## Original PR description

### What does this PR do?

Add first-class support for **weighted multi-output agent-loop trajectories**.

An agent loop may return an ordered `list[AgentLoopOutput]` for one logical trajectory — e.g. a long multi-turn episode split into context-bounded training segments, or a Gateway session that materialises several branches (verl-project/uni-agent#185). Today each output becomes an independent training row, so under `seq-mean-token-mean` a trajectory's share of the policy gradient is proportional to how many rows it produced. Segment count becomes an implicit, unintended optimisation weight.

This PR lets each output carry an explicit per-row `loss_weight` so the agent loop can choose what a multi-row trajectory should count for, and makes the trainer apply that weight correctly. **Scope, stated precisely:** the V1 TransferQueue agent loop, whose session-aware advantage propagation (final row per `{uid}_{session}` computed, then broadcast) is GRPO-only upstream and is not changed here; the objective that is fully verified is *session-equal* weighting (`1/N`, every logical trajectory counts once — what uni-agent#185 asks for) under `seq-mean-token-mean`. A *partition-preserving* weight (`T_j / mean(T)`, reproduce the unsplit trajectory's loss) is documented and unit-tested; it has not been run live, but on the same sixdatasets its advantage vector has cosine 0.94–0.96 with the session-equal one (table below), so the live evidence carries over.

1. **`loss_weight` on `AgentLoopOutput`**, stored per row by the V1 TransferQueue adapter, applied to the policy-gradient term; padding rows are zeroed; per-step metrics distinguish stored rows / logical trajectories / optimizer updates.
2. **Global renormalisation and every-term weighting.** Every `loss_agg_mode` divides by an *unweighted* denominator, so raw `1/N` shrinks the whole loss by `mean(1/N)` over the batch and that factor drifts step to step. `normalize_loss_weight_global` rescales weights to `mean_rows = 1.0` once over the global batch in the trainer (ratios preserved, packing-invariant). This conserves loss magnitude **exactly for row-normalised aggregation**(`seq-mean-token-mean`, the only mode where a per-row weight is needed to make splitting neutral); under `token-mean` the effective scale is the token-weighted mean of `w`, which is 1 only if `w` is uncorrelated with row length — documented and pinned by a test rather than claimed away. The weight is also broadcast onto the entropy and KL terms so a down-weighted row does not keep full KL/entropy pressure against a reduced policy gradient.Adds `training/trajectory/score_mean` (one value per logical session) next to the row-weighted `critic/score/*`.
3. **`scripts/analyze_multi_output_loss_weight.py`** — reads standard `trainer.rollout_data_dir` dumps and computes both objectives from the same rollouts, so anyone can measure the effect on their own data without training twice.

Single-output agent loops are unaffected (`loss_weight=None → 1.0`, bit-identical). Multi-output is a V1 TransferQueue feature; the legacy batch adapter keeps its single-output contract and raises on a list.

- **The session-equal invariant holds exactly.** Per-trajectory influence is `N×` unweighted and `1.0×` weighted in every run and every N bucket. In run E, N=10 trajectories are 13% of trajectories but 34% of the gradient, and 76% of them are failures.

- **Cost:** Kish ESS 52–60% of rows — the intended price of not counting duplicated segments as independent samples.

**End-to-end soak.** Changes 1+2 ran for 100 steps (run E: 71.7k weighted rows, 32×H100) with `training/trajectory/loss_weight/mean` = 1.000 every step and min/max = 0.37 / 3.66. Held-out task success rose from 44.6% to 53.7% (paired bootstrap 95% CI [+1.4, +17.2] pp), monotone across five checkpoints, no entropy collapse. This demonstrates stability at production scale; it is *not* a claim that weighting caused the gain.

**Live single-variable A/B (paired fork, 20 steps).** Fork of run E at step 60 — same checkpoint, optimizer and sampler state (identical prompts per step), same data — with `loss_weight=None`; the OFF arm reported `loss_weight/min = max = 1.0` every step. Pre-registered prediction: the unweighted arm drifts away from long episodes (lower mean length, lower max-length share, higher terminate-but-fail; α=0.01, ~1000 episodes per arm). **Result: 0/3 in both the full and the late (last 10 steps) window** — no behavioural divergence was detectable in 20 steps; optimizer statistics (clip fraction, approx-KL, KL loss, grad-norm) stayed within run-to-run noise of the ON arm, and task success was equal (72.0 % vs 71.5 %). Two secondary observations: the OFF arm's row-weighted success (the quantity its objective actually optimises) sat 15 pp below its trajectory-level success, reproducing the offline bias live; and OFF-arm entropy ran +0.02 higher (paired on step, p<1e-8) — consistent with commit 2 also weighting the entropy bonus, but not a pre-registered metric. Read: at this point of training the weighting is benign, not load-bearing; the case for the PR rests on the exact-influence invariant and the sign-flipping reward bias above, not on a short-horizon effect. ### API and Usage Example

```python
# AgentLoopBase.run(): one logical episode -> N ordered training segments
segments = self._seal_segments(...)
return [
    AgentLoopOutput(
        prompt_ids=seg.prompt_ids,
        response_ids=seg.response_ids,
        response_mask=seg.response_mask,
        # seq-mean-token-mean normalises by rows, so choose the objective explicitly:
        #   session-equal        -> 1.0 / len(segments)          (every trajectory counts once)
        #   partition-preserving -> seg.n_tokens / mean_tokens   (== the unsplit trajectory's loss)
        loss_weight=1.0 / len(segments),
    )
    for seg in segments
]
```

Under `token-mean` leave `loss_weight=None`: splitting is already partition-preserving there (see the two tables in `docs/advance/agent_loop.rst`).The adapter warns once if a multi-output loop returns no weights. `1/N` is *not* partition-preserving when segments have unequal length (1000 tokens cut 100/900 with per-token loss 0.2/0.8: unsplit 0.74, `1/N` 0.50, `T_j/mean(T)` 0.74 — `test_one_over_n_is_session_equal_not_partition_preserving`).

Measure the effect on an existing run:

New metrics: `training/trajectory/{stored_rows, expanded_rows, logical_sessions, segments_per_session/mean, score_mean, loss_weight/{mean,min,max}}`, `training/actor/{mini_batches_per_epoch, optimizer_updates}`. Note that the existing `critic/score/*`, `response_length/*` etc. remain **row-weighted** (an N-row trajectory counts N times); `training/trajectory/score_mean` is the trajectory-level counterpart.

### Design & Code Changes

- **Why the adapter does not invent `1/N`.** The neutral weight depends on `actor.loss_agg_mode`, which the rollout worker does not own; a `1/N` default under `token-mean` would silently shrink every split trajectory. The adapter stays neutral, warns once, and lets the agent loop choose.
- **Why renormalise in the trainer, not the loss function.** The loss function sees a micro-batch; a micro-batch of same-weight rows would rescale to 1.0 and erase the reweighting. Normalising once over the global batch, right after `validate_loss_weights`, preserves every `w_i/w_j` and is packing-invariant (parametrized test).
- **Why every term, not only the policy gradient.** If only advantages were weighted, a trajectory split into `N` segments would have its policy gradient divided by `N` while its KL penalty and entropy bonus still counted `N` full rows — the deeper the trajectory, the harder it is held to the reference policy. Broadcasting the weight onto the per-token entropy and KL matrices is exact for every `loss_agg_mode` (all are linear in `loss_mat`). One observable consequence, seen in the live A/B below: with weighting on, down-weighted long trajectories exert less entropy pressure, so entropy runs slightly lower (−0.02 here); worth knowing when tuning `entropy_coeff`.
- **`loss_weight` is a relative weight.** Because of the mean-1.0 rescaling it expresses how much of the batch a sample accounts for, not an absolute scale; it is not a channel for importance ratios. The doc says so explicitly.
- **What is *not* in scope (and why).** (a) Session-aware advantage propagation is GRPO-only in upstream `compute_advantage_multi_output` (other estimators are delegated to per-row `compute_advantage` unchanged); this PR adds weighting on top and does not widen that. Extending session semanticsand critic value-loss weighting to GAE/PPO is a separate change. (b) The agent loop still hard-codes the weight while `loss_agg_mode` lives in the trainer config, so changing the mode later silently changes the objective; the adapter warns, but deriving the weight in the trainer from a declared`trajectory_weighting.mode` is the cleaner API and is left as a follow-up. (c) Only `score_mean` is added at trajectory level; the rest of `compute_data_metrics` stays row-weighted.
- **Mini-batch accounting stays row-based.** `ppo_mini_batch_size` counts stored rows; the variable expansion factor cannot be a static divisibility constraint. `training/actor/optimizer_updates` makes the cost visible.
- **Files:** `verl/utils/trajectory.py` (new: validate / apply / normalise), `verl/experimental/agent_loop/agent_loop.py`, `verl/trainer/ppo/v1/agent_loop_tq.py`, `verl/trainer/ppo/v1/trainer_base.py`, `verl/trainer/ppo/v1/utils.py`, `verl/workers/utils/losses.py`, `verl/trainer/distillation/losses.py`, `docs/advance/agent_loop.rst`, `scripts/analyze_multi_output_loss_weight.py`, tests.

## Reading the result

The pre-registered behavioural prediction did **not** materialise: 0/3 in both windows. A few things are worth stating plainly so the number is notover- or under-read.

1. **What the null means.** Twenty steps from a checkpoint that had already trained 60 steps *with* weighting, where max-length episodes are ~13 % of trajectories, was not enough for the `N×` over-weighting of long failures to move episode length, max-length share or terminate-but-fail rate beyond noise (per-step n≈50, pooled n≈1000; the tests would detect ~2 steps / ~5 pp). Optimizer statistics of the two arms overlapped throughout (clip fraction 0.28–0.39 both, approx-KL 3–8e-4 both, KL loss 0.093 vs 0.094 at step 66), and trajectory-level success was equal (72.0 % vs 71.5 %, late window 72.9 % vs 68.9 %, p=0.16). So: in this regime the weighting is **benign, not load-bearing over a short horizon**.

2. **What the run did confirm live.** The OFF arm's *row-weighted* success — the quantity an unweighted objective actually optimises — was 56.3 % against a trajectory-level 71.5 % (late window 52.9 % vs 68.9 %). That 15 pp gap is the same bias the offline analysis measures on six stored datasets (6–14 pp, sign-flipping between runs). Weighting removes it exactly; the question this A/B asked was whether removing it changes behaviour within 20 steps, and the answer is "not detectably".

3. **Entropy** ran +0.02 higher in the OFF arm, paired on step index, p<1e-8 in both windows — the only significant difference, and in the *opposite* direction to the (diagnostic-only) prediction. The most likely mechanism is commit 2: with weighting on, the entropy bonus is also weighted, so long trajectories contribute less entropy pressure per token. This is a real, small side-effect of the design choice "weight every loss term the sameway" and is worth knowing when tuning `entropy_coeff`.

4. **Null calibration** on two adjacent windows of the ON run alone (steps 41–60 vs 61–80) also gives 0/3 with the same entropy drift (+0.02, sinceentropy rises within the run), so the tests are not over-sensitive and the entropy signal here is at the edge of what within-run drift produces.

5. **Which objective did the A/B test?** The ON arm used `1/N` (session-equal). It did not run the partition-preserving `T_j/mean(T)` weight. On the same six datasets the two weightings' advantage vectors have cosine 0.94–0.96 (vs 0.69–0.71 against unweighted), so the null here applies to both;a separate live arm would be unlikely to separate them.

**Bottom line for review.** The PR's justification is the offline invariant (per-trajectory influence exactly `1.0×` instead of `N×`; row-weighted reward bias 6–14 pp with sign flips; `mean(1/N)` loss-scale drift fixed by global normalisation), plus a 100-step production soak showing stability.The live A/B adds: no short-horizon harm, no short-horizon gain, one small measurable side-effect on entropy. I would rather report that than a cherry-picked window. Scripts to reproduce every number: `scripts/analyze_multi_output_loss_weight.py` (offline, any `rollout_data_dir`) and the paired-fork report script referenced in the description.
