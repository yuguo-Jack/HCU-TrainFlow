### What does this PR do?

Add `verl.runtime`, a backend-neutral API for worker placement, invocation, and object storage. Ray and its callers move to this API, and Monarch with TorchStore becomes an opt-in backend; Ray remains the default.

### API and Usage Example

```bash
python -m verl.trainer.main_ppo --config-name ppo_monarch_neoproto \
  runtime.monarch.job_mode=current
```

The recipe selects `runtime.backend=monarch` and configures the store under `runtime.monarch.object_store`. `job_mode=current` (the default) loads the job started by `monarch apply`. `strategy=host` creates one CPU volume process per host; `strategy=local_rank` creates one per worker process.

### Design & Code Changes

#### Runtime ownership

`Runtime` configures the backend, selects resource pools, creates worker groups, and coordinates cleanup; a process has at most one live Runtime. The root owns backend resources. Workers attach through an `AttachSpec` carrying the Runtime identity, backend configuration, the group's resource scope, and the ObjectStore client configuration; groups on the controller pool also receive the compiled topology and device pools, while other groups receive only their parent pool. Nested callers reach this context through `current_runtime()`.

```python
# Controller: the root Runtime owns backend resources.
with Runtime.from_config({"backend": "ray", "ray": {}}) as runtime:
    pool = runtime.create_resource_pool(nnodes=1, processes_per_node=8, device_type="gpu")
    actor_wg = runtime.create_worker_group(ClassWithInitArgs(ActorWorker, config), on=pool)

# Inside an ActorWorker method: the attached Runtime creates nested groups on its own host.
runtime = current_runtime()
host_pool = runtime.current_host_resource_pool()
```

Runtime tracks groups without keeping them alive. Local rank and fused-role views keep their parent group alive; remote projections do not. Releasing the last local reference allows backend workers to be reclaimed. `Runtime.close()` closes live groups; failed cleanup can be retried.

```python
rank_zero = actor_wg.rank(0)   # local view: keeps the workers alive
handle = actor_wg.remote()     # serializable projection: does not
del actor_wg                   # workers keep running; rank_zero still works
del rank_zero                  # last local reference: the workers are reclaimed
```

The private `RuntimeBackend` protocol supplies resource discovery, placement resolution, group construction, object-store startup, and backend cleanup. Runtime controls orchestration and ownership; the backend handles scheduling and execution.

#### Worker and invocation contracts

- `Worker` is the user implementation running in one process. `register` declares how a method dispatches arguments, selects ranks, and collects results, independent of the execution backend.
- `ClassWithInitArgs` describes a Worker constructor without creating it in the controller. `WorkerContainer` constructs the Worker in its execution context, dispatches calls, and owns its close operation.
- `WorkerGroup` owns a set of ranked workers; a single actor is a group with `world_size=1`. Rank selections and `RemoteWorkerGroup` projections can invoke methods but do not own the processes.
- `RemoteCall` is an asynchronous result with a submit-time deadline. `result()` and `await` observe the same outcome; `RemoteCall.wait()` and `RemoteCall.gather()` combine several calls into a new `RemoteCall`. An observation timeout does not cancel the remote operation; a later observation can still return the result if the operation has completed.
- Fused groups place several named Worker roles in each process; role views keep their method contracts, and the owning root closes the shared processes once. Upstream dependencies are resolved before the downstream dispatch, within the caller's deadline.

```python
first = actor_wg.save_checkpoint(path_a, timeout=300)    # registered with blocking=False
second = actor_wg.save_checkpoint(path_b, timeout=300)
done, pending = RemoteCall.wait([first, second], count=1).result()
results = RemoteCall.gather([first, second]).result()  # in input order

roles = runtime.create_worker_group({"actor": ActorWorker, "ref": RefWorker}, on=pool)
roles["ref"].compute_ref_log_prob(batch)                # both roles share each process
```

#### Placement and object storage

`ResourcePool` is an ordered, reusable placement of ranks: node count, processes per node, and device type. Slices are non-owning views that keep the placement coordinates and Runtime scope. `Topology` expresses `Cluster -> DevicePool -> Model`; Runtime compiles model selections into pools that backends can allocate.

```python
pool = runtime.create_resource_pool(nnodes=2, processes_per_node=8, device_type="gpu")
pool.slice(slice(0, 8))    # node 0
pool.slice(slice(8, 12))   # four processes on node 1
pool.slice(slice(4, 12))   # ValueError: crosses a node boundary
```

`ObjectStore` is the data boundary: `put`, `get`, `delete`, their batch forms, and `close`. References are opaque to the neutral layer.

```python
from verl.runtime import delete, get, put

ref = put("advantages", tensor)  # ObjectRef on Ray, TorchStoreReference(store_name, key) on Monarch
value = get(ref)
delete(ref)                      # releases this reference
```

#### Ray backend

`RayRuntimeBackend` implements the private backend protocol. It derives `RayResourcePool` views, resolves topology into Ray placement, creates worker groups, and installs the process-global `RayObjectStore`. Resource views retain node and device affinity; only the pool that created a placement group removes it, and views never do.

`RayWorkerGroup` owns Ray actors and adapts their methods to the neutral invocation facade. `RayClassWithInitArgs.from_class_init` builds a Runtime-bound actor that attaches the child Runtime and then constructs the user Worker through `WorkerContainer`.

`RayRemoteCall` observes singleton ObjectRefs directly, collects batched results in rank order, and implements the shared result, deadline, error, and aggregation API. `RayObjectStore` returns native ObjectRefs from the `verl.runtime` storage functions; its `delete()` is a no-op, so Ray's distributed reference counting decides object lifetime.

The call path is:

```text
trainer -> Runtime.create_worker_group -> RayRuntimeBackend
        -> Runtime-bound Ray actor -> WorkerContainer -> user Worker

WorkerGroup method -> shared dispatch -> Ray RPC -> shared collection
```

#### Caller migration

PPO and SFT create the Runtime at startup and request resource pools and worker groups from it. Rollout replicas and servers, checkpoint helpers, and agent/reward/teacher integrations use the same construction and invocation contracts. Nested workers use the attached Runtime context instead of creating another root.

Protocol futures carry `RemoteCall` objects instead of raw ObjectRefs. NeoProto resolves storage from the active Runtime, through Runtime's object-store functions on Ray; outside a Runtime it uses inline values unless a storage engine is configured explicitly.

When a Ray group is garbage-collected, its actors are killed without waiting for worker shutdown RPCs; explicitly detached actors survive.

Shared dispatch, collection, resource interfaces, and lifecycle code remain in the base modules. Ray-specific construction, placement, RPC, and compatibility helpers live under `verl.single_controller.ray`.

Ray tests live under `tests/single_controller/ray`: CPU examples initialize the Runtime, construct wrapped Workers, and release their groups; NeoProto dispatch tests use the Runtime-owned store; shared fixtures use canonical imports and select the Ray backend.

#### Monarch backend

`MonarchCluster` manages cluster resources: it uses an externally allocated job or owns a ProcessJob, exposes named HostMeshes, and creates ProcMeshes for worker groups. Cleanup releases only the resources this Runtime owns.

`MonarchResourcePool` maps the neutral rank layout to a HostMesh and its local process/device coordinates. `MonarchWorkerGroup` owns the ProcMesh and ActorMesh for its workers; rank and role projections remain non-owning views. `MonarchRemoteCall` adapts native Futures to the same observation, deadline, aggregation, and error semantics as Ray.

Workers receive an `AttachSpec`, bind their process/device environment, attach the Runtime context, and construct the user Worker through `WorkerContainer`.

When a Monarch group is garbage-collected, native mesh termination starts without waiting for worker shutdown RPCs; Runtime waits for it to finish before releasing backend dependencies.

#### TorchStore ownership and clients

`TorchStoreBackend` owns one global named store and its CPU volume ProcMesh, with one volume process per host (`host`) or per worker process (`local_rank`). `client_config` carries the store identity into controller and worker Runtime contexts.

`TorchStoreObjectStore` implements the synchronous ObjectStore interface over TorchStore's asynchronous client. `TorchStoreReference(store_name, key)` is self-addressing: a reader can resolve a producer's reference even when its local client writes to another store. Native batches group requests by source store, deduplicate keys, and return values in the original request order.

On close, the root Runtime stops its worker groups, closes its controller client, and then closes the global store and volume mesh. A partial failure keeps the unfinished phase, so a retry does not repeat completed steps.

#### NeoProto integration

`TorchStorageEngine` maps NeoProto refs to TorchStore references and applies logical slice and field operations on read. Runtime and storage configuration choose the backend, so PPO needs no Monarch-specific trainer. For ref-table dispatch on TorchStore, each consumer receives its own published copy and releases it independently.

Temporary SDK adaptations live in `verl.single_controller.monarch.patches`: bootstrap/codec handling and TorchStore wire-state overrides. Each module states its purpose and the upstream change that allows its removal.

The `monarch` extra pins Monarch and TorchStore to git commit SHAs. TorchStore still declares `torchmonarch==0.4.1`, so standard dependency resolution reports a conflict with the pinned Monarch commit; validation used Monarch and TorchStore wheels built from source. The backend also adds the `ppo_monarch_neoproto` recipe and portable correctness/equivalence entry points. Tests under `tests/single_controller/monarch` cover configuration, storage boundaries and native worker lifecycles.

#### Validation entry point

`run_runtime_matrix_1x8.sh --mode correctness|performance|all` runs and reports the 1x8 cases; 2x8 was run separately. Both modes compare baseline Ray, Runtime Ray, and Runtime Monarch on NeoProto with the configurations above.
