# [fsdp] fix: fused-kernel gradient tracking bug.

[Upstream PR](https://github.com/verl-project/verl/pull/6913) · state: closed · merged: True

## Original PR description

### What does this PR do?

> Add **concise** overview of what this PR aims to achieve or accomplish. Reference related GitHub issues and PRs that help with the review.

Currently using use_liger and use_fused_kernel flags create silently corrupted result. The issue is that the .flatten(0,1) inside the fused kernels autograd forward body flips the  requires_grad flag as gradients are not tracked by default within the autograd Functions. In the backward pass, the hidden_states requires_grad is false and that returns None as the gradients. This silently breaks the backpropagation and the reward does not improve.

This PR uses the original requires_grad flag from the hidden_states without relying on the underlying behavior of .flatten(0,1).

- yueyiming2009 · comment · 2026-07-02T03:42:13Z · [source](https://github.com/verl-project/verl/pull/6913#issuecomment-4861977213)

Nice catch, and the diagnosis is spot on. Worth noting why it's silent: `vocab_weights`/`lm_head` isn't flattened, so the head keeps training while the backbone is frozen.

The fix works, but restoring `requires_grad` on an intermediate tensor is a bit side-effecty. Since the real consumers are the `if hidden_states.requires_grad:` checks in `backward`, gating on `ctx.needs_input_grad` is more idiomatic and robust here. The engine snapshots that tuple from the original `.apply()` args *before* `forward` runs under no-grad — so unlike the flag on the flattened tensor, it isn't clobbered by `flatten(0, 1)`, and needs no flag mutation:

```python
# needs_input_grad is positional over forward args:
# [0] -> hidden_states, [1] -> vocab_weights (input_ids/scalars are False)
if ctx.needs_input_grad[0]:      # was: hidden_states.requires_grad
    dhidden_states = torch.zeros_like(hidden_states)
if ctx.needs_input_grad[1]:      # was: vocab_weights.requires_grad
    dvocab_weights = torch.zeros_like(vocab_weights)
```

This also lets you leave the `flatten(0, 1)` line untouched. Either way fixes the bug — just flagging the alternative.

Might also be worth a small regression test on the 3D path asserting `hidden_states.grad is not None`.

Using the in-place method `requires_grad_()` is the standard and more robust way in PyTorch to modify the `requires_grad` attribute of a tensor, especially when dealing with views or intermediate tensors. Additionally, naming the variable `hidden_states_requires_grad` (with an 's') is more consistent with PyTorch's attribute name `requires_grad`.

```suggestion
            hidden_states_requires_grad = hidden_states.requires_grad
            hidden_states = hidden_states.flatten(0, 1)
            hidden_states.requires_grad_(hidden_states_requires_grad)
```
