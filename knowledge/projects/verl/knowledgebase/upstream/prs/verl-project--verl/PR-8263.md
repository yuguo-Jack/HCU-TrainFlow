# [vllm, rollout] fix: reject routing replay when vLLM ran a different prompt

[Upstream PR](https://github.com/verl-project/verl/pull/8263) · state: closed · merged: False

## Original PR description

### What does this PR do?

Rollout routing replay (R3) returns one routed-experts row per token vLLM ran. The agent loop places those rows on the trainer's prompt by position. Nothing checks that the two prompts are the same token sequence.

They can differ for multimodal prompts. vLLM's multimodal processor expands each image placeholder into a span, so the prompt vLLM runs can be longer than the prompt the trainer replays on. When that happens, every row from the first divergent token on lands on the wrong token, and the tail is cut by `routed_experts[: len(prompt_ids) + response_length]`. Nothing fails. In the multimodal DeepSeek-V4.1 Flash run reported in vllm-project/vllm#61097, R3 made the train-inference mismatch worse than running without it.

This PR compares vLLM's prompt (`RequestOutput.prompt_token_ids`) with the trainer's prompt before returning routed experts, and raises if they differ. A row is the routing of one token in one context. A different prompt has different tokens and contexts, so no reordering of rows can be correct. With R3 enabled, failing is the only safe option.

The comparison uses the prompt the trainer holds, not the deduplicated one sent to vLLM. Qwen2.5-VL's deduplicated `<|image_pad|>` runs are re-expanded by vLLM to the same span, so they still pass.

### Test

`tests/workers/rollout/rollout_vllm/test_submitter_gate_on_cpu.py` gets one parametrized case that drives `vLLMHttpServer.generate` with R3 enabled, against a mocked engine that records the prompt it is sent and reports the prompt it ran:

| case | vLLM prompt | expected |
|---|---|---|
| `same-prompt` | same as the trainer's | routed experts returned |
| `qwen-vl-dedup-reexpanded` | the trainer's span, as vLLM re-expands the deduplicated Qwen2.5-VL prompt | one placeholder sent; routed experts returned |
| `engine-expanded-further` | the image expanded to more placeholders | `ValueError` |
| `same-length-other-tokens` | same length, different tokens | `ValueError` |

The whole file passes (20 tests) with the vLLM nightly `0.32.0rc1.dev281+g49cb2bbf7` on GB200. Each mutation fails only the listed cases:
- removing the check fails `engine-expanded-further` and `same-length-other-tokens`;
- comparing only lengths fails `same-length-other-tokens`;
- comparing against the deduplicated prompt sent to vLLM fails `qwen-vl-dedup-reexpanded`;
- sending the undeduplicated prompt to vLLM fails `qwen-vl-dedup-reexpanded`.

### API and Usage Example

No API change. Only the failure behavior changes: a rollout with `enable_rollout_routing_replay=True` whose prompt differs from the one vLLM ran now fails with:

```
ValueError: Rollout routing replay for request <id>: the prompt vLLM ran (270 tokens) differs from the trainer's prompt (77 tokens) from position <i>. Multimodal placeholders must expand to the same tokens on both sides.
```

### Design & Code Changes

- `vLLMHttpServer.generate`: keep the trainer's `prompt_ids`; send the Qwen2.5-VL-deduplicated copy to vLLM as `engine_prompt_ids`; with R3 enabled, raise if `final_res.prompt_token_ids != prompt_ids`.
- Test as above.

Scope: only the vLLM server. The SGLang server also returns routed experts, but its output does not report the prompt it ran, so there is nothing to compare against there.
