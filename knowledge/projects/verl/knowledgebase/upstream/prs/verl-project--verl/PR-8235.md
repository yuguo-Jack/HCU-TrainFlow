# [megatron] fix: onload the offloaded optimizer before load_checkpoint (resume with optimizer_cpu_offload)

[Upstream PR](https://github.com/verl-project/verl/pull/8235) · state: open · merged: False

## Original PR description

### What does this PR do?

Resuming a Megatron-engine run that uses `actor.megatron.optimizer_offload=True` together with `optimizer_cpu_offload=True` (Megatron `HybridDeviceOptimizer`, HDO) fails at the first `optimizer.step()` after the resume:

```
KeyError: tensor(...)      # HybridDeviceOptimizer._set_sub_optimizer_grads
```

or, with Megatron-LM PRs NVIDIA/Megatron-LM#4046 / NVIDIA/Megatron-LM#7785 applied,

```
RuntimeError: attempting to assign a gradient with device type 'cpu' to a tensor with device type 'cuda'
```

`MegatronEngine.load_checkpoint` calls `load_megatron_model_to_gpu` but leaves the optimizer where verl parked it after construction (fp32 shards on the host). HDO rebuilds its sub-optimizers inside `load_state_dict` and classifies every parameter by `is_cuda`: a shard that is still on the CPU gets no pinned copy and is treated as a CPU-resident parameter; when verl later onloads the optimizer, the CPU sub-optimizer holds a CUDA tensor. #6690 (`pin_memory` failure on the same resume path) is a neighbour of this bug.

Fix: in `load_checkpoint`, call `load_megatron_optimizer(self.optimizer)` when `self._is_offload_optimizer`, before `checkpoint_mananager.load_checkpoint` — symmetric to the model onload that is already there; the existing code offloads it again afterwards. The `KeyError` half of the problem is Megatron-LM's (#4046 / #7785, both open); this change is needed in addition to them.

### Test

Not coverable by CI (needs a multi-node Megatron run with CPU-offloaded optimizer and a checkpoint). Validated on GB200 (aarch64), verl `1d367a4f`, Megatron-LM `43e45e13` + #4046/#7785, DeepSeek-V4-Pro:

- 4-layer truncated model, 8 nodes, resume from `global_step_2` (`model+optimizer+extra`): fails as above without the change (two runs, both failure modes), resumes and finishes step 3 with it (rollout/actor Pearson 0.9992);
- 61-layer model, 128 nodes (PP16/EP32), resume with `model+extra`: resumes and finishes step 3 (Pearson 0.9955).

The change stays within the existing training-job boundary and does not expand checkpoint access or permissions. A failed restore can now leave optimizer memory on the GPU until cleanup or worker termination, creating a limited recovery risk.

**Retained concerns**
- **Low · reliability · inferred:** The newly added optimizer GPU transition has no exception-safe cleanup. A checkpoint validation or restoration failure after onload skips the final CPU offload, so surviving workers can retain optimizer GPU allocations that the base did not explicitly onload before restoration. This weakens job-local failure containment and recovery. Successful restoration still offloads the optimizer, and the inspected trainer does not continue training after a restore exception.
