# [megatron] fix: onload the offloaded optimizer before load_checkpoint (resume with optimizer_cpu_offload)

[Upstream PR](https://github.com/verl-project/verl/pull/8235) · state: closed · merged: True

## Original PR description

### What does this PR do?

Resuming a Megatron-engine run that uses `actor.megatron.optimizer_offload=True` together with `optimizer_cpu_offload=True` (Megatron `HybridDeviceOptimizer`, HDO) fails at the first `optimizer.step()` after the resume:

```
KeyError: tensor(...)      # HybridDeviceOptimizer._set_sub_optimizer_grads
```

or, with Megatron-LM PRs NVIDIA/Megatron-LM#4046 / NVIDIA/Megatron-LM#7785 applied,

```
RuntimeError: attempting to assign a gradient with device type 'cpu' to a tensor with device type 'cuda'
```

`MegatronEngine.load_checkpoint` calls `load_megatron_model_to_gpu` but leaves the optimizer where verl parked it after construction (fp32 shards on the host). HDO rebuilds its sub-optimizers inside `load_state_dict` and classifies every parameter by `is_cuda`: a shard that is still on the CPU gets no pinned copy and is treated as a CPU-resident parameter; when verl later onloads the optimizer, the CPU sub-optimizer holds a CUDA tensor. #6690 (`pin_memory` failure on the same resume path) is a neighbour of this bug.

Fix: in `load_checkpoint`, call `load_megatron_optimizer(self.optimizer)` when `self._is_offload_optimizer`, before `checkpoint_mananager.load_checkpoint` — symmetric to the model onload that is already there; the existing code offloads it again afterwards. The `KeyError` half of the problem is Megatron-LM's (#4046 / #7785, both open); this change is needed in addition to them.

- linmuchuiyang · comment · 2026-10-20T09:19:27Z · [source](https://github.com/verl-project/verl/pull/8235#issuecomment-6287698790)

Thanks for checking, @wuxibin89. Yes, it is still needed; I re-tested on top of #8286 to be sure:

- #8286 changes what `offload_megatron_optimizer` does with the HDO's *state* (it now leaves the sub-optimizer state alone), but it keeps calling `offload_megatron_copy_params`, which still parks the fp32 master shards (the optimizer's `param_groups[...]["params"]`) on the CPU. That is the part this PR is about: `MegatronEngine.load_checkpoint` runs with those shards on the CPU, and the HDO's `post_load_state_dict_hook` then calls `_init_sub_optimizers()`, whose `_get_sub_optimizer_param_groups` classifies every parameter by `param.is_cuda`. Shards that are only temporarily on the CPU are sorted into the CPU sub-optimizer with no pinned GPU copy; after verl moves them back to the GPU the first `step` fails in `_set_sub_optimizer_grads` with `attempting to assign a gradient with device type 'cpu' to a tensor with device type 'cuda'`.
- Re-ran the 4-layer DeepSeek-V4-Pro save → resume smoke on `main`'s `megatron_utils.py` from #8286 (GB200, 8 nodes, EP16, `optimizer_offload=True`, `optimizer_cpu_offload=True`, fraction 1.0):
  - with the stock `load_checkpoint` (i.e. #8286 alone): save at step 2 fine, resume loads `global_step_2`, then the first optimizer step fails exactly as before:
    ```
    File "megatron/core/optimizer/cpu_offloading/hybrid_optimizer.py", line 169, in step
    File "megatron/core/optimizer/cpu_offloading/hybrid_optimizer.py", line 121, in _set_sub_optimizer_grads
    RuntimeError: attempting to assign a gradient with device type 'cpu' to a tensor with device type 'cuda'
    ```
  - with this PR on top of #8286: resume from the same kind of checkpoint, step 3 trains and the run completes (rollout/actor log-prob Pearson 0.9993, unchanged from the pre-resume steps).

So the two fixes are complementary: #8286 fixes the per-step offload for fraction < 1, this PR fixes the resume path for any fraction. The change is a one-liner that only runs when `_is_offload_optimizer` is set, and the existing post-load offload still puts the optimizer back on the CPU afterwards. Rebased on current `main` (includes #8286).
