# [data] fix: rl_dataset.py with multiple dataset workers

[Upstream PR](https://github.com/verl-project/verl/pull/2487) · state: open · merged: False

## Original PR description

### What does this PR do?

It's a bugfix. Currently when running `verl/recipe/dapo/run_dapo_qwen2.5_32b.sh` on main this results in errors in the TaskRunner. Because of the following:

(1) It creates the default `rl_dataset.py` which has `serialize_dataset=False`
(2) The `StatefulDataLoader` has `num_workers=8` and when initializing the workers it sends them over the pickled dataset which is created with the custom `__getstate__` method in `rl_dataset.py`
(3) Bc `serialize_dataset=False` the state in the workers then does NOT have the `dataframe` object, which results in an error when trying to sample from it in the form of: `AttributeError: 'RLHFDataset' object has no attribute 'dataframe'`

This PR fixes this by overwriting the default __set_state__ method to load the dataframe if it wasn't serialized.

## Code Review

This pull request fixes a bug where using multiple `DataLoader` workers would cause a crash due to an uninitialized `dataframe` in the worker processes. The fix introduces a `__setstate__` method to the `RLHFDataset` class, which correctly reconstructs the dataset's `dataframe` when it's unpickled by a worker. The overall approach is sound and directly addresses the issue. I have one suggestion to improve the logging practice in the new code to make it more robust for multi-process environments.

Using `print()` for logging within a library, especially in code executed by multiple `DataLoader` workers, is strongly discouraged. It can lead to several issues in a distributed or multi-process environment:

*   **Uncontrollable Output**: `print` writes directly to `stdout`, making it difficult to suppress, redirect, or format log messages consistently across the application.
*   **Log Noise**: With multiple workers, interleaved `print` statements can clutter the console output, making it hard to debug and monitor the training process.
*   **Performance**: In some environments, writing to `stdout` can be a blocking operation and might introduce performance overhead.

This class already defines a `logger` instance at the module level. Using it would be more consistent with best practices and the existing code in the file (e.g., line 328). This change will make the library more robust and easier to use in production environments.

```suggestion
            logger.info("__setstate__ called: reconstructing dataframe")
```
