# [model, fsdp, rollout, vllm] feat: Step-5-Preview FP8 GRPO with LoRA on FSDP2

[Upstream PR](https://github.com/verl-project/verl/pull/8246) · state: open · merged: False

## Original PR description

### What does this PR do?

Adds RL support for **Step-5-Preview** (FP8 block-quantized MoE with sparse
DSA attention) on the FSDP2 engine. It covers GRPO with LoRA against a vLLM
rollout, rollout routing replay (R3), and adapter-only weight sync.

verl has no Step5 model, so the PR adds a verl-native text model and an example
recipe, plus the generic changes the run needed. 21 files; each commit can be
reviewed on its own:

| # | Commit | Files | Scope |
|---|---|---|---|
| 1 | `[utils] fix: honor tokenizer.json when AutoTokenizer rebuilds the pre-tokenizer` | 1 | all models, only when the loaded tokenizer deletes whitespace that its `tokenizer.json` keeps |
| 2 | `[vllm] fix: treat untagged vLLM source builds as the newest API` | 6 | untagged vLLM builds (`0.1.devN`); the TCP-store path for every build |
| 3 | `[rollout, vllm] perf: stage LoRA buckets in one host block; optionally drop the adapter host copy` | 4 | LoRA sync to vLLM |
| 4 | `[fsdp] feat: support R3 router replay` | 4 | FSDP engine, off by default; LoRA reference routing in every engine |
| 5 | `[fsdp, model] feat: Step-5-Preview text model for FSDP2 LoRA RL` | 6 new + engine hooks | `model_type == "step5"` only |

**Dependency on vLLM.** Upstream vLLM does not serve Step5 yet. The rollout
needs a vLLM build with the Step5 model, LoRA serving on its fused attention
and sparse-indexer projections, and pageable host backups for level-1 sleep
(pinned backups made host memory grow on every sleep/wake cycle until OOM).
Those vLLM changes are being upstreamed separately. Until then this PR is a
draft; the verl side does not depend on any vLLM internals beyond the
existing LoRA/weight-sync paths.

**Overlap with open PRs. Please reconcile before merging.**

- #8193 addresses the same tokenizer failure as commit 1. Commit 1 acts only on
  the observed failure (whitespace deleted on a round trip, kept by the file),
  and refuses to load rather than swap when special tokens, added tokens, the
  vocabulary size, the chat template or the special tokens around plain text
  would change.
- #8194 is the same feature as commit 4. Here the FSDP engine turns R3 on
  while it builds the model, so VeOmni (which builds its own model and has its
  own replay hook) needs no change.

### API and Usage Example

```bash
# Needs a vLLM build that serves Step5 (see "Dependency on vLLM").
# ckpt_dir must be on storage shared by all nodes.
bash examples/grpo_trainer/run_step5_preview_dapo_lora_fsdp.sh
```

- Model: `stepfun-ai/Step-5-Preview` (FP8). Data: DAPO-Math-17K for training,
  AIME-2024 for validation.
- 4 nodes x 4 GPUs, two TP8 vLLM engines; LoRA r32/α64, lr 1e-5 constant;
  R3; sequence-level geometric rejection (`seq_mean_k1`, 0.995–1.005), no IS
  weights; 4096-token responses.
- The recipe passes its environment to the Ray workers through
  `ray_kwargs.ray_init.runtime_env.env_vars`; a plain `export` does not reach
  workers of a pre-started cluster.
- Extra packages beyond verl's: `peft==0.21.2`, `accelerate==1.15.0`.
- Optional, for repeatable LoRA outputs: point `VLLM_TUNED_CONFIG_FOLDER` at a
  LoRA shrink config with `split_k=1`. The default reduces with atomic adds.
- Cost: about 13 minutes per step, plus about 4 minutes per AIME validation.

New environment variables (all default to the validated behavior):

- `VERL_STEP5_FP8_ACT_QUANT` (default 1): FP8 activation rounding on routed experts.
- `VERL_STEP5_LORA_PER_EXPERT` (default 0): per-expert instead of shared expert factors.
- `VERL_STEP5_ROUTING_AGREEMENT` (diagnostic): logs trainer-router agreement with the replayed routing.
- `VERL_LORA_STAGE_PIN` (default 1): pin the LoRA staging blocks in the vLLM worker.
- `VERL_LORA_DROP_HOST_COPY` (opt-in): release the adapter's host copy in the vLLM worker.

### Design & Code Changes

**Step5 text model** (`verl/models/transformers/step5/`)

- `modeling_step5.py`: the model.
- `loading.py`: FP8 checkpoint loading into FSDP2 shards, and the engine hooks.
- `lora.py`: LoRA attach and adapter export.
- `register.py`: Auto registration.

What it does:

- **Model.** A plain-PyTorch port of the vLLM Step5 text model. It keeps the
  pieces that change numerics:
  - GQA with sliding and sparse (DSA) attention and a head-wise gate;
  - zero-centered RMSNorm and FP32 residual;
  - a FP32 sigmoid router with correction bias;
  - packed routed experts plus a shared expert.

  It has no inference kernels, KV cache or TP. The config class comes from the
  installed vLLM, because transformers has no `step5` type. Registration goes
  through `VERL_USE_EXTERNAL_MODULES=verl.models.transformers.step5.register`.
- **FP8 checkpoint.** Block-FP8 weights are dequantized to BF16 straight into
  each rank's FSDP2 local shard. No rank ever materializes the full model.
- **FP8 activation rule.** Routed experts stored in FP8 see the same 1x128
  UE8M0/E4M3 activation rounding as the serving kernel, with a
  straight-through gradient.
- **LoRA targets.** Attention projections and every MLP, including the routed
  experts through PEFT `target_parameters`. Expert adapters are applied
  unfolded, `s * (x A^T) B^T`, as vLLM does, with FP32 masters. They are never
  folded into a BF16 expert stack. The rank must be a multiple of 8 (grouped
  GEMM alignment).
- **Shared factors.** By default the expert gate/up `A` and down `B` are shared
  across the experts of a layer. The export expands them to the per-expert vLLM
  format.
- **R3.** Recorded rollout routing replaces the native top-k for recorded
  tokens. The weights still come from the trainer router.
- **Packed inputs.** verl's remove-padding rows (`input_ids` + `position_ids`)
  are unpacked into a padded batch and packed back. Any other row whose valid
  tokens do not have strictly increasing positions raises, instead of silently
  attending across sequences. Multi-axis (mRoPE-style) positions are refused.
- **Sync.** The rollout loads the base weights itself. Adapters are streamed
  to it in the per-expert format, using grouped all-gathers. There is no full
  host copy per rank.
- **Engine hooks.** `FSDPEngine` dispatches on `model_type == "step5"` for the
  meta-model build, LoRA attach, sharding/loading, adapter export and the
  refusals below. Other models take the existing path unchanged.

**Known gaps**

- Text-only. The vision tower and MTP layers are not loaded.
- Startup refuses configurations that were not validated or cannot work:
  sequence parallel, liger and fused kernels; activation/param/optimizer
  offload, QAT, a separate reference engine; resuming from
  `lora_adapter_path` (resuming through the verl checkpoint manager works);
  `lora.merge` and merged `hf_model` export (PEFT cannot merge the shared
  expert factors); a LoRA rank not divisible by 8; a base-weight sync
  (`rollout.load_format=dummy` or a non-naive checkpoint engine); adapter
  export from a model built from selected source layers.
- Numerics not yet compared operation by operation with the serving kernels:
  the dense and shared-expert SwiGLU rounds SiLU to BF16 before the
  multiplication, and each routed expert's output is rounded to BF16 before
  the routing weight is applied. Both can move a BF16 result by one ulp. They
  stay as validated until checked against the serving implementation.
- Commit 1 covers tokenizers loaded through `hf_tokenizer`/`hf_processor`. Text
  sent to the rollout server as text is tokenized by the server. Versioned
  tokenizer files (`fast_tokenizer_files`) are not looked up.
- Commit 2 assumes an untagged build is the newest vLLM. An untagged checkout
  of an older vLLM passes the minimum-version checks and fails later inside
  vLLM (for R3 on a pre-0.22 checkout with several KV-cache groups, an
  IndexError in the routed-experts capture). The warning says so; build from a
  tagged checkout to keep the checks.
- Commit 4 checks the R3 prerequisites at startup on the FSDP engine only.
- The grouped adapter gathers are bounded by `max_gathered_bytes`, which is not
  a ceiling on peak memory: a single larger tensor is gathered alone.
- A failure inside a weight sync can still leave the other side waiting, as
  before this PR.

**Rollback / impact on other models**

- Commit 5 is gated on `model_type == "step5"`.
- Commit 4 is gated on `router_replay.mode`, which is off by default, with
  one exception: reference log-probs computed through the actor with the
  adapter disabled (the LoRA reference) now route natively instead of
  replaying the actor's rollout routing, as a separate reference worker does.
  The flag is shared by all engines, so Megatron and VeOmni runs that combine
  a LoRA reference with routing replay change too.
- Commit 1 does nothing unless a probe decodes back with some of its
  whitespace deleted and nothing else changed. A healthy tokenizer costs one
  encode and decode; a tokenizer whose own file also loses the whitespace is
  left alone without a second load.
- Commit 2 changes branch selection only for untagged `0.1.devN` builds
  (prereleases and post-releases of it are parsed as before). A real nightly
  below 0.22, such as `0.21.2.devN`, is still refused for R3. The gates where
  the older path is the safe one (the `mm_processor_cache_gb=0` workaround,
  the NPU 0.23 patch window) keep the raw version. The TCP-store path in
  `stateless_init_process_group` now follows `StatelessProcessGroup`'s fields
  rather than the version, which picks the same path for every tagged release.
- Commit 3 copies LoRA buckets in the vLLM worker as one host block per bucket
  (expert factors in their own block) instead of one clone per tensor, and
  refuses a tensor name sent twice in an adapter-only update. Dropping the
  host copy is opt-in and is ignored with a warning unless the adapter has a
  single slot.
