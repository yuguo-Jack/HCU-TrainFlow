# fix: handle labels=None in fused forward to avoid crash without MTP (#5273)

[Upstream PR](https://github.com/verl-project/verl/pull/5332) · state: open · merged: False

## Original PR description

## Problem

When `use_fused_kernels=True` and `mtp.enable=False`, the patched `_fused_GPTModel_forward` receives `labels=None` from the non-fused caller path (`gptmodel_forward_no_padding`). This causes an `AttributeError` in `linear_cross_entropy` because it tries to access `labels.shape` on `None`.

**Root cause:** `patch_fused_forward` replaces `GPTModel.forward` globally, but the non-fused caller path (`gptmodel_forward_no_padding`) only passes `labels` when both `enable_mtp` and `post_process` are `True`. When MTP is disabled, the patched forward is still called without `labels`, leading to the crash.

**Error traceback:**
```
File "verl/utils/kernel/linear_cross_entropy.py", line 74, in forward
    if len(labels.shape) != 1:
           ^^^^^^^^^^^^
AttributeError: 'NoneType' object has no attribute 'shape'
```

## Fix

Add a guard in `_fused_GPTModel_forward` that, when `labels is None`, falls back to standard logit computation via `model.output_layer` — matching the original `GPTModel._postprocess` behavior.

## Testing

This fix is a minimal guard that only activates when `labels is None`. It does not affect the existing fused kernel path (which always receives labels via `fused_forward_no_padding`).

Fixes #5273

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

While this change correctly fixes the crash, it highlights a deeper design issue: `_fused_GPTModel_forward` has inconsistent return types. It returns a `CausalLMOutputForPPO` object when `labels` are provided, but a `torch.Tensor` when they are not.

This is brittle because different callers have different expectations:
- `fused_forward_no_padding` expects a `CausalLMOutputForPPO` object to access attributes like `.log_probs`.
- `gptmodel_forward_no_padding` expects a raw `torch.Tensor` to pass to `postprocess_thd_no_padding`.

The current implementation relies on an implicit contract that `fused_forward_no_padding` will always provide labels. This is fragile and can be easily broken by future changes, leading to runtime errors.

A more robust solution would be to make the return type consistent. For example, `_fused_GPTModel_forward` could always return a `CausalLMOutputForPPO` object:
```python
if labels is None:
    logits, _ = model.output_layer(hidden_states, weight=output_weight)
    return CausalLMOutputForPPO(logits=logits)
```
This would then require modifying `gptmodel_forward_no_padding` to extract the tensor it needs (e.g., `output_orig.logits`).

While a larger refactor might be out of scope for this PR, this design flaw is critical for long-term maintainability and should be addressed to make the code more robust.
