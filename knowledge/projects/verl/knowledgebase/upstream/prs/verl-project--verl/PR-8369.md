# [veomni] fix: support the trainer-side rollout weight quantizer in the VeOmni engine

[Upstream PR](https://github.com/verl-project/verl/pull/8369) · state: closed · merged: True

## Original PR description

### What does this PR do?

Since #8287 (unify QAT and low-precision rollout), `init_model` hands the actor engine a rollout weight quantizer whenever the rollout is quantized — for a checkpoint whose `quantization_config` is FP8 (e.g. DeepSeek-V4-Flash-Base), `dispatch_rollout_weight_quantizer` returns an `Fp8ConfigWeightQuantizer` — and calls `engine.set_rollout_weight_quantizer`, which only the Megatron engine implements. Every VeOmni-engine run on such a checkpoint, including `examples/grpo_trainer/run_deepseek_v4_veomni.sh` with its default model, therefore stops in `init_model`:

```
NotImplementedError: VeOmniEngineWithLMHead does not support trainer-side rollout quantization
```

This PR implements it the way the Megatron engine does: the engine keeps the quantizer and applies it to the per-tensor stream of `get_per_tensor_param`. For DeepSeek-V4, VeOmni's checkpoint converter already exports the release FP8/FP4 layout, and the quantizer is a pass-through for that model type (as for Megatron-Bridge's export); other models' BF16 streams get quantized to what the rollout loads.

### Test

- `tests/workers/test_veomni_rollout_quantizer_on_cpu.py`: the exported stream is returned unchanged without a quantizer and passes through it otherwise; the checkpoint's `hf_model` export stays unquantized, and `initialize()` hands the checkpoint manager that unquantized export.
- `tests/utils/test_rollout_weight_quantizer_dispatch_on_cpu.py`: a `rollout.quantization` override for DeepSeek-V4 is rejected whether or not the checkpoint is quantized, and so is `delta_sharded` sync with a quantized rollout; DeepSeek-V4's native config still passes through, and an override for another model is dispatched.
- End to end, with #8370 and #8371: `run_deepseek_v4_veomni.sh` with its defaults (DeepSeek-V4-Flash-Base, FP8) gets past `init_model` and trains on two nodes each of AMD gfx942 and gfx950. The trainer exports the FP8 weights through this path at every weight sync, and rollout and trainer token probabilities stay consistent after each sync.

### API and Usage Example

No API or config change. `VeOmniEngine` now implements the existing `set_rollout_weight_quantizer` hook, so a run with `model_engine=veomni` on a checkpoint whose `quantization_config` is FP8 (such as `run_deepseek_v4_veomni.sh` with its default model) gets past `init_model`. Two combinations the trainer cannot sync now fail at `init_model` with an explicit error, for both engines: a `rollout.quantization` override for DeepSeek-V4, and `checkpoint_engine.backend='delta_sharded'` with a quantized rollout.

### Design & Code Changes

- `VeOmniEngine.set_rollout_weight_quantizer` stores the quantizer; `get_per_tensor_param` applies it to the export of `_get_hf_export_per_tensor_param` (converter path and state-dict path). The checkpoint manager's `hf_model` export calls `_get_hf_export_per_tensor_param` directly, so saved checkpoints keep the trainer's weights.
- `dispatch_rollout_weight_quantizer` rejects `rollout.quantization` overrides for DeepSeek-V4. Both engines export it under its checkpoint names (e.g. `ffn.experts`, which the override's `mlp.experts` MoE target does not match) and, for a quantized checkpoint, in its own FP8/FP4 layout, which `CompressedTensorsWeightQuantizer` passes through unchanged.
- It also rejects `delta_sharded` sync for a quantized rollout: after the seed, that backend streams `get_per_tensor_param_delta_shard`, which bypasses the quantizer. vLLM's delta weight transfer already refuses quantized models; SGLang's delta loader has no such check.
