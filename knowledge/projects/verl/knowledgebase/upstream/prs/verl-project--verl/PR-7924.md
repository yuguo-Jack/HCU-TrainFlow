# [cfg, worker, trainer] fix: reject non-positive batch, parallelism and GPU-count values at config time

[Upstream PR](https://github.com/verl-project/verl/pull/7924) · state: open · merged: False

## Original PR description

### What does this PR do?

Zero (or negative) values for a handful of integer knobs are currently accepted by config validation and fail later in ways that do not name the knob:

| override | current main (3efe38c) |
|---|---|
| `trainer.n_gpus_per_node=0` | `ZeroDivisionError` *inside* `validate_config` (`utils/config.py:124` — the modulo runs before the assert can format its message) |
| `actor_rollout_ref.rollout.tensor_model_parallel_size=0` (or `data_parallel_size=0`) | `ZeroDivisionError` at `engine_workers.py:658`, after ray + model init (~60 s); the explanatory assert is one line below the division |
| `actor_rollout_ref.actor.ppo_micro_batch_size_per_gpu=0` | `ZeroDivisionError` at `engine/utils.py:125`, after init and the first rollout (~2 min) |
| `actor_rollout_ref.rollout.n=0` | after ~2 min: `RuntimeError: Sync replay buffer selected terminal groups with no materializable trajectories. Enable trainer.v1.sampler.sync_refill_failed_groups...` — names an unrelated setting |

This PR validates these at config construction with errors that name the parameter:
- `RolloutConfig.__post_init__`: `n`, `tensor_model_parallel_size`, `data_parallel_size`, `pipeline_model_parallel_size` must be positive integers.
- `ActorConfig` / `CriticConfig.__post_init__`: `ppo_mini_batch_size`, `ppo_micro_batch_size`, `ppo_micro_batch_size_per_gpu` must be positive when set.
- `validate_config`: `trainer.n_gpus_per_node * trainer.nnodes` must be `> 0`.
- The two engine-side asserts now check positivity before dividing, so they fail with their own message instead of `ZeroDivisionError` if reached some other way.

No behavior change for valid configs.

Note: the `RolloutConfig` checks fire where the dataclass is instantiated today (worker construction, after ray init), so they surface at ~1 min rather than ~7 s; instantiating the rollout config from `validate_config` as well would move them to the driver and could be a follow-up.

### API and Usage Example

No API change; invalid values that previously crashed later now fail at config validation.

### Design & Code Changes

- `verl/workers/config/rollout.py`: positivity checks at the top of `RolloutConfig.__post_init__`.
- `verl/workers/config/actor.py`, `critic.py`: positivity checks for the PPO batch-size fields in `__post_init__`.
- `verl/utils/config.py`: `n_gpus > 0` guard before any divisibility arithmetic in `validate_config`.
- `verl/workers/engine_workers.py`, `verl/workers/engine/utils.py`: assert positivity before dividing.

- koriyoshi2041 · comment · 2026-09-18T22:47:36Z · [source](https://github.com/verl-project/verl/pull/7924#discussion_r4051244056)

File: `verl/workers/config/actor.py` · line None

The Actor/Critic checks do not currently enforce the stated positive-integer contract. They only raise when `value` is an `int` (and not `bool`) with `value < 1`, so values such as `False` and `0.5` bypass validation, unlike the stricter `RolloutConfig` check in this PR. Since direct dataclass/Hydra instantiation is part of this config path, could these loops use the same predicate as rollout for non-`None` values (`isinstance(value, bool) or not isinstance(value, int) or value < 1`) and add bool/float cases to the table test?
