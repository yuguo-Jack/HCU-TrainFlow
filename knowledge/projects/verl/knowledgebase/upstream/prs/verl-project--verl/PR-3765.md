# fix: gradient vanish in FusedLinearForPPO

[Upstream PR](https://github.com/verl-project/verl/pull/3765) · state: open · merged: False

## Original PR description

### What does this PR do?

`torch.autograd.Function.forward` is effectively under a `torch.no_grad` block, causing operations such as `flatten` to create tensors with `requires_grad=False`. In the case of LoRA, where `vocab_weights.requires_grad == False`, this leads to vanished gradients. Rearranging the code order fixes this. Moreover, using `ctx.needs_input_grad` is always recommended in `torch.autograd.Function.backward`, providing an additional layer of safeguard.

## Code Review

This pull request correctly fixes a critical gradient vanishing bug in `FusedLinearForPPOFunction`. The issue was caused by operations within `torch.autograd.Function.forward` creating new tensors without gradient tracking, which is addressed by calculating `output_requires_grad` before any tensor modifications. The PR also improves the robustness of the `backward` pass by correctly using `ctx.needs_input_grad` instead of checking `requires_grad` on saved tensors, which is a best practice for custom autograd functions. The changes are accurate and well-explained. I've added one suggestion to further optimize the backward pass by avoiding unnecessary gradient computations, which aligns with the performance-oriented nature of this fused function.

While the use of `ctx.needs_input_grad` is correct, there's a performance optimization opportunity here. The `_fused_linear_for_ppo_bwd` function unconditionally computes gradients for both `hidden_states` (`h`) and `vocab_weights` (`v`). These computations, especially the matrix multiplications, can be expensive.

However, they are only used if the corresponding `needs_input_grad` is true. This means we might be computing gradients that are then discarded.

I recommend modifying `_fused_linear_for_ppo_bwd` to conditionally compute these gradients based on boolean flags. For example:

```python
def _fused_linear_for_ppo_bwd(
    ...,
    compute_dhidden: bool,
    compute_dvocab: bool,
) -> tuple[Optional[torch.FloatTensor], Optional[torch.FloatTensor]]:
    ...
    dhidden_states = dlogits @ vocab_weights if compute_dhidden else None
    dvocab_weights = dlogits.t() @ hidden_states if compute_dvocab else None
    return dhidden_states, dvocab_weights
```

Then, in the `backward` method, you can call it like this:
```python
h, v = _fused_linear_for_ppo_bwd(
    ...,
    compute_dhidden=ctx.needs_input_grad[0],
    compute_dvocab=ctx.needs_input_grad[1],
)

if h is not None:
    dhidden_states[chunk_start:chunk_end] += h
if v is not None:
    dvocab_weights += v
```
This would avoid unnecessary expensive computations when gradients are not required for one of the inputs.
