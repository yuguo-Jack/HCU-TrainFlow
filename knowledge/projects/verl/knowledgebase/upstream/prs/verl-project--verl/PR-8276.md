# [reward] fix: match whole words in search_r1 subEM and ignore empty golden answers

[Upstream PR](https://github.com/verl-project/verl/pull/8276) · state: open · merged: False

## Original PR description

### What does this PR do?

`search_r1_like_qa_em.subem_check` matches a golden answer as a *character* substring of the
prediction, so the subEM reward is given for answers that do not contain the golden answer:

| answer | golden | subEM before | after |
|---|---|---|---|
| comparison | Paris | 1 | 0 |
| Parisa Khosravi | Paris | 1 | 0 |
| 1999 | 1 | 1 | 0 |
| anything at all | The (normalizes to "") | 1 | 0 |

This PR matches the golden answer as a contiguous run of whole words, ignores golden answers that
normalize to "" in both `subem_check` and `em_check`, and adds an optional `max_answer_tokens` to
`compute_score_subem` (default `None`, unchanged behaviour) so a policy cannot collect the reward by
listing many candidates in one `<answer>`.

### reviews

- rahul05ranjan · COMMENTED · 2026-10-19T14:46:28Z · [source](https://github.com/verl-project/verl/pull/8276#pullrequestreview-5573332535)

Verified the new semantics against the old code — the token-run comparison in `_contains_tokens` handles the short-prediction case correctly (the range is empty when the answer is longer than the prediction, so `any` is false), and skipping goldens that normalize to `""` closes the `"" in ""` loophole in both `em_check` and `subem_check`, not just subEM.

One thing I'd make explicit in the description or docs: this is a breaking change to the subEM metric relative to the upstream Search-R1 implementation (`golden in normalized_prediction` on characters). Reward curves will be discontinuous across versions — e.g. `subem_check("Newcastle", ["New"])` flips from 1 to 0, and a prediction of only "The" against a "The" golden now scores 0 where it used to match. That's clearly the point (the parameterized tests document each case), but anyone comparing runs across versions should know.

Smaller notes:

- `max_answer_tokens` is only on `compute_score_subem`; the EM path keeps the >10 `</answer>` tag penalty that subEM never had. Not new, just a reminder that the two functions keep drifting apart — at some point it may be worth unifying the shared skeleton.
- `compute_score_subem` gained the parameter at the end, so positional callers are unaffected. Good.

The empty-golden tests (`["."]` next to `"Paris"`) are a nice touch — that fixture pattern is exactly what a dataset with junk goldens looks like in the wild.
