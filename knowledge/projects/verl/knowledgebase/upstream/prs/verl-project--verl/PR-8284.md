# [hardware, test] fix: convert hardcoded cuda/nccl from unit tests and linear cross-entropy kernel host code

[Upstream PR](https://github.com/verl-project/verl/pull/8284) · state: open · merged: False

## Original PR description

### What does this PR do?

Replace hardcoded `"cuda"`, `torch.cuda.*`, and the `"nccl"` backend in unit tests and the Triton linear cross-entropy kernel host code with the existing `verl.utils.device` helpers (`get_device_name`, `get_torch_device`, `get_device_id`, `get_nccl_backend`, `is_device_available`). On CUDA these resolve to the same `cuda`/`nccl` values as before, so CUDA behaviour is unchanged. The change targets `verl.plugin.platform`'s accelerator abstraction generally; **Intel XPU is used here only as the non-CUDA hardware to demonstrate the refactor works off-CUDA**, not as the motivation for it. Originally triggered by a unit-test report where `tests/workers/rollout` failed with "Test hardcodes cuda" when run off-CUDA.

Two source changes were required for `tests/utils/test_linear_cross_entropy.py` to run off CUDA:
- `LinearCrossEntropy` now calls `get_platform().nvtx_range(...)` instead of `torch.cuda.nvtx.range(...)`, which raised on non-CUDA builds.
- The host asserts in `verl/utils/kernel/kernels.py` now check `tensor.device.type != "cpu"` instead of `tensor.is_cuda`, so any non-CPU device is accepted.

This revision also fixes three pre-existing test bugs, unrelated to CUDA vs. XPU, that an earlier version of this PR had listed as known failures:

- **`tests/models/test_fsdp_no_padding_on_gpu.py`** — the three tests build the engine via `__new__`, bypassing `__init__`. `self.pad_to_length` (added to `__init__` by #7272, before this branch's base) is read by `prepare_model_inputs`, so the un-set attribute raised `AttributeError`. Fixed by setting `engine.pad_to_length = False`, matching the documented default.
- **`tests/models/test_liger_vl_compat.py`** — the test's own tiny `Qwen3VLConfig` used the old `rope_scaling={"type": "mrope"}` key style, which current transformers has no init function for (`KeyError: 'mrope'`). Fixed with `rope_type="default"`.
- **`tests/single_controller/test_ray_collectives.py`** — the CUDA-only skip compared `get_device_name() != "cuda"`, but `get_device_name()` falls back to `"cuda"` when no accelerator is detected at all (e.g. a CPU-only box). Added `is_device_available()` to the guard so that case actually skips instead of hitting a `ray.init()`/NCCL crash.

All three were reproduced and fixed on an NVIDIA A100 (not just XPU) — see Test section.

The two tests fixed in this revision were also confirmed to fail with the exact `AttributeError`/`KeyError: 'mrope'` when reverted — on CUDA, not just XPU — so these are pre-existing bugs, not platform-specific ones.

`test_high_level_scheduling_api.py` fails under this single pinned non-zero GPU index (`CUDA_VISIBLE_DEVICES=6`) because it asserts device index `0`; reproduces identically on unmodified `main` with the same pinning, so it's an environment artifact, not a regression.

`test_ray_collectives.py`'s guard fix is verified by code inspection (see above); the collective path itself needs 3 GPU slots and wasn't re-run end-to-end — same multi-GPU constraint the XPU run described needing "a node" for its 8-GPU tests. `test_device_mesh_register.py`, `test_split_resource_pool.py` (8 GPUs) and the 2-rank distributed tests were not re-run on CUDA in this pass; see the XPU results above for those.

### Known failures that are not addressed here

- `tests/workers/rollout/test_hf_rollout.py`: `HFRollout` doesn't implement the abstract methods of `BaseRollout`, and the test asserts a batch expansion by `n` that `HFRollout` doesn't do.
- `tests/models/test_engine.py` split test: first run in a fresh XPU pod stalls inside a Level Zero memory copy; reruns in the same pod pass. Not diagnosed.

### Why these bugs went unnoticed

None of the three fixed-in-this-revision test files are collected by any existing CI job, upstream or on this fork: `cpu_unit_tests.yml` restricts discovery to `*_on_cpu.py` via `pytest.ini`; `gpu_unit_tests.yml` runs with `--ignore-glob="tests/models/"` (a deliberate, pre-existing split — `tests/models/` needs 8-GPU `torchrun` setups and runs via the dedicated `model.yml` job instead); and `model.yml`'s GPU job only names specific files (`test_transformer.py`, `test_transformers_ulysses.py`, `test_engine.py`, `test_model_forward_fused.py`). Confirmed by running both unmodified on `main` directly — same failures reproduce there.

### Design & Code Changes

- 18 test files: hardcoded `cuda`/`nccl` replaced by `verl.utils.device` helpers; CUDA-only skip guards use `is_device_available()`.
- `verl/utils/kernel/linear_cross_entropy.py`: use `get_platform().nvtx_range(...)`.
- `verl/utils/kernel/kernels.py`: host asserts accept any non-CPU device.
- `tests/models/test_fsdp_no_padding_on_gpu.py`: set `engine.pad_to_length = False` on the manually-constructed engine.
- `tests/models/test_liger_vl_compat.py`: `rope_type="default"` instead of `type="mrope"`.
- `tests/single_controller/test_ray_collectives.py`: device helpers plus `is_device_available()` added to the CUDA-only skip.
