# [hardware, doc] feat: speed up the Qwen3-4B TPU GRPO example (256 concurrent rollouts, micro batch 4, 1024-token buckets)

[Upstream PR](https://github.com/verl-project/verl/pull/8226) · state: closed · merged: True

## Original PR description

### What does this PR do?

Roughly halves the step time of the Qwen3-4B TPU GRPO example (`examples/tpu/grpo/run_qwen3_4b_torchtitan.sh`, added in #8225) with three defaults:

- `MAX_NUM_SEQS` 32 -> 256: vLLM decodes all 32 x 8 rollouts of a batch at once. With 32 concurrent sequences the trainer waited 35-45 s per step in the weight-sync pause for in-flight requests; now ~0.1 s.
- `MICRO_BATCH_SIZE` 1 -> 4, also used for `actor_rollout_ref.ref.log_prob_micro_batch_size_per_gpu`: 4 sequences per micro batch in the actor update and the reference log-probs halves the trainer time.
- `pad_to_length=True`, `pad_to_length_bucket=1024` (the reference model inherits them): packed micro batches are padded to 1024-token buckets instead of 256, so the at most 6 shapes all compile in the first step instead of new shapes compiling during training.

Not a duplicate: the only other change to these files was #8225.

### Test

2 TPU v6e-4 slices (4 trainer + 4 rollout chips), GKE spot, image built from `examples/tpu/grpo/Dockerfile`, `verl-hardware-plugin` `main`. Command from `examples/tpu/grpo/README.md` with `TOTAL_TRAINING_STEPS=10 TEST_FREQ=100 VAL_BEFORE_TRAIN=False`:

| Per step (s) | `main` (micro batch 1, 32 seqs) | + micro batch 4 | + 256 seqs | This PR (+ 1024-token buckets) |
|---|---|---|---|---|
| `update_actor` | ~26 | 13-14 (23-38 when compiling) | 11-13 (23-25 when compiling) | 11.7-12.7 (steps 2-10) |
| `ref` | ~5.0 | 2.6-2.9 (7-12 when compiling) | 2.3-2.7 (7-7.5 when compiling) | 2.5-3.0 (steps 2-10) |
| weight-sync pause (`tpu-sync/quiesce`) | 25-35 | 35-43 | 0.03-0.14 | ~0.1 |
| `step`, mean of steps 2-10 | ~72 | 67 | 35.5 | **32.0-32.8** |

- Each run 10/10 steps, reward rising to ~0.55-0.65 by step 10 in all configurations, response lengths unchanged.
- Validation of this branch as committed (no overrides besides `RAY_DATA_HOME`): 10/10 steps, all 20 model compiles in step 1, `update_actor` 11.0-12.1 s and `ref` 2.5-2.9 s from step 3, weight sync ~1.8 s, mean step over steps 2-10 **32.0 s**.
- Tried and not adopted (no gain or slower): `max_num_batched_tokens=8192` (32.2 s), `gpu_memory_utilization=0.85` (32.0 s), 2 batches in flight with `MAX_NUM_SEQS=512` (43.5 s).
- With 256-token buckets, sums of 4 sequences take up to 24 packed lengths, and steps that met a new one paid 10-25 s of compiles (steps 3, 5, 7); with 1024-token buckets every shape compiles in step 1.
- The step is now bound by the rollout (~35-40 s per batch); steps whose batch was already generated take ~17 s.
- Memory fits on 4 trainer chips, but libtpu logs more recoverable `RESOURCE_EXHAUSTED ... Fragmentation` allocation retries than at micro batch 1. `MICRO_BATCH_SIZE=1 MAX_NUM_SEQS=32` restores the old rollout and trainer batching.

### API and Usage Example

No API change. `MICRO_BATCH_SIZE=1 MAX_NUM_SEQS=32 bash examples/tpu/grpo/run_qwen3_4b_torchtitan.sh` keeps the previous settings.

### Design & Code Changes

- `run_qwen3_4b_torchtitan.sh`: `MAX_NUM_SEQS` default 32 -> 256; `MICRO_BATCH_SIZE` default 1 -> 4; `actor_rollout_ref.ref.log_prob_micro_batch_size_per_gpu` uses `${MICRO_BATCH_SIZE}` (was 1); `actor_rollout_ref.actor.torchtitan.pad_to_length=True` and `pad_to_length_bucket=1024`.
- `examples/tpu/grpo/README.md`: expected 4B step time ~70 s -> 30-40 s.
- `docs/hardware/multi_chip_support.rst`: list Google TPU v6e with a link to `examples/tpu/grpo` instead of "experimental, under development".
