# [hardware] feat: enable TPU GRPO with TorchTitan and vLLM via verl-hardware-plugin

[Upstream PR](https://github.com/verl-project/verl/pull/8155) · state: open · merged: False

## Original PR description

### What does this PR do?

Adds `examples/tpu/grpo/run_qwen3_4b_torchtitan.sh` to run Qwen3-4B-Base GRPO on GSM8K using TorchTitan training, vLLM rollout, and `verl-hardware-plugin`.

Builds on [PR #50](https://github.com/jialei777/verl-upstream/pull/50). 


### API and Usage Example

On an existing Ray TPU cluster with the hardware plugin, model, and datasets available:

```bash
bash examples/tpu/grpo/run_qwen3_4b_torchtitan.sh
```

### Launch Script Recipe

- Default configuration: 250 training steps, 128 prompts per step, 16 responses per prompt, and 2048-token responses.
- Validates the full GSM8K test split before training and every 20 steps.
- Supports environment-variable overrides and additional Hydra arguments.

- wuxibin89 · comment · 2026-10-10T02:23:42Z · [source](https://github.com/verl-project/verl/pull/8155#discussion_r4236016961)

File: `verl/workers/utils/padding.py` · line None

+1 to @jialei777's suggestion — I'd like the `_tpu_padded_values` handling to move out of core before this lands.

**`padding.py` / `losses.py`**

- `no_padding_2_padding` and `ppo_loss` now branch on a private attribute (`_tpu_padded_values`) that only the plugin's engine sets. That's a hidden contract between core and an out-of-tree engine: nothing in core documents or tests it, and any refactor of either function can silently break TPU.
- In `ppo_loss`, the TPU branch replaces `data` (a `TensorDict`) with a plain `dict`. It only works because the rest of the function happens to use `data[...]` and `data.get(...)`; anyone adding a `TensorDict` method call later will break TPU only.

Since the plugin already owns the TPU engine, it can hand `ppo_loss` a real `TensorDict` with `response_mask` / `old_log_probs` / `advantages` / `ref_log_prob` / `rollout_is_weights` already padded to the bucketed width on device, and return log_probs / entropy that `no_padding_2_padding` handles through its normal path. Then neither branch is needed in core.

**The assert relaxation (`==` → `<=`)**

This applies to every device, not just TPU. On GPU, `sequence_offsets[-1] != values.shape[0]` has always meant a real misalignment between the model output and the batch, and the strict check caught that. With `<=`, an output with extra rows now slices silently from the wrong offsets.

If trailing bucket padding really has to be allowed here, could we make it explicit (e.g. only allow extra rows when the caller says the output is bucket-padded) and add a small CPU unit test for both the exact and the padded case? Otherwise, please keep `==` and drop the trailing pad rows on the plugin side.
