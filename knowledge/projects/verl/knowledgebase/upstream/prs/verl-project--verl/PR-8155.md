# [hardware] feat: enable TPU GRPO with TorchTitan and vLLM via verl-hardware-plugin

[Upstream PR](https://github.com/verl-project/verl/pull/8155) · state: closed · merged: True

## Original PR description

### What does this PR do?

Adds `examples/tpu/grpo/run_qwen3_4b_torchtitan.sh` to run Qwen3-4B-Base GRPO on GSM8K using TorchTitan training, vLLM rollout, and `verl-hardware-plugin`.

Builds on [PR #50](https://github.com/jialei777/verl-upstream/pull/50). 


### API and Usage Example

On an existing Ray TPU cluster with the hardware plugin, model, and datasets available:

```bash
bash examples/tpu/grpo/run_qwen3_4b_torchtitan.sh
```

### Launch Script Recipe

- Default configuration: 250 training steps, 128 prompts per step, 16 responses per prompt, and 2048-token responses.
- Validates the full GSM8K test split before training and every 20 steps.
- Supports environment-variable overrides and additional Hydra arguments.

## Summary

We found nine serious and thirteen smaller findings. The most important problem is that the new placement pin makes any pool spanning more than one TPU slice impossible to place, and the 4B script's default asks for exactly that. The earlier review requests to move the TPU-specific handling out of core and to regenerate the generated trainer config are not repeated here.

## Serious findings

**1. A multi-slice pool can never be placed [verl/single_controller/ray/base.py]**
The new branch pins every bundle in a pool to one TPU slice resource, and the code then waits for the placement group with no timeout. The 4B script asks for 8x4 chips per role, which is more than one v6e-8 slice, so it waits forever instead of failing.
*Change:* Pin per slice, or fail with a clear message, and give the wait a timeout.

**2. Every TPU worker can be pinned to chip 0 [verl/single_controller/base/worker.py]**
When TPU_VISIBLE_CHIPS is absent the code defaults it to "0" and sets LOCAL_RANK and the device to 0 for every worker. The removed line used each worker's own Ray-assigned id.
*Change:* Keep the per-worker id when the variable is absent, instead of defaulting to chip 0.

**3. The platform hook never runs on an already-running Ray cluster [verl/plugin/platform/platform_base.py]**
The new ray.init hook is read only inside the main_ppo branch that runs when Ray is not yet initialized. On the existing cluster this pull targets, it is never applied, and the fallback launch applies no platform runtime environment.
*Change:* Apply the platform's runtime environment on the already-initialized path too.

**4. Core calls a platform method that is never declared [verl/single_controller/ray/base.py]**
Core calls auto_assign_accelerator_type on the platform, but PlatformBase does not declare it and nothing in this repo defines it. A TPU platform without it raises an AttributeError.
*Change:* Declare the method on PlatformBase with a default, or guard the call.

**5. The 0.6B script loads no plugin when run directly [examples/tpu/grpo/run_qwen3_0_6b_torchtitan.sh]**
The script exports VERL_PLATFORM but not VERL_USE_EXTERNAL_MODULES, so the plugin is never imported. The engine and checkpoint backend it asks for then fail to resolve. The 4B script does export it.

+1 to @jialei777's suggestion — I'd like the `_tpu_padded_values` handling to move out of core before this lands.

**`padding.py` / `losses.py`**

- `no_padding_2_padding` and `ppo_loss` now branch on a private attribute (`_tpu_padded_values`) that only the plugin's engine sets. That's a hidden contract between core and an out-of-tree engine: nothing in core documents or tests it, and any refactor of either function can silently break TPU.
- In `ppo_loss`, the TPU branch replaces `data` (a `TensorDict`) with a plain `dict`. It only works because the rest of the function happens to use `data[...]` and `data.get(...)`; anyone adding a `TensorDict` method call later will break TPU only.

Since the plugin already owns the TPU engine, it can hand `ppo_loss` a real `TensorDict` with `response_mask` / `old_log_probs` / `advantages` / `ref_log_prob` / `rollout_is_weights` already padded to the bucketed width on device, and return log_probs / entropy that `no_padding_2_padding` handles through its normal path. Then neither branch is needed in core.

**The assert relaxation (`==` → `<=`)**

This applies to every device, not just TPU. On GPU, `sequence_offsets[-1] != values.shape[0]` has always meant a real misalignment between the model output and the batch, and the strict check caught that. With `<=`, an output with extra rows now slices silently from the wrong offsets.

If trailing bucket padding really has to be allowed here, could we make it explicit (e.g. only allow extra rows when the caller says the output is bucket-padded) and add a small CPU unit test for both the exact and the padded case? Otherwise, please keep `==` and drop the trailing pad rows on the plugin side.
