# [rollout] fix: fall back to default continuous-token builder without Qwen ChatML tokens

[Upstream PR](https://github.com/verl-project/verl/pull/8311) · state: closed · merged: False

## Original PR description

### What does this PR do?

GRPO / any v1 rollout with **DeepSeek-R1-Distill-Qwen** models fails for every prompt with:

```
ValueError: Tokenizer does not define required token '<|im_end|>'
```

and validation then dies with the misleading `ValueError: Received an empty list as keys.`

Continuous Token builder selection is an exact lookup on the root `config.json` `model_type`, and `qwen2` maps to the Qwen ChatML builder. R1-Distill-Qwen reports `model_type: qwen2` but ships a DeepSeek tokenizer without the ChatML tokens.

This PR falls back to the default builder (with a warning) when the family was **auto-resolved** to a Qwen text family and the tokenizer does not define `<|im_end|>`. An explicit `model_family=qwen` still raises, so a real misconfiguration is not hidden.

### API and Usage Example

No API change. `model_family="auto"` (the default) now degrades gracefully for Qwen-architecture models with a non-ChatML tokenizer; `model_family="qwen"` keeps the strict check.

### Design & Code Changes

- `verl/utils/tokenizer/continuous_token_wiring.py`: when the family was auto-resolved to a Qwen text family and `_tokenizer_defines_token(tokenizer, "<|im_end|>")` is false, log a warning and use the default builder.
- `verl/utils/tokenizer/continuous_token.py`: `require_token_id` also treats a tokenizer's `unk_token_id` as missing (HF tokenizers with an unk token return it for unknown strings instead of `None`), including when the id comes back wrapped in a one-element list. The unk token itself is still accepted.
- `tests/utils/test_continuous_token_on_cpu.py`: new cases listed above.

- wuxibin89 · comment · 2026-11-04T03:45:56Z · [source](https://github.com/verl-project/verl/pull/8311#issuecomment-6621982492)

I think the fallback target is not safe yet. Missing `<|im_end|>` proves that the tokenizer does not implement Qwen ChatML, but it does not prove that `ContinuousTokenBuilder` implements the checkpoint's conversation protocol.

In particular, #7637 already documents a concrete regression for `DeepSeek-R1-0528-Qwen3-8B`: its tool template concatenates `function['arguments']` as a string. The default builder creates synthetic tool-call arguments as `{}`, while `DeepSeekContinuousTokenBuilder` uses `"{}"` (from #7630). With this PR, that checkpoint will construct successfully and then fail on the first tool append with a `TypeError`. The GSM8K E2E run does not exercise tools, and the PR explicitly says that default-builder token boundaries were not evaluated.

There is a second issue in `_tokenizer_defines_token`: catching every `ValueError` from `require_token_id` also treats malformed results (multiple IDs, negative IDs, wrong types) as “token absent” and silently falls back. Only an explicit missing/unk-token condition should be recoverable; tokenizer contract errors should still surface.

I suggest keeping the `unk_token_id` validation, but not merging the generic default fallback. Safer options are:

1. expose/use an explicit `continuous_token.model_family` override and fail with actionable guidance (the direction previously preferred on #7638/#7639); or
2. if automatic routing is desired, use an exact DeepSeek tokenizer-protocol signature (`<｜end▁of▁sentence｜>` and `<｜Assistant｜>` present, `<|im_end|>` absent) and select `DeepSeekContinuousTokenBuilder`, not the default builder.

Whichever route is chosen should add template-equivalence tests comparing incremental rendering with full `apply_chat_template`, including first and later tool turns for R1-0528-Qwen3 and the older R1-Distill-Qwen checkpoints. The later-turn `is_output_first` gap tracked in #7636 also still needs consideration.
