# [trainer] fix: exclude valid=0 NaN placeholders from rollout_probs_diff aggregation

[Upstream PR](https://github.com/verl-project/verl/pull/8538) · state: open · merged: False

## Original PR description

### What does this PR do?

Fixes #8504.

**Root cause.** In the V1 `MetricsAggregator`, `rollout_probs_diff_mean` goes through the `weighted_avg` reduction while `rollout_probs_diff_valid` goes through `last` (verl/trainer/ppo/v1/utils.py:52-55,105-124). On steps with an empty response mask, the emitter sends a `(valid=0, mean=NaN)` placeholder (verl/utils/debug/metrics.py:110-113). `NaN * 0` weight is still `NaN`, so the placeholder poisons the aggregated mean, while the validity flag only reports the final local step — the emitted "valid" flag disagrees with the mean it is supposed to qualify.

**Fix.** All changes are confined to the aggregator (`verl/trainer/ppo/v1/utils.py`):
- Aggregate the validity flag with `max` (1 when any local step was valid), so it covers the same steps as the mean.
- In the `weighted_avg`/`max` reductions, drop entries whose companion `*_valid` flag is 0, together with their weights; nonfinite values from `valid=1` steps are deliberately kept so genuine numerical failures stay observable (no nanmean-style hiding).

Test updates/additions are confined to `tests/trainer/ppo/v1/test_metrics_aggregator_on_cpu.py`: the previously pinned "last" semantics of the validity flag were updated, and 4 regression cases for issue #8504 were added (weighted-mean poisoning, zero-sample-weight placeholder, genuine nonfinite value from a valid step, all-invalid steps), plus a `max` placeholder case.

### API and Usage Example

No API change: `MetricsAggregator.add_step_metrics` / `get_aggregated_metrics` signatures and emitted metric names are unchanged.

```python
agg = MetricsAggregator()
agg.add_step_metrics({"training/rollout_probs_diff_mean": 0.01, "training/rollout_probs_diff_valid": 1}, sample_count=1)
agg.add_step_metrics({"training/rollout_probs_diff_mean": float("nan"), "training/rollout_probs_diff_valid": 0}, sample_count=0)  # empty-mask placeholder
agg.add_step_metrics({"training/rollout_probs_diff_mean": 0.02, "training/rollout_probs_diff_valid": 1}, sample_count=1)
agg.get_aggregated_metrics()
# before: training/rollout_probs_diff_mean = nan, training/rollout_probs_diff_valid = 1
# after:  training/rollout_probs_diff_mean = 0.015, training/rollout_probs_diff_valid = 1
```

### Design & Code Changes

- `verl/trainer/ppo/v1/utils.py`: move `training/rollout_probs_diff_valid` into the `max` bucket; add `_validity_mask()` which resolves a metric's companion `*_valid` flag (stripping `_mean`/`_std`/`_max`/`_min`/`_avg` suffixes) and apply it in `weighted_avg` (entry + weight dropped, NaN if no entries remain) and `max` (entries dropped, NaN if none remain). The `_valid` metrics themselves are exempted from masking.
- `tests/trainer/ppo/v1/test_metrics_aggregator_on_cpu.py`: update the validity-flag semantics test and add the regression cases listed above.

Thanks to the automated review (@chatgpt-codex-connector) for catching this — the P2 finding is a real correctness issue and is fixed in 2efa20c.

**The problem:** `_aggregate_single_metric`'s `max` branch (`verl/trainer/ppo/v1/utils.py`) filtered out `valid=0` NaN placeholders but then called plain `max()`, and Python's `max()` returns the first comparable value when a NaN is present (`max([0.03, nan]) -> 0.03`). So a genuine NaN emitted by a `valid=1` step could be reported as a finite `rollout_probs_diff_max`, diverging from the upstream behavior this PR replaces.

**The fix:** after the validity filter, if any retained value is nonfinite (`value != value`), the aggregation now returns `NaN` so the failure stays observable, matching the documented intent that nonfinite values from valid steps are deliberately kept.

**Tests:** added `test_valid_step_nan_is_not_swallowed_by_max` covering exactly the reviewed sequence `(valid, max) = [(0, NaN), (1, 0.03), (1, NaN)]`; it fails against the previous code and the full file passes after the fix:
