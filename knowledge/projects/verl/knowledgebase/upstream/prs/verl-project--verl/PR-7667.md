# [rollout] fix: make GlobalRequestLoadBalancer full_determinism cross-process reproducible

[Upstream PR](https://github.com/verl-project/verl/pull/7667) · state: open · merged: False

## Original PR description

### What does this PR do?

Fixes #7666.

Under `full_determinism=True`, `GlobalRequestLoadBalancer` in `verl/workers/rollout/router.py` previously routed requests via `list(self._servers)[hash(request_id) % len(self._servers)]`.

This caused non-deterministic request-to-replica distribution across runs and worker processes due to:
1. Python's built-in `hash(str)` utilizing a process-randomized seed (`PYTHONHASHSEED`), producing different values in separate Python processes or subsequent runs.
2. `list(self._servers)` depending on dictionary insertion order.

This PR replaces `hash()` with `zlib.crc32()` over `sorted(self._servers.keys())`, ensuring platform- and process-independent deterministic routing (consistent with the determinism strategy in `verl/experimental/reward_loop/router/naive_router.py`).

- mynotwo · comment · 2026-10-26T19:34:14Z · [source](https://github.com/verl-project/verl/pull/7667#discussion_r4381612376)

File: `verl/workers/rollout/router.py` · line None

One concern with `sorted(self._servers.keys())`. The keys are `server_address` strings (`f"{ip}:{port}"`), and the port comes from `get_free_port`, so it changes from run to run. Sorting by address makes the index→replica mapping depend on those ports. The insertion order it replaces follows `server_addresses`, which is in replica rank order.

I checked this with a small simulation. It used 4 replicas on 2 nodes and 64 `det-{i}` ids, with ports redrawn in each of 20 runs and `PYTHONHASHSEED` pinned the way `main_ppo` does it:

| | same request grouping across runs | same request → replica-rank map |
|---|---|---|
| main (`hash` + insertion order) | 20/20 | 20/20 |
| this PR (`crc32` + sorted address) | 20/20 | 7/20 |

Which requests are batched together is unaffected. On homogeneous replicas with `VLLM_BATCH_INVARIANT=1`, outputs should not change either. But the PR describes "the same request always routes to the same replica across runs", and under that reading, replica identity becomes less stable than before. Replica identity matters on mixed hardware, and when per-replica logs are compared across runs.

Suggestion: keep `crc32`, but index into insertion order (`list(self._servers)`) rather than sorted addresses, or sort by a stable replica rank if one is available. The insertion-order test could then check that rank order is preserved rather than ignored. Happy to share the simulation script if useful.
