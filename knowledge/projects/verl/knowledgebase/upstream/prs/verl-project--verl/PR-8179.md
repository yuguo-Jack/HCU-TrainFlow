# [rollout, vllm] feat: pin each multi-turn session to one vLLM DP rank

[Upstream PR](https://github.com/verl-project/verl/pull/8179) · state: closed · merged: True

## Original PR description

### What does this PR do?

With a vLLM rollout replica that has `data_parallel_size > 1` (e.g. DP + EP inside one server), each DP engine has its own prefix cache. `LLMServerClient` sends every turn under a fresh uuid and no DP rank, so vLLM's internal DP load balancer picks the least-loaded engine per request, and the turns of a multi-turn session land on different DP ranks and miss their prefix cache.

`LLMServerClient` now forwards the sticky caller id as `session_id`. `vLLMHttpServer` turns it into `data_parallel_rank = crc32(session_id) % data_parallel_size` using its own DP size and passes it to `AsyncLLM.generate` (the in-process equivalent of the `X-data-parallel-rank` header vLLM's OpenAI server accepts from routers). `_pd_dispatch` forwards `session_id` to both PD legs, so each server pins with its own DP size. No config; DP == 1 is unchanged, and SGLang / TRT-LLM accept `session_id` as a no-op.

### Test

Nemotron-H 30B-A3B, SWE-bench Pro multi-turn agent replay on GB200, one DP4/EP4 vLLM server per node: prefix-cache hit rate went from 0.81 to 0.86 and long sessions finished 10-15% faster. In a full RL run with pinning, the cumulative hit rate was 0.93.

### Design & Code Changes

- `llm_server.py`: pass `session_id=request_id` to `server.generate`; the client stays backend-agnostic.
- `vllm_async_server.py`: `_dp_rank_for_session()` (CRC32 is stable across processes, unlike `hash()`; hash pinning ignores engine load, which is fine with many concurrent sessions per replica). `generate()` passes the rank to the engine; `_pd_dispatch()` forwards `session_id` to the prefill and decode legs.
- `async_sglang_server.py`, `trtllm_async_server.py`: accept `session_id` (unused for now).

Replica-level stickiness is unchanged (`GlobalRequestLoadBalancer` still maps a session to one replica); this adds the same stickiness inside a DP > 1 replica.

- wuxibin89 · COMMENTED · 2026-10-10T03:14:13Z · [source](https://github.com/verl-project/verl/pull/8179#pullrequestreview-5477314949)

Thanks, the motivation and numbers make sense. One design suggestion: I'd prefer to move the DP-rank selection out of `LLMServerClient` and into `vLLMHttpServer`, and have the client just forward the session identity.

**Proposal**

- `LLMServerClient.generate` passes `session_id=request_id` (the sticky caller id) to `server.generate.remote(...)`, without knowing anything about vLLM or DP.
- `vLLMHttpServer.generate(..., session_id: Optional[str] = None)` turns it into a rank using its own config:

```python
def _dp_rank_for_session(self, session_id: Optional[str]) -> Optional[int]:
    # Pin a session to one DP engine so its turns hit the same prefix cache.
    dp_size = self.config.data_parallel_size
    if session_id is None or dp_size <= 1:
        return None
    return zlib.crc32(str(session_id).encode()) % dp_size
```

and passes `data_parallel_rank=self._dp_rank_for_session(session_id)` to `self.engine.generate(...)`. `_pd_dispatch` forwards `session_id` to both legs instead of a precomputed rank.

**Why**

1. **Each server uses its own DP size.** The server already has `self.config.data_parallel_size`. In the current version the client reads the global `actor_rollout_ref.rollout.data_parallel_size`, and the rank computed for the prefill server is reused unchanged. Moving the computation into the server keeps the rank always consistent with the engine that actually runs it.
2. **PD decode leg.** Right now only the prefill leg is pinned; `decode_peer.generate.remote(...)` gets no rank, so a DP>1 decode server still scatters a session's turns. Forwarding `session_id` to the decode peer lets it pin with its own DP size for free.
3. **The client stays backend-agnostic.** `llm_server.py` already has a growing number of `rollout.name == "vllm"` branches (`priority_kwargs`, the sglang video handling). Engine-specific routing fits better next to the engine. Since the sglang/trtllm `generate` signatures don't take `**kwargs`, I'd add a no-op `session_id: Optional[str] = None` to them as well, so the client can pass it unconditionally. SGLang can later use it the same way for its own DP routing.

**Minor / FYI (not blocking)**

- Pure hash pinning ignores load. That's fine with many concurrent sessions per replica, but with few long sessions per replica the DP ranks can become noticeably imbalanced. Worth a sentence in the docstring.
- The GRPO `n` samples of one prompt have different `request_id`s, so they now spread across DP ranks deterministically rather than by load. Their shared prompt prefix gets prefilled once per rank either way, so this is no worse than today. Just noting it in case grouping by prompt uid is ever wanted.
