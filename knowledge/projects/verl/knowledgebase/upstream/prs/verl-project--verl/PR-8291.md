# [trainer, perf] feat: wake ReplayBuffer on prompt completion instead of 2 s polling

[Upstream PR](https://github.com/verl-project/verl/pull/8291) · state: closed · merged: False

## Original PR description

### What does this PR do?

`ReplayBuffer._wait_for_next_poll()` sleeps a hard-coded `poll_interval=2.0` between TransferQueue metadata syncs (used
by both the sync `sample()` and the async `wait_for_sampleable()`). The trainer therefore notices the last finished
prompt up to 2 s late, and `timing_s/gen` is quantized to multiples of 2 s (main, vLLM: 2.21, 4.21, 4.21, 2.21 … s;
SGLang: 2.28 s every step). This PR replaces the sleep with a wait on a small completion counter that rollout workers
bump when a prompt reaches a terminal status. On 8x MI355X GSM8K GRPO it cuts `timing_s/gen` by 22–31% and step time by
~10%, with no extra TransferQueue metadata traffic.

With this PR `timing_s/gen` is no longer quantized (1.65–2.49 s). Notify-to-wake latency is ~1.4 ms. The gain is
largest for short steps (small models, short rollouts, async / frequent weight sync); for 40 s+ steps it is ≤ ~2 s/step.

### API and Usage Example

No user-facing API or config change. `poll_interval` keeps its meaning as the maximum wait between syncs (now a
fallback timeout). Internally `_wait_for_next_poll()` gains an optional `need: int = 1` argument, so existing
subclasses that call or override it keep working.

### Design & Code Changes

- `CompletionNotifier` (async Ray actor, `num_cpus=0`): per-partition counter + `asyncio.Condition`.
- `completion_notifier()`: process-wide handle to the named actor (`get_if_exists=True`), cached per Ray job id and
  shared by producers and the replay buffer, so it outlives individual `ReplayBuffer` instances.
- `AgentLoopWorkerTQ._run_prompt`: after publishing the terminal status (`finished` / `failure`), call
  `notify(partition_id)` (best effort).
- `_wait_for_next_poll(..., need)`: wait until the counter grows by `need` — prompts still missing, or the in-flight
  count while DAPO drains — or until `poll_interval`. The counter kept from the previous wake is read before the
  caller's next metadata sync and producers notify only after the status write is acknowledged, so a wake can be early
  (one extra sync) but never late. Waiting for `need` instead of every completion keeps metadata syncs at ~2 per
  `sample()` (waking on every completion gave the same speedup but 43–65 syncs).
- If the notifier is unavailable (no Ray, actor died) the wait falls back to `time.sleep(poll_interval)`, i.e. the
  current behavior.
