# [tool] feat: integration to a variety of different multi-turn, tool-use environments via benchmax

[Upstream PR](https://github.com/verl-project/verl/pull/2792) · state: open · merged: False

## Original PR description

### What does this PR do?

This PR adds supports for `benchmax` environments. 

[benchmax](https://github.com/cgftinc/benchmax) is a training-framework-agnostic OSS RL environment library, consisting of a variety of **multi-turn, tool-use** environments ranging from spreadsheets to CRMs, we’re working on many more. This PR allows `verl` users to seamlessly access & train with those environments.

**Summary of what’s implemented**

- `verl/workers/reward_manager/benchmax.py`  implements a new Reward Manager that maps a `benchmax` environment’s rewards to a `verl` RewardManager.
- `verl/tools/benchmax_tool.py` maps tools in a `benchmax` environment to a list of `verl` `BaseTool` instances
- We also modify `verl/workers/rollout/sglang_rollout/sglang_rollout.py` with the following changes:
    
    ```bash
    first_tool = self._tool_map[list(self._tool_map.keys())[0]]
    if isinstance(first_tool, BenchmaxToolAdapter):
        workspaces = [
            first_tool.get_rollout_workspace(req.request_id) for req in sorted_output_req_list
        ]
        non_tensor_batch["workspaces"] = np.array(workspaces, dtype=object)
    ```
    
    - In `benchmax`, we store each rollout’s state in different `workspaces` to allow for rollout parallelization. E.g. for the spreadsheet agent, each rollout has a different spreadsheet being edited. This state is sometimes used during reward calculation (e.g. ensuring the final state of the spreadsheet satisfies the prompt to the agent). We add these `workspaces` to `non_tensor_batch` to ensure that the reward functions know which workspace to compute the reward for.
- `examples/data_preprocess/benchmax_data_process.py`  implements a data processing scripts that takes `benchmax` environment’s dataset, applies it’s preprocessing & dumps it into `verl` compatible parquet files

**Examples**

We’ve also added example scripts to show how to use `benchmax` environments seamlessly.

`examples/sglang_multiturn/benchmax/run_qwen2.5-3b_benchmax_math.sh`

- The core things we defined are:
    - `BENCHMAX_CLASS_NAME="benchmax.envs.wikipedia.math_env.MathEnv”` to define the `benchmax` environment to pull from.
    - `TOOL_CONFIG="$CONFIG_PATH/tool_config/benchmax_math_tool_config.yaml"` path to the tool config for `verl` to initialize the tools from
        
        ```bash
        # Example Benchmax Tool Config
        tools:
          # Class name points to benchmax class. This is expected to be a subclass of envs.BaseEnv
          - class_name: benchmax.envs.wikipedia.math_env.MathEnv
            config:
              type: benchmax
              # Specify initialization args for Sandbox here e.g. api_keys
        ```
        
    - `reward_model.reward_manager=benchmax`  reward_manager is set to `benchmax`
    

We believe this would be a great addition to the `verl` community & allow folks to more easily try different RL environments easily!

The `break` statement here will cause the `for` loop over `tools_config.tools` (from line 100) to terminate after processing the first `BENCHMAX` tool. If the configuration file contains other tool definitions after the `BENCHMAX` one, they will be ignored. This is likely unintended and could lead to incomplete tool initialization. The `break` statement should be removed to ensure all tools in the configuration are processed.

- gemini-code-assist[bot] · comment · 2025-07-29T04:58:00Z · [source](https://github.com/verl-project/verl/pull/2792#discussion_r2238524200)

File: `verl/workers/reward_manager/benchmax.py` · line 71

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The `data_item.non_tensor_batch.get("workspaces", "")` call defaults to an empty string if `workspaces` is not present. Subsequently, `Path("")` resolves to the current working directory. If a reward function relies on a specific workspace and it's not provided, it might read from or write to the current directory. This could lead to unexpected behavior, data corruption, or race conditions, especially in a parallel execution environment. It would be safer to handle an empty workspace path explicitly, for example, by raising an error if a workspace is required but not provided.
