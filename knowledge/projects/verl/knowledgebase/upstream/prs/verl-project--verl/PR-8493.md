# [megatron] fix: keep ranks in lockstep during the HF weight export

[Upstream PR](https://github.com/verl-project/verl/pull/8493) · state: open · merged: False

## Original PR description

### What does this PR do?
Prevents the 30-minute NCCL/gloo timeout during Megatron weight sync. No rank raises an exception: the sync hangs in `gather_from_ep_ranks` or `broadcast_obj_from_pp_rank` until the timeout kills the job.

### Why
Each tensor of the Megatron HF export is assembled by a chain of PP/EP/TP collectives, but consumers drive the generator asymmetrically: the checkpoint-engine master buckets and broadcasts between pulls, while other ranks discard the tensor and pull the next one. The drift explanation is inferred from the logs (a 63-collective gap between enqueued and completed work on the PP group); the barrier stopping the hang is observed.

### Change
Adds `lockstep_per_tensor_param`, which runs a barrier after the consumer finishes each tensor, around the `export_hf_weights` branch of `MegatronEngine.get_per_tensor_param`. Adapter-only exports and other backends are unchanged: a per-tensor barrier requires every rank to yield the same number of tensors, and only Megatron is validated.

### Tests
- Unit tests in `tests/checkpoint_engine/test_sharded_delta.py`; pre-commit passes.
- Cluster: GLM-5.1 and DeepSeek-V3 with TP=4 PP=3 EP=8. The hang hit about 1 run in 2 before the barrier and has not recurred since, on up to 480 trainer ranks. Measured on the `delta_sharded` seed sync only (about 140 s vs 80-130 s), on a v0.9.0-based implementation.

As requested we validated on the ordinary NCCL weight sync, with and without this PR, over repeated syncs (6 steps, parameter_sync_step: 1, so 7 syncs including init). 
Setup:
- verl v0.9.1 + #7661, Qwen2.5-3B, Megatron TP2/PP2 on 8 trainer GPUs, standalone SGLang TP4, GH200.

Both runs finished all 6 steps, with no hang or NCCL timeout. Rank 0's send time goes from ~0.29 s to 0.40 s per sync (~0.25 ms per tensor). timing_s/update_weights is 1.59 s vs 1.61 s and timing_s/step 3.31 s vs 3.32 s, the same within noise.

At this scale the baseline doesn't deadlock, so this shows the barrier is safe and costs little on the nccl path.
It doesn't reproduce the drift by itself. The drift showed up at 288–480 ranks with PP3/EP8: it was observed directly on the delta_sharded seed, and with the same signature (gather_from_ep_ranks timeouts) on the ordinary NCCL weight sync; with the barrier, the delta_sharded seed passed in every run that reached it.
