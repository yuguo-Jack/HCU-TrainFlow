## Original PR description

What does this PR do?
[worker, rollout] fix: integrate DeepSpeed as a training backend in verl, supporting dp+sp mixed parallelism, LoRA, ZeRO-1/ZeRO-2 with optional offload; align rollout batch scaling with dp*sp and clean async initialization for better parity with FSDP.
Purpose: bring DeepSpeed integration to parity with FSDP in batch semantics and async rollout stability.
Checklist Before Starting
 Similar PR search: https://github.com/volcengine/verl/pulls?q=deepspeed+rollout
 Title format example: [worker, rollout] fix: align deepspeed batch scaling with dp*sp
Test
Manual runs (Qwen2.5-0.5B):
dp=2, sp=1/2 async vLLM: steps run successfully; batch scaling matches dp*sp semantics.
LoRA smoke (lora_rank=8, target_modules=all-linear): load + weight sync + generation complete; first step still dominated by long sequences (expected).
No new CI tests added; manual validation only.
API and Usage Example
python3 -m verl.trainer.main_ppo -cn ppo_trainer \
  actor@actor_rollout_ref.actor=deepspeed_actor critic=deepspeed_critic \
  actor_rollout_ref.actor.strategy=deepspeed \
  actor_rollout_ref.rollout.name=vllm \
  actor_rollout_ref.rollout.mode=async \
  actor_rollout_ref.actor.ulysses_sequence_parallel_size=2 \
  critic.ulysses_sequence_parallel_size=2 \
  actor_rollout_ref.actor.ppo_mini_batch_size=128 \
  actor_rollout_ref.actor.ppo_micro_batch_size_per_gpu=16 \
  critic.ppo_mini_batch_size=128 \
  critic.ppo_micro_batch_size_per_gpu=16 \
  # add data/model overrides as needed
Batch scaling is handled automatically by dp*sp; no API changes.
Design & Code Changes
Batch normalization: per_rank_mini = ppo_mini_batch_size // (dp*sp), train_batch_size = micro_bsz * GAS * dp * sp; removes redundant per-dp scaling, GAS aligned with micro batches.
Async cleanup: removes noisy debug prints; clarifies dp*sp scaling comments.
Supports dp+sp, LoRA, ZeRO-1/2 with optional offload in the DeepSpeed worker; vLLM async rollout remains the inference path.

## Code Review

This pull request introduces a comprehensive integration of DeepSpeed as a training backend, bringing it to parity with the existing FSDP implementation. The changes are extensive, adding new configurations, worker implementations, and utility modules for checkpointing and managing different parallelism strategies (DP+SP). The code is well-structured, with clear separation of concerns, such as centralizing parallelism logic in `deepspeed_parallel.py` and providing sharding managers for different rollout engines. The addition of `DeepSpeedCheckpointManager` is a key component for ensuring training state can be saved and restored reliably.

I've found one critical issue related to an incorrect import path in the checkpoint manager that could lead to silent failures when parameter offloading is enabled. Other than that, the changes look solid and well-thought-out.

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The import path for `load_deepspeed_model_to_gpu` and `offload_deepspeed_model_to_cpu` is incorrect. It points to a non-existent file `verl.workers.engine.deepspeed.offload_utils`, and the `except Exception` block provides a no-op fallback. This will cause silent failures when parameter offloading is enabled with ZeRO, as the model's parameters will not be moved to the GPU before saving the checkpoint, potentially leading to corrupted or unusable checkpoints. This is a critical correctness bug.

The correct implementations for these functions are available in `verl/utils/deepspeed_utils.py`, which is also added in this pull request. Please correct the import path and narrow the exception to `ImportError`.

```suggestion
    from verl.utils.deepspeed_utils import (
        load_deepspeed_model_to_gpu,
        offload_deepspeed_model_to_cpu,
    )
except ImportError:  # pragma: no cover

    def load_deepspeed_model_to_gpu(engine):  # type: ignore
        return

    def offload_deepspeed_model_to_cpu(engine):  # type: ignore
        return
```
