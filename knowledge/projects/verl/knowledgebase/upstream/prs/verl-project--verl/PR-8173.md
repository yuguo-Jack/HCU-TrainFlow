# [perf, training_utils] fix: don't annotate unit strides as tl.int64 in fused kernels

[Upstream PR](https://github.com/verl-project/verl/pull/8173) · state: closed · merged: True

## Original PR description

### <p>Slop free TLDR:</p>
<p>Annotating the inner strides in with <code>tl.int64</code> makes the triton compiler unable to recognize if the stride is equal to 1. This info is needed to decide if the addresses are contiguous, so the current code causes failures in vectorization/coalescing memory access.</p>
<p>This is particularly bad on Ampere, which doesn’t have TMA so the load/store of tensor descriptors defaults to the generic pointer path, and the linear cross entropy kernels are measured up to 40-50x slower end to end on A100s. On Hopper/Blackwell the speed up are more modest but still noticeable.</p>
<p>This PR fix this issue by removing the tl.int64 annotation for the inner strides. The annotations for outer strides are kept so that the address calculation would still be in 64 bit.</p>

<h3><strong>What does this PR do?</strong></h3>
<p>#4576 found that the pointer-based path of the <code>linear_cross_entropy</code> kernels &quot;shows poor performance on Hopper GPU&quot; because of &quot;heavy address calculation&quot;, and switched Hopper and newer GPUs to TMA. This PR fixes the cause, which also speeds up the pointer path (A100, Ada, AMD) and the parts of the Hopper/Blackwell path that still use plain pointers.</p>
<p><strong>Cause.</strong> <code>verl/utils/kernel/kernels.py</code> annotates every stride as <code>tl.int64</code>. Since Triton 3.3, an int-annotated argument equal to 1 is no longer specialized to a constant (triton-lang/triton#5512). So the compiler can't prove that the tiles are contiguous and emits one scalar 16-bit load or store per element instead of 128-bit vector accesses. Triton's maintainers consider this intended and recommend not annotating unit strides (triton-lang/triton#9834).</p>
<p><strong>Fix.</strong> Remove <code>: tl.int64</code> from the strides that are always 1: the contiguous dims of the 2D tensors and the 1D per-token tensors. The host code asserts <code>is_contiguous()</code> on every input. The outer strides keep <code>tl.int64</code>, so every 2D address is still computed in 64 bits.</p>

<p><strong>Where the speedup comes from.</strong></p>
<ul>
<li><strong>A100 (pointer path).</strong> In the forward GEMM loop, main issues 48 scalar <code>ld.global.b16</code> per thread per K step; this PR issues 6 × 16-byte <code>cp.async</code>, and the loop shrinks from 414 to 160 instructions. With one 64-bit pointer per element live across the loop, main also runs out of registers: ptxas falls back to 32 registers with about 9 KB of spills per thread, compared with 255 registers and under 1 KB of spills with this PR. That is why the gap is much larger than vectorization alone would give.</li>
<li><strong>H100 / B200 (TMA path).</strong> The forward GEMM already uses TMA, so the forward pass is unchanged. In the backward <code>d_logits</code> kernel, the stores go from 128 × <code>st.global.b16</code> to 16 × <code>st.global.v4.b32</code> and its register spills (1.1–1.7 KB on main) disappear (H100: 27.8 → 19.5 ms for that kernel).</li>
</ul>
<h3><strong>Design &amp; Code Changes</strong></h3>
<ul>
<li><code>verl/utils/kernel/kernels.py</code>: drop <code>: tl.int64</code> from 70 unit-stride parameters, keep it on the outer strides, and add a comment explaining why. No kernel logic, TMA path or host code changes.</li>
</ul>
<p><strong>Overflow safety.</strong> Triton promotes integers per binary op, so <code>offs_m[:, None] * stride_m</code> stays in i64. The remaining i32 offsets are each bounded by a single dimension (<code>hidden_size</code>, <code>vocab_per_split</code> or <code>num_tokens</code>).</p>
<p><strong>Known caveat.</strong> <code>_Total_Fuse_MN</code>'s backward kernel, which nothing in verl selects, now needs 112 KB of shared memory. It no longer launches on GPUs with about 100 KB per block (sm_86 / sm_89, e.g. A10, L40S). I can lower its <code>num_stages</code> here if reviewers want.</p>
