Thanks for the update! One suggestion on `verl/trainer/config/transfer_queue/transfer_queue.yaml`: the mirrored TQ config is getting quite long, and I think we can keep it minimal, similar to how `rollout.yaml` handles `engine_kwargs` (only `vllm: {}` / `sglang: {}` are declared, everything else is passed through via `++`, e.g. `+actor_rollout_ref.rollout.engine_kwargs.vllm.compilation_config.cudagraph_mode="FULL_DECODE_ONLY"`).

**Why this is safe:** verl never reads the TQ sub-keys itself; it just forwards the whole node via `tq.init(config.transfer_queue)` (`verl/trainer/main_ppo.py`). And `tq.init` already merges the user conf on top of TQ's packaged `config.yaml`:

```python
default_conf = OmegaConf.load(resources.files("transfer_queue") / "config.yaml")
final_conf = OmegaConf.merge(final_conf, default_conf)
if conf:
    final_conf = OmegaConf.merge(final_conf, conf)
```

So any key we copy verbatim from TQ's defaults is redundant, and it has to be re-synced on every TQ bump (this PR is basically that sync). Comparing with TQ v0.1.11 `config.yaml`, the following are **identical to TQ defaults** and can be dropped:

- `controller.sampler`, `controller.polling_mode`
- `SimpleStorage.total_storage_size` (null), `required_node_resource`, the whole `ssd_offload` block
- `MooncakeStore.local_hostname` (""), `protocol`, `global_segment_size`, `local_buffer_size`, `device_name`, the whole `offload` block, `use_gdr`, `gdr_staging_buffer_mb`

What actually **differs from TQ defaults** (i.e. verl-specific choices worth keeping explicit) is just:

| key | verl | TQ default |
|---|---|---|
| `SimpleStorage.num_data_storage_units` | 8 | 2 |
| `MooncakeStore.auto_init` | false | true |
| `MooncakeStore.metadata_server` | P2PHANDSHAKE | localhost:50050 |
| `MooncakeStore.master_server_address` | localhost:50124 | localhost:50051 |
| `MooncakeStore.hard_pin` | true | null |

Suggested shape:

```yaml
# Whether to enable TransferQueue
enable: False

# Metrics configuration for TransferQueue
metrics:
  # If true, exposes Prometheus-style metrics via an HTTP /metrics endpoint.
  enabled: false
  # HTTP port for the /metrics endpoint (0 = auto-assign a free port)
  port: 0

# Pluggable storage and transport backend for TransferQueue.
# Only verl-specific overrides are listed here; all other options fall back to
# TransferQueue's default config.yaml and can be set via `++transfer_queue.<key>=<value>`, e.g.
#   ++transfer_queue.backend.SimpleStorage.ssd_offload.enabled=true
#   ++transfer_queue.backend.MooncakeStore.protocol=rdma
backend:
  # Storage backend type. Options: SimpleStorage, MooncakeStore
  storage_backend: SimpleStorage
  SimpleStorage:
    # Number of distributed storage units. Recommended: >= 2 x number of nodes.
    num_data_storage_units: 8
  MooncakeStore:
    # Whether TQ should automatically start mooncake_master (kills any existing one when true).
    auto_init: false
    # Address of the metadata coordination server ("P2PHANDSHAKE" for multi-NIC environments).
    metadata_server: P2PHANDSHAKE
    # Address of the Mooncake master server.
    master_server_address: localhost:50124
```

The `_generated_*.yaml` diffs would shrink accordingly, and future TQ bumps would mostly be version-only changes.

**Side note on `hard_pin: true`:** the comment says "Set to null to disable hard pinning when offload is enabled and enable it otherwise", but with verl explicitly setting `true`, enabling `MooncakeStore.offload.enabled=true` would keep everything hard-pinned, so eviction to SSD can't happen. Is `true` intentional here? If not, I'd just drop it and inherit TQ's `null` (auto) default.
