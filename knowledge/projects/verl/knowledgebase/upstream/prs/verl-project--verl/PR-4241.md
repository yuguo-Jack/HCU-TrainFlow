# [BREAKING][trainer, worker] feat: multi generative reward models

[Upstream PR](https://github.com/verl-project/verl/pull/4241) · state: open · merged: False

## Original PR description

### What does this PR do?

This PR add support for multiple reward models. The current implementation assumes one reward model. However, it can be useful to have different models running asynchronously in separate servers for specific reward tasks.

This is primarily done through the modification of the `AgentLoopWorker` in `verl/experimental/agent_loop/agent_loop.py` , so that it manages multiple instances of `RewardModelManager` and `RewardManagerWorker` through a dictionary with unique reward model name keys as defined in the configuration. An example configuration is provided in `recipe/mgrm`.

### API and Usage Example

The configuration of `reward_model` changes.
- When `reward_model.enable` is set to `False`: only the `reward_model.reward_manager` needs to be set, it selects which `RewardLoopManager` will run the reward functions without using reward models.
- When `reward_model.enable` and `reward_model.enable_resource_pool` are set to `True`: instead of directly defining the `RewardModelConfig` in the `reward_model` config, each reward model needs to be defined with a unique key, inside the `reward_model.reward_models` dict. This is true even when you're only using one reward model. `reward_model.reward_manager` will be ignored, and instead each model will have its own reward manager defined under their config.

Example:
```yaml
reward_model:
    enable: True
    enable_resource_pool: True
    reward_manager: naive
    reward_models:
        qwen:
              _target_: verl.workers.config.RewardModelConfig
              reward_manager: naive
              n_gpus_per_node: 4
              nnodes: 1
              ...
        openaioss:
              _target_: verl.workers.config.RewardModelConfig
              reward_manager: naive
              n_gpus_per_node: 4
              nnodes: 2
              ...
```
A cleaner alternative that defines each model in its own file is available in `recipe.mgrm`.

### How to convert to the new format if you use reward models.

`recipe.fapo` has already been refactored to the new format. Please look at the diff to see how to use the new config format, and how to override the format via the the `run_fapo_7b.sh` and `run_fapo_32b.sh` files.

### Reward score aggregation logic

For now it is a simple mean score of all reward models. It is defined in `verl/experimental/agent_loop/agent_loop.py` l.569

```Python
output.reward_score = sum(result["reward_score"] for result in results) / len(results)
```

### Future modifications

1. Add logic to choose a custom reward score function per reward_model to separate them per task. For now they all use the same `custom_reward_function.path` and `custom_reward_function.name` in the config.
2. Add logic to define custom aggregation, instead of the hardcoded mean in `agent_loop.py`.
