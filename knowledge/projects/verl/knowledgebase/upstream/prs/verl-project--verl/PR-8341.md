# [rollout, fully_async] fix: keep backend extra_fields across FullyAsyncLLMServerClient resumes

[Upstream PR](https://github.com/verl-project/verl/pull/8341) · state: open · merged: False

## Original PR description

### What does this PR do?

`FullyAsyncLLMServerClient.generate` rebuilds every response into a fresh `TokenOutput`. It copies back only the keys it merges itself: the top-k heads, `num_cached_tokens` and the `*_global_steps` keys. Every other key that the backend put in `extra_fields` is dropped on every call, with or without a resume.

This breaks any rollout backend or agent loop that returns its own payload in `extra_fields` and reads it back after `generate`: the payload is present in sync mode, where the base client returns the server's `TokenOutput` as is, and missing under the fully async trainer, which uses this client (`trainer_separate_async.py`, `get_client(client_cls=FullyAsyncLLMServerClient)`).

This PR carries every other key through. When a request resumes, the latest attempt's value wins, the same as `stop_reason`. The keys the method merges itself keep their current behavior.

- koriyoshi2041 · COMMENTED · 2026-10-23T03:54:55Z · [source](https://github.com/verl-project/verl/pull/8341#pullrequestreview-5623692365)

One resume boundary still looks lossy for speculative-decoding metrics. Both rollout backends emit `spec_num_draft_tokens`, `spec_num_accepted_tokens`, and `spec_num_verify_steps` for each server response (`vllm_async_server.py:826-828`, `async_sglang_server.py:704-708`), and `ToolAgentLoop` already treats those fields as additive across generation calls (`tool_agent_loop.py:268-270`). With this generic latest-value-wins copy, an aborted first segment's counts are overwritten by the resumed segment, even though `final_output.token_ids` contains tokens from both segments. That makes the final acceptance-rate metrics inconsistent with the final response.

Could these three keys use additive merging across resume attempts, with a two-segment regression (for example `10/6/4` followed by `5/3/2` yielding `15/9/6`)? A single-attempt control would also preserve the current backend behavior.
