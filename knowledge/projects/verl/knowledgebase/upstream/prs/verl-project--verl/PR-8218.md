# [tool, rollout, perf] feat: add opt-in one-step tool read-ahead

[Upstream PR](https://github.com/verl-project/verl/pull/8218) · state: closed · merged: False

## Original PR description

**Closed after an applicability review.** The measured ~16% reduction applies to a constructed linked-record workload with explicit successor IDs and synthetic tool delays. It does not establish a general rollout or end-to-end RL training speedup. The current implementation has not demonstrated value on a representative real RL workload, so this draft is being withdrawn. The implementation and recorded test results are retained for reference.

---

### What does this PR do?

A linked-record tool often returns the exact identifier the model will request next. This PR adds an opt-in `ReadAhead` helper that starts that one immutable read during the next model turn and delivers it only when the model actually requests the matching key. A runnable `ToolAgentLoop` example scopes the reader to a trajectory and cleans up pending HTTP work on completion, failure, or cancellation.

This is a separate direction from #8136's continuation admission burst. That PR is now closed and did not establish an isolated scheduling benefit. This contribution overlaps tool waiting with model work; it does not modify the model, inference kernels, backend scheduling, or default agent loop behavior.

### API and Usage Example

```python
from verl.tools.read_ahead import ReadAhead

reader = ReadAhead(fetch_record, lambda record: record.get("next_record_id"))
try:
    # Call read only when the model requests the key; keep reader across turns.
    result = await reader.read(record_id)
finally:
    await reader.aclose()  # At trajectory end, after demanded reads stop.
```

The example agent/tool YAML files are under `examples/tutorial/agent_loop_get_started/`. Configure an immutable record snapshot URL and select the custom loop, then set its `read_ahead` option to `true` (default `false`). `docs/advance/tool_read_ahead.rst` gives the service contract and rollout overrides.

### Design & Code Changes

- Keep at most one speculative result per trajectory. Derive the next key only from the consumed result; never recursively follow an unconsumed record.
- Reuse only a matching key. Cancel and join mismatches; retry failed speculation on demand; propagate demanded errors.
- Require serial reads, complete operation keys, immutable/read-only data, and cancellation-aware async fetches. The example serializes reads and binds its reader with a per-run context, without storing tasks in serialized outputs.
- Keep cleanup at trajectory scope because ordinary `BaseTool.release` runs after each call. Close the reader before its HTTP session.
- Add documentation, tests, and the 2026 individual-contributor header to the existing license allow-list for the new files.

Related work: [Conveyor](https://arxiv.org/abs/2406.00059v2), [PASTE](https://arxiv.org/abs/2603.18897v3), and [LLMCompiler](https://arxiv.org/abs/2312.04511v3). This is deterministic one-step lookahead, not a reproduction of learned prediction or joint scheduling. Wrong predictions can waste reads; service-wide admission limits remain the caller's responsibility, and cancelling an HTTP request does not guarantee remote work stops.
