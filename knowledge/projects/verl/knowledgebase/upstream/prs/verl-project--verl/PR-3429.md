# The previous sequential method for math verification often got stuck, leading to timeout errors on complex expressions. This commit resolves the issue by parallelizing the computation for greater stability and efficiency.

[Upstream PR](https://github.com/verl-project/verl/pull/3429) · state: open · merged: False

## Original PR description

This PR addresses a critical performance and stability issue in the ProfRewardManager. The previous sequential implementation for math verification would frequently hang on complex expressions, causing the entire training job to stall and fail with timeout errors.

This change refactors the manager to process reward scores in a robust, parallel batch, significantly improving both speed and stability.

Related to issue #2507

## Code Review

This pull request introduces parallel computation for math verification to address performance and stability issues, which is a great improvement. The implementation uses `multiprocessing.Pool` to run scoring tasks in parallel and includes a mechanism to restart the pool on timeouts.

My review has identified a critical issue that could lead to an infinite loop under certain timeout conditions. I've also pointed out a high-severity issue regarding a misleading parameter in the `ParallelRewardManager`'s constructor that breaks the base class contract. Addressing these points will significantly improve the robustness and usability of the new parallel processing logic.

File: `verl/utils/reward_score/math_verify.py` · line None

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

The current `except multiprocessing.TimeoutError` block can lead to an infinite loop. When a task consistently times out, the pool is terminated and restarted, but since the task's result is not updated from its initial `-1.0` state, it is resubmitted in the next iteration, causing the loop to repeat indefinitely. This is a critical stability issue.

To fix this, you should mark the task as completed with a failure score (e.g., `0.0`) before raising the `TimeoutError` to trigger the pool restart. This will prevent the task from being retried.

```suggestion
                    except multiprocessing.TimeoutError:
                        warnings.warn(f"Timeout when processing item at index {original_index}. Will restart pool.")
                        results[original_index] = 0.0  # Mark as failed to prevent infinite loop
                        raise multiprocessing.TimeoutError
                    except Exception as e:
                        warnings.warn(f"An error occurred retrieving result at index {original_index}: {e}")
                        results[original_index] = 0.0
```

File: `verl/workers/reward_manager/parallel.py` · line 37

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The `compute_score` parameter from the `__init__` method (line 29) is ignored, as `self.compute_score` is unconditionally hardcoded here to `parallel_compute_score`. This is misleading and violates the contract of the `AbstractRewardManager` base class, which implies that the scoring function should be customizable.

A user providing a custom `compute_score` function would find it has no effect, which can lead to subtle bugs.

To fix this properly, `parallel_compute_score` should be refactored to accept a sequential evaluation function as an argument. Then, `ParallelRewardManager` can honor the `compute_score` parameter from `__init__` and pass it to the parallel runner.
