## Code Review

This pull request aims to fix an issue where old checkpoints are not removed on all nodes in a multi-node training setup. The proposed change removes the `self.rank == 0` condition that restricted checkpoint cleanup to the master rank. However, this introduces a critical race condition where multiple processes could attempt to delete the same directory concurrently. My review focuses on this critical issue and suggests alternative, race-free approaches.

- gemini-code-assist[bot] · comment · 2025-08-02T14:36:01Z · [source](https://github.com/verl-project/verl/pull/2878#discussion_r2249267426)

File: `verl/utils/checkpoint/fsdp_checkpoint_manager.py` · line None

![critical](https://www.gstatic.com/codereviewagent/critical.svg)

Removing this `self.rank == 0` check introduces a critical race condition. While the goal of cleaning up old checkpoints on all nodes is correct, this change will cause all ranks to execute `self.remove_previous_save_local_path` simultaneously on the same directory path. This can happen if multiple ranks are running on the same node (accessing the same local filesystem) or if they are using a shared network filesystem.

The `remove_previous_save_local_path` method calls `shutil.rmtree`, which is not safe for concurrent execution. This race condition can lead to errors during file deletion or a partially deleted checkpoint directory, which could cause issues later.

The comment on line 204, `# remove previous local_path, only rank 0 should do this`, highlights the original intent to prevent this race condition. With this change, the comment is now misleading.

A better approach would be to ensure that only one rank per node performs the cleanup. This is often achieved by checking for the local rank (`if local_rank == 0:`). Alternatively, a file lock could be used to ensure that only one process can enter the deletion logic at a time for a given path.

I recommend reverting this change and implementing a race-free solution for multi-node cleanup.
