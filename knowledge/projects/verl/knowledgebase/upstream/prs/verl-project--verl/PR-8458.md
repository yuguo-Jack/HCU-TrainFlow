# [BREAKING][algo, cfg] fix: validate distillation estimator update modes

[Upstream PR](https://github.com/verl-project/verl/pull/8458) · state: open · merged: False

## Original PR description

### What does this PR do?

Proposes explicit validation of the k1/k3 estimator/update-mode combinations discussed in #8423. A detached k3 reward does not give the reverse-KL policy gradient, even at an exactly on-policy update with no clipping; it can ascend that KL. The loss kernels and PPO implementation are unchanged.

This is a **breaking configuration proposal**, pending maintainer agreement on the intended semantics of k3+PG:

- Reject k3/low_var_kl with `use_policy_gradient=True`; direct reverse-KL PG users to k1/kl.
- Change the Python dataclass PG default to False, matching the existing YAML default and retaining k3 as the default estimator.
- Extend the existing rejection of direct-backpropagation k1 to its equivalent kl alias.
- Document migration and add CPU construction/conversion and exact expected-gradient tests.

If k3+PG intentionally defines another reward-shaping objective, please clarify that intent before adopting this restriction. Direct supervised k3 remains available and is not claimed to be an equivalent reverse-KL PG update. Related to #8423; separate from #8386's numerical-cancellation fix.
