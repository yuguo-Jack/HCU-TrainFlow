#  [hardware, vllm, trainer] feat: add GRPO RL training support with TorchTitan actor and vLLM rollout on TPU                       

[Upstream PR](https://github.com/verl-project/verl/pull/7231) · state: closed · merged: False

## Original PR description

### What does this PR do?

This PR enables GRPO RL training support for Google Cloud TPU v6e instances on GKE using TorchTitan actor engine and vLLM rollout backend.            
                                                                                                                                                          
Key capabilities introduced:
                                                                             
- **Non-colocated TPU Multi-Slice Support**: Dedicated placement group isolation for TorchTitan trainer (`Slice 0`) and vLLM sampler/rollout (`Slice  1`).                                                                                                                                                    
- **Domain-Based Placement Group Resolution**: Added worker domain name-prefix filtering (`matching_pgs`) in `PlatformTPU.get_tpu_env_vars()` to  prevent inter-slice PJRT mesh mixing.                                                                                                                   
 - **TPU Checkpoint Engine Integration**: Implemented custom zero-copy weight synchronization via `TPUCheckpointEngine` and   `load_weights_from_ray_registry()`.                                                                                                                     
- **Vectorized TPU Logprobs**: Vectorized logprobs calculation in `torch_functional.py` for 30x faster reference logprob computation.

- wenjung2007 · comment · 2026-10-07T20:26:34Z · [source](https://github.com/verl-project/verl/pull/7231#issuecomment-6046207869)

Hi @jialei777, could you update the TPU image pins in this PR (`examples/tpu/gke/Dockerfile.tpu` and `examples/tpu/gke/ray-tpu-v6e8-2slice.yaml`) when you next rebase? The Raiden (tpu-sync) weight-sync engine in verl-project/verl-hardware-plugin#37 was validated with this set:

| Component | Version |
|---|---|
| `torch-tpu` | `0.1.1+release.2026.9.22.20260927223741` |
| `tpu-sync-torch` | `0.0.1.dev20261001132139` |
| vLLM / vllm-torchtpu | `v0.29.0` / `9faafb17` |
| Image | `us-west2-docker.pkg.dev/tpu-pytorch/raycluster/verl-tpu:v20261007-tsync1001132139` |

The PR currently pins `torch-tpu==0.1.1.dev20260527102151`, vLLM `v0.19.0` and image `v20260630-159c2e3e`.

The important part is that `tpu-sync-torch` and `torch-tpu` must be built as a matched pair: the tpu-sync extension is ABI-locked to the `torch-tpu` it was built against. With a mismatched pair (a `torch-tpu` dev build from before the 2026-09-22 release, plus a tpu-sync wheel built for that release), the `xla::PjRtCApiClient` vtables differ by one slot. Freeing a tpu-sync `WeightSynchronizer` then calls the wrong method and segfaults on the first sync. Suggest a comment in the Dockerfile next to both pins saying they must be bumped together.

One more suggestion for the Dockerfile: pass the GitHub token as a BuildKit secret (`RUN --mount=type=secret,id=github_token ...`, built with `--secret id=github_token,env=GITHUB_TOKEN`) instead of `ARG GITHUB_TOKEN`, and reset the clone remotes afterwards. Otherwise the token ends up in the image history and in the cloned repos' `.git/config`.

Thanks!
