# [trainer] fix: DataProto concat bug when timing generate_sequences is sightly different

[Upstream PR](https://github.com/verl-project/verl/pull/4030) · state: open · merged: False

## Original PR description

### What does this PR do?

During `DataProto` concat a list of data, it should ensure consistency for overlapping non-matric keys.  However, we've observed that data['timing']['generate_sequences'] may differ slightly across nodes, even though derived metrics like generation_timing/min, generation_timing/max, and generation_timing/topk_ratio are identical.

```
merged_meta_info[k]
{'generate_sequences': 73.94637298583984, 'generation_timing/max': 75.57780456542969, 'generation_timing/min': 71.02742767333984, 'generation_timing/topk_ratio': 0.1666666716337204}

v
{'generate_sequences': 73.94638061523438, 'generation_timing/max': 75.57780456542969, 'generation_timing/min': 71.02742767333984, 'generation_timing/topk_ratio': 0.1666666716337204}
```

We suspect that generate_sequences represents the average generation time across nodes, and minor floating-point differences are expected due to non-deterministic execution or rounding.

To address this, we propose ignoring the difference in generate_sequences when round(...) values are the same, allowing the merge to proceed without raising unnecessary inconsistencies.

This issue has been reported by multiple users, as seen in [volcengine/verl#3909](https://github.com/volcengine/verl/issues/3909).

The implementation of `meta_info_equal` can be made more robust.

1.  **Float Comparison**: Using `round()` for comparing floating-point numbers is not ideal. It can fail for values that are close but fall on opposite sides of a rounding boundary (e.g., `73.49` vs `73.51`). It's better to use `math.isclose()` with a suitable tolerance.

2.  **NumPy Array Comparison**: The `==` operator for NumPy arrays performs an element-wise comparison, which returns a boolean array. Using this in a boolean context (like an `if` statement) will raise a `ValueError`. It's safer to use `np.array_equal()` for this.

3.  **Recursion for Nested Data**: The current implementation is not recursive. If `meta_info` contains nested dictionaries, any `generate_sequences` key within them will be compared using `!=`, bypassing the special float comparison logic. A recursive implementation would handle these nested structures correctly.

Here is a suggested recursive implementation that addresses these points:

```python
        def meta_info_equal(a, b):
            import math
            import numpy as np

            if type(a) is not type(b):
                return False

            if isinstance(a, dict):
                if a.keys() != b.keys():
                    return False
                for key, val_a in a.items():
                    val_b = b[key]
                    if key == 'generate_sequences' and isinstance(val_a, float) and isinstance(val_b, float):
                        if not math.isclose(val_a, val_b, rel_tol=1e-6):
                            return False
                    elif not meta_info_equal(val_a, val_b):
                        return False
                return True
            
            if isinstance(a, np.ndarray):
                return np.array_equal(a, b, equal_nan=True)

            return a == b
```
