- yue-zeng-yue · comment · 2026-10-13T08:01:50Z · [source](https://github.com/verl-project/verl/pull/8185#issuecomment-6141086626)

@wuxibin89, is dense HSDP intended to be supported by this merger, and would a narrowly scoped follow-up be welcome? Is anyone already working on it?

From code inspection on main (3e0d79e), [_locate_shard rejects non-1-D meshes or multiple placements](https://github.com/verl-project/verl/blob/3e0d79ea8c38264bcaddc64de1b3465589580320/verl/model_merger/veomni_model_merger.py#L71-L84), while _merge_dtensor uses placements[0]. The engine can configure both dp_replicate and dp_shard greater than 1, and the [pinned VeOmni revision returns a 2-D dp_replicate × dp_shard FSDP mesh](https://github.com/ByteDance-Seed/VeOmni/blob/10a26aca258f91a7af3e698cc0db8c6c51705989/veomni/distributed/parallel_state.py#L234-L249) for that case. This looks like a possible support gap; this is code inspection only, and I haven't built a minimal failure reproduction yet.

The proposed scope would be dense (Replicate(), Shard(...)) layouts with CPU/Gloo regression coverage, leaving EP/MoE and quantized export outside the change. I'd like to confirm the intended scope and avoid duplicate work before proceeding.
