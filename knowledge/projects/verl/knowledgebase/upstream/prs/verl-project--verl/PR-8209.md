# [megatron] fix: allow BSHD with inactive MoE router losses

[Upstream PR](https://github.com/verl-project/verl/pull/8209) · state: closed · merged: False

## Original PR description

### What does this PR do?

Allow the Megatron BSHD path (`use_remove_padding=False`) with `calculate_per_token_loss=True` when no MoE router loss is active.

`calculate_per_token_loss=True` is auto-enabled by Megatron-Bridge at CP>1. On the BSHD path the engine currently raises for every model, because verl does not pass a padding mask to the MoE router, so the aux/z loss would be normalized by the padding-inclusive `B*S` while gradients are divided by real tokens. That mismatch only matters when an aux or z loss actually contributes. Dense models, and MoE configs with zero aux coefficients and z-loss disabled, are rejected even though they are unaffected.

This PR moves the check into `validate_bshd_moe_router_loss_compatibility()`. It raises only when an aux routing type (`aux_loss`, `seq_aux_loss`, `global_aux_loss`) has a positive coefficient (scalar or per-type list) or `moe_z_loss_coeff > 0`. Per-token normalization and the rejection of active aux/z losses are unchanged.

### Test


Result: `25 passed`.

The tests cover scalar and list routing configs, zero coefficients, z-loss, dense configs without router fields, the active-loss rejection, THD, and the non-per-token and forward-only paths. They check the loss sum, the CP token count and the returned gradients. To avoid CUDA-only Megatron imports, they run the engine's loss callback and token-count method on CPU without asserting source text. A real model forward and Megatron gradient finalization have not been run.

### API and Usage Example

No API change. Configs that were already supported behave the same. BSHD with per-token loss is now accepted when MoE aux/z losses are inactive.
