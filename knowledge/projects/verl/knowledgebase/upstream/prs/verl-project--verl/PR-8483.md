# [vllm, rollout] fix: reset uncalibrated KV cache scales after a quantized refit

[Upstream PR](https://github.com/verl-project/verl/pull/8483) · state: closed · merged: True

## Original PR description

### What does this PR do?

Quantized rollout (`rollout.quantization.linear/moe=FP8_BLOCK`) combined with an FP8 KV cache (`+actor_rollout_ref.rollout.engine_kwargs.vllm.kv_cache_dtype=fp8_e4m3`) makes vLLM generate garbage. This PR resets the attention q/k/v/prob scales to 1.0 after every quantized refit when the rollout quant config has no `kv_cache_scheme`. Each mode works alone; only the combination breaks.

Root cause (checked in vLLM 0.29 and 0.32):

1. verl's compressed-tensors rollout config sets `kv_cache_scheme: None`, but vLLM still attaches a `CompressedTensorsKVCacheMethod` to every `Attention` layer.
2. Its `create_weights` registers `q/k/v_scale` placeholders initialized to 1.0. `load_format="dummy"` overwrites them with its seeded uniform values (all -7.5e-4 here). Unlike `KVCacheScaleParameter`, these placeholders set no `dummy_weight_value`.
3. `CompressedTensorsKVCacheMethod.process_weights_after_loading` adopts the loaded placeholders as the live `_q/_k/_v_scale` (and the `_float` copies). Unlike `BaseKVCacheMethod`, it has no "not in the checkpoint → 1.0" fallback. The dummy load also randomizes `_prob_scale`.
4. verl's refit sends no attention scales and re-processes only the linear/MoE layers, so the random scales are never corrected. With `kv_cache_dtype=fp8`, FA3 then quantizes Q/K/V with a scale of -7.5e-4.

The fix adds `reset_uncalibrated_kv_cache_scales(model)` to `process_quanted_weights_after_loading`. For every layer whose quant method is a `BaseKVCacheMethod` and whose quant config has no `kv_cache_scheme`, it calls vLLM's own `set_default_quant_scales(layer, register_buffer=False)` under `torch.no_grad()`. The `no_grad` is needed because vLLM <= 0.29 keeps the scales as the grad-requiring placeholder Parameters. Configs that do carry a `kv_cache_scheme` are left untouched. With `kv_cache_dtype=auto` the scales are unused, so the reset is a no-op in effect.

Not a duplicate: open PRs touching FP8 KV cache or KV scales were searched (queries below). #4435 adds an FP8 KV cache feature on the older FSDP path with per-step scale recalibration in `vllm_fp8_utils.py`; it does not touch the compressed-tensors refit path changed here (`vllm_quant_utils.py`, added by #8287). No open PR resets these scales. This PR does not add an FP8 KV cache option; it only stops the existing `engine_kwargs` passthrough from producing garbage with quantized rollout.

### Test

**Unit test** (new, `tests/utils/test_vllm_kv_cache_scale_reset_on_cpu.py`; loads `vllm_quant_utils` by path against stub vLLM modules, so it runs in the CPU CI). It covers four cases:

- scales stored as buffers (vLLM 0.32) and as grad-requiring Parameters (vLLM 0.29) are both reset;
- a config with a `kv_cache_scheme` keeps its scales;
- layers without a KV cache method are ignored;
- `process_quanted_weights_after_loading` performs the reset.

**GPU repro on verl main + vLLM 0.32.0** (locked env, 1×H20, Qwen3-0.6B). Setup: dummy load with verl's `FP8_BLOCK` compressed-tensors config, then a refit of the real BF16 weights through `CompressedTensorsWeightQuantizer` → `prepare_quanted_weights_for_loading` → `model.load_weights` → `process_quanted_weights_after_loading`. Then greedy decoding of "The capital of France is":

| KV cache | fix | layer-0 q/k/v/prob scale after refit | prompt log-probs | greedy output |
|---|---|---|---|---|
| auto (BF16) | – | 1.0 | -12.56, -0.50, -3.58, -0.37 | " Paris. The capital of France is also …" |
| fp8_e4m3 | no | -7.46e-4 | -11.23, -21.75, -17.03, -27.64 | "-------\n-------\n-------\n…" |
| fp8_e4m3 | yes | 1.0 | -12.85, -0.55, -3.87, -0.35 | " Paris. The capital of France is also …" |

Before the fix, all 28/28 attention layers carry the dummy scales after a dummy load; after `process_quanted_weights_after_loading`, 0/28 do.

**End-to-end** (earlier verl main with the same fix, vLLM 0.29). Setup: Qwen3-30B-A3B-Base, Megatron TE blockwise FP8 training + FP8_BLOCK rollout + `kv_cache_dtype=fp8_e4m3`, DAPO-Math, 8×H20.

- Train-vs-rollout `k3_kl` probe (8 prompts × 4, 2K responses): NaN before the fix, 0.0066 after. For reference, BF16 gives 0.00085 and FP8_BLOCK without FP8 KV gives 0.0029.
- AIME-2024 at step 0: 0.0 before the fix, 4.6% after (BF16: 5.4%).
- The fixed run trained 100 steps stably; `k3_kl` over the last 20 steps was 0.0029.

### API and Usage Example

No API or config change. FP8 KV cache with quantized rollout now works through the existing passthrough:

```bash
actor_rollout_ref.rollout.quantization.linear=FP8_BLOCK \
actor_rollout_ref.rollout.quantization.moe=FP8_BLOCK \
+actor_rollout_ref.rollout.engine_kwargs.vllm.kv_cache_dtype=fp8_e4m3
```

The KV cache then runs with q/k/v scales of 1.0 (uncalibrated), the same as an FP8 KV cache on an unquantized model.

### Design & Code Changes

- `verl/utils/vllm/vllm_quant_utils.py`: new `reset_uncalibrated_kv_cache_scales(model)`, called from `process_quanted_weights_after_loading` (after the linear/MoE post-processing, before the ROCm `wo_a` cache rebuild). It returns early if the vLLM symbols are missing (older vLLM).
- `tests/utils/test_vllm_kv_cache_scale_reset_on_cpu.py`: CPU unit test.

Out of scope:

- Calibrated KV scales: exporting per-layer `k_scale`/`v_scale` through a `kv_cache_scheme` on each refit. A user-provided `config_file` with a `kv_cache_scheme` keeps the dummy scales today, because verl does not export KV scales. This PR leaves that path unchanged.
- SGLang: not checked.
