# [rollout] feat: continuous_token support Assistant Role in Merge and Encode Context

[Upstream PR](https://github.com/verl-project/verl/pull/7643) · state: closed · merged: True

## Original PR description

## Summary

This PR is stacked on unmerged pr #6804. It updates Continuous Token context merging to support rollback-style agent harness behavior.

Previously, CT exposed `merge_non_assistant_*` APIs for harness-returned messages, assuming those incremental messages only contained non-assistant roles such as `tool`, `user`, or `system`.

Some agent harnesses may rewrite a previous assistant turn during rollback. In that case, the context delta returned to CT can contain `role == "assistant"`. This PR renames the API from `non_assistant` to `context` and supports assistant messages inside context increments.

Main changes:

- Rename `merge_non_assistant_tokens` to `merge_context_tokens`.
- Rename `tokenize_non_assistant_incremental_messages` to `tokenize_context_incremental_messages`.
- Support `role == "assistant"` in context incremental messages.
- Keep `merge_assistant_tokens` for LLM-generated assistant tokens only.
- Context tokens always get loss mask `0` and logprob `0`, even when the context message role is `assistant`.
- Reject context incremental messages that end with an assistant message.
- Encode context increments by role-based groups instead of encoding the whole incremental message list at once.
- Update agent loop call sites from `non_assistant` to `context`.
- Update DeepSeekV4 CT builder from the old non-assistant API to the new context API.

## Context grouping behavior

CT now splits incremental context messages by role and delta-encodes each group separately.

Example:

```python
raw_messages = [system, user, assistant]
updated_messages = [system, user, assistant_c, tool_response, user]

keep_messages = [system, user]
incremental_messages = [assistant_c, tool_response, user]
```

CT groups the incremental messages as:

```python
[assistant_c], [tool_response], [user]
```

Then each group is delta-encoded and concatenated.

CT does not directly delta-encode the whole list:

```python
[assistant_c, tool_response, user]
```

## Why grouping is needed

There are two main reasons.

1. Some chat templates drop historical assistant thinking when a later user message exists. For example, Qwen3-style templates may remove assistant thinking from a previous assistant turn. CT intentionally preserves assistant thinking, so direct full incremental encoding is not always acceptable.

2. Different roles require different synthetic dummy contexts to get a stable suffix diff. For example, some MiniMax templates require a tool response to be preceded by an assistant tool-call message; otherwise the template cannot render the tool response correctly.

## Important behavior notes

1. CT rejects context incremental messages whose last message is `role == "assistant"`.

2. CT context messages are masked out for training:

   - loss mask: `0`
   - logprob: `0`

   This is true even if the context message role is `assistant`.

3. `merge_assistant_tokens` remains dedicated to LLM-generated assistant tokens. Those tokens keep loss mask `1`.

| Qwen3 | A(no think)+tool+user | Same empty think block behavior as above. |
| Qwen3 | A(think)+tool+user | Direct encoding drops or ignores historical assistant thinking because a later user message exists. CT grouped encoding preserves `reasoning_content`. |

| MiniMax M2 | A(think)+user | Same thinking-drop behavior. |

| GLM5 | A(think)+user | Same thinking-drop behavior. |

Overall, the false cases fall into two expected categories:

1. Direct encoding drops assistant thinking, while CT grouped encoding preserves it. This is the intended CT behavior.
2. CT may include an empty think tag. This is currently considered acceptable; newer templates such as Qwen3.5 also preserve empty think tags, so this may be the direction templates are moving toward.

- gxlvera · comment · 2026-09-02T04:16:48Z · [source](https://github.com/verl-project/verl/pull/7643#discussion_r3910652828)

Gemma4 and deepseek (v3 and before) has some special boundary behavior when merging different msg groups within context message list and that's why I override `tokenize_context_incremental_messages`. However, after I rechecked it and found that their special behavior can actually be implemented in some smaller hook instead of overriding the whole `tokenize_context_incremental_messages` and `merge_context_tokens()`.  I made the following change:
1. add a function`_merge_context_group()` to CT class to deal with special behavior of boundary handling when merging two msg group within context msg list (e.g. context msg list is `[tool response,user prompt]`, then `_merge_context_group()` will be called when merging tool msg group and user msg group)
2. let gemma4 and dpsk to use `tokenize_context_incremental_messages` and `merge_context_tokens` of the base class and override smaller hooks like `_merge_context_group` and `_merge_context_token_ids`. In this way, we can reduce repetitive codes and reuse the functions of the base class.
