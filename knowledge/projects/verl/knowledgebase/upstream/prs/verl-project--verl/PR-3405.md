# [trainer, worker] feat: Add CPU/MPS fallback support for local debugging

[Upstream PR](https://github.com/verl-project/verl/pull/3405) · state: open · merged: False

## Original PR description

### What does this PR do?

Enable the verl trainer and workers to run on CPU or MPS by:

- Setting `attn_implementation="eager"` when `flash-attn` is not available
- Skipping FSDP and using `.to(device)` for unsupported devices
- Using `psutil` for memory stats when Torch APIs are unavailable
- Updating `ray.init` and distributed `init` for flexible device support

Related to: https://github.com/volcengine/verl/issues/2517

The `while` loop here constitutes a busy-wait, which is inefficient and can lead to high CPU usage. It continuously calls `_read_files_and_tokenize()` if the dataframe is not yet available. If an error occurs during data loading that prevents `self.dataframe` from being set, this will result in an infinite loop. A more robust approach is to load the data once if it's missing, rather than repeatedly trying in a tight loop. The `print` statement inside the loop can also lead to excessive console output.

```suggestion
        if not hasattr(self, "dataframe") or self.dataframe is None:
            # The dataframe is not loaded, likely in a new worker process.
            # Load it once.
            self._read_files_and_tokenize()
```

- gemini-code-assist[bot] · comment · 2025-12-23T08:00:11Z · [source](https://github.com/verl-project/verl/pull/3405#discussion_r2642313441)

File: `verl/utils/profiler/performance.py` · line 64

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The memory statistics for CPU/MPS devices are being calculated using `psutil.virtual_memory()`, which reports system-wide memory usage. This is misleading as it doesn't reflect the memory usage of the current process or model, unlike `torch.cuda.memory_allocated()` which is device and process-specific. For example, `mem_allocated` is set to `mem.total - mem.available`, which is the total used memory on the system, not what the current process has allocated.

To get per-process memory usage, you should use `psutil.Process()`. For example:
```python
proc = psutil.Process()
mem_info = proc.memory_info()
mem_allocated = mem_info.rss  # Resident Set Size: memory in RAM
mem_reserved = mem_info.vms   # Virtual Memory Size

# For total/free, system-wide is appropriate.
vmem = psutil.virtual_memory()
mem_total = vmem.total
mem_free = vmem.available
```

- gemini-code-assist[bot] · comment · 2025-12-23T08:00:11Z · [source](https://github.com/verl-project/verl/pull/3405#discussion_r2642313443)

File: `verl/workers/fsdp_workers.py` · line 909

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The memory metrics for CPU/MPS devices are calculated using `psutil.virtual_memory()`, which reports system-wide memory usage. This is inconsistent with the CUDA/NPU path, which reports per-process peak memory usage using `max_memory_allocated()` and `max_memory_reserved()`. The current implementation for CPU/MPS reports current system-wide used memory as `max_memory_allocated` and system-wide available memory as `max_memory_reserved`, which is misleading.

To provide a more accurate analogy, you should use `psutil.Process()` to get per-process memory usage. For example:
```python
proc = psutil.Process()
mem_info = proc.memory_info()
max_memory_allocated = mem_info.rss / (1024**3)  # Resident Set Size
max_memory_reserved = mem_info.vms / (1024**3)   # Virtual Memory Size
```
Note that `psutil` reports current memory usage, not the peak usage, so there will still be a difference in what is being measured compared to the CUDA path.
