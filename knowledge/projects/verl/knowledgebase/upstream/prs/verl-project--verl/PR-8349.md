# [algo] fix: give uniform reward groups exactly zero grpo advantage

[Upstream PR](https://github.com/verl-project/verl/pull/8349) · state: open · merged: False

## Original PR description

### What does this PR do?

When every response in a GRPO group gets the same fractional reward, there is no preference between the responses, so every advantage in the group should be exactly zero. Right now the float32 group statistics invent one instead: the group mean can land about an ulp away from the shared reward, the std is then about the same size as that residue, and the division amplifies it into the same nonzero advantage for every response in the group.

Measured on CPU against current main (group of 16 identical rewards of 0.3, reward on the last token):

- `compute_grpo_outcome_advantage`: advantage **+0.0289** for every response
- `compute_grpo_vectorized_outcome_advantage`: **+0.0289** here too, and worse at other group sizes (0.7 at group size 64 gives **-0.2937**, 0.9 gives **-0.3482**)

The Miles fork (RadixArk/miles) found and fixed the same class of problem on their side in RadixArk/miles#4019. This is the verl side of it: same idea, but both verl GRPO implementations, which share no code with the Miles one. I came across it while checking how uniform reward groups (all responses wrong in the same way, or a verifier that gives partial credit to all of them) flow through advantage computation.

Why this is not a duplicate of existing work:

- I searched open issues and PRs for this first (queries in the checklist below). Nothing open covers uniform groups getting nonzero advantages.
- #6348 (merged) fixed the neighbouring case: *near*-uniform, low-variance groups being scaled down in the vectorized path. Exactly uniform groups still slip through both implementations on current main, which the new tests show.
- #7964 (open) is about keeping RLOO vectorized advantages in the reward dtype, a different estimator and a different concern.

A note on assistance, per AGENTS.md: this change was drafted with AI help. I reviewed every line, the reproduction and the tests were run locally, and I am happy to defend or adjust any part of it.

### API and Usage Example

No API or config changes. Same call as before, now with the correct result for a uniform group:

```python
adv, _ = compute_grpo_outcome_advantage(token_level_rewards, response_mask, index)
# a group where every response scored 0.3 now gets advantages of exactly 0.0,
# instead of about +0.0289 for every response
```

### Design & Code Changes

`verl/trainer/ppo/core_algos.py` only, two places:

- `compute_grpo_outcome_advantage`: when a group's scores are all equal, use the shared score itself as the group mean (and std 1.0, like the singleton case). The centered scores are then exactly zero with or without std normalization, and no other group changes.
- `compute_grpo_vectorized_outcome_advantage`: after computing the scalars the same way as before, groups with more than one response whose min and max scores are equal are set to exactly zero, taken from the scores themselves rather than from the rounded statistics. Singleton groups keep the existing mean 0, std 1 convention.

`compute_gdpo_outcome_advantage` builds on the scalar GRPO function per reward dimension, so it picks up the fix for free. I kept this to GRPO on purpose: GPG divides by `f_norm` rather than a near-zero std, so the residue is not amplified there, and RLOO has its own open work (#7964). Happy to extend it if you would like them covered here too.
