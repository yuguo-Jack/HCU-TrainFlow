# [recipe] feat: DeepSeek-V4.1 LoRA with bitwise train/inference log-probs and 262K context on 8 GPUs

[Upstream PR](https://github.com/verl-project/verl/pull/8403) · state: open · merged: False

## Original PR description

### What does this PR do?

Adds an example for DeepSeek-V4.1-Flash LoRA RL on verl + Megatron Lite (mLite) + vLLM with
**training/inference bitwise-identical log-probs**, including **262,144-token context on 8 GPUs**
(2 nodes x 4 GB200).

- `examples/grpo_trainer/run_deepseek_v41_lora_bitwise_megatron_lite.sh`: thin wrapper over the
  Megatron Lite DS4.1 launcher at a pinned commit, with two presets (`--mode long262k`, `--mode rl`),
  LoRA rank 32 / alpha 32 on layers 20-39 (attention, shared and routed experts), and a check that
  the mounted Megatron-LM checkout is the validated commit.
- `docker/Dockerfile.ds41_lora_bitwise`: the runtime image (vLLM, DeepGEMM, runtime venv), every
  input pinned. verl and Megatron-LM are mounted at run time.
- No change to verl core.
- The Dockerfile pins the same source commits as the measured runs but has not itself been built
  and run through these checks: the 262K run used a reference runtime built from the same vLLM /
  DeepGEMM sources (with verl `b9c513c4` byte-identical), and the 2048-token runs used an image built
  by the same steps before the helper files were inlined.

**Bitwise, not epsilon.** The actor forward calls the rollout's own vLLM operators. For every
response token, the FP32 log-prob bits of (1) the vLLM rollout, (2) the independent old-policy
recompute and (3) the grad-enabled actor are compared and are identical. Only the adapter is trained
and published to vLLM each step; the FP4/FP8 release base stays frozen.

### Results

Full DeepSeek-V4.1-Flash release (40 layers, 384 experts), LoRA r32/alpha32 on layers 20-39,
2 nodes x 4 GB200.

**DAPO training, 25 steps** (Megatron-LM `c6ec83ae10e922486dfea0f3e8d84310709efe20`, branch
`ds41-lora-dapo25-c6ec83ae`; vLLM `4d69bb52`, DeepGEMM `9f9f78ff`; KV-only lifecycle, rollout base
resident)

![DAPO 25 steps](https://raw.githubusercontent.com/ISEEKYAN/verl/03b211511421ae6c553458717b3a7916fb76b231/ds41-lora-dapo25.png)

- Data: DAPO-Math-17k deduplicated to 17,398 prompts, 17,270 for training and 128 held out (fixed).
- 128 prompts x n8 = 1,024 responses per step, max response 2048, mini-batch 128 (one optimizer
  update per step), Adam lr 3e-5 (0.9, 0.95); no dynamic filtering or refill; official DAPO reward
  (max response 8192, overlong buffer 4096); independent old-policy recompute every step.
- 25 steps (planned 30; the job stopped at its wall-clock limit): **37,951,531 response tokens,
  rollout = old-policy recompute = grad-enabled actor, FP32 bit-identical**;
  `training/rollout_probs_diff_max/mean` and `rollout_corr/k3_kl` are exactly 0 at every step.
- Held-out accuracy (128 prompts x 8, max 2048 tokens; fixed prompt list), **+19.63 pp** from step 0
  to step 25. Single seed, one sample per evaluation, no confidence interval, no AIME evaluation.

  | step | correct / 1024 | acc mean@8 | eval time |
  |---:|---:|---:|---:|
  | 0 | 504 | 49.22% | 134.5 s |
  | 5 | 537 | 52.44% | 116.0 s |
  | 10 | 551 | 53.81% | 112.1 s |
  | 15 | 601 | 58.69% | 115.9 s |
  | 20 | 659 | 64.36% | 115.6 s |
  | 25 | 705 | **68.85%** | 119.3 s |

- Per-step time over the 25 steps (seconds):

  | phase | mean | p50 | min | max |
  |---|---:|---:|---:|---:|
  | rollout generation | 102.80 | 103.5 | 95.28 | 109.1 |
  | independent old-policy recompute | 40.68 | 39.29 | 34.01 | 89.32 |
  | actor (forward / recompute / backward / optimizer) | 143.70 | 126.8 | 113.2 | 282.4 |
  | adapter publication and ACK | 27.50 | 26.56 | 25.22 | 41.0 |
  | **whole step** | **315.60** | 297.3 | 280.9 | 470.7 |

  Rollout generation averages about 1,848 tokens/s per GPU (response tokens / generation time /
  8 GPUs); mean response length 1,482 tokens (1,297-1,604).
- This run used a validation driver (resident entry, not part of the public tree) with the same
  model, LoRA and parallel layout as `--mode rl`, on Megatron-LM `c6ec83ae10` rather than the
  pinned `915b94e0`. Curves are plotted from the run's per-step metric log (the W&B run lost the
  final step and evaluation at the wall-clock stop).

**262,144-token context on 8 GPUs** (Megatron-LM `915b94e0`; the configuration `--mode long262k` uses)

- Actor EP8/CP8/PP1, rollout DEP4 x 2; actor and rollout strictly alternate on the GPUs
  (exclusive rollout, native same-source reload of the rollout base between phases).
- Prompt 262,016 + response 128 = 262,144 tokens; 8 sequences per policy generation, three
  generations: **3,072 response tokens, rollout = old-policy recompute = grad-enabled actor,
  FP32 bit-identical.**
- Two optimizer updates, finite and nonzero on all 8 ranks (grad norm 0.0064069 / 0.0058371);
  24 adapter publications, each acknowledged by every rollout receiver; base fingerprint unchanged.
- Host memory peak 828.9 / 826.1 GiB per node (run under an 850 GiB per-node admission limit);
  allocate whole nodes.
- Scope: a capacity/on-policy gate. The long prefix is a synthetic fixture (repeated real text) with
  exactly 128 response tokens (seeded single-turn agent, `ignore_eos`, proxy reward), run under a
  resident driver whose third step only scored. It shows that full-context on-policy LoRA training
  fits and stays bitwise on 8 GPUs; it is not a long-context quality or convergence result, and other
  response lengths or batch sizes are not covered. Step time: not measured.
- These results come from a validation driver (resident entry with a score-only third step) that
  is not part of the public tree. `--mode long262k` takes the run's configuration (2 prompts x n4)
  without those fixtures and launches through `verl.trainer.main_ppo`, **which has not been run at
  262K**;
  the launcher additionally selects vLLM's V2 model runner, which the measured run did not force.

**2048-token responses, save -> restart -> resume** (Megatron-LM `edfc2db6a9`, KV-only lifecycle)

- Production config: 128 prompts x n8, response 2048, actor EP8/CP1/PP1, rollout DEP4 x 2.
- Step 1 trained and saved; a new Ray cluster and new processes restored it and trained step 2.
  **1,605,586 (step 1) + 1,571,453 (step 2) response tokens, three-way FP32 bit-identical.**
- On all 8 ranks the trainable weights, FP32 master weights and Adam moments hash identically
  after save and after load; optimizer and LR-scheduler steps continue 1 -> 2.

**Same config, one production step** (Megatron-LM `a540b7db83`)

- 1,607,041 response tokens three-way FP32 bit-identical; actor update 139.94 s, whole step
  351.37 s; actor peak allocated 69.21-73.48 GiB per GPU.

The 2048-token runs used the DAPO trainer from verl-recipe; `--mode rl` reproduces their
configuration (KV-only lifecycle, rollout base resident) on the pinned commit through
`verl.trainer.main_ppo` and has not been run there. The pinned commit releases the CUDA cache after
every micro-batch backward (later heads make this optional); where this behavior was measured it
roughly doubled the actor update (286.74 s vs 139.94 s), so the `a540b7db83` step time above does not
apply to `--mode rl` on this commit.

### Not covered

- Long-context reward/convergence, real long-trajectory data, and per-step time at 262K.
- PP/CP parity of LoRA gradients across layouts, multiple concurrent adapters.
- x86/Hopper (this example is aarch64 GB200 only).
