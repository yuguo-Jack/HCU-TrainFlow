# [ci, fsdp] fix: pin PEFT to 0.20.0 for FSDP1 LoRA compatibility

[Upstream PR](https://github.com/verl-project/verl/pull/8184) · state: open · merged: False

## Original PR description

### What does this PR do?

Pin `peft` to `0.20.0` in `requirements-npu.txt` to restore FSDP1 LoRA compatibility.

PEFT 0.21.0 introduced a state-dict handling refactor in
[huggingface/peft#3490](https://github.com/huggingface/peft/pull/3490).
For nested FSDP1 models, PEFT may fail to match adapter module names against
the FSDP state dict and return an empty LoRA state dict, as tracked in
[huggingface/peft#3876](https://github.com/huggingface/peft/issues/3876).

In the affected verl workflow, the empty state dict is passed to vLLM, which
raises `StopIteration` while accessing the first LoRA module. The receiver
then exits without sending an ACK, causing the sender to hang until the CI
job times out.

The regression was observed in the following Ascend E2E job with PEFT 0.21.2:

- https://github.com/verl-project/verl/actions/runs/37787622168/job/113346339988

PEFT 0.20.0 is the latest known working version for this FSDP1 LoRA path.
This pin is intended as a temporary compatibility measure until the upstream
fix for nested `_fsdp_wrapped_module` prefixes is included in a stable PEFT
release.

Related verl PR:

- https://github.com/verl-project/verl/pull/8152 adds fail-fast validation for
  an empty LoRA state dict. It improves diagnostics but does not restore
  correct adapter state-dict extraction. This PR instead prevents the
  regression by selecting the known-good PEFT version.

**Remove the repeated `pip install peft==0.20.0` steps, or install from `requirements-npu.txt`.**

The workflow hard-codes the PEFT version in four places. Each run reinstalls it at test time. A later bump of the pin in `requirements-npu.txt` can leave these lines at the old version. The container image may also carry a newer PEFT, such as 0.21.2. The image can therefore differ from the pin on the first run.
