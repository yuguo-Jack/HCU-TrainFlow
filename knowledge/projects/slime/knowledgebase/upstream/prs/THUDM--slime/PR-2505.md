# fix: retain GPU locks while canceling command groups

[Upstream PR](https://github.com/THUDM/slime/pull/2505) · state: open · merged: False

## Original PR description

## Summary

Signal the whole owned command group on cancellation and retain GPU locks during bounded cleanup.

### Motivation

The cancellation handler stops only the direct child and exits as soon as that child finishes. A worker descendant can continue running after the launcher releases its GPU locks, allowing a later command to acquire the same lock and overlap the canceled work. Cleanup is also skipped when the direct child has already exited.

### Before and after

A controlled CPU reproduction uses real subprocesses and a private fake GPU flock:

| Observation | Base `540ea919` | This PR |
| --- | --- | --- |
| Lock while a stubborn descendant is still in its cleanup grace period | A competitor acquires it after the direct child exits | The launcher keeps it held through grace and escalation |
| Descendant when the launcher returns in the reproduction | Still running | Stopped |
| Cancellation exit status after `SIGTERM` | 143 | 143 |
| Normal command exit status | 7 | 7 |

The regression fails against the base helper and passes with this fix, including cancellation after the direct child exits. This demonstrates a cleanup correctness improvement. It does not measure a speedup, a reduction in historical CI failures, or actual CUDA resource reclamation.

## Changes

- Forward the handled cancellation signal to the whole owned command group, including when the direct child has already exited.
- Keep the locks during a bounded grace period, then send `SIGKILL` to remaining group members and perform another bounded wait. Polling also reaps the direct child.
- Preserve `128 + signal` cancellation status and the existing normal completion and device selection paths.
- Register a CPU regression test in the regular workflow template and include the regenerated YAML.

For review, focus on the handler's group lifetime and the subprocess assertions. The regression checks that the fake lock stays held during stubborn cleanup, that the descendant is stopped when the launcher returns, and that another process can then acquire the lock.

Cleanup targets the owned process group. Deliberately detached sessions remain the responsibility of container or caller cleanup. The waits are bounded, so this does not guarantee that an uninterruptible process has released its GPU resources.

## Testing

`python tests/ci/test_gpu_lock_exec.py` fails against the base helper and passes with the fix. It exercises cooperative and stubborn descendants, cancellation after direct-child exit, cancellation status, and normal exit status. It uses private lock files and process groups, with no GPU or Ray usage.

The [hosted CPU regression](https://github.com/THUDM/slime/actions/runs/40640459070/job/122657143188) and reported checks passed at `cc35b720`. Label-gated GPU jobs were skipped. Black 24.3.0, isort 5.13.2, Ruff 0.14.7, workflow regeneration, and `git diff --check` passed locally.

This patch is separate from the CPU batching change. If that workflow change lands first, regenerate the YAML from the merged template.
