# Adapt slime to Megatron core 0.20

[Upstream PR](https://github.com/THUDM/slime/pull/2518) · state: open · merged: False

## Original PR description


## Summary

Two API changes that came with the Megatron ae76c60e6 (core 0.20) upgrade (#2514) are not handled in slime yet.

### `use_gloo_process_groups`

Megatron renamed the argparse dest `enable_gloo_process_groups` to `use_gloo_process_groups` (the `--disable-gloo-process-groups` flag is unchanged). slime kept reading the old name, and `set_default_megatron_args` forced it to `True` when missing, so `--disable-gloo-process-groups` was ignored: Megatron treated Gloo as off while slime still created Gloo process groups for `parallel_state` and the optimizer.

- New `use_gloo_process_groups(args)`: prefers the new name, falls back to the old one, defaults to `True`.
- Read where it is used instead of caching a copy, because Megatron's `validate_args` can turn it off for a fake process group.
- Added the new name to the immutable-args list in `training_recovery`; the stateless Adam test gets the helper it now needs.

### `return_raw_freqs`

Megatron core 0.20 always passes `return_raw_freqs` when it calls the mRoPE module, so `Qwen3_5MultimodalRotaryEmbedding.forward` raised `TypeError: got an unexpected keyword argument 'return_raw_freqs'` in the first training step.

It now accepts the argument. It is `True` only on Megatron's fused mRoPE path, which asks for raw per-axis frequencies; this module only returns the final embedding in Qwen3.5's interleaved T/H/W layout, so it raises `NotImplementedError` instead of returning something that would be misread. The model config already forces `apply_rope_fusion` off, so Megatron does not ask for `True`.
