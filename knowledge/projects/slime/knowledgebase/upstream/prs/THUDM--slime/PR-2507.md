# fix(ppo): reduce cancellation in k3 KL estimates

[Upstream PR](https://github.com/THUDM/slime/pull/2507) · state: open · merged: False

## Original PR description

## Problem

For `k3` and `low_var_kl`, `compute_approx_kl` evaluates `exp(x) - 1 - x`, where `x = log_probs_base - log_probs`. This expression is nonnegative in real arithmetic, but subtracting 1 from a float32 exponential can erase the small KL term or make it negative when the policies are close.

With valid finite log-probabilities near -0.1, I reproduced a value of -1.4901161e-8 where an 80-digit reference gives 4.9986626e-11. The helper feeds the reported KL term and configured KL loss/reward paths; the Search-R1 example selects `low_var_kl` with a nonzero KL-loss coefficient.

## Change

Use `torch.expm1(x) - x` to reduce cancellation in the first subtraction. The estimator, importance weighting and the existing `low_var_kl` clipping order are preserved.

Extend the existing CPU KL test file with:
- Near-policy float32 values, both estimators and weighted/unweighted cases, checked against an 80-digit Decimal reference at the represented inputs.
- Analytic gradients, including importance ratios that depend on the current log-probability.
- Controls for importance weighting before low-variance clipping.

`tests/test_ppo_kl_metric.py` already has `NUM_GPUS = 0`, a direct-script entrypoint and registration in the `cpu-unittest` workflow matrix.

The same final test file failed 8 cases with 3 passing controls on the baseline, passed all 11 with the patch, and failed the same 8 after rollback. The restored patch also passed all 11 through the direct-script entrypoint. Adjacent policy-loss and CISPO tests passed (18 + 4), for 33 unique targeted CPU tests. A separate 80-digit reference probe passed 104 value comparisons. Scoped Ruff, isort, Black and `git diff --check` passed using the repository-pinned tool versions.

Additional CUDA validation reused an existing WSL2 environment: RTX 5070 Ti (SM120), driver 621.01, Python 3.12.3, PyTorch 2.14.0+cu130, CUDA runtime 13.0 and Triton 3.8.0. The unchanged test file ran with a local fixture selecting CUDA tensors; its assertions and tolerances were unchanged.

The GPU cases cover forward values, analytic gradients, differentiable importance ratios, and weighting before clipping. Compiled runs recorded 7 captured graphs and 11 generated kernels, no graph breaks, and `suppress_errors=False`; the generated Triton code uses `libdevice.expm1`. The existing Megatron stub in the logging test was retained, so this is not a real Megatron training run.

The earlier Windows Inductor CPU attempt remains blocked by the missing MSVC `cl` compiler. TP/CP distributed execution, full training and performance were not validated. No convergence or model-quality gain is claimed. This improves near-zero evaluation; it does not promise correctly rounded results for arbitrarily small inputs or address extreme exponential overflow.
