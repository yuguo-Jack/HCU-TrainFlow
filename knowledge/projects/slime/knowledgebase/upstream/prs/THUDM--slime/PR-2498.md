# [Fix] Keep DFLASH draft weights out of colocated weight updates

[Upstream PR](https://github.com/THUDM/slime/pull/2498) · state: open · merged: False

## Original PR description

## Problem

With `--sglang-speculative-algorithm DFLASH` and a colocated rollout engine, the first weight sync silently overwrites the DFLASH draft with target weights. After that, the acceptance length is ~1.0 and rollout is slower than with speculative decoding off.

How it happens:

- slime's colocated sender calls `update_weights_from_tensor` with `serialized_named_tensors`, `load_format="flattened_bucket"` and `weight_version`. It sets neither `selector` nor `disable_draft_model`.
- SGLang then fans the update out to every runner, because its default is `selector="all"`. The DFLASH worker exposes its draft runner for weight updates, so the draft is included.
- The DFLASH draft's `load_weights` strips the `model.` prefix. As a result it accepts the target's `model.layers.N.*` and `model.norm.weight` as its own `layers.N.*` and `norm.weight`. Names it doesn't have are skipped, and nothing raises.
- Every update returns `success=True`.

This is the same class of problem as #1177, which involved an EAGLE3 external draft and overlapping parameter names. sgl-project/sglang#15726 added `disable_draft_model` for exactly this case, and slime's `docker/patch/v0.5.21` keeps it for target-only tensor updates. However, slime's own sender never sets it.

## Fix

Send `disable_draft_model=True` with the colocated tensor update when the speculative algorithm is DFLASH. slime does not train DFLASH drafts, so the draft should keep the weights it was loaded with.

Changes:

- `update_weight_from_tensor.py`:
  - `_target_only_weight_update(args)` returns True for DFLASH.
  - `UpdateWeightFromTensor` passes the result down to `_send_to_colocated_engine`.
  - `_send_to_colocated_engine` adds `disable_draft_model=True` to the request only in that case, so the payload is unchanged for every other configuration.
- `sglang_engine.py`: `SGLangEngine.update_weights_from_tensor` accepts `disable_draft_model` and forwards it in the HTTP payload.
- `tests/test_empty_colocated_weight_bucket.py`, which already runs in CI with 0 GPUs, gets two new tests:
  - the flag reaches `update_weights_from_tensor.remote(...)`;
  - only DFLASH, case-insensitive, turns it on. EAGLE, EAGLE3 and an unset algorithm do not.

Equivalent alternative: SGLang's own `selector="target"`. The stock arm below measured it, and in the patched build `disable_draft_model=True` maps to the same target-only path. I used the flag that slime's patch keeps for target-only updates. I'm happy to switch to `selector="target"` if you prefer the native field, since SGLang main has since replaced `disable_draft_model` with it.

EAGLE/MTP is deliberately left alone. With `--enable-mtp-training` the draft is supposed to receive updated MTP weights, and the default fan-out is what makes that work.

## Evidence

Measured on 1× L40S, TP1, with SGLang 0.5.21 (sglang-kernel 0.4.7, torch 2.13.0+cu130), with and without the five `docker/patch/v0.5.21` patches from slime @ 540ea919.

- **Models:** Qwen3-4B target with the `z-lab/Qwen3-4B-DFlash-b16` draft, `speculative_num_draft_tokens=8`.
- **Workload:** T=1.0; 32 dapo-math-17k prompts × 1024 new tokens (every request hits the limit).
- **Engine:** an offline `sglang.Engine` with the colocate settings slime uses: `enable_memory_saver=True`, `enable_draft_weights_cpu_backup=True`, `cuda_graph_backend_prefill="disabled"`.
- **Push:** the target's 398 tensors (8.04 GB) as 15 `flattened_bucket` payloads of about 512 MB each. The request carries the same fields slime sends.
- **Checksums:** `check_weights(action="checksum", selector=...)` taken per runner before the update and after it.

slime itself was not run. Each arm is an offline-engine request carrying the same fields slime sends.

| arm | SGLang | update | acceptance length before → after | tok/s before → after | draft checksum |
|---|---|---|---|---|---|
| request as slime sends it today | patched | release → resume(weights) → from_tensor (no selector) → resume(kv_cache, cuda_graph) | 2.837 → **1.001** | 2605 → **1099** | **changed** |
| request with `disable_draft_model=True` (what this PR sends) | patched | same, plus `disable_draft_model=True` | 2.837 → 2.790 | 2621 → 2671 | unchanged |
| stock, target only | stock | `begin_weight_update("target")` → from_tensor(`selector="target"`) → end | 2.837 → 2.790 | 2606 → 2663 | unchanged |
| stock, default | stock | `begin_weight_update("all")` → from_tensor (default) → end | 2.837 → **1.001** | 2606 → **1099** | **changed** |

Three checks back this up:

- **The update really lands.** In all four arms the target checksum after the update equals the one before it. A separate probe push of `model.norm.weight * 2` moved the target checksum in every arm. In the two "all" arms it moved the draft checksum as well.
- **The overwrite is deterministic.** Both overwritten drafts end up with the same checksum, with or without the patches.
- **Release and resume alone are fine.** With the CPU backup on, a release/resume cycle with no push leaves the draft at 2.837 → 2.790. The damage comes from the push, not from the offload.

Tests:

- `python -m pytest tests/test_empty_colocated_weight_bucket.py`: 8 passed. Without the source change, the 6 new cases fail.
- `black`, `ruff check` and `isort --check-only` (the versions pinned in `.pre-commit-config.yaml`) are clean on the touched files.

## Not covered

- **HTTP + Ray path not run.** The measurements above use the offline engine with the same request fields. I did not run the actual HTTP server + Ray path end to end. In the patched SGLang, `disable_draft_model` is a field of the `UpdateWeightsFromTensorReqInput` body the endpoint takes, and `tests/test_sglang_weight_update_compat.py` covers the scheduler side.
- **Non-colocated path not changed.** `update_weights_from_distributed` is left as is. SGLang's request there also defaults to `selector="all"`, and the target hands what it receives to the draft runners, so the same overwrite probably happens. I have not measured it. If you want, I can add `selector="target"` for DFLASH there too.
- **Disk-based updates can't be fixed here.** That covers disk-delta, full-disk and pipeline modes. SGLang's `UpdateWeightFromDiskReqInput` has no selector, and the scheduler loads the target path into every runner, so slime cannot keep a DFLASH draft out of these updates. Reported to SGLang separately: sgl-project/sglang#46806.
- **Per-group overrides not consulted.** The check reads `args.sglang_speculative_algorithm`, which comes from the `--sglang-*` CLI args the actor receives. If DFLASH is enabled only through per-group `overrides` in `--sglang-config`, the flag is not set.
- **Other drafts and TP > 1 not tested.** Only one draft/target pair was tested, at TP1. External EAGLE3 drafts (#1177) are probably affected too. Telling them apart from MTP drafts needs a rule you may prefer to choose yourselves, for example "draft path differs from the model path and MTP training is off".

Related: #1177, sgl-project/sglang#15726, sgl-project/sglang#46806
