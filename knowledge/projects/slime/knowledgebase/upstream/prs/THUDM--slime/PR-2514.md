# build(docker): upgrade Megatron to NVIDIA/Megatron-LM dev ae76c60e6 (core 0.20.0)

[Upstream PR](https://github.com/THUDM/slime/pull/2514) · state: closed · merged: True

## Original PR description

## Summary

Upgrades the pinned Megatron-LM from `4b4acac9a` (core 0.19.2) to `ae76c60e6` (core 0.20.0) and regenerates both Megatron patches for `docker/patch/latest` and `docker/patch/v0.5.21` (identical copies). SGLang stays on v0.5.21; nothing SGLang-related changes.

PR #2493 was closed by accident, so I've resubmitted the changes as this PR (#2514).

## Patches (`docker/patch/{latest,v0.5.21}/`)

### `megatron.patch`

Regenerated against the new base: 11 files / 34 hunks -> 10 files / 21 hunks.

- Dropped, because upstream now carries them: the grad/param buffer CPU-backup plumbing (`param_and_grad_buffer.py`) and the fused MLA YaRN Triton kernel fixes (`fused_mla_yarn_rope_apply.py`).
- Adapted: the `GPTModel` `mtp_kwargs` hunk, the checkpoint-loading hunks (`strategies/torch.py`; `stream_ckpt_dequant` removed because upstream dropped it), and the `argument_utils` help escaping (`%` -> `%%` on top of the new prefix logic).
- Added: a `multi_token_prediction.py` hunk that relaxes the MTP layer's `position_ids is not None` assertion when the model has no position embedding (rope models), so slime does not need to build `position_ids` itself.

Changes in the regenerated `megatron.patch` (all under `megatron/`):

| File | Hunks | Change |
|---|---|---|
| `core/models/gpt/gpt_model.py` | 6 | `GPTModel.forward` / `_postprocess` accept `mtp_kwargs`; MTP runs only when `labels` or `mtp_kwargs["mtp_labels"]` is given, so label-free RL forward passes (reference / old-actor log probs) skip MTP; `mtp_labels` replaces `input_ids` as the MTP input when provided |
| `core/transformer/multi_token_prediction.py` | 1 | MTP layer allows `position_ids=None` when the embedding has no position embedding (rope models) |
| `core/optimizer/distrib_optimizer.py` | 3 | Do not keep `step` in bucket state or in the checkpoint's common state (it is restored from `param_groups`); drop a `None` `step` from param groups; drop local `padding` / `step` metadata when merging bucket state |
| `core/optimizer/cpu_offloading/hybrid_optimizer.py` | 1 | `update_fp32_param_by_new_param` refreshes every optimizer inner copy (including CPU copies of already-FP32 params), so a stale copy cannot overwrite loaded weights on the first step |
| `core/dist_checkpointing/strategies/torch.py` | 3 | Load planner skips keys that are missing from the checkpoint (warning instead of `KeyError`), filters tensor metadata accordingly, and enables `allow_partial_load=True` |
| `core/dist_checkpointing/strategies/common.py` | 1 | `load_common` calls `torch.load(..., weights_only=False)` |
| `training/checkpointing.py` | 3 | `--ckpt-step` is honored when it is `0` (`is not None`) and forces `release=False`; the non-persistent checkpoint lookup is skipped when `ckpt_step` is set |
| `training/argument_utils.py` | 1 | Escape `%` as `%%` in generated argparse help strings |
| `core/inference/contexts/dynamic_context.py` | 1 | Use the `TorchMemorySaver()` instance API of `torch_memory_saver` |
| `training/training.py` | 1 | Same `TorchMemorySaver()` instance API change |

### `megatron-sglang-aligned.patch`

Ported to the new `TransformerLayer` (hyper-connection / residual refactor); applies cleanly on top of `megatron.patch`.

## slime changes

**Build / packaging**
- `docker/Dockerfile`, `build_conda.sh`: pin the new commit and install `nvidia-resiliency-ext==0.7.0` (only declared in Megatron's `dev` extra, but needed for cached checkpoint metadata and async checkpointing); the core version assertion is now 0.20.0.
- `docker/README.md`: pinned-component text updated.
- GB10: `Dockerfile.gb10` pins Megatron `3714d81d` on a separate stack (TE 2.10), so it must not receive the new patch. The previous `latest` patch is frozen as `docker/patch/gb10/megatron.patch` and `Dockerfile.gb10` copies it, so the GB10 image is unchanged by this PR.

**Megatron API adaptation** (all guarded so older Megatron still works where noted)
- `slime/backends/megatron_utils/initialize.py`: registers the run config that Megatron `ae76c60e6` reads (`pretrain_cfg_container_from_args` / `set_run_config`), with a fallback for older Megatron.
- `slime/backends/megatron_utils/checkpoint.py`:
  - passes `restore_training_state` to `load_checkpoint` when the installed Megatron supports it (detected via `inspect.signature`), since Megatron `ae76c60e6` only restores optimizer / scheduler / data progress on request;
  - CPU staging for async saves now picks the `FileSystemWriterAsync` matching `--async-strategy` (`nvrx` from `nvidia_resiliency_ext`, otherwise Megatron's native one) instead of only handling `mcore`.
- `slime/backends/megatron_utils/model.py`: MTP loss logging handles the tracker layout of Megatron `ae76c60e6` (`loss_sums`, reduced by `MTPLossLoggingHelper.reduce_loss_in_tracker()`), and keeps the manual all-reduce path for older Megatron.
  - With `--calculate-per-token-loss`, the tracker already holds `sum(loss) / sum(tokens)` after the reduction, so slime no longer divides it by the microbatch count again (scale 1.0, the same rule as Megatron's own training loop). Microbatch-normalized losses are still averaged by `1 / num_microbatches`.
  - slime does not pass its own `position_ids` for MTP training: `position_ids` stays `None`, as in the non-MTP path (the MTP assertion is relaxed by the `multi_token_prediction.py` hunk in `megatron.patch`).
- `slime/backends/megatron_utils/model_provider.py`: `LinearForLastLayer` sets `gather_output = True`, because `GPTModel._postprocess` now reads `output_layer.gather_output` (the value head is never TP-sharded).
- `slime_plugins/models/qwen3_5.py`, `qwen3_next.py`: `Attention.__init__` accepts the new `pp_layer_offset` and `is_mtp_layer` arguments that Megatron now passes.
- `slime/utils/arguments.py`: Megatron `4b4acac9a` defaults `--async-strategy` to `nvrx`, and `ae76c60e6` dropped the native strategy and only offers `nvrx`. slime now forces the default to `mcore` only when the parser still lists it. Without this, startup fails with `async_strategy mcore is not supported`.
- Comments in the touched code name the Megatron commits (`ae76c60e6`, `4b4acac9a`) instead of saying "newer Megatron".

**Tests**
- `tests/test_megatron_argument_validation.py`: new unit test for the nvrx-only parser.
- `tests/test_megatron_tokenizer_init.py`: stubs for the new `set_run_config` / `pretrain_cfg_container_from_args` names.

## Validation

`tests/test_glm52_6layer_deterministic_e2e.py` (`MEGATRON_USE_SGLANG_FUSED_RESIDUAL_RMS=1`, i.e. the flag-on path of `megatron-sglang-aligned.patch`) on the `slimerl/slime:latest-cu130` image with both patches applied:

| Megatron | `train_rollout_logprob_abs_diff` | bound | result |
|---|---|---|---|
| ae76c60e6 (new) | 1.5667e-07 | 1e-6 | 2 passed |
| 4b4acac9a (old) | 1.5667e-07 | 1e-6 | 2 passed, identical to every digit |

Also checked on a single GPU: the patch's RMSNorm helper is bit-identical to SGLang's `RMSNorm.forward_native(x, residual)`; against `sgl_kernel.fused_add_rmsnorm` only a few elements differ by 1 ulp. The unpatched bf16-rounded boundary differs in ~20% of elements. Two real `TransformerLayer`s with the flag on vs off show the same error against an fp32 reference.

## Known limitations

- The gate was run on 2 nodes x 8 H100 (EP16), not the test's default single-node 8-GPU layout. With 80 GB GPUs the single-node layout OOMs in `deepgemm_moe_forward.py` backward (~71 GB); this happens identically on the old Megatron, so it is not a regression. The test file in the repo is unchanged.
- The GB10 image was not built in this PR and is intentionally kept on the pre-upgrade patch: it pins Megatron 3714d81d, while the new latest patch was regenerated against ae76c60e6 and drops hunks that upstream now carries, so it may not apply cleanly there; GB10 therefore copies a frozen copy of the old patch (docker/patch/gb10/megatron.patch). GB10 is a separate stack (DGX Spark, aarch64, CUDA 13.2, TE 2.10, sm_121a), and moving it to ae76c60e6 requires its own build and test on that stack, which this PR's validation (main image, TE 2.18.0) did not cover and which could not be run without GB10 hardware. Upgrading GB10 is left as follow-up work, so the GB10 image's build inputs stay identical to before this PR.
