# fix(rm_hub): score the GPQA answer the reply states

[Upstream PR](https://github.com/THUDM/slime/pull/2492) · state: open · merged: False

## Original PR description

Fixes #2491

`_extract_letter_from_response` read the wrong option letter in two common reply shapes:

- `re.IGNORECASE` also applied to the `([A-Z])` letter group, so the first letter of a lowercase word counted as an answer. `The answer is definitely C.` was read as D, and `My answer is clearly D.` as C.
- It took the first match of the first pattern, and that pattern also contained `option`/`choice`. `Option A can be ruled out. The answer is C.` was read as A.

## Change

In `slime/rollout/rm_hub/gpqa.py`:

- The keywords (`answer`, `final answer`, `is correct`, `option`, `choice`) stay case-insensitive through inline `(?i:...)` groups. The letter must be a standalone capital (`([A-Z])\b`).
- Answer statements are tried before option mentions: `final answer` → `answer` → `X is correct` → `option`/`choice`.
- Within each pattern, the last valid match wins, because replies often go through the options before stating the answer.

The standalone-capital fallback and the rest of `compute_gpqa_reward` are unchanged.

One tradeoff: a lowercase letter after the keyword (`the answer is c`) no longer matches the patterns. Allowing it would read the article in `the answer is a value near …` as A. Such replies still go to the existing fallbacks, which already required a capital letter.

## Results

Each reply template filled with every row of `gpqa_eval.jsonl` from `zyzshishui0627/gpqa_diamond` (198 rows, the file `examples/eval_multi_task` uses). `{L}` is the correct letter, `{W}` a wrong one and `{T}` the correct answer text:

| reply template | right answer? | mean reward on `main` | with this PR |
|---|---|---|---|
| `The answer is definitely {L}.` | yes | 0.263 | 1.000 |
| `The answer is approximately {T}, which is option {L}.` | yes | 0.338 | 1.000 |
| `Option {W} can be ruled out. The answer is {L}.` | yes | 0.000 | 1.000 |
| `Option {L} looks tempting, but it is ruled out. The answer is {W}.` | no | 1.000 | 0.000 |
| `My answer is clearly {W}.` | no | 0.288 | 0.000 |
| `The answer is {L}.` | yes | 1.000 | 1.000 |
| `The answer is {W}.` | no | 0.000 | 0.000 |

## Tests

New cases in `tests/test_rm_gpqa.py`:

- `test_extract_letter_ignores_lowercase_words_and_earlier_option_mentions`: 7 replies, including `Final answer: C. At first I thought the answer is B.`, which checks that `final answer` still outranks a later `answer is`.
- `test_reward_scores_the_stated_answer_on_gpqa_diamond_rows`: 4 replies scored with `compute_gpqa_reward` on a row shaped like the gpqa_diamond file.

`tests/test_rm_gpqa.py`: 32 passed. On `main`, 10 of the 11 new cases fail and the existing 21 pass. (Run against `gpqa.py` alone, since it imports only the standard library; Python 3.12.0.)

Lint with the versions pinned in `.pre-commit-config.yaml` (ruff 0.14.7, autoflake 2.0.2, isort 5.13.2, black 24.3.0) passes on both changed files.

This is separate from #2411, which changes the text-substring fallback that runs when no letter is extracted. The two PRs touch different parts of `gpqa.py`.
