# fix(ray): bind trainer CPU affinity to the selected GPU

[Upstream PR](https://github.com/THUDM/slime/pull/2460) · state: open · merged: False

## Original PR description

Workers with partial or reordered GPU allocations can select one CUDA device but bind their calling thread to another GPU's CPUs: the old affinity path uses global rank modulo GPUs per node as an NVML index. 
Resolve the already selected CUDA device by its UUID instead, intersect its preferred CPUs with the thread's existing effective affinity, and read back the applied mask.

Unsupported backends, missing identity/bindings, MIG, empty intersections and NVML/affinity errors remain nonfatal. Successful NVML initialization is always balanced with shutdown. 
The operation stays at the existing initialization site and affects only the calling thread; it does not place other threads or memory.

Validation: the real TrainRayActor constructor/init regression fails on the old path (CUDA GPU 4, but GPU 0's CPU mask) and passes after this patch. All 41 new CPU tests and 29 accelerator/placement tests pass, including direct execution and pytest collection. Black, isort, Ruff and git diff --check pass. 
Registered the test in the CPU CI template and regenerated the workflow.

Read-only inspection confirms distinct NUMA masks for GPUs 0 and 4 on the local eight-GPU host. CUDA/Ray execution, actual training-thread continuity and performance remain unvalidated because no GPU allocation or running Ray runtime was confirmed.
No throughput or memory-locality improvement is claimed.
