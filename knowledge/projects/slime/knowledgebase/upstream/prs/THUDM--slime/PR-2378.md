# feat(nemotron_h): native support for the Nemotron-3 hybrid stack

[Upstream PR](https://github.com/THUDM/slime/pull/2378) · state: closed · merged: False

## Original PR description

## What this adds

Support for Nemotron-3 (`model_type: nemotron_h`) — the Nano / Super / Ultra
family. It is not a transformer stack, so it needs all three of slime's model
registries rather than a bundle alone:

| Registry | File |
| --- | --- |
| `scripts/models/<model>.sh` | `nemotron-3-super-120b-a12b.sh` |
| a Megatron-side model | `slime_plugins/models/nemotron_h.py` |
| `_LOADERS["<hf model_type>"]` | `hf_to_megatron/nemotron_h.py` + one line |

Shape, for the Super 120B-A12B: 88 layers laid out by `hybrid_override_pattern`
as 40 Mamba-2 / 40 latent-MoE / 8 attention; MoE layers project 4096 → 1024,
route 22 of 512 experts in that latent space, and project back; experts are
squared-ReLU and **ungated** (`up_proj`/`down_proj`, no `gate_proj`); NoPE;
2 KV heads.

## Design notes

**The model provider is a `--spec` target, not a layer spec.** `model_provider.py`
already delegates construction when the spec result is callable with a
`pre_process` parameter, and megatron.core has a native hybrid model class — so
unlike `qwen3_next`, which must swap a `ModuleSpec` inside `GPTModel`, this can
return a provider directly. There are no modules in the file: megatron.core has
no Nemotron class either, only a generic hybrid stack configured by arguments,
so the whole thing is a constructor call plus argument validation.

**One adapter, which I'd rather you rejected in favour of a one-line core fix.**
`NemotronHModel` subclasses `MambaModel` purely to swallow `loss_mask`, which
`model.py` sends to every model unconditionally and which `MambaModel.forward`
does not declare (`GPTModel.forward` does). It feeds only the MTP block in
`GPTModel`, and a Mamba stack has none, so dropping it is safe — it raises if
MTP is ever configured. The cleaner fix is at the call site: pass `loss_mask`
only to models that declare it. That would let every non-GPT provider drop this
subclass, and I'm happy to do it that way instead if you prefer.

**The loader refuses TP > 1**, deliberately, rather than produce a quietly wrong
checkpoint. Three things in `common.py`'s generic sharding path are wrong for
this architecture: `_tensor_parallel_shard` splits every `linear_fc1` as a fused
gate+up tensor (correct for gated MLPs, garbage for ungated squared-ReLU
experts), and Mamba's `in_proj` (`[z, x, B, C, dt]`) and `conv1d` (`[x, B, C]`)
need per-component slicing rather than a naive chunk. The docstring says what
fixing all three would take. Until then the route is
`tools/convert_hf_to_torch_dist.py` once at TP1, after which megatron.core's own
dist-checkpoint reader reshards to any TP/EP.

## What is verified, and what is not

Being explicit, because `CONTRIBUTING.md` rightly treats unverifiable features
as a risk.

**Verified, in-container on 8×B200 with megatron.core 0.16.0rc0:**

- the weight map against the real checkpoint — all Megatron parameter names the
  loader can be asked for resolve against the safetensors index of the released
  BF16 weights (42,683 tensors), including the fused-QKV shape;
- the argument bundle parses through slime's and Megatron's parsers together,
  with the hybrid arguments surviving (`is_hybrid_model`, an 88-character
  pattern, `moe_latent_size=1024`);
- megatron.core capability: `E` in the hybrid symbol alphabet, a `moe_layer`
  slot in `mamba_stack_spec`, `TransformerConfig.moe_latent_size`;
- the loader's TP guard actually fires;
- the model provider imports and is callable from a Ray worker, not just the
  driver.

**Not verified — no training step has run with this code.** The checkpoint
conversion was still queued when this was opened, so neither the HF → torch_dist
conversion nor a forward/backward pass has completed. I'd rather say that than
imply otherwise.

Also worth knowing: the checks above were run against this code in its previous
out-of-tree form (a `--custom-model-provider-path` plugin). The move into the
tree changed the entry point to `--spec` and the import paths; the layout in
*this* commit has not been re-run through them.

**CI impact:** `tests/test_hf_to_megatron.py` only gains one key in
`test_loader_scope_stays_explicit`. It runs on CPU without Megatron installed,
so nothing here lengthens CI. I can add a loader-level mapping test in the style
of the existing `test_qwen_and_llama_share_the_basic_qkv_mapping` if you'd like
the map itself covered — say the word and I'll push it.

## Not included

- **The Megatron → HF exporter.** RL weight sync to SGLang needs it; SFT does
  not, and it would also need SGLang to recognise the architecture. Left out
  rather than half-done.
- **MTP.** The released checkpoints ship a Multi-Token-Prediction block;
  `MambaModel` has no MTP, so those tensors are never requested. A model trained
  through this path is the backbone without its speculative-decoding head.
