# fix(reward): guard expensive powers and factorials

[Upstream PR](https://github.com/THUDM/slime/pull/2517) · state: open · merged: False

## Original PR description

Fixes #2515.

`math` and `deepscaler` rewards can get stuck evaluating `9**9**9` or `(10^9)!` against a fractional label. The existing text checks miss Python power notation and large factorial arguments.

Before SymPy evaluates an expression, inspect its token-transformed syntax tree and bound numeric exponent/factorial arguments to 1,000. Numeric estimates use floating-point arithmetic to avoid constructing enormous integers. Symbolic arguments remain supported, including `(n+1)!`, `(2^3)^x`, and small negative powers. Existing caret filters and exact-match shortcuts remain in place. This is a guard for expensive numeric powers/factorials, not a general timeout for arbitrary SymPy simplification.

The related radixark/miles#4454 addresses power spellings but not the factorial case; #2416 moves scoring off the event loop but does not bound the computation. No matching slime fix was found in the issue timeline or searches for `2515` and `math reward`.

Validation on CPU, Python 3.12.13 / SymPy 1.14.0 / pylatexenc 2.11:

```bash
PYTHONPATH=. python -m pytest -q tests/test_rm_math.py tests/test_rm_math_dapo.py
# 78 passed
pre-commit run --files slime/rollout/rm_hub/math_utils.py tests/test_rm_math.py --show-diff-on-failure
# passed
```

The new guard tests fail on main (11 failed, 40 passed, excluding the subprocess regression so baseline CI cannot hang). The fixed subprocess test exercises both reported inputs through both graders and a correct fractional control. An additional comparison preserved all 48 bounded benign/control results, and the actual `async_rm` dispatcher returned 0 for both bad inputs and 1 for the control under both reward types. Existing CPU CI already runs `test_rm_math.py`. No GPU or end-to-end training was run.
