# build(docker): upgrade Megatron to NVIDIA/Megatron-LM dev ae76c60e6 (core 0.20.0)

[Upstream PR](https://github.com/THUDM/slime/pull/2493) · state: closed · merged: False

## Original PR description

## Summary

Upgrades the pinned Megatron-LM from `4b4acac9a` (core 0.19.2) to `ae76c60e6c35d913867d6dd7bad0f30b128b54e7` (core 0.20.0) and regenerates both Megatron patches for `docker/patch/latest` and `docker/patch/v0.5.21` (identical copies). SGLang stays on v0.5.21; nothing SGLang-related changes.

## Patches (`docker/patch/{latest,v0.5.21}/`)

`megatron.patch` was regenerated against the new base: 11 files / 34 hunks -> 9 files / 20 hunks.

- Dropped, because upstream now carries them: the grad/param buffer CPU-backup plumbing (`param_and_grad_buffer.py`) and the fused MLA YaRN Triton kernel fixes (`fused_mla_yarn_rope_apply.py`).
- Adapted: the `GPTModel` `mtp_kwargs` hunk, the checkpoint-loading hunks (`strategies/torch.py`; `stream_ckpt_dequant` removed because upstream dropped it), and the `argument_utils` help escaping (`%` -> `%%` on top of the new prefix logic).
- Narrowed: the `HybridDeviceOptimizer` change is now only `update_fp32_param_by_new_param`.
- `megatron-sglang-aligned.patch`: ported to the new `TransformerLayer` (hyper-connection / residual refactor); applies cleanly on top of `megatron.patch`.

## slime changes

- `slime/backends/megatron_utils/initialize.py`: registers the run config newer Megatron reads (`pretrain_cfg_container_from_args` / `set_run_config`), with a fallback for older Megatron.
- `docker/Dockerfile`, `build_conda.sh`: pin the new commit and install `nvidia-resiliency-ext==0.7.0` (only declared in Megatron's `dev` extra, but needed for cached checkpoint metadata); the core version assertion is now 0.20.0.
- `docker/README.md`: pinned-component text updated.
- `slime/utils/arguments.py` (071e504a): Megatron ae76c60e6 only offers `--async-strategy nvrx`, so slime now forces the default to `mcore` only when the parser still lists it. Without this, startup fails with `async_strategy mcore is not supported`. Covered by a new unit test in `tests/test_megatron_argument_validation.py`.
- GB10 (ec6eced0): `Dockerfile.gb10` pins Megatron `3714d81d` on a separate stack (TE 2.10), so it must not receive the new patch. The previous `latest` patch is frozen as `docker/patch/gb10/megatron.patch` and `Dockerfile.gb10` copies it, so the GB10 image is unchanged by this PR.

## Validation

`tests/test_glm52_6layer_deterministic_e2e.py` (`MEGATRON_USE_SGLANG_FUSED_RESIDUAL_RMS=1`, i.e. the flag-on path of `megatron-sglang-aligned.patch`) on the `slimerl/slime:latest-cu130` image with both patches applied:

| Megatron | `train_rollout_logprob_abs_diff` | bound | result |
|---|---|---|---|
| ae76c60e6 (new) | 1.5667e-07 | 1e-6 | 2 passed |
| 4b4acac9a (old) | 1.5667e-07 | 1e-6 | 2 passed, identical to every digit |

Also checked on a single GPU: the patch's RMSNorm helper is bit-identical to SGLang's `RMSNorm.forward_native(x, residual)`; against `sgl_kernel.fused_add_rmsnorm` only a few elements differ by 1 ulp. The unpatched bf16-rounded boundary differs in ~20% of elements. Two real `TransformerLayer`s with the flag on vs off show the same error against an fp32 reference.

## Known limitations

- The gate was run on 2 nodes x 8 H100 (EP16), not the test's default single-node 8-GPU layout. With 80 GB GPUs the single-node layout OOMs in `deepgemm_moe_forward.py` backward (~71 GB); this happens identically on the old Megatron, so it is not a regression. The test file in the repo is unchanged.
- The GB10 image was not built here; it is intentionally left on the pre-upgrade patch. Upgrading GB10 needs a separate test of `ae76c60e6` on its stack.

- shifangx · comment · 2026-10-27T01:58:52Z · [source](https://github.com/THUDM/slime/pull/2493#issuecomment-6431851635)

https://github.com/THUDM/slime/actions/runs/40433113947/job/121955323800?pr=2493
cpu-unittest (0, true, test_rollout_straw_transport.py) fails because of a behavior change in straw-queue, not because of this PR's code.

tests/test_rollout_straw_transport.py::test_failed_flush_does_not_publish_a_reference injects OSError("shared storage flush failed") at the before_directory_sync phase and expects pack_rollout_payload to raise StorageUnavailable.

Starting with straw-queue 0.1.4, the same fault surfaces as:

straw.errors.IndeterminateCommit: Incomplete publication cleanup must finish before reuse: OSError: shared storage flush failed

IndeterminateCommit and StorageUnavailable are sibling classes (both subclass QueueError directly), so pytest.raises(StorageUnavailable) does not catch it. The CI workflow installs straw-queue>=0.1.3 with no upper bound, so it picks up the latest release.

Reproduction (GPU node, image slime:v0.3.2-cu129, Python 3.12; the other 86 tests pass in every case):

| straw-queue | Result |
|---|---|
| 0.1.3 | 87 passed |
| 0.1.4 | 1 failed (this test) |
| 0.1.5 | 1 failed (this test) |

Caveat: I could not read the CI logs (sign-in required), so that CI installed 0.1.4 or newer is inferred from the matching failure rather than confirmed line by line.

Options for the fix

1. Update the test (recommended). Accept both exceptions: pytest.raises((StorageUnavailable, IndeterminateCommit), match="shared storage flush failed"). The test then writes again and reads back; on 0.1.4+ that step may hit the "cleanup must finish before reuse" state, so it may need adjusting. I have not verified this part yet.
2. Pin the dependency. Set straw-queue==0.1.3 in pr-test.yml and pr-test.yml.j2. This is quick but only hides the change, and later releases will hit it again.
3. Normalize in source. If pack_rollout_payload is meant to expose StorageUnavailable for flush failures, catch IndeterminateCommit and re-raise it as StorageUnavailable. This depends on the intended contract, and on whether callers need to tell "indeterminate commit" apart from "storage unavailable".

I prefer to go with option 1, plus an upper bound on the version range to avoid surprise breakage from future straw-queue releases.
