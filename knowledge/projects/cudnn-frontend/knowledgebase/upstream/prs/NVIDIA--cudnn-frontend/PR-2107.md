## Affected area

FE OSS kernels or CuTeDSL

## Summary

`conv/frost/engine.py::_check_sm100` raised `NotImplementedError("frost_conv requires SM100, but found 103")` on a B300. The conv tests gate on `100 <= SM < 120` (`conv/frost/utils.py::requires_sm100`), so on cc 10.3 they ran and failed: no engine proposed a plan, or the gate raised.

The gate now accepts 100 and 103. The SM100-family conv templates (`templates/sm100_conv.py`, `templates/sm100_block_scale_conv.py`) compiled with `options="--enable-tvm-ffi"` only, so CuTe DSL picked the target, and they cached the artifact by shape, tile and epilogue alone. With both parts admitted, a process that built a convolution on SM100 would get that SM100 launchable back for the same graph on SM103. So:

- `_cutedsl.build_target()` names the build device (`cudnn.frost.device.current_device()`, the handle's inside `build_plan`) and its target: `sm_100a` on cc 10.0, `sm_103a` on cc 10.3.
- Both templates key their compile cache on that pair, and compile under that device's context with an explicit `--gpu-arch`. The dense `compile` resolves the pair and calls a cached `_compile_cached`.
- `test_block_scale_compiler_cache_keys_on_the_build_device` and `test_dense_compiler_cache_keys_on_the_build_device` model an SM100 and an SM103 GPU in both orders, with `cute.compile` recorded.

## Why

cc 10.3 runs the same templates; only the gate refused it.

## Related issues

None found.

## API and compatibility impact

None on cc 10.0. On cc 10.3, FROST conv graphs are now planned instead of declined.

Not run on cc 10.0, where the gate admits the part as before.
