## Summary

- `_CompiledFusedGemm` gets two methods next to `workspace_bytes_for(batch, m, n)`:
  - `workspace_bytes_for_operands(operands, graph_order)` reads M off A and N off B the way the launch path reads them (`Operand.axes`, including the graph-order flags of slots the variant pack describes from the graph: bare addresses, and dense buffers of other extents that it re-describes as the declaration). It returns `workspace_bytes_for(recipe.batch, m, n)`. If the A or B layout cannot be located, it returns 0, because the launch path refuses that layout before it reads the workspace.
  - `workspace_bytes_for_overrides(override_uids, override_shapes)` reads M and N from the override dims of A and B (graph order; the recipe's declared axes handle swap-AB). For an extent the list does not give through A or B, it reads the override dims of a named output whose shape follows that extent: the dense output, or a per-row or per-column reduction (`Output.rule`, which is in graph order). Only an extent that no named tensor carries keeps the plan's own value.
- `_FrostGemmPlan.get_workspace_size_for_shapes` and `_FrostGemmPlan.execute` call these methods instead of reading `binding.outputs[0]`. `execute` now computes the graph-order flags before the workspace pre-check; it used to compute them just before the launch.
- `workspace_bytes_for(batch, m, n)`, the build-time `workspace_bytes`, the launch path (`lowered`) and the kernels do not change.
- Two new SM120 tests (3 cases in all).

## Why

Found in an audit of the SM120 Frost kernel templates (finding G8.2).

A workspace split-K plan writes `S * B * M * N` fp32 partials whatever its outputs are. This covers `sm120_matmul.py` and `sm120_block_scale_matmul.py`, whose partials `split_k_reduction_epilogue_fusion.py` then reduces. The launch path takes M from A and N from B (`lowered` in `compiler.py`: `m, n, k = (a_sh[1], b_sh[1], ...)`, then `workspace.view(0, "float32", (split_k_slices * batch * m * n,))`). The engine sized that region from output 0 instead:

- `get_workspace_size_for_shapes` took `(b, m, n)` from the override shape of `binding.outputs[0]`. This is what `graph.get_workspace_size(...)` and `get_workspace_size_plan_at_index(...)` return when override shapes are given. If the override list did not name output 0, it returned the plan's build-time size.
- `execute()` took its pre-check size from the shape of the output-0 buffer.

Outputs are bound in chain slot order: dense outputs first, then reductions. A graph whose only outputs are reductions is supported (`test_dense_amax_only_no_dense_output`), and in such a graph output 0 is the reduction, of shape `[B|1, M|1, N|1]`. At 24a8cd43 the automatic pick (`_auto_split_k` in `sm120/compiler.py`) splits K for these graphs when all of these hold:

- The output grid has at most half as many tiles as the GPU has SMs, so two K slices fit in one wave.
- K spans at least 2048 bytes, and each slice gets at least two K tiles.
- `_splitk_reject_reason` accepts two slices.
- No reduction would serialize the reducer (`_splitk_reduction_serializes`), and none is an fp32 ADD, AVG, NORM1 or NORM2 over all of M and N.

A per-row AMAX, MAX or MIN passes both reduction rules; the example below is the engine's own pick. An explicit config or a replayed `SPLIT_K_SLC` record also reaches these graphs.

Reproducer on develop 24a8cd43 (RTX PRO 6000, SM120), through the cuDNN graph API with the FROST plan selected. The graph is bf16 A `[1,16,4096]` and B `[1,4096,4096]` (K-major), then matmul -> AMAX `[1,16,1]` (fp32) as the only output, with uids 1, 2, 3. The engine picks `CONFIG_sm120_32x64x128_16x16x32_cluster1x1_warps2x4_splitK2` on its own.

| Call | Base 24a8cd43 | Kernel 1 writes |
|---|---|---|
| `g.get_workspace_size()` | 524288 | 524288 |
| `g.get_workspace_size(h, [1,2,3], <same shapes>, <strides>)`, and `get_workspace_size_plan_at_index(...)` | 128 | 524288 |
| the same with M overridden to 32 | 256 | 1048576 |
| `execute` with these overrides and a torch buffer of the reported 128 bytes | `ValueError: frost_gemm: workspace overrun — region [0, 524288) exceeds the 128-byte buffer (sizing bug)` | |
| `execute` with these overrides and a raw int workspace inside a canary arena | runs; 524288 bytes changed, 524160 of them past the reported 128 | |

A per-column AMAX `[1,1,N]` (bf16 128x256x1024, a pinned `..._splitK2` plan, normal and swap-AB) shows both mechanisms:

- The query with A, B and the reduction overridden at the same shape returns 2048 (needed 262144).
- An override of A alone at M=256, which leaves the reduction's shape unchanged, returns the build-time 262144 (needed 524288).

With this change, all of these return the size kernel 1 writes. A buffer of that size runs and matches torch exactly, and the canary arena is not written past it.

Why this approach:

- The region is sized from what the kernel writes over: the A and B extents, read the way the launch path reads them. The execute pre-check and the view `lowered` takes now agree, and the override query agrees with them whenever the list names a tensor that carries each changed extent (see API and compatibility impact).
- An override list may name an output and leave A or B out, while a strided view of that operand (which keeps its own description in the variant pack) runs at a new extent. The launch path refuses a call whose outputs do not follow A's M and B's N, so a named output that follows M or N gives that extent for every call that runs. The query reads it there when A or B is not named, as 24a8cd43 did for a dense output named alone. Override dims count elements, so there is no fp4 `n // 2` to undo (split-K declines a packed fp4 output anyway).
- The defect lives in the shared `engine.py`. The A/B bookkeeping it needs (the launch recipe) lives on the shared `_CompiledFusedGemm`. The sm120 tree has no code on this path: its `CompiledFusedGemm` only binds the compiler module, and the engine handed it nothing but output 0's shape. So the fix cannot stay inside `python/cudnn/gemm/frost/sm120/`.
- Raw-address workspaces stay accepted. The graph API accepts them for every engine (`_pygraph._workspace_extent_fallback`: "A raw address carries no observed capacity"). The audit also suggested refusing split-K calls of unknown capacity in `lowered`; that would reject this supported use, so it is not done here. What protects a raw-address caller is a correct size from the query.
- A measured buffer that is too small is still refused before any reduction seed or launch. Now the engine's pre-check refuses it with `needs a N-byte workspace`; for reduction-only graphs this used to be the launch path's "(sizing bug)" message. Rule 1: no allocation, conversion or device read is added on the execute path.

## API and compatibility impact

- On a FROST split-K plan, `graph.get_workspace_size(...)` and `get_workspace_size_plan_at_index(...)` with override shapes now return `align_up(S * B * M * N * 4)` for the overridden A and B extents:
  - For a graph with a dense output whose overrides name A, B and that output consistently, the value is the same as before.
  - For a reduction-only graph, the value grows to what kernel 1 writes.
  - For an override list that names neither A nor B, M and N come from a named output whose shape follows them (the dense output, or a per-row or per-column reduction), as 24a8cd43 did for a dense output named alone.
  - An extent that no named tensor carries keeps the plan's value, so such a list under-reports when an unnamed strided view runs at a larger extent; 24a8cd43 under-reports it too. Measured: bf16 128x256x1024 -> per-row AMAX on the pinned `..._splitK2` plan, a list naming only the reduction, and B an unnamed strided view at N=512. The query returns 262144 (24a8cd43: 1024), and kernel 1 writes 524288 bytes into a raw-address workspace. A torch buffer of the reported size is refused (`needs a 524288-byte workspace`), with the output left unseeded.
- On such a plan, `execute()` with a measured workspace that is too small now raises `frost_gemm: needs a N-byte workspace, got M bytes (size it with graph.get_workspace_size())` before the launch path runs. Reduction-only graphs used to raise "workspace overrun ... (sizing bug)" from the launch path; dense-output graphs already raised the first message.
- No numerics or kernel change. Plans without workspace split-K (workspace 0, including cluster split-K) and MoE plans do not take the new code.
- SM100: the changed code is shared, so SM100/SM103/SM107 split-K plans take the same path and get the same fix. At 24a8cd43 the sm100 tree has no copy of the defect of its own: the `workspace_bytes_for` the audit found in `sm100/compiler.py` now lives only in the shared `compiler.py`, and `sm100/compiler.py:2533` (`_splitk_workspace_bytes`, the build-time size) is correct. `sm100/compiler.py:2811` (`_splitk_reject_reason`) admits reduction-only split-K chains as well. None of this was run on SM100 hardware (none available), and no SM100-family CI lane runs a detector for the changed paths. The new tests are `@requires_sm120` and pin an SM120 config. The SM100-gated tests that query the workspace with overrides (`test_override_shape_frost`, `test_flashinfer_shaped_gemm.py`) use dense-output graphs whose lists name A, B and the output, which 24a8cd43 already sized correctly.
