## Summary

`benchmark/norms/benchmark_cudnn_vs_frost.py` compares "cuDNN native norm vs cuDNN frost norm". Its `cudnn` worker (`_norm_bench_worker.run_cudnn`) builds the LayerNorm / RMSNorm graphs with the default dispatch.

The FROST norm engines are default candidates on cc 10.0 and 10.3, and on cc 9.0 behind the opt-in. On those parts the "native" leg therefore built `norm_fprop_sm100` / `norm_bprop_sm100`, so the script compared FROST against FROST.

The worker now bars the `frost_norm_fwd` / `frost_norm_bwd` families by name before planning, as `benchmark_single_sdpa.py` does for FROST SDPA on its backend leg. It also prints the plans each graph built (a `PLANS` line), so the leg's route is visible in the output. The `RESULT` line and its parsing are unchanged.

## Why

On SM100 / SM103 the script's speedup column was not a FROST-vs-backend comparison.

## Testing

B300 SXM6 (cc 10.3), cuDNN 9.27.0.42, develop `af1a5181`, an 8192 x 4096 bf16 graph:

- develop: the `cudnn` worker built `norm_fprop_sm100` and `norm_bprop_sm100`, for both RMSNorm and LayerNorm;
- this change: it builds `eng5_k14=0_k24=0_k33=0_k34=1_k35=0_k36=1_k42=0` (forward) and `eng4_k14=1_k24=2_k30=-1_k33=0_k34=0_k35=2_k36=-1` (backward), both backend plans.

With the fix, `benchmark_cudnn_vs_frost.py` over all 15 model presets on that B300 gives these FROST / backend speedups:

| dtype | forward geomean (range) | backward geomean (range) |
|---|---|---|
| bf16 | 1.03x (0.76-1.24) | 0.98x (0.90-1.09) |
| fp16 | 1.03x (0.76-1.38) | 0.99x (0.76-1.18) |

FROST's correctness check against torch passed in every run. The per-preset table is in the script output.
