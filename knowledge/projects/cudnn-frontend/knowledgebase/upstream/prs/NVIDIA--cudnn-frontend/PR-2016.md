## Summary

The SM120 dense block-scale GEMM no longer runs a call whose declared F8_128x4 scale-factor (SF) layout it would read from the wrong rows.

- **Declared layouts, at `check_support`.** `_precheck_block_scale` (the gate behind `check_support` and `jit_from_cudnn_graph`) calls the new `_dense_sf_declaration_reject`. It declines a declared SFA / SFB that `_dense_sf_misread` rejects at the declared problem size. `k4 = ((K // block) + 3) // 4` (the template's `rest_k`) is its atom count per 128-row block. The rules:
  - when dim 0 counts more than one batch plane, each plane, padded to whole 128 x 4 atoms, must span exactly the template's plane;
  - SF-K must be exactly `k4` atoms when the template reads more than one 128-row block in all; with one row block it must be at least `k4`.

  These declarations are still accepted: logical (`[b, M, K / block]`), padded to whole atoms, batch 1 with more rows than M, K padding with one row block, and `[1, b x rows, SF-K]` (the batch planes stacked as rows, which is the template's own order).
- **Declared layouts at another problem size, at execute.** The sm120 `CompiledFusedGemm` wraps the shared launch closure. A plan can run another problem size than it was declared for: through execute-time overrides on the engine route, or A/B buffers of other extents on the direct path. At that size the same rule is checked against the declared SF. If the template would misread it, the call raises `ValueError` before any output is seeded or the kernel is launched.
  - The only exception is an SF slot whose extents are exactly the run's own SF extents (`_dense_sf_run_extents`): `(batch, rows, SF-K)` with rows and SF-K each logical or padded to whole 128 x 4 atoms, or `[1, batch x padded rows, padded SF-K]` (the planes stacked as rows), each in kernel or graph orientation. That covers an SF override to the run's extents and a buffer bound with exactly those extents.
  - Every other binding of the declared SF is refused, including other views of the same bytes: `(1, 512, 16)`, `(4, 128, 16)`, `(512, 16, 1)` or a flat blob of a `[2, 256, 16]` declaration.
  - The message names the graph's tensors and extents, swap-AB plans included. `deferrals` counts the refusal under `"scale-factor layout"`.
  - A call at the declared problem size skips the check after comparing the A/B extents.
  - A call that reads no scale factor is not judged: M or N = 0, or K below one scale block (K / block = 0). For such a call the pitch rules would compare the declaration with an empty plane. At M or N = 0 they would call any declaration of several batch planes misplaced, the packed one included. At K below one block they would also object to any declaration read over more than one 128-row block in all, batch 1 included. The call goes on to the launch path, which owns zero extents (see #2021 under Related issues). From K = block size on (one scale per row, one atom per row block), a call is judged like any other.
- **Bound buffers at the declared problem size.** A buffer's own extents are not read as a layout there. It supplies pointer, bytes and alignment, as the declaration contract says. So a larger buffer that holds the packed blob at its start, and any dense view of the blob, run as before. (At another problem size, a buffer's extents only decide whether the call runs, as above.)
- **#2008's per-call tests.** This PR's check refuses the K = 144 call of #2008's dense per-call test before #2008's own guard does. That test now checks the refusal by its effect (`ValueError`, no launch, output untouched) and accepts either message, and the MoE per-call test gets the same launch recorder. This is 1adac04a from the B01 branch, carried here because #2008 merged without it (see Related issues).

## Why

Found in an audit of the SM120 Frost kernel templates (finding B29).

`sm120_block_scale_matmul.py` takes each SF operand as a base pointer and rebuilds its TMA view from the call's M/N/K alone. In `_host`:

- `rest_k`, `rest_m` and `rest_n` are computed at `:810-812`;
- the SFA view is built at `:849-858`, and the SFB view at `:905-914`.

The view is `k4` atoms of 512 B (128 rows x 4 scales) per 128-row block, then the row blocks of a batch plane, then the planes, back to back. The SF tensor's own shape and stride are never read.

At 24a8cd43 nothing compared the declared SF dims with that read:

- `_precheck_block_scale` has no SF-dim rule;
- the per-call gate (`lowered` in `python/cudnn/gemm/frost/compiler.py:1129-1141`) checks only rank 3, 16-byte alignment, one dense byte run and a lower bound on the byte count.

**Reproducer.** RTX PRO 6000 (SM120), MXFP8 (e4m3 data, E8M0 scales, block 32), K = 512, N = 128 unless noted, fp16 out. The FROST plan is taken from the engine route. Buffers are laid out as declared. Results are max |error| per batch (max |ref| 38.8 to 44.9):

| Graph | FROST at 24a8cd43 | cuDNN engine 0 | cuDNN engines 7 and 10 |
|---|---|---|---|
| SFA `[2, 256, 16]`, M = 100 | batch 1: 38.8 | batch 1: 38.8 | 0 |
| SFB `[2, 16, 256]`, N = 100, M = 128 | batch 1: 44.9 | (not offered) | 0 |
| SFA `[1, 256, 32]`, M = 256 | rows 128..255: 44.9 | rows 128..255: 44.9 | 0 |
| built at M = 256 with SFA `[2, 256, 16]`, run at M = 100 with A and O overridden, SF not overridden | batch 1: 38.8 | batch 1: 38.8 | 0 |

The backend columns cover every backend plan the heuristics (A + FALLBACK) list for these graphs on cuDNN 9.24.

The same sweep shows three more things:

- Under a packed declaration, a `(2, 256, 16)` buffer is read as the packed blob at its start, by FROST and by every backend engine. At the declared size, a buffer's own extents carry no layout.
- An SF overridden to the run's extents (`[2, 128, 16]`) is read the same way by all engines.
- An SF overridden to `[2, 256, 16]` at M = 100 is read as declared by engines 7 and 10, and as the packed blob by engine 0.

So the declaration is the contract, as `docs/utilities/python_graph_and_execution_backends.md` says ("the buffer supplies pointer, bytes and alignment"). Engine 0 has the same misread as FROST. That is outside this repository and should be reported separately.

**Why this fix.**

- A declaration FROST cannot read where it lies is declined at `check_support`, so the router can pick another engine. This follows Rule 2 of `python/cudnn/AGENTS.md` (serve the declared layout natively, or decline) and the "Accept means run" section of `docs/utilities/python_graph_and_execution_backends.md` (what is decidable from the declaration is decided at `check_support`).
- A problem size that first appears at execute is checked at execute and refused before the launch. The overrides paragraph of the same document says execute-time override geometry "must be supported by the selected plan", and Rule 1 asks for a raise before the launch rather than a dropped override. The shared closure's runtime-quant check works the same way.
- At another problem size, the exemption is decided on the SF slot's extents alone, because the compiled GEMM does not learn which slots were overridden (the shared engine passes only the graph-described flags). A slot of exactly the run's SF extents is either an override that declares the run's packed layout, which every engine reads alike, or a buffer bound with exactly those extents. Every other binding is refused.
  - For the declared bytes, in any view, the refusal is required: they keep batch 1 where the template does not read it at this size.
  - It is also deliberately conservative. A flat or 2-D buffer of exactly the run's packed bytes is smaller than the declared layout and cannot hold it, but only extents are compared, so it is refused too. FROST and engine 0 would read such a buffer correctly; engines 7 and 10 read past its end. The remedy is to bind it with the run's extents or to override the SF to them.
- A call that reads no scale factor (M or N = 0, or K below one scale block) has nothing to misread. The check leaves it to the launch path instead of replacing that path's handling of zero extents with a refusal whose remedy cannot be followed ("override SFA to [2, 0, 16]").
- The review also suggested exempting any slot whose byte span is smaller than the declared layout's. That rule would also exempt an SF override to a smaller, non-packed pitch. Example: SFA overridden to `[2, 256, 16]` at M = 100 on a graph declared `[2, 384, 16]` at M = 300. Engines 7 and 10 honour such an override, and the template would misread it.
- The alternative from the audit is to pass the pitch into the TMA descriptor, as the MoE weight-SF path does with its expert stride. That would serve these layouts instead of declining them. It needs template changes, so this PR keeps to the smaller change.

**Why only the sm120 tree.** The template and the dense block-scale gate belong to the sm120 tree. The shared closure in `compiler.py` is wrapped by the sm120 subclass, not edited. SM100 behaviour is unchanged.

## API and compatibility impact

- **Newly declined graphs.** These are SM120 dense block-scale graphs, declined by the FROST engine's `check_support` and by `jit_from_cudnn_graph`:
  - a declared SF whose planes, padded to whole atoms, do not span exactly the template's plane, when dim 0 and the batch are both above 1;
  - an SF-K that is not `k4` atoms when more than one row block is read, or narrower than `k4`.

  The router then picks a backend plan. Engines 7 and 10 compute these graphs correctly; engine 0 has the misread described above.
- **Newly refused calls (`ValueError` before launch).** A call at another problem size whose declared SF would be misread at that size is refused, unless the SF slot has exactly the run's own SF extents (an SF override to them, or a buffer bound with exactly them).
  - Example: built at M = 256 with SFA `[2, 256, 16]` and run at M = 100. The declared bytes are refused whether they are bound as `(2, 256, 16)`, `(1, 512, 16)`, `(4, 128, 16)`, `(512, 16, 1)` or flat.
  - The remedy is to override SFA to `[2, 128, 16]` along with the A and O overrides, as cuDNN's dynamic-shape quantize test and FlashInfer's MXFP8 override path do, or to bind a buffer of exactly those extents.
  - A flat or 2-D buffer of exactly the run's packed bytes, with no SF override, is refused too: in the example, the run's 4096-B blob bound flat or as `(256, 16)` (the engine route reshapes a flat blob to `(b, bytes // b, 1)`). This is conservative, since such a buffer cannot hold the declared layout: FROST and engine 0 would read it correctly, engines 7 and 10 read past its end. Bind it as `(2, 128, 16)` or override SFA to `[2, 128, 16]`.
  - Only the slot's extents are compared, never its contents. So the declared-size `(2, 256, 16)` buffer is refused even when it holds the run's packed blob at its start, unless SFA is overridden to `[2, 128, 16]` as in the remedy above.
  - **Rule 9 note.** On such calls the backend's own engines disagree:
    - With the SF left at its declaration, engine 0 reads the run's packed blob and engines 7 and 10 read the declared pitch. FROST cannot read the declared pitch, so it refuses instead of silently matching one of them.
    - With the SF overridden to the run's extents, all engines and FROST agree.
    - With a buffer of exactly the run's extents and no SF override, FROST and engine 0 read it as the run's packed blob, while engines 7 and 10 read the declared pitch past the buffer's end. That is an out-of-bounds read: batch 1 comes out wrong or NaN, depending on the plan and the binding. FROST runs this call, because that buffer cannot hold the declared layout.
    - This refusal is decided from the declaration together with the override geometry (or the direct path's A/B extents), after `check_support` accepted the plan. So it is also an exception to the "Accept means run" section, which says nothing decidable from the declaration may refuse a call after acceptance. It rests on that document's overrides paragraph ("geometry must be supported by the selected plan") and on the backend engines' own disagreement on these calls.
- **Unchanged.**
  - Every binding at the declared problem size runs as before: packed, flat, `view(1, 1, -1)`, the engine's `(b, bytes // b, 1)` view of a flat blob, a larger buffer holding the packed blob, and other dense views of the blob.
  - Override runs whose declared SF is still read where it lies at the run's size also run unchanged, for example batch 1 with the same K.
  - So do runs with the SF overridden to the run's extents, which is what FlashInfer's MXFP8 override path passes.
  - A call that reads no scale factor (M or N = 0, or K below one scale block) is not judged by this check and reaches the launch path as on develop. There, since #2008, a K between 0 and one scale block is refused as a partial scale block (checked at K = 16 after the develop sync). Without #2021 an empty call or K = 0 still aborts the process (the zero extent reaches `cuTensorMapEncodeTiled`, and the DSL turns the failure into an abort); this PR does not change that. With #2021 the empty call skips the launch (only a plan's reduction seeds are written) and the K is refused.
  - MoE and plain GEMMs are unaffected.
- **Residual, not addressed.**
  - Bytes laid out at another pitch than their declaration states are read as declared. That is the caller's contract, and every engine does the same.
  - An SF override with a non-packed pitch is read as the packed blob, as engine 0 reads it, while engines 7 and 10 honour it. This happens only when the declared SF is still read correctly at the run's size. The compiled GEMM does not learn which slots were overridden: the shared engine passes only the graph-described flags.
  - Known limit: a stacked declaration `[1, B x rows, SF-K]` has no plane pitch to check, so at another M or N it is read at the run's own pitch and not refused (a K change is still checked). Bytes laid out as that declaration states are then misread. Example: built at M = 256 with SFA `[1, 512, 16]` (batch 1 at row 256), run at M = 100 with A and O overridden. FROST and engine 0, the only backend engine offered for that graph, both give batch 1 wrong (38.8), and both read the run's packed blob in the same buffer correctly. So there is no Rule 9 disagreement, but it is the pattern this PR refuses for `[2, 256, 16]`. It is left unchanged here.
  - Follow-up, not in this PR: have `_FrostGemmPlan.execute` pass `VariantPack.overridden` to the launch (a small shared `python/cudnn/gemm/frost/engine.py` change), so the sm120 wrapper can check an overridden SF slot's geometry at any size. Alternatively, serve the pitch through `problem_size` as the MoE weight-SF path does.
- **Host cost** (host-only `timeit` on this machine, engine route):
  - about 0.22 µs per dense block-scale call at the declared problem size, for the A/B extent comparison;
  - about 4.4 µs for a call at another size, for the full check, measured on a FlashInfer-style call that runs (4.1 µs with the round-1 rule).
  - There is no GPU work, allocation or device read.
- **SM100 (follow-up).** The same template SF views exist in the SM100 tree, which this PR intentionally leaves for a follow-up:
  - `python/cudnn/gemm/frost/sm100/kernel_templates/sm100_block_scale_matmul.py:1590-1592` and `:1635` / `:1690`;
  - `sm103_block_scale_matmul.py:1540` and `:1568` / `:1606`.

  `sm100/compiler.py:2688` `_precheck_block_scale` has no SF-dim rule either.
