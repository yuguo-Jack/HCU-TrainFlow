## Affected area

FE OSS kernels or CuTeDSL

## Summary

`DENSE_SERVING_CCS` held cc 10.7 and cc 10.0. Its comment declined cc 10.3 by name: "cc 10.3 (B300) runs the same SM100 kernels but is unproven through the block: DECLINED BY NAME until its cells run". Those cells have now run on a B300, so the tuple gains `(10, 3)`.

On cc 10.3 the block now serves the dense prefill, EXTEND and DECODE inference forms through the same SM100 d256 kernels. The cc 10.0 declines still apply there:

- `fuse_gate`
- the fused projection forks
- the quantized pipelines other than the FP8-projection mode below
- `save_for_backward`
- `thd=True` over the block's own K / V
- a QsaSpec geometry
- the 32-column decode arm

`FP8_PROJ_BF16_ATTENTION_CCS` gains `(10, 3)` as well (second commit): the FP8 forced-tile GEMM cell at the mode's shapes, which admits a part into that tuple, and the mode's DECODE / EXTEND cells ran on the B300. The launch-census table gains its cc 10.3 row (8 / 7, the cc 10.0 counts, measured by the census there). `decode_route(device_cc=(10, 3))` reads the SM100 line's rule, the same cells as cc 10.0 with `device_cc` (10, 3). This follows from the existing `cc != (10, 7)` line test, so no routing code changed.

Text changes:

- `api.py`: the module docstring, the `DENSE_SERVING_CCS` comment, the `decode_route` docstring, and the dense part statement ("cc 10.0 / 10.3 (SM100 / SM103: ...)"; the cc 10.3 suffix is gone).
- `SUPPORT_MATRIX_TRACKER.md`: an "Admitted 2026-10-31" paragraph with the run record (Rule S2), the cc 10.3 run record of the FP8-projection mode, the gaps row, and the sentences that called cc 10.3 declined / unserved.

The tests pinned the device to cc 10.0 in several places. On a B300 with only the tuple changed, 61 cases failed on these pins before reaching any oracle compare. They now read the device's own part:

- `_sm100_pin`: the compiled route's `device_cc == _cc()`.
- The decline texts on the part: `cc {major}.{minor}` and `this device is SM{major}{minor}`.
- The FP8-mode branch: `_cc() in FP8_PROJ_BF16_ATTENTION_CCS`.
- The extend envelope's `device_cc`.
- `_sm100_pin_extend` on the packed-KV EXTEND case also pins on cc 10.3.

The host rows change too:

- `test_the_sm100_route_table_is_the_adapters_rule` asserts that `decode_route(device_cc=(10, 3))` equals the cc 10.0 cell with `device_cc` (10, 3). Only sm80 is left as the unserved probe.
- `test_the_envelope_declines_every_other_part_without_raising` drops its `sm103` case.
- The conftest marker texts name both parts.

## Why

The block declined a part that runs its kernels. The constant's own comment named the missing step: running the cc 10.3 cells through the block.

## Related issues

None found.

## API and compatibility impact

`DENSE_SERVING_CCS` and `FP8_PROJ_BF16_ATTENTION_CCS` (public in `cudnn.gated_attention_block`) gain `(10, 3)`. A serving stack that reads it as its dispatch predicate now dispatches the dense bf16 / f16 forms to the block on cc 10.3. cc 10.0 and cc 10.7 behave as before. The only change there is the wording of the dense part statement that unserved parts see.

A process using both admitted SM100 and SM103 devices can reuse the first device's compiled SDPA artifact. The two parts load the same sm100 template for identical parameters: template_loader keys it by path/parameters, while decode_d256_f16.compile and prefill_d256_f16.compile have outer lru_cache keys with no device. That outer hit bypasses compiled_cache's device-aware memoization. A host probe of the real loader and decode compile function confirmed that changing the modeled part from 10.0 to 10.3 returned the same first-target artifact without reaching the compiler; clearing the outer cache reached the second target. Please include device identity/target in these outer keys or let the device-aware cache own reuse, and cover both device orders. This is an inherited mixed-device limitation; one device per process avoids it. No physical mixed-GPU failure was reproduced here.
