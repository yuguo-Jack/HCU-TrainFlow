## Summary

The SM120 FROST GEMM tree now declines a single-GEMM tile when the plain templates' epilogue-staging deduction would leave its AB ring with no stage. The decline is a `NotImplementedError` raised before anything is rendered: by the probe and the JIT of an explicit config, and by `build_plans()` for a replayed knob record. Before, the probe admitted the tile and the build then failed inside the CuTe DSL trace.

- `sm120/compiler.py`: new `_single_gemm_ring_reject(chain, cfg, tmpl)`. It computes the ring depth that the plain dense, MoE and MoE swap-AB templates end up with: the rendered `cfg.max_ab_stages(...)` minus `ceil(staging / _AB_STAGE_BYTES)`, where `staging = 4 * 528 * compute_warps` and `_AB_STAGE_BYTES = (num_a * cta_m + num_b * cta_n) * cta_k_bytes + 16`. When that depth is below one, it returns a decline message. Three places call it:
  - `_precheck_plain` and `_precheck_moe`, the two `precheck_path` gates that the sm120 probe and build paths run before they render. So `probe_chain`, `probe_supported(graph, cfg)`, the planner and heuristic probes, knob replay through `build_gemm_plan`, and `jit_from_cudnn_graph` decline such a tile before rendering. `FrostGemmEngine.check_support` probes only the graph's automatic config: it calls `probe_supported(graph)`, which plans its own config, and the engine API passes it no plan knobs. So it still passes for a knob-pinned plan, and `build_plans()` declines that plan. `_precheck_plain` binds the selected template once and passes it to both `active_reject` and the new check.
  - `_render_tile_constants`, for single-GEMM chains. The block-scale renderer already declines a zero-stage ring at the same point.

  Example message: `sm120_matmul.py: config 'CONFIG_sm120_256x256x128_16x16x32_cluster1x1_warps4x2' leaves no AB pipeline stage -- the SMEM budget holds 1 stage(s), and the template gives up 1 whole 65552-B stage(s) for its 16896-B epilogue staging; pick a smaller CTA tile or K tile`.
- The three plain templates: `assert ab_stages >= 1` after the deduction, as a backstop, matching the existing assert in the block-scale templates. The compiler never reaches it, because the host check raises first.
- Test: `test_sm120_single_gemm_tile_without_an_ab_stage_declines_at_probe` (dense, MoE, MoE swap-AB).

## Why

For a single GEMM, the sm120 renderer emits `ab_stages = cfg.max_ab_stages(smem_fixed_reserve=...)`. That count covers operand bytes only and raises only when not even one stage fits. The renderer also emits `stg_epi_prefunded = False`. The plain templates then pay for their transposed-STG epilogue staging by giving up whole stages, with no lower bound (`ab_stages = ab_stages - -(-_STG_EPI_BYTES // _AB_STAGE_BYTES)`). When the budget holds exactly one stage before that deduction, the kernel is traced with `ab_stages = 0`.

Only the catalog sweep (`_sm120_smem_feasible` in `tile_config.py`) applies this rule. `multi_gemm_reject` returns `None` for a single GEMM, and `_precheck_plain` / `_precheck_moe` have no single-GEMM stage check. So a geometry that is not in the catalog passes every probe. Such a geometry can arrive through an explicit config or through a knob record replayed with `create_execution_plan(engine_id, knobs)` (`GemmKnobs.to_config` -> `by_name` -> `_synthesize_config`).

Reproducer on the base commit (RTX PRO 6000, SM 12.0, opt-in SMEM 101376 B): bf16, `CONFIG_sm120_256x256x128_16x16x32_cluster1x1_warps4x2` (the `_swapAB` variant for MoE swap-AB). The rendered value is `ab_stages = 1` (99328 // 65536), and the template subtracts `ceil(16896 / 65552) = 1`.

| Route | Graph | `probe_chain` / `probe_supported(graph, cfg)` | Build |
|---|---|---|---|
| `jit_from_cudnn_graph(config=cfg)` | dense M=N=K=512 | OK / OK | `ValueError: num_elems must be at least 1` (`SmemAllocator.allocate_array`, at the first `cutlass.Array(cutlass.Int64, ab_stages, smem)`) |
| same | MoE NONE E=2, S=512, N=512, K=256 | OK / OK | same `ValueError` |
| same | MoE swap-AB, same graph | OK / OK | same `ValueError` |
| knob replay (`create_execution_plan` + `build_plans`) | dense, MoE | `check_support()` OK | `NotImplementedError: frost_gemm: num_elems must be at least 1`, after a full render and trace |

No kernel is built, so the result is never wrong. The defect is that the probe and the build disagree: `precheck_path` is documented as "every gate the matching `_jit_*` path runs before it renders anything", and here the build rejects a graph the probe accepted, late and with a message that does not say what is wrong. The automatic path is not affected. On SM 12.x, `select_config` returns either an sm120 catalog tile or an sm100 pick crossed over to sm120, and such a pick has `cta_m <= 128` and `cta_n <= 256`, which keeps at least one stage.

Scope at the 101376-B budget: `ConfigSm120` and the warp-layout rule accept 960 geometries with CTA sides <= 256 (multiples of 16), a 128/64/32-byte K tile and a 4- or 8-compute-warp grid. 62 of them render an empty ring. Those 62 cover 22 CTA tiles, all with a 128-byte K tile and `cta_m + cta_n >= 400` (for example 256x256, 256x144, 144x256 and 192x224). None of them is in the catalog. With this change those 62 are declined, and all 479 sm120 catalog entries still pass.

Why this fix:

- **Decline instead of re-accounting.** The alternative is to take the staging off the budget in bytes, as the multi-GEMM path does. That would turn these tiles into working one-stage kernels: one stage plus the staging is 83456 B for 256x256x128. It would also change the rendered ring depth of existing catalog tiles (for example 64x64x128 would go from 4 to 5 stages), which is a performance change on the automatic path. In addition, FlashInfer's `flashinfer/fused_moe/backends/cudnn_frost/device.py` recomputes the operand-only (pre-deduction) `ab_stages` per device for its exported sm_120a single-GEMM kernels, and relies on the exported template's whole-stage deduction (`stg_epi_prefunded = False` is one of the exported constants). If only the frontend switched to byte accounting, FlashInfer's next re-export would pair that operand-only count with a template that no longer deducts, which could oversubscribe SMEM. A change like that needs measurements and its own PR. This PR changes no ring depth.
- **Where the check lives.** It is in the sm120 tree (`_precheck_plain`, `_precheck_moe`, `_render_tile_constants`), so the probe of a config and the build of that config apply the same rule. It also stays inside `python/cudnn/gemm/frost/sm120/`. The shared `kernel_registry.py` is not changed. One consequence: calling `Sm120KernelTemplate.accepts()` directly on such a non-catalog tile still returns `None`. The registry only enumerates through `candidate_configs`, which walks the catalog (every entry passes the new rule), and a non-catalog config always reaches the prechecks above before anything is rendered.
- **The template assert is a backstop only.** An `AssertionError` raised while the generated module is imported is not one of the exceptions `FrostGemmEngine.build_plan` maps to a decline (`NotImplementedError`, `ValueError`). With the host check in front, the assert cannot fire through the compiler; it only names the problem if a future renderer change skips the host check.

Found in an audit of the SM120 Frost kernel templates (finding B21).

## API and compatibility impact

- Newly declined, before rendering, with `NotImplementedError`: single-GEMM sm120 dense, MoE and MoE swap-AB graphs that pin a non-catalog tile whose only AB stage the epilogue staging takes. At the SM 12.x budget these are the tiles with a 128-byte K tile and `cta_m + cta_n >= 400`. Such a tile reaches the frontend through `jit_from_cudnn_graph(config=...)` (declined by `probe_chain`, `probe_supported(graph, cfg)` and the JIT) or through a replayed knob record. These graphs could not be built before either.
- The engine's `check_support()` stays graph-level: it probes the graph's automatic config, because `BaseEngine.check_support(graph)` receives no plan and no knobs (`FrostGemmEngine` in the shared `gemm/frost/engine.py`, not changed here). So a knob record naming such a tile still passes `check_support()`, and `build_plans()` declines it, as before. The difference is that the decline now comes before rendering, with a message that names the SMEM shortfall, instead of `num_elems must be at least 1` after a full render and trace.
- Unchanged: every catalog tile, the automatic selection, multi-GEMM chains (still gated by `multi_gemm_reject`), block-scale chains, and the numerics and ring depth of every accepted plan.
- The three plain templates gain one line, so their generated kernel sources and cache keys change. Each kernel is compiled again once. FlashInfer ships frozen exports of the two plain MoE templates (its bf16 SM120 MoE kernels); they pick up the line only when FlashInfer re-exports them. FlashInfer's exporter step `source_template.extract_template` accepts host-rendered plain MoE and MoE swap-AB sources from this branch with the line in place.
- SM100: the sm100 tree does not have this defect. Its renderer counts the TMA-store staging in bytes (`cfg.max_ab_stages(..., extra_smem_bytes=smem_d_bytes)` in `python/cudnn/gemm/frost/sm100/compiler.py`), and its templates do not give up whole stages. No follow-up is needed there.
