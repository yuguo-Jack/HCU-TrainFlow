## Affected area

FE OSS kernels or CuTeDSL

- `python/cudnn/gemm/frost/epilogue_codegen.py`: the shared FROST GEMM epilogue emitter `_emit_binary_ext`, used by both the sm100 and sm120 trees
- `test/python/gemm/frost/test_matmul_relu_backward_nonfinite.py`: new SM120 regression test

## Summary

`_emit_binary_ext` gets an early branch for `relu_backward` / `leaky_relu_backward` at cuDNN's default parameters: no slope (or slope 0), lower clip 0, and no upper clip (or one at or above FLT_MAX). For these it emits `vector.where(x <= 0, +0, dy)` instead of `dy * mask`. Every other parameterization keeps the existing mask product unchanged. The new module constant `_FLT_MAX` holds the largest finite fp32. The new test file has seven cases.

## Why

The emitter computed `dy * m`, where `m` is an exact 0.0 / 1.0 float mask built with `_step01` (`epilogue_codegen.py:189-203` on 24a8cd43; the multiply is at `:203`). The multiply lowers to a plain `arith.mulf`. So on a dead unit (x <= 0):
- an inf or NaN dy came out NaN (`inf * 0`, `NaN * 0`);
- a negative dy came out -0.

Native cuDNN returns +0 there, and so does torch's `threshold_backward`.

Minimal reproducer (the new test): a dense bf16 GEMM with M = N = K = 128 and `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`, followed by `relu_backward(loss=C, input=x)` with a bf16 output. The rows of C are exactly +inf, -inf, NaN, -1.5 and 1.5. The columns of x are -1, 0, -0, 0.5, 2, NaN, -inf and inf.

| dy | x <= 0, 24a8cd43 | x <= 0, this PR | x <= 0, native cuDNN 9.24 (all 17 plans) |
|---|---|---|---|
| +inf, -inf | NaN | +0 | +0 |
| NaN | NaN | +0 | +0 |
| -1.5 | -0 | +0 | +0 |
| 1.5 | +0 | +0 | +0 |

At x > 0 and at x = NaN, 24a8cd43, this PR and every native plan return dy.

The trigger does not need non-finite inputs. Take the same GEMM and declare its output C fp16. Set B[:, 0] = 300, and A[:, 0] = 300 on even rows and -300 on odd rows, except that every fourth row of A is 1.0. Then three rows in four have a finite fp32 accumulator of ±90000, which rounds to ±inf in fp16 before `relu_backward` (an fp32 value rounds to fp16 infinity when its magnitude is 65520 or more). With x = `torch.randn` after `torch.manual_seed(0)`, as in the committed test, the FROST plan (`jit_from_cudnn_graph` with the config above) gave NaN on 6151 of 8218 dead units on 24a8cd43. Native eng10 on the same graph and data gave none, and matched `where(x <= 0, +0, fp16(acc))` in all 16384 outputs. That is the fp16 / bf16 training case the audit describes: an overflowed gradient on dead units becomes NaN only on the FROST plan, so loss-scaler skips and NaN checks behave differently from native cuDNN for the same graph.

Why the fix covers only the default parameters: the audit recommended a select for every `relu_backward` form. Before doing that, I measured native cuDNN 9.24 on the same SM120 GPU, running every native plan the heuristics offer (17 eng1 / eng7 / eng10 variants):
- **Default parameters:** every plan computes the threshold select `x <= 0 ? +0 : dy`.
- **`lower_clip=-1, upper_clip=1`, `upper_clip=1` alone, or `lower_clip=0.5`:** every plan multiplies instead. dy = inf on a clipped unit gives NaN, and dy = -1.5 gives -0.

For x below FLT_MAX, FROST already matches native bit for bit in those clipped forms (in every case I compared, x = -inf and NaN included). A select there would make it differ from native where it agrees today. So this PR leaves the clipped and sloped forms alone.

One pre-existing gap remains in the forms that keep the mask product without an explicit upper clip, for example `lower_clip=0.5`, `lower_clip=-1`, `negative_slope=0.1` and `leaky_relu_backward(negative_slope=0.1)`. For fp32 compute the frontend lowers the unset upper clip as FLT_MAX (`pointwise.h:131-133`), and the native multiply path applies it: at x = FLT_MAX and x = +inf, eng10 returns dy * 0 (NaN for an inf dy, -0 for a negative one). FROST's mask path has no upper term when `upper_clip` is unset, so it passes dy there. In my probe each of these four forms differs from eng10 in 2142 of 16384 outputs, all at x = FLT_MAX or +inf, on 24a8cd43 and with this PR alike. This PR neither causes nor fixes that gap; it suits a separate follow-up. With an explicit upper clip (`lower_clip=-1, upper_clip=1` or `upper_clip=1`), FROST matches eng10 in every output, x = ±inf and ±FLT_MAX included.

The frontend lowers an unset lower clip, slope and upper clip as 0, 0 and FLT_MAX for fp32 compute, and clamps a larger upper clip to FLT_MAX (`include/cudnn_frontend/node/pointwise.h:123`, `:131-133`, `:142`). So the explicit spellings below are the same backend graph. Native returned +0 for each of them on dead units:
- `lower_clip=0.0`
- `negative_slope=0.0`, including `leaky_relu_backward(negative_slope=0.0)`
- `upper_clip=FLT_MAX` and `upper_clip=inf`

The new branch takes all of them. A NaN x still passes dy, because `cmpf ole` is false for NaN. This was the audit reviewer's correction to the original suggestion, which used a `(x > lower) & (x < upper)` mask: that mask would have zeroed dy at x = NaN, while FROST and native both pass it.

Why the change is outside `python/cudnn/gemm/frost/sm120/`: at 24a8cd43, `relu_backward` is emitted only by the shared `python/cudnn/gemm/frost/epilogue_codegen.py`, which #1956 / #1993 moved the emitters into. Both arch trees reach it through `_emit_pointwise_dag` → `_emit_op` → `_emit_binary_ext`. `sm120/` has no copy to change. An sm120-only override would fork the shared emitter between the two trees.

Found in an audit of the SM120 FROST GEMM kernel templates (finding G4.3).

## API and compatibility impact

- **Numerics:** with `relu_backward` / `leaky_relu_backward` at the default parameters, a dead unit (x <= 0) is now +0 for any dy. Before, it was NaN for an inf or NaN dy and -0 for a negative dy. Nothing changes at x = NaN or in any clipped or sloped form. Live units do not change either, except with an explicit `upper_clip=FLT_MAX`: the old mask product applied that clip, so x = FLT_MAX and x = +inf gave dy * 0 (a signed zero, or NaN for an inf dy). They now give dy, as native eng10 does.
- **Newly compiling:** `relu_backward(upper_clip=inf)` used to fail at kernel build: the emitter formats the clip as `cutlass.Float32(inf)`, and the DSL raised `DSLUserCodeError` for `NameError: name 'inf' is not defined`. It now takes the default branch, which never formats the clip. Its result matches native eng10 in every output of my probe, and the new `upper_clip_inf` test case pins it. An infinite clip in any other form, such as forward `relu` or `relu_backward` with a slope, still fails that way (I checked both on this branch). That is a separate defect and is not addressed here.
- **Newly compiling (int32 compute):** the default `relu_backward` with `compute_data_type=INT32` used to fail at kernel build with `TypeError: floor is only supported for floating-point types`, from `cute.math.floor` in the `_step01` mask. On SM120 it now builds and computes the select on the int32-converted values: on the dense template, 0 of 16384 outputs differ from `where(int32(x) <= 0, 0, int32(dy))`. I did not compare it with native cuDNN or try it on the sm100 tree. #2022 (G4.4) declines int32-compute `relu_backward` on SM120, so once both PRs land this graph is declined again: on a scratch merge of the two branches, `jit_from_cudnn_graph` raises `NotImplementedError: pointwise op 0 ('relu_backward') computes in int32, which the sm120 epilogue emits only for ...`.
- **SM100:** the sm100 tree imports the same shared emitter, so its `relu_backward` changes the same way. There is no separate SM100 copy that needs a follow-up. With `CUDNN_FRONTEND_GEMM_ARCH_FAMILY=sm100`, the rendered epilogue has the select for the default form and the unchanged `_ba0 * _rmu0` for a clipped one. I only rendered it; I did not compile or run it on SM100 hardware.
- **Performance:** the default form now emits a compare and a select. Before, it emitted the `_step01` mask (subtract, floor, add, max, min), a subtract and a multiply. Not measured.
- **CuTe DSL:** `cutlass._mlir_helpers.vector.where` and the Vector comparison operators are already used by this module on 24a8cd43, in the `binary_select` emitter and the mainloop K-tail mask. No new DSL API or version gate is needed (Rule 7).
- FlashInfer's FROST exports contain no `relu_backward`.
