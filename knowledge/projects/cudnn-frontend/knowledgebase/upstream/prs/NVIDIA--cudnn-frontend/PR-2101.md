## Affected area

FE OSS kernels or CuTeDSL

## Summary

The native DSA training composition (`cudnn.deepseek_sparse_attention.training`, behind `DSA.sparse_attention`) raised "native sparse attention training currently requires SM100" on every part except cc 10.0. Every native kernel it calls already serves cc 10.3:

- sparse attention forward and backward map cc 10.3 to `sm_103a` (`_ARCH_FLAGS` / `_SM100_FAMILY_ARCH_FLAGS`);
- the top-k compaction and the score recompute gate on SM100+.

The composition now accepts cc 10.0 and 10.3, and `test_DSA_training.py` runs on both.

## Why

On a B300 the composition refused a workload its own kernels serve.

## Related issues

None found.

## API and compatibility impact

None on cc 10.0. On cc 10.3, training through the composition now runs instead of raising `NotImplementedError`.

## Testing

B300 (cc 10.3), develop `64ed3dfe` with its own extension, torch 2.14.1+cu130, cuDNN 9.27.0, CuTe DSL 4.8.1, run from `test/python`:

| Command | develop | this PR |
|---|---|---|
| `python -m pytest deepseek_sparse_attention/cutedsl/test_DSA_training.py` | 14 skipped | 14 passed |

Not run on cc 10.0, where the check admits the part exactly as before.

**[P2] Key the shared compiler and kernel caches by device target** ([source](https://github.com/NVIDIA/cudnn-frontend/blob/2f0013d598bb29f8586675e242b40940ef2f5bc7/python/cudnn/deepseek_sparse_attention/training.py#L51))

Admitting SM103 exposes a mixed-device failure in the training path's dependencies. utils/compiler.py caches gpu_arch_flag() without arguments, so the first GPU's target survives a later device switch. The compaction cache uses only (cols,), and the sparse attention score-recompute cache also omits device/architecture. After training on SM100, training on SM103 can therefore compile or reuse an sm_100a artifact even inside the correct q.device context; the reverse order has the same problem. Please key target selection and these compiled artifacts by the actual device/target, with a regression for both device orders. A host probe confirmed the stale target and same-width artifact reuse; this is a visible mixed-device failure risk, with one architecture per process as a workaround.

Evidence: probe-target-cache.py/log: modeled SM100 then SM103 retained sm_100a for a fresh compile key. Clearing only gpu_arch_flag.cache_clear() selected sm_103a for a fresh key but left the existing width cached as sm_100a. Source inspection confirms the score-recompute key also lacks device/architecture. No foreign-architecture GPU binary was launched. Attribution: The caches predate this PR; widening the training contract newly admits the SM100/SM103 combination that exposes their target mismatch.

Validation: All 14 focused DSA training tests passed on native SM100 using the exact Python head and a compatible native binding. Coverage includes FP32 output/gradient references, sink gradients, score targets, invalid and duplicate sparse metadata, empty rows, length clamps, trusted metadata, NaN suffixes, both checkpoint modes, synchronization guards, and changed-input CUDA Graph replay. A host-only probe confirmed target memoization and compiled compaction artifact reuse across modeled SM100/SM103 contexts. The mixed-device probe models target selection and cache reuse; it does not execute on a physical mixed-GPU system.

Thanks. Fixed in 22bf93a7 (the [P2] shared compiler and kernel caches):

- `utils.compiler.gpu_arch_flag(device=None)` reads the device's capability on every call. Only the capability-to-target map is cached.
- The index compaction (`compactify`) compiles for the target of the input's device and keys its artifact `(cols, target)`.
- Every SM100 score-recompute compile key (sparse indexer / attention, dense indexer / attention) carries `gpu_arch_flag()`, the target `compile_options()` compiles for. It goes right after the key's label, so the existing tail positions that `test_DSA_sparse_score_recompute_sm100_topk_length_none_compiles_out` reads are unchanged.
- `test_compiled_dependencies_follow_the_device_target` runs SM100 then SM103 and the reverse, twice each. It patches the capability and replaces `cute.compile` with a recorder, so nothing compiles for a foreign part. The compaction and the attention score recompute each compile exactly once per part, for that part's target, and the repeat of a part reuses its own artifact.

The sparse attention forward and backward caches already keyed by device / capability, so they are unchanged. Other DSA kernels outside the training path keep their caches as they are.

B300, this head: `python -m pytest deepseek_sparse_attention/cutedsl/test_DSA_training.py deepseek_sparse_attention/cutedsl/test_DSA_sparse_score_recompute.py` gives 42 passed. Develop on the same part: 26 passed, 14 skipped (the training suite, gated to cc 10.0 there).
