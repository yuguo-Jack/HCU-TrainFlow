# frost(sdpa): the Rubin paged d256 decode tile leads the backend by default inside its measured band

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1634) · state: closed · merged: True

## Original PR description

## Summary

On cc 10.7 a **paged dense-Q d256 decode graph at `S_q == 1`** -- the cuDNN decode graph shape FlashInfer builds (a dense Q over a page pool with
the padding mask, no causal mask / window / sink / Stats, the KV declared as `paged_attention_max_seq_len_kv`) -- rode the Rubin d256 decode tile
(`sm107/decode_d256_f16.py`, #1543) only under the opt-in flag: `_place_sm107_f16` led a PAGED graph through the THD split selectors, the paged
prefix launch and the paged packed-GQA prefill shard (`64 <= S_q`), so FE's default plan for the decode shape was the cuDNN backend engine on every
cell -- a plan that measured 1.1-2.3x slower than the tile on the same graph.

This PR adds the arm `placement._sm107_paged_d256_decode_tile_leads`, keyed on `engines.d256_decode_tile_selected` with the whole GQA group packed,
bounded by a measurement of the decode tile against the backend's default plan on the SAME FE graph, and the arm's pin test and tracker rows. The arm
admits exactly the measured shape: per-request KV lengths (the padding mask every band cell carried) and either in-page pool layout -- the token-major
one the band measured (FlashInfer's benchmark pool) and the head-major one (vLLM's cache layout), measured on the 24/2 core chunk below; every unmeasured
twin keeps the backend first, as the module's other arms do.

## The measurement (the band the bounds come from)

NVIDIA Rubin, cc 10.7, 212 SMs, aarch64 host, an EXCLUSIVE GPU of the perf-node class per cell; SM clock locked at 2376 MHz and SAMPLED per regime
(busy median 2364 MHz on the quotable rows); the `SW Power Capping` counter read before / after every regime (0 cap events); cudnn-frontend 1.32.0
(the develop tree carrying #1543 plus the serving integration commits), cuDNN 9.27.0 (build 9.27.0.21, the pre-release build the harness loads;
the released 9.27.0.42 re-check is noted below), nvidia-cutlass-dsl 4.8.0, torch 2.14.0+cu130, FlashInfer 0.7.2 (HEAD) + its 0.7.0.post1 kernel wheel.
Timing = FlashInfer's `bench_gpu_time` (CUPTI kernel time, the L2 flushed per iteration; a captured CUDA graph in the replay regime); 3 rounds x 100
iterations (+10 dry) per arm, the arm order shuffled per round, medians of medians; the backend's default plan and the first FROST plan each PINNED
by name on the same graph (an FE-side measurement; FlashInfer never pins an engine); a second backend arm as the control pair (within 1 % or the
cell is not quoted); a cell whose clock the NVML sampler could not verify (launch-bound kernels under ~20 us) is reported, not quoted; CUDA-graph
replay AND eager back-to-back submission. Cells: seven GQA geometries (24/2, 32/2, 16/4, 24/4, 8/1, 12/1, 16/1 = groups 12, 16, 4, 6, 8, 12, 16) x b
1 / 2 / 4 / 8 / 16 / 32 / 64 / 128 x declared KV 1k / 2k / 4k / 8k / 32k / 128k at page 16 bf16, page 32 / 64 at 24/2, one f16 twin per geometry,
the pool as FlashInfer's benchmark strides it (`[pages, H_kv, page, D]` dims, token-major in the page). `units = b * h_kv` (one packed unit of the
tile each); ratio = tile time / backend time.

| region (groups 4 / 6 / 8 / 12 / 16) | cells x regimes | quotable | tile / backend, eager | tile / backend, replay |
|---|---|---|---|---|
| `units >= 4` and `units x KV >= 2^16` tokens in flight (the band) | 289 per regime | 289 / 289 | **0.43 .. 0.90** (every cell faster) | **0.43 .. 0.81** (every cell faster) |
| the frontier cells of it (64 x 1k, 32 x 2k, 16 x 4k, 8 x 8k) | 36 per regime | 36 / 36 | 0.59 .. 0.90 | 0.67 .. 0.81 |
| its 512-unit edge (16/4, 24/4 at b 128) | 12 per regime | 12 / 12 | 0.53 .. 0.63 | 0.53 .. 0.62 |
| page 32 / 64 (24/2) inside the band | 32 per regime | 32 / 32 | 0.43 .. 0.85 | 0.43 .. 0.80 |
| the f16 twins (one per geometry) inside the band | 7 per regime | 7 / 7 | 0.46 .. 0.57 | 0.46 .. 0.57 |
| one step below: `units x KV = 2^15` (32 x 1k, 16 x 2k, 8 x 4k, 4 x 8k, 1 x 32k) | 39 per regime | 27 / 29 (12 / 10 launch-bound, unverifiable) | **mixed** 0.81 .. 1.79 | **mixed** 0.78 .. 1.79 |
| fewer than 4 units | 42 per regime | 20 / 22 | 0.76 .. 1.79 (the 128k column 0.75-0.83, one column) | 0.75 .. 1.79 |

So the arm LEADs exactly the band: `SM107_PAGED_D256_DECODE_GROUPS = (4, 6, 8, 12, 16)`, `MIN_UNITS = 4`, `MAX_UNITS = 512`, `KV_TOKENS = (1024, 131072)`,
`MIN_KV_TOKENS_IN_FLIGHT = 2**16`, `PAGE_SIZES = (16, 32, 64)`, half inputs; the eager and replay frontiers coincide (replay alone also led at
16 x 2k, 0.82-0.85 with three geometries unverifiable, and 8 x 4k, 0.89-0.95: not admitted). Everything else keeps the backend first:

- **held by decision, although measured faster than the backend**: group 32 (64/2, the 32-column tile in one unit: 0.27-1.00 of the backend; it
  trails FlashInfer's fa2 kernel by 7-9 % at the medians) and the MTP rows (`2 <= S_q <= 4` on 24/2 and 32/2 = the 32-column tile in up to two
  token units: 0.01-0.31 of the backend's plan, which costs 6.8-142 ms per launch at KV 128k, but 6 % (q 2) / 21-22 % (q 3-4) behind fa2) -- the
  32-column tile's issue-rate gap at 24-64 packed rows, recorded in the tracker's gaps table; both holds reopen with the kernel;
- **not measured**: Stats, a sink, a causal mask or window at `S_q = 1`, page 128, a dense (unpaged) d256 cache at `S_q = 1` (measured against the
  prefill body only), THD queries, the fused gate, a paged decode without per-request KV lengths (no padding mask).

## The head-major pool (the vLLM cache layout)

The band measured FlashInfer's benchmark pool only (`[pages, H_kv, page, D]` with the token-major in-page strides). The head-major pool (each head's
page contiguous: vLLM's `[blocks, 2, H_kv, block, D]`, FlashInfer's own HND tensors -- the same bytes per page in a friendlier order) was measured
on the 24/2 core geometry with the band's protocol on an exclusive GPU of the same 212-SM cc 10.7 class (SM clock locked at 2376 MHz and sampled,
busy median 2364; the power-capping counter delta 0; cuDNN 9.27.0 build 9.27.0.21; b 1 / 2 / 4 / 8 / 16 / 32 / 64 / 128 x declared KV 1k / 2k / 4k /
8k / 32k / 128k at page 16 bf16 = 48 cells x 2 regimes; the backend's default plan and the FROST tile pinned on the SAME graph; 3 rounds x 100
iterations shuffled, the control pair within 1 % or the cell is not quoted):

| region (24/2, head-major pool) | cells x regimes | quotable | tile / backend, replay | tile / backend, eager |
|---|---|---|---|---|
| the band (`units >= 4`, `units x KV >= 2^16`) | 32 per regime | 32 / 32 | **0.36 .. 0.92** (median 0.45; every cell faster) | **0.36 .. 0.92** (median 0.45; every cell faster) |
| outside the band (fewer than 4 units or 2^15 tokens in flight) | 16 per regime | mixed, launch-bound cells unverifiable | 0.73 .. 2.00 (median 1.17) | 0.80 .. 1.98 (median 1.40) |

The same verdict as the token-major band on every in-band cell (that band's 24/2 column read 0.43 .. 0.77 replay / 0.43 .. 0.88 eager on another GPU
of the class), so both in-page layouts are admitted and the arm reads no pool stride. With one KV head the two layouts coincide.

The SM100 row's `SQ1_*` constants were not copied: the Rubin frontier was fitted on these cells (it happens to coincide with a 2^16 tokens-in-flight
rule and has no 32-unit shortcut: 32 units x 1k keys is launch-bound here).

## Re-check on the arm's tree

The core geometry 24/2 (group 12) was re-run on the arm's tree with FE's DEFAULT placement (no engine pinned; the opt-in flag unset and
asserted in the process) over 48 cells x 2 regimes -- b 1 / 2 / 4 / 8 x declared KV 1k / 2k / 4k / 8k / 32k / 128k at page 16 bf16 -- on an
exclusive GPU of the same Rubin class (212 SMs; SM clock locked at 2376 MHz and sampled, busy median 2364 MHz; the power-capping counter delta 0),
cuDNN 9.27.0 build 9.27.0.21 (the pre-release build the harness loads), the band's driver and protocol (3 rounds x 100 iterations, the arm order
shuffled, the control pair, the served FE plan read back per cell):

- the plan FE's default served matched the arm's verdict on **96 / 96** (cell, regime) rows: `sdpa_fwd_prefill_sm107` on all 32 LEAD rows per
  regime (`units >= 4` and `units x KV >= 2^16`), the cuDNN backend engine on all 16 TRAIL rows per regime;
- on the 32 rows per regime that the arm leads, the default plan's time over the pinned backend plan's on the same graph: replay 0.43 .. 0.77 (median 0.52, 32 quotable
  rows), eager 0.43 .. 0.88 (median 0.52); the default vs FlashInfer's fa2 kernel on the same cells: replay -3.6 .. +41.6 % (median +6.3 %),
  eager -4.3 .. +44.0 % (median +4.8 %), positive = the default is faster;
- on the 16 rows per regime that stay with the backend, the default plan is the backend plan (0.99 .. 1.00 of it; 9 / 6 quotable rows per regime, the rest launch-bound and not
  verifiable by the clock sampler);
- caveat: the node's other GPU was held by another task's functional process during the run (idle at launch); the served-plan check is the
  evidence of this re-check, the replay regime is the quotable one and the eager numbers are informational.

The released cuDNN 9.27.0.42 build was NOT re-run before this draft (the node environment that held the unpacked wheel expired with its
reservation); that re-run is the first act before this PR leaves draft, with the build stated here.
