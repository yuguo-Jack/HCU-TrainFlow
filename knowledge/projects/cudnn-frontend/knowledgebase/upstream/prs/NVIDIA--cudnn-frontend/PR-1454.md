- YangXu1990uiuc · comment · 2026-10-07T18:58:10Z · [source](https://github.com/NVIDIA/cudnn-frontend/pull/1454#issuecomment-6044734550)

Integration compatibility note from the FlashInfer linear-attention work, checked against this PR at `b24029d`.

The additive default helps the GDN integration, but removing `qk_l2norm_additive_epsilon` needs coordination with the existing KDA callers:

- Merged FE #1418 added that graph attribute, and [FI #6078](https://github.com/flashinfer-ai/flashinfer/pull/6078) forwards it. [FI #6187](https://github.com/flashinfer-ai/flashinfer/pull/6187) explicitly passes `1e-6` when auto substitutes cuDNN for the native small-BH route. With this PR's graph schema, those calls get an unexpected-argument `TypeError`: explicit cuDNN fails, while auto falls back to native. Caching unsupported builds prevents repeated build work but does not restore the cuDNN route.
- FI currently has two native KDA normalization contracts: small-BH uses `x * rsqrt(sum_sq + 1e-6)`; the general CuTe/BT16 path uses `x * rsqrt(max(sum_sq, 1e-24))`. Our auto integration preserves the contract of the native route being replaced. Simply dropping the attribute would therefore fix the additive call's argument error but silently change the clamp route's mathematics. Zero/tiny-row coverage matters here; this is distinct from acceptable fusion/reduction rounding differences.
- For GDN, [FI #6186](https://github.com/flashinfer-ai/flashinfer/pull/6186) currently normalizes Q/K externally with additive `1e-6`, rounds to input dtype, and passes `use_qk_l2norm=False` to FE. This PR's shared FE normalization helper appears to provide the needed formula and dtype boundary. After numerical/performance qualification, FI can pass raw Q/K with `use_qk_l2norm=True` and remove its external normalization. GDN still launches FE's separate normalization kernel/workspace before its attention chain; this is not yet fusion into the GDN attention kernel.

Could we retain compatibility for the existing epsilon argument and an explicit way to request the needed normalization semantics, or coordinate the FI migration before removing/changing them? FE 1.31 version gating alone cannot distinguish these two source contracts. Please also retain equivalent zero/tiny-vector, output/final-state and continuation coverage when replacing the dedicated additive-normalization tests.

This is a source-level integration check; I have not run this PR's kernels.
