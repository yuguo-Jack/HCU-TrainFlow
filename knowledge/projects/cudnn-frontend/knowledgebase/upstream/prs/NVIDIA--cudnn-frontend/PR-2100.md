## Affected area

FE OSS kernels or CuTeDSL

## Summary

`MhcProjectionBackward.check_support` accepted only cc 10.0. The check now accepts cc 10.0 and 10.3 (`_SUPPORTED_CAPABILITIES`). Of its two kernels:

- the cuTile partial product was built with `gpu_code="sm_100"`. That cubin does not load on cc 10.3 (`cuModuleLoadData`: `CUDA_ERROR_NO_BINARY_FOR_GPU`);
- the Triton reduction was built for `GPUTarget("cuda", 100, 32)`, which Triton turns into an architecture-specific `sm_100a` cubin.

`_binaries(device)` now builds both for the device's own part: the partial for `sm_100` / `sm_103` and the reduction for `sm_100a` / `sm_103a`. It is cached per device, so the two parts never share a binary, and cc 10.0 compiles exactly as before. `test_mhc_projection_reduction_compiles_for_the_device` checks the reduction's PTX target.

Shapes and workspace are unchanged.

The test fixture accepts the same two parts, and the operation page and its docs index entry say SM100/SM103.

## Why

On a B300 the API raised "mHC projection backward currently supports SM100" although the same kernels serve that part.

## Related issues

None found.

## API and compatibility impact

None on cc 10.0. On cc 10.3, `check_support` now succeeds instead of raising `NotImplementedError`.

## Testing

B300 (cc 10.3), develop `64ed3dfe` with its own extension, torch 2.14.1+cu130, cuDNN 9.27.0, CuTe DSL 4.8.1, cuda-tile 1.7.0 with tileiras 13.4.92, Triton 3.8.0, from `test/python`:

| Command | develop | this PR |
|---|---|---|
| `python -m pytest -m "L0 or L1" gemm/cutedsl/test_mhc_projection_bwd.py` | 5 passed, 3 skipped | 9 passed |

The 3 cases skipped on develop are the descriptor case and the two numerical L1 cases (the prepared graph against its FP64 reference, and the wrapper). Not run on cc 10.0, where both kernels compile exactly as before.
