# sdpa: a score_mod graph is never served by a FROST row

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1960) · state: closed · merged: True

## Original PR description

## What

`cudnn.sdpa.graph_analyzer` derived `has_score_mod` from the record key `fn` — the kwarg name of `sdpa_fp8()` only. `sdpa()` / `sdpa_backward()` spell the callback `score_mod` (and `score_mod_bprop`), so for every f16 graph the fact was `False`, no FROST row ever declined a score_mod graph (no row claims `Capabilities.score_mod`), and the SM100 prefill row served them as **plain attention — the user's score modifier was silently dropped**.

Symptom: TransformerEngine `tests/pytorch/attention/test_flex_attention.py::test_dot_product_attention_score_mod` (`softcap` and `post_scale_bias`, sbhd/bshd, fp16/bf16 — b2 h4 **s16** d64) fails on Blackwell (SM100/SM103) with FE 1.31: `Mismatched elements: 3118/8192 (38.1%)` (post-scale bias) and `33/8192` (softcap). The causal cells pass only because TE runs them at s=64, a shape the row declines for another reason.

It looked like a cuDNN 9.27 → 9.28 regression. It is the FE python package moving **1.30.0 → 1.31.0** in the same test-container refresh: 1.30's SM100 prefill row did not serve d64 (`d_shapes` = {128, 192x128, 256, 512}), 1.31 added `(64, 64)`, and the latent analyzer bug became reachable.

## Fix

`has_score_mod` reads every spelling: `score_mod`, `score_mod_bprop`, `fn`. The SDPA fwd/bwd rows then decline by name ("graph uses score_mod, which this engine does not support") and the graph lowers to the cuDNN backend, which implements the modifier.

## Verification (local B200, cc 10.0, CuTe DSL 4.8.0)

- Exact PyPI `nvidia-cudnn-frontend==1.31.0` with TE-style physical tensors reproduces the failure to the digit on cuDNN 9.24 **and** 9.28: FROST `sdpa_fwd_prefill_sm100` selected for all 12 s=16 cells; softcap `33/8192, max|ΔO| 0.1324`, post-scale bias `3181/8192, 0.1945`; causal `962/8192` wrong at s=16, backend-served and correct at s=64 (TE's causal shape).
- Fixed tree: all 12 cells (fwd + bwd, both layouts, both dtypes) are backend-served (`graph.selected_engine is None`), O within 6.5e-4 of an fp32 torch reference, grads clean — on cuDNN 9.24 and 9.28.
- Collateral: `core/graph/test_python_plan_serdes.py`, `sdpa/frost/test_sdpa_backend_guard.py`, `sdpa/frost/test_heuristic_geometry.py`, `sdpa/frost/test_sdpa_bwd_d128_grouped_eligibility.py` — 895 passed.

## Detectors (both RED before the fix, GREEN after)

- `test/python/sdpa/frost/test_sdpa_score_mod_decline.py` — host-only: the fact on every spelling (sdpa / sdpa_backward with `score_mod` and/or `score_mod_bprop` / sdpa_fp8 `fn`), every fwd and bwd row declines, and the row that admits the same graph *without* the modifier (on this device) declines it **by name**. 7/8 cells failed before the fix. The SM100-row admission check is gated on that row's own `sm_lo..sm_hi` range and on the CuTe DSL being available for the device, so other architectures run only the device-independent checks.
- `test/python/sdpa/graph/test_flexible_sdpa_te_shape.py` — the TE graph (post-scale bias, b2 h4 s16 d64, sbhd/bshd strides, stats) is served by the backend and O carries the modifier. 4/4 cells failed before the fix with `a python engine admitted a score_mod graph: FrostSdpaFwdEngine(name='sdpa_fwd_prefill_sm100', engine_id=20511)`.
- Rule 10 in `python/cudnn/AGENTS.md` records the lesson (a kwarg that makes a graph ineligible for the python engines is read by the family's analyzer under the spelling of every op that takes it).

## Observed, not changed here

- With develop's native FROST binder, binding TE's *physically shaped* buffers (`(B,S,H,D)` with a BHSD-declared graph tensor) to a FROST-served plan raises `cudnn.sdpa: q: this plan was built for 4 heads of dim 64; got (2, 16, 4, 64)`; the backend path binds by pointer and accepts them. 1.31 did not raise — it computed. Worth a look under Rule 9 (one graph contract for both engines); it is orthogonal to this fix, which routes these graphs to the backend.
- TE's flex-attention path takes `nvidia-cudnn-frontend` from the installed environment, so it stays affected until a release carrying this fix is picked up.
