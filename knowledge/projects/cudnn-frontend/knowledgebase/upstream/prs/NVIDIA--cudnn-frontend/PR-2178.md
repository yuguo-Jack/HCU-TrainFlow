# sdpa(fwd): sanitize the runtime KV padding tail in the SM120 f16 prefill bodies

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2178) · state: closed · merged: True

## Original PR description

## Problem

On SM120, a dense SDPA forward graph with `use_padding_mask` and runtime `seq_len_kv` returns NaN in valid output rows when the K/V storage past a batch's `seq_len_kv` holds NaN bit patterns. Those rows are runtime padding. The default plan on SM120, `sdpa_fwd_prefill_sm120`, is affected for every f16/bf16 head dim (D64 to D512).

The score mask overwrites the padded columns with -inf, and that select is NaN-safe. But P @ V still multiplies P = 0 by the padded V row, and `0 * NaN = NaN` reaches every valid row of O. Q-only and K-only NaN padding does not leak.

`thd_helpers.sanitize_v_tail` already handles this case. It zeroes the `sV` rows at and past the runtime KV length on the first masked tile. The FP8 and MXFP8 SM120 bodies (`prefill_fp8`, `prefill_mxfp8`, `prefill_d512_fp8`, `prefill_d512_mxfp8`) call it when `thd_varlen or seq_kv_lens_present`. The three f16 bodies (`prefill_f16`, `prefill_d256_f16`, `prefill_d512_f16`) call it for THD only. The helper's docstring left the dense padded case as an open question. #2135 answered it for the SM80 bodies: runtime padding is unread data, NaN included.

## Change

- `prefill_f16`, `prefill_d256_f16`, `prefill_d512_f16`: use the FP8 bodies' condition, `(self.thd_varlen or self.seq_kv_lens_present) and in_mask_steps and is_first_kv_tile`.
  - `num_kv_tiles` is computed from the clamped per-batch `seqlen_k`, so the first masked tile is the only one that can hold pad rows. The helper zeroes nothing when that tile ends at or before `seqlen_k`.
- `sanitize_v_tail` docstring: describe the dense padded case it now serves.
- New `test/python/sdpa/frost/test_sdpa_sm120_padding_nan.py`, modelled on `test_sdpa_sm80_padding_nan.py`.
  - Fills the Q/K/V padding with NaN and checks O and Stats against an fp64 reference.
  - Replays a captured CUDA graph with changed lengths, then repeats with fresh bindings.
  - Covers D64/128/192/256/512, fp16/bf16, causal and non-causal.

The extra work is one tile's worth of shared-memory stores per CTA, and only on graphs with runtime KV lengths.

## Tests

On an RTX 5090 (cc 12.0), cuDNN 9.27, CuTe DSL 4.8.1:
- New test on develop (faf380e1): 40 failed, every one with NaN in valid O rows.
- New test with this change: 40 passed.
- Before the fix, I ran a probe over every ranked plan with NaN only in V's padding. All `sdpa_fwd_prefill_sm120` configurations leaked; backend `eng8` did not.
- `pre-commit` on the touched files passes.

- Existing SDPA tests on the patched tree, `-m "L0 or L1"`: `test_sdpa_fwd_dsl_sm120`, `test_sdpa_prepared_sm120`, `test_sdpa_fwd_decode_sm120`, `test_sdpa_fwd_split_kv_sm120`, `test_sdpa_frontend_integration`, `test_sdpa_native_dense_binding`, `test_sdpa_native_padded_stats_binding`, `test_flashinfer_shaped_sdpa`, `test_sdpa_fwd_score_stats` and `test_sdpa_prepared_thd`. 1603 passed, 1117 skipped, 1 failed.
  - The failure, `test_score_arm_adds_exactly_the_stores[sm_107a]`, fails the same way on develop. It is an sm_107a trace-compile check that this change does not touch.
