## Affected area

FE OSS kernels or CuTeDSL (FROST SDPA forward heuristics; no kernel change)

## Summary

`nonpaged_thd_split_choice` changes on cc 10.7 (Rubin) D128 only; the SM100 line is unchanged.

1. **KV floor.** The split is now proposed for caches of 1280-2047 tokens, not only from 2048. Below 2048 the declared cache must also hold at least 12x the declared query rows.
2. **Pack tie-break.** When packed and unpacked candidates tie on waves x loop and partial count, the packed one is chosen.

The wave budget stays at two waves. Placement already leads whenever a split is chosen (#1514).

## Why

A Rubin re-measurement of the 120 THD cases behind #1514 found 14 cases where the default ran >= 1.3x slower than the best FROST plan. Most were short caches (live max KV 1777-2038) with short queries: the default stayed on the backend because of the hard 2048 floor, while split 2-8 ran 0.55-0.7 of the backend. In two further cases (r5, g31) the split was taken unpacked where packed ran 1.5x faster.

The rule was refit on that set, checked on a 56-case random hold-out, adjusted, then checked on a second fresh 40-case hold-out. Each step changed the rule:

- Relaxing the wave budget to three waves looked better on the fit set (5.8 % vs 6.1 %). On the first hold-out it led to 1.33x / 1.39x lead-losses on Q256 over 1-2k caches, so the budget stays at two waves and the 12x cache/query ratio was added.
- A 1024 floor lost 1.19-1.29x warm on three caches of exactly 1024 tokens in the second hold-out (split 2 over 8 KV tiles), so the floor is 1280.

Final rule, all 216 cases (3 sets, cc 10.7, 216 SMs, cuDNN 9.27, CUDA-graph replay, warm and cold L2, guard-logged board with no other user):

| | develop | this PR |
|---|---|---|
| mean regret vs fastest measured provider | 10.3 % | 5.6 % |
| cases >= 1.3x off the fastest | 24 | 5 |
| lead-losses (FROST leads and > 3 % slower than backend, warm or cold) | 0 | 0 |

Of the remaining five >= 1.3x cases, several use bounded declarations that judge the split on declared capacity. That is the FlashInfer bucket contract (#1439 follow-up) and is not touched here.

The offline model reproduces develop's rule exactly on all 120 fit-set cases. A first patched build (same code path, earlier constants) chose the model's predicted (split, pack) on all 120 cases when measured on the board.

Note: all three sets took part in model selection. The fit set chose the shape of the change, the first hold-out produced the 12x ratio, and the second produced the 1280 floor. The 216-case aggregate is therefore a retrospective check, not a held-out estimate. A fresh set measured after freezing the rule is reported in a follow-up comment.
