## Affected area

Python API or bindings

## Summary

`_SdpaBwdBinder.bind` now converts the standalone runtime geometry with nanobind's converting constructor `py::tuple(handle)`, which calls `PySequence_Tuple`, so it takes any Python sequence. It used `py::cast<py::tuple>`.

## Why

Since the nanobind migration (#1523), `develop` fails 25 FROST backward tests on the sm100 and sm103 lanes with `RuntimeError: std::bad_cast` raised from `spec.native.bind(...)` (`cudnn/sdpa/bwd/prepared.py:112`):

- `test_sdpa_bwd_dsl_sm100.py::test_prepared_sm100_standalone_rejects_changed_layout[*]` (8)
- `test_sdpa_bwd_staged_sm100.py::test_direct_standalone_with_another_device_current[*]` (8)
- `test_sdpa_bwd_thd_sm100.py` (9)

The same 25 failures appear on #1574 (job 486030252), #1617 (485981478) and #1590 (485852484). The develop schedule of 2026-10-13 05:10 PT (484778616) ran before #1523 landed and does not have them.

Cause: `prepared_sm100.py` and `prepared_sm107.py` build `geometry` as a `list` and pass it to the native binder. pybind11's `py::tuple` converted any sequence with `PySequence_Tuple`. nanobind's `cast<tuple>` accepts only a real tuple and throws `nb::cast_error`, a `std::bad_cast`. The SM80 path passes `tuple(geometry)` and is unaffected. Fixing the binder rather than the two callers keeps it accepting what it accepted before #1523.

Related to #1523.

## API and compatibility impact

None. The binder accepts the same inputs it accepted before #1523.
