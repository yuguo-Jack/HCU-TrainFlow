# frost: serialize compile_cached's CuTe DSL compiles within a process

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2231) · state: open · merged: False

## Original PR description

**Stacked on #2226.** This PR's first commit is #2226's. Only the second commit, `a200e173`, is new here. I'll rebase once #2226 merges.

## Problem

`compile_cached` lets threads that miss on different keys compile at the same time. The artifact file lock is per key, and the memo keeps the first object stored. #2226 showed that the CuTe DSL keeps per-trace state on objects that every compile in the process shares, so two traces running at once corrupt each other. The same happens on this path.

Probe: two threads each build and run a different FROST GEMM graph (bf16, two shapes per seed) for the first time, in a fresh process with an empty cache. B300 (sm_103), CuTe DSL 4.8.1, `CUDNN_FRONTEND_ENABLE_FROST_ENGINES=1`.

| tree | seeds with an error |
|---|---|
| develop | 6 of 19 |
| this PR | 0 of 12 |

The errors are `AssertionError: Please start a session before accessing session data` and `IndexError: attempt to access out of bounds block`. The traceback is `gemm/frost/sm100/compiler.py:_compile_fused_gemm` → generated `compile` → `compiled_cache.compile_cached` → `_compile_persistent` → `_compile_and_export` → `cute.compile`.

## Change

- `compiled_cache.py` has four `cute.compile` calls: the two bypass paths, the unknown-manifest path and `_compile_and_export`. They now go through `_locked_compile`, which holds `dsl_compile_lock()`, the process-wide `RLock` that #2226 added.
- What does not change:
  - hits, memo hits and reloads take no lock;
  - the artifact lock stays per key;
  - the DSL lock is taken inside the artifact lock, only around the compile.
- Other processes still compile different keys concurrently. The lock is a `threading.RLock`, and `test_frost_different_keys_can_compile_concurrently` (child processes) is unchanged and passes.
- The cost: within one process, cold compiles of different keys no longer overlap. With the DSL as it is, they cannot overlap safely.
- Two comments are updated to match: the memo `setdefault` comment and the `_entry_lock` comment.

New test `test_frost_threads_never_trace_two_keys_at_once` in `test/python/core/frost/test_compiled_cache_concurrency.py`. It uses a stub compiler that records how many calls are inside it at once. Two threads miss on different keys behind a barrier.
- Unchanged `compiled_cache.py`: peak 2.
- This PR: peak 1, with 2 misses.
