# graph: decline a pre-Turing target on cuDNN 9.11 and newer instead of failing at execute

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2210) · state: open · merged: False

## Original PR description

## Problem

cuDNN 9.11 removed support for GPUs older than Turing: Maxwell, Pascal and Volta, i.e. compute capability below 7.5 ([9.11.0 release notes](https://docs.nvidia.com/deeplearning/cudnn/backend/v9.11.0/release-notes.html), "no longer supported"). The backend's heuristics still return plans on such a GPU, and those plans build and pass `check_support()`. The graph fails only at `execute()`.

On a V100 (cc 7.0), driver 580.178, develop 97b7bc31, a plain half `conv_fprop` graph gives:

| cuDNN | result |
|---|---|
| 9.10.2 | runs, max error 0.031 against `torch.nn.functional.conv2d` |
| 9.11.0, 9.11.1 | `execute` fails with `CUDNN_STATUS_EXECUTION_FAILED` |
| 9.27.0 | `execute` fails with `err 209 no kernel image is available for execution on the device` |

PyTorch rejects this pair up front (cuDNN ≥ 9.11 with SM < 7.5 in `torch.backends.cudnn`). That check also aborts this repo's test session on such a GPU, because `conftest.py` prints `torch.backends.cudnn.version()`.

## Change

- `graph_interface.h`: a new `check_backend_supports_sm_` declines with `GRAPH_NOT_SUPPORTED` when the backend is 9.11 or newer and the target SM is below 75. The message names the backend, the target SM and cuDNN 9.10 as the last pre-Turing release.
  - `check_support()` runs it after resolving the target SM.
  - `create_execution_plans()` runs it before the heuristics query, so a graph that goes straight to `build_plans()` fails before execute.
  - The target SM is the device's SM or the `sm_version` an AoT graph sets. A deviceless graph without a target keeps `sm_version` 0 and is not checked.
- `test/python/conftest.py`: prints PyTorch's cuDNN version only when PyTorch can initialize it.
- New `test/python/core/graph/test_pre_turing_target.py`:
  - targets SM 52/61/70/72 through `sm_version=` and expects the decline from both `create_execution_plans` and `check_support`;
  - checks that an SM75 target is not declined by this rule;
  - skips on cuDNN ≤ 9.10.

## Tests

- **V100 (cc 7.0), cuDNN 9.27:**
  - New test: 4 failed on develop (`DID NOT RAISE`), 5 passed with this change.
  - The conv graph above now declines at `check_support` with the new message instead of failing at `execute`.
- **V100, cuDNN 9.10.2:** the conv graph runs as before; the new tests skip.
- **B300 (cc 10.3), cuDNN 9.27:**
  - New test: 4 failed on develop, 5 passed.
  - `-m L0` over `test/python/core`, `conv`, `norm` and `fe_api`: 3174 passed, 13 failed with this change. The same 13 tests fail on develop, all in `test_native_backend_lowering` and `test_knob_vocabulary`; their failure list is identical with and without this change apart from the 4 new tests.
- `pre-commit` on the touched files passes (clang-format, black).
