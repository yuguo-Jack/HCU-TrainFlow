## Summary

- The four SM120 MoE grouped-GEMM templates now state, in a three-line comment at the `external_counter_reset` guard in `_host`, what a runtime that renders the flag `True` must do: zero the scheduler counter before every launch, visibly to the kernel's `griddepcontrol.wait`, because a launch started at zero leaves the counter at its tile count + `grid_num_clusters`. The comment also gives the failure of a single zero shared by FC1 and FC2. This is a comment-only change: the kernels are unchanged, and cudnn-frontend still renders `external_counter_reset = False`.
- `test_sm120_moe_external_counter_reset_states_its_contract` (host-only, all four templates) pins three phrases of that comment (`+ grid_num_clusters`, `before every launch`, `griddepcontrol.wait`) together with the scheduler facts it rests on: `sched_counter_ptr` is assigned once and used only as the pointer of one `nvvm.atomicrmw("add", ...)` call, the claim, so the kernel never writes the counter back. The test does not pin the memory order of that add; the contract does not depend on it. If the kernel gains another use of `sched_counter_ptr` (a self-reset store through it, for example), the test fails and points at the comment.
- `test_sm120_moe_scheduler_counter_needs_a_zero_before_every_launch` (GPU) runs FC1 then FC2 on one workspace, so both launches use one counter word, once with the default rendering and once with the constant flipped to `True`, and checks the counter value after each launch and which tiles were written. FlashInfer's FC1 and FC2 are two compiled kernels that are given one `desc` scratch; the test launches one compiled kernel twice, which shares the counter word in the same way.

## Why

The four SM120 MoE templates zero their grouped scheduler's global tile counter (the first int32 of the workspace, `moe_desc_slots = 0`) with a one-thread launch before the PDL main launch. #1881 added `external_counter_reset`: a runtime that zeroes the counter itself renders it `True` in its frozen source, and the host skips that launch. The scheduler never writes the counter back. Each CTA's scheduler warp claims tiles with `nvvm.atomicrmw("add", ..., mem_order="relaxed")` until its first claim past the last tile (`scan_base >= num_groups`). So a launch started at zero hands out exactly the claims `0 .. T + grid_num_clusters - 1` and ends with the counter at `T + grid_num_clusters`. The next launch that uses the same counter word starts claiming there. With `True`, the runtime therefore has to zero the counter before every launch, and the zero has to be visible when the kernel's `griddepcontrol.wait` returns. That wait covers only the previous grid on the stream.

#1881's comments said the opposite. The renderer said FlashInfer's MoE adapters zero the counter in their routing kernel, and the template said "its own routing kernel, say". A routing kernel runs once per layer, ahead of both FC1 and FC2 (#1881's commit message says so: "which runs before FC1 and FC2 in any case"), so that is one zero for both launches. FlashInfer does not do that. Its four cuDNN Frost MoE adapters (`flashinfer/fused_moe/backends/cudnn_frost/csrc/moe_*.cu`) launch FC1 and FC2 as two compiled kernels that are given the same `desc` scratch, and rely on the init kernel running on every call (`moe_bf16.cu:336`: "The frozen host initializes its scheduler counter on every invocation"; the other three adapters say "resets"). No FlashInfer source at upstream flashinfer-ai/flashinfer main b1cf76608 (#7426) mentions the flag. A runtime that followed those comments would start FC2 at FC1's final count, and every FC2 tile below it would keep stale output, with no error. #1993 deleted both comments. The flag's contract is now stated nowhere, and the #1881 commit message (which `git blame` shows for the guard lines) still carries the per-layer guidance.

Reproducer on an RTX PRO 6000 (SM120, `grid_num_clusters = 188`), at 24a8cd43. The test runs this case:

- BF16 MoE, NONE mode, `jit_from_cudnn_graph` with `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`, E=4, S=13312, N=256, K=128.
- One plan, one workspace. FC1 offsets `[0, 128, 128, 128, 128]` (2 tiles), then FC2 offsets `[0, 6656, 6656, 13184, 13312]` (208 tiles).

| rendering | counter before FC1 | counter after FC1 | FC2 output | counter after FC2 |
|---|---|---|---|---|
| default (`False`) | `1 << 30` (stale) | 190 | complete | 396 |
| `True` | 0 (one zero for the layer) | 190 | 3,112,960 elements unwritten = 190 tiles = FC1's 2 tiles + 188; the written tiles are correct; no error | 396 |
| `True`, zeroed again before FC2 | | | complete | |

The audit's recommendation for this finding is to correct the comment and state that every launch needs its own zero. It also discusses a self-resetting counter, where the CTA that makes a launch's last claim stores 0. That only helps a runtime whose counter word persists across calls and is zeroed once at allocation. cuDNN's per-execute workspace does not do that, and FlashInfer's pooled scratch does not either, so the audit places it in a separate opt-in render mode, together with the work to drop the per-layer init launches. It is not part of this fix. No supported path renders `True`: `sm120/compiler.py` renders `False` at both MoE sites (`:423`, `:749`), and FlashInfer's shipped SM120 sources (all 28 frozen `sm120_*.py` sources at b1cf76608) launch the init kernel unconditionally. So stating the contract fixes the defect without changing any kernel.

This was found in an audit of the SM120 Frost kernel templates (finding B18).

**Pass the current PyTorch stream to the compiled launch.**

When `stream` is omitted, SM120 `_as_custream` converts it to CUDA stream 0. `counter.zero_()` runs on PyTorch's current stream. A non-default nonblocking current stream can therefore leave the reset unordered with the launch, causing FC2 to observe a stale counter and skip output tiles.

+            workspace=workspace,
