## Affected area

FE OSS kernels or CuTeDSL

## Summary

An explicit `attn_scale` of 0 now means a zero scale everywhere in FROST SDPA. It never means "use the 1/sqrt(d) default". Kernels that cannot compute a zero scale now refuse it instead of silently computing a different function.

1. **Sentinel removed.** Every `scale_softmax == 0.0 -> default` clause is gone. `None` is the only "use the default" value. #1212 already did this for the SM100/SM107 backward adapters. This PR covers the rest:
   - forward adapters: SM80, SM100/SM107 and SM120;
   - backward adapters: SM80, SM120 and SM100 MXFP8;
   - their execute-time overrides;
   - the prepared binders: `fwd/prepared.py`, `fwd/prepared_sm80.py`, `bwd/prepared.py`, and the native `python/pygraph/sdpa_sm80_binding.cpp` and `python/pygraph/sdpa_bwd_binding.cpp` (the latter arrived with #1433);
   - the `softmax_scale_prefolded` "requested" check.
2. **Kernel limitation stated where it lives.**
   - **Why zero fails:** the SM80, SM100/SM107 and SM120 forward kernels keep the running max over raw, `-inf`-masked scores and fold the scale into `exp2` afterwards. A zero scale therefore turns masked entries into `0 * -inf = NaN`. SM80 also divides its additive bias by the scale.
   - **Adapters:** these forward adapters and the SM80 binders now refuse 0 at plan time and at execute time, with an error that cites #1435.
   - **Graph eligibility:** the `zero_scale` capability declines 0, so the backend serves the graph.
   - **Removing it:** #1435 tracks the kernel fix. Once that lands, the capability can be removed.
3. **SM80 backward bias fixed at the root.** `bprop_f16.py` added `bias * (1/scale)` to the unscaled score before scaling, so a zero scale with an additive bias gave `inf * 0 = NaN` in dQ/dK/dV/dBias (review finding on this PR). The kernel now adds `bias * log2(e)` after scaling, the same function for every nonzero scale, and the `inv_softmax_scale` kernel parameter is gone.
4. **Rows that claim `zero_scale`.** Each was measured on GPU at scale 0, with and without a causal mask:
   - `sdpa_fwd_prefill_sm90`, which compiles a separate softmax per sign of the scale (`SCALE_ZERO`);
   - `sdpa_bwd_sm80`, `sdpa_bwd_sm100` and `sdpa_bwd_sm100_d256`;
   - the SM107 backward rows, whose existing zero-scale tests are unchanged.

   `SUPPORT_MATRIX_TRACKER.md` is updated per Rule S2.

A negative scale with a mask has the same NaN mechanism in the same forward kernels. That is a different root cause: there is no sentinel, and the SM120 FP8 d512 kernel deliberately supports negative scales. It is tracked in #1435 for a separate PR.

## Why

Rule 8 requires one graph contract across providers. With zero scale, P is uniform, so O is the mean of V and Stats is log(S_kv). The backend's correct engines compute that.

Measured on develop `1abe9e26d` before this PR: cuDNN 9.26, bf16, B=1, H=2, S=256, D=128, FROST ranked first under `CUDNN_FRONTEND_ENABLE_FROST_ENGINES=1`. Values are max absolute errors.

| GPU | engine | mask | O | Stats | dQ |
|---|---|---|---:|---:|---:|
| B200 | `sdpa_fwd_prefill_sm100` | none / causal | 0.62 / 1.91 | 1.01 / 1.34 | |
| A100 | `sdpa_fwd_prefill_sm80` | none / causal | 0.62 / 1.91 | 1.01 / 1.34 | |
| A100 | `sdpa_bwd_sm80` | none / causal | | | 2.27 / 4.78 (exact answer: 0) |

In every row the error against a 1/sqrt(d) reference is about 0, which shows the substitution.

With the sentinel removed, the per-kernel results are:
- `sdpa_fwd_prefill_sm100`: exact unmasked, NaN causal, at d = 128, 256 and 512.
- `sdpa_fwd_prefill_sm80`: raises `ZeroDivisionError` from its binder.
- `sdpa_fwd_prefill_sm90` (H100, d512): exact masked and unmasked.
- `sdpa_bwd_sm80`, `sdpa_bwd_sm100_d256`, `sdpa_bwd_sm100` (d512): dQ = dK = 0 exactly, and dV within 0.01 of the oracle, masked and unmasked.

## Related issues

- #1435: forward kernel support for scale <= 0.
- #1428: the backend's first-ranked causal engines (B200 eng10/eng5, H100 eng9) also return NaN at scale <= 0. This PR does not change backend selection. A default causal zero-scale graph on B200 now gets that NaN instead of a finite but wrong FROST result.

## API and compatibility impact

- **Direct API:** passing `scale_softmax=0.0` to the SM80, SM100/SM107 or SM120 forward adapters used to run at 1/sqrt(d). It now raises `NotImplementedError` at plan time, or `ValueError` at execute time.
- **Backward adapters** that newly keep 0 (SM80, SM120, SM100 MXFP8): passing 0.0 now means 0.
- **Graph API:** a graph declaring `attn_scale=0` is now served by the backend wherever the FROST row declines it. No other graph's eligibility changes.
