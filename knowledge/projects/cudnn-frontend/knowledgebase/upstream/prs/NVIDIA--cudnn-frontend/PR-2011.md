## Summary

The SM120 `block_scale_quantize` epilogue now writes 0 to the K-direction padding slots of every F8_128x4 scale row it produces. Before this change it left them unwritten.

- An F8_128x4 scale blob pads each scale row to a whole 4-block quad: `roundup(N/bs, 4)` slots for a row quant (blocks along N), `roundup(M/bs, 4)` for a col quant (blocks along M). The padding slots sit in the same 4-byte quad as the row's last real block. The lane that stores that block now also stores 0 to the remaining slots of the quad, under the same predicate as the scale store.
- `_emit_block_quant_col` (the SM120 col-quant emitter) does this inline.
- For the row quant, the SM120 `_emit_block_quant` wrapper appends the same stores after the shared `_emit_block_quant_row`. The shared emitter in `python/cudnn/gemm/frost/epilogue_codegen.py` is not modified, so the SM100 tree's output does not change.
- Grouped token-axis segments render as before. Their groups start at multiples of `4 * block_size`, so they have no padding slots.
- Rows that pad the blob up to a 128-row atom stay unwritten. Only consumer rows that are never stored read them.
- 10 new SM120 GPU tests. Each prefills the scale buffer with 0xFF and compares every real scale row, including its padding slots, against a zero-padded reference. They run only in a process that runs the sm120 tree, and the four block-scale ones only on an SM12x GPU.
- A host-only render check (3 cases) renders the kernel through the sm120 compiler without compiling it. Every row-quant scale store must be followed by a padding block under the same guard, and every col-quant scale store directly by its padding block, so a change to the shared row emitter's store guard or variable names fails it.

## Why

Nothing wrote the padding slots, so they kept whatever bytes the caller's buffer held: the epilogue stored only real `(row, block)` pairs, and no host step initialized the blob. A block-scaled GEMM whose K is the quantized axis and that loads whole F8_128x4 atoms multiplies these slots against its zero-filled K tail. Frost's own `sm120_block_scale_matmul.py` is one such consumer. If the buffer held a NaN encoding there (E8M0 `0xFF`, E4M3 `0x7F`/`0xFF`), `0 x NaN = NaN` turns that whole output row into NaN, with no error. Any `torch.empty` or reused allocation can hold such bytes. The existing tests did not catch it: they zero-fill the buffer, use shapes with no padding, or run only on SM100.

Minimal reproducer on SM120 through `jit_from_cudnn_graph` with `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`:

- Producer: bf16 GEMM M=200, N=2880 (the gpt-oss intermediate size), K=128, then `block_scale_quantize(block_size=32, axis=-1)`, FP8 E4M3 data and E8M0 scales with `F8_128x4` reordering, `scale_dim = (1, 256, 92)`. The scale buffer is prefilled with 0xFF.
  - Observed on develop: real scales and data are exact, but the 400 padding slots (blocks 90-91 of each of the 200 rows) are still 0xFF.
  - Expected: 0.
- Consumer: the SM120 MXFP8 block-scaled GEMM with A = that output, K = 2880, N = 128.
  - Develop: 200 of 200 output rows are NaN.
  - This branch: 0 NaN rows, max relative error 4.9e-4 against a torch dequantize reference.

The same gap shows up for the col quant (dense M=352: M-block 11 of 12 unwritten), for plain MoE (feature-axis N=160 and token-axis S=352, both kernel orientations), and for block-scale MoE (global and per-group segmented feature-axis blobs with N=160, both orientations). Every path that renders `_emit_block_quant` in the SM120 tree is affected: dense `sm120_matmul.py`, the two plain MoE templates and the two block-scale MoE templates. The dense block-scale template rejects quant epilogues.

Why this fix:

- It is done in the kernel, at the store that already owns the row's last block. There is no extra memset launch per call (Rule 2), no allocation and no host work. The generated code gains one integer compare (`block + 1 == num_blocks`) per scale store: `vsize / block_size` per chunk for the row quant, and `vsize / 32` per lane for the col quant (`vsize / 16` with 16-element blocks). A row quant under a row predicate also evaluates that predicate a second time, in a separate `if`. Only the lane that stores a scale row's last real block then runs three `block % 4` compares and up to three byte stores.
- 0 is a finite scale in every format used here: E8M0 `0x00` is 2^-127 and E4M3 `0x00` is +0. Each padding slot multiplies zero-filled data, so its value does not change any real output. TRT-LLM's quantizer (used by FlashInfer) writes 0 to its SF padding in the same way, and the test helper `to_blocked()` zero-pads.
- Only the K-direction padding is written. The 128-row padding feeds only consumer rows that are masked at the store: in the reproducer above, the 56 padding rows still hold 0xFF after this fix and the consumer output has no NaN. Zeroing those rows would need stores past the last M tile, because a CTA tile can be shorter than the 128-row atom. This PR leaves them alone, and the emitter docstring says so.

This was found in an audit of the SM120 Frost kernel templates (finding B03).

## API and compatibility impact

- Behaviour change, SM120 tree only: fused `block_scale_quantize` epilogues with `F8_128x4` scales now overwrite the K-direction padding slots of each stored scale row with 0. Before, those bytes kept the caller's contents. Real scale bytes, quantized data, the 128-row padding, and the accepted and declined graphs are unchanged.
- MoE graphs whose last offset is below the routed capacity (`fto[G] < S`): rows past `fto[G]` are not processed, as before. For a token-axis quant, the last capacity block then is not stored, and neither are the padding slots after it. This matches the documented untouched-trailing-rows behaviour.
- Backend/FROST parity (Rule 9): no engine defines these bytes today. On the same SM120 GPU, the native cuDNN 9.24 backend returns 7 `eng10` plans for the dense reproducer graph (M=200, N=320, 0xFF prefill). Three write 0 into the K-direction padding; knob-free `eng10` and `eng10_k24=11` also zero the 128-row padding. The other four, including the top-ranked `eng10_k24=25`, leave 0xFF. FROST now matches the plans that write zeros.
- Exported FlashInfer artifacts are not re-rendered. Their shapes (H and I multiples of 128) have no K-direction padding anyway.
- SM100 has the same gap, and that copy is intentionally left for a follow-up (the repo convention is to fix both trees):
  - The col quant scale store is at `python/cudnn/gemm/frost/sm100/epilogue_codegen.py:395-401`.
  - The row quant goes through `sm100/epilogue_codegen.py:405-420` into the shared `_emit_block_quant_row` (`python/cudnn/gemm/frost/epilogue_codegen.py:1064-1070`).
  - The follow-up must also update `_run_moe_swap_ab_quant` (`test_moe_grouped_matmul_fwd.py`, SM100 only; `test_moe_grouped_block_scale_matmul_fwd.py::test_moe_swap_ab_quant` calls it too). Its F8_128x4 cases with K-direction padding (`row_mmajor`, `row_reorder`, `row_grouped`, `col`, `packed`) expect those slots to keep the 0xA5 sentinel. `col_grouped` has none.
- Docs: the zero-padding contract that the audit recommends documenting is not added in this PR. Until the SM100 follow-up lands it would be false for the SM100 tree, so it belongs in that follow-up. Neither the public docs nor `fusion_ir.py` describe these padding bytes today. The SM120 behaviour is recorded in the emitter docstrings (`_f8_128x4_k_padding`, `_emit_f8_128x4_k_pad_zero`).
