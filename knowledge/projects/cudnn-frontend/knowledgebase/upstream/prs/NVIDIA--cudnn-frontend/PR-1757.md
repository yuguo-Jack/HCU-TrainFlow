## Affected area

FE OSS kernels or CuTeDSL (DSA dense indexer forward: SM100-family score kernels and their Python entry points).

## Summary

The dense indexer forward can now write BF16 scores instead of FP32.

- `DSA.indexer_forward_wrapper(..., out_dtype=None)`: new trailing parameter. `torch.float32` (default) or `torch.bfloat16`; `None` takes `out.dtype` when `out` is given, else FP32. The same parameter is appended to the SM100 `indexer_forward._interface.indexer_fwd`.
- `DSA.IndexerForward`: `sample_out` / `out` may be BF16; the plan's score dtype is the sample's dtype, and `execute()` rejects an `out` of another dtype.
- Kernels: in the SM100/SM103 BF16 scorer (`IndexerScoreUnifiedSm100`) and the MXFP8 scorer (`IndexerScoreUnifiedSm100Mxfp8`, all three epilogue variants), the dense store goes through `round_score_for_store(score, mOut.element_type)`. Accumulation, the per-head ReLU x W FMA chain and the head reduction stay FP32; a BF16 output rounds the finished score once (`Float32.to(BFloat16)` lowers to `arith.truncf` with the default rounding, i.e. `cvt.rn.bf16.f32`). For an FP32 output the helper returns the score unchanged, so the FP32 kernels are unchanged.
- Layout: BF16 rows are padded to whole 16 bytes like FP32 rows (`ceil8(S_k)` instead of `ceil4(S_k)`); the strict entry (`_indexer_fwd_bound`) and `IndexerForward.check_support()` enforce the per-dtype alignment.
- The output dtype is part of both compile keys (BF16 and MXFP8 scorers).
- The `-inf` prefill of a BF16 buffer whose rows hold an even number of elements is issued through an `int32` view of the same storage (two `0xFF80` per store). torch's `fill_` stores 16-bit elements at about half the bandwidth of 32-bit ones (1M-key GB300 case below: 8.4 ms for the 32 GiB BF16 buffer vs 8.8 ms for the 64 GiB FP32 one); the int32 view brings it to 4.39 ms (FP32: 8.8 ms). Same bits, still one kernel, no copy; other shapes keep the plain `fill_`.
- SM90 writes FP32 only: `out_dtype=torch.bfloat16` (or a BF16 `out`) raises `NotImplementedError` before the SM90 interface runs. The compressed-logits path (`indexer_forward_top_k_wrapper`) keeps its FP32 candidates; passing a BF16 `out_dtype` to it raises `ValueError`.
- Docs: `docs/fe-oss-apis/dsa.md`, Indexer Forward output contract and example.

## Why

Long-context DSA training writes the dense indexer scores and immediately runs top-k over them. At GLM-5.2 1M-token context (CP64, rank 0: 16384 query rows x 1M keys, 32 heads x 128, top-k 2048, GB300) the FP32 score buffer is 64 GiB per call, and the top-k reads all of it. Casting the finished FP32 matrix afterwards does not help: the 64 GiB buffer and the FP32 write stay, and the cast adds a full read + write pass (about 48 GB for the causal part, 103 GB for the whole rectangle). Only the kernel writing BF16 removes them.

This follows what DeepSeek ships for DSA: DeepGEMM's MQA-logits kernels write BF16 logits from the epilogue (at DeepSeek-V4's release `logits_dtype` with an FP32 head reduction and one cast at the store; since 057ca59 BF16 is hard-wired on SM100 with each head's product rounded to BF16 and a BF16 head reduction), and DeepSelect's lightning-indexer top-k takes BF16 input. The rounding here is the DSv4-release one: FP32 math, one round-to-nearest-even at the store, so it is numerically no worse than either DeepGEMM variant.

Measured effect at the 1M CP64 rank-0 shape on GB300 (details in Testing):

- Memory: the score buffer halves (64 -> 32 GiB) and the peak of scorer + FE top-k drops by 36 GiB (72.25 -> 36.19 GiB, the top-k scratch is halved too).
- Time: the scorer (fill + kernel) goes from 60.2 to 55.0 ms; the kernel itself is compute-bound (51.5 vs 50.6 ms), so most of that is the `-inf` fill (8.8 -> 4.4 ms). With DeepSelect's BF16 top-k (5.9 -> 4.0 ms) the scorer + top-k pipeline drops from 66.0 to 58.9 ms per call (MXFP8 scorer: 51.0 -> 44.7 ms).
- FE's own `indexer_top_k` accepts BF16 but is currently slower on BF16 than on FP32 at 1M keys (14.4 -> 22.7 ms), so with it the pipeline gets slower (74.6 -> 77.5 ms); see Follow-ups.
- Selection: the BF16 selection differs from the FP32 one only by keys tied at the BF16 cutoff value (verified on every row of every run, 0 exceptions); recall@2048 against the FP32 selection is 0.995 at 1M on synthetic and real-activation inputs and 0.999 on 240 real training calls.

### Hard Rules notes (`python/cudnn/AGENTS.md`)

- Rule 1: `IndexerForward.execute()` validates `out`'s dtype against the plan and never converts; no new allocation on the strict path.
- Rule 2: no extra kernel. The BF16 prefill is the same single fill, issued on an `int32` view of the caller's storage.
- Rule 4: the output dtype is a plan-time property of `out` and joins the compile key (detector: the class test asserts exactly one new key differing only in the dtype).
- Rule 7: no new CuTe DSL API (`Float32.to(BFloat16)` exists at the 4.6.2 floor; tested on 4.6.2).

## Related issues

None filed. Overlap: a separate draft PR from the same author adds `clean_logits` (opt-out of the `-inf` prefill) to the same dense wrappers (`indexer_forward_wrapper`, `IndexerForward`, `_interface.indexer_fwd` / `_indexer_fwd_bound`, `_interface_sm90.indexer_fwd`). Both append a trailing parameter and both touch the prefill call site; whichever lands second needs a small rebase (the two features combine: `clean_logits=False` skips the BF16 prefill too).

## API and compatibility impact

- Append-only: `out_dtype` is the new last parameter of `indexer_forward_wrapper` and `_interface.indexer_fwd`, default `None` (= FP32 unless the caller's `out` is BF16). `IndexerForward` keeps its signature; it now also accepts a BF16 `sample_out`.
- Default behaviour is unchanged: FP32 scores, same kernels, same `-inf` fill, same compile-cache entries plus the dtype element.
- Previously a BF16 `out` raised `ValueError`; it now selects BF16 scores. An unsupported `out` dtype (e.g. FP16) still raises `ValueError`.
- `TMA_ALIGN_ELEMS` (= 4) and `padded_seqlen_k(seqlen_k)` keep their values for FP32; `padded_seqlen_k` gained an optional `dtype` argument and `out_row_align_elems(dtype)` gives the per-dtype alignment.
- Architectures: SM100/SM103 for BF16 output; SM90 declines BF16 with `NotImplementedError` (FP32 unchanged). No new CuTe DSL API (works on the 4.6.2 floor).

## Follow-ups (not in this PR)

- FE `indexer_top_k` on BF16 input: its coarse 8-bit histogram key for BF16 is the top byte (sign + 7 exponent bits, two binades per bin), while FP32 goes through FP16 first (5 exponent + 2 mantissa bits). At 1M keys the BF16 threshold bin is much fuller, and BF16 top-k measured 22.7 ms vs 14.4 ms for FP32. Using the FP16-derived key for BF16 as well should fix that; separate PR.
- SM90 BF16 output (the SM90 scorer stores FP32 from its own epilogue).
