# perf(bsa): compile the SM100/SM103 FP8 blk128 kernel with --opt-level 2

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1801) · state: closed · merged: True

## Original PR description

## Summary
Pass `--opt-level 2` to `cute.compile` for the SM100/SM103 Sage FP8 blk128 kernel (`_bsa_attn_fwd_sm100_fp8_blk128`). The CuTe DSL default (`--opt-level 3`) makes this kernel ~2.4x slower on SM103, so blk128 was slower than blk64 despite doing more work per token pair. On SM100 the option is a small win (~2.5%) with no regression.

## Measurements
B1 H40 Sq=Sk=128K D=128, topk=256 selected KV blocks, Sage FP8, attention kernel only (Q/K/V quantized outside the timed region), median of 10 runs.

**B300 (SM103)**

| nvidia-cutlass-dsl | blk64 (default) | blk128 (default) | blk128 (`--opt-level 2`) |
|---|---|---|---|
| 4.6.2 | 30.87 ms / 1425 TFLOP/s | 98.78 ms / 891 TFLOP/s | 41.88 ms / 2101 TFLOP/s |
| 4.7.0 | 30.87 ms / 1425 TFLOP/s | 98.79 ms / 890 TFLOP/s | not measured |
| 4.8.0 | 30.66 ms / 1434 TFLOP/s | 98.88 ms / 890 TFLOP/s | not measured |

The slowdown does not depend on the DSL version.

**B200 (SM100)**, DSL 4.6.2, develop vs this PR, two runs each:

| | develop (O3) | this PR (O2) |
|---|---|---|
| blk64 (unchanged) | 35.27 / 35.45 ms | 35.33 / 35.49 ms |
| blk128 | 56.94 / 56.68 ms (~1548 TFLOP/s) | 55.21 / 55.34 ms (~1591 TFLOP/s) |

blk64 is unaffected by the option and is not changed here (its two columns differ by <0.2%, which is the noise floor). blk128 is ~2.5% faster on B200, close to the run-to-run spread, so read it as "no regression".

## Why O3 is slower (SM103, DSL 4.6.2, SASS comparison)
The PTX of the two builds is byte-identical, so the difference is entirely ptxas optimization level. Confirmed in SASS:
- **Register spills in the softmax warps** (the `0xb8`-register role, which contains the `tcgen05.ld.red...max` / `LDTM.STAT` row-max loads): O3 has 137 STL / 83 LDL there and a 304 B stack frame; O2 has 0 / 0 and a 40 B frame. The correction/epilogue role has ~11-13 spills in both builds (baseline).
- **exp loop register reuse serializes the exp chain**: in O3, 119 of 259 `MUFU.EX2` are fed from a just-written `FFMA2` temp (117 of them R2/R3 reused every pair), plus 428 `IMAD.MOV` register shuffles. In O2 there are 0 such temp-fed exps and 106 shuffles, and `FFMA2`/`MUFU.EX2`/`F2FP` are interleaved.

The "serialization causes the slowdown" part is inferred from the instruction pattern; no profile or stall-reason data was collected, and the two effects were not separated by turning off one at a time.

## Notes
- Only this one compile call changes; the other BSA compile sites were not measured and are left alone.
- Outputs of the O2 and O3 builds are bit-identical on a small shape (B1 H4 S4096 topk8, B300).
- Single shape only; no sweep over sequence length, topk or head count.
