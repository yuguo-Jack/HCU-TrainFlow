## Summary

The G08 lifecycle check in `samples/cpp/misc/cudagraph_topology.cpp` (added in #1140) compared `cudaMemGetInfo` free memory before and after each loop count and failed on a loss above 32 MiB. `cudaMemGetInfo` reports the whole device, so the check also fails when another process on the same GPU allocates during the window, or when the driver or a pool grows once. Neither is a leak in the lifecycle under test.

- Each loop count (10/50/100/200) now gets up to three attempts. An attempt counts as clean only when its delta stays within the 32 MiB slack in both directions; the loop count passes on the first clean attempt and fails after three unclean ones. A leak that scales with the loop count loses memory on every attempt, so it still fails. A large gain is another process freeing memory in the window, which could cancel a leak, so it is retried like a large loss.
- Both `cudaMemGetInfo` readings of an attempt must be valid (a failed call reads `{0, 0}`).
- Every attempt is logged with `attempt=<n>/3`, so a CI log shows a one-off loss and its clean retry next to each other.
- The comment states the remaining assumption: the window is not contaminated by an amount that matches the leak. On a shared GPU the check stays best-effort.
- No other test case changes; the 32 MiB slack, the warm-up and the per-loop work are the same.

## Why

Fixes #1797. On the H100 PCIe CI job, loops=10 passed with a 0 B delta and loops=50 failed with `device_free_delta_bytes=-295698432` while every checksum passed. A leak in the loop would have scaled down to loops=10 (about 59 MiB there); a one-time ~282 MiB step is what a foreign allocation or a one-time driver/pool growth looks like.

## Related issues

Fixes #1797. Introduced by #1140.

## API and compatibility impact

None. Sample-only change.

## Testing

GH200 (sm_90), cuDNN 9.27.0, CUDA 13.2: `cudagraph_topology.cpp` built alone with the samples target's warning flags (`-Wall -Wextra -Wpedantic -Werror`) and run as `"186 G08*"`. "develop" is the unmodified file; "this PR" is `0ab2b07785d5`. The control variants exist only for this test and are not part of the PR.

| Case | Runs | develop | this PR |
|---|---|---|---|
| idle GPU | 5 / 10 | 5 passed | 10 passed |
| control: 1 MiB `cudaMalloc` leaked per iteration | 3 | 3 failed (loops=50: −52 MiB) | 3 failed (loops=50: −48 to −52 MiB on all three attempts) |
| control: one-time 300 MiB `cudaMalloc` at the start of loops=50 | 3 | 3 failed (loops=50: −304 MiB) | 3 passed (attempt 1 −300 MiB, attempt 2 0 B) |
| another process takes and returns 300 MiB every 15 ms | 30 | 25 failed | 13 failed |
| the same neighbour **and** the 1 MiB/iteration leak | 15 | | 15 failed (the first head of this PR, `0a2b181a`, passed 2 of these 15) |

The one-time step reproduces the CI signature (−314572800 B here, −295698432 B in #1797). The last row is the cancellation the review pointed out: with the first head's rule (accept any attempt that did not lose more than the slack), a run where the neighbour's free lands in a window passed despite the leak; with the symmetric rule none did. A neighbour that churns memory every few milliseconds can still fail the check (13 of 30 here); that is the documented limit of a device-wide reading, not a leak. GH200 windows are shorter than on H100 PCIe (loops=200 takes about 12 ms here against 540 ms in the CI log), so the CI timing itself was not reproduced.
