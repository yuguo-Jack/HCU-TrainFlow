## Summary

Follow-up to #2011 (B03, merged). #2011 made the SM120 `block_scale_quantize` epilogue write 0 to the K-direction padding slots of each F8_128x4 scale row. Its internal review asked for two test changes. The commit that makes them landed on the #2011 branch after the PR had merged, so this PR cherry-picks it onto develop 18df4c38 (`git cherry-pick -x 7bd0877d`, no conflicts). Nothing under `python/` changes.

- New host-only test `test_matmul.py::test_sm120_quant_scale_k_padding_render` (3 cases, L0 through the module mark). It renders the kernel source through `cudnn.gemm.frost.sm120.compiler.jit_from_cudnn_graph`, with `_import_kernel` monkeypatched to raise before the DSL compile, so nothing is compiled or launched. The cases:
  - `plain`: dense row quant, M=200, N=2880, no row predicate.
  - `bounded_rows`: dense row + col quant, M=352, N=320. The row quant runs under the col quant's row predicate.
  - `swap_ab`: MoE token-axis quant, which is the row quant of the weight-by-token kernel and is bounded by `group_end`.

  In the rendered source it checks that:
  - the row-quant scale stores `(gC_tap_<t>_ptr + _q<i>_sidx<k>).store(_q<i>_scale<k>, alignment=1)` and the padding blocks `if _q<i>_scol<k> + 1 == (N // 32):` match one for one, in order, each pair under the same enclosing guard;
  - each padding block reads only `_q<i>_scol<k>` / `_q<i>_sidx<k>` names that the rendered source assigns before it;
  - every col-quant scale store is followed directly by its padding check `if _q<i>_mb + 1 == (M // 32):` (only `bounded_rows` has a col quant).
- The 10 GPU tests that #2011 added now call `skip_unless_pipeline_active(cfg)` first: `test_matmul.py::test_sm120_quant_scale_k_padding_is_zeroed` (2), `test_moe_grouped_matmul_fwd.py::test_moe_quant_scale_k_padding_is_zeroed_sm120` (4) and `test_moe_grouped_block_scale_matmul_fwd.py::test_e2e_quant_scale_k_padding_is_zeroed_sm120` (4). In a process that runs the sm120 tree they run as before.

## Why

#2011's tests left two gaps.

1. **Nothing checked, without a GPU, that the row-quant padding still matches the emitter it is attached to.** The shared `_emit_block_quant_row` (`python/cudnn/gemm/frost/epilogue_codegen.py`, also used by the sm100 tree) emits the row-quant scale stores, and #2011 left it untouched. The sm120 `_emit_block_quant` (`python/cudnn/gemm/frost/sm120/epilogue_codegen.py`) appends the padding stores after the shared emitter's output. It repeats that emitter's store guard (`if ({row_pred}) & (col_j + {width} <= {col_bound}):`) and reads its local names `_q{i}_scol{k}` / `_q{i}_sidx{k}`. A later edit of the shared emitter can break the sm120 padding without touching any sm120 file:
   - Renamed locals: the rendered kernel reads names that no longer exist and fails to compile.
   - A changed store guard: the padding is written under a different predicate than its scale. A stored scale row can then keep stale padding bytes, or padding can be written for a row whose scale store the new guard excludes.

   Before this PR, only the GPU tests could notice, and only on an SM12x GPU that runs the sm120 tree. The render check notices on every lane that runs `test_matmul.py` (100 <= SM < 130), in about 1.5 s.

2. **The GPU tests fail instead of skipping in a process that runs the sm100 tree.** That is every SM10.x GPU without `CUDNN_FRONTEND_GEMM_ARCH_FAMILY=sm120`. The tests pin `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`. The sm100 compiler declines that config in a semantic check before its family check runs: root `AGENTS.md` (FROST GEMM bullet) says `_check_own_family` declines the other family's template *after* the semantic gates. The frost conftest turns only the arch-range and family messages into skips, so this decline is reported as a failure.

   Minimal reproducer on develop 18df4c38, SM120 GPU, sm100 tree pinned:

   ```
   cd test/python
   CUDNN_FRONTEND_GEMM_ARCH_FAMILY=sm100 python -m pytest -q -p no:cacheprovider -p no:xdist \
       gemm/frost/test_matmul.py gemm/frost/test_moe_grouped_matmul_fwd.py \
       gemm/frost/test_moe_grouped_block_scale_matmul_fwd.py -k quant_scale_k_padding
   ```

   - Observed: `10 failed`, each with `NotImplementedError: block_scale_quantize requires block_size to divide the epilogue chunk width (= the largest quant block, clamped to the lowest set bit of cols_per_acc_stage=128 and to 32 elements); got block_size=32, vsize=8`.
   - Expected: the 10 tests skip, like other tests that pin an sm120 config in a process running the sm100 tree.
   - This branch: `3 passed, 10 skipped` (`the sm120 pipeline is served by the sm120 arch tree; this process runs the sm100 tree`).

   On SM10.x hardware the 4 block-scale MoE tests already skip through `requires_sm120`. The ones that fail there are the 2 dense and 4 plain-MoE tests, which are gated only by `requires_matmul_gpu` (100 <= SM < 130).

Why this approach:

- The render check reads the generated source, which is where the two emitters' output meets, and needs no GPU and no DSL compile. It imports the sm120 compiler by name, as root `AGENTS.md` asks of a test of one tree's renderer, so it also runs in a process that runs the sm100 tree.
- `skip_unless_pipeline_active` (`gemm_test_utils.py`) is the existing helper for tests that pin one family's config. `test_matmul.py` already imports it as `_skip_unless_active`. The two MoE files import it inside the test, as they already do for other `gemm_test_utils` helpers.
- No AGENTS.md change: the ordering this relies on (family check after the semantic gates, only the family message reported as a skip) is already in the root `AGENTS.md` FROST GEMM bullet.

Both changes were asked for in the internal review of #2011. #2011 fixed a finding from an audit of the SM120 Frost kernel templates (finding B03).

## API and compatibility impact

None. This PR changes only tests:

- In a process that runs the sm120 tree, the 10 GPU tests run as before.
- In a process that runs the sm100 tree, they now skip instead of failing.
- The 3 render checks are new L0 tests. They run wherever `test_matmul.py` runs (100 <= SM < 130), in either arch tree.

SM100: the SM100 tree still leaves the K-direction padding unwritten. #2011 left that copy for a follow-up, and this PR does not change it. The render check covers only the sm120 tree's padding.
