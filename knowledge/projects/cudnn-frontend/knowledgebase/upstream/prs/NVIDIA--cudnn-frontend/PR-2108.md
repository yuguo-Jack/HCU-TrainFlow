## Summary

Four tests skipped everywhere but cc 10.0, although the code they cover also serves cc 10.3:

| Test | Gate before | Why cc 10.3 is in scope |
|---|---|---|
| `norm/graph/test_frost_norm_affine.py` (autouse fixture) | `!= (10, 0)` | the FROST norm rows list `archs = {(10, 0), (10, 3)}` (`norm/fprop/engines.py`, `norm/bprop/engines.py`) |
| `core/jax/conftest.py` (autouse fixture) | `compute_capability != "10.0"` | `cudnn.jax.call` has no arch check; `linear_attention/jax/conftest.py` already accepts `("10.0", "10.3")` |
| `gemm/jax/test_grouped_gemm_canonical_jax.py::test_canonical_jax_glu_hadamard_quant_delayed_act` | `!= (10, 0)` | the GLU-Hadamard-quant kernel accepts SM100+, and cc 10.3 runs the same epilogue barriers |
| `sdpa/frost/test_sdpa_native_split_binding.py::test_standalone_split_requires_caller_workspace_without_allocating` | `!= (10, 0)` | the d64 split decode goes through the SM100 row, which spans cc 10.3 |

Each gate now accepts `(10, 0)` and `(10, 3)`. No product code changes.

## Why

These cases never ran on a B300.

## Related issues

None found.

None. Test only.

## Testing

B300 (cc 10.3), develop `64ed3dfe` with its own extension, torch 2.14.1+cu130, cuDNN 9.27.0, CuTe DSL 4.8.1, JAX 0.12.0.1, `CUDNN_FRONTEND_ENABLE_FROST_ENGINES=1`, run from `test/python`:

| Module | develop | this PR |
|---|---|---|
| `norm/graph/test_frost_norm_affine.py` | 114 skipped | 114 passed |
| `core/jax/test_call_jax.py` | 13 skipped | 13 passed |
| `gemm/jax/test_grouped_gemm_canonical_jax.py::test_canonical_jax_glu_hadamard_quant_delayed_act` | 1 skipped | 1 passed |
| `sdpa/frost/test_sdpa_native_split_binding.py` | 181 passed, 25 skipped | 183 passed, 23 skipped |

The 23 remaining skips in the split-binding module are the dense-binding cases it reuses, which pin each part on purpose: cc 10.3 has its own variants in `test_sdpa_native_arch_binding.py`. Not run on cc 10.0, where every gate admits the part as before.
