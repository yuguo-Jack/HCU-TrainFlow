# perf(bsa): faster KPage layout build on SM90 and SM100 (CuTe metadata check, fewer syncs, coalesced table fills)

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2246) · state: closed · merged: True

## Original PR description

## Summary

Speeds up building a KPage layout: `kpage_prepare_layout`, and the build that every `kpage=True` call runs. This PR covers only the work before the attention kernel. The attention kernels are unchanged, and every table they read is bit-identical to `develop`.

**All architectures**
- The metadata check is one CuTe DSL kernel (`ValidateMetadata`). It replaces about a dozen torch kernels, one of them a sort of the whole index tensor. Invalid metadata still raises the same errors: if the kernel finds a violation, the former torch check runs to locate it.
- The check result is read back on the build's table-sizing sync, so a forward layout synchronizes the host once instead of twice.
- Docs: the KPage section and the `kpage` docstring now recommend one prebuilt layout per sparse pattern, passed to every layer's forward and backward. A layout build synchronizes the host; calls that take a prebuilt layout do not.

**SM90 (blk64 and blk128)**
- `RefineBlk128ToBlk64` runs one warp per walk and also writes the blk64 block sizes. It writes its output directly in the final `[heads, n_q64]` row layout, so the zero fill and the `.contiguous()` copy of the whole index are gone.
- `PairWalkStats` writes the tile counts and `PairWalkFill` derives its own offsets. This removes several torch ops.
- `PairWalkFill` stores coalesced: page ids are staged in shared memory, and dense bitset words are written by a warp. The padding-row mask is built only when a backward first needs it.

**SM100/SM103**
- Backward tables: `BwdKvPackSlots` replaces the single-thread packer and about 17 torch ops around it with a parallel kernel. A cumsum plus scatter replaces the single-CTA work compaction and a stable argsort. The backward config goes through pinned memory, so the backward tables synchronize once.
- Forward tables:
  - The blk128 `WalkFill` stages its stores for coalescing.
  - `WalkFill` places full and tail pages in one pass over the edges.
  - The M128/M64 route ordering is one launch.
  - Tile ends are consumed in place, so the blk64 build reads no Q sizes.

## Validation
- **Bit-identical tables.** Every table was compared with the previous commit after each change, on production-shaped and random layouts (65-107 per change). The layouts cover partial blocks, empty rows, sequences ending 64 rows into a block, `bwd_kv_groups` and multi-chunk K/V. `torch.empty` was sentinel-filled during the comparison, so the entries each kernel writes were checked as well.
- **Sanitizers.** compute-sanitizer memcheck, racecheck and synccheck are clean on the new kernels, with `PYTORCH_NO_CUDA_MEMORY_CACHING=1`.
- **SM90 initcheck.** The reports are unchanged by this PR. They are all in the backward's `sum_OdO`, which reads O after the forward wrote it with TMA stores. initcheck does not count TMA stores as initializing memory; pre-filling O with ordinary stores makes the reports disappear.
- **Contract test.** `test_BSA_kpage.py` gains these cases: zero valid tokens, count > capacity, and violations in late walks of a mask with more walks than the check has CTAs.
- **Tests.** On the rebased branch:
  - SM103 (B300): `test_BSA_kpage.py` (all levels), 36 passed.
  - SM90 (H100): `test_BSA_kpage.py`, `test_BSA_kpage_blk64.py`, `test_BSA_sm90_blk128.py`, `test_BSA_pair_refinement.py` and `test_BSA_sm90_backward_sync.py` (all levels), 176 passed and 0 failed. These also report 8 errors at teardown, all `AttributeError: 'cuBLASModule' object has no attribute 'allow_tf32'` from the torch build in the test environment.
  - B200 was not rerun.
