# Accept canonical layouts in the grouped Hadamard GLU and test NVFP4 canonical backward

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1601) · state: closed · merged: True

## Original PR description

## Summary

Extends the canonical layouts from #1233 and #1422 to the NVFP4 paths that Transformer Engine's fused grouped MLP calls, and trims host time in the NVFP4 wrappers.

- **Hadamard GLU** (`grouped_gemm_glu_hadamard_wrapper_sm100` and `GroupedGemmGluHadamardSm100`) accepts contiguous A `(m, k)`, dense B `(l, n, k)`, prob `(m,)`, and packed scale buffers of any rank. With 2-D A the wrapper returns 2-D C and D. The wrapper advertises `supports_canonical_layouts`. Legacy layouts are unchanged.
- **dGLU and wgrad** already accept canonical NVFP4 operands; this adds the tests. No code change was needed.
- **Host time:** `wrapper_operand_meta`, which builds the memo keys of the dGLU, wgrad, quant and GLU wrappers, reads torch metadata directly. The dGLU workspace alias check reads one byte size per contiguous operand.

Canonical operands must be `torch.float4_e2m1fn_x2`. Raw `torch.uint8` FP4 inputs keep the legacy layouts.

## Benchmark: TE NVFP4 fused grouped MLP

Setup:
- TE #3641 (`756f427`), default `NVFP4BlockScaling` recipe (RHT, so FC1 runs the Hadamard GLU), SwiGLU, per-expert weights.
- B200 with one pinned CPU core.
- Host time is the p50 of 200 steps. Each cell is the median of 3 interleaved runs.
- The path is host-bound at both shapes: end-to-end time is host time plus 15 to 20 µs.

Shapes:
- **S:** 8 experts, H 2048, F 512, 4096 tokens.
- **L:** 64 experts, H 4096, F 1024, 16384 tokens.

Host time, µs:

| | S fwd | S fwd+bwd | L fwd | L fwd+bwd |
|---|---:|---:|---:|---:|
| develop | 553 | 1906 | 965 | 3266 |
| this PR | 555 | 1885 | 964 | 3225 |
| this PR + #1602 (stream fast path) | 557 | 1851 | 972 | 3206 |
| TE unfused (cuBLAS) | 476 | 1340 | 959 | 3010 |

Per-wrapper host time, µs per call. Each wrapper is called in isolation with the exact arguments TE passes at shape S, median of 3 interleaved runs:

| | Hadamard GLU | dGLU | wgrad |
|---|---:|---:|---:|
| develop | 41 | 119 | 22 |
| #1602 stream fast path only | 41 | 91 | 22 |
| this PR | 43 | 107 | 18 |
| this PR + #1602 | 43 | 81 | 18 |

The Hadamard GLU is about 1 µs slower because of the canonical layout checks.

TE with canonical NVFP4: a local TE patch passes canonical operands to the Hadamard GLU (2-D A, flat SFA, 1-D prob).
- The forward output, dx, dprob and every weight gradient are bitwise identical to the legacy layouts.
- Forward host time drops from 555 to 543 µs because TE no longer builds the 3-D/6-D views.

The FE wrappers account for about 350 µs of the 1.85 ms fwd+bwd step at shape S. The rest is TE host work, for example eight `_nvfp4_global_scale` calls per step, group quantization, and the cuBLAS FC2 and dgrad GEMMs. That host work is why the fused path is still slower than unfused here; this PR cannot close that gap.

## Testing

All on SM100, comparing canonical against legacy bitwise.
- **Hadamard GLU:** C, D, amax and post-RHT amax for three FP4 recipes, with physical and flat scale buffers, on cold and warm calls (6 new tests).
- **dGLU, NVFP4:** D_row and amax bitwise, dprob within tolerance, with physical and flat scale buffers (2 new tests).
- **wgrad, NVFP4:** flat scale buffers, including a changed token count that reuses the compiled kernel (the existing test is now parametrized over MXFP8 and NVFP4).
- **Targeted:** the Hadamard GLU, backward canonical, canonical layout, wrapper memo, dGLU workspace, prepared call, GLU canonical and quant canonical suites: 203 passed.
- **Wider regression** (every `gemm/cutedsl` test matching `grouped`): 1809 passed, 1320 skipped, 0 failed.

## Not covered

- `grouped_gemm_glu_hadamard_quant_wrapper_sm100` still takes only the legacy layouts.
- Rubin is not hardware-tested.
- Transformer Engine still disables canonical layouts for NVFP4; the patch measured above is local and not part of this PR.
- TE's NVFP4 fused path with `single_grouped_weight=True` crashes on upstream main: the FC1 weight scale view uses the logical K (`ceil_div(fc1_weight_shape[1], k_sf_divisor)`). The measurements above use per-expert weights.
