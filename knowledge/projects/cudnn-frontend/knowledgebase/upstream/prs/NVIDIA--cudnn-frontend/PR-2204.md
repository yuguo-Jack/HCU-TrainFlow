# test(sdpa): qualify SM120 base-2 Stats on the f16 and FP8 forward templates

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2204) · state: open · merged: False

## Original PR description

## Problem

The SM120 table in `SUPPORT_MATRIX_TRACKER.md` kept **Base-2 stats (`stats_use_log2`)** at ❔ on both forward columns.

- The wiring reaches all four f16 templates (decode tile included), the FP8/MXFP8 templates and the final split combine, but the section says "target-SM120 numerical validation remains required".
- Before this change, only the exact-D128 FP8 sink split (#2184) and the decode tile's own test drew base-2 Stats on SM120.

## Change

New `test/python/sdpa/frost/test_sdpa_stats_log2_sm120.py`. It checks `Stats == log2(e) · LSE` and O against an fp64 reference.

- `test_sm120_stats_use_log2` (f16/bf16):
  - Templates: general (D64, D128), D256, and D512 (D320 envelope and native D512).
  - Shapes: `S_q == 1` and prefill, causal and non-causal.
  - Plans: the first ranked unsplit plan and the first ranked split plan, so the base-2 LSE also comes out of the split combine.
  - Decode shapes at D64/D128 rank only split plans; their unsplit case skips.
- `test_sm120_fp8_stats_use_log2` (per-tensor FP8):
  - D64 to D512, prefill and decode, unsplit and split-4.
  - Uses the shared prepared-FP8 harness (`test_sdpa_prepared_fp8`), as #2184 does.

Tracker: SM120 base-2 Stats are now ✅ for f16/bf16 and for per-tensor FP8. MXFP8 stays ❔, because `sdpa_mxfp8` graphs take no `stats_use_log2` input. The validation note names the test and states that no cc 12.1 device was run.

No kernel or lowering change.

## Tests

On an RTX 5090 (cc 12.0), develop d760fefe, cuDNN 9.27, CuTe DSL 4.8.1:
- `test_sdpa_stats_log2_sm120.py`: 88 passed, 8 skipped (the D64/D128 decode shapes that rank no unsplit plan).
- `pre-commit` on the touched files passes.

The session fixture binds cudnn_handle to a separate nonblocking CUDA stream, while this test creates Q/K/V and fills O/Stats on the current Torch stream. execute uses the handle's stream without waiting for those writes. With pending producer work, the test can read unfinished inputs or race the sentinel fills and report a numerical failure. The device synchronize after execute waits for completion but does not order these operations. Before execute, make torch.cuda.ExternalStream(cudnn.get_stream(cudnn_handle)) wait for torch.cuda.current_stream(); the existing synchronize then covers the reference reads. This is a test reliability issue, not a confirmed attention-kernel defect.
