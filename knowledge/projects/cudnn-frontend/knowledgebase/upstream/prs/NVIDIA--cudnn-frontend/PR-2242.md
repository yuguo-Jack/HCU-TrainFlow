# frost(linear_attention): fused GDN decode and MTP verify steps for SM100-class parts + the frost_fe backend of FlashInfer's Qwen 3.5 GDN block

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2242) · state: closed · merged: True

## Original PR description

## Summary

Two fused Gated DeltaNet (GDN) kernels for the GDN sub-layer of a Qwen 3.5-architecture dense 27B model (tensor-parallel rank 1: 16 K heads, 48 V heads, head dim 128, conv width 4, hidden 5120), each one CuTe DSL launch per serving step on SM100-class parts, plus their registration as the `frost_fe` backend of FlashInfer's experimental Qwen 3.5 GDN block (`flashinfer.qwen_3_5_gdn_block`, public since FlashInfer PR #8131).

- **Decode step** (`GdnDecodeFused`): after the FP8 QKVZ projection, one launch does the BA projection, the causal conv + SiLU over the slot's history, the Q / K RMS scales, the gated delta-rule state update, the gated RMSNorm, the static per-tensor FP8 output quantization and the conv-history shift. One CTA per (request row, V head) with 256 threads in two warpgroups; the 128 x 128 fp32 state rows stay register-resident across the two passes and travel through padded, bank-conflict-free shared-memory boxes by `cp.async.bulk`.
- **MTP verify step** (`GdnVerifyFused`): the same chain for a request's `T` tokens (`T` = 1 + drafts, a compile-time constant) run sequentially on the register-resident state in one launch, the state after every token written to its own slot in FlashInfer's per-token `state_indices` layout (request `n` with `a` accepted tokens starts from slot `[n, a - 1]` and writes token `t` to `[n, t]`; a slot `<= 0` skips the write; a request whose source or conv slot is `<= 0` is padding and touches nothing). Ragged steps (a request with fewer than `T` tokens) are served when the caller states the step's row count.
- **The default form follows two plan-time facts, the request count and the device's SM count**: a cluster pair (two CTAs per V head, half the state rows each; for the verify step the gated norm's chain sums are exchanged per token through distributed shared memory by `st.async`) while the `requests x 96` cluster grid has an SM per CTA (one request on 148- / 152-SM parts); one CTA per SM while the `requests x 48` grid has one (two or three requests there); a register-capped two-CTAs-per-SM form past that, so the grid runs in one wave. The two register-resident verify forms trace the token loop once (`ROLLED_TOKENS`: the same arithmetic in the same order in a far smaller image), because every layer's launch in a serving step finds its code evicted from the instruction cache. Every knob -- thread mapping, state path, streaming, occupancy pad, conv-first issue, store pipeline, single traced tail, the pair, the rolled loop, the PDL launch mode -- is a compile-time axis of one kernel body and bitwise with the pick.
- **PDL launch knob**: both entries take `pdl` / `pdl_release` (programmatic dependent launch), appended, default off. Under `pdl=True` the kernel waits for its predecessor (`griddepcontrol.wait`) only right before it reads the QKVZ projection's rows and the normed hidden -- the slot, the parameters, the BA weight rows, the state slab and the conv operands load ahead of the wait -- and with `pdl_release` (following `pdl` unless given) releases its successor at entry so the out projection's prologue overlaps this kernel. The caller owes the obligation stated in the config docstrings: the launch's immediate predecessor must not write this layer's state, conv state or slot indices. PDL and plain are two compiled kernels (the knob is part of the compile key).
- Numerics reproduce FlashInfer's built-in `frost` backend byte for byte, including the gated norm's sum-of-squares association, which follows that backend's CTAs-per-head policy per request count.

## API

Direct-call entries (the kernel-level surface, with the FlashInfer block's argument contract; not graph engines):

```python
from cudnn.linear_attention.frost import GdnDecodeFused, GdnVerifyFused  # also lazily: cudnn.GdnDecodeFused / cudnn.GdnVerifyFused

decode = GdnDecodeFused(device, eps, cfg=None, debug=False, pdl=None, pdl_release=None)
qout = decode(rows, x, cs, cw, al, dt, state, idx, z, w, scale, hidden, baw)  # fp8 [rows, 48, 128]; decode.outputs(rows): qout, out (bf16), counts

verify = GdnVerifyFused(device, eps, cfg=None, debug=False, pdl=None, pdl_release=None)
out = verify(qkv, z, hidden, ba_weight, A_log, dt_bias, ssm_state, state_indices, cu_seqlens, num_accepted_tokens,
             norm_weight, out_scale, conv_state, conv_weight, out=None, out_bf16=None)  # the fp8 output; out_bf16 receives y before quantization
```

- `compile(...)` once per plan-time key (rows / step shape, the strides the kernel is specialized on, the parameter dtypes where they vary, the config, eps); `__call__` launches on torch's current stream. Every per-layer tensor is a launch argument, so one compiled kernel serves every layer and CUDA-graph replay. Entry-owned work buffers (`qout` / `out` / `counts`) are allocated once per shape at the first compile or call, outside any capture; the debug dumps exist only under `debug=True` (their kernel slots are compiled out otherwise).
- Validation: `check_binding` (dtype, device, shape, stride, 16-byte alignment, the step shape) runs at compile time **and again before every launch** -- a compiled CuTe DSL entry accepts a tensor of another dtype or footprint silently, so the host is a launch's only guard; `check_support` adds the architecture gate. Declines are typed and name the operand (`TypeError` / `ValueError` / `NotImplementedError`); more than 65535 requests per call (one grid row each, CUDA's grid-Y limit) is a typed decline, not a launch error.
- Gates (python/cudnn/AGENTS.md Rule 7): the kernels' own DSL floor is `nvidia-cutlass-dsl >= 4.8.0` (`DSL_FLOOR`), checked through the one parser in `cudnn.frost.buffers` -- `cutedsl_too_old(version, floor=...)` / `cutedsl_requirement_error(what, floor=...)` gain an appended `floor` parameter whose default is the library's `CUTEDSL_MIN_VERSION`, so existing callers are unchanged. The decline names the installed version. The DSL is imported inside `compile()` after the version and target gates; a host without it still constructs the entries and runs their declines. Device: compute capability 10.x (`cc_supported`), the DSL's target gate deciding per part; validated on cc 10.0.
- Device readings, never constants: the SM count (the pick), the shared memory per SM and the per-CTA opt-in maximum (the occupancy pad and the verify step's tokens budget) are read from the device at construction.

FlashInfer backend (`cudnn.linear_attention.frost.flashinfer_gdn_backend`):

```python
import cudnn.linear_attention.frost.flashinfer_gdn_backend  # the import registers "frost_fe"; register_frost_fe(replace=False) is the explicit entry
from flashinfer.qwen_3_5_gdn_block import qwen_3_5_gdn_block_decode, qwen_3_5_gdn_block_support, qwen_3_5_gdn_block_verify

sup = qwen_3_5_gdn_block_support(device, geometry, "decode", "frost_fe")
out = qwen_3_5_gdn_block_decode(..., geometry=geometry, backend="frost_fe")
sup = qwen_3_5_gdn_block_support(device, geometry, "verify", "frost_fe", requests=4, tokens_per_request=6)
out = qwen_3_5_gdn_block_verify(..., geometry=geometry, backend="frost_fe")
```

```bash
python benchmarks/bench_qwen_3_5_gdn_block.py --register cudnn.linear_attention.frost.flashinfer_gdn_backend --backends frost frost_fe
```

- `support` answers with FlashInfer's typed decline kinds and imports no kernel: `form` (decode / verify), `geometry` (naming the fields that differ from d_model 5120 / 48 V heads / 16 K heads / head dims 128 / conv kernel 4), `device` (cc 10.x), `dsl` (the installed version named), `shape` (up to 65535 rows or requests; verify `tokens_per_request` from 2 up to the picked form's shared-memory budget on the device -- on cc 10.0: 35, 8 and 45 tokens for the pair, one-CTA-per-SM and two-CTAs-per-SM forms).
- `build` returns the runners. `prepare` compiles for the binding's strides once (the entries' typed declines propagate: decode parameter dtypes other than `A_log` fp32 and `dt_bias` / `norm_weight` bf16, or a dim-first verify conv pool, are a `NotImplementedError` naming them, before any device work); `run` launches on the current stream into the caller's FP8 `out` (and bf16 `out_bf16` when given) and refuses a binding that no eager run compiled under CUDA-graph capture (`RuntimeError`), per the block's contract. Compiled kernels are shared by every plan of one form, device and norm epsilon.
- FlashInfer floor: the block's backend registry, on FlashInfer main at or after PR #8131 (2026-10-31). No tagged FlashInfer release carried it when this was written, and FlashInfer marks the block experimental (it may change or be removed without deprecation). Importing the module without the registry raises `ImportError` naming the requirement.
- Import boundary: nothing here is reached from `import cudnn`. `cudnn.GdnDecodeFused` / `cudnn.GdnVerifyFused` are lazy entries with the usual install hint, and the FlashInfer registration happens only on the explicit import of the backend module.

## Results

One GPU class: **GB200 (1200 W, 152 SMs), SM clock locked at 1830 MHz and observed in every cell, one exclusive GPU.** Measured in situ inside a serving step of a Qwen 3.5-architecture dense 27B NVFP4 path at batch 1: CUPTI kernel-duration medians (torch.profiler traces) over the 720 decode / 240 verify launches of one profiled 16-token greedy request per arm, the same launch mode on both sides (the decode kernels plain-launched; the verify kernels as PDL secondaries, the FlashInfer frost verify kernel's own mode and this PR's `pdl=True`). Speed-up = `baseline / new - 1`, positive = faster.

| step | FlashInfer `frost` backend | this PR (`frost_fe`) | speed-up |
|---|---|---|---|
| GDN decode step, 1 request | 8.58 us | 4.90 us | +75.1 % |
| GDN MTP verify step, T = 6 (5 drafts), 1 request | 15.01 us | 12.77 us | +17.5 % |

The arm that swaps only the GDN kernels (everything else as on the `frost` path) read 4.93 / 12.93 us (+74.0 % / +16.1 %); its per-GDN-layer period (launch start to launch start of consecutive GDN layers) moved 63.71 -> 59.74 us (decode) and 69.17 -> 66.94 us (verify). The pick thresholds themselves come from cold-instruction-cache A/B measurements on 148-SM SM100 parts; only the GB200 run is quoted here, one class per table.

Outputs are bitwise identical to the `frost` backend: on every saved reference set with that backend's recorded outputs (14 verify sets; fp8 output, bf16 output, every fp32 state slot, the conv pool), on FlashInfer's own reference cases and benchmark input sets (`test_flashinfer_gdn_backend.py`), and in serving (identical greedy tokens over 6 prompts x 128 tokens, identical acceptance counters).

End to end on that path (3 interleaved rounds, acceptance-length gate): the time per output token at batch 1 went 1.323 -> 1.243 ms (+6.4 %) with MTP (5 drafts) and 4.296 -> 4.019 ms (+6.9 %) without, against the same path on the FlashInfer frost backend kernels. Those two figures are the kernels plus the PDL launch mode plus GEMM tactic changes made in the same path; the GEMM part is not this PR. The kernels' own share, read in the same run against the same-snapshot control (the frost kernels on the identical software snapshot, within 0.1 % of the frost arm): +2.0 % with MTP (verify kernel on the PDL launch path; 1.298 ms) and +4.6 % without (decode kernel, plain launch; 4.106 ms). Launching the decode kernel with PDL as well adds +1.5 % at batch 1; the forms ship with PDL off.

## Follow-ups

1. **One FE graph-API form (Rule 9).** The entries are direct-call kernels behind FlashInfer's backend registry and the cudnn-level names. A graph-API form with the FE Python graph contract (prepare, bind, execute, capture / replay) is the next step, so callers reach the fused steps through the one FE contract instead of a kernel-specific call signature.
2. **Larger request counts for the verify step.** Past `requests x 48 <= SMs` the pick is the streamed two-CTAs-per-SM form, which sits at the HBM floor; in the same serving path at MTP (5 drafts) with 8 / 16 concurrent requests the kernels-only arm trailed the FlashInfer frost backend by 3.5-5.8 % per output token. An 8-or-more-requests verify form (and a lower-register three-CTAs-per-SM decode form for 8 or more rows) is the next kernel item.
3. **Other parts and geometries.** cc 10.3 is admitted by the device-reading rule but has not run; parts without a 228 KB shared-memory budget or without thread-block clusters need a re-derived form. The kernels serve the dense-27B tensor-parallel-rank-1 geometry only; other head counts are typed declines.
4. **PDL defaults.** The forms keep PDL off. The same-path A/B says PDL on the verify launch is worth +4.0 % and on the decode launch +1.5 % at batch 1, but FlashInfer's plan spec has no launch-mode knob, so a backend-side default (with the predecessor obligation) is a discussion with FlashInfer.
5. **CI coverage.** The device cells need an SM100 GPU; the backend module's cells additionally need FlashInfer main (after PR #8131) and, for FlashInfer's own tests, its source tree next to the installed package. Without them the backend module skips at collection and the device cells skip.
