## Summary

- `_check_block_scale_geometry` (SM120 tree) now raises `NotImplementedError` for a block-scale tile whose K-major operand spans more than 256 rows: `cta_tile_m > 256` with a K-major A, or `cta_tile_n > 256` with a K-major B (kernel coordinates). The SM120 block-scale templates load such an operand as one `[cta_k, cta_tile_m | cta_tile_n]` TMA box per stage, and `cuTensorMapEncodeTiled` caps each box dimension at 256 (`_TMA_BOX_DIM_MAX`).
- The rule does not apply to MN-major operands, which are loaded in 128-element swizzle-group boxes, or to a GATHER token, which is loaded one `[cta_k, 1]` box per routed row. Those keep their wide tiles.
- The function runs in `_precheck_block_scale`, `_precheck_moe_block_scale` and the block-scale renderer, so the check covers all three affected templates: `sm120_block_scale_matmul.py`, `sm120_moe_grouped_block_scale_matmul_fwd.py` and `sm120_moe_grouped_block_scale_matmul_fwd_swap_ab.py`.
- New tests: two gate tests (dense; MoE in both orientations, including the MN-major and GATHER cases that stay accepted) and two SM120 route tests (dense; MoE fwd and swap-AB). The route tests check that `jit_from_cudnn_graph` and a replayed FROST knob record each decline before a kernel is compiled, with one test case per route.

## Why

Found in an audit of the SM120 Frost kernel templates (finding B22).

Reproducer (develop 24a8cd43, RTX PRO 6000, SM120): dense MXFP8 block-scale matmul with A `[1, 512, 256]` FP8 E4M3 K-major, B `[1, 256, 128]` FP8 E4M3 K-major, E8M0 scales in F8_128x4 at block 32 and FP16 output, built with `jit_from_cudnn_graph(g, config=by_name("CONFIG_sm120_512x16x128_16x16x32_cluster1x1_warps8x1"))`.

- Observed: `probe_chain` accepts the config, the kernel compiles, and the first execute aborts the process with `CUDA Dialect Assertion failed on CUDA error: cudaErrorInvalidValue - invalid argument` (SIGABRT). There is no exception, so the engine cannot decline or fall back.
- Expected: a decline before compilation.

The same abort happens for:

- NVFP4 with the 512x16 tile.
- A K-major B (`CONFIG_sm120_32x384x128_16x16x32_cluster1x1_warps1x8`, MXFP8, M=64, N=384).
- 384-row tiles.
- The MoE fwd template (token tile 512, weight tile 384) and the MoE swap-AB template (weight tile 512, token tile 384).
- The public graph route. A FROST knob record naming the 512x16 config is replayed with `create_execution_plan(engine_id, knobs)`. It passes `check_support()` and `build_plans()`, and `execute_plan_at_index` aborts.

Cause: the non-block-scale paths check the box limit in `_check_dtype_config_compat` (`sm120/compiler.py:1313`). The block-scale paths instead call `validate_block_scale_config_sm120` (`tile_config.py:983`): `KernelTemplate._config_reject` at `kernel_registry.py:388`, and `_precheck_block_scale` / `_precheck_moe_block_scale` through `_check_block_scale_geometry`. That function only requires a CTA extent that is a multiple or a divisor of 128 (`:987`), so 384 and 512 pass. The templates then encode `box_dims=[cta_tile_mnk[2], cta_tile_mnk[0] | cta_tile_mnk[1], 1]` for K-major operands:

- dense `sm120_block_scale_matmul.py:843` and `:899`
- MoE `sm120_moe_grouped_block_scale_matmul_fwd.py:1108` and `:1186`
- swap-AB `sm120_moe_grouped_block_scale_matmul_fwd_swap_ab.py:1122` and `:1160`

Only explicit configs reach this: `by_name` builds a config from any well-formed name, and a hand-made knob record replays one. The automatic planner caps block-scale `cta_tile_n` at 128. On these 99 KB parts, the only kb=128 catalog tiles with an extent above 256 (32x320, 64x288, 64x320) fail the multiple-or-divisor-of-128 rule.

Why this fix:

- Declining is the conservative option. The alternative is to split a K-major operand into boxes of at most 256 rows, as `sm100_block_scale_matmul.py` and the two SM100 MoE block-scale templates do for A with `_a_tma_box_m`. That would change all three templates and their transaction byte counts.
- The check belongs in `_check_block_scale_geometry` because that function sees the operand layout and the MoE mode, and it runs on every build path (both prechecks and the renderer).
- A config-only rule in the shared `validate_block_scale_config_sm120` cannot tell the operand layouts apart. It would decline MN-major and GATHER tiles that work today. Checked on the GPU with the develop code and with this change, all four match the reference:
  - MXFP8 dense with an M-major A and a 384x16 tile
  - MXFP8 dense with an N-major B and a 32x384 tile
  - MoE GATHER token with a 384x16 tile (fwd)
  - MoE GATHER token with a 32x384 tile (swap-AB)

Reviewer note: `KernelTemplate.accepts()` (shared `kernel_registry.py`) still applies only the config-level rule to block-scale templates. The block-scale branch of its `_config_reject` (`kernel_registry.py:381-390`) checks the tile only through `validate_block_scale_config`, which for an SM120 config is `validate_block_scale_config_sm120`. So `accepts()` still admits such a tile: on this branch it returns `None` for the 512x16 and 32x384 tiles on a K-major dense chain and on the MoE fwd and swap-AB chains, while `_precheck_block_scale` and `_precheck_moe_block_scale` raise the new `NotImplementedError`. No build path relies on `accepts()` alone. For the SM120 block-scale templates it is called only by the catalog enumeration (`candidate_configs`), by `_check_registry_funnel` after this check, and by tests:

- Every build path runs the precheck, which calls this check before the registry funnel, and then the renderer. No plan can be built for such a tile.
- The catalog enumeration only walks the catalog. Over all 479 SM120 catalog configs and seven chain variants (dense K-major NVFP4 and MXFP8, dense MN-major MXFP8, MoE fwd and swap-AB, GATHER fwd and swap-AB), the check accepts the same 240 pairs before and after this change, so the enumeration lists no tile that this check declines.

Leaving `accepts()` as it is keeps this change inside `sm120/`. A later PR could add the same layout-aware rule to `Sm120KernelTemplate._extra_reject` in the shared `kernel_registry.py`, so that `accepts()` and the build paths agree.

AGENTS.md exception: root `AGENTS.md` § Reviewing a PR asks for a new, checkable trap to land in the relevant `AGENTS.md` in the same PR. This fix rests on one that no `AGENTS.md` covers yet. This PR does not add it, because this series keeps each fix inside `python/cudnn/gemm/frost/sm120/` and its tests. Proposed follow-up note for `python/cudnn/AGENTS.md`:

> A CuTe DSL host stub that builds a TMA descriptor with `cutlass.experimental.cuda.tensor_map.create_tensor_map_tiled` encodes it at launch and checks `cuTensorMapEncodeTiled` with `cuda.result.assert_success` (`tensor_map.py:1074` in nvidia-cutlass-dsl 4.7.1). A refused descriptor, such as one with a box dimension above 256, aborts the process ("CUDA Dialect Assertion failed on CUDA error", SIGABRT) instead of raising, so decline every descriptor limit at plan time. Test such a decline with a tripwire on the compile step (monkeypatch `_import_kernel` to raise), so that a RED run fails the test instead of killing the pytest session.

## API and compatibility impact

- Newly declined: explicit SM120 block-scale configs whose K-major operand has a CTA extent above 256, for the dense, MoE and MoE swap-AB templates. Examples: `CONFIG_sm120_512x16x128_16x16x32_cluster1x1_warps8x1`, `CONFIG_sm120_384x16x128_16x16x32_cluster1x1_warps8x1`, `CONFIG_sm120_32x384x128_16x16x32_cluster1x1_warps1x8`. `jit_from_cudnn_graph` raises `NotImplementedError`. A replayed knob record still passes `check_support()`, which probes the graph and not the knob, and `build_plans()` declines the plan:
  - with that plan selected (`select_plan`), `build_plans()` raises `NotImplementedError: frost_gemm: block-scale config ... exceeds the TMA box_dim ceiling of 256 ...`;
  - without a selection, it moves on to the next plan in the list, and if none builds, it raises `cudnnGraphNotSupportedError: no plan in the list could be built`, which lists the same reason.

  Before this change these configs aborted the process on the first execute, so no working configuration is removed.
- No change to automatically selected plans, catalog configs, MN-major operands, GATHER tokens, or numerics.
- SM100 tree: not affected, no follow-up needed.
  - `sm100_block_scale_matmul.py` and the two SM100 MoE block-scale templates split a K-major A into boxes of at most 256 rows (`_a_tma_box_m`, `sm100/compiler.py:1997-2000`). SM100 configs cap `mma_tile_n` at 256 (`_MMA_TILE_N_MAX`, `tile_config.py:331`, checked at `:347`), so their B boxes stay within the limit. `CONFIG_sm100_128x384x128_...` is refused when the config is built, and `CONFIG_sm100_512x128x128_...` is loaded in 256-row A boxes.
  - `sm103_block_scale_matmul.py` loads A and B as one box each (`:1555`, `:1593`), but `ConfigSm103` caps `cta_tile_m` at 128 (`MMA_SIZE_M_MAX = 1` with `mma_tile_m` in (64, 128), `tile_config.py:397` and `:330`) and `cta_tile_n` at 256 (`:331`). A 256-row and a 384-column SM103 tile are both refused when the config is built.
