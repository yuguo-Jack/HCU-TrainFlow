# gemm(frost sm100): decline is_negative_scale on signed block-scale factors

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2197) · state: open · merged: False

## Original PR description

## Problem

#2015 (B07) declined this on SM120. The SM100 tree drops the attribute the same way. The shared analyzer records `is_negative_scale` on each `block_scale_dequantize` op, but no chain field or gate reads it, and the tcgen05 block-scale MMA takes every scale as an unsigned `.ue4m3` / `.ue8m0` operand.

Measured on a B300 (cc 10.3): an NVFP4 GEMM (M = N = 256, K = 512, E4M3 F8_128x4 scales, `is_negative_scale=True` on both dequantize nodes) planned with `CONFIG_sm100_128x128x128_128x128x32_cluster2x1_2ctamma`. Setting the sign bit of every other SFA byte left the output **bit-identical** (max |diff| = 0). A block whose scale is `-|s|` contributes `+|s|`, and nothing reports it.

## Change

- `sm100/compiler.py`: the SM120 tree's `_check_block_scale_sign`, run from a new `_analyze_graph`. That function does one analyzer pass (`_state_from_graph` + `_analyze_state`, as `analyze_with_binding` does), then the check. `probe_supported` and `jit_from_cudnn_graph` now use it, so `FrostGemmEngine.check_support`, the heuristics and the direct JIT all decline the graph.
- Sign-free scale types (`fp8_e8m0`, `fp8_e5m3`) cannot hold a negative value, so flagged graphs on them keep their plans.
- Tests, mirroring the SM120 ones:
  - `test_sm100_analyze_graph_declines_signed_negative_scale` (host-only).
  - `test_sm100_block_scale_declines_signed_negative_scale` (dense, engine and JIT).
  - `test_sm100_moe_block_scale_declines_signed_negative_scale` (MoE, normal and swap-AB).

## Tests

On a B300 (cc 10.3):
- The three new tests on develop: 3 failed (the graphs plan). With this change: 4 passed, 2 skipped (the SM120 twins).
- `test_block_scale_matmul.py`, `-m "L0 or L1"`: 452 passed, 193 skipped.
- `pre-commit` on the touched files passes.
