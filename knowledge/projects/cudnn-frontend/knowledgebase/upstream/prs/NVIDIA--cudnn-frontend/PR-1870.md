## Summary

**Draft for the FROST GEMM owner's review. Please do not merge yet.**

This PR adds a low-latency (decode, M ≤ 32) path for block-scaled GEMM (NVFP4 / MXFP8 / MXFP4) on the sm100 FROST template, and three kernel fixes that came out of profiling it (two in the mainloop, one in the prologue).

1. **Block-scale N tiles below 128.** The SF 128x4 swizzle stores the scale for row `32c + l` in TMEM column `c`, lane `l`. A narrow tile therefore reads its rows out of the shared 128-row SFB block:
   - **64-wide tile, any N:** the MMA's `scale_b` address moves by 0 or 2 TMEM columns. An odd column shift faults `tcgen05.mma`, so 64 is the narrowest tile that works for every N.
   - **8 / 16 / 32-wide tiles, kernel N ≤ 32:** the utccp SMEM source moves by whole rows and the TMEM address stays put.
   - These tiles are limited to 1-CTA MMA with a 128-row CTA tile (`cta_tile_m == mma_tile_m == 128`), cluster N 1, and non-MoE graphs. The registry gate declines a narrow N for MoE chains.
   - SFB TMA bytes are now separate from the SMEM ring stride. A narrow tile carries one 512 B atom of slack, and sizing `expect_tx` from the padded stride hangs the kernel.
2. **Small-M plan rule.** It applies to a single block-scale GEMM with ≤ 32 rows and no quant / reduction epilogue. It plans swap-AB (tokens on the MMA N axis) and splits K for one wave: the largest power of two with `weight_tiles × slices ≤ SMs`.
   - When the graph's shapes are fixed, it uses a narrow token tile.
   - Under override-shape graphs it uses the 64-wide tile, and only up to 48 weight tiles; past that the 64-wide tile is slower than the default plan.
   - These graphs sit outside every fitted cost profile, for three reasons: M is below `mn_bounds[0]`, N is often above `mn_bounds[1]`, and FlashInfer's scalar alpha MUL is outside `b200_block_f4`'s eligibility gate. So until now they always took the default 2-CTA 128x128 plan.
3. **In-cluster split-K (N tile ≤ 32, S = 2 / 4 / 8).** Such a plan runs as one kernel on a `(1, 1, S)` cluster instead of the main kernel + workspace + `splitk_reduce`:
   - Each peer rank stages its FP32 tile in its own SMEM and bulk-copies it (`cp.async.bulk` SMEM → peer SMEM, `complete_tx`) into rank 0's mailbox. Rank 0 adds the slices in order and runs the graph's normal epilogue. The output is **bitwise identical** to the workspace path.
   - The plan keeps `SPLIT_K_SLC`; only the rendered kernel changes, so there is no new knob. `CUDNN_FROST_DISABLE_CLUSTER_K=1` restores the workspace path.
   - The gate admits N tiles ≤ 32 with a mailbox ≤ 48 KiB (so 32-wide tiles stop at S = 4).
   - The owner releases each peer's mailbox with a remote arrive at **`.release.cta`** scope, the form CUTLASS uses for a remote `consumer_release` before a TMA refill. It orders the owner's mailbox reads before the peer's next bulk write. A cluster-scope release lowers to `MEMBAR.ALL.GPU` per peer and cost ~1.2–1.7 µs per call (M=8 2560×8192: 10.38 vs 8.79 µs). An earlier revision used a relaxed arrive, which is as fast but does not order the reads (thanks to @yanqinz2 for flagging it).
   - The cluster kernel leaves the PDL trigger to grid exit, as split-K already does. An early trigger let the next launch's clusters take, through CLC, the clusters still waiting for SMs and run them back to back.
4. **One TMEM column set per SF word (all sm100 block-scale tiles, when it fits).** The MMA warp used to `tcgen05.cp` every SF word of a K-tile into the same TMEM columns, interleaved copy → MMA → copy → MMA, so each copy waited for the previous MMA to read its scales and the tensor pipe ran serially (a fixed per-K-tile cadence, with the TMA producer throttled by empty barriers). The compiler now renders `sf_word_stride_cols`: when the TMEM left after the accumulator stages holds every word of a K-tile, each word gets its own columns, all copies go first, then the MMAs issue back to back. Otherwise the stride is 0 and the layout is unchanged (256-wide N tiles, overlapped accumulators, sm103, MoE).
5. **Tile-swizzle width resolved on the host.** Every warp used to run `_auto_swizzle_w`'s 64-bit division chain in the prologue before its first TMA / MMA / epilogue step. The width depends only on the problem shape, so `_host` computes it and passes it as a kernel argument, and `l2_swizzle_tile` skips its two divisions when the width is 1 at runtime (every decode plan). The helper change reaches the other sm100 templates too; there the width is still computed in the kernel.
6. **Safety.**
   - Override-shape or dynamic graphs never get a narrow tile. A replayed narrow knob record on such a graph declines at plan time.
   - A narrow-tile plan whose call has kernel N > 32 refuses with a named error instead of faulting. The check lives in both the per-call guard and `explain`.
   - A cluster split-K plan refuses a call with fewer K tiles than slices (an empty slice would contribute an uninitialized accumulator).

## Why

cuDNN sits in FlashInfer's auto dispatch: `mm_fp4(backend="auto")` tries cuDNN first on SM100 / SM107, and cuDNN is also a backend of `mm_bf16` / `mm_fp8` / `bmm_fp8` / `mm_mxfp8`. Measured through FlashInfer's own benchmark (`flashinfer_benchmark.py`) on B200, cuDNN 9.27, cuDNN time / best other FlashInfer backend, geomean over real Llama-70B / Qwen3 shapes (5 shapes untuned for the first three rows; 14 shapes with FlashInfer autotuning for NVFP4):

| GEMM | M ≤ 8 | M = 32 | M ≥ 128 |
|---|---:|---:|---:|
| FP8 per-tensor (`mm_fp8`, `bmm_fp8`) | 1.00–1.05 | 1.01 | 1.00 |
| BF16 | 1.05–1.23 | 1.00 | 1.00 |
| MXFP8 | 1.20 | 1.19 | 0.86–0.92 |
| NVFP4 | 1.44–1.45 | 1.33 | 1.08–1.12 |

Large-M and non-block-scaled GEMMs are in good shape. The headroom is in block-scaled GEMM at decode row counts, where the problem is weight streaming at low occupancy: the backend runs one 256x128 2-SM tile (no split-K, no swap), and FROST's default plan was one 2-CTA 128x128 tile. This PR gives FROST a plan and kernel shaped for that regime: tokens on the narrow MMA N axis, K split across a one-wave cluster, the reduction kept on chip.

## How the two mainloop inefficiencies were found

A K sweep at fixed grid (M=8, 2560×8192, `(1,1,4)` cluster, 80 CTAs) split the kernel time into a fixed part and a per-K-tile part; the per-K-tile cost (0.37 µs) was well above what HBM streaming at that occupancy needs (another SM100 kernel on the same grid ran 0.28 µs). IKET in-kernel traces and the SASS then showed:
- the per-K-tile part: SF words sharing TMEM columns (item 4); the MMA warp ran at a fixed cadence with the producer throttled, i.e. the consumer set the pace rather than memory;
- most of the fixed part: the cluster-scope release `k_free` arrive (item 3).

Ruled out along the way: TMA L2 promotion (none vs 256 B, no change), tensormap prefetch (already present), stage count (9 vs ~10), CTA launch skew (≤ 300 ns on both).

## Not in this PR / open questions for review

- **Prologue, what is left.** After item 5 the TMA warp spends ~100 ns in `setmaxnreg`, ~160 ns on its first empty-wait + `expect_tx`, and ~130 ns in the cluster barrier. Serial mbarrier init by one warp measured ~220 ns; a lane-parallel init was slower (~1.4 µs) and spreading it over four warps saved 30–60 ns, so neither is in this PR.
- **Weight loads before `griddepcontrol.wait`** (tried, not in this PR). Issuing the first ring stages of A + SFA before the PDL wait shortens a [predecessor → GEMM] chain by 0.6–2.6 µs when the predecessor triggers `launch_dependents` early, but FlashInfer's rmsnorm / quantize trigger at their end (overlap window ~0.4 µs), and standalone it costs 0.6–1.4 µs (the preloaded A boxes queue ahead of the first B box). It would need fewer preloaded stages or a producer-aware switch.
- **Tried and dropped:** a rolling TMA L2 prefetch of the weight stream (+9–26% on the large shapes; it shares the TMA issue path with the real loads), and an `evict_first` hint on the weights (neutral once the L2 flush itself is clean, see next item).
- **Benchmark caveat.** Flushing L2 with `zero_()` leaves it full of dirty lines; on the larger shapes that adds 2–4 µs to the measured kernel (14336×8192 20.3 → 16.8 µs with a read-only flush). The tables above all use the `zero_()` flush for every column, so the comparison is consistent, but absolute numbers on the large shapes are pessimistic.
- **The in-cluster reduction is not a knob.** I lowered `SPLIT_K_SLC` to a cluster instead of adding `TILE_CGA_K`, because the two paths are bitwise equal. If you prefer an explicit knob, the kernel side is unchanged; only the gate moves into the config.
- **Per-thread `st.async` at a 64-wide tile.** My first cluster-K version sent the tile with one 16-byte `st.async` per thread per chunk; at a 64-wide tile that cost ~10 µs on the long-K shape in this template. Staging in SMEM plus one bulk copy does not.
- **PDL early trigger and CLC.** FROST's dense (split 1) path also fires `launch_dependents` early, and a grid larger than the idle SM count can have its waiting clusters taken by the next launch. Not measured on the dense path yet.
- **No refit of the cost profiles.** The rule bypasses them for ≤ 32 rows; the split pick is the one-wave heuristic above.
- **Hardware coverage.** Measured on a CC 10.0 dev board whose device name is not "NVIDIA B200", so the fitted B200 profiles never applied in these sweeps (the rule does not depend on them). The `word_atoms > 1` (SM107 K64) SF path with the new word stride compiles but was not run on hardware; production B200 and SM103 / SM107 were not measured.
- **sm103 (K=48 B) and sm120 templates are unchanged.** The narrow tile and the word stride are sm100-pipeline only.

## API and compatibility impact

- **New:** `plan_config` / `plan_configs` / `select_strategy` / `select_strategies` take `narrow_n_ok` (keyword, default `False`), and both families gain `_graph_shapes_fixed`.
- **Behavior change:** block-scale GEMMs with ≤ 32 rows now plan swap-AB + split-K instead of the default tile. Like the rest of `frost_gemm`, this only reaches users who set `CUDNN_FRONTEND_ENABLE_FROST_ENGINES=1`.
- The SM120 compiler accepts the new parameter and does not use it.

**Follow-up design: in-cluster split-K reduction.** Not in this PR; this needs the GEMM owner's call before I build it.

The biggest remaining cost at small M is the split-K reduction. nsys at M = 8, 2560×8192, warm L2: the main kernel takes 7.36 µs, plus a separate `splitk_reduce` kernel of 2.54 µs and its launch. For reference, FlashInfer's `cute-dsl` kernel does the whole thing in one 6.75 µs kernel.

FlashInfer's `dense_blockscaled_gemm_sm100_splitk.py` (the protocol comes from DKG's FP8 split-K tutorial) shows a nice way to avoid the second kernel:
- It runs a physical `(1, 1, split)` cluster per output tile.
- Peers `st.async` their FP32 accumulator fragments into an owner CTA's SMEM mailbox and complete the owner's mbarrier tx.
- The owner sums them and runs the normal epilogue. There is no workspace and no second kernel.

Proposed shape for FROST (sm100 block-scale, the narrow tiles only):

1. **No new knob.** Keep `SPLIT_K_SLC`. The compiler realizes `split ∈ {2, 4}` on a narrow 1-CTA tile as a z-cluster instead of workspace + `splitk_reduce`. If the owner adds slices in the same order the reduce kernel does (p0 + p1 + p2 + p3), the two are bitwise equal, so it stays a performance-only knob (AGENTS knob rule). The alternative is a frontend-band `TILE_CGA_K` knob and a `cga_size_k` field on the config name. That is more explicit, but it is a new public vocabulary entry. **Which do you prefer?**
2. **Rank decomposition.** `n_rank = cta_rank_in_cluster >> m_shift` assumes there is no z; it becomes `(rank >> m_shift) & (cluster_n - 1)`, with `k_rank = rank >> (m_shift + n_shift)`. This is pinned by `test_mixed_cga_uses_host_constant_masks_and_shifts_at_every_use_site`, so that test would change with it.
3. **CLC.** The response carries the cluster's base z, so each CTA uses `tile_l = l_idx + k_rank`. The existing `tile_l // split`, `tile_l % split` K-range code then works unchanged.
4. **Epilogue codegen.** The kernel keeps `split_k_slices` for its K ranges but renders the non-split epilogue (alpha / cast / store, no partial store). Only `k_rank == 0` stores; the others send their tile to the owner.
5. **Persistence.** The template is persistent (CLC), so a mailbox can be reused across tiles. The owner arrives remotely on each peer's `mailbox_free` mbarrier after consuming, and peers wait on it (per-tile parity) before their next send. Mailbox size is `(split - 1) × 128 × tile_n × 4 B`, at most 48 KiB at split 4 / tile 32. It comes out of the AB-stage budget.

Expected effect: at split 4 (2560×8192, M = 8) the 2.54 µs reduce kernel and its launch go away. The main kernel itself would still need separate main-loop work.

**Two more commits: two FROST inefficiencies found by profiling next to FlashInfer's cute-dsl kernel.** Still draft, not for merge until the GEMM owner has looked.

FlashInfer's cute-dsl `mm_fp4` at M<=32 uses the same decomposition as this PR (swap-AB 128xN8/16/32 tile, (1,1,S) cluster split-K with DSMEM reduction), which made it a convenient reference: with identical grid and cluster (M=8 N=2560 S=4; M=8 N=5120 S=2), any difference has to come from inside the CTA. A K sweep showed FROST with ~1.3-1.5 us more fixed cost and 0.37 vs 0.28 us per k-tile. IKET in-kernel traces and SASS located both parts:

- `047284cd2`: **SF words reused one set of TMEM columns.** Every SFA/SFB `tcgen05.cp` targeted the same columns, interleaved cp -> mma -> cp -> mma, so each copy waited for the previous word's MMA to read its scales. The MMA warp ran at a fixed cadence with the TMA producer throttled by empty barriers, i.e. consumer-bound. The compiler now renders `sf_word_stride_cols`: when the TMEM left after the accumulator stages holds every word of a k-tile, each word gets its own columns, all copies go first, then the MMAs issue back to back. Otherwise the stride is 0 and the old layout is unchanged (256-wide N tiles, sm103, MoE). This also speeds up 128x128 1-CTA dense tiles by ~14%. The default large-M plan (128x256 2-CTA) has no room, so it is unchanged.
