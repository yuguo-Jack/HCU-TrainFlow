## Affected area

FE OSS kernels or CuTeDSL

## Summary

Two changes, both in the FROST linear-attention chunk kernels.

1. **Exact steep-decay path for KDA (fixes #1773).** This ports the GDN-2 design from `common/steep_decay.py`: a fast launch with a steep vote, followed by an exact twin that runs only when a tile is steep.
   - **Kernels:** all six KDA chunk kernels get it (prep, prefill, summary, recompute, bprop, bprop_summary), plus their wrappers, the engine (state snapshot and dstate scratch workspace regions) and JAX.
   - **β:** KDA's scalar β sits outside K decay and is already folded into the strict dM tile, so its corrections pass `beta_ptr=None`.
2. **A faster exact path, shared by KDA and GDN-2.** Every change except the warp-cooperative backward leaves the arithmetic bitwise unchanged; that one moves `dq`/`dg` at fp32 rounding level only (see Testing).
   - **Token factors:** the exchange keeps per-token factors `exp2(g)`, so an interval's decay is a product of factors, with no `exp2` and no prefix subtraction.
   - **Constant trip counts:** interval products and the backward corrections walk all 16 tokens and mask the rest, so loads issue ahead of the decay chain and lanes at different tokens don't diverge.
   - **Warp-cooperative backward (`d_k = 128`):** one lane owns a channel at every token, so a single steep channel used to keep that one lane busy for 16 tokens in series. `steep_grad_corrections_warp` and `steep_dk_restore_warp` now hand each steep channel's tokens to a lane each. When most of the warp is steep, it falls back to the per-lane walk.
   - **Batched dK restore:** the split-channel path (`d_k = 64`) loads each FP32 state value once for all of a lane's tokens.
   - **Real branches, not predication:** `steep_row_corrections` visits only set bits. Per-element steep work runs in zero- or one-trip loops, because ptxas predicates branch-free `if` bodies, which then issue on every mild lane. ncu showed the dgate-last FP32 scratch loads in bprop issuing on every tile.
   - **Mild tiles keep the fast schedule:** in the exact backward, compute group 2 releases the FP32 dstate, U and raw stages where the fast kernel does, and compute group 1 skips the waits that only feed the steep dU term.
   - **Row-stage barriers:** these take one elected arrival per warp after `bar.warp.sync`, in both modes, instead of every correction-writing thread arriving.

The KDA steep tests are the GDN-2 ones, parametrized over `STEEP_VARIANTS = ("gdn2", "kda")`.

## Why

Trained KDA and GDN-2 models can produce gates steeper than ~5.5 nats/token.

- **KDA on `develop`:** NaN on every layer of a trained model. One steep tile poisons the rest of its sequence, even on layers with almost no steep tiles.
- **KDA on this branch:** matches an fp64 reference at bf16 level, with relative RMS error 2.5e-3–8e-3 on `o`.
- **GDN-2:** already exact on `develop`, but its exact launch was the bottleneck. A steep layer of a trained model took 34–68 ms per fwd+bwd on `develop`, and 10–27 ms at an intermediate revision of this branch, before about half of the speedups below.

## Related issues

Fixes #1773.

## API and compatibility impact

- **API:** no public API changes.
- **KDA performance:** KDA now carries the steep vote and the empty exact launch that GDN-2 already has. On all-mild inputs that costs ~2% (742 → 757 µs at H=16, T=8192), the same overhead GDN-2 pays on `develop`.
- **KDA workspace:** grows by the state snapshot and dstate scratch regions, as GDN-2's does.

## Performance

B300, bf16, K = V = 128, in-kernel l2norm, fwd+bwd, CUDA-graph replay, H = 16, T = 8192, one sequence. Gate patterns:
- **mild:** g ∈ (−0.05, 0) nats.
- **one channel:** one channel per head at −8 nats/token.
- **real:** 4 random channels per head at −8 in a random 60% of tiles, sized to match the steep-gate rates seen in trained models.
- **dense:** every channel at −12.

| pattern | GDN-2 `develop` | GDN-2 this PR | KDA `develop` | KDA this PR |
|---|---|---|---|---|
| mild | 0.751 ms | 0.751 ms | 0.742 ms | 0.758 ms |
| one channel | 7.00 ms | 2.56 ms (2.7×) | NaN | 2.49 ms |
| real | 7.45 ms | 3.38 ms (2.2×) | NaN | 3.41 ms |
| dense | 15.46 ms | 9.27 ms (1.7×) | NaN | 8.32 ms |

At H = 96, GDN-2 with one steep channel per head goes from 51.7 to 13.6 ms (3.8×). This was measured at an earlier revision, whose outputs are bitwise identical and whose H = 16 timings are within 1%.

**Not done here.** The exact kernels are still ~50% slower than the fast ones on mild tiles; for example exact bprop_summary takes 167 µs vs 80 µs, and the profile points at the row-stage warp group. The fast-then-exact pair keeps all-mild inputs at fast speed, but on steep inputs that pair costs ~19% more than an exact-only launch would. Removing that overhead would make a single exact launch the better choice everywhere; that's left as follow-up work.

## Testing

On B300 (sm_103), at the branch state before the cleanup described below:
- **Steep tests:** `cd test/python && pytest linear_attention/test_la.py -k "steep and gdn2"` and `-k "steep and kda"` pass 140/140 each. They were also run on a build that forces the exact launch, to cover the exact kernels on mild tiles.
- **Bitwise checks:** each optimization step was compared against the previous one, on `o`, `dq`, `dk`, `dv`, `dg`, `dβ` (and `dw` for GDN-2).
  - **Coverage:** mild, single-channel, spread, spike and dense gates, at `d_k` 128 and 64, with and without in-kernel l2norm, and T = 2048 and 8192.
  - **Result:** all identical, with one exception. The warp-cooperative `d_k = 128` backward moves `dg` and `dq` at fp32 rounding level (max 7.5e-9 absolute in `dg`): the product that used to contract into the accumulate is now computed on another lane and passed over a shuffle.
- **Race check:** every synchronization change was rerun 3–5 times, with bitwise-identical results.
- **Test bug fixed:** with β = 1/25 and |k|² = 25, the KDA variant of `test_steep_fp16_inverse_range_without_normalization` projected channel 0 out, so its true `dg` was zero and the test compared against noise. It now uses β = 1/50.

The cleanup removes the measurement-only environment switches I used to benchmark (keeping the default code paths), trims comments to the kernels' convention, and applies black. The second commit changes comments and docstrings only: every file it touches parses to the same code. The cleanup has not been rerun on Blackwell. I checked it in three ways:
- **Compile:** with `CUTE_DSL_ARCH=sm_100a`, across fwd, bwd, summary and summary-bwd; prep, uncut and chain schedules; and K=64, fp16, safe-gate and initial-state variants, for both GDN-2 and KDA (36 configurations).
- **Collection:** `pytest --collect-only linear_attention/test_la.py -k steep` collects 282 tests.
- **Formatting:** pre-commit passes.

The cleanup and the full KDA / GDN-2 suite have not been rerun on GPU yet, because no Blackwell capacity is free; I'll post results here when it is.
