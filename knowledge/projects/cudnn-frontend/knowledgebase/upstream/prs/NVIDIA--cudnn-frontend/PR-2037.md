## Summary

Adds SM120 hardware tests for the split-K plans that the automatic plan picks on an RTX PRO 6000 Blackwell Server Edition but that no gemm/frost test launched, and removes a stale SM120 skip.

- `test_sm120_splitk_planned_configs` (dense, bit for bit against torch), six configs:
  - 128x128 warps4x2, S=11;
  - 128x64 warps4x2, S=10;
  - 128x64 warps4x2 swap-AB, S=19 and S=8;
  - fp8 e4m3 on 64x128 warps4x2, S=15;
  - 32x64 warps2x4, S=8.
- `test_sm120_splitk_batched_aux_and_row_sum`: B=3, a per-batch row aux `[B,M,1]`, a 3-D aux `[B,M,N]` and a per-row fp32 ADD output, on 32x64 S=16. Exact against torch.
- `test_sm120_block_scale_matmul_splitk_numerics`, three new cases:
  - nvfp4 on 128x128, S=16;
  - mxfp8 on 64x64, S=11;
  - mxfp8 on 64x64 swap-AB, S=11.
- `test_sm120_block_scale_splitk_batched_row_aux`: nvfp4, B=3, a per-batch row aux, 128x128 S=16. Exact against torch.
- `test_splitk_epilogue_fusion[row_aux]` now runs on SM120: the skip is removed.

Each new case pins its config, so a cost-model refit or a GPU with another SM count or device name does not change what runs. The pinned config is the plan's first pick for the case's shape, except the mxfp8 swap-AB case, which is the third entry of the same shortlist. The planner shape is named in a comment.

## Why

This was found in an audit of the SM120 Frost kernel templates (finding G8.6).

**Coverage gap at 24a8cd43.** On SM120, every dense split-K test runs one tile, `_SM120_SPLITK_CFG` = 128x128 warps4x2 (`test_matmul.py:3551`, `:3559-3560`), with `S in (2, 3, 8)` (`:3667`), plus S=6 and S=8 in the epilogue cases. The block-scale split tests use S=5 and S=3 (`test_block_scale_matmul.py:3517-3518`).

I recorded every SM120 split-K launch of the whole `gemm/frost` suite with a local pytest plugin that wraps the sm120 `CompiledFusedGemm` launch; the plugin is not part of this PR. On base, 22 tests launch split-K, all on 128x128 tiles, with S in {2, 3, 5, 6, 8}. None of them runs:

- **S >= 9.** `splitk_reduce_slice_groups` (`split_k_reduction_epilogue_fusion.py:20-26`) gives the shared reducer four lane groups only for S > 8. Its second shuffle step (`_splitk_group_tree`, `:42-49`) therefore ran only in the SM100 tests. S = 11, 15 and 19 also leave a three-slice tail (`:69-70`, `:90`). No gemm/frost test runs one on SM120, and none of the gemm/frost SM100 or SM103 cases that I checked does (see the SM100 note under API and compatibility impact).
- **swap-AB split-K**, or any tile other than 128x128.
- **dense fp8 split-K.**
- **batch > 1** with an aux operand or a reduction.

**What the plan picks.** On an RTX PRO 6000 Blackwell Server Edition (188 SMs) at 24a8cd43, `plan_config(analyze(graph), shapes_fixed=True)` picks all of these:

| graph | automatic plan |
|---|---|
| bf16 64x2048x7168 | 128x128 warps4x2, S=11 |
| bf16 128x1024x16384 | 128x64 warps4x2, S=10 |
| bf16 64x1024x16384 | 128x64 warps4x2 swap-AB, S=19 |
| bf16 64x2560x8192 | 128x64 warps4x2 swap-AB, S=8 |
| fp8 e4m3 64x1024x16384 | 64x128 warps4x2, S=15 |
| bf16 16x1024x16384 (below the cost model's 32-row bound) | 32x64 warps2x4, S=8 (power-of-two baseline) |
| bf16 B=3 32x128x16384, `[B,M,1]` and `[B,M,N]` aux, per-row fp32 sum | 32x64 warps2x4, S=16 (baseline) |
| nvfp4 128x1024x16384 | 128x128 warps4x2, S=16 |
| mxfp8 64x1024x16384 | 64x64 warps4x2, S=11. The swap-AB S=11 variant is the third entry of its shortlist. |
| nvfp4 B=3 128x256x8192, `[B,M,1]` aux | 128x128 warps4x2, S=16 (baseline) |

Graphs with per-row or 3-D aux or with a reduction are not eligible for the cost model (`planning.py` `_eligible_graph`), so their split comes from `_auto_split_k`.

The cost model's SM120 profiles name that exact device, and `planning.py` `profile_for` returns no profile for any other device name, so on any other SM120 GPU every graph above gets the power-of-two baseline. Planned for a different device name with the same 188 SMs and 128 MiB L2, the five dense cost-model rows become 32x64 warps2x4 with S = 2 or 4 and the mxfp8 row becomes 128x128 S=16; the other rows do not change. The tests pin their configs, so this does not change what they run.

**Stale skip.** `test_splitk_epilogue_fusion` skipped `row_aux` on SM120 because "the dense sm120 template hoists per-row aux loads before `row` is defined" (`test_matmul.py:4011-4012`, added in f87c0beb). Since 37582a75 (drain hooks), the S=1 render loads `_aux_r_pre` after `row = coord_m + row_in_cta` in both drains, and the case passes.

**Why tests only.** The kernels at 24a8cd43 are correct for every new case, so this PR adds coverage and changes no code. To show the tests close the gap, I broke the shared reducer twice in a scratch worktree:

- The four-group tree loses its second shuffle step.
- A three-slice tail loses its last slice.

Every existing SM120 split-K test still passes with either change. The new tests fail (numbers under Testing).

**Aux name.** The block-scale batched test names its aux `row_scale`, not `r`. With an aux named `r`, the SM120 block-scale template does not compile, at S=1 or S=16, because its local `r` (`sm120_block_scale_matmul.py:552`) shadows the aux view; its local `c` (`:557`) has the same problem. That defect is not split-K specific and is out of scope here.

## API and compatibility impact

None; this PR changes tests only.

- The new tests are gated with `requires_sm120`.
- The removed skip applied only on SM 12.0.
- SM100 runs are unchanged.

SM100 note: the SM100 gemm/frost tests do run the shared reducer's four-group tree, but none that I checked has a three-slice tail:

- Their explicit slice counts are at most 8, or 16 and 32; `test_matmul.py:3724` uses S in {2, 3, 4, 5, 8, 16, 32}. The SM103 split-K cases use S = 3 and 7.
- The two gemm/frost tests that let the planner choose S on SM100 get, for a B200, S = 1, 4, 26 and 12 (`test_joint_strategy_selected_config_executes`, six shapes) and S = 18 (`test_override_shape_frost[splitk]`). This is the audit's CPU replay of their planner calls, which I re-ran at 24a8cd43.
- Not checked: SM100 parts other than the B200 (`test_override_shape_frost` plans for the GPU it runs on), and suites outside gemm/frost that reach the shared reducer on SM100, such as the gated_attention_block projection GEMMs.

I did not add an SM100 case because I have no SM100 GPU to verify it on; that is left for a follow-up.
