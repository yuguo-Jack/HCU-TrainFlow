## Affected area

## Summary

Eleven `gemm/frost` planning tests fail on any GPU outside SM100–SM119. They check plan-time decisions and do not launch kernels, but two device queries answer first:

- **Swap-AB validation tests.** These are `test_moe_swap_ab_token_quant_requires_aligned_groups` (4 cases), `test_moe_swap_ab_segmented_feature_quant_requires_scale_prefix` and `test_moe_swap_ab_preserves_block_scale_tile_constraints` (2 cases). They expect a specific plan-time decline. The template's active-GPU gate rejects first with "template sm100_moe_grouped_matmul_fwd_swap_ab.py runs only on 100 <= SM < 120, but the active GPU is sm_89", so the `match=` fails. They now plan on the SM100 compiler, which a new `plan_as_sm100(monkeypatch)` in `gemm_test_utils` returns after pinning the arch probe to 100 on it and on the active family's compiler (the one the template gate reads); the other planning tests in this directory pin the arch the same way (31 `_current_arch` pins under `test/python/gemm/frost`). The SM100 compiler is named explicitly because on SM120 `cudnn.gemm.frost.compiler` is the sm120 tree.
- **`test_block_scale_sf_ring_budget` (4 cases).** It already pinned the arch and now plans on the SM100 compiler through the same helper. But rendering the 2-CTA config sizes the grid from `cudnn.frost.occupancy.max_active_clusters`, which queries the active GPU. A GPU without clusters raises "a 2-CTA cluster does not fit on cuda:0". The test checks the AB stage count, which does not depend on the cluster count, so it stubs `_grid_num_clusters`.

No product code changes.

## Why

Running the gemm suite on a non-Blackwell GPU (here an L40S, while validating other work) reported these as failures, although no kernel was involved.
