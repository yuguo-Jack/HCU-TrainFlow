## Summary

Follow-up to #1548. It handles the P2 that the Codex review raised there ([discussion](https://github.com/NVIDIA/cudnn-frontend/pull/1548#discussion_r4236344804)).

1. In layernorm training, a `MEAN` or `INV_VARIANCE` whose dims the caller did not set now takes the dims set on the other stat. Before, it took the dims inferred from `scale`, or `{N,1,...}` without a scale.
2. `MEAN` and `INV_VARIANCE` with different dims return `INVALID_VALUE` ("Layernorm MEAN and INV_VARIANCE dims differ.") from `validate()`.
3. The no-scale ambiguity check (#1548) now also accepts `MEAN` dims, not only `INV_VARIANCE` dims. Its message reads "set the MEAN or INV_VARIANCE dims".
4. The Python graph's layernorm shape inference (`_pygraph._NORM_FWD_INFER`) applies the same rule, so the dims reported after `validate()` match the C++ node.
   - The structured builder fills both stats' dims when `graph.layernorm()` runs, before the caller can set either. So the layernorm spec now names `mean` and `inv_var` as `reinfer` ports.
   - `validate()` re-infers a `reinfer` port unless the caller assigned its dims, and a stat follows its sibling only when that sibling's dims were user-assigned.
   - Without this, a stat the caller did not set kept `[2,1,1]` after `validate()` while C++ had `[2,8,1]`, so a buffer allocated from it was 8x short. This was caught in review.
   - A re-inferred port keeps a stride the caller set. Without that, padded stats such as `[16,2,1]` would build and run with a row-major layout instead of being refused. Also caught in review.

## Why

Example: scale-free training, `X = {2,8,64}`, with only `INV_VARIANCE = {2,8,1}` set.
- Before this change, `validate()` inferred `MEAN = {2,1,1}` and accepted the graph.
- `build_operation_graph()` then failed with `CUDNN_STATUS_BAD_PARAM_SHAPE_MISMATCH`. This was measured in the #1548 review on cuDNN 9.27.

Explicitly mismatched stats failed the same way. With this change both are settled at `validate()`: the first case is served and the second is refused.

## API and compatibility impact

- Graphs with a scale, and graphs whose stats dims are both unset or both set and equal, behave as before.
- A graph with one stat's dims set used to fail at `build_operation_graph()` whenever the other stat's inferred dims differed. It now gets matching dims.
- adalayernorm and rmsnorm are unchanged. rmsnorm has no `MEAN`.

[P1] Refresh inferred statistics before returning from validate()

The structured builder eagerly fills both statistics, so this helper runs before the caller can set either returned tensor's dimensions. Later `validate()` skips inference for nonempty Python dimensions and does not synchronize the dimensions inferred by C++. For a scale-free training input `[2,8,64]`, setting only `mean` to `[2,8,1]` leaves Python `inv_var.get_dim()` at `[2,1,1]` after successful validation, while its native tensor is already `[2,8,1]`; setting only `inv_var` produces the symmetric problem. A caller allocating outputs from those validated dimensions gets 2 FP32 elements instead of 16. `build_operation_graph()` subsequently changes the metadata, but both public execute paths still forward the original undersized tensor's pointer to the native launcher (confirmed by interception before launch), exposing an out-of-bounds output write on this newly accepted configuration. Recompute non-explicit statistics dimensions from the explicitly set counterpart, or synchronize validated native properties before `validate()` returns, and assert both Python shapes immediately after validation in the regression tests. This is approval-blocking because the metadata mismatch can lead to invalid memory writes.

[P2] Preserve explicitly assigned statistics strides during re-inference

The new branch also executes the unconditional `out_t.stride = _row_major_stride(...)`, even when `stride_assigned` is true.
