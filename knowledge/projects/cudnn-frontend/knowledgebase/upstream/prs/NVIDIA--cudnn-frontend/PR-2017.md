## Summary

- New `_quant_scale_plane_reject(buf)` and `_quant_scale_blob_reject(chain, outputs)` in `sm120/compiler.py`. The second applies the first to every quant-scale output whose quant uses `F8_128x4` reordering: each batch plane must be one dense byte run (the strides of the two inner axes, sorted, must form a dense chain; a permuted plane qualifies) and, when the batch extent is above 1, the batch stride must be at least the plane size so planes do not overlap.
- New class flag `_validate_quant_scale_blobs` (default `False`) and method `_check_quant_scale_blobs()` on the shared `_CompiledRuntime`. The SM120 `CompiledFusedGemm`, `CompiledMoeGemm` and `CompiledMoeBlockScaleGemm` set the flag, the same way they already opt into `_validate_runtime_quant` and `_validate_combine`.
- With the flag set, the launchers run the check before any memset or launch:
  - dense `lowered`: checks only the `F8_128x4` scale slots found when the plan was lowered, with `_quant_scale_plane_reject`, and refuses the call (deferral `"quant scale blob"`); `explain()` then raises the `ValueError`;
  - plain MoE `_launch_single` and `_call_multi_gemm`;
  - block-scale MoE `_launch_single` and `_call_multi_gemm`, after the existing grouped-row check;
  - swap-AB MoE (`_launch_moe_swap_ab` in `sm120/compiler.py`), after its existing checks. Those already refused a scale view that is not one dense byte run as a whole: `_sf_blob_reject` requires the view's span to equal its element count. That still accepts an aliasing view whose span happens to equal its element count, for example one with a stride-0 row axis; the per-plane check refuses it.

## Why

The `F8_128x4` block-quantize epilogue stores the scale blob at compact offsets from the scale tensor's base pointer: `tile_l * quant_scale_stride_l + ((row // 128) * ncb + scol // 4) * 512 + ...`. Row quant uses the shared `_emit_block_quant_row` (`python/cudnn/gemm/frost/epilogue_codegen.py:1051-1060`), col quant `sm120/epilogue_codegen.py:739-752`. `quant_scale_stride_m/n` are passed but never used, and `tile_l` is a literal 0 on MoE. The compile-time fake has symbolic strides and the required alignment of a scale tap is 1 byte. Of the launchers, only swap-AB MoE (`sm120/compiler.py:_launch_moe_swap_ab`) checked the scale tensor, and only as a whole blob: `_sf_blob_reject` requires its span to equal its element count. The dense launcher and the non-swapped MoE launchers compared shapes only. Block-scale MoE also checked grouped row scales, but skipped non-grouped and col quants (`compiler.py:612` on develop). A pitched or element-strided view of the declared shape was accepted, and the blob was written into the view's gaps, which is memory outside the tensor.

Reproducer (RTX PRO 6000, SM120, `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`). The graph is a bf16 matmul M = N = 256, K = 128, then `block_scale_quantize` (block 32, FP8_E4M3 data, FP8_E8M0 scale, `F8_128x4`, scale dims `[1, 256, 8]`). The scale is bound as `raw.view(1, 256, 16)[:, :, :8]` (stride `(4096, 16, 1)`) of a buffer filled with `0xA5`:

- Observed on develop: the call is accepted, 1024 bytes outside the view are overwritten, and the view's own elements hold the wrong scales. Expected: a `ValueError` before launch, as swap-AB raises.
- Element stride 2 (`(4096, 16, 2)`) behaves the same way.
- The public path (`graph.execute()` with the FROST plan) behaves the same way.
- Plain non-swapped MoE (E = 4, S = 300, N = 256): 1024 and 1200 bytes outside the view are written.
- Block-scale MoE (nvfp4, S = 512, N = 256), row and col quant, one GEMM and with an epilogue op: 2048 bytes outside the view are written.
- Dense batched L = 2 with interleaved batch planes (stride `(8, 16, 1)`): the view is one dense byte run as a whole, so nothing outside it is written, yet 1468 to 1493 of the 2048 bytes of each plane, read through the view, are wrong. These counts are from three runs on develop and change from run to run: the two planes overlap in memory and their writes race.
- Dense batched L = 2 with overlapping planes (stride `(1024, 8, 1)`): the two planes overwrite each other inside the view (173 to 258 wrong bytes per plane in the same runs); nothing outside it is written.
- Swap-AB plain MoE (E = 4, S = 512, N = 256, scale dims `[1, 512, 8]`), measured on this PR's first commit, whose swap-AB launcher is the same as on develop: a view with stride `(4096, 0, 585)` (every row aliases row 0) spans exactly its 4096 elements, so the swap-AB check accepts it, and 4088 of the 4096 blob bytes land at addresses the view does not contain.

Why decline, and why a per-plane rule:

- The epilogue addresses this tensor only through the base pointer, the batch stride and the fixed atom layout. Making the index honor the M/N strides would change compiled kernels and their cost for a layout no normal caller uses. Refusing such a binding at execute, with a `ValueError` before anything is written, is the execute-time validation of Rule 1, and matches what FROST already enforces for SF inputs and for the swap-AB launcher. Rule 2's build-time decline of a declared layout the kernel cannot address is not part of this change (see API and compatibility impact).
- The rule is per batch plane, not the whole-blob `_sf_blob_reject`, because the dense epilogue applies the runtime batch stride. A whole-blob density check accepts the interleaved view above, which is still written wrong, and aliasing views like the swap-AB one. It also rejects a padded batch pitch (for example `big[:, :256, :]` of a `[2, 512, 8]` buffer), which the kernel addresses correctly today. Rule 1 notes the same for `F8_128x4` weight-scale expert planes: whole-blob density does not establish a per-plane contract.
- On MoE the batch extent is 1, so the rule reduces to: the one plane is a dense byte run.

Why shared code is touched: since #1993 these launch guards live in the shared `python/cudnn/gemm/frost/compiler.py`. The check itself is in the SM120 tree. The shared code calls it only under the opt-in flag, so the SM100 classes keep their current behaviour.

Found in an audit of the SM120 Frost kernel templates (finding B27).

## API and compatibility impact

- SM120 tree only. A call that binds an `F8_128x4` quant-scale output as a view whose batch plane is not one dense byte run (a row pitch, an element stride, interleaved planes, rows that alias each other), or whose batch planes overlap, now raises `ValueError` before anything is written. Such calls used to be accepted and left wrong scales in the view (swap-AB MoE already refused the views that are not one dense byte run as a whole). With a row pitch, an element stride or aliasing rows the blob was also written to bytes outside the view; interleaved or overlapping planes overwrote each other inside it.
- Compact bindings, dense permuted planes and a padded batch pitch are unaffected. No numerics change, no kernel or compile-key change, and no graph is newly declined at build time.
- A graph that declares a non-packed stride for an `F8_128x4` scale is still accepted at build. Bindings that carry that declared layout, a bare address (which takes the declared stride) or a torch view with the declared pitch, are now refused at execute instead of being written outside the view. A compact torch tensor bound to the same graph keeps its own strides and is accepted; the blob lands inside it (checked through `graph.execute()` with a declared stride `[4096, 16, 1]`). On the same GPU the native backend rejects such a declaration at build (cuDNN 9.24: "For CUDNN_TENSOR_REORDERING_F8_128x4 the scale tensor is expected to be tightly packed. Expected stride (batch_stride, non_block_scaling_stride, block_scaling_stride) to be (2048, 8, 1) but found (4096, 16, 1)"). Declining that declaration at build in FROST too (Rule 2, and Rule 9's single contract with the backend) is left for a follow-up.
- SM100: the same defect exists and is intentionally left for a follow-up, following the convention that fixes land in both trees. The SM100 col-quant index (`python/cudnn/gemm/frost/sm100/epilogue_codegen.py:381-394`) and the shared row-quant index ignore the M/N strides. The SM100 `CompiledFusedGemm`, `CompiledMoeGemm` and `CompiledMoeBlockScaleGemm` (`sm100/compiler.py:1923`, `:2891`, `:3045`) leave `_validate_quant_scale_blobs` off. The SM100 swap-AB launcher checks with the whole-blob `_sf_blob_reject` only (`sm100/compiler.py:2925`), so it keeps the aliasing gap closed here for SM120. The follow-up would set the flag there, add the same call to the SM100 swap-AB launcher and move `_quant_scale_plane_reject` and `_quant_scale_blob_reject` into the shared module. It needs SM100 hardware to test, which this change was not run on.
