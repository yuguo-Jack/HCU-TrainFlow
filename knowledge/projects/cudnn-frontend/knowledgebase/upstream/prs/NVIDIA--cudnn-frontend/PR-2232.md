## Affected area

FE OSS kernels or CuTeDSL

## Summary

Serves the SM120 per-tensor FP8 and MXFP8 FROST forward rows (`sdpa_fwd_prefill_sm120_fp8`, `sdpa_fwd_prefill_sm120_mxfp8`) by default on cc 12.x, without `CUDNN_FRONTEND_ENABLE_FROST_ENGINES`. A forward precision defect found while qualifying them is fixed first.

Two commits:

1. **FP8 / MXFP8: cast P with a 2^8 bias instead of 2^4** (`prefill_fp8.py`, `prefill_mxfp8.py`, `prefill_d512_fp8.py`, `prefill_d512_mxfp8.py`).
   - P is relative to the row max, so in a peaked long row the other keys sit far below `1/S`. With 2^4, every P under 2^-14 (9.7 nats below the max) rounded to zero in e4m3, and the tail's mass was lost from O.
   - With 2^8, P is kept down to 2^-18 (12.5 nats), the range the backend's `Scale_S = 448` gives. The online softmax adopts every new row max, so P ≤ 1 and the cast peaks at 256 < 448.
2. **Default placement** (`engines/manifest.py`, `fwd/placement.py`).
   - The FP8 row ranks against the backend per a measured shard: it goes behind the backend on d128 prefill over a short cache (`S_kv <= 512`, or `<= 1024` mask-free) and on graph features the A/B did not build (THD, padding mask, right band, sink, block-scaled O, fused gate, E5M2).
   - The MXFP8 row leads everywhere: the backend has no MXFP8 SDPA on cc 12.x.

## Why

On cc 12.x the backend serves per-tensor FP8 forward only at d <= 128 with `S_q > 1` (cc 12.0 only), and no MXFP8 at all. Without the flag, every other FP8 graph and every MXFP8 graph on RTX 50 / RTX PRO 6000 / DGX Spark had no engine, and where both serve, FROST is faster on most shapes.

## Benchmark

RTX PRO 6000 Blackwell Server Edition, SM / memory clocks locked at 2100 / 12481 MHz, cuDNN 9.27.0.42, CuTe DSL 4.8.0, `benchmark/attention_training/benchmark_single_sdpa.py` (torch-profiler kernel time). Three providers per case (the backend with FROST deselected, FROST pinned, and the flag-less default), three rounds in rotating order, median of per-round ratios; every case passed the between-round CV <= 5% gate.

75 dense BSHD E4M3 graphs where both providers serve (d64 / d128, 16/16 and 32/8 heads, b x s from 8 x 512 to 1 x 16k, causal and mask-free, chunks q512-4096 over kv 4k-16k, decode-shaped q 2-16 over kv 8k, a 1k window):

| | |
|---|---|
| FROST / backend | 0.33-1.21, median 0.77; FROST slower on 8 |
| mean regret of the default against the faster provider | 45.4 % with the backend first -> 0.0 % with this placement |
| worst default pick | 6.0 % (d128, b4 32/8 s1024 mask-free, FROST 0.94: inside the trail band) |
| FROST-first cases slower than the backend | 1 (1.025, b4 32/8 q512 over kv 4096) |

The RTX 5090 measurements behind the same band are in the `fwd/placement.py` docstring.

Commit 1 is time-neutral: FROST before vs after on 68 FP8 and MXFP8 graphs (d64-d512, prefill squares, decode q1 / q8 over 16k), alternating processes on one locked GPU, new / old 0.988-1.008 (median 1.000), every case reportable.

## Numerics

Against an exact fp64 reference on the dequantized inputs (nothing quantized), FROST and the backend on identical inputs, E4M3 in and out, 4k and 16k keys, d64 / d128, causal and full, logit spread 1-6: the O RMS error of the two providers agrees within 0.5 % on all 24 graphs, and `Amax_O` is within 1e-4 relative on peaked rows. (The graph suites' FP8 reference reproduces the backend's own `Scale_S` quantization, so it is not a neutral yardstick between the two.)

The new tail-mass test puts two anchors 10 nats above 32766 keys: before commit 1 FROST's O misses the tail's 0.427 of the mass entirely; after it, within 1 %.

## Related issues

None.

## API and compatibility impact

- No public API change. Graphs on cc 12.x that previously had no engine now run on FROST; where both providers serve, the faster one is listed first per the measured shard.
- `Scale_S` / `Descale_S` are not read by any FROST FP8 row (this was already true of the SM100 and SM107 default rows): each kernel uses its own power-of-two P bias and cancels it exactly, which equals the graph for the reciprocal pair the docs prescribe. The `graph_analyzer.py` comment that said otherwise is corrected.
- With the flag set, FROST still ranks first everywhere.

## Testing

On an RTX PRO 6000 (cc 12.0), CuTe DSL 4.8.0, cuDNN 9.27.0.42:

- RED -> green: the 4 new tail-mass tests (FP8 and MXFP8 at d128 / d512) fail before commit 1 and pass after.
- `sdpa/frost` at L0 + L1: 2354 SM120 tests and 9925 others pass.
- Graph-API suites with the flag unset (the production walk), all passing:
  - `test_mhas_v2` random forward / decode / ragged / bias / lean: 1285
  - FP8 / MXFP8: 451
  - the cc 12.x default-walk tests: 96
  - `suites/context` and `suites/generation` FP8: 1186 (plus the existing backend `Amax_O` xfail)
  - `suites/context` MXFP8: 388
  - `test_graph_native`, edge cases, chunked prefill, THD: 85
  - the backward suites: `test_mhas_v2` 346, `suites/bprop` 473, models 17
- Fresh-seed sweep through the flag-less walk: 462 FP8 / MXFP8 graphs pass (FROST served 256 and 157 of them).
- compute-sanitizer: memcheck 0 errors over 150 SM120 forward suite tests and 114 random graphs; synccheck 0 errors. Racecheck reports one pattern, which is ordered: the redundant per-warp zeroing of padded V rows (`sanitize_v_tail`: every warp stores the same zeros, then syncs the warp before its own reads; every recorded value is 0).
- The same suites with `cuda:1` as the current device on a two-GPU node: 295 + 574 pass.

Not in this PR:

- THD lowerings still assume fully packed storage (documented in `Capabilities.thd`).
- Single-token decode that also requests Stats keeps the backend first, although FROST measured 2-5x faster there.
- The f16 split-KV decode partials stay in the io dtype; against fp64 their O RMS error is 1.2-1.45x the backend's at 32k-128k keys.
