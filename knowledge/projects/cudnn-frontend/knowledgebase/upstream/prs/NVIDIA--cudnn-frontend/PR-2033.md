## Summary

The SM120 col-quant epilogue emitter (`_emit_block_quant_col`) writes the scales of a block quantize along the kernel's M axis. It now computes its F8_128x4 scale offset in Int64 on all three of its paths:

- Dense and ungrouped paths: `mcb` (the number of 4-block M atoms) was a Python literal baked from the build-time M. It is now emitted as `_q0_mcb = ((M // bs) + 3) // 4` from the kernel's Int64 `M`. The row-quant emitter derives its `ncb` from the Int64 `N` the same way, except on its swap-AB grouped branch (see "Known remaining sibling" below).
- Grouped non-swap MoE path: `mcb` was `((group_end - group_begin) // bs + 3) // 4` in Int32. It is now computed from `cutlass.Int64(group_end - group_begin)`.
- Swap-AB grouped MoE path: unchanged. It serves a graph row (feature-axis) quant with `group_offset` and already derived `mcb` from `M`.

With an Int64 `mcb`, the atom term `((n // 128) * mcb + mb // 4) * 512` is promoted to Int64 before it can overflow.

Which graph-level quants this covers:

- Covered: a graph col (axis=1) quant on non-swap dense and MoE plans, grouped or not.
- Covered: a graph row quant on swap-AB dense and MoE plans, which the kernel computes as a col quant.
- Not covered: a graph col quant on a swap-AB plan. The kernel computes it as a row quant in the shared row emitter. The ungrouped case there is already Int64. The MoE grouped case still wraps and is left for its own PR (see "Known remaining sibling").

The new test has three parts:

- L0 GPU cells (dense and grouped MoE, ordinary sizes): check every computed scale (not the F8_128x4 padding slots) and all quantized data.
- L1 cells (`gpu_exclusive`, about 12 GiB each), dense and grouped MoE at N = 16, 2^28 + 64 rows, block 16. That is the smallest group-aligned wrapping shape: MoE group offsets are multiples of 4 * block_size, and the dense path already wraps at 2^28 + 16 rows. The cells check the scales and data of the first atom, the last atom below 2^31 and the atom past it, and that the 2 GiB guard below the scale tensor is untouched. The scale tensor sits 2 GiB into a buffer pre-filled with a sentinel byte, and each cell has one batch (one group) starting at the tensor's offset 0. A store whose offset wrapped therefore lands on that buffer's head, which the test owns and checks, instead of on memory the test does not own.
- A host-only L0 render check: the rendered index must multiply by an Int64 `_q0_mcb` and must not depend on the plan's M.

## Why

`row`, `col_j` and the lane index are Int32, and CuTe DSL keeps Int32 op small-int arithmetic in Int32 without overflow flags. So the col-quant scale index `((n // 128) * mcb + mb // 4) * 512 + ...` was evaluated in 32 bits before being added to the Int64 batch term (and, on the grouped path, to the Int64 group base).

It wraps once one batch's padded scale table passes 2 GiB, i.e. `ceil(N/128) * ceil(M/(4*bs)) > 2^22`. On the grouped path, it wraps once one group's table passes 2 GiB. From then on, each scale byte past offset 2^31 of that table is stored a multiple of 2^32 bytes below its slot (2^32 for tables up to 6 GiB), and the slot itself is never written. Where the store lands depends on where the table starts:

- The first batch, or a group whose table starts at offset 0, with a table of at most 4 GiB: before the scale tensor, an out-of-bounds write.
- A later batch (L > 1), a later MoE group, or a larger table: the store can also land inside the scale tensor, in an earlier batch's or group's table or in an earlier part of its own table, and silently overwrite those scales. On 24a8cd43, with two MoE groups of 2^28 + 64 rows, the second group's 64 wrapped scale bytes replaced the first group's scales of rows 64..127 (probe under Testing).

Minimal reproducer on 24a8cd43 (RTX PRO 6000, SM 12.0, `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`):

- Graph: dense `matmul` with bf16 A `[1, M, 8]` and B `[1, 8, 16]` (both K-major), M = 2^28 + 64.
- Quant: `block_scale_quantize(axis=1, block_size=16)` with FP8 E4M3 data and FP8 E8M0 scales, F8_128x4 reordering, scale dim `[1, 128, 4 * (2^22 + 1)]`.
- Observed: the 64 scale bytes of the last 64 rows (offsets 2^31 to 2^31 + 243) are never written, and 64 bytes are written 2 GiB below the start of the scale tensor. Rows below the boundary and all quantized data are correct.
- Expected: every scale byte at its F8_128x4 offset and nothing written outside the scale tensor.

The same happens on these other plans that this emitter serves:

- The MoE NONE-mode template's col quant, grouped (`group_offset=fto`) and ungrouped.
- A MoE swap-AB plan whose graph row quant the kernel computes as a col quant: 2^29 + 128 tokens, N = 16, block 16, so the scale table is 2 GiB + 512 bytes. The 128 scale bytes past 2^31 are never written, and 128 bytes land below the tensor.

Because F8_128x4 pads N to 128, N = 16 is the cheapest way to reach a 2 GiB scale table. At N >= 128 a wrapping call needs at least 32 GiB (block 16) or 64 GiB (block 32) of FP8 data output from one GEMM (SM120 declines FP4 output), so this is a low-severity defect. When it triggers, it silently corrupts memory before the scale tensor or scales inside it.

Deriving `mcb` from the runtime `M` instead of wrapping the literal in `Int64` also removes the build-time literal from the generated source. On every accepted call the result is the same: `_check_runtime_quant` re-runs the quant gates at the runtime M, and those gates require the planned `scale_dim`, whose padded M-block count is `4 * mcb`. Offsets and values are therefore unchanged for every shape below 2 GiB. TRT-LLM's `cvt_quant_get_sf_out_offset` likewise computes the swizzled SF offset with int64 strides.

The audit entry named only the dense template (`sm120_matmul.py`). The same emitter also serves the MoE templates' col quant: the ungrouped path used the same literal, and the non-swap grouped path used an Int32 group extent. Both reproduced the same wrap, so this PR fixes every path of this emitter.

**Known remaining sibling (not fixed here).** On a MoE swap-AB plan, a graph col (token-axis) quant with `group_offset` is computed by the kernel as a row quant.

- Location: the shared `_emit_block_quant_row` in `python/cudnn/gemm/frost/epilogue_codegen.py` emits it for both SM100 and SM120. Its swap-AB grouped branch (`epilogue_codegen.py:1040`) still computes `_ncb = (((group_end - group_begin) // bs) + 3) // 4` in Int32. The same atom term therefore wraps once one group's table passes 2 GiB.
- Reproducer (the same result on 24a8cd43 and on this branch): `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2` with `swap_ab=True`, MoE NONE, one group of 2^28 + 64 tokens, N = 16, K = 8, `block_scale_quantize(axis=1, block_size=16, group_offset=fto)`, F8_128x4, scale tensor 2 GiB into a 0xFF carrier. The 64 scale bytes past 2^31 are never written, and 64 bytes land below the tensor.
- Why it is a separate PR: the fix is the same widening (`cutlass.Int64(group_end - group_begin)`), but it is in a shared module and also changes SM100's generated code.

Found in an audit of the SM120 Frost kernel templates (finding B28).

## API and compatibility impact

- Public API: none.
- Numerics and layout: unchanged for every shape whose padded scale table per batch (per group on the grouped path) is at most 2 GiB. Beyond that, on the plans covered above, the scale bytes past 2^31 are now stored at their slots instead of a multiple of 2^32 bytes below them. A graph col quant with `group_offset` on a MoE swap-AB plan still wraps (see "Known remaining sibling").
- Generated code: the F8_128x4 atom term is now a 64-bit multiply per stored scale byte, as on the row path. On the dense and ungrouped paths, `mcb` comes from the kernel's `M` argument instead of an immediate. On the grouped non-swap path, `mcb` was already computed at runtime from the Int32 group extent; that extent is now widened to Int64. Performance was not measured, because the GPUs were shared and not used for timing.
- SM100: the same defect exists in `python/cudnn/gemm/frost/sm100/epilogue_codegen.py:382` (literal `mcb`, used at `:387`) and `:373` (Int32 group extent). It is intentionally left for a follow-up; this change touches only the sm120 tree. The sibling in the shared row emitter applies to SM100 as well.
