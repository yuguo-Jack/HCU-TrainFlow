## Affected area

DSA score recompute: docstrings of the Python wrappers

## Summary

Addresses #1549. Docstrings only; no behavior change.

`docs/fe-oss-apis/dsa.md`, under "Compact vs. non-compact sparse indices", already sets the contract, and it shipped in 1.31.0 via #957:
- Slots past `topk_length[row]` must hold `-1`, even when `topk_length` is passed.
- The reason is that the SM100 attention score-recompute wrapper may run its non-compact kernel.

The mechanism, in `_interface_sm100.sparse_attn_score_recompute`:
- When the compact and non-compact tile configs match, it sets `topk_length = None`.
- For H128/D512 with `topk <= 512`, both configs are `(128, 128, 128)`, which is the shape in #1549.
- The non-compact kernel then skips slots by index value, so `0` padding is read as a live key.

The two public wrappers, `sparse_attn_score_recompute_wrapper` and `sparse_indexer_score_recompute_wrapper`, did not mention this. Callers read `topk_length` as "masks everything past the prefix". Both docstrings now state the `-1` requirement. The attention wrapper also says why.

Not changed: the dispatch itself. Honoring `topk_length` on that path would give up the static-loop-bound codegen win (18–28% per the code comment) or add a masking pass. That is a decision for the DSA owners.
