# frost(sdpa bwd sm100 d128): run the cta_group::2 pair body on cc 10.3; tests skip by name where the body declines

## Original PR description

## d128 grouped THD `cta_group::2` pair body: admit cc 10.3 by name; the pair-body test rows skip (never fail) where the body declines

### The failure
The GPU CI lane `python/sdpa/frost:cutlass-rel:sm103` (cc 10.3) fails every pair-body row of the four d128 2-CTA test modules
(`test_sdpa_bwd_d128_2cta_stail_sm100.py`, `..._xfa4_sm100.py`, `test_sdpa_bwd_d128_cta_pair_heuristic.py`, `test_sdpa_bwd_d128_dkv_accum_sm100.py`),
e.g. `test_xfa4_zero_trip_items_do_not_hang[zero_trip_first_item_ramp]`: the child script builds the pair body through
`d128_2cta_test_utils.make_adapter_2cta`, whose `assert api.check_support()` let the library's typed decline out as a failure:

    NotImplementedError: sdpa_bwd_sm100_d128: cta_pair 'on' requires cc in ((10, 0),) (the measured part); got (10, 3)

Two defects, both on our side: (1) the pair route's cc gate (`d128_grouped_2cta_contract.CTA_PAIR_CCS`) admitted the measured part only, although
GB300 (cc 10.3) carries the same tcgen05 / `cta_group::2` / TMEM / CLC features and the one-CTA d128 body already serves cc 10.0 / 10.3
(`d128_contract.ACCUMULATION_CCS`); (2) the test helper turned a typed decline into a failure instead of a skip, so the same rows fail on the
sm80 / sm120 lanes as well -- hidden there inside jobs the bot already tags "Old Failure".

### The fix (one commit)
**(A) Library -- admit the SM100 line.** `CTA_PAIR_CCS = ((10, 0), (10, 3))`; the decline text names the line ("requires cc in ((10, 0), (10, 3))
(the SM100 line; the per-S threshold was measured on GB200, cc 10.0)"); the adapter docstrings and the tracker rows say cc 10.0 / 10.3.  Nothing else is
per part: the pair route already compiles for the device exactly as the one-CTA body does -- `prepared_sm100_d128_grouped_2cta.compile_plan` passes
`sm = cc[0] * 10 + cc[1]` into the artifact key and the host renders with `--gpu-arch sm_{sm}a` (`prepared_d128_grouped_2cta_host.py:227`, the same
line as `prepared_d128_grouped_thd_host.py:166`), so cc 10.3 compiles `sm_103a`.  The cluster admission (occupancy query) and the per-S threshold are
unchanged; no SM count is hard-coded in the pair route (`grep -n "148\b\|sm_count\|multiprocessor_count"` over its config / contract / host / kernel
files: no hit).  The sm_103a host render of the default chain has the same census and register split as sm_100a and every kernel's `.entry` md5
matches the committed record (only the module's `.target` line differs), so the record file stays single-arch like the one-CTA body's.

**(B) Tests -- a typed decline is a SKIP with the decline as its reason.**  `make_adapter_2cta` maps `NotImplementedError` out of `check_support()`
to `pytest.skip("pair body declined on this device: <text>")` (a `ValueError` and a silent `False` still fail: those are bugs); the fresh-process
skew / hang-repro children exit `CHILD_EXIT_SKIP = 77` with the reason on stdout (documented beside the watchdog's `70` = HANG) and their parents
map 77 to `pytest.skip`; `_require_2cta` reads `CTA_PAIR_CCS` from the contract instead of its own copy.  The `cta_pair=auto` fallback rows and
`test_cta_pair_on_declines_by_name_off_the_measured_part` still RUN on every lane: they are the proof of the decline path off the SM100 line.

RED-first host rows (red on develop, green here): cc patched to (10, 3) -> the pair body is selected under `auto` and `on` passes `check_support`;
cc patched to (8, 0) / (12, 0) -> the helper raises `pytest.skip.Exception` with the decline text; the sm_103a host render matches the record.

### Proof

  (every pair-body row skips with the decline text; the decline rows run).  No sm103 node is available to us locally; the compile target follows the
  device by the same mechanism the one-CTA body has used on that lane.
