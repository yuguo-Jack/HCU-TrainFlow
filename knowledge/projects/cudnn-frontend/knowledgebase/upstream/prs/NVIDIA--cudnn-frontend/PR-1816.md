## Affected area

FE OSS kernels / CuTeDSL: GDN-2 steep-decay backward correction, plus a reproducible benchmark.

## Summary

When steep gates repeatedly activate the exact fallback, rebuilding overlapping intervals adds substantial backward-pass cost. This change reuses those sums while preserving the numerical safeguard.

Reduce redundant interval summation in `steep_grad_corrections`. Walk backward through earlier tokens and forward through later tokens, extending each bounded gate interval one element at a time. Reuse the restore-scale interval during the backward walk too.

This reduces interval-accumulation work from quadratic to linear per token/channel. It preserves the exact fallback, nonpositive exponents and direct token-log accumulation; it does not subtract cumulative prefixes, clip gates or change dispatch. Lower-triangle summation order changes, so bitwise equivalence to the old implementation is not claimed.

## How it works

The old code rebuilds overlapping log-gate intervals from zero. The patch walks earlier keys backward and later queries forward, extending each interval by one gate.

![Animated comparison of independently recomputed log-decay intervals versus incremental reuse, with numeric gates and running totals](https://github.com/alfredclwong/cudnn-frontend/releases/download/evidence-pr-1816-20261023/gdn2-interval-accumulation-loop.gif)

Rows are query tokens and columns are key tokens. For `(5, 0)`, both methods accumulate `g₁…g₅` to −15, excluding `g₀`. The optimized traversal reuses the previous pair’s sum. Both traversal paths stay in the causal lower triangle.

This seven-token illustration reduces decay-term accumulations from **16 to 6**. Its cells show completed interval sums using illustrative log₂ gates, not the inputs used for the benchmark. The count excludes restore-scale work and other gradient arithmetic; playback does not represent GPU time. ### Why retain conditional dispatch?

A separate experiment compared the optimized conditional path with an always-exact variant on one B300 in the same public container. It used the same six synthetic cases and checked the output and all six gradients against FP64. The variant forced exact arithmetic on every channel and removed the fast launch and flag dependency. Profiler counts confirmed fewer launches: 8 to 5 at 16 tokens, and 17 to 11 at 256 tokens.

Always-exact reduced GPU busy time by **15.6% / 12.3%** when all 64 channels were steep at 16 / 256 tokens. But it took **3.28× / 5.02×** as long for mild inputs, and **60.3% / 85.2% longer** with one steep channel. All 24 cases across four BAAB arms passed the 1% FP64 tolerance. The worst always-exact relative Frobenius error was **0.483%**. Values average two per-arm medians and measure GPU busy time, not end-to-end throughput.

These results support conditional dispatch for general inputs. This PR retains it and reduces work within the exact fallback. The experimental variant is not part of the proposed source changes. Its baseline used the optimized runtime at `9dc7dd3047e5de579970544080eee8ec13a22596`.
