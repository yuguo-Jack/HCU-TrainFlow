## Affected area

FE OSS kernels or CuTeDSL (DSA `indexer_top_k` radix kernel and its scratch sizing).

## Summary

`indexer_top_k` on BF16 rows wider than 32,768 columns now bins its coarse histogram with the same FP16-derived key the FP32 path uses, so BF16 top-k is no longer slower than FP32 on long rows.

- `IndexerTopKKernelVarlen`: new `bf16_fp16_coarse_key` (BF16 and `max_num_cols > 32768`, via `bf16_uses_fp16_coarse_key()`). For those specializations `to_coarse_key` converts BF16 -> FP32 -> FP16 and takes the FP16 top byte (sign + 5 exponent + 2 mantissa bits), exactly as FP32 does. The fine key stays the exact 16-bit BF16 key; because a coarse bin no longer fixes its top byte, the refine covers both bytes in two rounds (`first_refine_shift = 8`, `num_refine_rounds = 2`), which alternate between two candidate buffers like FP32's four rounds (`num_buffer_smem_input_idx = 2`).
- `buffer_numbers(torch_dtype, num_cols=None)`: new trailing `num_cols`; 2 int32 scratch rows per input row for FP32 and for BF16 wider than 32,768 columns, else 1 (`None` returns the dtype's maximum). `IndexerTopK` passes its `num_cols`, so `scratch_workspace_bytes()` follows; `benchmark/dsa/benchmark_deterministic_top_k.py` updated the same way.
- Unchanged: FP32, FP16, and BF16 up to 32,768 columns (same coarse key, rounds, buffers and scratch). Up to that width every candidate fits the single shared-memory buffer of the native BF16 key, and on SM120 the 99 KiB block budget holds only that one buffer there (wider BF16 already takes the small-buffer large-occupancy specialization on SM120, so the second buffer costs at most 16 KiB of shared memory).
- Docs: `docs/fe-oss-apis/dsa.md` workspace formula.

## Why

The radix top-k histograms an 8-bit coarse key, collects every candidate of the threshold bin (shared memory first, then the global scratch), and refines them with the exact key. For FP32 the coarse key is the FP16 top byte, a quarter binade per bin. For BF16 it was the BF16 top byte, sign + 7 exponent bits, i.e. two binades per bin. Scores concentrated in a few binades (indexer scores, Gaussian-like data) then put a large share of a long row into the threshold bin: a CPU model of the GLM-5.2 indexer score distribution gives 7K to 90K threshold-bin candidates per 1M-key row with the BF16 key versus 2.5K to 6.3K with the FP16-derived key. Those candidates spill to the global scratch and are gathered again in the refine round.

At GLM-5.2 1M-token context (CP64, rank 0: 16384 rows x 1,048,576 keys, top-k 2048, GB300) FE top-k took 22.75 ms on BF16 scores versus 14.45 ms on FP32 scores, although it reads half the bytes; with this change BF16 takes 13.35 ms. This is what makes BF16 dense indexer scores (the separate BF16-scores PR) usable with FE's own top-k.

Exactness: BF16 -> FP32 is exact and FP32 -> FP16 round-to-nearest is monotonic (saturating to inf above 65504), so the coarse bins never reorder the exact keys (checked exhaustively over all non-NaN BF16 values by `test_DSA_indexer_top_k_bf16_fp16_coarse_bins`). Elements in bins before the threshold bin are strictly larger than every threshold-bin element, and the threshold bin is resolved on the exact 16-bit key, so the selected set, `tie_break` and deterministic mode are unchanged in meaning. The FP16 zero bin and the two saturated bins span many BF16 exponents, which is why both refine bytes are needed (the same test asserts it).

### Hard Rules notes (`python/cudnn/AGENTS.md`)

- Rule 1 / Rule 8: the scratch stays caller-owned; `scratch_workspace_bytes()` reports the larger size for wide BF16 and `execute()` still validates, never allocates.

## API and compatibility impact

- `buffer_numbers` (kernel module helper) gains a trailing `num_cols=None`; positional callers keep working and get the dtype's maximum, which is safe (over-provisioned) for every width.
- `IndexerTopK.scratch_workspace_bytes()` doubles for BF16 inputs wider than 32,768 columns (now equal to FP32's: `n_rows * 2 * num_cols * 4`). Callers that size the workspace from `scratch_workspace_bytes()` or use `indexer_top_k_wrapper` need no change; a caller that hard-coded one scratch row for BF16 gets the existing "undersized workspace" error before launch. At 1M keys and Megatron's 1024-row chunks the BF16 top-k peak above the scores goes from 4.19 to 8.19 GiB (FP32: 8.25 GiB).
- Performance: BF16 rows wider than 32,768 columns only; see Testing for where it is faster and where it is slower.
- Architectures unchanged (SM90+); SM120 shared-memory limits and the deterministic-mode column limits are unchanged.

### Correctness at scale

On every S3 / S3-outlier / S4 row (16384 / 16384 / 4096 rows, 14080 / 14080 / 2048 of them longer than k), the BF16 selection was compared with the FP32 path's selection of the same values upcast to FP32: `tie_break=1`, `tie_break=2` and `deterministic=True` select identical sets (deterministic: ascending order too), `tie_break=0` selects the same value multiset; returned values equal the BF16 scores at the returned indices bit for bit; no duplicates; `-1` padding exact. 24 sampled long rows per case also match `ref_indexer_top_k` (and so does the FP32 reference). 0 mismatches in all three jobs.

Not run: SM90 (no Hopper), SM100 (B200), SM120 (the native SM120 tests skip on SM103; the SM120 shared-memory budget argument is above), a supported (non-hybrid) develop build, other suites (no other code path changes; `qsa_select` calls the top-k on FP32 scores).

## Follow-ups (not in this PR)

- For coarse bins inside FP16's normal and subnormal range the first (top-byte) refine round is degenerate: such a bin holds one BF16 exponent. Skipping it based on the threshold bin was exact but measured slower (S3 BF16 14.94 ms vs 13.35 ms), presumably from the dynamic shift/loop bound in the hot collect pass; worth revisiting together with FP32, whose first round is degenerate for the same bins.
- At 1M keys FP32 and BF16 now take about the same time (14.4 vs 13.4 ms) although BF16 reads half the bytes, so the kernel is bound by per-element work (the shared-memory histogram atomics) rather than bandwidth; DeepSelect's BF16 top-k takes 4.0 ms on the same rows.
