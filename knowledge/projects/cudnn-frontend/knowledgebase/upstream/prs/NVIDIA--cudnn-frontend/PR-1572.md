## Summary

Fixes #1571. Fixes #1579.

**The problem.**
- Every tensor declares a 16-byte alignment by default (`Tensor_attributes::alignment`), and the native SDPA kernels rely on it.
- The backend checks neither the row strides nor the caller's pointers against it, so a misaligned Q/K/V/O is not rejected.
- On cuDNN 9.27, on every native plan tried (B200 `eng10`/`eng8`, H100 `eng9`/`eng8`, A100 and L40S `eng8`):
  - **Forward:** the output is wrong on H100/B200 with success returned (0.73 to 0.77 max error with only Q misaligned, non-finite with all operands misaligned). On A100/L40S the kernel faults with `CUDA error: misaligned address`, which is sticky and ends the CUDA context.
  - **Backward** (`eng5`/`eng6`/`eng7`): `err 716 misaligned address` on B200, H100 and L40S.

**The fix.** The frontend enforces the alignment it already declares, for SDPA operands only.
- **Build:** `post_validate_node` of the SDPA forward base (composite and unified) and of the FP16/BF16 backward node rejects a stride when the dimension's extent is > 1, the stride is not 1, and `stride × element size` is not a multiple of the tensor's alignment.
  - The forward check covers Q, K, V and O. The backward check covers Q, K, V, O, dO, dQ, dK and dV.
  - This makes the native lowering decline the graph. A Python engine can still claim it: on B200, FROST `sdpa_fwd_prefill_sm100` serves a 136-byte pitch correctly (BF16 max error 2.6e-3).
- **Execute:** those nodes report each operand's uid, alignment and element size through a new `collect_aligned_operands_node` hook. Build caches the result, and it is serialized as an optional `aligned_operands` key (`uid: [alignment, element_bytes]`).
  - `prepare_variant_pack_template` turns it into `(slot, alignment)` pairs. These cover the caller's slots and the legacy Slice destinations.
  - `execute_plan_at_index` checks the pointers after the Slice replacements are applied. It refuses a misaligned one with `INVALID_VARIANT_PACK` before anything launches. The cost is one modulo per SDPA operand per execute.
    - On cuDNN < 9.22 headers, Slice is lowered by pointer offset, so a slice starting off the alignment is caught here even though the caller's source pointer is aligned.
  - `populate_cuda_graph()` and `update_cuda_graph()` build their own variant pack. Before adding or updating any node, they derive the legacy Slice destinations (source pointer + offset) the way `execute()` does, then run the same pointer check.
    - The derived bindings live in a per-call map and are never written back to the caller's map. A reused map therefore re-derives from its current source, and only a destination the caller binds itself overrides the derivation.
  - `override_strides` of an aligned operand get the build-time stride rule, so an override cannot bring back a misaligned pitch. Per #1570 the native forward plans ignore override strides today, so before this change such an override gave wrong output instead.
  - Graphs serialized before this change carry no key, so they keep the old behavior.
- **Legacy Slice in `execute()` (#1579).** Below cuDNN 9.22, the template gives the Slice source a slot, and `execute()` handed that uid to the backend as well. The SDPA engine rejects the extra uid (`varPackUidCount > expected_uid_count`), so a Slice + SDPA graph could not execute on 9.21.
  - `prepare_variant_pack_template` now records the backend's slots and uids without such sources.
  - `execute()` compacts the pointers to that list only when such a source exists.
  - The template slots and `get_variant_pack_uids_sorted()` are unchanged.
- Other ops are unchanged. Sequence-length, ragged-offset and page-table tensors are not checked: callers commonly pass 4-byte-aligned slices of those, and they are outside this measurement.
