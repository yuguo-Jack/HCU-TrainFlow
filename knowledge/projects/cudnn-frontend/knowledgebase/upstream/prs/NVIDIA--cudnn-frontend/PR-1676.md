# Release what CUDA graphs handed back when a plan or graph is destroyed, not during execute

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1676) · state: closed · merged: True

## Original PR description

## Problem

Since the frontend started keeping runtime-compiled plans alive for the CUDA graphs that record them, a destroyed CUDA graph hands its plan back through a CUDA user-object destructor. That destructor may not call CUDA, so the plan is queued, and the queue was drained by the next `execute()` on a stream that is not being captured.

Releasing a plan destroys its backend descriptor, which frees device memory and unloads its runtime-compiled code. Both wait for all work on the device. So an otherwise asynchronous `execute()`, of any plan, could:

- block until unrelated work on other streams finished, or
- deadlock, if that work waited for the application to continue after the call (for example a host callback waiting on a flag).

Measured on H100: unloading code or freeing memory while another stream has 600 ms of pending work takes 580–910 ms, against 0.02 ms when the device is idle. Doing it from another thread doesn't help, because launches from other threads stall for the same time.

## Fix

Drain the queue when a `CudaGraphRetainedResource` is destroyed, that is when the frontend destroys an execution plan or graph, right after the owner drops its own reference. `execute()` and capture only add references to the graph being recorded.

- A CUDA graph still keeps its plan (and host-copy data such as ALiBi slopes) alive for as long as the graph exists. Only the release of plans whose graphs are already gone moves.
- A plan whose graphs outlive every frontend plan and graph stays alive until the next one is destroyed, or until process exit.
- The cuDNN backend makes the matching change for the code it releases itself, targeted for cuDNN 9.28. That change alone isn't enough for frontend users, because the frontend would still destroy the plan inside `execute()`.

## Tests

The CUDA graph lifetime tests move from `samples/cpp/misc/cudagraphs.cpp`, which is meant as a sample, to the unit tests in a new `test/cpp/cuda_graph_lifetime.cpp` (second commit, moved unchanged, including the two direct populate/update sections #1140 added to "Cuda graph outlives the frontend graph"). The sample file keeps "Cuda graphs with matmul add". New tests there:

- **Retained resources are released when an owner is destroyed:** with a payload that counts its releases, a graph that outlives its owner keeps the payload; recording on an uncaptured stream (what `execute()` does) releases nothing; destroying any owner releases it. An owner that outlives its graphs releases the payload in its own destructor.
- **Executing a frontend graph does not release what CUDA graphs handed back:** three uncaptured `execute()` calls leave a queued release pending; destroying the frontend graph releases it.

A third commit fixes the capture-release test for the new release timing: building a graph destroys temporary plans, which now releases what is queued, so the test builds everything the capture needs before queuing the release, and checks that the release is still pending when the capture starts and done after.

Rebased on develop (including #1140) and run on H100 against a cuDNN 9.28 build with the matching backend change: the 6 `[cudagraph]` cases in `tests` pass, as do the 3 `[cudagraph]` and the `[cudagraph_186]` cases in `samples`, and the rest of `tests` (64 cases: 62 passed, 2 skipped). The `[cudagraph]` cases include "Cuda graph outlives the frontend graph" and "ALiBi slopes outlive the frontend graph in a CUDA graph", which check that graphs keep their plans alive. With the old headers, the new release-timing tests fail at the three expected points.
