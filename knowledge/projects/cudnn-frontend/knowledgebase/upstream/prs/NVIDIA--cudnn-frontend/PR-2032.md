## Summary

- The grouped scheduler of the four SM120 MoE templates now clamps each group into the routed rows before it counts the group's tiles: `end = min(max(fto[g+1], 0), R)` and `begin = min(max(fto[g], 0), end)`. R is the routed extent the kernel already receives: `M` on the token-by-weight kernels, `N` on swap-AB. Every later token-axis bound derives from these two values: the drain row and column guards, the per-row aux clamp, the `token_index` / `token_ks` reads and the tile count. So all of them stay inside the buffers. For a table that meets the contract, the clamp returns the values the scheduler used before.
- The two block-scale schedulers also place each group's 128-row scale-factor segment from a prefix of the clamped groups. After the clamp, a decreasing table can still describe overlapping groups, and their segments can add up past the segmented SF capacity that the host checks (`segmented_row_scale_capacity_rows(S, G)`). A grouped row-quantized scale output is stored at that prefix with no other bound. These two schedulers now also cap each segment start at `capacity - blocks`. The capacity is the same formula the host uses for the SF descriptor (`rest_m_sf` / `rest_n_sf`). A valid table never reaches the cap.
- `first_token_offset[0]` is still not read: group 0 begins at row 0, as before.
- New SM120 tests, 7 cases:
  - BF16 and MXFP8 NONE mode, token-by-weight and swap-AB, with the output placed between guard rows;
  - BF16 GATHER with a table past R;
  - MXFP8 with a grouped row-quantized FP8 output and its segmented scale output, each followed by a guard.

## Why

The schedulers built each group straight from the device-side `first_token_offset`. At 24a8cd43 the reads are at `sm120_moe_grouped_matmul_fwd.py:301-303`, `sm120_moe_grouped_matmul_fwd_swap_ab.py:298-300`, `sm120_moe_grouped_block_scale_matmul_fwd.py:441-444` and `sm120_moe_grouped_block_scale_matmul_fwd_swap_ab.py:440-443`. Everything below the scheduler bounds the token axis by `group_end` only:

- The drains store a row when `row < group_end` (`sm120_moe_grouped_matmul_fwd.py:688`, `:748`), or a token column when `col_j < group_end` on swap-AB. `sm120/epilogue_codegen.py:808-809` renders `row_bound` / `col_bound = "group_end"`.
- GATHER, SCATTER and COMBINE read `token_index[row]` / `token_ks[row]` for any `row < group_end` (`tile_helpers.py:207`, `:398`).
- SM120 always stores through raw-pointer STG, so nothing clips at S. Only the TMA operand loads are clipped.

The host checks only the number of boundaries (`_moe_num_groups`, `gemm/frost/compiler.py:487`), and it cannot read device data without a sync. The documented contract (`docs/operations/MoeGroupedMatmul.md:52`) is: nondecreasing, starting at zero, last boundary at most the routed rows. A table that breaks it therefore corrupts memory instead of producing wrong values. I reproduced this on an RTX PRO 6000 (SM120) at 24a8cd43. Each output was an exactly shaped view inside a sentinel-filled buffer:

| plan (E=2, S=256, N=256) | `first_token_offset` | rows stored outside the output, base | this branch |
|---|---|---|---|
| BF16, K=128, `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2` | `[0, 128, 384]` | 128 after it | 0 |
| same | `[0, 128, 456]` | 200 after it | 0 |
| same | `[0, -64, 128]` | 64 before it | 0 |
| BF16 swap-AB | `[0, 128, 384]` | 128 after it | 0 |
| MXFP8, K=256, token-by-weight and swap-AB | `[0, 128, 384]` | 128 after it | 0 |
| BF16 GATHER, R=257, G=6 | last boundary 297 | 40 after it | 0 |

In the GATHER case, the 40 rows are bit-equal to `token[5] @ W[2]^T`, and 5 is the value in the `token_index` storage past R. So the kernel also read the index vector out of bounds. The in-bounds rows matched the reference on both trees. A decreasing pair also hands `cute.ceil_div` a negative extent. The audit's reviewers found, from the scan code and CPU models of it, that once the tile count comes out negative, the following groups lose their first tiles. That was not reproduced on the GPU: the audit's GPU probe ran one decreasing table, `[0, -64, 128]` (the row above), and its decreasing pair gets a tile count of zero.

The audit's reviewers proposed the per-lane clamp above. It costs a few integer min/max per lane per 32-group scan window, needs no host sync, and gives identical schedules for valid tables. On the two block-scale templates the clamp alone is not enough. The case I used: MXFP8, E=G=5, S=512, and an FP8 output with grouped F8_128x4 E8M0 row scales, so the scale output is 8192 bytes.

- Table `[0, 512, 0, 512, 0, 512]`. On base this table stays inside the scale output, because the negative SF block count of each decreasing pair cancels the overlap. The clamp makes that count zero, so groups 0, 2 and 4 each take four 128-row segments. With the clamp but without the cap, both block-scale templates stored 4096 bytes past the scale output. With the cap they stored none.
- Table `[0, 1, 2, 3, 4, 1024]`. On base this stores 512 rows past the quantized output and 4064 bytes past the scale output. On this branch it stores none.

I also tried reading the table as its nondecreasing envelope (a running maximum of the clamped ends) in the block-scale schedulers. That removes the overlap itself, but it adds a dependent six-step shuffle chain to every 32-group scan window. That scan is on the critical path of each CTA's first claim when E is large. The cap costs one subtraction and one min per lane and leaves the scan as it is, so I used the cap. With a bad table, overlapping groups still write the same in-bounds rows. The contract leaves that case undefined anyway.

`first_token_offset[0]` stays unread. This is audit finding B05, which the reviewers judged to be inside the documented contract. The audit report suggested fixing B05 together with B04. This PR leaves `fto[0]` unread on purpose: reading it would change what a table with `fto[0] > 0` computes, and this fix does not need that. The clamp also runs on group 0's begin, so a later B05 change that reads `fto[0]` into it composes with this one unchanged.

This was found in an audit of the SM120 Frost kernel templates (finding B04).

## API and compatibility impact

- Tables that meet the documented contract: no change. The clamp and the cap return the values the scheduler used before, so schedules and numerics are unchanged, and no graph is newly declined.
- Tables outside the contract: the kernels no longer touch memory outside the output, scale and routing buffers. They drop the rows past R instead. Rows that a negative or decreasing boundary no longer covers keep their contents.
- Cost: the token-by-weight and swap-AB scans gain four integer min/max per lane per 32-group window. The block-scale scans gain six, plus a few operations once per CTA. I did not time this, because the GPUs are shared. The added operations are small next to the scan's global load and its five-step shuffle prefix. The template sources change, so the first use of each SM120 MoE plan compiles once more.
- FlashInfer: its SM120 MoE kernels are frozen exports, so they are unaffected until they are re-exported. Its routing kernels produce tables that meet the contract.
- SM100: the SM100 MoE templates have the same unclamped reads: `sm100_moe_grouped_matmul_fwd.py:453-455`, `sm100_moe_grouped_matmul_fwd_swap_ab.py:452-454`, `sm100_moe_grouped_block_scale_matmul_fwd.py:470`, `:487`, `:555`, `:570`, `:639`, and `sm100_moe_grouped_block_scale_matmul_fwd_swap_ab.py:462`, `:479`, `:547`, `:562`, `:631`. The repo convention is that a fix lands in both trees; this PR intentionally leaves the SM100 copy for a follow-up. The SM100 block-scale schedulers use a different scan, so that fix will not be a copy of this one.
