# Draft: 769: Funnel attribute port maps through one JSON serializer instantiation

## Problem

`cudnn_frontend.h` is header-only, so every customer TU pays its full parse and instantiation cost. Measured with g++ 11.4 on one TU:

| TU | `-fsyntax-only` | `-O2 -c` |
|---|---|---|
| `#include <cudnn_frontend.h>` + build one SDPA graph | 13.0 s | 32.5 s |
| same, `-DCUDNN_FRONTEND_SKIP_JSON_LIB` | 5.7 s | 19.9 s |

JSON accounts for 7.3 s of that 13.0 s — but only 0.78 s of it is parsing `json.hpp`. The rest is the compiler instantiating nlohmann's machinery over **our** types.

Each `*_attributes` class declares its own private `input_names` / `output_names` enum and keys `inputs` / `outputs` by it. Handing those maps directly to `NLOHMANN_DEFINE_TYPE_INTRUSIVE` makes nlohmann instantiate its object/array serialization machinery once per enum type — 76 instantiations across the graph API.

Isolated repro, 38 classes with two port maps each:

| key type | time |
|---|---|
| distinct enum per class (status quo) | 3.16 s |
| one shared key type | 2.08 s |
| `json.hpp` alone, no classes | 0.78 s |

I also checked whether nlohmann's own feature switches could help. They can't — every macro that compiles (`JSON_NO_IO`, `JSON_HAS_RANGES=0`, `JSON_HAS_THREE_WAY_COMPARISON=0`, `JSON_HAS_STATIC_RTTI=0`, `JSON_NOEXCEPTION`, `JSON_USE_GLOBAL_UDLS=0`), individually or combined, lands within run-to-run noise of the 12.9 s baseline. They only trim parts of the 0.78 s header parse; none of them touch the instantiation cost.

## Change

Route each serialized member through `json_detail::json_set` / `json_get`. The generic overload is the same assignment nlohmann's macro emitted. The port-map overload converts to a single common `port_list_t` first, so the heavy instantiation happens once instead of 76 times.

`CUDNN_FE_DEFINE_ATTRIBUTES_JSON` mirrors `NLOHMANN_DEFINE_TYPE_INTRUSIVE` exactly, substituting those two calls, and replaces it at the 39 attributes classes. `Concatenate_string` has no port maps and is left on the upstream macro.

## Wire compatibility

Unchanged. The funnel emits the same array of `[port_name, tensor]` pairs that `Graph::serialize` already folds into a uid-keyed object (`graph_interface.h:2610-2640`).

Verified by dumping `Graph::serialize(json&)` for conv+pointwise+reduction, layernorm, matmul and SDPA graphs before and after — output is byte-identical.

## Draft — open questions

This recovers roughly half of the JSON overhead without any API or format change. The other half needs a call I'd rather not make unilaterally:

- Deferring the 39 serializer bodies out of `graph_properties.h` entirely (declaration there, definition in `utils/serialize.h`, following the existing `Tensor_attributes` precedent at `graph_properties.h:154` / `serialize.h:599`) takes the baseline to **8.3 s**. Dropping `serialize.h` from `cudnn_frontend.h` on top of that reaches **5.7 s** — but that is source-breaking for anyone calling `Graph::serialize` / `deserialize` without adding an include. Worth doing as a follow-up, and if so, on what deprecation path?
- Separately: `CUDNN_FRONTEND_SKIP_JSON_LIB` already exists (`CMakeLists.txt:8`) and is documented nowhere. Should it be surfaced in the README for consumers who never serialize?
