## Summary

An SM120 FROST GEMM call with a zero extent no longer kills the process.

- New `_zero_extent_problem(m, n, k, block_size, source_rows)` in `sm120/compiler.py`. It returns `True` when M or N is 0 (nothing to compute). It raises `ValueError` for K = 0, for a block-scale K below one scale block, and for a MoE GATHER whose token buffer has no rows.
- New class flag `_check_zero_extents` on `_CompiledRuntime` in the shared `compiler.py`, default `False`. The three sm120 classes (`CompiledFusedGemm`, `CompiledMoeGemm`, `CompiledMoeBlockScaleGemm`) set it to `True`.
- When the flag is set, every launcher calls the helper after its existing validation and before the first write:
  - the dense `lowered` closure (plain, block-scale, multi-GEMM and split-K plans);
  - `_launch_single` and `_call_multi_gemm` of the plain and block-scale MoE classes;
  - the sm120 `_launch_moe_swap_ab` calls the helper directly.
- For an empty call, the reduction seeds and the COMBINE zero-fill are written as before, and then the launcher returns without launching. A dense split-K plan skips its split-K shape check and does not require a workspace for such a call.
- Tests: launch-recorder tests for every launcher, and SM120 runs through the public FROST engine and `jit_from_cudnn_graph` MoE.

## Why

Found in an audit of the SM120 Frost kernel templates (finding B25).

None of the launchers checked that an extent is positive. Zero passes every divisibility and alignment check, and `_pow2_floor(0)` returns its cap, so the null data pointer of an empty tensor counts as aligned. The compiled template host then calls `cuTensorMapEncodeTiled` with a zero `globalDim` (for example `global_dims=[k_sym, m, a_batch]` in `sm120_matmul.py`). The driver returns `CUDA_ERROR_INVALID_VALUE`. The DSL checks that result with `cuda_dialect_assert_success`, which prints a message and calls `abort()`. The host process dies with exit code 134. There is no exception to catch, and the engine cannot fall back.

Minimal reproducer: a bf16 FROST plan for `[1,256,128] x [1,128,256]` through the graph API. Execute it with `override_shapes=[[1,0,128],[1,128,256],[1,0,256]]` (M = 0):

```
CUDA Dialect Assertion failed on CUDA error: cudaErrorInvalidValue - invalid argument
(process exit 134)
```

Expected: the call does nothing, because there is nothing to compute. A realistic trigger is an expert-parallel rank that received no tokens and calls its MoE plan with S = 0.

Each case below ran in its own process on an RTX PRO 6000 (SM120):

| Path | Call | develop 24a8cd43 | This PR |
|---|---|---|---|
| dense bf16, `jit_from_cudnn_graph` | M = 0 or N = 0 | abort (134) | returns, no launch |
| dense bf16, `jit_from_cudnn_graph` | K = 0 (strided view) | abort (134) | `ValueError` |
| dense bf16, `jit_from_cudnn_graph` | K = 0 (contiguous) | TVM-FFI `ValueError` (`problem_size[4] ... divisible by 8`) | `ValueError` naming K = 0 |
| FROST engine, `override_shapes` | M = 0 or N = 0 | abort (134) | returns, output untouched |
| FROST engine, `override_shapes` | K = 0 | abort (134) | `ValueError` |
| MoE bf16 NONE, both orientations | S = 0 or N = 0 | abort (134) | returns, no launch |
| MoE NVFP4 NONE, both orientations | S = 0 | abort (134) | returns, no launch |
| dense NVFP4 | M = 0 or N = 0 | abort (134) | returns, no launch |
| dense MXFP8 | K = 16 (scale-factor K extent `(16 // 32 + 3) // 4 = 0`) | abort (134) | `ValueError` |
| MoE GATHER bf16 | token buffer `[1,0,96]`, 257 routed rows | abort (134) | `ValueError` |

Why this fix:

- The abort happens inside compiled host code, so the guard has to run in Python before the launch. Guarding only the descriptor encode in `_host` does not help. The dense grid would still have a zero dimension, and clamping the extents to 1 would make TMA read rows that do not exist.
- **M or N = 0.** The kernel would compute no tile. The reduction identities that the launcher already writes, and the COMBINE zero-fill, are the result that a zero-tile kernel would leave. This matches the existing convention for empty MoE groups: for example, AVG of an empty group reads 0 (`_group_reduction_ref`). The engine sizes a split-K workspace from the call's output, so an empty call gets no workspace. The dense path therefore no longer asks for one when it launches nothing.
- **K = 0.** The outputs would be the epilogue applied to an all-zero product, and the kernel cannot produce that. The audit left the choice open between refusing the call and computing `epilogue(0)`. This PR takes the conservative option and refuses with a clear message. The check runs before any seed is written, so a refused call leaves the caller's buffers untouched (Rule 1).
- **Block-scale K below one scale block** (MXFP8/MXFP4: K < 32; NVFP4: K < 16). The scale-factor descriptor's K extent `(K // block + 3) // 4` is 0, which fails in the same way, so the call is refused. The fix for finding B01 (#2008) declines every block-scale K that ends inside a scale block, which includes these values, and refuses them earlier with its own message. With both merged, this branch of the check is only a backstop, and K = 0 is the case it still covers.
- **GATHER from an empty token buffer.** No routed index can be valid, so the call is refused.

Why `python/cudnn/gemm/frost/compiler.py` changes: #1993 moved the dense launch closure (`_CompiledFusedGemm._lower`) and the token-by-weight MoE launchers out of `sm120/compiler.py` into this shared module. The guard has to run there, between validation and the first write. To keep SM100 unchanged, the new behaviour is opt-in through a class flag. This follows the existing pattern of `_validate_runtime_quant`, `_validate_combine`, `_check_padded_operands` and `_check_all_operands`. All four are read by the shared launchers and set only by the sm120 classes, and the first three call helpers that exist only in `sm120/compiler.py`.

Hard Rules (`python/cudnn/AGENTS.md`):

- **Rules 1, 2, 3 and 8.** An empty call writes only what the plan already writes before its launch (the seeds and the COMBINE zero-fill) and then launches nothing. The guard adds no kernel, allocation, device read or synchronization. Non-empty calls take exactly the same path as before.
- **Rule 1, "No degenerate-path fixups".** Nothing is re-implemented adapter-side. The seeds and the zero-fill are the pre-launch writes that every call already makes; the guard only skips a launch that has no tile to compute. The rule's other remedy, a never-dereferenced dummy view, does not fit here, for the reason given above: the grid would keep its zero dimension, and a widened extent would be read.
- **Rule 9, one contract for backend and FROST.** The two engines still differ on these degenerate shapes, in both directions. I ran the reproducer's override-shape `execute()` on the native engine (engine 0) on the same GPU:

  | Graph | Override | native engine 0 | FROST, this PR |
  |---|---|---|---|
  | `is_override_shape_enabled=True` | M = 0 or N = 0 | `RuntimeError`: `CUDNN_STATUS_NOT_SUPPORTED_INVALID_DYNAMIC_SHAPE` | returns, output untouched |
  | `is_override_shape_enabled=True` | K = 0 | writes zeros to the live 128 x 256 region | `ValueError` |
  | flag not set (the reproducer above) | M = 0, N = 0 or K = 0 | ignores the override and computes the declared 256 x 256 x 128 problem | same as the rows above |

  Rule 9 lets capabilities differ, but not the contract. FROST applies the override in every case, and what it cannot compute it refuses with an exception before writing anything. One check does get weaker: an empty call returns before the compiled binding, so the binding's front-door checks, the dtype check among them, no longer run for any of its operands (see "API and compatibility impact"). The K override only arrives at `execute()`, so `check_support()` cannot decline it.

  Producing the K = 0 result (`epilogue(0)`) would need one of two things: a kernel that runs with no K tiles (its K-major descriptors cannot encode K = 0), or an adapter-side fill, which Rule 1 forbids. So this PR refuses K = 0.

  For M = 0 and N = 0, FROST could raise instead, to mirror the native refusal. I kept the no-op because the MoE launchers share this guard, and the realistic trigger is an expert-parallel rank with no tokens. The bf16 MoE graph of these tests has no native plan on this GPU: the backend fails to finalize it with `CUDNN_STATUS_BAD_PARAM`, and FROST is its only plan. So for S = 0 there is no native result to match.

## API and compatibility impact

- SM120 FROST GEMM and MoE plans: a call with M = 0 or N = 0 now returns after writing the reduction seeds and the COMBINE zero-fill, without launching a kernel. For MoE this means no routed rows in NONE mode, or N = 0. Previously the process aborted. A dense split-K plan accepts such a call without a workspace.
- Exception: plans with a `block_scale_quantize` output run their existing runtime quantization check first. As on develop, it refuses with a `ValueError` a runtime M or N that does not match the quant-scale shape declared in the graph. For example, a dense plan built for 256 x 256 raises `block_scale_quantize requires scale_dim=(1, 0, 8); got (1, 256, 8)` for M = 0.
- Since #2008 (now on develop), a block-scale call whose K ends inside a scale block is refused before this PR's check, even when M or N is 0. I checked this on the merged tree with the launch recorders. MXFP8 calls with K = 16 and M = 0 or N = 0 (dense), or S = 0 (MoE, both orientations), raise #2008's `block-scale K=16 is not a multiple of the scale block size 32 ...`, launch nothing and write nothing. With K = 256 (dense) or K = 128 (MoE), the same empty calls return without a launch.
- These calls now raise `ValueError` before anything is written (previously they aborted, or for contiguous K = 0 raised a TVM-FFI `ValueError` after the seeds were written):
  - K = 0;
  - a block-scale K below one scale block;
  - a MoE GATHER whose token buffer has no rows.
- An empty call never reaches the compiled binding, so the binding's front-door checks (TVM-FFI), the dtype check among them, run for none of its operands. A mistyped operand of an empty call is therefore no longer refused, whether that operand is itself empty or not. The Python checks that come before the zero-extent check still run for an empty call: operand rank and layout, alignment, and the runtime quantization check of the exception above. Measured on this GPU before the merge of develop 18df4c38 ("develop" below is 24a8cd43), each case in its own process:
  - Direct `jit_from_cudnn_graph` path, bf16 plans. Each of these calls raised `ValueError: Mismatched Tensor on argument #n` on develop, and now returns without an error:
    - dense, M = 0, with an fp16 A `[1, 0, 128]` or an fp32 C `[1, 0, 256]` (both empty), or with an fp16 B `[1, 128, 256]` (not empty);
    - MoE, S = 0, with an fp32 output `[1, 0, 256]` (empty) or an fp16 weight `[8, 256, 128]` (not empty).

    Non-empty calls keep the check: the same fp16 B in a dense call with M = 256 is refused with `Mismatched Tensor` on develop and on this branch.
  - `graph.execute` on the FROST plan, with an empty torch tensor of the wrong dtype and no override (fp16 A `[1, 0, 128]`, or fp32 C `[1, 0, 256]`). Such a buffer keeps its own description, so the result is the same: develop raised `Mismatched Tensor`, and this branch returns. With override shapes or bare addresses, the slot carries the declared dtype.
  - Nothing is read. The only writes are the seeds and the COMBINE zero-fill, which develop also made, because they come before the binding call. A non-empty mistyped buffer that covers the declared bytes is reinterpreted at the declared dtype by `graph.execute`, on develop and on this branch alike.
- A CUDA graph captured from an empty call contains only the pre-launch writes. I checked this with a probe, not a committed test, on a dense MAX-reduction plan: M = 0 and N = 0 each captured one MEMSET node and no KERNEL node, the capture raised nothing under `torch.cuda.set_sync_debug_mode("error")`, and replay rewrote the seed. The non-empty control captured one MEMSET and one KERNEL.
- The native engine handles these shapes differently; see Rule 9 under "Why".
- Non-empty calls, the public API and SM100 are unchanged.
- SM100 has the same defect; I checked this by reading the code, not on SM100 hardware. Its classes do not set the flag:
  - `python/cudnn/gemm/frost/sm100/compiler.py:1923` (`CompiledFusedGemm`), `:2891` (`CompiledMoeGemm`) and `:3045` (`CompiledMoeBlockScaleGemm`);
  - its `_launch_moe_swap_ab` (`sm100/compiler.py:2897`) launches at `:2960` with no extent check;
  - its templates encode the same descriptors, for example `sm100/kernel_templates/sm100_matmul.py:1279` (`global_dims=[k_sym, m, a_batch]`) and `sm100_moe_grouped_matmul_fwd.py:1355` (`a_dims = [k_sym, m, 1]`).

  The repo convention is to fix both trees. The SM100 copy is intentionally left for a follow-up: set `_check_zero_extents = True` on the three sm100 classes, give that tree the same helper, and call it in its `_launch_moe_swap_ab`.
