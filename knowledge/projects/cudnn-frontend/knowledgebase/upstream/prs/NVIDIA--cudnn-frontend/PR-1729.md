# Accept raw uint8 FP8 operands with dtype metadata in the block-scaled grouped GEMM wrappers

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1729) · state: open · merged: False

## Original PR description

## Summary

Transformer Engine stores quantized MXFP8 data and scales as `uint8` and tracks the FP8 format in its own metadata. To call the grouped GEMM wrappers it currently views every operand as `float8_e4m3fn` / `float8_e8m0fnu` first: about 20 views per MXFP8 training step, each costing 0.6–1 µs. This came up in the NVIDIA/TransformerEngine#3641 review.

With this change, the block-scaled GLU, quant (dgrad), dGLU and wgrad wrappers and class APIs take those buffers as they are:
- **Data:** raw `uint8` A and B, with `a_dtype` and `b_dtype` naming the FP8 dtype they hold (`float8_e4m3fn` or `float8_e5m2`). For GLU, quant and dGLU, `b_dtype` applies to a dense `b_tensor`; it already names the weight dtype in discrete mode.
- **Scale factors:** raw `uint8` SFA and SFB, whose dtype follows `sf_vec_size`: 32 is E8M0, 16 is E4M3. `uint8` scale factors were rejected before, so this is unambiguous.
- **Packed FP4 unchanged:** `uint8` data without `a_dtype` still means packed FP4.
- **Feature flag:** the four wrappers advertise `supports_raw_uint8_operands`.

How it works:
- **Checks** see the logical dtype, because the operand descriptors are relabeled at construction.
- **Compilation** uses `uint8` placeholders for the raw operands. The compiled kernel's call-time check compares dtype codes exactly, so a kernel compiled for FP8 rejects a `uint8` tensor.
- **The kernel's jit launcher** relabels each raw operand with `cute.recast_ptr`, next to the existing canonical-layout conversions. This touches no data and adds no per-call host work.

## Measurements

GLU wrapper host time p50, MXFP8, canonical operands, 4 experts × 512 rows. B200, one pinned CPU core, medians of 3 rounds:

| Caller | µs per call |
|---|---:|
| Views `uint8` buffers as FP8/E8M0 before each call, as TE does today | 38.4 |
| Passes raw `uint8` with `a_dtype` / `b_dtype` | 34.6 |

That is 3.8 µs saved for 4 operands. TE's MXFP8 fused grouped MLP makes 6 such calls per training step.

## Testing

All on SM100.
- **New `test_grouped_gemm_raw_uint8.py`:** raw `uint8` against typed operands, bitwise, on cold and warm calls:
  - GLU with physical and flat scale buffers; the test also confirms the raw path compiled (12 tests in the file);
  - quant with K- and N-major B, BF16 and FP8 outputs;
  - dGLU with K- and N-major B, physical and flat scale buffers, deterministic dprob;
  - wgrad with flat scale buffers;
  - rejection of a non-FP8 `a_dtype`.
- **Wider regression** (every `gemm/cutedsl` test matching `grouped`): 1833 passed, 1320 skipped. The 2 failures were in the new GLU test's raw-path check, which assumed every cached API has `raw_dtypes`. After fixing it, the GLU canonical and raw `uint8` files pass (46 tests).

## Not covered

- **NVFP4 data:** relabelling 4-bit data changes the element count, so it needs a layout change and is not in this PR. NVFP4 `uint8` scale factors are inferred as E4M3 but not tested.
- **Discrete weight mode:** pointer tables already carry their dtype through `b_dtype`.
- **Other APIs:** the Hadamard GLU and SReLU variants are unchanged.
- **Rubin:** the Rubin kernels get the same relabel lines but are not hardware-tested.
- **TE:** the Transformer Engine change that passes raw buffers is not part of this PR.

**[P1 · high risk] Include both logical FP8 dtypes in the wgrad compiled-plan cache key** ([source](https://github.com/NVIDIA/cudnn-frontend/blob/5030428791b4345d07566bae3001a52efb5e45e1/python/cudnn/gemm/cutedsl/grouped/wgrad/api.py#L445))

The outer wrapper memo includes a_dtype and b_dtype, but this second-level cache key includes neither. With raw uint8 operands, the physical tensor signatures are identical for E4M3 and E5M2. A new-format outer memo miss therefore retrieves the old-format compiled plan and permanently memoizes it for the new format too. Using the existing wgrad fixture with expert token counts [256, 384], flat raw scale buffers and sf_vec_size=32, each format separately matches its typed reference with cold caches. Calling E4M3 then E5M2 without clearing caches makes the E5M2 call return exactly the E4M3 result: 484154 BF16 output elements differ from the correct reference, with maximum absolute error 141.0. The reverse order fails likewise. This is silent corruption of a supported training-gradient operation, not a rejection of an unsupported layout. Add both logical data dtypes to the compiled-plan key and cover E4M3 -> E5M2 -> E4M3 plus the reverse sequence. Please address this before merging.
