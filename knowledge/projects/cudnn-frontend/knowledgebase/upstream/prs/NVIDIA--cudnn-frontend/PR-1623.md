## Affected area

## Summary

Fix an off-by-one in the residual mask of the NSA top-k reduction kernel (`native_sparse_attention/top_k/nsa_top_k_reduction_fwd.py`).
The compressed key at index `s_k`, one past the sequence, was not masked, so it leaked into a selection block's score. Both bounds now use `>=`.
Adds an L0 noninterference test.

## Why

The mask compares the query and key indices with the sequence lengths:

```python
if q_idx > cur_s_q or k_block_idx > cur_s_k:
    tTR_rS[i] = -cutlass.Float32.inf
```

`cur_s_q` and `cur_s_k` are lengths (exclusive bounds), so key index `cur_s_k` is not masked. When `s_k` is not a multiple of the
128-column key tile, that key is loaded with the last tile:

- `T,H,D`: it is the **next sequence's first compressed key**, so one sequence's top-k depends on another sequence's data
  (for the last sequence it is a padding row after `cum_seqlen_k[-1]`, or TMA zero fill).
- `B,H,S,D`: it is a TMA zero-fill row, which still contributes `exp(0 - LSE)` per head instead of 0.

The key is added to the score of selection block `s_k // (selection_block_size // compress_stride)`. The candidates of query `q`
are the blocks `0 < g < (q + 1) // selection_block_size - 2`, so the leak can change outputs only when
`s_k < s_q / compress_stride - 2 * selection_block_size / compress_stride`. At the usual compressed length (`s_k ≈ s_q / compress_stride`)
the leaked block is never a candidate. The existing tests use s_q = 4096 and s_k = 128 and do not check values, so they cannot see it.
The API accepts any `cum_seqlen_k`, though, for example a shorter compressed sequence or a longer compression block.

Repro on B200 (sm_100): two `T,H,D` sequences, s_q = 4096, `selection_block_size` = 64, `compress_stride` = 32, k = 16, h_q = 4,
h_k = 1, d = 128. Scale the first compressed key of sequence 2 by 4 and compare sequence 1's top-k:

| s_k | changed sequence-1 indices, develop | with this PR |
|---|---|---|
| 128 | 0 | 0 |
| 127 | 0 | 0 |
| 120 | 608 | 0 |
| 64 | 14138 | 0 |

The counts are the same for causal and non-causal. In the `B,H,S,D` layout (b = 2, s_q = 4096, s_k = 34, so blocks 0..16 hold keys),
455 of the 8192 rows select block 17, which holds no key, on develop (causal and non-causal); 0 with this PR.

The query-side change (`q_idx >= cur_s_q`) changes no output, because row `cur_s_q` is never stored. It keeps the mask consistent with
the exclusive bounds. A build with only the key-side change gives outputs bit-identical to this PR on all 14 configurations compared, including the
ones that trigger the leak.

## Related issues

touches neither `api.py` nor the end of that test file, and the two merge without conflicts: a 3-way merge of the test file against

## API and compatibility impact

None. There is no API change. Outputs are bit-identical to develop whenever the leaked block cannot be selected. They were compared
bitwise on 9 configurations:

- layouts `T,H,D` and `B,H,S,D`, causal and non-causal;
- s_k = s_q / 32, including ragged s_q = [1000, 3000, 2048] with s_k = [31, 93, 64];
- s_k = 127 and s_k = 130 at s_q = 4096.

Kernel time is unchanged within run-to-run noise (A/B/A/B on 4 shapes with CUDA events, and on 5 shapes with CUPTI device time).
