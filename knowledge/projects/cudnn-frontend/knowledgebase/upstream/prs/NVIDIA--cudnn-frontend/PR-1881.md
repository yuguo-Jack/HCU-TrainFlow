## Affected area

- FE OSS kernels or CuTeDSL (`python/cudnn/gemm/frost/sm120/compiler.py`, the four SM120 MoE templates)

## Summary

After #1880 landed on develop as 6fcc0aa5, develop was merged into this branch (merge commit 58f89829, whose tree equals eec1d8a8 rebased onto 6fcc0aa5), so the diff against develop is the counter-reset change only: 7 files, +33/-4 (`sm120/compiler.py`, the host launch of the four SM120 MoE templates, and two test files). The compiler renders an `external_counter_reset = False` constant into the SM120 MoE tile constants; when a runtime that pre-zeroes the grouped scheduler's global tile counter renders it `True` in its frozen source, the host skips the one-thread `dynamic_scheduler_counter_initialization` launch. The kernel is unchanged and reads the counter after `griddepcontrol.wait` either way.

## Why

The four SM120 MoE templates zero the scheduler counter with a one-thread launch before the PDL main launch. A runtime that wraps the kernel in its own pipeline can zero that qword earlier on the same stream (FlashInfer's MoE adapters zero it in their routing kernel, which runs before FC1 and FC2 in any case) and save the launch: at decode sizes the two init kernels and their serialization are about 2 us of a 45 us MoE call.

Status, stated plainly: the FlashInfer adapter change that would render `True` was prototyped and then rolled back on the FlashInfer side (it touched code owned by another contributor), so no shipped consumer renders `True` today; the default `False` keeps today's behavior bit for bit. The knob is offered for the integration that wants it.

## Related issues

None. Follows #1880 (merged as 6fcc0aa5); develop is merged into the branch, so GitHub no longer sees the duplicated 9769e15b hunks as a conflict.

## API and compatibility impact

- No public API change; default behavior identical (`external_counter_reset = False`).
- A frozen source rendered with `True` must guarantee the counter is zeroed on the same stream before the launch; the render smoke tests pin the constant and the guarded launch.
- Supported GPU / cuDNN / CUDA / Python versions unchanged.

## Testing

- Render smoke tests in `test/python/gemm/frost/test_moe_grouped_block_scale_matmul_fwd.py` / `test_moe_grouped_matmul_fwd.py` pin the constant and the guarded launch (this commit's additions).
- The SM120 MoE test selection across `test/python/gemm/frost/test_moe_grouped_*matmul_fwd*.py` was run on 2026-10-26 on an RTX PRO 6000 Blackwell Server Edition (SM120; CUDA 13.4, cutlass-dsl 4.7.1, torch 2.14.0+cu130) with this branch checked out: 630 passed; render smoke / footprint tests 14 passed.
- End to end (FlashInfer unified MoE, MXFP8 x MXFP4, with the since-reverted adapter rendering `True`): the two counter-init launches disappear from the per-call kernel trace; about 2 us at T=1.
