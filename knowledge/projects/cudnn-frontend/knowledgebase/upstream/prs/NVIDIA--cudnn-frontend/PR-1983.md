# sdpa bwd (sm100): dense D192x128, D64 with a left window, FP8 / MXFP8 dK/dV + dQ kernel pair

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1983) · state: closed · merged: True

## Original PR description

## What

New SM100 backward rows served by FROST:

- **Half precision**: a dense D192x128 accumulation row (`sdpa_bwd_sm100_d192`), and D64 plus a left sliding window on the existing D128 accumulation route (`sdpa_bwd_sm100_d128`).
- **FP8 (per-tensor) and MXFP8 (block-scale)**: a dK/dV + dQ kernel pair for dense and grouped D128 (`sdpa_bwd_sm100_d128_fp8`), D64 with a left sliding window, and dense D192x128 (`sdpa_bwd_sm100_d192_fp8`). The block-scale rows run under the existing `sdpa_bwd_sm100_mxfp8` engine.

Kernel pair: the dK/dV kernel owns one key tile and streams the query tiles; the dQ kernel owns one query tile and streams the key tiles. P and dS travel through SMEM rings, the exponentials split between MUFU and the FMA pipe, and only the diagonal and tail tiles are masked. The block-scale mode keeps the scale factors in tensor memory; at D192x128 the transposed operands reuse the stage one tile behind.

The new engine slots (11, 12, 13) are opt-in.

## Scope

cc 10.0 to 10.6, compact BSHD, top-left causal or full masks, a left sliding window where listed. THD, bottom-right causal and the deterministic mode stay on their existing routes.

## Validation

- `test_sdpa_bwd_d192_accum_sm100.py`, `test_sdpa_bwd_d64_accum_sm100.py` (new): the half accumulation rows against the fp32 reference, with masks, windows, layouts and odd lengths.
- `test_sdpa_bwd_fp8_sm100.py`, `test_sdpa_bwd_d192_fp8_sm100.py` (new) and `test_sdpa_bwd_mxfp8_sm100.py` (extended): the per-tensor and block-scale rows against the exact fp32 reference, including grouped heads, windows, dgrad amax and the fp8 / half output dtypes.
- `test_sdpa_bwd_heuristics.py`, `test_sdpa_bwd_d128_dense_bounds.py`, `test_sdpa_bwd_d128_sm100.py`: placement, bounds and workspace sizing.
- The existing d128 accumulation, grouped, THD and dkv-accum suites pass on the merged tree.
- `SUPPORT_MATRIX_TRACKER.md` and the d128 backward API page record the new rows, the D64 route and the `(D + 1)` workspace formula.

**Align `DV_COL` and `DK_COL` with the TMEM layout the kernel uses.**

`make_config(d)` sets `DV_COL = 512 - 2 * d` and `DK_COL = 512 - d`. For `d == 64`, this gives 384 and 448.

The kernel in `bprop_d128_accum_f16.py` places the planes differently. `_mma_loop` uses `tmem_base + 256` for dV and `tmem_base + 256 + CFG.D` for dK. `_native_epilogue` reads the same columns. For D64 these are 256 and 320.

`validate_config` also asserts `256 + 2 * cfg.D <= cfg.TMEM_COLS`, which assumes the 256 base. Line 189 asserts `DK_COL + D == TMEM_COLS`, which assumes the other layout.

Nothing reads `DV_COL` or `DK_COL` for D64 today. The `dkv_accum` path is D128-only. The two assertions contradict each other, so `validate_config` cannot detect drift in the D64 plane placement.

Derive the columns from the kernel's layout, and relax the line 189 assertion to match. D128 values stay 256 and 384.
