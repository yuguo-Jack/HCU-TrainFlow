# norm(fprop): launch the warp LN / RMS forward through tvm-ffi

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2141) · state: closed · merged: True

## Original PR description

## Problem

On a B300, the warp-per-row LayerNorm / RMSNorm forward took about 90-250 µs of host time per call before any GPU work, depending on host load. The kernel is 2-45 µs at the shapes below. Two costs dominate a warm call:

- `dyn()` wraps each of the six operands with `from_dlpack(...).mark_layout_dynamic()` on every call. Under cProfile, `dyn()` was the largest single cost of a warm norm call (43% of a backward call).
- `cur_stream()` reads the stream through `torch.cuda.current_stream()`, which builds a torch `Stream` object (about 6 µs).

In eager use the forward is therefore host-bound at every shape measured.

## Change

- Both warp launches, persistent and pipelined, compile once with `--enable-tvm-ffi`, on fake operands whose row count is one `cute.sym_int` (the AGENTS.md "runtime extents compile DYNAMIC" rule). Each call passes the torch tensors directly, detached when they are on an autograd tape, as `dyn()` did. The compile key is unchanged and still free of the row count.
- `cur_stream()` reads the raw handle through the existing `cudnn._torch_stream._raw_current_stream`, falling back to `torch.cuda.current_stream()`. This also helps every other norm launch that calls it.
- New helpers in `norm/utils.py`: `ffi()` and `fake_rows()`.

The kernels are untouched. The other norm routes keep `dyn()`. The backward has a pending change in its file (#2139) and can follow the same pattern once that lands.

## Measurements (B300, cc 10.3)

Following the AGENTS.md host-overhead recipe, I measured warm enqueue and captured replay separately. Develop and this branch ran in separate processes, alternating, three times.

- **`cudnn.norm.norm_fprop`, warm enqueue.** 16 cases: LayerNorm / RMSNorm, bf16 / fp16, 333-8192 rows x 1024-8192 columns, gamma passed as a `requires_grad` parameter. The median per rep was 208 / 223 / 225 µs on develop and 56 / 60 / 60 µs on this branch. The host was shared, so the absolute numbers moved between sessions: an earlier session measured 88 against 22 µs.
- **Graph API with the FROST plan selected:** warm enqueue of `g.execute`, and per-execute GPU time of a captured CUDA graph of 20 executes (medians of three reps):

| norm | rows x C | develop enqueue µs | this branch enqueue µs | develop replay µs | this branch replay µs | replay ratio |
|---|---|---:|---:|---:|---:|---:|
| LayerNorm | 1024 x 1024 | 228 | 107 | 3.21 | 3.19 | 0.994 |
| LayerNorm | 4096 x 4096 | 231 | 111 | 10.82 | 10.78 | 0.996 |
| LayerNorm | 16384 x 4096 | 232 | 110 | 44.16 | 44.24 | 1.002 |
| LayerNorm | 2048 x 8192 | 230 | 110 | 11.75 | 11.77 | 1.002 |
| RMSNorm | 1024 x 1024 | 223 | 100 | 2.94 | 2.93 | 0.997 |
| RMSNorm | 4096 x 4096 | 226 | 105 | 7.75 | 7.76 | 1.001 |
| RMSNorm | 16384 x 4096 | 224 | 104 | 45.09 | 45.12 | 1.001 |
| RMSNorm | 2048 x 8192 | 226 | 105 | 8.82 | 8.78 | 0.995 |

The graph path keeps its own binding cost (`resolve_variant_pack`, `on_stream`), so it gains about 2x rather than 4x. Replay time is unchanged, within ±0.6%.

## Correctness

- **Bitwise identical to develop.** 216 output tensors (y, mean, rstd) across both entry points and all three reps match exactly.
- **CUDA graph capture.** Replay output equals eager output in every graph case.
- **New `test/python/norm/cutedsl/test_frost_norm_fwd_ffi_launch.py`:**
  - one artifact serves 1 / 300 / 4097 / 20000 rows on both warp launches, with no recompile;
  - `nn.Parameter` gamma / beta and a `requires_grad` input give results bitwise equal to the detached call;
  - a launch issued under a side stream lands on that stream, checked by a default-stream snapshot taken while the side stream is held.
- **Full `test/python/norm` on B300:** 1333 passed, 1 skipped. Develop gave 1329 passed, 1 skipped; the four extra passes are the new tests.
