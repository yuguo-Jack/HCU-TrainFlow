## Summary

- `sm120/compiler.py`: new `_check_int32_compute(chain)` raises `NotImplementedError` for an epilogue op whose
  `compute_dtype` is `int32` unless the shared emitter computes that op on Int32 vectors: `identity`, `relu`,
  `leaky_relu`, `abs`, `neg`, `add`, `sub`, `mul`, `max`, `min`, `add_square`, `binary_select`, `gen_index`,
  `aux_load`. It also raises it for an int32-compute op from that list whose output, aux or producing input is
  `fp8_e4m3`, `fp8_e5m2` or `fp8_e8m0`, which the epilogue cannot convert to or from Int32 (except the input of
  `gen_index`, which reads only that input's shape). It runs in `probe_chain` (so
  `FrostGemmEngine.check_support` and the planner see it) and in `jit_from_cudnn_graph` (the direct entry and
  `build_plan`), next to the existing `dtype_arch_reject` call.
- `epilogue_codegen.py`: `gen_index` that computes in int32 builds the index from the Int32 coordinate
  (`cutlass.Int32(row)`, an Int32 register tensor of `col_j + k`, and `cutlass.Int32(moe_scatter_row(...))` for the
  MoE SCATTER token axis) instead of going through `cutlass.Float32`. With fp32 compute the emitted source is
  unchanged.
- New SM120 tests for both parts, plus a host-only pin of the emitted `gen_index` code.

## Why

INT32 compute reaches the epilogue in two ways: the graph default of an int8 GEMM
(`pygraph(io_data_type=INT8, compute_data_type=INT32)`, the setup Frost's own int8 tests use), or a per-op
`compute_data_type=INT32` on any graph. `_compute_cast` turns the operands into Int32 vectors, but most emitters
use Float32-only CuTe DSL math, and nothing in the sm120 probe read `FusionOp.compute_dtype`. So
`check_support` accepted these graphs, FROST was the first plan, and `build_plans()` failed in `cute.compile`
with an exception that is not a decline type, which stops the walk before the native plans.

Minimal reproducer on an RTX PRO 6000 (SM120): int8 `A[1,128,128]` x int8 `B[1,128,128]` (K-major), graph compute
INT32, one pointwise op (binary ops take a per-column int32 aux `z`), int32 output, then the default
`create_execution_plans([A, FALLBACK])` + `build_plans()` + `execute()`:

| op (INT32 compute) | before: default `build_plans()`, FROST is plan 0 | native plan `eng10_k24=25`, FROST barred |
|---|---|---|
| `cmp_lt`, `cmp_eq`, `logical_not`, `floor` | `TypeError: floor is only supported for floating-point types` | exact |
| `ceil` | `TypeError: ceil is only supported for floating-point types` | exact |
| `mod` | `DSLRuntimeError` (invalid IR) | exact |
| `exp`, `sigmoid` | `TypeError: exp2 is only supported for floating-point types` | no plan |
| `pow` | `DSLRuntimeError` (invalid IR) | no plan |
| `div` | builds; 16327 of 16384 outputs wrong, e.g. `-1082130432` where `-1` is expected | exact |

"exact" means 0 of 16384 values differ from an integer reference.

For `div`, the emitter writes `a / b`; on Int32 vectors CuTe DSL 4.7.1 lowers `/` to `itofp` + `divf` while the
vector keeps its Int32 type, so the later `.to(Int32)` does nothing and the int32 output holds the bit pattern
of the fp32 quotient (`-1082130432` is `-1.0f`). The same happens on a BF16 graph with a per-op INT32 `div`.

`gen_index` with int32 compute and an int32 output also went through `cutlass.Float32(row)`, so indices above
2**24 were rounded: int8 `A[1, 2**24 + 64, 16]`, `B[1, 16, 4]`, `Y = C + gen_index(C, axis=1)` with `A == 0`
wrote row 16777217 as 16777216 (128 of the 512 values in the last 128 rows wrong).

Ops that have an int32 emitter (the list in the Summary) failed in the same way when they read or write fp8. The
epilogue converts an int32-compute op's inputs and result with a direct `.to()` between Int32 and the declared
dtype, and NVVM rejects the Int32 <-> Float8 casts (`sitofp <8 x i32> to <8 x i8>` for an fp8 output). With the
setup above, `add(C, z)` with an fp8_e4m3 or fp8_e5m2 output (int32 `z`), or `add` / `mul` / `max` with an
fp8_e4m3 `z` and an int32 output: `check_support` accepted, FROST was plan 0, and the default `build_plans()`
raised `CompilerDiagnosticError` ("NVVM backend compilation failed"), which is not a decline type; with FROST
barred, the native plan `eng10_k24=25` built and was exact. The same compile failure occurs with an fp8_e4m3
output for every op on the list except `gen_index` and `aux_load` (not tried), for `add` with an fp8 aux in each
broadcast mode (per-column, per-row, scalar, per-element), for a GEMM output typed fp8 feeding `add`, and for a
prior op's fp8 output used as the first or second operand of `add` or as the `binary_select` mask. With per-op
FP32 compute, each of these kinds of graph (fp8 output, fp8 aux, GEMM output typed fp8, fp8 operand, fp8 mask)
compiles.

Why this fix:

- Declining in the probe is the engine's contract for input it cannot compute (python/cudnn/AGENTS.md Rule 2 and
  R5): the default walk then reaches the native plan, which computes these ops exactly (verified above for
  `cmp_lt`, `floor`, `div`, `mod`), or the graph is reported as unsupported with `cudnnGraphNotSupportedError` when
  no engine computes it (int32 `exp`). The accepted set is what the shared emitter computes on Int32 vectors
  today: `identity`, `relu`, `abs`, `neg`, `add`, `sub`, `mul`, `max`, `min`, `add_square`, `binary_select` and
  `gen_index` were each built on FROST with INT32 compute on SM120, with int32 operands and an int32 output, and
  matched an integer reference (and the native plan where it has one). `relu` / `leaky_relu` with float
  attributes keep their current behaviour (the attributes are converted to int32, i.e. truncated); this cuDNN
  offers no native plan for those int8 graphs to compare with, and the audit did not count that as part of this
  defect. `aux_load` is listed because its emitter is a plain load into the compute dtype (the analyzer creates it
  with fp32 compute today).
- `div` is declined rather than re-emitted as a truncating integer division: that would change FROST numerics
  (and needs a decision on division by zero and `INT_MIN / -1`), while the native plan already computes it.
- fp8 is declined by the same check rather than converted through Float32 in the shared emitter (the mainloop
  transforms already take that detour for an int32 -> fp8 result): the decline stays inside the sm120 tree, and
  the native plan computed the fp8-output and fp8-aux graphs above exactly. The rule names the fp8 dtypes that
  reach this check on SM120 (`fp8_e5m3` is declined earlier by `dtype_arch_reject`). The input of `gen_index` is
  not checked: an int32 `gen_index` of a GEMM output typed fp8 compiles and is exact today (0 of 16384 values
  wrong on either axis), and it stays accepted. fp4 is not part of the rule: an fp4 aux compiles with either
  compute dtype, and a GEMM output typed fp4 fails to compile (`DSLRuntimeError`) with FP32 compute as well, so
  neither case is specific to INT32 compute.
- Mapping `TypeError` / DSL compile errors to `NotImplementedError` in `FrostGemmEngine.build_plan` (the audit's
  suggested backstop) is not part of this change: it cannot catch `div`, it lives in the engine shared by both
  arch trees, and it would turn real codegen or compiler bugs on every FROST graph into silent fallbacks.
- `gen_index` is fixed in the emitter rather than declined, because it is correct below 2**24 today and an int32
  index is exactly what int32 compute asks for. The emitter has lived in the shared
  `python/cudnn/gemm/frost/epilogue_codegen.py` since #1993, and there is no sm120 copy to change, so the fix is
  made there; it only changes the int32-compute form.

Found in an audit of the SM120 Frost kernel templates (finding G4.4).

## Related issues

cleanly with this branch (`git merge-tree` against their current heads):

  uint8 outputs.

## API and compatibility impact

- Newly declined on SM120: a graph with an epilogue op that computes in INT32 and is outside the list above, or
  that is on the list but reads or writes fp8 (its output, aux or producing input; not the input of
  `gen_index`). Before, `build_plans()` raised a non-decline exception for it, or, for `div`, FROST built and
  returned wrong values. Now FROST is not offered for it; the default walk uses the native engine where it has a
  plan, and raises `cudnnGraphNotSupportedError` where no engine has one.
- Changed numerics: `gen_index` that computes in INT32 is exact above 2**24 (it was rounded through fp32). Because
  the emitter is shared, this also applies to the SM100 tree.
- SM100: the missing int32 gate is the same in `python/cudnn/gemm/frost/sm100/compiler.py:2776` (`probe_chain`) and
  `:2841` (`jit_from_cudnn_graph`), which use the same shared emitters. That includes the fp8 case: compiled for
  sm_100a on this host (see Testing), an int32 `add` with an fp8_e4m3 output or an fp8_e4m3 aux fails with
  `CompilerDiagnosticError`, while the int32 control compiles. It is intentionally left for a follow-up (the repo
  convention lands such fixes in both trees).
- No change for fp32-compute graphs: their generated source is byte-identical.
