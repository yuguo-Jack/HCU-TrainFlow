# Fix grouped GLU + Hadamard compiled-object cache reuse across devices

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1813) · state: closed · merged: True

## Original PR description

## What

`grouped_gemm_glu_hadamard_wrapper_sm100` memoizes its compiled `GroupedGemmGluHadamardSm100` object in `_cache_of_GroupedGemmGluHadamardSm100Objects` under a key of shapes, dtypes, strides and tile options -- but not the operand device. The object retains `self.hadamard_tensor`, built once on the sample operands' device, and `execute()` passes it whenever the caller supplies no Hadamard matrix. A later call whose operands live on another GPU therefore reused the first device's object and failed inside the compiled call:

```
ValueError: Mismatched device index on argument #15 when calling __call__(a, b, sfa, sfb, ..., prob, hadamard, ...)
```

This PR adds `a_tensor.device` to the cache key, exactly as #1808 did for the grouped GLU and SwiGLU wrappers (the Hadamard sibling was left out there), so every device gets its own compiled object and its own Hadamard matrix. A cache miss also runs the support check and the compilation in the input device's context, so the cached workspace lives on that GPU even when another device is current.

## Why

The nightly CuTeDSL lane has been red on this with a different parameter each night, depending on which worker's device compiled first:

- `test/python/gemm/jax/test_grouped_gemm_canonical_jax.py::test_canonical_jax_glu_hadamard_parity[wrapper-nvfp4-geglu]`
- `test/python/gemm/jax/test_grouped_gemm_canonical_jax.py::test_canonical_jax_glu_hadamard_parity[wrapper-mxfp4-swiglu]` (the night before)

The JAX bridge lands its operands on whichever device the worker holds; with several GPUs per test process the cached object is the one operand on the wrong device.

## Test added

`test/python/gemm/cutedsl/test_grouped_gemm_glu_hadamard.py::test_grouped_gemm_glu_hadamard_wrapper_cache_separates_devices` (L0) mirrors the GLU detector from #1808: it compiles on two devices without clearing the shared cache, captures a CUDA graph per device on an explicit per-device stream, changes the inputs, and replays on first / other / first, comparing `c`, `d`, `amax` and `post_rht_amax` bitwise with eager runs. It skips without two SM100-class devices. Against the unfixed wrapper it fails with the CI error above.

## Verification

- Host: `python -m py_compile` on both files; `pre-commit run` (clang-format / black -l 160 / SPDX) clean.
- GPU, the follow-up (the device-context wrap): the detector 1 passed with two GPUs visible; a variant with the inputs on one GPU and the OTHER GPU current at the first call: the compiled object, its Hadamard matrix and its workspace all land on the input GPU and the later cache-hit call is bitwise identical; the module `-m L0` 32 passed.
- GPU, on a shared cc 10.7 development host (204 SMs) with two GPUs visible to the test process -- cuDNN backend 9.27, CuTe DSL 4.8.0, torch 2.14.1+cu130:
  - the new detector on this branch: 1 passed (53.7 s; both devices seen, no skip);
  - the same detector against the unfixed wrapper: 1 failed with `ValueError: Mismatched device index on argument #15` -- the CI error;
  - `test/python/gemm/cutedsl/test_grouped_gemm_glu_hadamard.py -m L0` on this branch with two GPUs visible: 32 passed, 0 failed, 0 skipped (90.9 s).
- Not run: the JAX cells of `test/python/gemm/jax/test_grouped_gemm_canonical_jax.py` (no `jax` on the GPU host used). The JAX bridge calls the same wrapper and the same cache that the torch detector exercises.
