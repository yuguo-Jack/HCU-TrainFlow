## Summary

On SM120, AMAX, MAX and MIN reductions (fp32 compute) now skip NaN elements on every code path. This is the native cuDNN engines' behaviour.

- **NaN replacement.** The new helper `_nan_to_identity` emits `cutlass.select_(x == x, x, identity)`. It replaces a NaN with the reduction's identity before the value reaches a register fold or an atomic. The identities are 0 for AMAX, -inf for MAX and +inf for MIN, the same values the outputs are seeded with.
- **Chunk-folded paths.** `_emit_reduction_chunk_combine` wraps the shared `_emit_reduction_local_combine` and applies the helper to the folded chunk. The register partials (scalar, per-batch, per-expert), the per-chunk atomics (reductions that drop N) and the lane-run row folds now use it.
- **Per-element paths.** The per-element atomics (reductions that keep N) and the lane-run column folds apply the helper to each element.

After this change, the butterflies, lane scatters and flush atomics only see NaN-free values. ADD, AVG, NORM1, NORM2, MUL, MUL_NO_ZEROS and int32 reductions are unchanged. The two new tests cover dense with and without split-K, and MoE in both orientations at `first_token_offset` alignment 1 and 8.

## Why

The SM120 reduction paths had no common NaN policy:

| path (24a8cd43) | used for | NaN element |
|---|---|---|
| per-element atomics: `atomic_fmax(\|v\|, sign_bit=False)`, `atomic_fmax(v)`, bit-pattern MIN | reductions that keep the kernel's N axis: dense per-column under split-K; MoE per-feature (normal plan) and per-token (swap-AB plan) | AMAX kept it; MAX kept it when the sign bit was clear; MIN kept it when the sign bit was set |
| `maxnumf` chunk fold, then one atomic | reductions that drop the kernel's N axis: dense scalar and per-row under split-K; MoE per-token (normal) and per-feature (swap-AB) | dropped, unless the whole chunk was NaN |
| register partials and lane-run folds (seeded 0 / -inf / +inf, `maxnumf`) | dense scalar, per-row and per-column without split-K; MoE scalar and per-expert | dropped; for AMAX an all-NaN chunk can poison the slot (next paragraph) |

`fusion_ir.swap_ab` transposes `red.dim`, the swap-AB chunk width follows the declared `first_token_offset` alignment, and split-K moves the dense epilogue into the reducer. So a knob decided whether a graph reported NaN.

The lane-run folds also have a compiler problem. The first fold of an AMAX slot is `max(0.0 seed, |x|)`. The PTX still has that clamp (`setp.ge` + `selp`), but the ptxas bundled with CuTe DSL 4.7.1 (CUDA 13.3, V13.3.27, compiling for sm_120a; the PTX header and the cubin both name it) emits no SASS instruction for it. A chunk that is entirely NaN therefore leaves the slot NaN. The next fold compiles to `FSETP.GTU` + `FSEL`, which keeps the NaN, so the chunks that lane folds after it are lost. The cross-lane flush (a `maxnumf` butterfly) then drops that lane's NaN slot whenever another lane's slot is not NaN, and with it those later chunks. Per-row and per-column AMAX therefore come out finite, but below the NaN-free maximum.

**Minimal reproducer.** These are the new tests. A bf16 MoE GEMM with E = 2, S = N = K = 64, groups [0, 24, 64] and `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`; the table is for `first_token_offset` alignment 8. Token 5 holds one NaN, so its row of C is NaN. Expert 1's weight row 9 holds one NaN, so feature 9 is NaN for tokens 24..63.

| reduction | on 24a8cd43, normal plan | on 24a8cd43, swap-AB plan | with this PR (both plans) |
|---|---|---|---|
| AMAX per feature (1, 1, 64) | 64 / 64 outputs NaN | 1 / 64 NaN (feature 9, whose 8-token chunks are all NaN) | max of the non-NaN elements |
| AMAX per token (1, 64, 1) | 1 / 64 NaN (token 5) | 41 / 64 NaN | max of the non-NaN elements |

With alignment 1, which the test also runs, the swap-AB plan uses 1-token chunks, and per-feature AMAX is NaN for all 64 features again. The normal plan compiles to the same kernel at both alignments and gives the same results. On the dense template (128 x 128 x 256), C has NaN in row 5 and in columns 0..7:

- **Without split-K:** per-row AMAX gives row 5 NaN, and 10 rows are finite but below the NaN-free maximum. Per-column AMAX gives 8 NaN columns and one column below the NaN-free maximum.
- **With split-K 2:** on C, AMAX and MAX are NaN for every set that contains a NaN.
- **`neg(C)`:** the sign bit of the NaN that reaches the atomic depends on the path. Where an 8-element chunk is folded first (split-K scalar and per-row; MoE per-token on the normal plan and per-feature on the swap-AB plan at alignment 8), it is set, so MIN reports an all-NaN chunk and MAX drops it. On the per-element atomics, and on the swap-AB plan's 1-token chunks at alignment 1, it is clear, so MAX reports NaN (split-K `neg max (1, 1, 128)`: 128 NaN cells; MoE normal plan `neg max (1, 1, 64)`: 64) and MIN drops it.

**Why skip NaN rather than propagate it.** The audit suggested `propagate_nan=True` in the folds "so every path matches atomic_fmax", or one documented policy applied on every path. I took the second option, with the skip policy, for these reasons:

- **Native cuDNN skips NaN.** I ran native cuDNN 9.24 on the same GPU: a dense matmul plus one reduction (AMAX / MAX / MIN at scalar, per-row and per-column), with a NaN row or a NaN column in C. None of the 18 results is NaN: a set with a finite element gives the max / min of its non-NaN elements, and an all-NaN set gives 0 (AMAX), -FLT_MAX (MAX) or +FLT_MAX (MIN). Backend and FROST share one graph contract (python/cudnn/AGENTS.md Rule 9). The reduction node has no NaN-propagation attribute, unlike RELU_FWD, which the frontend creates with CUDNN_PROPAGATE_NAN.
- **Most FROST paths already skip NaN.** Propagating would change the common paths (scalar AMAX partials, MAX / MIN folds) to disagree with the backend on every NaN-containing reduction.
- **`minimumf` alone breaks MIN.** It produces the canonical NaN 0x7FFFFFFF, which the bit-pattern MIN atomic drops. A chunk containing one NaN would then lose its finite values unless the atomics were also rewritten.

The companion change for audit finding G4.2 follows native cuDNN in the same way: relu propagates NaN because native eng10 does.

**Why an explicit select.** The select tests `x == x`, which compiles to `FSETP.NAN` + `FSEL`. It does not rely on `maxnumf` surviving ptxas, and it does not depend on the NaN's sign bit.

**Scope.** Every changed source line is in `python/cudnn/gemm/frost/sm120/epilogue_codegen.py`. The shared `_emit_reduction_local_combine` in `python/cudnn/gemm/frost/epilogue_codegen.py` is wrapped, not modified, so the sm100 tree's generated code does not change.

Found in an audit of the SM120 FROST GEMM kernel templates (finding B15).

## API and compatibility impact

- **Numerics (SM120 FROST plans only):**
  - For AMAX / MAX / MIN reductions with fp32 compute, NaN elements no longer contribute on any path. Outputs that were NaN on some paths become the max / min of the non-NaN elements.
  - The lane-run AMAX outputs that came out finite but too small become correct.
  - For inputs without NaN (±inf included), the select passes each value through as is and the fold and atomic code after it is unchanged, so the result is the same.
  - Other reduction modes and int32 reductions are unchanged.
- **Remaining difference from native:** a set whose elements are all NaN returns the output seed: 0 for AMAX, -inf for MAX, +inf for MIN. Native cuDNN 9.24 returns 0, -FLT_MAX and +FLT_MAX there. That is the seed value, not NaN handling, and is not changed here.
- **SM100:** `python/cudnn/gemm/frost/sm100/epilogue_codegen.py` has the same defect:
  - `:140-163`: the chunk fold through the shared `epilogue_codegen.py:654-676`, then `atomic_fmax` keeps the NaN of an all-NaN chunk.
  - `:201-202`: the per-element AMAX atomic keeps NaN.
  - `:233-234`: the per-element MAX keeps sign-clear NaN.
  - `:236-247`: the per-element MIN keeps sign-set NaN.

  The repo convention is that a fix lands in both trees. The SM100 copy is intentionally left for a follow-up, because this PR is scoped to the SM120 tree and I have no SM100 hardware to verify it on.
- **Kernel caches:** the generated source changes for graphs with AMAX / MAX / MIN reductions, so their cached kernels are rebuilt once.
- **Performance:** not measured; the GPUs here are shared. The cost is one `FSETP` + `FSEL` per folded chunk, and one per element on the per-element atomics and lane-run column folds.
- **API and DSL:** none. `cutlass.select_` and Float32 comparisons are already used by this codegen, so no CuTe DSL version gate changes (Rule 7).
- **FlashInfer:** its shipped SM120 kernels contain no reductions.
