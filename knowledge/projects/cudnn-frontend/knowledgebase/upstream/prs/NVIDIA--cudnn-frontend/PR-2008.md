## Summary

The SM120 FROST GEMM engine now declines a block-scaled GEMM whose K is not a multiple of the scale block size. Before this change it planned and ran such a GEMM whenever the 16-byte TMA rule admitted the K. That covers MXFP8 and one-sided FP8 x MXFP8 graphs, except GATHER graphs that carry a token scale tensor. The usual scale-factor blob holds `ceil(K / 32)` scales; that is the layout the native engine reads. With such a blob, FROST returned wrong numbers when the partial block needed one more 512-byte scale-factor atom per 128-row block than the kernel's view holds (K mod 128 in 1..31 for block 32). The other partial-block K (K mod 128 in 33..127) computed correctly with such a blob. This PR declines them as well (see "API and compatibility impact").

- Build time: `_precheck_block_scale` and `_precheck_moe_block_scale` call a new `_check_whole_scale_blocks(chain)`, which raises `NotImplementedError`. `check_support` therefore declines, and another engine can take the graph if one supports it. In the MoE precheck the new check runs before `mma_arch_reject`. Without that ordering, a GATHER graph would be declined with the GATHER token-SF message, which asks for `floor(K / block)` columns even though the analyzer requires `ceil(K / block)`. That placement also puts it before the MoE precheck's TMA alignment check, which changes the decline reason for some MoE graphs that were already declined.
- Per call: the kernels take K from the bound tensors, so a plan built for a whole-block K can still be called with a partial-block K. Two launch paths now refuse such a call with `ValueError` before any launch or output write:
  - the dense path (`_CompiledFusedGemm._lower` / `explain`; the fast-path refusal is counted as `"partial scale block"`);
  - the MoE block-scale path (`_CompiledMoeBlockScaleGemm._call_variant_pack`).

  Both checks sit behind a new class flag, `_validate_whole_scale_blocks`. It defaults to off, and only the SM120 `CompiledFusedGemm` and `CompiledMoeBlockScaleGemm` turn it on.
- A new shared helper, `_partial_scale_block_reject(K, block_size)`, holds the reason text. It is exported like `_tma_alignment_reject`.
- No kernel template changes.

Revision (1adac04a, tests only): the two per-call tests check the refusal by its effect (`ValueError`, no launch, output untouched, a message that names the problem) instead of by which guard fired. With #2016 (B29) applied as well, #2016's execute-time check refuses the dense test call first, in its own words (see Related issues).

## Why

Found in an audit of the SM120 Frost kernel templates (finding B01).

All three SM120 block-scale templates build the F8_128x4 scale-factor TMA view from `rest_k = ((K // block_size) + 3) // 4` atoms per 128-row block, that is, from `floor(K / block_size)` scales:

- `sm120_block_scale_matmul.py:810`
- `sm120_moe_grouped_block_scale_matmul_fwd.py:1094`
- `sm120_moe_grouped_block_scale_matmul_fwd_swap_ab.py:1087`

They use `512 * rest_k` bytes as the 128-row block pitch. The K loop, however, runs `ceil(K / 128)` tiles and loads SF atom `k_tile_idx`. The runtime blob checks use the same floor and only enforce a minimum size: the dense `k4` and MoE `_sf_k4` in `compiler.py`, and `recipe._sf_blob_reject`.

Before this change, the only K gate was the 16-byte TMA rule: K % 16 for a K-major fp8 operand, and no K rule at all for dense M-major A with N-major B. The one exception is the GATHER token-SF checks described under "API and compatibility impact". MXFP8 graphs, and one-sided FP8 x MXFP8 graphs, with a partial last scale block therefore planned and ran. When K mod 128 is in 1..31, `ceil(K / 32)` scales need one more 512-byte atom per 128-row block than the view holds. Two things then go wrong:

- The last K tile's SF box lies past the view, and TMA fills it with zeros (E8M0 0x00 = 2^-127). The tail's K elements are lost.
- The SF blob is laid out for `ceil(K / 32)` scales. That is the layout the backend tests declare (`k_scale = ((K + BLOCK_SIZE - 1) // BLOCK_SIZE + 3) // 4 * 4` in `test/python/gemm/graph/test_low_precision_matmul.py`) and the layout the backend reads. With the view's shorter pitch, every 128-row SF block after the first is read at the wrong offset.

When K mod 128 is in 33..127, the partial block's scale falls inside the last atom the view already holds, and with a `ceil(K / 32)` blob the result is correct.

Reproducer on SM120 with `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`:

- Inputs: e4m3 data, E8M0 scales with block 32, `ceil(K/32)` scales per row packed with `to_blocked`.
- Reference: float64 dequant. An output counts as wrong when it is off by more than 0.2 + 2%.

| Case | Wrong outputs on develop 24a8cd43 |
|---|---|
| Dense M = N = 256, K = 144 | 54025 of 65536 (max error 26.8, mean \|ref\| 2.8) |
| Dense K = 160, K = 176 and K = 208 | 0 |
| MoE NONE, E = 2, S = N = 256, groups [0, 128, 256], K = 144, normal and swap-AB | 53917 of 65536 |
| MoE NONE, same setup, K = 160 and K = 176, normal and swap-AB | 0 |

Through the public graph API (`CUDNN_FRONTEND_ENABLE_FROST_ENGINES=1`, `validate` / `build_operation_graph` / `create_execution_plans` / `check_support` / `build_plans` / `execute`):

- On develop, `frost_gemm` is selected for the K = 144 dense graph and returns the same 54025 wrong outputs.
- On this branch FROST declines, the native engine (cuDNN 9.24) serves the graph, and 0 of 65536 outputs are wrong.
- K = 160 is still served by `frost_gemm`, with 0 wrong.
- The MXFP8 MoE NONE graph above has no other engine on SM120. The native engine fails to build it with `CUDNN_STATUS_BAD_PARAM`, even at K = 160. On develop `frost_gemm` is selected at K = 144 and at K = 176. On this branch both raise `cudnnGraphNotSupportedError` at plan time, and K = 160 is still served by `frost_gemm`.

Why a decline rather than sizing the view from `ceil(K / block_size)`: the audit left both options open, and this PR takes the conservative one.

- Serving partial blocks would mean changing the scale indexing of three kernel templates and the two GATHER SF descriptors.
- It would also mean changing the runtime blob and GATHER-SF checks, which the SM100 tree shares and which would then disagree with the SM100 templates (those still use floor).
- It would newly admit GATHER graphs that are declined today.

The decline changes no kernel and no numerics for any K that keeps running. The native engine serves the declined dense K = 144 graph above, but no engine serves the declined MXFP8 MoE NONE graphs on SM120. Only MXFP8 and one-sided FP8 x MXFP8 graphs are newly declined, because an fp4 operand already needs K % 32 for TMA. For some MoE graphs that were already declined, only the reason changes. FlashInfer's FROST MoE path requires K % 128 and is not affected.

### Why the shared compiler changes

Since #1993, the per-call launch paths (`_CompiledFusedGemm._lower` / `explain` and `_CompiledMoeBlockScaleGemm._call_variant_pack`) live in the shared `python/cudnn/gemm/frost/compiler.py`. The refusal has to come before any write, and in both paths that point is in the shared code:

- The dense fast path computes K inside the shared `lowered` closure and seeds the reduction outputs there, before it calls the family's compiled launchable.
- In the MoE path, the check sits next to the shared SF-blob checks, ahead of the dispatch. One site therefore covers the normal, swap-AB, multi-GEMM and GATHER launches before any write. The SM120 tree's `_launch_moe_swap_ab` also receives the call's K, but it serves only swap-AB. It also runs after the shared GATHER token-SF check, which would refuse a `ceil(K / 32)`-column token SF with the misleading floor-shape message.

The guard sits behind an opt-in class flag. This follows the existing `_validate_runtime_quant` / `_validate_combine` pattern, so the SM100 executors keep their current behaviour.

## API and compatibility impact

- **Newly declined on SM120 (graph time):** block-scale GEMM graphs whose K is not a multiple of the scale block size and that develop planned. These are MXFP8 or one-sided FP8 x MXFP8 graphs with K % 32 != 0 that pass the 16-byte TMA rule: K % 32 == 16 for K-major operands, or any K % 32 != 0 for dense M-major A with N-major B. They are:
  - dense, both orientations;
  - MoE NONE, SCATTER and COMBINE, both orientations;
  - MoE GATHER with a raw FP8 token and an MXFP8 weight, both orientations. Develop planned this graph, and at K = 144 it returned 29117 of 33152 wrong outputs.

  A direct `jit_from_cudnn_graph` caller gets `NotImplementedError`. With the FROST engines enabled, a declined graph goes to another engine if one supports it. The native engine serves the dense K = 144 graph (see "Why"). It does not build an MXFP8 MoE NONE graph on SM120 at all (cuDNN 9.24: `CUDNN_STATUS_BAD_PARAM`, even at K = 160), so such a graph now fails at plan time with `cudnnGraphNotSupportedError`. The other MoE modes were not checked against the native engine.
- **MoE GATHER with a token scale tensor, graph time:** already declined on develop; only the reason changes.
  - A linear token SF with `ceil(K / 32)` columns got `MoE GATHER token SF must have shape [1, 137, 4]`, which names `floor(K / 32)` columns. It now gets this PR's reason.
  - A token SF with `floor(K / 32)` columns still fails the analyzer's `MoE GATHER linear scale shape must be (1, 137, 5)`.
- **Newly refused per call:** a call whose K ends inside a scale block, bound to a plan built for a whole-block K, gets `ValueError` before any write. This covers the dense path and every MoE block-scale mode, GATHER included. On develop such calls ran. For GATHER that held when the linear token SF had the `floor(K / 32)` columns its per-call check asks for. A `ceil(K / 32)`-column token SF was refused, with the misleading shape message above.
- **K mod 128 in 33..127 (e.g. K = 176, 208) is declined too, although it computed correctly.** There the partial block's scale fits in the last atom the view holds:
  - With a `ceil(K / 32)` blob, develop's FROST results were correct: dense K = 176 and K = 208, and MoE NONE K = 176 in both orientations, all gave 0 of 65536 wrong.
  - With a `floor(K / 32)` blob, the tail block has no scale of its own. FROST and the native engine both dropped the tail: dense K = 176 and K = 208 gave 0 of 65536 wrong for both, against the first 160 / 192 K.

  So these K had no FROST-specific error. They are declined only to keep one rule, K % block_size == 0, on every block-scale path. GATHER with a token scale tensor needs that rule, because its linear token-SF TMA descriptors and its token-SF checks count `floor(K / block_size)` columns. The native engine builds and runs the dense K = 176 and K = 208 graphs. The MoE NONE graph at K = 176 now has no engine on SM120.

  A narrower rule would keep them on FROST: decline only the K whose `floor` and `ceil` atom counts differ (`K % block_size != 0 and (K // block_size) % 4 == 0`) on the F8_128x4 paths, and keep the full rule for GATHER with a token scale tensor. This PR does not do that.
- **Decline reason changes for some MoE graphs that were already declined:** the new check runs before the MoE precheck's TMA alignment check. A MoE block-scale graph whose K breaks both rules now gets this `NotImplementedError` instead of the TMA `ValueError`. That covers MXFP4 and mixed fp4 x fp8 graphs with K % 32 != 0 (e.g. K = 144), and any MoE block-scale graph with K % 16 != 0 (e.g. MXFP8, MXFP4 or NVFP4 at K = 136). The engine declines either way, but a direct `jit_from_cudnn_graph` caller sees a different exception type. Dense graphs whose K breaks both rules keep the TMA `ValueError`, because the dense precheck runs the TMA check first. So do MoE NVFP4 graphs with K % 32 != 0 but K % 16 == 0 (e.g. K = 144).
- **Unchanged:** acceptance and numerics for K % block_size == 0; which NVFP4, MXFP4 and mixed fp4 x fp8 graphs are accepted; plain GEMMs; FlashInfer's exported kernels.
- **SM100:** the SM100 tree has the same floor sizing and no K % block_size gate (static reading, not run on SM100 hardware):
  - `rest_k` floor in `sm100/kernel_templates/sm100_block_scale_matmul.py:1590`, `sm100/kernel_templates/sm103_block_scale_matmul.py:1540`, `sm100/kernel_templates/sm100_moe_grouped_block_scale_matmul_fwd.py:2068` (also `:766` and `:2081`), and `sm100/kernel_templates/sm100_moe_grouped_block_scale_matmul_fwd_swap_ab.py:2060` (also `:759` and `:2098`);
  - no K % block_size gate in `sm100/compiler.py` `_precheck_block_scale` (`:2688`) or `_precheck_moe_block_scale` (`:2716`).

  The repo convention is to fix both trees. This PR intentionally leaves the SM100 copy for a follow-up: the SM100 executors keep `_validate_whole_scale_blocks` off, so SM100 behaviour does not change. The follow-up is to call the shared helper from the two SM100 prechecks and set the flag on SM100's `CompiledFusedGemm` and `CompiledMoeBlockScaleGemm`.
