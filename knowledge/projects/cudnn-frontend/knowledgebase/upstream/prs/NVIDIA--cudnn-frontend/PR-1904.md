# Fix grouped quant cache reuse across CUDA devices

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1904) · state: closed · merged: True

## Original PR description

Grouped quant can reuse a compiled kernel and workspace from another CUDA device. The inner cache keyed the GPU family but omitted the device, even though the outer memo included it.

## Affected area

FE OSS kernels or CuTeDSL: grouped quant GEMM.

## Summary

Include `a_tensor.device` in the shared dense/discrete compiled-object cache key. Add a regression that alternates two devices, checks workspace placement before launch, and compares outputs.

## Why

On SM107, the four `test_canonical_jax_quant_fp4` cases fail when run together. The first Torch NVFP4 reference runs on GPU 3; after JAX initialization, the later reference runs on GPU 0 but retrieves the GPU 3 plan. CUDA rejects the launch with `cudaErrorInvalidValue`.

## Related issues

Same cache boundary as #1813, applied to grouped quant.

## API and compatibility impact

No public API change. Cached plans remain specific to their operand device.

## Testing

Native ARM64 SM107, CuTeDSL 4.8.0, CUDA driver 620.62. Commands run from `test/python`.

- Before the fix: `pytest -s -q gemm/jax/test_grouped_gemm_canonical_jax.py -k canonical_jax_quant_fp4` — 1 failed, 3 passed.
- New cross-device regression: fails before the fix, passes after it. Its guard catches the foreign workspace before an invalid GPU launch.
- After the fix: `pytest -n 1 -q gemm/cutedsl/test_grouped_gemm_quant_canonical.py gemm/jax/test_grouped_gemm_canonical_jax.py` — **245 passed**.
