# test(sdpa) + fix(gated_attention_block): re-record the two sm107 d256 rendering pins that #1547 moved; the cache-write launcher pins every operand to one CUDA device

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1730) · state: closed · merged: True

## Original PR description

Two small FROST cleanups, one commit each.

## 1. `test(sdpa)`: re-record the two sm107 d256 rendering pins that #1547 moved

### Symptom

On `develop`, two rendering-md5 pins in `test/python/sdpa/frost/test_sdpa_fwd_dsl_sm107.py` fail wherever `nvidia-cutlass-dsl` 4.8.0 knows `sm_107a` (they trace-compile on the host, no GPU needed):

* `test_sm107_thd_gate_descriptor_leaves_the_dense_gated_and_ungated_thd_cubins_byte_identical` (`_THD_GATE_CUBIN_RECORD`): `dense_gated_bf16_lse` renders `fde505d0...`, the record says `50657ada...`
* `test_shared_d256_body_gate_seams_leave_every_ungated_rendering_byte_identical_on_both_archs` (`_PAGED_GATE_CUBIN_RECORD`): `sm_100a_dense` `dc698e8b... -> 7db6daaf...`, `sm_107a_dense` `b4af8e7d... -> 63d9b3ef...`

### Cause

#1547 (`bdf93dbb3`) changed the shared d256 f16 prefill body on the dense CLC path (one scheduler publisher, `read_tile_id_arrive_on_leader`, under `not CFG.THD_VARLEN`) and re-recorded only the d512 renderings. The two pins here exist so that a HOST-side feature (the THD gate descriptor, the paged gate seams) cannot move the body unnoticed; a deliberate body change re-records them.

### Attribution (measured, not inferred)

With the tests' own probes (host trace-compiles, DSL 4.8.0): at `bdf93dbb3~1` all five arms of interest render their recorded md5s; at `bdf93dbb3` exactly the three dense arms render the new ones, and those equal what `develop` renders today -- no later commit moved them again. Every THD / paged / gated arm (the ten other keys) still renders its record, as the `THD_VARLEN` guard predicts.

### Change

The three md5s, re-recorded under the same DSL, plus one provenance comment per record. Test-only.

## 2. `fix(gated_attention_block)`: the cache-write launcher pins every operand to `src_a`'s CUDA device

### Symptom

`run_cache_write` validated dtype, rank, extents, strides and alignment but never the device: `check_pool` / `check_slot_mapping` were called without their `device=` argument. A CPU `slot_mapping` -- a serving stack's `torch.tensor(slots, dtype=torch.int32)` with no `device=` -- passed every launcher check and reached the compiled call. The served route was already guarded (the block's execute preflight pins the pools and the slot mapping to the plan's device through the same helpers); the gap was the launcher's standalone contract, which the kernel tests and downstream launchers use directly.

### Change

The launcher requires `src_a.is_cuda`, `src_b` on `src_a`'s device, and passes `src_a.device` to `check_pool` (both pools) and `check_slot_mapping` -- the helpers' existing parameter and messages (`<name> must live on <device>, got cpu`). `is_cuda` alone cannot tell a tensor on another GPU from a local one, hence the comparison by device. Host attributes only: nothing is read back from the device (Rule 3), and the check raises `ValueError` by name instead of converting (Rule 1).

### Test

Four refusals appended to `test_block_serving_extend.py::test_kernel_runner_refuses_a_mismatched_binding` (L0, any GPU): CPU `slot_mapping`, CPU `pool_b`, CPU `src_b`, CPU `src_a`.
