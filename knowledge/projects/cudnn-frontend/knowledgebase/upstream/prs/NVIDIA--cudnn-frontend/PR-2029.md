## Summary

The rejections a MoE plan raises when it is called now name each operand in the graph's terms in both kernel orientations:

- `_CompiledMoeGemm._call_variant_pack` and `_CompiledMoeBlockScaleGemm._call_variant_pack` compute `a_role, b_role = ("weight", "token") if isinstance(self.chain.moe, backend.MoeSwapAbSpec) else ("token", "weight")` once. This is the same expression that `_mixed_width_operand_reject` and `_check_moe_combine_operands` in `sm120/compiler.py` already use. The roles label:
  - the 16-byte base-address check of the data operands (both classes);
  - the 32-byte padded-e2m1 (`.b4x16_p64`) check, which only the SM120 block-scale class runs;
  - the scale-factor alignment entries, which change from the kernel-frame `SFA` / `SFB` to `token SF` / `weight SF`. These are the names the scale-factor blob checks a few lines further down already use (`token SF[i]`, `weight SF[j]`).
- `_resolve_moe_variant_pack` reports a scale-factor buffer missing from the variant pack as `token SF` / `weight SF`, instead of `SFA` / `SFB`, in both orientations.
- The swap-AB branch of `_resolve_moe_variant_pack` now passes the two operands to the runtime TMA extent check (`_tma_alignment_reject`) in graph order, with their graph majors and extents. Its message (`TMA input contiguous dimensions must be 16-byte aligned: ...`) then names `A` (the token) and `B` (the weight) with the graph's majors and `M` / `N`, word for word as the normal plan does. Before, it called kernel A `A`, and under swap-AB kernel A is the weight. `_tma_alignment_reject` and its dense callers are unchanged.

Only message text changes. Every check still applies the same requirement to the same buffer.

## Why

A swap-AB MoE plan computes the transposed product: `_resolve_moe_variant_pack` binds the weights as kernel A and the tokens as kernel B. The two `_call_variant_pack` methods still labelled kernel A `"token"` and kernel B `"weight"`, so every swap-AB rejection named the other operand. They also labelled the scale factors in kernel frame, where `SFA` is the weight's scale under swap-AB but the token's scale otherwise. The runtime TMA extent check in the swap branch of `_resolve_moe_variant_pack` printed kernel-frame names as well: `A` for the weight, and `m-major` / `M` for the extent of an N-major weight.

Minimal reproducer on SM120 (RTX PRO 6000), at develop 24a8cd43:

- Grouped mixed MXFP8 x MXFP4 block-scale GEMM: E = 2, S = 256, N = 128, K = 256, fp8 token, fp4 weight. It is planned with `jit_from_cudnn_graph(graph, config=replace(by_name("CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2"), swap_ab=True), padded_e2m1=True)`, and the fp4 weight is bound 16 bytes past a 32-byte aligned allocation.
  - Observed: `padded e2m1 operands (TMA .b4x16_p64) need a 32-byte aligned base address and 32-byte aligned strides: token: base address 0x... is 16-byte aligned`.
  - Expected: `weight: base address ...`.
  - With an fp4 token and an fp8 weight, a misaligned token is reported as `weight`.
- Any swap-AB MoE plan, BF16 or block-scaled, with one operand 8 bytes past a 16-byte boundary (`runtime tensor alignment is below the kernel's compiled requirement: ...`):
  - a misaligned token is reported as `weight: alignment 8B < required 16B`, and a misaligned weight as `token: ...`;
  - a misaligned weight scale is reported as `SFA: ...`, and a misaligned token scale as `SFB: ...`.
- Any swap-AB MoE plan called with an operand extent that breaks the 16-byte TMA rule (`TMA input contiguous dimensions must be 16-byte aligned: ...`):
  - the same mixed MXFP8 token x MXFP4 weight graph, called with K = 48 (packed fp4 needs K % 32): the normal plan reports `B (k-major, fp4_e2m1) requires K % 32 == 0, got K=48`, the swap-AB plan `A (k-major, fp4_e2m1) requires K % 32 == 0, got K=48`;
  - an MXFP8 graph with an N-major weight, called with N = 136: the normal plan reports `B (n-major, fp8_e4m3) requires N % 16 == 0, got N=136`, the swap-AB plan `A (m-major, fp8_e4m3) requires M % 16 == 0, got M=136`.

The kernel itself was never at risk; the bad buffer is still refused before launch. The wrong name sends the caller to fix the wrong tensor. The existing test only matched `32-byte aligned`, so it did not catch this.

The fix derives the label from the plan's orientation at the one place each list is built, as the existing role-aware rejections do. For the TMA extent check, the swap branch hands `_tma_alignment_reject` the operands in graph order instead, so both orientations produce the same text. No new helper or export was needed.

Why the change is outside `python/cudnn/gemm/frost/sm120/`: at 24a8cd43 the defective code exists only in the shared `python/cudnn/gemm/frost/compiler.py`, which #1993 moved it into from `sm120/compiler.py`. The SM120 `CompiledMoeGemm` and `CompiledMoeBlockScaleGemm` classes only set class flags; they inherit `_call_variant_pack` and use the shared resolver. Fixing it in `sm120/` would mean copying both methods (about 140 lines) into the SM120 classes and would leave the shared copy wrong.

Found in an audit of the SM120 FROST kernel templates (finding B39). The audit listed the block-scale swap-AB template. Its review added the non-block-scale swap-AB template and the `SFA` / `SFB` labels. The missing-buffer label in `_resolve_moe_variant_pack` is the same defect on the same call path, so it is included here. PR review found the TMA extent message in the same function; the second commit fixes it.

## API and compatibility impact

- **Error messages only:** `ValueError` / `KeyError` text of rejected MoE calls. No graph or call is newly accepted or declined, and the checks and their order are unchanged.
  - In the swap-AB orientation, `token` and `weight` now name the right operand.
  - In both orientations, the scale-factor entries read `token SF` / `weight SF` instead of `SFA` / `SFB`, for both the alignment message and the missing-buffer `KeyError`.
  - In the swap-AB orientation, the TMA extent message reads as the normal plan's for the same graph and buffers: `A` is the token and `B` the weight, with the graph's majors and `M` / `N`. When both operands fail, the token's entry now comes first.
- **Where it applies:**
  - The 16-byte alignment messages (data operands and scale factors) and the TMA extent message appear on direct `jit_from_cudnn_graph` plan calls and on `graph.execute` through the FROST engine (MoE plans have no lowered launcher, so the engine calls the plan's `_call_variant_pack`).
  - The padded-e2m1 message appears only on plans built directly with `jit_from_cudnn_graph(..., padded_e2m1=True)`. `padded_e2m1` is a keyword of the SM120 `jit_from_cudnn_graph` only. The engine's `build_gemm_plan` calls `jit_from_cudnn_graph(graph, config=config)` without it, and no knob or graph attribute sets `block_scale.padded_e2m1`, so the engine never opts in.
  - The missing-buffer `KeyError` appears only on direct plan calls: `graph.execute` stops first with the native variant pack's `variant-pack operand N was not filled by the caller`.
- **Not changed:** the plan-time check of the graph-declared extents, `_check_input_alignment` in `sm120/compiler.py` (an identical copy is in `sm100/compiler.py`), runs on the swapped chain of every swap-AB plan, dense or MoE, and still names kernel A / B. `jit_from_cudnn_graph` declines a BF16 MoE graph whose N-major weight has N = 132 with `A (m-major, bf16) requires M % 8 == 0, got M=132` under swap-AB, and with `B (n-major, bf16) requires N % 8 == 0, got N=132` otherwise. It is per-family code that dense plans share, so it is left for a follow-up.
- **SM100:** the sm100 tree inherits the same shared methods, so its swap-AB messages change in the same way. There is no separate SM100 copy of the changed code needing a follow-up. The padded-e2m1 check runs only on SM120 (`_check_padded_operands`). The new host-side tests run the sm100 family's real plan classes on this SM120 host without launching anything.
- **Hot path:** one `isinstance` per call, the label strings, and in the swap-AB branch two string comparisons that give the graph majors. No allocation, conversion or device access (Rule 1).
- **Performance and kernels:** the generated kernel source is unchanged (the same `gen_<digest>` sources); the edited code runs at call time, after rendering. As with any edit to the package, the persistent compiled-plan cache (`python/cudnn/frost/compiled_cache.py`) stores its entries under a digest of the environment manifest, which includes a digest of every `.py` file in the installed `cudnn` package. A build with this change therefore files its compiled plans under a new environment directory and rebuilds each one once.
