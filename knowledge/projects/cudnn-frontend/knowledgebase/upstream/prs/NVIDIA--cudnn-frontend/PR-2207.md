# gemm(frost sm100): render split-K partials for a chain whose first output is a reduction

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2207) · state: open · merged: False

## Original PR description

## Problem

Under workspace split-K, the SM100 main kernel stores only fp32 partials, through output 0's TMA slot. The reducer kernel renders the outputs and reductions.

`generate()` in `sm100/epilogue_codegen.py` still emitted the reductions into the main kernel's body before replacing that body with the partial store, and it looked up each reduction's tap past the TMA slots. When the reduction is output 0, i.e. the chain has no dense output, there is no tap for it, so compilation raises `KeyError: 0`.

The automatic pick reaches this path. On B300 (cc 10.3), develop d760fefe, `matmul -> relu -> reduction` at 256x256x16384 lists only a `SPLIT_K_SLC=4` FROST plan, and `build_plans()` raised `KeyError: 0`:
- for ADD, AVG and AMAX over all of M and N, ADD per row and MAX per column;
- at 128x384x8192 (`SPLIT_K_SLC=6`) as well.

The cuDNN backend reports `NOT_SUPPORTED` for these graphs, so the user gets no working plan. When the chain also stores the dense output, output 0 is that output and the same plans already work. SM120 does not use the TMA store epilogue, so it never routes a reduction to slot 0.

## Change

- `sm100/epilogue_codegen.py`: under `workspace_split_k`, skip the reductions in the main kernel's body. The reducer still renders them, as before.
- `test_matmul.py`:
  - `test_splitk_reduction_only_outputs`: an explicit split-8 config on a chain whose only output is AMAX over everything, a per-row ADD or a per-column MAX. It uses integer data, so every partial is exact and the results must match exactly. It runs on the active family.
  - `test_frost_gemm_builds_its_split_k_pick_for_a_reduction_only_chain` (SM100): the engine path. It builds and runs the listed FROST plan for `matmul -> relu -> AMAX` at 256x256x16384, and skips if the automatic pick does not split K on the device.

## Tests

On B300 (cc 10.3), develop d760fefe (the GEMM tree is the same as at 97b7bc31):
- The two new tests: 4 failed on develop (`KeyError: 0`), 4 passed with this change.
- Probe over all ranked FROST plans of the graph path:
  - 2 shapes × 5 reduction kinds without a dense output: every plan raised on develop; with this change every plan returns the exact result.
  - The same 10 cases with a dense output: unchanged.
- Not yet run: the wider split-K / reduction regression subset of `test_matmul` and `test_gemm_knobs`. Our shared B300 is busy, and I'll post the result here.
- `pre-commit` on the touched files passes.

Separately, fp32 ADD/AVG/NORM sums over all of M and N drift under split-K on SM100 as they do on SM120 (#2019). That is #2208.
