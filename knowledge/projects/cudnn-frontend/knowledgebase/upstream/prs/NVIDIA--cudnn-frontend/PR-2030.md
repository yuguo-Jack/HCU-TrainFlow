## Summary

- Under fp32 compute, `_emit_binary_ext` now emits the `mod` epilogue op as `{new} = {a} % {b}`. CuTe DSL lowers `%` on
  Float32 vectors to `arith.remf`, which compiles to an exact fmodf. Before, `mod` was emitted as `a - b * trunc(a / b)`:
  `q = a / b` (`div.rn.f32`), `trunc(q) = floor(|q|) * (step01(q) - step01(-q))`, then `a - b * trunc(q)`.
- INT32 compute keeps the existing form (see "API and compatibility impact").
- New regression test `test_epilogue_mod_is_exact_fmod`, with the GEMM output as dividend (`mod_C_x`) and as divisor
  (`mod_x_C`), on the dense SM120 template and, on SM100-family GPUs, the dense SM100 template.

## Why

cuDNN's MOD is the C floating-point remainder, fmod: Frost's own test reference is `torch.fmod`, and native cuDNN returns
exact fmod on the same SM120 GPU apart from subnormals, which it flushes to zero (see Testing and "API and compatibility
impact"), e.g. `mod(2**25, -3) = 2` and `mod(3, inf) = 3`. The emitted form rounds the quotient before truncating it. The
truncation of the rounded quotient is exact, and ptxas contracts the final multiply-subtract into one FFMA, so the result is
fmod when `trunc(fl(a / b)) == trunc(a / b)`, with two exceptions listed in the last bullet: infinite divisors and exact
negative multiples. It is wrong otherwise:

- when `a / b` lies just below a nonzero integer and rounds up to it, the result is `fmod(a, b) - sign(a) * |b|`, a small
  value of the wrong sign. This is common with integer dividends and decimal divisors: `mod(k, 0.1f)` is wrong for every
  integer `k` tested, e.g. `mod(2, 0.1f) = -2.98e-8` instead of `0.09999997`;
- from `|a / b| >= 2**23` the rounded quotient has no fraction bits. Below `2**25` it is at most one away from
  `trunc(a / b)`, so about half of the results are off by `|b|`: `mod(2**25, -3) = -1` instead of `2`. From `2**25` it is a
  multiple of 4 or more, so results can also leave `(-|b|, |b|)`: `mod(5 * 2**27, 0.7f) = 17.83` instead of `0.3286`,
  `mod(2**40, 1.3f) = 20669` instead of `0.3476`. `mod(x, 2 pi)` for a phase `x` in `[1e6, 1e8]` was wrong for about a
  third of the values;
- `b = +-inf` gives NaN (`inf * 0`) instead of `a`, and exact negative multiples return `+0` instead of `-0` (`mod(-4, 2)`),
  although the truncated quotient is right in both cases; a quotient that overflows gives `-inf` instead of the remainder
  (`mod(1e38, 2**-100) = -inf`, fmod `0`).

Minimal reproducer (the new test): dense `sm120_matmul` through `jit_from_cudnn_graph` with
`CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`, bf16 A/B, M = N = K = 128, fp32 intermediate and compute, fp32
output `y = mod(C, x)` (or `mod(x, C)`) with `x` an fp32 per-element aux. `A` is the identity, so `C` holds exactly the
chosen bf16 values. Values that differ bitwise from fmod on develop 24a8cd43:

| `mod(C, x)` operand group | wrong on develop |
|---|---|
| `k / 0.1f` rounds up to `10 k`, `k = 1..256` and `-1..-64` | 320 of 320 |
| `\|C / x\| >= 2**23` (`2**25 .. 3 * 2**50` by `-3, 0.7, 1.3, 2.9`) | 19 of 24 |
| `x = +-inf` | 8 of 8 (NaN) |
| exact negative multiples (`-0` expected) | 3 of 3 (`+0`) |
| `C / x` overflows | 2 of 2 (`-inf`) |
| `C mod 6.2831855`, `C` in `[1e6, 1e8]` | 79 of 256 |
| `x = 0` (NaN expected) | 0 of 2 |
| small quotients, `\|C / x\| <= 16` | 1 of 128 (`mod(-8, 0.5) = +0`) |

For `mod(x, C)`: 84 of 256 phases `x` in `[1e6, 1e8]` mod `bf16(2 pi)`, 3 of 3 large or overflowing quotients, and the same
signed-zero case. With this change every value matches fmod bitwise.

`arith.remf` is the right lowering: it states fmod semantics in the IR instead of approximating them. On SM120 and SM100 it
compiles to the exact fmodf expansion (a quotient estimate corrected through an exact FMA remainder, a reduction loop once
`|a / b| > 2**23`, and `copysign` for the sign of `a`), with no `div.rn.f32` and no floor (PTX counts under Testing). The
audit also ran it against `math.fmod` on 358,400 operand pairs on SM120, including `+-0`, subnormal, `+-inf` and NaN
operands, with no difference, and the random-operand sweep under Testing found none in 524,288 more. Patching the old form
(for example with a remainder correction step) would still need special cases for infinite divisors, quotient overflow and
signed zeros.

The change is outside `python/cudnn/gemm/frost/sm120/` because, since #1993, the epilogue op emitter exists only in the
shared `python/cudnn/gemm/frost/epilogue_codegen.py`: both families' `generate()` call the shared `_emit_pointwise_dag`
(`sm120/epilogue_codegen.py:827`, `sm100/epilogue_codegen.py:498`), which, like the shared `generate_mainloop`, reaches it
through `_emit_op`. There is no per-family copy to fix instead.

Found in an audit of the SM120 Frost kernel templates (finding G4.1).

## API and compatibility impact

- No API change. FlashInfer's exported Frost graphs contain no `mod`.
- Numerics: an fp32-compute `mod` now returns exact C fmod in every epilogue that reaches the emitter. On SM120 that is all
  six templates (dense and block-scale matmul, MoE grouped matmul and its swap-AB form, MoE grouped block-scale matmul and its
  swap-AB form) and the split-K reduction epilogue; SM120 has no mainloop fusion. Results that were already exact, such as
  the quotients below 10 drawn by the existing sweep, are unchanged except for the sign of exact-zero remainders.
- Native cuDNN parity (AGENTS.md Rule 9): on every operand group of the new test, FROST now gives the same bits as native
  cuDNN. They still differ on subnormals, and that predates this change: native cuDNN flushes subnormal operands and results
  to zero (a subnormal divisor gives NaN, a subnormal dividend or exact remainder gives `+-0`), while FROST computes exact
  fmod on them; develop's FROST kernel did not flush either. In the random-operand sweep under Testing every native
  difference from fmod is one of these subnormal cases. The new test does not pin subnormal behaviour.
- SM100: the emitter is shared, so the SM100 family's generated code changes the same way: every SM100 template epilogue,
  the split-K reduction epilogue and the `sm100_matmul_mainloop.py` mainloop-fusion transform (a `mod` with a scalar divisor
  on A or B). Both kinds were compile-checked for `sm_100a` on the SM120 host (see Testing); nothing ran on SM100 hardware.
  The new test's two SM100 cases (the dense SM100 template, gated by `requires_sm100`) give SM100 CI a bitwise check of the
  changed path; they compile for `sm_100a` but have not run. The existing SM100 `mod` case,
  `test_matmul_epilogue_fusion.py::test_pointwise_mode_coverage[mod]` (quotients below about 10, bf16 output, tolerance
  5e-2, 0.2% mismatch budget), still exercises the path on SM100 CI but cannot detect this defect.
- INT32 compute is unchanged: a `mod` node with `compute_data_type=INT32` keeps the old form and still fails at build with
  the same `DSLRuntimeError` (`'arith.addf' op operand #1 must be floating-point-like, but got 'vector<8xi32>'`).
  INT32-compute epilogue ops are a separate audit finding (G4.4, #2022, which declines an INT32-compute `mod` on SM120).
  Emitting `%` there would select `arith.remsi`, whose zero-divisor and overflow cases are undefined.
- Performance: the fmodf expansion is longer than the old divide-and-floor sequence and adds a short data-dependent loop
  for `|a / b| > 2**23`. Only graphs with a `mod` node are affected. Not measured.
- Chains with `mod` render different kernel source, so their cached kernels are rebuilt once.
