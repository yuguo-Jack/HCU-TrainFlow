## Summary

In `_emit_op`, the `tanh`, `elu` and `softplus` emitters now use `cutlass._mlir_helpers.vector.where` to choose per element between the existing closed form and the leading Taylor terms. The Taylor terms are used below a bound of 1/8: in |x| for tanh, in |min(x, 0)| for elu (so for every x > -1/8, positive x included), and in y = e^-|x| for softplus.

- **tanh:** for |x| < 1/8, x + x^3 (-1/3 + x^2 (2/15 - 17/315 x^2)). Otherwise the existing 1 - 2/(e^2x + 1).
- **elu:** max(x, 0) + expm1(min(x, 0)). The expm1 term is n + n^2 (1/2 + n/6 + n^2/24 + n^3/120 + n^4/720) for n > -1/8, and e^n - 1 otherwise. For x >= 0 it is exactly 0, so a positive x passes through unrounded.
- **softplus:** max(x, 0) + log1p(y), y = e^-|x|. log1p(y) is y - y^2/2 + ... - y^8/8 for y < 1/8, and log(1 + y) otherwise.

The bound and the coefficients are new module-level constants (`_SERIES_BOUND`, `_TANH_SERIES`, `_EXPM1_SERIES`, `_LOG1P_SERIES`), and `_horner` is a new helper. Like every other name in the module, they are registered in `_SHARED_EXPORTS`. `_tanh_expr` is unchanged; only its docstring now states its absolute error. `gelu_tanh`, `tanh_backward` and `gelu_tanh_backward` keep using it, because they depend only on its absolute error.

The new test is `test_tanh_elu_softplus_relative_precision`. It has one case per op on each arch tree's dense config: `CONFIG_sm100_128x128x128_128x128x32_cluster1x1_1ctamma` and `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`. A process renders only its own tree, so the other tree's cases skip. The second commit is a review follow-up: it renamed the test from `test_sm120_tanh_elu_softplus_relative_precision`, added the sm100 cases, and added a comment on why the negative inputs stop at -80.

The first commit's message is imprecise in two places, which this description states correctly:
- "4.7e-5 off at 1e-3" for elu is a relative error. The absolute error is 4.7e-8.
- It says the series is selected below 1/8 "in |x| for tanh and elu". For elu, the select is on min(x, 0) > -1/8, which covers every x > -1/8.

## Why

The emitters used forms that cancel where the result goes to 0:

- **tanh:** 1 - 2/(e^2x + 1). The rounding of e^2x and of e^2x + 1 near 1 and 2 leaves an absolute error of about 1e-7 whatever x is.
- **elu:** `max(x, 0) + e^min(x, 0) - 1`, evaluated left to right. A positive x became (x + 1) - 1, and a small negative x became e^x - 1. CuTe DSL emits these adds as `arith.addf` / `arith.subf` without fastmath flags, so nothing reassociates them.
- **softplus:** `log(1 + y)`. Adding 1 rounds away the low bits of a small y, and the result is 0 once y < 2^-24.

Measured on the dense SM120 template (`CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`, bf16 GEMM, fp32 output). The activation input is exactly the fp32 value x:

Minimal reproducer, which is the new test's sm120 case: a dense GEMM with M = N = K = 128 on that config, bf16 A = B = 0, and an fp32 per-element aux X added to the accumulator. Then comes tanh, elu or softplus, with fp32 output. X holds 6000 log-uniform magnitudes in [1e-30, 10] of both signs, 4382 uniform values in (-80, -2] and ±inf. Compared with torch at rtol 1e-5 on 24a8cd43:
- tanh: 10562 of 16384 elements mismatch, greatest relative difference 1.87.
- elu: 10499 mismatch, greatest relative difference 1.0.
- softplus: 4196 mismatch, greatest relative difference 1.0.

Why this fix:

- **The Taylor terms are used only where the closed forms cancel.** Truncation at the bound is below 1e-8 relative: 1.3e-9 for tanh, 8e-10 for expm1, 7e-9 for log1p. Beyond the bound the closed forms are kept. On a sweep of 65536 fp32 inputs, those outputs are bitwise identical to 24a8cd43: 39323 tanh cells, 26215 elu cells and 43600 softplus cells. Results for ±inf and NaN inputs are unchanged.
- **A select, not a 0/1 mask blend.** The audit suggested blending with the module's `_step01` mask. A multiply-blend turns inf or NaN in the unused branch into NaN; for example, the tanh polynomial at x = ±inf is NaN, while tanh(±inf) must be ±1. `vector.where` (`arith.select` on an `arith.cmpf` predicate) ignores the unused branch. The module already emits it for `binary_select` and for the mainloop K-OOB mask. The compare is ordered, so a NaN input to tanh or softplus takes the closed form and stays NaN. elu's NaN result (0, from the default max/min) is unchanged here; see Related issues.
- **Native `cute.math.tanh` / `expm1` / `log1p` were not used.** With cutlass-dsl 4.7.1 they compile in the SM120 dense epilogue and gave accurate results in a probe. I still did not switch to them, for three reasons:
  - They would change every output, not only the cancelling range.
  - The FROST conv epilogue still notes that vector tanh fails to lower (`python/cudnn/conv/frost/templates/epilogue.py:33-34`).
  - These emitters also serve the sm100 tree, which I can only compile here, not run.
- **Accuracy after the fix.** Over the 65536-input sweep, the worst relative error is:
  - tanh: 1.1e-6, just above the bound, from the unchanged closed form.
  - elu: 6.3e-7.
  - softplus: 3.6e-6 at x ≈ -78. This comes from rounding the unchanged exp2 argument |x|·log2e.

  A denser sweep goes down to x = -87.33. That is just above about -87.34, below which softplus is no longer an fp32 normal. Over that range softplus is at worst 3.8e-6, at x ≈ -85.9. A CPU model of the argument rounding alone (fp32 |x|·log2e with the fp32 constant, then an exact exp2) gives 3.81e-6, so the rounding accounts for that worst case.
- **Native cuDNN on the same GPU.** I ran native cuDNN 9.24 eng10 on bf16 inputs with magnitudes 1e-12..1 and fp32 output:
  - tanh: accurate, with a worst relative error of 9.9e-6.
  - elu: exact for x > 0. For a small negative x it computes e^x - 1, which is 7.5% off at -1e-6, the same as FROST on 24a8cd43.
  - softplus: worse than FROST, 41% off at -15 and 0 at -20.

  With this PR, FROST tanh and positive elu agree with eng10 to fp32 precision. For small negative elu and for softplus, FROST is now closer to torch than eng10 is.

Reachability: no SM120 rule declines these ops. They are reachable through the FROST engine and `jit_from_cudnn_graph` on all six SM120 templates, and the same holds on the sm100 tree. No SM120 test covered them before this PR. The SM100 tests that run them use tolerances too loose to see this defect. For example:
- `test_matmul_epilogue_fusion.py::test_pointwise_mode_coverage` runs elu and softplus at atol = rtol = 5e-2.
- `test_matmul_epilogue_fusion.py::test_fusion_default_axis` runs tanh with bf16 output at atol = 1e-1, rtol = 1e-2.

The new test has an sm100 case for each op, so an SM100 GPU runs the same rtol 1e-5 check. Those cases have not been run here, because there is no SM100 GPU on this host.

Why the change is outside `python/cudnn/gemm/frost/sm120/`: at 24a8cd43 these emitters exist only in the shared `python/cudnn/gemm/frost/epilogue_codegen.py`, which #1956 / #1993 moved them into. Both arch trees reach them through `_emit_op`: epilogues through `_emit_pointwise_dag`, which `sm100/epilogue_codegen.py` and `sm120/epilogue_codegen.py` import from the shared module, and mainloop operand transforms through `generate_mainloop`. `sm120/` has no copy to change.

Found in an audit of the SM120 FROST kernel templates (finding B11).

## API and compatibility impact

- **Numerics:** FROST GEMM epilogue tanh, elu and softplus change only where the Taylor terms are selected:
  - tanh: |x| < 1/8.
  - elu: x > -1/8, which includes every positive x; those now pass through exactly.
  - softplus: e^-|x| < 1/8, that is |x| > ln 8 ≈ 2.08.

  In those ranges:
  - tanh and elu move to within about 1e-7 relative of torch. A dense sweep gives a worst case of 8.8e-8 for tanh and 1.1e-7 for elu.
  - softplus moves to within about 4e-6, with a worst case of 3.8e-6 at x ≈ -86. Its floor is the fp32 rounding of the unchanged exp2 argument |x|·log2e, which grows with |x|.
  - softplus results below FLT_MIN (x < about -87.3) still flush to 0, as on 24a8cd43, because exp2 is emitted as `ex2.approx.ftz.f32`. torch returns subnormals there, down to about x = -104.

  Elsewhere outputs are bitwise unchanged, and so are the ±inf and NaN results. No graph is newly declined, and no API changes.
- **SM100:** the sm100 tree uses the same shared emitters, so its epilogues change in the same way. There is no separate SM100 copy that needs a follow-up.
  - I did not run this on SM100 hardware. The new test's sm100 cases skip on this SM120 GPU.
  - Compile-only check: the SM100 dense template (`CONFIG_sm100_128x128x128_128x128x32_cluster1x1_1ctamma`) with each of the three ops compiles for sm_100a on this host, using `CUDNN_FRONTEND_GEMM_ARCH_FAMILY=sm100 CUTE_DSL_ARCH=sm_100a`. This holds for the plain `matmul -> act` graph and for the test's exact graph, `act(matmul + X)` with an fp32 aux X and fp32 output. The rendered SM100 kernels contain the new select lines.
- **FROST conv:** `python/cudnn/conv/frost/templates/epilogue.py` uses the same closed forms: tanh at `:32-37`, elu at `:40-42` and softplus at `:64-66`. It is a different engine and is not changed here.
- **Pre-rendered kernels:** they keep the old lines until they are re-exported. For example, FlashInfer's SiTU FC1 artifacts inline this tanh twice, in the gate cap (×4) and the linear cap (×25); they have bf16 output, and the audit rated the effect there as negligible.
- **Kernel cache:** the generated source of chains with these ops changes. Its digest changes with it, so no stale cache entry is reused.
- **Performance:** not measured; no timing was run on the shared GPUs. `vector.where` lowers to a `selp` in PTX, and the PTX computes both the series and the closed form for every element. The closed-form cost is unchanged, and the series cost comes on top of it.

  Static counts come from the compiled dense kernels for `act(matmul + X)` with fp32 output, comparing 24a8cd43 with this branch. The SM100 kernels were cross-compiled for sm_100a and not run.
  - **Arithmetic:** per activation, the SASS adds 5 (tanh), 6 (elu) and 8 (softplus) FP32 multiply or FMA operations on both trees, plus one compare. On SM100 they are packed FFMA2/FMUL2 instructions. A separate FSEL appears only in the SM100 tanh and elu kernels. In total, SASS grows by 6.0, 7.4 and 9.4 instructions per activation on SM120, and by 3.2, 3.8 and 3.4 on SM100.
  - **MUFU:** the instructions (ex2 for all three ops, rcp for tanh) are the same in number. softplus's log is not a MUFU instruction (there is no `lg2`) but a software FMA sequence, and that sequence is unchanged.
  - **Registers:** on the SM120 config, whose epilogue vector is 8 elements wide, registers per thread stay at 168. On the SM100 config the vector is 32 elements wide, and registers rise from 106 (tanh, elu) and 119 (softplus) to 128. No kernel uses local memory (no spills), before or after.
  - **FlashInfer:** its SiTU FC1 graph calls `graph.tanh` twice per element (`flashinfer/fused_moe/backends/cudnn_frost/export.py:217` and `:222` at flashinfer-ai/flashinfer main b1cf76608), so a re-export picks up two of these selects per output element. Before FlashInfer re-exports those artifacts, a maintainer should time epilogue-heavy shapes on SM100 and SM120.
- **CuTe DSL version:** the change uses only constructs the module already emits: `vector.where`, float vector compares and `cute.math.abs/min/max/exp2/log/rcp`. No new version gate is needed (Rule 7).
