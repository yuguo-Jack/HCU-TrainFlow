## Summary

- Under fp32 compute, `_emit_binary_ext` now emits each `cmp_*` epilogue op as a native vector compare selected to 1/0:
  `cutlass._mlir_helpers.vector.where(a OP b, full_like(a, 1.0), full_like(a, 0.0))`, with OP one of `==`, `!=`, `<`, `<=`, `>`, `>=`
  (the new module constant `_CMP_PY_OPS`, next to `_CMP_OPS`).
  These lower to `arith.cmpf` with the IEEE predicates OEQ, UNE, OLT, OLE, OGT and OGE. Before, every `cmp_*` op was emulated as
  `step01(d) = min(max(floor(d) + 1, 0), 1)` over `d = a - b` or `b - a`.
- INT32 compute keeps the existing step form (see "API and compatibility impact"); `_step01` is unchanged and still serves the
  logical ops, `mod` and the backward ops.
- New SM120 regression test `test_cmp_ops_follow_ieee_for_nonfinite_operands_sm120`: the six ops with the aux on either side of the
  compare, plus the isnan and isfinite idioms.

## Why

The emulated compares are exact only for finite operands. `a - b` is NaN when either operand is NaN, and when `a` and `b` are the
same infinity. `cute.math.max` / `cute.math.min` default to `propagate_nan=False` and lower to the NaN-ignoring
`arith.maxnumf` / `arith.minnumf` (PTX `max.f32` / `min.f32` without `.NaN`), so `step01(NaN)` is 0. As a result:

- a NaN operand made `cmp_lt` and `cmp_gt` return 1 (IEEE: 0); `cmp_eq`, `cmp_neq`, `cmp_le` and `cmp_ge` happened to be right;
- equal same-signed infinities inverted all six ops: `cmp_eq`, `cmp_le` and `cmp_ge` returned 0, `cmp_neq`, `cmp_lt` and `cmp_gt` returned 1;
- so the isnan idiom `cmp_neq(C, C)` reported +-inf as NaN, and the isfinite idiom `cmp_lt(abs(C), inf)` returned 1 for inf and NaN.

Minimal reproducer (the new test): dense `sm120_matmul` through `jit_from_cudnn_graph` with
`CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`, bf16 A/B, M = N = K = 128, fp32 intermediate and compute, fp32 outputs
`y = cmp_op(C, X)` and `y = cmp_op(X, C)` with `X` an fp32 per-element aux. Rows of C are forced to +inf, -inf or NaN by putting that
value in `A[:, 0]` with `B[0, :] = 1`. On develop 24a8cd43, in both operand orders, every equal-infinity cell is wrong for all six ops
(1024 per 16-row band), every NaN cell is wrong for `cmp_lt` / `cmp_gt` (2048 per band, NaN on either side), and every finite cell is
right (equal values, +-0.5 / +-1 offsets, finite vs +-inf, 0 vs +-subnormal). The plain MoE templates and the dense block-scale
template show the same pattern (ad hoc checks below).

Through the public `graph.execute()` path on the same GPU (with `CUDNN_FRONTEND_ENABLE_FROST_ENGINES=1`, since the FROST GEMM engine
is opt-in), the first cuDNN backend plan (engine 10) for `y = cmp_op(C, X)` returns IEEE masks, and the FROST plan (engine 20400) did
not on develop. So the two engines gave the same graph different results,
while Rule 9 of `python/cudnn/AGENTS.md` asks backend and FROST to keep the same semantics for a graph both support. With this
change they agree (counts under Testing).

A native compare has IEEE semantics by construction: the ordered predicates are false when an operand is NaN, the unordered `UNE` is
true, and equal infinities compare equal. No arithmetic on `a - b` can give `cmp_eq` / `cmp_le` / `cmp_ge` for equal infinities, so
patching the NaN handling of `max` / `min` would not be enough. `vector.where` over a vector compare is the lowering `binary_select`
and the mainloop K-tail mask already use in this module, so this adds no new CuTe DSL dependency.

The change is outside `python/cudnn/gemm/frost/sm120/` because, since #1993, the emitter lives only in the shared
`python/cudnn/gemm/frost/epilogue_codegen.py`, whose `_emit_pointwise_dag` both arch families call
(`sm120/epilogue_codegen.py:827`, `sm100/epilogue_codegen.py:498`). There is no per-family copy to fix instead.

Found in an audit of the SM120 Frost kernel templates (finding B09).

Related PRs from the same audit that change `python/cudnn/gemm/frost/epilogue_codegen.py`:

  compatibility impact").
- #2030 (G4.1, `mod`), #2026 (G4.3, default `relu_backward`) and #2009 (B10, `relu` / `relu_backward` with a slope) change other
  branches of `_emit_binary_ext`; G4.1 and G4.3 also replace step forms there.
- #2012 (G4.2), #2025 (B11), #2014 (B13) and #2013 (B14) change other emitters in the same file.

`git merge-tree` merges each of these branches with this one without conflicts.

## API and compatibility impact

- No API change.
- Numerics: under fp32 compute, `cmp_*` masks change only where an operand is NaN or both operands are the same infinity; they now
  match IEEE comparison and torch, and in the `graph.execute()` check under Testing they match cuDNN backend engine 10 on the same
  graphs. Masks for finite operands are unchanged.
- SM100: the emitter is shared, so the SM100 tree (dense, block-scale, MoE, the split-K reduction epilogue and SM100 mainloop-fusion
  transforms) gets the same fix. It was not run on SM100 hardware here; the existing SM100 cmp cases in
  `test_matmul_epilogue_fusion.py::test_pointwise_mode_coverage` (finite inputs) exercise the new code on SM100 CI.
- INT32 compute is unchanged: a `cmp_*` node with `compute_data_type=INT32` still takes the step form and still fails at build with
  `TypeError: floor is only supported for floating-point types`. That failure is a separate audit finding (G4.4); its PR #2022
  declines such graphs on SM120. `sm100/compiler.py` has no such check, so removing the int32 step form is left for a follow-up.
- Chains with `cmp_*` ops render different kernel source, so their cached kernels are rebuilt once.
