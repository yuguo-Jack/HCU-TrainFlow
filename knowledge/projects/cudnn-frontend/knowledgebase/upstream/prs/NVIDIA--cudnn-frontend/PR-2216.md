## Affected area

Python API or bindings (`cudnn.torch`, the PyTorch SDPA provider)

## Summary

The `cudnn.torch` overrides of `torch_attn::_varlen_attn`, `_varlen_attn_out` and `_varlen_attn_backward` now honor the backend that `varlen_attn` selected. Where the ops take a trailing `backend` argument, an override serves a call only if it selected cuDNN and `_varlen_supported` admits it. Every other call goes to the kernel the override replaced, which is torch's own op body. Torch versions without the argument behave as before.

## Why

Since pytorch/pytorch#193631, `varlen_attn` picks flash or cuDNN from `sdpa_kernel` and the SDPA priority order, and passes the choice to these ops as a trailing `backend` argument. The overrides were written before that and take no such argument, so on current torch they break both ways:

- **cuDNN selected:** the dispatcher passes `backend` and the override raises `TypeError` (forward, out and backward).
- **Flash selected:** `backend` is at its default, so the dispatcher leaves it out and the override runs anyway. Calls inside `sdpa_kernel(SDPBackend.FLASH_ATTENTION)` get cuDNN whenever the config is one the python path supports.

A review of pytorch/pytorch#195981, which adds `torch.backends.cuda.enable_cudnn_sdp_python` on top of `install_sdpa_overrides()`, found this. Accepting and ignoring the argument would fix the exception but not the routing.

How the calls are passed on: before registering each override, `install_sdpa_overrides()` captures the op's current CUDA kernel with `torch.library.get_kernel` and registers the override `with_keyset=True`. Calls the override doesn't serve go back to that kernel with `call_boxed`, the pattern the `get_kernel` docs describe. That kernel is torch's op body, which runs flash or torch's C++ cuDNN path as selected. So a cuDNN call that the python path declines (for example with `seqused_k`) stays on cuDNN rather than dropping to flash, and the provider doesn't copy any of torch's dispatch logic.

## Related issues

Related to pytorch/pytorch#195981 (review comment on the varlen backend contract).

## API and compatibility impact

- No public API change. `install_sdpa_overrides()` keeps its signature and handle.
- **Torch with the `backend` argument:** torch also decides which configs can select cuDNN for varlen, and its rules admit only full or causal windows. Sliding-window and right-bounded calls therefore go to flash, and the provider no longer serves them there. They can only reach the python path once torch's selection admits them.
- **Torch without the argument** (2.13 and earlier nightlies): unchanged. Every varlen call is served here as before, sliding windows included.
- `calls` gains `fwd_torch` and `bwd_torch`, counting varlen calls passed on to torch.

## Testing

- New `test/python/sdpa/torch/test_torch_provider_backend.py` (L0; skips where the ops have no `backend` argument):
  - cuDNN selected: served, forward and backward.
  - Flash selected: passed on to torch, with output bitwise-equal to the same call without the overrides.
  - `varlen_attn_out` follows the selection both ways.
  - A cuDNN-selected `seqused_k` call (which the python path declines) runs torch's C++ cuDNN path, per torch's own log line, and not flash.
- `test_torch_provider.py`: the varlen tests select cuDNN explicitly and skip the windows torch rules out of cuDNN.
