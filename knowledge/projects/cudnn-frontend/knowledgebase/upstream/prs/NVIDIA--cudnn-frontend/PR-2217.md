# test(qsa_topk_decode): skip launch cells a 99 KB shared-memory part declines

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2217) · state: open · merged: False

## Original PR description

## Problem

`test_qsa_topk_decode.py` says the single-CTA form "runs on any CuTe DSL device". On a part with 101376 B of opt-in shared memory per block (cc 8.6 / 8.9 / 12.x), though, `compile_qsa_topk_decode` declines these by name before any compile:

- the 1024-thread single-CTA form at `K = 512`, which needs 116144 B (the fast path's staging pool is `32 x (K + RANK_CAP)` words);
- the cluster form, which needs 108 to 118 KB.

The decline reads:

```
qsa_topk_decode at cols_cap = 8192 with threads_per_cta = 1024 needs 116144 B of shared memory per CTA; the device allows 101376 B -- the row is too wide for this device
```

Every cell that launches those forms therefore fails with `NotImplementedError` on these GPUs. The kernel is behaving correctly here; only the tests assume a device with more shared memory.

## Change

This is a test-only change. A small `_skip_when_too_wide()` context manager turns exactly that decline into `pytest.skip` with its text, and any other `NotImplementedError` still raises. It wraps:

- `_run`, which `_check` also goes through;
- the first launch in the two-device test;
- the compile in `test_execute_form_checks_refuse_by_name`;
- the facade call in `test_the_facade_serves_the_kernel_module_at_or_above_the_floor`.

`test_declines_a_shared_memory_need_above_the_device_limit` still pins the decline itself through a monkeypatched limit outside the helper, so the gate keeps its coverage. On large-smem parts (cc 8.0 / 9.x / 10.x) nothing changes, because the decline never fires there.

The `[...-512]` thread-count cells still run and pass on SM120, so the select keeps real coverage there.

If you'd rather have the 1024-thread cells fall back to the 512-thread arm on these parts instead of skipping, I can switch to that.
