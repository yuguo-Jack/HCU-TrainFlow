## Affected area

FE OSS kernels or CuTeDSL (Python/JAX entry points)

## Summary

Follow-up to #1399 and #1535, which gave the MXFP8 GLU, dGLU and wgrad kernels a canonical dense JAX path. This PR extends that path to the rest of the grouped GEMM matrix, in one place: every grouped op that has a kernel, in every format the kernel supports.

| Op | JAX entry | MXFP8 | NVFP4 / MXFP4 | BF16 dense | Rubin kernel |
|---|---|---|---|---|---|
| GLU | `grouped_gemm_glu_jax_sm100` | #1399 | new | new | yes |
| dGLU | `grouped_gemm_dglu_jax_sm100` | #1535 | new | new | yes |
| wgrad | `grouped_gemm_wgrad_jax_sm100` | #1535 | new | new (dense output) | yes |
| quant (FC2, dFC1) | `cudnn.ops.grouped_gemm_quant_forward_jax` (new) | new | new | no kernel | yes |
| SReLU | `cudnn.ops.grouped_gemm_srelu_forward_jax` (new) | new | new | no kernel | no |
| dSReLU | `grouped_gemm_dsrelu_jax_sm100` | new (dense) | new | no kernel | no |
| GLU + Hadamard | `cudnn.ops.grouped_gemm_glu_hadamard_forward_jax` (new) | FP4-only kernel | new | no kernel | no |
| GLU + Hadamard + quant | `cudnn.ops.grouped_gemm_glu_hadamard_quant_forward_jax` (new) | FP4-only kernel | new | no kernel | not enabled for JAX |

The shared `*_wrapper_sm100` functions dispatch JAX inputs with a dense `b_tensor` to these entries (wgrad: with `sfa_tensor`), before the hot-loop memo.

1. **Packed FP4 from JAX.** JAX has no packed FP4 dtype, so FP4 operands travel as `uint8` with two values per byte and the adapters reinterpret them as 4-bit elements (`kernel_facing_fp4`). The entries gain `sf_vec_size`; scales are E4M3 per 16 (NVFP4) or E8M0. FP4 wgrad takes B as `(n, tokens/2)`, since 4-bit operands must be K-major, plus the per-expert global scales for NVFP4.
2. **Accumulator outputs.** BF16/FP16 outputs return the per-expert amax, which the bridge initializes (to -inf, or to zero for the Hadamard kernels, as Torch does). `grouped_call` takes the initialized outputs as `(index, initializer)` pairs.
3. **New entries** for quant, SReLU, GLU + Hadamard and GLU + Hadamard + quant follow `docs/fe-oss-apis/api_conventions.md` (`cudnn.ops.<op>_forward_jax`, exported from `cudnn.ops`). Existing `*_jax_sm100` entries only gain modes.
4. **Layout views.** Since #1601 and #1602, the BF16 GLU and dGLU kernels and the Hadamard GLU kernel convert canonical operands themselves, so their adapters pass the arrays through (FP4 still gets its 4-bit view). The SReLU, dSReLU and GLU + Hadamard + quant kernels do not, so their adapters build the kernel-facing views (metadata only). BF16 dense wgrad takes natural 2-D inputs.
5. **GLU + Hadamard + quant** returns NVFP4 D and RHT as packed `uint8`; JAX requests them with `cutlass.Float4E2M1FN`. `norm_const` and `rht_norm_const` are kernel scalars, so from JAX they are compile-time constants: a data-dependent value retraces.

## Why

TE's JAX MoE needs the same fused ops as its PyTorch path, across MXFP8, NVFP4 and BF16. Doing the matrix in one PR keeps the shared helpers (`canonical_jax.py`, the FP4 view, the test problems) consistent across ops.

## Related issues

Follow-up to #1275 / #1399 / #1535. Supersedes #1594.

## API and compatibility impact

- Four new exports (API index updated): `cudnn.ops.grouped_gemm_quant_forward_jax`, `cudnn.ops.grouped_gemm_srelu_forward_jax`, `cudnn.ops.grouped_gemm_glu_hadamard_forward_jax`, `cudnn.ops.grouped_gemm_glu_hadamard_quant_forward_jax`.
- Existing JAX entries gain keyword-only parameters (`sf_vec_size`; wgrad `global_scale_a`/`global_scale_b`; dSReLU `b_tensor`/`sfb_tensor`). dSReLU's `b_ptrs`, `sfb_ptrs`, `n`, `norm_const_tensor` become optional in the signature; discrete mode still requires them.
- Wrappers that raised for dense JAX inputs now run them: quant, SReLU, dSReLU, GLU + Hadamard, GLU + Hadamard + quant, and BF16 dense GLU/dGLU. A caller passing kernel-facing (3-D) JAX arrays with a dense `b_tensor` now gets "JAX requires canonical A" instead of "not expressible as JAX arrays". Three legacy error tests are updated accordingly.
- For BF16/FP16 output the GLU, dGLU, SReLU and dSReLU kernels do not write D_col, so the JAX entries return `d_col_tensor=None` there (Torch returns an unwritten buffer).
- Unsupported from JAX, raising `ValueError`: discrete block-scaled weights, bias, dbias, dynamic scheduling, row scale, deterministic reduction, dSReLU reuse, `tanh_clamp_scale` on dSReLU, and the op classes. FP4 wgrad needs `nvidia-cutlass-dsl >= 4.8`.
- Torch behavior and wrapper defaults are unchanged; the JAX check is one framework test per wrapper call.

## Testing

Environment: SM100 (CC 10.0), Python 3.14, JAX 0.11.2, CuTeDSL 4.8.0, torch 2.14.1+cu130, cuDNN 9.24.

- Rebased onto `develop` after #1601, #1602 and #1597 (head `ac2b4c000`). `pytest test/python/gemm/jax` plus the Torch suites of the touched wrappers (SReLU, dSReLU, GLU + Hadamard, GLU + Hadamard + quant, wgrad, wrapper memo, and the canonical-layout suites including #1602's BF16 one): **711 passed, 211 skipped, 2 xfailed**.
- `test_grouped_gemm_canonical_jax.py` now has 210 tests. Every new path is compared with the Torch wrapper on the same bytes (canonical Torch inputs where the Torch wrapper takes them, which now includes BF16 GLU/dGLU and Hadamard GLU): byte-exact for data, scales and amax, and to tolerance for the `dprob` accumulator. Each runs through the entry and the shared wrapper, eagerly and under `jax.jit` with command buffers, with a repeated compiled call where an accumulator must restart:
  - GLU, dGLU, quant, wgrad with NVFP4 (E4M3 per 16) and MXFP4 (E8M0 per 32); wgrad includes an empty expert and the NVFP4 global scales.
  - quant MXFP8 with K- and N-major B, BF16 and FP8 output, with and without prob, and amax.
  - SReLU (MXFP8 to FP8 and to BF16, NVFP4, MXFP4) and dense dSReLU (MXFP8, NVFP4, MXFP4).
  - GLU + Hadamard (swiglu, geglu, srelu) and all seven output modes of GLU + Hadamard + quant (BF16 or NVFP4 D, with no, rowwise BF16, rowwise NVFP4, or colwise NVFP4 RHT), with non-default `norm_const`/`rht_norm_const`.
  - BF16 dense GLU, dGLU and wgrad.
- The new tests poison the JAX allocator first, so an output the kernel never writes cannot pass by reading back as zeros. Seen red: without it, the unwritten BF16-output D_col of dGLU matched Torch's equally unwritten buffer in isolation and failed only when memory was reused.
- `test_canonical_jax_wrappers_without_torch`: every wrapper above runs jitted in a subprocess with `sys.modules["torch"] = None`.
- API index runtime check against the editable package: only the GNN native exports differ, which this local cuDNN 9.24 build lacks. `pre-commit` passed on the changed files.
- **Rubin is not hardware-tested:** the Rubin host currently reports no GPU. As a compile-only check on SM100 with `CUTE_DSL_ARCH=sm_107a` and the device family forced to Rubin, GLU, dGLU, quant and wgrad each trace and lower through their Rubin kernel for MXFP8, NVFP4 and MXFP4 (12 combinations). No Rubin kernel was executed. The BF16 dense paths were not checked for Rubin.
- Not tested: FP4 wgrad on CuTeDSL < 4.8, which the entry rejects (the kernel's own layout workaround there would double-apply).
- PR CI's JAX lane uses CuTeDSL 4.6.2, which collection-skips these tests (they need >= 4.7); the 4.7/4.8 JAX lanes run nightly.
