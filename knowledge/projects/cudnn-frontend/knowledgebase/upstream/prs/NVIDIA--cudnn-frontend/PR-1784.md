## Summary

- `mxfp8_ref.compute_ref_backward`: round the scale multiplier and the separately formed Stats-derived exponent term to FP32 first, then evaluate their multiply-subtract in FP64 and round the exponent once to FP32 to model the FFMA operands and final rounding.
- `exec_sdpa_mxfp8`: compare dQ / dK / dV through `assert_close_mxfp8_grad`, which retains the existing FP8 count budget and `atol=0.125, rtol=0.2`, but caps every extra mismatch at `4 * atol` (0.5), including the element-budget path. The reduction length remains `keys` (`s_kv` for dQ, `s_q` for dK / dV). The ordinary elementwise tolerance still applies; lifting the extra-mismatch cap would require intermediate evidence.

## Why

Two `bprop.mxfp8.dense` L0 cases fail on SM103 (B300) on develop `4e27a6fa`. In both cases the kernel and the reference round one value to different E4M3 codes because it sits on a code midpoint. The original B300 investigation attributed these failures to reference/quantization rounding:

- **test169**, dV `[3, 3, 482, 41]` = 0.2988 vs reference 0.1113 (one element). Key 482 is attended by 4318 rows; several have `P*256` at 248.008–248.031, which is just above the E4M3 midpoint between 240 and 256. The reference's two FP32 roundings move them below it. Recomputing that element with the exponent rounded once gives 0.2989, the kernel's value, and with the old formula 0.1114, the reference's.
- **test236**, dK row `[1, 2, 11590, :]` off by ±0.25 in all 112 elements. Every one of the 13618 query rows has the same P (0.307974) for key 11590, and the generated Q is ±16 in every column. One dS value on a midpoint, rounded differently on the two sides, therefore shifts the whole row by `16 * 2^-6`. Recomputing dS in FP64 in the reference does not remove it: the residual difference comes from the kernel's own delta pre-pass and `ex2` approximation. This is the event `assert_close_fp8_grad` documents and budgets for the per-tensor FP8 suites (GB300 test310, one dS flip moving a dK row by 0.25). Here the flip affects 112 of 15,252,160 elements in 1 of 136,180 rows, with max |diff| 0.252, inside both the element budget (152) and the row cap (`4 * atol`).

The forward MXFP8 comparisons in the same file already use `assert_close_fp8_grad`. A real tile-level defect stays orders of magnitude above the budget.
