## Summary

Follow-up to #2009 (B10), which is merged. #2009 was squash-merged from its first commit (6148b3a2). Its second commit, 9b8de27a, answered a review comment about zero slopes. It was added to the branch after the merge, so develop does not have it. This PR is that commit, cherry-picked onto develop 18df4c38 without conflicts. The diff is unchanged; only the commit message was updated for the new base.

- `_emit_op`, `relu` with attributes: the slope line `max(x, lower) + slope * min(x - lower, 0)` now runs only for a nonzero `negative_slope` (`if slope:` instead of `if slope is not None:`). `relu(negative_slope=0.0, ...)` takes the existing no-slope line `max(x, lower)`, with `lower` defaulting to 0, then `min(., upper)` as before when `upper_clip` is set. The comment above the slope line says why.
- `test_matmul_relu_slope_clip.py`: new `test_relu_zero_slope_at_neg_inf`. It runs four zero-slope attribute sets on a matmul whose first rows accumulate to -inf and +inf and compares with `max(x, lower)`, then `min(., upper)`. The module docstring gets one sentence on the zero-slope case.

## Why

Found in review of #2009, the fix for finding B10 of an audit of the SM120 Frost kernel templates.

What was missing: #2009 computes `relu` with any `negative_slope` as `max(x, lower) + slope * min(x - lower, 0)`. With slope 0 and x = -inf that is `lower + 0 * -inf` = NaN. With an `upper_clip`, the following `min(., upper)` drops the NaN and returns `upper`. So `relu(negative_slope=0.0, lower_clip=0.5, upper_clip=6.0)` returns 6.0 at x = -inf, where develop before #2009 (24a8cd43) returned 0.5. With a lower clip and no upper clip the result is NaN, where 24a8cd43 returned the lower clip. Without a lower clip, 24a8cd43 already returned NaN (or `upper`), through the same `0 * -inf` in its slope-only line.

Minimal reproducer: a bf16 128x128x128 matmul followed by `relu`, bf16 output, FROST through `jit_from_cudnn_graph` with `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`, on an RTX PRO 6000 (SM120). A = 0.1 * randn with `A[0, 0:4, 0] = -inf` and `A[0, 4:8, 0] = +inf`, B = randn with `B[0, :, 0] = 1`, so output rows 0-3 are exactly -inf and rows 4-7 exactly +inf. Output at x = -inf:

| graph | FROST 24a8cd43 | FROST develop 18df4c38 | FROST this PR | eng1, eng7, eng10 |
|---|---|---|---|---|
| `relu(negative_slope=0.0)` | NaN | NaN | 0 | 0 |
| `relu(negative_slope=0.0, upper_clip=6.0)` | 6.0 | 6.0 | 0 | 0 |
| `relu(negative_slope=0.0, lower_clip=-1.0)` | -1.0 | NaN | -1.0 | -1.0 |
| `relu(negative_slope=0.0, lower_clip=0.5, upper_clip=6.0)` | 0.5 | 6.0 | 0.5 | 0.5 |

- The same four graphs without `negative_slope` give 0, 0, -1.0 and 0.5 on FROST at all three commits, and on eng1, eng7 and eng10 (one plan each). eng0 returns 0 at x = -inf for all eight graphs; it ignores the relu attributes.
- At x = +inf every column gives +inf, or 6.0 with the upper clip.
- For finite x, no FROST element is off cuDNN's formula on develop or on this branch. 24a8cd43 still has the finite-x error that #2009 fixed, in `relu(negative_slope=0.0, lower_clip=-1.0)`.

Why this is the right fix:

- The frontend sends a slope of 0.0 when none is set (`include/cudnn_frontend/node/pointwise.h`, `relu_lower_clip_slope.value_or(0.0)`). So `relu(negative_slope=0.0, ...)` and the same `relu` without `negative_slope` are one backend descriptor. Rule 9 of `python/cudnn/AGENTS.md` (backend and FROST share one graph contract) needs one descriptor to compute one function, on both engines and for both spellings.
- With a zero slope, `max(x, lower)` equals cuDNN's RELU_FWD formula, `x < lower ? lower + 0 * (x - lower) : x`, for every finite x. It is the line FROST already emits for the slope-less spelling. Finite and +inf inputs give the same values as before; x = -inf now gives `lower`, as the native engines do.
- A nonzero slope keeps the #2009 line, which gives -inf at x = -inf for a positive slope, as eng1, eng7 and eng10 do.

Why the change is in the shared module, not in `gemm/frost/sm120/`: since #1956 and #1993 this emitter exists only in `python/cudnn/gemm/frost/epilogue_codegen.py`. `sm120/epilogue_codegen.py` and `sm100/epilogue_codegen.py` both import `_emit_pointwise_dag`, which calls the shared `_emit_op`. No file under `gemm/frost/sm100/` is touched.

## API and compatibility impact

- Numerics change on both arch families (the emitter is shared), for `relu` with an explicit `negative_slope=0.0`, at x = -inf only. The result is now `lower_clip` (0 without one), then the upper clip. Develop returns NaN without an upper clip and `upper_clip` with one. Finite and +inf inputs do not change.
- Graphs with a nonzero slope or without a slope emit the same code as before. `relu_backward`, `leaky_relu` and `leaky_relu_backward` are not touched.
- SM100: the SM100 tree imports the same shared emitter and changes the same way. There is no SM100 copy left for a follow-up.
- Not changed: `leaky_relu(negative_slope=0.0)`. FROST records `leaky_relu` as its own op, and its emitter still computes `max(x, 0) + slope * min(x, 0)`. On this branch that gives NaN at x = -inf, where eng0, eng1, eng7 and eng10 (one plan each) give 0. That emitter is outside this change.
- No public API change.
