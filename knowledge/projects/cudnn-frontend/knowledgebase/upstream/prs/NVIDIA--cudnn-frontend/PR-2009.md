## Affected area

## Summary

The FROST GEMM epilogue now computes `relu` and `relu_backward` with a `negative_slope` the way cuDNN defines them when a clip is also set.

- Forward (`_emit_op`, `relu` with a nonzero `negative_slope`): the slope line is now `max(x, lower) + slope * min(x - lower, 0)`, with `lower` defaulting to 0. That is `x < lower ? lower + slope * (x - lower) : x`, followed by the existing `min(., upper)`. The `max(., lower_clip)` clamp that used to follow the slope is removed. With no `lower_clip`, or with `lower_clip=0.0`, the slope line is the same text as before.
- Forward, `relu` with `negative_slope=0.0`: takes the existing no-slope line `max(x, lower)`, then `min(., upper)`, instead of the slope line. For finite x both lines give the same values. At x = -inf the slope line computes `lower + 0 * -inf` = NaN, and the NaN-dropping `min(., upper)` then turns that into `upper`.
- Backward (`_emit_binary_ext`, `relu_backward` / `leaky_relu_backward` with `negative_slope`): the slope term is weighted by the existing `[x <= lower]` indicator instead of `1 - m`, where `m = [lower < x < upper]`. Inputs `x >= upper_clip` now get gradient 0. Without `upper_clip` the two weights are equal, so slope-only and (slope, lower) gradients do not change.
- New test `test_matmul_relu_slope_clip.py`: three forward (slope, lower) attribute sets and two backward (slope, upper) sets, through `jit_from_cudnn_graph` on one dense config per arch family, compared with cuDNN's formula. Four zero-slope forward sets run on a matmul whose first rows accumulate to -inf and +inf, compared with `max(x, lower)` then `min(., upper)`. The cell of the family the GPU does not run is skipped.

## Why

Found in an audit of the SM120 Frost kernel templates (finding B10).

cuDNN's backend documentation for `CUDNN_ATTR_POINTWISE_RELU_LOWER_CLIP` and `CUDNN_ATTR_POINTWISE_RELU_LOWER_CLIP_SLOPE` defines the forward, and the backward is its derivative:

- RELU_FWD: `if (x < lower_clip) x = lower_clip + lower_clip_slope * (x - lower_clip)`, then `min(x, upper_clip)`.
- RELU_BWD: `dx = dy * (x <= lower_clip ? lower_clip_slope : (x < upper_clip ? 1 : 0))`.

`negative_slope` is `lower_clip_slope` (`python/pygraph/pointwise.cpp`), and the node always sends `relu_lower_clip.value_or(0.0)` (`include/cudnn_frontend/node/pointwise.h`). So `relu(negative_slope=s, lower_clip=0.0)` and `leaky_relu(s)` are the same backend descriptor. FROST computed `max(max(x, 0) + s * min(x, 0), lower_clip)` instead: the slope started at 0 and `lower_clip` acted as a second, hard clamp. In the backward it computed `m + s * (1 - m)`, which gives `s` wherever `m = 0`, including `x >= upper_clip`. The audit ran the same graphs through the native runtime-fusion engines on an RTX PRO 6000: all 17 eng1, eng7 and eng10 plans follow the documented rule in these cases (eng0 ignores every relu attribute).

Reproducer: a bf16 128x128x128 matmul followed by the op, bf16 output, `jit_from_cudnn_graph` with `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`, RTX PRO 6000 (SM120), develop 24a8cd43. Counts are elements outside atol/rtol 1e-2 of cuDNN's formula, out of 16384 (the new test's data):

| graph | FROST on 24a8cd43 | cuDNN rule | elements off |
|---|---|---|---|
| `relu(negative_slope=0.1, lower_clip=0.0)` | plain ReLU: every x < 0 gives 0 (x = -1.62 gives 0.0) | `0.1 * x` (-0.162) | 7684 |
| `relu(negative_slope=0.1, lower_clip=-1.0)` | `0.1 * x` on [-1, 0) and `max(0.1 * x, -1)` below (x = -1.62 gives -0.162) | `x` on [-1, 0), `-1 + 0.1 * (x + 1)` below (-1.0625) | 8208 |
| `relu(negative_slope=0.1, lower_clip=0.5, upper_clip=2.0)` | every x < 0.5 gives 0.5 (x = 0.09 gives 0.5) | `0.5 + 0.1 * (x - 0.5)` (0.459) | 10320 |
| `relu_backward(negative_slope=0.1, upper_clip=1.0)` | `0.1 * dy` for x >= 1 | 0 | 4709 |

The worked x values come from a scratch repro with larger A; the counts come from the test.

Why the fix is in the shared module and not in `gemm/frost/sm120/`: since #1956 and #1993 these emitters exist only in `python/cudnn/gemm/frost/epilogue_codegen.py`. `sm120/epilogue_codegen.py` and `sm100/epilogue_codegen.py` both import `_emit_pointwise_dag` from it, which calls the shared `_emit_op`, and the facade copies the shared emitters over the active family module (`_SHARED_EXPORTS`). An SM120-only fix would need a second copy of the pointwise emitter and would leave the two trees computing different ReLUs. No file under `gemm/frost/sm100/` is touched.

The forward keeps the branch-free max/min form the emitter already uses. For finite x it is exactly cuDNN's expression: below `lower` it is `lower + slope * (x - lower)`, and above it `x + slope * 0 = x`. It is not a 0/1-mask product, so `x = +inf` stays `+inf` and `x = -inf` gives `-inf` for a positive slope. This also follows Rule 9 of `python/cudnn/AGENTS.md`: the backend and FROST serve one graph contract, so the same graph must mean the same function on both.

A zero slope takes the no-slope line instead. The node also sends `relu_lower_clip_slope.value_or(0.0)`, so `relu(negative_slope=0.0, ...)` is the same backend descriptor as the same `relu` without a slope. At x = -inf the slope line would give NaN, or `upper` once the upper clip follows. One plan each of eng1, eng7 and eng10 on the RTX PRO 6000 returns the limit for both spellings instead: 0 for `relu(negative_slope=0.0)` and for `relu(negative_slope=0.0, upper_clip=6.0)`, -1 for `relu(negative_slope=0.0, lower_clip=-1.0)`, and 0.5 for `relu(negative_slope=0.0, lower_clip=0.5, upper_clip=6.0)` (eng0 returns 0 in all four). `max(x, lower)` then `min(., upper)` gives those values, and the same values as the slope line for every finite x. 24a8cd43 already returned NaN and 6 for the first two graphs, through the same `0 * -inf` in its slope-only line.

Two behaviours that are separate audit findings are left as they are:

- NaN input still maps to a finite value. The slope line uses `cute.math.max/min` like the rest of the ReLU family (G4.2).
- The backward still multiplies `dy` by a 0 / 1 / slope factor, so an inf or NaN `dy` where the factor is 0 gives NaN, as in every `relu_backward` variant today (G4.3). With this change, `x >= upper_clip` is one of those zero-factor positions for the slope variant too.

## Related issues

## API and compatibility impact

- Numerics change on both arch families (the emitter is shared), for these attribute combinations:
  - `relu` with a nonzero `negative_slope` and a `lower_clip` (any value, including 0.0) now computes `x < lower ? lower + slope * (x - lower) : x`, then applies the upper clip.
  - `relu` with `negative_slope=0.0` and a negative `lower_clip` now computes `max(x, lower)`, then the upper clip, like the same graph without the slope (24a8cd43 returned plain ReLU for finite x). With `lower_clip >= 0` the values do not change.
  - `relu` with `negative_slope=0.0` and no `lower_clip`: only x = -inf changes, to 0 before the upper clip (was NaN, or `upper_clip` when one is set).
  - `relu_backward` with `negative_slope` and `upper_clip` now gives gradient 0 for `x >= upper_clip` (was `slope * dy`).
  Every other `relu`, `leaky_relu`, `relu_backward` and `leaky_relu_backward` attribute set produces the same values as before, and the forward with a nonzero slope and no `lower_clip` emits identical source.
- Not changed: `leaky_relu(negative_slope=0.0)`. FROST records it as its own `leaky_relu` op, whose emitter still computes `max(x, 0) + 0 * min(x, 0)`. That gives NaN at x = -inf, where eng0, eng1, eng7 and eng10 (one plan each), and now `relu(negative_slope=0.0)`, give 0. That emitter is outside this change.
- SM100: at 24a8cd43 there is no separate SM100 copy of these emitters; the SM100 tree imports the same shared functions. This PR therefore changes SM100 numerics in the same way, and nothing under `gemm/frost/sm100/` is left for a follow-up. The FROST conv epilogue has its own copy of the old forward convention (`python/cudnn/conv/frost/templates/epilogue.py:111-128`), and its test reference encodes that convention (`test/python/conv/frost/epilogue_cases.py:32-48`). That engine is not changed here and needs a follow-up.
- Not changed: the `relu(negative_slope, upper_clip)` forward when `slope * x` exceeds `upper_clip`. FROST applies the documented `min(y, upper)`. The audit measured the native eng1, eng7 and eng10 engines returning `max(min(x, upper), lower + slope * (x - lower))` there (slope 0.2, upper 2, x = 15 gives 3). That is a difference between the native engines and the documentation, outside this fix. The new test keeps x in the range where both agree.
- FlashInfer (audit finding G5.1): FlashInfer's cudnn_frost exporter (`flashinfer/fused_moe/backends/cudnn_frost/export.py`) writes the SwiGLU-step up clamp as `relu(up, negative_slope=1.0, lower_clip=-7.0, upper_clip=7.0)`. Its -7 lower bound comes only from the old behaviour; under cuDNN's definition, a slope of 1 makes the lower clip a no-op. FlashInfer's shipped kernels are pre-rendered sources and do not change with this PR.
  - Re-exporting against a frontend with this fix would silently drop the lower bound. On FlashInfer's bf16 `grouped_gemm1_swiglu_step` graph (S=N=K=256, E=G=4, normal and swap-AB SM120 tiles), 9681 of 65536 outputs differ from `clamp(up, -7, 7)`; all 65536 match `min(up, 7)`.
  - Writing the clamp as `relu(up, lower_clip=-7.0, upper_clip=7.0)`, without the slope, gives `clamp(up, -7, 7)` both before and after this change (0 of 65536 differ in both cases).
  - That one-line exporter change has to land in FlashInfer before its next re-export of the FROST sources. Both exported architectures carry the old lowering (`max(leaky, -7)`) in their pre-rendered epilogue fragments: `sm_120a`, rendered by the SM120 tree, and `sm_107a`, rendered by the SM100 tree through the same shared emitter. It is outside this repository and not part of this PR. The gate clamp `relu(silu, negative_slope=1.0, upper_clip=7.0)` is not affected.
