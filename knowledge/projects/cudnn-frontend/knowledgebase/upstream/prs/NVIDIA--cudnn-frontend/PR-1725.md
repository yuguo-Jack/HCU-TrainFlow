## Summary

<!-- What changed? Keep the scope concise. -->
Add `graph.serialize(as_bytes=True)` and support `bytes` input in
`graph.deserialize()`. The default `serialize()` return type remains
`list[int]` for backward compatibility.

## Why

<!-- What problem does this solve, and why is this approach appropriate? -->

Graph serialization produces a binary payload. The existing `list[int]`
representation comes from the automatic conversion of C++
`std::vector<uint8_t>`, rather than the semantics of the data.

`bytes` represents this payload more naturally and avoids constructing
a Python list with one entry per byte, reducing conversion overhead and
memory usage. The serialized format and contents remain unchanged.

Unlike graph serialization, device properties and kernel cache
serialization produce JSON text, so their `str` return types remain
appropriate.

## API and compatibility impact

<!-- Note public API, supported GPU/cuDNN/CUDA/Python versions, performance, or backward-compatibility changes. Write "None" if not applicable. -->

This behavior predates the nanobind migration: both pybind11 and nanobind
automatically convert `std::vector<uint8_t>` to `list[int]`.

Since graph serialization produces binary data, `bytes` is a more natural
representation. This PR adds bytes support while preserving the existing
API behavior.

Would it be preferable to return `bytes` by default and accept only `bytes`
for binary deserialization? That would be a breaking API change.
