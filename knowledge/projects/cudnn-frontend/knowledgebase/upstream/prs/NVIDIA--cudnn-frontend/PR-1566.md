## Affected area

C++ header `include/cudnn_frontend_shim.h` (`NV_CUDNN_FRONTEND_USE_DYNAMIC_LOADING`, used by the Python package), plus three callers that read device properties: `context.h`, `graph_interface.h` and `experimental/sm100_rms_norm_silu_engine.h`.

## Summary

Fixes #1563.

**The problem.**
- Under dynamic loading, the shim may load a `libcudart` whose major version differs from `CUDART_VERSION`.
- This is the default situation for the published wheel. The `nvidia_cudnn_frontend-1.31.0` cp312 wheel references `cudaStreamGetCaptureInfo` and not `cudaStreamGetCaptureInfo_v2`, so it is a CUDA 13 build.
- Next to a CUDA 12 torch, only `libcudart.so.12` is present, so that is what the shim loads.
- The shim resolves each runtime entry point by name and calls it with the compiled prototype. Three entry points changed ABI between CUDA 12 and 13:

| entry point | CUDA 13 build on a CUDA 12 runtime (develop) |
|---|---|
| `cudaStreamGetCaptureInfo` | On CUDA 12, the unversioned symbol is the legacy 3-parameter call, so the capturing graph is never reported. The #1195 retention of plans and host-copy buffers is skipped silently. |
| `cudaGraphNodeGetDependentNodes` | CUDA 13 added an edge-data parameter. On CUDA 12 the call returns `cudaErrorInvalidValue`, so `update_cuda_graph` fails. |
| `cudaGetDeviceProperties` | The `cudaDeviceProp` layout moved, so `multiProcessorCount` reads 1. The RmsNorm+SiLU OSS engine sizes its grid from it. |

The reverse case also fails. A CUDA 12 build on a CUDA 13 runtime aborts on the first capture query, because CUDA 13 does not export `cudaStreamGetCaptureInfo_v2`.

**The fix.**
- `loaded_cudart_version()` queries `cudaRuntimeGetVersion` once.
- `cuda_stream_get_capture_info` and `cuda_graph_node_get_dependent_nodes` now call the loaded runtime's prototype, through function-pointer types that do not depend on the compile-time headers.
- The three internal readers of compute capability and SM count now use `cudaDeviceGetAttribute`, whose ABI is stable across majors. It is exposed as a new shim function, `cuda_device_get_attribute`.
- `cuda_get_device_properties` is kept. A CUDA 12 build now resolves `cudaGetDeviceProperties_v2` when a CUDA 12 runtime is loaded, as its headers do; before, the unversioned symbol filled the CUDA 11 layout. A comment notes that the struct is only valid for the matching major.
- Statically linked builds (no dynamic loading) are unchanged.

I audited every `NV_FE_CALL_TO_CUDA` symbol in `include/` (38 of them) against the exports of `libcudart.so.12` (12.8.90) and `libcudart.so.13` (13.2). The three above are the only ones whose ABI differs. `cudaEventElapsedTime` has a `_v2` in 12.8, but its prototype is the same.

## Testing

All runs are on B200 with cuDNN 9.27.

**C++ shim probe, 2×2 matrix.** The shim is built with CUDA 12.8 or 13.2 headers and run against `libcudart.so.12` (12.8.90, pip) or `libcudart.so.13` (13.2), selected with `CUDNN_FRONTEND_CUDART_LIB_NAME`:

| build → runtime | develop | this branch |
|---|---|---|
| 13 → 13 | OK | OK |
| 13 → 12 | SM count 1; capture graph `NULL`; dependent nodes `cudaErrorInvalidValue` | SM count 148 (attribute); graph reported; dependent nodes 1 |
| 12 → 12 | OK | OK |
| 12 → 13 | abort: `Unable to find symbol cudaStreamGetCaptureInfo_v2` | capture, dependent nodes and attributes OK. `cuda_get_device_properties` itself still mis-reads across majors; no FE code calls it any more. |

**Python package, built with CUDA 13.2.** I ran `populate_cuda_graph`, then `update_cuda_graph` with new buffers, then a replay checked against `torch.bmm`:

| runtime loaded | develop | this branch |
|---|---|---|
| `libcudart.so.12` | `update_cuda_graph` raises `cuda_graph_node_get_dependent_nodes(...) failed with invalid argument` | OK, max abs err 0.014 (fp16) |
| `libcudart.so.13` | OK | OK |

**pytest** `-m "L0 or L1"` on `core/graph`, `core/test_dispatch.py` and `norm/graph`:
- develop with `libcudart.so.12`, this branch with `libcudart.so.12`, and this branch with the default runtime: each 5465 passed, 23 skipped, 1 failed.
- The one failure is `test_stream_captured_graph_outlives_the_cudnn_graph` ("OSS RmsNorm+SiLU engine not built"). It fails identically on develop in this local environment and is green in CI.
- The existing suite does not exercise the cross-major path. CI loads a single runtime, so there is no in-repo regression test here.

**`-Wall -Wextra -Werror`:** a syntax-only TU of `cudnn_frontend.h` is clean for dynamic and static builds, with both CUDA 12.8 and 13.2 headers.

Not tested: real Windows, and the RmsNorm+SiLU engine's grid sizing (the engine is not built locally).
