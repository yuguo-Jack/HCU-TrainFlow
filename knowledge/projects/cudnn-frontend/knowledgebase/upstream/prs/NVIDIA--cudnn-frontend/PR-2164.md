# test: refresh three L0 tests left behind by recent changes

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2164) · state: closed · merged: True

## Original PR description

## Problem

Three L0 tests fail on develop. On a B300 the full `-m "L0 or L1"` run of these directories shows them; the first two do not depend on the device at all, and the third fails on every part that is not cc 10.7.

- **`test_bsa_fp8_blk128_dispatch_preserves_v_layout_and_metadata[120]`** monkeypatches the arch, so it fails on any GPU. Since #2004, the SM120 blk128 path passes `k_quant_block_size` to `_quantize_sage_bhsd` and to `_bsa_attn_fwd_sm120_fp8`. The test's stubs still assert the old keyword sets: `assert {'v_block_size': 128, 'k_quant_block_size': 16} == {'v_block_size': 128}`.
- **`test_the_two_bodies_differ_only_in_the_arch_delta`** is a pure source comparison of the two LayerNorm-prologue dual-GEMM bodies. Since #1993, both bodies open with an 8-line module docstring, so the guard `assert spans[0] > 50 and spans[1] > 50` fails (`8 > 50`). The diff check after it still passes (16 changed lines, all arch constants or comments).
- **`test_check_support_declines_unserved_declarations_before_any_device_work[kw2-...]`** declares a head-major `(B, N, H, S, D)` q and expects the layout decline "does not bind". Since #2038, `config_sm100.dense_bind_strides` binds any B / H / S stride permutation, so `activation_binds_zero_copy` now returns True for that layout. `check_support` moves past the layout check: off cc 10.7 the arch decline fires instead, and on cc 10.7 nothing in this check raises.

## Change

- **BSA:** the SM120 stubs expect `k_quant_block_size=16` (the default) on the quantizer and the launch.
- **trimul:** the guard only checks that each body has a module docstring before the code.
- **triangle_attention:**
  - the decline case uses a layout that still does not bind: the "layout_left" memory form with a head-dim stride of 2;
  - the unused `_head_major_desc` helper is removed;
  - the `activation_binds_zero_copy` docstring and the `check_support` decline message no longer require a token-major nest.

On a CPU-only check of the current tree, `activation_binds_zero_copy` returns True for head-major and "layout_left" strides, and False for the new strided-head-dim layout.

Not changed, and not checked here because I have no cc 10.7 part: the `triangle_attention` function docstring and its repack comments still describe a head-major activation as repacked with a counted copy. The Rubin-only test `test_head_major_inputs_are_repacked_with_counted_copies_and_the_output_follows_q` asserts those copies. The function decides its repacks through the same predicate (`_activation_zero_copy`), so since #2038 it should no longer repack a head-major input, and that test probably fails on cc 10.7 too.

## Tests

On a B300 with this change, `test_BSA_attention_fp8.py`, `test/python/triangle_attention` and `test/python/triangle_multiplicative_update` at `-m "L0 or L1"`: 230 passed, 73 skipped. On develop, the three tests above fail in the same run.
