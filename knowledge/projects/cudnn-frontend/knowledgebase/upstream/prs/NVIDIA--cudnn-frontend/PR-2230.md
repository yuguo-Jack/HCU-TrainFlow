# gemm(frost): bind the CUDA context before each compiled GEMM launch

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2230) · state: open · merged: False

## Original PR description

## Problem

A compiled FROST GEMM launches through driver-API calls on the calling thread: first the output fills, then the kernel. An autograd backward runs on a worker thread whose context stack can still be empty. If the FROST GEMM is the first CUDA work on that thread, the launch aborts the whole process:

```
CUDA Dialect Assertion failed on CUDA error: cudaErrorDeviceUninitialized - invalid device context
Fatal Python error: Aborted
```

`swiglu_mlp` hits this through `_frost_dswiglu`. On B300 (sm_103), `test/python/gemm/test_swiglu_mlp.py::test_swiglu_mlp_partial_grad` aborts every time for `x-only`, `Wg-only` and `Wu-only`, and passes for `Wd-only`, `weights-only` and `all`. The three failing cases skip the `dWd` matmul, so the FROST GEMM is the worker's first CUDA call. In the passing cases, the cuDNN matmul that runs first happens to bind the context. Under xdist this shows up as `worker 'gwN' crashed`.

How I narrowed it down (B300, `swiglu_mlp` x-only forward + backward):

| variant | result |
|---|---|
| as is | abort, `cudaErrorDeviceUninitialized` |
| `torch.autograd.set_multithreading_enabled(False)` | passes |
| `ensure_current_context(stream, device)` before `_frost_dswiglu` | passes |
| calling `_frost_dswiglu` on a plain new `threading.Thread` | passes |

So the trigger is the autograd worker, not threads in general.

## Change

`python/cudnn/gemm/frost/compiler.py` calls `ensure_current_context(stream, device)` in the two launch entries, right after the existing `_check_plan_device` and before any fill or launch:
- the fused GEMM's `lowered` closure. `__call__`, `run_resolved` and direct `run_resolved` callers such as `gated_attention_block/kernels/proj_gemm.py` all reach it;
- `_CompiledMoeBase.__call__`, which every grouped/MoE launch goes through.

The order is deliberate. `_check_plan_device` still runs first, so a real device mismatch is still refused rather than masked by the bind.

This is the same per-launch bind the SDPA DSL launch paths already use (`sdpa/fwd/api_dsl.py`, `sdpa/bwd/prepared_sm100*.py`).

New test `test/python/gemm/frost/test_launch_on_autograd_worker.py`:
- It compiles a GEMM with `jit_from_cudnn_graph` and launches it once on the main thread.
- Then it launches it again as the first CUDA work in an autograd backward.
- It runs in a child process, so the abort fails one test instead of killing the pytest worker.

## Testing

B300 (sm_103), driver 610.57.04, torch 2.14.1+cu130, cuDNN 9.27, CuTe DSL 4.8.1. Validated on develop `e77fe6d4`, whose `compiler.py`, `_device.py`, `swiglu_mlp.py` and `test_swiglu_mlp.py` are identical to this PR's base `a0f7b9f4`.

- New test:
  - develop: 2 of 2 fail (child exits -6 with `cudaErrorDeviceUninitialized`);
  - this PR: 2 of 2 pass.
- `test/python/gemm/test_swiglu_mlp.py` (serial):
  - develop: aborts on the first of the three cases;
  - this PR: 37 passed, 2 skipped.
- `-m L0 test/python/gemm/frost`:
  - this PR: 7,936 passed, 3,849 skipped.
  - 5 failed, identical to develop: they are `benchmark`/`samples` import tests, and my test tree does not contain those directories.
- Host cost: on a thread whose context is already bound, one `ensure_current_context` call takes about 0.21 µs (native path). A small direct-JIT GEMM call costs about 32 µs of host time. An interleaved A/B over 6 process pairs showed no difference above the host noise, which was 17–42 µs per process on this shared machine.

`black 26.3.1 --line-length 160 --fast` is clean.
