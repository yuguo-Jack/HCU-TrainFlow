## Summary

The SM120 FROST GEMM codegen now declares the compile-time fake of a non-segmented quant-scale output (the scale tensor of `block_scale_quantize`) with a fresh `cute.sym_int64()` for every non-unit extent.

Before, `_tap_fake_shape` emitted the kernel's own `sym_m` for the scale's rows whenever they equalled the kernel's build M, and a literal otherwise. It treated the other two extents the same way with `(sym_n // block_size)` and `sym_l`, but those never refused a call: TVM-FFI binds the derived `(sym_n // block_size)` to a Var of its own, and the dense batch is fixed. Only the `sym_m` binding was a real tie.

Nothing else changes. The epilogue stores the scales through the tap's raw pointer with the same index math, and the host checks of the scale buffer are untouched.

## Why

The scale buffer of a `block_scale_quantize` output is a plan constant. Its output rule is CONST (`recipe._output_rule`), and on SM120 `_check_runtime_quant` re-runs the quant gates at the call's kernel-frame (M, N). A call that keeps the padded extents is therefore admitted. An F8_128x4 row-quant scale has rup(M, 128) rows, so a plan built at M = 256 admits a call at M = 200 with the same [1, 256, 8] scale buffer.

The compile fake disagreed with that contract. The kernel's M is the graph's M (the token count S for MoE), or the graph's N in a swap-AB plan, which runs the graph transposed. `_tap_fake_shape` emitted `sym_m` for the scale's rows whenever they equalled that M at build time. For example:

- row quant: whenever M (S) is a multiple of 128;
- col quant: whenever rup(N, 128) == M;
- swap-AB row quant: whenever rup(M, 128) == N (rup(S, 128) == N for MoE).

The TVM-FFI spec converter allocates one Var per `SymInt` object, so every launch then checked the scale's row count against the kernel's runtime M.

Minimal reproducer on an RTX PRO 6000 (SM120):

- Graph: bf16 A [1, 256, 128] (K-major) times bf16 B [1, 128, 256], then `matmul`, then `block_scale_quantize(block_size=32, axis=-1)`. The data output is FP8_E4M3 [1, 256, 256]; the scale is FP8_E8M0 [1, 256, 8] with `F8_128x4` reordering.
- Call: build the FROST plan, then run it with A [1, 200, 128], data output [1, 200, 256] and the same [1, 256, 8] scale buffer.
- Observed: `ValueError: Mismatched c_tap_1.shape[0] on argument #4 when calling: _host(...), expected to match a_0.shape[0]`. The error is the same through `graph.execute(...)` with the M = 200 buffers, through `graph.execute_plan_at_index(...)` with `override_shapes`, and through the plan from `jit_from_cudnn_graph`.
- Expected: the call runs, as FROST's own checks allow. A plan of the same graph built at an unaligned M (for example 200, whose fake carries the literal 256) runs every M in that padding.

The other affected plans fail the same way:

- The plain MoE template `sm120_moe_grouped_matmul_fwd.py` and the block-scaled MoE template `sm120_moe_grouped_block_scale_matmul_fwd.py`, where `sym_m` is the token count S. They refuse S = 200 after a build at S = 256 (on argument #6 and #8).
- Swap-AB plans, on another axis. In dense swap-AB (`sm120_matmul.py` on the transposed chain), `sm120_moe_grouped_matmul_fwd_swap_ab.py` and `sm120_moe_grouped_block_scale_matmul_fwd_swap_ab.py`, `sym_m` is the graph's N (the weight-feature extent). The fake therefore tied the scale rows rup(M, 128) to N when the two were equal. Token-count changes kept working, but a call that changed N inside the scale padding was refused:
  - dense swap-AB built at M = N = 256 and called with N = 224: `Mismatched c_tap_1.shape[0] on argument #4`;
  - MoE swap-AB and block-scaled MoE swap-AB built at S = N = 256 and called at S = 200 with weights of N = 224: the same error on #6 and #8.
- GATHER plans, plain and block-scaled, render the same fake. A GATHER plan counts S in routed rows (the `token_index` extent), and the token operand's source rows have a symbol of their own (`sym_source_m`, or `sym_source_n` in the swap-AB templates). So `sym_m` is the routed S in the normal orientation and the weights' N under swap-AB, and the scale rows were tied the same way. Built at 256 routed rows gathered from 137 token rows:
  - plain and block-scaled (NVFP4) GATHER plans refuse a call at 200 routed rows, on argument #7 and #9;
  - their swap-AB versions refuse a call at 200 routed rows with weights of N = 224, on the same arguments. As in the other swap-AB plans, a call that changes only the routed rows runs.

Not affected: segmented (per-group) scales already used fresh symbols. COMBINE plans allow no operation after the grouped GEMM, so they cannot carry a quant-scale output. SCATTER plans cannot either: `_check_executable` declines a SCATTER graph with quantization or a reduction (`sm120/compiler.py:1608-1610`). `sm120_block_scale_matmul.py` declines quant epilogues on SM120 (`_DENSE_BLOCK_SCALE_QUANT_DECLINE`).

Why this fix:

- The fake only gives TVM-FFI its calling convention. The epilogue addresses the scale blob through `mC_tap_i.iterator.raw_ptr()`, with plan-literal and `problem_size` stride math.
- The host already holds the buffer to the declared shape: the CONST output check in `lowered()` on the dense path, and `_expected_output_shape` in every MoE launcher, including the swap-AB one. It also holds the buffer to the runtime padding through `_check_runtime_quant`, which runs on every SM120 path: all three SM120 compiled classes set `_validate_runtime_quant`, and `_launch_moe_swap_ab` calls it directly.
- Fresh symbols match two existing patterns: the segmented-scale branch directly above in the same function, and the SFA / SFB fakes of the block-scale templates.

The audit named one other option: emit the declared extents as literals. I did not take it. Literals would put the padded M bucket into the rendered source. Dense row-quant plans built at M = 256 and M = 384 render one source today and share one compiled artifact; with literals they would compile separately, which is the over-keying that Rule 4 warns against. With fresh symbols, these builds render byte-identical sources:

- dense row-quant plans built at M = 200, 256 and 384
- MoE plans built at S = 200, 256 and 384

This was found in an audit of the SM120 Frost kernel templates (finding B33).

## API and compatibility impact

- Some calls passed FROST's own checks but were refused by the TVM-FFI front door. They now run. These are calls on plans whose non-segmented quant-scale rows equalled the kernel's build M, where the call moves the kernel's M but keeps the F8_128x4 padded extents. For example:
  - a runtime M (dense) or S (MoE; routed rows for GATHER) that differs from the build value, on plans with a row-quant scale built at a 128-aligned M (S), or with a col-quant scale where rup(N, 128) == M;
  - in swap-AB plans (dense, MoE and block-scaled MoE, including GATHER), a runtime N that differs from the build value, on plans whose row-quant scale rows rup(M, 128) (rup(S, 128) for MoE) equal the build N.

  No graph is newly declined, and the numerics of calls that ran before are unchanged.
- Calls that change the padded extents are still refused before launch with the same `scale_dim` ValueError (`F8_128x4 ... block_scale_quantize scale output currently requires scale_dim=...`). On the dense path it comes through `explain()`, which adds its existing kernel-frame note for swap-AB plans; the MoE launchers raise it directly from `_check_runtime_quant`. The new dense test checks this for each of its cases.
- The rendered kernel source changes for plans with a non-segmented quant-scale output, so their cached kernels recompile once.
- SM100: the same code is at `python/cudnn/gemm/frost/sm100/epilogue_codegen.py:440` (`_tap_fake_shape`, lines 423-443). It is intentionally left for a follow-up; the repo convention is that such fixes land in both trees. Two notes for that follow-up, both from reading the code only (no SM100 GPU was available, so neither was run):
  - The SM100 compiled classes do not set `_validate_runtime_quant`, so the SM100 dense and non-swap MoE launches do not re-check the quant extents at runtime (the SM100 MoE swap-AB launcher does, inline). On those two paths, for 128-aligned builds, the `sym_m` tie is what currently refuses a runtime M whose padded rows exceed the declared blob. Porting this change alone would remove that refusal, so the port also needs the host-side runtime quant check there.
  - An SM100 dense or non-swap MoE plan built at an unaligned M already renders a literal scale extent, and I found no other runtime check that holds a call to that plan's padding. Such a plan may therefore already admit a runtime M whose padded rows exceed the declared blob, and store past it.
