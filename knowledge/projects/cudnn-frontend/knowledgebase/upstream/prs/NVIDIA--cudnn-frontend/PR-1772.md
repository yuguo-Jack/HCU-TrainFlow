## Affected area

## Summary

`pygraph.tensor_like()` now picks the declared dtype with `_buffer_dtype_to_cudnn()`, the same table `execute()` uses to describe the buffer. `_buffer_dtype_to_cudnn()` itself now falls back to the dtype's name when the dtype object is not a key, so the declaration and the cupy and numba paths of `execute()` resolve such a dtype the same way. A new CPU-only test file, `test/python/core/graph/test_tensor_like_dtype.py`, covers it.

## Why

`tensor_like()` looked up `template.dtype` with `_torch_to_cudnn_data_type()`, which only knows torch dtypes. A CuPy, JAX or numpy array has a numpy dtype, so the lookup returned None and the tensor fell back to the graph's `io_data_type`. For example, in a graph built with `io_data_type=HALF`, `g.tensor_like(cupy.zeros((4, 8), cupy.float32))` was declared HALF, while `execute()` describes the same buffer as FLOAT through `_buffer_dtype_to_cudnn(data.dtype)`. An int32 array was declared HALF as well. Every op builder that accepts framework arrays goes through `tensor_like()` via `_ensure_tensor()`, so `g.matmul(A=cupy_a, B=cupy_b)` declared both inputs HALF too. The plan is built from the declaration, so it would read the buffer with the wrong element type. The classic C++ `PyGraph::tensor_like(py::object)` in `python/pygraph/pygraph.cpp` takes the dtype from the DLPack capsule, so this case used to work.

The name fallback is there for ml_dtypes types like JAX bfloat16 and fp8. If the lookup table was built before ml_dtypes registered its types, `np.dtype(ml_dtypes.bfloat16)` is not a key, but its name `"bfloat16"` is, and the name is also what the DLPack path in `execute()` looks up. The fallback started out in `tensor_like()` only and moved into the shared lookup after review, since the cupy and numba paths in `execute()` call the same function with `data.dtype`. Torch dtypes are in the same table, so torch callers get the same dtype as before.

## Related issues

None filed.

## API and compatibility impact

No signature changes. Non-torch arrays passed to `tensor_like()` or to an op builder are now declared with their own dtype instead of `io_data_type`. Code that relied on the old behavior to get an io_data_type declaration for, say, a float32 CuPy array would now get FLOAT. That old declaration did not match the buffer, so I don't expect anyone depends on it.

## Testing

I don't have a GPU or a cuDNN build here, so I ran the Python tests against the source tree with an enums-only stand-in for `cudnn._compiled_module`, outside the repo, and with `--noconftest` because the shared conftest needs cuda-python and a device.

`pytest --noconftest -p stubplugin core/graph/test_tensor_like_dtype.py`, where `stubplugin` installs the stand-in, passes 7 of 7 with torch installed. With numpy only, 6 pass and the torch case is skipped. With the `_pygraph.py` change reverted, 5 of them fail with `assert data_type.HALF == data_type.FLOAT` (or INT32 / BFLOAT16). The second commit adds a check that `_buffer_dtype_to_cudnn()` resolves a name-only bfloat16 dtype. With numpy and ml_dtypes, 7 pass and the torch case is skipped, and reverting the `datatypes.py` part makes that check and the bfloat16-by-name case fail.

`core/graph/test_graph_native.py` gives the same result with and without the change. 47 pass, 1 is skipped (SDPA support check), and 6 fail in both runs because those tests lower to the C++ graph, which the stand-in module cannot do. These should be run on a real build.

I also checked by hand with ml_dtypes installed that a bfloat16 and a float8_e4m3fn numpy array are declared BFLOAT16 and FP8_E4M3, with the lookup table built before ml_dtypes was imported.
