## Summary

The SM120 block-scale mainloops (dense, MoE grouped, MoE grouped swap-AB) now clear the K-padding bytes of the F8_128x4 scale word that holds a row's last K-scale before the block-scaled `mma.sync` reads them.

- Once per compute warp: `sf_last = ceil(K / block_size) - 1`, `sf_tail_word = sf_last >> 2` (the K word holding the row's last live scale) and `sf_tail_keep`, an AND mask that keeps that word's live bytes (`0xFF`, `0xFFFF`, `0xFFFFFF`, or all ones when `ceil(K / block_size)` is a multiple of 4).
- Every k-tile: for each of the stage's `sf_k4` word positions, select `sf_tail_keep` when it is `sf_tail_word` and all ones otherwise, then AND every SF word loaded from SMEM, for SFA and SFB. In the MoE templates the AND is applied before `_sf_kblk_words`, so the duplicated-scale PRMT path (fp4 + e4m3 at block 32) sees the cleared bytes too. A one-sided (fake-dequant) side still uses the constant `sf_one` words.
- Tests: two new SM120 tests fill the K-padding bytes of both blobs with a NaN encoding. `to_blocked()` gets an optional `k_pad_byte` argument (default 0, no change for existing callers) and `_run_bs_numeric` / `_run_e2e` pass it through; `_run_e2e` sizes the static token-SF capacity by the padded scale width `4 * ceil(sf_k / 4)`, which is the same value for every existing caller (all have `sf_k % 4 == 0`).

## Why

Whenever `ceil(K / block_size)` is not a multiple of 4, the last F8_128x4 word of every row holds 1-3 padding bytes: for example MXFP8 / MXFP4 with `K % 128` in {32, 64, 96} (gpt-oss: `K = 2880`) or NVFP4 with `K % 64 == 32`. The SF descriptor's K extent `rest_k` rounds up, so TMA loads that word from the blob; only whole words past `rest_k` are zero-filled. The last k-tile still issues every k-block's block-scaled `mma.sync`, and the k-blocks past K (or the zero-filled half of a 2X / 4X k-block that straddles K) take those padding bytes as `scale_A` / `scale_B`. PTX defines `D = (A * scale_A) * (B * scale_B) + C`, so a padding byte that encodes NaN (UE8M0 `0xFF`, UE4M3 `0x7F` / `0xFF`) gives `0 x NaN = NaN`: one such byte in SFA turns that whole output row into NaN, one in SFB the whole output column (in MoE, that column for every group that uses the expert). Nothing writes or validates these bytes: the runtime blob checks look at size and layout only, and Frost's own F8_128x4 quantize epilogue leaves them unwritten, so a Frost producer writing into a `torch.empty` scale buffer can feed them to this kernel.

Reproducer at 24a8cd43 (`jit_from_cudnn_graph`, `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`, data and real scales fixed, only the K-padding bytes changed):

| template | case | pads `0x00` | NaN pads |
|---|---|---|---|
| dense | MXFP8 M=256 N=200 K=320 (pad slots 10-11), one SFA row's pads `0xFF` | exact | that row 200/200 NaN |
| dense | same, one SFB row's pads `0xFF` | exact | that column 256/256 NaN |
| dense | NVFP4 K=288, MXFP4 K=320, all pads NaN | exact | 51200/51200 NaN |
| MoE, normal and swap-AB | E=4 S=384 N=256 groups [0,130,130,300,384], MXFP8 K=2880 / NVFP4 K=2848, token row 5 pads `0xFF` | exact | token row 5 256/256 NaN |
| MoE, normal and swap-AB | same, expert-2 weight row 7 pads `0xFF` | exact | column 7 NaN for rows 130-299 (the group using expert 2) |

Expected: the output does not depend on the padding bytes, which are not data.

Only the word that holds a row's last K-scale can carry loaded padding bytes: the words before it are fully live, and the words after it lie past `rest_k` and are zero-filled. So the kernel masks exactly that word and needs no change to the producer, the host or the descriptors. The mask is derived from `ceil(K / block_size)`, so it also covers MXFP8 with a partial last scale block (`K % 32 == 16`, e.g. `K = 48` or `80`), whose tail word holds padding bytes too; #2008 (finding B01) makes Frost decline a K that ends inside a scale block. With finite padding bytes the results are bitwise identical to before: a live byte is kept, and a padding byte now reaches the MMA as `0x00` instead of its old value, but either value only scales TMA-zero-filled K data. I checked on GPU that NaN pads now give the same bits as zero pads:

- dense, every tail-word position and live-byte count: NVFP4 K = 288, 320, 352, 416, 480, 512; MXFP4 K = 288 ... 512 in steps of 32; MXFP8 K = 160, 192, 224, 256. On the base every K with padding bytes returns 51200/51200 NaN; the K values whose scale count is a multiple of 4 have no padding bytes and are unaffected on both.
- MoE, normal and swap-AB, including the forms only the MoE templates issue: fp4 + e4m3 at block 32 (each scale duplicated by PRMT), fp4 + e8m0 at block 16 (inline-PTX 4X UE8M0), the mixed MXFP8 x MXFP4 pair in both operand orders, and one-sided dequant on either side. On the base each of these returns 98304/98304 NaN.
- Every MoE mode, because the mask sits in the mainloop that NONE, GATHER, SCATTER and COMBINE share. In GATHER only the weight SF is F8_128x4; the token SF is linear, and its TMA view ends at `K / block_size` scales, so TMA zero-fills the rest of its last word.
  - GATHER, K = 544 (17 MX or 34 NVFP4 scales per row), NaN pads in the weight SF: NVFP4, MXFP4, MXFP8 and the mixed MXFP8 x MXFP4 pair with the fp8 operand on either side, normal and swap-AB. The base returns only NaN in the eager launch, in a CUDA-graph replay with changed routing and scales, and after re-binding the token SF; the branch passes all three checks.
  - SCATTER top_k = 2 (MXFP8 K = 2880, eager and CUDA-graph replay) and COMBINE top_k = 2 (NVFP4 K = 288, two launches), normal and swap-AB, NaN pads in both blobs: only NaN on the base, correct on the branch.
- MXFP8 with a partial last scale block, dense K = 48 and K = 80: 51200/51200 NaN on the base with NaN pads, correct on the branch.

The mask is computed per k-tile with selects instead of a branch on the last k-tile, which keeps the unrolled k-tile body straight-line. In the SASS of the single-GEMM 128x128x128 4x2-warp kernels I disassembled, the k-tile loop keeps its 64 block-scaled MMAs and 168 registers with no spills; it gains one `LOP3` per loaded SF word (3 for MXFP8, 6 for MXFP4, 12 for NVFP4 with this tile) plus a few uniform-datapath `UISETP` / `USEL` / `UIADD3` ops. Instructions per k-tile: dense NVFP4 197 -> 221, dense MXFP8 188 -> 193, MoE NVFP4 256 -> 263, MoE swap-AB NVFP4 242 -> 280 (12 of these are register moves from a different allocation). Not every variant stays spill-free: one opt-in dual-weight MoE kernel spills more (see "API and compatibility impact"). I did not time it (shared GPUs).

This was found in an audit of the SM120 Frost kernel templates (finding B02). The audit also recommends the producer side, Frost's F8_128x4 quantize epilogue writing zero padding (finding B03, #2011); that is a separate fix and this one does not depend on it.

## Related issues

None. Related PRs from the same audit:

- #2011 (finding B03) is the producer side of the same bytes: Frost's own F8_128x4 quantize epilogue writes zeros into these padding slots. This fix protects the consumer against padding written by any producer and does not depend on it.
- #2008 (finding B01) makes Frost decline a K that ends inside a scale block, which includes the MXFP8 `K % 32 == 16` shapes mentioned under "Why".
- #2013, #2027, #2032 and #2036 change other parts of the two SM120 MoE block-scale templates. #2008, #2011, #2014, #2015, #2016, #2017, #2019, #2023, #2024, #2029, #2032, #2035, #2036 and #2037 also change `gemm_test_utils.py`, `test_block_scale_matmul.py` or `test_moe_grouped_block_scale_matmul_fwd.py`. `git merge-tree` merges this branch with each of the 29 other open branches of the series without conflicts.

## API and compatibility impact

No API change and no graph is newly declined. Results are bitwise unchanged when the padding bytes are finite. F8_128x4 K-padding bytes that encode NaN no longer turn SM120 block-scale outputs into NaN.

Performance: the mask adds ALU work to every k-tile. These numbers come from static SASS only; nothing was timed (the GPUs are shared). Pairing the base and branch builds of each of the 50 block-scale kernel variants that `pytest gemm/frost -k sm120` compiles on the base:

- All 50 stay at 168 registers. The k-tile loop body grows by 2 to 40 instructions (+0.4% to +15.7%). The largest relative growth is in dense NVFP4 with 128x64 / 64x128 tiles (133 -> 153) and in MoE swap-AB NVFP4 (242 -> 280).
- 48 variants have no spills on either side. The NVFP4 GATHER kernel already spills on base (17 STL / 17 LDL, none in the k-tile loop) and is unchanged.
- One variant spills more: the opt-in dual-weight (SwiGLU) MXFP8 x MXFP4 MoE kernel in the padded e2m1 form (`padded_e2m1=True`, TMA `.b4x16_p64`), normal orientation, `ab_stages = 1`, as built by `test_dual_moe_grouped_block_scale_matmul_fwd_swiglu_mixed_sm120[padded-normal]`. It already spills on base. Its stack frame grows from 40 to 56 bytes, STL / LDL from 9 / 9 to 13 / 13, and LDL inside the k-tile loop from 6 to 10 (loop body 521 -> 561 instructions). The padded form only runs K that is a multiple of 128, so this kernel never sees padding bytes and the mask never changes a byte in it. The default packed form of the same kernel and both swap-AB forms have no spills on either side.

FlashInfer's exported Frost kernels are not affected: its catalog requires N and K to be multiples of 128, so they have no K-padding bytes, and its shipped artifacts are not re-rendered. Its SM120 MXFP8 x MXFP4 sources keep the e2m1 operand in the packed form, not the padded one.

The SM100 tree has the same K-tail handling and is intentionally left for a follow-up (static check only, no SM100 GPU here): `rest_k` rounds up in `python/cudnn/gemm/frost/sm100/kernel_templates/sm100_block_scale_matmul.py:1590`, `sm103_block_scale_matmul.py:1540`, `sm100_moe_grouped_block_scale_matmul_fwd.py:2068` and `sm100_moe_grouped_block_scale_matmul_fwd_swap_ab.py:2060`, and the tcgen05 block-scale MMA loops issue every K block of the last tile with no K bound (`sm100_block_scale_matmul.py:1165` / `:1188`, `sm103_block_scale_matmul.py:1105` / `:1195`, `sm100_moe_grouped_block_scale_matmul_fwd.py:1274` / `:1298` and `:1577` / `:1601`, `sm100_moe_grouped_block_scale_matmul_fwd_swap_ab.py:1257` / `:1281` and `:1560` / `:1584`).
