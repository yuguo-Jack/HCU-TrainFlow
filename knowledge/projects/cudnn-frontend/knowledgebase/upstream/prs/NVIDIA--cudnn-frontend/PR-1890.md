## Affected area

FE OSS kernels or CuTeDSL

## Summary

- `frost.device.PORTABLE_ELEMENTWISE_CCS = ((9, 0), (10, 0), (10, 3), (12, 0))` is the one served set for the tail RoPE, vision RoPE, fp8 RoPE QDQ and Engram gate kernels. Their plan checks compared the device cc exactly against `(10, 0)`, but the kernels emit only arch-portable instructions (fma/mul/add inline asm, warp shuffles, plain loads and stores); the fp8 QDQ uses the e4m3x2 converts, which exist from sm_89.
- The fp4 RoPE QDQ needs the e2m1x2 converts: it serves the new `FP4_CONVERT_CCS = ((10, 0), (10, 3), (12, 0))`, so B300 and SM120 gain fp4 and Hopper keeps declining it.
- Every part this PR adds was run (below); cc 10.0 was already served. SM121 (DGX Spark) was not, so it stays out of both; the gate test keeps it as a declined part, per the sets' own rule that a part joins once the kernels have run on it.
- Tests: module skips use the shared set; the fp4 QDQ cases skip outside `FP4_CONVERT_CCS`; a new L0 case checks the QDQ gate per quantization on cc 8.0, 9.0, 10.3, 12.0 and 12.1; the multi-device tail RoPE and the vision RoPE rejection cases use cc 8.0 as the unsupported sentinel, since cc 9.0 is now served.

## Why

Proposed in #1817: GH200/H100, B300 and RTX PRO 6000 Blackwell were refused by kernels that emit nothing B200-specific.

## Related issues

Fixes the RoPE / Engram part of #1817.

## API and compatibility impact

No API change. On cc 9.0 tail/vision RoPE, the fp8 RoPE QDQ and the Engram gate now produce plans; on cc 10.3 and 12.0 all of them, fp4 included. cc 10.0 is unchanged.
