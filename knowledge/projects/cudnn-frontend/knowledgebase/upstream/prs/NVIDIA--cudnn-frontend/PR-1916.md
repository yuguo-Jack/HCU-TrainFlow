# perf(bsa): enable the blk64 forward short-tile optimizations only on the persistent scheduler

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1916) · state: closed · merged: True

## Original PR description

## Summary

Follow-up to #1736.

**1. Gate `short_tile_opt` on the persistent scheduler.** `short_tile_opt` (shared first softmax step + single-stage epilogue) was gated only on the sparse-index capacity. With a **fixed top-k** (no `q2k_block_nums`) the wrapper uses the static one-tile-per-CTA scheduler unless `tiles >= 8192 and top-k >= 256` or `top-k <= 128` with enough tiles (`choose_blk64_use_clc`). On that scheduler the single-stage epilogue is already off (it needs the persistent path) and the only thing left, the shared first softmax step, has no per-tile ramp to overlap and is a net loss: **5-12% slower** on several MiniMax-H3 shapes. My #1736 measurements always passed per-row counts, i.e. always ran on CLC, so this path was not covered. `short_tile_opt` is now additionally gated on `is_persistent` (host-side, no sync); with the flag off the kernel is code-identical to before #1736.

**2. Drop the redundant `not self.is_split_kv` from `epi_single_stage`.** Split-KV always writes FP32 O partials, so `o_dtype == BFloat16` already excludes it; the term never changed the generated kernel.

## Measurement (B300, `benchmark_bsa_minimax_h3.py` h3 suite, B=1, H=7, D=128, BF16, blk64)

Sampled fp32 reference check of O and LSE on every case: max |err| <= 1.8e-4. The CLC cases (5s/15%, 15s/30-50%) keep the #1736 behaviour.

Why the gate needs `is_persistent` and not just a different capacity threshold: on the static scheduler with the h3 shapes, each optimization on its own (7 interleaved rounds per case, B300) gives single-stage epilogue alone -2.3..+0.6%, shared first softmax step alone **+6.5..+15.9%**, both together +0.6..+3.2%, all with O and LSE bit-identical to the baseline.
