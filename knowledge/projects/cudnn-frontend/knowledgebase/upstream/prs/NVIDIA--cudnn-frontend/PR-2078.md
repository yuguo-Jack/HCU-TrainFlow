## Affected area

Python API: FROST norm graph binding.

## Summary

Accept UID `0` in the shared norm variant-pack resolver. Extend the existing layernorm graph round trip to use input UID zero with tensor keys and integer keys, in forward and backward.

## Why

The classic graph section of `samples/python/20_layernorm_forward.ipynb` sets `UID.X = 0`. The norm resolver rejected that UID, then raised `KeyError` at `resolved[id(facts.x_t)]` when a FROST norm plan executed. The graph API also normalizes tensor keys to UIDs, so both public binding forms are affected.

This failed in develop schedule `77582241`, source `d48ab66e451ecc39b1f829bec22e69509ca1faed`, jobs `516630820` and `516630827`. Prior schedule job `514364054` completed the same notebook.

## Related issues

Follow-up to #1509, which introduced the resolver. Shared Auto-FE todo: 0008.

## API and compatibility impact

UID zero now works for FROST norm bindings. Plan selection, kernels and numerical checks are unchanged.

## Testing

Built the native bindings from this worktree and verified both the package and norm module import paths. Local SM100 with rebuilt native bindings.

From `test/python`:

```
python -m pytest -o addopts= -n 0 -rA norm/graph/test_frost_norm_graph_roundtrip.py
```

- Before the resolver fix: **2 failed**, both with the same UID-zero `KeyError`.
- After: **2 passed**. Both cases check BF16 and FP32 forward/backward outputs against PyTorch, with poisoned outputs.
- The unchanged notebook's classic graph section fails with `KeyError` before and passes its numerical checks after.
- Changed-file pre-commit (Black, line length 160; SPDX) and `git diff --check` pass.

The local backend differs from the nightly backend. The notebook's convenience `Graph` section was not run locally. The separate `python_samples` CI trigger checks the full notebook; the round-trip module above was run locally because the general CI target excludes names containing `frost`.

**Count distinct tensors when checking UID uniqueness.**

When a backward graph uses the same tensor for `input` and `grad`, `bound_tensors()` counts that tensor twice. Its UID is then excluded from `by_uid`, including UID `0`. The backward executor can consequently raise `KeyError` while resolving `dy`.

Deduplicate bound tensors by identity and add a regression test for this shared-input case.

<details>
<summary>Suggested fix</summary>
<dl>
<dd>

```diff
     def bound_tensors(self) -> list:
-        return [t for t in self.tensors.values() if t is not None]
+        seen = set()
+        tensors = []
+        for t in self.tensors.values():
+            if t is None or id(t) in seen:
+                continue
+            seen.add(id(t))
+            tensors.append(t)
+        return tensors
```
