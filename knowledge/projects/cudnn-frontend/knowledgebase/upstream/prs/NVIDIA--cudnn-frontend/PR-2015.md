## Summary

The SM120 FROST GEMM tree now declines `block_scale_dequantize(..., is_negative_scale=True)` when the scale-factor tensor's type has a sign bit (`FP8_E4M3`), instead of planning the graph and dropping the attribute.

- `sm120/compiler.py`: new `_check_block_scale_sign(state)`, called from `_analyze_graph` right after `_check_graph_lowered`. It reads the attribute the shared analyzer already records on each `block_scale_dequantize` op and raises `NotImplementedError` naming the op and its scale tensor, for example: `block_scale_dequantize 'block_scale_dequantize.0' sets is_negative_scale=True on its fp8_e4m3 scale factors 'SFA', which the sm120 block-scale MMA cannot honor: it reads every scale as an unsigned .ue4m3 / .ue8m0 value, so a negative scale would be applied as its magnitude`.
- Sign-free scale types (`fp8_e8m0`; also `fp8_e5m3`, which sm120 does not serve) cannot hold a negative value, so the attribute cannot change their result. Those graphs are still accepted.
- Tests: `test_sm120_block_scale_declines_signed_negative_scale` (dense) and `test_sm120_moe_block_scale_declines_signed_negative_scale` (MoE, normal and swap-AB) run on SM120 GPUs. `test_sm120_analyze_graph_declines_signed_negative_scale` checks the decline in `_analyze_graph` and has no architecture gate, so test lanes without an SM12x GPU run it too. The graph helpers `_build_nvfp4_graph` and `_build_graph` get a trailing `negative_scale=(False, False)` argument. By default they pass `None`, which leaves the attribute unset, so every existing test builds the same graph as before.

## Why

cuDNN defines `is_negative_scale` as "whether the scale values can be negative": with it set the dequantized value is `x * s`; without it, `x * |s|`. The shared GEMM analyzer stores the attribute on its recorded op (`graph_analyzer.py`, `_RecordedOp.is_negative_scale`). However, `_capture_dequant_operand`, `BlockScaleSpec` and the registry key do not carry it, and no gate reads it. A flagged graph therefore produced the same `FusionChain` and the same rendered kernel as an unflagged one.

The SM120 warp MMA (`mma.sync ... block_scale`) takes every scale factor as an unsigned `.ue4m3` or `.ue8m0` operand. PTX defines `ue4m3` as a 7-bit unsigned format, held in a byte whose MSB must be zero, and does not say what the MMA does with a byte whose MSB is set. With E4M3 scales, every live scale byte reaches the MMA unchanged (the mask from #2010 clears only K-padding bytes), and on this GPU the MMA ignores bit 7 (measured below). A block whose scale is `-|s|` contributes `+|s|`, and nothing reports it.

Reproducer on the base commit 24a8cd43, re-run on develop 18df4c38 with the same results (RTX PRO 6000, SM120). NVFP4 GEMM: FP4_E2M1 A/B, FP8_E4M3 F8_128x4 scales, block 16, `is_negative_scale=True` on both dequantize nodes, half of the SFA bytes negative (sign bit set), catalog config `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`:

| Route | Shape | Output | max\|out - signed ref\| | max\|out - \|s\| ref\| |
|---|---|---|---|---|
| dense, `jit_from_cudnn_graph` | M=N=256, K=512 | fp16 | 6594 | 0 |
| MoE NONE, `jit_from_cudnn_graph` | E=2, S=256, N=256, K=512 | bf16 | 6448 | 0 |
| MoE swap-AB, `jit_from_cudnn_graph` | same | bf16 | 6448 | 0 |

The output matched the `|s|` reference bit for bit. `FrostGemmEngine.check_support` accepted both graphs, and through the front door (`CUDNN_FRONTEND_ENABLE_FROST_ENGINES=1`), `create_execution_plans([A, FALLBACK])` ranked a `frost_gemm` plan first (dense: first of 3 plans; MoE: the only plan). Frost conv already declines the same attribute (`python/cudnn/conv/frost/engine.py`: "does not support negative scale encoding"). python/cudnn/AGENTS.md Rule 9 says an engine must decline what it cannot honor, never silently ignore an argument.

Why this fix:

- The scale operand of the SM120 block-scale MMA has no signed form, so a per-block sign cannot be passed through it. Honoring the attribute would need a different data path (for example folding the sign into the sign-magnitude data, an extra pass over the operand). A decline is the conservative fix and changes no numerics.
- The check is in the sm120 tree's own `_analyze_graph`, which every sm120 route goes through: `FrostGemmEngine.check_support` (via `probe_supported`), which `engines.heuristics.rank` consults before it lets the family propose plans; and `jit_from_cudnn_graph`, which `build_plan`, a replayed `create_execution_plan(engine_id, knobs)` and direct callers use. It sits next to `_check_graph_lowered`, which declines graphs that the shared analyzer lowered only in part. The shared analyzer (`graph_analyzer.py`, also used by the sm100 tree) is not changed.
- E8M0 scales are left alone on purpose. They have no sign bit, so `x * s == x * |s|`, and the kernel already computes what the attribute asks for. Declining them would only drop working plans.

Found in an audit of the SM120 Frost kernel templates (finding B07).

## API and compatibility impact

- Newly declined on SM120: block-scale GEMM graphs in which a `block_scale_dequantize` with `is_negative_scale=True` reads `FP8_E4M3` scale factors. That covers NVFP4 (block 16) on all three templates (dense, MoE, MoE swap-AB), plus fp4 + E4M3 at block 32 on the two MoE templates. The dense template does not serve fp4 + E4M3 at block 32 and declines it with or without the attribute (`kernel_registry.py`, `DENSE_UNISSUED_FP4_SCALES`); a flagged graph of that kind is now declined by this check first, with this check's message. Through the front door these graphs are no longer offered a `frost_gemm` plan and go to the backend's plans. Where the backend offers none, `create_execution_plans` raises `cudnnGraphNotSupportedError` naming both declines; on this configuration that is the case for the flagged MoE NVFP4 graph, where the backend's MoE operation fails to finalize (`CUDNN_STATUS_BAD_PARAM`). A direct `jit_from_cudnn_graph` call raises `NotImplementedError`. FlashInfer's exported Frost kernels never set this attribute.
- On this GPU with cuDNN 9.24, the backend offers only `eng0_k24=0` and `eng0` for the flagged dense NVFP4 graph, and both also return the `|s|` result (max diff 6594 against the signed reference, 0 against `|s|`). So the decline does not make front-door results signed on this configuration. It stops Frost from accepting an attribute it ignores.
- Unchanged: graphs without the attribute, and graphs whose flagged scales are `FP8_E8M0` (MXFP8, MXFP4, fp4 + E8M0 at block 16). No numerics change for any accepted graph.
- Possible follow-up, not changed here: without the attribute, E4M3 scale bytes with the sign bit set also reach the MMA unchanged in all three templates (#2010's mask keeps live bytes whole). Such a graph gets the `x * |s|` that cuDNN defines only because this GPU ignores bit 7, which PTX does not promise. Clearing the sign bit of every byte of an E4M3 scale word (`& 0x7F7F7F7F`) before the MMA would make that path independent of the measured behaviour. The mask must not touch E8M0 scales, where bit 7 is part of the exponent.
- SM100: the sm100 tree has the same gap. Its `probe_supported` (`python/cudnn/gemm/frost/sm100/compiler.py:2760`) and `jit_from_cudnn_graph` (`:2846`) call the shared `analyze_with_binding` directly, and its `tcgen05.mma ... block_scale` path also takes unsigned scale types. This was checked statically only (no SM100 GPU here). By repo convention a fix lands in both trees; this PR deliberately changes only the sm120 tree, and the sm100 copy is left for a follow-up.
