# Fix BatchNorm cache reuse for strided vectors

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2258) · state: open · merged: False

## Original PR description

## Problem

BatchNorm caches compiled CuTe functions without including the layout specialization of the affine and statistics vectors. `dyn()` specializes unit strides but represents non-unit strides dynamically. Reusing a function compiled for a contiguous vector with a stride-2 view, or vice versa, therefore can produce incorrect outputs, NaNs, or incorrect running statistics.

The issue affects training, inference, and backward across the generic, NCHW, and NHWC routes.

## Change

Include the affected vectors' unit-stride classifications in the six kernel cache keys, including the separate NCHW/NHWC inference entries. Different non-unit strides continue to share their dynamic signature. Running mean and variance remain in-place outputs; this adds no operand copies or device allocations.

## Validation

- B300 (SM103) and GH200 (SM90): 72 new cases passed against PyTorch, covering all three routes, training/inference/backward, each affine or statistics vector independently, both call orders, dynamic stride reuse, and changed-input CUDA Graph replay with caller workspace. Training checks the updated running statistics and sentinel values in the gaps between view elements.
- Before the fix, nine isolated B300 cases failed across the three phases and routes, and GH200 independently reproduced training, inference, and backward failures.
- B300: 15 representative cases passed in each of CuTe DSL 4.8.0/cu12, 4.8.0/cu13, and 4.8.1/cu12; all 72 passed on 4.8.1/cu13.
- Existing norm layout/fallback/kernel L0 selection: 3 passed, 1 deselected on B300.
- Black 26.3.1 with the repository's `--line-length 160 --fast` options and `git diff --check` passed.
