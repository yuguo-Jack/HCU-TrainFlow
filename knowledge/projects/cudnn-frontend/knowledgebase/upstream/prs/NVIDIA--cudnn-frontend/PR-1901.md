# Fix KDA JAX tests and SM100 GLU quant epilogue deadlock

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1901) · state: closed · merged: True

## Original PR description

SM100 JAX CI reports six stale KDA schedule assertions and a GLU/Hadamard/quant timeout. This fixes the schedule tests and the GEMM synchronization defects, including a barrier-reuse race reproduced by delaying ACT warps.

## Before submitting

- [x] Contribution uses the terms of LICENSE.txt.

- [x] Reviewed the applicable AGENTS.md rules.
- [x] Applied labels: `cat-bugfix`, `area:frost`, `area:linear_attention`, `orig-nv-eng`, `mod-cutedsl`.

## Changes

- KDA: run the six cases with default scheduling and with chaining forced. Require chain plans only in the latter case; retain output and gradient checks. The production chain threshold stays unchanged.
- GEMM: use unaligned named barriers in warp-specific branches, including TMEM allocation, and recompute the tile-info consumer count when a cached kernel changes output modes.
- GEMM deadlock: RHT can reach tile completion after its nonblocking subtile arrival but before ACT resets that barrier. Reusing the same barrier can then count RHT twice and hang. Give tile completion a separate barrier, preserving overlap between ACT stores and RHT computation. Remove an unreachable wait and stale comments.
- Add a regression that delays ACT before its subtile barrier. It reproduces the hang on the preceding commit and passes with the separate tile barrier. Synccheck alone reported zero errors for the hanging run.

The barrier-reuse constraint is specified in the [PTX barrier documentation](https://docs.nvidia.com/cuda/parallel-thread-execution/#parallel-synchronization-and-communication-instructions-bar).

## Validation

Local SM100, CuTeDSL 4.8.0, cuDNN 9.27, Python 3.12, JAX 0.11, PyTorch 2.13+cu130:

- Torch GLU/Hadamard/quant L0: **17 passed, 6 skipped**.
