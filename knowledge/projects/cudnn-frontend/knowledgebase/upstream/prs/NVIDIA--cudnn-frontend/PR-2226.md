# norm: serialize the kernels' lazy CuTe DSL compiles on a process-wide lock

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2226) · state: open · merged: False

## Original PR description

## Problem

The FROST norm kernels compile on first use. Each kernel module keeps a dict cache and calls `cute.compile` on a miss. When two threads make the first call at the same time (an autograd worker and the caller, or a thread pool), both miss and trace concurrently.

The CuTe DSL keeps its per-trace state on objects that every compile in the process shares, so the two traces corrupt each other:

| DSL | failure |
|---|---|
| 4.8.1 | `TypeError: 'NoneType' object is not iterable` in `cutlass_dsl/cutlass.py` `_track_deferred_kernel_launches` (`self._pending_launches` is saved and restored on the shared DSL object) |
| 4.8.0 | `AssertionError: Please start a session before accessing session data` / `ValueError: _warp_fwd_host() requires a code object with 0 free vars, not 2` |

`test/python/norm/torch/test_torch_norm_ops.py::test_norm_custom_ops_are_thread_and_stream_safe[rms_norm]` (L1) fails this way on B300 in 10 of 10 runs, with either DSL version.

## Change

- Add `cudnn.frost.compiled_cache.dsl_compile_lock()`, a process-wide `RLock`, re-exported from `cudnn.norm.utils`.
  - It is process-wide because the DSL state is shared by every compile in the process, so a per-module lock would only stop norm-vs-norm races.
  - It is reentrant in case a build compiles a nested kernel.
- Each of the 28 lazy-compile misses in `python/cudnn/norm` now takes the lock and re-checks the cache inside it. The edit is mechanical and identical at every site:

  ```python
  if fn is None:
      with dsl_compile_lock():
          fn = _KCACHE.get(key)
          if fn is None:
              fn = cute.compile(...)
              _KCACHE[key] = fn
  ```

  The hit path is still a single dict lookup, and launches never take the lock.

## Testing

B300 (sm_103), cuDNN 9.27, CuTe DSL 4.8.1:
- `test_norm_custom_ops_are_thread_and_stream_safe`:
  - develop: `rms_norm` fails 10/10;
  - this PR: both cases pass 10/10.
- `test/python/norm`, L0 + L1: 5697 passed, 3 skipped.

`black 26.3.1 --line-length 160 --fast` is clean.

## Not in this PR

- `cudnn.frost.compiled_cache.compile_cached` intentionally lets threads race on an empty slot ("each compiled once"). Under this DSL behaviour that racing path is unsafe too. Taking `dsl_compile_lock()` there would be the natural follow-up, but it changes a documented choice, so I've left it to the owner.
- Other packages that call `cute.compile` lazily can adopt the same lock.
- The root cause, the DSL's shared per-trace state, belongs upstream in the CuTe DSL.

Follow-up data on the `compile_cached` point under "Not in this PR". That racing path does fail in practice, so here are numbers for deciding where the fix should go.

**Probe.** Two threads build and run different FROST GEMM graphs (bf16, two shapes per seed) for the first time, in a fresh process with an empty cache. B300 (sm_103), CuTe DSL 4.8.1, `CUDNN_FRONTEND_ENABLE_FROST_ENGINES=1`.

| tree | seeds with an error |
|---|---|
| develop | 6 of 19 |
| this PR + `compile_cached` under `dsl_compile_lock()` | 0 of 12 |

The develop errors are the same DSL state corruption as the norm case: `AssertionError: Please start a session before accessing session data` and `IndexError: attempt to access out of bounds block`. The traceback goes through `gemm/frost/sm100/compiler.py:_compile_fused_gemm` → generated `compile` → `compiled_cache.compile_cached` → `_compile_persistent` → `_compile_and_export` → `cute.compile`. The two keys differ, so `_entry_lock` does not serialize them.

**The change I tested.** The four `cute.compile` calls in `compiled_cache.py` (two bypass paths, the unknown-manifest path and `_compile_and_export`) go through one helper that takes `_DSL_COMPILE_LOCK`. Hits, memo hits and reloads still take no lock. The file lock stays per key, and the DSL lock is taken inside it only around the compile itself.

The cost is that cold compiles of different keys no longer overlap within one process. With the DSL as it is, they cannot overlap safely anyway.

Would you like this added to this PR, or as a separate follow-up after it merges? Either works for me.
