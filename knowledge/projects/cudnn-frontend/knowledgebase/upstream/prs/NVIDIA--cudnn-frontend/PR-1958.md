# test: pin the d128 grouped backward rendering records per kernel; the shared fold kernel is excluded (its change in #1925 reddened the chain-wide records)

## Affected area

FE OSS kernels or CuTeDSL (tests only: the host rendering records of the SM100 d128 THD backward chains; no kernel or host code changes)

## Summary

The PTX md5 records of the d128 THD backward chains (the one-CTA THD hosts, the cta_group::2 pair body's default and `16w_fa4` renderings)
hashed the whole dumped module, so #1925's change to the shared dK / dV group-fold kernel reddened three unrelated modules' pins. The records
now hold one md5 per kernel the chain owns (its main kernel, the setup, delta-zero and dQ-cast launches), the shared fold kernel is excluded
by name, and the rows are re-pinned to the current `develop` renderings.

## Why

A rendering pin exists to catch a change to the kernel it names. Hashing the chain made every pin a function of every kernel the chain
launches, including one owned elsewhere; the fold kernel changed with #1925 after the pins were taken and the pins went red on `develop`
itself (the record tests skip on another DSL build, so a lane without the record's build did not see it). Per-kernel rows keep each pin
to its own kernel; a shared kernel is pinned by its own module, not by every chain that launches it.

## Related issues

Related to #1925 and #1943. None otherwise.

## API and compatibility impact

None (test records and test helpers only).

```
cd test/python && pytest -m L0 -ra sdpa/frost/test_sdpa_bwd_d128_2cta_stail_sm100.py sdpa/frost/test_sdpa_bwd_d128_2cta_stail_xfa4_sm100.py \
    sdpa/frost/test_sdpa_bwd_d128_dkv_accum_sm100.py sdpa/frost/test_sdpa_bwd_d128_diag_dq_reduce_add_sm100.py
```
Host tier (x86, no GPU, DSL 4.8.1): 41 passed / 0 failed / 78 skipped over the four modules (every GPU row skips on the host tier). Skips are GPU rows on the host tier only.
RED-then-green: with the previous chain-wide record files the per-kernel pins fail (no per-kernel rows; the chain-wide rows themselves fail
on the current `develop` at the record's DSL build: `54c2f7c4` rendered against the recorded `645f8a24` for the pair default), and pass
with the re-pinned records.

## Symptom

On `develop` after #1925, at the records' DSL build (nvidia-cutlass-dsl 4.8.1), eight host rows fail: `test_2cta_stail_host_renders_for_sm_100a_and_matches_its_record`,
`test_2cta_stail_host_renders_debug_clk_for_sm_100a`, `test_2cta_stail_host_renders_mask_forms_for_sm_100a`,
`test_xfa4_host_renders_for_sm_100a_and_matches_its_record`, `test_xfa4_default_rendering_is_unchanged_and_16w_named_is_the_default`,
`test_dkv_accum_default_renderings_are_unchanged_and_bf16_partials_named_is_the_default[1cta|pair]` and
`test_default_rendering_ptx_md5_is_unchanged[grouped_thd]` -- "the default rendering moved" -- while no kernel of those chains changed.

## Root cause

The records hashed the whole dumped PTX module of each chain. The grouped THD chains (one-CTA and pair) launch the shared dK / dV group-fold
kernel; #1925 changed it, so the chain-wide md5 of every chain launching it moved while every kernel those modules own was byte-identical.

## Fix (1 commit)

- `frost_test_utils.py`: `ptx_kernel_md5s` (the md5 of each `.entry` region of a dumped module, keyed by the DSL function name), the record
  row reader / writer and `assert_kernel_record` (every recorded kernel renders its md5; every rendered kernel outside the shared set is
  recorded; the shared set is excluded by name), the shared set `D128_THD_SHARED_KERNELS`.
- The pair-chain render helper and the two probe children also report the dumped file; the four modules pin per kernel through the helper
  (skip-then-assert on the record's DSL build, unchanged).
- The three record files: one row per owned kernel, the fold kernel excluded, re-pinned on the current `develop`; the comments say why.

## Equivalence

No kernel, host or API code changes: every rendering is byte-identical to `develop`'s (the PTX of each chain is unchanged; only what the
records hash changed). No GPU behaviour change; no GPU lane needed.
