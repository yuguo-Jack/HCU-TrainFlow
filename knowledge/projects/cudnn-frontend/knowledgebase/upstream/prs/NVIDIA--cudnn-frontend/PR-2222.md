# ops(causal_conv1d): bind the CUDA context before each binding call (FFT, plain, NWH, B2B)

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2222) · state: open · merged: False

## Original PR description

## Problem

The `cudnn.ops` causal conv1d primitives launch their kernels through the driver API (`cuModuleLoadDataEx`, `cuLaunchKernel`), and the driver API needs a context bound to the calling thread. This covers the FFT paths (medium and long) and the plain, NWH and B2B forwards.

An autograd backward runs on a worker thread whose context stack is empty. So does a `DataParallel` replica, and so does any fresh Python thread. On those threads the primitives fail with status 5000:

```
FFT causal conv1d backward JIT compilation failed: cuModuleLoadDataEx failed: CUDA_ERROR_INVALID_CONTEXT
RuntimeError: cudnnFFTCausalConv1dBackward failed with status 5000
```

This happens even when the same kernels were already built and run on the main thread. In the suite it shows up as `test_medium_fft_supported_dtypes` failing for some dtypes under xdist, depending on which thread runs the backward first.

## Change

Each of the ten binding calls now binds the work's context first, through `cudnn._device.ensure_current_context(stream, device)`. That is the helper the SDPA backward and packed-LSE paths already use, as described in the "native context checks" rule in `python/cudnn/AGENTS.md`. The calls are:
- `fft_causal_conv1d.py`: medium forward and backward, long forward and backward;
- `causal_conv1d.py`: plain, NWH and B2B forward and backward.

The non-FFT backwards already worked on a fresh thread. They get the same guard so that every primitive follows one rule.

## Testing

New tests `test_fft_causal_conv1d_runs_on_a_thread_with_no_cuda_context[medium|long]` and `test_causal_conv1d_runs_on_a_thread_with_no_cuda_context[plain|nwh|b2b]`:
- each path runs forward and backward on the main thread (FFT medium in fp32, FFT long in fp64, the others in fp32);
- then it runs them again on a fresh thread that makes no CUDA call of its own;
- the results must match exactly.

A100 (sm_80), cuDNN 9.27, CUDA 13 headers on `CUDA_HOME`:

| `test_fft_causal_conv1d.py` | failed | passed |
|---|---|---|
| develop + new test | 2 (both new cases: `cuLaunchKernel ... CUDA_ERROR_INVALID_CONTEXT` at the fresh thread's first launch) | 7 |
| this PR | 0 | 9 |

RTX 5060 Ti (sm_120), cuDNN 9.27, CUDA 13 headers. `test_causal_conv1d.py` and `test_fft_causal_conv1d.py` together:
- develop + new tests: 7 failed / 44 passed;
- this PR: 2 failed / 49 passed.

All five fresh-thread cases fail on develop with `CUDA_ERROR_INVALID_CONTEXT` at the first launch and pass here. The 2 failures left are the NWH fp64 status-3010 cases that #2215 handles. The failure does not depend on the architecture; it only needs a thread with no context bound.

`black 26.3.1 --line-length 160 --fast` is clean.
