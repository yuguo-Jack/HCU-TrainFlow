## Summary

On SM120, an ungrouped AVG reduction over the MoE token axis now divides by the routed rows the groups cover, `first_token_offset[G]`, instead of the routed capacity.

- The four SM120 MoE templates compute `moe_used_rows = max(min(first_token_offset[num_groups], capacity), 1)` once per CTA. The load runs in the compute warps after their `griddepcontrol.wait`. The capacity is `M` in the token-by-weight templates and `N` in the swap-AB ones. The value is passed to `red_part_flush_tile` / `red_part_flush_cta` as a fourth element of the MoE context tuple.
- `sm120/epilogue_codegen.py` names that symbol once (`_MOE_USED_ROWS`) and unpacks it from the MoE flush context. MoE chains reach two AVG divisor call sites, the per-CTA partial flush and the per-chunk atomic path, and both pass it. The third call site, the lane-run fold flush, passes it only for consistency: lane-run folds are planned only for dense chains (`_lane_run_tile` in `sm120/compiler.py` returns `None` for MoE chains, and `generate()` plans folds only when `not chain.has_moe`). For a dense chain the keyword is ignored, so that call site renders the same code as before.
- The shared `_emit_reduction_avg_inverse` gains a keyword-only `token_extent` (default `None`). For an ungrouped AVG in a MoE chain, it replaces the token-axis extent with that expression. With `None`, the emitted code is the same as before. Grouped AVG keeps `group_end - group_begin`, and dense chains are unchanged.
- New test `test_moe_avg_divides_by_used_rows_sm120`.

## Why

An ungrouped AVG whose reduced dims include the MoE token axis divides by the kernel's token extent. That covers the scalar `(1,1,1)` AVG and the per-feature `(1,1,N)` AVG, which becomes `(1,M,1)` after swap-AB. The token extent is the routed capacity: `Token.shape[1]`, or `len(token_index)` under GATHER. The sums, however, only cover rows `[0, first_token_offset[G])`, because the scheduler visits only the groups and every contribution is bounded by `group_end`. `docs/operations/MoeGroupedMatmul.md` allows a final offset below the capacity, calls the trailing routed rows unused, and leaves their output rows untouched. ADD, MAX, MIN, AMAX and the grouped AVG already exclude those rows. The ungrouped AVG therefore came out multiplied by `fto[G] / capacity`. A grouped AVG with one group disagreed with an ungrouped AVG over the same rows. The final offset below capacity became legal in #1295, which did not update the AVG divisor.

Minimal reproducer (SM120, 24a8cd43, `jit_from_cudnn_graph` with `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`):

- Graph: NONE mode, E=2, G=4, 192 routed rows, N=K=128, BF16 token of ones, BF16 weight of all +1 (or all -1), FLOAT output. Five reductions are fused on the output: AVG `(1,1,1)`, AVG `(1,1,N)`, MAX `(1,1,1)`, ADD `(1,1,1)` and grouped AVG `(G,1,1)`.
- Every used output element is 128 (-128 with the -1 weight).
- With the +1 weight and `first_token_offset = [0, 32, 32, 96, 160]`, both ungrouped AVGs read 106.67 (128 * 160 / 192). With `[0, 8, 8, 16, 24]`, they read 16.0. The expected value is 128 in both cases.
- In the same launches, ADD equals the sum over the used rows, the grouped AVG reads 128 for the three non-empty groups (and 0 for the empty group 1), and the trailing output rows stay untouched.
- With the -1 weight and `[0, 32, 32, 96, 160]`, both ungrouped AVGs read -106.67, while MAX reads -128. MAX would read 0 if the trailing rows counted as zeros. With the +1 weight, MAX cannot show this.
- The same numbers appear on all four SM120 MoE templates: plain BF16 and NVFP4 block-scale (the same values as E2M1 codes with unit scales), token-by-weight and swap-AB.

This was found in an audit of the SM120 Frost kernel templates (finding B14).

Why this fix:

- It makes the ungrouped AVG agree with the documented contract (trailing routed rows are unused) and with every other reduction, including the grouped AVG.
- The used-row count is read on the device, after the PDL wait, from the same offsets the scheduler reads. Nothing is read back to the host (Rule 3), and the compile key does not change (Rule 4). Because the count is read at run time, a CUDA graph captured once divides by the offsets present at each replay, including offsets changed in place between replays (checked, see Testing item 9).
- When the final offset equals the capacity, the divisor has the same value as before, so the results are unchanged.
- The lower bound of 1 keeps an empty routing (final offset 0) at the AVG seed of 0. Without it, the per-CTA flush would compute `0 * (1/0)` and write NaN.

Alternatives considered:

- Declining the graphs: not possible at plan time, because `first_token_offset` is device data. Declining every ungrouped token-axis AVG would also remove a fusion that is correct whenever the routing fills the capacity.
- Documenting a capacity divisor: this would leave the AVG inconsistent with the documented meaning of unused rows and with the grouped AVG.

Why a file outside `sm120/` changes: the divisor is built by `_emit_reduction_avg_inverse`, which #1993 moved from `sm120/epilogue_codegen.py` into the shared `python/cudnn/gemm/frost/epilogue_codegen.py`. Both trees import it from there. The SM120 codegen needs it to emit the used-row symbol for the token axis. The new parameter is keyword-only and defaults to the old behaviour, so the SM100 tree renders byte-identical code (checked, see Testing). Copying the emitter into `sm120/` would duplicate the grouped-AVG rule instead.

## API and compatibility impact

- Numerics (SM120 only): an ungrouped AVG reduction over the MoE token axis now averages the rows `first_token_offset[G]` covers. This applies in NONE and GATHER mode; SCATTER and COMBINE decline reductions. Results change only when the final offset is below the routed capacity. Results with a full routing are unchanged, and an empty routing still yields 0. Per-token AVG, grouped AVG and all other reduction modes are unchanged.
- No public API change. The private `_emit_reduction_avg_inverse` gains a keyword-only parameter with a default.
- Performance: a plan with a fused token-axis AVG does one extra 4- or 8-byte load per compute thread per CTA. Without such an AVG the value is unused. Two such plans were compiled on base and branch and gave identical PTX: the token-by-weight plain template with a scalar ADD reduction, and the swap-AB plain template without reductions. Other configurations were not compared. The first commit's message says every kernel without a token-axis AVG compiles to the same PTX; that generalizes from these two checks.
- FlashInfer's exported SM120 MoE sources are pre-rendered and contain no reductions, so they are unaffected.
- SM100: the same defect exists and is intentionally left for a follow-up. This PR does not change SM100 behaviour, and no SM100 GPU was available here. The repo convention is that a fix lands in both trees. The SM100 copy:
  - `python/cudnn/gemm/frost/sm100/epilogue_codegen.py:139` calls the shared emitter without a token extent.
  - The capacity is bound at `sm100/kernel_templates/sm100_moe_grouped_matmul_fwd.py:374` (`M = m`), `sm100_moe_grouped_matmul_fwd_swap_ab.py:374` (`N = n`), `sm100_moe_grouped_block_scale_matmul_fwd.py:458` (`M = m`) and `sm100_moe_grouped_block_scale_matmul_fwd_swap_ab.py:450` (`N = n`).
  - A static render on this branch still emits `1 / (M * N)` for the scalar AVG, plus `1 / M` (normal) or `1 / N` (swap-AB) for the per-feature AVG.
