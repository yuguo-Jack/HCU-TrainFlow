## Problem

`gemm/cutedsl/test_gemm_swiglu.py` fails 64 cases on B200 with pip torch 2.13 (`ab_dtype=float32`, both `ab12` dtypes) and passes in CI.

```
check_ref_gemm_swiglu: torch.testing.assert_close(ab12, ab12_ref, atol=0.01, rtol=9e-03)
Mismatched elements: 293 / 131072 (0.2%)   Greatest absolute difference: 0.0362
```

**Not the DSL.** The same 64 cases fail under nvidia-cutlass-dsl 4.6.2, 4.7.0 and 4.7.1.

**The cause.** The kernel runs fp32 operands on the TF32 MMA. The reference GEMM uses torch's default fp32 matmul precision, which differs by environment:

- NGC containers, including CI, set `TORCH_ALLOW_TF32_CUBLAS_OVERRIDE=1`, so the reference is TF32.
- Pip torch computes it in IEEE fp32.

With the override exported locally, the 64 cases pass.

**The kernel is right.** An fp64 replay of one dumped case (a 256×512×2 problem) compares the kernel's `ab12` with four references:

| reference operands | max \|err\| | mismatches at the test tolerance |
|---|---|---|
| fp32 (IEEE) | 0.0387 | 293 / 131072 |
| TF32, truncated | 0.106 | 1482 |
| TF32, round-to-nearest | 0.0038 | **0** |
| bf16 | 0.268 | 15616 |

So the kernel computes round-to-nearest TF32 products accumulated in fp32. The remaining TF32 residual also explains the SwiGLU output check failing on a handful of elements when only the operands are pre-rounded: the existing failure diagnostic shows the kernel's `c` equals swiglu of its own stored `ab12`, and the residual is amplified where one factor is large (|input| ≈ 51 against gate ≈ 0.009).

## Change

Test-only.

- **`check_ref_gemm_swiglu`:** for fp32 operands, computes the reference with `torch.backends.cuda.matmul.fp32_precision = "tf32"` and restores the previous value on exit. This makes explicit the condition CI already runs under.
- **`test/AGENTS.md`:** new note "fp32 operands and TF32 references" recording the trap.
