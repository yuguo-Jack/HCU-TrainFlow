## Summary

- New helper `_splitk_reduction_drifts(red)` in the SM120 compiler. It is true for an fp32 `add` / `avg` / `norm1` / `norm2` reduction whose output keeps neither M nor N (dims `[1,1,1]` or `[B,1,1]`). This is the predicate `_auto_split_k` already applied.
- `_splitk_reject_reason` now lists such a reduction as a reason. `jit_from_cudnn_graph`, `probe_chain` and FROST knob replay all use this gate (`build_gemm_plan` runs `probe_chain` on a replayed record). So an explicit split-K config for such a chain is now declined with: `split_k_slices=2 is not supported with: fp32 avg reduction over all of M and N (the reducer adds it with one same-address atomic per vector, which drifts)`.
- `_auto_split_k` no longer has its own copy of the rule. It already calls `_splitk_reject_reason(chain, replace(config, split_k_slices=2))` first, so the automatic pick does not change.
- Three new SM120 tests (8 cases) and one host-only test of the gate (2 cases).

## Why

Found in an audit of the SM120 Frost kernel templates (finding G8.1).

When `split_k_slices > 1`, `sm120_matmul.py` and `sm120_block_scale_matmul.py` hand the graph epilogue to the shared reducer `kernel_templates/split_k_reduction_epilogue_fusion.py`. The reducer runs the epilogue once per 2- or 4-element output vector. Its snippets are generated with `drain_hooks=False` (`_splitk_reduce_snippets`), so `use_partials` is false (`sm120/epilogue_codegen.py`: `use_partials = drain_hooks and (not workspace_split_k)`). A reduction over all of M and N therefore gets one relaxed fp32 `atomicrmw add` per vector: B\*M\*N/elems sequential round-to-nearest adds into one address for `[1,1,1]`, and M\*N/elems into each batch's address for `[B,1,1]`. For AVG each addend is already multiplied by 1/count. When the input has repeated values, the rounding error is biased. The unsplit kernel folds the same sum into a register partial and issues one atomic per warp.

`_auto_split_k` already accounted for this: it never splits such a chain. But the rule existed only there. `_splitk_reject_reason` did not have it, and that is the split-K gate an explicit config or a replayed record meets. Both therefore compiled an ADD, AVG or NORM1 chain and returned a drifted result (a NORM2 chain never ran; see API and compatibility impact).

Reproducer on develop 24a8cd43 (RTX PRO 6000, SM120). The graph is bf16 A `[1,3000,1024]` = 1 and B `[1,1024,3000]` = 0.125 (K-major), then matmul -> relu -> reduction AVG to `[1,1,1]` in fp32. Every relu output is exactly 128, so the AVG must be 128:

| Path | Config | AVG | Relative error |
|---|---|---|---|
| `jit_from_cudnn_graph` | `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2` (S=1) | 127.99815 | 1.4e-5 |
| `jit_from_cudnn_graph` | same tile, `split_k_slices=2` | 124.37894 | 2.8e-2 (the dense relu output is exact) |
| `graph.create_execution_plan(20400, record)`, the public replay | a record for the same 128x128x128 warps4x2 tile with `SPLIT_K_SLC=2` (the engine's own listed plan for this graph is 64x192 with `SPLIT_K_SLC=1`) | 124.37894 | 2.8e-2 |
| block-scale template: mxfp8, e4m3 A = 1, B = 0.125, e8m0 scales = 1, 3072x3072x1024, matmul -> AVG `[1,1,1]` | S=1 / S=2 | 128.0016 / 126.2765 | 1.2e-5 / 1.3e-2 |

The audit (on its commit cd969f28, with the same tile at `split_k_slices=2` given as an explicit config) also measured 8.6% low at 8192x7168x1024 with constant data (117.05 instead of 128), and about 1.3e-4 relative error at S=2 on relu(randn) data at 3000x3000x1024 (about 6e-7 at S=1).

This reverses a documented policy on purpose. Before #1993 (ce16f495), comments in `_auto_split_k` and `_splitk_reduction_serializes` said "an explicit split-K config is honored as given", and the `_auto_split_k` comment recorded the AVG drift (2.8% at 3000x3000x1024 split 2). #1993 removed those comments together with most comments in the file; the code of both functions did not change. This PR declines these chains instead, because the knob contract in the root `AGENTS.md` says knobs are performance-only, and an explicit config or a replayed record silently returned these sums 2.8% low (3000x3000x1024, both paths, measured here) to 8.6% low (8192x7168x1024, explicit config, measured by the audit) on constant data.

Why decline instead of changing the reducer:

- The knob contract in the root `AGENTS.md` says knobs are performance-only: "a plan computes the same function under any knob value, so an autotuner may pick freely". A `SPLIT_K_SLC` value that moves an AVG by 2.8% breaks that.
- The automatic pick already declines these chains. With one shared gate, every split-K path follows the same rule, and the change is in one place.
- Lifting the restriction would mean the reducer has to carry the `red_part` register partials and grid-stride over row segments. The audit's fp32 model of the constant-input AVG shows that a per-warp fold alone still leaves about 6.4e-4 (3000x3000) and 5.1e-3 (8192x7168) relative error. That is a template change that needs its own numerics and performance validation, so it is left for a separate change.
- `_splitk_reduction_serializes` (MUL CAS loops, per-row and per-column atomic counts) stays a rule of the automatic pick only. It is a performance rule, and an explicit request that is slow but correct is still honoured.

## API and compatibility impact

- Newly declined on SM120 (`NotImplementedError`, or the engine's typed decline at `build_plans()`): a dense or block-scale GEMM chain that has an fp32 ADD, AVG or NORM1 reduction over all of M and N (`[1,1,1]` or `[B,1,1]`), combined with either of:
  - an explicit split-K config (`split_k_slices > 1` given to `jit_from_cudnn_graph`, including a `_splitK<S>` config name);
  - a replayed FROST record with `SPLIT_K_SLC > 1`.

  These used to compile and return drifted reductions. The automatic pick and the heuristics plan list never chose split-K for these chains, so plans the engine selects itself, and their numerics, do not change. All other reductions keep explicit split-K as before, including AMAX, MAX, MIN and int32 sums (exact under atomics) and per-row and per-column reductions. The frost benchmark sweeps (`--sweep-split-k`) record a decline and continue (an `ERR` row, a `FAIL` line or a skip, depending on the script); none of them builds a reduction graph.
- NORM2 is in the rule for parity with the automatic pick's old rule, but such a chain could not execute on SM120 before this PR either. `probe_chain` (the engine's plan list and knob replay) declined it in `_check_executable` ("a norm2 reduction takes a square root after the kernel, which is a device operation this engine does not own") and still does, because that check runs before the split-K gate. `jit_from_cudnn_graph` (dense and block-scale) compiled the split kernel and declined at execute ("cudnn.frost gemm: this kernel has no launch path -- a norm2 reduction ..."); it now declines at compile time with the split-K reason.
- SM100: the sm100 tree has no such gate on any path. `python/cudnn/gemm/frost/sm100/compiler.py:2540` (`_auto_split_k`) and `:2811` (`_splitk_reject_reason`) both admit these chains. Its reducer (`_splitk_reduce_snippets`, `:514`) and its unsplit kernel both fold them with one atomic per epilogue vector (`sm100/epilogue_codegen.py:140-182`). The repo convention is that fixes land in both trees. The SM100 copy is intentionally left for a follow-up: there the unsplit kernel has the same per-vector atomics, so it needs its own decision. It was also not tested here (no SM100 GPU).
