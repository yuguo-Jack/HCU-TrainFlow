## Summary

In `_emit_op`, the relu, leaky_relu and elu emitters now pass `propagate_nan=True` to their `cute.math.max` / `cute.math.min` calls. These calls now lower to `arith.maximumf` / `arith.minimumf` instead of `arith.maxnumf` / `arith.minnumf`. The change covers every relu form (plain, `negative_slope`, `lower_clip`, `upper_clip`), leaky_relu and elu. A comment explains the choice and notes that the binary `max` / `min` ops keep the default.

The new test `test_relu_family_propagates_nan` has six activation cases. Each runs on the sm100 tree (`CONFIG_sm100_128x128x128_128x128x32_cluster1x1_1ctamma`) and on the sm120 tree (`CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`). A process renders only one tree, so the other tree's cases skip.

## Why

These emitters used the DSL default `propagate_nan=False`, which is IEEE maxNum/minNum: when one operand is NaN, the other operand is returned. So a NaN reaching any of these ops came out finite. It became 0 for relu, leaky_relu, the slope forms and elu, and `lower_clip` for clipped relu.

Minimal reproducer (the sm120 cases of the new test): a dense bf16 GEMM with M = N = K = 128, fp32 output and `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`. A and B contain one NaN, an inf/-inf pair, and an inf that multiplies zeros. This gives 320 NaN and 64 ±inf accumulators, followed by:

| op | on 24a8cd43, at the 320 NaN accumulators | with this PR | test reference |
|---|---|---|---|
| `relu` | 0.0 | NaN | `torch.relu(x)` |
| `relu(lower_clip=-1.5, upper_clip=6)` | -1.5 | NaN | `torch.clamp(x, -1.5, 6)` |
| `relu(negative_slope=0.1, upper_clip=6)` | 0.0 | NaN | `torch.clamp(leaky_relu(x, 0.1), max=6)` |
| `relu(negative_slope=0.1, lower_clip=-1, upper_clip=6)` | 0.0 | NaN | NaN positions only |
| `leaky_relu(0.01)` | 0.0 | NaN | `leaky_relu(x, 0.01)` |
| `elu` | 0.0 | NaN | `elu(x)` |

Each torch reference returns NaN at the 320 positions and is compared with every output, the 64 ±inf accumulators included, at atol = rtol = 1e-5. The case with both `negative_slope` and `lower_clip` compares only the NaN positions. torch has no such op, and a separate fix changes the finite values of that combination (see Related issues), so this test does not pin them.

A swish control keeps NaN on both commits. I also ran these templates on 24a8cd43 and on this branch:
- Dense block-scale template, MXFP8 with an E4M3 NaN in A: relu gave 0 and clipped relu gave -1.5 on 24a8cd43; both give NaN with this PR.
- MoE grouped templates (normal and swap-AB) with graphs that mirror FlashInfer's BF16 FC1 export (`relu2`, `swiglu_step`): both gave 0 at all 192 / 256 NaN positions on 24a8cd43; all stay NaN with this PR.

Why NaN propagation is the right behaviour for these ops:
- The graph API sets `CUDNN_PROPAGATE_NAN` on `RELU_FWD` / `RELU_BWD` (`include/cudnn_frontend/node/pointwise.h:114-121`). `leaky_relu` and clipped relu lower to `RELU_FWD` (`python/pygraph/pointwise.cpp:178-182`).
- torch's relu, clamp, leaky_relu and elu return NaN, and the FROST tests use them as references.
- I ran native cuDNN 9.24 on the same GPU, with A = I and a NaN column in B:
  - eng10 returns NaN for relu, clipped relu, leaky_relu and elu.
  - For both sloped relu forms in the test, all 17 eng10, eng7 and eng1 plans return NaN. For `relu(negative_slope=0.1, upper_clip=6)` their finite values match the test's reference.
  - eng0, which ranks above eng10, returns 0 for relu, clipped relu, leaky_relu and both sloped forms; it is not offered for elu. It also ignores `negative_slope` and `upper_clip` here: `relu(negative_slope=0.1, upper_clip=6)` maps -10 to 0 and 9 to 9. So the native engines do not agree with each other; eng10 is the one that follows the requested attribute.

The binary `max` / `min` ops are deliberately left as they are. On the same GPU eng10 returns `max(NaN, 1) = 1` and `min(NaN, 1) = 1`, and the graph API sets the NaN-propagation attribute only for RELU_FWD / RELU_BWD.

Why the change is outside `python/cudnn/gemm/frost/sm120/`: at 24a8cd43 these emitters exist only in the shared `python/cudnn/gemm/frost/epilogue_codegen.py`, which #1993 moved them into. Both arch trees reach them through this `_emit_op`: epilogues through `_emit_pointwise_dag`, and the sm100 mainloop operand transforms through `generate_mainloop`. `sm120/` has no copy of them to change.

Found in an audit of the SM120 FROST kernel templates (finding G4.2).

## Related issues

Related to #2009 (merged) and #2025, which change the same emitter lines, and to #2001 and #2031.

#2009 (finding B10) and #2025 (finding B11) come from the same audit. Each conflicts textually with this PR. The resolution should keep `propagate_nan=True` on both the `max` and the `min` of each rewritten line. In those lines a NaN in either term makes the sum NaN, so either flag alone keeps a NaN input NaN: this PR's test catches a resolution only if it drops both flags.
- **relu `negative_slope` + `lower_clip` (#2009, finding B10, merged).** That fix moved relu with a slope to cuDNN's definition, `x < lower ? lower + slope * (x - lower) : x` with `lower` defaulting to 0, written as `max(x, lower) + slope * min(x - lower, 0)`. This branch now merges develop 18df4c38, which contains it. The merge conflicted only there; the resolution keeps #2009's lowering and adds `propagate_nan=True` to its `max` and `min`. #2009's semantics do not contradict this PR's test:
  - The `relu_slope_upper` case has no lower clip. It gives the same values under both lowerings and on native eng10.
  - The `relu_slope_lower` case compares only NaN positions.
- **ELU / tanh / softplus precision near 0 (#2025, finding B11).** That fix rewrites the elu line as `max(x, 0) + expm1(min(x, 0))`, with a Taylor series for small inputs.

Before #2009 was merged, I merged both branches into this branch in a scratch tree (#2009 at 9b8de27a, #2025 at 12b35105) and resolved the conflicts with both flags kept. This test, #2009's `test_matmul_relu_slope_clip.py` and #2025's `test_sm120_tanh_elu_softplus_relative_precision` then passed together (see Testing). 9b8de27a also sent a zero slope to the `max(x, lower)` line; that part was not merged with #2009 and is not in this branch. #2025's current head (1201e763) still conflicts with this branch only on the elu line.

#2013, #2014, #2018, #2022, #2026 and #2030 edit other parts of `epilogue_codegen.py`; `git merge-tree` merges each of them with this branch without conflicts.

NaN handling in the AMAX / MAX reductions is a separate finding (#2031) and is not changed here.

## API and compatibility impact

- **Numerics:** for a NaN input, relu (all forms), leaky_relu and elu in FROST GEMM epilogues now return NaN instead of 0 or `lower_clip`. Binary max/min are unchanged. Finite and ±inf inputs give the same results as before, with one exception below:
  - In five of its six cases, the new test compares them with torch at atol = rtol = 1e-5.
  - The existing tests that build these ops have identical outcomes.
  - The exception is relu with an explicit `negative_slope=0.0` and an `upper_clip`, at x = -inf. Its slope line computes `0 * -inf` = NaN, which the upper clip's `min` replaced with `upper_clip` on develop; now the NaN reaches the output. A scratch probe on the sm120 tree gave 6.0 for `relu(negative_slope=0.0, upper_clip=6)` and for `relu(negative_slope=0.0, lower_clip=0.5, upper_clip=6)` on develop 18df4c38, and NaN for both on this branch. Without an upper clip, `relu(negative_slope=0.0)`, `relu(negative_slope=0.0, lower_clip=-1)` and `leaky_relu(negative_slope=0.0)` give NaN at -inf on both. The native engines return `lower_clip` (0 without one) there, as measured while preparing #2009. Sending a zero slope to the `max(x, lower)` line, as #2009's branch did at 9b8de27a, gives that value; it is left to a separate follow-up.
- **SM100:** the sm100 tree uses the same shared emitter, so its epilogues change the same way, and so do its mainloop-fused operand relu, leaky_relu and elu. Since #2001 the graph analyzer accepts `negative_slope` on leaky_relu operand ops; it still declines every other operand-op attribute, so the relu forms with a slope or clip never reach the mainloop path. The sm120 templates decline mainloop fusion. There is no separate SM100 copy that needs a follow-up. The new test has sm100 cases, but I did not run them: there is no SM100 GPU here.
- **Pre-rendered kernels:** kernels that embed the old lines keep them until they are re-exported. One example is FlashInfer's shipped SM120 FC1 artifacts for relu, relu2 and swiglu_step.
- **FROST conv:** the conv epilogue (`python/cudnn/conv/frost/templates/epilogue.py:42`, `:119-125`, `:136`) uses the same default max/min for elu, relu and leaky_relu. It is a different engine and is not changed here.
- **Performance:** not measured. I compiled a standalone `max(x, 0)` for sm_120a with cutlass-dsl 4.7.1. With `propagate_nan=True` it emits `setp.le.f32` + `selp.f32`; the default emits the same pair plus `setp.nan.f32` + `selp.f32`.
- **CuTe DSL version:** `cute.math.max/min` take `propagate_nan` in nvidia-cutlass-dsl 4.6.2, 4.7.1, 4.8.0 and 4.8.1 (I checked installed copies). That spans the FROST floor of 4.7.0, so no new version gate is needed (Rule 7).
