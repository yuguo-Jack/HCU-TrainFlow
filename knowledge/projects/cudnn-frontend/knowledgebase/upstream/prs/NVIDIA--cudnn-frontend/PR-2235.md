# rmsnorm_rht_amax: reduce the amax with a shuffle where redux.f32 does not assemble

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2235) · state: open · merged: False

## Original PR description

## Problem

`rmsnorm_rht_amax`'s kernel reduces the per-warp and per-CTA amax with `cute.arch.warp_redux_sync(..., "fmax")`, which emits `redux.sync.max.f32`. ptxas does not accept that instruction on `sm_120a` / `sm_121a`, nor on `sm_110a`; the SM110 case is #1686, which `_cutlass_helpers/warp_reduce.py` already handles for the GEMM kernels. `check_support()` admits any SM100+ part, so on cc 12.x every compile fails:

```
ptxas application ptx input, line 786; error   : Instruction 'redux.f32' not supported on .target 'sm_120a'
```

RTX 5060 Ti (cc 12.0), develop `a0f7b9f4`, `-m L0 test/python/norm`: 25 failed, all in `norm/cutedsl/test_rmsnorm_rht_amax.py` (`compile_execute`, `wrapper`, `check_support_shared_memory_bound`).

## Change

Both reductions in `python/cudnn/rmsnorm_rht_amax/kernel.py` now go through `_warp_fmax`:
- Where the target has `redux.f32`: the same single `redux.sync.max.f32` as today.
- Where it does not: a five-step butterfly of the kernel's own `max.f32`. This applies when `target_needs_shuffle_amax()` is true (SM110) or the target is cc 12.x. It keeps the existing semantics (no NaN propagation, like the non-`.NaN` `redux` and the in-thread `max.f32`) and leaves the result on every lane.

I left the shared predicate in `_cutlass_helpers/warp_reduce.py` alone. `test_sm110_amax_reduction.py` pins it to SM110 for the GEMM kernels, which are gated off cc 12.x anyway.

## Testing

PTX check: I compiled the kernel from develop and from this PR with a forced target (`CUTE_DSL_ARCH`, `CUTE_DSL_KEEP=ptx`), for two shapes, and compared the PTX with `.file`/`.loc` lines stripped.

| target | develop | this PR |
|---|---|---|
| `sm_100a` | 4 `redux…f32` | byte-identical to develop |
| `sm_103a` | 4 `redux…f32` | byte-identical to develop |
| `sm_120a` | ptxas fails | assembles, no `redux.f32` |
| `sm_110a` | ptxas fails | assembles, no `redux.f32` |

RTX 5060 Ti (cc 12.0), cuDNN 9.27, CuTe DSL 4.8.1, `-m L0 test/python/norm`:
- develop: 25 failed, 1222 passed.
- this PR: 1247 passed, 172 skipped, 0 failed. That includes `test_rmsnorm_rht_amax_check_support_shared_memory_bound`.

I have no SM110 part, so for SM110 the claim is only that the kernel now assembles there.

`black 26.3.1 --line-length 160 --fast` is clean.

## Not in this PR

Other direct `warp_redux_sync(..., "fmax")` users have the same target limits, but did not fail in my sweeps: `block_sparse_attention/_fp8_quant.py`, the `deepseek_sparse_attention` sm100 score-recompute kernels, `frost/tile_dsl/pointwise.py`, `gated_attention_block/kernels/proj_gemm_norm_rope_mxfp8.py`, and the `moe_ep` megamoe helpers. They are gated or SM100-specific, as far as I can tell.
