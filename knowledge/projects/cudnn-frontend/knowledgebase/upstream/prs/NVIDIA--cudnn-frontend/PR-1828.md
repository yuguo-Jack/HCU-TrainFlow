## Affected area

FE OSS kernels or CuTeDSL (SDPA forward heuristics / placement)

## Summary

This PR changes the default order and split choice for **paged bf16 d128 THD causal prefill** with page 16 and head-major in-page K. All of it is graph-declaration policy: nothing reads device lengths.

**Rubin (cc 10.7)**, `_sm107_paged_gqa_prefill`. The FROST block leads in two cases:
- **Chunks:** GQA 4 / 8 / 16 bottom-right chunks with b 1–4, 128 < effective Q ≤ 1024 and S_kv 2k–32k. This holds for exact and bounded (`shape_overrides`) declarations.
- **Full squares:** GQA 4 / 8 / 16 full causal squares with 768 ≤ S ≤ 8192, in either alignment. A bounded square is judged on its declared Q = KV capacity, which is how FlashInfer's full prefill declares it.

MHA and group 2 keep the backend.

**SM100 (cc 10.0)**, `_sm100_paged_gqa_prefill`. The FROST block leads for:
- GQA16, whether the declaration is exact or bounded;
- GQA 4 / 8 when the declaration is bounded or carries no total-Q bound.

Paged SM100 also lists the packed set first for GQA16.

**Split budget (`paged_thd_split_choice`):**
- Rubin's split domain now admits group 16.
- On Rubin, GQA (group ≥ 4) chunks past one 128-row Q tile get a two-wave budget, because the declared capacity (b · max_q) overstates mixed-length work.
- The first-wave split is listed right after the default split as an autotune candidate (review P2).

## Why

On these graphs the default was the backend wherever the earlier Rubin paged LEAD box did not apply, which was everything except large-batch short-query graphs. On SM100 the default was engine 10 for every paged GQA prefill.

The backend works against the declared capacity, while FROST runs the actual lengths. Mixed-length bounded declarations, which FlashInfer uses, are where that gap is largest. The mechanism is stated as consistent with the data, not verified.

**Review P2 (two-wave tie-break).** Preferring the first-wave split at equal modelled work was measured on mixed-length declarations and regressed one case: one short and one long KV under the same declared capacity. That is why the default keeps the two-wave split and the first-wave split is offered as the next candidate.

**Validation.** Done with the FlashInfer prefill integration work.
- **Holdouts:** every extension was checked on a holdout frozen before the rule was written, using the real FlashInfer paged prefill wrapper metadata. The holdouts covered exact and bounded declarations, Stats on and off, and both traversal orders.
- **Correctness:** full FP64 O / LSE, fresh pointers, and replayed / retained CUDA-graph captures.
- **Default dispatch:** the runs used default dispatch with `CUDNN_FRONTEND_ENABLE_FROST_ENGINES` unset, which bypasses placement when set.
- **Results:** performance outcomes are kept internal.
