# fix(bsa): SM100 blk64 bwd LSE/sum_OdO cp.async zero-fill and Q-tail pad block

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1682) · state: closed · merged: True

## Original PR description

## Summary

Two fixes in the SM100 blk64 BSA backward load warp (`csrc/bwd/sm100_blk64/bsa_bwd_sm100.py`).

### 1. LSE / sum_OdO zero-fill not covered by `PipelineCpAsync`

`load()` copied valid LSE / sum_OdO rows with `cp.async` but cleared out-of-range rows with plain shared-memory stores (`.fill(0.0)`), then signalled the compute warps through `PipelineCpAsync.producer_commit` (`cp.async.mbarrier.arrive.noinc`). That arrive only tracks the issuing thread's `cp.async` operations, so it does not by itself make the plain zero stores visible to the consumer.

The out-of-range rows now go through the same `cp.async` with src-size 0 (a predicated `CopyG2SOp` copy), so valid data and zero-fill share one completion mechanism. All 8 sites are covered: first round and main loop, LSE and sum_OdO, both Q-block slots. The pipeline protocol is unchanged: still `PipelineCpAsync`, same acquire/commit/wait/release, stage advance and arrival counts, and no added fences or barriers.

PTX of the compiled kernel (DSL 4.6.2):

| | before | after |
|---|---|---|
| `st.shared.b32 [..], 0` | 16 | 0 |
| `cp.async.ca.shared.global ..., 4, %r` with `%r = selp.b32 4, 0, %p` | 0 | 16 |
| `cp.async.mbarrier.arrive.noinc` | 4 | 4 |

This closes a synchronization gap. It has not been shown to be the cause of any observed training NaN.

### 2. Odd-length k2q pad slot aliased the real tail block when `seqlen_q % 64 != 0`

An odd-length per-KV Q list pads its second slot with `seqlen_q // 64`. When `seqlen_q` is not a multiple of 64, that index is the real partial last Q block, so every odd-length KV list processed it a second time: it was counted twice, or attended KV blocks it never selected. The backward API does not reject such `seqlen_q`, and the blk64 forward handles it correctly.

The pad now uses `ceil_div(seqlen_q, 64)` at all three sites: `load()` first round, `load()` main loop, and the dQ reduce warp. With that index the pad block's Q / dO are TMA zero-filled, its LSE / sum_OdO are cp.async zero-filled, and its dQ TMA reduce falls past the dQ accumulator rows (`round_up(Sq, 8)`). For 64-aligned `seqlen_q` the index is unchanged.

### 3. DSA test fix for the develop-side CI failure (separate commit)

After rebasing onto the current develop (`bd4ebddd`), the `python/*/cutedsl:cutlass-rel:sm100` lane hit 10 DSA backward failures that exist on develop itself and are unrelated to BSA. They come from two PRs that never ran CI together:

- #1666 proves the H128 two-CTA route by finding its key in `flash_attn_bwd_sm100.compile_cache`.
- #1679 makes deterministic SM100 plans compile their own artifact in `compile()` (`_compile_deterministic_sm100`) and launch it through `_compiled_kernel`, so that key never appears.

The 10 failing cases are the `deterministic-d512` variants of `h128_two_cta_handles_sink_limits` (6), `h128_two_cta_one_key_padded_gradients` (3) and `h128_two_cta_padded_slots_under_very_negative_lse` (1). They fail only on the route assertion; their gradient checks pass.

For deterministic cases the tests now record the backend each deterministic plan compiles, via a spy on `_compile_deterministic_sm100`. The spy also empties the wrapper's plan cache for the test, so a plan built by an earlier test still reaches `compile()`. Ordinary cases keep the original `compile_cache` assertion unchanged.

- The 3 tests, all combinations (D512/D576 × ordinary/deterministic): 40 passed. develop has 10 failures on the same selection.
