# fix(hstu): give each SiLU warp group its own epilogue barrier at q_stage=1

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2007) · state: closed · merged: True

## Original PR description

Addresses the main item of #2002: a hang (and possible wrong output) in the HSTU SM100 forward kernel when `q_stage == 1`.

## Problem

With `q_stage == 1`, SiLU group 1 stores the single O accumulator and calls `store_O(stage=0)`. Both `store_O` barriers then use `EPILOGUE_BARRIER_BASE + 0` = **barrier 1**, which is also SiLU group 0's scheduler-tail barrier. The two groups can be in flight at the same time. The emitted 2-CTA PTX on `develop` shows the collision: `bar.sync 1, 128` ×3 (two in `store_O`, plus group 0's tail) and `bar.sync 2, 128` ×1.

A named barrier's count is a participant *count*. It does not say which threads arrive, so arrivals from the two groups mix across phases:

- **Early release → wrong output.** Group 1's warp 0 can be released together with group-0 warps and issue the TMA store before group 1's other warps have written `sO`. This affects multi-row M128 epilogues, which today means the 2-CTA path (selected only on SM107 for D128 causal).
- **Deadlock.** Example interleaving:
  1. Phase 1: g1 w1–w3 (store_O #1) + g0 w0 (tail).
  2. Phase 2: g1 w1 (store_O #2) + g0 w1–w3 (tail).
  3. Phase 3: g1 w2, w3 (#2) + g1 w0 (#1, late because it was waiting on the previous bulk store). That is 3 warps, and the 4th can only be w0's own later arrival, so the phase never completes.

  The hang depends only on barrier arrival order, so it reaches **every q_stage=1 config with CLC + TMA-O on SM100/103/107**, including the qlen=1 paths, with or without the CLC descriptor.

## Fix

- Select the `store_O` barrier by the owning warp group: `EPILOGUE_BARRIER_BASE + (stage if q_stage == 2 else 1)`. Accumulator indexing and the scheduler-tail IDs are unchanged, and the `q_stage == 2` mapping is identical. Group 0 now owns barrier 1 and group 1 owns barrier 2. PTX: `barrier.sync 1, 128` ×1, `barrier.sync 2, 128` ×3.
- These epilogue/tail barriers are reached only from the SiLU warp-role branch, so they now use an unaligned `barrier.cta.sync` (`named_barrier.sync_unaligned`, the same helper pattern as `flex_attention/kernels/common/barrier.py`) instead of the implicitly aligned `bar.sync`.

## Validation (GB200, CuTe DSL 4.8.0)

The race window is narrow: 80k natural launches of the forced 2-CTA kernel on `develop` never failed. To reproduce deterministically, I injected `globaltimer` spin delays on specific warps in a scratch copy of the kernel (not part of this PR). 2-CTA was forced by overriding the cached device capability to (10, 7).

| Injected schedule | `develop` | this PR |
|---|---|---|
| Corruption schedule, 2-CTA | 50/50 launches wrong (~96 rows × 148 CTAs each) | 0/50, bit-exact vs the 1-CTA q_stage=2 kernel |
| Deadlock schedule, 2-CTA | **hang** (600 s timeout) | completes, bit-exact |
| Deadlock schedule, qlen=1 M64 (GB200 default), descriptor on | **hang** (300 s timeout) | completes |
| Deadlock schedule, qlen=1 M128, descriptor on | **hang** (300 s timeout) | completes |

- `test/python/hstu/cutedsl/hstu_attention -m "L0 or L1"`: 304 passed, 1 skipped.
- The reporter confirmed that applying this change removed the hang they were seeing.
- Not run on SM107 hardware (the only arch where the 2-CTA path is selected through the public API).

## Not in this PR (follow-ups from #2002)

- The 2-CTA TMEM allocation/release named barriers (IDs 3/4, partly through `TmemAllocator`) still lower to aligned `bar.sync` / `bar.arrive` on a warp subset.
- 2-CTA initialization emits `barrier.cluster.arrive.relaxed` twice before any `wait`, because `PipelineClcFetchAsync.create` runs its own cluster sync after `pipeline_init_arrive`. Fix: `defer_sync=True` plus a single arrive/wait after all pipelines are initialized.
