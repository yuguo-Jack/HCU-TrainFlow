## Affected area

FE OSS kernels or CuTeDSL

## Summary

Keep the online softmax of block-sparse attention forward on Blackwell SM100/SM110 max-centered for large finite logits, in both the 128×128 (blk128) and 64×64 (blk64) kernels.

Main changes:

- Guard the FFMA exponent argument in `SoftmaxSm100.scale_subtract_rowmax` so it stays max-centered for large logits: a warp holding a row with a large scaled max subtracts the max first. This is the guard from #1213's SM90 blk64 `inc_softmax_ffma`, and blk64 uses it; see Online softmax correction.
- Add the constexpr keyword `always_center=False` at the end of the helper's signature. blk128 passes `True`, so it always subtracts the max before scaling, which costs it less than the guard's branch; see Performance.
- Add L0 regression tests for SM100/SM110 with finite logits on the order of 1e10; see Testing.

The blk64 Sage FP8 path, the SM90 blk128 forward and the `SoftmaxSm100` copy in `flex_attention` compute the same FFMA form and are unchanged; #1213 covers SM90 blk64. Backward recomputes P from the stored LSE, whose own rounding at these magnitudes needs a separate look.

### Online softmax correction

Online softmax subtracts the running row max, so P stays small before its FP16/BF16 conversion. The FFMA form `fma(s, c, −fl(max·c))`, with `c = softmax_scale·log2 e`, is not exactly centered. At `s = max`, it returns the rounding error of `fl(max·c)`, not 0. For `|max·c| < 2^11`, this error is at most 2^-14, and P(max) still rounds to 1. For logits near 1e10, P overflows or underflows, and O becomes 0 or NaN.

By default, a warp with any row at `|max·c| ≥ 2^11` now subtracts the row max first. The same FFMA then computes `(s−max)·c`, which is exactly 0 at the max. A warp vote keeps the branch uniform, and blk64 calls the helper from a converged warp. Other warps keep the single FFMA. With `always_center=True`, every warp computes `(s−max)·c` as FADD2 + FMUL2. The new DSL calls all exist in nvidia-cutlass-dsl 4.6.2, the package floor.

## Why

Finite logits near 1e10 silently give O = 0 or NaN, and often LSE = ±inf. Such logits are far outside typical activations but inside the supported input domain. On B200, the unfixed blk128 BF16 kernel also hung when such rows shared a warp with ordinary rows. #1213's review found the defect. It already exists on `develop` (`a5d61f45`), and #1213 fixes only SM90 blk64.

## Performance check

On B200, forward latency changes by **−4.36%** for blk64 (BF16) and by **+3.72%** / **+2.34%** for blk128 (FP16 / BF16). Each is a geometric mean over #1213's six shapes against `develop`. Measured the same way, the guard costs blk128 +12.03% / +8.79%, and always centering costs blk64 +3.64%. The B200 runs predate a refactor that left the sm_100a SASS unchanged.

### sm_100a SASS check

The guard's check is one FSETP, VOTE.ANY, FSEL and uniform branch per call site. In blk128, the branch also changes register allocation and moves spill traffic into the per-block softmax step. Always centering adds 64 packed ops per call site. It keeps `develop`'s registers, stack and spills. 

## Testing

The new `test_bsa_attention_forward_sm100_large_*` cases in the [BSA forward tests](https://github.com/Butterfingrz/cudnn-frontend/blob/bsa-sm100-softmax-fix/test/python/fe_api/bsa/test_BSA_attention_forward.py) check the online softmax correction on blk128 (FP16) and blk64 (BF16). They cover equal large logits, a running max that rises or falls, and large-logit rows that share a warp with ordinary rows. On B200, all 10 fail on `develop`. With this PR, they pass, and so do the BSA forward, backward and FP8 L0 suites. On ordinary inputs, blk64 stays bitwise identical to `develop`, and blk128 stays within 2e-3 of it. SM103 and SM110 were not tested.

Test environment:

- NVIDIA B200, driver 580.95.05.
- PyTorch 2.14.0+cu130, CUDA runtime 13.0.
- `nvidia-cutlass-dsl==4.8.0`, CUDA 13.4 compilation backend.
