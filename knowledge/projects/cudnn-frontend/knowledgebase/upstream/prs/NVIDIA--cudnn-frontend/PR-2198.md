# gemm(frost sm100): zero the K padding slots of F8_128x4 quant-scale rows

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2198) · state: open · merged: False

## Original PR description

## Problem

#2011 (B03) fixed this in the SM120 tree. The SM100 `block_scale_quantize` epilogue also leaves the K-direction padding slots of every F8_128x4 scale row unwritten.

A scale row holds `roundup(blocks, 4)` slots, but the epilogue stores only real `(row, block)` pairs, and no host step initializes the blob. A block-scaled GEMM whose K is the quantized axis loads whole F8_128x4 atoms and multiplies those slots against its zero-filled K tail. A stale NaN encoding there (E8M0 `0xFF`, E4M3 `0x7F`/`0xFF`) turns that whole output row into NaN, with no error.

## Change

- `sm100/epilogue_codegen.py`: the lane that stores a scale row's last real block now also stores 0 to the remaining slots of its 4-byte quad, under the same predicate.
  - Inline in the SM100 col-quant emitter.
  - After the shared row emitter's scale stores, in the SM100 `_emit_block_quant` wrapper. The shared emitter is unchanged.
  - Same helpers (`_f8_128x4_k_padding`, `_emit_f8_128x4_k_pad_zero`) as the SM120 tree.
  - Grouped token-axis segments have no padding slots, and rows that only pad a 128-row atom stay unwritten.
- Tests:
  - `test_sm120_quant_scale_k_padding_is_zeroed` becomes a helper that SM100 also runs: row, and row under the col quant's row predicate. Each prefills the scale buffer with 0xFF.
  - `_run_moe_swap_ab_quant` (SM100, plain and block-scale MoE) expected the K padding slots of real scale rows to keep the buffer's `0xA5`. It now expects 0 there, except for token-axis grouped segments, which have none.

## Tests

On a B300 (cc 10.3), develop d760fefe:
- New `test_sm100_quant_scale_k_padding_is_zeroed`: 2 failed on develop, 2 passed with this change.
- `-m "L0 or L1" -k quant` over `test_matmul.py`, `test_moe_grouped_matmul_fwd.py` and `test_moe_grouped_block_scale_matmul_fwd.py`: 132 passed, 38 skipped.
- `pre-commit` on the touched files passes.

**What the rework does.**
- The shared row emitter and the SM100 col emitter are byte-identical to develop.
- Each quantized output gets one padding block appended at the end of the epilogue body, after every store.
- Only the thread holding the row's last real block enters it, under that block's own store predicate.
- The padding is written as raw 0x00 bytes (`Int8(0)` bitcast to the store type).

**Correctness (B300).**
- Residues 0–3 for both row and col quant pass, each run through one compiled kernel (changed-shape reuse). So do an SM100 MoE twin (both axes, both orientations) and the swapAB quant cases. Padding bytes are asserted as `uint8`.
- The quant/FP4 subset of `test_matmul` / `test_moe_grouped_matmul_fwd` / `test_block_scale_matmul` passes: 338 passed, 186 skipped.

**What's left.** The remaining +2–5% on unpadded shapes is the per-vector guard itself: one predicate and one branch per epilogue vector. I don't think more predicate tuning will reach zero; in the sm_100a PTX this branch shape is fragile. So the choice is between:

- **(a)** Keep the rework as is. Every plan serves every N, at +1.8–4.8% on unpadded shapes.
- **(b)** Plan-time specialization. A plan whose N (or M, for col quant) ends its scale rows on whole quads emits exactly develop's epilogue, with zero overhead. A plan built for a padded N keeps the guarded block and serves any N.
  - The cost is narrower reuse: an unpadded plan executed at a padded N must refuse with a typed `ValueError`, or it would leave the padding stale.
  - SM100 plans don't run `_check_runtime_quant` today (`_validate_runtime_quant` is only set in the sm120 tree), so this adds that execute-time check on SM100.
- **(c)** Compile both variants at plan time and pick one on the host from N's residue at launch. Zero overhead and full reuse, but 2× compile time for these chains plus a check per launch.

My preference is (b), because the zero-overhead claim then holds structurally rather than only for the shapes I timed. But it narrows reuse, so I'd rather you choose. Which do you prefer?
