# Fix SDPA stats rendering checks across DSL builds

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/2190) · state: closed · merged: True

## Original PR description

## Summary
The 2-CTA SDPA stats census misses valid global-to-shared bulk copies emitted as `shared::cta` by newer DSL builds. Correcting that count alone still skips the reported build because only a 4.8.1 rendering record exists.

## Fix
Recognize both CTA and cluster destination spellings, and add measured per-kernel records for the exact 4.9 development build. Select records by full DSL version while keeping the existing 4.8.1 records and unknown-build skip guard.

Check the cast against each form’s exact record: its entry-region hash includes the following kernel’s `.globl` annotation, which differs between forms even with identical cast instructions. All owned-kernel hashes and opcode counts remain pinned.

## Manual verification
[PASSED] Five affected host-render tests on DSL 4.8.1 and five on `4.9.0.dev0+20261028185815.e475245` (with the matching libs and the reported libs-base build). Includes sm_100a, sm_103a, debug-clock, mask-form and stats-form checks; no skips.

The original matcher reproduces the zero-versus-one failure on the 4.9 build. Control checks reject corrupted hashes and skip unrecorded DSL versions. Matcher exclusion, Black/Black Jupyter, SPDX and whitespace checks pass.

These are host-compilation/PTX checks; numerical GPU execution and performance were not measured.

- RomanAnders90 · comment · 2026-11-03T02:58:02Z · [source](https://github.com/NVIDIA/cudnn-frontend/pull/2190#issuecomment-6594293620)

Post-merge review. The fix is right and well documented: the census matcher now accepts both bulk-copy destination spellings, and the exact-version record selection keeps the unknown-build skip guard intact. Three small follow-ups, none blocking:

1. **Labels.** `AGENTS.md` § PR labels and the PR template ask for one `orig-*` label per PR; this one carries `cat-bug` + `area:*` only (every other merged PR in the 1.33.0 milestone has an `orig-*` label). `orig-nv-eng` looks right for the dkg-ai-bugfix agent unless maintainers want a dedicated originator label for agent-created PRs. Sibling fix PRs also use `cat-bugfix` rather than `cat-bug` (the issue-report label). The agent-generated body dropped the template checklist, so the label step was never self-checked; worth fixing in the agent so its PRs arrive fully labeled.

2. **Per-kernel md5 regions.** `ptx_kernel_md5s` hashes from a kernel's `.entry` line up to the *next* `.entry`, so every region ends with the following kernel's `// .globl <mangled name>` line. That is why the cast md5 differs between the two forms here, and the existing one-CTA record already pins the byte-identical `delta_zero_thd_d128_kernel` at two different md5s (`thd` vs `grouped_thd`) for the same reason. A signature change or reorder of a neighbour, including the excluded shared fold whose `.globl` sits inside the cast's region, reddens an unchanged kernel's row, which the per-kernel records were introduced to avoid. Dropping that trailing line (or ending the region at the closing `}`) would make every row self-contained and let the dropped `cast_ldg == cast_default` invariant come back, at the cost of re-pinning the 28 rows of the four record files once. Optional, and the hash stays a strict superset either way (false reds only, never a missed change).

3. **Record key on dev builds.** The selection and the skip guard key on the `nvidia-cutlass-dsl` metadata version, but that wheel is metadata-only; the PTX text comes from `nvidia-cutlass-dsl-libs-core` / `-libs-cu12|cu13` (plus `-libs-base`), and this record's own header shows the dev build carrying a different libs-base stamp. Release wheels pin the libs wheels with exact `==`, so only dev/nightly installs could see a same-DSL/different-libs md5 failure instead of a skip. Folding the libs versions (or the compiler DSO's `DSO_SHA256` fingerprint) into the `dsl=` key would make the dev-build pin honest too. This is the repo-wide record convention, so a separate issue if at all.
