## Affected area

FE OSS kernels or CuTeDSL (Python/JAX entry points)

## Summary

Follow-up to #1399 and #1535. The grouped quant wrapper, which Transformer Engine's fused MLP uses for FC2 and for the FC1 dgrad, rejected every JAX input. This adds the canonical MXFP8 JAX path, so the MXFP8 MoE forward and backward set (GLU, dGLU, wgrad, quant/dgrad) is complete from JAX on SM100 and Rubin.

- **New entry `cudnn.grouped_gemm_quant_jax_forward`** (jittable, built on `cudnn.jax.call`), dense weights only:
  - A `(m, k)`; B `(experts, n, k)`, or column-wise `(experts, k, n)` with `b_major="n"` (the dFC1 layout from #1422); packed E8M0 scale bytes at any dense rank; optional prob `(m,)`.
  - BF16/FP16 `d_dtype` (default BF16) produces D only. An FP8 `d_dtype` requires `norm_const_tensor` and also produces D_col and the SFD buffers.
  - Returns a `TupleDict` with the eager wrapper's keys; `amax_tensor` is always None. Outputs are not zero-filled.
  - Runs the Rubin quant kernel on SM107 and the SM100 kernel otherwise. The plan cache is keyed by architecture.
- **Wrapper dispatch:** `grouped_gemm_quant_wrapper_sm100` sends JAX inputs with a dense `b_tensor` to it, before the memo.
- **Name:** this is a new public op, so it follows `docs/fe-oss-apis/api_conventions.md` (`<op>_jax_<direction>`, no architecture suffix), unlike its older `*_jax_sm100` siblings. It is reachable from the `cudnn.gemm.cutedsl.grouped` family module only because the lazy-export table and the API index route through it.

## Why

TE's JAX MoE runs GLU and dGLU through cuDNN but the FC1 dgrad through its own grouped GEMM, because no cuDNN JAX path existed for it. After #1422 the quant kernels take canonical layouts, including N-major B, so the JAX adapter passes arrays straight through.

## Related issues

Follow-up to #1275 / #1399 / #1535.

## API and compatibility impact

- One new export: `grouped_gemm_quant_jax_forward` (API index updated).
- `grouped_gemm_quant_wrapper_sm100` with dense MXFP8 JAX inputs now runs instead of raising. It requires `sf_vec_size=32`, and `generate_amax=False` for a BF16/FP16 output (the wrapper default is True; amax is not generated from JAX). Bias, row scale, a caller `d_tensor`, dynamic scheduling, FP4 and `sf_fp8_dtype_override` raise `ValueError` naming the option.
- Discrete (`b_ptrs`) JAX inputs and the `GroupedGemmQuantSm100` class stay rejected, as before. Torch behavior is unchanged.

- `pytest test/python/gemm/cutedsl/test_grouped_gemm_quant.py test/python/gemm/cutedsl/test_grouped_gemm_wrapper_memo.py`: **216 passed, 196 skipped**.
- New in `test_grouped_gemm_canonical_jax.py`:
  - `test_canonical_jax_quant_parity`: K- and N-major B, BF16 and FP8 output, with and without prob, 1 and 4 experts, entry and wrapper; eager, jit with command buffers, and an alpha change on the compiled call; byte parity against the Torch wrapper on the same buffers.
  - `test_jax_quant_rejects_unsupported_options`, quant added to the kernel-dispatch test (gated on the DSL's `sm_107a` support) and to the torch-free (`sys.modules["torch"] = None`) jitted run.

No Rubin kernel was executed.
