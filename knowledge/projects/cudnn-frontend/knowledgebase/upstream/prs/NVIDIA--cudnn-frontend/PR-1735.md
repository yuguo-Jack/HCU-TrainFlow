## Affected area

`cudnn.linear_attention` cuTile engine and its tests.

## Summary

1. Run the existing linear-attention determinism tests on cuTile as well as FROST.
2. The cuTile launch autotune can change GDN's bits, so skip it when `torch.are_deterministic_algorithms_enabled()` is true.

## Why

The determinism tests pinned `frost` only. Running them on cuTile passed (repeats inside one process reuse the first autotune pick), but that hides the real hazard: the pick is timing-based and cached per process. Forcing each candidate config shows that for **GDN** the output, `dq` and `dk` are not the same across candidates (pinned config, run twice, hashes of `o`):

```
gdn  config (occ,nww)   o-hash
     0 (1,4)            69c4538b
     2 (2,4)            69c4538b
     1,3,4,5,6,7        35551d88   (final_state identical for all; each config repeats itself)
kda  all 8 configs      identical
```

So two runs whose timings pick differently disagree, even though each config is repeatable. `autotuned_launch`'s docstring says tuning never moves numerics; that holds for KDA (BV is pure V-tiling) but not for GDN's occupancy / num_worker_warps hints.

## How

- `cutile/kernels/common.py`: `deterministic_requested()` reads torch's flag if torch is already loaded (a JAX-only process is unaffected). In `autotuned_launch`, a deterministic run takes the first config without timing; the cache key includes the flag.
- `cutile/kernels/kda.py`: `autotuned_launch_bv` takes `bv_choices[0]` under the same condition (BV does not move the numerics; this only removes the timed pick).
- Tests: `DETERMINISM_BACKENDS = ["frost", "cutile"]` on `test_determinism_fwd/_bwd/_multi_tile_fwd/_multi_tile_bwd` and `test_multi_graph_stress` (fwd tests now inside `waive_unsupported`). New `test_determinism_cutile_autotune_configs` forces each autotune pick under deterministic mode and compares fwd/bwd bits.

## API and compatibility impact

Default (non-deterministic) behaviour is unchanged. Under `torch.use_deterministic_algorithms(True)` cuTile uses the first config instead of the tuned one, so it can be slower there.

## Testing

1x GB300 (SM103), nemo 26.10.rc5 image, cudnn-frontend 1.29.0 (`1.29-megatron` checkout) with this diff overlaid:

```
test_determinism_cutile_autotune_configs   with fix:    gdn PASSED, kda PASSED
                                           without fix: gdn FAILED ("autotune pick 1 o differs bitwise"), kda PASSED
determinism fwd/bwd/multi_tile/stress on frost+cutile  36 passed, 12 skipped (cuTile has no gdn2/gdp/mamba2 plan)
```

Not run: the commit as rebased onto `develop` (`42200cd6`; needs a newer compiled module than the 1.29.0 checkout above), other architectures, and whether the first config is the fastest (the deterministic path may be slower). The rebase and the later comment edits in `test_la.py` (the determinism section header and `MAX_AUTOTUNE_CONFIGS`) change no code paths; the numbers above are from the earlier, pre-rebase run of the same diff.

## Related: KDA and Gated Delta Product determinism

Measured on 1x GB300, FLA 0.5.2, bf16, one shape per kernel, with the Megatron-Bridge deterministic-recipe setup applied. This is a measurement of the FLA Triton kernels, not a change in this PR:

- FLA `chunk_kda` and `chunk_gated_delta_product` are bit-exact across repeats inside one process (packed and dense).
- Across two processes they differ (KDA `dA_log`, GDP `dg`) while FLA's own timed autotune is outside Megatron's pinned autotune scope, and are identical once it is pinned. The cuTile fallback in this PR is the same shape of hazard, which is why it is pinned here.
- cuTile has no GDP plan, so the GDP rows of the determinism tests here are skipped.
