# fix(sdpa): share masked D192 CGA2 loader state

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1841) · state: closed · merged: True

## Original PR description

The masked two-CTA D192/V128 loader started carrying independent K and V cursor states in #1794. These rings have the same depth and advance together, but keeping both states live across scheduler decodes increased SM103 local-memory instructions and tripped the existing spill regression check.

Share the cursor for masked CGA2 loads and drain the paired rings together. Keep the single-CTA sub-stage pipeline and dense CGA2 lowering unchanged. There is no new tuning knob, dispatch rule, host execution work, or relaxed test threshold.

Validation:
- Same public CuTe DSL 4.8 compiler and SM103 target: the existing causal configuration returns from 32 stores / 38 loads to 12 / 12. Dense CGA2 and both CGA1 control cubins remain byte-identical. The immediate parent / #1794 comparison reproduces the change.
- B200: 53 existing D192 forward, split-KV and paged tests passed with zero skips. Four fresh ABBA processes each passed 16 FP16/BF16 cases checking O/LSE against fp64, changed lengths, fresh bindings/workspaces and poisoned retained CUDA-graph replay. This source-specific run used public develop5169b269 plus the kernel patch, cuDNN9.27 and public DSL4.8.
- The PR starts from develop6534a09d7, whose D192 source matches that baseline. The final source only adds explanatory comments to the qualified candidate. Scoped pre-commit and diff checks passed.
- Exact-PR-source B200 sanitizer qualification completed: 16 memcheck cases and 16 synccheck cases passed with zero errors, retaining all numerical and capture assertions. The validation uses driver-compatible CUDA bindings and explicit API-error reporting; no-FE controls attribute the initial API reports, and an invalid-device control still fails as expected. [Full qualification and reporting-mode details](https://github.com/NVIDIA/cudnn-frontend/pull/1841#issuecomment-6388705253). SM103 runtime performance is not claimed, and the independent backward-artifact subprocess timeouts are not addressed by this change.
