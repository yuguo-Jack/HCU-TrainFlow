# Accept canonical layouts in the BF16 grouped GEMM backends and stop reading offsets to the host

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1602) · state: closed · merged: True

## Original PR description

## Summary

Brings the BF16 grouped GEMM backends in line with the block-scaled ones (#1233, #1422) for Transformer Engine's BF16 fused grouped MLP, which calls GLU, the plain grouped GEMM, dGLU and wgrad. It folds in the host-overhead work from @tingyangk's #1628.

**No device reads on the host (Rule 3).**
- The BF16 GLU, plain grouped GEMM and wgrad backends copied `padded_offsets` / `offsets_tensor` to the host to validate them: once at construction, and again in `execute()` whenever it saw a tensor it had not validated before. They did the same for pointer-array entries. A caller that builds a new offsets tensor each step paid a blocking device-to-host read on every call.
- These checks now use the existing `debug_validate_offsets` / `debug_validate_pointer_values` helpers, as BF16 dGLU already does: a no-op unless `CUDNN_FE_GROUPED_GEMM_VALIDATE_DEVICE_VALUES=1`.
- wgrad's `can_implement` gets a synthetic split with the right total instead of the sample's values.

**Cheaper `execute()`.**
- All four backends check operand metadata once per distinct (shape, stride, dtype, device) signature, cached in one dictionary lookup. Data-pointer alignment and pointer-array stream recording still run on every call.
- The plain grouped GEMM wrapper also uses its fast path when the caller supplies `c_tensor` or `d_tensor`, as TE does.
- `stream_context` treats a default-stream sentinel handle (0 or 1) as a no-op while torch is on its default stream. TE passes `torch.cuda.current_stream().cuda_stream`, which is 0 there, so every wrapper used to enter a `torch.cuda.stream()` context on every call.

**Canonical layouts (torch).**
- **GLU, plain grouped GEMM and dGLU** accept contiguous A `(m, k)`, prob `(m,)`, and dense B `(l, n, k)`. dGLU also accepts C `(m, 2n)`, dprob `(m,)` and a 2-D activation output. With 2-D A, outputs are 2-D, including a caller-provided `d_tensor` for the plain GEMM.
- **N-major canonical B:** the plain grouped GEMM and dGLU accept the `(l, k, n)` buffer with `b_major="n"`. For a dgrad GEMM this is the weight as stored, so the caller needs no transposed copy and no pointer array.
- wgrad already takes natural 2-D inputs and needed no layout change.
- Operands compile at their own rank and the kernels convert them at trace time. `execute()` rejects an operand whose layout differs from the one the kernel was compiled for.
- All four wrappers advertise `supports_bf16_canonical_layouts`, the name #1628 used. The GLU and dGLU wrappers' existing `supports_canonical_layouts` only covers the block-scaled backend.
- Legacy layouts are unchanged.

## Measurements

SM100, pinned CPU, medians of three interleaved rounds.

**TE BF16 fused grouped MLP** (NVIDIA/TransformerEngine#3646 on TE `main`), 64 experts, hidden 4096, FFN 1024, 16384 tokens, in µs:

| cuDNN frontend | Forward host | Forward end-to-end | Fwd+bwd host | Fwd+bwd end-to-end |
|---|---:|---:|---:|---:|
| `develop` | 533 | 658 | 4526 | 4742 |
| #1628 | 200 | 626 | 1455 | 4551 |
| This PR | 200 | 625 | 1447 | 4645 |
| This PR, with TE passing the N-major weight and two TE host fixes | 200 | 632 | 846 | 2094 |
| Unfused TE (cuBLAS), for reference | 264 | 698 | 1340 | 2263 |

- On `develop` the host blocks on the device reads, so host time nearly equals end-to-end time.
- Most of the remaining fused backward GPU time (2.3 ms) is TE transposing the whole FC1 weight on every step for the dgrad GEMM. Passing the stored weight with `b_major="n"` removes that copy. With it, outputs and all gradients are bitwise identical to the copy path.
- The two TE host fixes are a dense dGLU weight instead of per-expert pointers, and allocating the weight-gradient buffer directly instead of building a split GroupedTensor (217 µs per call).
- The TE changes are not part of this PR.

**Wrapper alone**, a new offsets tensor each call, before the caching changes above (µs):

| Wrapper | `develop` | This PR's first commit |
|---|---:|---:|
| GLU | 72.5 | 43.3 |
| Plain grouped GEMM | 66.9 | 38.0 |
| dGLU | 72.1 | 73.7 |

**Block-scaled wrappers:** the stream fast path applies to them as well. Called with the exact arguments TE's NVFP4 MLP passes, NVFP4 dGLU host time drops from 119 to 91 µs per call (see #1601).

## Testing

All on SM100.
- **New `test_grouped_gemm_bf16_canonical.py`:**
  - GLU, plain GEMM and dGLU: canonical against legacy, bitwise, on cold and warm calls, including the N-major weight and a caller-provided 2-D `d_tensor`.
  - No host read: after a warm-up call, a second call with a new offsets tensor runs under `torch.cuda.set_sync_debug_mode("error")` for all four backends in both layouts. On `develop` this fails for GLU, plain GEMM and wgrad.
  - The class API rejects a legacy operand on a kernel compiled for canonical layouts.
- **BF16 and JAX suites** (`test_grouped_gemm_bf16.py`, `test_grouped_gemm_dglu_activation.py`, `test_grouped_gemm_dglu_bf16_training.py`, `gemm/jax`): 233 passed, 1 skipped, 2 xfailed.
- **Wider regression** (GLU, dGLU, dGLU workspace, wgrad, wgrad tensormap, quant canonical, prepared calls, the canonical-layout suites, wrapper memo, `core/cutedsl` including the stream-sentinel tests, and the files above): 1347 passed, 762 skipped, 2 xfailed.
- `core/torch/test_torch_stream.py` and the `core/cutedsl` stream tests: 24 passed, 1 skipped.

## Behavior changes

- Malformed sample offsets no longer raise at construction or `check_support()` unless `CUDNN_FE_GROUPED_GEMM_VALIDATE_DEVICE_VALUES=1`, matching BF16 dGLU.

## Not covered

- JAX arrays keep the legacy BF16 layouts.
- Rubin is not hardware-tested.

**[P2] Preserve the requested device when skipping the default-stream context** ([source](https://github.com/NVIDIA/cudnn-frontend/blob/a6d29312d3c477f1957288b419c034caffdd32ee/python/cudnn/_torch_stream.py#L106))

With CUDA device 1 current, `stream_context(0, torch.device('cuda', 0))` now takes this shortcut because device 0's current raw stream is also 0. It leaves device 1 current, so `torch.empty(1, device='cuda')` inside the context allocates on cuda:1; the base enters device 0 and allocates on cuda:0. The new path also accepts `torch.cuda.default_stream(1)` with an explicit cuda:0 device, bypassing the previous Stream/device mismatch error. Preserve the device-context and Stream-object validation before taking the shortcut, for example by requiring the requested device to be current and validating a Stream object's device first. This is a reproduced host-context regression; grouped-GEMM numerical corruption was not demonstrated.
