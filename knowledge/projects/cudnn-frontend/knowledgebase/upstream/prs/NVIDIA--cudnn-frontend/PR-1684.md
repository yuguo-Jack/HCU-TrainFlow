## Affected area

FE OSS kernels or CuTeDSL (FROST SDPA forward default placement; no kernel change) and Documentation.

## Summary

1. **Rubin per-tensor FP8 row offered by default.** `sdpa_fwd_prefill_sm107_fp8` drops `opt_in`. The new arm `placement._place_sm107_fp8` puts it ahead of the backend on exact cc 10.7 at exact d256 / d512 (dense E4M3, causal top-left / bottom-right or mask-free, Stats on or off). It keeps the backend first for:
   - one KV tile with at most 8 Q tiles (launch-bound, both providers about 7 us);
   - d128 and d192;
   - every feature the A/B did not cover: THD, paged KV, padding mask, window, right band, sink, block-scaled O, fused gate, E5M2.
2. **`Amax_S` is deprecated.** `docs/operations/Attention.md` ("Amax S") and the `sdpa_fp8` docstring now say to leave it virtual and set `scale_s` from the bounds there: `448` without dropout, `448(1-p)` with dropout probability `p`, `448 / (|c| · max |m|)` with a custom dropout mask `m` and scale `c`.
   - A graph that declares it still runs on backend engines only (the FROST FP8 kernels dropped it in #602).
   - The frontend now logs that once per process, from the FROST FP8 rows' decline, past their device-arch check, so devices without a FROST FP8 row stay silent.

## Why

**The backend's d256 FP8 path on Rubin runs at its BF16 rate.** The FROST d256 FP8 kernel already exists but was hidden behind the opt-in.
- d256 GQA 16/2 causal prefill, E4M3 in, BF16 out, same inputs and CUDA-graph timer (cc 10.7, 216 SMs, cuDNN 9.27.0.42):
  - s=4k: backend 62.0 us vs FROST 36.7 us.
  - s=32k: backend 3279 us vs FROST 1479 us.
  - s=128k: backend 45.8 ms vs FROST 26.0 ms.
- At s_q = 1, mask-free, the backend builds no plan at all for d128 / d192 / d256 / d512 (NVRTC compile failure), so those graphs had no provider without the flag.

**Placement A/B.** 456 dense cases (the per-tensor FP8 sets behind `_place_sm100_fp8`, plus a 72-case hold-out), measured with `ab.py`:
- Same graph on both arms, with Amax_S virtual.
- Two rounds with the arm order swapped, warm and cold L2.
- An extra eager-mode pass over the 83 d256 / d512 cases with S_kv < 1024.

Results (regret = slowdown against the faster provider):

| set | develop regret (backend only) | this PR | lead-losses (> 3 % warm or cold) |
|---|---|---|---|
| d256, 81 cases | 67.3 % | 1.3 % | 0 |
| d256 hold-out, 12 | 105.9 % | 0.0 % | 0 |
| d512, 82 cases | 127.9 % | 0.5 % | 0 |
| d512 hold-out, 13 | 152.3 % | 0.0 % | 0 |
| d256 / d512 eager, S_kv < 1024, 83 | 50.3 % | 1.9 % | 0 |

- On the led graphs, FROST time over backend time is 0.16-0.96 at d256 and 0.13-0.81 at d512.
- The trailed small graphs run at 0.82-0.98, except d512 b1 8/1 q32 kv128 mask-free at 1.07-1.11 (graph and eager). That case is why the one-KV-tile floor exists.
- d128 (square median 1.08-1.09, tails to 1.58) and d192 (0.88-1.14, tails to 1.88) stay backend-first.

The SM100 FP8 arm's wider floor (S_kv < 1024 with at most one wave of Q tiles) was not carried over: on this board it would trail 64 graphs that FROST wins in both graph and eager timing.

Note: the hold-out set was visible when the head-dim split was chosen; the KV-tile floor was fitted on the other sets.

**Amax_S.** Every harness that copies the usual `sdpa_fp8` pattern (`set_output(True)` on all four outputs) silently loses the FROST rows; my own comparison did.
- Without dropout every entry of S is at most 1, so `scale_s = 448` never saturates S.
- E4M3 is floating point, so a larger data-derived scale changes only the underflow threshold, not the relative precision.
- Transformer Engine's `fused_attn_fp8.cu` declares the output, so its FP8 attention stays on the backend until it leaves Amax_S virtual.

## Related issues

Related to #602 (Amax_S dropped from the FROST FP8 kernels), #1415 (FP8 graphs with no supported plan when Amax_S is declared), #1613 (SM100 backend Amax_S below the true maximum at short S_q).

## API and compatibility impact

- **Default plan selection** changes for cc 10.7 per-tensor FP8 forward graphs at d256 / d512.
- **Amax_S** is deprecated in documentation only; behavior is unchanged except for the new one-time log line.
- **No public API change.**

## Testing

- New `test_sdpa_fwd_amax_s.py`: decline reason unchanged, warning logged once, and no warning when Amax_S is virtual or the device is outside the row.
- New placement tests in `test_sdpa_fwd_placement.py`:
  - d256 / d512 lead on cc 10.7 and trail elsewhere;
  - each unmeasured feature trails;
