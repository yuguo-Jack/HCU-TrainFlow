# frost: MXFP8 d=256 backward reads canonical F8_128x4 scale factors natively (drop SF repack)

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/908) · state: closed · merged: False

## Original PR description

## Summary

Follow-up to #904. The SM100 d=256 MXFP8 backward engine (`sdpa_bwd_sm100_mxfp8`) no longer repacks the seven F8_128x4 scale-factor tensors into the kernels' 2-CTA "slot" layout ahead of the two kernels. The eleven repack launches, their workspace and `bprop_sf_repack_mxfp8_sm100.py` are removed; `execute()` launches exactly the dQ kernel and the fused dK/dV kernel (python/cudnn/AGENTS.md Hard Rule 2, no remaining exception).

## What changed

**Kernels** (`bprop_dq_d256_mxfp8_sm100.py`, `bprop_dkdv_d256_mxfp8_sm100.py`, shared helpers in `_bprop_mxfp8_common_sm100.py`):

- Scale factors are TMA-loaded straight from cuDNN's canonical F8_128x4 planes through explicit tensor maps (`make_sf_tensor_map`): dims `[16-byte atom row, 32 rows, 4-group tile, (row tile, plane)]` for the rowwise tensors and `[..., (plane, row tile)]` for the columnwise `descale_*_T` tensors, so their D-tile-major atom order (`((rt*L + l)*rest_k + ct)*512`) is a stride, not a copy. One 512-byte atom column per load lands in slot 0 of the kernels' existing staged smem layouts; the K^T / Q^T / dO^T loads fetch both 128-row D tiles as one box.
- The 2-CTA MMAs (M = 128 across the pair, 64 rows per CTA) read scale factors in the "2x2" TMEM data path: sub-partition `s` reads 32-bit column `s % 2`, so the peer CTA's A-operand rows 64..127 and a B operand's row groups m1 = 2, 3 have to sit in atom positions 0, 1 -- the 16-byte atom row shifted left by 8 bytes. No copy engine can do that shift: TMA faults (illegal instruction) on a bounding-box start coordinate that is not 16-byte aligned (verified on B200 with a standalone probe; a 16-byte-aligned shift plus OOB zero fill works, 8 bytes does not), and `tcgen05.cp` smem descriptors are 16-byte granular. So **each CTA's load warp** builds its own shifted slot atoms in shared memory right after its canonical atoms land (32 lanes x one 8-byte load + one 16-byte store per atom), issues `fence.proxy.async`, and arrives once per iteration on the **leader's** stage-full barrier (a DSMEM arrive from the peer). Those barriers now have arrival count 3 (producer `expect_tx` + one load warp per CTA), so the MMA warp's existing `consumer_wait` also covers the slots -- no new waits on the MMA path, the smem->TMEM (`tcgen05.cp` 2x64) path is untouched.
- dK/dV prefetches its scale factors: new per-stage `sf_free` barriers are released by `tcgen05.commit` (multicast to both CTAs) right after the stage's smem->TMEM copies, so the load warp fetches and builds the next iteration's scale factors before it blocks on the payload stages' empty barriers. The one KQ arrival covers the VDO / KQ_aux slots of the same iteration because the MMA warp always waits KQ first.
- Alternatives measured and rejected (documented in `_bprop_mxfp8_common_sm100.py`): a leader-only design that multicasts the atoms and builds the peer's slots through DSMEM stores + cluster-scope fences was 1.5-2x slower on dK/dV; a dedicated SF helper warp per CTA was no faster than doing the build in the load warp.
- Scale-factor bytes are tracked per CTA on new `sf_landed` tx-barriers (one per load-pipeline stage); the pipelines' full barriers count payload bytes only. This also closes a latent race in the old code: the peer CTA's SFB loads used to signal a barrier nobody waited on before the leader's `cta_group::2` `tcgen05.cp` read the peer's smem.
- Numerics are unchanged (the standalone smoke produces bit-identical dQ/dK/dV to the repack path).

**Adapter** (`api_dsl_mxfp8_sm100.py`): binds the graph SF tensors as flat E8M0 byte planes (any dense stride declaration, no `.contiguous()`), `scratch_workspace_bytes()` is the kernels' own scratch only. Docstrings, `engines.py`, `kernels/__init__.py` and `SUPPORT_MATRIX_TRACKER.md` updated; `test_workspace_accounts_for_repack_buffers` becomes `test_workspace_is_kernel_scratch_only`.

## Layout facts

- Canonical F8_128x4 atom: 512 bytes = 32 rows (`m0 = row % 32`) x 16 bytes (`m1 = row // 32 % 4` at stride 4, `k0 = group % 4` at stride 1). Rowwise (rows = S) planes are plane-major, `atom(l, rt, ct)` at `((l*rest_m + rt)*rest_k + ct)*512`; columnwise (rows = D) tensors put the D tile outside the plane, `((rt*L + l)*rest_k + ct)*512`.
- 2x2 TMEM data path (M = 128 2-CTA MMA): SFA per CTA = its own 64 rows in columns 0, 1 of all four sub-partitions (sub-partition `s` reads column `s % 2`); SFB = rows 0..63 in lanes 0..63 and rows 64..127 in lanes 64..127, again columns 0, 1. The old "slot" layout was exactly the 8-byte-shifted atom copies that make this fall out of the 64x128b `tcgen05.cp` variants; they are now produced in smem instead of in a pre-pass.

## Tests

- `test/python/sdpa/frost/test_sdpa_bwd_mxfp8_sm100.py`: 33 L0 passed, 1 L1 passed (B200, cuDNN 9.26), including `test_ragged_kv_only` and `test_batch_and_heads`.
- Standalone smoke against `mxfp8_ref.compute_ref_backward` (both kernels driven directly with canonical SFs): 11 shapes incl. GQA (hq=4/hk=2), b=2, S_q = 96 / 384 (ragged Q tiles), S_kv = 160, causal, fp16 and bf16 -- all pass, results bit-identical to the repack path.
- `test/python/sdpa/frost/test_sdpa_fwd_mxfp8_sm100.py` (shared analyzer): 98 passed.

## Perf

`benchmark_single_sdpa --head_dim 256 --data_type mxfp8 --sdpa_backend cudnn_oss --fwd_bwd --skip_ref --profile_pass bwd --batch_size 4 --num_q_heads 16 --num_kv_heads 16 --q_seqlen 8192 --kv_seqlen 8192 --attn_mask no_mask --num_iterations 20` on this B200 (SM clock pinned at 847 MHz, so absolute numbers are low; compare relatively):

- develop (#904, repack): 18.399 ms median bwd
- this branch (native SF): 18.634 / 18.630 ms median bwd (two alternating baseline/native runs: baseline 18.399 / 18.397 ms)

Per-kernel (CUDA events, same shape): repack path dQ 7.495 ms / dK/dV 9.275 ms; native dQ 7.357 ms / dK/dV 11.279 ms. dQ is on par; dK/dV pays about 2 ms for the cross-CTA readiness signal (the peer's DSMEM arrive on the leader's stage-full barrier sits on the MMA warp's critical path; the `sf_free` prefetch hides most but not all of it). Removing the eleven repack launches (~1.6 ms at this shape) compensates for most of it: end to end the branch is +1.3% (18.40 -> 18.63 ms) vs. #904 on this benchmark. Noted in the tracker; a follow-up will look at moving the readiness signal off the MMA warp's path (e.g. a per-CTA slot-ready barrier waited by the MMA warp only for its own half, or building the shifted rows on the TMEM side).
