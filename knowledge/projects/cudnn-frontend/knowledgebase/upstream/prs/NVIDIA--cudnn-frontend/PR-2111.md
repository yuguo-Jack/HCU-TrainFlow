## Affected area

FE OSS kernels or CuTeDSL

## Summary

Follow-up to the [P2] on #2105. The SM100 SDPA forward templates have an outer `@lru_cache` on `compile()` (for example `sm100/decode_d256_f16.py` and `sm100/prefill_d256_f16.py`), and their modules are cached by `(path, params)`. cc 10.0 and cc 10.3 load the same module for the same record. So in a process that drives both parts, the second part reaches the first part's compiled object through the outer cache, before the device-aware memo in `compiled_cache.compile_cached` is consulted.

`api_dsl._load_kernel_template` takes the plan's part (`part=`). cc 10.0 and cc 10.7 keep the key every caller has had (`_HOME_KEY_PARTS`). Any other part, cc 10.3 today, folds itself into the loader's `extra_key`. It then gets its own module, so its own `compile()` cache and its own compiled-artifact digest, in either load order. `_load_sm100_kernel_module` passes `part` on the SM100 arms, and `SdpaFwdDslSm100.compile` passes `self._device_cc`.

`test_sm100_line_parts_load_their_own_template_modules` loads cc 10.0 then cc 10.3, and the reverse. It checks that cc 10.0's module is the historical one (`part=None`), that cc 10.3's module and its `compile` are distinct, and that a repeat hits each part's own module.

## Why

The mixed-device reuse that #2105's review found. One device per process avoided it.

## Related issues

Follow-up to #2105.

## API and compatibility impact

None on cc 10.0 and cc 10.7 (same keys, same persisted artifacts). On cc 10.3 the template modules and their compiled artifacts are new entries, compiled once more.

## Testing

B300 (cc 10.3), develop `64ed3dfe` with its own extension, torch 2.14.1+cu130, cuDNN 9.27.0, CuTe DSL 4.8.1, `CUDNN_FRONTEND_ENABLE_FROST_ENGINES=1`, from `test/python`:

| `python -m pytest sdpa/frost/test_sdpa_fwd_dsl_sm100.py` | 1156 passed, 8 skipped |

The second row ran with #2105's gated-block files also in the tree, which this suite does not import. Not run on cc 10.0 or cc 10.7, where the key is unchanged.
