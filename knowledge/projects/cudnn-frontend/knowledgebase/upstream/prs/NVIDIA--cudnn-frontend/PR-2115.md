## Summary

Fixes #2099. Develop has three stale test assertions there: the code they guard changed, and the tests did not. No product code changes.

**`core/graph/test_native_backend_lowering.py`** (`test_native_layernorm_fwd_bwd_lowers_to_backend`, `test_native_rmsnorm_lowers_to_backend`). The FROST norm engines are default candidates on the parts they serve: cc 10.0 and 10.3, with cc 9.0 opt-in. Since #2078 their variant-pack binding accepts UID zero, and they now claim these layernorm and rmsnorm graphs. `_assert_ran_on_backend` then finds `FrostNormFwdEngine` selected. These tests cover the generic structured-op lowering to the backend. A new helper `_bar_frost_norm(g)` bars the `frost_norm_fwd` / `frost_norm_bwd` families by name before `build`, as `benchmark_single_sdpa.py` does for FROST SDPA on its backend leg. FROST norm keeps its own suites under `test/python/norm`.

**`sdpa/graph/test_sdpa_benchmark_single_sdpa.py`** (`test_backward_graphs_carry_the_sliding_window_the_flop_model_counts`). #1983 gave `sdpa_mxfp8_backward` its band (`left_bound`) and set `bwd_sliding_window = args.sliding_window_size`. The tripwire for that step still asserted the old state and asked for exactly that change. It now asserts the new state: the mxfp8 call carries `left_bound`, and the backward FLOP count takes the window.

## Why

These three cases fail on every develop pipeline listed in #2099.

## Related issues

Fixes #2099. The other two CI issues filed with it (#2097, #2098) are not touched here.
