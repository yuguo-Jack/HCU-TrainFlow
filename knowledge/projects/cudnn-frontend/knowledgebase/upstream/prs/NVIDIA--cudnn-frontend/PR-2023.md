## Summary

The SM120 dense templates (`sm120_matmul.py`, `sm120_block_scale_matmul.py`) launch one CTA per output tile on a `(ceil(M / cta_tile_m), ceil(N / cta_tile_n), batch * split_k_slices)` grid. With split-K, the reducer launches `(ceil(M / 4), ceil(N / reducer_tile_n), batch)`. This PR checks both grids against CUDA's 65535 limit on `grid.y` and `grid.z`:

- `_launch_grid_reason(chain, config, n)` in `sm120/compiler.py` computes both grids for a kernel-frame N and names every dimension over the limit.
- `_precheck_plain` and `_precheck_block_scale` call it with the declared N and raise `NotImplementedError`. `check_support` then declines (the backend serves the graph), `jit_from_cudnn_graph` refuses to build, and the planner's candidate probe moves an automatic pick to a wider N tile when one fits.
- The SM120 `CompiledFusedGemm` sets a new `_validate_launch_grid` flag. The shared `lowered()` then checks each call's N right after the split-K shape check, before the workspace check and before any reduction seed is written, and raises `ValueError`. The message starts with `cudnn.frost gemm:`, like the neighbouring per-call errors, and ends with the remedy `the plan was built for a smaller N; rebuild for this shape`, in the style of `check_split_k_shape`. `explain()` raises the same message: `lowered()` and `explain()` both call one shared method, `_check_launch_grid`.
- `_splitk_reduce_tile_n` restates the reducer kernel's `splitk_reduce_tile_n` (three lines), because that module imports CuTe DSL and `check_support` does not load CuTe DSL today. A test pins the two together for S = 2..32 and every reducer vector width.

No kernel template changes. A plan whose declared shape fits the launch grid is unchanged, and so is every call on it that fits the grid.

## Why

Found in an audit of the SM120 Frost kernel templates (finding B26). Every 65535 check was in split-K-only code:
- `_splitk_reject_reason` returns before its `grid.z` check when `split_k_slices == 1`.
- The per-call `check_split_k_shape` runs only for S > 1.
- The planners cap S at `65535 // batch`, which leaves a batch past 65535 at S = 1, the unchecked case.

Nothing checked `grid.y`. Reproduced on an RTX PRO 6000 (SM120) at develop 24a8cd43:

| Case | 24a8cd43 | This PR |
|---|---|---|
| bf16 `[B,32,64] x [B,64,32]`, B = 65536 / 70000 (`grid.z` > 65535), S = 1, FROST opt-in, graph API | `frost_gemm` is offered; at B = 70000 the default `build()` picks it and `execute` raises `CUDADialectError [CUDA_LAUNCH_INVALID_CONFIG] cudaErrorInvalidValue` | FROST declines; at B = 70000 the default build runs on the backend, output exact |
| same at B = 65536 through `jit_from_cudnn_graph` + `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2` | builds; every launch fails as above | `NotImplementedError: ... grid.z = batch=65536 * split_k_slices=1 = 65536` |
| bf16 M = 32, N = 8,388,608, K = 64, automatic plan, graph API | auto pick `32x128` (`grid.y` = 65536); `execute` raises `CUDA_LAUNCH_INVALID_CONFIG` | auto pick `64x192` (`grid.y` = 43691); output exact |
| bf16 M = 32, K = 64, `CONFIG_sm120_128x16x128_16x16x32_cluster1x1_warps8x1` built at N = 1,048,560 | N = 1,048,560 (`grid.y` = 65535) exact; the same plan called at N = 1,048,576 fails the launch | N = 1,048,560 exact; N = 1,048,576 raises `ValueError: cudnn.frost gemm: ... grid.y = ceil(N=1048576 / 16) = 65536 -- the plan was built for a smaller N; rebuild for this shape`, output untouched |
| nvfp4 block-scale, M = 32, K = 256, same 128x16 config, called at N = 1,048,576 | the launch fails with cudaErrorInvalidValue (raised as `CUDADialectError [CUDA_LAUNCH_INVALID_CONFIG]` or `RuntimeError: CUDA Error Code: 1`, see below) | `ValueError` naming `grid.y`, output untouched |
| bf16 M = 32, K = 1024, explicit `_splitK16` (a reducer CTA covers 16 columns when N % 4 == 2) | N = 1,048,558 exact; at N = 1,048,562 the main kernel runs and writes the workspace, then the reducer launch fails (output untouched) | built at N = 1,048,562: `NotImplementedError: ... split-K reducer grid.y = ceil(N=1048562 / 16) = 65536`; a plan built at a smaller N refuses the N = 1,048,562 call with `ValueError` before any launch (output and workspace untouched) |

On 24a8cd43 the failing launch raised one of two exceptions in these runs. When the kernel had been compiled in the same process, it was `CUDADialectError [CUDA_LAUNCH_INVALID_CONFIG] CUDA launch failed: cudaErrorInvalidValue (1)`. When the kernel had been loaded from the kernel cache, it was `RuntimeError: CUDA Error Code: 1`. Two consecutive runs of the RED tests, and of the nvfp4 call, raised one and then the other: the first ran on an empty kernel cache, the second on a warm one. Both are cudaErrorInvalidValue.

Zero-extent calls (M, N or K = 0) are a separate audit finding and are not changed here.

Batch and the slice count are fixed per plan, so the plan-time check covers `grid.z`. N is not fixed: a plan built at a legal N can be called with a larger one, so the per-call check is needed as well. Automatic split-K requires fewer output tiles than SMs, so only an explicit split-K config reaches the reducer case.

Declining is the conservative fix. Numerics and the supported envelope below the limit do not change. Folding batch (and N tiles) into a linear `grid.x` index, as CUTLASS's persistent scheduler does, would lift the limit. It would also change the CLC tile decode and the L2 raster in both kernel templates, so it belongs in a separate change if these shapes matter.

Why the shared `compiler.py` changes: the per-call guards of every dense plan run in the shared `_CompiledFusedGemm._lower` / `explain`. That is the only place where a per-call N check can run before the workspace check and the reduction seeds. python/cudnn AGENTS.md Rule 1 requires validation before reduction outputs are initialized, so that a rejected call leaves the caller's buffers unchanged. Wrapping the launchable in the SM120 module would run after the seeds. The shared change is a class flag that defaults to `False`, plus a small method, `_check_launch_grid`, that calls the family's `_launch_grid_reason` and raises the per-call `ValueError` for `lowered()` and `explain()`. Only the SM120 subclass sets the flag, so the SM100 path is unchanged.

## API and compatibility impact

- Newly declined: SM120 dense and dense block-scale plans whose declared shape needs any of the following:
  - `grid.z = batch * split_k_slices > 65535`
  - `ceil(N / cta_tile_n) > 65535`
  - for split-K, `ceil(N / reducer_tile_n) > 65535`

  FROST `check_support` raises `NotImplementedError` for these, so the backend gets the graph; `jit_from_cudnn_graph` raises `NotImplementedError`. Before this PR these plans built, and a call at the declared shape then failed at a kernel launch with cudaErrorInvalidValue. In the split-K reducer case, the main kernel ran and wrote the workspace before the reducer launch failed. A call with a smaller N that fit the grid did launch on such a plan. For example, on 24a8cd43 the 128x16 plan built at N = 1,048,576 ran N = 4096 exactly. Now such a plan is declined as a whole. An automatic pick moves to a wider N tile instead when one fits (for example `64x192` instead of `32x128` at N = 8,388,608).
- Per call: when a call's N outgrows these limits, the call now raises `ValueError` (`cudnn.frost gemm: ... rebuild for this shape`) before any write (no reduction seed, workspace untouched). Before, a kernel launch failed inside the launcher; in the reducer case, the main kernel had already written the workspace.
- No numerics change and no public API change. The support-probe path gets no new imports: `check_support` still does not import CuTe DSL.
- MoE templates are unaffected: they launch a 1-D persistent grid.
- SM100 has the same gap. It is intentionally left for a follow-up, since the repo convention is that fixes land in both trees:
  - `python/cudnn/gemm/frost/sm100/compiler.py:2811-2833`: `_splitk_reject_reason` returns at `:2813` for `split_k_slices == 1`, before the `grid.z` check at `:2832`.
  - The launch grids are at `python/cudnn/gemm/frost/sm100/kernel_templates/sm100_matmul.py:1333` and `sm100_block_scale_matmul.py:1717`.

  The follow-up can set `_validate_launch_grid` on the SM100 `CompiledFusedGemm` and add an SM100 `_launch_grid_reason`; its grids multiply the tile counts by the cluster shape.
