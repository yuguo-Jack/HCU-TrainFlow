## Affected area

## Summary

`_emit_round` now narrows int8 / uint8 values the way cuDNN's native engines store these types: round half to even, saturate to the type's range (±inf included), and store NaN as 0. These are the semantics of `cvt.rni.sat.s8.f32` / `cvt.rni.sat.u8.f32`.

- **fp32 source:** `max(x, 0) + min(x, 0)` (x itself, or 0 for NaN), then `cute.math.roundeven`, then a clamp to [-128, 127] / [0, 255]. The existing `.to()` follows and is now exact.
- **INT32 source** (an op that computes in INT32): a clamp to the range, then the existing `.to()` (`trunci`).

Every other dtype keeps the single `.to()`. The report also names `_store_cast_expr`, the store-time cast. It only re-casts the value `_emit_round` already produced (int8 to int8, uint8 to uint8 plus a bitcast), so it is unchanged.

There are two new tests with six cases in total. Both compare the stored bytes with `gemm_test_utils.int8_store_ref` (round half to even, saturate, NaN -> 0):
- `test_matmul.py::test_sm120_int8_output_rounds_to_nearest_even_and_saturates` (four cases): a dense GEMM -> `mul(scale)` -> INT8 / UINT8, in FLOAT and in INT32 compute, with N- and M-major outputs. The FLOAT cases store ties, fractions, both range edges, values past int16, ±inf and NaN. The INT32 cases store 3 x int8 products (|x| <= 381) that pass both the int8 and the uint8 range edges; they have no ties, fractions or non-finite values.
- `test_moe_grouped_matmul_fwd.py::test_moe_int8_output_rounds_to_nearest_even_and_saturates_sm120` (two cases): a bf16 MoE GEMM stored straight to INT8 (normal template) and UINT8 (swap-AB template, SM120 only), with the values of the FLOAT cases.

## Why

The epilogue narrowed with a bare `.to(cutlass.Int8)` / `.to(cutlass.Uint8)`. The CuTe DSL lowers fp32 to int8 as `arith.fptosi`, which compiles to `cvt.rzi.s16.f32` plus a `prmt` that keeps the low byte on sm_120a. It lowers INT32 to int8 as `arith.trunci`. So values were rounded toward zero and wrapped modulo 256.

Minimal reproducer (the FLOAT cases of the new dense test): a dense bf16 GEMM with M = N = K = 64, built so that row m is exactly x_m (one nonzero K term), then `mul` by an fp32 scalar scale of 1.0, stored as INT8 or UINT8 with `CONFIG_sm120_128x128x128_16x16x32_cluster1x1_warps4x2`.

The defect is not specific to one template, because every SM120 template rounds through this helper (via `_emit_pointwise_dag`). On 24a8cd43 I also reproduced it with:
- the dense template with an M-major output;
- both MoE templates, normal and swap-AB;
- int8 x int8 with an s32 accumulator;
- an INT32-compute `mul` chain (3 x int8: 129 -> -127 and 300 -> 44 as INT8, -300 -> 212 as UINT8);
- the split-K reducer epilogue;
- the public `frost_gemm` engine through `graph.execute`.

Why round half to even with saturation:
- On the same GPU, cuDNN's native engines store this dense graph exactly that way for INT8 and UINT8. That holds for eng1, eng7 and eng10 (all 17 plans) on every element, including ±inf (the range ends) and NaN (0). The backend and FROST serve one graph contract (python/cudnn/AGENTS.md Rule 9), so a FROST plan computed a different function for the same graph.
- The native engines saturate an INT32-compute chain the same way. For int8 x int8 -> `mul` by an INT32 scale in INT32 compute -> INT8 / UINT8 (M = N = K = 64, products of 3 x int8), all 9 plans (eng10 and eng7) store every element as the clamped product, which is what the new clamp stores: 300 -> 127, -300 -> -128 and 129 -> 127 as INT8; -3 -> 0 and 381 -> 255 as UINT8.
- CUTLASS's int8 epilogue converter (`NumericConverter<int8_t, float, round_to_nearest>`, `cvt.rni.sat.s8.f32`) does the same. FROST already narrows to 8-bit floats with rounding and saturation (`cvt.rn.satfinite`).

Why not decline int8 / uint8 outputs instead: the audit suggested declining them only until a rounding, saturating conversion exists. With the conversion in place, nothing admitted today becomes unsupported, and exact in-range integers are stored as before.

The conversion uses only DSL vector operations the shared emitters already use (`cute.math.max` / `min`, `cutlass.full_like`, `.to()`), plus `cute.math.roundeven`. So it works on every template's epilogue value type, without inline PTX and without new imports in the templates.

Why the change is outside `python/cudnn/gemm/frost/sm120/`: at 24a8cd43, `_emit_round` exists only in the shared `python/cudnn/gemm/frost/epilogue_codegen.py`, which #1993 moved it into from `sm120/epilogue_codegen.py` and `sm100/epilogue_codegen.py`. All six SM120 templates reach it through `_emit_pointwise_dag` (rounding of each GEMM output and of each op). `sm120/` has no copy of it to change.

Found in an audit of the SM120 FROST kernel templates (finding B13).

## API and compatibility impact

- **Numerics:** int8 / uint8 values now round half to even and saturate, with ±inf stored as the range ends and NaN as 0. This covers stored outputs and int8 / uint8 intermediate tensors, whether a GEMM or an op produces them. An INT32-compute value is clamped to the range before it is narrowed. Exact in-range integers are unchanged, so the existing tests that store int8 / uint8 (the values 1, 2, 200 and small integer sums) are unaffected. No graph is newly declined or admitted.
- **SM100:** the sm100 tree has no copy of this code. `sm100/epilogue_codegen.py` reaches the same shared `_emit_round` through `_emit_pointwise_dag` (epilogues) and `generate_mainloop` (mainloop operand transforms, such as an int8 `abs` / `relu` / `neg` operand). So SM100 int8 / uint8 outputs and int8 mainloop operands change the same way. There is no separate SM100 copy that needs a follow-up, and nothing under `sm100/` is edited.
  - I could not run SM100 hardware tests here.
  - The SM100 tests that store int8 / uint8 use exact in-range integers, where the old and new conversions agree: `test_epilogue_output_dtypes`, `test_epilogue_uint8_output_preserves_values_above_int8_positive_range`, `test_mixed_dtype_rank3_broadcast_patterns`, `test_e2e_mainloop_int8` and `test_mainloop_int8_identity_preserves_signed_arithmetic`.
  - I compiled the emitted lines in a standalone probe kernel (compile only) for sm_100a and for sm_120a; the two PTX files differ only in the `.version` / `.target` header and comments.
  - I also compiled the real SM100 templates for sm_100a on this host (compile only, nothing launched; the sm100 tree selected with `CUDNN_FRONTEND_GEMM_ARCH_FAMILY=sm100` and the arch query patched to 100): the mainloop with an int8 `abs` operand (FLOAT compute) and an int8 `neg` operand (INT32 compute), and the epilogue with an STG int8 output and a TMA-store uint8 output. All four render the new lines and `cute.compile` with `--gpu-arch sm_100a`.
- **Performance:** each int8 / uint8 element now goes through the NaN map, a `cvt.rni.f32.f32` and the clamp before the convert-and-pack. That is roughly ten instructions per element in the epilogue instead of two. Not measured.
- **CuTe DSL version:** `cute.math.roundeven` exists in each installed copy of nvidia-cutlass-dsl I checked (4.6.2, 4.7.0, 4.7.1, 4.8.0 and 4.8.1). 4.8 wraps it together with `floor`, which the shared emitters already use. No new version gate is needed (Rule 7).
- **Pre-rendered kernels:** I know of none that store int8 / uint8. FlashInfer's SM120 FROST artifacts store bf16 and fp8.
