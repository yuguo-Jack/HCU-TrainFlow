# test(gated block): the QSA suites gate the gated O by the repo's bf16 output bound; the F8 measurement note

[Upstream PR](https://github.com/NVIDIA/cudnn-frontend/pull/1995) · state: closed · merged: True

## Original PR description

## What

The block-sparse QSA suites of the gated attention block -- `test_block_qsa_end_to_end.py` and `test_block_qsa_decode.py` -- held the **gated O** against the fp32 oracle at an absolute `atol 2e-2`. That number is the SDPA stage test's bar on the **LSE** (`test_sdpa_stage_sm107.py`; its O checks are `cos > 0.999`), transplanted onto bf16 O values of magnitude up to ~3, where one bf16 ulp is 0.015625 (78 % of the bar) and any single rounding flip at `|O| >= 4` (ulp 0.03125) would exceed it for every implementation alike.

This PR makes the gate the repo's **existing bf16 / f16 output convention** -- the one the block backward suite calibrated once on Rubin and never widened (`test_block_backward.py`): per element

```
|d| <= 2^-7 * max|ref| + 2^-6 * |ref|      and      cos >= 0.999        (bf16; f16: 2^-10 / 2^-9)
```

* New shared helper `test/python/gated_attention_block/cutedsl/gated_block_bounds.py` (`assert_output_close`, `output_bound_stats`, the three constants). `test_block_backward.py` now imports its constants from it, so the numbers have ONE definition.
* The two QSA suites use `assert_output_close` on every gated-O comparison against the oracle (the dense `_check`, the packed per-sequence `_check_thd`, the decode `_Case.check`, the MTP pos0 reading, the adversarial cell's rows below the identity bound) and on the kernel-vs-kernel comparisons (fused vs unfused-then-gated, lean vs tcgen05) that used the same transplanted number. `max|d|` stays printed beside the worst cell's fraction of the bound in every message, so a calibration or a regression is a number, never a silent widening.
* The **LSE keeps its 2e-2 bar**; the plant margins of the adversarial cell are untouched; **the oracle is unchanged**.
* `qkvg_from_hf`'s docstring gains the measured consequence of its documented bf16 `(1 + w)` rounding; the docs sentence on the lean / tcgen05 agreement names the bound.

## Why (the measurement behind it)

On the Qwen3.8-Flash-Next geometry (bf16, 24 / 2 heads, `d_head` 256, T 2048, B 1, the identity block list), the three FROST sparse arms read **max|d| = 0.0215 on exactly one gated-O element in 12,582,912** against the fp32 oracle -- row 5 (six visible keys), one head, one near-cancelling dim (two dominant keys with large opposite-sign V) -- and were refused by the 2e-2 bar.

Three independent re-derivations from the kernel's dumped operands reproduce the value bitwise on all 256 dims of that row: the mechanism is the **documented** bf16 rounding of the QK-RMSNorm weight `(1 + w)` in `qkvg_from_hf` (fp32 `(1 + w)` rounded once into the activation dtype; `norm_weight_offset` 0), which flips ~30 % of the normed `q` and ~27 % of the `k` elements by one bf16 ulp against the fp32-`(1 + w)` reference (an HF-faithful chain shows ~7 % from its own rope-dim rounding) and shifts that row's softmax weights by up to 1.5 %. Under the block's own operand convention the sparse core sits at the bf16-P floor (one ulp); the element is a property of the operand convention, not of any kernel. Rows attending >= 1024 keys stay within ~2e-3, which is why the decode suites (every row >= 2048 keys; ~1,460 gate records, worst 0.0020) never showed it.

Under the output bound the same tensors read **0.877 of the bound** (cos 0.99999; 0 elements above it) for the FROST sparse arms, 0.717 for the dense FROST route and 0.331 for the vLLM reference arm -- recorded, not hidden. The fp32 in-kernel offset form (`norm_weight_offset = 1.0`, HF-faithful numerics) stays a separate, later lever.

**Tolerances:** the oracle is unchanged; the bound is the repo's existing output convention (calibrated once on Rubin cc 10.7 for the block backward: accept cells at 0.40-0.66 of it). Nothing is widened for the LSE or for `out`.

## RED -> GREEN

On the real dumped tensors of that cell (CPU): the old assertion refuses the FROST sparse arms (`gated O off the oracle by 0.021484375 (budget 0.02)`); `assert_output_close` passes them at 0.8767 of the bound (`n_above_bound 0`, `cos 0.999989`); the dense route (0.7173) and the vLLM arm (0.3307) pass under both. The helper refuses a planted one-element excursion (44x the bound) and accepts a pure bf16 rounding of the reference (0.14).

## Tests

Host tier (A100 host; the Rubin cells skip): `test_block_qsa_decode.py` 30 passed / 90 skipped, `test_block_qsa_end_to_end.py` 3 passed / 99 skipped, `test_block_backward.py` 40 passed / 70 skipped (combined 73 / 259 / 0 failed).

Rubin cc 10.7 (shared development GPU, functional only): `test_block_qsa_decode.py` **120 passed / 0 failed / 0 skipped** (349 s) and `test_block_qsa_end_to_end.py` **102 passed / 0 failed / 0 skipped** (344 s), the whole L0 modules, one process each on a shared cc 10.7 GPU. Across the 359 gated-O comparisons the new helper printed, the worst cell sits at **0.544 of the bound** (decode) / **0.541** (end-to-end), no element above it, the gated-O cosine >= 0.999990. The backward module imports the shared constants and collects unchanged (its host cells pass; its Rubin gradient cells are not re-run here -- the constants are the same numbers).

`black -l 160` + `pre-commit` (black, SPDX) pass on the six files.

## Sibling suites (not changed here)

`test_block_qsa_fp8_kv.py` and `test_block_serving_extend.py` carry their own `2e-2` on the gated O; their cells attend long histories and are not exposed. Moving them to the shared helper is a follow-up.
