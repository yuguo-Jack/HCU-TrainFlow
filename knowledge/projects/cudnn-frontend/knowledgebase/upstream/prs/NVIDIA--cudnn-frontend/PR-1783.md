## Affected area

FE OSS kernels or CuTeDSL

## Summary

- Admit cc 10.3 on the d128 backward (`sdpa_bwd_sm100_d128`) paths that were gated to exact cc 10.0: the dense MHA accumulation chain, packed THD MHA and grouped GQA/MQA (dense and THD). One `ACCUMULATION_CCS = ((10, 0), (10, 3))` tuple in `d128_contract.py` is used by plan-time implementation selection, the engine's declaration check and both prepared entries.
- Compile the THD and grouped prepared hosts for the build device's arch. They passed a fixed `100` (`--gpu-arch sm_100a`) while the dense hosts already pass `cc[0] * 10 + cc[1]`; on SM103 the fixed target left no positional tvm-ffi entry, and every THD / grouped case failed with "requires a positional tvm-ffi entry".
- Eligibility tests: cc 10.3 is now admitted; the decline cases use an in-envelope cc that is neither 10.0 nor 10.3. The API page and `SUPPORT_MATRIX_TRACKER.md` (Rule S2, same commit) state cc 10.0 or 10.3 and record the B300 run below.

## Why

On B300 (cc 10.3) dense d128 MHA backward fell back to the one-launch recompute implementation, and THD and grouped d128 declarations were declined, although the same CuTeDSL kernels build for `sm_103a` and pass the existing suites unchanged. The tracker said "the new chain is not selected on SM103" and "SM103 d128 remains unsupported for THD". This also fills the d128 backward cells of the SM103 support-matrix issue.

## Related issues

Related to #380.

## API and compatibility impact

No API change. On cc 10.3 the opt-in d128 backward engine now selects the accumulation chain for dense MHA that meets its existing conditions (it previously used the recompute implementation there) and accepts THD and grouped declarations it previously declined. cc 10.0 behaviour and every other cc are unchanged. Capability only: no B300 performance claim; the row stays opt-in.
