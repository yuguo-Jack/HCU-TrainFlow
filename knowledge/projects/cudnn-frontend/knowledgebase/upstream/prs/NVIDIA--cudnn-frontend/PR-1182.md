## Summary

DSA plan APIs now use caller-owned outputs and workspace instead of retaining device buffers or allocating scratch during execution. This makes memory ownership explicit for CUDA graph capture and concurrent calls. The convenience wrappers continue to allocate omitted buffers and normalize supported input/output layouts on the launch stream.

This PR is now independent of #1181. It includes only DSA changes plus the required `WorkspaceCarver`, stream/lifetime helpers, and a test detector scoped to DSA. The grouped-GEMM, SDPA, linear-attention migrations and shared scratch cache from #1181 are excluded. Current develop fixes, including Top-K tie-breaking, are preserved.

Thanks to @icavan for confirming the plan/wrapper contract in [the API discussion](https://github.com/NVIDIA/cudnn-frontend/pull/1182#issuecomment-6076143777).

## API and compatibility

- Backward plans require caller workspace when `scratch_workspace_bytes()` is nonzero. `SparseAttentionBackward.execute` requires `dq`, `dkv`, and keyword-only `d_sink`.
- `IndexerTopK.execute` retains `current_stream` in its original positional slot; the new output arguments are keyword-only. Callers supply `out_indices`, optional `out_values`, and workspace.
- Score-recompute plans require outputs/denominators; THD plan construction also takes maximum sequence lengths. The SM90 dense THD convenience wrappers retain their per-batch adapter.
- `IndexerForward.execute` binds a suitably padded output. The private `indexer_forward._interface.indexer_fwd` convenience entry point retains omitted-output allocation, contiguous results, and staging/copy-back for logical-shape outputs.
- Convenience-wrapper parameter order is preserved; backward wrappers add optional workspace reuse. Shared caller buffers must not be used by overlapping executions.
- Torch stream interop rejects the special `CUstream(2)` per-thread sentinel instead of incorrectly mapping it to the legacy default stream. Use a concrete `torch.cuda.Stream` or its raw handle. Staging helpers retain source/destination storage on both explicit and implicit current launch streams.

## Remaining limitations

Some DSA APIs still compile lazily on first execute, so warmup is required before capture. Four existing SM90 score-recompute operand-layout copies remain covered by explicit expected failures; this PR does not claim that every DSA path is allocation-free. Backward zero-initialization remains asynchronous memset work; kernel fusion is deferred.

- zkyue · comment · 2026-09-22T08:34:23Z · [source](https://github.com/NVIDIA/cudnn-frontend/pull/1182#issuecomment-5773514273)

Separately from the v2 entry-point question, I found two public-wrapper compatibility changes at `137e2d3` that appear inconsistent with the stated "wrappers unchanged" scope.

**1. `sparse_attention_backward_wrapper`: previously supported strided inputs can now be rejected.**

`SparseAttentionBackward.check_support()` now declines non-contiguous inputs, and the SM100 interface removes its `.contiguous()` normalization. The public wrapper constructs the plan from the original inputs and calls `check_support()` without normalizing them first, so the stricter plan contract also reaches wrapper callers. For example, non-contiguous LSE or `dout` metadata accepted by the previous H64/D512 support gate is now rejected on both SM90 and SM100. The old non-contiguous-aux-input success test is also replaced by a rejection test, and the SM90 qh32 test drops its head-major input views.

Could the input normalization move to the public wrapper, on the resolved launch stream, while the plan remains strict and allocation-free? Caller-provided gradient outputs should retain their identity rather than being silently replaced.

**2. `indexer_forward_wrapper`: SM100 dense output layout / `out=` behavior changes when `S_k % 4 != 0`.**

Previously, `_return_output` made a newly allocated logical result contiguous, or copied back into the caller's `out`. The wrapper now returns a slice of the padded allocation and requires a padded-stride `out` even at the public entry point. For logical shape `(2, 3, 5)`, ordinary contiguous strides `(15, 5, 1)` are rejected; padded strides `(24, 8, 1)` are accepted. Thus both callers supplying ordinary contiguous output buffers and callers relying on the default result's contiguity can be affected.

Could staging/copy-back and the previous default-result layout remain wrapper responsibilities, leaving the no-copy padded-layout contract at the plan/interface layer?

Suggested regression coverage: public-wrapper success cases for strided backward inputs (cold and warm cache), ragged-K forward calls with and without a supplied contiguous `out`, output identity, and non-default streams. Replacing old success cases with expected errors does not establish wrapper compatibility.

These findings are from source comparison and execution of the validation helpers with tensor-metadata stand-ins; I have not run a new GPU numerical or performance regression for this PR.
