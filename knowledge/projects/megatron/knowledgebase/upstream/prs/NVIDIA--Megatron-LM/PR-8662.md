# Fix default MoE auxiliary normalization and add SFT target masking

# What does this PR do?

Correct MoE auxiliary normalization by default under `--calculate-per-token-loss`, and add `--moe-aux-loss-masking` for regularizing only main-loss target positions in GPT/Hybrid text training.

The denominator mismatch was identified internally by @aamjad-nvidia. Maintainer feedback is that the existing per-token behavior is incorrect and should be fixed directly, rather than protected behind an opt-in flag.

## Default normalization

The router seeds a summed input-token auxiliary gradient, but the training finalizer divides all gradients by the global **scored-target** count `T`. With `N` real input tokens, prompt masking therefore changes the effective auxiliary coefficient by `N/T`.

For example, two DP replicas each process 200 real input tokens and score 60 and 140 targets. If their auxiliary mean gradients are `g0` and `g1`, the desired input-token mean is `(g0 + g1)/2`; the existing per-token path gives `g0 + g1`.

The standard GPT/Hybrid training loops now compute an optimizer-step-wide `max(T,1)/max(N,1)` correction automatically, using the existing `moe_grad_scale_func` hook. This cancels the shared target denominator for auxiliary gradients while retaining the main-loss normalization. AMP scaling is composed with the correction. An explicitly supplied `moe_grad_scale_func` remains a full override, responsible for its own normalization.

Only the logical output stage buffers one step of CPU batch references. Shallow batch copies prevent frontend CUDA assignments from retaining GPU inputs in those buffered records. Counts are communicated across explicit TP/DP/PP groups before CP slicing, avoiding duplicated CP counts. Other physical/virtual stage iterators retain their consumption order. The device ratio buffer has a stable address for graph replay. SFT router padding excludes PAD tokens while retaining prompts; ambiguous PAD/EOD aliases are rejected.

## Optional target masking

`--moe-aux-loss-masking` (Core: `TransformerConfig.moe_aux_loss_masking`) applies the existing binary main loss mask to load-balancing and router z-loss statistics. The mask follows prediction positions, without another shift. It is passed independently of the padding mask: token routing, expert computation, expert-bias updates and logits retain their existing behavior.

- With per-token loss, auxiliary gradients use the scored-token denominator across the optimizer step.
- Without per-token loss, preserve equal microbatch/rank weighting. A fully masked microbatch contributes zero and remains in the microbatch divisor.
- Sequence auxiliary loss omits empty physical sequence columns; per-token mode weights nonempty sequence means by their selected-token counts, while legacy mode averages those means equally. This does not introduce conversation-aware sequence statistics for packed data.
- Global auxiliary statistics track cumulative expert **and token** counts, so uneven/empty microbatches do not dilute the running distribution. Their global backward scale accounts for DP averaging.
- Z loss uses a token-weighted TP/CP mean with uneven or empty shards. Cumulative token/expert counts stay integer through BF16 model conversion.

Ordinary PP, interleaved/virtual PP, TP/SP, fixed CP, EP and full activation recomputation are exercised. Recomputed/retained forwards keep their own masks; there is no mutable global target-mask state.

## Scope and remaining work

Input-token correction rejects custom frontends without count metadata/an explicit hook, MTP, sequence-packing schedulers and GTP weight rematerialization. These require token counts from the actual runtime token plans, potentially per router/depth.

The new target-mask option rejects CUDA graphs, overlapped MoE schedule plans, MTP, sequence-packing schedulers, training MLP chunking and hybrid shortcut/mHC wrappers until those paths carry masks with defined reduction semantics. The default ratio has an isolated CUDA-graph replay test; full-model graph-capture coverage is still outstanding.

Dynamic CP is currently rejected through its sequence-packing scheduler: token ownership/counts still need integration, and upstream HybridModel itself currently rejects dynamic CP. Fixed-CP packed SFT is a separate supported frontend path. Existing physical sequence grouping limitations for packed/SP/CP `seq_aux_loss` are also not resolved here. Auxiliary diagnostic logging retains its existing accumulation policy.

See `docs/moe-input-token-normalization.md` for the derivation, API contract and test commands.
