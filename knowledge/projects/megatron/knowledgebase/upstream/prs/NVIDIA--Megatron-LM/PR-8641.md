# Fail evicted requests that no longer fit one prefill step

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8641) · state: open · merged: False

## Original PR description

## What does this PR do?

Without chunked prefill, the dynamic engine must prefill a request's whole
prompt in one step, so `_add_request` already rejects any prompt longer than
`max_tokens` with `TokenOverflowError`. Eviction checkpoints a request by
appending its generated tokens to its prompt, then requeues it at the head of
the waiting queue. If that checkpointed prompt exceeds `max_tokens`, no step
can ever admit it. Because non-chunked scheduling stops at the queue head,
every request behind it waits forever, and `generate()` never returns.

This PR applies `_add_request`'s rule at eviction. An evicted request whose
checkpoint exceeds `max_tokens` while chunked prefill is off fails immediately
with `TokenOverflowError`, and its reply carries the tokens generated so far.
Requests that still fit, and all requests when chunked prefill is enabled, are
requeued as before. This matches what RECOMPUTE resume already does for the
same oversized checkpoint.

## Example failure scenario(s)

**Scenario (evicted request blocks the queue)**
- The engine has a 16-token step budget, six 8-token KV blocks, and no
  paused-block budget.
- Requests A and B each have a 15-token prompt and may generate 12 tokens,
  and short request C waits behind them.
- A and B outgrow the six blocks, so A is evicted once the pool is full, and
  its checkpointed prompt grows past 16 tokens.
- A is requeued at the head of the queue, but its prompt can never fit the
  16-token budget, so C is never admitted.
- B finishes, and then every later step makes no progress, so `generate()`
  hangs with A and C unfinished.

## How was this bug discovered?

A stateful search drove the real engine through random sequences of
submissions, steps, suspends, resumes and drains. A deterministic synthetic
model made every expected output known. The search checks after every step
that some unfinished request makes progress. Without chunked prefill, it
found engine steps that made no progress at all: an evicted request sat at
the head of the queue while its checkpointed prompt exceeded `max_tokens`. A
two-request reproducer of the stall fails the same way on unmodified `main`.

## Scope

- Production: `megatron/core/inference/engines/dynamic_engine.py`, the
  eviction branch of `post_process_requests` only (+13/−1).
- Tests: `tests/unit_tests/inference/engines/test_dynamic_engine.py`
  (+176/−1):
  - `test_post_process_eviction_fails_checkpoint_beyond_max_tokens`, with
    chunked prefill off and on, using a bare engine.
  - `test_eviction_beyond_max_tokens_fails_without_blocking_queue`, the
    scenario above, end to end with a zero-logit model forward. Paged attention
    kernels need 256-token blocks, while the scenario needs 8-token blocks.
  - Two fixture lines in the existing eviction-requeue test.
- No functional-test, config, or API change. RECOMPUTE resume behavior is
  unchanged.
- Not addressed here: replaying an oversized checkpoint in chunks so that the
  request completes. GDN models cannot use chunked prefill, so fail-fast is
  the behavior that applies to every model.
