# Stage request payloads off the dynamic engine loop

# What does this PR do?

Runs `RequestPayloadStager.stage()` off the dynamic engine loop, so a slow payload write no longer pauses decoding for every active request.

Addresses [NVIDIA-NeMo/RL#4663](https://github.com/NVIDIA-NeMo/RL/issues/4663) (Megatron token capture: the TQ media write blocks the engine step).

On `main`, `_send_requests_to_coordinator` calls `payload_stager.stage()` inline for each completed request before sending replies, from the bookkeeping pass of every engine step. When the stager's write is a blocking network round trip, every finished request stalls the engine loop for the duration of its write. NeMo-RL token capture is one such stager: it writes each completed request's token delta (and, with media capture, its pixels) to a TransferQueue store.

Now each stageable completed request gets its own asyncio task:

- `_stage_and_reply` builds the `OffloadedRequestPayload` on the loop thread, runs `stage()` via `asyncio.to_thread`, then sends that request's reply from the loop thread (the ZMQ socket stays single-threaded).
- Each reply still waits for its own write, so `payload_stage_metadata` keeps describing a completed write (stage-before-ack is unchanged). Only the engine stops waiting. This matches what the NeMo-RL vLLM worker already does with the same write.
- Failed and unstaged replies are sent immediately, as before. A stager exception sends the reply unstaged instead of failing the loop.
- Tasks are held in `_staging_tasks`, because the event loop keeps only [weak references to tasks](https://docs.python.org/3/library/asyncio-task.html#asyncio.create_task). `shutdown()` drains them before closing the socket and logs how many it waited for.
- The periodic step log reports the staging backlog (`payload staging: in-flight N, peak M`), so a write path that cannot keep up is visible.
- The `RequestPayloadStager` protocol is unchanged, and stagers need no changes.

This PR removes the engine-side share (~1.3 s/step). The rest is on the NeMo-RL consumer side (reassembler queueing, media transfer through the store). That part is shared with the vLLM backend (same pipeline, [vLLM capture-on run](https://wandb.ai/adlr/mllm-rl-dev/runs/pjrbikqm)) and is tracked in NeMo-RL.

**Default async layout** (three generation replicas, one step of lookahead): no measurable overhead even on `main`, because generation has spare capacity and hides the write: 35.6 s vs. 36.2 s/step ([on](https://wandb.ai/adlr/mllm-rl-dev/runs/n63nmvq0), [off](https://wandb.ai/adlr/mllm-rl-dev/runs/pszdknot), [overlay](https://wandb.ai/adlr/mllm-rl-dev?nw=vd6ela6gjmk)).

- tdene · comment · 2026-10-13T12:32:20Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8169#discussion_r4258646081)

File: `megatron/core/inference/engines/dynamic_engine.py` · line None

This code sits outside the `try/except`.

If there is any error raised here, it vanishes into the void. The task this is running in does get awaited with `return_exceptions=True` in `_drain_staging_tasks`, but the done callback on L1720 removes the task from `self._staging_tasks` before it can be awaited. The exception never gets raised, so for the client, a request that fails here is an infinite hang. If it happens during shutdown, there is a `return_exceptions=True`, but the exception is still dropped afterwards.

I think this can be reasonably expected to fail sometimes. I've reviewed 2 other PRs this week that have had bugs in the serialization logic, so it's a hotspot of sorts. And also, `response_metadata` is validated only at pack time, so any bug in Gym / NeMo RL can cause a silent degradation here.

So this needs a fix. Here are some options I see:

The easiest way to handle this is to decorate `_stage_and_reply` with `trace_async_exceptions`, to make the error loud, but that will cause the entire process to fail which is not ideal. Better than a silent hang still.

A good fix is to wrap the serialization and send in a `try/except` as well, and then publish any failure from this `_stage_and_reply` the same way as `_fail_submission` does, by replying to the caller with an explicit failure.

The best fix, I think, is to properly reap the exception. Instead of having a done callback that discards the task from the task list, await the task list inside the engine loop with something like:
```
if self._staging_tasks:
    done, _ = await asyncio.wait(self._staging_tasks, timeout=0)
    for task in done:
        self._staging_tasks.discard(task)
        exc = None if task.cancelled() else task.exception()
        if exc is not None:
            self._send_failed_reply(task.request, exc)
```
