# Add opt-in BF16 CPU staging during DDP initialization

# What does this PR do?

Add opt-in CPU staging for plain BF16 parameters during distributed-optimizer DDP initialization, reducing the overlap between old parameter storage and new contiguous GPU buffers.

## Issue tracking

Linked issue: Fixes #8832

## Details

`DistributedDataParallelConfig.ddp_cpu_staging` defaults to `False`. When enabled together with `use_distributed_optimizer`, plain BF16 CUDA parameters move synchronously to CPU after buffer layout/compatibility checks and before contiguous buffers are allocated. Existing remapping restores their values into GPU buffer views and preserves `Parameter` identity, including tied references.

FP32, FP16, TE quantized and grouped storage use the existing initialization path. The new option is a Core config API; this PR does not add a training CLI argument. The documented tradeoff is temporary host memory and extra synchronous transfers during initialization.

### Measured memory tradeoff

A bounded 2-rank H200 experiment uses 1 GiB BF16 parameters and FP32 main gradients per rank. Both ranks give:

| Measurement | Existing initialization | CPU staging |
| --- | ---: | ---: |
| Peak allocated CUDA memory | 4 GiB | 3 GiB |
| Final allocated CUDA memory | 3 GiB | 3 GiB |
| Additional sampled host RSS | about 1 MiB | about 1 GiB |
| Synchronized constructor duration, one sample | about 5.3 ms | about 738 ms |

All initialized parameter values are exactly preserved. RSS was sampled every 2 ms. These numbers describe an allocation tradeoff on a small model, not training throughput or a full-model performance claim.

## Validation

Python 3.12, PyTorch 2.14.1+cu132, Transformer Engine 2.20.2+6ea2a74, H200:

```bash
# New targeted coverage: 9 passed per rank on 2 GPUs.
CUDA_VISIBLE_DEVICES=0,1 python -m torch.distributed.run \
  --master-addr=127.0.0.1 --master-port=29801 --nproc-per-node=2 \
  -m pytest -q tests/unit_tests/distributed/test_ddp_cpu_staging.py

# Wider coverage: 74 passed per rank on 8 GPUs.
python -m torch.distributed.run \
  --master-addr=127.0.0.1 --master-port=29802 --nproc-per-node=8 \
  -m pytest -q tests/unit_tests/distributed/test_ddp_cpu_staging.py \
  tests/unit_tests/distributed/test_param_and_grad_buffer.py \
  -k "DDPCPUStaging or bucket_sizes or NVFP4IndexMaps"
```

- Two actual distributed Adam updates: initialized values, gradient buffers and updated parameters match baseline bit-exactly for BF16/FP32 main gradients and overlap on/off.
- Stable `Parameter` identity, tied weights, multiple buckets and a no-op without distributed optimizer.
- Real TE FP8 and grouped BF16 parameters retain values and specialized storage behavior. NVFP4 index-map regressions pass; direct NVFP4 GPU-storage coverage requires a compatible accelerator and was not run on H200.
- Disabling staging in the production runtime makes the peak-memory regression fail as expected on both ranks.
- `tools/autoformat.sh` black/isort/pylint/ruff gates passed. Mypy remains advisory in that script and reports existing typing/import-stub errors in the isolated lint environment; a clean type-check result is not claimed.

No full-model, 32-node, or checkpoint-resume run was performed on this upstream revision.
