# What does this PR do?
Preserve the FP32 token-scaling factor when multiplying FP16/BF16 gradient buffers.

A zero-dimensional CUDA tensor does not promote the buffer dtype. The reciprocal token count can therefore lose precision in BF16 or round to zero in FP16 before multiplication. Use a one-element view of the factor for the flat gradient buffer so multiplication preserves FP32 precision and only the stored result is rounded. Keep the original scalar tensor for separate FP32 gradients, which may themselves be scalars. The factor remains dynamic during CUDA graph replay. The scaling API requires `torch.Tensor`, matching the training caller.

Validation on 4× GB300 (Slurm 1481522, PyTorch 2.13.0a0, TE 2.20.dev, NCCL 2.30.7):

- 37 targeted tests passed on every rank: FP16/BF16/FP32, eager and graph replay, changing factors, CPU-scalar/CUDA-vector tensor inputs, and separate FP32 gradients.
- The original validation (Slurm 1480683) reproduced 14 numerical regression failures with the production file restored to unmodified main.
- Repository autoformat and kernel-determinism coverage gate passed. The exact scaling regression is registered with the existing gradient-buffer entry.
