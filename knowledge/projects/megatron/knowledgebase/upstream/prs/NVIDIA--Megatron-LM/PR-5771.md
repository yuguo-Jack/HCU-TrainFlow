# [data] Support Nemotron-SFT, RP2, and CodeForge datasets in the varlen loader; prefetch packed global batches

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/5771) · state: closed · merged: True

## Original PR description

## What does this PR do?

Extend `VarlenDataset` to load the current public `nvidia/Nemotron-SFT-*` text datasets, and stop the packed-sequence data path from stalling the GPU at the start of every training step.

**Datasets**
- Preserve message metadata, tools, and dataset-provided chat-template kwargs. Only the fields a message actually sets reach the chat template; Arrow's `None` placeholders are dropped.
- Map legacy roles to template roles: `developer` -> `system`; legacy `function` replies and Llama `ipython` turns -> `tool`.
- Accept raw pretraining text from `text`, RP2 `raw_content`, and CodeForge `content` fields.
- Normalize OpenAI, legacy function-call, OpenCode tool, structured tool-result, and JSON-encoded Parquet fields.
- Load Hugging Face repos by config and split: the repo's declared default config if there is one, otherwise all configs; per config, `train`, otherwise every split except evaluation splits (`test`, `validation`, `dev`, ...). Several configs/splits are interleaved with a permutation seeded by the dataset `random_seed`, so `--split` ranges and sequential samplers mix them.
- Fall back to a cached map-style JSON payload dataset by reading raw JSONL/Parquet files when Hugging Face Arrow schema casting fails.

**Data loading speed**
- Build varlen samples with numpy/torch instead of Python lists; outputs are byte-identical.
- For training loaders behind a sequence-packing scheduler, set the DataLoader `prefetch_factor` so one global batch stays in flight: the next step's batch is built and pinned while the current step trains. No new argument; other loaders keep the PyTorch default.

## Why?

The existing loader assumed one `train` split and string-only message content. That changed tool-aware tokenization and could not load repositories with thematic splits, OpenCode tool-result blocks, JSON-encoded tool calls, or heterogeneous schemas such as Math-v4.

Packing schedulers pull the whole global batch at the start of every step, while the DataLoader prefetched only 2 items per worker and built each sample as Python lists (~4.6 ms per 50K tokens). On a Qwen3.5 dynamic-CP run (GBS 512, DP 1) the GPU sat idle for ~2.8 s per step waiting for data.

## Scope

This covers the public `nvidia/Nemotron-SFT-*` text repositories (17 repositories and 68 configs/splits as of 2026-10-15), plus RP2 and CodeForge raw-text schemas. Multimodal/VLM datasets remain out of scope for this text-only loader.

## Strict review: Nemotron-SFT / RP2 / CodeForge support in the varlen loader

**Findings:** CRITICAL: 0, IMPORTANT: 5, SUGGESTION: 0. All five are posted as inline comments, and each one includes a reproducible trigger, a fix, what the fix must not break, and checks to confirm it.

### Most impactful
1. **The Hub loader now changes what you train on, with no error or warning.** Before this PR, [`load_dataset(path, split="train")`](https://github.com/NVIDIA/Megatron-LM/blob/c75a269efd3fdf6d82ba5a07fff00ed40f350cba/megatron/training/datasets/varlen_dataset.py#L264) loaded only the repo's default config. Now every config is concatenated (`varlen_dataset.py` L519).
   - **Overlapping configs are duplicated.** In `HuggingFaceFW/fineweb-edu`, `default` already holds every row, and the `sample-*` and per-`CC-MAIN-*` configs repeat subsets of it, so documents get trained on several times.
   - **Test splits are trained on.** When a config has no `train` split, all its splits are used (L521). For `HuggingFaceH4/ultrachat_200k` that means training on `test_sft` and `test_gen`. Before, this case raised an error.
2. **Templates that check whether a key exists now crash.** `dict(m)` (L323) passes through the `None` values Arrow fills in for message fields a row doesn't have. Llama-3.x templates check `'tool_calls' in message`, then call `message.tool_calls|length`, which raises `TypeError` on every user turn. The base code built only `{role, content}`.
3. **Old-style function-calling data now fails.** The assistant's `function_call` is converted to `tool_calls`, but the matching `role: "function"` reply now raises `ValueError` (L309). The same happens to `ipython` turns, which the base code passed through.
4. **Joined configs/splits aren't mixed.** They are concatenated end to end (L590). `--split` takes contiguous index ranges and the `single` sampler reads them in order. So the validation set comes only from the last config/split, and training goes through one topic at a time.

### Overall risk: medium
The tokenizer changes ([`sft_tokenizer.py`](https://github.com/NVIDIA/Megatron-LM/blob/6c595853b9fb0d2edf257530951c52f0179d477a/megatron/core/tokenizers/text/libraries/sft_tokenizer.py#L130-L167) and [`text_tokenizer.py`](https://github.com/NVIDIA/Megatron-LM/blob/6c595853b9fb0d2edf257530951c52f0179d477a/megatron/core/tokenizers/text/text_tokenizer.py#L123-L154)) are backward compatible: the new `chat_template_kwargs` argument is optional, keyword-only, and actually used. The masking prompt formats tokenize each turn without the extra kwargs. That is consistent, because their custom templates don't use those kwargs. The RP2/CodeForge text-field aliases and the logic that maps an index to a config/split (including empty ones and negative indices) look correct. I found no unused new arguments, attributes or locals.

The problems are in data selection and normalization. They change what the model trains on without any error, which is the failure this review checks for most. Two of them also break datasets and tokenizers that worked before this PR.
