# [MoE] Give the fused shared expert's TE ops one unit scale per row

## Original PR description

# What does this PR do?

Fixes a crash in the first training forward of `FusedSharedExpertMLP` (`use_grouped_gemm_for_shared_expert=True`) whenever Transformer Engine does not fuse its grouped MLP.

**Bug.** The fused shared expert runs TE's `GroupedLinear` + `ScaledSwiGLU` (or `ScaledClampedQGeGLU`) + `GroupedLinear` ops with a one-element unit scale. Only TE's fused grouped MLP accepts that scale: it reads the activation op's `_grouped_mlp_unit_activation_scale` mark and skips the scales. Megatron cannot know in advance whether TE fuses. TE's op fuser decides that from:

- the TE version;
- `NVTE_CUTEDSL_FUSED_GROUPED_MLP` at TE import (TE 2.20.2+44f31bbe, the CI image's version, has no `split_alignment` and registers the fusion only when the variable is set before TE is imported);
- the cuDNN frontend;
- the shapes (FC sizes must be multiples of 64, the interleave must be 32, and a clamped QGeGLU with non-default parameters needs cuDNN frontend >= 1.24).

When TE does not fuse, it runs the three ops one by one. The unfused scaled GLU then fails: `scaled_activation_compute: Assertion failed: scales_tensor.numel() == rows. scaled activation expects one scale per input row`. On the CI image that is every training run (and every RL logprob pass) that does not set the environment variable at launch. Found on 2× GB200 in the CI image.

**Fix** (`megatron/core/transformer/moe/shared_experts.py`):
- `_fused_grouped_swiglu_no_comm` passes the cached unit scale as a stride-0 `expand` to one scale per row. TE's fused grouped MLP still ignores it: the mark is on the activation op, not on the tensor. TE's unfused ops make it contiguous and get one scale per row. Megatron adds no allocation, kernel or host sync. The forward and the overlapped `linear_fc1_forward_and_act` both go through this function.
- `_validate_fused_grouped_swiglu` rejects at construction a `moe_shared_expert_glu_interleave_size` that is not a multiple of 32 or does not divide the per-rank FFN shard. TE's scaled GLU kernels cannot run that layout on either path (`scaled_activation.cu`).

## Tests

- `tests/unit_tests/transformer/moe/test_shared_experts.py::TestFusedSharedExpertTrainingPaths::test_training_matches_unfused_shared_expert[unfused|fused, clamp None|0.5]` (1 Blackwell GPU, `launch_on_gb200`; the ops need an MXFP8 recipe). It runs a training forward and backward of the fused shared expert and compares it with the unfused `SharedExpertMLP` holding the same weights as checkpoints store them, converted with the checkpoint loader's permutation, under the same MXFP8 recipe.
  - It compares the output (to 5e-2), the input gradient and both weight gradients (to 1e-1). It also checks that the ops took the expected TE path. As a control, a separate `SharedExpertMLP` loaded with the interleaved rows read as `[gate | up]` must differ by more than 0.5. That module is loaded before its first forward, because Megatron's TE linears reuse the MXFP8 weight quantized at the first microbatch. The measured relative errors are recorded as test properties in the JUnit XML.
  - `unfused` turns TE's grouped-MLP fusion off for the test. Both cases fail on main with TE's assertion.
  - `fused` needs TE's fused grouped MLP. On TE without `split_alignment` that means `NVTE_CUTEDSL_FUSED_GROUPED_MLP=1` before TE is imported. The test skips when TE reports the fusion unavailable, so in CI images that do not set the variable at launch it covers only the unfused path.
- CPU: `test_fused_grouped_swiglu_no_comm_flattens_and_caches_fused_ops` now checks the per-row stride-0 scale view and that no scale is allocated per call. `test_validate_fused_grouped_swiglu_rejects_unsupported_configs` adds interleave 16, and 64 over a 32-wide FFN shard. The stand-in module's FC sizes are now a valid shared expert. All three fail on main.
- `tools/check_kernel_determinism_coverage.py --base-ref origin/main` passes.

On GB200 in the CI image (`mcore_ci_dev:main`, aarch64, 2026-11-02, TE 2.20.2), with `NVTE_CUTEDSL_FUSED_GROUPED_MLP=1` set before TE is imported, `TestFusedSharedExpertTrainingPaths` passes (4 cases, on both TE paths). On `main`, the two unfused cases fail with TE's `scales_tensor.numel() == rows` assertion and the two fused cases pass. Measured relative errors: the output is within 0.020 (tolerance 5e-2), and the input and weight gradients within 0.071 (tolerance 1e-1; the largest are the clamp 0.5 cases). The misread control differs by 1.40 (it must exceed 0.5). An earlier commit's control copied the rows into the reference after its first forward and measured 0.0, because TE reused the cached quantized weight; the control now loads a fresh module.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), `test_fused_grouped_swiglu_no_comm_flattens_and_caches_fused_ops` and `test_validate_fused_grouped_swiglu_rejects_unsupported_configs` pass (9 cases) and fail on `main` (3 of 9: the scale-view check and the two new interleave cases). The rest of `test_shared_experts.py` passes on H100 (27 cases, 6 skipped). No neighbor tests ran on GB200 at this head; at an earlier head, the one GB200 neighbor (the split_alignment test) skipped every case, so it was dropped.
