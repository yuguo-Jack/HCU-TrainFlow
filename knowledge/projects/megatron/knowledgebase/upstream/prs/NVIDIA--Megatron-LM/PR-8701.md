# [CI][MLA] Build FlashMLA's SM90 kernels into the dev CI image

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8701) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Builds FlashMLA's SM90 (Hopper) kernels into the dev CI image, and re-enables the DSA tests that were disabled for a CUDA error in H100 CI and now pass on H100.

**Bug.** The dev CI image runs on H100 and GB200 (`NVTE_CUDA_ARCHS="90;100"`). #5481 builds FlashMLA from source with `FLASH_MLA_DISABLE_SM90=1`, so the image has no SM90 kernels. On H100, the first FlashMLA decode call aborts the process. H100 CI therefore cannot run MLA decode through FlashMLA, and tests that need FlashMLA on Hopper are disabled or gated to SM100.

**Fix.**
- The Dockerfile no longer sets `FLASH_MLA_DISABLE_SM90`. At the pinned revision (`b7643bd`, from `uv.lock`), FlashMLA's `setup.py` builds exactly two targets unless told not to: `sm_90a` and `sm_100f` (the SM100 family: GB200 and GB300). The build no longer depends on `NVTE_CUDA_ARCHS`.
- The uv cache mount id gets a `-flash-mla-sm90` suffix. uv keys git-built wheels by commit, not by build environment, so a warm cache would otherwise reinstall the old wheel without SM90 kernels. #8013 added the `-cudnn-fe-1.32` suffix for the same reason.

**Tests changed.**
- #5099 disabled ten tests with the comment "fails with a CUDA error in CI (deterministic, not truly flaky). Re-enable once the kernel/build root cause is resolved." These files run only in the H100 unit-test buckets, and their fused cases call `flash_mla_sparse_fwd`. With the SM90 kernels, none of them hits a CUDA launch error on H100. This PR re-enables what passes there and keeps the rest disabled, each with its observed H100 failure as the reason in place of the CUDA error (details under Known open issues):
  - Re-enabled (1 GPU): `test_dsa_native_parity.py::test_fused_absorbed_mla_dsa_matches_native` except cuDNN with sparse indexer loss (12 of 16 cases: every dense-loss case and every TileLang case), `test_cudnn_attention_backward_supports_small_local_head_count` and `test_cudnn_attention_backward_pads_small_local_head_count`. To mark the cuDNN sparse-loss cases on their own, the fused test's `kernel_backend` and `use_sparse_loss` parameters are now one combined parameter, so its case ids change (e.g. `[sparse_loss-cudnn-False-1024]`).
  - Still disabled: the four cuDNN sparse-loss cases of `test_fused_absorbed_mla_dsa_matches_native` (three failed; the passing `True-2048` case is disabled with its group), `test_unfused_absorbed_mla_dsa_matches_native`, `test_cudnn_full_fusion_real_kernel_packed_cp_varlen_matches_reference`, `test_cudnn_split_real_kernel_packed_cp_varlen_matches_reference`, and all four `test_dsa_backend_tp_sp_parity.py` tests (TP2 + CP2, 4 GPUs).
- `test_dsv4_packed_cp.py::test_packed_cp_matches_full_attention_and_gradients`: the skip below SM100 becomes a skip below SM90. On SM90 the dense-indexer-loss case (ratio 4, coefficient 0.2) now asserts with `pytest.raises` that `TransformerConfig` rejects it, so the test fails if that rejection is relaxed. **This test still runs in no CI lane:** it keeps `flaky` and `flaky_in_dev` from #8193 (AUT-2537). That quarantine is unrelated to SM90. Both recorded failures were GB200 merge-queue runs, in the dense-indexer-loss CP2 case: the indexer compressor weight gradients reached cosine similarity 0.9988 against a 0.999 threshold. This PR does not address that.
- `test_csa_fused_sparse_attention.py::test_real_fused_sbhd_forward_backward_matches_native_reference` stays disabled. Its comment now describes the H100 failure (see the open issue below) instead of the missing kernels.

**H100 results** (at an earlier head): the re-enabled DSA cases pass (14, 1 GPU), and the dsv4 CP test passes all 12 cases on 4 GPUs, its two dense-indexer-loss cases asserting the SM90 rejection.

**What starts running in CI.** In the H100 unit-test buckets: the 14 re-enabled DSA cases above, the probe-gated `TestMLALatentCacheDecode` from #8571 (FlashMLA dense decode on H100), which skips with today's image, and the `[mla]` row of `test_coordinator_backends_pairwise.py` (see the follow-up below).

**Known open issues** (H100 with FlashMLA's SM90 kernels; none is fixed here, and SM100 is unverified):
- Fused CSA kv gradient. With the SM90 kernels, `test_real_fused_sbhd_forward_backward_matches_native_reference` runs on H100 and fails. The forward output and the query gradient match the native reference. The kv gradient, which comes from cuDNN Frontend's DSA sparse-attention backward, does not: 2.6% (1 head) and 3.0% (2 heads) of its elements are outside rtol = atol = 5e-2, with a max relative difference of 7.8% and max absolute differences of 0.30 and 0.56. `TransformerConfig` allows fused CSA with sparse indexer loss on SM90, so this may affect DSv4 training on H100 with `dsa_kernel_backend='cudnn'`.
- cuDNN fused DSA with sparse indexer loss (`test_fused_absorbed_mla_dsa_matches_native`): the `indexer.linear_wk.weight` gradient misses the cosine-similarity bar of 0.999, at 0.998945, 0.998996 and 0.998912 (per-token loss False at seqlen 1024 and 2048, True at 1024). The `True-2048` case passed.
- Unfused DSA parity (`test_unfused_absorbed_mla_dsa_matches_native`) runs out of memory on an 80 GB H100. All four seqlen 4096 cases fail; the first tries to allocate 8 GiB with 63.6 GiB already allocated by PyTorch. Three 1024/2048 cases that run after a 4096 case in the same process fail too, with 77-78 GiB allocated.
- Packed-CP varlen real-kernel tests (`test_cudnn_full_fusion_real_kernel_packed_cp_varlen_matches_reference`, `test_cudnn_split_real_kernel_packed_cp_varlen_matches_reference`): cuDNN Frontend's SM90 sparse score-recompute kernel, used for the sparse indexer-loss target, fails to compile. CuTe DSL raises `ValueError: Expected size in shape to be strictly positive, but got 0` in `softmax_l1norm_parallel` (`sparse_score_recompute_sm90.py`).
- TP2 + CP2 DSA parity (`test_dsa_backend_tp_sp_parity.py`): in `test_packed_cp_tp2_sequence_local_query_backend_matches_unfused_attention[cudnn]`, the output differs from the unfused reference on ranks 1, 2 and 3 (cosine similarity 0.37, 0.87 and 0.52; above 0.995 required). Those ranks then time out after 600 s in `destroy_model_parallel`'s barrier, and the NCCL watchdog aborts the communicator. Every later case in the process, including the TileLang case of the same test and all cases of the other three tests, fails at its start with `torch.distributed.DistBackendError: NCCL communicator was aborted on rank 1`, so those nine cases have not actually run on H100.

**Build cost.** FlashMLA compiles each of its 24 CUDA sources once per target, so adding `sm_90a` roughly doubles FlashMLA's device compilation. Measured: building the FlashMLA wheel at `b7643bd` with both targets took 251 s on an 8-GPU H100 node (at an earlier head; `pip install --no-build-isolation`, `NVCC_THREADS=4`, `MAX_JOBS` unset, with test jobs running on the same node). I have not measured the image build. It uses `NVCC_THREADS=16` and builds TE in the same `uv sync`. This PR's container-build job will measure its time and memory.

**H100 results** (official CI image `mcore_ci_dev:main`, with FlashMLA `b7643bd` built for `sm_90a` and `sm_100f` on the job, at earlier heads):
- `test_packed_cp_matches_full_attention_and_gradients` (4 GPUs): all 12 cases pass, the 2 dense-indexer-loss cases by asserting `TransformerConfig`'s SM90 rejection.
- `test_real_fused_sbhd_forward_backward_matches_native_reference` (1 GPU): both cases fail on the kv gradient, as described above.
- Dynamic-batching MLA inference: the 18 MLA configurations of our out-of-tree inference configuration matrix ran end to end on H100 with this FlashMLA build.
- The ten DSA tests #5099 disabled (1 and 4 GPUs): 20 cases pass and 22 fail (see Known open issues). 14 of the passing cases stay enabled: 12 of 16 `test_fused_absorbed_mla_dsa_matches_native` cases (all except cuDNN with sparse loss) and both small-head backward tests. The 5 passing cases of `test_unfused_absorbed_mla_dsa_matches_native` stay disabled with that test, because its failures do not split cleanly by parameter. The passing cuDNN sparse-loss `True-2048` case stays disabled with its group.
- After that run, the tests changed only in their markers, reasons and the fused test's parameter layout (case ids). Every enabled case passed in that run.

This PR has no failing-on-main regression test: the defect is in the image build, not the source tree.

**Follow-up: the pairwise MLA backend test's gate.** `tests/unit_tests/inference/test_coordinator_backends_pairwise.py` was added to `main` after this branch was cut, so `main` is merged into the branch first (signed, no conflicts; the PR's diff against `main` is unchanged).
- `test_routed_native_model_modes_match_direct[mla]` requires dynamic MLA decode to run through `flash_mla_with_kvcache`. It gated itself to compute capability >= 10, with the comment "CI builds FlashMLA with FLASH_MLA_DISABLE_SM90=1, so its decode kernel needs SM100".
- The premise was backwards. At the pinned FlashMLA (`b7643bd`), dense decode is SM90-only (`csrc/api/dense_decode.h` rejects anything but SM90a), and its SM100 kernels are sparse-only. Upstream FlashMLA has since removed dense decode.
- So the row could never pass on GB200: it raises "Dense decode MLA is only supported on SM90a architecture" at the first decode step. It also never ran there, having no `launch_on_gb200` marker. On H100, the one device it can pass on, it was skipped.
- The gate is now `HAVE_FMLA` and compute capability exactly 9.0, and the comment says why. With this PR's SM90 FlashMLA build the row runs on H100. GB200 cannot run FlashMLA's dense decode at all: dynamic MLA decode on Blackwell needs FlashInfer's MLA decode, which our PR stacked on #8571 adds (#8873; PR number to fill in). The row instruments only FlashMLA, so it stays SM90-only until both land.
- With the SM90 FlashMLA build, the row runs and passes on H100 (2 GPUs; see the results at the end of the next section).

**Follow-up (review): probe the kernel, not the import.**
- `import flash_mla` succeeds for a build without its SM90 kernels, such as the image before this PR, a warm uv cache with the old wheel, or a local `FLASH_MLA_DISABLE_SM90=1` build. The first decode launch then exits the process: both ranks of the `[mla]` row die and every later test in the bucket is lost.
- The row now probes FlashMLA's dense decode in a subprocess first. The probe is `tests/unit_tests/test_utilities.py::is_flash_mla_dense_decode_available`, the same probe #8571 runs from `test_multi_latent_attention.py`. It is shared here so that #8571's copy can move to it; whichever of the two lands second should drop its own.
- If the probe fails, the row fails rather than skips: this PR's image builds the SM90 kernels, so a build without them on H100 is a regression to report. The collection-time gate (`HAVE_FMLA` and compute capability 9.0) still skips other devices and images without FlashMLA (the LTS image), the same on every rank.
- Not applied here: gating the row on the per-device kernel resolver of the Blackwell MLA decode PR (#8873, stacked on #8571) and instrumenting FlashInfer's decode with `launch_on_gb200`. That needs both PRs merged first, and belongs in a follow-up PR.
- On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), at this head, with FlashMLA `b7643bd` built for `sm_90a` and `sm_100f` on the job: the probe passes and the `[mla]` row passes; the 14 re-enabled DSA cases (1 GPU) and the 12 dsv4 CP cases (4 GPUs) pass. The probe's failure path, an image without the SM90 kernels, was not run for this row. There is no `main` run: the defect is in the image build.
- Merge order: this PR first. The KV page initialization PR (`fix/kv-page-init`), https://github.com/NVIDIA/Megatron-LM/pull/8571 and the Blackwell MLA decode PR (`fix/mla-decode-blackwell`, stacked on #8571) land after it, in that order.
