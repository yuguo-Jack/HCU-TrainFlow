# What does this PR do?

Makes every relaunch of a training job log to the same wandb run, instead of opening a new run per restart.

`wandb.init()` opens a new run unless given an id to resume, and `_set_wandb_writer` runs on every process start. A long job restarts many times (on requeue, on node failure, or through an in-job restarter), so one training run was scattered across as many wandb runs as it had restarts, each chart covering only the stretch between two failures.

**Commit 1: resume the same run.** Derive a stable run id from the experiment name and pass `resume='allow'`, so the first launch creates the run and every later one appends to it.

```python
run_id = cfg.logger.wandb_run_id or _wandb_run_id(cfg.logger.wandb_exp_name)
wandb_kwargs = {
    'dir': save_dir,
    'id': run_id,
    'name': cfg.logger.wandb_exp_name,
    'project': cfg.logger.wandb_project,
    'config': wandb_config,
    'resume': 'allow'}
```

The id is part of the run URL and wandb rejects the characters that would be ambiguous there (the API returns `invalid run name "a/b/c", cannot contain character "/" at position 1`), so `_wandb_run_id` substitutes `/ \ # ? % :` with `-` rather than failing, since experiment names are often paths. The display name is untouched. `--wandb-run-id`, a new `LoggerConfig` field, overrides the derived value, for when two experiments would otherwise collide on an id or to keep resuming a run whose experiment name has since changed.

**Commit 2: let a relaunch update the job name.** A resumed run's config already holds the `slurm_job_name` of the attempt that created it, so relaunching under a new job name crashed the logging rank at startup:

```
wandb.sdk.lib.config_util.ConfigError: Attempted to change value of key "slurm_job_name" from <job>_v0 to <job>_v1
If you really want to do this, pass allow_val_change=True to config.update()
```

The `config.update` call in `pretrain()` now passes `allow_val_change=True`, so the resumed run's config keeps the latest job name.

### Notes for review

- `resume='allow'` rather than `'must'`: the first launch has nothing to resume, and `'must'` would fail it. `'allow'` is the only setting that works for both the initial launch and every relaunch.
- **Behaviour change.** Anyone relying on a relaunch producing a separate wandb run now gets one merged run instead.
- Restarts replay iterations from the last checkpoint, and wandb will not accept a step it already holds, so at each restart boundary it keeps the value logged before the crash and drops the replayed one, even though the replayed value is the one that trained. On a 229k-iteration run that affected 3681 steps, about 1.6%, concentrated at restart boundaries. Fixing it needs `resume_from` to rewind the run to the checkpoint iteration, which is a separate change with its own side effects (forked lineage), so it is deliberately not bundled here.
- Ported onto current `main`: the writer reads its settings from `cfg.logger` rather than `args`, and the CLI flag comes from the `LoggerConfig` argument factory.

### Preserve initialization when the experiment name is omitted

**Failure:** On the logging rank, use `LoggerConfig(wandb_project="project", wandb_save_dir="/tmp/wandb")`, leaving both identity fields unset. [`wandb_exp_name` defaults to `None`](https://github.com/NVIDIA/Megatron-LM/blob/9f025be21288c678cf5e7c06475c83134b7c95b9/megatron/training/config/training_config.py#L377-L389), and the existing guard rejects only `""`. This expression consequently calls `_wandb_run_id(None)`, and `re.sub` raises `TypeError` before `wandb.init`. The [base implementation](https://github.com/NVIDIA/Megatron-LM/blob/53015a0d7bf410be799be52d9c52b0b0fcebdb58/megatron/training/global_vars.py#L347-L378) passed `name=None`, allowing W&B to assign its own name and ID.

**Correction:** Derive an ID only when a name exists; an omitted optional name must not enter the string sanitizer. Replace this assignment with:

```python
        run_id = cfg.logger.wandb_run_id or (
            _wandb_run_id(cfg.logger.wandb_exp_name)
            if cfg.logger.wandb_exp_name is not None
            else None
        )
```

This preserves automatic identity for unnamed launches, explicit-ID precedence, and stable resumption for named experiments. Verify the suggestion against the installed SDK before adopting it.

**Proposed acceptance checks:** With W&B mocked, the setup above must reach `wandb.init` with `name=None` and `id=None`, without exception. An explicitly empty experiment name must still raise the existing `ValueError`. A named `group/run` must retain its display name, produce `id="group-run"`, and pass `resume="allow"` on both initial launch and reinitialization. An explicit `wandb_run_id="previous-id"` must remain unchanged with either a renamed experiment or an omitted name. Also verify an unnamed first launch against the installed SDK. These checks were not executed.

It also does not exercise the [job-name update](https://github.com/NVIDIA/Megatron-LM/blob/9f025be21288c678cf5e7c06475c83134b7c95b9/megatron/training/training.py#L2185-L2191).

**Correction and proposed acceptance:** Extend that test module using its existing mocked-W&B/config fixtures:

- Initialize twice, resetting `_GLOBAL_WANDB_WRITER` between calls; assert identical derived IDs and `resume="allow"` each time.
- Supply `--wandb-run-id previous-id` through `ArgumentParser` and `_default_config_from_args`; assert it reaches `LoggerConfig` and overrides derivation even after the experiment name changes.
- Exercise the production `pretrain` config-update branch with an existing `slurm_job_name="job_v0"` and `SLURM_JOB_NAME=job_v1`. Use a config fake that rejects changed values unless `allow_val_change=True`; expect `job_v1` without an exception and retain an unrelated config entry.
