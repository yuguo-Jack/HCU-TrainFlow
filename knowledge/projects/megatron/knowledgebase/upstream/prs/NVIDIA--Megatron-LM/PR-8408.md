# inference: encode the images of waiting requests together before prefill

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8408) · state: closed · merged: True

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Encode the images of all waiting multimodal requests with one vision-encoder call right before they are scheduled for prefill, instead of one call per request at admission.

## Issue tracking

Linked issue: Closes #8407

## Motivation

Today `add_request` runs the vision encoder once per request, synchronously on the engine loop. When many image requests arrive at once they are encoded one after another: on A100 x2 with Nemotron 3 Nano Omni and 64 concurrent single-image requests, MCore reaches 571 output tok/s against vLLM's 1646 on the same images (Measurements below). A request with several images already hands the encoder its patches concatenated, one `imgs_sizes` row per image, so the images of several requests can be concatenated the same way and the output split back per request. vLLM batches encoder inputs across requests per scheduler step in the same way ([scheduler budget](https://github.com/vllm-project/vllm/blob/db3b0f0fae4bc98492b3863685e541e62bc59576/vllm/v1/core/sched/scheduler.py#L1869), [runner batch](https://github.com/vllm-project/vllm/blob/db3b0f0fae4bc98492b3863685e541e62bc59576/vllm/v1/worker/gpu_model_runner.py#L2782)).

## Changes

- `_build_vlm_request` admits a dynamic-resolution image request whose patch tensor is `[P, F]` or `[1, P, F]` without encoding it, and keeps the embedding count its prompt expansion expects (`expected_embedding_count`) on the request as `deferred_image_embedding_count`. Videos, static tiling and cache hits are encoded at admission as before.
- `schedule_waiting_requests` now starts with `_encode_waiting_images`, which encodes all waiting deferred requests together (one `_batched_request_image_encode` call per group of at most `context.max_tokens` embeddings), splits the result per request, validates it, caches it and registers it on the context. Cached images are reused, requests sharing a `media_cache_key` are encoded once, and a shared call that fails (including OOM) or whose output does not match the expected counts falls back to per-request encodes, so a request whose own encode or count is wrong is failed on its own.

Prefill scheduling is the last point before a request enters the context, so encoding there batches everything that arrived since the previous prefill while admission order and abort handling stay unchanged.

## Measurements

Nemotron 3 Nano Omni 30B-A3B (same HF weights for both engines), A100 80GB x2, a distinct 448x448 image per request, 64 output tokens per request (`ignore_eos`), output tokens/s, median of 3 rounds x 3 reps. Every engine sees 280 prompt tokens per request (256 image tokens).

- vLLM 0.32.0, TP2, default V1 settings (CUDA graphs, chunked prefill, prefix caching; no image is repeated, so the encoder cache never hits).
- MCore base = upstream/main `45b68f914`, this PR = `45b68f914` + this commit. Both: Nemotron Omni via Megatron-Bridge (`NemotronOmniInferenceWrapper`), TP2 EP2, `--transformer-impl inference_optimized`, nccl MoE dispatcher, decode CUDA graphs, `--max-tokens 2048`, dynamic-resolution images with the HF preprocessor range (1024 to 13312 patches).

| concurrent requests | vLLM | MCore base | MCore this PR | this PR / base |
|---|---|---|---|---|
| 1 | 149 | 70 | 71 | 1.01x |
| 8 | 562 | 298 | 374 | 1.26x |
| 32 | 1230 | 488 | 780 | 1.60x |

Text-only throughput (128 output tokens) is unchanged: 80/579/1765/2973 on base vs 84/582/1789/3103 tok/s with this PR at conc 1/8/32/64 (vLLM 194/812/2465/4581). Greedy outputs for 8 images sent one at a time and all at once agree for 6/8 images with this PR, 4/8 on base and 5/8 on vLLM; the differences come from bf16 batch composition and exist without this PR as well.

## Notes for reviewers

- The group budget counts projected embeddings (what one prefill step can consume), not encoder patches; with pixel shuffle the encoder processes a multiple of that per call. A patch-based cap can be added if this turns out to be too large.
- Each pass encodes every deferred request in the queue, not only the ones this step can admit. The total work is the same as encoding at admission; it is just no longer spread across admissions.
- An image whose encode fails, or whose prompt does not match its images, is no longer rejected inside `add_request`: the request is admitted, and when its encode fails before prefill it is failed through `_handle_failed_request`, so a direct `add_request` caller sees a failed request instead of an exception.
