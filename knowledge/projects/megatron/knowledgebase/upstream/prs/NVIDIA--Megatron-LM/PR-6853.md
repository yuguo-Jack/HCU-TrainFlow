## Original PR description

## What does this PR do?

This PR is the exact cumulative integration form of the current asynchronous-scheduling pairwise series. It combines the shared unit matrix, four production fixes with their focused regressions, and the separately approved GPTOSS HTTP/SSE test on current `NVIDIA/Megatron-LM:main`. It is rebuilt from the current source PR tips and does not reuse the superseded aggregate #6420.

Every positive matrix row runs the same companion configuration twice:

- baseline: `async_sched_mode=LEGACY`
- treatment: `async_sched_mode=ASYNC`

All other flags, requests, seeds, and model settings stay fixed. Runtime witnesses prove that both scheduling modes and the named companion behavior execute; results must match the legacy oracle or satisfy the row's precise invariant.

The cumulative production fixes are:

| Source | Production fix | How the defect was exposed |
| --- | --- | --- |
| [fork #43](https://github.com/lmcafee-nvidia/Megatron-LM/pull/43) | Clear pending async logits after reset and RECOMPUTE suspension while preserving them for PERSIST and OFFLOAD. | Seeded pending logits remained marked valid after the inference state that produced them was discarded. |
| [fork #44](https://github.com/lmcafee-nvidia/Megatron-LM/pull/44) | Compact every request-metadata tensor when a middle request completes. | Request rows `[0, 2]` survived, but termination IDs remained `[90, 91]` instead of `[90, 92]`. |
| [fork #46](https://github.com/lmcafee-nvidia/Megatron-LM/pull/46) | Honor each request's logprob opt-in policy inside a heterogeneous async batch. | An opted-out request received an empty logprob list instead of leaving its result fields `None`. |
| [fork #45](https://github.com/lmcafee-nvidia/Megatron-LM/pull/45) | Move a CPU-initialized fused RoPE cache to CUDA on first GPU use. | The direct device check and real FlashInfer row found a CPU table at the CUDA kernel boundary. |

## How was the test matrix determined?

The matrix starts from supported inference settings whose execution, request-local state, cache ownership, batch shape, or distributed communication can interact with scheduling:

- engine behavior: request/token capacity, chunked prefill, prefix caching, KV residency, CUDA graphs, and token events;
- request behavior: sampling filters, logprob modes, output-length controls, BOS insertion, termination IDs, stop sequences, and speculative decoding;
- model and kernel behavior: dense GPT, hybrid Mamba, Transformer Engine, inference-optimized layers, BF16/FP8, sliding-window attention, and softmax sinks;
- parallel behavior: tensor, pipeline, sequence, data, and expert parallelism plus NCCL expert dispatch.

A configuration counts only when the test forces its production path to run, records a feature-owned runtime witness, and compares scheduler behavior or a precise invariant. Merely setting a flag or inspecting configuration state receives no coverage credit. Related settings are grouped when they naturally execute together; configurations requiring special GPU topology have separate rows.

The companion-disabled cells are omitted because every row already has a legacy-scheduler control with the same companion active. Repeating a companion-disabled cell would test the scheduler alone again without proving another interaction.

The GPTOSS SSE case is a separate end-to-end boundary rather than pairwise credit. It was selected because the unit matrix cannot validate the real HTTP server plus Hugging Face incremental-tokenizer path.

## How are results checked?

The common unit workload contains seven requests with prompt lengths `(9, 5, 12, 7, 10, 6, 11)` and output lengths `(10, 5, 9, 7, 11, 6, 8)`. They arrive in three waves while capacity is limited to four active requests. This forces waiting, arrivals during decoding, middle-request completion, metadata compaction, overlap and no-overlap phase shapes, and complete drain.

Deterministic rows require matching completion state, output length, exact generated tokens, finite logprobs within tolerance, top-N content, and event sequences where requested. Stochastic and FP8 rows require valid shapes, lengths, token ranges, and finite values across schedulers; a repeated ASYNC run must reproduce the first ASYNC run exactly.

Every row checks both the shared async runtime contract and a feature-specific witness, such as nonzero prefix hits, executed graph dimensions, FlashInfer calls, Mamba compaction, attention kernels, FP8 forwards, parallel collectives, pipeline broadcasts, or NCCL expert dispatch/combine calls. Four negative guards verify explicit rejection of routing replay, mismatched MTP depth, processed logprobs with speculation, and skipped async bookkeeping.

Focused regressions check exact lifecycle and request-local invariants for the four fixes. The HTTP/SSE case joins streamed deltas, validates its terminal reconstruction, and then compares the complete legacy and async responses.
