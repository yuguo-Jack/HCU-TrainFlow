# Warn on silent global process-group fallbacks in core helpers

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8755) · state: closed · merged: False

## Original PR description

Depends on #6303 (which contains #6293), #8017 (which contains #6259), #8032, #8035 (which contains #8034 up to its last, test-only commit), #8047, #8049 and #8053. Please review the diff from their merge: [scoped diff](https://github.com/Connor-XY/Megatron-LM/compare/ac9889a8f9...yx/pstate-c8-misc-owner-fallbacks).
- Every commit uses #8049's `resolve_process_groups` and `ProcessGroupFallbackWarning`.
- Each area builds on the PR that last changed it: #8047 for the group arguments of the hash check, #8053 for the `ep_size` of `unpermute`, #8034 and #8035 for the amax group and the TE wrappers' collection, and #8032 for the pipeline group of `CudaGraphManager`.
- Three edited test files use the module-level `ProcessGroupCollection` import that #6303 adds. The new tests use #8017's helpers that forbid the global grid.
- The merge of #8035 resolves its existing conflicts with #6293 and #6303 in `transformer_engine.py`, `t5_model.py`, `multi_token_prediction.py` and `test_hybrid_block.py`. The merges regenerate the process-group allowlist where it conflicted. Each merge commit lists its resolutions.

#7029 changes the same import lines in `transformer_engine.py` and `cuda_graphs.py`. Whichever lands second keeps both.

Land this after #8748 and #8739:
- Until #8748, owners such as MLA, DSA, CSA and GDN build their Transformer Engine linears without their collection, so a per-module quantization recipe on them would warn in stock training.
- Until #8739, the combined 1F1B schedule opens its delayed-FP8 context without a collection and would warn from `get_fp8_context`.

**Why.** Several Megatron Core helpers fill in an omitted process group from the global `parallel_state` grid, with no warning. A model on its own grid, such as a MIMO module, an RL inference model or a second model in the job, then does this work over another grid's ranks: logging, hash checks, RoPE, token sharding, the expert combine, FP8 amax reduction, CUDA-graph capture and config-dump naming.

**What.** Each omitted group goes through `resolve_process_groups`. It emits a `ProcessGroupFallbackWarning` (deprecated in 0.21, removed in 0.23) and builds only the groups the helper reads, which on the standard grid are the groups used before. One commit per area:
- `log_on_each_pipeline_stage` (`tp`, `dp_cp_gtp_remat`) and `check_param_hashes_across_dp_replicas` (`dp`, `expt_dp`).
- `apply_rotary_pos_emb`. Only packed (THD) sequences read `cp_group`, so only they fall back. Unpacked sequences no longer need a grid.
- The multimodal CP gather. The forward resolves the group once and stores it for the backward. The gather and reduce-scatter helpers take a required group, so the backward no longer reads the global grid a second time, silently.
- `PartitionConfig.from_mp_config`: the CP group, and the TP group with sequence parallelism.
- Batch-invariant `unpermute` without `ep_size`: the size of the global expert-parallel group.
- `get_fp8_context`, `get_fp4_context` and the Transformer Engine per-module recipe autocast (`tp_cp`, `tp_dp_cp`). The `model_parallel_is_initialized()` probes are gone. The per-module warning names the TE module class, since a module built without `pg_collection` is what the caller has to fix.
- `CudaGraphManager` (`pp`) and `TECudaGraphHelper` (`tp`, `dp_cp`, `pp`, `tp_cp`, `tp_dp_cp`).
- `log_config_to_disk` takes a keyword-only `pg_collection` and names each dump from its six groups. `GPTModel`, `BertModel`, `HybridModel`, LLaVA, `T5LMHead`, `CLIPViTModel`, `RADIOViTModel` and `DistributedDataParallel` pass theirs.

Tests that relied on the global grid pass its groups explicitly. The FP8/FP4 cases use a new test helper, `global_amax_groups()`. The allowlist goes from 172 counted reads to 169, and 12 of them are now guarded.

**Tests.** New per-owner tests check that omitted groups warn and select the same groups, and that passed groups read no global state:
- new files: `test_utils_process_group_fallbacks.py`, `test_rope_process_groups.py`, `test_multimodal_cp_gather_groups.py`, `test_cuda_graph_helper_process_groups.py` and `test_config_logger_process_groups.py`;
- extended: `test_mimo_partition.py`, `test_batch_invariant_unpermute.py`, `test_amax_reduction_group.py` and `test_cuda_graphs.py`.

On 4 GPUs against its base, this PR's unit-test files pass 648 tests here vs 622 on the base, and 30 new tests pass: 7 in `test_utils_process_group_fallbacks.py`, 5 in `test_config_logger_process_groups.py`, 4 in `test_rope_process_groups.py`, 3 in `test_multimodal_cp_gather_groups.py`, 3 in `test_mimo_partition.py`, 3 in `test_amax_reduction_group.py`, 2 in `test_cuda_graph_helper_process_groups.py`, 2 in `test_batch_invariant_unpermute.py` and 1 in `test_cuda_graphs.py`. The 4 base tests absent here are renamed to say that they warn. The remaining files pass the same tests on both sides, apart from these, which fail on both sides:
- 15 tests in `test_gtp_grouped_cg.py`, because the test container's Transformer Engine is older than GTP needs (2.19);
- 15 cases in `test_virtual_experts.py`, which fail the same way on main, including on 8 GPUs (two nodes);
- `test_unquantized_fp32_tilelang_dsa_matches_native`, the TileLang fp32 parity case, which fails the same way on main;
- the functional-test helper `moe_perf/__main__.py`, which errors at pytest collection.

`test_multi_latent_attention.py` did not finish on either side.

In the integration run, with all #6307 PRs merged onto main, every unit-test file this PR touches except `test_multi_latent_attention.py` finishes with no regressions against main. That includes main's adapted `test_moe_batch_invariant_unpermute.py`, which passes 24 tests on both sides; the 4-GPU run against the base did not include it. On 8 GPUs (two nodes) there, `test_multi_latent_attention.py` again did not finish on either side. End-to-end training smokes with all #6307 PRs applied, 22 configurations on 4 GPUs, give bit-identical losses to main and record no process-group fallback warning.

Before the 2026-11-01 sync, the branch ran on 4 CPU gloo ranks, one test file at a time, with no regressions. Ten of the new tests pass there, the others need CUDA, and the checker tests pass.

**Compatibility.**
- On the standard grid the groups and ranks are the same, so numerics and checkpoints do not change.
- `set_tensor_model_parallel_rank`, `set_data_parallel_rank` and `set_expert_model_parallel_world_size` no longer affect the log filter and `unpermute`, which now read the groups. The checkpoint converter and lazy MPU init set these overrides, and neither reaches these fallbacks. Two RL tests that used the EP override pass `ep_size=2` instead. Main's `test_moe_batch_invariant_unpermute.py` set the EP size through the same override, and its `unpermute` calls now pass `ep_size` explicitly. Main's `test_batch_invariant_unpermute_replays` in `test_moe_kernels.py` patched the global EP size, and it now passes `ep_size=2`.
- Without a global grid:
  - Packed-sequence RoPE, the multimodal gather, MIMO `from_mp_config` and `unpermute` with `torch.distributed` initialized raise a `ValueError` that names the argument. Before, they asserted or went on with a `None` group.
  - The FP8/FP4 contexts still pass no amax group, which Transformer Engine reads as WORLD, now with a warning. Raising there would break setups that work on main before the fallback is removed.
  - The no-grid tests for FP8/FP4, single-process `unpermute` and MIMO `from_mp_config` rely on `resolve_process_groups` returning `None` groups there rather than raising. #8733 keeps that and makes the warning name the `None` groups.
- `log_config_to_disk` also falls back when the collection lacks one of its six groups. Otherwise two processes could get the same dump name.
- With `--config-logger-dir`, the optimizers and both Megatron-FSDP wrappers still call `log_config_to_disk` without a collection, so stock training warns there until #8763 lands.
- The private `_get_fp8_autocast_for_quant_recipe` and `_get_fp8_autocast_for_quant_params` gained a required keyword-only `owner`, so an out-of-tree caller gets a `TypeError`. Should `owner` get a default so that such callers keep working?
- Review nits left as they are: `CudaGraphManager`'s warning names `pg_collection.pp`, though the missing field is usually on the graphed module's collection, and the new test docstrings say "as before".
- Needs `determinism-exempt`: `fp8_utils.py`, `fp4_utils.py` and `batch_invariant.py` are registered kernel files. Only the source of the groups and of `ep_size` changes, not the arithmetic.
