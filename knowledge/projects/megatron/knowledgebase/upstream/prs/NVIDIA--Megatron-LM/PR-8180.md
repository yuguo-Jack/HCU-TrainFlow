# feat(determinism): Accept an empty NCCL_ALGO and Ring,NVLS under --deterministic-mode

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8180) · state: closed · merged: True

## Original PR description

# What does this PR do?

Accept `NCCL_ALGO=""` under `--deterministic-mode` as a request to let NCCL choose the algorithm for each collective, as suggested in #8138 ([comment](https://github.com/NVIDIA/Megatron-LM/issues/8138#issuecomment-6131995489)). This replaces the opt-in flag proposed in the issue.

On main, `--deterministic-mode` fills in `NCCL_ALGO=Ring` when the variable is unset and rejects the empty string, because the token check needs at least one token. With this PR the empty value is kept. PyTorch 2.8 and later write `NCCL_ALGO=^NVLS` under `torch.use_deterministic_algorithms(True)` only when the variable is unset, and they count an empty `NCCL_ALGO` as set ([c10/util/env.cpp](https://github.com/pytorch/pytorch/blob/v2.12.1/c10/util/env.cpp#L51-L66)). NCCL 2.24 and later read no algorithm from the empty string and so exclude none ([tuning.cc, 2.27.7](https://github.com/NVIDIA/nccl/blob/v2.27.7-1/src/graph/tuning.cc#L401-L405)), which leaves the choice to NCCL's cost model and to the tuner plugin, if one is loaded; NCCL 2.23 and earlier enable only Ring and Tree for it (only Ring when CollNet is available), so they do not use NVLS ([tuning.cc, 2.23.4](https://github.com/NVIDIA/nccl/blob/v2.23.4-1/src/graph/tuning.cc#L297-L315)). Rank 0 issues a warning that bit-exact reproducibility then rests on what NCCL selects.

Unset still defaults to `Ring`, `Tree` is still rejected, and `torch.use_deterministic_algorithms(True)` stays in `validate_args`. A value of only whitespace is still rejected, now with a message saying why: NCCL 2.24 and later fail to parse it.

As suggested in review ([comment](https://github.com/NVIDIA/Megatron-LM/pull/8180#issuecomment-6188474175)), `NCCL_ALGO=Ring,NVLS` (in either order) is accepted too. NCCL then chooses between Ring and NVLS for each collective and does not use Tree. A list with `NVLS` must also contain `Ring`, because broadcast and reduce run only with Ring ([tuning.cc L255, 2.27.7](https://github.com/NVIDIA/nccl/blob/v2.27.7-1/src/graph/tuning.cc#L255)). NCCL uses NVLS only for a communicator with more than two GPUs in the node and, without CollNet, only for one that stays within a single node ([nvls.cc L160](https://github.com/NVIDIA/nccl/blob/v2.27.7-1/src/transport/nvls.cc#L160), [tuning.cc L446-L448](https://github.com/NVIDIA/nccl/blob/v2.27.7-1/src/graph/tuning.cc#L446-L448)), so a group that spans nodes, often the data-parallel group, runs Ring. PyTorch leaves the value alone because it is set, and no warning is issued for it.

On Hopper GPUs (compute capability 9) the empty value and any list with `NVLS` are rejected, while `^NVLS` stays accepted. There the result of an NVLS reduction can depend on multicast objects allocated earlier in the process unless the kernel driver and Fabric Manager are 550.144.03 or later in the 550 branch, or 570 or later ([NVIDIA/nccl#2360](https://github.com/NVIDIA/nccl/issues/2360#issuecomment-5705740833)), and Megatron does not check those versions.

After `_initialize_distributed` creates the default process group, a runtime check, `assert_nccl_algo_still_empty`, reads `NCCL_ALGO` through libc and stops the run if an empty value has been replaced, for example by PyTorch's `^NVLS`. In `docs/user-guide/deterministic-training.md`, the `NCCL_ALGO` row lists the empty value and links a new section, "Letting NCCL choose the algorithm", which also covers `Ring,NVLS`, the version boundaries, the Hopper rejection and the runtime check.

The first new test in `tests/unit_tests/training/test_determinism_args.py` covers unset, `""`, `^NVLS`, `Ring,NVLS`, `NVLS,Ring`, `" "`, `Tree` and a bare `NVLS`. Unset becomes `Ring`, the next four are kept, and in these cases the other variables still get their defaults; the last three are rejected with their own messages and leave the environment unchanged. Other tests cover the warning (rank 0 only, and only for the empty value), the Hopper rejection (of `""` and `Ring,NVLS`, before any warning; unset and `^NVLS` still pass) and the runtime check (it raises once libc holds `^NVLS` and ignores an unset value). A GPU test creates a process group under `torch.use_deterministic_algorithms(True)` and reads `NCCL_ALGO` through libc: PyTorch writes `^NVLS` for an unset value (this case is skipped below PyTorch 2.8) and leaves `""` alone. With the replay test below, the two files pass on CPU (28 passed, 10 of them existing, and the 3 GPU items skipped) and under `torchrun --nproc_per_node 8` on 8 × H100 (30 passed on every rank, with the replay test skipped on Hopper).

`tests/unit_tests/determinism/correctness/test_nccl_nvls_allreduce.py` replays the pattern of NVIDIA/nccl#2360 under `NCCL_ALGO=Ring,NVLS`: for k = 0 to 3, it creates k other communicators that each run a small AllReduce, then AllReduces a fixed 32 MiB bf16 tensor twice on a new one, and every result must have the same bits on every rank. The input is normal values scaled by 2^e, with e from -8 to 24, chosen to make the sum sensitive to the reduction order even with fp32 accumulation. The unit-test `conftest.py` sets `NCCL_NVLS_ENABLE=0` and `NCCL_MAX_NCHANNELS=1`, which NCCL reads once per process, at its first communicator, so rank 0 of the pytest run starts the replay as a separate single-node `torch.distributed.run` job without those two variables. The test is marked `launch_on_gb200`, the marker by which the GB200 unit-test lane selects tests; it is skipped on Hopper, with two GPUs or fewer, and without NVLink multicast, and it has not run in NVIDIA CI yet. On one 8 × B200 node (driver 580.178.04, NCCL 2.27.7), the test passed on its own and after `test_determinism_args.py` in the same pytest session with CI's marker filter: NCCL ran each of the eight 32 MiB AllReduces with NVLS on 24 channels, and all 64 results (8 ranks, 4 histories, 2 repeats) had the same digest, the same in both runs.

On one 8 × H100 node, `pretrain_gpt.py` with `--deterministic-mode` and `NCCL_ALGO=""` (mock data, TP 2, PP 2, DP 2, 20 iterations; NGC PyTorch 25.09 with NCCL 2.27.7) stops at the Hopper check on every rank before `torch.distributed` is initialized. With `NCCL_ALGO` unset, the same run trains, the runtime check is called on every rank, and all 248 TensorBoard scalar values are bit-identical to the same run on main.

On 8 B200 nodes (64 GPUs), `--deterministic-mode` with `NCCL_ALGO=""` reproduced the 8-node opt-in runs from #8138 bit for bit in the three dense layouts (TP 8 with and without the distributed optimizer, and TP 2; seed 1234, 100 steps). These runs used the image of the B200 runs in #8138 (NGC PyTorch 25.09, NCCL 2.27.7, aws-ofi-nccl 1.21.1 and its tuner), with this change ported to the Megatron code base of those runs. The logged lm loss, grad norm, params norm and num zeros matched at every step, also on a node set that shares no node with the opt-in runs, and the empty-value runs matched each other across a repeat and a run with every 8-rank block moved one node over. NCCL made the same algorithm and protocol choice for every collective and size as under the opt-in, including NVLS for the 32 MiB TP AllReduce at TP 8 and Tree for the 4- and 8-byte cross-node AllReduces, and the tuner made the same choices.

We then ran this PR's first commit in the same image, with only the Megatron tree replaced: in the three layouts it gave the same bits and the same NCCL and tuner choices as the runs with the ported change, also on a repeat and with every block moved. With `NCCL_ALGO` unset, every collective ran Ring.

With `NCCL_ALGO=Ring,NVLS`, this PR's code in the same image gave the same bits in all three layouts across a repeat and a run with every 8-rank block moved one node over: NCCL ran every 32 MiB TP AllReduce at TP 8 with NVLS and every other collective with Ring, and NCCL and the tuner made the same choices in each pair.

Could we also check at runtime that `NCCL_ALGO=""` survived, so upstream PyTorch
change can't silently bring `^NVLS` back?

PyTorch writes `NCCL_ALGO=^NVLS` from C++ when it builds the NCCL process group
under `torch.use_deterministic_algorithms(True)` and the variable is unset. This PR
relies on an empty value being left alone, but nothing in the code verifies it.
`os.environ` can't see the C++ write, so the check reads the variable through libc
after the first `init_process_group`.

`megatron/training/determinism.py` (add `import ctypes`):

```python
def assert_nccl_algo_still_empty() -> None:
    """No-op unless NCCL_ALGO was set empty. Call after the first NCCL process group.

    PyTorch writes NCCL_ALGO from C++, which ``os.environ`` does not see, so the value is
    read back through libc.
    """
    if os.environ.get("NCCL_ALGO") != "":
        return
    libc = ctypes.CDLL(None)
    libc.getenv.restype = ctypes.c_char_p
    libc.getenv.argtypes = [ctypes.c_char_p]
    actual = libc.getenv(b"NCCL_ALGO")
    assert actual == b"", (
        f'NCCL_ALGO was "" but is {actual!r} after process-group creation, so '
        "PyTorch's NVLS exclusion applied anyway. Unset NCCL_ALGO to use the Ring default."
    )
```

`megatron/training/initialize.py`, right after `inprocess_restart.maybe_force_nccl_backend_init(device_id)`
(same indentation):

```python
        if args.deterministic_mode:
            from megatron.training.determinism import assert_nccl_algo_still_empty

            assert_nccl_algo_still_empty()
```

Tests, in `tests/unit_tests/training/test_determinism_args.py` (add `import ctypes`, import
`assert_nccl_algo_still_empty`, and `from tests.unit_tests.test_utilities import Utils`):

```python
def test_assert_nccl_algo_still_empty(monkeypatch):
    """Passes while libc still sees "", fails once a C++ write (PyTorch's) changes it."""
    monkeypatch.setenv("NCCL_ALGO", "")  # putenv, so libc agrees with os.environ
    assert_nccl_algo_still_empty()
    ctypes.CDLL(None).setenv(b"NCCL_ALGO", b"^NVLS", 1)  # what PyTorch does in C++
    with pytest.raises(AssertionError, match="NVLS exclusion applied anyway"):
        assert_nccl_algo_still_empty()


@pytest.mark.skipif(not torch.cuda.is_available(), reason="needs a CUDA device")
@pytest.mark.parametrize("nccl_algo, expected", [(None, b"^NVLS"), ("", b"")])
def test_pytorch_leaves_empty_nccl_algo_alone(nccl_algo, expected, monkeypatch):
    """Negative control (unset -> PyTorch writes ^NVLS) and the claim this PR relies on ("" is left alone).

    Without the control, the "" case could pass because PyTorch stopped banning NVLS.
    """
    Utils.initialize_distributed()
    libc = ctypes.CDLL(None)
    libc.getenv.restype = ctypes.c_char_p
    libc.getenv.argtypes = [ctypes.c_char_p]
    if nccl_algo is None:
        monkeypatch.delenv("NCCL_ALGO", raising=False)
    else:
        monkeypatch.setenv("NCCL_ALGO", nccl_algo)
    try:
        torch.use_deterministic_algorithms(True)  # the autouse fixture restores it
        group = torch.distributed.new_group(list(range(torch.distributed.get_world_size())))
        assert libc.getenv(b"NCCL_ALGO") == expected
        torch.distributed.destroy_process_group(group)
    finally:
        libc.unsetenv(b"NCCL_ALGO")  # PyTorch's C++ write bypasses monkeypatch
```

If it fires, the run would only lose NVLS (a performance loss, not a determinism
one), so a warning would also be defensible, but the assert makes the failure
impossible to miss. It only checks the first process group. I ran the logic of the
first test against the real libc with a stub `torch`; the second test needs a GPU
and I haven't run it.

Bit-exact reproducibility then rests on the algorithms NCCL selects, which Megatron does not check.
