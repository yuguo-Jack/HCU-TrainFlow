# fix(inference): promote TorchSampling temperature divisor to FP32

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8316) · state: open · merged: False

## Original PR description

Fixes #7857.

## What

`TorchSampling.filter_logits` ran `last_token_logits.div_(temperature)` in
the input's dtype. For BF16/FP16 logits that

  - loses precision in the scaled logit and shifts top-p nucleus membership
    at moderate temperatures like 0.1, and
  - overflows FP16 at temperature=0 (the divisor is floored to
    `MIN_SAMPLING_TEMPERATURE=1e-6` → `logits * 1e6` → `inf`).

Issue #7857 documents both failures on a trained Nemotron-H-8B-Base-8K through
the dynamic engine: BF16 rounding changes which token wins at temperature=0.1,
top_p=0.9; FP16 scaling overflows at temperature=0. The FlashInfer sampler
already pins this invariant (`scaled.dtype == torch.float32`); the
TorchSampling path is the divergent one.

## Fix

Promote the working buffer to FP32 when the divisor path runs; the downstream
softmax / log_softmax already promote to FP32, so this is the right dtype for
both sampling and log-probs. The `temperature == 1.0` shortcut still preserves
the input dtype and the in-place mutation guard.

## Tests

New tests in `tests/unit_tests/inference/sampling/test_torch_sampling.py`
pin:

  - the issue's exact BF16 reproducer (`leading` token kept, runner-up
    masked) for both BF16 and FP16 inputs,
  - FP16 does not overflow at temperature=0,
  - the fixed path matches the FP32 reference (mask agreement plus
    finite-entry value match) across several `(temperature,\` \`top_p)`
    combinations,
  - `filter_logits` returns FP32 for `temperature != 1.0` and preserves
    the input dtype for `temperature == 1.0`,
  - the input tensor is not mutated in the `temperature == 1.0` path.
