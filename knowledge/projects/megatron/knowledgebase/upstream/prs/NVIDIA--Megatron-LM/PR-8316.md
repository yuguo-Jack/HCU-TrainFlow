# fix(inference): promote TorchSampling temperature divisor to FP32 (fixes #7857)

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8316) · state: open · merged: False

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Fixes the `TorchSampling` temperature-scaling precision bug in #7857.

`TorchSampling.filter_logits` divided logits by the temperature **in the input's dtype**. For BF16/FP16 logits that (a) loses precision in the scaled logit and shifts top-p nucleus membership at moderate temperatures, and (b) overflows FP16 at `temperature=0` (the divisor is floored to `MIN_SAMPLING_TEMPERATURE=1e-6`, so `logits * 1e6` → `inf`). The fix promotes the working buffer to FP32 before the division and the nucleus filtering; the downstream softmax / log-softmax already ran in FP32, so this is the right dtype for both sampling and log-probs. The `temperature == 1.0` shortcut still preserves the input dtype.

`Tensor.to(dtype)` returns `self` when the dtype already matches, so promoting the buffer has to request the copy explicitly. Without `copy=True` the `div_` would mutate the caller's logits in place for an FP32 input — the framework default (`params_dtype` defaults to `torch.float32`). The static batching path hands the sampler a **view** of the model's logits (`logits[:, -1, :]`), so the mutation would write the temperature-scaled and top-k/top-p-masked values back into that buffer, and the prompt log-probs computed from it afterwards (`F.log_softmax(logits, dim=2)`) would come out as `-inf` for every token outside the nucleus. `filter_logits` documents *"Returns a new tensor (input unmodified)"*; `copy=True` keeps that contract.

## The failure

![BF16 nucleus shift and FP16 overflow](https://raw.githubusercontent.com/muditagrawal2007/Megatron-LM/issue-7857-figures/fig1_precision.png)

The issue's own numbers (Nemotron-H-8B-Base-8K, generated-token index 29, seed 123, `temperature=0.1`, `top_p=0.9`):

| Candidate | raw logit | BF16 scaled logit | probability (pre-fix) | probability (fixed) |
| --- | ---: | ---: | ---: | ---: |
| `" to"` (1317) | 26.625 | 266 | 0.88079703 | 0.92414182 |
| `" over"` (2136) | 26.375 | 264 | 0.11920292 | 0.07585818 |

The leading token needs a probability above `top_p = 0.9` for the nucleus to stay a single token. BF16 rounding of the divisor (`26.625 / 0.1 = 266.25` → `266`) drops it to `0.8808`, so the runner-up survives the filter and the engine emits `2136` where the FP32 reference emits `1317` with the same prefix and RNG state.

The second failure is the issue's FP16 column: at `temperature = 0` the divisor is floored to `1e-6`, so `30.0 / 1e-6 = 3e7` overflows FP16 (max 65504) to `inf`, the softmax returns `NaN`, and the sampler emitted token `0` instead of the greedy token.

![Divergence map over temperature and logit gap](https://raw.githubusercontent.com/muditagrawal2007/Megatron-LM/issue-7857-figures/fig2_disagreement.png)

Left: the BF16 divisor quantizes the scaled gap, so the runner-up keeps ~12% of the mass until the raw gap passes `0.31`, while the FP32 reference drops it above `0.23` — the shaded band is where the two paths disagree. Right: how often the pre-fix path can emit a token the FP32 reference excludes; the issue's operating point (`temperature=0.1`, gap `0.25`) is marked.

Both figures are generated by `make_figures.py` in the [evidence branch](https://github.com/muditagrawal2007/Megatron-LM/tree/issue-7857-figures); it reproduces the pre-fix `filter_logits` and the fixed one side by side.

## Root cause

```python
# before
last_token_logits = last_token_logits.clone()
if temperature != 1.0:
    last_token_logits.div_(max(temperature, MIN_SAMPLING_TEMPERATURE))
```

`Tensor.div_(scalar)` runs in the tensor's own dtype, so the scaled logit is rounded to BF16/FP16 **before** the nucleus filter sees it.

## The fix

```python
# after
if temperature != 1.0:
    last_token_logits = last_token_logits.to(torch.float32, copy=True)
    last_token_logits.div_(max(temperature, MIN_SAMPLING_TEMPERATURE))
else:
    last_token_logits = last_token_logits.clone()
```

The divisor and the nucleus filter now run in FP32, so the scaled logits are the FP32 ones and the top-p boundary matches the reference exactly. At `temperature == 1.0` there is no division, so the input dtype is preserved and the extra FP32 copy is skipped.

`filter_logits` is shared with `log_probs_kernel`, so the processed log-probs now match the distribution that was actually sampled.

## Code provenance

No code was copied or adapted from an external source. The change is an independent implementation in the repository's own idiom; the `copy=True` promotion follows the existing `Tensor.to(..., copy=True)` usage in `megatron/core/optimizer/optimizer.py`.

### Manual verification of the end-to-end effect

Replaying the static batching sequence (`logits[:, -1, :]` → sample → `F.log_softmax(logits, dim=2)`) on FP32 logits, with the top-p filter applied:

| `filter_logits` variant | caller's logit buffer | prompt log-probs |
|---|---|---|
| released code (clone + in-dtype `div_`) | not mutated | exact |
| FP32 promotion without `copy=True` | **mutated** | `-inf` for every token outside the nucleus |
| this PR (FP32 + `copy=True`) | not mutated | exact |

The middle row is the hazard the `copy=True` avoids: the released code cloned the logits first, so it never mutated the caller, and neither does this PR.

## Notes for reviewers

- The FlashInfer sampling path is untouched. It already pins the invariant this PR establishes for TorchSampling (`scaled.dtype == torch.float32`, `flashinfer_sampling.py:104`).
- The dynamic engine reads the same `_all_logits_cuda` buffer for both sampling and log-probs, but survives today only because both paths copy their rows out via advanced indexing (`torch_sampling.py:233`, `torch_sampling.py:324`). This PR removes the reliance on that being incidental, but does not change the dynamic path's behavior.
- `temperature == 1.0` still returns the caller's dtype (unchanged behavior), while the divisor path returns FP32. Downstream `softmax`/`log_softmax` promote to FP32 either way.
- Performance: for BF16/FP16 inputs the filter now allocates an FP32 working buffer instead of a BF16/FP16 one, and the top-p sort runs over FP32. That is the same trade-off the FlashInfer backend already makes (it also scales into FP32), and it only applies to the `temperature != 1.0` path.
- Out of scope: the issue also asks whether the direct core APIs should normalize `temperature = 0` to greedy the way the HTTP endpoints do. That is an API-behaviour decision and is not touched here — this PR only removes the precision loss.
