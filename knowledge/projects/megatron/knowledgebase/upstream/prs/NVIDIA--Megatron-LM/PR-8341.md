# refactor(training): add GPTDatasetConfig and DataloaderConfig to PretrainConfigContainer

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8341) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Adds the `dataset` section to `PretrainConfigContainer`: a declarative `GPTDatasetConfig` (plus `DataloaderConfig` and a `DatasetRuntimeContext`) that every entry point carries, serializes into `run_config.yaml`, and that the GPT dataset providers build their Megatron Core runtime config from, instead of re-reading the argparse namespace. First PR of the DatasetConfig series (follow-ups: TokenizerConfig authoritative, dataloader and batch consumers, `seq_length` ownership).

## Issue tracking

Linked issue: Related to #3554 (make `PretrainConfigContainer` authoritative), #6003 (load `run_config.yaml` into the container).

## Design

- **Declaration vs runtime object.** `megatron.core.datasets.gpt_dataset.GPTDatasetConfig` is a runtime object (asserts a built tokenizer, derives `split_matrix` / `token_dtype_code`, carries parallel sizes). The new `megatron.training.config.GPTDatasetConfig(MCoreGPTDatasetConfig, DataloaderConfig)` inherits its field names but holds what the user declared: no tokenizer, no file reads. `to_core_config(context)` builds a fresh Megatron Core config (or the existing runtime `GPTFIMDatasetConfig` for `dataset_type="fim"`) from the declaration plus a `DatasetRuntimeContext` (tokenizer, seed, parallel sizes, validation flags); the values Megatron Core derives and the defaults that depend on other fields (the legacy `split` when only `data_path` is given, `create_attention_mask` under inter-document masking, the SFT mock distribution from `seq_length`, `persistent_workers` with no workers) exist on the runtime object only and are never written back into the declaration. A declaration built from the CLI copies the validated `args`, which already carry the defaults `validate_args` materializes; a Python or YAML declaration gets them at conversion time. `megatron/core` is untouched.
- **Container lifecycle.** `validate()` is read-only and may run repeatedly (#6925); `finalize()` applies the spelling normalizations once, from `PretrainConfigContainer._finalize()` (`sequence_length` → `seq_length`, string `data_path` → list, phase transitions → sorted list, unset `dataloader_type` → `single`). `to_cfg_dict()` serializes that spelling-normalized declaration, so a reloaded `run_config.yaml` reacts to an edit of `seq_length`, `inter_document_masking` or `num_workers` like a fresh declaration, and it raises the `validate()` error for a declaration it cannot normalize instead of serializing a different, valid-looking one. Conversion and serialization are identical before and after finalization.
- **One family selector.** `dataset_type: Literal["gpt", "fim", "varlen", "sft"]` replaces the per-provider precedence over `--sft` / `--use-varlen-dataset` / `--fim-data`; the three flags stay as aliases of the new `--dataset-type`, and `validate_args` resolves the family once and writes it back into `args`, so both spellings drive the same checks, loaders and batches. An explicit value is accepted when it equals the aliases' legacy resolution (`sft` over `varlen` over `fim`, so `--dataset-type sft --sft --fim-data` is consistent); any other disagreement is an error, and `--sft --use-varlen-dataset` stays rejected. `mock_data` stays orthogonal.
- **Container threading.** `pretrain()` passes its container to `build_train_valid_test_data_iterators` → `build_train_valid_test_data_loaders` → `build_train_valid_test_datasets` (new keyword-only `cfg_container=None`, defaulting to the run config). A provider that declares `dataset_config` / `context` parameters receives `cfg.dataset` and the runtime context; every other provider, including ones taking `**kwargs`, is called exactly as before.
- **Per-entry-point policy.** `pretrain_gpt.py`, `pretrain_hybrid.py` and `pretrain_hybrid_flex.py` keep their own dataset-class tables and family-substitution rules (hybrid builds the gpt family for a fim request, flex for varlen and fim requests, each with a warning as before); `tools/prepare_cache.py` keeps its fixed GPT class and effective-config rule. Each passes the keywords its factory never forwarded through `to_core_config(exclude=...)` (unknown names are rejected), so the runtime object each builds is field-identical to the one it built before, over the tested matrix and with the three exceptions listed below. The four `core_gpt_dataset_config_from_args` functions remain as thin wrappers of the legacy call shape.

Three documented behaviour differences, all intentional:

1. `--sft --fim-data` and `--use-varlen-dataset --fim-data` keep their dataset class and raw `validate_args` checks, but their runtime config is a plain `GPTDatasetConfig` instead of the `GPTFIMDatasetConfig` wrapper `pretrain_gpt` built around an SFT / varlen dataset. Tested: class and shared-field equality, an AST check that `sft_dataset.py` / `varlen_dataset.py` read no `fim_*` attribute, and identical mock SFT / varlen samples under the wrapper and the plain config. Real-data sample parity for these two combinations follows from those facts and is not demonstrated here (no local SFT / varlen fixture).
2. A declaration with no data source and no `--mock-data` now selects the mock dataset class where one exists (`pretrain_gpt`: gpt, SFT, varlen; hybrid: gpt, varlen; flex: gpt); the legacy providers keyed on `--mock-data` and paired a mock runtime config with the real dataset class, which failed to build.
3. `--mock-data` next to `--data-args-path` or `--per-split-data-args-path` (accepted by `validate_args`, which does not count file-backed sources) is rejected at container validation with the single-source message; the legacy GPT and hybrid providers paired `MockGPTDataset` with a runtime config resolved from the file (`mock=False`), which `MockGPTDataset` refuses, so the combination never trained (`tools/prepare_cache.py` rejects `--mock-data` itself). Two file-backed sources together are rejected the same way.

Scope boundary: dataset construction is migrated; the data loaders and batch functions still read `args` (`pin_memory`, `persistent_workers` and `drop_last` are accepted in YAML / Python but the existing loaders keep their built-in values until the consumer migration, next PR), and the parallel sizes and validation flags of the runtime context are still taken from `args` in `build_dataset_runtime_context` until their sections are authoritative.
