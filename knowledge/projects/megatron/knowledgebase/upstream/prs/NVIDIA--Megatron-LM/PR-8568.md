# [Inference][SSM] Decode each request on its own state slot in static-batching Mamba decode

# What does this PR do?

Fixes static-batching Mamba decode with more than one request. Before this fix, the whole batch was decoded as one request's token sequence.

**Bug.** `MambaMixer._static_decode` projects the sequence-first decode input `(1, b, d_model)` to `zxBCdt` of shape `(1, b, proj)`. It passed that tensor unchanged to `ssm_decode`, which takes batch-first `(batch, seq, proj)` input. When `b > 1`, the decode kernels saw one request with a `b`-token (speculative-style) sequence:
- `causal_conv1d_update` and `selective_state_update` ran all `b` tokens through state slot 0, one after another.
- Slots `1..b-1` were never updated.
- Every request except the first got a wrong output.

The output still had the `(1, b, d_inner)` shape that `out_proj` expects, so nothing failed loudly.

This affects legacy static-batching inference (`StaticInferenceContext`: the static engine and `generate_all_output_tokens_static_batch`) for any model with Mamba layers, on every decode step, whenever the micro-batch is larger than 1. Dynamic batching is not affected. Neither is `GatedDeltaProduct`, whose static decode already transposes. The bug came in with #3594 (8f539df74), which made `ssm_decode` batch-first and moved the transpose into the dynamic path only. It went unnoticed because the static functional recipes use micro-batch 1, and `test_hybrid_model.py::test_inference` runs batch 2 but checks only shapes. On H100, a batch-2 step compared with two batch-1 steps gave: request 1 output max error 1.33, conv/SSM states of both slots wrong (up to 5.8), and slot 1 never updated.

**Fix.**
- **Layout.** Transpose the projection to `(b, 1, proj)` before `ssm_decode`, and transpose the result back to `(1, b, d_inner)` for `out_proj`, the same way `GatedDeltaProduct._static_decode` does. Both transposes are views that PyTorch treats as contiguous, because they only move a size-1 dimension. So the change adds no copies, allocations, syncs or launches. At `b = 1` the computation is unchanged.
- **Shape check.** `ssm_decode` now asserts, when it gets no `batch_indices`, that the batch dimension equals the number of conv/SSM state slots. In that case request `i` uses slot `i`, so the counts must match. This makes the bug class fail loudly: a sequence-first input now raises instead of returning a correctly shaped wrong result. The check compares host-side shapes only, so it adds no sync and is CUDA-graph safe. Dynamic batching always passes `batch_indices`, so it never runs this check.

**Tests.**
- `tests/unit_tests/ssm/test_mamba_mixer.py::TestMambaMixer::test_static_decode_is_per_request[1|2]` runs one static decode step through `MambaMixer.forward`, starting from distinct per-request conv/SSM states in the static cache. It checks the output and every state slot against a reference: the same in/out projections around one single-request `ssm_decode` per state slot. Production and reference run the same GEMM shapes, so the fp32 comparison is tight (`1e-5`). `[2]` fails on `main` and passes with this PR.
- `TestMambaMixer::test_ssm_decode_is_batch_separable` checks that batch-first `ssm_decode` (the layout dynamic batching uses) equals one call per request.
- `TestMambaMixer::test_ssm_decode_rejects_sequence_first_input` checks that the new shape check rejects a `(1, b, proj)` input when there are `b` state slots.
- `tests/unit_tests/models/test_hybrid_model.py::TestHybridModel::test_static_batch_inference_matches_single_requests` runs a `HybridModel` (Mamba, attention and MLP layers) end to end:
  - a batch-2 static prefill, then two decode steps;
  - each request's logits must match its own batch-1 run.

  This also pins the static-batching plumbing above the mixer. The tolerance is `2e-2`. The two runs use different GEMM shapes, whose results agree to about `1e-3` relative on H100. A request decoded on another request's state is off by O(1).
- `tests/unit_tests/determinism/kernels/test_ssm_kernels.py::test_mixer_static_decode_replays` replays a 64-request static decode step bit-exactly. It is determinism coverage only. It is skipped only when `mamba_ssm` is missing: the mixer and its gated RMSNorm need it. The `ssm_mamba_mixer` manifest note mentions this test.

**GPU results.** On H100 in the CI image (first commit):
- The new tests fail on `main` in 1 of 4 cases: `test_static_decode_is_per_request[2]`, with request 1's output off by up to 1.31.
- They pass with this PR (4/4).
- The neighbor tests pass: `TestMambaMixer`, `TestHybridModel::test_inference` and `test_manifest.py`.

On H100 in the CI image (rerun at this PR's head), the regression tests pass (6/6) and 3 fail on `main`. The neighbor tests pass. On CPU, using `TRITON_INTERPRET=1` with a mixer built without TE:
- the shape-check test passes with this PR;
- it fails with the check removed;
- with the check but without the transposes, `test_static_decode_is_per_request[2]` now raises the shape assertion.
