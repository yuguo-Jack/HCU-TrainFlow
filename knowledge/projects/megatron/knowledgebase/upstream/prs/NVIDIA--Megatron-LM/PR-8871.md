# [Inference][MoE] Serve inference batches of any size from the fused shared expert

## Original PR description

# What does this PR do?

Makes `use_grouped_gemm_for_shared_expert` work in inference-optimized models. Before this change, the fused shared expert raised on any batch whose token count was not a multiple of 256, so decode steps and most CUDA-graph sizes crashed.

Stacked on #8566 (https://github.com/NVIDIA/Megatron-LM/pull/8566, `fix/d2-moe-glu-options`), whose interleave-aware GLU kernels it uses.

**Bug.** The flag is a `TransformerConfig` field with a CLI option, and nothing rejects it for `transformer_impl="inference_optimized"`. The inference MoE spec then builds `FusedSharedExpertMLP` (`_build_shared_experts`). Its forward always runs the TE `GroupedLinear(num_groups=1)` fused ops, which:

- raise unless the token count after TP communication is a multiple of `TE_GROUPED_GEMM_EXPERT_TOKEN_ALIGNMENT` (256). On H100, a 3-token decode batch raised `ValueError ... divisible by 256`;
- bypass the inference-optimized linears: their symmetric-memory collectives and inference weight formats (MXFP8). They also need an MXFP8 or NVFP4 recipe;
- run their collectives on the global TP group (`gather_from_sequence_parallel_region` and the others take no `group=`), not the module's `tp_group`.

A Transformer Engine model served with this flag (the dynamic and static engines set `InferenceMode`) hits the same fused ops, through the forward or, with `moe_shared_expert_overlap`, through the overlapped methods the `alltoall` and `flex` training dispatchers call.

Falling back to the unfused `SharedExpertMLP` in inference would be silently wrong. Whenever the flag is set, the checkpoint loader interleaves the shared FC1 rows in blocks of `moe_shared_expert_glu_interleave_size` (`glu_checkpointing.py`), and `MLP` would split those rows as `[gate | up]`.

## Fix

- Under `InferenceMode`, `FusedSharedExpertMLP` runs the module's own linears, in its forward and in the overlapped methods the `alltoall` and `flex` training dispatchers call (`linear_fc1_forward_and_act`, `linear_fc2_forward`; with `moe_shared_expert_overlap` the linears do not communicate, and `pre_forward_comm` / `post_forward_comm` do the TP collectives over the module's group). These linears accept any token count and communicate over the module's TP group (the inference-optimized ones through symmetric memory). Between them, the GLU kernel of the inference MoE (`bounded_silu_mul` with `GLUOptions`, from #8566) reads FC1's interleaved rows directly. It applies `activation_func_clamp_value` and no linear offset, as the fused ops' `ScaledSwiGLU` / `ScaledClampedQGeGLU` do. The FC1 layout and the activation are the ones the model was trained with, so checkpoints and refit need no change.
- The numerics are not bit-identical to training. The fused ops run only under an MXFP8 or NVFP4 recipe (`_get_fused_grouped_swiglu_recipe` raises otherwise) and quantize FC1's input and the SwiGLU output. Inference runs the model's linears (BF16, MCore MXFP8 or, for a Transformer Engine model, the TE recipe) with an FP32 SwiGLU rounded once to BF16. Inference matches training to quantization error. Before this change, inference with the flag did not run at all.
- Training and RL logprob passes (`InferenceMode` inactive) keep the fused ops. Their four collectives now pass `group=self.tp_group`.
- `bounded_silu_mul` (from #8566) gains an entry without a device row bound (`n_rows=None`, every row live), so the shared expert allocates nothing per call, and it launches a fixed grid, so a row count that changes every step does not compile a new kernel variant. The routed vLLM path's results are unchanged (the kernel is elementwise).
- No host sync, no per-call allocation; CUDA-graph capturable.

## Tests

- `tests/unit_tests/transformer/moe/test_shared_experts.py::TestFusedSharedExpertInference` (1 GPU, H100; TE >= 2.14 and, for the clamp cases, TE's `ScaledClampedQGeGLU`, both in the CI image; a missing one fails rather than skips). `test_fused_shared_expert_serves_any_token_count[impl, tokens 3|257, clamp None|0.5]` runs the fused shared expert under `InferenceMode` from the inference-optimized MoE spec, from the Transformer Engine spec, and from the Transformer Engine spec through the overlapped methods. Each must match the unfused `SharedExpertMLP` of the same spec holding the same weights as checkpoints store them: `[gate | up]`, converted with the checkpoint loader's own permutation (`glu_checkpointing._permute_glu_rows`). The reference therefore does not share the fused path's reading of the interleaved rows. Reading those rows as `[gate | up]` must differ by more than 0.2. On the base branch every case raises the divisible-by-256 `ValueError`.
- `TestFusedSharedExpertInferenceMatchesTraining::test_inference_matches_fused_training_ops[tp 1|2, clamp None|0.5]` (Blackwell, `launch_on_gb200`, 2 GPUs): one Transformer Engine shared expert runs its training ops (TE's GroupedLinear and scaled GLU, MXFP8; fused into TE's grouped MLP only when TE registers it) and its inference path (the same TE linears under the same MXFP8 recipe, with the GLU kernel) on the same weights at 256 tokens. They must agree to 5e-2, while reading FC1 as `[gate | up]` or dropping the clamp must differ by more than 0.5. TP 2 runs sequence parallel, so each rank interleaves its own FC1 shard. This pins TE's interleaved block order and `ScaledClampedQGeGLU(alpha=1.0, limit)` clamp to what the GLU kernel computes.
- `test_fused_grouped_swiglu_forward_communicates_over_own_tp_group[sp False|True]` (CPU): the fused path's collectives receive the module's TP group. Fails on the base branch.
- Determinism: `tests/unit_tests/determinism/kernels/test_moe_kernels.py::TestMoEModules::test_fused_shared_expert_inference_replays[forward|overlapped]` (1 GPU) replays the inference path bit-exactly at 333 tokens. `shared_experts.py` is registered with that test instead of its old exemption ("no kernel of its own", no longer true). `test_inference_kernels.py` replays the unbounded `bounded_silu_mul`. `tools/check_kernel_determinism_coverage.py --base-ref origin/main` passes.

Checked on CPU under the Triton interpreter: the overlapped inference methods give the forward's output bit for bit and match the checkpoint-layout SwiGLU (rel. err 2.8e-3); the unbounded and bounded kernel entries agree.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), the H100 regression tests (`TestFusedSharedExpertInference`, the TP-group test and the two replays) pass (16 cases). On `main` with #8566 merged in, all 16 fail: the token-count cases and both replays raise the divisible-by-256 `ValueError`, and the fused path's collectives get no group. The neighbor tests (the rest of `test_shared_experts.py`, `test_inference_kernels.py::test_inference_moe_activations_replay`, `test_moe_dispatching_and_routing.py::TestInferenceGroupedMLPMatchesTraining`) pass (70 cases, 6 skipped).

On GB200 in the CI image (`mcore_ci_dev:main`, aarch64, 2026-11-02), `TestFusedSharedExpertInferenceMatchesTraining` passes on 2 GPUs (4 cases: TP 1 and 2, clamp None and 0.5). The image does not set `NVTE_CUTEDSL_FUSED_GROUPED_MLP`, so the training side ran TE's unfused ops. On `main` with #8566 merged in, all 4 cases fail because that base has no `FusedSharedExpertMLP._inference_glu_options`, which the test reads. The measured errors are not logged, so the margin to the 5e-2 tolerance is not known.

## Merge order

Merge after #8566 (`fix/d2-moe-glu-options`, which this branch is stacked on, up to its latest commit) and after the #8870 PR (`fix/fused-shared-expert-unfused-scale`), which this branch merges. #8870 makes the fused shared expert's training path run when TE does not fuse its grouped MLP. That is how GB200 CI runs `TestFusedSharedExpertInferenceMatchesTraining`: without `NVTE_CUTEDSL_FUSED_GROUPED_MLP` at TE import, so on TE's unfused ops. Before #8870 that path raised TE's "one scale per input row" assertion. #8870's own test covers the fused TE path. Because #8870 is based on a newer `main`, this branch now also contains `main` up to `a0ef64615`. Until #8566 merges `main` again, a diff against #8566 also shows those `main` commits.
