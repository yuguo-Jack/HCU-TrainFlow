# Add NeMo-RL adapter test foundation

## What does this PR do?

This PR adds test-only coverage for the way NeMo-RL uses Megatron Core's dynamic inference engine. Each test sends the same prompts twice: once straight to the engine, and once through NeMo-RL's real Megatron generation adapter. The two runs must give the same tokens and scores, and runtime checks confirm that the feature under test actually ran.

The foundation adds:

- a shared harness that loads NeMo-RL from the checkout named by `NEMO_RL_SOURCE`, builds engines, runs both paths and compares them;
- 15 direct-versus-adapter feature cases on one GPU;
- two standalone adapter checks: sampling distribution and row attribution for asynchronous requests;
- six parallel-layout cases, which need at least two GPUs.

This PR used to carry a fix to the shared test helper `test_utilities.py`, so tests can restore PyTorch backend flags after determinism tests have locked them. Main now has that fix (NVIDIA/Megatron-LM#7575), so this PR no longer changes the file.

Without `NEMO_RL_SOURCE`, the adapter tests skip, so ordinary Megatron CI is unaffected. There are no production changes.

The tests also run under a multi-rank launch, such as CI's eight-rank one:

- **One-GPU cases:** every rank runs its own engine. NeMo-RL's adapter only lets rank 0 submit requests, so each rank submits as rank 0 of its own one-rank deployment.
- **Parallel-layout cases:** these use every rank, adding data-parallel replicas of the layout.
- **MXFP8 case:** skips below SM100, because Transformer Engine cannot dequantize MXFP8 parameters there.

## How was the test matrix determined?

NeMo-RL drives Megatron inference during reinforcement-learning training: it generates samples, updates the weights, and generates again. Megatron had no tests that run this caller, so a difference between a direct engine call and the adapter's call could go unnoticed.

The matrix has three layers:

1. **Feature cases** cover the engine settings NeMo-RL users turn on: model families, layer implementations, quantization, prefix caching, CUDA graphs, speculative decoding (MTP), sampling settings and fused RoPE.
2. **Standalone adapter checks** cover adapter behavior that has no direct-engine equivalent: how sampling settings are passed down, and which reply belongs to which prompt.
3. **Parallel-layout cases** cover two-way tensor, sequence, pipeline, data and expert-tensor parallelism. A larger launch repeats each layout as data-parallel replicas.

This is **differential coverage**: each feature case compares the direct and adapter paths with the feature on in both. It does not test every pair of features. Cases that need a production fix are in that fix's PR, and cases that need several fixes are in the series' tests PR.

## How are results checked?

For each feature case, the direct and adapter runs must have identical generated token IDs and log probabilities. Greedy requests use FlashInfer top-k 1 sampling. That sampler breaks exact ties for the top logit with the sampling RNG, so the adapter run restarts from the direct run's RNG state. The adapter output must also keep the prompt, report the right lengths, pad with zeros, and release every request.

Each case also checks that its feature ran on the compared requests:

- prefix caching records cache hits and frees its blocks;
- CUDA graphs replay;
- MTP proposes speculative tokens;
- fused RoPE calls the FlashInfer kernel;
- FP8 and MXFP8 use the expected quantization recipe;
- processed log probabilities come from the expected logits rows.

The hybrid-layer counter also counts the direct run, so it is not claimed as proof that the adapter run used those layers.

The sampling check compares the adapter's sampling settings and token frequencies with the expected distribution. The asynchronous check requires each reply's tokens and scores to match its own prompt. Each parallel case runs on every rank. It checks completion, reply order and per-replica seeds, and requires every rank to run the adapter's requests.

## Scope

This PR changes one test file: it adds `test_nemo_rl_adapter_contract.py` (+887 net unit-test lines). It has no production, functional-test, configuration, recipe or golden changes.

The adapter tests need a NeMo-RL checkout. They were validated with NeMo-RL `b2de3de156167b6ad7fc7d01dba72944991c8b60` plus the three NeMo-RL Megatron fixes in this series: lmcafee-nvidia/RL#1 (stop token IDs), lmcafee-nvidia/RL#2 (truncation) and lmcafee-nvidia/RL#3 (reply validation). Those drafts are the review records; separate landing PRs to `NVIDIA-NeMo/RL` will follow.

The production fixes found with this foundation are separate PRs on `lmcafee-nvidia/Megatron-LM`, each based on this one: lmcafee-nvidia/Megatron-LM#124, lmcafee-nvidia/Megatron-LM#135, lmcafee-nvidia/Megatron-LM#136, lmcafee-nvidia/Megatron-LM#137, lmcafee-nvidia/Megatron-LM#138, lmcafee-nvidia/Megatron-LM#139, lmcafee-nvidia/Megatron-LM#140, lmcafee-nvidia/Megatron-LM#141, lmcafee-nvidia/Megatron-LM#142. The end-to-end adapter tests that need several of them are in lmcafee-nvidia/Megatron-LM#143.

Changes since the previous head `701a70328f1da9ed606d3efbe2d7f65e4c8b7883` let the module run under multi-rank launches. That earlier head failed most of its cases under an eight-rank launch:
- the one-GPU cases now submit through the adapter as rank 0 on every rank;
- the parallel-layout cases now run on any launch size their layout divides, not only on exactly two GPUs;
- the MXFP8 case now skips below SM100;
- the feature cases and the asynchronous check now replay the direct run's sampling-RNG state for the adapter run. Without that, the MLA latent-cache and small-head fused-RoPE rows disagreed on ranks where an exact top-logit tie drew a different token. Each rank offsets the sampling seed by its data-parallel rank.
