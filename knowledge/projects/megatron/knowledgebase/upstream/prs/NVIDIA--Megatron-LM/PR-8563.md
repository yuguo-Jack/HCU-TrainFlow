# [Inference][MoE][MTP] Refresh MoE dispatcher metadata in MTP forwards instead of reusing the main forward's

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8563) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes every MTP-layer forward refresh the inference MoE dispatcher metadata (valid-token count and EP token layout) for its own rows, and take the NCCL EP dispatch path that matches how it runs (eager or graphed). It also bounds the four fused-MoE kernels that trusted that count by the routing-map rows.

## Issue tracking

Linked issue: none; this PR's regression tests reproduce the bug.

**Bug.** The inference MoE dispatchers share per-forward metadata:
- the valid-token count the experts read, and its host estimate;
- at EP > 1, the per-rank token layout: NVLS `rank_token_offset` / `ep_max_tokens`, NCCL per-rank counts.

`set_moe_metadata_sync` let only the first MoE layer of the module walk refresh it. That layer is in the decoder, which is registered before `mtp`. Speculative decoding runs each MTP layer as a forward of its own, on request-shaped rows: the draft depths, the draft-KV commit pass, and the EP dummy passes. So the MTP layers' MoE reused the main forward's larger metadata.

Affected: MoE in both the decoder and the MTP head, with `num_speculative_tokens >= 1`.
- **EP=1 (both dispatchers) and NCCL EP > 1.** The experts read the main forward's count.
  - `_count_local_tokens_kernel` (and its persistent variant) and the vLLM align scatter read pairs past `routing_map`.
  - Permute offsets and `n_used` are inflated.
  - `_moe_sum_kernel` writes output rows past its output tensor.
  - Reproduced on H100: a real `GPTModel` MTP layer ran 4 rows but read `valid_tokens=16`. With 6 rows and a count of 10, `vllm_fused_moe` stored rows 6-9 past a 6-row output.
- **NVLS EP > 1.** The all-gather-v and reduce-scatter-v place the MTP rows at the main forward's offsets, and the experts also process the stale rows left by the previous layer.
  - The GPU run showed metadata `[14, ...]` instead of `[5, ...]`: wasted expert work, but no read past the real rows.
  - A fix that refreshed only `valid_tokens` would turn this into wrong outputs, so the count and the layout must be refreshed together.
- **NCCL EP > 1, eager steps.** Pad/compact use the main forward's per-rank counts, so the combine returns the wrong number of rows (on H100: `shape '[5, 1, 64]' is invalid for input of size 512`).
- **NCCL EP > 1, graphed steps (found in review, by reading).** The step's dispatch path follows the main forward, so the eager draft-KV commit pass, whose row count differs per rank (a real commit on one rank, a 1-row dummy on another), runs the fixed-count all-gather. That all-gather then mismatches across ranks.

**Root cause.** The metadata describes one forward pass, but it was refreshed once per model step. Likewise, the NCCL dispatcher's choice between its fixed-count (graphable) and variable-count paths followed the step, not the forward.

**Fix.**
- `set_moe_metadata_sync` now flags the first MoE layer of each forward: the main forward and every `MultiTokenPredictionLayer`. A layer without an inference dispatcher does not use up its forward's refresh.
- `update_metadata` therefore runs inside every MTP forward, at the point where the row count changes. It refreshes the count, its host estimate and the EP layout together, and for FlashInfer the `-1` routing fill too.
- It is captured in the MTP CUDA graphs like the decoder's refresh: no host sync on the graphed path, no new allocation.
- MTP forwards already run in lockstep on every EP rank (the dummy passes exist for the MoE collectives), so the extra metadata collective is matched.
- Cost per MTP-layer forward: one `fill_` (EP=1, NCCL graphed), or one single-CTA metadata kernel (NVLS EP > 1). The eager NCCL EP > 1 path adds the same count all-gather the main forward already does, which its pad/compact needs.
- The context now selects the NCCL EP dispatch path per forward (`_select_nccl_ep_dispatch_path`): fixed-count when the forward is graphed (EP-synced, equal counts), variable-count when it is eager. It is called where each forward's CUDA-graph flag is published: the main step, every MTP forward (`_mtp_activate_attn_metadata`), and the restore in `_mtp_forward_phase`. So the eager commit pass and its dummy take the variable-count path on every rank, and graphed draft depths take the fixed-count path again.
- Defense in depth: `_count_local_tokens_kernel`, `_count_local_tokens_kernel_persistent`, `_scatter_token_indices_kernel` and `_moe_sum_kernel` now bound their work by the routing-map rows. `_permute_tokens_kernel` and the other `valid_tokens`-gated kernels already did this. Nothing changes when the count is at most the rows. The new bounds are `do_not_specialize`, so new row counts do not compile new kernel variants.

**Test.**
- `tests/unit_tests/inference/test_moe_dispatching_and_routing.py::TestMTPDispatcherMetadata` (TE, 1+ GPUs):
  - It builds a `GPTModel` with MoE in its 2 decoder layers and 2 MTP layers, and applies the real `set_moe_metadata_sync`.
  - `test_first_moe_layer_of_each_forward_syncs_metadata` checks the flags: one per forward.
  - `test_mtp_forwards_see_their_own_metadata[{nccl,nvls}-{ep1,ep_world}]` runs a main forward (8/6 tokens per rank), then the MTP layer-0 forward (5/4 rows) and the MTP layer-1 forward (3/2 rows) through the model's real dispatchers, with identity experts.
  - For every MoE layer it checks the valid-token count, the NVLS step metadata, the gathered rows and the combined output.
  - `test_mtp_forward_refreshes_metadata_eager_and_graphed[{nccl,nvls}-{ep1,ep_world}]` runs real `compute_mtp_single_step` forwards (embedding, attention, router, dispatcher) after a main MoE forward, with the experts recording the count they receive. It runs them eagerly for both MTP layers, then captures MTP depth 0 in a CUDA graph and replays it after another main forward.
  - On main the MTP layers read the main forward's count (EP=1), the NVLS step metadata is stale, and the NCCL eager combine fails.
- `tests/unit_tests/inference/contexts/test_dynamic_context_mtp_kv_cache.py::TestMtpMainExecutionState::test_mtp_forwards_select_their_own_nccl_ep_dispatch_path`: on a graphed NCCL EP step, the commit pass and the EP dummy select the variable-count path, graphed draft depths select the fixed-count path, and leaving the MTP phase restores the step's path.
- `tests/unit_tests/inference/test_inference_utils.py::TestInferenceUtils::test_metadata_sync_goes_to_the_first_layer_with_an_inference_dispatcher` (CPU).
- Kernel tests pass a count above the routing-map rows, with the routing map and output as views of larger buffers, so nothing leaves an allocation on main:
  - `test_moe_permute.py`: `TestComputeLocalTokensPerExpert` / `TestPermuteTokens::test_valid_tokens_past_routing_map_rows`;
  - `test_vllm_fused_moe.py`: `TestMoeAlignBlockSize::test_valid_tokens_past_routing_map_rows` and `TestVllmFusedMoe::test_valid_tokens_past_input_rows` (no store past the output).
  - All fail on main and pass with the fix.
- Determinism: `test_inference_kernels.py::test_vllm_fused_moe_clamps_valid_tokens_to_rows_replay` replays the clamped `vllm_fused_moe` path bit-exactly and checks it equals the `valid_tokens == rows` result. The `inference_moe_kernels` manifest entry already covers both kernel files and this test, so `manifest.py` is unchanged. `tools/check_kernel_determinism_coverage.py --base-ref origin/main` passes.

## Follow-up: merged main

- Merged `main` (a0ef64615), keeping both appended tests in `test_inference_kernels.py`. The production changes merged without conflicts.
- #4743 renamed the `ep_group` argument of `NVLSAllGatherVDispatcher.allocate_buffers` to `tp_ep_group`, so the `nvls-ep_world` cases of `TestMTPDispatcherMetadata` failed with a `TypeError`. The test helper now passes `tp_ep_group`, as the other dispatcher tests do. Expert tensor parallelism is 1 in these tests, so the group is still the EP group.
- On `main` the 2-GPU run of these tests hung after the last test had failed. When `test_mtp_forward_refreshes_metadata_eager_and_graphed` fails, the failed test's frames keep its CUDA graph alive. If that graph captured an NCCL collective, destroying the communicator in the session teardown waits for the graph and never returns. The test now asserts on the eager MTP forwards before it captures, so on `main` it fails before any capture. It also resets the graph before it asserts on the replay.
