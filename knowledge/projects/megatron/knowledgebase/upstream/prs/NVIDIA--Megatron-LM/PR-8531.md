# Detect batch-size schedule steps by global batch size

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8531) · state: closed · merged: True

## Original PR description

## Summary

With `--step-batch-size-schedule` and `--save` set, the training loop saves a checkpoint and exits when the global batch size steps up, so the run can be relaunched at the new size. It detected the step only when the number of microbatches changed. The unchecked update rounds that number down, so a new global batch size that the data-parallel size does not divide left it unchanged: 8192 → 12288 at `micro_batch_size` 1 and data-parallel size 8192 gives 1 microbatch both before and after. The step went undetected, and the consistency check right after it crashed the job without saving:

```
AssertionError: current global batch size (12288) is not divisible by micro_batch_size (1) * data_parallel_size (8192)
```

With a step batch-size schedule set, the loop now also tracks the global batch size and treats a change in either value as a step. The comparison is limited to the schedule because RL without sequence packing resizes the global batch every step. The "should not decrease" assertion checks the global batch size instead of the number of microbatches. The RL sequence-packing path, which skips the save, is unchanged.

On relaunch, the load-time consistency check still rejects a configuration whose `micro_batch_size × data_parallel_size` does not divide the new batch size.

## Testing

Not run. The path is exercised only by a training run that crosses a schedule step; the change is confined to the step-detection condition in `train()`.

This bug fix adds no regression test. Removing the new comparison would therefore leave those assertions passing while restoring the reported failure: an unchanged rounded microbatch count reaches consistency validation without saving.

Add a focused mocked `train()` test under the [training unit-test directory](https://github.com/NVIDIA/Megatron-LM/tree/f7902b8ed8926d2e89ad5b5a27a26ed2f7260580/tests/unit_tests/training), using `run_config` and monkeypatch conventions. Minimal setup: microbatch size 1, logical DP size 8, sequence length 1, schedule `0:8 8:12`; initialize the calculator at batch size 8, then enter the loop at completed iteration 1 with 8 consumed samples, saving enabled and packing disabled. Exercise the production branch, not a copied predicate. Assert exactly one checkpoint at iteration 1, exit before another `train_step`, and no checked update at batch size 12. The [base condition](https://github.com/NVIDIA/Megatron-LM/blob/e3f528380c197e8811fb68064d9ef3acf59fd3c6/megatron/training/training.py#L5114-L5152) should fail this test.

Preservation checks should distinguish these cases: divisible scheduled growth `8 → 16` still saves/exits; invalid `8 → 12` without saving still raises the divisibility assertion without checkpointing; iteration zero does not automatically save; an unscheduled RL global-size-only change with unchanged microbatch count does not save; sequence packing bypasses automatic saving and the monotonic assertion when its microbatch count decreases. Retain the existing calculator assertions accepting undersized past entries and rejecting an invalid current entry.

These are proposed tests, not executed results. The surrounding mocked-loop harness needs author integration; its invariant should explicitly protect both transition detection and saving before validation or further training.
