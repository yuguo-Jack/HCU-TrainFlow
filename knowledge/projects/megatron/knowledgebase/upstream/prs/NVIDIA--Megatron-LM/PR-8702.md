# What does this PR do?

Fixes dynamic-batching MLA (`cache_mla_latents=True`) with tensor and sequence parallelism, and, under per-tensor FP8 recipes, stops a request's keys and values from depending on the rest of the latent pool (see the follow-up section). Before this fix, every forward with tensor and sequence parallelism crashed:

```
RuntimeError: Sizes of tensors must match except in dimension 2. Expected size 192 but got size 384 for tensor number 1 in the list.
```

at `kv_cached = torch.cat([kv_compressed, k_pos_emb_squeezed], dim=-1)` in `qkv_up_proj_and_rope_apply_for_cached_latent_kv`. The two sizes are the step's tokens on this rank (`s / TP`) and in all (`s`), so they vary with the step: 192 vs 384 and 256 vs 512 in the configuration matrix below, 64 vs 128 in this PR's test.

**Affected.** Dynamic-inference MLA with TP > 1 and sequence parallelism. The inference-optimized layers require sequence parallelism at TP > 1, so this covers every inference-optimized MLA model at TP > 1. Runs at TP > 1 without sequence parallelism (`transformer_impl="transformer_engine"`) are not affected. It crashes on the first forward (CUDA-graph warmup, or the first step without CUDA graphs), in prefill, mixed and decode steps alike. On H100, all six TP=2 MLA rows of a dynamic-inference configuration matrix failed this way (dense and MoE, with and without CUDA graphs, NVLS and NCCL).

**Root cause.** The latent KV cache stores every token's latent (`kv_lora_rank + qk_pos_emb_head_dim`) on each TP rank. Latents are shared by all heads, so they are not split across ranks (`DynamicInferenceContext` sizes the cache that way). Under sequence parallelism, `get_query_key_value_tensors` still treated `kv_compressed` as it does without latent caching:
- With the duplicated (`TELinear`) down-projection, the output is split along the sequence. Only `k_pos_emb` was gathered, and `kv_compressed` stayed at `[s / TP]`. Without latent caching that is right, because the column-parallel `linear_kv_up_proj` gathers its input. The cached-latent path has no such projection, so it concatenated `[s / TP]` latents with `[s]` RoPE keys.
- With a column-parallel down-projection, the code had the whole sequence but scattered `kv_compressed` back to `[s / TP]`, with the same result.
- Behind that crash, by reading the code: prefill and mixed steps read the cache back by running `linear_kv_up_proj_linear`, the column-parallel linear that `prepare_for_absorption` splits from `linear_kv_up_proj`. That module all-gathers its input along the sequence: the split `TEColumnParallelLinear` because it inherits `sequence_parallel=True`, and the `InferenceColumnParallelLinear` that #8570 reuses there because it always gathers at TP > 1. With a replicated cache, that gather is wrong.

**Fix** (`megatron/core/transformer/multi_latent_attention.py`):
- When caching latents with sequence parallelism, `get_query_key_value_tensors` all-gathers the down-projection output (latent and RoPE parts) along the sequence once, before splitting it. This replaces the `k_pos_emb`-only gather. After a column-parallel down-projection, it no longer scatters `kv_compressed`; the gather and scatter in that branch now use the layer's TP group (`self.tp_group`) instead of the global one. Every rank then appends the same whole latents to its cache, and the query (already gathered by `linear_q_up_proj`) covers the same tokens.
- A new method, `MLASelfAttention.up_project_whole_latents`, up-projects latents that every TP rank holds in full. It runs one local GEMM on this rank's column shard of the KV up-projection weight (`linear_kv_up_proj_linear.weight`), so it never communicates, whatever module `linear_kv_up_proj_linear` is. `uncompress_kv_from_cache` uses it instead of running that module.
- As in the absorbed decode path (`up_k_weight`, `up_v_weight`), the GEMM runs in high precision: quantized (FP8 or MXFP8) weight storage is dequantized, and the cache is not quantized. Inside an FP8 autocast, the prefill up-projection of the cache therefore no longer runs in FP8, as the split TE linear would; it now matches decode.
- Both the absorbed decode path (FlashMLA) and the unabsorbed path now get whole latents. The unabsorbed path covers prefill, mixed steps, and decode in batch-invariant mode with #8571.
- The cached path still issues one all-gather per layer, now of the whole latent instead of its RoPE part. It goes through `torch.distributed` as before, not through the inference symmetric-memory buffer. The cache up-projection issues none. There are no new host syncs, so the path stays CUDA-graph safe.
- The all-gather is exact, so batch-invariant results are unchanged. `kv_layernorm` now normalizes the whole sequence on every rank, as it does at TP=1.
- The paths without latent caching (training, static batching) are unchanged.

**Tests** (`tests/unit_tests/transformer/test_multi_latent_attention.py`, `TestSequenceParallelMLALatentCache`, 2 GPUs):
- Setup: an MLA layer of the GPT inference spec at TP=2 with sequence parallelism, and a real `DynamicInferenceContext` with one 100-token request in 64-token blocks.
  - The attention kernel `flash_decode_and_prefill` is stubbed to capture its inputs, so neither FlashAttention nor FlashMLA is needed.
  - Parametrized over a duplicated and a column-parallel down-projection, and over the KV-norm mode: fused into `linear_kv_up_proj` (split by `prepare_for_absorption`), or disabled (`linear_kv_up_proj` is an `InferenceColumnParallelLinear`).
  - The disabled cases are skipped on this branch. Without #8570, `prepare_for_absorption` fails on an up-projection without a fused norm, since it tries to split off a norm that is not there.
- `test_prefill_up_projects_whole_cached_latents` checks a prefill step:
  - Each rank caches every token's latent, identical on both ranks.
  - The latent part matches the normalized KV down-projection of the token's hidden state.
  - The query covers every token.
  - The keys and values cover every cache slot and equal this rank's heads of the up-projected cached latents.
- `test_decode_absorbs_every_token` checks a decode-only step after the prefill:
  - It caches the new token's latent the same way.
  - It builds the absorbed query (`kv_lora_rank + qk_pos_emb_head_dim` per head) for every token.
- On H100 in the CI image, the four fused-norm cases fail on main, each with `Expected size 64 but got size 128` at the `torch.cat` above, and pass with this PR's first commit. The neighbor tests `TestSequenceParallelMLAAttention`, `TestTensorParallelMLAAttention` and `TestParallelMLAAttention` pass (one existing rope skip). With the review-fix commit (dfw 21004395): the 4 fused-norm cases pass and fail on `main` as before, the 4 non-fused cases skip (they need #8570), and the neighbors pass. On an integration tree of current `main` with #8570 and every other open fix (dfw 21007037), all 8 cases pass, including the non-fused ones. The 57-task inference-vs-training matrix passes on integration trees of current `main` with every open fix (dfw 21004395, 21007036).

**Label.** Needs `determinism-exempt`. The kernel determinism gate flags `multi_latent_attention.py`, which is registered for its RoPE kernel dispatch (`mla_rope_dispatch`). This PR changes no kernel or dispatch: it changes which tensor is all-gathered, and runs the cache up-projection as a plain `torch` GEMM instead of through a TE linear.

**Related PRs.**
- Composes with #8571, where batch-invariant MLA decode takes the unabsorbed path; this PR makes that path work at TP > 1.
- Composes with #8570 (DSA and latent-cache absorption) in either merge order. #8570 lets `prepare_for_absorption` keep an up-projection without a fused KV norm as `linear_kv_up_proj_linear`; under the inference spec, that is an `InferenceColumnParallelLinear`, which gathers its input at TP > 1. This PR never runs that module on the cache: it uses only its weight, in a local GEMM. With both merged, the cache up-projection is local for every KV-norm mode.
- The production code merges cleanly with both, and the test file conflicts on one import line. Whichever of this PR and #8570 lands second should drop the skip on the disabled-KV-norm cases of `TestSequenceParallelMLALatentCache`, which then cover that combination at TP=2 (#8570's own tests run at TP=1).

## Follow-up: FP8 no longer couples a request's keys and values to the rest of the latent pool

This PR also fixes a second defect, found in review and reproduced on H100. It now claims it and pins it with a test.

- **Bug.** Prefill and mixed steps up-project the layer's whole latent pool, including unused, freed and never-written blocks (the pool is `torch.empty`). On `main` that ran through `linear_kv_up_proj_linear`, a TE linear, inside the layer's FP8 autocast. Tensorwise current scaling takes one scale over the whole input, so a request's keys and values depended on what every other block held. On H100 under tensorwise FP8, filling five unused blocks with 1e4 or Inf moved the used rows' values by up to 0.033 (dfw 21197274), and the test below fails on `main` in exactly those cases. NaN did not move them, because TE's amax skips NaN. Under delayed scaling the same fills did not move the used rows on `main` (the test's delayed-scaling cases pass there), so the defect is not shown for that recipe. NVFP4's global scale was not tested. MXFP8 and FP8 blockwise scale per row and are not affected.
- **Fix.** Already in this PR: `up_project_whole_latents` is a high-precision GEMM on the dequantized weight and never quantizes the latents, so each row of the result depends only on its own latent.
- **Test.** `tests/unit_tests/transformer/test_multi_latent_attention.py::TestMLALatentPoolUpProjection::test_used_blocks_ignore_unused_blocks` (1 GPU, TE; the FP8 cases skip without FP8 support). It runs `uncompress_kv_from_cache` on an 8-block pool with 3 used blocks, inside the layer's FP8 context, after `prepare_for_absorption`. The used blocks' keys and values must be bitwise unchanged when the unused blocks hold 1e4, Inf or NaN instead of 0. It runs under bf16, tensorwise FP8 and delayed FP8, and checks that FP8 autocast is active. Delayed scaling quantizes with a scale derived from earlier calls' amax, so each fill gets a fresh layer with the same weights (the same amax history) and up-projects the pool twice: the second step uses the scale that the first step's amax set. On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), all nine cases pass with this PR. On `main`, the tensorwise FP8 cases with 1e4 and Inf fail and the other seven pass. The delayed-scaling cases also pass on `main`, so this test does not reproduce the coupling under delayed scaling; for that recipe it only guards the fix.
- **Results at this head** (same run). `TestSequenceParallelMLALatentCache` on 2 GPUs: the 4 fused-norm cases pass and fail on `main` with `Expected size 64 but got size 128`; the 4 disabled-KV-norm cases skip, as they need #8570. The neighbor tests `TestSequenceParallelMLAAttention`, `TestTensorParallelMLAAttention` and `TestParallelMLAAttention` pass (27 cases, 1 skipped).
- **#8703 (n7)** is stacked on this PR and merges its branch, so it carries `up_project_whole_latents` and adds a second caller: the context-free MTP draft step, which up-projects that step's own latents, so it does not quantize them either. The two compose: n7 contains this PR's earlier commits, and this test commit merges into n7's branch cleanly. Once this PR lands, n7's diff loses the shared change.
