# test: add standalone MXFP8 coverage foundation

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8491) · state: open · merged: False

## Original PR description

## What does this PR do?

This PR adds a test-only foundation for standalone MXFP8 inference. Each production fix in this series builds on it. It provides:
- independent reference helpers that the dependent fix PRs use for their byte-exact storage and rounding regressions;
- tests of GEMM execution, bounded MoE decode and engine scheduling, all running on unmodified production code.

The foundation adds:

- `tests/unit_tests/inference/test_mxfp8_contract.py`:
  - **Reference helpers** for the MXFP8 rounding rule (`_reference_quantize`), the cuBLAS swizzled scale layout (`_swizzle_scales`), a scale-byte decoder (`_logical_scale_bytes`) and a boundary-value input generator (`_boundary_input`). They don't call the code under test. In this PR, only the GEMM test uses `_logical_scale_bytes`. The other helpers exist for the dependent fix PRs, which add the byte-exact cases.
  - **A direct linear test** that runs the real activation quantizer and the selected GEMM (Torch `scaled_mm` or FlashInfer) on identical values.
  - **A two-rank linear test** with tensor and sequence parallelism, which runs the production column- and row-parallel MXFP8 linears in one step.
- three bounded-decode tests in `tests/unit_tests/inference/test_flashinfer_mxfp8.py`. They check that:
  - the controller enables bounded rows only for safe decode steps;
  - the expert layer forwards that policy and its FP32 output buffer to the routed kernel;
  - the kernel writes only the live rows.
- a refactor in the same file: the routed-weight preparation helper moves from inside the existing `test_flashinfer_routed_mxfp8_is_batch_invariant` to module level, as `_prepare_routed_mxfp8_weight`, so the new bounded-execution test can reuse it. The existing test is otherwise unchanged.
- an engine test in `tests/unit_tests/inference/engines/test_dynamic_engine_parallel_and_chunked_prefill.py`, in which asynchronous scheduling, chunked prefill and prefix reuse all run on the same engine steps as routed MXFP8 MoE;
- MXFP8 options for the shared dynamic-engine test configuration in `tests/unit_tests/inference/engines/test_dynamic_engine.py`. Only MXFP8 configurations select the FlashInfer grouped-GEMM backend; every other configuration keeps the default.

## How was the test matrix determined?

An audit of MXFP8 inference coverage on main found three gaps:
- MXFP8 storage and rounding had no independent reference;
- the bounded-row decode policy was untested from controller to kernel;
- no test ran MXFP8 MoE together with the scheduler features it shares engine steps with.

This PR covers the second and third gaps directly. For the first, it provides the reference helpers; each dependent fix PR adds the byte-exact cases for the behavior it corrects, because those cases fail on unmodified production.

The tests in this PR form three layers:

1. **GEMM execution:** each supported backend checked against a dequantized-matmul reference, plus one parallel linear step.
2. **Bounded decode:** the policy traced from the controller, through the expert layer, into the routed kernel.
3. **Engine interaction:** one run with every scheduler feature that shares an engine step with routed MXFP8 MoE.

This is targeted coverage of interaction boundaries, not a cross-product of every MXFP8 option.

## What combinations are tested?

### GEMM execution (3 cases)

| Case | Configuration | Check |
| --- | --- | --- |
| `torch-scaled-mm` | Real activation quantizer and the Torch `scaled_mm` MXFP8 GEMM | Output close to a dequantized FP32 matmul under a BF16 bound. The GEMM writes into a preallocated buffer and leaves its NaN-filled tail untouched. |
| `flashinfer` | Real activation quantizer and the FlashInfer MXFP8 GEMM | The same checks |
| TP/SP linear | Two ranks, tensor parallel 2 with sequence parallel, production column- and row-parallel MXFP8 linears | Both linears quantize and dispatch once, and each rank's output matches a quantized reference |

### Bounded decode policy (6 cases)

| Case | Setup | Expected |
| --- | --- | --- |
| Controller, decode step, capacity 32 | Decode-only step whose worst-case row count fits the capacity | Bounded rows on |
| Controller, decode step, capacity 31 | Decode-only step one row short of its worst-case row count | Bounded rows off |
| Controller, prefill step, capacity 32 | Step that includes prefill | Bounded rows off |
| Controller, decode step, no capacity | Bounded mode not configured | Bounded rows off |
| Expert hand-off | Expert layer with bounded rows enabled and an FP32 NVLS-shaped buffer | Routed kernel receives the policy, buffer, capacity and expert offsets |
| Bounded execution | FlashInfer routed MXFP8 on 37 live rows of a 128-row, NaN-filled FP32 buffer | Live rows equal the unbounded result exactly, and rows past capacity stay NaN |

### Engine interaction (1 case)

| Case | Configuration | Check |
| --- | --- | --- |
| Async, chunked prefill and prefix reuse with routed MXFP8 | Four expert-parallel ranks, MoE layers with MXFP8 parameters and the FlashInfer routed backend, asynchronous scheduling, chunked prefill, two requests generating 4 tokens each. Runs once with prefix caching off and once with it on. | With prefix caching on, routed MXFP8 runs during the asynchronous forward while one request is still in chunked prefill, and the cache records hits and skipped prefill tokens. Generated tokens match the prefix-caching-off run exactly. |

## How are results checked?

- **GEMMs:** output compared with a dequantized FP32 reference under an explicit BF16 error bound. A NaN-filled output buffer tail proves the kernel wrote only the expected rows.
- **Bounded decode:** policy flags and buffer identity are checked at each hand-off. Bounded execution must match the unbounded result exactly on the live rows.
- **Engine test:**
  - Instrumented counters confirm the routed MXFP8 kernel ran inside the asynchronous forward on a step where a request was still in chunked prefill, and that the prefix cache was hit.
  - Generated tokens must match exactly between the prefix-caching-off and prefix-caching-on runs, and every request must finish with exactly 4 tokens.
- **Byte-exact storage and rounding:** not checked in this PR; the dependent fix PRs add those checks.

## Scope

- **Test-only:** this PR changes no production code, functional test, configuration, recipe or golden.
- **Upstream engine tests unaffected:** existing non-MXFP8 inference-optimized MoE engine tests keep the default grouped-GEMM backend.
- **Known CI limitations:**
  - The TP/SP linear test runs only when exactly 2 ranks are launched.
  - The bounded-execution and engine tests need Blackwell but sit in files without the GB200 launch marker, so current CI may skip them.
- **Not in this PR:** production defects found while building this coverage are fixed in the dependent PRs, each with its own regression.

[P2] Calculate the RCEIL reference exponent in higher precision

The [reference helper](https://github.com/NVIDIA/Megatron-LM/blob/2c3ec9181dba6a82a3ca8ef3cb7f348a8650e965/tests/unit_tests/inference/test_mxfp8_contract.py#L44-L65) evaluates `log2` in FP32, which can round a value just above an integer exponent back to that integer before `ceil`. For a `(1, 32)` FP32 block filled with `469762080`—the next FP32 value above `448 * 2**20`—source reasoning gives scale byte **147** and payload **448** here. Mathematical RCEIL requires exponent 21: byte **148** and payload **224**. Although current GEMM tests do not call this helper, it is introduced as the independent byte-exact oracle for dependent regressions.

Use FP64 for the exponent calculation while retaining the existing payload calculation:

```suggestion
        torch.ceil(torch.log2(max_abs.double() / torch.finfo(torch.float8_e4m3fn).max))
```

Preserve the `max_abs == 0` multiplier condition: nonzero blocks with scale byte zero must still use the finite scale `2**-127`, unlike all-zero blocks.

**Proposed acceptance checks, not executed:** the example above must produce byte 148/payload 224; exactly `448 * 2**20` must retain byte 147/payload 448; an all-zero block must retain byte 0/payload 0; and a block filled with `torch.finfo(torch.float32).tiny / 4` must retain byte 0/payload 0.5. Verify the suggested replacement before adopting it.
