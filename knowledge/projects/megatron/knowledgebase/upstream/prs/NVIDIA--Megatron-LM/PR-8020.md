# Fix data-schedule domains for explicit groups and custom layouts

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8020) · state: open · merged: False

## Original PR description

**Why.** `HybridCPDataLoaderWrapper` and `wrap_data_iterator` partition samples over the replicate `dp_cp`/`dp` groups when a `ProcessGroupCollection` is passed. When the collection is omitted, they use the GTP-remat-inclusive groups, which the hybrid-CP scheduler also uses. With `gtp_remat_size > 1` the explicit path covers only part of the data domain: the sample reroute fails, or each GTP peer packs only its own samples.

The reroute also maps global ranks to DPxCP ranks with `r // tp` (and `% dp_cp` for packing). That holds only for the default rank order starting at rank 0. Grids at a rank offset fail, and `--use-tp-pp-dp-mapping` with PP > 1 already breaks sequence packing on the global grid (`Split sizes doesn't match total dim 0 size`).

**What.**
- Explicit collections use `dp_cp_gtp_remat`/`dp_gtp_remat`, and `dp_cp`/`dp` only when those fields are not set (GTP-remat off). A field set to `None` raises `ValueError`.
- Ranks are converted with `torch.distributed.get_group_rank`, so the wrapper no longer needs the TP group.
- Missing groups raise `ValueError` instead of failing an `assert`.

**Tests.** New `tests/unit_tests/data/test_data_schedule_process_groups.py` (4 GPUs):
- explicit, fallback and global group ranks agree, and packed outputs are identical, for GTP-remat 1 and 2;
- two grids at rank offsets;
- the `tp-cp-ep-pp-dp` order.

15 of the 22 cases fail on main. The existing sequence-packing and hybrid-CP tests give the same results as on main.

**Compatibility.** Behavior without a collection and with the default layout is unchanged. `reroute_samples_to_dcp_ranks` keeps its signature (`tp_group` is now unused). The `tp_group` attribute of `HybridCPDataLoaderWrapper` is removed; nothing in this repository reads it.
