# Tile the streamwise backward kernels 16 x 512 to stop FP32 register spills

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8527) · state: closed · merged: True

## Original PR description

## Summary

With an FP32 residual stream, the streamwise (wide-residual) write backward kernel spills heavily at the tile it shares with the forward kernels, 32 x 256 with 4 warps: about 1,300 32-bit words per thread, at about 1 TB/s. In a 576-GPU GB300 training run with `--fp32-residual-connection`, that kernel alone accounted for about 180 ms of the 270 ms per-iteration regression the flag caused.

This gives the two backward kernels (read and write) their own tile, 16 x 512 with 4 warps, whenever 512 divides the stream width, and keeps the existing tile otherwise.

- The forward kernels keep their tile, so forward outputs, and with them residual-stream recompute replay, are unchanged bit for bit.
- The backward activation gradients are elementwise and unchanged bit for bit; only the summation order of the read, write and retention logit gradients changes. Their error against an FP64 reference stays around 1e-7 relative for both tiles.
- With 512 dividing the width, the new tile writes no more logit-gradient partials than the old one (`ceil(B/16) * W/512 <= ceil(B/32) * W/256`), so `_can_use_streamwise_triton` never newly rejects a shape for exceeding the partial reduction limit. That limit is why the faster tiles from the sweep, such as 8 x 512, were not usable: at 24,576 tokens of width 3,072 they write 18,432 partials, past the 16,384 cap.

## Measurements

GB300, Triton 3.7.1, 24,576 tokens (micro-batch 3 x sequence 8,192), stream width 3,072, three streams, learned retention. Per call:

| Kernel | Residual | 32 x 256 (before) | 16 x 512 (after) |
|---|---|---|---|
| write backward | FP32 | 2.987 ms, 1,296 spilled words | 0.522 ms, 50 spilled words |
| write backward | BF16 | 0.324 ms | 0.306 ms |
| read backward | FP32 | 0.323 ms, 14 spilled words | 0.290 ms, no spills |
| read backward | BF16 | 0.160 ms | 0.156 ms |

Through the public autograd path (`streamwise_sigmoid_writeback` backward), FP32 goes from 2.987 ms to 0.530 ms and BF16 from 0.333 ms to 0.315 ms.

At a wider shape (8,192 tokens, micro-batch 1 x sequence 8,192, stream width 10,240, three streams, learned retention), register and spill counts are the same as above: they depend on the tile, the warp count, the number of streams and the dtypes, not on the stream width or token count, which only change the number of programs. Per call:

| Kernel | Residual | 32 x 256 (before) | 16 x 512 (after) |
|---|---|---|---|
| write backward | FP32 | 3.332 ms, 1,296 spilled words | 0.582 ms, 50 spilled words |
| write backward | BF16 | 0.362 ms, 18 spilled words | 0.341 ms, no spills |
| read backward | FP32 | 0.358 ms, 14 spilled words | 0.319 ms, no spills |
| read backward | BF16 | 0.179 ms | 0.175 ms |

Through the public autograd path at this shape, FP32 goes from 3.333 ms to 0.591 ms and BF16 from 0.372 ms to 0.351 ms. 512 divides 10,240, and both tiles write 10,240 logit-gradient partials, within the reduction limit.

The tile was chosen from a sweep of `BLOCK_BATCH` in {8, 16, 32, 64}, `BLOCK_WIDTH` in {64, 128, 256, 512} and {2, 4, 8} warps over all four streamwise kernels. 16 x 512 was the fastest tile within the partial limit for both backward kernels and both dtypes. It also matched the old tile's activations bit for bit in every kernel except the BF16 write forward, which this change leaves on the old tile.

## Testing

- `tests/unit_tests/transformer/test_streamwise_residual_ops.py`: 90 passed on GB300 (NGC PyTorch 26.07). The existing fused-versus-reference GPU tests at widths 512 and 5,120 now run the backward at the new tile.
- New CPU tests: the backward tile never writes more partials than the forward tile, across batches and widths (including widths 512 does not divide, which keep the old tile), and is 16 x 512 at width 3,072.

### Add determinism replay coverage for the new backward tile

The [new tile branch](https://github.com/NVIDIA/Megatron-LM/blob/67d52d44c1ba76cbff71c202896d2c2e7b92d869/megatron/core/transformer/streamwise_residual_ops.py#L80-L98) changes backward reduction geometry, but its [registered replay test](https://github.com/NVIDIA/Megatron-LM/blob/67d52d44c1ba76cbff71c202896d2c2e7b92d869/tests/unit_tests/determinism/kernels/test_streamwise_residual_ops.py#L27-L35) remains fixed at width 256 and never exercises 16 × 512. The added CPU tests verify geometry, not bit-exact execution. GPU kernel changes require an updated replay test under the repository’s [determinism policy](https://github.com/NVIDIA/Megatron-LM/blob/e3f528380c197e8811fb68064d9ef3acf59fd3c6/docs/developer/determinism/testing.md#L86-L101).

This also fails the coverage gate without an exemption: the [manifest](https://github.com/NVIDIA/Megatron-LM/blob/67d52d44c1ba76cbff71c202896d2c2e7b92d869/tests/unit_tests/determinism/kernels/manifest.py#L256-L263) names only that unchanged determinism-test file, so the [gate’s changed-test check](https://github.com/NVIDIA/Megatron-LM/blob/67d52d44c1ba76cbff71c202896d2c2e7b92d869/tools/check_kernel_determinism_coverage.py#L163-L183) reports “kernel 'streamwise_residual_ops' changed but none of its determinism tests did.” This is source reasoning, not an executed CI result.
