## What does this PR do?

This PR adds eager mixed-precision execution for streamwise wide residuals when `fp32_residual_connection=True` and branch modules use BF16 or FP16 parameters.

It keeps the residual stream in FP32 while allowing each ordinary-width branch to run in the configured parameter dtype:

```text
FP32 wide residual [S, B, K*D]
        |
        | fused streamwise read + terminal cast
        v
BF16/FP16 branch input [S, B, D]
        |
        | attention, MLP, or Mamba branch
        v
BF16/FP16 branch update [S, B, D]
        |
        | fused streamwise writeback + update promotion
        v
FP32 wide residual [S, B, K*D]
```

The implementation:

- lets a residual connection request the branch-input dtype through its normal module call
- fuses the FP32-to-BF16/FP16 conversion into the streamwise read store
- allows BF16/FP16 branch updates to be promoted while the fused writeback loads them 
- retains native PyTorch fallbacks for unsupported geometry or dtype combinations
- keeps controller factors and streamwise accumulation in FP32 until the final store

The fused Triton path and native fallback now share one precision contract: controller nonlinearities and streamwise arithmetic are evaluated in FP32, BF16/FP16 activation values are promoted on load, and results are rounded only at the requested output or residual store. The native fallback processes one stream at a time, avoiding a full-width FP32 intermediate.

Selective residual-stream replay is intentionally not part of this PR. It remains in the dependent replay PR (#6805), which only needs to preserve this dtype request during checkpoint
reconstruction.
