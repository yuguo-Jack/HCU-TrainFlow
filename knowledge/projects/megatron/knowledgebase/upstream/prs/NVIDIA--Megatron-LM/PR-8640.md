# fix(MoE): apply the SwiGLU clamp and reject SiTU-GLU in TE fused MLPs

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8640) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

The Transformer Engine fused MLP classes now apply the SwiGLU clamp (`activation_func_clamp_value`) or reject SiTU-GLU (`activation_func_tanh_clamp_scale`). Before this change, `TEFusedMLP`, `TEFusedMLPWithGroupedLinear` and `FusedSharedExpertMLP` silently ran plain SwiGLU when either option was set. `TEFusedMLP` and `TEFusedMLPWithGroupedLinear` now use TE's clamped SwiGLU ops. All three classes now raise a `ValueError` for SiTU-GLU, as the routed experts' fused path already declines it.

### What's wrong

`MLP`, `SharedExpertMLP` and the routed experts support two optional clamps on the FC1 output:

- `activation_func_clamp_value=c` (DeepSeek-V4). For SwiGLU it computes `silu(min(g, c)) * clamp(u, -c, c)`.
- `activation_func_tanh_clamp_scale=s_g` with an optional `activation_func_tanh_clamp_scale_linear=s_l` (Kimi-K3, #7003). With gated silu this is SiTU-GLU: `s_g*tanh(g/s_g)*sigmoid(g) * s_l*tanh(u/s_l)`. With a non-gated activation it is a tanh soft clamp of the input.

Three fused classes build their activation without reading these options:

- `TEFusedMLP` (a dense MLP with `use_transformer_engine_op_fuser=True`). `_make_te_ops_activation` maps `(F.silu, gated)` to `te.pytorch.ops.SwiGLU` whatever the clamp settings.
- `TEFusedMLPWithGroupedLinear` (`use_grouped_gemm_for_dense_mlp=True`). It always appends `ScaledSwiGLU(glu_interleave_size=32)`.
- `FusedSharedExpertMLP` (`use_grouped_gemm_for_shared_expert=True`). It applies `activation_func_clamp_value` through `ScaledClampedQGeGLU`, but it never checks `activation_func_tanh_clamp_scale`, so a SiTU-GLU config runs plain SwiGLU.

None of them raises an error or a warning. The routed experts already handle both options. `TEGroupedMLP._is_fused_impl_supported` uses `ScaledClampedQGeGLU` for the clamp. For SiTU-GLU it returns False ("A clamped gated activation is SiTU-GLU, which the fused GLU path does not implement"), so those layers fall back to the unfused path.

### Reproduction

```python
# torchrun --nproc-per-node 1 repro_short.py   (from a Megatron-LM checkout, one GPU, TE >= 2.17)
import torch
import torch.nn.functional as F

from megatron.core.extensions.transformer_engine import (
    TEFusedMLP,
    TELayerNormColumnParallelLinear,
    TERowParallelLinear,
)
from megatron.core.tensor_parallel.random import model_parallel_cuda_manual_seed
from megatron.core.transformer.mlp import MLP, MLPSubmodules
from megatron.core.transformer.transformer_config import TransformerConfig
from tests.unit_tests.test_utilities import Utils

Utils.initialize_model_parallel(1, 1)
model_parallel_cuda_manual_seed(123)
submodules = MLPSubmodules(linear_fc1=TELayerNormColumnParallelLinear, linear_fc2=TERowParallelLinear)
for act in (
    {"activation_func_clamp_value": 10.0},  # DeepSeek-V4 SwiGLU clamp
    {"activation_func_tanh_clamp_scale": 4.0, "activation_func_tanh_clamp_scale_linear": 25.0},  # K3
):
    config = TransformerConfig(
        num_layers=1, hidden_size=64, ffn_hidden_size=112, num_attention_heads=4, num_moe_experts=4,
        activation_func=F.silu, gated_linear_unit=True, add_bias_linear=False,
        bias_activation_fusion=False, **act,
    )
    mlp = MLP(config, submodules, ffn_hidden_size=112).cuda()
    with torch.no_grad():
        mlp.linear_fc1.weight.normal_(0.0, 1.0)  # FC1 outputs with std ~8, so the clamps are active
    try:
        fused = TEFusedMLP(config, submodules, ffn_hidden_size=112).cuda()
    except ValueError as e:
        print(act, "ValueError:", e)
        continue
    fused.load_state_dict(mlp.state_dict())
    x = torch.randn(32, 2, 64, device="cuda")
    print(act, "max |TEFusedMLP - MLP|:", (fused(x)[0] - mlp(x)[0]).abs().max().item())
Utils.destroy_model_parallel()
```

Results:

- On main (8e13411), this prints `max |TEFusedMLP - MLP|: 19.77` for the clamp and `19.50` for SiTU-GLU.
- With this PR, it prints `0.0` for the clamp, and SiTU-GLU raises `ValueError: TEFusedMLP does not support activation_func_tanh_clamp_scale: ...`.

A longer script also compares gradients and covers the other two classes. Each fused module and its reference have the same weights. The relative error is `||a - b|| / ||b||`.

| Path and config | main | this PR |
|---|---|---|
| `TEFusedMLP`, SwiGLU (control), fp32 | op `SwiGLU`; output, dx and dW_fc1 rel err 0 | same |
| `TEFusedMLP`, clamp 10, fp32 | op `SwiGLU`; output rel err 0.616 (max abs 14.45); dx 0.679; dW_fc1 0.696 | op `ClampedSwiGLU`; output 0; dx 1.1e-6; dW_fc1 1.1e-6 |
| `TEFusedMLP`, SiTU-GLU 4/25, fp32 | op `SwiGLU`; output rel err 1.92 (max abs 20.98); dx 1.68; dW_fc1 1.74 | `ValueError` |
| `FusedSharedExpertMLP`, SiTU-GLU 4/25, bf16 + NVFP4 | builds `ScaledSwiGLU`; vs `SharedExpertMLP` with SiTU-GLU: 1.219; vs `SharedExpertMLP` with SwiGLU: 0.248 | `ValueError` |
| `TEFusedMLPWithGroupedLinear`, clamp 10, bf16 + NVFP4 | builds `ScaledSwiGLU`; vs `MLP` with the clamp: 1.456; vs `MLP` without it: 0.247 | builds `ScaledClampedQGeGLU`; vs `MLP` with the clamp: 0.277; vs `MLP` without it: 0.663 |

In the NVFP4 rows, the fused path's error against the reference it matches (0.25 to 0.28) is mostly quantization error. For comparison, the clamped and unclamped `MLP` references differ by 1.45 on these inputs, and the SiTU-GLU and SwiGLU references differ by 1.18. The FC1 weights are drawn so that FC1 outputs have a std of about 6 to 11, which keeps the clamps active on many elements.

### Impact

- A config is affected when it sets `activation_func_clamp_value` or `activation_func_tanh_clamp_scale` and also enables one of these fused paths:
  - `use_transformer_engine_op_fuser=True` for dense MLP layers;
  - `use_grouped_gemm_for_dense_mlp=True`;
  - `use_grouped_gemm_for_shared_expert=True`.

  Routed experts are not affected.
- These layers train and evaluate with a different activation from the one configured, and nothing reports it. On the inputs above, the outputs differ from the configured activation by 62% to 192% (relative norm), and the gradients by 68% to 174%.
- Weights trained through a fused path behave differently when loaded into the unfused classes, for example `MLP`, which apply the configured activation.
- I have not measured the effect on a real training run.

### Fix

- `_make_te_ops_activation` takes the clamp value. For a clamped SwiGLU it returns `te.pytorch.ops.ClampedSwiGLU(limit=c, alpha=1.0, glu_linear_offset=0.0)`, which computes `silu(min(g, c)) * clamp(u, -c, c)`, the same as `MLP`. The config already requires `glu_linear_offset == 0` with the SwiGLU clamp. `TEFusedMLP._make_fused_impl` passes `activation_func_clamp_value`.
- When the clamp is set, `TEFusedMLPWithGroupedLinear._make_fused_impl` builds `ScaledClampedQGeGLU(glu_interleave_size=32, alpha=1.0, limit=c, glu_linear_offset=0.0)`. These are the same arguments `FusedSharedExpertMLP` and `TEGroupedMLP` use.
- `TEFusedMLP.__init__`, which `TEFusedMLPWithGroupedLinear` inherits, raises two errors:
  - a `ValueError` when `activation_func_tanh_clamp_scale` is set;
  - a `RuntimeError` when the clamp is set with TE < 2.17.0.dev0. That is the bound `FusedSharedExpertMLP` and `TEGroupedMLP` use for `glu_linear_offset`.

  These checks run at construction, because the fused ops are only built on the first forward.
- `FusedSharedExpertMLP._validate_fused_grouped_swiglu` raises a `ValueError` when `activation_func_tanh_clamp_scale` is set, next to its other config checks.

I chose to reject SiTU-GLU rather than use TE's `SiTUGLU` and `ScaledSiTUGLU` ops (TE 2.20) for three reasons:

- The routed experts do not use those ops yet.
- Megatron allows the gate scale without the linear scale. The TE ops require a finite, positive `beta2` for the linear half, so they cannot express that case.
- #6674 is the open PR that adds SiTU-GLU through TE.

This PR stops the silent fallback until #6674 or similar work lands. That work would replace these `ValueError`s.

The input-gradient error with the clamp (0.183 against 0.083 for the control) comes from MXFP8. The gradient is zero on one side of the clamp, and rounding the FC1 operands moves some pre-activations across it. With the clamp at 10 and FC1 outputs of std ~11, 1522 of 131072 clamp decisions change, which alone changes dx by 0.161 (relative). Against an fp32 reference that takes its clamp decisions from MXFP8-quantized operands, the kernel's dx error is 0.106. With the clamp at 30 it is 0.084 to 0.089, the control level. An MXFP8 test of a clamped activation therefore needs a looser dx tolerance than an unclamped one, or a reference whose clamp decisions come from the quantized operands. None of the tests in this PR compares a clamped gradient under MXFP8.

`tools/check_kernel_determinism_coverage.py` reports one issue. `transformer_engine.py` is also a source of the `paged_stash_marker_propagation` entry, and that entry's test, `test_fused_activations.py`, is unchanged. The new `test_te_wrappers.py` case covers the file's other two entries, `transformer_engine_wrappers` and `te_fused_cross_entropy`. This change does not touch paged stashing. Could a maintainer add the `determinism-exempt` label? I can't add labels myself. If you prefer, I can add a case to `test_fused_activations.py` instead.

Not covered:

- GEGLU or ReGLU with `activation_func_clamp_value`. The unfused `MLP` clamps any gated activation, but `TEFusedMLP` still ignores the clamp for these two. The config documents the clamp only for SwiGLU and quick-GELU, which the TE op path does not support. `MLP`'s own fused `bias_geglu_impl` also ignores the clamp, so I left this as is.
- The `activation_func_tanh_clamp_scale` docstring still mentions only the routed-expert fused path.
