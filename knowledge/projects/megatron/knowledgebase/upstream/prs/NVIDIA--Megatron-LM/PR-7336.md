# Add mHC pipeline and virtual-pipeline support

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7336) · state: open · merged: False

## Original PR description

## What does this PR do?

Enable mHC with pipeline parallelism and interleaved virtual pipelines on main. Intermediate stages carry `hidden_size * mhc_num_residual_streams` activations; both schedules now allocate their P2P buffers with that width, including physical-rank wraparound between virtual chunks.

Related to #2919. This ports the pipeline capability from #2943 onto main's mHC interfaces. The separate CUDA graph PR #7337 covers graph execution.

Tracking PR #5795 also lists this capability as P3. The earlier stacked draft #5943 was closed to rebuild P3 on main after P2; its [closure comment](https://github.com/NVIDIA/Megatron-LM/pull/5943#issuecomment-5059183514) explains that sequencing. This PR adapts the transport to main's current mHC interfaces.

The generic PP2 batched P2P message-order prerequisite overlaps open draft #7177 ([its standalone fix](https://github.com/NVIDIA/Megatron-LM/commit/9915a24149eb3f741cfc83dd624c545c71aa40ef)). Current main and dev both retain the old order, so this prerequisite is an independently reproduced pipeline bug fix. Reconcile it with #7177 as that work lands.

The deterministic GDN prerequisite addresses the same missing Q/K-normalization coverage as open dev PR #6613. This implementation also preserves FLA's backward formula using the output rounded to the input dtype, verified against the actual kernel. Main PR #6966 addresses shared autotune-cache configuration more broadly. Main PR #5396 changes the normalization call site behind an optional fusion flag; these changes should be reconciled when combined.

### Changes

- Share the pipeline residual-width calculation between the ordinary and interleaved schedules, preserving sequence/context parallel sequence dimensions and variable-length shape exchange.
- Return independent output storage from empty intermediate Hybrid stages so pipeline output deallocation preserves backward propagation.
- Keep embedding-only mHC output viewless after stream expansion, and match forward/backward batched P2P payload and shape-message ordering when PP2 shares the same peer in both directions.
- Keep Hybrid MTP on the final output chunk and reject the unsupported combination of mHC pipeline parallelism with EP communication overlap.
- Preserve existing configuration names, checkpoint keys, GPT mean contraction, Hybrid learned contraction, and eager selective mHC recomputation.
- Fix generic distributed-optimizer checkpoint prerequisites exposed by mixed FP32/BF16 mHC training: align per-parameter lookup indices with existing main-parameter order and exclude trailing DP alignment padding from unpadded checkpoint tensors. Checkpoint format remains unchanged.
- Make GDN/GDN2 Q/K normalization deterministic when requested. The native normalization preserves additive epsilon, FP32 intermediates and FLA's rounded-output backward contract; ordinary training retains the optimized FLA path.

## Review — mHC pipeline / virtual-pipeline support

I read the full changeset against the mounted base tree, then re-read the surrounding code in `megatron/core/pipeline_parallel/{schedules,p2p_communication}.py`, `megatron/core/optimizer/distrib_optimizer.py`, `megatron/core/transformer/{transformer_block,transformer_config}.py`, `megatron/core/models/hybrid/{hybrid_block,hybrid_model}.py`, `megatron/core/ssm/gated_delta_net/common.py`, the inference wrapper base class, and the new tests, recipes and goldens.

**Findings: CRITICAL 0 · IMPORTANT 1 · SUGGESTION 3.**

### Verified and dropped as findings

Several things that looked suspicious on first pass hold up under tracing, so I am not raising them:

1. **The `_batched_p2p_ops` reorder is a real fix, not a regression.** In the base, sends to a peer were enqueued `[send_prev, send_next]` while receives from that peer were `[recv_prev, recv_next]`; at PP2 `prev_rank == next_rank`, so NCCL matched the peer's gradient send against this rank's activation receive. The new order `[send_next, recv_prev, send_prev, recv_next]` pairs correctly, is symmetric across ranks, and is unaffected at PP>2 where the two peers differ. `_p2p_ops` already used this relative ordering in both its even and odd branches, so the batched path is now consistent with the non-batched one. `_communicate_shapes`' `else` branch (p2p_communication.py:242) is the non-`ring_exchange` path used by both `batch_p2p_comm` settings, and it already used `batch_isend_irecv` in the base — so delegating to `_batched_p2p_ops` is behaviour-preserving apart from the intended reorder, and shape messages are `wait()`ed before any data op is issued, so there is no cross-matching between the shape and data phases.

2. **The padding bound in `sharded_param_state_dp_reshardable` cannot produce a negative-size tensor.** `min(gbuf_local_numel, gbuf_world_numel_unpadded - data_parallel_rank * gbuf_local_numel)` can be negative for a high DP rank whose whole shard is alignment padding, but reaching the `torch.empty(next_param_start - cur_param_end)` branch additionally requires `data_parallel_rank * gbuf_local_numel + cur_param_end < gbuf_world_numel_unpadded`, which together with a negative bound would imply `cur_param_end < 0`. Coverage of the global `(gbuf_world_numel_unpadded,)` tensor stays complete.

3. **The optimizer index reordering matches both `orig_group["params"]` constructions.** `_build_model_and_main_param_groups` builds `[*shard_fp32_params, *shard_fp32_from_float16_params]` in the default branch and `[*shard_fp32_params, *shard_float16_params]` in the precision-aware branch — both fp32-first — so keying on `param.dtype == torch.float32` reproduces the optimizer's own order. Quantized params report a non-fp32 `.dtype`, so they bucket identically in both places.

4. **The `hidden_states.clone()` for empty intermediate Hybrid stages is necessary and consistent.** `make_viewless_tensor` returns its input object unchanged when the input is already viewless, so without the clone `deallocate_output_tensor` would resize storage the stage still needs to receive and propagate the gradient. It mirrors the pre-existing clone at transformer_block.py:799-800 and only fires for zero-layer stages.

5. **The new `make_viewless_tensor` after `input_expand` is required.** `input_expand` ends in a `view`, so the result has a non-`None` `_base` and would trip `deallocate_output_tensor`'s assertion on an embedding-only stage. Hardcoding `requires_grad=True` matches the immediately preceding call at transformer_block.py:630.

6. **The deterministic GDN normalization is correctly wired and covered.** `torch_l2norm` is reached through the shared `_prepare_input_for_gated_delta_rule`, so GDN2 is covered by the same call site; the new kernel test checks output, gradient, FP32 intermediates and the saved-rounded-output contract against `fla.modules.l2norm.l2norm` in both eager and compiled form, plus a bit-exact replay under contention; and `test_deterministic_mode` now monkeypatches `common.l2norm` to a raiser, which is a good way to prove the FLA path is not reached.

7. **No new direct process-group reads in library code, and no dead new identifiers.** `_get_pipeline_hidden_size`, `_TorchL2Norm`, `torch_l2norm`, `main_param_order` and the new fixture all have live use paths; the only `parallel_state.get_*` calls added are in tests.

### What is good

The width plumbing is small and placed where it belongs, and the new coverage is unusually strong for a transport change: `test_pp_mhc_compatibility.py` compares real schedules, losses and *every* finalized gradient against an identically initialized PP1 model across PP2/VPP2/standalone-chunk/empty-chunk/TP-SP-MTP/CP-variable cases, and `test_pp_mhc_dsv4_shapes.py` drives the production schedules at 4096/7168 hidden with four streams against an `rtol=0, atol=0` serial oracle while also asserting the sent tensors were pseudo-deallocated. The two new optimizer regressions assert real `ShardedTensor` global bounds rather than just shapes. Replacing the blanket `NotImplementedError` with a narrow `overlap_moe_expert_parallel_comm` rejection, and adding the inference-side guard keyed on the *inference* PP group (not `config.pipeline_model_parallel_size`), are both the right shape of change.

### Risk and follow-ups

- **Highest-blast-radius change is `_batched_p2p_ops`**, which every pipelined model uses. It is correct, but it fixes a latent generic PP2 bug and the description says the same prerequisite exists in open draft #7177 (`9915a24`). The reorder is idempotent, so a double landing is harmless, but an unreconciled merge could reintroduce the base order in one of the two files — worth calling out in the commit message so a future bisect can find it.
- **Transport coverage is batched-only.** Every new mHC PP case pins `batch_p2p_comm=True` (`_make_config`, `test_pp_mhc_dsv4_shapes`, `test_mhc_batched_p2p_preserves_directions`) and neither functional recipe sets `--overlap-p2p-comm`. The `overlap_p2p_comm=True` / `batch_p2p_comm=False` `_p2p_ops` path — common in production VPP — has no mHC coverage. Nothing about it looks broken (the width comes from the same `tensor_shape`), but one parity case there would close the only transport this PR leaves unexercised.
- **Unguarded, untested compositions** now reachable since the blanket PP guard was lifted: `hybrid_cp_schedule.py`, `bridge_communicator.py`, `multimodule_communicator.py`, `fine_grained_activation_offload.py`, and CUDA graphs. The new doc text says CUDA graph/offload/full-recompute "retain their existing restrictions"; if there is in fact no config-level restriction for mHC + PP + CUDA graphs (PR #7337 covers graph execution separately), an explicit rejection would be safer than prose.
- **Checkpoint semantics across the optimizer index fix.** The on-disk format is unchanged, but a checkpoint written *before* this commit for a parameter group mixing fp32 and fp16/bf16 params recorded each parameter under the old (wrong) index; resuming after the fix restores those tensors onto the parameters they were mislabeled with. This affects any model using `mark_keep_in_fp32`, not just mHC. Worth one sentence in `docs/user-guide/features/dist_optimizer.md` and the PR description, or a version/marker gate that rejects such checkpoints loudly.

Diff size is large (~1.5k lines) but it is ~85% tests, docs and goldens; the library change is ~90 lines across seven files and each piece is independently motivated, so I would not ask for a split.

- svcnvidia-nemo-ci · comment · 2026-09-23T21:49:44Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/7336#discussion_r4087652969)

File: `megatron/core/pipeline_parallel/schedules.py` · line 2125

**[IMPORTANT Correctness]** GPT + mHC + PP + MTP can still disagree on the wire width.

**Issue.** This helper encodes the invariant the new docs state — "[the n-stream width] applies to **every communicating edge**" (docs/api-guide/core/pipeline_parallel.md:29-31) and "the stage containing the final output contracts the residual before the loss" (L23-24). For `TransformerBlock` that invariant depends on where the contraction happens, and the contraction is keyed on `has_final_layernorm_in_this_stage()` (transformer_block.py:782). When `config.mtp_num_layers is not None`, that helper does **not** return the last pipeline stage — it returns the stage holding the last *decoder* layer (transformer_block.py:435-451, "for model with MTPLayer, the final layernorm is set in the stage which has the last layer of the decoder").

So for a layout where at least one more chunk follows the chunk holding layer `num_layers` — e.g. `pipeline_model_parallel_layout="E|tt|ttm|L"`, which is legal per the field docstring in transformer_config.py:123-147 — the contracting chunk emits `[s, b, C]` while the receiving chunk allocates `[s, b, n*C]` from this function.

**Impact.** With fixed-shape P2P that is a send/recv size mismatch: a hang or a corrupt buffer, not a clean error. There is no config-level rejection for it: the mHC block in `transformer_config.py` now only rejects `overlap_moe_expert_parallel_comm`, and `HybridModel` got a guard for its analogous case (hybrid_model.py:268-273 — Hybrid ties its contraction to `post_process`, so `post_process`-only MTP is sufficient there) while the GPT path got none. Coverage is asymmetric too: `test_mhc_schedule_matches_pp1` only parametrizes `mtp=True` for `kind="hybrid"` (the `tp_sp_mtp` case), so no GPT + MTP + PP case runs. A dynamic shape-exchange path may rescue *some* MTP layouts, but relying on that implicitly for an unrejected, untested composition is fragile.

**Suggestion.** Pick one:
- reject it in `TransformerConfig.__post_init__`, inside the existing `if self.enable_mhc_connections:` block — e.g. raise when `pipeline_model_parallel_size > 1 and mtp_num_layers` unless the contraction chunk is provably the last communicating chunk; or
- make the GPT contraction site match Hybrid's (`post_process`) when mHC is on, so the width is uniform by construction; or
- if the composition is already correct via shape exchange, add a `kind="gpt", mtp=True` case to `test_mhc_schedule_matches_pp1` and say so in the docstring here, since the invariant this function relies on is otherwise invisible to the next reader.

Either way, the doc sentence at L23-24 should name which model families place the contraction on the last stage, because with MTP GPT does not.
