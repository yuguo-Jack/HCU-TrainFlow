# Add a public process-group registry to parallel_state

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8747) · state: closed · merged: False

## Original PR description

Depends on #8039 (which contains #6259). Please review the diff from the merge of #8039 into main: [scoped diff](https://github.com/Connor-XY/Megatron-LM/compare/2ac4d937e0...yx/pstate-r1-registry). #8039's head includes its merge of #6259 and the follow-up commit that puts the intra Gloo groups in the collection that `build_process_group_collection()` returns.

**Why.** A framework that builds its own grid, for example with `HyperCommGrid`, has no supported way to make code that still reads `parallel_state` use that grid. `initialize_model_parallel()` registers its groups through a private helper that needs every `StandardGridExtras` field, so Megatron-Bridge MIMO and `tools/checkpoint` write `parallel_state`'s private module variables instead.

Teardown is also incomplete. `destroy_model_parallel()` leaves ten values behind: the hierarchical CP groups, the partial data-parallel group with CP and its Gloo group, and seven global rank lists. After a teardown, `use_mpu_process_groups()` still returns the old `hcp` and `intra_dp_cp` groups, and the source, first and last rank accessors return ranks of the old grid.

**What.**
- `register_process_groups(pg_collection, *, extras=None)` sets the module variables that the accessors and `use_mpu_process_groups()` read, and records the collection. `get_registered_process_groups()` returns it.
- Without `extras`:
  - the global rank lists are the ranks of the collection's groups;
  - the GTP-inclusive partial data-parallel groups are the partial groups when GTP weight remat is off;
  - the groups a collection cannot describe stay `None`: the data-parallel, data-parallel-with-CP and expert data-parallel Gloo groups, and TP×DP.
- The intra partial data-parallel Gloo groups come from the collection's `intra_dp_cp_gloo` and `intra_expt_dp_gloo` fields (#6259), with or without `extras`, like every other field it has.
- A field that is unset registers no group, so a collection that leaves `dynamic_cp` unset no longer fails in `dict.update()`.
- Registration raises `TypeError` for another type and `RuntimeError` when groups are already registered, instead of an `assert`.
- `initialize_model_parallel()` is `build_process_group_collection()` plus `register_process_groups()`, followed by the global memory-buffer creation that #8026 removes. `get_registered_process_groups()` returns the collection it built.
- `destroy_model_parallel()` clears every value that registration sets, destroys the partial data-parallel Gloo group like the other Gloo groups, and clears the registered collection.

**Tests.** New `tests/unit_tests/test_process_group_registry.py`:
- CPU tests with fake groups: initialization registers its collection; a custom collection's groups, rank lists, sizes and `_MPU_*` overrides; unset fields; double registration; other types; teardown clears every registered value; the accessor table covers every collection field.
- Tests on real process groups: a `HyperCommGrid` collection with PP varying fastest (needs CUDA), teardown of a registration, and the builder's result registered with `extras`.

`test_build_process_group_collection.py` now expects `RuntimeError` for a second initialization.

On 4 GPUs against its base: `test_build_process_group_collection.py`: 21 passed here vs 21 on the base; `test_process_group_registry.py`: 31 new tests pass, including the `HyperCommGrid` test that needs CUDA. Neither file has a regression. With the other process-group changes from #6307 applied, the full unit test suite shows no regressions against main, and end-to-end training smokes match main's loss at every iteration. In that run, this PR's two test files pass (21 and 31 tests); neither file exists on main. Before the sync, this branch ran both test files on 4 CPU ranks with Gloo: 51 passed, and the `HyperCommGrid` test, which needs CUDA, failed.

**Compatibility.** On the standard grid every group creation, barrier, module variable, accessor and `use_mpu_process_groups()` field after initialization is the same as before.
- The accessors keep reading the module variables, so existing writes to them (Megatron-Bridge MIMO, `tools/checkpoint`, tests) still change what the accessors and `use_mpu_process_groups()` return. The registered collection is a second copy and can disagree with the accessors after such a write. Code should not assume the two agree until `tools/checkpoint` (#8762) and Megatron-Bridge MIMO stop writing the private variables.
- A second initialization raises `RuntimeError` instead of `AssertionError`. The message is the same, plus a hint to call `destroy_model_parallel()` first. On ranks outside a `rank_offset` window, a repeated `initialize_model_parallel()` without a teardown also raises now. Before, it registered the empty collection again.
- Needs `determinism-exempt` only while #6259 is unlanded: its change to `megatron/core/optimizer/__init__.py` comes in through #8039.

Known limitations:
- Without `extras`, registration aliases the GTP-inclusive partial groups when GTP is off, but not the GTP-inclusive collection fields (`dp_gtp_remat`, `dp_cp_gtp_remat`, ...). A collection that sets only `dp` and `dp_cp`, as Megatron-Bridge MIMO does, then hits an `AssertionError` in the default `get_data_parallel_group()`.
- A field that holds `NON_GROUP_MEMBER` fails at registration with an unclear error.
- The only way to unregister is `destroy_model_parallel()`, which tears everything else down too.
- `StandardGridExtras.intra_dp_cp_gloo` and `intra_expt_dp_gloo` now duplicate collection fields. Removing them would change #8039's builder API, so they stay.

Landing:
- #8026 removes the `_GLOBAL_MEMORY_BUFFER` declaration next to this PR's `_REGISTERED_PROCESS_GROUPS`, and the `_set_global_memory_buffer()` call right after this PR's `register_process_groups()` call. The two conflict in `parallel_state.py`. Whichever lands second keeps this PR's lines and drops the memory-buffer ones.
- This PR and #7029 both change `destroy_model_parallel()`, and they conflict there and at the `_REGISTERED_PROCESS_GROUPS` declaration. Whichever lands second:
  - keeps `_REGISTERED_PROCESS_GROUPS = None`;
  - does not bring back main's `_global_process_group_list = None`, which #7029 removed: clearing the list before `_destroy_created_process_groups()` leaks every group;
  - keeps one copy of the `_INTRA_PARTIAL_DATA_PARALLEL_GROUP_WITH_CP` and `_HIERARCHICAL_CONTEXT_PARALLEL_GROUPS` resets;
  - drops this PR's explicit destroy of `_INTRA_PARTIAL_DATA_PARALLEL_GROUP_WITH_CP_GLOO`, which #7029's tracked teardown already destroys.
