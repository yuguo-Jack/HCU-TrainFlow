  # What does this PR do?

  Fix parameter norm logging with LayerWise optimizer and overlapped parameter gather.

  Mark LayerWise main weights as DP-sharded so norm computation sums owners’ updated main weights
  and skips non-owners’ potentially stale model copies.

Light review — the core fix looks correct: marking every bf16/fp16 model param in the LayerWise param groups *before* `shard_params()` narrows the groups, combined with `Float16OptimizerWithFloat16Params` only creating `main_param` for the local shard afterwards, means each param contributes exactly once (owner’s fp32 master) while non-owners return `(None, True)` and are skipped. The `dp_cp_size == 1` early-return path is fine too, since the sharded buckets then reduce over a group of size 1.

Two things:

**1. Missing regression test (main ask).** The PR body notes multi-GPU testing is pending and no test is added. This is exactly the class of bug a unit test would catch — `tests/unit_tests/training/test_param_norm.py` already has a LayerWise/Muon case (`test_layer_wise_muon_grad_norm_uses_expert_tp_group_for_row_parallel_bias`), and `tests/unit_tests/test_utils.py::test_param_norm_linear` already asserts `main_param_sharded` for DistOpt. A LayerWise analogue would be cheap:

```python
def test_layer_wise_param_norm_counts_each_param_once_with_overlapped_gather():
    """Norm must sum owners fp32 masters, not non-owners stale model copies."""
    Utils.initialize_model_parallel()
    model = ...  # bf16 model, weights filled with 1.0, DDP with overlap_param_gather=True
    optimizer = get_megatron_optimizer(
        OptimizerConfig(optimizer="muon", bf16=True,
                        use_layer_wise_distributed_optimizer=True, ...),
        [model], pg_collection=ProcessGroupCollection.use_mpu_process_groups())
    for param in model.parameters():
        if param.dtype in (torch.bfloat16, torch.float16):
            assert getattr(param, "main_param_sharded", False)
    with mock.patch("megatron.training.utils.get_args", new=lambda: SimpleNamespace(bf16=True)):
        assert training_util.calc_params_l2_norm(model, force_create_fp32_copy=False) \
            == pytest.approx(training_util.calc_params_l2_norm(model, force_create_fp32_copy=True))
```

Ideally also cover the post-`step()` case (perturb the owner’s `main_param`, then check the norm reflects it *without* a param sync) — that is the actual regression from #7131.

**2. fp32 params under LayerWise still read possibly-stale copies.** The new loop only marks `HalfTensor`/`BFloat16Tensor`. fp32 params in LayerWise’s groups (e.g. router weights) are also assigned to a single owner rank by `shard_params()`, but they never get a `main_param`, so `_get_param_data` returns `(param.data.float(), False)` → non-sharded bucket → every rank counts its own local copy, which is stale on non-owners under overlapped gather. Same failure mode this PR fixes for bf16. Worth either handling here or calling out as a known limitation in the comment/commit message.
