### Notes on individual commits

- **Row 15.** Main #6754 (in the base through #7960) runs the synchronous LayerWise MXFP8
  parameter sync through the DDP bucket groups with `grad_data` as the receive buffer. Row 15
  keeps only the per-parameter staging into the receive slot and the equal-size tensor all-gather.
- **Rows 17 and 18.** Row 17 adapts the cuDNN DSA call sites to the FE >= 1.26 defaults: global
  sparse top-k ids (`topk_indices_global=True`) and explicit bottom-right causal offsets, passed
  from FE 1.26, the release that changed the default. CPU fakes cover both frontend generations.
  Row 18 makes cuDNN DSA deterministic on top of row 17 and carries the `+inf` top-k membership
  fix.
- **Row 22.** A layer that runs KPool selection
  ([#8287](https://github.com/NVIDIA/Megatron-LM/pull/8287)) without tail selection does not
  certify its top-k rows as non-empty. Its CPU test needs only dev.
- **Row 23.** `TransformerConfig` checks a custom `pipeline_model_parallel_layout` at parse time,
  on every rank. With `dsa_indexer_topk_freq > 1`, it rejects a layout whose pipeline stage or
  virtual stage starts on a DSA index-sharing layer. Such a layout therefore fails at parse time,
  on CPU and on every rank, rather than at model build or the first forward, on the GPU and only
  on the ranks that own the bad chunk.
- **Row 35** also fixes the test double
  `TestThdStaticPPCommunicationShapes::test_get_tensor_shapes_uses_static_thd_width`. Its config
  lacked `pipeline_model_parallel_size`, which dev reads (main #7336, synced through #7960).
- **Row 38** covers interleaved (VPP) THD full-iteration plumbing on CPU: the schedule shape and
  layout, dynamic-CP scheduling per model chunk, the per-(chunk, microbatch) static slots, and the
  dynamic-CP certificate across VPP slots.
- **Row 39** holds the native recipes (layouts under "Native full-model recipes") and their Slurm
  and Pyxis launch. It replaces `42779557cc`, whose recipes lacked the formal cells' DSA flags,
  runtime stack and launch (see "The recipe run").

Each snapshot is one squash-pick of its upstream PR, adapted to the current dev, so its tree does
not equal the PR head; the upstream PRs are based on older dev. The #6741 snapshot keeps its
sequence-roll code in `mtp_sequence_roll.py`. Adaptations that change behaviour (each is recorded
in its commit message):

  full recompute when forward sharing is enabled.

  `decoder_input`, and the attention CP layout is not `contiguous`. In all other cases dev's

  `moe_hybridep_pad_variable_tokens` for sequence packing and exempts

  `cudagraph_needs_generator_registration()` asks for it (main #7348).

## Native full-model recipes

256 GB300, 78 decoder layers (3 dense + 75 MoE), 256 experts,
TP1/PP4/EP64/configured CP64 (1M: interleaved, two virtual stages per PP rank),
packed THD/dynamic CP, shared repeated MTP7
E2E-TV with detached heads, per-head Muon, force balance and MoK. No offload.
MXFP8 covers eligible projection/grouped GEMMs, MoK routed experts and the DSA
indexer's key scoring (DeepGEMM). MoK shared experts use BF16, with FP8 execution
and FP8 parameter storage disabled; cuDNN DSA sparse attention remains BF16, with
FP32 reductions/state where required. This is a performance
recipe, not long-term convergence or complete official optimizer-parity evidence.
Data uses NullTokenizer and fixed-length varlen mock samples with force-balanced
routing; these results do not establish real-data performance or convergence.

| Property | 4K | 128K | 1M |
| --- | ---: | ---: | ---: |
| Nominal sequence limit | 4,096 | 131,072 | 1,048,576 |
| Valid post-shift tokens/sample | 3,968 | 126,976 | 1,015,808 |
| Effective CP / DP | 1 / 64 | 32 / 2 | 64 / 1 |
| GBS / MBS | 2,048 / 1 | 64 / 1 | 8 / 1 |
| Realized microbatches/step | 32 | 32 | 8 |
| Local valid tokens / capacity | 3,968 / 4,096 | 3,968 / 4,096 | 15,872 / 16,384 |
| Valid global tokens/step | 8,126,464 | 8,126,464 | 8,126,464 |
| Decoder layers per PP rank + MTP7 | 22/24/24/8 + 7 | 22/24/24/8 + 7 | 22/24/20/12 + 7 (VPP2) |
| Pipeline schedule | 1F1B | 1F1B | Interleaved, batched PP send/recv |
| Recompute | Layernorm only | Layernorm only | Full uniform1 |
| MoK mini / macro | 4,096 / 40,960 | 4,096 / 40,960 | 4,096 / 131,072 |

Pipeline layouts:
- 4K and 128K: `Et*22|t*24|t*24|t*8m*7L` (1F1B). PP3 also holds MTP7 and the output head, so it
  carries the fewest decoder layers.
- 1M: `Et*10|t*12|t*12|t*12|t*12|t*12|t*8|m*7L`, interleaved with two virtual stages per PP rank
  (22/24/20/12 decoder layers per rank). It sets `no_overlap_p2p_communication`, because
  full-iteration CUDA Graphs are validated with batched PP send/recv only.
- With index sharing every fourth layer, every stage and virtual stage must start at a layer that
  computes its own top-k, so stage boundaries can only move in steps of four layers (the current
  chunks start at decoder layers 1, 23, 47 and 71, and at 1M at 1, 11, 23, 35, 47, 59 and 71).
  Row 23 enforces this at config time.

Recipes: `examples/moe_recipes/glm5_2/gb300/`
`mxfp8_THD{4K,128K,1M}_256GPU_TP1PP4EP64CP64_full_cg_mok.yaml`;
renderer: `examples/moe_recipes/glm5_2/run.py`; Slurm launch: `srun_rank.sh` and
`check_placement.py` next to it. Their README gives the runtime artifacts, the launch steps and
the validation scope (the formal cells and the recipe run).
Actual topology places each EP64 group within one of four NVL domains.
The sweep compares runnable recipes. Local tokens, CP, microbatch count, PP split, schedule and
recompute differ across lengths, not just sequence length.

**What each stage changes.**
- P0–P2 ran the head plus local, experiment-only feature-disabling patches (not part of this
  stack); P3 and P4 ran the head unchanged.
  - In P0–P2, one patch reverts #6166's invalid-slot handling and turns off the inverse-permutation
    backward (row 24) and top-k certificate sharing (row 27).

    unfused per-head fallback (FP32 matmuls; BF16 indexer only). This per-head path is the
    intended P0 stage definition and the validators require it on every call; it is not an
    unintended fallback in the sense of "Metric scope and qualification limits" below.

    device, per rank, on every DSA call, with no host layout, memo or prebuilt tables.
  - In P1, one patch turns off only the prebuilt layout tables; the #6206 host layout is built once
    per microbatch and memoized.
  - The layout patches change timing only: in CPU tests the layout tables and the DSA forward
    inputs are bitwise identical to the head's.

  variable token counts, as eager HybridEP requires. P2–P4 run the native full-iteration graph,
  captured at step 4.
- P0–P3 use HybridEP with paged stash (rank capacity factor 1.2, GLU32 expert layout) instead of
  MoK; P4 is the native recipe.
- P1 and P2 score with the BF16 cuDNN packed fused scorer, including its `-inf` prefill. P3 adds
  #6166, rows 24 and 27, the MXFP8 indexer with the DeepGEMM scorer, and DeepSelect top-k; the
  prefill goes away with DeepGEMM, which never pre-fills (the row 28 skip is inert in every
  stage).
- The MTP optimizations, #6741 absolute-row addressing and the shard-only shared-embedding gradient
  all-reduce (row 12), are on in every stage.
- P4 runs the launch arguments of the 128K trained formal cell on the same 64 nodes as job `12015`
  and reproduces it: 15.728 / 15.720 s against 15.72805 s, 226.9 GiB max allocated in both.

**How to read it.**
- Stage gains depend on the order of the stages: each delta is measured on top of the stages before
  it.
- P0 is not a pure historical baseline. It runs the current code with current kernels: the
  unfused scorer is today's bound-aware per-head FP32 fallback (about 108 ms per 128K call,
  CUDA-event timing), the pre-#6206 device layout costs about 25–29 ms per 128K CP32 call
  (synchronized timing of the device builder, adjusted for in-run contention), and the explicit
  cuDNN causal offsets (row 17) stay on. Two millisecond-scale leftovers remain and are not
  subtracted: P0 still builds the inverse key permutation on every DSA call although nothing
  consumes it, and still copies the host `cu_seqlens` at batch time although its layout path
  ignores them.
- P0 and P1 eager times include eager-only host costs on the current code: the HybridEP
  token-count equalization sync on every dispatch, variable-shape PP send/recv and, in P0, per-rank
  layout synchronizations. P1 → P2 removes them together with the graph, so it is not a pure graph
  gain.
- The MTP optimizations are part of the baseline by choice. Repeated-MTP KV and top-k sharing is
  part of the model and stays on.
- Only the eager stages run the runner's read-only host-side observers on their timed steps (graph
  replay skips them); their bound is at most 0.014% of a step.
- Numerics are not bitwise across stages: the MXFP8/DeepGEMM scorer selects different keys, MoK
  (BF16 shared experts) and HybridEP (GLU32 expert layout) compute the MoE layers differently, and
  forced-balance routing draws its random numbers in execution order. The routing map is realized
  as `bool` in P0–P3 and natively by MoK in P4.
- Execution-adjusted TF is not computed for P0: its per-head scorer is outside the metrics tool's
  execution ledger. Eager rates (P0, P1) are wall-time rates. As in the formal cells, the upper end
  adds a bound for MoK routed-FC1 replay; the tool applies it to every stage, including P1–P3,
  which do not run MoK.
- One allocation, one window per cell and a fixed order (no ABBA); P4a and P4b bracket the job.

### What the profiles show

**Current time budget** (profiled iteration 8, stage medians of the sampled ranks).

| Trained cell | Profiled step, NVTX median (s) | Layer compute + MoK, share | Fill/drain bubble (s) | Stage imbalance (s) | Outside graph, unprofiled estimate (s) |
| --- | ---: | ---: | ---: | ---: | ---: |
| 4K | 13.764 | 80% | 1.056 | 0.377 | 1.015 |
| 128K | 15.892 | 79% | 1.256 | 0.615 | 0.686 |
| 1M | 25.122 | 74% | 3.836 | 0.533 | 0.610 |

- **Pipeline.** PP1 is the critical stage in every cell; PP2 ties it at 4K and 128K. PP3 (MTP7,
  output head and loss) is not critical. With stages starting only on top-k-computing layers, an
  exhaustive schedule simulation (within −20 to +78 ms of the measured graph spans) finds the
  current layouts optimal.
- **Outside the graph.** The pre-graph phase is CPU-bound. At 4K its critical path is the
  dynamic-CP reroute on PP3, which copies all 2,048 local samples per key and keeps about 2%. All
  ranks wait for it in the full-iteration graph's WORLD capture-signature check
  (`FullCudaGraphWrapper._check_capture_signature`), not in the packing scheduler, whose DP
  all-gathers launch no kernel at DP size 1. The post-graph phase (~0.6 s) is paced by the Muon
  step's CPU launch rate on the rank with the most small matrices: a per-head Newton–Schulz loop
  over the MLA up-projections, 128 calls per matrix.
- **Communication.** NCCL never overlaps other GPU work. PP send/recv time is waiting, not
  transfer. The in-layer CP all-gather and reduce-scatter are fully exposed.
- **Kernels.** Utilization figures are modelled from kernel times and FLOPs or bytes, not measured
  with hardware counters.
  - On the bottleneck stage MoK is the largest family (27–36% of the graph), the sparse-attention
    backward the largest compute family (21–24%).
  - The sparse-attention backward reaches about 25% of BF16 peak at 4K/128K and 16–19% at 1M, the
    forward 42–44%; the backward takes 4.3–5.3x the forward time for 2.53x the FLOPs.
  - At 1M the backward per call rises from 21.8 ms at CP position 0 to 28.0 ms at position 63
    (modelled as key-range L2 locality), and faster ranks wait about 0.5–0.7 s per stage per
    step.
  - The DeepGEMM scorer reaches 46 / 62 / 60% of FP8 peak (4K / 128K / 1M); MXFP8 projections
    63–71%. Layout copies take 5.8–7.4% of the bottleneck graph.
  - With the MXFP8 indexer, the trained indexer loss runs two score-recompute kernels per indexer
    call: the 64-head recompute and a 32-head FP32 recompute that the MXFP8 loss requires.

**Frozen vs trained.** Same code and layout; the formal saving (0.912 / 1.224 / 1.443 s) is
indexer-loss work: score recompute 0.27 / 0.45 / 0.58 s, indexer backward 0.18 / 0.20 / 0.29 s,
the extra LSE-only sparse forward 0.15 / 0.22 / 0.29 s, loss elementwise kernels 0.15 / 0.16 /
0.18 s. The frozen indexer's remaining cost is 0.7% / 1.7% / 5.4% of the graph.

**Remaining opportunities** (model estimates per step, not measured; nothing is implemented, and
optimization work is paused), low effort and strong evidence first:
1. Copy only the received samples in the dynamic-CP reroute, then prepare step n+1's data during
   the graph replay: about 0.4 s at 4K, at most 0.13 s elsewhere.
2. Batch the per-head Newton–Schulz of the MLA up-projections in Muon: about 0.15 s.
3. Trained indexer: drop the extra LSE-only sparse forward: 0.16–0.28 s.
4. Drop the redundant top-k compaction sort: 0.05–0.08 s.
5. Remove avoidable layout copies around absorbed MLA and the CP all-gather: 0.31–0.45 s.
6. Larger: the sparse-attention backward kernel (0.3–1.0 s), 1-layer stage boundaries with a
   cross-PP top-k handoff (0.1–0.5 s), selective recompute at 1M (about 0.5 s, memory risk), and
   intra-layer overlap of the CP collectives (0.15–0.35 s).

**Not recommended.** VPP2 at 4K/128K and VPP4 (or VPP3 with MTP7 in one chunk) at 1M: the
simulation predicts slower steps in every cell except 128K trained, where it predicts a 0.04 s
saving, within model error. One score-recompute kernel: the MXFP8 indexer loss needs the second.
MXFP8 output and MTP heads: PP3 is not critical. Tuning the absorbed-MLA BF16 batched
GEMMs: they are memory-bound (modelled at 75–85% of the HBM roofline).

**Limits.** Only 4 of 64 ranks per stage were profiled, so stage maxima may lie on unsampled
ranks. The formal graph replay is assumed equal to the profiled span. Two collectives are
identified only by order and size. Open measurements: a formal 4K VPP2 run, ncu and per-rank
timing of the 1M sparse-attention backward across CP positions, and CUDA-event timers in an
unprofiled run.

## Metric scope and qualification limits

- **Logged/model TFLOPS:** logical model arithmetic on valid tokens/lengths,
  including detached MTP heads; FMA=2. No precision weighting or recompute charge.
- **Execution-adjusted TFLOPS:** valid-pair defining GEMMs and accounted replay/
  recompute, plus the declared norm proxies. Excludes padding/tile inflation,
  router GEMMs, other elementwise/communication/optimizer work; not instruction
  counting or peak utilization. Unlogged MoK replay gives an interval, not
  an exact point. Use step time/tokens for speedup, not inflated replay TFLOPS.
- **Nonfinite-performance policy:** NaN/Inf loss or gradient-norm observations may be kept as
  numerical metadata, never as correctness or convergence evidence, and never waive timing,
  step/microbatch, sparse-capacity, topology, backend or capture/replay checks. A shortened top-k
  workload, dropped routes, fallback, CUDA/NCCL error or other structural failure invalidates the
  cell. Nothing is sanitized to obtain a result.
- Allocator maxima include warmup/capture. Device-used is sampled on all 256
  ranks after steps 1/2/32, not continuously; retain per-rank/PP-stage evidence.
- Full-iteration graphs apply to fixed realized packing, effective shape and
  microbatch counts. Enabled dynamic CP does not establish arbitrary changing
  CP/shape/microbatch graph support.
- The formal jobs control the allocation within each length, but each runs its cells once, in a
  fixed order; this is not ABBA evidence. No drift qualification is claimed. Every allocation is
  labeled and no cross-allocation ratio is claimed as a controlled causal speedup.
- Resolved commands, source/image/dependency identities, native YAML checksums,
  topology and raw logs remain in the experiment evidence.
