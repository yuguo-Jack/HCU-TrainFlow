# [Inference][MLA] Zero padding rows of the dynamic MLA attention output under FP8/FP4

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8874) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes dynamic-batching MLA zero the padding-token rows of its attention output before `linear_proj` under FP8/FP4, as standard attention does. Every dynamic-batching mixer (attention, MLA, SSM) now goes through one context method, and MTP draft forwards now report their own real row count, so their padding rows are zeroed too.

**Bug.**
- Dynamic batching pads the token dimension, in eager steps as well as under CUDA graphs. Padded requests have query length 0, so the attention kernels leave their output rows unwritten.
- Standard attention zeroes those rows whenever quantization scales are in use (`inference_context.zero_padding_tokens(core_attn_out)` in `forward_pre_attn_and_core_attn`). A per-tensor scale reads every row of `linear_proj`'s input.
- The dynamic branch of `MultiLatentAttention.forward` did not. Whatever the kernel left in the padding rows, NaN included, entered `linear_proj`'s input scaling and changed real tokens' outputs.

Affected: dynamic-batching MLA (`cache_mla_latents`) with a per-tensor recipe (tensorwise or delayed FP8, NVFP4). MXFP8 and FP8 blockwise scale row-locally. Prefill and mixed steps are affected. So are absorbed decode-only steps whenever the decode kernel leaves a zero-length slot's rows non-zero; on Blackwell that kernel is FlashInfer's (the Blackwell MLA decode PR, below). Reproduced on H100 with the kernel stubbed: 48 of 48 padding rows reached `linear_proj` as the kernel left them (NaN). Under tensorwise FP8, real-token outputs moved by up to 0.047 (max |out| 1.31) when the padding rows held 1e4 instead of 0.

A second gap: MTP draft and commit forwards are shaped by request count, but `gpu_view.real_token_count`, which the zeroing reads on device, still held the main step's token count B·(1+D). The controller moved it to the MTP row count only under the NVLS MoE dispatcher (`NVLSAllGatherVDispatcher.modify_real_token_count_for_mtp`, which writes the same tensor). Without NVLS, a draft forward's padding rows B..padded−1 counted as real.

**Fix.**
- `DynamicInferenceContext.zero_padding_tokens_for_quantization(tensor, config)` checks `is_using_quantization_scales(config)` and zeroes the padding rows. It is the one place that decides which configurations need the zeroing.
- `Attention.forward_pre_attn_and_core_attn` calls it once after both dynamic arms (the varlen kernel and the `_dynamic_core_attention_forward` hook, which had no zeroing). `MultiLatentAttention.forward` calls it on the kernel output, before the absorbed value up-projection. The SSM mixer's own predicate check is replaced by the same call.
- `DynamicInferenceContext.set_forward_real_token_count(n)` sets the device-side real token count. The MTP controller calls it before the commit pass and before the draft loop, with or without NVLS. The NVLS routing mask reads the same tensor, so NVLS behavior is unchanged, and the dispatcher's own setter is removed. EP dummy MTP forwards, whose output is discarded, are unchanged.
- The embedding zeroing in `GPTModel`/`HybridModel` keeps its own check: it is not a mixer output, also checks `is_dynamic_batching()`, and other tests patch it there.

**Tests.** `tests/unit_tests/transformer/test_multi_latent_attention.py::TestDynamicInferencePaddingRows` (1 H100, TE; the standard-attention cases need flash-attn >= 2.7.3, FA3 or FA4).
- The setup is a TE-spec `MLASelfAttention` or `SelfAttention` with a real `DynamicInferenceContext` holding one 16-token prefill padded to 64 tokens. `flash_decode_and_prefill` is stubbed with fixed real rows and a chosen fill in the padding rows.
- Each comparison of two fills runs one layer on fresh contexts, so both runs share weights. This fixes the harness flaw from the first GPU run of the repro, which compared two separately built layers.
- `test_mla_zeroes_padding_rows`: with an FP8 config, the `linear_proj` input rows past the 16 real tokens are zero when the kernel left NaN. Fails on `main` (48 of 48 rows NaN).
- `test_mla_real_rows_ignore_padding_under_fp8`: under tensorwise FP8, real-token outputs are bitwise equal for padding fills 0 and 1e4. Fails on `main`.
- `test_mla_absorbed_decode_zeroes_padding_rows` and `test_mla_absorbed_decode_real_rows_ignore_padding_under_fp8` do the same for the request's first decode step: decode-only, absorbed, one real token padded to 64. They pin the zeroing on the absorbed path, before the value up-projection. Both fail on `main`.
- `test_mla_absorbed_decode_zeroes_padding_rows_on_cuda_graph_replay` captures that decode step in a CUDA graph (BF16, with the zeroing switched on by patching the predicate). It replays the graph with real token counts 1 and 3: rows from the count published at replay on are zero, and the rows before it are not.
- Controls, which pass on `main`: standard attention zeroes the rows, standard attention's real rows ignore padding under FP8, and MLA's real rows ignore padding in BF16.
- `test_mtp_kv_cache_controller.py`: without NVLS, the commit pass and the draft loop publish their row counts (6, then 2) to `gpu_view.real_token_count`. These replace the two tests of the removed NVLS setter. The SSM stand-in contexts in `test_gdp_dynamic_inference.py` (including `TestGDPSpeculativeDecode`'s) bind the context's real method, and the predicate patch in `test_gpt_model.py` follows the move to the context. Only `DynamicInferenceContext` reaches these dynamic paths in production.
- On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), the regression tests pass (95 cases: 8 in `TestDynamicInferencePaddingRows`, 87 in `test_mtp_kv_cache_controller.py`) and fail on `main` (92 of 95 cases). On `main`, the four MLA padding cases fail their checks (non-zero `linear_proj` input rows, real rows that move with the padding fill), and the three controls pass. The CUDA-graph case and the 87 controller tests fail on `main` only because they patch names `main` lacks (`dynamic_context.is_using_quantization_scales`, `DynamicInferenceContext.set_forward_real_token_count`); they do not show the bug there. The bug on `main` is shown by the four MLA padding cases and by the step 3 GPU repro of R11-F2 on H100 (2 of 2 cases: 48 of 48 padding rows reach `linear_proj` as the kernel left them, and real-token outputs move by up to rel 0.047 under tensorwise FP8). The neighbor tests (`test_gpt_model.py::TestGPTDynamicInferencePaddingWithCudaGraphs`, `test_gdp_dynamic_inference.py`, `test_dynamic_context_mtp_kv_cache.py`) pass (169 cases; 3 TP=2 cases skip on one GPU).

**Determinism gate.** `tools/check_kernel_determinism_coverage.py` flags `attention.py` and `multi_latent_attention.py`. This PR needs the `determinism-exempt` label:
- The `attention.py` change is a refactor: the same kernel is called under the same condition, now also after the `_dynamic_core_attention_forward` hook, which no subclass implements yet.
- MLA's only new kernel launch is `zero_padding_rows`. That kernel stores zeros to rows past the device-side real token count and never reads the activation. It is already registered and replayed by `tests/unit_tests/determinism/kernels/test_inference_kernels.py::test_zero_padding_rows_replays`.
