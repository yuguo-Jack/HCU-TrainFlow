# What does this PR do?
Reduce reserved GPU memory by allocating activation reload destinations on the compute stream, while preserving the required stream ordering.


### Implementation

Two allocation sites leave reusable GPU memory in side-stream allocator pools:

- **Activation reloads:** allocate destinations on the consumer's compute stream. Before copying, the H2D stream waits for prior compute-stream use of those blocks and for the group's offload completion. The consumer waits for the H2D reload-completion event before reading them. This preserves both lifetime dependencies without using `record_stream` for the eager reload handoff. The graph-capture path is preserved.

### Memory and throughput

Ultra configuration, fused-MoE activation offload fraction 0.6, mock data, 16 updates; steady-state window 6–15. Memory is GiB, maximum over ranks. These two comparisons isolate the reload change:

| GPUs / job | Configuration | Reserved: baseline → reload | Allocated: both | Device memory: baseline → reload | Step time: baseline → reload |

- lhb8125 · comment · 2026-10-30T13:40:20Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8666#discussion_r4424226259)

File: `megatron/core/pipeline_parallel/fine_grained_activation_offload.py` · line None

**[IMPORTANT Observability]** Could we merge `_reload_into()` back into the decorated `reload()` and accept a keyword-only optional `destination=None`?

The bulk path now calls `_reload_into()` directly, bypassing the `_otel_trace_fn('activation_offload', 'megatron.activation.reload')` decorator that remains on `reload()`. When this span group is enabled, normal bulk reloads therefore lose their reload spans, while the on-demand fallback still emits them.

A single `reload(..., *, destination=None)` can allocate only when no destination is supplied, then perform the copy, pinned-source release, and view restoration. Bulk reload would keep allocating on the consumer stream and call `reload(state, stream=self.h2d_stream, destination=gpu_tensor)` inside the H2D stream context. This preserves the existing stream ordering, avoids allocating twice, and keeps both paths under one tracing entry point.

I checked this refactor locally with CPU control-flow doubles: both paths allocate once and invoke the reload decorator once per tensor. Real GPU ordering and CUDA graph replay were not tested.

- lhb8125 · comment · 2026-10-30T13:51:03Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8666#discussion_r4424334947)

File: `megatron/core/pipeline_parallel/fine_grained_activation_offload.py` · line None

**[SUGGESTION]** Could we rename this helper to `_allocate_reload_buffer`? Its responsibility is to allocate an empty GPU buffer for a subsequent reload. `buffer` describes the object being allocated more directly, whereas `destination` is a relational term whose meaning depends on the later copy operation. `_allocate_reload_buffer` would make the helper's purpose easier to read at both call sites. This is a readability suggestion; the allocation behavior can stay unchanged.
