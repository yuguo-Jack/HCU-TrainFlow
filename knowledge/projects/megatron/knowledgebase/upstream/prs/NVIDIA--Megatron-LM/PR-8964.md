# [Core][MoE][BatchInvariant] Declare the expert offsets' alignment to each inference grouped GEMM and check it on the host

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8964) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Each inference MoE grouped GEMM now receives the alignment its expert offsets were built with, and checks it on the host against its own requirement. The batch-invariant DeepGEMM grouped GEMM therefore rejects offsets built from raw cumulative counts, or with another backend's alignment, before they can silently mix experts. The PR also documents the offsets contract, checks the shape of `offs`, and pins the inference MoE to aligned offsets.

**Bug (latent).** `grouped_gemm_batch_invariant(a, b, offs=, m_total=)` runs DeepGEMM's contiguous M-grouped bf16 GEMM over the expert blocks that `offs` delimits. It serves FC1 and FC2 of every BF16 inference MoE layer under batch-invariant mode, via `inference/moe/batch_invariant.grouped_mm`. DeepGEMM takes the expert of each M tile from the tile's first row (`scheduler/gemm.cuh`, `grouped_layout[m_block_idx * BLOCK_M]`), so every expert block must start at a multiple of `grouped_gemm_batch_invariant_alignment()`. Nothing checked this. With `offs = [A + 5, 2A + 5]`, expert 1's rows `A + 5 .. 2A - 1` were multiplied by expert 0's weights without any error. On H100 and GB200, 123 of expert 1's 128 rows were wrong (dfw 21222522, hsg 8572259; oracle `test_deepgemm_grouped.py::test_misaligned_offsets_raise_or_stay_correct`).

Production is not affected: `mcore_fused_moe` builds `offs` with `permute_tokens(..., alignment=batch_invariant.grouped_mm_alignment())`. A new caller would be affected if it passed raw cumulative counts or offsets built for another backend, for example torch `grouped_mm`'s 16.

## Fix

**The alignment travels with the offsets.** `mcore_fused_moe` already chooses each backend's grouped GEMM (`mm_fn`) and the alignment it gives the permute (`expert_alignment`) together. It now passes that alignment with the offsets, as `mm_fn(x, w, offs, expert_alignment)`. Each backend checks the declared alignment against its own requirement:

| Entry point | Signature | Requirement |
|---|---|---|
| `batch_invariant_kernels.grouped_gemm_batch_invariant` | `(a, b, *, offs, offs_alignment, m_total)` | `offs_alignment > 0` and a multiple of `grouped_gemm_batch_invariant_alignment()` (DeepGEMM's) |
| `inference.moe.batch_invariant.grouped_mm` | `(x_bf16, weight, offs, offs_alignment)` | forwards to `grouped_gemm_batch_invariant` |
| `fused_moe._mxfp8_grouped_mm` | `(act, weight, offs, offs_alignment)` | `offs_alignment > 0` and a multiple of `MXFP8_SCALE_ROW_BLOCK` (128), as `scaled_grouped_mm` and the swizzled scale layout require |
| `fused_moe._bf16_grouped_mm` | `(x_bf16, weight, offs, offs_alignment)` | none: torch `grouped_mm` takes groups starting at any row |

The checks compare host integers, so they add no sync, allocation or kernel, and they are safe under CUDA-graph capture. A violation raises an `AssertionError` that names both alignments. `offs_alignment` is keyword-only and has no default in `grouped_gemm_batch_invariant`, so every caller has to declare it.

**`offs` shape.** `grouped_gemm_batch_invariant` also asserts `offs.shape == (b.shape[0],)`. With more entries than experts, rows could be assigned an expert that `b` does not have, and DeepGEMM would address that expert's weights past the end of `b`. The sibling entry point `_bf16_grouped_gemm_contiguous` already asserts `len(counts) == E`.

**Documented, not checked: the offset values.** The declared alignment is trusted. A caller that declares 128 but passes raw cumulative counts is not caught. The values live on the device and change between replays of a captured CUDA graph, so checking them would take one of three things:

- a host sync on every MoE GEMM;
- a device-side assert, which kills the process;
- a sticky device flag OR-ed on the hot path and read at a later sync. This is capture safe and non-fatal, and training already uses one (the MoE dispatcher's `over_budget`, read by `paged_stash.py`).

The flag is the only acceptable option of the three. It is not taken because nothing on the inference decode path would read it, and the only producer of these offsets aligns them by construction. The docstring of `grouped_gemm_batch_invariant` states this and points to `_bf16_grouped_gemm_contiguous`, which pads per-expert counts known on the host.

**Comments.** `_offs_to_m_indices` and the DeepGEMM alignment comment claimed that DeepGEMM skips rows tagged -1. They now say that it computes and stores those rows with expert 0's weights, and that the rows are ignored or dropped (observation O8a-N6).

Names are unchanged. The implementation is already called `_bf16_grouped_gemm_aligned_contiguous`, and the new required keyword is what makes the precondition visible at every call site.

## Tests

- `tests/unit_tests/transformer/moe/test_moe_batch_invariant.py::test_grouped_gemm_rejects_offsets_built_with_another_alignment[raw_counts|torch_grouped_mm|half|zero]`. It builds offsets for counts `[A + 5, A]` with alignment 1, 16, A/2 or 0 and declares that alignment; each must raise before DeepGEMM runs.
- `...::test_grouped_gemm_rejects_offsets_not_one_per_expert[fewer_than_experts|more_than_experts]`. It passes one or three offsets for two experts. Every extra block is empty, so the launch would stay inside `b`.
- `...::test_inference_moe_aligns_every_expert_block`. It runs `mcore_fused_moe` under batch-invariant mode with expert counts `[A + 5, 1, 0, 2A + 1]` and records what reaches `grouped_gemm_batch_invariant`. FC1 and FC2 must both receive the aligned blocks `[2A, 3A, 3A, 6A]`, declared with DeepGEMM's alignment. This pins the caller of the precondition whose values stay unchecked.
- `tests/unit_tests/inference/test_mxfp8_utils.py::TestPermuteAndQuantizeMxfp8::test_grouped_mm_rejects_offsets_built_with_another_alignment[1|16|32|64]`. The MXFP8 grouped GEMM must reject these alignments before calling `scaled_grouped_mm`. The existing `test_batch_invariant_moe_dispatches_fused_permute_quantize` fake grouped GEMM takes the new argument.

On `main`, every case above fails with a `TypeError`, because the entry points there do not take the alignment. At the first commit, before the alignment argument existed, the shape cases failed on `main` with `DID NOT RAISE`.

- **H100, first commit** (dfw 21232738): the shape test and the inference pin passed, and the shape test failed on `main`.
- **Review follow-up:** checked on CPU under the Triton interpreter, with a fake DeepGEMM that applies the first-row-of-tile rule:
  - misdeclared alignments raise and aligned ones (A, 2A) run correctly;
  - the MXFP8 check rejects 1/16/32/64 and passes 128/256;
  - `mcore_fused_moe` passes `([256, 384, 384, 768], 128)` to both GEMMs. The interpreter cannot run the activation and unpermute kernels, so a torch stand-in replaced the activation.

  The follow-up's GPU run is pending.

`tools/check_kernel_determinism_coverage.py` flags `batch_invariant_kernels.py`, `inference/moe/batch_invariant.py` and `inference/moe/fused_moe.py`, which are registered as whole files. This PR changes no kernel, dispatch or numerics (host assertions on integers and tensor metadata, an extra argument, docstrings), so it needs the `determinism-exempt` label.

## Review follow-up

- The declared-alignment guard described above replaces the earlier documentation-only treatment of the alignment (review P2).
- The rationale now names the sticky-flag option and why it is not taken. The earlier text said a check needed a host sync or a fatal assert (review P3).
- The two stale comments about DeepGEMM skipping rows tagged -1 are fixed (review P4).
- The oracle case `test_deepgemm_grouped.py::test_misaligned_offsets_raise_or_stay_correct` belongs to the oracle PR. Its calls need the new `offs_alignment=` keyword. A misaligned `offs` declared with an alignment DeepGEMM cannot use now raises. One declared with DeepGEMM's alignment but holding misaligned values is still silently wrong, by the documented contract.
