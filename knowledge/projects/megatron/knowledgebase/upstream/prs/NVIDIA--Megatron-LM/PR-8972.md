# [Test][Inference] Independent oracles for FlashInfer MoE, GEMM and quantization call sites

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8972) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Adds `tests/unit_tests/inference/oracles/flashinfer_moe/`: independent oracle tests for the FlashInfer MoE, GEMM and quantization kernels that Megatron's inference path calls. No production code changes.

**Stacked on the oracle harness PR #8966 (`test/inference-oracle-harness`)**, whose `oracle_utils` it uses. Retarget to `main` once the harness is merged.

## Why

These call sites had no independent check:
- the routed MXFP8 weight repack (`shuffle_matrix_a` and the scale shuffle) was never compared with anything;
- the routed MXFP8 MoE kernel was tested only for batch invariance at a fixed row count, and none of those tests ran in CI (they are Blackwell-gated without `launch_on_gb200`);
- the per-token NVFP4 MoE was checked by cosine similarity, which cannot see a per-token scale error under squared ReLU (`relu(s z)^2 = s^2 relu(z)^2`);
- the BF16 `cutlass_fused_moe` was only ever mocked;
- `mm_mxfp8` with FlashInfer weights was never executed.

A wrong layout or scale in any of them gives wrong but finite MoE outputs that no test flagged.

## What is in it

One module per kernel. Each has a contract written from the call site, MCore's MoE math and FlashInfer's documented API; a reference that does not share the kernel's algorithm; inputs derived from the kernel's structure; the harness tolerance policy (no hand-picked `atol`); memory checks (guard bands, NaN poison, read-only inputs, one `sanitizer` case); and hardware markers.

- **`spec.py`** (shared):
  - OCP MX and NVFP4 element and scale codecs;
  - an exact MXFP8 quantizer with the RCEIL scale (the scale exponent is found by exact comparisons);
  - the cuBLAS 128x4 scale layout as a per-element offset formula;
  - the TRT-LLM Major-K row map;
  - an fp64 per-token MoE reference;
  - generators of structured inputs.
- **Lossless inputs for the quantized MoEs.** The MXFP8 and NVFP4 kernels requantize the FC2 input inside the kernel. With dense random inputs, rounding noise flips FP8/FP4 codes there, so no reference could bound the kernel without a hand-picked tolerance. The tests therefore use:
  - FC2 weights and tokens on the MX/NVFP4 grid, each block's amax pinned so every RCEIL implementation picks the same scale;
  - a rank-1 FC1 `u v^T` with `u = +-2^-n` at constant levels inside each FC2-input quantization block;
  - for MXFP8, tokens whose `v . x` is a power of two.

  Then every quantization, the in-kernel one included, is exact under both RCEIL and OCP's floor rule, and the fp64 MoE of the unquantized values is the exact contract. CPU tests check each of these claims.
- **`test_shuffle_matrix_a.py`**, **`test_get_shuffle_matrix_sf_a_row_indices.py`**: the routed MXFP8 repack is exact against the layout definitions:
  - data and scales, padding, an exact round trip, and refit into 0xFF-poisoned storage at fixed addresses;
  - Megatron's `_unshuffle_cublas_scale` and `_block_scale_interleave`;
  - on Blackwell, byte equality with FlashInfer's own `shuffle_matrix_sf_a`. This guards Megatron's private reimplementation against FlashInfer layout changes.
- **`test_mxfp8_quantize.py`**: `quantize_routed_mxfp8_input` (linear scales) and `MXFP8Tensor.from_bf16(backend="flashinfer")` (swizzled), bit-exact against the spec, with codes and scales reported apart. Cases:
  - the kernel's two code paths and column/row tiles; production sizes;
  - ties at every E4M3 midpoint; an amax of exactly `448 * 2^k` and its neighbours;
  - zeros, -0.0 and subnormal codes; an input that is a prefix of a NaN-filled buffer;
  - NaN/Inf;
  - opt-in (`large`) element offsets past 2^31.
- **`test_trtllm_fp8_block_scale_routed_moe.py`**, **`test_cute_dsl_moe_wrapper.py`**, **`test_cutlass_fused_moe.py`**: the MoE outputs per row against the fp64 reference. The bound comes from a trusted fp32 torch implementation on the same device that sums the routes in BF16, as the documented finalize does. Covered:
  - tokens around the kernels' tiles, top-k 1 to 8, EP offsets, padded and production shapes, empty experts and -1 rows;
  - bounded-row prefixes with a guarded, poisoned output buffer. For NVFP4 the test also checks that every per-token input handed to FlashInfer has only the prefix rows;
  - dispatch through `InferenceGroupedMLP._flashinfer_forward`;
  - CUDA graph replay with an in-place weight refit/refresh;
  - bitwise batch invariance across row counts (routed MXFP8; the NVFP4 two-stage finalize, with up to 2 and with 6 local routes per token, and under a permuted batch);
  - both finalize paths, and every GEMM2 tactic FlashInfer reports valid (BF16);
  - BF16 Relu2 and ClampedRelu2 (L = 0.5, 8), NVFP4 Relu2 and SwiGLU, and MXFP8 ClampedRelu2 in the saturated and the unsaturated regime (below).
- **`test_mm_mxfp8.py`**: `mm_mxfp8` and `_mm_mxfp8_flashinfer` against an fp64 GEMM of MX-exact operands. The weight's FlashInfer bytes are first decoded by the spec. Also covered: a preallocated output with guard bands, and the `K < 128` / `N < 128` / wrong-`out` errors.

## Tests

Hardware:
- **Blackwell (GB200):** everything except the BF16 Relu2 CUTLASS MoE tests, which run on H100 too, and the layout tests, which run on any GPU with FlashInfer. Every Blackwell test carries `launch_on_gb200`.

Cases:
- **H100:** 333 (layout modules, BF16 Relu2, and since the sixth commit the 3 CPU input checks for MXFP8 ClampedRelu2). FlashInfer's SM90 CUTLASS fused-MoE module must be built (flashinfer-jit-cache or one prebuild; its JIT build takes about 40 minutes). Without it the CUTLASS tests skip, or fail on a runner that declares H100.
- **GB200:** 696 collected (650 before the sixth commit). 3 are the opt-in `large` cases, which passed on GB200.

Local checks only; no GPU run yet:
- **CPU:** 117 passed. These are the spec codecs against torch's E4M3 cast, the layout formula against the existing `ref_swizzle`, Megatron's repack helpers, the lossless-input claims and the call-site argument checks. The FlashInfer- and GPU-gated cases skip.
- **CPU with FlashInfer's pure-torch row-index helper stubbed:** the 304 layout cases pass.

GPU runs (H100 dfw-21220623, GB200 hsg-8571739, on the first commit) found two kinds of failure:
- **Test-side, fixed in the second commit.** The oracles had not modelled two BF16 stores that the
  kernels make, as MCore's BF16 path does:
  - FlashInfer's unfused `Relu2` writes the FC1 output in BF16 before the activation;
  - the per-token NVFP4 MoE stores the FC2 input in BF16 before requantizing it.

  A CPU model of these stores reproduces the GPU errors to 3-4 digits.
- **Findings.** These tests are expected to keep failing on GB200 until the findings are resolved:
  - `test_mxfp8_quantize.py::test_nan_element_stays_nan_and_is_isolated`: a NaN element is quantized to `+448 * scale` (finding O4b-N1);
  - `test_infinite_element_saturates_with_its_sign_and_is_isolated[-inf]`: -Inf decodes to `+448 * 2^127` (finding O4b-N2);
  - `test_trtllm_fp8_block_scale_routed_moe.py::test_hidden_128_is_served_or_rejected_by_megatron[128|256]`: FlashInfer has no TRT-LLM kernel config for a hidden size of 128, and Megatron's config does not reject it; the first forward dies with a tvm `InternalError` (finding O4b-N3).

Mutation testing (GB200) left three survivors in the NVFP4 path; the fourth commit handles them:
- **Hidden states not cut to the bounded prefix.** FlashInfer sizes its work by `token_selected_experts`, so the output could not show the extra rows. The bounded-rows test now records the row count of every per-token argument Megatron passes to FlashInfer's quantizer and to `CuteDslMoEWrapper.run`. The contract says only the prefix is processed.
- **Batch-invariant mode keeping the fused BF16-atomic finalize.** Every two-stage case gave a token at most 2 local routes, and a sum of two BF16 values does not depend on order. The batch-invariance test now also routes each token to 6 local experts and checks a permuted batch bitwise. Catching this mutant depends on the atomics landing in a different order between launches, which is very likely with 6 routes.
- **K and N padded to 128 instead of 256.** All 48 cases still pass, including shapes whose K is an odd multiple of 128. The padding is zeros, so the result does not change. The 256 requirement in the code comment looks stricter than this FlashInfer version needs; padding to 128 could be a simplification. This is not a bug, and no test pins the constant.

A fifth commit completes the `sanitizer` cases (one small case per kernel, run under compute-sanitizer memcheck): the scale repack and the MXFP8 ClampedRelu2 MoE had none that ran on the GPU.
- `test_get_shuffle_matrix_sf_a_row_indices.py::test_sanitizer_small_case` (H100 and GB200) runs the routed scale repack and its round trip on the GPU for 2 experts of 97 rows by 5 scale columns, so every shuffle block and swizzle tile is partial.
- `test_cutlass_fused_moe.py::test_sanitizer_mxfp8_clamped_relu2_small_case` (GB200) runs the saturated MXFP8 ClampedRelu2 oracle at H = I = 128 with 65 tokens, top-2, at EP rank 1 of 2.

The memcheck pass covers 3 cases on H100 and 8 on GB200, one per kernel; it has not run yet.

A sixth commit adds the oracle for **MXFP8 ClampedRelu2 outside saturation**; until then only the saturated regime (every FC1 output beyond 40 L, activation exactly `L^2` or 0) was checked.
- **Contract** (from `flashinfer_cutlass_mxfp8_moe` and MCore's `clamped_squared_relu`): the FC2 input is `mxfp8(act(z))`, the activation of the FP32 FC1 output requantized with the RCEIL scale. A correct kernel may evaluate `tanh` approximately (FlashInfer uses `tanh.approx.f32`, about 2^-11) and may store the activation in BF16 first, as MCore's BF16 path does. Together these move an activation by less than 2^-8.4.
- **Inputs** (`ClampedMxfp8Problem`): MXFP8- and BF16-exact operands, a rank-1 FC1 with one all-positive and one all-negative 32-row block (so every routed token has an all-zero FC2-input block), and dense tokens scaled so that `log2(|z| / L)` covers a regime: near zero (2^-13), the knee at L, the transition near 2.4 L where the activation reaches `L^2` at FP8 precision, and FP32 saturation up to 40 L. Tokens are redrawn until moving every activation by 2^-7 (plus the FP32 noise of FC1) changes no FC2-input code or block scale.
- **Oracle:** the fp64 MoE with the spec MXFP8 requantization of the fp64 activation is then the FC2 input of every correct kernel. The test checks that the trusted fp32 implementation requantizes identically, then bounds each row at factor 2.
- **Cases (GB200):**
  - 36 pairwise cases over L 0.5, 3.5, 6, 8, 16 x regime, tokens, shapes up to (2688, 2048), top-k, EP, finalize and zero tokens. RCEIL and OCP's floor rule agree on these inputs.
  - 3 cases at a power-of-two L in the transition regime, where 46% of the block amaxes have a mantissa in (1.75, 2). There RCEIL keeps the element and OCP's floor rule would clip it by up to 12.5%.
  - Every GEMM1 tactic (the fused activation + MXFP8 epilogue variants) and every GEMM2 tactic, with both finalizes.
  - A CPU check of the input claims (3 cases, any runner).
- **CPU kernel models** (scratch, not committed), against the same oracle:
  - Pass: a correct model with `tanh` off by ±2^-11 and a BF16 store.
  - Fail: a hard clamp `min(relu(z), L)^2` (except near zero, where it equals the contract), round-toward-zero E4M3 codes, elements scaled by the unrounded `amax / 448`, and a `tanh` off by 2^-6 or 2^-8.
  - An OCP-floor requantizer passes the sweep and fails the RCEIL cases.

## Notes for reviewers

- **GB200 CI buckets.** In a fresh container these tests JIT-compile FlashInfer's MoE kernels on first use, about 23 minutes on GB200. `flashinfer_moe/` therefore has its own GB200 bucket, and `test_cutlass_fused_moe.py` (the largest compile) one of its own. A CI-shaped run took 979 s and 619 s for them, and 842 s for the remaining oracle directory, all under the 30-minute limit. #8873's FlashInfer JIT cache would remove the compile time.
- **FlashInfer bugs run as strict xfails.** No Megatron change can fix O4b-N1 (`test_nan_element_stays_nan_and_is_isolated`) or O4b-N2 (`[-inf]`), so they carry `ou.xfail_upstream(..., "flashinfer-python", fixed_after="0.7.2.post1", raises=AssertionError)`, bounded by the version `uv.lock` pins for the CI image. A FlashInfer release with the fix makes them XPASS, which fails until the mark is removed. `[+inf]` stays a plain test. O4b-N3 still fails on `main` until s4f-mxfp8-moe-hidden-size lands.
- **FlashInfer NaN/Inf behaviour** (predicted from source, confirmed on GB200). FlashInfer's MXFP8 quantizer takes the block amax with `__hmax2`, which ignores NaN, and then clamps with `fminf`/`fmaxf`, which turn NaN into the bound. For an infinite element the scale saturates to `2^127`, whose `rcp.approx.ftz` flushes to 0. So a NaN hidden state entering the routed MXFP8 MoE becomes a finite value, unlike the torch and vLLM backends, and -Inf changes sign. The tests assert the contract (NaN stays NaN; Inf keeps its sign) and isolation of every other block and row.
- **RCEIL boundary.** The kernel computes the scale as `amax * rcp.approx(448)`, rounded up. `test_amax_at_and_around_448_times_a_power_of_two` checks that an amax of exactly `448 * 2^k` gets scale `2^k`.
- **BF16 storage points.** The references store in BF16 where the kernels do: the FC1 output of the unfused BF16 `Relu2` (only `ClampedRelu2` is fused into GEMM1's epilogue), and the FC2 input of the per-token NVFP4 MoE. NVFP4 tokens are redrawn when the row's common factor sits within 2^-16 of a BF16 rounding boundary, so FP32 noise cannot round it the other way.
- **Precision of the trusted implementations.** The MoE tests sum route outputs in BF16, the precision FlashInfer documents for its fused finalize. With FP32-finalize kernels the bound is therefore looser than it needs to be for top-k 6 to 8. Any layout, scale, routing or offset error still exceeds it by orders of magnitude.
- **Not covered.**
  - MXFP8 FC1 accumulation over dense K with an exact oracle: up to 8 nonzero K blocks per token; dense inputs appear in the batch-invariance tests.
  - MXFP8 ClampedRelu2 activation errors below 2^-7 of the activation (the input margin), and FC2-input elements in the E4M3 subnormal range of their block.
  - Quantizer blocks with amax below about 2^-100, where flush-to-zero legitimately differs.
  - Run-to-run determinism under fused-finalize tactics, which #8574 tests.
- **Determinism manifest.** No kernel or dispatch changes, so there is no determinism test or manifest entry.
