# What does this PR do?
<!-- Add a one line overview of what this PR aims to accomplish. -->
This is the first of four stacked PRs that introduces training support for a simplified version of DSA. These stacked PRs split PR #[6869](https://github.com/NVIDIA/Megatron-LM/pull/6869).

This PR includes Triton kernels and autograd support for simplified DSA with GQA attention. Included are triton kernels for both the indexer and sparse GQA attention, along with wrapper classes and torch autograd functions. A summary of the changes included in summary of the changes in each file is included below.

Miscellaneous notes:
- Mathematically, the simplified DSA indexer is topk(QK), where Q and K are one head.
- The kernels are "min memory". That is, they compute QK on tiles on a block of Q and a block of K, and merge topk across the K dimension. This is to avoid materializing a `seq_len x seq_len` QK matrix.

| File | Change |
|---|---|
| `megatron/core/transformer/experimental_attention_variant/dsa_min_memory_triton.py` | Triton kernels for the simplified indexer: selected-score forward/backward, gathered linear wgrad, RMSNorm stats, top-k index blocks. |
| `megatron/core/transformer/experimental_attention_variant/dsa_min_memory.py` | Minimum-activation memory autograd functions over those kernels (`DSASimplifiedMinMemoryGQAFn`, `DSASimplifiedDenseIndexerLossFn`), tile-wise projection/routing helpers, per-stage timing profiler. |

- kwangjunahn · comment · 2026-09-25T19:54:33Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/7152#discussion_r4108124337)

File: `megatron/core/transformer/experimental_attention_variant/dsa_min_memory.py` · line None

To clarify my suggestion above.

For example, consider `S=131072` and `query_chunk=8192`. There are 16 query tiles, whose `q_end` values are:
`8192, 16384, ..., 131072`.
These prefixes contain a total of 1,114,112 token row which is equivalent to processing the complete sequence `8.5` times. Let's hence call this `8.5s`.
 The current forward effectively projects each prefix twice. Once for routing and once again for the selected-score KL calculation. So in total, the computation work is about `17S`.

I think there are two options to reduce the repeated computation: 

1.  **Reuse within one query tile.** After routing projects `K[:q_end]`, keep that same tensor long enough to calculate the selected scores for that query tile, then release it before processing the next tile. This would reduce forward learned-K projection work from `17S` to `8.5S`. 

2. **Reuse throughout one forward invocation.** Construct the complete `full_k_index` once before the query-tile loop, preferably by filling it in bounded chunks. Every query tile would then use the required slice, such as `full_k_index[:q_end]`, rather than projecting its prefix again. Do not put this temporary tensor in `ctx.save_for_backward`, and allow it to be released when this forward invocation finishes. This would project each sequence position only once, reducing forward learned-indexer-K  projection work from approximately `17S` to `S`.

Similar logic I think applies to the backward pass to save the repeated computation.
