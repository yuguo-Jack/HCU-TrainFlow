# Overlap FsdpMuon communication with Newton-Schulz across FSDP groups

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8684) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

## What does this PR do?

Muon's optimizer step works through the FSDP groups one at a time: gather each weight's shards to an owner rank, run Newton-Schulz there, then send the update back. Until now `FsdpMuon` waited for each transfer before moving on. This PR overlaps the transfers with Newton-Schulz across groups. A new `lookahead` argument sets how many groups ahead the transfers are started; 0 keeps the old, non-overlapped order.

Stacked on #8548 and #8547: until they land, the diff also shows their commits.

## Implementation

- `gather` and `scatter` now return handles to their in-flight peer-to-peer transfers instead of waiting for them. Callers wait only where they need the result.
- `FsdpMuon.step` starts the gathers for the next `lookahead` groups before running Newton-Schulz on the current group, starts each scatter right after that group's Newton-Schulz, and applies a group's update only after `lookahead` later groups have been scattered. This bounds the number of buffers alive at once.

## Validation

On 8 H100 (AWS), the whole `mfsdp_v2` unit test directory passes, including checks that Muon matches unsharded training at `lookahead` 0 and 2.

On the DSV4 recipe (7 layers, 64 GB200, EP64, MXFP8), we measured the optimizer step time with Nsight on ranks 0, 32 and 63, steps 9 to 11:

| | Optimizer step |
|---|---:|
| previous serial `FsdpMuon` | 1186 ms |
| `lookahead=0` (no overlap, new code) | 1217 ms |
| `lookahead=2` | 986 ms |
| `lookahead=8` | 848 ms |
| distributed Muon (for reference) | 728 ms |

With `lookahead=8` the optimizer step is about 28% shorter than before. A larger lookahead keeps more buffers alive, but the optimizer step's peak memory stays 12 to 19 GiB below the forward/backward peak in all runs, so the iteration's peak memory does not grow. One run per setting, so differences under 2 to 3% are noise.
