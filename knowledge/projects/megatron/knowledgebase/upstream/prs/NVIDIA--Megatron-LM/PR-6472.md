# [Dev] Introduce forward sharing state and enable repeated MTP sharing

# What does this PR do?

Introduce a shared infrastructure for cooperating components to exchange per-forward payloads, migrate existing DSA cross-layer IndexShare onto it, and use it to implement independently selectable index and latent-KV sharing across repeated MTP prediction depths.

## Implementation and review order

The PR is organized into three commits:

1. **Generic forward sharing state.** Introduce `ForwardSharingState`, a type-keyed payload registry with explicit lifetime management. Payloads define their own tensor layout and per-layer indexing. State is carried through existing packed-sequence parameters, attention masks, or config, without adding a new Transformer-layer forward argument. Outer scopes clear payloads on exit; nested scopes join the active lifetime. Temporary state binding and per-checkpoint snapshots preserve the sharing records needed by existing checkpoint/schedule paths. Ordinary DSA cross-layer IndexShare is migrated to this infrastructure.
2. **Repeated MTP index sharing.** Reuse depth-0 sparse-attention indices at later depths of the same repeated physical MTP layer. Ordinary IndexShare still determines how depth 0 obtains its indices; repeated-MTP sharing controls their reuse at subsequent depths. DSA owns the tensor payload, while MTP controls source/consumer sequencing.
3. **Repeated MTP latent-KV sharing.** Independently reuse depth-0 post-RoPE, post-TP/CP-layout latent KV, avoiding repeated KV computation and CP gathering. Shared KV stays connected to autograd so consumer gradients accumulate into the source projection.

The common infrastructure manages payload lookup, binding, and cleanup; it does not prescribe DSA tensor layouts or make arbitrary sharing/recompute combinations safe.

## Feature scope and compatibility

Set `mtp_use_repeated_layer: true`, `mtp_num_layers > 1`, and select `"sparse_attention_index"`, `"latent_kv"`, or both through `mtp_repeated_layer_shared_components`. Repeated-MTP sharing currently supports the DSA GPT MTP path only. Queries and sparse attention remain query-dependent and are computed at every depth. This is training-time activation reuse, not inference KV caching.

- Existing selective recompute of `mlp`, `moe`, `moe_act`, `shared_experts`, `layernorm`, and `mhc` remains supported, subject to those modules' existing requirements.
- `mla_up_proj` recompute supports index-only sharing, but not latent-KV sharing in this PR.
- Full recompute and selective `core_attn` recompute remain unsupported with repeated-MTP sharing. Set `recompute_modules` explicitly, since selective recompute defaults to `core_attn`.
- Attention CUDA graph capture remains unsupported with repeated-MTP sharing; MoE-only scopes remain compatible. Unsupported inference and hybrid-layer combinations are rejected explicitly.

The dependent draft #7107 extends repeated-MTP recompute compatibility; it is not required for the ordinary IndexShare checkpoint handling or the selective combinations supported here.

## Strict Review Summary

**CRITICAL: 1 · IMPORTANT: 7 · SUGGESTION: 3**

The core design is sound and carefully executed: `MTPDSAIterationContext` is a clean carrier, `_checkpointed_forward` correctly threads the shared tensors as *positional* checkpoint args so the iteration-0 graph survives recomputation, the new native-parity test suite is genuinely thorough, and the explicit `RuntimeError`s at every producer/consumer boundary make misuse loud rather than silent. The CUDA-graph and config rejections in `__post_init__` are the right instinct.

The findings below are concentrated in one place: **the `core_attn` selective-recompute path did not get the same treatment the `mla_up_proj` and `full` recompute paths did.**

---

### Most impactful

**1. `core_attn` selective recompute silently drops consumer-iteration gradients (CRITICAL)**

`absorbed_mla.py:897-899` threads `mtp_dsa_context` into `_checkpointed_attention_forward` via closure capture from inside `custom_forward`. `CheckpointFunction.forward` runs that function under `torch.no_grad()`, so `capture()` at `dsa.py:2409` stores a `source_key` with `grad_fn=None`. Every consumer iteration's gradient then terminates at that detached key — `linear_kv_down_proj` and `kv_layernorm` receive roughly `1/mtp_num_layers` of their correct weight gradient, with no error raised.

**This is reachable by default**: `recompute_modules` defaults to `["core_attn"]` (`transformer_config.py:2205-2206`), so plain `--recompute-granularity selective` hits it. Nothing in `__post_init__` rejects the combination, and the new tests only cover `["mla_up_proj"]` and `"full"`. `_checkpointed_forward` already demonstrates the correct pattern (shared tensors as positional checkpoint args, recompute-local context rebuilt inside `custom_forward`) — either apply it here, or reject the combination explicitly. Threading the context into a path that produces wrong gradients is worse than not supporting it.

Secondary effect on the same path: because `custom_forward` re-runs during `backward`, `capture()` fires twice and overwrites `produced_tensors` after the block has already consumed it.

**2. The non-sharing path is not actually unchanged (IMPORTANT)**

The PR description states the existing non-sharing path is unchanged, but the `select_rotary_pos_emb` extraction changes the key branch to slice by `q_absorbed.size(0)` where the previous code passed the unsliced `rotary_pos_emb`. Under TP+SP these differ, since `kv_compressed` is explicitly gathered to full sequence while `q_compressed` is not. This needs a non-sharing TP2/SP regression test to substantiate the claim.

**3. Selective-recompute branch gates on the wrong condition (IMPORTANT)**

`absorbed_mla.py:741` splits on `mtp_dsa_context is not None` rather than `shared_key is not None`, so iteration 0 loses its joint Q/K checkpoint unnecessarily even though it computes both tensors. `qkv_up_proj_and_rope_apply` already handles `shared_key` internally, so the narrower gate is a small change that recovers iteration-0 memory behavior.

---

### Also worth addressing

- **Indexer loss weighting changes** with the flag (`dsa.py:2064-2069`) — `save_loss_to_tracker` accumulates with `+=` per layer, so gating `computes_topk` on `not reuse_mtp_source` turns N charges per microbatch into one. Defensible semantics, but it silently alters the objective when the flag is flipped on an existing recipe, and it is neither documented nor measured against the non-sharing baseline.
- **Fused DSA kernel silently disabled** for the whole MTP layer (`dsa.py:2219-2220`) with no config-time warning and no measured step-time delta.
- **`source_key` / `topk_indices` locality mismatch** (`dsa.py:2037-2040`): a globally-gathered key is paired with TP-locally-sliced top-k indices. The invariance of the TP row window across iterations is load-bearing and undocumented; the TP2/SP test should pin row counts on both source and consumer.
- **Conditional return arity** on public `MultiTokenPredictionLayer.forward` (4-tuple vs 5-tuple, `multi_token_prediction.py:2740-2745`) — safe today via the `None` default, but not reflected in the docstring and a trap for external subclasses.
- **`recompute_method="block"`** falls through to a different shared-tensor provenance than `"uniform"` (`multi_token_prediction.py:2619-2628`), and `isinstance(outputs, torch.Tensor)` is a fragile discriminator for whether the checkpoint path ran.

---

### Testing gaps

Every config the tests cover passes. The gap is *which* configs are covered: `recompute_modules=["core_attn"]` — the default — is absent, and that absence is what lets finding 1 through. `dsa_indexer_loss_coeff` is `0.0` in `_make_config`, so the nonzero-coefficient interaction is only reached by monkeypatched tests, none comparing loss magnitude against a non-sharing baseline. No functional test was added (the PR checklist marks that box unchecked) — reasonable for an experimental flag, though `mtp_use_repeated_layer` + `dsa_mtp_index_kv_share` touching gradient flow is exactly the class of change golden values catch and unit tests do not.

### Risk assessment

**Medium-high.** The feature is opt-in behind `dsa_mtp_index_kv_share=False` and gated to `experimental_attention_variant="dsa"` with `mtp_use_repeated_layer=True`, which bounds the blast radius to users who explicitly enable it — no existing recipe silently changes. Within that scope, though, finding 1 is a silent wrong-gradient path reachable via the *default* `recompute_modules`, which is the worst failure mode for a training framework: it converges, just to the wrong place. Findings 2 and 3 are lower severity but touch code the PR describes as untouched.

Recommend resolving finding 1 before merge — fix or explicit rejection, either is acceptable — and substantiating finding 2 with a regression test. The remaining items are reasonable follow-up material.

    source_key = key           # dsa.py:2037-2040
...
mtp_dsa_context.capture(source_key, topk_indices, topk_length)   # dsa.py:2409-2411

**[IMPORTANT Performance]** The selective-recompute branch splits on `mtp_dsa_context is not None`, not on whether sharing is actually active — so it degrades memory for *every* MTP iteration including iteration 0.

`mtp_dsa_context` is non-`None` for all iterations whenever `dsa_mtp_index_kv_share=True`. At iteration 0, `shared_key is None`, so this branch checkpoints only `q_up_proj_and_rope_apply` and runs `key_rope_apply` **outside** the checkpoint. The key's RoPE-applied activation (`[num_tokens, 1, kv_lora_rank + qk_pos_emb_head_dim]`) is now retained rather than recomputed.

For iterations 1..N-1 that is unavoidable and correct — the shared key must outlive the checkpoint. But at iteration 0 the key is only consumed by iteration 0's own sparse attention *and* by later iterations, so it does have to stay resident.
