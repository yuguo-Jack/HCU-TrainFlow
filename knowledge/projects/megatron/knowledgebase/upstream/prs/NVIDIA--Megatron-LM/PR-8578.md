# Keep the HybridEP static budget when moe_preprocess is CUDA-graphed

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8578) · state: open · merged: False

# What does this PR do?

Keeps the HybridEP static receive budget (`--moe-expert-rank-capacity-factor`) in effect when `moe_preprocess` is CUDA-graphed. Before this fix, the budget was silently dropped after capture.

### Bug

`_HybridEPManager.setup_metadata` sets the integer budget `num_permuted_tokens` from `moe_expert_rank_capacity_factor`. With `--cuda-graph-impl transformer_engine --cuda-graph-modules ... moe_preprocess`, that Python code runs only during capture:

- Replay restores only the tensor attributes listed in `cudagraph_attrs` (`token_probs`, `routing_map`, `topk_idx`).
- `combine()` resets `num_permuted_tokens` to `None` after every step.

As a result, every `dispatch()` after capture passes `num_permuted_tokens=None` to HybridEP. HybridEP then takes its dynamic path: `non_blocking=False`, with a `cudaStreamSynchronize` in metadata preprocessing. On that path it never drops tokens and never reports overflow, so the static budget does nothing and no error or warning is raised.

### Measured symptom

On Nemotron 3 Nano (hybrid Mamba + MoE + attention) on GB200, with the factor set and `moe_preprocess` graphed:

- About 180 HybridEP host syncs per iteration remained.
- The paged-stash path never reported a single overflow rerun.

### Fix

- Move the budget computation into `_HybridEPManager._rank_capacity_budget(num_tokens)`. `setup_metadata` uses it as before, so eager behavior does not change.
- In `dispatch()`, when no `rank_capacity` is passed, `num_permuted_tokens` is unset and the factor is configured, rebuild the budget from `hidden_states.shape[0]`. This only happens when `setup_metadata` did not run for the call, which is the graph-replay case. When `setup_metadata` did run, the budget is already set and this branch is skipped. When `--moe-hybridep-pad-uneven-dispatch-inputs` is used, `setup_metadata` sets both the budget and `_padded_num_tokens`, so this branch is never reached.
- Unaffected paths:
  - `drop_and_pad`: `combine()` keeps its budget, so the new branch is never reached.
  - Dropless overflow reruns: they set the factor to `None`, so the new branch is not taken.
  - Virtual experts (MoonEP): they pass `rank_capacity` explicitly.

### Test

New CPU-only unit test `test_hybridep_static_budget_without_setup_metadata`. It runs two dispatch/combine rounds without `setup_metadata`, restoring only the `cudagraph_attrs` tensors before each round as graph replay does, and checks that both dispatches pass the static budget to HybridEP.

- It fails without the fix (`[None, None] != [1024, 1024]`).
- It passes in the CI container on GB200.

New GPU determinism test `TestMoEModules.test_hybridep_static_budget_replays_without_setup_metadata` in `tests/unit_tests/determinism/kernels/test_moe_kernels.py`. It needs HybridEP and a world size divisible by 4.

- Each replay runs real HybridEP dispatch + combine at EP=4 with top-1 routing, so `combine` does no cross-rank reduction, and the budget is sized so nothing overflows.
- Each replay does one round through `setup_metadata`, then a second round that restores only the graph's tensor attributes.
- It asserts that every dispatch received the static integer budget, that nothing overflowed, and that outputs and gradients match exactly across replays under stream contention.
- It has not been run on GPU yet; this PR's CI will be its first run.

### Related

- #8285 (against `dev`) saves and restores the budget around dropless overflow reruns. It is a separate mechanism. This PR targets `main` and covers every post-capture step.
- #8410 clears HybridEP metadata references in `combine()`. The new test restores the `cudagraph_attrs` tensors every round, so it stays valid whichever PR merges first.

### Known follow-ups (out of scope)

With the budget actually applied, two things showed up on Nemotron 3 Nano that this PR does not address:

- Mock-data runs overflow often, which triggers paged-stash reruns. The factor may need tuning for mock data.
- In 2 of 3 runs, the first step after capture produced a NaN. It did not reproduce on rerun, and its cause has not been established.

Both will be investigated and reported separately.
