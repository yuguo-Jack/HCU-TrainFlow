# What does this PR do?

Lets Qwen3.5-VL train on the Mixture-of-Kittens (MoK) MoE megakernel backend from #8210, and makes that path fast. The PR has eight commits, meant to be reviewed one at a time. Commit 1, a router fix for per-layer CUDA graphs, applies to native MoE as well.

## Summary

#8210 adds MoK as an MoE backend on `main`. Qwen3.5-VL could not use it as is, and the path was slow:

- **Blockers.** MoK failed at step 1 with the Qwen3.5 router settings: router fusion, the Flex dispatcher and HybridEP in indices mode (commit 2). #8210 also rejects Qwen3.5's shared-expert output gate for MoK (commit 6). With per-token loss and no padding mask, capturing the router in a per-layer CUDA graph failed, for native MoE as well (commit 1).
- **Padding.** In the padded Qwen3.5-VL training measured here, about 94% of the routed rows were padding tokens, and the megakernel computed all of them (commits 4 and 7).
- **Host overhead.** #8210 rejects per-layer CUDA graphs that touch the MoE layer for MoK. The router and MoK's per-call host work ran eagerly in every MoE layer and microbatch, and the 397B step was host-bound (commits 3, 5, 7 and 8).

**Headline results.** Qwen3.5-VL training on GB300, MoK against native MoE on the same batch, in the full configuration: this PR with the related PRs below. The qualifiers are under Performance.

| model | at the start of this work | final |
|---|---|---|
| 35B, 8 GPUs, EP4 | -15% to -21% | +39.3% |
| 397B, 64 GPUs, EP32, forced load balancing | +2.9% | +63.8% / +64.7% (two runs, earlier build) |

In a 500-step 35B convergence A/B with two seeds, MoK's mean LM loss over the last 100 steps was within or below the spread of two native variants.

**Related PRs.** The rest of this description uses the short names in bold.

- **MoK PR**, on QiZhangNV/mixture-of-kittens: *perf: routed-row kernels, fused gate backward and eager host path for Qwen3.5-VL* (link to be added)
- **Bridge PR**, on NVIDIA-NeMo/Megatron-Bridge: *feat(model)!: pass a padding mask to Qwen3-VL MoE layers and run the vision merger on graph-padded rows* (link to be added). Its commits 1 and 2 run the Qwen3-VL vision patch merger on the CUDA-graph-padded rows and zero those rows first; its commits 3 and 4 add an opt-in padding mask for Qwen3-VL MoE layers and document it.

### 1. fix(moe): count aux-loss tokens on device so moe_router CUDA graphs can capture them

Files: `router.py`.

- **Why.** With `calculate_per_token_loss`, `TopKRouter.attach_and_log_load_balancing_loss` scales the auxiliary loss by the number of local tokens. When that count is a Python `int`, the shape-derived count used when no padding mask is passed, the router built the scalar with `torch.tensor(num_local_tokens, device=...)`. That is a copy from host memory, and a CUDA graph cannot record it. With a padding mask, the count is a tensor, which was already capturable. With the router inside a per-layer Transformer Engine graph (`cuda_graph_modules` containing `moe_router`, or `moe`), capture therefore failed with `Cannot copy between CPU and CUDA tensors during CUDA graph capture`. Qwen3.5-VL 397B training on the native MoE path, with per-token loss, the global auxiliary loss and `[attn, moe_router]`, failed this way at the first graph capture.
- **Change.** The scalar is filled on the device with `torch.full((), num_local_tokens, device=...)`. Its value and dtype (int64) are unchanged, and so is the all-reduce that follows. No other code path changes, and eager execution is unchanged. The `moe_router` and `moe` scopes then work with per-token loss and an integer token count; for MoK, commits 3 and 8 allow those scopes.
- **Evidence.** The new tests capture the router forward with per-token loss in a CUDA graph and replay it; the replay matches eager execution. A 4-layer Qwen3.5-VL 397B training smoke at EP32 on 32 GB200 GPUs with `[attn, moe_router]` and per-token loss captured the router graphs and trained for 20 steps, with native MoE and with MoK. The later full-size 397B MoK runs on 64 GB300 GPUs (EP32) also captured the router with this change.
- **Independent of MoK.** This commit needs neither #8210 nor the other commits, and it also fixes `moe_router` graph capture for native MoE. It can be split out again, to merge on `main` ahead of #8210, if reviewers prefer.

<details><summary>Details of commit 1</summary>

- **Value.** `torch.full((), n)` and `torch.tensor(n)` both produce an int64 scalar equal to `n`. Only the way the scalar is created changes, so no behavior change is expected.
- **Training runs.** They ran on the development tree described under Correctness and validation (main f711d35fe with the #7695 port), with a byte-identical `router.py` change.
- **Unit tests** (`test_routers.py`, new class `TestPerTokenAuxLossCudaGraph`).
  - `test_router_forward_is_capturable[aux_loss|seq_aux_loss|global_aux_loss]` captures the router forward with per-token loss into a CUDA graph and replays it. The replay matches eager execution.
  - `test_integer_token_count_scale_is_captured` captures an integer token count. The test checks that the count is reduced over the group and scales the loss.
  - The class records into a private MoE metrics tracker (an autouse fixture), so its 2-layer aux-loss entries do not leak into the global tracker that later tests read. Without the fixture, `test_aux_loss.py` failed when it ran after these tests in the same process.
- **`dev`.** `dev` has the same code. The `router.py` change applies there unchanged; the test class needs a different insertion point.

</details>

### 2. fix(moe): keep dense routes when a megakernel backend is selected

Files: `router.py`.

- **Why.** With router fusion and the Flex dispatcher, `TopKRouter` asks the fused top-k kernel for compact route indices instead of the dense routing map: int64 for DeepEP and NCCL-EP, and int16 for HybridEP with `moe_hybridep_routing_map_mode='indices'` when the expert count fits. A megakernel backend builds no token dispatcher and consumes the dense `[tokens, experts]` probs/routing_map pair. MoK therefore failed at the first step, in `routing_map_to_mok_inputs`: `probs and routing_map must have the same shape`.
- **Change.** `TopKRouter._dense_route_indices_dtype` returns `None`, meaning dense routes, whenever `moe_megakernel_backend` is set. The check runs before the Flex checks; configurations without a megakernel backend are unchanged. The fused router's compact output then goes unused, which loses nothing, because the megakernel needs the dense pair anyway.
- **Evidence.** `test_dense_route_indices_dtype_keeps_dense_routes_for_megakernel[deepep|ncclep|hybridep]`: each of these configurations compacts its routes without a megakernel backend and keeps them dense with `moe_megakernel_backend='mok'`. No performance effect of its own. All MoK training in this work ran with this change, byte-identical: 35B on 8 GPUs, 397B on 64 GPUs, and the GB200 smoke.

### 3. feat(moe): allow the moe_router CUDA graph scope with the MoK backend

Files: `transformer_config.py`, `moe_layer.py`, `transformer_layer.py`, MoE README.

- **Why.** #8210 rejects every per-layer CUDA graph scope that touches the MoE layer for MoK: `moe`, `moe_router` and `moe_preprocess`. The router, with its gating GEMM, top-k, auxiliary losses and their logging, therefore always ran eagerly, paying its kernel launches and Python on the host in every MoE layer and microbatch.
- **Change.** The router is captured as for the native dispatchers: the layer's TE graph ends after the router and returns its outputs, and the megakernel runs eagerly after the replay, on those outputs. `TransformerConfig` accepts `moe_router` for MoK with `cuda_graph_impl='transformer_engine'`. `moe_preprocess` stays rejected, and so does `moe` until commit 8. With per-token loss and no padding mask, the capture relies on commit 1.
- **Evidence.** A 4-layer Qwen3.5-VL training check ran `[attn, moe_router]` and `[attn]` on the same code: the loss is identical at steps 1 and 2, and later steps differ within MoK's run-to-run variation. All later MoK training used `[attn, moe_router]`, or `[attn, moe]` from commit 8.
- **Known limitations, not changed here:** a stale error text; a `pre_mlp_layernorm` recompute request that is silently dropped with the router graph; `mlp_chunks_for_training > 1`, which fails at capture, as on the native path. See the details.

<details><summary>Details of commit 3</summary>

- **Partial capture.** While the `moe_router` scope is captured, the router raises `MoECudaGraphPartialCaptureSignal`. `MoELayer`'s megakernel branch now catches it and returns the partial-capture outputs, without a shared-expert output, because MoK computes the shared expert inside the megakernel. For megakernel layers, `TransformerLayer` therefore adds no shared-expert graph submodule and pops no shared-expert output from the graph outputs on replay.
- **Config.** The `moe_router` scope is rejected for MoK with the local implementation.
- **README.** The MoK support table lists per-layer TE capture with the `moe_router` scope. In the list of unsupported features, "partial MoE CUDA Graph replay" becomes "the `moe_preprocess` CUDA Graph scope".
- **Training check.** An exact repeat of the `[attn]` run differed from the first run by as much as the two arms differed at later steps.
- **Unit tests** (`test_mok_weights.py`). `test_mok_accepts_transformer_engine_moe_router_cuda_graph` and `test_mok_rejects_local_moe_router_cuda_graph`. The existing reject test now covers `moe` and `moe_preprocess`; it lost its `moe_router`-only cases.
- **Known limitations.**
  - The error raised when a megakernel layer receives intermediate tensors still says "remove moe_router/moe_preprocess". Only `moe_preprocess`, which the config rejects, could lead there now.
  - With MoK and the router graph, a `pre_mlp_layernorm` recompute request is silently dropped.
  - `mlp_chunks_for_training > 1` with a TE `moe_router` graph fails at capture. The native path already fails the same way.

</details>

### 4. feat(moe): give padding tokens no routes in the MoE megakernel path

Files: `moe_utils.py`, `moe_layer.py`.

- **Why.** The router keeps padding tokens in its routes and only excludes them from its statistics. The native dispatchers receive the padding mask and can skip padded rows, as dropless HybridEP does. The megakernel path, however, handed the full routing result to the backend, which dispatched and computed every padding token.
- **Change.** New `moe_utils.drop_padding_routes(routing_probs, routing_map, padding_mask)` returns copies of the dense routing result with the rows of padding tokens zeroed: probs 0 and routing map False. The megakernel path applies it right after `route()` whenever a `padding_mask` is passed. That also covers the unmasked router outputs that a `moe_router` graph replay returns. As with dropless HybridEP, padding tokens then get no routes, and their routed output is zero. Nothing changes unless the caller passes `padding_mask`.
- **Evidence.** In 4-layer training checks, 35B at EP4 and 397B at EP32, native MoE and MoK each had a bit-identical LM loss at steps 1 and 2 with and without the mask. The forward pass of the real tokens therefore did not change; later steps differ slightly.
- **Risk: training semantics.** With a mask, the router's auxiliary-loss statistics exclude padding. The router already does that whenever it receives a mask, but turning the mask on changes training slightly. The mask is opt-in on the caller's side, off by default in the Bridge PR (its commit 3), and model owners should sign off before a recipe enables it by default.

<details><summary>Details of commit 4</summary>

- **Mask layout.** `padding_mask` is batch-first `[bsz, seq]`, with True marking padding. Tokens are flattened sequence-first, as in the hidden states.
- **Placement.** #8210's `route(..., packed_seq_params=...)` call in `megakernel_forward` is kept, and the masking follows it.
- **Cost.** The copies cost one pass over the `[tokens, experts]` probs and routing map per MoE layer, until commit 7 removes them.
- **Unit tests** (`test_moe_layer.py`).
  - `test_megakernel_receives_no_padding_routes[eager|recompute|moe_router_graph_replay]`: the backend receives no routes for padding tokens, and the router call counts match each path.
  - `test_megakernel_moe_router_graph_capture_outputs_unmasked_routes`: a `moe_router` capture returns the unmasked router outputs and does not run the backend.
  - The existing megakernel routing test checks the masked routes. #8210's packed-metadata test in `test_mok_megakernel.py` compares the routes the backend receives by value, because they are now masked copies.

</details>

### 5. perf(moe): cache MoK parameter, main-grad and gradient-sentinel state across calls

Files: `mok/backend.py`, `mok/runtime.py`, `parameter_bridge.py`.

- **Why.** `MoKMegakernel` rebuilt host-side state on every forward and backward: the routed parameter tuples (2 × `num_local_experts` parameters with split expert weights), the main-grad validation and split descriptor tables, and one gradient sentinel per parameter. The autograd function also saved every routed parameter for backward. With many local experts, this host work outweighed the MoE layer's GPU time once padding rows were skipped, so the GPU waited for the host.
- **Change.** The parameter tuples and the sentinel buffers are resolved once. The validated main-grad arguments are cached while every parameter keeps the same `main_grad` object at the same address. `_reset_derived_state()` drops all of this state, and `load_state_dict` and `_apply` call it. Only `x`, the router weights and the shared weights are saved for backward. Each gradient sentinel becomes an alias of one shared buffer per (shape, dtype, device), like Transformer Engine's `get_dummy_wgrad`.
- **Evidence.** In a single-MoE-layer harness on 4 GPUs (GB200), EP4, at Qwen3.5-VL MoE shapes, all 548 gradient tensors are bitwise identical before and after this change.
- **Risks.**
  - **Memory.** The sentinel buffers live for the process lifetime: one uninitialized, parameter-sized buffer per distinct (shape, dtype, device), shared-expert weights included. With single grouped expert weights, that is about one layer's routed and shared expert weights. Before, the sentinel aliased the parameter's own storage. TE's `get_dummy_wgrad` makes the same trade.
  - **Cache validity.** The cache relies on DDP assigning each `main_grad` once. Every call checks the cached arguments by object identity and data pointer, and rebuilds them when either changes.

<details><summary>Details of commit 5</summary>

- **Sentinels.** `param.detach()` allocates nothing, but on a quantized (MXFP8) parameter it builds a tensor subclass in Python, and AccumulateGrad's steal builds a second one. Now `dummy_weight_gradient_buffer` returns one uninitialized buffer per (shape, dtype, device), and `dummy_weight_gradient` returns a fresh detached alias of it. `AccumulateGrad` steals the alias into `.grad` without a copy, also for MXFP8 parameters. All parameters of the same shape share the buffer, and its values are never read. The shared-expert weights get sentinels through `finish_weight_gradient`.
- **Main-grad cache.** The cached arguments include the split descriptor tables. A replaced `main_grad` or moved storage, for example after a grad-buffer offload and reload, rebuilds them, and a missing `main_grad` still raises.
- **Resets.** `_reset_derived_state()` also drops the weight views. In `_apply` it replaces #8210's three invalidation lines; it clears the same state plus the new caches. Commit 8 adds a guard that refuses this reset while a CUDA graph holds the cached views.
- **Saved tensors.** Backward reads the routed weights through the cached views. The routed parameters stay autograd inputs, so each one's `AccumulateGrad` node, and with it the DDP hook, still fires.
- **Unit tests** (`test_mok_megakernel.py`).
  - `AccumulateGrad` steals the sentinel under a DDP-style hook, for a BF16 and an MXFP8 parameter, and no quantized tensor is constructed.
  - The parameter tuples are resolved once, and again after `_apply`.
  - The main-grad arguments are reused until a `main_grad` is replaced, its storage moves or it disappears.
  - The autograd function saves only the backward inputs and still delivers a gradient to every routed parameter.
  - #8210's dtype-conversion (`_apply`) test and the checkpoint test check that every cached field is reset.
  - `test_parameter_bridge_uses_main_grad_and_a_cached_dummy_gradient` replaces `..._without_allocating_dummy_storage`.

</details>

### 6. feat(moe): run the shared-expert output gate inside MoK

Files: `mok/backend.py`, `mok/runtime.py`, `transformer_config.py`, MoE README. Port of #7391 (see Credits).

- **Why.** Qwen3.5 gates the shared expert's output with a learned per-token sigmoid gate (`moe_shared_expert_gate`). #8210 rejects that option for MoK, because the MoK version it pins has no such gate. Qwen3.5 could therefore only run with MoK without the gate, which makes it a different model.
- **Change.** MoK 7a8cfb7 and later apply the gate inside the megakernel, through the `shared_output_gate_weight` arguments of `mok.functional.forward` and `mok.functional.backward`. `MoKMegakernel` registers the shared expert's `gate_weight` as a MoK parameter alias and passes it to MoK, together with its `main_grad` in backward. The gate gradient is finished through the parameter bridge, so its DDP hook fires. `TransformerConfig` no longer rejects `moe_shared_expert_gate` for MoK; shared-expert overlap is still rejected. Ungated layers make the same MoK calls as before.
- **Evidence**, with the real MoK kernels.
  - The ungated path is bitwise equal to the code before this change, at the 35B shape at EP4 and at the 397B shape at EP4 and EP32.
  - On the gated path (35B and 397B shapes, EP4 and EP32), the routed weight gradients and `d_probs` are bitwise equal to the gate-off results, padding rows are exact, and recompute is bitwise. The gate gradient has the same error against an exact reference as native BF16 autograd.
  - 4-layer training smokes, 35B at EP4 and 397B at EP32, tracked native MoE and an MCore-side gate implementation.
- **Risks.** With MoK older than 7a8cfb7, a gated configuration passes config validation and then fails at the first forward call, with a `TypeError` on the gate keyword argument. A follow-up could turn that into a config-time error with a version or signature check, as commit 7 does for its backward option. Gated configurations cannot run in CI yet (see Dependencies).

<details><summary>Details of commit 6</summary>

- **Gate weight.** The alias puts the gate into MoK's parameter-gather hooks; the `shared_experts` module still owns the only checkpoint entry. The gate must be a native, contiguous BF16 `Parameter` of shape `[1, H]`. `_MoKAutograd` passes the gate weight to MoK's forward, and the gate weight and its `main_grad` to MoK's backward.
- **README.** The gate requires MoK 7a8cfb7 or later, which is newer than the MoK snapshot pinned in the CI image.
- **Differences from #7391.** The gate weight is saved for backward next to commit 5's reduced set of saved tensors. #7391's `_apply` hunk is not needed, because `_apply` already resets all derived state (commit 5). The README sentence is new.
- **Unit tests** (`test_mok_megakernel.py`, `test_mok_weights.py`). Gate validation; checkpoint keys with the gate; gate-gradient accumulation into `main_grad` with the DDP hooks, for BF16 and MXFP8 and for split and single grouped weights; a missing gate `main_grad`; and acceptance of MoK configurations with the gate. #8210's checkpoint test keeps its ordered `named_parameters()` assertion for the ungated cases. With the gate, it compares parameter names as a set, because the shared module lists its own gate weight before the parameters of its submodules.
- **Older MoK.** The test group also ran with the MoK a2ad2d0 build in the test container (the commit the CI image pins; it has no gate): the new and re-parametrized tests pass, no test that passes on the parent fails, and the ungated paths are unaffected.

</details>

### 7. perf(moe): fold the padding mask into MoK route compaction and cut per-call host work

Files: `megakernel/backend.py`, `mok/route_adapter.py`, `mok/backend.py`, `mok/runtime.py`, `moe_layer.py`.

- **Why.** After commits 4 to 6, each MoK call still did avoidable host and memory work. It built commit 4's masked copies of the `[tokens, experts]` probs and routing map, and autograd materialized a zero gradient for the integer route indices, which nothing reads. The shared FC1 gate/up views and the main-grad arguments in MoK's six-buffer order were rebuilt on every call, so MoK validated new tensor objects each time. MoK also zeroed the router-weight gradient at unrouted slots, which the route adapter never reads. The 397B configuration was host-bound at this point, so host time per call translated directly into step time.
- **Change.**
  - `MegakernelBackend.forward` takes an optional batch-first `padding_mask`. `MoELayer` passes the mask to the backend instead of calling `drop_padding_routes`, which remains the reference implementation used by the tests.
  - The Triton route-compaction kernel (`RoutingMapToIndices`) drops the routes of padding tokens while it compacts them. Values and the `probs` gradient equal those of `drop_padding_routes` followed by compaction.
  - The indices gradient is no longer materialized, and the views and main-grad arguments are cached. `zero_unrouted_router_grads=False` is passed to `mok.functional.backward` when the installed MoK accepts it; older MoK builds work unchanged.
- **Evidence.** At the MoE-layer level, this commit with the MoK PR's eager host path installed is bitwise identical to the previous commit with the earlier MoK build. The check covers outputs and all gradients, including recompute and step boundaries, on every rank, at the 35B shape and a 397B proxy on 4 GPUs (GB200), and at the real 397B shape at EP32 on 32 GPUs (GB200). With `zero_unrouted_router_grads=False`, filling MoK's router-gradient buffer with NaN before backward changes no result.
- **Risks.**
  - **Interface change.** `padding_mask` is now an optional part of the `MegakernelBackend.forward` interface. Any other megakernel backend must accept it and give padding tokens no routes.
  - **Test-only helper.** From this commit on, `drop_padding_routes` is used only as the reference in tests; its docstring still describes commit 4's direct use. It stays in `moe_utils` as the reference semantics that the new `MegakernelBackend.forward(padding_mask)` contract requires of any other backend, and it can move to the tests if reviewers prefer.
  - **Teardown hang.** One 397B run with these host cuts hung at process teardown after it had finished training. The other 397B runs with them exited cleanly, and the hang was not reproduced.

<details><summary>Details of commit 7</summary>

- **Indices gradient.** `RoutingMapToIndices` calls `ctx.set_materialize_grads(False)` and handles a missing `probs` gradient.
- **Cached arguments.** The shared FC1 gate/up views are valid while the parameter object and its storage address are unchanged. With them and the main-grad arguments cached, MoK receives the same tensor objects on every call and validates them once. The routed FC1 payload is passed directly as both gate and up, as `_gate_up_weight_arguments` already did.
- **Backward option.** Whether the installed `mok.functional.backward` accepts `zero_unrouted_router_grads` is detected once per installed function, from its signature.
- **Unit tests.**
  - `test_multihot_indices_converter.py`: the in-kernel mask matches `drop_padding_routes` followed by compaction in values, indices and `probs` gradient, for boolean, integer and strided masks; the mask is validated; backward creates no zero-filled indices gradient.
  - `test_mok_kernels.py`: the bit-exact replay of the compaction kernel gains a `padded` parameter, which uses a strided padding mask.
  - `test_moe_layer.py`, `test_mok_megakernel.py`: the mask reaches the backend; the cached arguments, views and backward options are covered. #8210's packed-metadata test now asserts that the backend receives `(hidden, probs, routes, padding_mask)`.

</details>

### 8. feat(moe): capture the router and MoK megakernel in per-layer TE CUDA graphs

Files: `transformer_config.py`, `module.py`, `cuda_graphs.py`, `transformer_layer.py`, `megakernel/backend.py`, `mok/backend.py`, MoE README.

- **Why.** With `[attn, moe_router]`, the megakernel still runs eagerly after each graph replay, so its Python host work and kernel launches stay on the critical path of every MoE layer and microbatch. That cost dominates at the 397B shape, which is host-bound.
- **Change.** MoK layers can use `cuda_graph_modules` containing `moe` with `cuda_graph_impl='transformer_engine'`. The layer's graph then covers the router and the megakernel, and its output is the layer output. After warm-up, MoK has static shapes and no host synchronization.
  - **Config.** For MoK, the `moe` scope needs TE 2.19 or later: older TE clones every returned parameter gradient on replay, and MoK returns full-size gradient sentinels. It also needs `pipeline_model_parallel_size=1`. Every validation of the scope ran without pipeline parallelism, where each microbatch's backward runs before the next microbatch replays the layer's graph; pipeline schedules keep several microbatches in flight. The scope is rejected with pipeline parallelism, with `'moe'` in `recompute_modules` and with the local implementation. The `moe_router` scope stays allowed with pipeline parallelism, because MoK runs eagerly after that graph. Megakernel backends do not need the `moe` scope's drop-and-pad requirement, because they have static shapes without it.
  - **Weight views.** A new pre-replay hook refreshes MoK's cached weight views eagerly, including the MXFP8 scale swizzle once per optimizer step. During capture, MoK uses the cached, address-stable views and refuses to reset them while a graph references them.
  - **Warm-up.** TE runs each graphed callable eagerly on its static inputs before capture. All-ones hidden states route every token to the same experts, which can exceed MoK's schedule capacity under real routing. For a graphed megakernel, the static padding mask therefore marks every token as padding, so the warm-up routes none. Replay copies the real mask into the buffer.
  - **Teardown.** Deleting the TE graphs releases MoK's captured weight views, so parameters can be reloaded or moved afterwards.
  - **README.** The MoK CUDA Graph row lists the `moe` scope with its TE, pipeline-parallel and `padding_mask` requirements (see Risks and limitations). #8210's paragraph on per-layer MoK replay now says that it goes through the `moe` scope, which refreshes MoK's weight views before each replay, that whole-layer capture stays unsupported, and that the scope was validated only without pipeline parallelism.
- **Evidence.** In a deterministic harness, the graphed run is bitwise identical to eager in every training tensor, on every rank and step. That holds at the 35B shape and a 397B proxy on 4 GPUs and at the real 397B shape at EP32 on 32 GPUs (GB200), with forced load balancing and with real routing, all without pipeline parallelism. Negative controls: without the eager weight-view refresh, results diverge after the first optimizer step; without the warm-up mask, real routing at EP32 traps in MoK's capture warm-up.

## Risks and limitations

- **`moe` scope warm-up without a padding mask.** Unless `moe_router_force_load_balancing` is set, the `moe` scope needs a `padding_mask` model input during the eager `cuda_graph_warmup_steps`. The all-True warm-up mask exists only when the layer saw a padding mask during those steps. Without one, which is the usual case in LLM pretraining, TE's warm-up still sends every token to the same experts under real routing. That can exceed MoK's schedule capacity and stop the run with a device-side trap at capture, as in commit 8's negative control. Every validated configuration either passed a padding mask or used forced load balancing.
  - The README's MoK CUDA Graph row states this requirement.
  - Nothing in the code checks it yet. A follow-up should raise or warn at capture when a graphed megakernel layer has seen no padding mask, or give such layers an internal all-padding warm-up mask.
- **`moe` scope and pipeline parallelism.** The `moe` scope is rejected with `pipeline_model_parallel_size > 1`, because every validation of it ran without pipeline parallelism. There, each microbatch's backward runs before the next microbatch replays the layer's graph. With pipeline parallelism, MCore captures one graph per layer and microbatch, which may already keep each in-flight microbatch's MoK state apart, but that is untested. The `moe_router` scope is not affected.
- **Memory.** With the `moe` scope, reserved memory is about 10% higher at 397B, because the graph pool keeps MoK's per-layer context alive. Commit 5's sentinel buffers are covered with that commit.
- **Training stability.**
  - Across the shorter (150-step) 35B runs, MoK runs entered phases of elevated load-balancing loss, some with grad-norm spikes, more often than native runs.
  - That comparison is confounded by initialization. The native recipe uses GLU-interleaved FC1 weights, which MoK does not support, and the native runs with MoK's weight layout also showed the elevated load-balancing loss.
  - The 500-step A/B includes such a layout-matched native arm, and no MoK run there showed such a phase. A larger layout-matched comparison has not been run.
- **Test coverage.** The new tests ran on GB200 only. The MoE/MoK test group ran with MoK 7a8cfb7 and the MoK PR at commits 2 to 8 and on all eight commits together; commits 5 and 6 also ran with the test container's MoK a2ad2d0, the commit the ARM64 (GB200/GB300) CI image pins. In CI, the new tests run only in the H100 buckets: the GB200 unit-test buckets launch only tests marked `launch_on_gb200`, and none of the changed test files carries that marker. The H100 CI images have no MoK. The new MoK tests use fake `mok` modules and Blackwell or TE-version skips, and commit 1's tests need no MoK, so they should pass there, but that is unverified. Watch the H100 unit-test buckets.
- **Per-commit risks** are listed with each commit: the router-scope limitations (3), the training semantics of the mask (4), sentinel memory and cache validity (5), the late failure on older MoK (6), and the backend interface, the test-only helper and a one-off teardown hang (7). Commit 1 changes only how a scalar is created and is not expected to change behavior.
