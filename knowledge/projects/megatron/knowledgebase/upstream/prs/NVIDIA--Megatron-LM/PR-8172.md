# What does this PR do?
Between the varlen short conv and the chunked recurrence, GDP dynamic-batching prefill split the post-conv activations into value, key and query, folded the Householder copies into the sequence dimension, GQA-expanded query/key, and computed beta = sigmoid(b) and g = -exp(A_log) * softplus(a + dt_bias): about 14 copy and elementwise kernels per layer, three of them strided copies of most of the post-conv tensor. For a production-sized hybrid model that is ~148 us of GPU time per GDP layer for a 4096-token step.

Decode already does the same work in one kernel (gdp_decode_prepare). Generalize that kernel and add gdp_prefill_prepare on top of it. The two entry points share the loads, the libdevice math (so both stay bitwise identical to the eager path) and the [n, T*M, H, ...] value/key/beta layout, and differ only where their consumers do:

- decode interleaves query and g onto the Householder copies for the fused recurrent kernel and runs one program per head;
- prefill keeps query and g one per token, as chunk_gated_delta_product_varlen expects, and runs one program per (token, copy) covering every head, because a prefill step carries thousands of tokens.

A constexpr selects the query/g layout and the head-block size selects the grid. The prefill token count is a runtime argument, so prefill lengths do not each compile a kernel; decode keeps its token count (1 plus the draft length) as a compile-time constant. decode_prepare.py becomes prepare.py, holding the kernel and both entry points.

ssm_prefill now runs the varlen conv through a new _prefill_conv helper (the counterpart of _decode_conv) followed by the fused kernel, and the varlen branch moves out of _prepare_qkv, which only training and static batching use.

Tests assert torch.equal against the eager sequence across Householder counts, GQA ratios, dtypes, strided inputs and step sizes up to 4096 tokens, and a determinism replay covers the prefill entry point.
