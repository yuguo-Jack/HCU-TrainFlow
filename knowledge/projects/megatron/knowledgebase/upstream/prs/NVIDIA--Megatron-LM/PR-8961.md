# [Inference][MoE][BatchInvariant] Reject the multimem batch-invariant combine on Hopper and document the NVLS in-switch sums' rounding

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8961) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

`TransformerConfig` now rejects `batch_invariant_collective="multimem"` in batch-invariant mode on Hopper (compute capability 9), because the NVLS in-switch sum it uses was measured not batch-invariant on an H100 system. It also corrects the comments and docstrings that said this sum is correctly rounded on every GPU, and it documents how the bf16 in-switch sum rounds on each GPU.

**Bug.** Under `batch_invariant_mode`, the `"multimem"` combine collective of the NVLS MoE dispatcher sums the EP ranks' fp32 partials with the in-switch reduce (`multimem.ld_reduce ... .add.v4.f32`, in `multimem_reduce_scatter_v`). Batch invariance needs that sum to be deterministic and a token's sum to depend only on that token's partials. On one 8-GPU H100 system this did not hold. The test was `test_multimem_fp32_combine_is_batch_invariant` (dfw 21229991). Over six calls it changes the per-rank counts, the probe tokens' row positions, the co-batched tokens and the timing. Each probe token's combined row changed bits at 4 and 8 GPUs, in all 4 of 4 cases: on rank 0, 89 of 384 up to 8739 of 21504 elements differed. Two GPUs kept the bits. The same test passed on another H100 system (pdx 7849969) and on GB200 (hsg 8573706, 2 and 4 GPUs). So whether `"multimem"` is batch-invariant on Hopper depends on the system.

This matches what `docs/user-guide/deterministic-training.md` already records for Hopper: an NVLS reduction's result can depend on the multicast objects allocated before it in the same process unless the kernel driver and Fabric Manager are 550.144.03 or later in the 550 branch, or 570 or later (NVIDIA/nccl#2360). The driver and Fabric Manager versions of the two H100 systems were not recorded, so the PR does not claim that cause, and Megatron cannot check those versions at run time. For the same reason, `--deterministic-mode` already rejects NVLS on every Hopper GPU (`megatron/training/determinism.py`).

**Wrong documentation.** The `token_combine` comment, the `batch_invariant_collective` docstring (also the `--batch-invariant-collective` help text) and the training-side `_unpermute_loop` comment called the in-switch fp32 sum correctly rounded and bitwise-equal to an fp64 reference. They implied this on every GPU and called `"multimem"` batch-invariant.

## Fix

- `TransformerConfig.__post_init__`: with `batch_invariant_mode` and `batch_invariant_collective="multimem"`, on a device of compute capability 9, raise `ValueError`. The message gives the same reasoning and driver reference as the deterministic-mode NVLS rejection and points to `"ordered"`, the default rank-ordered fp32 combine, which is deterministic by construction. There is no driver-version escape hatch, as in deterministic mode. Blackwell keeps `"multimem"`. Without CUDA the check does not apply, and the NVLS kernels cannot run there anyway. All users go through this check: training and RL build this config from the same arguments that enable the mode, and inference builds the model from it.
- Documentation, scoped to what was measured:
  - The `batch_invariant_collective` docstring, the `token_combine` comment and the inference user guide say that `"multimem"` is rejected on Hopper and why. On GB200 it was measured batch-invariant and correctly rounded at 2 and 4 GPUs, as on B200 (16.7M adversarial channels, the existing measurement). Larger NVLink domains are unmeasured.
  - `_unpermute_loop` (the training mirror of the combine): the fp64 mirror of `"multimem"` is what the in-switch sum returned on B200 and on GB200 at 2 and 4 GPUs.
  - `ld_128` (`multimem_asm.py`): the measured rounding of both in-switch sums. fp32 is correctly rounded on GB200 at 2 and 4 GPUs and on H100 at 2 GPUs, but not on H100 at 4 or 8 GPUs, where 28-45% of elements differed from the fp64 sum rounded once (dfw 21220462). The two 4-GPU groups of one node also returned different bits for the same partials. bf16 rounds to nearest even on H100 at 2, 4 and 8 GPUs. On GB200 at 2 and 4 GPUs most inexact sums come out rounded toward zero, ties included, so a result can be one bf16 ulp from the nearest-even one (hsg 8573706). The exceptions: 1 − 2⁻²⁰ returns 1.0, and a tie from a carry into the next binade rounds away from zero.
  - The GTP doc (§2.7) and its `arguments.py` warning: when a registered NCCL pool takes precedence over the fp32-accumulation all-to-all, the in-switch result is bf16 rounded by the switch, mostly toward zero on GB200, a bias that §2.6's fp32 output does not have.
  - The determinism manifest's exemption reason for the NVLS collectives: batch-invariant mode reduces with the rank-ordered kernel unless `"multimem"` is selected, which is rejected on Hopper. Bitwise parity with training also relies on the in-switch sum's rounding.

The GPU measurements come from the independent NVLS oracle tests on `test/inference-oracles-o5` (`tests/unit_tests/inference/oracles/nvls/`). That PR is still open, so its tests are not in this branch:

- `test_multimem_fp32_combine_is_batch_invariant`
- `test_bf16_in_switch_sum_rounding`
- `test_multimem_fp32_sum_is_correctly_rounded` (at d33426625)
- `test_hopper_refuses_batch_invariant_multimem`, which builds the config on an H100 and expects this rejection

## Tests

`tests/unit_tests/transformer/test_transformer_config.py::test_batch_invariant_multimem_collective_is_rejected_on_hopper` (4 cases, CPU). It builds a valid batch-invariant config with the device arch faked through `torch.cuda.is_available` and `torch.cuda.get_device_capability`:

- `"multimem"` on arch 9 must raise the rejection;
- `"ordered"` on arch 9, and both collectives on arch 10, must build.

The multimem-on-arch-9 case fails on `main` (the config builds), and every case passes with the fix. A scratch script checked the config behavior both ways. Black, isort and ruff ran on the changed files; `megatron/training/arguments.py` is outside autoformat's scope and was not reformatted. `tools/check_kernel_determinism_coverage.py` flags the comment change in `moe/batch_invariant.py`, a registered kernel source; its docs say comment-only edits get the `determinism-exempt` label, so please add it. The GPU run of the new test is pending.
