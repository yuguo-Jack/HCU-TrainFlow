# feat(moe): Train-gen parity for MXFP8 and per-token NVFP4 MoE on FlashInfer

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7798) · state: closed · merged: True

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

**This PR adds one opt-in knob, `moe_training_matches_inference`, meant to be enabled only by RL training.** It is off by default, and generation's forward is unchanged with it on or off.

With the knob on, the training forward of an inference-optimized MoE layer runs the same FlashInfer routed kernel that generation runs. A token's training log-prob then equals its generation log-prob bitwise, for FlashInfer routed MXFP8 and per-token NVFP4 MoE. The backward is unchanged: it comes from the Transformer Engine (TE) recompute pass. The requirement is that this adds no forward–backward inconsistency beyond what the default TE recipe already has; see [Core metric](#core-metric-no-extra-forwardbackward-inconsistency).

Numbers below are for one MoE layer with Nano-v3 shapes, GB300 × 4, EP 4, eager; see [Performance](#performance). The value pass runs through training's own router module and all-to-all dispatcher, so training needs none of generation's buffers.

Training keeps one derived copy of the expert weights for FlashInfer: BF16 plus NVFP4 for per-token NVFP4, and MCore MXFP8 plus FlashInfer's routed layout for MXFP8.

### Per-token NVFP4: faster and smaller, no trade-off

Against TE's per-token NVFP4 recipe, the same quantization scheme:
- **Bitwise train–gen parity** for every token's log-prob.
- **Log-prob forward 3.4–4.4× faster.**
- **Train step 2.3–3.1× faster** than TE NVFP4 + recompute, and 1.05–1.21× faster than BF16 TE + recompute.
- **Less memory:** lower peak at every size (log-prob 165 vs 262 MiB at 1024 tokens per rank, 2633 vs 3580 MiB at 16384), and about 180 MiB less static memory per layer, because its cached kernel weights (about 180 MB per layer per rank) are smaller than TE NVFP4's cached quantized weights (about 350 MiB).
- **Same gradient:** the backward is TE's, and the forward is within 0.4% of TE's distance from BF16 on every seed and input ([Core metric](#core-metric-no-extra-forwardbackward-inconsistency)).

Checked by bitwise parity with generation (including after a refit), kernel batch invariance, bit-exact replay under contention, and the core metric; see [What is tested](#what-is-tested).

### MXFP8: faster, with extra memory during each call

Against TE MXFP8:
- **Bitwise train–gen parity** for every token's log-prob.
- **Log-prob forward 1.4–1.7× faster.**
- **Train step 1.11–1.16× faster** than TE MXFP8 + recompute, with the same peak, plus a kernel-weight rebuild of about 36 ms per MoE layer once per optimizer step (see [Performance](#performance)).
- **Same gradient:** the backward is TE's, and the forward is closer to BF16 than TE's on every seed and input.

Checked by the same parity and core-metric tests; the parity tests also cover a token's output across launch sizes.

**The drawback is memory held between optimizer steps:**
- **Cached kernel weights:** about 330 MB per MoE layer per rank, about 7.6 GB for 23 MoE layers. TE MXFP8 needs no extra copy, because its `fp8_param` weights already are its kernel's input. `training_matches_inference.release_inference_value_pass_weights(model)` frees it, for example before colocated generation.
- **Small log-prob passes:** each launch keeps at least the rows for the kernel's largest tile, so log-prob peak is 41 MiB higher than TE's at 1024 tokens per rank; it is lower from 2048.
- **If memory is tight,** generation can use the torch MXFP8 backend (`inference_grouped_gemm_backend: torch`), which already matches TE training bitwise under `batch_invariant_mode`, without this flag or the cache.

## Usage

On top of generation's FlashInfer settings (`inference_optimized`, `batch_invariant_mode`, and per-token NVFP4 or MXFP8 with `fp8_param`), the RL trainer adds:

```yaml
moe_training_matches_inference: true
moe_token_dispatcher_type: alltoall
recompute_granularity: selective
recompute_modules: [moe]
```

The value pass also runs under `model.eval()`, so the RL log-prob forward takes it too.

**Training-side memory**
- **Activations:** the value pass saves none. The cost is one extra MoE forward per layer.
- **Kernel weights** (sizes above): built on the first value pass after a weight change and held until the next optimizer step, `state_dict()` call, checkpoint load, in-place write to the parameters, or `training_matches_inference.release_inference_value_pass_weights(model)`. The log-prob pass and the training microbatches of one step share a single build. Against TE without recompute, the MoE activations recompute frees outweigh the MXFP8 cache from about 4096 tokens per rank per microbatch.
- **No generation buffers:** the value pass uses training's all-to-all dispatcher, so it works the same with generation colocated, on other GPUs, or on another cluster. Training must use generation's EP size.

## Background

Under `batch_invariant_mode`, the torch and vLLM inference MoE kernels already match TE training bitwise. FlashInfer, the production path for MXFP8 rollouts, cannot: #7302 reports the MXFP8 mismatch, and per-token NVFP4 from #8262 is batch invariant but does not match training either. FlashInfer fuses the activation and the FC2-input quantization into the FC1 epilogue, applies routing probabilities after FC2, and accumulates in its own order, so the training path cannot be aligned to it by hand. In RL, the gap shows up as a bias in the importance ratio.

FlashInfer owns only the per-rank expert compute and the sum of each token's routes on a rank (its finalize); the router, dispatch and cross-rank combine are Megatron's. Under `batch_invariant_mode`, training's router already picks generation's experts and training's all-to-all combine already adds the EP ranks as generation's does. The training forward therefore keeps training's router and dispatcher, and reproduces only FlashInfer's expert compute and its per-rank sum.

## Scope

The forward and the backward come from different libraries, so the gradient is not the derivative of the forward. That only matters for recipes whose backward was the exact derivative of their forward to begin with, and those are out of scope:
- **Consistent (out of scope):** the backward reuses the forward's dequantized operands in high-precision GEMMs.
- **Already inconsistent (in scope):** TE MXFP8 quantizes separate row-wise and column-wise copies for the forward and backward, and quantizes the output gradient too, so its backward is a quantized estimate of the BF16 layer's gradient. The NVFP4 recompute runs in BF16, so it also computes the BF16 layer's gradient.

For the in-scope recipes, the backward stays exactly as it was. The forward moves from one quantized implementation to another that differs only in quantization details, accumulation order and where the routing probabilities are applied. FlashInfer's routed MoE has no backward, so an all-FlashInfer path is not an option.

## Core metric: no extra forward–backward inconsistency

**Claim.** Using generation's forward does not make the gradient fit the loss worse than the default TE recipe already does.

Quantization has zero derivative almost everywhere, so a quantized backward computes the gradient of the BF16 layer, not of its quantized forward:

| Recipe | Forward that produces the loss | Gradient the backward computes | Backward GEMMs |
|---|---|---|---|
| MXFP8, default TE | TE MXFP8 | The BF16 layer's | MXFP8 |
| MXFP8, this PR | FlashInfer MXFP8 | The BF16 layer's (same TE backward) | MXFP8 |
| NVFP4, default TE (per-token, `backward_override='high_precision'`) | TE per-token NVFP4 | The BF16 layer's | BF16 |
| NVFP4, this PR | FlashInfer per-token NVFP4 | The BF16 layer's (same TE backward) | BF16 |

The inconsistency is the gap between the quantized forward and the BF16 layer. Within each recipe the backward is identical, so the metric is each forward's relative distance from BF16 on the MoE output, with the same weights and tokens:

```math
d_{\mathrm{recipe}} = \frac{\lVert y_{\mathrm{recipe}} - y_{\mathrm{BF16}}\rVert}{\lVert y_{\mathrm{BF16}}\rVert}
```

**Pass condition**, for every recipe, seed and input type:

```math
d_{\mathrm{FI}} \le (1 + \alpha)\, d_{\mathrm{TE}}, \qquad \alpha = 1\%
```

Both forwards use the same quantization scheme, so either can land slightly closer to BF16; 1% is small next to the roughly 20% both are from BF16.

**How it is measured:** `TestForwardBackwardMismatch` in `tests/unit_tests/inference/test_moe_training_matches_inference.py`.
- Three layers share one set of weights: this PR's value pass, the default TE recipe, and TE BF16. For MXFP8, the BF16 layer gets the dequantized MXFP8 weights.
- The NVFP4 baseline is TE's per-token recipe, `NVFP4BlockScaling(row_scaled_activation=True, disable_2d_quantization=True, disable_rht=True, disable_stochastic_rounding=True, backward_override='high_precision')`, the same scheme as FlashInfer's, so the comparison measures the kernel rather than the scheme.
- Inputs are 512 tokens per rank with seeds 11–13, each as Gaussian tokens and as tokens with 5% scaled by 30. Only forwards run, so the comparison is deterministic.

```bash
uv run python -m torch.distributed.run --nproc-per-node 4 -m pytest -q -s \
  tests/unit_tests/inference/test_moe_training_matches_inference.py -k TestForwardBackwardMismatch
```

**Results** (EP = 4, GB200). Each cell is the range over seeds 11–13 (lower is better). The last number column is the largest amount by which this PR exceeds TE on any seed; negative means this PR is closer to BF16 on every seed.

| Recipe | Input | This PR ($`d_{\mathrm{FI}}`$) | Default TE ($`d_{\mathrm{TE}}`$) | Largest excess over TE | Pass ($`\le 1\%`$) |
|---|---|---|---|---|---|
| MXFP8, squared ReLU | Gaussian | 0.0413–0.0414 | 0.0415–0.0416 | −0.17% | yes |
| MXFP8, squared ReLU | 5% outliers | 0.0400–0.0409 | 0.0405–0.0421 | −1.2% | yes |
| NVFP4, squared ReLU | Gaussian | 0.1957–0.1963 | 0.1958–0.1963 | 0.00% | yes |
| NVFP4, squared ReLU | 5% outliers | 0.1985–0.2021 | 0.1984–0.2027 | +0.40% | yes |
| NVFP4, SwiGLU | Gaussian | 0.2307–0.2325 | 0.2309–0.2325 | +0.04% | yes |
| NVFP4, SwiGLU | 5% outliers | 0.2224–0.2315 | 0.2224–0.2321 | +0.40% | yes |

The test also prints the worst single token's distance, which is not part of the pass condition:
- **NVFP4:** this PR's worst token is closer to BF16 in 9 of 12 runs; the largest excess is 0.363 against 0.360.
- **MXFP8:** closer in 2 of 6 runs; the largest excess is 0.080 against 0.071. The average is still lower on every run, so the error is spread differently over tokens but is not larger overall.

**Limits.** This compares one layer's forward, not a training curve. A finite-difference gradient check does not work here, because the loss of a quantized forward is piecewise constant in the weights.

## Performance

One MoE layer with Nano-v3 shapes (hidden 2688, 128 experts, top-6, squared ReLU, shared expert), GB300 × 4, EP 4, batch-invariant mode, eager, mean of 20 iterations. The baseline is TE in the same quantization: TE MXFP8, or TE's per-token NVFP4 recipe (FlashInfer's scheme, run outside batch-invariant mode). Peak is the extra memory allocated during the pass, on top of resident memory; the cached kernel weights are resident, so they appear under static memory, not peak. All numbers come from one run.

**Train** (forward + backward). The flag requires `moe` recompute, so the baseline is TE + recompute. The tables time microbatches after the first, where neither side converts weights.

| Recipe | Tokens/rank | TE + recompute ms | This PR ms | Speedup | TE + recompute peak MiB | This PR peak MiB |
|---|---|---|---|---|---|---|
| MXFP8 | 1024 | 31.43 | 27.30 | 1.15× | 733 | 732 |
| MXFP8 | 4096 | 32.22 | 28.50 | 1.13× | 1276 | 1275 |
| MXFP8 | 16384 | 35.68 | 31.09 | 1.15× | 4630 | 4632 |
| NVFP4 | 1024 | 59.47 | 20.53 | 2.90× | 750 | 721 |
| NVFP4 | 4096 | 61.48 | 21.37 | 2.88× | 1403 | 1334 |
| NVFP4 | 16384 | 62.46 | 27.42 | 2.28× | 4593 | 4416 |

**Weight rebuild.** The first value pass after each weight change also rebuilds the kernel weights: about 36 ms per MoE layer for MXFP8 (stack and FlashInfer shuffle of the TE MXFP8 parameters) and about 18 ms for NVFP4 (requantization from BF16), independent of the token count. The cost is shared across the step's microbatches and its log-prob pass. The rebuilt weights are allocated inside that first forward, so its saved memory includes them (about 326 MiB MXFP8, 200 MiB NVFP4).

- Both sides run the TE recompute forward and the TE backward; they differ in the first forward, where this PR's FlashInfer pass is faster than TE's. Peak is set by the recompute, so it is the same.
- The NVFP4 recompute in this PR runs TE BF16 (see [What is changed](#what-is-changed)), while TE NVFP4 + recompute runs the slow per-expert NVFP4 forward twice. Against BF16 TE + recompute (21.9–31.4 ms), this PR is 1.05–1.21× faster.
- **Static memory** per rank: MXFP8 1695 vs 1367 MiB (the MXFP8 kernel-weight cache), NVFP4 1543 vs 1721 MiB.

**Log-prob** (`eval()` forward under `no_grad`). Nothing is saved for backward and nothing is recomputed, so the baseline is plain TE.

| Recipe | Tokens/rank | TE ms | This PR ms | Speedup | TE peak MiB | This PR peak MiB |
|---|---|---|---|---|---|---|
| MXFP8 | 1024 | 7.15 | 5.11 | 1.40× | 235 | 276 |
| MXFP8 | 4096 | 9.27 | 6.52 | 1.42× | 898 | 763 |
| MXFP8 | 16384 | 11.02 | 7.82 | 1.41× | 3552 | 2698 |
| NVFP4 | 1024 | 20.54 | 5.61 | 3.66× | 262 | 165 |
| NVFP4 | 4096 | 23.53 | 5.40 | 4.36× | 921 | 660 |
| NVFP4 | 16384 | 21.03 | 6.24 | 3.37× | 3580 | 2633 |

- **This PR's log-prob time** is about 5–8 ms at every size. At small sizes it is bound by the all-to-all dispatcher's CPU work (kernel launches and the host sync for its split sizes); at 16384 tokens per rank the three NCCL all-to-alls take about 1.6 ms of it. These are the costs of training's own dispatcher, which the train step pays in its recompute anyway.
- **TE NVFP4** takes 20–24 ms at every size because TE 2.18 runs row-scaled NVFP4 GEMMs one expert at a time in Python: per expert, a separate activation quantization, an FP32 GEMM, and a per-row rescale and copy. That is about 700 kernel launches per pass for about 2.6 ms of GPU work, so the pass is bound by CPU launch cost, and its timing varies between runs. BF16 TE takes 6.1–10.1 ms here. With CUDA graphs, the gap would shrink toward TE's GPU time.

Script: `bench_match_generation_forward.py` (not part of this PR). `--weight-cache cached` (the default) gives the tables above; `--weight-cache rebuild` resets the cache before every pass, which gives the rebuild cost.

## What is changed

- `TransformerConfig.moe_training_matches_inference` (default off). Construction fails unless:
  - `transformer_impl='inference_optimized'` and `inference_grouped_gemm_backend='flashinfer'`. Torch and vLLM need no value pass.
  - MXFP8 or `inference_moe_nvfp4_recipe` is set. FlashInfer BF16 is not batch invariant.
  - `batch_invariant_mode` is on, `moe_token_dispatcher_type='alltoall'`, and selective `moe` recompute is enabled.
  - Nothing makes the training router choose different experts than generation: no sinkhorn or quantile balancing, input jitter, forced load balancing, local CUDA graphs, or overlapped 1F1B schedule. Expert tensor parallelism is also rejected.
- `MoELayer.forward` hands off to `training_matches_inference_forward` when the flag is on and inference is not active; `custom_forward` is unchanged. Everything else is in the new `moe/training_matches_inference.py`, and the layer keeps no state:
  - With grad enabled, the layer runs under `precision_aware_checkpoint`, whose first call runs without grad and whose recompute runs with it. The grad mode picks the pass: no grad runs the value pass, grad runs the training `custom_forward` (the recompute, which supplies the gradient). A `no_grad` eval forward, the RL log-prob pass, runs the value pass directly.
  - Generation itself never enters the value pass, so its weights, buffers, CUDA graphs and kernels are untouched.
- The value pass runs the layer's own stages: router, preprocess, training's all-to-all dispatch, expert compute, all-to-all combine, and postprocess. Two of them differ from the training forward:
  - **Routing** calls the layer's router through its generation path (under `InferenceMode.active()`, for that call only), which returns each token's top-k routes in generation's order. Training's routing map does not keep that order, and FlashInfer sums a token's routes in it. This path also leaves the router's expert-bias token counts to the recompute.
  - **Expert compute** launches FlashInfer once over all dispatched rows, each row as a top-1 token with probability 1.0, so FlashInfer returns each route's expert output unscaled. The routed MXFP8 kernel has no tile config for a few rows per local expert, so MXFP8 launches are padded with unrouted rows to more than 128 rows per local expert (4097 rows for Nano-v3 at EP 4), where its tile is its largest; batch invariance makes the rows independent of the tile.
  - **Unpermute** uses a new `BF16_RANK_PARTIALS` mode of the batch-invariant unpermute kernel (`moe/batch_invariant.py`, `unpermute_with_bf16_rank_partials`). For each EP rank it adds the token's routes on that rank in top-k order as FP32 fused multiply-adds of probability and row, from zero, and quantizes the sum to BF16, as FlashInfer's finalize does. It then adds the ranks as the existing batch-invariant combine does, matching generation's ordered or multimem combine. The existing training path compiles the kernel with the mode off, unchanged.
  - The recompute pass runs the normal TE path and supplies the gradient.
- The value pass calls the same routed MXFP8 or NVFP4 FlashInfer kernel that generation calls, directly from `training_matches_inference.py`, on kernel weights built from the training parameters (MXFP8: the Major-K shuffle from TE's MXFP8 parameters; NVFP4: the requantization from BF16). `InferenceGroupedMLP` keeps no value-pass state and its `forward` has no value-pass branch; its only change is allowing the TE MXFP8 recompute with the flag on. Generation's `_flashinfer_forward` is unchanged.
- The kernel weights are cached in `training_matches_inference.py`, keyed weakly by experts module, with the address and version of every source tensor, so an in-place write to the parameters rebuilds them. TE writes into MXFP8 parameters bypass the version counter, so a process-wide optimizer step post-hook (`torch.optim.optimizer.register_optimizer_step_post_hook`) and `state_dict` and `load_state_dict` post-hooks on the experts, all registered there, also drop them. A reference-model swap that copies into `state_dict()` tensors, as NeMo-RL's does, is covered. `training_matches_inference.release_inference_value_pass_weights(model)` drops them on request, for example before colocated generation. The training pipeline (`MegatronModule`, the schedules, the optimizer) is unchanged.
- Reading the weights without running the expert linears, the value pass runs Megatron DDP's parameter all-gather pre-forward hooks on them; any other pre-forward hook, such as Megatron-FSDP's, and sharded (DTensor) expert parameters are rejected.
- NVFP4 refit: `refresh_cache()` requantizes the NVFP4 copy after a refit, replacing `main`'s `NotImplementedError`.
- The NVFP4 recompute runs TE BF16, because the batch-invariant config rejects TE `fp4` with inference-optimized MoE. The MXFP8 recompute runs TE MXFP8.

## Limitations

- **Same EP as generation:** generation's combine is not EP-invariant, so training must use the same EP. An EP-invariant generation combine would remove this.
- **All-to-all dispatcher only:** the flex (DeepEP, HybridEP) and all-gather dispatchers have no batch-invariant combine that adds the EP ranks as generation does.
- **ETP > 1 is rejected.**

### [P2] Refresh NVLS metadata for every value-pass chunk

**Failure:** use two NVLS MoE layers with capacity `C`, and run `C + 1` tokens per rank after generation has called [set_moe_metadata_sync](https://github.com/NVIDIA/Megatron-LM/blob/926785ce908d1c0c57efcb9dfdd7f2d2a1c13ced/megatron/core/inference/utils.py#L219-L235). That helper disables metadata updates on every dispatcher except the first. The first layer finishes chunking with metadata for its one-token tail. The second layer then starts a `C`-token chunk using those stale one-token counts, offsets and launch bounds, because [token_dispatch skips its metadata update](https://github.com/NVIDIA/Megatron-LM/blob/926785ce908d1c0c57efcb9dfdd7f2d2a1c13ced/megatron/core/transformer/moe/token_dispatcher_inference.py#L599-L623). Consequently real rows are omitted or gathered at incorrect offsets instead of producing the generation-equivalent result. The new [chunk loop](https://github.com/NVIDIA/Megatron-LM/blob/926785ce908d1c0c57efcb9dfdd7f2d2a1c13ced/megatron/core/transformer/moe/moe_layer.py#L596-L605) makes the formerly per-step metadata change within each layer.

**Correction:** every collective chunk must use metadata derived from that chunk on every layer. Immediately before `self.dispatch(...)` in `_chunked_dispatch_and_compute`, the smallest correction is:

```python
if not dispatcher._runs_metadata_sync:
    dispatcher.update_metadata(chunk.stop - chunk.start)
dispatched_input, chunk_probs = self.dispatch(hidden_states[chunk], probs[chunk])
```

Dispatchers with `_runs_metadata_sync=True` already update inside `token_dispatch`; this supplies the missing update without doubling theirs or changing generation's optimization.

**Preservation / proposed acceptance:** test a two-layer NVFP4 stack with dispatcher sync flags `[True, False]`, a heap of 8 rows per rank, and 9 tokens per rank. Its output must equal a same-weight reference with both flags true, bitwise. Repeat with uneven rank counts crossing the heap boundary. Keep the existing single-layer heap-chunking equality and uneven-rank parity assertions. Ordinary generation must retain first-layer-only metadata synchronization. These are proposed checks, not executed results.

### [P2] Exclude generation's padding scalar from training value passes

It's built on the first value pass after a weight change and reused until the next optimizer step, state_dict() call, checkpoint load or in-place write.

Megatron has no single offload point it could hook without guessing, so the cache is dropped explicitly: release_inference_value_pass_weights(model) frees it, and the next value pass rebuilds it from the parameters. For colocated generation, the trainer should call it before offloading. In NeMo-RL that's offload_before_refit / offload_after_refit in megatron_policy_worker.py. I'll send that as a NeMo-RL follow-up rather than reaching into the trainer from Megatron.

Writing FlashInfer's layout straight from the main-parameter update, so there's only one copy, is the right long-term fix. It needs a change in the optimizer's parameter-update path, so I'd like to keep it out of this PR.
