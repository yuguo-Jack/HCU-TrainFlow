# feat(moe): run the inference expert kernel as the MoE training forward for train/generation parity

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7798) · state: open · merged: False

## Original PR description

# What does this PR do?

Add an opt-in `moe_inference_training_forward` mode: during training, the MoE layer's **value-producing forward runs the same expert kernel generation runs**, while the **backward still comes from the ordinary TE path** (via the MoE-layer recompute pass). A training log-prob and a generation log-prob of the same token then agree by construction, instead of by hand-reproducing each inference kernel's rounding in the training path.

## Motivation: RL

In RL (GRPO and similar) the policy that samples rollouts (Megatron Inference) and the policy that scores them for the loss (the Megatron training forward) are the same weights run through different code. Any numerical gap between the two is a train/generation mismatch: it shows up as nonzero `gen_kl_error`, biases the importance ratio, and forces off-policy corrections that exist only because of kernel rounding rather than because the policy moved. The goal is a **zero train/generation log-prob gap** for on-policy rollouts.

Batch-invariant kernels (`batch_invariant_mode`) removed the dependence on batch composition. The MoE expert path is what remained: training and generation run different kernels there (TE grouped GEMM vs the inference grouped GEMM), and under MXFP8 they hold different weight representations. Matching an inference kernel's arithmetic by hand in the training path does not scale: each backend rounds where it rounds, and the copy silently rots as kernels change. This PR instead runs the inference kernel itself in the training forward.

## How it is used with TE recompute

The mode is built on Transformer Engine's selective recompute of the MoE layer (`recompute_granularity: selective`, `recompute_modules: [moe]`, required):

* **Pass 1 (forward, produces the output):** runs generation's expert kernel and dispatcher and saves no activations. This pass's numbers become the log-probs, so it equals generation.
* **Pass 2 (recompute, triggered by backward):** runs the ordinary TE path (TE grouped GEMM, training dispatcher) and builds the autograd graph, so **gradients are TE's**.

So the value is the inference kernel's and the gradient is TE's. In BF16 the two differ only by rounding; under MXFP8 the value is quantized and the gradient is that of the BF16 function (a straight-through estimator). The log-prob pass under `eval()` has no backward, so its single forward is the value pass.

The PR is two pieces that share one switch:

## 1. `moe_inference_training_forward`: inference kernel as the training value pass (BF16)

In a training step with selective `moe` recompute the MoE layer's forward runs twice: once to produce the output, once from backward to rebuild the graph. This mode makes the first run the inference expert kernel and leaves the second on TE.

* `TransformerConfig`: new `moe_inference_training_forward` and `moe_inference_training_max_tokens_per_rank`, with construction-time validation that rejects configurations where the value pass would be silently wrong rather than loudly broken:
  * `transformer_impl` must be `inference_optimized` (builds the inference-capable expert module).
  * `inference_grouped_gemm_backend` must be `vllm` or `torch`. `flashinfer` is rejected: it reads a shuffled copy derived from the parameters, so without a per-forward rebuild it would read weights the optimizer has already moved.
  * Selective recompute with `moe` is required (the value pass stores no activations); `cuda_graph_impl='local'` is rejected (it disables MoE-layer recompute).
  * `overlap_moe_expert_parallel_comm` is rejected (the overlapped schedule never reaches `MoELayer.forward`, where the pass is chosen).
  * Router settings that make the training router select different experts than generation's plain top-k are rejected: sinkhorn / quantile balancing, input jitter, forced load balancing.
* `InferenceGroupedMLP` (`experts.py`):
  * `forward()` takes `_inference_training_forward_pass()` on the value pass and falls through to `TEGroupedMLP` on the recompute pass. Dispatch is by `inference_grouped_gemm_backend`, so another backend is one branch plus a config allow-list entry.
  * `_uses_mcore_grouped_gemm()` is the single rule for which kernel torch/vLLM run; generation and the value pass both read it, so they cannot pick differently.
  * `_dense_routing_to_topk()` converts the training router's boolean map + dense probs to the `[tokens, topk]` indices the inference kernels take (selection read from the map, not from the largest probs, because `expert_bias`/`group_topk` choose on adjusted scores).
  * BF16 weights need no per-forward rebuild: the concatenated build redirects each parameter's `.data` into the stacked buffer, so optimizer updates write through.
* `MoELayer` (`moe_layer.py`):
  * `custom_forward()` picks the pass: value pass -> generation's dispatcher, recompute pass -> training's. The "value pass" flag is set just before the (possibly checkpointed) closure and consumed by its first call, so the recompute from backward always takes TE.
  * `_inference_forward_applies()` is intentionally **not** conditioned on `self.training`: RL frameworks run the log-prob pass under `eval()`, which is exactly the pass that must match generation.
  * The value pass allocates what the inference context normally provides: the valid-tokens scalar and, on NVLS, the symmetric heap (`_allocate_parity_symmetric_buffers`). The heap cannot grow, so it is sized to the larger of the live microbatch and `moe_inference_training_max_tokens_per_rank`, reduced across the EP group; an oversized later pass fails with a named assertion on every rank instead of hanging.

## 2. MXFP8 handling for the value pass

Under MXFP8 a training process holds TE's own MXFP8 parameters, whereas generation holds MCore `MXFP8Tensor`s produced once at load by `quantize_model_to_mxfp8` (which *deletes* the `nn.Parameter` it replaces, so it can only run on a model that will never see an optimizer). The value pass therefore cannot reuse generation's weight representation, and cannot cache one:

* `InferenceGroupedMLP._expert_params_use_te_mxfp8()` detects TE MXFP8 storage on the live parameters (the training counterpart of the existing `_expert_weights_use_mxfp8`).
* `_mxfp8_training_stack()` re-derives the stacked fc1/fc2 weights **every forward** from the live parameters. MXFP8 storage is a lossy function of the parameter, so a cached copy goes stale the moment the optimizer steps and the kernel would silently read last step's weights. It takes the same route generation took to the same bits: `_to_bf16` (dequantize TE storage) then `MXFP8Tensor.from_bf16`, per expert, with the backend `resolve_mxfp8_backend` picks. Per-expert quantization is kept (swizzled scales are not a reshapeable view) until a test pins a batched form.
* Kernel choice: torch always runs MCore's grouped GEMM; vLLM does so only for MXFP8 (its Triton kernel has no MXFP8 layout), exactly as in generation, via the shared `_uses_mcore_grouped_gemm()` rule.
* The existing assertion "MXFP8 inference optimized is not compatible with training / colocated RL" is kept for the normal path and exempted only in this mode, where the inference MXFP8 representation is never installed (the value pass quantizes into a scratch stack; the recompute pass runs TE, which owns its MXFP8).
* Semantics (opt-in, documented on the config field): under MXFP8 the value is quantized and the gradient is that of the BF16 function (straight-through estimator). In BF16 the value and TE's gradient differ only by rounding.

## End-to-end validation: Nemotron-3-Nano-30B-A3B GRPO (MXFP8 experts + TE recompute)

Model: `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-Base-BF16` (hybrid Mamba + MoE, squared-ReLU experts), GRPO in NeMo-RL, 2 nodes x 4 GB300, non-colocated (1 training node, 1 generation node). Job 694496, [W&B](https://wandb.ai/init-4bit-pretraining/rl_bi/runs/nanov3-mxfp8-infopt-zero-kl-694496).

* **Training:** TP1 / PP1 / CP1 / EP4 / ETP1; `batch_invariant_mode=true` (`te_native`), `use_mamba_mem_eff_path=false`, `MAMBA_DETERMINISTIC=1`; MXFP8 (`fp8_recipe: mxfp8`, `fp8_param: true`) on the **routed experts only**, everything else BF16; `moe_inference_training_forward=true` with `recompute_granularity=selective`, `recompute_modules=[moe]` (TE recompute); `moe_inference_training_max_tokens_per_rank=1024`; sequence packing and dynamic batching off.
* **Generation:** `transformer_impl=inference_optimized`, `inference_grouped_gemm_backend=vllm`, NVLS dispatcher, MXFP8 experts, local CUDA graphs (`block` scope), `logprobs_mode=raw_logprobs`.
* **Workload:** 3 GRPO steps, 4 prompts x 2 generations, `max_total_sequence_length=1024`, logprob batch size 1.
* **Result:** `Generation KL Error` is **0.0000 at steps 1, 2 and 3**. Steps 2 and 3 follow real optimizer updates and MXFP8 refits, so this checks that the value pass re-derives the MXFP8 stacks from the updated parameters every forward (a cached stack would have drifted).
* **What moved it from 0.0112 to 0.0000:** the earlier MXFP8 runs sat at a deterministic `0.0112` (identical over three runs). The cause found was precision policy, not the kernel: a `*experts*linear_fc1*` glob also matched `mlp.shared_experts.*`, so the dense shared expert was MXFP8 in training while generation did not expect that. Pinning shared experts to BF16 (a `*shared_experts*` matcher ahead of the routed-expert ones) gave 0.0000. The layer-level bitwise test cannot see this because it wraps only the routed-expert path. This is the observed effect of the change, not a traced proof of the mechanism.
* **Also in that run (not part of this PR):** #7562 (hybrid Mamba + squared-ReLU parity) and a separate fix for the shared MXFP8 param/grad buffer lifecycle under the distributed optimizer's offload, without which multi-step MXFP8 runs crashed in refit. See "Related PRs".
* **Limits of this evidence:** one model, 3 steps, short sequences; the metric prints four decimals; average reward is 0 (base model), so this is a parity check, not a training-quality result. Bitwise equality is established by the unit tests; this run shows the same at RL scale to the logged precision.

# Scope and known limits

* Opt-in; defaults are unchanged (`moe_inference_training_forward=False`), so the diff on the normal training path is behaviour-neutral.
* Backends: `vllm`, `torch`. `flashinfer` has no training-side weight lifecycle yet.
* Refit is deliberately not covered by the MXFP8 parity tests: in RL, generation's MXFP8 weights are quantized on the receiver from BF16 slices, while here both layers start from the same TE parameters.
* `overlap_moe_expert_parallel_comm` and local CUDA graphs are rejected, not supported.
* Throughput is not a goal: the mode exists for train/generation parity.
