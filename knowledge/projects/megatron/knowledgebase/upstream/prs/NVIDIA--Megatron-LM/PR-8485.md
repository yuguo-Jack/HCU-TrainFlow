# Unify preset FSDP execution order traversal

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8485) · state: closed · merged: True

## Original PR description

## Summary

Replace separate forward and backward execution orders with one weakly held sequence of `ExecutionEvent(module, phase)` values and one cursor. Registration mode populates the sequence during construction; recorded mode populates it from execution. Both use the same traversal.

## Implementation

- Validate each observed module and phase against the event at the cursor, raising on divergence.
- Use argument-free `advance()`, which automatically wraps at the end of the sequence.
- Prefetch successive events using each event's phase and the existing prefetch budget. Forward/backward phase changes do not stop lookahead.
- Preserve every recorded occurrence, including repeated calls to the same module.
- Test registration-order divergence with a model that executes its two layers in the opposite order from registration.
- Use recording mode for the shared-MTP regression, whose shared block runs twice per forward pass; retain its five-step comparison with unsharded training.

The execution-order implementation follows #8721. This PR changes three production files and three test files. Complete schedule-window recording, PP/VPP and EP-overlap integration, and evaluation handling are covered separately in #8778.

- shjwudp · comment · 2026-11-02T08:52:29Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8485#issuecomment-6572980742)

> A question raised during my cleanup: given we consolidate forward and backward into one order, should prefetching stop at phase boundary? My first instinct says it shouldn't because forward and backward can interleave in PP and VPP.

@wujingyue Yes, I agree—we shouldn't impose phase boundaries on prefetching. If `execution_order` spans multiple microbatches, prefetching should be able to cross those boundaries as well.

While comparing DSv4 Flash performance with ZeRO-3 (M-FSDP v2 + MXFP8) and ZeRO-1 (DistOpt + MXFP8), I found that the all-gather at the start of each microbatch and the reduce-scatter (RS) at the end account for a **10% gap in step time**. Prefetching the next microbatch's module weights could help narrow this gap by unblock next microbatch executing.
