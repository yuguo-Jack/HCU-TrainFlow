# Enter the paged-stash capacity reduction on every rank

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8821) · state: closed · merged: False

## Original PR description

**Why.** `PagedStashRunner.check_moe_overflow` first votes over WORLD on whether any rank went over its receive budget. When one did, a second `all_reduce` takes the MAX of the receive capacity the step needed. Only ranks whose model chunks hold an MoE layer that reports a required capacity entered that second call: NCCL EP built in non-eager mode.
- A pipeline stage made only of dense layers has no such layer, so it skipped the reduction. The MoE stages waited in it while the dense stage moved on to the rerun.
- The result is a deadlock until the NCCL timeout, or a later WORLD collective paired with the wrong one.
- Example: `--moe-layer-freq ([0]*3+[1]*5)` with 8 layers and PP=4 puts two dense layers on stage 0. Add `--moe-flex-dispatcher-backend ncclep` and `--moe-expert-rank-capacity-factor`, and the first over-budget step hangs.
- WORLD is the right group here, because the rerun is a job-wide decision that pairs with the vote. The bug is the rank-local guard around the call.

**What.**
- Once the vote reports an over-budget rank, every rank enters the reduction. A rank without a reporting MoE layer contributes 0.
- The same call reduces `max_tokens_per_rank * router_topk`, so a dense rank 0 logs the same capacity factor as the MoE ranks. Ranks without MoE layers no longer read `self.moe_layers[0]`.
- A capacity of 0 after the reduction leaves `_required_recv_capacity` unset, as before. That is the case for HybridEP, which reports none.
- The happy path keeps its single collective.

**Tests.**
- Two new tests in `tests/unit_tests/transformer/moe/test_paged_stash_runner.py` run `check_moe_overflow` for a rank with an over-budget MoE layer and for a rank with no MoE layers. `torch.distributed.all_reduce` is replaced by a two-rank stand-in.
  - Both ranks must issue the same collectives (a SUM over 3 flags, then a MAX over 2 values), and both must get the same capacity and factor.
  - When no rank reports a capacity (HybridEP), both ranks enter the reduction, and the capacity stays unset.
- On CPU this branch gives 5 passed. Main with only the new tests gives 1 failed and 4 passed. The failure is the dense-stage test, where the dense rank issues only the vote.
- On 4 GPUs, `test_paged_stash_runner.py` gives 5 passed here: main's 3 plus the 2 new tests. `test_quantile_balancing.py`, which also drives the paged-stash runner, gives 51 passed and 8 skipped on both sides. No unit or functional test runs NCCL EP with `moe_expert_rank_capacity_factor` and a dense pipeline stage end to end.
- `tools/check_process_group_usage.py` reports the same 3 pre-existing entries as main. `tools/check_kernel_determinism_coverage.py` passes for both files.

**Compatibility.**
- Steps within budget: no change.
- Over-budget steps: every rank issues one more `all_reduce`, of 2 int64 values. With HybridEP the reduced capacity is 0, so nothing else changes.

The audit of group-less collectives for #6307 found this. The bug is on main, and the fix changes no process group.
