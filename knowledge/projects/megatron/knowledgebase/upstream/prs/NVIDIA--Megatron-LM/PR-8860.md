# [CI][Attention] Lock FlashAttention-4 to the releases its quack-kernels and Transformer Engine can run

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8860) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Locks flash-attn-4 (FA4) to the releases that work with both the quack-kernels and CuTe DSL it calls and the Transformer Engine Megatron locks, makes the dev CI image import the locked copy, and makes Megatron gate FA4 on the copy that actually imports. In the current dev image, FA4 cannot compile its SM100 forward, so dynamic-batching attention crashes on GB200. Newer FA4 releases fix that but make TE 2.20's FA4 backend return zeros for causal attention, so the lock stops below them and Megatron refuses that pairing.

**Bug.** The dev CI image pairs the base image's flash-attn-4 `4.0.0b24` with the quack-kernels `0.6.5` that Megatron's lock installs into `/opt/venv` (`constraint-dependencies = ["quack-kernels>=0.6.5"]`, from #7683). The venv's quack shadows the base image's `0.6.2`. FA4 `4.0.0b20` through `b25` call `quack.activation.sub_packed_f32x2`, and quack-kernels 0.6.5 removed it:
- b24 calls it in `ex2_emulation_2` (`flash_attn/cute/utils.py:770,773`), which the SM100 softmax uses for head dim <= 128 (SM103 disables the emulation).
- b24 also calls it in `flash_bwd_sm100.py:3269`, in the backward pass.

So every such FA4 forward on SM100 fails to compile with `AttributeError: module 'quack.activation' has no attribute 'sub_packed_f32x2'`. Dynamic-batching attention prefers FA4 whenever it is installed (`Attention._resolve_flash_version`), so every dynamic prefill and decode on GB200 hits this. So does anything that pins `flash_attention_version=4`, such as the FlashInfer MXFP8/NVFP4 inference tests.

**A second incompatibility, with Transformer Engine (P4-N6).** Moving FA4 to 4.0.0b37 fixed the compile but broke TE: in the GB200 batch-invariant RL test, TE `DotProductAttention` on its FA4 backend differed from an fp32 reference by rel 1 in every call, so engine log-probs and the batched forward differed by up to 0.28 nats. Megatron's own FA4 calls stayed correct (rel ~0.002). TE before 2.21 passes FA4 the window `(-1, 0)` for every causal mask (`check_set_window_size`), with -1 meaning unbounded. FA4 4.0.0b30 changed `_resolve_causal_local_window` to drop the window only when both bounds are negative (b29 and earlier dropped it when their sum was negative), so b30 and later read `(-1, 0)` as a window from i+1 to i, which is empty, and every causal row comes out zero. Megatron passes `(-1, -1)`, which every release reads as no window. TE fixed this in #3532, merged through #3540 (in TE 2.21.0), by passing FA4 `None` for -1; the TE that Megatron locks (2.20.2+44f31bbe) predates it. TE runs FA4 by default (`NVTE_FLASH_ATTN_V4` defaults to 1) on SM90 and newer, preferring cuDNN where it can, so this zeroes causal attention in any run with `--attention-backend flash` (including batch-invariant mode) and in auto-backend calls cuDNN cannot take.

**Root cause.** FA4 is not in Megatron's lock, so nothing keeps it in step with the quack-kernels and nvidia-cutlass-dsl that the lock moves. There is a second, packaging layer: FA4 installs into FlashAttention 2's `flash_attn` package (its wheel ships `flash_attn/cute/` and no `flash_attn/__init__.py`). The base image ships FA2 and FA4 together in the system site-packages, where FA2's `flash_attn/__init__.py` makes `flash_attn` a regular package. Python then resolves `flash_attn.cute` only in that directory. A copy that uv installs into the venv is never imported, but `importlib.metadata.version("flash-attn-4")`, which Megatron's `HAVE_FA4` gate read, reports the venv's version first. So the gate could pass for a copy that is not the one that runs.

**Fix.**
- `pyproject.toml`: `flash-attn-4>=4.0.0b27,<4.0.0b30` in the `dev` extra, next to the other CuTe DSL kernel packages (`flashinfer-python`, `nvidia-cudnn-frontend[cutedsl]`). The dev image installs that extra and the LTS image does not, so LTS is unchanged. From each release's metadata and a scan of its sources against quack-kernels 0.6.5 and nvidia-cutlass-dsl 4.8.0:
  - Floor b27: b20 to b25 call the removed `quack.activation.sub_packed_f32x2`. b26 calls `cute.arch.sub_packed_f32x2` instead, but b20 to b26 pin `nvidia-cutlass-dsl==4.6.0.dev0`, and quack-kernels 0.6.5 requires `nvidia-cutlass-dsl>=4.7`. b27 and later need `nvidia-cutlass-dsl>=4.6.2` and `quack-kernels>=0.5.3`, which the lock (4.8.0 and 0.6.5) satisfies, and every quack attribute they reference exists in 0.6.5.
  - Ceiling b30: the window change above, which TE <= 2.20 cannot drive. The ceiling comes off with the TE bump to 2.21.0, a separate follow-up PR.
  - b27 to b29 declare `apache-tvm-ffi>=0.1.12`, which the lock's existing override replaces with 0.1.11; their only direct `tvm_ffi` use (`tvm_ffi.Function`, `tvm_ffi.__version__`) is the same as in b34 and later, which accept 0.1.11.
- The lock pins 4.0.0b29, the newest release in that range (see **Lock** below). Its `flash_attn_varlen_func` takes every argument Megatron passes (`page_table`, `seqused_k`, `num_splits`, `return_lse`, `softcap`, and `window_size=(-1, -1)`), it returns `(out, lse)`, and it has the same paged-KV and split-KV support by architecture as b36/b37 (paged KV not on SM80 or SM120, split-KV not on SM80, SM90 or SM120).
- `megatron/core/transformer/attention.py`:
  - `HAVE_FA4` now reads the version of the flash-attn-4 distribution that owns the `flash_attn/cute/__init__.py` that `import flash_attn.cute` resolves to (`_imported_fa4_version`), instead of the first `flash-attn-4` metadata on `sys.path`. An environment whose imported copy is older than the floor (for example a venv with the locked FA4 over a base image with FA2 and an older FA4) now falls back cleanly to FA3 or FA2 rather than crashing in the FA4 compile. An editable install, which owns no file next to its metadata, still counts when it is the only one installed.
  - `_MIN_FA4_VERSION` goes from `4.0.0b20` to the same floor as pyproject.toml, `4.0.0b27`. There is no runtime ceiling here: Megatron's own FA4 calls are correct on b30 and later.
  - An installed FA4 below the floor is no longer dropped silently: Megatron warns at import (`flash-attn-4 4.0.0b24 is installed, but Megatron needs >= 4.0.0b27, so FlashAttention-4 will not be used`), and a pinned `flash_attention_version=4` fails with that reason instead of "FlashAttention-4 is not installed". This includes the stock NGC 26.09 pairing (FA4 b24 with quack-kernels 0.6.2), which runs but is outside the dependency set Megatron requires (`quack-kernels>=0.6.5`).
- `megatron/core/transformer/utils.py`: `set_attention_backend`, which configures TE's attention backends when a model is built, now refuses the TE/FA4 pairing above: Transformer Engine before 2.21 together with an imported flash-attn-4 (the copy `flash_attn.cute` loads) at 4.0.0b30 or later, when TE can select its FA4 backend for the model (FlashAttention and its version 4 enabled in TE's environment, which covers `attention_backend` flash and auto, batch-invariant mode and `flash_attention_version=4`; an SM90 or newer GPU; not `transformer_impl='local'`). The `RuntimeError` explains the empty window and how to resolve it: flash-attn-4 within the locked range, Transformer Engine >= 2.21.0, or an attention backend that keeps TE off FA4. The pyproject bound covers uv installs only; this covers anyone who installs a newer FA4 next to an older TE.
- `docker/Dockerfile.ci.dev`: `uv sync` skips flash-attn-4 (`--no-install-package flash-attn-4`). The locked flash-attn-4 requirement, with its hashes, is taken from `uv export --frozen` (same extras as the sync) and installed with `--no-deps --require-hashes` into the system site-packages, next to FA2, replacing the base image's copy. The image then has one FA4, the locked one, and it is the one that imports.
  - The install names its interpreter: the one the venv was created from, `sys.base_prefix/bin/pythonX.Y` as the venv reports it (`/usr/bin/python3.12` in the NGC PyTorch images, the same on x86_64 and aarch64 as derived at build time, whose system packages live in `/usr/local/lib/python3.12/dist-packages`). `uv pip install --system` does not: it takes the first Python on PATH, which in this image is `/opt/venv`, so the base image's b24 stayed in place and kept being imported. A diagnostic run in an image built from `main` showed exactly that.
  - The build then fails unless the venv's interpreter imports the locked flash-attn-4: a short inline check resolves `flash_attn.cute` with `importlib.machinery.PathFinder`, without running FA2's or FA4's `__init__`, so it needs no GPU, and compares the version of the distribution that owns that file with the locked one. It also fails if the image's Transformer Engine is older than 2.21.0 and the locked FA4 is 4.0.0b30 or later, so lifting the ceiling without the TE bump breaks the build. A wrong or missed install now breaks the image build instead of producing a stale image.
  - `--no-config` keeps the project's unpinned `constraint-dependencies` out of the `--require-hashes` install. The LTS image is built from `Dockerfile.ci.lts`, whose extras do not include flash-attn-4, so it is unchanged.
  - I ran these exact commands with uv 0.7.2, the version the image uses, on a stand-in base interpreter with FA2's `__init__.py` and FA4 b24, under a `--system-site-packages` venv that is first on PATH: the check fails before the step (b24 imports), and after it the base has only the locked FA4, the venv has no FA4, and the check passes. In the same setup, `--system` picked a different interpreter from PATH. The TE part of the check passes for b29 with TE 2.20.2+44f31bbe and fails for b37.

**Lock.** `uv.lock` is not regenerated in this PR; it must be regenerated inside the CI container (on a host, `uv lock` fails building the git sources `torch-memory-saver` and `mamba-ssm`). Use `uv lock --upgrade-package flash-attn-4==4.0.0b29`, not `--upgrade`. The diff must contain only:
- a new `[[package]]` `flash-attn-4` `4.0.0b29` from PyPI (wheel `flash_attn_4-4.0.0b29-py3-none-any.whl`, `sha256:85dd4b0e98ca38f5681a3214b2f9f230638030e3b868a50f3873336fc98d7537`; sdist `sha256:ad79d2029dbb0c7fb09b92d989caf72cfa207cedb09d58b281caab23bed077bc`), with dependencies `apache-tvm-ffi`, `einops`, `nvidia-cutlass-dsl`, `quack-kernels`, `torch` (marker `sys_platform == 'never'`), `torch-c-dlpack-ext` and `typing-extensions`;
- in `megatron-core`, `{ name = "flash-attn-4" }` under the `dev` optional dependencies and `{ name = "flash-attn-4", marker = "extra == 'dev'", specifier = ">=4.0.0b27,<4.0.0b30" }` in `requires-dist`.

No other version may change: `nvidia-cutlass-dsl` 4.8.0, `quack-kernels` 0.6.5, `apache-tvm-ffi` 0.1.11, `torch-c-dlpack-ext` 0.1.5, `einops` 0.8.2 and `typing-extensions` 4.16.0 are already locked. Until the lock is regenerated, `uv sync --locked` in the image build fails. Any other PR that regenerates `uv.lock` (for example the FLA one) must re-run `uv lock` in the CI container after the other lands, rather than merge lock hunks.

**Follow-up (not in this PR).** Bump Transformer Engine to 2.21.0 (`7457e47d`), which contains #3532/#3540 and the #3635 change the current pin carries, and lift the FA4 ceiling in the same PR. That moves TE by 119 commits (cuDNN minimum 9.12, attention-backend changes, a TE rebuild), so it is its own PR.

**Kernel change on H100 too.** Until #8584 lands, dynamic batching auto-selects FA4 on Hopper as well, so the H100 dev image's dynamic-batching attention also moves from FA4 b24 to b29 when the image is rebuilt, not only GB200. So does TE's FA4 backend wherever TE selects it. Dynamic-inference functional goldens may move on both.

**Test** (`tests/unit_tests/transformer/test_attention_fa4.py`, marked `launch_on_gb200`, and `tests/unit_tests/transformer/test_utils.py`):
- `test_te_flash_attention_4_causal_matches_reference[32|128-default|batch_invariant]` (SM90+, H100 and GB200): Megatron's `TEDotProductAttention` with TE pinned to its FA4 backend (`NVTE_FLASH_ATTN_V4=1`, FA2/FA3/fused/unfused off), causal, q/k/v as views of the fused projection as the training forward passes them, without and with batch-invariant mode, against fp32 causal attention. It first checks that TE actually ran FA4. With TE 2.20 and FA4 b30+ (b37) every row is zero (rel 1); with b29 it passes on H100 and GB200.
- `test_utils.py::test_set_attention_backend_refuses_te_flash_attention_4_window_pairing` (CPU, mocked TE and FA4 versions and device): refuses TE 2.20 with FA4 b30/b37 for `flash`, `auto` and pinned version 4; accepts b29, TE 2.21, the fused backend, a pinned FA2, and no FA4. The three refusal cases fail without the check.
- `tests/unit_tests/models/test_gpt_model_batch_invariant.py::TestGPTModelBatchInvariant::test_dynamic_engine_matches_batched_forward_rl` is the end-to-end check for P4-N6: it failed with b37 on H100 and GB200 (up to 0.28 nats) and passes with b24 on H100.
- `test_fa4_version_is_read_from_the_copy_that_imports[venv-over-fa2|namespace|editable]` (CPU): builds site-packages directories in `tmp_path` and checks the version `_imported_fa4_version` reads. With a venv b37 over a base image with FA2 and b24, it reads b24, the copy that imports, where the old gate (`importlib.metadata.version`) read b37. Without FA2 (`flash_attn` a namespace package), it reads the first copy, b37. For an editable install, it reads the only distribution's version.
- `test_megatron_gates_on_the_fa4_that_imports`: in the running environment, Megatron's gate version is the version of the copy `flash_attn.cute` loads, and that FA4 meets the floor. In the CI image without the Dockerfile step, this fails with `flash-attn-4 4.0.0b24 is installed, but Megatron needs >= 4.0.0b27`.
- `test_fa4_quack_references_resolve`: reads every quack attribute that the imported FA4's sources reference (`ast`) and checks that each one resolves in the importable quack-kernels.
- These two environment checks guard the CI images. They fail, rather than skip, wherever an FA4 older than the floor is installed, and the quack scan counts every reference as required.
- `test_fa4_paged_attention_on_sm100[prefill|decode]`: runs `Attention.flash_decode_and_prefill` with `flash_attention_version=4` and head dim 128 on SM100, which is the emulated-exp2 path. Paged KV with GQA, a fresh 64-token prompt, and a 300-token request spanning two blocks (chunked prefill, then decode). Compared to an FP32 reference. On SM100 a missing or too-old FA4 is a failure, not a skip.

With the real wheels (FA4 b24/b37, quack-kernels 0.6.5, nvidia-cutlass-dsl 4.8.0), b37 passes both environment checks and b24 fails both; a static scan finds every quack attribute b27, b28 and b29 use in quack-kernels 0.6.5. The GPU reference was checked against `scaled_dot_product_attention` on CPU.
- Earlier, on b37 with the Dockerfile step emulated (GB200): the G1 tests passed 7/7, and Megatron's own FA4 calls matched fp32 at 16/128/256-token pages, contiguous and strided q, prefill and decode, one split and the split heuristic; TE's FA4 backend did not (P4-N6).
- On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), with this PR's Dockerfile change applied in the container (FA4 4.0.0b29 installed into the base interpreter; the Dockerfile's check then reports that `flash_attn.cute` imports b29 with TE 2.20.2+44f31bbe): the regression tests pass (16 cases: the TE FA4 test, the three layout tests, the refusal test and the batch-invariant RL test). The neighbor tests (`test_utils.py`, `test_softmax_scale.py`) pass (32 and 18 cases).
