# [Dev] Bound optimizer-owned master weights by the offload chunk size

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8232) · state: closed · merged: True

## Original PR description

# What does this PR do ?

Makes `--optimizer-state-offload-chunk-size-mb` bound optimizer-owned master weights.

Chunked optimizer-state offload (#6244) restored every selected master weight as one full window before the first state chunk, so the chunk size never bounded masters:

- **Optimizer-owned masters** (precision-aware FusedAdam's `state['master_param']`, an fp32 copy or the int16 remainder of a bf16 parameter) are read only by the optimizer's own update. They are now ordinary chunk state: staged, updated and copied back with their chunk, and counted by the chunk planner.
- **MCore-owned masters** are read by main-to-model copies after the update, so they keep the full restore window.

One manager still cannot hold both kinds; `_validate_master_storage` rechecks this after lazy init.

## Memory

One H200, on `dev` at c3010d6: a bf16 MLP with hidden size 4096 (268M parameters) under a dense `DistributedOptimizer`, precision-aware FusedAdam (fp32 moments, int16 master remainders, the `store_param_remainders` default), offload fraction 1.0, 128 MiB chunks. Peak is the maximum `active_bytes` above the pre-step level during the step:

| | `dev` | this PR |
|---|---|---|
| step peak | 768 MiB | **320 MiB** (−58%) |
| step time | 70.8 ms | 66.4 ms |

On `dev` the peak grows with the model, because the whole master window (2 bytes per parameter here) is restored at once; with this PR it stays at the chunk bound. Parameters match a non-offloaded run exactly.

## Tests

- New `test_optimizer_owned_masters_ride_with_their_state_chunk`: a chunk step never sees the whole master window on GPU, and the result matches a non-offloaded run bit for bit.
- `tests/unit_tests/test_optimizer_state_offloading.py` on H200: 52 passed, 1 skipped (`dev`: 51 passed, 1 skipped).

- hxbai · comment · 2026-10-20T03:12:49Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8232#discussion_r4321089879)

File: `megatron/core/optimizer/cpu_offloading/chunked_optimizer_state_offload.py` · line 27

Could we use a single-byte buffer per device in each staging slot, with 256-byte-aligned typed views? (the buffer allocation in `_state_staging_views`)

Now that master_param participates in chunk staging, the dtype-keyed pools can retain unused capacity. With BF16 moments and parameter remainders enabled, two native-FP32 chunks followed by two BF16 chunks—each containing C bytes of state including masters—leave 3C of backing storage across the two slots: the old FP32 master buffers remain allocated alongside the new int16 buffers.

A shared byte buffer would reuse capacity across dtype changes while preserving the existing stream ordering. Could we also add a mixed-FP32/BF16 regression checking total backing-buffer bytes and storage reuse? Counting CUDA-bound master tensors does not capture unused buffers retained by the slots.

File: `megatron/core/optimizer/cpu_offloading/chunked_optimizer_state_offload.py` · line 27

Good catch, thanks. Done in 2b9cf62: each staging slot now holds one `uint8` buffer per device, and every state tensor is a 256-byte-aligned typed view into it, so a dtype change reuses the same storage. Stream ordering is unchanged.

Added `test_mixed_dtype_chunks_reuse_one_staging_buffer_per_slot`: two FP32 chunks (FP32 moment + FP32 master), then two BF16 chunks (BF16 moments + int16 remainder). It checks that the BF16 views share storage with the FP32 ones, that each slot holds one buffer, and that the total backing bytes equal `2 * largest chunk`. On the previous commit it fails (the FP32 buffers stay allocated next to the BF16 and int16 ones); with the change, the whole file passes on H200 (53 passed, 1 skipped).
