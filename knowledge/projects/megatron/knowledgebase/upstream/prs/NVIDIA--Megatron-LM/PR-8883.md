# [SSM][KDA][Determinism] Pin FLA's autotuned kernels in deterministic mode, which KDA and GDP run on

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8883) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes `deterministic_mode` pin the Triton autotune choices of FLA's kernels, which KDA and Gated Delta Product (GDP) layers run on, as it already pins the in-tree, `mamba_ssm` and Transformer Engine kernels. In deterministic mode, FLA's kernels no longer time their candidates; outside it they still do.

**Bug.** KDA has no non-FLA core kernel. Under `deterministic_mode` it still runs FLA's `chunk_kda`. With two-stage gates it also runs FLA's L2 norm and fused gated RMSNorm; single-stage gates swap in `torch_l2norm` and `F.conv1d`. GDP training runs FLA's `chunk_gated_delta_product` and `l2_norm` whatever `deterministic_mode` says, and its chunkwise-CP backend launches FLA kernels directly. GDN and GDN2 avoid FLA under `deterministic_mode` by requiring `gdn_kernel_backend="torch"`.

The autotune policy pinned only `DEFAULT_MODULES = ("mamba_ssm", "transformer_engine", "megatron.core")`. FLA's `CachedAutotuner` goes through the patched `Autotuner.run`, but it was out of scope, so every multi-candidate FLA autotuner kept Triton's timed choice. FLA's own config cache is off by default and the wheel ships no tables. Triton persists the timed winner per cache directory, so cold runs (new nodes, CI, per-job caches) and different ranks can pick different configs.

In the step 3 GPU repro on H100, forcing one candidate at a time in a deterministic two-stage KDA layer (H = 4, K = V = 128, T = 256, B = 2, BF16) changed the layer output's bits for three kernels:

| FLA kernel | Reference vs. candidate | max \|diff\| |
|---|---|---|
| `fla.modules.l2norm.l2norm_fwd_kernel` | `num_warps` 1 vs 8 | 3.9e-3 |
| `fla.modules.fused_norm_gate.layer_norm_gated_fwd_kernel` | `num_warps` 4 vs 16 | 9.8e-4 |
| `fla.ops.kda.gate.kda_gate_chunk_cumsum_vector_kernel` | `BS` 32 vs 64 | 3.9e-3 |

`chunk_kda_fwd_kernel_inter_solve_fused` and `chunk_gla_fwd_kernel_o` were bit-identical over the candidates tried. The determinism manifest note for the gated-delta-net group said deterministic mode avoids FLA, which was false for `kda.py`.

**Fix.**
- Add `fla` to the policy's default modules. In deterministic mode FLA's autotuners are now pinned like the in-tree ones: from a recorded table when one matches, else the cheapest candidate by the policy's static estimate, without timing. I preferred this to rejecting KDA with `deterministic_mode`, which would leave KDA without a deterministic configuration at all. This also re-pins GDP's FLA forward and backward kernels in deterministic training.
- Outside deterministic mode FLA's kernels keep Triton's timed choice, but the options that observe the timed choices now also see FLA's: `record` mode records their winners (so FLA tables can be recorded), and `--triton-autotune-verify-every` compares them across ranks, warning (or, with `--triton-autotune-verify-strict`, raising) when cold ranks timed different winners.
- KDA's two-stage gated norm now calls FLA's `rms_norm_gated` outside `torch.compile`; `jit_fuser` moves to the single-stage norm-and-gate helper, as GDN splits it. Under `no_grad` (evaluation, static inference) Dynamo used to trace `layer_norm_gated_fwd_kernel` into the compiled graph, where Inductor times the candidates itself and never calls `Autotuner.run`, so the policy could not pin it. With grad, Dynamo graph-breaks inside FLA's autograd function, so only no-grad forwards were affected.
- The static cost estimate understands FLA's tiles. It counted only `BLOCK*` arguments, so every FLA candidate cost `(num_stages, num_warps)`: the pin was the fewest-stage, fewest-warp candidate in FLA's list order, whatever its tile. `estimate_config_cost` now also counts `B` plus the tiled dimension (`BT`, `BK`, `BV`, `BS`, ...), so the pin is the smallest tile with the fewest stages, the likeliest to fit in shared memory. Among equal tile costs it prefers one warpgroup (4 warps), the smallest launch on which Triton uses Hopper's and Blackwell's warpgroup tensor-core instructions, then the nearest larger count, then the nearest smaller one, instead of 1-2 warps. This applies to every pinned kernel without a table entry, so in-tree kernels pinned at 1-2 warps on architectures without a table (for example the mHC kernels and the GDP forks on H100) now run at 4 warps. The estimate is still not a throughput model; a recorded table recovers the timed winner's speed. I did not ship FLA tables: they have to be recorded on sm90 and sm100 with `--triton-autotune-mode record`.
- FLA also dispatches some backward kernels to TileLang when TileLang is installed (it is, through `mamba_ssm`): KDA's `chunk_kda_bwd_wy_dqkg_fused` in FLA 0.5.1 and 0.6.0, and the gated `chunk_bwd_dqkwg` that GDP's backward calls (every GPU in 0.5.1, Hopper in 0.6.0). Those never reach Triton's autotuner, but they make no timed choice: their tiles, warps and stages follow from the input shapes and the GPU (checked in both versions' source; no TileLang autotuning, no atomics). The replay tests cover them and assert that they ran. I did not disable the dispatch under deterministic mode. `FLA_DISABLE_BACKEND_DISPATCH` is read once, when FLA is imported, which is before deterministic mode is known. With `FLA_TILELANG=0`, FLA 0.5.1 raises in the gated `chunk_bwd_dqkwg` on Hopper with Triton >= 3.4 (FLA #640), which would break GDP's deterministic backward on H100.
- I did not mark the bit-identical kernels as config-invariant: the run tried only one-axis variants, and the policy admits only kernels proven invariant over every candidate.
- The manifest notes say how each layer is covered. The tuning README and the deterministic-training guide describe the new default scope and the estimate.

**Tests.**
- `tests/unit_tests/tuning/test_autotune_interception.py::test_deterministic_mode_pins_the_fla_kernels_kda_runs` (CPU, Triton's real `Autotuner` over a fake launcher). Under the default policy in deterministic mode, a tuner defined in each of FLA's L2 norm, gated norm and KDA gate modules runs its pinned config without benchmarking. On `main` it benchmarks, and the test fails (checked on CPU).
- `tests/unit_tests/tuning/test_autotune_policy.py::test_cheapest_counts_fla_tile_sizes` and `::test_cheapest_prefers_one_warpgroup_on_equal_tiles` (CPU). They fail with the old estimate and pass with the new one (checked).
- `tests/unit_tests/determinism/kernels/test_ssm_kernels.py::test_kda_deterministic_mode_pins_fla_autotuners` (1 H100, TE and FLA), for head dims 64, 128 and 256 with single-stage gates, two-stage gates, and two-stage gates under `no_grad`. Any benchmark fails it. The forward (and backward) must replay bit-exactly, every FLA autotuner the layer reaches must be pinned, including the three kernels above, and FLA's TileLang KDA backward must have run wherever FLA dispatches to it. On `main` the first FLA launch benchmarks; before the gated-norm change, the `no_grad` case misses `layer_norm_gated_fwd_kernel`.
- `test_ssm_kernels.py::test_gdp_deterministic_mode_pins_fla_autotuners` (1 H100). The GDP mixer's forward and backward replay bit-exactly with every FLA autotuner pinned and no benchmark, and FLA's TileLang `chunk_bwd_dqkwg` must have run wherever FLA dispatches to it.
- `test_ssm_kernels.py::test_fla_chunk_gated_delta_rule_replays_fwd_bwd` is no longer `xfail`: its FLA kernels are now pinned and reduce without atomics, and it passes on H100.

`tools/check_kernel_determinism_coverage.py --base-ref origin/main` passes, and so does `test_manifest.py`.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), the regression tests pass (16 cases, including the nine KDA cases at head dims 64, 128 and 256) and fail on `main` (15 of 16 cases). On `main` the pinning tests fail because an FLA autotuner benchmarked a config, and the two estimate tests fail on the old estimate. `test_fla_chunk_gated_delta_rule_replays_fwd_bwd`, without its `xfail`, passes both with this PR and on `main`. The neighbor tests (`determinism/kernels/test_ssm_kernels.py`, `determinism/kernels/test_autotune_kernels.py`, `ssm/test_kda.py`) pass (122 cases, 12 skipped).
