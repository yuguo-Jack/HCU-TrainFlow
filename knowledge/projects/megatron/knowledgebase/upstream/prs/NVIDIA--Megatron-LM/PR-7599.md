## What does this PR do?

Adds the concrete, model-independent streamwise wide-residual components on top of the generic
residual-connection protocol and structured operators introduced by #7579:

- `WideResidualConfig`;
- positive streamwise sigmoid read and write controllers;
- `StreamwiseSigmoidWideResidualConnection`;
- optional bounded learned retention;
- ordinary-width-to-wide expansion and wide-to-ordinary readout helpers;
- optimizer and tensor-parallel metadata for the small replicated controller parameters; and
- direct numerical, state-dict, module-hook, optimizer-routing, and TP synchronization tests.

This PR does **not** wire these components into Transformer, Mamba, GPT, or HybridStack model
construction. It therefore does not enable wide-residual execution by itself. That architecture
integration remains in the dependent PR #6716.

## Motivation and algorithm

A wide residual state carries `K` contiguous streams of ordinary hidden width `D`. The stored
tensor has shape `[S, B, K * D]` and can be viewed conceptually as

$$
X_\ell \in \mathbb{R}^{S \times B \times K \times D}.
$$

For one ordinary-width residual branch, the connection first reads a width-`D` activation:

$$
z_\ell = \sum_{i=1}^{K} c_{\ell,i} X_{\ell,i},
\qquad c_{\ell,i} = \sigma(\alpha_{\ell,i}).
$$

The existing branch computes an update $v_\ell$ at width `D`. The connection then writes that
update to every stream:

$$
X_{\ell+1,i} = \rho_{\ell,i} X_{\ell,i} + w_{\ell,i} v_\ell,
\qquad w_{\ell,i} = 2\sigma(\beta_{\ell,i}).
$$

Retention is disabled by default, in which case $\rho_{\ell,i}=1$. When enabled, it is bounded by

$$
\rho_{\ell,i} = 1 - \mathrm{max\_forget}\,\sigma(-\gamma_{\ell,i}).
$$

At initialization, every read factor is exactly `1 / K`. Write logits are evenly spaced and
symmetric around zero, so mirrored write factors sum to two and the mean write factor is exactly
one. Consequently, with retention disabled, replicated input streams preserve the ordinary
residual computation at initialization while allowing individual streams to diverge during
training.

## Design

### Concrete connection modules

`StreamwiseSigmoidWideResidualConnection` implements the abstract `ResidualConnection` contract
from #7579. It owns separate child modules for the read map, write map, and optional retention.
Calling those child modules through `nn.Module.__call__` ensures parameter materialization hooks
run before their logits are accessed.

The connection delegates arithmetic to the structured native/Triton operators from #7579. It
does not construct dense `K * D` by `D` maps or allocate a repeated full-width branch update.

### Small replicated controller parameters

Read, write, and retention logits contain only one active scalar per stream. Their storage is
padded to a small minimum size so distributed-optimizer partitioning does not create empty shards;
only the first `K` values participate in computation, and the padded suffix receives zero
gradient.

The controllers are replicated across tensor-parallel ranks and carry explicit gradient-reduction
metadata. Read/write maps opt out of Muon routing. Learned-retention parameters carry a dedicated
marker so they inherit the run's configured weight decay rather than the generic zero-WD rule for
one-dimensional parameters.

### Model-boundary helpers

`expand_wide_residual_stream` copies one ordinary-width activation into `K` contiguous streams.
`StreamwiseSigmoidResidualReadout` contracts a wide activation back to width `D` using the same
positive read parameterization. This PR defines and tests these helpers but does not decide where
a model invokes them; #6716 owns that architecture-level wiring.

## Scope and dependency chain

1. #7579 provides the generic residual-connection protocol and native/Triton structured operators.
2. **This PR** provides the concrete streamwise connection, configuration, parameter policy, and
   model-boundary helpers.
3. #6716 integrates those components into explicit wide Transformer and Mamba layers and
   HybridStack model construction.
4. FP32 execution support is isolated in a subsequent focused follow-up.

Keeping these responsibilities separate lets the connection mathematics and parameter semantics
be reviewed without also reviewing model construction, training CLI, or activation replay.
