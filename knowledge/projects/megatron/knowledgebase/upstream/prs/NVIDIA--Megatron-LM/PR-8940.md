# Fix FP32 router numerical contract: bypass TE general_gemm for fp32 routers (TF32-grade despite FP32 operands)

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8940) · state: open · merged: False

## Original PR description

## Summary

Bypasses `te_general_gemm` for `router_dtype == torch.float32` (forward and backward), routing FP32 routers through the existing `torch.mm` fallback branch. Fixes #8126 (reported by @tang-t21, analysis in the issue thread).

## Why the "explicit operand casts" candidate does not work

Measured on GB200 + TE 2.16.0 (torch 2.7.1+cu128, `allow_tf32=False`):

- **Forward with FP32 operands**: `general_gemm(weight.float(), inp.float())` output is **bitwise identical** to a `torch.mm` run with TF32 enabled (100% of elements, max abs diff 0) — TE truncates to TF32 regardless of operand dtype, so the casts only cost time (+122 µs at S=8192) and memory, with no precision gain.
- **Backward**: the existing `.to(router_dtype)` casts produce gradients **bitwise identical** to a tf32 `torch.mm` (rel 2.081e-04 vs FP64), i.e. ~680x the error of true FP32 (`torch.mm` tf32-off: 3.055e-07).

Since TE's cuBLASLt path cannot deliver FP32 compute for these GEMMs, the only way to honor the FP32 router contract is the `torch.mm` branch — which already exists in both functions; this PR extends the existing FP64 exclusion to FP32.

## Validation (memory/perf)

GB200, S=8192, H=4096, E=288:

| path | latency | peak memory |
|---|---|---|
| bwd, current TE (tf32-grade) | 407 µs | 340 MB |
| bwd, this PR (true FP32) | 837 µs | **206 MB** |
| fwd, current TE (bf16 ops) | 47 µs | — |
| fwd, this PR (true FP32) | 493 µs | — |

Full fix cost ≈ +880 µs per routed layer ≈ ~8% of the MoE block's expert GEMM time (top-8, S=8192), and **saves 134 MB of peak memory** (TE workspace). FP16/BF16/FP8 routers keep the TE path unchanged.

Note: `tests/unit_tests/transformer/moe/test_moe_layer_discrepancy.py` already uses `moe_router_dtype="fp64"` for discrepancy testing, consistent with FP32-via-TE being non-reproducible today.

## Regression test

`tests/unit_tests/transformer/moe/test_routers.py::test_router_gating_linear_fp32_contract` asserts true-FP32 numerics for the fp32 router path against FP64 references with TF32 disabled: forward rel < 1e-6 (measured 0.0 through `torch.mm`; 4.4e-6 on the TE path), `grad_input`/`grad_weight` rel < 1e-5 (measured 3.1e-7 / 8.1e-7; ~2.1e-4 on the TE path). On hosts without TE the two branches coincide (`torch.mm`), so the test is green either way there.

## Additional observation

The backward call form in current main (`te_general_gemm(weight, ..., layout="NN", grad=True)`) raises a cublasLt dimension assertion on TE 2.16.0 — the raw API expects the matrices transposed (`weight.t()`). With this PR the FP32 path no longer calls that API at all; flagging in case other TE versions behave differently.
