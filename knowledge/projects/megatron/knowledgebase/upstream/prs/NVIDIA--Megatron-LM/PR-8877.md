# [Inference][MoE][MXFP8] Check each expert-TP rank's FFN shard for FlashInfer CUTLASS MXFP8 alignment

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8877) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Rejects, when the config is built, FlashInfer CUTLASS MXFP8 configurations whose per-rank expert FFN shard is not 128-aligned. Before this change they were accepted and failed at the first forward.

**Bug.** The FlashInfer CUTLASS MXFP8 path (ClampedRelu2 experts, added by #8013) packs each rank's expert weights, `[E, F/ETP, H]` for FC1 and `[E, H, F/ETP]` for FC2. `prepare_cutlass_mxfp8_weights` requires rows and columns divisible by 128 (`_pack_cutlass_mxfp8_scale`). `TransformerConfig` checked `moe_ffn_hidden_size % 128` on the global FFN size. Expert TP defaults to TP and is accepted with the NVLS dispatcher, so for example TP 2 with `moe_ffn_hidden_size = 1920` passed validation, and then the 960-wide shards raised `requires weight rows and columns divisible by 128; got shape=(960, 256)` when the first forward built the weights. The routed (unclamped) MXFP8 path pads its shards to 128 and is unaffected.

## Fix

The check now validates the per-rank shard: the FFN must be divisible by `128 * expert_tensor_parallel_size`. It lives in one method, `TransformerConfig.validate_flashinfer_cutlass_mxfp8_expert_shapes()`, which runs twice:

- in `TransformerConfig.__post_init__`, so a misconfigured model is rejected when its config is built;
- in `InferenceGroupedMLP.__init__`, before the expert weights are allocated. RL builds its inference model from a deep copy of the training config and overrides `expert_tensor_parallel_size` after validation (`megatron/rl/training_setup.py`, and per shard in `megatron/rl/inference/disagg.py`). The experts check the layout they are built with, so these configs are rejected when the model is built instead of at the first forward.

The message names the split and both FFN fields, e.g. `FlashInfer CUTLASS MXFP8 requires expert hidden and per-rank FFN dimensions divisible by 128; got hidden 256 and FFN 1920 split over 2 expert tensor-parallel ranks (the FFN is moe_ffn_hidden_size, or ffn_hidden_size when that is unset).`

Not done: zero-padding each rank's FFN shard to 128, which ClampedRelu2 would keep exact. The CUTLASS path deliberately views the canonical MXFP8 expert weights and their swizzled scales in place, so in-place refits reach the kernels without a copy. Padding would need a padded copy of every expert stack (as the routed path makes for its layout change) or padded expert parameters; that is a separate design change.

## Tests

In `tests/unit_tests/inference/test_flashinfer_mxfp8.py` (CPU, no kernel launches):

- `test_flashinfer_cutlass_mxfp8_rejects_unaligned_expert_tp_shards`: three configs whose FFN is 128-aligned but whose expert-TP shards are not are rejected with the message: TP 2 with the default ETP and FFN 1920; ETP 2 and FFN 1920; ETP 4 and FFN 384. All three were accepted on `main`.
- `test_flashinfer_cutlass_mxfp8_accepts_aligned_expert_tp_shards[1|2]`: aligned shards are accepted, and the production `prepare_cutlass_mxfp8_weights` packs each rank's FC1 and FC2 shard.
- `test_flashinfer_cutlass_mxfp8_experts_reject_a_resharded_config`: a validated ETP 1 config with FFN 1920, deep-copied with ETP set to 2 as RL does, is rejected when `InferenceGroupedMLP` is built.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02, with Transformer Engine), the regression tests pass (6 cases) and fail on `main` (4 of 6 cases). On `main` the three unaligned configs are accepted, and the resharded-config test fails only on an unrelated `AttributeError` (`'InferenceGroupedMLP' object has no attribute 'config'`), not on the alignment check, so it does not show the resharded case on `main`. The step 3 GPU repro of this finding (R03-F4) showed the bug on `main` on H100: `TransformerConfig` accepted FFN 1920 with TP 2 (ETP 2), whose expert-TP shards are 960 wide. The two aligned cases pass there. The whole of `test_flashinfer_mxfp8.py`, including the existing `dimensions divisible by 128` cases, passes (52 cases; 4 routed-MXFP8 cases skip, as they need Blackwell).

The determinism-coverage check flags `experts.py` (kernel `moe_experts`). The change there is a construction-time shape check that cannot affect numerics, so this PR needs the `determinism-exempt` label.
