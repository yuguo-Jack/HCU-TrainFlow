# [Inference][MXFP8] Clamp the device row count in mxfp8_quantize_rows to the buffer height

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8564) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Bounds `mxfp8_quantize_rows` by the height of its input, so a device-side row count larger than the buffer no longer reads past `x` or writes past the outputs.

## Issue tracking

Linked issue: none; this PR's regression tests reproduce the bug.

**Bug.** `_mxfp8_quant_swizzle_rows_kernel` loops `for row in tl.range(pid, n_rows, NUM_PROGRAMS)`, with `n_rows` loaded on device and nothing bounding it by the height `M` of `x`. With `n_rows > M` the kernel:
- reads rows `[M, n_rows)` past `x`;
- writes FP8 rows past `out_data` (`torch.empty(M, K)`);
- writes scale bytes into the padding rows of `out_scale`'s last 128-row tile, and past `out_scale` once `n_rows > ceil(M / 128) * 128`.

On H100 the repro saw nonzero scales computed from memory past `x`. Under `PYTORCH_NO_CUDA_MEMORY_CACHING=1 compute-sanitizer --tool memcheck`, it reported out-of-bounds writes in the kernel.

**Who is affected.** The only caller is `_quantize_mxfp8_used_rows` in `moe/fused_moe.py`. It runs in batch-invariant mode with MXFP8 experts and passes `n_used = inclusive_expert_offsets[-1]`. Today that count stays within the permuted buffer by construction. It can exceed the buffer when the expert offsets are built from an inflated valid-token count, such as the stale MTP count filed separately. So this bug is latent on its own, but it is one more out-of-bounds writer when that happens.

**Root cause.** The kernel receives a device count but not the buffer height. The wrapper cannot check the count on the host without a device-to-host sync, because the count is a device scalar captured in CUDA graphs.

**Fix.**
- Pass `M` to the kernel as a runtime argument and loop to `min(n_rows, M)`.
- The clamp runs on device, so the launch stays CUDA-graph safe: no host sync, no new allocation, no recompilation per count.
- Rows at or past the clamped count keep the existing contract (data uninitialized, scales zero). A count above `M` therefore returns exactly `mxfp8_quantize(x)`.
- A host-side error would need a sync, and a device assert would kill the CUDA context, so the clamp is the right contract here.
- This does not fix the upstream stale count. It makes this kernel memory-safe for any count.
- `mxfp8_quantize_rows` now also asserts that `x` is contiguous, because the kernel addresses row `r` at `r * K`. No current caller passes a strided view; before this check, one would have been quantized from the wrong elements without any error.

**Test.** All new tests are in `TestMxfp8QuantizeRows` in `tests/unit_tests/inference/test_batch_invariant_live_rows.py`.
- `test_count_clamped_to_height`:
  - `x` is the head of a larger buffer of ones, and the count ends inside the last scale tile (`M` = 120 or 124, `n` = 128).
  - An unbounded kernel therefore reads the ones and writes their nonzero scales into the tile padding, where the test sees them. The overrun stays inside allocations: at most 256 B past `out_data`, which fits the caching allocator's 512 B rounding.
  - The expected output is `mxfp8_quantize(x[:min(n, M)])`, whose swizzled scales are a prefix of the full buffer's, followed by zeros.
  - The `n <= M` cases are controls that pass on main. The two `n > M` cases fail on main and pass with the fix.
- `test_count_past_last_scale_tile_stays_in_bounds` covers a count past the last scale tile (`M` = 120, `n` = 256).
  - Through the wrapper, that overrun cannot be contained: the scale buffer is a whole number of 512 B tiles, so the allocator leaves no slack behind it.
  - The test therefore launches the kernel as the wrapper does, but into the heads of larger canary-filled data and scale buffers. It checks that the canaries are untouched and that the output equals `mxfp8_quantize(x)`.
- `test_rejects_non_contiguous_input` checks the new contiguity assert.
- Determinism: `test_mxfp8_quantize_rows_replays` also replays a count past the buffer height and checks it bit-exact against `mxfp8_quantize(x)`.
  - Height 16382, `K` 128, count 16384, so the count ends inside the last scale tile and the input sits on a buffer of ones.
  - If the clamp regressed, this case would fail the padding comparison and stay inside its allocations (256 B past `out_data`, within the 512 B rounding).
  - The kernel's manifest entry (`inference_moe_kernels`) already covers this file and test, so `manifest.py` is unchanged.
- `tools/check_kernel_determinism_coverage.py --base-ref origin/main` passes.

**Results.** On H100 in the CI image (`mcore_ci_dev:main`), for the first commit of this PR:
- `TestMxfp8QuantizeRows` passes with this PR (18/18). On main, the two `n > M` cases of `test_count_clamped_to_height` fail and the other 16 pass.
- `PYTORCH_NO_CUDA_MEMORY_CACHING=1 compute-sanitizer --tool memcheck` reports 0 errors. Its one failing case, `test_cuda_graph_replay_with_changing_count`, fails because CUDA graph capture cannot allocate with caching disabled; that failure is not related to this change.
- Neighbor tests pass: `test_batch_invariant_live_rows.py` (21), `test_mxfp8_quantize_rows_replays` (1) and `test_mxfp8_utils.py::TestMxfp8Quantize` (47).
On H100 in the CI image (rerun at this PR's head), the regression tests pass (21/21), compute-sanitizer reports 0 errors, and 5 tests fail on `main`. The neighbor tests pass.
