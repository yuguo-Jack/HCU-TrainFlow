# Add a reproducible MoE token-imbalance benchmark with an all-to-all baseline

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7488) · state: open · merged: False

## Original PR description

**Incremental review:** [Files changed](https://github.com/NVIDIA/Megatron-LM/pull/7488/files) against `main`. The second commit implements the workload semantics discussed with @VVsssssk in the comments.

First slice of the "public runtime token-imbalance benchmark" work item from #6757. It
does not implement ECHO / MoonEP / UltraEP or a runtime-aware scheduler.

## What is added

`benchmarks/moe/token_imbalance/`, plus its CPU unit tests.

**Rank-level load.** For dropless MoE with EP, the busiest EP rank sets the step time, so
every arm records the destination load of each EP rank at every step. The load counts
token-expert assignments after top-k expansion. From that vector the benchmark reports:

- `maxvio`: the max/mean of the rank loads.
- Concentration: `1 - H(p)/log R`.
- Hot-rank persistence across steps.

Per-expert statistics are kept alongside.

**Two experiments, reported separately.**

| Experiment | Workloads | What is held fixed |
|---|---|---|
| `trace_replay` | W0, W1, W3, W4, W5, W6, W7 | one logical trace (global expert ids), replayed at any layout; rank loads are reported, not controlled |
| `rank_target` | R0, R1, R2 | the per-rank load vector, constructed for the given layout and checked exactly |

- R1 and R2 have the same busiest-rank load, and therefore an identical `maxvio`. R1 spreads the remainder evenly over the other ranks; R2 packs it onto as few ranks as possible. They differ only in concentration.
- `--schedule static|rotate|random` changes which rank carries each load slot, without changing the per-step load multiset.
- W3 is W1 with its expert ids relabeled, so it isolates placement at identical per-expert heat.

**Three modes.**

| Mode | What runs |
|---|---|
| `dispatch_only` | the dispatcher round trip |
| `moe_fwd_bwd` | the real `MoELayer` forward and backward, with the router's top-k replaced by the workload through `RouterReplay` |
| `training_step` | the above plus an optimizer update |

**An exact oracle.** These checks run at every step:

- distinct top-k per row;
- assignment and histogram reconciliation;
- an exact dispatch -> identity -> combine round trip, with a measured combine factor;
- receive-split reconciliation;
- for `rank_target` workloads, realized rank loads equal the target;
- for the model modes, the routing map the layer used equals the workload.

**trace v1** persists every step of a workload with per-tensor sha256 and strict validation on load.

## Changes in the second commit

- Rank-level metrics and the `rank_target` family, as above.
- `moe_fwd_bwd` previously ran the dispatch-only loop. Both model modes now run the real layer with the workload routing.
- `training_step` previously used the router's own routing.
- W2 was the same construction as W1. It is retired.
- W3 changed the hot-set size as well as its placement. It is now a relabeling of W1.
- W4 did not vary the source token count. It is renamed `W4_random_balanced`.
- The old "rank max/mean" was derived from per-source receive splits and is replaced by the destination rank load.
- Per-step workloads refuse a `--steps` too small to exercise them, and each step is timed on its own.

The first revision's results table is withdrawn. Its `moe_fwd_bwd` and `training_step` rows did not measure what they claimed, and its W2/W4 columns were mislabeled.

## Validation

- CPU: 258 unit tests, rerun after rebasing onto `main@fce1e2051`. They include exact realization of every R workload under every schedule at EP 1/2/4/8, `topk` 1/2/4 and 8/16/32 experts, and the W1/W3 heat-preservation property.
- GPU, one GH200: all 10 workloads in `dispatch_only` with `--steps 6` passed the oracles. This early run overlapped another workload, so its timings are discarded.
- GPU, one GH200: `moe_fwd_bwd` and `training_step`, all 10 workloads each, six logical steps; 20 configurations passed every oracle.
- GPU, 2×H100 SXM 80 GB with NV18: all three modes × 10 workloads, six logical steps, plus three rotating R workloads (four steps): 33 configurations / 66 rank records passed every boolean oracle. Each run used one warmup and three measured iterations; these are correctness runs, not a performance comparison. Runtime: NGC PyTorch 26.09, torch 2.14.0a0+b2c75dd062.nv26.09, CUDA 13.4, TE 2.19.0+5e52befd, Triton 3.8.0.

Timings are not reported yet. They will be added once the workload semantics are agreed, from an idle node with repeated independent runs.

## Scope and known limitations

- Every source rank sends the same block of rows, so source-side (pre-dispatch) skew is not modeled.
- Only the standard all-to-all backend exists. Adapters wait until the semantics are agreed.
- The grouped-GEMM expert path is not exercised: experts are a per-expert loop in every mode.
- Results across EP widths are weak-scaling comparisons, because per-rank tokens are fixed.
- Based on `main`. The roadmap places this item on `dev`, and which branch to target is an open question in the comments.

GPU source binding: the runs used benchmark revision `e3648e5407eeaf9089b8e1ef835b31380acbb2f3` on core `13a9d46d9`. The submitted revision retains the tested benchmark logic after rebase and repository formatting (the non-import syntax trees are unchanged); intervening upstream commits do not change the exercised MoE code. GH200 used torch 2.14.1+cu130 and TE 2.20.2+44f31bbe, so hardware timings are not pooled.

Review questions: are the rank-target and temporal definitions appropriate, and should this roadmap contribution ultimately target `dev`? A separate draft follow-up is being validated against the existing HybridEP / VirtualExpertLoadBalancer interface merged in #7450. It does not assume a future MoEScheduler API or maintainer acceptance of the backend choice.

Black/isort formatting and the 258 CPU tests pass after formatting. The repository autoformat script does not include `benchmarks/`; an additional pylint run reports existing CLI `print` usage, missing docstrings and unused imports, which are retained in the local audit rather than described as a full lint pass.

- VVsssssk · comment · 2026-09-23T04:25:53Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/7488#issuecomment-5789036530)

Thanks for contributing this and for posting an initial version so we can discuss the workload definitions before extending the benchmark. Establishing a reproducible baseline for token imbalance is valuable.

I’d like to discuss whether we should define imbalance scenarios primarily at the EP-rank level, while retaining per-expert statistics. For dropless MoE with EP, uneven expert routing translates into uneven work across ranks, and overloaded ranks become stragglers. Expert-level imbalance alone does not capture this: multiple hot experts placed on the same rank can have a different impact from those spread across ranks.

I think we could organize the workloads around three dimensions, aiming to vary one at a time while controlling the others where feasible:

1. Intra-batch rank load skew (maxvio): How overloaded is the busiest rank? We could start with max(rank_token_assignments) / mean(rank_token_assignments), counting token–expert assignments after top-k expansion. To make the convention explicit, this ratio is 1 for a balanced workload; subtracting 1 would express the relative overload.

2. Intra-batch rank load concentration: How broadly is the excess load distributed? At a fixed total assignment count and a comparable maximum rank load, is the remaining load concentrated on a few ranks or spread across many? Recording the full destination-rank load vector would distinguish distributions with the same max/mean. Entropy over the normalized rank loads could summarize this: lower entropy indicates greater concentration. Alternatively, 1 - H(p)/log(R) gives a concentration measure that increases as the distribution becomes more concentrated, where R is the number of EP ranks.

3. Inter-batch hotspot persistence (consistency): How stable are the hot ranks over time? Does the same rank remain hot for N iterations, does the hotspot rotate periodically, or does it change unpredictably? Ideally, we would preserve the per-batch load distribution and change only which ranks carry those loads, separating temporal behavior from imbalance severity.

With that framing, I have a few questions about the current W0–W7 definitions:

- W1 vs. W2: My understanding is that this comparison is intended to examine concentration. Is concentrating hot experts on one rank sufficient to capture that dimension? For example, rank-load vectors [40, 20, 20, 20, 0] and [40, 15, 15, 15, 15] have the same total load and max/mean, but different concentration. Could we explicitly construct cases like these?

- W2 vs. W3: W3 appears to change the hot-set cardinality as well as its placement. This could change both maxvio and concentration. Could we specify which dimension this comparison is intended to isolate and hold the other properties fixed?

- W4: Could you clarify which variable this workload is intended to isolate, and how it relates to the dimensions above?
- W6/W7: Could we explicitly specify and exercise the temporal sequence? With the default --steps=1, repeated timing iterations replay step 0, so they do not exercise hotspot rotation or burst/recovery behavior.

There is also a definition question around layout independence: keeping a logical routing trace fixed across EP layouts is useful, but it does not preserve the same rank-level imbalance. Could we distinguish the following two experiments and report the resulting rank loads in both cases?

- Replaying a fixed logical trace across different layouts.
- Constructing a target rank-load distribution for a given layout.

I’d suggest agreeing on these workload semantics and adding tests to verify that they produce the intended load distributions before adding more backend adapters.

- 0z5a · comment · 2026-10-26T13:58:32Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/7488#issuecomment-6417840466)

Thanks @VVsssssk, this framing is right, and working through it turned up problems in the first revision that go beyond the workload definitions. I have pushed a revision, rebased onto current `main`, that reorganizes the benchmark around the three dimensions you listed and fixes those problems. Summary below. The README has the full definitions.

**Rank-level load is now the primary measurement.** Every arm records, at every step, the destination load of each EP rank. The load counts token-expert assignments after top-k expansion, with Megatron's contiguous expert placement. From that vector it reports:

- `maxvio = max/mean`, so a balanced load is exactly 1.
- concentration `1 - H(p)/log R`.
- hot-rank persistence across steps.

Per-expert statistics are kept alongside. Your example pair gives maxvio 2.0 for both, with concentration 0.172 for `[40, 20, 20, 20, 0]` and 0.065 for `[40, 15, 15, 15, 15]`.

**The two experiments are now separate and reported in separate tables.**

- `trace_replay` (W\*) replays one logical trace at any layout. The resulting rank loads are reported, not controlled.
- `rank_target` (R\*) constructs routing for the given layout so that each rank receives a chosen load exactly. Each rank's load is spread evenly over its local experts, so only the rank-level shape varies. The realized vector is a hard oracle check.
  - `R1_hot_rank_spread` and `R2_hot_rank_concentrated` share the busiest rank's integer load, so their maxvio is identical rather than approximately equal. They differ only in concentration: your two vectors are exactly R1 and R2 at EP=5.
  - At EP=4 with 256 assignments per source rank, R1 is `[128, 43, 43, 42]` (concentration 0.104) and R2 is `[128, 64, 64, 0]` (0.250).
  - The two coincide at EP=2, where the hot rank's share fixes the other rank.
  - `--hot-maxvio` sets the severity.

**Temporal persistence.** `--schedule static|rotate|random` changes only which rank carries each load slot. The per-step load multiset, and therefore maxvio and concentration, stays the same at every step, which separates the temporal behavior from the severity of the imbalance. Per-step workloads and non-static schedules now refuse a `--steps` value too small to exercise them, instead of replaying step 0. Every step is also timed on its own.

**Your W1/W2/W3/W4 questions**, answered by what the code actually did:

- **W1 vs W2:** the two were the same construction, differing only in the random stream. That was my mistake. W2 is retired, and hot-rank cases now live in the R family, where they can be constructed for a layout.
- **W2 vs W3:** you were right that W3 also changed the hot-set size (E/2 against E/4). W3 is now W1 with its expert ids relabeled so the hot block is strided across the range. Per-expert counts are W1's exactly, as a multiset, and only placement differs. At EP=2 this turns W1's `[225, 31]` into `[128, 128]`.
- **W4:** it did not vary the source token count. In fact every source rank sends the same block of rows, so source-side skew is not modeled at all. It is now `W4_random_balanced`, a random control around balance against W0's exact round-robin. Source-side skew is listed as a limitation.

**Fixes outside the workload semantics**, which also invalidate parts of the first revision's results table:

- `moe_fwd_bwd` ran the dispatch-only loop and never called the `MoELayer`.
- `training_step` used the router's own routing, so the workload had no effect on it.
- Both model modes now run the real layer and replace the router's top-k with the workload through `RouterReplay`. They then check, at every step, that the routing map the layer actually used equals the workload.
- The "rank max/mean" column was computed from one destination's per-source receive splits. Those are equal whenever every source sends the same routing, which is why it read 1.000 throughout. It is replaced by the destination rank load.

I have removed the old table from the README and the PR description rather than leave numbers that do not mean what they claim.

**Validation:**

- 258 CPU tests. They include exact rank-load realization for every R workload and schedule at EP 1/2/4/8, `topk` 1/2/4 and several expert counts, plus the W1/W3 heat-preservation property.
- GPU, one GH200: all 10 workloads in each of the three modes, six steps. Every oracle check passed, including `rank_target_exact` and, in the model modes, `replayed_routing_exact`.
- GPU, 2×H100 at EP=2: all three modes × 10 workloads (six steps), plus the three R workloads under a rotating schedule. 33 configurations / 66 rank records passed every oracle check.

These are correctness runs (one warmup, three measured iterations), not a timing comparison. Timings will follow once the semantics are settled.

Two questions before I build anything on top of this:

1. Do these definitions match what you had in mind? In particular, is R2's construction the concentration case you meant? R2 puts the remainder at the mean on as few ranks as possible, which yields your `[40, 20, 20, 20, 0]`.
2. The roadmap places this item on `dev`, which I can now reach. Should this PR target `dev` instead of `main`?

One thing I should flag against your suggestion to settle the semantics first: I have also opened #8388, which runs the HybridEP virtual-expert path from #7450 on these workloads. It is built on the definitions in this PR, so it will follow whatever we agree here. I will not extend it until this thread is settled.
