# Add a reproducible MoE token-imbalance benchmark with an all-to-all baseline

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7488) · state: open · merged: False

## Original PR description

**Incremental review:** [Files changed](https://github.com/NVIDIA/Megatron-LM/pull/7488/files) against `main`.

First slice of the "public runtime token-imbalance benchmark" work item from #6757. It does
not implement ECHO / MoonEP / UltraEP or a runtime-aware scheduler.

## What is added

`benchmarks/moe/token_imbalance/`, plus its unit tests.

**Workloads W0-W7**, derived from `(workload, seed, step)` only, so the same logical workload
is reproduced regardless of execution method or EP/ETP layout. Every row carries exactly
`topk` distinct experts. Each workload isolates a different variable:

| ID | isolates |
|---|---|
| W0_balanced | fully balanced control |
| W1_hot_expert_set | per-expert heat |
| W2_hot_rank | per-rank placement, at comparable heat to W1 |
| W3_spread_hot_experts | the same heat spread across the layout instead of contiguous |
| W4_source_ragged | pre-dispatch skew |
| W5_zero_expert_rank | zero-load experts and ranks |
| W6_rotating_hotspot | step-to-step plan staleness |
| W7_burst | hiding a re-plan in steady-state numbers |

**Three modes**, each documented with what it may be used to claim: `dispatch_only`,
`moe_fwd_bwd` (real `MoELayer` forward and backward, router included) and `training_step`
(plus a real optimizer update).

**An exact oracle**, not a tolerance check, because the values under test are counts and row
identities: `topk` distinct experts per valid row, assignments reconciling with
`tokens * topk * world`, an exact dispatch -> identity expert -> combine round trip, and a
combine scaling factor that is **measured first and asserted to equal `topk`** so that a change
in the dispatcher contract fails the run instead of silently rescaling the comparison.
`training_step` additionally requires a finite loss and non-zero gradients.

**trace v1** persists a workload with per-tensor sha256, validating schema, dtype, shape,
checksum, expert-id range, top-k distinctness and gate finiteness/sum on load, using
`weights_only=True` so no arbitrary object is reconstructed. A validation failure raises rather
than truncating, reordering or padding.

count, which makes the total token count grow with EP (weak scaling). Read a row, not a column.

Imbalance is configuration dependent, so two measured points are recorded in the README rather
than one being presented as "the" number. At EP=4, 128 tokens/rank, topk 2:
W0 1.000, W1 3.312, W2 3.219, W3 1.281, W4 1.281, W5 2.156, W6 3.312, W7 1.219
(expert max/mean).

Correctness: **72 of 72 arms across the nine configurations passed every oracle check**, plus
76 CPU-only unit tests covering the generator invariants and the trace format, including
11 malformed-trace rejection cases that each assert the rejection reason.

## Scope and known limitations

* **Written against `main` (`d564dd01d`), not `dev`.** The roadmap states this work item is
  based on `dev`; that branch was not reachable from the machine used. Landing it may require
  layout changes, and this should be checked before merge.
* **Router replay is not wired in.** Routing is supplied at the dispatcher level, or produced
  by the real router in `training_step`. This is a separate path from the model's
  `RouterReplay`.
* **Only the standard all-to-all backend exists.** Adding ECHO / MoonEP / UltraEP should reuse
  that method's own code and configuration rather than reimplementing it here.
* **The grouped-GEMM expert path is untested** on nodes without `transformer_engine`; on such a
  node the capability probe reports `grouped_gemm: UNSUPPORTED` and absolute step times are not
  comparable with a TE-enabled node.
* **`strong` vs `weak` scaling is not a recorded field**, only documented in the README, since
  a column-wise reading of the table above would be wrong.
* The nine-configuration matrix is a starting scan, not a full sweep: a rollout would want more
  repeated independent runs for intervals, which this change does not attempt.

- VVsssssk · comment · 2026-09-23T04:25:53Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/7488#issuecomment-5789036530)

Thanks for contributing this and for posting an initial version so we can discuss the workload definitions before extending the benchmark. Establishing a reproducible baseline for token imbalance is valuable.

I’d like to discuss whether we should define imbalance scenarios primarily at the EP-rank level, while retaining per-expert statistics. For dropless MoE with EP, uneven expert routing translates into uneven work across ranks, and overloaded ranks become stragglers. Expert-level imbalance alone does not capture this: multiple hot experts placed on the same rank can have a different impact from those spread across ranks.

I think we could organize the workloads around three dimensions, aiming to vary one at a time while controlling the others where feasible:

1. Intra-batch rank load skew (maxvio): How overloaded is the busiest rank? We could start with max(rank_token_assignments) / mean(rank_token_assignments), counting token–expert assignments after top-k expansion. To make the convention explicit, this ratio is 1 for a balanced workload; subtracting 1 would express the relative overload.

2. Intra-batch rank load concentration: How broadly is the excess load distributed? At a fixed total assignment count and a comparable maximum rank load, is the remaining load concentrated on a few ranks or spread across many? Recording the full destination-rank load vector would distinguish distributions with the same max/mean. Entropy over the normalized rank loads could summarize this: lower entropy indicates greater concentration. Alternatively, 1 - H(p)/log(R) gives a concentration measure that increases as the distribution becomes more concentrated, where R is the number of EP ranks.

3. Inter-batch hotspot persistence (consistency): How stable are the hot ranks over time? Does the same rank remain hot for N iterations, does the hotspot rotate periodically, or does it change unpredictably? Ideally, we would preserve the per-batch load distribution and change only which ranks carry those loads, separating temporal behavior from imbalance severity.

With that framing, I have a few questions about the current W0–W7 definitions:

- W1 vs. W2: My understanding is that this comparison is intended to examine concentration. Is concentrating hot experts on one rank sufficient to capture that dimension? For example, rank-load vectors [40, 20, 20, 20, 0] and [40, 15, 15, 15, 15] have the same total load and max/mean, but different concentration. Could we explicitly construct cases like these?

- W2 vs. W3: W3 appears to change the hot-set cardinality as well as its placement. This could change both maxvio and concentration. Could we specify which dimension this comparison is intended to isolate and hold the other properties fixed?

- W4: Could you clarify which variable this workload is intended to isolate, and how it relates to the dimensions above?
- W6/W7: Could we explicitly specify and exercise the temporal sequence? With the default --steps=1, repeated timing iterations replay step 0, so they do not exercise hotspot rotation or burst/recovery behavior.

There is also a definition question around layout independence: keeping a logical routing trace fixed across EP layouts is useful, but it does not preserve the same rank-level imbalance. Could we distinguish the following two experiments and report the resulting rank loads in both cases?

- Replaying a fixed logical trace across different layouts.
- Constructing a target rank-load distribution for a given layout.

I’d suggest agreeing on these workload semantics and adding tests to verify that they produce the intended load distributions before adding more backend adapters.
