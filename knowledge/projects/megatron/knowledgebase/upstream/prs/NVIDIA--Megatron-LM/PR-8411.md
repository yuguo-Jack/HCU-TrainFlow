# fix(training): use scheduled batch sizes for iteration LR horizons

# What does this PR do?

Fix LR warmup, cosine/WSD decay and weight decay horizons when `--train-iters` is combined with `--step-batch-size-schedule`. In a 100-iteration CPU reproduction with batches of 8 then 16, main finishes warmup at iteration 2 and decay at iteration 13; the configured boundaries are 10 and 100. This PR reaches the configured boundaries.

## Issue tracking

The regression follows the removal of the iteration-mode batch-ramp guard in #4411. The same PR changed the shipped GPT-3 175B example to specify both a schedule and `--global-batch-size`, which argument validation rejects. No separate issue has been filed.

## Changes

- Convert iteration horizons into the samples consumed by the batch schedule in `PretrainConfigContainer._resolve_scheduler_step_fields`. WSD covers the final configured anneal iterations. A fractional warmup iteration uses the next iteration's batch.
- Keep the existing constant-batch and sample-based formulas.
- Remove the conflicting global batch argument from the example and explicitly retain its evaluation batch size of 1536.

Merged current main at b29123508 and resolved the conflict caused by upstream moving scheduler derivation into configuration finalization. The fix now lives in `megatron/training/config/container.py`.

## Compatibility and review questions

- Existing checkpoints using the buggy horizons require `--override-opt-param-scheduler` to adopt corrected values. `--use-checkpoint-opt-param-scheduler` retains their previous horizons.
- Warmup fractions apply to iteration counts. For the shipped example, 0.001 of 430,000 decay iterations means 430 warmup iterations.
- The independent dataset sample-budget calculation still uses `train_iters * global_batch_size`; correcting that can change dataset indices and sample order and needs a separate change.
