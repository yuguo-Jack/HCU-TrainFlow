# [dev] Use binary search for the THD row lookup in fused MLA RoPE

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7806) · state: closed · merged: True

## Original PR description

Thanks @TKONIY for the contribution to this PR!

- [x] I, the PR author, have personally reviewed every line of this PR.

## Summary

- The fused MLA RoPE kernels in `megatron/core/fusions/fused_mla_yarn_rope_apply.py` map every row of a packed THD input to its position with `_get_thd_token_idx`. Six kernels use it, all forward and backward:
  - the in-place kernels: MLA query RoPE and DSA indexer RoPE;
  - the packing kernels: absorbed-MLA query and key/value;
  - the key/value split kernels: MLA key and value.
- The helper walks over **every** packed sequence of `cu_seqlens` in **every** Triton program. The kernels therefore slow down with the number of sequences in a packed THD micro-batch, as produced by sequence packing in SFT and RL. With context parallelism the slowdown is larger.
- Example: the GLM-5 DSA indexer key on 256K local rows takes 0.14 ms as one sequence, but 8.1 ms (59x) when packed as 512-row samples.
- This PR replaces the walk with a binary search, like the one this module already uses in `_get_contiguous_thd_token_idx`. Only integer index arithmetic changes, and the outputs are **bitwise identical** (7345 checks, plus 7540 on top of #7789).
- B200, cold L2, each module at its best `BLOCK_H`:
  - packed inputs: up to **11.4x** faster with 2048-row samples, **37.7x** with 512-row samples, and **20.0x** with CP 2 and 4096-row samples;
  - one sequence: unchanged within -1.6% to +1.7%.
  - The RoPE kernels of one GLM-5 micro-batch, forward and backward, take 201 ms instead of 927 ms at 256K rows in 2048-row samples.
- The autotune configurations are not changed.
- Please merge after #7789: without its barrier, a race that already exists in the in-place backward shows up on a different set of inputs with this change (see Notes for reviewers).

## Problem

THD inputs that come with `cu_seqlens` and without `position_ids` or `thd_global_start` take this path when RoPE fusion is on:

- the MLA query and key/value RoPE with packed sequences (`fused_apply_mla_rope_for_q` / `_for_kv` in `multi_latent_attention.py`);
- the absorbed-MLA query and key/value packing (`fused_mla_rope_concat` in `absorbed_mla.py`);
- the DSA indexer query and key RoPE (`DSAIndexer._apply_rope` in `dsa.py`, fused path);
- the experimental CSA and DeepSeek-V4 hybrid attention RoPE on packed sequences (`_apply_fused_rope` in `csa.py`; `deepseek_v4_hybrid_attention.py` without CP).

Nothing fails and the results are correct; the kernels just get slower as more sequences are packed into a micro-batch. Times of the unpatched kernels (`ac100f773`, forward, best `BLOCK_H` of each cell, cold L2, 262144 local rows), against one sequence of the same size:

| GLM-5 shape | 1 sequence | 2048-row samples (128 sequences) | 512-row samples (512 sequences) | CP 2, 1 sequence | CP 2, 4096-row samples (128 sequences; vs CP 2, 1 sequence) |
|---|---|---|---|---|---|
| DSA indexer query 32 x 128 | 878 us (BLOCK_H 8) | 2.87 ms (BLOCK_H 32), 3.3x | 8.40 ms (BLOCK_H 32), 9.6x | 1.05 ms | 7.38 ms (BLOCK_H 64), 7.0x |
| DSA indexer key 1 x 128 | 136 us | 2.11 ms, 15.5x | 8.06 ms, 59x | 187 us | 6.48 ms, 35x |
| MLA query TP8 8 x (192 + 64) | 222 us | 2.19 ms, 9.8x | 8.15 ms, 37x | 260 us | 6.78 ms, 26x |
| absorbed query TP8 8 x (512 + 64) | 712 us | 2.25 ms, 3.2x | 8.22 ms, 11.6x | 710 us | 6.83 ms, 9.6x |
| absorbed key/value 1 x (512 + 64) | 149 us | 2.14 ms, 14.3x | 8.11 ms, 54x | 212 us | 6.47 ms, 30x |

With 512 packed sequences, every shape takes about 8 ms whatever its size, because the lookup, not the data, sets the time.

## Root cause

### Mechanism

The kernels launch a grid of `(rows, cdiv(heads, BLOCK_H))` programs, and each one first maps its row through `_get_thd_token_idx`:

```python
token_idx = tl.full((), -1, dtype=tl.int64)
seq_idx = 0
last_cum_seqlen = tl.load(cu_seqlens).to(tl.int64) // cp_size
while seq_idx < seq_num:
    cur_cum_seqlen = tl.load(cu_seqlens + seq_idx + 1).to(tl.int64) // cp_size
    if token_idx == -1 and cur_cum_seqlen > pid_m:
        token_idx = pid_m - last_cum_seqlen
        this_seq_len = cur_cum_seqlen - last_cum_seqlen
    last_cum_seqlen = cur_cum_seqlen
    seq_idx += 1
```

The loop has no early exit, so every program makes `seq_num` load-compare-select steps, wherever its row is. The total work is `rows x cdiv(heads, BLOCK_H) x seq_num` steps, while each program moves only a few hundred bytes. For a fixed sample length, `seq_num` grows with the number of tokens, so this work grows with the square of the micro-batch size.

### Worked example: the GLM-5 DSA indexer key

The key is `[rows, 1, 128]` with 64 rotary channels (`rope_first=True`).

- 262144 local rows packed as 512-row samples are 512 sequences.
- Each of the 262144 programs reads all 513 entries of `cu_seqlens`, to rotate 64 bf16 values (128 bytes in, 128 bytes out, plus the cos/sin rows): 134M loop steps per call.
- The forward kernel takes 8.06 ms, against 0.136 ms for one 262144-row sequence (59x), and 2.11 ms (15.5x) for 2048-row samples.
- With one head, a larger `BLOCK_H` does not reduce the number of programs, so nothing amortizes the walk. The absorbed-MLA key/value packing (1 head) behaves the same.

The multi-head kernels can spread the walk over more heads per program. Their best `BLOCK_H` therefore moves with the packing:

- For the 32-head indexer query, it is 8 for one sequence and 16 to 64 for 512-row samples.
- The larger tiles cost bandwidth, and even that best configuration is still 7-8x slower than with the search.
- The best configuration depends on the number of sequences, but the autotuner key (head and channel counts, dtypes) does not. A configuration tuned on the first micro-batch is then reused for micro-batches packed differently.

### Context parallelism

With CP, `cu_seqlens` describes the global sequences and every rank holds `1/cp_size` of each of them.

- The rows per rank shrink, but the number of sequences per rank does not, so the walk takes a larger share of the kernel.
- Triton folds an integer argument into the kernel only when it is 1. With `cp_size > 1`, every step of the walk therefore also divides a 64-bit offset by `cp_size`. The PTX of the old loop has a `div.s64` (with a 32-bit fast path) per step; with `cp_size == 1` it has none.
- With CP 2 and 4096-row samples (2048 local rows per sequence), the indexer key takes 6.48 ms on 262144 local rows, 35x its single-sequence time with CP 2.

### When it matters

| condition | effect |
|---|---|
| THD input with `cu_seqlens`, without `position_ids` / `thd_global_start`, RoPE fusion on | uses the walk |
| one sequence per micro-batch | one step per program; no measurable effect |
| many packed sequences (SFT, RL, any sequence packing) | cost proportional to the number of sequences: 3-59x at 256K rows in the table above |
| context parallelism | fewer rows per rank, same number of sequences, plus a 64-bit division per step |
| SBHD inputs, `position_ids`, `thd_global_start` (contiguous slices) | do not call the helper; compiled code unchanged |

### How it was found

We measured the `BLOCK_H` autotuning of these kernels on GLM-5 MLA and DSA shapes: cold L2, every `BLOCK_H` forced, kineto kernel times, single-sequence and packed THD layouts. The packed layouts were far slower than one sequence of the same size, and their best `BLOCK_H` grew with the number of sequences. Both trace back to the per-program walk.

## Change

`_get_thd_token_idx` now finds the row's sequence with a binary search, the upper bound that `_get_contiguous_thd_token_idx` already uses:

```python
row_end = (pid_m + 1) * cp_size
start_offset = tl.load(cu_seqlens)
end_offset = start_offset
low = tl.full((), 0, dtype=tl.int32)
high = seq_count
while low < high:
    mid = (low + high) >> 1
    offset = tl.load(cu_seqlens + mid + 1)
    go_left = row_end <= offset
    low = tl.where(go_left, low, mid + 1)
    high = tl.where(go_left, mid, high)
    start_offset = tl.where(go_left, start_offset, offset)
    end_offset = tl.where(go_left, offset, end_offset)
in_sequence = low < seq_count
seq_start = start_offset.to(tl.int64) // cp_size
seq_end = end_offset.to(tl.int64) // cp_size
token_idx = tl.where(in_sequence, pid_m - seq_start, 0)
this_seq_len = tl.where(in_sequence, seq_end - seq_start, 0)
```

- **Steps.** It takes at most `ceil(log2(seq_num + 1))` steps instead of `seq_num`: 10 instead of 512 in the example.
- **No division in the loop.** The condition `cu_seqlens[i + 1] // cp_size > row` is tested as `cu_seqlens[i + 1] >= (row + 1) * cp_size`. The two are equivalent for non-negative offsets. With CP, only the two divisions after the loop remain, as many as the old code needs for one sequence. In a single-process measurement, an earlier draft that divided inside the loop was up to 19% slower than the old code on one sequence with CP 2 (6-15% at `BLOCK_H=8` for the in-place and packing shapes).
- **No second load.** The loop carries `cu_seqlens[low]` and `cu_seqlens[high + 1]`, so the bounds of the sequence found are not loaded again. A draft that reloaded them was up to 8% slower on one sequence with CP 2, in the same kind of measurement.
- **Unchanged.** The CP position mapping after the lookup, the kernels, the wrappers and the autotune configurations stay as they are.

## Correctness

### Why the results are identical

- The old walk returns the first sequence `i` with `cu_seqlens[i + 1] // cp_size > row`, together with `row - cu_seqlens[i] // cp_size` and `cu_seqlens[i + 1] // cp_size - cu_seqlens[i] // cp_size`.
- `cu_seqlens` is a non-decreasing prefix sum, and so is `cu_seqlens // cp_size`. The condition is therefore monotone in `i`, and the binary search returns the same `i`.
- For `c >= 0` and `k >= 1`, `c // k > r` holds exactly when `c >= (r + 1) * k`.
- Invariants of the loop: `start_offset == cu_seqlens[low]`, and `end_offset == cu_seqlens[high + 1]` once `high < seq_num`. When the loop ends with `low < seq_num`, they are the bounds of sequence `low`.
- A zero-length sequence `i` (`cu_seqlens[i + 1] == cu_seqlens[i]`) is never the first match in either version. If it matched, sequence `i - 1` would match too, and for `i == 0` the row would be below `cu_seqlens[0] == 0`.
- Rows past `cu_seqlens[-1] // cp_size` (CUDA-graph padding) match no sequence. Both versions give them position 0 and length 0.
- Only integer index arithmetic changes. Every floating-point instruction sees the same `token_idx` as before.

## Performance

### Method

- B200, Triton 3.6.0, torch 2.11.0+cu130, SM clock 1927-1965 MHz.
- Six processes. Each loads the old module (`ac100f773`) and the new module and runs them interleaved, ABBA in odd and BAAB in even processes. Each process is split into three GPU jobs (in-place, packing, key/value split); no other work ran on the GPU.
- Before every timed call, a 1 GiB buffer is written, which evicts the 126 MB L2. Kernel durations come from kineto CUDA activity records.
- Every `BLOCK_H` the autotuners offer (1-128) is forced, 20 calls per module per process: 120 samples per cell and module. Old cells slower than 75 ms per call (`BLOCK_H` far from the best) use 6-18 calls per process; every best configuration has 120 samples.
- Each module is compared at its own best `BLOCK_H`, the median over all samples; ranges are over the six processes.
- Shapes:
  - GLM-5: DSA indexer query 32 x 128 and key 1 x 128 (rope first); MLA query 64 x (192 + 64) at TP 1 and 8 x (192 + 64) at TP 8; absorbed-MLA query 64 x (512 + 64) and 8 x (512 + 64), and key/value 1 x (512 + 64).
  - MLA key/value split: DeepSeek-V3 dimensions, 128 x (128 + 128) and 16 x (128 + 128). GLM-5's split (192 + 256) does not compile on `dev` because the kernel needs powers of two; #7803 fixes that.
  - Layouts: one sequence, 2048-row samples and 512-row samples (CP 1); CP 2 rank 0 with one sequence and with 4096-row samples (2048 local rows each).
  - Local rows: 16K, 64K and 256K. Inputs of `2**31` or more elements are skipped, since `ac100f773` computes row offsets in 32 bits (#7787).

## Risk and compatibility

- **Same sequence chosen.** The old loop picks the first `i` where `cu_seqlens[i+1] // cp_size > pid_m`. The new loop tests `cu_seqlens[i+1] >= (pid_m+1)*cp_size`. For non-negative offsets and `cp_size >= 1` the two conditions are the same, and the condition only flips one way as `i` grows. So a binary search for the first match returns the same `i`. Zero-length sequences are skipped as before.

Once `high < seq_num`, it also keeps `end_offset == cu_seqlens[high+1]`, because `high` only ever moves through the `go_left` branch. When the loop ends with `low < seq_count`, these are exactly the bounds of the matched sequence.
- **Padding rows unchanged.** Rows past the last offset get `low == seq_count`, which gives `token_idx = 0` and `this_seq_len = 0`. The CP branch then still produces 0, as the old `-1 → 0` clamp did.
- **Types.**
  - Values carried through the loop keep one type each: `low`/`high` are int32, and the two offsets keep the dtype they were loaded with.
  - `row_end` is int64, so the compare is done in 64 bits.
