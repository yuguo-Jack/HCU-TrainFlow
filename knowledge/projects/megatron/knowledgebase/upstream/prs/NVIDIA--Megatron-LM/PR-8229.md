# What does this PR do?

Prevent background data-loader pinning from invalidating optimizer CUDA graph capture by setting `capture_error_mode="thread_local"`, matching `FullCudaGraphWrapper`.

During the first optimizer capture (step 4 with three warmup steps), a DataLoader pinning thread can need a fresh `cudaHostAlloc` for a future batch. The optimizer wrapper currently inherits PyTorch's `global` capture mode. In the controlled reproduction, the background allocation returns `cudaErrorStreamCaptureUnsupported` (900), invalidates capture, and causes the training thread to fail with an invalidated-capture allocator assertion or error 901.

`thread_local` is appropriate because the background allocation is pinned **CPU** memory for future input; the optimizer graph does not reference it or depend on its allocation being replayed. The optimizer operates on existing GPU parameters, gradients, and optimizer state. This change keeps the capture restrictions on the capturing thread while allowing independent background allocations. It does not add synchronization or make shared-memory races safe. See the [CUDA capture-mode semantics](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__STREAM.html#group__CUDART__STREAM_1g9d0535d93a214cbf126835257b16ba85).

Re-enable `hybrid_llama3_proxy_mfsdp_v2_cuda_graph` in both the internal `mr` and GitHub `mr-github` scopes, removing the quarantine associated with #8218. The existing functional test covers full-iteration and optimizer graph capture with MFSDP v2.
