# [Test][Inference] Independent oracles for the FlashInfer sampling and RoPE call sites

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8971) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Adds independent oracle tests for the seven FlashInfer kernels Megatron calls for sampling and fused RoPE in dynamic inference:
- the four samplers behind `FlashInferSampling.sample_kernel`: `sampling_from_logits`, `top_p_sampling_from_probs`, `top_k_sampling_from_probs` and `top_k_top_p_sampling_from_logits`;
- the two renormalizations behind `FlashInferSampling.log_probs_kernel` (processed log-probs): `top_k_renorm_probs` and `top_p_renorm_probs`;
- `rope.apply_rope_with_cos_sin_cache` behind `DynamicInferenceContext.apply_fused_qk_rotary_emb`.

The tests are under `tests/unit_tests/inference/oracles/flashinfer_sampling_rope/`, one module per kernel, with a shared `sampling_oracle.py`. No production code changes.

**Stacked on the oracle harness PR #8966 (`test/inference-oracle-harness`)**, which adds the shared helpers. Retarget to `main` once it merges.

## Why

These call sites had almost no independent checks:
- No test compared any FlashInfer sampler's draws with a distribution. `top_p_sampling_from_probs` never ran at all: its only test mocked FlashInfer.
- `top_p_renorm_probs` only ever ran with `p = 1`, a no-op. The renormalized values of `top_k_renorm_probs` were never checked, only the count of finite log-probs.
- Fused RoPE was compared with Megatron's own RoPE only at head dims 16 and 64. The functional goldens were generated on the fused path itself.

## The oracles

Each module docstring holds the contract. It was written from the call site, the sampling and RoPE definitions and FlashInfer's documented API, before the kernels were read.

**Samplers: statistical tests against an fp64 distribution.**
- The reference distribution (`sampling_oracle.reference_distribution`) works in fp64 on exact copies of the inputs:
  - temperature `max(T, 1e-6)`;
  - top-k keeps every token tied with the k-th value; `k <= 0` and `k >= V` keep every token;
  - top-p applies to the top-k-renormalized distribution. It keeps the smallest set whose mass reaches p, with every token tied at the cut, so a cut exactly on a cumulative boundary drops the next token;
  - greedy rows (`top_k == 1`) take the lowest-index argmax.
- An input whose cut lies within fp32 rounding is rejected as a test-design error. Exact-boundary cases use dyadic probabilities, whose sums are exact.
- The tests call Megatron's `sample_kernel` with a stand-in context that carries the real filter flags. A spy checks that each launch reached the kernel under test.
- Each row is replicated across the batch and over repeated launches. The counts get a chi-square test per row group (false-failure rate 1e-6 per assertion, Bonferroni over groups, fixed seed). Any draw outside the reference support fails exactly.

**Renormalizations and processed log-probs: bounded against fp64, in two parts.** FlashInfer multiplies each row by the reciprocal (`rcp.approx` in the ternary and radix kernels) of an fp32 sum that each thread accumulates in sequence. Its rows therefore carry a common relative scale error of a few ulp that torch's pairwise sum does not.
- The kept set must be exact: zero (`-inf` after the log) exactly off the reference support.
- **Scale.** The row's mass must be 1 within the fp32 summation bound of FlashInfer's reduction tree: depth `ceil(V/1024) + 13 + CTAs`, plus `3u` for the reciprocal and the products (Higham, ch. 4). That is 1.6e-5 at V = 262144.
- **Values after the scale.** They must be within the harness bound: 2× the error of plain torch fp32 on the same GPU running the same pipeline (softmax, mask the reference's kept set, renormalize, log), normalized the same way, plus one ulp, per row.

**RoPE: fp64 rotation.**
- The rotary span is compared with the fp64 rotation of the exact inputs (the fp32 cache values as given), bounded per (token, head) by a torch fp32 rotation rounded once. The pass-through span must be bit-exact.
- A second check recomputes the frequencies in fp64 from the RoPE definition: base, rotary_percent, position interpolation and llama-3 scaling. Megatron's unfused `_apply_rotary_pos_emb_bshd` in bf16 bounds that comparison. It is fed the definition's angles rounded to fp32, not `RotaryEmbedding`'s frequencies, so it shares nothing with the cache under test.

**Memory checks.**
- Inputs sit in NaN guard bands: Q/K, the positions, the cache and the probabilities. An out-of-range read then shows up as NaN in the output.
- Positions and gather indices past `n` are poisoned, and Q/K rows past `n` are NaN.
- Outputs go into guard-banded buffers: the samplers' `output`, and RoPE through FlashInfer's in-place variant, which runs the same kernel.
- Read-only inputs must stay unchanged. Each module has `sanitizer` cases.

## What it covers

- **Sampler structure.** One block of 1024 threads per row, each thread reading `gcd(4, V)` tokens. The vocabularies tested:
  - around 1024, 2048, 4096 and 8192, plus 4094 (vec 2) and 1;
  - the production vocabularies 32000, 128256, 151936, 152064 and 262144.

  Hot tokens sit on the first and last id and on every 4096-token block edge.
- **Radix top-k** (`top_k_mask_logits` inside the joint sampler, and `top_k_renorm_probs`). V around the one- and two-CTA split derived from H100's shared memory (57591-57593, 115183-115185) and the production sizes, with hot tokens on every chunk edge.
- **`top_p_renorm_probs` branches.** The ternary search (V < 2048) and AIR radix (V ≥ 2048) at 2047/2048/2049, with float and integer histograms (`is_deterministic` False/True). 8192 tokens tie at the threshold, 8× AIR's candidate buffer.
- **Parameters.**
  - k: 1, 2, 3, 5, 31, 32, 33, V-1, V, V+1 and 0;
  - p: 1e-6, mid cuts, 0.8, 0.9, 0.98, 0.999999, 0 and 1;
  - T: 0, 0.3, 0.5, 0.7, 1, 2, 3, 5;
  - ties at the k-th value and ties straddling the top-p cut;
  - rows of every kind in one batch (k only, p only, both, neither, greedy).

  The joint test checks that its top-k-first row and the p-only row have different supports, so a kernel that applies the filters in another order fails.
- **Megatron glue.**
  - `gather_indices` with poisoned padding; each source row is gathered by rows of both temperatures, so a row must use its own temperature, not its source's.
  - `token_to_request_index` for the unfiltered and top-p samplers and for processed log-probs (a speculative step: three rows per decode request, one per prefill request). The stand-in context's GPU view is sized like production's `max_requests` buffer, so parameters read by row position instead of by request come out wrong rather than out of range.
  - `output`, and the sentinel mapping: in the joint sampler, `k = V - 1` drops exactly the least likely of 64 distinct tokens, while `k = V`, `V + 1` and the sentinel keep it.
  - Rows with neither filter (`k <= 0` or `k >= V`) of a filtered batch are bit-equal to `log_softmax`. Non-greedy `T = 0` log-prob rows score the clamped temperature, over logits `2**-20` apart.
  - Sampled tokens must have finite processed log-probs and follow `exp(log_probs)`.
- **RNG.** The same generator state replays bit-exactly, each call advances the generator, and a new sampler with the same seed reproduces the draws.
- **Robustness.** NaN rows return valid ids and leave the other rows' draws intact. `-inf` tokens are never drawn.
- **RoPE.**
  - 44 head shapes: D in {16, 32, 40, 48, 64, 72, 80, 96, 112, 128, 160, 192, 256, 512} with R in {D, D/2, D/4}, plus 128/40, 96/24 and 512/48;
  - NeoX and GPT-J layouts, bf16 and fp16;
  - nnz in {1, bdy-1, bdy, bdy+1, 4096, 65536} (head-parallel and token-parallel launches), MHA, GQA 32:8 and one K head, contiguous Q/K and strided fused-QKV views, combined pairwise;
  - positions 0, 1, L-2, L-1 and random, with L up to 131072;
  - int32 positions on the direct kernel, and CUDA-graph replay with new inputs against eager.

  For the shapes FlashInfer rotates exactly, the spy also checks that Megatron used FlashInfer. NeoX D16, which `main` rotates itself, runs at full, half and quarter rotary.
- **int32 offsets** (`large`, opt-in): sampler rows whose offsets `row * V` straddle 2³¹, and RoPE tokens whose Q offsets do.

All cases are for H100 (`requires_sm(HOPPER)`). Without FlashInfer they skip, or fail when the runner sets `MCORE_ORACLE_TARGET_SM`.

Checked locally without FlashInfer, which is not installed here. These runs predate the rule against running unit tests locally; since then, only imports, formatters, `git diff --check` and a scratch script that evaluates every spec's fp64 reference have run. The runs used the laptop GPU (sm_89, not evidence), with a scratch emulator of FlashInfer's documented semantics standing in for FlashInfer. For RoPE, the emulator also ports R08's FlashInfer index math.
- **RoPE.** On `main`, with the exact emulator, every case run passes. With the index-math port, only `test_fused_rope_rotates_shapes_flashinfer_cannot` fails, in 66 of 102 cases. Of the other 36, 6 are NeoX D16, which `main` already rotates in torch. The remaining 30 are GPT-J overlaps, which the in-order emulator happens to resolve correctly and which race on a GPU. On a scratch tree of #8862, all 400 non-`large` cases pass.
- **Samplers on `main`.**
  - Every non-greedy case that ran passes; the last 11 cases of the joint sampler's file were not run.
  - The greedy cases fail as designed: 1062 of 2048 greedy rows return the tied id 11.
  - On a scratch tree of #8875, the top-k greedy tests pass. The joint and log-prob greedy tests were not run there.
  - Injecting a 5% bias in the probability exponent, or doubling the temperature, makes every `sampling_from_logits` distribution test fail.

**H100, run 1** (pdx 7849977, first commit). Regression: 424 passed, 28 failed, 10 `large` skipped; the `large` cases passed 10/10. Every expected failure on `main` failed: the three greedy tests, and the RoPE test in 100 of 102 cases (CUDA "misaligned address" among them). The 28 failures:
- **21 renormalization value bounds.** The kept set was exact; the rows carried a common 1-5 ulp scale (28 ulp at V = 262144); and a single kept token came out as `1 + 2**-23`. That is FlashInfer's summation order and reciprocal, not a wrong value. The second commit checks scale and values separately, as described above. Checked on CPU against an emulation of that arithmetic (accepted) and two negative controls (rejected).
- **6 launch failures** (O4a-N1) and **1 chi-square row** (O4a-N2, p = 2e-26). Both now have focused tests.

**H100, run 2** (dfw 21223592, second commit). Regression: 446 passed, 2 failed; the `large` cases passed 10/10; every expected failure on `main` failed. The two failures were log-prob value checks at V = 151936. In both, the kernel was about 1 ulp off per element (two reciprocal renormalizations, then the log), while torch was 0.1 ulp off. Torch's error was the same offset on every kept value, because the ramp rows form an exact arithmetic progression. The third commit raises the log-prob floor to 4 ulp per element, with the reason stated in the code.

**Mutation testing** (dfw 21227864, H100, third commit). Nine mutants of the call sites survived. Eight were oracle gaps, which the fourth commit closes (the glue cases above, NeoX D16 on `main`, and the RoPE definition check's independent angles). Before, the gather test's temperatures lined up with its sources, `token_to_request_index` ran only unfiltered, every unfiltered joint row had tokens tied at the bottom, only the `k = 0` row was compared bit for bit, no non-greedy log-prob row had `T = 0`, and the definition check's bound shared the cache's frequencies. The ninth, `deterministic=False` for top-p sampling, is equivalent: it only swaps FlashInfer's in-block prefix scan for cub's, and both are fixed-order. On FlashInfer's emulator, each new case passes on `main` and fails on its mutant; the H100 rerun of those mutants is pending.

Rerun 3 is pending.

## Notes for reviewers

- **FlashInfer bugs run as strict xfails.** No Megatron change can fix O4a-N1 or O4a-N2, so their kernel cases carry `ou.xfail_upstream(..., "flashinfer-python", fixed_after="0.7.2.post1")`, the version `uv.lock` pins for the CI image (`sampling_oracle.XFAIL_O4A_N1/N2`):
  - every `top_k_renorm_probs` shared-memory size (14);
  - the two `top_k_mask_logits` sizes with no headroom, 115183 and 115184;
  - the two T = 0 tie cases (AssertionError only).

  A FlashInfer release with the fix makes them XPASS, which fails until the mark is removed. A newer FlashInfer without the fix fails them as plain tests. The drafted upstream patches are in the reasons. Megatron's call site (`test_log_probs_kernel_at_the_shared_memory_limit`) stays a plain test that needs #8572.
- **Contract choices the tests pin.**
  - Ties at the top-k cut are kept, as torch's `topk`-threshold filter does.
  - A top-p cut exactly on a cumulative boundary excludes the next token. Holtzman's definition and FlashInfer's own `top_p_renorm_probs` docs both say so. `TorchSampling` keeps it (`cumsum > p`, shifted), but the softmax makes this a measure-zero event outside the dyadic tests.
  - `k = V` is a no-op for `top_k_renorm_probs`, as Megatron relies on, although FlashInfer documents `k` in `(0, V)`.
  - A NaN row's token is unspecified but must be a valid id.
- **Statistical power.** A probability exponent off by 5% (`p**1.05`) and a doubled temperature were each detected by every distribution test on the emulator.
- **Structure-derived sizes are H100-specific.** The radix CTA split comes from H100's 227 KiB opt-in shared memory. The RoPE head-parallel/token-parallel switch depends on resident CTAs, and nnz = 65536 is above it for every head dim.
- **Determinism.** No kernel or dispatch changes, so there is no determinism test or manifest entry. The log-prob replay test is the processed-log-prob determinism contract of #8572.

## Issue tracking

Linked issue: none. Step 4 of the inference kernel audit (family 04, packet O4a: sampling and RoPE). Two suspected findings, both FlashInfer-side:
- **O4a-N1 (confirmed on H100).** FlashInfer sizes each radix CTA's shared memory to the full 227 KiB and does not count the kernel's static scratch, so some vocabularies cannot launch.
  - `top_k_renorm_probs`, which backs Megatron's processed log-probs, fails when a row's per-CTA chunk is 57510-57511 tokens or more. This holds at any batch size and any k.
  - The failing 128-padded vocabularies are 115072; 172544, 172672; 230144, 230272; 287616, 287744, 287872; and so on.
  - No production vocabulary is affected. The multi-CTA `top_k_mask_logits` fails only at sizes that are not multiples of 128.
  - #8572 replaces the renorm with the mask, which removes Megatron's exposure. Its call-site case, `test_log_probs_kernel_at_the_shared_memory_limit`, is in this PR.
- **O4a-N2.** `sampling_from_logits` at T = 0 → 1e-6 skews the choice among exactly tied maxima, because its Gumbel noise is added to fp32 logits scaled by 1e6. Low severity; #8875 maps T = 0 to greedy.

The tests also encode R08-F1 (fused RoPE head shapes), R08-F2 (greedy ties) and s12 (processed log-prob determinism).

## Interaction with other open PRs

- **#8875 (`fix/sampling-contract`)** makes greedy rows take the lowest-index argmax in both FlashInfer kernels' call sites. Three tests need it (table above). With #8875, every other test has the same expected result: its other changes are in the torch backend, `SamplingParams` and the engine.
- **#8862 (`fix/flashinfer-fused-rope-shapes`)** rotates the shapes FlashInfer gets wrong in fp32. `test_fused_rope_rotates_shapes_flashinfer_cannot` needs it. Every other RoPE test takes shapes `main` rotates correctly: those FlashInfer rotates exactly, and NeoX D16, which `main` rotates itself.
- **#8572 (`fix/s12-processed-logprob-determinism`)** replaces `top_k_renorm_probs` in `log_probs_kernel` with `top_k_mask_logits` + softmax, and makes `top_p_renorm_probs` deterministic. The log-prob tests assert the distribution, not the kernel, so they hold with and without #8572. The replay test needs #8572.
- **#8863 and #8864** (stacked on #8862) change which models build the cos/sin cache, not how it is applied. No expected result changes.
