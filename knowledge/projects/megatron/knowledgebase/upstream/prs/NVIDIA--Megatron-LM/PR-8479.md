# Separate MFSDP construction scope from runtime context

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8479) · state: closed · merged: True

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

## What does this PR do?

Previously, `fully_shard_context` was an alias for `FsdpContext`, coupling construction-scope management with runtime state that persists throughout training. These responsibilities have different reasons to change: construction controls which context new modules join, while runtime behavior controls communication streams and prefetching. Separating them follows Robert C. Martin's [Single Responsibility Principle](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html).

`fully_shard_context(context)` now accepts an existing `FsdpContext`; configuration belongs to the `FsdpContext` constructor.

```python
context = FsdpContext(device=device, caller_managed_grad_sync=True)
with fully_shard_context(context):
    fully_shard(model, mesh=mesh, placements=placements)
```

The scope activates the supplied context for construction, finalizes it on successful exit, and clears the active scope on exit. `FsdpContext` no longer implements context-manager methods or stores a scope token.

Export `FsdpContext` alongside `fully_shard_context`, migrate the MCore adapter, training entry points, and tests, and update the API documentation. The existing context-sharing test checks that modules retain the supplied context.

## Validation

Rebased onto `origin/main` at `7d6895ac6a3ee9e16c53f573f363d2a52b88bf94`. Resolved the overlap with main's `RuntimePolicy` API: callers now pass `fully_shard_context(FsdpContext(...))`, with runtime options still grouped in `RuntimePolicy`. The read-only `is_finalized` property is preserved.

On two RTX A6000 GPUs with NGC 26.08, the context, fully-shard, dense-adapter, pipeline context-sharing, quantization, and gradient-multiplicity suites completed with **75 passed, 31 skipped per rank**. Skips require four or more ranks or Blackwell hardware. Black, isort, Ruff, Pylint (10/10), and `git diff --check` passed in the repository's formatter scope. All context call sites were checked for the new construction API and supported `FsdpContext` arguments.

- ahmadki · comment · 2026-10-28T14:11:46Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8479#discussion_r4401617476)

File: `megatron/core/distributed/fsdp/src/megatron_fsdp/experimental/context.py` · line 91

nit, but `parameter_to_owner` could be a `fully_shard` argument.
The PR says the scope controls construction and `FsdpContext` holds runtime state, but `parameter_to_owner` is construction-only: it's read once per `fully_shard` call and cleared in `finalize()`.
For the whole runtime life of the context, the field is just `None`.

The fix:
```python
# fully_shard.py
def fully_shard(module, mesh, placements, ..., grad_accumulation_count=None,
                parameter_to_owner: dict[nn.Parameter, int] | None = None) -> None:
    ...
    FsdpModule.__init__(module, context=context, ..., parameter_to_owner=parameter_to_owner)
```

`FsdpModule.__init__` would then pass it to `FsdpParameterGroup` instead of reading `context.parameter_to_owner`.
