# fix(inference): pass prefix-caching routing settings to served frontends

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8597) · state: open · merged: False

## Original PR description

## What does this PR do?

`MegatronLLM.serve()` and `MegatronAsyncLLM.serve()` started the OpenAI-compatible HTTP frontend without passing the engine's KV block size or its prefix-caching coordinator policy. The frontend's `InferenceClient` needs both to hash prompts for prefix-affinity routing. A served engine with prefix caching therefore could not route requests that share a prefix to the engine that already caches it.

This PR forwards `block_size_tokens` (when prefix caching is enabled) and `prefix_caching_coordinator_policy` from the engine's context to `start_text_gen_server`.

## Example failure scenario(s)

**Scenario (served prefix caching without routing hints)**

- An engine runs with prefix caching, 256-token KV blocks, and the `longest_prefix` coordinator policy.
- The caller starts the HTTP frontend with `llm.serve(serve_config)`.
- Before this fix, the frontend's client received no block size or policy, so it did not hash prompts for routing.
- With this fix, the frontend receives block size 256 and the `longest_prefix` policy.

## How was this bug discovered?

The sync and async serve tests capture the arguments passed to `start_text_gen_server` and expect `block_size_tokens=256` and `prefix_caching_coordinator_policy="longest_prefix"`. On `main` neither argument is passed.

## Dependency and scope

This PR is independent and based on `main`. The change is limited to the `serve()` methods in `apis/llm.py` and `apis/async_llm.py`. The regression is a new test, `test_serve_forwards_prefix_caching_routing_settings`, which covers both `MegatronLLM` and `MegatronAsyncLLM`. The existing serve tests are unchanged.
