# [Fix bug] order the inline reload after its group's device-to-host copy

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7399) · state: open · merged: False

## Original PR description

Fixes #7398 

### The bug 

`ChunkOffloadHandler.reload()` enqueues its host-to-device copy on the caller's current stream (the `tensor_pop` path is the compute stream) with no ordering edge on the group's `_offload_event`, recorded on `d2h_stream`. `bulk_reload_group` supplies that edge itself before looping; `tensor_pop` calls `reload()` inline and has no edge at all, so a backward that reaches a group before any prefetch reloaded it can read the pinned staging buffer while the device-to-host copy filling it is still in flight. The activation silently becomes stale bytes, the gradients computed from it are wrong, nothing raises, and the loss curve still descends.

This contradicts the feature's own documented design (`docs/user-guide/features/fine_grained_activation_offloading.md`): *"Before the group's backward, tensors are reloaded from CPU to GPU on `h2d_stream`, and the compute stream waits for the transfer to complete."*

The inline path is not rare. The prefetch trigger `on_group_start_backward` is the backward of the *group-start* marker, which autograd runs at the **end** of that group's backward, so the LIFO must be primed one group ahead by `pre_reload_last_layer`. During warmup nothing primes it as `should_bulk_offload` returns `True` unconditionally while `is_warmup`, and `tensor_pop` drained a group's tensors while leaving the group object on `_groups_to_reload`, so every `bulk_reload_group` re-targeted an already-drained tail and the priming branch was never reached. Measured on a 4-layer `GPTModel` with `--offload-modules core_attn`:

| iter | inline (unordered) | prefetched | bulk calls | bulk hit an empty group |
|---|---|---|---|---|
| 0 (warmup) | **24** | **0** | 4 | **4** |
| 1–3 (steady) | 0 | 18 | 3 | 0 |

Steady state is clean only because `post_warmup_callback` keeps the last group of each offload-module name resident, which incidentally leaves the LIFO correctly primed.

### The change

A `reload_pending` latch on `OffloadTensorGroup`, set when that group's D2H is enqueued and cleared by whichever reload consumes it. On the inline path `tensor_pop` waits on the group's offload event on the compute stream and removes the group from `_groups_to_reload` so the prefetch advances.

A latch keyed by group identity is needed rather than an unconditional wait: `_offload_event` is a single `torch.cuda.Event` per group, re-recorded every iteration, so a group that was *not* offloaded this iteration would otherwise wait on a stale edge. `reset()` clears the latch for groups offloaded but never reloaded, and `bulk_reload_group` clears it too so a prefetched group never re-serializes compute behind the D2H.

Restoring the LIFO bookkeeping also repairs prefetching itself: warmup goes from 24 inline / 0 prefetched to 6 inline / 18 prefetched, and the 6 that remain are ordered.

### Evidence

With no artificial stall at all — a 256 MiB device-to-host copy and nothing else — 20 trials per arm:

| tree | GPU | corrupted |
|---|---|---|
| before | B300 (sm_103) | **19/20** |
| before | A40 (sm_86) | **20/20** |
| after | B300 (sm_103) | **0/20** |
| after | A40 (sm_86) | **0/20** |

Corrupted trials return a *mixture* of stale and correct values within one tensor, with the boundary in a different place each time as the H2D reading a buffer the D2H is still writing.

### Tests

Adds `test_inline_reload_is_ordered_after_the_groups_offload`, which stalls `d2h_stream` with `torch.cuda._sleep` before the commit to make the race deterministic, asserts the stall actually landed (without which the test would pass for the wrong reason on faster hardware), and then checks both the ordering and the reloaded values.

Mutation-verified: reverting `if group.reload_pending:` → `if False:` turns the test red with the intended assertion. Passes on B300 and A40.

No existing test covers this.
