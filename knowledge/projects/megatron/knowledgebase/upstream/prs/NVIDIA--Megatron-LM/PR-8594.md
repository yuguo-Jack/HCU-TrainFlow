# fix(inference): abort submitted requests when their caller stops waiting

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8594) · state: open · merged: False

## Original PR description

## What does this PR do?

When a caller stopped waiting for inference requests it had already submitted, those requests kept generating until their token limits. That happened when the caller was cancelled, when a sibling request failed, or when a later submission failed. The requests held batch slots for work nobody would read.

This PR aborts already-submitted requests in each of these cases:

- `MegatronLLM` / `MegatronAsyncLLM` `generate` tracks every request ID it submits and aborts all of them if the call is cancelled or one request fails.
- `AsyncStream` aborts its request when the consumer is cancelled, including when the stream from `InferenceClient.add_request_streaming` is iterated directly rather than through `generator()`.
- `/v1/completions` and `/v1/chat/completions` abort already-admitted streams when a later streaming submission fails. They also abort all admitted requests when one non-streaming request fails.
- `InferenceClient` releases its ownership record when a request's socket send fails, and sends an abort when the engine reports an error that left remote state behind (`source_safe=False`).

## Example failure scenario(s)

**Scenario 1 (cancelled batch generate)**

- A caller submits requests A and B through `MegatronAsyncLLM.generate`.
- The caller's task is cancelled while both requests are still generating.
- Before this fix, neither A nor B was aborted, so both kept generating to their token limits.
- With this fix, the cancelled call aborts both A and B.

**Scenario 2 (partially admitted streaming request)**

- A streaming chat request asks for `n=3` choices.
- Choices 1 and 2 are submitted, and the send for choice 3 fails.
- Before this fix, the endpoint returned a 500 while choices 1 and 2 kept generating.
- With this fix, the endpoint aborts choices 1 and 2 before returning the 500.

**Scenario 3 (failed sibling in a non-streaming request)**

- A `/v1/completions` request submits three prompts.
- The engine fails prompt 2.
- Before this fix, the endpoint returned a 500 while prompts 1 and 3 kept generating.
- With this fix, the endpoint aborts all three admitted requests.

**Scenario 4 (cancelled direct stream iteration)**

- A client iterates the stream returned by `add_request_streaming` directly.
- The consuming task is cancelled while the request is generating.
- Before this fix, no abort was sent, because only `generator()` handled cancellation.
- With this fix, the stream sends the abort when its consumer is cancelled.

## How was this bug discovered?

Unit tests use fake clients that record which request IDs are aborted. Each test cancels or fails a call while requests are in flight and expects specific aborts. On `main` the recorded abort list is empty, and a failed send leaves the request in the client's ownership set.

## Dependency and scope

This PR is independent and based on `main`. Production changes are in:

- `apis/_llm_base.py` (`generate`);
- `async_stream.py`;
- `inference_client.py`;
- the chat and completions endpoints.

Two existing tests change their expectations because the old behavior is the bug:

- `test_terminal_error_and_abort_acknowledgement` now expects an automatic abort after an error that leaves remote state behind.
- The `engine-error` cases of `test_failures_before_formatting_are_a_500` keep their replies and now expect the admitted requests `[1, 2, 3]` to be aborted.

If sending an abort itself fails while `generate` is already unwinding, that send error is ignored so the original error reaches the caller.

### Keep failed abort sends retryable

The new guard in [_send_abort](https://github.com/NVIDIA/Megatron-LM/blob/13732f4dabf646d354068ae1139292811f922ae5/megatron/core/inference/inference_client.py#L452-L468) treats `aborted_request_ids` as proof that an abort was sent, but the method adds that marker before `socket.send` succeeds.

**Failure:** submit a request, make the first abort send raise, and catch the exception from `abort_request(id)`. After sending recovers, call `abort_request_and_wait(id)`. It creates an acknowledgement future, but the new guard suppresses the retry. No abort reached the coordinator, so remote work continues and the acknowledgement stays pending until some other source-safe completion arrives. The [base implementation](https://github.com/NVIDIA/Megatron-LM/blob/259f6a7c27117ea3aca8ca0fa38b33b3a937c026/megatron/core/inference/inference_client.py#L452-L473) permits this retry because the newly created abort waiter passes its guard.

**Correction:** move `aborted_request_ids.add(request_id)` after the successful send. The client uses a [synchronous ZMQ socket](https://github.com/NVIDIA/Megatron-LM/blob/13732f4dabf646d354068ae1139292811f922ae5/megatron/core/inference/inference_client.py#L104-L114), so there’s no event-loop suspension between sending and recording success. Suggested replacement for the final portion of `_send_abort`; verify it before adopting:

```python
        self.request_submission_times.pop(request_id, None)
        payload = [Headers.ABORT_REQUEST.value, request_id]
        self.socket.send(msgpack.packb(payload, use_bin_type=True))
        self.aborted_request_ids.add(request_id)
```

The duplicate-send guard must represent a successfully queued abort, not merely an attempted one. Keep `_pending_source_requests` until a source-safe reply or acknowledgement arrives.

**Preservation and acceptance:** add a proposed regression in [the client tests](https://github.com/NVIDIA/Megatron-LM/blob/13732f4dabf646d354068ae1139292811f922ae5/tests/unit_tests/inference/test_inference_client.py), parameterized over future and streaming submissions. Make the first fire-and-forget abort send fail; assert that ownership remains and the successful-send marker is absent. Restore sending, call `abort_request_and_wait`, and assert that it sends `[ABORT_REQUEST, id]`, remains pending before acknowledgement, and resolves and clears ownership after `REQUEST_ABORTED(id, True)`. Retain the distinct existing cases: [an unsafe terminal error followed by an acknowledgement waiter](https://github.com/NVIDIA/Megatron-LM/blob/13732f4dabf646d354068ae1139292811f922ae5/tests/unit_tests/inference/test_inference_client.py#L212-L230) must send only one successful abort; [an unsafe request without a public handle](https://github.com/NVIDIA/Megatron-LM/blob/13732f4dabf646d354068ae1139292811f922ae5/tests/unit_tests/inference/test_inference_client.py#L496-L508) must still send; and [completed future and stream IDs](https://github.com/NVIDIA/Megatron-LM/blob/13732f4dabf646d354068ae1139292811f922ae5/tests/unit_tests/inference/test_inference_client.py#L531-L557) must remain no-ops. The proposed ordering preserves these branches by source reasoning; I haven’t executed the checks.
