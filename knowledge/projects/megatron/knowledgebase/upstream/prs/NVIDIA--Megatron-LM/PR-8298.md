# Add bf16 reduce-scatter option for 2-rank expert-TP MoE combine

# What does this PR do?

Adds `moe_combine_reduce_in_activation_dtype` (default off), which lets the alltoall dispatcher's expert-TP reduce-scatter in the token combine run in bf16 instead of the FP32 router dtype when the expert-TP group has exactly two ranks. In that case the result is bit-identical, and the change removes an FP32 copy of every token-expert row.

:warning: For major changes (either in lines of code or in its impact), please make sure to first share a design doc with the team. If you're unsure what's the best way to do so, contact @NVIDIA/mcore-oncall.

## Why the upcast costs memory

`MoEAlltoAllTokenDispatcher.combine_preprocess` reduce-scatters expert outputs across the expert-tensor-parallel group as

```python
reduce_scatter_to_sequence_parallel_region(
    hidden_states.to(self.probs.dtype), group=self.tp_group, ...
).to(hidden_states.dtype)
```

With `moe_router_dtype='fp32'`, `self.probs` is FP32, so this allocates an FP32 copy of every token-expert row this rank received, and the collective sends twice the bytes of the bf16 tensor. At long context this copy is the largest single allocation in the MoE layer. In SkyRL, on GLM-5.3-Flash (TP8, EP32 x ETP2), it was 19.31 GiB/GPU at 576k tokens, the allocation that ran that length out of memory.

The upcast exists so that the cross-rank sum does not round to bf16 at every step. That only matters when there is more than one step:

- **2 ranks:** each output element is one addition, `a + b`. NCCL's Ring and PAT kernels compute a bf16 sum by accumulating in FP32 and rounding once, so `reduce_scatter(bf16)` gives the same result as `reduce_scatter(fp32).to(bf16)`.
- **More than 2 ranks:** Ring adds partial sums hop by hop, and a bf16 reduction rounds after each hop. That differs from the FP32 path, so the upcast is kept.
- **NVLS:** the reduction happens inside the NVSwitch with different rounding. A forced `NCCL_ALGO=NVLS` bf16 reduce-scatter differs from the FP32 path in roughly 10-20% of elements, by at most 1 bf16 ulp. The upcast is kept whenever `NCCL_ALGO` asks for NVLS.

## Change

- `TransformerConfig.moe_combine_reduce_in_activation_dtype: bool = False`. The CLI flag `--moe-combine-reduce-in-activation-dtype` is generated from the config field.
- `MoEAlltoAllTokenDispatcher._tp_reduce_dtype(hidden_states)` returns the activation dtype when the flag is set, `self.tp_size == 2`, and `NCCL_ALGO` does not ask for NVLS. In every other case it returns `self.probs.dtype`, which is today's behavior. `combine_preprocess` calls it in place of `self.probs.dtype`. Nothing else in the method changes.
- `_nccl_algo_may_use_nvls()` matches `NCCL_ALGO` values that contain `nvls` (for example `NVLS`, `Ring,NVLS`, `reducescatter:nvls`), and does not match the exclusion form `^NVLS`.
- One row added to the Token Dispatching table in `megatron/core/transformer/moe/README.md`.

With the flag off, the code path is unchanged.

## Alternatives considered

- **Always reduce in the activation dtype.** Not exact for expert-TP groups larger than 2, and not exact under NVLS, so it would change numerics for those configurations.
- **Chunk the upcast and reduce-scatter.** This bounds the FP32 peak, but every byte is still sent in FP32 and the code gets more complex, even though for 2 ranks the FP32 path buys no accuracy.
- **Ask NCCL which algorithm it will pick.** PyTorch does not expose NCCL's per-collective algorithm choice, so the guard reads the `NCCL_ALGO` that the user set. With `NCCL_ALGO` unset, a 2-rank reduce-scatter selected Ring at every size from 1 KiB to 1 GiB in SkyRL's measurements (NCCL 2.29.7, B200).
- **Enable by default.** The result is bit-identical under Ring/PAT, but that depends on NCCL's reduction kernels, so this PR leaves the flag off. Reviewers may prefer it on.

The allgather dispatcher's `token_combine` has the same upcast pattern over the `tp_ep` group. It is out of scope here.

## Validation (from SkyRL)

The same change has been running in SkyRL as a monkeypatch, [NovaSky-AI/SkyRL#2414](https://github.com/NovaSky-AI/SkyRL/pull/2414) (split out of [#2341](https://github.com/NovaSky-AI/SkyRL/pull/2341)):

- **Exactness:** 2-rank bf16 reduce-scatter compared with the FP32 reduce-scatter cast back to bf16: 0 of 64M elements differ (Ring/PAT). The SkyRL patch notes record that the bit-for-bit check passed on up to 512M elements spanning five orders of magnitude, within a node and across nodes (NCCL 2.29.7, B200).
- **Memory:** On full GLM-5.3-Flash at 512k context (64 B200, ETP2), the FP32 combine ran out of memory and the bf16 combine fit at 144 GiB. At 576k tokens (TP8, EP32 x ETP2), the FP32 copy this removes was 19.31 GiB/GPU.

## Test plan

- New `tests/unit_tests/transformer/moe/test_combine_reduce_dtype.py`:
  - `TestTpReduceDtype` (CPU): dtype decision for flag off/on, expert-TP sizes 2/4/8, bf16 and fp16 activations, and `NCCL_ALGO` values (`NVLS`, `nvls`, `Ring,NVLS`, `reducescatter:nvls`, `^NVLS`, `Ring`, `PAT`). It also checks that `combine_preprocess` hands the reduce-scatter the expected dtype and returns the activation dtype.
  - `TestCombineReduceInActivationDtype` (GPU, 8 ranks, TP2 x EP4, `NCCL_ALGO=Ring`): runs dispatch/combine through two MoE layers with identical weights, flag off and flag on. Each expert-TP rank gets a different bf16 partial result, and the test asserts that the combined outputs are `torch.equal`.
- Ran locally on CPU: `pytest tests/unit_tests/transformer/moe/test_combine_reduce_dtype.py`. Result: 17 passed, 1 skipped (the 8-rank GPU test).
- The GPU test has not been run on this branch. It needs an 8-GPU `torchrun` in CI.
