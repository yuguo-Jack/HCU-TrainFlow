# refactor: separate FSDP configuration from DDP

## What does this PR do?

Megatron-FSDP currently stores its settings in `DistributedDataParallelConfig`, so constructing FSDP requires a DDP config and backend-selection flags. Introduce an independent `FullyShardedDataParallelConfig` whose type selects Megatron-FSDP and whose fields and validation belong to FSDP.

```python
fsdp_config = FullyShardedDataParallelConfig(
    version=2,
    data_parallel_sharding_strategy="optim_grads_params",
    main_grads_dtype=torch.float32,
)
model = FullyShardedDataParallel(
    config=transformer_config,
    module=model,
    fsdp_config=fsdp_config,
    pg_collection=pg_collection,
)
```

Model builders accept `data_parallel_config=fsdp_config`; native training configs accept `data_parallel=fsdp_config`. The adapters expose the effective config as `model.fsdp_config`, and optimizer consumers use that config.

### Design and migration tradeoffs

- Independent DDP and FSDP dataclasses, with no inheritance between them. Shared settings appear in both classes so each public API can evolve independently.
- One FSDP config covers v1 and v2. `version` defaults to 1; validation rejects unsupported v2 combinations. FSDP-specific fields omit redundant `fsdp_`/`megatron_fsdp_` prefixes.
- Validation leaves requested settings unchanged; adapter construction resolves inherited settings on a copy.
- Existing CLI flags, `ddp_config=` callers, and serialized `ddp` training configs remain supported. A compatibility view forwards legacy FSDP reads and writes to the effective FSDP config, including v1's runtime adjustments.
- Legacy FSDP fields remain in `DistributedDataParallelConfig` during migration. Removing them would be a later breaking change. The compatibility view is the main additional complexity to assess in this draft.
