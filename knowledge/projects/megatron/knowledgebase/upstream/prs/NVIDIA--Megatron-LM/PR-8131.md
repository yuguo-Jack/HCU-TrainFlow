# [Dev] Add identity hyper-connections (iHC)

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8131) · state: open · merged: False

## Original PR description

## Summary

Adds an identity hyper-connections (iHC) variant of mHC behind a new `TransformerConfig` flag, `enable_identity_hyper_connections` (CLI: `--enable-identity-hyper-connections`; requires `--enable-hyper-connections`).

With the flag on, `HyperConnectionModule` fixes the residual mixing matrix `H_res` to the `n x n` identity instead of the Sinkhorn-projected manifold matrix:

- `mapping_proj` only produces `H_pre` and `H_post` (`2n` outputs instead of `n^2 + 2n`); `alpha_res` and the `H_res` part of `bias` are not created.
- The `H_res` projection and the Sinkhorn-Knopp step are skipped entirely; `compute_mappings` materializes a per-token identity `[s, b, n, n]` in the activation dtype.
- The downstream `H_res` / `H_post` / BDA path (`fused_h_res_h_post_bda`, native and fused `h_post_bda` kernels, mHC recompute, CUDA graph plumbing) is unchanged and consumes the identity as-is. Kernel-level shortcuts for the identity case are left for a follow-up.
- With `use_fused_mhc=True`, aggregate and `h_post_bda` stay fused; the projection takes the native path because the fused `proj_rms_compute_h` kernel assumes the mHC output layout.
- mHC and iHC checkpoints are not interchangeable (parameter shapes differ).

The resulting propagation is `x_{l+1} = x_l + H_post^T @ F(H_pre @ x_l)`.

One change outside the module: `TransformerLayerNode.detach` in the fine-grained EP-overlap schedule now records a gradient bridge only for tensors that require grad. It used to hand every detached tensor to `run_backward`, which raises for a tensor without `grad_fn`; the constant iHC `h_res` is exactly that, so `overlap_moe_expert_parallel_comm` would have crashed. For mHC every bridged tensor requires grad, so behaviour there is unchanged (verified below).

## Test plan

New tests:
- `tests/unit_tests/transformer/test_identity_hyper_connection.py`: config validation, parameter layout (`2n` rows, no `alpha_res`), identity `h_res` in fp32 / bf16, empty-sequence forward/backward, output equals `x_l + H_post^T (F + bias)` stream by stream, iHC matches mHC whose Sinkhorn output is forced to the identity (outputs and gradients), `_forward_with_checkpoint` matches `_forward_normal`, `use_fused_mhc=True` path, `HyperConnectionTransformerLayer` forward/backward with and without `recompute_modules=[mhc]`.
- `tests/unit_tests/a2a_overlap/test_mhc_schedule.py::test_identity_hyper_connections_schedule_matches_eager` (EP=4 alltoall overlap schedule vs eager, with and without mHC recompute), placed last in its class.
- `tests/unit_tests/models/test_hybrid_moe_model.py`: the new field is registered in `GOLDEN_CONFIG`.

Why the iHC tests run under `torch.compiler.set_stance("force_eager")`: the constant `h_res` would otherwise add `requires_grad=False` guard variants to the `torch.compile`'d mHC kernels that every mHC test in the bucket shares (`native_h_post_bda`, `native_h_aggregate`, ...). Several existing eager-vs-schedule / eager-vs-graph comparisons (`test_full_recompute_carries_the_mhc_bridge_gradient`, `test_gpu_mhc_split_replay_matches_eager`) are sensitive to the compile-cache history: they fail when the default recompile limit of 8 is crossed, or a cold compile happens, between their two arms. On an 8x H100 node, clean `dev` fails `test_gpu_mhc_split_replay_matches_eager[True-False-False]` in a process that only runs `test_hyper_connection_recompute.py` before it, so this is pre-existing order sensitivity rather than an iHC regression; the eager stance keeps the cache history seen by those tests identical to `dev`. (An earlier revision of this PR reset the dynamo caches in the iHC teardowns instead; that changed the history and made CI fail the graph-split test, which is how this was found.)

**What I checked and found correct:**
- **iHC parameter layout:** `mapping_proj` and `bias` have `2n` outputs. `alpha_res` is registered as `None`. The `mark_keep_in_fp32` and `sequence_parallel` calls skip it when it is missing. iHC never reads `alpha_res` in the native `_compute_h` or the fused H_post/BDA kernels.
- **`compute_mappings`:** under iHC it builds a contiguous `[s, b, n, n]` identity in the activation dtype that does not require grad, and skips Sinkhorn. The mHC fused and native paths are unchanged; the `h_res.view(s, b, n, n)` call just moved into the Sinkhorn argument.
- **Kernel selection with `use_fused_mhc`:** iHC keeps the fused aggregate and `h_post_bda` kernels. The projection goes through the native `_projection_and_get_norm`, because the fused projection kernel assumes the `n^2 + 2n` layout.
- **`TransformerLayerNode.detach`** ([fine_grained_callables.py](https://github.com/NVIDIA/Megatron-LM/blob/5cf1a2003591696b4b68330e0188c517f1659662/megatron/core/models/gpt/fine_grained_callables.py#L406-L419)): only tensors that require grad are recorded for the backward bridge. `backward_impl` still pairs each recorded tensor with its detached copy, and `ScheduleNode._backward` accepts a variable number of gradients. Every bridged mHC tensor requires grad, so mHC behavior is unchanged.
- **Config:** `enable_identity_hyper_connections` defaults to `False`. Setting it without `enable_hyper_connections` raises an error. `ArgumentGroupFactory` generates the CLI flag automatically, and the flag is registered in the hybrid-MoE `GOLDEN_CONFIG`. Every new identifier is actually used.
- **Test helper teardown** ([test_utilities.py](https://github.com/NVIDIA/Megatron-LM/blob/5cf1a2003591696b4b68330e0188c517f1659662/tests/unit_tests/test_utilities.py#L115-L140)):
  - It copies `ps._global_process_group_list`, which holds only the groups this rank joined through MCore's `create_group`.
  - It resets the FP8 and DTensor caches, calls `ps.destroy_model_parallel()`, then destroys the remaining groups in reverse creation order.
  - WORLD is preserved, and so are the `HyperCommGrid` groups, which are created with `new_subgroups_by_enumeration`.
- **Other users of the changed shapes:** I found no other code that depends on the `alpha_res` or `mapping_proj` shapes. [gpt_hybrid_conversion.py](https://github.com/NVIDIA/Megatron-LM/blob/5cf1a2003591696b4b68330e0188c517f1659662/tools/checkpoint/gpt_hybrid_conversion.py) has no hyper-connection handling. The hybrid wrapper ([hybrid_block.py](https://github.com/NVIDIA/Megatron-LM/blob/5cf1a2003591696b4b68330e0188c517f1659662/megatron/core/models/hybrid/hybrid_block.py)) only passes `h_res` through.

The PR says the identity is materialized and run through a bmm on purpose, with kernel shortcuts for the identity case planned as a follow-up. I treated that as an intentional design decision and did not flag it.
