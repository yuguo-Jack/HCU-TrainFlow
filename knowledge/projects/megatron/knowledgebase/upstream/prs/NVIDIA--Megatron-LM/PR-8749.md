# Warn on the FSDP process-group fallbacks to the global grid

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8749) · state: closed · merged: False

## Original PR description

Depends on #8017, #8045, #8049 (which contains #6293) and #8051. Please review the diff from the merge of their heads: [scoped diff](https://github.com/Connor-XY/Megatron-LM/compare/c9cdc74d6e...yx/pstate-c2-fsdp-fallbacks). The #8049 merge regenerates the process-group allowlist, whose total conflicted.

Land this after #8725, which rejects GTP weight remat in Megatron-FSDP v1. The commits apply without it, but the FSDP v1 fallback selects the same groups as before only because v1 runs without GTP weight remat. Land it after #8731 too. Until then `FullyShardedOptimizer` names experts without an expert layout, so Megatron-FSDP v2 MoE runs reach the new `get_ep_layer_offset` warning once, with the same names as before.

**Why.** When the caller passes no process groups, three FSDP paths read the global grid in `parallel_state` with no warning and no removal date:
- Megatron-FSDP v1 has 11 group accessor calls in `_init_dist_index`.
- Torch FSDP reads its shard group.
- The FSDP-DTensor expert offsets (`get_ep_layer_offset`) read the global EP rank and size. They did this for dense models too, although a dense model's offset is always 0. `get_global_unique_param_name` names every parameter through this helper.

Separately, MFSDP v2 checked `dp_cp` with `hasattr`, which is always true for a declared collection field, so an unset `dp_cp` reached `DeviceMesh.from_group` as `None`.

**What.**
- Each fallback goes through `resolve_process_groups`. It emits a `ProcessGroupFallbackWarning` once per owner (deprecated in 0.21, removed in 0.23), then returns the same groups as before.
  - FSDP v1 builds a collection with every field its collection path reads, then takes that path. The collection holds the replicate DP groups, while the old fallback read the GTP-inclusive accessors. With GTP weight remat off, these are the same group objects.
  - Torch FSDP resolves `dp_cp_gtp_remat`, which is the group it read before: `get_data_parallel_group(with_context_parallel=True)`.
  - `get_ep_layer_offset` returns 0 for a model without experts and reads nothing. With experts, it warns and takes the rank and size of the global EP group. If `parallel_state` has no EP group, it raises `RuntimeError` (before, this was an assertion or a division by zero).
- MFSDP v2 checks `dp_cp` with `vars()`, so an unset or `None` `dp_cp` raises `ValueError`.
- The checker goes from 173 reads to 162: 14 accessor reads become 3 guarded `resolve_process_groups` calls. The allowlist also records the reads that main added since this PR was written.

Megatron-LM training already passes its groups to FSDP v1, Torch FSDP and the checkpoint helpers, so stock training does not warn once #8731 is in.

**Tests.**
- `mfsdp_v1/test_mcore_fsdp_dist_index.py`: in eight layouts, the fallback warns, reads the grid only through the resolver, and selects the same groups as an explicit collection. This replaces the old test of the fallback's ranks.
- `test_torch_fully_sharded_parallel.py`: the fallback warns and picks `get_data_parallel_group(with_context_parallel=True)`. An explicit group reads nothing global.
- `transformer/test_fsdp_dtensor_expert_offsets.py`: a dense model reads nothing. With experts at EP=2, the fallback warns and matches the global layout. Without an EP group, it raises.
- `mfsdp_v2/test_mcore_dense.py`: a collection with `dp_cp` unset or `None` is rejected.
- `mfsdp_v2/test_checkpoint.py` passes its collection's expert layout.

On 4 GPUs against its base, `mfsdp_v1/test_mcore_fsdp_dist_index.py` passes 20 tests here and 20 on the base; the 8 layout tests that replace the old fallback-rank test pass. `mfsdp_v2/test_checkpoint.py` passes 11 tests on both sides. `mfsdp_v2/test_mcore_dense.py` passes 14 here vs 12 on the base, and its 2 new tests pass. `transformer/test_fsdp_dtensor_expert_offsets.py` passes 12 here vs 8 on the base, and its 4 new tests pass. No test regresses in these four files. `test_torch_fully_sharded_parallel.py` did not finish on either side on 4 GPUs; its `test_fsdp2_swiglu_sharded_tensor_factory` fails on both sides there because it hard-codes an 8-rank TP2xDP4 layout. On 8 GPUs (two nodes) in the integration run, the file's 3 tests pass, as on main. In the integration run, this PR's test files show no regressions against main. The dist-index and expert-offset test files are not on main; they come from the PRs below this one, and their 20 and 12 tests pass in that run.

Before the sync, a fix to the no-experts test fixture was checked separately: the 2 fixture tests fail without it. Before the sync, the branch also ran on 4 CPU gloo ranks: no regressions, the 4 new offset tests pass, and every other failure also occurs on the base, mostly for lack of CUDA. The MFSDP v2 tests cannot be collected on CPU.

**Compatibility.**
- On the standard grid, groups, expert offsets and checkpoint names are unchanged.
- Callers that omit groups get one warning per class or function. In this repo, the MFSDP v1 end-to-end tests, `test_checkpointing.py` and `test_save_run_config.py` still build FSDP v1 without a collection and now warn. They keep covering the default path.
- The old EP accessors honored the overrides that offline tools set with `set_expert_model_parallel_world_size` and `set_expert_model_parallel_rank`. The fallback reads the group instead, so such callers must pass `ep_rank` and `ep_size`. No in-repo tool calls these helpers without them. Megatron-Bridge calls `handle_experts_in_state_dict` without an expert layout, so it warns for MoE models until it passes one.
- Suppose the global grid runs GTP weight remat while the FSDP v1 config does not. The old fallback silently used the GTP-inclusive groups; the new one fails at mesh construction. Every consistent configuration selects the same groups.
- Not changed here: MFSDP v2 with MoE at EP=1 and no `expt_dp` still passes `None` to `DeviceMesh.from_group`, because validation checks `expt_dp` only for EP>1.
- Needs `determinism-exempt` only while the PRs below this one are unlanded. CI diffs against main, and the base carries registered kernel files. This PR's own diff passes the coverage check.

This PR's edits to those classes are applied unchanged where the code moved, and the process-group allowlist follows the move. On 4 GPUs against its new base, the Megatron-FSDP adapter tests and this PR's own tests (10 files) show no regressions: 103 passed here, 97 on the base. The two CUDA-graph end-to-end cases of `test_mcore_fully_sharded_data_parallel.py` fail on both sides, as they do on main. `test_torch_fully_sharded_parallel.py` stops on both sides at a case that needs 8 GPUs.
