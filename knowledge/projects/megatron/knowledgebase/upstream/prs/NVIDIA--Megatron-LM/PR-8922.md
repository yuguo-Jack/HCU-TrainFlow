# fix(mfsdp): validate grad_reduce_in_fp32 against explicit gradient dtypes

## Original PR description

## What does this PR do?

#5462 deliberately decoupled MFSDP's gradient dtypes from `grad_reduce_in_fp32` to remove the confusing interaction between the legacy flag and MFSDP's explicit dtype settings. MFSDP uses separate controls for main-gradient storage/accumulation and gradient communication, allowing those precisions to be configured independently. That change retained BF16 defaults to avoid unexpectedly increasing memory usage in existing recipes. Recipes requesting FP32 gradients therefore needed to [migrate their explicit MFSDP settings](https://github.com/NVIDIA/Megatron-LM/pull/5462#discussion_r3502498292).

This PR adds the missing validation so users cannot set `grad_reduce_in_fp32=True` and assume MFSDP will follow it while its explicit settings still select lower precision. For MFSDP v1 and v2, `DistributedDataParallelConfig` now requires:

- `megatron_fsdp_main_grads_dtype=torch.float32`.
- `megatron_fsdp_grad_comm_dtype=torch.float32` or `None` to inherit FP32 main gradients.

Each inconsistent setting raises an actionable error directing the user to the explicit dtype controls. The flag validates those choices; it does not override them. With `grad_reduce_in_fp32=False`, MFSDP's dtype choices remain independent. DDP behavior is unchanged.
