# What does this PR do?
<!-- Add a one line overview of what this PR aims to accomplish. -->

With chunked optimizer-state offload, train_step force-syncs the LayerWise (Muon) bucket groups at the start of the iteration, stages the sibling DistributedOptimizer's MXFP8 param buffer, and only then moves the LayerWise fp32 masters to pinned CPU memory. The DistOpt staging ended with DistributedDataParallel.reset_param_sync_dispatch_state(), which cleared param_gather_dispatched on *every* bucket group, so the forward pre-hooks dispatched a second LayerWise all-gather. That gather staged Q(bf16(main_param)) from masters that had just been rebound to CPU buffers whose D2H copies were still in flight, and one stale MXFP8 weight per iteration was enough to change the training trajectory.

Symptoms: with --chunked-optimizer-state-offload, --fp8-param-gather, --reuse-grad-buf-for-mxfp8-param-ag and --overlap-param-gather, a hybrid MoE model trained with Muon separated from its offload-free twin by ~1 nat after 32 steps, and CP1 vs CP2 runs of the same recipe split systematically at step 2 (max |dlm_loss| 0.159 over 32 steps, vanishing with the offload disabled). A small MoE GPT reproduces it on 4 GPUs within 1-2 steps.

* DistributedDataParallel.reset_param_sync_dispatch_state(skip_layer_wise=...) leaves LayerWise-managed bucket groups alone; DistributedOptimizer._copy_main_params_to_param_buffer uses it, since it only re-stages its own buckets.
* _ParamAndGradBucketGroup.finish_param_sync no longer warns about a next bucket whose synchronous gather already completed (force_sync leaves dispatched=True, handle=None).
* fp8_utils._stage_param_to_bf16 raises instead of silently staging from a CPU-resident master; MegatronOptimizer.prepare_model_params_for_param_sync restores offloaded masters so the eval/checkpoint force_param_sync path stays valid.
* Tests: MoE + expert-DP {1,N} + chunked offload {1 MiB, full window} bitwise parity against the plain step, including the dequantized MXFP8 weights; DistOpt staging keeps the LayerWise dispatch state; staging from a CPU master raises.

- hxbai · comment · 2026-09-16T05:44:55Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/7392#discussion_r4022857514)

File: `megatron/core/fp8_utils.py` · line 348

[P2] Handle the aligned VPP gather path as well

Preserving param_gather_dispatched fixes the forward pre-hook path, but the aligned VPP schedule can still re-dispatch these buckets. With Muon + FP8 param gather + chunked offload, VPP enabled, and DP > 1, train_step force-syncs the LayerWise buckets and then offloads their masters. The interleaved schedule subsequently invokes config.param_sync_func, which calls DDP.start_param_sync() without checking param_gather_dispatched. This launches another LayerWise staging pass and reaches the new CPU-master error here.

Could we also make the aligned scheduling path skip LayerWise buckets already force-synced for the current iteration, while preserving explicit force_sync behavior? A regression test with PP=2, VP=2, DP=2 and align_param_gather=True would cover this; the added tests use PP=1 and therefore miss this entry point.
