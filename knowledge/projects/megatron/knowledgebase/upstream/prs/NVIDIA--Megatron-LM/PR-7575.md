# fix: correct partial activation offload during warmup and backward

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7575) · state: closed · merged: True

## Original PR description

## What does this PR do?

This PR fixes partial activation offload in two places: it respects the configured fraction during warmup and prevents activations from being reloaded too early during backward.

With partial offload, some groups' activations are moved to CPU while others stay on GPU. Backward still processes every group, in reverse order. Previously, the reload schedule contained only the offloaded groups, but advanced after every backward group. Processing a GPU-resident group therefore triggered a reload for an earlier group, even though its activations were not needed yet. Several such groups could bring many activations back to GPU early and increase peak memory.

For a simple example, forward runs **A → B → C → D**. A and B are offloaded; C and D remain on GPU. Backward runs **D → C → B → A**:

| After backward of | Without fix: reload | With fix: reload |
| --- | --- | --- |
| D | B | None — C is already on GPU |
| C | A | B |
| B | None | A |

Before B's backward begins, the old code has already restored both A and B. With the fix, only B has been restored; A stays on CPU until B finishes.

The fix keeps GPU-resident groups in the reload schedule as steps that require no copy. Reload then follows the actual backward order, avoiding the buildup of activations waiting to be used.

Warmup also previously ignored the fraction and offloaded every eligible group. Reducing the fraction therefore did not reduce the CPU buffers allocated during warmup, which remained in the pool afterward. The fix applies the fraction as groups are discovered: after `k` eligible groups, at most `ceil(k * fraction)` are offloaded. The existing post-warmup policy still avoids offloading the last group and selects the steady-state groups. No explicit cache cleanup is needed.

Ports the reload fix from #5101 to main and fixes the warmup allocation issue.

## Validation

### Backward GPU memory

Ran a synthetic CUDA chain of 17 groups, each saving a 32 MiB activation, with `activation_offload_fraction=0.5`. Eight groups were offloaded. Compared main `626fe3a10` with the reload fix `cd7bb4de2` on the same GPU, with three measured iterations after warmup.

Both versions started backward at **352 MiB**.

| Measurement | Without fix | With fix |
| --- | ---: | ---: |
| Peak reloaded activations waiting to be used | 256 MiB | 32 MiB |
| Peak GPU memory during backward | 448 MiB | 416 MiB |

![Backward memory comparison with and without the fix](https://raw.githubusercontent.com/lhb8125/Megatron-LM/71e4f0d3f84de5189eeda11913a65c6ce7db7512/pr7575/backward-memory.png)

Left: reloaded activations waiting to be used. Right: peak CUDA allocation reached so far during backward.

Without the fix, unused reloaded activations grew from 32 to 256 MiB. With the fix, only one 32 MiB group was prefetched at a time. The measured backward peak fell by **32 MiB (7.1%)**, consistently across all three iterations.

The **224 MiB** reduction on the left does not translate directly into total peak savings. Backward also frees activations as groups finish, so some early reloads occupy memory that has just been released. Total GPU memory includes other live tensors and backward temporaries, and its peak need not coincide with the peak of waiting activations. The left plot shows that reload buildup is eliminated; the right shows the actual **32 MiB** peak reduction for this workload.

GPU peaks were measured with `torch.cuda.max_memory_allocated()`, reset immediately before backward.

### Host memory during warmup

Reused the same 17 × 32 MiB chain with fraction=0.5, comparing before the warmup fix (`cd7bb4de2`) with after (`e7a804fec`). Each version ran in two fresh processes on the same GPU, with one warmup and three steady iterations.

![Pinned host memory before and after the warmup fix](https://raw.githubusercontent.com/lhb8125/Megatron-LM/722466b571526a340f60c65da1c2ab544563257f/pr7575/host-memory.png)

Warmup allocated **17 CPU buffers before the fix and 9 afterward**. Actual pinned host memory, including cached buffers, fell from **544 MiB to 288 MiB**: a **256 MiB (47.1%)** reduction. Both pools then stayed constant across the three steady iterations, with no explicit cache cleanup. The fixed pool retains 9 buffers, of which 8 are used in steady state.

Process RSS measurements independently showed approximately **256 MiB less growth**, after establishing a baseline with CUDA/NCCL initialization complete. Outputs and gradients matched, and the peak of reloaded activations waiting to be used remained **32 MiB**.

Good catch, thanks! Fixed this margin case in 82c06cb7e. Here is the scheduling change in more detail.

Let `N0/C0` and `N1/C1` denote the norm/core-attention groups in two successive layers. With fraction 1.0, `N0` and `C0` are offloaded, while the post-warmup margin keeps `N1` and `C1` on GPU. More precisely, the margin reserves the last group of each module name.

As you pointed out, norm commits after the attention residual addition. The resulting orders are:

```text
Forward group starts:         N0 -> C0 -> N1 -> C1
Forward group commits:        C0 -> N0 -> C1 -> N1
Backward activation consumers: C1 -> N1 -> C0 -> N0
```

Previously in this PR, all four groups entered the reload queue in commit order: `[C0, N0, C1, N1]`, consumed from the right. Without an initial `pre_reload_last_layer()`, completing C1 backward consumed N1's resident slot; completing N1 backward then consumed C1's already-used slot. Neither step launched a copy, so C0 had to reload through `tensor_pop()` on the compute stream. The existing check that removes the just-completed group from the queue did not help, because the queue's top was the other group at each step.

The fix records margin membership separately as `is_offload_margin` and excludes those groups from the reload queue. Their autograd markers remain active and still trigger prefetches after their internal backward completes. The queue in this example is therefore `[C0, N0]`:

| Backward progress | Before this fix | After this fix |
| --- | --- | --- |
| C1 finishes | Consume resident N1 slot; no copy | Prefetch N0 on the H2D stream |
| N1 finishes | Consume already-used C1 slot; no copy | Prefetch C0 on the H2D stream |
| C0 needs its saved tensors | Compute-stream fallback reload | Use the prefetched tensors after the existing reload-event wait |

This restores the original prefetch behavior at the margin boundary. It is a targeted fix for margin handling; the queue still uses commit order, so N0 is prefetched before C0 in this example.

Only margin-reserved groups are excluded. Groups kept resident by the fraction or PP-rank delta policy still retain their no-copy slots, which are needed to prevent the early reload buildup this PR addresses. Warmup has no reserved margin yet, so it also retains its slots.

I added a regression test that constructs the delayed norm commit and checks outputs/gradients, queue membership, and that reloads run on the H2D stream without a compute-stream fallback. It covers fractions 0.5 and 1.0, with and without an initial pre-reload, and both repeated norm/attention pairs and the `[N0, C0, N1, N2, N3]` sequence. The existing partial-offload accumulation test is retained. GPU validation is still pending.
