# [Test][Inference] Independent oracles for MoE routing, permutation and metadata kernels

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8967) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Adds independent oracle tests for the inference MoE routing kernels: the per-expert token counts, the NVLS step metadata, and the permutation they drive. They live in `tests/unit_tests/inference/oracles/moe_routing/`. No production code changes.

**Stacked on the oracle harness PR #8966 (`test/inference-oracle-harness`)**, which adds the shared helpers these tests use. Retarget to `main` once it merges.

## Why

These kernels decide which rows every expert GEMM sees. Their existing tests leave gaps:
- **`valid`.** The count kernels are tested only with `valid == rows`. Nothing tests `valid > rows`, which MTP forwards produce on `main` (audit finding F1, fixed by #8563).
- **CUDA graphs.** No test captures `permute_tokens` or `unpermute_tokens` in a CUDA graph and replays it with a smaller `valid` or `n_used`. Nothing checks that stale rows past `n_used` are never written.
- **NVLS metadata.** The step metadata (`valid`, the rank offset and the max) is never asserted. An oversized `valid` only adds wasted work, so the end-to-end tests pass with it. The kernel is never run on more than one group shape.
- **Vacuous checks.** The vLLM-backend end-to-end checks that exercise these kernels compare at `atol = 5e-2` on outputs of about 1e-2.

## The oracles

Each module's docstring holds the kernel's contract. It was written from the launcher's documented API and its callers before the kernel body was read. Every integer and routing output is checked exactly.

- **Count kernels** (`_count_local_tokens_kernel` and its persistent variant): a CPU `torch.bincount` of the live pairs, `t < min(valid, rows)`, on the local slice.
  - Every routing map is the head of a larger buffer whose tail routes to a local expert, so any read past the map's rows changes a count.
  - The output is checked in a launcher-allocated buffer and in a caller-zeroed buffer between guard bands.
  - Metamorphic: the persistent kernel's counts do not depend on the SM count (`_NUM_SMS` monkeypatched), and every CUDA-graph replay matches the bincount at that replay's `valid`.
- **NVLS metadata** (`_fused_metadata_kernel`): an NCCL `all_gather_into_tensor` of every rank's count on the same group, combined on the host into `[sum, prefix, max]`.
  - It runs on every power-of-two group of an 8-GPU world (sizes 2, 4 and 8, contiguous and strided), with guard bands on `step_metadata` and a canary after the symmetric slots.
  - End to end, the dispatcher's own metadata, AGV and RSV sequence runs for six steps with changing per-rank counts and nothing in between. Each step is then checked against NCCL gathers: the metadata (and its `valid` alias), every rank's AGV rows at its offset, and the RSV output (exact: power-of-two multiples of bf16).
- **Prefix sum**: a Python aligned running sum.
- **Init map**: the definition on a guarded, poisoned buffer.
- **Permute and zero padding**: per expert block, the multiset of `(token, prob bits)` against a Python grouping of the live pairs. Then each claimed row must equal `hidden[token]` bitwise. Padding rows hold `-1` (and zeros with `zero_padding`), and the inverse map points at the row holding each pair. Outputs are allocated poisoned (PyTorch's `fill_uninitialized_memory`), so rows past `n_used` must stay poisoned.
- **Unpermute and zero output**:
  - dyadic inputs make every product and sum exact in fp32 in any atomic order, so the result must equal an fp64 per-token sum bit for bit;
  - random bf16 inputs are bounded by torch's fp32 `index_add_` on the same device (harness policy, factor 2);
  - output rows past `valid` must stay untouched;
  - stale rows past `n_used` point at live tokens with large values and must not be read.

## What it covers

- **Count kernels.**
  - `rows * topk` and `valid * topk` just below, at and just above one and two 1024-pair blocks, plus 0 and 1;
  - `valid` in {0, 1, rows-1, rows};
  - pairwise: `E_l` {1, 2, 7, 16, 32, 128} × first / second / last slice (so `start` 0, 1 and 16 occur) × top-k {1, 2, 6, 8, 16} × int64 / int32 maps × live rows;
  - ids at the slice edges and `-1`, all pairs on one expert, duplicates within a token;
  - production shapes: Nemotron-3 Nano EP1 prefill, DeepSeek-V3 EP8 AGV height and EP64 decode (`E_l = 4 < topk`);
  - for the persistent variant, `num_sms` in {1, 2, blocks-1, blocks, blocks+1, 132, 1000}.
- **Metadata.**
  - counts 0, 1 and 16, which hit Triton's value specialisations, and mixed counts;
  - a tied maximum, one active rank, and a sum of exactly 2³¹ − 1;
  - four graph-baked buckets replayed in shuffled order, with the metadata re-poisoned before each replay;
  - the dispatcher sequence at expert TP 1 (EP 8) and expert TP 2 (EP 4).
- **Permute.**
  - pairwise over: H {1, 33, 1023, 1024, 1025, 2688, 4096} (one and two 1024 tiles) × top-k {1, 2, 6, 8} × `E_l` {1, 2, 7, 32} × slice × alignment {1, 16, 32, 128} × row alignment {1, 128} × inverse map × zero padding × dtypes (bf16/fp32 hidden, fp32/bf16 probs) × `valid` (including masked CUDA-graph padding rows);
  - `rows * topk` at the 512-program grid cap;
  - production shapes with H 2688 and 7168, non-BI and BI flags;
  - CUDA-graph replay: the map keeps the previous step's entries past the new `n_used`, and they must not change;
  - the zero-padding kernel launched directly on bf16 rows and on FP8 rows as bytes (the MXFP8 launch), with stale `-1` entries past `n_used`.
- **Unpermute.**
  - pairwise over H × `num_tokens` and `output_size` at 511/512/513 × `valid` × up to 1, 2 or 8 rows per token (three or more race in the atomics) × stale tail × launcher-allocated or caller-provided output;
  - `n_used = 0`;
  - production shapes, including the NVLS `global_max` height;
  - CUDA-graph replay of the fixed-buffer (RSV) form with `n_used` and `valid` changing.
- **Prefix sum.** `E_l` around powers of two (1 to 129, and 256) × alignments {1, 2, 8, 16, 32, 64, 128, 256} × counts 0, 1, a−1, a, a+1, random, and aligned sums of 2³¹ − 1.
- **int32 limits** (`large`, opt-in, one case per process; 16–34 GiB each):
  - live pair counts of 2³¹ − 1024, 2³¹ − 8 and 2³¹ for both count kernels;
  - maps of more than 2³¹ entries behind a 2³¹-entry front guard in the same allocation, for
    the count and init-map kernels' block offsets; a wrapped offset then hits the guard and
    fails an assertion instead of faulting;
  - inverse-map offsets `tok * E_l + lid` past 2³¹;
  - hidden rows read and permuted rows written of width 7168 whose element offsets reach 2³¹
    (permute), and expert and output rows that do (unpermute). In the permute case every real
    token is claimed, so the highest permuted row written sits at the fits / crosses /
    row-starts-past boundary.
- **Memory.** One `sanitizer` case per module.

`routing_reference.py` holds the shared references and input builders.

The single-GPU modules run on any CUDA device. Without one, they run on the CPU under `TRITON_INTERPRET=1`. The metadata module needs Hopper or newer with NVLink multicast and a power-of-two world (`torch.distributed.run`, 8 ranks in CI). With `MCORE_ORACLE_TARGET_SM` set, a missing GPU or missing multicast fails these tests instead of skipping them.

Checked on CPU with the Triton interpreter:
- **On `main`:** 807 passed and 8 failed. The failures are the F1 cases below. 38 cases do not run on CPU: CUDA graphs, production shapes, NVLS and `large`.
- **With #8563's `permute.py`:** all 815 pass.
- **Interpreter shim.** The zero-padding, zero-output and unpermute kernels call `.to()` on a loop index, which the interpreter does not support. They ran on a scratch copy where `row.to(tl.int64)` became `tl.full([], row, tl.int64)`. The kernels in this branch are unchanged.
- **Hand mutants.** 15 mutants of the kernel source were run against these tests. 14 are detected. The survivor (`tok < valid` → `tok <= valid` in the permute loop) is equivalent, because the loop already bounds `tok < valid`. One more mutant, the zero-padding loop ignoring `n_used`, first survived and is now detected by the direct zero-padding test.

The H100 runs (1 GPU and 8 GPUs) are pending.

### Expected to fail on `main`

Finding F1: in MTP forwards on `main`, `valid` exceeds the routing-map rows.
- **Count kernels.** The non-persistent kernel reads up to the end of its last 1024-pair block past the map. The persistent kernel reads `(valid - rows) * topk` entries past it.
- **Permute.** It clamps to `rows`, so offsets and placements disagree.

These tests fail on `main` and pass with #8563, which bounds both count kernels by the routing-map rows:
- `test_count_local_tokens_kernel.py::test_valid_above_rows_counts_only_the_map_rows` (3 cases);
- `test_count_local_tokens_kernel_persistent.py::test_valid_above_rows_counts_only_the_map_rows` (3 cases);
- `test_count_local_tokens_kernel_persistent.py::test_valid_above_rows_in_cuda_graph_replay`;
- `test_permute_tokens_kernel.py::test_valid_above_rows_permutes_only_the_map_rows` (2 cases).

They also fail on this branch until #8563 merges. Merge #8563 first, or stack this PR on it.

Six `large` cases are expected to fail on `main` and with #8563 alike. They pin int32 wraps that need at least 64× the largest production routing map:
- **The pair count `valid * topk`.**
  - `test_int32_pair_count[count-wraps]` in both count modules. Confirmed on H100: every count is 0 at 2³¹ pairs.
  - `[cdiv-wraps]` of the persistent kernel, whose `cdiv` adds 1023 first.
- **The block offsets `pid * 1024`.** `test_int32_block_offsets` of the non-persistent count and init-map kernels. On H100 the unguarded case faulted with an illegal memory access.
- **The inverse-map offset `tok * E_l + lid`.** `test_int32_inverse_map_offsets`.

The other large cases are expected to pass.

## Notes for reviewers

- **Poisoned outputs.** `permute_tokens` and `unpermute_tokens` allocate their outputs internally. To poison them, the tests run each launcher call with `torch.use_deterministic_algorithms(True, warn_only=True)` and `fill_uninitialized_memory`, scoped to that call and restored afterwards. Then NaN or `INT32_MAX` marks every element the kernels did not write.
- **NVLS groups.** The metadata module creates five subgroup families, each with its own 1 MiB symmetric buffer. It calls `fused_metadata_update` directly, outside the dispatcher. The dispatcher test re-initialises model parallel at EP 8, and at EP 4 × expert TP 2.
- **Order of calls.** In the kernel-level tests, consecutive metadata calls on one buffer are separated by the NCCL reference gather. The kernel needs an inter-rank barrier between calls. In the dispatcher test, nothing but the dispatcher's own AGV and RSV separates the steps, as in production.
- **Determinism.** No kernel or dispatch changes, so there is no determinism test or manifest entry.
