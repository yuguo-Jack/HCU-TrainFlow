# Refuse MoE grouped-tensor execution on cuBLASLt with the grouped GEMM bug

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8618) · state: open · merged: False

## Original PR description

# What does this PR do?

Makes `TEGroupedMLP` fail fast when MoE GroupedTensor execution (`moe_use_grouped_tensor=True`, also turned on by `use_transformer_engine_op_fuser`) would run on a cuBLASLt grouped GEMM known to corrupt outputs.

## Problem

cuBLASLt from 13.7.0 up to (not including) 13.8.1 can leave rows of a grouped GEMM output unwritten on Blackwell and Rubin GPUs. The [cuBLAS 13.8.1 patch notes](https://docs.nvidia.com/cuda/cublas-patch-release-notes/#cublas-patch-release-13-8-1) list the fix: grouped GEMM "could produce incorrect results on Blackwell and Rubin GPUs", introduced in 13.7.0. With `moe_use_grouped_tensor=True`, every expert GEMM goes through this path, so the experts silently read stale memory.

We hit this on GB200 with an NGC image that ships cuBLAS 13.7.0.27 (Nemotron 3 Nano MoE, HybridEP):
- intermittent grad-norm spikes (1,000-12,600) and occasional NaN loss at step 1, only with `--moe-use-grouped-tensor`;
- with TE's GEMM outputs filled with NaN instead of `torch.empty`, every run hit a NaN within 3-11 steps. Each traced case was an fc1 forward grouped GEMM with clean inputs and correct split sizes whose output kept NaN in exactly 32 rows of one expert segment;
- a single-GPU repro without Megatron (TE `GroupedLinear(use_grouped_tensor=True)`, the same inputs on every call) leaves 32 rows unwritten in roughly 0.1-0.5% of forward calls.

TE 2.20.2 prints a one-time warning at the first grouped GEMM (`cuBLAS version 130700 has a grouped GEMM bug that may cause data corruption`), but it is easy to miss in a training log, and we missed it.

## Change

- `megatron/core/transformer/moe/experts.py`: new `_check_cublaslt_grouped_gemm_version()`. It is called from `TEGroupedMLP.__init__` after the GTP split-quantize fallback has decided whether grouped-tensor execution is actually used. It raises `RuntimeError` when all of these hold:
  - the current GPU is SM100-SM110 (`torch.cuda.get_device_capability()`);
  - the cuBLASLt loaded at run time (`transformer_engine_torch.get_cublasLt_version()`, i.e. `cublasLtGetVersion()`) is in `[130700, 130801)`, the same range TE warns on.
- Escape hatch: `MCORE_ALLOW_BUGGY_CUBLAS_GROUPED_GEMM=1` downgrades the error to a warning, for example to reproduce the bug or to benchmark.
- The check runs at run time, not in `TransformerConfig`, because config validation cannot see the device or the loaded library.

Example error:

```
RuntimeError: cuBLASLt 13.7.0 grouped GEMM can leave output rows unwritten on Blackwell and Rubin GPUs (this GPU is SM100), which silently corrupts MoE expert outputs with moe_use_grouped_tensor=True (also enabled by use_transformer_engine_op_fuser). Upgrade cuBLAS to 13.8.1 or newer, or disable both options. Set MCORE_ALLOW_BUGGY_CUBLAS_GROUPED_GEMM=1 to downgrade this error to a warning.
```

CI impact: none expected. The dev CI image already installs cuBLAS 13.8.1.7 (#7685), and the LTS image (25.09) predates 13.7.0. Hopper is unaffected.

## Tests

In `tests/unit_tests/transformer/moe/test_grouped_mlp.py`. They mock `torch.cuda.is_available`, `torch.cuda.get_device_capability` and `transformer_engine_torch.get_cublasLt_version`, so no GPU kernels run:
- error on SM100/103/110 with cuBLASLt 13.7.0, 13.7.5 and 13.8.0;
- no error or warning for 13.6.4, 13.8.1 and 13.9.0 on SM100, or for 13.7.0 on SM90 and SM120;
- warning instead of error with `MCORE_ALLOW_BUGGY_CUBLAS_GROUPED_GEMM=1`;
- `TEGroupedMLP` construction raises with grouped tensor, and skips the check when the GTP split-quantize fallback turns grouped tensor off.

Ran locally on CPU torch: the 16 new tests and the existing GTP/paged-stash construction tests pass (22 tests). black, isort, ruff and pylint are clean.
