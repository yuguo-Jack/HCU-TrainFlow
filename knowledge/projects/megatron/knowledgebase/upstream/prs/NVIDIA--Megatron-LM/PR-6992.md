# What does this PR do?
Preserves evaluation semantics after a training CUDA graph has been captured.

  Capture a separate validation graph instead of replaying a graph captured with training and grad mode enabled. This
  prevents capture-time Python branches and buffer mutations, such as MoE router token-count
  accumulation, from being replayed during validation.

Light review. The eager-eval fallback and the tests look right for the standard `evaluate()` path, but the new gate is broader than the PR description and docs claim, and it silently turns off graph replay for two paths that intentionally relied on it.

**1. RL reference-logprob path loses training-graph replay**

`megatron/rl/rl_utils.py:2177-2180` deliberately enters eval + `no_grad` *specifically so it can replay the training graph*. Its own comment says so: "Avoid self.training checks which will trigger cudagraph capture; this path reuses the forward pass from training after it has been captured on the 1st iteration." It then calls `model.eval()` followed by `get_logprobs(..., no_grad=True)`.

Under the new gate this call has `module_is_training=False`, `torch.is_grad_enabled()=False`, `is_in_checkpoint_fwd=False`, and is neither `is_inference_mode` nor `_inline_capture` — so `can_replay_training_graph` is False and it falls back to eager. Replaying here is the point of `--rl-training-cuda-graphs`: when that flag is off, `rl_utils.py:2285-2289` already deletes `cudagraph_manager` via `toggle_cuda_graphs`, so the manager only survives at this call site when the user explicitly asked for replay.

This is a silent perf regression rather than a correctness one, which makes it easy to miss in CI. Worth either exempting this path explicitly (e.g. an opt-in flag on the manager, similar to `_inline_capture`) or confirming the RL owners are fine with the slowdown.

**2. `--freeze-all-layers` training also falls back**

`_forward_backward_grad_context()` (`megatron/training/training.py:2349-2360`) runs a *training* step under `torch.no_grad()` with the model still in `train()` mode. That gives `module_is_training=True`, `grad_enabled=False` -> `can_replay_training_graph` False -> eager. Previously this replayed.

That may well be the desired outcome, but it means the doc paragraph is narrower than the code:

> A graph captured during training is not replayed by standard evaluation under `model.eval()` with autograd disabled.

The actual condition is "the module is not in training mode **or** autograd is disabled (outside a checkpoint-forward)". Suggest rewording so users grepping for why replay stopped can find it, e.g.:

```
A graph captured during training is only replayed while the module is in training mode with
autograd enabled (or during a checkpointed recompute forward). Standard evaluation under
`model.eval()`, and forward-only training with autograd disabled, run eagerly so that
capture-time Python branches and mutable-buffer updates retain their eager semantics.
Explicit inference CUDA graphs remain unaffected.
```

**3. Test coverage gap**

`test_training_graph_falls_back_to_eager_during_evaluation` covers the fallback well (both the wrapped-method and whole-module forms), but nothing asserts the *negative* side of the new gate — that replay is still taken where it should be. A cheap addition to the same class: after `create_cudagraphs()`, run one `train()` + `torch.no_grad()` forward and assert the intended behaviour explicitly, so a future tightening of this condition cannot quietly disable replay for the frozen-teacher and RL cases above.

Light review — traced the new validation capture/replay paths. The design looks sound: the eager fallbacks for pre-capture / shape-mismatch / grad-enabled eval mirror the pre-existing fallbacks, `preserve_model_state` keeps `buffer_backup` and `saved_fp8_tensors` symmetric (and incidentally fixes FP4 being saved but never restored), the fresh `ArgMetadata` inputs carry no `cg_buffer_metadata` so `fwd_buffer_reuse_ref_count` accounting is untouched, and holding detached `outputs` before `_weakref_forward_buffers(False)` correctly keeps output storage owned. Test coverage is good.

One thing worth a look:

**With PP > 1, one validation graph is captured per microbatch runner but only the first is ever replayed.**

`_create_cudagraphs` captures a val graph for *every* grad-enabled runner:

```python
# megatron/core/transformer/cuda_graphs.py:717
for runner in dict.fromkeys(g[0] for g in cls.cudagraph_record):
    if runner.grad_enabled:
        runner.create_val_graph()
```

but the selection in `__call__` scans `self.cudagraph_runners` in order and — deliberately, per the test comment — never rotates the list:

```python
# megatron/core/transformer/cuda_graphs.py:2154
runner = next(
    (r.val_runner for r in self.cudagraph_runners if ...), None
)
```

When `reuse_cudagraphs` is False (`pp.size() > 1`) there is one runner per microbatch, and all of them were recorded from the same training signature, so `get_mismatch_errors` never rejects index 0. The selected runner is therefore always `cudagraph_runners[0].val_runner`, and the remaining `num_microbatches - 1` validation graphs per graphed module are captured, hold their output buffers strongly for the life of the run, and are never replayed.

Correctness looks fine — the forward-only schedules send each stage output before the next microbatch's forward, so a single shared val graph per module is safe — so this is purely wasted capture time and pool memory, scaling with `num_microbatches × num_graphed_layers`.

Since the capture loop lives on `_CudagraphGlobalRecord` and has no manager grouping, the cheap fix is probably to skip runners that would produce a duplicate val graph, e.g.:

```python
# Backwards have released the training activations, so validation can reuse their pool.
# Validation replay never rotates `cudagraph_runners`, so it always selects the first
# runner's graph; capturing one per microbatch would only waste pool memory.
captured_val_keys = set()
for runner in dict.fromkeys(g[0] for g in cls.cudagraph_record):
    key = (id(runner.base_module), runner.func)
    if runner.grad_enabled and key not in captured_val_keys:
        captured_val_keys.add(key)
        runner.create_val_graph()
```

(keying on `runner.func` as well as the module matters for the method-wrapped form, where two managers can share one `base_module` under different `function_name`s.)

Alternatively, if the per-microbatch graphs are intentional as headroom for a future rotating validation path, a comment saying so would help — the `PP creates one runner per microbatch` test comment currently reads as if all of them are exercised, and `test_separate_evaluation_graphs` asserts over every entry of `val_runners` without distinguishing the one that actually replays.
