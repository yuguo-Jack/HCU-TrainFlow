# What does this PR do?

Fix an overly restrictive check that excluded every non-delayed FP8 recipe (MXFP8, blockwise) from the precision-aware optimizer path, even when the model parameters stay BF16 (fp8_param_gather=False). That forced an MCore-managed FP32 copy of the main params and gradients, so FP8 compute used more optimizer memory than plain BF16.

Only quantized (FP8) parameters need MCore-managed masters. With BF16 params, TE FusedAdam can own the masters and write the params in-kernel, as in normal BF16 training. This adds OptimizerConfig.fp8_param_gather and keeps the precision-aware path when it is False.

approved with only nits, @kunlunl to sanity check and understand the complexity here:

- We store a new field in the checkpoint SD to identify if the optimizer state main parameters are FP32 or INT16 remainders.
  - **_We should not have saved two different types of checkpoint data completely controlled by internal logic not exposed to the saved checkpoint, making this technical debt the moment we need to improve the logic._**
  - We have legacy checkpointing logic when `store_param_remainders=None` (default) so that if older checkpoints without the new remainder flag are ingested, we have backwards compatibility where using the PAO was synonymous with (and thus implies that this checkpoint has data with...) store_param_remainders=True.
    - BF16 weights in this case was not using the PAO for the MXFP8/NVFP4 quantized compute case, so it would store FP32 state, and thus in this case we would make sure to verify our MCore flags are also set to store_param_remainders=False (after resolving our new logic).
- New perf case is now supported where BF16 model weights and quantized (MXFP8/NVFP4) compute can now be used with the PAO (main weights + decoupled grad) and `store_param_remainders=True` for FP32 main weights, giving us our optimizer state memory back in this specific case.
  - Originally, this combination of arguments would just invalidate the PAO and use MCore-managed FP32 weights without any option to use remainders in the optimizer state.
  - Now:
    - If the user does not specify `--store-param-remainders`, then we default to the legacy logic for remainders, which still does FP32 main weights but now managed by TE PAO / FusedAdam.
      - If the user asks for it, of course. This is a good behavior change since the PAO would just be randomly turned off and you would have no idea why, this is one such case that will no longer randomly turn it off.
      - We set `store_param_remainders=False` but still use the PAO through the new BF16 / non-fp8-ag path.
    - If the user specifies it to True or False, we adhere to that.
    - Check against the loaded checkpoint (using the saved flag or legacy logic as a fall-back) to make sure they agree on logic.

[Update] AI breakdown to sanity-check my own analysis:

## Old logic (`main`)

TE keeps the masters when `main_params_dtype != fp32` or `fp8_recipe in {None, "delayed"}` or `optimizer_cpu_offload`.

| main params dtype | FP8 recipe | Parameters | CPU offload | Master owner | `"param"` in checkpoint |
|---|---|---|---|---|---|
| BF16/FP16 | any | any | any | TE | BF16/FP16 (TE keeps no remainders here)* |
| FP32 | `None` | BF16 | no | TE | `int16` remainders by default, FP32 if `store_param_remainders=False` |
| FP32 | `delayed` | BF16 | no | TE | same as above |
| FP32 | `delayed` | FP8 (`fp8_param_gather`) | no | TE | should be same as above as FP8 model params will generate BF16 grads and state |
| FP32 | non-delayed | any | yes | `HybridDeviceOptimizer` | its `master_param`, stored under `"param"`; not traced further |
| FP32 | non-delayed | BF16 | no | Megatron Core | FP32 |
| FP32 | non-delayed | FP8 | no | Megatron Core | FP32 |

\* There's a quirk on `main` independent of this PR. When the template is built before any optimizer step, `distrib_optimizer.py` line 1128 allocates `int16` whenever `store_param_remainders and bf16`, without checking `main_params_dtype`. TE stores a BF16 master in this row, so the template and the real state disagree.

## New logic (this PR)

The PR adds `or not self.fp8_param_gather`, a new `OptimizerConfig.fp8_param_gather` defaulting to `False`, and a consistency check in `distrib_optimizer.py`.

| main params dtype | FP8 recipe | DDP `fp8_param_gather` | Optimizer `fp8_param_gather` | Master owner | `"param"` in checkpoint |
|---|---|---|---|---|---|
| BF16/FP16 | any | any | any | TE | unchanged |
| FP32 | `None` / `delayed` | any | any | TE | unchanged (`int16` by default for BF16 parameters) |
| FP32 | non-delayed, with offload | any | any | `HybridDeviceOptimizer` | unchanged |
| **FP32** | **non-delayed** | **False (BF16 parameters)** | **False** | **TE (new)** | **`int16` remainders by default, previously FP32** |
| FP32 | non-delayed | True (FP8 parameters) | True | Megatron Core | FP32, unchanged |
| FP32 | non-delayed | True | False (the default) | — | `ValueError` from the new check† |
| FP32 | non-delayed | False | True | Megatron Core | FP32; works but misses the memory saving† |

## Problems with the newly enabled row

1. **Checkpoints stop loading.** An old checkpoint for that configuration has FP32 `"param"`. After the PR, TE's `set_scaled_state` asserts `int16` for that key, and the template at line 1128 allocates `int16` too. This is @kunlunl's DP-zero restore concern, and it covers the other checkpoint formats as well.
2. **`--optimizer-cuda-graph` fails at startup.** That flag is passed to TE as `capturable=True`, and TE raises `"Capturable mode doesn't support storing param remainders"`. This configuration used to get past initialization because TE didn't keep the masters (@guihong-nv).
3. **Parameter-norm logging drops BF16 weights.** `main_param=None` with `main_param_sharded=True` makes `_get_param_data` skip them, so an all-BF16 model reports a norm of zero (@guihong-nv).

The plan @cspades posted on Oct 14 forces `store_param_remainders=False` for the newly enabled row. That fixes the first two: TE keeps a full FP32 `master_param`, so `"param"` is FP32 with the same shape as before, and capturable mode no longer conflicts. The parameter-norm issue and the second-config-flag issue need separate fixes. For the flag, @guihong-nv suggested deriving `fp8_param_gather` from the DDP config instead of adding an optimizer-config flag that defaults to `False`.

Overview of what ended up making up this PR:

**Added**

_Precision-aware optimizer (PAO) with BF16 params_
- PAO works with BF16 params: TE owns the FP32 master weights.
- `OptimizerConfig.fp8_param_gather` is derived from the DDP config instead of being set by hand.
- The conditions for when TE owns the master weights are defined once, in one helper.
- `--[no-]store-param-remainders` flag (tri-state: unset, on, off). It only takes effect with BF16 params and FP32 main params.
- Checkpoints record whether they hold param remainders (`param_state_param_remainders`).
- Loading a checkpoint whose remainders setting doesn't match the run raises an error.
- Checkpoints from before this PR have their format inferred, so mismatches are still caught.

_Main param API_
- `DistributedOptimizer.get_main_param_shard(model_param)`: one way to read a param's FP32 master-weight shard on this rank, whether MCore or TE owns it. Returns `None` if this rank holds no shard.
- `ChainedOptimizer` and the module-level optimizer wrapper forward `get_main_param_shard` to their inner optimizers.
- `calc_params_l2_norm(..., main_param_getter=None)` takes the getter, including on the MIMO path. The training loop passes `optimizer.get_main_param_shard`.

**Fixed**
- The param norm was zero for BF16 params with PAO. It now uses the exact FP32 master weights.
- Param remainders are turned off with the optimizer CUDA graph.
- Param remainders are turned off under Megatron-FSDP.
- With FP16 main params, remainders are no longer assumed (TE never stores them there), so checkpoint loading no longer builds an `int16` slot for a param TE keeps in FP16. This was a quirk on `main`.
- The docs and the `--store-param-remainders` help text match the new behaviour.
