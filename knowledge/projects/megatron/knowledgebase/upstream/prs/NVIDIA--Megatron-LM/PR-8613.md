# Hook DDP into backward_dw when expert wgrad overlap delays wgrad

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8613) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Fixes wrong expert gradients with `--overlap-dispatch-backward-with-experts-wgrad` under Megatron DDP: DDP now registers its expert grad hooks where the delayed wgrad actually fires (`backward_dw()`), as it already does for `--delay-wgrad-compute`.

### Bug

`--overlap-dispatch-backward-with-experts-wgrad` makes TE's grouped expert linears delay their weight gradient to `backward_dw()`:

- `TEGroupedLinear.delay_wgrad_compute` is `config.delay_wgrad_compute or config.overlap_dispatch_backward_with_experts_wgrad` (`megatron/core/extensions/transformer_engine.py`).
- TE marks those weights with `skip_backward_post_hook`, and `backward_dw()` fires the hooks registered through `register_wgrad_accumulation_and_reduce_hooks`.

`DistributedDataParallel.__init__` registers its grad hook on the module (so it fires from `backward_dw()`) only when `ddp_config.delay_wgrad_compute` is set. Otherwise it hooks autograd's `AccumulateGrad`. `get_megatron_ddp_config` copied only `--delay-wgrad-compute` into `ddp_config.delay_wgrad_compute`, so with the overlap option alone (the two options are mutually exclusive) DDP hooked autograd for the expert weights. As a result:

- `param.grad` of the expert weights is never cleared.
- The stale gradient is added to `main_grad` again in the next iteration.

This is the failure that the comment in `TEGroupedMLP.backward_dw` (`megatron/core/transformer/moe/experts.py`) describes for the fused path. With this option, DDP never registers the module hooks in the first place.

### Measured symptom

Nemotron 3 Nano (hybrid Mamba + MoE), 2 GB200 nodes, EP 8, HybridEP flex dispatcher:

- Every run with the option has a different grad norm from iteration 2 on: 26.06 instead of 22.33. Iteration 1 matches, as expected for a gradient carried over from the previous step.
- This includes a run on unmodified `main` (26.03 vs 22.20).
- One run hit a NaN grad norm at iteration 1, then ran out of memory in iteration 2 (NaN routing inflates HybridEP's buffers).

### Fix

In `get_megatron_ddp_config`, set `ddp_config.delay_wgrad_compute` when either `--delay-wgrad-compute` or `--overlap-dispatch-backward-with-experts-wgrad` is enabled, so DDP's hook placement matches `TEGroupedLinear.delay_wgrad_compute`.

With the fix, grad norms match the run without the option: 21.974, 22.326, 35.15-35.19 and 38.2-38.3 for iterations 1-4, the same spread as two runs without the option. These runs were on a branch that also carries other, unrelated MoE changes that are not part of this PR.

Unaffected paths:

- `ddp_config.delay_wgrad_compute` is read only by `DistributedDataParallel`'s hook registration.
- Megatron-FSDP handles the option separately (`setup_delayed_wgrad_acc_hook`) and does not read this field.
- Torch FSDP2 returns its own config before this code.

### Test

New parametrized unit test `TestPretrainContainerFromArgsStructure::test_ddp_hooks_follow_delayed_expert_wgrad` in `tests/unit_tests/test_argument_utils.py`. It parses each flag set with the real argument parser and checks `get_megatron_ddp_config(...).delay_wgrad_compute`:

- no flag: `False`
- `--delay-wgrad-compute`: `True`
- `--overlap-dispatch-backward-with-experts-wgrad`: `True` (returned `False` before this fix)

It passes in the CI container.

### Known follow-up (out of scope)

`validate_args` checks a few requirements of the delayed-wgrad DDP path only for `--delay-wgrad-compute` (TE >= 2.8.0 with `--overlap-grad-reduce`, and the CUDA-graph conditions). They are not applied to `--overlap-dispatch-backward-with-experts-wgrad`, which only asserts TE >= 2.3.0 in `TransformerConfig`. This PR leaves the validation unchanged.
