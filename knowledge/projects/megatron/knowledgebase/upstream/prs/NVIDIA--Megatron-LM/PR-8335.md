# What does this PR do?

With context parallelism, running a shorter sequence after a longer one can reuse the wrong YaRN positions and change the model's output. The cache contains positions already split between CP ranks. For CP2 rank 0, length 64 caches positions `0…15, 48…63`, but length 32 needs `0…7, 24…31`. Taking a prefix of the old cache gives the wrong positions.

Rebuild the cache when a non-packed sequence shrinks with CP > 1. CP1 and packed inputs can still reuse the cache.

<details>
<summary>Reproduction and validation</summary>

Base: `ce852bfb93f364f64a556602fc71a5d9ed2c377e`.

With the repository's CUDA test dependencies installed, run:

```bash
python -m torch.distributed.run --standalone --nproc_per_node=1 -m pytest -q \
  tests/unit_tests/fusions/test_mla_yarn_rope_apply.py \
  -k 'test_yarn_cache_with_shorter_sequence or TestApplyRotaryPosEmbTHD'
```

Results: 13 passed in 0.67 seconds. With the original cache method, the two non-packed CP2 cases fail; the four CP1 and packed cases pass. The new test compares cached cos/sin against direct computation across lengths 64 → 32 → 64 → 16 and checks cache reuse for CP1 and packed inputs.

I also checked a small BF16 HybridModel with MLA, CP2, `apply_rope_fusion=True`, and public text inputs. After a longer forward, the shorter forward differed from a fresh model with identical weights by up to `0.00390625` in logits. With the fix, logits and log-probabilities matched exactly on both ranks. This exercises the experimental MLA RoPE fusion training path, without an inference context.

Autoformat and determinism coverage passed. Mypy reports the same two errors on the base and this branch: the return type of `yarn_find_correction_range` and missing Triton type declarations.
