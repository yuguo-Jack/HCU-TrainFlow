# Add full_recompute_input to fine-grained activation offloading

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8300) · state: open · merged: False

## Original PR description

# What does this PR do?

Adds `"full_recompute_input"` to `offload_modules`: with full activation recompute, each checkpoint's hidden-states input is moved to host memory through the existing fine-grained activation offloading manager and reloaded right before that checkpoint is recomputed in backward.

## Why it is needed

With `recompute_granularity="full"`, `checkpointed_forward` runs each layer (or each chunk of `recompute_num_layers` layers) under `no_grad` inside `CheckpointFunction`. The only tensors autograd keeps across the forward are the checkpoint inputs that `CheckpointFunction.forward` passes to `ctx.save_for_backward`. The large one is the hidden-states input, one per checkpoint. It stays on the GPU from the moment the checkpoint runs in forward until backward reaches that layer, and nothing reads it in between. Its size scales with sequence length times hidden size times the number of checkpointed layers on the rank, so at long context these inputs are one of the largest terms in peak memory once recompute has removed everything else.

Megatron's existing offloading features do not cover these tensors:

- `cpu_offloading` (TE layer-level offload) rejects any recompute: `TransformerConfig.__post_init__` raises "CPU offloading does not work when activation recomputation is enabled".
- `fine_grained_activation_offloading` offloads the inputs of submodules (`attn_norm`, `core_attn`, `expert_fc1`, ...) by opening an offload group around them. Under full recompute those submodules run inside the checkpoint's `no_grad` forward, so they save nothing and their groups offload nothing. The checkpoint's own `save_for_backward` happens outside every group.

## The change

This extends fine-grained activation offloading instead of adding a separate mechanism:

- `checkpointed_forward` (shared by `TransformerBlock` and `HybridStack`) wraps each checkpoint call in `FineGrainedActivationOffloadingInterface(..., "full_recompute_input")` and commits the group on the checkpoint output with `group_offload`. The saved-tensor hooks of `PipelineOffloadManager` then catch the checkpoint's `save_for_backward`. The input is copied to host on the manager's D2H stream after the checkpoint's forward, and the copy runs while the next chunk's forward executes. In backward, the group's commit node runs just before `CheckpointFunction.backward` and waits for the reload, and the group's start node issues the reload of the previous chunk's input.
- The other checkpoint arguments (attention mask, rotary embeddings, context, padding mask, token IDs) are the same tensors for every chunk. Copying them would free no GPU memory, so they are marked with `mark_not_offload` and stay on device.
- Everything else comes from the existing manager unchanged: the pinned host tensor pool reused across iterations, keeping on GPU the group that backward needs first, PP/VPP chunk handling, `min_offloaded_tensor_size`, `activation_offload_fraction` and `delta_offload_bytes_across_pp_ranks`.
- Validation in `TransformerConfig`: `"full_recompute_input"` requires `recompute_granularity="full"` and cannot be combined with other `offload_modules`. Those modules run inside the checkpointed region, where their groups would open in the `no_grad` forward and again in the recompute during backward. With `recompute_method="block"`, only the checkpointed layers are offloaded.
- Off by default. Usage:

  ```bash
  --recompute-granularity full --recompute-method uniform --recompute-num-layers 1
  --fine-grained-activation-offloading --offload-modules full_recompute_input
  ```

- `docs/user-guide/features/fine_grained_activation_offloading.md` gains the new module in the module table and a "Combining with Full Recomputation" section.

## Alternatives considered

- **Wrap `checkpointed_forward` in `torch.autograd.graph.save_on_cpu`.** This is how SkyRL ships it today, as a monkeypatch ([NovaSky-AI/SkyRL#2412](https://github.com/NovaSky-AI/SkyRL/pull/2412)). It is a few lines, but it offloads every saved checkpoint argument (including the shared RoPE and mask tensors, once per layer), copies on the compute stream, has no prefetch, and allocates pinned memory through PyTorch's caching host allocator on every step. SkyRL had to add an explicit `torch._C._host_emptyCache()` after each step to keep that cache from holding the host RAM the CPU optimizer needed. It would also be a second, parallel offload mechanism next to fine-grained offloading.
- **A separate boolean such as `offload_full_recompute_inputs`.** This reads more directly, but it would duplicate the fine-grained offloading settings (minimum size, fraction, PP balancing, warmup) or leave them unused. An `offload_modules` entry reuses all of them.
- **Offloading inside `CheckpointFunction` itself.** This would also catch checkpoints that are not layer-level, such as MTP's own `_checkpointed_forward` and `CheckpointWithoutOutput`. Those already interact with fine-grained offloading in different ways, so this PR keeps the change at the block-level call site.

## Scope and limitations

- Covers `checkpointed_forward` in `megatron/core/recompute.py`, which is used by `TransformerBlock` and `HybridStack`. MTP layers have their own `_checkpointed_forward` and are not covered.
- Host memory: each offloaded input takes the same number of bytes in pinned host memory, per microbatch in flight. The pool reuses buffers across iterations, so this is a standing host allocation.
- Offloading needs the TE CPU-offload module, the same requirement as the existing fine-grained offload modules.

## Test plan

- New CPU test `test_full_recompute_input_offloads_only_checkpoint_hidden_states` in `tests/unit_tests/pipeline_parallel/test_fine_grained_activation_offloading.py`, parametrized over `uniform`/1, `uniform`/2 and `block`/3 on a 4-layer toy block. It runs the real `checkpointed_forward`. The offload interface is replaced by a recorder that keeps host copies, and the checkpoint is replaced by torch's reentrant checkpoint, which saves inputs with `save_for_backward` like `CheckpointFunction`. It checks that:
  - each checkpoint opens one `full_recompute_input` group;
  - exactly the checkpoint's hidden-states input is offloaded, while the mask and RoPE tensors are saved inside the group but kept on device;
  - the group is committed;
  - outputs and all gradients, computed from the offloaded copies, match the run without offloading;
  - no group opens when the option is off.
  With this change: 3 passed. Without the `recompute.py` change: all 3 fail (`assert 0 == 4` and similar, no groups opened).
- New CPU config tests in `tests/unit_tests/transformer/test_transformer_config.py`: the option is accepted with full recompute, rejected with no or selective recompute, and rejected when combined with another offload module. 4 passed.
- Both files on a CPU-only run (`CUDA_VISIBLE_DEVICES=""`): 69 passed, 35 skipped (CUDA required).
- New GPU test `test_gpt_full_recompute_input_offloading_correctness_and_memory` (8-layer GPTModel with TE, full recompute, uniform/1): checks that logits and grads match the run without offloading, that offloaded bytes are non-zero, and that peak memory is lower. **Not run for this PR.** `_build_gpt_model` gains a `full_recompute` flag for it, and existing callers are unchanged.
- black, isort, pylint and ruff (versions pinned in `pyproject.toml`) are clean on the changed files.

## Validation (SkyRL)

The same tensors have been offloaded in SkyRL with the `save_on_cpu` monkeypatch described above ([NovaSky-AI/SkyRL#2412](https://github.com/NovaSky-AI/SkyRL/pull/2412)), so these numbers come from that implementation, not from this PR's code path. The memory effect should carry over, because the same tensors leave the GPU. The step-time numbers will not transfer directly, because the copy paths differ. All step times were measured in SkyRL with a per-step `torch.cuda.empty_cache()` enabled.

Full GLM-5.3-Flash, 64 B200, full recompute:

| Setting | Peak memory per GPU | Step time |
|---|---|---|
| 256k tokens, no offload | 142 GiB | 84 s |
| 256k tokens, offload (pinned) | 98 GiB | 102 s |
| 256k tokens, offload (pageable) | — | 130 s |
| 512k tokens, TP8, no offload | OOM | — |
| 512k tokens, TP8, offload | fits | — |

- With offload, 384k tokens per sequence ran at 126.8 GiB per GPU, against 141.5 GiB at 256k without it.
- 4-layer GLM-5.3-Flash slice, 1 node, 32k tokens, 3 steps: loss over steps 0..2 was 12.780 / 12.777 / 12.767 without offload, and 12.778 / 12.775 / 12.766 with pinned offload. That is within run-to-run random-init noise (~0.017).
