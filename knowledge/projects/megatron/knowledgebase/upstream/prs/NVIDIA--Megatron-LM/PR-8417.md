# What does this PR do?

The LOC of this PR is not really large because it's stacked on a previous one, this PR needs https://github.com/NVIDIA/Megatron-LM/pull/8210 to be merged first to land the basic infra code for adding MegaMoE.

Currently we need to modify `dist_moe` interface a little: https://github.com/zhongbozhu/dist_moe/tree/mcore-integration which might not be the best idea so we will see if there are ways to remove/reduce that.

Toggles:
```
# This env var has been removed by TE, only older TE needs it 
export NVTE_GROUPED_LINEAR_SINGLE_PARAM=1

--moe-megakernel-backend dist_moe \
--moe-grouped-gemm \
--moe-use-grouped-tensor \
--moe-single-grouped-weight \

# mxfp8 
--fp8-format e4m3 \
--fp8-recipe mxfp8 \
--fp8-param-gather \
--reuse-grad-buf-for-mxfp8-param-ag
```

About MXFP8 recipe: 

Dist-MoE’s native **32×32 weight quantization** lets forward and dgrad share one FP8 payload. TE’s MXFP8 recipe instead produces independently quantized **1D rowwise and columnwise payloads**.

I kept TE’s existing recipe, Dist-MoE’s GEMMs accept TE’s 1D MXFP8 operands because native 2D scales are expanded into the same hardware layout; that's why I have to currently change `dist_moe` API a little and bring in TE’s separate forward/dgrad FP8 payloads, repacks only the scales, and caches the imported weights across microbatches, normally refreshing on the first microbatch of each optimizer step.

- With **FP8 parameters**, the adapter directly aliases TE’s rowwise/columnwise weight buffers.
- With **BF16 parameters**, it uses TE’s `MXFP8Quantizer` and `group_quantize`, caching the resulting workspace across microbatches.
- It converts only the scale layout, then passes both orientations through the new Dist-MoE `import_block_scaled_weight()` API.

Thus Dist-MoE consumes TE’s quantized weights without applying its native 2D quantization. This preserves TE’s weight-quantization semantics and avoids a BF16 shadow for FP8 parameters.
