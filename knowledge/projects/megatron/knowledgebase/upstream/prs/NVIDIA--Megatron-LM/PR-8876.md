# [Inference][MoE] Key MoE lockstep and bounded-row decisions on the replicas sharing tp_ep

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8876) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Fixes three bugs that share one cause. #4743 moved the inference MoE collectives to the expert tensor-and-model-parallel (`tp_ep`) group. The decisions that keep the ranks of that group consistent still read `expert_model_parallel_size`:

1. **Silent corruption with mixed phases (any ETP).** The bounded FlashInfer MXFP8/NVFP4 rows (`inference_flashinfer_mxfp8_token_capacity`) were enabled from each rank's own decode-only phase. A decode-only rank computed and wrote only the first `capacity` rows of the NVLS all-gather. A prefilling peer's tokens past those rows then got the bounded rank's stale reduce-scatter rows instead of its expert outputs. The NVLS dispatcher has no per-step agreement.
2. **Silent corruption with ETP > TP, even when every rank decodes.** The bound was `max_requests * (spec + 1) * EP`, but the all-gather over `tp_ep` holds the decode tokens of `ETP * EP / TP` data-parallel replicas. With TP 1, ETP 2, EP 2, `max_requests` 64 and capacity 128, the bound allowed 128 rows while 256 were gathered, so rows [128, 256) were never computed.
3. **Hang with ETP > TP, EP = 1 and MoE MTP layers.** Three paths skipped the MTP MoE collectives because `expert_model_parallel_size <= 1`: an idle rank's dummy step (`_run_dummy_serial_mtp_forward`), the async primer and the idle async base step. Their active `tp_ep` peer issued them, so the collectives mis-paired and the engine hung. The no-coordinator guard (`_llm_base.py`) and the reserved recurrent-state dummy slot had the same gap.

All three were reproduced on GPU: (1) and (2) with the real NVLS dispatcher and FlashInfer kernels on 4 GB200, (3) on 2 H100.

## Fix

- **One helper.** `get_moe_dp_replica_count(config)` (`megatron/core/inference/utils.py`) counts the data-parallel replicas whose tokens the MoE collectives gather: `ETP * EP / TP`, at least 1. TP is the innermost dimension of both the attention and the expert rank layouts, so `tp_ep` lies inside one attention TP group when its size divides TP, and is made of whole TP groups when TP divides it.
  - Other layouts (e.g. TP 4 with EP 3: the `tp_ep` group of ranks 3-5 holds parts of two TP groups) are rejected when the inference context or `MegatronLLM` is built. The ranks of one TP group would sit in different `tp_ep` groups, whose engine consensus is separate, so they could take different dummy-step decisions and mismatch their TP collectives. They need non-power-of-two EP or TP.
- **Lockstep gates.** These now key on the replica count instead of EP: the dummy MTP forward, the async primer's dummy MTP, the idle async base step and the coordinator requirement of `MegatronLLM`. The reserved dummy recurrent-state slot keys on `tp_ep` having peers, because the engine's consensus spans `tp_ep`.
  - The coordinator check reads `model.config` instead of the global `parallel_state`.
  - Changed behavior: it now rejects direct mode for ETP > TP. It no longer rejects EP groups that lie inside one TP group (e.g. TP 2, EP 2, ETP 1), which serve a single replica.
- **Bound.** The context sizes the bounded rows for every replica's decode tokens: `replicas * max_requests * (spec + 1) <= capacity`.
- **Agreement on the launched phase.** With more than one replica, the context uses the bounded rows only in steps that every replica agrees are decode-only.
  - Each step, before its first MoE collective, every `tp_ep` rank announces whether the forward it launches is decode-only, through `DynamicInferenceContext.agree_on_moe_decode_only()`. The vote travels over the engine's existing `tp_ep` ZMQ communicator, on the CPU, with no GPU kernel or host sync. The controller votes at its step entry and in `dummy_forward()`; `initialize_attention_state()` consumes the result.
  - The vote cannot wait until admission or `initialize_attention_state()`: an async step launches the previous forward's MTP collectives first, and a no-overlap rank waits on them on the host before it admits. A peer that held its own MTP launch until the vote would deadlock it.
  - So each rank must know its phase at step entry. Legacy steps admit before the step. Overlap steps and dummy steps are decode-only. A no-overlap step's update turns every request of the pending forward into a decode request, so its forward is decode-only unless it admits prefill; a primer launches the context's requests as they are.
  - While the agreement is active, a no-overlap step therefore admits prefill only when an entry probe allows it; otherwise it admits only decode-ready KV imports. The probe reads the counts the step's update will leave (`DynamicInferenceContext.counts_after_update()`: no request finishes, each active request continues as one decode row), not the pending forward's, so a prompt that fits once a prefill turns into decode rows is admitted in the next step as before. A chunked prefill in flight always counts as admitting prefill, so consecutive chunks run in consecutive steps. Only a prompt that fits solely because a request finishes in that same update waits one step. A paused request, too little KV to prepare, a KV import, the first decode after a prefill and a decode-only primer all vote decode-only, and the vote matches the launched forward.
  - `initialize_attention_state()` raises if this rank's batch has prefill rows in a step that every replica, this one included, agreed was decode-only. The check compares host integers, so it adds no device sync.
  - Without the agreement, admission is unchanged.
  - Without the communicator (no coordinator), a multi-replica group never bounds its rows.
  - The controller's forward takes the per-step flag from the context.
- **CUDA graphs on both paths.** A captured graph fixes whether its FlashInfer kernels process only the bounded rows, so CUDA graph keys now include that flag (`DynamicInferenceContext.cuda_graph_key`, used by `CudaGraphManager` for dynamic batching).
  - A single-replica decode-only graph is captured bounded, as before. With more than one replica, decode-only graphs are captured unbounded when the engine is built and bounded too once `start_listening_to_data_parallel_coordinator()` attaches the `tp_ep` communicator, which makes the agreement possible. Without the coordinator, no bounded graph is captured.
  - MTP draft forwards always run bounded when decode rows fit (`DynamicInferenceContext.mtp_draft_moe_rows_bounded`, set around each draft forward with `InferenceMode.bounded_mxfp8_rows`). A draft forward's rows, at most one per request on each rank, always fit, so this holds in every step, whether or not the replicas agreed on the base forward. The MTP commit pass, whose rows can be a prompt's, keeps the base forward's flag. MTP graph keys carry the flag (`mtp_cuda_graph_key`), so each draft size has one graph, captured at construction, on every layout.
  - A decode-only rank whose peer prefills replays its unbounded decode graph; nothing falls back to eager.
  - Cost: only with bounded rows, more than one replica and the coordinator, every decode-only base graph is captured twice, the second set at coordinator start; `engine.capture_stats` reports both passes. Each extra graph keeps its output buffers in the CUDA graph pool, about tokens x hidden_size x 2 bytes per decode graph (bf16), e.g. 14.7 MB for a 1024-token graph at hidden 7168, so on the order of 100-250 MB for a typical list of 16-32 decode sizes up to that graph; the engine logs each graph's pool growth, which the GPU run reports. MTP draft graphs are not doubled on any layout.
- **Dummy steps keep the context's requests.** An idle EP dummy step can run while the context holds requests but none is active: paused requests, or a chunked prefill hidden between chunks. `add_dummy_requests_for_expert_parallel_step()` now sets aside their counts and the rows it overwrites, and `end_expert_parallel_dummy_step()` restores them instead of resetting the context, which dropped them and freed their KV blocks; a hidden chunk's next chunk then ran on a block table of -1. This was reachable on `main` when a continuing chunk could not get a KV block.
- **A step that launches nothing still meets its peers.** With more than one replica, every peer launches a forward or a dummy step in each step. A step with work that launches no forward (nothing admitted, or a kept chunk that cannot continue yet; async overlap or primer path, or legacy) now runs a dummy step after its vote instead of returning, so its peers' MoE collectives never wait on it. On `main` such a step issued no collectives.
- **No dummy-step GPU sync.** The coordinator loop no longer synchronizes the device after each dummy forward. That wait made an idle rank cast vote N+1 only after forward N ended, holding every active rank's prepare and launch of forward N+1 until then. `dummy_forward()` now waits for its previous dummy forward's event after its vote and before restaging the host buffers, which keeps it at most one forward ahead and lets it reach vote N+1 once forward N-1 has ended, before the active ranks do.
- **Cost of the vote.** It is spent only when bounded rows are configured and fit, the group spans more than one replica, and the coordinator runs. In the all-active steady state it is one blocking `sync_all_reduce_max` of one integer per step: each rank pushes its vote to the `tp_ep` leader, which publishes the maximum, i.e. two small TCP messages, tens of microseconds within a node, plus the wait for the slowest replica to reach its step entry. It runs at step entry while forward N is still on the GPU, so it lengthens a step only when the slowest rank's CPU work for the step (resolve, vote, prepare, launch) already exceeds the forward's GPU time.

## Follow-up (review round 3)

- MTP draft forwards run bounded whenever decode rows fit, on every layout, so each draft size has one CUDA graph again (round 2 captured two per size, also on single-replica layouts); no MTP graph is captured at coordinator start, so the KV-aware MTP capture on a reset context the review asked to test no longer happens.
- A step with work that launches no forward runs a dummy step when the tp_ep group spans more than one replica, instead of leaving its peers' MoE collectives waiting (the stuck kept-chunk hang).
- `TestAsyncSchedulePhaseAgreement` now turns the vote on (agreement flag and a single-rank communicator), so the context's vote-versus-launch check runs on every step, records every launch against its step's vote, and adds a paused-request run. New CPU tests cover the no-forward dummy step and the draft and commit-pass bounds; the engine capture test checks one bounded MTP graph per size and none at coordinator start.
- `megatron/core/inference/utils.py` keeps `main`'s typing import, so it no longer conflicts with #8873.
- Not done: an MTP case in the real-engine tests (their model forward is stubbed, and the MTP path needs real hidden states), and a GPU replay of a bounded MTP graph (the bounded FlashInfer kernels are SM100-only; the H100 MTP graph tests exercise the keys unbounded).
- At this head, on H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), the regression tests pass (102 cases on 1 GPU, 17 on 2) and fail on main (73 cases on 1 GPU; on 2 GPUs the test module fails at import on main); the neighbor tests pass. On GB200 (aarch64 image) the Blackwell regression test passes (12 cases on 4 GPUs) and fails on main (12).

## Follow-up (review round 4)

- The MTP commit pass no longer reads `InferenceMode`'s bounded-row flag, which holds whatever the last forward set. The controller records the bound when a step launches its base forward (`_base_forward_bounded_moe_rows`; a CUDA graph capture does not record it). The commit pass and an idle rank's dummy commit forward run under that bound. Before, a capture left the flag at the last captured variant, and an engine resume reset it to False.
  - Reachability: a capture resets the context, so the next step discards a forward that was pending across it. The case that could happen was a PERSIST or static-pointer resume. There the commit pass of the pending forward ran unbounded, which is correct but slower.
- New tests, 1 GPU each:
  - `test_mtp_kv_cache_controller.py::TestExpertParallelForwardParity::test_commit_pass_keeps_its_base_forward_bound_after_a_graph_capture` covers the real and dummy commit passes after a capture that flips the flag. It fails on the previous head.
  - `test_dynamic_engine_async_sched.py::TestAsyncSchedulePhaseAgreement::test_step_that_cannot_continue_its_chunk_runs_a_dummy_step` runs a real engine and refuses a chunk's continuation for two steps. The second step launches nothing and runs the dummy step, unmocked. The test checks that the hidden chunk is set aside for the dummy row and given back, that the dummy launch binds to the step's decode-only vote, and that the trace matches the run without the agreement.
  - The CPU controller forward test also checks the recorded bound.
- Not run on GPU yet.
