# Start a chunked prefill only when its whole prompt fits

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8790) · state: open · merged: False

## Original PR description

## What does this PR do?

With chunked prefill enabled, the dynamic engine can stop making progress
under KV-cache pressure, and `generate()` never returns.
`_can_schedule_chunked_prefill()` lets a new request start a chunked
prefill when the KV cache has room for one prompt token. A long prompt can
therefore start, take the last free blocks, and then wait for one more
block. A partial chunked prefill keeps its blocks until it finishes and is
never preempted. Requests decoding beside it then pause for want of a
block. If they hold no more blocks than the paused-block budget, nothing is
evicted, and neither the partial prefill nor the paused requests can ever
move.

This PR restores the earlier admission rule: a new chunked prefill starts
only when KV for its whole remaining prompt is available. A continuation
still needs KV for one more token, and the scheduler's per-chunk
availability check is unchanged. The long request now waits in the queue
until enough blocks are free for its whole prompt.

## Example failure scenario(s)

**Scenario (partial prefill takes the last blocks)**
- The engine has 9 usable 8-token KV blocks, a 32-token step budget, and a
  3-block paused budget. Request A decodes in 1 block.
- Request B arrives with a 67-token prompt, which needs 9 blocks, and starts
  a chunked prefill although only 8 blocks are free.
- B's first two chunks take all 8 free blocks, leaving 5 prompt tokens that
  need a ninth block.
- A fills its block, needs a second, and is paused while holding 1 block,
  within the paused budget.
- No block is ever freed, so every later step does nothing and both
  requests stay unfinished.

## How was this bug discovered?

A stateful search drove the real engine through generated sequences of
submissions, steps, suspends, resumes, aborts and drains, with a synthetic
model that makes every output known. After every step, the search checks
that some unfinished request makes progress. Three of seven seeds on
current `main` found steps where nothing progressed: one request was paused
and a partial chunked prefill waited at the queue head with no free block.
The same shrunk histories pass on `main` from October 28. Per-step state
dumps showed the sequence above. The admission probe changed from the
whole remaining prompt to one token in the prompt-score sidecar change
(#7063), which reached `main` through #8426.

## Scope

- Production: `megatron/core/inference/engines/dynamic_engine.py`,
  `_can_schedule_chunked_prefill()` only (+9/−3).
- Tests (+107):
  - `test_chunked_prefill_schedule_characterization.py`:
    `test_chunked_prefill_starts_only_when_whole_prompt_fits`, with the
    real context and allocator. With one free block, a new 12-token request
    waits, while a continuation still schedules its next 4-token chunk.
  - `test_dynamic_engine.py`: `test_chunked_prefill_waits_for_whole_prompt_kv`,
    the scenario above end to end with a zero-logit model forward. Both
    requests must finish.
- No functional-test, config or API change. Continuation chunks and the
  per-chunk check are unchanged.
- A side effect is intended: the async overlap decision uses the same probe,
  so it again overlaps while a new long prompt waits for KV.
