# Reject GTP weight remat in Megatron-FSDP v1

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8725) · state: closed · merged: False

## Original PR description

**Why.** GTP weight rematerialization gives each rank of a GTP group a different shard of a weight, and only Megatron DDP handles it. Megatron-FSDP v1 shards and reduces parameters over one data-parallel group with no GTP handling, so neither group it can pick is correct:
- Without a `pg_collection`, the adapter takes the GTP-inclusive group from `parallel_state`. Construction succeeds, and FSDP shards and reduces across ranks that hold different GTP shards as if they were replicas.
- With the grid's collection, it takes the replicate `dp_cp`, and mesh construction fails with an opaque einops shape error.

Training rejects the combination only through conflicting `--ckpt-format` requirements. Direct Megatron Core users, such as Megatron-Bridge, reach the adapter unguarded.

**What.** `FullyShardedDataParallelV1.__init__` raises `ValueError` when `gtp_weight_remat_size` or `expert_gtp_weight_remat_size` is above 1, or when the collection's `gtp_remat` or `expt_gtp_remat` group spans more than one rank. The check reads only the config and the collection, so it adds no `parallel_state` reads.

**Tests.** New `tests/unit_tests/distributed/mfsdp_v1/test_mfsdp_gtp_weight_remat.py`:
- dense and expert GTP set in the config, on a GTP grid;
- GTP groups in the collection, with every `parallel_state` accessor patched to raise;
- a collection with single-rank GTP groups, which still constructs.

Before the sync, on 4 GPUs against main: no regressions, the 4 reject cases fail on main and pass here, and all 5 pass. Two other tests in the run fail on main and here alike.

In the integration run (main 77391e71cc with all #6307 PRs merged, against main), this PR's test files show no regressions: the new file passes 5 of 5 tests on 4 GPUs, and main has no such file.

**Compatibility.** No change without GTP, for DDP or for Megatron-FSDP v2. Megatron-FSDP v1 with GTP now fails at construction with a clear message.
- Expert GTP > 1 is rejected even for a dense model, matching how training and DDP treat GTP as active. Should the expert axis be checked only when `num_moe_experts` is set?
- The message names the derived fields `gtp_weight_remat_size` and `expert_gtp_weight_remat_size`, while users set `--tensor-parallel-num-weight-shards` and `--expert-tensor-parallel-num-weight-shards`. Should it name those flags instead?
- Layers decide GTP sharding from the group size in `resolve_gtp_remat_group`, not from the config. Two inconsistent setups still pass the check and use the GTP-inclusive group, as on main: a global grid with `gtp_remat_size > 1` under a config with GTP off and no collection, and a collection without the GTP fields. Catching them would take a global read.
- Megatron-FSDP v2 with GTP and TorchFSDP2 with GTP are out of scope.
- Merges cleanly with #8051, which also edits this adapter.
