# fix(inference): run coordinator-mode shutdown once with complete teardown

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8595) · state: open · merged: False

## Original PR description

## What does this PR do?

Shutting down `MegatronLLM` / `MegatronAsyncLLM` in coordinator mode had several gaps:

- **Early return:** a second async caller of `shutdown()` returned before teardown had finished.
- **Leaked runtime:** a cancelled caller could leave the runtime thread running.
- **Skipped cleanup:**
  - If the stop or coordinator-shutdown step failed, `InferenceClient.stop()` was never called.
  - If the frontend stop failed, coordinator teardown was skipped.
- **Calls after shutdown:** calls made after shutdown were still accepted and reached a stopped event loop.
- **Fake success:** `InferenceClient.stop()` ended open streams as if they had completed normally.

This PR makes shutdown run once, with one shared outcome:

- **One shared result:** every caller, including concurrent callers and callers on different event loops, waits for the same completion and sees the same result.
- **Complete teardown:** teardown keeps going after a failed step: it stops the frontend, pauses and stops the engines, shuts down the coordinator and stops the client. It then reports the first error once the runtime thread has been joined.
- **Calls after shutdown:** `generate`, `pause`, `unpause`, `suspend`, `resume`, `serve`, `submit` and `run_sync` raise "This Megatron LLM instance has been shut down".
- **Client stop:** `InferenceClient.stop()` fails open streams with `InferenceRequestAborted("Inference client stopped")` and clears its remaining request bookkeeping.

As on `main`, calling the synchronous `shutdown()` from the runtime's own event loop raises an error.

## Example failure scenario(s)

**Scenario 1 (second async caller returns early)**

- Caller A starts `await llm.shutdown()`.
- Caller B calls `await llm.shutdown()` while A's teardown is still running.
- Before this fix, B returned immediately and could continue while the engine was still stopping.
- With this fix, B waits for the same teardown as A and receives the same result.

**Scenario 2 (failed coordinator shutdown leaves the client open)**

- During teardown, `shutdown_coordinator()` raises because the coordinator has already exited.
- Before this fix, `client.stop()` was skipped, leaving the client's sockets and tasks open.
- With this fix, `client.stop()` still runs, and the coordinator error is raised afterwards.

**Scenario 3 (generate after shutdown)**

- A caller finishes `llm.shutdown()`.
- The caller then calls `llm.generate(...)`.
- Before this fix, the request was submitted to a stopped runtime loop.
- With this fix, `generate` immediately raises "This Megatron LLM instance has been shut down".

**Scenario 4 (stopped client reports an empty success)**

- Request A is streaming when `InferenceClient.stop()` is called.
- Before this fix, A's stream ended with no items, which looked like a successful empty completion.
- With this fix, A's stream raises `InferenceRequestAborted("Inference client stopped")`.

## How was this bug discovered?

Unit tests drive shutdown with mocked runtimes, clients and engines and check exactly what teardown ran and what each caller observed. On `main` the tests see:

- a concurrent caller that returns before teardown completes;
- teardown steps awaited zero times after an earlier failure;
- `client.stop()` never called;
- a stopped stream that yields nothing instead of raising.

## Dependency and scope

This PR is independent and based on `main`. Production changes are in `apis/_llm_base.py`, `apis/async_llm.py`, `apis/llm.py` and `InferenceClient.stop()`.

The regressions are nine new tests in `high_level_api/test_apis.py` and a new `test_client_stop_releases_request_bookkeeping`. The existing `test_client_stop_terminates_open_streams` changes only its final check: it expected the stopped stream to end with no items, which is the bug, and now expects `InferenceRequestAborted`.

This PR and the following sibling PRs, also based on `main`, edit nearby lines. Whichever merges second needs a small merge-conflict resolution:
- #8594: `test_apis.py`

Three logic errors need correction. I reviewed all six changed files and traced the affected lifecycle, streaming and handoff paths. This was static inspection; I didn't execute tests.

### 1. Don't turn cleared bookkeeping into a source-safe acknowledgement

**Failure:** Submit a KV-handoff stream, call `client.stop()` before receiving a terminal reply or safe ACK, then await `client.abort_request_and_wait(stream.request_id)`. It returns `True`: the newly cleared `_pending_source_requests` makes [abort_request_and_wait](https://github.com/NVIDIA/Megatron-LM/blob/1b234684b1d95be248a82b83b8ef58989142e63c/megatron/core/inference/inference_client.py#L429-L443) treat the request as source-safe. That contradicts the [ownership contract](https://github.com/NVIDIA/Megatron-LM/blob/1b234684b1d95be248a82b83b8ef58989142e63c/megatron/core/inference/inference_client.py#L121-L126): local transport shutdown doesn't prove remote reads have stopped. The [handoff cleanup path](https://github.com/NVIDIA/Megatron-LM/blob/1b234684b1d95be248a82b83b8ef58989142e63c/megatron/inference/integrations/dynamo/llm_engine.py#L589-L592) uses this acknowledgement to authorize source-storage release. This establishes a false acknowledgement, not an executed corruption scenario.

**Correction:** Retain local bookkeeping cleanup, but distinguish a stopped client from acknowledged completion. In [InferenceClient](https://github.com/NVIDIA/Megatron-LM/blob/1b234684b1d95be248a82b83b8ef58989142e63c/megatron/core/inference/inference_client.py#L753-L782), add the following state and guard:

```python
# __init__, alongside request bookkeeping:
self._stopped = False

# stop(), before cancelling or clearing request state:
self._stopped = True

# abort_request_and_wait(), after validating the request ID,
# before looking up or creating an acknowledgement future:
if self._stopped:
    raise RuntimeError("Inference client stopped before source safety could be confirmed")
```

The invariant is that clearing local state must never establish remote source safety.

**Preservation and proposed acceptance checks:** Submit `add_request_with_kv_handoff_streaming([1, 2], SamplingParams(), {"agent": "prefill"}, [10])` with no incoming reply, then stop. All cleared collections should remain empty, but a subsequent safety check must raise rather than return `True` or register another ACK future. Preserve both live-client cases in [test_abort_acknowledges_racing_normal_completion](https://github.com/NVIDIA/Megatron-LM/blob/1b234684b1d95be248a82b83b8ef58989142e63c/tests/unit_tests/inference/test_inference_client.py#L225-L263): completion-before-abort returns `True` without sending ABORT, while abort-before-completion waits for the terminal reply. Preserve the [unsafe-error case](https://github.com/NVIDIA/Megatron-LM/blob/1b234684b1d95be248a82b83b8ef58989142e63c/tests/unit_tests/inference/test_inference_client.py#L196-L208), which must wait for an explicit safe ACK. Open streams must still raise `InferenceRequestAborted("Inference client stopped")`; buffered partials and already completed final results must retain their ordering and delivery.

### 2. Keep the runtime-loop guard in synchronous `wait_for_shutdown`

**Failure:** A coroutine submitted before shutdown can call synchronous `wait_for_shutdown()` while another thread's shutdown is pending. The new [shutdown-started branch](https://github.com/NVIDIA/Megatron-LM/blob/1b234684b1d95be248a82b83b8ef58989142e63c/megatron/core/inference/apis/llm.py#L247-L255) blocks that runtime thread on `shutdown_complete_future.result()`. Teardown still needs the thread, and completion also requires joining it, so neither caller finishes. The [base implementation](https://github.com/NVIDIA/Megatron-LM/blob/259f6a7c27117ea3aca8ca0fa38b33b3a937c026/megatron/core/inference/apis/llm.py#L235-L240) always passed through `run_sync`, whose runtime-loop guard raised instead of deadlocking.

**Correction:** In `MegatronLLM.wait_for_shutdown`, immediately after the direct-mode early return, reject runtime-loop callers before either blocking path:

```python
assert self._loop_manager is not None
try:
    running_loop = asyncio.get_running_loop()
except RuntimeError:
    running_loop = None
if running_loop is not None and running_loop is getattr(self._loop_manager, "_loop", None):
    raise RuntimeError("wait_for_shutdown called from the background loop would deadlock")
```

The invariant is that a synchronous wait cannot block the runtime whose progress or termination it requires.

**Preservation and proposed acceptance checks:** Use a real `_EventLoopManager`, a coordinator-mode test instance marked shutdown-started, and a pending shared completion future. Through the manager, submit a coroutine that calls `wait_for_shutdown`; it must promptly raise `RuntimeError` containing `background loop`. Resolve the test completion future and stop the manager in `finally` so a regression cannot strand the test. Outside the runtime loop, callers must still wait for pending completion and receive its result or exception. Retain the [existing completed-shutdown assertions](https://github.com/NVIDIA/Megatron-LM/blob/1b234684b1d95be248a82b83b8ef58989142e63c/tests/unit_tests/inference/high_level_api/test_apis.py#L309-L326) that waiting doesn't reuse `run_sync`, and keep direct-mode waiting a no-op.

### 3. Reject async shutdown from the runtime loop before waiting for its join

**Failure:** `llm.submit(llm.shutdown()).result()` on `MegatronAsyncLLM` now hangs. The shutdown coroutine runs on the runtime loop and [awaits the shared completion future](https://github.com/NVIDIA/Megatron-LM/blob/1b234684b1d95be248a82b83b8ef58989142e63c/megatron/core/inference/apis/async_llm.py#L179-L183). But [stop_when_complete](https://github.com/NVIDIA/Megatron-LM/blob/1b234684b1d95be248a82b83b8ef58989142e63c/megatron/core/inference/apis/_llm_base.py#L142-L159) resolves that future only after stopping and joining the same loop's thread. Its loop-local wrapper can therefore never resume, leaving the submitted public call unfinished. The previous path raised when attempting to join its current thread; it didn't leave this bridge waiting indefinitely.

**Correction:** Add the same explicit runtime-loop rejection used by synchronous shutdown. At the start of `MegatronAsyncLLM.shutdown`, before acquiring the lock:

```python
if self._use_coordinator:
    assert self._loop_manager is not None
    if asyncio.get_running_loop() is getattr(self._loop_manager, "_loop", None):
        raise RuntimeError("shutdown called from the background loop would deadlock")
```

Don't resolve the shared future before joining as a workaround: external callers must continue to observe completed teardown and thread termination.

**Preservation and proposed acceptance checks:** With a real loop manager and mocked successful teardown, submit `llm.shutdown()` through the public bridge. Its returned future must promptly raise the background-loop error without starting teardown; bound the wait and cancel the submitted future/stop the manager in `finally`. Shutdown from an external event loop must still complete after one runtime stop. Retain the [concurrent-caller assertion](https://github.com/NVIDIA/Megatron-LM/blob/1b234684b1d95be248a82b83b8ef58989142e63c/tests/unit_tests/inference/high_level_api/test_apis.py#L228-L243) that both callers wait, the cross-thread case's single stop, and the [cancelled-caller assertion](https://github.com/NVIDIA/Megatron-LM/blob/1b234684b1d95be248a82b83b8ef58989142e63c/tests/unit_tests/inference/high_level_api/test_apis.py#L280-L295) that cancellation doesn't cancel shared teardown.

All code above is suggested from source reasoning and needs verification before adoption.
