# fix(inference): accumulate the batch-invariant torch MoE combine in fp64 to match training

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8195) · state: closed · merged: True

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Make the torch-backend batch-invariant MoE combine accumulate in fp64, matching training's batch-invariant unpermute, so MXFP8 (and torch-backend BF16) MoE layers give bitwise-identical training and generation outputs on tokens with outlier activations.

## Issue tracking

Linked issue: none. Found while chasing nonzero train/generation KL in the Qwen3-30B-A3B MXFP8 zero-KL RL recipe.

End-to-end verification: [NVIDIA-NeMo/RL#4683](https://github.com/NVIDIA-NeMo/RL/pull/4683) (MXFP8 zero train/generation KL recipe, which needs this fix).

Related: [#6521](https://github.com/NVIDIA/Megatron-LM/pull/6521) (fp64 top-k reduction in the vLLM backend's `_moe_sum`), [#6806](https://github.com/NVIDIA/Megatron-LM/pull/6806) (training-side mirror of that reduction), [#7302](https://github.com/NVIDIA/Megatron-LM/pull/7302) (MXFP8 batch invariance and the parity test extended here).

## The bug

Under batch-invariant mode, training's `unpermute` (`megatron/core/transformer/moe/batch_invariant.py`) mirrors the inference engine's summation tree. When router probabilities are applied before the combine (gated SwiGLU and the batch-invariant squared-ReLU kernels), it sums each EP rank's expert contributions in **fp64**, then rounds the rank partial to fp32 once. That mirrors the vLLM backend's `_moe_sum(acc_fp64=True)` from #6521.

The torch backend's combine, `_unpermute_tokens_in_expert_order_kernel` (`megatron/core/inference/moe/batch_invariant.py`), summed the same contributions in **fp32**, in local-expert-id order. MXFP8 always runs this kernel, including vLLM-backend MXFP8 layers, which fall back to the mcore path.

fp32 is exact only while a token's contributions on a rank span roughly 16 binades. A typical token stays inside that, so both paths agree. An outlier token can have one dominant expert output (about ±31) next to contributions below 2^-20, which fp32 drops and fp64 keeps. Usually that is invisible after the final BF16 rounding. But when the large terms sum to exactly a BF16 halfway point, the dropped tail decides the rounding direction, and training and generation land one BF16 ULP apart.

## Why the existing test did not catch it

`test_batch_invariant_moe_matches_training` covers the right code path (NVLS dispatcher, `mcore_fused_moe`, the batch-invariant combine) with the wrong data:

- the `NANOV3_BASE` toy layer: hidden 128, 8 experts (2 per rank at EP=4), top-6;
- 17 + rank tokens per rank;
- plain `torch.randn` hidden states.

With Gaussian inputs, every token's expert outputs have similar magnitudes, so the fp32 sum is already exact and order-independent. The two accumulators can only diverge on inputs with a heavy-tailed scale.

## Reproduction (fails on `main`)

`test_batch_invariant_mxfp8_moe_matches_training_with_outlier_tokens` reuses the existing parity test with:

- the Qwen3-30B-A3B MoE shape and router: hidden 2048, FFN 768, 128 experts, top-8, softmax;
- 500 + rank tokens per rank;
- outlier inputs: `randn × exp(randn per token) × exp(0.5·randn per channel)`.

On `main` (4 × GB200, EP=4) it fails on rank 1:

```
AssertionError: Tensor-likes are not equal!
Mismatched elements: 5 / 1026048 (0.0%)
Greatest absolute difference: 0.125 at index (457, 0, 685)
Greatest relative difference: 0.00714111328125 at index (457, 0, 1738)
```

Token 457 is an outlier row (input absmax 97.5 against a median row absmax of 10.75). The five elements that differ are its largest outputs, each off by exactly one BF16 ULP:

| column | training | generation |
|---|---|---|
| 333 | −12.125 | −12.0625 |
| 685 | −31.375 | −31.5 |
| 803 | −9.1875 | −9.125 |
| 1738 | −17.5 | −17.375 |
| 1970 | +31.875 | +31.75 |

Localization: a temporary probe (not part of this PR) fed each generation expert kernel's real inputs from this failing forward to its training counterpart. It ran on the real 32 local experts per rank, with training's 32-row padding against generation's 128.
- fc1 quantization, fc1 GEMM, SwiGLU and fc2 GEMM all matched bitwise on all four ranks.
- The fc2 input quantization differed only in the FP8 sign bit, consistent with +0 against −0, and the fc2 GEMM outputs still matched.
- So the experts are identical; the difference came from the combine.

## What changed

- `megatron/core/inference/moe/batch_invariant.py`: `_unpermute_tokens_in_expert_order_kernel` accumulates in fp64 and rounds once to the fp32 rank partial, matching training's `within_rank_fp64` mirror and the vLLM `_moe_sum`. The kernel is batch-invariant-only, so the default path is untouched. Memory traffic is unchanged (BF16 in, fp32 out), and there are at most top-k fp64 adds per element.
- `tests/unit_tests/inference/test_moe_dispatching_and_routing.py`:
  - optional `config_overrides`, `base_local_tokens` and `outlier_tokens` arguments on the parity test (defaults keep every existing case unchanged);
  - the `_QWEN3_30B_A3B_MOE` shape;
  - the outlier-token test above;
  - an NVLS symmetric-buffer reset before allocation. Buffers are cached by name and sized on first use, so a larger-hidden case otherwise fails with `symmetric memory init failed [ep_agv_h, ep_rsv]`.

## Validation

4 × GB200, EP=4:

```bash
python -m torch.distributed.run --nproc-per-node 4 -m pytest -q \
  tests/unit_tests/inference/test_moe_dispatching_and_routing.py \
  -k "batch_invariant_moe_matches_training or outlier_tokens"
```

- Before the fix: the outlier test fails (above); the existing cases pass.
- After the fix: all pass: `vllm`, `vllm-clamped`, `torch-mxfp8-swiglu`, `vllm-mxfp8-swiglu` and the new outlier test. Four cases are skipped by environment (no DeepGEMM BF16 kernels; the grouped-tensor case needs cuBLASLt 13.5.1).
- End to end: the NeMo-RL MXFP8 zero-KL recipe in [NVIDIA-NeMo/RL#4683](https://github.com/NVIDIA-NeMo/RL/pull/4683) runs synchronous GRPO on Qwen3-30B-A3B. It uses Megatron training and non-colocated Megatron generation on the torch MXFP8 backend, with MXFP8 on every TE linear, on GB200 (2 nodes × 4 GPUs). With this fix in its Megatron-LM tree:
  - the all-MXFP8 nightly (job 988940) and an experts-only MXFP8 variant (job 988570) both ran 5 steps;
  - both recorded `train/gen_kl_error` exactly 0 and `train/token_mult_prob_error` exactly 1 on every step;
  - before the fix, the Qwen3-30B-A3B MXFP8 recipe's `gen_kl_error` was nonzero.

  That PR depends on this one.
- Kernel and determinism suites: `test_moe_permute.py` (including `test_batch_invariant_unpermute_is_token_local`) and `test_inference_unpermute_batch_invariant_path_replays` pass (34 passed). `test_inference_default_unpermute_is_the_racy_path` XPASSed; it is the non-batch-invariant negative control and doesn't use the changed kernel.
