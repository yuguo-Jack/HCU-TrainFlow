Status update from the L20 validation side, so this does not stay silent.

I checked the current base (`d564dd01de4549a4884be26b1d74e169798fd877`) and confirmed that
inference ETP is still rejected there:

```python
# megatron/core/transformer/transformer_config.py:1856
if self.expert_tensor_parallel_size > 1:
    raise ValueError(
        "Inference-optimized MoE layers does not support expert tensor parallelism."
    )
```

and that this PR's `tp_ep` plumbing is not present in that base, so I have not branched off
this PR's head and have not taken over its implementation.

Rather than duplicate this PR, I opened #7484 for the design question (which axis the fused
expert weights are sharded along, and where the ETP partial-sum reduction belongs) and #7485
for the part that does not depend on an ETP implementation: dispatcher regression coverage for
zero-local-token ranks, the compact row-order contract, equal/ragged/zero-local transitions on
one live dispatcher, and a pinned capability test for the ETP boundary.

One finding that may be useful here: `dynamic_context` sets
`_use_allgather_v = not using_cuda_graph_this_step()`, so the equal-count path is the
CUDA-graph decode path where equal counts hold by construction, while the ragged path is the
eager prefill path. Feeding unequal counts to the equal-count path is not a reachable state and
hangs rather than returning a wrong answer. If ETP changes which ranks hold which tokens, that
invariant is worth re-checking explicitly.

If you would rather this work continue on top of your branch, or if the sharding axis is
already settled on your side, I am happy to align with it instead -- otherwise no action is
needed from you here.
