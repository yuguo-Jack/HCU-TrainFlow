# What does this PR do?

On the non-compact (pre-SM100) path, _indexer_topk_core materializes the full fp32 score matrix (total_q x max_seqlen_kv) even when callers only need Top-K results. Add scores_output="topk" | "none", which scores query rows in chunks under a 1 GiB budget and keeps only the selected scores. Each chunk reuses the THD kernel path with per-segment q_causal_offsets, so BSHD and THD share one implementation and indices are unchanged. Chunk index, length, and score outputs are allocated once. Sparse indexer loss uses the compact Top-K softmax or the dense-fallback Top-K scores, and raises if neither was produced.

Use it for inference Top-K and for the sparse indexer loss in FusedCSAIndexerSparseAttnFunc; the dense loss keeps the full matrix.

Linked issue: #4468

### Findings
1. **[IMPORTANT Performance]** The chunked loop in [`_indexer_topk_row_chunked`](https://github.com/NVIDIA/Megatron-LM/blob/2d0324378cf9cef196471df18a97c2f2d93bc064/megatron/core/transformer/experimental_attention_variant/csa_utils/fused_sparse_attention.py#L2233-L2262) keeps every per-chunk index and score tensor in lists, then calls `torch.cat` on them. For a moment, the full Top-K indices and scores exist twice, about `2 x total_q x topk x 8` bytes. That is bigger than the 1 GiB score budget once `total_q x topk x 8 > 1 GiB`, which is the long-context case this path is for. Fix: allocate the outputs before the loop and copy each chunk into its rows.
2. **[SUGGESTION Simplification]** With sparse loss, `indexer_scores` is now always `None`. The `prepare_sparse_loss` branch at [L3026-L3037](https://github.com/NVIDIA/Megatron-LM/blob/2d0324378cf9cef196471df18a97c2f2d93bc064/megatron/core/transformer/experimental_attention_variant/csa_utils/fused_sparse_attention.py#L3026-L3037) can no longer run; the only way to reach it is to fail the `assert`. Replace it with an explicit error.
3. **[SUGGESTION Testing]** No test runs the multi-chunk path on real cuDNN kernels. In that path BSHD inputs go through the THD form of the kernel, with made-up `cu_seqlens`, segments that have no query rows, and causal offsets for segments cut mid-sequence. The new tests check this only against the PyTorch stand-in, yet the [new test docstring](https://github.com/NVIDIA/Megatron-LM/blob/2d0324378cf9cef196471df18a97c2f2d93bc064/tests/unit_tests/transformer/experimental_attention_variant/test_csa_indexer_row_chunking.py#L8-L9) says the GPU suite covers it. **[IMPORTANT Performance]** `torch.cat` briefly holds two full copies of the Top-K outputs, which works against this path's memory bound.

**Failure.** Each chunk's `chunk_indices` (int32) and gathered scores (fp32) are appended to `index_chunks` / `score_chunks`. Those lists stay alive until the function returns. L2260-L2262 then allocate a second full-size copy of each.

With `scores_output="topk"` the peak is about `2 x total_q x topk x 8` bytes. The expected peak is `total_q x topk x 8` plus one score chunk of at most 1 GiB. The extra memory appears once `total_q x topk x 8 > 1 GiB`, which is the long-context case this path exists for.

Example: a 1M-row call (the 1M-token case used in `test_chunk_rows_respects_budget_and_alignment`) with `topk=512` has 2 GiB of indices and 2 GiB of scores. The concat peak is about 8 GiB; with preallocation it would be about 5 GiB.

**Correction.** Allocate the outputs before the loop and copy each chunk into its row slice. Drop the three lists and the `torch.cat` calls.

Invariant to restore: at most one copy of the final outputs plus one score chunk are live at any time.

```python
topk_indices = torch.empty((total_q, topk), dtype=torch.int32, device=device)
topk_length = torch.empty((total_q,), dtype=torch.int32, device=device)
topk_scores = (torch.empty((total_q, topk), dtype=torch.float32, device=device)
               if return_topk_scores else None)
for row_start in range(0, total_q, chunk_rows):
    ...  # chunk_cu_q / chunk_offsets / _indexer_topk_core call unchanged
    topk_indices[row_start:row_end].copy_(chunk_indices)
    topk_length[row_start:row_end].copy_(chunk_length)
    if topk_scores is not None:
        topk_scores[row_start:row_end].copy_(_gather_topk_scores(chunk_scores, chunk_indices))
    del chunk_indices, chunk_length, chunk_scores
```

The dtypes already match the inner THD return:
- indices come back as `topk_indices.int()`;
- `sanitize_topk` returns int32 lengths;
- the dense scores are fp32.

**Preservation.**
- The single-pass branch (L2191-L2212) is unchanged.
- Output shapes and dtypes are unchanged: indices `(total_q, topk)` for THD or `(b, sq, topk)` for BSHD, int32 lengths, fp32 scores with `-inf` at `-1` slots.
- `scores_output="none"` still allocates no score output.
- The chunk count still depends only on shapes, so CUDA-graph behaviour is unchanged.

**Acceptance.** These existing tests must pass unchanged:
- `test_bshd_chunked_matches_single_pass`
- `test_thd_chunked_matches_single_pass`, including the padding-row `-1` / `0` asserts
- `test_thd_chunked_matches_independent_reference`
- `test_peak_score_block_is_bounded` (`forward_calls == 16`)

Static invariant: no list accumulation or `torch.cat` of full-size outputs remains in this function.

Optional CUDA test (proposed): use `_force_chunk_rows` and assert that the increase in `torch.cuda.max_memory_allocated()` is at most `total_q*topk*8 + chunk_rows*sk*4` plus slack.

**Failure.** This docstring says the GPU tests in `test_csa_fused_sparse_attention.py` cover kernel numerics, but none of them reaches the multi-chunk branch:
- The real fallback test `TestRealKernelIndexerTopk.test_real_indexer_topk_set_matches_reference` uses b=2, sq=128, sk=128, which is 128 KiB of scores. That is far below the 1 GiB `_CSA_INDEXER_SCORE_CHUNK_MAX_BYTES`, so `_indexer_topk_row_chunked` always takes its single-pass branch.

The multi-chunk branch is the only code that:
- (a) sends SBHD/BSHD inputs through the THD form of `_DSA.indexer_forward_wrapper` (made-up `cu_seqlens_q/k` plus `q_causal_offsets`) instead of the BSHD form;
- (b) passes segments that have no query rows but do have K rows;
- (c) passes causal offsets for segments cut mid-sequence.

All three are checked only against `ReferenceDSA`, which assumes `position = offset + local_row`. The `_indexer_topk_core` docstring goes further and says chunked indices and lengths are "identical to 'full'". If cuDNN behaves differently, Top-K is silently wrong only at the long-context sizes where chunking turns on. The legacy CP layout uses a similar clipping pattern, which lowers the risk but does not cover the BSHD-to-THD switch.

**Correction.** Add a real-kernel test that forces chunking by monkeypatching the budget; no production change is needed. Proposed, in `TestRealKernelIndexerTopk`:

```python

def test_real_indexer_topk_row_chunked_matches_single_pass(
    self, chunk_rows, monkeypatch, reset_lazy_kernel_state
):
    _skip_if_real_kernels_unavailable()
    # same q_indexer / k_indexer / weights as test_real_indexer_topk_set_matches_reference
    kw = dict(topk=8, ratio=4, indexer_softmax_scale=128**-0.5,
              use_compact=False, deterministic=True)

    monkeypatch.setattr(dk, "_CSA_INDEXER_SCORE_CHUNK_ROW_ALIGNMENT", 1)
    idx, length = indexer_topk(q_indexer, k_indexer, weights, **kw)
    assert torch.equal(length, full_len)
    # per-row set overlap with the reference >= max(1, n - 1), as in the existing test
```

To keep the docstring's "identical" claim, also assert `torch.equal(idx, full_idx)` with `deterministic=True`. Otherwise, soften that docstring to "same lengths; same Top-K sets up to kernel rounding". Update this module docstring either way.

**Preservation.** Keep the CPU stand-in tests in this file unchanged. They remain the logic-level checks for row slicing, offsets and padding.

**Acceptance.**
