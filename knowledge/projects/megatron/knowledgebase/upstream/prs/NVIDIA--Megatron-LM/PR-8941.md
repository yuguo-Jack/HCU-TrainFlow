# Fix MFSDPv1 HSDP outer reduce issue

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8941) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?
Megatron-FSDP v1 with hybrid sharding (HSDP / HFSDP, i.e. `num_distributed_optimizer_instances > 1`) can reduce a bucket's gradient over DP-Outer more than once per optimization step, over-counting that gradient. This PR makes the DP-Outer reduction run once per step for each bucket group.

## Problem
With hybrid sharding, each backward pass reduce-scatters a bucket's new gradient over DP-Shard and accumulates it. In the last microbatch the accumulated shard is then reduced over DP-Outer. That DP-Outer reduction runs **in place** (`main_grad_buffer` is a view of the buffer it reads), so it is not idempotent. It  used to run every time a bucket was reduced in the last microbatch.

  A bucket is reduced more than once in the last microbatch when its parameters get gradients from separate backward passes. Under the 1F1B overlap schedule (`overlap_moe_expert_parallel_comm`), the **word embedding** gets gradients from both the model and the MTP layer, in separate backward passes. When the embedding  has a bucket of its own (`bucket_size` no larger than the embedding), its DP-Outer reduction ran twice. 

## Fix
  - In the last microbatch, `_bucket_group_gradient_reduce()` now records the bucket group, at most once, instead of reducing it over DP-Outer right away.
  - The new `GradReducePipeline.reduce_outer_fsdp_group_gradients()` reduces each recorded group over DP-Outer once. It keeps the existing HSDP all-reduce and HFSDP reduce-scatter paths.
  - `MegatronFSDP.synchronize_gradient_reduce()` calls it after all DP-Shard reductions have completed.
  - The DP-Shard reductions are unchanged. Repeating them is correct because each one accumulates a new gradient.

  **Trade-off:** the DP-Outer reductions no longer overlap with the last microbatch's backward pass. 

## Test
  `TestMegatronFsdpSharedEmbeddingOverlapSchedule` in `test_mcore_fully_sharded_data_parallel.py` trains a GPT + MTP model under HSDP and HFSDP. The embedding has a bucket of its own (DP-Shard `optim_grads`, EP=2). It compares the 1F1B overlap schedule with the standard schedule through  `forward_backward_no_pipelining`, from identical weights, under `deterministic_mode`.

  - Before the fix: losses differ by 7–12% at step 1.
  - After the fix: they match to 5e-6.

### Release each outer communication buffer before allocating the next group

**Failure:** The deferred reduction exhausts the double-buffer pool when gradient communication uses a different dtype. A minimal setup is three identical linear FSDP units, a `(DP-Outer=2, DP-Shard=2)` mesh, `fsdp_double_buffer=True`, FP32 main gradients, BF16 `grad_comm_dtype`, and automatic gradient synchronization. This affects both HSDP (`outer_dp_sharding_strategy="no_shard"`) and HFSDP (`"optim"`).

The new [outer-reduction loop](https://github.com/NVIDIA/Megatron-LM/blob/88cc385ceca3b0799b01709644781c7ab5d2f30e/megatron/core/distributed/fsdp/src/megatron_fsdp/param_and_grad_buffer.py#L4264-L4312) allocates a temporary communication buffer for every pending group, but [cleanup](https://github.com/NVIDIA/Megatron-LM/blob/88cc385ceca3b0799b01709644781c7ab5d2f30e/megatron/core/distributed/fsdp/src/megatron_fsdp/param_and_grad_buffer.py#L4357-L4363) runs only after all groups. The [allocator has two unit slots](https://github.com/NVIDIA/Megatron-LM/blob/88cc385ceca3b0799b01709644781c7ab5d2f30e/megatron/core/distributed/fsdp/src/megatron_fsdp/param_and_grad_buffer.py#L2618-L2669), so the third symmetric unit reaches the [“No buffer found” assertion](https://github.com/NVIDIA/Megatron-LM/blob/88cc385ceca3b0799b01709644781c7ab5d2f30e/megatron/core/distributed/fsdp/src/megatron_fsdp/param_and_grad_buffer.py#L839-L866). `MaxPoolAllocator` has the same limitation. Previously, [per-group cleanup](https://github.com/NVIDIA/Megatron-LM/blob/77bcb7fe27ce33cc61be8314b3deaf574edaa9a8/megatron/core/distributed/fsdp/src/megatron_fsdp/param_and_grad_buffer.py#L4482-L4501) allowed those buffers to be recycled. Gradient synchronization should complete without retaining temporary buffers for the whole model.

**Correction:** In `GradReducePipeline.reduce_outer_fsdp_group_gradients()`, release each group's temporary buffers after its collective and copy-back, before allocating the next group. Keep release and reuse ordered on the outer-reduction stream. Replace the tail at [lines 4352–4363](https://github.com/NVIDIA/Megatron-LM/blob/88cc385ceca3b0799b01709644781c7ab5d2f30e/megatron/core/distributed/fsdp/src/megatron_fsdp/param_and_grad_buffer.py#L4352-L4363) with:

```python
                for main_grad_buffer, reduced_grad in grad_accum_closure:
                    main_grad_buffer.copy_(reduced_grad)

                # Recycle this group's temporary buffers on their use stream.
                for bucket_id in bucket_group:
                    hsdp_comm_gbuf = self.buffer.parameter_groups[bucket_id].hsdp_comm_gbuf
                    if hsdp_comm_gbuf is not None:
                        hsdp_comm_gbuf.free_bucket_storage()

        torch.cuda.current_stream().wait_stream(self.outer_fsdp_group_grad_reduce_stream)
```

This leaves persistent accumulated gradients intact and retains the once-per-step outer reduction. Please verify the suggested change before adopting it.

**Preservation and acceptance:** Add a regression with the three-unit setup above, parameterized over fixed/max-pool allocation and both outer sharding strategies. For two optimization steps, assert that synchronization completes, `hsdp_grad_comm_alloc.using_buffer` is empty afterward, and SGD-updated local shards match a reference with double buffering disabled. HSDP must copy the full reduced buffer back before reuse; HFSDP must copy only its local outer shard. Also check the equal-dtype path, which allocates no outer communication buffer. Retain the new [shared-embedding regression](https://github.com/NVIDIA/Megatron-LM/blob/88cc385ceca3b0799b01709644781c7ab5d2f30e/tests/unit_tests/distributed/mfsdp_v1/test_mcore_fully_sharded_data_parallel.py#L1823-L1897): both schedules must continue matching over two steps with `rtol=1e-3, atol=0`, despite repeated inner reductions.

This finding and suggested correction are based on source tracing; I couldn't execute GPU tests. I completed the light review of all three changed files and their directly affected synchronization, buffer, optimizer, and schedule paths.
