# perf(inference): budget batch-invariant hybrid prefill separately from decode tokens

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8655) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

In batch-invariant mode, hybrid (Mamba) models now budget chunked-prefill tokens separately from decode tokens. This lets a mixed prefill+decode step admit a full SSM-chunk-aligned prefill chunk. On Nemotron-3-Ultra with 32 requests and 6.7k-token prompts, the time until all requests are decoding drops from 62.6 s to 34.3 s, against 33.3 s without batch invariance. Logprobs are bitwise unchanged.

## Details

Under batch invariance, `_mamba_batch_invariant_prefill_chunk_length` ends every non-final prefill chunk on an SSM chunk boundary (`ssm_chunk_alignment`, 128 for Nemotron-3). This keeps the chunked scan's state-passing boundaries independent of the batch. A mixed step's prefill room was `max_tokens - active_token_count`, so any decode tokens in the step pushed it below `max_tokens`.

With `max_tokens=256` and D decoding requests, the room is `256 - D`. That rounds down to 128 prompt tokens per step, so close to half of every mixed step's budget went unused while long prompts were admitted behind decoding requests.

The change applies only when batch invariance, a hybrid model and chunked prefill are all enabled:
- `DynamicInferenceContext` keeps the configured `max_tokens` as the per-step prefill budget, `max_prefill_tokens`. It raises the step capacity `max_tokens` by `ssm_chunk_alignment` before any buffer is sized and any CUDA graph is generated.
- `DynamicInferenceEngine._chunked_prefill_token_budget()` returns `min(max_tokens - active_token_count, max_prefill_tokens - prefill_tokens_in_step)`. Both `schedule_chunked_prefill` and `_can_schedule_chunked_prefill` use it.
  - With up to `ssm_chunk_alignment` decode tokens, a mixed step admits the full `max_prefill_tokens`.
  - With more decode tokens, it still admits at least `max_tokens - D` prompt tokens, the non-batch-invariant amount, provided `max_tokens` is a multiple of the SSM chunk.
- CUDA graphs: if `cuda_graph_max_tokens` covered the whole prefill budget, it now extends to the new capacity. The larger mixed steps therefore replay a captured graph instead of running eagerly. With `cuda_graph_max_tokens=512`, `max_tokens=256` and `max_requests=128`, the largest mixed graphs are `[384]: 1 P + 127 D` and `[384]: 2 P + 126 D`, and every prefill-phase step in the runs below replayed a graph.
- KV and Mamba state budgeting is unchanged. Prompt chunks still go through `check_availability`, and every non-final chunk still ends on an SSM chunk boundary.
- `max_tokens > ssm_chunk_alignment`, the existing batch-invariant requirement, is now checked against the configured prefill budget.

Every other configuration has `max_prefill_tokens == max_tokens`. For those, `_chunked_prefill_token_budget()` returns `max_tokens - active_token_count` exactly as before, and the graph ceiling is unchanged.

Memory cost: every buffer sized by `max_tokens` grows by `ssm_chunk_alignment` (128) tokens, and the largest prefill/mixed CUDA graph grows by 128 tokens. These buffers are the per-token bookkeeping, the sequence-parallel all-gather buffer, the MoE dispatcher buffers and the logits buffers. Measured peak allocation:
- Nemotron-3-Ultra, TP8 EP8: 117.18 GB -> 117.24 GB (+0.06 GB).
- Nemotron-3-Nano, TP2 EP4: 72.28 GB -> 72.30 GB (+0.02 GB).

## Performance

Setup:
- GB200, MXFP8, CUDA graphs for decode and mixed steps, chunked prefill, async scheduling, FP32 Mamba states.
- `max_tokens=256`, `max_requests=128`, `cuda_graph_max_tokens=512`.
- 32 requests with 6,667-token prompts are added at once and generate 2,293 tokens each.

Before and after are batch-invariant runs on the same tree with the change disabled and enabled. "Default" is the same tree without batch invariance.

| model | arm | all 32 decoding | TTFT p50 | TTFT p90 | prefill-phase steps | steady decode step |
|---|---|---|---|---|---|---|
| Ultra TP8 EP8 (2 nodes) | BI before | 62.59 s | 32.91 s | 56.62 s | 1639 | 24.09 ms |
| | BI after | **34.31 s** | **18.16 s** | **31.09 s** | 849 | 24.07 ms |
| | default | 33.33 s | 17.08 s | 29.98 s | 890 | 23.09 ms |
| Nano TP2 EP4 (1 node) | BI before | 22.51 s | 11.64 s | 20.33 s | 1639 | 7.36 ms |
| | BI after | **12.41 s** | **6.48 s** | **11.24 s** | 849 | 7.30 ms |
| | default | 11.29 s | 5.78 s | 10.16 s | 890 | 6.90 ms |

How to read the table:
- A mixed step now carries 256 + D tokens instead of 128 + D. Its median time rises from 37.8 to 40.6 ms on Ultra and from 13.7 to 14.5 ms on Nano, but the number of such steps halves.
- Steady decode steps are unchanged.
- With 861-token prompts on Nano, the time to all-decoding drops from 2.50 s to 1.57 s (default 1.41 s), and decode stays within 0.05 ms (7.08 vs 7.12 ms).

## Tests

- New `TestMambaPrefixCaching::test_batch_invariant_mamba_chunked_prefill_budget_excludes_decode`. It runs a hybrid context with chunked prefill, `max_tokens=256` and 0, 1, 40 or 63 resident decode requests, schedules a 1000-token prompt and checks:
  - the step capacity;
  - that batch-invariant mode admits a 256-token chunk aligned to the SSM chunk;
  - that non-batch-invariant mode still admits exactly `256 - D`.
- The two scheduler test harnesses that build a stand-in context or call `schedule_chunked_prefill` unbound now provide `max_prefill_tokens` or mock the new helper.
- On GB200, these files give the same 13 failures with and without this change, and 8 more passes with it:
  - `tests/unit_tests/ssm/ops/mamba2/test_batch_invariant_decode.py`
  - `tests/unit_tests/inference/engines/test_batch_invariant_mamba_prefix_caching.py`
  - `tests/unit_tests/inference/contexts/test_dynamic_prefix_caching.py`
  - `tests/unit_tests/inference/engines/test_dynamic_engine_async_sched.py`
  - `tests/unit_tests/inference/test_disagg_handoff_lifecycle.py`
  - `tests/unit_tests/inference/test_inference_config.py`
  - `tests/unit_tests/inference/test_batch_dimension_utils.py`
  - `tests/unit_tests/inference/engines/test_hybrid_prefix_caching_e2e.py`

  Results: 767 passed vs 759, 7 skipped and 131 subtests passed in both. The 13 failures come from the single-process environment (FlashAttention-4 not installed, tests needing 4 ranks or an EP group, a missing event loop) and are identical on `main`.
- Inference engine, Nemotron-3-Nano, MXFP8, TP2/SP, EP4, batch-invariant mode, CUDA graphs:
  - batch 1 vs 24: 0 of 2,796 prompt, 0 of 780 generated and 0 of 1,024 decode-vs-prefill-rescoring logprobs differ;
  - batch 1 vs 96: 0 of 2,796, 0 of 786 and 0 of 1,024.
  - Against the same runs without this change, every prompt logprob (5,592), rescored logprob (3,820) and solo-generated logprob (1,024) is bitwise identical.
- Inference engine, Nemotron-3-Ultra (108 layers), TP8/SP, EP8, batch-invariant mode, batch 1 vs 96: 0 of 2,796 prompt, 0 of 208 generated and 0 of 1,024 decode-vs-prefill logprobs differ.
- black, isort, pylint and ruff with the `tools/autoformat.sh` settings report no changes on the changed files.
