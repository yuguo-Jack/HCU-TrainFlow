# fix: replace MultimodalRotaryEmbedding matmul with element-wise multiply

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8885) · state: open · merged: False

## Original PR description

## Summary

`MultimodalRotaryEmbedding.forward` computes RoPE angles with a batched fp32 matmul (`inv_freq_expanded @ seq_expanded`). cuBLAS may execute this in TF32, which is the default in NGC/NeMo containers (`TORCH_ALLOW_TF32_CUBLAS_OVERRIDE=1`) and whenever `torch.backends.cuda.matmul.allow_tf32 = True`. TF32 keeps only 11 mantissa bits, causing angle errors of several radians at positions above ~2048.

This replaces the matmul with broadcasting element-wise multiplication (`seq[..., None].float() * self.inv_freq`), which uses the fp32 ALU and is immune to the TF32 matmul override. The base `RotaryEmbedding` class already uses `torch.outer` (element-wise), so this brings `MultimodalRotaryEmbedding` in line.

## Changes

- `megatron/core/models/common/embeddings/rotary_pos_embedding.py`: replace the 4-line matmul sequence (expand + matmul + transpose) with a single broadcast multiply
- `tests/unit_tests/transformer/test_rope.py`: add `test_forward_precision_under_tf32` regression test that enables TF32 and checks angle precision against an fp64 reference

## Test plan

- [ ] Existing `TestMultimodalRotaryEmbedding` tests pass (shape, dtype, device)
- [ ] New `test_forward_precision_under_tf32`: enables TF32, runs forward, verifies max angle error < 1e-3 rad vs fp64 reference
