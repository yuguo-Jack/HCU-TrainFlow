# [Test][Inference] Independent oracles for batch-invariant kernels, the inference router and fused-TP selection

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8976) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Adds independent oracle tests for five high-risk kernels outside `megatron/core/inference` that inference depends on: the batch-invariant log-softmax, DeepGEMM's dense and grouped bf16 GEMMs behind the batch-invariant backends, `InferenceTopKRouter`, and the fused-TP kernel selection (`configure_fused_tp_inference`). No production code changes.

**Stacked on the oracle harness PR #8966 (`test/inference-oracle-harness`)**, which adds `tests/unit_tests/inference/oracles/` and its helpers. Review only this PR's commits: `68d344ea8` (the tests), `cd5e7e386` (fixes after the first GPU run), `f41833b56` (cases added after mutation testing), `5c6855da4` (the router's sanitizer case), `7460b6d77` (quantile balancing, router replay and the remaining fused-TP paths) `478f52a82` (the grouped GEMM's declared offsets alignment, and fixes after the second GPU run), `6721da2ef` (fixes after the third) `288d2741b` (the graphed engine cases gated on #8880) and `9409d06d3` (the fused-TP verdicts exchanged over a gloo group: gathering them over the default NCCL group aborted the 2-GPU case under compute-sanitizer memcheck). Retarget to `main` once the harness is merged.

## Why

These kernels had no independent oracle. The log-softmax was never compared with `torch.log_softmax`. No test ran DeepGEMM's dense GEMM: the only "deepgemm" test fed fp32, which goes to Triton. The grouped GEMM was checked only against itself, through split invariance. The router's probabilities were never compared with anything. The fused-TP selection had only end-to-end goldens. Every test module here starts from a contract written from the semantics: the aten op a kernel replaces, the router options' documented meaning, the layer math. The reference is then built from that contract, not from the kernel.

## What is in it

`tests/unit_tests/inference/oracles/batch_invariant/`, five modules, 624 cases collected:

| Module | Kernel | Oracle | Tolerance | Hardware |
|---|---|---|---|---|
| `test_log_softmax.py` (156 cases) | `_log_softmax_kernel` | fp64 `x - logsumexp(x)` with torch's special values; trusted `torch.log_softmax` | per row, factor 2 (bf16/fp16), 4 (fp32, see below); bit-exact metamorphic | H100 + GB200 |
| `test_deepgemm_dense.py` (210) | DeepGEMM `bf16_gemm_nn` (`_mm_deepgemm`), and mm/addmm on every GEMM each backend dispatches to | fp64 `a @ b` (+ bias); trusted cuBLAS `torch.mm`/`addmm` | per row, factor 2; exact dispatch; bit-exact row invariance; bit-exact on dyadic inputs for `matmul_persistent` | H100 + GB200 |
| `test_deepgemm_grouped.py` (43) | DeepGEMM `m_grouped_bf16_gemm_nt_contiguous` (aligned and padded entry points) | per-expert fp64 loop; trusted per-expert cuBLAS | per row, factor 2; bit-exact invariance; guard bands around DeepGEMM's output | H100 + GB200 |
| `test_inference_topk_router.py` (184) | `InferenceTopKRouter` (compiled, Triton sigmoid kernel, batch-invariant eager, TE fused; quantile balancing, router replay) | fp64 routing from the score-function, QB and replay semantics, on bf16-exact logits with a selection margin; the eval-mode router cross-checked for QB | expert sets, QB state and recorded indices exact; probs factor 4 (see below); dispatch exact; graph replay bit-exact | H100 |
| `test_fused_tp_dispatch.py` (31) | `configure_fused_tp_inference` + `_matmul_reduce_scatter`, in blocks, pipeline stages, CUDA graphs, the engine, MTP, HybridStack and MLA | zero-projection metamorphic (output == input); fp64 RMSNorm for each GEMM input | exact output, dispatch, norm wiring and cross-rank traces | H100, 1, 2, 4 and 8 GPUs |

Structure-derived inputs:
- **Log-softmax**: n_cols at B−1/B/B+1 of 1024 and 2048, production vocabularies (32000, 151936, 152064, 262144), rows 0..1000, every special value (NaN, ±inf, all −inf, constant, underflowing gap, subnormal, overflow to −inf). Base offsets within 16 bytes, which change Triton's pointer specialization. Int32-overflowing offsets (`large`).
- **Dense GEMM**: M at B−1/B/B+1 of every block_m DeepGEMM's heuristics can choose (SM90 16/32/64/128/256, SM100 32/64/128), K around block_k = 64 and unaligned (8, 60, 63, 65), N unaligned (50, 60, 129). Operand layouts: row-major, `w.t()`, padded stride, misaligned base. M = 0, N = 0, K = 0, and A offsets past 2³¹ (`large`).
- **Grouped GEMM**: per-expert counts 0, 1, A−1, A, A+1, 2A−1, 2A+1 (A = DeepGEMM's alignment, read at runtime). All experts empty; one expert holding every row; E up to 128; tail rows past `offs[-1]`; M_total = 0.
- **Router**: E ∈ {8, 64, 256} (512 and 1024 for the kernel's dispatch boundary; 160 in the sanitizer case), k ∈ {1, 2, 6, 8, 32, E}, T ∈ {0, 1, 7, 128, 129, 4096}, B ∈ {1, 2, 3}. Every score function, expert bias, scaling factor, hash layers and sinkhorn. Expert biases that make the k-th selected sigmoid + bias score negative (the Triton kernel orders scores by integer keys, with a separate rule for negative floats). Quantile balancing at both estimation scopes (micro batch: top-k of z − β on the compiled path; global batch: its bias through the sigmoid kernel), router replay RECORD into a tensor, a static buffer and the async engine's banked buffer, and REPLAY_FORWARD to experts off the natural top-k; both under CUDA-graph replay.
- **Fused TP**: TP 1, 2 and 8, flag on and off. NVLS kernels disabled, batch-invariant mode, fp16, a symmetric buffer too small for the tensor. First, middle and last layer; TP 2 × PP 2 stage boundaries with the final norm; decode, mixed and prefill token counts on both sides of the buffer's capacity; the block or each layer captured in CUDA graphs at sizes that decide alike and differently; the dynamic engine with layer- and block-scope graphs and mixed steps; the MTP inner layer (depth 1, 2), a HybridStack and MLA blocks.

Memory safety:
- guard bands with NaN sentinels around the log-softmax input;
- NaN padding rows inside grouped-GEMM expert blocks;
- DeepGEMM's grouped output goes into a guarded buffer (one alignment block of rows each side) through a spy. Rows past `offs[-1]` are unspecified: DeepGEMM computes them with expert 0's weights, as its own tests allow, and the callers never read them;
- the `"tp"` symmetric buffer is NaN-poisoned before every fused-TP forward, so a stale read shows up;
- inputs are checked to be unchanged;
- one `sanitizer` case per GEMM, the log-softmax and the router (160 experts, so the sigmoid kernel's column mask is active, and 7 tokens, so its last 4-row block is partial).

### Factors other than the default

- **fp32 log-softmax outputs and router probabilities: factor 4.** Triton lowers fp32 `tl.exp`/`tl.log` and `tl.sigmoid` to the approximate PTX instructions (`ex2.approx` after a log2(e) prescale, `lg2.approx`; about 2⁻²² relative). The trusted torch ops use CUDA's `expf`/`logf` (1–2 ulp).
  - Where |y| < 1, for example a few-column log-softmax, a log-sum-exp error of 1e-7 is several ulps of the output.
  - A wrong maximum, a dropped term, a wrong normalization or a wrong score function errs by orders of magnitude more.
  - The ratio is reasoned, not measured; the GPU run should report it.
- **bf16 and fp16 outputs keep the default.**

## GPU run 1 (H100 dfw 21220462, GB200 hsg 8571400) and follow-up `cd5e7e386`

Every expect-fail task failed. The H100 O8a-N3 ones failed on a test precondition instead of the bug, so they must be rerun. Four test-side problems are fixed in `cd5e7e386`:
- **Misaligned operands** moved from the pairwise numerics into the focused O8a-N5 test.
- **Rows past `offs[-1]`** are no longer asserted untouched; guard bands check that no write leaves the output.
- **Router logits** are now drawn per token. Before, the rms bound rested on two repeated probabilities: the failing case had max error equal to torch's, 1 ulp.
- **The gating test's TF32 precondition** is dropped. Its trusted GEMM has bf16 operands, which TF32 holds exactly.

## Follow-up `f41833b56` (mutation testing)

The mutation run (`audit/step4/mutation/RESULTS.md`) left four O8a survivors. Two were gaps, now closed:
- **Negative routing scores** (`test_negative_routing_scores_select_like_fp64`, 12 cases): every earlier case selected its k-th expert among positive scores, so a kernel that orders negative scores backwards passed. All but k/2 experts now get biases in [-2, -1], on every path, for k < 8 and k ≥ 8.
- **addmm's bias on every GEMM** (`test_mm_and_addmm_on_every_dispatch_path`, 12 cases): the dispatch test only spied which GEMM ran for the Triton targets, so a Triton addmm that dropped its bias passed. Dyadic inputs make `x @ w^T + bias` exact in fp32 (and TF32), so `matmul_persistent` must match the fp64 result rounded once, bit for bit; DeepGEMM's bf16 addmm (two roundings, documented) stays bounded.

The other two (8-byte instead of 16-byte outer strides, and the alignment test inverted) are documented, not tested: on `main` DeepGEMM forwards to cuBLASLt, which accepts any leading dimension, so no result tells them apart. Only DeepGEMM's own TMA kernels (#8867) need 16 bytes, and the existing unaligned-N/K cases cover that on #8867's tree.

## Local checks

No GPU. CPU venv with torch 2.14 and the Triton 3.8 interpreter; no TE, no DeepGEMM. The laptop GPU cannot build Triton launchers, so nothing ran on it.
- **Log-softmax**: 94 cases pass in fp32/fp16. bf16 numerics cannot be checked: the interpreter truncates bf16 stores, which was verified separately. The empty-last-dim crash (O8a-N2) reproduces.
- **DeepGEMM modules**: 176 checks against a fake DeepGEMM pass, on `main` and on the #8867 tree. The fake applies the pin's host-side layout rules and the contiguous scheduler's first-row rule; it checks the tests' plumbing and the misaligned-offsets detection. It is not DeepGEMM.
- **Router**: run on the CPU with gloo; Inductor (no C++ compiler here) was replaced by `aot_eager`, and the sigmoid kernel ran in the interpreter.
  - 52 checks on `main`. The top-1, B > 1 and sinkhorn checks fail there, as stated.
  - 55 on the #8562 tree, where they pass.
- **Fused TP and the TE fused router** need TE and were only collected. For `7460b6d77`, all 19 configs the new fused-TP cases build pass `TransformerConfig` validation on the CPU.
- **`7460b6d77`** (router on the CPU, as above): 73 of the 86 new router cases pass on `main` (all but the five global-QB cases on the sigmoid kernel, which needs CUDA logits, and the eight CUDA-graph cases), and 7 unchanged routing cases still pass after the shared-check refactor.
- **`f41833b56`** (interpreter): the sigmoid kernel selects the fp64 expert sets on all 129 rows of each negative-score case, and a copy with negative scores ordered backwards on none. `matmul_persistent`'s dyadic mm/addmm are bit-exact in fp32/fp16, and a copy that drops the bias is not.
- **Formatting**: `black` 26.3.0, `isort` 5.13.2, `ruff` 0.9.10 clean.

## Second GPU run (dfw 21232953) and follow-up `478f52a82`

- **The grouped GEMM's new `offs_alignment`** (s4f-grouped-gemm-alignment makes it required and keyword-only): the module calls the entry point through a helper that passes it only when the signature has it, so the aligned cases run on `main` and with that PR. The misaligned case declares its offsets' true alignment, and new cases check that a declaration DeepGEMM cannot use, or an `offs` of the wrong length, is rejected before the GEMM. Offsets declared with DeepGEMM's alignment but holding misaligned values stay that PR's documented, unchecked precondition.
- **Fused-TP step sizes**: the single-token-per-rank decode moved to its own case, which fails on `main` in the fused kernel's launcher (#8880).
- **Full-iteration graphs**: the test seeds the inference RNG tracker before capturing, as the engine does; the training tracker reseeded the generator inside the capture.
- **Engine**: the model has no learned position embedding (an fp32 `torch.nn.Embedding` made the decoder input fp32, which TE's RMSNorm cannot take with bf16 weights).

## Third GPU run (pdx 7856500) and follow-up `6721da2ef`

- **Engine test**: pins `flash_attention_version` (3, or 2 without FA3). Auto-selection picks FA4 and asks it for split-KV on Hopper, which #8584 fixes; the backend is not what this test checks.
- **Graph test**: every captured graph is reset before the verdict. A graph that captured the NCCL fallback made teardown hang after the test had already failed.
- **Sanitizer**: no 2-GPU case. NCCL died under compute-sanitizer on both clusters (no memcheck record), so the 2-GPU cases run as ordinary expect-pass tasks.

## Notes for reviewers

- **Not covered**:
  - fused TP with a toy hidden size whose rows are not 16-byte multiples (the NVLS kernel's precondition, covered with the NVLS kernels), and n12's race checker (only on #8709);
  - router replay on hash layers, REPLAY_BACKWARD (training only), and QB with B > 1 or top-1 (after #8562);
  - `_bf16_grouped_gemm_device_counts`, which #8866/#8869 add and `main` does not have;
  - equality between DeepGEMM's K-major and MN-major kernels: the contract requires invariance within a layout, and equality is not required.
- **Sanitizer**: the compute-sanitizer (memcheck) pass runs only the `sanitizer` cases: 6 on one H100, 4 on GB200. Fused TP has none (NCCL is not reliable under compute-sanitizer on these clusters). The whole package would be too slow under memcheck, and CUDA-graph capture cannot allocate with the caching allocator off. It has not run yet.
- **Hand-captured graphs vs `CudaGraphManager`**: `test_cuda_graph_replay_keeps_the_residual` captures the block or each layer with `torch.cuda.graph`, so it can check every layer's GEMM inputs (copies captured in the graph refresh on replay). The engine test reaches the real manager at layer and block scope, where only the eager embedding and output layer around the graphed decoder can be observed.
- **Determinism**: test-only; no kernel or dispatch change, so there is no determinism test or manifest entry.
