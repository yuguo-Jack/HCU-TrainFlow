# [Inference][SSM] Reject a dynamic context whose SSM prefill chunking differs from the model's

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8884) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes the inference wrapper reject a dynamic context whose SSM prefill chunking differs from the chunking the model's SSM kernels run at, instead of silently computing wrong prefill outputs and states.

**Bug.** Dynamic prefill builds its chunk boundaries (`cu_chunk_seqlens`, `last_chunk_indices`) from `MambaInferenceStateConfig.mamba_chunk_size`. The context copies that value into `MambaMetadata` (`attention_context/mamba_metadata.py`). `MambaMixer.ssm_prefill` runs the chunked scan at the mixer's own `chunk_size`. Nothing checked that the two agree. `from_model` copies the mixers' value, and every in-tree builder uses it, so only a hand-built config passed through `InferenceConfig.mamba_inference_state_config` could differ. The field's docstring ("The chunk size used by the Mamba SSM Triton kernels") invited setting it. Leaving the default 128 while the mixer's `chunk_size` comes from the spec is the same mistake.

- **Larger context chunk:** wrong prefill outputs and cached states, and an out-of-bounds read. `_chunk_cumsum_fwd_kernel` writes dt/dA for `chunk_size` columns, while `_chunk_state_fwd_kernel` loops to the longer chunk. In the step 3 GPU repro on H100, context chunk 256 with mixer chunk 128 on a 200-token prompt: last-token logits off by a relative error of 1.34 against the full forward.
- **Smaller context chunk:** plain prefill stays correct. In batch-invariant mode the cached state is wrong whenever a prompt's tail exceeds the context chunk, because the tail is taken modulo the mixer's chunk while the chunk index comes from the metadata. On H100, context chunk 64 with a 200-token prompt cached the state after token 192 instead of 128.

**Fix.** The kernels must keep the mixer's chunk: batch-invariant decode replays at it, and training runs at it. So the context has to follow the model.
- New `check_ssm_chunking(model, mamba_chunk_size, ssm_chunk_alignment, gdp_num_householder)` in `inference/config.py` compares the context's settings with `ssm_chunking` of the model's SSM layers, and checks only what the kernels and the allocator need:
  - the Householder count must equal the SSM layers' (it sizes the Gated Delta Product chunk descriptors; GDN is one update);
  - for Mamba, `mamba_chunk_size` must equal the mixers' `chunk_size`. GDP prefill chunks at its own fixed 64, so a GDP config's `mamba_chunk_size` is not compared;
  - `ssm_chunk_alignment` must be a multiple of the chunk the inference kernels run at, the same rule the prefix-cache slot allocator applies. A coarser snapshot quantum, such as 256 on a 128-token Mamba model, stays allowed.

  On a mismatch it raises a `ValueError` that lists each disagreement and points to `from_model`.
- It finds the decoder the way the inference controller finds the language model: through DDP or `Float16Module`, then under a multimodal wrapper's `language_model`. A model without a decoder there (a wrapper whose context config was built from a language model the caller resolved) and a pipeline stage without SSM layers have nothing to check, so engine construction never fails on reachability.
- The inference wrapper calls it when it is built with a dynamic context of a hybrid model, with the context's own copies of the three settings, which are what prefill uses. Model and context first meet there, before any controller or engine, so every path that drives a dynamic context is covered, with or without an engine. The context cannot check at its own construction, because it does not see the model.
- The `mamba_chunk_size` docstring now states the contract.

**Tests.**
- `tests/unit_tests/inference/test_inference_config.py::TestSSMChunkAlignment` (CPU, stand-in mixers):
  - Configs from `from_model` pass, for Mamba with chunk 128 and 256 and for GDP. So do a coarser Mamba or GDP alignment and a GDP config left at the default `mamba_chunk_size` of 128 with a 64-token mixer.
  - These are rejected: a larger context chunk, a smaller one, the default 128 for a 256-token mixer, a Mamba alignment of 192 on a 128-token mixer, a GDP alignment of 96, and a different GDP Householder count.
  - A multimodal wrapper is checked through its `language_model`; a model without a reachable decoder, and a stage without SSM layers, check nothing.
- `tests/unit_tests/inference/model_inference_wrappers/test_abstract_model_inference_wrapper.py::test_wrapper_checks_the_dynamic_context_chunking` (CPU): the wrapper accepts a dynamic context that matches the model and raises for context chunks of 256 and 64 on a 128-token mixer. On `main` the wrapper builds (checked).
- `tests/unit_tests/inference/engines/test_dynamic_engine.py::TestDynamicEngineSSMChunking` (1 GPU; TE and `mamba_ssm`), on the `"M*-"` hybrid model of the repro. A wrapper, controller and engine build with `from_model`'s chunking. The wrapper raises for context chunks of 256 and 64 with a 128-token mixer; on `main` it builds.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), the regression tests pass (31 cases), also under compute-sanitizer with no errors. On `main` the only evidence from this run is an import failure: `test_inference_config.py` imports `check_ssm_chunking`, which this PR adds, so that run stops before any case. The step 3 GPU repro of this finding (R10-F1) shows the bug on `main` on H100, in both directions described above. The neighbor tests (`test_hybrid_prefix_caching_e2e.py::TestMambaPrefixCachingE2E`, `ssm/test_gdp_dynamic_inference.py`, `engines/test_gdp_cuda_graph_e2e.py`) pass (74 cases, 3 skipped).
