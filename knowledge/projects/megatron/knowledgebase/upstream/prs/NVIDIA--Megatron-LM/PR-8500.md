# [Dev] Extend MoonEP with modular MoEScheduler support for ECHO,EPLB,UltraEP

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8500) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Refactor the existing MoonEP integration into reusable planning, expert execution, and communication components, and introduce MoEScheduler to support MoonEP, ECHO, UltraEP and EPLB through a common interface.

This allows training to redistribute work across expert-parallel ranks by creating temporary expert replicas or migrating expert ownership, while preserving gradient accumulation, optimizer state, and checkpoint consistency.

Existing MoonEP configuration and import paths remain supported.

## Main changes

### Modularize the existing MoonEP integration

- Separate placement planning, execution state, expert storage, and peer transport.
- Reuse the upstream MoonEP placement kernel and capacity policy.
- Give each MoE layer one scheduler owner while preserving the native MoonEP execution order.
- Keep the native fixed-slot runtime and configurable replica runtime behind the common interface.

### Add configurable expert replication

- Support MoonEP, ECHO, and EPLB planners with configurable replica slots.
- Support Peer-TMA and NCCL P2P replica weight transfer and gradient reduction.
- Support BF16 and native-parameter MXFP8 execution with Transformer Engine grouped experts.
- Provide shared or layerwise replica storage, including MXFP8 buffer reuse.

### Bound communication memory and preserve gradient ownership

- Exchange replica weights, gradients, and home-expert state through reusable buffers with configurable size limits.
- Accumulate expert gradients directly into the owning `main_grad`, avoiding an additional native-gradient staging buffer.
- Preserve buffer lifetime and stream ordering across repeated forwards and backwards.

### Support home-expert migration and restart

- Add periodic EPLB home migration after a successful optimizer step, including expert weights, optimizer state, and routing-map updates.
- Support zero-replica EPLB using native expert computation without allocating replica weights or gradient buffers.
- Save and restore scheduler placement state alongside training checkpoints.
- Reject unsupported configurations during initialization.

The PR also fixes compact-routing probability handling, BF16 receive-buffer slack handling, and the configuration conflict between fixed THD input padding and HybridEP/MoonEP requirements.

## Validation

Validation was performed on Lyris GB200 with an isolated Transformer Engine 2.22.0.dev0 build.

- Native MoonEP and integration tests: 34 passed, with two existing upstream FC1-offload skips.
- Extended scheduler regression: 489 cases passed across two complementary runs.
- EP=8 validation: 40 cases plus topology checks passed on all eight ranks, with no skips.
- Determinism, integration, and kernel-manifest checks: 354 passed.
- BF16 and MXFP8 checkpoint continuation: a two-layer, zero-replica EPLB proxy completed uninterrupted 100-step training and a fresh-process restart from step 40. Logged losses matched exactly over iterations 5–100; model, optimizer, RNG, planner, and TrainState comparisons passed.
- DeepSeek-V4 Flash proxy: eight layers plus one MTP layer completed 100 iterations on eight GPUs with MXFP8, MoonEP + Peer-TMA, mock THD data, and force balancing/MOK disabled.
- CI selection tests, kernel determinism coverage, and formatting/static checks passed.

The main regression matrix was run on `8656ad413`. The subsequent fixed-THD-padding change was checked with configuration and tensor-padding regressions and exercised by the successful Flash training run on `609ec6e42`.


## Current limitations

- The two inherited FC1-offload test skips require a separate HybridEP/TE capacity-buffer fix.
- Peer-TMA requires a supported NVLink domain and symmetric-memory environment.
- FSDP v2, EP=1, and full activation recomputation are rejected for MoEScheduler.
- Validation used a feature container; official upstream CI-image validation remains separate.
