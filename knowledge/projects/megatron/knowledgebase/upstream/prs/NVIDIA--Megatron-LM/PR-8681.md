# Add opt-in fused KPool score postprocessing

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8681) · state: open · merged: False

# What does this PR do?

Add opt-in fused KPool score postprocessing for detached selection-only FP32 scores, combining optional ReLU, weight multiplication and the 32-head sum without changing the scoring GEMM or ordered top-k algorithm.

## Issue tracking

Fixes #8679.

## Scope and interface

- Introduce `dsa_indexer_kpool_score_backend: Literal["torch", "triton"] = "torch"`.
- Put the operation contract, torch reference, backend selector and optional Triton implementation under `megatron/core/ops/attention/dsa`.
- Bind the backend once during indexer construction. The default torch backend does not import the optional Triton implementation. Unsupported or unavailable explicit Triton choices fail clearly rather than silently falling back.
- Support KPool > 1, 32 indexer heads, FP32 projected weights and disabled indexer auxiliary loss. Kernel inputs are detached CUDA FP32 scores/weights; scores must have dense non-overlapping storage and contiguous head/key axes. Non-contiguous or broadcast weights are supported.
- Preserve the GEMM, scoring precision, chunk budget, packed/CP bounds, masks, pool expansion, tail selection, ordered top-k and process groups. Keep the complete-score/loss path unfused.
- Do not include TP scoring deduplication, checkpoint selection replay or mHC changes.

The single-key specialization explicitly fixes the addition tree to the inspected ATen CUDA 16/8/4/2/1 shuffle order, rather than assuming the compiler-selected `tl.sum` tree matches the reference. The multi-key specialization retains the four-accumulator reference order. Reference parity and replay determinism are separate tests; replay alone cannot establish unchanged discrete selection.

## Isolated microbenchmark

Run from the repository root:

`python -m tests.performance_tests.benchmark_kpool_score_postprocess`

`python -m tests.performance_tests.benchmark_kpool_score_postprocess --no-relu`

Shape `[257, 1, 32, 4096]`, FP32 scores/weights, 5 warmups and 25 measured repetitions. The benchmark resets the score input equally for both backends outside the event interval, alternates backend order and requires a zero-tolerance reference comparison. Measurements are CUDA-event medians; first-call wall time uses a fresh independent Triton cache.

| Mode | Torch warm median | Triton warm median | Isolated speedup | Torch first call | Triton first call including compile |
| --- | ---: | ---: | ---: | ---: | ---: |
| ReLU | 0.220416 ms | 0.080512 ms | 2.738x | 38.216 ms | 1922.372 ms |
| No ReLU | 0.157152 ms | 0.082048 ms | 1.915x | 27.577 ms | 2061.055 ms |

Both benchmark invocations returned zero and passed the exact reference comparison. These are isolated postprocessing measurements, not end-to-end training-step speedups or memory-savings claims. They exclude the preceding GEMM, process groups and training contention. Historical bridge evidence used an older `dev@ee743d3` GLM integration; PR #5 also enabled mHC, so its combined training results do not isolate this operation or certify the migrated main-based implementation.
