# Add MoE inference test foundation

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8638) · state: open · merged: False

## Original PR description

## What does this PR do?

This PR adds unit-test coverage for mixture-of-experts (MoE) layers in dynamic inference. It runs real MoE models through the engine under both the legacy and the overlapped scheduler, together with other inference features. It also checks the optimized dispatchers and expert kernels directly against the training layer. It changes no production code, and every test it adds passes on unmodified `main`. It keeps every upstream test case, but the upstream batch-invariant MoE cases now check more, and some shared harness behavior changes (see Scope).

The foundation adds:

- 5 single-GPU engine rows in `test_dynamic_engine_async_sched.py`. They cover local MoE layers, FlashInfer BF16 experts with a latent projection, Transformer Engine FP8 experts, and optimized MoE with KV offload and with KV recompute across suspend and resume;
- 6 expert-parallel engine rows in the same file, covering NVFP4 experts, dense and expert data parallelism, pipeline parallelism, a hybrid GDN-MoE model with hash routing, sliding-window attention with a learnable sink, and chunked prefill. The existing `moe-ep2-nccl` row is kept unchanged;
- 2 KV-handoff tests in `test_dynamic_engine.py`, in which an MoE decode engine continues a request whose prefill KV cache came from another engine, locally or over NCCL;
- an optimized-MoE row (`ep4-optimized-moe-lru`) in the prefix-caching engine matrix, next to the existing local-MoE row;
- dispatcher and expert-kernel tests in `test_moe_dispatching_and_routing.py`, listed below; and
- the test-harness support these need (see Scope).

## How was the test matrix determined?

A review of the MoE inference tests on `main` found three gaps:

1. Most engine tests used dense models. The only expert-parallel MoE row used one expert backend and one topology.
2. The optimized dispatchers and fused expert kernels were tested mostly in isolation. Few tests compared them with the training layer on the same weights and input.
3. Runtime checks were thin. A row could pass without proving that the intended expert backend, dispatcher or companion feature actually ran on the request.

The matrix therefore has three layers:

1. **Single-GPU engine pairs.** Each MoE implementation is paired with one inference feature, and the legacy and overlapped schedulers must agree.
2. **Expert-parallel engine pairs.** Expert parallelism 2 with the NCCL dispatcher is paired with each major topology or model feature that interacts with expert routing.
3. **Layer and kernel checks.** Each optimized path is compared with the training layer, or with an FP64 reference where BF16 rounding makes exact comparison impossible.

This is pairwise coverage of MoE with the features most likely to interact with it, not every combination of flags. Cases that need a production fix from this series live in that fix's PR. Cases that need more than one fix live in the series' tests PR.

## How are results checked?

Every engine row first proves that the paired behavior ran on the request, then compares outputs. These checks include:
- the expert backend and the steps on which experts, dispatch and combine ran;
- the token rows each GPU sent and received;
- the topology sizes;
- the latent projection steps, chunked-prefill steps, sliding-window and sink kernel calls; and
- hash-route and recurrent-state compaction counts.

Then tokens, finish reasons, log probabilities and top-N entries must match between schedulers, within each row's tolerance. Two rows are exempt, like `main`'s own sampled and FP8 rows: `moe-ep2-ddp4-edp2-nccl` samples stochastically with per-rank seeds, and `transformer-engine-fp8-moe` computes its tensorwise FP8 scales from each forward batch, which can differ between the schedulers. For these two rows the overlapped run must match the legacy run's completion status and output lengths with valid token IDs, and a second overlapped run must reproduce the first run's tokens. The FP8 row also checks each expert forward against an FP32 reference and each route exactly.

Numeric bounds:
- The FP8 row compares each expert forward with an FP32 reference: relative L2 at most 0.075 and cosine similarity at least 0.997.
- The NCCL rows with different token counts per GPU compare with an FP64 weighted-expert reference. Routes must match exactly, and the relative L2 and maximum errors must be at most 6 BF16 rounding steps.

The KV-handoff tests require the handed-off request to produce the same tokens as an uninterrupted request. They also require expert forwards in both the prefill and the decode engine.

## Scope

This PR is test-only and changes 6 files under `tests/unit_tests/` (+1,215/−80 against `main` `90f4d527`). It makes no production, functional-test, configuration or golden change. The whole MoE series adds 2,009 net unit-test lines, within the 2,021 approved for this series.

The upstream `test_batch_invariant_moe_matches_training` cases keep their exact training-to-inference match and now also require the training and inference routes to agree and both outputs to be finite.

The harness changes are:
- `DynamicEngineTestConfig` gains MoE options: expert backend, NVFP4 recipe, router settings, hash layers, latent size and expert tensor parallelism. Expert tensor parallelism keeps its upstream default unless a row sets it. `num_moe_experts` is now set when a test asks for MoE layers, even with one expert-parallel GPU;
- `hybrid_stack_spec_for` can return the inference-optimized hybrid specs. The engine harness uses them only for hybrid MoE rows, so upstream hybrid cases keep their spec;
- `_InInferenceMode` moves to module level in `test_moe_kernels.py`, and its `forward` now accepts `*args, **kwargs` instead of one `hidden` argument.

This PR no longer changes `test_utilities.py`: `main` (NVIDIA/Megatron-LM#7575) now restores PyTorch backend flags under PyTorch's mutation guard, which this PR used to add.

The NCCL KV-handoff test needs exactly 2 GPUs, one prefill engine and one decode engine, and skips at other GPU counts. The local KV-handoff test uses a head size of 64 and the newest installed FlashAttention: FA3 on our Hopper builds, FA4 on Blackwell and in GitHub CI's H100 image. The FlashInfer BF16 MoE row skips without the `flashinfer-jit-cache` package, because `main`'s MoE layer requires its prebuilt kernels; CI's image does not ship it.

### Read MTP acceptance counts after synchronization

In [traced_mtp_rewind](https://github.com/NVIDIA/Megatron-LM/blob/c78347831169a2634b78683530c988a36fbde8eb/tests/unit_tests/inference/engines/test_dynamic_engine_async_sched.py#L1300-L1311), the CPU reduction runs before the original rewind method. The [producer](https://github.com/NVIDIA/Megatron-LM/blob/c78347831169a2634b78683530c988a36fbde8eb/megatron/core/inference/text_generation_controllers/text_generation_controller.py#L2217-L2241) fills this pinned buffer asynchronously, while [the original rewind](https://github.com/NVIDIA/Megatron-LM/blob/c78347831169a2634b78683530c988a36fbde8eb/megatron/core/inference/text_generation_controllers/text_generation_controller.py#L2493-L2508) establishes readiness. When that copy is still pending, the new accepted/rejected counters consume stale or uninitialized values instead of the current verification result.

Call the original rewind first. It doesn't replace the count buffer or change the decode-request count, so recording afterward preserves production rewind behavior and its return value. Suggested replacement for this wrapper, based on source inspection and not executed:

```python
def traced_mtp_rewind(sample_result):
    result = original_mtp_rewind(sample_result)
    counts = sample_result.accepted_counts_cpu_view
    decode_count = context.num_decode_requests
    if counts is not None and decode_count > 0:
        accepted = counts[:decode_count].clamp(min=0)
        runtime["mtp-acceptance-decisions"] += decode_count
        runtime["mtp-accepted-tokens"] += int(accepted.sum())
        runtime["mtp-rejected-tokens"] += int(
            (controller.num_speculative_tokens - accepted).sum()
        )
    runtime["mtp-rewind-calls"] += 1
    return result
```

Acceptance: with a delayed count copy containing `[0, 1]`, two decode requests and speculative depth two, the witness should record one accepted and three rejected tokens after completion. A prefill-only call should record no acceptance decisions. Retain both existing MTP rows, their numerical-parity assertions, and the original rewind/error behavior. The static invariant is that every CPU read of this view follows synchronization of `accepted_counts_cpu_ready_event`. The author should verify the suggested replacement before adopting it.
