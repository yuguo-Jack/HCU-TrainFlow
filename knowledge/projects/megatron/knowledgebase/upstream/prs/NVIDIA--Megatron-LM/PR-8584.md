# [Inference] Stop requesting FlashAttention-4 split-KV on Hopper

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8584) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Fixes dynamic inference on Hopper when FlashAttention-4 is installed. Before this fix, it crashed with `AssertionError: SplitKV not supported on SM 9.0` once a KV sequence passed about 512 tokens, and at any length under CUDA graphs.

**Bug.** Two things combine on SM90:
- `Attention._resolve_flash_version` auto-selects FA4 whenever `flash-attn-4` (>= 4.0.0b20) is installed, with no device check. The 26.09 PyTorch image ships it.
- Both FA4 call sites in `flash_decode_and_prefill` (prefill and decode) pass `num_splits=0` outside batch-invariant mode (#5804). FA4's heuristic then splits the KV sequence once it spans more than four 128-token tiles and SMs are spare, which is normal for decode. FA4's SM90 forward asserts `not is_split_kv`.

Under CUDA graphs, decode runs with `max_seqlen_k = max_sequence_length`, so it crashes at any length. A pinned `flash_attention_version=4` on Hopper crashed the same way.

Affected: Hopper users with FA4 installed who leave `flash_attention_version` unset or set it to 4, outside batch-invariant mode. On H100 in the CI image (`mcore_ci_dev:main`: FA2 2.8.3 and FA4, no FA3), every row of a dynamic-inference integration matrix failed this way, on `main` and on other fix branches alike.

CI did not catch it because #7725 pinned FA2 in nearly every inference test and in `_run_training.sh`. The remaining FA4 tests are batch-invariant (`num_splits=1`) or use a fake kernel.

**Fix.** Kernel selection now follows what each kernel can run on the device. The support matrix comes from the `flash-attn-4` 4.0.0b36 source:
- FA4 runs paged KV, which dynamic batching uses, on SM90/SM100/SM110, but not on SM80 or SM120.
- FA4 splits the KV sequence only on SM100/SM110. SM80 and SM90 assert against split-KV, and SM120 forces a single split.
- FA3 builds target SM90 only.

The changes:
- **Device read.** A module-level helper, `_flash_attn_majors(device_index)`, is cached per device index and warmed when `Attention` is constructed. It returns the device's compute-capability major and the major FA4 runs kernels for, which honors FA4's `FLASH_ATTENTION_ARCH` override. The forward does no device query and stays CUDA-graph safe. Objects built without `__init__` still work.
- **Auto selection.** It picks the first installed kernel that runs paged KV on the device: FA3 (Hopper only), then FA4, then FA2.
  - On Hopper, FA4 stays ahead of FA2. That keeps MLA prefill working there: its q/k and v head dims differ (192 and 128), which FA2 rejects.
  - On SM100/SM110 the choice is unchanged (FA4).
  - FA3 is no longer picked off Hopper, and FA4 is no longer picked on SM80/SM120. FA2 is used there.
- **`num_splits`.** Both FA4 call sites take it from one helper, `_fa4_num_splits(device)`. It returns 1 in batch-invariant mode or where FA4 cannot split KV, otherwise 0. FA4 now runs unsplit on Hopper, whether pinned or auto-selected.

The `flash_attention_version` docstring now says that auto selection depends on the GPU.

**Tests.**
- `tests/unit_tests/transformer/test_attention.py::TestFlashAttentionDeviceSelection` (CPU) fakes the device capability (SM80, SM90, SM100, SM110, SM120). It checks:
  - auto resolution with FA3/FA4 installed or not;
  - the `num_splits` a fake FA4 kernel receives in prefill and decode, with and without batch-invariant mode;
  - the `FLASH_ATTENTION_ARCH=sm_90` override on SM100;
  - that Hopper prefill with MLA head dims (q/k 192, v 128) runs FA4 rather than FA2 when FA3 is absent.

  Run against `main`'s selection logic on CPU, 12 of its 30 cases fail: the SM90 split-KV cases, FA3 off Hopper, FA4 on SM80/SM120, the override, and the MLA case. All pass with this PR.
- `tests/unit_tests/inference/engines/test_dynamic_engine.py::TestDynamicInferenceEngine::test_long_context_on_hopper_with_fa4_installed` runs only on SM90 with FA4 installed. It generates 4 tokens from a 1000-token prompt, in eager mode and with CUDA graphs (`max_sequence_length` 1004). It runs once unpinned and once with FA4 pinned. Each run must complete and match an FA2 run token for token.
- Determinism: `tests/unit_tests/determinism/kernels/test_runtime_cp_attention.py::test_flash_decode_dispatch_config_softmax_scale_replays` now covers FA4 as well as FA2. It uses 600/700-token KV sequences, past FA4's split threshold, so the FA4 split-KV path is replayed bit-exactly on Blackwell and the unsplit path on Hopper. The manifest note is updated, and `tools/check_kernel_determinism_coverage.py` passes.
- Updated tests: the FA3 and FA4 cases in `test_softmax_scale.py` now pin their version, since auto selection depends on the device.

On CPU, the new and neighboring tests pass. On H100 in the CI image, the tests pass (38/38), including the long-context engine test with FA4 auto-selected and pinned, eager and under CUDA graphs, token-for-token against FA2; on `main` the new test file does not collect. The neighbor tests pass. With this PR, the step-level inference-vs-training configuration matrix runs in the CI image on H100: both control rows and 15 configurations pass (13 batch-invariant configurations skip because the image has no FA3).

**Follow-up (not in this PR).** #7725 pinned FA2 in `DynamicEngineTestConfig`, in the static, prefix-caching and parallel engine tests, and through `--flash-attention-version 2` in `_run_training.sh`. With auto selection now safe on Hopper, those blanket pins should be revisited so CI covers the unpinned default again.

## Follow-up: reject a FlashAttention-2 that cannot read the paged KV cache

Review finding (R11-F7): FlashAttention-2 reads paged KV only in blocks of a multiple of 256 tokens, and only with value heads as wide as query/key heads (flash-attn 2.8.3 `csrc/flash_attn/flash_api.cpp`). Nothing checked either limit, for a pinned FA2 or for automatic selection that falls back to it.

- **Bug.** `DynamicInferenceContext` accepted `flash_attention_version=2` with any `block_size_tokens`, and with MLA. MLA's latent cache forces 64-token blocks, and its unabsorbed prefill attends with query/key heads wider than its value heads (192 and 128 for DeepSeek shapes). The first prefill then failed inside flash-attn ("Paged KV cache block size must be divisible by 256"). On H100 this reproduced for MLA and for MHA with 64-token blocks (dfw 21197274). The pin is common: `_run_training.sh` adds `--flash-attention-version 2` to every non-NeMo functional test, and `DynamicEngineTestConfig` defaults to it. Automatic selection falls back to FA2 the same way when no FA3 or FA4 that runs paged KV is installed for the GPU: on SM80 and SM120 (FA4 has no paged KV there), and on images without FA3 or FA4, such as the LTS image.
- **Fix.** One helper, `check_flash_attn_2_paged_kv` in `attention.py`, holds the rule and its `ValueError`. The message names both limits, the cache's block size and head widths, and what reads the cache on this GPU instead: FA3 on SM90, FA4 where it runs paged KV (SM90, SM100, SM110), and, without MLA, a block size that is a multiple of 256. Where none applies, it says so. It is used in two places:
  - `Attention.flash_decode_and_prefill` calls it where it dispatches to FA2 (the prefill varlen call and the decode kvcache call), on the shapes FA2 will read: the paged cache's block size `k.shape[1]`, and `q` against `v` head dims. This covers a pinned FA2 and automatic selection, and per-layer configurations that the global config cannot see. It reads static shapes only, so it adds no host sync and is CUDA-graph safe; with CUDA graphs it fires during warmup, when the engine is built. FlashMLA decode never reaches it. The check sits in the FA2 branches rather than before the dispatch, so it does not repeat the MLA decode branch condition, which the open MLA Blackwell decode PR (#8873, FlashInfer MLA decode) reworks.
  - The context still rejects a pinned FA2 when it is built, next to the FlashMLA block-size check, but only when layers run FlashAttention on its cache: a plain transformer without an attention variant, or a hybrid with attention or MLA layers. A hybrid whose KV-cache layers are all DSA, which use their own kernels, is no longer rejected.
- **Updated tests.** One engine test (`test_prefix_caching_single_token_effective_chunk`, 16-token blocks) and the controller tests with 4-token blocks pinned FA2 but mock the forward. They now leave the version unpinned. The mocked-kernel tests that drive the FA2 branches (`TestFlashDecodeAndPrefillSoftcap`, `test_softmax_scale.py`) now pass 256-token pages.

Tests:
- `tests/unit_tests/transformer/test_attention.py::TestFlashAttentionDeviceSelection::test_auto_fa2_rejects_paged_kv_it_cannot_read` (CPU) forces automatic selection to FA2 (FA3 and FA4 not installed, or FA4 on SM80/SM120) and runs prefill and decode with 64-token blocks on SM80/SM90/SM100, and with unequal head dims on SM120. It expects the `ValueError` with the device's remedy, and checks that the FA2 kernel is not called. The 8 cases fail without the check. `test_auto_fa2_runs_paged_kv_it_can_read` checks that FA2 still runs 256-token blocks.
- `tests/unit_tests/inference/contexts/test_dynamic_context.py::TestDynamicContext::test_pinned_flash_attention_2_rejects_unsupported_paged_kv` (1 GPU, no flash-attn needed) builds a context with FA2 pinned for MHA with 64-token blocks and for MLA, and expects the `ValueError`. Both cases are expected to fail on `main`; the GPU run below could not check that (see there). `test_paged_kv_accepted_where_the_kernel_reads_it` checks that FA2 with 256-token blocks, and FA4 or automatic selection with 64-token blocks, still build. `test_pinned_flash_attention_2_checks_only_layers_that_run_it` checks that a hybrid with attention layers is rejected and one whose KV layers are all DSA is accepted; the DSA case fails on the previous commit.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), at this commit, the regression tests pass (56 cases), including the 8 `test_auto_fa2_rejects_paged_kv_it_cannot_read` cases, the three context tests and the long-context engine test. On `main` the only evidence from this run is an import failure: `test_attention.py` imports `_flash_attn_majors`, which this PR adds, and that collection error stops the run before any test runs, the pinned-FA2 context test included. The step 3 GPU repro of R11-F7 reproduced the bug on `main` on H100 (4 of 4 cases): MLA and MHA with FA2 pinned and 64-token blocks are accepted by the config and the context, then the first prefill fails inside flash-attn. The neighbor tests (`test_softmax_scale.py`, `TestFlashDecodeAndPrefillSoftcap`, `test_prefix_caching_single_token_effective_chunk`) pass (18, 8 and 1 cases).

**Merge order.** #8584 and the FA4/quack-kernels lock PR (#8860) both touch FA4 selection in `attention.py` and merge cleanly in either order. Land #8584 first: it adds FA4's `flash_decode_and_prefill` determinism replay, which the lock PR's FA4 bump (b24 to b29) otherwise lands without. #8584's FA4 support tables were re-checked against b37, which the lock PR first moved to; they have not been re-checked against b29.
