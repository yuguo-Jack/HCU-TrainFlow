# Warn on optimizer, TP and helper fallbacks to WORLD or the global grid

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8734) · state: closed · merged: False

## Original PR description

Depends on #8017 (which contains #6259), #8031, #8042 and #8049 (which contains #6293). Please review the diff from the merge of their heads: [scoped diff](https://github.com/Connor-XY/Megatron-LM/compare/d2755470e4...yx/pstate-g4-optimizer-boundary). The #8042 merge resolves its conflict with #6259 in `megatron/core/optimizer/__init__.py`: it keeps #6259's error for a missing collection and #8042's `set_duplicate_filter_groups` call. The #8049 merge regenerates the process-group allowlist. This PR now also carries #8750 and #8764, which close in its favor.

Land this after #8737, #8738 and #8752, or stock training reaches the new warnings. Until #8737, stock `pretrain()` calls `model_parallel_cuda_manual_seed` without groups and warns once per process. With #8738 and #8752, stock training passes its collection to `DistributedDataParallel` and `get_megatron_optimizer`, so it reaches none of the group-helper warnings.

**Why.** The optimizer reduces the gradient norm, the zero count and the found-inf flag over its grad-stats group. When that group is `None`, `torch.distributed` uses WORLD. WORLD can span other optimizer instances, other models in the job and ranks that never step, and nothing reports it. This happens for:
- a `DistributedOptimizer` without `grad_stats_parallel_group`, for example from a collection with `intra_dist_opt=None`;
- a non-distributed optimizer with `grad_stats_parallel_group=None`, for example from a collection with `mp=None`;
- a `LayerWiseDistributedOptimizer` built from a collection without `intra_dist_opt`.

Raising is not possible yet. Megatron-Bridge sets `intra_dist_opt=None` on purpose for a single optimizer instance, where WORLD holds the right ranks, and core's own setup error told callers to use `None`.

Other paths read the global `parallel_state` grid, with no warning, when the caller omits their groups:
- a non-distributed optimizer that never got the grad-stats attribute, which reads the global model-parallel group;
- the duplicate filters `param_is_not_tensor_parallel_duplicate` and `param_is_not_gtp_duplicate`, for a hand-built optimizer or a direct caller;
- `model_parallel_cuda_manual_seed` and `gtp_replica_rank`;
- three helpers in `megatron/core/process_groups_config.py`, which the process-group checker exempts, so their reads were not counted either:
  - `resolve_gtp_remat_group`, when its caller passes no collection, or one without the `gtp_remat` or `expt_gtp_remat` field;
  - `setup_process_groups_for_ddp`, when `DistributedDataParallel` is built without `pg_collection`;
  - `ProcessGroupCollection.setup_process_groups_for_optimizer`, a public static method that reads about fourteen groups when it is called without a collection.

A caller on its own grid got the global ranks with no signal, so these fallbacks could not be removed on a published schedule.

**What.** Every fallback below emits a `ProcessGroupFallbackWarning` (deprecated in 0.21, removed in 0.23) and returns the same groups as before. Each warns once per owner and argument, and every time under an `error` filter.
- Grad-stats groups:
  - `DistributedOptimizer.get_grad_stats_parallel_group` and `MegatronOptimizer.get_grad_stats_parallel_group` warn on a `None` group. `LayerWiseDistributedOptimizer` warns at construction, because it reads the attribute directly. This warning has its own message, since the fallback is the default group, not a `parallel_state` group, and it fires once per optimizer class.
  - `MegatronOptimizer.get_grad_stats_parallel_group` warns through `warn_global_process_group_fallback` before it reads the global model-parallel group.
  - The setup error for a collection without `intra_dist_opt` asks for the ranks of one optimizer instance instead of suggesting `None`.
- Duplicate filters: both warn and name the missing argument (`tp_group` or `expert_tp_group`, `gtp_group` or `expert_gtp_group`). They then resolve the group through `resolve_process_groups` or `resolve_gtp_remat_group` instead of calling the rank accessors. Without a global grid the GTP filter still keeps every parameter.
- `model_parallel_cuda_manual_seed` without a collection:
  - Omitted TP, EP and expert-TP ranks come from `resolve_process_groups`.
  - Omitted GTP-remat ranks and sizes warn and come from `resolve_gtp_remat_group(None)`, as the layers resolve them without a collection. Those axes stay off when there is no global grid.
  - The global TP, EP and expert-TP groups are resolved only when one of those ranks is missing. A builder that passes them before any global grid exists, like Megatron-Bridge's MIMO builder, keeps seeding.
- `gtp_replica_rank` resolves `dp_cp`, or `expt_dp` for a routed-expert weight, through `resolve_process_groups` when `parallel_state` is initialized. It returns 0 in a single-process save, and raises `RuntimeError` when there is no group to elect a writer over, as before.
- `VocabParallelEmbedding`, `ColumnParallelLinear` and `RowParallelLinear` read the replica group of their GTP shards from the collection field instead of `getattr` with a default. An unset field still stamps no group, and checkpointing then takes the warned fallback.
- Group helpers:
  - `setup_process_groups_for_ddp(None, ...)` warns as `DistributedDataParallel` before its first read.
  - `setup_process_groups_for_optimizer(None, ...)` warns under its own name before its first read, so an error filter stops it before the grid is touched. It names itself rather than a caller because it is public. Its two in-repo callers, the adam/sgd and the emerging-optimizer paths of `get_megatron_optimizer`, pass the collection that `get_megatron_optimizer` resolved. #8752 makes that resolution warn when it gets no collection, so only direct callers that omit the collection reach this warning.
  - `resolve_gtp_remat_group` takes a keyword-only `owner` and warns under it when the global group it falls back to shards weights, that is, spans more than one rank. A missing or single-rank group means GTP is off, which is what an absent field will mean once the fallback is removed, so that case stays silent. The warning names `pg_collection`, or the missing `pg_collection.gtp_remat` or `pg_collection.expt_gtp_remat` field.
  - Callers of `resolve_gtp_remat_group` name themselves: the Transformer Engine linears, `ColumnParallelLinear`, `RowParallelLinear`, `VocabParallelEmbedding`, `InferenceLinear`, `MoELayer` for its latent projection, `TensorParallelMuon`, `get_megatron_optimizer` for its duplicate filters, and `setup_model_and_optimizer` for the GTP NCCL user-buffer pools. `param_is_not_gtp_duplicate` and `model_parallel_cuda_manual_seed` already warn about their own fallback, so they pass `owner=None`. Without an `owner`, the warning names `resolve_gtp_remat_group`.
  - The docstrings of `DistributedDataParallel` and both setup helpers say that the fallback is deprecated.
- The checker goes from 173 reads to 164, 3 of them guarded. Twelve accessor reads go away. Six become 3 guarded `resolve_process_groups` calls. The other 6 are GTP-remat reads that now go through `resolve_gtp_remat_group`, which the checker exempts.

Return values are unchanged everywhere. The optimizers that `get_megatron_optimizer` builds and the training parameter statistics pass their groups and do not warn.

**Compatibility.**
- Numerics, groups and return values are unchanged. On the standard grid, the seeds, the duplicate filtering and the checkpoint writers use the same groups and ranks.
- Optimizers that `get_megatron_optimizer` builds take their groups from the collection and pass `use_global_fallback=False`, so stock runs do not warn there. No unit test runs the stock factory under an `error` filter yet. End-to-end training smokes with the other process-group changes from #6307 applied passed with fallbacks fatal before the sync, and record no fallback warning after it.
- Bridge runs with a single-instance `intra_dist_opt=None`, Muon layer-wise runs and hand-built optimizers print one warning per process and keep working. Bridge's `param_is_not_tensor_parallel_duplicate(param)` call without groups also warns once.
- Code that builds `DistributedDataParallel` without `pg_collection`, calls `setup_process_groups_for_optimizer` without a collection, or builds a GTP-sharded layer without a collection that sets the GTP fields now warns once, and raises under an error filter.
- `resolve_gtp_remat_group` gains a keyword-only `owner`. Existing calls keep working and warn under the helper's name.
- The fallbacks read group ranks. A rank forced with `set_tensor_model_parallel_rank` or the expert rank setters no longer replaces the group rank there. With `lazy_mpu_init`, which sets a provisional TP rank, the seed then uses the TP group rank. #8737 makes the same change for training and asks for sign-off on it. Checkpoint tools set rank overrides but neither seed nor call these filters.
- About 700 test calls of `model_parallel_cuda_manual_seed(123)` without a collection now warn once per process. They are not converted here. The snippet in `megatron/core/QuickStart.md` makes the same call.
- Without groups, the duplicate filters build a collection for every parameter, which is slower than one accessor call. In-repo optimizers pass their groups, so only hand-built optimizers and direct callers pay for it.
- `gtp_replica_rank`'s warning names the `explicit_group` argument, which the checkpoint path never passes. What is actually missing is `dp_cp` or `expt_dp` in the layer's collection. The `RuntimeError` text says so.
- `optimizer.py` imports #8049's private `_FALLBACK_WARNING_SKIP_PREFIXES` and keeps its own once-per-owner registry for the WORLD warning. A shared emit helper in `process_groups_config.py` would be cleaner. I can switch to one if reviewers prefer.
- The `mp` and `tp_ep_pp` setup errors in `process_groups_config.py` still say to set the group to `None` if it is not needed. A `None` there now makes the optimizer warn about WORLD. Should those messages change here too?
- The WORLD warning suggests `pg_collection.intra_dist_opt` as the fix. That does not help a caller like Megatron-Bridge, which sets `intra_dist_opt=None` on purpose. Should the warning name the ranks of one distributed-optimizer instance instead?
- The new `DistributedOptimizer.get_grad_stats_parallel_group` docstring says `get_megatron_optimizer` sets the group from `intra_dist_opt`. Under Megatron-FSDP it uses `mp` for `no_shard` and `dp_cp` when the outer DP level shards the optimizer state. The docstring should say so, and I'll fix it in review.
- #8042 looks the GTP groups up through `resolve_gtp_remat_group`, which can differ from `getattr(pg_collection, 'gtp_remat', None)` when `gtp_remat` is unset. Please confirm that this is intended.
- Not covered here: `resolve_gtp_remat_group` reads the grid before it decides whether to warn, so an error filter cannot stop that read, and the fallback stays silent when GTP is off. #8769 builds on this PR and moves the warning ahead of the read.
- Landing conflicts, all in import or argument lines. Whichever lands second keeps both sides:
  - #7029 adds teardown imports next to this PR's import in `generalized_tensor_parallelism.py`.
  - #8730 changes the `parallel_state` import block in `tensor_parallel/layers.py` that this PR trims.
  - #8035 adds a `pg_collection=` argument next to this PR's `owner=` in `InferenceLinear`.
  - #8752, which lands first, imports other names from `process_groups_config` in `optimizer/optimizer.py`. This PR then takes the union of both import lists.
  - #8060 merges cleanly, but once it and this PR are both in, `layers.py` no longer uses `get_tensor_model_parallel_rank`, and that import has to go.
