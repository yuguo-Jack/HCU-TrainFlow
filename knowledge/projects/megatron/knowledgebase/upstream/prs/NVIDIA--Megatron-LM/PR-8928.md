# Log the per-bucket shard size and largest params in the layerwise layout

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8928) · state: open · merged: False

## Original PR description

## Summary

The layerwise layout already reports its aggregate overhead:

```
Layerwise param layout: 199 params, 1 buckets, dp_size=60, total_param_numel=2566062080,
total_buffer_numel=12582912000, total_padding=10016849920 (shard_imbalance=10016849920),
overhead=390.4%
```

That says a buffer is wasteful, but not which bucket or which tensor made it so. A shard is the fullest bin after packing, so one parameter larger than a balanced share forces every shard in its bucket to its size, and no rebalancing helps. Many similar parameters that merely pack poorly are a different problem with a different fix (more buckets, or a different `bucket_size`).

This adds one INFO line per bucket, next to where the padded shard size is computed:

```
Layerwise bucket 0: shard=209715200 x dp=60, real=2566062080, largest=[...]
```

If `largest[0]` equals the shard size, the bucket is held hostage by one tensor; if the largest few are well below it, packing is the problem.

- Numels rather than shapes: the function receives unnamed parameters, and a numel identifies a tensor as well as a shape here while keeping the line short.
- One line per bucket, so log volume follows bucket count, not parameter count.
- `chunk_params` can contain `None` (the shared-embedding path), hence the filter.
