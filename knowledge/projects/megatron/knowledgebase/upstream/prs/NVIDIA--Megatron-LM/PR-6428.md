# Test streaming responses with async scheduling

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/6428) · state: closed · merged: False

## Original PR description

## What does this PR do?

This PR adds a standalone end-to-end functional test for streaming responses under asynchronous scheduling. It launches the real OpenAI-compatible inference server once with legacy scheduling and once with asynchronous scheduling, then sends the same synchronized concurrent workload to both.

The test adds:

- one self-contained server runner that sends six ordinary requests and one streaming request at the same time;
- real HTTP and server-sent-event coverage through the production server;
- checks for incremental text, present and finite per-token log probabilities, and terminal response reconstruction;
- exact cross-mode comparison of the streamed text, token IDs, finish state, and chunk sizes; and
- one H100 functional-test recipe.

## How was the test matrix determined?

The async-scheduling unit matrix exercises scheduler behavior in process, while streaming unit tests exercise individual client and response-formatting components. The remaining gap was the boundary between them: a real server had not been tested while asynchronous scheduling served a streaming request under concurrent admission pressure.

The test therefore uses a focused differential comparison. It runs the same stream-enabled workload once with `--inference-dynamic-batching-async-sched-mode=legacy` and once with `--inference-dynamic-batching-async-sched-mode=async`. Six simultaneous non-streaming requests keep the server busy while the streaming request progresses, and the server admits at most two requests at a time.

This is the separately approved end-to-end functional exception, not another pairwise-matrix layer. It does not repeat stream-disabled cells and receives no pairwise-coverage credit.

## What combinations are tested?

### Scheduler comparison (two sessions)

Both sessions use the same local checkpoint and tokenizer fixture, deterministic settings, TP2/PP2/DP2 topology, prompts, and synchronized request release. Only the scheduling mode changes.

| Session | Scheduling mode | Concurrent workload |
| --- | --- | --- |
| Control | `legacy` | Six ordinary requests plus one streaming request |
| Treatment | `async` | The identical six ordinary requests plus one streaming request |

### Request mix (seven requests per session)

All seven requests use greedy generation, ignore EOS, and request log-probability data. A barrier releases them together against a two-request active-capacity limit.

| Request type | Count | Generated-token counts | Streaming interval |
| --- | ---: | --- | ---: |
| Ordinary completion | 6 | 24, 6, 18, 8, 20, 10 | — |
| Streaming completion | 1 | 16 | 2 |

## How are results checked?

Each ordinary request must return one nonempty completion, finish because it reaches its requested length, and contain the expected number of token IDs and finite log probabilities.

The streaming request must use the SSE content type, emit valid `data:` records and a final `[DONE]` marker, produce multiple one- or two-token deltas totaling 16 tokens, and emit exactly one terminal result. Every delta and the terminal result must contain the expected number of finite log probabilities. Joining the text deltas must reproduce the terminal text exactly.

Finally, the legacy and async streamed results must agree exactly in text, token IDs, finish reason, delta sizes, and response structure. Numeric log-probability values are validated independently in each session because different dynamic batch shapes can produce small BF16 score differences; exact generated content is compared only for the streaming request under test.

## Scope

This PR adds one functional-test runner and one H100 recipe. It changes no production code, existing functional test, prompt, or golden output. The runner supplies the explicit architecture used by the repository's existing Qwen3-8B functional tests because the converted checkpoint does not store model arguments.

The selected checkpoint and tokenizer are locally provisioned test fixtures, not subjects of coverage. The behavior under test is the interaction between real HTTP streaming and asynchronous scheduling. The six ordinary completions provide concurrent load and are validated within each session; only the streaming response is the cross-mode oracle.
