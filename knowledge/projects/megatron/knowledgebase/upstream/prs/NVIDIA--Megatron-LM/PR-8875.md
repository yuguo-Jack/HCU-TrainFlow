# [Inference] Give both sampling backends one contract for top-k + top-p, temperature and greedy

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8875) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes the torch and FlashInfer sampling backends implement one sampling contract: top-k and top-p together (top-p over the renormalized top-k set), temperature applied in fp32, greedy (`top_k == 1`, and temperature 0 for every caller) as the lowest-index argmax, and a top-k at or above the vocabulary as no top-k, settled at admission. Before, each backend missed one part of it, and two of the gaps crashed the engine.

## Bugs

1. **Torch backend: `top_k` + `top_p` kills the engine (crash, default backend).** `TorchSampling.filter_logits` and `sample_from_logits` asserted `"Cannot have top-p and top-k both active"`. Nothing rejects the combination at admission (`SamplingParams`, `add_request` or the HTTP endpoints), so the assertion fires inside the engine step and fails every in-flight request. Under the coordinator the exception leaves `run_engine_with_coordinator` and the engine process exits. A client does not have to ask for it:
   - `/v1/completions` and `/v1/chat/completions` fill omitted fields from the model's `generation_config.json`. A Qwen-style card (`top_k: 20, top_p: 0.95`) gives every request both filters.
   - `do_sample: false` becomes `top_k = 1` and keeps a declared `top_p`, so a greedy request crashes the engine too.
2. **Torch backend: temperature applied in bf16 (silent wrong distribution).** `filter_logits` divided the logits by `T` in their own dtype. They reach the sampler in bf16 with `--cuda-graph-impl local` (the logits are copied into a `params_dtype` buffer), with PP > 1, and with a model not wrapped in `Float16Module`. At LM-head magnitudes (max logit 15-30) the bf16 spacing of `l / T` is up to 0.5, which moves 1-4% of the sampling mass (TV) and up to ~20% of the top token's probability. The FlashInfer backend and the processed log-probs already scale in fp32, so sampling and processed log-probs disagreed.
3. **Torch backend: `top_k` at or above the vocabulary size kills the engine (crash).** Nothing compares `top_k` with the vocabulary at admission, so `filter_logits` asserts `top-k is larger than vocab size.` inside the step (for example `/v1/completions` with `top_k=200000`), with the same outcome as bug 1. FlashInfer already treats it as no filter.
4. **FlashInfer backend: greedy picks among tied maxima by batch row (determinism).** Temperature 0 maps to `top_k = 1`. FlashInfer has no greedy path: those rows go to `top_k_sampling_from_probs` (all-greedy batch) or the joint kernel (mixed batch). Their top-k acceptance keeps every token tied at the bf16 maximum and draws among them with the batch row as the Philox subsequence. On H100, 1024 identical rows with ids 7 and 11 tied returned `{7: 536, 11: 488}`. The torch backend returns 7, the first maximal index.

## Fix

- `TorchSampling.filter_logits` scales an fp32 copy of the logits (`to(torch.float32, copy=True)` replaces the `clone()`), so the result equals `fp32(logits) / T` whatever dtype arrives. The logits buffer may stay bf16: the output GEMM is bf16, so only the division needed fp32.
- `filter_logits` applies top-k, then top-p over the renormalized top-k set (FlashInfer's `top_k_first`). Both assertions are removed. Sampling and the torch processed log-probs share `filter_logits`, so both follow.
- Greedy rows take the lowest-index argmax on both backends, with or without a top-p (top-1, then top-p, keeps that token):
  - `FlashInferSampling.sample_kernel` returns the argmax for an all-greedy batch without launching a kernel, as `TorchSampling` already did. In a mixed batch it replaces the greedy rows' draws with `torch.where(top_k == 1, argmax, sampled)`. Whether a batch has greedy rows is read from the pinned CPU metadata, so there is no host sync. The kernels still run for the other rows with the same RNG offsets as before.
  - `TorchSampling`'s all-greedy shortcut no longer requires `top_p == 0`.
  - Processed log-probs of a greedy row are one-hot on that token in both backends. Before, both kept the tied maxima and reported `log(1/m)`.
- **Admission.** `DynamicInferenceEngine._add_request` admits a `top_k` at or above the vocabulary size as no top-k (`top_k = 0`), next to the request's top-p. Normalizing, rather than rejecting, matches the existing `SamplingParams` contract: it already maps the other no-op filter values to the disabled sentinels (`top_k <= 0` to 0, `top_p >= 1.0` to 0.0), and a top-k that keeps the whole vocabulary filters nothing. FlashInfer already treated it that way, and `_add_request` already clamps an oversized `num_tokens_to_generate` instead of rejecting it. The engine is the first place that knows the vocabulary (`controller.vocab_size`, the width the samplers see), so the check lives there; the samplers' `top_k < vocab_size` assertion becomes an invariant admission guarantees.
- **Temperature 0 is greedy for every caller.** `SamplingParams._normalize_filters` maps `temperature == 0` to `top_k = 1, top_p = 0.0`, so the offline, RL and library APIs get the lowest-index argmax and one-hot processed log-probs, as the HTTP endpoints and Dynamo did. Their three copies of that mapping (`/v1/completions`, `/v1/chat/completions`, `build_sampling_params`) are removed.
- The user guide's `SamplingParams` table states the order of the filters, the greedy rule, temperature 0 and the top-k at or above the vocabulary.
- The legacy static text-generation server no longer rejects `top_k` with `top_p`; `tests/functional_tests/dynamic_inference_functional_tests.md` marks that known issue resolved.

## Notes for reviewers

- **Changed numerics.** Sampling with `T != 1` on bf16 logits (CUDA graphs, PP > 1, unwrapped models) now draws from the fp32 distribution, so seeded generations there change. An all-greedy FlashInfer step no longer advances the sampling RNG; torch already behaved this way. Later random draws in such runs shift. `SamplingParams(temperature=0.0)` from the offline, RL or library API now samples the lowest-index argmax with one-hot processed log-probs instead of drawing among tied maxima at T = 1e-6 (no functional test runs with temperature 0).
- **FlashInfer functional goldens.** All four `*_flashinfer` dynamic-inference functional tests (`gpt_dynamic_inference_tp1_pp1_583m_flashinfer`, `gpt_dynamic_inference_tp4_pp1_583m_flashinfer`, `gpt_dynamic_inference_tp1_pp1_583m_prefix_caching_chunked_prefill_flashinfer`, `hybrid_dynamic_inference_tp1_pp1_dp8_583m_flashinfer`) run `--top_k 1` with `--inference-repeat-n 8` and compare generated tokens and log-probs. On `main` FlashInfer breaks a bf16 tie at the maximum by batch row; with this PR it takes the lowest index, so a tie in those goldens changes tokens. They have not run with this PR; run them on H100 and refresh their goldens if they move.
- **Cost.** A torch top-k + top-p bucket sorts the vocabulary once for top-p, as a top-p-only bucket does. The torch filter's copy is fp32 instead of the logits' dtype; the softmax after it already allocated fp32. FlashInfer pays an argmax and a `torch.where` only in batches that mix greedy and sampled rows. Running top-p on the `torch.topk` values instead of the whole vocabulary would sort far less, but it would drop logits tied at the k-th value, which both backends keep in the top-k set; an exact version needs the size of the kept set, a host sync or a data-dependent shape. Left for a follow-up.
- **Ties at the k-th logit for k > 1** are kept on both backends, as before.
- **The deprecated legacy static engine** (`StaticInferenceEngine(legacy=True)` or its fallback) does not admit requests through `_add_request`, so a library call there with `top_k` at or above the vocabulary still fails that `generate` call on the sampler's assertion; it is not a shared engine step. Its HTTP server caps `top_k` at 1000.
- **#8572** (FlashInfer processed log-probs determinism) changes the same `log_probs_kernel`. The two branches merge cleanly, and the one-hot greedy override composes with its `top_k_mask_logits`. If #8572 lands first, its replay test becomes the one registered for `flashinfer_sampling.py`, and this PR adds a greedy replay case to it (the all-greedy shortcut, the mixed-batch `torch.where` and the one-hot log-prob override) rather than taking the `determinism-exempt` label. If this PR lands first, #8572 needs that case when it registers the file.
