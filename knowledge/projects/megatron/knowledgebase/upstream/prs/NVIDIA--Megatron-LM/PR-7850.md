# fix: prevent fused softmax from ignoring sliding-window attention

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7850) · state: closed · merged: True

## Original PR description

## Summary

Fix `FusedScaleMaskSoftmax` selecting the Apex fused softmax path when sliding-window attention is configured.

The Apex fused softmax kernels do not accept a `window_size` parameter. When a windowed configuration satisfied the existing fusion eligibility checks, it could therefore enter the fused path and silently compute full causal attention instead of applying the configured sliding-window restriction.

This change prevents windowed configurations from selecting the Apex fused kernels and allows them to use the existing PyTorch softmax path, which applies the sliding-window mask correctly.

## Root Cause

`FusedScaleMaskSoftmax.is_kernel_available()` checked the existing fusion, dtype, mask, and shape requirements but did not account for `window_size`.

As a result, a configuration such as:

```python
window_size=(4, 0)
scaled_masked_softmax_fusion=True
```

could still select the Apex fused kernel even though the kernel has no mechanism to represent the configured window.

## Fix

Add `self.window_size is None` to the fused-kernel eligibility condition.

Windowed configurations now fall through to `forward_torch_softmax()`, where the configured sliding-window mask is applied.

Non-windowed configurations remain eligible for the existing Apex fused path.

The windowed configuration therefore avoids the Apex fused path and produces zero probability outside the configured attention window, while the non-windowed configuration continues to use the fused implementation.
