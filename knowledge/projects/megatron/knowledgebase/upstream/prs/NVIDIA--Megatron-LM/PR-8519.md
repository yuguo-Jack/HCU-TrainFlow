# Validate DistOpt instance layouts

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8519) · state: open · merged: False

## Original PR description

This PR was prompted by a larger effort to improve support for multi-site training (https://github.com/NVIDIA/Megatron-LM/issues/8482), but is relevant to single-site training as well.

### Problem statement

The current implementation of multiply-instantiated DistOpt uses the same inter-instance process groups for both "expert" and "dense" (non-expert) parameters. Concretely,  

```
# These three exist:
_INTRA_PARTIAL_EXPERT_DATA_PARALLEL_GROUP
_INTER_PARTIAL_EXPERT_DATA_PARALLEL_GROUP
_INTRA_PARTIAL_DATA_PARALLEL_GROUP_WITH_CP

# This one does not:
# _INTER_PARTIAL_DATA_PARALLEL_GROUP_WITH_CP
# Non-expert parameters actually use the nominally expert-specific _INTER group!
```

For the inter-instance process group to be well defined, it is necessary and sufficient that the number of DistOpt instances divides both `DP * CP` and `EDP`, and the (default) `tp-cp-ep-dp-pp` or (non-default) `tp-cp-ep-pp-dp` rank order is used. The current logic includes the two divisibility checks, but **does not check the rank order**.

The following example shows concretely that this missing check is necessary. Use 4 workers, and set `CP = EP = DP = EDP = num_distopt_instances = 2` (`GTP = EGTP = 1`). This satisfies the divisibility checks (2 divides both 4 and 2). Now pass (non-default) `order="tp-cp-dp-ep-pp"` directly to `initialize_model_parallel`. Here is the result:

```
Parameter class     Replica groups	  Required inter-instance pairs
Dense	            [0,1,2,3]	      (0,2), (1,3)
Expert	            [0,1], [2,3]	  (0,1), (2,3)
```

As you can see, the required inter-instance pairs are different for the two parameter classes. When Megatron reuses the expert-derived groups for the dense parameters, it pairs the wrong dense gradient shards. This type of failure may be hard to detect.

### How this PR fixes it

This PR tries to catch such failures earlier, in `parallel_state.py`, and provide the caller with more useful feedback.

Rather than racking our brains reasoning about all possible orderings, then later needing to repeat/extend this reasoning when things like GTP are added, I am proposing to simply validate the inter-instance groups directly.

### Side comment 

I was curious about this design decision. Elsewhere, the two parameter classes are treated with separate collectives on disjoint buffers/buckets, so why are we making them share an inter-instance process group? Based on internal discussions with colleagues, I've concluded that this design decision was motivated by simplicity, and a concern about the overhead of additional process groups. However, this simplification introduces constraints on the process grid and parallelism parameters, and I'd like to revisit it in the future (in other PRs).
