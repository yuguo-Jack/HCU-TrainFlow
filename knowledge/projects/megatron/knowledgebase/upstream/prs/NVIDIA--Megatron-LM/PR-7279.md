# Fix mixed-dtype gradient norms and clipping

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7279) · state: open · merged: False

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Group gradients by dtype before fused L2-norm and clipping-scale calls, so mixed BF16/FP32 lists produce the intended norm and in-place scaling.

The fused backend tested here interprets a list using its first tensor's dtype. For example, `[BF16[128], FP32[128]]` filled with `1/64` returns `0.2165063471` instead of `0.25`. Reversing the order can read beyond the logical BF16 view. Scaling has an independent defect: even with coefficient `0.5` supplied directly, mixed lists leave some elements unscaled or modify padding beyond the gradient view. The reproductions use padded backing allocations.

The change:

- Buckets L2-norm inputs locally and sums their squared norms before the existing distributed reductions. This preserves collective order for empty ranks and ranks with different dtype sets, and accumulates into the existing zero-valued CUDA tensor.
- Buckets both scalar- and tensor-coefficient scaling calls, and avoids calling fused kernels with empty lists.
- Adds focused numerical regressions for both mixed orders, decoupled gradients, scalar- and tensor-coefficient clipping, a non-vector-aligned length, backing-storage preservation, empty gradients, and asymmetric rank ownership. Ordinary `.grad` is also exercised by the mixed-dtype determinism tests.
- Adds mixed-dtype norm/clipping bit-exact replay under side-stream contention to the existing registered optimizer determinism tests.

The existing single-device gradient-list contract is retained. No kernel implementation or optimizer-state layout changes are required.

## Validation

The GPU component results below describe the original fix at `333ecc9`. Validation of the review cleanup is recorded separately below.

- Native two-rank GB200 investigation with PyTorch `2.11.0+cu130` and the Transformer Engine backend: all 48 norm boundary cases per rank matched first-dtype byte interpretation, with 15 incorrect logical norms. Both scaling APIs failed on both mixed orders. Bucketed controls preserved padding and matched the logical reference.
- Matched caller regression: the original had 24 numerical failures in 96 cases per rank; the corrected caller passed those cases plus four empty-list cases per rank. Mixed-buffer and FP32-buffer DDP/DistributedOptimizer/FusedAdam fixtures each completed eight arms per rank.
- The production file on the PR base is byte-identical to the original file used for that investigation. The PR adds typing and repository formatting to the validated implementation.
- Repository `tools/autoformat.sh`: Black, isort, pylint, and Ruff passed. Mypy could not resolve Torch/TE/Apex/pytest imports in the isolated local lint environment.
- `python3 tools/check_kernel_determinism_coverage.py --base-ref origin/main`: passed.
- Exact PR tests on two GB200 ranks with the native TE backend: the original caller produced 29 expected failures out of 105 unit cases per rank; the fixed caller passed all 105 with no skips or errors. Both mixed-dtype determinism cases passed on both ranks, including four bit-exact replays with side-stream contention. Test dependencies were staged separately from the pinned runtime; unrelated top-level suite fixtures were excluded for this focused run.

Review cleanup (`09f6e03`): DFW job `19072876` completed on two H100 80GB GPUs with PyTorch `2.11.0+cu130` and Transformer Engine `2.15.0+42b84005`. The runner verified exact source hashes and native TE dispatch; unrelated top-level suite fixtures were excluded. Local formatting/lint and the determinism coverage check also pass.

The reporter in [#7338](https://github.com/NVIDIA/Megatron-LM/issues/7338#issuecomment-5725704816) also completed a three-step H100 training smoke after adapting the caller patch to their older `dev` checkout. Following up on my report in #7338 (same cluster): a second production caller that produces the mixed-dtype list, this time from RL rather than SFT.

**Setup**: verl GRPO (`main@45a40312`) on the Megatron-Bridge backend, Megatron-LM `43e45e13` (Megatron-Bridge 0.6.2's `.dev.commit`, which predates this PR), DeepSeek-V4-Pro (61 layers, 1.57 T) on 64 H100-80GB nodes, actor PP32/EP8/DP2, `use_precision_aware_optimizer=True`, `main_grads_dtype=bf16`, DDP `grad_reduce_in_fp32=False`, `optimizer_cpu_offload=True` (HybridDeviceOptimizer).

**What the caller sees**: on every rank and every step the list handed to `get_grad_norm_fp32` / `clip_grad_by_total_norm_fp32` is mixed. DSv4's native fp32 parameters (hc alpha/bias, ape, attn_sink) keep fp32 grads while everything else has bf16 decoupled grads. Logged per rank by our shim:

```
groups={'torch.float32': 1, 'torch.bfloat16': 37}    # Pro, PP32 (37–66 bf16 tensors depending on the stage)
groups={'torch.float32': 9, 'torch.bfloat16': 321}   # Flash (43 layers), PP8
```

**Result**: with a caller-side per-dtype split installed at runtime (bucket by dtype, sum of squared per-bucket norms, then the existing single all-reduce; per-bucket in-place scaling — the same contract as this PR, re-implemented as a monkeypatch because we are pinned to `43e45e13`, so this is **not** a validation of this PR's code) the runs are healthy: 5-, 3-, 2-, 3- and 13-step GRPO runs, rollout/actor log-prob Pearson 0.994–0.998, HF checkpoint save/resume continuing the metrics. We did not run the RL path without the split; the crash for this parameter mix is the one documented in #7338.
