# [Inference][MoE] Rule out fused-finalize FlashInfer tactics for deterministic BF16 experts

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8574) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes BF16 FlashInfer expert layers deterministic and batch invariant in deterministic and batch-invariant mode, whichever GEMM2 tactic FlashInfer's autotuner selects.

**Bug.** Config validation allows selectively-BF16 expert layers inside an MXFP8 model on the FlashInfer backend in batch-invariant mode. These layers call `fused_moe.cutlass_fused_moe` without `use_fused_finalize`, so FlashInfer also offers GEMM2 tactics that fuse the finalize into the GEMM2 epilogue. Those tactics sum each token's top-k routes with BF16 atomics, whose order is not fixed. FlashInfer documents this path as not deterministic run to run.

The untuned default tactic does not fuse the finalize, and Megatron never runs FlashInfer's autotuner itself. However, once the autotuner holds a tuned tactic, the fused path can be selected, and nothing in Megatron prevents it. That happens with a `flashinfer.autotune()` warmup anywhere in the process, a loaded autotune cache, or `FLASHINFER_AUTOTUNER_LOAD_FROM_FILE=1`.

On H100 with FlashInfer 0.6.16.post3, the runner offers 81 GEMM2 tactics, 36 of them fused-finalize (45 remain with `use_fused_finalize=False`). All 36 are neither deterministic nor batch invariant. For one of them, 192k of the 1M outputs differ between replays; for another, a token's output differs in 575 of its 1024 elements across co-batch sizes. With FlashInfer 0.7.0.post1 in the CI image, the first fused-finalize tactic (18) fails the same way. The same bug affects BF16 FlashInfer layers under `torch.use_deterministic_algorithms`.

**Root cause.** The batch-invariance guarantee for these layers relied on FlashInfer staying untuned. The per-token NVFP4 path already requests the unfused finalize in these modes (`flashinfer_nvfp4.py`); the BF16 path did not.

**Fix** (`megatron/core/transformer/moe/experts.py`):
- Under deterministic algorithms or batch-invariant mode, the BF16 branch of `InferenceGroupedMLP._flashinfer_forward` passes `use_fused_finalize=False`, as the NVFP4 path does. FlashInfer then builds a runner that offers no fused-finalize tactic. The runner instance key and the autotune cache key both include the flag, and the C++ runner gates the fused epilogue on it too. Any tactic the autotuner can select therefore runs the separate finalize kernel, which reduces each token's routes in order.
- `use_fused_finalize` exists from FlashInfer 0.6.15 on, while `pyproject.toml` allows `>=0.5.0`. `HAVE_FLASHINFER_UNFUSED_FINALIZE` detects it by capability, as `experts.py` already does for TE. Older FlashInfer cannot turn off the fused finalize, so a config with `deterministic_mode` or `batch_invariant_mode` is rejected with a clear error.
- That check runs once, when a layer's BF16 FlashInfer expert weights are built: the lazy build at the layer's first forward, the eager step that already sets up the concatenated weights, not at every forward. This is the first point where a layer is known to be BF16. It is keyed on the config, like `assert_causal_conv1d_deterministic`, so `warn_only` and unrelated global flags do not affect it. MXFP8 and NVFP4 layers are not affected.

Outside these modes, nothing changes. Untuned runs in these modes already used an unfused GEMM2 tactic. The forward-time decision is a host-side flag test, with no sync or allocation, and is CUDA-graph safe.

**Tests.**
- `tests/unit_tests/determinism/kernels/test_moe_kernels.py::TestMoEModules` builds real inference BF16 experts (16 experts, top-8, squared ReLU) on the FlashInfer backend. A patched `AutoTuner.choose_one` stands in for a tuned autotuner cache and pins GEMM2 tactics.
  - `test_inference_flashinfer_bf16_experts_replay_for_every_gemm2_tactic[deterministic|batch_invariant]` exercises each mode in isolation, with the other one explicitly off. It first asserts that the runner FlashInfer uses offers no fused-finalize tactic; on main this fails immediately. It then bit-checks every GEMM2 tactic of that runner, plus the untuned default: a 1024-token batch must replay bit-exactly, and one of its tokens must give the same bits alone. Only FlashInfer's `RuntimeError` counts as a tactic being unrunnable, and at least half of the tactics must run.
  - `test_inference_flashinfer_bf16_fused_finalize_is_the_racy_path` is the negative control the determinism guide asks for. It records that the default runner's fused tactics race. It is `xfail(strict=False, raises=AssertionError)`, so an infrastructure error still fails it.
  - These GPU tests need FlashInfer >= 0.6.15 (the lock pins 0.7.0.post1) on SM90, SM100 or SM103. They also need FlashInfer's CUTLASS fused-MoE module already built, through `flashinfer-jit-cache` or a warm FlashInfer JIT cache, and skip otherwise. The first use of that module JIT-compiles over 200 CUTLASS translation units for every dtype combination. That took about 38 minutes on an H100 node with the CI image, longer than the 30-minute determinism bucket. With the module built, both modes and the control take seconds.
- `tests/unit_tests/inference/test_flashinfer_mxfp8.py` (CPU, mocked kernel):
  - `test_bf16_flashinfer_rules_out_fused_finalize_when_deterministic[default|deterministic|batch_invariant]` checks that the flag is passed only in these modes.
  - `test_bf16_flashinfer_weight_build_requires_unfused_finalize[deterministic_mode|batch_invariant_mode]` checks that older FlashInfer is rejected when the BF16 FlashInfer weights are built.
  - Both fail on main and pass with this fix.
- The manifest note for `moe_experts` is updated. `tools/check_kernel_determinism_coverage.py --base-ref origin/main` passes.

Follow-up, not in this PR: with the BF16 FlashInfer path now batch invariant, the config rule that rejects batch-invariant mode for an all-BF16 FlashInfer model could be revisited.

## Follow-up: the CUTLASS MXFP8 experts

After this branch was opened, `main` gained FlashInfer CUTLASS MXFP8 experts with ClampedRelu2 (#8013). `flashinfer_cutlass_mxfp8_moe` is a second `cutlass_fused_moe` call and did not pass `use_fused_finalize`. Under deterministic algorithms, a tuned or loaded autotuner cache could therefore still select an atomic fused-finalize GEMM2 tactic for these experts. The untuned default tactic is unfused, so the bug stays latent until FlashInfer autotunes in the process or loads a tuned cache. On GB200, every autotuned CUTLASS MXFP8 call kept FlashInfer's default (fused) finalize. Batch-invariant mode is already rejected for ClampedRelu2 by the config.

- **Merge of `main`** ("Merge main into fix/s3-flashinfer-bf16-bi-tactics"): no textual conflicts. The BF16 call keeps main's `clamped_relu2_limit` next to this branch's `use_fused_finalize`. Main's `forward()` now calls `_build_flashinfer_clamp_limit`, so the stand-in module in the weight-build test gains that method.
- **Fix:** one helper, `_cutlass_fused_moe_finalize_kwargs()` in `experts.py`, decides `use_fused_finalize` for both `cutlass_fused_moe` calls of `InferenceGroupedMLP`. The BF16 call passes it directly; the CUTLASS MXFP8 call passes it through a new `use_fused_finalize` argument of `flashinfer_cutlass_mxfp8_moe` (default `True`, FlashInfer's default). The weight-build check that rejects deterministic configs on FlashInfer < 0.6.15 runs for BF16 layers only. The CUTLASS MXFP8 layers need no such check: they need ClampedRelu2, and every FlashInfer release with ClampedRelu2 also has `use_fused_finalize`.
- **Tests:**
  - `test_flashinfer_mxfp8.py::test_cutlass_mxfp8_flashinfer_rules_out_fused_finalize_when_deterministic[default|deterministic|batch_invariant]` (CPU): the CUTLASS MXFP8 path passes `use_fused_finalize=False` in these modes and keeps FlashInfer's default otherwise. It fails at the merge commit and passes with the fix.
  - `test_moe_kernels.py::TestMoEModules::test_inference_flashinfer_cutlass_mxfp8_experts_replay_for_every_gemm2_tactic` (1 Blackwell GPU): under deterministic algorithms the runner must offer no fused-finalize tactic. Then every GEMM2 tactic, plus the untuned default, must replay a 4096-token, top-4 batch bit-exactly.
  - The `inference_mxfp8_quantization` manifest entry now lists `test_moe_kernels.py`, and `tools/check_kernel_determinism_coverage.py` passes.
  - The GPU results are at the end of the last follow-up section.

## Follow-up: review of the CUTLASS MXFP8 commit

- **The GB200 test runs in GB200 CI.** GB200 CI selects unit tests by the `launch_on_gb200` marker (`tests/unit_tests/find_test_cases.py`), so the CUTLASS MXFP8 replay never ran: it skips below SM10x, and H100 is the only other CI platform. It is now marked `launch_on_gb200`. On Blackwell it no longer skips. A FlashInfer without ClampedRelu2 or `use_fused_finalize` fails it. If the image has no `flashinfer-jit-cache` (which the FlashInfer MoE backend already requires for serving, `check_flashinfer_jit_cache_installed`), FlashInfer builds its CUTLASS fused-MoE module on first use; that build took about 8 minutes on a GB200 node with the CI image. Shipping `flashinfer-jit-cache` in the CI images would remove that build. That is an image change, outside this PR. The BF16 tests keep their skip on an unbuilt module: the SM90 build takes about 38 minutes, longer than the determinism bucket.
- **`deterministic_mode` in the config now counts.** `_cutlass_fused_moe_finalize_kwargs` took only `torch.are_deterministic_algorithms_enabled()` and the global batch-invariant mode into account. Only `megatron/training` turns on the torch flag, so Bridge, NeMo or an RL framework serving a `TransformerConfig(deterministic_mode=True)` through `MegatronLLM` could still get a fused-finalize tactic from a tuned or loaded autotuner cache. The helper now takes the config and also rules out the fused finalize under `config.deterministic_mode` or `config.batch_invariant_mode`, as the weight-build check already did. This covers both `cutlass_fused_moe` calls.
- **Docstring.** The helper no longer implies that the old-FlashInfer rejection covers the CUTLASS MXFP8 path (see above).

Tests:

- `test_bf16_flashinfer_rules_out_fused_finalize_when_deterministic` and `test_cutlass_mxfp8_flashinfer_rules_out_fused_finalize_when_deterministic` (CPU) add `deterministic_mode` and `batch_invariant_mode` cases, set in the config only. They fail without this commit and pass with it. Stand-ins of `InferenceGroupedMLP` that reach `cutlass_fused_moe` gain a `config`, including the one in `test_inference_kernels.py::test_flashinfer_clamped_relu2_replays`.
- The GB200 replay above, marked `launch_on_gb200`, 1 GPU.

`tools/check_kernel_determinism_coverage.py --base-ref origin/main` passes. The conflict with #8566 is unchanged: one hunk each in `tests/unit_tests/determinism/kernels/manifest.py` and `test_moe_kernels.py`, resolved by whichever PR merges second. The GPU results are in the next section.

## Follow-up: the GB200 tactic sweep

On GB200 (CI image, FlashInfer 0.7.2.post1), the CUTLASS MXFP8 replay ran 43 of the runner's 216 GEMM2 tactics. It required half of all 216 to run, so it failed. On `main` it fails as intended, on the fused-finalize check. The runner lists more GEMM2 tactics than its CUTLASS dispatch can launch with MXFP8 on this GPU. FlashInfer's autotuner offers only those its runner reports valid (`MoERunner.get_valid_tactics`, which probes the TMA warp-specialized dispatch and drops tactics with zero occupancy), so it never selects the others. The test now takes that list from the runner. It replays the untuned default and every valid GEMM2 tactic bit-exactly, and fails, listing each error, if a valid tactic cannot run. Its failure message reports how many tactics FlashInfer rules out; a passing run does not print the count.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), at this PR's head and with FlashInfer's CUTLASS fused-MoE module prebuilt, the H100 regression tests pass (15 cases: the BF16 replay in both modes, the racy-path control, and the BF16 and CUTLASS MXFP8 flag and weight-build tests). On `main`, 14 of 15 fail (all but the racy-path control). The BF16 replay fails on the fused-finalize check ("FlashInfer offers fused-finalize GEMM2 tactics to BF16 experts"); the flag and weight-build tests fail because `main` has no `HAVE_FLASHINFER_UNFUSED_FINALIZE`, which they patch. The neighbor tests (`test_flashinfer_mxfp8.py`, `test_flashinfer_nvfp4.py`, `test_moe_kernels.py::TestMoEModules`) pass (115 cases, 63 skipped).

On GB200 in the CI image (`mcore_ci_dev:main`, aarch64, 2026-11-02), the CUTLASS MXFP8 replay passes: the untuned default and every GEMM2 tactic FlashInfer reports valid replay bit-exactly. The passing run does not record how many tactics FlashInfer reports valid, so that count, and whether it equals the 43 tactics that ran before, are not known. On `main` it fails on the fused-finalize check ("FlashInfer offers fused-finalize GEMM2 tactics to CUTLASS MXFP8 experts").
