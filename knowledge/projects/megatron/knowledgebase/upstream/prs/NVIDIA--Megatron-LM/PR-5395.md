# fix(optimizer): skip grad-norm clipping for Muon optimizers

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/5395) · state: open · merged: False

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

**Background.** Encountered while running **ms-swift + Megatron-Core SFT of Qwen3.5-35B-A3B** (GatedDeltaNet hybrid, `optimizer=dist_muon`) on **16× B200 across 2 nodes (2×8)**. Full root-cause write-up in #5394.

## Scope & root cause (optimizer-agnostic)

The underlying failure is **not Muon-specific**. A benign-but-large global `grad_norm` (here ~5e7 from the GatedDeltaNet layers, growing to ~2e11) makes the clip coefficient `c = clip_grad / grad_norm ≈ 2e-8`, which scales per-matrix gradients below the optimizer's numerical floor and freezes updates. The same condition stalls **AdamW** too (its `eps` floor) — i.e. the clip, **not the optimizer**, is the root cause. This is now confirmed directly (see Testing): AdamW with `clip_grad=1.0` stalls at ~0.5, while AdamW with `clip_grad=0` overfits a fixed batch to **0.029** (vs Muon's 0.019). (We used `dist_muon` here following the model's training recipe; it is not required — it is simply naturally immune to this clip, since magnitude clipping is a no-op for an orthogonalizing update.)

This PR fixes the case that has a **clean, side-effect-free fix**: for an orthogonalizing optimizer, magnitude clipping is *semantically meaningless* — Newton–Schulz discards gradient magnitude — so skipping it is unambiguously correct. There is no equally clean "skip clip" for a magnitude-based optimizer (it legitimately uses clipping for spike protection); the optimizer-agnostic alternative is to clamp the clip coefficient so a benign-large `grad_norm` can't drive gradients under the eps floor (listed below).

## The harmful path, concretely

`ChainedOptimizer.step` clips every non-stub sub-optimizer's `main_params` with the global `grad_norm` whenever `optimizer.config.clip_grad > 0`. Applied to a Muon sub-optimizer, the tiny `c ≈ 2e-8` pushes its per-matrix gradients below Newton–Schulz's internal `F.normalize` floor, so the orthogonalization **silently degenerates** (near-zero, non-orthogonal update) and training stalls — with the forward/loss looking completely normal.

## Why not a config-level fix

Setting `clip_grad=0` only for the Muon sub-optimizer is not possible via `config`, because `ChainedOptimizer` requires all sub-optimizers to share the same `OptimizerConfig` (the DistOpt+LayerWise path even resets `result.config = config` to satisfy this). So this PR uses a per-optimizer attribute instead.

## Change

- `ChainedOptimizer.step`: skip the norm-clip for a sub-optimizer carrying `skip_grad_norm_clip = True`. The attribute defaults to `False` on `MegatronOptimizer`, so all existing optimizers are unaffected. `grad_norm` is still computed and returned for logging; only the clip is skipped, and only for the flagged (Muon) sub-optimizer — Adam sub-optimizers still clip normally. Separate grad-norm groups such as MTP are computed over that same non-exempt subset.
- `get_megatron_optimizer` / `_build_emerging_optimizer`: set `skip_grad_norm_clip = True` on the emerging (Muon) optimizer — both the standard-chain wrapper and the `LayerWiseDistributedOptimizer` (which owns the Muon-managed matrix params for `dist_muon`).

## Testing

The runtime effect — not magnitude-clipping the Muon param group — was validated on the actual **Qwen3.5-35B-A3B (GatedDeltaNet) model on 16× B200 across 2 nodes (2×8)**, `optimizer=dist_muon`:

- Muon group's gradient clipping **off** (equivalent to this PR; in our run via `clip_grad=0`): a fixed 32-example batch overfits to **~0.02**, real-data training learns.
- Global clip **on** (`clip_grad=1.0`, current behavior): training **stalls** (loss flat ~0.5, `grad_norm` 7.5e7 → 2.2e11).
- Dual single-variable control: keeping `clip_grad=1.0` but only lowering Newton–Schulz `eps` 1e-7→1e-30 also unblocks learning, confirming the `clip → NS-eps` interaction.
- **Optimizer-agnostic confirmation** (`optimizer=adam`, fixed 64-example overfit, 200 steps): `clip_grad=0` → loss `0.69 → 0.029` (vs Muon `clip_grad=0` → 0.019), while `clip_grad=1.0` stalls at ~0.5. `grad_norm` stayed 1e8–3e12 throughout with no NaN — Adam's per-parameter second-moment normalization digests the raw gradients fine once they are not crushed by the clip. So the clip is the sole cause across optimizers; Adam is viable without it, and Muon is not required for correctness (just lower/steadier).

This PR reproduces that validated behavior via the `skip_grad_norm_clip` attribute instead of a global `clip_grad=0`; the exact attribute wiring should additionally be exercised by CI.

## Alternatives

1. A config/CLI flag (e.g. `--no-clip-orthogonalizing-optimizers`) instead of an implicit attribute.
2. Detect orthogonalizing optimizers by type rather than an attribute.
3. A more general fix that also helps magnitude-based optimizers: clamp the clip coefficient with a floor so a benign-but-large `grad_norm` can't drive per-matrix gradients under the optimizer's numerical eps. (Broader blast radius — affects all training — hence not chosen here.)
4. Pair with the related robustness fix so the orthogonalizer doesn't silently degenerate on small inputs: NVIDIA-NeMo/Emerging-Optimizers#229 / PR NVIDIA-NeMo/Emerging-Optimizers#230.

**Critical — flag set on the container, not on the inner sub-optimizers; fix is a no-op when `results` is empty**

`LayerWiseDistributedOptimizer` is a subclass of `ChainedOptimizer` and does not
override `step()`. Its `self.chained_optimizers` are the per-layer sub-optimizers
built from `layer_wise_base_results` — and none of those objects receive
`skip_grad_norm_clip=True`.

**When `results` is non-empty** the caller gets
`ChainedOptimizer([layer_wise_optimizer] + results)`. The outer `step()` iterates
`layer_wise_optimizer` as a single element, reads the flag from it, and skips
clipping — this path works correctly.

**When `results` is empty** `layer_wise_optimizer` is returned directly to the
training loop. Calling `.step()` on it invokes the inherited `ChainedOptimizer.step()`
with `self.chained_optimizers` = the per-layer sub-optimizers. The guard at line 1677:

```python
if optimizer.config.clip_grad > 0.0 and not getattr(optimizer, "skip_grad_norm_clip", False):
```

evaluates to `True` for every inner sub-optimizer — none of them carry the flag.
Clipping still fires. **The fix is entirely bypassed for this path.**

Suggested fix — propagate the flag to each raw sub-optimizer before appending:

```python
# in the use_layer_wise branch, before layer_wise_base_results.append(...)
setattr(optimizer, 'skip_grad_norm_clip', True)
layer_wise_base_results.append((optimizer, init_state_fn))
```

Setting it on the assembled container after the fact is insufficient whenever that
container is the top-level optimizer returned to the training loop.

- ShauryaaSharma · comment · 2026-06-18T19:04:05Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/5395#discussion_r3438257857)

File: `megatron/core/optimizer/__init__.py` · line None

**High — `skip_grad_norm_clip` applied unconditionally to all emerging optimizers, not just orthogonalizing ones**

`_get_megatron_emerging_optimizer` is the entry point for every optimizer registered
in `_EMERGING_OPTIMIZERS`, which currently includes SOAP and Lion in addition to Muon
variants. The `setattr(..., 'skip_grad_norm_clip', True)` at this line fires for all
of them.

The exemption is only semantically valid for **orthogonalizing** optimizers: Muon's
Newton–Schulz step discards gradient magnitude by construction, making L2 norm
clipping a no-op on the update direction and actively harmful when the clip coefficient
is small. SOAP and Lion have no such property — they are magnitude-sensitive and should
remain subject to clipping. Silently disabling it risks training instability for any
non-Muon emerging optimizer with `clip_grad > 0.0`.

Suggested fix — introduce an explicit allowlist and gate on it:

```python
_ORTHOGONALIZING_OPTIMIZERS = frozenset({'muon', 'dist_muon'})
if opt_name in _ORTHOGONALIZING_OPTIMIZERS:
    setattr(optimizer, 'skip_grad_norm_clip', True)
```

This also future-proofs the function: any new optimizer added to `_EMERGING_OPTIMIZERS`
will clip by default and must explicitly opt out, rather than silently inheriting an
exemption it may not deserve.

**Nit/Medium — Muon grads inflate the shared `grad_norm` used for `grad_norm_skip_threshold`**

`grad_norm` is computed at the top of `ChainedOptimizer.step()` via
`self.get_grad_norm()` — a combined norm across **all** sub-optimizers, including
Muon. This same scalar is then used in the threshold comparison for every
sub-optimizer in the loop, including AdamW.

The issue report documents Muon grad norms of ~5×10⁷ growing to ~2×10¹¹. If a user
configures a finite `grad_norm_skip_threshold` (e.g. to guard against spike-and-NaN
cascades), the AdamW sub-optimizer's update will be suppressed based on a norm Muon's
gradients are dominating — even if AdamW's own gradients are well-behaved. The entire
step is dropped via `should_skip_update = True`.

This is consistent with the stated goal of the PR: if Muon grads are excluded from
clipping, they should arguably also be excluded from the threshold comparison for
non-Muon sub-optimizers. The straightforward fix is to compute a separate `grad_norm`
that excludes parameters whose sub-optimizer has `skip_grad_norm_clip=True`, and use
that narrower norm for the threshold check.

`grad_norm_skip_threshold` defaults to `float('inf')` so this won't affect most users
today, but it is a quiet footgun for production configs that set a finite value.

**Low — `should_clip` predicate ignores `skip_grad_norm_clip`, triggering a wasted collective**

`should_clip` is evaluated by checking `optimizer.config.clip_grad > 0.0` across all
sub-optimizers, but does not consult `skip_grad_norm_clip`. When every sub-optimizer
that has `clip_grad > 0.0` also carries `skip_grad_norm_clip=True` (e.g. a Muon-only

sub-optimizer will actually use for clipping.

should_clip = any(
