# [Inference][MLA] Apply the attention sink in dynamic MLA and make its decode batch-invariant

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8571) · state: open · merged: False

## Original PR description

# What does this PR do?

Fixes two bugs in dynamic-batching MLA (`cache_mla_latents`):
- It applies the attention-sink softmax (`off-by-one` / `learnable`), which was dropped.
- In batch-invariant mode, a request's decode output no longer depends on its co-batch.

**Bug 1: sink dropped.** `MultiLatentAttention.forward`'s dynamic branch called `flash_decode_and_prefill` without `softmax_offset`. Standard attention passes `softmax_offset=self._get_inference_softmax_offset()`.
- So for an MLA model with `softmax_type != "vanilla"` served by the dynamic engine, the kernel received `softmax_offset=None`.
- Neither the FlashAttention prefill correction nor the FlashMLA decode correction ran.
- Attention computed `exp(qk)/Σexp(qk)`, while the static path (TE attention with `softmax_type`) computes `exp(qk)/(exp(sink)+Σexp(qk))`.
- The output was too large by `1/sigmoid(lse − sink)` per head and token.

**Bug 2: batch invariance broken.** Under `batch_invariant_mode`, every other attention branch pins `num_splits=1`. Dynamic MLA instead ran decode-only steps as absorbed attention through FlashMLA.
- FlashMLA computes its split-KV schedule inside the kernel launch from every request's KV length. Its API takes no split count.
- So a request's reduction order depended on its co-batch. On H100, request 0's decode output differed by up to 0.002 between batch size 1 and batch size 32.
- Mixed steps and training run unabsorbed attention, which rounds differently. A decode token's bits therefore also depended on whether a prefill shared its step, and could not match the training forward. Both properties are part of the batch-invariance contract (see `test_dynamic_engine_is_batch_invariant_under_kv_cache_saturation`).
- Config validation accepted the combination.

**Fix.**
- `multi_latent_attention.py`:
  - The dynamic branch passes `softmax_offset=self._get_inference_softmax_offset()`. For vanilla softmax this is `None`, so vanilla models see no change.
  - A new `MultiLatentAttention._absorbs_cached_latents(inference_context)` is the one place that decides whether a step runs absorbed attention: decode-only steps outside batch-invariant mode. The query construction, the kernel choice, and the up-projection of the output now all read it.
- `attention.py`: `_adjust_key_value_for_inference` reads the same predicate to decide whether to up-project the cached latents to keys and values.
- In batch-invariant mode, decode-only steps therefore take the existing unabsorbed path, like mixed steps and training: they up-project the cached latents and run the varlen FlashAttention kernel with `num_splits=1`.
  - Batch-invariant mode already requires `flash_attention_version` 3 or 4; FlashAttention 2 cannot read 64-token KV blocks.
  - In the CI image (FA2 and FA4), this path runs FA4 on H100 with one split.
  - The path is CUDA-graph safe: the routing is a per-step Python decision, as before, and the up-projection has a fixed shape.
- Outside batch-invariant mode, decode keeps the absorbed FlashMLA path.
- Cost: a batch-invariant decode step up-projects the whole latent cache in each layer, as mixed steps already do, so it costs about as much as a mixed step.
- `docs/mcore-inference-user-guide.md`: the MLA bullet under Known Limitations and the batch-invariant section say that batch-invariant mode works with the latent cache, and what decoding costs in that mode.

**Tests** (`tests/unit_tests/transformer/test_multi_latent_attention.py`):
- `TestParallelMLAAttention` (mocked context, no attention kernel):
  - `test_dynamic_inference_forwards_sink_offset_to_flash_attention[off-by-one|learnable × prefill|decode-only]`: the layer's per-head sink reaches the kernel.
  - `test_dynamic_inference_forwards_decode_only_to_flash_attention`, now also parametrized by batch-invariant mode: the decode kernel runs only for decode-only steps outside batch-invariant mode.
  - `test_dynamic_inference_up_projects_cached_latents_unless_absorbed`: the cached latents are up-projected for every step that does not absorb.
- `TestMLALatentCacheDecode` (real `DynamicInferenceContext`, real kernels, FlashAttention 3 or 4):
  - `test_batch_invariant_decode_is_independent_of_cobatch`: in batch-invariant mode, request 0's decode output is bitwise identical in three cases: decoded alone, next to 31 other decoding requests, and in a step that also prefills another request.
  - `test_batch_invariant_decode_matches_unabsorbed_prefill`: that decode output bitwise equals the output for the same token when it ends a prefill.
  - `test_flash_mla_decode_applies_sink`: absorbed FlashMLA decode with a learnable sink matches the unabsorbed prefill with the same sink (relative error < 5%). Without the sink correction, the error exceeds 20%. It runs only on SM90 with a FlashMLA build that includes its SM90 kernels, and is skipped otherwise. A FlashMLA build without those kernels exits the process at its first launch, so the test first probes the kernel in a subprocess, once per session.
- `tests/unit_tests/determinism/kernels/test_runtime_cp_attention.py::test_mla_flash_prefill_dispatch_sink_offset_replays[off-by-one|learnable]`:
  - Determinism coverage, not a regression test of the call site: it calls `flash_decode_and_prefill` directly with the offset MLA hands over, and it passes on main.
  - It replays the sink-corrected MLA prefill (FA2) bit-exactly and checks that the sink changes the output.
  - It is registered for `multi_latent_attention.py` in the kernel determinism manifest, whose note also points at `TestMLALatentCacheDecode` for the batch-invariant path. `tools/check_kernel_determinism_coverage.py` passes.

**H100 results** (official CI image):
- First commit: the new regression tests passed (35 passed, 1 skipped; `test_gpu_forward_with_yarn_rope_fusion[rope]` skips by design). On main, 9 failed: the 8 sink cases and the batch-invariant config test that a later commit replaced. Neighbor tests passed: `test_manifest.py`, `test_flash_decode_dispatch_config_softmax_scale_replays`, and `test_dynamic_sink_attention_e2e.py`.
- This PR's head, after the merge of `main` (CI image `mcore_ci_dev:main`, 2026-11-02): the regression tests pass (47 passed, 2 skipped). The passes include both batch-invariant tests, `test_batch_invariant_decode_is_independent_of_cobatch` and `test_batch_invariant_decode_matches_unabsorbed_prefill`, and every `TestParallelMLAAttention` case, among them the batch-invariant routing cases. The neighbor tests pass (`test_manifest.py`, 299 cases; `test_flash_decode_dispatch_config_softmax_scale_replays`, 2; `test_dynamic_sink_attention_e2e.py`, 3).
- On main, the run aborts inside FlashMLA's decode in `test_batch_invariant_decode_is_independent_of_cobatch` ("no kernel image is available for execution on the device"; see below), so it records no results. Its log shows, before the abort, the 8 sink cases failing and four batch-invariant cases of `TestParallelMLAAttention` failing (two routing, two up-projection), because decode-only steps never up-project the cached latents on main.
- `test_flash_mla_decode_applies_sink` is skipped in this image. The image's FlashMLA has no SM90 kernels: it imports, but its first launch on H100 exits the process with "no kernel image is available for execution on the device". The absorbed FlashMLA decode path therefore cannot run in that image on H100. The test probes FlashMLA in a subprocess first (last commit), so the run skips it instead of aborting. The other skip is `test_gpu_forward_with_yarn_rope_fusion[rope]`, by design.
- Merge order: after https://github.com/NVIDIA/Megatron-LM/pull/8701 and the KV page initialization PR (`fix/kv-page-init`). "Run dynamic MLA decode with FlashInfer on Blackwell, where FlashMLA has no dense decode" (`fix/mla-decode-blackwell`) is stacked on this PR and lands after it.
