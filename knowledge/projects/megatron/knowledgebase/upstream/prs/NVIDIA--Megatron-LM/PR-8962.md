# [Inference][MoE] Stop int32 pair counts and offsets from wrapping in the MoE routing kernels

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8962) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes the inference MoE routing kernels compute their pair counts and offsets in int64: the count, init-map and permute kernels in `megatron/core/inference/moe/permute.py` and the vLLM path's scatter in `vllm_fused_moe.py`. They computed pair counts, block offsets and inverse-map offsets in int32, which wraps at 2^31. The quantities the API keeps int32 (expert offsets, claimed row positions, the vLLM path's sorted pair ids) are now bounded by host checks on the shapes: a permuted output or a vLLM pair table of 2^31 or more slots is rejected with an error instead of wrapping.

**Stacked on #8563** (`fix/d3-s6-mtp-moe-metadata`). #8563 rewrites the very lines this PR changes in the count kernels and the vLLM scatter (`valid_pairs = tl.minimum(valid_tokens * topk, max_pairs)`). It also defines `valid_tokens` above the routing-map rows (only the map's rows are used), and the small regression tests below rely on that. Its clamp does not fix the wrap: `tl.minimum` takes the already wrapped product. Merge #8563 (including its merge of main) first, and review only the commits on top of it.

**Merge order with #8566 and #8871.** Both change the permute kernels (`SCALE_BY_PROB`) at other lines; `permute.py` merges cleanly. In `vllm_fused_moe.py`, #8566 reformats the two calls whose live-row bound this PR makes int64 (`bounded_silu_mul` and the batch-invariant squared ReLU), so whichever lands second resolves a two-line conflict: keep #8566's `is_gated` structure and pass `valid_tokens.to(torch.int64) * topk` as the bound.

## Issue tracking

Linked issue: none. These are oracle findings O1-N1, O1-N2 and O1-N3. None is reachable at production sizes today: the largest routing map (the NVLS all-gather buffer, about 4M rows at top-8) is at least 64x below 2^31 pairs, and so is the largest inverse map.

**Bug 1: the live pair count wraps.** `valid_tokens * topk` is int32 in `_count_local_tokens_kernel`, `_count_local_tokens_kernel_persistent`, `_permute_tokens_kernel`, `_permute_quantize_mxfp8_kernel` and the vLLM path's `_scatter_token_indices_kernel`, and on the host in `vllm_fused_moe`'s SwiGLU and batch-invariant squared-ReLU live-row bounds.
- At 2^31 live pairs (268M rows at top-8) it wraps to -2^31 and every count is 0. Confirmed on H100: 0 instead of 67108864 on all 32 experts, with no fault.
- The persistent kernel's `tl.cdiv` adds 1023 first, so it already counts nothing from 2^31 - 1023 pairs.
- The permute kernels return early, so the permutation is silently empty. On the vLLM path nothing is scattered, so `_moe_sum` sums intermediate rows that were never computed.
- The product also wraps for a map of any size when `valid_tokens >= 2^31 / topk`. #8563's contract allows that value and clamps it to the map rows.

**Bug 2: block offsets wrap.** `pid * BLOCK_SIZE` is int32 in `_count_local_tokens_kernel`, `_init_permutation_map_kernel` and `_scatter_token_indices_kernel`. For a buffer of more than 2^31 entries, the last program's offsets wrap to -2^31 and pass the mask (`< valid_pairs`, `< n_used`) whatever the live count is.
- The count kernel then reads 16 GiB before the routing map. On H100 a 2^31 + 8-pair map faulted with an illegal memory access.
- The init kernel writes `-1` 8 GiB before the permutation map (by reading).
- `block_id * BLOCK_SIZE` in the persistent count kernel would wrap the same way once bug 1 is fixed.

**Bug 3: the inverse-map offset wraps.** The batch-invariant inverse-map store `tok * num_local_experts + lid` is int32 in both permute kernels (by reading). Once tokens x local experts reach 2^31, the store lands 8 GiB before the `[tokens, E_l]` map and the entry stays `-1`, so the batch-invariant unpermute would drop that contribution (or the stray store faults).

The permute kernels' pair index is int32 too. Their sm_90 PTX steps it with `add.s32` by `NUM_BLOCKS`, so for a map within 512 pairs of 2^31 it wraps after the last pair and the loop goes on to read before the map.

## Fix

- Form the pair count in int64 in all five kernels: `valid_tokens.to(tl.int64) * topk`. The persistent kernel's block counts, block ids and offsets follow from it, as do the permute kernels' pair index, `tok`, `tok * topk + k` and the inverse-map offset.
- Make the block offsets of the count, init-map and vLLM scatter kernels int64: `pid.to(tl.int64) * BLOCK_SIZE`. The permute kernels already form their row offsets this way (`pos.to(tl.int64) * hidden_dim`).
- Pass `valid_tokens.to(torch.int64) * topk` as the live-row bound of `vllm_fused_moe`'s SwiGLU and batch-invariant squared-ReLU activations. The kernels clamp it to their rows.
- What stays int32, and the new host checks on the shapes (no device work, no sync):
  - `permute_tokens` and `permute_and_quantize_mxfp8` assert fewer than 2^31 output rows. Below that, the per-expert counts, the prefix sums passed to the grouped GEMMs as `offs`, `n_used` and the claimed row positions all fit int32.
  - `_moe_align_block_size_cuda_graphable` asserts fewer than 2^31 sorted slots (pairs plus padding), since `sorted_token_ids` stores pair indices in int32.
- No host sync, allocation or launch-shape change, so the kernels stay CUDA-graph safe.
- Cost, from sm_90 SASS at production sizes (map below 2^31 pairs): the count kernels gain a few integer instructions per routing-map element, which they spend waiting on memory anyway. The persistent kernel also does one 64-bit division per CTA. At top-8 the permute kernels' pair loop gets shorter, because the compiler folds `tok * topk + k` back into the pair index; the fused MXFP8 kernel adds a few instructions per local row, next to that row's quantization.

## Tests

Regular unit tests. These fail without the fix and pass with this PR:
- `valid_tokens` at its int32 maximum on small maps whose buffer tail would be counted if read. Only the map rows may be used:
  - `test_moe_permute.py::TestComputeLocalTokensPerExpert::test_valid_pairs_past_int32[topk 2, 8 x persistent]`.
  - `test_moe_permute.py::TestPermuteTokens::test_valid_pairs_past_int32[inverse]` and `test_mxfp8_utils.py::TestPermuteAndQuantizeMxfp8::test_valid_pairs_past_int32[inverse]`: offsets, rows (bit for bit, or against the MXFP8 reference) and the inverse map.
  - `test_vllm_fused_moe.py::TestMoeAlignBlockSize::test_valid_pairs_past_int32`: every pair counted and scattered.
  - `test_vllm_fused_moe.py::TestVllmFusedMoe::test_valid_pairs_past_int32[squared ReLU, SwiGLU x plain, batch-invariant]`: the output equals the `valid_tokens == rows` output bit for bit. The persistent intermediate buffers are filled with NaN first, so a row that is summed but never computed shows up.
- Block offsets past 2^31 without a large buffer: `TestComputeLocalTokensPerExpert::test_block_offsets_past_int32` and `TestInitPermutationMap::test_block_offsets_past_int32` launch the kernel with the grid of a buffer of more than 2^31 entries, but back only its live head. Programs whose block starts at 2^31 must not touch memory. With int32 offsets they access 8 GiB before the buffer, which faults (sticky for the process) or corrupts memory, so these fail loudly rather than on an assertion.
- The host checks: `TestPermuteTokens::test_rejects_outputs_past_int32_rows[bf16, mxfp8]` and `TestMoeAlignBlockSize::test_rejects_pair_tables_past_int32`, on stride-0 views, so nothing large is allocated.

Large cases, opt-in: `test_moe_permute.py::TestInt32Limits`, marked `large` (8-28 GiB of device memory each). A new `tests/unit_tests/inference/conftest.py` registers the marker and skips these cases unless the `-m` expression names `large`. No CI job runs them: run them on an H100 with `-m large`, one per process (on the base, a wrapped offset can leave a sticky illegal-address error).
- `test_count_live_pairs[cdiv-wraps|count-wraps|offsets-past-int32 x persistent]`: 2^31 - 8, 2^31 and 2^31 + 1024 live pairs. Every pair must be counted. The last one is the only way to reach the persistent kernel's offsets past 2^31, since it reads every live pair.
- `test_count_block_offsets[persistent]` and `test_init_permutation_map_block_offsets`: maps of 2^31 + 8 and 2^31 + 1 entries, each right after a 2^31-entry front guard in the same buffer. A wrapped block offset hits the guard, so the test fails on an assertion instead of a fault.
- `test_permute_live_pairs`: `permute_tokens` at 2^31 live pairs. Each row carries its token index in its bits, so the check is bitwise.
- `test_inverse_map_offsets[bf16|mxfp8]`: 2^24 + 1 tokens on 128 local experts. Every token must get its inverse-map entry and nothing else. This one cannot be made CI-sized: the offending store is 2^31 entries past the map's base, so the map itself must hold 2^31 int32 entries (8 GiB).

Determinism: `test_inference_kernels.py::test_inference_permute_valid_pairs_past_int32_replays`. Both count kernels, both permute kernels (with the inverse map) and `vllm_fused_moe` run with `valid_tokens` at its int32 maximum. They must replay bit-exactly and match the `valid_tokens == rows` result. The `inference_moe_kernels` manifest entry already registers `permute.py` and `vllm_fused_moe.py` with this test file.

The `large` marker's skip duplicates the one in the inference oracle-test harness (`tests/unit_tests/inference/oracles/conftest.py`, not merged yet). Whichever lands second should drop its copy, so that one rule decides the opt-in.

Evidence:
- H100 (dfw 21223138, first commit on #8563 merged with main): the 9 regression cases pass there and fail on #8563; all 10 large cases pass, one per process; the neighbor tests pass.
- The review-follow-up commit has not run on a GPU yet. On CPU (Triton interpreter), the vLLM align case and `vllm_fused_moe` at `valid_tokens = INT32_MAX` fail before the follow-up (no pairs placed, NaN outputs) and pass with it. A copy that keeps the int32 SwiGLU bound fails the SwiGLU case, and both host checks raise.
- Earlier CPU checks: a copy that fixes only the count kernels fails the permute cases. The large-case bodies pass at 2^14 in place of 2^31, and with block offsets patched to wrap at 2^14 the guard assertions fire. All kernels compile for sm_90 with `max_pairs` as i32 and as i64.
