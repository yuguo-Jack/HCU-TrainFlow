# Add configurable batch and sequence partitioning within GTP_remat

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7748) · state: closed · merged: True

## Original PR description

## Summary

Adds `--tensor-parallel-num-sequence-shards` to configure batch and sequence partitioning within GTP\_remat groups. By default, GTP\_remat ranks process independent microbatches. Increasing the sequence-shard count partitions each sequence across more ranks and reduces the number of independent batch partitions.

Weight sharding remains controlled by `--tensor-parallel-num-weight-shards`. The new sequence-shard flag includes TP when sequence parallelism (SP) is enabled:

```
SP degree = TP with SP enabled, otherwise 1

gtp_remat_num_sequence_shards = tensor_parallel_num_sequence_shards / SP degree
gtp_remat_num_batch_shards = GTP_remat_size / gtp_remat_num_sequence_shards
batch_parallel_size = DP × gtp_remat_num_batch_shards
```

Both divisions must be exact. Leaving the flag unset preserves existing behavior: the sequence-shard count defaults to the SP degree, so `gtp_remat_num_sequence_shards=1` and `gtp_remat_num_batch_shards=GTP_remat_size`. Sequence partitioning within GTP\_remat requires SP when TP \> 1.

For example, weight shards=64, TP=2 with SP enabled, and sequence shards=16 produce **4 independent batch partitions**, each with **2 SP partitions × 8 sequence partitions within GTP\_remat**, in each TP × GTP\_remat weight-sharding group.

`--context-parallel-size` adds further sequence partitions across weight replicas. The resolved runtime CP size excludes TP/SP:

```
runtime_CP = configured_CP × gtp_remat_num_sequence_shards
```

This allows sequence partitioning to span more ranks than a single weight-sharding group.

The implementation introduces `GTPParallelLayout`, which describes two views of the same ranks:

- **Weight layout:** TP × GTP\_remat shards weights; configured CP × DP replicates those shards. These groups drive weight materialization, gradient reduction, and optimizer-state sharding.
- **Batch and sequence layout:** DP × `gtp_remat_num_batch_shards` distributes independent microbatches, while configured CP × `gtp_remat_num_sequence_shards` partitions each sequence, in addition to TP/SP. These groups drive data distribution, CP communication, and sample accounting.

Argument validation resolves the runtime CP size, and process-group construction builds the existing groups from these views. Global batch size is calculated as:

```
global_batch_size = micro_batch_size × batch_parallel_size × num_microbatches
```

Training progress and sample-based schedules use the same independent-sample count.

For example, on 128 GPUs with PP=1:

```
--tensor-model-parallel-size 1 \
--tensor-parallel-num-weight-shards 64 \
--tensor-parallel-num-sequence-shards 64 \
--context-parallel-size 2
```

This gives DP=1, with weights sharded across GTP\_remat groups of 64 ranks and two replicas of each weight shard. Each sequence is partitioned across 128 ranks. The batch dimension is unpartitioned (`batch_parallel_size=1`), so all 128 ranks process different sequence partitions of the same microbatch.

This placement example assumes **64 GPUs per NVLink domain**. The current implementation supports rank order `tp-cp-ep-dp-pp`, with TP as the innermost axis and PP as the outermost axis. Place each 64-rank weight-sharding group entirely within one NVLink domain. CP then spans both domains, while weight all-gathers and gradient reduce-scatters stay within each domain.

## Comparing with PR #6886

PR #6886 folds the entire CP axis into the weight-sharding group, so its folded weight group is at least as large as its CP degree. This PR allows 128 sequence partitions with 64-rank weight groups, as in the example above.

PR #6886 additionally preserves optimizer-state sharding across CP for **parameters not sharded by GTP**, such as norms and biases. This implementation uses one dense weight-replica group, so those optimizer states remain replicated within each GTP group, although they can still be sharded across weight replicas. This trades some memory efficiency for simpler ownership and reduction rules.

The flag values also differ: for TP=1, #6886's CP=64 / GTP_remat=1 corresponds here to weight shards=64, sequence shards=64, and CP=1.

The changes are deliberately minimal: resolve weight and token layouts during process-group construction, update sample accounting, and reuse existing GTP, DDP, and optimizer paths. This covers the target static-CP use case without adding CP-specific parameter flags, buffer routing, or optimizer checkpoint keys, reducing the number of interacting special cases to validate and maintain.

### Apply sequence-shard defaults before resolving the layout

**Failure:** In [validate_args](https://github.com/NVIDIA/Megatron-LM/blob/1cd936e062ff1d59d4dc254b93eec109a4e7b57d/megatron/training/arguments.py#L450-L465), an unset `tensor_parallel_num_sequence_shards` is immediately resolved to 1 (or TP with SP). The later [programmatic-defaults loop](https://github.com/NVIDIA/Megatron-LM/blob/1cd936e062ff1d59d4dc254b93eec109a4e7b57d/megatron/training/arguments.py#L644-L654) therefore treats it as explicitly supplied and ignores `args_defaults` for the new flag.

For example, with world=8, TP=PP=1, weight shards=2, configured CP=1, and `ckpt_format="torch_dist"`, calling `validate_args(args, {"tensor_parallel_num_sequence_shards": 2})` leaves sequence shards=1, runtime CP=1, and batch parallel size=8. Expected: sequence shards=2, runtime CP=2, and batch parallel size=4. Bootstrap consequently constructs a different token layout from the caller's requested default.

**Correction:** Apply this particular default while the argument still retains its unset state, before the sequence-shard resolver. Keep the invariant that explicit CLI values win and all layout arithmetic uses the effective sequence-shard value. Suggested insertion immediately before line 450:

```python
if args.tensor_parallel_num_sequence_shards is None:
    args.tensor_parallel_num_sequence_shards = defaults.get(
        "tensor_parallel_num_sequence_shards"
    )
```

This is a source-reasoned suggestion; verify it before adopting it.
