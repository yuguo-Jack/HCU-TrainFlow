# [Inference][MoE][MXFP8] Reject routed FlashInfer MXFP8 experts whose hidden size pads to 128

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8959) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Rejects routed FlashInfer MXFP8 MoE configurations that FlashInfer has no kernel for when the config is built. Before this change they were accepted and failed at the first forward.

**Stacked on #8877** (`fix/cutlass-mxfp8-etp-alignment`). That PR moves the FlashInfer CUTLASS MXFP8 shape check into `TransformerConfig.validate_flashinfer_cutlass_mxfp8_expert_shapes()` and runs it again when `InferenceGroupedMLP` is built. This PR extends that method to the routed path. Please review the commits above #8877's only.

**Bug.** With `inference_grouped_gemm_backend='flashinfer'`, `fp8_recipe='mxfp8'` and unclamped squared-ReLU experts, Megatron uses FlashInfer's TRT-LLM routed MoE (`trtllm_fp8_block_scale_routed_moe`). `prepare_routed_mxfp8_weights` zero-pads each rank's `[E, F/ETP, H]` FC1 and `[E, H, F/ETP]` FC2 weights to multiples of 128. H is the expert hidden size (`moe_latent_size`, or `hidden_size`); F/ETP is the per-rank FFN. If H pads to 128, FlashInfer 0.7.2.post1 (the `uv.lock` pin) has no batched-GEMM config. On GB200 the first forward raised `tvm.error.InternalError: ... trtllm_batched_gemm_runner.cu:605: No valid config found for the given problem shape`. This happened in all 35 H = F = 128 cases of the step 4 oracle (hsg-8571739), and for H 128 with F 256 (hsg-8573939, `test_hidden_128_is_served_or_rejected_by_megatron[256]`). `TransformerConfig` checked expert shapes only on the CUTLASS ClampedRelu2 path, so these configs were accepted. Every shape with a larger H worked: padded (H, F/ETP) of (256, 128), (256, 256), (512, 384), and (2688, 1920) at production size. The routed path with H 256 and F/ETP 128 also passes `test_flashinfer_moe_bounded_rows` at ETP 2. Only small or toy models are affected.

## Fix

- `validate_flashinfer_cutlass_mxfp8_expert_shapes()` is renamed to `validate_flashinfer_mxfp8_expert_shapes()`. It now covers both FlashInfer MXFP8 paths:
  - CUTLASS (ClampedRelu2): unchanged; both dimensions must be divisible by 128 per rank.
  - Routed (unclamped): rejects `H <= 128`, whatever the FFN or expert TP. The message names the size and the field it comes from, and points to the `torch` or `vllm` backend.
- `__post_init__` runs the check for every MXFP8 config, not only inside the ClampedRelu2 block. `InferenceGroupedMLP.__init__` still runs it, so a config whose layout is changed after validation is also caught (RL does this for its inference model). This matters for the CUTLASS rule, which depends on expert TP.
- `flashinfer_routed_mxfp8_moe`, the kernel entry, raises the same `ValueError` next to its other shape checks. Code that calls it directly, without a `TransformerConfig`, now gets Megatron's error instead of FlashInfer's. The layout repack (`prepare_routed_mxfp8_weights`) stays shape-agnostic, because refit, the writeback and layout tests use it on small shapes.

**Which sizes.** The rule is `H <= 128`, the expert hidden size alone. FlashInfer's TRT-LLM config tables were not available here: they are the `KernelMetaInfo` shipped with the batched-GEMM cubins, fetched at run time. So the rule follows the GB200 runs. H 128 failed with F 128 (hsg-8571739) and with F 256 (hsg-8573939). Every H >= 256 that was tested runs, including F/ETP 128. An earlier revision of this PR rejected only H and F/ETP both at most 128, but hsg-8573939 showed H 128 with F 256 fails too.

**Tied to the FlashInfer version.** The check notes it was seen with FlashInfer 0.7.2.post1. `test_flashinfer_routed_mxfp8_rejects_hidden_128_before_flashinfer[128|256]` (GB200) checks that Megatron's kernel entry raises its error. It then calls FlashInfer below that check and asserts FlashInfer still has no config for hidden 128. A FlashInfer release that adds one fails that test, which says to relax the rule. Not done: querying FlashInfer's `trtllm_get_valid_moe_configs` when `InferenceGroupedMLP` is built. It is an internal op of FlashInfer's SM100 MoE module, not public API, and its 0.7.2 signature and empty-result behavior could not be checked here. Calling it would load that module at model construction. It also needs the token counts the engine will run, which `InferenceGroupedMLP` does not know when it is built.

## Tests

In `tests/unit_tests/inference/test_flashinfer_mxfp8.py`:

- `test_flashinfer_routed_mxfp8_rejects_unsupported_expert_shapes` (CPU config construction). Five configs are rejected: hidden 128 with FFN 128, 256, and 2048 over ETP 2; hidden 96 (pads to 128) with FFN 512; and `moe_latent_size` 128 with `hidden_size` 256. All are accepted on the base branch.
- `test_flashinfer_routed_mxfp8_moe_rejects_unsupported_expert_shapes` (CPU): the kernel entry rejects hidden 128 and 96 experts (FFN 96 to 1024) before quantizing or calling FlashInfer. The base branch has no such check.
- `test_flashinfer_routed_mxfp8_accepts_supported_expert_shapes` (control, CPU): the GPU-tested shapes are still accepted: 256/128, 160/96, latent 256 with hidden 128, and FFN 256 over ETP 2.
- `test_flashinfer_routed_mxfp8_runs_the_smallest_accepted_expert_shape` (GB200, `launch_on_gb200`): hidden 256 / FFN 128 runs at 1, 64 and 1024 tokens. The output is checked against an fp32 reference on the unquantized weights (per-token cosine similarity above 0.98).
- `test_flashinfer_routed_mxfp8_rejects_hidden_128_before_flashinfer[128|256]` (GB200): Megatron's error, then FlashInfer's own, as described above.
- The GB200 tests skip only off Blackwell. On a Blackwell runner without FlashInfer they fail rather than skip.
- `_make_bounded_mxfp8_config` now defaults to hidden 256 (FFN stays 128), because 128/128 is now rejected. The existing Blackwell batch-invariance test shares the new `_prepare_routed_mxfp8_weight` helper.

The GPU run is pending. Checked locally on CPU only (no unit-test runs). Scratch scripts built configs with TE's version gate patched. The base branch accepts all five rejected configs; this branch rejects them, accepts the supported ones, and leaves the CUTLASS, BF16 and vLLM paths unchanged. The kernel-entry check raises only for a hidden size that pads to 128, and the repack does not raise for any shape. Existing Blackwell tests that repack small weights (`test_mxfp8_refit.py` routed refresh, `test_flashinfer_routed_mxfp8_writeback_replays`, `test_mxfp8_expert_weight_build_replays[flashinfer_routed]`) and the O4b layout oracles are therefore unaffected.

The determinism-coverage check flags `experts.py` (`moe_experts`) and `flashinfer_mxfp8.py` (`inference_mxfp8_quantization`). Both changes are shape checks that raise before any kernel and cannot affect numerics, so this PR needs the `determinism-exempt` label.

Merge order: this PR is stacked on #8877 and merges after it. It merges cleanly with `main` and with the O4b oracle PR.
