# [Core][Inference][BatchInvariant] One rank-ordered tensor-parallel reduction for batch-invariant training and inference

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8868) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

In batch-invariant mode, every tensor-parallel reduce-scatter and all-reduce now sums a token's partials in rank order: fp32 adds in a fixed order, then one rounding to the input dtype. That covers training and inference, the TE, local and inference-optimized layers, and the forward and backward passes. A token's reduced row then no longer depends on where the co-batched requests put it. Before, with TP >= 3, it did. RL rollouts reproduce training's reduction at any TP size.

**Bug.** Batch-invariant mode reduced across TP with NCCL on every path:
- TE's row-parallel layers: `reduce_scatter_along_first_dim` / `allreduce`.
- Megatron's mappings: local layers, embeddings, sequence parallelism, MoE.
- The inference-optimized layers, which skip NVLS under batch-invariant mode.

NCCL's ring reduce-scatter (`src/device/reduce_scatter.h`, `runRing`) sums the chunk owned by ring position u as `((x[u+1] + x[u+2]) + ...) + x[u]`, rounding to bf16 after every add. Its all-reduce chunks the tensor the same way. Row i of a T-row step lands in chunk `i // (T / TP)`, and both i and T depend on the other requests in the step.
- **TP = 2:** every chain is a single commutative add, so the result is invariant.
- **TP >= 3:** the result depends on the token's chunk. On H100 at TP=4, every rank gave all rows the same random partial. About 1,700 of the 4,096 hidden elements of a row in chunks 1-3 then differed from the same row in chunk 0, at every T from 4 to 4096. This held both for the inference-optimized path and for TE's `reduce_scatter_along_first_dim`.
- **RL:** training and rollouts used different chunk layouts, so a rollout token matched training only when both put it in the same chunk.

Affected: batch-invariant mode with TP >= 3, in any `transformer_impl`, in training and inference.

## Fix

The new module `megatron/core/tensor_parallel/batch_invariant_reduction.py` provides the one reduction: `batch_invariant_reduce_scatter` (equal or uneven splits) and `batch_invariant_all_reduce`. Each output element is `((x_0 + x_1) + x_2) + ...` over the ranks' partials: fp32 adds in ascending rank order, each rounding to fp32, then one rounding to the input dtype. For bf16/fp16 partials with nearby exponents the fp32 adds are exact, but in general this is a fixed-order fp32 chain, not one rounding of the exact sum. The adds use one shared primitive, `add_rn_f32` in `torch_symm_triton/utils.py`: an inline-PTX `add.rn.f32` that the compiler cannot reorder. A chain of plain adds is not safe: LLVM's SLP vectorizer can turn it into an ordered `llvm.vector.reduce.fadd` with its lanes reversed, so the sum runs from the last rank. A local smoke run showed this for this kernel's first version, and the reviewer confirmed it.
- **Symmetric memory (one kernel):** the inference-optimized row-parallel layer puts its GEMM output into the `"tp"` symmetric buffer. One Triton kernel then reads every peer's partial of this rank's rows and sums them. It uses the entry barrier of `ordered_reduce_scatter_v` and reads the same bytes as `multimem_reduce_scatter`, so the buffer-reuse rules of the NVLS path still hold. This kernel works at any TP size. `symm_mem_sync` used to need a power-of-two group, because `tl.arange(0, world_size)` must have a power-of-two length. It now takes an optional `padded_world_size`: the arange is padded to the next power of two and the extra lanes are masked. Existing callers are unchanged. The multimem all-gather still calls the unpadded barrier, so a batch-invariant inference-optimized model at TP=6 still fails to compile in its all-gather; that failure predates this PR. The embedding's `inference_reduce_scatter_to_sequence_parallel_region` copies into the buffer first, as its NVLS path does.
- **The GEMM writes into the buffer under every backend.** `torch.matmul(..., out=...)` lowers to `aten::mm.out`, which the `triton` and `deepgemm` backends do not replace, so the inference layer's `_apply_linear` now calls their GEMM into the buffer directly (`mm_out_batch_invariant`; `matmul_persistent` takes an `out`). Under `triton` the persistent kernel writes straight into symmetric memory, and the first version's `[T, H]` copy is gone. Under `deepgemm` one copy remains inside the helper, because `_mm_deepgemm` owns its TMA-aligned output layout; passing `out` through belongs after #8867 (fix/deepgemm-bi-dense), which rewrites `_mm_deepgemm`. Replacing `aten::mm.out` itself would be the general fix, but it would conflict with s13 (#8573), which restructures `enable_batch_invariant_mode`.
- **No symmetric memory:** an NCCL all-to-all hands each rank every partial of its rows, and the same kernel sums them. An all-reduce is that reduce-scatter on the flattened tensor (zero-padded to a multiple of TP) followed by an all-gather, so it moves the bytes a ring all-reduce does.
  - **Asynchronous.** With `async_op` (TE's and Megatron's backward input-gradient reductions), the all-to-all is launched on NCCL's stream and the call returns a handle. Its `wait()` makes the stream wait for the all-to-all, with no host sync, and then launches the sum kernel and, for an all-reduce, the all-gather. The weight-gradient GEMM that TE and `layers.py` schedule before `wait()` therefore overlaps the communication, as it did with NCCL's reduce-scatter.
  - **Temporaries.** The received partials, the padding and the all-reduce's chunk are plain caching-allocator tensors on the calling stream, allocated per call.
    - Stream-ordered: a reduction issued from another stream at the same time, such as the shared-expert overlap or the MoE communication stream, has its own.
    - A CUDA graph that captures a reduction owns its temporaries in the graph's private pool, so a larger eager step afterwards cannot free them.
    - Once cached, an allocation costs a few microseconds of host time and no device work.
    - An earlier revision kept them in Megatron's grow-only global memory buffer. A larger eager step could then free memory a captured graph still wrote, two streams could share a buffer, and the reduction needed `initialize_model_parallel`. The reduction now takes its group from the caller and reads no `parallel_state`.
- **TP = 2 without symmetric memory:** NCCL's reduce-scatter and all-reduce stay in use. Their single add is correctly rounded, and the fp32 sum rounded once gives the same bits, because fp32 has at least 2p + 2 bits for bf16's and fp16's p-bit significands. A test checks this bit for bit on random, signed-zero and subnormal partials, at sizes across NCCL's algorithm choices. Integer reductions also keep NCCL, since they are exact in any order.

Where it is used:
- **Megatron's mappings:** `_reduce` and `_reduce_scatter_along_first_dim` (equal and uneven splits), and `async_reduce_scatter_along_first_dim`. Through them it covers local row-parallel layers, embeddings, the sequence-parallel paths, the MoE expert-TP combine, and the inference fallback without symmetric memory.
- **The local linear backward:** the column-parallel input-gradient all-reduce / reduce-scatter.
- **Transformer Engine:** while batch-invariant mode is on, TE's `reduce_scatter_along_first_dim`, `allreduce` and `symmetric_all_reduce` are replaced at each of TE's import sites: `distributed`, `module.linear`, `module.layernorm_linear`, `module.layernorm_mlp` and `ops.basic.basic_linear`. TE's GEMM and RMSNorm are already patched the same way under this mode. This covers TE's row-parallel forward and its column-parallel dgrad in backward, in training and in TE-impl inference. Leaving the mode restores the originals.
- **Inference-optimized layers:** `InferenceRowParallelLinear` and `inference_reduce_scatter_to_sequence_parallel_region`, from symmetric memory when the buffer is available.

Rejected at config time: TP reductions that happen inside TE cannot be routed through Megatron. `TransformerConfig` rejects them in batch-invariant mode:
- **At `tensor_model_parallel_size > 2`, the Userbuffers reduce-scatter overlaps:** `tp_comm_overlap_rs`, `tp_comm_overlap_rs_dgrad` and `tp_comm_bulk_wgrad`, when `tp_comm_overlap` is on. They reduce inside the GEMM. The all-gather overlaps sum nothing and stay allowed at any TP; with the reduce-scatter overlaps off, TE reduce-scatters through the patched function.
- **At `tensor_model_parallel_size > 2`, `use_transformer_engine_op_fuser`:** the fused operations call `torch.distributed` directly, for example `ops.AllReduce`, `ops.ReduceScatter` and `BasicLinear`'s dgrad all-reduce.
- **`tp_comm_overlap` at any TP under the `triton` and `deepgemm` backends.** Their GEMM replaces TE's and cannot run Userbuffers' overlapped GEMMs: it raised at the first forward before this PR, and now fails at config time.

With two ranks under `te_native`, every option stays allowed, because each element is a single add.

Cost (estimates; not timed on GPU):
- **Symmetric-memory path:** the NCCL reduce-scatter becomes one Triton kernel, which reads `TP x` this rank's rows over NVLink: the same bytes as a ring reduce-scatter. The GEMM writes into the buffer directly, except under `deepgemm`, which adds one `[T, H]` device copy, as noted above.
- **Fallback, TP <= 2:** unchanged NCCL, so no cost.
- **Fallback, TP >= 3:** an NCCL all-to-all, which moves a ring reduce-scatter's bytes, then one sum kernel. The kernel reads the received `[T, H]` partials once and writes `[T / TP, H]`. For a TP=8, 8192-token, hidden-8192 bf16 dgrad that is about 144 MiB of HBM traffic, roughly 0.05 ms on H100. In backward the all-to-all overlaps the wgrad GEMM; only the sum kernel runs after it. An all-reduce also runs its all-gather after `wait()`, so in the non-SP dgrad all-reduce that half of the communication is not overlapped.
- **Memory:** the received partials (`[T, H]`) and, for all-reduces of sizes that are not a multiple of TP, a padded copy, from the caching allocator for the duration of each reduction.
- **Constraints:** no host syncs. The synchronous and asynchronous paths both capture in CUDA graphs. Non-batch-invariant paths are unchanged.

Hardening on main's MoE kernel: `inference/moe/batch_invariant.py::ordered_reduce_scatter_v`, the batch-invariant EP combine's cross-rank sum, now adds through the same `add_rn_f32`. It compiles in order with Triton 3.8 today, but nothing in its source guaranteed that. This is hardening, not a fix for an observed bug. Its determinism entry (`inference_moe_kernels`) stays, and it gains a one-GPU replay test over stand-in peers (below). The entry's note that the multi-rank run is not replayed still holds; d2 and #8871 edit that note.

What is still expected to differ between training and rollouts: nothing in the TP reduction, at any TP. The MoE expert-parallel combine has its own layout question, handled in the companion PR #8881. That PR requires the rollout TP to equal training's: a different TP shards the GEMMs differently, so no reduction can make those trees match.

Not covered: the vocab-parallel cross-entropy (`tensor_parallel/cross_entropy.py`, `fusions/fused_cross_entropy.py`) all-reduces its fp32 loss normalizer with `torch.distributed` directly. That value is a training-loss statistic, not an activation. RL log-probs do not use it: `vocab_parallel_selective_log_softmax` all-gathers the per-rank statistics and sums them in rank order already.

Interactions: the PR merges cleanly with origin/main and with the open PRs that edit `InferenceRowParallelLinear._matmul_reduce_scatter` or the `"tp"` buffer: d1 (#8561), n8 (#8704), n12 (#8709) and n16 (#8712). Its symmetric-memory kernel reads the per-rank segments that n12's barrier rules assume a reduce-scatter reads. It also merges cleanly in either order with:
- #8881;
- n15 (#8708), #8867 and s13 (#8573), which edit `enable_batch_invariant_mode` and `_mm_deepgemm`;
- d2 and #8871, which edit `inference/moe/batch_invariant.py`.

Merge order: after #8865 (`fix/bi-te-gemm-accumulate`) and #8866 (`fix/te-grouped-bi-bypass`), alongside #8867 (`fix/deepgemm-bi-dense`); the op-fuser PR #8869 (`fix/bi-op-fuser-dense`) comes after.

## Tests

- `tests/unit_tests/tensor_parallel/test_batch_invariant_reduction.py` (4 or 8 H100 ranks, TP=2 and TP=4 groups; replaces `tests/unit_tests/inference/test_batch_invariant_tp_reduction.py`):
  - `test_reduction_is_position_invariant[tp][entry]`: each rank feeds one random partial to every row. At T in {4, 64, 256, 4096}, every output row must equal the rank-order fp32 sum bit for bit. The entries are:
    - the repro's two entry points: `InferenceRowParallelLinear` from symmetric memory, and TE's `reduce_scatter_along_first_dim` as TE's Linear calls it;
    - the embedding's `inference_reduce_scatter_to_sequence_parallel_region`;
    - TE's row-parallel Linear with and without SP, TE's column-parallel dgrad in backward, and TE's `allreduce`;
    - `TELayerNormColumnParallelLinear`'s dgrad, the QKV/FC1 path of Megatron's TE spec, through `module.layernorm_linear`'s own binding. Its input is zero, so the norm's backward scales every row by the same factor; the rows must all agree;
    - local row-parallel, local column-parallel dgrad, and the mappings' reduce-scatter, async reduce-scatter and all-reduce.

    The TE dgrad entries pass `async_op=True`, so they also run the asynchronous handle.

    The TP=4 cases fail on `main`; the TP=2 cases pass there.
  - `test_rollout_reproduces_training`: one token at different rows and chunks in a 256-row training forward (TE's reduction) and a 64-row rollout step (inference-optimized, from symmetric memory) must give the same bits. Fails on `main` at TP=4.
  - `test_two_rank_nccl_add_equals_rank_order_sum[dtype][numel]`: for bf16, fp16 and fp32, NCCL's two-rank reduce-scatter and all-reduce must equal the kernel's rank-order sum, on its all-to-all and symmetric-memory inputs. The partials span a wide exponent range and include signed zeros and subnormals; sizes run from 8 elements to 16M per rank, across NCCL's algorithm and protocol choices. This is the condition for keeping NCCL at TP=2.
  - `test_async_reduction_finishes_on_wait[op]`: async reduce-scatter and all-reduce return a handle with the all-to-all in flight, and after `wait()` give the synchronous bits. Two are in flight at once, waited in reverse order.
  - `test_reduction_at_tp6`: six ranks of the job (needs at least 6 GPUs), through symmetric memory, the all-to-all and the all-reduce, with no model-parallel state initialized.
  - `test_graph_replay_after_a_larger_eager_reduction[op]`: it captures a 64-row reduce-scatter or all-reduce, runs a 1024-row one eagerly, allocates tensors of the small temporaries' size, and replays. The replay must give the eager bits and leave those tensors intact. With the grow-only buffer of the earlier revision, the replay wrote into the freed block.
  - `test_reductions_on_two_streams_do_not_share_temporaries`: it issues two reductions from two streams, holding the first stream's sum until the second's all-to-all has run. Both results must be the rank-order sums. With shared temporaries, the first summed the second's partials.
  - `test_layout_matches_nccl`, `test_uneven_reduce_scatter_sums_in_rank_order`, `test_reduction_replays_in_cuda_graph` (symmetric memory, all-to-all, async all-to-all, all-reduce), and `test_te_reductions_are_restored_outside_batch_invariant_mode`. The last now checks every patched TE module, including `layernorm_linear` and `layernorm_mlp`.
- `tests/unit_tests/inference/engines/test_batch_invariant_pairwise.py::test_parallel_batch_invariance[tp4-sp]` (new case; needs 4 GPUs, and CI runs it at 8 as two TP=4 groups): a TE-impl model at TP=4 with sequence parallelism, with the target request decoded alone and co-batched. It fails on `main` (the generated tokens differ).
- `tests/unit_tests/transformer/test_transformer_config.py` (CPU), all failing on `main`:
  - `test_batch_invariant_rejects_tp_reductions_inside_te` covers the Userbuffers reduce-scatter overlaps and the op fuser at TP=4, and Userbuffers under `triton`.
  - `test_batch_invariant_accepts_tp_communication_without_te_internal_reductions` checks that all-gather overlaps at TP=4 and every option at TP=2 under `te_native` are accepted.
  - `test_batch_invariant_rejects_userbuffers_under_substituted_gemms` covers `deepgemm` at TP=2.
- `test_batch_invariant_reduction.py::test_inference_gemm_into_symmetric_memory_runs_the_backend_kernel` (1 GPU): under `triton`, the inference GEMM written into a given buffer runs the persistent kernel into it, with the bits of the unbuffered GEMM.
- Determinism (1 GPU each):
  - The kernel is registered as `tensor_parallel_batch_invariant_reduction`. `test_tensor_parallel_kernels.py::test_batch_invariant_rank_ordered_sum_replays` replays it on the all-to-all output.
  - `test_batch_invariant_rank_ordered_sum_from_peers_replays[3, 6, 8]` replays its symmetric-memory reading. A new harness helper, `LocalSymmetricPeers`, stands in local buffers for the peers and primes the barrier slots, which exercises the padded arange at TP 3 and 6.
  - `test_inference_kernels.py::test_ordered_reduce_scatter_v_sums_in_rank_order_and_replays[2, 4]` does the same for the MoE kernel. It is a guard: it also passes on `main`, whose plain fp32 chain compiles in rank order with Triton 3.8; it fails if a compiler ever reorders the adds.
  - Each test checks bits against a torch rank-order sum. `tools/check_kernel_determinism_coverage.py` passes.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), the regression tests pass (73 cases): `test_batch_invariant_reduction.py` on 8 ranks (54 cases, including `test_reduction_at_tp6`), `test_parallel_batch_invariance` on 4 ranks (4 cases), and the determinism and config tests on 1 GPU (15 cases). On `main`, `test_parallel_batch_invariance[tp4-sp]` fails (generated tokens differ) and the other three cases pass. The 8-rank and 1-GPU sets only fail at import on `main`: they import `megatron.core.tensor_parallel.batch_invariant_reduction`, which this PR adds, so none of their cases runs there, and their "Fails on `main`" notes above are not checked on GPU. Besides `[tp4-sp]`, the step 3 GPU repro of this finding (R04-F3) shows the bug on `main` at TP 4 on H100: the NCCL reduce-scatter gives the same token different bits depending on its chunk and the step's token count. The neighbor tests (`test_mappings.py` on 8 ranks, `test_mtp_kv_cache_inference_optimized_sequence_parallel` on 2, `test_ordered_reduce_scatter_v_sums_in_rank_order_and_replays`) pass (11 cases).
