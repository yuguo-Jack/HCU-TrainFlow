# Fix LayerWise buffer routing to respect use_muon = False

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/6642) · state: closed · merged: True

## Original PR description

## Summary of this PR

This PR makes a change to respect explicit `use_muon=False` exclusions when assigning parameters to LayerWise optimizer buffers.

## Problem

The problem is with a 2D parameter with `use_muon=False` (for instance, the `in_proj` params in Mamba2, GDP etc).

In that case, the Muon parameter-group routing already sends this parameter to the configured scalar optimizer. The layout-based LayerWise path classified the same parameter only by shape and embedding metadata, so it still tagged that matrix as LayerWise-managed.

That disagreement leaves this parameter unassigned: The scalar `DistributedOptimizer` filters out LayerWise buffers, while the `LayerWiseDistributedOptimizer` receives only Muon parameter groups. The excluded
matrix therefore has no optimizer that can update it in the layout-based path.

## Simple fix

`is_managed_by_layer_wise_optimizer()` now returns `False` for a parameter marked `use_muon=False` before applying its normal matrix and embedding checks. This makes DDP buffer ownership agree with Muon's existing parameter-group routing.

## Tests

- CPU routing test verifies that Muon's exclusion predicate and LayerWise ownership agree for an explicitly excluded 2D matrix.
- CPU tagging test verifies that an ordinary 2D matrix and an excluded 2D matrix land in different ownership classes.
- Eight-rank distributed test verifies that the excluded matrix is actually updated by the scalar distributed optimizer and remains bitwise identical across DP ranks.
- Existing layout and LayerWise optimizer tests remain enabled in the post-fix gate.
- A pre-fix snapshot with the new tests reproduces both failures; the same tests pass with the one-line fix.

- claude[bot] · comment · 2026-08-18T21:31:18Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/6642#issuecomment-5334310331)

Light review — the fix looks correct. `is_managed_by_layer_wise_optimizer()` is now the exact negation of `_is_muon_excluded()` (`megatron/core/optimizer/emerging_optimizers.py:147`) for every attribute/shape combination, so DDP buffer ownership and Muon param-group routing agree. Nice catch on the silent-no-update failure mode, and good that the distributed test asserts the weight actually changes rather than just that `step()` succeeds.

One non-blocking suggestion on test coverage. The two predicates are still independent implementations of the same rule, which is exactly what allowed this bug — and `test_explicit_muon_exclusion_matches_optimizer_routing` only pins the agreement for the single `use_muon=False` 2D case. A parametrized agreement test over the full attribute/shape matrix would guard against the next divergence (e.g. someone adding a condition to one predicate but not the other):

```python
@pytest.mark.parametrize(
    "shape,attrs",
    [
        ((16, 8), {}),                                          # plain matrix -> LayerWise
        ((16, 8), {"use_muon": False}),                         # explicit exclusion
        ((16, 8), {"use_muon": True}),                          # explicit opt-in
        ((16, 8), {"is_embedding_or_output_parameter": True}),   # embedding matrix
        ((16,), {}),                                            # bias / LayerNorm
        ((16,), {"use_muon": False}),
        ((4, 4, 4), {}),                                        # non-matrix
    ],
)
def test_layer_wise_ownership_is_negation_of_muon_exclusion(self, shape, attrs):
    param = _make_param(shape, **attrs)
    assert is_managed_by_layer_wise_optimizer(param) == (not _is_muon_excluded(param))
```

This subsumes the existing single-case test, so it could replace it rather than be added alongside.

Also worth double-checking the `MuonExcludedMatrixModel` distributed test at `WORLD_SIZE=8`: the LayerWise buffer ends up holding exactly one param (`muon.weight`, shape `(5, 8)`) spread over 8 shards, leaving 7 shards empty. `TinyModel` already exercises a similar single-matrix layout so this is probably fine, but confirm the run is green on 8 ranks and not just locally.
