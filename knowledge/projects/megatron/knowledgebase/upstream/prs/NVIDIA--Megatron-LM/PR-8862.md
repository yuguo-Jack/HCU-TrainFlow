# [Inference] Rotate head shapes FlashInfer's fused RoPE gets wrong exactly in fp32

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8862) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

With `use_flashinfer_fused_rope`, dynamic inference now rotates every head shape correctly. Shapes FlashInfer's fused RoPE kernel cannot handle are rotated in fp32 instead; before, they were silently mis-rotated or crashed.

## Bug

`DynamicInferenceContext.apply_fused_qk_rotary_emb` sent every head shape to `flashinfer.rope.apply_rope_with_cos_sin_cache`, except NeoX with head dim 16. That one case has an fp32 fallback, added for "FI 0.6.6 corrupts NeoX D16 heads".

FlashInfer (0.7.2.post1, the `uv.lock` pin) rotates one vector of `vec` lanes per thread. Each vector gets one sign, one partner offset and one cos/sin index, and is read and written with 16-byte loads and stores:
- head dims 64/128/256/512 use a dedicated kernel with `vec = max(8, D/32)`;
- every other head dim uses `RopeQuantize` with `vec = 16`.

So with head dim `D` and rotary width `R` (the cos/sin cache width, `R < D` for `rotary_percent < 1`), any shape whose NeoX half or interleaved span is not a whole number of vectors goes wrong:
- **Silent mis-rotation:** NeoX with `R ≡ 16 (mod 32)` on the generic kernel. Lanes `R/2..R/2+7` take the first-half sign and partner. On H100: 32/16, 48/48, 80/80, 96/48 and 112/112 (`|err|` up to 2.2). Full-rotary examples are 48, 80 (GPT-3-2.7B-style, hidden 2560 with 32 heads) and 112; partial ones are 32/16, 96/48, 160/80 and 224/112.
- **Crash:** NeoX with `R % 16 != 0` (either kernel). The partner load at `R/2` is misaligned, which raises a sticky `CUDA error: misaligned address`. On H100: 72/72, 96/24 (GPT-NeoX-20B style) and 128/40. Pythia/StableLM-style 80/20 is another example.
- **Racy and out of bounds:** interleaved with `R ≡ 8 (mod 16)`. The last vector spills into lanes that other blocks store; when `R = D`, it writes 16 bytes past the output.

The feature is opt-in (`use_flashinfer_fused_rope` defaults to False, or None to use FlashInfer when installed). Common production shapes (head dim 64/128/256 at full, 1/2 or 1/4 rotary; 96/160/192 at full rotary) were and stay exact.

## Fix

- `flashinfer_fused_rope_supports(head_dim, rotary_dim, interleaved)` in `dynamic_context.py` states the rule: the NeoX half (`R/2`) or interleaved span (`R`) is a multiple of `vec`, and `D % 8 == 0`, so that 16-byte head bases are aligned.
- `apply_fused_qk_rotary_emb` sends a shape to FlashInfer only when that holds. Every other shape is rotated in fp32 with the same cos/sin cache, by the existing NeoX D16 fallback, now generalized to any shape and to the interleaved layout. Supported shapes run the same FlashInfer kernel as before.
- Both `use_flashinfer_fused_rope=True` and `None` route unsupported shapes this way. The fallback is exact, so there is no shape to reject.

Where the decision is made: the rule is a pure function of `(D, R, layout)`. It is evaluated from the call's shapes, as the D16 check it replaces was. It cannot run at context construction: `R` comes from `GPTModel`'s `rotary_percent`, which neither `TransformerConfig` nor `InferenceConfig` carries. The check is a few integer operations on the host, issues no GPU work and no syncs, and does not run on CUDA-graph replays. Moving the decision into the models is a follow-up (see the notes below).

## Tests

New in `tests/unit_tests/inference/contexts/test_dynamic_context.py`:
- `test_flashinfer_fused_rope_supports` (CPU): the predicate accepts the shapes FlashInfer rotates exactly and rejects the silent, crashing, racy and D16 shapes. Fails on `main` (no predicate).
- `test_flashinfer_fused_rope_matches_fp64_rotation[...]` (1 GPU, FlashInfer). Three query and two key heads are views of one buffer, with 4 of 6 rows active, the same layout as the existing oracle in `test_coordinator_features_pairwise.py`. The test checks every lane against an fp64 complex rotation (`atol = 2 eps(bf16)`) and checks which shapes reach the FlashInfer kernel:
  - 6 kernel shapes (controls, pass on `main`): 32/32, 96/96, 64/64, 64/16 and 128/48 NeoX, 32/16 interleaved.
  - The 5 silent shapes: 32/16, 48/48, 80/80, 96/48 and 112/112 NeoX. They fail on `main`, on lanes `R/2..R/2+7`.
  - 2 racy interleaved shapes, 16/8 and 96/24. Their result on `main` depends on block order.
- `test_flashinfer_fused_rope_kernel_shapes_match_fp64_rotation` (1 GPU, FlashInfer): all 49 shapes the predicate sends to FlashInfer (head dims up to 256 in steps of 8, and 512; `rotary_percent` 1, 0.5 and 0.25; both layouts) against the same fp64 rotation, and each must reach the kernel. The predicate encodes one FlashInfer release's vector widths and dispatch; a release that changes either fails here instead of mis-rotating silently. It is a control for the predicate; on `main` it fails only because `main` has no predicate.
- `test_flashinfer_fused_rope_fault_shapes_run` (1 GPU, FlashInfer): 72/72, 96/24 and 128/40 NeoX, plus 72/72 interleaved (`R = D`, out-of-bounds store). The fault is sticky, so the four shapes run in one child Python process, which must exit cleanly with exact rotations. On `main` the child dies with a misaligned address at the first NeoX shape. The interleaved 72/72 shape alone may pass on `main`, so three of the four are failing-on-`main` cases.

These GPU tests fail rather than skip when FlashInfer is missing, since the CI image ships it.

Determinism: `tests/unit_tests/determinism/kernels/test_inference_kernels.py::test_flashinfer_fused_rope_replays` replays `apply_fused_qk_rotary_emb` bit-exactly under side-stream contention on both of its paths: 128/128 NeoX on the FlashInfer kernel, 96/24 interleaved on the fp32 path. The kernel races on that interleaved shape, so a change that sends it back to FlashInfer can show up as a replay mismatch. A new `inference_flashinfer_fused_rope` entry in `tests/unit_tests/determinism/kernels/manifest.py` registers this dispatch in `dynamic_context.py` with that test; before, the file was registered only under the integer-bookkeeping exemption, which does not cover RoPE. As for `attention.py`, a later PR that changes `dynamic_context.py` must then touch `test_inference_kernels.py` or carry the `determinism-exempt` label. `python3 tools/check_kernel_determinism_coverage.py --base-ref origin/main` passes.

The existing `test_small_neox_rope_matches_complex_rotation` keeps passing unchanged, including its D16 NeoX fallback and its "native kernel called" counts.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02, FlashInfer 0.7.2.post1), the regression tests above pass (18 cases) and fail on `main` (12 of 18 cases):
- The 5 silent shapes and the 2 racy interleaved shapes fail on the fp64 comparison, on lanes `R/2..R/2+7` (up to 3.76 off). The 6 kernel-shape controls pass.
- In the fault-shape test, the child process dies with `CUDA error: misaligned address`.
- The predicate test, the 49-shape test and both replay cases fail because `main` has no `flashinfer_fused_rope_supports`.

Under `compute-sanitizer --tool memcheck`, the same tests except the fault-shape test (a child process) pass (17 cases), with no memory errors reported. The neighbor tests (`test_coordinator_features_pairwise.py::test_small_neox_rope_matches_complex_rotation` and the `flashinfer-fused-rope` case of `test_dynamic_engine_async_sched.py::TestAsyncSchedulePairwise`) pass (9 cases).

## Notes for reviewers

- **Performance.** Affected shapes now run several eager elementwise ops on `[tokens, heads, R]` instead of one fused kernel. Before, those shapes produced wrong results or crashed.
- **FlashInfer version.** The rule was derived from FlashInfer 0.7.2.post1's `pos_enc.cuh`, the `uv.lock` pin. The step-3 H100 image had 0.7.0.post1, and the repro's controls and failures matched there. The tests above ran on 0.7.2.post1. The 49-shape test checks the rule against whichever FlashInfer is installed.
- **Upstream.** The mis-rotated and faulting shapes should be reported to FlashInfer, together with a pre-existing over-read. For interleaved layouts both kernels load `vec` floats of sine from `R/2 + tx*vec/2`, so the last thread reads `vec/2` floats (16 to 32 bytes) past the cos/sin row. The values are unused and the output stays exact. At the cache's last position, though, the read goes past the end of `rotary_pos_cos_sin`, so `compute-sanitizer memcheck` can report an interleaved kernel shape at position `max_sequence_length - 1`. The fp32 path does not over-read, and the fault-shape test calls no FlashInfer kernel. This PR does not change the over-read.
- **Where the decision lives.** The kernel-capability check stays next to the kernel call in the context. Moving it into the models' RoPE-input helper (added by #8863) would let unsupported shapes take the standard unfused RoPE path and retire this fp32 rotation. That needs this PR, #8863 and #8864 merged first, so it is a follow-up.
- **Attention dropping RoPE** (the review's P4-N1): attention dropped `rotary_pos_emb` whenever the context enabled fused RoPE, so GPT YaRN and multimodal RoPE, HybridModel RoPE and YaRN got no RoPE, and `no_rope_freq` layers still got the fused rotation. That is a separate root cause in the model and attention code, fixed by #8863 and #8864 below, not here.

## Interaction with other open PRs

Three PRs fix FlashInfer fused RoPE in dynamic inference, each at a different layer:
- **#8862 (this PR, `fix/flashinfer-fused-rope-shapes`)**, the context: whatever cos/sin cache a model passes, `apply_fused_qk_rotary_emb` rotates every head shape exactly.
- **#8863 (`fix/hybrid-flash-decode-rope`)**, the models: one `LanguageModule` helper owns the RoPE inputs of `GPTModel` and `HybridModel`, so RoPE hybrids also build the FlashInfer cos/sin cache and pass it through `HybridStack`.
- **#8864 (`fix/fused-rope-model-embedding`, stacked on #8863)**, attention: fused RoPE runs only when the model passes a cache, which the helper builds for RoPE and YaRN; no-RoPE layers get none, and multimodal RoPE runs unfused.

They change different code. Together, every model with fused RoPE on gets its own RoPE, rotated exactly for every head shape. The merge order is this PR, then #8863, then #8864, and stacking enforces it: #8863 (which turns fused RoPE on for RoPE hybrids) and #8864 (which turns it on for YaRN) both contain this branch. Without this PR, FlashInfer's kernel faults on some of their head dims (e.g. 72) and silently mis-rotates others (e.g. 80). Once this PR is merged, the manifest entry added here makes the coverage gate flag their `dynamic_context.py` edits, which only add constructor checks; they need the `determinism-exempt` label.

This PR also merges cleanly with `main` and with every open fix branch that merges with `main`. Its manifest entry sits next to the other FlashInfer dispatch entry, away from the entry #8880 adds.
