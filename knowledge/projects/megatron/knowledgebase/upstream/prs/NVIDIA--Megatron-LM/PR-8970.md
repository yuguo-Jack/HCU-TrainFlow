# [Test][Inference] Independent oracles for the vLLM fused MoE backend

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8970) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Adds an independent oracle test for the vLLM fused-MoE backend, `vllm_fused_moe`, the default `inference_grouped_gemm_backend` for BF16 MoE layers. The test is `tests/unit_tests/inference/oracles/moe_vllm/test_vllm_fused_moe.py`. It covers the whole pipeline:
- the Triton grouped GEMM and its block alignment (init, count, prefix-sum, fill and scatter kernels);
- the launch-config table and the persistent buffer pool;
- the activation glue (`bounded_silu_mul` and the batch-invariant weighted activations) and the top-k reduction (`_moe_sum`).

No production code changes.

**Stacked on the oracle harness PR #8966 (`test/inference-oracle-harness`)**, which adds the shared helpers this test uses. Retarget to `main` once it merges.

## Why

The existing unit tests for this backend miss most errors:
- They compare against a per-token loop with `atol = rtol = 5e-2`. Their outputs are around 1e-2, so an all-zero output, a wrong expert or swapped SwiGLU halves would all pass.
- The only discriminating test (the tanh clamp) covers BLOCK_SIZE_M 16 and 32.
- BLOCK_SIZE_M 128, GROUP_SIZE_M 16, the grid-stride path and the default SwiGLU path have no reference check.

## The oracle

The module docstring holds the contract. It was written from the call site (`InferenceGroupedMLP._vllm_forward`), the training expert math and the function's API before the kernels were read. For each live token:

    out[t] = Σ over local slots j of p[t, j] · W2[e] · act(W1[e] · x[t])

`act` is squared ReLU, the tanh-clamped squared ReLU `(s·tanh(relu(h)/s))²`, or SwiGLU with the gate in the first half. The contract also fixes the rounding points of each mode and the batch-invariance promise. Three oracles check it, all without hand-picked tolerances.

1. **fp64 reference.** A per-token MoE built from the expert weights, with no padding, tiles or index tables. The tolerance follows the harness policy: per output row, the kernel's max-abs and rms errors must be at most 2× those of a trusted torch MoE, plus one ulp. The trusted MoE uses fp32 matmuls with TF32 off, on the same device, with the contract's rounding points.
2. **Exact rounding-point spec.** The inputs are small integers and probabilities j/16. Every GEMM and top-k sum is then exact in fp32 in any order, and each case checks this precondition. The squared-ReLU output must equal the spec bit for bit. A wrong token, expert, slot, column, K-tail term, probability or rounding point changes bits.
3. **Batch invariance, bitwise.** Six probe tokens run alone, then inside 11 batches whose size, padding and hint select every launch config, including a striding grid. Their rows must match bit for bit. The alone run also matches the fp64 reference.

Memory checks:
- Every float input sits in a NaN-sentinel guard band, so an out-of-bounds read shows up as a NaN in the output.
- Rows past `valid_tokens` are NaN, so a read of them shows; the output rows past it must stay poisoned.
- The output has a 128-row guard band. Inputs must be unchanged after the call.
- The persistent pool is replaced by poisoned, guarded buffers. Its unrequested tails must stay untouched, and a previous layer's data must not leak into the next.
- Two small cases carry the `sanitizer` marker.

## What it covers

- **Launch configs.** Every row of `_get_default_config`:
  - BM 16/32/32/64/64/128, with BN 64/128, BK 128/64, 4/8 warps and 3/4 stages;
  - GROUP_SIZE_M 1 and 16;
  - the batch-invariant BK pin.

  Each case asserts the config the kernel actually launched (a spy on `_invoke_fused_moe_kernel`). Both sides of every threshold (1, 32/33, 64/65, 96/97, 128/129, 512/513) are run, as a hint and as `max_tokens`.
- **Tokens around BLOCK_SIZE_M for every config.** One expert holds BM−1, BM, BM+1 or 2BM+1 rows. Other cases mix per-expert counts BM−1, BM, BM+1, 0, 1, 2BM−1, 2BM and 2BM+1 in one call.
- **Activations.** SwiGLU, squared ReLU, and the tanh clamp at the production scale 16 and a saturating 0.5. Each runs with and without batch-invariant mode, and with and without probabilities on the input.
- **Routing.**
  - top-k 1, 2 and 8;
  - empty experts, including the first and last local expert, and every token on one expert;
  - `-1` slots, and experts on other EP ranks on both sides (EP 1, 2, 4, 8);
  - int32 and int64 routing maps.
- **Grid-stride path.** Hint ≪ tiles, checked to actually stride. It includes a GROUP_SIZE_M 16 swizzle over 46 M-tiles with a partial last group, and a hot expert with 132 BM16 blocks (the fill kernel's 128-block loop).
- **Tile edges.**
  - H and F at 63/64/65/127/128/129, which are the BK and BN edges for 64 and 128, plus 96/97;
  - 1025, past the 1024-wide blocks of `_moe_sum` and the activations;
  - hidden states with a row stride larger than H.
- **Outputs.** fp32, bf16, allocated and pooled.
- **Degenerate inputs.**
  - `valid_tokens = 0` and `max_tokens = 0`;
  - every slot non-local, or every slot masked: exact zero rows;
  - top-k = E_local, one local expert, a single token.
- **Production shapes:**
  - DeepSeek-V2-Lite (SwiGLU 2048/1408, top-6, EP 8);
  - Nemotron 3 Nano (squared ReLU 2688/1856, top-6; prefill, clamp-16 decode and batch-invariant);
  - Qwen3-30B-A3B (2048/768, top-8);
  - Mixtral 8x7B (4096/14336, top-2).
- **CUDA graphs.** One capture is replayed with new inputs, routing and `valid_tokens`. `valid_tokens` takes 0, 1, values around BM and values above the captured hint. Each replay is checked against the fp64 reference, with a poisoned pool and output.
- **int32 offsets.** FC1 output rows of width 8192 straddle 2³¹. These cases are `large`, so they are opt-in.

## Tests

`tests/unit_tests/inference/oracles/moe_vllm/test_vllm_fused_moe.py` has 228 cases, all for H100 (`requires_sm(HOPPER)`):
- `test_exact_squared_relu` (54), `test_block_m_boundaries` (48), `test_matches_fp64_reference` (41) and `test_tuner_thresholds` (22);
- `test_probs_on_input` (17), `test_degenerate` (9), `test_production_sizes` (7) and `test_nan_hidden_row_propagates_to_its_token_only` (6);
- `test_batch_invariance_bitwise` (6), `test_grid_stride` (5) and `test_cuda_graph_replay` (5);
- `test_int32_offsets` (4, `large`), `test_pooled_buffers` (2) and `test_sanitizer` (2).

`test_batch_invariance_bitwise` also runs on GB200 (`launch_on_gb200`). Blackwell's tensor-core instructions may accumulate differently from Hopper's, and batch-invariant mode pins only BLOCK_SIZE_K.

Checked on CPU with the Triton interpreter, on `main`:
- every test passes except those listed below, apart from the CUDA-graph and `large` cases, which do not run on CPU;
- 8 of 9 hand mutants of the source are detected. The ninth, an off-by-one in the expert-block fill, is equivalent under the interpreter's in-order execution; on a GPU it is a race.

The H100 and GB200 runs are pending.

Two groups are expected to fail on `main`:
- **`test_probs_on_input`** (17 cases) fails with `TypeError: unexpected keyword argument 'apply_probs_on_input'`. `moe_apply_probs_on_input` is silently ignored by inference-optimized MoE layers on `main`; #8566 fixes it and adds this parameter. On a merge of #8566, all 17 pass on CPU, and the other tests run there (all but the production sizes and CUDA graphs) give the same results as on `main`.
- **`test_nan_hidden_row_propagates_to_its_token_only`** fails for squared ReLU and the clamp, in both modes (4 cases); SwiGLU passes. A NaN hidden row gives that token a zero MoE output instead of NaN. `tl.maximum(x, 0.0)` (default `propagate_nan=NONE`, i.e. `maxnum`) drops the NaN, both in the fused FC1 epilogue and in the batch-invariant `squared_relu_with_probs`. Torch's `relu`, and training, propagate it. This is a suspected finding of low severity, not yet checked on a GPU.

## Notes for reviewers

- **The trusted implementation models the contract's rounding points, not the kernel's code.** It does the same bf16 roundings as the contract, with torch's fp32 GEMMs (TF32 off) on the same device. On correct code, kernel and trusted errors therefore measure about 1:1. A wrong rounding point, a probability applied twice or a dropped term exceeds the 2× bound.
- **Exactness preconditions are checked, not assumed.** The exact spec raises a precondition error if a case's operands could make any fp32 partial sum inexact. It checks this from each operand's power-of-two quantum and an absolute-sum bound.
- **The config spy** monkeypatches `vllm_fused_moe._invoke_fused_moe_kernel` to record the launch config. It ensures each case exercises the variant its sizes were derived from. If the table changes, `spec_config` must be updated with it.
- **The pool test** replaces `VllmFusedMoeBuffers._buffers` with poisoned, guarded buffers of the sizes `allocate_buffers` chose, and deletes them afterwards.
- **Determinism.** No kernel or dispatch changes, so there is no determinism test or manifest entry.
