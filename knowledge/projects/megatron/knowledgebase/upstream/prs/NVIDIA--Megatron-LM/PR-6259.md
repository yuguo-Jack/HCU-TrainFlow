# Give gloo process groups a home in ProcessGroupCollection

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/6259) · state: open · merged: False

## Original PR description

**Why.** Distributed-optimizer checkpoint I/O can use Gloo copies of the data-parallel groups, but an explicit `ProcessGroupCollection` has no place for them: passing a collection together with `use_gloo_process_groups=True` is rejected today, so callers on their own grid cannot use Gloo.

**What.**
- Add optional `intra_dp_cp_gloo` and `intra_expt_dp_gloo` fields to `ProcessGroupCollection` and populate them in `use_mpu_process_groups()`; the Gloo accessors in `parallel_state` gain `check_initialized` so a collection can be built in jobs without Gloo groups.
- `setup_process_groups_for_optimizer` uses the collection's Gloo groups when Gloo is enabled and checks that each holds the same ranks, in the same order, as the group the distributed optimizer shards over (`dp_cp`/`expt_dp`, or `intra_dp_cp`/`intra_expt_dp` with more than one optimizer instance); a mismatch raises `ValueError`. If Gloo is enabled but a needed Gloo group is missing, it raises `ValueError` (as the global path already did) instead of silently running without Gloo. The expert Gloo group is only needed when the collection has an expert data-parallel group. GTP_remat jobs, which never build Gloo groups, keep running without them.
- `get_megatron_optimizer` resolves the global collection once, at its entry point, and passes it to the internal helpers instead of each helper falling back to global state; the helpers raise `ValueError` if they are called without a collection.
- Two fixes in the emerging-optimizer (Muon) path this touches: the separate `DistributedOptimizer` that layer-wise mode builds for non-Muon parameters now honors `use_gloo_process_groups` (Gloo was hard-coded off, so the first memory-efficient fully reshardable checkpoint save failed an assert), and without the distributed optimizer, expert gradient statistics are reduced over `tp_ep_pp_with_egtp_remat` like the standard path (over `tp_ep_pp`, EGTP_remat peers computed different grad norms and clip factors).
- `tools/process_group_usage_allowlist.json`: 196 → 195 reads, where 196 is the count for the code of main 77391e71cc. The two helper fallbacks are gone; the one remaining read is the reviewed `get_megatron_optimizer` boundary entry. The file also records three reads main added and drops one read main removed; main's own copy lists 194 entries and has neither change.

**Tests.** New tests cover: missing and supplied Gloo groups and the enable flag (including the new errors); Gloo groups whose ranks differ from the group they mirror (dense and expert, one and two optimizer instances, and a collection whose `dp_cp` was replaced); a dense collection that supplies only the dense Gloo group; freshly created Gloo groups in the collection reaching the dense and expert distributed optimizers; accessor initialization checks; the layer-wise `DistributedOptimizer`'s Gloo group, plus a Muon + Lion memory-efficient fully reshardable checkpoint round trip; and the Muon grad norm with EP=2 and EGTP_remat=2 (before the fix the two EGTP_remat peers reported 53.1 and 73.3 instead of 89.1). Before the 2026-11-01 sync with main, on 4 GPUs, `test_optimizer.py`, `test_layer_wise_optimizer.py`, `test_process_groups_config.py`, `test_parallel_state.py`, `tests/unit_tests/optimizer/`, `test_emerging_optimizers.py`, `test_lion_optimizer.py` and `dist_checkpointing/test_optimizer.py` gave 457 passed, with the same 87 failures as main (cases that need 8 GPUs on one node). On 8 GPUs (two nodes), the first three files gave 93 passed, with the same 7 checkpoint-test failures as main. In the integration run (main 77391e71cc with all 93 #6307 PRs and 6 main-based gap fixes merged, against main), the test files this PR touches give, on 4 GPUs: `test_optimizer.py` 42 passed vs 35 on main, `test_layer_wise_optimizer.py` 50 vs 48, `test_parallel_state.py` 74 vs 68, and `optimizer/test_initializer_cleanup.py` 8 vs 8. On 8 GPUs (two nodes), `dist_checkpointing/test_optimizer.py` gives 154 passed vs 153 on main. Nine `test_parallel_state.py` cases (`test_different_initialize_order_consistency` and `test_pipeline_parallel_initializations`) fail on both sides because they build 8-rank grids and the file ran on 4 GPUs. In the integration run, this PR's test files show no regressions against main. No new kernels or nondeterministic operations (hence `determinism-exempt`); the only numerics change is the EGTP_remat fix, which makes EGTP_remat peers compute the same grad norm. The rank check runs once at optimizer construction, so there is no performance impact, and the checkpoint format does not change.

**Compatibility.** `get_data_parallel_group_gloo` / `get_expert_data_parallel_group_gloo` gain a keyword with the old default. `use_gloo_process_groups=True` with a collection that lacks the needed Gloo groups, or whose Gloo groups do not mirror its data-parallel groups, is now an error (previously rejected outright for any explicit collection). Muon with the distributed optimizer now builds its separate `DistributedOptimizer` with Gloo groups when `use_gloo_process_groups` is True (the default); jobs that disable Gloo process groups pass False and are unchanged. Muon with the layer-wise distributed optimizer and the default `use_gloo_process_groups=True` now raises `ValueError` when its process groups have no Gloo groups (an explicit collection without them, or parallel state initialized with `create_gloo_process_groups=False`). It used to run because Gloo was hard-coded off. Such callers pass `use_gloo_process_groups=False`.

**Release notes.**
- Muon jobs with the layer-wise distributed optimizer now build the separate `DistributedOptimizer` with Gloo groups by default. Their memory-efficient fully reshardable checkpoint saves now gather over Gloo instead of failing an assert.
- Muon without the distributed optimizer and with EGTP_remat > 1 now computes the same grad norm and clip factor on every EGTP_remat peer.
