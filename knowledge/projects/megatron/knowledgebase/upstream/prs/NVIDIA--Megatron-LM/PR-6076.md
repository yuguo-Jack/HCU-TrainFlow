# Make Triton autotune configuration selection deterministic

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/6076) · state: closed · merged: True

## Original PR description

Triton picks a kernel configuration by timing its candidates the first time the kernel runs. The winner can differ between ranks and between runs, and a different tiling changes the floating-point reduction order, so two identical runs can produce different numbers. Caching the winners (`TRITON_CACHE_AUTOTUNING=1`) doesn't fix this: a rank that misses the cache times the candidates again on its own.

This PR adds `megatron.core.tuning`. Under `--deterministic-mode`, every autotuner in scope is pinned to one configuration that is chosen without timing. Runs without `--deterministic-mode` keep Triton's timed autotuning.

## How a configuration is chosen

1. The packaged table entry for the kernel and shape, if there is one. The `sm100` and `sm103` tables cover the in-tree Mamba, MLA RoPE and mHC kernels.
2. Otherwise, a configuration that matches `block_sizes`, if set.
3. Otherwise, the cheapest candidate, or an error with `on_miss="error"`.

The default scope is `mamba_ssm`, `transformer_engine` and `megatron.core`. Transformer Engine's MoE permutation kernels stay timed: their output doesn't depend on the configuration, and pinning would make them about 5x slower.

## Usage

`--deterministic-mode` is all most runs need. Every other option is a `--triton-autotune-*` argument generated from the `AutotunePolicy` fields, or a `triton_autotune` section with `--yaml-cfg`. `initialize_megatron` installs the policy before any kernel runs. Code that builds models without the training initializer calls `install(AutotunePolicy(...))`. The README in `megatron/core/tuning` lists all options.

- `--triton-autotune-verify-every N` compares the configurations that ranks chose every N steps.
- `--triton-autotune-enumerate-autotuners` lists every autotuner a run reaches and whether it is pinned.
- To build a table for a new GPU, run with `--triton-autotune-record-path PREFIX`, merge the per-rank files with `python -m megatron.core.tuning merge`, and pass the result's directory to `--triton-autotune-table-path`.

## Behavior changes

- Megatron's own SSM kernels follow `--deterministic-mode` instead of `MAMBA_DETERMINISTIC`, which still controls the external `mamba_ssm` package.
- `block_sizes` replaces the `TRITON_AUTOTUNE_BLOCK_*` environment variables.
- Under `--deterministic-mode`, `TRITON_CACHE_AUTOTUNING` only matters for autotuners outside the scope, because pinned kernels never time candidates.
- `ArgumentGroupFactory` gains a `prefix` option and supports `tuple[T, ...]` fields.

## Performance

Without a table entry, the cheapest candidate was up to 12.5x (MLA RoPE) and 16x (mHC) slower per kernel than the timed winner. With the packaged tables, total Triton kernel time for these kernels is within 1% of timed autotuning at the measured shapes, and within 6% at a head count that wasn't measured. These numbers are from GB300. The `sm100` table reuses the `sm103` entries and wasn't measured separately.

## Strict Review Summary

**Findings — CRITICAL: 0, IMPORTANT: 2, SUGGESTION: 1**

This is a carefully engineered and unusually well-documented change. The core mechanism — pinning Triton's candidate list to a single entry chosen by a pure, timing-free rule, restored in a `finally` so per-shape selection still works — is sound and correctly exploits Triton's `len(configs) > 1` benchmarking gate. The layering (`policy` / `selection` / `table` / `interception`) cleanly isolates the one file that touches Triton internals, and the table-lookup-against-live-candidates approach correctly degrades a stale entry to a miss rather than an invalid launch. The CPU-only unit tests cover the meaningful branches. Determinism gating (`use_deterministic_mode`) means non-deterministic perf runs are genuinely untouched.

### Most impactful findings

1. **`verify_choices(group=...)` sizes gather lists by global world size but passes a subgroup** (`interception.py:111-117`) — the default `group=None` path works (hence green tests), but any subgroup call, which is the natural use, breaks. Latent trap in a public diagnostic API.

2. **`verify_every` / `MCORE_AUTOTUNE_VERIFY` is inert** (`policy.py:83`) — parsed and documented as a step-cadence check, but never read and `verify_choices()` is never called from the training loop. A user enabling it to catch cross-rank divergence silently gets no protection. Either wire it in or drop it from the surface until the call site lands.

3. **`_explicit_mode` is a dead field** (`policy.py:87`) — stored, never read; the "explicit mode wins" behavior is already realized in `from_env`. Minor cleanup.

### Risk assessment

**Low risk to existing users.** Behavior is fully gated behind deterministic mode / explicit env opt-in; the default `auto` mode leaves Triton untouched, and `install()` is idempotent and no-ops without an interception. No checkpoint-format, config-default, or public-signature breakage. Legacy `DET_AUTOTUNE_*` env names are preserved. The `megatron/core` process-group guidance does not apply (no new `parallel_state.get_*_group()` reads). The two IMPORTANT items are correctness/UX gaps in the *new* diagnostic surface rather than risks to the pinning path that is the point of the PR — the pinning itself is validated by the reported 1536-GPU bit-exact runs. Worth resolving the `verify_choices` group sizing and the inert `verify_every` before merge so the shipped diagnostics do what they advertise.

**[IMPORTANT Correctness]** `verify_choices(group=...)` sizes both gather lists with the *global* world size (`torch.distributed.get_world_size()`) but passes `group=group` to `all_gather_object`. `all_gather_object` requires `len(object_list) == get_world_size(group)`; when a caller passes a non-default subgroup, the list is the wrong length and the collective errors (or silently mis-fills).

Why it matters: the `group` parameter is part of the public API of this diagnostic, and the natural use — verifying agreement within a DP/TP subgroup — is exactly the broken path. The default `group=None` case works, which is why tests pass, so this is a latent trap.

Suggestion: size the lists to the group's world size:
```python
world_size = torch.distributed.get_world_size(group=group)
digests: list = [None] * world_size
torch.distributed.all_gather_object(digests, choice_digest(), group=group)
...
maps: list = [None] * world_size
torch.distributed.all_gather_object(maps, dict(_choice_log), group=group)
```

If the wiring is deliberately deferred, add a `TODO` and note in the README that the cadence var is not yet honored.
