# Raise ValueError for missing sequence-packing process groups

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8727) · state: closed · merged: False

## Original PR description

**Why.** `wrap_data_iterator` checks its process groups with an `assert`, while the sibling `get_batch_on_this_rank_for_sequence_packing` raises `ValueError` for the same caller error. Under `python -O` the assert is stripped, so a missing group shows up later as an `AttributeError` on `None`. The assert message names `dp_cp` and `dp`, but the function reads the GTP-remat-inclusive `dp_cp_gtp_remat` and `dp_gtp_remat` first, and the docstring leaves those fields out. A `None` collection fails with an `AttributeError`.

**What.**
- Raise `ValueError` naming exactly the groups the collection lacks, for example `pg_collection must define dp_gtp_remat (or dp), tp for sequence packing`. A field set to `None` counts as missing.
- Reject a `None` collection with the message the sibling function uses.
- Group selection is unchanged: `dp_cp_gtp_remat` or `dp_cp`, `dp_gtp_remat` or `dp`, `tp`, `pp`.
- The docstring covers the fields read (including `dynamic_cp`), `num_microbatches` and the error.

**Tests.** New cases in `tests/unit_tests/test_sequence_packing.py`:
- each missing group, absent or `None`, appears in the `ValueError`, raised before any group method is called;
- a `None` collection raises `ValueError`;
- on the standard grid, a collection with only `dp`/`dp_cp`, or only the GTP-remat data groups, packs the same batch as the full collection.

Before the sync, on 4 GPUs against main: no regressions. With the other process-group changes from #6307 applied, the 13 new cases passed on 4 GPUs. At 4 GPUs, 7 existing tests in this file failed on main and here alike. In the integration run (main 77391e71cc with all #6307 PRs merged, against main), `test_sequence_packing.py` runs on 8 GPUs (two nodes) and passes in full: 53 passed vs 40 on main, the difference being the 13 new cases. In the integration run, this PR's test files show no regressions against main. The new cases were not run against main on GPU. A CPU check of main's function gives `AssertionError` and `AttributeError` where they expect `ValueError`.

**Compatibility.** The conditions that raise are the same. Only the exception type changes: `AssertionError` becomes `ValueError`, and for a `None` collection `AttributeError` becomes `ValueError`. No in-repo or known downstream caller catches either. The two `or` fallbacks stay independent, as on main, so a collection that mixes the GTP-inclusive and replicate data groups (for example `dp_cp_gtp_remat` with `dp` but no `dp_gtp_remat`) still passes validation when GTP remat is above 1.
