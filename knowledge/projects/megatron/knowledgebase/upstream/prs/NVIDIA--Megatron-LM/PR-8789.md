# Handle aborts while a RECOMPUTE suspend has freed request state

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8789) · state: open · merged: False

## Original PR description

## What does this PR do?

A RECOMPUTE suspend without static KV pointers deletes every tensor on the
dynamic context, including `request_ids`, `request_output_lengths` and the
other per-request rows. The engine keeps handling coordinator messages while
it is suspended. When an `ABORT_REQUEST` arrives in that window,
`schedule_requests()` reads `context.request_ids` to find the request's row,
and the engine raises `AttributeError` instead of acknowledging the abort.

This PR skips that row lookup while the context is under RECOMPUTE and its
tensor state is released. The handler still shortens the request's record
to the tokens generated so far. Resume re-adds every request that a
RECOMPUTE suspend saved from that record, so the request then finishes with
exactly those tokens. PERSIST and OFFLOAD keep their rows across a suspend
and still update them.

## Example failure scenario(s)

**Scenario (abort during a RECOMPUTE suspend)**
- An engine uses RECOMPUTE KV management without static KV pointers, and
  request A has generated 3 of its 8 tokens.
- The engine is suspended, which saves A for recompute and deletes the
  context's request tensors.
- A client cancels A, so the coordinator sends `ABORT_REQUEST` while the
  engine is still suspended.
- The engine's next `schedule_requests()` reads `context.request_ids`, which
  no longer exists, and raises `AttributeError`.

## How was this bug discovered?

A stateful search of the dynamic engine was being extended with an abort
action that sends `ABORT_REQUEST` through the real `schedule_requests()`
handler. While writing that action, reading the handler showed that it
looks up the request's context row unconditionally, and that a RECOMPUTE
suspend without static pointers deletes those rows. The expected result was
that an abort is acknowledged in every engine state and the request
completes with the tokens it already had. A short replay (submit, step,
suspend, abort, resume, drain) on the search's October 28 `main` raised
`AttributeError: 'DynamicInferenceContext' object has no attribute
'request_ids'`. The same replay passed under PERSIST and under RECOMPUTE
with static KV pointers, where the rows still exist.

## Scope

- Production: `megatron/core/inference/engines/dynamic_engine.py`, the
  `ABORT_REQUEST` branch of `schedule_requests()` only (+17/−9).
- Tests: `tests/unit_tests/inference/engines/test_dynamic_engine.py` (+75):
  `test_abort_while_suspended_keeps_generated_tokens`, parametrized over
  RECOMPUTE and PERSIST without static pointers. It generates 3 of 8 tokens,
  suspends, sends the abort through `schedule_requests()`, resumes and
  drains, and requires the request to complete with exactly its 3 tokens.
- No functional-test, config or API change.
