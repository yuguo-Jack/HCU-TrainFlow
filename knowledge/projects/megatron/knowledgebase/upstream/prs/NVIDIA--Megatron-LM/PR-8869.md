# [Core][BatchInvariant] Make the TE op fuser's dense GEMMs and RMSNorm batch-invariant

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8869) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Under `batch_invariant_backend="deepgemm"` or `"triton"`, models built with the TE operation fuser (`use_transformer_engine_op_fuser=True`) now run their dense GEMMs and RMSNorm on the batch-invariant kernels.

**Stacked on #8866 (`fix/te-grouped-bi-bypass`), and depends on #8865 (`fix/bi-te-gemm-accumulate`).** This PR extends #8866's fail-closed binding mechanism from TE's grouped GEMMs to its dense GEMM and RMSNorm. It also needs #8865's `general_gemm` that honors `accumulate`, `alpha` and `beta`, because the op fuser's linears rely on them. That branch is merged into this one. Review only the commits `Make the TE op fuser's dense GEMMs and RMSNorm batch-invariant` and `Address review feedback: leave accumulate/alpha/beta to #8865; the merge commit brings in #8865 unchanged. Retarget to `main` once #8866 and #8865 are merged.

## Bug

Batch-invariant mode makes TE's GEMMs and norms batch-invariant by rebinding the module-level names TE calls them through. Two op-fuser paths were not rebound:
- **Dense GEMM.** The dense patch rebound `general_gemm` only in `cpp_extensions`, `module.linear` and `module.layernorm_linear`. The op fuser's `te.ops.BasicLinear`, which builds Megatron's `TEFusedMLP` linears, imports `general_gemm` into `ops/basic/basic_linear.py` (TE 2.20.2, line 15). It therefore ran TE's cuBLASLt GEMM with TE's full workspace, whose split-K choice depends on the token count, so a token's output bits depend on its co-batch. TE's `module.layernorm_mlp`, `ops/fused/userbuffers_*` and `ops/fused/grouped_mlp` bind it too.
- **RMSNorm.** The op fuser's `te.ops.RMSNorm` imports `transformer_engine_torch.rmsnorm_fwd` by name (`ops/basic/rmsnorm.py:15`) and never goes through the `RMSNorm` class or `apply_normalization` that the norm patch replaces. It ran TE's norm kernel, whose reduction depends on the row count.

Rebinding these sites alone would not be enough. The op fuser's linears pass `accumulate` into `main_grad`, `alpha=None` on every dgrad and wgrad, and 3D `x` and `dy` that TE flattens to 2D before transposing. Honoring all three is #8865 (P4-N4), which this branch merges. Without it, the first op-fuser backward would raise.

Affected: batch-invariant mode with `deepgemm`/`triton` and the op fuser (dense layers, and the norms of MoE models). `te_native` is unchanged: it patches no GEMM or norm.

## Fix

- **Dense GEMM, fail closed.** `general_gemm` is replaced by identity, like the grouped GEMMs in #8866. Every global of a loaded `transformer_engine` module that is TE's `general_gemm` is rebound to the batch-invariant GEMM, whatever the module. If one still binds the original afterwards, enabling the mode raises. Disabling restores every binding. Megatron's own `extensions.transformer_engine.general_gemm` is patched as before. The fixed per-module code for `module.linear` and `module.layernorm_linear` is removed.
- **What the patched GEMM serves.** `_te_general_gemm_patched` comes from #8865. It computes `alpha * op(A) @ op(B) + beta * out + bias` like TE, and raises for calls it cannot honor instead of running TE's cuBLASLt kernel: GELU fusion (`module.layernorm_mlp`), output quantization, quantized operands, and Userbuffers. Rebinding the op fuser's sites routes them through it.
- **RMSNorm.** Under `deepgemm`/`triton`, `transformer_engine_torch.rmsnorm_fwd` is rebound the same way wherever a TE module binds it, which at TE 2.20.2 is the op fuser's `ops.basic.rmsnorm`. The replacement, `_te_rmsnorm_fwd_patched`, computes the same batch-invariant RMSNorm as the patched fused-module normalization; both now share one helper. It returns fp32 `rsigma` of shape `[rows]`, which TE's native `rmsnorm_bwd` consumes, so the backward stays TE's. A quantized output raises.
- **LayerNorm, made batch-invariant rather than rejected.** TE's LayerNorm module subclasses `te.ops.LayerNorm`, which binds `transformer_engine_torch.layernorm_fwd` by name (`ops/basic/layer_norm.py:15`). The fused-module `apply_normalization` used to fall back to TE's native LayerNorm. So under `deepgemm`/`triton`, LayerNorm models were batch-dependent on every path: op fuser, `TENorm` and fused `LayerNormLinear`.
  - `layernorm_fwd` is now rebound the same way as `rmsnorm_fwd`, to `_te_layernorm_fwd_patched`. It computes the mean and variance in fp32 with the batch-invariant `mean_dim` and returns fp32 `mu` and `rsigma` of shape `[rows]` for TE's native `layernorm_bwd`.
  - `apply_normalization` runs the same LayerNorm.
  - Why support rather than reject: a batch-invariant LayerNorm is a small, row-local computation on the same `mean_dim` kernel as RMSNorm. Rejecting LayerNorm under `deepgemm`/`triton` would also break the existing batch-invariant configurations that use it, such as the triton pairwise tests with TE-spec LayerNorm models. The rule is to reject only what cannot be supported.
- **TEFusedResidualRMSNorm.** `TEFusedResidualRMSNorm` (`fused_residual_rmsnorm=True`, op fuser not needed) overrides the patched `te.pytorch.RMSNorm.forward` and runs `te.ops.RMSNorm`. Until now it therefore ran TE's native norm under batch-invariant mode; it is now batch-invariant too. The identity rebind also replaces `cpp_extensions.rmsnorm_fwd` (star-imported from `transformer_engine_torch`). Nothing calls that under `deepgemm`/`triton` batch invariance: `inference_layers._te_rms_norm_kernel` calls it only outside that mode.
- The inference user guide states the supported range below instead of "Keep `use_transformer_engine_op_fuser=False`".

**Supported range, once the merge order below is followed.** The op fuser is batch-invariant under `deepgemm` and `triton`, with RMSNorm or LayerNorm, for BF16 dense layers and MoE experts (#8866), at tensor-parallel size 1 or 2:
- **TP > 2:** the rejection is not on this branch. It comes from #8868 (`fix/bi-tp-reduce-scatter-order`), which rejects the op fuser in batch-invariant mode at TP > 2 because `te.ops.AllReduce`/`ReduceScatter` call NCCL directly. With two ranks, each element is a single add. #8868 is therefore a merge prerequisite, and the guide's "larger sizes are rejected" holds only once it lands.
- **deepgemm:** its dense kernel is batch-invariant only with #8867 (`fix/deepgemm-bi-dense`, X5-N1).
- `te_native` still rejects the op fuser for MoE.
- FP8/FP4 are rejected under `deepgemm`/`triton` (#8865).

## Tests

`tests/unit_tests/transformer/test_te_layers_batch_invariant.py` (1 GPU, H100; already registered for `batch_invariant_kernels.py` in the determinism manifest, so no new manifest entry is needed). The `deepgemm` case skips only in the LTS image (`is_lts_ci_image`) and fails in the dev image without DeepGEMM:
- `test_te_op_fuser_mlp_two_microbatch_training[triton|deepgemm x op-fuser|layernorm-linear x RMSNorm|LayerNorm]`: two training microbatches of different composition, with `[s, 2, h]` input and `gradient_accumulation_fusion`. They go through either a `TEFusedMLP` (norm op, BasicLinear, bias, SwiGLU, BasicLinear) or the MLP of TE's `LayerNormLinear` and `Linear` modules. That exercises forward, backward through the norm, dgrad, and wgrad accumulated into `main_grad` (by the op fuser's `BasicLinear`, which passes `alpha=None`, in the op-fuser cases). The test checks four things:
  - under triton, the target rows' forward bits match across the two compositions;
  - `main_grad` is bit-identical across two repeats;
  - outputs, input gradients and `main_grad` match the run without the mode within tolerance;
  - TE's cuBLASLt GEMM (`tex.generic_gemm`) is made to raise and never runs.

  Bit invariance is asserted only under triton, because the `deepgemm` dense kernel's invariance belongs to #8867, and the test therefore does not depend on that PR. Backward results are compared within tolerance, because batch invariance covers the forward pass and TE's native `rmsnorm_bwd` is kept. Fails on `main` and on #8866. On the old #8865 head it fails with `float(None)`.
- `test_te_op_fuser_mlp_batch_invariant` (triton): 8 target tokens get the same bits alone and in co-batches of 9 to 131 rows. The op fuser's `rmsnorm_fwd` is replaced while the mode is on and restored after. Fails on `main`.
- `test_te_op_fuser_rmsnorm_batch_invariant[ops-rmsnorm|fused-residual-rmsnorm x zero_centered_gamma]`: `te.ops.RMSNorm` and `TEFusedResidualRMSNorm` under the mode equal the batch-invariant RMSNorm bit for bit and keep a token's bits across co-batches. Their backward, through TE's `rmsnorm_bwd` with the replacement's `rsigma`, matches an fp64 reference. Fails on `main`.
- `test_te_layernorm_batch_invariant[ops-layernorm|te-layernorm|layernorm-linear x zero_centered_gamma]`: the op fuser's `te.ops.LayerNorm`, TE's LayerNorm module and a fused `LayerNormLinear` (its returned norm output) under the mode equal the batch-invariant LayerNorm bit for bit and keep a token's bits across co-batches. `layernorm_fwd` is replaced while the mode is on and restored after. The two norm modules' backward, through TE's `layernorm_bwd`, matches an fp64 reference. Fails on `main`.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), the regression tests pass (13 cases). On #8866, the stacked base, all 13 fail: the two training cases because TE's `tex.generic_gemm` ran under batch-invariant mode, and the norm tests because #8866 has no `_te_rmsnorm_fwd_patched` or `_te_layernorm_fwd_patched`, which the tests call. The neighbor tests (`test_te_layers_batch_invariant.py`, `fusions/test_rmsnorm_residual_fusion.py`, `test_te_wrappers.py::TestTEWrappers::test_te_fused_mlp_builder_replays`) pass (96 cases, 1 skipped). The accumulate/alpha/beta and 3D-operand tests belong to #8865; here they run as part of the `test_te_layers_batch_invariant.py` neighbor.

## Follow-up: norm statistics for unflattened input (TE 2.21)

Found by the TE 2.21.0 bump (`fix/te-2.21.0`). TE 2.21 (TransformerEngine PR 3523) no longer flattens `LayerNormLinear`'s input to 2D before `apply_normalization`. The patched norms returned `rsigma.squeeze(-1)` and `mu.squeeze(-1)`, which give `[s, b]` for an `[s, b, h]` input, so `LayerNormLinear`'s backward raised "RSigma has invalid shape". Every norm statistic the branch returns is now flattened with `reshape(-1)` to `[rows]`, which TE 2.20.2 and 2.21 both take. That covers `rsigma` and `mu` from `apply_normalization` (RMSNorm and LayerNorm), `rsigma` from the `rmsnorm_fwd` replacement, and `mu` and `rsigma` from the `layernorm_fwd` replacement. The `apply_normalization` RMSNorm `squeeze` came from `main`, so `main` has the same problem under TE 2.21.

Tests:
- New `test_bik_norm_statistics_are_rows[2d|3d]` runs on CPU, with torch's mean standing in for `mean_dim`. The three replacements must return `mu` and `rsigma` of shape `[rows]`, with the per-row values, for 2D and `[s, b, h]` input. On the CPU venv it passes. Against the previous head (72e16a6be), the 3D case fails with `[3, 2] != [6]`. It fails on `main`, which lacks the replacements.
- `test_te_op_fuser_mlp_two_microbatch_training` (H100) now uses `[s, 2, h]` input. It also runs a non-fused MLP whose `LayerNormLinear` back-propagates through the replaced `apply_normalization`, under RMSNorm and LayerNorm. Under TE 2.20.2, which flattens first, these cases cannot tell `squeeze` from `reshape`. Under TE 2.21 they cover the reported failure. Not yet run on GPU.
