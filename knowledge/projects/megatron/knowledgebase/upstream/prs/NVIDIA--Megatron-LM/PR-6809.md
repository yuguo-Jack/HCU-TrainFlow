# What does this PR do?
<!-- Add a one line overview of what this PR aims to accomplish. -->

Associated with: https://github.com/NVIDIA-NeMo/RL/pull/3920

- Extend image modality to support video modalities in Megatron-Inference. 
  - Modalities
    - Images can be either shipped into the completions endpoint as raw bytes (`{"image": [image1_bytes, image2_bytes]}`), or passed `Megatron(Async)LLM.generate` as preprocessed Tensors (`{"image": {"imgs": ..., "imgs_sizes": ..., "num_tiles": ..., "num_img_embeddings_per_tile": ...}}`).
    - Video can be either shipped into the completions endpoint as raw bytes (`{"video": [video1_bytes, video2_bytes]}`) or a byte-string containing paths to video frame images (`VideoProcessingConfig.frame_manifest_magic + json.dumps({"frame_paths": [...]}).encode("utf-8")`), or passed to `Megatron(Async)LLM.generate` as preprocessed Tensors (`{"video": {"imgs": ..., "imgs_sizes": ..., "num_frames": ... }}`).
    - Pre-processed Tensors can be optionally pre-expanded with multimodal placeholders by RL or the user using the config `media_tokens_preexpanded: bool` in the `multi_modal_data` dictionary input to `Megatron(Async)LLM.generate`.
      - In a nutshell, pre-processed + pre-expanded Tensors = NeMo-RL non-Gym handles the multimodal preprocessing, while bytes = NeMo-RL Gym sends over the raw data for Megatron-Inference to handle the multimodal preprocessing. Having direct engine access in the first (Tensor) case is generally something we want to keep maintaining, not only to support non-Gym in RL but also for users to have direct control over what Tensors go into the encoder/decoder.
    - If you ever see the term "compact" describing prompt tokens it means "prior to expansion" where we have a single token placeholder representing an image or frame or video that will be expanded into many placeholder multimodal tokens for embedding injection before generation. This form is stored and used in some situations where we want to return a non-negative prompt of tokens back to RL and also in multi-turn chat where we re-tokenize and re-expand these compact prompts for chat continuation.
    - These match existing NeMo-RL vLLM API's for multimodal. (But it's honestly a mess of possible inputs depending on what each multimodal dataset prefers...)
  - Just like images, the video embeddings are computed in `_build_vlm_request` before the controller takes over decoding, and the embedding installed in the request can be used for checkpointing, etc. I hope I didn't unintentionally change too much for the trunk of the decoder engine here.
  - Caching / Routing - A cache key is computed here depending on the bytes: `inference_request.py/compute_media_cache_key`
    - Support media affinity via cache key in coordinator routing, which mixes into the affinity score produced by prefix hits for text.
    - Support vision embedding caching to skip the encoder pass on subsequent generations. The cache is LRU-cleared and cleared on suspend.
    - Salt in a media cache key in `compute_block_hashes_batched` to make prefix caching aware of the multimodal data in the prompt as well.
      - Note to self: `DynamicVLMInferenceRequest` saves the media key into the context and this is used later (`_compute_block_hashes`) to salt and recompute the engine-internal KV cache hash, which uses the expanded prompt with ``
  - Inference wrappers have a few more methods that are common to multimodal: `supports_<modality>` for quick-checking what a wrapper can support for a model, `MultimodalPromptConfig` and `resolve_media_token_id` for looking up what image/video placeholders and token IDs should be for a model so that the inference engine can use them as embedding placeholders in `expand_image_tokens` called by `_build_vlm_request`. This is a very _**experimental**_ API for inference wrappers.
    - Added a new inference wrapper for Nemotron Omni: `NemotronOmniInferenceWrapper`.
    - Also updated `VLMInferenceWrapper` for video and LLaVA.
  - `dynamic_res_preprocess` has been updated to support multiple ways of patching frames, and `video_maintain_aspect_ratio=True` is required for parity with RL + vLLM.
  - For video frames, we only sample up to `num_frames` so we can sample first, then convert the sampled frames to PIL / Tensor.

For both images and video, we have vLLM parity: https://wandb.ai/adlr/mllm-rl-dev?nw=nwusercye_nv

**Strict review summary — PR #6809**

**Findings: CRITICAL: 5 · IMPORTANT: 16 · SUGGESTION: 5** (26 inline comments)

Reviewed all 26 changed files against `origin/main` at head `08b5d38`. This is a substantial, generally careful feature — the inline comments explaining *why* a decision was made (prefix-cache disabling for image requests, the `suspend()` cache clear, the tubelet grouping) are genuinely useful and above the norm for this area. The findings below are concentrated in three places: the multi-turn chat path, the temporal branch in `LLaVAModel.forward`, and video preprocessing.

**Most impactful**

**1. Multi-turn multimodal chat is broken (two independent CRITICAL bugs, same code path).**
`_collapse_expanded_media_tokens` is a no-op on the tokens it actually receives: `prompt_token_ids` comes back from the engine containing `-1` pads (the engine deliberately refuses to substitute LLaVA's negative `image_token_index` — `dynamic_engine.py:1514-1528`), while the collapse looks for `-200`. The stitched prefix therefore keeps hundreds of pads, and the next turn has zero media markers. Independently, the collapse condition merges *adjacent distinct* placeholders, which the PR's own `[[11, -200, -200, 12]]` test case demonstrates. Both fail silently or as a spurious embedding-count `ValueError`.

**2. `get_multimodal_prompt_config` publishes `-200` as a real token id.**
`_tokenize_with_media_slots` appends it verbatim into tokens that get hashed, detokenized, and returned to clients; and when the tokenizer *does* define `<image>`, the `token_id != resolved_id` check 400s every multimodal chat request on a correctly-configured LLaVA deployment. The fix is a two-line change: only surface non-negative ids, let `None` mean "resolve from tokenizer".

**3. `num_frames` is silently ignored when `temporal_patch_dim == 1`, where `main` raised `NotImplementedError`.**
Reachable from the new server: `temporal_patch_size` defaults to 1 for non-temporal models, and `add_request` enters the VLM path on `num_frames` alone. Pointing the video endpoint at an image VLM now silently produces per-frame image embeddings instead of an error. Related: `num_frames` without `imgs` degrades to a text-only generation.

**4. `fp8_enabled=False` hardcoded in the temporal CP split while `fp8_recipe` is passed through.**
The two arguments contradict each other; `fp8_recipe` only selects the padding multiple that `fp8_enabled` gates. FP8 vision + CP>1 + video gets unpadded local shards. The constructor already computes the right value at line 353. No test covers CP>1 on this path.

**5. `pixel_shuffle` numerics change for non-square grids affects existing image inference.**
`main`'s non-square branch was a pure reshape; it is now full 2x2 spatial grouping plus a new divisibility assert, and `pixel_shuffle_dynamic_res` delegates to it. The rewritten test confirms both halves. I read this as an intentional fix, so the ask is disclosure + golden values, not reversion — but it needs to be called out as breaking, and the divergence from `examples/mimo/model_providers/radio_encoder.py:131` ("e2e-validated; do not swap to match it") reconciled.

**Also worth attention**

- **Cache safety:** `media_cache_key` hashes media bytes only, but embeddings depend on `num_frames`, resolution, and `temporal_patch_size`. The sole reuse guard is embedding *count*, which collides easily. Mix the preprocessing parameters into the key.
- **Video preprocessing:** the full stream is decoded to PIL before sampling frames (GBs for a 1-minute 720p clip); `reference_hw` from the first video is applied to all videos in the batch (silent aspect distortion); `_video_target_resolution` ignores `spatial_merge_size` and `min_patches` and lacks the `<= max_patches` assert that `dynamic_res_preprocess` has.
- **Untrusted input:** data-URL video bypasses `_MAX_IMAGE_BYTES` entirely (that cap only guards the http branch) — and video is *required* to be a data URL. `_load_frame_sequence_manifest` reads arbitrary local paths from request payloads with no root confinement; opt-in and off by default, but it needs a configured root before anyone enables it.
- **Sync / CUDA-graph:** `.item()` inside `LLaVAModel.forward` (line 1331) plus two in `_build_vlm_request`, all avoidable — the counts are known host-side. `_build_vlm_request` visibly tries to stay sync-free (see its own comment at 1572-1575).
- **Routing:** since `media_cache_key` is always set, *every* multimodal request now bypasses the scored `get_best_data_parallel_rank` for an affinity router whose only load signal is `pending < max_requests`. `_remove_engine` also rebuilds `_hash_table` but not `_media_cache_affinity`.
- **Mandatory unused-identifier check** found three write-only additions: `supports_text/image/video/audio` (declared + assigned, zero readers — they look like the capability gate that would have prevented finding 3), `MultimodalPromptConfig.from_dict` (no callers), `DynamicInferenceRequest.compact_prompt_tokens` (written and merged, never read).

**Process**

- **All five pre-check boxes are unchecked** (unit tests, functional tests, typing, docs, autoformat), and there is **no linked issue** for a new modality. Import order in the two new test files is not isort-clean — run `uv run isort` per CLAUDE.md, then `BASE_REF=main CHECK_ONLY=true bash tools/autoformat.sh`.
- **Test coverage gap:** the new engine tests mock out `_get_cached_vision_embedding` / `_cache_vision_embedding`, so the vision cache — including the `suspend()`-clear that prevents serving stale embeddings across a weight refit — is entirely untested. No functional tests or golden values for the video path.
- **Scope:** the head commit (ZMQ XPUB subscription handshake) is unrelated to video and would land faster as its own PR. It also has a correctness issue of its own: it counts `b"\x01"` frames rather than distinct peers, so a startup reconnect can release the barrier early.

**Risk assessment: High**

Not because the design is wrong — the temporal/tubelet approach and the packed dynamic-res plumbing look sound — but because four of the five CRITICAL findings are silent-wrong-answer paths reachable from the default server configuration, and the new code touches `LLaVAModel.forward` and `pixel_shuffle`, which existing image-only VLM deployments depend on. Findings 1-3 and 5 should block; 4 needs either the config-derived value or an explicit `NotImplementedError`. I would want the vision-cache tests and at least one video functional test with golden values before merge, plus the two compat changes (`pixel_shuffle` numerics, `num_image_tiles` default) documented in the PR description.
