# Fix Muon’s scaling when distributed GTP tensors contain alignment padding

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7236) · state: closed · merged: True

## Original PR description

## Summary

Fix Muon scaling when distributed GTP tensors contain alignment padding. Newton–Schulz still uses the padded tensor for collectives, while the scale factor now uses:

`logical_rows = local_rows × gtp_size - pad_length`

## Background

GTP shards weights along dimension 0. When the row count cannot be divided into equally sized, alignment-compatible shards, GTP appends zero rows before sharding.

For instance, the 16-row per-rank alignment would add paddings as follows:

- `[126, N]` with GTP8 is padded to `[128, N]`, giving each rank 16 rows.
- `[62, N]` with GTP8 is also padded to `[128, N]`; some ranks contain only padding.
- `[124, N]` with TP4 × GTP2 is first split into 31-row TP slices, then each slice is padded to 32 rows.

These zeros are required for storage and communication, but must not affect Muon’s logical shape or update scale.

## Test cases covered

| Layout | Padded shape | Logical shape | Spectral scale |
|---|---:|---:|---:|
| GTP2 | `[8, 4]` | `[6, 4]` | `2.828 → 2.449` |
| TP2 × GTP4 | `[16, 8]` | `[13, 8]` | `4.000 → 3.606` |
| TP4 × GTP2 | `[32, 8]` | `[20, 8]` | `5.657 → 4.472` |

## Light review

Read the diff, `megatron/core/optimizer/emerging_optimizers.py` in context, and the `mcore-testing` skill.

**The fix looks correct.** The `scale_shape` override is threaded only into the final `get_muon_scale_factor` call and deliberately leaves `grad`/`partition_dim` untouched, so the NS collectives keep the physical padded layout they need. I checked the shape math against all four parametrized layouts and it reconstructs the logical shape in each:

- `partition_dim=None` / `1`: `local * gtp - pad` recovers the full logical dim-0, and the `size[partition_dim] *= tp_size` on dim 1 restores the columns.
- `partition_dim=0`: GTP pads each TP dim-0 block independently, so `pad` is per-TP-block and the `*= tp_size` correctly re-multiplies the already-unpadded per-TP row count. Applying the pad subtraction before the TP multiply is the right order here — the reverse would undercount by `tp_size x pad`.

The `grad.shape != p.shape` guard is a good addition: `pad_length` comes off `p` while the row count comes off `grad`, so that invariant is exactly what makes the formula valid, and it is checked rather than assumed.

**Test coverage is solid** and directly targets the regression: the `gtp-only-padding-spans-shards` case (`logical_m=62`, GTP8) covers the section 3.7 Case B layout where padding spills backward past the tail rank, both TP x GTP directions are covered, and the unit tests assert `expected_scale != padded_scale` so they would fail if the override silently stopped applying. The `assert pad_length > 0` guards keep the shapes from quietly drifting into a no-padding configuration that tests nothing.

No GPU kernel is added or changed here — the diff only alters which scalar multiplies the NS output — so the `tests/unit_tests/determinism/kernels/` requirement does not apply.

Two minor comments inline (one stale docstring, one missing test guard); neither affects the fix itself.
