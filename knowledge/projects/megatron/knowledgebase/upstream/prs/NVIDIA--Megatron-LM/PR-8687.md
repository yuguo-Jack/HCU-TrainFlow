# What does this PR do?

Fixes MFSDP v2 silently training on stale weights when a model runs its modules in a different order than it registers them: backward prefetch no longer re-gathers a module whose backward already finished in the current pass.

:warning: For major changes (either in lines of code or in its impact), please make sure to first share a design doc with the team. If you're unsure what's the best way to do so, contact `@NVIDIA/mcore-oncall`.

## Problem

MFSDP v2 prefetches along the static module registration order (`FsdpContext.forward_order` / `backward_order`). If a model registers submodules in a different order than it runs them, the predicted backward order is wrong:

```python
class Model(nn.Module):
    def __init__(self):
        super().__init__()
        self.second = nn.Linear(8, 8, bias=False)  # registered first
        self.first = nn.Linear(8, 8, bias=False)

    def forward(self, x):
        return self.second(torch.relu(self.first(x)))  # executed second
```

The predicted backward order is `[root, first, second]`, but autograd runs `second` and then `first`. When `first` enters backward, it prefetches `second`, whose `post_backward()` has already resharded it. Nothing releases that gather, so `second` keeps its unsharded Parameters and unshard events through `optimizer.step()`. In the next forward, `FsdpParameterGroup.unshard_parameters()` sees the existing events and returns early, so `second` computes with the weights from before the step. No error is raised, and `model.second.weight` stays the unsharded Parameter after backward instead of the sharded DTensor.

On 2 GPUs in fp32 with plain SGD, the loss drifts from an unsharded reference from the second step on (max |Δloss| 2.27e-3 over 5 steps, versus 0 with prefetch disabled). The same happens with sibling FSDP roots, a reused layer (`A -> A -> B`), activation recompute (reentrant and non-reentrant), gradient accumulation, and several forwards followed by several backward passes, whenever the predicted order revisits a module that already finished backward. `LLaVAModel` registers `language_model` before `vision_model` but runs the vision model first, so it may be exposed; I have not run it.

## Fix

`FsdpContext` keeps a weak set of modules whose `post_backward()` ran in the current backward pass, and `_prefetch_parameter_groups()` skips them as backward prefetch targets, in both the next-module and the element-budget paths.

- The set is cleared in `register_post_backward_hook()` when the first root enters backward. Sibling roots in one autograd pass therefore share it, and delayed weight-gradient `post_backward()` calls that run after autograd completes are cleared when the next pass starts.
- A correctly predicted order never targets a finished module, so its prefetches are unchanged. The skipped prefetch was always a wasted all-gather.
- Forward prefetch and demand gathers are unchanged, so skipping a prefetch can never leave a module without its weights.
- Paths that don't use the prefetch hooks (`register_hooks=False`, which MCore's combined 1F1B uses) are unaffected.

Alternatives considered:

- **Release leftover gathers at `context.post_backward()`:** this would also drop valid cross-pass prefetches, such as the backward prefetch from one VPP model chunk to the next.
- **Re-gather in `unshard_parameters()` when weights are stale:** in the case above (fp32, same placements for model and optimizer weights) the stale flag is never set, so it would not trigger. It would also leave the module's unsharded Parameters installed after backward.

This complements #8478 without depending on it. #8478 adds an opt-in `PrefetchOrder.RECORDED` that avoids the misprediction, but the default registration order stays exposed, and this guard applies to any static order. This change touches the `_prefetch_parameter_groups()` loop that #8485 rewrites, so whichever lands second needs a rebase.

## Tests

`tests/unit_tests/distributed/mfsdp_v2/test_execution_order.py::test_backward_prefetch_skips_finished_modules` trains the reverse-registered model above for 3 SGD steps against an unsharded reference, with the default (`next_module`) and the element-budget prefetch policy. After each backward it checks that every parameter is a resharded DTensor, and after each step it checks loss parity.

On `main`, both cases fail with `AssertionError: second.weight is still unsharded after backward.` With that assertion removed, the loss check fails (`Expected 0.041016772389411926 but got 0.04216116666793823`, absolute difference 1.1e-3). Both cases pass with this change.

## Verification

All runs used 2x RTX 6000 Ada in fp32.

- **Numerics probe**, reverse-registered model, 5 SGD steps against an unsharded reference: max |Δloss| goes from 2.27e-3 on `main` to 0.
- **Scenario sweep** of 20 cases, logging every prefetch request:
  - The 12 correctly predicted or no-prefetch cases have identical prefetch logs on `main` and with this change, and are exact against the reference. They cover in-order, element budget, 3 microbatches, 3 forwards then 3 backward passes, sibling roots, VPP-like chunks in separate passes, `A -> A -> B` reuse, and reentrant and non-reentrant recompute.
  - The 8 mispredicted cases drift by 2e-5 to 9.5e-4 on `main` and leave unsharded parameters across the step. With this change they are exact, and their only prefetch difference from `main` is the dropped backward prefetch of the already-finished module.
- **MFSDP v2 unit suite**, 25 files run one at a time: same results on `main` and with this change, apart from the 2 new tests (267 → 269 passed, 0 failed, 110 skipped). `test_overlap.py` and `test_symmetric_memory.py` were not run.
- `tools/autoformat.sh` in check mode passes.
