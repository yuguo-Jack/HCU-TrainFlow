# Add SchedulePolicy.unshard_all_planes_in_backward for MXFP8 recomputation in MFSDP v2

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8432) · state: closed · merged: True

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

 Lets an FsdpModule opt in to gathering all MXFP8 planes in backward, for recomputation inside the module that does not re-enter its forward hooks. Follow-up to #7907, which gathers only the MXFP8 planes each compute phase needs.

 **Problem.** Backward unshards gather only columnwise planes. A recomputation that does not re-enter the owning FsdpModule's `pre_forward` therefore finds no rowwise planes and fails in Transformer Engine (`Requested row-wise usage, but MXFP8Tensor is missing row-scaled FP8 data`), e.g. MTP `eh_proj` under the root with `--recompute-granularity full`.

  **Change.** `SchedulePolicy(unshard_all_planes_in_backward=True)` makes the module's backward unshards, including its prefetch by the preceding module, gather rowwise planes together with columnwise ones. The default is unchanged, and weights of other dtypes are unaffected.

  **Tests** (`test_quantization.py`, zero3, reentrant and non-reentrant):
  - `test_mxfp8_backward_unshard_gathers_rowwise_for_recompute_inside_fsdp_module`: recomputing a root-owned `proj` fails without the opt-in and has both planes ready with it.
  - `test_mxfp8_recompute_inside_fsdp_module_matches_no_recompute`: bit-exact against no recompute with the opt-in.

  **TODO (follow-ups).**
  - The Megatron adapter does not enable the opt-in yet. It should enable it for FsdpModules whose MXFP8 weights are used by recomputation that does not re-enter them, e.g. the root for MTP full recompute (`eh_proj`).
  - Recomputation that re-enters a module still gathers rowwise planes on demand, without overlap. On top of #8478 and #8485, prefetching them needs:
    1. Record recomputation in the execution order, distinguishable from the original forward (e.g. `Phase.RECOMPUTE`).
    2. Prefetch each event for its own phase: recompute events gather rowwise planes and don't end the backward prefetch window.
    3. Advance the order and prefetch from the recomputation's `pre_forward`.
    4. Use `PrefetchOrder.RECORDED` in the adapter, since registration order has no recompute events.

Thanks for the question. This isn't the #7777 case, and no parameter escapes its owner; my description was misleading there.

In #7777, the replay is attached outside the owner, so it runs before the owner's pre-backward and reads sharded params. Here the checkpoint is created inside the owner's forward:
 - MTP: inside the root's forward, via MultiTokenPredictionLayer._checkpointed_forward;
 - --recompute-modules mlp: inside TransformerLayer.forward.

So the recompute runs inside the owner's backward. The weights are gathered, but only the columnwise MXFP8 planes, since BACKWARD skips the rowwise ones after #7907. Recompute is forward compute and needs rowwise, hence "missing row-scaled FP8 data". We only detect recompute when it re-enters the owner's `__call__`, which doesn't happen when the checkpoint sits inside it.

Fixing this in the model code would need one of two things:
 - Make eh_proj and the MLP their own FSDP units. This adds smaller collectives every step.
 - Require every checkpoint to wrap a whole FsdpModule. Selective recompute can't satisfy that, and nothing would catch a violation.

This PR hooks the owned leaves, but the hook gathers the owner's whole group, not per-leaf params. Ownership, sharding, and the per-step collectives without recompute are unchanged. Only a recompute adds one rowwise gather per owner, which recompute needs anyway.

- XiaodaNV · comment · 2026-10-29T09:10:20Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8432#discussion_r4410494075)

File: `megatron/core/distributed/fsdp/src/megatron_fsdp/experimental/module.py` · line 371

Agreed, re-entered recomputation is a prefetch-order problem. I scoped unshard_all_planes_in_backward to recomputation that doesn't re-enter the module (e.g. MTP eh_proj under the root), and left a TODO in pre_forward.

For #8478 to prefetch rowwise planes ahead of a re-entered recomputation, I think it needs:
1. Record recomputation in backward order. `pre_forward` skips recording when recomputing. Record it as a (module, FORWARD) entry next to pre_backward's (module, BACKWARD). A reentrant checkpoint then records `(L, FWD) → (L, BWD)`, and a non-reentrant one `(L, BWD) → (L, FWD)`.
2. Prefetch each successor for its recorded phase. `_prefetch_parameter_groups` unshards successors for `self.phase`, so backward prefetch only gathers columnwise planes. Using the successor entry's phase would gather rowwise planes for `(L, FWD)`.
3. Advance and prefetch from the recomputation's `pre_forward`. It calls `unshard(FORWARD, prefetch=False)` and never consumes the backward order. It should advance the backward cursor and prefetch the next entry, e.g. `(L, BWD)`'s columnwise planes.

With these, the standard contract holds without special cases: `post_forward` releases the rowwise planes right after recomputation, and `pre_backward` only needs columnwise planes, which were already prefetched.
