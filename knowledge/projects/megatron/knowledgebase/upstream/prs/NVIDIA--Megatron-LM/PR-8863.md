# [Inference][Hybrid] Give GPTModel and HybridModel one owner for RoPE inputs; apply RoPE in hybrids under flash_decode and FlashInfer fused RoPE

# What does this PR do?

Makes `HybridModel` with RoPE get every RoPE input `GPTModel` gets, from one helper both models share: the cos/sin tables of static `flash_decode`, and the cos/sin cache of FlashInfer's fused RoPE in dynamic inference. It also rejects `flash_decode` with a dynamic context for every model, with a clear message when the context is built.

**Stacked on #8862 (`fix/flashinfer-fused-rope-shapes`)**, merged in as `4c00782e3`, because this PR routes RoPE hybrids onto FlashInfer's fused RoPE. Review `104459a2f` and `90be2f50f`; retarget to `main` once #8862 is merged.

**Bug.** In inference, attention applies RoPE from precomputed tables instead of `rotary_pos_emb` in two cases: under `flash_decode` (`rotary_pos_cos`/`rotary_pos_sin`, in the static prefill and inside the flash-decode kernel) and when the dynamic context uses FlashInfer's fused RoPE (`rotary_pos_cos_sin`). `GPTModel` built these tables. `HybridModel` built only `rotary_pos_emb`, and `HybridStack.forward` had no parameters for the tables.
- **Static `flash_decode` (silent).** A hybrid with `position_embedding_type='rope'` and attention layers ran static prefill and decode with no positional encoding at all. On H100 its prefill applied RoPE 0 times, and its last-token logits differed from `flash_decode=False` by rel 0.01.
- **FlashInfer fused RoPE (silent).** With `use_flashinfer_fused_rope=True`, or `None` with FlashInfer installed, attention dropped `rotary_pos_emb` and got no cache, so every dynamic prefill and decode step of a RoPE hybrid ran without RoPE.
- **`flash_decode` under a dynamic context (unclear crash).** Flash decoding runs only under static batching. `GPTModel` stopped with "Flash decode is only applicable to static batching." when it built RoPE tables. Every other model (RoPE hybrids, NoPE hybrids such as Nemotron-H, learned-absolute GPTs, MLA) instead failed a bare, message-less `assert inference_context.is_static_batching()` in its first attention layer. The default `StaticInferenceEngine` runs a dynamic context underneath, so this is what those models got there.
- **YaRN with `flash_decode`.** `GPTModel` raises `NotImplementedError` (the tables carry no YaRN scaling). `HybridModel` ran it without RoPE.

**Fix.**
- `LanguageModule._rotary_pos_emb_inputs` owns RoPE-input preparation. It is `GPTModel`'s former RoPE block (RoPE, YaRN and multimodal RoPE; the flash-decode tables; FlashInfer's cos/sin cache) and returns `(rotary_pos_emb, rotary_pos_cos, rotary_pos_sin, rotary_pos_cos_sin)`. `GPTModel` and `HybridModel` both call it. `GPTModel`'s behaviour is unchanged: same cache keys, tables, YaRN and multimodal-RoPE rejections, and MTP assert.
- The tables are computed only on a cache miss. `dict.setdefault`, copied from GPT, used to recompute them on every forward and discard them.
- The tables are built only when the decoder's attention takes them. MLA layers apply their own RoPE, so a hybrid whose decoder uses MLA gets `rotary_pos_emb` as before, even if its MTP head does not use MLA.
- `HybridStack.forward` takes `rotary_pos_cos`, `rotary_pos_sin` and `rotary_pos_cos_sin`, as `TransformerBlock.forward` does, and threads them to attention layers, including those inside `HyperConnectionHybridLayer` (both paths) and the attention half of a `ShortcutMoEBlock` in inference.
- `DynamicInferenceContext` raises `ValueError("Flash decode is only applicable to static batching; ...")` when built with `model_config.flash_decode`, for every model. The check moves out of the RoPE helper, where only RoPE models reached it. A model with `flash_decode` under the default `StaticInferenceEngine` now falls back to the legacy static engine, which runs flash decoding, instead of crashing at the first prefill.
- One more behaviour change, not a fix: `HybridModel` now passes the packed sequence's runtime CP group to its rotary embedding, as `GPTModel` does. This makes a difference only when `local_cp_size` is set, and then it matches the group attention uses.

**Tests.**
- `tests/unit_tests/models/test_hybrid_model.py::TestHybridModelFlashDecodeRope` (1 GPU, TE, flash-attn 2). The model has pattern `*-`, RoPE, fp16 and init std 0.1, so attention, and therefore RoPE, moves the logits. It is built with `flash_decode` in its config, since every hybrid layer gets its own copy of the config.
  - `test_static_generation_matches_without_flash_decode`: a static prefill and one decode step. RoPE is applied through the cos/sin path in the prefill, and the decode kernel gets the RoPE tables. The logits of both steps match a `flash_decode=False` model with the same weights within a tenth of the effect of dropping RoPE, which the test measures with the same weights and `position_embedding_type='none'`. A missing RoPE, or one at the wrong position, fails it. On `main` RoPE is applied 0 times. flash-attn is in the CI image, so the test fails rather than skips without it.
  - `test_dynamic_context_is_rejected[rope|none]`: building a `DynamicInferenceContext` for a RoPE hybrid and a NoPE hybrid with `flash_decode` raises the `ValueError`. On `main` construction succeeds, and the first attention layer fails a bare assert.
  - `test_yarn_is_rejected`: YaRN with `flash_decode` raises `NotImplementedError`, as for GPT.
- `tests/unit_tests/inference/contexts/test_dynamic_context.py::test_flash_decode_is_rejected` (CPU): the context rejects `flash_decode` for a plain `TransformerConfig`, with no model at all. On `main` it fails only on an unrelated setup error (see the results below).
- `tests/unit_tests/inference/test_flashinfer_fused_rope_models.py::TestHybridModelFusedRope::test_fused_rope_matches_unfused[rope]` (1 GPU, TE, flash-attn, FlashInfer): a hybrid runs a prefill of two requests and a decode step with FlashInfer fused RoPE off and on. The queries and keys reaching the attention kernel must agree within 2% (bf16 rounding of the two RoPE paths is about 0.3%; a missing rotation moves them by tens of percent), and fused RoPE must run once per step. On `main` it runs 0 times. The stacked #8864 adds YaRN to this test.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), the regression tests pass (6 cases) and fail on this PR's base, #8862 (6 of 6 cases). There, the flash-decode prefill applies no RoPE, the dynamic-context and YaRN rejections do not raise, and fused RoPE runs 0 times in two steps. `test_flash_decode_is_rejected` fails there only on an unrelated setup error: with nothing rejecting `flash_decode` first, the context constructor stops on "expert model parallel group is not initialized", so this case does not show the missing rejection. The step 3 GPU repro of this finding (R11-F5) showed it on `main` on H100: a HybridModel with `flash_decode` under a dynamic context failed a bare assert in `attention.py` instead of a clear rejection, and its static prefill applied RoPE 0 times. The neighbor tests (`test_hybrid_model.py::TestHybridModel` and `::TestHybridModelWithYarn`, `test_gpt_model.py`) pass (60 cases; 1 MXFP8 case skips, as it needs Blackwell).

## Interaction with other open PRs

Three PRs fix FlashInfer fused RoPE in dynamic inference, each at a different layer:
- **#8862 (`fix/flashinfer-fused-rope-shapes`, this PR's base)**, the context: whatever cos/sin cache a model passes, `apply_fused_qk_rotary_emb` rotates every head shape exactly.
- **#8863 (this PR, `fix/hybrid-flash-decode-rope`)**, the models: one helper owns RoPE inputs, so RoPE hybrids build the cache and pass it through `HybridStack`.
- **#8864 (`fix/fused-rope-model-embedding`, stacked on this PR)**, attention: fused RoPE runs only when the model passes a cache; the helper builds it for RoPE and YaRN; no-RoPE layers get none; multimodal RoPE runs unfused. GPT YaRN and multimodal RoPE, HybridModel YaRN and `no_rope_freq` layers stay wrong with fused RoPE until then.

The order is #8862, then this PR, then #8864, and stacking enforces it. This PR turns fused RoPE on for RoPE hybrids, and without #8862 FlashInfer's kernel faults on some head dims (e.g. 72) and silently mis-rotates others (e.g. 80). This branch therefore contains #8862 (merge commit `4c00782e3`): review only `104459a2f` and `90be2f50f`, and retarget to `main` once #8862 is merged. #8864 is stacked on this branch the same way. After the retarget, the coverage gate flags this PR's `dynamic_context.py` change, a constructor check with no numerics, against #8862's manifest entry for that file. It needs the `determinism-exempt` label.

Others:
- #8878 (static `flash_decode` window and output gate) changes the attention side of the same path. The two compose: the decode kernel gets the hybrid's cos/sin from this PR and applies the window and gate from that one. With this PR, every `flash_decode` model under `StaticInferenceEngine` takes the legacy static engine that #8878 fixes.
- n12 ([#8709](https://github.com/NVIDIA/Megatron-LM/pull/8709)) changes `gpt_model.py`, `hybrid_model.py`, `hybrid_block.py` and `hybrid_hyper_connection.py` elsewhere. It merges cleanly, as does every open fix branch that merges with `main`.
