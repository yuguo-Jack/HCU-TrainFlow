# Inference: keep one copy of FlashInfer MXFP8 expert weights by refitting into the routed layout

# What does this PR do?
The FlashInfer routed MXFP8 MoE path kept two resident copies of every expert weight: the canonical MCore `MXFP8Tensor` per expert (the refit destination) and the shuffled Major-K stack the TRT-LLM kernel reads, rebuilt from the canonical copy after each refit. This doubled MXFP8 expert memory. This PR makes refit write directly into the routed layout, so only the routed copy stays resident.

- `MXFP8Tensor` gets an optional `writeback` field. When it is set, `quantize_` (and therefore `copy_`) hands the logical value to it instead of writing `data` / `scale`.
- New `attach_routed_mxfp8_writeback(weight, routed, expert)` in `flashinfer_mxfp8.py`. It frees the expert's canonical storage (replaced by one-element broadcast placeholders that keep the shapes) and installs a writeback that quantizes with the canonical Triton kernel (`MXFP8Tensor.from_bf16`) and repacks that one expert into its routed slot with the existing `prepare_routed_mxfp8_weights(..., out=slot)`. Attaching twice raises.
- `InferenceGroupedMLP._build_concatenated_mxfp8_weights` attaches the writeback to every local expert right after building the routed stack.
- Refit itself is unchanged: `MXFP8ReshardTransform.persistent_buffers` holds these same tensor objects, so its existing `buf.copy_(...)` now lands in the routed layout. The routed bytes are the same as the old quantize-then-repack path, and buffer addresses do not change, so captured CUDA graphs stay valid.
- `refresh_flashinfer_mxfp8_weights` no longer repacks. It still returns True so refit synchronizes before graph replay.

After the FlashInfer build, `weight{i}.data` / `.scale` on routed MXFP8 experts no longer hold the weight values. Nothing in Megatron reads them at that point.

**Results** (Nemotron-3-Ultra, 2 nodes, TP=4, EP=8, selective MXFP8 recipe, 128 requests × 512 tokens, CUDA graphs)
- Peak allocated memory, FlashInfer MXFP8: 189.9 GB before, 131.9 GB after (torch MXFP8 baseline: ~133 GB).
- All routed weight builds are byte-identical to the old stack-then-repack build (on every rank and MoE layer).
- Generations: 128/128 identical to the pre-fix run.

- kahyunnam · comment · 2026-11-02T21:03:09Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8560#issuecomment-6588386459)

Status: design ask, no code change yet.

What we found: this PR hand-packs expert weights into the layout FlashInfer's TRT-LLM block-scale MXFP8 MoE reads because FlashInfer offers no API for it. `TrtllmFp8BlockConfig.prepare_weights` only allocates fresh stacks from BF16 (no `out=`, no per-expert subset, no pre-quantized input), the W1/W2 permute helpers are private, and the public `shuffle_matrix_a` reproduces the W2 payload but not the gated W1 payload, which also needs an unpublished gate/up reorder. On an SM100 Blackwell GPU, refitting one expert into its slot of an existing prepared stack with the same per-expert steps gives tensors byte-identical to a full re-prepare, with unchanged data pointers, so an in-place refit API is a thin wrapper over existing FlashInfer code and needs no kernel or layout change.

Next steps:
1. FlashInfer maintainers: add a public in-place per-expert refit for the TRT-LLM FP8 block view (MXFP8 and DeepSeek FP8) that writes into existing storage, with byte-equality and CUDA-graph tests.
2. FlashInfer maintainers: add a repack entry taking already-quantized E4M3 payloads plus UE8M0 scales that applies only the permutation and interleave.
3. FlashInfer maintainers: document the MXFP8 layout contract (W1 reorder plus MajorK shuffle, W2 shuffle, scale interleave, 128-divisibility, per-expert slice independence, which activation constants may be refilled in place).
4. Open question for the FlashInfer maintainers: should the refit live on `TrtllmFp8BlockConfig` or on `MoEWeightPack` as a generic per-backend `refit`?

Once 1 or 2 ships, `prepare_routed_mxfp8_weights` can drop its hand packing; we will link the FlashInfer PR here.
