# Use the trained model's process groups in the RL training path

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8745) · state: closed · merged: False

## Original PR description

**Why.** The RL training path reads the global parallel grid in several places:
- the rollout split across data-parallel ranks;
- sequence packing: the gather, bin distribution, CP alignment and statistics;
- microbatch and throughput accounting;
- the logprobs schedule;
- the NCCL warmup;
- the last-stage check in `train_rl.py`.

Each of these reads assumes the trained model sits on the global grid. It need not: RL can run a separate inference model on its own grid in the same processes, and `pretrain()` can be given the trained model's collection. The `train_rl.py` stage check can also disagree with `get_logprobs`, which already uses the model's pipeline group.

**What.**
- `prepare_data_for_update` takes `dp_gtp_remat`, `cp` and `pp` from the trained model's collection. It passes them to packing, the microbatch calculator and the logprobs schedule, which also gets a `P2PCommunicator` over that pipeline group.
- `PackingContext` records the data-parallel group its bins were distributed over. Efficiency, the packing log and the throughput metrics read it.
- The logging callback, the communicator warmup and `train_rl.py` use the trained model's groups.

**Tests.** In `tests/unit_tests/rl/`, the global data-parallel group spans every rank while the trained model's groups are rank pairs: its data-parallel group in `test_prepare_data_for_update_uses_training_model_groups`, and its data-parallel and context-parallel groups in `test_pack_all_trajectories_uses_given_process_groups`. The first of these and `test_eager_train_comm_warmup_uses_given_groups` also make every `parallel_state` accessor raise. The callbacks and the other packing helpers are tested with explicit groups. On 4 GPUs against main: `test_rl_utils.py`: 176 passed here vs 173 on main, and 3 new tests pass; `test_sequence_packing_utils.py`: 33 passed here vs 32 on main, and 1 new test passes; `test_rl_callbacks.py` passes 10 tests and `tests/unit_tests/training/test_initialization_lifecycle.py` passes 112 on both sides. No test fails on either side. On the code before the sync with main, on 4 CPU ranks with Gloo, with `tensorboard` and other modules the CPU environment lacks stubbed out, the three files in `tests/unit_tests/rl/` give the same per-test results as the earlier version of this PR stacked on #8037. Their failures and errors come from the CPU environment, mostly the missing CUDA, and occur on both. In the integration run, with the other process-group changes from #6307 applied, `test_rl_utils.py`, `test_sequence_packing_utils.py` and `test_rl_callbacks.py` pass (176, 33 and 10 tests on 4 GPUs) and show no regressions against main. The `forbid_global_grid` helper in `test_rl_utils.py` is a local copy of #8017's `forbid_global_process_groups` and can switch to it once #8017 lands.

**Compatibility.** On the standard grid the groups are identical.
- The `megatron/rl` packing helpers (`pack_all_trajectories`, `distribute_packed_bins`, `update_microbatch_calculator`, `bin_batch_size`, `get_sequence_packing_tensorboard_metrics`) gain required group arguments, `get_inference_interface` gains a required `training_model`, and `PackingContext` gains a required `dp_group` field. Every caller in this repository is updated, and `megatron.rl` is not part of the `megatron-core` package.
- `dp_gtp_remat`, `cp` and `pp` are read from the collection directly, as `get_logprobs` already does for `cp` and `pp`. Collections from `pretrain()` and `use_mpu_process_groups()` set all three. A hand-built collection without them fails with `AttributeError` rather than `ValueError`. Elsewhere the repo falls back with `dp_gtp_remat or dp`.
- The warmup's log labels are now collection field names (`dp_gtp_remat`, ...) instead of `dp`, `dp_cp`, ....
