# [dev] Mask padding before HybridEP dispatch under an expert-rank budget

# What does this PR do?

Extends the HybridEP padding mask from NVIDIA/Megatron-LM#5542 to runs with a static expert-rank budget (`--moe-expert-rank-capacity-factor`).

#5542 made `TopKRouter.routing()` zero the probabilities and clear the routing-map entries of padding rows before dispatch. It did this only for dropless HybridEP: the condition requires both `moe_expert_capacity_factor is None` and `moe_expert_rank_capacity_factor is None`, and its test lists `("flex", "hybridep", None, 1.0)` among the configurations that keep padding routes. HybridEP with an expert-rank budget consumes the same sparse routing map, so the second condition is not needed. This PR removes it. HybridEP now masks padding whenever per-expert capacity (`--moe-expert-capacity-factor`) is off. Other dispatchers, and HybridEP with per-expert capacity, keep their fixed-route behavior, as in #5542.

Why it matters: with a rank budget, `_HybridEPManager` gives HybridEP a static receive budget of `local rows × topk × factor` (rounded up for alignment), and padding rows are part of the local rows. Padding rows that keep their routes are dispatched like real tokens. They take receive-buffer and expert-input rows and count against the receiving rank's budget, leaving less headroom for load imbalance among real tokens. Padding rows can also route alike: with hash routing, for example, all padding rows with the same pad token id go to the same experts. When a rank receives more rows than the budget, HybridEP drops the excess in that attempt and sets its over-budget flag. In the Megatron training loop, `PagedStashRunner` wraps the step whenever `moe_expert_rank_capacity_factor` is set. It all-reduces the flag after forward-backward. If any rank was over budget, it discards the attempt (zeroes the gradients) and reruns the step once in dropless mode: the capacity factor is cleared, paged stash is off, and HybridEP sizes dispatch with a host sync. A captured TE whole-MoE CUDA graph cannot fall back, so in that case the runner raises an error.

In the Megatron training loop, routed padding therefore never silently drops tokens. It costs throughput: steps with padding carry extra dispatch and expert rows, and a step in which a rank goes over budget pays for a second, dropless forward-backward. With a captured TE whole-MoE graph, such a step stops the run instead. With this PR padding takes none of the budget. Routing of real tokens does not change: the new test checks that probabilities and routing maps equal, exactly, the routing computed without a rank budget. We have not measured how often the rerun triggers with and without this change.

We found this while benchmarking dynamic context parallelism with CUDA graphs (NVIDIA/Megatron-LM#6479). There, packed sequences are padded up to a fixed per-rank capacity, so every pack whose sequences do not fill that capacity carries padding rows.

## Tests

In `tests/unit_tests/transformer/moe/test_routers.py`:

- New `test_hybridep_rank_capacity_masks_padding` covers eager and CUDA-graph-captured routing, with and without hash routing, replayed with 2, 5, 0 and 2 valid tokens. It checks three things:
  - padding rows get no routes;
  - every valid token gets its top-k routes;
  - probabilities and routing maps equal, exactly, the routing computed without a rank budget.
- `test_hybridep_dense_routing_masks_padding` now also runs with a rank capacity factor.
- The `("flex", "hybridep", None, 1.0)` case leaves `test_padding_mask_preserves_routes_outside_dropless_hybridep`, because that configuration now masks padding.

On 8×H100 (torch 2.11 container, TE 2.19), `test_routers.py` gives 72 passed, 2 skipped and 2 failed. The two failures, `test_router_gating_linear[router_dtype1]` and `test_router_gating_linear_bias[router_dtype1]`, fail the same way on dev c3010d6d5.
