## What does this PR do?

I'm aware of #8485 and will rebase this PR on top of it after it lands.

When MFSDP modules execute in a different order from their registration, construction-order prefetch can gather the wrong next layer. Choose `fully_shard_context(FsdpContext(prefetch_order=PrefetchOrder.RECORDED))` to record the first ordinary eager forward/backward pass and use those orders for subsequent prefetching.

```python
with fully_shard_context(FsdpContext(prefetch_order=PrefetchOrder.RECORDED)) as context:
    fully_shard(model, mesh=mesh, placements=placements)

loss = model(inputs).square().mean()
loss.backward()  # context.post_backward() ends recording.
```

Record forward entry in `pre_forward()` and backward entry in `pre_backward()`. Only modules participating in backward enter its trace. Checkpoint recomputation does not add another forward occurrence. Repeated calls to a shared layer are skipped while it is already in `BACKWARD` and its weights remain available. Recording and replay use the same existing guard, so backward calls `A → A → B` record `A → B` in this case.

`PrefetchOrder.REGISTRATION` remains the default; `PrefetchOrder.RECORDED` selects the observed order. This reuses the existing `ExecutionOrder` objects and prefetch budgets; parameters are gathered on demand while recording. Discard the context if recording fails. Subsequent passes must repeat the recorded call order consistently across data-parallel peers.

The final autograd callback ends recording in `context.post_backward()`, alongside its existing weight cleanup and gradient synchronization.

LGTM with couple of nits.
There is a bug originating in `main` and not this PR that needs a follow-up PR though.

with the default `REGISTRATION` order, a model that registers its modules in a different order than it runs them can silently train on stale weights.

Example: `second` is registered before `first` but runs after it. In backward, `second` finishes first. Then `first` runs and, following the registration order, prefetches `second` again. Nothing releases that gather, so it is still there after `optimizer.step()`. In the next forward, `second` looks already gathered, skips the weight refresh, and computes with the pre-step weights.
