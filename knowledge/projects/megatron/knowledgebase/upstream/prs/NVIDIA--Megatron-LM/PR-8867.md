# [Core][BatchInvariant] Run DeepGEMM's own kernel for batch-invariant dense GEMMs and read weights in place

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8867) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes the `deepgemm` batch-invariant backend run DeepGEMM's fixed-K-order GEMM kernel again, instead of the cuBLASLt heuristic it has silently run since #7725. It also hands DeepGEMM linear weights in place, instead of copying the whole weight on every GEMM and every CUDA-graph replay.

**Bug 1: the backend runs cuBLASLt.** At the pinned DeepGEMM (`ea2b7805`), `bf16_gemm_nt` (and `bf16_gemm_nn`, which calls it) sends the GEMM to cuBLASLt unless `deep_gemm.use_deterministic_algorithms(True)` was called (`csrc/apis/gemm.hpp:498-500`). The cuBLASLt call takes the top-1 heuristic algorithm, allows split-K reductions and uses DeepGEMM's own 16 MiB workspace. Megatron never calls the switch. The switch and the cuBLASLt dispatch both arrived in DeepGEMM's 26/09 release (`66081d4`), and #7725 moved the pin past it. Before that, `bf16_gemm_nt` always ran DeepGEMM's kernel, which the backend was designed around. As a result:
- every dense bf16 GEMM under `batch_invariant_backend="deepgemm"` (training, TE-implementation inference and inference-optimized inference) runs cuBLASLt, which picks split-K per row count;
- on H100, the profiled kernel for `F.linear([64, 4096] x [4096, 4096])` is `nvjet_sm90_tst_64x32_64x16_1x2_h_bz_NNT`, and row 0 of that GEMM changes bits between M=1 and M=16.

**Bug 2: every linear copies its weight.** `F.linear` and `x @ w.t()` hand `aten::mm` the view `b = w.t()`, whose strides are `(1, K)`. `_mm_deepgemm` kept an operand only if `stride(0)` was 16-byte aligned. For `w.t()` that is the inner stride, which is 1, so every call allocated a padded row-major `[K, N]` buffer and copied the weight into it. Under CUDA graphs the copy kernel replays every step. `BatchInvariantTEGemmFn` also made the transposed weight contiguous under `deepgemm`. DeepGEMM needs neither copy: it reads an operand along its unit-stride dimension, so `w.t()` is read as the K-major `w`. On H100 at M=64, `F.linear` took 142 µs for a 4096 x 4096 weight (32 MiB copied per call) and 488 µs for 14336 x 4096. The GEMM in those calls took 11 µs and 46 µs, but that GEMM was cuBLASLt's `nvjet` kernel (Bug 1), not the DeepGEMM kernel this PR switches to, so these numbers show the cost of the copy, not the end-to-end speed-up. The DeepGEMM kernel's time at these shapes, against cuBLASLt, has not been measured.

## Fix

- Under the `deepgemm` backend, `enable_batch_invariant_mode` turns DeepGEMM's deterministic algorithms on (after its checks, right before the mode is marked on), and `disable_batch_invariant_mode` turns them back off. At `ea2b7805` only DeepGEMM's dense bf16 GEMMs, einsum and the fused mega kernels read the switch (`gemm.hpp:498`, `einsum.hpp:72,95`, `mega_mhc.hpp:16`, `heuristics/mega_gate.hpp:206`); the M- and K-grouped GEMMs that `triton` and the inference MoE experts use do not. So `te_native` and `triton` leave the switch alone, and only `deepgemm` changes it for other DeepGEMM users in the process. The switch is process-global and DeepGEMM binds only its setter, so the mode records that it set it, and disabling the mode turns it off even if other code had turned it on before; both docstrings say so. DeepGEMM releases without the switch never dispatch to cuBLASLt, so nothing changes for them.
- `_mm_deepgemm` applies DeepGEMM's operand rules: one unit stride, and a 16-byte aligned outer stride and base pointer. It also requires the outer stride to cover the inner extent, so expanded (stride-0) and overlapping views are copied rather than handed to the TMA descriptor. An operand that meets them is passed as is, so a linear's weight is read K-major in place whenever K is a multiple of 8. Any other operand is copied into the same layout with a padded outer stride, so the copy stays K-major too. A column-major A, such as `grad_output.t()` in aten's weight gradient, therefore reaches DeepGEMM MN-major, which DeepGEMM supports for bf16 GEMMs on SM90 and SM100. The base-pointer check is new and also covers sliced activations, which DeepGEMM would otherwise reject.
- `_mm_deepgemm` compiles only N into DeepGEMM's JIT kernel (`compiled_dims="n"`; the binding default `"nk"` also compiles K). The token count is K in weight-gradient GEMMs (`grad.t() @ x`, TE's `NT` layout) and M in forward and data-gradient GEMMs, so with `"nk"` every new training token count would trigger a multi-second nvcc build on every rank. N is fixed for a given linear in all three. K is now a runtime loop bound in inference too; its effect on kernel time has not been measured.
- `BatchInvariantTEGemmFn` passes the transposed weight view under `deepgemm`, as it already does under `triton`. TE GEMMs (training) and `F.linear`/`x @ w.t()` (inference) therefore give DeepGEMM the same K-major weight and run the same kernel variant.

No host syncs and no new allocations: the hot path loses a weight-sized allocation and copy per GEMM.

## Tests

New cases in `tests/unit_tests/inference/test_batch_invariant_deepgemm_stride.py`, the dense DeepGEMM test registered for `batch_invariant_kernels.py` in the determinism manifest (whose entry now describes these checks). 1 GPU, Hopper or Blackwell, DeepGEMM with bf16 bindings:
- `test_dense_deepgemm_runs_deepgemm_kernel`: profiles `F.linear` under the backend and requires DeepGEMM's `sm90_bf16_gemm_impl`/`sm100_bf16_gemm_impl` kernel. It also checks that the mode turns the switch on and back off. This fails on a future DeepGEMM bump that reroutes the call.
- `test_dense_deepgemm_rows_are_invariant_across_batch_size`: row 0 of `F.linear` has the same bits at M = 1, 16, 256 and 4096, for (K, N) = (4096, 4096) and (16384, 64), and matches an fp64 reference.
- `test_transposed_weight_reaches_deepgemm_uncopied`: `F.linear`, `torch.matmul(x, w.t())` and the TE `TN` GEMM hand DeepGEMM the weight's own storage, K-major, for (N, K) = (4096, 4096). For K = 60 they hand it a padded K-major copy. Outputs match an fp64 reference.
- `test_weight_gradient_reads_column_major_grad`: aten's weight gradient `torch.mm(g.t(), x)` hands DeepGEMM `g` itself, MN-major (strides `(1, O)`), for (O, T, I) = (4096, 37, 1024), and a padded column-major copy (strides `(1, 64)`) for O = 60, T = 64. K is the token count, with a tail that is not a multiple of 64, and the output matches an fp64 reference. It also checks that K is not compiled into the kernel.
- `test_other_backends_leave_deepgemm_switch_alone[te_native|triton]`: enabling and disabling those backends never calls DeepGEMM's switch.
- `test_expanded_operand_is_copied`: `torch.mm(x, v.expand(128, 32))` hands DeepGEMM a copy with strides `(1, 128)`, not the stride-0 view, and matches an fp64 reference.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), the regression tests pass (10 cases) and fail on `main` (7 of 10 cases). On `main`, the kernel test and the aliasing test fail, and the row test fails at 4096 x 4096 (row 0 differs at M=16) and passes at 16384 x 64. The weight-gradient and expanded-operand tests also fail on `main`, which copies both operands row-major and compiles K into the kernel; the switch-scope test passes on `main`, which never touches the switch. The neighbor tests pass (58 cases, 1 skipped): the existing stride-boundary test (its DeepGEMM witness now forwards keyword arguments; row-major weights are padded exactly as before), `test_te_layers_batch_invariant.py`, and `test_batch_invariant_pairwise.py::test_dense_dynamic_feature_batch_invariance`.
