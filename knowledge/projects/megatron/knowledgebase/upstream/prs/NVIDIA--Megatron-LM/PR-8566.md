# [Inference][MoE] Apply the GLU and probs-on-input options in inference-optimized MoE experts

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8566) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes the inference-optimized MoE experts (`InferenceGroupedMLP`, torch and vLLM grouped-GEMM backends) apply `activation_func_clamp_value`, `glu_linear_offset`, `moe_mlp_glu_interleave_size` and `moe_apply_probs_on_input` the way training does. Before this change, the experts dropped these options without an error.

## The bug

`InferenceGroupedMLP._resolve_mcore_activation_type` maps every gated-SiLU configuration to plain SwiGLU. The `torch` and `vllm` (default) backends then receive only the activation type and the tanh clamp scale. `TEGroupedMLP`, the training path of the same module, applies four options that inference never read:

- `activation_func_clamp_value`: caps the gate at `v` and clamps the linear half to `[-v, v]`.
- `glu_linear_offset`: `silu(gate) * (linear + offset)`.
- `moe_mlp_glu_interleave_size`: FC1 rows alternate gate and linear blocks.
- `moe_apply_probs_on_input`: the expert input is scaled by the routing probability, and the output is left unweighted.

Config validation rejected these options only under `inference_moe_nvfp4_recipe`. A model trained with any of them and served with `transformer_impl='inference_optimized'` therefore produced wrong outputs. This affected BF16 and MXFP8 weights, and batch-invariant mode too. On H100 in the CI image, the expert outputs of `main` differ from training by a normwise relative error of 7.1 (clamp 0.5), 0.64 (offset 1.0) and 1.4 (interleave 32). A model-level matrix showed 0.8–1.7 nats of mean log-prob error.

## Root cause and fix

The inference kernels implemented only plain SwiGLU, and nothing passed the options to them.

- **GLU options** (`activations.py`, `batch_invariant.py`): a frozen `GLUOptions` value holds the clamp, the linear offset and the interleave size. Two shared Triton helpers do the work. `glu_columns` finds the gate and linear columns of an output column in either FC1 layout. `glu_inputs` applies the clamp and the offset to the FP32 inputs. All four SwiGLU kernels use them: `padded_swiglu` (torch backend and MXFP8), `bounded_silu_mul` (vLLM), and the batch-invariant `swiglu_with_probs` and `weighted_silu_mul_bounded`.
  - The options are constexpr flags, so the default configuration computes exactly what it did before.
  - Like training's `torch.clamp`, the clamp keeps NaN inputs NaN.
  - Handling the interleave in the kernel keeps the per-expert parameters as views of the stacked weights, which refit relies on.
- **`moe_apply_probs_on_input`**: as in training, each routed input row is multiplied by its probability and rounded to BF16, and the expert output is not weighted again. The torch backend does this in the permute kernels (`permute_tokens` and the fused MXFP8 `permute_and_quantize_mxfp8`), which then write unit probabilities, so the activation and unpermute code is unchanged. The vLLM backend scales the A rows in its FC1 GEMM (`MUL_ROUTED_WEIGHT_ON_INPUT`). It then skips the probability in FC2's GEMM epilogue (where main applies it outside batch-invariant mode) and, in batch-invariant mode, in the activation (`weighted_silu_mul_bounded` / `squared_relu_with_probs` accept `None`).
- **Plumbing** (`fused_moe.py`, `vllm_fused_moe.py`, `experts.py`): `InferenceGroupedMLP` builds `GLUOptions` from the config for gated units, which is the only case where training applies them. It passes the options and `moe_apply_probs_on_input` to `mcore_fused_moe` and `vllm_fused_moe`.
- **Validation** (`transformer_config.py`):
  - The FlashInfer MoE kernels apply routing probabilities only to the expert output. `moe_apply_probs_on_input` with `inference_grouped_gemm_backend='flashinfer'` is now rejected with a message that points to `torch`/`vllm`. The GLU options were already excluded on FlashInfer: gated units reach it only under the NVFP4 recipe, which rejects them.
  - The Transformer Engine GLU activations have no linear offset, so two training paths silently trained without `glu_linear_offset` while inference now applies it. Those paths are `use_te_activation_func` and the op-fuser `ScaledSwiGLU` (`use_transformer_engine_op_fuser` with SwiGLU experts). Both combinations are now rejected, so training and inference cannot disagree on the offset.

No new allocation, host sync or per-step setup, so the change is CUDA-graph safe.

In batch-invariant mode, the clamp keeps the inference kernels bit-identical to training's fused clamped weighted-SwiGLU (tested). For `glu_linear_offset` and the interleave, training always uses the unfused eager GLU. Its BF16 roundings are not reproduced; the same is true today for plain SwiGLU with `bias_activation_fusion=False`. Those cases now match training to BF16 tolerance but not bit for bit.

## Follow-up: gated squared-ReLU experts

Review finding: a gated squared-ReLU MoE (`activation_func=squared_relu` with `gated_linear_unit=True`) trains as `FC2(relu(gate)^2 * up)`, and config validation accepts it for `inference_optimized` on the `torch` and `vllm` backends. Megatron's CLI cannot build this pair, but a directly built `TransformerConfig` (Bridge, NeMo, RL frameworks) can.

- **Bug.** `_resolve_mcore_activation_type` mapped `squared_relu` to the non-gated `SQUARED_RELU` without looking at `gated_linear_unit`. The vLLM backend (the default) then squared the whole `[gate | up]` FC1 output and launched FC2 with `K = fc2.size(2) = F` over rows of width `2F`. FC2 read only `relu(gate)^2` and dropped the up half, without an error. On H100 the expert output differed from training by a normwise relative error of 1.04, against 0.0061 for `FC2(relu(gate)^2)` alone. The torch backend crashed in `grouped_mm` on the shape mismatch.
- **Fix.** The mapping now covers `(activation_func, gated_linear_unit)` pairs exactly, and gated squared ReLU becomes `ActivationType.GATED_SQUARED_RELU`. The four GLU kernels of this PR (`padded_swiglu`, `bounded_silu_mul`, and the batch-invariant `swiglu_with_probs` and `weighted_silu_mul_bounded`) take a `SQUARED_RELU_GATE` constexpr that replaces SiLU with `relu(gate)^2`. Gated squared ReLU therefore gets the same GLU options (clamp, linear offset, interleave), probability handling and backends as SwiGLU. The SiLU instruction sequences are unchanged.
- **Shape check.** The vLLM GEMM launcher (`_invoke_fused_moe_kernel`) raises a `ValueError` unless its input width equals the weight's K and its output width equals the weight's N. The kernel takes N and K from the weight, so a mismatched operand would otherwise be half-read. The check is on the host and costs nothing under CUDA graphs.
- Training has one path for gated squared ReLU, the unfused eager GLU of `TEGroupedMLP` (the fused SwiGLU and weighted squared-ReLU ops do not apply to it). The inference kernels reproduce its roundings (see the second follow-up below), so in batch-invariant mode they match training bit for bit.

Tests:

- `TestInferenceGroupedMLPMatchesTraining` (1 GPU, TE) adds `gated_squared_relu`, alone and with clamp, offset and interleave, on both backends, with batch-invariant mode on and off. The batch-invariant torch case needs DeepGEMM. On `main`, the vLLM cases give a relative error of 1.28 (9.25 with the GLU options) and the torch cases crash on the GEMM shape mismatch.
- `test_vllm_fused_moe.py::TestVllmFusedMoe::test_matches_reference_gated_squared_relu` compares the vLLM backend with a sequential `relu(gate)^2 * up` reference at O(1) activations. `test_rejects_gemm_input_width_mismatch` checks that a gated FC1 output reaching FC2 without the gated activation raises instead of being half-read.
- Determinism: `test_inference_kernels.py` replays the squared-ReLU-gate variants of the four kernels and `vllm_fused_moe` with `GATED_SQUARED_RELU`. `test_moe_kernels.py::TestMoEModules::test_inference_grouped_mlp_glu_options_replay` adds a gated squared-ReLU expert with interleave. `tools/check_kernel_determinism_coverage.py --base-ref origin/main` passes.

Checked on CPU under the Triton interpreter: the new kernel variants match a PyTorch reference, the SiLU variants are bit-identical before and after the change, and both backends match the reference end to end. The H100 results for this section and the next are at the end of the next section.

## Follow-up: review of the gated squared-ReLU commit

- **Training's rounding, bit for bit.** Gated squared ReLU trains only through `TEGroupedMLP`'s unfused GLU, which runs each step as a BF16 torch op. The previous commit computed `relu(gate)^2 * up` (times the probability) in FP32 with one final rounding, so batch-invariant inference was only tolerance-close. A shared Triton helper, `squared_relu_glu`, now reproduces the eager sequence in all four GLU kernels: the clamp (torch rounds its bound to BF16; rounding after the FP32 clamp gives the same value), `bf16(relu(gate)^2)`, `bf16(linear + offset)` and `bf16(product)`. The batch-invariant kernels then apply the FP32 probability and round once more, as training does. The SiLU instruction sequences are unchanged.
- **NaN.** The squared-ReLU gate used `tl.maximum(gate, 0.0)`, which returns 0 for a NaN gate on the GPU; training's `F.relu` keeps NaN. It now propagates NaN. The non-gated squared-ReLU kernels on `main` have the same `tl.maximum` and are left as they are.
- **Validation.** `TransformerConfig` now rejects, for `inference_optimized` MoE on the `torch` and `vllm` backends, every activation `InferenceGroupedMLP` has no kernel for: anything other than squared ReLU (gated or not) and SwiGLU, and the tanh-clamped gated form (SiTU-GLU). These configurations used to pass validation and fail at module construction (GELU, GeGLU, non-gated SiLU) or at the first forward (SiTU-GLU). The gated-unit message no longer advertises GeGLU. `tests/unit_tests/determinism/kernels/test_te_wrappers.py::test_per_module_mxfp8_recipe_model_init_policy` built such a config (inference-optimized MoE with the default GELU) only to test weight storage; it now sets squared ReLU.
- **Kernel names.** The GLU kernels keep their names and the separate `squared_relu_gate` argument, whose docstrings now name both gates. At the `mcore_fused_moe` / `vllm_fused_moe` API the gate comes from `ActivationType` (`SWIGLU` or `GATED_SQUARED_RELU`) and `GLUOptions` holds the options of either; moving the gate into `GLUOptions` would let the two disagree.

Tests:

- `tests/unit_tests/determinism/kernels/test_inference_kernels.py::test_batch_invariant_gated_squared_relu_matches_training` (1 GPU): both batch-invariant kernels against the eager BF16 GLU built from training's `squared_relu`, weighted and unweighted, plain and with a clamp of 0.3, an offset of 0.7 and interleave 64 (neither value is a BF16 number), `atol=0`.
- `tests/unit_tests/inference/test_moe_dispatching_and_routing.py::TestNVLSAllGatherVDispatcher::test_batch_invariant_gated_squared_relu_moe_matches_training` (2 GPUs, NVLS): a gated squared-ReLU MoE layer's training path (all-to-all, unfused GLU) and its batch-invariant inference path, bit for bit, on both backends, plain and with the GLU options. The torch backend needs DeepGEMM, as the existing cases of this test do. `test_batch_invariant_moe_matches_training` now lets its `config_overrides` replace the activation settings.
- `test_moe_permute.py::test_glu_propagates_nan` (renamed from `test_swiglu_clamp_value_propagates_nan`) covers both gates, clamped and unclamped.
- `test_config_rejects_activations_without_inference_kernel` (CPU): GELU, non-gated SiLU, GeGLU and SiTU-GLU on both backends; fails without the new check.

Checked on CPU under the Triton interpreter (with FP32-to-BF16 casts patched to round to nearest even, as the GPU does): the new kernel variants reproduce the eager BF16 GLU bit for bit, the previous kernels did not (2–7k of 16k elements differed), and the SiLU variants are bit-identical to the previous commit. `tools/check_kernel_determinism_coverage.py --base-ref origin/main` passes.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), at this PR's head, the regression tests pass: 169 cases on 1 GPU (16 Blackwell-only cases skipped) and the 4 cases of the 2-GPU NVLS layer test. On `main`, 76 of the 169 1-GPU cases fail, and all 4 2-GPU cases fail (the torch backend on the K mismatch, the vLLM backend on the bitwise comparison with training). Among the 1-GPU failures, the gated squared-ReLU parity cases fail as described in the previous section, and the activation-rejection test fails because `main` does not raise. The NaN test and the batch-invariant gated squared-ReLU kernel test fail on `main` because `main` has no `GLUOptions`, so they do not reach the NaN or rounding checks there. The neighbor tests (`test_vllm_fused_moe.py`, `test_moe_permute.py` and the 2-GPU `test_batch_invariant_moe_matches_training`) pass (1013 cases, 4 skipped).
