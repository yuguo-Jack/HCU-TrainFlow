# Use local optimizer tensors in MFSDP v2 until checkpointing

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7322) · state: open · merged: False

## Original PR description

## Summary

Related to #7264.

Keep MFSDP v2 parameters, gradients, and optimizer state as local tensors during training. Construct DTensors only at the native and MCore distributed-checkpoint boundaries, where global shapes and sharding metadata are needed.

- Bind local gradient views without caching wrappers or tracking an installed gradient buffer.
- Use the owning gradient buffer's layout to account for replication in gradient norms and zero counts.
- Wrap model and parameter-shaped optimizer state for native and MCore checkpoint save/load, preserving uneven-shard metadata and optimizer parameter identity.
- Build checkpoint views by traversing `FsdpModule.parameter_groups` and calling the existing `DBuffer.get_dtensor(index)`. `DBuffer` and the `FsdpParameter` record keep their main-branch APIs; optimizer-state conversion stays in checkpoint code.
- Cover local runtime tensors, gradient accumulation and zeroing, clipping, and checkpoint roundtrips.

## Performance before rebase

Verified against the PR's direct parent on the same eight H100 GPUs using a DeepSeek-V3 proxy: four layers, hidden size 1024, 32 experts/top-8, sequence length 512, EP=2, TP=PP=CP=1, four optimizer instances with outer optimizer sharding, microbatch size 1 and global batch size 16. BF16 training uses FP32 main gradients, precision-aware Adam, and clipping. Expert-rank capacity factor is 4.0 with flex/hybridep dispatch.

Median iteration latency over steps 5–20, excluding startup and capture:

| Configuration / run order | Base | This PR | Latency reduction |
| --- | ---: | ---: | ---: |
| Eager, base then PR | 132.2 ms | 115.4 ms | 12.7% |
| Eager, PR then base | 131.7 ms | 117.2 ms | 11.0% |
| Full-iteration + optimizer graphs, PR then base | 22.7 ms | 21.9 ms | 3.5% |

All 20 logged losses match between base and PR within each mode, including both eager repeats. This is agreement at log precision, not a bitwise-equivalence claim. No capacity-overflow reruns were reported. The repeated eager improvement is stronger evidence than the small, single-pair graph improvement.

These absolute timings are not a reproduction of #7264's historical ~245–250 ms eager baseline. That workload used capacity factor 1.0; the retained profiling log reports over-budget dispatch and a forward/backward fallback on all 20 iterations. The current capacity-factor-4.0 workload avoids those reruns. The container/revision, main-gradient dtype, and timer settings also differ. The table above isolates this PR against its parent under the current workload, not the historical baseline.

For reference, v1 with the same capacity factor and FP32 main gradients measured 107.1 ms eager (one run). This PR reduces the eager gap to v1 from about 23% to 8–9%. v1 and v2 are not numerically identical: final losses were 5.385768 and 5.405390, respectively.

Performance-tested head: `cf845881bae30c142febbce8458f7032bf1ec603`; base: `54c62dfb6852e9218bf38590be9b90930bf7d589`. Subsequent cleanup removes prototype scaffolding and an unused DTensor helper, and corrects documentation without changing the executed training path.

## Compatibility and scope

Bare `state_dict()` calls now expose local shards. Distributed checkpoints use the native MFSDP v2 save/load helpers or MCore's `state_dict_for_save_checkpoint` and optimizer `sharded_state_dict` interfaces added in #6215. Both paths construct checkpoint-only DTensor views and unwrap loaded optimizer state before reinstalling it. MCore optimizer checkpointing retains #6215's explicit rejection of expert parallelism. Non-elementwise or factored-state optimizers are not added by this change.

The remaining MFSDP v2 test files and consumers outside the validated paths that assume runtime DTensors still need validation. This PR does not address the separate buffer-layout construction overhead.
