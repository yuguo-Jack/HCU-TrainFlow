# Warn on the last unwarned core reads and once per omitted collection

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8772) · state: closed · merged: False

## Original PR description

Depends on #8770, #8748, #8729 and #8732. Please review the diff from their merge: [scoped diff](https://github.com/Connor-XY/Megatron-LM/compare/f2e7c9fd6d...yx/pstate-h2-core-residuals).
- #8770 classifies each core read of the global grid as warned or unwarned. Its tests list the two reads this PR moves in `UNWARNED_READS`.
- #8769, inside #8770, makes `resolve_gtp_remat_group` warn before it falls back. That is why the partial fallback collections fixed here warn more than once.
- The edited code comes from #8073 (MoE metrics and MoE's default collection), #6293 and #8035 (MTP placement), #8754 (the MTP virtual-pipeline warning), #8729 (Attention's fallback), #8748 (the owner-linear tests) and #8733 (the uninitialized-grid warning). #8073, #8754 and #8733 come in through #8770.
- The MoE-layer case of the owner test reads `experts.pg_collection`, which #8732 adds to SequentialMLP and `TEGroupedMLP`.
- The merges of #8748 and #8770 resolve the existing conflicts of #8035 with #6293 and #6303 in the Transformer Engine wrappers, `t5_model.py`, `multi_token_prediction.py` and the MLA projections, and regenerate the process-group allowlist. Each merge commit lists its resolutions.

#8773 stacks on this PR and makes an unwarned core read fail the checker tests.

**Why.**
- Two core reads of the global grid followed their fallback warning only through data flow: the data-parallel group in `MoEMetricsTracker._sync_metrics` and the pipeline size in `mtp_on_this_rank`. Each sat under an `if` on a value that only the warned branch leaves `None`. The checker cannot follow that and counts both as unwarned.
- Since #8769, a linear whose collection lacks `gtp_remat` or `expt_gtp_remat` warns before it falls back. Attention, the MTP block and MoE's default collection build fallback collections without these fields, so each kind of linear built on them warned again. One omitted collection gave 3 warnings for SelfAttention, CrossAttention, the MTP block and MoELayer, and 5 for MoELayer with shared experts.

**What.**
- `MoEMetricsTracker._sync_metrics` warns and reads in one block. The warning, the read order and the reduction groups are unchanged.
- `mtp_on_this_rank` reads the pipeline size in its warned branch. The read now comes before the virtual-pipeline fallback instead of after it, which only reorders two reads of the global grid.
- The allowlist marks both reads `:warned`, and `UNWARNED_READS` is empty. The checker reports 101 grandfathered reads: 57 guarded, 44 warned and 0 unwarned (the base has 42 warned and 2 unwarned).
- Attention and `MultiTokenPredictionBlock` add `gtp_remat` to the groups of their fallback collection. It is read without requiring an initialized grid, as the linears' own fallback read it, so the linears get the same group and the owner's warning is the only one. The DSA owners keep their `tp` and `cp` lists, since their linears take an explicit GTP group or none. MLA already builds every group.
- MoE's `get_default_pg_collection` also builds `gtp_remat` and `expt_gtp_remat`. Its check that `parallel_state` created every group skips them, since `None` means the axis is off. SequentialMLP and the latent projections get the groups they read before without a warning of their own. The shared experts do too with GTP off. With dense GTP on (`gtp_remat` has more than one rank), their Transformer Engine linears still warn for `pg_collection.dp_cp`.
- The uninitialized-grid warning no longer names `gtp_remat` and `expt_gtp_remat` among the `None` groups that `torch.distributed` reads as WORLD. For these two fields `None` means the axis is off. This edits #8733's `_warn_fallback_to_uninitialized_grid` (6 lines).
- Docstrings and comments say which linears still lack a `dp_cp` replica group without a collection (see Compatibility).

With GTP off, an owner built without a collection now gives one warning, with local and Transformer Engine linears alike.

**Tests.**
- `test_owner_linear_pg_collection.py`: on CPU, SelfAttention, CrossAttention, the MTP block and MoELayer (with and without shared experts) built without a collection give one warning, and the fallback collection holds the global GTP group. On GPU, the same for SelfAttention with the Transformer Engine spec and for CrossAttention with Transformer Engine linears. The CPU fixture now sets both GTP fields to `None`. Without them, 5 owner tests failed under `-W error::...ProcessGroupFallbackWarning`.
- `test_process_group_fallback.py`: the uninitialized-grid warning does not name the GTP groups.
- `test_moe_process_groups.py` expects both GTP fields in the default collection and no warnings from the experts' linears.
- `test_moe_egtp.py`: phase 2 builds its MoELayer without a collection and checks that the grouped experts are sharded.
- `test_check_process_group_usage.py`: `UNWARNED_READS` is empty.

Before the 2026-11-01 sync, the branch ran the edited test files and the checker and guard tests on 4 CPU ranks with Gloo: 120 passed, against 107 on the base. No test that passed on the base failed. The same 14 failed on both trees: the CUDA cases of `test_moe_process_groups.py` and one context-parallel helper test.

On 4 GPUs against its base: `test_owner_linear_pg_collection.py`: 35 passed here vs 21 on the base, with the Transformer Engine cases, and the 14 new tests pass. `test_process_group_fallback.py`: 34 passed vs 33, and the 1 new test passes. `test_moe_process_groups.py` (23), `test_check_process_group_usage.py` (52, with 130 subtests), `test_parallel_state_deprecation.py` (110), `test_example_process_groups.py` (11), `inference/high_level_api/test_apis.py` (29) and the Transformer Engine extension tests `test_te_extension_process_groups.py` (11) and `test_te_layernorm_column_parallel_linear.py` (8) pass the same counts on both sides. No test fails on either side. `test_moe_egtp.py` reports no tests on either side, and no GTP-on path ran: GTP needs Transformer Engine 2.19 or later, and no available container has it. In the integration run, this PR's test files show no regressions against main. End-to-end smokes on 4 GPUs with all #6307 PRs applied cover 22 training configurations, MoE and MTP among them: they give bit-identical losses to main and record no process-group fallback warning. Before the sync, the stacked run of all #6307 changes also passed `test_multi_token_prediction.py` (225 tests) on 4 GPUs.

**Compatibility.**
- No change for callers that pass a collection. Stock training passes full collections.
- Without a collection, the groups and the order of the warnings stay the same, with one exception below.
- Behavior change: a MoELayer built with `pg_collection=None`, Transformer Engine grouped GEMM and expert GTP larger than 1 now shards its experts over the global expert GTP group. Before, it silently did not. This matches SequentialMLP and a `TEGroupedLinear` built without a collection. With expert GTP off nothing changes. The new behavior has not run on GPUs. Do maintainers accept this change? If not, dropping `expt_gtp_remat` from `get_default_pg_collection` and reverting the `test_moe_egtp.py` change restores the old behavior; SequentialMLP then keeps its two extra warnings.
- Not fixed here: with dense GTP weight remat on and no collection, SelfAttention, CrossAttention, the MTP block and MoELayer's Transformer Engine shared-expert linears still warn once per Transformer Engine linear class for `pg_collection.dp_cp`. The latent projections get no `dp_cp` replica group, without a warning. Checkpoint saving elects the shard writers over `parallel_state`'s `dp_cp` group, with a warning. The fix is to add `dp_cp` to these fallback collections only when `gtp_remat` has more than one rank. The `dp_cp` accessor asserts an initialized grid and would be a new counted read, so this PR leaves it out. Should it be fixed in a follow-up, or is the documented warning acceptable?
- An MTP block with MoE layers still cannot be built without a collection, because the block's fallback collection has no `ep` group. This predates this PR.
- Needs `determinism-exempt`: the kernel coverage check flags `attention.py` and `moe_utils.py`. Only the groups of the fallback collections change there, not the numerics.
