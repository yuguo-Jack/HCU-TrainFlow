# fix(inference): reject malformed completion and chat requests with 400

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8596) · state: open · merged: False

## Original PR description

## What does this PR do?

`/v1/completions` and `/v1/chat/completions` mishandled several malformed requests, sometimes after work had already been submitted to the engine:

- **Server errors (500):**
  - a sampling field of the wrong type, such as `"top_k": [1]` (a `TypeError` escaped);
  - a JSON body that is not an object, such as a JSON array;
  - a non-object `stream_options` on a streaming request.
- **Accepted:** a chat request with `n` less than 1 returned 200.

This PR validates these inputs before anything is submitted and returns a 400 client error. A non-streaming request with a malformed `stream_options` is still accepted, because that field only applies to streaming.

## Example failure scenario(s)

**Scenario 1 (wrong-typed sampling field)**

- Client A posts a completion with `"top_k": [1]`.
- Converting the list to an integer raises `TypeError`, which only `ValueError` handling would have caught.
- Before this fix, client A received a 500.
- With this fix, client A receives a 400 "Invalid sampling parameter" message.

**Scenario 2 (malformed stream_options on a streaming request)**

- Client B posts a streaming chat request with `"stream_options": ["include_usage"]`.
- Before this fix, the endpoint submitted the request and then failed while reading `include_usage` from the list, returning a 500.
- With this fix, client B receives a 400 before anything is submitted.

**Scenario 3 (JSON array body)**

- Client C posts the JSON array `["not", "an", "object"]` as the request body.
- Before this fix, reading fields from the array raised an error and the endpoint returned a 500.
- With this fix, client C receives a 400 "Invalid or missing JSON body".

## How was this bug discovered?

Endpoint tests post each malformed request and expect a 400 with no prompts submitted to the client. On `main` they receive 500s, except the `n=0` chat request, which returns 200; in the streaming case the request had already been submitted. Existing cases that expected 500 for a list-valued `top_k` and for explicit `null` sampling fields now expect 400.

## Dependency and scope

This PR is independent and based on `main`. Production changes are input checks in `chat_completions.py` and `completions.py`.

The regressions are:

- `test_malformed_stream_options_is_rejected_before_submission` and `test_non_object_json_body_is_rejected_before_submission` in `test_endpoints_common.py`;
- updated cases in `test_malformed_chat_requests_are_rejected_before_submission` and `test_malformed_completions_requests_are_rejected_before_submission`.
