# Clear the Mamba prefix cache whenever the KV prefix cache is reset

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8916) · state: open · merged: False

## Original PR description

## What does this PR do?

For a hybrid model with prefix caching and a Mamba state cache
(`prefix_caching_mamba_gb`), a RECOMPUTE suspend and resume that keeps
its buffers (unified memory or `torch_memory_saver`) resets only the
context's metadata. `reset_metadata()` empties the KV prefix cache, but
only `reset()` also empties the Mamba slot allocator, whose cached states
are keyed by the hashes of those KV blocks. The Mamba cache therefore keeps
entries naming blocks that no longer hold their hashes; nothing ever
removes them.

A request that keeps its pre-suspend hash salt can later match such an
entry. It then skips the matched prompt tokens, finds no state in the KV
block it matched, and continues from a zeroed Mamba state, so its
remaining tokens are computed without the skipped prefix.

This PR resets the Mamba slot allocator in `reset_metadata()`, together
with the KV block allocator; `reset()` calls `reset_metadata()`, so its own
reset is removed.

## Example failure scenario(s)

**Scenario (a re-admitted request restores a zeroed state)**
- A hybrid model runs with prefix caching, a 2-slot Mamba state cache,
  chunked prefill, LRU eviction, and RECOMPUTE suspends with
  `torch_memory_saver`.
- Request A finishes, and the Mamba states at its block boundaries are
  cached; request B shares A's first blocks, skips them through a cache
  hit, and is part-way through chunked prefill when the engine suspends.
- The resume empties the KV prefix cache but keeps the Mamba cache. B
  restarts its prefill under its original salt, publishing its blocks
  under the hashes the stale Mamba entries still name.
- B is evicted and re-admitted. Its first chunk matches its own cached
  blocks, and the farthest Mamba match is a stale entry, so B skips 16
  prompt tokens, but the block it matched holds no state.
- B continues from a zeroed state: with 41 tokens in its KV cache, its
  Mamba state reflects only the last 25, so every later token is computed
  without its first 16 tokens.

## How was this bug discovered?

A stateful search drove the real engine through generated sequences of
submissions, steps, suspends, resumes and aborts on a hybrid model whose
Mamba layer was replaced by an exact synthetic recurrence running through
the context's real state slots, step metadata and Mamba prefix cache. Each
request's recurrent state is a known function of the tokens it has
processed, and logits depend on it.

After a RECOMPUTE suspend and resume with static buffers, a check that
every cached Mamba state is the state of its block's prefix failed: an
entry still named a block under a hash that block no longer held. A
per-step dump showed the entries surviving the resume, and then their
slots being freed while the hash entries remained. Replaying that history
with memory pressure after the resume evicted the request that kept its
salt; on re-admission it skipped 16 prompt tokens and continued from a
zeroed state, which a check that each live state matches its computed
tokens caught (state over 25 tokens against 41 computed). The same
replays pass with this change.

## Scope

- Production: `dynamic_context.py` only (+3/−3), in `reset_metadata()` and
  `reset()`.
- Test (+23): `test_dynamic_prefix_caching.py`:
  `test_recompute_resume_with_static_buffers_clears_mamba_cache`. It caches
  two Mamba states, runs the static-buffer RECOMPUTE suspend and resume, and
  requires both prefix caches, and every Mamba slot, to be empty.
- `reset()` behaves as before; the non-static RECOMPUTE resume already
  rebuilds both caches.
- No functional-test, config or API change.
