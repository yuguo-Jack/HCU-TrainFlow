# Add sm103 tuned entries for in-tree SSM, GDN and DSA min-memory kernels

## Original PR description

# What does this PR do?

Adds packaged `sm103` entries for 26 in-tree Triton autotuners that had none, 32 entries in total:
- the GDP/GDN prefill kernels (`ssm/ops/gdp`)
- the in-tree Mamba2 SSD kernels
- the causal-conv1d varlen kernels
- the fused pre-gated-delta-rule kernels
- the DSA min-memory kernels

The existing 25 kernels' entries are unchanged.

Without an entry, a pinned (deterministic) run falls back to the cheapest candidate by static cost. On B300 that fallback is up to 3.5x slower than the best candidate for these kernels, and 1.5x to 1.7x slower for several of them. With these entries, the worst case over the swept shapes is 1.05x.

It also makes `test_packaged_entries_name_live_candidates` handle kernels with `@triton.heuristics` above `@triton.autotune`. Six of the new kernels are wrapped that way. For those the module attribute is a `Heuristics` object, so without the change the test would skip the whole test at the first of them instead of checking the entries. It now unwraps `Heuristics` first, so every packaged entry is checked.

## How the entries were chosen

This is the same method the README describes for the MLA RoPE and mHC sweeps:
- Each kernel family was driven through its entry point at 2k, 8k and 32k tokens, one process per token count. That way, kernels whose tuning key leaves out the token count were timed at every count.
- Triton timed every candidate.
- Each kernel gets a `*` entry with the smallest worst-case slowdown over all swept observations.
- A tuning key gets its own entry when its own best candidate beats `*` there by more than 5%. That happened for three kernels: one extra entry for `chunk_fwd_kernel_o`, two for `chunk_gated_delta_product_fwd_kernel_h_blockdim64` and three for `_g_beta_backward_kernel`.

`chunk_fwd_kernel_o` sizes its BK/BV candidates from a shared-memory probe: [64, 128] on H100/B300-class GPUs and [32, 64] when no GPU is visible. So its entries were chosen among the BK = BV = 64 candidates, which exist in both lists. Its `*` alone would be 1.15x instead of 1.04x; with the extra per-key entry the worst case is 1.04x.

Shapes:
- GDN: 16 key heads, 32 value heads, head dim 128, conv width 4, packed THD and padded BSHD, forward and backward.
- GDP prefill: M = 1 (32 heads) and M = 2 (16 heads), head dim 128, four sequences per step; `gdp_prefill_prepare` with M = 3.
- Mamba2: 128 heads of dim 64, 8 groups, d_state 128, chunk 128, four sequences; causal-conv1d over the matching 10,240 channels.
- DSA-GQA min-memory: 32 query heads, 8 and 1 KV groups, head dim 128, top-k 2048, simplified indexer, forward and backward.

"Slowdown" below is the time of the chosen candidate divided by the fastest candidate at the same observation, worst over the swept observations. The fallback column is the cheapest-by-static-cost candidate that a table miss selects.

## Not covered

8 of the 34 in-tree multi-config autotuners without an `sm103` entry stay without one:
- `ssd_chunk_state._chunk_state_varlen_kernel`: nothing in the tree calls `chunk_state_varlen`.
- `gdp.common.l2norm_fwd_kernel1`: only used for head dims above 512.
- DSA min-memory: the configurations I drove did not reach these six kernels:
  - `_dsa_selected_index_scores_kernel` and its backward (standard indexer mode)
  - `_dsa_simplified_selected_scores_kernel` and its backward (learned-K mode)
  - `_dsa_simplified_gathered_linear_wgrad_kernel` (fused input norm)
  - `_dsa_sparse_attention_backward_kernel` (the accumulate path)

## Testing

On B300 (SM103), with Triton 3.8.0 and PyTorch 2.14.1+cu130:
- `tests/unit_tests/tuning`: 93 passed and 1 skipped (needs two ranks) with a GPU; 92 passed and 2 skipped without one. Both runs include `test_packaged_entries_name_live_candidates` over all packaged entries.
- A pinned run of the four kernel families at 2k and 8k tokens: each of the 26 kernels chose its table entry for every tuning key it saw (37 and 38 keys), none fell back.

The timings are Triton's per-candidate benchmark medians, one run per observation. They rank candidates for these kernels; they are not end-to-end model throughput numbers.
