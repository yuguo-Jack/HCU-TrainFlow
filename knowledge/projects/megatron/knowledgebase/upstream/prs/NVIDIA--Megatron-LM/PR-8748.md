# Pass owners' process-group collections to the linears they build

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8748) · state: closed · merged: False

## Original PR description

Depends on #8017 (which contains #6259) and #8035 (which contains #8034 up to its last, test-only commit). Please review the diff from the merge of their heads: [scoped diff](https://github.com/Connor-XY/Megatron-LM/compare/33420ae5dd...yx/pstate-c9-owner-linear-collections). #8035 gives `TELinear` its `pg_collection` parameter and stores `_pg_collection` on the fused Transformer Engine layers, and this PR uses both. The new test uses #8017's `build_test_pg_collection`. Before the sync, the base ended with a commit that regenerated the process-group allowlist: the merges kept #8035's total of 195, while the merged entries recorded 194, and no entry changed. The scoped diff now starts from the merge of the synced heads and does not touch the allowlist.

**Why.** Many modules hold a `ProcessGroupCollection` but build their linear layers with only its TP group, or with no group at all. A linear without a collection takes its `gtp_remat` group and the replica group of its GTP shards from `parallel_state`. With a per-module quantization recipe, a Transformer Engine linear also takes its amax group from there. A model on its own grid then runs those linears on another grid's groups. With GTP weight remat or a per-module quantization recipe, these linears take the global-group fallbacks, which start to warn with #8753 and #8755. Both land after this PR, so stock training stays free of those warnings.

**What.** Each owner passes its collection to every linear it builds:
- MLA (plain, fused and absorbed), including `linear_proj`.
- Cross-attention. It also passes its TP group to `linear_q` and `linear_kv`, which its `linear_proj` and head split already used.
- The DSA, simplified DSA and CSA indexers, the CSA compressor and the Q down projection of DSv4 attention.
- GDN's `in_proj` and `out_proj`.
- `MoELayer`'s latent projections, `TELinear` or `InferenceLinear`.
- `TEFusedMLP.as_mlp_submodule`, as `MLP.as_mlp_submodule` already does.
- `split_te_layernorm_column_parallel_linear`, which MLA uses to unfuse `linear_kv_up_proj` when it caches latents. It takes the fused layer's collection.
- RADIO's patch embedders, and LLaVA's `MultimodalProjector`, which got only the TP group before.

The ModelOpt specs put the ModelOpt `Linear` in the MLA down projections and the DSA indexer projections, so it now accepts `pg_collection`. It has no GTP shards and no Transformer Engine quantization, so it ignores the argument, as it does `tp_comm_buffer_name`. The process-group allowlist does not change.

**Tests.**
- New `tests/unit_tests/transformer/test_owner_linear_pg_collection.py` builds each owner on a collection from `build_test_pg_collection`. Its groups have the standard grid's ranks but are not the `parallel_state` groups. The test checks that every linear received that collection object:
  - MLA (with and without `q_lora_rank`, and with the ModelOpt down projections), fused MLA, absorbed MLA, cross-attention and the three indexers, from local linears. Without CUDA these build on CPU in one process with a one-rank gloo group, which the fixture destroys afterwards.
  - The same owners from Transformer Engine linears, plus GDN, the split helper and `TEFusedMLP.as_mlp_submodule`. These also check the linear's own `_pg_collection`. The fused-MLP case checks that both Transformer Engine linears get the owner's collection. The sync merge drops its `assert mlp.pg_collection is owner_pg_collection`, because `MLP.pg_collection` comes from #8044, which is not in this PR's base.
- The DSv4 attention, latent MoE, LLaVA and RADIO tests check their projections.
- The new tests run at TP=1. That is enough for identity checks, but no TP>1 test covers cross-attention's new `tp_group`.
- The CPU branch of the fixture is optional. Should the file run on GPU only instead?

On 4 GPUs against its base, there are no regressions. The new `test_owner_linear_pg_collection.py` passes all 21 of its tests, including the Transformer Engine cases, which need CUDA and #8035. `test_dsv4_hybrid_attention.py` passes 47 tests vs 46 on the base, `test_radio_model.py` 48 vs 46 and `test_llava_model.py` 26 vs 25. The 4 new tests in those three files pass. `test_latent_moe_layer.py` (15), `test_te_layernorm_column_parallel_linear.py` (5), `test_te_amax_reduction_group.py` (7) and `test_amax_reduction_group.py` (22) pass the same tests on both sides. Four `test_process_embedding_token_parallel` cases in `test_llava_model.py` fail on both sides because they need 8 ranks. In the integration run, with all #6307 PRs merged onto main, this PR's test files show no regressions against main. There, `test_llava_model.py` passes all 30 of its tests on 8 GPUs (two nodes), against 29 on main. End-to-end training smokes on that tree (22 configurations on 4 GPUs) give bit-identical losses to main and record no process-group fallback warning. Before the sync, this branch also ran on CPU with Gloo, one test file at a time, with no regressions. The local-linear owner cases and the DSv4 test pass there and fail on the collection check without the code changes.

**Compatibility.**
- On the standard grid the collection holds the global groups, so sharding, initialization, checkpoints and numerics do not change.
- Off the standard grid, two changes are intended fixes:
  - The separate RL inference model is built from `build_inference_pg_collection`, which sets `gtp_remat=None`. These linears used to resolve the training run's global `gtp_remat` there and could come out GTP-sharded. They are now unsharded, like that model's other linears.
  - `CrossAttention`'s `linear_q` and `linear_kv` now shard over the owner's TP group.
- Owners built without a collection fall back to partial ones: `CrossAttention` (tp, cp, hcp), `DSAttention` and `DSAIndexer` (tp, cp), and `SimplifiedDSGQAIndexer` (tp, cp). Their linears now receive that partial collection. With #8034, a per-module quantization recipe on them raises `ValueError` in `amax_reduction_group`, because the collection has no `tp_cp` or `tp_dp_cp`. `SelfAttention`'s linears already behave this way. Stock training is not affected, because `TransformerLayer` and MLA always pass a full collection.
- A custom spec class in these slots must accept `pg_collection`, as the local, Transformer Engine, inference and ModelOpt linears do.
- Not changed here, all outside `megatron/core`: `FlextronRouter`'s linears, the InternViT example's `linear_qkv` and the MIMO example projector specs still build without a collection.
- The diff needs eight CODEOWNERS teams. Should the MoE, fused-MLP and vision commit move into its own PR?
- Needs `determinism-exempt`: the kernel coverage check flags the touched Transformer Engine, attention, MLA, DSA, GDN and MoE files, but only process-group plumbing changes.

Landing: #8722 adds a `tp_group=` argument next to this PR's `pg_collection=` argument in seven files: `absorbed_mla.py`, `csa.py`, `deepseek_v4_hybrid_attention.py`, `dsa.py`, `dsa_gqa.py`, `moe_layer.py` and `multi_latent_attention.py`. #8023 does the same in `absorbed_mla.py` and `multi_latent_attention.py`. They conflict with this PR there, and whichever lands second keeps both arguments.
