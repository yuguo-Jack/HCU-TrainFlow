# Fix the quickstart example's optimizer so training updates weights

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8819) · state: closed · merged: False

## Original PR description

**Why.** `examples/run_simple_mcore_train_loop.py` trains nothing. It wraps the model in Megatron Core's `DistributedDataParallel`, then steps a `torch.optim.Adam` over the parameters.
- DDP's backward hook adds each gradient into `param.main_grad` and sets `param.grad` to None (`distributed_data_parallel.py:624`).
- Adam skips every parameter whose `grad` is None, so none of the 5 iterations changes a weight.
- The loop never calls `zero_grad_buffer()`, so `main_grad` holds the sum of every iteration's gradients.
- The bug came in with the DDP wrap in feb68a3d9e.

This is not a parallel_state deprecation gap. The #6307 audit of the examples found it.

**What.**
- New `get_optimizer()` builds the optimizer with `get_megatron_optimizer()`: Adam, lr 1e-3 (torch Adam's default) and `use_gloo_process_groups=False`. The other settings are `OptimizerConfig` defaults, including weight decay 0.01 and grad clipping at 1.0. With fp32 params the factory returns a `ChainedOptimizer` around an `FP32Optimizer`, which steps on `main_grad`.
- New `train_step()` holds the loop body. It calls `zero_grad_buffer()` and `optim.zero_grad()` before the backward pass, then `finalize_model_grads()` and `optim.step()`. `megatron/training/training.py` uses the same order.
- `__main__` builds the optimizer with `get_optimizer()` and calls `train_step()` 5 times. The DDP wrap, the data, the checkpointing and the process groups do not change.
- No collective is added. `get_megatron_optimizer()` all-gathers the param-group keys over WORLD, and `optim.step()` all-reduces the grad norm over the model-parallel group. Every rank builds one optimizer and runs the same number of steps, so every rank of each group enters both.

**Tests.**
- New `tests/unit_tests/test_run_simple_mcore_train_loop.py`:
  - `test_train_step_clears_grads_before_backward_and_steps_after_finalize` runs on CPU. It passes mocks to `train_step()` and checks the call order: `zero_grad_buffer`, `zero_grad`, the schedule, `finalize_model_grads`, `step`.
  - `TestTrainStepUpdatesWeights::test_two_iterations_update_weights_from_fresh_grads` needs CUDA and an even world size. It wraps the example's model in DDP at TP2 and runs `train_step()` twice on synthetic batches. Every parameter with a nonzero `main_grad` must change in each iteration. `main_grad` must be all zero when each backward pass starts.
- On 4 CPU ranks with Gloo, the file gives 1 passed and 1 skipped (the CUDA class) on this branch. Main with only the new file added gives 1 failed (`train_step` does not exist) and the same 1 skipped.
- I also ran the CUDA test's steps on 2 CPU ranks with Gloo, with CUDA allocations, streams and the RNG tracker shimmed to CPU. The shims are not part of this PR, and on CPU the factory falls back to torch's AdamW.
  - This branch: 29 of 29 parameters got gradients and all 29 changed in both iterations. `main_grad` was 0 at both backward starts.
  - The old loop on the same harness: all 29 stayed unchanged and `param.grad` was None on all of them. `main_grad` had a max of 0.11 at the start of iteration 2.
- On 4 GPUs both tests pass.
- `torchrun --nproc_per_node=2 examples/run_simple_mcore_train_loop.py` on 2 GPUs:
  - This branch: the loss goes 4.6136, 4.6034, 4.5822, 4.5679, 4.5565 over the 5 iterations, and the checkpoint saves and loads.
  - Main: 4.6139, 4.6139, 4.6121, 4.6114, 4.6084. No weight changes there, so the loss moves only with the batches.
- `tools/check_process_group_usage.py` reports the same 3 pre-existing entries before and after. It scans only `megatron/core`.

**Compatibility.**
- Only the example and a new test change. No library code changes.
- The example now changes its weights every iteration, so its checkpoint holds trained weights instead of the initial ones.
- `megatron/core/QuickStart.md` shows an older loop without DDP, where `torch.optim.Adam` does see `param.grad`. It is not changed here.

**Landing.** #8746 edits the same loop and conflicts with this PR in one hunk, the loop body in `__main__`.
- Keep this PR's `train_step()` call.
- #8746's `pg_collection=pg_collection` arguments on the schedule call and on `finalize_model_grads()` move into `train_step()`, which then takes `pg_collection`. The conflict hunk shows them only on the old inline calls, so taking this side drops them unless the resolver adds them to `train_step()`.
- `get_optimizer()` also takes `pg_collection` and passes it to `get_megatron_optimizer()`.
- The other hunks of `get_optimizer()` and `train_step()` merge without a conflict, so they come out without `pg_collection` unless the resolver adds it. The same holds for the new test file, which merges cleanly but calls `model_provider()` with no argument. With #8746, the test has to pass the collection to `model_provider`, DDP, `get_optimizer`, the schedule lookup and `train_step`, and expect `finalize_model_grads([model], pg_collection=...)`.
- With that resolution and the rest of #6307 merged, both tests pass on 4 GPUs, and the example trains (loss 4.6118 to 4.5525 over 5 iterations) and reloads its checkpoint on 2 GPUs.
