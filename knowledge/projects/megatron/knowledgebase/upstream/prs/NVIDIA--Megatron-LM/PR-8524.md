# Add support for step-wise LR multipliers on top of the LR schedule, with optional linear ramps

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8524) · state: closed · merged: True

## Original PR description

## Summary

Adds step-wise LR multipliers on top of the existing LR schedule, with optional linear ramps between steps. A typical use is scaling the LR together with a batch-size ramp, e.g., multiplying it by √(B / B_final) at each batch-size increase, without changing the underlying warmup and decay.

- `--step-lr-rescale-schedule "SAMPLES:MULT,..."` multiplies the whole LR schedule (warmup, constant, decay and `min_lr`) by a piecewise-constant factor keyed on consumed samples. Entries may be comma- or whitespace-separated; the first entry must be at sample 0, and thresholds must strictly increase. Example: `0:0.5,1000:1.0`.
- `--step-lr-rescale-warmup-samples N` replaces each step after the first entry with a linear ramp over N samples. N must not exceed the gap between consecutive thresholds. The default of 0 keeps hard steps.
- Both values are saved in the scheduler state dict and checked on resume through `_check_and_set`. Checkpoints without them load unchanged.

Both flags default to off, so existing runs are unaffected.

The invariant is that each group's rescaled LR equals its existing scheduled LR multiplied by the active factor, including nonzero floors and overridden bounds. For example, this proposed test covers the changed branches without changing production code:

```python
@pytest.mark.parametrize("style", ["linear", "cosine", "inverse-square-root", "WSD"])
def test_rescale_composes_with_decay_and_group_bounds(style):
    def make(schedule):
        groups = [
            {"params": [], "default_config": True},
            {"params": [object()], "max_lr": 0.2, "min_lr": 0.02},
        ]
        scheduler = OptimizerParamScheduler(
            optimizer=MagicMock(param_groups=groups),
            init_lr=0.0,
            max_lr=0.1,
            min_lr=0.01,
            lr_warmup_steps=120,
            lr_decay_steps=1000,
            lr_decay_style=style,
            start_wd=0.0,
            end_wd=0.0,
            wd_incr_steps=1000,
            wd_incr_style="constant",
            wsd_decay_steps=200,
            lr_wsd_decay_style="linear",
            step_lr_rescale_schedule=schedule,
            step_lr_rescale_warmup_samples=40 if schedule else 0,
        )
        return scheduler, groups

    base, base_groups = make(None)
    scaled, scaled_groups = make("0:0.5,100:0.75")
    for samples, factor in [
        (50, 0.5), (100, 0.5), (120, 0.625),
        (140, 0.75), (900, 0.75), (1001, 0.75),
    ]:
        base.step(samples - base.num_steps)
        scaled.step(samples - scaled.num_steps)
        for plain, rescaled in zip(base_groups, scaled_groups):
            assert rescaled["lr"] == pytest.approx(plain["lr"] * factor)
            assert rescaled["weight_decay"] == plain["weight_decay"]
        assert get_canonical_lr_for_logging(scaled_groups) == pytest.approx(
            scaled_groups[0]["lr"]
        )
    assert scaled_groups[0]["lr"] == pytest.approx(0.0075)
    assert scaled_groups[1]["lr"] == pytest.approx(0.015)
```

Acceptance is the explicit assertions above: overlapping warmups, ordinary decay, post-decay floors, both group bounds, unchanged weight decay, and empty-default-group logging. Preserve the existing disabled-feature expected values, hard-step LR change from `0.05` to `0.075` at sample 100, and transition values `0.0625` at 120 and `0.075` at 140. ### Keep rescale thresholds on the consumed-sample clock

**Failure:** The advertised sample-keyed options reach a rescale lookup based on `num_steps`, but [train_step advances that counter only after successful optimizer updates](https://github.com/NVIDIA/Megatron-LM/blob/4d67b0afe26f6b98f20ebb7186d49fad92b0a409/megatron/training/training.py#L3573-L3581). In contrast, [consumed samples advance after unsuccessful updates too](https://github.com/NVIDIA/Megatron-LM/blob/4d67b0afe26f6b98f20ebb7186d49fad92b0a409/megatron/training/training.py#L5354-L5363), and [batch-size transitions use that consumed count](https://github.com/NVIDIA/Megatron-LM/blob/4d67b0afe26f6b98f20ebb7186d49fad92b0a409/megatron/training/training.py#L5111-L5119).

For constant base LR `0.1`, rescale `0:0.5,100:1.0`, and 10-sample batches, one failed optimizer update before sample 100 leaves `num_steps=90` at 100 consumed samples. The next batch can use the larger batch size but still receive LR `0.05`, rather than `0.1`. Ordinary checkpoint restoration retains that discrepancy.

**Correction:** Give only the rescale lookup an actual consumed-sample position, synchronized at iteration boundaries including failed or explicitly skipped updates, and refresh the optimizer LR accordingly. Initialize/restore that position from restored training progress; do not reinterpret existing `num_steps` checkpoints or globally advance base warmup/decay on failed updates. Preserve standalone scheduler callers that currently advance through `step(increment)`. The exact interface and compatibility implementation require a decision, so no speculative patch is supplied.

**Preservation and acceptance — proposed, not run:** Simulate ten 10-sample batches with one unsuccessful update. Before the first batch beginning at consumed sample 100, LR must be `0.1` while the base successful-update position remains 90; repeat across save/restore at that boundary. With transition warmup 40, factors must be `0.5`, `0.75`, and `1.0` at consumed samples 100, 120, and 140 despite the skipped update. Retain current behavior when rescaling is disabled, existing no-skip hard-step/ramp boundaries, and [the iteration-clock assertion](https://github.com/NVIDIA/Megatron-LM/blob/4d67b0afe26f6b98f20ebb7186d49fad92b0a409/tests/unit_tests/test_training.py#L434-L447): iteration scheduling returns running batch size 256 even when actual samples seen are 3342; sample-based scheduling returns 3342.
