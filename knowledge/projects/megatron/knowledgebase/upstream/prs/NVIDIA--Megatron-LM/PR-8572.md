# [Inference] Make FlashInfer processed log-probs run-to-run deterministic

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8572) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes the processed log-probs of the FlashInfer sampling backend (`FlashInferSampling.log_probs_kernel`) bitwise run-to-run deterministic for top-k and top-p rows at any vocabulary size.

## Bug

With `sampling_backend='flashinfer'`, the processed log-probs (temperature, top-k, top-p) that RL consumes change between identical runs whenever a batch contains a row with top-k or top-p. We measured this on an H100 with FlashInfer 0.6.16.post3:
- 32K vocabulary: 27 of 63 identical reruns differed bitwise. The differences were in top-p rows whose `top_p` falls on a cumulative-mass boundary.
- 152K vocabulary: 31 of 31 reruns differed, top-k rows included.

Unfiltered rows were not affected, because they bypass the renorm kernels.

## Root cause

`log_probs_kernel` computed `softmax(logits / T)`, then `flashinfer.sampling.top_k_renorm_probs`, then `top_p_renorm_probs`. Neither renorm call is deterministic:
- **Top-p.** Since FlashInfer 0.6.7, `top_p_renorm_probs` runs the AIR radix kernel for vocabularies of 2048 or more. By default (`is_deterministic=False`) it builds its threshold histograms with float `atomicAdd` across several blocks per row. When a row's cumulative mass lies within rounding of `top_p`, the kept set can change from run to run. The sampling calls in the same class pass `deterministic=True`, but this call did not.
- **Top-k.** `top_k_renorm_probs` has no determinism switch. When a row does not fit in one CTA's shared memory, the row is split over several CTAs and their partial sums are added with a float `atomicAdd`. On H100 that happens with three or more CTAs, above about 115K entries, for example with 128K or 152K vocabularies. Megatron runs this stage on every filtered row, including top-p-only rows (`k = vocab`). So passing `is_deterministic=True` to the top-p call alone would not be enough.

## Fix

In `megatron/core/inference/sampling/flashinfer_sampling.py`:
- **Top-k** is applied to the logits with `flashinfer.sampling.top_k_mask_logits`, then softmax. This is what the joint `top_k_top_p_sampling_from_logits` kernel does with `filter_apply_order="top_k_first"`. The mask's pivot comes from a radix select with integer counts, and the kept logits are copied unchanged. The result is deterministic in every supported FlashInfer version (one block per row in 0.5, integer histograms from 0.6). The kept set is the same as before, up to exact float ties.
- **Top-p** passes `is_deterministic=True` to `top_p_renorm_probs` whenever the installed FlashInfer accepts that parameter (0.6.7 and later). `__init__` checks the function's signature once, so rc, dev and backport builds are handled correctly too. Versions without the parameter renormalize with one block per row and a `cub` block reduction, which is deterministic.

The number of kernels is unchanged (mask, softmax, top-p renorm instead of softmax, top-k renorm, top-p renorm). No host syncs are added.

## Tests

- New `tests/unit_tests/determinism/kernels/test_flashinfer_sampling.py`, registered in the determinism manifest in place of the old exemption:
  - `test_log_probs_replay_bit_exact` replays `log_probs_kernel` bit-exactly under side-stream contention in two cases. The first has a 32K vocabulary, with 16 rows whose `top_p` lies on a cumulative-mass boundary, 32 random top-p rows and 16 unfiltered rows (32 replays). The second has a 152K vocabulary with top-k=50 rows and top-p rows (8 replays). Unfiltered rows must equal `log_softmax` exactly.
  - `test_log_probs_request_deterministic_top_p_renorm` checks that, with the real FlashInfer, the sampler passes the switch whenever FlashInfer has it.
  - `test_default_renorm_is_not_bit_exact` contains negative controls for FlashInfer's default `top_k_renorm_probs` at 152K and default `top_p_renorm_probs` on the boundary rows. Both are non-strict `xfail`. An XPASS shows that the replay test is sensitive on the setup at hand, and a FlashInfer that stops racing, or a GPU that splits rows differently, does not fail CI.
- New in `tests/unit_tests/inference/contexts/test_dynamic_context.py`:
  - `test_flashinfer_filtered_log_probs_match_torch_filters` checks that top-k, top-p and top-k+top-p rows keep the same set as TorchSampling's top-k then top-p filters, and that their values match `log_softmax` of the filtered logits.
  - `test_flashinfer_log_probs_request_deterministic_top_p` runs on CPU with stand-in FlashInfer functions, with and without the parameter. It checks that the switch is passed exactly when the signature has it. It fails on main.
- `python3 tools/check_kernel_determinism_coverage.py --base-ref origin/main` passes.

**H100 results** (CI image, FlashInfer 0.7.0.post1), for the first commit:
- The new tests fail on main in 3 cases: both `test_log_probs_replay_bit_exact` cases ("not bit-exact across replays") and `test_log_probs_request_deterministic_top_p_renorm`.
- With this PR they pass, 6 of 6. That includes both negative controls, which observed the races.
- The neighbor tests pass: `test_flashinfer_no_op_filter_rows_get_exact_log_softmax`, `test_flashinfer_sample_kernel_dispatch` and `tests/unit_tests/determinism/kernels/test_manifest.py`.
On H100 in the CI image (rerun at this PR's head), the regression tests pass (8/8) and 5 fail on `main`. The neighbor tests pass.

The GPU tests need one GPU and FlashInfer, and skip otherwise.

## Notes for reviewers

- **TorchSampling boundary (existing, not changed here).** When a row's cumulative mass equals `top_p` exactly, TorchSampling's top-p filter keeps one more token than FlashInfer does. The cross-backend test uses `top_p` values away from such boundaries and does not pin this case.
- **Top-k selection.** Log-probs now select top-k on the logits, as the joint sampler and TorchSampling do. The top-k-only sampling kernel selects on fp32 probabilities, so the two can differ only when distinct logits round to equal probabilities at the k-th boundary.
- **Performance.** The cost of `is_deterministic=True` (uint64 instead of float histograms in the top-p renorm) on the log-prob path was not measured.
