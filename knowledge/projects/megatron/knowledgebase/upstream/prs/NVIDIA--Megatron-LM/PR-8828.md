# [MFSDP] Reuse model-weight storage on singleton DP axes

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8828) · state: open · merged: False

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

## What does this PR do?

On singleton DP axes, sharded model weights already contain the values needed by the replicated compute view. Reuse that storage instead of allocating an unsharded buffer and gathering the same values into it.

`DBuffer.can_redistribute_locally()` checks whether the target placements can be satisfied by a local view; `QuantizedDBuffer` delegates the check to its rowwise data buffer. The parameter group creates `model_weight.view(unsharded_placements)` when possible. Weight lifecycle checks use `is_alias_of()` so distinct views sharing storage retain the persistent weights and MXFP8 scale copies through unshard/reshard.

## Related work

This PR covers model weights. #8949 separately skips gradient packing when inner reduction is unnecessary. **Both target `main`, have no dependency on each other, and can merge in either order.** The gradient path does not use the buffer APIs added here.

The two PRs separate the weight and gradient optimizations discussed in #8393. No isolated performance gain is claimed for this weight-only change.

## Validation

Agent-run checks of the weight-only branch in the development CI Docker image on two RTX A6000 GPUs:

- Buffer APIs, parameter storage lifetime, and existing training parity: **9 passed per rank**, eight MXFP8 cases skipped.
- Singleton-inner HSDP/HFSDP training parity: **32 passed per rank**, covering both `zero_grad` modes, one/three microbatches, serial/overlapped outer reduction, and padded/unpadded layouts.
- Black, isort, Pylint, and Ruff passed; optional mypy was unavailable.

Dedicated buffer API tests cover local redistribution and alias identity across storage release/reallocation. The MXFP8 training test covers inner DP sizes 1 and 4, but MXFP8 hardware execution and larger meshes remain unverified on Ampere.

Hi @wujingyue 
We benchmarked both PRs on DeepSeek V4 Flash (128 GB200, EP64, expert inner DP=1, outer DP=2). #8393 gives about +2.3% throughput over the baseline, and #8828 about +1.0%.

The difference comes from how the two pipelines handle the expert gradients after the first microbatch. 
```
baseline: BF16 grad -> pack into FP32 buffer -> reduce-scatter -> scale -> add into main grad
#8393:    BF16 grad -> fused scale+add into main grad            (1 pass: add_(grad, alpha=scale))
#8828:    BF16 grad -> cast to FP32 -> scale -> add into main grad  (3 passes)
```
