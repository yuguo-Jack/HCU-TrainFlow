# [Core][MoE][BatchInvariant] Run TE grouped-tensor and op-fuser expert GEMMs on DeepGEMM under deepgemm/triton batch invariance

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8866) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Under `batch_invariant_backend="deepgemm"` or `"triton"`, TE MoE experts on the GroupedTensor path (`moe_use_grouped_tensor=True`) and on the op-fuser path (`use_transformer_engine_op_fuser=True`) silently ran TE's cuBLASLt grouped GEMM instead of the batch-invariant DeepGEMM grouped GEMM. This PR routes TE's grouped GEMMs through DeepGEMM wherever TE binds them, and fails closed if one cannot be replaced. That makes the grouped-tensor expert path batch-invariant rather than rejected. The op fuser's experts are covered too, but the op fuser is not yet batch-invariant as a whole: its dense linears and RMSNorm are a separate PR (see "Not covered here").

**Bug.** Under `deepgemm` and `triton`, batch-invariant mode makes TE's expert GEMMs batch-invariant by rebinding TE's `general_grouped_gemm` to a DeepGEMM grouped-GEMM dispatcher (`_te_patch_general_grouped_gemm`). It did this in `module.grouped_linear`, `cpp_extensions` and `cpp_extensions.gemm`. TE 2.20.2 has a second grouped-GEMM entry point, and a fourth module that binds both:
- **Grouped tensors.** With `moe_use_grouped_tensor=True`, `GroupedLinear` takes its GroupedTensor path wherever TE supports it: BF16 on Hopper with cuBLASLt 13.4 or later, or on Blackwell. That path calls `general_grouped_gemm_for_grouped_tensor` for forward, dgrad and wgrad. Megatron never rebound that name.
- **Op fuser.** `te.pytorch.ops.GroupedLinear`, which Megatron builds for op-fuser experts, imports both names into `ops/basic/grouped_linear.py`, which Megatron did not patch. On SM90+ BF16 it takes the GroupedTensor path. TE's fused grouped-MLP ops are MXFP8/NVFP4-only, so BF16 op-fuser experts always run these basic ops.

Both ran TE's device-metadata cuBLASLt grouped GEMM with TE's full workspace. `te_native` accepts that kernel only on SM100 with cuBLASLt 13.5.1 and raises elsewhere (`_get_te_native_grouped_workspace`). Under `deepgemm` and `triton` it ran silently, which breaks the patch's own contract ("Unsupported calls fail rather than silently using a kernel that is not guaranteed batch invariant"). On H100 in the CI image, all four combinations (each backend with each path) ran TE's grouped GEMM and never DeepGEMM's.

Affected: batch-invariant MoE with TE experts under `deepgemm` or `triton`, with grouped tensors or the op fuser. That includes `transformer_impl="inference_optimized"`: `InferenceGroupedMLP` builds the same TE `GroupedLinear` experts and delegates to `TEGroupedMLP.forward` outside inference mode (training and log-prob forwards in colocated RL). `te_native` is unchanged.

## Fix

- **Every binding, fail closed.** `enable_batch_invariant_mode` replaces TE's two grouped GEMMs, `general_grouped_gemm` and `general_grouped_gemm_for_grouped_tensor`, by identity rather than from a list of modules. Every global of a loaded `transformer_engine` module that *is* one of them is rebound, whatever its name. At TE 2.20.2 that covers `module.grouped_linear`, `cpp_extensions`, `cpp_extensions.gemm`, `ops.basic.grouped_linear` and `ops.fused.grouped_mlp`. Modules imported later bind the replacement from `cpp_extensions`. If any TE module still binds an original afterwards, enabling raises instead of letting it run TE's cuBLASLt grouped GEMM. Disabling restores the originals the same way, including in modules imported since. Because the fix sits at TE's GEMM entry points, it covers every `transformer_impl`.
- New `_te_grouped_tensor_gemm_patched` runs the same DeepGEMM grouped GEMMs as the legacy dispatcher, and so produces the same bits:
  - **Forward (`TN`) and dgrad (`NN`)** take each group's row count from the GroupedTensor's device metadata (`first_dims`). `_bf16_grouped_gemm_device_counts` scatters each group's rows into its own DeepGEMM-aligned block of a buffer sized for any counts, runs `m_grouped_bf16_gemm_nt_contiguous`, and gathers the rows back. This needs no host read, so the GroupedTensor path stays CUDA-graph safe. Discrete weights and a single grouped weight are both handled, and so are the grouped bias and the op fuser's per-token scaled bias.
  - **Rows past the groups' total** (a caller's capacity buffer) are tagged `-1`, are not computed, and keep their previous output values, as TE's contract says.
  - **Wgrad (`NT`)** runs DeepGEMM's K-grouped GEMM over the same zero-padded block layout.
    - On Blackwell it passes the device group sizes as DeepGEMM's psum layout, so it stays on the device.
    - On Hopper DeepGEMM requires the group sizes on the host (`ks_cpu`, `csrc/apis/gemm.hpp:675-679`), so they are copied there. This is a host sync, and the one part that is not CUDA-graph safe. The legacy path syncs there too, and Megatron's `TEGroupedMLP` already syncs in forward under batch invariance (its alltoall padding calls `tokens_per_expert.tolist()`).
    - The result stays fp32 and is rounded only for a bf16 target. Accumulation into an fp32 `main_grad` is therefore exact; before, the legacy path rounded to bf16 first, and its accumulation is exact now too.
  - Quantized operands, `alpha`/`beta`, and `grad=True` raise instead of falling back to TE's kernel.
- The legacy dispatcher also accepts the op fuser's dgrad and wgrad calls, which do not pass `grad=True`.
- **Config.** `TransformerConfig` now rejects MXFP8 `inference_optimized` MoE under `deepgemm`/`triton`, with a message pointing to `te_native`. Outside inference mode (colocated RL training and log-prob forwards) those experts run TE GroupedLinear, and the DeepGEMM grouped dispatchers take BF16 only, so this configuration would otherwise crash at its first training-mode forward. The previous commit's grouped-tensor and op-fuser rejections stay reverted. The `te_native` op-fuser assertion is unchanged.
- The inference user guide now says what `moe_use_grouped_tensor=True` does under `deepgemm`/`triton`, and that MXFP8 experts need `te_native`.

**Not covered here.** The op fuser's dense MLPs (`TEFusedMLP`, built from `te.ops.BasicLinear`) call `general_gemm` through `ops/basic/basic_linear.py`, which the dense GEMM patch does not rebind. That patch also ignores `accumulate`, `alpha` and `beta`. The op fuser's `te.ops.RMSNorm` binds `tex.rmsnorm_fwd` (`ops/basic/rmsnorm.py:15`), outside the batch-invariant norm patch. So `use_transformer_engine_op_fuser=True` is still not batch-invariant under `deepgemm`/`triton` for dense layers and norms, and the guide's "Keep `use_transformer_engine_op_fuser=False`" stays. Both gaps are fixed by the follow-up PR stacked on this one (`fix/bi-op-fuser-dense`, P4-N3), which extends the same fail-closed binding mechanism to the dense GEMM and the norm.

**Relation to #8708.** #8708 makes the aten GEMMs that a backend leaves native honor batch invariance. This PR applies the same rule (every GEMM entry point honors the backend) to TE's grouped expert GEMMs. They touch different code and merge cleanly.

## Tests

In the dev CI image, the new tests assert that DeepGEMM and TE's GroupedTensor path (cuBLASLt 13.4 or later on H100) are present, so they fail rather than skip without them. In the LTS image, which ships neither, they skip. `is_lts_ci_image()` decides which image is running. It compares `NVIDIA_PYTORCH_VERSION` with the LTS release, read from `docker/.ngc_version.lts`, as the suite's other LTS skips compare the NGC release. The whole of `test_moe_batch_invariant.py` now follows the same rule.
- `tests/unit_tests/transformer/moe/test_moe_batch_invariant.py` (1 GPU):
  - `test_te_grouped_linear_grouped_tensor_path_matches_legacy_kernels[deepgemm|triton x 7 variants]`, also on GB200 (`launch_on_gb200`). A `TEGroupedLinear` with `moe_use_grouped_tensor=True` must give bit-identical forward output, input gradient and weight gradients to the legacy kernels. The variants:
    - 256-aligned splits, and unaligned splits with an empty expert;
    - a single grouped weight;
    - discrete biases;
    - a single grouped weight with a single grouped bias;
    - wgrad accumulated in fp32 into a pre-filled `main_grad`, with discrete or single grouped weights.
    TE builds a single grouped weight or bias only when `NVTE_GROUPED_LINEAR_SINGLE_PARAM=1`. Without it, TE warns and falls back to per-expert `weight{i}`. The single-weight variants therefore set the variable, as the suite's other single-grouped-weight tests do. They assert that the module holds a GroupedTensor `weight` (and `bias`) and that the adapter receives a GroupedTensor weight in forward and dgrad, and a GroupedTensor gradient in wgrad.
    Every TE cuBLASLt grouped GEMM is made to raise, and DeepGEMM's M- and K-grouped GEMMs are counted. Fails on `main`.
  - `test_te_op_fuser_grouped_linear_runs_batch_invariant_grouped_gemm[deepgemm|triton x none|bias|scaled-bias]`: `te.pytorch.ops.GroupedLinear` forward and backward run DeepGEMM with TE's grouped GEMMs forbidden, including its grouped bias and per-token scaled bias, bit-identical to the legacy kernels. Fails on `main`.
  - `test_grouped_gemm_device_counts_matches_host_counts`, also on GB200. The device-count M-grouped GEMM and wgrad give the host-count kernels' bits, so on GB200 the psum wgrad is checked against the host-count kernel. Rows past the groups' total keep their values and are left out of wgrad. Fails on `main`.
  - `test_batch_invariant_mode_rebinds_every_te_grouped_gemm`: `ops.fused.grouped_mlp` and a probe module binding both grouped GEMMs under other names are rebound on enable and restored on disable. Fails on `main`.
  - `test_unreplaceable_te_grouped_gemm_binding_fails_closed`: a TE module whose binding cannot be replaced makes the patch raise, naming it. Fails on `main`.
- `tests/unit_tests/inference/test_moe_dispatching_and_routing.py::test_config_rejects_mxfp8_experts_outside_te_native[deepgemm|triton]`: MXFP8 `inference_optimized` MoE under `deepgemm`/`triton` is rejected at construction. Fails on `main`.
- `tests/unit_tests/determinism/kernels/test_te_wrappers.py::TestTEWrappers::test_te_grouped_linear_grouped_tensor_batch_invariant_replays[deepgemm|triton]` is a neighbor test, not a regression test: on `main` it replays TE's own kernel and can pass. It checks that the grouped-tensor path replays bit-exactly under side-stream contention. It skips in the LTS image and is registered for `batch_invariant_kernels.py`.
- `test_moe_batch_invariant.py::test_tegroupedmlp_per_token_invariance_across_batch_sizes[True]` is also a neighbor check, not a regression test: it runs with the rest of `test_moe_batch_invariant.py`. The full `TEGroupedMLP` (alltoall, 256-row padding) on grouped tensors must keep a target token's bits across co-batches.

The adapter's layout, trailing rows, bias, scaled bias, and the Hopper and Blackwell wgrad paths were checked on CPU against the legacy dispatcher, using fakes of TE's GroupedTensor and DeepGEMM. The binding mechanism was checked on CPU with fake TE modules. The first GPU runs (H100 and GB200, at 4f219b528) passed everything except the six single-weight variants, including the GB200 check of DeepGEMM's psum K-grouped GEMM against the host-count one. Those failed because the test did not set `NVTE_GROUPED_LINEAR_SINGLE_PARAM`, so TE built per-expert weights. The test now sets it.

At this head, on H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), the regression tests pass (28 cases). On GB200 in the CI image (`mcore_ci_dev:main`, aarch64, 2026-11-02), the two GB200 tests pass (18 cases), including the single-weight variants. On `main`, on both GPUs, the only evidence is an import failure: `test_moe_batch_invariant.py` imports `is_lts_ci_image`, a test helper this PR adds, so no test runs. The "Fails on `main`" notes above have not been checked on GPU. The step 3 GPU repro of this finding (R04-F2) did reproduce it on `main` on H100 (4 of 4 cases, controls passing): the grouped-tensor module path and the op-fuser path bypass the batch-invariant grouped GEMM under `deepgemm` and `triton`. That repro saw no bit-level effect on H100. The neighbor tests (`test_te_wrappers.py::TestTEWrappers::test_te_grouped_linear_grouped_tensor_batch_invariant_replays`, `test_moe_batch_invariant.py`, `test_moe_dispatching_and_routing.py`) pass on H100 (100 cases, 9 skipped).
