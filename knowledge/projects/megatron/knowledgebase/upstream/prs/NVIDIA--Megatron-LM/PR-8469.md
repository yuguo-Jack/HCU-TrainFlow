# Checkpoint domains for multi-site training

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8469) · state: open · merged: False

## Original PR description

This PR was prompted by a larger effort to improve support for multi-site training (https://github.com/NVIDIA/Megatron-LM/issues/8482), but is relevant to single-site training as well.

### Problem statement

Megatron's default checkpointing logic may fail when training across multiple sites. The checkpoint files will be scattered across the different sites' filesystems (in the same-named path on each), guaranteeing at least one `FileNotFoundError` on checkpoint load. (See below for a more concrete example.) 

### How this PR fixes it

This PR adds "checkpoint domains" to Megatron's distributed checkpointing API. A checkpoint domain scopes save/load collectives and shard writer/reader selection to a supplied process group. By setting these domains to reflect site localities, callers can avoid the aforementioned problem.

### Additional details

This API change specifically focuses on the default path (`torch_dist`, `fully_parallel_save`). Given that this is already an invasive change to a complex part of Megatron, I'm hoping this is an acceptable boundary to set. (To be clear, this is a "validation boundary"; the feature may already work more generally.)

It remains to connect this new API to Megatron’s training checkpoint flow. To reduce complexity, this logic has been refactored into https://github.com/nick-knight/Megatron-LM/pull/1, stacked on this PR. Once this PR merges, the stacked PR will be rebased onto `main`, and become a PR to the upstream repo (vs. my fork).

### Example of failure

As an example of the type of failure this addresses, consider a two-site job. (All ranks belong to one `torch.distributed` job.) To avoid distractions, let's assume there is one complete distributed-optimizer instance at each site. Suppose all ranks pass the valid path `/scratch/checkpoints` as the save path, but `/scratch` is a separate filesystem at each site.

In the default (`torch_dist`) checkpointing path, with the default ("fully parallel") save strategy, Megatron may (e.g.) assign one tensor shard to a writer at site A and another to a writer at site B. PyTorch DCP treats those writes as one checkpoint: its global coordinator collects the write results and writes a single `.metadata` file listing both shard files. Megatron also writes the checkpoint tracker from global rank 0. Suppose that rank is at site A. The resulting directories might look like this (other files omitted):

```
Site A: /scratch/checkpoints/iter_0000100/
        .metadata  __0_0.distcp

Site B: /scratch/checkpoints/iter_0000100/
        __1_0.distcp
```

The save could report success, because both writers completed and their results reached the coordinator. But neither site has a standalone checkpoint. On restart, a worker at A can read `.metadata` but gets a file-not-found error when it needs the shard in `__1_0.distcp`; a worker at B cannot even read `.metadata`. PyTorch’s reader resolves shard filenames within its local checkpoint directory. 

In summary, to produce an independently loadable checkpoint at each site, each site must select local writers for all required shards and finalize its own metadata and tracker.
