# [Inference][SSM] Check batch-invariant SSM kernel pinning against the installed autotune policy

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8700) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes the batch-invariant check for SSM layers ask what actually pins their Triton kernels, the installed autotune policy, and runs it where that policy is in force.

**Bug.** `TransformerConfig` asserted `use_deterministic_mode()` when `batch_invariant_mode` was on for a hybrid model, and its message asked for `MAMBA_DETERMINISTIC=1`. Since #6076 neither decides whether the SSM kernels are pinned: the installed `megatron.core.tuning` policy does, when each kernel launches. As a result:
- A user who follows the message relaunches with `MAMBA_DETERMINISTIC=1` and is rejected again with the same advice.
- `--triton-autotune-mode pinned` and the README's `install(..., deterministic=True)` pin every SSM kernel, but the check rejected them.
- `torch.use_deterministic_algorithms(True)` set after a default `install()` passed the check while the policy stayed `auto`. SSM kernels imported earlier then keep Triton's timed per-shape autotuning, which is what the check exists to prevent.

**Fix.**
- `AutotunePolicy.covers(module)` and `megatron.core.tuning.pins(*modules)` report whether the installed policy pins the kernels a module defines: mode `pinned`, with the module in the policy's scope. The adapter's own scope test uses `covers` as well.
- `assert_ssm_kernels_pinned()` in `megatron/core/ssm/ops/common/determinism.py` requires `pins("mamba_ssm", "megatron.core.ssm.ops")`. `MambaMixer` calls it when it is built with `batch_invariant_mode`. The message shows the installed policy and names every remedy:
  - `--deterministic-mode`;
  - `--triton-autotune-mode pinned`, keeping `mamba_ssm` and `megatron.core` in `--triton-autotune-modules`;
  - without the training initializer, `install(..., deterministic=True)` or `install(AutotunePolicy(mode='pinned'))` before building the model.

  It also says that the `deterministic_mode` config field, `torch.use_deterministic_algorithms(True)` and `MAMBA_DETERMINISTIC=1` do not install a policy.
- `TransformerConfig` no longer runs the check. `pretrain_hybrid.py` and `train_rl.py` build the model config before `initialize_megatron` installs the policy, so a config-time policy check would reject `--deterministic-mode`. The mixer is built after the policy is installed. A hybrid model without Mamba layers runs no SSM kernel and no longer needs pinning.
- The `deterministic_mode` field keeps its role: `initialize_megatron` passes it to `install`, which pins the policy. Config construction does not install process-wide state, and `test_model_config_does_not_install_a_policy` already guards that. Applications that skip the training initializer call `install` themselves, as the message and `megatron/core/tuning/README.md` now say.

**Tests.**
- `tuning/test_autotune_config.py` covers each remedy the message names, applied as intended: the CLI flags go through the training parser and `initialize_megatron`'s `install` call, then the README recipe, then `install(AutotunePolicy(mode='pinned'))`. Before each one, the check rejects with a message that names it; after it, the check passes. Five states are rejected: the default training policy, torch's flag set after `install`, `MAMBA_DETERMINISTIC=1`, `--deterministic-mode` with an explicit `--triton-autotune-mode auto`, and a pinned policy whose modules exclude the SSM packages. Runs on CPU.
- `transformer/test_transformer_config.py`: a batch-invariant hybrid config builds with no policy installed and no deterministic flag, as training requires. It fails on `main`.
- `ssm/test_mamba_mixer.py`: building a batch-invariant `MambaMixer` fails under the `auto` policy and succeeds under the pinned one.
- `ssm/test_mamba_train_gen_parity.py`: the two scan parity tests now run under a pinned policy, through a new `pinned_autotune` fixture. Before, they skipped unless `MAMBA_DETERMINISTIC=1` was exported, and that variable pinned only the `mamba_ssm` side.
- `test_batch_invariant_mamba_prefix_caching.py` and `test_hybrid_moe.py::TestDynamicInferenceNVLS::test_batch_invariant_prefill_matches_full_forward` build batch-invariant Mamba layers; they now use the same fixture.
- `determinism/kernels/test_ssm_kernels.py`: each pinning assertion also checks that `pins()` agrees with the choices the adapter made.

**Results.**
- On H100 in the CI image, the regression tests fail on `main` (11 cases fail, 2 skip). The config test fails with the old assertion, and the remedy tests fail because the check does not exist there.
- With this PR, 13 regression cases pass, including all three parity tests. The mixer test failed in that run because it built the mixer without seeding the model-parallel CUDA RNG. The test now seeds it. In the rerun (dfw 21008435), all 14 regression cases pass with this PR; on `main`, 11 fail and 2 error (the check does not exist there), and the neighbor tests pass (prefix caching 4, `test_ssm_kernels.py` 57).
- Neighbors pass on H100: `test_batch_invariant_mamba_prefix_caching.py` (4 tests) and `determinism/kernels/test_ssm_kernels.py` (57 tests).
- `test_hybrid_moe.py::TestDynamicInferenceNVLS::test_batch_invariant_prefill_matches_full_forward` fails the same way on `main` and with this PR ("Tensor-likes are not equal"). That failure predates this PR; the test is marked `flaky_in_dev` (#7958). This PR only adds the fixture the test now needs to build its model.
