# [Inference][MLA] Run dynamic MLA decode with FlashInfer on Blackwell, where FlashMLA has no dense decode

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8873) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Fixes a crash on every decode-only step of dynamic-batching MLA on Blackwell (SM100 and SM103) by running those steps with FlashInfer's MLA decode kernel.

**Merge order (required).** Stacked on https://github.com/NVIDIA/Megatron-LM/pull/8571 (s8), whose `_absorbs_cached_latents` this builds on. The branch carries #8571 and current `main` (merged through #8571's branch); the commits after #8571 are new. Merge in this order:
1. https://github.com/NVIDIA/Megatron-LM/pull/8701. `launch_on_gb200` tests also run in H100 CI, and there `TestMLAAbsorbedDecode` needs FlashMLA's SM90 kernels, which the dev image builds only with #8701. Before it, all of its H100 cases fail.
2. The KV page initialization PR (`fix/kv-page-init`). The latent pool is `torch.empty`. TRTLLM-GEN's 128-token tiles load the rows past each request's length in its last page and in MTP lookahead pages. Masked probabilities (0) times NaN bit patterns from recycled memory give NaN logits, silently. That PR zeroes acquired pages.
3. #8571 (s8), then this PR. The FA4/quack lock PR (`fix/fa4-quack-lock`, G1) must also be in first: layers without an absorbed kernel decode through FA4 on Blackwell, which does not compile in the CI image without it.

**Bug.** Dynamic MLA caches latents (`cache_mla_latents`) and runs each decode-only step as absorbed attention over them. `flash_decode_and_prefill` picked FlashMLA's `flash_mla_with_kvcache` for every MLA layer by config type alone, with no device or `HAVE_FMLA` check.
- At the pinned FlashMLA (`b7643bd`), dense decode starts with `TORCH_CHECK(false, "Dense decode MLA is only supported on SM90a architecture")` on any other device. Its SM100 kernels are sparse FP8 only.
- Upstream FlashMLA has since removed dense decode, so no FlashMLA upgrade helps.
- The first decode-only step therefore raises on B200, GB200, B300 and GB300 (reproduced on GB200), and raises `TypeError` on any device without `flash_mla`. This is the default path of every dynamic MLA model.

**Fix.** The absorbed decode kernel is chosen per device when the layer is built (`get_absorbed_mla_decode_kernel`, stored as `MultiLatentAttention.absorbed_decode_kernel`). `_absorbs_cached_latents`, which already decides how cached latents are read, absorbs only when a kernel exists:

| Device and layer | Decode-only step |
|---|---|
| SM90 | FlashMLA, unchanged |
| SM100, SM103: bf16, up to 64 or a multiple of 64 heads per rank, FlashInfer's prebuilt kernels installed | FlashInfer `trtllm_batch_decode_with_kv_cache_mla` (FlashInfer 0.7.2.post1, which `main`'s `uv.lock` pins) |
| Anything else | Unabsorbed: up-project the cached latents and run the varlen kernel, as batch-invariant mode already does, with a warning when the layer is built |

The FlashInfer call follows the 0.7.2.post1 source:
- It reads Megatron's `[pages, 64, 576]` bf16 latent pool, int32 `[B, max_blocks]` block table and int32 lengths as they are. The query is `[B, S, H, 576]`, so MTP's S > 1 works.
- `bmm1_scale` is MLA's `softmax_scale`, including YaRN's mscale².
- The attention sink goes in as `sinks` (fp32), which the kernel adds to each head's softmax denominator. FlashMLA's LSE post-correction is not needed.
- `backend="trtllm-gen"` is explicit. `"auto"` also considers a CuTe DSL kernel and then requires the block table to span a multiple of 128 tokens, which MTP's lookahead block breaks.
- CUDA graphs: `max_seq_len` is the block table's capacity, which stays fixed across replays and also bounds MTP's lookahead past `max_sequence_length`. The graphed `max_seqlen_k` does not, and graph-warmup steps run eagerly with it, so eager steps use the capacity too. The 128 MiB workspace is one per device, allocated when the layer is built, before the KV cache and any capture. The split-KV semaphores are a persistent zeroed buffer per device (the kernel resets them after each launch), allocated outside capture. FlashInfer would otherwise allocate and zero one on every call. There is no host sync.

**Prebuilt kernels, locked; no download or compile at a decode step.** FlashInfer's TRTLLM-GEN decode runs prebuilt cubins (`flashinfer-cubin`) through a compiled launcher, the `fmha_gen` module of a per-GPU `flashinfer-jit-cache` provider. Without them at flashinfer-python's exact version, FlashInfer's first call downloads the cubins and nvcc-compiles the launcher. That call happens inside CUDA-graph warmup: it fails without network access and otherwise stalls for minutes.
- **Locked.** A dependency group, `flashinfer_kernels`, pins flashinfer-python, flashinfer-cubin, flashinfer-jit-cache and its SM90/SM100/SM103 providers (`sm90a`, `sm100a`, `sm103a`), all at 0.7.2.post1, with a sha256 per wheel in `uv.lock`. The kernels must match flashinfer-python exactly, so the six pins move together.
  - The wheels come from FlashInfer's own indexes (`https://flashinfer.ai/whl` and `.../whl/cu130`), declared `explicit` and pinned per package in `[tool.uv.sources]`.
  - The jit-cache wheel depends on every architecture's provider (six on x86_64, eight on aarch64). `override-dependencies` drops the five the CI GPUs do not use, with the `sys_platform == 'never'` pattern pyproject already uses for torch. uv also needs index sources for the overridden packages, so all eight are pinned there.
  - It is a group, not a published extra, because sources do not reach published wheel metadata.
- **Installed through the lock.** The dev Dockerfile adds `--group flashinfer_kernels` to its locked `uv sync` (not for the LTS image), so the wheels are hash-checked and cached with the rest. `uv.lock` is regenerated with `uv lock` in the CI container; this PR does not include that regeneration yet. Any later re-sync in the container must pass the group, or uv removes the kernels.
- **Checked as FlashInfer's loader sees them.** The layer picks FlashInfer only if `missing_flashinfer_prebuilt_kernels` (`megatron/core/inference/utils.py`) finds nothing missing. That check follows `flashinfer.jit.env`, so FlashInfer's version rule and its `FLASHINFER_CUBIN_DIR` and `FLASHINFER_DISABLE_VERSION_CHECK` overrides apply. It requires three things:
  - a jit-cache provider covering this GPU at FlashInfer's version;
  - a prebuilt `fmha_gen` for it;
  - every file in the TRTLLM-GEN FMHA checksum manifest, in the cubin directory FlashInfer resolved: flashinfer-cubin, `FLASHINFER_CUBIN_DIR`, or a cache that `flashinfer download-cubin` filled.
- An H100-only kernel install on a GB200, a shim without providers, or a partial download cache therefore gives no kernel and a warning that names what is missing. Nothing is compiled at model build. The FlashInfer MoE backend's construction check (`check_flashinfer_jit_cache_installed`) now uses the same helper. Before, it accepted any flashinfer-jit-cache version, which FlashInfer ignores before JIT-compiling.

**Padding slots.** CUDA-graph-padded decode steps contain padding requests with KV length 0. On GB200, TRTLLM-GEN leaves non-finite values in their output rows at 16, 24 and 48 heads per rank (seen in an earlier GB200 run of this PR). Those rows flow on into later norms and MoE routing. After either absorbed decode kernel, `flash_decode_and_prefill` therefore zeroes every output row from `cu_seqlens_q[-1]` on. Padding requests come last and have no query rows, so that count marks where they start. The zeroing uses the existing `zero_padding_rows` kernel: it reads the count on device, stores only to the padding rows, adds no host sync, and replays correctly in CUDA graphs.

**Rows a decode kernel may load past a request.** TRTLLM-GEN loads KV in 128-token tiles. For a request with an odd page count, the last tile also loads the block-table entry after its last page. That entry is the context's dummy block, which also fills the rows of padded requests. Padding tokens append their latents into the dummy block, and those latents can be non-finite: padding rows of an attention output are left unwritten. Masked probabilities (0) times NaN rows give NaN. The dynamic context now writes zeros over the latent pool's dummy block after every latent append, so it is zero whenever a kernel reads it. The rows past a request's length in its own last page are zeroed when the page is acquired (the KV page initialization PR, required first) or hold earlier finite latents. Routing padding writes to a separate scratch block, instead of the per-append fill, was considered. It would need a second reserved block in the allocator that MHA and Mamba share, and MTP's write maps also target the dummy. The fill stays: one 72 KiB memset per MLA layer per step, captured in CUDA graphs.

**Layers without an absorbed kernel** decode unabsorbed: each decode step up-projects the layer's whole latent pool (every page, not only active requests) to keys and values and runs FlashAttention over them, as a mixed step does. This makes decoding much slower. They are:
- fp16: TRTLLM-GEN's MLA cubins are bf16 and FP8 only, and FlashMLA's SM100 kernels are sparse FP8.
- 65 to 127 heads per rank, or a count above 64 that is not a multiple of 64: TRTLLM-GEN's head tiles are 8 to 64 heads, and it ships no MLA kernel for the 65 to 127 gap. FlashInfer's CuTe DSL MLA decode covers that gap, but it compiles each kernel with `cute.compile` at its first call (no prebuilt copies ship), which the no-compile rule above excludes. Common deployments are not affected: DeepSeek-V3/R1 at TP 1, 2, 4 or 8 has 128, 64, 32 or 16 heads per rank, and Kimi-K2 has 64 or 32.
- Latent shapes other than 512 + 64, devices other than SM90/SM100/SM103, or FlashInfer or its prebuilt kernels missing.

The warning names the reason, once per reason.

**Tests** (`tests/unit_tests/transformer/test_multi_latent_attention.py`):
- `TestMLAAbsorbedDecode` (`launch_on_gb200`) checks the kernel the device picked against a plain PyTorch absorbed-attention reference in fp32. On SM100/SM103 the layer must pick FlashInfer, with the resolver's reason as the failure message. On SM90 it must pick FlashMLA with its SM90 kernels. Only other devices skip. Every case runs at 16, 24, 48, 64, 128 and 192 heads. These cover the three TRTLLM-GEN kernel families, the padded head tiles for counts that are not powers of two (24 runs in a 32-head SwapsMmaAb tile, 48 in a 64-head KeepsMmaAb tile), and the 16- or 64-head tiling above 128 heads without the 2-CTA kernel. Each request must be within 2% relative L2. As in the dynamic context, the zero-length padding slot has no query rows, and its output must be zero:
  - six requests (3 to 300 latents, mostly odd page counts, one page-aligned, one padding slot), and a single request (FlashInfer's batch-1 kernels), with one or two (MTP) query tokens, with and without a learnable sink;
  - large finite values past each request and in the dummy page, which the tile past an odd page count spans;
  - a CUDA graph captured for one step and replayed for the next, with one request moving to a new page;
  - a decode-only step of the layer under a real `DynamicInferenceContext`.
- `test_latent_cache_dummy_block_stays_zero` appends NaN padding latents and checks that the dummy block is zero and the request's latents are in place. It fails without the context change. It runs on any CUDA device.
- `test_absorbed_mla_decode_kernel_follows_device` checks the per-device choice, the head rule, and that missing prebuilt kernels give no kernel.
- `tests/unit_tests/inference/test_flashinfer_prebuilt_kernels.py` checks the shared helper against a stand-in for FlashInfer's loader state:
  - complete installs pass;
  - an `sm90a`-only provider on SM100, no provider, no `fmha_gen`, a partial cubin cache and no cubins are each named;
  - the MoE check raises with the missing piece.
- #8571's dispatch tests are parametrized over the kernel, including none.
- `test_mla_flashinfer_decode_dispatch_sink_offset_replays` replays the FlashInfer decode bit-exactly under contention, at the same six head counts (64 requests up to 2K latents, learnable sink). It also checks that the sink changes the output and asserts that the layer picked FlashInfer on SM100/SM103. The determinism manifest notes are updated.
- On #8571's head the new tests fail (see the results below).

**GPU results.**
- On GB200 in the CI image (`mcore_ci_dev:main`, aarch64, 2026-11-02), with this PR's locked `flashinfer_kernels` group installed in the container, `TestMLAAbsorbedDecode` and the FlashInfer decode replay pass (72 cases). Their assertions cover causal masking of MTP's two query tokens; the 64- and 128-head kernel families, the padded 24- and 48-head tiles, 192 heads and the batch-1 variant; masking past an odd page count; zero output for padding slots of length 0; and bit-exact replay of the split-KV reduction with the persistent semaphore buffer. Before the padding-row zeroing, an earlier commit passed 61 of 72: the padding slots were non-finite at 16, 24 and 48 heads. On #8571's head all 72 fail, because that head has no `resolve_absorbed_mla_decode_kernel`, which the tests call (the replay test fails importing it).
- On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), with the same group installed and FlashMLA `b7643bd` built with its SM90 kernels on the job (as #8701 builds it into the image), the regression tests pass (90 cases: `TestMLAAbsorbedDecode` on FlashMLA, the dummy-block test, the per-device choice test and `test_flashinfer_prebuilt_kernels.py`). On #8571's head all 90 fail. `test_latent_cache_dummy_block_stays_zero` fails its assertion (the dummy block is not zero); the other 89 fail because that head has no `resolve_absorbed_mla_decode_kernel` or `_missing_flashinfer_prebuilt_kernels`. The neighbor tests pass: `TestParallelMLAAttention` (75 cases, 1 skipped), `TestMLALatentCacheDecode` (3 cases) and `test_runtime_cp_attention.py` (11 cases; 10 skipped: the six FlashInfer replay cases, which need SM100/SM103, and four CP4 cases, which need a world size divisible by four).

The Blackwell tests need FlashInfer's prebuilt kernels in the image: this PR's locked group, once `uv.lock` is regenerated. Without them they fail, by design.

**Conflicts.** This PR merges cleanly with `main`, #8571's head, the FA4/quack lock, #8701, KV page initialization and the MLA padding-rows PR. It has a one-line import conflict in `attention.py` with #8709 (n12): both add an import from `megatron.core.inference`; keep both. #8571's existing import conflict in the MLA test file with #8702, #8570 and #8703 is unchanged.

**Related.**
- #8701 gates `test_coordinator_backends_pairwise.py::test_routed_native_model_modes_match_direct[mla]` to SM90, since that row instruments only FlashMLA. Once both land, the row can cover Blackwell by instrumenting FlashInfer's decode.
