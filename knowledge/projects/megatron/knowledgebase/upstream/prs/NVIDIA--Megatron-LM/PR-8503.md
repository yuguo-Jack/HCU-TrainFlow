# fix(gtp+CG): prevent eager wgrad memory retention across CUDA graph replay

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8503) · state: closed · merged: True

## Original PR description

## Summary

<img width="1145" height="411" alt="image" src="https://github.com/user-attachments/assets/a55c643f-03df-4183-8081-d864e599916c" />


Fix eager weight-gradient buffers remaining allocated after training switches to CUDA-graph replay in GTP’s grouped reduce-scatter path.

On the DSV3 proxy at 256 GPUs, **this removes 22 retained allocations totaling 3.61 GiB**, without changing gradient precision, numerical results in the validation tests, or measured throughput.

## Root cause

The homogeneous grouped reduce-scatter path uses:

```
with torch.distributed._coalescing_manager(
    group=self.group, device=wgrads[0].device, async_ops=async_op
) as cm:
```
In the tested PyTorch revision, specifying device starts an additional device-coalescing scope around the existing reduce-scatter fast path:

1. The fast path creates an inner Work handle.
2. Closing the outer scope replaces it with another Work handle.
3. `cm.wait()` waits on the outer handle, **while the inner Work’s allocator-safety storage can retain the input tensors**.
4. After execution switches to CUDA-graph replay, those eager allocations can remain live because replay does not issue the host-side collective calls that would otherwise trigger deferred cleanup.

## Change

**Remove `device=` from the homogeneous grouped reduce-scatter scope:**

```
with torch.distributed._coalescing_manager(
    group=self.group, async_ops=async_op
) as cm:
```

**This preserves fast-path collective coalescing and retains the correct Work handle for waiting and cleanup.** Existing stream dependencies remain unchanged.

The FP32-accumulation path does not require this fix: its all-to-all operations use device coalescing without the redundant fast-path nesting that causes this retention.

## Validation

- Regression test on four GPUs: covers synchronous and asynchronous grouped reduce-scatter, input-storage release, and numerical correctness across CUDA-graph replay. The asynchronous lifetime assertion fails without the fix and passes with it.
- Training sanity check: 10 eager warmup steps followed by graph replay, 22 updates total. Retained eager wgrad storage stays at zero on all four ranks; final FP32 optimizer parameters match the reference bitwise.
- DSV3 proxy on 256 GB300 GPUs:

| Measurement | Before | After |
|---|---:|---:|
| **Retained eager wgrad allocations** | 22 / 3.61 GiB | 0 |
| Rank-0 device memory after update 20 | 163.52 GiB | 159.62 GiB |
| Throughput, TFLOP/s/GPU | 1,150.08 | 1,150.80 |
| Maximum sampled device memory | 184.43 GiB | 184.43 GiB |

The fix reduces persistent memory after warmup. The observed warmup peak is unchanged (that's further fixed in #8507), so these results do not establish a peak-memory reduction.

Tested with PyTorch 2.13.0a0+9186a08b2c.nv26.7.59513937, Transformer Engine 0ee1320e, CUDA 13.3, and NCCL 2.30.7.
