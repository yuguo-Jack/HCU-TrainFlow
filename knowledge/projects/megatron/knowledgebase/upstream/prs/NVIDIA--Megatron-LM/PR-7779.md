# Support CC 10.7 in CSA CuTe runtime compilation

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7779) · state: closed · merged: True

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

## What does this PR do?

On a device reporting CUDA capability `(10, 7)`, CSA/THD layout kernels fail in MCore's architecture whitelist before `cute.compile()` is called, even when the installed CuTe DSL supports the device. Add `(10, 7): "sm_100f"` to that runtime target map and update the unsupported-architecture message. Existing mappings and kernel code are unchanged.

This uses the previously exercised SM100-family target; it does not switch these kernels to explicit `sm_107*` code generation. Updating dependency wheels alone cannot change this MCore-owned runtime check.

## Validation

- A focused check executed the actual `_run_compiled_launch` function with mocked device capability and compiler boundary: `(10, 7)` reproduces the original exception, then reaches compilation with `--gpu-arch sm_100f` after this change. Existing 9.0/10.0/10.3 targets are unchanged and unsupported 8.0 remains rejected. This is dispatch validation, not GPU numerical execution.
- Repository `tools/autoformat.sh` with `BASE_REF=dev CHECK_ONLY=true`: Black, isort, pylint and Ruff passed. Its non-gating mypy step reports unavailable Torch/CUDA/CuTe imports in the isolated lint environment and the existing unannotated compile cache.
- The same target selection was exercised in separate Rubin component and training runs on an earlier DSV4 source snapshot with CUDA 13.4 and CuTe DSL 4.8. Those runs do not qualify current `dev`'s newer layout kernels.
- Pending on current `dev`: the existing `test_projected_compressor_graph_replay_updates_maps_and_backward` and `test_composed_cp_layout_maps_every_index_and_gradient_to_its_source` cases in `test_csa_thd_layout_kernels.py`, on a CC10.7 device. Kept as draft pending GPU validation.
