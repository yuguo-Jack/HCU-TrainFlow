# [Inference][MoE][Test] Make the batch-invariant NVLS test run in CI at EP = world size

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8879) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Repairs `tests/unit_tests/inference/test_batch_invariant_nvls.py` so that it runs in CI; it has never run. `test_moe_dispatching_and_routing.py` already runs batch-invariant NVLS layers at EP = world size in the same 8-rank bucket (`test_cuda_graph_batch_invariant_moe_layer_uses_ordered_rsv`, `test_batch_invariant_moe_matches_training`), with the `triton` backend and the ordered reduce-scatter-v. This file adds coverage those tests lack: the default `te_native` backend, target-row bit invariance across co-batch compositions with real routing, stale symmetric-buffer reuse after a wider step, and, with this PR, both combine collectives (ordered and multimem).

**Why it never ran.**
- **Renamed argument.** `_build_nvls_layer` calls `NVLSAllGatherVDispatcher.allocate_buffers(ep_group=...)`. #4743 renamed that argument to `tp_ep_group`, and #8426 then added this test with the old name. Every case raised `TypeError` before any kernel ran. Reproduced at 4 ranks on H100.
- **World size.** The module skipped unless the world size was exactly 4. The H100 `tests/unit_tests/inference/**/*.py` bucket launches 8 ranks, so every case skipped there. The file has no `launch_on_gb200` mark, so the 4-GPU GB200 bucket never selected it. No dedicated 4-rank launch exists, despite the comment that said one did.
- **Launch environment.** With the default `te_native` backend, the fixture required `CUBLASLT_WORKSPACE_SIZE=0` in the launch environment. No CI bucket sets it.

The determinism manifest lists the file as coverage for `moe_utils.py`, so that coverage was dead too.

## Changes (test only)

- **Process group.** The test passes the expert tensor-and-model parallel group (`get_expert_tensor_and_model_parallel_group()`) as `tp_ep_group`, as dynamic inference does. That group spans ETP x EP, and is the EP group here because ETP is 1.
- **World size.** Experts span every rank: EP 8 in the H100 inference bucket and EP 4 in the GB200 bucket. The file now carries `launch_on_gb200`, so GB200 selects it. It skips only where the NVLS Triton barrier cannot run, that is, when the world size is not a power of two greater than 1, as the sibling NVLS tests in `test_moe_dispatching_and_routing.py` do.
- **Token counts.** Per-rank counts follow the world size: idle peers, or peers with 32, 64 and 96 tokens in turn, within the 128-token per-rank buffers. The router-width test's peers gate 32, 64 or 96 tokens the same way. At EP 4 both reduce to the old counts. The oracle gathers one partial per rank.
- **No skips on CI hardware.** The H100 and GB200 CI images ship DeepGEMM 2.8.0, so the `torch` grouped-GEMM cases fail, rather than skip, when its bf16 grouped kernels are missing. Without NVLS multicast or symmetric memory, `NVLSAllGatherVDispatcher.allocate_buffers` raises, so every case errors. The module skips only at a world size where the NVLS barrier cannot run (not a power of two above 1); the CI buckets launch 8 and 4 ranks.
- **te_native precondition.** The `CUBLASLT_WORKSPACE_SIZE=0` launch requirement is dropped. That pin only matters for aten GEMMs, and this layer runs none: the router GEMM is TE's, whose workspace `te_native` starves when the mode is enabled, and the experts and the combine are Triton or DeepGEMM kernels.
- **Collectives in CI.** The target test is parametrized over the combine collectives valid on the device, in one process: `ordered` everywhere and `multimem` off Hopper (see the follow-up below). The fixture enables and disables the mode around each freshly built layer, so no fresh interpreter is needed. On GB200, CI therefore asserts that a target row's bits stay fixed across co-batches under the multimem in-switch reduction too. `MCORE_BI_TEST_BACKEND` still selects another GEMM backend for a dedicated launch; CI runs `te_native`. In this layer the backend changes only the router's TE GEMM, while the dispatch, experts and combine run the same kernels under every backend.

No recipe change is needed. The file stays in the H100 `tests/unit_tests/inference/**/*.py` bucket (8 GPUs), and GB200 picks it up through its marker (4 GPUs).

## Tests

The repaired file is the test: `test_nvls_empty_router_width` and `test_nvls_target_batch_invariance[idle|uneven x vllm|torch x collective]`. Acceptance: on 8 H100 ranks (the H100 CI world size), all 5 cases (`ordered` only) pass and none skip on every rank; on 4 GB200 ranks (the GB200 bucket, which selects the file through `launch_on_gb200`), all 9 (`ordered` and `multimem`) pass and none skip on every rank.

The following runs predate the follow-ups, when both collectives ran on every architecture. On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), at 8 ranks with no extra environment, all 9 cases pass on every rank and none skip. With `MCORE_BI_TEST_BACKEND` set to `triton`, and to `deepgemm`, all 9 also pass on every rank. The neighbor `test_moe_dispatching_and_routing.py::TestNVLSAllGatherVDispatcher` passes (31 cases, 9 skipped). On GB200 in the CI image (`mcore_ci_dev:main`, aarch64, 2026-11-02), at 4 ranks, all 9 pass on every rank and none skip. This was the file's first run on Blackwell.

The repair is test-only, so the repaired file should pass on `main` too; it was not run there. The run also launched `main`'s own file at 4 H100 ranks, expecting the `TypeError` above. It did not get that far: all 5 cases error at setup, on the file's `CUBLASLT_WORKSPACE_SIZE=0` precondition (the variable was unset), before `allocate_buffers` is called. So this run shows only a setup error on `main`; the `TypeError` is shown by the step 3 GPU repro of this finding (R09-F1), which reproduced it at 4 H100 ranks. The claim that every case skips at 8 ranks on `main` was not rerun.

## Follow-up: multimem oracle, Hopper, and merge with main

- **Merge.** The branch merges current `main`. The test already called `allocate_buffers(tp_ep_group=...)`, #4743's name, so `main` plus this PR has no `TypeError`; `main`'s own copy of the file still passes `ep_group=` and is what this PR replaces.
- **Multimem oracle.** The multimem case expected the target rows to equal the fp64 sum of the ranks' partials, rounded once to fp32 and then to bf16. The NVLS in-switch fp32 sum does not promise that: it adds in an order the switch picks, and on H100 it is not correctly rounded (at 4 and 8 ranks, 28-45% of fp32 elements differ from the once-rounded sum, and two 4-GPU groups of one node gave different bits for identical data). After the bf16 cast a mismatch is rare but possible, so the case could fail on correct hardware behavior. The test now records the fp32 rows each combine writes, before the cast, and checks:
  - `ordered`: equal, bit for bit, to the rank-order fp32 sum (unchanged contract, now checked before the cast);
  - `multimem`: within the recursive-summation bound `gamma_(ws-1) * sum|x|` of the fp64 sum (Higham eq. 4.4), which holds for any add order;
  - both: the bf16 output is that fp32 row cast once, and the target's fp32 rows keep their bits across the test's four runs (idle or busy peers, target at row 0 or 120). That is the batch invariance the collective must provide.
- **No multimem on Hopper.** On one H100 system the multimem combine was not batch-invariant: a token's combined row changed bits with its row position and the tokens batched alongside it (4 and 8 GPUs; another H100 system and GB200 passed). This matches the Hopper NVLS issue in NVIDIA/nccl#2360, where a reduction can depend on multicast objects allocated earlier unless the driver and Fabric Manager carry the fix; Megatron already rejects NVLS in deterministic mode on Hopper for that reason, and a separate PR rejects `batch_invariant_collective="multimem"` on compute capability 9. The test therefore chooses its collectives from the device at collection: `ordered` everywhere, `multimem` only off Hopper. No case skips on its target hardware, and the file passes whether or not that rejection has landed, because it never builds a multimem config on Hopper. The rejection itself is tested in that PR.
- **Hardware.** Unchanged: 8 H100 ranks in the H100 bucket (5 cases), 4 GB200 ranks through `launch_on_gb200` (9 cases); acceptance is all pass and none skip on every rank. Not run on GPU yet at this head.
