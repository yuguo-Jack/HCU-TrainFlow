# What does this PR do?
Support `use_gigatoken=True` while maintaining HF parity (with fallback on a fixed set of unicode characters). The default path remains `use_gigatoken=False`, this change requires user to explicitly opt in via use_gigatoken=True` or the `--use-gigatoken` flag. The tokenization encoding time is 10x - 40x faster depending on input. The functional support is achieved through:
1. Support right-aligned numeric grouping [Gigatoken PR](https://github.com/jupiterepoch/gigatoken/pull/1/changes). The current Gigatoken supports NT3, where a number string "12345" is broken into "1", "2", "3", "4", "5", whereas NT4 would break it into "12", "345".
2. Wire gigatoken into Megatron-LM
3. Fall-back to HF when Gigatoken process unicode characters differently. Gigatoken's ICU 2.2 Unicode 17 character classes differ from HF tokenizers 0.22's Unicode 16 regex. A compiled guard covers the 28 affected ranges and routes the entire input or batch through HF to preserve token boundaries. ASCII skips the regex; compatible Unicode uses Gigatoken. The guard also checks characters introduced by rendered chat templates. Direct native encoding and bulk `encode_files` bypass this guard.

### Validation

Validated with end2end run, with transformers 5.15.1 and tokenizers 0.22.2:

- All **38 new tokenizer tests** and **283 existing serving tests** passed. Tests are added to the existing tokenizer test file.
- Local parity checks against a complete HF tokenizer configuration covered all **1,112,064 valid Unicode scalars** in contextual inputs, in both normal and ordinary-text encoding modes: zero ID or round-trip differences.
- Public HTTP handlers with the real tokenizer configuration and a canned inference client passed prompt-ID and response comparisons, native/fallback routing, template-introduced Unicode, tokenizer copying and **16 concurrent requests**.
