# What does this PR do?
Support `use_gigatoken=True` while maintaining HF parity (with fallback on a fixed set of unicode characters). The default path remains `use_gigatoken=False`, this change requires user to explicitly opt in via use_gigatoken=True` or the `--use-gigatoken` flag. The tokenization encoding time is 10x - 40x faster depending on input. The functional support is achieved through:
1. Support right-aligned numeric grouping [Gigatoken PR](https://github.com/marcelroed/gigatoken/pull/61/changes). The current Gigatoken supports NT3, where a number string "12345" is broken into "1", "2", "3", "4", "5", whereas NT4 would break it into "12", "345".
2. Wire gigatoken into Megatron-LM
3. Fall-back to HF when Gigatoken process unicode characters differently. Gigatoken's ICU 2.2 Unicode 17 character classes differ from HF tokenizers 0.22's Unicode 16 regex. A compiled guard covers the 28 affected ranges and routes the entire input or batch through HF to preserve token boundaries. ASCII skips the regex; compatible Unicode uses Gigatoken. The guard also checks characters introduced by rendered chat templates. Direct native encoding and bulk `encode_files` bypass this guard.

### Performance

A/B test on SWE-bench-pro with replay on the same 16 GB300 GPUs with a Nano SFT model (TP1/PP1/CP1, dense DP16, EP4). The standalone tokenization encoding time speedup is between 16x to 19x, and the end2end latency reduction is around 7-10%. To ensure fairness, we replay identical frozen conversation/tool histories with verified HF prompt-ID equality, matched output lengths, and request order.

### Setup for right-aligned tokenizer configurations

Either install from pip
```
python -m pip install --force-reinstall --no-deps "gigatoken==0.11.0"
```

Or from source commit that includes the digit grouping rule
```bash
python -m pip install --force-reinstall --no-deps \
  "gigatoken @ git+https://github.com/marcelroed/gigatoken.git@aeb515b3101c9dfd179290c37937457ce3713a94"
```
If using source build, need Git and the Rust nightly toolchain specified by the fork's `rust-toolchain.toml`.

**Refresh the native encoders after vocabulary mutations**

The adapter inherits HF's mutation APIs, but builds `_gigatoken` only here and never invalidates the cached ordinary-text matcher. With the new fixture, call `native.add_special_tokens({"additional_special_tokens": ["<new-special>"]})` after construction. The public [wrapper](https://github.com/NVIDIA/Megatron-LM/blob/6f861d9ecd7e669c96e3ee931e7d69982ec490ae/megatron/core/tokenizers/text/libraries/huggingface_tokenizer.py#L243-L270) updates the HF backend and exposes the new token ID, while the native matcher still has the old vocabulary. Normal encoding of `"<new-special>"` therefore cannot emit that new ID, unlike HF fallback. Inherited `add_tokens` also leaves a previously populated [ordinary-text matcher](https://github.com/NVIDIA/Megatron-LM/blob/6f861d9ecd7e669c96e3ee931e7d69982ec490ae/megatron/core/tokenizers/text/libraries/huggingface_tokenizer.py#L490-L500) stale.

Handle `add_tokens` and `add_special_tokens` changes in the adapter: synchronize the retained HF state, rebuild `_gigatoken`, refresh the exposed `tokenizer` handle used by bulk encoding, and invalidate `_split_special_tokenizer`. Include changes that mark an existing token special even when no new ID is allocated. The invariant is one vocabulary and special-token classification across native encoding, HF fallback, saving and serialization. The exact mutation-hook override depends on the supported Transformers implementation, which isn't mounted here, so I can't provide a verified replacement implementation.

**Proposed regression:** populate the ordinary-text cache, add `<new-ordinary>` through each fixture tokenizer's `add_tokens`, and add `<new-special>` through each wrapper's `add_special_tokens`. Normal encoding must recognize both additions. With `split_special_tokens=True`, the ordinary addition must still match, while the special addition must be encoded as ordinary text exactly like HF. Also reclassify an existing ordinary token as special and check those two modes. Repeat parity checks with forced HF fallback, after pickle, and after save/reload. Retain the existing `<ordinary>`/`<extra>` distinctions, Unicode fallback, and serialization equality assertions. These checks weren't executed.
