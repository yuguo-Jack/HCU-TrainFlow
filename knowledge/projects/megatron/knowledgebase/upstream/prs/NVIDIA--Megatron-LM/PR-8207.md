# Replace IndexedOrder with ExecutionOrder for MFSDP v2

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8207) · state: open · merged: False

## Original PR description

Replace MFSDP v2's `IndexedOrder` with `ExecutionOrder` so repeated calls to one module can have different prefetch successors. For example, in `A → B → A → C`, the two occurrences of `A` lead to `B` and `C` respectively.

As items are appended, a weak lookup records each unique module's index or marks it as repeated. Unique modules select their position by identity, preserving construction-order behavior for grouped VPP chunk calls. Repeated modules must match the next occurrence at the cursor; a mismatch raises without consuming it. `next_item(offset)` looks ahead without advancing execution. Parameter budgets and gathering remain in the caller.

The diff covers the order class replacement, context construction and annotations, the prefetch consumer, and three focused unit tests. Runtime order recording remains follow-up work.

Validation:
- Five source-level cases pass for occurrence-specific prefetch budgets, unique-call repositioning, repeated-call validation, cursor wrapping, and weak ownership.
- Twenty-four source-level VPP traces generated with the production schedule table and context finalization match `IndexedOrder` lookahead for forward and reversed-chunk backward calls.
- Black 26.3.0, isort, Ruff, syntax checks, and `git diff --check` pass.

- shjwudp · comment · 2026-10-15T02:29:23Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8207#discussion_r4278403956)

File: `megatron/core/distributed/fsdp/src/megatron_fsdp/experimental/execution_order.py` · line 37

In short, `_unique_index` currently preserves VPP compatibility. We can remove it once iteration-scoped recording and replay are available.

It preserves the existing construction-order (`IndexedOrder`) behavior. With VPP, multiple chunks share a context, and the scheduler can execute several microbatches of one chunk before switching to another. A cursor over the construction order alone would therefore diverge from valid execution.

Modules appearing once can unambiguously select their position, while repeated modules use the occurrence cursor. This is a compatibility mechanism, rather than a fundamental requirement of ExecutionOrder.

For recorded orders, capturing the complete iteration—including VPP chunk scheduling—would allow a pure cursor without resetting it in each root hook. I would prefer to handle the recording lifecycle and any necessary VPP integration in the follow-up, while keeping this PR focused on the data structure.
