# [Core][MoE][BatchInvariant] Stop rounding the router's fp32 logits to bf16 under the triton and deepgemm backends

## Original PR description

# What does this PR do?

Under the `triton` and `deepgemm` batch-invariant backends, keeps an fp32-output GEMM of bf16 operands in fp32, as TE's `general_gemm` does. The MoE router's logits are the main such GEMM. Before this change, they were rounded to bf16 and then widened back to fp32.

Stacked on #8867 (`fix/deepgemm-bi-dense`). #8867 changes both functions this PR changes (`_mm_deepgemm` and `BatchInvariantTEGemmFn.forward`). It also makes the `deepgemm` backend run DeepGEMM's own batch-invariant kernel instead of cuBLASLt. The `deepgemm` case of the new test asserts batch invariance, so it needs that kernel. #8562 changes `router.py` but not the router's gating GEMM, and this PR does not touch `router.py`, so it is not stacked on #8562. The two merge cleanly.

**Bug.** With `batch_invariant_backend` set to `triton` or `deepgemm`, TE's `general_gemm` is replaced by `BatchInvariantTEGemmFn`. It ran `mm_batch_invariant(opB, opA)` and cast the result to `out_dtype` afterwards. Both of the GEMMs that call can reach allocate their output in the operands' dtype: `matmul_persistent` allocates `c` in `a.dtype`, and `_mm_deepgemm` allocates `d` in `a`'s dtype. So for bf16 operands, the fp32 accumulator was rounded to bf16 before the cast to fp32.

The router computes its logits exactly this way: `router_gating_linear` calls `te_general_gemm(weight, inp, torch.float32, layout="TN")` with bf16 weight and input. So with `moe_router_dtype='fp32'` (required for inference-optimized models), the logits carried bf16 rounding (relative error up to 2⁻⁸), and near ties they can select different experts than the router outside batch-invariant mode. This affects training and inference under these two backends; `te_native` does not replace TE's GEMM. Two other GEMMs take the same path: the DSA indexer's fp32 weights projection (`dsa.py`) and an LM head that writes fp32 output for the fused cross entropy (`tensor_parallel/layers.py`).

## Fix

- `mm_batch_invariant`, `matmul_persistent` and `_mm_deepgemm` take an `out_dtype` (default: the operands' dtype). Each writes that dtype directly from its fp32 accumulator, rounding once.
  - Triton: the persistent kernel already stores `accumulator.to(c_ptr.dtype.element_ty)`, so only the allocation changes. The tile config is still chosen by the input dtype.
  - DeepGEMM: at the pinned `ea2b7805`, `bf16_gemm_nt` (which `bf16_gemm_nn` calls) accepts a bf16 or fp32 D (`csrc/apis/gemm.hpp:491`). It writes the fp32 accumulator directly on SM90 (`sm90_bf16_gemm.cuh`) and SM100. D's outer stride is now aligned to 16 bytes for D's own element size.
  - bf16 operands with any other output dtype (for example fp16) go to Triton rather than being rounded twice.
- `BatchInvariantTEGemmFn.forward` passes TE's `out_dtype` to the GEMM.
- The kernels, tile shapes and K order are unchanged: no split-K, and the reduction order does not depend on M. Outputs therefore stay batch-invariant. GEMMs whose output dtype equals the operands' dtype are bit-identical to before.
- No host syncs and no new allocations. The output buffer was already allocated per call; only its dtype changes.

## Tests

- `tests/unit_tests/transformer/test_te_layers_batch_invariant.py::test_bik_router_gating_logits_are_fp32[triton|deepgemm]` runs `router_gating_linear` on bf16 operands (64 experts, hidden 1024) under each backend. It checks that the logits:
  - are fp32;
  - are not on the bf16 grid;
  - are within 1e-4 of an fp64 reference (bf16 rounding misses this tolerance on about 80% of the elements);
  - keep a token's bits at 1, 16, 129 and 4096 tokens.

  On the base branch both cases fail with `router logits were rounded to bf16`. The reference is computed in fp64, so the test does not depend on the TF32 setting.
- Determinism: `tests/unit_tests/determinism/kernels/test_inference_kernels.py::test_batch_invariant_fp32_router_gating_replays[triton|deepgemm]` replays the same GEMM at 8192 x 4096 x 256 bit-exactly. The manifest note for `batch_invariant_kernels` records the fp32-output case. `tools/check_kernel_determinism_coverage.py --base-ref fix/deepgemm-bi-dense` passes.
- Checked on CPU with the Triton interpreter and a stand-in DeepGEMM that applies the pin's D-dtype and stride checks:
  - base: the fp32 outputs lie on the operands' grid, and DeepGEMM receives a bf16 D;
  - fix: DeepGEMM receives an fp32 D, the errors are about 3e-7, and bf16-output GEMMs are unchanged.

  On H100 (dfw job 21222562, on this PR's first commit), the four new cases and the neighbor tests pass, and on `main` the regression test fails with `router logits were rounded to bf16`. The keyword fix to the GDP test (below) has not run on a GPU yet.

## Merge order

Merge after #8867 (`fix/deepgemm-bi-dense`), which this branch is stacked on. It merges cleanly with `main`, #8865, #8866, #8708, #8573, #8562 and #8566. Two PRs conflict trivially:
- #8868: both PRs add a keyword argument to `matmul_persistent`. Keep both `out` and `out_dtype`, and allocate and check the output against `out_dtype or a.dtype`. #8868's new `mm_out_batch_invariant` merges without a conflict but must also follow `out`'s dtype. Otherwise an fp32 `out` with bf16 operands is rounded to bf16 again under `deepgemm`, or rejected by the dtype assert under `triton`. Whichever PR lands second makes it call `_mm_deepgemm(a, b, out.dtype)` and `matmul_persistent(a, b, out=out, out_dtype=out.dtype)`. Its callers pass bf16 buffers today, so the issue is latent until then.
- #8869: both PRs append tests at the end of `test_te_layers_batch_invariant.py`.

Follow-up for #8865 (and #8869, which carries it). Its fp32 weight-gradient path `_te_gemm_product_fp32` copies both operands to fp32 and always runs Triton. Its alpha/accumulate branch also rounds the product to the operands' dtype before combining it in fp32. Once this PR lands, both can use `mm_batch_invariant(opB, opA, out_dtype=torch.float32)`. That gives the same exact fp32 products with no operand copies, and runs on DeepGEMM under `deepgemm`.

The existing `tests/unit_tests/ssm/test_gdp_triton_projection_no_copy.py` replaces `mm_batch_invariant` with a wrapper. The wrapper now forwards keyword arguments, so it receives the `out_dtype` that `BatchInvariantTEGemmFn` passes.
