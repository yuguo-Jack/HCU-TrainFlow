# Add tensor-parallel Muon Hyperball optimizers

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/6422) · state: open · merged: False

## Original PR description

## Summary

- add `TensorParallelMuonH`, registered as `--optimizer muon_h`, for Emerging Optimizers' standard Hyperball Muon behavior
- make `TensorParallelMuonHT`, registered as `--optimizer muon_ht`, the tangent-constrained MuonHT variant
- initialize every MuonH/MuonHT-managed matrix to the configured radius in Megatron's model-initialization lifecycle, before mixed-precision copies are created
- compute logical Frobenius norms and inner products across dense/expert TP and GTP-remat shards without reducing replica-only axes
- require an explicit `ProcessGroupCollection` throughout both constrained optimizers; neither new path falls back to `use_mpu_process_groups`
- keep the fixed radius as configuration rather than per-parameter optimizer state, avoiding scalar distributed-checkpoint entries
- keep the implementation summary in the optimizer docstrings; no optimizer-directory README is added

## Update rules

For Muon's orthogonalized update `U_t`, learning rate `eta_t`, configured radius `R`, and `Normalize(X) = X / ||X||_F`, MuonH applies:

```
W_(t+1) = R * Normalize(W_t - eta_t * R * Normalize(U_t))
```

The pre-update extension point rescales the logical update norm to `R`; the post-update extension point retracts the logical updated weight to `R`.

MuonHT first projects the raw gradient onto the Frobenius sphere's tangent space, before momentum accumulation and Newton-Schulz orthogonalization:

```
G_tangent = G - (<W, G>_F / <W, W>_F) * W
```

It then applies the same normalized update and retraction as MuonH. This matches the distinction in [marin-community/marin#2434](https://github.com/marin-community/marin/issues/2434).

Numerical-zero decisions consistently compare norms against `muon_ht_eps`; no dtype-relative tolerance or host-synchronizing per-step `.item()` test is used. Both variants replace weight decay and require `weight_decay=0`.

## Integration and initialization

`TensorParallelMuonH` subclasses Megatron's `TensorParallelMuon`, which subclasses Emerging Optimizers' `OrthogonalizedOptimizer`. It reuses momentum, Newton-Schulz orthogonalization, QKV handling, and TP/GTP-aware Muon behavior while implementing the constraint through `pre_weight_update_fn_inplace` and `post_weight_update_fn_inplace`.

`TensorParallelMuonHT` subclasses `TensorParallelMuonH`. It temporarily supplies the tangent-projected raw gradient to the inherited optimizer step so the projection occurs before momentum and orthogonalization, then restores the original `param.grad`.

Megatron owns the initialization contract: when `muon_ht_radius` is configured and parameter initialization is enabled, model construction scales each managed matrix to `R` before mixed-precision wrapping. The caller performs the configuration gating directly; checkpoint-oriented construction with `perform_initialization=False` does not mutate parameters.

## Sharding and checkpoint behavior

- norm sums and tangent inner products use FP32 accumulation and `all_reduce(SUM)` over applicable `tp`/`expt_tp` and `gtp_remat`/`expt_gtp_remat` groups
- CPU-initialized shards stage only the FP32 scalar reduction through CUDA when the selected group uses NCCL, then return the result to the parameter device
- TP and GTP-remat axes are reduced sequentially to cover the logical tensor's Cartesian shard product
- replica-only axes are excluded
- the configured radius is not stored as per-parameter optimizer state, so distributed checkpointing does not encounter scalar state for sharded parameters

## Tests added

- MuonH update normalization and post-update radius preservation
- MuonHT tangent projection occurs before momentum and restores the original gradient object
- full optimizer-step radius preservation without persistent radius state
- fixed-radius, weight-decay, epsilon, and required-process-group validation
- model initialization filters exactly Muon-managed parameters
- model initialization rejects norms below epsilon and accepts norms equal to epsilon
- unsharded CPU initialization remains local and performs no collective
- CPU-resident TP shards use CUDA scalar reductions over NCCL and remain CPU-resident
- model lifecycle initialization runs before distributed/mixed-precision wrapping
- checkpoint-oriented `perform_initialization=False` leaves parameters unchanged
- optimizer factory construction for both `muon_h` and `muon_ht`
- normal training setup forwards the explicit process-group topology only to `muon_h` and `muon_ht`, preserving Adam/SGD behavior
- multi-rank TP logical norm normalization
- multi-rank TP tangent projection using the global sharded inner product
- multi-rank GTP-remat logical norm normalization
- bit-exact replay determinism for MuonH and MuonHT projection, normalization, update, and retraction

### Forward process groups from the normal training setup

**Failure:** A normal training launch with `--optimizer muon_h` or `muon_ht`, a configured radius, and zero weight decay cannot reach its first optimizer step. Although `pretrain()` supplies a collection to `setup_model_and_optimizer()`, that function's [optimizer-factory call](https://github.com/NVIDIA/Megatron-LM/blob/a2d1c3e59c1dd9312b583b6e56e7de015830ffec/megatron/training/training.py#L2799-L2805) omits it. The new [explicit-collection guard](https://github.com/NVIDIA/Megatron-LM/blob/a2d1c3e59c1dd9312b583b6e56e7de015830ffec/megatron/core/optimizer/__init__.py#L775-L780) therefore always raises for both new CLI choices.

**Correction:** In that call, forward the already supplied collection for the constrained optimizers:

```python
            pg_collection=(
                pg_collection
                if config.optimizer in ("muon_h", "muon_ht")
                else None
            ),
```

This restores the invariant that model initialization and optimizer construction receive the same explicit topology. Keep the direct factory's rejection of `None`. Do not indiscriminately forward the collection for Adam/SGD: their [process-group setup rejects explicit collections with Gloo enabled](https://github.com/NVIDIA/Megatron-LM/blob/a2d1c3e59c1dd9312b583b6e56e7de015830ffec/megatron/core/process_groups_config.py#L528-L533), so that broader change would alter existing launches.

**Acceptance — proposed, not executed:** Exercise `setup_model_and_optimizer()` with an explicit collection, radius 2.5, weight decay zero, and each new optimizer name; construction and one training step must succeed. Retain the existing factory assertion that passing `pg_collection=None` raises. Existing Adam/SGD setup with Gloo enabled must retain its previous behavior. The suggested insertion is source-reviewed, not execution-verified.

### Support CPU-initialized shards before performing NCCL norm reductions

**Failure:** The builder lifecycle deliberately [leaves CPU-initialized models on CPU](https://github.com/NVIDIA/Megatron-LM/blob/a2d1c3e59c1dd9312b583b6e56e7de015830ffec/megatron/training/models/dist_utils.py#L187-L201), but the newly invoked norm helper [reduces its CPU scalar directly over the parameter's group](https://github.com/NVIDIA/Megatron-LM/blob/a2d1c3e59c1dd9312b583b6e56e7de015830ffec/megatron/core/model_initialization.py#L86-L88). For example, construct a CPU `ColumnParallelLinear` with TP=2, `use_cpu_initialization=True`, and radius 2.5, then call `prepare_existing_model_chunks_for_distributed_training(..., wrap_with_ddp=False, mixed_precision_wrapper=None)` with the normal NCCL groups. Initialization fails because NCCL cannot reduce CPU tensors, instead of normalizing the logical weight.

**Correction:** Stage only the reduction scalar onto CUDA when a CPU tensor needs an NCCL collective. In `logical_frobenius_inner_product`, replace the reduction loop with:

```python
    for group in _parameter_shard_groups(param, pg_collection):
        reduction_input = inner_product
        if (
            inner_product.device.type == "cpu"
            and torch.distributed.get_backend(group) == "nccl"
        ):
            reduction_input = inner_product.to(
                device=torch.device("cuda", torch.cuda.current_device())
            )
        torch.distributed.all_reduce(
            reduction_input, op=torch.distributed.ReduceOp.SUM, group=group
        )
        inner_product = reduction_input.to(device=lhs.device)
```

The invariant is an FP32 logical sum over the same unique shard axes, returned on the input device. This retains CPU parameter placement, GPU-native reductions, CPU/Gloo operation, sequential TP/GTP reductions, and exclusion of replica-only axes.

**Acceptance — proposed, not executed:** Add the two-rank CPU/NCCL lifecycle case above and assert that the sum of squared shard weights has square root 2.5 while parameters remain on CPU. Retain the existing GPU TP and GTP norm assertions, and check that unsharded CPU initialization with an empty explicit collection still works without a collective. Verify the suggested code before adopting it.
