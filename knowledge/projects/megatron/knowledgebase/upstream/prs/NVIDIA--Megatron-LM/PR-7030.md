# skip moe_act recompute path when grad is disabled

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7030) · state: closed · merged: True

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?
This PR helps fix a growing `TE queue(_is_first_fp8_module)` process state accumulation issue which occurs during MoE training with activation checkpointing enabled. The fix directly improves the overall step time increase pattern that is observed otherwise over longer MoE training runs(>10K steps).

## Description
During training with `moe_act` selective activation recompute, `TEGroupedMLP.forward()` runs two forward passes: the original forward pass (batch inputs through the network) and a recompute forward pass triggered during backward via a registered hook.

**The bug:** the original forward pass was always taking the `CheckpointWithoutOutput` path regardless of whether grad was enabled, leading to an entry push into `_is_first_fp8_module` TE queue, but never gets popped because there is no hook registered.

The fix guards the `CheckpointWithoutOutput` setup behind `torch.is_grad_enabled()`, so the original forward pass under `torch.no_grad()` takes the plain `else` branch, ensuring no dangling entries in the queue.

Light review.

The fix is correct and well-scoped. `CheckpointWithoutOutput.checkpoint()` unconditionally pushes onto TE state via `activation_recompute_forward(recompute_phase=False)`, while the matching pop only happens inside `_recompute`, which runs from the grad hook registered by `discard_output_and_register_recompute()`. Under `torch.no_grad()` that hook is never registered (`hook_tensor.requires_grad` is False), so the push leaks. The diagnosis in the description matches the code in `megatron/core/tensor_parallel/random.py`.

Caching the predicate in `use_activation_recompute` rather than re-reading `torch.is_grad_enabled()` at line 1067 is the right call: the two sites must agree even if grad mode changes across the `linear_fc2` call, and `self.activation_checkpoint` would otherwise be a stale object from a previous forward. Guarding on `torch.is_grad_enabled()` is also the established idiom in this area (see `router.py` and `cuda_graphs.py:1036`).

Two things:

1. Formatting, flagged inline. The three-line parenthesized assignment is not Black output and will fail the `linting` job.

2. Regression test. Both test boxes are unchecked in the description. This is a state-leak bug that no existing test caught, and it is cheap to cover without FP8 hardware: the leak is observable as `self.activation_checkpoint` having been created at all after a `torch.no_grad()` forward through `TEGroupedMLP` configured with `recompute_granularity=selective` and `recompute_modules=[moe_act]`. `tests/unit_tests/transformer/moe/test_grouped_mlp.py::TestTEGroupedMLP` already runs `no_grad` forwards, so the fixture cost is near zero. Asserting `getattr(mlp, "activation_checkpoint", None) is None` after such a forward would pin the fix.

A note for follow-up rather than this PR: `gdn.py:257`, `gdn2.py:315`, `gated_delta_product.py:692` and `shortcut_block.py:197` construct `CheckpointWithoutOutput()` behind the same shape of unguarded `if self.recompute_*` predicate and look susceptible to the same leak. Worth an issue instead of expanding this diff.

No determinism-test obligation here: the change adds no kernel and alters no numerics, it only selects between two paths that were already both present.
