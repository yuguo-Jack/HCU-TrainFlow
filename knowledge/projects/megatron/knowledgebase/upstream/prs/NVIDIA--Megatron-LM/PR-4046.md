# Fix HybridDeviceOptimizer KeyError after mixed-precision param replacement

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/4046) · state: open · merged: False

## Original PR description

## Summary

This fixes the `HybridDeviceOptimizer` `KeyError` that happens on the first `optimizer.step()` when CPU optimizer offload is used together with bf16/fp16 mixed precision.

## Root Cause

`HybridDeviceOptimizer` built its internal mapping using tensor object identity from the original `param_groups`.

Later, `Float16OptimizerWithFloat16Params` replaces entries in `optimizer.param_groups` with new FP32 main parameters. On the first step, HDO still looks up the old tensor objects and fails with:

```python
inner_param = self.param_to_inner_param[param]
KeyError: tensor(..., device='cuda:X')
```

## Fix

Use a stable logical mapping based on parameter position in `param_groups` instead of relying on tensor object identity remaining unchanged.

This also updates:
- grad sync from current params to inner/sub-optimizer params
- copy-back from sub-optimizers to current params
- HDO state synchronization to follow the current wrapped params

## Tests

Added a single-GPU regression test covering:
- `HybridDeviceOptimizer + Float16OptimizerWithFloat16Params`
- `bf16`
- `fp16`
- first `optimizer.step()` no longer raises `KeyError`

Validation run:
```bash
OMP_NUM_THREADS=1 .venv/bin/python -m pytest tests/unit_tests/test_optimizer_cpu_offloading.py -vv
```

Fixes #4042

- shjwudp · COMMENTED · 2026-04-20T09:22:27Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/4046#pullrequestreview-4138756921)

Hi @ma-ben , thanks a lot for catching this issue and for the careful investigation and fix. 

I agree that there are currently composability issues between `HybridDeviceOptimizer` and other optimizers. I’ve been thinking about how to address this in a more systematic way.

First, I don’t think `param_update_in_fp32` is a good option in HDO, as it essentially introduces hard-coded behavior.

From a design perspective:

- `HybridDeviceOptimizer` (optimizer offloading) is responsible for offloading optimizer states and gradients to CPU to reduce GPU memory usage, while leveraging a side CPU optimizer to perform the optimizer step.
- `Float16OptimizerWithFloat16Params` is responsible for maintaining FP32 copies of parameters outside the optimizer to improve update precision.

If we want to make optimizer offloading more general and composable with different optimizers, I think we may need to:

1. Apply optimizer offloading at the final stage, so that as many optimizer states as possible (e.g., FP32 parameters introduced by `Float16OptimizerWithFloat16Params`) can be offloaded to CPU.
2. Remove `param_update_in_fp32` from HDO, and make the CPU optimizer class optional, so that HDO can still provide value (i.e., optimizer state offloading) even when a CPU optimizer is not available.

Based on these considerations, I feel that instead of adding special-case compatibility in `HybridDeviceOptimizer` for `Float16OptimizerWithFloat16Params`, it may be better to rethink the relative positioning of `HybridDeviceOptimizer` in the optimizer stack.

This likely requires some refactoring of HDO and may not be trivial to implement immediately. I don’t yet have a complete design in mind, but I’d be happy to discuss this further if you’re interested.
