# What does this PR do?
Reduce ordinary NCCL MoE dispatch from three data all-gathers to one while preserving the batch-invariant path

This extracts the NCCL dispatcher optimization from #8114. Hidden states, router probabilities, and routing indices are packed into aligned byte rows, gathered together, and unpacked into their original dtypes

The optimization covers both equal-token CUDA Graph dispatch and variable-token prefill dispatch. The variable-token path retains its existing token-count metadata gather. Grad-enabled execution, batch-invariant execution, tensors with different row counts, and unaligned layouts retain the original three-gather path. Token combine is unchanged

The helpers handle empty and strided inputs. No model-specific tuning was introduced.

## Validation

This PR is rebased onto main `db3a6cd8a` (no conflicts); the PR head is `ff51a2d45`. The full-model logit validation below was run before rebasing, against main `442d0183d`. After rebasing, the dispatcher and determinism suites (423 per rank, five optional-backend skips) pass on each of 4 GB300 ranks, including the new row-count fallback check, and the end-to-end runs below generated the same tokens as main in every allocation

- Distributed unit tests: 84 tests passed on every rank at both EP4 (one node) and EP8 (two nodes), with no failures or skips. Coverage includes equal and ragged token counts, zero-token ranks, all-empty inputs, strided inputs, CUDA Graph replay with updated inputs, alignment fallback, BI fallback, rank-local gradient flags, and autograd preservation
- Bit-exact packing tests: repeated packing and unpacking preserve the original bytes, including signed zero, infinities, subnormals, and NaN payloads. Coverage is registered as `inference_nccl_packed_dispatch` in `tests/unit_tests/determinism/kernels/manifest.py`
- Full-model logits: all 60 comparison cells passed across Nano, Super, and Ultra: five workloads per model, eager/decode CUDA Graph execution, and shared-expert overlap off/on. Every valid prefill, mixed, and decode position and all 131072 vocabulary entries were compared through integer views, without tolerance or downcasting. All eight ranks participated, with two repeats per case per process. Input IDs, positions, generated tokens, and replay results also matched. A one-bit negative control verified the comparator
- Workload coverage: batch sizes 1, 7, 16, 31, and 32; prompt lengths from 1 to 257 tokens; output lengths of 64 or 128 tokens
- Static checks: Black, isort, pylint, Ruff, determinism-manifest coverage, and `git diff --check` passed. `tools/autoformat.sh` was run in check mode. Its non-gating mypy step reported missing local Torch imports/stubs and Optional-access diagnostics in unchanged code.

Full-model validation used GB300, two nodes with four GPUs each, TP8/EP8/ETP1, BF16 weights, FP32 router, and BI disabled. `MAMBA_DETERMINISTIC=1` and `TRITON_CACHE_AUTOTUNING=0` were set identically for baseline and candidate. In decode-graph configurations, prefill and mixed steps remained eager.

## Performance

End-to-end batch generation speedup against main `db3a6cd8a` (candidate `ff51a2d45`):

| Model | BS16 speedup | BS32 speedup |
|---|---:|---:|
| Nano | 1.100x | 1.080x |
| Super | 1.082x | 1.067x |
| Ultra | 1.059x | 1.051x |

Measurement setup:

- Two nodes, 8 NVIDIA GB300 GPUs, TP8 / EP8 / ETP1; official BF16 checkpoints converted to Megatron Core, FP32 router, FA4, decode CUDA Graphs, NCCL dispatcher (`--inference-moe-token-dispatcher-type nccl`); batch-invariant mode and prefix caching disabled; shared-expert overlap off
- 16 or 32 requests with 32–33 prompt tokens and exactly 128 greedy output tokens each
- Three independent allocations per model. Each runs four fresh processes per batch size (baseline → candidate → candidate → baseline at BS16, reversed at BS32) with five timed generations per process
- Speedup = baseline / candidate latency, using the mean of the two per-process medians; the table shows the geometric mean of the three allocation ratios and a 95% t interval on the log ratios. All samples are retained
- Triton autotune selection is pinned for both versions (`--triton-autotune-mode pinned`), so fresh processes generate comparable tokens. Generated tokens were identical between baseline and candidate in every allocation
- Timing starts after request enqueue and ends when all requests finish (prefill and decode). Model loading, warmup and tokenization are excluded
