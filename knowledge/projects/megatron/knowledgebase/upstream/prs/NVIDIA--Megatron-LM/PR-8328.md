# Fix pad_routing_map capacity checks for unaligned expert counts

# What does this PR do?

Fail explicitly when routing-map padding cannot reach the requested alignment within the existing token capacity.

For example, an expert receiving 90 of 100 tokens cannot be padded to a multiple of 128 by flipping existing zero entries. Both helpers previously returned 100 tokens for that expert without reporting that the alignment contract was not met.

- Check that each expert's next aligned token count fits within `num_tokens` in both `pad_routing_map` and `fused_pad_routing_map`.
- Use `torch._assert_async` to avoid adding a device-to-host synchronization on the CUDA path. Infeasible CPU inputs raise `RuntimeError`; on CUDA the assertion is asynchronous and may surface at a later synchronization point.
- Document the capacity precondition and add three CPU tensor regression cases for normal padding, the exact-capacity boundary, and the reported infeasible input.

## Validation

The three new tests are in `tests/unit_tests/transformer/moe/test_token_dispatcher.py`:

- `test_pad_routing_map_pads_each_expert_to_multiple`
- `test_pad_routing_map_uses_every_remaining_token_when_needed`
- `test_pad_routing_map_raises_when_not_enough_tokens`
