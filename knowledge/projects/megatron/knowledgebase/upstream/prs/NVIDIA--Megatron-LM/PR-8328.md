# Fix pad_routing_map capacity checks for unaligned expert counts

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8328) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Fail explicitly when routing-map padding cannot reach the requested alignment within the existing token capacity.

For example, an expert receiving 90 of 100 tokens cannot be padded to a multiple of 128 by flipping existing zero entries. Both helpers previously returned 100 tokens for that expert without reporting that the alignment contract was not met.

- Check that each expert's next aligned token count fits within `num_tokens` in both `pad_routing_map` and `fused_pad_routing_map`.
- Use `torch._assert_async` to avoid adding a device-to-host synchronization on the CUDA path. Infeasible CPU inputs raise `RuntimeError`; on CUDA the assertion is asynchronous and may surface at a later synchronization point.
- Document the capacity precondition and add three CPU tensor regression cases for normal padding, the exact-capacity boundary, and the reported infeasible input.

## Strict review: PR #8328, `pad_routing_map` capacity checks

**Findings by severity:** CRITICAL: 0, IMPORTANT: 0, SUGGESTION: 1

**Most important finding:** one `[SUGGESTION Style]` comment, posted inline. The new `Raises: RuntimeError` docstrings in both helpers say the call raises a catchable `RuntimeError`. That only happens on CPU. On CUDA, which is the only production path, `torch._assert_async` triggers a device-side assert instead. The call returns normally, the error appears at a later synchronization point, and the CUDA context cannot be used afterwards. No code change is needed; only the docstrings should be corrected.

**Overall risk:** low. The new check rejects only inputs that the old code already handled wrongly: it padded every remaining zero and returned token counts that were not aligned, with no error. Every input that was already feasible gives exactly the same output as before.

### What I checked

**The feasibility check.**
- In the torch helper, `num_ones + num_to_pad <= routing_map.shape[1]` is evaluated after the transpose, so `shape[1]` is `num_tokens`.
- In the fused helper, `num_ones + (-num_ones) % pad_multiple <= num_tokens`: `%` binds tighter than `+`, and torch's `%` result is never negative for a positive divisor.
- Both are equivalent to "the row has at least `num_to_pad` zeros" for 0/1 maps. That is the exact condition under which the existing torch mask and the existing Triton kernel produce aligned counts.
- The `num_tokens == 0` early return in the fused helper is unchanged.

**Callers.**
- [`token_dispatcher.py#L664-L669`](https://github.com/NVIDIA/Megatron-LM/blob/40f62448a1c13282ab59188f25dbcfe6ab93684e/megatron/core/transformer/moe/token_dispatcher.py#L664-L669) (all-to-all dispatcher): when the router pads, [`skip_routed_expert_padding`](https://github.com/NVIDIA/Megatron-LM/blob/40f62448a1c13282ab59188f25dbcfe6ab93684e/megatron/core/transformer/moe/moe_utils.py#L1560-L1567) disables expert-side padding. Unaligned counts therefore already reached the GEMM, which [`get_align_size_for_quantization`](https://github.com/NVIDIA/Megatron-LM/blob/40f62448a1c13282ab59188f25dbcfe6ab93684e/megatron/core/transformer/moe/moe_utils.py#L1538-L1546) says needs this alignment.
- [`token_dispatcher.py#L1603-L1617`](https://github.com/NVIDIA/Megatron-LM/blob/40f62448a1c13282ab59188f25dbcfe6ab93684e/megatron/core/transformer/moe/token_dispatcher.py#L1603-L1617) (DeepEP): this path already checks feasibility on the host and falls back before calling either helper, so the new assert cannot fire there.
- No new host sync is added, and the extra work per call is a few small ops.

**Tests.**
- I re-derived every expected value: 90/100 rows with pad 16 gives `[96, 16, 0]`; 90/128 rows with pad 128 gives `[128, 0]`; the exact-capacity case gives `[256, 256, 128, 0]` (expert 2 has `ceil(256/3) = 86` tokens and pads to 128).
- On CPU, the infeasible 90/100 case reaches `torch._assert_async(..., msg)`, which raises `RuntimeError` with the message, so `match="not enough tokens"` is satisfied.
- In [`manifest.py`](https://github.com/NVIDIA/Megatron-LM/blob/40f62448a1c13282ab59188f25dbcfe6ab93684e/tests/unit_tests/determinism/kernels/manifest.py#L196-L350), `fused_pad_routing_map.py` maps to `test_fused_triton_kernels.py` and `moe_utils.py` maps to `test_moe_kernels.py`. This PR updates both test files, so the kernel-determinism coverage check is satisfied.
- The new replay tests use the harness's `out` key, its return value and `backward=False` correctly. Both test modules already skip when no GPU is available.

**[SUGGESTION Style]** The new `Raises: RuntimeError` contract only holds on CPU. The same wording is in [`fused_pad_routing_map.py#L84-L87`](https://github.com/NVIDIA/Megatron-LM/blob/40f62448a1c13282ab59188f25dbcfe6ab93684e/megatron/core/fusions/fused_pad_routing_map.py#L84-L87).

**Failure.** Both helpers check feasibility with `torch._assert_async`.
- **CPU:** an infeasible map raises `RuntimeError` at the call. `test_pad_routing_map_raises_when_not_enough_tokens` covers this.
- **CUDA:** an infeasible map does not raise at the call. CUDA is the only production path: the callers in [`token_dispatcher.py#L664-L669`](https://github.com/NVIDIA/Megatron-LM/blob/40f62448a1c13282ab59188f25dbcfe6ab93684e/megatron/core/transformer/moe/token_dispatcher.py#L664-L669) and [`#L1612-L1617`](https://github.com/NVIDIA/Megatron-LM/blob/40f62448a1c13282ab59188f25dbcfe6ab93684e/megatron/core/transformer/moe/token_dispatcher.py#L1612-L1617), and the Triton kernel in `fused_pad_routing_map`.
  - The function returns a map with unaligned counts.
  - A device-side assert fires asynchronously and surfaces at a later synchronization point, for example `_maybe_dtoh_and_synchronize`.
  - After that the CUDA context cannot be used.
  - The PR description says this, but the docstrings do not.
- **Why it matters:** a caller who trusts the docstring might write `try: pad_routing_map(...) except RuntimeError: <fallback>`, the way the DeepEP manager falls back at [`#L1603-L1610`](https://github.com/NVIDIA/Megatron-LM/blob/40f62448a1c13282ab59188f25dbcfe6ab93684e/megatron/core/transformer/moe/token_dispatcher.py#L1603-L1610). On GPU that fallback never runs and the process cannot recover.

**Correction.** Change only the docstrings; keep the check as it is. This is a multi-line, two-file edit, so here is the text rather than a suggestion block.

In `pad_routing_map`, replace L766-769 with:
```python
    Raises:
        RuntimeError: On CPU tensors, if an expert's ``num_ones + num_to_pad`` exceeds
            num_tokens, so its row has too few zeros left to reach the next multiple of
            pad_multiple. On CUDA tensors the same check is a ``torch._assert_async``
            device-side assert: this call returns normally, the error surfaces at a later
            synchronization point, and the CUDA context is unusable afterwards, so it
            cannot be caught here to fall back.
```
In `fused_pad_routing_map`, the kernel only runs on CUDA. Replace L84-87 with:
```python
    Note:
        Each expert must satisfy ``num_ones + num_to_pad <= num_tokens``. A violation is
        detected with ``torch._assert_async``: a device-side assert that surfaces at a later
        CUDA synchronization point and leaves the CUDA context unusable, so it cannot be
        caught at this call to fall back.
```

**Preservation.**
- No change to the predicate, the error message, or the `_assert_async` call, so feasible maps keep returning the same output.
- The CPU `RuntimeError` with "not enough tokens" stays.
- The DeepEP host-side fallback stays as it is.

**Acceptance.**
- Static check: neither docstring claims a synchronous, catchable `RuntimeError` for CUDA inputs.
- The existing tests still pass unchanged:
  - `test_pad_routing_map_raises_when_not_enough_tokens`: CPU, `RuntimeError`, "not enough tokens".
  - `test_pad_routing_map_pads_each_expert_to_multiple`: `[96, 16, 0]`.
  - `test_pad_routing_map_uses_every_remaining_token_when_needed`: `[128, 0]`.
  - `test_fused_pad_routing_map_replays_at_exact_capacity` and `test_pad_routing_map_replays[exact-capacity]`: `[256, 256, 128, 0]`.
