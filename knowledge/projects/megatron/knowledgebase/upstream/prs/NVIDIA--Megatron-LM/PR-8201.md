# What does this PR do?

Runs the two Nemotron 3.5 Lightning GB200 functional tests (`..._ep8_dgx_gb200` nightly and `..._ep4_dgx_gb200_1N4G`) and the two Nemotron 3 Super release tests (`nemotron3_super_release_gb200`, `..._gb200_sm`) in `--deterministic-mode`, so CI compares them bit for bit.

Changes in each `model_config.yaml`:

| Change | Reason |
|---|---|
| `NVTE_ALLOW_NONDETERMINISTIC_ALGO: 0`, `NCCL_ALGO: Ring`, `CUBLAS_WORKSPACE_CONFIG: :4096:8` | Deterministic env values; also remove `NON_DETERMINSTIC_RESULTS` |
| `--deterministic-mode: true` | Enables the mode |
| Drop `--cross-entropy-loss-fusion` and `--cross-entropy-fusion-impl` | Deterministic mode rejects fused cross-entropy |

`--attention-backend` and the HybridEP dispatcher are unchanged.

## Testing

Ran each recipe's `MODEL_ARGS` and `ENV_VARS` on GB200 (26.10 rc5 image) with `--mock-data` and a fresh init instead of the Pile data and frozen checkpoint, which are not available on my cluster. Each recipe ran twice:

| Recipe | Nodes | Result |
|---|---|---|
| [1N4G (EP4)](https://forge.coreweave.com/wandb/nvidia/mbridge-dev-zhiyul?nw=0pkjc1ukr7rk) | 1 | 20/20 iterations, both runs bit-identical |
| [nightly (EP8, HybridEP)](https://forge.coreweave.com/wandb/nvidia/mbridge-dev-zhiyul/workspace?nw=wpcjt0e2u5) | 2 | 20/20 iterations, both runs bit-identical |
| [Super 64n](https://forge.coreweave.com/wandb/adlr/mbridge-dev-zhiyul?nw=eppi14wwbda) | 64 | 20/20 iterations, both runs bit-identical |

Compared at full float32 over all 20 steps: lm loss, mtp_1 loss, mtp_2 loss, num-zeros, grad norm, load-balancing loss.

- The Super release recipes are not yet validated at their 64-node scale (tp2, ep64, MXFP8, TE CUDA graphs); an A/A pair is queued. Treat that part as unverified until it reports.
- Golden values (`golden_values_dev_dgx_gb200.json`, and the nightly's `..._gb300.json`) were recorded in non-deterministic mode and need regenerating from a CI run. Until then the bit-exact compare will fail.
- HybridEP is listed as not yet verified in the determinism docs. This is evidence at 8 GPUs and 20 steps only.

- `TRITON_CACHE_AUTOTUNING: 1` in all four recipes, and `_run_training.sh` defaults `TRITON_CACHE_DIR` to `$OUTPUT_PATH/triton_cache` when it is 1 (deterministic mode requires a shared cache dir; the image defaults the flag to 1). 1N4G A/B (cold) and a warm rerun, and a 2-node nightly A/B, are bit-identical over 20 iterations on GB200 (mock data). A cold cache adds ~12 min to the first run on 1N4G; a warm cache starts in ~3 min.
- The Super release recipe needs the router fix in #8217 to get through CUDA graph capture.

File: `tests/functional_tests/test_cases/nemotron/nemotron3_super_release_gb200/model_config.yaml` · line 16

**Regenerate both Super baselines before enabling exact comparison.**

Both the [Super golden](https://github.com/NVIDIA/Megatron-LM/blob/7f3bb510e3ad6de9512fab13c9b6c55f5a5394e6/tests/functional_tests/test_cases/nemotron/nemotron3_super_release_gb200/golden_values_dev_dgx_gb200.json#L1-L11) and the [Super SM golden](https://github.com/NVIDIA/Megatron-LM/blob/7f3bb510e3ad6de9512fab13c9b6c55f5a5394e6/tests/functional_tests/test_cases/nemotron/nemotron3_super_release_gb200_sm/golden_values_dev_dgx_gb200.json#L1-L11) still contain rounded losses without `"value_precision": "full"`. Removing `NON_DETERMINSTIC_RESULTS` enables `DeterministicTest`, but [the metric model defaults to legacy precision](https://github.com/NVIDIA/Megatron-LM/blob/7f3bb510e3ad6de9512fab13c9b6c55f5a5394e6/tests/functional_tests/python_test_utils/common.py#L81-L86), and [the comparison then rounds both sides to five decimals](https://github.com/NVIDIA/Megatron-LM/blob/7f3bb510e3ad6de9512fab13c9b6c55f5a5394e6/tests/functional_tests/python_test_utils/common.py#L366-L373). For example, `float32(10.78729)` and its next larger float32 value both round to the checked-in Super step-1 loss and both pass, despite differing by one ULP. These newly deterministic recipes therefore still miss differences that the intended bit-exact check should reject.

**Correction:** regenerate both Super golden JSONs from their corresponding deterministic runs with the real recipe data and topology, retaining the full-precision markers emitted by the existing extractor. Do not simply add markers to the rounded samples. Exact replacement values require captured run output, so no numeric patch can be justified from source alone.

**Preservation and acceptance (proposed, not executed):** each regenerated deterministic capture should pass against its own baseline; changing one recorded `lm loss` sample by one float32 ULP must fail. Check that both files carry full-precision markers. Keep the Lightning full-precision goldens unchanged, and retain approximate timing/memory checks. Do not remove legacy compatibility globally: [the existing regression tests](https://github.com/NVIDIA/Megatron-LM/blob/7f3bb510e3ad6de9512fab13c9b6c55f5a5394e6/tests/functional_tests/python_test_utils/test_common.py#L189-L210) must still accept five-decimal matching for untouched legacy goldens and reject a one-ULP mismatch for full-precision goldens.
