# Bound MFSDP v2 MXFP8 buffer padding by row width

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8355) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Prevent MFSDP v2 OOMs during initialization or CUDA graph capture caused by excessive MXFP8 buffer padding when an FSDP unit contains weights with different row widths.

MXFP8 block-atomic layouts align each data-parallel shard to 32 rows of every tensor in a parameter group. Grouping only by dtype and `requires_grad` makes this alignment depend on the least common multiple of unrelated row widths. At 256 data-parallel ranks, a representative DeepSeek V3 dense layer with 231,145,472 logical elements expands to **2,818,572,288 padded elements**. Replicated MXFP8 data and scale planes alone then occupy about **5.414 GiB per layer**.

Group MXFP8 parameters by row width as well as dtype and `requires_grad`. The same example now uses **264,241,152 padded elements**, or about **0.508 GiB** for those compute-weight planes. Requested parameter, gradient, and optimizer placements remain unchanged. Floating-point parameter grouping is unchanged.

Add a regression test using full-size meta parameter shapes and update the existing MXFP8 training/reference test to validate multiple quantized groups across ZeRO-3, ZeRO-2, and unsharded placements. More parameter groups can increase collective count; this change bounds the padding cost.

## Validation

- Four focused GPU test cases passed on each of two ranks: the new padding regression and all three MXFP8 training/reference placement cases.
- An earlier Megatron-Bridge integration run using HybridEP completed 100 training iterations on 256 GPUs with MXFP8, EP=64, four optimizer instances, dense `optim_grads`/outer `optim`, and expert `optim_grads_params`/outer `no_shard`. All 256 ranks completed full-iteration CUDA graph capture. Every logged LM loss and gradient norm was finite, with no skipped or NaN iterations; LM loss decreased from 11.895 to 4.760.
- That earlier integration run averaged **942.8 model TFLOP/s/GPU** at **4.518 seconds/step** over steps 51–100. This is the measured Bridge integration configuration, not an isolated Core performance comparison.
- A subsequent matched 256-GPU comparison used NCCL EP and dense `optim_grads_params`/outer `optim`, retaining expert sharding, MXFP8, EP=64, four optimizer instances, GBS=1024, MBS=1, sequence length 4096, and all 61 layers plus MTP. Both variants used Core `60547a3f419bd8027bb6ffb91793c2fa99ad97ed` with the same pre-existing kwargs-aware expert-hook change; the production-source difference was this row-width grouping fix.
- **GBS=1024 without the fix:** three finite warmup steps, then CUDA OOM during graph capture on step 4; 256 capture-start messages and zero completion messages. `allocate_partial_grad_buffer()` requested **15.75 GiB** with **6.03 GiB free** on one reported rank. There is no steady-state throughput result for that run.
- **GBS=512 / GA=2 without the fix:** A follow-up changed only global batch size (MBS=1, training DP=256), retaining the same NCCL EP, precision, sharding, activation offload, and graph settings. It also OOMed on capture step 4 after three finite warmup steps; 256 capture-start messages and zero completions. The same gradient-buffer allocation requested **15.75 GiB**, with **8.53 GiB free** in the first report; PyTorch held **253.39 GiB**, including **54.59 GiB in private pools**. LM losses were **11.89582, 11.89472, 10.51192** and gradient norms **24.326, 24.337, 109.583**, with zero skipped/NaN counters. The job ended FAILED (143:0) after distributed abort. There is no replay or steady-state throughput result; reducing GA alone was insufficient.
- **HybridEP at GBS=512 / GA=2 without the fix:** A subsequent 256-GPU run changed only the dispatcher from NCCL EP to HybridEP and added its four GB300 backend environment settings, retaining dense/expert ZeRO-3 and all other training settings. Preflight verified the full resolved configuration against the GBS512 NCCL EP run. It also OOMed on capture step 4 in `allocate_partial_grad_buffer()`, requesting **15.75 GiB** with **9.24 GiB free** in the first report. Three finite warmup steps had LM losses **11.89582, 11.89471, 10.51057** and gradient norms **24.326, 24.338, 109.924**, with zero skipped/NaN counters. Logs contain **256 capture-start messages and zero completions** (markers lack rank IDs). Job 1171742 ended FAILED (143:0); no successful replay or steady-state throughput was available. The dispatcher change did not resolve this no-padding failure. This differs from the earlier successful HybridEP run, which used the fix and dense ZeRO-2.
- **HybridEP without CUDA graphs, GBS=512 / GA=2, without the padding fix:** A follow-up changed only `model.cuda_graph_impl` from `full_iteration` to `none` (plus the output path), retaining the prior HybridEP configuration and sources. Preflight and actual-config comparisons verified this isolation. Job 1175214 completed **34 contiguous finite iterations**, with zero skipped/NaN counters and no logged CUDA OOM or training graph capture/replay, before Slurm terminated it at the **35-minute time limit**. It did not complete the 100-step target. As a partial-run measurement, **steps 11–34 averaged 50.9875 model TFLOP/s/GPU at 42.0414 seconds/step**; steps 21–34 averaged 50.9071 at 42.1171 seconds/step. There is no steps 51–100 result. LM loss went from 11.89582 to 8.114134; all recorded gradient norms were finite. Rank 0's logged allocator peaks through step 2 were 238.43 GB allocated / 284.58 GB reserved (decimal GB; not an all-rank or full-run peak). Eager execution passed the prior capture-failure point for the observed 34 steps, but this is not a completed 100-step validation or an isolated speed comparison against a successful graph-enabled run. The logs do not establish the cause of the low eager throughput.

- **NCCL EP at GBS=1024 with the fix:** 100 finite iterations, zero skipped/NaN counters, 256 capture-start/completion messages, and replay through step 100. LM loss declined **11.89503 → 3.542798**. Gradient norms were **0.458–166.501** overall (maximum at warmup step 3), **0.458–13.307** on steps 11–100, and **1.376–5.153** on steps 51–100.
- The NCCL EP run's steps 51–100 averaged **843.228 model TFLOP/s/GPU** at **5.0517 seconds/step**. Rank 0's logged peak through step 4 was **211.74 GB allocated / 231.99 GB reserved** (decimal GB; not an all-rank or full-run peak). The job and all steps exited **COMPLETED, 0:0**, with no logged forced termination or shutdown timeout using a 180-second cleanup grace.
- After rebasing onto current `main`, all four focused cases passed on each of two ranks. The repository autoformatter passed in check mode after one regression-test line-wrap adjustment: Black, isort, pylint (10.00/10), Ruff, and `git diff --check` passed. Its non-blocking mypy step reported six diagnostics: five missing Transformer Engine typing markers and one existing `FsdpModule.register_load_state_dict_pre_hook` attribute diagnostic.

The integration run uses mock data and forced balanced routing, so it does not establish real-data convergence or production routing performance. Throughput is a modeled FLOP rate, not a hardware utilization percentage.
