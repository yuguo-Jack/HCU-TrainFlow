# [Core][BatchInvariant] Return torch's result for empty and 0-dim inputs in the batch-invariant log_softmax

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8963) · state: open · merged: False

## Original PR description

# What does this PR do?

Makes the batch-invariant `log_softmax` accept every shape `torch.log_softmax` accepts along the last dim, including an empty last dim, zero rows and 0-dim tensors.

**Bug.** `enable_batch_invariant_mode` registers the Triton `log_softmax` for `aten::_log_softmax` under every backend (`te_native`, `triton`, `deepgemm`). While the mode is on, it therefore serves every `torch.log_softmax` / `F.log_softmax` on CUDA in the process. Its launcher flattened the input with `input.reshape(-1, input.shape[-1])`, so:

- an empty last dim (`[3, 0]`, `[0, 0]`, `[2, 3, 0]`) raised `RuntimeError: cannot reshape tensor of 0 elements into shape [-1, 0]`, because the row count of an empty row is ambiguous;
- a 0-dim tensor raised `IndexError` for `dim=-1` (it has no `shape[-1]`), and `ValueError` ("only supports log_softmax along the last dimension") for `dim=0`, which torch treats as its last dim.

`torch.log_softmax` returns an empty tensor of the input's shape for the first case and `0` for the second (NaN for a non-finite value). Inputs with zero rows but a non-empty last dim (`[0, 5]`) already worked.

Inference never calls `log_softmax` with an empty vocabulary or a 0-dim tensor, so the bug is a latent crash, not a wrong result. It is reachable from any other code that runs under batch-invariant mode.

## Fix

- When the input has no elements, the launcher returns an empty contiguous tensor of the input's shape and dtype without launching the kernel.
- A 0-dim input is one row of one element, and the last-dim check accepts `dim` 0 or -1 for it, as torch does. The kernel gives `x - x - log(1) = 0`, and NaN for a non-finite input, as torch does.
- The kernel, the launch and the results for every non-empty input of one or more dims are unchanged. Nothing changes on the hot path; the new branch reads only `numel()` and `ndim`.

## Tests

`tests/unit_tests/transformer/test_te_layers_batch_invariant.py::test_log_softmax_handles_empty_and_0d_inputs` (10 cases: `0`, `3x0`, `0x0`, `2x3x0`, `0x5`, `2x0x7`, and 0-dim inputs holding a random value, +inf, -inf and NaN). It is placed next to the `mean` tests for the same module. For each input, with `dim=-1` and with the last dim's index, it compares `log_softmax(x)`, and `torch.log_softmax(x)` under batch-invariant mode, against `torch.log_softmax` outside the mode. It checks shape and dtype, and values exactly, with NaN matching NaN.

On `main`, every case fails except the two controls `0x5` and `2x0x7`, with the errors above. With the fix, all ten pass.

- **H100, first commit** (dfw 21232738): the six cases at that commit passed, and on `main` the four non-control cases failed.
- **Review follow-up:** the `0` case and the non-finite 0-dim cases were checked on CPU under the Triton interpreter (they pass with the fix and raise on `main`). Their GPU run is pending.

The empty-last-dim crash was also confirmed on H100 by the step 4 oracle (dfw 21222522, `test_log_softmax.py::test_empty_inputs[3x0]`).

`tools/check_kernel_determinism_coverage.py` passes: the changed launcher's registered test file (`test_te_layers_batch_invariant.py`) changes. The existing replay test (`test_batch_invariant_kernels_replay`) covers the unchanged kernel.

## Follow-up: review feedback

- The test also covers the 1-D empty input `(0,)`, which crashed on `main` as well, and 0-dim inputs holding +inf, -inf and NaN, so the "NaN for a non-finite input" behavior is checked on the GPU.
- Not changed, out of scope: a non-last `dim` and `F.log_softmax(fp16, dtype=torch.float32)` (`half_to_float`) still raise. Every Megatron caller uses the last dim, and batch-invariant mode is BF16-only. Keeping row invariance for another dim would take a `movedim` + `contiguous` follow-up.
