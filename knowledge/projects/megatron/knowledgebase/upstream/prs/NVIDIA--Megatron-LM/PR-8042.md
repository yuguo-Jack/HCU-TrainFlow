# Filter optimizer grad-norm duplicates by the collection's TP and GTP groups

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8042) · state: open · merged: False

## Original PR description

**Why.** Optimizers built from a `ProcessGroupCollection` copy its `tp`, `expt_tp`, `gtp_remat` and `expt_gtp_remat` groups for the grad-norm and zero-count duplicate filters, but the filters read the global rank whenever a group is `None`. A model whose collection turns GTP off (`gtp_remat=None`) next to a global grid with GTP=2 drops every replicated parameter on global GTP rank 1, so its gradient norm is under-counted and clipping is too weak. With `expt_tp=None`, expert parameters are filtered by the dense TP rank and under-counted as well.

**What.**
- `param_is_not_tensor_parallel_duplicate`, `param_is_not_gtp_duplicate` and `count_zeros_fp32` take a keyword-only `use_global_fallback` (default `True`, unchanged). With `False`, a `None` group marks an axis that is off.
- `set_duplicate_filter_groups(optimizer, pg_collection)` reads the fields with `vars()`: `tp` is required, `expt_tp` defaults to `tp` only when unset, and the GTP groups resolve the way the model's layers resolve them. Both optimizer builders and `LayerWiseDistributedOptimizer` use it, and their norm and zero-count paths pass `use_global_fallback=False`.

**Tests.** New cases in `test_grad_norm_gtp_invariance.py` run with the global accessors patched to raise: TP and GTP axes off next to a global TP=2/GTP=2 grid, expert TP different from TP, and a collection without `tp`. They fail on main and pass here on 4 GPUs. Optimizer, layer-wise, Lion and emerging-optimizer tests match main.

**Compatibility.** The standard grid filters the same parameters. A collection passed to the optimizer builders must set `tp` (`None` when TP is off).
