### Abort label updates when active reviews cannot be retrieved

**Failure:** Consider a non-draft PR changing `megatron/training/training.py`, with a training approval and an existing `Approved` label. If the GraphQL request fails, [_get_latest_reviews](https://github.com/NVIDIA/Megatron-LM/blob/4cbc3ef0f4e0d7b286dd518d0f555da3e210b13c/tests/test_utils/python_scripts/swap_pr_labels.py#L162-L180) now returns `{}`. The caller interprets that as a successful empty review history, marks training pending, and [removes `Approved`](https://github.com/NVIDIA/Megatron-LM/blob/4cbc3ef0f4e0d7b286dd518d0f555da3e210b13c/tests/test_utils/python_scripts/swap_pr_labels.py#L248-L275). A PR in Final Review can similarly be demoted to expert review. The workflow then succeeds despite having changed labels using unavailable data. Expected behavior is to abort without label mutations. Responses containing GraphQL errors alongside readable partial data are also no longer rejected.

**Correction:** Restore failure propagation and explicit GraphQL-error rejection in `_get_latest_reviews`. Keep the previous request timeout so an unavailable API cannot leave evaluation waiting indefinitely. Suggested patch, targeting that function:

-            nodes = resp.json()["data"]["repository"]["pullRequest"]["latestReviews"]["nodes"]

The invariant is that unsuccessful or partial review retrieval never reaches label mutation; a successfully retrieved empty history must remain distinct from failure.

**Preservation and acceptance — proposed, not executed:** Use a training-only fixture with nonempty training membership. ### Keep final-team change requests blocking expert-stage advancement

**Failure:** Take a non-draft PR changing only `megatron/training/training.py`, with no review-stage label. Let a training member approve and a `core-nemo` member request changes. Training is satisfied, `final_required` is empty, and `pending_final` contains the core reviewer. This assignment nevertheless makes `needs_final_review` false, so the [expert-stage handler](https://github.com/NVIDIA/Megatron-LM/blob/4cbc3ef0f4e0d7b286dd518d0f555da3e210b13c/tests/test_utils/python_scripts/swap_pr_labels.py#L304-L324) adds `Approved` despite the outstanding change request. The same failure applies to a `core-adlr` reviewer. Expected behavior is to enter Final Review until that blocker is resolved, consistent with the other stage handlers.

**Correction:** Restore the blocker-aware decision without restoring the author exemption:

```suggestion
        needs_final_review = bool(final_required or final_non_approvers)
```

The invariant is that an active final-team change request blocks approval even when changed files do not require that team's CODEOWNERS approval.

**Preservation and acceptance — proposed:** With training membership `{trainer}`, core memberships containing distinct reviewers, and reviews `{trainer: APPROVED, core-reviewer: CHANGES_REQUESTED}`, assert that Expert Review adds only `Final Review`, testing each core team. With no core blocker, the same approved training-only PR must add `Approved`; with training still pending, it must not advance. A required core-team approval must remain necessary for core-owned changes. Retain the [deleted blocker tests'](https://github.com/NVIDIA/Megatron-LM/blob/7d6895ac6a3ee9e16c53f573f363d2a52b88bf94/tests/test_utils/python_scripts/test_codeowners_approval.py#L193-L229) distinctions: a core approval is not a blocker; an active core change request keeps Final Review pending; from Approved it removes `Approved` and restores Final Review. Adapt their setup to satisfy training approval rather than rely on the removed RL exemption. Drafts must remain unchanged. Suggested code and checks were traced statically, not executed.
