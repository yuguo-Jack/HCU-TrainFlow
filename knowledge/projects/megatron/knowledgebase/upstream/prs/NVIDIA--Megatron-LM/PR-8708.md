# [Core][BatchInvariant] Run native aten GEMMs on cuBLASLt with a starved workspace under every backend

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8708) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes batch-invariant mode keep the aten GEMMs it leaves native from splitting K:
- under the default `te_native` backend, every aten GEMM, such as the bias-free `torch.matmul` of `ColumnParallelLinear`, which the GPT output layer uses;
- under `deepgemm` and `triton`, `aten::bmm` and `aten::baddbmm`, which `einsum` lowers to.

**Bug.** `te_native` keeps the native GEMM kernels. It gets batch invariance by starving their workspace, which rules out split-K:
- aten GEMMs: it pins `CUBLASLT_WORKSPACE_SIZE=0`;
- Transformer Engine GEMMs: it patches TE's workspace size.

`CUBLASLT_WORKSPACE_SIZE` is a cuBLASLt setting, but PyTorch's preferred BLAS library on CUDA is cuBLAS. A plain `torch.matmul` therefore ran on cuBLAS with its full workspace, where cuBLAS can choose a split-K variant by row count. A token's output then depended on how many other tokens shared its batch.

An inference-vs-training configuration matrix on H100 hit this:
- Three batch-invariant MLA rows (TP=2, or TP=1 with EP=2) lost bit-equality with their eager twins once CUDA graphs padded steps to other token counts.
- A per-module trace of one row found every module bit-identical except the output layer. From identical inputs, it gave different logits for 7 tokens.
- A GEMM probe on H100 reproduced it with hidden size 512 and 50 output columns, the shape of a 100-token vocabulary at TP=2. Rows of `x[:M] @ w.T` differ between M=192 or 256 and M=16 or 384. The result is the same whether the mode is enabled before or after the first GEMM.
- With cuBLASLt preferred, every probed shape is invariant.

The bug is not specific to CUDA graphs. Any two batches with different token counts can pick different split-K variants for the same token.

`deepgemm` and `triton` replace `aten::mm` and `aten::addmm` with batch-invariant kernels, but leave `aten::bmm` and `aten::baddbmm` on cuBLAS in the same way. Such GEMMs are reachable in batch-invariant mode:
- the einsums of `AbsorbedMLA` and of DeepSeek-V4 attention in forwards without an inference context (the grouped output projection has a large K);
- MLA's absorbed-decode einsums, until #8571 stops batch-invariant MLA from absorbing;
- mHC's per-token `bmm`, whose K is the stream count, too small to split.

**Fix.** Enabling batch-invariant mode now does the following under every backend:
- It pins cuBLASLt's workspace to 0. Before, only `te_native` did, and only through `CUBLASLT_WORKSPACE_SIZE`, which cuBLASLt reads once, at its first GEMM. On PyTorch 2.14 and later, the mode now sets the size through `torch.backends.cuda.cublaslt_workspace_size`. PyTorch looks that size up at every GEMM, so the pin holds even when the mode is enabled after the first GEMM. Older PyTorch keeps the environment-variable pin.
- It prefers cuBLASLt, so the GEMMs the backend leaves native run under the pinned workspace. This uses `torch.backends.cuda.preferred_blas_library`, an API that PyTorch marks experimental.
- It raises PyTorch's `bgemm_internal_cublaslt error` warning as an error. PyTorch issues this warning when cuBLASLt fails a GEMM and it reruns the GEMM on cuBLAS with the full workspace, which would lose invariance silently.

Disabling the mode restores the workspace size, the library, the environment variable and the warning filters. `te_native` also keeps its TE workspace patch. This matches what the backend's docstrings already state ("keeps the native cuBLASLt kernels (aten and TE)").

Two limits remain, and the docstring states them:
- PyTorch always runs fp32 and fp64 matrix-vector and dot products on cuBLAS.
- Before PyTorch 2.14, the mode must be enabled before the first GEMM, as `initialize_megatron` does.

The warning for a late enable now fires only on PyTorch without `cublaslt_workspace_size`. It keys on CUDA initialization, which importing `megatron.core` on a GPU already triggers, so it used to fire even when the mode was enabled in time. On 2.14 and later a late enable is safe, so the warning is no longer needed there.

**Performance.** The switch is process-global while the mode is on.
- Training in batch-invariant mode also runs its aten GEMMs on cuBLASLt without split-K. Examples are the output layer's dgrad, and its wgrad when `gradient_accumulation_fusion` is off. GEMMs with few output tiles lose the parallelism that split-K gave them.
- Eager inference pays cuBLASLt's per-call descriptor setup and heuristic query. CUDA-graph replay does not.
- Under `deepgemm` and `triton`, only `bmm` and `baddbmm` change. TE GEMMs are unchanged.

**Tests.** Both tests are in `tests/unit_tests/transformer/test_te_layers_batch_invariant.py`, the determinism test registered for `batch_invariant_kernels.py`:
- `test_batch_invariant_prefers_cublaslt_and_restores_it` runs for each backend. It checks the preferred library, the workspace pin and the fallback error inside the mode, and that they are restored after it.
- `test_native_aten_gemms_batch_invariant` runs in a fresh process for `te_native` and `triton` with the mode enabled before the first GEMM, and for `te_native` with the mode enabled after a GEMM on cuBLASLt with a 1 MiB workspace (PyTorch 2.14 and later). For `torch.matmul` (`aten::mm`) and a per-head `einsum` (`aten::bmm`), it checks that row slices are bit-equal to the full batch's rows.
  - Shapes: the output-layer shape (K=512, N=50) and three neighbors at 16 to 384 rows. Also large-K, small-N shapes (K=8192 or 16384, N=8 or 64) at 1 to 64 rows, where cuBLASLt with a workspace splits K.
  - With PyTorch 2.14 it also checks that cuBLASLt reports a zero workspace.
  - Setting `MCORE_BI_TEST_CUBLASLT_WORKSPACE_KIB` gives cuBLASLt a real workspace instead. Then the test should fail, which shows on a given GPU that the shapes do split K.

On H100 in the CI image, the first version of these tests failed on `main` in 2 cases and passed with this PR:
- The preferred library was cuBLAS.
- Rows of the output-layer GEMM differed at 128 rows.

With this PR, the neighbor tests also passed: `test_te_layers_batch_invariant.py` (45 passed, 1 skipped because FlashAttention-3 is missing) and `test_gpt_model_batch_invariant.py` (4 passed). The inference-vs-training matrix passed all 57 tasks. With the review changes (dfw 21004395): the 6 regression cases pass with this PR and fail on `main`. As a control, the subprocess test fails when a 1 MiB or 32 MiB cuBLASLt workspace replaces the pin, so its new shapes do split K. The neighbors pass: `test_te_layers_batch_invariant.py` (49), `test_gpt_model_batch_invariant.py` (4), the te_native vLLM MoE and FP8 cases, `test_batch_invariant_deepgemm_stride.py`, and the H100 cases of `test_te_wrappers.py` and `test_inference_kernels.py` (their SM100 cases skip). The 57-task inference-vs-training matrix passes on integration trees of current `main` with every open fix (dfw 21004395, 21007036).

**Interaction with #8573.** #8573 rolls back a failed enable by calling `disable_batch_invariant_mode()`. With this PR, that call also restores the BLAS library, the workspace pin and the warning filter. The two PRs conflict textually in two places:
- `enable_batch_invariant_mode`: #8573 wraps its steps in `try`, and this PR's new call belongs inside it.
- The imports of the test file.

Whichever PR lands second resolves both. It also adds `torch.backends.cuda.preferred_blas_library()` to the state that `test_enable_batch_invariant_mode_rolls_back_on_failure` checks.
