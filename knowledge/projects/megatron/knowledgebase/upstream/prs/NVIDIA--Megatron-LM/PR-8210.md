# Add Mixture-of-Kittens MoE backend on main

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8210) · state: closed · merged: True

## Original PR description

## What does this PR do?

Enable `moe_megakernel_backend=mok` on main, including the gated shared experts used by Qwen3.5. MCore supplies routing and owns parameters, optimizer state, and checkpoints; MoK executes dispatch, routed/shared experts, and combine.

Ports #6572, #7289, and #7391, building on the earlier main adaptation in #7695. Related to #5795 and #7756.

- Support BF16 and native MXFP8 routed weights, BF16 shared experts, and an optional BF16 sigmoid shared-output gate through `moe_shared_expert_gate`.
- Preserve native parameter aliases, DDP hooks, and canonical checkpoint entries, including the gate's FP32/BF16 `main_grad`. Keep native weight payloads zero-copy and refresh converted scales after parameter updates.
- Preserve packed-sequence/hash-routing inputs and main's precision-aware whole-MoE recomputation.
- Retain TP=1/ETP=1 and the existing configuration restrictions. Native shared-expert fallback for TP>1, latent MoE, GTP, native shared overlap, and per-layer MoE graph capture remain outside this PR.

## External dependency

Pin the merged [MoK integration snapshot `7a8cfb7`](https://github.com/QiZhangNV/mixture-of-kittens/tree/7a8cfb7fdd96a1cfba506caf4756c6c86073399a), which includes shared-output-gate support. Remove the now-upstreamed local build patch; retain both SM100/SM103 targets and the existing AMD64/H100 skip.

## Reviewer guide

Start with `moe_layer.py` → `mok/backend.py` → `mok/runtime.py`, then `parameter_bridge.py` and `weights.py`. MCore remains the owner of routing, parameters, optimizer state, DDP hooks, and checkpoint entries. MoK owns the fused dispatch/expert/combine execution and its workspace/saved forward state. The GEMM kernels live in the pinned external dependency.

- On four GB200 GPUs, all 56 MCore configuration/adapter tests and nine upstream gated-kernel tests passed on every rank.
- Actual gated forward/backward, gate gradients, microbatch accumulation, parameter updates, and checkpoint ownership/reload passed for BF16/MXFP8 and FP32/BF16 main gradients. Ungated BF16 and DSv4-sized MXFP8 regression checks also passed.

MXFP8 loss/gradient-norm/parameter-norm values matched exactly at iterations 5–8 across eager, resume, graph, and an independent eager repeat. BF16 graph matched the independent eager repeat; resume's maximum deviations were smaller than the eager-repeat differences.
- Both Blackwell cubins compiled successfully. Formatting/lint, syntax, and kernel determinism coverage checks passed.
- The previous [CI run](https://github.com/NVIDIA/Megatron-LM/actions/runs/39392759688) exposed a native-dispatcher input-hook integration failure; the follow-up guards that call and preserves MoK boolean routing. CPU route/metadata/gradient boundary checks and formatting/lint/determinism-coverage checks passed. The branch is rebased onto main `29e1a7b`, which also includes the existing MFSDP test-setup fix #8326. [Fresh distributed CI](https://github.com/NVIDIA/Megatron-LM/actions/runs/39539853118) is running on `604e820aa4`; DCO and process-group checks have passed.

These are functional proxy checks, not a full Qwen3.5/DSv4 performance result. Multi-node/EP8+, routed expert DP>1, and Muon were not qualified here.

## Reject unsupported FP64 routing during MOK configuration

An otherwise-supported BF16 MOK setup—for example, hidden/intermediate size 256, 512 local tokens, and two experts/top-k two—with `moe_router_dtype="fp64"` and `moe_router_fusion=False` passes configuration validation but fails on its first forward. [Router.gating](https://github.com/NVIDIA/Megatron-LM/blob/0c6cf7bd83aecacd3c1fb08fc82355a1d209bf6c/megatron/core/transformer/moe/router.py#L141-L147) produces double logits, [routing preserves that dtype](https://github.com/NVIDIA/Megatron-LM/blob/0c6cf7bd83aecacd3c1fb08fc82355a1d209bf6c/megatron/core/transformer/moe/moe_utils.py#L1034-L1055), and the new [route adapter](https://github.com/NVIDIA/Megatron-LM/blob/0c6cf7bd83aecacd3c1fb08fc82355a1d209bf6c/megatron/core/transformer/moe/megakernel/mok/route_adapter.py#L116-L121) raises `TypeError`.

Until MOK supports FP64 weighted averaging, reject this combination explicitly during configuration rather than after distributed model construction. Inside the existing MOK-only block in [TransformerConfig.__post_init__](https://github.com/NVIDIA/Megatron-LM/blob/0c6cf7bd83aecacd3c1fb08fc82355a1d209bf6c/megatron/core/transformer/transformer_config.py#L2609-L2623), add:

```python
if self.moe_router_dtype == "fp64":
    raise ValueError("MOK does not support moe_router_dtype='fp64'; use 'fp32' instead")
```

Also document the restriction in the [MOK support table](https://github.com/NVIDIA/Megatron-LM/blob/0c6cf7bd83aecacd3c1fb08fc82355a1d209bf6c/megatron/core/transformer/moe/README.md#L625-L636). Do not simply remove the converter's dtype check: it produces FP32 weights, whereas the [router option](https://github.com/NVIDIA/Megatron-LM/blob/0c6cf7bd83aecacd3c1fb08fc82355a1d209bf6c/megatron/core/transformer/transformer_config.py#L998-L1001) also controls weighted-averaging precision.

**Acceptance and preservation:** Add configuration cases to [the MOK configuration tests](https://github.com/NVIDIA/Megatron-LM/blob/0c6cf7bd83aecacd3c1fb08fc82355a1d209bf6c/tests/unit_tests/transformer/moe/test_mok_weights.py#L98-L131): MOK plus `"fp64"` must raise the explicit error; MOK with `None` or `"fp32"` and native MoE with `"fp64"` must remain accepted. Retain the converter's existing exact FP16/BF16/FP32 forward/backward checks, including missing-route padding.

This patch and the proposed checks are source-reasoned, not executed; verify before adopting. Static light review covered all changed files and affected interfaces. Tests/builds were not run, and the external pinned MOK implementation was unavailable for independent inspection.
