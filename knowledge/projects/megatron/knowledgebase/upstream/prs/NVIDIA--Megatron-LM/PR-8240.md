# test(moe): refresh goldens for the DeepSeek proxy optimizer CUDA graph test

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8240) · state: closed · merged: True

## Original PR description

## What does this PR do?

Refreshes the goldens of `moe/deepseek_proxy_mfsdp_v2_ep2_bf16_cg_optim_1node` (GB200, `dev`). This test runs only in GitLab's `mr` scope and has failed on every `main` pipeline since #7407 added it. Only the golden file changes.

Latest failure: [job 487847526](https://gitlab-master.nvidia.com/ADLR/megatron-lm/-/jobs/487847526) in `main` pipeline [73895766](https://gitlab-master.nvidia.com/ADLR/megatron-lm/-/pipelines/73895766) at 80781ab0a.

- `mem-allocated-bytes` is 101,978,112 B (+13.2%) above the golden at every step, so the 5% check fails.
- `lm loss` fails the exact check. Step 1 is 10.901482582 against 10.901466370, and the largest relative difference is 2.3e-4. The approximate check passes.

## Why the goldens are wrong

#7407 recorded the goldens from a manual 4-GPU run, not from CI. That run needed `NVTE_CUTEDSL_FUSED_GROUPED_MLP=1` exported by hand to get past Megatron's op-fuser assertion; #7495 later added it to the recipe. This test's history on `main` shows the goldens never matched CI:

| `main` range | CI result |
| --- | --- |
| a2585b244 (#7407, 09-17) → c711dc0a7 (09-21) | Fails at init: the recipe lacks `NVTE_CUTEDSL_FUSED_GROUPED_MLP` |
| dae135048 (#7495, 09-22) → 1cb9fe85c (10-02) | Trains. `mem-allocated-bytes` is +100,667,392 B at every step, and `lm loss` already differs from step 1 |
| 16f377ea2 (#6615, 10-02) → 80781ab0a (10-14) | `mem-allocated-bytes` is +101,978,112 B, and `lm loss` is unchanged |

All 50 `lm loss` values are bit-identical in every run from 09-22 to 10-14. That covers the TE 2.20 bumps, NGC 26.09, the cuBLAS 13.8.1 image change, and #6615.

- **+100,667,392 B, present from the first completed CI run:** Transformer Engine's grouped-tensor GEMM workspaces. TE keeps these allocated on purpose.
  - For bf16 on GB200, every routed-expert GEMM goes through `general_grouped_gemm_for_grouped_tensor`.
  - Since TE#3171, that path keeps one `lru_cache`d cuBLAS workspace per layout (TN fprop, NN dgrad, NT wgrad), each 32 MiB + 1 KiB, plus a setup workspace (a 624 B request, which occupies a 1,024 B block).
  - Total: 3 × 33,555,456 + 1,024 = 100,667,392 B.
  - TE builds without TE#3171 (2.17.x, and some 2.18.0 builds such as `release_v2.18_nemo_26.08`) allocate these per call, so they are freed before memory is sampled at the end of an iteration.
  - Megatron has pinned a TE with TE#3171 since #6917 (08-28), before the goldens were recorded. The golden run therefore used a different TE build, and these goldens could never have matched CI.
  - #7495 saw the same gap ("about 96 MiB above the existing golden") with a bit-identical loss, and left the golden unchanged.
- **+1,310,720 B since #6615:** `_HybridEPManager.topk_idx`, an int16 `[32768, 4]` tensor (262,144 B) in each of the 5 MoE layers.
  - #6615 derives these dense top-k ids from the bool routing map when DeepEP ≥ 10d4dd73 (#7358) is installed.
  - They stay referenced on each layer's dispatcher after `combine()`.
  - The amount is constant from step 1 and is 0.16% of the metric, so it does not cause the failure.
- **`lm loss`:** it moved between 3226303b3, where #7495 still matched the goldens exactly, and dae135048, the first CI run to get past init.
  - In that window, TE 2.19 (#7379) is the only identified change on this config's forward path. Its `ScaledSwiGLU` op now calls the fused `tex.scaled_swiglu`, which rounds `silu(a)·b·prob` to bf16 once instead of twice.
  - The DeepEP pin bump (#7358) also landed then; DeepEP's tests expect it to be bit-neutral.
  - No Megatron change in `3226303b3..main` alters this config's forward math.
  - Library bumps that change numerics refresh their own goldens, but this test runs only on GitLab, so no bump PR ever refreshed it.

## How was the new golden produced?

- The file is copied byte-for-byte from the `results/…/golden_values_dev_dgx_gb200.json` artifact of job 487847526. This is the file `download_golden_values.py --source gitlab` would move.
  - I didn't run that script over the whole pipeline. That pipeline's `hybrid_mhc_tp2_pp2_mtp` job hit `Disk quota exceeded` and left a 0-byte golden file, which the script would have copied over that test's good goldens.
- The job ran the recipe three times, on three GB200 hosts (`nvl72158`, `nvl72082`, `nvl72023`). The TensorBoard scalars for `lm loss`, `num-zeros`, `mem-allocated-bytes` and `mem-max-allocated-bytes` were bit-identical across all three runs.
- I re-ran CI's comparison (`test_pretraining_regular_pipeline.py`, with `--actual-values-path` set to the job's output):
  - with the old goldens it fails on `lm loss, mem-allocated-bytes`, as CI did;
  - with the new goldens it passes.
