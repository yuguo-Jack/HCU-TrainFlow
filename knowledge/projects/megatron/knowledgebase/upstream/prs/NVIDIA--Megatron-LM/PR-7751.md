# Enable BF16 in DeepSeek recipes and reject mixed-dtype MFSDP fusion

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7751) · state: open · merged: False

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

## Problem

MFSDP v1 can silently scale gradients incorrectly when division fusion is enabled and a coalesced reduction group mixes BF16 and FP32 gradient buckets. This PR rejects that configuration during initialization and enables BF16 in the two affected DeepSeek FP8 recipes.

The existing [one-node](https://github.com/NVIDIA/Megatron-LM/blob/2f16cb1641702df7a88657ecc5ad2eee33476c6f/tests/functional_tests/test_cases/moe/deepseek_proxy_mfsdp_v1_ep2_1node/model_config.yaml#L25-L37) and [two-node](https://github.com/NVIDIA/Megatron-LM/blob/2f16cb1641702df7a88657ecc5ad2eee33476c6f/tests/functional_tests/test_cases/moe/deepseek_proxy_mfsdp_v1_ep2/model_config.yaml#L26-L38) recipes enable FP8 parameter gather but omit `--bf16`. Non-FP8 parameters therefore retain Megatron's [default FP32 dtype](https://github.com/NVIDIA/Megatron-LM/blob/ca07f7364b6dd2e682cf3f7f8d3a284e060b6fca/megatron/training/arguments.py#L1219-L1232). MFSDP's [default gradient policy](https://github.com/NVIDIA/Megatron-LM/blob/ca07f7364b6dd2e682cf3f7f8d3a284e060b6fca/megatron/core/distributed/fsdp/src/megatron_fsdp/param_and_grad_buffer.py#L2384-L2393) assigns BF16 gradients to FP8 weights and otherwise follows the parameter dtype. Consequently, norm/router gradients are FP32 while FP8-weight gradients are BF16 within the same FSDP unit.

MFSDP coalesces buckets by `(fsdp_unit_id, is_expert_param)`, omitting dtype from the grouping key. Whether this omission is intentional or itself a grouping bug needs further investigation. The confirmed failure is that preprocessing chooses `PREMUL_SUM` for FP32 and explicit scaling followed by `SUM` for BF16, but PyTorch's coalescing helper applies the first bucket's reduction operator to the entire call.

This MFSDP bug was previously masked by a separate PyTorch BF16 `PREMUL_SUM` scalar-dtype bug, which zeroed the affected gradients for factors such as `0.25`. The PyTorch bug is fixed in NGC 26.09, exposing the existing MFSDP bug reported in [#7735](https://github.com/NVIDIA/Megatron-LM/issues/7735): the already-scaled BF16 gradients receive the `PREMUL_SUM` factor again. The old stack zeroed these gradients; the new stack scales them twice. Both results are incorrect.

## Changes

- Add only `--bf16: true` to the one-node and two-node DeepSeek MFSDP v1 recipes. Retain the default gradient dtype policy, which now produces BF16 gradient buffers for both FP8 and non-FP8 parameters. These buckets all use the existing explicit-scaling/SUM path.
- Add an [initialization guard](https://github.com/NVIDIA/Megatron-LM/blob/ca07f7364b6dd2e682cf3f7f8d3a284e060b6fca/megatron/core/distributed/fsdp/src/megatron_fsdp/param_and_grad_buffer.py#L2593-L2614) that rejects fusion when a coalesced group has multiple gradient communication dtypes. The error identifies the dtypes and explains how to disable fusion or choose one communication dtype. The check honors dtype overrides, excludes parameters without gradient buffers, and permits different dtypes in separate coalesced groups.
- Document the restriction in the MCore and standalone configurations. Preserve `gradient_reduce_div_fusion=True`, the original `--no-gradient-reduce-div-fusion` CLI, and existing reduction preprocessing.

## Validation

Validated commit `ca07f7364` on oci-aga with four GB300 GPUs per node and deterministic mock data. Jobs `942282` (one node) and `942283` (two nodes) completed successfully.

- Both recipes completed 50 steps on their corresponding topologies in both NGC 26.08 and 26.09: four successful training runs. Runtime assertions confirmed BF16 gradient buffers throughout, no gradient dtype overrides, and fusion configured `True`.
- Loss, gradient norms, parameter norms, and zero counts were finite throughout. Mean absolute cross-image loss differences were 0.0330% for one node and 0.0541% for two nodes.
- Separate validation of the unchanged guard/helper passed 22 constructor/collective cases per rank on four GPUs in each image, including mixed-dtype rejection, homogeneous dtypes, overrides, separate units, frozen parameters, and real coalesced NCCL reduce-scatter.
- Verified tested source hashes and the original CLI's default-on/explicit-off behavior. Black, isort, pylint, Ruff, kernel determinism coverage, and `git diff --check` passed. The formatter's non-blocking mypy step reports missing dependencies and existing type errors in the isolated lint environment.

The verification harness is outside the changeset. These GB300/mock-data runs do not replace canonical GB200/Pile validation.

## Possible follow-up fixes

To support fusion with mixed gradient communication dtypes:

1. Explicitly scale all buckets and use a common SUM when a group requires incompatible operators; retain fusion for compatible groups.
2. Split coalescing groups by compatible process group, collective kind, communication dtype, reduction operator, and scaling factor.
3. Run reductions separately so each retains its own operator, at a potential communication-overhead cost.

Removing the BF16 exclusion also needs backend validation, including older supported PyTorch versions with the scalar-dtype bug. Matching operators alone does not ensure matching scaling factors.

Related to #7735. [Investigation and reproducer results](https://github.com/NVIDIA/Megatron-LM/issues/7735#issuecomment-5918205274).
