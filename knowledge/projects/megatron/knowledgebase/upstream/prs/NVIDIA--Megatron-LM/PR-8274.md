# Fix padding-token zeroing for quantized inference under CUDA graphs

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8274) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes padding-token zeroing in dynamic inference work inside local CUDA graphs. Today it is skipped on every replay, so with FP8/FP4 the padding rows reach the per-tensor amax with whatever stale memory they hold.

This is why `gpt_dynamic_inference_tp1_pp1_583m_cuda_graphs_fp8_logitsmatch` (GitLab, H100) has failed on every `main` pipeline since 2026-09-17, always with the same output: token 5 diverges from the golden.

## Root cause

#2585 added the zeroing to keep padding tokens out of FP8 amax. It indexes the rows with `inference_context.padding_slice`, a Python `slice(active_token_count, padded_active_token_count)`.

- **Capture:** under local CUDA graphs the slice is evaluated once, at capture. Dummy requests fill the graph exactly at that point, so the slice is empty and the graph records no zeroing.
- **Replay:** a graphed prefill or mixed step replayed with fewer real tokens than the graph holds leaves the padding rows of the attention output unwritten. The varlen kernel only covers the real sequences.
- **Effect:** those rows go through `linear_proj` into the residual stream, and from there into the tensorwise amax of every later FP8 GEMM.
- **Why it only surfaced on 09-17:** before #7093, `--deterministic-mode` NaN-filled uninitialized memory, and TE's amax ignores NaN, which hid the problem. #7093 turned that fill off.

| Site | Captured, so broken, under |
|---|---|
| `attention.py`, `core_attn_out` | layer and block scope |
| `ssm_inference.py`, SSM mixer output `y` | layer and block scope |
| `gpt_model.py`, `decoder_input` | block scope |
| `hybrid_model.py`, `decoder_input` | block scope |

## Fix

`DynamicInferenceContext.zero_padding_tokens(tensor, sequence_parallel_rank=0)` zeroes rows at or past `gpu_view.real_token_count`. That is the fixed-address token count the context publishes on every step, and the MoE routing mask already reads it to mask CUDA-graph padding. All four sites now use it.

The zeroing is a small Triton kernel, `inference/contexts/zero_padding_rows_kernel.py`, following the pattern of `mask_routing_padding`:
- It reads the count on device and stores zeros to padding rows only. It never reads the activation.
- It falls back to `masked_fill_` without Triton or for non-contiguous tensors.

Measured on an A6000 with a hidden size of 4096, per call:

| Case | Kernel | `masked_fill_` | Old slice |
|---|---|---|---|
| Inside a graph, 64 tokens | 1.2 µs | 4.3 µs | — |
| Inside a graph, 512 tokens | 2.4 µs | 10 µs | — |
| Inside a graph, 2048 tokens | 3.3 µs | 54 µs | — |
| Eager, 8192 tokens | 11 µs | 212 µs | 5 µs |

`masked_fill_` rewrites the whole activation. The old slice is not graph-safe.

- **Eager steps:** it zeroes the same rows as before.
- **Steps with no real work** (graph capture, EP dummy steps): the published count is 0, so every row is zeroed. Those outputs are discarded, and the MoE routing mask already treats such rows as padding.
- **Embedding sites under sequence parallelism:** they hold this rank's shard, so they pass the TP rank. Before this change, ranks ≥ 1 left most of their padding rows as `embedding(token 0)` even in eager mode.
- **Hybrid:** now zeroes after its own SP scatter, so both models see a shard at that point.
- **GPT:** skips the zeroing when `decoder_input` is `None`, which is the case on pipeline stages without the embedding. `None[slice] = 0.0` raised `TypeError` there.

Unchanged:
- Models without quantization scales; the gate is not touched.
- MTP draft forwards without the NVLS dispatcher keep the main step's count. The old slice did not cover their padding either.

## Tests

| Test | What it checks |
|---|---|
| `test_dynamic_context.py`: helper tests | Eager zeroing, the SP-rank offset, and a captured CUDA graph replayed with different counts. Capture with 16 or 0 real tokens; stale rows hold finite values or NaN. Each runs on the kernel and on the fallback path |
| `determinism/kernels/test_inference_kernels.py::test_zero_padding_rows_replays` | Bit-exact replay of the new kernel. It is registered in the kernel manifest |
| `TestDynamicContext::test_real_token_count_for_padding_zeroing` | The context publishes 0 on graph capture and the active token count on a graphed step. Called eagerly, the helper zeroes exactly what `padding_slice` covers |
| `test_gdp_dynamic_inference.py::test_decode_ssm_zeroes_padding_rows_on_cuda_graph_replay` | The SSM mixer site under graph replay |
| `test_gpt_model.py::TestGPTDynamicInferencePaddingWithCudaGraphs`, layer and block scope | Captures graphs the way the engine does, replays a 10-token prefill in a 64-token graph with the never-written attention rows poisoned, and checks padding logits are zero |

The quantization gate is patched on so the tests run in BF16 on any GPU.

Checked locally on an RTX A6000:
- On unfixed `main`, the GPT model test (both scopes) and the SSM test fail on their padding assertions. The helper tests fail there because the method doesn't exist yet.
- With this PR, all of them pass.
- `test_dynamic_context.py` shows the same environment-only failures on `main` and here (single GPU).
- black, isort, ruff and pylint are clean, as are `tools/check_process_group_usage.py` and the kernel manifest tests.

Coverage gap: the hybrid embedding site has no CUDA-graph test. It calls the same helper as the GPT site, and with block scope the CLI only allows FP8 as MXFP8, whose per-block scales padding can't affect. The CI image has the Mamba kernels this would need; my local image does not.

Determinism check: `tools/check_kernel_determinism_coverage.py` flags `attention.py`, which is registered as `attention_kernels_and_dispatch`. This PR only swaps the padding-zeroing call there, and the new kernel has its own bit-exact test, so the PR carries the `determinism-exempt` label.

## Expected functional-test impact

`gpt_dynamic_inference_tp1_pp1_583m_cuda_graphs_fp8_logitsmatch` should pass again against its existing golden, with no golden change:
- **Why zero rows match the old NaN rows:** the checkpoint uses RMSNorm and no linear biases, so zeroed padding rows stay exactly zero through the network. That gives the same amax as the NaN rows did before #7093.
- **CI evidence:** in pre-#7093 pipelines, the `..._decode_graphs_only` sibling (eager prefill, so its padding was zeroed) produced tokens and log-probs identical to this test's.
- **Local check:** a small model with emulated tensorwise FP8 used to change by up to 2.4e-2 in log-probs depending on stale memory. With the fix it is bit-identical with and without the NaN fill, and matches the pre-#7093 behaviour.

No other functional test combines dynamic inference, FP8/FP4 and prefill/mixed CUDA graphs, so no other golden should move.

The FP8 test is GitLab-only (`scope: [mr]`), so GitHub CI on this PR does not run it. It needs an internal pipeline to confirm.
