# MFSDP v2: write TE fused wgrads directly into the reduce-scatter buffer

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7860) · state: open · merged: False

## Original PR description

# What does this PR do?

Lets Transformer Engine modules built with `fuse_wgrad_accumulation=True` write their weight gradients directly into the experimental Megatron-FSDP (v2) reduce-scatter buffer through TE's `weight.main_grad`, removing the per-micro-batch gradient copy.

Linked issue: Fixes #6942

## Summary

Today, after each module's backward, `copy_gradients_to_partial_buffer` copies every parameter's unsharded gradient into the reduce-scatter buffer. On H200 that copy is 1.2–3.9% of step time for a 4.54B-parameter Llama-shaped model (numbers in #6942). With this PR, TE writes the weight gradients of fused modules straight into the buffer.

## Design

As agreed in #6942:

- **Detection:** a parameter group treats a 2-D weight as fused when its owning module has `fuse_wgrad_accumulation=True`. MFSDP follows the TE module's own setting; there is no new `fully_shard` argument.
- **Buffer:** when a module's own backward starts, its group allocates and zeroes the reduce-scatter buffer on the compute stream and sets `weight.main_grad` to each fused weight's view. TE accumulates into it and returns no gradient to autograd. Post-backward adds the remaining autograd gradients (biases, LayerNorm, unfused weights) into their views, removes `main_grad`, and hands the buffer to the reduce-scatter stream as before.
- **Recompute:** a checkpointed region is recomputed before its modules' backward. No buffer is prepared during recompute, so each one is allocated only when its own module's backward starts.
- **Lifetime:** the buffer is allocated on the compute stream, so it is released only after the compute stream's next wait on the reduce-scatter stream (the next group's reduction or the end of backward). Allocation and release stay on one stream without `record_stream`, and at most two fused buffers are alive at once. With `delay_wgrad_compute=True`, a buffer lives until `backward_dw()` has run and the next reduction has waited for it.
- **TE contract:** only the documented `main_grad` attribute is used, not `__fsdp_param__` or `is_distributed_weight`.
- **MXFP8:** parameters with fusion raise a `ValueError` at `fully_shard` for now.

`runtime_schedule.md` gains a "Fused Weight Gradients" section describing this.

## Scope and follow-ups

- The MCore adapter still rejects `gradient_accumulation_fusion` for v2 (`mcore_fsdp_adapter.py`), so this PR applies to `fully_shard` used directly with TE modules. Allowing it in the adapter, including the combined-1F1B path, is the next PR.
- `overwrite_main_grad` to skip the zeroing for weights with a single contribution per step.
- MXFP8 support.
- Requires PyTorch 2.8 or newer: the post-accumulate-grad hook must fire when TE returns no gradient, and 2.7's `AccumulateGrad` returns early on an undefined gradient.

## Question for reviewers

Detection reads TE's `fuse_wgrad_accumulation` module attribute, a documented constructor argument that MCore also reads. The alternative is an explicit `fully_shard` argument. Happy to switch if you prefer that.

- Achyuthan-S · comment · 2026-10-19T21:37:27Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/7860#discussion_r4319130460)

File: `megatron/core/distributed/fsdp/src/megatron_fsdp/experimental/module.py` · line None

Release isn't deferred to the end of backward. `_reduce_gradient_groups()` already makes the current stream wait for the reduce-scatter stream before packing each group; main issues that wait today. The fused path drops the previous module's buffers right after that same wait, so each buffer is freed at the next module's reduction. Only the last buffer of a backward waits for the end-of-backward wait. With one FSDP module per layer, at most two modules' buffers are alive: one being filled by TE and one being reduced. I'm merging current main into this branch and will push once the GPU tests pass. In that update the end-of-backward release moves into `finish_grad_sync()`, so it also happens with `caller_managed_grad_sync=True`.

Why delay at all: today `partial_grad` is allocated on the reduce-scatter stream right before the copy, so dropping it immediately is safe. The fused buffer has to exist when the module's backward starts, and TE writes it on the compute stream. If it were allocated on the reduce-scatter stream, the compute stream would have to wait for that stream before writing into it, as the copy path does before packing. At backward start, that wait would include the reduce-scatter the previous module just launched, so the module's backward would no longer overlap it. So the buffer is allocated on the compute stream. Dropping it right after launching its reduce-scatter would let the allocator hand the block to the next compute-stream allocation while the reduce-scatter is still reading it. That leaves two options: `record_stream()`, or holding the reference until the compute stream has waited. runtime_schedule.md avoids `record_stream`, so I hold the reference. This adds no wait that main doesn't already issue.

Today AI_1 sits on the RS stream behind RS_2, but the only thing that waits on it is CI_1, and CI_1 runs after Bwd_1. So Bwd_1 overlaps RS_2.

With fusion there's no CI_1. TE writes into the buffer during Bwd_1, so Bwd_1 itself has to wait on AI_1. Allocating AI_1 when Bwd_1 starts doesn't help, because RS_2 was already launched at CI_2, so AI_1 still lands behind it on the RS stream. And it does need that wait: once DI_2 frees RS_2's input, the allocator can hand that same block to AI_1 (layers are usually the same size), and RS_2 may still be reading it. Your idea does work if AI_1 moves one step earlier: allocate layer 1's buffer next to AI_2, before RS_2 is launched. Agreed, getting the order right belongs in #7998. I won't try to handle a wrong order here.

There's still one wait I need even when the order is right, though. backward_order puts a parent before its children (root first, then the last layer), and a parent's post-backward only runs after all of its children are done. So when the root pre-allocates the last layer's RS input, no post-backward wait comes between that allocation and the last layer's backward, and TE could start accumulating into the buffer before the zeroing on the RS stream has finished. delay_wgrad_compute has the same gap: the previous module's post-backward only runs after its backward_dw(), and the caller decides the order of the backward_dw() calls.

So I'd keep just a wait at the module's own backward start, on an event recorded after the allocation. That's the same thing _unshard_event already does for the prefetched all-gather. In the plain layer-to-layer case the wait before CI_i has already covered it, so it costs nothing there. I'll drop the fallback and the cleanup that were only there for a wrong order. The one exception is the root: it's first in backward_order and nothing prefetches for it, so if it owns fused weights itself it allocates its own buffer when its backward starts.
