# What does this PR do?

Cover fixed-length BF16 GPT training with activation offload fractions 0, 0.5 and 1. The test runs four decoder layers, two microbatches and three SGD steps, compares losses and all gradients against offload-disabled training, and checks that positive fractions perform transfers while fraction zero does not.

After #7575, the original fraction-zero `Chunk mismatch` failure no longer reproduces on `main`. The `finish_all_groups()` workaround has been removed; this PR now adds regression coverage. Q/K normalization follows the upstream offload tests so the positive-fraction controls use supported, unpacked attention inputs.

**[IMPORTANT Correctness rationale] Could you demonstrate why this additional H2D-to-D2H dependency is needed under the actual training scheduler?**

We traced the pool lifetime and the existing stream dependencies. Under the configurations checked so far, we could not establish a reachable overwrite of a CPU buffer whose previous H2D read is still unordered with the new D2H:

- The shared pool is bucketed by `(shape, dtype)` and uses FIFO reuse (`free: append`, `allocate: popleft`). Returning a buffer immediately after enqueueing H2D does not by itself establish that the next forward will reuse that buffer before a consumer has waited for its reload.
- For PP1 combined scheduling, with one pooled offload scope and one fixed-shape tensor per layer, the first training warmup iteration offloads all `L` layers. The next microbatch's first forward scope executes before the previous microbatch's first backward scope, so the pool grows to `L+1` buffers and retains them across reset. In warmup, fallback H2D runs on the compute stream; the subsequent forward and the existing D2H wait on that stream provide the H2D-to-next-D2H ordering even when a just-returned buffer is immediately reused. This is separate from the missing D2H-to-fallback-H2D dependency addressed by #7399.
- Even `L=1` retains two buffers in PP1 combined scheduling. In steady state, after F1 offloads to P0 and B0 prefetches/returns P0 for B1, the free FIFO is `[P1, P0]`. F2 takes P1; B1 waits for P0's reload before F3 takes P0. Thus the consumer wait and the existing D2H wait on compute form a transitive dependency.
- We also traced ordinary PP and VPP schedules, including combined VPP. For example, PP2/rank0/L4 retains eight buffers after warmup. After F0/F1/B0, the free FIFO is `[P7, P2, P1, P0, P6]`, where P6 is the outstanding prefetch for B1. F2 takes the first four buffers, not P6.

For validation, we executed the original pool/manager/handler Python methods with fake tensors and a stream/event dependency model, removing only this added wait in the #8243 diagnostic copy. The checks covered L=2/4/8 with PP=1/2/4, VPP=2/3 where applicable, and a separate L=1 matrix; the checked warmup and steady-state sequences did not report unordered reuse. These are source-driven dependency checks, **not GPU training or CUDA numerical tests**, and assume fixed shapes, one pooled scope/tensor per layer, fraction=1, and no CUDA graphs, recomputation, or MTP. They do not prove safety for all supported configurations.

The new UT exercises a different state: it creates an empty pool, manually sets `is_warmup=False`, enqueues H2D from the only buffer, then immediately submits another offload without the normal backward consumer wait. This valid low-level test demonstrates that the added wait protects that sequence, but does not establish that the training scheduler can reach it.

Could you provide the concrete scheduler/configuration that defeats the existing FIFO/capacity/consumer ordering, ideally with an end-to-end regression test following the normal warmup lifecycle and identifying the reused buffer? Our current conclusion is that the necessity of this extra synchronization remains unproven for the checked training schedules, not that it is universally unnecessary. This distinction matters because the streams are shared across chunks: this wait also orders D2H against unrelated H2D work even when their buffers belong to different buckets.

**[SUGGESTION Integration] Please let #7399 own the fallback reload synchronization and remove this duplicate implementation when integrating the two PRs.**

#7399 already orders fallback H2D after the group's D2H. It also removes the group from `_groups_to_reload` when inline reload takes over, allowing the next bulk prefetch to advance to the preceding group. In this implementation, after inline consumption of G2, the queue still contains G2 and the next bulk reload processes that now-empty group instead of prefetching G1. This bookkeeping issue predates this PR, but #7399 already addresses it alongside the synchronization.

Given the review work already invested in #7399, please rebase on it once it lands (or explicitly make this PR depend on it), remove the overlapping fallback wait, and retain this PR's distinct forward-only warmup, fraction-zero, and forward-chunk progression fixes and their regression tests. The target branch must contain #7399 or an equivalent fallback fix before this PR lands without this wait.
