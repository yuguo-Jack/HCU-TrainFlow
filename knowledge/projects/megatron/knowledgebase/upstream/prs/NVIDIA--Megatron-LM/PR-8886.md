# Keep every top-n row for the async prompt-score commit

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8886) · state: open · merged: False

## Original PR description

## What does this PR do?

With prefix caching, async scheduling and prompt log-probs with top-N, a
request that finishes with trimmed output can crash the dynamic engine.
Under async scheduling, `_finalize_async_sched_requests()` passes the step's
log-probs and top-N dict to the engine, which finalizes finished requests
before `commit_prompt_logprob_writes()` caches the step's prompt rows. The
engine's stop-sequence, EOS and token-limit trims shorten a finished
request's top-N list in place in that shared dict, while they trim
log-probs only through a local variable. When a trim reaches below the
request's prompt rows, as when a stop sequence lies in tokens re-prefilled
after a checkpoint, the commit pairs its prompt rows with fewer top-N rows
and raises `IndexError`, failing the engine step.

This PR passes the engine's finalize callback a shallow copy of the top-N
dict. Its trims stay on the copy, and the commit sees every row the step
produced.

## Example failure scenario(s)

**Scenario (a stop sequence among re-prefilled tokens)**
- Prefix caching is on, scheduling is async, and request A asks for prompt
  log-probs with top-1 and a stop sequence.
- A generates some tokens, is checkpointed by a RECOMPUTE suspend, and
  resumes with those tokens appended to its prompt.
- In the step that prefills A's final chunk, the stop sequence is found
  among the re-prefilled tokens, so A finishes and the engine trims 3 of
  its rows.
- The engine shortens A's top-N list from 9 rows to 6 in the shared dict,
  while the step's prompt-score write still covers 8 prompt rows.
- The commit indexes the 6 top-N rows with an 8-row mask and raises
  `IndexError`.

## How was this bug discovered?

A stateful search drove the real engine through generated sequences of
submissions, steps, suspends and aborts, with prompt log-probs, top-N and
stop sequences requested under prefix caching, and checks every request's
tokens and scores against an exact reference. A 44-action history crashed
in the prompt-score commit with `IndexError`, and the same history fails on
`main`. Replays showed that it needs both stop sequences and top-N. A dump
of each write at commit showed the failing request on its second checkpoint
segment: its write covered 8 prompt rows, the step's log-prob list had 9
rows, and its top-N list only 6, the rows left after the engine trimmed the
stop sequence from the re-prefilled tokens.

## Scope

- Production: `text_generation_controller.py` only (+3/−1), in
  `_finalize_async_sched_requests()`.
- Test (+31): `test_text_generation_controller.py`:
  `test_async_sched_finalize_keeps_top_n_rows_for_prompt_score_commit`. A
  finalize callback trims a request's top-N rows in place, as the engine
  does; the dict the commit reads must keep all of them.
- The engine's own processing is unchanged: it trims its copy exactly as
  before, and `post_process_requests()` skips requests already finalized.
- Independent of #8853, which changes how the commit checks its blocks.
- No functional-test, config or API change.
