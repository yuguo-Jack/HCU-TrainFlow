# perf(ssm): cache FP32 conv and batch-invariant decode parameters for Mamba inference

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8646) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Mamba inference reads FP32 copies of the conv weight and bias from a cache instead of casting them at every step when the conv states are FP32. Batch-invariant decode also reads `A` and `dt_bias` from caches. Outputs are unchanged, and each decode step is 0.2 to 0.4 ms faster.

## Details

With `--mamba-inference-conv-states-dtype fp32` and BF16 parameters, every Mamba layer cast the conv weight and bias to FP32 at every step:
- decode, `causal_conv1d_update` path: `rearrange(conv1d_weight).to(conv_state.dtype)` and `conv1d_bias.to(conv_state.dtype)` (`mamba_mixer.py`, `ssm_decode`);
- the same casts in the batch-invariant decode;
- the same casts in prefill (`ssm_prefill`).

The default decode already caches `-exp(A_log.float())` in `_A_neg_exp_cache`, which `refresh_cache()` refreshes in place after a refit (`resharding/execution.py`) and on a train-to-eval switch. It reads `dt_bias` without a cast. Batch-invariant decode, however, recomputed `-exp(A_log.float())` and `dt_bias.float()` at every step.

`MambaMixer` now allocates FP32 caches for the conv weight and bias, and in batch-invariant mode for `dt_bias`, next to the A cache at construction (outside any CUDA-graph capture, a few KB per layer). `refresh_cache()` fills them with the same expressions the steps evaluated, so the cached values are bitwise the per-step casts:
- `_get_conv_params` returns the cached conv weight and bias in inference (eval mode, no grad, context-parallel size 1) when FP32 is requested for lower-precision parameters. Otherwise it casts per call as before, which leaves training, grad mode, context parallelism and matching dtypes unchanged.
- `_get_batch_invariant_decode_params` returns the cached `A` and `dt_bias` under the same conditions.

## Performance

GB200, Nemotron-3-Nano engine decode (23 Mamba layers, MXFP8, TP2 with SP, EP4, CUDA graphs, FP32 conv and SSM states), at 1 to 32 requests and 1k to 8k context:
- Batch-invariant mode: 0.32 to 0.38 ms faster per decode step in three runs, against steps of 5.1 to 7.7 ms.
- Default mode: 0.19 to 0.28 ms faster per decode step (conv weight and bias only), against steps of 4.4 to 7.0 ms.

## Tests

### [P2] Invalidate populated caches after parameter dtype conversion

**Failure:** In [MambaMixer’s cache getters](https://github.com/NVIDIA/Megatron-LM/blob/de3c9b271dd0e640a7f69e9f783e7ee9fec50dab/megatron/core/ssm/mamba_mixer.py#L1101-L1131), cache validity depends only on `_A_neg_exp_cache_stale`, which module dtype conversion does not invalidate. Minimal reproduction: construct an FP32 mixer, fill its conv weight with `1.001`, call `eval()`, then `bfloat16().eval()`. Under no-grad, `_get_conv_params(..., torch.float32)` returns the populated cache containing approximately `1.001`, although the current BF16 parameter’s FP32 cast is `1.0`. Before this change, the conv path cast the current parameter per call.

Batch-invariant decode newly exposes the same failure for cached `A`: [Float16Module converts unmarked parameters through `_apply`](https://github.com/NVIDIA/Megatron-LM/blob/de3c9b271dd0e640a7f69e9f783e7ee9fec50dab/megatron/core/transformer/module.py#L489-L542), including `A_log`, without changing the plain-tensor cache or its stale flag. The existing [prefix-cache setup](https://github.com/NVIDIA/Megatron-LM/blob/de3c9b271dd0e640a7f69e9f783e7ee9fec50dab/tests/unit_tests/inference/engines/test_batch_invariant_mamba_prefix_caching.py#L84-L97) evaluates the model before wrapping it, so this initialization order is present in the repository.

**Correction:** Invalidate cached contents after parameter transformations. For same-device dtype conversions, a small correction is to add this override to [MambaMixer](https://github.com/NVIDIA/Megatron-LM/blob/de3c9b271dd0e640a7f69e9f783e7ee9fec50dab/megatron/core/ssm/mamba_mixer.py#L1087-L1162):

```python
def _apply(self, fn, recurse=True):
    result = super()._apply(fn, recurse=recurse)
    self._A_neg_exp_cache_stale = True
    return result
```

The existing `eval()` and lazy getters then refresh from the transformed parameters. The invariant is that every returned cache equals its expression evaluated from current parameters. Keep the cache tensors FP32 and their storage addresses stable; making them ordinary castable buffers would lose those guarantees. This suggestion addresses dtype invalidation, not general device migration, and must be verified before adoption.

**Preservation and acceptance — proposed checks, not executed:** Using the existing mixer fixture, populate non-BF16-representable FP32 conv weight/bias and `A_log`/`dt_bias`; evaluate, convert to BF16, and evaluate again. Under no-grad, require exact equality to the current rearranged conv weight’s FP32 cast, `conv1d_bias.float()`, `-torch.exp(A_log.float())`, and `dt_bias.float()`, with unchanged FP32 cache pointers. Also omit the second `eval()` and verify lazy refresh. Retain the [new direct-refresh and train→eval assertions](https://github.com/NVIDIA/Megatron-LM/blob/de3c9b271dd0e640a7f69e9f783e7ee9fec50dab/tests/unit_tests/ssm/test_mamba_mixer.py#L138-L191), including exact refreshed values, stable pointers, grad-enabled bypass, and matching-FP32 conv views. Training, CP>1, and non-FP32 requests must continue using per-call conversions.
