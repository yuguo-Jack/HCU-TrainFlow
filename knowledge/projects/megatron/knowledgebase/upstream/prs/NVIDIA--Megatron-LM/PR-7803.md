# [dev] Fix fused MLA RoPE key/value split for non-power-of-two head dims

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7803) · state: closed · merged: True

## Original PR description

Thanks @TKONIY for the contribution to this PR!

- [x] I, the PR author, have personally reviewed every line of this PR.

## Summary

With `apply_rope_fusion=True`, `MLASelfAttention` builds its key and value with the fused MLA RoPE
key/value split, `fused_apply_mla_rope_for_kv`. This is an alias of `fused_mla_rope_kv_split` in
`megatron/core/fusions/fused_mla_yarn_rope_apply.py`. Its two Triton kernels compile only when
`qk_head_dim`, `v_head_dim` and half of `qk_pos_emb_head_dim` are powers of two.

GLM-5's MLA head dims are `qk_head_dim` 192, `v_head_dim` 256 and `qk_pos_emb_head_dim` 64. With
them, the first training forward pass of an MLA layer stops with:

```
triton.compiler.errors.CompilationError: at 62:24:
    k_in_off = kv_off + tl.arange(0, k_dim)[None, :]
                        ^
arange's range must be a power of 2
```

This PR pads the three widths to the next power of two inside the two kernels and masks the padding
lanes, as `fused_mla_rope_concat` in the same file already does. The masks are built only when a
width is actually padded. Power-of-two configurations, such as DeepSeek-V3's, therefore compile to
exactly the same kernels as before: identical PTX and SASS. A new GPU test covers GLM-5's dims and a
case in which all three widths are padded.

## Problem

`MLASelfAttention.get_query_key_value_tensors` (`multi_latent_attention.py`) takes the fused path
when `should_use_fused_mla_rope(config)` is true:

```python
key, value = fused_apply_mla_rope_for_kv(
    kv,                                # [tokens, heads, qk_head_dim + v_head_dim]
    k_pos_emb,                         # [tokens, 1, qk_pos_emb_head_dim]
    rotary_pos_cos,
    rotary_pos_sin,
    self.config.qk_pos_emb_head_dim,   # emb_dim
    self.config.qk_head_dim,           # k_dim
    self.config.v_head_dim,            # v_dim
    cu_seqlens_kv,
    cp_rank,
    cp_size,
)
```

With GLM-5's head dims, this call raises the `CompilationError` above instead of returning `key` and
`value`. The query RoPE just before it (`fused_apply_mla_rope_for_q`) works with the same dims.
Nothing checks the dims beforehand.

Reproduced on `dev` at `ac100f773` (B200, Triton 3.6.0, torch 2.11):

- The public entry points `fused_mla_rope_kv_split` and `fused_apply_mla_rope_for_kv` with GLM-5's
  dims, at 64 heads (TP 1) and 8 heads (TP 8), in SBHD and in THD format: the forward kernel fails at
  line 62 of `_mla_rope_fwd_kv_split_kernel`. `_FusedMLARoPEKVSplit.backward` called on its own fails
  at line 54 of `_mla_rope_bwd_kv_split_kernel`, `dk_out_off = dkv_off + tl.arange(0, k_dim)[None, :]`.
- An `MLASelfAttention` (Transformer Engine spec, bf16, 8 heads) with GLM-5's head dims and
  `apply_rope_fusion=True`, in SBHD and in packed THD format: the forward pass fails in
  `qkv_up_proj_and_rope_apply`, at the `fused_apply_mla_rope_for_kv` call.

## Root cause

### Mechanism

The key/value split kernels take the three widths as `tl.constexpr` and build their tiles with
`tl.arange` over them:

```python
# _mla_rope_fwd_kv_split_kernel, before this PR
cos_left = tl.load(COS + token_idx * emb_dim + tl.arange(0, emb_dim // 2))
...
k_in_off = kv_off + tl.arange(0, k_dim)[None, :]
v_in_off = kv_off + k_dim + tl.arange(0, v_dim)[None, :]
```

The backward kernel has the same pattern: `dk_out_off`, `dv_out_off`, `dk_in_off`, `dv_in_off`, and
the rotary accumulators `tl.zeros((BLOCK_H, emb_dim // 2))`.

Triton tensor shapes must be powers of two. `tl.arange(0, n)` checks this when the kernel is
compiled, which happens at its first launch (here, the autotuner's first benchmark run). For any
other `n` it raises `ValueError("arange's range must be a power of 2")`, which Triton reports as a
`CompilationError`.

**Worked example: GLM-5 at TP 8.** The inputs are `kv` `[tokens, 8, 192 + 256]` and `k_pos_emb`
`[tokens, 1, 64]`; the outputs are `key` `[tokens, 8, 192 + 64]` and `value` `[tokens, 8, 256]`.

| tile | GLM-5 | power of two? | DeepSeek-V3 |
|---|---|---|---|
| key channels without RoPE, `tl.arange(0, k_dim)` | 192 | **no** (3 x 64) | 128 |
| value channels, `tl.arange(0, v_dim)` | 256 | yes | 128 |
| rotary pairs, `tl.arange(0, emb_dim // 2)` | 32 | yes | 32 |

So the forward kernel fails at its key tile, and so does the backward kernel. DeepSeek-V3-style dims
are all powers of two, which is why this has not shown up before.

The other kernels of the file handle GLM-5's dims (checked on `ac100f773`, forward and backward):

- `fused_mla_rope_concat` (absorbed MLA) already pads its widths with `NOPE_BLOCK` and `ROT_BLOCK`
  and masks the rest.
- The in-place query kernels (`fused_mla_rope_inplace`: the MLA query, 64 x (192 + 64), and the DSA
  indexer query and key) skip the channels without RoPE with a runtime offset; when the backward
  copies them into `out=`, it already pads. Their only unpadded head-width extent is
  `emb_dim // 2` = 32.

### How it shows up

- It is a hard failure, not a silent one. The model builds; the first forward pass raises the
  `CompilationError` from inside the Triton compiler.
- No configuration check catches it earlier. `should_use_fused_mla_rope` looks only at
  `apply_rope_fusion`, `rope_type` and `rotary_percent`.
- The only workaround is to turn RoPE fusion off (`--no-rope-fusion`, or `apply_rope_fusion=False`),
  which runs the unfused PyTorch path instead. For GLM-5's shapes that path is several times slower;
  see Performance.

### When it triggers

All of the following:

1. The layer is the standard MLA attention module, `MLASelfAttention`. This includes its
   `mla_down_proj_fusion` subclass `FusedMLASelfAttention` and the MLA layers of hybrid models, which
   share `get_query_key_value_tensors`.
2. Training. MLA RoPE fusion is not supported in inference; the code asserts
   `inference_context is None`.
3. `should_use_fused_mla_rope(config)` is true: `apply_rope_fusion=True` and either `rope_type`
   `"yarn"` or `"rope"` with `rotary_percent` 1.0. In the Megatron-LM training scripts,
   `apply_rope_fusion` is on by default with `--position-embedding-type rope` (MLA then uses
   `rope_type` `"yarn"` unless `--rope-type` says otherwise); `--no-rope-fusion` turns it off, and
   any other `--position-embedding-type` except `mrope` turns it off too.
4. `qk_head_dim` or `v_head_dim` is not a power of two, as with GLM-5's `qk_head_dim` 192.

These are per-head widths, and parallelism never changes them:

- Tensor parallelism divides the heads: each GPU's `kv` is `[tokens, 64 / TP, 192 + 256]` for
  GLM-5, so `[tokens, 64, 448]` at TP 1 and `[tokens, 8, 448]` at TP 8.
- Context parallelism divides the tokens of each sequence. Sequence parallelism only splits the
  activations outside attention; inside it, `kv` covers all the tokens of the CP rank.
- Pipeline parallelism splits the layers.

The head width of every tile stays 192 (key), 256 (value) and 32 rotary pairs. GLM-5's dims
therefore fail at every parallel layout, and in both the SBHD and the packed THD format.

**Not affected: DSA.** With `experimental_attention_variant="dsa"` (GLM-5's own configuration), the
attention module is `AbsorbedMLASelfAttention`. It applies RoPE through `fused_mla_rope_concat` and
never calls the key/value split. So the failure hits GLM-5's head dims on the standard MLA module,
for example a GLM-5-shaped model trained with dense MLA attention.

### How it was found

It was found while timing the fused MLA RoPE kernels on GLM-5 shapes: the key/value split case with
GLM-5's head dims did not compile.

## Fix

- The two launches in `_FusedMLARoPEKVSplit` pass three new constexprs: `K_BLOCK`, `V_BLOCK` and
  `ROT_BLOCK`, the next powers of two of `k_dim`, `v_dim` and `emb_dim // 2`
  (`triton.next_power_of_2`).
- Both kernels range over these blocks instead of the widths and mask the lanes past each width. All
  offsets still use the real widths.

  ```python
  rot_mask = None if ROT_BLOCK == emb_dim // 2 else tl.arange(0, ROT_BLOCK) < emb_dim // 2
  ...
  k_in_off = kv_off + tl.arange(0, K_BLOCK)[None, :]
  v_in_off = kv_off + k_dim + tl.arange(0, V_BLOCK)[None, :]
  k_mask = mask if K_BLOCK == k_dim else mask & (tl.arange(0, K_BLOCK)[None, :] < k_dim)
  v_mask = mask if V_BLOCK == v_dim else mask & (tl.arange(0, V_BLOCK)[None, :] < v_dim)
  k = tl.load(KV_ptr + k_in_off, mask=k_mask)
  ```

- The masks cover every access whose extent is a padded width:
  - forward: the `cos`/`sin` and `k_pos_emb` loads, the key and value loads and stores, and the
    rotary stores;
  - backward: the `dK`/`dV` loads, the `dKV` stores, the per-head rotary loads and the `dK_POS_EMB`
    stores. The rotary accumulators become `[BLOCK_H, ROT_BLOCK]`.

**Why it is correct and complete.**

- Every `tl.arange` in the two kernels now has a power-of-two extent: `K_BLOCK`, `V_BLOCK`,
  `ROT_BLOCK`, or `BLOCK_H` from the autotuner configs. Any width compiles.
- Padded lanes are never loaded or stored, so no access goes past a width. compute-sanitizer
  memcheck, with the caching allocator off so that every tensor is its own allocation, reports no
  errors on padded widths at every `BLOCK_H`.
- Padded lanes never mix with valid lanes. The arithmetic is elementwise along the channel axis. The
  backward's only reduction, the rotary gradient summed over the heads, runs along the head axis, so
  a padded column never reaches a stored one.
- The valid lanes compute exactly what the old kernels compute for power-of-two widths. On GLM-5's
  widths (and others), the new kernels give bitwise the same key, value and gradients as the old
  kernels on the same data zero-padded to powers of two (192 + 256 run as 256 + 256), at every
  `BLOCK_H`.
- The rotary width is padded the same way. The key/value split therefore no longer needs any width
  to be a power of two.

**Why the masks are built only for padded widths.** An unconditional mask folds to "true" for
power-of-two widths, but it still turns the unmasked loads of `cos`, `sin` and `k_pos_emb` into
predicated loads, and the compiler then schedules the kernel differently. Compiled for B200, an
always-masked variant changed the SASS of 50 of the 256 power-of-two variants checked below. In 6 of
them (DeepSeek-V3 dims, forward kernel, `BLOCK_H` 64 and 128), it also changed the bf16 FMA
contraction of the rotary arithmetic (`HFMA2` 16 -> 15, `HMUL2` 4 -> 5), which can change results
bitwise. Building the masks only for padded widths keeps power-of-two kernels identical.

**What it does not change.**

- Power-of-two widths compile to identical PTX and SASS: 256 of 256 variants (DeepSeek-V3's 128 + 128
  with 64 rotary channels at 128 and 16 heads, the MLA unit tests' 16 + 16 with 8 at 8 heads, and
  64 + 512 with 64 at 1 head; forward and backward kernels; SBHD and THD; both `remove_interleaving`
  values; every `BLOCK_H`). Their outputs are bitwise the same as before (96 of 96 forced-`BLOCK_H`
  runs), and so is their speed.
- No API, argument or autotuner change.
- The in-place query kernels are unchanged. MLA calls them with the same rotary width, so a model
  whose `qk_pos_emb_head_dim / 2` is not a power of two would still fail there. The 64 rotary
  channels of DeepSeek-V3 and GLM-5 give 32.

## Performance

Cold L2 kernel times on B200:

- Method:
  - before every timed call, a 1 GiB buffer is written, which evicts the 126 MB L2;
  - kernel times come from kineto;
  - 6 processes, alternating which module runs first; 120 samples per module per cell; medians;
  - SM clock 1950-1965 MHz, and no other process on the GPU.
- Inputs: THD, bf16, one sequence. BLOCK_H is either forced or chosen by the autotuner ("auto").

**Power-of-two dims: unchanged.** The code is identical, so this only confirms that timing is too.

| | backward | 64 / 64 | 362.9 | 362.9 | 1.0000 | 0.9998-1.0002 |

| | backward | 16 / 16 | 184.4 | 184.4 | 1.0002 | 0.9996-1.0001 |

**GLM-5's dims: now fused.** The old kernels do not compile, so the comparison is with the path
that `apply_rope_fusion=False` runs: split, `apply_rotary_pos_emb` on the shared `k_pos_emb`,

| case | fused forward us (auto pick) | fused backward us (auto pick) | effective bandwidth | unfused / fused, forward | unfused / fused, forward + backward |
|---|---|---|---|---|---|
| GLM-5 TP 1: 64 heads x (192 + 256), 16384 tokens | 302.7 (64) | 299.1 (64) | 6.7-6.8 TB/s | 6.3x (1 vs 31 kernels) | 6.5x (2 vs 45 kernels) |

  as the old kernels do for 256 + 256 widths. It is far slower than the best configuration (for
  example 935 vs 152 us for the TP 8 forward), and the autotuner never picked it.

## Risk and compatibility

- No API change. Power-of-two head dims compile to the same PTX and SASS as before, so their results
  and speed do not change.
- Head dims that are not powers of two used to fail at compile time. They now work.
- The padded tiles are larger than the real widths. For GLM-5's dims, the largest configuration
  (`BLOCK_H=128`, 256 + 256 lanes per head) spills registers; the autotuner does not pick it (see
  Performance).
- The kernels use only standard Triton features: masked loads and stores, and `constexpr`
  conditional expressions (`x if CONSTEXPR_COND else y`, `rot_mask is None`), as the file already
  does for `position_ids is not None`.

## Notes for reviewers

- The constexpr choice between "no mask" and "mask" is deliberate. An always-on mask is simpler but
  changes the compiled power-of-two kernels, including the FMA contraction in some of them (see Fix).
- The test helper is extended below its first lines rather than given new parameters. #7789 (the
  in-place RoPE race fix) adds its test right above `_test_fused_mla_rope_kv_split`, and this way
  the two PRs do not touch neighbouring lines.
- Three other pending changes touch the same two files: #7787 (64-bit row offsets for inputs of
  `2**31` or more elements), #7789, and #7806 (a binary search for the THD row lookup). All four
  apply in any order without conflicts (`git am` without `-3`, `git cherry-pick`, `git merge-tree`), and the
  result does not depend on the order. On top of the 64-bit offset fix, this PR's kernels are again
  identical for power-of-two widths.
- The open head-mask fixes #6890, #7104 and #7770 (against `main`; `BLOCK_H` not dividing the head
  count) rewrite the `mask = ...` line just above this PR's first change in both key/value split
  kernels and in the backward's per-head loop. #6890 and #7770 also add `other=0.0` to the four
  rotary-gradient loads that this PR re-masks. Whichever lands on `dev` second needs a mechanical
  rebase:
  - keep the new head mask and this PR's lines below it;
  - write those four loads as `mask=x_mask, other=0.0`.

  `k_mask`, `v_mask` and `x_mask` are built on `mask`, so they inherit the new head mask. This was
  checked on a port of #7770 to `dev` with this PR on top: every `BLOCK_H` matches an fp64 reference
  with partial head blocks (12 and 127 heads) and padded widths, and the kernel tests of both PRs
  pass. This PR's tests use 8 and 4 heads, so they do not depend on the head-mask fix.

**Checks on the kernel changes (reading only):**
- **Out-of-bounds accesses.** Every padded lane that would read or write past its real width is masked:
  - `k_mask` covers the key lanes, which would otherwise spill into the value channels.
  - `v_mask` covers the value lanes, which would otherwise spill into the next head.
  - `x_mask` covers the rotary stores, where `x_right_off = x_left_off + emb_dim // 2` would otherwise write past `k_dim + emb_dim` into the next head.
  - `rot_mask` covers the `cos`/`sin`/`k_pos_emb` loads and the `dK_POS_EMB` stores.
  - All offsets still use the real `k_dim`/`v_dim`/`emb_dim`.
- **Backward reduction.** The only reduction ([L1269-L1270](https://github.com/NVIDIA/Megatron-LM/blob/40b1cd3bb3344f93af9b212e465f4a5867eb84ea/megatron/core/fusions/fused_mla_yarn_rope_apply.py#L1269-L1270)) sums over the head axis. Padded columns hold undefined values, but they never mix with valid columns and are never stored. Accumulation stays in fp32 and is cast to the `dEMB` dtype, as before.
- **Power-of-two dims compile to the same kernel.** `ROT_BLOCK == emb_dim // 2`, `K_BLOCK == k_dim` and `V_BLOCK == v_dim` are comparisons between constexprs, so the `x if c else y` and `rot_mask is None` choices are made at compile time. For power-of-two widths, `mask` is used unchanged and the `cos`/`sin`/`k_pos_emb` loads stay unmasked, so DeepSeek-V3-style dims build the same kernel as before.
