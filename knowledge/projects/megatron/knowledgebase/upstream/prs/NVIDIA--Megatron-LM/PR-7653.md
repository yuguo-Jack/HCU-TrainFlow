# fix(training): use model config for kernel warmup

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7653) · state: closed · merged: True

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Use the model's configuration when warming training kernels so config-only settings select the same variants as training.

`activation_func_fp8_input_store` is excluded from generated CLI arguments. When a model config enables it, the previous `getattr(args, ..., False)` warms the wrong SwiGLU backward specialization, causing another Dynamo compilation when training starts. This affects warmup coverage, not numerical correctness.

Resolve GPT/Hybrid TransformerConfig, logits dtype and vocabulary padding inside the warmup module. Keep training.py's call short and pass the actual schedule/dataloader sequence length and microbatch size explicitly; model `seq_length` represents positional capacity. Activation selection uses the config's callable, gating and fusion settings. Retain the argument-derived fallback for legacy/MiMo providers.

Fix https://github.com/NVIDIA/Megatron-LM/pull/7635#issuecomment-5821058095

### What I checked

**Activation dispatch.** I compared the kernel selection in [`_warmup_training_kernels`](https://github.com/NVIDIA/Megatron-LM/blob/e264336251c43f73aa2efd9960138c104d04bdcc/megatron/training/kernel_warmup.py#L265-L303) with the dispatch in [`MLP.forward`](https://github.com/NVIDIA/Megatron-LM/blob/e264336251c43f73aa2efd9960138c104d04bdcc/megatron/core/transformer/mlp.py#L269-L371). The two agree:
- TE activation: nothing is warmed.
- Fused path: GeGLU, GeLU (which requires bias) and SwiGLU, including SiTU-GLU and the clamp and FP8-store arguments.
- The fused, tanh-clamped squared-ReLU kernel, which only runs when fusion is off.
- The eager path: `situ_glu`, the clamped GLU and `tanh_soft_clamp` followed by the activation.

The combinations that `MLP.forward` rejects (fused quick-GeGLU without per-token weights, and fused SiLU without gating) correctly warm nothing. [TransformerConfig validation](https://github.com/NVIDIA/Megatron-LM/blob/e264336251c43f73aa2efd9960138c104d04bdcc/megatron/core/transformer/transformer_config.py#L2948-L3044) also rejects bias fusion with squared-ReLU, tanh clamps on non-SwiGLU fused paths, and FP8 input store on anything other than SwiGLU. So the selection conditions are mutually exclusive for every config that can actually be built.

**Earlier inline comment from @maanug-nv (on a previous commit).** The concern was that `gated_linear_unit` is not the same as `args.swiglu`. The current head fixes this: SwiGLU is selected only when `activation_func == F.silu and gated_linear_unit and bias_activation_fusion`. GeLU, GeGLU and squared-ReLU are each keyed on activation, gating and fusion together in the same way.

**Vocabulary and dtype.** The padding logic matches the GPT and Hybrid builders ([gpt.py](https://github.com/NVIDIA/Megatron-LM/blob/e264336251c43f73aa2efd9960138c104d04bdcc/megatron/training/models/gpt.py#L293-L301), [hybrid.py](https://github.com/NVIDIA/Megatron-LM/blob/e264336251c43f73aa2efd9960138c104d04bdcc/megatron/training/models/hybrid.py#L179-L189)). The `pretrain_gpt.py`, `pretrain_hybrid.py`, `train_rl.py` and MiMo entry points resolve `vocab_size` through [`resolve_tokenizer_vocab_size`](https://github.com/NVIDIA/Megatron-LM/blob/e264336251c43f73aa2efd9960138c104d04bdcc/megatron/training/argument_utils.py#L566-L584) before calling `pretrain`. That means the new "vocabulary must be resolved" error can't fire on those normal startup paths. `logit_dtype` now comes from the model config; when the config is built from args, it holds the same value as before.

**Legacy fallback.** When `cfg_container.model` is not a GPT or Hybrid config (for example MiMo, or `None`), `core_transformer_config_from_args` derives the same flags the old code read from args: `bias_activation_fusion` comes from `bias_swiglu_fusion` or `bias_gelu_fusion`, and squared-ReLU and quick-GeGLU are mapped the same way.

**Call site.** The [call in `pretrain`](https://github.com/NVIDIA/Megatron-LM/blob/e264336251c43f73aa2efd9960138c104d04bdcc/megatron/training/training.py#L1730-L1736) is the only caller. It still passes `args.seq_length` and `args.micro_batch_size`.

**Tests.** They cover the reuse of the FP8 backward specialisation, mapping each config to a kernel path, real compilation of every path, and what `pretrain` passes in (model config, batch dimensions, padding and the legacy fallback).

### Suggestion

Per the review rubric, this is a structural change, so it goes here instead of in a `suggestion` block.

**[SUGGESTION Decomposition]** Move the activation-path selection out of `_warmup_training_kernels` ([kernel_warmup.py L265-L303](https://github.com/NVIDIA/Megatron-LM/blob/e264336251c43f73aa2efd9960138c104d04bdcc/megatron/training/kernel_warmup.py#L265-L303)) into its own function.

- **Issue:** The function body is now about 85 lines. It runs the CE warmup, picks the activation path (about 40 lines that copy `MLP.forward`'s dispatch), loops over widths, runs the residual warmup and does cleanup. Because of this, `test_selects_fused_activation_from_config` has to run the whole warmup just to see which path was chosen. That includes `torch.cuda.synchronize`, shutting down the compile workers and `empty_cache`, with `_warmup_activation` monkeypatched to record the choice.
- **Why it matters:** This is maintenance only; nothing is incorrect today. The selection has to be kept in step with `MLP.forward` by hand. A small pure function makes that copy easier to compare and to test, which is also what the earlier review asked for ("more for clarity").
- **Fix:** add a helper and call it once.

```python
def _select_activation_kernel(config: TransformerConfig) -> str | None:
    """Return the activation path MLP.forward runs for fixed-shape (dense/shared) MLPs.

    None means nothing to warm: TE activations, or fused combinations MLP.forward rejects.
    """
    if config.use_te_activation_func:
        return None
    if (
        config.activation_func == squared_relu
        and not config.gated_linear_unit
        and config.use_fused_weighted_squared_relu
        and config.activation_func_tanh_clamp_scale is not None
    ):
        return "squared_relu"
    if not config.bias_activation_fusion:
        return "unfused"
    if config.activation_func == F.silu and config.gated_linear_unit:
        return "swiglu"
    if config.activation_func == F.gelu:
        if config.gated_linear_unit:
            return "geglu"
        return "gelu" if config.add_bias_linear else None
    return None
```

In `_warmup_training_kernels`, replace the five booleans, the `if`/`elif` chain and the `use_te_activation_func` guard with `kernel = _select_activation_kernel(config)` and `if kernel is not None:` before the width loop.

- **Invariant to keep:** the helper returns exactly the path `MLP.forward` takes for a dense or shared MLP. I traced it against the current chain:
  - Fused squared-ReLU is still checked before fusion, as it is now.
  - Fusion off gives `"unfused"` only when fused squared-ReLU doesn't apply.
  - Fused non-gated GeLU without bias gives `None`.
  - Fused SiLU without gating, and quick-GeLU, give `None`.
- **What must not change:** all nine cases in `test_selects_fused_activation_from_config` should produce the same result:
  - `squared_relu`→`"squared_relu"`, `swiglu`→`"swiglu"`, `gelu`→`"gelu"`, `geglu`→`"geglu"`
  - `te`→`None`
  - `unfused_gelu` and `unfused_gated_squared_relu`→`"unfused"`
  - `fused_quick_geglu_needs_weights` and `fused_silu_without_gating`→`None`
  - `test_other_configurations_and_later_compilation` and `test_config_activation_storage_reuses_warmed_backward` should behave exactly as now.
- **How to check (proposed test change):** in `test_selects_fused_activation_from_config`, swap the monkeypatch and full warmup for `assert kernel_warmup._select_activation_kernel(config) == expected`, using the same parameters; every case should pass unchanged. Also read the code to confirm that `_warmup_training_kernels` calls the helper exactly once and enters the width loop only when it returns something other than `None`. Please run these yourself before adopting the patch.

- **Tests.** In `test_pretrain_passes_model_config_and_runtime_batch`, the `pretrain_until_warmup` fixture checks the forwarded model config, TP group, batch dimensions, padded vocabulary and `logit_dtype` for GPT and Hybrid configs. `test_warmup_skips_without_model_config` checks the skip path.
