# [dev] Padding-aware kernels for THD tail padding: live-row GEMMs, Triton cross entropy, bounded mHC/RoPE

# What does this PR do?
This PR makes the row-linear kernels of a packed-sequence model skip the padding tail:

This PR adds:
- `--padding-aware-lm-head` / `--padding-aware-dense-linear`: the LM head, the TE linears, the fused norm+linear and the DSv4 grouped o-projection run as a one-group grouped GEMM over the live rows only. The live-row count is a device-side scalar derived from the padding mask (CUDA-graph safe); the choice of kernel is static per module from the model shape and `--padding-aware-assumed-padding`, never from the runtime row count.
- `--cross-entropy-fusion-impl triton`: a one-program-per-row online-softmax cross entropy over bf16 logits (TP via gathered row statistics), replacing the several fp32 passes of the native fused CE. Matches native to fp32 rounding; 5-7x fewer bytes.
- Row-bounded mHC hyper-connection kernels (cuTile/Triton) and RoPE fusion. Bounded RMSNorm, three-way gradient add and MTP argmax are included but off by default (`MCORE_PADDING_AWARE_SKIP`), measured net-negative end to end.

Results on the 256K DSv4 recipe, 128 GPUs (CP16, chunk CUDA graphs + MOK): -2.0 % step time, last-stage max reserved 123.1 -> 107.6 GiB; on a CP1 proxy -10.9 %. Together with a CP window matched to the longest sample (config only, no code): -13.4 % step time, +15.4 % TFLOP/s, -22 GiB on the last stage.

Requires the Transformer Engine strided grouped-GEMM change (GroupedTensor leading_dim); without it the GEMM path stays off and only the Triton CE and bounded kernels are active. Eager mode gets only a gate (launch-bound, no wall-clock gain). Linear CE row bound, op-fuser MLPs and the MOK shared experts are out of scope.

Tests: unit tests for the CE (incl. TP2 and graph replay), norm, mHC kernels (GB200), GEMM policy and numerics, and the kill-switch semantics.
