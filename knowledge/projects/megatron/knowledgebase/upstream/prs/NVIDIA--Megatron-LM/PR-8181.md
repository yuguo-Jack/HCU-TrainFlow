# What does this PR do?

Limit promoted activation-weighting temporaries in the unfused `TEGroupedMLP` path while retaining FP32 router probabilities and the activation output dtype.

## Motivation

Weighting BF16 or FP16 expert activations with FP32 router probabilities materializes a full FP32 product. Large or uneven dropless expert batches can therefore allocate large temporaries in both forward and backward. Eager GLU evaluation also retains intermediates for backward.

## Change and impact

Process large promoted products in row chunks and recompute supported, deterministic, parameter-free GLU activations during backward. Preserve activation rounding and the forward CUDA autocast context. Small inputs, products without dtype promotion, unsupported layouts, and GLU activations under paged stash retain the native path; custom parameterized activations retain their existing gradient handling.

The target is 16,777,216 elements per chunk, or 64 MiB for an FP32 product. At least one row is processed per chunk, so a wider row can exceed that target. This limits individual promoted temporaries and reduces saved GLU intermediates. It does not bound total model memory, eliminate every OOM, or establish a throughput improvement.

The chunked path supports first-order gradients only. Python chunk iteration and activation recomputation add work; CUDA router gradients can differ from the native expression by FP32 reduction roundoff. The testing and downsides below describe these limits.

## Testing

Targeted CUDA correctness, autocast backward, activation checkpointing, and determinism replay passed on the pinned NGC base with its bundled Transformer Engine. Formatting, lint, and the determinism coverage gate passed; optional mypy was unavailable.

I also profiled and tested this branch merged into main on an eight-GPU B200 node, with PyTorch 2.13.0+cu130 and the pinned Transformer Engine revision built with NCCL EP. That environment is not the CI image. It does not include FlashMLA, MambaSSM, or the Apex CUDA extensions that some MoE tests require.

The table shows peak allocated memory above the inputs during forward and first-order backward, with BF16 activations and FP32 router probabilities. Each row is a median across eight ranks.

| Case | Main peak | PR peak | Main / PR step time |
|---|---:|---:|---:|
| `TEGroupedMLP` SwiGLU, 32,768 tokens | 3,232 MiB | 1,648 MiB | 6.7 / 8.7 ms |
| `TEGroupedMLP` SwiGLU, 8,192 tokens | 832 MiB | 592 MiB | 2.1 / 3.6 ms |
| `TEGroupedMLP` squared ReLU, 32,768 tokens | 2,464 MiB | 1,344 MiB | 4.4 / 4.7 ms, and 4.4 / 9.4 ms in a later run |
| `TEGroupedMLP` squared ReLU, 8,192 tokens | 640 MiB | 480 MiB | 2.1 / 2.3 ms |
| `TEGroupedMLP` SwiGLU, 1,024 tokens, native path control | 132 MiB | 132 MiB | 2.0 / 2.0 ms |
| `MoELayer`, EP=8, all-to-all dispatcher, 8,192 tokens per rank | 1,571 MiB | 882 MiB | 20.2 / 19.9 ms |
| The same `MoELayer` with `moe_act` recompute | 1,827 MiB | 1,010 MiB | Too noisy to compare |

In these runs, outputs and input gradients matched main exactly. The `TEGroupedMLP` router gradients also matched, and every `MoELayer` parameter matched after five SGD steps. The FP32 roundoff note below stays because an earlier measurement with other shapes did show that difference.

With paged stash enabled, the unfused GLU keeps the native expression. `TransformerConfig` rejects unfused activations with paged stash only when the op fuser is off. With the op fuser on, experts that do not execute quantized take the unfused path, and the chunked GLU would save the FC1 output. That tensor has no pool if an input crosses the threshold after the capture step, and such a run failed with a `KeyError`. With the native GLU, outputs and gradients matched bit for bit across the capture and stash steps, including when the router weighting changed between its native and chunked paths. A regression test covers the saved tensors.

Fine-grained activation offload on the same `MoELayer` also matched the native path exactly, with lower peak memory.

The MoE unit-test directory had the same failures on this branch and on main, through the CI runner and its bucket exclusions. The determinism kernel directory differed only in `test_virtual_expert_planner_graph_replay`, the race that #8620 addresses.

One directory run on this branch stopped at a collective timeout after `test_shared_expert_forward_backward` failed on one rank. That test uses the fused activation, so it does not reach this change. A second directory run did not reproduce the failure, and neither did eight repeats of the test on this branch and eight on main. Full model training, the CI image, and the functional tests still need maintainer CI vetting and the `Run functional tests` label.

The standard unit-test entry point in the CI container is:

```sh
uv run python -m torch.distributed.run --nproc-per-node=8 -m pytest tests/unit_tests
```

See the [testing guide](https://github.com/NVIDIA/Megatron-LM/blob/main/skills/mcore-testing/SKILL.md) for setup and focused runs.

### Downsides

The chunked path supports first-order gradients only and adds Python chunk iteration and activation recomputation. CUDA router gradients can differ from the native expression by FP32 reduction roundoff; repeated chunked executions remain bit-exact.

I measured the allocation that this PR targets on a B200 at `2ee823f74a`. I compared the PR helper with the native expression on the same BF16 activations, FP32 router probabilities and BF16 incoming gradient. | Shape and operation | Native peak | PR peak | Native / PR time |
|---|---:|---:|---:|
| `32769 × 2048`, weight only | 1,024.03 MiB | 416.13 MiB | 1.10 / 1.36 ms |
| `32769 × 2048`, clamped SwiGLU then weight | 768.02 MiB | 416.16 MiB | 1.36 / 2.81 ms |

I used the shipped 16,777,216-element chunk target, not a test override. I compared the full output and both gradients on identical inputs. Outputs and input gradients matched exactly. Timings are median CUDA-event measurements from interleaved runs.

This supports a memory trade-off for large promoted products, not a throughput improvement or a guarantee against training OOMs. Transformer Engine integration, multiple ranks and model training were not part of this measurement.

**<sub><sub>![P1 Badge](https://img.shields.io/badge/P1-orange?style=flat)</sub></sub>  Preserve autocast during activation recomputation**

When `enable_autocast=True` and a large gated activation uses an op whose CUDA autocast policy changes precision, the forward callback runs inside the autocast scope established in `megatron/core/pipeline_parallel/schedules.py:510-516`, but backward normally runs after that scope has exited and this recomputation restores only grad mode. For example, gated `squared_relu` runs its `torch.pow` in FP32 during the forward but recomputes it from the saved BF16 input here, so the FC1 and router gradients correspond to a different activation (and may also encounter a grad-output dtype mismatch). Preserve the forward autocast enabled state and dtype around the recomputation, such as by pairing AMP `custom_fwd`/`custom_bwd` decorators.
