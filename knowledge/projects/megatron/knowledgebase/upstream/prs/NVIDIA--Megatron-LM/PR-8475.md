# inference: run prefill and mixed CUDA graphs with the nccl EP dispatcher

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8475) · state: open · merged: False

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

On pre-Hopper GPUs such as A100, the inference-optimized MoE path fails with the default `'nvls'` token dispatcher, and with the `'nccl'` dispatcher every step that contains a prefill runs eagerly, because non-decode CUDA graphs are force-disabled for it. This PR makes the nccl dispatcher the automatic fallback on those GPUs and lets it run prefill and mixed (prefill and decode in the same step) CUDA graphs, as the NVLS dispatcher already does. On A100 x2 this cuts the single-request time to first token by up to 3x and the time to first token by 1.7-3x when requests arrive at random intervals (tables below). Hopper and Blackwell keep the default NVLS dispatcher, whose path is unchanged except after a RECOMPUTE resume (last item below).

## Changes

1. **Padding rows skip the experts.** On the nccl graph path, the rows that pad each rank up to the graph size are masked with `mask_routing_padding` before the gather, as the NVLS dispatcher already does, so they no longer go through the expert GEMMs. On A100 x2 this lowers single-request decode from 11.3-11.8 to 10.2-10.4 ms/token, compared with this PR without the mask. vLLM skips padding tokens in MoE routing by default as well (`VLLM_MOE_SKIP_PADDING`). The MTP forwards point the mask at their own row counts for nccl, as they already do for NVLS; the NVLS code is unchanged.
2. **Prefill and mixed graphs for the nccl dispatcher.** The EP batch-dimension sync takes the maximum of the token, prefill and decode counts, so every rank picks the same graph instead of the whole group going eager when one rank prefills. Only `inference_optimized` gets this; the NVLS dispatcher does not use this sync.
3. **Prefill check across EP ranks.** The async scheduler normally prepares step N+1 on the CPU while the GPU still runs step N (overlap ordering), which assumes a decode-only graph. With the graphs above, one rank's prefill pads every other rank into a mixed graph, so before each step the EP ranks exchange one flag, "may prefill", and if any rank sets it, all take the no-overlap ordering for that step. With the coordinator this is one more blocking ZMQ exchange of the kind `match_graph_config` already does every step; without it, an NCCL all-reduce over the EP group. It runs only with nccl prefill and mixed graphs, never with NVLS.
4. **nccl fallback.** For `inference_optimized` with EP > 1 on pre-Hopper GPUs, `resolve_inference_moe_dispatcher_type` switches `'nvls'` to `'nccl'` with a warning. NVLS-only features raise instead. Hopper and newer, and other `transformer_impl` values, get the setting back unchanged.
5. **Real-token-count binding survives a RECOMPUTE resume.** The binding moves from `__init__` into `initialize_all_tensors`, next to the attention metadata binding, so a resume rebinds it before the CUDA graphs are recaptured. This also fixes the NVLS dispatcher, which kept reading the pre-suspend tensor after such a resume; on a fresh start nothing changes.

## Known limitations

- **KV-cache pressure:** a rank with paused and waiting requests reports a possible prefill every step, so the EP group stays on the no-overlap ordering until the pressure clears. Only the scheduling order changes, not the graphs that run.
- **One more exchange per step:** the prefill check adds one small exchange per step with nccl prefill and mixed graphs: a blocking ZMQ exchange with the coordinator, or an NCCL all-reduce and a host sync without it, next to the same kind of exchange the batch-dimension matching already does.
- **Per-dimension maximum:** prefill and decode counts are maximised separately across ranks, so a combination beyond the largest graph runs eagerly.
- **Config EP size:** the fallback reads the config's EP size, so a config with EP = 1 on a larger EP group does not trigger it, as before.

## Notes for reviewers

- **Greedy outputs.** Single-request greedy outputs can diverge from base after a few tokens (for example "place" vs "charm"), because the prefill now runs as a padded CUDA graph instead of eagerly and bf16 rounding differs. With prefill and mixed graphs disabled (`use_cuda_graphs_for_non_decode_steps=False`), single-request outputs match base exactly.
- **Why vLLM needs no such check.** vLLM also exchanges a value across DP/EP ranks once per step and pads every rank to the largest token count ([dp_utils.py](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/worker/dp_utils.py#L122)). On steps with a prefill its graphs are PIECEWISE (attention runs outside the graph), so a peer's prefill only adds empty rows to the token-wise parts. MCore graphs capture attention as well, so a peer's prefill turns this rank's step into a mixed one, which is what the prefill check accounts for. Folding the prefill check into the existing batch-dimension sync would avoid one exchange but requires reordering the engine step.
- **Relation to [Optimize NCCL MoE dispatch](https://github.com/NVIDIA/Megatron-LM/pull/8307).** That PR packs the three per-layer AllGathers of the nccl dispatcher into one. The padding mask touches the same function but reduces expert compute rather than communication; the two compose.
