# Check prompt log-prob cache writes instead of pinning KV blocks

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8853) · state: open · merged: False

## Original PR description

## What does this PR do?

With prefix caching and async scheduling, requests that return prompt
log-probs can crash the dynamic engine. To cache prompt log-probs on their
KV blocks, `capture_prompt_logprob_writes()` pins the blocks that a step's
prompt rows write to, and `commit_prompt_logprob_writes()` stores the rows
and releases the pins. Under async scheduling the commit runs after the
step's update and admission, so the pins outlive a request that finishes in
that step. Holding its blocks through that window breaks the engine in
three ways:
- The finished request's pinned blocks are unavailable to other requests.
  A request that needs a block then is paused, and if no other request is
  active, `update_requests()` fails its assertion "active_request_count ==
  0 with 1 paused requests and no hidden chunked prefill". This happens
  under both eviction policies.
- The pin covers only the blocks the last chunk wrote, so a chunked
  request's earlier blocks are released while its later blocks stay in use.
  With `REF_ZERO`, the earlier blocks leave the hash map while the later
  ones stay registered, and the next request with the same prefix makes
  `_find_kv_match_count()` raise `KeyError` on the missing parent.
- With `LRU`, those earlier blocks count as evictable, but leaf-peel
  eviction cannot remove a block whose child is in use, so an allocation
  that relies on them fails the assertion in `evict_lru_blocks()`.

This PR removes the pin. The capture records each row's block, the block's
index in the request's block table, and its hash; the commit stores a row
only while its block still belongs to the same request or is still cached
under the same hash, and drops the other rows. A finished request's blocks
are released at once, and the only cost is that rows whose blocks were
freed or reused before the commit are not cached.

## Example failure scenario(s)

**Scenario 1 (a finished request's pinned blocks starve another request)**
- The engine has three usable 8-token blocks, a one-block paused budget,
  and async scheduling.
- Request A decodes in one block, and request B asks for prompt log-probs
  on a 16-token prompt that fills the other two blocks.
- B finishes after one token in the same step in which A needs a second
  block.
- B's two blocks stay pinned until its rows are stored after that step's
  update, so A is paused.
- No request is active, and `update_requests()` fails its assertion.

**Scenario 2 (`REF_ZERO`: a shared prefix loses its first block)**
- The engine has 8-token blocks, a 12-token step budget, prefix caching
  with `REF_ZERO`, and async scheduling.
- Request A asks for prompt log-probs on a 24-token prompt, prefilled in
  chunks of 12 and 12, and its second chunk's blocks 1 and 2 stay pinned
  until their rows are stored.
- Request B, with the same prompt, waits while A generates its one token
  and releases its blocks in the step that resolves that chunk.
- Block 0 drops to zero references and leaves the cache, while the pinned
  blocks 1 and 2 stay cached.
- In the same step's admission, B's prefix match finds block 1 cached
  without its parent block 0 and raises `KeyError`.

**Scenario 3 (`LRU`: eviction cannot free a counted block)**
- The engine has four usable 8-token blocks, a 12-token step budget, prefix
  caching with `LRU`, and async scheduling.
- Request A asks for prompt log-probs on a 24-token prompt, prefilled in
  chunks of 12 and 12, and finishes while its blocks 1 and 2 are still
  pinned.
- Block 0 drops to zero references and counts as evictable, so the engine
  sees one free block and one evictable block.
- Request B, with a different 24-token prompt, is admitted in the same step
  and needs two blocks.
- Eviction cannot remove block 0 while its child is in use, so
  `evict_lru_blocks()` fails its assertion.

## How was this bug discovered?

A stateful search drove the real engine through generated sequences of
submissions, steps, suspends and aborts, with prompt log-probs requested
under prefix caching, and checks every request's tokens and scores against
an exact reference. On current `main`, a 16-action history crashed in the
admission check with a `KeyError` from `_find_kv_match_count()`; a per-step
dump of the hash map showed a request's first block removed while its
pinned later blocks stayed registered, exactly before the lookup. A first
fix pinned each request's whole block prefix instead. A search that also
drew `LRU` eviction then found a history failing in `evict_lru_blocks()`
with "leaf peel evicted 2 of 3 requested from 5 cached blocks", and a
later search with the whole-prefix pin found the paused-request assertion.
A two-request probe reproduced that assertion on `main` in 5 of 72 timings
per eviction policy with prompt log-probs on, and in none with them off, so
the pin itself is the cause. The pin arrived with the prompt-score cache
(#7063) through #8426.

## Scope

- Production (+65/−34):
  - `megatron/core/inference/contexts/dynamic_context.py`:
    `PromptLogprobsWrite` gains `request_id`, `block_indices` and
    `block_hashes`; `capture_prompt_logprob_writes()` pins nothing, and
    `commit_prompt_logprob_writes()` stores only rows whose blocks still
    hold their tokens.
  - `text_generation_controller.py`: one comment.
- Tests (+245/−2), each end to end with a zero-logit model forward:
  - `test_dynamic_engine.py`: `test_prompt_log_probs_do_not_starve_other_requests`
    (scenario 1, both policies, three timings),
    `test_prompt_log_probs_keep_cached_prefix_chain_whole` (scenario 2,
    checking after every step that the prompt's cached blocks form a
    prefix), and `test_prompt_log_probs_leave_finished_blocks_evictable`
    (scenario 3).
  - `test_dynamic_prefix_caching.py`:
    `test_commit_skips_rows_whose_blocks_were_released` (both policies),
    and `test_capture_and_commit_cache_rows_on_their_blocks` now expects
    the capture to leave reference counts unchanged.
- Caching behavior: under `LRU`, a finished request's full blocks keep
  their rows while still cached, as before; its partly filled last block,
  which returns to the free pool, no longer gets rows. Under `REF_ZERO`,
  its blocks are deregistered at release, so their rows are dropped, as
  they were when the old pin was released.
- No functional-test, config or API change.
