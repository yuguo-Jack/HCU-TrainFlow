# Remove host syncs from the MTP draft loop and CUDA-graph the commit pass

# What does this PR do?
Two sources of GPU idle in MTP speculative decoding, measured with nsys on Nemotron Super v3 (TP2, EP4, 12 draft tokens, 8 requests per engine):

- Draft-loop metadata: every draft depth rebuilt its attention metadata with ~30 small eager ops, two of them scalar writes that forced a host sync. A single Triton kernel (`mtp_draft_step_metadata`) now writes the same token maps, lengths, cumulative lengths and block table, bit-exact with the eager path, so the host can enqueue the next depth while the current one runs.

- Commit pass: the per-step refresh of accepted drafts' MTP KV ran eagerly (~140 launches, ~11 ms of host time per step). On graphed decode-only steps it now replays a fixed-shape CUDA graph: each request gets `num_speculative_tokens` rows, unused rows write the dummy block, and the uniform layout takes the decode attention kernel. A second Triton kernel (`mtp_commit_step_metadata`) stages the metadata from GPU-resident accepted counts, so no host sync is needed. Mixed, prefill and eager steps keep the existing varlen commit pass. EP dummy ranks replay the same graph, and the engine warmup captures it per request count.

Under nsys, the median full-batch decode step dropped from 53.4 ms to 41.4 ms with the draft-loop kernel and the FlashInfer sampler (45.8 ms with the torch sampler), and the draft loop went from 49% to 93% GPU-busy. With the commit pass graphed as well, an unprofiled run takes 29.2 ms.
