# Keep hidden chunked prefill rows during async overlap resolution

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8642) · state: open · merged: False

## Original PR description

## What does this PR do?

With chunked prefill and async scheduling (the default), a request whose next
prefill chunk cannot be admitted, for example because KV blocks are short,
waits in a row just past the active rows. Meanwhile, decode requests continue
through async overlap steps, which retire finished requests with
`DynamicInferenceContext.resolve_requests`. That function did not account for
the waiting row:
- **When every active request finished,** it cleared every KV block table
  and reset Mamba state. The waiting request lost its prefilled blocks, which
  were never released, and its next chunk ran with invalid block IDs for the
  already-prefilled prefix.
- **When only some finished,** the waiting row was left in place instead of
  moving to the new boundary of the active rows.

This PR keeps the waiting row through resolution and pulls it to the new
boundary, as `update_requests` already does for the legacy scheduling order.
The waiting request keeps its prefilled KV blocks, and every block is
released when it finishes.

## Example failure scenario(s)

**Scenario (waiting prefill loses its KV blocks)**
- The step budget is 48 tokens, with ten 8-token KV blocks.
- Requests A (16 tokens) and B (15 tokens) decode 9 tokens each. Request C
  (47 tokens) prefills a 17-token first chunk into 3 blocks.
- C's remaining 30 tokens need blocks that are not free, so C waits while A
  and B decode through overlap steps.
- A and B finish in the same overlap step, which clears C's block table while
  its 3 blocks stay allocated.
- C's next chunk is admitted with block table `[-1, -1, -1, 6, 7, 1]`, so it
  attends to invalid KV for its prefix. After C finishes, only 7 of 10
  blocks are free.

## How was this bug discovered?

A stateful search drove the real engine through random sequences of
submissions, steps, suspends, resumes, and drains under both scheduling
orders, with a deterministic synthetic model. After every step, the search
checks the documented chunked-prefill invariant: the waiting chunked request
keeps its row, with its KV blocks, just past the active rows. Under async
scheduling, a step in which every decode request finished left the context
with no rows and a stale request ID where the waiting chunk's row should be.
Snapshotting every step showed `resolve_requests` clearing the waiting
request's block table, and a three-request reproducer showed 3 of 10 blocks
leaked on unmodified `main`. Legacy scheduling releases all 10.

## Scope

- Production: `megatron/core/inference/contexts/dynamic_context.py`,
  `resolve_requests` only (+13/−1). It reuses `_swap_book_keeping_tensors`,
  the helper `update_requests` uses for the same move.
- Tests:
  - `tests/unit_tests/inference/contexts/test_dynamic_context.py` (+36):
    `resolve_requests` with a waiting chunk row, for all finished, the first
    finished, and the last finished, with GPT and hybrid models. The row's
    index, block table, block count, and Mamba slot must be preserved, and only
    the finished rows' blocks may be released.
  - `tests/unit_tests/inference/engines/test_dynamic_engine_async_sched.py`
    (+107): the scenario above, end to end with a zero-logit model forward.
    It requires an overlap step while request C waits, all three completions
    at their exact lengths, and every block free afterward.
- The legacy order and the async no-overlap path are unchanged.
- Related: #6442 allowed overlap to proceed while a chunk waits; this PR
  makes the resolution that follows keep the waiting row.
