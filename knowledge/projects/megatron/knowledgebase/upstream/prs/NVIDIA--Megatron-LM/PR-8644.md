# perf(inference): batch-invariant TP=2 reduce-scatter over symmetric memory

# What does this PR do?

Batch-invariant inference at TP=2 reduces the sequence-parallel partials with a symmetric-memory pull kernel instead of an NCCL reduce-scatter. The result is bitwise NCCL's, which is what training uses, and each decode step is about 0.3 ms faster.

## Details

At TP=2 every reduced element is a single addition, so its order cannot vary. Batch-invariant mode still turned off the NVLS path for the row-parallel and sequence-parallel reduce-scatters and used NCCL, because the NVLS `multimem.ld_reduce` reduction does not produce NCCL's bits. Over all 2^32 pairs of BF16 bit patterns, `multimem.ld_reduce.add.acc::f32.bf16x2` differs from NCCL on 183,246,885 pairs (4.3%). It matches neither round-to-nearest-even nor round-toward-zero, and it differs on about 19% of the elements of random activations. NCCL's reduce-scatter equals `bf16(fp32(a) + fp32(b))` on every pair.

The new `pull_reduce_scatter` (`torch_symm_triton/pull_collectives.py`) loads the rank's shard from every peer's symmetric buffer with plain NVLink loads. It starts from rank 0's value, so signed zeros survive, adds the remaining partials in FP32 in rank order, and rounds to BF16 once. At two ranks this is the correctly rounded sum: it equals NCCL on all 2^32 pairs and on activation messages of 64 to 8192 tokens. Synchronization is the same `symm_mem_sync` barrier the other symmetric-memory collectives use, so the kernel is CUDA-graph safe.

`InferenceRowParallelLinear` and `inference_reduce_scatter_to_sequence_parallel_region` use it when batch-invariant mode is on and TP=2 (BF16, NVLS-eligible tensors, symmetric buffer available). The row-parallel GEMM writes its output straight into the symmetric buffer, as the non-batch-invariant NVLS path does. Other TP sizes keep NCCL, and the non-batch-invariant path is unchanged.

## Performance

GB200, Nemotron-3-Nano engine decode (MXFP8, TP2 with SP, EP4, CUDA graphs), batch-invariant mode:
- Reduce-scatter of 64 tokens x 2688 in a CUDA graph: NCCL 21.1 us, NVLS multimem 6.3 us, pull 6.4 us per call.
- Decode step: 0.28 to 0.31 ms faster at 1 to 32 requests and 1k to 8k context, against steps of 5.7 to 7.7 ms.

## Tests

- `tests/unit_tests/inference/test_pull_reduce_scatter.py` (2 or more GPUs, TP=2 groups) checks the pull kernel bitwise against `torch.distributed.reduce_scatter_tensor`:
  - on activations of 2 to 4096 tokens;
  - on every BF16 bit pattern against a set of edge-case patterns: signed zeros, subnormals, the normal boundary, overflow to infinity, ties, and NaN.
- The kernel is registered as `inference_pull_reduce_scatter` in `tests/unit_tests/determinism/kernels/manifest.py`.
- On GB200 (4 GPUs): `test_pull_reduce_scatter.py` and `tests/unit_tests/inference/test_moe_dispatching_and_routing.py`, 66 passed and 9 skipped per rank (the skips need DeepGEMM BF16 grouped kernels, the TE grouped-tensor API or FlashInfer NVFP4); `tests/unit_tests/determinism/kernels/test_manifest.py`, 290 passed.
- Inference engine (Nemotron-3-Nano, MXFP8, TP2/SP, EP4, batch-invariant mode): log-probabilities are bitwise those of the NCCL path, 0 of 5,592 prompt, 0 of 2,048 generated and 0 of 3,820 rescored tokens differ.
- Megatron-LM's RL loop (Nemotron-3-Nano, GRPO, TP2/SP, EP8, batch-invariant mode, 3 iterations): 0 of 486,586 generated tokens have an engine log-probability that differs from the trainer's. The same run with the NVLS multimem reduce-scatter in place of the pull kernel differs on 93.7% of tokens.
- black, isort, pylint and ruff with the `tools/autoformat.sh` settings report no changes on the changed files.
