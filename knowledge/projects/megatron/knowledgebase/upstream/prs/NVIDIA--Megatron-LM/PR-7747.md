# fix(inference): enforce request token stops and preserve finish reasons

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7747) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Let the dynamic engine enforce explicit per-request stop token IDs and report whether a completed response stopped or exhausted its token budget. RL clients need this distinction to filter overlong responses correctly: an EOS/stop at the last allowed token is not a length truncation.

Add validated `SamplingParams.stop_token_ids`, independent of model EOS stopping. Retain the matched stop token, remove speculative tokens and scores after it, and reuse the existing deferred-finish bookkeeping for engine-side stop detection. Explicit stops still apply with `termination_id=-1` (ignore model EOS).

Set `InferenceRequest.finish_reason` to `stop` or `length` at the dynamic-engine completion boundary, preserving stop-string detection even when text is stripped. Carry the field through serialization and request-record merging. A stop occurring beyond the response budget does not override a length finish. KV handoff is not a completed generation and leaves the reason unset.

There's an edge-case here.

Sampling params' stop IDs, stop words, and MTP EOS, all check for finish reason inside the engine, after the controller has already finished its step. Which means these requests will run for one extra step past finish.

Thus, there is a 1-step window where the request is finished and the `finish_reason` is set by the engine (not this method, but the L2715 block), but the request can still be evicted or suspended.

If an eviction or suspend happens during this 1-step window, the request gets `checkpoint()`'d and loses both its `finish_reason` and `generated_tokens`. This method then makes it default to `length`.

Prior to this PR, this edge-case successfully said `stop` instead of `length. I think this fix is necessary; basically, we re-check whether the context thinks this request is finishing:
```
        is_token_stop = request.request_id in self.stop_word_being_finished_ids or (
            bool(request.generated_tokens)
            and request.generated_tokens[-1] in self._terminating_token_ids(request)
        )
```

See the other thread, on L2914, regarding the edge-case behavior with requests getting suspended on their final step.

If that scenario occurs, and also upon re-admission the prompt goes through chunked prefill, the finish flag is entirely lost and the request just keeps generating past its normal finish point.

This is a pre-existing bug, but it's also aggravated further by this PR.

The place to fix this would be around L2900, inside `_get_and_clear_stop_word_finished_ids`:
```
        # Find which stop word finished IDs are in the current active requests
        result = self.stop_word_finished_request_ids & set(active_request_ids)
+       # A partially prefilled request cannot finish this step.
+       result.discard(self.context.chunked_prefill_request_id)
        # Move to "being finished" set so post_process_requests can skip the extra token
        self.stop_word_being_finished_ids = result
        # Clear the IDs that we're returning (they'll be marked as finished)
        self.stop_word_finished_request_ids -= result
        return result
```
