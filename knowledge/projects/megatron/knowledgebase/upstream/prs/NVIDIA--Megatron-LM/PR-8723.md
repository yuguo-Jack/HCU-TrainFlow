# Create DDP's fallback expert data-parallel group collectively

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8723) · state: closed · merged: False

## Original PR description

**Why.** `ProcessGroupCollection.setup_process_groups_for_ddp` fills a missing or `None` `expt_dp` with `torch.distributed.new_group(ranks=[rank])`. Each rank passes a different rank list, but `new_group` requires every rank to create the same groups with the same arguments in the same order. The call works only because each group has one member. The same group name then stands for a different rank on every rank, which breaks tools that match groups across ranks by name, such as the flight recorder. Megatron-Bridge MIMO takes this path in production: it builds per-module collections without `expt_dp` and wraps DDP per module.

**What.**
- Create the single-rank groups once, over every rank, with `torch.distributed.new_subgroups_by_enumeration`, and keep the one that holds this rank. This is how `parallel_state` builds groups, and #8051 does the same for Megatron-FSDP v1.
- A collection that provides `expt_dp` is used as before.
- No new `parallel_state` reads.

**Tests.** New `tests/unit_tests/distributed/test_ddp_expert_dp_fallback.py`:
- The helper and `DistributedDataParallel` on a collection without `expt_dp` (absent or `None`) create identical groups on every rank. Each rank keeps a single-rank group of its own, and a later group can still be created and all-reduced on.
- A provided `expt_dp` is used and no group is created.

Before the sync with main, on 4 GPUs against main: no regressions, the 3 fallback tests fail on main and pass here, and all 4 pass. In the integration run, all 4 tests in `test_ddp_expert_dp_fallback.py` pass on 4 GPUs, and this PR's test files show no regressions against main. Like many existing tests, the new ones do not destroy the groups they create.

**Compatibility.** Group membership is unchanged: one rank, this rank. On this path DDP setup makes `world_size` `new_group` calls (one per rank of the job) instead of one, so Bridge MIMO pays that once per DDP-wrapped module. With lazy NCCL init, the Megatron and Bridge default, non-members create no communicator. No API or checkpoint change.

This is a partial fix. All ranks must still take the fallback branch together. If only some ranks' collections lack `expt_dp`, as with uneven MIMO module grids, group creation still goes out of step, on main and with this change alike. Which full fix do you prefer: require `expt_dp` for modules with expert-parallel parameters, or create the fallback only once DDP knows whether expert buffers exist, and then on every rank?

Left as on main: an MoE model with expert-DP > 1 and no `expt_dp` still reduces expert gradients over a single-rank group, with only a warning. Raising here would break callers that follow the optimizer setup's advice to leave `expt_dp` unset when they don't need it, including Bridge's dense MIMO models.
