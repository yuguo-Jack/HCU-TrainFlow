# fix(mtp): count acceptance before CE when the loss gives no argmax

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7623) · state: open · merged: False

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Compute MTP acceptance counts in `process_mtp_loss` *before* `compute_language_model_loss`, so Transformer Engine fused cross-entropy cannot overwrite the logits buffer in place and silently zero `mtp_{k}_acceptance_rate`.

## Why

TE fused CE reuses the input logits storage for softmax-onehot dgrad scratch (`overwrite_input=True` is the MCore default after #7309). Acceptance was introduced after CE in #3458, so argmax ran on destroyed logits: target entries become negative while non-target entries stay nonnegative, reporting 0% acceptance while the loss itself stayed correct.

This matches the root-cause writeup on [NVIDIA-NeMo/Megatron-Bridge#5947](https://github.com/NVIDIA-NeMo/Megatron-Bridge/issues/5947) (@yaoyu-33). Reordering preserves the intentional CE memory design and also covers native/unfused FP32 paths that mutate storage after `.float()` is a no-op. Cloning logits on the TE path only would miss those backends and cost a full `[s, b, v]` copy on long sequences.

## Issue tracking

## Changes

- `megatron/core/transformer/multi_token_prediction.py`: call `_compute_mtp_acceptance_counts` before CE when `is_training`.
- `tests/unit_tests/transformer/test_multi_token_prediction.py`: CPU unit test with a TE-like destructive CE mock that overwrites logits in place; asserts acceptance stays full and post-CE argmax no longer matches labels.
