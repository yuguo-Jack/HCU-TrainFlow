# [GTP] Preserve independent expert prefetch chains under CUDA graphs

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8345) · state: closed · merged: True

## Original PR description

## Description:

Extend #6057’s separate grouped-expert FC1/FC2 prefetch chains to full-iteration and local CUDA graphs.

Previously, captured expert weights shared the general graphed chain: current FC1 prefetched current FC2 instead of next-block FC1, reducing the available communication-overlap window. Additionally, recording gather completion when consumed could make current FC2 wait for unrelated later FC1 communication on the shared all-gather stream.

## This change:

- Preserves independent captured FC1/FC2 chains and their buffer ownership.
- Uses consistent captured-chain filtering for communication drains and stream joins.
- Records grouped-gather completion immediately after issue, **after the underlying communication wait,** including synchronous fallbacks without a Work handle.
- Replays gradient-ready hooks on each parameter’s actual reduce-scatter stream.

## Prefetch chains under full-iteration CUDA graphs

BEFORE: one logical captured chain
```
  [Dense] → [Grouped FC1] → [Grouped FC2] → [Dense] → ...
                  all classified as GTP_graphed
```

AFTER: three logical captured chains

```
  Dense: [Dense 0] → [Dense 1] → [Dense 2] → ...
  FC1:   [FC1 L0]  → [FC1 L1]  → [FC1 L2]  → ...
  FC2:   [FC2 L0]  → [FC2 L1]  → [FC2 L2]  → ...
```

The FC1/FC2 chains remain independent but share one AG stream. Each prefetch targets the same weight family in the next MoE block.

## Completion-event ordering and safety
<img width="1400" height="1100" alt="image" src="https://github.com/user-attachments/assets/93abc15b-e48a-4b5d-8b28-311627ccdaa6" />


- **Steps 1–3:** the underlying `Work.wait()` establishes the NCCL → AG-stream dependency **before** recording the completion event. It does not insert a wait on the default stream.
- **Steps 4–5:** the consumer still waits on that event before using the weights.
- `completion_recorded=True` prevents re-recording the event at consumption, which would make it include unrelated later gathers. The later wrapper `wait()` only updates tracking state; its underlying Work handle has already been cleared.

This preserves synchronization while allowing current FC2 computation to proceed without waiting for next-layer FC1 communication.

### Why this fix is critical for GTP+full-iter CG's performance

- `Earlier prefetch`: The merged chain prefetches the next weight in execution order. Separate chains let FC1/FC2 prefetch their counterparts in the next MoE layer, giving communication more time to overlap computation.
- `Fewer unnecessary waits`: The completion-event fix lets a GEMM start once its own weights arrive, without waiting for unrelated gathers queued afterward.
- `CG makes this overlap more useful`: Full-iteration CG removes much of the CPU launch overhead. Better prefetching then helps keep the GPU compute stream busy instead of waiting for weights.

## Validation:

- 89 targeted tests passed per rank on four GB300 GPUs: 80 basic GTP, 7 grouped-CG, and 2 partial-CG tests.
- Covers BF16 full/local graph replay, eager/captured completion ordering, synchronous gather fallbacks, and native-MXFP8 SwiGLU replay across six Adam updates.
- Fixed test isolation so captures do not join stale streams from earlier tests.

## Perf Results on DSV4-pro-half-proxy: 35% e2e perf gain

Both runs use 256 NVIDIA GB300 GPUs, MXFP8, Adam, and the DSV4-Pro 30-layer proxy + MTP1, with TP1/PP1/CP1/EP64/**GTP64/EGTP4**, **full-iteration CUDA graphs**, and profiling enabled.

> By putting the ag_event before the handle wait,

That's not True.

We do not record the event before the underlying communication wait. Both Work.wait() and event recording move to the gather-issue site, in that order on ag_stream. The later wrapper wait only performs bookkeeping; the consumer still waits on ag_event before using the weights.
