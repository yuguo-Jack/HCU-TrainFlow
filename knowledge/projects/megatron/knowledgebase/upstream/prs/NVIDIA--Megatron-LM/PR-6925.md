# What does this PR do?

Support RL gradient-buffer offload when legacy DDP uses NCCL user-buffer registration (UBR).

The affected path is selected by:

```text
--perform-rl-step
--rl-offload-optimizer-during-inference
--use-nccl-ub
```

For this non-CUDA-graph RL path, persistent parameters and disposable gradients receive separate NCCL memory pools. Offload deregisters and releases only the gradient pool; restore recreates gradient storage in a new pool and explicitly registers it with the same data-parallel communicator. Parameter storage stays registered at the same address.

MXFP8 layouts that alias parameter and gradient storage are rejected because those lifetimes cannot be separated.

## Why?

Today, parameters and gradients share one registered pool. Shrinking gradient storage does not release that pool while parameter storage remains live. Restore then grows the storage outside the old pool context, so the replacement address is not explicitly registered.

Training can therefore continue with correct gradients while silently losing both requested properties:

- the old pool retains the released gradient segment instead of returning it for inference;
- restored gradient collectives no longer use explicitly registered storage.

This is a lifecycle and capacity bug, not a crash or numerical-corruption claim.

## Implementation

- Separate non-mutating configuration validation from runtime finalization. `initialize_megatron()` calls `container.finalize()` before runtime services, distributed initialization, and RNG seeding. Finalization applies RNG derivations and, only for RL runs, the required `grad_buffer_offload` layout to the owned `cfg.ddp`; both model-construction paths consume that same configuration without copies. Explicit layout requests are preserved, and CUDA-graph RL does not require gradient-buffer offload.
- Finalization applies runtime derivations once. Subsequent calls are no-ops to support initialization re-entry; use a fresh container for a differently configured run. This repeated-call policy is explicitly raised in the review discussion.
- Split pools only for the registered offload-capable layout; ordinary allocation and other UBR users keep their existing layout.
- Validate every registered buffer and complete all gradient-pool deregistrations before mutating storage. If deregistration fails partway through, storage remains intact but earlier deregistrations are not undone; the run must abort rather than retry offload or reuse the model.
- Drop the old gradient-pool owner after its storage is released; no process-wide `gc.collect()` is needed.
- Allocate and explicitly register the initial replaceable gradient pool, so construction fails rather than retaining an unregistered pool. Restore likewise allocates replacement storage inside a new pool and registers it explicitly. This is deliberate: the existing `nccl_mem` context suppresses registration `RuntimeError`, which is unsafe at either lifecycle boundary. A restore registration failure leaves the buffer offloaded and retryable.
- Add registration/restore error context with exception notes, preserving the original exception type, including CUDA out-of-memory errors.
- Deregister every distinct live pool during shutdown.
- Preserve the existing default gradient-content contract: offload discards and restore zeros gradient contents.

Draft #7383 separately proposes opt-in gradient-content preservation by changing the same private offload/reload helpers. The contracts are independent, but whichever PR lands second will need a semantic rebase; this PR does not claim automatic compatibility with that draft.

## Behavior and cost

This makes the three requested options honor registered-buffer ownership; it is not a blanket speedup. The measurements below are historical evidence from earlier revisions of the same lifecycle design, not performance measurements of the current head.

A paired same-node 128 MiB reduce-scatter probe measured the unfixed post-restore path 10.17% slower than its own pre-offload path. The fixed path changed by 0.007%, and its post-restore service was 7.52% faster than the unfixed post-restore path.

The correct transition has a real cost because it deregisters, destroys, recreates, and registers a pool. In a synthetic stock-`train_rl.py` GRPO comparison, fixed local and symmetric registration were respectively 0.9% and 2.7% slower end to end than the unfixed path. The tradeoff is restored registration and usable inference headroom: a capacity probe exposed 2.1035 GiB more memory per rank and completed a common 73.5 GiB inference allocation that the unfixed path could not allocate.

### What I checked
- **Offload/restore order** ([distributed_data_parallel.py#L773-L810](https://github.com/NVIDIA/Megatron-LM/blob/74ac87c6071eaca6e8f35671306bf196885207c1/megatron/core/distributed/distributed_data_parallel.py#L773-L810)):
  - Offload checks every registered buffer first. It deregisters all gradient pools before touching any storage, then resizes storage to 0, then drops the pool owner.
  - Restore creates a new pool, allocates through `torch.cuda.use_mem_pool`, and registers it explicitly.
  - Parameter pools are never touched.
- **tdene's earlier comments (both fixed in the current code):**
  1.   2. The parameter pool is created and registered inside a `try` block, and a failure there rolls back the gradient pool that was already registered ([#L1280-L1294](https://github.com/NVIDIA/Megatron-LM/blob/74ac87c6071eaca6e8f35671306bf196885207c1/megatron/core/distributed/param_and_grad_buffer.py#L1280-L1294)). - **The new `RuntimeError` can't be hit from in-tree RL code:**
  - Both RL offload sites only offload gradients when `not args.rl_training_cuda_graphs`: [rl_utils.py#L797-L801](https://github.com/NVIDIA/Megatron-LM/blob/74ac87c6071eaca6e8f35671306bf196885207c1/megatron/rl/rl_utils.py#L797-L801) and [#L3031-L3036](https://github.com/NVIDIA/Megatron-LM/blob/74ac87c6071eaca6e8f35671306bf196885207c1/megatron/rl/rl_utils.py#L3031-L3036). This fallback does not work. I would say this is a torch bug.

The first thing that `register_mem_pool` does is record the pool's ID in an internal torch bookkeeping dictionary. If `register_mem_pool` fails after that, it does not clear the bookkeeping dictionary.

Instead, what happens is that, as soon as `pool` is garbage-collected (which here happens when we `raise`), we get a C-level crash inside torch.

To resolve this, we would need something like
```
        except RuntimeError:
            # Leave the buffer offloaded so a caller can retry or shut down cleanly.
            self.offload_to_cpu(move_params=False, move_grads=True)
            try:
                nccl_allocator.deregister_mem_pool(pool, self.data_parallel_group)
            except RuntimeError:
                pass
            raise
```

This should probably be reported upstream to torch.
