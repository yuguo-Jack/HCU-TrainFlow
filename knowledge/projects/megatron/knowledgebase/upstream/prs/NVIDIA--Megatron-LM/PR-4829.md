## Original PR description

# What does this PR do ?

PR 1/4 of the planned scaling-recipes stack. 
Design doc: [PR_MuP.pdf](https://github.com/user-attachments/files/27854711/PR_MuP.pdf)
Adds
- internal scaling-policy infrastructure used by the follow-up `mup`, `depth_mup`, and Muon interaction PRs, without introducing the public scaling-recipe surface yet, as planned in #4381. 

This PR:
  - Adds `megatron.core.parameterization` with resolved scaling context, model policy, training policy, and parameter-role helpers.
  - Routes existing model-side MuP-sensitive behavior through policy hooks for embeddings, logits, attention scaling, initialization, and transformer-layer construction.
  - Routes optimizer override construction through the resolved training policy while preserving existing behavior.
  - Preserves scaling metadata through model and FSDP parameter paths.
  - Makes optimizer param-group resume matching stable for older checkpoints by:
    - excluding mutable scheduler values such as `max_lr` / `min_lr` from group identity;
    - default-normalizing missing legacy identifier fields to runtime defaults.
  - Adds internal documentation and regression coverage for the policy seam and optimizer group compatibility.

  This is intentionally the infrastructure slice only. Follow-up PRs layer on:

  1. `feature/scaling-recipe-mup`: canonical width-MuP recipe API.
  2. `feature/depth-mup`: experimental dense-GPT depth-MuP support.
  3. `feature/muon-spectral-mup`: Muon scalar optimizer interaction.

- janEbert · comment · 2026-07-20T13:17:27Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/4829#issuecomment-5022678498)

Hey, what I like about the initial design here is that it has a very explicit goal, hardcoding things where it makes sense to enable parametrization support but nothing else, which keeps things simple.

However, I think that's also a limitation that we'd like to avoid integrating before other design decisions. I'd prefer we start with general user-facing optimizer and initialization configuration APIs, which would allow other modern related configurations as well. I've had the feeling that modern LLM trainings really like to make use of per-layer configuration and enabling more general configuration options would benefit both goals in the long-term, enabling another dimension of user-freedom. The proposed scaling recipes could then be worked on top of those general APIs. (Although we'd prefer these to stay as examples. We would probably not maintain a list of parametrization policies in the core codebase.)

I think it makes sense to first consider these questions, which were also raised in https://github.com/NVIDIA/Megatron-LM/issues/5732, and work from there.
