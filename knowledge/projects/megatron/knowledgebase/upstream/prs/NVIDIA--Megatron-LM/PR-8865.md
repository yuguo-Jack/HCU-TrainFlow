# [Core][BatchInvariant] Accumulate fused weight gradients into main_grad in the batch-invariant TE GEMM

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8865) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Fixes lost weight gradients in batch-invariant training. Under `batch_invariant_backend="deepgemm"` or `"triton"` with `gradient_accumulation_fusion` (on by default in Megatron's CLI), every TE linear kept only the last microbatch's weight gradient in each step. The batch-invariant TE GEMM now accumulates into `main_grad`, and honors `alpha` and `beta`, as TE's own `general_gemm` does.

**Batch-invariant training results change.** With `deepgemm` or `triton`, gradients, and therefore losses after the first step, differ from before this PR. With more than one microbatch per step, the old numbers were wrong: they kept only the last microbatch. Single-microbatch runs change slightly too. BF16 configurations never pass `is_first_microbatch` to TE, so every fused weight gradient is an accumulating call, which now adds an fp32 product instead of a bf16-rounded one. Inference, forward outputs and `te_native` (which patches no GEMM) are unchanged.

## Bug

Batch-invariant mode replaces TE's `general_gemm` with `_te_general_gemm_patched` under `deepgemm`/`triton`. That function read only `A`, `B`, `out_dtype`, `layout`, `out`, `bias` and `grad`, and ended with `out.copy_(result)`. It never read `accumulate`, `alpha` or `beta`.

TE's fused weight-gradient path calls `general_gemm(x, dy, out=main_grad, accumulate=True, layout="NT", grad=True, ...)` (TE 2.20.2 `module/linear.py:1594-1630`, and the same in `layernorm_linear`). Megatron passes `is_first_microbatch` to TE only for FP8/FP4, kitchen or `quant_recipe` modules, so for BF16 every one of these calls accumulates. With the patch, each call overwrote `main_grad`, and Megatron's distributed optimizer reduced a `main_grad` that held only the last microbatch's weight gradient. Megatron's own `_wgrad_gemm(..., accumulate=True)` (`tensor_parallel/layers.py:712-736`), which GTP uses to sum a weight's several consumes through `te_general_gemm`, lost its accumulation the same way. Bias gradients go through `.grad` and were not affected. On `main` no forward call reached the patch with `accumulate` or `alpha`: TE's Linear and LayerNormLinear forwards pass neither.

## Fix

`_te_general_gemm_patched` now computes what TE computes, `alpha * op(A) @ op(B) + beta * out + bias`:
- **Operand ranks as in TE.** TE flattens both operands to 2D before applying the layout's transposes, and its output keeps B's leading dims unless B is transposed (`getGemmOutputShape`, `csrc/extensions/gemm.cpp:41-81`). The batch-invariant GEMM now does the same in every path: the fp32 weight-gradient product, `BatchInvariantTEGemmFn` forward and backward (which returns gradients in the operands' own shapes), and the bias gradient. This matters because TE Linear's weight gradient passes its saved input at `[s, b, in]` with `dy` at `[s*b, out]`, and the op fuser's `BasicLinear` passes 3D `x` and `dy`. 2D calls keep their bits.
- `accumulate` adds into `out`, with `beta` defaulting to 1 as in TE. A non-zero `beta` without `accumulate` raises, as in TE.
- **`None` means TE's default.** `alpha=None` is 1 and `beta=None` is 1 when accumulating, else 0, as TE maps them (`validate_gemm_scale`). TE's own `BasicLinear` passes `alpha=None` on every dgrad and wgrad. Every other optional argument is read the way TE reads it.
- **Weight gradients into fp32** (`main_grad`), whether they accumulate or overwrite, use the same fp32 path. The product is computed in fp32 by the batch-invariant persistent kernel from fp32 copies of the operands. bf16 values are exact in fp32 and TF32, so the products are exact and accumulate in fp32. The result is then combined into `out` in place (`mul_` and `add_`), so there are no `main_grad`-sized temporaries beyond the product. This makes a tracked first microbatch (overwrite) and later ones (accumulate) equally precise. The operands are upcast, rather than having `matmul_persistent` store its fp32 accumulator directly, because #8868 also changes `matmul_persistent`'s signature; that follow-up can come after both land.
- **Other calls** with `alpha` or `accumulate` (for example a bf16 residual) are combined in fp32 and rounded once to the result's dtype.
- **All other calls**, without `alpha` or `accumulate` and not into fp32 under `grad`, take the old path unchanged and keep their bits. Forward outputs therefore do not change.
- Arguments are mapped to TE's own `general_gemm` signature, so positional calls work and an unknown argument raises.
- **Rejected at config time.** Under `deepgemm`/`triton`, `TransformerConfig` now rejects global FP8/FP4 (`fp8`, `fp4`), with a message pointing to `te_native`: every TE GEMM would then get quantized operands, which these BF16 kernels cannot run. Before, such runs failed at the first GEMM; on `main`, with an `AttributeError`.
- **Rejected at runtime.** The GEMM itself still raises, pointing to `te_native`, for what no configuration-level check can decide:
  - a module that a per-module `quant_recipe` quantizes, since those precisions depend on module names that `TransformerConfig` cannot see, and a recipe may quantize only modules that never reach this GEMM (for example routed experts served by inference-optimized kernels);
  - GELU fusion (TE `LayerNormMLP`, which Megatron does not build);
  - Userbuffers. #8868 (`fix/bi-tp-reduce-scatter-order`) owns the config-time `tp_comm_overlap` rejection under `deepgemm`/`triton`; until it lands, the runtime raise is the guard, as on `main`.

No host syncs. Most of the change is confined to `_te_general_gemm_parameters`, `_te_quantized_tensor_types`, `_te_general_gemm_patched` and the new `_te_gemm_product_fp32`, which no other open branch touches. The flattening in `BatchInvariantTEGemmFn` sits on lines that fix/deepgemm-bi-dense does not change, so the two merge cleanly. The PR also adds the config check, next to the existing FP8/NVFP4 batch-invariance checks. The now unused `_extract_te_gemm_args` is removed. Cost: a weight gradient into fp32 runs the fp32 (TF32) persistent kernel, also under the `deepgemm` backend, on fp32 copies of `x` and `dy`.

## Tests

`tests/unit_tests/transformer/test_te_layers_batch_invariant.py` (1 GPU, H100; already registered for `batch_invariant_kernels.py` in the determinism manifest, so the coverage check passes without a new entry). The `deepgemm` cases skip only in the LTS image, which has no DeepGEMM (`is_lts_ci_image`, also added by #8866 with identical text). In the dev image they fail without DeepGEMM:
- `test_te_linear_fused_wgrad_accumulates_over_microbatches[triton|deepgemm x linear|layernorm_linear x b1|b2]`: a `TEColumnParallelLinear` and a `TELayerNormColumnParallelLinear` with `gradient_accumulation_fusion=True` run two microbatches of `[s, b, h]` inputs (b = 1 and b = 2) from a zero `main_grad`, both accumulating as TE does for BF16. Under batch-invariant mode, `main_grad` must equal the run without the mode (rtol 1e-2, atol 5e-2). Fails on `main`, where `main_grad` holds only the second microbatch.
- `test_bik_te_general_gemm_honors_accumulate_alpha_beta[triton|deepgemm x 11 cases]`: `general_gemm` under the mode matches TE's own result, in value and output shape (rtol 2e-2, atol 0.1). It uses the operand ranks TE's call sites pass:
  - TE Linear's weight gradient into fp32 `main_grad` with a 3D input (b = 1 and b = 2) and 2D `dy`;
  - `BasicLinear`'s weight gradient into fp32 (`alpha=None`, `beta=None`) and into bf16, its dgrad, and a forward, all with 3D operands;
  - 2D weight gradients into fp32: accumulate, and overwrite then accumulate (a tracked first microbatch);
  - `alpha=0.5`, `beta=2`, plus bias, into a bf16 residual;
  - `alpha=0.25` alone;
  - `alpha=None` alone.
- `test_batch_invariant_gemm_backends_reject_fp8[deepgemm|triton]`: construction raises. Fails on `main`.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), the regression tests pass (32 cases). On `main` the only evidence from this run is an import failure: the test module imports `is_lts_ci_image` from `tests/unit_tests/test_utilities.py`, a test helper this PR adds, so no test runs and the "Fails on `main`" notes above are not checked on GPU. The step 3 GPU repro of this finding, `test_step3_p4_n4_bi_te_wgrad_accumulation.py`, did reproduce it on `main` on H100 (4 of 4 cases): under `triton` and `deepgemm`, TE `Linear` and `LayerNormLinear` with `fuse_wgrad_accumulation=True` left `main_grad` matching the last of two microbatches, not their sum. The neighbor tests (`test_te_layers_batch_invariant.py`, `determinism/kernels/test_te_wrappers.py`, `inference/test_batch_invariant_deepgemm_stride.py`) pass (108 cases, 29 skipped).
