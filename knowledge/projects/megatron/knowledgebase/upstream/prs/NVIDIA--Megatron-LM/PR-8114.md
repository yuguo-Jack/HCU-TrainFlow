# What does this PR do?
Optimize MoE inference routing, token dispatch, and expert GEMMs, with correctness and end-to-end performance validation on GB300.

:warning: For major changes (either in lines of code or in its impact), please make sure to first share a design doc with the team. If you're unsure what's the best way to do so, contact @NVIDIA/mcore-oncall.

## Changes

- Fuse eligible sigmoid/top-k routing and parallelize expert token-alignment table construction
- Apply measured BF16 GEMM configurations to matching GB300 expert shapes, retaining heuristic fallbacks for other configurations
- Reduce NCCL/NVLS dispatch overhead through packed gathers and fused masking, output conversion, and shared-expert addition
- Share ordered TP reductions between batch-invariant (BI) training and inference paths
- Add unit tests and registered bit-exact kernel determinism tests

## Performance

Measured using Nemotron 3.5 Lightning 30B-A3B BF16 and the stakeholder-provided GSM8K HTTP workload on GB300, with four GPUs per node. One-node tests use TP4/EP4; two-node tests use TP4/EP8
- Candidate: 379fc56cd
- Ordinary baseline: unchanged main 442d0183d
- BI baseline: the same main revision with the identical ordered TP correction applied to both baseline and candidate. BI ratios are therefore not relative to unchanged main

Four fresh servers were run in baseline/candidate/candidate/baseline order. Speedup is baseline total batch wall time divided by candidate total batch wall time for equal work.

Each entry reports end-to-end speedup for BS8 / BS32 / BS128, where BS is the number of concurrent requests in each client batch. Values above 1 indicate improvement; values below 1 indicate regression. All formal samples are included in this table.

Across these long-output cells, geometric mean throughput improves by approximately 17–20% in ordinary mode and 1–2% in BI mode. These are end-to-end HTTP batch measurements, not isolated kernel speedups or TTFT/ITL measurements.

## Correctness and validation

- Numerical validation covered BS8/32/128 and output lengths 1/1024/2048/4096/8192 on all five supported mode/topology combinations above
- Each comparison covered 2,580,648 generated positions, with zero token differences and zero full-vocabulary BF16 logit-row hash differences. Each row contains 131,072 logits; baseline-repeat controls also passed.
- Ordinary validation used fixed admission; BI validation used dynamic HTTP admission. This does not claim ordinary-mode bitwise equality across arbitrary dynamic schedules
- Targeted unit, distributed, and determinism tests were run. Shared baseline/candidate test outcomes matched, including the two failures below
- Black, isort, Ruff, Pylint, whitespace, and kernel-determinism coverage checks passed. Full upstream CI remains pending.

## Issue tracking

Linked issue: None yet. The following follow-up issues have not been opened.

### Known issues and limitations

- Existing BI training/inference mismatch: `test_dynamic_engine_matches_batched_forward_rl` fails on both baseline main and the candidate in the tested environment. Training-style forward and dynamic-inference log probabilities differ. The root cause remains unconfirmed, and this PR does not fix it. Successful baseline/candidate inference comparisons do not establish training/inference parity
- Missing dependency: `test_batch_invariant_prefill_matches_full_forward` fails on both versions because the selected backend requires unavailable DeepGEMM BF16 grouped-GEMM bindings. This path needs a dependency-complete rerun
- Latency spikes: Multi-second host-side stalls occur in both baseline and candidate and remain unresolved. Separate Output Length 1 analyses retain raw results alongside explicitly labeled paired exclusions; filtered results are not tail-latency guarantees. First-use GEMM compilation overhead is a separate remaining issue
- Remaining regressions: BI two-node NVLS/Output Length 1/BS8 measured 0.949×, with both repeated comparisons slower and no multi-second outliers. BI one-node BS128 long outputs measured approximately 1.0–1.3% higher latency. These results remain under investigation and are not dismissed as noise
- Benchmark-client sensitivity: Ordinary one-node NVLS/Output Length 1/BS128 measured 0.923× with the original client. A separate investigation identified connection-pool overhead; an independent client configuration measured 1.039×. That configuration changes the benchmark protocol, is not part of this production-code change, and does not replace the original result.

They can merge in any order; the only conflict is in the determinism manifest between [#8306](https://github.com/NVIDIA/Megatron-LM/pull/8306) and [#8307](https://github.com/NVIDIA/Megatron-LM/pull/8307), so whichever lands second needs a trivial rebase.

The batch-invariance part (fixed-order TP reduce-scatter, and running these optimizations in batch-invariant mode) is not up yet. I can not yet show that it causes no slowdown on all three models, so I am holding it until I can and will open it as a separate PR.

One difference from your port in `1c0ad27c`: [#8296](https://github.com/NVIDIA/Megatron-LM/pull/8296) uses the fused kernel only for top-k < 8. For Super/Ultra (top-22) it replaces only `aten.topk` with a parallel version, so expert indices and FP32 probabilities stay bit-identical to main. That's why it adds `ParallelTopKMode`.
