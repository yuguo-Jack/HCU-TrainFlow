# What does this PR do?
`ChainedOptimizer.get_grad_norm` combined the per-optimizer norms with `math.sqrt(sum(x**2))`, a host synchronization that makes the optimizer step uncapturable into a CUDA graph (`--optimizer-cuda-graph`). Keeping the norm as a float32 device tensor instead changes the clip coefficient by one float32 rounding and breaks exact golden values of multi-optimizer runs (Muon), as the `gpt3_moe_..._muon` functional test showed.

- `get_grad_norm` now returns `torch.sqrt(sum(x**2).to(torch.float64))`: squares summed in fp32 as before, root in float64 on the device. CUDA's double `sqrt`, like `math.sqrt`, is IEEE correctly rounded, so the value equals the Python-float path bit for bit and no host sync remains.
- `clip_grad_by_total_norm_fp32` forms the coefficient in the norm's dtype (float64 → same arithmetic as the Python path) and rounds it once to fp32 before TE's `multi_tensor_scale_tensor`, which reads the scale as `float*`. The fp32 tensor path used by single-optimizer runs is unchanged (`.to(torch.float32)` is a no-op there).
- Tests: the clipped gradients from a float64 device norm equal those from the Python-float path (`torch.equal`, clipped and unclipped branches); the chained float64 norm equals `math.sqrt(float(sum))`.

Validation: 4-GPU A/B of the Muon functional-test configuration (EP4, clip 1.0, deterministic, 20 iterations): loss, grad norm and num-zeros identical to dev on every iteration; DSv4 proxy with `--optimizer-cuda-graph` + chunk-wise graphs captures and replays (no measurable step-time change).

### What I checked

**Norm combination** ([optimizer.py L1939-L1955](https://github.com/NVIDIA/Megatron-LM/blob/96d6098c84ede07b558b2c7238d47aa8a4606be0/megatron/core/optimizer/optimizer.py#L1939-L1955))
- The squares are still summed in fp32, including the mixed float-and-tensor case, as in the base code.
- The widening `.to(float64)` is exact, and CUDA's double `sqrt` is correctly rounded. So the combined norm matches the old `math.sqrt(tensor)` value bit for bit.
- Removing `_grad_norm if _grad_norm else 0.0` takes out the hidden `bool(tensor)` host sync. A zero norm and `None` still behave the same numerically.

**Clipping** ([clip_grads.py L179-L198](https://github.com/NVIDIA/Megatron-LM/blob/96d6098c84ede07b558b2c7238d47aa8a4606be0/megatron/core/optimizer/clip_grads.py#L179-L198))
- When the coefficient is at least 1, it is clamped to 1.0 and the gradients are multiplied by 1.0. For finite values that gives the same result as the Python path, which skips scaling.
- The single rounding to fp32 matches the conversion the Python float gets on its way into the float-scalar kernel.
- For the existing fp32 tensor path, `.to(torch.float32)` is a no-op.

**Downstream consumers of the float64 tensor**
- [`reduce_max_stat_across_model_parallel_group`](https://github.com/NVIDIA/Megatron-LM/blob/96d6098c84ede07b558b2c7238d47aa8a4606be0/megatron/training/utils/common_utils.py#L252-L270) converts to fp32 before logging, as it did for the old Python float. Logged grad norms are unchanged.
- The `grad_norm > grad_norm_skip_threshold` comparison works on the tensor.
- [`MimoOptimizer.get_grad_norm`](https://github.com/NVIDIA/Megatron-LM/blob/96d6098c84ede07b558b2c7238d47aa8a4606be0/megatron/core/models/mimo/optimizer.py#L62-L73) handles it like the shape-(1,) fp32 norms that single optimizers already return.
- `OptimizerCudaGraphWrapper` hands back the captured result tuple. A device-tensor norm is refreshed by each replay; the old Python float was the reason capture failed.

**Override:** `LayerWiseDistributedOptimizer` overrides `get_grad_norm` and returns an fp32 tensor. So `ChainedOptimizer([layer_wise, distopt])` only ever combines fp32 norms.

### Suggestions (non-blocking)
1. **The bit-exact claim only holds for power-of-two `clip_grad`.** In [clip_grads.py L179](https://github.com/NVIDIA/Megatron-LM/blob/96d6098c84ede07b558b2c7238d47aa8a4606be0/megatron/core/optimizer/clip_grads.py#L179), `max_norm / tensor` computes the reciprocal and then multiplies, which rounds twice. The Python path rounds once. The new tests only use `max_norm` 1.0 and 0.5, so they don't cover this. Either qualify the comments or use a tensor/tensor division for the float64 case (see the inline comment).
2. **The main invariant, "no host sync", has no regression test.** Reintroducing `if _grad_norm` would still pass. Running `get_grad_norm()` under `torch.cuda.set_sync_debug_mode("error")` would catch it (see the inline comment).

File: `megatron/core/optimizer/clip_grads.py` · line None

**[SUGGESTION Documentation]** The "exactly like the Python-float path" claim only holds when `max_norm` is a power of two.

**Failure.** `clip_coeff = max_norm / (total_norm + 1.0e-6)` ([L179](https://github.com/NVIDIA/Megatron-LM/blob/96d6098c84ede07b558b2c7238d47aa8a4606be0/megatron/core/optimizer/clip_grads.py#L179)) goes through `Tensor.__rtruediv__`, which PyTorch implements as `self.reciprocal() * other`.
- Device path, float64: `RN(RN(1/x) * m)`, two roundings.
- Python path: `RN(m/x)`, one rounding.
- For `m = 1.0` or `0.5` the multiply is exact, so the two agree. That is what the tests cover.
- For values like `clip_grad=0.3`, `3.0` or `5.0`, the float64 coefficient can be off by 1 ulp.
- Rounding to fp32 hides almost all of these cases. The fp32 coefficient only changes when an fp32 rounding boundary falls between the two doubles, roughly 2^-29 per occurrence. The practical impact is tiny, but the comments at clip_grads.py L186-188, [optimizer.py L1947-1952](https://github.com/NVIDIA/Megatron-LM/blob/96d6098c84ede07b558b2c7238d47aa8a4606be0/megatron/core/optimizer/optimizer.py#L1947-L1952) and the test docstring overstate the guarantee.

**Correction.** Pick one:

(a) Smallest option: say in those three places that bit-identity holds for power-of-two `max_norm`.

(b) Make it exact, at L179 in `clip_grad_by_total_norm_fp32`. This is outside the diff hunk, so it can't be a suggestion block:
```python
    # Scale.
    if isinstance(total_norm, torch.Tensor) and total_norm.dtype == torch.float64:
        # ``max_norm / tensor`` is ``tensor.reciprocal() * max_norm`` (two roundings); a
        # tensor/tensor division rounds once, like the Python-float expression.
        clip_coeff = torch.full_like(total_norm, max_norm) / (total_norm + 1.0e-6)
    else:
        clip_coeff = max_norm / (total_norm + 1.0e-6)
```
The invariant to restore: the float64 coefficient equals `RN(max_norm / (float(total_norm) + 1e-6))` before the single fp32 rounding.

- The divisor is a CUDA tensor, not a CPU scalar, so PyTorch's `a * (1/b)` shortcut does not apply.
- `full_like` is a device fill, so the code stays graph-capturable.

**Preservation.**
- Keep the fp32 tensor branch exactly as it is (`max_norm / fp32_tensor`). Single-optimizer and shared-group runs use it, and their golden values depend on it.
- Keep the Python-float branch (`elif clip_coeff < 1.0`) unchanged. `MimoOptimizer` reaches it.
- For power-of-two `max_norm`, (b) gives the same result as the current code.

**Acceptance.**
- Keep `test_float64_device_norm_clips_like_the_python_float_path[1.0, 0.5]` passing.
- Static check: in the float64 branch, the coefficient comes from a tensor/tensor division.
- Proposed test (from reading the source, not run): for about 1000 random float64 CUDA norms `t`, check `(torch.full_like(t, 0.3) / (t + 1e-6)).item() == 0.3 / (t.item() + 1e-6)` holds for every `t`. With `0.3 / (t + 1e-6)` I expect some values to mismatch.
- Adding `0.3` to the existing grad-level parametrization alone would almost always pass either way, so it would not distinguish the two versions.
