# Cache prompt log probabilities with prefix blocks

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7063) · state: closed · merged: False

## Original PR description

## What does this PR do?

**October 20 main refresh:** head `7aa55309ae7f754352fbba3d4d307892e216f0c1`, parent `474b1e9ee72fbe19205a6dfe26d56620977a6275`, pinned NVIDIA main `474b1e9ee72fbe19205a6dfe26d56620977a6275`. Existing branches and dependencies are preserved. Prompt-score sidecars are filled before main’s early request cleanup; public completion still follows bookkeeping. Async staging and offloaded results use the same completed score data.

This PR lets prefix caching reuse prompt log probabilities when the prompt and score settings match, and preserves original-prompt scores across cache-disabled recompute checkpoints.

- It stores selected prompt scores and requested top-N scores in compact, mutable sidecars on canonical KV blocks.
- It reuses scores only when every setting that can affect them matches.
- It fills missing rows without replacing valid cached rows during hybrid-model replay.
- It carries chunk-boundary scores on the request until the continuation is admitted.
- It reconstructs complete prompt-score results for completion and streaming without private KV copies or a fallback scheduler.
- It keeps canonical and deprecated prompt-score controls synchronized when a sidecar-backed request is checkpointed for recomputation.
- It promotes the first complete cache-disabled prompt-score recomputation back to the original record segment before merging or coordinator streaming.
- It supports GPT and hybrid models under legacy and asynchronous scheduling.

## Example failure scenario(s)

**Scenario 1 (matching scores)**

- Request A has 513 prompt tokens and asks for top-5 scores.
- Request A caches 2 full blocks and their reusable prompt scores.
- Request B repeats the 513 tokens with the same settings.
- Request B reuses the canonical blocks and stored scores while computing only the required tail.
- Request B returns the same complete result as cache-disabled inference.

**Scenario 2 (different settings)**

- Request A caches top-5 scores for a 513-token prompt.
- Request B repeats the prompt but asks for top-4 scores.
- The exact sidecar key rejects Request A's top-5 values.
- Request B recomputes top-4 scores on the canonical KV blocks.
- Request B returns correct rows without receiving false cache-hit credit.

**Scenario 3 (chunk boundary)**

- Request A has 513 prompt tokens and reaches a prompt-chunk boundary.
- The first chunk produces the score for the next prompt token.
- Request A carries that score until its continuation is admitted.
- The next chunk attaches it to the correct sidecar row.
- Legacy and asynchronous scheduling return the same complete score sequence.

**Scenario 4 (hybrid replay)**

- Request A caches top-5 scores for 2 full prefix blocks.
- Request B restores recurrent state after the first block.
- Request B replays the second block to continue the prompt.
- Replay preserves valid cached rows and fills only missing rows.
- Request B matches the cache-disabled result.

**Scenario 5 (memory pressure)**

- Request A leaves 2 matching canonical prefix blocks pinned.
- Only 1 KV block remains allocatable.
- Request B repeats the prompt and needs 1 tail block.
- Request B reuses the 2 pinned blocks and finishes.
- No shadow blocks or fallback scheduling path are needed.

**Scenario 6 (checkpointed top-N scores)**

- Request A reuses 511 of its 513 prompt tokens and asks for top-5 scores.
- The engine checkpoints Request A after its first generated token.
- The sidecars first materialize all 512 original prompt-score rows.
- The checkpoint segment skips recalculating those prompt scores.
- Request A resumes and returns the same complete scores as cache-disabled inference.

**Scenario 7 (cache-disabled recompute)**

- Request A asks for prompt and top-3 scores with prefix caching disabled.
- The async engine starts A but has not yet attached its pending prompt scores.
- The engine suspends and checkpoints A for recomputation.
- A later segment recomputes the complete prompt-score rows and restores them to the first segment.
- A returns the same complete prompt scores as legacy recompute.

## How was this bug discovered?

A cache-off versus cache-on comparison first showed that generated tokens matched while the cache-on result omitted prompt scores skipped by prefix reuse. The oracle was the complete cache-disabled token, selected-score, and top-N result.

Focused regressions then crossed exact and mismatched score settings with real chunk boundaries, concurrent variants, one-free-block pressure, allocator cleanup, GPT attention, hybrid recurrent-state restoration, and both scheduling modes. Exact hybrid comparison exposed that replay could replace already-valid cached rows with slightly different values, so valid rows are now authoritative and only missing rows are filled.

The historical HTTP sentinel regression is retained, but current main already supplies that endpoint correction.

Reconciliation with fork PR #50 added a real prefix-hit checkpoint comparison. It showed that score materialization was correct, but the checkpoint copied a stale deprecated top-N control that contradicted the new skip setting and stopped the request before resume.

Adding prompt and top-3 scores to the existing asynchronous RECOMPUTE suspend/resume pair exposed a separate cache-disabled defect. HSG job `7003965` reproduced it: legacy returned 8 prompt rows while async returned 0 because a later checkpoint segment held the complete recomputation while result publication still read the empty first segment. The fix promotes only the earliest complete zero-based recomputation and leaves prefix-offset reconstruction with #7063's position-aware sidecars.

The problem happens when the "donor" is not chunked.

`compute_and_store_offsets` decides when to save snapshots. For a 513-token unchunked donor, `kv_div_abs` doesn't match anything, and `last_aligned_abs` and `penultimate_abs` both match token 512 (end of block 1). If the donor was chunked, the chunk-end clause would save a snapshot at token 256, but that doesn't happen for unchunked.

The next request arrives with the same prompt and matches. After this PR, that request tries to get the penultimate snapshot. The penultimate snapshot doesn't exist; the request is trying to resume from an undefined `matched_block_ids[executable_blocks − 2]`. There is no check on whether that snapshot was actually made, we just try to load it regardless.

The `matched_block_ids[executable_blocks − 2]` trace is `prefix_skip_tokens = max(0, executable_blocks - 1) * self.block_size_tokens` -> `restore_block_count = prefix_skip_tokens // self.block_size_tokens` -> `matched_block_ids[restore_block_count − 1]`.
