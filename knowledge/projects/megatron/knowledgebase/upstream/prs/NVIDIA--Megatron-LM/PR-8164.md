# Synchronize ranks before re-initializing model parallel in unit tests

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Fixes the intermittent MoE unit-bucket hang in #7745 by synchronizing all ranks before `Utils.initialize_model_parallel` tears down the existing process groups.

**Cause**

`Utils.initialize_model_parallel` calls `ps.destroy_model_parallel()` without a barrier. `TestRouterAuxLoss.setup_method` initializes model parallel, and `test_force_balanced_aux_loss` (like several other tests) initializes it again in the test body. A rank that finishes creating the setup's groups early therefore destroys them while slower ranks are still inside Gloo `connectFullMesh` for the last one. Those ranks fail with `Connection closed by peer`, pytest moves them on to the next test, and the remaining ranks wait 30 minutes on Gloo store keys for a group the others never create. The NCCL watchdog timeouts, the launcher restart and the job-limit cancellation in #7745 all follow from that.

The all-rank logs of [run 37393427924](https://github.com/NVIDIA/Megatron-LM/actions/runs/37393427924/artifacts/11385665581) show the sequence. Ranks 3–5 fail in `setup_method` with `Connection closed by peer` at 00:53:27.285. By then ranks 0 and 2 have already destroyed those groups and are waiting in the test body's re-initialization; their 30-minute store waits start at 00:53:27.58.

**Fix**

Barrier on the default group (after `torch.cuda.synchronize()`) before destroying the groups, as `Utils.destroy_model_parallel` already does on teardown. The condition is `torch.distributed.is_initialized()`, which is the same on every rank, so the barrier cannot itself desynchronize ranks.

**Testing**

- Standalone reproduction: 8 Gloo processes on CPU repeatedly create an 8-rank group and immediately destroy it, with 3 ms of loopback latency to widen the window. Without a barrier, every rank fails within 18 cycles with the errors seen in CI (`connectFullMesh ... Connection closed`, `DistStoreError: wait timeout ... keys: /default_pg/0//19//cpu//0/2`). With a barrier before the destroy, all 40 cycles complete.
- `tests/unit_tests/test_parallel_state.py` and `tests/unit_tests/transformer/moe/test_aux_loss.py` on 2 GPUs with the CI software stack: identical pass/fail sets with and without the change. The failures are cases that need 4–8 ranks.
- The 8-rank cases themselves run only in the H100 MoE bucket. The failure is intermittent, so a green CI run is necessary but not sufficient evidence.
