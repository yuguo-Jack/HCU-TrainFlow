# Inference contexts: pad to the context's TP size and accept a collection

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8029) · state: open · merged: False

## Original PR description

## Why

`DynamicInferenceContext` takes its TP size from its process-group collection, but its padding called `round_up_tokens`/`round_up_requests` without one, so they used the global TP size. When the two differ (RL inference at its own TP size, or a model on its own grid), eager steps were padded to the wrong multiple: with two speculative tokens, inference TP=8 and global TP=1 or 2, three decode requests became four, i.e. 12 tokens across 8 TP ranks. The NVLS/vLLM MoE buffer sizes divided that padding by the context's TP size.

`StaticInferenceContext` could not take a collection, and `StaticInferenceEngine` built its internal dynamic context without one, so that context and its engine used the global groups even when the wrapper used a collection.

## What

- `DynamicInferenceContext` stores `tp_size` and passes it to every internal `round_up_*` call. The classmethods keep their optional `tp_size` for external callers.
- `StaticInferenceContext(..., *, pg_collection=None)` stores the collection in its config; `StaticInferenceEngine` builds its dynamic context with it.

## Tests

New `tests/unit_tests/inference/contexts/test_context_process_groups.py` uses collections whose TP size differs from the global grid and patches every global group/rank/size accessor to raise. It checks step padding, MoE buffer sizes and the static engine's groups. All 10 cases fail on main (global read; without the patch, e.g. 13 padded tokens instead of 14) and pass on 4 GPUs. Existing context, static-engine, controller and GPT parallel-engine tests match main.

## Compatibility

Additive keyword-only argument. On the standard grid the context's TP size equals the global one, so padding is unchanged.
