# test(inference): add serving and streaming coverage foundation

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8593) · state: open · merged: False

## Original PR description

## What does this PR do?

This PR adds a unit-test foundation for serving and streaming in dynamic inference. It streams real engine output through the coordinator reply path and the live client APIs, checking each partial reply against the final result and against the same request run without streaming. It changes no production code, and every test passes on unmodified `main`.

The foundation adds:

- streaming variants of the async-scheduling pairwise tests: every single-GPU scenario, the suspend/resume scenarios with a weight refit while suspended, and the distributed scenarios. They run beside the existing non-streaming tests, which are unchanged;
- five new async-pair scenarios: hybrid GDP, hybrid GDN, MXFP8 Transformer Engine, NVFP4 inference-optimized MoE, and MoE with EP2 and expert-TP2;
- real-engine streaming tests:
  - prompt KV handed off between two ranks over NCCL and NIXL;
  - image and video requests on a small LLaVA model;
  - two live clients streaming through a real coordinator, the high-level API facades, and a cancelled request beside a survivor;
  - generation-epoch control messages arriving during streaming;
- endpoint streaming tests: a client disconnect aborts every open stream, and a non-streaming completion ignores a malformed `stream_options` field;
- test infrastructure:
  - a LLaVA model option in the engine test environment, and an engine-class override;
  - configuration fields for expert TP, the MoE expert count, the FP8 recipe, the KV transport backend, the grouped-GEMM backend and the NVFP4 recipe;
  - a shared test tokenizer whose `detokenize` accepts keyword arguments and that resolves an `<image>` token.

## How was the test matrix determined?

An audit of serving coverage found that streaming was tested mainly with simple single-feature requests. Streaming was not crossed with the engine features that change how requests are scheduled, such as prefix caching, chunked prefill, CUDA graphs, MTP, hybrid models, MoE, parallel topologies and suspend/resume. The end-to-end paths that only exist with streaming also had no real-engine coverage: disaggregated KV handoff, multimodal media and live coordinator clients.

The matrix has two layers:

1. **Streaming crossed with the async-pair scenarios.** The async-scheduling suite already has one scenario per behavior-affecting feature. The new streaming variant runs each scenario with streaming on and compares the result with the legacy non-streaming run. The five added scenarios extend the suite to model, precision and topology features it did not cover.
2. **Real-engine streaming paths.** These exercise the coordinator, the client, KV handoff and multimodal media with real model steps.
3. **Endpoint streaming.** Two endpoint behaviors that already work on `main` and had no test: a client disconnect during a stream, and a malformed `stream_options` on a non-streaming completion.

This is differential coverage: each streaming run is compared with the non-streaming legacy run of the same scenario. The existing non-streaming async tests still run unchanged, so the async-scheduling coverage on `main` is not replaced.

## How are results checked?

Streaming variants first require the scenario's runtime checks, the same ones the non-streaming test uses, which show that the scenario's feature actually ran. They then check every partial reply:

- the request is still live when its partial is sent;
- each partial carries new tokens, with log probabilities and top-N entries exactly when the request asked for them;
- the streamed tokens are a prefix of the final tokens;
- partials coincide with the steps where the scenario's feature actually ran, for example a CUDA-graph replay, an MTP step or a prefix-cache hit.

The final tokens and scores must match the legacy run within each scenario's tolerance. Suspend/resume cases also require that a request was streamed across the suspend and that the weight refit happened.

The real-engine tests compare streamed output against a greedy or non-streaming baseline of the same request and check that each request ends exactly once. The coordinator test also requires that the first partial arrives while its stream is still open, that prefix caching and chunked prefill both ran on the ranks that served the requests, and that the cancelled request is aborted while its sibling finishes with the baseline tokens. The epoch test requires a partial for every request in every epoch, and boundaries stamped by the real control message.

## Scope

This PR is test-only and is based directly on `main`. It changes `test_dynamic_engine.py`, `test_dynamic_engine_async_sched.py` and `test_endpoints_common.py`, and makes no production, functional-test or configuration change. The whole serving/streaming series adds 2,230 net unit-test lines, within the user-approved 2,232.

Details:

- **Harness changes:** the existing async pairwise tests keep their non-streaming path and their MoE and tensor-parallel checks. The only exceptions are the new NVFP4 and expert-TP scenarios, whose experts do not use the NCCL token dispatcher.
- **Shared tokenizer:** it does not define `eod`, so tests that leave `termination_id` unset still run to their token limit, as on `main`.
- **KV handoff test:** it needs exactly two ranks, one prefill and one decode, so it skips at other world sizes. It therefore does not run in the standard 8-GPU or 4-GPU CI jobs; it ran here in dedicated two-rank jobs.
- **Coordinator test on several ranks:** CI launches unit tests on 8 ranks, which gives the coordinator test eight data-parallel engines. The test turns off the load term of the coordinator's routing score, so requests that share a prefix reach the same engine, and it gathers its engine-side checks from every rank after the engines stop. It runs its baseline requests by stepping the engine on its own event loop. Called from inside a running loop, the synchronous `generate()` runs each step on a helper thread that starts on CUDA device 0, which crashed every rank other than 0 with an illegal memory access. That production issue is outside this PR.
- **Narrowed RECOMPUTE refit check:** in `test_async_streaming_survives_suspend_refit_resume[recompute-suspend-resume]` the async run must match the legacy run's tokens exactly and report only finite scores, but no prompt or generated log-prob or top-n values are compared. Since NVIDIA/Megatron-LM#8426, `main` keeps the scores a recomputed request already has, which the legacy run computed before the suspend. The async run drops its pending forward at a RECOMPUTE suspend and rescores after the weight refit, which shifts its prompt scores by up to 0.21 and its generated scores by up to 0.005. Refit's lmcafee-nvidia/Megatron-LM#167 finishes that forward at suspend instead and should restore full parity; tighten this check then. Every other case stays exact.
- **Out of scope:** the production fixes found with this foundation, and the end-to-end SSE and HTTP checks that need several of them, are separate PRs: production fixes #8492, #8594, #8595, #8596, #8597, #8598, #8599, #8600, #8601, lmcafee-nvidia/Megatron-LM#125, and tests lmcafee-nvidia/Megatron-LM#126.
