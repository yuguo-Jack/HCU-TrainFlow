# Fix potential positional embedding tensor reuse for train/rollout 0-mismatch RL

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8358) · state: closed · merged: True

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

This PR fixes the potential RoPE / YaRN bug that may occur during colocated RL training/rollout with NeMo-RL + Megatron inference. In rollout, the positional embedding tensors are captured by CUDA graph and cached by Python `lru_cache`. In the transition from generation to train phase, NeMo-RL will GC and empty unused CUDA memory allocations:

https://github.com/NVIDIA-NeMo/RL/blob/f4bcf7e21db3c254c818d19df01a606b07cb05f3/nemo_rl/models/policy/workers/megatron_policy_worker.py#L4699-L4710

So the positional embedding tensors may be re-claimed and then re-allocated to tensors used in training. But their addresses are already captured and recorded in CUDA graphs for generation. This leads to potential data races in following generations steps, especially for 0-logprob train/rollout mismatch. This happens when trying to run colocated 0-mismatch RL for Qwen3.

## Validation & Results

See this [w&b link](https://forge.coreweave.com/wandb/nvidia/nemo-rl/runs/gnl4hzxr?nw=nwuserxuantengh) showing the `train/gen_kl_error` is always 0 in the 20 steps, where the initial runs with NeMo-RL detects a non-zero KL error in step 4 https://github.com/NVIDIA-NeMo/RL/pull/3208.

- tdene · COMMENTED · 2026-10-23T14:58:16Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8358#pullrequestreview-5623424931)

A quick something that doesn't have to be addressed by this PR, but can go into a follow-up instead:     
There are two other caches with the same issue: `rotary_pos_emb_cache` at `gpt_model.py` L216-228, and `_set_cos_sin_cache` at `rotary_pos_embedding.py` L277-286. They share the same failures.

But given the comments I left in-code, I want to talk about the high-level design.

In general, right now, the `_cuda_graph_cache_keys` lives on the module but since the module can be called by multiple different CUDA graphs, there is no way to tell when it's safe to modify `_cuda_graph_cache_keys`. As an alternative, we could have this type of pin live inside `_CudagraphGlobalRecord` itself, with a new `register_capture_constant` entry point, using the graph's own `is_graph_capturing` logic, and being deleted by `delete_cuda_graphs`. This what makes the most sense in terms of caching.

Honestly, an alternate design though is to just get rid of the cache altogether. I don't understand why we have it at this point. When it was first introduced, we couldn't build an entire precomputed table at init. Now we can. Inference is basically already using a precomputed table by caching on `inference_context.max_sequence_length`; we should just make that official.

```
def register_capture_constant(tensor: torch.Tensor) -> None:
    """Keep a tensor's storage alive for the capture currently managed by MCore."""
    if not torch.cuda.is_current_stream_capturing():
        return
    constants = _CudagraphGlobalRecord.active_capture_constants
    if constants is None:
        constants = _CudagraphGlobalRecord.unowned_capture_constants
        if not constants:  
            logger.warning(
                "CUDA graph captured outside capture_constants(); cached positional "
                "embeddings it reads are retained for the process lifetime."
            )
    constants[id(tensor)] = tensor
```
