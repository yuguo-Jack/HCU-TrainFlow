# [Fix] Fix offline dataset cache preparation for phase-specific runs.

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/5740) · state: open · merged: False

## Original PR description

## Summary

This PR fixes several issues in `tools/prepare_cache.py` that prevented offline dataset cache generation from working for large phased training runs.

The changes allow cache preparation to run without full model-training arguments, handle `eval_iters=0` without requiring an eval interval, and add support for generating cache only for the current phase via `--prepare-cache-start-iteration`.

## Motivation

`tools/prepare_cache.py` previously reused parts of the training argument and sample-count logic that assume a real training launch. This caused failures during offline cache preparation, including:

- argparse help formatting failures when help strings contain literal `%`
- `validate_args()` assertions for model execution arguments such as `micro_batch_size`
- sample-count calculation failures when `eval_interval` is unset and `eval_iters=0`
- inability to generate cache for a later phase such as `[xxx, xxxx)`

## Changes

- Add a Megatron argparse help formatter that preserves argparse substitutions such as `%(default)s` while escaping literal `%` characters.
- Normalize prepare-cache arguments before validation:
  - require `--seq-length` or encoder sequence length
  - apply `--prepare-cache-world-size`
  - set `iteration=0` by default
  - fill minimal validation-only defaults for model arguments that are unused by offline cache construction
- Add `--prepare-cache-start-iteration` to select the active phase when `--phase-transition-iterations` is provided.
- Replace the training sample-count helper with a prepare-cache-specific implementation that:
  - supports `eval_iters=0`
  - supports missing `eval_interval` when no eval samples are needed
  - computes phase-local train samples based on the current iteration
- Add unit coverage for prepare-cache normalization, sample-count behavior, phase selection, and literal `%` help formatting.

## Example

For generating cache for phase `[xxx, xxxx)`:

```bash
python tools/prepare_cache.py \
  --data-args-path xxxx.txt \
  --split xx,x,x \
  --data-cache-path xxxx \
  --global-batch-size xxxx \
  --train-iters xxxx \
  --phase-transition-iterations "xxxx" \
  --prepare-cache-start-iteration xxxx \
  --eval-iters 0 \
  --eval-interval 1 \
  --seq-length 4096 \
  --tokenizer-type HuggingFaceTokenizer \
  --tokenizer-model xxxx \
  --prepare-cache-world-size xxxx

## Strict Review Summary

**Findings by severity:** CRITICAL: 0 · IMPORTANT: 0 · SUGGESTION: 1

### Assessment

This is a focused, low-risk fix for offline dataset cache preparation. I traced the three behavioral changes against their counterparts in the training path:

- **`_MegatronHelpFormatter` / `_escape_literal_help_percent_characters`** — correctly preserves argparse substitutions (`%(default)s`, `%(prog)s`) while escaping bare literal `%`, mirroring argparse's own `_expand_help` param preparation (SUPPRESS removal, `__name__` mapping, `choices` join). The literal-percent unit test covers the relevant cases, and applying it only to the local parser keeps blast radius minimal.
- **`_get_prepare_cache_num_samples`** — faithful reimplementation of `get_train_valid_test_num_samples()` with two deliberate, safe relaxations for offline use: it tolerates `eval_iters=0` and a missing `eval_interval` (returning 0 eval samples), and guards `total_train_samples` against `train_samples=None` (the original appends raw `args.train_samples` into the phase list, which would break here). Phase-local sample math matches the training path.
- **`_normalize_prepare_cache_args`** — the minimal model-arg defaults (`micro_batch_size`, `num_layers`, `hidden_size`, etc.) exist only to satisfy `validate_args()` and are genuinely unused by dataset construction; the comment documents this. All new args have real read paths (verified via grep).

New identifiers all have meaningful uses; no unused-variable or process-group concerns (this is training-tool code, not `megatron/core`). Backward compatibility is preserved — the training-path helper is untouched and its own test still imports it.

### Most impactful finding

The single SUGGESTION notes that `--prepare-cache-start-iteration` makes `args.iteration` user-controllable, so an out-of-range value can reach the `min(...)` over phase-transition samples with an empty sequence and raise an opaque `ValueError`. Worth an up-front bounds check, but not blocking.

**Risk level: Low.** Well-tested, isolated to `tools/prepare_cache.py` plus an additive local help formatter.

- claude[bot] · comment · 2026-07-10T08:36:41Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/5740#discussion_r3557506540)

File: `tools/prepare_cache.py` · line 175

**[SUGGESTION Correctness]** With the newly added `--prepare-cache-start-iteration`, `args.iteration` is now directly user-controllable. If a user passes a start iteration at or beyond the end of the run (so `current_sample >= total_train_samples`), the generator `(sample for sample in phase_transition_samples if sample > current_sample)` becomes empty and `min(...)` raises the cryptic `ValueError: min() arg is an empty sequence`.

The training-path `get_train_valid_test_num_samples()` has the same latent expression, but there `iteration` is bounded by the resume checkpoint rather than arbitrary CLI input, so this failure mode is newly reachable here.

(1) *Issue*: bad/edge `--prepare-cache-start-iteration` values crash with an opaque error. (2) *Impact*: confusing failure for the exact phase-selection feature this PR introduces. (3) *Suggestion*: validate the start iteration up-front (e.g. in `_normalize_prepare_cache_args`, after `train_iters` is known, assert `iteration < train_iters`) or guard the `min(...)` here with a clear message like "no phase begins after iteration N — start iteration exceeds train_iters".
