# Run the Mamba training path batch-first to shrink its layout copies

# What does this PR do?
Runs `MambaMixer`'s memory-efficient training path batch-first, so its two sequence↔batch layout copies move the `d_model`-wide hidden state instead of the much wider in_proj and SSM outputs.

## Why
The Mamba SSM kernel is batch-first, so `_ssm_training` transposes the in_proj output (`l b d → b l d`) and the SSM output (`b l d → l b d`), each with a `.contiguous()` copy, forward and backward. Those tensors are wide: in Nemotron 3.5 Lightning the in_proj output is 10,304 wide and the SSM output 4,096, against a 2,688-wide hidden state.

## Change
When `use_mem_eff_path` is on, outside inference, with `cp_size == 1` and no sequence parallelism, `_mamba_chunk` transposes the input before `in_proj`, `_ssm_training` skips both rearranges, and a new `_out_proj` helper transposes the `out_proj` output back to `[s, b, h]`. Both `forward()` and the two-stage path (`forward_pre_attn_and_core_attn` / `forward_post_core_attn`, used by `MambaLayer` and `WideResidualMambaLayer`) go through it. The intermediate SSM output passed between the two stages is opaque to both callers. Context and sequence parallelism communicate along the sequence dimension, and inference keeps its own layout, so those paths are unchanged.

## Testing
- New `test_batch_first_ssm_matches_sequence_first` (plain `forward` and the two-stage path): runs forward and backward through both layouts on the same input, in fp32 with TF32 off, over two SSM chunks with a batch size distinct from the other dims.
  - Outputs and input gradients are bitwise identical.
  - Weight and norm gradients reduce over tokens in a different order, so they differ by ~1e-6 of their max (fp32 summation order). The test bounds them at 1e-5 × max.
  - Conv and SSM-parameter gradients differ only by the atomics noise the sequence-first path already has run to run.
- On one B200 (`nvcr.io/nvidia/nemo:26.08.01`, Megatron-LM 3914483fd), `test_mamba_mixer.py`, `test_mamba_layer.py` and `test_mamba_train_gen_parity.py` with `MAMBA_DETERMINISTIC=1`: 23 passed with this change vs 21 without (the 2 new cases). The only failures, on both, are the 3 `TestMambaMixerErrorChecks` cases that need TP 2/4 on a 1-GPU run.
- `black` 26.3.0, `isort` 5.13.2 and `ruff` 0.9 pass on the changed files (run individually, not via `tools/autoformat.sh`).
