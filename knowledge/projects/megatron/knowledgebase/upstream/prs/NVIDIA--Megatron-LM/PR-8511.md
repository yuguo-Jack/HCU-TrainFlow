# test(inference): add CUDA graph replay coverage foundation

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8511) · state: open · merged: False

## Original PR description

## What does this PR do?

This test-only PR adds coverage for dynamic inference with CUDA graphs. It runs real inference engines with graphs captured and replayed, and compares each run with eager execution of the same requests. It passes on unmodified `main`; production fixes that the coverage exposed come in separate PRs that build on it.

The foundation adds:

- 36 single-GPU graph-versus-eager comparisons across major inference features, delayed-scaling FP8, and graph lifecycle events;
- 3 multi-GPU graph-versus-eager comparisons covering tensor, sequence and expert parallelism;
- 9 new eager async-versus-legacy cases, including the MXFP8 MoE and expert-tensor-parallel all-gather paths;
- a Blackwell kernel test that replays the MXFP8 top-2 fused MoE in a CUDA graph and compares it with eager execution;
- replay tracing in the existing GDP and prefix-caching CUDA graph tests, so they prove an actual graph replay at the expected padded shape, and that eager runs replay nothing;
- test-harness support for the configurations above (expert and expert-tensor parallel sizes, MoE expert count and grouped GEMM, FP8 recipe, graph warmup steps, deferred graph creation, and a VLM model);

Every case that exists on `main` keeps its exact definition. Where a graph comparison needs different settings or extra checks, it is a new named case built from main's case, so main's own case is unchanged.

## How was the test matrix determined?

An audit found that existing CUDA graph inference tests mostly checked that graphs were built or that a configuration flag was set. They did not show that a step actually replayed a captured graph, or that replayed output matched eager output, for each inference feature.

The matrix has two layers:

1. **Feature differential.** Each selected feature runs twice on identical requests: once with graph replay switched off, and once with graphs on, using deferred capture and real replay. The features are the ones whose code paths change under graph capture: prefix caching, chunked prefill, graph size ladders, sampling filters, log-probability outputs, stop and termination handling, MTP, VLM input, disaggregated decode hand-off, hybrid Mamba/GDN/GDP models, Transformer Engine and inference-optimized layers, fused RoPE, FlashAttention 3 and 4, and sliding-window attention with sinks.
2. **Graph lifecycle.** Static-pointer suspend/resume and weight refit, with graphs kept across the event.

This is differential coverage, not a full cross-product of inference flags. The graphs-off run is the reference for its graphs-on twin, so graphs-off cells are not repeated separately.

Six graph comparisons are new cases built from a case on `main`:

| New case | Built from | Difference |
| --- | --- | --- |
| `graph-decode-block-warmup-one` | `graph-decode-block-exponential` | one graph warmup step, FlashAttention 2, and last-token logits checked |
| `graph-mixed-layer-all-prefill` | `graph-mixed-layer-linear` | also requires a replayed all-prefill step |
| `sampling-request-seeds` | `sampling-temperature-top-k` | per-request sampling seeds |
| `flashinfer-fused-rope-exact` | `flashinfer-fused-rope` | exact rather than reproducible parity |
| `moe-ep2-nccl-routing-replay` | `moe-ep2-nccl` | grouped experts and routing replay |
| `fp8-transformer-engine-delayed` | `fp8-transformer-engine` | delayed scaling, compared on a fixed generation history |

Some features need production fixes before their graph replay can pass:
- current- and block-scaling FP8 graph replay;
- MXFP8 graph replay;
- MLA latent caching;
- UVM offload;
- the expert-tensor-parallel all-gather;
- graph recapture at TP2, PP2, sequence parallel and DP2 after graphs are deleted.

Those graph cases are added by the PRs carrying those fixes. Rebuilding graphs after a non-static OFFLOAD or RECOMPUTE suspend while requests are still running is outside this series.

## How are results checked?

A graphs-on run only counts if graphs actually ran:
- captured graph runners replay during the steps under test;
- the executed padded shapes are shapes that were captured;
- feature-specific runtime evidence appears on those steps, for example fused-RoPE kernel calls, the requested FlashAttention version, sink-correction calls, MTP inner layers, VLM image tokens, and hybrid mixer replays.

Lifecycle cases also check:
- static-pointer suspend/resume keeps the same graph runners and graph objects (the graph-resource-lifecycle PR adds the shared memory pool to this check);
- weight refit changes a parameter;
- replay continues afterwards.

FlashInfer sampling cases also check every sampled token against the top-k and top-p filters. The check compares values, as FlashInfer does, so a token tied with the k-th largest logit counts as kept.

Output checks:
- **Exact cases:** generated tokens must be identical. Prompt and generated log-probabilities must match within an absolute tolerance of 1e-3, or 5e-3 for the VLM and hybrid cases. Top-n log-probabilities must match as well, except in two cases where a near-tie can swap the last entry. Those two cases run the graph mode a second time, and that run must reproduce the first run's top-n entries within the same tolerance.
- **Sampled cases and the optimized TP2 case:** each mode runs twice and must reproduce itself exactly, with finite log-probabilities. The graph-resource-lifecycle PR's TP2/PP2/DP2 graph comparison uses the same check.
- **Delayed-scaling FP8:** the graph run is fed the eager run's tokens. At every generated position, the logits and the last KV-cache row must equal the eager run's exactly, and a repeated graph run must match too. The same fixed-history comparison is used by the FP8 and MXFP8 graph cases that later PRs add.

Main's existing cases keep their definitions and output tolerances, including the top-n tolerance of 0.1, and the shared harness gives them stronger runtime checks as well. New FP8 cases round eager token counts to the recipe's alignment, while main's own FP8 case keeps main's rounding; the setting is restored after every test.

## Scope

This PR changes only unit tests and test utilities. It has no Megatron Core production changes, and no functional tests, configurations, runners, prompts, recipes or goldens.

The nine CUDA graph fixes, each with its own regression, are separate PRs based on this one:

- FP8 capture alignment (lmcafee-nvidia/Megatron-LM#114);
- OFFLOAD with unified memory (lmcafee-nvidia/Megatron-LM#115);
- padded all-gather MoE dispatch (lmcafee-nvidia/Megatron-LM#117);
- the MoE layer cache owner (lmcafee-nvidia/Megatron-LM#118);
- non-fused MLA absorption (lmcafee-nvidia/Megatron-LM#119);
- graph buffer release and shared-pool recreation (lmcafee-nvidia/Megatron-LM#144);
- each module's FP8 recipe at replay (lmcafee-nvidia/Megatron-LM#145);
- local attention key and value widths (lmcafee-nvidia/Megatron-LM#146);
- the top-k axis in the inference router (lmcafee-nvidia/Megatron-LM#147).

Cases that need two of these fixes are in the tests PR, lmcafee-nvidia/Megatron-LM#148.

The full CUDA graphs series adds 2,094 net unit-test lines, within the approved 2,249.

[P2] Retain repeat top-N checks when cross-mode equality is waived

For `raw-prompt-top-n-logprobs` and `mtp-graph-heterogeneous-logprobs`, `graph_parity` is `"exact"`, `eager_logits` is empty, and `scenario.exact_top_n` is false. The [first comparison](https://github.com/NVIDIA/Megatron-LM/blob/9091f84eacbe3088a6fd14047c2a4008f7997751/tests/unit_tests/inference/engines/test_dynamic_engine_async_sched.py#L3212-L3218) therefore checks top-N cardinality and finiteness but not identities or values, and this condition skips the repeat entirely. Unstable non-selected top-N entries can pass while generated tokens and selected-token log-probabilities remain correct. The [existing pair oracle](https://github.com/NVIDIA/Megatron-LM/blob/9091f84eacbe3088a6fd14047c2a4008f7997751/tests/unit_tests/inference/engines/test_dynamic_engine_async_sched.py#L3041-L3058) retains a same-mode repeat for this exception.

Extend the condition so these cases also enter the existing repeat branch:

```suggestion
            if graph_parity != "exact" or eager_logits or not scenario.exact_top_n:
```

That branch already compares against `graph_expected` with top-N identities and values checked at the scenario's tolerance. This preserves permitted near-tied final-slot differences between eager and graph execution while checking reproducibility between identical graph runs. Sampled and fixed-history FP8 cases retain their current repeat behavior; cases with `exact_top_n=True` retain direct eager-versus-graph checks.

Proposed acceptance checks, not executed: confirm both named scenarios perform a second graph run. Changing only a non-selected top-N token key, or a value beyond `scenario.atol`, in that repeat must fail. Identical graph repeats must pass even when their final near-tied top-N slot differs from eager. Verify the suggested change before adopting it.
