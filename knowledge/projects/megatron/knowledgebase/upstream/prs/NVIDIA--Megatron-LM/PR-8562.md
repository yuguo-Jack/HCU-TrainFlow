# [Inference][MoE] Return dense [num_tokens, topk] routing from InferenceTopKRouter with router fusion and top-1

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8562) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes `InferenceTopKRouter` return probs and expert IDs shaped `[num_tokens, topk]` in every configuration. Before this PR, router fusion and top-1 routing broke that shape. The contract is now enforced where the routing is produced.

**Bugs.** The inference MoE dispatchers and expert backends (vLLM, torch, FlashInfer) use the router output directly as fp32 `[num_tokens, topk]` probs and integer `[num_tokens, topk]` expert IDs. No shape check sits between them.

- **`moe_router_fusion=True` (for example, a training config reused for serving).** `InferenceTopKRouter._forward` requests `dense_output=True`. But the fused branch of `topk_routing_with_score_function` returned TE's result before reaching `dense_output`, so the router returned full-width `[num_tokens, num_experts]` probs and a bool map. The expert kernels read the bool map as expert IDs 0/1. Every token then went to expert 1 with weight `sum(p)`, plus zero-weight work on expert 0. Measured on H100 (TE 2.20), compiled and batch-invariant router paths:
  - EP=1: silently wrong output, relative error 1.67 against a plain-torch MoE.
  - EP=2 with the NVLS dispatcher: an all-gather-v assertion.
  - EP=2 with the NCCL dispatcher: `illegal memory access` / device-side asserts.
- **`moe_router_topk=1`.** The router ended with `probs.squeeze(1), top_indices.squeeze(1)`. With one expert per token that removes the top-k dimension. Both inference expert backends then raised `IndexError` on `routing_map.shape[1]`, so `transformer_impl=inference_optimized` could not serve top-1 MoE models.

The training `TopKRouter` was not affected by either bug. It sets up the fused dense path itself, passing TE a `topk_indices` buffer.

**Fix.** The rule in `topk_routing_with_score_function`: the routing features and TE's capability choose the implementation; the output format the caller asked for is always kept.
- The fused path honours `dense_output`. TE writes the selected expert IDs into a `[num_tokens, topk]` `topk_indices` buffer (passed by the caller, or an int64 one allocated here), and the full-width probs are gathered at those IDs with int64 indices, so int16/int32 caller buffers also work. With dense output, TE no longer builds the `[num_tokens, num_experts]` bool map.
- The unfused path is used when:
  - the installed TE cannot write dense indices and dense output was requested (the rule `TopKRouter.routing` already applies);
  - `router_replay` is set. Router replay records or overrides the top-k selection, which TE's fused kernel makes internally. Before this PR, fused routing silently skipped record and replay, in training and inference alike.

  The unfused path now also fills a caller's `topk_indices` buffer, so callers that pass one (TopKRouter's flex and MoonEP routes) get the same output either way. Requesting fusion when TE has no fused router still raises.
- `InferenceTopKRouter._forward` flattens the logits with `view(-1, num_experts)`, as the hash path does, so `[seq, batch > 1, hidden]` input also works. It returns the routing result without squeezing it.
- `InferenceTopKRouter` warns once when `moe_router_fusion` is set but TE cannot write dense indices, so the unfused fallback is not silent.
- The NVLS dispatcher's all-gather-v (`multimem_all_gatherv_3tensor`) moved only 8- or 16-byte-aligned rows. The fp32 probs of an odd top-k have 4-byte-aligned rows, so top-1 crashed there with "not 8-byte aligned; cannot use NVLS". The collective now selects a 32-bit multimem path for 4-byte-aligned rows (the existing `ld_32`/`st_32` helpers), so the dispatcher needs no padding or copies.

So the contract holds, and the inference dispatchers and experts consume it, for every configuration: fused or not, any top-k, compiled or batch-invariant, any `[seq, batch]` layout, NCCL or NVLS dispatcher, and with router replay, hash routing or quantile balancing. Hash and quantile-balancing routing were already dense. Sparse callers are unchanged. The change adds no host syncs. The fused path adds one small gather and drops TE's bool-map output.

## Follow-up: sinkhorn routing

Review finding: `InferenceTopKRouter` ignored `moe_router_load_balancing_type='sinkhorn'`.

- **Bug.** In eval mode, `TopKRouter` routes sinkhorn by the sinkhorn activation of the logits: `sigmoid` for top-1, the full softmax over all experts for top-k > 1. It selects the top-k experts of that activation and weights them by it, without renormalization, `moe_router_topk_scaling_factor` or expert bias, whatever `moe_router_score_function` is. `InferenceTopKRouter._forward` never read the routing type and always called `topk_routing_with_score_function`. Under `InferenceMode` it therefore selected the same experts with different weights:
  - top-1 got 1.0 (times the scaling factor) instead of `sigmoid(z)`. On `main`, top-1 inference routing crashes first (d9); with this PR's top-1 fix it would be silently wrong.
  - top-k >= 2 got renormalized or sigmoid weights. On H100 the probabilities differed from eval routing by up to 0.4.

  Config validation accepts sinkhorn for `inference_optimized`, and even exempts top-1 sinkhorn from the pre-softmax requirement.
- **Fix.** The sinkhorn activation becomes a `TopKRouter` method, `_sinkhorn_activation`, shared by `sinkhorn_load_balancing` and `InferenceTopKRouter`. For sinkhorn, the inference router returns the dense top-k of that activation: fp32 probs and int64 expert IDs. These are the eval routing's experts and probabilities. The sinkhorn normalization only balances selection in training and is not used in inference. The training path is unchanged. The fix adds no host sync and is CUDA-graph safe.
- **Score function.** `InferenceTopKRouter.__init__` no longer requires a sigmoid or softmax score function for sinkhorn routing, which ignores it. A sinkhorn model with `moe_router_score_function='sqrtsoftplus'` and no hash layers routes in eval-mode `TopKRouter`, and now also constructs and routes in inference (before, it failed the constructor assertion).

Tests:

- `test_moe_dispatching_and_routing.py::TestInferenceTopKRouter::test_sinkhorn_routing_matches_eval_routing` (1 GPU). It covers top-1, and top-2 with softmax, sigmoid, pre-softmax and `sqrtsoftplus` score functions, with the base config's top-k scaling factor of 2.5. The sinkhorn branch returns before the choice between the compiled and the batch-invariant routing, so one path serves both modes and the test does not parametrize them. The inference routing must select the eval-mode `TopKRouter`'s experts, with bit-identical probabilities, which also equal `sigmoid` / `softmax` of the logits. Without this commit, all cases fail.
- `test_moe_kernels.py::TestMoEModules::test_inference_topk_router_sinkhorn_replays` (top-1 and top-4) replays the inference router's sinkhorn routing under `InferenceMode`. `tools/check_kernel_determinism_coverage.py --base-ref origin/main` passes.

On a local GPU, the router was smoke-checked on the eager path (not evidence). Without the commit, the probabilities differ by 0.27 to 1.99. With it, they are identical to eval routing. The H100 results are at the end of the next section.

## Follow-up: the expert-parallel test against current `main`

- **`main` merged** ("Merge main into fix/d4-d9-inference-router-shape"; no conflicts). #4743 renamed `NVLSAllGatherVDispatcher.allocate_buffers(ep_group=...)` to `tp_ep_group=` when the NVLS all-gather-v gained expert tensor parallelism. `TestInferenceRoutingExpertParallel::test_moe_layer_matches_training` now uses the new name. Against today's `main`, its 8 NVLS cases had raised `TypeError` on 2×H100.
- **Fails by assertion on `main`.** On `main`, the full-width (router fusion) or squeezed (top-1) routing reached torch `grouped_mm`. Its device-side assert aborted the process before any result was written, so the 2-GPU run reported no tests. Before running the layer, the test now checks the router's dense `[num_tokens, topk]` int64 output. On `main` the fused and top-1 cases fail there by assertion; the unfused top-2 cases are controls.

On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), at this PR's head, the regression tests pass: 101 cases on 1 GPU, including the sinkhorn tests, and the 16 cases of `TestInferenceRoutingExpertParallel` on 2 GPUs. On `main`, 73 of the 101 1-GPU cases fail. On 2 GPUs, `main` no longer aborts: the 12 fused and top-1 cases fail on the router output shape check, and the 4 unfused top-2 controls pass. The neighbor tests pass: `TestNVLSAllGatherVDispatcher` at EP=2 (31 cases, 9 skipped), `test_routers.py::TestAuxLossFreeTop2Router` on 8 GPUs (13 cases), and the rest of `test_routers.py` on 1 GPU (150 cases, 18 skipped).
