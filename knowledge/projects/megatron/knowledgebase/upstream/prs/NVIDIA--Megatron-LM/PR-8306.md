# What does this PR do?

Reduce kernel launches in ordinary (non-batch-invariant) NVLS MoE inference by writing the BF16 combine output directly from the FP32 reduce-scatter and, when eligible, adding the overlapped shared-expert output inside it.

The implementation preserves the original two-step rounding: convert the FP32 reduction result to BF16, then perform the BF16 addition. The output is bitwise identical to the previous reduce-scatter → `.to(bfloat16)` → `+ shared_expert_output` sequence.

This PR extracts the ordinary NVLS changes from [#8114](https://github.com/NVIDIA/Megatron-LM/pull/8114):

- Write BF16 outputs directly from the FP32 reduce-scatter
- Fuse the shared-expert addition when the shared-expert output is BF16, contiguous, 8-byte aligned and sized like the output. The combine then waits for the overlapped shared expert before the reduce-scatter rather than after it
- Preserve the existing computation steps for both ordered and multimem batch-invariant paths

The fused shared-expert addition applies to models without MoE latent projections (Nano). Super and Ultra add the shared expert after the latent back-projection, so only the BF16 conversion fusion applies to them.

Following review, the routing-padding mask fusion into the all-gather was removed: `multimem_all_gatherv_3tensor` and `token_dispatch` are unchanged from main.

Router kernels, NCCL dispatch, expert GEMM/alignment/sum kernels and TP reductions are outside this PR.

## Performance

End-to-end batch generation speedup of tst main `2d7ea246f`, with the 95% interval in brackets.

Shared-expert overlap on (`--moe-shared-expert-overlap`):

| Model | BS16 speedup | BS32 speedup |
|---|---:|---:|
| Nano | **1.022x** [1.015, 1.030] | **1.016x** [1.003, 1.028] |
| Super | 1.012x [0.989, 1.036] | 0.998x [0.980, 1.016] |
| Ultra | **1.008x** [1.004, 1.013] | **1.008x** [1.003, 1.014] |

Shared-expert overlap off:

| Model | BS16 speedup | BS32 speedup |
|---|---:|---:|
| Nano | 1.009x [0.984, 1.034] | 1.009x [0.993, 1.026] |
| Super | 1.004x [0.977, 1.032] | 0.997x [0.968, 1.026] |
| Ultra | 1.004x [0.994, 1.014] | 1.003x [0.998, 1.008] |

Bold cells are measured speedups (95% interval above 1): Nano and Ultra with shared-expert overlap. Super shows no measurable end-to-end change, and neither does any model with overlap off, where only the BF16 conversion fusion applies; their intervals include 1, and the two Super BS32 point estimates below 1 are within that noise. The median decode-step GPU time was lower with this PR in all 12 cells (0.3–2.6%), but outside the bold cells that difference is smaller than the allocation-to-allocation variation.

Measurement setup:

- Two nodes, 8 NVIDIA GB300 GPUs, TP8 / EP8 / ETP1; official BF16 checkpoints converted to Megatron Core, FP32 router, FA4, decode CUDA Graphs, NVLS dispatcher; batch-invariant mode and prefix caching disabled; shared-expert overlap off or on as labeled
- 16 or 32 requests with 32–33 prompt tokens and exactly 128 greedy output tokens each
- Three independent allocations per model. Each runs four fresh processes per batch size (baseline → candidate → candidate → baseline at BS16, reversed at BS32) with five timed generations per process
- Speedup = baseline / candidate latency, using the mean of the two per-process medians; the table shows the geometric mean of the three allocation ratios and a 95% t interval on the log ratios. All samples are retained
- Triton autotune selection is pinned for both versions (`--triton-autotune-mode pinned`), so fresh processes generate comparable tokens. Greedy output tokens were identical between main and this PR in all 36 model / batch / allocation comparisons
- Timing starts after request enqueue and ends when all requests finish (prefill and decode). Model loading, warmup and tokenization are excluded

- Waterpine · comment · 2026-11-03T01:11:10Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8306#discussion_r4449707897)

File: `megatron/core/transformer/moe/token_dispatcher_inference.py` · line 731

Good point. Each rank's RSV now waits for its own shared expert, so a late shared expert also delays its EP peers in the RSV barrier.

It can't form a cycle, though. Every rank launches its shared expert right after routing, before entering the AGV (`launch_shared_expert`). Once any rank reaches the RSV, the AGV has completed on all ranks, so every peer has already launched its shared expert and the shared expert's TP collectives can finish. A side effect is that a rank's RSV never spins at the same time as its own shared expert's TP collectives, the same kind of overlap behind the hang described in `launch_shared_expert`.

On the critical path for small decode batches: in GB300 EP4 profiles, the fused add was neutral at BS 8 and about 1% faster at BS 32/128 than adding after the RSV. End to end, Nano with shared-expert overlap, where the fused add applies, is 1.022x / 1.016x vs main at BS16 / BS32 (table in the description).

I added a comment at the wait describing this dependency.
