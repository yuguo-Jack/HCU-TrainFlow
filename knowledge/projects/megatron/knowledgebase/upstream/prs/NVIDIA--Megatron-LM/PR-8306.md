# What does this PR do?

Reduce kernel launches in ordinary NVLS MoE inference by fusing routing-padding masking into all-gather and BF16 conversion into reduce-scatter

When eligible, reduce-scatter also adds the overlapped shared-expert output. The implementation preserves the original two-step rounding: convert the FP32 reduction result to BF16, then perform the BF16 addition

This PR extracts the ordinary NVLS changes from [#8114](https://github.com/NVIDIA/Megatron-LM/pull/8114):

- Fuse routing-padding masking into the existing all-gather
- Write BF16 outputs directly from the FP32 reduce-scatter
- Fuse the shared-expert addition when dtype, layout (contiguous and 8-byte aligned) and autograd conditions allow it. The combine then waits for the overlapped shared expert before the reduce-scatter rather than after it
- Preserve the existing computation steps for both ordered and multimem batch-invariant paths.

The fused shared-expert addition applies to models without MoE latent projections (Nano). Super and Ultra add the shared expert after the latent back-projection, so only the masking and BF16 conversion fusions apply to them.

Router kernels, NCCL dispatch, expert GEMM/alignment/sum kernels and TP reductions are outside this PR. This change does not depend on the fused-router PR [#8296](https://github.com/NVIDIA/Megatron-LM/pull/8296).

### Correctness

Full-logit validation covered Nano, Super and Ultra on two nodes with four GB300 GPUs per node, using TP8/EP8/ETP1, BF16 weights, FP32 router, MAMBA_DETERMINISTIC=1 and BI disabled

All 60 tested configurations passed bitwise comparisons:
- Three models × five workloads × eager/decode CUDA graphs × shared-expert overlap off/on
- Every valid prefill, mixed and decode position, including all 131072 vocabulary entries, compared through integer views
- Input IDs, positions, generated tokens and repeated runs also matched
- A one-bit negative control verified the comparator.

Prefill and mixed steps remained eager in the decode-graph configurations. Padding rows were excluded from logit comparisons

Additional validation:
- EP4 dispatcher suite: 146 passed and five optional-backend prerequisite skips per rank
- EP8 dispatcher suite: 126 passed and five skips per rank on identical production code, followed by 40 final padding/offset cases per rank. These counts overlap
- Added determinism replay tests covering BF16 rounding ties, overflow, subnormal values and signed zero
- isort, black, ruff, compileall, determinism coverage and git diff --check passed

The optional skips require unavailable DeepGEMM BF16 or specific TE/cuBLASLt support. Literal zero-row tensors reproduce an existing Triton compilation issue on both baseline and candidate; supported padded engine cases are covered.

### Performance

End-to-end batch generation speedup against main `db3a6cd8a` (candidate `bb940739d`).

Shared-expert overlap off:

| Model | BS16 speedup | BS32 speedup |
|---|---:|---:|
| Nano | 1.021x | 1.015x |
| Super | 1.014x | 1.006x |
| Ultra | 1.004x | 1.008x |

Shared-expert overlap on (`--moe-shared-expert-overlap`):

| Model | BS16 speedup | BS32 speedup |
|---|---:|---:|
| Nano | 1.026x | 1.029x |
| Super | 1.011x | 1.019x |
| Ultra | 1.008x | 1.008x |

Measurement setup:

- Two nodes, 8 NVIDIA GB300 GPUs, TP8 / EP8 / ETP1; official BF16 checkpoints converted to Megatron Core, FP32 router, FA4, decode CUDA Graphs, NVLS dispatcher; batch-invariant mode and prefix caching disabled; shared-expert overlap off or on as labeled
- 16 or 32 requests with 32–33 prompt tokens and exactly 128 greedy output tokens each
- Three independent allocations per model. Each runs four fresh processes per batch size (baseline → candidate → candidate → baseline at BS16, reversed at BS32) with five timed generations per process
- Speedup = baseline / candidate latency, using the mean of the two per-process medians; the table shows the geometric mean of the three allocation ratios and a 95% t interval on the log ratios. All samples are retained
- Triton autotune selection is pinned for both versions (`--triton-autotune-mode pinned`), so fresh processes generate comparable tokens. Generated tokens were identical between baseline and candidate in every allocation
- Timing starts after request enqueue and ends when all requests finish (prefill and decode). Model loading, warmup and tokenization are excluded
