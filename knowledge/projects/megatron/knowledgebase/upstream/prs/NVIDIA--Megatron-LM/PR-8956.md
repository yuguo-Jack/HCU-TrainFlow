# [Inference][MXFP8] Give tiny MXFP8 groups E8M0's smallest scale and quantize strided inputs by value

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8956) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes Megatron's MXFP8 quantize kernels bit-exact with the OCP MX encoding for groups whose absolute maximum is at most 448 * 2^-127, and makes `mxfp8_quantize`, `mxfp8_quantize_into`, `mxfp8_quantize_rows`, `MXFP8Tensor.from_bf16(backend="triton")` and `MXFP8Tensor.quantize_` quantize strided inputs by value. The fused squared-ReLU and permute MXFP8 wrappers now reject strided input instead of misreading it.

**Stacked on #8564** (`fix/d8-mxfp8-rows-bound`). Both PRs change `_mxfp8_quant_swizzle_rows_kernel` and `mxfp8_quantize_rows`. #8564 adds the row bound and makes `mxfp8_quantize_rows` reject strided inputs. This PR passes the input strides through the shared row helper, so it drops that assert and updates #8564's launch test to pass the strides. Review the last two commits.

## Issue tracking

Linked issue: none; the regression tests below reproduce both bugs.

**Bug 1: tiny groups get a scale twice too large.** Per 32-element group, the scale should be the smallest power of two X >= 2^-127 (the smallest E8M0 value) with amax / X <= 448. The kernels round amax / 448 up to a power of two by adding `0x7FFFFF` to its fp32 bits and masking the exponent. When amax <= 448 * 2^-127, amax / 448 is an fp32 subnormal: any nonzero subnormal plus `0x7FFFFF` has exponent field 1. The kernels therefore wrote E8M0 byte `0x01` (2^-126) instead of `0x00` (2^-127), and the FP8 data were half the spec's values. Values that small (about 7.5e-37) barely matter numerically, but the encoding is not bit-exact against OCP MX or a round-up E8M0 conversion for those groups. Confirmed on H100 and GB200 by the MXFP8 oracle tests: all five tiny blocks got `0x01` and the neighboring blocks were exact. The same code is copied in `mxfp8_quantize.py`, the fused squared-ReLU + MXFP8 kernel (`moe/activations.py`) and the fused permute + MXFP8 kernel (`moe/permute.py`).

**Bug 2: strided inputs read the wrong elements.** `_mxfp8_quant_swizzle_row` addressed row `r` of `x` at `r * K` and never checked `x`'s layout. A transpose or a column slice passed to `mxfp8_quantize`, `mxfp8_quantize_into` or `MXFP8Tensor.from_bf16(backend="triton")` was quantized from the wrong elements without any error (1019 of 1024 scales differed for a transposed [128, 256] view). This bug is latent: no current caller passes a strided view, and `MXFP8Tensor.quantize_` makes its input contiguous first.

**Fix.**
- One Triton helper, `_mxfp8_group_scales(max_vals)` in `mxfp8_quantize.py`, now computes the E8M0 exponents and quantization multipliers for all three kernels, so the scale rule lives in one place. The fused kernels import it.
- Groups with `amax <= 448 * 2^-127` are mapped to scale 2^-127 (exponent field 0) before the bit trick. The comparison is on amax itself, which is exact. Comparing the rounded quotient would be wrong: an fp32 amax one ulp above the bound has a quotient that rounds to exactly 2^-127, but its scale must be 2^-126.
- A zero exponent field now quantizes with 2^127, the reciprocal of 2^-127; before, the multiplier was 0. All-zero groups still give byte 0 and zero data. Groups with larger amax, and the Inf and NaN cases, are unchanged.
- The two kernels in `mxfp8_quantize.py` now take `x`'s element strides. Triton specializes a unit column stride as a constant, so for contiguous inputs the sm_90 and sm_100 PTX keeps the same vectorized loads (`ld.global.v4.b32`). The only additions are the tiny-group compare and select. The fix adds no copy, host sync or allocation, so it stays CUDA-graph safe. The column offsets are int64 because a strided source can span more than 2^31 elements.
- `MXFP8Tensor.quantize_` (and `copy_`) no longer makes a contiguous copy on the Triton path; it keeps `.contiguous()` for FlashInfer only.
- `squared_relu_and_quantize_mxfp8` and `permute_and_quantize_mxfp8` had the same dense row addressing and now assert that their input is contiguous. This check is host-side and CUDA-graph safe. Their kernels consume the MoE pipeline's own dense buffers (FC1 output, `hidden_states`), and the sibling kernels in those modules (`padded_squared_relu`, `permute_tokens`, ...) make the same assumption. Generalizing that layout is outside this PR, so a strided input now fails loudly instead of being misread.
- Note: the PyTorch reference `ref_to_mxfp` in `test_mxfp8_utils.py` multiplies groups at the smallest scale by 1, which flushes their data to zero. This PR follows OCP MX (data = x / X) instead, so the tiny tests use a small exact encoder, `exact_mxfp8`.

**Test.**
- `tests/unit_tests/inference/test_mxfp8_utils.py`:
  - `TestMxfp8Quantize::test_tiny_groups_take_the_smallest_scale[bf16, fp32]`: groups at the bound, one value above it (byte 1), at 2^-127 and at the smallest subnormal. Data and swizzled scales must equal `exact_mxfp8` bit for bit.
  - `TestMxfp8Quantize::test_strided_input_is_quantized_by_value`: a transpose, a column slice and a row-step view through `mxfp8_quantize`, `mxfp8_quantize_into` and `MXFP8Tensor.from_bf16`. Each must equal the quantization of the contiguous copy.
  - `TestSquaredReluAndQuantizeMxfp8::test_tiny_groups_take_the_smallest_scale` and `TestPermuteAndQuantizeMxfp8::test_tiny_groups_take_the_smallest_scale`: the fused kernels against `exact_mxfp8`.
  - `TestSquaredReluAndQuantizeMxfp8::test_rejects_strided_input` and `TestPermuteAndQuantizeMxfp8::test_rejects_strided_input`: the fused wrappers raise on a column slice.
  - `TestMXFP8Tensor::test_triton_copy_reads_strided_source_in_place`: `copy_` hands the caller's transposed view to the Triton quantizer (no copy), and the result equals the quantization of the contiguous copy.
- `tests/unit_tests/inference/test_batch_invariant_live_rows.py`: `test_strided_input_is_quantized_by_value` replaces #8564's `test_rejects_non_contiguous_input`. The direct launch in `test_count_past_last_scale_tile_stays_in_bounds` now passes the strides.
- Determinism: `test_mxfp8_quantize_replays` also replays a strided input whose groups sit at the smallest scale, and checks it against the contiguous copy. The `inference_moe_kernels` manifest note says so. `tools/check_kernel_determinism_coverage.py` passes.
- On CPU with the Triton interpreter, the new tests pass with this PR and fail on #8564's head. The fused kernels and both `mxfp8_quantize.py` kernels compile for sm_90 and sm_100.
- On H100, the first commit's regression tests (26) pass, the neighbor tests pass, and the regression tests fail on #8564's head. The GB200 run and the GPU run of the review follow-up commit are pending.

**Merge order.** Merge after #8564. Merging into current `main` gives one conflict in `MXFP8Tensor.quantize_`: `main` added the `writeback` branch right after the line this PR changes. To resolve it, keep this PR's FlashInfer-only `.contiguous()` block, then `main`'s `if self.writeback is not None: ... elif (...)`. The write-back path quantizes with `from_bf16(backend="triton")`, which reads strides. `manifest.py` conflicts with #8566 and #8871, whose notes sentences go in the same place; keep both sentences.
