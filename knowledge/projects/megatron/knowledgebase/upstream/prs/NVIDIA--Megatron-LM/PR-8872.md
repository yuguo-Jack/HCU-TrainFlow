# What does this PR do?

Zeroes newly acquired KV pages in the bookkeeping publish ahead of the forward, with no host sync, and for every KV layout: MHA value pages and MLA latent pages.

**Why pages are zeroed.** Paged attention multiplies the masked (zero) probabilities of a request's last page by that page's unwritten rows, and 0 * NaN is NaN. #8426 therefore zeroes each newly acquired MHA value page (`_initialize_mha_value_pages`). That left two bugs.

**Bug 1: the async overlap is lost whenever a request needs a new page (performance, default config).**
- `_initialize_mha_value_pages` copied the CPU block ids to the GPU with `torch.as_tensor(..., device=cuda)`. That is a blocking copy (`cudaMemcpyAsync` + `cudaStreamSynchronize`), and its pageable int32 source rules out a real async copy anyway.
- Under the default ASYNC schedule, the overlap step calls `prepare_requests()` while forward N is still in flight. Whenever a decode row crossed a block boundary, the host waited for forward N before sampling N and launching forward N+1, so the GPU idled for that CPU time. With 256-token blocks this hits about 22% of steps at batch 64 and 63% at batch 256 (about 4x as often with MTP).
- The MTP decode allocation (`_allocate_mtp_decode_blocks`), prefill admission, resume and disaggregated-handoff continuation blocks paid the same blocking copy.
- Reproduced on H100: with `torch.cuda.set_sync_debug_mode("error")` around the overlap prepare, a step that acquires a block raises "called a synchronizing CUDA operation" from this copy; a step without a new block does not.

**Bug 2: MLA latent pages were never zeroed (silent wrong output, Blackwell).**
- `_initialize_mha_value_pages` returned early for the latent cache, although the latents hold the values.
- The pool is `torch.empty`, so a recycled or fresh latent page can hold NaN bit patterns in rows past the request's length.
- On Blackwell, FlashAttention-4 split-KV for MLA's unabsorbed (192, 128) head dims lowers its key tile to 64 tokens, the latent page size. That selects the paged TMA path, which loads whole pages, so the unwritten tail of a request's last page reaches P·V and makes the output NaN. It needs a long request (about 8K+ keys) in a step with few query tiles, for example TP >= 4 or a handful of requests, in a prefill or mixed step.
- H100 in BF16 is not affected: FlashMLA decode, FA3 and FA4 on SM90 zero-fill out-of-bound V rows for 64-token pages.
- Reproduced on GB200 with an FA4 that compiles (see Tests). In the CI image as it is, FA4 cannot compile its SM100 forward (fixed separately in "Lock FlashAttention-4 to the releases its quack-kernels and Transformer Engine can run").

**Fix.**
- Acquiring a block now only queues its id on the CPU: `_queue_kv_page_zeroing(block_ids)`, called from the same five sites as before.
- `transfer_bookkeeping_to_gpu()` zeroes the queued pages (`_zero_pending_kv_pages`). It stages the ids in a preallocated pinned buffer, copies them non-blocking into a preallocated GPU index buffer, and zeroes the pages with `index_fill_`, stream-ordered ahead of the forward that first writes them. This follows the existing deferred-Mamba-ops pattern.
- The pinned buffer is reused under the same rule as the bookkeeping buffer, and the copy runs ahead of that buffer's copy: the legacy copy blocks, and async scheduling synchronizes the bookkeeping event before it stages the next step.
- The same path zeroes MHA value pages (keys need nothing: masked scores are assigned, not multiplied) and whole MLA latent pages.
- A queued zeroing belongs to the owner that acquired the block. Deferring it opens a hazard that zeroing at acquisition did not have: a block released before the next publish (an aborted disaggregated import, say) can be handed to a later import, whose transfer writes the page outside a forward; zeroing it on the previous owner's behalf would wipe the transferred KV. The allocator therefore keeps a per-block generation, advanced on every path back to the free pool (release, REF_ZERO and LRU deregistration, LRU eviction, reset). Each queued id carries its generation, and the publish drops ids whose generation changed. The next owner queues the block again if a forward writes it; an import queues only its continuation blocks.
- A block leaves the pool once per generation and each acquisition is queued once, so the ids that survive are distinct and fit the one-slot-per-block buffers.
- The dummy block (`pool_size - 1`) is never acquired, so it is queued whenever the allocator is reset (pool allocation, engine reset, recompute resume). Padding rows, and the block-table columns past a row's last block, point at it; a kernel must not read it for a real row. Padding tokens map to it, but the fused MHA append skips their writes, so without this it would keep whatever `torch.empty` returned.

**Tests.** On H100 in the CI image (`mcore_ci_dev:main`, 2026-11-02), the H100 regression tests below pass (10 cases) and 9 of them fail on `main`. Three fail on their checks: both cases of `test_new_kv_pages_are_zeroed_for_every_layout`, and the engine test's new-block case, with "called a synchronizing CUDA operation" (its control passes). The other six fail because `main` has no `_zero_pending_kv_pages`, `_queue_kv_page_zeroing` or `KVBlockAllocator.block_generation`, which they call. The neighbor tests (`TestPrefixCachingCore`, `test_dynamic_context_mtp_kv_cache.py`, `test_suspend_resume_cycle`) pass (13, 107 and 6 cases). On GB200 in the CI image (`mcore_ci_dev:main`, aarch64, 2026-11-02), with FA4 4.0.0b37 installed in the container so that FA4 compiles on SM100 (from an earlier version of the FA4/quack lock PR, which now locks 4.0.0b29), `TestDynamicMLAUnwrittenLatentRows` passes (2 cases). On `main` its partial-last-page case fails ("unwritten latent rows reached the output") and the page-aligned control passes.
- `tests/unit_tests/inference/contexts/test_dynamic_context.py` (1 GPU, no TE or flash-attn):
  - `test_async_sched_prepare_requests_success`: now runs `prepare_requests()` and the async publish under sync debug mode "error". On `main` it fails before that, because `main` has no `_zero_pending_kv_pages`; the engine test below shows the host sync on `main`. The test then checks that the publish zeroes only the new value page.
  - `test_new_kv_pages_are_zeroed_for_every_layout[mha|mla_latents]`: on a NaN-filled pool, a prefill's two pages (one partial) are zero after the publish and the rest of the pool is untouched. On `main`, both cases fail: `mla_latents` because its new pages are not zero, `mha` because the dummy page is not zero.
  - `test_new_kv_pages_are_zeroed_for_every_layout` also checks the dummy page.
  - `test_kv_page_zeroing_is_dropped_when_its_block_is_released`: a block queued, released and re-acquired more times than the pool holds blocks, whose last owner writes it like an import, keeps its contents through the publish, while another newly queued page is zeroed.
- `tests/unit_tests/inference/test_disagg_handoff_lifecycle.py::test_released_continuation_block_keeps_a_later_imports_kv` (CPU): with the real `KVBlockAllocator`, import A's continuation block is queued, A is aborted and released, import B receives that block as its last imported block, and the publish must keep the KV the transfer wrote. It fails if the generation check is removed.
- `tests/unit_tests/inference/contexts/test_kv_block_allocator.py::test_block_generation_advances_when_a_block_returns_to_the_free_pool` (CPU): every path back to the free pool advances the generation, and a block still referenced or still cached does not.
- `tests/unit_tests/inference/engines/test_dynamic_engine_async_sched.py::TestAsyncScheduleOverlapPrepareHostSync` (1 H100, TE, flash-attn): the real engine runs every overlap prepare under sync debug mode "error". With 250-token prompts and 12 generated tokens, position 256 starts block 1; this fails on `main`. The control, 2-token prompts that stay in block 0, passes on `main`.
- `tests/unit_tests/transformer/test_multi_latent_attention.py::TestDynamicMLAUnwrittenLatentRows` (1 GB200, `launch_on_gb200`, TE, FA4): a mixed step over a NaN-filled latent pool must match a zero-filled pool. Request A has 8258 keys after its decode token, so its last page holds 2 of 64 rows. The control is a page-aligned A. The test requests FA4 split-KV explicitly (`num_splits=2`): for (192, 128) head dims over at least 64 key tiles of 128, a requested split makes FA4 (b24 to b37) lower its key tile to 64 tokens, the page size, which selects the paged TMA path that loads whole pages, whatever split count its heuristic then settles on. It asserts that the mixed step ran paged FA4. It runs on SM100/SM110 only and fails, rather than skips, when FA4 is missing. It needs the FA4/quack lock fix to compile FA4 on SM100 in CI.
- These existing tests checked a page right after allocation and now publish first: `test_dynamic_prefix_caching.py` (two tests), `test_dynamic_context_mtp_kv_cache.py::test_async_prepare_checks_draft_headroom_before_mutating_state`, `test_disagg_handoff_lifecycle.py::test_nixl_handoff_reuses_decode_cached_prefix` and `test_dynamic_engine.py::test_suspend_resume_cycle[recompute-*]`.
