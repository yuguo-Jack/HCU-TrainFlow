# Run torch_dist sync save's DCP coordination on a Gloo group (avoid per-peer NCCL P2P buffers on the coordinator)

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8445) · state: open · merged: False

## Original PR description

## What does this PR do?

`TorchDistSaveShardedStrategy.save` (the synchronous `torch_dist` save) calls `torch.distributed.checkpoint.save` without a `process_group`. As a result, DCP's coordinator exchange runs on the default NCCL group: it gathers the local plans with `gather_object`, scatters the global plan with `scatter_object_list`, and gathers the write results at the end.

NCCL implements gather and scatter with point-to-point sends. The first ones set up P2P connections, with per-channel buffers, between the coordinator and every other rank. These connections stay allocated for the lifetime of the communicator, and training never uses them otherwise. The coordinator's non-PyTorch device memory therefore grows by roughly 0.4 GiB per peer at the first save, and the memory is never released. The cost is linear in the world size. On a GB200 run with 8 ranks, rank 0 gained 2.62 GiB, from 10.94 to 13.56 GiB.

This PR passes a world-sized Gloo group to `checkpoint.save`. The group is created lazily on the first save and cached per default group. Gloo carries only the pickled plans and write results. Each rank still writes its own shards, so the checkpoint files are unchanged.

When `torch.distributed` is not initialized, when Gloo is unavailable, or when the default backend is already Gloo, the helper returns `None` and DCP behaves as before.

## Measurement

The repro is standalone: Megatron-LM main at 92641a4, `torchrun` with 4 ranks on one GB200 node, NCCL 2.30, torch 2.11. Each rank saves a 64 MiB `ShardedTensor` with `dist_checkpointing.save`. Before the "before" reading, the script runs warmup collectives (all_reduce, broadcast, all_gather_object, broadcast_object_list, barrier) so that the ring and tree buffers already exist. The metric is non-PyTorch memory, computed as `mem_get_info` used minus `memory_reserved()`. It was cross-checked against NVML per-process usage.

| sync `torch_dist` save, 4 ranks | rank 0 (coordinator) | ranks 1-3 | second save |
|---|---|---|---|
| main | **+1.168 GiB** | +0.418 GiB | +0 |
| this PR | +0.000 GiB | +0.000 GiB | +0 |

The shard files (`__{0..3}_0.distcp`) have identical md5 with and without the change. `load` is not affected because it uses `no_dist=True`.

**Async save (not changed here).** The nvrx async path has the same exchange, because `save_state_dict_async_plan` is called with `process_group=None`. On main it shows +0.980 GiB on the coordinator. Simply passing the Gloo group there is not safe, though. `save_state_dict_async_finalize` broadcasts a CUDA tensor on the planning group. Over Gloo, that broadcast made each of ranks 1-3 create a CUDA context on GPU 0 (about 0.67 GiB each). The async path therefore needs an nvidia-resiliency-ext change first: a CPU tensor for the failure broadcast when the group is Gloo. That fix is left for a follow-up.

## Test

The new test is `tests/unit_tests/dist_checkpointing/test_torch_dist.py::TestDCPCoordinationGroup::test_sync_save_object_exchange_runs_on_gloo`. It records the group of every `gather_object` / `scatter_object_list` call made during a sync save. It asserts that every call uses a Gloo group spanning the whole world, then loads the checkpoint back and checks it.

- With this change: passes with 2 and 4 ranks.
- Without it: fails (`group is None`, i.e. the default NCCL group).

The existing tests in this file need 8 GPUs, so I could not run them locally.
