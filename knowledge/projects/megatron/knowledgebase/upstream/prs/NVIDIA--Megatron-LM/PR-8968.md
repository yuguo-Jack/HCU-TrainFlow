# [Test][Inference] Independent oracles for MoE activations and MXFP8 quantization

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Adds independent oracle tests for the inference MoE activation kernels (SwiGLU and its batch-invariant and vLLM variants) and the MXFP8 quantization kernels, in `tests/unit_tests/inference/oracles/moe_activations/`. No production code changes.

**Stacked on the oracle harness PR #8966 (`test/inference-oracle-harness`)**, which adds the shared helpers these tests use. Retarget to `main` once it merges.

## Why

- **`_swiglu_kernel` (`padded_swiglu`) has no value check at all.** It is the SwiGLU activation of the torch-backend MoE experts (BF16 and MXFP8) and of vLLM-backend MXFP8 experts. Its only tests check that padding rows are zero and that the kernel replays bitwise.
- The vLLM-backend `bounded_silu_mul` is checked only end to end, at `atol = rtol = 5e-2`. The batch-invariant `weighted_silu_mul_bounded` claims bitwise training parity but is compared with a tolerance, never with the training op.
- The MXFP8 quantizers are compared with a copy of PyTorch's `to_mxfp`, not with the OCP specification. Nothing tests tiny, NaN or Inf blocks, strided inputs, or that the GEMM reads the swizzled scales where the kernel puts them, except a multi-GPU training-parity test.

## The oracles

Each module's docstring holds its kernel's contract, written from the call sites, the training math and the OCP specs before the kernel body was read. No reference mirrors a kernel's index math or bit tricks.

- **SwiGLU kernels.** The reference is fp64 `silu(gate) * linear` (gate first, as training's `torch.chunk`), times the routing probability where the kernel applies one. Two assertions per output:
  - **Rounded once from fp32**, element by element: the correctly rounded value, or either bf16 neighbour where the exact value lies within 2^-16 (relative) of a rounding midpoint. 2^-16 bounds the fp32 evaluation error of the formula with a margin. An intermediate bf16 rounding, truncation or a wrong formula fails it.
  - **The harness policy**, per row, against torch's own fp32 SiLU rounded once on the same device.
  - The batch-invariant kernels are also checked **bitwise against the live training ops** (`weighted_swiglu`, compiled), which is the parity they claim.
- **MXFP8 quantizers.** A reference written from OCP MX v1.0 and the OCP FP8 tables (`_mx_spec.py`):
  - E4M3 elements rounded to nearest even;
  - E8M0 scales by the round-up rule the kernel cites (Mishra et al.): the smallest power of two with `amax / X <= 448`, within E8M0's range. OCP MX §6.3 permits it ("other algorithms may be supported"); the spec leaves the scale algorithm out of scope;
  - the cuBLAS 128 x 4 scale-tile layout, built by reshaping the scale matrix as cuBLAS describes it.

  Outputs must be bit-exact, with codes and scales reported apart.
- **Reference self-tests.** `test_references.py` checks the references themselves, on CPU and on the CUDA device: the MX reference against the spec tables, against torch's `float8_e4m3fn` cast on every bf16 value, and against the cuBLAS layout description; the bf16 rounding against torch's fp32 -> bf16 cast; and torch's own fp32 SwiGLU, rounded once, must pass the rounded-once check. Powers of two are built from their bits, because `torch.ldexp` is inexact on CUDA.
- **Memory.** The launchers allocate their outputs. The tests swap those allocations for NaN-poisoned buffers between guard bands, so rows a kernel must not write are checked bitwise and overruns are caught. Inputs are checked read-only.

## What it covers

- **`_swiglu_kernel`** (93 cases):
  - widths around the 1024-column tile cap and inside one tile, plus production widths 768, 1856 and 2688;
  - rows and `n_used` around the 512-program persistent grid, including `n_used = 0` and `n_used > M`;
  - padding rows at the programs' first rows and wrap points, in runs, at random and everywhere;
  - both `ZERO_PADDING` variants and int32 and int64 maps, combined pairwise;
  - special values: zeros, subnormals, saturated and underflowing sigmoids, overflowing products, infinities and NaN;
  - CUDA-graph replay with a changed `n_used`;
  - offsets past 2^31 (opt-in `large`).
- **`bounded_silu_mul`, `swiglu_with_probs`, `weighted_silu_mul_bounded`**: the same structure. For the element-bounded kernel, bounds sit around `XBLOCK`, the grid stride and a row's end, and run past the buffer. Its grid size is checked not to change any bit.
- **`mxfp8_quantize`, `mxfp8_quantize_into`, `MXFP8Tensor.from_bf16` / `quantize_`**:
  - K around powers of two, with 1 to 3 padded scale columns;
  - M around the 128-row tile;
  - bf16, fp16 and fp32 inputs;
  - blocks on the round-up tie `amax = 448 * 2^k` and its neighbours, elements on E4M3 rounding midpoints, signed zeros, wide-range scales, reused storage.
  - On Blackwell, `x_q @ I` through the production `scaled_mm` consumer, with an identity weight encoded from the spec, must equal the spec decode exactly.
- **`mxfp8_quantize_rows`**: live counts around the 128-row tile and the 4096-program grid, a count past the buffer, CUDA-graph replay.
- **`squared_relu_and_quantize_mxfp8`**: with and without the tanh clamp. Clamped, any activation within the fp32 window of a tie is admissible. Covers live counts, padding layouts and special values.

Hardware: the activation modules run on H100. The `_swiglu_kernel` module and the three MXFP8 modules also carry `launch_on_gb200` and run on GB200, where the MXFP8 expert paths run. One small case per kernel is marked `sanitizer`.

## Tests

On CPU (Triton 3.8 interpreter, torch 2.14), on this branch:
- 573 passed, 9 failed, 26 skipped (17 CUDA-only cases and 9 `large` cases).
- The 9 failures are by design. Each one asserts the contract on main:
  - **`test_mxfp8_quant_swizzle_kernel.py::test_tiny_blocks_take_the_smallest_scale` (2): finding O2-N1.** Blocks with `amax <= 448 * 2^-127` get scale byte 0x01, not 0x00. The fp32 quotient `amax / 448` is subnormal there, and the kernel's add-0x7FFFFF round-up then sets the exponent field to 1.
  - **`test_mxfp8_quant_swizzle_kernel.py::test_strided_input_is_quantized_or_rejected`: O2-N2.** `mxfp8_quantize` silently quantizes the wrong elements of a strided view.
  - **`test_squared_relu_quantize_kernel.py::test_special_values` (2): O2-N3.** `tl.maximum(x, 0.0)` drops NaN (`maxnumf`), so a NaN FC1 output is quantized to 0.
  - **`test_mxfp8_quant_swizzle_rows_kernel.py::test_count_past_the_buffer` (3) and `::test_strided_input_is_quantized_or_rejected`**: the bugs #8564 fixes. All 48 cases of that module pass on #8564's branch (one is GPU-only and skips on CPU).

The CPU runs use interpreter-only shims in `_common.py`, active only with `TRITON_INTERPRET=1`, that make the interpreter follow compiled Triton:
- `tl.range` yields tensors;
- bf16 and E4M3 casts round to nearest even;
- `libdevice.exp` and `tanh` exist.

On GPU (H100 and GB200, first commit):
- The 9 intended failures failed with the predicted messages on both architectures, so the three findings are confirmed.
- The MXFP8 modules passed, including `large`, the sanitizer cases and `scaled_mm` on GB200.
- The batch-invariant kernels matched the training ops bitwise.
- The GLU value checks failed only because the reference's rounding grid came from `torch.ldexp`, which is inexact on CUDA. Every reported element was in fact correctly rounded. Fixed in the follow-up commit; the GLU rerun is pending.

Mutation testing (H100) left two survivors in the GLU kernels:
- `swiglu_with_probs` reading the probability through the permutation map (`probs[permutation_map[r]]`) instead of by row survived, because every test map was the identity on live rows. The third commit fills live rows with original token indices in expert-grouped order, with repeats, as `permute_tokens` does. The values come from a generator of their own, so every other input is unchanged. On CPU the kernel passes and that mutant fails.
- Zero padding written as `-0.0` is an equivalent mutant. Triton turns any literal equal to 0 into +0.0, so the compiled kernel is identical. The tests already compare padding with +0.0 bitwise.
