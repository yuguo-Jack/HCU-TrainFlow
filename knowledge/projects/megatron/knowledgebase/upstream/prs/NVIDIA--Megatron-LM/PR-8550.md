# Add opt-in GC freeze and overlap modes for dynamic inference

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8550) · state: open · merged: False

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Adds an opt-in `--inference-gc-mode` (`InferenceConfig.gc_mode`) so that Python's cyclic garbage collector stops stalling dynamic-inference serving: `freeze` keeps long-lived engine state out of every collection, and `freeze_overlap` also runs collections right after a forward pass is queued, so they overlap GPU work. The default mode leaves current behavior unchanged.

## Details

### Problem

After startup, an inference process holds millions of GC-tracked objects (model modules, CUDA graph state, compile caches). A CPython full (generation-2) collection scans all of them. On a 4-GPU MoE deployment (TP1, EP4, local CUDA graphs, async scheduling), full collections took 0.65–1.2 s per rank. Each rank collects at a different time, and with expert parallelism the other ranks wait for it. In one trace, a 631 ms collection on one rank left its GPU idle while the other three waited in a barrier kernel. After the CPU submits a decode step, only ~5.6 ms of GPU work remains queued, so moving the collection alone cannot hide it. The collection itself has to get cheaper.

### Change
The core logic is in `megatron/core/inference/engines/dynamic_engine.py`

- **`freeze`**: after engine setup and after `resume()`, collect, then `gc.freeze()` so that long-lived objects are never scanned again, then collect once more. The second collection resets CPython's record of the old-generation size; without it the next full collection is deferred into one large scan. The engine freezes once more the first time it drains, which covers state built by the first requests (for example kernels compiled on first use). Automatic GC stays on, and its collections now scan only objects created since the freeze.
- **`freeze_overlap`**: everything `freeze` does, plus automatic GC is disabled while serving. After each forward pass is queued, `_trigger_gc_now()` runs whichever collection CPython's own thresholds say is due, so it overlaps queued GPU work instead of starting right before the next launch. Idle coordinator ticks (all EP ranks idle) run it too.
- **Interface**: `--inference-gc-mode {default,freeze,freeze_overlap}` maps through `InferenceSetupConfig` to `InferenceConfig.gc_mode`.

### Safety

- Freezing never frees an object early. Reference counting is unaffected.
- The cost is that an object alive at a freeze point that later becomes cyclic garbage is kept until `suspend()`. Freezes happen when no requests are in flight to reduce long-lived engine state objects. A unit test checks that a CUDA tensor in a frozen reference cycle is released by `suspend()`, this ensures that we do not cause dead GPU memory blocks.

### Results

4× GB300, TP1/EP4 MoE NT4, 64 requests of 128 tokens per process. `default` (current behavior) was measured in four processes, two of them on a build without this change; each other mode in two. Will attach screenshot to show the effect of freezing.

### Testing

- New: `test_gc_mode_releases_frozen_garbage_on_suspend` (`freeze`, `freeze_overlap`) in `test_dynamic_engine.py`, `test_trigger_gc_now_follows_cpython_thresholds` in `test_text_generation_controller.py`, and config and flag tests in `test_inference_config.py`.

 On torch >= 2.9 this fallback shouldn't run at all. `cuda_graphs.py` only freezes and unfreezes around a capture when FREEZE_GC is true, and it forces that to False on torch >= 2.9, so an inline capture doesn't touch the frozen heap. Switching overlap off and scheduling a refreeze unnecessarily costs real performance, because overlap stays off until the next full drain, which may never come under sustained load. Can we gate on FREEZE_GC additionally?

I do recognize that the real problem here is that we should get rid of the pre-torch 2.9 path. Unfortunately it looks like the repo will support torch < 2.9 for a little longer.
