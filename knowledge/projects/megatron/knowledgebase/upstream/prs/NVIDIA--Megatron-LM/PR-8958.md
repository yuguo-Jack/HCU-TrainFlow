# What does this PR do?

Makes `fused_multimem_rs_add_norm_ag`, the launcher of the fused NVLS reduce-scatter + residual add + RMSNorm + all-gather (`--inference-fuse-tp-communication`), refuse inputs its kernel would process out of bounds, before anything is launched.

Stacked on #8880 (https://github.com/NVIDIA/Megatron-LM/pull/8880, `fix/fused-rs-per-token-blocks`). #8880 rewrites the same launcher's block and grid sizing, and its `test_nvls_fused_collectives.py` is the module's test file, which the new test joins. This branch merges cleanly with `main` and with #8709, #8561, #8704, #8712 and #8868. Of these, only #8709 touches this file, and only the docstring.

**Bug.** The launcher checked only that three of its four tensors are bf16 and that the buffer's element count is a multiple of 8. `_multimem_reduce_scatter_residual_add_kernel` gives every rank `cdiv(T, world_size)` tokens of `cdiv(H, 8)` 128-bit lanes and reads the norm weights as `H` raw bf16 values. The launcher therefore accepted:

- `T % world_size != 0`: the last rank reduces and normalizes rows past `T`. It multicasts them past `T * H * 2` bytes into every rank's symmetric buffer, and it reads and writes its residual past its `T / world_size` rows.
- `H % 8 != 0` (with `T * H % 8 == 0`): every row after the first is misaligned and reads the next row's elements.
- fp32 norm weights, which are read as bf16 pairs and silently misdecoded, and weights that are not `H` long, which are read out of bounds.
- residual input or output tensors that do not hold `T / world_size * H` elements, which are read or written out of bounds.
- strided views with the right element count, such as a slice of a wider hidden buffer. The kernel addresses every tensor through its data pointer as dense rows, so it would read and write the wrong elements.

The production call site (`InferenceRowParallelLinear._matmul_reduce_scatter`) meets the contract: dynamic inference pads `T` to a multiple of TP, and it passes the layer's bf16 residual and the next layer's bf16 norm weights. The bug is therefore latent. On H100, the launcher accepted 5 of the 6 out-of-contract inputs of the oracle test (`test_launcher_refuses_inputs_outside_the_contract`, one launch each). The consequences above are from reading the kernel.

## Fix

- The launcher asserts the contract from tensor metadata before computing the launch geometry. It checks the weights' dtype, `H % 8 == 0` (rows of whole 128-bit lanes, replacing the weaker whole-buffer check), `T % world_size == 0`, `rms_norm_weights.numel() == H`, that both residual tensors hold `T / world_size * H` elements, and that all four tensors are contiguous. Each message names the offending size or dtype.
- The checks read only shapes and dtypes on the host. They add no device sync, allocation or kernel, and there is nothing new on the CUDA-graph path. The kernel itself is unchanged.
- The docstring now states the expected shapes.

## Tests

`tests/unit_tests/determinism/kernels/test_nvls_fused_collectives.py::test_launcher_refuses_inputs_outside_the_contract` (11 cases). It runs the real launcher with the Triton kernel replaced by a recorder and a namespace standing in for the symmetric-memory handle. The checks run before any symmetric-memory use, so the test needs one process and no GPU (Triton importable).

- A valid control launches once.
- Each of ten out-of-contract inputs raises the matching error and launches nothing: a token count not divisible by the world size, H % 8 != 0, fp32 weights, weights not H long, a wrong-size residual input or output, and a strided view with the right element count for each of the four tensors.

On the base branch the control passes and the ten refusal cases fail (each input is launched). With the fix, all eleven pass. On H100, the first seven cases passed with the fix and the six refusals failed on the base. The four contiguity cases were checked locally by running the launcher in a scratch script.

The module's existing tests are unchanged: the launch-geometry test and the TP replay test against the shard-sized launch. They pass contract-satisfying inputs. `tools/check_kernel_determinism_coverage.py` passes, because the module's registered test file changes.
