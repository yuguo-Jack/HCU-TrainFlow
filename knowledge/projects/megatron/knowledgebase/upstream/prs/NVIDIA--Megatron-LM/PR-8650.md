# Keep the DSA sparse-attention value sum in fp32 on every architecture

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8650) · state: open · merged: False

## Original PR description

# What does this PR do?

`_dsa_sparse_attention_forward_kernel` (DSA min-memory) computed its weighted value sum two ways:
- on SM < 10: a `tl.dot` on a 16-row padded probs matrix;
- on Blackwell: an fp32 elementwise reduction, as a workaround for a Triton 3.7 compiler bug.

The `tl.dot` path casts the probabilities to the value dtype first, so for fp32 inputs the sum runs in TF32. It is also the slower path. This PR uses the elementwise reduction on every architecture and removes `_use_dot_mma`. It also adds `test_triton_sparse_attention_tile_matches_fp64_reference`: no existing test compared this kernel's output with a reference.

## Measurements

Each autotune config was launched on its own, both value-sum paths, median of 20 runs, compared with an fp64 reference. The table gives each path's fastest config. Shapes:
1. 256 queries / 4096 keys, 16 heads, 1 KV group, head dim 128, top-k 512
2. 128 queries / 8192 keys, batch 2, 64 heads, 1 KV group, head dim 192, value dim 128, top-k 2048
3. 64 queries / 4096 keys, 32 heads, 4 KV groups, head dim 256, top-k 1024
4. 128 queries / 2048 keys, 16 heads, 1 KV group, head dim 64, top-k 64

GH200 (Hopper), Triton 3.8.0. This is the architecture whose default changes:

| Shape | dtype | elementwise (ms) | `tl.dot` (ms) | `tl.dot` / elementwise | max abs error vs fp64, elementwise / `tl.dot` |
|---|---|---|---|---|---|
| 1 | bf16 | 0.277 | 0.391 | 1.41x | 1.9e-3 / 2.2e-3 |
| 1 | fp16 | 0.270 | 0.389 | 1.44x | 2.4e-4 / 3.9e-4 |
| 1 | fp32 | 0.419 | 1.427 | 3.41x | 3.0e-7 / 6.2e-4 |
| 2 | bf16 | 6.835 | 9.351 | 1.37x | 8.5e-4 / 1.4e-3 |
| 2 | fp16 | 6.449 | 8.935 | 1.39x | 1.1e-4 / 1.5e-4 |
| 2 | fp32 | 10.448 | 14.678 | 1.40x | 1.5e-7 / 3.2e-4 |
| 3 | bf16 | 0.502 | 1.366 | 2.72x | 9.7e-4 / 1.2e-3 |
| 3 | fp16 | 0.456 | 1.410 | 3.09x | 1.2e-4 / 1.8e-4 |
| 3 | fp32 | 0.932 | 1.500 | 1.61x | 1.0e-7 / 3.4e-4 |
| 4 | bf16 | 0.091 | 0.057 | 0.62x | 3.8e-3 / 5.3e-3 |
| 4 | fp16 | 0.065 | 0.053 | 0.82x | 4.8e-4 / 5.7e-4 |
| 4 | fp32 | 0.060 | 0.058 | 0.98x | 6.0e-7 / 1.6e-3 |

Only the smallest shape (head dim 64, top-k 64, about 60 µs per call) is faster with `tl.dot`. With fp32 inputs the `tl.dot` path is about three orders of magnitude less accurate than the elementwise one. 18 of the 48 `tl.dot` (shape, dtype, config) combinations failed to launch for lack of shared memory, with the larger BLOCK_K configs at head dims of 128 and above.

On B300 (SM103) with Triton 3.8.0, forcing the `tl.dot` path no longer hits the Triton 3.7 bug; it compiles and runs. Even so, it was 1.15x to 2.67x slower at the first three shapes, 0.78x to 1.51x at the fourth, and showed the same accuracy gap and the same 18 shared-memory launch failures. So Blackwell keeps the path it already uses.

## Testing

- New test (fp32 / fp16 / bf16; GQA; keys past the query position must be masked), with tolerances rtol/atol 1e-5/1e-6, 2e-3/5e-4 and 2e-2/2e-3:
  - with this PR: passes on GH200 and B300;
  - on main on GH200: the fp32 case fails, max abs difference 6.1e-4. fp16 and bf16 pass.
- `tests/unit_tests/transformer/test_dsa_min_memory_kernels.py`: 41 passed on GH200 and on B300 with this PR.
- black 26.3.0 and isort 5.13.2 report no changes; pylint and ruff were not run.

On Hopper the forward output changes numerically: it is no longer bit-identical to main, and it is closer to the fp64 reference. The kernel's backward is unchanged.
