# Keep GDP `A_log` and `dt_bias` in FP32 under BF16 training

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8528) · state: closed · merged: True

## Original PR description

## Summary

Keeps the Gated DeltaProduct (GDP) decay parameters `A_log` and `dt_bias` in FP32 when the model trains in BF16.

`A_log` was already initialized in FP32, but `Float16Module` cast it to BF16 along with every other floating-point parameter when it wrapped the model. `dt_bias` was initialized directly in `params_dtype`, so it never had FP32 values to begin with. Both feed the per-head decay, `exp(-exp(A_log) * softplus(x + dt_bias))`, where BF16 rounding of the parameters shifts the decay rate of every head.

This PR initializes `dt_bias` in FP32 and marks both parameters with `mark_keep_in_fp32`, the same mechanism the hyper-connection and MTP head parameters already use, so `Float16Module` leaves them in FP32. `in_proj` and the other weights still become BF16. Every consumer of these parameters (the training gate computation and the Triton inference kernels) already upcasts them to FP32, so no compute path changes.

## Testing

`test_decay_parameters_stay_fp32_in_float16_module` builds a GDP mixer, wraps it in `Float16Module`, and checks for both parameters that the dtype stays FP32 and the values are bit-identical to their initialization, while `in_proj.weight` becomes BF16.

The new `dt_bias` initialization also exposed a fragile comparison in `TestChunkedPrefillCudaGraphs`: its small random models have nearly flat logits, so some greedy steps have a top-2 gap of one BF16 ulp or zero, and eager and CUDA-graph runs, which differ by about one ulp per logit, picked different tokens on H100. The chunked-prefill and short-final-chunk tests now record the logits each run sampled from and accept a divergence only if each run puts the other's token within two BF16 ulps of its own, stopping at the first divergence.

[P1] Preserve checkpoint resume across the decay-parameter dtype change

**Failure:** Save a BF16 GDP training checkpoint from the base revision using `use_distributed_optimizer=False` and `ckpt_format="torch"`, then resume at this head with unchanged settings. Previously `Float16Module` converted both decay parameters to BF16, so their masters appeared in `fp32_from_float16_groups`. These markers move them into the native-FP32 group, but [the optimizer loader](https://github.com/NVIDIA/Megatron-LM/blob/d64485cc0c6e5bb6a13d68e32e5d5f4858ba3f56/megatron/core/optimizer/optimizer.py#L1308-L1316) still restores saved masters by position within the filtered low-precision lists. It now pairs a saved decay master with the next remaining BF16 parameter. With four GDP heads and hidden size 256, this attempts to copy a four-element decay vector into a 256-element normalization weight and raises a size-mismatch error. [Training checkpoint loading](https://github.com/NVIDIA/Megatron-LM/blob/d64485cc0c6e5bb6a13d68e32e5d5f4858ba3f56/megatron/training/checkpointing.py#L3289-L3313) reaches this loader directly. Expected: existing checkpoints resume with each parameter's own master value and optimizer state.

**Correction:** Retain both FP32 markers, but migrate the legacy master-parameter lists before the positional restore in `Float16OptimizerWithFloat16Params.load_state_dict`. Use checkpoint-era parameter identities/dtypes to restore decay masters into their newly native-FP32 parameters and align the remaining masters with their corresponding BF16 parameters. Merely dropping two entries per group is unsafe for multiple GDP layers or custom groups. The invariant is preservation of parameter identity across the dtype transition. The exact patch depends on how checkpoint model metadata is passed into this loader; that interface needs to be established rather than guessed here.

**Preservation and proposed acceptance checks:** Save a base-format checkpoint with distinct master values and initialized Adam states, load it into the FP32-marked model, and assert every master/model value and Adam state remains associated with its original parameter. Include two GDP layers and another native-FP32 parameter; a subsequent controlled-gradient step should match a reference using the restored masters. Also retain same-head mixed-dtype round trips, weights-only loading, FP32 decay parameters, and BF16 projection weights. These checks are proposed, not executed.

[P2] Bound ties by actual BF16 spacing

**Failure:** The relative-epsilon formula admits three BF16 representable steps despite the helper's two-ULP contract. For example, baseline tokens `[0]` with logits `[1.75, 1.7265625]` and test tokens `[1]` with reversed logits pass both checks: the gap is `0.0234375` (three BF16 steps), while the tolerance is `0.02734375`. Consequently, both changed regression tests can accept a divergence outside the intended rounding allowance. `eps * abs(value)` approaches twice the actual spacing near the top of a binade.

**Correction:** In [`_assert_tokens_match_up_to_ties`](https://github.com/NVIDIA/Megatron-LM/blob/d64485cc0c6e5bb6a13d68e32e5d5f4858ba3f56/tests/unit_tests/inference/engines/test_dynamic_engine_parallel_and_chunked_prefill.py#L1623-L1659), replace the tolerance calculation with an actual two-step BF16 bound. The recorded logits are BF16 values widened to FP32, so the existing gap assertion can use:

```python
upper = row[other].to(torch.bfloat16)
for _ in range(2):
    upper = torch.nextafter(upper, torch.full_like(upper, float("inf")))
tolerance = (upper.float() - row[other]).item()
```

**Preservation:** Retain reciprocal checks, the identical-token fast path, and stopping at the first accepted divergence because subsequent prefixes differ. Keep the short-final-chunk conv/SSM state assertions unchanged.

**Proposed acceptance checks:** The three-step example must raise; reversed rows separated by zero, one, or two BF16 steps must pass; a near-tie in only one run with a three-step gap in the other must raise. Include negative logits and the boundary-crossing pair `1.9921875`/`2.015625`, which is two representable steps and must pass. The suggested code and tests require author verification; they were not executed here.
