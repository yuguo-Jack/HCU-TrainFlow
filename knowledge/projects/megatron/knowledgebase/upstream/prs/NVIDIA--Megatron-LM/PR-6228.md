# Support TE single-grouped MoE weights in Megatron-FSDP v2

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/6228) · state: open · merged: False

## Original PR description

## What does this PR do?

Fix silent stale expert weights when MFSDP v2 wraps TE `GroupedLinear(single_grouped_weight=True)`. A `GroupedTensor` stores the values consumed by GEMM in `rowwise_data`; assigning `parameter.data` leaves TE reading the original allocation while the optimizer updates FSDP storage.

The fix binds grouped storage during construction **and every unshard**, clears cached member/columnwise views, and reads the original grouped values when initializing the master weights. Ordinary tensors retain their existing path. Quantized grouped storage is explicitly rejected; importing MFSDP still works without TE or on TE versions without `GroupedTensor`.

Based on upstream `main` at `474b1e9ee`. The expert-parallel test covers both expert weight layouts and all dense/expert ZeRO placement combinations. Four-rank runs use EP=2 / EDP=2; eight-rank runs use EP=4 / EDP=2.

## Optimizer initialization

The MCore optimizer's checkpoint-name map is now lazy. Grouped expert names such as `linear_fc1.weight` do not fit the existing per-expert checkpoint naming rules, and eagerly constructing that map prevents otherwise supported training. The same resolver and empty-shard handling run when checkpoint metadata is first requested.

**This does not implement grouped-weight checkpoint save/load.** Checkpointing remains disabled in the grouped training benchmark.

## Validation

Current production sources were tested on **four GB300 GPUs**, with per-rank reports checked:

| Coverage | Result on each rank |
| --- | --- |
| Grouped-linear optimizer/storage regression | 8 passed |
| EP=2 / EDP=2, both expert layouts and all 16 dense/expert ZeRO combinations | 32 passed |
| Lazy checkpoint names (separate run) | 1 passed |

On unchanged `main`, the four separate-weight controls pass and all four grouped-weight cases fail because their original 32 KiB backing allocations remain attached. The corrected checkpoint regression also fails on unchanged `main` because construction already resolves the names.

The new grouped-linear regression uses exactly representable BF16 values and checks forward outputs, reduced gradients, and updated FP32 weights across three SGD steps. It covers separate/grouped weights and no-shard/ZeRO-1/ZeRO-2/ZeRO-3 layouts. A separate test checks that training performs no checkpoint-name lookups and that first checkpoint access resolves and caches them.

`tools/autoformat.sh` passes Black, isort, pylint, and Ruff. Its advisory mypy step reports unavailable local PyTorch/TE dependencies and the existing unannotated `_casted_grads` list.

Earlier four-GPU AdamW replay on the benchmark source stack matched separate and grouped weights exactly for all eight steps. A separate 64-GPU, 128-step comparison measured **3.467 → 2.421 s/step** when enabling both `moe_use_grouped_tensor` and `moe_single_grouped_weight`, with the same host-overhead fixes applied to both cases. That is a combined parameter-representation/GEMM result, not an isolated speedup from this PR. The full-model training trajectories were not identical.

## Related work and limits

- [TransformerEngine #3340](https://github.com/NVIDIA/TransformerEngine/pull/3340) uses plain high-precision parameters for the fusible grouped-linear op. Its current scope leaves the ordinary `GroupedLinear` module on `GroupedTensor`, so this storage integration remains relevant.
- Quantized grouped parameters and CPU/meta initialization are outside this PR's validated scope.
- Full-gradient buffer limits and the communication schedule are unchanged.
