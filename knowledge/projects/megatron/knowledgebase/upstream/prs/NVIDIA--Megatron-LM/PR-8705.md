# [Inference][MTP] Build MTP-only pipeline stages from the decoder's backend and test the inference GPT MTP head

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8705) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Adds regression tests for the inference-optimized GPT MTP head that #8426 introduced. Also fixes the one path that still gives an inference-optimized GPT model a local MTP layer: a pipeline stage without decoder layers, built by `GPTModelBuilder`.

**Background.** Before #8426, `get_gpt_mtp_block_spec` took the MTP norms and `eh_proj` from the Transformer Engine backend or, for every other `transformer_impl`, from the local one. Inference-optimized layers require RMSNorm and, at TP > 1, sequence parallelism. The local RMSNorm (`WrappedTorchNorm`) asserts on sequence parallelism, so no inference-optimized GPT model with MTP could be built at TP > 1:

```
AssertionError: sequence parallel not supported by torch LayerNorm
```

#8426 (`0a513268e`) fixed this: `get_gpt_mtp_block_spec` now picks its backend with `_base_backend_name()`, as the decoder layers and final norm do. It added no test for it. This PR adds the tests, and a comment there on why the MTP head must follow the decoder's backend.

An inference-vs-training configuration matrix on H100 found the bug before #8426 landed. It has four GPT MTP rows at TP=2. Three of them (r10, r19, r29) failed with this assertion. The fourth (r08) hit a different build error first, from MLA with fused TP communication, which is fixed separately. No TP=1 GPT row and no hybrid MTP row hit the assertion: the hybrid inference MTP spec already used `TENorm` and `InferenceColumnParallelLinear`.

**Remaining bug: MTP-only pipeline stage.** In `megatron/training/models/gpt.py`, `mtp_block_spec` takes the MTP inner layer from the stage's decoder block spec. A stage can have no decoder layers, for example with an MoE block spec and a `pipeline_model_parallel_layout` that puts only MTP and the loss on the last stage. Then it falls back to `_te_or_local_layer_spec`, which returns a local layer for every impl except Transformer Engine. For an inference-optimized model at TP > 1 with SP, that layer's `WrappedTorchNorm` raises the same assertion. At TP = 1 the stage pairs an inference MTP head with a local inner layer: torch norms, no inference linears and no all-gather barrier wiring.

**Fix.** The fallback is renamed `_backend_layer_spec`. It returns the layer spec of the backend that `transformer_impl` selects (Transformer Engine, inference-optimized or local), which is the rule the decoder block spec follows. The inference-optimized case includes MoE, like the decoder's MoE layers. `default_layer_spec`'s dense inference branch now calls it too, so the two cannot drift apart. Transformer Engine and local builds are unchanged.

**Tests.**
- `tests/unit_tests/transformer/test_multi_token_prediction.py::TestMultiTokenPredictionLayer::test_constructor_inference_optimized` builds an inference-optimized MTP block at TP=1, and at TP=2 with SP. It checks that `eh_proj` is `InferenceColumnParallelLinear` and that it is set to barrier before its input all-gather reuses the symmetric buffer. `MultiTokenPredictionLayer` sets that barrier, and no other test checks it.
- `tests/unit_tests/inference/text_generation_controllers/test_text_generation_controller.py::TestTextGenerationController::test_mtp_inference_optimized_gpt_no_unbarriered_consecutive_all_gathers` is the GPT twin of the existing hybrid test. It builds the model at TP=2 with SP and runs a serial MTP step. It checks that no all-gather overwrites the symmetric buffer right after another all-gather without a barrier.
- `tests/unit_tests/training/models/test_gpt_builder.py::TestMtpBlockSpec::test_empty_layer_specs_use_the_decoder_backend` checks, for each `transformer_impl`, that an MTP-only stage gets its MoE layer spec from that impl's builder. On `main` the `inference_optimized` case fails because it gets a local layer; the Transformer Engine and local cases pass. It mocks the builders and runs on CPU.

**Results.** On H100 in the CI image (dfw 20990094), the first two tests failed on `main` before #8426 (`01ac4e83d`) in 3 cases: the wrong `eh_proj` class at TP=1, and the assertion above at TP=2 and in the controller test. All 3 cases passed with this change. The neighbor tests `test_constructor_ues_te[2-1]`, `test_constructor_local[2]` and `test_mtp_inference_optimized_hybrid_no_unbarriered_consecutive_all_gathers` passed. Matrix rows r10, r19 and r29 pass with this change merged together with the fixes for the other bugs the matrix found. Current `main` has the same `gpt_layer_specs.py` change from #8426, so these two tests pass there and guard it.

With the review changes (dfw 21004395): every regression case passes with this PR; on current `main`, the builder test fails in its `inference_optimized` case and the two GPU tests pass, as they guard #8426's change. The neighbors pass. The 57-task inference-vs-training matrix passes on integration trees of current `main` with every open fix (dfw 21004395, 21007036).

**Behavior notes.**
- Since #8426, an inference-optimized GPT MTP head uses `TENorm` and `InferenceColumnParallelLinear` instead of torch RMSNorm and `ColumnParallelLinear`, including at TP = 1. Parameter names are unchanged; the TE modules add `_extra_state` entries. `eh_proj` is a TE module built under the MTP layer's FP8 init context. So with `fp8_recipe=mxfp8` and `fp8_param`, its weight becomes MXFP8 (`quantize_model_to_mxfp8`, then `mm_mxfp8`) instead of BF16. MTP drafts and acceptance rates can then change by more than norm rounding. This matches training and the hybrid MTP head. It has been `main`'s behavior since #8426, and this PR does not change it.
- With this PR, an inference-optimized model's MTP-only stage gets an inference-optimized inner layer instead of a local one. That layer has TE norms and inference linears, and becomes MXFP8 under the same settings.

**Not changed.** `gpt_builders.py` (`pretrain_gpt.py`, `train_rl.py`) still asserts against `inference_optimized` with MTP. #1908 added that guard when the MTP head had no inference variant. If a follow-up lifts it, that file's MTP-only-stage fallback (`_get_transformer_layer_spec`) needs the same MoE handling.
