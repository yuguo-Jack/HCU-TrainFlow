# fix(gtp): preserve scratch lifetime during full-iteration capture

# What does this PR do?

Full-iteration CUDA-graph capture with GTP had three independent problems:

1. **Event ordering inside one graph.** GTP's AG/RS handoff events were created `external=True`, which is right for partial graphs (record in one graph, wait in another) but gives no ordering edge when record and wait are captured into the same graph, so a replay could observe the previous iteration's record. Full-iteration chains now use internal events.
2. **Scratch released while the RS stream still reads it.** Wgrad send buffers and FP32 all-to-all scratch were freed on the compute stream after `handle.wait()`, which orders only the RS stream. Under capture the graph pool could hand that storage to the next compute-stream allocation, producing wrong expert gradients. Graphed chains now `record_stream(rs_stream)` before releasing. The eager scratch pool is also never read or written while capturing, so a graph cannot bake in an address that eager reuse later overwrites (relevant to partial graphs with mixed chains) and capture allocations are never cached for eager reuse.
3. **Registered send-buffer pool across capture.** Warmup fences cannot be waited on from inside a capture; a repeated backward (MTP) needed a second registered buffer at capture although warmup used one; and after a graph reset the slot freed inside the capture still carried a fence recorded in the graph, which an eager `wait_event` rejects with `cudaErrorInvalidValue`. Fences are now dropped before capture and when the graphs are reset, and the repeated-backward drain also runs during full-iteration capture.

Builds on the merged wgrad-reuse fences (#7927) and dummy-gradient readiness fix (#7467).

**Memory note (non-registered path only).** Scratch that is `record_stream`'d during capture stays allocated until the capture ends unless `PYTORCH_CUDA_ALLOC_CONF=graph_capture_record_stream_reuse:True` lets the graph pool reuse it once the RS stream rejoins. The registered path (`--gtp-remat-nccl-ub` / `--gtp-expert-remat-nccl-ub`) owns its buffers and is unaffected.

## Tests

| Test | Pins | Without the fix |
|---|---|---|
| `test_full_iteration_fp32_accumulation_scratch_lifetime` | `record_stream` on release | wrong gradients on every rank under allocation pressure |
| `test_repeated_wgrad_reuses_one_buffer_in_full_iteration_capture` (4 GPUs) | drain during capture | registered pool raises "exhausted during capture" |
| `test_full_iteration_reuses_registered_scratch_after_warmup` (4 GPUs) | fence drop before capture / on reset, in-capture reuse dependency | eager restart after reset fails with `cudaErrorInvalidValue` |
| `test_capture_does_not_borrow_eager_wgrad_storage` | eager-pool bypass under capture | graph keeps an address eager reuse later overwrites |

Validated on 4x GB300 (PyTorch 2.13 nv26.07, TE 2.20, NCCL 2.30.7) with the allocator reuse option on and off, plus `test_gtp_grad_correctness.py`; `tools/autoformat.sh` clean against `main`.
