# [Dev] Bound a chained optimizer's state staging to one manager's windows

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8233) · state: open · merged: False

## Original PR description

# What does this PR do ?

Bounds a `ChainedOptimizer`'s chunked-offload staging to one manager's two windows.

Each chunked offload manager (#6244) stages state through two GPU windows, and a chain steps its children one at a time, yet a chain held one window set per child:

- Every offloading child prefetched its first chunk during gradient finalization and held it through the earlier children's updates.
- A child freed its windows while its last D2H copies were still running. The caching allocator withholds such blocks until their `record_stream()` events complete, so the next child allocated new windows. `max_memory_allocated()` hides this; `active_bytes` shows it.

## Change

- Only the first offloading child prefetches ahead of the update; later children restore their first chunk when their own step begins. A LayerWise child counts as offloading through its nested Muon manager, and a nested chain in a later position defers too (LayerWise honors the flag).
- `ChainedOptimizer.prefetch_optimizer_state_for_step` follows each child's deferral instead of prefetching every child.
- The chain shares one `_StagingSlotPool` across its managers, like its transfer streams, and holds it around the children loop in `_step`. Each child hands the windows to the next instead of freeing them; every H2D already waits for the shared D2H stream, so the handover adds no wait. The windows are freed when the loop ends, before any post-step parameter staging such as the deferred MXFP8 sync.
- When a child starts its step it frees the windows of state dtypes it does not use, so a child with different state dtypes (e.g. Muon fp32 momentum next to Adam bf16 moments) does not keep its predecessor's windows alive.

## Memory

One H200, on `dev` at c3010d6: a bf16 MLP with hidden size 4096 split across a chain of three dense `DistributedOptimizer`s (134M parameters each), precision-aware FusedAdam, offload fraction 1.0, 128 MiB chunks. Peak is the maximum `active_bytes` above the pre-step level during the step:

| | `dev` | this PR |
|---|---|---|
| step peak | 1536 MiB | **1024 MiB** (−33%) |
| step time | 108.2 ms | 109.4 ms |

The saving is exactly two staging windows: the second and third optimizers'. The peaks also include each optimizer's master window, which #8232 bounds. Parameters match a non-offloaded chain exactly. Step time rises about 1%, because later optimizers no longer prefetch their first chunk.

## Tests

- New `test_chained_managers_hand_staging_windows_over_while_d2h_drains`: the first manager's D2H is held behind a GPU sleep, so the second starts while it runs. The chain must stay within one manager's peak, and both managers' state must match plain Adam. Without the shared pool it fails at 9.0 vs 5.0 MiB.
- `test_chained_optimizer_defers_later_children_state_prefetch` now compares parameters against a non-offloaded chain; new unit tests cover LayerWise counting as the first child, a nested chain deferred from a later position, a deferred LayerWise prefetching only masters, the chain-level prefetch, and a child with a different state dtype freeing its predecessor's windows.
- `tests/unit_tests/test_optimizer_state_offloading.py` on H200: 58 passed, 1 skipped (`dev`: 51 passed, 1 skipped). `test_layer_wise_optimizer.py` skips entirely at a single rank, on `dev` too.
