# [resharding] Fast NCCL M2N refit for MoE: stack experts per family, support strided GLU shards, split communicators by default

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8606) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes non-collocated NCCL M2N refit fast for MoE models by resharding each expert family as one EP-sharded tensor
instead of one native call per expert, lets dense SwiGLU models use M2N, and enables M2N split communicators by
default.

## Large-scale results: M2N before vs after this PR

Non-collocated refit, BF16, GB200 NVL72 (each job inside one rack), training and inference on disjoint GPUs, median
of 10 refits after 3 warmups. "Before" = this branch with `MEGATRON_NCCL_M2N_STACK_EXPERTS=0` (one native call per
expert tensor, the current behavior); "after" = this branch. Both M2N columns with `NCCL_RESHARD_SPLIT_COMM=1`.
All three backends of a row ran in the same job. Destination weights after an M2N refit are bitwise identical to
an NCCL send/recv refit of the same weights (per-tensor bit fingerprints, 0 mismatches).

Measured on this branch (`cc5989a57`), one 8-node job (16 training GPUs -> 2 inference replicas x 8 GPUs):

| model | layout train -> inference | GB per refit | NCCL send/recv | M2N before | M2N after | after vs before | after vs NCCL | bitwise (before / after) |
|---|---|---|---|---|---|---|---|---|
| Nemotron-3-Ultra (550B-A55B) | TP8 EP16 -> TP8 EP8 x2 | 2248 | 4597 ms | 1602 ms | **706 ms** | **2.27x** | **6.51x** | 0/111216 / 0/111216 |
| Qwen3-235B-A22B | TP4 EP16 -> TP4 EP8 x2 | 974 | 1484 ms | 983 ms | **371 ms** | **2.65x** | **4.00x** | 0/58704 / 0/58704 |
| Llama-3-70B (dense) | TP8 PP2 -> TP8 x2 | 282 | 273 ms | 160 / 97 ms | 88 / 152 ms | no change (same plan) | about 2.9x | 0/7728 / 0/7728 |

Larger scale, same branch and settings (Nemotron-3-Ultra, BF16, median of 10):

| scale | layout train -> inference | TB per refit | NCCL send/recv | M2N before | M2N after | after vs before | after vs NCCL | bitwise (after) |
|---|---|---|---|---|---|---|---|---|
| 16 nodes, one rack | TP8 EP32 -> TP8 EP8 x4 | 4.50 | 3410 ms | 3210 ms | **1302 ms** | **2.47x** | **2.62x** | 0/222432 |
| 32 nodes, two racks | TP8 EP64 -> TP8 EP8 x8 | 8.99 | 32042 ms | 35891 ms | **22615 ms** | **1.59x** | **1.42x** | 0/444864 |

At 32 nodes the training ranks fill one NVL72 rack and the inference ranks the other, so every byte crosses racks over InfiniBand; all three backends are bandwidth-bound there.

An earlier independent 8-node run of the same layouts (same code apart from this branch's MXFP8 handling) gave
Ultra 4582 / 1600 / 717 ms and Qwen3-235B 1479 / 984 / 331 ms (NCCL / before / after).
Llama-3-70B has no experts, so stacking does not change its plan (564 native calls per rank either way); its
minimum refit time is 87.5 ms after vs 87.8 ms before. The two medians per setting come from two interleaved
repeats in this allocation, which was noisy for both settings; a quieter allocation gave a steady 87 ms.

## Why it was slow: per-call cost, not bytes

The native spec builder described every expert weight as its own 1-rank -> 1-rank tensor, so a MoE refit issued
one `m2n.reshard` per expert tensor: 3,750 calls per rank per refit for Qwen3-30B-A3B, 11,227 for Nemotron-3-Super.
At equal bytes, splitting the experts of Qwen3-30B into 16 instead of 128 experts drops the per-expert path from
950 ms to 322 ms (about 0.23 ms per call), while the stacked path takes 146 ms and 144 ms for the two variants.
Host time inside the calls is only 19-68 ms per refit; each per-expert call drives a single link while the rest of
the EP mesh idles.

## Changes (three commits)

1. **Enable M2N split communicators by default.** `NCCLM2NCopyService.__init__` sets `NCCL_RESHARD_SPLIT_COMM=1`
   (via `os.environ.setdefault`, before `m2n.init()`), leaving an explicit user value untouched. It was faster on
   every layout measured: e.g. Llama-3-70B TP4 PP2 -> TP8 91 ms vs 757 ms, Nemotron-3-Super 1.54 s vs 4.31 s,
   Nemotron-3-Ultra 1.6 s vs 10.8 s (per-expert path), Qwen3-235B 331 ms vs 425 ms (stacked path).
2. **Strided GLU shards in native specs.** A TP shard with `partition_stride=s` (SwiGLU `linear_fc1`, s=2) holds `s`
   equal blocks, block `j` being the rank's shard of global component `j`. That is the packed layout
   `partition_sizes=[local/s]*s` the spec builder already supports for Mamba `in_proj`, so strided shards are now
   described that way instead of being rejected (`partition_stride=2 is unsupported`). Indivisible shapes keep the
   rejection. Dense SwiGLU models (Llama, Qwen) can now use M2N.
3. **Expert stacking.** Megatron places experts on EP ranks in contiguous blocks, so the experts of one projection
   form a regular `[E, *shape]` tensor sharded on dim 0 over the EP mesh on both sides. The planner emits one such
   spec per expert family and destination EP group (destination EP groups are spread over source EP replicas
   round-robin); the service stacks the local experts (a zero-copy view when adjacent in memory) and scatters the
   received stack back with `torch._foreach_copy_`. Receiver-side MXFP8 keeps working: transformed experts are
   received into a staging tensor and passed through `prepare_recv`/`finalize_recv` one expert at a time.
   Families that do not meet every condition (ETP>1, packed or strided layouts, missing experts, overlapping
   meshes) keep the per-expert path. `MEGATRON_NCCL_M2N_STACK_EXPERTS=0` disables stacking. Stacking also cuts the
   number of M2N communicators (Ultra 34 -> 4, Qwen3-235B 36 -> 6), which shortens the first refit
   (Ultra 12.6 s -> 8.9 s).

## Tests

- `tests/unit_tests/resharding/test_planner.py`: strided GLU shard -> two packed component specs (TP2 -> TP1,
  TP2 -> TP4); indivisible stride keeps the rejection reason.
- `tests/unit_tests/resharding/test_nccl_m2n_copy_service.py`:
  - split-communicator default and respect of an explicit user value;
  - expert family -> one EP-sharded spec (stacking on) or per-expert specs (off); fallback when an expert is
    missing; adjacent-view and staging/scatter writebacks; receiver-side transform on a stacked family;
  - 4-GPU integration test: planner-built stacked specs vs per-expert specs through M2N vs NCCL send/recv, with
    half of the experts converted to MXFP8 on the receiver, compared bitwise.
- Ran `tests/unit_tests/resharding` on one GB200 node (4 GPUs) at main (`ea99fdfce`) and at each of the three
  commits, single process and under `torch.distributed.run --nproc-per-node 4`. Every commit has exactly the same
  failing tests as main (42 single-process, 34 under torchrun, all in `test_model_swap.py`: multi-rank swaps that
  need more ranks in single-process mode, and NVSHMEM variants), so no new failures; passing tests under torchrun go
  395 (main) -> 398 -> 400 -> 406. The 4-GPU MXFP8 integration test passes on all ranks.
