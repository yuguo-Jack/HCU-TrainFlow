## Original PR description

# What does this PR do?
Add the mHC (Manifold-Constrained Hyper-Connections) numerics used by [GLM-5.3-Flash](https://huggingface.co/zai-org/GLM-5.3-Flash) as opt-in `TransformerConfig` flags, and support full activation recompute with mHC-wrapped hybrid layers.

Split out of #7054 (GLM-5.3-Flash support) as discussed there; #7054 now carries only the KDA layers. Sibling PRs: #7522 (KPool DSA indexer) and #7523 (blockwise FP8 wgrad guard). All are independent of each other and based on `main`.

## Changes

- `mhc_norm_eps_inside_sqrt`: compute the mapping norm as `rsqrt(mean(x²) + layernorm_epsilon)` instead of `‖x‖ / √K + 1e-6`.
- `mhc_keep_mappings_in_fp32`: keep `h_pre` / `h_post` / `h_res` and the residual-stream mixing in FP32 until the final cast to the activation dtype.
- `mhc_learned_output_contract` (default `True`, the current behaviour): with `False`, the residual streams are contracted by their mean instead of the learned `hc_head_*` weights, in both the `HybridStack` post-process and the MTP layer (GLM-5.3-Flash has no learned head).
- Full activation recompute with mHC-wrapped hybrid layers: `HyperConnectionHybridLayer` sets `supports_hybrid_recompute_kwargs`, `recompute.py` forwards the matching kwargs (including `packed_sequence_cp_metadata`) without importing `hybrid_block`, and the `NotImplementedError` in `TransformerConfig.__post_init__` is removed.
- `use_fused_mhc` raises `ValueError` together with either new precision flag (the fused kernels do not implement them).

All new flags default to the current behaviour. GLM-5.3-Flash uses mHC with 4 residual streams and 20 Sinkhorn iterations and has no learned output head, i.e. `mhc_norm_eps_inside_sqrt=True`, `mhc_keep_mappings_in_fp32=True`, `mhc_learned_output_contract=False`.

## Motivation

GLM-5.3-Flash's reference implementation computes the mHC mapping norm with the epsilon inside the square root, keeps the mappings and the stream mixing in FP32, and contracts the residual streams by their mean. Matching this is needed for the Megatron model to reproduce the released checkpoint's numerics. Full recompute with mHC removes the `NotImplementedError` that previously blocked full activation recompute for mHC models.

## Testing

- `tests/unit_tests/transformer/test_mhc_precision.py` (new): mappings, aggregation and mixing against a pure-torch reference in both precision modes; fused mHC rejects the new flags.
- `tests/unit_tests/models/test_hybrid_mhc.py`: full recompute (uniform / block × fp32 / bf16 + FP32 mixing / bf16 fused) matches forward and backward without recompute; a wrapped residual layer does not double-count its input.
- `tests/unit_tests/transformer/test_hyper_connection_recompute.py`: drop the obsolete "mHC + full recompute is rejected" case.

Under full activation recompute the layer forward runs under `no_grad` and is replayed with grad enabled, so `_projection_and_get_norm` takes the `else` branch (this compiled `native_proj_rms`) in the forward but the checkpointed eager `_proj_rms_impl` branch (L321-L325) in the replay and in runs without recompute. The two are not bitwise identical, so the backward uses a replay that does not match the forward whose output the later layers consumed. Before this PR, both passes called `native_proj_rms`.

What we checked on CPU at this head:
- With and without grad, `_projection_and_get_norm` returns the same `proj`, but `norm` differs in the last bits (max abs diff 1e-7 to 7e-7) for 18-20 of 20 seeds in each config (FP32/BF16 input, both `eps_inside_sqrt` modes).
- A reentrant `torch.utils.checkpoint` around `compute_mappings` (forward under `no_grad`, replay under grad) gives a different `h_res` than a plain call for most of 20 seeds.

With the change below, both checks match bitwise in every trial. In our port we also have a 4-stream FP32 variant of `test_full_recompute_matches_forward_backward` (block recompute, learned output contraction; not part of this PR). On GPU, a few seeds exceeded the default FP32 tolerance in the gradient checks, and they passed after this change.

The no-grad path (inference/eval and the full-recompute forward) loses `torch.compile` here. Since both branches must use the same arithmetic, the eager recipe looked like the simplest way to guarantee that. With this change, L322 could also reuse `self._proj_rms_op`, and `native_proj_rms` would then only be used by tests. A CPU test that catches the mismatch:

```python
@pytest.mark.parametrize("eps_inside_sqrt", [False, True])
def test_mhc_projection_matches_with_and_without_grad(eps_inside_sqrt):
    """Full recompute runs the forward under no_grad and replays it with grad enabled."""
    torch.manual_seed(10)
    config = TransformerConfig(
        num_layers=1,
        hidden_size=32,
        num_attention_heads=4,
        use_cpu_initialization=True,
        enable_mhc_connections=True,
        mhc_num_residual_streams=4,
        mhc_norm_eps_inside_sqrt=eps_inside_sqrt,
    )
    module = HyperConnectionModule(config, layer_number=1)
    x = torch.randn(8, 2, 128, requires_grad=True)
    proj, norm = module._projection_and_get_norm(x)
    with torch.no_grad():
        replay_proj, replay_norm = module._projection_and_get_norm(x)
    assert torch.equal(replay_proj, proj)
    assert torch.equal(replay_norm, norm)
```

```suggestion
        # Full activation recompute runs this module under no_grad and replays it with grad
        # enabled; use the same eager FP32 recipe as the checkpointed grad path so the replay
        # reproduces the forward bitwise.
        self._proj_rms_op = partial(_proj_rms_impl, eps_inside_sqrt=config.mhc_norm_eps_inside_sqrt)
```
