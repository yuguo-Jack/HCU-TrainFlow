# fix(inference): decode completed responses like the stream

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8601) · state: open · merged: False

## Original PR description

## What does this PR do?

Completed (non-streaming) completion and chat responses decoded the generated tokens on their own. The streaming path decodes them in the context of the prompt. Some tokenizers produce different text at the prompt/generation boundary, so a completed response could differ from the same request streamed; for example, "world" instead of " world". Streaming also always dropped a trailing EOS token, even when the request asked to keep the stop sequence.

This PR:

- adds `detokenize_generated_tokens`, which decodes a completed generation with the same prompt-aware incremental detokenizer that streaming uses. Completions and chat both use it. Hugging Face fast tokenizers follow the streaming decode; other tokenizers keep the previous decoding;
- makes the incremental detokenizer hold back EOS tokens until it knows whether they are trailing. It drops a trailing EOS only when `remove_eos` is set, which follows `detokenize_stop_sequence`. Held EOS text counts toward the log-probability text offset of the next streamed token, so a token after an interior EOS (with `ignore_eos`) gets its position in the text;
- flushes any text the detokenizer is still holding when a choice finishes, including an incomplete UTF-8 character at the end of the generation, which decodes to U+FFFD as a batch decode does. Because flushed text arrives without new tokens, the stream now sends a text update when an update produces text or carries log probabilities, rather than whenever it carries new tokens. An update whose text is still held, on a request without log probabilities, no longer produces an empty record.

## Example failure scenario(s)

**Scenario 1 (completed text loses its leading space)**

- Request A's prompt ends in "hello" and the model generates the token for "world".
- The streamed response decodes the token after the prompt and produces " world".
- Before this fix, the completed response decoded the token alone and produced "world".
- With this fix, the completed response also produces " world", matching the stream.

**Scenario 2 (stop sequence dropped from the stream)**

- Request B sets `detokenize_stop_sequence=True` and generates "a" followed by the EOS token `<|im_end|>`.
- The completed response keeps "a<|im_end|>".
- Before this fix, the streamed text was "a" because streaming always removed the EOS.
- With this fix, the streamed text is "a<|im_end|>", and with `remove_eos` it is "a" in both paths.

## How was this bug discovered?

A test with a small WordPiece tokenizer decodes one generated token after a one-token prompt and expects " world". With the fix reverted, the completed path decodes the token on its own and the test receives "world". Streaming tests with a chat EOS marker expect the stream to match the non-streaming text for both EOS policies; with the fix reverted, the kept-EOS stream drops `<|im_end|>`.

### [P2] Resolve pending EOS before filtering a subsequent special token

In [the update loop](https://github.com/NVIDIA/Megatron-LM/blob/72349bbb4d9ca285a8057d5edd844dcb6b8d83dd/megatron/core/inference/text_generation_server/dynamic_text_gen_server/incremental_detokenizer.py#L78-L90), filtering a non-EOS special token before resolving pending EOS makes an interior EOS look trailing. Using `_with_chat_markers(eos_marker="<|im_end|>")`, register `<special>` in the special-token map and generate `a<|im_end|><special>` with EOS stopping disabled and `remove_eos=True`. The result is `a`, rather than `a<|im_end|>`. The [established utility contract](https://github.com/NVIDIA/Megatron-LM/blob/72349bbb4d9ca285a8057d5edd844dcb6b8d83dd/megatron/core/inference/utils.py#L29-L47) removes the raw trailing EOS suffix before filtering specials; the final `<special>` means this EOS isn't trailing.

**Correction:** replace the body of `update()`'s `for token_id in token_ids` loop with the following, so every non-EOS token ends the pending EOS run even if that token won't appear in the decoded output:

```python
if token_id in self._eos_token_ids:
    self._pending_eos_token_ids.append(token_id)
    continue
decode_ids.extend(self._pending_eos_token_ids)
self._pending_eos_token_ids.clear()
if token_id not in self._skipped_token_ids:
    decode_ids.append(token_id)
```

This retains special-token filtering and removes only an actual trailing run of model-EOS IDs. The author should verify this proposed replacement before adopting it.

**Proposed acceptance checks:** test both a single update and updates split around EOS/special tokens. `a<EOS><special>` must produce `a<EOS>` under both removal policies. `a<EOS><special><EOS>` must produce `a<EOS>` when removing and `a<EOS><EOS>` when retaining. Consecutive trailing EOS IDs must still all be removed when requested, and mapped non-EOS specials must remain invisible. Preserve the [existing regression](https://github.com/NVIDIA/Megatron-LM/blob/72349bbb4d9ca285a8057d5edd844dcb6b8d83dd/tests/unit_tests/inference/test_openai_streaming.py#L584-L596): its middle EOS stays visible and only its final EOS is policy-dependent. Check both `detokenize_generated_tokens()` and concatenated incremental updates plus `finish()`.

[P2] Flush an unfinished decoder suffix, not only pending EOS

With the [byte-level fixture](https://github.com/NVIDIA/Megatron-LM/blob/72349bbb4d9ca285a8057d5edd844dcb6b8d83dd/tests/unit_tests/inference/test_openai_streaming.py#L56-L64), take an empty prompt and `ids = hf.encode("é", add_special_tokens=False)[:1]`. A token budget can end after this first UTF-8 byte. Batch decoding represents it as `"�"`, but `DecodeStream` withholds the incomplete character. With no pending EOS, `finish()` calls `_decode([])`, which never steps or drains the decoder. Consequently, [the new completed helper](https://github.com/NVIDIA/Megatron-LM/blob/72349bbb4d9ca285a8057d5edd844dcb6b8d83dd/megatron/core/inference/text_generation_server/dynamic_text_gen_server/incremental_detokenizer.py#L156-L164) returns `""`, losing the terminal representation that the previous completed path returned.

**Correction:** make `finish()` reconcile the native decoder's un-emitted suffix using the same prompt context and token-filtering policy. Append the terminal fragment to `_text_fragments` and update `_text_length`, so both completed responses and streaming finalization see it. Don't simply batch-decode generated tokens alone, which would undo the prompt-boundary fix. The mounted tree doesn't expose the native decoder's terminal API, so I can't provide an exact implementation patch.

**Proposed acceptance checks:** the one-byte setup must produce `"�"` from both the completed helper and concatenated updates plus `finish()`. Feeding both bytes must still produce exactly `"é"`, without emitting a premature replacement character. Retain the [WordPiece assertion](https://github.com/NVIDIA/Megatron-LM/blob/72349bbb4d9ca285a8057d5edd844dcb6b8d83dd/tests/unit_tests/inference/test_openai_streaming.py#L507-L520) that the generated suffix is `" world"`, existing complete UTF-8 decoding, chat-marker preservation, both trailing-EOS policies, and idempotent finishing. These checks weren't executed.

[P2] Include buffered EOS text in subsequent logprob offsets

For a completion with `ignore_eos=True` and logprobs enabled, stream partial tokens `[a, eos]`, then final tokens `[a, eos, b]`, using the byte-level chat-marker fixture and binding its `detokenize` to the HF decoder. The first update emits `a` and holds `<|im_end|>`, leaving `text_length == 1`. The next update releases `<|im_end|>b`, but [openai_stream's offset calculation](https://github.com/NVIDIA/Megatron-LM/blob/72349bbb4d9ca285a8057d5edd844dcb6b8d83dd/megatron/core/inference/text_generation_server/dynamic_text_gen_server/openai_streaming.py#L392-L403) assigns `b` offset 1. In the resulting `a<|im_end|>b`, `b` begins at offset 11. This becomes incorrect because the change now preserves interior EOS text; the base implementation dropped that text.

**Correction:** update `openai_stream`'s offset bookkeeping together with the detokenizer's buffering contract. A token following buffered EOS must include the decoded width of that EOS, rather than use only pre-update emitted `text_length`. Preserve prompt-echo offsets and don't count a dropped trailing EOS as emitted text. I haven't established an exact patch that also respects skipped specials and incomplete UTF-8 buffering; expose the needed token positions or buffered-width information explicitly rather than blindly shifting every offset.

**Proposed acceptance checks:** for the split above, either `remove_eos` policy must yield text `a<|im_end|>b` and combined offsets `[0, 1, 11]`; echo `zz` must change them to `[2, 3, 13]`. Preserve the [trailing-EOS regression](https://github.com/NVIDIA/Megatron-LM/blob/72349bbb4d9ca285a8057d5edd844dcb6b8d83dd/tests/unit_tests/inference/test_openai_streaming.py#L213-L271): retained versus removed trailing EOS still yields `a<|im_end|>` versus `a`, with first-frame offsets `[2, 3]`. Ordinary final-token reconciliation and skipped-special/UTF-8 cases must remain unchanged. These checks weren't executed.
