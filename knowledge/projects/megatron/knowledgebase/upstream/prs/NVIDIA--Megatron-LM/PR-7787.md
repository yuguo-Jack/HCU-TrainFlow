# [dev] Fix fused MLA RoPE for inputs of 2**31 or more elements

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7787) · state: open · merged: False

## Original PR description

Thanks to @TKONIY for the contribution to this fix.

- [x] I, the PR author, have personally reviewed every line of this PR.

## Summary

The Triton kernels in `megatron/core/fusions/fused_mla_yarn_rope_apply.py`, which implement the
fused RoPE (`apply_rope_fusion`) of MLA and DSA, compute element offsets in 32 bits:

- every kernel computes each row's offset with a 32-bit multiply, and
- the packing kernel (`fused_mla_rope_concat`) also computes the head and channel offsets of its
  inputs in 32 bits, although its inputs may have any strides and the absorbed-MLA query it packs
  is head-major.

Once an offset reaches `2**31`, the kernel reads (and, for the rows, also writes) at a wrapped
offset, a multiple of `2**32` elements (8 GiB in bf16) before the right place. Nothing reports it:
the output is silently wrong, and an illegal memory access is raised only when the wrapped address
happens to be unmapped.

| Entry point | Caller |
|---|---|
| `fused_apply_mla_rope_for_q` (in place) | MLA query, `multi_latent_attention.py` |
| `fused_apply_mla_rope_for_kv` (key/value split) | MLA key and value, `multi_latent_attention.py` |
| `fused_mla_rope_concat` (packing) | absorbed-MLA query and compressed key/value, `absorbed_mla.py` (the attention module of the DSA layer spec) |
| `fused_mla_rope_inplace(..., rope_first=True)` (in place) | DSA indexer query and key, `dsa.py` |

Every other caller of these kernels has the same limits. For GLM-5 (MLA + DSA), counting the
tokens on one context-parallel rank:

- the DSA indexer query wraps from 524288 tokens at every tensor-parallel size;
- the absorbed-MLA query packing wraps from 58255 tokens at TP 1 (466034 at TP 8) through its
  output rows, and from 66577 tokens at TP 1 (599187 at TP 8) through the heads of `q_absorbed`.

So a 1M-token sequence on one context-parallel rank is affected at every TP size, and with CP 8 the
absorbed query is still wrong at TP 1 and 2.

This PR makes the row index 64-bit in all six kernels and the head and channel indices 64-bit in
the packing forward kernel, and adds GPU regression tests that fail without the fix.

## Root cause

### 1. Row offsets (all six kernels)

Every kernel in the file addresses its row as `X + pid_m * stride_seq`, for example in the
in-place forward kernel:

```python
pid_m = tl.program_id(axis=0)                                       # int32
...
Q = Q + pid_m * stride_x_seq + pid_head * BLOCK_H * stride_x_nheads
```

`tl.program_id` returns int32, and Triton specializes an integer kernel argument whose value is
below `2**31`, such as `stride_x_seq`, to int32 as well. The product is therefore computed in 32
bits and only then sign-extended into the 64-bit pointer offset. Compiled for the DSA indexer query
call (THD, `rope_first=True`, `[t, 32, 128]`):

```
%Q_32 = arith.muli %pid_m, %stride_x_seq : i32
%Q_33 = tt.addptr %Q, %Q_32 : !tt.ptr<bf16>, i32
PTX:   mul.lo.s32   %r11, %r6, %r5           // stride_x_seq * ctaid.x, wraps
       mad.wide.s32 %rd34, %r11, 2, %rd17    // Q + sign_extend(offset) * 2 bytes
```

The same kernel already widens `pid_m` to 64 bits for its token-index lookup in `cu_seqlens_q`,
but not for the row offset. So the first wrapped row is `ceil(2**31 / elements_per_row)`: row `r`
is addressed correctly only while `r * elements_per_row < 2**31`. The in-place backward kernel adds
the head-block offset to the row offset in the same 32-bit sum
(`row_off = pid_m * stride_x_seq + pid_head * BLOCK_H * stride_x_nheads`), so when
`elements_per_row` does not divide `2**31`, the higher heads of the row just below that one wrap as
well (for the 128-head MLA query below: gradient rows 87381 and 87382). The GLM-5 rows of 4096 and
16384 elements divide `2**31`. Grid limits play no part: the grid is
`(rows, cdiv(heads, BLOCK_H))`, and `gridDim.x` allows `2**31 - 1` programs.

Worked example, the GLM-5 DSA indexer query (32 heads x 128 channels = 4096 elements per row):

| Row | True offset (elements) | int32 offset | Where the program reads and writes |
|---|---|---|---|
| 524287 | 2147479552 = `2**31 - 4096` | 2147479552 | in place (the last correct row) |
| 524288 | 2147483648 = `2**31` | -2147483648 | `2**31` elements (4 GiB in bf16) **before** the start of the tensor |
| 524289 | 2147487744 | -2147479552 | 8 KiB above that |
| 1048575 | 4294963200 = `2**32 - 4096` | -4096 | the last row before the tensor |

Every wrapped row is addressed a multiple of `2**32` elements before its place: first below the
tensor, and once the offsets pass `2**32`, onto earlier rows of the same tensor.

### 2. Head and channel offsets of the packing inputs

`fused_mla_rope_concat` documents that its inputs "may use arbitrary input strides", and its
forward kernel adds the head and channel offsets to the row pointer in 32 bits:

```python
head_idx = pid_head * BLOCK_H + tl.arange(0, BLOCK_H)                 # int32
nope_idx = tl.arange(0, NOPE_BLOCK)                                    # int32
nope_offsets = head_idx[:, None] * stride_nope_head + nope_idx[None, :] * stride_nope_dim
nope = tl.load(nope_row + nope_offsets, mask=nope_mask)
```

The absorbed-MLA module passes it a head-major tensor. In `absorbed_mla.py`:

```python
q_absorbed = torch.einsum("...nd,ndk->...nk", q_no_pe, k_up_weight)  # [t, n, 512]
q_absorbed = fused_mla_rope_concat(q_absorbed, q_pos_emb, ...)
```

`einsum` computes this as a matmul batched over the heads, so its output keeps the heads outermost:
strides `(512, t * 512, 1)`. Head `h` therefore starts at element `h * t * 512`. Compiled for this
call, the head offset is `arith.muli %nope_offsets, %nope_offsets_22 : tensor<8x1xi32>` followed by
`tt.addptr ... tensor<8x512xi32>`, so it wraps once `h * t * 512 + 511 >= 2**31`, for every token,
long before the rows of `q_absorbed` do. Worked example, GLM-5 at TP 8 (8 heads) with 1M tokens on
one context-parallel rank (`t = 2**20`, head stride `2**29`):

| Head | True start (elements) | int32 offset | Where the program reads |
|---|---|---|---|
| 3 | 1610612736 = `3 * 2**29` | 1610612736 | in place |
| 4 | 2147483648 = `2**31` | -2147483648 | 4 GiB (bf16) below the start of `q_absorbed` |
| 5 | 2684354560 | -1610612736 | 3 GiB below the start |
| 6 | 3221225472 | -1073741824 | 2 GiB below the start |
| 7 | 3758096384 | -536870912 | 1 GiB below the start |

Each wrapped head is read `2**32` elements (8 GiB) before its place. The RoPE input (`q_pos_emb`, a
view of the row-major query) and the packed output are head-minor and stay in range. The channel
offsets would wrap the same way for an input whose channels are outermost in memory; no caller
passes one, but the kernel accepts it.

### Why it is silent, and when it crashes

- The wrapped rows are left unrotated, and the memory at the wrapped offsets is rotated or
  overwritten in their place. Nothing checks the address.
- When an in-place kernel autotunes (on its first call in a process), the autotuner's
  `restore_value` copy of the input was placed right below the input in our runs. The wrapped
  writes land in that copy, which is copied back afterwards, so rows *below* the limit come back
  corrupted as well. A CUDA caching-allocator trace of a 524289-row indexer query shows this: the
  autotuner's two restore copies lie at [-8.81, -4.81) and [-4.78, -0.78) GiB relative to the
  input, row 524288 is accessed at -4.00 GiB, inside the second copy at its row 102400, and after
  the copy-back row 102400 of the input comes back wrong.
- Otherwise the wrapped accesses hit whatever tensor lies below, for example a gradient buffer,
  and an illegal memory access is raised only when they reach unmapped memory. A trace of a
  1048576-row indexer query faulted because its restore copy lay at [-9, -1) GiB, so the wrapped
  range [-4, 0) GiB reached the unmapped gap above it.
- The wrapped heads of `q_absorbed` are only read: the packed query gets whatever lies there in
  those heads, without an error, or the read faults.

### When it triggers

The limits count the tokens of one call on one GPU: the tokens on one context-parallel rank
(sequence length / CP size, also with the load-balanced zigzag split) for THD inputs, and
`seq * micro_batch` for SBHD inputs. Tensor parallelism divides the attention heads, and with them
the elements per row and the heads of `q_absorbed`, but not the DSA indexer heads, which every TP
rank holds in full.

| Tensor (per GPU) | What wraps | First wrapped token |
|---|---|---|
| GLM-5 DSA indexer query `[t, 32, 128]` | rows of 4096 elements | 524288 (any TP) |
| GLM-5 absorbed-MLA query packing output `[t, 64/TP, 512 + 64]` | rows of 36864 / TP elements | 58255 (TP 1), 116509 (TP 2), 233017 (TP 4), 466034 (TP 8) |
| GLM-5 `q_absorbed` `[t, 64/TP, 512]`, strides `(512, t * 512, 1)` | head `64/TP - 1`, at element `(64/TP - 1) * t * 512` | 66577 (TP 1), 135301 (TP 2), 279621 (TP 4), 599187 (TP 8) |
| MLA query, 128 heads of 128 + 64 `[t, 128, 192]` | rows of 24576 elements | 87382 (TP 1) |
| MLA key/value split input, 128 heads of 128 + 128 `[t, 128, 256]` | rows of 32768 elements | 65536 (TP 1) |
| Absorbed-MLA packing output, 128 heads of 512 + 64 `[t, 128, 576]` | rows of 73728 elements | 29128 (TP 1) |
| DSA indexer query, 64 heads of 128 `[t, 64, 128]` | rows of 8192 elements | 262144 (any TP) |

GLM-5: 64 attention heads, `qk_nope_head_dim` 192, `qk_rope_head_dim` 64, `kv_lora_rank` 512, 32
indexer heads of 128 channels. For a 1M-token GLM-5 sequence:

| CP size | Tokens per rank | DSA indexer query wraps | Packing output wraps | `q_absorbed` heads wrap |
|---|---|---|---|---|
| 1 | 1048576 | yes | at TP 1, 2, 4 and 8 | at TP 1, 2, 4 and 8 (TP 8: heads 4-7) |
| 2 | 524288 | no (exactly `2**31` elements) | at TP 1, 2, 4 and 8 | at TP 1, 2 and 4 (TP 4: heads 8-15) |
| 4 | 262144 | no | at TP 1, 2 and 4 | at TP 1 and 2 (TP 2: heads 16-31) |
| 8 | 131072 | no | at TP 1 and 2 | at TP 1 (heads 32-63) |

### How it was found

In long-sequence tests (sequences of up to 1M tokens), a fused RoPE call on a long local sequence
failed with an illegal memory access. Checking every output row then showed silently wrong rows at
shorter lengths that did not fail. The head offsets of `q_absorbed` showed up when the packing was
checked with `q_absorbed` in the layout the absorbed-MLA module passes (the `einsum` output) rather
than as a contiguous copy. All examples here were reproduced with the MLA and DSA entry points.

## Fix

In each of the six kernels (in-place forward and backward, packing forward and backward,
key/value split forward and backward):

```python
# Row offsets are pid_m * row stride; keep them 64-bit for inputs of 2**31+ elements.
pid_m = tl.program_id(axis=0).to(tl.int64)
```

and in the packing forward kernel:

```python
# The inputs may have any strides, and the absorbed MLA query (an einsum output) is
# head-major, so head and channel offsets can pass 2**31 too; keep these indices 64-bit.
head_idx = (pid_head * BLOCK_H + tl.arange(0, BLOCK_H)).to(tl.int64)
...
nope_idx = tl.arange(0, NOPE_BLOCK).to(tl.int64)
...
rope_idx = tl.arange(0, ROT_BLOCK).to(tl.int64)
```

### Why it is correct and complete

- Every row offset in these kernels is derived from `pid_m`: the row pointers of all inputs,
  outputs and gradients, and in SBHD layouts `pid_m // batch_size` and `pid_m % batch_size`. With
  `pid_m` in int64 they are all computed in 64 bits. For the indexer call above the row offset now
  compiles to `arith.muli %pid_m_2, %Q_32 : i64` and `tt.addptr %Q, %Q_33 : !tt.ptr<bf16>, i64`
  (PTX `mul.lo.s64`).
- In the packing forward kernel every other offset is a head, channel or RoPE-pair index times a
  stride, and all three indices are now int64, so every offset into its inputs and its output is
  computed in 64 bits whatever the strides. For the `q_absorbed` call the head offset now compiles
  to `arith.muli %nope_offsets, %nope_offsets_25 : tensor<8x1xi64>` and
  `tt.addptr %nope, %nope_offsets_29 : tensor<8x512x!tt.ptr<bf16>>, tensor<8x512xi64>`.
- The other five kernels address `[rows, heads, channels]` tensors with unit channel stride (their
  wrappers assert it or make the tensor contiguous) whose heads lie within each row: the
  activations the MLA and DSA callers pass (linear-layer outputs) and their gradients, and the
  tensors the wrappers allocate. Their head and channel offsets therefore stay below one row of a
  tensor. The cos/sin offsets are a position times the table's row stride.
- These six are all the kernels in the file; its two `@triton.jit` helpers, which map a THD row to
  its token position, already work in 64 bits. The regression tests cover all three entry points,
  forward and backward, and head-major and channel-major packing inputs; each of the three index
  changes in the packing kernel is needed for one of them to pass.

### What it does not change

- Below the limits the results are bitwise identical at the same `BLOCK_H`, apart from last-bit
  FMA-contraction differences in the packing kernel at `BLOCK_H=128` (see Tests).
- Kernel times are unchanged within 1%, except the packing of the one-head compressed key/value,
  which is about 1.7% slower (see Tests).
- No API, argument, autotuning or launch change.

Alternatives considered: widening each offset expression instead of the indices gives the same
results for a larger diff; chunking on the host would need a row-offset argument for the zigzag
context-parallel and `position_ids` paths, and making `q_absorbed` contiguous before packing would
cost an extra read and write of it.

## Risk and compatibility

- The kernel changes are the types of `pid_m` (all six kernels) and of the head, channel and
  RoPE-pair indices (packing forward). Below the limits, results are bitwise identical at the same
  `BLOCK_H`, apart from the last-bit FMA-contraction differences in the packing kernel at
  `BLOCK_H=128` described above.
- No API, configuration or checkpoint change. Inputs below the limits behave as before; larger
  inputs, which were silently wrong or crashed, are now correct.
- The new tests need about 9 GiB (in place, strided packing) and 19 GiB (key/value split, row
  packing) of free GPU memory and skip otherwise. Together they take about 35 s on B200.

## Notes for reviewers

- The in-place test uses `remove_interleaving=True`, while the MLA query and DSA indexer callers
  use `False`. The row offset does not depend on the channel layout, and with `True` every rotated
  pair is written back to the slots it was read from, so the result does not depend on how a
  program orders its loads and stores. The `remove_interleaving=False` in-place kernels have a
  separate ordering race at `BLOCK_H=2`, which #7789 fixes.
- #7789, #7803 (key/value split for non-power-of-two head dims) and #7806 (binary search for the
  THD row lookup) change the same two files at different lines. The four PRs apply without
  conflicts, and on the combined tree every test of the four passes. None of them depends on
  another; #7806 should be merged after #7789.
- The key/value split test uses 128 heads of 128 + 128 channels because the key/value split kernel
  needs power-of-two key and value head dims (`tl.arange`). GLM-5's 192 / 256 cannot use it, and
  its DSA layers use the absorbed-MLA packing instead. That limitation is unrelated to this PR; #7803 fixes it.
- The strided packing test allocates inputs of just over `2**31` elements but packs only their
  first 16 rows, so its output stays small. The two calls it compares share the autotuned
  `BLOCK_H`, so they are compared bitwise.
