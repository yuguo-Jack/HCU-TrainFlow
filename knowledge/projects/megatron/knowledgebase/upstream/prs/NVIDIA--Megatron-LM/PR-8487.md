# fix(lite): [DeepSeek-V4] miscellaneous minor bug fixes for Megatron Lite and CSA kernels

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8487) · state: open · merged: False

# What does this PR do?

## Summary

This PR bundles six small, independent fixes found while running
DeepSeek-V4 with Megatron Lite:

1. stream CPU-offloaded FSDP2 weights through a per-tensor GPU staging
   path during online weight synchronization;
2. wire the existing cross-entropy fusion capability into the
   DeepSeek-V4 Lite protocol;
3. restore GPipe overlap for non-interleaved forward-only pipeline
   execution;
4. release the final retained pipeline input after a normal 1F1B
   training step;
5. use 64-bit row arithmetic in the CSA `sanitize_topk` Triton kernel;
6. isolate TorchInductor and Triton compile caches by global Ray rank.

The changes are intentionally narrow. Existing defaults remain unchanged,
and each fix is covered by a focused regression test.

## Changes

### 1. Stream CPU-offloaded weights during export

Commit: `fix(lite): stage CPU-offloaded weights during export`

When parameter offload is enabled, the existing online synchronization path
moves the full model back to CUDA before exporting weights. This defeats the
purpose of parameter offload and can produce a large temporary GPU-memory
peak.

This change adds an opt-in `cpu_resident` argument to
`MegatronLiteEngine.get_per_tensor_param()`:

- `cpu_resident=False` remains the default and preserves the existing path;
- `cpu_resident=True` skips the full-model `self.to("cuda")`;
- the exporter stages each parameter or persistent buffer to the local CUDA
  device immediately before yielding it;
- the export buffer remains at the existing 2 GiB limit;
- the new path is currently accepted only for the FSDP2 optimizer backend;
- unsupported backends fail explicitly with `NotImplementedError`.

#### verl integration

The Megatron Lite change deliberately does not infer this mode from
`param_offload`. The caller owns the model residency policy, so verl must
explicitly forward `cpu_resident=True` when all of the following hold:

- the actor uses Megatron Lite;
- parameter offload is enabled;
- the Lite optimizer backend is FSDP2.

For example, verl's weight-update call sites can pass the resolved policy:

```python
per_tensor_param, peft_config = self.actor.engine.get_per_tensor_param(
    layered_summon=self.layered_summon,
    base_sync_done=True,
    cpu_resident=mlite_param_offload_enabled,
)
```

The same policy needs to be forwarded by every applicable
`get_per_tensor_param()` call, including disaggregated checkpoint-engine
weight transfer and base-weight synchronization. Until verl forwards the
flag, behavior is unchanged.

The end-to-end SFT run used parameter offload disabled, so it validates that
this commit does not regress the default path. The CPU-resident path itself
is covered by focused CUDA and engine unit tests.

### 2. Wire cross-entropy fusion into DeepSeek-V4

Commit: `fix(lite): wire cross-entropy fusion into DeepSeek-V4`

`DeepseekV4ForCausalLM` already supports the fused linear cross-entropy path,
but the DeepSeek-V4 Lite protocol did not expose or propagate the setting.
Consequently, enabling cross-entropy fusion in the engine configuration had
no effect and the model materialized the full logits tensor.

This change:

- adds `cross_entropy_fusion: bool = False` to the DeepSeek-V4
  `ImplConfig`;
- applies the setting to all model chunks during model construction;
- adds the required forward argument in `_forward_step`;
- keeps the feature disabled by default.

This matches the protocol wiring already used by other Lite model families.

### 3. Restore GPipe overlap for forward-only PP

Commit: `fix(lite): restore GPipe overlap for forward-only PP`

The generic virtual-pipeline forward-only schedule processes one
microbatch through all physical stages before starting the next one. For
`VPP=1`, the stage barriers serialize the pipeline and prevent normal GPipe
microbatch overlap.

This change adds a dedicated single-chunk forward-only path that follows the
expected per-stage order:

```text
receive -> forward -> send
```

It also retains dynamic shape exchange for THD batches, so variable-length
microbatches allocate correctly sized P2P receive buffers.

The existing generic schedule remains in use for multiple virtual chunks.
Training schedules are unaffected.

### 4. Release the retained input after 1F1B

Commit: `fix(lite): release retained pipeline input after 1F1B`

After a non-first pipeline stage completes a normal 1F1B step, the wrapped
model can retain the final microbatch input through its `input_tensor`
slot. This keeps the last activation reachable between training steps and
unnecessarily raises steady-state GPU memory.

After all backward communication has completed, this change clears that
reference with:

```python
unwrap_model(model).set_input_tensor(None)
```

First-stage behavior is unchanged, and the cleanup happens only after the
normal 1F1B schedule completes.

### 5. Prevent `sanitize_topk` row-offset overflow

Commit:
`fix(csa): use int64 for row index in sanitize_topk kernel to prevent overflow`

The Triton kernel previously kept `tl.program_id(0)` as an `int32`. A score
offset such as:

```text
row * stride_scores_row
```

can exceed `INT32_MAX` even when each individual tensor dimension fits in
32 bits. For example, `41943 * 51202 = 2147565486`. The wrapped pointer
offset can cause an illegal memory access.

The fix casts the row program ID to `tl.int64`, making all row-based pointer
arithmetic in the kernel 64-bit. Small-shape behavior is unchanged.

The regression test constructs an offset beyond `INT32_MAX` and verifies the
kernel result rather than relying only on a static type assertion.

### 6. Isolate compile caches by global Ray rank

Commit: `fix(lite): isolate compile caches by global Ray rank`

Ray actors can all report `LOCAL_RANK=0`. Using `LOCAL_RANK` first therefore
maps multiple actors to the same TorchInductor and Triton cache directories,
which can cause concurrent cache writes and compilation races.

This change:

- prefers the globally unique `RANK`;
- retains `LOCAL_RANK` as the torchrun fallback;
- stores the original cache roots in
  `VERL_MLITE_BASE_TORCHINDUCTOR_CACHE_DIR` and
  `VERL_MLITE_BASE_TRITON_CACHE_DIR`;
- avoids nested paths such as `rank_3/rank_3` during repeated engine
  construction;
- logs the before/after cache paths for diagnosis.

If a cache environment variable is not configured, the function leaves it
unset.

## Compatibility and scope

- CPU-resident export is opt-in and currently FSDP2-only.
- DeepSeek-V4 cross-entropy fusion defaults to `False`.
- The GPipe specialization applies only to forward-only execution with one
  model chunk.
- The 1F1B cleanup only removes a stale reference after normal completion.
- The Triton change only widens pointer-offset arithmetic.
- Compile-cache isolation only rewrites cache variables that are already set.

The SFT end-to-end environment also contained the independent FSDP2 CPU
AdamW pipeline from
[#7542](https://github.com/NVIDIA/Megatron-LM/pull/7542). None of the changes
in this PR depends on, modifies, or is required by that optimizer pipeline.

## Validation

### End-to-end DeepSeek-V4 SFT

The complete patch series and a baseline with the six changes disabled were
exercised in paired DeepSeek-V4 SFT runs.

Test characteristics:

- 4 nodes, 8 NVIDIA H20 GPUs per node;
- Megatron Lite with the FSDP2 backend;
- pipeline, expert, and context parallelism enabled;
- fixed microbatch scheduling with dynamic batching disabled;
- long-context inputs;
- optional offload and fused-cross-entropy settings exercised through the
  same launcher.

Both feature-on and feature-off variants met the smoke-test acceptance
criteria. In the longer archived run with this patch series:

- training progressed continuously from step 1 through step 495;
- approximately 390 million training tokens were processed;
- loss decreased from `1.092` at step 1 to the expected `0.3-0.5` range;
- gradient norms remained finite;
- peak allocated GPU memory stabilized at approximately `43.14 GiB`;
- no Python traceback, CUDA illegal-memory access, OOM, or NCCL failure was
  observed.

The compile-cache diagnostics also showed distinct cache directories for all
global ranks 0 through 31.

This SFT run directly exercises the DeepSeek-V4 protocol, the 1F1B cleanup,
the CSA kernel, and Ray cache isolation. CPU-resident RL weight
synchronization and forward-only GPipe are validated separately below
because they are not active in a normal non-offloaded SFT training step.

### End-to-end DeepSeek-V4 RL

An ongoing long-context GRPO math run also exercised this patch series in a
realistic RL stack:

- 4 nodes, 8 NVIDIA H20 GPUs per node;
- Megatron Lite with FSDP2 and PP2/EP8/CP8;
- 128K actor and rollout context limits;
- parameter, optimizer, and gradient offload enabled;
- repeated CPU-resident actor-to-rollout weight synchronization;
- DeepSeek-V4 cross-entropy fusion enabled.

The anonymized validation trend was:

| Step | Math reward / score | Core accuracy |
| ---: | ---: | ---: |
| 10 | 0.4625 | 0.7313 |
| 20 | 0.5604 | 0.7802 |
| 30 | 0.6917 | 0.8458 |
| 40 | 0.8646 | 0.9323 |
| 50 | 0.8708 | 0.9354 |
| 60 | 0.8938 | 0.9469 |

The rollout/training absolute log-PPL difference remained approximately
`6e-4` to `9e-4` over the observed steps, while the math score increased
normally. The run remained active through at least step 64 without a Python
traceback, CUDA illegal-memory access, OOM, or NCCL failure.

This RL result is compatibility evidence, not an isolated attribution study.
The tested stack also included:

- the independent FSDP2 CPU AdamW pipeline from
  [#7542](https://github.com/NVIDIA/Megatron-LM/pull/7542);
- the mHC numerical-semantics fixes from
  [#8450](https://github.com/NVIDIA/Megatron-LM/pull/8450);
- an experimental activation-offload implementation that is not part of this
  PR and has not yet been submitted upstream.

In particular, #8450 directly affects model numerical semantics. The quality
increase therefore demonstrates that this PR coexists with the complete RL
stack and does not introduce an obvious optimization regression; it should
not be interpreted as a quality gain caused by this PR alone.
