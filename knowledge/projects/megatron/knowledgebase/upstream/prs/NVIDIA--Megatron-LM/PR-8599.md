# fix(inference): finish SSE choices promptly and report missing final records

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8599) · state: open · merged: False

## Original PR description

## What does this PR do?

The OpenAI-compatible SSE stream (`openai_stream`) had several protocol problems:

- **Delayed terminals:** a choice's terminal record (finish reason, token IDs and generated text) was sent only after every other choice had finished.
- **False success:** an engine stream that ended without a final record was closed as if it had succeeded.
- **Wrong finish reason:** a choice that streamed tool calls and then hit its token limit reported `tool_calls` instead of `length`.
- **Pending tasks:** closing the stream cancelled its per-choice reader tasks but did not wait for them.

With this PR:

- each choice gets its terminal record as soon as that choice finishes;
- a missing final record produces an SSE error record instead of the usage record and `[DONE]`;
- `length` takes precedence over `tool_calls`;
- closing the stream waits for the cancelled readers.

The streaming chat parser no longer catches and logs its own exceptions, so a parser failure now ends the stream with that exception instead of silently dropping text.

## Example failure scenario(s)

**Scenario 1 (short choice waits for a long one)**

- A streaming completion asks for two choices.
- Choice A finishes after 1 token while choice B is still generating.
- Before this fix, A's terminal record was sent only after B finished.
- With this fix, A's terminal record is sent as soon as A finishes, while B is still streaming.

**Scenario 2 (stream ends without a final record)**

- Request A's engine stream ends without delivering its final record.
- Before this fix, the client received a normal terminal record, a usage record and `[DONE]`.
- With this fix, the client receives an error record that names the choices that have no final record.

**Scenario 3 (tool call at the token limit)**

- A chat choice streams a tool call and then reaches its `max_tokens` limit.
- Before this fix, the choice reported `finish_reason: "tool_calls"`.
- With this fix, it reports `finish_reason: "length"`, matching the engine's actual stop reason.

## How was this bug discovered?

Streaming tests feed `openai_stream` scripted engine streams and check the exact SSE records. On `main`:

- the short choice's terminal record arrives after the long choice finishes;
- a stream with no final record still ends with `[DONE]`;
- the tool-call parser reports `tool_calls` at the token limit;
- reader tasks are still pending after the generator closes.

## Dependency and scope

This PR is independent and based on `main`. The change is limited to `openai_streaming.py`. Non-streaming responses are unchanged; the separate non-streaming log-probability fix is its own PR.

New tests in `test_openai_streaming.py` cover each case. The existing tool-call finish-reason test keeps its `tool_calls` assertion and gains the `length` case.
