# What does this PR do?
A block-scope inference graph keeps its output tensor alive for replay, and graphs are keyed by batch dimensions, so each captured graph pinned its own full-vocabulary logits in the graph pool. With prompt log-probs (every token's logits materialized) that is ~0.5 MiB per token per graph: about 2 GiB per 4096-token prefill graph, and ~36 GiB for the prefill/mixed graphs of a max_tokens=4096 run with --inference-cuda-graph-all-prefills, which ran out of memory during capture.

Copy the logits of graphed dynamic-batching forwards into a single model-owned [1, max_rows, vocab] buffer and return a view of it, where max_rows covers max_tokens and every request's speculative tokens. The buffer is allocated during the eager warmup before the first capture, so it lives outside the graph pool at a fixed address. Reuse across replays is safe because the controller copies the logits into its own buffer on the current stream immediately after the forward (`_dynamic_step_forward_logits`) and never reads the returned tensor again, including under async scheduling; the next replay is ordered after that copy.

- mathemakitten · comment · 2026-10-13T14:36:44Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8167#discussion_r4260024866)

File: `megatron/core/models/hybrid/hybrid_model.py` · line 568

Is this essentially a duplicate buffer of `_all_logits_cuda`?

```
# Copy logits to contiguous buffer.
        if self._enable_cuda_graph:
            self._all_logits_cuda[:, :logits_seq_len, :].copy_(logits[:, :logits_seq_len, :])
```

Now it looks like the logits sit in two different persistent buffers and are copied twice per step. `_all_logits_cuda` already has a fixed address and is sized correctly regardless of whether we're in "full prompt logits" mode or "last-token only" mode. 

Can we instead consider having the inference context own this buffer via allocating it in `DynamicInferenceContext.initialize_all_tensors`? It would need to size it the same way as `_all_logits_cuda`, so `max_requests * (num_speculative_tokens + 1)` rows when only last-token logits are materialized, `max_tokens` rows otherwise. We could then also de-duplicate the two buffers and double copy by having the controller use that buffer instead of  copying into `_all_logits_cuda`. Does that proposed refactor make sense to you?
