# [Inference][SSM] Compute softplus as log1p(exp(x)) in the Mamba decode kernel

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8960) · state: open · merged: False

## Original PR description

# What does this PR do?

Makes the Mamba-2 decode kernel's fp32 softplus as accurate as torch's, so that an fp32 SSM state (the default) stays as accurate as torch fp32 doing the same recurrence. Before this change, the state lost several times torch's fp32 error on every decode step.

Based on `main`. #8569 (s10) also changes `mamba_ssm.py`, but only the launcher `selective_state_update` (a D shape check), not `softplus`. Its edits to `test_selective_state_update.py` and to `test_selective_state_update_replays` are separate hunks, so this branch merges cleanly with #8569, #8568 and `main`.

**Bug.** `_selective_scan_update_kernel` (behind `selective_state_update`, every non-batch-invariant Mamba decode and speculative verification step) computed `softplus(dt + dt_bias)` as `log(exp(x) + 1)` in fp32. Rounding `exp(x) + 1` to fp32 before the log leaves an absolute error of up to 2^-24 in the step size dt'. `MambaMixer` initializes `dt_bias` so that dt' lies in [1e-3, 1e-1]. There, that is a relative error of up to ~5.5e-5 in dt' (log1p: ~4e-8), and `exp(A * dt')` with |A| up to 16 carries it into the state on every step.

Against an fp64 recurrence, the fp32 state's error was 2.3-9.7x torch fp32's in 24 of 59 fp32 sweep cases on H100. The production shape (8 heads, head dim 64, dstate 128, fp32 state: rms 1.30e-7 vs torch's 4.81e-8 on H100) and the speculative-rollback snapshots failed the same way on H100 and GB200. That is about one fp32 ulp of an O(1) state per step. bf16 states and outputs are rounding-dominated and were unaffected.

## Fix

- `softplus` now computes `libdevice.log1p(libdevice.exp(x))`. That is `torch.nn.functional.softplus` below its threshold, and the GDP prepare kernel (`gdp/prepare.py`) already computes it this way. The callers keep the identity above 20 (`tl.where(dt <= 20.0, softplus(dt), dt)`), which is torch's threshold. Both kernel branches use it: dt, A and dt_bias broadcast over the head dim (TIE_HDIM, the mixer's layout) and dense.
- Cost: compiled for sm_90, the production specialization grows from 528 to 536 SASS instructions (TIE_HDIM, where softplus runs once per program and token) and keeps the same number of MUFU instructions. The dense branch grows from 688 to 720. The kernel is bound by its state loads and stores, so no measurable effect is expected. It was not benchmarked on a GPU.
- Same formula, deliberately unchanged: `ssd_chunk_state.py`'s `softplus` in `_chunk_cumsum_fwd_kernel` (chunked prefill and the batch-invariant decode). Batch-invariant rollout must match `mamba_ssm`'s training scan bit for bit, and that scan uses the same formula (`test_batch_invariant_decode.py` asserts it). A comment at that `softplus` now says so. Its prefill outputs are also dominated by bf16 and TF32 tensor-core rounding. The chunk scan, state passing and varlen kernels take dt' from that kernel and compute no softplus of their own. Gated Delta Product's `common.softplus` is FLA's inline PTX, copied to stay bitwise identical to upstream, and is out of scope.

## Tests

- `tests/unit_tests/ssm/ops/mamba2/test_selective_state_update.py::TestSelectiveStateUpdateAccuracy::test_fp32_state_matches_fp64` uses production shapes and dtypes (bf16 activations; fp32 A, D, dt_bias and state). A and dt_bias follow `MambaMixer`'s initialization. It covers 1 and 4 tokens and both dt/A layouts. The final state and the per-token states must be within 2x torch fp32's max-abs and rms error against an fp64 recurrence, plus one ulp. This fails on `main` and passes with the fix. On H100, all 4 cases fail on `main` (for example, broadcast decode: max-abs 2.60e-6 against a bound of 1.45e-6) and pass with the fix. GB200 is pending.
- `...::TestSelectiveStateUpdateAccuracy::test_softplus_within_4_eps_of_fp64[broadcast_dt_A|dense_dt_A]` reads the softplus out of single steps exactly and bounds it against fp64 alone, without a torch reference or the 2x factor:
  - With a zero state and x = B = 1, the new state is dt' itself. Over dt + dt_bias in [-8, 2], -20, 0 and both sides of the threshold 20, dt' must be within 4 eps. libdevice's `expf` and `log1pf` are documented within 2 and 1 ulp.
  - With a unit state and x = 0, the new state is exp(A dt') at A = -16 and dt' ~ 1e-3, where A dt' is too small for the exp2 argument rounding to matter. It must also be within 4 eps.

  On CPU under the Triton interpreter, `main` is off by up to 494 eps on dt' in the production range (and returns 0 at -20) and up to 8.1 eps on exp(A dt'). The fix is within 1.5 and 0.3 eps. This test has not run on a GPU yet.
- Determinism: `tests/unit_tests/determinism/kernels/test_ssm_kernels.py::test_selective_state_update_dense_dt_A_replays` replays the dense branch bit-exactly. The existing `test_selective_state_update_replays` covers the broadcast branch. The manifest note for `ssm_mamba2_varlen_kernels` records both. `tools/check_kernel_determinism_coverage.py` passes.

Functional goldens: only non-batch-invariant decode changes, by about an fp32 ulp of the state per step. Inference goldens compare tokens exactly and logprobs at 1e-3, so only a greedy near-tie can flip a token. The most exposed tests are `hybrid_dynamic_inference_tp1_pp1_dp8_583m` (fp32 states), `hybrid_static_inference_tp1_pp1_2B_*` and `hybrid_dynamic_inference_tp1_ep8_nanov3_chunked_prefill`. Run them once with "Run functional tests", and refresh only a test that actually flips a token.
