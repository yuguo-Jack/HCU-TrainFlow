# Capture mrope, yarn and vision RoPE inputs in TE per-layer CUDA graphs

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8671) · state: open · merged: False

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Fix Transformer Engine (TE) per-layer CUDA graphs silently dropping the rotary embedding for every position embedding type except `rope`: from the first replay on, the graphed attention of `mrope` models (Qwen2.5-VL, Qwen3-VL, Qwen3.5-VL), of `yarn` models (for example GPT-OSS) and of vision encoders graphed by `VisionTECudaGraphHelper` ran without RoPE.

:warning: For major changes (either in lines of code or in its impact), please make sure to first share a design doc with the team. If you're unsure what's the best way to do so, contact `@NVIDIA/mcore-oncall`.

## Problem

With `cuda_graph_impl="transformer_engine"` and the self-attention inside the graph (whole-layer graphs, or `attn` in `cuda_graph_modules`):

- At replay, a TE graphed callable copies only the keyword inputs it was captured with into the graph and ignores every other keyword argument (`functionalized` in `transformer_engine/pytorch/graph.py`).
- `TECudaGraphHelper._get_sample_arguments` adds a `rotary_pos_emb` sample only when `position_embedding_type == "rope"`.
- `VisionTECudaGraphHelper._get_sample_arguments` captures the vision layers with `hidden_states` and the attention mask only.

So the `rotary_pos_emb` that the model passes at every replay never reaches the graph, and nothing reports it. Affected:

- `position_embedding_type="mrope"`: the Qwen2.5-VL, Qwen3-VL and Qwen3.5-VL language models. Megatron Bridge's Qwen-VL recipes that use TE graphs over attention, including its Qwen3.5-VL performance recipes, train with NoPE attention in every graphed layer.
- `position_embedding_type="yarn"` with standard attention: for example GPT-OSS and other YaRN-scaled checkpoints, and `HybridModel` with `yarn`.
- Vision encoders that pass a rotary embedding to their layers and are graphed by `VisionTECudaGraphHelper`, such as the Qwen-VL vision towers.

Not affected: `rope` (captured), MLA (it computes its rotary embedding inside the attention), `cuda_graph_impl="local"` (`CudaGraphManager` records every tensor argument of the layer call) and `full_iteration`.

Evidence on `main`, with tiny models on one GB200 GPU and deterministic kernels: graphed replays are compared with an eager model that has the same weights, on outputs and every parameter gradient.

| Model | Graphed vs eager | Graphed vs eager with the rotary embedding removed |
|---|---|---|
| GPT, `mrope` | outputs differ by 107%, the worst gradient by 134% | bit-identical, for two batches with different position ids |
| GPT, `yarn` | 89% / 160% | bit-identical |
| ViT block with a 2D RoPE, `VisionTECudaGraphHelper` | 89% / 161% | bit-identical |
| GPT, `rope` (control) | bit-identical | - |
| GPT, `mrope`, `cuda_graph_impl="local"` | bit-identical | - |

(Relative differences: maximum absolute difference over the maximum absolute value.) The two `mrope` batches' eager outputs differ by 82%, but their graphed replays are bit-identical to each other.

Evidence at scale, from runs on a production (release-based) Megatron Core, not on `main`:

- An 8-node text-only run (Qwen3.5-VL 397B-A17B shape, 16 layers): the losses of the run with per-layer graphs leave those of an eager run at the capture iteration.
- A 1-node run with images (4 language-model layers, one of them attention, and the 27-layer vision encoder): a profile of the RoPE calls shows that none of them happen during the graph capture, so the graphs replay no RoPE kernels, neither for the language-model attention layer nor for any of the 27 vision layers. The model passes a rotary embedding to the graphed layers at every replay.

## Changes

`megatron/core/transformer/transformer_layer.py`:

- `_forward_attention` records the shape and dtype of the first `rotary_pos_emb` tensor that the layer receives in training, that is in the `cuda_graph_warmup_steps` before the capture. It already records the `padding_mask` shape the same way.
- `get_layer_static_inputs` adds a `rotary_pos_emb` graph input of that layout and dtype when the graph contains the self-attention. Its leading (sequence) dimension is the graph's sequence length per context-parallel rank.
  - Both helpers build their samples with this method. The language-model and the vision graphs therefore get the input from the same code, for any model or encoder that passes a rotary embedding to its layers, with no per-model code.
  - Each (layer, microbatch) sample gets its own buffer, because `mrope` and vision RoPE change with every batch. The helper's existing buffer reuse recycles it only after that sample's backward.
  - For `rope`, `TECudaGraphHelper` still replaces it with its sample from the model's rotary module, one buffer shared by all layers. `rope` graphs are unchanged.
- `_te_cuda_graph_capture` records whether the graph takes a rotary embedding. `_te_cuda_graph_replay` raises in two cases:
  - A replay passes a rotary embedding to a graph captured without one. This happens when no eager step before the capture passed one to the layer, for example with `cuda_graph_warmup_steps=0` or for a vision layer that saw no image. Before this change, such a graph silently ran without RoPE.
  - A replay passes none to a graph captured with one, which TE would misalign with its flattened inputs.

`megatron/core/transformer/cuda_graphs.py`: comments and the `VisionTECudaGraphHelper` docstrings only.

`docs/user-guide/features/cuda_graph.md`: a paragraph on the rotary graph input and the warmup-step requirement.

Notes for reviewers:

- Models that pass a rotary embedding other than `rope` now need at least one eager step before the capture, as the `padding_mask` input already does. The default `cuda_graph_warmup_steps` is 3, and the docs already advise against 0. Without that step the first replay raises an error that names the cause, instead of training without RoPE. For a vision encoder this means that the warmup steps must include images: with mixed text and image data, a rank whose warmup batches have none stops at its first image.
- Cost: the graphed attention now does the RoPE work that it silently skipped (the unfused RoPE: q and k, forward and backward). Measured with an earlier revision of this change (see "At scale" below):
  - At the Qwen3.5-VL 397B-A17B shape with text-only data: +0.5% step time raw, about +1.1% after adjusting for the worse routing of the unfixed run; one run per arm. An in-graph microbenchmark of the RoPE work predicts +1.3%.
  - With images, on a one-node setup that also graphs the 27-layer vision encoder: +3.5% from the RoPE work the graphs had skipped (27 vision layers and one LLM attention layer).
  - A fused MRoPE kernel could recover most of it.
- This PR does not add a generic guard that checks every replay keyword argument against the captured inputs. Such a guard needs per-layer-class allow lists for arguments that a graph legitimately does not read, and it would change behavior for every TE-graphed model. It can follow separately.

## Overlap with #8555

Draft PR #8555 ("Fix mRoPE inputs for Transformer Engine CUDA graphs") fixes the same bug for the language-model `mrope` case. It adds an `mrope` branch to `get_rotary_pos_emb` in `TECudaGraphHelper._get_sample_arguments`, which builds the sample with the model's rotary module from zero position ids, and a test that compares graphed replays at two sets of positions with eager training (within `rtol=1e-5`).

- Scope: this PR also covers `yarn` and any other rotary embedding that a model passes to its layers, vision encoders graphed by `VisionTECudaGraphHelper`, and the replay check that raises instead of dropping the input silently. Its tests compare graphed and eager bit for bit for `mrope`, `yarn`, `rope` and a vision encoder.
- Approach: #8555 builds the sample per position-embedding type from the model chunk that the helper sees, which must therefore expose `rotary_pos_emb` and `mrope_section`. Megatron Core's `GPTModel` does. Megatron Bridge's Qwen3-VL model exposes `position_embedding_type`, `rotary_pos_emb` and `decoder` to the helper but not `mrope_section` (Bridge `main` of 2026-10-28), so there the new branch would raise an `AttributeError` at capture (from reading the code; not run). This PR reserves the input in `TransformerLayer.get_layer_static_inputs` from the layout that the layer received in the eager warmup steps, the way `padding_mask` is already reserved, so both helpers share the code and no model has to expose anything. The price is the warmup-step requirement in the first note above, which #8555's `mrope` sample does not have. An earlier revision of this change built the `mrope` sample with the model's rotary module, as #8555 does; the at-scale runs below used it.

If #8555 merges first, the two diffs still apply cleanly, in either order. For `mrope`, `_get_sample_arguments` then replaces the input from `get_layer_static_inputs` with #8555's sample. Both have the shape and dtype that the model passes at replay (`[s, b, 1, d]` from the model's rotary module, split across context-parallel ranks), so the helper's sample and the recorded layout agree, each (layer, microbatch) sample keeps its own buffer, and the replay check still applies. Two follow-ups on rebase: the comment above that assignment would name `mrope` next to `rope`, and `test_replay_rotary_mismatch_raises`, which captures an `mrope` model without an eager step and expects an error, would switch to `yarn`, because #8555 gives the `mrope` graphs their input without an eager step.

## Validation

All runs used the NeMo nightly container of 2026-10-07 (PyTorch `2.14.0a0+4fdf77b940.nv26.08`, TE 2.20.2) on GB200.

**New tests.** `tests/unit_tests/transformer/test_cuda_graph_rotary_inputs.py` has 8 tests. They use the unfused attention backend and `NVTE_ALLOW_NONDETERMINISTIC_ALGO=0` so that graphed and eager runs can be compared bit for bit:

- Graphed equals eager bit for bit (outputs and every parameter gradient) over replays A, B, A whose positions differ, for `mrope`, `yarn` and `rope` GPT models and for a ViT block with a 2D RoPE graphed by `VisionTECudaGraphHelper`.
- The `mrope` input has the model's `[s, b, 1, d]` layout and its own buffer per layer. The `rope` sample is unchanged and shared.
- A capture without an eager step raises at the first replay that passes a rotary embedding (language model and vision), and a replay without one still works. A graph captured with the input raises when a replay passes none.

On this branch all 8 pass, on one GPU and on each rank of an 8-rank run (8 ranks under `torch.distributed.run`, the rank count of the H100 unit-test CI; here on 2 GB200 nodes x 4 GPUs). On `main` the same 6 fail in both setups: the `mrope`, `yarn` and vision equality tests on the numerics (98% of the logits and more than 99% of the vision outputs differ), the two capture-without-eager-step tests because nothing is raised, and the `mrope` input test because the capture samples have no rotary input. The two `rope` tests pass on both. At 8 ranks, the file followed in one pytest process by the `TestTECudaGraphHelper` tests of `test_cuda_graphs.py`, its neighbor in CI's `transformer` bucket, gives 23 passed and 3 skipped (VPP cases with PP 1) on every rank.
