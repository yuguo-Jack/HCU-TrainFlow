# Reject unsupported dynamic inference context parallelism

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8493) · state: open · merged: False

## Original PR description

## What does this PR do?

Dynamic inference keeps every request's whole sequence on each GPU. Its key/value cache and attention calls never split a sequence across a context-parallel group, or gather it back. Even so, `DynamicInferenceContext` accepted `context_parallel_size=2` and built its cache. The only check for this setting sat in a higher-level argument parser, which code that builds the engine directly never calls.

`DynamicInferenceContext` now raises a clear `ValueError` when either the model configuration or the context-parallel process group has a size other than 1. The check runs before any cache memory is allocated. An unsupported setting now fails at once instead of being silently ignored.

## Example failure scenario(s)

**Scenario (engine built directly with context parallelism 2)**

- A script starts 2 GPUs as one context-parallel group of size 2, sets `context_parallel_size=2`, and builds the dynamic engine directly with Transformer Engine attention.
- Before this change, construction succeeded, and each GPU allocated a KV cache for the complete sequences.
- Both GPUs then ran all 4 requests in full and produced identical tokens, equal to GPU 0's tokens without context parallelism, so the requested split across the 2 GPUs never happened.
- With this change, construction stops with "Dynamic inference does not support context parallelism" before any cache is allocated.

## How was this bug discovered?

A source review of how dynamic inference handles each parallelism mode found that context parallelism was only rejected by the argument parser. Nothing in the attention or cache code divides or gathers sequences across a context-parallel group, so a direct construction path had no protection.

A GPU probe on `main` then ran 4 requests through the engine with context parallelism 2 and Transformer Engine attention. Both GPUs produced identical tokens, equal to GPU 0's tokens in a run with context parallelism 1, so the setting was silently ignored. (In that run, GPU 1 was a separate data-parallel replica with different requests.) With local attention, the model cannot be built with context parallelism at all.

The regression runs on 2 GPUs inside a real context-parallel group of size 2. It requires construction to raise, and the CUDA memory in use to be unchanged afterwards, so the check fires before the cache is allocated. Without the new check, construction continues instead of raising.

## Dependency and scope

This PR is an independent fix on `main`, found by the MoE inference test series (foundation NVIDIA/Megatron-LM#8638). The change is in `DynamicInferenceContext.__init__` (`megatron/core/inference/contexts/dynamic_context.py`). It reads the explicit process-group collection when one is supplied and adds no new read of a global process group.

This update replaces the earlier single-GPU regression. That version had no real context-parallel group, so without the fix it failed later on an unrelated missing-pipeline-group assertion, not on the missing check. The new version needs at least 2 GPUs and skips on one.

Supported RL flows are not affected, because none of them hands a context-parallel model configuration to `DynamicInferenceContext`:
- Megatron RL always builds a separate inference model with `context_parallel_size=1` when training uses context parallelism (`force_cp1_inference_model` in `megatron/training/training.py`), and disaggregated inference shards also set it to 1 (`megatron/rl/inference/disagg.py`).
- NeMo-RL pins Megatron generation to context parallelism 1: `merged_inference_megatron_cfg` rejects any other value, and a colocated run whose training layout differs, which context parallelism larger than 1 always does, builds a dedicated inference model with that configuration.

It does not claim that every other inference entry point lacks context-parallel support. It also does not test a model configuration of 1 combined with a larger process group. No production code changed in this update, and there are no functional-test changes.

### 2. Measure peak allocation to enforce the before-allocation contract

The [memory assertion](https://github.com/NVIDIA/Megatron-LM/blob/2e5cfdedd6a35ae1607965b159618c7ea60159cb/tests/unit_tests/inference/contexts/test_dynamic_context.py#L153-L156) checks only live allocation after the exception. A constructor that allocates a CUDA tensor, releases it, and then raises the expected error can pass this assertion. That doesn't protect the test's stated requirement to reject before allocating the cache.

**Correction:** replace that measurement block with the following suggested code. If applying the preceding patch too, pass its `inference_config` instead of constructing one inline.

```python
torch.cuda.reset_peak_memory_stats()
allocated = torch.cuda.memory_allocated()
with pytest.raises(ValueError, match="does not support context parallelism"):
    DynamicInferenceContext(model_config, InferenceConfig(buffer_size_gb=0.01))
assert torch.cuda.max_memory_allocated() == allocated
assert torch.cuda.memory_allocated() == allocated
```

**Preservation and acceptance:** keep the matching exception assertion, final live-memory assertion, and group cleanup. The current early guard should pass without increasing PyTorch-tracked CUDA allocation. A proposed mutation that allocates and deletes a CUDA tensor immediately before the guard should fail the peak assertion even though live allocation returns to baseline. Removing the guard should still fail the exception assertion. These are source-derived acceptance checks, not executed results; verify the suggested changes before adopting them.
