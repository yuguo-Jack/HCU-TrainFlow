# Make partial_grad respect grad_comm_dtype in MFSDPv2

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8185) · state: closed · merged: True

## Original PR description

## What

`FsdpParameterGroup.allocate_partial_grad_buffer` used the dtype of the unsharded `.grad`
(bf16 for BF16/MXFP8 models) for the reduce-scatter input, so `MixedPrecisionPolicy.grad_comm_dtype`
had no effect in v2. The buffer is now allocated in `grad_comm_dtype`, falling back to the
main-gradient dtype like v1's `ParamAndGradBuffer`. 

## Why

Makes v1 and v2 reduce gradients in the same dtype so they can be compared fairly.

## Test

`tests/unit_tests/distributed/mfsdp_v2/test_grad_comm_dtype.py`: the partial buffer allocated
during backward has the policy dtype (default, bf16 override, no `main_grads_dtype`) and `.grad`
keeps the main-grad dtype. Passed on 4 GPUs.

- XiaodaNV · comment · 2026-10-15T09:29:25Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/8185#discussion_r4281310340)

File: `tests/unit_tests/distributed/mfsdp_v2/test_grad_comm_dtype.py` · line 216

The baseline needs fp32 master weights to match FSDP's main_params_dtype=fp32. 

With both models in bf16, the baseline's Adam rounds every update to bf16 while FSDP updates fp32 main params; that rounding dominated the loss difference (~1.8e-3) for both reduction dtypes, so the test could not tell them apart. 

With an fp32 master and bf16 autocast the baseline uses the same mixed-precision scheme as FSDP, the fp32-reduction case is bit-exact, and the bf16 case isolates the reduction error.
