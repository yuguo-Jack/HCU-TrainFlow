# [MFSDP] Wrap each ShortcutMoEBlock with fully_shard

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8312) · state: closed · merged: True

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

## What does this PR do?

Call `fully_shard` on each `ShortcutMoEBlock` by default, so the block owns its residual and norm parameters. Its compute and MoE transformer layers execute through helper methods that bypass their own FSDP hooks; their parameters must stay with the enclosing block. Routed experts retain a nested FSDP unit on their expert-DP mesh.

Select `TEGroupedMLP` and `SequentialMLP` directly alongside transformer layers, Mamba layers, and shortcut blocks. Ordinary `MoELayer` modules are not separate default FSDP units: their router and shared-expert parameters remain owned by the enclosing transformer layer, preserving main's grouping. An explicit `fsdp_unit_modules` list replaces the defaults and must include the expert-container types when expert and dense sharding settings differ.

`FsdpUnitCollector.collect()` returns selected units in wrapping order, children before parents with the root last, while suppressing transformer/Mamba helper layers below shortcut blocks. It preserves the existing reverse-pre-order sequence and deduplication. The adapter iterates the result directly and chooses the expert mesh from the expert-container type.

The adapter rejects `residual_stream` recomputation before sharding: stack-managed replay can read weights before their owner gathers them (#7777). Remove `residual_stream` from `recompute_modules` and clear `residual_stream_recompute_num_layers`. Other selective recomputation remains available. Layer-local replay is separate work in #8422.

The constructor registration-order change and tests that wrap norms separately are in #8505 (replacing closed #7809). This PR does not depend on that fix: its shortcut tests keep norms inside their enclosing block. Parameter locations and names are unchanged.

## Validation

The CI checkpoint failures on `6d51e2e2` exposed a circular import from the new expert-container imports through pipeline schedules and `fsdp_dtensor_checkpoint`. Import the expert types when constructing the v2 wrapper instead. On two RTX A6000 GPUs, the existing MLA checkpoint-conversion class reproduced **12 failures per rank** before the fix. With `75a859089`, the full checkpoint-conversion file plus the four MoE training/clipping cases passed **148 tests per rank**. Black, isort, Ruff, Pylint (10/10), and `git diff --check` passed. GitHub CI is pending on the corrected head.

On two RTX A6000 GPUs with NGC 26.08, the MoE training/clipping suite passed **4 tests per rank**: ordinary MoE with grouped and sequential experts, plus shortcut MoE with overlap off/on. These compare five optimizer updates against an EP=1 reference and assert the intended FSDP boundaries. Both ordinary-MoE boundary assertions fail on the previous implementation, confirming that they catch the accidental wrapper. The four cases were rerun after moving the reversal into `collect()`. Black, isort, Ruff, Pylint (10/10), and `git diff --check` passed.

Merge-queue run [40785580621](https://github.com/NVIDIA/Megatron-LM/actions/runs/40785580621) exposed exact-loss mismatches in five H100 and one GB200 DeepSeek cases. The prior revision accidentally wrapped ordinary MoE MLPs separately. That grouping change is now removed, and all six golden files have been restored to the original main versions; this PR has no golden-file changes.

On EOS (8 H100 GPUs, NGC 26.08, PyTorch `2.14.0a0+4fdf77b940.nv26.08`, Transformer Engine `2.19.0+5e52befd`), the corrected head `92e2de6c` matches the main baseline `01ac4e83` exactly at all 50 full-precision loss steps in each of the five affected H100 recipes: basic EP=2, EP overlap, MB=2, HSDP MB=2, and HFSDP MB=2. The previous revision `78670136` differs from main at 48/50 steps in the basic-case control (maximum absolute difference `0.0003762245`); the correction reduces that difference to zero. EOS jobs: `6392969_0` and `6392833_1`–`6392833_4`.

These are same-environment comparisons, not passes against the checked-in CI goldens: both the main baseline and the correction fail the original exact-loss comparison in this older EOS container. Golden values and tolerances remain unchanged. The affected GB200 recipe has not been rerun directly.

This revision has not been rerun on the full MIMO model and makes no new latency or full-model numerical-equivalence claim.
