# Resolve the schedules' process groups through one warned fallback

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8055) · state: closed · merged: False

## Original PR description

Depends on #8049 (and #6293). Please review the diff from #8049's head: [scoped diff](https://github.com/Connor-XY/Megatron-LM/compare/d89eccea46...yx/pstate-as1-schedule-groups).

**Why.** Called without `pg_collection` and `p2p_communicator`, each `forward_backward_*` schedule silently rebuilds both from `parallel_state`, with no removal date. That default collection stores the GTP-remat-inclusive data-parallel groups under `dp`/`dp_cp`, unlike `use_mpu_process_groups()`. A collection that is passed is checked with `hasattr`, which always passes, so a missing `tp` or `cp` surfaces later as an `AttributeError` on `None`, or not at all.

**What.**
- `_resolve_schedule_groups`, shared by the three schedules. Without groups it warns once per schedule (`ProcessGroupFallbackWarning`, deprecated in 0.21, removed in 0.23) and builds, through `resolve_process_groups`, only the fields that the schedules and `finalize_model_grads` read. The default communicator uses the resolved `pp` group. `dp_cp` is the replicate group; its readers use `dp_cp_gtp_remat`, so they reduce over the same ranks as before.
- A passed collection must set `tp` and `cp` (`ValueError`).
- `get_forward_backward_func` warns when it falls back to the global pipeline sizes.
- `get_pp_rank_microbatches` takes `p2p_communicator` as a required keyword argument; every caller passes one.

Global reads in `schedules.py`: 17 → 3, one of them guarded.

**Tests.** New tests check one warning per entry point with results equal to explicit groups, explicit groups with every `parallel_state` accessor patched to raise, missing fields, and the field mapping under GTP-remat 2. Before the 2026-11-01 sync, they failed on #8049's head and passed on 4 GPUs, and the schedule, a2a-overlap, pipeline-layout and full-CUDA-graph suites matched the base. In the integration run against main, `test_schedule_process_groups.py` passes all 16 tests on 4 GPUs with no regressions (the file does not exist on main). The `test_schedules.py` run on 8 GPUs (two nodes) in the integration run timed out before reporting a result.

**Compatibility.** Callers that omit the groups keep working and get one warning per entry point; stock pretrain stops hitting it with #8037, so land with or after it.

Synced with main 77391e71cc on 2026-11-01 by merging the updated base, so existing commits and review links stay valid. The only conflict was in the process-group allowlist, which now also records the reads main added since this PR was written.

Part of #6307.
