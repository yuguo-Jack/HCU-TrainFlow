# [dev] Fix a race in in-place fused MLA RoPE with remove_interleaving=False

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7789) · state: closed · merged: True

## Original PR description

Thanks @TKONIY for the contribution to this PR!

- [x] I, the PR author, have personally reviewed every line of this PR.

## Summary

The MLA query RoPE and the DSA indexer RoPE (query and key) rotate their inputs with the in-place
Triton kernels of `megatron/core/fusions/fused_mla_yarn_rope_apply.py`, using
`remove_interleaving=False`:

- the MLA query RoPE is `fused_apply_mla_rope_for_q` in `multi_latent_attention.py`;
- the DSA indexer RoPE is `DSAIndexer._apply_rope` in `dsa.py`, which calls `fused_mla_rope_inplace`
  with `rope_first=True` for the indexer query `[t, H_idx, 128]` and key `[t, 1, 128]` when
  `dsa_indexer_rope_interleaved=True`. GLM-5 sets this option (its Hugging Face config has
  `indexer_rope_interleave: true`). With the default `False`, the indexer uses
  `apply_rotary_pos_emb` instead of these kernels.

Both callers use these kernels only with RoPE fusion on (`apply_rope_fusion=True`). In training,
their backward un-rotates the incoming gradient in place with the same kind of kernel.
With `remove_interleaving=False`, the kernels write each head's channels back to different positions
of the same buffer. Nothing makes a program finish its loads before it starts its stores. With
Triton 3.6, the backward kernel at `BLOCK_H=2` splits every head between two warps. It can then
silently return wrong gradients that change from run to run. This happens when those warps drift
apart, which packed THD batches of many short sequences make likely.

The single-head DSA indexer key is the most exposed: its backward autotuner often chooses
`BLOCK_H=2`, and on packed THD batches the indexer key gradient then comes back wrong in nearly
every call.

This PR adds a `tl.debug_barrier()` before the permuting stores of both kernels, and a regression
test that fails without the barrier.

## Related work

This race is the cause of the flaky test reported in #4640
(`TestFusedApplyMLARope::test_forward_backward_for_q[thd]`, backward mismatch beyond bf16 tolerance),
and #5963 by @Sunt-ing fixes it on `main` with the same approach: a `tl.debug_barrier()` before the
permuting stores of the in-place forward and backward kernels. This PR is the `dev` counterpart; it
does not replace #5963:

- `fused_mla_yarn_rope_apply.py` has diverged substantially between `main` and `dev`, so #5963 does
  not apply to `dev`, and this patch does not apply to `main` (checked with `git apply --check`).
- On `dev`, the same in-place kernels also implement the DSA indexer RoPE (`rope_first=True`, used by
  GLM-5 with `dsa_indexer_rope_interleaved=True`). Its single-head key backward is the most exposed
  case, because the autotuner often settles on `BLOCK_H=2` for it. The `rope_first` path does not
  exist on `main`.
- The regression test added here sweeps every `BLOCK_H` from 1 to 128 for an MLA query shape and a
  DSA indexer shape, checks the in-place forward and backward against an fp32 reference and bitwise
  across repeated runs, and includes an `out=` aliasing variant. It fails on unpatched `dev` and
  passes with this fix.

If #5963 lands on `main` first, the nightly `main` -> `dev` sync will touch the same lines. Both
changes add the barrier before the same stores, so the conflict can be resolved to either version.
I am happy to rebase this PR down to the `dev`-specific test coverage, or to close it, whichever the
maintainers prefer.

## Root cause

### Mechanism

With `remove_interleaving=False`, both kernels move the RoPE channels within each head of the same
buffer:

- The forward kernel `_mla_rope_fwd_inplace_kernel` loads the interleaved pairs `(2i, 2i + 1)` and
  stores the rotated values as two halves `(i, d/2 + i)`.
- The backward kernel `_mla_rope_bwd_kernel` does the reverse: it loads the halves `(i, d/2 + i)` and
  stores interleaved pairs `(2i, 2i + 1)`. `_FusedMLARoPEInplace.backward` reaches it through
  `mla_rope_unapply_raw`.

So element `i` of the `[BLOCK_H, d/2]` tile stores into channels that other elements load. Nothing
in the kernel orders one thread's loads before another thread's stores. Whether this matters depends
only on how Triton spreads the tile over the four warps.

**Worked example: the GLM-5 DSA indexer key.** It has one head of 128 channels, of which the first
64 are rotary, so `d/2 = 32`. At `BLOCK_H=2`, Triton 3.6 compiles the backward kernel with
`threadsPerWarp = [2, 16]`, `warpsPerCTA = [1, 4]`, `order = [0, 1]`:

| warp | elements `i` | loads channels | stores channels |
|---|---|---|---|
| 0 | 0-15 | 0-15 and 32-47 | 0-31 |
| 1 | 16-31 | 16-31 and 48-63 | 32-63 |
| 2, 3 | copies of the above | (same) | none (stores are predicated off) |

Warp 0's stores to channels 16-31 can land before warp 1 has loaded them. Warp 1's stores to
channels 32-47 can land before warp 0 has loaded those. In the compiled PTX nothing sits between the
global loads and the global stores (`ld.global ... st.global`, no `bar.sync`).

The other configurations are correct only because of the compiler's layout choices:

| kernel | BLOCK_H | layout with Triton 3.6, 4 warps | result |
|---|---|---|---|
| backward | 2 | each head row is split between warps 0 and 1 | **races** |
| backward | 1 | each head row stays within one warp, whose stores depend on its own loads | correct by layout |
| forward | 1, 2 | each head row stays within one warp (`threadsPerWarp = [1, 32]`, `warpsPerCTA = [4, 1]`) | correct by layout |
| both | 4 to 128 | the stores go through a shared-memory `convert_layout`; its `bar.sync` also orders the loads before the stores | correct by layout |

### How it shows up

Nothing fails. The affected channels come back as a mix of correct values and values computed from
inputs that were already overwritten. The errors are several units, up to about 8 in testing, while
bf16 rounding is about 0.03. Which elements are wrong changes from run to run.

In training, the result is a wrong gradient for the MLA query or, when the indexer loss is on, for
the DSA indexer query or key and, through them, for the indexer's projections. There is no error and
no NaN.

### When it triggers

**Configurations that run these kernels.**

- RoPE fusion must be on: both callers check `apply_rope_fusion=True` through
  `should_use_fused_mla_rope` in `rope_utils.py`. The Megatron-LM training arguments turn it on by
  default; `--no-rope-fusion` turns it off.
- The DSA indexer also needs `dsa_indexer_rope_interleaved=True`. The default is `False`; GLM-5 sets
  it.
- The indexer's inputs are detached, and it records gradients only for its own KL loss: in training,
  with `dsa_indexer_loss_coeff > 0`. Only then does the indexer RoPE run backward, so only then can
  it race. The MLA query RoPE runs backward in every training step.

**The race.** It needs two things: the backward kernel runs at `BLOCK_H=2`, and the warps of a
program drift apart.

**Inputs that make the warps drift.** Packed THD batches of many short sequences make it likely,
because every program first walks `cu_seqlens_q`. The following was measured on the unfixed kernel
(upstream `dev` at `ac100f773`, B200, Triton 3.6.0, torch 2.11). Each cell is 20 calls on fresh
copies of one input. A call counts as wrong if it misses the fp32 formula by more than the bf16
tolerance of the test file, or differs bitwise from the first call.

| shape (backward at `BLOCK_H=2`) | 64 packed sequences | other inputs |
|---|---|---|
| GLM-5 DSA indexer query, 32 x 128, rope first | 20/20 wrong at 512, 2048 and 8192 rows | one 4096-row sequence: 13/20; SBHD 2048 rows: 2/20 |
| GLM-5 MLA query TP1, 64 x (192 + 64) | 20/20 at 512, 2048 and 8192 rows | SBHD: 0/20 |
| GLM-5 MLA query TP8, 8 x (192 + 64) | 9/20 at 512 rows, 16/20 at 1024, 20/20 at 2048, 4096 and 8192 | 4 packed sequences, 4096 rows: 3/20 to 6/20 (three measurements); SBHD 512/1024 rows: 9/20 |
| GLM-5 DSA indexer key, 1 x 128, rope first | 8/20 at 2048 rows; 20/20 at 4096, 16384 and 65536; 19/20 or 20/20 at 8192 (four measurements) | one sequence of 512 to 262144 rows: 0/20 |
| MLA query 128 x 192 and 16 x 192, DSA indexer 64 x 128 and 32 x 128 | 160/160 at 2048 and 8192 rows (all four shapes) | |

Cells with a range were measured several times. One of those measurements was an independent check
that compared every call bitwise with the same kernel's result into a separate `out=` buffer.

At 8192 rows, a wrong call had a median of about 100 wrong elements for the key and 7k to 337k for
the query shapes. In the scan of the last row, the other 47 configurations were wrong in 0 of 160
calls each. They cover the forward, the backward into a separate `out=`, both `remove_interleaving`
values and every other `BLOCK_H`.

**Whether `BLOCK_H=2` runs.** The autotuner decides. Its key is `emb_dim`, `head_num` and the
dtypes, not the row count, and its first tuning applies to every later input in the process.

- The DSA indexer key is the most exposed; it has one head at every tensor-parallel size. Its
  backward autotuner chose `BLOCK_H=2`:
  - in 18 of 40 fresh tunings on one 65536-row sequence, an input on which `BLOCK_H=2` happens to
    stay correct;
  - in 14 of 40 tunings on 64 packed sequences of 8192 rows, an input on which the key gradient is
    then wrong in nearly every call.
- Tensor parallelism divides the MLA query heads (64 / TP for GLM-5) but not the 32 DSA indexer heads,
  whose projections are duplicated across TP ranks.
- For the multi-head shapes, the autotuner chose 4 or more on inputs of 16384 rows or more. On short
  inputs, its own (warm) timings of several configurations are within a few percent of each other.
  For the GLM-5 MLA query at TP 8 (8 heads) on a 4096-row sequence, the backward autotuner chose
  `BLOCK_H=2` in one of the six performance processes below, both before and after this change.
- Context parallelism divides the rows per rank (sequence length / CP), which makes short local
  inputs more common.

### How it was found

It was found in long-sequence tests, while validating the fix for inputs of `2**31` or more elements
(#7787).
We compared these kernels bitwise at every `BLOCK_H` on MLA query and DSA indexer shapes. The
in-place backward at `BLOCK_H=2` gave different results from run to run, both before and after that
fix.

## Fix

Add a `tl.debug_barrier()` (a `bar.sync 0`) right before the permuting stores of both kernels,
after the arithmetic that consumes the loads:

- forward: in the `remove_interleaving=False` branch;
- backward: under `if not REMOVE_INTERLEAVING:`. The backward also takes the barrier when it writes
  to `out=`, because `out=` may alias the input; the wrapper only checks shape, stride and dtype.

**Why it is correct and complete.**

- A CTA barrier orders every global load of the program before every global store, whatever layout
  Triton picks. In the compiled PTX of every variant we checked (both kernels, both head layouts,
  every `BLOCK_H`), the barrier now sits between the last global load and the first global store.
- It does not depend on `BLOCK_H`, on purpose. Limiting it to `BLOCK_H <= 2` would rely on Triton
  keeping the shared-memory conversion for larger tiles.
- The forward kernel has the mirror-image hazard. It is safe today only because of its layout, so it
  gets the barrier as well.
- Only these two kernels write channels to different positions within the buffer they read. With
  `remove_interleaving=True`, every value is stored where it was loaded. The packing and key/value
  split kernels read and write different buffers.

**What it does not change.**

- Both barriers sit in `constexpr` branches. All 97 `remove_interleaving=True` variants of the two
  kernels compile to the same PTX as before. Each of the 48 `remove_interleaving=False` variants gains
  exactly one `bar.sync 0` and keeps every other instruction, so results that were not racing do not
  change.
- There is no API, argument or launch change.

## Risk and compatibility

- No API change.
- `remove_interleaving=True` kernels compile to identical PTX.
- `remove_interleaving=False` kernels gain one `bar.sync` per program and keep every other
  instruction.
- Gradients of the MLA query RoPE and DSA indexer RoPE change only where the old kernel raced. There
  it returned wrong values that changed from run to run.
- `tl.debug_barrier()` is a plain CTA barrier. The kernels no longer depend on the compiler's layout
  choices, so a future Triton version that splits head rows differently is covered too.

### [IMPORTANT Correctness] Head-block mask ignores `pid_head` (predates this PR, not in the diff, non-blocking)

This is not introduced here: base has the same lines ([fwd L178-L182](https://github.com/NVIDIA/Megatron-LM/blob/c75a269efd3fdf6d82ba5a07fff00ed40f350cba/megatron/core/fusions/fused_mla_yarn_rope_apply.py#L178-L182), [bwd L297-L300](https://github.com/NVIDIA/Megatron-LM/blob/c75a269efd3fdf6d82ba5a07fff00ed40f350cba/megatron/core/fusions/fused_mla_yarn_rope_apply.py#L297-L300)). I'm raising it because it limits the PR's claim that these kernels are race-free. It also hits the very `tl.store(..., mask=mask)` calls the new barriers protect.

**The bug.** Both in-place kernels add `pid_head * BLOCK_H * stride_x_nheads` to the base pointer, then build the mask from the *local* head index only:

- forward: [L178-L182](https://github.com/NVIDIA/Megatron-LM/blob/f3b7f60e27c84506bd6375c1882fc736c2ac1b1b/megatron/core/fusions/fused_mla_yarn_rope_apply.py#L178-L182)
- backward: [L295-L302](https://github.com/NVIDIA/Megatron-LM/blob/f3b7f60e27c84506bd6375c1882fc736c2ac1b1b/megatron/core/fusions/fused_mla_yarn_rope_apply.py#L295-L302)

```python
mask = x_off < head_num * stride_x_nheads   # x_off = arange(BLOCK_H)*stride + rope_offset
```

The grid is `cdiv(nheads, BLOCK_H)` ([L402](https://github.com/NVIDIA/Megatron-LM/blob/f3b7f60e27c84506bd6375c1882fc736c2ac1b1b/megatron/core/fusions/fused_mla_yarn_rope_apply.py#L402), [L472](https://github.com/NVIDIA/Megatron-LM/blob/f3b7f60e27c84506bd6375c1882fc736c2ac1b1b/megatron/core/fusions/fused_mla_yarn_rope_apply.py#L472)). So when `head_num > BLOCK_H` and `head_num % BLOCK_H != 0`, the last head block is never masked.

**Smallest trigger.** `head_num=48`, `BLOCK_H=32` (the autotuner benchmarks every config, so it always runs this one):

- Program `(m, 1)` processes global heads 32..63.
- With a contiguous `[rows, 48, D]` layout, heads 48..63 are really row `m+1`'s heads 0..15. Program `(m, 1)` rotates them with row `m`'s cos/sin.
- Meanwhile program `(m+1, 0)` reads and writes those same channels. The result is wrong and changes from run to run.
- For the last row, the writes go past the end of the tensor.
- The same happens for 24 heads at `BLOCK_H=16`, 40 heads at 16/32, and similar cases.

**Expected behaviour:** heads `>= head_num` are fully masked.

The concat kernel already builds the mask correctly ([L771-L772](https://github.com/NVIDIA/Megatron-LM/blob/f3b7f60e27c84506bd6375c1882fc736c2ac1b1b/megatron/core/fusions/fused_mla_yarn_rope_apply.py#L771-L772)). The CTA barrier added here cannot fix overlap between different programs.

**Who is affected.** The common per-rank head counts (16/32/64/128, power-of-two TP) are always fully covered, so they are safe. Any non-power-of-two per-rank head count that is not a multiple of the chosen `BLOCK_H` is not.

**Fix.** Use the global head index in both in-place kernels. This is a two-line change per kernel, in this PR or a follow-up; it was not compiled or run here, so please verify it.

```python
# _mla_rope_fwd_inplace_kernel, replace L182; _mla_rope_bwd_kernel, replace L302
head_idx = pid_head * BLOCK_H + tl.arange(0, BLOCK_H)
mask = (head_idx < head_num)[:, None]
```

The invariant to restore: a program touches only global heads `< head_num` of its own row.

**What the fix keeps.**

- The mask shape stays `[BLOCK_H, 1]`, so the rope loads/stores and the `COPY_NOPE` `mask & (nope_idx < nope_dim)` broadcast exactly as before.
- For `pid_head == 0` the new mask equals the old one, because `0 <= rope_offset < stride_x_nheads`.
- So every currently-correct case (power-of-two heads at every `BLOCK_H`, `_test_fused_mla_rope_inplace` with 32 heads, the new race test) computes the same mask.
- Keep the barriers added by this PR.

**Acceptance (proposed test).**

- Add `pytest.param(48, 192, False, id="mla-query-48-heads")` and `pytest.param(24, 128, True, id="dsa-indexer-24-heads")` to `test_mla_rope_inplace_channel_permutation_is_race_free`.
- Allocate `x` as `buf[:rows]` from `buf = torch.empty(rows + 1, H, D)` and assert the pad row is unchanged. That way the last row's out-of-bounds writes show up as a mismatch instead of an illegal-address error.
- Expected today: failures at `block_h=32` (48 heads) and `block_h=16` (24 heads).
- Expected after the fix: every `block_h` passes, and the 16/32-head cases still pass.

The KV-split kernels use the same masking pattern ([L1106-L1108](https://github.com/NVIDIA/Megatron-LM/blob/f3b7f60e27c84506bd6375c1882fc736c2ac1b1b/megatron/core/fusions/fused_mla_yarn_rope_apply.py#L1106-L1108), [L1216-L1218](https://github.com/NVIDIA/Megatron-LM/blob/f3b7f60e27c84506bd6375c1882fc736c2ac1b1b/megatron/core/fusions/fused_mla_yarn_rope_apply.py#L1216-L1218), [L1235-L1237](https://github.com/NVIDIA/Megatron-LM/blob/f3b7f60e27c84506bd6375c1882fc736c2ac1b1b/megatron/core/fusions/fused_mla_yarn_rope_apply.py#L1235-L1237)).
