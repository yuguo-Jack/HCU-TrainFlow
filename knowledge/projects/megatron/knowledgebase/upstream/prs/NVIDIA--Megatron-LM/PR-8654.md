# feat(moe): Qwen3.5 support and speedups for the MoK megakernel backend

# What does this PR do?

Lets Qwen3.5-VL train efficiently on the Mixture-of-Kittens (MoK) MoE megakernel backend that #8210 added to `main`: padding tokens get no routes, and the router and the megakernel can run in per-layer CUDA graphs, with less host work per call. #8210 is merged, and this PR is now based on `main`; it supersedes #8281, which GitHub closed when the mirror branch of #8210 it targeted was deleted. It has ten commits, meant to be reviewed one at a time; commit 8 adds the determinism test that the `linting` job requires for two of the changed files, and commits 9 and 10 address the automated review. The rebase onto `main` is described in its own section below.

## Summary

#8210 adds MoK as an MoE backend on `main`. Its final version also accepts Qwen3.5's shared-expert output gate, keeps the routes dense for megakernel backends, and pins MoK 7a8cfb7 in the CI image; `main` also counts the per-token auxiliary-loss tokens on the device (#8217). With that, Qwen3.5-VL runs on MoK, but the path is slow:

- **Padding.** In the padded Qwen3.5-VL training measured here, about 94% of the routed rows were padding tokens, and the megakernel computed all of them (commits 3 and 6).
- **Host overhead.** #8210 rejects per-layer CUDA graphs that touch the MoE layer for MoK. The router and MoK's per-call host work ran eagerly in every MoE layer and microbatch, and the 397B step was host-bound (commits 2, 4, 6 and 7).

**Headline results.** Qwen3.5-VL training on GB300, MoK against native MoE on the same batch, in the full configuration: this PR with #8210 and the related PRs below. The qualifiers are under Performance.

| model | at the start of this work | final |
|---|---|---|
| 35B, 8 GPUs, EP4 | -15% to -21% | +39.3% |
| 397B, 64 GPUs, EP32, forced load balancing | +2.9% | +63.8% / +64.7% (two runs, earlier build) |

**Caveat found after these measurements.** Both arms used Transformer Engine per-layer CUDA graphs for attention. In current `main` these graphs do not capture MRoPE (`position_embedding_type="mrope"`), so Qwen3.5-VL's full-attention layers ran without rotary embeddings after graph capture; a fix is being prepared as a separate MCore PR. The skipped work is the same in both arms, so the comparison stays like-for-like, but with the fix both arms do slightly more work, which lowers MoK's relative gain somewhat. The numbers will be re-measured once the fix lands.

In a 500-step 35B convergence A/B with two seeds, MoK's mean LM loss over the last 100 steps was within or below the spread of two native variants.

- **Bridge PR**, NVIDIA-NeMo/Megatron-Bridge#6496 (merged): *feat(model)!: pass a padding mask to Qwen3-VL MoE layers and run the vision merger on graph-padded rows*. ### 1. test(moe): cover moe_router CUDA graph capture of the per-token aux-loss scale

Files: `test_routers.py`.

- **Why.** With `calculate_per_token_loss`, `TopKRouter.attach_and_log_load_balancing_loss` scales the auxiliary loss by the number of local tokens. When that count is a Python `int`, the shape-derived count used when no padding mask is passed, the router used to build the scalar with `torch.tensor(num_local_tokens, device=...)`, a copy from host memory that a CUDA graph cannot record. With the router inside a per-layer Transformer Engine graph (`cuda_graph_modules` containing `moe_router`, or `moe`), capture failed with `Cannot copy between CPU and CUDA tensors during CUDA graph capture`; Qwen3.5-VL 397B training on the native MoE path, with per-token loss, the global auxiliary loss and `[attn, moe_router]`, failed this way. `main` now fills the scalar on the device (#8217). Before the rebase, this commit made the same change.
- **Change.** Tests only. #8217's own test captures the router with `seq_aux_loss` in the determinism suite; these tests also cover `aux_loss` and `global_aux_loss`, compare the replay with eager execution, and check the integer-count path end to end.
- **Evidence.** The 4-layer Qwen3.5-VL 397B smoke at EP32 on 32 GB200 GPUs with `[attn, moe_router]` and per-token loss, and the full-size 397B MoK runs on 64 GB300 GPUs, ran with this commit's former `router.py` change, which differs from #8217's only in that #8217 spells out the int64 dtype.

- **Unit tests** (`test_routers.py`, new class `TestPerTokenAuxLossCudaGraph`).

### 2. feat(moe): allow the moe_router CUDA graph scope with the MoK backend

Files: `transformer_config.py`, `moe_layer.py`, `transformer_layer.py`, MoE README.

- **Why.** #8210 rejects every per-layer CUDA graph scope that touches the MoE layer for MoK: `moe`, `moe_router` and `moe_preprocess`. The router, with its gating GEMM, top-k, auxiliary losses and their logging, therefore always ran eagerly, paying its kernel launches and Python on the host in every MoE layer and microbatch.
- **Change.** The router is captured as for the native dispatchers: the layer's TE graph ends after the router and returns its outputs, and the megakernel runs eagerly after the replay, on those outputs. `TransformerConfig` accepts `moe_router` for MoK with `cuda_graph_impl='transformer_engine'`. `moe_preprocess` stays rejected, and so does `moe` until commit 7. With per-token loss and no padding mask, the capture relies on #8217 on `main`.
- **Evidence.** A 4-layer Qwen3.5-VL training check ran `[attn, moe_router]` and `[attn]` on the same code: the loss is identical at steps 1 and 2, and later steps differ within MoK's run-to-run variation. All later MoK training used `[attn, moe_router]`, or `[attn, moe]` from commit 7.
- **Known limitations, not changed here:** a stale error text; a `pre_mlp_layernorm` recompute request that is silently dropped with the router graph; `mlp_chunks_for_training > 1`, which fails at capture, as on the native path. See the details.

<details><summary>Details of commit 2</summary>

- **Partial capture.** While the `moe_router` scope is captured, the router raises `MoECudaGraphPartialCaptureSignal`. `MoELayer`'s megakernel branch now catches it and returns the partial-capture outputs, without a shared-expert output, because MoK computes the shared expert inside the megakernel. For megakernel layers, `TransformerLayer` therefore adds no shared-expert graph submodule and pops no shared-expert output from the graph outputs on replay.
- **Config.** The `moe_router` scope is rejected for MoK with the local implementation.
- **README.** The MoK support table lists per-layer TE capture with the `moe_router` scope. In the list of unsupported features, "partial MoE CUDA Graph replay" becomes "the `moe_preprocess` CUDA Graph scope".
- **Training check.** An exact repeat of the `[attn]` run differed from the first run by as much as the two arms differed at later steps.
- **Unit tests** (`test_mok_weights.py`). `test_mok_accepts_transformer_engine_moe_router_cuda_graph` and `test_mok_rejects_local_moe_router_cuda_graph`. The existing reject test now covers `moe` and `moe_preprocess`; it lost its `moe_router`-only cases.
- **Known limitations.**
  - The error raised when a megakernel layer receives intermediate tensors still says "remove moe_router/moe_preprocess". Only `moe_preprocess`, which the config rejects, could lead there now.
  - With MoK and the router graph, a `pre_mlp_layernorm` recompute request is silently dropped.
  - `mlp_chunks_for_training > 1` with a TE `moe_router` graph fails at capture. The native path already fails the same way.

</details>

### 3. feat(moe): give padding tokens no routes in the MoE megakernel path

Files: `moe_utils.py`, `moe_layer.py`.

- **Why.** The router keeps padding tokens in its routes and only excludes them from its statistics. The native dispatchers receive the padding mask and can skip padded rows, as dropless HybridEP does. The megakernel path, however, handed the full routing result to the backend, which dispatched and computed every padding token.
- **Change.** New `moe_utils.drop_padding_routes(routing_probs, routing_map, padding_mask)` returns copies of the dense routing result with the rows of padding tokens zeroed: probs 0 and routing map False. The megakernel path applies it right after `route()` whenever a `padding_mask` is passed. That also covers the unmasked router outputs that a `moe_router` graph replay returns. As with dropless HybridEP, padding tokens then get no routes, and their routed output is zero. Nothing changes unless the caller passes `padding_mask`.
- **Evidence.** In 4-layer training checks, 35B at EP4 and 397B at EP32, native MoE and MoK each had a bit-identical LM loss at steps 1 and 2 with and without the mask. The forward pass of the real tokens therefore did not change; later steps differ slightly.
- **Risk: training semantics.** With a mask, the router's auxiliary-loss statistics exclude padding. The router already does that whenever it receives a mask, but turning the mask on changes training slightly. The mask is opt-in on the caller's side, off by default in the Bridge PR (its commit 3), and model owners should sign off before a recipe enables it by default.

<details><summary>Details of commit 3</summary>

- **Mask layout.** `padding_mask` is batch-first `[bsz, seq]`, with True marking padding. Tokens are flattened sequence-first, as in the hidden states.
- **Placement.** #8210's `route(..., packed_seq_params=...)` call in `megakernel_forward` is kept, and the masking follows it.
- **Cost.** The copies cost one pass over the `[tokens, experts]` probs and routing map per MoE layer, until commit 6 removes them.
- **Unit tests** (`test_moe_layer.py`).
  - `test_megakernel_receives_no_padding_routes[eager|recompute|moe_router_graph_replay]`: the backend receives no routes for padding tokens, and the router call counts match each path.
  - `test_megakernel_moe_router_graph_capture_outputs_unmasked_routes`: a `moe_router` capture returns the unmasked router outputs and does not run the backend.
  - The existing megakernel routing test checks the masked routes. #8210's packed-metadata test in `test_mok_megakernel.py` compares the routes the backend receives by value, because they are now masked copies.

</details>

### 4. perf(moe): cache MoK parameter, main-grad and gradient-sentinel state across calls

Files: `mok/backend.py`, `mok/runtime.py`, `parameter_bridge.py`.

- **Why.** `MoKMegakernel` rebuilt host-side state on every forward and backward: the routed parameter tuples (2 × `num_local_experts` parameters with split expert weights), the main-grad validation and split descriptor tables, and one gradient sentinel per parameter. The autograd function also saved every routed parameter for backward. With many local experts, this host work outweighed the MoE layer's GPU time once padding rows were skipped, so the GPU waited for the host.
- **Change.** The parameter tuples and the sentinel buffers are resolved once. The validated main-grad arguments are cached while every parameter keeps the same `main_grad` object at the same address. `_reset_derived_state()` drops all of this state, and `load_state_dict` and `_apply` call it. Only `x`, the router weights, the optional shared-expert gate weight and the shared expert weights are saved for backward. Each gradient sentinel becomes an alias of one shared buffer per (shape, dtype, device), like Transformer Engine's `get_dummy_wgrad`.
- **Evidence.** In a single-MoE-layer harness on 4 GPUs (GB200), EP4, at Qwen3.5-VL MoE shapes, all 548 gradient tensors are bitwise identical before and after this change.
- **Risks.**
  - **Memory.** The sentinel buffers live for the process lifetime: one uninitialized, parameter-sized buffer per distinct (shape, dtype, device), shared-expert weights included. With single grouped expert weights, that is about one layer's routed and shared expert weights. Before, the sentinel aliased the parameter's own storage. TE's `get_dummy_wgrad` makes the same trade.
  - **Cache validity.** The cache relies on DDP assigning each `main_grad` once. Every call checks the cached arguments by object identity and data pointer, and rebuilds them when either changes.

<details><summary>Details of commit 4</summary>

- **Sentinels.** `param.detach()` allocates nothing, but on a quantized (MXFP8) parameter it builds a tensor subclass in Python, and AccumulateGrad's steal builds a second one. Now `dummy_weight_gradient_buffer` returns one uninitialized buffer per (shape, dtype, device), and `dummy_weight_gradient` returns a fresh detached alias of it. `AccumulateGrad` steals the alias into `.grad` without a copy, also for MXFP8 parameters. All parameters of the same shape share the buffer, and its values are never read. The shared-expert weights and the gate get sentinels through `finish_weight_gradient`.
- **Main-grad cache.** The cached arguments include the split descriptor tables. A replaced `main_grad` or moved storage, for example after a grad-buffer offload and reload, rebuilds them, and a missing `main_grad` still raises.
- **Resets.** `_reset_derived_state()` also drops the weight views. In `_apply` it replaces #8210's three invalidation lines; it clears the same state plus the new caches. Commit 7 adds a guard that refuses this reset while a CUDA graph holds the cached views, and commit 9 makes `_apply` run the reset before the conversion.
- **Saved tensors.** Backward reads the routed weights through the cached views. The routed parameters stay autograd inputs, so each one's `AccumulateGrad` node, and with it the DDP hook, still fires.
- **Unit tests** (`test_mok_megakernel.py`).
  - `AccumulateGrad` steals the sentinel under a DDP-style hook, for a BF16 and an MXFP8 parameter, and no quantized tensor is constructed.
  - The parameter tuples are resolved once, and again after `_apply`.
  - The main-grad arguments are reused until a `main_grad` is replaced, its storage moves or it disappears.
  - The autograd function saves only the backward inputs and still delivers a gradient to every routed parameter.
  - #8210's dtype-conversion (`_apply`) test and the checkpoint test check that every cached field is reset; #8210's gate autograd test no longer sets the descriptor cache that this commit replaces.
  - `test_parameter_bridge_uses_main_grad_and_a_cached_dummy_gradient` replaces `..._without_allocating_dummy_storage`.

</details>

### 5. test(moe): port the remaining #7391 tests for the MoK shared-expert output gate

Files: `test_mok_megakernel.py`. Tests from #7391 (see Credits).

- **Why.** Qwen3.5 gates the shared expert's output with a learned per-token sigmoid gate (`moe_shared_expert_gate`). #8210 ported #7391's in-kernel gate to `main`, with one autograd test for split BF16 weights. Before the rebase, this commit carried the same port; its production code equaled #8210's apart from comments, and the gate path at this PR's tip makes the same MoK calls as before the rebase.
- **Change.** Tests only: the #7391 tests that the port did not carry over. They build the real adapter against a mocked `mok` package.
  - A gate weight that is not a native, contiguous BF16 `Parameter` is rejected.
  - Gate gradients accumulate into `main_grad` across microbatches and after zeroing, with MCore DDP's forward pre-hook and backward post-hook wired to the gate, for BF16 and MXFP8 and for split and single grouped weights.
  - A missing gate `main_grad` raises before MoK is called.
- **Evidence** for the gate path, collected on this commit's former port with the real MoK kernels. The ungated path is bitwise equal to the code before the port, at the 35B shape at EP4 and at the 397B shape at EP4 and EP32. On the gated path (35B and 397B shapes, EP4 and EP32), the routed weight gradients and `d_probs` are bitwise equal to the gate-off results, padding rows are exact, and recompute is bitwise. The gate gradient has the same error against an exact reference as native BF16 autograd.

### 6. perf(moe): fold the padding mask into MoK route compaction and cut per-call host work

Files: `megakernel/backend.py`, `mok/route_adapter.py`, `mok/backend.py`, `mok/runtime.py`, `moe_layer.py`.

- **Why.** After commits 3 to 5, each MoK call still did avoidable host and memory work. It built commit 3's masked copies of the `[tokens, experts]` probs and routing map, and autograd materialized a zero gradient for the integer route indices, which nothing reads. The shared FC1 gate/up views and the main-grad arguments in MoK's six-buffer order were rebuilt on every call, so MoK validated new tensor objects each time. MoK also zeroed the router-weight gradient at unrouted slots, which the route adapter never reads. The 397B configuration was host-bound at this point, so host time per call translated directly into step time.
- **Change.**
  - `MegakernelBackend.forward` takes an optional batch-first `padding_mask`. `MoELayer` passes the mask to the backend instead of calling `drop_padding_routes`, which remains the reference implementation used by the tests.
  - The Triton route-compaction kernel (`RoutingMapToIndices`) drops the routes of padding tokens while it compacts them. Values and the `probs` gradient equal those of `drop_padding_routes` followed by compaction.
  - The indices gradient is no longer materialized, and the views and main-grad arguments are cached. `_MoKWeightArguments.from_combined` takes the cached gate/up views. `zero_unrouted_router_grads=False` is passed to `mok.functional.backward` when the installed MoK accepts it; older MoK builds work unchanged.
- **Evidence.** At the MoE-layer level, this commit with the MoK PR's eager host path installed is bitwise identical to the previous commit with the earlier MoK build. The check covers outputs and all gradients, including recompute and step boundaries, on every rank, at the 35B shape and a 397B proxy on 4 GPUs (GB200), and at the real 397B shape at EP32 on 32 GPUs (GB200). With `zero_unrouted_router_grads=False`, filling MoK's router-gradient buffer with NaN before backward changes no result.
- **Risks.**
  - **Interface change.** `padding_mask` is now an optional part of the `MegakernelBackend.forward` interface. Any other megakernel backend must accept it and give padding tokens no routes.
  - **Test-only helper.** From this commit on, `drop_padding_routes` is used only as the reference in tests; its docstring describes commit 3's direct use until commit 10 rewrites it as reference semantics. It stays in `moe_utils` as the reference semantics that the new `MegakernelBackend.forward(padding_mask)` contract requires of any other backend, and it can move to the tests if reviewers prefer. Commit 8 adds its determinism replay test.
  - **Teardown hang.** One 397B run with these host cuts hung at process teardown after it had finished training. The other 397B runs with them exited cleanly, and the hang was not reproduced.

<details><summary>Details of commit 6</summary>

- **Indices gradient.** `RoutingMapToIndices` calls `ctx.set_materialize_grads(False)` and handles a missing `probs` gradient.
- **Cached arguments.** The shared FC1 gate/up views are valid while the parameter object and its storage address are unchanged. With them and the main-grad arguments cached, MoK receives the same tensor objects on every call and validates them once. The routed FC1 payload is passed directly as both gate and up, as `_gate_up_weight_arguments` already did.
- **Backward option.** Whether the installed `mok.functional.backward` accepts `zero_unrouted_router_grads` is detected once per installed function, from its signature.
- **Numerics test.** In #8210's `test_real_mok_ddp_numerics`, the gate/up mutation control now swaps the views that `shared_fc1_gate_up()` returns; patching the per-call split no longer reaches MoK once the views are cached.
- **Unit tests.**
  - `test_multihot_indices_converter.py`: the in-kernel mask matches `drop_padding_routes` followed by compaction in values, indices and `probs` gradient, for boolean, integer and strided masks; the mask is validated; backward creates no zero-filled indices gradient.
  - `test_mok_kernels.py`: the bit-exact replay of the compaction kernel gains a `padded` parameter, which uses a strided padding mask.
  - `test_moe_layer.py`, `test_mok_megakernel.py`: the mask reaches the backend; the cached arguments, views and backward options are covered. #8210's packed-metadata test now asserts that the backend receives `(hidden, probs, routes, padding_mask)`.

</details>

### 7. feat(moe): capture the router and MoK megakernel in per-layer TE CUDA graphs

Files: `transformer_config.py`, `module.py`, `cuda_graphs.py`, `transformer_layer.py`, `megakernel/backend.py`, `mok/backend.py`, MoE README.

- **Why.** With `[attn, moe_router]`, the megakernel still runs eagerly after each graph replay, so its Python host work and kernel launches stay on the critical path of every MoE layer and microbatch. That cost dominates at the 397B shape, which is host-bound.

## Risks and limitations

- **`moe` scope warm-up without a padding mask.** Unless `moe_router_force_load_balancing` is set, the `moe` scope needs a `padding_mask` model input during the eager `cuda_graph_warmup_steps`. The all-True warm-up mask exists only when the layer saw a padding mask during those steps. Without one, which is the usual case in LLM pretraining, TE's warm-up still sends every token to the same experts under real routing. That can exceed MoK's schedule capacity and stop the run with a device-side trap at capture, as in commit 7's negative control. Every validated configuration either passed a padding mask or used forced load balancing.
  - The README's MoK CUDA Graph row states this requirement.
  - Nothing in the code checks it yet. A follow-up should raise or warn at capture when a graphed megakernel layer has seen no padding mask, or give such layers an internal all-padding warm-up mask.
- **`moe` scope and pipeline parallelism.** The `moe` scope is rejected with `pipeline_model_parallel_size > 1`, because every validation of it ran without pipeline parallelism. There, each microbatch's backward runs before the next microbatch replays the layer's graph. With pipeline parallelism, MCore captures one graph per layer and microbatch, which may already keep each in-flight microbatch's MoK state apart, but that is untested. The `moe_router` scope is not affected.
- **Memory.** With the `moe` scope, reserved memory is about 10% higher at 397B, because the graph pool keeps MoK's per-layer context alive. Commit 4's sentinel buffers are covered with that commit.
- **Training stability.**
  - Across the shorter (150-step) 35B runs, MoK runs entered phases of elevated load-balancing loss, some with grad-norm spikes, more often than native runs.
  - That comparison is confounded by initialization. The native recipe uses GLU-interleaved FC1 weights, which MoK does not support, and the native runs with MoK's weight layout also showed the elevated load-balancing loss.
  - The 500-step A/B includes such a layout-matched native arm, and no MoK run there showed such a phase. A larger layout-matched comparison has not been run.
- **Not re-measured after the rebase onto `main`.** The throughput runs, the bitwise harnesses and the training smoke ran on the code before this rebase. MoK receives the same arguments as there, and the remaining differences are #8210's own later changes (see Rebase onto main).
- **Test coverage.** The new tests ran on GB200 only, with MoK 7a8cfb7 and with the MoK PR's build. In CI, the GB200 unit-test buckets launch only tests marked `launch_on_gb200`. Of the changed test files, only #8210's `test_mok_numerics.py`, whose mutation control commit 6 adapts, carries that marker; the other new tests run only in the H100 buckets, whose images have no MoK. The new MoK tests use fake `mok` modules and Blackwell or TE-version skips, and commit 1's tests need no MoK, so they should pass there, but that is unverified. Commit 8's tests need neither MoK nor Blackwell; they run in the H100 determinism-kernel bucket. Watch the H100 unit-test buckets.
- **Per-commit risks** are listed with each commit: the router-scope limitations (2), the training semantics of the mask (3), sentinel memory and cache validity (4), and the backend interface, the test-only helper and a one-off teardown hang (6).

### Reject captured-weight conversions before modifying parameters

In [MoKMegakernel._apply](https://github.com/NVIDIA/Megatron-LM/blob/3998e7f5bb0e8eb4cb691430d13aa16dd3c85c90/megatron/core/transformer/moe/megakernel/mok/backend.py#L465-L500), the captured-view guard runs **after** `super()._apply(...)`. With `_weight_views_captured=True`, calling `backend.float()` converts its BF16 parameters and then raises from `_reset_derived_state()`. The operation reports refusal, but parameters have already changed while cached views and captured graphs reference the previous storage. Expected behavior is to reject the backend conversion without changing parameters or caches.

**Correction:** move `_reset_derived_state()` before the snapshots and conversion, removing its trailing call. This restores the backend-local invariant that the captured-view error precedes parameter mutation. Suggested edit, not executed; verify before adopting:

```diff
@@
-        snapshots = {
+        self._reset_derived_state()
+        snapshots = {
@@
-        self._reset_derived_state()
         return out
```

**Preservation:** uncaptured conversions must still preserve aliased-parameter metadata and invalidate all five derived caches. Graph deletion must continue releasing the pin so subsequent conversions succeed. This backend-local check should not be treated as a model-wide preflight: native parameter owners can be visited earlier during a containing model’s conversion.
