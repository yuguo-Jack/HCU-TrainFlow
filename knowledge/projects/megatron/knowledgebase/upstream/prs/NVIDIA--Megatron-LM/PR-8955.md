# [Inference][MoE] Propagate NaN through the inference squared-ReLU kernels

# What does this PR do?

Makes Megatron's own Triton squared-ReLU kernels for inference MoE keep a NaN FC1 output NaN, as training's `F.relu` does. Before this change, a token whose FC1 output was NaN got a finite (zero) MoE output.

Stacked on #8566 (https://github.com/NVIDIA/Megatron-LM/pull/8566, `fix/d2-moe-glu-options`). #8566 changes two of the three kernels fixed here (`_squared_relu_with_probs_kernel` gains `APPLY_PROBS`, `_fused_moe_kernel` gains `MUL_ROUTED_WEIGHT_ON_INPUT`). Its gated squared ReLU (`squared_relu_glu`) already uses the NaN-propagating ReLU this PR applies to the non-gated kernels. #8871 (stacked on #8566) and #8868 do not touch these kernels, and this branch merges cleanly with both and with `main`. It has a one-hunk conflict in `tests/unit_tests/determinism/kernels/manifest.py` with the sibling fix `fix/mxfp8-quant-tiny-scales-strides`: both extend the `inference_moe_kernels` notes. Whichever lands second keeps both sentences. `activations.py` merges cleanly with that branch.

**Bug.** Every non-gated Triton squared-ReLU kernel in `megatron/core/inference/moe/` computed the ReLU as `tl.maximum(x, 0.0)`. Triton's default `propagate_nan=NONE` lowers that to `maxnum`, which returns the non-NaN operand, so `relu(NaN)` was 0. This affected squared-ReLU MoE models (for example Nemotron 3 Nano), clamped (`activation_func_tanh_clamp_scale`) and unclamped. The affected kernels are these three:

- the vLLM backend's FC1 epilogue (`_fused_moe_kernel`, `FUSE_SQUARED_RELU`);
- the torch backend's `padded_squared_relu` and fused `squared_relu_and_quantize_mxfp8` (both through `_clamped_relu`);
- the batch-invariant `squared_relu_with_probs`, used by both backends.

A NaN from upstream (an overflowed FC1 GEMM, a bad weight) was silently replaced by a zero expert contribution. Training (`squared_relu`, `weighted_squared_relu`, `weighted_clamped_squared_relu`, all `F.relu`), the SwiGLU kernels and the gated squared ReLU propagate it. Confirmed on H100 (vLLM path: all 128 outputs of the NaN token finite where the reference is NaN) and GB200 (MXFP8 path: the NaN element decodes to 0.0).

## Fix

- Pass `propagate_nan=tl.PropagateNan.ALL` at the three ReLU sites. It lowers to `maximumf`, emitted as `max.NaN.f32` on sm_80 and later. That is one instruction, as before, so the hot path is unchanged.
- Infinities are unchanged (`relu(+inf)^2 = inf`, or `s^2` with the clamp; `relu(-inf) = 0`). `-0.0` squares to `+0.0`, as in torch.
- No other kernel under `megatron/core/inference/` computes a ReLU this way.
- The FlashInfer backends (`inference_grouped_gemm_backend='flashinfer'`) are outside this PR. These are the routed MXFP8 and NVFP4 `Relu2` paths and CUTLASS `ClampedRelu2`. FlashInfer computes their squared ReLU inside its own kernels; Megatron only selects the activation type. This PR neither changes nor tests their NaN handling, which is checked separately.
- `experimental_attention_variant/dsa_min_memory_triton.py` (lines 840 and 953, the DSA indexer's `relu(q.k)`) has the same pattern. It is out of scope here.

## Tests

These fail on the base branch and pass with the fix:

- `tests/unit_tests/inference/test_moe_permute.py::test_squared_relu_propagates_nan[padded_squared_relu|squared_relu_with_probs, unclamped|clamped]`: inputs with NaN, +inf, -inf and -0.0 must match training's squared ReLU (`squared_relu`, `weighted_squared_relu`, `weighted_clamped_squared_relu`). The NaN positions must match, and every other element must match bit for bit.
- `tests/unit_tests/inference/test_mxfp8_utils.py::test_squared_relu_and_quantize_mxfp8_propagates_nan[unclamped|clamped]`: NaN inputs must quantize to the E4M3 NaN. The fused kernel must still match the unfused route (`padded_squared_relu` then MXFP8 quantization) bit for bit.
- `tests/unit_tests/inference/test_vllm_fused_moe.py::TestVllmFusedMoe::test_nan_token_propagates[unclamped|clamped]`: a NaN in one token's hidden state must make that token's whole MoE output NaN and leave every other token bit-identical.

Determinism: `tests/unit_tests/determinism/kernels/test_inference_kernels.py::test_squared_relu_special_values_replay` and `::test_vllm_fused_squared_relu_special_values_replay` replay the four kernels bit-exactly on inputs that contain NaN, infinities and -0.0. The manifest note for `inference_moe_kernels` records this. `tools/check_kernel_determinism_coverage.py --base-ref fix/d2-moe-glu-options` passes.

Checked on CPU under the Triton interpreter. On the base branch the NaN outputs are 0 (vLLM: the NaN token's row is all zeros; MXFP8: code 0x00). With the fix they are NaN and the other rows are unchanged. On H100, all 12 regression cases and the neighbor tests pass, and the new tests fail on the base as expected. The GB200 run is pending.
