# [Inference] Restore the batch-invariant collective when leaving a set_batch_invariant_mode scope

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8573) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Makes `set_batch_invariant_mode` keep the batch-invariant collective along with the mode and backend, so toggling the mode no longer switches a `"multimem"` run to `"ordered"`. It also makes a failed `enable_batch_invariant_mode` roll back instead of leaving the mode half on.

**Bug.** `set_batch_invariant_mode(False)` inside an enabled scope disables the mode on entry and re-enables it on exit with `enable_batch_invariant_mode(backend=prev_backend)`. That call does not pass `collective`, so it falls back to the default `"ordered"`. A process that enabled batch-invariant mode with `collective="multimem"` (`--batch-invariant-collective multimem`) silently changes collective after any nested disable:
- the inference EP combine switches from `multimem_reduce_scatter_v` to `ordered_reduce_scatter_v` (`token_dispatcher_inference.py`);
- the batch-invariant MoE reference switches its cross-rank accumulation from fp64 to fp32 (`moe/batch_invariant.py`).

No in-tree caller nests a disable inside an enabled scope, so the trigger is an external caller such as an RL framework that toggles the mode around a training step.

**Root cause.** The context manager saved the on/off state and the backend, but not the collective. Related gaps:
- An outermost `set_batch_invariant_mode(True)` scope always enabled `"ordered"`, and on exit it left its own backend and collective (`"triton"`, `"ordered"`) behind instead of the values it found. A run configured with `"multimem"` that disables the mode and re-enters it through the context manager therefore also switched to `"ordered"`.
- `enable_batch_invariant_mode` sets the mode flag and registers the aten library before steps that can raise (TE patch, Mamba autotuner pin). A failure there left the mode on with some patches applied and nothing to undo them. It also stored the collective before validating the backend, so a rejected enable still changed the collective.

**Fix** (`megatron/core/transformer/custom_layers/batch_invariant_kernels.py`):
- `set_batch_invariant_mode` saves the collective next to the backend and restores both in its `finally`, so they are restored whether the scope ends normally or by an exception. A nested disable re-enables with the enclosing backend and collective. An outermost enable disables the mode and puts back the previous backend and collective.
- `set_batch_invariant_mode` takes an optional `collective`. When the mode is off on entry, it enables the collective the process last enabled the mode with (initially `"ordered"`, so existing callers see no change). Inside an active scope a different collective is rejected, the same as a different backend. The backend default stays `"triton"`, the documented helper default for tests that exercise non-bf16 operators.
- `enable_batch_invariant_mode` validates its arguments before changing any state. If a later step raises, it undoes the steps that already ran (through `disable_batch_invariant_mode`) and restores the previous backend and collective before re-raising. This also covers entry into `set_batch_invariant_mode`, which enables through it.

No hot-path change: this code only runs when the mode is toggled.

**Tests** (`tests/unit_tests/transformer/test_te_layers_batch_invariant.py`, no GPU work):
- `test_set_batch_invariant_mode_nested_restores_enclosing_state[ordered|multimem]`: a nested enable, a nested disable, and a nested disable left by an exception all restore `(mode, backend, collective)`. A nested scope that asks for a different collective is rejected.
- `test_set_batch_invariant_mode_outermost_restores_disabled_state`: an outermost scope leaves the disabled backend and collective unchanged whether it ends normally, ends by an exception, or is rejected for an unknown backend.
- `test_set_batch_invariant_mode_keeps_configured_collective[ordered|multimem]`: re-entering from disabled enables the collective the process was configured with.
- `test_enable_batch_invariant_mode_rolls_back_on_failure`: when the last enable step fails, both a direct call and `set_batch_invariant_mode` entry leave the previous state and restore `CUBLASLT_WORKSPACE_SIZE`.

On H100 in the CI image (`mcore_ci_dev:main`, torch 2.14, TE 2.20.2), the first commit's tests (the two nested cases and the outermost test) fail on main in 2 cases (`nested_restores_enclosing_state[multimem]`, `outermost_restores_disabled_state`) and all 3 pass with this PR. The `ordered` case passes on main, which is why the existing tests, all on the default collective, did not catch the bug. The neighbor tests `test_te_layers_batch_invariant.py` (31 passed, 1 skipped), `test_vllm_fused_moe_batch_invariant.py::TestTeNativeBackend` and `tests/unit_tests/rl/test_rl_batch_invariant.py` pass. On the rerun at this PR's head, the regression tests pass (6/6), 6 fail on main, and the neighbor tests pass. On CPU (TE patch stubbed), all 6 test cases pass with this PR and fail on main.
