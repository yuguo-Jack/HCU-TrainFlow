# fix(ssm): batch-invariant Mamba decode without a z replay buffer

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8221) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

# What does this PR do?

Batch-invariant Mamba decode no longer keeps a `z` replay buffer: the chunk scan gates only the target row, so it reads the current token's `z` directly. Outputs are bitwise unchanged; per-request decode memory drops by `chunk_size x d_inner x dtype bytes` per Mamba layer.

A second commit replaces the decode step's tile kernels with row kernels that compute only the consumed row (bitwise the same; about 1.9x faster per Mamba layer at 64 to 256 rows), and fuses the step's bookkeeping into one kernel.

## Problem

`BatchInvariantDecodeBuffers` stores x, z, dt, B and C for every token of the current chunk, per request slot and Mamba layer, so decode can replay the training chunk scan for one row. `z` is not needed for that. In `_chunk_scan_fwd_kernel`, z only enters through the row-local gate `acc *= z * sigmoid(z)`. In target-rows mode (the decode path), only the target row is stored. So no buffered z row other than the current token's ever reaches an output.

The z buffer is `max_requests x chunk_size x d_inner` per layer, the same size as the x buffer. Per request slot (chunk 128; ssm state fp32, as batch-invariant mode requires):

| per-rank shape (TP=1) | z buffer per slot, bf16 / fp32 activations | per sequence at 8k context, before -> after (bf16) |
|---|---|---|
| Nemotron-3-Nano-30B (23 Mamba layers, 64 x 64 heads) | 23 / 46 MiB | 153 -> 130 MiB (+18% sequences per GPU) |
| Nemotron-3-Super-120B (40 layers, 128 x 64) | 80 / 160 MiB | 408 -> 328 MiB (+24%) |
| 2x-width / 50-layer stand-in for larger hybrids | 200 / 400 MiB | 913 -> 713 MiB (+28%) |

With fp32 in_proj activations the gains are larger: +28% (Nano), +37% (Super) and +42% (stand-in) at 8k context. These numbers are derived from the buffer shapes plus conv/SSM state and fp16/bf16 KV, under the assumption that decode is limited by per-request state memory. They were not measured end to end.

## The change

- `ssd_chunk_scan._chunk_scan_fwd`: in target-rows mode, `z` is one row per entry, shape `(nchunks, nheads, headdim)`. Every M-lane of the target tile reads that row (row stride 0); the gate arithmetic is unchanged. The full-sequence (non-target-rows) path is untouched.
- `batch_invariant_decode`: removes `z` from `BatchInvariantDecodeBuffers` (field, `allocate`, `seed`). `batch_invariant_decode_buffered_scan` passes the current token's `z` to the scan. `MambaBatchInvariantDecode.seed` no longer takes `z`.
- `MambaMixer`: the prefill seed call drops its `z` argument.

## Tests

- `tests/unit_tests/ssm/ops/mamba2/test_batch_invariant_decode.py`:
  - existing bitwise decode == full-scan tests, updated to the new `seed` signature.
  - new `test_independent_gate_across_chunk_boundaries`: z independent of x (the existing tests reuse x as z, which would hide a wrong z row); two slots decoded in one call; prefill tails on both sides of a chunk boundary; 2 x chunk + 3 decode steps. Every step must equal `mamba_chunk_scan_combined(..., z=z)` bitwise.
  - new `test_replay_buffers_hold_no_gate`: buffer-size check.
- `tests/unit_tests/determinism/kernels/test_ssm_kernels.py`: new `test_batch_invariant_decode_step_replays`, a bit-exact replay of one decode step (target-rows chunk scan with z) that includes a chunk-boundary crossing. `tools/check_kernel_determinism_coverage.py` passes.
- Before this change, MCore's decode with every buffered z row overwritten by noise gave 0 differences over 1.8M outputs (300 steps, two chunk crossings, final state equal). Production use is NeMo-RL's batch-invariant RL engine on Nemotron-3 hybrids, where the same gate-only-the-target-row change is checked bitwise against the z-buffer decode.

## Risk

- Semantics change in `_chunk_scan_fwd` target-rows mode: `z` must now be per entry. That mode's only caller is the batch-invariant decode, updated here; the shape is asserted.
- API: `BatchInvariantDecodeBuffers.seed` / `MambaBatchInvariantDecode.seed` drop the `z` parameter, and the `z` field is gone. Both are internal to the batch-invariant decode path.
- Independent of `fix/mamba-ssd-train-inference-parity` (training on the generation kernels). The two PRs touch different source files and different tests.

Not in this PR: `DynamicInferenceContext` sizes the hybrid Mamba share of the inference buffer from conv + SSM state only. The batch-invariant replay buffers (x, dt, B, C, out; still ~200 MiB per slot at Super width in fp32 after this PR) are allocated lazily for every `max_requests` slot outside that budget, so a configured concurrency can overcommit GPU memory. That accounting gap is a separate fix.

## Row kernels for the decode step (second commit)

The decode step still ran the training kernels in target-rows mode: a full training M tile per (entry, head) for the chunk scan and for CB, and chunk-state plus state-passing programs for every entry, although only entries that fill their chunk (about 1 in `chunk_size`) commit a boundary state. The new `megatron/core/ssm/ops/mamba2/batch_invariant_decode_rows.py` computes only what the step consumes:

- `_chunk_scan_row_kernel`: the chunk scan on the 16-row MMA tile that holds the target row, gate included. It uses the training tile's `BLOCK_SIZE_N` / `BLOCK_SIZE_K` and causal bound `K_MAX`, so it sums the same zero-weight products.
- `_bmm_row_kernel`: CB with the training kernel's config, loading and storing only the target row.
- `_chunk_state_passing_rows_kernel`: chunk state (training config) and the state-passing update fused, run only for crossing entries. The update `exp(dA) * S + new` is written as one `tl.fma`, because the state-passing kernel compiles it to `fma.rn.f32`. A mul + add would round twice and change committed states by an ulp. Tests that let `exp(dA)` underflow over a chunk miss this, so the tests below draw per-head decay `|A|` from 1e-4 to 2.
- `_decode_step_prep_kernel` (in `batch_invariant_decode.py`): the step's bookkeeping in one launch instead of ~25 small ops. It writes the current token into the replay buffers and sets target rows, chunk flags and chunk starts. It also zeroes the output and advances the cursor. It does integer updates and copies only.

**Why the bits are the same.** A tensor-core MMA computes each output row from that row of A alone. With the same instruction, the same k decomposition and the same accumulation order, the target row's bits do not depend on how many other rows share the tile. The tile is not guessed: each row kernel takes its block sizes (and, for CB / chunk state, `num_warps` / `num_stages`) from the one config the training autotuner launches with. `_pin_mamba_autotuners` pins that config in batch-invariant mode. `row_kernel_configs` falls back to the existing tile pipeline in three cases:
- an autotuner is not pinned to a single config;
- `dstate > 128` (the scan then splits K over several dots);
- the chunk-scan tile compiles to warpgroup / tcgen05 MMAs (`num_warps >= 4` and `BLOCK_SIZE_M >= 64`).

That last condition is measured: on GB200, every such candidate differs from the 16-row `mma.sync` tile in fp32, and every `mma.sync` candidate matches it bitwise.

**Speed.** One decode step of one Mamba layer, `batch_invariant_decode_buffered_scan` captured in a CUDA graph, GB200. Per-rank Nemotron-3-Nano shape: 64 heads x 64, 8 groups, dstate 128, chunk 128. Each value is the best of 3 runs x 500 replays.

| rows | dtype | before | prep fused, tile kernels | prep fused + row kernels |
|---|---|---|---|---|
| 1 | fp32 | 48.4 us | 22.1 us | 18.5 us |
| 8 | fp32 | 58.6 us | 32.7 us | 25.1 us |
| 64 | fp32 | 170.3 us | 142.7 us | 91.6 us |
| 256 | fp32 | 524.6 us | 488.8 us | 274.6 us |
| 1 | bf16 | 47.1 us | 20.5 us | 17.6 us |
| 8 | bf16 | 56.1 us | 29.7 us | 22.7 us |
| 64 | bf16 | 143.9 us | 115.7 us | 75.3 us |
| 256 | bf16 | 419.3 us | 384.9 us | 212.2 us |

End to end, the same kernels have run in NeMo-RL's batch-invariant engine. There they are applied as a patch over Megatron with fp32 replay buffers and the gate as a separate kernel. Results on full Nemotron-3-Nano with CUDA graphs:
- device time per Mamba layer: 113 -> 74 us at 64 rows and 414 -> 251 us at 256 rows;
- wall time per decode step at EP1: 15.68 -> 14.84 ms at 64 rows and 25.29 -> 21.91 ms at 256 rows;
- wall time per decode step at EP4: 10.71 -> 9.87 ms at 64 rows per rank and 20.06 -> 16.61 ms at 256;
- greedy generations are bitwise identical with the kernels on and off, at EP1 and EP4, with graphs on and off.

Those end-to-end numbers were not re-measured with this Megatron-native version.

**Tests** (new class `TestBatchInvariantDecodeRowKernels` in `test_batch_invariant_decode.py`). The class pins the autotuners the way batch-invariant mode does.
- `test_row_pipeline_matches_tile_pipeline`: 256 entries hitting every target row 0..127, about 1 in 5 crossing a chunk boundary, shuffled slots, a padding lane and signed zeros. Per-head decay `|A|` runs from 1e-4 to 2. It covers scales 1e-3 / 1 / 30, fp32 and bf16, `D` per head and per channel, and runs with and without the gate. Outputs and committed SSM states must match the tile pipeline bit for bit (raw bits) in all 72 cases.
- `test_row_kernels_follow_the_pinned_tiles`: pins each training kernel (chunk scan, CB, chunk state) to every candidate in its autotune list, in fp32 and bf16. The row kernels must either decline or match that tile bitwise. Tiles the training kernel itself cannot launch are skipped.
- `test_many_step_decode_matches_tile_path_and_training_scan`: 300 decode steps over five slots with prefills 1..300 (several crossings per slot), mixed decay, an independent gate and a padding lane. It runs eagerly and as a CUDA graph replay. Outputs and final states must equal the tile pipeline's; in bf16 every output must also equal `mamba_chunk_scan_combined` over the full sequence.
- `test_row_kernels_selected_when_pinned`: the pinned configs select the row kernels (including the dims of the existing decode tests, so those tests now run through them), and an unpinned scan keeps the tiles.
- Run on GB200: `test_batch_invariant_decode.py` plus the two Mamba determinism replay tests: 22 passed, 131 subtests passed. `tests/unit_tests/ssm/ops/mamba2/`, `test_ssm_kernels.py` and `test_manifest.py`: 343 passed, 2 xpassed. The 2 failures are `test_gdn_torch_l2norm_matches_fla_and_replays[compiled-*]`, which fail the same way on the base commit and are unrelated.
- The new module is registered in `manifest.py` under `ssm_mamba2_batch_invariant_decode`. `check_kernel_determinism_coverage.py` passes. black / isort / ruff are clean, and pylint 3.2.6 gives 10.00.

**API.** `BatchInvariantDecodeBuffers` gains a `chunk_starts` field, which `allocate` creates. `_mamba_chunk_scan_decode_rows` gains `use_row_kernels=True`. `batch_invariant_decode_buffered_scan` now asserts int32 `batch_indices` (as `_masked_update_rows` already required) and contiguous buffers.
