## Original PR description

# feat(moe): logical token multiplicities and fixed-row router blocks

## What this PR does

In a packed layout one row can stand for several logical tokens. For example,
a shared prompt row stands for one copy of the prompt per completion. This PR
lets the MoE router count such rows correctly for expert-bias updates and makes
its forward routing scores independent of packing. Only
`local_tokens_per_expert` is weighted. Aux losses, z-loss, capacity dropping,
quantile balancing, routing replay and router diagnostics still count physical
rows, and the backward GEMMs are unchanged, so a caller must disable those
features. #7914 rejects the loss, dropping, balancing and replay settings; router
diagnostics must be left off by the caller. Without a caller that opts in, routing is
unchanged.

## Changes

- `token_multiplicities` (optional, default `None`) on `TopKRouter.forward`,
  `InferenceTopKRouter.forward`, `TopKRouter.routing`,
  `TopKRouter._apply_expert_bias` and `MoELayer.route`. When set, each row is
  counted that many times in `local_tokens_per_expert`, so expert-bias updates
  match a dense forward. Counts stay exact in the existing int64 buffer.
  - On the default path, routers and routing callables are still called with
    exactly the upstream keywords.
  - Existing callers and replacement `routing` callables therefore keep
    working.
- `RouterInterface.forward` declares the optional argument, and the router
  docstrings describe it: one logical token count per flattened
  sequence-first row.
- `shared_prefix_token_multiplicities`: a keyword-only argument of
  `MoELayer.forward`, `None` by default. It holds one logical token count per
  flattened sequence-first row of `hidden_states`.
  - `MoELayer.forward` hands it to `route()` as `token_multiplicities`,
    including on the megakernel path.
  - The MoE recompute and megakernel checkpoints capture it in the closure they
    recompute, so a backward replay counts with the same values.
  - Paths that call `route()` directly or replay a CUDA graph do not receive
    it, so a caller must use the eager forward.
  - The MoE layer keeps no per-call state.
- `TransformerLayer` passes `shared_prefix_token_multiplicities` to the MoE
  layer only.
  - `TransformerLayer.forward` removes it from its keyword arguments before
    `_forward_attention`, so attention never sees it.
  - `_forward_mlp` and `_run_mlp` pass it on to the MLP, and
    `MoETransformerLayer._forward_mlp` passes it on to the eager path.
  - When `_run_mlp` runs the MLP in sequence chunks, it splits the
    multiplicities by chunk. Each chunk owns a contiguous range of the
    flattened rows.
  - A recomputed MLP receives the value through the checkpointed call's
    arguments.
  - A non-`None` value raises `ValueError` with a dense MLP, with
    `packed_seq_params`, or with partial MoE CUDA graphs. With
    `packed_seq_params`, rows may be un-flattened and reordered before the MoE
    layer, so the counts would no longer match their rows.
  - Without the argument, `TransformerLayer` behaves as before.
- `moe_utils.router_gating_token_blocks()`: inside this scope the forward
  router GEMM runs over fixed row blocks. A packing change can otherwise select a
  different GEMM reduction, and even FP32 router differences below 2e-6 can
  flip BF16 expert choices.
- `tensor_parallel/random.py`: `CheckpointFunction` and
  `CheckpointWithoutOutput` recompute inside a copy of the forward pass's
  `contextvars` context.
  - CUDA autograd can run backward on an engine thread with different context
    values.
  - Without this change, a forward-scoped setting such as the
    `router_gating_token_blocks()` scope is lost during recomputation.
  - Tensor observations stay suspended inside the restored context.
  - This applies to every recompute through these two helpers and keeps
    results unchanged. `te_checkpoint`, used with FP8/FP4, is unchanged.
- `RouterGatingLinearFunction.backward` computes only the gradients autograd
  requires. A frozen router still produces the input gradient but skips the
  weight-gradient GEMM, which has no consumer. This applies to every MoE run.
