# Take the CUDA-graph GTP finalize groups from the graphed module

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8052) · state: open · merged: False

## Original PR description

**Why.** At replay, a GTP CUDA graph runner fires the DDP grad-ready hook of each parameter finalized during backward capture on the reduce-scatter stream of that parameter's GTP group. `_CudaGraphRunner._set_gtp_finalize_hook_plan` read the dense and expert GTP groups from the global parallel state, so a graphed module on its own grid got the global grid's groups. A MIMO language model never initializes the globals and got `None` for both. Its dense and expert parameters then fell into one bucket, on a stream that none of their reduce-scatters use.

**What.**
- Resolve both groups from the graphed module's `pg_collection` with `resolve_gtp_remat_group`, the helper its GTP linear layers use.
  - A field set on the collection is used as given, including `None` for an axis that is off.
  - A module without a collection, or a collection without the field, keeps the global groups.
- Refresh the process-group read allowlist (210 to 209).

**Tests.**
- New `test_cuda_graph_gtp_groups.py` drives the plan on a stub runner. It needs no GPU and no GTP-capable Transformer Engine.
  - With every global accessor and `use_mpu_process_groups` patched to fail, it checks dense and expert bucketing and an explicit `None`. Both cases fail on main.
  - A third test covers the global fallback.
- `test_cuda_graphs.py` and `test_process_groups_config.py` pass on 4 GPUs, as on main.
- The stub runner in `test_gtp_basics.py` gains a `base_module`.

**Compatibility.** No change on the standard grid, where the module's collection holds the global groups. No API change.
