# Add an optional copy-engine gather/scatter for FsdpMuon

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/8915) · state: open · merged: False

## Original PR description

## What does this PR do?

Muon's optimizer step gathers each weight matrix's pieces to an owner rank and scatters the update back. Those transfers are NCCL send/recv, which run on the GPU's SMs. This PR adds an optional path that moves them with peer-to-peer copies on the GPU's copy engines instead, so the transfers use no SMs. Enable it with `FSDP_MUON_CE=1`. It is off by default.

Stacked on the Muon step-latency PR (#8782) and on #8684, #8548 and #8547: until they land, the diff also shows their commits, and only the top commit is new.

## Implementation

- With `FSDP_MUON_CE=1`, each FSDP group that needs communication keeps two persistent buffers in PyTorch symmetric memory: one for the momentum inputs that a gather reads, one for the updates that a scatter writes. Every rank can address its peers' buffers, so a plain `copy_` between a local tensor and a peer's buffer is a peer-to-peer copy on a copy engine (`ce_transfer.py`).
- The exchange is ordered with symmetric-memory barriers on the side stream: a gather starts after every rank has filled its inputs, and every rank applies a scatter only after all pushes have landed. Both are enqueued on the current CUDA stream, so there are no handles to wait on.
- `DBuffer` accepts an existing local buffer, so the staging buffers can back the usual sharded buffers.
- This path needs the default CUDA symmetric-memory backend, because the NCCL backend has no barrier. The unit-test fixture therefore skips `symm_mem.set_backend("NCCL")` when `FSDP_MUON_CE=1`.

## Validation

`test_muon` and `test_mcore_muon` pass on 8 H100 with `FSDP_MUON_CE=1`.

On the DSV4-Pro recipe (7 layers, 64 GPUs), measured with Nsight, data movement takes 0.2 to 1.8 ms per optimizer step with no copy kernels, and 80 to 95% of it runs under the Newton-Schulz GEMMs. Optimizer step time, compared with the NCCL gather/scatter from the step-latency PR:

| | NCCL gather/scatter | Copy engine |
|---|---:|---:|
| Optimizer step, GB200 | 777-804 ms | 800-842 ms |
| Optimizer step, GB300 | 671-672 ms | 663-674 ms |

The step time is unchanged: with all gathers started up front, NCCL's transfers are already hidden behind Newton-Schulz here, so moving them to the copy engines does not shorten the critical path. The 842 ms GB200 sample ran on a node with slower GEMMs; the other sample was 800 ms. What changes is where the transfers run: they no longer launch NCCL kernels or compete with the GEMMs for SMs. The staging buffers are persistent, two per FSDP group with communication, and their memory cost was not measured.
