# [megatron] fix: balance R2 padding for peak-memory reduction

[Upstream PR](https://github.com/verl-project/verl/pull/7524) · state: open · merged: False

## Original PR description

### What does this PR do?

**Goal: reduce padding-driven peak GPU memory concentration on expert 0 and its owning EP rank during Megatron R2 actor updates.** Loss masking removes padding's direct contribution to the actor loss, but the padding rows still enter MoE dispatch and expert computation, allocating buffers and activations before that loss is masked.

THD/BSHD preprocessing adds alignment rows whose replay indices are zero-filled. This change carries row validity through the same preprocessing layout and redistributes only final-layout padding routes after CP packing and before SP scatter. Assignments cycle through EP ranks before local expert slots; recorded routes remain unchanged, and R3 stays on its existing masked path.

The memory tradeoff matters: duplicate zero top-k indices collapse to one entry per padding row in the boolean routing map. This implementation instead creates K distinct entries. For 240 padding rows with E=256, EP=32, K=8, a CPU probe of the actual replay-to-routing-map code gives a busiest-rank padding contribution of 240 rows before and 60 after, while total padding assignments increase from 240 to 1,920. The aim is a smaller padding hotspot on the busiest receiving rank; this is not a claim of lower aggregate work, faster training, or measured whole-step GPU memory savings. EP <= K may give no rank-level reduction or increase rank-level load.

PR #7106, now merged, fixes R2 THD alignment and reconstructs alignment routes as zeros; this PR addresses their dispatch concentration. The related open #7519 changes MXFP8 alignment options, but its replay-util diff does not redistribute padding routes. Refreshed searches found no open PR implementing the same balancing fix.

The THD regression uses the pinned Megatron-Core preprocessor and observes the tensor immediately before SP scatter. For `E=64`, `EP=32`, `K=8`, and four padding rows, all 32 EP ranks receive exactly one assignment. The focused unit cases cover partial prefixes, 32- and 64-way EP, multiple layers, valid-route preservation, per-row uniqueness, and a full expert cycle.

An exact-helper property probe checked 6,852 layouts and 20,088 per-layer histograms across 8-256 experts, every power-of-two EP divisor, top-k 1/2/4/8, and 0 through `min(2E/K + 3, 64)` padding rows without a counterexample.

A production-layout CPU probe with Megatron-Core 0.18, FP8 alignment, TP=4, CP=2, 48 layers, and 240 padding rows measured:

- before: 92,160/92,160 padding top-k index slots selected expert 0 (duplicate slots collapse to one dispatched assignment per padding row);
- after: all 256 experts received 7-8 assignments per layer, and all 32 EP ranks received exactly 60 per layer;
- all non-padding routes were unchanged.

A fresh CPU probe at the same head executed the unmodified padding helper and replay-to-routing-map definitions for E=256, K=8, P=240, EP=1/8/32/64, with deterministic routing both enabled and disabled. Total unique padding assignments changed from 240 to 1,920 in every case; maximum per-rank padding rows changed from 240 to 1,920/240/60/30 respectively. This confirms the topology-dependent tradeoff rather than measuring GPU memory.

No multi-GPU training run or GPU memory benchmark was performed. The original validation environment's Megatron-Core did not expose `PackedSeqParams.cp_partition_mode`, so contiguous CP was not exercised. The affected static-zigzag packing and dispatch-input boundary was covered with the repository's pinned Megatron-Core on CPU; distributed execution remains for upstream CI.

### Peak-memory validation still needed

Compare maximum per-rank allocated and reserved GPU memory, receive-buffer sizes, expert token counts, and step time on the same model, batch, topology, dispatcher, and precision. CPU route balance supports the mechanism but does not establish end-to-end peak-memory savings. Capacity-padded buffers, token dropping, quantization alignment, and routing-dependent expert-bias updates require separate validation; preserving recorded indices alone does not prove unchanged learning behavior under every configuration.
