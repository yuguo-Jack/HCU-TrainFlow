# [fsdp, ckpt] fix: preserve merged LoRA export precision and staged weights

[Upstream PR](https://github.com/verl-project/verl/pull/8198) · state: open · merged: False

## Original PR description

### What does this PR do?

Follow up on #8180: FSDP2 merged-LoRA HF export reuses the rollout generator, which casts FP32 master weights to BF16 before the HF writer applies its export dtype policy. FP16 and FP32 exports therefore lose precision and contain BF16 tensors. Preserve stored precision for the HF callback and let the existing writer apply its dtype policy; rollout retains its BF16 default.

For CPU-offloaded shards, finish host-to-device staging before the merge context can restore the pinned source storage. Otherwise, a consumer retaining the generated tensors can receive restored base weights while the asynchronous copy is still pending. The change retains per-tensor streaming and the existing merge/restore lifecycle.

The final patch passes all 6 regression cases across FP32/FP16/BF16 and CPU offload on/off. The same test on main fails all 4 FP32/FP16 cases on dtype and passes the 2 BF16 controls. It checks saved dtype/weights and HF reload outputs against an independent PEFT merge, tied-weight coverage, exact restoration of training parameters, and BF16 rollout behavior.

Actual FSDPEngine initialization and two training steps also pass with CPU offload on/off, with HF export/reload between the steps. The original engine continues training; HF files are checked as inference exports. A local diagnostic queues `torch.cuda._sleep(200_000_000)` before consuming the merged rollout generator: the dtype-only fix still corrupts 509/1024 q_proj elements, while the complete patch passes.
