# [doc, hardware, worker, trainer] feat: add SFT support for TPU using TorchTitan engine

[Upstream PR](https://github.com/verl-project/verl/pull/8098) · state: closed · merged: True

## Original PR description

## Summary

Addresses all review feedback on `verl-project/verl#8098`:
1. **Zero TPU checks in `verl` core**: All TPU-specific runtime workarounds (`ReduceOp.AVG`, `all_gather_object` on `tpu_dist`, FSDP2 `SUM` gradient reduction, `sft_loss` bucketed tensor adaptation, `set_numa_affinity`, `logprobs_from_logits`, and `torchrun` PJRT env setup) have been moved to `verl-hardware-plugin`.
   - `verl/workers/engine_workers.py`, `verl/workers/utils/losses.py`, `verl/utils/device.py`, `verl/utils/distributed.py`, and `verl/utils/torch_functional.py` now have **0 diff** against `main`.
2. **Device-agnostic cleanups in `verl`**:
   - `verl/workers/engine/torchtitan/utils.py`: Removes the redundant `torch.unique_consecutive(sample_cu_seqlens)` call in `_create_varlen_metadata_for_document` for all devices (since `boundary_positions` from `nonzero()` is already strictly increasing `< seq_len`).
   - `verl/trainer/sft_trainer_ray.py`: Computes driver-side scalar aggregations (`train/global_tokens` and `val/loss`) on CPU without allocating accelerator tensors on the Ray driver.
3. **TPU SFT Example (`examples/tpu/sft/`)**:
   - Uses `engine.pad_to_length=True` and `engine.pad_to_length_bucket=256` from `#8150`.
   - Supports both `verl.trainer.sft_trainer_ray` (`SFT_TRAINER_MODE=ray`) and `verl.trainer.sft_trainer` (`SFT_TRAINER_MODE=torchrun`).
   - Documents why `data.ignore_input_ids_mismatch=True` is set for Qwen3 thinking chat templates.

- wuxibin89 · COMMENTED · 2026-10-08T08:33:46Z · [source](https://github.com/verl-project/verl/pull/8098#pullrequestreview-5453877741)

Thanks for the work on TPU SFT. Agree with @wuxibin89's comments; overall I think most of the TPU-specific branches should move to `verl-hardware-plugin` (per the direction in verl-project/verl-hardware-plugin#32 / #7917), and a few changes can be simplified for all devices instead of branching. Details:

**1. `engine_workers.py`: loss all-reduce can be silently wrong**
- The TPU branch only reduces when `torch.distributed.get_world_size() == self.engine.get_data_parallel_size()`. With TP>1 (or any other parallel dim), the logged loss silently falls back to the local rank's value. It also reduces over the default group rather than `dp_group`.
- The `(self.device_name != "tpu" or metrics)` guard only covers SFT; once metrics is non-empty (e.g. RL), TPU still hits the unsupported `all_gather_object`.
- Suggest handling `ReduceOp.AVG` / object all-gather via a plugin-side patch (like `reduce_avg_allreduce_patch` in plugin#32) and leaving core unchanged.

**2. `verl/utils/device.py`: `is_tpu_available` contradicts commit 7521721**
- The first commit message of this PR explains that `is_tpu_available` and the TPU early-return in `set_numa_affinity` are unshippable now that the platform is out-of-tree, and that this should be a vendor-neutral hook (e.g. `supports_numa_affinity()`). This version brings it back by eagerly importing `torch_tpu` at `import verl` time.
- Side effects: every platform tries `import torch_tpu` at import time, and on TPU hosts `torch.tpu.is_available()` runs at module load, including in the driver / CPU-only actors. Could you confirm this doesn't initialize libtpu or claim chips in those processes?

**3. `losses.py`: implicit contract on `_tpu_padded_values`**
- Nothing in verl defines `_tpu_padded_values`; core loss now depends on a private attribute set by the plugin. +1 to supporting `pad_to_length` / `pad_to_length_bucket` in the torchtitan engine (as FSDP/VeOmni #7272 and Megatron #7358 do), so TPU only needs config.

**4. `torchtitan/utils.py`: `unique_consecutive` is a no-op, just remove it**
- `boundary_positions` always contains 0 (`boundary_mask[:, 0] = True`) and all indices are `< seq_len`, then `seq_len` is appended, so the sequence is strictly increasing and never has consecutive duplicates. Removing the line for all devices is simpler than a TPU branch.
- Also, boolean-mask indexing (`sample_cu_seqlens[keep_mask]`) is data-dependent in shape just like `unique_consecutive` (and the `nonzero()` above it), so it doesn't avoid host sync as the description claims.

**5. `sft_trainer_ray.py`: no need to branch**
- `batch_seqlens` is already a Python list (`.tolist()`) and `val_losses` are scalars. The driver never needs the accelerator for these reductions; just compute on CPU unconditionally and drop the `is_device_available()` branches.
- The val path still has `self.device_name == "tpu" and isinstance(metrics, list)`, which only exists because of the all-gather skip in (1).
- Also echoing the question above: `sft_trainer_ray.py` is a POC; is there a reason TPU doesn't use `sft_trainer.py`?

**Minor**
- `torch_functional.py`: the `logits.device.type == "tpu"` dispatch to `logprobs_from_logits_naive` is reasonable but should also be a platform hook / plugin patch. Note naive materializes full-vocab log_softmax (~1.2GB fp32 per micro-batch for Qwen3 vocab at 2048 tokens).
- PR description is stale: it mentions `single_controller/ray/base.py`, `base/worker.py`, `TPU_VISIBLE_CHIPS`, and passing `get_ray_init_kwargs()` to `ray.init()`, none of which are in the current diff (`ray.init()` is still bare).
- Example script: why `data.ignore_input_ids_mismatch=True`? It can hide tokenization mismatches. Since the script isn't usable until torch_tpu is released and has no CI coverage, maybe land the example once it is runnable. The checklist marks CI tests as added, but none are in the diff.

**Suggested split**
1. Device-agnostic changes in core: drop `unique_consecutive`, CPU-side driver metrics, `pad_to_length_bucket` for torchtitan.
2. Everything else (AVG all-reduce, `all_gather_object`, logprobs impl, NUMA skip) in `verl-hardware-plugin` via patches / existing platform hooks.
3. Example + README after torch_tpu is publicly available.
