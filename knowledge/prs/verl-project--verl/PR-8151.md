# [hardware, profile] fix: improve existing pytorch profiling to support other pytorch supported device

[Upstream PR](https://github.com/verl-project/verl/pull/8151) · state: closed · merged: True

## Original PR description

### What does this PR do?

`get_torch_profiler` knew exactly one device activity, `ProfilerActivity.CUDA`, and
`TorchProfilerToolConfig` accepted exactly one device keyword, `"cuda"`. On an accelerator that is
not CUDA there was then no way to record device kernels: the default `contents=[]` asks for CUDA,
torch logs `CUDA is not available, disabling CUDA profiling` and the trace holds CPU ops only, while
naming the real device in `contents` fails config validation.

torch exposes one `ProfilerActivity` member per backend it can profile, named after the device type
it profiles, and a single profiler session records exactly one of them. So the active platform's
`device_name` is both the activity to collect and the `contents` keyword that requests it. This PR
resolves it that way instead of hardcoding CUDA, and takes the accepted device keywords from
`torch.profiler.ProfilerActivity` rather than from a verl-maintained list.

**No new `PlatformBase` API** — `device_name` is already an abstract property.

### No change for existing platforms

`PlatformCUDA.device_name` is `"cuda"`, and `PlatformROCm`, `PlatformMetaX` and `PlatformIluvatar`
inherit it (torch exposes HIP as `torch.cuda`), so all four build exactly the same `activities` list
as before. Platforms with no matching member (`npu`, `mlu`, `musa`, `gcu`, `tpu`, `supa`) still get a
CPU-only trace, exactly as they do today when torch disables the unavailable CUDA activity — the
warning explaining it is now verl's, and it names the device.

`xpu`, `hpu` and `mtia` start working with no further verl change and no plugin code.

### Out-of-tree backends whose activity is not named after the device type

`DEVICE_ACTIVITIES` is a module-level `device type -> ProfilerActivity` map, so a backend that needs
a different pairing can add one entry from its plugin:

```python
from verl.utils.profiler.config import DEVICE_ACTIVITIES
DEVICE_ACTIVITIES["mlu"] = torch.profiler.ProfilerActivity.PrivateUse1
```

This is deliberately data rather than API: it keeps the mapping out of `PlatformBase` while leaving
privateuse1-based backends a one-line override. In practice those backends all select a vendor
profiler through `global_profiler.tool` instead, which this PR does not touch.

`CPU` and `PrivateUse1` are excluded from the map and `"privateuse1"` is not an accepted `contents`
keyword: CPU activity is collected in every trace regardless of `contents`, and `PrivateUse1` is
torch's slot for an out-of-tree backend rather than a device type any platform reports as its
`device_name`, so accepting it would validate a value that is then silently never recorded.
`"cpu"` remains accepted.

### Why this is not a duplicate

- #7988 proposed the same fix through two optional `PlatformBase` hooks,
  `torch_profiler_activity()` and `torch_profiler_content_name()`. This PR drops both: `device_name`
  already carries the information, which removes the paired-hook invariant between them, removes the
  requirement for every plugin to implement them, and leaves `platform_base.py` untouched.
- `gh pr list --repo verl-project/verl --state open --search "profiler activity"` — nothing else open
  in this area.

New tests:

- `TestDeviceActivityFromPlatform` — a non-CUDA device is recorded and CUDA is *not* added alongside
  it (torch checks CUDA before every other device, so leaving it in would disable device profiling
  altogether); CUDA platforms are unchanged; every entry in `DEVICE_ACTIVITIES` resolves to its own
  activity, so the lookup holds for whatever members a given torch build exposes; a device with no
  member warns; a CUDA-written `contents` run on another accelerator warns and records no device
  activity; `contents` naming only profiler options warns nothing; a CPU platform does not add CPU
  twice.

  The non-CUDA cases take their device from whatever `torch.profiler.ProfilerActivity` the running
  build exposes rather than hardcoding one accelerator, and skip if a build offers none.
- `TestDeviceContentsConfigValidation` — every keyword in `DEVICE_CONTENTS` validates, profiler
  options still validate, an unknown keyword and `"privateuse1"` are both rejected.

Two pre-existing tests (`test_get_torch_profiler`, `test_cpu_activity_added_for_device_only_contents`)
assert the CUDA activity, which until now was hardcoded and so held on any machine. They now patch in
a CUDA platform, stating the assumption they always had — without it they fail when the suite runs on
non-CUDA hardware.

No new e2e CI test: CI has no non-CUDA device. Manually verified end to end on Intel Arc Pro B60
(device kernels present in the chrome trace, which was not the case before this change).

### API and Usage Example

No API change. On a non-CUDA accelerator, the default config now records device kernels:

```yaml
global_profiler:
  tool: torch
  global_tool_config:
    torch:
      contents: []          # records the active platform's device activity, e.g. xpu
      # contents: [xpu]     # equivalent, explicit
      # contents: [stack]   # CPU-only, as requested, no warning
```

### Design & Code Changes

- `verl/utils/profiler/config.py` — `DEVICE_ACTIVITIES` map built from
  `torch.profiler.ProfilerActivity.__members__` (keyed by lowercased device type, so the lookup does
  not depend on how torch capitalizes a member); `DEVICE_CONTENTS` derived from it for config
  validation, replacing the hardcoded `["cuda", "cpu", "memory", "shapes", "stack"]`.
- `verl/utils/profiler/torch_profile.py` — `get_torch_profiler` resolves the active platform's
  `device_name` through that map; warns when the platform has no activity, and when `contents` names
  a device activity belonging to a different backend.
- `docs/perf/torch_profiling.md` — documents the device keyword per accelerator.
- `tests/utils/test_torch_profile.py` — as above.
