# [algo, worker, fsdp, megatron] fix: normalize bypass-mode token-mean loss by tokens kept after rejection sampling

[Upstream PR](https://github.com/verl-project/verl/pull/8176) · state: open · merged: False

## Original PR description

### What does this PR do?

Fixes #4852.

In bypass mode, rejection sampling (`rollout_rs`) drops tokens inside the loss, using each micro-batch's current log probs. The engine counts `batch_num_tokens` before any micro-batch runs, and `token-mean` divides the kept tokens' loss by that pre-rejection count, which shrinks the loss by the fraction of tokens kept. Decoupled mode applies the rejection mask to `response_mask` before the update, so its count matches.

The kept-token count of the whole mini-batch is only known after the last micro-batch's forward pass, but each micro-batch runs its backward pass right after its own forward. This PR therefore normalizes in the engine, after gradient accumulation and before gradient clipping.

**Revision.** The first version of this PR rescaled each micro-batch by its own share of kept tokens. As pointed out in review, that can turn the gradient around when micro-batches keep different shares (with 1 and 7 kept tokens: exact +0.05, that version −0.4, `main` +0.025). It also does nothing for micro-batches whose tokens are all rejected. This version replaces that approach.

### Root cause

- The engines set `batch_num_tokens = loss_mask.sum()`, all-reduced over the data-parallel group, before splitting the mini-batch into micro-batches. `ppo_loss` copies it into `config.global_batch_info`.
- `compute_policy_loss_bypass_mode` builds the rejection mask from the current log probs and passes it to the policy loss. `agg_loss(..., "token-mean")` then computes `masked_sum(loss, kept mask) / batch_num_tokens * dp_size`.

### Design & Code Changes

- **`ppo_loss`** (`verl/workers/utils/losses.py`): in bypass mode with `rollout_rs`, it computes the rejection once and averages every term (policy, entropy, KL) over the kept tokens, as decoupled mode does. Under `token-mean` it reports the kept-token count as a `LOSS_NUM_TOKENS` metric, summed over micro-batches.
  - The rejection is computed by the new `compute_bypass_mode_rollout_correction` (`core_algos.py`), which is the code moved out of `compute_policy_loss_bypass_mode` unchanged.
  - The bypass loss takes the result as an optional `rollout_correction`; without it, it behaves as before.
- **`BaseEngine.train_batch`** (`verl/workers/engine/base.py`): between `forward_backward_batch` and `optimizer_step`, it pops that metric and sums it over data-parallel ranks the way `batch_num_tokens` is summed. It then multiplies the gradients, the loss and its `SUM`-aggregated metrics by `batch_num_tokens / kept tokens`.
  - This happens before clipping, so `grad_norm` and clipping see the corrected gradient.
  - Losses that report nothing skip this step without any extra communication.
- **`scale_gradients`** per engine:
  - FSDP/FSDP2 (and VeOmni, which inherits it), TorchTitan and Automodel multiply `param.grad`.
  - Megatron calls the DDP wrapper's `scale_gradients` (Megatron-FSDP implements it too), the same call Megatron's `finalize_model_grads` uses for per-token loss.
- **Megatron `_reduce_loss_num_tokens`:** only the last pipeline stage runs the loss, so the count is broadcast to the other stages. With PP > 1, that is one 2-element broadcast per `train_batch`. Under dynamic CP the count isn't all-reduced over data parallel, matching `batch_num_tokens`, because the outputs already cover the whole batch.

Scope and behavior:

- In `token-mean`, every PPO term of the bypass-mode loss is now the token-mean over the kept tokens of the whole mini-batch, however the mini-batch is split into micro-batches and ranks.
- **Behavior change:** with rejection sampling, the entropy and KL terms skip rejected tokens in every `loss_agg_mode`, as in decoupled mode.
- **Other losses in the same backward pass** (MoE router auxiliary losses, the distillation loss) are multiplied by the same factor, so their weight relative to the policy loss stays what it was before this PR.
- **Unchanged:**
  - the seq-mean modes, which divide by `global_batch_size` (the same in both modes), and `token-sum`;
  - IS-only bypass mode (no `rollout_rs`), which doesn't change the mask.

- Alexander230 · comment · 2026-10-11T13:32:16Z · [source](https://github.com/verl-project/verl/pull/8176#issuecomment-6109559547)

Thank you, I reproduced it: with micro-batches keeping 1 and 7 of their 8 tokens, the exact token-mean gradient is +0.05, `main` gives +0.025 and the first version of this PR gave -0.4. That version also did nothing for micro-batches whose tokens are all rejected.

I've replaced it with an engine-level fix. `ppo_loss` now reports how many tokens it kept, and `BaseEngine.train_batch` divides by the kept total once every micro-batch has run, before gradient clipping (Megatron also broadcasts the count across pipeline stages). Entropy and KL now skip rejected tokens too, as in decoupled mode. The token-mean is then exact however the mini-batch is split.

A small change can't fix this. The kept-token count only exists after the last micro-batch's forward pass, but each micro-batch runs its backward pass right after its forward. Normalizing each micro-batch on its own either keeps `main`'s scale error or reweights the micro-batches (the sign flip above). The only other exact option is an extra forward pass before the update, which is what decoupled mode does and what bypass mode exists to avoid.

So this needs a maintainer decision. The fix changes `BaseEngine.train_batch` and adds a `scale_gradients` to each engine. If an engine change isn't worth it for this bug, I'll close the PR; the alternative is documenting that bypass mode divides by the token count before rejection.
