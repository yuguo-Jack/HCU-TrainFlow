# [model, hardware] fix: preserve Transformers 5 Qwen3-VL-MoE checkpoint layout on NPU

[Upstream PR](https://github.com/verl-project/verl/pull/8190) · state: open · merged: False

## Original PR description

### What does this PR do?

Loading a native Transformers 5 Qwen3-VL-MoE checkpoint on Ascend fails after verl applies its NPU patches. The patch replaces the entire sparse-MoE class with the Transformers 4 implementation, reversing the last two dimensions of the expert parameters. A small real HF checkpoint reproduces both mismatches:

```text
experts.gate_up_proj: checkpoint [4, 256, 64], patched model [4, 64, 256]
experts.down_proj:    checkpoint [4, 64, 128], patched model [4, 128, 64]
```

`Qwen3VLMoeTextModel.from_pretrained()` raises with `ignore_mismatched_sizes=False`. The same patch also replaces the native top-k router with `nn.Linear`, preventing HF's class-based router-output recording. FSDP calls `apply_npu_fsdp_patches()` before loading the model, so this affects the normal Ascend initialization path.

For the modern API, identified by `Qwen3VLMoeTextTopKRouter`, patch only `Qwen3VLMoeTextExperts.forward`. Reuse the existing Qwen3.5 NPU grouped-matmul implementation: both models have the same expert-forward arguments and `[experts, out_features, in_features]` stored weights. The native constructor, sparse block, router, checkpoint layout and output-recording hooks are preserved. The Transformers 4 branch continues using the existing NPU classes.

The modern contract is visible in the [upstream Transformers implementation](https://github.com/huggingface/transformers/blob/v5.12.1/src/transformers/models/qwen3_vl_moe/modeling_qwen3_vl_moe.py).

### Test

Local hardware: one Ascend 910B2, CANN 8.5.2, torch 2.7.1+cpu with torch-npu 2.7.1.post2, Python 3.12.0/aarch64.

```bash
python -m pytest -q -s tests/models/test_qwen3_vl_moe_npu_patch_on_cpu.py tests/models/test_qwen3_vl_moe_npu_patch.py
```

| Transformers | Result |
| --- | --- |
| 5.12.1 | 7 passed |
| 5.5.3 (current requirements minimum) | 7 passed |
| 4.57.6, CPU schema tests | 1 passed, 1 skipped (modern-router test) |

Before the fix, both CPU regression tests fail against real HF classes; the two-layer native checkpoint also fails `from_pretrained()` with the mismatches above. After the fix, the tests cover strict weight loading, FP16/BF16 outputs, input gradients and every parameter gradient against native HF on the same NPU, top-1/top-2 routing (including empty experts), and native-checkpoint → NPU forward → save → reload. The latter verifies exact parameter equality, bitwise output equality after reload, and `output_router_logits=True` for each layer.

Maximum relative L2 errors across both modern versions and all cases:

| dtype | MoE output | input/parameter gradients |
| --- | --- | --- |
| BF16 | 0.468% | 0.970% |
| FP16 | 0.0663% | 0.1014% |

The tests bound elementwise error using dtype epsilon and independently bound relative L2 error. Normalized top-1 router gradients are checked against mathematical zero with an absolute 1e-6 bound. Native CPU/NPU top-k rounding differences are avoided by comparing the MoE implementations on the same device.

`pre-commit run --all-files --show-diff-on-failure`: all 14 hooks passed. The NPU regression file is explicitly added to `npu_unit_tests.yml`, whose general test command excludes `tests/models/`; the CPU file is collected by the existing CPU workflow.

Validation uses small real models and real NPU operators. Full 30B/235B RL training and throughput benchmarking were not run; this PR makes no training-quality or speedup claim.
