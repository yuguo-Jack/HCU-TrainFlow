# [ckpt, trainer] fix: resume SFT after epoch checkpoints

[Upstream PR](https://github.com/verl-project/verl/pull/7402) · state: open · merged: False

## Original PR description

## Problem and change

Closes #7401.

At an SFT epoch-boundary checkpoint, the trainer calculates the next starting epoch while the saved StatefulDataLoader iterator is exhausted. Restoring that iterator can make the next epoch yield zero batches and let training exit successfully without its remaining updates.

Pass the resolved checkpoint step to the shared CheckpointHandler loader path. For a positive step at a boundary of the current dataloader length, keep the fresh iterator. Restore saved position normally for mid-epoch checkpoints. Both Ray and SPMD orchestration use this path.

This revision narrows the PR to the boundary fix and its CPU regressions. It removes sidecar metadata, the associated validation errors, changes to checkpoint publication ordering, and trainer termination guards. There is no new checkpoint format or configuration. Boundary inference assumes the number of batches per epoch is unchanged; changed datasets, sampler geometry, and distributed topology are outside this validation.

## Related work

This updates the existing PR for #7401 rather than opening a duplicate. Merged #5725 handles the PPO trainer, while this fix applies to the shared SFT checkpoint handler. The scope also addresses the concern that the sidecar validation merely duplicated the existing boundary calculation while adding new rejection conditions.

Drive-by review, not a maintainer — take or leave. I hit this same bug independently and
landed on the same root cause, so first: **the diagnosis here is right.** On `main`,
`CheckpointHandler._load_dataloader_state` (`verl/utils/checkpoint/checkpoint_handler.py:170-178`)
unconditionally calls `train_dataloader.load_state_dict(...)`. When the checkpoint was taken at an
epoch boundary that saved state is an *exhausted* `StatefulDataLoader` iterator. Meanwhile
`verl/trainer/sft_trainer.py:341` computes `start_epoch = global_step // self.steps_per_epoch`,
which is already the *next* epoch, and line 357 calls `set_epoch(start_epoch)` before iterating.
So the loop enters the next epoch holding an exhausted iterator, yields zero batches, and if that
was the final epoch the process falls out of the loop and exits 0 having done no updates. Silent,
exactly as described. Both trainers route through the shared handler, so fixing it there is the
right place.

Two things I'd want resolved before this lands, plus some smaller notes.

## 1. The sidecar metadata provably computes the same boolean as the one-line fallback

The legacy path in this diff is:

```python
at_epoch_boundary = steps_per_epoch > 0 and resume_step % steps_per_epoch == 0
```

The metadata path is ~50 lines that end at:

```python
at_epoch_boundary = saved_steps_per_epoch > 0 and saved_step_in_epoch == 0
```

But by the time that line runs, the validation above it has already forced all three of:

- `saved_step == resume_step`
- `saved_step_in_epoch == saved_step % saved_steps_per_epoch`
- `saved_steps_per_epoch == steps_per_epoch`

Substituting those, the metadata branch reduces to
`steps_per_epoch > 0 and resume_step % steps_per_epoch == 0` — character-for-character the fallback.
The two branches cannot disagree, because the validation raises in every case where they could.

So the sidecar's only *behavioral* contribution is the `ValueError` in concern 2 below. Everything
else it buys — the on-disk format, the version field, the `.tmp` + `os.replace` write, the
compat path, the four `test_invalid_dataloader_metadata_fails_with_context` cases — is
infrastructure guarding a value the handler can already derive from `resume_step` and
`len(self.train_dataloader)`, both of which it has in hand.

Was a minimal version considered — just the boundary check, no new on-disk artifact? That's a
roughly 5-line diff in `_load_dataloader_state`, it needs no format version, no legacy path, no
forward-compat story, and it fixes every checkpoint ever written rather than only new ones. Given
that the reproducer in #7401 is satisfied by exactly that check, I think the burden is on the
sidecar to justify itself, and right now the code shows it computing a value it was not needed for.

If there's a follow-on use for the metadata that isn't in this diff, that's a fine answer — worth
saying so in the PR body, and possibly worth splitting into its own change so this fix can land
small.

## 2. `different number of batches per epoch` is a new hard failure for resumes that work today

```python
if saved_steps_per_epoch != steps_per_epoch:
    raise ValueError("Cannot safely resume SFT with a different number of batches per epoch: ...")
```

`len(self.train_dataloader)` is batches *per DP rank*. Changing the DP world size changes it. So
resuming a checkpoint on a different GPU count — 4→8 after a preemption, or rescheduling onto a
smaller node because that's what the scheduler had — goes from "works, with an approximate
dataloader position" to a hard crash, with no flag to override it. That's a real regression for
anyone running on preemptible capacity, and it's the kind that shows up at 3am. The same applies
to a checkpoint directory that was manually staged or copied, which the strict
`saved_step != resume_step` check will also now reject.

There's also an ordering problem: this raise fires *before* `at_epoch_boundary` is determined, so
it triggers even at an epoch boundary — the exact case where the geometry mismatch is harmless,
because the saved state is about to be discarded unread. Moving the geometry comparison to only
guard the mid-epoch restore path would make it fire only when it can actually matter.

My suggestion would be to downgrade it: warn loudly, discard the now-meaningless position, and
start the epoch fresh. That's strictly better than today's behavior (silent skip) without
converting a recoverable situation into a dead job. If a hard failure is genuinely wanted, a config
flag with a permissive default seems safer than making it unconditional.

## 3. Smaller notes

**Three changes in one PR.** The boundary fix, the `fit()` early-return guard, and the SPMD
`barrier()` + `os.rename`→`os.replace` publication-ordering change are independent. The latter two
look correct and worth having, but they're separate concerns bundled into a bugfix, which makes
the diff harder to review and harder to revert selectively if one of them turns out to be wrong.
Splitting the barrier/ordering change out would help.

**The new barrier isn't guarded.** `torch.distributed.barrier()` is called unconditionally in the
SPMD branch of `save_checkpoint`. Worth an `is_initialized()` check, or a note in the PR that SPMD
mode guarantees an initialized process group at that point.

**`test_fit_does_not_train_past_completed_step_target` asserts the wrong thing.**

```python
assert trainer.fit() is None
```

`fit()` returns `None` on the normal path too, so this assertion doesn't distinguish the guard
firing from the guard being absent — it only passes today because a `__new__`-constructed trainer
would `AttributeError` without the guard, which is incidental. Asserting that `Tracking` was never
constructed (or that no step ran) would test the actual behavior.

**Test coverage of the reported bug looks good.** `test_epoch_boundary_resume_starts_next_sft_epoch`
comparing against a fresh loader at `set_epoch(1)` is the right shape, and pairing it with
`test_mid_epoch_resume_restores_sft_dataloader_position` to pin the non-regression is exactly what
I'd want to see. Those two tests would carry over unchanged to a minimal fix.

---

None of this is blocking from my side — the bug is real, high-value, and correctly located. My
concern is that the fix is carrying an on-disk format and a new failure mode that the diff itself
shows aren't required to close #7401. Happy to be wrong on the metadata if there's a downstream
consumer planned.
