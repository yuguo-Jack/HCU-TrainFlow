# [data] fix: correct enable_thinking_default YAML value and loss mask mismatch

[Upstream PR](https://github.com/verl-project/verl/pull/8086) · state: closed · merged: True

## Original PR description

### What does this PR do?

Two bugs in `MultiTurnSFTDataset` cause a mismatch between tokenization and loss masking when the chat template produces different token counts for thinking ON vs OFF.

1. **Wrong YAML type**: `enable_thinking_default: none` in `sft_trainer_engine.yaml` is the string `"none"`, not Python `None`. `bool("none")` evaluates to `True`, so `_process_single_message` silently enables thinking mode.
2. **Loss mask ignores thinking mode**: `extract_system_prompt_and_generation` (which measures the generation prompt length for loss masking) receives `apply_chat_template_kwargs` but never `enable_thinking_default`. It always measures with the template's built-in default, regardless of what `_process_single_message` uses.

Bug 1 triggers bug 2: `_process_single_message` renders with thinking ON, while `extract_system_prompt_and_generation` measures with the template default. When the two modes produce different prefix lengths, template tokens get non-zero loss and are trained on as content.

This PR fixes both:
1. **YAML default**: `none` → `null`, so the value becomes Python `None` and both methods skip passing `enable_thinking`, letting the template's built-in default apply consistently.
2. **Loss mask**: `extract_system_prompt_and_generation` now receives `enable_thinking_default` via `apply_chat_template_kwargs`, matching `_process_single_message`. This prevents the mismatch from reoccurring if a user explicitly sets `enable_thinking_default` to `true` or `false`.

- wuxibin89 · COMMENTED · 2026-10-08T08:04:41Z · [source](https://github.com/verl-project/verl/pull/8086#pullrequestreview-5453583445)

Thanks for the fix! The YAML change (`none` → `null`) is clearly correct: OmegaConf parses `none` as the string `"none"`, so `bool("none")` silently turned thinking on for every sample. 👍

However, I think the second change (passing `enable_thinking_default` into `extract_system_prompt_and_generation`) can introduce a **new** loss-mask bug for Qwen3-style templates, so I'd suggest dropping it or reworking it.

**Why:** `generation_prompt` is computed as the diff between `add_generation_prompt=True` and `False`. However, it's used to mask the prefix of an assistant message rendered **on its own** (`_process_single_message`, `add_generation_prompt=False`). For Qwen3 these two don't match when `enable_thinking=False`:

- Qwen3 template, `add_generation_prompt` branch:
  ```jinja
  {{- '<|im_start|>assistant\n' }}
  {%- if enable_thinking is defined and enable_thinking is false %}
      {{- '<think>\n\n</think>\n\n' }}
  {%- endif %}
  ```
  With this PR and `enable_thinking_default: false`, `generation_prompt` = `<|im_start|>assistant\n<think>\n\n</think>\n\n`.
- But a single assistant message rendered alone (`messages=[assistant]`, so `last_query_index == 0` and `loop.index0 > ns.last_query_index` is false) is `<|im_start|>assistant\n{content}<|im_end|>\n`. It has no empty think block.
- So `loss_mask[: len(self.generation_prompt)] = 0` would zero out the first few tokens (`<think>`, `\n\n`, `</think>`, `\n\n` ≈ 4 tokens) of the **actual answer content**. On current `main` this doesn't happen, because `generation_prompt` is always `<|im_start|>assistant\n` for Qwen3.

`sanity_check` won't catch it either, since it only compares `input_ids` and doesn't check `loss_mask`.

There's also a related gap. `enable_thinking` can come per sample from the `enable_thinking_key` column, but this change only uses the global default. Datasets with mixed per-row values would still be inconsistent.

**Suggestion:**
1. Keep the YAML fix. That alone resolves the reported `bool("none")` issue.
2. If we want to make the loss mask robust to `enable_thinking`, here are two options:
   - Compute `generation_prompt` per effective `enable_thinking` value (e.g. cache for `None/True/False`) and pick it in `__getitem__`.
   - Better: check that the rendered assistant `input_ids` actually start with `generation_prompt` before masking (assert, or mask only the matching common prefix). That way template quirks fail loudly instead of silently masking content.
3. Please add a case to `tests/utils/dataset/test_multiturn_sft_dataset_on_cpu.py` that checks the loss mask with `enable_thinking=False` on a Qwen3 tokenizer. The "Test" section of the PR description is currently empty.
