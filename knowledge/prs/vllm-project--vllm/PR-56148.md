# [Attention][Spec Decode] Multi-query Triton split-K for spec-decode verify, with empty-segment/padding hardening

[Upstream PR](https://github.com/vllm-project/vllm/pull/56148) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Purpose

Spec-decode verify runs attention with a few query tokens per request (1+K). On `main`, the Triton backend admits only `max_seqlen_q == 1` to the 3D split-K kernel, so verify batches fall back to the 2D kernel, which parallelizes only over Q blocks and gets slow at long context and low batch. This PR lets short multi-query batches use split-K, with a shape-only gate in `unified_attention`: split-K runs when `max_seqlen_q <= 8` and `num_seqs * cdiv(max_seqlen_q, BLOCK_Q) <= seq_threshold_3D` (identical to `main` for `max_seqlen_q == 1`). There is no uniform-decode detection or platform special case; non-causal, per-sequence-causal and mm-prefix masking and the SM100 head-256 path stay on 2D. It also makes split-K exact for fully masked tiles, empty segments and CUDA-graph padding rows.

## Changes

- `triton_unified_attention.py`: the shape-only 3D gate above; launch-time scratch check with 2D fallback.
- `triton_attention_helpers.py`: `softmax_step` no longer clamps a fully masked tile's −inf running max to 0; `reduce_segments` skips empty/unvisited segments and returns early for padding rows and `seq_len <= 0`.
- `triton_attn.py`: split-K scratch sized per query token, `min(seq_threshold_3D, max_num_seqs) * (1+K)` rows (`1+2K` with parallel drafting, only when ≤ 8), composed with #58482's 64-segment row cap on SM12.0.
- Tests: speculative split-K vs reference incl. FP8 query (asserting split-K ran), padding/empty-segment cases, scratch sizing, 64-segment row coverage for verify batches.

- **Memory:** scratch grows for spec decode, e.g. MiniMax-M3 TP8 +24 MiB (K=3) / +42 MiB (K=5) per Triton metadata builder per rank; non-spec ≤ `main`. Computed, not measured; like `main`'s scratch it is allocated after KV-cache profiling.

Thanks for the update. The shape-only gate, the B300 E2E numbers vs `main` and the trimmed description look good. Three remaining points:

### 1. SM12.0: the 64-segment choice counts requests, not Q blocks

`build()` switches to 64 segments when `num_reqs <= max_seqs_64_segments`, where `max_seqs_64_segments = (num_SMs - 1) // (16 * num_kv_heads)` is the number of requests at which a 16-segment *decode* grid still under-fills the GPU. This PR moved the 3D gate to Q blocks (`num_seqs * cdiv(max_seqlen_q, BLOCK_Q)`) because Q blocks are what size the grid, but the 64-segment decision still assumes one Q block per request. For a verify batch the 16-segment grid is already `cdiv(1 + K, BLOCK_Q)` times larger than for decode at the same request count.

Example from the commit message (SM12.0, 188 SMs, 8 q heads / 1 KV head so `BLOCK_Q = 2`, K=3): 11 requests are 22 active Q blocks, so the 16-segment grid is 22 × 16 = 352 CTAs, about 1.9 waves on 188 SMs. The batch still gets 64 segments (1408 CTAs), and `test_split_k_segment_rows_cover_verify_queries` pins "10/11 requests → 64 segments" as the expected behavior. Applying the #58482 occupancy rule to Q blocks would stop 64 segments at 5 requests for K=3 and at 3 requests for K=5. The c1 K=5 case (one request, 3 Q blocks) keeps 64 segments either way.

Could you either share SM12.0 kernel timings of 16 vs 64 segments for these verify shapes (e.g. 4–11 requests, K=3/5, short and long context), or count Q blocks in `build()`, e.g.:

```python
num_q_blocks = seq_lens.shape[0] * cdiv(max_query_len, self.block_q)
if self.max_seqs_64_segments > 0 and (
    self.max_seqs_64_segments < num_q_blocks
    or self.softmax_segm_max.shape[0] < num_actual_tokens
):
```

Here `self.block_q` mirrors `BLOCK_Q` in `unified_attention`, ideally through a small shared helper so the two cannot drift. The 64-segment row cap could then shrink accordingly (20 rows instead of 44 in the example above). If 64 segments still win on those shapes at long context, keeping the request count is fine, but then the comment and the test should say that this is deliberate.

### 2. The launch-time scratch check still silently falls back to 2D

The `use_3d = all(...)` block in `unified_attention` re-validates ndim, trailing shape, dtype, device and contiguity of all three scratch tensors on every 3D-admitted call, and silently runs 2D if any of them fails. These properties are invariants of the buffers that `TritonAttentionMetadataBuilder` allocates (it is the only caller that passes scratch), so a mismatch is a bug that should fail loudly, not a silent perf drop. Only the row capacity (`shape[0] >= q.shape[0]`) depends on the batch. The check also costs host time on every call that is not replayed from a FULL CUDA graph (eager, PIECEWISE, non-uniform batches): about 3 µs per layer call in a quick CPU measurement.

The silent fallback is already hiding a real gap. With parallel drafting and K ≥ 4, `1 + 2K > MAX_3D_QUERY_LEN`, so `max_query_len_3d` drops to 1 and the scratch gets one row per request (the `(4, True, 8, 8)` case in `test_segment_scratch_covers_only_configured_eligible_queries`). The target verify width is still `1 + K = 5`, which the gate admits, but it fits the scratch only for a single request. I checked this on the PR head with that builder config (`num_speculative_tokens=4, parallel_drafting=True, max_num_seqs=8`, 8 q / 1 KV heads, 2k context, counting `reduce_segments` launches): the scratch has 8 rows, 1 request runs 3D, and 2–8 requests silently run 2D.

Suggestions:

- Move the structural checks out of the hot path: the builder guarantees them (optionally assert once in the builder), and in `unified_attention` keep only the row-capacity check.
- Size the scratch for the longest query that can actually take split-K, e.g. `max_query_len_3d = min(query_len, MAX_3D_QUERY_LEN)`, instead of resetting to 1 when `1 + 2K > 8`.
- Consider logging once when the capacity fallback triggers, so this kind of gap shows up in logs.

### 3. Tests are ~10× the size of the production change

Production code is +75/−17 and tests are +727/−33. AGENTS.md asks to cut scope when the test diff dwarfs the code change. Concrete candidates:

- `test_six_query_native_fp8_query_head_families` (~100 lines) builds a metadata builder, wraps the kernel in `MagicMock` and asserts the exact grid tuple. FP8 query + FP8 KV at width 6 can be one more parametrization of `test_speculative_splitk_matches_reference` (`test_triton_unified_attn` already takes `q_dtype`), with the `reduce_segments` spy asserting that split-K ran.
- `test_splitk_validates_each_scratch_tensor` (7 cases) exists only to cover the defensive validation from point 2. Without that validation it reduces to a single row-capacity case.
- `test_native_graph_replay_preserves_buffers_and_padding` with its helpers (~150 lines) and `test_reduce_segments_leaves_graph_padding_untouched` (~50 lines) both target the padding early returns in `reduce_segments`. One level should be enough.
- There are two ad-hoc factories for the same builder: `_builder`/`_metadata` in `test_triton_attention_metadata.py` and `_build` in `test_triton_attn_segments.py`, and the kernel test imports helpers across test modules. Please consolidate them into one shared helper or fixture.
