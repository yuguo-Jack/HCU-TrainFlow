# [Bugfix][Frontend] Flush engine reasoning parser at engine-reasoning → tool streaming boundary

[Upstream PR](https://github.com/vllm-project/vllm/pull/47606) · state: closed · merged: True

## Original PR description

> _Edit: reworked to use the flush-based approach suggested by @bbrowning in review (previously decoded raw token ids, which is unsafe for multi-token characters)._

## Summary

When an engine-based reasoning parser (e.g. `qwen3`) is paired with a text-based tool parser (e.g. `hermes`), a streamed tool call can be dropped.

If one streamed delta contains both the end of reasoning and the start of the tool call (`</think><tool_call>`), the engine-based reasoning parser confirms reasoning end but buffers the text after `</think>` (the leading `<`) internally, surfacing it only via `finish_streaming`. In `DelegatingParser.parse_delta`, the transition only flushed the reasoning parser when **both** parsers were engine-based, so with a text-based tool parser the `<` was never flushed. The tool parser never saw `<tool_call>`, and the whole call leaked into `content` with `tool_calls` empty.

It only happens when tokens are batched into one delta (async scheduling / `stream_interval > 1`), so it shows up as a flake, e.g. `test_named_tool_use` on `AMD: Entrypoints Integration (API Server OpenAI - Part 2)` (build 76318). It also fails on NVIDIA, so it is not ROCm specific.

## Fix

Split the `self._engine_based` check at the transition. Flush the reasoning parser whenever the **reasoning** parser is engine-based (independent of the tool parser), so its buffered post-`</think>` text is detokenized correctly — via the reasoning parser's own detokenizer, which preserves multi-token holdback — and passed to the tool parser.

This avoids decoding raw token ids, which is unsafe for multi-token / non-ASCII characters. Thanks to @bbrowning for catching the original approach and suggesting the flush.

## Testing

Added regression tests in `tests/parser/test_streaming.py` using the real `Qwen3ParserReasoningAdapter` + `Hermes2ProToolParser`:
- token-by-token, boundary chunks, and engine-lexer holdback (the batched `</think><` case that triggers the bug),
- a multi-token-character holdback: tool-call args carrying a multi-byte ZWJ emoji, streamed through the real `DecodeStream`, verifying the boundary stays byte-safe (fails without the fix, passes with it),
- engine-reasoning content pass-through with no tool parser.

End to end (Qwen3-0.6B, hermes + qwen3, `--stream-interval 2`): `test_named_tool_use` fails without this change and passes with it.

I don't think this is quite right- we previously used to decode tokens in the engine-based parser path here but that causes issues with multi-token characters, as not every individual token can properly decode on its own into the right text character without holdback to check for multi-token sequences.

I think the logic above that checks `if self._engine_based` actually needs to be split up a bit. If the reasoning parser is engine based (vs both reasoning and tool parser), we need to extract those flush_delta.content as it does above to get the proper current_text. At least, that's what I think at first glance - that will flush the final text out of the reasoning parser for the proper transition.

The root of this is we don't actually have any tests and I didn't realize we had real-world scenarios where we're mixing engine based reasoning parsers and non-engine based tool parsers. The example found was qwen3 reasoning with hermes tool?

Thanks for the super quick review! You're right, my approach was naive. Decoding tokens individually skips the holdback for multi-token sequences, so it breaks for non-ASCII text.

I am fixing it in the way you suggested: instead of requiring both the reasoning and tool parsers to be engine-based, we now flush whenever the reasoning parser is engine-based, so its buffered text comes out via flush_delta.content for the transition.

You're also right that we had no coverage here, so I added a device-independent regression test mixing an engine-based reasoning parser with a text-based (hermes) tool parser over the batched </think>< delta. And yes, the real case is qwen3 reasoning + hermes tool.
