# [Bugfix][CPU] Handle strided tensors in GELU-tanh

[Upstream PR](https://github.com/vllm-project/vllm/pull/60933) · state: open · merged: False

## Original PR description

## Overview

Fix incorrect CPU GELU-tanh results for strided input and output tensors. Preserve the existing vector kernel for contiguous tensors.

## Claims

- Handle sliced, transposed, and higher-rank input layouts correctly.
- Write through output strides without changing neighboring storage.
- Reuse the existing GELU-tanh vector math.

## Validation

Tested on Apple M1 Max with 64 GB RAM.

```sh
OMP_NUM_THREADS=4 .venv/bin/python -m pytest tests/kernels/core/test_cpu_activation.py -q -k 'gelu_tanh_input_layout or gelu_tanh_output_layout'
OMP_NUM_THREADS=4 .venv/bin/python -m pytest tests/kernels/core/test_cpu_activation.py -q -k 'not (None and dtype0)'
pre-commit run --files csrc/cpu/activation.cpp tests/kernels/core/test_cpu_activation.py
```

- New layout tests: 18 failures and 6 passes before the fix; all 24 pass afterward, covering FP32, FP16, and BF16.
- Supported activation suite: 78 passed, 4 excluded. The full suite has four existing BF16 GELU-LUT failures because `activation_lut_bf16` is unavailable on this Apple build.
- Large sliced input/output tensors and broadcast inputs passed separate local checks in all three kernel dtypes.
- All pre-commit hooks passed.

Controlled model comparison: `bigcode/tiny_starcoder_py` at revision `8547527bef0bc927268c1653cce6948c5c242dd1`, FP32, eager CPU execution, three prompts, twelve greedy tokens each. Substituting this kernel at all twenty GELU layers, with either contiguous inputs or equivalent stepped views, produced the same 36 tokens as native PyTorch GELU. Maximum selected-token log-probability difference was `6.7e-6`. This model currently uses Transformers GELU by default; the substitution explicitly exercises the CPU kernel and does not establish a naturally occurring model regression.

Other CPU architectures were not tested locally. The existing ARM CI job runs this test file.

## Details

The CPU activation loop assumes packed rows and ignores tensor strides. A slice such as `x[:, :d]` can retain a larger row stride, causing the kernel to read the wrong values. Independently strided outputs also require different write offsets.

For non-contiguous input or output, use PyTorch `TensorIterator` for stride-aware traversal, gather vector-sized groups, apply the existing GELU-tanh math, and scatter valid results. Contiguous tensors retain the existing implementation. The generic path adds traversal and gather/scatter overhead; no performance improvement is claimed.

Searched existing issues and open PRs for GELU-tanh and stride handling; no matching fix was found. Related PR #54540 changes ARM activation selection rather than tensor layout handling.
