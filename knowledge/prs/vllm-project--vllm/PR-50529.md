# [Bugfix] Ignore signals during EngineCore shutdown to avoid premature kill

[Upstream PR](https://github.com/vllm-project/vllm/pull/50529) · state: open · merged: False

## Original PR description

## Purpose

When the API server shuts down, `ProcessManager` sends `SIGTERM` to the
`EngineCore` process to trigger graceful teardown (the busy loop notices the
shutdown request and begins cleanup). The `finally` block of `run_engine_core`
then runs `engine_core.shutdown()` to release resources (KV connectors,
executor workers, sockets, etc.).

Previously the `finally` block reset `SIGTERM`/`SIGINT` to `SIG_DFL` *before*
calling `engine_core.shutdown()`. If `ProcessManager` (or the process's
`--shutdown-timeout` supervision path) delivered a second `SIGTERM` while
cleanup was still in progress, the default disposition terminated the process
immediately, aborting `engine_core.shutdown()` partway through and leaking
resources (e.g. worker subprocesses, transfer connections).

This change ignores `SIGTERM`/`SIGINT` for the duration of cleanup and restores
`SIG_DFL` only after `engine_core.shutdown()` returns:

```python
finally:
    # Ignore further signals during cleanup so ProcessManager's
    # concurrent SIGTERM (from APIServer shutdown) doesn't kill
    # EngineCore before engine_core.shutdown() completes.
    signal.signal(signal.SIGTERM, signal.SIG_IGN)
    signal.signal(signal.SIGINT, signal.SIG_IGN)
    if signal_callback is not None:
        signal_callback.stop()
    if engine_core is not None:
        engine_core.shutdown()
    signal.signal(signal.SIGTERM, signal.SIG_DFL)
    signal.signal(signal.SIGINT, signal.SIG_DFL)
```

## Why this matters (shutdown-timeout / cleaner shutdown)

Deployments that rely on `vllm serve --shutdown-timeout <N>` expect the engine
to have a bounded window to clean up gracefully before being force-killed. With
the old behavior, a concurrent `SIGTERM` arriving inside that window could kill
`EngineCore` mid-cleanup, defeating the purpose of the timeout. Ignoring signals
during cleanup lets `engine_core.shutdown()` run to completion within the
`--shutdown-timeout` budget, giving a clean, deterministic shutdown. This is
particularly important for disaggregated / KV-transfer setups (e.g. the NIXL
connector), where orphaned workers or half-torn-down transfer state can wedge
subsequent runs.

## Not a duplicate

No open PR modifies the `finally` cleanup block of `run_engine_core`. The
closest related PR, #44751, installs signal handlers *before* engine
construction so a signal during model load/warmup aborts startup cleanly; it
does not touch the shutdown-time `finally` block or the `SIG_IGN`-during-cleanup
behavior addressed here.

- CS-icez · comment · 2026-10-09T02:36:56Z · [source](https://github.com/vllm-project/vllm/pull/50529#issuecomment-6073114009)

Independent confirmation of this race, with some reproduction numbers in case they help review.

We hit the same thing on `releases/v0.23.0` (`78743ab5b`) and have been carrying a local patch with the same reordering (`SIG_IGN` around the teardown, `SIG_DFL` restored afterwards). The `finally` block on current `main` still restores `SIG_DFL` before `engine_core.shutdown()`, so the window is still there.

**Setup**

- Single node, `vllm serve --api-server-count 1 --shutdown-timeout 10`, UniProcExecutor, one A40, dummy weights.
- An out-of-tree `KVConnectorBase_V1` whose `shutdown()` prints a final-state line and sends a goodbye frame to an external per-node service. That makes "did the teardown callback chain actually finish" directly observable: the service treats a disconnect without a goodbye frame as a peer crash and exits non-zero.
- Stop by sending `SIGTERM` to the process group, so the API server and EngineCore both receive it at the same time.

**Results** (one sample = one start/stop cycle of the same config)

| variant | cycles | `connector.shutdown()` ran to completion |
|---|---|---|
| unpatched | 7 | 1 |
| unpatched + `VLLM_LOGGING_LEVEL=DEBUG` | 1 | 1 |
| with the reordering | 4 | 4 |

The DEBUG run succeeding is consistent with a race: the extra logging slows the parent enough that EngineCore finishes teardown before the parent's `proc.terminate()` lands.

**Two things we learned that may be useful here**

1. The existing log lines do not tell you whether teardown completed. In the failing runs we still saw `EngineCore: start mode=drain`, `request processing complete; starting resource teardown` and `exiting busy loop`, and no `force killing remaining processes`. The process was killed after those lines, inside `engine_core.shutdown()`. Only the connector's own output distinguished the two cases. We had misread earlier runs as clean for exactly this reason.
2. Process-group stops are the common way to hit it (an orchestrator's `killpg`, `kill -- -PGID`, Ctrl-C in a terminal). With only one side signalled the two shutdown paths run in sequence. When both are signalled, EngineCore may already be past the `SIG_DFL` reset when the parent's second `SIGTERM` arrives. The slower the teardown, the more likely the hit, which is why deployments without a connector never notice.

**One small difference in our version**: we put the teardown in `try` and the `SIG_DFL` restore in an inner `finally`, so the default disposition comes back even if `engine_core.shutdown()` raises. Not essential, since the parent's `SIGKILL` fallback covers a hung teardown either way.

**Limits of the above**: small sample; measured on v0.23.0 with our equivalent patch, not with this PR's exact diff on `main`; `SIGTERM` only; single node with UniProcExecutor only.
