# [Bugfix][Kernel] Keep batch x heads out of gridDim.z in the shared FLA recurrent kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/59414) · state: open · merged: False

## Original PR description

## Purpose

The shared FLA recurrent launchers in `vllm/third_party/flash_linear_attention/ops/` put the batch x value-head product in `gridDim.z`:

```python
grid = (NK, NV, N * HV)
```

CUDA caps `gridDim.y`/`gridDim.z` at 65535, so any decode (or spec-decode) batch with `N * HV > 65535` fails to launch with `Triton Error [CUDA]: invalid argument`. For example, 1024 sequences x 64 local value heads, or 2048 x 32. This affects:

- `fused_recurrent_gated_delta_rule_fwd`: Qwen3-Next / Qwen3.5 GDN decode, OLMo hybrid GDN
- `fused_sigmoid_gating_delta_rule_update`: Qwen GDN decode / spec decode
- `fused_recurrent_kda_fwd` in `ops/kda.py`: reuses the same kernel, used by `bailing_moe_v3`

This PR flattens the grid to `grid = (N * HV * NV, NK)`, so `N * HV` lives in `gridDim.x`, whose limit is 2^31 - 1. The kernels recover `i_nh, i_v = pid // NV, pid % NV`, so the V tile varies fastest. This keeps the original launch order: the V tiles of one (sequence, head) stay adjacent and share that head's q/k/g loads in L2. The packed decode kernel in the same file already guards against this limit with `SPLIT_BATCH_HEAD_GRID`. The kernel bodies are otherwise unchanged.

A first version put `N * HV` in X and the V tiles in Y. That spread the V tiles of a head `N * HV` CTAs apart and made KDA decode up to 1.4x slower at large batches; see the benchmark below.

**Not a duplicate:** #56974 fixes the same class of bug, but only in the GLM-5.3-Flash KDA copy (`vllm/models/glm5next/nvidia/...`). It does not touch these shared files. I found no other open PR that changes the grid of these launchers. #54637 and #51508 touch the same files but not the launch grid.

## Test Plan

I added `test_recurrent_decode_supports_large_batch_head_grid` to `tests/kernels/fla/test_fused_recurrent_packed_decode.py`, parametrized over the three launchers. It uses B=1024 and HV=64, which gives 65536 programs, and compares each launcher's output and final state against `fused_recurrent_gated_delta_rule_packed_decode`. That kernel splits its grid at this size and indexes (sequence, head) independently, so it is a valid reference. The KDA case uses a per-channel gate that is constant over K, which reduces KDA to GDN.

```bash
# new test, before and after the fix
pytest tests/kernels/fla/test_fused_recurrent_packed_decode.py -k large -q

# related kernels
pytest tests/kernels/fla/test_fused_recurrent_packed_decode.py \
       tests/kernels/fla/test_fused_sigmoid_gating_delta_rule.py \
       tests/kernels/fla/test_fused_gdn_post_conv.py \
       tests/kernels/mamba/test_gdn_forward_core_split.py -q

# broader FLA / mamba sweep
pytest tests/kernels/fla tests/kernels/mamba \
       -k "gdn or fla or recurrent or kda or delta" -m "not distributed" -q

# kernel timing, once per revision, then compare
python benchmarks/kernels/benchmark_fla_recurrent_decode.py --save base.json
python benchmarks/kernels/benchmark_fla_recurrent_decode.py --save new.json
python benchmarks/kernels/benchmark_fla_recurrent_decode.py --compare base.json new.json
```

Environment: RTX 5060 (8 GB, SM120), WSL2 Ubuntu 22.04, torch 2.13.0+cu130, Triton 3.7.1. Single GPU only, so multi-GPU tests were not run.

## Test Result

- **New test before the fix:** all 3 cases fail with `RuntimeError: Triton Error [CUDA]: invalid argument`.
- **New test after the fix:** all 3 cases pass.
- **Related kernels:** `115 passed, 1 skipped`. The skipped test needs the CuteDSL SM10x prefill backend.
- **Broader sweep:** `1701 passed, 18 skipped`. The skips are CPU-only, ROCm-only, SM10x-only, and one flashinfer-installed skip.
- **Kernel timing:** K=V=128, bf16, B in {1..256}, HV in {8, 16, 32}, T=1 and T=4 (spec decode), under CUDA graphs with per-layer states read from DRAM. Over 162 configs, time relative to the parent commit has a geomean of 1.000 (max 1.015) for all three launchers. Two runs of the same revision agree to about 1%. Full table in the review reply below.
- **Lint:** `ruff check` and `ruff format --check` (v0.14.0, as pinned in pre-commit) pass on the changed files.

The change keeps the launch order and per-program work identical, so I don't expect any numerical change. No model eval was run.

Thanks @stecasta, the launch-order concern was right. The first version regressed at large batches, so I pushed 1aa81ec to fix it.

**What went wrong.** With `grid = (N * HV, NV, NK)`, the NV=4 V tiles of one (sequence, head) launch `N * HV` CTAs apart. They share that head's q/k loads (and g for KDA), and once the batch is large enough the state streaming between them evicts those from L2. KDA is hit hardest because H == HV there (q/k are not shared across value heads) and g is per-channel fp32.

**Fix.** Flatten to `grid = (N * HV * NV, NK)` and recover `i_nh, i_v = pid // NV, pid % NV`. The V tile varies fastest, which is the same launch order as before this PR, and `N * HV` still stays out of `gridDim.y/z`.

**Benchmark.** RTX 5060 (SM120), torch 2.13.0+cu130, Triton 3.7.1. K=V=128, bf16 q/k/v and state, varlen layout as the GDN/KDA layers call it. B ∈ {1..256}, HV ∈ {8, 16, 32}, T=1 (decode) and T=4 (spec decode, `num_accepted_tokens` random in [1, 4]): 162 configs per launcher set. Each number is the per-call median under CUDA-graph replay, with one call per layer and every layer using its own recurrent state, so the state comes from DRAM rather than L2 (~370 GB/s, against a 448 GB/s peak). Base is d71f662606, the parent of this PR. Two repeated runs of the same revision agree to about 1%.

The KDA regression in the first version starts once the per-launch q/k/g footprint passes roughly 8 MB (B·HV ≥ 8192 at T=1, ≥ 2048 at T=4), which is consistent with the L2 explanation. This is a single consumer GPU with a 32 MB L2; the threshold will differ on Hopper/Blackwell, but since this commit restores the original launch order I'd expect it to be neutral there too. A B200 run would be welcome if you have one handy.

The benchmark is added in `benchmarks/kernels/benchmark_fla_recurrent_decode.py`. To reproduce, run it with `--save` on each revision, then `--compare base.json new.json`.

**On `SPLIT_BATCH_HEAD_GRID`:** the packed decode kernel already launches V tiles fastest, so flattening it the same way would let the flag go without changing launch order. I'd rather do that in a follow-up: the new test uses the packed kernel as its reference precisely because it indexes the grid differently, and unifying the indexing in the same PR would leave the test comparing a kernel against itself. The follow-up would switch the reference to a torch implementation first. Let me know if you'd prefer it here instead.
