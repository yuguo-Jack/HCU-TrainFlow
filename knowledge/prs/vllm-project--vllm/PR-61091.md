# [ROCm][Perf] Add native per-token FP8 Triton linear backend and RDNA4 tuning

[Upstream PR](https://github.com/vllm-project/vllm/pull/61091) · state: open · merged: False

## Original PR description

## Purpose

Add a native Triton per-token FP8 scaled-MM linear backend, with tuned configurations for Radeon AI PRO R9700 / gfx1201. Select it with `--linear-backend triton` for dynamic per-token activation scales and per-channel weight scales.

Related: [#60672](https://github.com/vllm-project/vllm/pull/60672), which enables the existing AITER per-token FP8 backend. This PR provides the vLLM-native implementation and keeps its tuning configurations in vLLM.
this fixes the regression in #57838 without disabling the working but slower `RowWiseTorchFP8ScaledMMLinearKernel` in #57861

The per-token FP8 runtime lives in `linear/scaled_mm/triton.py`, reuses the existing shared Triton scaled-MM kernel, and supports BF16/FP16 output, bias, compiled dynamic shapes, and graph replay. Tile and scheduling choices live in configuration files, with guarded fallbacks for unsupported layouts and unmeasured shapes.

## Validation

Test environment: Radeon AI PRO R9700 / gfx1201, Torch 2.13 with ROCm 10, and Triton 3.8. Model: `RedHatAI/gemma-4-12B-it-FP8-Dynamic`.

Validation covers operator correctness, backend selection, compiled execution, graph replay, strided scales, and tile/layout boundaries. Kernel comparisons use identical FP8 operands and scales against Torch RowWise, with quantization excluded from the timings. Serving performance compares Torch RowWise and native Triton with the same attention backend and AITER linear disabled.

```bash
uv run pytest \
  tests/kernels/quantization/test_triton_scaled_mm.py \
  tests/kernels/quantization/test_scaled_mm_kernel_selection.py \
  -k 'not rocm_compressed_tensors_w8a8'
```

Operator and backend-selection tests, rerun after the FP8 runtime relocation: **163 passed, 1 deselected** (optional INT8 checkpoint test). The shared Triton kernel and tuning configurations are unchanged from the benchmarked version. The fresh serving comparison below completed **480 successful requests**, with no errors or incomplete requests.

### Accuracy validation

GSM8K accuracy was evaluated with vLLM's `tests/evals/gsm8k/gsm8k_eval.py` on the full **1,319-question** test set: **5-shot**, greedy decoding (`temperature=0`, seed 42), chat completions with thinking disabled, a 1,024-token output limit, and 32 concurrent requests. Both runs used **TP2**, **FP8 KV cache**, and default serving settings, changing only `--linear-backend`. Attention was selected automatically (`TRITON_ATTN`); no attention or AITER environment override was used. Evaluated PR commit: `bf64ce9836f2`.

| Backend | Correct / questions | Accuracy | Invalid answers |
|---|---:|---:|---:|
| Torch RowWise | 1,255 / 1,319 | 95.15% | 0 |
| Native Triton | 1,251 / 1,319 | 94.84% | 0 |

Triton minus Torch RowWise: **-0.30 percentage points**. In the paired comparison, Triton answered 13 questions correctly that Torch missed, and missed 17 questions Torch answered correctly. Triton answered 4 fewer questions correctly in this single run. All **2,638 evaluation requests** completed successfully; 0 responses reached the output-token limit. These results cover this model and GSM8K configuration; other models and platforms need separate evaluation.

This accuracy comparison uses default attention. The TP1 serving performance measurements below use explicitly selected `ROCM_AITER_UNIFIED_ATTN`.

To reproduce, start each server separately, using `torch` for the baseline and `triton` for the candidate:

```bash
vllm serve RedHatAI/gemma-4-12B-it-FP8-Dynamic \
  --tensor-parallel-size 2 \
  --kv-cache-dtype fp8 \
  --linear-backend torch
```

Run the evaluator against each server:

```bash
uv run tests/evals/gsm8k/gsm8k_eval.py \
  --model RedHatAI/gemma-4-12B-it-FP8-Dynamic \
  --num-questions 1319 \
  --num-shots 5 \
  --use-chat-completions \
  --chat-template-kwargs '{"enable_thinking": false}' \
  --temperature 0 \
  --seed 42 \
  --max-tokens 1024 \
  --max-concurrency 32 \
  --request-timeout-seconds 7200 \
  --save-results gsm8k-results.json
```

### Serving commands

Install vLLM from this PR. Run each configuration separately on the same GPU.

**TP1 baseline (Torch RowWise)**

```bash
VLLM_ROCM_USE_AITER=1 \
VLLM_ROCM_USE_AITER_LINEAR=0 \
vllm serve RedHatAI/gemma-4-12B-it-FP8-Dynamic \
  --tensor-parallel-size 1 \
  --max-num-seqs 8 \
  --gpu-memory-utilization 0.90 \
  --max-num-batched-tokens 8192 \
  --max-model-len 32768 \
  --kv-cache-dtype fp8 \
  --load-format safetensors \
  --attention-backend ROCM_AITER_UNIFIED_ATTN \
  --linear-backend torch
```

**TP1 native Triton**

```bash
VLLM_ROCM_USE_AITER=1 \
VLLM_ROCM_USE_AITER_LINEAR=0 \
vllm serve RedHatAI/gemma-4-12B-it-FP8-Dynamic \
  --tensor-parallel-size 1 \
  --max-num-seqs 8 \
  --gpu-memory-utilization 0.90 \
  --max-num-batched-tokens 8192 \
  --max-model-len 32768 \
  --kv-cache-dtype fp8 \
  --load-format safetensors \
  --attention-backend ROCM_AITER_UNIFIED_ATTN \
  --linear-backend triton
```

### Workload

Benchmark with GuideLLM 0.7.3:

- 8 turns.
- 2048 configured prompt tokens per turn.
- 512 output tokens per request.
- 1/2/4/8 streams with 8/16/32/64 requests.
