# [Bugfix] Reject dynamic speculative decoding with ngram_gpu

[Upstream PR](https://github.com/vllm-project/vllm/pull/61123) · state: open · merged: False

## Original PR description

## Overview

Reject dynamic speculative-decoding schedules with `ngram_gpu` during
configuration.

`ngram_gpu` currently requires the runtime speculative-token count to equal
its configured maximum. Dynamic schedules can select a smaller value,
including zero, causing an assertion failure that terminates the engine and
fails every in-flight request.

Fixes #60981.

## Claims

- Replaces the runtime `NgramProposerGPU` assertion failure with an actionable
  configuration error.
- Prevents unsupported dynamic `ngram_gpu` schedules from reaching live GPU
  inference.
- Preserves existing static `ngram_gpu` and CPU `ngram` configurations.
- Directs users to remove the dynamic schedule or use CPU `ngram`.

## Details

The dynamic speculative-decoding scheduler can choose a per-batch draft length
different from `num_speculative_tokens`. The CPU n-gram proposer supports this
by accepting values less than or equal to its configured maximum. The GPU
proposer currently requires exact equality:

```python
assert num_speculative_tokens == self.k
```

When a dynamic schedule changes the draft length—for example, from `K=4` to
`K=0` above 16 concurrent requests—the assertion terminates the engine instead
of producing a configuration error.

This change adds validation to `SpeculativeConfig` so the unsupported
combination fails before the engine begins serving traffic:

- `ngram_gpu` with a dynamic schedule: rejected with an actionable error.
- `ngram_gpu` with a static draft length: unchanged.
- CPU `ngram`: unchanged.

Supporting variable K in the GPU proposer would require separate kernel and
output-shape work. This PR intentionally provides the smaller safety fix
described in #60981 without changing GPU decoding semantics.

I reviewed #60981, its comments, linked development, and open PR searches using
the issue number and relevant keywords. I found no open PR implementing this
validation or variable-K support for `NgramProposerGPU`.
