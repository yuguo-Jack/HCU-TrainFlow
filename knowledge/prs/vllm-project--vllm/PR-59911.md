# [Bugfix] Alias vendored DeepGEMM submodules for FlashInfer MoE-EP

[Upstream PR](https://github.com/vllm-project/vllm/pull/59911) · state: closed · merged: False

## Original PR description



## Overview

Fixes #59904. With only vLLM's vendored DeepGEMM installed (the default in vLLM's images), `--moe-backend flashinfer_moe_ep_mega_deep_gemm` crashes with `ImportError: generic_type: type "Runtime" is already registered!` wherever FlashInfer does `from deep_gemm.utils import ...`. This PR makes vLLM's `deep_gemm` alias cover the vendored submodules too.

## Claims

- After `_expose_deep_gemm_to_flashinfer()`, `from deep_gemm.utils import ...` reuses the already-loaded vendored `utils` and `_C` modules, so DeepGEMM's pybind11 extension isn't initialized twice.
- The 8 `flashinfer_moe_ep_mega_deep_gemm` cases of `test_init_warmup_forward_is_exact_on_grid_inputs` pass; they failed 8/8 on the nightly. These pass bf16 weights, so FlashInfer quantizes them through `deep_gemm.utils`.
- Serving with FlashInfer's torch staging fallback (`FLASHINFER_MEGA_FUSED_STAGE=0`) no longer hits the `ImportError`.
  - With CUDA graphs off, it serves.
  - With CUDA graphs on, it still fails later, at graph capture. I haven't root-caused which op breaks capture; it's out of scope here.
- Default serving of pre-quantized MXFP4 checkpoints never reaches the dotted import, and it serves as before.
- New CPU-only test `test_deep_gemm_alias_reuses_vendored_submodules` in `tests/kernels/moe/test_flashinfer_moe_ep.py`, which the L4 MoE Kernels job runs. It fails on `main` and passes with the fix.

## Details

**Root cause.** `_expose_deep_gemm_to_flashinfer()` did `sys.modules.setdefault("deep_gemm", <vllm.third_party.deep_gemm>)`, which covers only the top-level package. When FlashInfer imports `deep_gemm.utils`:
1. Python doesn't find it in `sys.modules`, so it re-executes the vendored `utils` package as a new module named `deep_gemm.utils`.
2. That package's `layout.py` does `from .._C import ...`, which now resolves to `deep_gemm._C`. That's a cache miss, because the extension is registered as `vllm.third_party.deep_gemm._C`.
3. So the same `_C` shared object is initialized a second time, and pybind11 rejects re-registering `Runtime`.

**Where FlashInfer makes that import** (0.7.0.post1, also 0.7.1rc2):
- `fp8_fp4_bf16_deepgemm/weights.py` `_quantize_grouped_fp4`, when the weights aren't pre-quantized;
- `staging.py`'s torch fallback, used with `FLASHINFER_MEGA_FUSED_STAGE=0` or when the fused quant stage is unsupported for the input.

**Fix.** Alias every already-loaded `vllm.third_party.deep_gemm.*` module under the matching `deep_gemm.*` name. The vendored package imports `_C` at import time, so `deep_gemm._C` always resolves to the existing extension module, even if FlashInfer later imports some other submodule lazily. With a site-packages DeepGEMM the alias name equals the module name, so this is a no-op.

**Alternatives considered.**
- *A meta-path finder that redirects `deep_gemm.*`:* I rejected it. It adds a process-wide import hook and more code, and importlib would overwrite the existing module's `__spec__`.
- *A FlashInfer-side change:* FlashInfer could import only top-level `deep_gemm` attributes, which DeepGEMM re-exports. That would also avoid this, but vLLM pins 0.7.0.post1.

**Duplicate check.** `gh issue list` / `gh pr list --repo vllm-project/vllm` searches for `already registered`, `deep_gemm`, `flashinfer_moe_ep_mega_deep_gemm` and `59904 in:body` found nothing relevant except #59904, which I filed for this bug, and #59900, where it was first noted as a follow-up.

- wangshangsam · comment · 2026-10-11T02:54:59Z · [source](https://github.com/vllm-project/vllm/pull/59911#issuecomment-6104796273)

Closing: this is no longer needed on current `main`.

#48962 (merged 2026-10-06, after this PR was opened) moved the vendored DeepGEMM from a pybind11 `_C` extension to `TORCH_LIBRARY` (`_C.py` + `_C_extension.abi3.so`). FlashInfer's `from deep_gemm.utils import ...` still loads the vendored submodules a second time under `deep_gemm.*`, but that no longer re-registers `Runtime`, so the `type "Runtime" is already registered` crash can't happen.

Re-checked on 4× GB200 with `vllm/vllm-openai:nightly` arm64 (`sha256:f853a683…`, built from 7d0b4e57aa, FlashInfer 0.7.0.post1), **without** this PR:
- `_expose_deep_gemm_to_flashinfer(); from deep_gemm.utils import per_token_cast_to_fp4, per_token_cast_to_fp8` imports, and both run on a CUDA tensor.
- `pytest kernels/moe/test_flashinfer_moe_ep.py -k "test_init_warmup and deep_gemm"`: 8/8 pass (this PR's description had 8/8 failing on the older nightly).
- `FLASHINFER_MEGA_FUSED_STAGE=0 vllm serve deepseek-ai/DeepSeek-V4.1-Flash --data-parallel-size 4 --enable-expert-parallel --reasoning-parser deepseek_v41 --moe-backend flashinfer_moe_ep_mega_deep_gemm --compilation-config.cudagraph_mode=NONE`: serves, no import error, GSM8K 0.895 (1319 questions, 5-shot).

The duplicate module copy that remains is harmless, so I'm not keeping this as a cleanup PR.
