# [Core] Add defer mode for long prefills

[Upstream PR](https://github.com/vllm-project/vllm/pull/61080) · state: open · merged: False

## Original PR description

## Purpose

Adds `--long-prefill-token-threshold-defer`, off by default. Instead of capping each long prefill at `long_prefill_token_threshold`, long prefills take turns:
- one long prefill per step;
- it runs after the waiting requests, with the leftover budget, if that is at least the threshold;
- one that sat out its turn runs first the next step.

**Why:** with context parallelism, each step costs a fixed amount, plus an amount for each request in it that grows with its context. On H200 (GLM-5.3, PCP8×DCP8, 8192 tokens per step) that is about 230 ms fixed, plus about 335 ms for a request at 1M context. Splitting the budget pays these costs more often. Under load the adaptive threshold also splits short cached prompts, which cuts throughput just when the queue is longest.

## Results

Agent X ([Weka trace](https://huggingface.co/datasets/semianalysisai/cc-traces-weka-062126)) with GLM-5.3 at 1M context on 16× H200: PCP8/DCP8 prefill → DP8 decode, 20-minute runs. Adaptive = threshold 2048 + adaptive.

| concurrency | arm | requests | TTFT p50 | p99 |
|---:|---|---:|---:|---:|
| 48 | adaptive | 430 | 1.5 s | 518 s |
| 48 | no threshold | 613 | 3.4 s | 414 s |
| 48 | **defer** | **609** | 6.6 s | **302 s** |
| 64 | adaptive | 160 | 154 s | 837 s |
| 64 | no threshold | 380 | 7.5 s | 558 s |
| 64 | **defer** | **396** | **5.0 s** | **539 s** |

- At concurrency 32 (below saturation) the arms are within run-to-run noise (±4% requests).
- gsm8k is the same in all arms (0.736–0.750).
- These runs used an equivalent prototype that ran long prefills oldest-first. A rebench of this commit is in progress.
