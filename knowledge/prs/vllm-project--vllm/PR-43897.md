# [Misc] add option to prevent private networks access for media urls

[Upstream PR](https://github.com/vllm-project/vllm/pull/43897) · state: open · merged: False

## Original PR description



## Purpose

For multimodal models, users can provide media urls in their requests to be downloaded by vllm before being passed on to the models.
Those media urls can therefore be used to scan local (private) resources accessible internally by the network vllm is deployed on.

The `--allowed-media-domains` engine argument can be used to only allow urls for specific domains, however this argument cannot really be used to allow any public resources to be accessed.

This PR introduces the ability to prevent private networks access for the media inputs by declaring a new `--forbid-media-private-networks-access` engine argument.

## Test Plan

Start vllm with the `--forbid-media-private-networks-access` engine argument.

Make a request with a media url pointing to a private network:

```
{
  "messages": [
    {
      "role": "user",
      "content": [
        {
          "image_url": {
            "url": "http://localhost:9002/some/path/image.png"
          },
          "type": "image_url"
        },
        {
          "text": "describe this picture",
          "type": "text"
        }
      ]
    }
  ],
  "model": "gemma-4-26b-a4b-it",
  "stream": false
}

```

The response should be:
```
{
  "error": {
    "message": "The media URL must resolve to a public domain. Input media URL: http://localhost:9002/some/path/image.png",
    "type": "BadRequestError",
    "param": null,
    "code": 400
  }
}
```

Note: this only concerns models for which the download of media is handled by vllm (e.g.: mistral models relying on the mistral tokenizer of `mistral_common` can bypass this mechanism as the download of the media is handled by `mistral_common`)

- ErenAta16 · CHANGES_REQUESTED · 2026-07-11T00:12:43Z · [source](https://github.com/vllm-project/vllm/pull/43897#pullrequestreview-4675740383)

Went through the SSRF-hardening mechanics in detail, this is genuinely careful work. A few things I checked and confirm are correct:

- Using `ip_obj.is_global` instead of `is_private` is the right call, `ipaddress.ip_address("100.64.0.1").is_private` is `False` but `is_global` correctly returns `False` too, so CGNAT ranges (used internally by AWS EKS pod CIDRs, per the comment) are still caught. Verified this against a public IP and against `169.254.169.254` as well, both classify correctly.
- Resolving once and pinning the connection to `pre_validated_ip` (instead of just validating the hostname and letting the client re-resolve at connect time) is the correct defense against DNS-rebinding TOCTOU, and preserving `server_hostname`/SNI against the original hostname for the sync adapter means HTTPS cert validation isn't broken by connecting via IP. That's the detail a lot of "block private IPs" implementations get wrong.
- Setting `allow_redirects=False` when the flag is on correctly closes the redirect-bypass angle too.

One real bug: `SSRFSafeAsyncResolverWrapper.__init__` doesn't call `super().__init__()`, which is reasonable since `resolve()` is fully overridden and never touches the real aiodns-backed resolver (calling `super().__init__()` would also hard-require `aiodns` to be installed for no reason). But `AsyncResolver.close()` references `self._manager` and `self._resolver`, neither of which ever gets set on this subclass:

```python
resolver = SSRFSafeAsyncResolverWrapperFixed("93.184.216.34")  # (unpatched version)
await resolver.resolve("example.com")   # works
await resolver.close()                  # AttributeError: 'SSRFSafeAsyncResolverWrapper' object has no attribute '_manager'
```

`close()` gets called as part of normal `TCPConnector`/`ClientSession` teardown, so this surfaces whenever the SSRF-safe async client is cleaned up. Simplest fix, since there's no real resolver underneath to release:

```python
async def close(self) -> None:
    pass
```

Verified that override makes `resolve()` still work and `close()` return cleanly with no exception.

Related to that: `get_async_ssrf_safe_client` builds a brand new `aiohttp.ClientSession` + `TCPConnector` + resolver on every call, unlike `get_async_client()` which caches `self._async_client`. Nothing in `get_async_response` explicitly closes that session after the request finishes (only the response is released via the `async with` block), so every private-network-checked async media fetch currently leaks a session/connector, which is worse once you add the broken `close()` on top, since eventual GC-triggered cleanup would raise instead of releasing cleanly. Worth either caching one SSRF-safe client per `pre_validated_ip` the way the plain client is cached, or explicitly closing it in a `finally` after the request.

However, two things to note:
1) here the PR does not really add a new flag, it leverages the already existing )[`--media-io-kwargs`](https://docs.vllm.ai/en/stable/configuration/engine_args/#-media-io-kwargs) flag. As a result the current vllm engine args api is not changed, and the `forbid_private_networks_access` key proposed in this PR can be used alongside the already existing other arguments, e.g.:
```
--media-io-kwargs '{"video": {"num_frames": 40,"forbid_private_networks_access":true},"image":{} }'
```

This also allows to selectively forbid private networks access per media type (the use case that lead us to propose this PR does not require that, but using the `--media-io-kwargs` offers this flexibility).

2) enabling `--allowed-media-domains` to use regexes is not very practical for this use case (preventing access to private network), since it would be very hard to construct a regex that can match any public hostname just by matching a name. As an example, any service deployed on a kubernetes cluster has [several dns associated with](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/), whose names can resemble public domains for some of the forms. Also it means that if new services are added to the cluster, the regex might need to be fine-tuned (and therefore the vllm models to be restarted each time). And similarly, adding a `--forbid-media-domains` suffers from the same drawbacks.

Classic TOCTOU DNS rebinding bypass: `socket.getaddrinfo()` resolves the hostname for validation, but the HTTP client re-resolves DNS at connection time. An attacker controlling a DNS server can return a public IP during this check and a private IP (e.g., `169.254.169.254`) during the actual fetch, bypassing SSRF protection entirely.

<details>
<summary>💡 Fix Suggestion</summary>

**Suggestion:** To prevent DNS rebinding, implement IP pinning: resolve the hostname once, validate that the resolved IP is public, and then force the HTTP client to connect to that specific IP address instead of re-resolving DNS.

Concretely:
1. Modify `_assert_network_is_public()` to return the validated (resolved) IP address(es) instead of just asserting.
2. Modify `load_from_url()` and `load_from_url_async()` to pass the pinned IP to the HTTP connection layer.
3. In `HTTPConnection` (in `vllm/connections.py`), modify `get_bytes()` and `async_get_bytes()` to support connecting to a specific IP address while preserving the original `Host` header. For `requests`, use a custom `HTTPAdapter` with a custom `urllib3.PoolManager` that maps the hostname to the pinned IP. For `aiohttp`, use a custom `aiohttp.TCPConnector` with a custom resolver (e.g., `AsyncResolver` subclass) that returns only the pre-validated IP.
4. After fetching, also validate the IP of the actual connection to guard against redirects to private IPs (since `allow_redirects` may be enabled).

Alternatively, a simpler (but less robust) mitigation is to perform the IP validation **after** fetching by inspecting the socket/connection peer address, and rejecting responses from private IPs — though this still allows the request to reach the private network before being discarded.

Another option is to perform two DNS resolutions with a short delay and ensure both resolve to public IPs, which raises the bar for rebinding attacks but doesn't fully eliminate them.

**Approach 1 (simplest):** When `forbid_private_networks_access` is enabled, force `allow_redirects=False` for the HTTP request. ```python
SECURITY_SENSITIVE_KEYS = frozenset({FORBID_PRIVATE_NETWORKS_ACCESS_IO_KWARGS})

def merge_media_io_kwargs(...):

    for key in all_keys:

        override_kwargs = (overrides or {}).get(key)

                if k not in SECURITY_SENSITIVE_KEYS

    ...
