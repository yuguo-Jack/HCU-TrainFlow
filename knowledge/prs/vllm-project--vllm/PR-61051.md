# [Bugfix] Bound CoW block-copy transient to avoid OOM near the memory limit

[Upstream PR](https://github.com/vllm-project/vllm/pull/61051) · state: open · merged: False

## Original PR description

## Overview

`copy_kv_cache_blocks_inplace` (`vllm/v1/worker/utils.py`) ends with `blocks[dst] = blocks[src]`, whose RHS gather materializes `len(src)` rows in one allocation. Rows can be tens of MiB (mamba state blocks), so a large copy-on-write wave — many concurrent requests sharing one prefix — transiently allocates multi-GiB and OOMs when the deployment runs close to `gpu_memory_utilization`. This PR replaces the final gather with a byte-bounded chunk loop (256 MiB default).

## Claims

- The CoW copy transient is bounded by `max(256 MiB, one row)`; the multi-GiB single-gather allocation is gone.
- Hermetic reproduction of the symptom: with the CUDA allocator capped via `set_per_process_memory_fraction`, the unchunked single gather raises `torch.OutOfMemoryError` while the chunked copy completes with byte-identical results.
- No behavior change for small copies (attention rows, ~KiB): the chunk covers all rows and the loop body executes once.
- Production-proven: this exact fix has run in the author's production since 2026-09-30 under `enable_mamba_shared_prefix_checkpoint`, where a 16-request shared-prefix wave put 67 mamba state rows (~50 MiB each) in the CoW list and the gather tried to allocate 3.15 GiB at once, OOMing at gpu_memory_utilization 0.955 (1.53 GiB free).

## Validation

```bash
python -m pytest tests/v1/worker/test_utils.py::test_copy_kv_cache_blocks_inplace_unchunked_gather_ooms_chunked_survives tests/v1/worker/test_utils.py::test_copy_kv_cache_blocks_inplace_chunked_matches_unchunked tests/v1/worker/test_utils.py::test_copy_cpu_kv_cache_logical_blocks_ignores_storage_padding -q
```

`4 passed` on a CUDA device. The new OOM-repro test caps the allocator at 672 MiB with a 512 MiB cache and a 64-pair × 4 MiB wave: the pre-fix path (bound forced to one chunk) exceeds the cap and raises `torch.OutOfMemoryError` before any write; the 64 MiB-bounded path peaks at ~576 MiB, completes, and matches the reference. The equivalence test additionally forces `_MAX_COW_TRANSIENT_BYTES` down to a single row and asserts chunked ≡ unchunked across two cache tensors and three copy pairs. `pre-commit` (ruff check/format, mypy) passes on the changed files.

## Details

**Root cause.** The final `blocks[dst] = blocks[src]` advanced-indexing RHS is a materializing gather: `len(src)` rows are copied into one temporary before the scatter. With mamba state rows (~50 MiB each), a 67-pair CoW wave needs a 3.15 GiB temporary; deployments near `gpu_memory_utilization` don't have it.

**Chunking is order-equivalent.** CoW `dst` blocks are freshly allocated (`get_new_blocks(1)` at both CoW sites), so no `dst` of a later chunk is the `src` of an earlier one; each chunk reads only never-written rows and writes only never-read rows, making the final state independent of the partition. Same-step re-hits of a fresh dst are structurally excluded (duplicate-hash cache hits return the insertion-order-first original; the mamba manager defers same-step hits on moved entries).

**Relationship to other PRs.** #55112 (overlaid KV views) and #55806 (tuple-valued layer caches) touch the same function with different bug classes; neither bounds the copy. Expect rebase interaction — this patch applies cleanly on current main and only replaces the final gather line.

**Tradeoffs / limitations.** Fallback-free and bounded: worst case is one extra slice-view + range per copy for KiB-sized attention rows (single loop iteration, no measurable cost). The OOM-repro test requires a CUDA device and skips otherwise; the equivalence test runs on CPU.
