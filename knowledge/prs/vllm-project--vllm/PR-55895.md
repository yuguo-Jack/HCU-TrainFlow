## Purpose

Under `VLLM_BATCH_INVARIANT=1` the Mamba2 SSD kernels (`_bmm_chunk_fwd_kernel`, `_chunk_cumsum_fwd_kernel`, `_chunk_state_fwd_kernel`, `_chunk_scan_fwd_kernel`, `_state_passing_fwd_kernel`) still pick their tile configuration by autotuning. The autotune keys exclude batch and sequence length, so one process is consistent with itself, but the choice is made by timing and can differ between processes, for example a trainer rescoring a rollout and the inference engine, or two engine restarts. The tile changes the reduction order and therefore the bits: on GB200 with chunk size 64 and 8 heads, `BLOCK_SIZE_H` 2 versus 8 or 64 in the chunk cumsum gives different fp32 prefix sums and 59 to 351 of about one million output elements differ.

This PR pins each of the five kernels to one of its existing candidates under `VLLM_BATCH_INVARIANT=1`. The pin is applied to the autotuner right after each kernel definition, so the candidate lists are not touched and default mode autotunes exactly as before. #55627 and #55905 build on this: they compare decode bits against prefill bits from these kernels, so the tile has to be fixed rather than timed.

Not a duplicate: #54993 and #55627 change how Mamba2 prefill and decode run, not the kernels' autotune selection. #48213 adds CPU-tuned candidate lists for the Triton CPU backend; since this PR leaves the lists alone, the two do not overlap.

The new file checks the pin helper, that each pinned tile is one of the kernel's candidates and that under `VLLM_BATCH_INVARIANT=1` each kernel exposes exactly that one configuration, and that the rows of a prefix do not depend on the tokens that follow.

For the training side of the alignment claim: Megatron's deterministic mode (`MAMBA_DETERMINISTIC=1`, without `TRITON_CACHE_AUTOTUNING=1`) already pins its vendored SSD kernels to one configuration per kernel, the cheapest candidate by block product times stages. On Triton 3.7.1 that is M64/N32/K32 (5 stages, 2 warps) for bmm, chunk_state and chunk_scan, `BLOCK_SIZE_H=2` for the cumsum and `BLOCK_SIZE=64` for state passing. Those differ from the tiles pinned here only in N, stages and warps, and the SSD + gate + norm kernel composition of vLLM batch-invariant mode versus Megatron's `mamba_chunk_scan_combined_varlen(z=...)` is bitwise identical for the granite-350m and Nemotron-H shapes at chunk 128 and 256 (16/16 comparisons, out-of-tree script). Pinning vLLM to Megatron's exact picks gives the same result, so the bits depend on `BLOCK_SIZE_K` (and on the M tile of the row-gated emit kernel in #55905), not on N, stages or warps. With autotuning on both sides the chunk-128 cases differ, which is the reason for pinning at all.

- NolenLiang · comment · 2026-09-11T13:34:30Z · [source](https://github.com/vllm-project/vllm/pull/55895#issuecomment-5635207246)

A correction to my earlier note here. Megatron's training path calls the SSD kernels of the `mamba_ssm` package (`mamba_split_conv1d_scan_combined`), not the copy vendored under `megatron/core/ssm/ops`, which serves the varlen inference paths; my "only N, stages and warps differ" statement was about that vendored copy. `mamba_ssm` has the same `MAMBA_DETERMINISTIC` cheapest-config rule and, on the commit NeMo RL pins, selects the same M64/N32/K32 tiles but `BLOCK_SIZE_H=1` for the chunk cumsum (its candidate list includes 1; the list here starts at 2). Stage by stage, with the same cumsum fed in, every other kernel is bitwise identical across the two stacks; the cumsum itself depends on the head tile, and the two cumsum kernels agree with each other at H=2 for chunk sizes 128 and 256 while diverging at H=1 for chunk 256 (GB200, Triton 3.7.1, Granite-350M and Nemotron-H-8B shapes). So the tile pinned here stays at H=2 and the training side needs the same value; that currently requires a change in `mamba_ssm`, which I will propose there. With #55627 + #55895 + #55905 + #56244 + #52905 and H=2 on both sides, under one fixed setup (GB200, bf16, TP=1, eager prefill of a single 578-token prompt), the first Mamba layer of Nemotron-H-8B-Base is bitwise identical between the Megatron training forward and vLLM batch-invariant mode; the next MLP layer's RMSNorm is the first observed divergence, and subsequent layers then receive different inputs.
