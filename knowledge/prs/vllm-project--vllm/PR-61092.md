# [Bugfix] Size Gemma 4 encoder CUDA graph capture rows by token budget

[Upstream PR](https://github.com/vllm-project/vllm/pull/61092) · state: open · merged: False

## Original PR description



## Overview

With `cudagraph_mm_encoder` on and video enabled, Gemma 4 gives every encoder CUDA graph a pixel buffer of `max(max_batch_size, max_frames_per_batch)` full-image rows. With the auto-inferred sizes that is 1856 rows at `--max-num-batched-tokens 4096`, and capture OOMs. This PR caps the rows at `token_budget // 70`, which is the most rows a replay of that budget can hold.

Fixes #61045.

## Claims

- `google/gemma-4-E2B-it` with `cudagraph_mm_encoder` and video enabled now starts on a 48 GB L40S. On main it OOMs during capture with `Tried to allocate 6.69 GiB`, the same error as in #61045.
- Capture rows for budgets 70 to 4096 go from 1856 each to 1, 2, 4, 8, 16, 32 and 58.
- Replay is unchanged. A budget-B replay never has more than B // 70 rows, because each image bills `max_soft_tokens` (at least 70) and each video frame bills 70. Image outputs match eager up to the bf16 noise eager itself shows between runs.
- The CI config (`max_frames_per_batch=16`, budget `[1120]`) still gets 16 rows.

## Validation

Setup: 1xL40S, nightly `2eb491e18b` with either main (`239a3fa3a8`) or this branch overlaid. All runs use `LLM(model="google/gemma-4-E2B-it", max_model_len=8192, max_num_batched_tokens=4096, max_num_seqs=8, gpu_memory_utilization=0.85)` with greedy decoding for 48 tokens. Inputs are 4 images (stop_sign, cherry_blossom, and a resized copy of each), run batched and one by one, plus a 16-frame `baby_reading` video.

| encoder | `limit_mm_per_prompt` | main | this PR |
|---|---|---|---|
| CG | image=1, video=1 (`max_frames_per_batch=1856`) | OOM in capture: `Tried to allocate 6.69 GiB` | starts; 7 graphs; all 5 items replayed through graphs (5 hits, 0 misses) |
| CG | image=1, video=0 (`max_frames_per_batch=0`) | starts; 58 rows for every budget | starts; 1 to 58 rows |
| eager | image=1, video=1 | ok | ok |

Greedy token ids compared with eager:

- **Images:** identical, except cherry_blossom, which switches between two continuations at token 6 to 18. Eager does the same between the main and branch runs, and so does image-only CG on main.
- **Video:** CG differs from token 0, on this branch and on main whenever video CG runs (for example with an explicit `max_frames_per_batch`). That is the replay gather stride mismatch #60687 fixes. With #60687 on top of this PR, the video output is `A baby is reading a book while wearing glasses.` vs eager `A baby is shown reading a book while wearing glasses.` (first diff at token 3).

Existing test:

```bash
pytest tests/models/multimodal/generation/test_vit_cudagraph.py -k gemma4
```

On 1xL40S:

- `test_vit_cudagraph_image[gemma4]` passes on this branch.
- When `test_vit_cudagraph_video[gemma4]` runs right after the image test in the same session, it segfaults in a CPU op during engine init, before encoder capture. Main does the same, with the same stack.
- Run on its own, the video test passes on both main and this branch. This config pins 16 rows, and this PR keeps 16.

`pre-commit run --files vllm/model_executor/models/gemma4_mm.py` passes.

## Details

Root cause: when nothing is set, `EncoderCudaGraphManager` infers `max_batch_size = min(4096 // 70, 70) = 58` and, with video enabled, `max_frames_per_batch = 58 * 32 = 1856`. Gemma 4's `prepare_encoder_cudagraph_capture_inputs` uses `max(max_batch_size, max_frames_per_batch)` as the row count of a dense `[rows, min(budget, 280) * 9, 768]` buffer. So every budget of 280 or more holds a `(1856, 2520, 768)` bf16 dummy (6.69 GiB), which stays alive as the graph's input buffer. The warm-up forward also pushes about 4.7M patch tokens through the vision tower in one call.

`_execute_local` bills each row (an image or a frame) at least 70 output tokens and replays a batch on the smallest budget that covers its total. So `token_budget // 70` rows always fit. The outer `max(1, ...)` keeps user-set budgets below 70 capturable as before. Row width is unchanged: video frames still get full-image-width rows. Separate per-modality graphs would save more, but that is a bigger change.

No test added: the gemma4 entry in `test_vit_cudagraph.py` pins the sizes on purpose to keep CI memory low. Covering auto sizing there would mean capturing all default budgets in CI.

Not a duplicate: no PR references #61045 (searched by number and by "gemma4 encoder cudagraph", "max_frames_per_batch" and "prepare_encoder_cudagraph_capture_inputs"). #60687 changes the same function (the `max_soft_tokens` lookup and the gather stride) but not the row count, so the two are complementary. #60112 adds an eager fallback when a replay exceeds the captured buffers, which leaves the capture size unchanged.

AI assistance (Claude Code) was used to trace the sizing, write the change and run the validation above.
