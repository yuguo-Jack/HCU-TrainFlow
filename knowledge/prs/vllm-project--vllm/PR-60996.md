# [KV Cache] Size packed groups by pooled bytes per request, not layer padding

[Upstream PR](https://github.com/vllm-project/vllm/pull/60996) · state: open · merged: False

## Original PR description



## Overview

`_get_packed_kv_cache_groups` sizes every block in the shared pool by the widest
group, but picks the group split with a heuristic that never looks at that cost:
`_approximate_gcd` minimizes the *layer-count* padding and prefers the larger
value on ties. Replace it with a search over the bytes a max-length request
draws from the shared pool. On DeepSeek-V4.1-Flash at 1M context this takes the
KV pool from 1.88x to 3.16x concurrency with the pool size unchanged; a second
commit batches the sliding-window metadata build so the higher group count does
not add host time per step.

Related: #58207, #60967, #58380, #58818, #60426.

### Why this is not a duplicate

The four open PRs above cover adjacent ground, so I tested whether they subsume
this. Cherry-picking all of them onto the same branch and booting the model
leaves the allocation **exactly at the unfixed 1.88x**:

| applied | cached tokens | 1M concurrency | groups |
|---|---|---:|---:|
| #60967 + #58818 + #58207 | 1,971,956 | 1.88x | 18 |
| #60967 + #58818 + #58380 | 1,971,956 | 1.88x | 18 |
| **this PR** | **3,315,539** | **3.16x** | **50** |

- **#60967** gates its only behavioural lever on `MambaSpec`
  (`if widen and isinstance(spec.first_spec, MambaSpec)`), and then only takes
  the widened split if it also *reduces the group count*
  (`len(widened) < len(groups)`). DeepSeek-V4.1-Flash has no `MambaSpec` at all
  (its caches are `CircularBufferSpec` and `MLASpec`), so the two builds are
  identical and the `bytes_per_request` comparison is never reached — a no-op
  for this model by construction.
- **#58207** rewrites the *uniform-page-size* path
  (`_get_kv_cache_groups_uniform_page_size`); a mixed-page-size model resolving
  to a block-outermost layout never reaches it.
- **#58380** chooses between block-outermost and layer-outermost layouts; the
  layout and the split here are unchanged by it.
- **#58818** / **#60426** share metadata *builds* across groups (host launch
  count); they cannot change block accounting.

None of them touches `_approximate_gcd`, which is the actual source of the
over-reservation. This is the "materially different approach" case from
`AGENTS.md`, not a competing implementation.

## Claims

- Packed allocation stops over-reserving: DeepSeek-V4.1-Flash's widest block
  goes 138,240 → 46,080 bytes and the split 18 → 50 groups, so at an unchanged
  6.32 GiB pool the cached tokens go 1,971,956 → 3,315,539 and 1M-context
  concurrency 1.88x → **3.16x**.
- The core change is a net simplification: `_approximate_gcd` is deleted
  (`vllm/v1/core/kv_cache_utils.py` is net −7 lines).
- End-to-end serving is unchanged at the requested test points, and the higher
  group count does not cost per-step host time (second commit).

## Details

### Root cause

For a balanced bucket (one layer per page size per repeat) the allocator splits
the repeats across groups, and every group draws the same number of blocks from
one shared pool. What a max-length request costs is therefore
`(blocks it needs) x (bytes of the widest group's block)`, and
`widest_group_bytes = sum(cdiv(len(names), n) * page)` grows as the group count
`n` falls, because each group then carries more layers.

The old heuristic picked `n` by minimizing
`sum((d - x % d) % d)` over the layer counts, tie-breaking toward the **larger**
`d`. Fewer, wider groups score better on that objective while making the block —
the quantity every block in the pool is sized for — larger. It optimizes a cost
the allocator does not pay.

### What changed

- The split is chosen by searching the repeats per group and taking the one that
  minimizes the bytes a max-length request draws from the pool, with the plan
  consumed by the existing emit loop.
- A state bucket (Mamba / circular buffer / unsplit sliding window) is capped at
  the states a block already fits instead of being allowed to widen the block.
- `_approximate_gcd` is removed.
- `SWAWindowMetadata` computes the sliding-window window rows for all groups in
  one batched kernel per step; each group's
  `DeepseekV41SparseSWAMetadataBuilder` returns its own view of the shared rows
  instead of launching its own kernels. Batches the shared rows do not describe
  (the non-causal DSpark draft, image spans, a missing state) fall back to the
  per-group build, which is also what runs when the state is absent.

### Tradeoffs and limitations

- **More groups cost per-group attention-metadata work.** That is why the
  second commit is here; without it the higher group count would spend the
  capacity win on the host side. Models whose metadata is already cheap, or
  those that prefer fewer groups, may want the opposite trade — that is the
  lever #58207's `--min-kv-cache-group-layers` exposes, which this change does
  not add.
- **Group counts are model-specific**; the 18 -> 50 figure is DeepSeek-V4.1-Flash.
- **Residual padding remains.** 2.00 GiB per 1M-token request against the
  ~1.87 GB nominal fp8 figure; the leftover is page padding inside one shared
  pool (the 8-token state group and the 128-token ratio-2 groups). Two pools
  would recover more and are deliberately out of scope here.
- **Textual conflict:** this touches the same region as #60967's `build_groups`
  refactor and #58380's planner, so it will need a rebase whichever lands first.
  Happy to rebase onto either.
- Validated on sm120 only; the allocation change is platform-independent, but I
  have not measured other architectures.

## Summary

This pull changes two things: how the KV cache packing search chooses its split, and a new shared metadata path for DeepSeek-V4.1 sliding-window attention. We found 7 serious problems and 6 smaller ones. The most important: the split search ranks candidates on a block width the allocator won't actually use, and the new shared metadata path can serve stale or wrongly addressed rows without raising an error.

Each finding below says what's wrong, why it matters and what to change. The full report above shows the exact code for each one.

## Serious findings

**1. The split search ranks candidates on the wrong block width** (`kv_cache_utils.py`)
The search picks the split with the lowest memory cost, but it prices each candidate before the hidden-state groups are added. Those groups are appended only after the search returns, and the pool's block width is the widest group, hidden groups included. If a hidden-state page is wider than every candidate group, the width the search minimized is not the width that gets allocated.
*Change:* price the candidates with the hidden-state groups included.

**2. The shared path can silently fill key fields with zero** (`sparse_mla.py`) — *please double-check: our final check could not confirm this one either way*
The new fast path sets only a few metadata fields directly and takes the rest (including the decode window width and the batch counts) from a dictionary of shared rows. If any key is missing, the field quietly falls back to its default of 0 instead of raising an error, and the FlashInfer code reshapes by that width on every forward pass.
*Change:* set these fields explicitly, or fail loudly when a key is missing.

**3. One table stride is used for every group** (`swa_metadata.py`)
The stride is read from the first group's block table only, then used to address every group's table. Block tables are built per group and can have different widths, so any later group with a different width is read at the wrong positions.
*Change:* check every group's table, and either require one shared stride or pass a stride per group.

**4. A failed or skipped step can serve the previous step's rows** (`swa_metadata.py`, `model_state.py`)
When the observe step fails one of its checks, it returns early without resetting its "ready" flag. The consumer then serves whatever rows were built on the previous step as if they were current. The same happens when observe isn't called at all, which occurs whenever a group has more than one metadata builder.
*Change:* clear the pending and ready flags on every failure path, and on the path where observe is skipped.

**5. The window size comes from the model config, not from each group** (`model_state.py`)
The window and index sizes are read from the model's global sliding-window setting. That setting is legitimately allowed to be empty, which makes buffer allocation fail. Even when it's set, the groups have their own window sizes (the compressor caches use 8 or 256), so the rows can be sized wrong.
*Change:* read the window from each group's own sliding-window spec, and handle an empty value explicitly.

**6. Memory grows with the number of groups while the old buffers go unused** (`swa_metadata.py`)
The new shared rows are allocated once per group, sized by the batch's token budget and the window. Each builder also still allocates its own per-builder buffers, which the shared path never reads. So the change adds memory while leaving the memory it replaced in place.
*Change:* skip the per-builder buffers when the shared path is active, or size the shared buffers so they don't scale with the group count.

**7. The new shared path has no tests** (`swa_metadata.py`) — *please double-check: our final check could not confirm this one either way*
Nothing in the pull tests the new observe/prepare handshake, its failure cases, or the fallback path. The shared rows are only exercised on a live model, so a mistake would only show up at runtime.
*Change:* add tests for the success case, each failure case, the skipped-observe case, and the fields the consumer reads.

For more, checkout the full report.
