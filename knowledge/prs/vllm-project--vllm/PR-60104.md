# [Bugfix][Sampler] Stabilize standalone Triton top-p normalization

[Upstream PR](https://github.com/vllm-project/vllm/pull/60104) · state: open · merged: False

## Original PR description

## Overview

Fixes #60030 by stabilizing the standalone Triton top-p normalization when most logits are very negative and hot tokens occur outside the sampled head tile.

## Claims

- Prevents exponential overflow from a first-tile normalization estimate and the resulting keep-all mask.
- Preserves the existing top-k behavior, sigma outlier heuristic, pivot search, and split-path dispatch without another vocabulary pass or host/device synchronization.
- Adds a compact regression to the existing sampler suite for zero/denormal probability backgrounds, hot-token positions, and split/monolithic batch sizes.
- Preserves standalone boundary-tie budgets in probability space and the existing monolithic NaN-row fallback.

## Details

The monolithic standalone top-p path used `avg_logit + 10 * std_logit` from the first tile as a fixed exponential reference. Later hot logits can overflow that reference, produce an invalid normalization/pivot, and trigger the existing keep-all guard. The fix uses an online max-normalized exponential sum, matching the numerical approach already used by the split statistics path, and uses the row maximum throughout subsequent probability calculations.

Review identified a round-trip dependency in the old duplicate matching: converting the searched probability back to a logit can exceed the `1e-9` equality tolerance and skip the duplicate budget. Standalone matching now recomputes the boundary probability directly, like the existing split mask; top-k and combined-path matching are unchanged. The exponential accumulation mask also excludes only `-inf`, allowing NaN to reach the existing invalid-pivot guard rather than silently changing normalization. This restores the original monolithic fallback without defining NaN sanitization or changing split-path behavior.

This is separate from #59804's gate and boundary-search changes, as documented in #60030. #48927 changes pivot search rather than the exponential normalization, and #58231 addresses the split path. The submitted diff contains the normalization repair, its required tie/NaN safeguards, and existing-suite regressions.

I retested a normalization-only adaptation on #59804's current head `0ae548aa1d`. Its unchanged production code fails six cases from this PR's sparse regression; the adaptation repairs the three -200 cases, leaving three -100 cases that also fail on unchanged #59804. The combined mask still retains background tokens in those remaining cases. All other paired Triton tests pass, including the latest gate/search-tile regression; the earlier additional quarter-mass failure is no longer present, and no FP64 diagnostic patch was imported. The combined full suite reports 153 passes, three failures, and one existing ROCm-only skip. A controlled real-model V2 run also changes the -200 two-hot case from 32/33 outputs to 65/0 with normalization alone. These results support the distinct normalization contribution, not a blanket compatibility claim. If #59804 lands first, this change still needs rebasing and full revalidation with that implementation.

The October 10 CUDA controls on that same #59804 head and the normalization adaptation pass the reviewer's moderate-background and large-tie cases. The two quarter-mass fixtures match PyTorch after adaptation, while the independent -100 two-hot failure remains. These are CUDA results, not a rerun of the reviewer's triton-cpu backend.

**How the rows are built**

mod = "topk_topp_triton_base" if "--base" in sys.argv else "topk_topp_triton"
apply_top_k_top_p_triton = __import__(f"vllm.v1.sample.ops.{mod}", fromlist=["x"]).apply_top_k_top_p_triton

ROWS = {  # (V, seed): ulp offsets d of p from the top-V/4 mass; 79 rows that over-keep on e00cf466 and are OK on 74c5cbcd7

def quarter_row(V, seed):  # V/4 tokens at 1.5 + Exp(1), the rest at -Exp(1), shuffled

    x = -rng.exponential(1.0, V)
    x[:V // 4] = 1.5 + rng.exponential(1.0, V // 4)
    x = rng.permutation(x).astype(np.float32)
