# [Bugfix] Treat max_tokens as output upper bound, not input-space reservation

[Upstream PR](https://github.com/vllm-project/vllm/pull/57035) · state: closed · merged: True

## Original PR description

## Why are these changes needed?

Fixes #42474.

`TokenizeParams.max_input_tokens` was defined as `max_total_tokens - max_output_tokens`, treating the client's requested `max_tokens` as a **hard reservation** off the model's context window. Per the OpenAI API spec — and how Zed/Factory/opencode-style clients actually use it — `max_tokens` is an *upper bound* on generation, not a reservation. The real generation budget is already clamped downstream by `get_max_tokens()` in `vllm/entrypoints/serve/utils/api_utils.py` based on actual post-tokenization prompt length, so the output side stays bounded regardless.

Example: model context 128000, prompt 62466 tokens, `max_tokens: 65535`
- before: rejected (`62466 > 128000-65535 = 62465`)
- after: prompt accepted, sampling `max_tokens` clamped to `65534`

## Why this is a fix at the source, not whack-a-mole

The property feeds seven consumers. Patching only one (e.g. `_token_len_check` alone) left `get_encode_kwargs` capping the tokenizer at `max_input_tokens + 1`, silently truncating prompts for left-truncation chat models and breaking prefix-cache locality. Fixing the property at the source corrects all seven consistently.

## What stays correct

- `__post_init__` still rejects `max_output_tokens > max_total_tokens` (a genuine bug)
- `_token_len_check` / `_text_len_check` still reject genuine context overflow; their messages are updated to reflect that the rejection means *input alone* exceeds the context, not input+output
- `with_kwargs` now preserves the original `max_output_tokens` when no explicit `max_length` is passed, instead of recomputing it to 0 (this was flagged on the existing POC PR)
- `get_max_tokens()` continues to clamp `sampling_params.max_tokens` to `max_model_len - input_length`

## Tests

`tests/renderers/test_completions.py::TestMaxTokensNotReservation` (7 tests):
- large `max_tokens` no longer eats the prompt budget (the reported symptom)
- genuine prompt overflow is still rejected
- `truncate_prompt_tokens=-1` / `pad_prompt_tokens=-1` map to `max_total_tokens`, not `max_total - max_output`
- `with_kwargs` preserves/re-derives the output budget correctly

All pre-existing renderer tests run with `max_output_tokens=0`, so their behavior is unchanged.

## Related PR

#42482 is an open proof-of-concept for the same fix. This PR additionally addresses the functional regression (output budget reset in `with_kwargs`) and the now-inconsistent validation messages that its bot review called out.

Fixed in f5f3718.

`EmbeddingTokenizeParamsMixin.build_tok_params` encoded the `max_embed_len` cap by setting `max_output_tokens = max_model_len - max_embed_len`, relying on the old `max_input_tokens == max_total_tokens - max_output_tokens` formula. Tests in `tests/entrypoints/pooling/test_embed_max_embed_len.py` cover the chunked and non-chunked paths plus the unset-`max_embed_len` fallback.
