# [Bugfix][Multimodal] Fix per-video cache option reuse

[Upstream PR](https://github.com/vllm-project/vllm/pull/55203) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Preserve each Qwen3-VL video's effective sampling options across repeated items and partial multimodal-cache hits. Reject option lists that are too short before indexing them.

## Claims

- Each video's selected `fps` and `num_frames` contribute to its cache identity.
- Partial cache hits filter option lists together with the remaining videos.
- Configured defaults, request options, flat/nested scopes, UUID reuse, and encoder profiling preserve their existing behavior.
- Short option lists raise a clear `ValueError` with and without a processor cache. Unused trailing entries remain supported.

The Qwen3 processor, generic processing, and cache suites pass, as do the applicable scoped hooks. The CUDA sleep/wake integration was skipped in the CPU suite. The short-list reproducer failed with `IndexError: list index out of range` before the guard and raises the expected `ValueError` afterward. Regressions exercise empty/short lists, warm caches, longer lists through partial hits, and profiling with fewer videos than configured options.

The cache regression checks prompts, placeholders, tensors, hashes, scalar-reference grids, duplicate videos, partial hits, reordering, model/request options, flat/nested scopes, and UUID-only reuse. Input options remain unmodified.

## Details

Request-wide option-list hashes let repeated videos reuse the first video's result despite different sampling settings. Partial hits removed videos without removing the corresponding option entries.

The existing base hooks let Qwen3-VL refine item hashes and select cache-miss options while preserving other processors. The final text/image HF call suppresses configured video lists so merging cannot reintroduce them. The review fix stays in the Qwen3 processor and its existing regression suite.

Merged #56372 handles option scoping and the cache API; this fix uses that behavior. The current overlap search found no competing per-item cache identity/partial-hit fix. #54527 addresses scoped option reads in other models; #60879 bounds MiniMax video decoding.

Affected hashes retain the full option list as well as selected item options, so equivalent reordered requests can incur extra misses. Scalar paths retain their existing hashes.

- claude · comment · 2026-10-11T04:06:18Z · [source](https://github.com/vllm-project/vllm/pull/55203#discussion_r4240194653)

File: `vllm/model_executor/models/qwen3_vl.py` · line 1380

🟡 (optional) A request whose per-video `fps`/`num_frames` list is shorter than the number of videos now crashes even when every video is already cache-hit, where before it succeeded. `_get_mm_hashes` (qwen3_vl.py:1357-1370) indexes `values[i]` for every video in `hashes["video"]` with no length check against `per_video_kwargs` lists, and this runs on every `apply()` call (processor.py:1481/1514), before cache lookup even happens. On base, hashing never indexed into these lists, so a length mismatch only surfaced on a cache miss; an all-cache-hit request with a too-short list just worked. Fix: validate that each per-video `fps`/`num_frames` list length matches the video count (or clamp/pad) before indexing in `_get_mm_hashes`, covering both keys and both the hashing and `_get_cache_missing_processor_kwargs` filtering paths.

<details>
<summary>Why this was flagged</summary>

Trigger: a request (or repeated same-session request after the first call cached the videos) supplies `videos_kwargs={"fps": [2.0]}` (or `num_frames`) while attaching 2+ videos, a plausible client bug e.g. list not updated when a video is appended. `_get_mm_hashes` at qwen3_vl.py:1366 does `values[i]` for `i` in `range(len(hashes["video"]))` with no bound check, raising IndexError. This runs unconditionally for every `apply()` call (processor.py:1481, 1514), including when all videos are already cached, so `_get_cache_missing_items` (which would otherwise make the mismatch a no-op for cached items) never gets a chance to run. On base branch, hashing did not index into fps/num_frames lists at all, so the same malformed request succeeded whenever the videos were already cached; only actual per-video HF processing (qwen3_vl.py:1492-1496) indexed the list, so a mismatch only mattered for cache misses. No existing validation anywhere in qwen3_vl.py checks list length against video count (verified via grep for is_list_of/len(fps)/len(videos)).

**Verification:** `_get_mm_hashes` at vllm/model_executor/models/qwen3_vl.py:1362-1369 builds one hash per video and evaluates `{key: values[i] for key, values in per_video_kwargs.items()}` (line 1366) for `i` over `enumerate(hashes["video"])`, with no check that `len(values) >= len(hashes["video"])`. A request attaching N videos with a shorter per-video list raises IndexError.
