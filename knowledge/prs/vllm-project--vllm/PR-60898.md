# [Bugfix][Spec Decode] Clamp token_indices_to_sample to the request's first query row

[Upstream PR](https://github.com/vllm-project/vllm/pull/60898) · state: open · merged: False

## Original PR description

## [Bugfix][Spec Decode] Clamp token_indices_to_sample to the request's first query row

Fixes #60897

## Purpose

`eagle_prepare_inputs_padded_kernel` (vllm/v1/spec_decode/utils.py) computes
`index_to_sample = q_last_tok_idx - num_rejected_tokens` without a lower
bound. When a request's query carries fewer rows than the rejection count
assumes, the index underflows past the start of the request:

- For the first request, the index is negative → out-of-bounds gather.
- For any later request, the index lands inside the **previous request's**
  rows → silently cross-wired sampled tokens and corrupted drafting.

The underflow is reachable when the query has no bonus-token row. With
PP > 1, the scheduler can schedule only the draft tokens
(`num_scheduled_tokens == num_draft_tokens`), while
`valid_sampled_tokens_count` still assumes the bonus row is present
(`num_rejected_tokens = num_draft_tokens + 1 - valid_count`). The same
unclamped formula exists in the CPU implementation
(csrc/cpu/spec_decode_utils.cpp), so both backends are affected.

Downstream, `token_indices_to_sample` is consumed by
`drafter.propose(...)` to select per-request sampled tokens
(vllm/v1/worker/gpu_model_runner.py), so an out-of-range index corrupts
every subsequent decode step.

## Reproducer

Unit-level, hermetic (no network, no gated models). Runs on any CUDA GPU
(e.g., an RTX 3090 24GB) — the kernel is pure integer index arithmetic, so
the bug is hardware-independent:

```bash
python -m pytest tests/v1/spec_decode/test_eagle.py::test_prepare_inputs_padded_index_stays_within_request_rows -x -q
```

Two requests, 2 draft tokens each, query contains only the draft tokens
(no bonus row), entire draft rejected (`valid_sampled_tokens_count = [1, 1]`).

Before the fix, the kernel emits `[-1, 1]` — request 1 gathers out of
bounds, request 2 gathers request 1's rows [evidence: before.log].
After the fix, `[0, 2]` — both clamped to their own first query row
[evidence: after.log].

## Fix

Clamp `index_to_sample` to `query_start_loc[req_idx]` (the request's own
first row) in both implementations:

- Triton kernel: `tl.maximum(index_to_sample, tl.load(query_start_loc_gpu_ptr + req_idx))`
- CPU C++: `std::max(index_to_sample, query_loc_ptr[req_idx])`

This is a no-op whenever the bonus row is present: with
`valid_count >= 1`, `num_rejected_tokens <= num_draft_tokens` and the raw
index is already `>= query_start_loc[req_idx]`. The boundary is exercised
by a test where a fully-rejected request lands exactly on its first row
[evidence: normal-path.log].

Clamping to the request's own start (rather than to 0) is required for
multi-request batches: `index_to_sample` is an absolute row index, so a
0-clamp would point later requests into request 1's rows.

## Test plan

```bash
python -m pytest tests/v1/spec_decode/test_eagle.py -k prepare_inputs_padded -q
```

Two new tests in tests/v1/spec_decode/test_eagle.py (hermetic configs, no
network):

- `test_prepare_inputs_padded_index_stays_within_request_rows` — the
  underflow scenario above; asserts `[0, 2]`.
- `test_prepare_inputs_padded_unaffected_when_bonus_row_present` — the
  standard layout (bonus row present, rejections `[1, 0, 2]`); asserts the
  historical expected output `[1, 5, 6]`, proving the clamp is a no-op
  including the exact-boundary case.

The pre-existing `test_prepare_inputs_padded` (same scenario via gated
meta-llama configs) runs in upstream CI.

Independently walked the arithmetic on current main and it checks out. The [-1, 1] example from the issue falls out of the formula exactly.

Both call sites are covered: the Triton kernel here and the CPU twin (csrc/cpu/spec_decode_utils.cpp had the same unclamped line). query_start_loc[req_idx] is the right clamp boundary, it keeps the gather inside the request's own rows in every case.

One premise I cannot confirm from source alone: that PP actually produces num_scheduled_tokens == num_draft_tokens (no bonus row) in the wild. The kernel bug is real given the input state, and the clamp is harmless when the state never occurs, so this is worth taking either way. If someone with a PP setup can point at the draft-only scheduling step, that closes the loop.


- michael-gpu · comment · 2026-10-09T19:31:24Z · [source](https://github.com/vllm-project/vllm/pull/60898#issuecomment-6087849806)

Thanks for the independent verification — and for pushing on the premise; it led to a stronger answer than the PR originally carried.

**On the PP premise:** the draft-only scheduling state is real — we hit it in production with PP + MTP (async scheduling disabled): the worker-side sanity assert fired with 1 query row vs 2 logits rows, which is exactly the no-bonus-row state reaching the spec-decode path. On current main that state trips the assert at `vllm/v1/worker/gpu/model_runner.py` (`assert (num_scheduled_tokens_np >= num_logits).all()` — its comment acknowledges query rows can come up short) rather than reaching the kernel, so on main it manifests as a crash, not silent corruption.

**But the underflow is reachable on current main without PP**, via the drafter's discard path: `eagle_prepare_next_token_padded_kernel` (vllm/v1/spec_decode/utils.py) stores `valid_sampled_tokens_count = 0` for requests the drafter discarded (over capacity). `num_rejected_tokens` then evaluates to `num_draft + 1` while the query still carries the bonus row, so `index_to_sample = query_start_loc[req] - 2` — with the scheduler's assert still satisfied. I've added a third test covering exactly this input state (`test_prepare_inputs_padded_discarded_request_zero_valid_count`): before the fix the kernel emits `[-1, 2]`, after the fix `[0, 3]`, captured on an RTX 3090 (before/after logs in the description).

The clamp stands either way, as you said — but the discard path makes it a live correctness fix on main, not just hardening.
