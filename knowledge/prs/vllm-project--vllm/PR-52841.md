# [Rust Frontend] Add ERNIE 4.5 tool and reasoning parsers

[Upstream PR](https://github.com/vllm-project/vllm/pull/52841) · state: open · merged: False

## Original PR description

## Purpose

Add the `ernie45` tool parser and `ernie45` reasoning parser to the Rust frontend (#44280). ERNIE 4.5 is not on the current parser checklist there; the parsers are proposed because the ERNIE 4.5 thinking models are a current, widely used open model family whose output needs both a reasoning and a tool parser to be served at all (the Python frontend ships `ernie45` for both, and the model card points vLLM users at them). Happy to close if the maintainers consider the family out of scope.

ERNIE 4.5 thinking models (`baidu/ERNIE-4.5-21B-A3B-Thinking`) prefill `<think>\n` in the generation prompt and emit

```text
{reasoning}\n</think>\n<response>\n{content}\n</response>\n\n\n<tool_call>\n{"name": ..., "arguments": {...}}\n</tool_call>\n
```

### Reasoning parser (`rust/src/parser/src/reasoning/ernie45.rs`)

Wraps the shared delimited `<think>`/`</think>` state machine with prompt-first initialization (the templates prefill `<think>` and the model only emits `</think>`) and adds a small state machine for the `<response>` answer wrapper that strips exactly the framing the chat template renders, following the convention of the other Rust parsers and the roundtrip test rather than byte-for-byte Python output (Python's own parser is not self-consistent here: non-streaming returns `("reason\n", "\nanswer\n")`, streaming strips token by token):

- the single `\n` right before `</think>` is dropped from reasoning;
- the run of newlines directly after `</think>` is dropped from content (the model does not always reproduce the template's single newline);
- if the content then opens with `<response>`, the marker and the single `\n` after it are dropped; inside the answer, `</response>` and the single `\n` before it are dropped; the run of newlines after `</response>` is dropped;
- everything after `</response>` is passed through verbatim, so `<tool_call>` blocks that follow the answer reach the tool parser untouched, response markers inside their JSON included;
- content that does not open with `<response>` (`abc\n</think>\ndef`, or a tools-only turn) is passed through as is.

Markers and framing newlines split across chunk boundaries are handled by holding back the ambiguous suffix; every test runs the input in one piece, split in two at every byte, and byte by byte, and asserts identical output. Newlines inside the answer are kept (`<response>\n\npara\n\n</response>` yields `\npara\n`).

### Tool parser (`rust/src/parser/src/tool/json/ernie45.rs`)

The ERNIE 4.5 tool-call shape (`<tool_call>{json}</tool_call>`, repeated blocks for parallel calls, optional whitespace around the JSON) is the Hermes shape, so `Ernie45ToolParser` wraps the shared marker-wrapped JSON parser under the `ernie45` name with the template's `\n\n\n<tool_call>` framing as the framed start marker, and drops the newlines the template renders after `</tool_call>` (before `<|im_end|>` and between calls) so they do not leak into content.

### Forced tool choice

For `tool_choice="required"` and named tool choice, the parser reuses the Hermes structural tag, which ends the output right after `</tool_call>` and starts it at `<tool_call>`. ERNIE 4.5 writes a newline after `</think>`, after every `</tool_call>` and between calls, so with the newline masked the model kept emitting tool calls until `max_tokens` (observed on the real model: 100+ repeated calls at 4096 tokens). `Ernie45ToolParser` now keeps the Hermes tags but allows those framing newlines around and between calls (text between calls stays rejected), with a grammar snapshot test.

### Registration and model matching

Both parsers are registered under `ernie45`. The model matcher is scoped to `ernie-4.5-21b-a3b-thinking`: the `ERNIE-4.5-*-PT` text checkpoints have no `<think>`/`<tool_call>` tokens and use a plain `User:`/`Assistant:` template, so auto-selecting the reasoning parser for them would fail at parser creation (`MissingToken`); the VL checkpoints ship only a sentencepiece tokenizer, which the Rust tokenizer backend does not load.

### Renderer: `thoughts`

The ERNIE thinking template reads assistant reasoning history from `message.thoughts` (not `reasoning`/`reasoning_content`), so `TemplateMessage` now exposes `thoughts` alongside the two existing variants. Without it the template drops reasoning from history.

### Roundtrip fixture

`baidu/ERNIE-4.5-21B-A3B-Thinking` is added to `rust/src/chat/tests/roundtrip.rs` for `reasoning_and_content` and `tool_call_mix`, but marked `#[ignore]`: the model's published `tokenizer.json` does not round-trip the shared fixture text (`2 + 2` encodes to `▁ 2 ▁▁ +` and decodes as `2  + 2`, and `4.` as `4 .`; the original `tokenizer.model` round-trips exactly), which the text-completion path has rejected since #59048. In addition `<|im_end|>` is not an EOS token for this model (`</s>` is), so the grammar replay's stop-token assumption does not hold either. The fixture can be enabled once the tokenizer is fixed upstream.

## Not a duplicate

## Test Result

On the current head (cargo, CPU):
- `vllm-parser`: 570 passed (the ERNIE tests plus the new forced-choice grammar test).
- `vllm-chat --lib`: 352 passed. The `audio_pipeline_attributes_stage_timings_to_request` failure mentioned in an earlier revision was a timing flake on a loaded machine; it passes on a quiet host on both `main` and this branch.
- `cargo fmt --check` and `cargo clippy -D warnings` clean on the touched crates.

Real model (1x H200, `baidu/ERNIE-4.5-21B-A3B-Thinking` @ 4341bb4, Rust frontend built from this branch merged into main c23ca06b6, `--reasoning-parser ernie45 --tool-call-parser ernie45 --enable-auto-tool-choice`, greedy):
- 24/24 responses parse to the same reasoning, content and tool calls as an independent parse of the generated token IDs (reasoning-only, a single call, two parallel calls, multi-turn with reasoning history rendered via `thoughts`, tools offered but not needed).
- With `VLLM_BATCH_INVARIANT=1`, streaming and non-streaming outputs are identical in every compared case, including single- and two-call responses.
- Standalone `vllm-rs serve` without parser flags auto-selects ernie45.
- `tool_choice="required"` before the grammar fix: 100+ repeated calls until `max_tokens`; after: the expected call(s) and `finish_reason: tool_calls`. Named and auto unchanged. Held-out prompts and tools (required with two tools, two needed calls, no useful tool, `parallel_tool_calls=false`, named) all end correctly.
