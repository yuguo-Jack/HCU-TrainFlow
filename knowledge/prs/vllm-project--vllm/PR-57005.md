# [Tool Calling][Bugfix] Schema-aware type correction various small fixes

[Upstream PR](https://github.com/vllm-project/vllm/pull/57005) · state: open · merged: False

## Original PR description

## Purpose

This PR aims to fix various issues in schema-aware type correction mechanism that were found by @xeophon in PR https://github.com/vllm-project/vllm/pull/53729
Since the original PR was complex enough in my opinion I decided to open this PR as a attempt to simplify the changes and describe more precisely what issues are going to be fixed. Some of the existing issues I decided to stay as it is now not to overcomplicate the fix. If there will be still a need for these fixes in the future a separate attempt should be made.

This PR fixes 4 cases:
1. Nested field inside a decoded object
Schema: item is an object with age: integer. Model: `{"item": "{\"name\":\"Alice\",\"age\":\"42\"}"}`
`{"age": "42"}` → `{"age": 42}`
_coerce_value: the string branch decoded the object and returned immediately, so recursion into its fields never happened. It now falls through.

2. Combinator instead of a direct properties
Schema: properties sits inside allOf/anyOf/oneOf — either on a property or at the root of parameters.
no coercion at all → types are coerced
get_properties: when properties is absent at the top level, look one level into the combinators. Used both in _coerce_value and in find_tool_properties.

3. const without type
Schema: `{"retries": {"const": 3}}`. The model answered correctly: `3`.
`"3"` → `3`
No type was inferred from const, the ["string"] fallback kicked in, and a correct number was turned into a string. const now yields a type the same way enum does.

4. Coercion to object returned an array
Schema: item is object (or `["object","string"]`). Model: `[1,2]`.
`[1, 2]` → `"[1,2]"`
json.loads returned whatever it parsed, and the result's type was never checked. It is now checked in the branch (isinstance) and in the tail fallback (masked against the real JSON Schema types).

- bbrowning · comment · 2026-09-16T12:08:16Z · [source](https://github.com/vllm-project/vllm/pull/57005#issuecomment-5697161827)

I did one pass of an automated code review, just to find the other regressions here besides what Flora pointed out above. Here's that list:

  
**vllm/tool_parsers/utils.py:1218 stringifies already-correct JSON scalars**

The new tail type-mask returns the raw string when `_json_type_name(parsed) not in declared`. With `{"n": {"type": "integer"}}`:
  
```
  ┌─────────────┬────────┬────────┐
  │    input    │ before │ after  │
  ├─────────────┼────────┼────────┤
  │ {"n": null} │ null   │ "null" │
  ├─────────────┼────────┼────────┤
  │ {"n": true} │ true   │ "true" │
  ├─────────────┼────────┼────────┤
  │ {"n": 3.5}  │ 3.5    │ "3.5"  │
  └─────────────┴────────┴────────┘
```
  
  A model emitting null for an optional param whose schema omits "null" from its type — common — now passes the 4-character string "null" to the tool. `k2_horizon_tool_parser` regresses identically via `_coerce_json_value`/`_coerce_xml_value`. No test covers it. Suggested fix: apply the mask only when parsed is a container, and/or never let `_coerce_value` replace a non-str with a str. Side note: `_json_type_name` never returns "number" for an int, so a declared {"number"} rejects parsed integers.
  
 **utils.py:1028, allOf returns only the first branch**

`allOf` is a conjunction; the early `return branch["properties"]` drops the rest. Two branches declaring a and b → only a gets coerced. That's the exact schema-generator shape the PR claims to fix, so the fix only works for single-branch allOf.
  
**utils.py:1028, anyOf/oneOf coerces with the wrong branch's types**

First-branch-with-properties wins, so a oneOf where v is integer in one branch and string in another turns a correct `"007"` into `7` - and before the PR there was no coercion at all. Safe behavior is to skip keys whose declared type differs across branches. Propagates to `k2_horizon` and `deepseek_v4._unwrap_wrapper_args`.
