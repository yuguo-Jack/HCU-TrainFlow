# [Perf][Kernel][WIP] Single-launch fused scoring+top-k kernel for sparse-indexer prefill, without materializing logits

[Upstream PR](https://github.com/vllm-project/vllm/pull/60618) · state: open · merged: False

## Original PR description

First of all, this is WIP, so any suggestion is welcomed.

### Summary

* Adds one CUDA kernel that computes the DSA indexer scores of every visible key and selects each row's top-2048 keys **without materializing the `[rows, keys]` logits matrix**.
* One call covers a prefill chunk of up to 16,384 query rows and up to 1M keys. The dense path needs up to 127 call pairs (`fp8_mqa_logits` + `top_k_per_row_prefill`) for the same chunk.
* Opt-in (`VLLM_USE_FUSED_MQA_TOPK=1`, default 0). The dense path is unchanged and remains the default and the fallback.

### Motivation: what materializing the scores costs

The dense prefill path writes the fp32 scores of every (query row, visible key) pair to HBM, then reads them back to select the top-k. One 16,384-row prefill chunk needs `16,384 × keys × 4 B` of logits:

| Keys | Logits for one 16K-row chunk | Dense calls under the 512 MiB budget | Logits HBM traffic (write + read) |
|---|---|---|---|
| 16K | 1 GiB | 2 | 2 GiB |
| 128K | 8 GiB | 16 | 16 GiB |
| 512K | 32 GiB | 64 | 64 GiB |
| 1M | 64 GiB | 127 | 128 GiB |

This produces the following pattern:
<img width="3757" height="293" alt="Screenshot 2026-10-08 at 12 18 17" src="https://github.com/user-attachments/assets/ce60736e-03e9-45dc-9355-7b517f9c8907" />

Which can become increasingly concerning the larger the context, e.g. ISL 512K:
<img width="3727" height="279" alt="Screenshot 2026-10-08 at 12 19 32" src="https://github.com/user-attachments/assets/9a00072a-b55f-40e5-bed5-667394b1abdf" />

Two consequences:

1. **The logits budget trades KV-cache capacity against indexer speed.** During memory profiling, `sparse_attn_indexer` allocates a dummy `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB` buffer, so the logits budget is part of the  peak memory the KV cache is sized from. On GLM-5.x with an FP8 KV cache, one token costs 47.7 KB per GPU (78 MLA layers × 576 B + 21 indexer layers × 132 B;  MLA KV is replicated across TP ranks). Measured at startup (TP4, B300, `--max-model-len 1048576`):

   | Configuration | Available KV memory | KV cache tokens |
   |---|---|---|
   | Dense, 512 MiB budget (default) | 115.66 GiB | 2,603,456 |
   | Dense, 8 GiB budget | 109.23 GiB | 2,458,816 (−5.6%) |
   | Fused (this PR) | 115.37 GiB | 2,596,928 (−0.25%) |

   At the default budget the logits buffer fits under the profiling run's other peak allocations, so it costs no KV cache. The cost is speed: rows per dense call shrink as keys grow (2²⁷ / keys), so a 128K-token prefill in 16K-token steps needs 76 dense call pairs and a 1M-token prefill needs 4,217, against 8 and 64 fused calls. Buying fewer dense calls means raising the budget, and that memory comes straight out of the KV cache. An 8 GiB budget (one dense call per 16K-row chunk at 128K keys) costs 144,640 tokens of KV cache. One dense call per chunk at 1M keys would need 64 GiB, more than the KV cache of the entire 1M-token sequence (46.6 GiB). The fused kernel gets single-call chunks at every length for a fixed 296 MiB workspace.
   
2. **The logits round trip is pure overhead.** Only 2048 of the `keys` scores per row are needed. The fused kernel keeps only a gated candidate set: in shared memory up to 16K keys, and above that about 3K–7K candidates per row at 6 B each, i.e. about 0.3–0.7 GB written per 16K-row chunk, versus 16–128 GiB of logits traffic at 128K–1M keys.

### What this PR does

<img width="2925" height="291" alt="Screenshot 2026-10-08 at 12 18 53" src="https://github.com/user-attachments/assets/c829d24b-9d43-4a4d-94ab-95df6f5053d7" />

### Memory

* Fused workspace: a pool of 2 eight-row slots per SM, fixed size, independent of rows, keys and context. It is 296 MiB on a 148-SM B300, allocated once per device during the profiling run, so it is accounted against the KV cache: −6,528 tokens (−0.25%) versus dense at the default budget (table above).
* With the fused path enabled and `max_model_len ≤ 1M`, no prefill chunk can reach the dense path, so the profiling run skips the dense logits dummy buffer. On GLM-5.x this changes nothing measurable, because that buffer sits under the profiling peak, but it no longer reserves memory the fused path never uses.

### Related Work

This kernel's sampled gate is inspired by LiteTopK (#48726, arXiv:2607.11976): indexer scores concentrate in a narrow range, so a sampled threshold can discard most keys before the top-k. I open a separate PR because:

* **Scope:** LiteTopK fuses only single-request chunks of exactly 8192/8128 rows with 192K–1M keys. Other chunks keep dense chunking, and even a fused chunk needs a separate seed-logits launch and about 2.6 GiB of workspace. Here every eligible chunk (≤ 16384 rows, ≤ 1M keys, multi-request) is one launch with no logits buffer and a 296 MiB workspace.
* **Correctness:** on B300 (commit `c7184685`) I found an undersized shared-memory allocation (4100 memcheck errors), racecheck hazards in the candidate ring and the seed/radix-select kernels, and no recovery from candidate-buffer overflow (the mapping kernel traps). LiteTopK's selection is also approximate (99.998% recall); this PR matches dense up to boundary ties.
* **Gain on B300:** the only B300 serving data in #48726 shows TTFT within ~1% of  stock at ~200K tokens. This PR measures 1.10× at 256K and 2.05× at 1.04M (different setups, so not like-for-like).

The PR credits LiteTopK (arXiv:2607.11976) as the inspiration for the sampled gate where it is implemented.

However, the scoring half of this kernel is largely an adaptation of DeepSeek's code. This PR replaces the logits write-out with a sampled gate, candidate emission and in-kernel top-k selection.
