## Purpose

With `VLLM_BATCH_INVARIANT=1` and `compilation_config.custom_ops=["all"]`, so that the norm and activation kernels run in both modes, the same model still produces different bits in eager mode and under torch.compile. On Nemotron-H-8B-Base (bf16, one 578-token prompt, GB200, Triton 3.7.1) 85% of the logits differ and only 2 of 577 prompt logprobs are identical. Each mode is batch-invariant on its own, but they disagree with each other, which matters when vLLM output is compared against a reference computed elsewhere.

The cause is narrow. The Triton launches that `forward_cuda` selects (`_rms_norm_kernel` behind `rms_norm_batch_invariant`, and `_layer_norm_fwd_1pass_kernel` behind `rms_norm_gated`) are traced by Dynamo and re-emitted by Inductor, which types the Python float `eps` as fp64, while the eager launch passes it as fp32. `mean_sq + eps` is then computed in fp64 under compile and the reciprocal square root rounds differently for about 1e-5 of the output elements; the following layers amplify that. Warps and stages are identical in both modes, and the persistent matmul, which has no float arguments, is bitwise identical eager versus compiled.

This PR casts `eps` to fp32 inside the two kernels. The compiled kernels become bitwise identical to their eager launches and eager callers are unchanged. It affects the configurations in which compiled batch-invariant mode actually traces these kernels: the residual-free RMSNorm path and the `rms_norm_gated` Triton kernel (on main the gated Mamba2 norm reaches it for `n_groups == 1`). The fused-residual C++ path, model-specific norms and quantized norm paths are not touched.

Related, not duplicates: #32992 and #35404 (compiled batch invariance on B200 and gpt-oss, GEMM side), #39096 (compile and CUDA graphs on SM<90), #48391 (pins the fused_add_rms_norm block size), #40921 (RMSNormGated Dynamo tracing failure at startup). None covers the fp64 `eps` in the re-emitted kernels.

## Test Plan

```bash
pytest tests/kernels/mamba/test_layernorm_gated_compile.py
pytest tests/v1/determinism/test_rms_norm_batch_invariant.py
```

The new tests compile each wrapper with `torch.compile(backend="inductor")` and require bitwise equality with the eager launch at two activation scales; small activations make `mean(x^2)` comparable to `eps`, where the fp64 addition changes the rounding. Both kernels are tested in bf16, the plain RMSNorm also in fp16.

## Test Result

GB200, Triton 3.7.1, on the final commit: the 12 new cases pass, the full RMSNorm batch-invariance file passes (479 cases), pre-commit passes on the changed files. Without the casts the new tests fail (RMSNorm 4 of 4, gated norm 8 of 8), so they detect the problem.

End to end, out of tree, on a development tree that also carries #55627, #55905, #56244 and #52905: Nemotron-H-8B-Base, one 578-token prompt, `VLLM_BATCH_INVARIANT=1`, `custom_ops=["all"]`: eager and compiled logits and all 577 prompt logprobs are bitwise identical with the casts, against 85% of logits differing without them; eager results are unchanged. With the default `custom_ops` setting the compiled path still differs from eager, because Inductor decomposes the norm and activation ops instead of running these kernels; that is a separate question for batch-invariant mode.
