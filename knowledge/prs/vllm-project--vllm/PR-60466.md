# [Feat][Frontend] structured decisions: DiffusionGemma read strategy

[Upstream PR](https://github.com/vllm-project/vllm/pull/60466) · state: closed · merged: True

## Original PR description

## Overview

Implement DiffusionGemma's structured read strategy for single questions.  Follow-up to #59299.

#60696 (noul and score question types) is landing in parallel. A merge of the two is here: https://github.com/mmastrac/vllm/tree/systemone-question-types-dgemma

## Claims

Serve DiffusionGemma (`DiffusionGemmaForBlockDiffusion`) on `/v1/systemone`.

_Important_: Questions are not diffused en-banc - that will be a follow-up, opt-in option. In this PR, each question gets its own canvas.

- Each question is one read-only request with one denoising step (`diffusion_max_steps` 1, `diffusion_read_only`). The prompt is the same one the next-token strategy builds (A to Z labels, thinking off), ended with the empty thought block a reply with thinking off starts with.
- The canvas is 16 tokens: the label slot as noise, then `<turn|>`, then padding. The label logprobs come from the slot, at the denoising schedule's temperature 1.
(`label_mass` 0.27 to 0.82). With the block in the prompt, `label_mass` at the slot is 0.99 to 1.00.
- The noise at the slot is drawn from a hash of the prompt, so a repeated read gets the same canvas. The DiffusionGemma engine does not guarantee the same output across batch sizes, so reads can still differ slightly between runs.

Important note: The empty thought block must go in the prompt, not as fixed tokens in the canvas. DiffusionGemma fails to converge with the label in the correct slot otherwise.

## Validation

On a GB10 (DGX Spark) with DiffusionGemma NVFP4 (served canvas 64), `vllm/vllm-openai:nightly` at 92044241a with this branch's files mounted over it, no additional flags beyond what was needed for diffusiongemma:

- **Question sets**: every answer is right on copy, routing, yes/no and language questions, with `label_mass` 0.99 to 1.00. A forced one-option coin flip reads 0.72. A read takes about 100 ms. Thinking on returns 400.
- **JevBench** (231 public items, one read per item, thinking off, the `jevbench_systemone.py` client from #59299): Intelligence 78.4 to 80.1 over four runs (comparison: djev's published one-step reads score 78.9)
- **Tests**: `test_canvas_read` pins the canvas layout and the thought block appended to the prompt. `pytest tests/entrypoints/generate/structured_decisions tests/entrypoints/generate/generative_scoring` passes on Qwen3-0.6B (41 passed).

## Details

- `NextTokenStrategy` gains two hooks, `_sampling_params` and `_read_input`, which `CanvasStrategy` overrides. `READ_STRATEGIES` maps each supported architecture to its strategy.
- `/v1/systemone` now answers on any DiffusionGemma server. A served canvas shorter than 16 tokens, or a tokenizer without a pad token, turns the endpoint off (501).
- Not covered in CI: there is no DiffusionGemma end-to-end test

- simon-veitner-redhat · comment · 2026-10-09T14:21:29Z · [source](https://github.com/vllm-project/vllm/pull/60466#issuecomment-6082809920)

Thanks for the PR. I ran it on an H200 with `google/diffusiongemma-26B-A4B-it` and have one fix and three smaller points.

**1. Canvas reads near `max_model_len`**

The renderer's length check reserves one output token (`ReadPromptRequest.build_tok_params`, `max_output_tokens=1`), but a canvas read then appends the 4 thought tokens and needs a 16-slot canvas. With `--max-model-len 1024`:

- rendered prompt of 1020 to 1023 tokens: the engine returns a 400 for a "decoder prompt" of 1024 to 1027 tokens, longer than anything the client sent;
- rendered prompt of 1005 to 1019 tokens: the canvas is cut short and the read returns a 200 that can be far off. With one slot left, `label_mass` was 0.0096 (0.9997 for the same read with room). Over 20 statements, the median `label_mass` was 0.21 with 4 slots and 0.003 with 2.

A check in `CanvasStrategy._read_input` turns both into one 400 that names the real budget:

```python
extra = len(self.thought) + self.width
if len(prompt_ids) + extra > self.max_model_len:
    raise StructuredDecisionError(
        f"the prompt has {len(prompt_ids)} tokens and a canvas read adds "
        f"{extra}; together they exceed max_model_len={self.max_model_len}"
    )
```

with `self.max_model_len = vllm_config.model_config.max_model_len` in `__init__`. The commit, with one case in `test_canvas_read`, is https://github.com/simon-veitner-redhat/vllm/commit/d407da4e81108b6e4969f042f970716be8cbfb26 (branch `pr60466-read-fixes`), if you want to cherry-pick it.

**2. Silent 501 when the strategy cannot be built**

`init_generate_state` (`vllm/entrypoints/generate/api_router.py:246`) catches the `ValueError` from the strategy's `__init__` and drops it. This PR adds three new causes (canvas too short, no pad token, no `<turn|>` token). Serving DiffusionGemma with `canvas_length` 8 gives `501 The model does not support the structured decision API` on every request, and nothing in the log says why. Could you log the reason there?

```python
except ValueError as e:
    logger.info("/v1/systemone is disabled: %s", e)
    strategy = None
```

`info` rather than `warning`, since every unsupported architecture goes through the same path at startup.

**3. The token in the label slot**

`_sampling_params` fills the label slot of the canvas with one vocabulary token picked by `random.Random(sha256(prompt_ids))`. Any change to the prompt picks a different token, and some tokens pull most of the probability away from the labels, so `label_mass` and `confidence` jump.

Experiment: one `choice` question ("Which team should handle this ticket?", labels billing / shipping / security), sent twice to `/v1/systemone`. The two requests are identical except for one digit in the state:

```
state: "Ticket <N>: I was charged for a delivery that never arrived and I want my money back."
```

| N | token the hash puts in the slot | answer | `label_mass` | `confidence` | `argmax_is_label` |
| --- | --- | --- | --- | --- | --- |
| 1027 | (hash pick) | billing | 0.9999 | 0.986 | true |
| 1028 | `Ar` | billing | 0.0298 | 0.028 | false |
| 1028, pad token in the slot instead | pad | billing | 0.9999 | 0.987 | true |

The pad row replays the exact 1028 prompt and canvas through `/v1/completions` with only the slot token changed.

On the 1028 prompt we then kept everything fixed and only swapped the slot token for 300 random vocabulary tokens: the answer stayed billing every time, but 3 of 300 tokens pushed `label_mass` below 0.5 (worst 0.0015, token `STR`). With a 1000-token state the same sweep put 20 of 100 tokens below 0.5.

We tried pad in the slot (`canvas = [self.pad, self.end] + [self.pad] * (self.width - 2)`) on the 231 public JevBench items, 5 passes each:

| | hashed token (this PR) | pad |
| --- | --- | --- |
| accuracy | 83.1% | 84.8% |
| worst confidence swing over 5 passes | 0.62 | 0.34 |
| AUROC of `confidence` | 0.867 | 0.820 |
| p50 latency, one at a time | 22 ms | 22 ms |

Pad costs nothing at serving time and drops the `hashlib`, `json` and `random` imports and `vocab_size`. The cost is ranking quality: part of the per-read `label_mass` variation was informative. Since the model was trained with random noise in the canvas, you know better whether pad is safe. Could you confirm it on your own sets?

**4. Run-to-run variance in the docs**

Not a blocker, and mostly engine behavior. Over 5 passes on the same 231 items (2 sequential, 3 with 16 or 64 requests in flight), the confidence of an unchanged answer moved by up to 0.62, and 4 items changed answer, all with confidence below 0.6. The causes are the first read of a prompt against later prefix-cache hits, and batch composition. Only `VLLM_BATCH_INVARIANT=1` removed it (0 changes over 5 passes), at p50 22 → 36 ms and 144 → 104 questions/s on an H200. Could you add a paragraph after "How it works" in `structured_decisions.md`, for example:

> Probabilities can differ between identical requests: they depend on which requests share a batch and, for DiffusionGemma, on whether the read hits the prefix cache. Set `VLLM_BATCH_INVARIANT=1` for reads that repeat exactly, at a cost in throughput.

**5. `noul` without criteria (on main, not this PR)**

While testing the merge with main, `noul` questions without `criteria` lost most of their `label_mass` on DiffusionGemma (0.013 to 0.48), because the model answers "Yes"/"No" while #60696 reads lowercase `yes`/`no`. That is not caused by this PR, so I opened #60862 for it.
