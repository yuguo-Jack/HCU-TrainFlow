# [ROCm][Bugfix] Pass per-sequence context lengths to the AITER paged MQA-logits kernels

[Upstream PR](https://github.com/vllm-project/vllm/pull/59420) · state: closed · merged: True

## Original PR description

## Error

MTP with native DSA-indexer decode above `next_n=2` crashes during warm-up on MI355X (seen at `next_n=3` and `next_n=6`). GLM-5.2-MXFP4, TP4, `num_speculative_tokens=5` (`next_n=6`), Gluon paged MQA logits:

```
Memory access fault by GPU node-4 (Agent handle: 0x20465ea0) on address 0x792dc0bf1000. Reason: Unknown.
```

Where it does not crash, the indexer silently uses wrong causal bounds: in a direct call at `next_n=3`, the 8192-token sequence loses its last 2 valid positions in every row (9/12 rows correct).

## Cause

With native decode (`next_n > 1`), `rocm_fp8_paged_mqa_logits` receives a `(B, next_n)` table of per-row context lengths, `[b, j] = L_b - next_n + j + 1`, built in [`indexer.py#L1136-L1152`](https://github.com/vllm-project/vllm/blob/2df122e65e87dc12870ce5f0180b49f012e7a53b/vllm/v1/attention/backends/mla/indexer.py#L1136-L1152). The AITER Gluon `deepgemm_fp8_paged_mqa_logits` and `deepgemm_fp8_paged_mqa_logits_stage1` kernels read the table as a flat `[B]` array and some sequences get another row's length.

Example: 4 requests, `next_n=3`, context lengths 8192 / 1500 / 3000 / 700:

| `b` | `j=0` | `j=1` | `j=2` | `L_b` |
|---|---|---|---|---|
| 0 | 8190 | 8191 | **8192** | 8192 |
| 1 | 1498 | 1499 | **1500** | 1500 |
| 2 | 2998 | 2999 | **3000** | 3000 |
| 3 | 698 | 699 | **700** | 700 |

The kernel expects `[8192, 1500, 3000, 700]` and computes each row's bound itself. Reading the `(4, 3)` table as `[4]`, it gets the first four values in memory, `[8190, 8191, 8192, 1498]`: request 0 loses its last 2 positions in every row, and requests 1 to 3 get lengths past their own KV pages, the likely source of the fault. Column `j = next_n - 1` equals `L_b`, which is what the kernel needs.

## Fix

Pass the kernels the last column, which is the per-sequence length. `[B]` and `(B, 1)` inputs, the C4A Triton path and the torch fallback are unchanged.

On ROCm native decode is used for `next_n` 1 and 2 today, so MTP with one speculative token goes through this path. #59421 raises that cap, which needs this fix.

## Test Plan

- `pytest tests/v1/attention/test_rocm_paged_mqa_context_lens.py` (new): the helper returns the per-sequence lengths for a `(B, next_n)` table and passes `[B]` / `(B, 1)` through unchanged.
- Direct call of `rocm_fp8_paged_mqa_logits` on one MI355X against a torch reference: `B=4`, `next_n=3`, contexts 8192/1500/3000/700, block size 64.
