# [Rust Frontend][gRPC] Remove `GenerateStream` producer task so disconnects abort requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/60922) · state: closed · merged: True

## Original PR description

## Overview

Cancel native gRPC `GenerateStream` requests promptly when the client disconnects, including requests that have produced no engine output, by removing the detached producer task so that the response body owns the generation stream. Related downstream report: [ai-dynamo/dynamo#16012](https://github.com/ai-dynamo/dynamo/issues/16012).

This PR was first opened by @alec-flowers with a `tx.closed()` race in the producer loop; the root cause is the `tokio::spawn` itself, so this revision removes it instead. The original description is kept below.

## Claims

- The gRPC response body owns the generation stream, so a client disconnect drops it and triggers the existing auto-abort, even before any engine output. This matches the HTTP SSE handlers, which already return the stream directly.
- Removing the producer task is not a performance regression: on a mock engine it saves one cross-runtime wakeup per delivery and cuts frontend CPU substantially at default worker counts.

## Validation

- `dropping_generate_stream_aborts_before_engine_output` (added in the first revision) passes, and fails on the original spawn code with the five-second abort timeout.
- `cargo nextest run -p vllm-server`: **455 passed**; `cargo clippy -p vllm-server --tests -- -D warnings`: passed.

Mock-engine comparison on GB200: Rust mock engine DP=4, one token per step; closed-loop gRPC client, 32 prompt tokens → 512 output tokens with text output, concurrency 2048 over 32 HTTP/2 connections, 32768 requests after warmup; two runs per variant in alternating order.

| Regime | Variant | req/s | Frontend CPU |
| --- | --- | ---: | ---: |
| Default workers (frontend + mock on 70 cores) | spawn (base) | 1495 | 350 s |
| | `tx.closed()` select (first revision) | 1500 | 376 s |
| | no spawn (this PR) | **2366 (+58%)** | **151 s (−57%)** |
| Frontend-bound (frontend on 8 cores) | spawn (base) | 2255 | 86 s |
| | `tx.closed()` select (first revision) | 2371 | 85 s |
| | no spawn (this PR) | 2305 | 81 s (−6%) |

The mock emits a token every ~0.1 ms per request, so wakeup overhead weighs far more than with a real model; the gain in production will be much smaller.

## Details

`generate_stream` spawned a producer task that owned the generation stream and fed a 32-slot channel; the response body held only the receiver. A client disconnect dropped the receiver, and the producer only noticed when `tx.send()` failed. A queued request produces no events, so its stream and engine work stayed alive indefinitely.

The conversion loop is now a `#[try_stream]` fn returned directly as the response body, instrumented with the request span, as the HTTP SSE handlers do. The match body is unchanged, an error still ends the stream after it is sent, and the "stream closed" log stays at the normal end of the stream. `tokio-stream` is no longer needed by `vllm-server`.

The task did not provide useful isolation, since the per-request engine output channel is already unbounded. Its one side effect was running detokenization and proto conversion on the request runtime, at the cost of an extra cross-runtime wakeup per delivery (ZMQ → request → IO runtime). HTTP SSE already does this work while the body is polled on the IO runtime, and the frontend-bound run above shows no cost from moving it.

## Original description (first revision)

### Overview

Cancel native gRPC `GenerateStream` requests promptly when the response stream disconnects, including requests that have produced no engine output. Related downstream report: [ai-dynamo/dynamo#16012](https://github.com/ai-dynamo/dynamo/issues/16012).

### Claims

- A disconnected client releases the owned generation stream without waiting for another engine event, allowing the existing auto-abort path to run.
- One regression test verifies the real gRPC transport and Rust engine client deliver the correct request ID in an engine abort while the scripted engine emits no output.

### Validation

- The new `dropping_generate_stream_aborts_before_engine_output` test fails on unpatched upstream with a five-second abort timeout.
- `cargo test --manifest-path rust/Cargo.toml -p vllm-server --locked grpc::tests -- --nocapture`: **40 passed**, including the new regression and existing normal-streaming/error/control tests. `cargo-nextest` was unavailable locally.
- `cargo clippy --manifest-path rust/Cargo.toml -p vllm-server --tests --locked -- -D warnings`: passed.
- `pre-commit run --files rust/src/server/src/grpc/inference.rs rust/src/server/src/grpc/tests.rs`: passed.
- The test is included in the existing Rust frontend workspace CI suite.

Real-engine validation used one H100 PCIe, `Qwen/Qwen3-0.6B`, and the Python engine from `vllm/vllm-openai:v0.31.0-ubuntu2404`. Both native server binaries were built from `ffdde24f54`; their only source difference was this producer-loop fix.

| Scenario | Unpatched | Patched |
| --- | --- | --- |
| Disconnect a queued, zero-token request with two blockers still running | Waiting=1 throughout the five-second observation window | Waiting=0 observed after **57 ms**, running=2 |
| Subsequent normal streaming request | Completed, 16 tokens | Completed, 16 tokens |

One run per variant; occupancy was polled approximately every 50 ms. The 57 ms value is observed queue-removal latency, not a precise engine-abort timestamp. These were direct native gRPC requests, without Dynamo or a client-issued `Control.Abort` during the observation window.

Server command for each binary:

```bash
vllm-rs serve Qwen/Qwen3-0.6B \
  --host 127.0.0.1 --port 18100 --grpc-port 18200 \
  --max-model-len 4096 -- \
  --enforce-eager --max-num-seqs 2 \
  --kv-cache-memory-bytes 1119388000 --gpu-memory-utilization 0.1
```

Submit two streaming requests with `max_new_tokens=3500`, `min_new_tokens=3499`, and `ignore_eos=true`; require output from both and running=2. Submit a third request and require running=2/waiting=1 with zero target tokens. Cancel only that gRPC stream and observe the scheduler gauges while both blockers remain active. Explicit abort is used afterward solely to clean up the test load.

### Details

The detached response producer owns the generation stream. Previously it awaited `stream.next()` and only detected a disconnected receiver when `tx.send()` failed. A queued request can produce no events, keeping the stream and its engine work alive indefinitely.

Race `tx.closed()` against the next engine event with `tokio::select!`, prioritizing closure when both are ready. Exiting drops the stream and uses the existing per-request auto-abort machinery. This adds no polling task, timer, protocol change, or explicit abort RPC. The regression reuses the existing server fixture and synchronizes on engine admission.

Open upstream PR searches for GenerateStream cancellation and gRPC disconnect found no duplicate. [Dynamo #16007](https://github.com/ai-dynamo/dynamo/pull/16007) instead sends an explicit abort from a downstream client; this change repairs native server disconnect handling for all clients.
