# [Feature][KV Offload] Support joint GPU/CPU prefix cache lookup

[Upstream PR](https://github.com/vllm-project/vllm/pull/57325) · state: open · merged: False

## Original PR description

## Purpose

### Background

We deploy DeepSeek V4 Flash Vision Exp with vLLM Ascend v0.27 in our internal network, with Simple CPU Offload enabled. During operation, we observed a cache miss rate exceeding 10%. Investigation showed that some reusable cache entries were not being retrieved due to the unimplemented TODO in `vllm/v1/simple_kv_offload/manager.py`: the existing API only matches a CPU suffix following the GPU prefix, rather than searching for a complete valid prefix across both pools.

After implementing joint lookup, we ported the change to the v0.27 branch in our fork and redeployed it in the same environment. The deployment has been running for five days, with normal operation and successful retrieval of cache entries previously affected by this limitation.

This PR targets upstream main. The deployment observations above come from the v0.27 backport in our fork.

### Changes

Support valid prefixes composed of interleaved GPU and CPU cache blocks, replacing the limitation of matching a GPU prefix followed by a CPU suffix.

For example, given a `GPU → CPU → GPU` cache layout, reuse both GPU blocks directly and allocate and load a target block only for the middle CPU block. When both pools contain a required block, prefer the GPU copy.

The implementation:

- Provides a read-only joint lookup view for existing attention-specific matching algorithms, preserving hybrid-attention convergence and memoizing queries within each request.
- Records hit sources by group and block position, distinguishing GPU hits, CPU blocks requiring loads, and attention padding.
- Pins source blocks before allocation and allocates targets only for CPU hits. Targets are registered in the cache after loading completes, without re-registering interleaved GPU hits.
- Attributes GPU/CPU cache statistics and cache events to their actual sources.
- Preserves full-block CPU loads, copy-on-write for partial GPU hits, and existing watermark and speculative-decoding reservation rules. If capacity is insufficient, allocation of the entire match is deferred.

### Relationship to related work

This PR implements joint lookup for interleaved GPU/CPU prefixes in `SimpleCPUOffloadConnector`. The related #52773 / #52774 address boundary backfill in `OffloadingConnector`, so the connector and implementation scope differ.

## Test Plan

Cover the following behaviors:

- All-GPU, all-CPU, multiple interleavings, duplicate hits across pools, missing intermediate blocks, and different sources across groups.
- GPU block identity reuse, exact CPU transfer positions, and no publication of target cache entries before loading completes.
- SWA/Mamba, different block sizes, DCP/EAGLE matching boundaries, final-token recomputation, and copy-on-write for partial blocks.
- Insufficient capacity, speculative-decoding reservations, and reference cleanup after retries, cancellation, and reset.
- Bypassing separate GPU/CPU scans on the joint path, with no repeated probes for the same hash/group.
- GPU/CPU statistics and interleaved cache events.

Local real-model validation uses OPT-125m, Qwen3-0.6B, and Qwen3.5-0.8B. GPU cache capacity is constrained and cache residency layouts are controlled to trigger actual CPU loads. Validation compares cold-cache and warm-cache outputs under deterministic generation settings and checks transfer positions and reference cleanup.

## Test Result

After the September 20 rebase, 575 distinct relevant tests passed (574 in the broad run and one rerun after restoring the Ray test dependency), along with pre-commit and Python 3.10/3.12 type checks. This includes regressions for discarding short joint hits under bounded prefix replay and replaying longer hits after CPU loading. Earlier, 22 real-model combinations passed, completing 9,146 exact cold/warm output comparisons and exercising actual CPU loads, copy-on-write, and preemption; that model matrix has not been rerun after this rebase. Some OPT/MTP combinations showed cold/warm differences that also reproduced on the legacy lookup path and are excluded from the passing results.
