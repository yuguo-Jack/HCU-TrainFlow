# [ROCm][DSv4] Fuse the shared expert into AITER MegaMoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/61004) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Adds an opt-in env var, `VLLM_ROCM_AITER_MEGA_MOE_FUSE_SHARED_EXPERTS=1`. With it set, `--moe-backend aiter_mega_moe` (#59685) runs DeepSeek-V4's shared expert inside AITER MegaMoEV2, as one extra local expert per EP rank, instead of as a separate FP8 MLP after the MoE. This is the ROCm counterpart of the DeepGEMM MegaMoE shared-expert fusion (#53040), using the same extra-slot scheme as sglang on ROCm (sgl-project/sglang#35619).

## Claims

- DeepSeek-V4-Pro on MI355X (DEP8): decode **ITL drops 4–9%** at concurrency 1–64 and **2–5%** at 128.
- **Output throughput rises 3–8%** at concurrency 1–64. At concurrency 128 the gain is small (+1–2%).
- Accuracy is unchanged:
  - Thinking mode: GPQA-Diamond 0.894 → 0.899 (official Think High 89.1) and MMLU-Pro 0.852 → 0.854, both within 1σ.
  - GSM8K stays within stderr, and NIAH is 1.00 from 4k to 128k context.
- With the env var unset, behavior is unchanged.

## Details

- **Routing:** each rank holds 48 routed + 1 shared expert, so the kernel runs with `experts=392, topk=7`. A small Triton kernel remaps routed id `e → e + e // 48` and appends `ep_rank * 49 + 48` with weight 1.0. The routed weights already include `routed_scaling_factor`. The shared route always stays on the token's own rank, so it adds no all-to-all traffic.
- **Weights:** the shared MLP loads as usual. When MegaMoE weights are finalized, its block-FP8 weights are requantized to MXFP4 (`scaled_dequantize` + `mxfp4_quantize`, i.e. aiter `dynamic_mxfp4_quant`) into the shared slot, and the MLP is dropped. MTP and DSpark layers go through the same finalize path.
- **Tradeoffs:**
  - The shared expert runs at MXFP4 instead of FP8 (about 12% relative weight error), the same format the routed experts use.
  - `topk=7` needs a larger MoRI heap, so its default rises from 8G to 16G when the flag is on.
- **Known issue, not introduced by this PR (ROCm hipBLASLt):** with the default `max_num_batched_tokens=16384`, startup can hang in the profile run on MI355X, with or without this flag, on the unmodified image too.
  - **Root cause:** hipBLASLt 1.2.2 (ROCm 7.2.3) keeps Stream-K fixup flags in one per-handle `Synchronizer` that every stream shares. DSv4's CSA layers run the two compressor `torch.mm` calls (N=2048 and N=512, fp32 out) concurrently on two aux streams with the same torch handle. At ≥12288 tokens per rank, the N=512 GEMM picks a Stream-K remainder kernel (`…SK3_SKFTR0_SKXCCM8`). One kernel can then clear a flag the other is waiting on, and that workgroup spins in `label_SK_Fixup` forever (seen with rocgdb). The other ranks then wait in the MegaMoE collective. It is not a MegaMoE bug.
  - **Fix:** ROCm/rocm-libraries#10951 (per-stream Stream-K flags) and #11691 (gfx950 cross-XCD flag coherence). Neither is in ROCm 7.2.3 or 7.2.4.
  - **Workaround until a ROCm release includes them:** `--max-num-batched-tokens 8192` (the AgentX recipe). At that size the N=512 GEMM never takes the remainder path, and every run started reliably.

**Tests:** `pytest tests/models/test_deepseek_v4_aiter_mega_moe.py` passes on MI355X (6 passed). The new `test_shared_expert_route_appended` covers the id remap, `-1` padding routes, and the appended shared route. The end-to-end EP8 path needs 8× gfx950 and the DSv4 checkpoint, so it is validated outside CI (results above).

**Not a duplicate:** the existing MegaMoE shared-fusion PRs are NVIDIA DeepGEMM (#53040, #56568, #59927) or Kimi K3 (#53556). #53847 targets the non-mega AITER fused-MoE path.
