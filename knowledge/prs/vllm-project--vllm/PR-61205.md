# [Bugfix] Bound consecutive whitespace in tool-call structural tags

[Upstream PR](https://github.com/vllm-project/vllm/pull/61205) · state: open · merged: False

## Original PR description

## Overview

Cap consecutive whitespace inside tool-call structural tags at 64 characters, so a request with a forced or required tool can no longer spin on whitespace tokens until `max_tokens`. FIX #55541.

## Claims

- Every structural tag built by `vllm/tool_parsers/structural_tag_registry.py` (xgrammar builtins such as `glm_4_7`, and the vLLM-side builders for hermes, longcat, minimax, plamo3, kimi_k3 and the GLM-4.7 shallow tag) now passes `max_whitespace_cnt=64`; before, none of them bounded whitespace.
- With GLM-5.3-Flash and the schema from #55541, the grammar at a nested-object boundary (`<arg_key>salary</arg_key><arg_value>`) previously admitted an unbounded run of newline tokens (425 of the 451 allowed tokens were whitespace-only); it now stops after 64 characters and forces `{`. Same inside the object: after `{` and after a member, newline runs go from unbounded to 64.
- Pretty-printed arguments are unaffected: 64 characters is well above the indentation any model emits.

## Validation

- `tests/tool_parsers/test_structural_tag_registry.py`: two new tests (`test_glm47_tool_call_whitespace_is_bounded[False|True]`, `test_hermes_tool_call_whitespace_is_bounded`) fail on `main` and pass with the change; the two tests that compare vLLM's GLM tag with the xgrammar builtin pass the same bound to the reference. Whole file: 271 passed (CPU, Python 3.12, xgrammar 0.2.8, `VLLM_USE_PRECOMPILED=1` build of ee8f7ea44).
- Token-level check with the real `zai-org/GLM-5.3-Flash` tokenizer, feeding the prefix from the issue's first failure and then newline tokens (script: https://gist.github.com/jinwukong/e020a7b6d047c239ce4bcefef1317e04, extended to build the tag through `get_model_structural_tag`):

| path | before | after |
|---|---|---|
| non-strict tool, named choice (vLLM shallow tag, `main` since #56403) | boundary forces `{`; inside the object: unbounded | 64 |
| strict tool, named choice (xgrammar builtin, what v0.30/v0.31.0 used for every tool) | unbounded at the boundary and inside the object | 64 |

- `pre-commit run --files` on both files: clean.
- Not validated end to end on a GPU: I do not have one that can serve GLM-5.3-Flash. The reporter's failure signature (`finish_reason="length"`, `arguments` cut exactly at an object boundary after 6k+ tokens, only with forced tool choice) is the whitespace loop described below; a live run on the reporter's 4×H200 setup would confirm the symptom is gone.

## Details

At each value boundary inside a tool call the grammar allows whitespace with no upper bound. When the model's own next token is masked out (with a forced tool it is often one it did not plan to call), the surviving probability mass lands on whitespace, and nothing ever forces it back to progress, so it emits whitespace until `max_tokens`; the parser then strips the whitespace, which is why `arguments` is truncated precisely at the boundary. This is the same self-loop xgrammar fixed for Qwen's XML format by adding `max_whitespace_cnt` (mlc-ai/xgrammar#802); vLLM never passed it. The Rust `output_grammar` options already carry the same field (`max_whitespace_cnt: Option<i32>`), so the Python path now matches that contract.

Trade-off: a fixed module constant (`TOOL_CALL_MAX_WHITESPACE_CNT = 64`) rather than a new `StructuredOutputsConfig` field. The bound is far above any real indentation, and a knob would need plumbing through every tool parser for a value nobody should need to tune; happy to add one if preferred.
