# [Bugfix] Fall back to one pipeline stage when Triton decode attention exceeds shared memory

[Upstream PR](https://github.com/vllm-project/vllm/pull/61068) · state: open · merged: False

## Original PR description

Fixes #60172

## Purpose

On GPUs whose opt-in shared memory per block is 101376 bytes (consumer Ampere, Ada and Blackwell: sm_86, sm_89, sm_120), `TRITON_MLA` decode fails as soon as the first token is generated, or during CUDA graph warmup:

```
triton.runtime.errors.OutOfResources: out of resource: shared memory, Required: 102400, Hardware limit: 101376.
```

`_decode_grouped_att_m_fwd` launches the MLA tile (`BLOCK_DMODEL=512`, `BLOCK_DPE=64`, `BLOCK_N=32`, `BLOCK_H=16`) with `num_stages=2`. The existing guard only drops to one stage for `BLOCK_DMODEL >= 1024`, so it never fires for MLA (latent width 512). Since `TRITON_MLA` is the only MLA backend offered on sm_120, every DeepSeek-style model with `--kv-cache-dtype fp8` is unservable there.

## Why not extend the shape rule

The shared memory the compiled kernel needs depends on the KV-cache dtype as well as the tile. Measured from Triton's compile metadata on an RTX 5070 (sm_120, limit 101376):

| config | num_stages=2 | num_stages=1 |
|---|---|---|
| MLA Lk=576/Lv=512, fp8 cache | **102400 (fails)** | 83968 |
| MLA Lk=576/Lv=512, bf16 cache | 63488 | 59392 |
| MLA Lk=288/Lv=256, bf16 cache | 31744 | 29696 |
| non-MLA Lk=576, bf16 (existing guard) | 132096 (fails) | 98304 |

A rule on `BLOCK_DMODEL` alone cannot see the dtype. Instead, the launcher now catches `OutOfResources`, which Triton raises after compilation and before any launch, retries with `num_stages=1`, logs once, and caches the decision per configuration (tile constants, dtypes, device). Devices with 227 KB (Hopper, datacenter Blackwell) keep two stages and are unaffected; the first attempt succeeds and nothing else changes.

## Test Plan

- Standalone reproduction from #60172 on RTX 5070: fails before, passes after (`OK`, with one warning line).
- First launch inside `torch.cuda.graph` capture on a fresh process: capture succeeds, replay equals eager output.
- New test `test_decode_attention_mla_fp8_shared_memory` (MLA tile, fp8 cache, page size 16, compared against the bf16 reference with the tolerances used by the existing fp8 test). Fails with `OutOfResources` on the unpatched module, passes with the patch.
- Full `tests/kernels/attention/test_triton_decode_attention.py`: 116 passed on RTX 5070 (torch 2.13.0+cu130, triton 3.7.1, vLLM 0.31.0 wheel with this module replaced).
- `ruff check` and `ruff format --check` clean on both files.
