# [ROCm][MLA] Cut ~21x host dispatch from the MLA metadata build

[Upstream PR](https://github.com/vllm-project/vllm/pull/58381) · state: open · merged: False

## Original PR description

> [!IMPORTANT]
> **Scope: this is a host-dispatch microbenchmark, not an end-to-end throughput claim.**
> The numbers below are measured on the host build path, with per-call dispatch counts. Against a multi-millisecond decode step a
> change of this size sits inside run-to-run variation (~1% on a conc=1 arm), so
> **no measurable serving throughput improvement is claimed, and none should be
> inferred.** The value is removing host torch dispatches that serialize against the GPU on a path that is
> on the critical path at low concurrency. Details under "End-to-end (side note)".

## Summary

Two spots on the MLA attention metadata build spend more time in PyTorch
dispatch than in the work they do. Both operate on tensors that are already
host-side and hold one entry per request, and both run on **every** build,
between decode steps.

### 1. `AiterMLAMetadataBuilder._uniform_padded_mtp_qo_len`

Eight tensor dispatches — `sum()/item()`, a boolean-mask index, `numel()`,
`torch.all`, `eq`, `torch.nonzero`, `item()`, `torch.any` — to decide a single
integer. `qo_len` is derived from `query_start_loc_cpu`.

### 2. `MLACommonMetadataBuilder.build`, non-causal multi-token decode

A validation block using `torch.count_nonzero`, two `torch.all` calls and two
tensor-to-bool conversions (each lowering to `aten::is_nonzero`), purely to
raise a `ValueError` on a malformed query block.

Both now read the tensor out once and decide on Python ints.

## Results

Host cost, measured **without a GPU**. Both inputs are CPU tensors, so there is
no device work and no profiler involved in these numbers.

**`_uniform_padded_mtp_qo_len`**

| reqs | before | after | speedup | saved |
|---:|---:|---:|---:|---:|
| 1 | 1.88 µs | 0.32 µs | **5.9×** | 1.56 µs |
| 2 | 17.62 µs | 0.53 µs | **33.6×** | 17.10 µs |
| 8 | 17.65 µs | 0.71 µs | **24.8×** | 16.94 µs |

**non-causal query-block validation**

| reqs | before | after | speedup | saved |
|---:|---:|---:|---:|---:|
| 1 | 11.88 µs | 0.84 µs | **14.1×** | 11.04 µs |
| 2 | 12.44 µs | 0.89 µs | **13.9×** | 11.55 µs |
| 8 | 12.58 µs | 1.20 µs | **10.5×** | 11.38 µs |

Combined at 2 requests: **30.06 µs → 1.42 µs, ~21×, 14 tensor dispatches
removed per build.**

The step from one request to two in the first table is the padded-CUDA-graph
case: with dummy rows present the function stops early-returning and runs the
full `nonzero`/`any` path, which is the shape a graph-captured decode hits.

## Why this path matters

On a Kimi-K3 conc=1 384K-context decode trace, all 8 GPUs are idle across the
metadata-build window between decode steps, so host time there is on the
critical path rather than overlapped. These two sites account for the
`count_nonzero`, `is_nonzero` and `eq`/`nonzero` operations visible in that
window.

## Correctness

No FLOPs change and no device work changes; both sites return small integers
and booleans.

- `_uniform_padded_mtp_qo_len`: **34067 cases, 0 mismatches** — exhaustive over
  every `qo_len` combination up to 4 requests × length 4 crossed with every
  plausible `num_decode_tokens`, plus 20000 randomised larger cases. Covers
  empty, all-zero, zero-interior, non-divisible totals, `uniform_qo_len <= 1`
  and trailing-zero inputs.
- non-causal validation: **21364 cases, 0 mismatches** — exhaustive over every
  query-length combination up to 5 requests × length 3, plus 20000 randomised
  cases, comparing all three returned predicates.

The `ValueError` text is unchanged: it now formats a list rather than calling
`.tolist()` on a tensor.

## End-to-end (side note)

Deliberately last, and not the claim being made. End-to-end effect at this
operating point depends on how many metadata builds occur per step and on the
tuning of surrounding kernels, which is out of scope here. On our conc=1
Kimi-K3 configuration the expected effect is well under the run-to-run spread
we measure (~0.8%), so the function-level speedup above is the honest result.

Note in case anyone saw the earlier version of this PR: I briefly added two commits changing the MLA decode `kv_granularity` from 16 to 256, plus a section in the description. **Both have been reverted and the description restored.** This PR is back to being purely the bit-exact host-dispatch cleanup it started as.

Why I withdrew it: the change had already been evaluated and deliberately rejected in our own benchmark tree. It was defaulted to 512 on microbenchmark evidence, then reverted to 16 because end to end the two measured **within noise** at concurrency 1 — the +0.86% interactivity p90 never cleared the ~1% noise floor. The general point is worth restating, since it applies to a lot of kernel-level work on this path: MLA decode is only ~5-9% of the decode step, so even a 15-25% kernel-level improvement lands under 1% end to end.

My own sweep, which is what prompted the proposal, turned out to argue the same way once run at the right operating point: **+23.8% at ctx=65536 but only +1.58% at 384k**, the context the p90 request actually carries — roughly 0.22% of the decode step.

Sorry for the noise. Nothing in the current diff is affected.
