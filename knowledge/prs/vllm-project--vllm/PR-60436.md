# [Bugfix][Tool Parser] Keep newlines inside Olmo3 tool call arguments

[Upstream PR](https://github.com/vllm-project/vllm/pull/60436) · state: open · merged: False

## Original PR description



## Overview

Fixes #60421. The Olmo3 tool parser (`--tool-call-parser olmo3`) replaced newlines inside string arguments with `", "` and dropped calls formatted across several lines. This parses the call block as Python statements instead of joining its lines.

## Claims

- String arguments that contain newlines keep their value, for triple-quoted strings and for raw newlines inside `'...'` / `"..."` strings, in streaming and non-streaming mode.
- A call formatted across several lines is returned as a tool call instead of plain content.
- Behavior that worked on `main` is kept: newline-separated calls, indented calls (non-streaming), comma-separated calls on one line, and plain text returned as content. Assignments such as `x = f()` are not treated as tool calls.

## Validation

Reproducer from #60421, using the real parser on `main` and on this branch:

| Model output inside `<function_calls>` | `main` | This PR |
|---|---|---|
| `write_file(path="a.py", content="""def f():`↵`    return 1`↵`""")` | `{"content": "def f():, return 1, "}` | `{"content": "def f():\n    return 1\n"}` |
| `write_file(content='a`↵`b')` | `{"content": "a, b"}` | `{"content": "a\nb"}` |
| `get_weather(`↵`    city='SF',`↵`    metric='celsius'`↵`)` | no tool call, returned as content | `{"city": "SF", "metric": "celsius"}` |

The comma-separated case and `test_assignment_is_not_a_tool_call` pass on both and guard behavior that a module-based parse could otherwise change. `tests/tool_parsers` runs in CI on `cpu-small` (`.buildkite/test_areas/misc.yaml`).

## Details

**Root cause.** Olmo 3 writes one call per line inside `<function_calls>`. To make that parseable as a Python list, the parser split the block on every newline, stripped each line, and joined the lines with `", "`. Newlines inside string literals and inside a call's parentheses were split too.

**Fix.** A helper, `_parse_newline_separated_calls`, used by both the streaming and non-streaming paths:

1. Escapes raw newlines inside string literals with the existing `escape_ctrl_chars_in_strings` (the same helper and order the lfm2 parser uses since #48171). The values do not change, because `\n` evaluates back to a newline.
2. Strips leading whitespace from each line, so an indented call does not raise `IndentationError`. This keeps `main`'s tolerance and cannot touch string values, because no string spans a line after step 1.
3. Parses the block with `ast.parse` as a module and takes each top-level expression statement as a call. Python ignores newlines inside parentheses, so calls across lines work without extra code. A one-line `f(), g()` parses as a tuple and is flattened.

`TOOL_CALL_REGEX` now allows whitespace after `(`, so the non-streaming regex check accepts a call whose arguments start on the next line. In streaming, escaping runs before `make_valid_python`.

**Alternatives considered.** A hand-written string- and bracket-aware splitter (about 30 lines; reviewing it found a regression for raw newlines in plain strings), and `tokenize` (raises on ordinary text such as `I can't`, and on mixed indentation, so it needs a fallback path).

**Limitations.** A triple-quoted string with an odd number of inner quote characters (`"""it"s`↵`    x"""`) loses its inner indentation (`main` turned it into `it"s, x`). Unicode line separators used *between* calls (` `, `\x85`) no longer split calls; `\n`, `\r\n` and `\r` do. These behave the same on `main` and are left for follow-ups: an indented second call is dropped in streaming, `)(][` inside a string fails the regex check, `'''it's`↵`x'''` fails in streaming, and a triple-quoted argument in a later call is corrupted when streamed one character at a time.
