# [Perf][Kernel] Flat-grid silu_and_mul_quant: fix dead vector loop, fp32 fast-math chain

[Upstream PR](https://github.com/vllm-project/vllm/pull/59514) · state: open · merged: False

## Original PR description

## Purpose

`silu_and_mul_quant` (`act_and_mul_quant_kernel`, `csrc/libtorch_stable/quantization/activation_kernels.cu`) is the fused SiLU-and-mul + static per-tensor FP8 quant that the manual activation+quant fusion (#51415, `maybe_fused_act_quant`) routes every wired static-FP8 model through by default (Llama, Nemotron-H on main). Before the wiring, those models ran the Inductor-generated fused kernel for this boundary instead.

On an H100 this kernel is 2.3x slower per launch than that Inductor kernel, and the wiring costs Llama-3.1-8B-FP8 about 3% of serving throughput (numbers below). Two causes:

- The vectorized loop never ran. Line 69 called `round_to_previous_multiple_of(elems_per_128bit_load, block_end)` with the arguments swapped: it rounds 8 down to a multiple of `block_end`, which is 0 for any `d > 8`, so `vec_loop_end` was 0 and every element went through the scalar cleanup loop with 2-byte loads and 1-byte stores. Present since the kernel landed (#10867). Runtime proof on `main`: with the input pointer misaligned by 8 bytes the op completes and matches the aligned result for d = 14336 and 10752 (no 16-byte load executed), and faults with `misaligned address` at d = 8, the one shape where the loop bound is non-zero.
- One block per token. At decode sizes that is 32 blocks on 132 SMs; at prefill each of 512 threads walked 28 dependent scalar iterations. 1.9 TB/s effective at 16384 x 14336 against 3.1 TB/s for the Inductor kernel.

This PR replaces the kernel:

- One flat grid over 16-element chunks of the output. Each thread issues two 16-byte gate loads and two 16-byte up loads, computes 16 activations, converts pairs with the packed fp8 cvt (the hardware convert instruction, `cvt.rn.satfinite.e4m3x2.f32`) and writes one 16-byte store. 256-thread blocks, grid capped at SMs x 8 with a stride loop, `__launch_bounds__(256, 4)` (at full 8-block occupancy the bf16 kernel measured 20% slower at 16384 tokens; 4 resident blocks per SM was the best of 4/6/8/16).
- Rows that are not 16-byte vectorizable (d not a multiple of 16, or an unaligned data pointer) use the same kernel with one element per thread. A new test asserts `torch.equal` between the two paths.
- The arithmetic is the fp32 chain the NVFP4 sibling (`silu_and_mul_nvfp4_quant`) and the Inductor kernel use: `__fdividef(x, 1 + __expf(-x)) * up * inv_scale`, clamp, one round-to-nearest at the fp8 cast. The old kernel used accurate `expf`, an IEEE divide, and rounded SiLU and the product to bf16/fp16 before scaling. Against an fp64 reference on 29M elements per case (Llama-like scale, bf16 and fp16, two input ranges): old kernel 2.1-2.5% of bf16 outputs one fp8 code off; this kernel 0 for bf16 and 8-12 elements for fp16; bit-identical to the Inductor kernel on bf16, 3-4 elements per 29M on fp16. So the output moves from the old kernel's numerics to the numerics main already serves through Inductor. GSM8K below.
- `scaled_fp8_conversion` is split into `scaled_fp8_saturate` + `fp8_from_saturated` so the packed and scalar paths share one clamp; no behavior change for its other callers. The now-unused `round_to_previous_multiple_of` and the float instantiation of the kernel (the op only accepts 16-bit inputs) are removed.
- Tests: the reference in `test_fused_quant_activation.py` is the fp32 chain, checked with the shared `fp8_ulp_distance` criterion the layernorm quant tests use (at most one E4M3 code apart, bounded outlier count); `test_silu_mul_quant_fusion.py` gets the same 5e-2 tolerance for the static-FP8 model that it already uses for the block-quant model, for the same reason (fp32 fused chain vs bf16 storage in the eager reference).

**Not a duplicate.** No open PR touches this kernel. #49828 adds a separate per-token dynamic kernel in the same file with its own launch. #53131 no longer lists this file. #50670 is an opt-in Triton SiLU+FP8 for LFM2.5 only.

## Test Plan

- Runtime proof of the dead vector loop on `main` (misaligned-pointer test above) plus SASS of both builds.
- Numerics vs an fp64 reference and vs the Inductor kernel: 2048 x 14336, bf16 and fp16, sigma 1 and 3, scale 0.0135.
- Vector path vs scalar fallback: `torch.equal` on a one-element storage offset (misaligned data pointer), shapes up to 3045 x 8192 (exercises the stride loop).
- `pytest tests/kernels/test_fused_quant_activation.py tests/compile/passes/test_silu_mul_quant_manual_fusion.py tests/compile/passes/test_silu_mul_quant_fusion.py tests/compile/passes/test_functionalization.py`
- Microbenchmark: H100 80GB, driver 580, CUDA 13.0, torch 2.13.0+cu130, `do_bench_cudagraph` median; `benchmarks/kernels/benchmark_silu_and_mul_quant.py` (added) run on both builds, plus a wider sweep script in the logs (bf16 and fp16, tokens 1..16384, d in {8192, 10752, 14336, 28672}). Inductor column = `torch.compile` of `SiluAndMul.forward_native` + `QuantFP8(static).forward_native`, one static-shape compile per config.
- E2e on RedHatAI/Meta-Llama-3.1-8B-Instruct-FP8 with main's own wiring. Three arms, interleaved: `main` kernel, this PR, and the same tree with the `llama.py` wiring line reverted (Inductor path, what main ran before #51415):

## Test Result

- Proof on `main`: d = 14336 and 10752 complete on 8-byte-misaligned pointers and match the aligned output; d = 8 faults with `CUDA error: misaligned address`.
- Vector vs scalar path: identical on all shapes. Tests: **245 passed, 76 skipped** (4 files).
- Numerics vs fp64 (29.4M elements per case): bf16 **0 differ** (old kernel: 2.46% / 2.06%), fp16 12 / 8 elements, all one code. Vs Inductor: bf16 0, fp16 3 / 4.
