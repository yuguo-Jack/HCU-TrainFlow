# [Metrics] Export KV cache capacity in bytes

[Upstream PR](https://github.com/vllm-project/vllm/pull/54183) · state: open · merged: False

## Original PR description

## Review summary

- Adds startup-time `vllm:kv_cache_capacity_bytes`, with capacity preserved per global DP rank.
- Rebased onto main `36f3972812`; 30 CPU checks and changed-file pre-commit passed.
- Existing HiSparse two-pool accounting remains unsupported; see Details.

## Overview

Expose a numeric KV-cache byte-capacity Gauge for byte-based dashboards and
capacity alerts, using post-profiling `KVCacheConfig` backing sizes summed across
workers in each DP engine.

This complements #42206's group-aware token capacity and maximum concurrency
in `vllm:cache_config_info`, rather than duplicating that work. The original
duplicate-work searches found no equivalent open byte-capacity PR.

## Claims

- Counts one backing allocation per worker for dense/contiguous cache layouts,
  without double-counting aliased cache-group descriptors.
- Initializes each `engine` Gauge from its matching global-DP-rank ready response,
  independent of response arrival order.
- Computes capacity at startup with no steady-state GPU work; the Gauge uses
  the existing model/engine labels.

## Details

Ready responses carry the capacity from each EngineCore; the frontend stores
it by global DP rank and initializes the matching `engine` Gauge once.
`docs/design/metrics.md` documents the new metric. This rebase preserves both
the upstream prefix-cache alignment fields and the capacity field/hash exclusion;
it does not change the published metric behavior.

Known limitations, unchanged by this rebase:

- HiSparse has separate host/device pools. The current single-backing assertion
  can fail when their sizes differ, and accounting is incomplete even if equal.
  HiSparse compatibility needs a separate fix before claiming support.
- ROCm allocator tail padding to 4096 bytes is excluded from the descriptor-based
  value; this can undercount storage by less than 4096 bytes per worker. No ROCm
  runtime validation is claimed.

File: `vllm/v1/metrics/loggers.py` · line None

**[P2] Preserve capacity per DP engine.** Each EngineCore computes and reports its own capacity, and the ready response already carries `data_parallel_rank`. However, `_apply_ready_response()` keeps only the first non-`None` capacity in the shared `CacheConfig`, so this loop writes the first response's value to every `engine` label. DP cores profile memory independently, so their allocations can legitimately differ. Please retain capacity keyed by rank and initialize each gauge from its matching value. A two-ready-response test with ranks 0/1 and capacities 111/222 (including reversed arrival order) would catch this.
