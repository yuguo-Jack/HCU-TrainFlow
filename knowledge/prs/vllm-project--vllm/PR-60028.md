# [Startup][UX] Start multiproc workers concurrently when using spawn

[Upstream PR](https://github.com/vllm-project/vllm/pull/60028) · state: open · merged: False

## Original PR description

## Purpose

Related: #59433.

With spawn, `Process.start()` blocks while the child imports vLLM and torch, so
`MultiprocExecutor` started local workers one after another (~6s each, ~50s for
TP8). This starts them from a thread pool so the imports overlap.

`vllm serve` defaults to spawn (`cli_env_setup`), so this applies to the default
serving path with TP>1.

The serial loop is kept when concurrency is unsafe:

| Case | Reason |
|---|---|
| fork | inherited fds are passed between workers |
| CPU backend | per-worker OpenMP env |
| `numa_bind` | per-worker numactl executable patch |
| 1 local worker | nothing to overlap |

If one worker fails to start, the ones that did start are still recorded in rank
order, so existing cleanup terminates them.

## Overlap with #39414

#39414 (stale, conflicted) also parallelizes worker spawning, together with
EngineCore startup. This PR covers only the worker part, adds partial-failure
cleanup and a NUMA exclusion, and includes tests and measurements.
