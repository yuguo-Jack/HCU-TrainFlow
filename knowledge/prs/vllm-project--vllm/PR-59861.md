# [Bugfix][Rust Frontend] Pass through raw characters in byte-level decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/59861) · state: closed · merged: True

## Original PR description



## Overview

The Rust frontend's byte-level decode fast path turns raw whitespace in added tokens into NUL bytes. Pass those characters through, as HuggingFace `tokenizers` does.

## Claims

- Non-special added tokens whose content has a raw space, newline, or other character the GPT-2 byte table never emits now decode verbatim instead of as `\0`.
- Fixes code indentation for GPT-NeoX-tokenizer models (Pythia, OLMoE, Mamba), whose whitespace-run added tokens decode to runs of `\0` on `main`.
- Fixes tool-call parsing when the parser's markup is such a token: a checkpoint with `<parameter name="` / `\n</parameter>`-style added tokens returned every tool call with `"arguments": "{}"` from the Rust frontend, while Python parsed them correctly from the same token IDs.

## Validation

```bash
cd rust
cargo nextest run -p vllm-tokenizer
cargo clippy -p vllm-tokenizer --all-targets -- -D warnings
```

- `vllm-tokenizer`: 96 passed. The new `added_tokens_with_raw_whitespace_decode_verbatim` fails on `main` with `left: "<parameter\0name=\"city\">\nParis\0</parameter>…"` and passes here; it checks the fastokens fast path and the HF backend against the same text, including an added token `\ncafé` that a per-character pass-through decodes as `\ncaf�`.
- Real tokenizer, out of tree: a scratch crate with a path dependency on `vllm-tokenizer` decodes `def f(x):\n        if x:\n                return x\n` with `allenai/OLMoE-1B-7B-0125-Instruct`'s `tokenizer.json` (IDs 50270 and 50262 are 8- and 16-space added tokens):
  - `main`: `"def f(x):\n\0\0\0\0\0\0\0\0if x:\n\0\0\0…\0return x\n"`
  - this PR: identical to the HF backend and the original text.
- End to end, on the checkpoint with tool-call markup tokens (GB200, TP4): prompt and generated token IDs were identical between the Python and Rust frontends, and the Rust raw completion text showed the `\0` in place of the space and newline. That run predates this patch; the unit test reproduces the same decoded string.

## Details

`CHAR_TO_BYTE` is a flat reverse table over U+0000..U+0143, filled only at the 256 codepoints the GPT-2 byte-to-unicode map emits. Every other slot was `0`, so a codepoint like U+0020 or U+000A mapped to byte 0 instead of falling through to the pass-through branch that already handles non-GPT-2 codepoints such as DeepSeek's `｜` and `▁`. Byte-level vocab entries never contain those codepoints, but added tokens store raw text, and `id_to_token` returns that text unchanged. HuggingFace's `ByteLevel` decoder passes a token through verbatim when any of its characters is unmapped, so the Python frontend was unaffected.

The table now stores `Option<u8>`, and a token with any `None` or out-of-table codepoint passes through whole, as in HF. Characters the table does emit in the same token, such as `Ġ` or `é`, therefore stay verbatim; previously, out-of-table codepoints such as DeepSeek's passed through one character at a time. The common path still does one table lookup per character.

The fast path was written to match `fastokens::decoders::ByteLevelDecoder`, and fastokens 0.2.1 has the same table; that will be fixed there separately. vLLM only reaches fastokens' decoder for decoders that are not a single `ByteLevel` stage, so the common byte-level tokenizers are covered by this change.
