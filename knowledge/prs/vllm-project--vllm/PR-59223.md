# [Bugfix] Preserve FP8 indexer WK pairs across load_weights calls

[Upstream PR](https://github.com/vllm-project/vllm/pull/59223) · state: open · merged: False

## Original PR description

## Purpose

**In short**: Bugfix for GLM-5.3 sometimes starting with degraded performance (thinking loops) due to dropped weights when using runai_streamer loader due to a "race" (non-deterministic I/O completion order).

**Details**:
GLM-5.3 / DeepSeek-V3.2 (`deepseek_v32`) checkpoints store the indexer `wk` projection in FP8 as two tensors: values and a scale factor. The loader parks the first half in a dict and dequantizes once the second half arrives, but that dict was created fresh on every `load_weights()` call, so the two halves had to arrive within the same call.
 
With runai_streamer as loader, tensors arrive in IO-completion order (this is partly the cause for the non-deterministic "race"), and `AutoWeightsLoader` splits the weight stream into multiple `load_weights()` calls at every `model` <-> `lm_head` prefix transition. When the split between calls happens to fall between the two halves of a pair, both are silently dropped: the WK half of the fused `wk_weights_proj` parameter keeps its initialization, one layer's sparse-attention indexer runs on garbage, and every load-completeness check still passes. In production this shows up as a per-launch coin flip where short answers look fine but long reasoning degenerates into thinking loops, rendering the performance almost useless.

Fix: keep the pending dict on the model instance instead of a local variable (similar fix as #46168 for the generic `deepseek_v2` path, applied to the remaining copies: `deepseek_v32` nvidia/amd model+mtp, and `deepseek_mtp`).

Note that this is NOT a duplicate of #56584, which fixes the `glm5next` (GLM-5.3-Flash) copy of the same bug. The two PRs touch disjoint files and both are needed.

## Test Plan

```bash
     .venv/bin/python -m pytest tests/model_executor/model_loader/test_deepseek_v32_weight_loading.py -v
```

That test is CPU-only, no GPU and no checkpoint needed.

## Test Result

* Unpatched main: 13 failed (the WK half of the fused parameter stays all-zero, which is the bug addressed in this PR)
* With this PR: 13 passed.

Also verified end-to-end on a real GLM-5.3 deployment (TP=8, B200, --load-format runai_streamer). In addition to checking by hand with complex prompts that force the model to do multi-thinking steps and therefore validating that the thinking loops were gone, the following checks were done (with help of AI):
* Dumped the live in-VRAM wk_weights_proj tensors from all 8 TP workers and compared them bitwise against values dequantized from the on-disk checkpoint: 168/168 identical.
* 10 greedy prompts (math / code / instructions): content and reasoning byte-identical to a known-good instance of the same weights, so a healthy load is provably unchanged and accuracy benchmarks are unaffected.

No documentation update is needed.
