# [Rust Frontend] return_top_k_logprobs and return_token_logprobs on raw generate

[Upstream PR](https://github.com/vllm-project/vllm/pull/60916) · state: open · merged: False

## Original PR description



## Overview

Rust frontend support for `return_top_k_logprobs` and `return_token_logprobs` on `/inference/v1/generate`, matching the Python frontend. Top-k output logprobs come back as one packed base64 block instead of per-token JSON objects. Part of RFC #57479.

> **Draft, stacked.** This branch sits on #60541 (streamed default render) and on a cherry-pick of #57442 (Python `return_token_logprobs`). The new commits are "server: return_top_k_logprobs for raw generate" and "server: support return_token_logprobs on raw generate". The Python counterpart is #60915.

## Claims

- **`return_top_k_logprobs`.** With `sampling_params.logprobs = k >= 1`, `choices[0].logprobs` is
  `{"content": null, ["sampled": [...],] "top_k": {"num_positions": N, "k": k, "token_ids": <b64 LE int32[N*k]>, "logprobs": <b64 LE f32[N*k]>}}`,
  with engine slots 1..=k in engine order and the raw engine logprob bits (no clamp). This is the same wire format as the Python PR.
- **`return_token_logprobs` (#57442), previously rejected by the Rust frontend.**
  - With `logprobs = 0` the engine sends only `new_sampled_logprobs`, and the response is `{"content": null, "sampled": [...]}`.
  - With `logprobs > 0`, `content` is rendered as before, followed by `sampled`.
  - `sampled` is clamped like `content`.
- **Errors.** Both flags return 400 with `stream=true`. `return_top_k_logprobs` also returns 400 for `logprobs` absent, 0 or −1. Malformed engine output fails only its own request with a 500: a missing position, rows narrower than k+1, or ids beyond int32.
- **Default unchanged.** Responses without the flags are unchanged.

New tests cover:
- the exact top-k body bytes;
- top-k decoded against the default render of the same rows;
- a round trip that keeps engine rows and raw f32 bits;
- base64 segments that are bounded and concatenate to a one-shot encoding;
- padded rows truncated to k, and narrower rows rejected;
- malformed outputs failing only their request;
- the 400 cases;
- the `sampled` bodies (engine `sampled_logprobs`, falling back to rows, count checks);
- an engine-client round trip of `new_sampled_logprobs`.

**Performance (prototype, not yet rerun on this rebase).** On the earlier compact-format prototype, an RL abort with 245,760 output tokens at top-128 produced about 2.2 GB per response in per-token form and 337 MB as the packed block. The Rust frontend's speedup was similar to Python's (about 21 s down to about 1.8 s on DP8 with 32 requests). I'll rerun this end to end on this branch before marking it ready.

## Details

- **Encoding and body.** Each engine step's logprobs are base64-encoded as they arrive, into segments of at most 1 MiB. They're taken off the output before the unchanged `collect_output`. The body sends those segments without copying, with an exact `Content-Length`. The rest of the response comes from serde through the placeholder split in #60541.
- **Engine flag.** `return_token_logprobs` with `logprobs = 0` sets the engine's private `_sampled_logprobs_only`, which is omitted on the wire when false. `vllm_text::SamplingParams` carries it serde-skipped, so clients can't set it.
- **Limitation.** The Rust frontend can't see `--logprobs-mode`, so Python's `raw_logprobs` / `processed_logprobs` check isn't applied.
- **Known gap.** The #57442 cherry-pick predates its latest commit (1b3dc5b2fc, "reject logprob_token_ids, read any logprobs layout"). It will be dropped when #57442 merges.

**Not a duplicate.** No open PR adds these flags to the Rust frontend (#60789 replays logprobs through the AuxOutput connector, not the HTTP response) (`gh pr list --state open --search "57479 in:body"`, `"rust return_token_logprobs"`).
