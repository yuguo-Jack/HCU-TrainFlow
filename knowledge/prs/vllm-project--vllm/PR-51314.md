# [ROCm][Perf] Skip cleaning sparse prefill MQA logits

[Upstream PR](https://github.com/vllm-project/vllm/pull/51314) · state: open · merged: False

## Original PR description

## Summary

The sparse prefill path creates the MQA-logits buffer with `torch.full(..., -inf)`.
This launches an FP32 fill before every logits kernel.

This PR passes `clean_logits=False` to AITER, so the buffer uses `torch.empty`
and the fill is removed.

## Safety

The only consumer is `top_k_per_row_prefill`. It reads each row only inside
`[cu_seqlen_ks, cu_seqlen_ke)`. Its vectorized path also guards the final partial
load, so padding values are never read. The top-k result is unchanged.

## Results

MI355X, TP=4, rank 0, comparable before/after captures:

| metric | before | after |
|---|---:|---:|
| FP32 fill launches | 18,162 | **0** |
| FP32 fill GPU time | 1,250.2 ms | **0 ms** |
| MQA-logits launches | 18,108 | 17,930 |

The removed fill was **0.89% of total GPU kernel time**. In the sample below it
takes 74.6 µs and is fully serialized before the logits kernel.

![Before: FP32 fill before MQA logits](https://raw.githubusercontent.com/amd-sriram/vllm/ce9490285bbd8099e2d37c5aec8b3d24b7a20785/figures/fig_pr4_before.png)

![After: fill removed](https://raw.githubusercontent.com/amd-sriram/vllm/ce9490285bbd8099e2d37c5aec8b3d24b7a20785/figures/fig_pr4_after.png)

- stefanskiasan · comment · 2026-09-07T18:30:07Z · [source](https://github.com/vllm-project/vllm/pull/51314#issuecomment-5574442855)

Independent confirmation on different hardware and a different model, in case
it helps this land: **GLM-5.3 (full, `glm_moe_dsa`), Quark MXFP4 + FP8
attention, MI355X / gfx950, TP4, `max_model_len=1M`, MTP k=4.**

I arrived at the same change independently (as a runtime switch over
`rocm_aiter_mla_sparse.py`) before finding this PR, so the numbers below are
from a separate implementation of the same idea.

## Accuracy — the part I wanted to be sure about

My concern was sequences *shorter* than the indexer's top-k width (2048 here):
if the consumer ever ranked over the unwritten region, it would pick stale
values out of a reused workspace arena rather than garbage, which is the kind
of bug that stays silent. Your reasoning that `top_k_per_row_prefill` only
reads within bounded row ranges is what makes this safe, and it holds
empirically — GSM8K prompts sit well under 2048 tokens, so that benchmark
exercises exactly this case:

| | GSM8K (full 1319) |
|---|---|
| `clean_logits=True` (stock) | 1280 / 1319 = 97.0 % |
| `clean_logits=False` | 1279 / 1319 = 97.0 % |

One question apart, against a standard error of 0.39 % on the full set. No
degradation. (Worth using the full 1319 for this — at 150 questions a
one-question difference is not resolvable, which nearly cost me a working fix
in an unrelated case.)

## Throughput — consistent with your "minimal throughput changes"

Prefill-heavy load, 16k context, 32 concurrent, 128 requests, **caches
disabled** (`--no-enable-prefix-caching`, no LMCache — with the prefix cache on,
this comparison is meaningless):

| | throughput | TTFT |
|---|---|---|
| stock (n=3) | 147.58 tok/s | 19 596 ms |
| `clean_logits=False` (n=6) | 147.06 tok/s | 19 521 ms |

Run-to-run spread is 3.55 tok/s (2.4 %), so a ~0.9 % kernel-time effect is
simply below the resolution of an end-to-end measurement here — which matches
what you report rather than contradicting it. I mention it only so nobody
reads a flat end-to-end number as evidence against the change: the fill
launches do disappear, and removing work that the CUDA path already skips
(`sparse_attn_indexer.py:506,611` and `sparse_attn_indexer_kpool.py:600,911`
all pass `clean_logits=False`) is right on its own terms.

We're holding off on carrying this as a local patch and will pick it up when
this merges. Happy to re-run either measurement on this hardware if that's
useful for review.
