# [Bugfix][XPU] Remove stale W4A8 weight after repacking

[Upstream PR](https://github.com/vllm-project/vllm/pull/57511) · state: closed · merged: True

## Original PR description

## Purpose

Fixes #57503.

`XPUW4A8IntLinearKernel.process_weights_after_loading()` repacks the checkpoint-format W4A8 weight into the runtime `weight_packed` parameter.

Previously, after repacking, it released the original unpacked weight with:

```python
layer.register_parameter("weight", None)
```

This leaves the `weight` attribute present with a value of `None`.

LoRA device detection checks `weight` before `weight_packed`, so the stale attribute causes LoRA wrapper creation to fail on:

```text
AttributeError: 'NoneType' object has no attribute 'device'
```

This change removes the obsolete `weight` attribute after repacking:

```python
delattr(layer, "weight")
```

The XPU W4A8 runtime path uses `weight_packed`, `weight_scale`, and `weight_zero_point`, so the unpacked `weight` is no longer needed after conversion.

This also allows the existing LoRA `weight_packed` fallback to work without changing generic LoRA device-detection behavior.

Removing the original weight after packing follows an existing compressed-tensors pattern, for example `compressed_tensors_wNa8o8.py`.

This PR supersedes #57480, which addressed the same failure by changing generic LoRA device probing. This PR instead fixes the stale state in the XPU W4A8 repacking path where it is introduced.

AI assistance was used for investigation, implementation, and validation. The resulting changes were reviewed by the submitter.

The adapter loaded successfully, appeared as a child of the base model in `/v1/models`, and requests explicitly targeting the adapter returned HTTP 200 with output different from the deterministic base-model request, confirming that the LoRA path was exercised.

| Configuration | Accuracy | Invalid rate |

| W4A8 + LoRA | 77.5% (155/200) | 0.0% |

I did not report the GSM8K wall-clock numbers as a performance comparison because the base and LoRA runs generated different numbers of output tokens. A meaningful performance comparison would require a fixed-length workload and repeated measurements.
