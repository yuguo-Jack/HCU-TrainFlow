# [Bugfix][Distributed] Own SHM out-of-band buffers before releasing read slots

[Upstream PR](https://github.com/vllm-project/vllm/pull/61000) · state: closed · merged: True

## Original PR description

## Overview

Fix retained NumPy arrays changing after `MessageQueue.dequeue()` releases their shared-memory ring slot. Copy out-of-band buffers before releasing the slot, following the ownership rule used for Torch tensors in #48442.

## Claims

- Received out-of-band arrays retain their values after ring reuse, including writable and read-only NumPy arrays.
- Torch reconstruction reuses the owned `bytearray`, avoiding a second copy. The wire format, inline pickle payload, and ZMQ receive paths remain unchanged.

## Validation

Added a deterministic regression in `tests/distributed/test_shm_broadcast.py`: two SHM cases using `uint16`, covering writable and read-only arrays. It retains a received array while reusing a one-slot queue, then checks that its values and writability remain correct. The broader dtype/transport matrix was used as a development control, not retained in CI.

A separate real-queue reproducer sent a valid `[2048, 48, 10]` uint16 routing array in `(WorkerProc.ResponseStatus.SUCCESS, ModelRunnerOutput)`, retained it, cycled the ten-slot ring, and sent a smaller valid routing message. Sender data remained unchanged in every case:

| Receive path | Invalid retained IDs (>511) |
|---|---:|
| Baseline | 1,430 |
| Baseline + sender-copy control matching #53217 | 1,430 |
| This fix | 0 |

CPU copy-cost microbenchmark: one writer/local reader, one SHM slot, five trials of 100 measured messages after five warmups per trial. Values are median dequeue time; parentheses show the range of trial medians. This measures transport overhead, not serving throughput.

### Qwen3.8 Flash Next GPU validation

[Reproduction scripts and all measurements](https://gist.github.com/aoshen02/43ed12722a1a724519c2cb5897b40562).

One node with **4 GB200 GPUs**, Qwen/Qwen3.8-Flash-Next revision `09c48120cd32ed3a6f9bb1506035015135ced7a3`, BF16, TP4 + EP, AsyncLLM/Multiproc, async scheduling, R3 and prefix caching enabled. Pinned image source `2eb491e18`; its queue file is byte-identical to this PR's base. Only the two ownership expressions differ between arms.

The diagnostic retains actual received R3 arrays and hashes them **before releasing the SHM slot**, then rechecks after subsequent messages. This compares the same execution's data, not separate inference runs:

| Actual large R3 arrays retained | Baseline | Fixed |
|---|---:|---:|
| Arrays whose bytes changed after receipt | **17 / 26** | **0 / 26** |
| Repeated array checks | 5,060 | 5,066 |

The 26 arrays cover 8 warmup text requests, 16 measured text requests and 2 image requests. Both arms passed final shape, dtype and expert-ID bounds; the retention audit catches corruption that bounds checks alone miss.

Separate **uninstrumented** throughput runs: 2,048 input / 256 output tokens, concurrency 32, 64 requests per trial. After a full 64-request warmup, run five trials per arm in fixed-then-baseline order:

| Output tokens/s | Baseline | Fixed |
|---|---:|---:|
| Median | 2,066.7 | 2,076.5 |
| Trial range | 2,049.5–2,069.7 | 2,063.9–2,078.2 |

Median difference **+0.48%**: no throughput regression observed in this workload; not a claim of significant speedup. Each arm also passed two image-request smoke tests. An earlier baseline-first pair used insufficient warmup and showed first-trial drift; all preliminary and final samples are retained in the linked results.

These are synthetic text/image serving-engine tests, **not** the reporter's exact Prime-RL training workload or a language-model task-accuracy benchmark. They establish the SHM lifetime bug and its fix, not that it was the sole cause of a historical training failure.

## Details

`pickle.loads(..., buffers=...)` reconstructs large NumPy arrays from views into the ring slot. Exiting `acquire_read` marks that slot reusable, but downstream consumers can retain the arrays. Later writes then change the already received data. Copying the out-of-band buffers inside the read context gives those consumers independently owned storage. `bytearray` preserves writability; `_rebuild_tensor` can safely reuse it.

This adds one allocation and CPU copy per SHM out-of-band buffer. Remote and overflow ZMQ frames keep their existing ownership behavior; the separate tensor arena is unchanged.

**Duplicate check:** searched open PRs for `shm_broadcast`, NumPy/shared-memory copying, and out-of-band/dequeue lifetime. #53217 fixes sender buffers being mutated during asynchronous ZMQ sends; it does not detach received arrays from reusable SHM slots. The sender-copy control above still reproduces this failure. #48442 protects Torch tensors, but ordinary NumPy arrays bypass its reducer. Nearby #50548 and #50606 concern reader-index retries and queue sizing respectively.
