# [Bugfix][Core] Reclaim parked streaming sessions in reset_prefix_cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/60764) · state: open · merged: False

## Original PR description

## Overview

Fixes #60744. `reset_prefix_cache(reset_running_requests=True)` now drains `kv_holding_waiting` (parked streaming sessions and other block-holding waiters) instead of crashing on them, so `pause_generation(mode="keep", clear_cache=True)` works with idle streaming sessions attached.

## Claims

- `pause_generation(mode="keep", clear_cache=True)` no longer raises `RuntimeError` when a streaming session is parked in `WAITING_FOR_STREAMING_REQ`; its blocks are reclaimed and it recomputes on resume.
- Resuming a session whose blocks were reclaimed (by this reset or by preemption) no longer wipes its whole trajectory: the resume fold previously sliced at `num_computed_tokens == 0`.
- The RL pause router docstring no longer claims `clear_cache` is ignored for `mode="keep"`, which the code path never honored.

## Details

Root cause: the reset only preempted `self.running`, then required `kv_cache_manager.reset_prefix_cache()` to succeed. A parked streaming session holds blocks in `kv_holding_waiting` outside `running`, so the manager-side reset always failed and the `RuntimeError` path fired.

The fix reclaims `kv_holding_waiting` members that can be freed, reusing the preemption body factored out of `_preempt_request` as `_reclaim_request_kv`. Parked sessions keep `WAITING_FOR_STREAMING_REQ` status and token history and move to the plain waiting queue (they hold no blocks now); other holders are marked `PREEMPTED` with the same stale-output handling as a running preemption. `WAITING_FOR_REMOTE_KVS` holders keep the reset unsupported, unchanged.

One latent bug surfaced while testing: `_update_request_as_session` folds prior-turn output into the prompt by slicing at `num_computed_tokens`. Any reclaimed session (including a resumable request preempted by this reset while running) resumes with `num_computed_tokens == 0`, and the old slice deleted the entire trajectory, turning a keep-pause into a silent abort. The fold now keeps the full prior turn when no tokens are computed.

Related open PRs this does not duplicate: #59339 reclaims KV from idle sessions under allocation pressure (a different trigger; its new reclaim helper could later reuse `_reclaim_request_kv`), and #58778 keeps resumable sessions alive through stop-while-preempted (status handling; it touches the same fold region, so whichever lands second needs a small rebase).

One correctness issue in the fold guard.

```python
num_computed_tokens = session.num_computed_tokens
if num_computed_tokens == 0:

```

The frontier should be `session.num_tokens - 1`. The unreclaimed path discards the final
sampled output token, and `num_tokens` keeps it. So a reclaimed session folds its stop
token into the next turn's prompt, and resuming after a reset produces a different
trajectory than resuming without one.

This is an executed result, not a reading of the diff. I substituted the expression into a
local tree carrying the same reclaim logic and ran a test that compares the resumed session
against a second scheduler which never saw a reset:

```
assert session.prompt_token_ids == reference_session.prompt_token_ids
E  assert [0, 0, 0, 0, 7, 0, ...] == [0, 0, 0, 0, 0, 0, ...]
```

`7` is the stop token, now sitting in the prompt. With `num_tokens - 1` both sides match.

`test_resume_after_reset_preserves_parked_session_history` can't catch this, because its
expectation is `prior_tokens + list(chunk.prompt_token_ids)` and `prior_tokens` is captured
after the stop token has been appended. The assertion encodes the extra token as correct.
The shape that does catch it is a second `create_scheduler(enable_prefix_caching=True)`
parked identically but never reset, then asserting `prompt_token_ids` and `_all_token_ids`
are equal across the two schedulers after both resume. I can post that test here if it's
useful to you.

#58778 lands on the same frontier independently: `keep_end = session.num_tokens - 1` with
`assert keep_end >= num_computed_tokens`.

  `num_stale_output_tokens = request.num_in_flight_tokens` are set on a request that was

- he-yufeng · comment · 2026-10-10T03:03:35Z · [source](https://github.com/vllm-project/vllm/pull/60764#issuecomment-6093113024)

Fixed in c49370d9, thanks for catching this. The stop-token splice is exactly what was happening: the guard kept the full prior turn, so a reset+resume folded token 7 into the next prompt while a plain resume dropped it.

The regression test now has the shape you described: a second scheduler parks the same session, never resets, and after both resume the two must agree on `_all_token_ids` and `num_prompt_tokens`. It fails on the old frontier (8 tokens against 7, the stop token sitting in the prompt) and passes with `num_tokens - 1`. I also made the parked session generate a non-stop token before the stop, so the fold has something real to keep and the assertion can't pass on an empty slice. Full `test_scheduler.py`: 210 passed. Nice to see #58778 land on the same frontier independently; the assert there is a good belt for it.

On the two read-only points:

- The stale-output assignment mirrors `_handle_stopped_request`, which does the same `drop_stale_output = True` + `num_stale = num_in_flight` when a resumable request stops. A nonzero in-flight count on a kv-holding waiter is only reachable through the async pipeline-depth overlap, where the previous turn's output is still draining; in the common case it is 0 and the assignment is inert, because `output_is_stale` gates on `num_stale_output_tokens > 0`. Defensive in practice, but consistent if the overlap ever shows up.
- `add_request` was deliberate. The running drain prepends in reverse FIFO so preempted running requests come back first. Reclaimed kv-holding waiters were waiting, not running, and their drain-first privilege died with their blocks, so they append behind the waiters already queued, same as the plain path in `_enqueue_waiting_request`. For parked sessions queue position doesn't matter at all: they only re-enter scheduling when the next chunk arrives.
