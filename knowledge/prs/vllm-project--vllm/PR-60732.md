# [Bugfix][Attention] Re-plan DSA indexer decode schedule for DBO's reduced DeepGEMM SM count

[Upstream PR](https://github.com/vllm-project/vllm/pull/60732) · state: open · merged: False

## Original PR description



## Overview

With `--enable-dbo` and an all2all backend that reserves communication SMs (e.g. DeepEP high-throughput), DSA models (DeepSeek-V3.2, GLM-5.x) crash in the sparse-attention indexer as soon as a microbatched step contains a decode-branch request:

```
RuntimeError: Assertion error (csrc/apis/attention.hpp:346): _schedule_meta_size == num_sms + 1 and _meta_info_size == 2
```

The indexer builder plans DeepGEMM's paged-MQA-logits schedule for the whole GPU, but DBO lowers DeepGEMM's SM count (`set_num_sms(total - VLLM_DBO_COMM_SMS)`) while the microbatches run. This PR re-plans the schedule at the call site when the two counts differ. No existing issue or PR covers this (searched `schedule_meta_size`, `dbo indexer num_sms`, `paged_mqa_logits set_num_sms`: 0 results). Rechecked 2026-10-08 against open PRs: #56476 (DeepSeek-V4.1 per-microbatch index state) also edits `sparse_attn_indexer.py`, in different lines, and does not touch the schedule metadata.

## Claims

- Fixes the DSA indexer decode crash under DBO (Model Runner V1 and V2, CUDA + DeepGEMM).
- The re-planned schedule gives bit-identical indexer logits, so the fix does not change results: with it, GLM-5.3 accuracy under DBO matches DBO with SM partitioning disabled (`VLLM_DBO_COMM_SMS=0`), where this code path never runs.
- Separately, GLM-5.3 accuracy with DBO on is well below DBO off (GSM8K ~0.6 vs 0.93) with or without this change. That is a separate, pre-existing DBO bug in GLM-5.x's shared top-k layers that this crash was hiding, fixed in #60734 (see Validation).
- No cost when the SM count is unchanged (one host-side `get_num_sms()` per indexer layer). Under DBO, one ~9 µs metadata kernel per microbatch per forward, reused by all indexer layers. No host syncs; CUDA-graph safe.
- XPU / ROCm paths unchanged.

## Details

**Root cause** (main @ 240785b8):
- `create_sm_control_context` (`vllm/v1/worker/ubatch_utils.py:83-126`) uses `deep_gemm.set_num_sms` as the compute-SM setter whenever `has_deep_gemm() and comm_sms > 0`, so inside the microbatches DeepGEMM sees `total - VLLM_DBO_COMM_SMS` SMs (132 - 20 = 112 on H100/H200). It keys on DeepGEMM being importable, not on `VLLM_USE_DEEP_GEMM`. `comm_sms` is 0 only for DeepEP low-latency and NIXL-EP.
- The context wraps the microbatched forward in both runners (`gpu_ubatch_wrapper.py:426,453`; MRV2 `gpu/ubatch_utils.py:496`), after attention metadata has been built.
- The indexer builder plans the decode schedule for `num_compute_units` SMs (`v1/attention/backends/mla/indexer.py:967-968`, `:1688-1697`, MTP drafts `:1782-1789`), and `sparse_attn_indexer.py:729` / `glm5next/nvidia/sparse_indexer.py:582` pass it to `fp8_fp4_paged_mqa_logits`, which asserts it against the current SM count.
- The decode branch takes every request with `query_len <= 1 + num_speculative_tokens`, including 1-token short extends of prefix-cached prompts, which the reorder puts first. A step is microbatched only when every DP rank votes for it.

**How it was found:** GLM-5.3 RL with P/D disaggregation; prefill DP32/EP32 with DeepEP high-throughput, DBO, `cudagraph_mode NONE`, prefix caching, vLLM 0.29.0 on H200. One prefill rank hit the assertion after ~28 h; the other 31 then timed out in DeepEP dispatch and failed with `torch.cat(): expected a non-empty list of Tensors`.

**Fix:** `DeepSeekV32IndexerDecodeMetadata` records the SM count and block size the schedule was planned with. `get_schedule_metadata()` returns the planned schedule when DeepGEMM's current SM count matches; otherwise it re-plans with the same inputs and caches the result per SM count. The planned count is stored rather than derived from the tensor shape because SM90 `next_n=4` plans `num_sms // 2 + 1` schedule rows. `update_draft_decode_metadata` rewrites `seq_lens` in place, so it clears the cache. In FULL-graph DBO capture the re-plan kernel is captured and reads the persistent `seq_lens`/`indices` buffers; eager warmups under the same context JIT-compile it before capture.

<details>
<summary>Alternatives considered</summary>

1. Plan for the reduced SM count in the builder: the builder would need to replicate `create_sm_control_context` (all2all `max_sms_used()`, `VLLM_DBO_COMM_SMS`, the ROCm override) for both runners, and anything else that changes DeepGEMM's SM count would break it again.
2. Skip `set_num_sms` in SM control: removes DBO's compute/communication SM partitioning for every DeepGEMM GEMM.
3. Re-plan inside the `fp8_fp4_paged_mqa_logits` wrapper: no per-forward object to cache on, so every indexer layer would re-plan.
4. Build both schedules up front: an extra kernel every step even when DBO does not split.
</details>

**Not affected:** the sparse-MQA schedule of DeepSeek-V4.1 (planned inside the forward), FlashMLA scheduler metadata, and prefill `fp8_fp4_mqa_logits`.

- aniravich · comment · 2026-10-09T23:31:41Z · [source](https://github.com/vllm-project/vllm/pull/60732#issuecomment-6091036840)

> why can not we build metadata based on `total - VLLM_DBO_COMM_SMS` in the first place? Instead of changing it at forward time?

@zyongye  I considered that, so:
 - Whether a step is microbatched is only known per step, and the builder doesn't know. With --enable-dbo, DP ranks decide each step whether to split, and steps that don’t split run with all SMs. The microbatch-0 builder (get_metadata_builder(ubid or 0)) builds metadata for both split and unsplit steps, and build() gets no microbatch flag. A schedule planned for the reduced count up front would hit the same _schedule_meta_size == num_sms + 1 assertion on every unsplit step. Doing it at build time would mean passing a “microbatched / compute SM count” argument from the runner into the builder, in both MRV1 and MRV2.
 
- The compute SM count actually isn’t just total - VLLM_DBO_COMM_SMS. create_sm_control_context uses min(VLLM_DBO_COMM_SMS, all2all_manager.max_sms_used()), forces 0 on ROCm with DeepEP HT, and only calls deep_gemm.set_num_sms when DeepGEMM is available and the comm SM count is > 0. The builder would need to duplicate that and stay in sync with it.

Re-planning at the call site uses the SM count DeepGEMM is actually running with (get_num_sms()), so it stays correct whichever code path changes it (The cost ofc is one small metadata kernel per microbatch, on the first indexer layer.)
