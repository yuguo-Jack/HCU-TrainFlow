# [Test][V1] Cover input-queue arrivals during uncapped prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/60796) · state: open · merged: False

## Original PR description

## Overview

Add a regression test for a request arriving through EngineCore's input queue after an empty poll, while an uncapped lone-prefill batch is pending. This follow-up was discussed [with the author of #60485](https://github.com/vllm-project/vllm/pull/60485#issuecomment-6074742668).

Depends on #60485. The branch is based on `84d4578`, so the current comparison against `main` also includes the two commits from that prerequisite PR. The follow-up commit itself changes only the test file. After #60485 merges, the branch should be rebased onto the updated `main` and revalidated before merging this follow-up.

## Claims

- Cover both synchronous and asynchronous scheduling through the real input-queue dispatch, scheduler, and GPU model execution.
- Verify that no extra prefill batch is scheduled before the pending batch is drained, and that the next poll admits the newcomer before the next schedule.
- Verify that the original long request is capped again: with a budget of 10 and threshold of 5, the next batch contains 5 tokens for the long request and 1 for the newcomer.

## Details

The test reuses `DummyExecutor` and the existing request helper. It initializes an `EngineCoreProc` with in-process queues and manually drives the production poll/step methods without starting ZMQ threads. Events hold the executor's single worker until a receiver thread has enqueued the newcomer at the first batch's result-wait boundary. This controls ordering without sleep-based timing; it does not require a CUDA kernel to be executing at the instant of arrival.

The long prompt has 24 tokens, leaving 14 after its first 10-token chunk, so the later 5-token allocation demonstrates that the threshold is reapplied to the original request. Requests are drained to completion and the executor is released and shut down in `finally`.

This does not duplicate #60485's existing test, which adds the second request directly to the scheduler after draining the first batch. Focused searches for `60476 in:body`, `input_queue prefill`, and `lone prefill` found no open PR implementing this input-queue regression.

The follow-up commit makes no production code changes. HTTP/ZMQ transport, model-quality evaluation, and latency/throughput measurements are outside this test's scope; no performance claim is made.

@Ondre119 Thanks for driving this through. I walked the test against the actual `step_with_batch_queue` flow and it pins exactly the contract from #60485:

Step 1 leaves the queue empty and returns early (spy=1), because `can_schedule_ahead` sees `batch_queue[0].has_uncapped_lone_prefill` after the uncapped chunk lands. Step 2 is where the regression would show: with the old `if self.scheduler.has_requests()` check, the mid-step arrival would trigger a second `schedule()` while batch 1 sits in the queue, and `spy.call_count == 1` fails. So the assertion set (call counts, `batch_queue` drain, `"short" not in requests`, `num_computed_tokens == 10`) would all break without the fix, and the re-cap `{"long": 5, "short": 1}` on the next poll confirms the threshold re-engages once the arrival is visible.

The timing control is clean: patching `first_future.result` to gate on the receiver thread makes the mid-step arrival deterministic, and the `finally` blocks plus the 30s timeouts keep a broken run from hanging. The `EngineCoreProc.__new__` + manual attribute injection matches the harness style already used in this file for avoiding ZMQ I/O threads.

Two small nits, neither blocking:

1. `blocker = core.model_executor.thread_pool.submit(release_execution.wait, 30)` — the 30s here is the Event-wait timeout that becomes the blocking delay if `receive_newcomer` fails its assert, which is fine, but if the DummyExecutor finishes faster than the event you get a spurious pass path only on timeouts. Not a real concern given the `assert blocker.result(timeout=30)` afterwards.
2. After the final `core._process_engine_step()`, the drain loop runs up to 20 iterations but the engine actually needs only a handful (long has 24-15=9 tokens left, then decode for both). If the loop were ever to time out on `has_work()`, a failing assertion would point at a scheduler stall rather than this PR's surface. Fine as written.

One process note for when #60485 lands: please do rebase the test commit onto the updated main and rerun the GPU validation you reported, exactly as your body says. I will re-check the assertions once more against the rebased commit.

LGTM as the regression test for the input-queue path.
