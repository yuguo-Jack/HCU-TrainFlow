# [DeepSeek-V4-P1] Add standalone batch-invariant SiLU FP8 quantization

[Upstream PR](https://github.com/vllm-project/vllm/pull/59863) · state: open · merged: False

## Original PR description

## Motivation

DeepSeek-V4 MoE needs token-local activation quantization in batch-invariant mode. A token's FP8 activations and scales should not change when unrelated tokens or experts are added to the batch. This PR adds the CUDA quantization primitive; it does not switch a model or MoE backend to use it automatically.

## Implementation and numeric contract

- Register `fused_silu_mul_per_token_group_quant` through the existing stable `_C` extension and expose a Python wrapper in `fp8_utils.py`. The wrapper fails if the operator is unavailable, rather than silently selecting another quantizer.
- For each token and 128-element group, compute `SiLU(gate) * up`, its local absolute maximum, FP8 E4M3 values, and the corresponding scale. Support optional activation clamping, rounded or unrounded FP32 scales, and rounded packed UE8M0 scales.
- Accept contiguous BF16 `[tokens, 2 * hidden]` input and masked `[experts, tokens, 2 * hidden]` input with per-expert token counts. The current masked kernel requires a group count divisible by 16; unsupported narrow counts are rejected. Scale layouts follow the downstream expert GEMM contract.
- Use 64-bit offsets where large tensors exceed the 32-bit element range. In batch-invariant mode, disable custom all-reduce through parallel configuration; this does not itself validate distributed numerical alignment.

The invariant here is **token-local quantization**, not prefill/decode equivalence or end-to-end model invariance. The default quantization path is not changed by this PR.

## Validation

- The existing `persistent_masked_m_silu_mul_quant` is not a drop-in replacement on current main: it has no clamp argument and, with one expert and no clamp, differs from the original PR by 772 FP8 bytes/2 scale values at 16x4096 BF16 and 6,815 bytes/19 scales at 128x4096. On H100 its contiguous 16-token CUDA-graph median is 7.67 us versus 3.37 us for the original kernel; these are operator-level measurements only.
- H100 operator comparison against the original PR's standalone extension: FP8 output and scales are bitwise equal in 36/36 tested cases (contiguous/masked layouts, FP32/packed UE8M0 scales). The stable extension's median CUDA-graph latency ratio is 1.00 across those cases.
- H100 two-step DP4/EP4 integration with the other DeepSeek-V4 split PRs and weight reload: `training/rollout_probs_diff_max/mean/std = 0` at both steps, with `max_num_batched_tokens=1024` and `gpu_memory_utilization=0.55`. The original 2048-token setting OOMs during the optimizer step on this 80 GB setup, so this does not establish exact-configuration reproduction.
- Skipping redundant scale initialization only for contiguous output preserves FP8 bytes and scales in 24/24 cases; quant-wrapper CUDA-graph latency improves in every tested case (median ratio 1.25). This is not an end-to-end throughput claim.
- Local Ruff and diff checks pass. No new test files are part of this PR; the H100 comparison artifacts remain outside the PR.
