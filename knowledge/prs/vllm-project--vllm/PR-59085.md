# [Feature][Attention] Cover a whole spec-verify in one DiffKV split-KV program

[Upstream PR](https://github.com/vllm-project/vllm/pull/59085) · state: closed · merged: True

## Original PR description

## Purpose

This PR upstreams work from the patch set of the MiMo recipe we deploy — Diffbot's MiMo-V2.6-Flash-RL FP8KV/W4A8 recipe (Hugging Face: diffbot/MiMo-V2.6-Flash-RL-FP8KV-W4A8-2x-RTX-PRO-6000, built by Mike Tung): the idea and the original implementation belong to its authors, not to us. Their version of this change is the recipe's `triton_unified_attention_diffkv.py` patch — the same file #59054 links, which also carries an independent copy; we re-derived the diff against upstream main, wrote the tests, and ran the checks.

Fixes #59054.

### Motivation

Spec-decode verify batches do not take the Triton DiffKV split-KV path: the launcher's gate admits multi-token queries only by excluding them, so a q=8 verify runs as several 2D programs that each re-read the whole KV prefix, instead of one shared read for the verify. On the deployment (46K context, TP2) that was an 18-CTA grid; #59054 measures the same pathology independently on sm80.

This PR groups a whole verify into one split-KV program: `BLOCK_M = min(128, next_power_of_2(max_seqlen_q * num_queries_per_kv))`, adopted only when that grouped size exceeds the stock `BLOCK_M`, is a whole multiple of the GQA group, and fits the softmax-segment scratch — behind a `spec_3d` predicate (full attention, `1 < max_seqlen_q <= 16`) — with `num_warps` and `TILE_SIZE` launch kwargs. It also carries the deployment's epilogue correctness guard: once several query tokens share a program, a row can sit in a segment whose keys are all masked for it, ending at `M = 0, L = 0`; the epilogue reports `-inf` for that segment so `reduce_segments` treats it as absent. It then clamps an all-`-inf` `overall_max` to 0 in the reducer (the line from #58141, carried here per @hclsys's finding), so a row with no keys at all resolves to 0 rather than NaN.

### Relationship to open work

- **#58141** admits bounded multi-token batches to split-KV while keeping **each CTA a single query token** (plus an SM-count bound on the 2D grid, and reducer changes: a padding-row early return and an `overall_max` `-inf` clamp for queries with no keys). This PR is a different granularity — **all verify tokens of one request share a program** (one K/V tile read for q=8). After @hclsys's review this PR also carries #58141's one-line `overall_max` `-inf` clamp in the reducer beside the epilogue guard: without it a row whose keys are all masked computes `exp(-inf - -inf)` and emits NaN, so the guard alone was necessary but not sufficient. The two patches now both touch the reducer, whichever merges second drops the duplicated line, and if #58141 lands first this still needs its gate line rebased onto #58141's rewritten predicate.
- **#59052** (ours) rewrites the same `use_3d` gate line into the shared `can_use_split_kv` predicate — a textual conflict for whichever merges second; we will rebase.
- **#58650** (open) edits the same launcher file and the same `kernel_unified_attention_diffkv[grid](...)` call site (window-aware split-KV gate plus occupancy-aware launch config, gfx950-gated) — different purpose, same region, named so reviewers see it.
- **#58177** inserts at the same launcher site and also extends `tests/kernels/attention/test_triton_unified_attention_diffkv.py` (+80 lines); whoever merges second sees a test-file conflict.

### Duplicate-work check

Re-ran immediately before opening: `58141 in:body`, `DiffKV split-KV in:title`, `triton_unified_attention_diffkv`, `verify BLOCK_M`, and open issues matching `DiffKV verify split-KV` — no open PR duplicates this change; the overlaps are the four named above, and the only issue hit is #59054, which this PR fixes.

Pieces deliberately NOT in this PR (fail-closed): the prefill `BLOCK_M 128 / 8 warps` override is constants-only versus open #58177 (same launcher insertion point and same 64-token threshold; #58177's gate is narrower — SM12x, `num_queries_per_kv == 16`, 192/128 heads, bf16 — and we served our 128/8-warp delta as a review comment there); the 64-segment full-attention knob is a constant plus a builder realloc with no kernel change (served as a review comment on #58141); the custom `prefill_attn.cu` dispatch stays local (JIT CUDA extension pinned to one model's shapes, no test compiles CUDA, sm_120 correctness not CI-attestable).

## Test Result

Results: ruff clean, mypy clean, **1 passed, 96 skipped** — the 96 are the pre-existing FA3/FA4-gated kernel tests (FA3/FA4 not installed here). The new test `test_spec_verify_block_m_grouping_and_launch_kwargs` is host-only: it mocks both Triton entry points and pins `BLOCK_M`/`BLOCK_Q`/`IS_3D`/`TILE_SIZE`/`num_warps`/grid for a q=8 verify and for a plain decode, asserting `num_stages` absent on both paths, so the launcher decisions are covered without a GPU.

Disclosures, stated plainly:

- **No Triton kernel was compiled or executed anywhere in this work, and no speedup is claimed by us.** The epilogue guard's runtime effect and any output comparison against a reference are not-run in this environment; the deployment's numbers — decode 87–94 → 156–175 tok/s, bundled across its whole kernel row so no single change owns them — are theirs, and #59054 carries independent sm80 measurements of the same fix.
- The deployment exposes `_SPEC_3D_*` knobs (`VLLM_DIFFKV_SPEC_3D_MAX_Q` etc.) as environment variables; this PR ships them as module constants, matching upstream's `MIN_LAUNCH_GRID_SIZE_2D` precedent.
- `num_stages` is not set on this path (the deployment only sets it in the prefill branch, out of scope here).
- Post-review verification: an ad-hoc harness on an RTX 4090 (sm_89) reproduced @hclsys's result — at q=8, kv_len=1 the 3D leg emits 56 NaN rows without the clamp and 0 with it, and the clamp leaves every normal shape's output bit-identical (same max|d| as the unclamped run). No test was added for this: zero-key rows cannot occur at a live attention call (`seq_lens >= q_len` on every real batch), and even the stock 2D kernel writes NaN on them here.
- `pre-commit run` itself cannot execute in this NixOS environment (`stub-ld`), so the pre-commit-pinned ruff 0.14.0 and the manual mypy hook were run directly.

```
k=7  q=8          True     2.4e-04    no

ragged [2,8,4]    True     3.9e-03    no
q=8, kv_len=1     FALSE    nan        YES
q=8, kv_len=3     FALSE    nan        YES
```

The grouping itself is fine — the six normal verify shapes track the 2D path. The failures are rows with **no causal keys at all**, which is the case your epilogue guard is aimed at:

```python
M = tl.where(L > 0.0, M, float("-inf"))
```

That marks an empty *segment* absent, but when **every** segment for a row is empty, `reduce_segments` loads all `-inf`, `overall_max` is `-inf`, and `segm_expsum * exp(segm_max - overall_max)` is `0 * exp(-inf - -inf)` = NaN, so the row comes out NaN rather than zero.

Which makes this a hard dependency on #58141 rather than an independent change. I added **only** its reducer clamp on top of your branch, nothing else:

```python
overall_max = tl.where(overall_max > float("-inf"), overall_max, 0.0)
```

```
q=8, kv_len=1     True    0.000e+00
q=8, kv_len=3     True    0.000e+00
disagreements: 0
```

So the epilogue guard is necessary but not sufficient on its own. Your "Relationship to open work" says this PR "guards in the kernel epilogue rather than in the reducer, and touches neither the reducer nor any grid/SM bound" and that neither change is a superset of the other — true, but the ordering isn't free: **merged before #58141 this ships a NaN on the shape where `seq_lens` is a graph-capture dummy of 1**, which is the exact case #58141's clamp documents. I'd either carry that one line here too, or say in the description that it depends on #58141 landing first.

I haven't seen it on a live server — I hit it synthetically at `kv_len < max_seqlen_q`, and I'm taking the graph-capture-sets-1 detail from @lucamotz's note on #58141 rather than from my own trace.

Everything else I checked was clean: six shapes agree, no unwritten rows, and `q=1` never enters the path.

Good question, and no — the 2D leg really is NaN-free here. Re-ran counting rows the way you did, on your branch before the clamp commit:

```
case              rows   nanRows2D   nanRows3D   zeroRows2D
q=8 kv_len=1       256           0         224          224

ctrl q=8 kv=512    256           0           0            0
2 reqs q=4         256           0           0            0
q=1 kv_len=1        32           0           0            0
```

`zeroRows2D` is the thing that answers it: on GB10 the 2D kernel **writes exact zeros** into precisely the rows the unclamped 3D leg NaNs — 224 and 224, 160 and 160. So post-clamp the two legs agree rather than 3D being cleaner, and the `agree True / 0.000e+00` wasn't NaN-tolerance: `torch.allclose` defaults `equal_nan=False`, and my max|d| came from a plain subtract, which would itself be NaN if either side were.

Head config was `nqh=32 / nkvh=2`, so `num_queries_per_kv = 16` and the 2D path takes `BLOCK_M=16, BLOCK_Q=1` — if your MiMo shape is 64/4 that's also 16, so the tile isn't the difference and I can't account for the sm_89 behaviour from here.

One methodological thing that might be the whole discrepancy: with `out` pre-filled with NaN, a NaN row means either *the kernel wrote NaN* or *the kernel never wrote that row*, and those look identical. Mine is provably the first case for 3D (arithmetic NaN) and a real write for 2D (exact zeros). If you re-run your sm_89 leg with a distinctive finite sentinel — say `-12345.0` — the rows that come back as the sentinel are skipped writes and the rows that come back NaN are computed ones. On your table that would tell you whether sm_89's 2D kernel is producing NaN or just not storing those rows, which are quite different bugs.

Agree with not adding a test for it: `seq_lens >= q_len` on any real batch, so it isn't reachable outside a synthetic call. Thanks for carrying the line and for amending the reducer claim in the description.
