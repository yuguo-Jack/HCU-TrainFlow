# [ROCM][Perf] Add ROCM_SEGMENTED_ATTN attention-backend works across RDNA3/3.5/4

[Upstream PR](https://github.com/vllm-project/vllm/pull/59132) · state: closed · merged: True

## Original PR description

## Summary

Add an opt-in `ROCM_SEGMENTED_ATTN` attention backend with segmented Triton attention for paged decode, prefill, and multi-token verification. Startup tuning persists launch choices and shares a Triton cache across target and draft compilation.

- Supports RDNA3, RDNA3.5, and RDNA4 (gfx11/gfx12) with native FP16/BF16 KV; FP8 KV is gated to gfx12.
- Covers head sizes 64, 128, and 256, GQA ratios 1–16, causal and non-causal attention, sliding windows, and attention sinks.
- Includes focused kernel, backend-selection, workspace, tuning-cache, and Triton-cache tests.
- Uses the existing Triton/ROCm stack and adds no package dependency or custom compiler build.
- Startup autotuning is disabled by default to avoid the tuning sweep during engine startup. Set `--kernel-config.enable_rocm_segmented_attn_autotune=True` to enable it; skipping tuning may reduce serving performance.

## Relationship to existing work

This overlaps with [#55996](https://github.com/vllm-project/vllm/pull/55996), which adds generalized Triton SplitKV paged decode plus an optional RDNA4 FlyDSL path.The overlap is in terms of paged attention optimization. That optional path requires a custom FlyDSL build. `ROCM_SEGMENTED_ATTN` uses Triton already in vLLM, with no additional dependency, and covers paged decode, prefill, and multi-token verification across gfx11/gfx12. It also covers D=64, sliding windows, and attention sinks. The serving results below compare against `ROCM_ATTN`; they are not a direct performance comparison with #55996.

## Validation

The three serving comparisons used ROCm 10, the same PyTorch version, and the same GuideLLM 0.7.3 `simple-agent-multiturn-prefix-cache` workload. Each run used eight turns, 2,048 configured prompt tokens per turn, 512 output tokens per request, seed `20260715`, and 1/2/4/8 configured streams with 8/16/32/64 completed requests, respectively. All runs finished with zero errors or incomplete requests.

Each table compares `ROCM_ATTN` (baseline) with `ROCM_SEGMENTED_ATTN` (candidate). Values are arithmetic means across successful requests; output tokens/s is **per-request**. These are end-to-end serving measurements, including model execution and scheduling, rather than isolated kernel timings. Hardware, model, and serving options are listed for each comparison.

## Speculative decoding: Qwen3.8-27B-FP8 + DFlash2 on gfx1201

Measured on two Radeon AI PRO R9700 GPUs (TP2), using `Qwen/Qwen3.8-27B-FP8` with `z-lab/Qwen3.8-27B-DFlash2`, seven speculative tokens, FP8 KV, and concurrency 4. Both the target and draft use the backend selected for each case:

- **A:** `ROCM_ATTN`.
- **B:** `ROCM_SEGMENTED_ATTN`, autotuning disabled.
- **C:** `ROCM_SEGMENTED_ATTN`, autotuning enabled.

### Accuracy checks first

GSM8K uses the same first 100 test questions and five worked training examples in every case. Sampling follows the model's thinking-mode recommendation: temperature 1.0, top-p 0.95, top-k 20, min-p 0, presence penalty 0, repetition penalty 1, and default `xhigh` reasoning effort. Each question uses a fixed seed.

| Case | GSM8K correct / 100 |
| --- | ---: |
| A: baseline | 98 |
| B: segmented, static | 98 |
| C: segmented, tuned — pass 1 | 99 |
| C: segmented, tuned — pass 2 | 98 |

A/B miss IDs 12 and 45; C misses ID 12 in pass 1 and IDs 12 and 45 in pass 2. C repeats the same 100 questions, rather than adding 100 new evaluation questions. This is a quick quality check, not a full canonical GSM8K evaluation.

The long-context inputs are **coherent GSM8K worked problems**, followed by a new question; no random-token prompts are used. Actual input lengths are 16,606–16,636 and 32,817–32,847 tokens, with four requests at each length. These speed checks use a **512-token output cap**:

| Input | A correct / 4 | B correct / 4 | C correct / 4, passes 1 / 2 |
| --- | ---: | ---: | ---: |
| 16K | 3 | 3 | 3 / 3 |
| 32K | 3 | 3 | 3 / 3 |

The small sample and truncated outputs make the long-context results a serving check, not an accuracy claim.

### A → B: speculative-decoding speed with segmented attention

The backend covers multi-token verification and non-causal draft attention. The PR also reserves attention scratch space before graph capture, initializes draft attention in its own workspace lane, and preserves a shared Triton cache across target/draft compilation.

| Workload | A: baseline output tokens/s | B: segmented static output tokens/s | B / A |
| --- | ---: | ---: | ---: |
| GSM8K, 100 questions | 102.27 | **253.50** | **2.48×** |
| 16K coherent input, 4 requests | 8.20 | **185.47** | **22.62×** |
| 32K coherent input, 4 requests | 4.08 | **131.54** | **32.27×** |

These are **aggregate final output tokens/s**, calculated as returned completion tokens divided by batch wall time, including prefill and scheduling and excluding warmup and draft proposals. They differ from the **per-request** GuideLLM rates in the earlier tables.

Mean acceptance length (`1 + accepted draft tokens / draft rounds`) was approximately **4.05 → 4.05** for GSM8K, **1.04 → 3.92** at 16K, and **1.03 → 3.90** at 32K. The large long-context gains coincide with recovering draft acceptance from near one token per round in A. Both target and draft backends change, so this does not isolate a single kernel or establish the cause of the baseline acceptance collapse. The 22–32× figures describe this specific DFlash2 workload, not a general serving speedup.

### B → C: additional performance with autotuning

The tuner selects launch configurations for the target and draft attention workloads. Updated C uses the original C run's saved **125 target and 42 draft** tuning records, unchanged, with two warmed measured passes.

| Workload | B: static output tokens/s | C: tuned mean output tokens/s | C passes 1 / 2 | Observed C vs B |
| --- | ---: | ---: | ---: | ---: |
| GSM8K, 100 questions | 253.50 | **268.79** | 261.97 / 275.62 | **+6.0%** |
| 16K coherent input, 4 requests | 185.47 | **195.80** | 186.04 / 205.56 | **+5.6%** |
| 32K coherent input, 4 requests | 131.54 | **134.64** | 135.35 / 133.94 | **+2.4%** |

C is the arithmetic mean of both batch rates. These results suggest additional serving benefit from autotuning, but **A/B are historical single runs and C uses extended warmup plus prefix-cache resets**. The smaller B/C differences are observed comparisons, not an isolated or statistically established autotuning gain.

### First engine startup cost

Autotuning adds work on the **first startup with an empty matching tuning cache**:

| Configuration | Tuning time | Engine initialization time | Extra initialization vs B |
| --- | ---: | ---: | ---: |
| B: autotuning disabled | — | 253.88 s | — |
| C: cold autotuning (separate startup measurement) | 410.02 s target + 88.44 s draft | 750.34 s | **496.46 s (~8.3 min)** |

These are logged engine initialization times (profiling, KV allocation, and model warmup), not full process launch-to-ready times. Matching cached startups loaded all 167 records and tuned zero workloads, avoiding the tuning sweep; model loading, compilation, and graph capture still have their own costs. Cache invalidation can require retuning. Set `--kernel-config.enable_rocm_segmented_attn_autotune=False` to skip tuning.

- ydawei · comment · 2026-10-09T06:15:00Z · [source](https://github.com/vllm-project/vllm/pull/59132#issuecomment-6075470459)

Appreciation from the field: `ROCM_SEGMENTED_ATTN` rescues hybrid MoE decode on RDNA4. 8.8 → 68 t/s at 32K context on a single R9700.

If you run a hybrid linear-attention model (GDN/Mamba layers plus a few full-attention layers) on an AMD RDNA GPU, the regular ROCm decode path collapses at long context. The attention block size gets inflated to fit GDN state pages (my log line: `Setting attention block size to 1056 tokens`), the block is not a power of two, vLLM refuses the optimized `paged_attention_rocm` kernel and falls back to generic Triton paged decode, and decode degrades with context length until it is unusable. This is the same collapse described in https://github.com/vllm-project/vllm/issues/50264 .

With this backend, on llama-benchy (`--pp 2048 --tg 512 --depth 0 32768 --runs 3`, concurrency 1):

| config | decode t/s | decode t/s @ 32K ctx | prefill @ 32K (t/s) | TTFT @ 32K |
|---|---|---|---|---|
| vllm/vllm-openai-rocm:latest (v0.31.0), backend auto | 49.1 ± 0.1 | **8.8** | 2024 | 17.2 s |
| nightly (v0.31.1rc1.dev88+g81198e97b), backend auto | 50.1 | 9.5 | 2152 | 14.7 s |
| nightly + `--attention-backend ROCM_SEGMENTED_ATTN` | **73.8 ± 0.1** | **68.2 ± 0.2** | **4718** | **6.7 s** |

That is 7.8× faster decode at 32K context and 2.6× faster time-to-first-token, on the identical model, image, and flags. The `auto` rows were measured on the same machine minutes apart, so the comparison is a clean A/B. Note the backend only exists in builds newer than this PR's merge, so a `latest` image from before Oct 6 does not have it.

Environment:

- GPU: Radeon AI PRO R9700 32 GB (RDNA4), single card
- vLLM ROCm Docker nightly, v0.31.1rc1.dev88+g81198e97b
- Model: `cyankiwi/Qwen3.6-35B-A3B-AWQ-4bit` (hybrid GDN + attention MoE, AWQ INT4, head_dim 256)
- Flags: `--gpu-memory-utilization 0.97 --max-num-seqs 16 --enable-chunked-prefill --max-num-batched-tokens 2048 --attention-backend ROCM_SEGMENTED_ATTN`, prefix caching on, KV cache auto-fit to 239,712 tokens

Thank you @big-yellow-duck for building this and to @cadamcat whose profiling in #50264 laid out the mechanism. The hybrid-block-alignment plus generic-Triton-fallback path has degraded my Qwen3.6-35B-A3B slot repeatedly since v0.27 (0.27.0: 9.1 t/s at 32K, recovered by 0.29, 8.8 again on 0.31.0). This is the first fix that holds, and the 32K-context tier of my local serving stack is usable again.
