# [Core][Spec Decode] Add lookahead-aware prefix cache hashing for EAGLE-style draft models

[Upstream PR](https://github.com/vllm-project/vllm/pull/50897) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Implements #50438. EAGLE-family speculative decoding drops the last matched prefix-cache block and recomputes it, because the drafter's KV at the block's last position depends on the token after the block. **Lookahead block hashes** put that token into the cache key, so the block is reused only when it is proven equal. The drop costs one cache unit per hit, which is 544–1600 tokens on hybrid attention + Mamba/GDN models.

## Claims

- Prefix-cache hits with EAGLE, EAGLE3, MTP, DFlash and DSpark reach `floor((N - 1) / B) * B`, the same as without speculative decoding, instead of one unit less.
- Reuse stays correct: a hit reads the same draft KV as a cold run of the same prompt. A block whose lookahead token differs is not matched.
- Works with the local prefix cache and with Offloading, Nixl, Mooncake P2P, Mooncake Store and MultiConnector (when all children support it). Multi-module MTP and other connectors keep today's block drop.
- Model runners are unchanged; no new CPU/GPU synchronization.

## Details

**Design**

- `is_lookahead_block_hashing_enabled` (`kv_connector/v1/prefix_cache.py`) turns the mode on when all of these hold; otherwise the existing drop is unchanged:
  - `SpeculativeConfig.use_eagle_block_drop()`;
  - `VllmConfig.num_prefill_lookahead_tokens == 1`, because the key proves only the next token;
  - prefix caching, or a KV connector whose `supports_lookahead_block_hashes` is true.
- `get_request_block_hasher(..., use_lookahead_block_hashes=True)` emits the hash for a block ending at `e` only once token `e` exists, with `(block_keys, token_e, token_e_keys)` as extra keys. All KV cache groups share these hashes, since a request has one hit length across groups.
- Blocks are cached at allocation, as without lookahead hashes. At request finish, the block whose lookahead token is the last sampled one is cached from `update_from_output`.
- The scheduler clears `use_eagle_block_drop` in this mode, so the last-block drop, Mamba checkpoint back-off and replay-boundary shift are skipped.
- Content-addressed connectors (Offloading, Mooncake Store) save only blocks covered by `request.block_hashes`, which lag the computed tokens by up to one block. Mooncake Store pins a final save job at request finish for that block. Nixl and Mooncake P2P transfer the request's own blocks; for Mamba models they keep truncating the prefill side at `h(N-1)`.
- MultiConnector's children are built from per-child configs, so the factory pushes the parent's decision down to every child.

**Why it is correct.** For a block `[s, e)` the key proves the prefix through `e - 1` and the token at `e`. The drafter writes the draft KV at `e - 1` (input `(h_{e-1}, token e)`) in the step that prefills or samples token `e`. The hash exists only once token `e` is in `all_token_ids`, which never holds draft or in-flight tokens. Caching at allocation therefore never exposes a block whose draft KV is not written by the end of that step. Later reads are ordered after that write on the GPU, as for regular prefix caching.

**Limitations**

- Multi-module MTP (`num_nextn_predict_layers > 1`, k ≥ 2) keeps the block drop. Its module j at position p reads token p + j, and during decode it can read unverified drafts.
- Engines sharing a content-addressed store must use the same mode. KV events keep `main`'s shape; lookahead extra keys are `(block_keys, lookahead_token_id, lookahead_keys)`, and no field marks the scheme for external consumers. When cache blocks are coarser than `prefix_match_unit`, an event carries one extra-key tuple per block, as on `main`.
- Hybrid models lose the hit when a prompt diverges exactly at the producer's last retained Mamba boundary. After a request finishes, align mode keeps its Mamba state only at the last aligned boundary of its prompt. The lookahead key then falls back one unit, where no state is kept, so the hit is 0; the drop on `main` keeps that unit's state and hits one unit. `prefix_match_unit` does not change this.

Ported this PR onto a GLM-5.2 deployment branch (MTP-5, DCP-4, MooncakeStoreConnector, `fp8_ds_mla`) and hit two bugs in the MooncakeStoreScheduler that the current test suite doesn't catch. Sharing in case they're useful before merge.

---

**Bug 1 — pending-load save range not truncated (`data.py:286` assert crash)**

`build_connector_meta`'s pending-load branch hard-codes `max_save_tokens=None`:

```python
# scheduler.py, "Handle requests with pending load specs not yet scheduled"
req_meta = ReqMeta.from_request_tracker(
    request_tracker,
    self._block_size,
    load_spec=load_spec,
    ...
    max_save_tokens=None,   # <-- here
)
```

The other four `from_request_tracker` call sites all pass `self._max_save_tokens(...)`. When `can_load=False` but `kvpool_cached_tokens > 0` (partial lookup hit that didn't qualify for load), `_request_hashes_for_meta` truncates `block_hashes` to the publishable boundary via `_publishable_hashes`, but `token_len_chunk` covers the full kvpool prefix. `process_tokens` then trips:

```
assert token_len // self.hash_block_size <= len(block_hashes)
```

All 8 TP workers crash simultaneously. External prefix cache hit rate stays 0% because every save is aborted.

Fix: pass `self._max_save_tokens(unfinished_req, load_spec)` — same as the other call sites.

---

**Bug 2 — group-count mismatch when `req_tuple[1]` is empty (`EngineCore` fatal)**

`update_state_after_alloc` stores `()` (0 groups) into `_unfinished_requests` when `num_external_tokens == 0`:

```python
local_block_ids: tuple[list[int], ...] = ()
if num_external_tokens > 0:
    local_block_ids = blocks.get_block_ids()
self._unfinished_requests[request.request_id] = (request, local_block_ids)
```

The None-guard in the cached-req loop rebuilds from `req_tuple[1]`:

```python
new_block_ids = cached_reqs.new_block_ids[i]
if new_block_ids is None:
    new_block_ids = tuple([] for _ in req_tuple[1])   # req_tuple[1] == () → still ()
if not new_block_ids and not self.use_eagle_prefix_cache_hashing:
    continue
```

With EAGLE hashing active the `continue` is skipped, so `()` flows into `RequestTracker.update(())` → `ValueError: Group count mismatch: tracker has 1 groups, update has 0` → `EngineCore` fatal crash.

Before the factory wires up `set_eagle_prefix_cache_hashing(True)` the `continue` masks this; after it propagates, the crash surfaces.

Fix: rebuild from the tracker's `allocated_block_ids` (group count fixed at prefill/resume time) instead of `req_tuple[1]`:

```python
if not new_block_ids:
    if not self.use_eagle_prefix_cache_hashing:
        continue
    tracker = self._request_trackers.get(req_id)
    if tracker is not None:
        new_block_ids = tuple([] for _ in tracker.allocated_block_ids)
    else:
        new_block_ids = tuple([] for _ in req_tuple[1])
```

---

Both reproduced locally with unit tests (`test_pending_load_miss_truncates_save_to_publishable_hashes`, `test_eagle_cached_request_empty_block_list_uses_tracker_groups`); stashing either fix makes the corresponding test fail with the exact error above. Happy to send patches if that's easier than picking from the description.]

- Leoyzen · comment · 2026-08-16T04:31:22Z · [source](https://github.com/vllm-project/vllm/pull/50897#discussion_r3790942223)

File: `vllm/distributed/kv_transfer/kv_connector/v1/mooncake/store/scheduler.py` · line None

**Issue**: `num_publishable_block_hashes` starts at 0 and only advances after decode tokens are finalized, but save metadata is built before the fence advances (`build_connector_meta` runs ahead of `update_from_output`). On a cold-start prefill this publishes an empty hash list, so prefill KV is never written to distal KV stores (Mooncake L3 / offloading), breaking cross-instance prefill-cache sharing.

Prefill block hashes are suffix-bound to *finalized prompt tokens*, so they must not be gated by the publication fence (which exists to guard draft-token successors during decode). Suggest taking the max of the fence and the prefill-covered block count:
```python
prefill_hashes = request.num_prompt_tokens // self._hash_block_size
publishable = max(request.num_publishable_block_hashes, prefill_hashes)
```
Verified on TP8+DCP4 GLM-5.2 with Mooncake: cold prefill now saves prefill KV (save_put +32 keys/112MB), and after local prefix-cache reset the same prompt loads 2048 tokens back (load_get 8 ops/224MB, 0 failures).
