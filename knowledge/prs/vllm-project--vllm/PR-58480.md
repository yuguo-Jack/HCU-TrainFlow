# [Bugfix][Elastic EP] Keep the drafter compile tag and config on reset and reset the V1 drafter

[Upstream PR](https://github.com/vllm-project/vllm/pull/58480) · state: open · merged: False

## Original PR description

## Purpose

Fixes the crash in #58479.

#53934 made `_release_cuda_graphs` reset the drafter compile wrapper too but two parts are still missing on main.

`reset_compile_wrapper` re-runs the wrapper init under the current config and with an empty prefix. Elastic EP calls it under the target config so the drafter is rebuilt with the target config and the global `backbone` model tag and recompiles into the target's cache dir. With `VLLM_USE_AOT_COMPILE=0` it then loads the target's inductor graph and fails with `ValueError: too many values to unpack (expected 9)`. The wrapper now keeps the model tag it was built with and re-inits under its own config.

The drafter reset on main only finds the MRV2 drafter through `model_runner.speculator`. The V1 model runner keeps it on `model_runner.drafter` so it was never reset there and kept replaying CUDA graphs captured before the reconfigure. It now falls back to `get_draft_model()`.

The dummy drafter weights on new engines from the issue are not fixed here.

The E2E table below was run before the rebase onto the main that has #53934.

| | 2 to 4 | 4 to 2 |
|---|---|---|
| main | illegal memory access | server dead |
| main with `--enforce-eager` | ok | ok |
| main without `--speculative-config` | ok | ok |
| only the drafter reset with `VLLM_USE_AOT_COMPILE=0` | `ValueError: too many values to unpack` | server dead |

Every completion in the ok runs was `' Paris.\n\nThe official language is French.\n\nThe currency is the'`. Acceptance is 0 in all runs because the drafter is random. With this PR the old engines log separate `backbone` and `eagle_head` cache dirs after each scale.

- itayalroy · comment · 2026-10-10T00:14:44Z · [source](https://github.com/vllm-project/vllm/pull/58480#issuecomment-6091477008)

Thanks, this is indeed a bug in the CUDA graph recapture flow. 

In general, I am wondering about the future of this flow. The fast Elastic EP results we get (~1 second of downtime) are only achieved with the graph reuse path used by NIXL EP, which avoids the recapture entirely. Currently, we keep this fallback path because no other EP backend supports graph reuse (in particular, we have no coverage for StandardLayout MoE paths with graph reuse until we support that in NIXL EP, which is on the way).

Anyway, as long as we keep this path, we should keep it working, so I do think we should merge this fix
