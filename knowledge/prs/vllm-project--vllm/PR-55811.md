# [ROCm][Kimi-K3] Add merged MoE front

[Upstream PR](https://github.com/vllm-project/vllm/pull/55811) · state: open · merged: False

## Original PR description

## Summary

Integrates the Kimi-K3 merged MoE front from ROCm/aiter#5321.

Kimi-K3's MoE front applies three projections to the same `x[M, 7168]`:
shared gate/up `7168 -> 1536`, router logits `7168 -> 896`, and routed latent
`7168 -> 3584`. For the measured token counts this PR replaces them with one
BF16 GEMM into an FP32 `7168 -> 6016` accumulator followed by AITER's generic
SiTU/split epilogue. Routed experts remain on the existing modular AITER MXFP4
backend.

Unsupported configurations and token counts fall back to the native front.
There is no feature environment variable.

## Safety gate

The merged path is enabled only when all assumptions used by the optimized
implementation hold:

- gfx950;
- exact Kimi-K3 BF16 CUDA weight shapes and compatible devices;
- DP, EP, and PCP are all 1;
- sequence parallelism is disabled;
- the routed latent tail is shardable and has not already been reduced;
- modular routed experts are in use;
- activation is `SituAndMul(beta=4, linear_beta=25)`.

The runtime token gate intentionally matches the discrete set used for the
successful C1/C4 AgenticX measurements:

```text
1..16, 32, 48, 64, 80, 96, 112, 128, 192,
512, 1024, 1536, 2048
```

This retains the prefill anchors that were enabled during those runs. Other
prefill remainders and larger shapes use the native path. Expanding prefill to a
continuous range is deferred to the separately measured AITER tuning follow-up.

## Resource lifecycle

hipBLASLt is initialized only when a selected tuned row actually dispatches to
hipBLASLt. Initialization is process-cached, and all Kimi-K3 MoE layers in one
worker share a single front workspace. Weight processing therefore does not
allocate one hipBLASLt workspace per layer or unnecessarily reduce the KV pool.

The native fallback calls the internal implementation directly so a fallback
from the custom-op boundary does not advance the MoE layer index twice.

## Accuracy

GSM8K, full 1319-question split, 5-shot greedy: baseline 0.9659 strict-match,
merged 0.9719. Of 24 discordant answers, 16 changed to correct and 8 to
incorrect (two-sided sign test p=0.15), consistent with run-to-run numerical
nondeterminism rather than an accuracy change.

### GSM8K accuracy A/B

Adding the accuracy evidence this PR was missing. The numerical tests compare
the fused kernel against a `torch.mm` reference built from the same merged
weight, which is self-consistent and therefore blind to the one failure mode
specific to this change: the merged front slices its router logits out of a
`7168 -> 6016` accumulator where the native front runs a separate `7168 -> 896`
GEMM. Both are BF16 x BF16 -> FP32, but the wider shape picks a different
solution with a different accumulation order, and that rounding difference can
flip a borderline top-16 expert selection. Only an end-to-end score can see it.

Full 1319-question GSM8K test split, 5-shot, greedy. Both arms ran back to back
on one node from the same image, at `max_num_seqs=8` with
`num_speculative_tokens=3` and block rejection sampling, so a saturated decode
step submits 32 tokens and the merged front is the decode path for effectively
the whole run.

| Filter | Baseline | Merged |
|---|---:|---:|
| strict-match | 0.9659 | 0.9719 |
| flexible-extract | 0.9651 | 0.9712 |

Both arms answer the same questions, so the paired view is the informative one
rather than the unpaired +/- 0.005 binomial band: 1295 of 1319 answers agree, 16
flip to correct and 8 flip to incorrect, and an exact two-sided sign test on the
24 discordant pairs gives p = 0.15.

The merged front is indistinguishable from the native front on accuracy. The
+0.6 pp is run-to-run nondeterminism, not a claimed improvement.
