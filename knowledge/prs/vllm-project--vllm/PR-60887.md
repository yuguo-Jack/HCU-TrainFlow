# [KV Connector][Mooncake] Publish Store residency once per complete block

[Upstream PR](https://github.com/vllm-project/vllm/pull/60887) · state: open · merged: False

## Original PR description

## Overview

`MooncakeStoreConnector` now publishes residency for a logical block exactly once, when every Store namespace a later lookup probes for its cache group has reported, instead of deciding "common" from the number of workers that happened to report in one engine step. Implements item 2 of #58520. The first commit is #58293 (the prerequisite, rebased onto current `main` with its conflict resolved — review the second commit); #58670 takes item 4 and #52731 the read half of item 3.

## Claims

- A `BlockStored` is released only once the union of the reporting ranks' coverage spans the namespace set `MooncakeStoreWorker._lookup_key_prefixes` holds for that cache group, so a repeated report from one rank or namespace cannot stand in for a missing one.
- Coverage accumulates across engine steps: ranks that finish the same Store block in different steps still produce one announcement, at the last namespace, and a later report of an already announced block is dropped for the rest of the residency epoch.
- The quorum is the group's own lookup prefixes, so replicated GQA/MQA, rank-specific shards, PCP, DCP, PP and `store_tp_size` layouts are covered without a second topology formula.
- Dedup hits count locally: a block whose Store objects were all already resident is reported too, and a block whose other objects were resident is still reported when its own put commits, while a partial `batch_put` failure reports nothing for the blocks it touched.
- A reset that wipes the Store drops the reports buffered on the wiping rank for the objects it removed, so they cannot enter the next poll as residency of the fresh Store.
- `AllBlocksCleared` (item 4) ends the residency epoch: pending coverage and the announced ledger are retired, so a successful reset lets a block stored again be announced again, and a failed reset keeps the ledger because the Store still holds what it announced.

The aggregation contract is covered by new tests: cross-step completion announcing once at the last namespace, a repeated namespace not covering another, empty polls neither completing nor resetting coverage, per-shape required sets (replicated / rank-specific / PCP / PP / `store_tp_size`), coverage outside the lookup table and disagreeing per-rank tables rejected, one block announced once when its two reports carry different payloads, a completed block leaving no partial state behind, worker-container pickle transport, clear retiring pending and announced state with pre-clear releases ordered before it, and successful/failed `reset_cache` epochs. The worker side asserts the namespaces each rank reports for a shared `store_tp_size` group, a fully deduplicated block still being reported, put failures being mapped back through dedup to the block they belong to, a partial put reporting nothing, and a wipe dropping the reports it invalidated (through `LookupKeyServer._reset_store`, not a copy of it).

Prompts are 4106 tokens; every run ends by repeating the first prompt. In the healthy runs the announced set is exactly what the Store holds: 176 objects and 152 complete blocks (each mamba block in two rank namespaces, each MLA block in one), 152 announcements, none premature and none missing, and the repeated prompt added no announcement at all.

The 24 MB runs are where the two revisions separate: puts fail, and the pre-item-2 revision announced 11 and 12 blocks twice, because it released a block once `reports * replication_factor >= workers` without any rank identity in the count, so a later re-report of the same block crossed the threshold again. This revision announced every block once in each of the three runs, and never announced a block whose Store objects are not all committed.

Under that pressure the Store also reclaims objects it accepted: it ends the run holding 72-73 objects and 58-64 complete blocks out of roughly 150 objects written per rank, while only 9-12 puts failed, so objects were dropped after being accepted. The connector has no eviction signal, which is the boundary #58520 assigns to item 4, and it is why the premature-announcement column is only filled for the runs without failures: once the Store reclaims objects faster than any observer can sample them, the same gaps appear for both revisions and cannot be attributed to the aggregation rule.

Artifacts (harness scripts, per-run logs, event streams, Store snapshots and the comparison reports) live on the test host rather than in this PR. Each scenario starts `mooncake_master` and `vllm serve` with the revision under test, reads the Store key list, drives the prompts through `/v1/completions` while subscribing to the event stream, and compares the announced blocks with the Store contents.

## Details

Root cause: the scheduler accumulated one `BlockStored` per rank in a `Counter` and released an entry when `count * tp_replication_factor >= num_workers`, with `num_workers` counting only the workers that reported in that step. The count carries no rank identity, so the same rank reporting a block twice (for example after the Store evicted its copy) reaches a two-worker quorum by itself, and entries whose second report never arrives stay in the counter indefinitely. `MooncakeStoreKVEvents` no longer counts; it keys pending state by `(group_idx, block_hash)` and releases a block when the reported namespaces cover the group's probe set.

Implementation: the send thread derives each committed block's namespaces from its Store object keys and reports them with the event. A block is reported when every one of its Store objects is in the Store, whether this call wrote it or found it already present, and the batched put's failed indices are mapped back through the dedup filter to the blocks they belong to, so an already resident object neither hides the block nor makes a failure land on the wrong one. `KVOutputAggregator` folds worker containers with `KVConnectorKVEvents.merge` so that metadata survives the step (the base implementation is the previous `add_events(get_all_events())` call, so other connectors are unaffected); the scheduler-side accumulator is created once and kept for the connector's lifetime, and `take_events` drains the released events. `add_residency` validates that a block's namespaces are inside its group's probe set and that every rank agrees on that set, and `AllBlocksCleared` arriving through the event stream retires the epoch. On the reset path, `LookupKeyServer._reset_store` drains in-flight puts, wipes the master, and then drops the reports this rank buffered for the objects it removed, so a job that finished after the last poll cannot report them into the fresh Store.

Tradeoffs and limitations: coverage for a block that never completes is retained until the epoch ends rather than expiring on a timer, which keeps the rule "a later contribution may complete it" — such entries hold the event payload, so a long run with permanent put failures accumulates them (reset releases them). Batches whose objects are all already resident now report their blocks, where they previously reported nothing, which adds events for re-requests in exchange for the coverage those blocks need; repeats of an announced block are dropped by the accumulator rather than at the source. Evictions remain invisible to the connector, so a rank that re-stores a block after an eviction can complete coverage whose earlier half the Store has since dropped; that is the boundary #58520 already documents for item 4. The reset slice above covers the rank that wipes the Store; the other ranks can still have reports buffered from before the wipe, and closing that needs a reset order across ranks (a generation broadcast or a per-rank reset hook), which belongs to item 4 and is the one known gap. The one shared-path touch is the `KVOutputAggregator` line above.

Coordination with item 4 (#58670): that PR drives the clear through `pop_common_events()` and keeps `_kv_cache_events` alive on failure. This change renames the drain to `pop_ready_events()`, keeps the accumulator on a failed reset, and drops it on a successful one; item 4 can queue its clear with `MooncakeStoreKVEvents.add_events([AllBlocksCleared()])`, which retires pending and released state and orders the clear after the events released before it.
