# [Rust Frontend] Stream the default /inference/v1/generate body from the request runtime

[Upstream PR](https://github.com/vllm-project/vllm/pull/60541) · state: open · merged: False

## Original PR description

## Purpose

Part of RFC #57479 (cheap frontend after an RL `pause(mode="abort")`).

A non-streaming `/inference/v1/generate` response with output logprobs is built in the Rust frontend as a full `GenerateLogProbs` tree, then serialized into one contiguous buffer by `axum::Json`. In RL rollouts with long generations and top-k logprobs, an abort returns every in-flight request at once. Each response is then several GB, all built at the same moment.

This PR writes the output logprobs straight from the engine rows into a streamed body. The bytes are the same as the serde serialization.

- A task spawned by the handler renders chunks of about 1 MiB into a bounded channel holding 2 chunks, and the HTTP body drains that channel. The task runs on the request runtime for the offloaded generate route.
  - The HTTP runtime, which also serves `/health`, `/pause` and `/resume`, only moves bytes that are ready.
  - Backpressure is kept, and dropping the body stops the render.
- The body is sent chunked. If the render task stops early, an explicit completion marker makes the body fail, so the client never gets truncated JSON that ends cleanly.
- Rows without candidates are still rejected with a 500 before the body starts.
- Responses without output logprobs are unchanged: they still go through `axum::Json` with an exact `Content-Length`.
- The rest of the response is still serialized by serde as a `GenerateResponse`. The choice's `logprobs` holds a unique placeholder string, and the body is split around it, so every other response and choice field (including ones added later) comes from serde unchanged. To allow the placeholder, `GenerateResponseChoice.logprobs` becomes an `Option<Box<RawValue>>` (serde_json `raw_value` feature).
- The `top_logprobs` selection (dedup, `max(requested, 1)`, or everything for `-1`) is shared between the serde path and the renderer.
- HTTP latency metrics now end when the headers are sent.

There is no API or output change.

**Based on:** aoshen02/vllm#107 (by @aoshen02), the Rust "streamed default render" PR from the RFC #57479 work. It is ported to current main:
- it renders the integer-id `GenerateLogProbs` shape from #58181;
- the response fields added since then (`sampling_mask`, `prompt_token_id_logprobs`, `prompt_token_ids`, `mm_placeholders`, `metrics`) come from serde through the placeholder split instead of a hand-written envelope;
- chunks are bounded by bytes instead of 64 positions, because a `logprobs=-1` row has no size bound.

**Not a duplicate.** No open PR streams or reworks this response body:
- `gh pr list --repo vllm-project/vllm --state open --search "57479 in:body"` returns only #58278 (API-server listeners) and #58314 (the `/v1/completions` serializer).
- #60251 adds `stop_reason` to this response. It needs no renderer change here, because the envelope comes from serde.

Co-authored-by: @aoshen02

## Test Plan

```bash
cd rust
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo test -p vllm-server --all-features --locked
```

The new tests cover:
- **Byte identity** against the serde reference for:
  - finish reasons abort, length, repetition, stop token and EOS;
  - `logprobs` 0, 1, 2, 8 and −1;
  - NaN, ±inf, −0.0, rank 0 and ids up to `u32::MAX`;
  - an escaped request id, every envelope field both null and populated, and a 5,000-position multi-chunk body.
- The direct writer against serde on 3,000 random rows, including repeated ids.
- Render placement on the request runtime, backpressure and early drop, the truncated-body error, the empty-row 500, and HTTP framing through `serve_connections`.

Real-GPU end to end, using a driver script (not part of this PR):
- **Parity:** sequential greedy requests with `ignore_eos` and k ∈ {0, 1, 8, 128}, compared against main with the `created` timestamp blanked.
- **Abort stress:** 32 concurrent non-streaming requests at top-128, with `POST /pause?mode=abort` 45 s after submission. The client only receives bytes while the clock runs and parses afterwards. Server RSS is sampled from the process tree.

## Test Result

- `cargo fmt` and `clippy -D warnings`: clean. `cargo test -p vllm-server`: 458 passed, 0 failed.

**Real GPU** (GB200, Qwen3-0.6B, `--data-parallel-size 2`, `VLLM_USE_RUST_FRONTEND=1`):
- **Parity:** the default response bytes are identical to main for all 16 requests (4 prompts × k ∈ {0, 1, 8, 128}, 256 tokens each).
- **Abort stress:** main vs this PR, 2 runs per side in A/B/B/A order. This PR's column is from 4 later runs at the current head. All responses are valid. Each run left about 400k aborted positions across 32 requests, about 2.6 GB of response bodies.

| | main | this PR |
|---|---|---|
| `/pause?mode=abort` returns | 0.03–0.07 s | 0.04–0.05 s |
| abort → all bodies received | 0.66–0.91 s | 0.49–0.79 s (median 0.55) |
| peak RSS, largest server process | 7.7–8.4 GiB | 3.9–4.1 GiB |
| peak RSS, whole server process tree | 20.8–21.4 GiB | 14.7–15.4 GiB |

The gain at this scale is mostly memory. The memory saving grows with response size. In the RFC #57479 mock-engine runs (32 × 245,760 tokens × top-128, DP8), the original version of this change, measured on the pre-#58181 logprobs format, cut abort-to-parsed time from 32.9 s to 20.7 s and peak memory from 202 GiB to 14.5 GiB.
