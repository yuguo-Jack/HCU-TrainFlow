# [Perf][Attention] Skip nonempty output rows during sparse MLA cleanup

[Upstream PR](https://github.com/vllm-project/vllm/pull/60835) · state: open · merged: False

## Original PR description

## Purpose

Draft for scope coordination with #48196. Current-main port and broader model
evaluation remain pending. The submission branch excludes the historical
correctness-fix commit used by the benchmark runtime.

Avoid rewriting valid attention outputs when cleaning up empty sparse-attention
shards. On the tested GLM-5.2 c32 workload, this reduced TPOT by **5.98%** and
increased output throughput by **6.53%**, with lower TTFT and p99 ITL.

```text
ASIS
sparse attention -> scan Top-K indices for empty rows
                 -> masked_fill over the entire O tensor
                 -> masked_fill over LSE -> DCP combine
```

```text
PR
sparse attention -> read existing valid-token count per row
                 -> nonempty: leave O and LSE untouched
                 -> empty: write O=0 and LSE=-inf -> DCP combine
```

The index-remapping kernel already computes the required valid counts. A single
Triton launch uses one block per row and a device-side conditional, so changing
which rows are empty remains compatible with CUDA-graph replay. It replaces the
index scan and two masked fills without changing attention math, projection,
communication, or buffer ownership.

## Relationship to #48196 and #60627

This overlaps with the empty-row cleanup portion of #48196. That broader PR
also changes projection/merge ordering and can fold cleanup into A2A packing.
Its standalone cleanup kernel uses one block per row/head; this implementation
uses one block per row and loops over the output only when the row is empty.
We have **not** measured a head-to-head comparison against #48196 and do not
claim to outperform its standalone or fused implementation.

The proposal is to coordinate a narrow standalone cleanup change with #48196's
author, rather than duplicate the broader output-merge work. Agreement on that
split is still pending.

This is separate from #60627, which accelerates the direct DCP Output/LSE
consumer. Both serving benchmark arms below already include #60627, so these
are incremental gains, not another measurement of that PR.

## Test Result

4x GB200 at 1800 MHz, GLM-5.2 NVFP4, TP4/DCP4/EP4, FP8 KV, FlashInfer sparse
MLA, 3072 input / 128 output tokens, c32. Prefix caching disabled, synchronous
scheduling, FULL_DECODE_ONLY/breakable CUDA graphs, compilation disabled.
Two fresh processes per arm, run in ABBA order; 128 counted requests per process
after identical correctness smoke and 32-request warmup. All 512 counted
requests succeeded.

| Metric | Baseline | PR | Improvement |
| --- | ---: | ---: | ---: |
| TPOT | 81.548 ms | 76.672 ms | 5.98% |
| Output throughput | 340.204 tok/s | 362.425 tok/s | 6.53% |
| TTFT | 1589.456 ms | 1472.422 ms | 7.36% |
| p99 ITL | 314.744 ms | 287.427 ms | 8.68% |

Paired TPOT improvements were 5.49% and 6.47%. Process TPOT CV was 0.55% for
baseline and 0.031% for candidate. These are two-pair observations, not a
confidence interval or a claim about other workloads.

**Validation scope:** pinned runtime `71323cbf1a`, with #60627's final native
consumer in both arms and only this Python backend module substituted in the
candidate. This is not a full current-main build comparison. No split-KV
prototype or scheduler change is included.

## Why this helps

A short profile found that the BF16 output masked fill accounted for 7.92% of
summed GPU-kernel time in a mixed prefill/decode window. These batches contained
roughly 4096 tokens, exceeding the direct consumer's decode workspace. The
cleanup still traversed every output element even when no row needed changing.
The percentage describes that profile window, not all c32 serving wall time.

For 4096 rows, H=64, D=512, BF16 O and FP32 LSE, CUDA-graph operator timing
including the old mask construction and both fills:

| Empty rows | Baseline cleanup | New cleanup |
| --- | ---: | ---: |
| None | 326.147 us | 2.914 us |
| One quarter | 288.615 us | 20.370 us |

These component results are separate from the serving measurements above.

## Test Plan

- 30 focused repository tests passed: strided outputs, changing-input graph
  replay, FP16/BF16, NaN payloads, zero rows, and valid-count/empty-mask equivalence
  for DCP sizes 1/2/3/4/8. The latter simulates rank mappings on one GPU; it is
  not an eight-GPU distributed test.
- A separate 180-case numeric/graph sweep passed.
- On actual FlashInfer outputs at 1/32/4096 rows, cleanup matched the original
  index-based masks exactly, and attention left the valid-count tensor unchanged.
- Applicable pre-commit hooks, including mypy, passed.
- GSM32 smoke scores were baseline 30/32 and 27/32, versus candidate 28/32 and
  28/32, with finite token logprobs throughout. This small variable smoke does
  not establish model accuracy equivalence; broader evaluation remains pending.

Focused tests, with the candidate backend loaded:

```bash
python -m pytest tests/v1/attention/test_sparse_mla_backends.py -q \
  -k 'flashinfer_empty_shards_preserve_valid_rows or dcp_valid_counts_match_empty_row_mask'
```

AI assistance was used for implementation, profiling, and validation.
