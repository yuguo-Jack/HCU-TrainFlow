# [Kernel] Integrate FA4 SM90 FP8 MMA for Gemma-4 full attention

[Upstream PR](https://github.com/vllm-project/vllm/pull/60372) · state: open · merged: False

## Original PR description



## Overview

Enable FP8 MMA in the SM90 FA4 full-attention kernel ([PR199](https://github.com/vllm-project/flash-attention/pull/199)) for Gemma-4 while retaining FP8 KV-cache storage.

Gemma-4 uses head dimension 512 for full attention and 256 for sliding-window attention. This change compares FP8 MMA against the existing path that reads FP8 KV, dequantizes it, and performs BF16 MMA.

On H200, FP8 full attention uses FA4, while FP8 sliding-window attention continues to use FA3. FA4 FP8 sliding-window attention with head dimension 256 is currently unsupported.

## Claims

- Integrate the SM90 d512 FP8-MMA kernel while preserving native FP16/BF16 queries and supported FA3 sliding-window routing.
- Gate unsupported kernel combinations and normalize descale layouts.
- Preserve automatic FA4 full-attention splits and the FA3 CUDA-graph split cap of 32.
- Report measured gains over the KV-dequantization baseline and the remaining regression against BF16 KV/MMA.

## Validation
The MMA labels describe the **full-attention path**. Both FP8-KV configurations use FA3 FP8 sliding-window attention; the BF16-KV reference uses FA4 BF16 sliding-window attention.

Serving setup:

- Gemma-4-31B-it-FP8 weights for all configurations.
- Four H200 GPUs on one node; TP4.
- Approximately 25K shared prefix plus 3K unique input tokens.
- 128 requests, 200 output tokens per request.
- MTP enabled with three speculative tokens.
- Prefix-cache reuse enabled.
- Concurrency 1–64; median of three rounds.

## Details

### Why FP8 is slower than BF16

Nsight shows that faster FP8 full attention does not necessarily produce faster end-to-end execution.

#### Sliding-window attention and KV-cache operations offset full-attention gains

The profiling setup uses 25K inputs, TP4, MTP enabled, prefix reuse enabled, and offered concurrency 64.

| Target-model kernel work | FP8 KV + FP8 MMA | BF16 KV + BF16 MMA | FP8 time reduction vs. BF16 |
|---|---|---|---|
| Full attention | **6.681 ms** | 7.584 ms | **+11.9%** |
| Sliding-window attention | 5.482 ms | **4.206 ms** | −30.3% |
| KV-cache writes | 0.261 ms | **0.157 ms** | −66.2% |
| Attention preparation | 0.105 ms | 0 | N/A |
| Whole-cycle GPU span | 29.879 ms | **29.391 ms** | −1.7% |

Time reduction is `100 × (BF16 time − FP8 time) / BF16 time`, calculated from the displayed times. Positive values mean less time (faster); negative values mean more time (slower). 

Full attention is approximately **12% faster**, but sliding-window attention is approximately **30% slower**, with additional KV-write, preparation, and combine work.

KV-write overhead refers to the kernels that reshape and write newly generated keys and values into the paged cache, including the FP8 conversion/quantization path. Attention reads and prefix-cache reuse accounting are separate from this kernel category.

Reuse-off profiles show the same pattern.
The following comparison uses **cc16**, 25K inputs, TP4, MTP enabled, and prefix-cache reuse disabled. These matched pure-decode cycles process **16 active requests per target step**. Values are medians across four GPU ranks of each rank's per-cycle medians, with 69 matched cycles per rank for BF16 and 87 for FP8.

| Target-model kernel work | FP8 KV + FP8 MMA | BF16 KV + BF16 MMA | FP8 time reduction vs. BF16 |
|---|---|---|---|
| Full attention | **1.9670 ms** | 2.4358 ms | **+19.2%** |
| Sliding-window attention | 1.9593 ms | **1.3867 ms** | −41.3% |
| KV-cache writes | 0.2551 ms | **0.1413 ms** | −80.5% |
| Attention preparation | 0.1098 ms | 0 | N/A |
| Whole-cycle GPU span | 14.6594 ms | **14.2903 ms** | −2.6% |

Full attention is faster, but SWA, KV-cache writes, and attention preparation/combine offset the gain. The whole-cycle GPU span is **2.6% longer** for FP8. This is a profiling comparison, not an unprofiled end-to-end throughput measurement.
