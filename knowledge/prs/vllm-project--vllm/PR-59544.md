# [KV Offload] Pin only each worker's own offload slots

[Upstream PR](https://github.com/vllm-project/vllm/pull/59544) · state: open · merged: False

## Original PR description

Outside the replicated layout, each worker only uses its own slot of every row in the shared CPU region, yet every worker `cudaHostRegister`s the whole region. At TP4, every page gets pinned four times.

Register only the worker's slot of each row, rounded out to pages. The replicated layout keeps whole-region registration. So do slots within a page of the full row and regions over 65,536 rows, where per-call overhead would dominate.

TieringOffloadingSpec workers pin through the same path, so they get this too. #59430 lists this redundant pinning as a follow-up, and no open PR changes it.

## Tests

4× H200, measured on `16d4ac4ba3` with this change (the touched files are unchanged on current main):

- GLM-5.3 W4A8, TP4 + EP, 256 GiB native CPU offload: the offload startup step fell from 63.6 to 34.8 s, and pinning from 20.8 to 6.8 s, as each rank registered 68.8 GB instead of 274.9 GB. A 20k-token retrieval prompt answered 8/8 lookups cold and 8/8 after `/reset_prefix_cache`, with 3.9 GB reloaded from CPU.
- `pytest tests/v1/kv_offload tests/v1/kv_connector/unit/offloading_connector tests/v1/kv_connector/unit/test_offloading_connector.py tests/v1/worker/test_utils.py`: 1184 passed. The 7 failing tests need a gated model and fail the same way on main.
- pre-commit, including mypy, passed.

An independent data point supporting this: when several processes pin the same region, as the TP ranks do on main, the pin time grows with TP. For 100 GB it went from about 9 s with one process to 31 s with eight. I also tried threading the registration within one process instead. It gave no speedup. So pinning less, as this PR does, looks like the right fix. Details are [here](https://github.com/YannikHinteregger/vllm-cpu-pin-benchmarks).
