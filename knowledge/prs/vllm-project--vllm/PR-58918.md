# [Bugfix][Compile] Replace Transformers AOT caching with graph caching

[Upstream PR](https://github.com/vllm-project/vllm/pull/58918) · state: open · merged: False

## Original PR description

## Purpose

Fix compilation caching for the Transformers backend by running Dynamo tracing on each startup while reusing PyTorch graph caches.

Decorated HF `forward` methods can fail model-AOT serialization. Disabling model AOT alone is insufficient: direct artifact lookup can reuse stale compiled code when decorator state changes between processes.

Following the review suggestion, HF opts out through `support_torch_compile(..., use_aot_compile=False)`. The option is passed explicitly through `init_backend` to the backend, compiler manager, and adaptors:

- Skip model AOT, mega artifacts, and direct artifact loading/saving, including existing cache-index lookup.
- Retain PyTorch graph caching and initialize persistent Inductor/Triton cache directories.
- Preserve native AOT caching, including native EAGLE3 drafts under an HF target.

This replaces the earlier `CompileCachePolicy`, owner ContextVar, and loader changes. The opt-out applies in `CompilationMode.VLLM_COMPILE`; cache-disable settings remain respected. HF does not attempt forced model-AOT loading when opted out.

Related to #50128, specifically compilation caching. Follows the graph-caching recommendation in #53295 and preserves the cache-relocation behavior from #52142. This addresses HF cache routing rather than the cache-key API migration in #39517 or empty-artifact validation in #56879.

## Test Plan

- Fresh-process regression for changed decorator closure state, warm graph-cache hits, and repeated forward calls, covering both Inductor adaptors.
- Native AOT save/load after an opt-out module runs under the same configuration.
- Functorch configuration restoration on normal/exceptional exit and hash calculation; bypass of existing direct-cache metadata and handles.
- Three HF models and a native control under two cache-persistence protocols; real TP=2 and full HF-target/native-EAGLE3 generation.
- Full Qwen3-0.6B GSM8K evaluation under the batch-invariant compilation configuration described below.

### Correctness and cache behavior

- **HF:** all After warm performance runs hit FX/AOTAutograd caches; model-AOT/direct-artifact save/load counts remain zero.
- **Native:** all cold runs save AOT; all five warm runs per version/protocol load it with zero model-AOT recompilations. Separate forced-load checks also pass.
- **TP=2:** Qwen3-0.6B HF completes cold/warm initialization and generation on both versions. Both After ranks record three FX and three AOTAutograd hits on warm start, with separate rank cache directories.
- **EAGLE3:** full generation with Qwen3-0.6B HF and `Nicolassuez/Qwen3-0.6B-eagle3` completes across cold/warm processes. The HF target uses graph caching; the native draft saves AOT on cold start and loads it on warm start.
- **Cache disable:** separate HF cold/warm checks retain compilation while recording zero FX/AOTAutograd cache hits and zero model-AOT/direct-artifact saves or loads.

Performance runs generate the same 32 prompts after initialization, using batch sizes 1/4/8, greedy decoding, and up to 64 tokens. **All 128 comparisons pass the existing repository helper without relaxed tolerances; 124/128 contain token-sequence differences.** Each comparison covers 32 prompts; this count is not a prompt failure rate or an accuracy measurement.

### Qwen3-0.6B GSM8K

All **1,319 questions**, 5-shot, greedy decoding, 256-token generation limit. Before cold, After cold, and After warm each score **519/1319 (39.35%)**, with **identical per-question answers and complete token sequences**. Each run has 3 invalid answers and generates 132,670 tokens. After warm records **29 FX graph hits and 29 AOTAutograd hits**.

This uses batch invariance with compilation enabled, max model length=4096, max batched tokens=2048, and max sequences=8. Batch invariance disables model AOT upstream; mega/standalone remain enabled. This evaluation does not establish quality equivalence under the default AOT-enabled configuration or for Qwen3-14B. Evaluation timings are excluded from the performance results.

- hmellor · COMMENTED · 2026-10-08T15:21:32Z · [source](https://github.com/vllm-project/vllm/pull/58918#pullrequestreview-5458963053)

Thanks for picking this up and for the thorough validation. Graph caching instead of AOT for the Transformers backend is the right direction, but I think the implementation can be much smaller.

The Transformers backend already applies `support_torch_compile` itself (`transformers/base.py`), so the owner of the compiled module is known at decoration time. Instead of `CompileCachePolicy` + the ContextVar + the loader changes, could we add a decorator option (e.g. `support_torch_compile(..., use_aot_compile=False)`), store it on the class, and pass it through `init_backend` to `VllmBackend`/`CompilerManager`? That handles the native EAGLE draft case for free and removes the `resolve()`/identity-check logic.

Smaller points:
- Make the flag a required argument in the compiler adaptors rather than defaulting to `resolve()`, so a missed call site can't silently fall back to the env policy.
- `bundled_autograd_cache=False` is patched in three places; passing the flag into `set_functorch_config()`/`_get_vllm_functorch_config()` would cover it once.
- Tests: please trim to behaviour, e.g. one warm-cache regression (changed decorator state recompiles instead of hitting a stale artifact) and one check that native AOT still saves/loads. Also pin `CompilationMode.VLLM_COMPILE` in them; several fail on platforms where it isn't the default.
- Please rebase (conflicts with #52142 among others) and note AI assistance in the description per AGENTS.md.

@zou3519 does the decorator flag sound right to you?
