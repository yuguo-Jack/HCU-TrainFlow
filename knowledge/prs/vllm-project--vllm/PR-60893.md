# [ROCm][Kernel] Add fused MoE int4_w4a16 config for E=128,N=704 on AMD Radeon AI PRO R9700

[Upstream PR](https://github.com/vllm-project/vllm/pull/60893) · state: open · merged: False

## Original PR description

## Overview

Adds a tuned Triton fused-MoE config for Gemma 4 26B-A4B (128 experts, top-8, `moe_intermediate_size` 704, hidden 2816)
with W4A16 weights (compressed-tensors, int4, group size 32, e.g. `cyankiwi/gemma-4-26B-A4B-it-AWQ-4bit`) on the AMD
Radeon AI PRO R9700 (gfx1201), TP=1:
`vllm/model_executor/layers/fused_moe/configs/E=128,N=704,device_name=AMD_Radeon_R9700,dtype=int4_w4a16.json`.
No code changes.

Not a duplicate: the open #60504 adds Gemma 4 E=128 configs for Instinct and NVIDIA GPUs in BF16/FP8; this PR covers a
different GPU (R9700) and dtype (int4_w4a16), and no file overlaps. #38086 added the existing R9700 configs (FP8, other
shapes).

## Claims

- Without this file vLLM logs `Using default MoE config. Performance might be sub-optimal!` for this model on this GPU.
- Per MoE layer, the tuned entries are 1.05x to 1.46x faster than the default config at M = 1, 2, 3, 4, 8, 12, 16 and
  32, with outputs matching the default config's.
- End to end, plain decoding: -4.2 % ms per output token one request at a time, +13.5 % output tok/s at 4 concurrent
  requests.
- Other GPUs, dtypes and shapes are unaffected: the lookup is keyed by device name, E, N and dtype.

## Validation

**Kernel.** Per MoE layer (`moe_align_block_size` + w13 GEMM + w2 GEMM, top_k=8), 20 launches captured in one HIP graph,
median of 5 replays, default config timed in the same process. One tuning run:

| M | default (us) | tuned (us) | speed-up | configs timed |
|---|---|---|---|---|
| 1 | 131.64 | 106.86 | 1.23x | 20 |
| 2 | 191.19 | 181.51 | 1.05x | 27 |
| 3 | 315.47 | 216.34 | 1.46x | 34 |
| 4 | 423.71 | 327.20 | 1.29x | 34 |
| 8 | 820.50 | 593.52 | 1.38x | 34 |
| 12 | 1037.63 | 793.73 | 1.31x | 41 |
| 16 | 1234.06 | 952.92 | 1.30x | 41 |
| 32 | 1784.07 | 1289.04 | 1.38x | 41 |

Each tuned entry's w13 and w2 outputs are finite and match the default config's on the same inputs
(`torch.allclose`, atol = rtol = 2e-2, bf16).

**End to end.** `vllm/vllm-openai-rocm:v0.30.0` with one local change in both arms: smaller Triton unified-attention
launch tiles for prefill-shaped batches (decode launches unchanged). One R9700, `cyankiwi/gemma-4-26B-A4B-it-AWQ-4bit`,
plain decoding (no speculative decoding), TRITON_ATTN, bf16 KV cache, max-model-len 32768, max-num-seqs 16, prefix
caching on, async scheduling off. Default arm: no config file (server log: `Using default MoE config`). Tuned arm: this
file via `VLLM_TUNED_CONFIG_FOLDER` (server log: `Using configuration from .../E=128,N=704,device_name=AMD_Radeon_R9700,dtype=int4_w4a16.json`).
Workload: a fixed set of 72 chat requests, greedy, two rounds per arm in ABBA order (default, tuned, tuned, default),
a fresh server per run.

| | default | tuned | change |
|---|---|---|---|
| one request at a time, ms per output token (rounds) | 15.151, 15.132 | 14.443, 14.556 | -4.2 % |
| 4 concurrent requests, output tok/s (rounds) | 140.5, 145.4 | 163.3, 161.3 | +13.5 % |

One at a time: ms per output token = 1000 x summed request seconds / completion tokens (request time includes time to
first token); 28,989 completion tokens in each of the four runs. 4 concurrent: output tok/s = completion tokens / wall
seconds; 29,614 and 29,862 completion tokens (default), 29,230 and 29,376 (tuned). We count a difference only if both
round pairs agree in sign and it exceeds each arm's round-to-round spread and the largest default-vs-default round
spread seen on this GPU (2.66 % one at a time, 3.39 % at 4 concurrent); both rows pass.

These runs used an earlier revision of this file that also had entries at M=5 and M=20; this PR drops them (see
Details). The measured runs never looked those entries up: the server logs show `cudagraph_capture_sizes [1, 2, 4, 8,
16, 24, 32]` with FULL_AND_PIECEWISE, and the CUDA graph dispatcher pads every batch of up to 32 tokens to one of those
sizes (cascade attention only rules out FULL), so the MoE saw M in {1, 2, 4, 8, 16, 24, 32} or M > 32, which resolve to
the same entries in both revisions.

Output: every request completed in every run (72 of 72, 0 errors, in all eight runs). In the one-at-a-time runs every run
had the same finish reasons (68 stop, 4 tool calls) and valid tool-call arguments. Comparing replies run against run, each
tuned-vs-default pair had the same agreement as default-vs-default (68 of 72 identical). That comparison includes the
tool-call objects, whose ids vLLM generates at random, so the 4 tool-call replies cannot match in any pair; the content of
those 4 was not compared separately.

## Details

Tuning used a small tuner of ours rather than `benchmarks/kernels/benchmark_moe.py --tune`: an exhaustive grid that
compiled each candidate in the timing process did not finish M=1 in 25 minutes on this GPU, so this one prunes the
search and compiles candidates in parallel worker processes before timing. It seeds from vLLM's default config and the
existing RDNA3.5 (`Radeon_8060S_Graphics`) and MI355X int4_w4a16 tables, then does coordinate descent over
`BLOCK_SIZE_N`, `BLOCK_SIZE_K`, `num_warps`, `waves_per_eu`, `num_stages` and `BLOCK_SIZE_M` (at most 3 rounds). The
winners are small-N tiles (`BLOCK_SIZE_N` 16-32, `BLOCK_SIZE_K` 32-64, 1-2 warps), the same family as the RDNA3.5 table.
Happy to re-run `benchmark_moe.py --tune` instead if reviewers prefer.

Keys 1, 2, 3, 4, 8, 12, 16 and 32 are tuned. Keys 21, 24, 40, 41 and 48-8192 copy exactly what vLLM's default heuristic
picks for this shape on ROCm (`BLOCK_SIZE_M` 32 or 64, `BLOCK_SIZE_N` 64, `BLOCK_SIZE_K` 32), so the small-batch tiles
do not stretch to large batches through the nearest-key lookup. With this key set (ties go to the smaller key, the first
in file order):
- M = 21-28 and M >= 37 keep the default tiling exactly.
- M = 1-18 and 29-36 use the nearest tuned entry; only the M values in the table were timed (M = 5 and 6 use key 4,
  M = 17 and 18 use key 16, M = 29-36 use key 32).
- M = 19 and 20 use key 21 (`BLOCK_SIZE_M` 32 where the default would use 16, same N and K); not timed.

An earlier revision also had M=5 and M=20 entries; they were not timed at Gemma 4's top_k=8, so they are dropped. The
M=5 entry was identical to the M=4 entry, so M = 5 and 6 get the same config as before.

The file is formatted like its neighbours (4-space indent, final newline, as `benchmark_moe.py` writes it).
