# [Feature][Core] Add native SynthID-Text watermarking

[Upstream PR](https://github.com/vllm-project/vllm/pull/58426) · state: open · merged: False

## Original PR description

## Purpose

Add native SynthID-Text watermarking to vLLM's watermarking infrastructure introduced in #53916 / #54053.

This started as an HF-compatible PoC, but after the discussion in this PR the implementation was updated to follow the current vLLM-native direction:

- derive SynthID `g` values at runtime rather than using the older HF sampling-table approach
- reuse vLLM's existing Philox PRF
- use one configured 64-bit master key
- keep the existing flat `WatermarkConfig`
- preserve vLLM's native `-1` partial-context semantics
- expose the algorithm as synthid_text
- require only one new SynthID-specific config field: `depth`

Exact generation/detection compatibility with the Hugging Face or Google implementations is intentionally not a goal. The implementation instead preserves the SynthID algorithmic construction while fitting the native vLLM watermarking architecture.

Related discussion: #53916

## Implementation

### Generation

Adds `SynthIDWatermarker`, integrated through `WatermarkConfig` and `create_watermarker`.

SynthID-Text reweights the categorical distribution using binary tournament-sampling layers and then delegates token selection to vLLM's normal stochastic sampler.

For each context/candidate-token pair, `PhiloxPRF.uint32()` provides a 32-bit word whose bits supply up to 32 tournament layers. `depth` defaults to 32 and accepts any positive value. Depths above 32 use additional Philox streams.

The reference implementation performs the tournament in FP32. On CUDA with the native Philox PRF, a fused Triton implementation processes tournament layers in four-bit chunks while preserving the same distribution. CPU/reference-vs-accelerator parity is covered by tests across depths spanning Philox stream boundaries.

Existing context deduplication and native -1 partial-context behavior are preserved.

### Philox

`PhiloxPRF` now exposes the raw uint32 output in addition to the existing uniform-float interface.

`uint32()` also accepts an internal `stream: int` identifier. The stream is split into two uint32 words before entering the compiled Philox implementation. Stream 0 preserves the existing Philox PRF mapping, while SynthID-Text uses its dedicated stream domain and additional low-word stream indices for depths above 32.

Compatibility vectors, stream determinism, CPU/accelerator parity, and stream-0 backward compatibility are covered by tests.

### Speculative decoding

SynthID-Text does not currently support speculative decoding.

Unlike Gumbel watermarking, the existing speculative-decoding recovery path cannot apply SynthID-Text to rejected or bonus tokens, so configuration validation rejects SynthID-Text when speculative decoding is enabled, including with `allow_target_only_watermarking=true`.

Full speculative-decoding support can be added separately.

### Detection

Adds `SynthIDWatermarkDetector`.

The detector recomputes the same Philox-derived `g` values for the observed token sequence and reports the unweighted mean score and a one-sided p-value under an ideal-PRF `Binomial(num_scored_tokens * depth, 0.5)` null.

Repeated contexts are deduplicated by default so repeated use of the same keyed random vector is not treated as independent evidence.

This is intentionally a simple first detector and does not attempt to reproduce Google's weighted-mean or trained Bayesian detector.

## Configuration

Example:

```bash
vllm serve MODEL \
  --watermark-config \
  '{"algorithm":"synthid_text","key":42,"context_width":4,"depth":32}'
```

`key` uses the existing 64-bit watermark master key. `context_width` controls the prior token context used by the PRF. `depth` controls the number of binary tournament reweighting layers and must be positive. Depths above 32 require additional Philox evaluations. The current PRF is `philox`.

## Performance and evaluation

GPU evaluation was performed on an NVIDIA Quadro RTX 6000 using Qwen models.

For `bench serve` with Qwen3-0.6B FP16, 1,000 requests, fixed 1,024-token inputs / 128-token outputs, max concurrency 32, and temperature 1.0:

- Before the fused CUDA implementation due to @simon-veitner-redhat, SynthID-Text reduced output throughput from 453.2 to 332.5 tok/s (-26.6%) and increased mean TPOT from 66.1 ms to 91.2 ms (+38.0%).
- With the Triton tournament kernel, output throughput was 455.0 tok/s without watermarking and 449.9 tok/s with SynthID-Text (-1.1%). Mean TPOT increased from 65.9 ms to 66.7 ms (+1.2%).
- Gumbel showed effectively no measurable overhead in the earlier comparison.

The relative Triton overhead depends on model, hardware, and batch size; separate H200 measurements madeby @simon-veitner-redhat are included in the review discussion.

A 300-example GSM8K run produced detection rates of 66.3% for SynthID-Text output, 1.3% for control output, and 2.0% with the wrong key. The observed accuracy difference between control and SynthID-Text was not statistically significant in the paired comparison (McNemar p=0.284).

A separate qualitative sanity check with Qwen3-4B across ordinary factual, explanatory, reasoning, summarization, email, and creative prompts did not show an obvious systematic generation-quality degradation.

## Testing

Coverage includes configuration/factory integration, Philox raw-word compatibility and stream behavior, CPU/accelerator parity, independent SynthID probability reweighting calculations, depths crossing 32-bit stream boundaries, FP32 tournament behavior, masked-token preservation, detection score/p-value calculations, Gumbel/SynthID stream-domain separation, context handling, random-sampler integration, skip masks, speculative-decoding rejection, deterministic golden fixtures, and warning behavior.

The focused watermarking tests pass locally on CUDA. The fused Triton path is tested against the CPU/reference implementation at depths 1, 32, and 65, including peaked distributions and masked logits.

- sebfelix · comment · 2026-09-25T06:13:38Z · [source](https://github.com/vllm-project/vllm/pull/58426#issuecomment-5827770085)

@kpratik41  Yes, I think the draft/target separation from #56122 should be reusable for SynthID, and Algorithm 6 looks like the right approach. I would probably do it as a follow-up rather than blow up this PR, though.

I looked through the current speculative watermarking path and there are basically two levels to this:

* The `SupportsSpeculativeDecoding` abstraction itself is perfectly reusable: SynthID could provide independent draft and target watermarkers, with draft tokens using the draft stream and rejection-recovery/bonus tokens using the target stream while keeping the ordinary unwatermarked P/Q acceptance test.
* The current implementation below that abstraction is more Gumbel-specific in its current state. `DraftWatermarker` currently assumes the watermarker can sample without the ordinary random sampler, whereas SynthID reweights logits and then needs normal stochastic sampling. More importantly, rejection-recovery and bonus sampling currently resolve a Philox Gumbel key and call `philox_gumbel_block_argmax` directly in the rejection kernel.

The second part is the main blocker to simply opting SynthID into `SupportsSpeculativeDecoding`. SynthID needs to reweight the residual distribution before sampling, including vocabulary-wide probability-mass reductions for each watermark depth, so it cannot directly substitute for the current block-local Gumbel resampling path.

So I think supporting it is feasible and #56122 gives us the correct high-level infrastructure, but it likely needs some generalization of the speculative recovery path rather than just wiring the current `SynthIDWatermarker` into it.

There is also a key/config question to settle: SynthID's existing keys: `list[int]` are depth keys, so we need to define how independent draft and target SynthID key streams are derived. More generally, the basic SynthID config question is still open as well: vLLM currently exposes a single `key: int` in the watermarking seam, while SynthID natively expects a `list[int]` of depth keys. We first need to settle thattogether with the other SynthID config/reference-semantics questions, but supporting speculative decoding seems like the obvious next step

From what I understand:
- the HF implementation creates a lookup table for the g-function outputs, which is fast but has a couple disadvantages around CPU/GPU parity and repeated outputs over vocab (16 bits that roll over the vocab so every ~65k tokens get repeated g values) , as well as additional config fields we'd need for the size of the lookup table etc

I think the most sensible here is to follow the google reference path, but we can add a few optimizations that should make it roughly equal in cost as well as align more with what we already have for watermarking:
- we can use the already existing Philox implementation with a new method to return the full 32 bit word: this way a single invocation covers `depth=32` of tournament sampling and cost doesn't scale as much with depth. This would make the implementation very similar to the already existing gumbel implementation in terms of performance impact
- we can prune on top-p/top-k in the fused kernel, so we only need to hash <O(100s) (for reasonable top-k/top-p settings) of tokens depending on the sampling params

An additional point: we do not need to match either HF/Google references exactly, i.e we do not need generation/detection compatibility between them. We should only care about maintaining the algorithmic guarantees

Hi @sebfelix, I tested head `d0799c8986` on H200 and found the bugs below. Each has a short trigger. The fixes are on [synthid-review-fixes](https://github.com/simon-veitner-redhat/vllm/tree/synthid-review-fixes) as two commits on top of `d0799c8986`: the bug fixes in `5588ff10d1` and an optional Triton kernel in `9d7e5b6a7c`. Line numbers are at `d0799c8986`, and each "Fix" line cites `5588ff10d1`.

**C1. Every SynthID request on CUDA kills the engine.**
`prfs/philox.py:66` computes `stream >> 32` inside `_philox_uint32`, which line 131 compiles with `dynamic=True`. Inductor lowers the shift through float32, and the XOR that follows fails to compile for every key and stream.

```python
ctx = torch.zeros(2, 4, dtype=torch.int64, device="cuda")
PhiloxPRF(42).uint32(ctx, torch.arange(1024, device="cuda"), stream=0)
# InductorError: IncompatibleTypeErrorImpl('invalid operands of type triton.language.float32 and triton.language.float32')
```

`LLM.generate` raises `EngineDeadError`, and `test_prf.py::test_philox_accelerator_matches_cpu` fails all 24 cases on CUDA.
Fix: split the stream into two uint32 words outside the compiled function, as the key already is (`philox.py:179`).

**C2. SynthID with spec decode passes config validation, then crashes at startup.**
`config/vllm.py:1357-1376` accepts it when `allow_target_only_watermarking=true`. `model_runner.py:488-495` then calls `speculative_target_watermark_key`, and `_philox_key` (`spec_decode.py:182-191`) raises for any non-Gumbel watermarker. `RejectionSampler` never applies SynthID either, so the docs claim at `watermarking.md:106-109` (SynthID on recovery and bonus tokens) is false.

```python
cfg = WatermarkConfig(key=42, algorithm="synthid_text", allow_target_only_watermarking=True)
speculative_target_watermark_key(cfg)
# NotImplementedError: In-kernel watermarked recovery supports only the Philox PRF GumbelWatermarker
```

Fix: reject SynthID with spec decode in config (`config/vllm.py:1335`) and correct the docs (`watermarking.md:107`).

**C3. The tournament runs in bf16 on the T=1.0 path, so a row's output depends on the rest of the batch.**
`sampler.py:238` skips the fp32 copy when no row in the batch needs logits processing, and `synthid.py:78` runs softmax in the input dtype. The same request gets a bf16 or an fp32 tournament depending on its batch neighbours.

```python
logits = torch.randn(4, 151936) * 2.5; logits[:, :20] += torch.linspace(12, 4, 20)
ctx, wm = torch.randint(0, 150000, (4, 4)), SynthIDWatermarker(42, 4, 32)
a = wm.watermark_logits(logits.bfloat16(), ctx).double().softmax(1)
b = wm.watermark_logits(logits.bfloat16().float(), ctx).double().softmax(1)
(a - b).abs().sum(1) / 2   # TV per row: up to 0.013 over a few runs
```

Against an fp64 reference, the bf16 path reaches TV 0.06 to 0.15.
Fix: softmax in fp32 (`synthid.py:81`).

**C4. SynthID and Gumbel share Philox stream 0, so each detector flags the other's text.**
`synthid.py:81` and `:185` use stream `start // 32`, and stream 0 yields the same Philox words Gumbel-max uses.

```python
wm, toks = GumbelWatermarker(42, 4), []
for _ in range(400):
    ctx = torch.tensor([([-1] * 4 + toks)[-4:]])
    toks.append(int(wm.sample(torch.randn(1, 4096) * 2, ctx).token_ids))
SynthIDWatermarkDetector(42, 4, 32).detect(toks)   # p=8.1e-204, flagged (key 43: p=0.94)
```

The reverse holds too: SynthID text gets p 1e-57 to 6e-51 from the Gumbel detector.
Fix: a "SYNT" constant in the stream's high word (`synthid.py:21`).

**C5. Startup OOM at `gpu_memory_utilization=0.95`.**
The profile run (`model_runner.py:954-965`) uses greedy dummy rows, so the [B, V] tournament temporaries (4.5 to 5.3 GiB at B=1024) are never budgeted. Qwen2.5-0.5B with `max_num_seqs=1024`, util 0.95, T=0.8: `torch.OutOfMemoryError` in `_update_probs` at startup. Watermarking off and Gumbel both start fine.
Fix: profile with watermarked dummy rows (`model_runner.py:966`). With it, the same setup starts and finishes at util 0.95.

**C6. `finfo.min` breaks the sampling mask: the whole vocab is reported kept.**
`synthid.py:97-101` replaces -inf with `finfo.min`, and `_compact_sampling_mask_kernel` keeps any finite token.

```python
logits = torch.randn(1, 1000); logits[:, 50:] = float("-inf")   # top_k=50
out = SynthIDWatermarker(42, 4, 32).watermark_logits(logits, torch.randint(0, 1000, (1, 4)))
torch.isfinite(out).sum()   # 1000, was 50
```

End to end with `return_sampling_mask=True` and top_k=50, every mask has 151936 ids.
Fix: restore -inf where the input was -inf (`synthid.py:102`).

**C7 (behaviour). Response openings lose diversity at depth 32.**
For the first `context_width` tokens the context holds only -1 padding (`gpu_sampler.py:175`), so every response starts from the same g-table. Qwen2.5-0.5B, 8 chat prompts, n=32, T=1.0, distinct first tokens per prompt: off `[11, 18, 9, 3, 8, 13, 8, 12]`, SynthID `[1, 14, 1, 1, 1, 1, 2, 1]`.
Suggestion, not in the fix branch: skip the padded opening contexts by default (`deduplicate_contexts='all'` already does) and have the detector skip them too.

**C8. `deduplicate_contexts="none"` causes repetition loops, but only Gumbel gets the warning.**
`config/watermarking.py:78-82` warns only for `gumbel` and `dual_key_gumbel`. `WatermarkConfig(key=42, algorithm="synthid_text", deduplicate_contexts="none")` logs nothing. Qwen2.5-0.5B, T=0.7, 400 tokens: 8/64 sequences end in loops, 0/64 with dedup.
Fix: warn for all algorithms (`config/watermarking.py:78`).

**F3. Processed logprobs expose the g-bits.**
`synthid.py:121` returns the watermarked logits, while Gumbel returns the unmodified ones. A client that also sends `watermarking=false` for the same context can read 32 g-bits per token from p_wm / p.

```python
s = SynthIDWatermarker(42, 4, 32).sample(torch.randn(1, 1000), torch.randint(0, 1000, (1, 4)), lambda x: x.argmax(-1))
# s.logits is the watermarked distribution: max |log p_wm - log p| is 14 to 23
```

Fix: return the unwatermarked logits (`synthid.py:124`).
