# [Bugfix] Preserve timed-trace chunk identity across benchmark runs

[Upstream PR](https://github.com/vllm-project/vllm/pull/60901) · state: open · merged: False

## Original PR description

## Overview

Generate timed-trace tokens from the full SHA-256 chunk-identity digest, independently of Python's randomized string hash and requested expansion length.

## Claims

- Identical trace chunks produce identical tokens across processes with different `PYTHONHASHSEED` values.
- A partial chunk matches the prefix of its full expansion.
- The reviewer's distinct trace IDs `69235` and `95303` no longer collapse to identical token chunks through a truncated 32-bit seed.
- Identity-and-size caching and request lengths remain unchanged.

## Validation

Three regressions exercise the real dataset argument parser and public `get_samples` API with a local fast tokenizer, five trace rows and two Python subprocesses using different hash salts. The vocabulary contains IDs 0..127, with special token 0 excluded.

## Details

Originally, `hash(f"{h}:{expanded_size}")` changed across interpreters and changed with partial expansion size. The initial PR used SHA-256 of the chunk identity but retained only four bytes. The reviewer supplied two IDs with the same four-byte digest prefix, producing an unintended shared benchmark prompt. Retain all digest bytes for Python's integer RNG seed while excluding expansion size.

Updated the Rust module note to describe the actual stable, client-specific seed schemes; no Rust algorithm changed. The pre-existing CLI seed-mapping observation remains outside this fix.

Synthetic token IDs change relative to historical runs and the original PR head. Old/new throughput runs must not be described as using identical prompt tokens. The correction removes this digest-truncation collision, not every possible coincidence between finite random token sequences. No inference behavior, model-quality or throughput improvement is claimed.

Duplicate searches for `TimedTrace` and timed-trace seed fixes found no overlapping PR. This updates the existing PR rather than opening another.

AI assistance was used to investigate, implement and test the change. Human review and a personal test rerun were confirmed before publication.

[P2] Avoid seed truncation collapsing distinct trace chunks

The first four SHA-256 bytes collide for distinct hash IDs `69235` and `95303`: both become seed `3240015334`. I reproduced this through the real dataset parser/get_samples path with two rows containing those respective IDs, 16-token chunks, and a fixed vocabulary of IDs 0..127 excluding special ID 0. Both rows produced exactly `[60, 30, 70, 18, 91, 118, 14, 79, 19, 126, 115, 108, 24, 35, 78, 122]`. This introduces a shared token prefix that the distinct trace hashes did not represent, affecting cache-replay fidelity. Please retain the full digest (or substantially more than 32 bits) for the RNG seed and cover this pair through the public sampling API, while continuing to exclude expansion size from seed derivation.
