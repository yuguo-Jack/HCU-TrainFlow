# [Bugfix] Keep AWQ and GPTQ linear layers batch invariant

[Upstream PR](https://github.com/vllm-project/vllm/pull/60479) · state: open · merged: False

## Original PR description



## Overview
Fixes #59086

With `VLLM_BATCH_INVARIANT=1`, two quantized linear paths still produce batch-dependent results:

- `AutoGPTQLinearMethod` always runs the Marlin GEMM. Marlin picks its tiling and K-split from the number of tokens, so the reduction order changes with the batch size.
- `AutoAWQLinearMethod` dequantizes and then calls `torch.matmul`, relying on the batch-invariant override of `aten.matmul`. That override does not reach matmuls inside `torch.compile`d regions, so the cuBLAS kernel runs.

This PR makes both paths use `matmul_batch_invariant` directly. For GPTQ, batch-invariant mode skips the Marlin kernel selection and repacking, keeps the checkpoint layout in memory, and unpacks the weight in `apply()`.

## Claims

- On `main`, `tests/v1/determinism/test_batch_invariance.py` fails for `Qwen/Qwen2.5-7B-Instruct-GPTQ-Int4` (14 of 22 ids) and `Qwen/Qwen3-8B-AWQ` (10 of 22 ids). With this PR all 22 ids pass for both models.
- Accuracy is unchanged: `lm_eval` gsm8k on the batch-invariant path matches the Marlin path within noise, and the top-1 tokens of the two GPTQ paths agree on a fixed prompt set.
- Without `VLLM_BATCH_INVARIANT` nothing changes: the same Marlin kernels are selected.
- Throughput in batch-invariant mode is lower than on `main` (numbers below): the GPTQ weight is dequantized on every forward, and both models now use the batch-invariant Triton matmul instead of Marlin / cuBLAS.
- New unit test checks the GPTQ unpack against vLLM's reference packer bit for bit.

## Details

**Root cause.** `vllm/model_executor/determinism/batch_invariant.py` overrides `aten::mm`/`aten::matmul` through `torch.library` and exposes `matmul_batch_invariant` for callers; linear methods that run their own kernels have to opt in. `AutoGPTQLinearMethod` never did: it always builds a Marlin `MPLinearKernel`. `AutoAWQLinearMethod` already had a batch-invariant branch, but it relied on the `torch.matmul` override, and that override is not reached from the compiled forward: a tripwire placed in `mm_batch_invariant` never fired from this path on `main` while the determinism test failed, whereas the unquantized LM head (which calls the helper directly) did reach it. The same pattern is why `UnquantizedLinearMethod` calls `linear_batch_invariant` explicitly.
The AWQ branch was made batch invariant in #38670 (April, tested on an RTX 3090) and `Qwen/Qwen3-8B-AWQ` is on the tested list in `docs/features/batch_invariance.md` (#40034); on today's `main` the suite fails again on the A10 (also SM 8.6), so this path regressed since.

**Change.**
- `auto_awq.py`: the batch-invariant branch calls `matmul_batch_invariant` after `awq_dequantize`.
- `auto_gptq.py`: with `VLLM_BATCH_INVARIANT=1`, `AutoGPTQLinearMethod` skips `verify_marlin_supported` / `choose_mp_linear_kernel`, leaves `qweight`/`scales`/`qzeros` in the checkpoint layout, and `apply()` unpacks the weight (`(q - bias) * scale` in the scales dtype, the same arithmetic as the Marlin dequantization) and calls `matmul_batch_invariant`. Without the flag the code path is unchanged.
- `tests/kernels/quantization/test_gptq.py`: `_dequantize_gptq_weight` is compared bit for bit against `gptq_quantize_weights` + `gptq_pack` for 4/8 bit, group sizes -1/32/128, fp16/bf16.

**Trade-offs and limitations.**
- The GPTQ weight is unpacked on every forward in batch-invariant mode, and both models now run the batch-invariant Triton matmul instead of Marlin / cuBLAS. On the A10 this costs throughput in batch-invariant mode (blocks in section 6): the decode-heavy GPTQ benchmark takes about 2.5x longer than `main`'s non-invariant Marlin path, the prefill-heavy one about 1.4x, and the AWQ benchmarks about 1.2x. Keeping a dequantized copy would be faster but would need the memory of the unquantized model, which is usually why a GPTQ checkpoint is used. A fused batch-invariant W4A16 Triton kernel would remove the cost; I kept that out of this PR.
- Only symmetric GPTQ without act-order is covered, which is what `AutoGPTQLinearMethod` supports today (`desc_act=True` is rejected at config time).
- `AutoGPTQMoEMethod` (GPTQ MoE experts) still uses Marlin and is not batch invariant; so are other Marlin users such as the compressed-tensors wNa16 scheme. This PR covers the two dense paths that were tested.
