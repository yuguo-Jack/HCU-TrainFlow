# [Bugfix][Tool Parser] Recover when a stray <tool_call> opens a phantom call in the glm47 parser

[Upstream PR](https://github.com/vllm-project/vllm/pull/60842) · state: open · merged: False

## Original PR description



## Overview

Fixes #60703: a stray `<tool_call>` special token emitted mid-prose made the glm47 streaming parser silently swallow the rest of the stream — including the model's genuine tool call — ending with HTTP 200, `finish_reason="stop"`, and no `tool_calls`.

## Claims

- A genuine tool call that follows a stray `<tool_call>` opener now parses correctly, streaming and non-streaming, from both the CONTENT and REASONING entry states.
- A stray `<tool_call>` inside an `<arg_value>` still round-trips verbatim as argument data (deliberately unchanged; regression-tested).
- Clean tool calls are unaffected; the change is one transition in `glm47_moe_config` (TOOL_NAME previously dead-ended on a second opener).

## Validation

- The issue's CPU repro, before → after on this branch: `content: 'Fetching the page. I will issue a '` / `tool calls: []` → real call parsed with correct name and arguments.
- New regression tests in `tests/parser/engine/test_glm47_moe.py`: prose-stray (non-streaming + streaming), reasoning-entry stray, and the arg-value round-trip guard.
- Suites at this head: `tests/parser/engine/test_glm47_moe.py`, `tests/parser/engine/test_parser_engine.py`, `tests/parser/engine/test_ling3.py` (Ling3 builds on `glm47_moe_config`, so the transition lands there too), `tests/tool_parsers/test_glm47_moe_tool_parser.py` — 163 passed.
- A chunk-boundary fuzz harness (the issue's scenario plus 10 variants — multibyte/CJK/emoji boundaries, adjacent tags, multi-call — replayed through `DelegatingParser.parse_delta` with real `DecodeStream` detokenization under 205 chunkings each, 1–4 tokens per delta): 409 failing chunkings on unpatched main → 0 on this branch.
- Test commands: `python -m pytest tests/parser/engine/test_glm47_moe.py tests/parser/engine/test_parser_engine.py tests/parser/engine/test_ling3.py tests/tool_parsers/test_glm47_moe_tool_parser.py` — 164 passed (incl. the 5 new regression tests); `pre-commit run --files vllm/parser/glm47_moe.py tests/parser/engine/test_glm47_moe.py` — all hooks pass.
- Red-green: on the parent commit, exactly the 3 recovery tests + the phantom-drop pin fail while the arg-value round-trip guard stays green.
- Independently verified by @he-yufeng on the issue (5-probe matrix on main @ 4274ae9, full `tests/parser/` tree: 6312 passed + 384 subtests, two pre-existing failures identical on unpatched main).
- The fix has also been running in the production deployment where the bug was found (nightly multi-tool agent workload; the original failure signature has not recurred).

## Details

Root cause: `glm47_moe_config` gave TOOL_NAME only `ARG_KEY_START` and `TOOL_END` transitions. A stray opener put the engine in TOOL_NAME, where the genuine call's `TOOL_START` fell through to `_emit_for_state` (appending into the phantom's name buffer), and at close `_handle_tool_end`/`_emit_name_delta` dropped everything because the prose "name" fails `_accept_tool_name` under `validate_tool_names=True` — with no content fallback.

The new `(TOOL_NAME, TOOL_START)` transition closes the phantom (invalid names are already discarded) and starts a fresh call — the same recovery idiom #59928 applies to the qwen3 parser for this bug class.

Overlap note: #60813, filed a few hours before this PR, implements the same transition proposed in #60703 (this PR's duplicate-check predated it); see https://github.com/vllm-project/vllm/issues/60703#issuecomment-6122418622 for the comparison. #59928 fixes this bug class for `vllm/parser/qwen3.py` only.

Scope and known limitations:

- `ling3.py` reuses `glm47_moe_config`, so the recovery applies there as well (its suite passes).
- A lone stray opener with no genuine call after it still truncates silently — recovering that needs re-emitting a dropped phantom's accumulated text as content, an engine-level change that would benefit the whole #58227/#60703 class and is left as follow-up.
- Theoretical edge: a phantom whose accumulated "name" exactly matches an advertised tool (no whitespace, perfect match before the next opener) would emit an empty-args call; prose cannot realistically satisfy this.

Local runs on this head (CPU only, macOS):

- tests/parser/engine/test_glm47_moe.py: 18 passed, including the 4 new ones.
- Red-green: with vllm/parser/glm47_moe.py reverted to the parent commit, exactly the 3 recovery tests fail while the arg-value round-trip guard stays green. Good pin design.
- Neighbors: test_ling3.py + test_parser_engine.py + test_glm47_moe_tool_parser.py, 145 passed.
- Full tests/parser/ tree (cohere excluded locally, it needs cohere_melody): 6317 passed + 384 subtests.

Two probes beyond the suite, same head. With a production-shaped request (tools=[get_weather], so validate_tool_names actually bites): a single stray and two consecutive strays both end with the phantoms dropped and only the real get_weather call parsed, arguments intact. That matches the matrix from the issue thread.

One non-blocking test-tightness note: the new tests build mock_request with tools=[], and _is_valid_tool_name accepts everything when the parser holds no tools, so in that configuration the phantom is actually emitted as an extra call with empty args ahead of the real one. The assertions on tool_calls[-1] stay green either way, so the suite pins the recovery but not the phantom drop. Serving only reaches this parser when the request carries a tools list, so there is no user-facing hole; but one case with a populated tools list asserting len(tool_calls) == 1 would lock the drop in for free.
