# [Bugfix][LoRA][MoE] Derive the fused MoE LoRA input row from the input shape

[Upstream PR](https://github.com/vllm-project/vllm/pull/61164) · state: open · merged: False

## Original PR description



## Overview

The fused MoE LoRA kernels pick the input row of a `(token, top_k)` route with `token_mapping_factor = 1 if mul_routed_weight else top_k`. This ties "apply the routing weight" to "the input has one row per route". An unweighted w2 delta therefore reads the wrong activation rows. This PR derives the row granularity from the input shape instead.

## Claims

- `fused_moe_lora` computes a correct w2 delta when `mul_routed_weight=False` (needed by MoEs that apply the routing weight after GEMM2).
- No behaviour change for existing callers: ambiguous shapes keep the old rule.

## Validation

GB300, main vs this PR:

```bash
pytest tests/lora/test_fused_moe_lora_kernel.py
```

| | main | this PR |
|---|---|---|
| `test_fused_moe_lora_kernel.py` | 413 passed | 415 passed (2 new) |

The new `mul_routed_weight=False` case fails on main's kernel (max rel diff 0.31, 0.02 allowed).

On a MoE model that applies the routing weight after a per-expert post-GEMM2 norm, the expert-LoRA output vs an adapter-merged reference improved from mean |Δlogp| 0.76 to 0.22 (noise floor 0.12–0.17).

## Details

- No in-tree caller passes an unweighted w2 today (`add_lora_w2` hard-codes `mul_routed_weight=True`), so the bug is latent. It surfaces for any MoE that finalizes after GEMM2 with LoRA.
- `_token_mapping_factor`: an input with one row per token (w13) gives `top_k`, otherwise one row per route (w2) gives 1. Same result as before for all existing callers; shape-only, no device sync.
- No open PR addresses this (searched "fused_moe_lora token_mapping_factor", "fused moe lora mul_routed_weight w2").
- AI assistance (Claude Code) was used; I reviewed every changed line and the test results.
