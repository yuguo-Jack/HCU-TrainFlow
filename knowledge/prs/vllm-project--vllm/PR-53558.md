## Purpose
Pick from https://github.com/vllm-project/vllm/pull/42309 to follow up kv cache config builder implementation. 

Add a pluggable KVCacheConfigBuilder so platforms or models can override KV cache planning end-to-end. Resolution order: platform override > model declaration > default. Default builder forwards to existing get_kv_cache_configs, so behavior is unchanged today.

- andakai · comment · 2026-09-22T07:43:09Z · [source](https://github.com/vllm-project/vllm/pull/53558#issuecomment-5772902453)

Refactoring the previous `get_kv_cache_configs()` into smaller APIs seems like a good direction. I wonder if the public interface could be simplified further.

My understanding is that most of the current methods can be put into common core codes. Layout validation, memory admission checks, `num_gpu_blocks_override`, auto-fit, null-block reservation, and cross-rank alignment could remain internal to Core. 

Profiling also does not seem to require a separate API. It already knows the min block count. For final allocation, the current GPU backing size is linear in `num_blocks`, so Core can ask the placement hook to describe a hypothetical one-block pool, without allocating GPU memory, and use that backing size to derive the final block count from `available_memory`. This also removes the need for `get_pool_bytes_per_block()`. 

The public interface could therefore be reduced to `get_kv_cache_configs()` as the full-flow escape hatch, plus `get_kv_cache_groups()` for logical grouping and `get_kv_cache_config_from_groups(..., num_blocks)` for physical placement. Platforms with a non-linear capacity model could still override the top-level flow.

I made a small prototype here: https://github.com/andakai/vllm/compare/refactor/pr53558-main-baseline...refactor/pr53558-public-api-simplification. I may have missed some platform-specific requirements and whether this smaller interface makes sense.
