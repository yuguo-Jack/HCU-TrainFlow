# [Perf][SM120][MLA] Use compact FP8 KV rows for NoPE models

[Upstream PR](https://github.com/vllm-project/vllm/pull/58305) · state: open · merged: False

## Original PR description

## Purpose

Follow-up to merged #55277: use compact 528-byte `fp8_ds_mla` rows for native NoPE on the FlashInfer SM120 backend. Rebased onto upstream main `e6674262f1`. Only tests conflicted: #55528 made the MLA KV-spec test's fake layer carry `attn_backend`, and the HiSparse test helper gained `max_union_rows`; both were resolved by keeping both sides. The two commits are now `aab1e922fa` and `e879b2ef44` (head), and the branch merges cleanly into current main.

The row contains 512 FP8 latent bytes and four FP32 group scales. There is no RoPE payload. A single backend-owned row-size method supplies both the KV spec and early HiSparse registration. On SM120, compact selection depends solely on `kv_lora_rank=512` and `qk_rope_head_dim=0`, independent of model name, connector, or offloading configuration. Other backend layouts are unchanged; real RoPE64 `fp8_ds_mla` retains 656-byte rows. No new dtype or CLI option is added.

The writer accepts NoPE 528/656, preserves legacy zero-tail behavior for 656, and rejects RoPE64 with 528. It distinguishes logical row width from physical stride. The fixed 576-dimensional gather rejects compact input. HiSparse uses actual row widths for byte movement and rejects incompatible shared-staging layouts.

No connector changes, layout negotiation, or old-cache migration are added. Local prefix caching remains supported. External connectors were not tested end to end.

Duplicate-work check: #53969/#55778/#55543 use padded compatibility layouts; #55219/#57169 address broader paging/stride plumbing, not this compact writer/spec change. The community B12X GLM_NEXT path already uses the same 528-byte encoding; that is a useful precedent, not the FlashInfer backend wiring implemented here. Reference: local-inference-lab/vllm `cff8aebfeb73de96c97b4c5a0550c5a49f27451c`, `b12x_mla_sparse.py`. FlashInfer compact-row support was merged in flashinfer-ai/flashinfer#5075.

## Test Result

### Revalidation after the rebase onto `e6674262f1` (head `e879b2ef44`)

Run on 4x RTX PRO 6000 Blackwell with FlashInfer built from main (includes flashinfer-ai/flashinfer#5075) and vLLM's CUDA extension rebuilt from a tree containing this branch:

- CUDA writer (`test_cache.py -k concat_and_cache_ds_mla`): **9 passed, 3 skipped**. Fixed-layout gather (`test_cp_gather_fp8.py`): **18 passed**. KV-spec tests (`test_mla_backends.py -k kv_cache_spec`): **10 passed**.
- `tests/v1/attention/test_sparse_mla_backends.py`: **119 passed**, 7 failed. All 7 fail identically on `e6674262f1` without this PR: `test_sparse_backend_prefill_correctness[*-auto-masked_mha*]` for deepseek_hd192_v128, glm5_hd256_v256 and glm53_flash_nope_hd256_v256, and `test_hisparse_speculative_rows_resolve_host_misses_consistently[long_mtp]`.
- GLM-5.3-Flash-NVFP4, TP4, text-only, context 65536, max sequences 32, batched tokens 8192, `--kv-cache-dtype fp8`, default FlashInfer autotune (no skip-ops workaround). GSM8K through the chat template (1,319 problems, flexible-extract, concurrency 32):

| GSM8K (chat, flexible-extract) | 0.973 | 0.972 |

Both evaluations ran on the same integration tree with unrelated changes for other models; one run each.

Compared with #55277 on the same hardware and serving configuration:

| Metric | #55277 | Compact |
|---|---:|---:|
| Encoded bytes per KV row | 656 | 528 (**−19.51%**) |

The benefit is more KV capacity within the same memory budget, not a throughput claim or a 19.51% reduction in total GPU allocation. Capacity is engine-reported, not saturation-tested; the validation runs used dirty source trees with differing build metadata.
