# [Bugfix] Accept GPU/MIG UUIDs in CUDA_VISIBLE_DEVICES when NVML is unavailable

[Upstream PR](https://github.com/vllm-project/vllm/pull/46132) · state: open · merged: False

## Original PR description

## Purpose

`Platform.device_id_to_physical_device_id()` passes each `CUDA_VISIBLE_DEVICES` entry to `device_control_id_to_physical_device_id()`. CUDA accepts device **UUIDs** there as well as integer indices: full-GPU (`GPU-...`) and MIG instance (`MIG-...`) UUIDs.

Since #45026, `NvmlCudaPlatform` resolves a UUID through NVML, so the NVML path no longer crashes on one. The base `Platform` implementation, used by `NonNvmlCudaPlatform` when NVML is unavailable, still calls `int()` on the entry and raises:

```
ValueError: Non-integer device ID 'MIG-4c60d78c-506f-5593-938d-a136eaa1fa52' is not supported by cuda
```

So pinning vLLM to a device by UUID still fails on the no-NVML path. That path is used when `pynvml` can't be loaded, e.g. in containers without the NVML library mounted. Before #45026, every CUDA user hit this crash: vLLM 0.10.0 on an A100 MIG 2g.10gb slice died at the `int()` call. On the `serve` path it surfaced as a misleading `Model architectures [...] failed to be inspected` error.

## Fix

When `device_control_id_to_physical_device_id()` rejects an entry with `ValueError`, fall back to the logical `device_id`. CUDA remaps the listed visible devices to logical ids in order, so the caller's `device_id` is already the correct index into the visible set. Integer-index behaviour is unchanged, and the NVML path is unaffected because it doesn't raise.

## Test Plan

`tests/test_platform_device_id.py` uses a stub platform that inherits the base implementation (the no-NVML path). It covers the integer path (unchanged), a single MIG UUID, a list of GPU UUIDs, and the empty-env case.

## Test Result

- The new tests pass on this branch (CPU-only, no GPU needed). On unpatched main, the two UUID tests fail with the `ValueError` above.
- The branch merges cleanly with current main, and the code it touches is unchanged on main since it was opened.

Not addressed here: on the NVML path, a MIG UUID is resolved with `nvmlDeviceGetHandleByUUID` followed by `nvmlDeviceGetIndex`. I haven't verified what index NVML reports for a MIG instance handle, so that path is left as #45026 implemented it.

Relates to #20939, #41848, #32569 and #45026.

Correct fix for the no-NVML UUID path.

**Problem is clear**: `CUDA_VISIBLE_DEVICES` accepts UUIDs (both `GPU-...` and `MIG-...`), but `device_control_id_to_physical_device_id()` calls `int()` on them, throwing `ValueError`.

**Fix is right**

When NVML is unavailable (e.g. containers without the NVML library), catching `ValueError` and returning the caller's logical `device_id` is correct — CUDA remaps visible devices to logical indices 0, 1, 2, ... in order, so `device_id` is already the correct index.

The stub-platform test is a good approach — no GPU needed to verify the logic. Tests cover the unchanged integer path, single MIG UUID, multiple GPU UUIDs, and empty env.

**Note on #45026**

Good that you left the NVML path as-is. The NVML path resolves the UUID via `nvmlDeviceGetHandleByUUID` → `nvmlDeviceGetIndex`, which gives the correct physical index. That's a different code path and out of scope here.

No blockers.
