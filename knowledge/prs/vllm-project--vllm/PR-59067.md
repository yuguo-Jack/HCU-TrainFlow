# [Bugfix][MRV2][LoRA] Fix LoRA metadata binding for eager KV-sharing fast prefill

[Upstream PR](https://github.com/vllm-project/vllm/pull/59067) · state: open · merged: False

## Original PR description



## Purpose

Fix an MRV2 KV-sharing fast-prefill correctness bug when a scheduled batch
contains both LoRA and non-LoRA requests.

The fast-prefill path compacts the model input to `logits_indices_padded`, but
the LoRA Punica metadata was still built for the original full token batch.
The existing kernel call then used the first `x.size(0)` entries of the full
mapping while retaining the full-batch sorted indices and token counts.  For a
base request followed by a LoRA request, this can route the compact rows to the
wrong adapter and can cause an out-of-bounds access in the LoRA shrink kernel.

This PR is limited to eager execution. It selects the LoRA mapping with
`logits_indices_padded`, rebuilds the Punica metadata for that compact
mapping, and scopes it only to the Gemma3n/Gemma4 cross-decoder call.
The original full-batch metadata remains active for the self-decoder and other
model operations.

## Test Plan

Unit tests:

```bash
python -m pytest -q \
  tests/lora/test_fast_prefill_lora_mapping.py \
  tests/v1/worker/test_attn_utils.py -k 'fast_prefill'
```

End-to-end comparison used the same two-request batch in every run:

- Request 1: a 32-repeat long base-model prompt.
- Request 2: `The answer is` with a rank-1 LoRA adapter.
- `max_tokens=1`, greedy sampling, `logprobs=5`, three repetitions.
- Gemma 4 E2B-IT, MRV2 model runner, KV-sharing fast-prefill enabled for the
  fast runs.
- The PR correctness comparison covers eager execution with fast-prefill and
  eager execution with fast-prefill disabled.

## Test Result

| Configuration | Repetitions | Result |
| --- | ---: | --- |
| Before fix, eager fast-prefill | 0/3 completed | CUDA illegal memory access in the LoRA shrink kernel; no request result returned |
| After fix, eager fast-prefill | 3/3 completed | Both requests completed with token/logprob results; selected tokens: `107`, `711` |
| After fix, eager full-prefill | 3/3 completed | Both requests completed with token/logprob results; selected tokens: `107`, `711` |

For the eager comparison, fast-prefill and full-prefill selected the same
token for both requests and produced the same LoRA-request top-5 token set.
The maximum absolute difference among matching top-5 logprobs was `0.076553`.
