# [ROCm][Attention] Shape-aware split-KV and launch config for Triton DiffKV (gfx950)

[Upstream PR](https://github.com/vllm-project/vllm/pull/58650) · state: open · merged: False

## Original PR description

## Overview

Two changes to Triton DiffKV attention on gfx950, the path MiMo-V2.x's sliding-window layers take on ROCm:

1. **Split only the sliding window across decode segments, and pick the segment count per shape.**
2. **Launch 2D with one wave per workgroup when the grid fills the device.** It is turned off under batch invariance and skipped where 4 warps are faster.

MiMo-V2.6-Pro-RL, TP4, MI355X: **+6–8% output throughput at 8k and +16–19% at 64k–128k**, with GSM8K unchanged. Full-attention layers are unchanged.

## Motivation

**Split-KV splits the wrong range.** The 3D decode path divides `[0, seq_len)` into 16 segments and only then clips each one to the window. Far past the window, the window lands in one or two segments, and the rest exit with no work. #59349 fixes the same problem in `triton_unified_attention`; this PR fixes it in the DiffKV kernel. The helper has the same signature as #59349's, so the two can converge.

**16 segments is also the wrong count for a small window.** A 128-token window is 8 tiles, so half of 16 segments are empty but still write partials that the reduce reads.

So the segment count now comes from the shape. Starting at 16, it halves while a segment would get less than one tile, or while the reduce would read more than 8 partials per window token. Below 4 segments it launches 2D. Every input is host-side and depends only on the padded batch, so CUDA graphs are unaffected.

Just past the window, the two splits are equally long and re-splitting only shifts tile alignment. The window split is therefore taken only once it shortens the longest segment by 1.5x.


## Changes

- `compute_3d_segments_diffkv`: used by both the attention and reduce kernels, so they cannot disagree. Without a window it compiles to the old expressions.
- `_num_kv_segments`: the segment-count rule. It applies on gfx950 to sliding-window layers only; elsewhere it stays at 16.
- `_use_single_wave_2d`: the occupancy-gated single-wave launch. It uses the `launch_num_warps`/`launch_num_stages` pattern from `triton_unified_attention`, caches the CU count, and is off under `VLLM_BATCH_INVARIANT`.

## Test Plan

- `pytest tests/kernels/attention/test_triton_unified_attention_diffkv.py`: 115 passed on MI355X. New tests:
  - decode up to 131k tokens against a dense reference, with blocks outside the window NaN-poisoned
  - bitwise-equal outputs across warp counts
  - the segment-count rule
- Decode kernel sweep, held out from the data used to tune the constants: 2944 cells covering heads 8/1–128/8, batch 1–128, window 128–8192/none, and KV 3k–131k.
- End to end on MiMo-V2.6-Pro-RL, nightly `ac68c308` with aiter main built from source. Only this file differs between builds:

```bash
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4 \
vllm serve XiaomiMiMo/MiMo-V2.6-Pro-RL -tp 4 --trust-remote-code \
  --gpu-memory-utilization 0.93 --max-model-len auto \
  --kv-cache-dtype auto --no-enable-prefix-caching \
  --reasoning-parser mimo --tool-call-parser mimo --enable-auto-tool-choice \
  --generation-config vllm
```

- GSM8K: all 1319 questions, 8-shot chat, greedy. Long-context needle retrieval: 4k–120k.
