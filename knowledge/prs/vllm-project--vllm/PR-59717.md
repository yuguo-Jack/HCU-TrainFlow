# [Bugfix][MoE] Remap invalid topk_ids in moe_permute without expert_map

[Upstream PR](https://github.com/vllm-project/vllm/pull/59717) · state: open · merged: False

## Original PR description



## Overview

Fixes #59686. `moe_permute` returns wrong `expert_first_token_offset` when `topk_ids` contains `-1` (the id the router writes for CUDA-graph padding tokens with `VLLM_MOE_SKIP_PADDING=1`, the default) and no `expert_map` is given. The CUTLASS fp8 MoE path then runs some valid tokens through the wrong expert. This always applies the existing invalid-id remap in `moe_sort_routing`.

## Claims

- Valid tokens' MoE outputs no longer depend on CUDA-graph padding when `CutlassExpertsFp8` (and the other `moe_permute` callers: `cutlass_moe.py` W4A8 path, Humming non-scatter path) run without an `expert_map`.
- Fixes single-request serving quality of fp8 MoE checkpoints on the auto-selected `VLLM_CUTLASS` backend (first-token collapse to `'\n'`, off-topic sampled output).
- No change when all ids are valid or when an `expert_map` is given (the remap already ran there).

## Details

Root cause: `CubKeyValueSorter` radix-sorts only the low `floor(log2(2E-1)) + 1` bits, so a raw `-1` (all ones) sorts after every real expert, but `findTotalEltsLessThanTarget` binary-searches the keys as signed ascending ints. Probes landing in the trailing `-1`s push offsets too high, so an expert's grouped-GEMM segment can cover the next expert's rows; when padding outnumbers valid tokens every offset equals the total route count and the valid MoE output is zero. `preprocessTopkIdKernel` already maps ids outside `[0, n_expert)` to the `n_expert` sentinel the sort expects, but it only ran with an `expert_map` or `build_inverse`; `moe_permute` / `moe_permute_with_scratch` pass neither on a single EP rank.

Cost: one `n_token * topk` int32 copy and one elementwise kernel per `moe_permute` call, no host sync, CUDA-graph safe.

`preprocessTopkIdLauncher` now returns early for an empty batch, since the unconditional call would otherwise compute `block = 0`. This overlaps #58790 (empty routing in `moe_permute`, open); whichever lands second can drop its guard.

Not duplicate: open PRs on the same `-1` padding sentinel target other backends (AITER #57036, FlashInfer b12x #57946, XPU #55231) or empty routing (#58790); none changes the `moe_sort_routing` remap gate. Searched `moe_permute`, `expert_first_token_offset`, `topk_ids -1 padding`, `VLLM_MOE_SKIP_PADDING`, `preprocessTopkId`.

Limitations: validated on H100 only; the sm_90 kernel build used CUDA 13.1.

- jlqibm · comment · 2026-10-08T01:11:09Z · [source](https://github.com/vllm-project/vllm/pull/59717#discussion_r4213620424)

File: `csrc/libtorch_stable/moe/moe_permute_unpermute_op.cu` · line 116

Good catch, thanks. Remapping -1 routes past the valid rows means `run_cutlass_moe_fp8` never writes
those rows of `mm1_out`, but with per-tensor dynamic activation quant (`per_act_token=False`) the
`act_out` scale reduces over the whole workspace, so stale data could skew the scale for valid
tokens.

The existing `mm1_out.fill_(0)` already covered exactly this case for expert-parallel/batched
runs (guarded by `expert_map is not None or use_batched_format`). I'm now applying it whenever the scale is
per-tensor. I added the same guard to `run_cutlass_moe_w4a8_fp8`, which has the same structure. The
per-token path doesn't reduce across rows and is unchanged. The fill is one memset of the `M*topk x 2N` workspace
and only runs on the per-tensor path.

`fused_humming_moe` had the same assumption in its scatter branch: `num_valid_tokens` was only
passed with an expert map. It now always comes from `expert_offsets[-1:]`.

New regression test: `test_run_cutlass_moe_fp8_padded_routes_per_tensor` in
`tests/kernels/moe/test_cutlass_moe.py`. It runs with half the tokens routed to -1, a garbage-filled
workspace and `a2_scale=None`, and compares the valid rows against an unpadded run. It fails
without the fill and passes with it on GB200 (SM100); without the fill the
output is NaN. The existing `test_run_cutlass_moe_fp8` cases and `test_moe_permute_unpermute.py`
(462 cases) still pass.
