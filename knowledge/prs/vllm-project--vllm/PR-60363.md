# [Bugfix][Tool Parser] Stream InternLM2 tool arguments from the raw text

[Upstream PR](https://github.com/vllm-project/vllm/pull/60363) · state: closed · merged: False

## Original PR description

## Overview

Fixes #60348. `Internlm2ToolParser.extract_tool_calls_streaming` rebuilt each argument delta from
the re-serialized partial parse, so characters went missing and the concatenated deltas were not the
completed arguments. It now streams slices of the raw argument text, tracking how much has been sent.

## Claims

- The concatenated argument deltas reconstruct the complete arguments JSON for every chunk boundary
  I tried, instead of losing characters such as `{"location": "Beijing, "days": 3`.
- `"parameters": {}` now streams `{}` rather than nothing.
- Braces inside a string value no longer confuse the end of the arguments object.

## Validation

New parametrized test `test_streaming_arguments_survive_every_chunk_boundary` in
`tests/tool_parsers/test_internlm2_tool_parser.py`, cutting the body at 1, 3, 6 and 12 characters
because what gets lost depends on where the boundary lands, asserting the concatenation is exactly
`{"city": "Beijing", "days": 3}`.

```
pytest tests/tool_parsers/test_internlm2_tool_parser.py
```

Driving the parser over 5 argument bodies (two keys, three keys, three-level nesting, a `}` inside a
string value, and `{}`) against 8 chunkings each: 40 of 40 combinations lose characters before this
change, 0 of 40 after. A second sweep over escaped strings (embedded quote, backslash, newline,
emoji, braces), all JSON value types and a pretty-printed multi-line body reconstructs the arguments
at every chunking, the existing `test_streaming_arguments_in_single_delta` scenario is unchanged, and
the five malformed inputs from the shared test config still return without raising when split
mid-string.

What the deltas now carry is the model's own argument text, so it is byte-identical to the
non-streaming `json.dumps(..., ensure_ascii=False)` only when the model emits that style; for a
compact or pretty-printed body the concatenation is JSON-equivalent rather than byte-equal. That is
the contract the Hermes parser already ships.

`ruff check` and `ruff format --check` are clean on `vllm/tool_parsers/internlm2_tool_parser.py`.

The shared `ToolParserTests` streaming cases for this parser stay `xfail`: they feed
`<|action_start|>` and `<|plugin|>` as separate token deltas and the marker check in this parser does
not join them. That is a different defect and this change does not touch it.

Model evaluation: not applicable. This only changes how already-decoded tool-call arguments are cut
into streaming deltas in the API layer — no weights, sampling, kernels or scheduling, so identical
generated text gives identical results.

## Details

The `cur_arguments and prev_arguments` branch computed deltas with `extract_intermediate_diff` over
`json.dumps` of two successive partial parses, and the `cur_arguments and not prev_arguments` branch
located the delta inside a re-serialized parse. Both rest on the serialized partial parse growing by
append, and it does not: `partial_json_parser` closes the object optimistically, so the `"` and `}`
it invents for one parse are gone from the next. Once a delta containing an invented character has
been sent, the stream is no longer a prefix of the finished arguments, so the missing characters
cannot be recovered and `get_remaining_unstreamed_args` cannot flush them either. On top of that,
the first parse that carries arguments is the same call that sends the function name, so
`prev_arguments` becomes non-`None` before anything has been streamed and the leading
`{"location": "Beijing"` is simply skipped.

The raw argument text, by contrast, only ever grows by append, so a character count into it is a
valid resume point. `get_raw_arguments` returns the raw object text as far as it has arrived, using a
small left-to-right scan that tracks string literals and escapes so a brace inside a value is not
read as the closing brace. Because the scan stops at the matching brace, what it returns for a prefix
of the action is always a prefix of what it returns for the whole, which is what makes the slice
safe. The streaming branch then sends `raw[len(already_streamed):]` and records the new length. The
partial parse is still used for the function name and for `prev_tool_call_arr`, which serving code
reads.

`jamba_tool_parser.py` has the same `extract_intermediate_diff` pattern. I kept this PR to the parser
the issue reports so the change stays reviewable; happy to do Jamba in a follow-up.

Not a duplicate: `gh pr list --state open --search "60348 in:body"` is empty. Of the open PRs on this
file, #57504 buffers the partial opening marker, #58346 fixes a `ValueError` on a second action
block, #50078 and #44140 handle malformed output, and #47968 returns early for unlisted tool names —
none of them changes how argument deltas are computed. #50461 does touch the same branch, and its
description sets out the loss it addresses and the class of argument bodies it leaves open; #60348 is
in that remaining class, and this PR closes it by not deriving deltas from the serialized parse at
all rather than by reconciling one afterwards.
