# [Bugfix][KVConnector] Drain preemptions before V2 request updates

[Upstream PR](https://github.com/vllm-project/vllm/pull/59410) · state: open · merged: False

## Original PR description

## Overview

Fixes #59409. Drain KV-connector preemptions before V2 request updates can zero or copy reused pages, matching V1's existing ordering.

## Claims

- Cover GPU and encoder-only runner entry points, including zero-token steps, without changing metadata binding or synchronous/deferred load timing.
- Invoke the callback once per step before page reuse. Decoder dummy steps retain the callback entry; the existing disabled-connector guard suppresses backend work during profiling/warmup.
- Keep the backend responsible for safe transfer completion; no new public backend API or global GPU synchronization is introduced.

## Details

Conflict resolution follows [the latest review](https://github.com/vllm-project/vllm/pull/59410#issuecomment-6094798101): retain #60754's explicit `pre_forward(scheduler_output, input_batch=None, attn_metadata=None)` signature and unchanged `_build_load_kwargs`, add `handle_preemptions` as a separate method, and remove its duplicate invocation from `pre_forward`. Tests retain upstream's `input_batch` including `num_tokens`.

`update_requests()` may zero newly assigned blocks or perform COW while an asynchronous connector save still reads them. Calling `handle_preemptions()` only from `pre_forward()` is too late. V1 already invokes it before `_update_states()`, including before its zero-token early return; V2 now follows that boundary.

Following [the review](https://github.com/vllm-project/vllm/pull/59410#pullrequestreview-5367161896), the decoder call is outside the `dummy_run` condition. Enabled dummy steps therefore retain the prior callback behavior; `_dummy_run()` already disables the connector for profiling/warmup. Tests cover both enabled and disabled dummy steps, including the all-DP-ranks-zero `no_forward()` branch. The helper and backend docstrings explicitly assign preemption handling to the runner before request updates. `no_forward()` services transfer work after that boundary and does not invoke a second drain.

This addresses the runner-boundary gap discussed in closed #56817; merged #42676 only reordered callbacks within `pre_forward`. Related #59028 changes Mooncake Store's connector-local re-admission cleanup rather than either V2 runner entry point.

- apex-mochen · COMMENTED · 2026-09-30T13:55:05Z · [source](https://github.com/vllm-project/vllm/pull/59410#pullrequestreview-5367161896)

Checked this out and ran it rather than only reading the diff -- I think it is correct and worth landing. Three things.

**1. The placement is right, and V2 is fully covered (not half-fixed).**

The two runner-side writes that actually touch physical KV pages both live inside `update_requests()`: `kv_block_zeroer.zero_block_ids(...)` at `gpu/model_runner.py:1230` and `copy_kv_cache_blocks_inplace(...)` (COW) at `:1235`. Draining before that call is strictly stronger than draining before the forward, so the window really does close. `block_tables.apply_staged_writes()` has exactly two call sites in the tree (`model_runner.py:1693`, `mm_encoder_model_runner.py:140`) and both are patched, so no third V2 runner is left behind.

Worth putting in the description: this restores parity with V1, where `gpu_model_runner.py:4180` already calls `handle_preemptions()` before `_update_states()` -- and does so unconditionally, before its own zero-token early return. That is the strongest argument for merging this.

**2. Both test arms reproduce.**

- PR head, `tests/v1/worker/test_gpu_kv_connector.py`: **8 passed**.
- Negative control (the three production files restored to main, your test file kept): the four real-step cases fail with `AssertionError: a pending save can still read reused pages` -> `assert [] == ['handle']`, and the dummy case passes -- 4 failed / 1 passed on the runner regression, matching your number. The other three failures in the module are the pre-existing tests you adapted, failing with `AttributeError: 'ActiveKVConnector' object has no attribute 'handle_preemptions'`, which is expected.

I also confirmed the refactor does not change how often the callback runs: on main `pre_forward` (and therefore `handle_preemptions`) is reached exactly once per non-dummy `execute_model`, either from the forward path at `:1962`/`:1988` or via `no_forward()` at `:1702`/`:1759`. So the `assert kv_connector_metadata is not None` that moved has the same reachability as before -- no new assert exposure.

**3. One question: dummy steps lose the drain, and `no_forward()` is no longer self-sufficient. Intended?**

On main, dummy runs *do* drain: `pre_forward` at `:1962`/`:1988` is not under the `if not dummy_run:` gate, so a dummy step with tokens reaches `handle_preemptions()` through it, and a zero-token dummy step reaches it via `no_forward() -> pre_forward()`. This patch closes both routes, and your test encodes that deliberately (`call_count == int(not dummy_run)`). The description says "skip decoder dummy steps" but does not say why that is safe, and V1 has no such gate.

Related: `ActiveKVConnector.no_forward()` (`gpu/kv_connector.py:130`) delegates to `pre_forward()` and used to inherit the drain from it. Now `no_forward()` on its own silently does not drain -- which is exactly why the two pre-existing tests needed manual `handle_preemptions()` calls. In-tree that is covered except one spot: `model_runner.py:1759` (`batch_desc.num_tokens == 0`, the all-DP-ranks-zero return) is reachable with `dummy_run=True`, where the new call is skipped.

I do not think this is a live bug -- the only producer of `valid_dummy_state_slots=True` is the SSM warmup path (`model_executor/warmup/replayssm_warmup.py:57`), where no real request exists and there is nothing to drain. So this is a "please confirm", not a blocker. If you would rather not carry the asymmetry, either keep the drain in `no_forward()` as well, or state in `KVConnectorBase_V1.handle_preemptions`'s docstring that the runner owns the call -- right now it reads as unconditional.

(All of the above was run in a CPU-only dev checkout against the mocked module -- no GPU involved, so the runner paths are exercised through your sentinel rather than on real hardware.)

- JunityZz · comment · 2026-10-11T09:36:20Z · [source](https://github.com/vllm-project/vllm/pull/59410#issuecomment-6107647525)

We hit this in practice, with user-visible corruption, on vLLM 0.30.0 with Model Runner V2, a hybrid model
(Qwen3.5 architecture, 48 Gated DeltaNet + 16 attention layers, compressed-tensors NVFP4, RTX 5090) and an
OffloadingConnector-based connector that stores a finished request's last, partially filled attention block.

What happens:

1. A request finishes. Its partial last block has no prefix-cache hash, so it goes to the front of the free queue.
2. In the next step, a newly scheduled request gets that block as its first new block, and the scheduler puts the
   pending store of the finished request into `jobs_to_flush`.
3. MRV2 writes the block before `pre_forward`: on a model with Mamba layers `update_requests` zeroes every new
   attention block (`new_block_ids_to_zero`) and runs the CoW copies, and `preprocess_state` pre-copies recurrent
   state into new Mamba blocks.
4. `handle_preemptions` then submits and waits for the store, which copies the zeros (or a GDN state) out under the
   finished request's key. Every later prefix hit on that block computes from garbage KV.

Numbers:

- Deterministic reproduction (`--max-num-seqs 1`, so the queued request takes the freed block in the very next step;
  then the follow-up turn hits the stored block; first-token KL against a cold prefill):
  - current MRV2 order: 6 of 10 hits produce garbage from the first token (KL 5.0-7.5);
  - with `handle_preemptions` moved before `update_requests` (the same change as this PR): 0 of 10, KL max 0.12
    (30 more cases: mean 0.08, top-1 equal 27 of 30). That is within the FP8 vs BF16 KV-cache noise on this model.
- Closed-loop multi-turn load (C=6, 900 s):
  - current order: 4 of 583 follow-up turns that hit such a block were garbage;
  - fixed order: 0 of 1,657 over two runs.

Moving the call to the start of `execute_model`, as this PR does, is equivalent to what we run. It also covers
`preprocess_state`, which runs after `update_requests`. +1 on landing it.

(Analysis and measurements prepared with AI assistance (Claude); the runs above were on real hardware.)
