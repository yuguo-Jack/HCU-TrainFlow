# [Model][ROCm] qwen4_exp: serve the AMD path in fp16

[Upstream PR](https://github.com/vllm-project/vllm/pull/60650) · state: open · merged: False

## Original PR description



## Overview

Let the AMD path of qwen4_exp (Qwen3.8-Flash-Next) run with `--dtype float16`. Today it hard-requires bf16 in the QSA backend, the indexer caches, the pre-indexer pooling and the hyper-connection parameters, so it cannot be served on GPUs where fp16 is the fast type, such as RDNA3 (gfx1100), whose `v_dot2_f32_bf16` runs at half the rate of the fp16 one.

## Claims

- `--dtype float16` loads and serves qwen4_exp on ROCm; bf16 is unchanged.
- No new kernels: the existing Triton QSA kernels already handle fp16; this removes the bf16-only checks and takes the cache and parameter dtypes from the model dtype.

## Validation

**Unit tests** (gfx1100): the QSA sparse attention and pre-indexer tests are parametrized over bf16 and fp16.

```
pytest tests/models/qwen4_exp/test_qsa_amd.py tests/models/qwen4_exp/test_qsa_pre_indexer_amd.py
# 37 passed, 8 skipped
```

**Serving on this branch alone** (current `main` + this PR, RX 7900 XTX, TP1): a 4-layer Flash-Next config with random weights (`--load-format dummy`, 64 experts), 2 requests of 32 tokens:

| | `--dtype float16` | `--dtype bfloat16` |
| --- | --- | --- |
| `main` | `NotImplementedError: Qwen4Exp QSA currently requires BF16` | serves |
| this PR | serves | serves |

**Full model in fp16**: Qwen3.8-Flash-Next pruned to 256 experts, GPTQ W4A16, TP4 on 4x RX 7900 XTX, MTP k=3: GSM8K 96.0% (chat, no thinking, 200 questions). That run needs RDNA3 changes that are not in `main` yet (asymmetric W4A16 MoE, an NF4 n-gram table), so it shows the fp16 path is numerically sound end to end rather than that `main` + this PR serves that checkpoint.

## Details

- QSA backend and impl (`amd/qsa.py`): accept fp16 next to bf16 for the model, the main KV cache (`auto`/`float16`) and Q/K/V; the cache storage must match the model dtype.
- Indexer (`amd/indexer_qsa.py`): the raw and compressed key caches take the model dtype instead of a hard-coded bf16.
- Pre-indexer (`amd/ops/qsa_pre_indexer.py`): the pooled key is rounded to the cache dtype before RMSNorm, matching the unfused path in either dtype.
- Sparse attention op (`amd/ops/qsa.py`): Q/K/V must share one of the two dtypes.
- Hyper-connections (`amd/model.py`, `amd/mtp.py`): parameters in the default dtype instead of bf16.
- `common/qsa_cache.py`: the side-cache backend lists fp16 as supported (no behavior change for the CUDA path, which keeps its own checks).
