# [RL] Support per-parameter source layouts for NCCL M2N

[Upstream PR](https://github.com/vllm-project/vllm/pull/60934) · state: open · merged: False

## Original PR description

## Overview

This PR extends the NCCL M2N weight-transfer backend introduced in #51520 so
each logical parameter can declare its own trainer-side source mesh and
placements.

This implements the source-side stage requested in #60563. It does not
duplicate an open contribution: no open PR currently implements per-parameter
NCCL M2N source meshes or placements.

This PR adds a general, per-parameter source-layout contract and
collective-safe M2N source plan. It is independent of the receiver reload
implementation and remains applicable if vLLM adopts modulewise reload.

Before this change, one source mesh described every parameter in a transfer
session. That cannot directly represent parameters using different mesh
factorizations over the same trainer ranks—for example, dense parameters on a
`(DP, TP)` mesh and expert parameters on an `(EDP, EP)` mesh—without first
gathering or normalizing one of those layouts.

After this change, the producer publishes an ordered parameter manifest
containing each parameter's global metadata and source layout. Each
`m2n.reshard()` operation uses the mesh and placements declared for that
parameter. The participating source-rank set remains unchanged; parameters may
use different mesh shapes and placements over that same set.

The contract is independent of model type, trainer framework, world size, and
parameter naming. DTensor-backed sources and custom producers use the same
interface.

This PR preserves the existing session-wide destination mesh. Per-parameter
destination meshes are future work. Model-native rank-local destination targets
are introduced separately by the next PR in this stack.

## Claims

- Adds a general source-layout contract in which every logical parameter
  declares its global shape, dtype, source mesh, and source placements.

- Supports different mesh factorizations over the same participating trainer
  ranks, allowing parameter groups with different parallel layouts to use one
  NCCL M2N transfer session.

- Provides a common producer interface for plain tensors, DTensors, and custom
  framework adapters without requiring the transport engine to infer model
  structure or parallelism from parameter names.

- Establishes a versioned, ordered source plan and requires collective
  agreement on its contents before constructing the NCCL data-plane
  communicator or entering an M2N reshard collective.

- Validates mesh geometry, placements, parameter order, local tensor shape,
  dtype, CUDA device, and contiguity before transfer.

- Preserves the existing session-wide destination mesh and receiver loading
  behavior. Rank-local destination targets are added by the next PR in this
  stack.

## Details

See #60563 for the motivation and representative mixed-layout trainer
topologies.

### Per-parameter source-layout contract

`M2NParamMeta` extends the existing parameter metadata with a required
`source_layout`. The layout contains the parameter's two-dimensional source
mesh and its placements on that mesh.

Layouts are validated before transfer. The validation checks that:

- the mesh covers the complete participating trainer-rank interval;
- the mesh and placements use the forms supported by NCCL M2N;
- at most one mesh axis shards the tensor;
- the referenced tensor dimension exists; and
- the tensor dimension is divisible by the corresponding mesh dimension.

`M2NWeightSource` publishes ordered parameter metadata and then yields each
rank's local tensors in that same order. It does not materialize global tensors.

Two source implementations are included:

- `DTensorModuleSource` derives each parameter's mesh and placements from its
  DTensor metadata and yields `to_local()`. Plain tensors are treated as
  replicated.
- `ManifestM2NWeightSource` allows custom trainer integrations to provide
  explicit layouts and lazily materialized rank-local tensors.

This keeps trainer-specific parameter classification and conversion outside the
transport engine.

### Collective-safe source plan

The initialization wire record carries each parameter's name, dtype, global
shape, source-mesh dimensions, and source placements. The wire schema is
versioned so incompatible producers and receivers fail during initialization.

A deterministic SHA-256 digest covers the complete ordered source plan. It
therefore detects changes to parameter metadata, source layouts, parameter
membership, or caller order.

Before constructing the NCCL data-plane communicator, the participants agree
on:

1. the versioned and ordered source plan;
2. TCPStore-derived versus pre-shared-UID data-plane bootstrap;
3. execution-affecting NCCL M2N settings;
4. local CUDA and runtime readiness; and
5. the loaded NCCL M2N library identity.

A pre-shared NCCL UID replaces only data-plane bootstrap. The TCP metadata
rendezvous remains active so participants can exchange and validate the plan.

Malformed metadata, missing or reordered parameters, configuration
disagreement, and local initialization failures are reported before any rank
enters an M2N reshard collective.

### Update-time source validation

Initialization establishes the allowed parameter manifest, but each update may
materialize new rank-local tensor views. The producer output is therefore
validated again when an update runs.

Before transferring a requested parameter, the trainer verifies that its local
tensor:

- appears in the declared manifest and in the expected order;
- has the local shape implied by its global shape and source layout;
- has the declared dtype;
- is on the expected CUDA device; and
- is contiguous.

The update path also rejects missing, additional, duplicate, or reordered
producer entries. These checks apply to full, subset, and repeated updates.

A source-contract violation fails the update instead of passing inconsistent
metadata or storage into `m2n.reshard()`.

### Deployment-global worker rank mapping

The shared NCCL communicator assigns trainer ranks to
`[0, rank_offset)` and inference ranks to
`[rank_offset, world_size)`. `rank_offset` therefore remains the start of the
complete destination mesh.

A single vLLM deployment can derive its global communicator rank directly from
that offset. When the destination consists of multiple independent vLLM
deployments, however, each deployment has its own local data-parallel ranks
starting at zero.

The optional `worker_rank_offset` identifies the first global rank assigned to
one inference deployment. Its local worker ranks are mapped into the common
destination interval without changing the destination mesh or parameter-layout
contract.

`worker_rank_offset` must lie inside the configured destination interval. When
it is omitted, it defaults to `rank_offset`, preserving the existing
single-deployment behavior.

### Failure and lifecycle safety

The receiver enforces a state machine around each update. Any initialization,
transfer, loading, or finalization failure poisons the session, releases its
NCCL M2N resources, and prevents reuse after a potentially partial update.

Trainer failures cancel outstanding work and attempt to release all transfer
resources. Shutdown during an active update is rejected to avoid racing the
collectives.

### Destination behavior and PR boundary

| Behavior | Before this PR | After this PR |
|---|---|---|
| Source mesh | One mesh for every parameter | Each parameter declares its own source mesh and placements |
| Destination mesh | One mesh shared by every parameter | Unchanged |
| Destination placements | Published per parameter over the shared destination mesh | Unchanged |
| Receiver loading | Exact-name in-place destination when available; otherwise reconstruct the full logical tensor and call `load_weights` | Unchanged |

This PR changes the source-layout contract and source-plan agreement. It does
not change how the receiver selects or loads destination storage.

The next PR in this stack, #60949, adds model-native rank-local destination
targets. Per-parameter destination meshes remain future work.

- hao-aaron · comment · 2026-10-12T01:21:31Z · [source](https://github.com/vllm-project/vllm/pull/60934#issuecomment-6116072407)

Thanks for putting this together. The per-parameter source layout is a clear improvement, and the mixed (DP, TP) / (EDP, EP) case is a real gap today.

One thing I'd like to discuss before going deeper: a fair amount of this PR is handling that seems specific to how `nccl_m2n` behaves, rather than to vLLM's weight-transfer logic. I'd rather keep that out of vLLM if the library can own it. Could some of these move to `nccl_m2n` / `nccl-extensions`?

- **NCCL runtime identity** (`prepare_m2n_nccl_runtime`, the `RTLD_GLOBAL` promotion, the `ncclCommWindowRegister` address check). The binding knows which NCCL it resolved, so it seems better placed to expose that or check the comm itself. Building the comm through nccl4py would avoid the mismatch entirely.
- **`NCCL_RESHARD_*` env agreement.** These settings are process-global and env-driven inside the library, and `ncclM2nConfig_t` only carries `maxCta`. Moving them into the config, with the library checking that ranks agree, would fix this for every caller, not just vLLM.
- **Layout limits and pre-NCCL validation.** We already mirror `MAX_SOURCE_SHARDS` / `MAX_DEST_SHARDS` from `reshard_limits.h`. A comm-free validate call, or exported limits, would let us drop that copy and stay correct if the caps change.
- **Local tensor checks.** Device and contiguity could be checked in the binding. For shape, an optional global shape on the tensor descriptor would let the library reject a bad local shape before entry.

If those can live upstream, the vLLM side becomes much smaller: per-parameter meshes and placements, the manifest source, and the name/order digest. Those are the parts only vLLM can do.

Could we also defer the lifecycle / poisoning changes to later? Failure handling is tied up with how modulewise reload (#59502) handles update integrity, which is still being worked out, so I'd rather not commit to a design here yet.
