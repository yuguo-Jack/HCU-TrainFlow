# [Test] Accept tied tokens at the k-th value in the Triton top-k test

[Upstream PR](https://github.com/vllm-project/vllm/pull/60726) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Lets `TestTritonTopkTopp::test_topk_only` accept the documented tie behaviour. `[128256-1024]` fails on MI355 with the ROCm 10.0 (TheRock) stack (#58761) and in main's scheduled ROCm 10 AMD CI lane.

## Claims

- The PyTorch reference may keep extra tokens only when they tie exactly with the k-th value.
- Triton must never keep a token the reference masked, so real over- and under-keeps still fail.

## Validation

`pytest tests/v1/sample/test_topk_topp_sampler.py -k TestTritonTopkTopp` on MI300X, with `hipGetDeviceProperties` shimmed to MI355's 128 CUs so torch generates CI's exact inputs:

| | ROCm 10 image | ROCm 7.2 image |
|---|---|---|
| before | 1 failed, 92 passed | 93 passed |
| after | 93 passed | 93 passed |

## Details

torch's random-number layout depends on the CU count, and TheRock's GPU `randn` differs from the 7.2 build by about 1 ULP. With MI355 inputs, row 330 contains two bit-identical logits at ranks 84 and 85, where k = 84. The sort-based reference keeps both and Triton keeps exactly k, so the test failed on 85 vs 84.

#50979 (closed by its author) tried to make the PyTorch path keep exactly k instead; its review noted that deterministic tie-breaking across Triton and both PyTorch paths would also be needed. This PR only aligns the test with the current documented behaviour.
