# [Bugfix][Parser] Keep a text-spelled reasoning marker as content in non-streaming parse

[Upstream PR](https://github.com/vllm-project/vllm/pull/60256) · state: open · merged: False

## Original PR description



## Overview

Non-streaming `parse()` drops a `</think>` that the model wrote out as ordinary text in its answer, while streaming keeps it. This makes the non-streaming path apply the rule the streaming engine already has: a reasoning marker is structural only when it arrived as its special token.

Part of #51679 (the streaming vs non-streaming split described in the later comments). The bug in that issue's original body, a tool parser alone consuming `</think>`, was already fixed by #47562.

## Claims

- For engine-based parsers behind `DelegatingParser` (for example `--reasoning-parser qwen3`, with or without `--tool-call-parser qwen3_xml`), a reasoning marker spelled with ordinary tokens now stays in `content` in non-streaming responses, as it does when streaming.
- A marker that arrives as its special token is handled as before, including the duplicate `</think>` absorb.
- Requests without token IDs, and legacy (non-engine) parsers, are unchanged.

## Validation

**End to end**, `Qwen/Qwen3-0.6B` on CPU (macOS arm64), `--reasoning-parser qwen3 --enable-auto-tool-choice --tool-call-parser qwen3_xml`. A `structured_outputs.choice` constraint makes the model write the literal, and since the grammar matches strings the model samples the split spelling (`'</'`, `'think'`, `'>`'`). Same request, `temperature=0`, sent streamed and non-streamed. The output holds one real `</think>` token (id 151668) followed by the spelled-out one.

| | non-streaming `content` | streaming `content` |
|---|---|---|

| this PR | ``'Close the block with `</think>` and continue.'`` | ``'Close the block with `</think>` and continue.'`` |

## Details

**Root cause.** `StreamingParserEngine._process_lex_tokens` treats a lexed terminal as content when that terminal has a special token ID and the stream has carried token IDs. `DelegatingParser.parse()` receives `model_output_token_ids` from serving but dropped them: the reasoning pass fed the engine text only, so every `</think>` in the text looked structural and the `(CONTENT, THINK_END)` transition absorbed it.

**Change.**

- `ParserEngine._feed_complete` replays the complete output as a stream would deliver it: each marker that arrived as its special token is fed as its own delta, with the text between markers decoded per run. It only uses the IDs when they reproduce the text. The IDs may run past the text (stop token, stop string) or cover a prefix of it; anything else falls back to the existing text-only path.
- `ParserEngineReasoningAdapter.extract_reasoning_with_token_ids` hands the IDs to the engine and reports whether they were used. The engine subclasses that override `extract_reasoning(model_output, request)` keep their signature.
- `DelegatingParser.parse` uses it and, when the reasoning pass did resolve markers by ID, runs the tool pass with `skip_reasoning_parsing` set, since any reasoning marker still in the content was spelled out by the model.

I first fed the whole text and all IDs through one `_feed` call. On a real server that bound the special `</think>` to the wrong occurrence: the IDs include the stop token and the text does not, so the scanner fell back to anchor matching with `rfind`. Replaying per segment avoids that path, and the new test covers it by passing IDs with a trailing stop token.

**Not changed, on purpose.**

- A duplicate `</think>` emitted as the special token after reasoning ended: with a reasoning parser only, streaming keeps it and non-streaming absorbs it. That is the default question still open in #51679.
- Thinking disabled (`enable_thinking=false`) with a tool parser: the engine skips the reasoning pass, the tool pass still sees text only, and a spelled-out closer is absorbed there.
- Tool-call markers spelled with ordinary tokens are still parsed as tool calls in non-streaming. Related: #58315, #59145.
- Parsers whose reasoning marker is shared with other structure (Inkling) are not affected by `skip_reasoning_parsing`, so their tool pass is unchanged.

**Duplicate check.** `gh pr list --state open --search "51679"` returns nothing. #55255 only adds tests for the tool-parser-only configuration. #59145 touches the same files but changes the structural-tag grammar, not parsing.
