# [CPU] Add variable-sized all-gather support to CPU communicator

[Upstream PR](https://github.com/vllm-project/vllm/pull/60958) · state: open · merged: False

## Original PR description



## Overview

Adds `all_gatherv()` support to `CpuCommunicator` using PyTorch distributed collectives.

Partially addresses #57837. This PR implements CPU variable-sized all-gather; `reduce_scatterv()` and end-to-end Wide Expert Parallelism support remain out of scope.

## Claims

- Supports variable-sized all-gather for both individual tensors and lists of tensors.
- Uses padding and trimming to handle unequal-sized rank contributions with Gloo.
- Avoids unnecessary padding when all ranks contribute equally sized tensors.
- Supports empty contributions, including when all ranks contribute zero elements.
- Preserves rank ordering and supports gathering along dimension 0.

## Validation

Added `tests/distributed/test_cpu_gatherv.py`, exercising the actual `CpuCommunicator` with two CPU processes and the Gloo backend.

The regression test covers:
- Unequal sizes (`[2, 3]`).
- Lists of tensors with different feature dimensions.
- Equal sizes with explicit `sizes` and `sizes=None`.
- One empty rank (`[0, 3]`).
- Both ranks empty (`[0, 0]`).

**Local validation:**
- `python -m pytest tests/distributed/test_cpu_gatherv.py -v` — 1 passed.
- `uvx ruff check` on both changed files — passed.
- `uvx ruff format --check` on both changed files — passed.
- `git diff --check` — passed.

Tested locally on macOS with PyTorch 2.13.0 using a two-process Gloo setup. Multi-node execution, CPU shared-memory communication, and end-to-end expert parallelism have not been validated.

## Details

The existing CPU communicator does not implement `all_gatherv()`, which is required by the all-gather/reduce-scatter expert-parallel communication path.

For unequal-sized contributions, the implementation pads each rank's tensor to the maximum specified size, performs a fixed-size `torch.distributed.all_gather_single()`, then removes the padding and concatenates the results in rank order.

For equal-sized contributions, the implementation uses a direct collective without padding.

The implementation uses PyTorch distributed directly rather than vLLM's specialized CPU shared-memory communicator. This provides a Gloo-compatible fallback but does not introduce a shared-memory-optimized variable-sized collective.

The operation currently supports `dim=0`. As with other distributed collectives, participating ranks must agree on the collective arguments and tensor shapes.
