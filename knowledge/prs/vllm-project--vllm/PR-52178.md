# [Bugfix] Propagate fatal EngineCore shutdown

[Upstream PR](https://github.com/vllm-project/vllm/pull/52178) · state: open · merged: False

## Original PR description

## Purpose

Fixes #48966.

When `EngineCore` dies unexpectedly, the HTTP launcher can finish with status 0,
so supervisors using `Restart=on-failure` do not restart the serving process.
A late SIGTERM makes this especially easy to reproduce: a supervisor observes a
failed health check, sends SIGTERM, and the signal can otherwise make an
engine-caused shutdown look graceful.

This change records the cause at the point where an observed `EngineCore` death
forces the HTTP server to exit. The first fatal `dead_error` is latched on the
server and is re-raised after HTTP cleanup. A later SIGINT/SIGTERM cannot clear
that cause. Conversely, when a signal is observed before engine teardown, the
shutdown remains intentional and exits successfully.

The `/health` path now performs the same fatal-state recording before returning
503. This closes the production supervisor sequence:

```text
EngineCore dies -> /health returns 503 -> supervisor sends SIGTERM -> exit 1
```

The decision remains consistent with `VLLM_KEEP_ALIVE_ON_ENGINE_DEATH`: when
keep-alive is enabled, engine death is not latched as the cause of process exit.
If an errored, stopped engine has no recorded `dead_error`, a fallback
`RuntimeError` preserves the nonzero-exit contract instead of silently reverting
to status 0.

The exception is not consumed by an intermediate cleanup handler on the
single-server path: `serve_http()` returns the failure coroutine,
`run_server_worker()` awaits it after leaving the engine-client context and
closes the socket in a `finally`, `run_server()` lets it propagate, and the CLI
calls `uvloop.run(run_server(args))` without a broad catch. The process-level
results below verify the end of that chain rather than only the coroutine.

After #54913 landed, this branch was rebased onto current `main`. Its render-only
server handling is now supplied by `main`; the overlapping implementation and
two render-only tests were removed from this PR so the remaining diff stays
focused on fatal-exit cause propagation.

## Test Plan

1. Unit-test fatal-cause latching with `errored` and `is_running` varied
   independently, including signal-first shutdown, keep-alive, preservation of
   the first error, and a missing `dead_error`.
2. Exercise both race orderings through `serve_http()`:
   engine death followed by SIGTERM remains fatal, while SIGTERM observed before
   engine teardown remains graceful.
3. Verify that `/health` records an observed `EngineDeadError` before returning
   503.
4. Start the OpenAI API server on one RTX 4090, issue a successful request, then
   compare an `EngineCore` SIGKILL with an intentional API-server SIGTERM.
5. Repeat the fatal path with TP=2 on two RTX 4090 GPUs by killing only one TP
   worker.
6. Reproduce the supervisor ordering directly: kill `EngineCore`, wait for
   `/health` to return 503, immediately send SIGTERM to the API server, and
   verify a nonzero top-level exit with no orphaned processes.

The remaining tests in `test_basic.py` start a model server and therefore were
not runnable in GPU-less mode. The process-level GPU validation below covers
the serving paths changed by this PR.

Process-level validation on NVIDIA GeForce RTX 4090 GPUs, PyTorch
2.13.0+cu130:

| Scenario | Top-level exit | `/health` after fault | Orphans |
| --- | ---: | ---: | --- |
| Single GPU: SIGKILL `EngineCore` | 1 | — | none |
| Single GPU: intentional SIGTERM | 0 | — | none |
| TP=2: SIGKILL only `VllmWorker-0` | 1 | — | none |
| Single GPU: SIGKILL `EngineCore`, observe failure, then SIGTERM | 1 | 503 | none |

The late-signal trial emitted both the signal-shutdown log and the fatal log,
then propagated `EngineDeadError` to the top-level process:

```text
[shutdown] API server: shutdown triggered
[shutdown] API server: EngineCore died unexpectedly; exiting non-zero
```

The TP=2 worker trial exercised the full propagation chain: the EngineCore log
reported `VllmWorker-0 died unexpectedly`, followed by an EngineCore fatal
error, `EngineDeadError` in the API server, the fatal shutdown log, and a
nonzero top-level process exit.

The multi-port DP supervisor remains a separate parent-process lifecycle path
and is not claimed as covered by this focused change.

Follow-up: audit and, if necessary, separately fix nonzero child-exit
propagation through the multi-port `DPSupervisor` parent process. That path has
different lifecycle semantics and should have its own focused regression.
