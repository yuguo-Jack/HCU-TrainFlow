# [Bugfix][DSv4] Gate indexer paged MQA metadata on DeepGEMM support

[Upstream PR](https://github.com/vllm-project/vllm/pull/53522) · state: open · merged: False

## Original PR description

## Purpose

Indexer decode fills `get_paged_mqa_logits_metadata` whenever `has_deep_gemm()` is true (package importable). That helper is the Hopper/Blackwell schedule and asserts 32 or 64 states.

DSV4 compress-128 pages have 2 states and trip the host assert. `is_deep_gemm_supported()` is the arch gate the rest of the tree already uses.

Skip the fill unless CUDA, `is_deep_gemm_supported()`, and `num_states in (32, 64)`. SM12x FlashInfer sparse MLA does not consume this schedule; skipping is also safe there when pages are not 32/64.

Not covered by #41834 / #53055 (those PRs do not change this call). Not a blanket `is_deep_gemm_supported() = False` on family 120.

## Test Plan

```bash
pytest tests/v1/attention/test_indexer_paged_mqa_metadata.py -q
```

## Test Result

CPU unit test with mocked `is_deep_gemm_supported` / `is_cuda`. 2x DGX Spark GB10 overlay skips this metadata fill; decode uses FlashInfer sparse MLA.

## The zeroing itself

The PR tests do not look at buffer contents, so I added a probe that builds each page twice and reads `schedule_metadata` back. A plain run cannot tell `torch.empty` from `torch.zeros`, because fresh CUDA memory in a new process tends to already be zero, so the probe first fills and frees 16 MiB of small-pool blocks with a sentinel (`12345`) so that later small allocations land on dirty memory. The control is the same image with only `torch.zeros` reverted to `torch.empty`.

| image | page | buffer non-zero at init | `schedule_metadata` after build 1 / build 2 |
|---|---|---|---|
| `6624a12` (`torch.zeros`) | 64 states | 0 | filled by DeepGEMM (same storage as buffer) |
| `6624a12` (`torch.zeros`) | 2 states | 0 | all zero / all zero |
| gate + `torch.empty` | 64 states | 98 of 98 | filled by DeepGEMM, sentinel fully overwritten |
| gate + `torch.empty` | 2 states | 98 of 98 | **98 of 98 are `12345`** / same |

So without this commit the skip path really does hand stale memory downstream, and with it the returned buffer is zero on every step. On the 64-state page the full `(num_sms + 1, 2)` slice is overwritten, so the initial contents never matter there.
