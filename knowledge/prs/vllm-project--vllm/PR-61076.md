# [RL] Add configurable staging and parallel stage pulls to sharded RDT

[Upstream PR](https://github.com/vllm-project/vllm/pull/61076) · state: open · merged: False

## Original PR description

## Purpose

The sharded-RDT consumer currently follows one ordered pull plan. Under trainer
pipeline parallelism, increasing ring depth overlaps chunks but does not
sustain pulls from several independent stages. More parallelism also multiplies
the GPU receive-slot memory.

This PR adds two independently configurable controls:

- `staging_device`: receive into GPU HBM or pinned host memory;
- `stages_in_flight`: pull independent owner-connected stage streams in
  parallel, with K `num_rdt_buffers` slots per active lane.

Defaults remain GPU staging and one stage in flight. The PR also carries the
required free-signal epoch, quant-stream lifetime, bounded slot-wait, and
transactional re-init fixes. GPU staging retains Ray >=2.56; host staging
requires Ray >=2.58.

This builds on the original sharded-RDT implementation in
[vLLM#43375](https://github.com/vllm-project/vllm/pull/43375).

## Test Plan

1. Run existing and new sharded-RDT unit/CUDA suites on one H100.
2. Run the four-GPU Ray/NIXL example with GPU and host staging.
3. Run Ruff, formatting, and diff checks.

## Test Result

- **301 passed, 3 deselected, 0 failed** on one H100 with Ray 2.58 and
  torch 2.13. The deselected pre-existing real-model cases require the full
  repository fixture.
- Real NIXL-UCX transfer passed on four H100s with both GPU and pinned-host
  staging: the first sync changed generation and the second reproduced it.
- Ruff, Ruff format, and `git diff --check` pass.

Measured large-model results:

- **Qwen3-235B-A22B**, two trainer nodes: S=P reduced sync wall by **19%,
  29%, and 49%** at PP 2, 4, and 8. At PP=8, host S=8 reached **3.86 s**
  versus **7.54 s** for serial pulls; GPU S=8 ran out of HBM.
- **Kimi-K2**, the published 48-node shape (32 trainer, 16 inference, four
  replicas): host S=8 reached **4.30 s** versus **7.53 s**, a **43%**
  reduction.

These large-model numbers predate the upstream refactor; the current-vLLM
evidence above validates the port and real GPU/host transport paths.

## Known limitations

- The real current-vLLM smoke has uniform ownership and one stage stream. S>1
  scheduling is covered by deterministic tests and the recorded multi-stage
  runs above.
- Receive memory is `effective_lanes * num_rdt_buffers * rounded_slot_size`.
  GPU slots remain outside `gpu_memory_utilization`; host mode moves that pool
  to pinned memory.
