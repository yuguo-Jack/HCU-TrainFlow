## Purpose
Fix cleanup on failure paths in the CuMem pluggable allocator.

`my_malloc()` reserves CUDA virtual address space and prepares CUmem handle metadata before returning memory to PyTorch. Several failure paths could leave reserved VA, CUmem handles, mapped memory, or Python-side allocation records behind when allocation setup fails.

This is not a duplicate: I searched existing open PRs for `cumem allocator`, `cuMemMap`, `cuMemSetAccess`, and `my_malloc` cleanup and did not find an active PR covering these failure paths.

AI assistance was used to inspect failure paths and prepare the patch. I reviewed the changed code.

<summary>Fix cleanup on failure paths in the cumem pluggable allocator.

`my_malloc()` reserves a CUDA virtual address and allocates handle metadata before invoking the Python allocation callback and mapping the allocation. Several early-return paths could previously leave the reserved address or created CUmem handle unreleased.

This change:
- releases the CUmem handle if `cuMemMap()` fails after `cuMemCreate()`
- unmaps and releases handles if `cuMemSetAccess()` fails after mapping
- frees reserved VA / C metadata if Python callback setup or invocation fails
- mirrors the cleanup for ROCm chunked allocation metadata paths

File: `csrc/cumem_allocator.cpp` · line 200

`cuMemUnmap` is a Driver API call that typically takes a `CUdeviceptr` (not `void*`). Building `void* unmap_addr` risks a compile-time type error or incorrect address conversion depending on how `CUdeviceptr` is defined under `USE_ROCM`. Prefer computing an address value in the same type expected by `cuMemUnmap` (e.g., use `CUdeviceptr` for address arithmetic, or cast to the exact `cuMemUnmap` parameter type in this build) to avoid ABI/type mismatches.

- copilot-pull-request-reviewer · comment · 2026-06-08T10:53:46Z · [source](https://github.com/vllm-project/vllm/pull/44866#discussion_r3372623529)

File: `csrc/cumem_allocator.cpp` · line 492

On `PyObject_CallObject` failure, the args tuple (`arg_tuple`) still needs to be decref'd (since the call does not steal a reference). If `Py_DECREF(arg_tuple)` happens later on the success path, this early return will skip it and leak a Python reference. Add a `Py_XDECREF(arg_tuple)` (or `Py_DECREF` if guaranteed non-null here) before releasing the GIL / returning.
