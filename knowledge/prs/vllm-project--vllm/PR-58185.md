# [Bugfix][Offload] UVA offload: allocate exact-size pinned host memory instead of Tensor.pin_memory()

[Upstream PR](https://github.com/vllm-project/vllm/pull/58185) · state: closed · merged: False

## Original PR description

## Purpose

Fixes the first half of #58178. Fixes #56410 (same bug, reported earlier by @raj-parihar).

Related: #56413 (@Vaishnavi220506) drops the same `pin_memory()` call in `wrap_modules`; this PR overlaps that hunk and additionally covers the re-offload in `device_loading_context`, adds the opt-in, and carries the GB300 measurements below.

`UVAOffloader.wrap_modules` pins each offloaded parameter with `Tensor.pin_memory()`, which goes through PyTorch's CachingHostAllocator and rounds every allocation up to the next power of two. For MoE expert tensors that is a 33–45% host-memory tax the log never shows: a 4.5 GiB `w13_weight` occupies 8 GiB of host memory, and `--cpu-offload-gb 305` consumed ~504 GiB on a 494 GiB Grace host and was OOM-killed mid-load, while the log reported "Total CPU offloaded parameters: 305 GiB".

`get_cuda_view_from_cpu_tensor()` (`csrc/libtorch_stable/cuda_view.cu`) already handles an *unpinned* input by allocating exact-size mapped pinned memory with `cudaHostAlloc` and copying into it — the view is pinned either way. This PR hands the unpinned CPU tensor straight to it on the UVA path, and does the same in `device_loading_context`'s re-offload after `process_weights_after_loading`. The non-UVA fallback path (`VLLM_WEIGHT_OFFLOADING_DISABLE_UVA`) keeps `Tensor.pin_memory()` as before, since there the tensor is what the GPU copies from.

**Opt-in to the old pinning.** Exact-size is the default because it is the only behavior that honors `--cpu-offload-gb`. `VLLM_WEIGHT_OFFLOADING_UVA_CACHING_PIN=1` restores `Tensor.pin_memory()` on the UVA path for users who have the host headroom. On the DSV4.1-Flash / GB300 A/B below it gives back about 2.5% decode, at the cost of power-of-two host rounding. `VLLM_WEIGHT_OFFLOADING_DISABLE_PIN_MEMORY` is now documented as not affecting the default UVA path, since the default already takes the exact-size branch it used to select. It still governs the non-UVA fallback and the opt-in.

Not changed here: the re-offload after `process_weights_after_loading` still makes a second host copy of the repacked tensor; that's the second half of #58178 and a separate change.

## Test Plan

In-process `LLM(...)` on a DGX Station GB300 (494 GiB Grace host), `XiaomiMiMo/MiMo-V2.6-Pro-RL` truncated to 16 layers (`hf_overrides={"num_hidden_layers": 16}`, needs #58184), `--offload-backend uva --cpu-offload-gb 40 --cpu-offload-params routed_experts.w13_weight routed_experts.w2_weight`, `--moe-backend marlin`. Read `/proc/meminfo` before construction and after load; report `(MemTotal − MemAvailable)` delta. Page cache dropped between runs.

Parity: forward hooks dumping the last-token residual after every decoder layer for a fixed prompt, stock vs this PR.

## Test Result

| configuration | host memory used by the load |
|---|---|
| `main`, default env (`Tensor.pin_memory()`) | **90.3 GiB** |
| `main`, `VLLM_WEIGHT_OFFLOADING_DISABLE_PIN_MEMORY=1` (takes the `cudaHostAlloc` branch today) | 57.8 GiB |
| this PR, default env | **58.4 GiB** |

40 GiB of experts offloaded in every row; the 32 GiB difference is the power-of-two rounding.

Output parity: per-layer residuals bit-identical to `main` (max abs diff `0.0` over all 16 layers); first-token top-5 unchanged. Full 70-layer model with 320 GiB offloaded loads on the same box with 126 GiB host free and serves correctly (that boot used the env-var route; this PR makes it the default behavior).

**Decode cost** ([full data](https://github.com/vllm-project/vllm/pull/58185#issuecomment-5833189800)). DeepSeek-V4.1-Flash, 1× GB300, off60 routed experts, nightly `dee37d89`. Nine sequential boots, page cache dropped before each, same saved autotune set:

| | host shmem | C1 tok/s | C16 tok/s | load |
|---|---|---|---|---|
| stock (3 boots) | 380.2 GiB | 91.0 | 420.4 | 192–194 s |
| this PR, default (4 boots) | **325.4 GiB** | 88.8 (−2.5%) | 409.8 (−2.5%) | 201–204 s |
| this PR + `VLLM_WEIGHT_OFFLOADING_UVA_CACHING_PIN=1` | 380.2 GiB | 91.5 | 425.1 | 192 s |

The default costs ~2.5–2.8% decode at every concurrency 1–16. The opt-in returns to stock memory and speed. Greedy parity (18 prompts): 8 of 9 boots were byte-identical to stock, and one PR boot differed on one tool-call prompt (still a valid call; two other boots of the same code were identical). The mechanism for the decode gap is not known yet; both paths end up pinned and mapped. Tested on one Grace-Blackwell box only.

`ruff check` / `ruff format --check` clean on all changed files. New test: `test_cpu_offload_uva_caching_pin` (output equality with the opt-in on).

- jmeadlock · comment · 2026-09-25T13:27:29Z · [source](https://github.com/vllm-project/vllm/pull/58185#issuecomment-5833189800)

The description only reports memory, so here is decode throughput on a real offload workload.

**Setup:** DeepSeek-V4.1-Flash on one GB300 (DGX Station, Grace-Blackwell C2C). Image `vllm/vllm-openai:nightly-dee37d89`, `--offload-backend uva --cpu-offload-gb 60` (routed experts only), plus Engram host tables, fp8_ds_mla KV, and DSpark MTP k=[[1,4,5],[5,24,1]]. Every arm loads the same saved FlashInfer autotune set. The arms ran one after another on the same box, with the page cache dropped before each boot, in the order A1 B1 C1 A2 B2 A3 B3:
- **A**: stock image
- **B**: this PR. The patched files are the nightly's own `uva.py` and `model_loader/utils.py` with this diff applied (`patch -p1`), bind-mounted in; file hashes were checked inside the running container.
- **C**: stock with `VLLM_WEIGHT_OFFLOADING_DISABLE_PIN_MEMORY=1`, which is the existing exact-size `cudaHostAlloc` route.

**Host memory** (container cgroup `shmem` after boot): A 380.2 GiB, B 325.4 GiB, so **−54.8 GiB** for 61.2 GiB of offloaded parameters. B and C are identical to the byte, and all three A runs were identical to each other.

**Decode throughput** (aggregate tok/s, mean of 3 reps per arm):

| conc | A1 | A2 | A3 | B1 | B2 | B3 | C1 | mean B vs mean A |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 90.1 | 91.8 | 91.1 | 88.7 | 88.7 | 88.9 | 88.4 | −2.5% |
| 2 | 123.3 | 126.2 | 125.2 | 121.5 | 121.3 | 121.8 | 121.0 | −2.7% |
| 4 | 166.4 | 170.6 | 169.0 | 163.4 | 164.2 | 164.4 | 163.1 | −2.8% |
| 8 | 300.2 | 307.6 | 304.4 | 295.7 | 295.3 | 296.3 | 295.0 | −2.7% |
| 12 | 365.4 | 375.6 | 371.6 | 360.4 | 359.8 | 361.4 | 359.7 | −2.8% |
| 16 | 412.8 | 426.3 | 422.2 | 410.9 | 408.7 | 409.7 | 411.7 | −2.5% |

At every concurrency, and on each of five fixed single-stream prompt types, the fastest PR run is slower than the slowest stock run. The stock boots spread by 2–3%, while the PR boots agree to within 0.5%. I read this as a small but real cost of **about 2.5–2.8% decode** on this box. The existing no-pin env var shows the same cost, which is expected since it takes the same path. There is no sign of drift: B3, run last, matches B1, run second. SM clock (2070 MHz) and power (~360–366 W) were the same in every arm. A separate mixed replay workload was too noisy to tell the arms apart (reps within one arm differ by ~25%).

I don't have a mechanism for the decode gap yet, since both paths end up pinned and mapped. Load is also ~5% slower on the exact-size path (192–194 s vs 201–203 s), probably from the per-tensor `cudaHostAlloc`. All of this is one model on one Grace-Blackwell box; I haven't tested PCIe hosts.

**Outputs:** on an 18-prompt greedy parity set (seed 42, 256 tokens), 6 of 7 arms were byte-identical to stock, including B1 and B3, which run the same code. B2 differed on one prompt: an agent tool-call prompt came out with different wording, but was still a valid tool call. Since the same code gave identical output on the other two boots, this is not a code-path determinism change. With a single occurrence, I can't separate kernel nondeterminism from anything else.

**Where I land:** exact-size should be the default, because it is the only behavior that actually honors `--cpu-offload-gb`. The caching allocator's power-of-two rounding can overshoot the budget by nearly 2x per tensor (a 4.5 GiB expert tensor takes 8 GiB), and that hits exactly the hosts where people turn on offload because memory is tight. I'll follow up with (1) an explicit opt-in to keep the old caching-allocator pinning for anyone who has the headroom and wants the ~2.5%, and (2) a docs update, since `VLLM_WEIGHT_OFFLOADING_DISABLE_PIN_MEMORY` no longer changes anything on the UVA path. I'll also put these numbers in the PR description. If maintainers would rather flip the default, I'll do that.

- jmeadlock · comment · 2026-09-26T03:43:22Z · [source](https://github.com/vllm-project/vllm/pull/58185#issuecomment-5842869239)

Measured the release question rather than asserting it. Same GB300 box, same nightly image with this branch's files bind-mounted.

**Primitive** (4 GiB bf16 tensor, 4 alloc/free cycles in one process, container cgroup `memory.current`):

| path | while alive | after `del` + `gc.collect()` | after 4 cycles |
|---|---:|---:|---:|
| exact-size `cudaHostAlloc` via `get_accelerator_view_from_cpu_tensor` (this PR's default) | +8.2 GiB (pageable source + pinned copy, transient) | back to baseline | **+0.18 GiB** |
| `Tensor.pin_memory()` (stock / `VLLM_WEIGHT_OFFLOADING_UVA_CACHING_PIN=1`) | +4.0 GiB | **+4.0 GiB** | +4.0 GiB, unchanged after `empty_cache()` |

The exact-size buffer is owned by the CUDA view's storage and is freed as soon as the parameter is dropped. The caching-allocator path keeps the pinned blocks in `CachingHostAllocator`'s cache after the tensors are gone, so an in-process release (the #57834 shape) only actually returns host memory on the exact-size path.

**End to end** (`facebook/opt-1.3b`, `cpu_offload_gb=2`, `offload_backend=uva`, `del llm`, sample cgroup for 30 s): residual after shutdown is +0.63 GiB on the default path and +0.66 GiB with the opt-in — the same, and it is not offload memory (EngineCore is a separate process, so exit frees both paths regardless). No leak in either mode.
