# [Perf][Attention] DiffKV: group spec-verify only when the split-KV grid is large

[Upstream PR](https://github.com/vllm-project/vllm/pull/58141) · state: open · merged: False

## Original PR description

## Purpose

This replaces the earlier version (one token per split-KV program with an SM-count bound), which #59085 supersedes.

#59085 groups a whole spec-decode verify into one split-KV program. For a single request that leaves `num_kv_heads × segments` programs, fewer than the SMs on GB10 (32 vs 48). This keeps the default tile while `q.shape[0] × num_kv_heads × segments ≤ 4 × SMs` and groups beyond that. The threshold is measured on GB10 only.

## Test Plan

```bash
pytest tests/kernels/attention/test_triton_unified_attention_diffkv.py
```

Kernel benchmark and serving on DGX Spark (GB10), vLLM main 02d8a94e + #59085: MiMo-V2.6-Flash-RL, TP2 across two nodes, DFlash (k=3), BF16 KV.

## Test Result

Kernel tests on GB10: 100 passed, 96 skipped (the FA-reference test needs FA3/FA4). The launcher test mocks the SM count, which now decides the grouping.

Kernel speedup vs #59085 for a single request (32 query / 2 KV heads, QK/V 192/128, CUDA graphs, 16K–128K KV): 1.29x at 4 query tokens, 1.12x at 2. Two or more requests and 8-token verifies are unchanged.

Serving vs #59085 (5 server starts per arm): one request at 128K context −1.9% time per decode step (p = 0.002). 64K and two concurrent requests unchanged.

AI-assisted (Claude). I have reviewed the code.

- hclsys · comment · 2026-09-26T02:12:17Z · [source](https://github.com/vllm-project/vllm/pull/58141#issuecomment-5842272430)

Ran this on my own GB10 (sm_121, 48 SMs, CUDA 13). Your test suite gives `5 passed, 96 skipped` here too. Correctness holds, perf reproduces, and one question at the end.

**2D vs split-KV on the same inputs**, eager, `out` pre-filled with NaN so an unwritten row shows up:

```
1 req x 4 tok    KV 1024        max|d| 9.8e-04
2 req x 4 tok    KV 4096/1000   max|d| 9.8e-04
4 req x 4 tok    ragged KV      max|d| 7.8e-03
[1,4,2,4] tok    ragged KV      max|d| 3.9e-03
kv_len == qlen                  max|d| 0
kv_len = 1 (graph dummy)        max|d| 0
```

I printed `use_3d` on both legs before trusting any of that — with the scratch passed but the bound not met you get 2D twice and the comparison means nothing.

**The `-inf` guard is load-bearing, and your test catches it.** Deleted just that line and re-ran:

```
graph dummy kv1   ->  NaN in the split-KV leg
mixed w/ kv1      ->  NaN in the split-KV leg
pytest            ->  1 failed (test_diffkv_multitoken_splitkv[16-seq_lens2-8-32-True])
```

So `seq_lens2` is actually covering the no-causal-keys row rather than passing incidentally. Worth stating because that case is easy to write and have it not bite.

**Speedup, best of 50, eager (no CUDA graphs):**

```
batch    KV1K   KV4K   KV16K   KV64K
1x4     1.46x  2.76x   4.21x   6.06x
2x4     1.31x  1.98x   2.98x   3.41x
4x4     1.05x  1.41x   1.92x   2.08x
```

Above 16K I'm a bit higher than your table, at 1K–4K clearly lower — mine is eager, so the two extra launches of the split-KV path are inside my measurement and dominate at 0.06 ms. Your graph-captured numbers are the fairer ones for the small-KV end. I added 4x4 since you stopped at 2x4: still 1.05–2.08x, and 1.05x at 4x4/KV1K is right where `q.shape[0] * num_kv_heads = 32` approaches the 48 SMs, which is the bound doing its job.

Also checked the bound is the right shape: the scratch is allocated `[seq_threshold_3D, num_heads_q, segments, ...]` in `triton_attn.py`, so it really is token-indexed and `q.shape[0] > seq_threshold_3D` is the correct guard where `num_seqs >` used to be.

**One question.** The new early return in the reducer means CUDA-graph padding rows (grid is `q.shape[0]`, real tokens are `cu_seqlens_q[num_seqs]`) are now left untouched in `out`, where before they were written. With a persistent graph output buffer that turns them from garbage into *stale from the previous step*. I can't tell from the kernel whether anything downstream can read past `cu_seqlens_q[num_seqs]` — if you've already confirmed nothing does, say so in the comment, since it now matters for the decode path too and not just the multi-token one.


- peperunas · comment · 2026-09-28T15:08:57Z · [source](https://github.com/vllm-project/vllm/pull/58141#issuecomment-5872784444)

Downstream measurement from an SM120 deployment (46K context, TP2) running the same enablement by a different route: one program covers a whole verify (BLOCK_M = q_len x 16, capped at 128) instead of one query token per CTA, and full-attention groups run 64 split-KV segments so the segment axis supplies the CTAs. Our kernel row — which bundles that with prefill BLOCK_M 128 and 8 warps and per-tensor E4M3 K/V — measured decode 87–94 → 156–175 tok/s and prefill 6.2K → 8.5K tok/s. This PR deliberately stops at one token per CTA behind an SM-count bound, so a q=8 verify still re-reads the KV prefix once per token; please say that explicitly in the description so reviewers don't read this as the whole fix, or take the whole-verify BLOCK_M as a follow-up.

*Posted by a downstream user; the numbers come from our deployment's patch set and bundle several changes, so no single change owns them.*
