# [Bugfix][Offloading] UVA offloader: release the accelerator blocks it frees

[Upstream PR](https://github.com/vllm-project/vllm/pull/54972) · state: open · merged: False

## Original PR description

## Purpose

Fixes an OOM that makes UVA CPU offload ineffective: with `--offload-backend uva --cpu-offload-gb N`, loading OOMs part-way through the model **no matter what `N` is**. On a 96 GiB card loading a 181 GiB checkpoint it dies around layer 22 with `expandable_segments: memory mapping failed`.

**Root cause.** `UVAOffloader._maybe_offload_to_cpu` moves a parameter to host and rebinds `p.data` to a host view. That drops the last reference to the accelerator storage — but the caching allocator keeps the freed block. Under `PYTORCH_ALLOC_CONF=expandable_segments:True` it then extends the segment for the *next* module rather than reusing what was just freed, so reserved memory grows with every offloaded module while live memory does not.

The offload therefore frees nothing that the rest of the engine (KV cache, activation workspaces, CUDA graphs) can use — sizing decisions downstream read `mem_get_info`, which counts those retained blocks as used.

**Fix.** One `torch.accelerator.empty_cache()` after a module has had parameters offloaded — matching the idiom already used in `v1/worker/`. It runs once per offloaded module, during load only.

The placement is load-bearing: `make_layers` hands `wrap_modules` a lazy generator, so module N+1 is constructed *after* N is offloaded. Releasing once at the end of `wrap_modules` would be simpler but too late to prevent the mid-load OOM.

CPU only — no accelerator required. `tests/model_executor/test_uva_offloader.py` drives the real `UVAOffloader` under `FakeTensorMode` with UVA and pin-memory disabled, and `torch.accelerator.empty_cache` monkeypatched to append to an event log, so the release is observed by its interleaving with module construction rather than by inspecting allocator counters.

- `test_offload_releases_blocks_before_next_module` — pins the interleaving, which is what the fix is actually about.
- `test_no_release_when_nothing_offloaded` — over-correction guard: a module whose parameters do not match `cpu_offload_params` freed nothing and must not flush the device cache.

Hardware measurement — GLM-5.3-Flash, 181.3 GiB NVFP4 checkpoint (163 GiB of it routed MoE experts), 43 MoE layers, RTX PRO 6000 Blackwell 96 GiB, `--offload-backend uva --cpu-offload-params experts`:

| | per offloaded MoE layer |
|---|---|
| `torch.cuda.memory_reserved` growth | **4.06 GiB** |
| `torch.cuda.memory_allocated` growth | 0.30 GiB |

`reserved - allocated` tracked the cumulative offloaded bytes exactly. Extrapolated over 43 MoE layers that is ~175 GiB reserved on a 96 GiB card — hence the mid-load failure at any `--cpu-offload-gb`.

With the release call, reserved tracks allocated (4.44 vs 4.40 GiB at the same point) and the model loads and serves.

No model evaluation is included: the change frees already-dead allocator blocks and does not touch any computation, so outputs are unaffected.

## Scope

`PrefetchOffloader` (`vllm/model_executor/offloader/prefetch.py:657`) drops GPU storage the same way and iterates the same lazy generator, so it is likely to show the same reserved-memory growth under `expandable_segments`. I have not reproduced it there, so I have left it out rather than change a backend I cannot test. Happy to extend if a maintainer wants it in the same PR.

## Alternatives

Happy to move the call if a maintainer prefers different placement — e.g. amortised every N modules, or gated on `reserved - allocated` exceeding a threshold, if a per-module `empty_cache` is considered too heavy for the load path.

## Duplicate work

Several other open PRs touch `vllm/model_executor/offloader/uva.py`. None
addresses this bug, so this is not duplicate work, but they will conflict
textually and I am happy to update this branch against whichever lands first.
Re-checked 2026-10-10: the diffs of #54610, #46690, #57472, #58185 and #53981
add no `empty_cache()` or other release of the freed blocks.

- **#54610** — "[Bugfix][Offloader] Prioritize sparse MoE experts in UVA CPU
  offloading". It changes *which* parameters get offloaded: `wrap_modules`
  becomes a two-pass priority loop and `_maybe_offload_to_cpu` is rewritten.
  It does not touch the caching allocator, so the reserved-memory growth
  measured above survives it unchanged — if anything #54610 makes this OOM
  easier to hit, because it deliberately offloads more expert weight. The
  overlap is textual and direct: this PR's release call sits inside
  `_maybe_offload_to_cpu`, and on top of #54610 it would need to hold for
  both of its passes.
- **#46690** — "[Bugfix] Fix UVA offload fallback copies". It fixes the
  non-UVA fallback forward path (a forward proxy, a `functional_call` state
  snapshot that avoids calling `state_dict()` in forward, and a lock). It
  adds no `empty_cache()` and no other release of the blocks an offload
  frees. It also creates `tests/model_executor/test_uva_offloader.py`, which
  this PR creates as well, so the test file will conflict too.
- **#57472**, **#58185**, **#53981** — other UVA offload fixes (the
  `--cpu-offload-gb` budget, exact-size pinned host memory, directly
  constructed embeddings). Different defects; the overlap is textual only.

The bug fixed here is orthogonal to both. It is about what the caching
allocator does with storage that an offload has *already* freed — whichever
parameters were selected, and whichever forward path runs afterwards.
