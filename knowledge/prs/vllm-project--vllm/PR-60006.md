# [Docs] Rewrite the preload (`ipc_cache`) guide and add Docker/Kubernetes usage

[Upstream PR](https://github.com/vllm-project/vllm/pull/60006) · state: open · merged: False

## Original PR description

## Overview

Rewrites `docs/features/preload.md` (the `vllm preload` / `--load-format ipc_cache` weight cache daemon) around the operator workflow and adds the missing Docker and Kubernetes guidance, plus pointers from the Docker deployment guide, the faster-startup list and the CLI reference.

## Claims

- Documents how to run the daemon and the engine in separate containers: a Docker `run` pair, a Docker Compose file gated on the daemon's health check, a scoped-namespace alternative, and the reason behind each requirement (`--ipc=host`, `--pid=host`, shared socket volume, same GPUs/UID/image tag, `--entrypoint vllm`).
- Documents the Kubernetes pattern: GPU device plugins allocate a GPU to one container, so the daemon and a `vllm serve` restart loop run in one container with startup/liveness probes on the daemon's health port and readiness on the engine.
- Documents previously undocumented behaviour: the `/health` readiness endpoint (`--weight-cache-health-port/-host`), the `fallback: false` wait, GPU memory accounting of daemon-held weights, the cold-start ordering pitfall, and a troubleshooting table keyed on the actual error strings.
- Corrects stale or wrong statements: pipeline parallelism was listed as rejected but the daemon plans PP ranks; `copy` mode was described as reusable per restart but the daemon releases its cache after the first handoff; the quantization support list now matches the `supports_pre_processed_weights` declarations (unquantized, `fp8`, ModelOpt NVFP4, MXFP4 except GPT-OSS).

The rendered `features/preload/` page has all 14 sections, 4 tables, 11 code blocks and both admonitions; the embedded Compose and Kubernetes YAML parse; every relative link and anchor resolves. Every statement about behaviour was checked against `weight_cache/daemon.py`, `ipc_loader.py`, `protocol.py`, `cli/preload.py` and `v1/worker/gpu_worker.py`.

**Not validated:** the Docker and Kubernetes examples were not executed on GPU hardware. The namespace requirements follow from the mechanism (legacy CUDA IPC handles are bound to the exporting process's PID namespace, see [openucx/ucx#11978](https://github.com/openucx/ucx/issues/11978) and [this NVIDIA forum thread](https://forums.developer.nvidia.com/t/cuda-ipc-sharing-across-containers/274989); PyTorch's reference counters for shared CUDA tensors are shared-memory files, so `/dev/shm` must be shared). A two-container run on a GPU host would confirm them before merge.

## Details

- `docs/features/preload.md`: restructured into requirements, quick start with the expected log lines, how it works, memory accounting, cache modes, health endpoint, Docker, Kubernetes, loader/daemon configuration tables, multi-node/DP, speculative decoding, security, lifecycle, troubleshooting.
- `docs/deployment/docker.md`: new "Keep model weights in GPU memory across engine restarts" section with the two-container example, linking to the full guide.
- `docs/configuration/optimization.md`: preload added as a fourth faster-startup mechanism.
- `docs/cli/README.md` and the `preload.py` module docstring: supported-parallelism wording updated; the CLI summary now lists the health and socket-dir flags.

**Duplicate-work check:** no open upstream PR documents preload for Docker/Kubernetes (`gh pr list --search "preload ipc_cache"` equivalent returned only #59648 and #59813, both bugfixes). Two open upstream PRs touch facts this guide states and will need a one-line reconcile if they land first: vllm-project/vllm#59648 changes the checkpoint fingerprint from safetensors headers to sampled tensor bytes, and vllm-project/vllm#56999 adds XPU support (the guide says CUDA/ROCm only, matching current `check_ipc_platform_support`).

AI assistance (Claude Code) was used to draft this PR; the submitting human has to review every line and run the Docker example before upstreaming.
