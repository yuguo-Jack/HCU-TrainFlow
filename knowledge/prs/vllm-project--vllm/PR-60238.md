# [Multimodal] Skip encoder towers on later PP stages under V2

[Upstream PR](https://github.com/vllm-project/vllm/pull/60238) · state: open · merged: False

## Original PR description



## Overview

Model Runner V2 runs multimodal encoders on the first pipeline stage only, but every stage still builds and loads the encoder towers. This skips them on the later stages through the existing `_mark_tower_model` path.

## Claims

- With PP under V2, later stages no longer allocate or load encoder towers: PP1 model loading drops by the tower size (0.58 GiB on LLaVA-1.5-7B, 0.62 GiB on Qwen3.5-4B, 0.85 GiB on Qwen3.6-35B-A3B, 1.27 GiB on Ultravox v0.5).
- Outputs are unchanged: image outputs under PP match HF in the new `llava-pp-broadcast` case, and the existing PP comparison tests pass.
- PP=1, the first stage and the V1 runner are unchanged.

## Validation

All runs on main (`6ad2e06c4a`) with and without this commit, two sm_80 GPUs, V2 runner, FlashInfer sampler off.

```text
pytest tests/models/multimodal/generation/test_common.py -k llava-pp-broadcast        # 1 passed (main and this change)
pytest tests/distributed/test_pipeline_parallel.py -k test_tp_multimodal_generation   # 3 passed (main and this change)
pytest tests/models/qwen4_exp/test_config.py                                          # 9 passed
```

`llava-pp-broadcast` is the existing `llava-broadcast` image test (outputs compared against HF) with PP=2 instead of TP=2. It checks short eager image generations under PP; it passes on main too, so it does not guard the memory saving, which the loading numbers below show. `test_tp_multimodal_generation` compares text completions only; it does not send image or audio inputs. Ultravox's Llama-3.2-1B-Instruct backbone is gated for this account, so it was taken from the ModelScope mirror, checked byte-identical to the Hugging Face repository at `9213176726` by file hashes, and run offline.

PP0 / PP1 model loading:

| Model | main | this change | without PP |
|---|---|---|---|
| LLaVA-1.5-7B (`llava-pp-broadcast`) | 6.86 / 6.86 GiB | 6.86 / 6.28 GiB | |
| InternVL3-1B | 1.17 / 1.17 GiB | 1.17 / 0.59 GiB | 1.76 GiB |
| Ultravox v0.5 (Llama 3.2 1B) | 2.68 / 2.68 GiB | 2.68 / 1.41 GiB | 3.59 GiB |

What remains above the single-stage size on Ultravox is the input embedding and LM head that PP keeps on separate stages.

Serving Qwen3.5-4B (BF16) and Qwen3.6-35B-A3B-NVFP4 with PP=2 (`--max-model-len 16384 --max-num-seqs 8`), five greedy chat requests (two text, two with one image, one with two images) with logprobs; main was served twice per model:

| | Qwen3.5-4B main | this change | Qwen3.6-35B-A3B main | this change |
|---|---|---|---|---|
| PP1 model loading | 5.27 GiB | 4.65 GiB | 11.28 GiB | 10.43 GiB |
| PP1 memory in use (`nvidia-smi`) | 58,612 / 58,632 MiB | 57,960 MiB | 58,824 / 58,852 MiB | 57,970 MiB |
| PP0 model loading | 5.27 GiB | 5.27 GiB | 11.01 GiB | 11.01 GiB |
| KV cache | 2,746,044 tokens | 2,746,044 tokens | 3,349,038 tokens | 3,349,038 tokens |

Qwen3.5-4B is identical in tokens and logprobs on all five requests across both main runs and this change. Qwen3.6-35B-A3B is not deterministic on main itself (the two main runs diverge on two requests, at tokens 47 and 119); against the second main run this change diverges on the other two (tokens 14 and 120) and the remaining three have the same tokens with slightly different logprobs, so these runs do not separate the effect of the change from run-to-run noise on that model. The KV cache is sized by PP0, which still holds the tower, so it does not grow there; the first main run of each model compiled from a cold cache and is left out of the KV row.

The compiled extensions came from a build that adds two unrelated kernels to main's sources; no kernel these models use differs from main.

## Details

`_mark_tower_model` already builds a tower on the meta device and wraps it in `StageMissingLayer` when `--limit-mm-per-prompt` is 0 for all of its modalities, and `AutoWeightsLoader` skips the weights of a `StageMissingLayer`. This adds a second condition to the same skip: the V2 runner and not the first stage. Under V2 the encoder only runs where `supports_mm_inputs and is_first_pp_rank` holds; the encoder cache, the encoder runner and the encoder CUDA graphs only exist on the first stage, and no `get_mrope_input_positions` implementation, which every stage runs, touches a tower. V1 is left out because its `profile_run` calls `embed_multimodal` on every rank.

Models that branch on a missing tower: Qwen3-VL, Qwen3-VL-MoE and Qwen3-Omni turn `use_deepstack` off on later stages, which do not use it since deepstack inputs are consumed on the first stage, and their PP `start_layer` check reads the config, so it still runs. Qwen4Exp gated that check on `use_deepstack`, so it is gated on image or video input being enabled (`get_limit_per_prompt`) instead. That is exactly when `use_deepstack` could be true before; the condition taken from both the NVIDIA and AMD files gives the same result as main in all 64 combinations of `language_model_only`, image and video limits, deepstack levels and `start_layer`. Pixtral and Llama 4 only use a missing tower to skip its weights.

About 100 model files build their towers through this helper; the GPU runs above cover the models listed. The new test case inherits `llava-broadcast`'s two-GPU mark and runs wherever that case runs.

No open PR covers this: searches for `_mark_tower_model`, `StageMissingLayer` and pipeline-parallel encoder or tower changes return nothing related.
