# [Bugfix][Core] Requeue encoder-stalled waiting requests

[Upstream PR](https://github.com/vllm-project/vllm/pull/59030) · state: open · merged: False

## Original PR description

## Purpose

A waiting request can end a scheduling pass with `num_new_tokens == 0`: its encoder inputs do not fit the cache or the compute budget, or the prefill-lookahead reserve consumes the tokens. The waiting loop `break`ed there, so the request kept its head-of-queue position and every request behind it went unscheduled for that step — repeating on every step while the resource condition holds.

It is now requeued with `skip_request()`, which preserves the drain-first priority of requests holding KV blocks (async KV-load resumes) and the `deferred_waiting` accounting.

The self-pinned encoder-cache release from the earlier revision is dropped here; #60553 proposes that.

### Duplicate-work check

Searched open issues and PRs for waiting-queue requeue / head-of-line blocking and encoder cache stalls. No open PR touches this path; the nearest matches are #56826 and #57368 (encoder input lifetimes across steps — different concern), #40707/#40709 (mamba split deadlock — different path), and umbrella EPD tracker #52409.

- gty111 · COMMENTED · 2026-10-02T02:24:48Z · [source](https://github.com/vllm-project/vllm/pull/59030#pullrequestreview-5387715110)

Thanks for the fix — the stall analysis matches what we observe. Four issues to address before merge:

**1. (Queue integrity) Please use `skip_request()` instead of the manual pop+prepend.** The manual requeue sends every stalled request to `step_skipped_waiting`. Requests holding KV blocks (e.g. async KV-load resumes) must instead go to `step_skipped_kv_holding` to keep their drain-first priority next pass, and `deferred_waiting` accounting is skipped entirely here. `skip_request()` already handles both.

**2. (Coverage) The requeue only fires for requests with encoder inputs.** The PR body says the zero can also come from `_reserve_prefill_lookahead`, but the `encoder_inputs_to_schedule is not None` condition excludes that: a request without encoder inputs zeroed by lookahead still hits `break` and starves the queue. Either cover that case or narrow the description.

**3. (Release condition) `_release_consumed_encoder_inputs` is more aggressive than the per-step `_free_encoder_inputs`.** The latter also accounts for `spec_lookahead` and `num_output_placeholders`; this helper frees any item with `offset + length <= num_computed_tokens`. With speculative decoding, an item at the frontier can be released while the drafter's gather/rejection may still reference it. Suggest aligning the condition with `_free_encoder_inputs` — the deadlock is still resolved, just one pass later.

**4. (Tests) Both fixes need regression coverage.** This control flow is subtle; without a test driving the requeue path and one for the self-pinned release, a future refactor can silently reintroduce the stalls.

- brokenlander · comment · 2026-10-07T12:47:57Z · [source](https://github.com/vllm-project/vllm/pull/59030#issuecomment-6038234457)

I tried the head (17d95d3) on a case it doesn't resolve yet: a request blocked by its own encoder reference.

With an EAGLE-family drafter (`num_prefill_lookahead == 1`) and two mm items that each fit the encoder cache but not together, the chunk stops at `start_2 - 1`, and item 1 is only released once `end_1 + 1 <= num_computed_tokens`. If the items are 0 or 1 tokens apart that never happens, so the request schedules 0 tokens on every pass and sits in RUNNING with the GPU idle until it's aborted. Since 17d95d3, `_release_consumed_encoder_inputs` uses the same margin, so it can't fire in this state either and the "one pass later" from review point 3 never comes. 7a40491, which released at the frontier, gets through the 1-token case.

A 1-token gap is the usual layout for Kimi K3: its renderer uses the string content format, so the images in one message are joined by a single `\n`, and two 4096x4096 images come out at 16641 embeds each, more than a 32768 encoder cache together. It's also the layout in vllm-project/vllm-ascend#17195. We reproduced the freeze on v0.30.0 on GPU with a Qwen VL model and MTP (gap 1 freezes, gap 2 and speculative decoding off don't), and the test below shows it on CPU:

| tree | lookahead 1, gap 0 | lookahead 1, gap 1 | gap 2, or lookahead 0 |
|---|---|---|---|
| v0.30.0 | stuck at 649 | stuck at 650 | pass |
| 17d95d3 | stuck at 649 | stuck at 650 | pass |
| 7a40491 | stuck at 649 | pass | pass |

If the margin has to stay for drafters that read mm embeddings, the zero-progress case still needs a way out.

import pytest

from tests.v1.core.utils import create_requests, create_scheduler
from vllm.multimodal.inputs import PlaceholderRange
from vllm.v1.core.encoder_cache_manager import EncoderCacheManager
from vllm.v1.outputs import ModelRunnerOutput


@pytest.mark.parametrize("gap", [0, 1, 2])
@pytest.mark.parametrize("lookahead", [0, 1])
def test_adjacent_items_that_cannot_coexist_make_progress(gap, lookahead):
    scheduler = create_scheduler(max_num_batched_tokens=4096)
    scheduler.use_eagle = lookahead > 0
    scheduler.num_prefill_lookahead = lookahead
    scheduler.max_num_encoder_input_tokens = 1000
    scheduler.encoder_cache_manager = EncoderCacheManager(cache_size=1000)
    first, length = 50, 600
    second = first + length + gap
    request = create_requests(
        num_requests=1,
        num_tokens=second + length + 20,
        mm_positions=[[PlaceholderRange(offset=first, length=length),
                       PlaceholderRange(offset=second, length=length)]],
        max_tokens=1,
    )[0]
    scheduler.add_request(request)
    for _ in range(8):
        output = scheduler.schedule()
        ids = list(output.num_scheduled_tokens)
        scheduler.update_from_output(output, ModelRunnerOutput(
            req_ids=ids, req_id_to_index={r: i for i, r in enumerate(ids)},
            sampled_token_ids=[[] for _ in ids], logprobs=None,
            prompt_logprobs_dict={}, pooler_output=[]))
    assert request.num_computed_tokens > second, (
        f"stuck at {request.num_computed_tokens}; second item starts at {second}")
