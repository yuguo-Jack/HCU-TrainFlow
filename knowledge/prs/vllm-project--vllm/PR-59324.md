# [Frontend] Make finish_reason and Responses item status truthful

[Upstream PR](https://github.com/vllm-project/vllm/pull/59324) · state: open · merged: False

## Original PR description

## Purpose

Fixes #53255, #58228, #57998. Also covers the `finish_reason` half of #53363 and #50889.

Chat `finish_reason` and Responses item `status` both claimed more than what happened:

- **Chat, non-streaming.** `tool_choice="required"` ending with engine `stop` but zero parsed tool calls returned `finish_reason="tool_calls"` next to an empty `tool_calls` array. An `auto` tool call parsed from a generation cut by `max_tokens` returned `tool_calls` instead of `length`, so a client could not tell a completed turn from one cut mid-arguments. The streaming path already guarded both (#46303), so the same request answered differently depending on `stream`. The `/derender` chat paths carried two more hand-written copies of the policy, one with the same `max_tokens` defect.
- **Responses, non-harmony.** Every `ResponseOutputMessage` and `ResponseFunctionToolCall` was hardcoded `status="completed"`, even inside a response whose top-level `status` is `incomplete` with `incomplete_details.reason = max_output_tokens`. The harmony path already did this correctly. In streaming the last `response.output_item.done` said `completed` and the stream ended with `response.completed` instead of the spec's `response.incomplete`.

### Relation to open PRs

This PR is a superset of the open partial fixes and makes all four sites share one rule:

- #53256 adds `and bool(tool_calls)` to the `required` clause only; leaves the `length` bug and both derender copies.
- #58286 gates the relabel on engine `stop` only; leaves the `required`-with-zero-calls bug, has conflicts.
- #47963 (streaming `length`) is superseded by the merged #46303.
- #47931 adds a fourth copy of the policy to derender; its e2e derender assertion is still useful on top of `resolve_finish_reason()`.
- #58018 fixes the non-harmony item status the same way (last item `incomplete`, streaming `close_current`); this PR covers that part and derives it from the same finish reason the chat rule uses. Its separate Harmony zero-delta lifecycle fix is independent and still stands.
- #45386 adds the `response.incomplete` terminal event; covered here (same `ResponseIncompleteEvent` wrapper and background-replay handling).

## Test Plan
Live A/B on H200 with `Qwen/Qwen3-0.6B`, `--enable-auto-tool-choice --tool-call-parser hermes --reasoning-parser qwen3 --max-model-len 4096` (plus a second pair of servers with no tool parser), this branch vs merge-base `dfc8e0f3e2`, 29 + 9 requests (chat non-stream/stream, `n=2`, Responses non-stream/stream, Anthropic) replayed twice at `temperature=0`. `max_tokens=18` cuts the model right after the closing brace of the tool-call JSON, so a call is parsed but the engine reports `length`.

## Test Result

Unit: 21 finish_reason tests and 130 Responses tests pass; full `test_serving_chat.py` 195 passed (GPT-OSS fixture errors also occur on main). `pre-commit` clean including mypy.

Live A/B, only these fields changed; every other response (complete calls, named, streaming chat, plain text, `n=2`, 400s without a parser) was byte-identical:

| Request | before | after |
|---|---|---|
| `/v1/chat/completions`, `tool_choice=auto`, `max_tokens=18` (call parsed, cut) | `finish_reason: "tool_calls"` | `"length"` |
| same, `stream=true` | `"length"` | `"length"` (now consistent) |
| `/v1/responses`, `max_output_tokens=6` (message cut) | item `status: "completed"` | `"incomplete"` |
| `/v1/responses`, `tool_choice=required`, `max_output_tokens=18` (call cut) | item `"completed"` | `"incomplete"` |
| same two, `stream=true` | `output_item.done: completed`, ends `response.completed` | `incomplete`, ends `response.incomplete` |
| no-parser server, `/v1/responses`, `max_output_tokens=6` | item `"completed"` | `"incomplete"` |
| `/v1/messages`, auto tool, `max_tokens=18` | `stop_reason: "tool_use"` | `"max_tokens"` |
| `required` / named with a complete call | `"tool_calls"` / `"stop"` | unchanged |

Thanks @sfeng33, this looks good. Having one `resolve_finish_reason()` for chat and both `/derender` paths is what I was hoping for. Its good that the returning `length` for a cut `auto` tool call matches streaming chat and the Rust frontend.

A few small things, none blocking but good to get them in if possible:

1. If the cut lands in reasoning, non-streaming leaves the reasoning item with `status=None` but streaming marks it `incomplete` through `emit_simple_reasoning_done`. Harmony doesn't set a status on reasoning, so I'd drop it from the streaming done event.
2. With `parallel_tool_calls=false`, the filter runs before `build_response_output_items`. So for `[complete, cut]`, the complete call is the one that gets marked `incomplete`. It's rare and fine to leave but maybe add a comment.
3. Harmony streams now end with `response.incomplete` too because the terminal event code is shared. That's correct but it's worth a line in the description.
4. Tests:
   - Could you add one for background replay stopping on `response.incomplete`?
   - The batch derender test would fit better in `test_derender_stream.py` using the existing `parsed_derenderer` fixture, instead of bare `MagicMock`s in `test_derender.py`
   - An `expect_tool_calls` column in the parametrize would read better than working the expectation out from the input text
