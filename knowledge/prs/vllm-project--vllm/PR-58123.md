# [Bugfix][EC Connector] Tolerate duplicate-push completion races in Mooncake

[Upstream PR](https://github.com/vllm-project/vllm/pull/58123) · state: closed · merged: False

## Original PR description

## Summary

Mooncake EC PUSH: fix a failure cascade when the same content (mm_hash) is pushed concurrently — e.g. requests sharing an image, or a producer re-push racing a consumer that stopped waiting.

Two robustness gaps in the reservation/complete path:

1. `ConsumerReservationManager.complete()` rejected completions of *follower* reservations. A reservation becomes a follower when a concurrent push of the same mm_hash is already writing; the producer cannot know this happened, and the writer publishes followers on completion anyway. Follower completion is now an idempotent no-op.
2. The producer aborted its **entire push batch** when the consumer rejected any single completion. One stale reservation (e.g. of an already-aborted consumer request) thus failed unrelated in-flight transfers, whose consumers then hit the 20s push wait timeout and failed their requests — which cancelled more reservations and poisoned the next batch. Rejections are now logged per item and the rest of the batch completes normally.

Observed on a 4E+4PD EPD deployment (Qwen3.5-35B-A3B, Mooncake RDMA, MUIRBench which reuses image sets across questions): a single rejection aborted a 4-item push batch, two consumer requests waited 20s and returned 500, 7/6000 requests failed in one run; a rerun without the race was clean.
