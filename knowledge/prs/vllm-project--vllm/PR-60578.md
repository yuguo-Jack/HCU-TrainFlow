# [Rust Frontend] Constrain MiniMax M3 tool calls with a nested argument grammar

[Upstream PR](https://github.com/vllm-project/vllm/pull/60578) · state: open · merged: False

## Original PR description

## Purpose

The Rust MiniMax M3 tool parser builds no output grammar, so `tool_choice="required"`, named tool choice, and strict tools leave M3 tool calls unconstrained. XGrammar's builtin `minimax_m3` structural tag (`minimax_m3_xml` style) is not a usable fallback: it rejects unconstrained argument schemas when compiling, which is what a non-strict tool sends under required or named tool choice, and silently narrows a nested `{"type": "object"}` without `properties` or an untyped array to empty values. The Python M3 parser keeps `supports_required_and_named = False` for the same reason (#59743).

M3 renders tool arguments as namespace-prefixed XML elements, recursively, as `to_xml` in the chat template does: an object's fields are child elements named by their keys, array items are `<item>` elements, and every closing tag repeats its key:

```
]<]minimax[>[<invoke name="create_event">
]<]minimax[>[<place>]<]minimax[>[<city>Paris]<]minimax[>[</city>]<]minimax[>[</place>
]<]minimax[>[<tags>]<]minimax[>[<item>work]<]minimax[>[</item>]<]minimax[>[</tags>
]<]minimax[>[</invoke>
```

The argument grammars from #59395 render only the root object as keyed parameters and hand nested values to XGrammar's JSON schema converter, so they cannot express this either.

- `ArgumentSyntax` can nest keyed parameters:
  - `ValueOption::fields` renders an object option's fields with the same syntax as the root arguments, and `ValueOption::items` yields an array option's item options;
  - both stop at schemas that enclose themselves through references or nest deeper than 32 levels, which `ValueOption::recurses` reports so a syntax can choose its own fallback;
  - `arguments` returns `None` when the arguments admit undeclared keys that the syntax cannot render, instead of silently dropping them. The existing syntaxes all render free keys, so Kimi K3 and the other grammars are unchanged.
- M3 gets its own `ArgumentSyntax` and structural-tag builder, wired through `build_visible_format`. The envelope (triggers, excluded markers, parallel calls, auto/required/forced) matches XGrammar's builtin.
- Because a closing tag repeats its key, only declared keys can be spelled:
  - a value that admits undeclared keys or takes any shape is free text up to its own closing tag, so a non-strict tool's arguments are free text up to `</invoke>`: the envelope is constrained, the arguments are not;
  - a schema that nests in itself always contains its own closing tag, so the whole call is free text up to `</invoke>`, the only marker the parser ends a call at.

Known limits:

- Without `any_order`, properties must follow schema order, as in XGrammar's builtin.
- Inside a free-text value, a nested element named after the enclosing key ends the value early. Only a recursive schema guarantees this, and that case falls back to the whole call.
- The M3 reasoning parser does not wrap visible formats yet, so the grammar covers only the final output (`final_output_only`), and the roundtrip replay compiles the grammar without replaying generations.

- `arguments` unit tests for nested objects and arrays, recursion and undeclared keys stopping the nesting, and a syntax without free keys returning `None`.

- Manual replay matched expectations in 14/14 cases. Accepted: nested objects, arrays of objects, an open `labels` object, a recursive tree, a non-strict tool with extra nested keys, and parallel calls. Rejected: plain text under required, a missing required argument, a wrong type, an undeclared nested key, a different tool under forced choice, and properties out of schema order.
