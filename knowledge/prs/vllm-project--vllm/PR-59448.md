# [Attention][Triton] Admit short spec-verify queries into the 3D split-KV path, guard masked segments

[Upstream PR](https://github.com/vllm-project/vllm/pull/59448) · state: open · merged: False

## Original PR description

## Purpose

Addresses #59054 for the non-DiffKV kernel (`vllm/v1/attention/ops/triton_unified_attention.py`).

Speculative-decode verify batches (`max_seqlen_q = 1 + k`) are kept off the split-KV 3D path by the `max_seqlen_q > 1` term of the launch gate. For one sequence, the 2D grid is `(total_num_q_blocks, num_kv_heads)`, which is a handful of programs, and each one walks the whole KV history. On long contexts this dominates the step time.

This PR:

1. **Adds `VLLM_TRITON_3D_MAX_Q`** (default `1`, which keeps today's behaviour). Queries with `max_seqlen_q <= VLLM_TRITON_3D_MAX_Q` may take the 3D path, provided the total token count fits the segment scratch (`q.shape[0] <= seq_threshold_3D`). The scratch buffers are indexed by token, and `reduce_segments` already runs per token.
2. **Guards fully masked segments.** With several query tokens per program, a row can have every key of a segment masked. This happens when a segment boundary sits just before the last query tokens. The online-softmax update then ends at `M = 0, L = 0`, and the epilogue would store `M = 0` as that segment's maximum. When the real maxima are strongly negative, `reduce_segments` underflows every real segment and the row comes out wrong. The epilogue now stores `-inf` when `L == 0`. The same idea is used for DiffKV in #59085.
3. **Clamps an all-`-inf` `overall_max` to 0** in `reduce_segments`, so a row with no visible key yields 0 instead of NaN. This is the same line as in #58141.

### Why this is not a duplicate

- #44652, #45450 and #52879 relax the same gate for this kernel, each with a different admission policy (constant, spec-config-derived, capacity-derived).
- None of them includes the per-row masked-segment guard (2). Without it, admitting multi-token queries to 3D produces wrong attention outputs. The new test `test_spec_verify_3d_fully_masked_segment_rows` fails if either (2) or (3) is removed.
- #59085 and #58141 only touch the DiffKV kernel.
- If maintainers prefer one of the open gate PRs, I am happy to close this one, provided the guard and the test are carried over. I posted the same analysis on #59054.

## Test Plan

```
pytest -q tests/kernels/attention/test_triton_unified_attention.py -k spec_verify
```

- `test_spec_verify_3d_matches_reference` checks the 3D path against a dense PyTorch reference. It covers bf16 and fp8 KV, block sizes 16 and 1600, `q_len` 2 and 4, and sequence lengths 37 to 32768.
- `test_spec_verify_3d_fully_masked_segment_rows` sweeps sequence lengths 1 to 199 at `q_len=4` with strongly negative logits. It covers rows with a fully masked segment (epilogue guard) and rows with no visible key at all, `seq_len < q_len` (reducer clamp).
- End-to-end serving with MTP, stock vs. `VLLM_TRITON_3D_MAX_Q=4`. Identical prompts (fixed seed), prefix caching off, greedy decoding, with a comparison of the generated text.

The clamp isn't redundant though — it's just unreachable from the sweep. `test_spec_verify_3d_masked_segment_sweep` runs `range(8, 521)` with `q_len=4`, so `context_len = seq_len - q_len >= 4` and every query row always sees at least one key. Going below that through your own `_run`:

```
q_len = 4, both guards        kv_len 1 2 3 4 5 8  ->  no NaN anywhere
q_len = 4, clamp removed      kv_len 1 2 3        ->  NaN
                              kv_len 4 5 8        ->  clean
```

So `kv_len < q_len` is the shape that needs it, and the sweep starts one step above it. Lowering the bound (or just adding `[1]` to the multi-sequence `seq_lens` set) would pin the clamp too — worth it because the clamp is the one that *looks* redundant next to the epilogue guard, so it's the one someone simplifies away later.

**Same pair, same order, on the DiffKV kernel.** #58141 carries the clamp and #59085 carried only the epilogue guard; on my card #59085 NaN'd at `q=8, kv_len=1` and `kv_len=3` until it picked up #58141's clamp, at which point those rows went to 0 and matched the 2D path exactly. Whichever combination lands, **both** guards need to survive, and only two of those five currently have the pair. Your closing note says #59448 can be dropped in favour of whichever lands "as long as the guard and the test are carried over" — I'd say that more strongly: it's two guards, and the test as written only proves one of them.

For multi-token sliding-window attention, a segment can start with a fully masked tile and later have valid keys. The first tile leaves `M=0, L=0`, so very negative scores in the next tile can underflow. This guard runs too late to recover the lost values.

- SCcagg5 · comment · 2026-10-11T15:33:29Z · [source](https://github.com/vllm-project/vllm/pull/59448#discussion_r4242131129)

File: `vllm/v1/attention/ops/triton_unified_attention.py` · line 643

Good catch, you're right. I reproduced it: with a sliding window the loop starts at the window of the first token of the query block, so for a later token the first tile can be fully masked. `softmax_step` then leaves `M = 0, L = 0`, and if the logits of the next tile are below about -100 its keys underflow against that stale `M`; the epilogue guard sees `L = 0` and drops the segment.

It only happens when the window start falls in the last few positions of a tile, and the 2D path behaves the same, so it predates this PR, but this PR makes it reachable for sliding-window models during spec verify.

Fixed in cce2aaa: reset `M` to `-inf` while `L == 0` before `softmax_step`. New test `test_spec_verify_3d_sliding_window_masked_first_tile` (windows 8/20/40, strongly negative logits, 4 segments so a segment holds several tiles, sweep over `seq_len`). On gfx1151:

| kernel | new tests | full file (1667 cases) |
|---|---|---|
| previous head | 3 failed (max abs diff 3.1) | 1663 passed, 4 failed |
| with fix | 3 passed | 1666 passed, 1 failed |
