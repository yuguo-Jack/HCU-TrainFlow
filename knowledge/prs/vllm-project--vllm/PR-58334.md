# [Bugfix] Avoid O(n) strip_covered_mm_data work per realtime step

[Upstream PR](https://github.com/vllm-project/vllm/pull/58334) · state: open · merged: False

## Original PR description

## Purpose

Fixes #58324.

Realtime (`/v1/realtime`) sessions re-enter the scheduler as new requests on every engine step. `NewRequestData.from_request` called `strip_covered_mm_data` over **all** accumulated multimodal features and `dataclasses.replace`'d every already-covered item. Per-step EngineCore time grew linearly with session age (~3 ms per minute of audio; quadratic over the session). A late-session profile put ~55% of EngineCore time in this path.

Covered features only grow, and `mm_features` are ordered by offset. This change:

1. Memoizes the stripped copy on each `MultiModalFeatureSpec`, so `dataclasses.replace` runs once per feature.
2. Keeps a covered prefix cache on `Request` (`_mm_stripped_prefix`) so later steps only examine newly covered features (O(new features), not O(all features)).

The scheduler-side `Request` still keeps the full payloads. Originals are not mutated. Preempt (`num_computed_tokens == 0`) clears the prefix cache so a later prefix-cache hit can re-strip from the originals.

**Not a duplicate:** searched open PRs for `#58324`, `strip_covered_mm_data`, and realtime scheduler mm-feature stripping. Issue #58324 is open with no linked PRs. `#52041` introduced the function; `#54994` only preserved SHM address items.

AI assistance was used to implement and test this change. The submitting human reviewed the diff.

This does not change model outputs, accuracy, or serving behavior — only scheduler CPU work for already-covered mm payloads.
