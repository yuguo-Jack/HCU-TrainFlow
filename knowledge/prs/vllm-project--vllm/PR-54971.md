# [Bugfix][Parser] GLM-4.7: stray arg tags must not leak into tool-call argument keys

[Upstream PR](https://github.com/vllm-project/vllm/pull/54971) · state: open · merged: False

## Original PR description

## Purpose

Fixes a tool-call corruption in the GLM-4.7 parser: stray `arg_key` markup leaks into the parsed argument **key**, so the client rejects the call.

Observed in production against a GLM server run with `--tool-call-parser glm47`:

```
list_dir({"path</arg_key>": "/Users/user/Desktop/project"})
-> client error: "must have required property 'path'"
```

The client rejects the call, the agent loses the step, and the model retries with an invented path.

**Root cause.** `_glm47_arg_converter` matched the key with an unbounded non-greedy group:

```python
r"<arg_key>(?P<key>.*?)</arg_key>\s*<arg_value>(?P<value>.*?)</arg_value>"
```

`.*?` is non-greedy but it is *not* bounded by the delimiter it is scanning for. If the stream contains a repeated or stray `arg_key` tag, the engine backtracks past the first `</arg_key>` because that is what it takes to reach the following `<arg_value>`, and the extra markup ends up inside the key. On

```
<arg_key>path</arg_key></arg_key><arg_value>/tmp/x</arg_value>
```

the old code yields `{"path</arg_key>": "/tmp/x"}`, reproducing the observed string exactly. The mirrored `<arg_key><arg_key>path…` case yields `{"<arg_key>path": "/tmp/x"}`.

**Fix.** Match runs of non-`<` text so the key group cannot cross its own delimiter, and accept a run of closing tags so a duplicate is skipped rather than shifting the key:

```python
_ARG_KEY = r"<arg_key>(?P<key>[^<]*+(?:<(?!/?arg_key>)[^<]*+)*+)(?:</arg_key>\s*)+"
```

Both `_ARG_RE` and `_PARTIAL_ARG_RE` are built from it, so the streaming path gets the same guarantee.

The unrolled possessive form is deliberate rather than the simpler tempered dot `(?:(?!</?arg_key>).)*`. `_compute_arg_delta` re-runs the converter over the whole accumulated buffer on every argument chunk, so the common streaming case is a *failing* match against a partial buffer — precisely where a tempered dot backtracks per character. Measured on an unterminated buffer:

| buffer | tempered dot | possessive (shipped) |
|---|---|---|
| 5 KB | 232 us | 4 us |
| 20 KB | 1251 us | 10 us |
| 50 KB | 2203 us | 21 us |

Equivalence was checked over 600,000 randomized tag-soup evaluations against both patterns: 0 differing results.

## Related work

Not a duplicate of the other open GLM-4.7 parser PRs (re-checked 2026-10-10) — each handles a different malformation in the same file:

- #47190 — recovers calls missing the **opening `<arg_key>`** (`tool_namearg</arg_key>`).
- #49249 — tolerates a missing **opening `<arg_value>`**.
- #60842 — recovers when a stray **`<tool_call>`** opens a phantom call.
- #58418 — preserves an **unclosed final argument** (touches the code that applies `_ARG_RE`/`_PARTIAL_ARG_RE`, not the patterns).
- this PR — a **stray or repeated `arg_key`** tag corrupting the key.

They will conflict textually where they edit `_ARG_RE`/`_PARTIAL_ARG_RE`. Happy to update this branch against whichever lands first.

The possessive-quantifier approach follows #54678, which fixed catastrophic backtracking in the `poolside_v1` and `dots` tool-call regexes.

## Scope note

The raw model stream that produced the production capture was not retained, so the exact upstream trigger for the stray tag is inferred from the corrupted output rather than replayed. The change is a strict improvement independently of what emitted the stray tag: it removes a way for the extraction to mis-key an argument, and leaves well-formed input byte-identical.

Two sibling parsers (`glm4_moe`, `dots1`) carry structurally similar key patterns; they are left alone here to keep this reviewable, and neither has a reported corruption.

- `<arg_key>path</arg_key></arg_key><arg_value>/tmp/x</arg_value>` → base produced key `path</arg_key>` (the exact production failure in the PR body); head → `{"path": "/tmp/x"}`.
- `<arg_key><arg_key>path</arg_key><arg_value>...` → base produced key `<arg_key>path`; head correct.

**Regression-proven:** all 5 new tests FAIL on base (4 param converter tests + the streaming e2e test), PASS on head. Full file: 20/20 pass on head vs 5 failed/15 passed on base (teardown `RuntimeError: Cannot access accelerator device` errors are the known CUDA-less noise, identical on both).

**No regressions on adjacent shapes** — probed base-vs-head over 22 inputs: well-formed single/multi-arg, `\s*` whitespace variants, keys containing `<` (e.g. `a<b`), arg_key-like markup inside values, empty keys/values, newlines, trailing partial values, junk prefix. Byte-identical output everywhere except the corrupt-key cases. One deliberate delta on the malformed two-keys-one-value input: base merged `a</arg_key><arg_key>b` into one corrupt key; head drops the value-less `a` and keeps `{"b": "1"}` — cleaner fail behavior, not a regression.

**Non-blocking note:** `vllm/tool_parsers/poolside_v1_tool_parser.py:82` uses the same `<arg_key>(.*?)</arg_key>\s*<arg_value>(.*?)</arg_value>` shape with stdlib `re` — same leak exists there (`findall` on `<arg_key>path</arg_key></arg_key><arg_value>/tmp/x</arg_value>` returns `[('path</arg_key>', '/tmp/x')]`). If poolside models can emit stray arg tags too, the same `[^<]*+(?:<(?!/?arg_key>)[^<]*+)*+` key pattern would apply. Out of scope for this PR, just flagging the sibling.
