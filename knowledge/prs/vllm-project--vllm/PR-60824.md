# [ZenCPU] Add zen5 CPU tests reusing the pushed zen image

[Upstream PR](https://github.com/vllm-project/vllm/pull/60824) · state: open · merged: False

## Original PR description

Add Zen-CPU kernel and platform-detection test steps on the zen5 queue, gated on zen source changes. To avoid recompiling vLLM/zentorch on the scarce zen5 box, zen-cpu-image-build now pushes the zen image to public ECR (anonymous pull, no credentials on the test side), and run-zen-cpu-test.sh pulls it, falling back to a local build (reusing the published -cpu base, else from source) when it is unavailable.

The test steps depend_on zen-cpu-image-build with allow_dependency_failure so the fallback still runs if that build fails or soft-fails, and run-zen-cpu-test.sh is added to the build step's source_file_dependencies so it is never pruned while a test runs. run-zen-cpu-test.sh pins ZENTORCH_VERSION (matching the zen extra in setup.py) so Dockerfile.zen installs zentorch directly instead of re-resolving vllm[zen], which fails on vLLM's transitive triton-cpu URL dependency.



## Overview

Add two Zen CPU hardware-test steps (kernel + platform-detection) that run on the `zen5` queue, reusing the zen CPU image published by the existing `zen-cpu-image-build` step instead of recompiling on the scarce Zen5 box. To enable that reuse, `zen-cpu-image-build` now pushes the zen image to public ECR, and `run-zen-cpu-test.sh` pulls it (with a local-build fallback). Builds on the merged zen image-build work in #60016.

## Claims

- Adds `Zen-CPU-Kernel Tests` and `Zen-CPU-Platform-Detection Tests` on `device: zen5`, gated on zen source changes.
- Publishes the zen image (`<repo>:<commit>-zen-cpu`) to public ECR from `zen-cpu-image-build`, so test nodes on other queues pull it (anonymous pull, no credentials on the test side) rather than rebuilding.
- `run-zen-cpu-test.sh` pulls the prebuilt zen image and falls back to a local build (reusing the published `-cpu` base, else from source) if it is unavailable; it installs zentorch directly via `ZENTORCH_VERSION` to avoid the `vllm[zen]` transitive triton-cpu URL resolution failure.

## Validation

- Local pre-commit (subset runnable without network): `check-buildkite-step-keys`, `check-test-tethering`, `check-filenames` pass; `bash -n` and YAML parse pass for all changed files. `shellcheck`/`typos` binaries were not available locally (sandbox + corporate SSL); CI covers them. All changed-file expansions are quoted (no SC2086).
- The underlying zen image build and direct-zentorch install path were already validated in CI (build #93708 / merged #60016): log shows `Using published CPU image as base: public.ecr.aws/q9t5s3a7/vllm-ci-test-repo:<commit>-cpu` and a clean `zentorch==2.13.0.1` install with no triton resolution error.
- Not yet verified (confirm on first CI run of this PR):
  1. the `amd-cpu` build agent has AWS credentials to push to public ECR;
  2. the `zen5` test step pulls the pushed image (log line `Using published Zen image: ...`) rather than falling back to a local build.
  If push credentials are absent, `zen-cpu-image-build` soft-fails (pipeline stays green) and the tests fall back to building the zen image locally — so a green pipeline alone does not confirm reuse; check the step logs.

## Details

- Reuse mirrors the existing `-cpu` image reuse: the push is guarded on `REGISTRY` being set (CI only); pulls are anonymous public ECR, so test nodes need no credentials.
- Tests `depends_on: zen-cpu-image-build` with `allow_dependency_failure: true` so the fallback still runs if that build fails/soft-fails. `run-zen-cpu-test.sh` is added to the build step's `source_file_dependencies` so the build step is never pruned while a test step runs (which would otherwise make `depends_on` error at pipeline upload).
- `ZENTORCH_VERSION` is pinned to `2.13.0.1` to match the `zen` extra in `setup.py`; this keeps `Dockerfile.zen` on its direct-zentorch `if` branch and avoids `uv` re-resolving `vllm[zen]` (which fails on vLLM's transitive `triton @ <url>` CPU wheel).
- Tradeoffs / limitations: the push assumes AWS creds on the `amd-cpu` agent (under test here); if absent, tests rebuild the thin zen layer locally per run. `soft_fail: true` on the build step means reuse must be confirmed from logs, not just a green check.
- Complexity: low — CI-only, no `vllm/` source changes (~130 added lines across 4 `.buildkite/` files).
