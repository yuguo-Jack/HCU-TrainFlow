# [Bugfix] Free the pinned CPU weight backup on wake_up

[Upstream PR](https://github.com/vllm-project/vllm/pull/60003) · state: open · merged: False

## Original PR description

## Purpose

After the first level-1 sleep, every worker keeps a host copy of its weights in pinned memory for the rest of the engine's life, including while it is awake.

**Cause.**
- `CuMemAllocator.sleep()` backs each offloaded allocation up into `torch.empty(..., pin_memory=True)`. That memory comes from torch's caching host allocator.
- `wake_up()` copies the data back and drops the tensor. The caching host allocator keeps the freed pinned block resident for reuse, and it rounds every block up to a power of two.
- So host RSS never goes back down. On DeepSeek-V4-Flash TP4 (GB300), each worker goes from about 10 GB RSS before the first sleep to 55 GB awake: 48.5 GiB of cached pinned blocks for a 43.0 GiB backup. Per node, MemAvailable while awake drops from 881 GiB to 703 GiB.
- This matters for colocated RL, where the trainer runs on the same node and needs that host RAM while vLLM is awake.

**Fix.** The CPU backup becomes pinned memory that `cumem.py` owns explicitly, outside torch's caching host allocator. This is what `torch_memory_saver` (SGLang) does: its CPU backup is a raw `cudaMallocHost`, and by default it is freed right after the resume copy (retention is opt-in).
- `sleep()` allocates each backup with `cudaHostAlloc` at its exact size (`hipHostMalloc` on ROCm). The memory is exposed as a non-owning uint8 tensor, so `AllocationData` is unchanged.
- `wake_up()` frees each backup with `cudaFreeHost` (`hipHostFree`) as soon as it has been copied back. A partial wake (for example `kv_cache` only) keeps the backups of tags that are still asleep.
- The backup is also freed when its allocation is freed, and at allocator shutdown.
- `CudaRTLibrary` gets `cudaHostAlloc` / `cudaFreeHost` bindings with their HIP mappings. No private torch API is used.
- When pinned memory is unavailable (`PIN_MEMORY` is False), the backup stays a pageable `torch.empty`, as before.

**Cost.** The next sleep has to pin its backup again, so each sleep costs about what the first sleep on main costs. On V4-Flash TP4 this is about +1.7 s per sleep: 2.8 s instead of 1.1 s, measured on one node with an earlier variant that re-pins the same way. On the node in the table below, where pinning is slower, it is 3.65–4.10 s instead of 0.95 s. Wake gets 0.5–0.9 s slower because of `cudaFreeHost`. The first request after wake is unchanged.

V4-Flash TP4 EP, per worker, 3 cycles, on one GB300 node:

| | main | this PR |
|---|---:|---:|
| Worker RSS awake (after the first sleep) | 55.0–55.6 GB | 9.5–10.2 GB |
| Node MemAvailable awake | 703.5 GiB | 877.2–877.7 GiB |
| Worker RSS asleep | 55.0–55.6 GB | 53.4–54.1 GB (no power-of-two rounding) |
| Node MemAvailable asleep | 703.5 GiB | 709.0–709.5 GiB |
| Sleep | 4.06 s first, then 0.94–0.95 s | 3.65–4.10 s every time |
| Wake | 0.91–1.08 s | 1.58–1.82 s |
| First request after wake | 0.36 s | 0.36 s |

Alternatives I measured and did not pick:
- Keep `torch.empty(pin_memory=True)` and call `torch._C._host_emptyCache()` after wake. It releases as well as this PR, but it uses a private API, still rounds up while asleep (48.5 instead of 43.0 GiB per worker), and empties torch's whole pinned host cache, not only the backups.
- Backup in pageable `torch.empty` + `cudaHostRegister`: the torch CPU allocator does not return all of it to the OS. Workers kept 13–17 GB RSS awake, against 10 GB.

## Test Plan

- New test `test_wake_releases_pinned_cpu_backup` in `tests/basic_correctness/memory/cumem/test_cumem.py`. It measures process RSS from `/proc/self/smaps_rollup` over two sleep/wake cycles with a 256 MiB `weights` allocation:
  - sleep must add at least the backup size;
  - a `kv_cache`-only wake must keep it;
  - the `weights` wake must give back at least half of it;
  - the weights must be bit-exact after every wake.
- The checks are per-cycle deltas, because an unrelated one-time RSS growth of about 100 MiB appears during the second sleep on both main and this PR.
- Mutation checks:
  - main;
  - this PR without `cudaFreeHost` on wake;
  - this PR with a wake that also frees the backups of tags that are still asleep.
- `test_cumem.py` (3 runs) and the sleep-mode suites: `sleep_mode/test_sleep_mode.py`, `model_executor/test_sleep_mode_tensor_ownership.py`, `entrypoints/serve/dev/test_sleep.py`. Each is compared with main.
- GB300 hardware: DeepSeek-V4-Flash TP4 EP, three sleep(level=1)/wake cycles, with 28 greedy probes compared against the awake reference after every wake. Each run ends with a SIGTERM while asleep, which exercises the shutdown free.
- `pre-commit run` on the changed files.

## Test Result

- New test: 5/5 passed. It fails on main 3/3, fails 3/3 on each of the two mutants, and passes 3/3 on the `_host_emptyCache` variant.
- `test_cumem.py`: 22/22 passed, 3 runs (GB300, torch 2.13.0+cu130).
- Sleep-mode suites: 37 passed, 3 failed, 2 skipped, the same as main. The 3 failures are environment issues on both: a missing `kaldi_native_fbank`, a Voxtral config attribute, and a model that is not cached.
- V4-Flash TP4: probes 84/84 bit-exact. The numbers are in the table above. Clean SIGTERM shutdown while asleep: exit code 0, no Traceback, no shutdown error.
- `pre-commit`: all hooks pass (ruff check/format, mypy, typos, SPDX, test tethering, and the rest).
