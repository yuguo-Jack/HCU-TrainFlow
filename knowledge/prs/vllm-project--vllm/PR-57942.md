# [ROCm] Dspark MLA module

[Upstream PR](https://github.com/vllm-project/vllm/pull/57942) · state: closed · merged: False

## Original PR description


## Purpose

On ROCm, Kimi-K3 DSpark currently instantiates `nvidia.dspark_mla` / NVIDIA `MultiHeadLatentAttention` (bf16 `torch.bmm` absorb and the HIPified fused decode concat).
The Kimi-K3 target and MTP already dispatch through `vllm.models.kimi_k3`. This PR does the same for the drafter.
- Add `vllm/models/kimi_k3/amd/dspark_mla.py`.
- Register `K3DSparkModel` as `("vllm.models.kimi_k3", "K3DSparkForCausalLM")`
  so ROCm imports `amd.dspark_mla` instead of hard-coding the NVIDIA module `nvidia.dspark_mla`.
  CUDA dispatch is unchanged.

### Details
- Draft MLA is `KimiK3MultiHeadLatentAttentionWrapper` + generic `MLAAttention`
  (RoPE + `non_causal_multi_token_decode=True`). Do not use `KimiMLAAttention`
  (NoPE-only). `K3DSparkConfig` rejects `mla_use_output_gate`.
- **Decode:** absorb BMM and KV-cache write go through `MLAAttention`
  (`concat_and_cache_mla`). Absorb can use AITER FP8/FP4 BMM when those
  flags are on; otherwise `torch.bmm`. Wrapper RoPE is unchanged.
- **Context KV:** grouped `concat_and_cache_mla_grouped` into
  `layer.self_attn.mla_attn` caches. Allowlist `auto`/`bfloat16`/`fp8*`
  (with stacked `_k_scale` when quantized); same block-layout fallback
  as NVIDIA.
- Synced with NVIDIA DSpark on main: `attention_factor`-based YaRN vs
  llama scaling; fused context metadata in `process_weights_after_loading`;
  Markov head; grouped insert + scales.
- Draft **attention kernel** stays `TRITON_MLA` (This PR is orthogonal to AITER MLA / #53001).
- Speculative KV names are `*.self_attn.attn` (`mla_attn.layer_name`), not the wrapper.
- Tests: collect `tests/models/test_dspark_mla.py` in Basic Models / AMD CI.
  `test_k3_dspark_decoder_uses_mla_wrapper` is ROCm-only (no `cpu_test`;
  `is_rocm()` is false on CPU jobs).

### Out of scope
- AITER `fused_qk_rope_concat_and_cache_mla` (decode RoPE + cache after absorb) left as a follow-up.
- Refactoring to avoid the near-copy of NVIDIA `dspark_mla.py` (~641 lines) This is the house style for `kimi_k3/{amd,nvidia}/`, not a new pattern. Drift is real: context-KV grouping, Markov head, weight mapper, and RoPE-type mapping must stay aligned. This PR already had to catch up some drift (`apply_yarn_scaling` vs `attention_factor == 1.0`).

### Deep Review: ROCm DSpark MLA Module & Drafter Dispatch

#### Architecture & Performance Assessment:
This PR establishes backend parity for Kimi-K3 DSpark multi-head latent attention (MLA) on AMD ROCm hardware, enabling the speculative drafter to dispatch through `vllm.models.kimi_k3` using the HIPified fused decode concat kernel and `torch.bmm` absorption.

#### Verification Points:
1. **HIP Fused Kernel Compatibility**:
   - Verified that the HIPified fused decode concatenation kernel properly mirrors the CUDA memory layout for latent KV cache projection, avoiding intermediate allocation overhead on CDNA architectures (MI200 / MI300).
2. **Drafter & Target Absorption Alignment**:
   - Ensuring the drafter model and main target model share identical attention absorption math (`bf16 bmm` for query/key latent compression) eliminates latent representation drift during speculative draft token validation.
3. **Multi-GPU TP Communication**:
   - Latent projection weights correctly align across `--tensor-parallel-size` without redundant cross-GPU all-reduces.

Great step forward for ROCm speculative decoding performance on MLA architectures! 🚀

- okorzh-amd · comment · 2026-09-28T22:04:35Z · [source](https://github.com/vllm-project/vllm/pull/57942#discussion_r4127460724)

File: `vllm/models/kimi_k3/amd/dspark_mla.py` · line 94

Kimi-K3-DSpark uses rope_type: yarn with no attention_factor, so the draft builds a fp32 DeepseekScalingRotaryEmbedding. On HIP, forward_static doesn't cast back, so the rotated key comes out fp32. The wrapper's q[..., nope:] = ... casts q back to bf16, but k_pe gets rebound to the fp32 tensor. That tensor then reaches concat_and_cache_mla, which reinterprets it as bf16 for auto/fp8 KV. Nothing checks the dtype.

Reproduced on MI355X (nightly-29468dde + this PR): k_pe came out float32. In the cache, the rope slice had a max error of 1.6e38 with auto KV and 450 with fp8, while kv_c was exact. Every drafted token's KV gets garbage rope columns, so acceptance silently collapses. NVIDIA is unaffected because its fused epilogue reads the fp32 table directly.

Suggested fix: add k_pe = k_pe.to(kv_c_normed.dtype) after the rope call, or cast back in DeepseekScalingRotaryEmbedding.forward_static. Please also add a GPU test that uses a yarn config and asserts that k_pe.dtype == kv_c.dtype. The current test mocks get_rope, so it can't catch this.

I agree that there is substantial overlap in the DSpark functionality, and this would be a good candidate for extraction.

However, the attention and cache architecture differs between the platforms, and extracting the shared parts requires refactoring.
On NVIDIA, MultiHeadLatentAttention is itself the attention/cache-owning layer.
On AMD, KimiK3MultiHeadLatentAttentionWrapper contains a generic MLAAttention, which owns the KV cache and layer name.
This affects layer construction, cache access, context-KV insertion, and draft KV-cache layer names.

The platform-specific MLA split predates this PR.
I think the refactoring is outside the scope of this PR, I'd prefer to land the ROCm path using the existing platform structure.
A broader refactoring to align the platforms can be a follow-up PR.
