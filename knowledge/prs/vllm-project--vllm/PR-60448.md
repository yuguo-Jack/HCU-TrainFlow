# [Bugfix][MoE] Fail fast when batched_triton lacks batched prepare/finalize

[Upstream PR](https://github.com/vllm-project/vllm/pull/60448) · state: open · merged: False

## Original PR description

## Purpose

Fixes #60432.

`moe_backend="batched_triton"` on an unquantized MoE model crashed engine startup mid-model-load with a raw `TypeError: BatchedTritonExperts.__init__() missing 2 required positional arguments: 'max_num_tokens' and 'num_dispatchers'`.

Root cause: `moe_backend="batched_triton"` maps to `BatchedTritonExperts`, which requires the `BatchedExperts` activation format. The batched prepare/finalize path only exists for all2all kernels or as an XPU-only opt-in (`BatchedPrepareAndFinalize` in `maybe_make_prepare_finalize`). On CUDA without all2all kernels, `maybe_make_prepare_finalize` falls back to a naive `Standard`-format prepare/finalize, and `make_unquantized_moe_kernel` then constructed `BatchedTritonExperts(moe_config=..., quant_config=...)` without the two required arguments.

This PR fails fast at the pairing point in `make_unquantized_moe_kernel`: when the selected experts class requires `BatchedExperts` but the prepare/finalize stage produces a different format, it raises a clear `ValueError` naming both sides and suggesting `moe_backend="triton"` instead. This mirrors the existing clean-rejection precedent for unsupported unquantized backends (e.g. the `ValueError` in `map_unquantized_backend`).

Why this is not a duplicate: I checked open PRs referencing issue #60432 (`gh pr list --search "60432 in:body"` → none) and open PRs touching `batched_triton` for unquantized MoE (only unrelated marlin-fallback, FlashInfer CUTLASS demotion, DeepEP, and kernel-rebuild PRs). No open PR addresses this crash.

## Test Plan

- New regression test `tests/kernels/moe/test_unquantized_backend_selection.py::test_batched_triton_rejects_non_batched_prepare_finalize`: builds the exact reported configuration (`moe_backend="batched_triton"` → `BatchedTritonExperts` + naive `Standard` prepare/finalize via the real `maybe_make_prepare_finalize` path, no mocks) and asserts the clear `ValueError`. CPU-runnable; no GPU kernels are launched.
- A standalone reproducer driving the same path confirmed the old code raised the raw `TypeError` and the new code raises the `ValueError`.
- `ruff check` and `ruff format --check` pass on both changed files.
