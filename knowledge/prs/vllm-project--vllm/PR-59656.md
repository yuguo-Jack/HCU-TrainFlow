# [Core][Spec Decode] Group sliding-window draft layers separately in the GLM-5.3 builder

[Upstream PR](https://github.com/vllm-project/vllm/pull/59656) · state: open · merged: False

## Original PR description

### Summary

GLM-5.3-Flash (`glm5_next`) fails to start with any EAGLE-family drafter whose layers are plain sliding-window attention (e.g. the block-diffusion DFlash2 drafter, 5 GQA `SlidingWindowSpec` layers). `_get_kv_cache_groups_glm5_next` only accepts exact `MLAAttentionSpec` in the attention group, so it declines; the generic page-size unification then cannot pad the DSA indexer (MLA family) and startup dies:

```
NotImplementedError: indexer.k_cache: page size is not divisible by the maximum
page size and cannot be padded. Padding is only supported for non-MLA attention layers
```

This is the same direction as the draft-group work in #58638 (KV cache grouping for hybrid models with speculative drafters), applied to the GLM-5.3 builder, which was not covered there.

### Root cause

`_get_kv_cache_groups_glm5_next` builds one packed group for `MLAAttentionSpec` + indexer (MLA with `tokens_per_state > 1`) layers and aliases the kpool tails onto the indexer tensors. Its gate requires every non-Mamba / non-`KpoolTailSpec` spec to be exactly `MLAAttentionSpec`. A drafter contributes uniform `SlidingWindowSpec` layers with the draft worker's own (small) block size, so the gate returns `None`. The generic `unify_kv_cache_spec_page_size` then tries to pad every page up to the max (MLA) page; the indexer page is MLA-family and explicitly refuses padding, so `get_kv_cache_groups` raises.

### Changes

One file, `vllm/v1/core/kv_cache_utils.py`:

- `_get_kv_cache_groups_glm5_next` splits `HiddenStateCacheSpec` (aux-eagle) and uniform drafter `SlidingWindowSpec` layers (excluding `KpoolTailSpec` / sliding-window MLA) out of `attn_specs`; the strict all-MLA gate now only applies to the target's attention layers. Absorbing the extras requires `speculative_config.use_eagle()`.
- Draft layers get their own `KVCacheGroupSpec`, re-aligned to the target block size (the packed GLM layout needs a single LCM / scheduler block), with `is_eagle_group=use_eagle_block_drop()` and `enable_kv_transfer=False`; hidden-state layers get one group each.
- `_glm5_next_tensor_layout` accepts such extra groups only when they are sliding-window / hidden-state and share the attention block size; anything else still declines the grouping.
- The extra regions are appended after the packed MLA+indexer regions of the GLM block (per-layer tensors, offset = `extra_base + region_bytes * num_blocks`), and `_get_kv_cache_bytes_per_block`, `get_kv_cache_config_from_groups` and `_max_memory_usage_bytes_from_groups` charge the extra groups at the packed stride.

No behavior change for models without a drafter (all existing glm5 tests pass unchanged), and no change for non-GLM spec-decode groupings.

### Reproduction (CPU-only, no weights)

```python
import torch
from types import SimpleNamespace
from vllm.v1.core.kv_cache_utils import _get_kv_cache_groups_glm5_next
from vllm.v1.kv_cache_interface import (
    MLAAttentionSpec, SlidingWindowSpec, MambaSpec, KpoolTailSpec)

BS, BF16 = 1280, torch.bfloat16   # unified block after mamba alignment
specs = {}
for i in range(11):  # 11 dense MLA + indexer + kpool tail layers
    specs[f"layers.{4*i+3}.attn"] = MLAAttentionSpec(
        block_size=BS, num_kv_heads=1, head_size=576, head_size_v=0,
        dtype=BF16, cache_dtype_str=None)
    specs[f"layers.{4*i+3}.indexer"] = MLAAttentionSpec(
        block_size=BS, num_kv_heads=1, head_size=128, head_size_v=0,
        dtype=torch.uint8, cache_dtype_str=None, tokens_per_state=8)
    specs[f"layers.{4*i+3}.tail"] = KpoolTailSpec(
        block_size=BS, num_kv_heads=1, head_size=128, head_size_v=0,
        dtype=torch.uint8, sliding_window=32, tokens_per_state=8)
for i in range(34):  # 34 KDA/mamba layers
    specs[f"layers.{i}.kda"] = MambaSpec(
        block_size=BS, shapes=((8, 128, 128), (8, 128, 256)),
        dtypes=(BF16, BF16))
for i in range(5):   # drafter: 5 GQA sliding-window layers @ draft block size
    specs[f"draft.layers.{i}.self_attn.attn"] = SlidingWindowSpec(
        block_size=16, num_kv_heads=2, head_size=128, head_size_v=128,
        dtype=BF16, sliding_window=2048)

spec_cfg = SimpleNamespace(
    method="dflash", use_eagle=lambda: True, use_eagle_block_drop=lambda: True,
    num_speculative_tokens=8, use_multi_module_mtp=lambda: False)
cfg = SimpleNamespace(
    cache_config=SimpleNamespace(num_gpu_blocks_override=None, mamba_cache_mode="align",
                                 prefix_match_unit=16, prefix_cache_retention_interval=1280,
                                 block_size=BS),
    parallel_config=SimpleNamespace(pipeline_parallel_size=1, decode_context_parallel_size=1,
                                    enable_expert_parallel=True, tensor_parallel_size=4),
    speculative_config=spec_cfg,
    model_config=SimpleNamespace(max_model_len=262144),
    max_in_flight_tokens=64,
    scheduler_config=SimpleNamespace(max_num_seqs=4))

print(_get_kv_cache_groups_glm5_next(cfg, dict(specs)))  # None on main
```

On unpatched main the builder returns `None`; running the same spec map through `get_kv_cache_groups` ends with the `NotImplementedError` above (the indexer page cannot be padded to the MLA page).

### Tests

- New unit tests in `tests/v1/core/test_kv_cache_utils.py`:
  `test_glm5_next_drafter_gets_its_own_eagle_group` (builder produces the drafter group with `is_eagle_group`, target block size, draft regions appended after the packed regions with no overlap with any other tensor, correct bytes-per-block and max-memory accounting) and `test_glm5_next_drafter_gate_requires_eagle_family` (builder declines without an EAGLE-family spec config). Both fail on main (RED: no draft group) and pass with the fix.
- `tests/v1/core/test_kv_cache_utils.py`: 158 passed; the 3 pre-existing `estimate_max_model_len` / `get_max_concurrency` cases are unchanged env/network cases.

### Verified

End-to-end on 4×A100 (TP4+EP4, AWQ W4A16, ctx 262144, block 1280) with the `GLM-5.3-Flash-DFlash2` drafter: server starts, prefix caching / reasoning & tool parsers work, speculative acceptance metrics normal; stable for hours under agent traffic.

### Note for reviewers

The one visible side effect: the GLM block is mamba-aligned (1280 tokens at TP4 in our setup), so `prefix_cache_retention_interval` must stay a multiple of the unified block — the builder already requires the extra groups to share the attention block size, which is what makes the layout valid.

Related: #58638 (RFC: KV cache grouping for hybrid models with speculative drafters)
