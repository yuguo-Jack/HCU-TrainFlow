# [FlashInfer] Migrate autotune warmup to flashinfer.autotune_v2 managed cache

[Upstream PR](https://github.com/vllm-project/vllm/pull/55671) · state: open · merged: False

## Original PR description

## Overview

Use FlashInfer's managed autotune cache for eligible single-rank deployments, with shared v1/v2 warmup execution. Multi-rank deployments retain upstream's legacy cache synchronization; this scoped migration can land independently of [FlashInfer #6185](https://github.com/flashinfer-ai/flashinfer/pull/6185).

## Claims

- Automatically select managed v2 when both APIs are present and the deployment is single-rank, single-node, PP=1 and non-elastic.
- Preserve #57635's per-rank legacy files, group-wide cache validation and PP stage-specific tuning groups. Multi-rank managed tuning remains disabled until a released FlashInfer fix is pinned and validated.
- Share generic warmup execution, including HiSparse, ReplaySSM and Kimi, and preserve the MRv2 sparse warmup route. Retain main's speculative-drafter bucket coverage and `round_up=True`; follow main's removal of the separate BF16-only pass.

This is a cache-lifecycle migration, with no claim of universal deadlock prevention, zero warm-start profiling or improved serving throughput.

## Details

**Mixed cache hits can hang before finalization.** A partial rank-specific cache, or another publisher between rank lookups, can make one rank skip profiling while another enters timing collectives. A final barrier/reload cannot repair that mismatch. [FlashInfer #6185](https://github.com/flashinfer-ai/flashinfer/pull/6185) coordinates the pre-profiling hit decision in the library. The single-rank gate here avoids enabling this distributed managed-cache path on the current pin. Re-enabling it requires a library release, a pin update and validation; PP, multi-node and Elastic EP retain additional constraints.

`VLLM_FLASHINFER_AUTOTUNE_CACHE_DIR` controls placement; FlashInfer owns managed entry/environment identity. Independently tuning deployments should use separate roots. Legacy persistence retains `autotune_configs_dp<dp>_rank<rank>.json` and group-coordinated load success.

SM120 sparse-MLA CPB/crossover calibration is a separate cache under `FLASHINFER_AUTOTUNE_DIR`; managed winner reload does not distribute its file or install its process-local state. The reporter supplied a private-API-based patch; supported calibration distribution and affected-hardware validation remain separate follow-up work. Some non-default per-op measurement policies also re-profile on warm starts.

This updates the existing migration, incorporates YangXu1990uiuc/vllm#1, and preserves the merged #57635. The open cache-only startup/search-strategy work addresses different behavior. FlashInfer #3573 handles EP/DP-aware profiling and final synchronization, not the pre-profiling hit decision. All conversation/review pages were revisited under the PR checklist. AI assistance was used for review, implementation and validation; the human submitter remains responsible for the contribution.

- Col-5555 · comment · 2026-10-06T09:56:37Z · [source](https://github.com/vllm-project/vllm/pull/55671#issuecomment-6013808100)

A note on the sparse-MLA calibration side file that this PR's docstring mentions ("some sparse kernels use a separate calibration cache"). It comes from 2× GB10 (TP=2 across two nodes, so the legacy path here), GLM-5.3-Flash NVFP4, vLLM `4be061c5`, FlashInfer 0.7.0.

FlashInfer measures the SM120 sparse-MLA cpb constants, the decode/prefill crossover and the per-shape overrides only in tuning mode. It keeps them in `sparse_mla_sm120_cpb.json`, not in the autotuner's winner cache. On the legacy path only rank 0 runs the sparse warmup in tuning mode, and only the winner cache is broadcast, so the side file exists on rank 0 alone. On our pair, rank 0's file set the 32-head GLM decode/prefill crossover at 16 tokens, with a cpb override at T=16. Rank 1 had no file, so it used decode-first routing up to 64 tokens and the C++ cpb heuristic. The two ranks therefore ran different kernels and splits for 17–64-token calls. A kernel-level check showed that the cpb choice alone changes rounding: up to 9 distinct outputs across 9 cpb values on the same input. We didn't attribute a wrong answer to it, but it means the numerics depend on which node happens to hold a file.

With the managed path in this PR, every rank runs the sparse warmup in tuning mode, so every rank calibrates for itself. That fixes the missing file. But as flashinfer#5142 shows on the same hardware, in-boot calibration is noisy (`c0` about 10 % high during startup, once 7×). So independent per-rank fits can still land on different crossovers or overrides, and can change from one boot to the next.

What we do on the legacy path: after the warmup and before graph capture, rank 0 broadcasts its side file, the other ranks write it atomically and load it into FlashInfer's process cache, and every rank logs its sha256. We also pin one measured file in the image (via `FLASHINFER_AUTOTUNE_DIR`), which is the pre-calibrate-and-reuse approach #5142 suggests. **What it does.** It adds one function, `_sync_sparse_mla_cpb_calibration(world, is_leader)`, that every rank calls right after the sparse warmup. That is before the existing winner-cache broadcast, and so before CUDA graph capture, which bakes the host-side routing choices into the graphs.

1. Rank 0 reads its side file (FlashInfer's `default_cache_path()`) and `broadcast_object`s the bytes; `None` if it has none.
2. The other ranks write the bytes under a `FileLock` and `os.replace` them into place.
3. **Install step:** every rank passes the parsed document to `_sparse_mla_sm120_cpb._publish_payload(doc)`, but only if `doc["schema_version"] == _SCHEMA_VERSION` (the same rule FlashInfer applies when it reads the file).
4. Every rank logs the file's sha256, so a mismatch between ranks shows up in the boot log.

**Why step 3 is needed.** Writing the file is not enough. FlashInfer re-reads the file only for entries it does not hold in memory yet (`get_constants`, `get_decode_max_tokens`, `get_cpb_override`). So a rank that already loaded or defaulted a value during warmup would keep it. `_publish_payload` puts the document into FlashInfer's process caches and bumps the constants version, so memoised picks are recomputed. Both of the names used are private. The patch therefore checks that they exist and raises if they don't, rather than silently doing nothing after a FlashInfer bump. If rank 0 has no file, every rank keeps its own and a warning is logged.
