# [Bugfix] Fix DeepSeek-V4 FP8 O-projection crash with a forced --linear-backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/60920) · state: open · merged: False

## Original PR description

## Overview

Fixes #60587

DeepSeek-V4 with a block-FP8 checkpoint fails at engine init when `--linear-backend` forces a non-DeepGEMM FP8 kernel, for example `--linear-backend marlin`. The error is a `torch.bmm` shape error in `deep_gemm_fp8_o_proj`. This change picks the kernel again for block-FP8 `is_bmm` layers after loading. On CUDA, `wo_a` then always gets the DeepGEMM layout that the O-projection reads.

Compared with #56119, this fix:

- Fixes the other forced backends too, not only Marlin: [#56119](https://github.com/vllm-project/vllm/pull/56119) guards only the Marlin case. On its tree, `humming` still fails with the issue's 4x shape error, and `triton` and `cutlass` fail with `t.dim() == N`. All of them pass with this change.
- Keeps `wo_a` in FP8: [#56119](https://github.com/vllm-project/vllm/pull/56119) runs `wo_a` as a bf16 copy through `torch.bmm`. On the reproducer below, that leaves 0.75 GiB less KV cache per GPU (65.97 vs 66.72 GiB with FlashMLA, 66.33 vs 67.08 GiB with FlashInfer).
- Tests the path that failed: The new test builds a real block-FP8 layer and runs `deep_gemm_fp8_o_proj`. It fails on the old code with the issue's error. The regression test in [#56119](https://github.com/vllm-project/vllm/pull/56119) uses a fake Marlin kernel and checks only the weight dtype.
- Is smaller and reuses existing kernel selection: It adds 29 lines in `vllm/` against 76. It picks the kernel again after loading, as the ModelOpt MXFP8 path already does, and adds no new dequantize helper that repeats `scaled_dequantize()`.


## Claims

- `deepseek-ai/DeepSeek-V4-Flash-Vision-Exp` with `--linear-backend marlin` now starts and serves. Both attention paths named in the issue work: the default (FlashMLA) and `--attention-backend FLASHINFER_MLA_SPARSE_DSV4`. Before, engine init failed in the memory-profiling forward pass.
- The same change fixes `humming`, `triton` and `cutlass` as forced backends. They broke `wo_a` in the same way.
- All other linear layers still use the requested backend. Only `wo_a` takes DeepGEMM. The model never calls `wo_a`'s own kernel. It only reads its weight.
- A new unit test covers this. It fails on the old code with the issue's error.

## Details

**Root cause.** DeepSeek-V4 builds `wo_a` as a plain `ColumnParallelLinear` and sets `is_bmm = True` after construction. So `Fp8LinearMethod.create_weights` picks `wo_a`'s kernel as for any other linear layer. The model never calls that kernel. `deep_gemm_fp8_o_proj` reads `wo_a.weight` and its scales directly and runs DeepGEMM's grouped `fp8_einsum`. That needs an FP8 weight in DeepGEMM's `(groups, rank, K)` layout. On CUDA, only `DeepGemmFp8BlockScaledMMKernel` reads `is_bmm` and builds that layout. With the default backend, DeepGEMM comes first, so it works. With `--linear-backend marlin`, Marlin repacks the FP8 `(4096, 4096)` weight into int32 tiles `(256, 16384)`. The O-projection then sees a non-FP8 dtype and takes its bf16 `torch.bmm` branch. There, `view(4, 1024, -1)` gives `[4, 1024, 1024]`, which is 4x too small. Triton and Cutlass leave the weight 2-D, so DeepGEMM asserts `t.dim() == N`.

A debug print at the entry of `deep_gemm_fp8_o_proj` confirmed this. Before the fix, `wo_a.weight` was `torch.int32 (256, 16384)` with `MarlinFP8ScaledMMLinearKernel`. With the fix, it is `torch.float8_e4m3fn (4, 1024, 4096)` with `DeepGemmFp8BlockScaledMMKernel`. The input shape was right (32 local heads = 4 groups x 8 heads).

**Fix.** This follows the ModelOpt MXFP8 path, which already picks the kernel again for `is_bmm` layers in `process_weights_after_loading`.

- `init_fp8_linear_kernel` takes a new `is_bmm` argument. For block FP8 it then uses `_POSSIBLE_FP8_BLOCK_BMM_KERNELS`. On CUDA that list holds only `DeepGemmFp8BlockScaledMMKernel`. Other platforms keep their usual lists, so ROCm, XPU and CPU do not change.
- `Fp8LinearMethod.process_weights_after_loading` picks the kernel again for a block-FP8 `is_bmm` layer, because `is_bmm` is set by then.
- If `--linear-backend` has no kernel in that list, the existing `_resolve_backend_kernels` logs the warning shown above and uses automatic selection for that layer.

**Limitations.**

- With `VLLM_USE_DEEP_GEMM=0` and `--linear-backend marlin`, startup now fails at load with `ValueError: Failed to find a kernel`. Before, it failed at the first forward pass. The message says only Hopper and Blackwell are supported, which is misleading on a B200.
- XPU may have a similar gap. `xpu_sparse.py` reads `wo_a.bmm_weight`, and only `XPUFp8BlockScaledMMKernel` sets it, so `--linear-backend triton` on XPU could fail. This is not changed, because XPU could not be tested here.
- Other quant methods that call `init_fp8_linear_kernel`, for example compressed-tensors FP8 block, do not pick the kernel again for `is_bmm`. No DSV4 checkpoint used here goes through them.
- Not run on GB10 (SM 12.1). `support_deep_gemm` includes the SM 12.x family, so `wo_a` should get DeepGEMM there too.
- `cutlass` and `humming` also failed before and pass now, but they are not in the test. Humming needs an optional package, and Cutlass block support depends on the GPU.
