# [ROCm] ROCm binding on common Kimi-K3 Dspark MLA module

[Upstream PR](https://github.com/vllm-project/vllm/pull/60857) · state: open · merged: False

## Original PR description



## Purpose

On ROCm, Kimi-K3 DSpark currently instantiates the NVIDIA draft module. This PR registers `K3DSparkModel` as `("vllm.models.kimi_k3", "K3DSparkForCausalLM")` and, on ROCm, imports `amd.dspark_mla`. CUDA still imports `nvidia.dspark_mla`.
Builds on top of #60054
Replaces #57942, which was the duplicate-and-modify approach (not touching NVIDIA).

## What changes

`amd/dspark_mla.py` is a binding over the common classes: a factory, `build_self_attn`, `build_mlp`, and `kv_cache_layer` returning `attn.mla_attn`.
Draft attention is `KimiK3MultiHeadLatentAttentionWrapper` around generic `MLAAttention`, with RoPE and `non_causal_multi_token_decode=True`.
`KimiMLAAttention` is not used: it is NoPE-only, and would add a second wrapper.
Context-KV insert, the weight mapper, the Markov head, and the confidence head stay in the common module, so the #58814 refresh and adaptive verification come along with the dispatch.

The factory duplicates the NVIDIA projection and YaRN setup.
The docstring records the settings that have to stay aligned.

HIP YaRN returns fp32. The query slice assignment casts Q back to bf16,
and rebinding `k_pe` used to leave it fp32. `concat_and_cache_mla` then stored those bits as the KV dtype.
After RoPE, the wrapper casts `k_pe` back with `k_pe.to(kv_c_normed.dtype)`.
On MI355 that cast removed the repetitive garbage in the target output.

Decode-only FP8 with a real embedding must not enter `_fused_decode`.
That path applies a one-row identity RoPE after the wrapper has already rotated.
The call site requires `rotary_emb is None`.
Target K3 still has `rotary_emb is None`, so its launch stays. DeepSeek does not use this wrapper.

## Trace

The baseline draft gap still launches `fusedKimiK3MLADecodeQConcatKVCacheKernel` five times per step, 21 µs total.
The trace for this PR does not use that kernel. Each draft layer instead runs native `DeepseekScalingRotaryEmbedding.forward_hip`, which calls `forward_native`, and then an ungrouped `concat_and_cache_mla`.
On the steady decode shape the eager gap grows from 3.41 ms to 3.85 ms (+0.44 ms, about 13%).

This PR is **slower** than the NVIDIA-module baseline on ROCm. The kernels that replaced the fused decode epilogue are the native YaRN elementwise chain plus the ungrouped cache insert.

## Potential follow-up

If the fusion in the follow-up (#60864) is not merged, then the following alternative should be considered:
`DeepseekScalingRotaryEmbedding.forward_hip` calls `forward_native`.
Pointing it at AITER Triton RoPE would remove the elementwise chain for this draft and for every other HIP model
that uses the same embedding.

## Validation

- `pytest tests/models/test_dspark_mla.py` on ROCm, including `test_k3_dspark_decoder_uses_mla_wrapper` (ROCm-only) and `test_hip_yarn_k_pe_is_cast_back_to_kv_dtype` (CPU; a fake fp32 RoPE, asserting the seen key is bf16).
- `test_amd_kv_cache_layer_returns_inner_mla_attn`: draft KV names end in `.attn`.
- `test_fused_decode_not_taken_when_rotary_emb_is_set`.

## Out of scope

- Integrating AITER `fused_qk_rope_concat_and_cache_mla` (#60864).
- Changing `DeepseekScalingRotaryEmbedding.forward_hip`.

Overall provided solution is slower than the code it replaces. 

The PR reports +0.44 ms per step in eager mode. Two things in this PR's scope cause most of it:

1. The new self.rotary_emb is None fusion check (amd/mla.py:282-284) isn't needed for correctness.
- The fused decode applies a one-row cos=1, sin=0 table. On already-rotated q_pe/k_pe that does nothing.
- On MI355X I called fused_qk_rope_concat_and_cache_mla exactly as _fused_decode does. Run on pre-rotated inputs, the KV rows and the fp8 q_out are byte-identical to the unfused path.
- With VLLM_ROCM_USE_AITER=1 and fp8 KV, this check is the only thing turning off the existing fused decode for the draft. In each of 5 layers, one fused launch becomes a separate cache write plus a q concat and quant.
- Please drop the check (or move it to #60864, where the wrapper skips its own RoPE). Also drop the "double RoPE" wording at :106-108 and :279-281.
 
2. Native YaRN costs 15 kernel launches per layer (75 per step): the forward_native elementwise chain, the slice copy-back, and the cast. 
 - An in-place ops.rotary_embedding(positions, q[..., nope:], k_pe, ...) with the fp32 table does it in 1. The common module already uses this op for context-KV RoPE.
 - It also makes the k_pe cast unnecessary. k_pe comes out byte-identical, and q differs by at most 1 bf16 ulp on a tiny fraction of elements.
 - Please re-measure in the mode production uses. The draft replays inside full CUDA graphs there, so the eager 3.41 → 3.85 ms overstates the per-step cost.
