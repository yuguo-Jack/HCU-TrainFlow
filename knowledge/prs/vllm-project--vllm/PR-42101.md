# [Frontend] Add serve warmup for completions, chat, and embeddings

[Upstream PR](https://github.com/vllm-project/vllm/pull/42101) · state: open · merged: False

## Original PR description

## Summary

This PR adds a pre-serve warmup feature for `vllm serve` that runs real requests against the async engine before the HTTP server starts accepting traffic. This avoids the first served request paying the lazy kernel compilation cost.

### What changed

- `vllm/entrypoints/warmup.py` (new): adds `WarmupConfig`, `WarmupPrompt`, `load_warmup_config()`, and `warmup_engine()`.
- `vllm/entrypoints/launchers/cli_args.py`: adds `--warmup-config` to `FrontendArgs` (serve only; not accepted by `run-batch`).
- `vllm/entrypoints/launchers/launcher.py`: parses and validates the config in `validate_api_server_args`, before the engine starts, and passes the parsed config to every API server worker via `args`.
- `vllm/entrypoints/launchers/api_server/entry.py`: runs warmup in `build_and_serve` after the app state is initialized and before `serve_http()` starts accepting traffic.
- `docs/serving/warmup.md` (new): documents the config format and serve startup behavior.

Behavior:
- At each concurrency level, every prompt runs: `max(concurrency, num_items)` requests are issued with at most `concurrency` in flight.
- `prompt` and `messages` are rendered through the server's `OnlineRenderer`, the same path as `/v1/completions` and `/v1/chat/completions`, so `--chat-template`, `--chat-template-content-format`, and `--default-chat-template-kwargs` apply.
- Embedding warmup uses `PoolingParams(task="embed")` like `/v1/embeddings`, and sends one request per string of a list-valued `input`.

### Why this is not duplicating existing work

I checked the existing issue and PR space for warmup-related work. The nearby work is about internal kernel warmup, speculative decoding warmup, or benchmark warmup. This PR is different because it adds a user-configurable serve startup warmup that exercises the real async serving path for completions, chat completions, and embeddings.

### Test commands and results

- `pytest tests/entrypoints/unit_tests/test_warmup.py`: 32 passed. Covers config parsing and validation, and `warmup_engine` scheduling against a mock engine client.
- `pre-commit run --files <changed files>`: passed.
- Not run: an end-to-end `vllm serve --warmup-config` on a GPU.

File: `vllm/entrypoints/llm.py` · line None

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The warmup implementation in the `LLM` class is inefficient and inconsistent with the `WarmupConfig`. It processes prompts one by one in a loop, ignoring the `concurrency` setting and missing the opportunity to use vLLM's batching capabilities. Passing all prompts at once to `self.generate`, `self.chat`, or `self.encode` is significantly more efficient and better simulates real-world usage patterns.

```python
    def _warmup_generate(self, warmup_cfg: WarmupConfig) -> None:
        chat_prompts, chat_params = [], []
        gen_prompts, gen_params = [], []

        for prompt_config in warmup_cfg.prompts:
            sampling_params = SamplingParams(
                max_tokens=prompt_config.max_tokens,
                **warmup_cfg.request_params,
            )
            if prompt_config.messages is not None:
                chat_prompts.append(prompt_config.messages)
                chat_params.append(sampling_params)
            else:
                gen_prompts.append(prompt_config.prompt or "")
                gen_params.append(sampling_params)

        if chat_prompts:
            self.chat(messages=chat_prompts, sampling_params=chat_params, use_tqdm=False)
        if gen_prompts:
            self.generate(prompts=gen_prompts, sampling_params=gen_params, use_tqdm=False)

    def _warmup_embed(self, warmup_cfg: WarmupConfig) -> None:
        prompts = [p.get_input_text() or "" for p in warmup_cfg.prompts]
        if prompts:
            self.encode(prompts=prompts, use_tqdm=False)
```

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The current implementation has a potential `UnboundLocalError` and leaks the background server task if an exception occurs during warmup. If `warmup_engine` raises an exception (e.g., due to an invalid configuration or engine error), `shutdown_task` is never assigned, causing line 758 to fail. Additionally, the `server_task` (uvicorn) will continue running in the background while the engine client is being shut down by the context manager, leading to a zombie server state. The server task should be cancelled if warmup fails.

```python
        # Start server in background so it accepts connections during warmup
        server_task = asyncio.create_task(
            build_and_serve_from_app(app, listen_address, sock, args, **uvicorn_kwargs)
        )

        try:
            # Give uvicorn a moment to begin accepting connections
            await asyncio.sleep(1)

            # Run warmup while server is already serving /health as 503
            warmup_cfg = load_warmup_config(args.warmup_config)
            if warmup_cfg is not None:
                await warmup_engine(engine_client, warmup_cfg)

            # Mark ready; /health will now return 200
            app.state.warmup_complete = True

            # Await server shutdown
            shutdown_task = await server_task
        except Exception:
            server_task.cancel()
            shutdown_task = server_task
            raise
```

- gemini-code-assist · comment · 2026-05-08T17:47:17Z · [source](https://github.com/vllm-project/vllm/pull/42101#discussion_r3210409764)

File: `vllm/entrypoints/warmup.py` · line None

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The `concurrency` parameter is currently ignored in terms of actual parallel execution. The nested loops process prompts sequentially, awaiting each `generate` call before starting the next. To properly warm up the engine for concurrent load (and trigger associated logic like CUDA graph capture for larger batches), multiple requests should be launched in parallel using `asyncio.gather`. This suggestion also incorporates a fix for token-based prompts (see the related comment on `_render_messages`).

```python
async def _warmup_generate(
    engine_client: "EngineClient",
    config: WarmupConfig,
) -> None:
    for concurrency in config.concurrency:
        logger.info(
            "Warming up generate with concurrency=%d, %d item(s)",
            concurrency,
            len(config.prompts),
        )

        async def run_one(prompt_config: WarmupPrompt, idx: int):
            sampling_params = _get_sampling_params(prompt_config, config.request_params)
            request_id = f"warmup_{id(prompt_config)}_{concurrency}_{idx}"

            prompt = None
            prompt_token_ids = None

            if prompt_config.prompt is not None:
                prompt = prompt_config.prompt
            elif prompt_config.messages is not None:
                engine_input = await _render_messages(
                    engine_client,
                    prompt_config.messages,
                )
                if isinstance(engine_input, dict):
                    prompt = engine_input.get("prompt")
                    prompt_token_ids = engine_input.get("prompt_token_ids")
                else:
                    prompt = getattr(engine_input, "prompt", None)
                    prompt_token_ids = getattr(engine_input, "prompt_token_ids", None)
            
            async for _ in engine_client.generate(
                prompt=prompt,
                prompt_token_ids=prompt_token_ids,
                sampling_params=sampling_params,
                request_id=request_id,
            ):
                pass

        tasks = [
            run_one(config.prompts[i % len(config.prompts)], i)
            for i in range(concurrency)
        ]
        await asyncio.gather(*tasks)
```

![high](https://www.gstatic.com/codereviewagent/high-priority.svg)

The `_render_messages` function and its usage in `_warmup_generate` do not account for chat templates that produce token IDs instead of raw strings (e.g., Mistral models or when `tokenize=True` is set). `_render_messages` currently returns a string representation of the `EngineInput` object, which will cause the engine to attempt to tokenize the literal string representation of a dictionary or list, leading to incorrect warmup or errors. It should return the `EngineInput` directly.

```suggestion
async def _render_messages(
    engine_client: "EngineClient",
    messages: list[dict[str, Any]],
) -> Any:
    """Convert a list of chat messages to an engine input object."""
    from vllm.renderers import ChatParams

    renderer = engine_client.renderer
    chat_params = ChatParams()

    _, engine_inputs = await renderer.render_chat_async(
        [messages],
        chat_params,
    )

    return engine_inputs[0]
```
