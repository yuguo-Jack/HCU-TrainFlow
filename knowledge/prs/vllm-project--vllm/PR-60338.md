# [Benchmark] NVIDIA Confidential Computing CPU<->GPU bridge microbench

[Upstream PR](https://github.com/vllm-project/vllm/pull/60338) · state: open · merged: False

## Original PR description

## Purpose

Adds a standalone microbenchmark (`benchmarks/confidential_compute/`) that measures how host<->device copies behave under NVIDIA GPU Confidential Computing (CC) and what that does to a vLLM-style decode loop. It does not import vLLM and changes no runtime code.

Tests: `semantics` (does a `non_blocking` copy block the host), `bandwidth`, `concurrency` (streams/threads/processes), `decode` (sync / async / staged-H2D / staged-H2D + D2H worker). `compare.py` diffs a CC-off and a CC-on JSON.

It gives the CC decode work in #52226 and #59981 a way to be validated on CC hardware. Touches only `benchmarks/confidential_compute/*` and one allowlist line in `tools/pre_commit/check_torch_cuda.py`.

## Not a duplicate

Checked against open PRs on 2026-10-06:

- #52226 and #59981 (CC decode optimizations, V1/V2 runner) change runtime code in `vllm/`; this PR adds only a benchmark and does not touch them.
- #57404 and #57415 (UVA fail-closed under CC) are runtime bugfixes.
- No open PR for "confidential computing" or "52226 in:body" adds a CC copy microbenchmark.

## Test Plan / Results

- `pre-commit run --files benchmarks/confidential_compute/* tools/pre_commit/check_torch_cuda.py`:
  all hooks pass.
- `compare.py` rendered correctly on two synthetic CC-off/CC-on JSON files.
- **Ran `run.sh --quick` on real CC hardware:** Azure `Standard_NCC40ads_H100_v5`
  (NVIDIA H100 NVL), `nvidia-smi conf-compute -f` reports `CC status: ON`, driver
  595.71.05, torch 2.13.0+cu130, `multi_gpu=none`. One `--quick` run, so treat the
  numbers as indicative, not as a tuned measurement. CC-off was not run. The run used
  a copy of `cc_bridge_bench.py` from just before this PR's last commit; the two differ
  only in the concurrency worker's error reporting and the D2H worker pool shutdown, not
  in any timed path.

| Case (CC on) | Result |
| --- | --- |
| Pinned H2D, `non_blocking=True`, same stream as 20 ms of queued work | host blocked **19.9 ms** (`blocks_on_busy_work`) |
| Pinned H2D on an idle stream | returns in **51 us** (`async`) |
| Pinned D2H, same stream / event-wait stream | blocked **19.9 ms** |
| Pageable H2D | `async` (47-78 us); pageable D2H still blocks like pinned |
| Pinned bandwidth, 16 MiB | 8.4 GB/s H2D, 9.5 GB/s D2H; streams and threads give x0.98-x1.02 |
| Decode loop, 3 ms forward: sync / async | step 4628 us / 4632 us (**x1.00**: async buys nothing) |
| Decode loop, 3 ms forward: staged H2D + D2H worker | step 3155 us (**x1.47**), GPU busy 65% -> 95% |
| Decode loop, 10 ms forward: staged H2D + D2H worker | step 10201 us (**x1.14**), GPU busy 86% -> 98% |

This matches the bounce-buffer model in the README's "Expected pattern": a pinned copy
issued on a busy stream is host-synchronous under CC, and staging it on a dedicated
stream plus a D2H worker is what recovers the overlap (the approach in #52226).
Reproduce with `bash benchmarks/confidential_compute/run.sh --quick`.

Limits: one GPU model, CC-off baseline not measured, #52226's own numbers are from B300
(NVLE) so Hopper PPCIe remains unvalidated.
