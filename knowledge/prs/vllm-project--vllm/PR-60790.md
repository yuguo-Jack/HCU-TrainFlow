# [Kernel] LiteTopK prefill for GLM-5.2 FP8 TP8 on SM100

[Upstream PR](https://github.com/vllm-project/vllm/pull/60790) · state: closed · merged: False

## Original PR description

## Overview

This is a focused split and kernel refinement of the LiteTopK prefill work in https://github.com/vllm-project/vllm/pull/48726, targeting **GLM-5.2 FP8 with TP8 on SM100/B200**.

As suggested by **@tkoniy from the Hunyuan team**, this version replaces **hotsample with fixed random page sampling** and improves the paged-cache scoring and h2048 selection path.

cc @LopezCastroRoberto @ibrahimnd2000 — please take a look at this focused LiteTopK prefill kernel update and its integration scope.

## Validation

Prepared against vLLM main `e31b823bf59bdd96d09fdcf310c5fb02e934d3bf`. The patch applies cleanly to that commit: **14 files changed, 3740 insertions, 18 deletions**.

Validated on a single B200 using PyTorch 2.13/CUDA 13, the updated main Python sources, and pre-existing vLLM core binaries. Both the LiteTopK CUDA extension and main's pinned DeepGEMM (`1e1842a833699298f7afc02eefb2ed168fff6938`, version 2.8) were compiled from source. DeepGEMM tests use the real patched `out=` implementation, with no allocation-and-copy adapter.

Coverage includes deterministic sampling, partial pages and causal bounds at TP rank offsets 0 and 7, selector boundary/tie/overflow cases, unsupported model and parallel-layout rejection, caller-owned DeepGEMM output, and the existing CP metadata regression. Ruff check/format and `git diff --check` passed. The nested DeepGEMM patch also applies cleanly to its pinned source.

**Full eight-GPU GLM-5.2 inference, model accuracy/quality evaluation, and end-to-end performance measurements have not been run for this main-based revision.** The available validation used one GPU; this description makes no model-quality or speedup claim and does not reuse the earlier hotsample results from #48726.

## Details

The supported target is GLM-5.2. Runtime qualification uses `model_type="glm_moe_dsa"` and `(index_n_heads, index_head_dim, index_topk)=(32, 128, 2048)` because the configuration does not provide a reliable GLM-5.2-only version tag. Other checkpoints with the same configuration are not separately qualified by these tests.

Enable with `VLLM_LITETOPK=1`, TP8, and prefix caching disabled. The optimized path handles single-request prefill chunks of 8192 or 8128 query tokens, split into 1024 or 1016 rows per TP rank, with 64-token KV pages. The default context range is 196608–1048576 tokens. Rank-local results are all-gathered, and ranks agree on whether the fused path succeeded before consuming the result.

The scoped LiteTopK path excludes DeepSeek models, TP4, PCP/DCP, FP4/compressed indexer cache, and prefix-cache reuse. Existing main behavior for these configurations and for decode is retained. The patch contains no hotsample or carry implementation. References to DeepSeek in the shared indexer classes and kernel license identify upstream infrastructure and provenance.

Selection uses high24 score keys, dropping the low eight FP32 bits; it is not a bitwise-equivalent FP32 TopK promise. Invalid or overflowing candidate output fails closed. Planned unsplit chunks cannot safely fall back to allocating full dense logits.

DeepGEMM receives a caller-owned output slab through a separately registered `out` operator with mutation/alias annotations. Its existing allocating operator retains its schema. LiteTopK requires the patched bundled backend or an external backend exposing the same `out=` API.

This extracts and refines the GLM prefill component of #48726; it does not reproduce that PR's LiteDSA or DeepSeek V4 features. The related open decode work (#59921, #59922, #57109) and the single-launch prefill WIP (#60618) were checked. This patch retains separate sample, scan, selection, and mapping stages, so it is not a single-launch implementation. Maybe @ LopezCastroRoberto can help to improve this PR like #60618.
