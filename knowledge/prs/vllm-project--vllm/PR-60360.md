# [Bugfix][Tool Parser] Fix xLAM streaming args: deep nesting and braces in strings

[Upstream PR](https://github.com/vllm-project/vllm/pull/60360) · state: open · merged: False

## Original PR description

## Overview

Fixes #60343. The xLAM parser's streaming path pulled each call's `arguments` object out of the
partial text with a brace-matching regex. Nesting deeper than two levels never matched and a `}`
inside a string value ended the object early, so streamed arguments did not match what
`extract_tool_calls` returns for the same output.

## Claims

- Arguments nested at any depth now stream instead of coming through as `""`.
- A `{` or `}` inside a string value no longer truncates the arguments.
- The streamed deltas for a call concatenate to exactly the non-streaming `arguments` string.

## Validation

New parametrized test `test_streaming_arguments_match_non_streaming` in
`tests/tool_parsers/test_xlam_tool_parser.py` feeds the model output one character at a time, so a
chunk boundary falls at every position including inside the string that holds a brace, and asserts
the concatenated deltas per tool index equal `extract_tool_calls`' arguments.

```
pytest tests/tool_parsers/test_xlam_tool_parser.py
```

Four cases: `deeply_nested_arguments`, `brace_inside_string_value`, and `flat_arguments` plus
`parallel_calls` as regression cover for the shapes that already worked. Driving the parser with
that same body, the two new cases produce `''` and `'{"text": "use }'` before the change and the
full arguments after it, while the two regression cases are unchanged.

`ruff check` and `ruff format --check` are clean on both changed files.

Model evaluation: not applicable. This only changes how already-decoded tool-call arguments are
sliced into streaming deltas in the API layer. It touches no weights, sampling, kernels or
scheduling, so identical generated text gives identical results.

## Details

Root cause is the regex `(\{(?:[^{}]|(?:\{[^{}]*\}))*\})`. It hard-codes one level of inner braces,
and `[^{}]` does not know about string literals, so `{"text": "use } to close"}` matches only as far
as the `}` inside the value. Once that short string is streamed it is also recorded as sent, and
nothing re-sends the tail.

`_extract_complete_arguments` replaces it with a scan using `json.JSONDecoder.raw_decode` from the
same `"name": ..., "arguments":` anchor the regex used. `raw_decode` gets nesting and string escapes
right for free, and raises on an object that is still arriving, which is the signal the streaming
loop already wanted: the scan stops there, so the list holds exactly the argument objects that have
arrived whole. Each one is serialised with `json.dumps(..., ensure_ascii=False)`, matching the
non-streaming path and the existing multi-tool branch just below.

Not a duplicate: `gh pr list --state open --search "60343 in:body"` is empty, and of the open PRs
touching this file #51698 fixes duplicated arguments on finalize and markers leaking into content,
and #47954 and #49535 fix the empty-arguments and phantom-tool-call detection. None of them touch
the argument-extraction regex, and this change does not touch what they do.
