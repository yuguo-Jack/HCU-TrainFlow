# [Model] Kolibri 1 via the Transformers modeling backend

[Upstream PR](https://github.com/vllm-project/vllm/pull/60827) · state: open · merged: False

## Original PR description

## Overview

Serve `Kolibri1ForCausalLM` via the Transformers modeling backend.
Not a duplicate of #60026: this is the Transformers-backend alternative its review suggested.

## Details

- Needs the `kolibri1` model from huggingface/transformers#49463.
- Second commit: under external routing, a shared expert now runs in `MoERunner`, overlapping with the routed experts as under internal routing. This only applies when the block is exactly `experts(x, ids, weights) + shared(x)` with `_, weights, ids = gate(x)` (up to reshapes); other blocks keep the HF forward.
- For Kolibri 1 FP8, set `VLLM_USE_DEEP_GEMM=0` to preserve the checkpoint's FP32 block scales. This is documented in the supported-models page.

## Validation

- `pytest tests/models/transformers` (macOS, CPU): 144 passed; the 16 failures and 1 error also fail on main `59ffd73e85`.
- vs #60026 with transformers#49463 installed, real FP8 weights, DeepGEMM off in both:
  - GSM8K: 94.2% vs 94.5% on B200, 94.2% vs 94.2% on DGX Spark.
  - B200, mean of two runs each in mirrored order (throughput: 256 prompts of 1024 in / 256 out; latency: 512 in / 256 out):

    | | Output tok/s | bs1 latency | bs32 latency |
    |---|---|---|---|
    | #60026 | 9930 | 1.297 s | 2.246 s |
    | This PR | 9822 (−1.1%) | 1.375 s (+6.0%) | 2.267 s (+0.9%) |

- TP=2 (2× DGX Spark, tiny random Kolibri): same error vs HF fp32 with and without the second commit.
- Tiny random Qwen2-MoE (internal routing): outputs unchanged by the second commit.
- After removing the automatic override: DGX Spark GSM8K 1245/1319 (94.4%) with `VLLM_USE_DEEP_GEMM=0`; `.venv/bin/python -m pytest tests/models/transformers/fusers/test_moe.py`: 19 passed.
