# [Bugfix][EPLB] Clear the load window when the expert map changes

[Upstream PR](https://github.com/vllm-project/vllm/pull/60686) · state: open · merged: False

## Original PR description

## Purpose
Fixes #60685.

EPLB records load per physical slot. When step_interval < window_size part of the window still holds load recorded under the old map, and the next rearrange counts it for the expert that now occupies the slot.

This clears the window when the new map is committed. Sync clears every layer in `_commit_eplb_maps`. Async clears only the committed layer in `_commit_eplb_maps_for_layer`. The window has already been summed or copied by then, so the current rearrange is not affected. After a rearrange the history only covers the steps since the new map. The defaults are not affected because their window is fully refreshed before every rearrange.

No open PR fixes this. #49700 only clears the window on an elastic EP topology change.

- itayalroy · CHANGES_REQUESTED · 2026-10-09T22:13:47Z · [source](https://github.com/vllm-project/vllm/pull/60686#pullrequestreview-5475837563)

This is a real issue with our current EPLB implementation (I mentioned it in #58473’s description as well), but I see two problems with this fix:

1. This is dangerous for async EPLB. Async EPLB transfers one layer at a time, so `_commit_eplb_maps_for_layer()` for the last layers might happen very close to the next EPLB reshuffle, depending on transfer time and window/step configs. That reshuffle could use very little data for those layers, or even no data if the last layer is committed in the same step that triggers a reshuffle. This can result in really bad mappings which severely hurt e2e performance.

2. For sync EPLB, this change effectively silently sets window_size to step_interval whenever window_size > step_interval, which is pretty misleading

I spent some time thinking about this while fixing #58473. I think the safest solution is to record load by logical expert, so changing the physical mapping does not invalidate the history. But this is not an easy change as we need to make sure we do it without slowing down statistics collection.

- almogtavor · comment · 2026-10-11T17:47:34Z · [source](https://github.com/vllm-project/vllm/pull/60686#issuecomment-6111881154)

Thanks @itayalroy it makes sense. What do you think about doing the logical conversion once per step instead of in the forward pass?

I mean leaving the forward pass as is so it keeps counting per physical slot in `expert_load_pass`. Then, in `step()` when the `expert_load_pass` is copied into `expert_load_window` we can apply`scatter_add_` by the logical ID using the `physical_to_logical_map` so the window will hold load per logical expert. The scatter index is cached and rebuilt only when the map changes.

I think this is safer than counting by logical ID in the forward pass, since recording code stays untouched, including the code that lives in `_eplb_map_and_record_i32_kernel` in `base_router.py` and also in model specific paths like deepseek_v4 and kimi_k3 that would otherwise need to change. `log_balancedness` also needs the per-physical counts to compute load per rank, and this keeps them. The extra work runs once per step for all layers together and not once per layer per forward. It solves both of your points because the copy happens before any commit. Nothing has to be cleared when the map changes.

I measured it on 4xH100 with DeepSeek-V2-Lite-Chat and EP with rearranges every 200 steps. The per-step copy went from about 9.2us to 10.5us, rearrange() got about 2x faster because the window is already logical, and E2E throughput was 80.3 req/s on main vs 81.3 with this change over 6 runs each. Already updated the PR with this, but happy to change it if you prefer a different approach

I benchmarked this PR with DeepSeek V4 Pro on 20 GB200 GPUs. Compared with upstream, the median gap between forward passes (measured with CUDA events immediately after one forward call and before the next) increased by about 11 µs, and the EPLB step itself increased by the same amount. No measurable effect on e2e performance though.

I suspect the extra kernel launch accounts for much of that 11 µs. A fused Triton kernel would probably help here (it could even improve performance over upstream as we can fuse three kernels into one, compared with two kernel launches in upstream), but it would add code complexity, so not sure if it is worth it.
