# [Bugfix] Probe optional HF files directly instead of listing the repo

[Upstream PR](https://github.com/vllm-project/vllm/pull/60750) · state: open · merged: False

## Original PR description



## Overview

`file_or_path_exists` now probes the one file it is asked about with `hf_hub_download`, instead of listing the whole repo through the Hub tree API. On Oct 8, main CI hit the Hub API rate limit ("quota of 100000 api requests per 5 minutes"), and this check was the call that turned the 429s into test failures: about 150 jobs failed across builds 93613–93655.

## Claims

- `file_or_path_exists` no longer calls `/api/models/{repo}/tree/main?recursive=true`. It sends one `HEAD .../resolve/{rev}/{file}` per file. Resolve requests count against a much larger quota than the listing API.
- When the file is missing, huggingface_hub writes its no-exist cache marker. Later processes therefore answer from disk with **zero** Hub requests. Before, every process listed the repo again.
- The function's return values are unchanged. Offline mode still returns False, and ModelScope still uses its file listing.

## Validation

In the CI image for `4274ae956c`, with a fresh `HF_HOME` shared by 3 sequential processes, each process checks `hf_quant_config.json`, `modules.json` and `config.json` on `Qwen/Qwen3-0.6B`. Hub requests were counted by hooking `httpx.Client.send`:

| | Answers | Hub requests, process 1 | Process 2 | Process 3 |
|---|---|---|---|---|
| main | False, False, True | 1 × `GET /tree/main` | 1 × `GET /tree/main` | 1 × `GET /tree/main` |
| this PR | False, False, True | 3 × `HEAD /resolve` + config.json download | **0** | **0** |

`pytest tests/transformers_utils/test_repo_utils.py`: 12 passed. The new test checks that a 404 returns False, that an existing file returns True, and that `list_repo_files` is never called.

## Details

**Root cause.** I took all 224 failed jobs on main from Oct 8 and traced the HfHubHTTPError tracebacks from the 429s back to their callers:

| Tracebacks | Caller | File checked |
|---|---|---|
| 379 | `get_config` (`config.py:936`) | `hf_quant_config.json` |
| 26 | `get_pooling_config` (`config.py:1012`) | `modules.json` |

Both are optional files that most models don't have, so the local-cache lookup returns `None`. `file_exists` then called `list_repo_files`. That result is cached only per process, a missing file is never recorded, and the call retries on failure. So every process of every model without these files listed the repo again, and when the Hub returned 429 the error propagated. 3,395 of the ~3,420 429 responses in those logs came from the `/tree/` listing endpoint.

**Behavior notes**
- The check now downloads the file when it exists. Every caller reads that file next through `get_hf_file_to_dict`, which then hits the cache, so no extra bytes are transferred.
- Errors other than a 404 still raise, as before. That includes network errors, 429s on resolve, and gated repos.
- `file_exists` is removed; `file_or_path_exists` was its only caller.

**Out of scope:** `is_mistral_model_repo` (config and tokenizer detection) and the `load_format=auto` check in `DefaultModelLoader` still list the repo. They already swallow errors and return False, so they don't fail tests, but they still spend API quota. A follow-up can handle them. vllm-project/vllm#59505 adds a cached-file-list fallback for network errors.

Not a duplicate: I searched open PRs for `file_or_path_exists`, `list_repo_files` and HF rate limiting. The only related one is #59505, which handles a different failure.
