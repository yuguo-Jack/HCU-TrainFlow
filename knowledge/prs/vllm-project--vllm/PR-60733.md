# [Bugfix][MoE] Clamp BLOCK_SIZE_K to the FP8 quantization block in the batched Triton MoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/60733) · state: open · merged: False

## Original PR description



## Overview

`invoke_moe_batched_triton_kernel` (the `BATCHED_TRITON` FP8 MoE used with DeepEP low-latency and other batched-activation all2all backends when DeepGEMM is unavailable or disabled) takes `BLOCK_SIZE_K` straight from the tuned config. With block-quantized FP8 weights the kernel loads one weight and activation scale per `BLOCK_K` tile (`offs_ks = k * BLOCK_K // group_k`), so a `BLOCK_SIZE_K` wider than the 128-wide quantization block applies one block's scale to the next block's values. 53 of the 64 shipped `fp8_w8a8, block_shape=[128,128]` configs pick `BLOCK_SIZE_K` = 256 for some batch sizes. The standard path already clamps (`fused_moe.py:843-844`); this PR applies the same clamp in the batched launcher.

No existing issue or PR covers this (searched `fused_batched_moe BLOCK_SIZE_K`, `BLOCK_SIZE_K batched fp8`, `batched triton block_shape BLOCK_K`). Rechecked 2026-10-08: open PR #51605 resizes batched Triton MoE tiles on XPU and edits the same launcher, but it does not clamp `BLOCK_SIZE_K` for block-quantized FP8 on CUDA; whichever lands second needs a small rebase.

## Claims

- Fixes wrong outputs from the batched Triton FP8 block-quant MoE whenever the selected config has `BLOCK_SIZE_K` > the quantization block. GLM-5.3 FP8 with DeepEP low-latency and DeepGEMM off: GSM8K 0.02 → 0.93.
- No change when the config already has `BLOCK_SIZE_K` <= 128, for per-token / per-tensor FP8, or for unquantized dtypes (`block_shape is None`).
- A smaller `BLOCK_K` can cost some kernel speed for the affected configs; correctness requires it, and the standard Triton MoE path made the same choice.

## Details

**Root cause:** `moe_mmk` iterates K in `BLOCK_K` steps and, for block quantization (`group_k > 0 and group_n > 0`), loads the scales for `k_start // group_k` once per step (`fused_batched_moe.py:162-170`). The launcher passes `config["BLOCK_SIZE_K"]` through unchanged (`:452`). With `BLOCK_K` = 256 and `group_k` = 128, the second half of every K tile is scaled with the first half's scales. `fused_experts_impl` avoids this: its launcher `invoke_fused_moe_triton_kernel` clamps `BLOCK_SIZE_K` to `min(block_shape)` before launch (`fused_moe.py:843-844`), but `BatchedTritonExperts`, which reads the same tuned config files through `try_get_optimal_moe_config` (`fused_batched_moe.py:934`), does not.

**How it was found:** GLM-5.3 RL with prefill/decode disaggregation; the decode instance (DeepEP low-latency, DeepGEMM off) produced much higher trainer-vs-inference KL than the prefill instance. The layer-level GEMM output matched the reference only after capping `BLOCK_SIZE_K`.

**Fix:** clamp `BLOCK_K` exactly as the standard path does.
