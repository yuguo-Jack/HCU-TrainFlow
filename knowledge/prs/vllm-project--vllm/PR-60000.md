# [KV Offload] Add admission policy framework and backpressure adapter

[Upstream PR](https://github.com/vllm-project/vllm/pull/60000) · state: open · merged: False

## Original PR description

## Summary

This PR implements the `TieringAdmissionPolicy` framework described in [RFC #53485](https://github.com/vllm-project/vllm/issues/53485), building on the admission-policy skeleton in [#51576](https://github.com/vllm-project/vllm/pull/51576).

It places the existing per-tier backpressure detectors from [#50045](https://github.com/vllm-project/vllm/pull/50045) behind one admission gate for cascade stores and promotions. The production configuration preserves the existing backpressure decisions while making admission a policy-level extension point.

## Functionality

- Add `TieringAdmissionPolicy`, `AlwaysAdmitPolicy`, `BackpressureAdmissionPolicy`, and `AdmissionPolicyFactory`.
- Evaluate cascade admission before primary-tier pinning and job-ID allocation.
- Evaluate promotion admission before primary allocation.
- Route admitted-job completion and cache-reset lifecycle events through the policy.
- Reuse the existing backpressure detectors, drop accounting, labels, metrics, and transition logging.
- Move backpressure metric definitions and collection into the policy.
- Update P2P and KVCR callers to handle rejected store jobs.
- Add policy and manager-wiring tests.

The policy receives plain admission inputs (`keys`, `tier_idx`, and `is_promotion`). Promotion admission hooks run once for the real batched job, while `JobMetadata` remains defined by the manager and is referenced by policies through `TYPE_CHECKING`.

On the promotion path, `should_admit()` is called per chunk from `lookup()` (here), while `on_admitted()` is called per batched job in [_flush_pending_promotions()](https://github.com/vllm-project/vllm/blob/cda0f3248538da3cc96b3760fe4cfaa7d3d652b9/vllm/v1/kv_offload/tiering/manager.py#L516), which only runs from `on_schedule_end()`.

With this split, I don't see how the `PromotionConcurrencyPolicy` outlined in #51240 could be implemented.
It increments `_inflight` in `on_admitted()`, so `_inflight` can't grow during a scheduler step, so if `self._inflight < self._max` holds at the first lookup, it holds for every lookup in that step. The cap is only enforced between steps, and a single step (a long prefix, or several new requests) can exceed it by an arbitrary amount. For example, with `max=2`, six promotion lookups in one step are all admitted.

Is that intended? If promotion policies are meant to build on this interface, it seems we'd need either a hook at reservation time (right after `prepare_write()` succeeds), or the manager owning the in-flight count and exposing it to the policy read-only.

`should_admit()` isn't side-effect-free here: `detector.should_store()` records drops and advances the throttle and cooldown counters. That contradicts [base.py](https://github.com/vllm-project/vllm/blob/cda0f3248538da3cc96b3760fe4cfaa7d3d652b9/vllm/v1/kv_offload/tiering/admission/base.py#L24-L26) ("no side effects") and #51240.

This breaks composition. With #51240's `CompositePolicy([backpressure, X])`:

- If backpressure admits and X rejects, backpressure's throttle state advances for a store that never happens.
- If X rejects first, all() short-circuits, so the result depends on list order.

`on_admitted()` can't take over this state, since it never fires on rejection. How about keeping `should_admit()` pure and adding `on_rejected(keys, tier_idx, is_promotion)` for the drop accounting, with the throttle and cooldown counters advanced in both hooks?

- ronensc · comment · 2026-10-06T10:03:33Z · [source](https://github.com/vllm-project/vllm/pull/60000#discussion_r4193975466)

File: `vllm/v1/kv_offload/tiering/manager.py` · line 170

This routes peer pins, e.g., from P2P's `_pin_and_register_hits()`, through `should_admit()` as `is_promotion=False`, the same as cascade stores, so an admission policy can't tell them apart. They differ quite a bit:
- **Cost of a rejection:** dropping a cascade to a storage tier only skips a backup copy, while rejecting a peer pin makes the remote instance recompute that prefix.
- **Completion signal:** for a peer pin, submission-to-completion includes waiting for the peer to fetch, not just transfer latency. IIUC, that's also why P2P [refuses backpressure detectors](https://github.com/vllm-project/vllm/blob/cda0f3248538da3cc96b3760fe4cfaa7d3d652b9/vllm/v1/kv_offload/tiering/p2p/manager.py#L268-L281).

AFAICT, this is a no-op today, since P2P rejects backpressure detectors.

Is gating peer pins intended? If so, should we consider an enum such as `TransferKind.{CASCADE, PROMOTION, PEER_PIN}` instead of `is_promotion` to let policies treat them differently?
