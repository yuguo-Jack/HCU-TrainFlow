## Overview

Export idle offload usage and development-operation gauges at startup without
overwriting real multiprocess samples. Related: #59988 and #60001.

## Claims

- Initialize known native/SimpleCPUOffload usage series for every supplied
  engine, and sleep/RL in-flight operation labels during router registration.
- Preserve real SimpleCPUOffload samples during late/concurrent initialization
  and native samples during same-process recorder recreation, including later
  real zero updates.
- Export startup defaults through both `/metrics` and `/metrics/`, without
  duplicate real samples or HTTP counters.

`gauge startup offload`, and `mostrecent gauge`. #60001 changes scheduler gauges
only; this PR does not change its logger or test. Other results address capacity,
config-info, slot sizing, or Rust metrics, not these Python usage/operation fixes.

## Details

Mostrecent gauges omit unset timestamp-zero samples. Calling `.set(0)` to seed
them gives a late writer the newest timestamp and can replace real stats. A
private cached timestamp check is not atomic across gauge objects either.
Startup defaults now live in a lock-protected process-local dictionary; vLLM's
multiprocess collector adds only missing series. No initialization write touches
real mostrecent storage, and a real zero supersedes a fallback normally.

The instrumentator's exporter otherwise constructs a plain multiprocess
collector and bypasses the fallback-aware registry. Both metrics routes now use
vLLM's scrape registry, separate from HTTP instrumentation to avoid duplicates.
Defaults require this registry; an external plain collector does not see them.
Read-only private mode/storage-kind/bound-label metadata remains a compatibility
dependency. Cleanup removes only `vllm:` fallback entries.

Native usage gauges opt in via metadata. Binding all/liveall children already
exposes zero, so avoiding a redundant `.set(0)` preserves retained mmap samples
when the recorder is recreated. Runtime observations still use ordinary setters.
Development-operation singletons initialize during router registration, not
module import, after multiprocess storage selection. No new dependency, scheduler
change, per-token work, or GPU synchronization is introduced.
