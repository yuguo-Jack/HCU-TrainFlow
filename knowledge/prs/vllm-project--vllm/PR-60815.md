# [Rust Frontend] Add `--always-constrain-output`

[Upstream PR](https://github.com/vllm-project/vllm/pull/60815) · state: open · merged: False

## Original PR description


## Overview

Step 5b of the parser-owned output grammar rollout, stacked on #60781 (answer constraint composition). Adds `--always-constrain-output` (off by default) to the Rust frontend: requests without tools or a structured-output constraint still get the parser's output grammar, so reasoning framing and tool-call envelopes are enforced for ordinary chat and non-strict `tool_choice=auto`. It reuses the Step 4 answer path rather than adding a grammar interface.

## Claims

- With the option, a request without a structured-output constraint gets an unrestricted `any_text` answer, and the parser builds its grammar for it:
  - no tools or `tool_choice=none`: the reasoning wrapper around free text, from token zero;
  - non-strict `auto`: the builder's own `auto` grammar (`triggered_tags`: free text, and a trigger must open a well-formed call to a declared tool), the same as `--tool-strict-level function`;
  - Kimi K3: its full channel structure with its own response text, which keeps excluding the channel markers.
- A free answer never composes as `Or[calls built as required, any_text]`: that `any_text` branch would accept malformed calls and weaken strict tools. Without a reasoning wrapper, free text alone builds no grammar.
- A request's own constraint takes precedence and composes as in #60781; one the grammar cannot compose (Lark) stays native. Without the option, behavior is unchanged.
- `vllm serve` accepts the flag only with `VLLM_USE_RUST_FRONTEND=1`, like `--grpc-port`, and forwards it to the Rust frontend.

## Validation

```bash
cd rust
cargo nextest run -p vllm-parser -p vllm-chat -p vllm-server -p vllm-cmd
cargo clippy --workspace --all-targets
cd .. && pytest tests/entrypoints/launchers/test_cli_args.py
```

- Tests: 1488 Rust tests pass (parser, chat, server, cmd), Clippy and rustfmt pass; the three new grammar tests fail if the free answer is composed like a real one. Python CLI args: 62 pass.
- Render check (`vllm-rs render`, Qwen3-8B, `qwen3` + `hermes`), structural tag per request:

  | Request | Off | On |
  | --- | --- | --- |
  | no tools / `tool_choice=none` | none | `think? any_text` |
  | non-strict `auto` | none | `think? triggered_tags` |
  | `required`, `response_format` | parser grammar | identical |
  | Lark `structured_outputs` | native | native |

- GPU smoke on GB200 with the Rust frontend, Qwen3-8B, `qwen3` + `hermes`, temperature 0, one server with the option and one without: 10/10 cases pass on both with identical outputs (plain chat streaming and not, thinking off, `auto` calling and answering, `none`, `required`, `response_format` with and without tools). Probe: asked to copy a call to an undeclared `delete_files` tool, the server without the option returns a `delete_files` call; with the option, the grammar forces a declared tool and it returns a `get_weather` call (streaming and not). No server errors.
- Not run: model evaluation, mask-cost benchmarks.

## Details

- No new grammar interface: the chat layer fills `OutputGrammarContext::answer` with `Format::any_text()`, and `OutputGrammarContext::constrained_answer` (which filters out exactly that format) is what builders compose. Under `auto` the present answer still makes the tool grammar apply, so non-strict tools reach the builder.
- Without a reasoning wrapper (no reasoning parser, or `kimi`, `minimax_m3`, `cohere_cmd`, `seed_oss`) and without calls, `CombinedParser` returns no grammar rather than a final-output `any_text`, which would put the request on the structured-output path without constraining it.
- Cost: grammar compilation sits on TTFT and the XGrammar cache key is the whole tag, so per-request tool sets compile per request; masking runs through long reasoning. The docs ask to measure before enabling it.
- Requests the option moves to xgrammar share the first-request backend issue described in #60781.
- Harmony (gpt-oss) uses its own output processor and is unaffected.
- The `frontend` args JSON ignores unknown keys, so the Rust field is what makes the Python flag take effect; a CLI test covers the JSON key.
- Duplicate check: no open PR adds an always-on output grammar; #60678 and #52390 scope structured outputs for Harmony and Muse Glimmer.
