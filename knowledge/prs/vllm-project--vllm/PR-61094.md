# [Frontend] Add --reasoning-effort-map to rewrite request reasoning efforts

[Upstream PR](https://github.com/vllm-project/vllm/pull/61094) · state: open · merged: False

## Original PR description

## Overview

Adds a `--reasoning-effort-map` frontend flag that rewrites the reasoning effort a client sends into one the served chat template supports, before it reaches the chat template or the Harmony preamble.

Addresses #52738. Related: #52739 (see "Not a duplicate" below).

## Claims

- `--reasoning-effort-map '{"minimal": "low", "medium": "low", "xhigh": "max"}'` rewrites the listed efforts; unlisted efforts pass through unchanged.
- Applies to the effort set through Chat Completions (`reasoning_effort`), Responses (`reasoning.effort`) and Anthropic Messages (`output_config.effort`), on both the chat-template and Harmony paths.
- `enable_thinking` follows the mapped effort, so mapping to `none` disables thinking and mapping `none` to another effort enables it.
- A `reasoning_effort` set directly in `chat_template_kwargs` is not rewritten.
- Keys are validated at startup against the known efforts, so a typo fails `vllm serve` instead of being silently ignored.
- With the flag unset (default) behavior is unchanged.

## Validation

Unit tests added to existing suites:

- `test_cli_args.py`: the flag parses, and unknown keys / non-string values / non-object JSON are rejected at startup.
- `test_reasoning_enable_thinking.py`: listed efforts are rewritten and unlisted ones are not (Chat Completions and Responses), `enable_thinking` follows the mapped effort in both directions, and `chat_template_kwargs` bypasses the map.
- `test_render_parity.py`: with `{"none": "low"}`, Harmony renders `none` to the same prompt tokens as `low` (and different from `high`) instead of rejecting it.

## Details

**Motivation.** The API accepts `none`/`minimal`/`low`/`medium`/`high`/`xhigh`/`max`, but chat templates recognize different subsets. Some raise on values they do not know (#52738), and others silently fall back to another effort, e.g. maximum reasoning. Clients such as agent harnesses often send a fixed effort that cannot be changed client-side, so operators need a server-side way to translate.

**Design.**

- The map is an explicit per-effort rewrite rather than an inferred one: the operator states exactly what each unsupported effort becomes. Values are passed to the template as-is and are not restricted to the API's effort names, since templates may define their own.
- It is applied where the effort is read off the request (`build_chat_params` for Chat Completions and Responses, and the two Harmony preamble builders) through one helper, `map_reasoning_effort`. The map lives on `OnlineRenderer`/`OnlineDerenderer`, so the API server and the render server behave the same. Anthropic Messages requests are converted to a `ChatCompletionRequest` and go through the same path.
- The `ReasoningEffort` literal moves to `vllm/renderers/params.py` so the request model and the startup validation share one definition.

**Limitations.**

- An effort passed in `chat_template_kwargs` bypasses the map; that is the escape hatch for sending a value to the template verbatim.
- The map is static per server; it does not inspect the template to discover which efforts it supports.

**Not a duplicate.** #52739 targets the same issue with `--supported-reasoning-efforts` plus `--reasoning-effort-rounding {down,up}`, rounding along a fixed ladder. This PR differs in that the mapping is explicit rather than rounded, it can map to and from `none` (#52739 always passes `none` through), values may be template-specific strings, and it is applied in the renderer so the render server is covered. #55432 (`--reasoning-effort-budgets`) maps efforts to `thinking_token_budget`, which is a different output. No other open PR was found for `reasoning effort map` / `reasoning_effort chat template`.
