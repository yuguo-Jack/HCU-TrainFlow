# [Bugfix][DP] Make duplicate scheduler resume idempotent

[Upstream PR](https://github.com/vllm-project/vllm/pull/55229) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->
## Overview

Make duplicate data-parallel scheduler resumes idempotent. Use the consensus-owned wave gate to decide whether a rank participates in the resume collective.

## Claims

- Already-resumed ranks return regardless of independently delivered request-wave messages.
- Genuine resumes and new Elastic EP ranks retain collective participation.
- The existing rejection of an in-flight pause is unchanged.

## Validation

Validated on 2026-10-10 at published head `e821bedbf6` and in a temporary merge with upstream `276fbcff2717bd934cfa37c8a2e4c391f3e7237b`. The published branch was not rebased.

```sh
VLLM_TARGET_DEVICE=cpu CUDA_VISIBLE_DEVICES='' .venv/bin/python -m pytest tests/v1/distributed/test_async_llm_dp.py -k test_dp_resume_preserves_barrier_participation -q
.venv/bin/pre-commit run --hook-stage manual --files vllm/v1/engine/core.py tests/v1/distributed/test_async_llm_dp.py
```

The five native regression cases pass on both versions; all applicable scoped hooks pass. Restoring the original `engines_running` predicate produces **1 failure and 4 passes**.

A two-process Gloo reproduction uses production resume, wave-message, and collective methods, with scheduler/model boundaries replaced. Asymmetric wave arrival makes the baseline time out on both ranks after 3000 ms. The guard passes duplicate resumes, genuine paused resumes with and without work, mixed existing/new Elastic EP participation, and in-flight pause rejection.

This establishes control-plane collective participation. GPU DP model-serving validation remains outstanding because only one GPU is available locally.

## Details

`engines_running` reflects independently delivered wave startup. One unpaused rank can return while another enters a collective, causing a deadlock. `ignore_start_dp_wave` changes through pause consensus and is also initialized for newly joined Elastic EP ranks. Using it alone addresses the [review feedback](https://github.com/vllm-project/vllm/pull/55229#discussion_r4170893423) without relying on scheduler-local state.

Fresh duplicate checks found no replacement. #59559 explicitly identifies this PR as complementary: it handles wakeup announcements rather than duplicate-resume barrier participation.

Upstream CI is blocked at contributor authorization. AI assistance was used for investigation, implementation, tests, and review.

I think `ignore_start_dp_wave` alone is enough here, and it's the safer thing to key the barrier on. It's set at pause consensus (same step on every rank) and only cleared in this function, so every rank agrees on it whenever a resume shows up. The scheduler pause state is set whenever each rank's pause message lands, so it depends on per-rank timing.

The only state where the two conditions would give different answers is "paused without consensus", and that already hits the `pending_pause` raise above. So behavior is the same today, and your test table passes unchanged.

```suggestion
        # ignore_start_dp_wave is set at pause consensus (same step on every
        # rank) and cleared only below, so all ranks agree on it when a
        # resume arrives. Skip the barrier iff it is clear.
        if not self.ignore_start_dp_wave:
```
