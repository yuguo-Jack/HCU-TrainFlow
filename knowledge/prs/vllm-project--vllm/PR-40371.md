## Update — review and hardening

The change has been reviewed and improved with AI assistance, and validated on real hardware.

### Why this is not a duplicate
This updates the existing PR (the only open one for prefill progress reporting). No other open PR addresses `return_progress` / `prompt_progress`:

```bash
gh pr list --repo vllm-project/vllm --state open --search "prompt_progress in:body"
gh pr list --repo vllm-project/vllm --state open --search "return_progress"
```

### What changed since the first review
- **Opt-in on the engine hot path.** The scheduler now emits a partial-prefill
  `EngineCoreOutput` only when the request set `return_progress` (plumbed via
  `SamplingParams`); `num_computed_tokens` is carried only for those requests.
  Before, an output was produced on every prefill chunk for *all* requests,
  adding work even when no client asked for progress.
- **Cache disclosure gated.** The `cache` field (`num_cached_tokens`) is now
  gated behind the server-side `enable_prompt_tokens_details` flag, matching
  every other cached-token disclosure in the serving layer.
- **Typed response model** `PromptProgress` instead of a raw `dict[str, int]`.
- Removed the redundant `num_computed_tokens < num_tokens` scheduler condition
  (subsumed by `is_prefill_chunk`), fixed the now-nuanced invariant comment,
  made the completion `total` consistent (incl. encoder tokens), and cleaned up
  formatting/lint.

### Tests run and results
- Lint: `ruff check` and `ruff format --check` pass on all touched files.
- New tests: `tests/entrypoints/openai/test_return_progress.py`.
- Live validation on an RTX 5090 (real server, `Qwen/Qwen3-0.6B`,
  `--enable-chunked-prefill --max-num-batched-tokens 256 --enable-prefix-caching`):
  - chat & completion: `prompt_progress` is emitted with `return_progress=true`
    (`processed` advances by the chunk size, e.g. `512, 768, … 1792`, `total=2009`),
    and is **absent by default** (no extra prefill outputs);
  - `cache = 0` without `--enable-prompt-tokens-details`, and disclosed
    (e.g. `320`) with it.

these improvements and tests. The change was reviewed by a human submitter.

The calculation of `time_ms` can be inaccurate by up to 1 second when `res.metrics.arrival_time` is not available. This is because `created_time` is an integer timestamp, created by `int(time.time())`, which truncates sub-second precision. For a feature reporting progress in milliseconds, this level of inaccuracy is significant and can lead to misleading metrics.

To fix this, a floating-point timestamp should be captured at the start of the request and used for this duration calculation.

Additionally, the current implementation calls `time.time()` twice, which is inefficient and can introduce minor inconsistencies.

Here's a suggested refactoring of this block. Please note that a complete fix also requires changing how `created_time` is initialized at the beginning of this function to preserve float precision for time calculations.

```suggestion
                    now = time.time()
                    start_time = res.metrics.arrival_time if res.metrics and hasattr(res.metrics, "arrival_time") else created_time
                    time_ms = int((now - start_time) * 1000)
```
