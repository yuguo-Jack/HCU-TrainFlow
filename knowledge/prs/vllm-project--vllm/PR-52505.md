# [Frontend] Write run-batch responses incrementally instead of at the end

[Upstream PR](https://github.com/vllm-project/vllm/pull/52505) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

`vllm run-batch` buffered every response and wrote the output only when the whole batch finished. Responses are now written in input order as the batch runs, and frontend memory no longer grows with the input. Follows #53500, which moved this file. Related: #30268.

## Claims

- An interrupted or failed run leaves the responses for a prefix of the input on disk, instead of nothing.
- Output stays in input order, as before.
- At most `--max-inflight` requests run at once, and at most 16 times that many are dispatched but not yet written.
- A malformed batch or a bad `--output-file` fails before the model loads. A dead engine fails the run instead of exiting 0.

## Validation

At 5dbc1cbe30 on an RTX A6000:

| Check | Result |
|---|---|
| `pytest tests/entrypoints/launchers/test_run_batch.py -v` | 52 passed, including the model-launching tests |
| 4000 requests, SIGINT after 1000 written | 1024 lines, all status 200, exactly the first 1024 input lines |

Pre-commit passes. @vinitrbl's A10G run showed SIGTERM and SIGKILL leaving every finished line, where v0.31.0 left no file, and peak frontend RSS on 50k requests dropping from 1876 to 1159 MiB.

**Reorder window.** Writing in input order lets one long request hold back everything behind it. Throughput against writing in completion order, on an H100 with 4000 chat requests, median of 3:

| Workload | Window 1x `--max-inflight` | 4x | 16x |
|---|---|---|---|
| Uniform | +2% | 0% | +1% |
| 2% of requests 16x longer | −54% | −9% | 0% |
| Heavy tail | −49% | −6% | +1% |
| A long request every window | −60% | −15% | −3% |

Qwen3-0.6B on the heavy tail gave −41%, −4%, and +1%. Peak frontend RSS was about 1.1 GB throughout.

## Details

- **Memory.** Finished responses wait as serialized JSON, at most 16x `--max-inflight` of them, which is about 45 MB of chat responses at the default.
- **Defaults.** `--max-inflight` is twice `max_num_seqs` across data-parallel engines, at least 1024, and capped at `--max-num-queued-reqs`.
- **Input.** Opened once and read twice. A pipe or URL is staged first.
- **Output.** A local file is truncated at start. A URL output is uploaded only on success.
- **Limitation.** The URL input download has no timeout. That needs a stall timeout in `vllm/connections.py`, so it belongs in a separate change.
- **Duplication.** No other open PR changes how run-batch handles requests.
- **Follow-up: resume.** An interrupt discards responses that finished but were waiting behind an earlier request, up to the reorder window, so a resume reruns them. A follow-up PR would write them on Ctrl+C or a failed run to a side file such as `results.jsonl.ahead`, in the same format and input order. A resume, or a later `--resume` flag, could then skip both the written prefix and that file. Handling SIGTERM the same way would cover preemption too.

- vinitrbl · COMMENTED · 2026-10-06T06:58:16Z · [source](https://github.com/vllm-project/vllm/pull/52505#pullrequestreview-5424847151)

Tried this on a GPU, mostly to see what an interrupted run actually leaves behind, since the runs in the description are 2-request batches.

A10G, PR head 08af037 (`VLLM_USE_PRECOMPILED=1`), tiny random-weight Llama, 4000 chat requests at 512 output tokens. I compared against v0.31.0, whose `run_batch.py` is the same as main at the merge base.

| | v0.31.0 | this PR |
|---|---|---|
| full run | | 4000/4000, no duplicate ids |
| SIGTERM at ~1660 done | no output file | 1664 complete lines |
| SIGKILL at ~1660 done | | 1664 complete lines |
| 50k small requests, peak frontend RSS | 1876 MiB | 1159 MiB |

No truncated lines in either kill case, and the memory number lines up with what #30268 hit.

Found one issue with Ctrl+C though. After SIGINT the output has the 1664 real responses plus 951 lines with status 400 and "Client disconnected". Those are the in-flight requests that get cancelled in the `finally` of `dispatch_batch`: the chat handler catches the `CancelledError` and returns an error response instead of raising, so `run_and_write` writes it out like a normal result. Probably the same happens when one request raises and the rest get cancelled. The existing cancel test monkeypatches `run_one_request`, so it never goes through the real handler.

So an interrupted output looks like it has a bunch of genuine 400s, and anything that reads the file to figure out what's left would think those requests are done. Maybe set a flag before cancelling the in-flight tasks and skip the write in `run_and_write` when it's set? Then SIGINT leaves the same thing behind as SIGTERM and SIGKILL.

Separate from this PR, but it bit me while testing: after SIGTERM or SIGKILL, `VLLM::EngineCore` keeps running with ~21 GB allocated (still there after 3 minutes), so rerunning on the same GPU fails until you kill it by hand. run-batch doesn't handle SIGTERM the way `vllm serve` does, so even a plain SIGTERM leaves it behind. That's #55510, and #55846 fixes it for run-batch too. I left numbers there.

Also noticed `vllm/entrypoints/launchers/` has no CODEOWNERS entry since the move in #53500, which might be why nobody got auto-requested on this one. cc @simon-mo

> Responses are written as each request finishes, so their order does not follow the input file. Match a response to its request with `custom_id` rather than by line number. The output file is truncated when the run starts; if the run fails partway, it holds the responses that finished, so check the exit code before treating it as complete. An output URL is uploaded only when the run succeeds.

This could be a breaking change for some users. We should preserve the order of the output and only advance writes after previous inputs have been completed.

- fangchenli · comment · 2026-10-08T21:30:25Z · [source](https://github.com/vllm-project/vllm/pull/52505#issuecomment-6069429164)

@DarkLight1337 Agreed, done in a3f69d0. Output is back in input order, and each response is written once every earlier one has been.

A window of `--max-inflight` alone halves throughput on mixed-length batches, because one long request stalls everything behind it. So up to 16x `--max-inflight` requests may finish ahead of the oldest unwritten one, while running requests stay capped at `--max-inflight`. The sweep behind the 16x is in the PR description.

An interrupted run now leaves a prefix of the input, so resuming means rerunning the remaining lines.
