# [Bugfix][DSv4.1] Match decoder-replay input_ids dtype for FlashInfer MegaMoE

[Upstream PR](https://github.com/vllm-project/vllm/pull/61041) · state: open · merged: False

## Original PR description

## Overview

Fixes #61040. DeepSeek-V4.1 served with `--moe-backend flashinfer_moe_ep_cutedsl` or `flashinfer_moe_ep_mega_deep_gemm` crashes in the decoder-replay CUDA graph once it serves long prompts or batched prefills (e.g. GSM8K at concurrency 128) (`RuntimeError: Expected out tensor to have dtype int, but got long int instead`), because the replay graph's `input_ids` buffer is int64 while the model passes int32 ids for these backends. This PR sizes the buffer to match what the model passes.

## Claims

- **Bug fix:** with either FlashInfer MegaMoE backend, the replay graph's `input_ids` buffer is now int32, matching the ids `DeepseekV4Model.forward` passes. GSM8K serving no longer crashes. `deep_gemm_mega_moe` keeps its int64 buffer, and the default backend keeps int32, so neither changes.
- **Test:** `test_replay_graph_matches_eager` now sweeps the MoE backends and feeds `input_ids` in the dtype the model passes, instead of the buffer's own dtype. Without the fix both FlashInfer cases fail; run on its own, each fails at the line that crashes in serving.

## Details

**Root cause.**
- `DecoderReplayCudaGraphManager.__init__` sized its `input_ids` buffer as int64 when `kernel_config.moe_backend in MEGA_MOE_BACKENDS` (`decoder_replay_cudagraph.py:59-60`). `MEGA_MOE_BACKENDS` is `NATIVE_MEGA_MOE_BACKENDS | FLASHINFER_MOE_EP_BACKENDS` (`vllm/config/kernel.py`).
- `DeepseekV4Model.forward` casts `input_ids` to int64 only when `use_native_mega_moe` (`moe_backend in NATIVE_MEGA_MOE_BACKENDS`, `vllm/models/deepseek_v41/nvidia/model.py:671-673`, `:929-930`); the runner's ids are int32 (`vllm/v1/worker/gpu/input_batch.py:25`).
- So for both FlashInfer backends `run()` copies int32 ids into the int64 buffer with `torch.index_select(..., out=buf[:num_rows])` (`decoder_replay_cudagraph.py:95`), which requires matching dtypes.
- It needs a large enough step, not concurrency as such: `run()` is reached only when a replay batch dispatches to a replay graph (a PIECEWISE step of at least `decoder_replay_trim_threshold` = 768 padded tokens, or an eager step with a prefill chunk longer than the 128-token window; `vllm/models/deepseek_v41/nvidia/model_state.py:456-501`), so by the code a single prompt of 768 or more tokens hits it too. Capture feeds the buffers directly and the eager fallback has no `out=`, so startup and short prompts work.
- The two checks diverged when #54049 narrowed the model's cast (and the other native-only paths) to `NATIVE_MEGA_MOE_BACKENDS` while #59532 was in flight with the wider `MEGA_MOE_BACKENDS` check.

**Fix.** Key the buffer dtype on `NATIVE_MEGA_MOE_BACKENDS`, with a comment pointing at the cast in `DeepseekV4Model.forward`. The FlashInfer backends don't need int64 ids: the router accepts int32 (`fused_topk_bias` only casts when a hash table exists; `dsv4_topk` widens the ids to int64 after loading them, and the CUDA fallback accepts int32 or int64 ids), the FlashInfer experts never see `input_ids`, and the non-replay layers already run with int32 ids on these backends.

**Alternatives considered.** Deriving the dtype from one shared helper on `vllm_config`, called from both `DeepseekV4Model.__init__` and `DecoderReplayCudaGraphManager.__init__`, would stop the two from drifting again; this PR keeps to the minimal fix. Removing the native backend's int64 cast (a DSv4 hash-routing leftover; DSv4.1 has no hash layers) would need native MegaMoE revalidation. Both are possible follow-ups.

**CI.** The test runs in `:nvidia: (H200 MIG 35GB) Basic Models (Other)` and its `:amd: (MI355) Basic Models (Other)` mirror (`.buildkite/test_areas/models_basic.yaml`); it needs one GPU but no weights or FlashInfer kernels.

**Duplicate check.** `gh issue list` / `gh pr list --repo vllm-project/vllm` searches for `decoder replay`, `decoder_replay`, `MEGA_MOE_BACKENDS`, `NATIVE_MEGA_MOE_BACKENDS`, `Expected out tensor to have dtype int` and `59532` found no issue or PR that fixes this bug. The only hit that describes it is #59912 (nvshmem4py), whose validation notes record this crash and leave the fix to a separate PR (this one); it does not change `decoder_replay_cudagraph.py`. Open #59039 (ROCm decoder replay) doesn't touch `decoder_replay_cudagraph.py`'s dtype logic, and the AMD model has no native MegaMoE.
