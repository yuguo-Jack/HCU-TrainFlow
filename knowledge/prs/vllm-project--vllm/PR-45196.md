# [Bugfix][Model] Validate DefaultModelLoader / LoadConfig and fail with clear errors

[Upstream PR](https://github.com/vllm-project/vllm/pull/45196) · state: closed · merged: True

## Original PR description


## Purpose

`DefaultModelLoader` / `LoadConfig` accept several invalid configs silently or fail late with confusing internal errors. This validates them at construction. Three small fixes in the same loader (bundled to avoid near-duplicate PRs; happy to split):

1. **Config validation** — type `safetensors_load_strategy` as `Literal["lazy", "eager", "prefetch", "torchao"] | None` (a typo used to silently fall back to lazy), and reject non-string `load_format`, non-dict `model_loader_extra_config`, non-bool `enable_multithread_load`, and non-positive `num_threads` (which otherwise failed late as `ThreadPoolExecutor: max_workers must be greater than 0`) with a clear field-level `ValueError`.
2. **Explicit safetensors must not fall back to `.pt`** — `_prepare_weights` appended `*.pt` whenever `fall_back_to_pt` was set, even for explicit safetensors formats (`use_safetensors=True`), so a pt-only model under `load_format="safetensors"` opened the `.pt` via `safe_open` (cryptic `SafetensorError`). Fix: skip the `.pt` fallback when `use_safetensors` is set; `auto`/`hf` still fall back.
3. **Reject `enable_multithread_load` with a non-lazy strategy** — the multi-thread path silently drops a requested `eager`/`prefetch`/`torchao` (the single-thread path honors it). Reject the combination at construction; `None`/`lazy` is unaffected. (Real multi-thread support for those strategies is larger parity work; failing loudly is the conservative first step.)

## Test Plan

```bash
pytest tests/model_executor/model_loader/test_registry.py -k default_loader
pytest tests/test_config.py -k "safetensors_load_strategy or load_format"
```

Folded into existing test files (no new file): `LoadConfig` field rejects in `test_config.py`; loader / `_prepare_weights` rejects (one per fix) plus an `hf`-fallback control in `test_registry.py`.

## Test Result

Unit tests pass; reverting each fix fails exactly its reject case. All three were also confirmed on a real engine (A800, stock main vs the fix patched in-place, same input):

| `LLM(...)` config | stock main | with fix |
| --- | --- | --- |
| `num_threads=0` (multithread) | `max_workers must be greater than 0` deep in `ThreadPoolExecutor` | `num_threads must be a positive integer` at the loader |
| `load_format="safetensors"` on a pt-only dir | `SafetensorError: deserializing header` (`.pt` opened as safetensors) | `Cannot find any model weights` |
| `safetensors_load_strategy="torchao"` + multithread | loads, strategy silently ignored | `ValueError: ... does not support ... 'torchao'` |

- Sunt-ing · comment · 2026-06-11T03:54:02Z · [source](https://github.com/vllm-project/vllm/pull/45196#issuecomment-4677031073)

Hi @Isotr0py Pydantic actually wasn't validating it here. The field was annotated `str | LoadFormats`, but `LoadFormats` is only imported under `TYPE_CHECKING` and falls back to `Any` at runtime, so the annotation collapses to `str | Any` = `Any` and pydantic skips validation — `load_format=None`/`123` reached `.lower()` and raised a bare `AttributeError`, which is what this guard caught.

That said, your underlying point is right: pydantic *should* handle this. I've changed the field to a plain `str` so pydantic now rejects non-str values directly (while still accepting arbitrary/custom registered load formats), and dropped the manual `isinstance` check.
