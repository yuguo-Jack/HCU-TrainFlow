# [Perf][MoE] Wrap GateLinear ll_bf16_gemm in custom op to prevent torch.compile branch freezing

[Upstream PR](https://github.com/vllm-project/vllm/pull/60681) · state: open · merged: False

## Original PR description

## Summary

In `GateLinear.forward`, Tier 1 (`ll_bf16_gemm`, the CuTe DSL low-latency BF16->FP32 router GEMM for `M <= 16` on SM90+) was gated by an inline Python conditional on `x.shape[0]`:

```python
if (
    self.allow_ll_bf16_gemm
    and x.shape[0] <= self.LL_BF16_MAX_TOKENS
    and x.dtype == torch.bfloat16
):
    output = ll_bf16_gemm(x, self.weight)
```

Unlike Tier 2 (`torch.ops.vllm.fp32_router_gemm_dispatch`) and Tier 4 (`torch.ops.vllm.rocm_bf16x3_router_gemm_dispatch`), Tier 1 did not wrap its runtime `x.shape[0]` check in a custom op:
* When `GateLinear` is called from a `@support_torch_compile` model `forward()`, vLLM's `TorchCompileWithNoGuardsWrapper` drops all Dynamo guards (`skip_all_guards_unsafe` / `guard_filter_fn`).
* Consequently, the Python branch `x.shape[0] <= 16` is evaluated once during the initial `torch.compile` trace (e.g. `M = 2048` during warmup) and **frozen to `False`** for all subsequent decode batch sizes (`M = 1..16`), permanently bypassing `ll_bf16_gemm` in favor of the Tier 5 `torch.mm(x, weight.T, out_dtype=torch.float32)` fallback.
* The Python branch is wrong regardless of which size traces first (an `M <= 16` first trace would freeze `ll_bf16_gemm` in at `M = 8192`), which is why Tiers 2 and 4 already use custom ops.

### Scope & Trade-offs
* **Affected models:** Tier 1 requires `bf16` weights + `out_dtype=torch.float32` + `bias=False` + unquantized + SM90+ and a gate called from `@support_torch_compile` model code. On `main`, that is **Gemma 4** (`Gemma4Router.proj`), **Nemotron-H** (`force_fp32_compute=True` keeps `bf16` weights when specialized kernels exist), and **MiMo-V2** when `moe_router_dtype` is `bfloat16`. Most models migrated in #58234 lack `out_dtype=torch.float32`, use `fp32` gate weights, set `bias=True` (`gpt-oss`), or pass `gate=` into the opaque `moe_forward_shared` custom op (DeepSeek family) and are unaffected.
* **Batch invariance:** After this PR, Gemma 4 decode (`M <= 16`) and prefill (`M > 16`) use different GEMM kernels, so router logits may differ in the last ULP across batch sizes; this is Tier 1's pre-existing design (DeepSeek already behaves this way) and `VLLM_BATCH_INVARIANT` gating is handled at init by #59985.
* **Warmup:** The `c1_pdl` (`M = 1`) warmup gap is addressed by #50177.

## Changes

1. **`vllm/model_executor/layers/fused_moe/router/gate_linear.py`**:
   * Register custom op `torch.ops.vllm.ll_bf16_router_gemm_dispatch(x, weight, max_tokens)` (mirroring `fp32_router_gemm_dispatch` and `rocm_bf16x3_router_gemm_dispatch`) so `0 < x.shape[0] <= max_tokens` is evaluated dynamically at runtime outside the compiled FX graph, calling `ll_bf16_gemm(x.contiguous(), weight)` for `0 < m <= max_tokens` and falling back to Tier 5 `torch.mm(x, weight.T, out_dtype=torch.float32)` otherwise.
2. **`tests/kernels/test_ll_bf16_gemm.py`**:
   * Update `test_gate_linear_torch_compile_dynamic_m_dispatch` to drop guards via `guard_filter_fn` and execute decode calls (`M in (1, 4, 16)`) under `torch.compiler.set_stance("fail_on_recompile")` after tracing at `M = 32`, emulating `TorchCompileWithNoGuardsWrapper` so the test fails on `main` (`AssertionError: assert [] == [1, 4, 16]`) and passes with the custom op.

<summary>Reproducible Microbenchmark Harness</summary>

```python
import torch
from vllm.model_executor.kernels.linear.cute_dsl.ll_bf16 import (
    ll_bf16_gemm,
    ll_bf16_gemm_c1_pdl_kernel,
    ll_bf16_gemm_kernel,
)
from vllm.model_executor.layers.fused_moe.router.gate_linear import GateLinear

device = "cuda"
K, E = 2816, 128
ll_bf16_gemm_c1_pdl_kernel.warmup(shapes=[(K, E)], m_values=(1,))
ll_bf16_gemm_kernel.warmup(shapes=[(K, E)], m_values=range(2, 17))

weight = torch.randn(E, K, device=device, dtype=torch.bfloat16) * 0.02


class MainGate(torch.nn.Module):
    def __init__(self, w):
        super().__init__()
        self.weight = torch.nn.Parameter(w, requires_grad=False)

    def forward(self, x):
        if x.shape[0] <= 16:
            return ll_bf16_gemm(x, self.weight)
        return torch.mm(x, self.weight.T, out_dtype=torch.float32)


class PRGate(torch.nn.Module):
    def __init__(self, w):
        super().__init__()
        self.weight = torch.nn.Parameter(w, requires_grad=False)

    def forward(self, x):
        return torch.ops.vllm.ll_bf16_router_gemm_dispatch(
            x, self.weight, GateLinear.LL_BF16_MAX_TOKENS
        )


# Emulate vLLM's TorchCompileWithNoGuardsWrapper by dropping all Dynamo guards
# and tracing first at M=2048.
compile_opts = {"guard_filter_fn": lambda entries: [False for _ in entries]}
main_compiled = torch.compile(
    MainGate(weight), fullgraph=True, dynamic=True, options=compile_opts
)
pr_compiled = torch.compile(
    PRGate(weight), fullgraph=True, dynamic=True, options=compile_opts
)

x_warmup = torch.randn(2048, K, device=device, dtype=torch.bfloat16)
main_compiled(x_warmup)
pr_compiled(x_warmup)


def bench_cudagraph(fn, x, repeats=50, trials=31):
    for _ in range(10):
        fn(x)
    torch.cuda.synchronize()
    g = torch.cuda.CUDAGraph()
    with torch.cuda.graph(g):
        for _ in range(repeats):
            fn(x)
    for _ in range(10):
        g.replay()
    torch.cuda.synchronize()
    times = []
    for _ in range(trials):
        s = torch.cuda.Event(enable_timing=True)
        e = torch.cuda.Event(enable_timing=True)
        s.record()
        g.replay()
        e.record()
        torch.cuda.synchronize()
        times.append(s.elapsed_time(e) * 1000.0 / repeats)
    times.sort()
    return times[len(times) // 2]


for m in (1, 2, 4, 8, 16):
    x = torch.randn(m, K, device=device, dtype=torch.bfloat16)
    t_main = bench_cudagraph(main_compiled, x)
    t_pr = bench_cudagraph(pr_compiled, x)
    print(f"M={m:2d}: main={t_main:.2f} us | PR={t_pr:.2f} us | speedup={t_main/t_pr:.2f}x")
```
