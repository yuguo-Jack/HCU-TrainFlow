# [Bugfix] Fix Triton prefill attention OutOfResources on GPUs with 99KiB shared memory

[Upstream PR](https://github.com/vllm-project/vllm/pull/60942) · state: open · merged: False

## Original PR description

## Overview

Fixes #60847.

`google/embeddinggemma-2` crashes in engine warmup with Triton `OutOfResources` (`Required: 163840, Hardware limit: 101376`) on GPUs with 99 KiB of shared memory per block, such as RTX 30/40/50 cards and L4. The cause is that `context_attention_fwd` picks its tile size from the dtype and compute capability only. This change keeps halving the tile on CUDA until its Q, K and P tiles fit the device's opt-in shared memory per block.

Compared with #60848, this fix:

- Keeps every tile that already fits. [#60848](https://github.com/vllm-project/vllm/issues/60847). estimates the need as `3*B*D`, which is up to 50% above what the kernel really needs. So on A100 it halves tiles that launch fine today, for example bf16 head size 256 (128 → 64) on this model's sliding layers. On an RTX 5090, halving a tile that fits made this kernel 1.18x to 1.65x slower.
- Adds a test that also catches the fp32 head-size-512 failure (`Required: 135168`). The test in [#60848](https://github.com/vllm-project/vllm/issues/60847) adds only D=256, so it would also pass with a fix that leaves that path broken.

Compared with #60631, this fix:

- Also fixes the reported model in float32. With [#60631](https://github.com/vllm-project/vllm/issues/60631), `vllm serve google/embeddinggemma-2 --runner pooling --dtype float32` still dies at engine start with `OutOfResources ... Required: 135168, Hardware limit: 101376`, from the same `context_attention_fwd` launch.
- Fits the tile for every head size, not only 256. With [#60631](https://github.com/vllm-project/vllm/issues/60631), on 99 KiB GPUs, bf16 head sizes 192, 320, 384, 576 and 1024 still fail, and so do fp32 head sizes 320 to 512. bf16 head sizes 320 and 384 also still fail on A100 and H100.

## Claims

- `vllm serve google/embeddinggemma-2 --runner pooling` now starts and serves embeddings on a GPU with 99 KiB of shared memory, in bf16 (the command from the issue) and in fp32. Before the fix, engine warmup failed with `OutOfResources`.
- On such GPUs, `context_attention_fwd` now launches for every tested bf16/fp16 head size from 160 to 1024 and for fp32 head sizes 320, 384 and 512. All of these failed before.
- Tiles that already launched do not change. Output is bitwise the same for every configuration that worked before.
- `test_context_attention` gets D=256 and D=512. 8 of the new cases fail on the old code on a 99 KiB GPU and pass with the fix.

## Validation

Hardware: 1x NVIDIA GeForce RTX 5090 (compute capability 12.0, driver 615.71.09). It has 101376 bytes of opt-in shared memory per block, the same limit as the RTX 5070 Ti and RTX 3060 in the issue. Software: vLLM `0.31.1rc1.dev173+g8cbd5d030` (commit `8cbd5d03006c`), and this change on top of it.


Before: all 4 runs failed in engine warmup. 3 ran in the `vllm/vllm-openai:nightly-8cbd5d03006c33185f402249ff2b448efd594986` image (torch 2.13.0+cu130, triton 3.7.1). 1 ran from an editable install of the same commit.

## Details

Root cause: `context_attention_fwd` sets `BLOCK_M = BLOCK_N = BLOCK` from `get_block_size(dtype)`. That returns 128 for bf16/fp16 on any GPU with capability 8.0 or higher, and 32 for fp32. The only other rule is `if Lk >= 512: BLOCK = min(BLOCK, 32)`. The kernel keeps a Q tile, a K tile and a P tile in shared memory. For bf16, head size 256 and BLOCK 128, that is `2 * (128*256 + 128*256 + 128*128) = 163840` bytes. A100 (166912) and H100/B200 (232448) have room for it, but sm_86, sm_89, sm_120 and sm_121 GPUs have only 101376. EmbeddingGemma2 has head size 256 on its sliding layers and 512 on its full layers, so vLLM forces `TRITON_ATTN`. Its bidirectional layers go through `_forward_encoder_attention` → `context_attention_fwd`. The 512 layers already get BLOCK 32 and fit. The 256 layers do not fit. The same problem breaks bf16/fp16 head size 192 and fp32 head size 512 (135168 bytes).

Fix: on CUDA, after the existing choices, halve BLOCK until `element_size * BLOCK * (2 * D + BLOCK)` fits in `get_max_shared_memory_bytes()` (`cudaDevAttrMaxSharedMemoryPerBlockOptin`). Here D is `next_power_of_2(Lk)`. BLOCK never goes below 16, the smallest tile `tl.dot` accepts. The result is cached per (block, head size, element size), so each call costs one cache lookup.

The formula comes from `_fwd_kernel.warmup().metadata.shared` on sm_120. For large head sizes it matches the real use exactly. For small head sizes it is higher than the real use. This holds for all 60 configurations measured. I do not claim it is an upper bound on every GPU: a review found that it under-counts fp16 use on sm_75, but the tiles it picks there still fit.

Effect on 99 KiB GPUs: head sizes up to 128 keep 128. bf16/fp16 head size 192 or 256 goes from 128 to 64 (73728 bytes). fp32 head size 512 goes from 32 to 16. On A100, bf16 head size 256 keeps 128 and fp32 head size 512 keeps 32.

Limitations:

- ROCm does not change (there is an `is_cuda()` gate). The formula was measured on NVIDIA's Triton backend. On MI300 (65536 bytes of LDS) it would shrink the common head-size-128 tile, and I could not check if that is needed. Head-size-256 encoder attention on 64 KiB ROCm GPUs may have the same bug. I did not test it.
- fp32 with head size above 512 still fails on 99 KiB GPUs, because 16 is the smallest tile. It also failed before this change.
- `get_max_shared_memory_bytes()` reads GPU 0 and keeps the first value it reads. On a host with mixed GPU types, the limit comes from one GPU. Other users of this helper have the same limit.
- The cache key does not include the limit, so a test that mocks a different limit in the same process can get a stale tile. The existing mocked tests `test_kv_tile_width_is_gated_by_platform` and `test_rdna_narrows_the_kv_tile_and_nothing_else` now read the real limit on CUDA. They pass on the RTX 5090. On a GPU with less than 98304 bytes, the `[not-rocm]` case would see tile 64.
