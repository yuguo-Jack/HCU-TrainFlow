# [Bugfix][Rust Frontend] Use prefiller cache hits for P/D usage

[Upstream PR](https://github.com/vllm-project/vllm/pull/58885) · state: open · merged: False

## Original PR description

## Purpose
Fix `usage.prompt_tokens_details.cached_tokens` in Rust P/D responses.

The decoder currently counts KV received from the prefiller as cached tokens. That can make a cold request look fully cached, even though the prefiller computed the entire prompt.

The Python frontend already handles this through `remote_prefill_cached_tokens` (#54222). This change reads the same metadata in Rust and uses it for response usage:

- Use the prefiller's count when `do_remote_prefill` applies, including an explicit zero.
- Keep the existing decoder count when no usable override is available.
- Include `cached_tokens: 0` when prompt-token details are enabled. This also applies to ordinary local requests.
- Keep decoder metrics based on the raw engine statistics.

No new wire fields or prompt-length upper clamp are added.

Related-work searches found no matching open Rust fix. #58730 proposes bounds handling in Python; #56318 concerns cache-source metrics.

Validated with live NIXL transfers with two H100 80GB GPUs on one host, with Qwen/Qwen3-0.6B. The patched Rust frontend reports the prefiller's actual cache hits: zero for cold requests and 5616 for warm requests.

Before the fix, the decoder counted transferred KV as cache reuse, even when the prefiller had no cache hits.

Each result below was reproduced with both streaming and non-streaming responses:

| Endpoint | Prefiller cache | Actual prefiller hits | Before | After |
|---|---|---:|---:|---:|
| Chat | Cold | 0 | 5635 | 0 |
| Chat | Warm | 5616 | 5636 | 5616 |
| Completions | Cold | 0 | 5623 | 0 |
| Completions | Warm | 5616 | 5624 | 5616 |

Eight baseline cases reproduced the bug; eight patched cases returned the correct count. Cold patched responses included explicit `cached_tokens: 0`, including final streaming usage.

<details>
<summary>Test setup and procedure</summary>

- Two H100 80GB GPUs on one host, with Qwen/Qwen3-0.6B.
- NIXL 1.4.1; engine commit `a9eafde59cbd`.
- Python prefiller on GPU 0; Rust decoder frontend with its engine on GPU 1.
- Prefix caching and prompt-token details enabled.
- `kv_load_failure_policy=fail`; NIXL compatibility checks passed.

The Python engine code stayed unchanged. Only the Rust decoder frontend binary switched between unpatched and patched builds, with the running binary verified from process listings.

A small HTTP driver sent each prompt to the prefiller, then forwarded its returned `kv_transfer_params` unchanged to the decoder. The decoder generated eight tokens.

Workers restarted before each cold/warm pair. The first request had a cold prefiller cache; the second shared the long prefix but changed the suffix.

The matrix covered both binaries, both endpoints, streaming and non-streaming, and cold and warm caches: 16 decoder requests in total.

</details>

<details>
<summary>Decoder metrics still describe actual KV transfer</summary>

After the patched cold chat request, the decoder reported:

```text
Response cached_tokens:                                      0
prompt_tokens_by_source_total{source="external_kv_transfer"}: 5635
prompt_tokens_cached_total:                                  5635
request_prefill_kv_computed_tokens_sum:                       0
```

Metric names above omit the `vllm:` prefix and common labels.

The decoder still recorded the KV it received, while response usage correctly reported that the prefiller had reused zero cached tokens.

Warm decoder requests also had local cache hits from the preceding cold request. Those remained separate from the prefiller count used for response usage.

</details>
