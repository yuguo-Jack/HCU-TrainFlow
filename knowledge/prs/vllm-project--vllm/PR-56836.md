# [Bugfix][KV Offload] Bound unanswered P2P lookup waits

[Upstream PR](https://github.com/vllm-project/vllm/pull/56836) · state: open · merged: False

## Original PR description

## Purpose

Addresses the unanswered-lookup portion of #56823. After a P2P handshake succeeds, a peer that keeps its transport alive but stops answering `LookupMsg` leaves the consumer returning `RETRY` indefinitely. The server's pending-lookup timeout cannot help when its serving loop stops progressing.

Start a 30-second progress deadline when the first unanswered lookup batch is sent for a request. A response that resolves a previously unanswered probe rearms that request's deadline while other probes remain pending. Repeated scheduler polls, additional keys, duplicate responses and unknown keys do not extend it. Completing all probes, fetching the matched prefix, or finishing the request clears the deadline. Unsent probes wait for `ConnectAckMsg` before their response deadline starts.

Each poll drains buffered messages and completed transfers before checking lookup expiry. Deferred store results are drained after transfer finalization, including jobs whose supplied blocks were not fetched. This preserves timely replies read by a delayed scheduler and returns completed load/store results before teardown. The warning identifies the peer, the expired request and elapsed time without progress. This is a progress timeout observed by the scheduler, not a per-key age limit or a transport-arrival timestamp guarantee.

### Session failure policy

An expired lookup sends a best-effort `DisconnectMsg` before marking the **whole peer session** dead, allowing the peer to retire its old session before reconnecting. Existing manager teardown converts unresolved requests to `MISS` for local prefill, retains their failure markers until request completion, and releases session resources. Other outstanding work on that same peer also fails through the existing disconnect path; completed results from the current poll are preserved. Maintainer agreement on retaining this session-wide policy is still requested. A request-local timeout would leave the same stalled peer available for subsequent requests to wait on again.

### Issue scope

This PR does **not** bound the pre-handshake `ConnectAck` wait. #51504 covers that path and is still open as of this revision. #56823 must remain open until both failure paths are addressed; this PR has no automatic issue-closing keyword.

The wire format and model computations are unchanged.

Thanks for the careful writeup — the duplicate-work checks, the disclosure and the fault-injection smoke test all made this straightforward to review. I reproduced your results: `tests/v1/kv_offload/tiering/p2p` gives **220 passed**, and `pre-commit` + `mypy-3.12 --hook-stage manual` on the four changed files are clean.

The mechanism is right and I want this bug fixed. Two things I'd like changed before merge (inline), one design point to confirm, and a note on issue scope.

### The `send_ready` gate is a real bonus fix

Beyond the timeout, gating the flush means `st.peer_lookup_open` is now set only when a LookupMsg actually reaches the wire, so `finish()` no longer owes a terminal empty FetchMsg for lookup state the peer never opened. Good catch, worth keeping regardless of how the rest lands.

### Design point: blast radius

#56823 proposed "cancel the pending lookup and return a tier-local MISS"; this escalates to `mark_dead()` on the whole peer session, failing every co-tenant request on that peer. You do disclose this in the PR body, and it's defensible — a peer silent for 30s is probably wedged, and a per-request MISS would make every later request eat a fresh 30s stall. I'm not asking you to change it, but it is the one place the implementation diverges from the issue, so it deserves an explicit sign-off from a maintainer rather than being buried in the body.

### Issue scope: please don't let this auto-close #56823

The issue covers both the `ConnectAck` and the `LookupResp` wait. This bounds only the latter, and `test_lookup_deadline_starts_after_handshake` asserts the session is still alive at t=100s with no handshake — which enshrines the unbounded pre-handshake wait as intended behaviour. That's a legitimate scope choice, but unless #51504 actually lands, a peer that never acks still defers requests forever and the reported hang is only half fixed. Worth saying so explicitly in the PR body so the issue isn't closed by a merge.

### Minor

`poll()`'s early return also skips the final `_server.collect_results()` / `drain_pending_aborts()`. That's safe today only because those buffers are populated exclusively inside `poll()`, and `server.close()` cancels inflight transports — but it's an unstated invariant, and a store that completed just before expiry gets reported failed rather than succeeded. A one-line comment on the early return would cover it.

### Session-wide teardown: co-tenant cost traced

I traced the co-tenant cost I raised earlier. A load that `close()` fails comes back as `JobResult(success=False)`. From there, `TieringManager._complete_promotion` calls primary `complete_store(success=False)`, which removes the write-pending chunk. The next lookup is a `MISS` and the request recomputes locally. It never becomes a GPU KV-load failure, so `kv_load_failure_policy: fail` does not turn a teardown into a 5xx. The blast radius is extra prefill for co-tenant requests, on the existing dead-peer path.

A healthy server also resolves deferred lookups within `_LOOKUP_PENDING_TIMEOUT_S` (5s). So the 30s budget only trips when the peer's serving loop has actually stopped. And one stuck probe can't be kept alive indefinitely by progress on other probes.

I'm comfortable with the session-wide policy. The final call is still a maintainer's.

### Non-blocking

- `lookup_clock` patches `time.monotonic` process-wide (`client_module.time` is the `time` module), so in the manager test it also drives `server.py`'s timeouts. `monkeypatch` restores it, so this is fine; one line in the docstring would make it explicit.
- Probes registered before the handshake now go out at the first `on_schedule_end` after `ConnectAck`, not at ack time: one extra scheduler step, which is negligible.

### Scope

This still covers only the post-handshake half of #56823. The reporter's hardware repro (unroutable IP, `p2p queries+ = 0`) is the `ConnectAck` path, so the issue needs to stay open until a handshake deadline lands (#51504, which currently has merge conflicts). The PR body already says so; thanks.

**This is the one change I'd ask for before merge: the deadline measures the request's whole lookup phase rather than peer silence, so it can kill a healthy peer.**

`flush_pending_lookups` uses `setdefault`, and this clears the deadline only when *all* of `st.probes` is resolved. A request that registers new keys while an earlier batch is still unanswered therefore never clears it, and the deadline stays anchored to the *first* batch no matter how promptly the peer answers.

I wrote a probe test — a peer that answers every single probe within one step (1s), one new key registered per step, nothing ever silent:

```
FAILED: session declared dead at t=30.0s even though the peer answered
        every probe within 1s of it being sent
WARNING [session.py:261] P2PSession peer:8000: lookup response timed out
```

And the cost isn't one request: `mark_dead()` tears down the whole peer session, failing all co-tenant work on that peer.

Your own `test_partial_response_does_not_extend_lookup_deadline` already encodes this — `hC` is asked at t=29 and answered at t=30, and the session dies for it.

It's also inconsistent with the timeout it's modelled on: `_LOAD_TIMEOUT_S` is measured per-operation (`now - load.submitted_at`), not across a request's lifetime.

Suggested fix — rearm on progress:

```python
progressed = False
for h, hit in zip(keys, hits):
    key = OffloadKey(h)
    if key in st.probes:
        progressed |= st.probes[key] is None
        st.probes[key] = hit
if all(hit is not None for hit in st.probes.values()):
    self._lookup_deadlines.pop(kv_request_id, None)
elif progressed:
    self._lookup_deadlines[kv_request_id] = time.monotonic() + _LOOKUP_TIMEOUT_S
```

I ran this: the probe passes, and **all 220 of your tests still pass except `test_partial_response_does_not_extend_lookup_deadline`** — the one asserting the current semantics. Silent-peer detection is fully preserved: `test_lookup_deadline_starts_after_handshake` and the manager-level `RETRY`→`MISS` test both still pass, because a peer that says nothing still makes no progress and still dies at 30s. Only a peer that *is* answering survives.

On reachability, to be fair: I've measured healthy lookup RTT on this path at roughly `2.69·c + 0.9 ms` (~42ms at concurrency 16), so a healthy peer will not trip 30s on RTT alone. It needs one request's lookup phase to span >30s across multiple batches, which is reachable because `get_num_new_matched_tokens` re-queries a shifting window (`start_chunk_idx = num_computed_tokens // tokens_per_chunk`, right edge bounded by `max_hit_size_tokens`), so new keys do get registered on later steps. So: a corner case, not the common path — but it fails an entire peer session, it would be thoroughly unpleasant to debug from a single `lookup response timed out` line in production, and the fix is five lines that remove the class of bug rather than narrowing it.
