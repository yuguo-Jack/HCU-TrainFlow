# [Bugfix] Stop re-forcing thinking-budget end tokens once the forced end sequence is complete

[Upstream PR](https://github.com/vllm-project/vllm/pull/58402) · state: open · merged: False

## Original PR description

## Purpose

Fixes #58390.

When `thinking_token_budget` is exhausted, the Model Runner V2 thinking-budget kernel (`vllm/v1/worker/gpu/sample/thinking_budget.py`) forces the model to walk out of the reasoning section by writing `1e9` onto the next token in `reasoning_end_token_ids`. With reasoning configs whose forced end sequence does not coincide with a natural-reasoning-end marker (e.g. distinct `reasoning_end_token_ids` / `natural_reasoning_end_token_ids`), the kernel never stops forcing after the walk completes and the request collapses into a repetition loop the moment the boundary is reached.

## Problem

The kernel advances the forced walk by measuring how long a prefix of `reasoning_end_token_ids` already matches the tail (`end_prefix_len`) and forcing `reasoning_end_token_ids[end_prefix_len + 1]`. The only thing that stops forcing is the natural-end early return (`last_start <= last_end`), which relies on a `natural_reasoning_end_token_ids` marker actually appearing in the sequence.

Once the *complete* forced end sequence is in the tail, the prefix alignment shifts: e.g. tail `[END_A, END_B]` no longer matches `prefix_len=1` against `END_A`, so `end_prefix_len` is recomputed as `0` and the kernel re-forces `END_A` again. On the next step the tail is `[END_B, END_A]`, which matches `END_A` and forces `END_B` again, and so on forever. For configs where the forced end tokens are not also natural-end tokens, `last_start <= last_end` never becomes true, so the loop only ends when the sampler's repetition guard trips (observed as ~`min_pattern_size * min_count` = 64 repeated tokens after the boundary).

## Root Cause

Missing "walk already complete" guard in `_thinking_budget_kernel`. The prefix-match loop only ever tests prefix lengths `1..END_LEN-1`, so it cannot recognize that the tail already contains the whole sequence. It therefore has no way to release forcing after the exit walk finishes.

## Solution

Before writing the forced logit, check whether the tail already ends with the *complete* `reasoning_end_token_ids` sequence. If so, return without forcing so the model can resume normal generation. This is safe:

- If the forced end tokens also coincide with natural-end tokens, the existing `last_start <= last_end` return already stops forcing; the new guard is redundant but harmless.
- It only triggers when the whole exit sequence is present, so it cannot cut a multi-token walk short mid-way (partial prefixes are still forced as before).
- A later reasoning re-entry (a new start marker) updates `last_start` and forcing resumes as expected.

## Test Plan

Added `test_v2_thinking_budget_stops_after_forced_end_sequence_complete` to `tests/v1/worker/test_gpu_thinking_budget.py`: with a distinct forced/natural-end config, after the full `[END_A, END_B]` sequence is committed, the next decode row must receive no `1e9` logit.

Existing tests still encode the intended walk:
- `test_v2_thinking_budget_continues_multi_token_end_marker` forces `END_A` then `END_B`.
- `test_v2_thinking_budget_uses_distinct_forced_end_marker` exercises the distinct config mid-walk.

## Test Result

- Ruff: `ruff check` and `ruff format --check` clean on both changed files.
- A CPU equivalent of the kernel decision logic (prefix match + force, with and without the new guard) reproduces the regression: the buggy path re-forces `END_A` after the complete sequence, the patched path returns without forcing, and the single-token-end and partial-prefix walk cases are unchanged.
- The new GPU test is skipped on CPU runners (`pytest.importorskip("triton")` / `torch.cuda.is_available()` guard, consistent with the rest of the file) and will run in CI.

## Compatibility

No API or config change. Behavior only changes for requests that previously hung in a repetition loop after `thinking_token_budget` was exhausted under a distinct forced/natural-end reasoning config; such requests now leave the reasoning section and continue generating.
