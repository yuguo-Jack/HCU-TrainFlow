# [Feature] Support batch invariance on ROCm

[Upstream PR](https://github.com/vllm-project/vllm/pull/52231) · state: open · merged: False

## Original PR description

## Purpose

`VLLM_BATCH_INVARIANT=1` makes a request's output independent of what else is in the batch. On ROCm the
mode set the flag and then ran ordinary kernels, and the determinism suite skipped itself, so nothing
noticed. This PR makes the mode work on gfx90a, gfx942 and gfx950 and runs the suite there. It builds on #58623
(custom all-reduce under batch invariance).

1. **`[Quantization] Fix FP8 GEMM paths that batch invariance relies on`**
   - `triton_scaled_mm` adds the bias in fp32 before the cast, as CUTLASS does, and no longer raises
     `UnboundLocalError` with `use_heuristic=False`.
   - `TritonFP8ScaledMMLinearKernel`, a scaled-mm linear kernel over `triton_scaled_mm` (per-tensor or
     per-token activations; per-tensor, per-channel or per-token weights), forced under batch invariance on
     ROCm. The block-scaled path takes `TritonFp8BlockScaledMMKernel`. Both warn when they override
     `--linear-backend` and raise, as NVFP4 does, if they can't implement the layer.
   - `fp8_scaled_mm_is_batch_invariant()`: the kernel is CUTLASS or Triton **and** the activation scale
     is static or per-token. It replaces the `isinstance(..., CutlassFP8ScaledMMLinearKernel)` checks in
     `Fp8LinearMethod.apply()` and the online per-tensor and PTPC paths.
   - Block FP8 skips the tuned config lookup under batch invariance.
   - `ocp_mx_emulation_moe` passes the checkpoint's static `a2_scale` (w_mxfp4_a_fp8 only) instead of `None`,
     which fell back to a dynamic per-tensor amax.
2. **`[ROCm][Core] Batch-invariant inference on gfx942 and gfx950`**
   - The persistent-matmul overrides on ROCm (sharing the SM80 branch), plus `mm.out`/`addmm.out`/`bmm.out`.
   - On ROCm, floating-point all-reduces the custom kernel declines, and floating-point reduce-scatters, take
     an all-gather (all-to-all) plus a fixed-order sum.
   - `+rms_norm` is forced into `custom_ops` under batch invariance on ROCm.
   - The AITER MX linear/MoE kernels pin their split-K or decline, the MXFP4 asm preshuffle path (which
     splits K) is skipped, and the skinny GEMMs are turned off.
   - MLA prefill: no `num_splits` on ROCm's `flash_attn_varlen_func`, and `ROCM_AITER_FA` is refused,
     whether auto-selected or explicitly selected.
3. **`[CI][ROCm] Run the determinism suite on gfx942 and gfx950`**
   - A ROCm entry in `DEVICE_BACKENDS`; the RMSNorm, online, NVFP4, LoRA-shrink and VLM tests un-skip
     on ROCm.
   - AMD mirrors for the Batch Invariance steps (A100 → MI250, H100 → MI300, B200 → MI355), running the
     same tests with `TRITON_ATTN` where the NVIDIA command selects `FLASH_ATTN`.
   - An optional distributed step (4×H100, mirrored on 4×MI300), running the E2E tests at TP=4 (with and without custom
     all-reduce) and at DP=4 with expert parallelism.

## Not ROCm-specific

- **`.out` overloads.** Inductor calls `extern_kernels.mm(..., out=buf)`, which bypassed the
  batch-invariant `mm`/`addmm`/`bmm`.
- **`torch.bmm`** is no longer rebound to the Python kernel. The `aten::bmm` registration covers it, as
  it does `mm` and `addmm`, and the rebinding broke `torch.bmm` on CPU tensors (as #60037 proposed).
- **Softmax** ignored `_softmax`'s `half_to_float` flag, so `torch.softmax(fp16, dtype=torch.float32)` returned
  fp16 (the bug #55249 also fixes).
- **Dynamic per-tensor FP8.** The scale is an amax over the whole batch, so no direct FP8 GEMM can be
  invariant with it; it keeps the BF16 fallback on every platform.
- **Block FP8.** Tuned tables change `BLOCK_SIZE_K` with M on 13 tables across 6 devices.
- **#58510's block32 MXFP8 GEMM** picks split-K by M; it now declines.

## Notable decisions

- **The all-reduce fallback stays, as a ROCm backstop.** #58623 removes the size threshold, but
  `should_custom_ar` still declines on dtype, byte alignment, contiguity, world size or a disabled custom
  AR, and on ROCm the next stop is RCCL. Integer all-reduces and reduce-scatters stay on RCCL, since
  integer sums are exact in any order.
- **Reduce-scatter.** Turning off SP/async TP under batch invariance (#56377) does not cover the
  model-level reduce-scatters: the MoE combine (`reduce_scatterv`) with DP>1 and EP, and SP MoE. On ROCm
  both go through all-to-all plus a fixed-order sum, ahead of the AITER reduce-scatter. RCCL
  `reduce(root=0)` (#45683's path) was measured batch variant at 4 ranks.
- **`ROCM_AITER_FA` MLA prefill is refused under batch invariance.** It is batch variant at kernel
  level: a 3.5k–6k-token sequence prefilled alone differs from the same sequence packed with others.
- **`+rms_norm` on ROCm.** With `custom_ops` at its compile default, `RMSNorm` runs `forward_native`, so
  `rms_norm_batch_invariant` is never reached, and Inductor lowers it to a reduction whose block size it
  picks by benchmarking at first launch. Forced on ROCm only; #60074 should address this on every platform.
  On an earlier ROCm image, DeepSeek-V2-Lite was not repeatable run to run (needle test 0/5), and 5/5 with
  the fix.
- **Scope.** The mode refuses known-incompatible configurations (sparse MLA, attention backends and MoE
  experts that don't declare support) and forces known-invariant implementations where one exists. It can't
  be swept against every kernel and flag in one PR, and AITER is invariant for some kernels and not others,
  so there is no blanket switch.

`B1` / `B2` / `B3` can be passed as a valid bias to `torch.addmm` and to our `addmm` overrides, which eventually land here. Without `stride_bias` we would read a wrong value for every entry other than the first. And there's no easy way to get rid of it via lightweight operations like reshaping/squeezing: we'd have to use `.contiguous()`.

It's worth noting that adding `stride_bias` doesn't change what's executed on GPU in the usual case (where it's = 1): Triton specializes some integer arguments (including 0 and 1) into `tl.constexpr`, so we don't actually do the multiply in VALU because it's optimized away before codegen.
