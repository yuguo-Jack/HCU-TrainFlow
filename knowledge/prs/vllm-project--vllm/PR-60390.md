# [Model][Core] Share the Qwen4Exp PLE table between co-located replicas

[Upstream PR](https://github.com/vllm-project/vllm/pull/60390) · state: open · merged: False

## Original PR description



## Overview

Share the CPU-offloaded Qwen4Exp PLE (n-gram) table between co-located replicas, the way `EngramConfig.dp_shared_memory` already does for DeepSeek V4.1's Engram; plus a process-group-free variant (`shared_host_table_dir`) for replicas that cannot share a collective. Motivation: two single-card Qwen3.8-Flash-Next replicas on a 121 GiB node are OOM-killed at boot because each pins its own 47.7 GiB table.

## Claims

- `dp_shared_memory` now applies to `Qwen4ExpForCausalLM` / `Qwen4ExpForConditionalGeneration`: one table in `/dev/shm` per node-local Engram DP group instead of one per rank. Two DP replicas of Qwen3.8-Flash-Next-NVFP4 boot on 101 GiB of host RAM where the unpatched pair needs about 136 GiB and dies.
- New `EngramConfig.shared_host_table_dir`: independent engine processes on one host share the table through a named file, no process group. Two single-card servers boot together in 150 s on 97 GiB; a restart maps the loaded table and is serving again in 99 s instead of reading 48 GiB.
- Lookups are unchanged (the pinned UVA path); answers are identical at temperature 0 and tool calling is unaffected.
- A request to share that cannot be honoured (no co-located group, `/dev/shm` too small) falls back to per-rank tables with a logged reason rather than an OOM-killed boot.

## Validation

Hardware: one node, two RTX PRO 6000 (96 GB each), 121 GiB host RAM, `RadixArk/Qwen3.8-Flash-Next-NVFP4`, `--kv-offloading-size 16`, `--max-num-seqs 16`, `--gpu-memory-utilization 0.94`, `/dev/shm` remounted at 104 GiB. Load: `vllm bench serve`, random 8K-in / 512-out prompts, `--request-rate inf`.

Tests (CPU, mocked groups in the style of the existing PLE tests): tests/distributed/test_engram_dp_shard.py::test_engram_group_creation_honors_model_and_options now expects the Qwen4Exp group, and none with embedding_across_dp or a resident table; tests/models/qwen4_exp/test_ple.py gains tests for the class selection and file-mode factory, the capacity fallback, both shared loaders' writer-only/fence contracts, the file naming and the ready-mark protocol; tests/test_config.py checks shared_host_table_dir requires cpu_offload. No multi-GPU CI test was added for the Qwen shared table (the DeepSeek one needs four GPUs); the hardware validation above stands in for it.

Details

Root cause. DPSharedEngramStorage and the node-local Engram DP group are DeepSeek-only: initialize_model_parallel builds the group only for DeepseekV41ForCausalLM, and Qwen4ExpPLEPinnedHostEmbedding allocates its whole table with pin_memory=True per rank without reading dp_shared_memory. The option is accepted and silently ignored for Qwen4Exp.

Design. The DeepSeek shape is kept: rank 0 creates a /dev/shm file, every rank maps it MAP_SHARED and cudaHostRegisters it, the lookup kernel is untouched, and the group fences on its CPU collectives (broadcast_object, all_gather_object, barrier) so the file is unlinked only after every rank has mapped it. The capacity check (can_share_ple_table) is the leader's decision, broadcast once per process and cached, because every PLE layer asks. The mapping code is one helper shared by both new classes. The group condition moves behind _engram_table_can_be_shared so DeepSeek's behaviour is unchanged and Qwen4Exp joins only when the table is offloaded and not already spread over the DP ranks by embedding_across_dp.

Why a second mode. Without --enable-expert-parallel, DP falls back to AllGather+ReduceScatter dispatch for every MoE layer, so DP replicas are not independent: on a board whose cards have no PCIe peer path (ours; ACS redirect, IOMMU faults) the per-layer collective hangs most boots. shared_host_table_dir gives those deployments the memory saving with no process group: O_EXCL decides the writer, the .ready mark is published ading and readers wait there, so a reader thatmapped early never reads an unfinished table. Theby design (a restart maps the loaded table); thename carries model, revision, layer prefix, shape so a changed checkpoint under the same name needsthe files removed — documented on the option.
Tradeoffs and limitations. About 400 non-test lines, of which the file-shared mode is roughly half; I am happy to split it into a follow-up PR if that eases review. docs/features/engram.md is updated for both. Readers in file mode trust the writer's .ready mark and a size check; there is no checksum. The ted whenever the table is offloaded, even ifsharing then falls back, which matches the DeepSeek path. No change to the model runner or scheduler; parallel_state.py gains one helper and a condition.
