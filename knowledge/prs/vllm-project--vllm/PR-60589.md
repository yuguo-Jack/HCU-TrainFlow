# [Rust Frontend] Support `--stream-interval` and per-request `stream_interval`

[Upstream PR](https://github.com/vllm-project/vllm/pull/60589) · state: closed · merged: True

## Original PR description

<!-- markdownlint-disable -->

## Overview

Support `--stream-interval` and the per-request `stream_interval` field (vllm-project/vllm#49754) in the Rust frontend, with the same semantics as the Python frontend's `RequestState.make_request_output()`: the first output is sent immediately, later outputs are merged until they carry at least `stream_interval` new tokens, and the terminal output always flushes. A request's value raises the server-level one.

Builds on vllm-project/vllm#60588 (merged; box rarely-set fields of per-token output types). This replaces vllm-project/vllm#59864 (closed: moved to an upstream branch so it can be stacked) and vllm-project/vllm#50101, which turns `--stream-interval` into a warn-and-ignore no-op.

## Claims

- `vllm-rs serve --stream-interval N` and `"stream_interval": N` on `/v1/chat/completions`, `/v1/completions`, and `/inference/v1/generate` (via the shared sampling params) batch SSE chunks as in Python. `0` is rejected (CLI validation error / HTTP 400).
- No throughput regression in any tested configuration; with `--stream-interval 4`, mock-engine throughput improves by 43–54% over the base PR, with 37–41% less frontend CPU.
- With the default interval of 1, throughput is unchanged to +20% (larger at 32 workers), because the dispatcher no longer clones a channel sender per token.

## Details

**Layering.** The interval rule (first output immediately, then at least `stream_interval` new tokens, terminal output flushes) lives in one place: the per-request output channel in the engine-core client (`engine-core-client/src/client/output_channel.rs`), which groups outputs without merging them. `EngineCoreOutputStream` yields one `EngineCoreStreamDelivery` per group (an enum: `One` keeps the common single output inline, `Many` holds outputs grouped by the interval), and the `llm` layer's `GenerateOutputStream` merges each delivery into one `GenerateOutput` (token ids, logprobs, and sampling-mask rows are concatenated; per-output fields take the later value, as Python does for the flushing output). It still observes request metrics on every raw engine output, so TTFT, ITL, and E2E metrics are unchanged. Merging stays in `llm` rather than the client because the client only sees wire-level outputs (undecoded tensors, opaque values) and metrics need each raw output. The effective interval is `max(request, --stream-interval)` as in Python. It travels in `EngineCoreSamplingParams.stream_interval`, the field Python's `SamplingParams` also carries on the wire (engine-core ignores it; we send the effective value, and omit it when it is 1), and `EngineCoreClient::call` reads it at registration. `EngineCoreOutputStream::into_outputs` flattens the stream for consumers that do not care about grouping.

**Why the engine-core client is involved too.** Merging only in the `llm` layer leaves the per-token cost below it untouched: the output dispatcher, which runs on the dedicated ZMQ runtime, still wakes each request task once per engine step. Those wakes are cross-runtime (`schedule_remote` takes the runtime-wide inject-queue lock). When the woken task only merges and returns `Pending`, HTTP workers mostly idle and park, and the dispatcher convoys on the same lock with their park/unpark traffic. In the same benchmark setup (on an earlier base), `llm`-only batching lost 16–48% throughput at 32/64 workers, and 10% at 8 workers with i16, while CPU also dropped. So the channel coalesces deliveries: the sender holds back outputs after the first until they reach the interval and sends them as one channel message; the terminal output, aborts, `finished_requests`, and client shutdown flush first. The client counts only `new_token_ids` and never merges or reorders outputs.

**Sending under the registry lock.** The stateful sender lives in the registry entry, and the dispatcher sends while holding the registry lock it already takes once per batch. Two alternatives were benchmarked: building sends under the lock and performing them after releasing it, and a per-entry lock. Both regressed at interval 1 (−4% to −25%), most likely from extra per-token work on the single dispatcher thread (sender clone and drop, plus moving each output through an intermediate `Vec`). Sending under the lock was the only placement without a regression in any configuration.

**Other notes.**
- The new request field is accepted by chat/completions/generate HTTP routes. The gRPC `SamplingParams` message is unchanged; gRPC requests use `--stream-interval`.
- Non-streaming requests also merge internally; the collected output is identical.
- `EngineCoreStreamDelivery` is an enum rather than a `SmallVec`: a `SmallVec` channel item added full-size copies per token on the output dispatcher (the serial stage) and cost about 8% throughput with 32 workers at interval 1, while an enum channel item was within noise of the per-output stream (t32 i1/i4 and frontend-on-8-cores i1, two runs each). The `llm` layer matches on it so the single-output case is converted without going through an iterator.
- Moving the dispatcher onto the HTTP runtime would make these wakes local and also lifts interval 1 at 32/64 workers, but costs ~19% throughput when the HTTP runtime is saturated (8 workers on a large host), which is the isolation vllm-project/vllm#46051 introduced. It is out of scope here.
