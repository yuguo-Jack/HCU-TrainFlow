# [ROCm] Enable the cuMem CUDA-graph pool offload on ROCm

[Upstream PR](https://github.com/vllm-project/vllm/pull/59523) · state: closed · merged: True

## Original PR description

## Purpose

#59160 captures CUDA graphs (both model runners) into a cuMem pool that sleep mode offloads, opt-in with `sleep_mode_offload_cudagraph` (off by default, like SGLang's `SGLANG_MEMORY_SAVER_CUDA_GRAPH`). Its policy (`VllmConfig.use_cumem_cudagraph_pool`) requires `current_platform.is_cuda()`, so on ROCm it is inert even when opted in: every capture site gets `nullcontext(pool)`, no `cudagraph` tag appears, and asleep memory equals main with #59156. This PR enables the same path on ROCm.

Based on main, which now includes #59156, #59158 and #59160. RFC: #59055. It composes with #59909 (release the graph pool instead of backing it up); see Test Result.

### What breaks with the Python gate alone

Relaxing only the policy's platform check makes the first PIECEWISE capture fail on MI355X with

```
CUDA Error: operation would make the legacy stream depend on a capturing blocking stream at csrc/cumem_allocator.cpp:233
```

(`hipErrorStreamCaptureImplicit`), followed by `unknown error at :461` and an engine start failure. The cause is ROCm-only code at the PR base: `create_and_map` zeroes every freshly mapped region with a **blocking `hipMemset` on the legacy stream** (the stale-VRAM guard for GDN state from #43022/#46203). On CUDA there is no memset, so a cuMem allocation during capture is legal; on ROCm the graph pool's first allocation during capture triggers the memset, and the memset breaks the capture.

### Changes

- `vllm/config/vllm.py`: `VllmConfig.use_cumem_cudagraph_pool` checks `is_cuda_alike()` instead of `is_cuda()`.
- `csrc/cumem_allocator.cpp`: the ROCm-only zero-fill in `create_and_map` is removed, so the CUDA and ROCm paths are identical again and nothing touches graph capture. Instead, on ROCm only, `CuMemAllocator.wake_up` zeroes discarded allocations (those without a CPU backup) after remapping them, and synchronizes after each zero-fill. `hipMemset` returns before it finishes, and vLLM's non-blocking stream does not wait for it. Without the sync, a late memset can overwrite the level-2 buffer restore. Main has the same race. On MI355X it reproduces at the allocator level: 200/200 on main, 0/200 with the sync. That is the memory that can hold stale VRAM on drivers that don't scrub on release (#44972); startup allocations don't need it (the KV cache is `torch.zeros`). Suggested by @mawong-amd. It stays because vLLM's ROCm floor (6.3) pairs with amdgpu 6.8–6.10, which don't scrub VRAM on release; amdgpu ≥6.14 does, so it can go once that is the floor. CUDA wake is unchanged. On ROCm it costs about 35 ms per wake for a 150 GiB KV cache.
- `AiterCustomAllreduce`: passes `enable_register_for_capturing=False` to AITER's `CustomAllreduce` when the cuMem graph pool is active. This is required: at capture AITER IPC-registers the graph input pointers, and `hipIpcGetMemHandle` rejects VMM memory just as `cudaIpcGetMemHandle` does on CUDA (#59160's custom-allreduce fix). Without it, capture with AITER custom allreduce at TP2 fails with `hipIpcGetMemHandle ... invalid argument` (`custom_all_reduce.cuh:4080`) and the engine doesn't start (gfx942, reproduced by @mawong-amd). AITER already forces copy-in for expandable-segment pointers for the same reason.
- `vllm/_aiter_ops.py`: the fused all-reduce + RMSNorm + per-group FP8 quant ops (plain and `emit_bf16`) passed `registered=<capturing>` to AITER's raw `fused_ar_rms_per_group_quant`, which bypasses `enable_register_for_capturing`, so under the cuMem graph pool the capture input was IPC-registered and capture aborted (`hipIpcGetMemHandle ... invalid argument`, reproduced on MI355X). Both now pass `registered=capturing and ca.enable_register_for_capturing`; with the fix capture succeeds and replay is bit-exact, also after sleep/wake of the `cudagraph` tag.
- Tests: the cuMem graph-pool tests (allocator-level sleep/release test and the engine-level capture-site test) run on ROCm. The TP=2 case asserts that neither vLLM's nor AITER's custom allreduce registers graph buffers, and the level-2 poisoned-remap test asserts that discarded memory comes back zeroed. On AMD CI the TP=2 cases already run in the MI300 distributed steps.
- AITER test coverage, by @indianspeedster (from #60525, commit authored by them): `test_sleep_cudagraph_pool[custom-ar-tp2]` now also runs when AITER custom allreduce is active (it skipped before because `ca_comm` is `None` then), and a new test covers the fused AITER allreduce + RMSNorm + per-group FP8 quant op under the cuMem graph pool. The new test fails without the `_aiter_ops.py` change above.

Confirmed and left alone:

- vLLM's own `CustomAllreduce` needs #59160's `_capture_registered = False` on ROCm too: forcing `registered=True` fails capture with `custom_all_reduce_hip.cuh:167 'invalid argument'`. The copy-in path works unchanged.
- #59160's `NCCL_GRAPH_REGISTER` default (`VllmConfig._verify_cumem_cudagraph_pool`: `setdefault("0")` when the pool is active, an explicit value kept with a warning, as in sgl-project/sglang#40648) keys on `use_cumem_cudagraph_pool`, so it applies to RCCL once this PR enables the gate on ROCm (RCCL 2.30.4 honours `NCCL_GRAPH_REGISTER`). Not duplicated. AITER's `enable_register_for_capturing=False`, like vLLM's custom allreduce (sgl-project/sglang#7873), applies only when the pool is active.
- QuickReduce copies into its own static IPC buffer and never registers graph buffers; bit-exact over 10 cycles with `VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=FP`.
- #59160 no longer requires Model Runner V2, so ROCm architectures that default to V1 (e.g. DeepSeek-V4-Flash) also use the pool when opted in. The MI355X numbers below were measured on V2 before that change; V1 on ROCm is not yet validated here.

### What this does not release

On ROCm the torch graph private pool is only **72–244 MiB** per GPU, while graphs cost 948 / 1044 / 1543 MiB (DSv2-Lite TP1 / TP2 / DP2) and 1743 MiB (V4-Flash TP4) against `--enforce-eager`. The remaining 0.85–1.5 GB is HIP runtime graph memory held outside any torch pool, the ROCm counterpart of the graph-exec residue described in #59160. One difference matters: in a bare-process probe on MI355X, destroying graphs **does** return that memory (200 graphs: +4070 MiB captured, back to baseline after `reset()` + `empty_cache()`), whereas `cuGraphExecDestroy` returned 0 on GB300. So "destroy graphs on sleep, recapture on wake" would recover roughly the full graphs-vs-eager delta on ROCm, at the cost of recapture time (9–50 s here). That is a possible follow-up, not part of this PR.

### Suggestion: zero discarded allocations on wake instead of zeroing every mapping

The ROCm zero-fill came from #44972 (not #43022/#46203). It works around amdgpu ≤6.10 not wiping VRAM on release. Doing it in `create_and_map` zeroes every mapping, including weights and the graph pool, which the restore copy overwrites immediately. It's also why this PR needs a private stream, a static per-device map, and a host sync around capture.

The only memory that needs it is a discarded allocation that gets remapped on wake. `CuMemAllocator.wake_up` already branches on exactly that:

```python
                if data.cpu_backup_tensor is not None:
                    ...
                    libcudart.cudaMemcpy(ptr, cpu_ptr, size_in_bytes)
                    data.cpu_backup_tensor = None
                else:
                    # Discarded contents: re-zero, as at first allocation
                    # (the KV cache is allocated with torch.zeros).
                    libcudart.cudaMemset(ptr, 0, handle[1])
```

With that, the ROCm block in `create_and_map` can be deleted, and the CUDA and ROCm paths are identical again. Wake never runs during capture, so nothing touches graph capture at all. I prototyped it (C++ memset removed + the snippet above): `test_cumem.py` 20/21 and `test_sleep_cudagraph_pool` 5/5. The one failure is `test_level2_discards_ordinary_tensor_with_weights_tag`, which asserts discarded memory still holds the `0xA5` poison; under this rule it should assert zero.

**Does it cover every case?** None of our hosts runs an affected driver (all ≥6.16), so I used a test build of the allocator that fills every fresh mapping with `0xFF` (NaN in bf16) to emulate the worst case. I confirmed the woken KV buffer was 100% `0xFF` before the first post-wake generation. Results:

- **Startup allocations don't need zeroing.** Every model ran normally with all first-time mappings poisoned; the KV cache is `torch.zeros`.
- **Most backends tolerate a fully poisoned KV buffer after wake, even with no zeroing at all:** GDN (`tiny-random/qwen3-next-moe`), Mamba2 (granite-4.0-tiny), LFM2, Qwen3-0.6B (default and AITER attention), and TRITON_MLA. None produced NaN logprobs or degenerate output. Mamba-family state is already zeroed per block in-engine (#35219/#43990).
- **`ROCM_AITER_MLA` does read stale KV.** On DeepSeek-V2-Lite with no zeroing, every output changes after a level-1 wake, and level 2 gives NaN logprobs. Zero-on-wake and this PR's memset both fix it, with identical results. So zeroing on wake is required, and zero-on-wake covers it.

Two related notes:
- #44972's `test_gdn_sleep_wake.py` passes even with *all* zeroing removed (allocator memset and block zeroing), so it doesn't guard this. `_wake_up_with_poisoned_mappings` in `test_cumem.py` already injects garbage at remap; with zero-on-wake, asserting zeros there becomes the regression test.
- If #59909 lands, `cudagraph` becomes a discarded tag, and zero-on-wake would memset it on every wake. That's correct but wasted work; it may be worth skipping that tag.

### AITER: `enable_register_for_capturing=False` is required, not defensive, and untested

On gfx942, removing it breaks capture: `hipIpcGetMemHandle ... invalid argument` at `custom_all_reduce.cuh:4080` when AITER registers the graph buffers, and the engine fails to start. The description should say so.

Nothing covers it:
- `custom-ar-tp2` only checks vLLM's `ca_comm`.
- The AMD "Basic Correctness Sleep Mode" job runs on `mi300_1` (1 GPU), so the TP2 case is always skipped there, and both AMD jobs are `optional: true`.

Could you add an AITER variant (`VLLM_ROCM_USE_AITER=1`, asserting `aiter_ca.enable_register_for_capturing is False`) and run it on a 2-GPU pool?

The `_aiter_ops.py` change looks right. It mirrors AITER's own `custom_fused_ar_rms_per_group_quant`, and there's no version risk because `enable_register_for_capturing` (aiter#2075) predates the per-group op. I couldn't exercise that path end to end on gfx942: FP8 checkpoints don't start with sleep mode on this nightly, which is unrelated to this PR.

@aoshen02 on whether we need the zeroing, I dug into this more on MI300X (gfx942, amdgpu 6.16):

- With AITER MoE off and #60389 applied, ROCM_AITER_MLA is still sensitive to KV slots it hasn't written, but only to NaN bit patterns. With no sleep at all, overwriting the idle KV cache with finite junk (bf16 0.0115 or 3.0) changes nothing, while overwriting it with `0xFF` changes all 8 prompts. TRITON_MLA doesn't care either way.
