# [Bugfix][MiniMax-M3] Cap video frames at the encoder's per-video budget

[Upstream PR](https://github.com/vllm-project/vllm/pull/60879) · state: open · merged: False

## Original PR description

## Overview

The MiniMax-M3 video loader samples at `fps` across the whole video with no frame bound, so a one-hour video at the default 1 fps decodes and holds 3,600 frames before any size check. This caps it at 500 frames per video, spread over the whole video, and lets `max_frames` in `media_io_kwargs` lower the cap, as `Qwen3VLVideoBackend` does.

500 is `_MAX_FRAMES_PER_VIDEO`, the per-video frame count the encoder budget is already sized for (192,000 vision tokens: 500 frames at 4:3, about 532 at 16:9). The processor's declared `max_frames` (768) is above that budget, so a 768 cap would still let a long video through to a rejection after the full decode.

- One-hour 1080p video, default 1 fps, no `max_frames` anywhere: served (HTTP 200, 500 frames). Without the cap, or with a 768 cap, it is rejected with HTTP 400 after the full decode.
- Peak RSS of the loading process drops from 24.4 GB to 5.1 GB, and loader time from 98 s to 78 s (median of 3).
- Videos up to 500 sampled frames are sampled exactly as before, matching HF `sample_frames`. Longer videos keep 500 frames spread over the whole video, with the original source indices, so timestamps stay correct.

A customer encountered this in a production deployment serving long videos with the default 1 fps. In a replay of that deployment:
- every over-length request (19/19) was rejected with a 400, but only after the API server had built a 1.8-5.6 GB pixel tensor for it;
- API-server memory reached 30 GB;
- 0 of 27 requests succeeded.

Additionally, at the moment the only way to handle a long video is the server-side global `fps`, but that also thins out short videos. With this PR, a server can bound frames per video instead (`--media-io-kwargs '{"video": {"max_frames": N}}'`, N ≤ 500).

## Validation

- Loader benchmark, CPU only. MiniMax loader with OpenCV, 1920×1080 at 30 fps, 3,600 s, fps 1; vLLM `8cbd5d03` plus this PR, against the same code with the cap removed; 3 runs each, alternating:

  | | without cap | with cap (500) |
  |---|---|---|
  | frames kept | 3,600 | 500 |
  | frame buffer | 22.4 GB | 3.1 GB |
  | peak RSS of the loading process | 24.4 GB | 5.1 GB |
  | loader time, median [range] | 98.0 s [96.2-99.5] | 77.6 s [75.4-82.1] |

  The time saving is smaller than the memory saving because OpenCV still steps through the file to the last kept frame.
- Served on a ROCm nightly at `8cbd5d03` (MiniMax-M3 FP8, TP4, MI325X, `--max-model-len 262144`, no `--trust-request-mm-kwargs`), 1-hour 1080p video, no per-request settings:

  | build | server `--media-io-kwargs` | result |
  |---|---|---|
  | this revision (cap 500) | none | served: HTTP 200 in 112 s; 500 frames over the whole hour; 180,683 prompt tokens (180,500 video) |
  | previous revision (cap 768), with #60878 | none | rejected: HTTP 400 after 107 s, prompt longer than `max_model_len` |
  | previous revision, with #60878 | `{"video": {"max_frames": 500}}` | served: HTTP 200 in 111 s; 500 frames; 182,847 prompt tokens (including 250 frame timestamps from #60878) |

- Served on the previous revision of this PR plus #60878, on the official `vllm/vllm-openai-rocm` nightly for `8cbd5d03` (same hardware), with server-wide `max_frames: 500` (what this revision makes the default) and `--gpu-memory-utilization 0.85`:
  - the same 1-hour video requested five times in one server lifetime at 500 frames, three sequential and two concurrent: all HTTP 200;
  - a 225-request VideoMMMU run had 0 failures.
- Server-wide frame budget, the deployment this PR enables. Previous revision plus #60878 on the official `vllm/vllm-openai-rocm` nightly for `8cbd5d03` (same hardware), with `--media-io-kwargs '{"video": {"max_frames": 32}}'`:
  - a 1-hour video sent with no per-request settings: HTTP 200, 32 frames over the whole hour (11,871 prompt tokens);
  - a 225-request VideoMMMU run had 0 failures. Every request got the same 32 frames as a client sending `fps = 32 / duration` (input tokens equal per question, up to 2-3 tokens of chat-template text), at the same throughput (361.9 vs 358.1 output tok/s; the two runs also differed in thinking mode);
  - the benchmark server allowed per-request kwargs only because lmms-eval always sends `num_frames`, which this loader ignores. In production the budget needs no client settings and no `--trust-request-mm-kwargs`.
- `pytest tests/multimodal/test_video.py -k minimax_m3`: 13 cases pass (12 new, plus the model-repo alignment case). The 12 new cases fail with `main`'s loader. `ruff check` and `ruff format --check` pass on the changed files.

## Details

- **Why not `num_frames`:** `VideoMediaIO` always passes `num_frames=32`, so honouring it would cut every video to 32 frames. `max_frames` reaches `compute_frames_index_to_sample` through the existing sampling kwargs.
- **Why 500, not the processor's 768:**
  - The encoder cache and the dummy-input profiling are sized for `_MAX_FRAMES_PER_VIDEO = 500` frames per video, so a video over ~500 frames is rejected after the full decode at ≥720p.
  - Capping at the budget turns those rejections into served requests with 500 frames over the whole video.
- **HF alignment:** HF's `sample_frames` has no cap. `test_video_processor_from_model_repo[minimax_m3_vl]` therefore compares against HF's samples thinned the same way above 500. vLLM matches HF exactly up to 500 sampled frames.
- **User-visible change:**
  - Videos over 500 sampled frames are now served with 500 frames, where at ≥720p they were rejected after the full decode.
  - Lower-resolution videos over 500 sampled frames, which could fit before, are now subsampled to 500.
- **Memory:** at ~500 frames the vision encoder needs room. At `--gpu-memory-utilization 0.92` the second distinct 500-frame request in a server's lifetime ran out of GPU memory on MI325X; 0.85 passed.
- **Limits:** since #58830, a per-request `max_frames` needs `--trust-request-mm-kwargs`. A server-wide `--media-io-kwargs` value applies to every request otherwise.
