# [Bugfix][MLA] Keep ds_mla cache-format canonicalization layer-local

[Upstream PR](https://github.com/vllm-project/vllm/pull/60957) · state: open · merged: False

## Original PR description

## Purpose

Fixes #48406.

`MLAAttention.__init__` canonicalizes the sparse-MLA KV cache format for FLASHMLA_SPARSE / SM120 (`fp8` -> `fp8_ds_mla`, `nvfp4` kept) and wrote the result back into the **shared global** `cache_config.cache_dtype`. Spec-decode drafters (DSpark / DFlash family) reuse that same `cache_config` object when the speculative config pins no `kv_cache_dtype`, so the drafter's non-MLA attention layers ran backend selection with `kv_cache_dtype=fp8_ds_mla`, which no non-MLA backend serves:

```
ValueError: No valid attention backend found for cuda with AttentionSelectorConfig(
    ..., kv_cache_dtype=fp8_ds_mla, use_mla=False, ...)
```

Simply deleting the writeback is not sufficient: the impl and the KV cache allocation are already driven by the layer-local canonical value (`self.kv_cache_dtype` -> `MLAAttentionSpec.cache_dtype_str`, 656B/token packed layout), but the metadata builders still read the global config, see the raw `fp8` alias, and skip building the fp8 metadata. The first forward then dies far from the root cause:

```
FlashMLASparseMetadataBuilder.__init__  -> use_fp8_kv_cache = False   (global says "fp8")
FlashMLASparseImpl                      -> use_fp8_cache = True        (layer says fp8_ds_mla)
forward -> _forward_fp8_kv_mixed_batch -> assert isinstance(fp8_metadata, FP8KernelMetadata)  # AssertionError
```

(the separate prefill/decode path asserts the same way at its two `FP8SeparatePrefillDecode` checks).

## Approach

The resolved cache format is a **layer property**, and it already has a propagation channel: `MLAAttention.get_kv_cache_spec()` writes it into `MLAAttentionSpec.cache_dtype_str`. So:

1. `mla_attention.py`: drop the `cache_config.cache_dtype` writeback in `MLAAttention.__init__` (keeps the global config un-polluted for spec-decode drafters — fixes #48406).
2. `flashmla_sparse.py`: `FlashMLASparseMetadataBuilder` now resolves the layout from `kv_cache_spec.cache_dtype_str`, falling back to the global `cache_config.cache_dtype` when the spec carries no such field (non-MLA specs). The PCP+DCP guard message uses the same source, so a genuinely non-ds_mla layout still raises `NotImplementedError` while a spec-level `fp8_ds_mla` no longer misreports.
3. `mla_attention.py` (`MLACommonMetadataBuilder`): the DCP workspace `use_packed_fp8_cache` flag reads the same spec field with the same fallback.

The DeepSeek-V4 / V4.1 packed-layout paths (`_resolve_dsv4_*`) are untouched: their drafters are MLA layers that need the ds_mla format, and their ~10 downstream readers (SWA page alignment, compressor, CuTeDSL kernels) still consume the global-config protocol as before.

## Not a duplicate

- #58773 fixes the same class of leak on the **drafter side** (strip inherited ds_mla dtypes in `load_dflash_model`); this PR fixes it at the **source** (the target no longer mutates the shared config). They are complementary: this PR covers drafters whose loaders pass `cache_config` through untouched, and also fixes the builder/impl split that a writeback removal alone would leave behind.
- #56155 adds a new `AttentionSpec.cache_dtype` field for layer-wise mixed KV encodings; this PR reuses the existing `cache_dtype_str` channel only and changes no spec schema.

## Test Plan

New regression tests in `tests/v1/attention/test_sparse_mla_backends.py`:

- `test_flashmla_builder_reads_fp8_layout_from_spec_not_global_config` — spec says `fp8_ds_mla`, global says `fp8`; builder must report `use_fp8_kv_cache=True` (red on a writeback-only removal, green here).
- `test_flashmla_builder_without_spec_dtype_falls_back_to_global_config` — specs without `cache_dtype_str` keep the global read.

Validated end-to-end on the target GPU server (per the reporter's environment, GLM-5.3 reuses the deepseek_v32 MLA implementation with FLASHMLA_SPARSE):

- GLM-5.3 + `--kv-cache-dtype fp8` + FLASHMLA_SPARSE + DSpark, TP=16 (128 heads / 16 ranks = 8 heads < 32 -> mixed-batch path) and TP<=4 (>= 32 heads -> separate prefill/decode path): startup and generation succeed, no `FP8KernelMetadata` / `FP8SeparatePrefillDecode` assertion.
- The drafter's non-MLA layers no longer observe `fp8_ds_mla` (fixes the #48406 backend-selection crash).

## Test Result

- Target GPU server: both TP configurations above pass (startup + generation).
- Local: ruff check + format clean on all three touched files; full pytest of `tests/v1/attention/test_sparse_mla_backends.py` not runnable in my local Windows environment (unix-only deps in the conftest chain); the two new tests were validated on the target server environment.
