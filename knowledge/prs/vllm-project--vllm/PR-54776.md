# [ROCm] Fix APU unified-memory accounting across GTT and host pressure

[Upstream PR](https://github.com/vllm-project/vllm/pull/54776) · state: open · merged: False

## Original PR description

## Summary

`RocmPlatform` does not override `is_integrated_gpu()`, so vLLM treats AMD APUs
like discrete GPUs and trusts `hipMemGetInfo()` as-is. On APUs that allocate from
GTT (system RAM mapped for the GPU — the default on Strix Halo and the
configuration AMD recommends), that is wrong in two ways:

- **free** is KFD's static system limit minus KFD's own allocations, so it
  ignores memory used by everything else on the host. With 60 GiB held by a CPU
  process, HIP still reports 100 GiB free while ~59 GiB is actually available.
  vLLM then sizes the KV cache for memory that does not exist and, without swap,
  ends in the OOM killer instead of a clean startup error.
- **total** is the TTM/GTT limit, which can exceed the RAM the OS sees (e.g.
  after enlarging the BIOS carve-out without retuning `ttm.pages_limit`). With a
  64 GiB carve-out and a 100 GiB GTT limit, HIP reports 100 GiB total with ~60 GiB
  of RAM, so the default `gpu_memory_utilization=0.9` cannot start.

This PR:

- Detects ROCm APUs via HIP's `is_integrated` device property.
- Replaces the platform branch in `MemorySnapshot.measure()` with a
  `Platform.get_integrated_gpu_memory_info()` hook. The default implementation
  keeps the existing NVIDIA UMA behavior (free from `psutil`) unchanged.
- On ROCm, determines which pool HIP allocates from by comparing the pool size
  HIP reports with the amdgpu sysfs sizes (`mem_info_vram_total`,
  `mem_info_gtt_total`, located via the amdsmi PCI BDF; no HIP context needed):
  - **GTT-backed:** `free = min(hip_free, MemAvailable)`,
    `total = min(hip_total, MemTotal)`.
  - **Carve-out-backed:** HIP's numbers are used as-is. The carve-out is hidden
    from the OS, so host memory must not bound it.
  - Native MI300A (no carve-out) is treated as GTT-backed; unreadable sysfs falls
    back to GTT-backed.

The pool is read from what HIP reports rather than re-deriving amdgpu's rule
because that rule depends on the kernel: before 6.10 consumer APUs allocate from
the carve-out, 6.10–6.14 always use GTT, and 6.15+ (`apu_prefer_gtt`) use GTT
only when the carve-out is smaller. Distribution kernels also backport amdgpu,
so the kernel version is not a reliable signal.

## Relationship to existing PRs

- **#50320** adds the same `is_integrated_gpu()` detection but applies the
  NVIDIA policy (free = `psutil` available). On GTT-limited systems that reports
  free > total and negative used memory (measured: −24 GiB at idle), and with a
  large carve-out it caps the GPU by unrelated host memory.
- **#40963** relies on DRM/sysfs heuristics and fixed reserves; this PR uses the
  values HIP reports and only uses sysfs to identify which pool they describe.
- An earlier revision of this PR used `min(hip_free, host_available)`
  unconditionally. Hardware testing showed that regresses carve-out-backed
  configurations (64 GiB carve-out, 38 GiB GTT: `main` starts, that revision
  failed with `57.29/64.0 < 57.6 GiB`), which led to the pool-aware version.

## Behavior notes

- Discrete GPUs and NVIDIA integrated GPUs are unchanged.
- When the GTT limit exceeds RAM, `gpu_memory_utilization` is now a fraction of
  the memory that actually exists. A value tuned on `main` to work around the
  inflated total yields a smaller KV cache (64 GiB carve-out + 100 GiB GTT,
  util 0.5: 48.04 → 29.09 GiB).
- In GTT-backed mode, host memory used by other processes during startup is
  accounted against the KV cache (conservative). If host memory is released while
  profiling, the existing ROCm fallback (#53591) applies.
- MI300A reports as integrated and takes the GTT-backed path; behavior was
  derived from the amdgpu/KFD source and is untested on hardware. Because
  `MemAvailable` is node-wide, the host bound rarely applies there.
- Enabling `is_integrated_gpu()` also enables the existing UMA cache release in
  `release_device_memory_under_pressure()` during weight loading on APUs.

@dllehr-amd I've updated the PR based on hardware testing on Strix Halo:

- **Pool-aware accounting.** On ROCm APUs the code now determines which pool HIP allocates from, by comparing the size HIP reports with the amdgpu sysfs carve-out and GTT sizes. It doesn't hard-code the driver's rule, because that rule changed across kernels (≤6.9 carve-out only, 6.10–6.14 always GTT, 6.15+ GTT only when carve-out < GTT).
  - **GTT-backed:** free is bounded by available host memory and total by host RAM, since GTT pages are system memory that HIP doesn't account for.
  - **Carve-out-backed:** HIP's numbers are used as-is, because host allocations can't touch the carve-out. The previous `min()` version regressed this case (`main` started, the PR failed).
  - **MI300A** has no carve-out, so it always takes the GTT path. This is derived from the driver source and is untested on hardware.
- **Structure:** added `Platform.get_integrated_gpu_memory_info()` with a ROCm override, replacing the `is_rocm()` branch in `MemorySnapshot`. Other backends, including NVIDIA UMA, are unchanged.
- **Validated** on gfx1151 with 0.5 GiB carve-out + 100 GiB GTT, 64 GiB carve-out + 38 GiB GTT (identical to `main`), and 64 GiB carve-out + 100 GiB GTT (`main` fails at util 0.9; this PR starts). Details are in the description.
- **Note: `gpu_memory_utilization` now applies to real memory.** When the GTT limit is set higher than the RAM the OS sees, `main` takes the GTT limit as total, so the utilization fraction applies to memory that doesn't exist. For example, with a 64 GiB carve-out and 100 GiB GTT on a 128 GiB machine (~62 GiB visible to the OS), util 0.9 asks for 90 GiB and fails to start. This PR caps total at host RAM, so util 0.9 asks for ~56 GiB and starts. The flip side: users who lowered utilization on `main` to work around this get a smaller KV cache for the same value (util 0.5: 48 → 29 GiB) and can raise it again. Configurations where GTT is smaller than RAM, including the default, are unaffected.
