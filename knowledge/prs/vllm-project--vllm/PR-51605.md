# [XPU][MoE] Resize batched Triton MoE tiles and change grid order

[Upstream PR](https://github.com/vllm-project/vllm/pull/51605) · state: open · merged: False

## Original PR description

# Purpose

Two changes to the expert-batched Triton MoE (`BatchedTritonExperts`):

- Grid order. `batched_triton_kernel` is launched with the expert id as the fastest-varying grid axis, so consecutive programs walk different experts' weights. `batched_triton_kernel_swapped` puts the tile index on axis 0 instead, so consecutive programs share an expert's weight tile. Same tiles computed, only the program-to-tile assignment changes. It is selected on XPU only, because the reorder costs up to 5.5% decode throughput on H200, so CUDA and ROCm keep the original kernel and the original grid.

- Tile sizes. `try_get_optimal_moe_config` gains an optional `default_config_func`, consulted after the config override and the tuned-JSON lookup, so tuned configs still win wherever they exist. `BatchedTritonExperts` passes `get_default_batched_config`, which narrows `BLOCK_SIZE_N`/`BLOCK_SIZE_K` to 32 on XPU. The shared heuristic sizes tiles for one large `[M, K] x [K, N]` GEMM, but the batched layout runs `E` small GEMMs of at most `max_num_tokens` rows, where wide N/K tiles are mostly masked-off work. Blockwise-quantized shapes keep the shared config's K because `moe_mmk` derives scale-group offsets from it, and configs without `num_warps` (batch-invariant, wna16) pin their own tiles.

`batched_triton_kernel` keeps its source and its position in the file, so its Triton cache key is unchanged and CUDA compiles the same kernel it does today. `batched_triton_kernel_swapped` differs from it by exactly the two `tl.program_id` assignments. `default_config_func` has exactly one caller, so no other config path changes.

`test_batched_mm_swapped_grid` runs the swapped kernel on whatever device is present and compares it against `native_batched_masked_quant_matmul`, which pins the tile→(expert, m, n) mapping to an independent reference and checks no row past an expert's token count is written. It targets the swapped kernel specifically because `test_batched_mm` goes through `invoke_moe_batched_triton_kernel` and so only covers the kernel the running platform selects. I confirmed it is not vacuous by transposing the in-kernel `pid_m`/`pid_n` decode, which fails 2 of its 3 shapes; the third is `max_tokens_per_expert=1`, where `randint(low=0, high=1)` gives every expert zero tokens and the kernel early-exits. A mutation that merely permutes the tile order does not fail, which is expected since a permutation is what this PR does.

`test_swapped_kernel_matches_original_source` compares the two kernels line by line, ignoring the `def` line and the `tl.program_id` assignments, so a change that lands in only one copy fails on CUDA too, where the swapped kernel is never launched. Adding `+ 0` to one copy's `num_pid_n` fails it.
