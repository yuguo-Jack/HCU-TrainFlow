# [watermarking] Add DFlash support to dual-key gumbel-max watermarking

[Upstream PR](https://github.com/vllm-project/vllm/pull/59554) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Enable `dual_key_gumbel` watermarking with DFlash speculative decoding. Builds on #56122 and #56807.

Closes #59662

## Claims

- DFlash + `dual_key_gumbel` is now supported. Draft tokens are watermarked with the correct per-step context, in both FULL CUDA graph and eager modes.
- With watermarking off or opted out, output is unchanged.
- No measurable overhead, and no change in acceptance length.
- DFlash2/LiLiCorr candidate-head drafters are rejected with draft watermarking. Their own sampling kernel skips the watermarker.

## Validation

**Unit and config tests:**
```bash
pytest tests/watermarking/ -v                                    # 151 passed
pytest tests/test_config.py -k "watermark or gumbel or dflash" -v  # 32 passed
```

**GPU validation:** 1× H100 NVL, `Qwen/Qwen3.6-27B` + `z-lab/Qwen3.6-27B-DFlash` (15 spec tokens), FULL CUDA graphs.

| Check | Result |
|---|---|
| Detection (32 prompts, T=1.0) | DFlash 22/32 vs no-spec-decode 25/32; opted-out control 0/32 |
| Draft tokens carry key A | +0.159 excess/token [95% CI 0.128, 0.192] vs control −0.017 |
| Context threading (score with contexts shifted 1 token) | −0.018 [−0.042, +0.006]: no stale-context signal |
| Watermarking off vs `main` (greedy) | 16/16 token-identical |
| GSM8K, 200 q (no WM vs WM, 2 seeds) | 76.5/71.5% and 70.0/69.0%; pooled McNemar p=0.13 (seed noise is ~6 pt) |
| Acceptance length | within 0.4% |
| Overhead | 7.28 vs 7.26 ms per draft round (`max_num_seqs=64`) |

DFlash scores below no-spec-decode on detection because only accepted drafts use key A under spec decode. The default detector weighting assumes the no-spec-decode key mix.

## Details

**Root cause:** DFlash computes all N draft logits in one pass, and `sample_draft` watermarked the flattened `(request, step)` batch in one call. That gives rows the wrong request's context and hides drafts 0…k−1 from step k, which the target verifies against.

**Fix:**
- A new overridable `DraftModelSpeculator._draft_sampler()`. Other speculators are unchanged.
- DFlash returns `DraftWatermarker.sample_parallel`, which samples one step at a time on the precomputed logits.
- No model-runner changes and no new buffers.

**Limitations:**
- Serving overhead (`vllm bench serve`, see [this comment](https://github.com/vllm-project/vllm/pull/59554#issuecomment-5957871640)): about 0% per engine step at batch ≤ 32 and ≤ ~2% at batch ~55. Opted-out requests pay the same per-step cost.
- Draft steps beyond about 3 are verified mostly indirectly (acceptance length is about 2.5 at T=1.0).
- No CI eval job; the GPU validation was run outside CI.

**Not a duplicate:** no other PR or issue adds DFlash watermarking.

**AI assistance:** Claude Code was used for implementation, tests and result analysis. The submitter has reviewed the change.

| Dataset | Config | 64 tok | 128 tok | 256 tok |
|---|---|---|---|---|
| C4 | nospec_wm | 100% | 100% | 100% |
| C4 | **dflash_wm** | **99.7%** | **99.3%** | **100%** |
| Dolly | nospec_wm | 44% | 71% | 84% |

**Results**
- **High-entropy text (C4):** DFlash is at parity with no spec decode. TPR at the empirical 1% FPR is 99.3–100% at every length.
- **False positives:** the unwatermarked DFlash outputs average 1.00 score/token and are near the nominal 1% FPR. The fused p-value is also calibrated on synthetic nulls.
- **Correctness:** a context-shift check (re-scoring key A with contexts shifted back 1–3 tokens) puts all key-A signal at the true context on both datasets. Drafts are keyed correctly.
- **Acceptance length is unchanged** by the watermark (1.88 vs 1.87 on C4, 2.58 vs 2.55 on Dolly).

**Moderate-entropy chat (Dolly): DFlash is noticeably weaker at fixed length.** It needs roughly 2× the tokens for the same detection rate. As far as I can tell this comes from the dual-key scheme under spec decode, not from the DFlash path:
- **Per-token signal is lower on drafts.** DFlash keeps about 84% of the total per-token excess (key A + key B: 0.29 vs 0.35). Target recovery/bonus tokens (key B) carry the same per-token signal as without spec decode. Accepted drafts (key A) carry about 30% less, because drafts are mostly accepted at low-entropy positions.
- **The signal is split across keys.** At acceptance length ~2.6 the tokens split roughly evenly between key A and key B. A fused score with fixed weights (default α=0.2, tuned for the non-spec ~90/10 key mix) combines two half-signals less efficiently than one.

**Detector setting:** α≈0.4 suits DFlash output better. It gains 7–10 points on Dolly at no FPR cost, while no-spec output loses only 3–4 points at 0.4. A default around 0.3–0.4 might fit mixed traffic, since the key mix depends on acceptance length. This should apply to dual-key with other spec methods too, but I've only measured DFlash. I'm happy to share the raw outputs and scoring scripts.

**Suggestion: fuse the DFlash draft watermark sampling loop**

`DraftWatermarker.sample_parallel` samples the DFlash draft steps in a Python loop of 15–19 kernel launches per step, which is 285 per round at N=15. The steps cannot run in parallel, because step k's Philox noise is keyed on a context that ends in token k−1, an argmax over all vocab blocks. They can be fused per step, though. Commit [`29b47dc574`](https://github.com/simon-veitner-redhat/vllm/commit/29b47dc5743927174bfa8dc0ba8a80cdba60d5e9) on [`fix/watermarking-dflash-kernel`](https://github.com/simon-veitner-redhat/vllm/tree/fix/watermarking-dflash-kernel) does this with 2 kernels per step plus a prologue (2N+1 launches). `_philox_gumbel_kernel` gains an in-kernel temperature divide, and a new `_draft_step_kernel` picks the token, shifts the context and builds the next step's dedup mask. It is a single commit on top of this PR's head (`4d8836d210`): 3 files, +365/−6, ready to cherry-pick.

**Correctness**
- Bit-exact against this PR's step loop on 818 synthetic cases, comparing tokens, contexts, prior contexts and the draft logits cache, eager and under CUDA graphs. The temperature divide must use `div_rn`: Triton's `/` lowers to `div.full.f32` and differs from the torch divide on 9–24% of values.
- Qwen3.6-27B + DFlash (N=15, 32 prompts, in-process engine): outputs are 32/32 identical in graph and eager mode, and watermark detection is unchanged (22/32 graph, 19/32 eager; opted-out 1/32).
- The existing watermarking tests pass. A new test checks the fused path against the step loop with `atol=0`.

**Performance** (H200, N=15)

| | this PR | fused | no WM |
|---|---|---|---|
| draft round, bs1 | 2.24 ms | 1.94 ms | 1.80 ms |
| draft round, bs8 | 2.75 ms | 2.31 ms | 2.13 ms |
| draft round, bs25 | 5.61 ms | 4.74 ms | 4.45 ms |
| serving ITL overhead, conc 1 / 8 / 32 | +2.9% / +2.7% / +1.7% | +1.7% / +1.4% / +1.0% | – |

This removes 68–75% of the watermark's draft-round overhead and about half of the serving overhead.

**What remains:** Philox noise costs about 5 µs per draft token, which is the floor. The dedup rescan of request history grows with draft count × history length and dominates at 8k-token histories, where fusion gains little. An incremental per-request hash set of seen contexts would remove it.
