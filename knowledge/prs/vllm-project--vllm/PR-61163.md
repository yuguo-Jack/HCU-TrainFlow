# [Perf][XPU] Fuse routed and shared experts for Qwen MoE decode

[Upstream PR](https://github.com/vllm-project/vllm/pull/61163) · state: open · merged: False

## Original PR description



## Overview

Add an opt-in XPU compile pass that fuses routed experts and one sigmoid-gated shared expert for Qwen MoE decode. Support FP16/BF16 activations with online/static per-tensor FP8 weights while preserving the existing gate/top-k routing and tensor-parallel reduction.

Kernel API: [vllm-xpu-kernels#628](https://github.com/vllm-project/vllm-xpu-kernels/pull/628). Router/norm extensions from [kernel #629](https://github.com/vllm-project/vllm-xpu-kernels/pull/629) are not required.

## Claims

- Replace the shared/routed tuple and its unscaled addition with one XPU custom op for supported decode ranges, with FP16/BF16 activations and online/static per-tensor FP8 weights. Default is off: `pass_config.fuse_xpu_moe_shared`; eligible compile ranges end at or below `pass_config.xpu_moe_shared_fusion_max_token_num` (default 8 tokens).
- Preserve the existing router and TP reduction. No model, scheduler, worker or common MoE implementation changes.
- Include the pass/adapter source and native operator schema/availability in the enabled pass's cache hash, and initialize per-layer plans lazily so AOT-loaded graphs use the correct runtime state.
- B1 TPOT drops by 20.2% (FP16) / 20.7% (BF16) with graph, and 45.7% / 44.8% with compile but no graph. Other batches/modes, including regressions, are shown below; eager does not dispatch this pass.

OMP_NUM_THREADS=32 \
  .venv/bin/python -m vllm.entrypoints.openai.api_server \
  --model /path/to/Qwen3.6-35B-A3B \
  --served-model-name Qwen3.6-35B-A3B --dtype float16 --quantization fp8 \
  --tensor-parallel-size 2 --host 127.0.0.1 --port 18467 \

  --gpu-memory-utilization 0.90 --block-size 64 \
  --compilation-config '{"mode":3,"backend":"inductor","splitting_ops":[],"cudagraph_mode":"FULL_DECODE_ONLY","cudagraph_capture_sizes":[1,2,4,8],"compile_ranges_endpoints":[8],"pass_config":{"fuse_xpu_moe_shared":true}}'

# Run each batch three times; change 1 to 2, 4 or 8.
.venv/bin/python -m vllm.entrypoints.cli.main bench serve \
  --model /path/to/Qwen3.6-35B-A3B \
  --served-model-name Qwen3.6-35B-A3B --port 18467 \
  --dataset-name random --seed 0 --temperature 0 --ignore-eos \
  --random-input-len 32768 --random-output-len 256 --num-prompts 1

## Details

This is the standalone MoE integration extracted from Wang Yuchen's broader [#60539](https://github.com/vllm-project/vllm/pull/60539): MoE commit `5246fc07e`, consolidated AMD-style pass organization `53f6b044e`, online FP8 support `8f3e461be`, and BF16 support `fc84b8304`. It uses the independent [kernel #628](https://github.com/vllm-project/vllm-xpu-kernels/pull/628) operator API rather than the router/norm extensions of [#629](https://github.com/vllm-project/vllm-xpu-kernels/pull/629). Additional safeguards require distinct single-use tuple outputs, rank-two contiguous input and `aten.add` with `alpha=1`; the AOT cache also tracks the relevant source and native schema. The source relationship is explicit so this MoE split can be coordinated with the original upstream PR.

Scope is AR decode: no [kernel #629](https://github.com/vllm-project/vllm-xpu-kernels/pull/629) router kernel, norm/QKV/projection fusion, standalone GEMM/GEMV optimization, in-place all-reduce, GDN output allocation change or speculative/MTP warmup patch. The current pass targets hidden size 2048, 256 experts, top-k 8 and matching routed/shared intermediate sizes on Xe2/Xe3. FP8 block scaling, LoRA, EP/EPLB, DP/PCP/SP and other unsupported layer configurations keep the original graph. The sizeable XPU implementation is isolated from common inference paths and justified by the measured E2E comparison above.

User-facing configuration is documented in `docs/design/fusions.md`, with an entry from the Intel XPU installation page: eager behavior, compile without graph, compile with graph and the supported token range. Existing compilation-pass CI collects graph/config tests; native XPU and checkpoint E2E coverage is provided by the hardware validation above, since generic non-XPU CI cannot exercise that path.
