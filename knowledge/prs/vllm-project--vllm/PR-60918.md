# [Frontend] Packed top-k logprobs for completion SSE

[Upstream PR](https://github.com/vllm-project/vllm/pull/60918) · state: open · merged: False

## Original PR description

## Overview

Add opt-in packed top-k logprobs to `/v1/completions`, including SSE deltas, for numeric RL and distillation clients. This is a standalone change using upstream's existing `FlatLogprobs`; it does not include or depend on #60542, #60915 or #60916.

## Claims

- `return_top_k_logprobs=true`, positive `logprobs`, and `return_tokens_as_token_ids=true` return `logprobs.top_k = {num_positions, k, token_ids, logprobs}`. The block matches the format proposed in #60915/#60916: base64 little-endian int32 IDs and float32 scores, row-major `[num_positions, k]`.
- Supports full completion responses and SSE deltas, including single-token, multi-token and empty terminal deltas. Sampled scores remain in `token_logprobs`, including samples outside top-k; completion offsets, finish reasons and usage are preserved.
- Reads existing flat primitive columns without rebuilding candidate `Logprob` objects or candidate JSON dictionaries. A private control skips output-candidate decoding while keeping prompt decoding enabled. No storage rewrite, generate-endpoint renderer, model-runner, scheduler or GPU changes.

## Details

**Nonduplication:** #60915/#60916 target `/inference/v1/generate` and reject streaming. This PR covers `/v1/completions` and SSE with matching flag/block names; completion sampled scores stay in the existing `token_logprobs` field. Their implementation changes are not part of this PR.

Engine slots `1..k` are packed without sorting or deduplication, preserving tie order and raw float32 candidate values, including negative infinity. Slot 0 supplies sampled scores with the completion API's -9999 lower clamp. Echo, beam search, custom candidate IDs and nonpositive/missing `logprobs` are rejected. Existing `stream_interval` controls batching.

The existing flat container still holds Python lists. Packing allocates CPU arrays proportional to positions × k and base64 has its usual 4/3 expansion. This change does not provide the NumPy-backed ingestion proposed separately in #60542. Usage and NumPy decoding: `docs/serving/packed_logprobs.md`.
