# [Bugfix][KV Offload] Reset a resumed streaming session's block table in OffloadingConnector

[Upstream PR](https://github.com/vllm-project/vllm/pull/60810) · state: open · merged: False

## Original PR description



## Overview

`OffloadingConnector` corrupts the CPU KV cache for streaming-input sessions. A session resumed for its next input chunk arrives as `NewRequestData` with its full block table, but `yield_req_data` flagged it as a delta, so the connector appended it to the table it already held.

## Claims

- A resumed streaming session's new chunks are offloaded from their own GPU blocks, so requests reusing that prefix from the CPU tier get correct KV.
- `yield_req_data` reports `is_full_table` (`True` for new requests) instead of `preempted`; the connector resets on it. NIXL and SimpleCPUOffload ignore the flag, so their behavior is unchanged.

## Validation

- `test_streaming_session_stores_new_chunks` (sync and async): the session's second chunk stores blocks `(0, 1, 2)` on main (earlier chunks' blocks) and `(2, 3, 4)` with this PR.
- `pytest tests/v1/kv_connector/unit/offloading_connector/ tests/v1/simple_kv_offload/`: all pass.
- E2E ran, and after a three-chunk streaming session, a greedy request on its 192-token prefix is served from the CPU tier and compared with a full recompute.
  - main: the outputs differ (the CPU-tier output loops on `5, 276, 183, 9`).
  - this PR: all 32 tokens match.

## Details

`_build_store_jobs` pairs chunk *j*'s key with `block_ids[j]`, so the duplicated table (`[1, 2, 3, 1, 2, 3, 4, 5, 6]` vs `[1, 2, 3, 4, 5, 6]`) stored earlier chunks' KV under later chunks' keys. For every other request the table is already empty when the reset runs, so it is a no-op for them.

`SimpleCPUOffloadConnector` duplicates the table the same way. It doesn't corrupt KV (it keys by block hash), but it skips offloading the session's new blocks. That will be a follow-up.
