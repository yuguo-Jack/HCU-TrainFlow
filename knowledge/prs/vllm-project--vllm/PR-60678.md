# [Bugfix][GPT-OSS] Scope engine-level structured outputs to the Harmony final channel

[Upstream PR](https://github.com/vllm-project/vllm/pull/60678) · state: open · merged: False

## Original PR description

<!-- markdownlint-disable -->

## Overview

Fixes #60664. GPT-OSS structured outputs that reach the engine without going through the OpenAI server's Harmony rewrite (`LLM.generate`/`LLM.chat`, frontends that call `AsyncLLM` directly such as Dynamo) are applied from token 0. This blocks the `analysis` channel and corrupts the JSON. This PR applies the same final-channel scoping from #45560 in `InputProcessor`.

## Claims

- On GPT-OSS, `json` / `json_object` / `regex` / `choice` / `grammar` constraints passed in `SamplingParams` now allow an optional `analysis` turn and constrain only the `final` channel, matching `/v1/chat/completions` and `/v1/responses`.
- No behavior change for requests from the OpenAI server: they already carry a Harmony structural tag, which is left untouched.

## Validation

- `pytest tests/parser/test_harmony.py tests/reasoning/test_gptoss_reasoning_parser.py` → 79 passed. The new tests compile the rewritten params with xgrammar and check which Harmony outputs are accepted, using the existing `TestAdjustRequest` samples.
- Negative control: with the `openai/gpt-oss-20b` tokenizer, a raw JSON-schema grammar rejects `<|channel|>analysis<|message|>reasoning<|end|><|start|>assistant<|channel|>final <|constrain|>json<|message|>{...}`. The scoped grammar accepts it.
- **E2E: pending.** I will run the issue's reproducer on GPU (offline `LLM.chat` with `json`/`json_object` on `openai/gpt-oss-20b`, and repros B/C against `vllm serve`) and post before/after results here before marking this ready for review.

## Details

**Root cause.**
- #45560 moved Harmony gating into the grammar. `HarmonyParser.adjust_request` wraps constraints in a structural tag with an optional `analysis` turn followed by `<|channel|>final[ <|constrain|>json]<|message|>…`.
- To match, `GptOssReasoningParser.is_reasoning_end` now always returns `True`, so the engine applies the grammar from the first token.
- The rewrite only runs inside `OnlineRenderer`. Callers that pass `SamplingParams(structured_outputs=...)` straight to the engine send a bare JSON grammar, and the engine enforces it from token 0. This is the risk raised in review of #45560.
- The engine always gets `openai_gptoss` as its reasoning parser for `gpt_oss` models, so this affects every non-OpenAI-server caller.

**Fix.**
- Extracted `to_harmony_structured_outputs(StructuredOutputsParams)` from `_adjust_output_format`. It is the same logic, now reusable.
- `InputProcessor.process_inputs` applies it to a cloned `SamplingParams`, before validation, so `auto` backend selection sees the structural tag. It runs only when:
  - the engine reasoning parser is `openai_gptoss`,
  - `enable_in_reasoning` is off,
  - the request has a plain (non-structural-tag) constraint.
- Constraints that fail to convert are passed through unchanged, so `_validate_params` reports the same error as before.

**Tradeoffs and limitations.**
- User-supplied `structural_tag`s that bypass the server are not wrapped. They cannot be told apart from server-generated Harmony tags, and they already describe the full output.
- With an explicit `--structured-outputs-config.backend guidance`, the Harmony structural tag is rejected, as it already is on the OpenAI server path today. Direct-engine callers now get a validation error, not silently corrupted JSON. Adding guidance support for the new structural-tag format is a separate follow-up.

**Duplicate check.** No open PR references #60664. #45560 covers only the OpenAI-server paths. #58958 (batch endpoint) and #52390 (Muse Glimmer) do not overlap.
