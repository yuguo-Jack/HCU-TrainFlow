# [Structured Output] Limit whitespace in JSON schema FSM to prevent runaway whitespace (issue #38696)

[Upstream PR](https://github.com/vllm-project/vllm/pull/44619) · state: open · merged: False

## Original PR description

## Summary

Fixes #38696 — JSON schema structured outputs producing runaway whitespace until `max_tokens`.

### Root Cause

`compile_json_schema()` was called without `max_whitespace_cnt`, so xgrammar's FSM allowed unlimited whitespace self-loops at JSON value positions. Models assigning high probability to whitespace tokens (e.g., Qwen3.5-9B with ambiguous inputs) would output hundreds of spaces before forcing a value.

### Fix

- Add `max_whitespace_cnt=8` to `StructuredOutputsConfig` (default)
- Wire through `XgrammarBackend` to `compile_json_schema()`
- `disable_any_whitespace=True` becomes syntactic sugar for `max_whitespace_cnt=0`

Limit `8` allows readable JSON while preventing runaway. Only affects whitespace between structural tokens, not inside string values.

### Related Work

This PR builds on ideas from several community discussions and PRs. Below is a comparison for context:

| PR | Approach | Contribution | Limitation |
|----|----------|--------------|------------|
| #34790 | Pass `whitespace_pattern` through backends | Identified the need for fine-grained whitespace control | xgrammar only supports `any_whitespace: bool`, not regex patterns, so this approach could not fully solve the issue |
| #42414 | Extend `disable_any_whitespace` to `auto` backend | Improved parameter compatibility across backends | Users still had a binary choice: compact JSON (no whitespace) or unlimited whitespace (the original bug remained) |
| **#44619 (this PR)** | Add `max_whitespace_cnt` parameter with a sensible default | **Closes the gap**: bounded whitespace = readable + safe, without requiring users to proactively configure anything | — |

Sunt-ing independently identified the same root cause on #38696 and proposed `max_whitespace_cnt` with measured data showing it eliminates runaway whitespace while keeping JSON readable. They also suggested maintainers consider defaulting to a small bound — this PR implements that.

### Tests

13 tests (all CPU, no model download):

```bash
# Config validation (3 tests)
.venv/bin/python -m pytest tests/test_config.py -k "structured_outputs_config" -v

# Mock parameter passing + FSM behavior (10 tests)
.venv/bin/python -m pytest tests/v1/structured_output/test_max_whitespace_cnt.py -v
```

All 13 pass. Tests verify: default=8, custom values, `None` (unbounded), `disable_any_whitespace` override, FSM rejects 3rd+ space at `max=2`, FSM allows unlimited at `max=None`, string-value whitespace unaffected.

- kolianik · comment · 2026-09-03T09:16:52Z · [source](https://github.com/vllm-project/vllm/pull/44619#issuecomment-5523463002)

@Alex-ai-future Tested the current head (`1d4ffde`) against the workload from #38696 that runs away on `Inferact/Qwen3.8-27B-NVFP4` — same engine, same request, three values of `max_whitespace_cnt`. Short version: **the patch removes the runaway completely; the default of 2 is too tight for pretty-printed JSON and degrades content, 8 or more does not.**

**Setup.** `vllm/vllm-openai:v0.28.0-ubuntu2404` with the two source files of this PR 3-way merged onto v0.28.0 (both merged cleanly; xgrammar 0.2.3 already accepts `max_whitespace_cnt`). 2× RTX 5090, TP=2, MTP speculative decoding (5 tokens), `--async-scheduling`, `--reasoning-parser qwen3`, default xgrammar backend. Request: `response_format=json_schema` (strict pydantic schema ~14 KB with a nested array), `temperature=0.3`, `max_tokens=6000`, `reasoning_effort=low`; 5 dialogs × 6 = 30 structured requests per engine launch, plus 15 control requests without `response_format`. Success criteria: no `finish_reason=length`, and the array field (`user_problems`) non-empty — the empty-array degeneration is what `disable_any_whitespace` produced on this checkpoint (29/30).

| Engine | Runaway whitespace / 30 | Valid / 30 | Empty array field / 30 | Avg time |
|---|---|---|---|---|
| stock v0.28.0 (baseline, previous day) | **12** | 18 | 0 | — |
| stock v0.28.0, `disable_any_whitespace=true` | 0 | 30 | **29** | — |
| this PR, default `max_whitespace_cnt=2` | **0** | 30 | **5** | 13.9 s |
| this PR, `max_whitespace_cnt=8` | **0** | 30 | 1 | 12.5 s |
| this PR, `max_whitespace_cnt=32` | **0** | 30 | 1 | 13.1 s |
| control: no `response_format` (every launch) | 0 / 15 | 15 / 15 | 0 | ≈12 s |

With the default of 2 the empties are not random: two of the five dialogs came back with `"user_problems": []` in both repeats, and a third lost two of three items once. With 8 and 32 only the longest dialog occasionally loses items (1/30 each), which is within what we see without any grammar on other checkpoints. Semantics of the populated answers (category ids, booleans, sentiment label) match the no-grammar control.

The reason is probably simple: the model's natural output is pretty-printed JSON, and at 2 spaces of indentation the whitespace run between elements is `"\n  "` = 3 characters at depth 1, 5 at depth 2, 7 at depth 3 — all forbidden by a limit of 2, so the grammar pushes the model into the compact `[]` branch the same way `disable_any_whitespace` does. **Suggestion: default to 8 (or 16) rather than 2**, or document that 2 effectively forces single-line JSON. Everything else in the PR behaves as described: `disable_any_whitespace=True` still maps to no whitespace, the engine-level flag applies, and the runaway is gone on all three values.

Engine logs (`Failed to advance FSM` from the MTP drafter, 41–45 lines per 30-request run) are unchanged by the patch, as expected — they are a separate matter (#44006).

Happy to re-run on the rebased branch or with a different default if useful; the same harness runs in ~3.5 minutes per engine launch.

Control without grammar: 15/15 valid on every launch. (`Qwen/Qwen3.8-27B-FP8`, reported earlier: 0/60 on stock.)

Two takeaways for the PR:
- The runaway is not a property of one odd quant: two independently produced NVFP4 checkpoints of the same model trip it, at very different rates (40 % vs 3 %). A bound in the grammar is the right place to stop it — the patch removed it in both cases.
- The limit has a small content cost on the checkpoints that need it (1–2 empty arrays out of 30 at 8 and 32, none on the stock grammar for RedHatAI), and no visible cost on the checkpoint that does not run away. That is still much better than `disable_any_whitespace` (29/30 empty), and consistent with the earlier finding that 2 is too tight (5/30 empty on Inferact). I would still suggest a default of 8 or higher.

Engine logs (`Failed to advance FSM` from the MTP drafter) are unchanged by the patch on all three checkpoints, as before.


- errmakov · comment · 2026-09-23T09:39:12Z · [source](https://github.com/vllm-project/vllm/pull/44619#issuecomment-5792519627)

Thanks for this — clean fix for #38696.

A scope question: the change adds `max_whitespace_cnt` to the two `compile_json_schema` call sites (`JSON` and `JSON_OBJECT`), but the `STRUCTURAL_TAG` branch of `XgrammarBackend.compile_grammar` is untouched. Runaway whitespace shows up there too — #50989 reports it for Qwen strict tool calling, which goes through `compile_structural_tag`, and #54497 tracks exposing the knob more generally.

It isn't just one more kwarg: `GrammarCompiler.compile_structural_tag()` has no `max_whitespace_cnt` parameter. For structural tags the limit is per-node, on `JSONSchemaFormat.max_whitespace_cnt` inside the payload, so covering it means walking the parsed tag and defaulting each `json_schema` node that doesn't already set one.

Do you plan to cover the structural-tag path here? If not, I'd like to do it as a follow-up built on your `StructuredOutputsConfig.max_whitespace_cnt` field rather than introducing a second config knob — I claimed #54497 for that. Mainly want to make sure we don't duplicate each other.
