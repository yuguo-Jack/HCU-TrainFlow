# [Bugfix][OpenAI] Respect allowed_token_ids in beam search

[Upstream PR](https://github.com/vllm-project/vllm/pull/47630) · state: open · merged: False

## Original PR description


## Purpose

OpenAI-compatible completion requests already accept `allowed_token_ids`, and the normal sampling path respects it. The beam-search path dropped that field while building `BeamSearchParams`, then ranked candidates from per-step logprobs that can include tokens outside the sampling mask, so a valid request could return HTTP 200 with forbidden `token_ids`.

This keeps `allowed_token_ids` on `BeamSearchParams`, forwards it from both completion and chat completion requests, and filters beam candidates before ranking. Small allowlists use `logprob_token_ids` so beam search can score the exact allowed set; the shared offline beam path also intersects request allowlists with structured-output grammar allowlists.

## Test Plan

I ran a real OpenAI-compatible `/v1/completions` reproduction on Qwen3-0.6B with `allowed_token_ids=[43096]`, where token 43096 decodes to `" banana"`. I ran the same server/client on current main, on this branch, and after reverting this branch diff, then ran ruff on the changed runtime files.

## Test Result

On main, the beam request returned forbidden token 12095 (`" Paris"`) while the normal sampling control returned allowed token 43096 (`" banana"`). On this branch, beam and sampling both returned token 43096; after reverting this branch diff, beam returned token 12095 again.

File: `vllm/entrypoints/generate/beam_search/utils.py` · line 29

🔴 A client's allowed_token_ids list, now threaded into beam search, has no size cap, so split_beam_scoring_params explodes it into ceil(len/128) sub-requests per beam per decoding step with no limit, letting one HTTP request spawn huge numbers of engine requests (DoS). In online.py:94-118, itertools.product(all_beams, scoring_params) issues beam_width*chunks tasks every step for up to max_tokens steps. The same unbounded fan-out happens in offline.py's scoring_params/scoring_beams loop (around line 286). Fix: cap allowed_token_ids length (or total chunk count) for beam search requests, e.g. reject or reasonably bound it in BeamSearchParams/the protocol validation, before it reaches split_beam_scoring_params.

<details>
<summary>Why this was flagged</summary>

Trigger: an OpenAI-compatible request with use_beam_search=True, beam_width>1, and a large allowed_token_ids list (client-controlled, up to vocab size) reaching ChatCompletionRequest/CompletionRequest.to_beam_search_params -> BeamSearchParams.allowed_token_ids -> online.py beam_search / offline.py _beam_search_step. split_beam_scoring_params (utils.py:21-29) chunks allowed_token_ids by MAX_LOGPROB_TOKEN_IDS=128 (sampling_params.py:32) with no upper bound on the number of chunks. online.py:94-118 then issues beam_width*len(scoring_params) engine_client.generate() tasks per decoding step, repeated for max_tokens steps - unbounded total requests per single incoming HTTP request. On the base branch allowed_token_ids was not forwarded to beam search at all, so no such amplification existed. No validation (e.g. _validate_allowed_token_ids, which only checks vocab bounds and only applies to SamplingParams, not BeamSearchParams) caps the list length before this fan-out.

**Verification:** The amplification is real and newly introduced by this change. split_beam_scoring_params (utils.py:21-29) chunks client-controlled allowed_token_ids by MAX_LOGPROB_TOKEN_IDS=128 with no upper bound. online.py:94-96 issues beam_width*ceil(len(allowed_token_ids)/128) concurrent engine requests per step, over max_tokens steps. On the base branch, beam search dropped allowed_token_ids, issuing only beam_width requests per step — no amplification.

</details>

- claude · comment · 2026-10-12T08:48:39Z · [source](https://github.com/vllm-project/vllm/pull/47630#discussion_r4246174739)

File: `vllm/entrypoints/generate/beam_search/offline.py` · line 490

🟡 (optional) Offline LLM.beam_search() callers who set both allowed_token_ids and structured_outputs on BeamSearchParams can silently get an empty or bogus result instead of an error when the two constraints conflict. In _build_beam_sampling_params, intersecting the grammar bitmask with request_allowed_set (offline.py:482-487) can make allowed_ids empty before any token is generated; offline.py:489 then treats that the same as 'grammar terminated'. Fix: at offline.py:489, distinguish 'no valid token under the combined allow-list+grammar constraint' from genuine grammar termination, and surface it as an explicit error/abort for the beam instead of silently dropping or faking a zero-token completion.

<details>
<summary>Why this was flagged</summary>

Trigger: an offline LLM.beam_search() call with BeamSearchParams(allowed_token_ids=[...], structured_outputs=...) where the user's allow-list has no overlap with the grammar's currently-allowed tokens (easy misconfiguration, e.g. JSON-schema grammar requiring '{' first). At offline.py:489 allowed_ids is empty, so result.append(None) runs. At the very first step len(beam.tokens) > prompt_len is False (offline.py in the caller at ~line 253), so the beam is never appended to instance.completed, yet it is also removed from active_indices. If it is the only active beam in the batch, _beam_search_step returns True immediately (offline.py:262-263) before instance.beams is ever reset, so beam_search() later does instance.completed.extend(instance.beams) with the stale zero-token initial beam (finish_reason=None), producing a fabricated 'completed' sequence with no generated tokens. If other beams in the batch stay active, the dead instance instead ends up with instance.beams=[] and BeamSearchOutput(sequences=[]) for that prompt.

**Verification:** nit. The mechanism is real and reachable. The new intersection at offline.py:482-487 filters `allowed_ids` down to `request_allowed_set`, which can become empty. offline.py:489-491 (`if not allowed_ids: result.append(None); continue`) then treats that identically to a terminated grammar. In the caller, offline.py:248-263 only moves a `None`-entry beam into `instance.completed` when `len(beam.tokens) > prompt_len` (line 253); at the first step this is False, so the beam is dropped and `if not active_indices: return True` (262-263) stops the search.

</details>
