# [ROCm][Perf] Fix Gemma AR+RMS prefill fallback

[Upstream PR](https://github.com/vllm-project/vllm/pull/58547) · state: open · merged: False

## Original PR description

## Purpose

1. Teach the AITER compilation pass to preserve raw Gemma weights and pass `gemma_norm` through the fused all-reduce op.
2. When custom all-reduce rejects a large prefill tensor, run the regular all-reduce followed by AITER's fused-add RMSNorm (the registered `vllm_aiter.fused_add_rms_norm` op, which gains a `gemma_norm` flag) instead of decomposing the norm into fp32 pointwise and reduction kernels. Keep Gemma inputs out of the QuickReduce fused RMSNorm path, which has no weight-bias mode.

On main alone, large prefill does not reach this fallback, so the speedup only shows up together with #57547, which sends prefill above the custom all-reduce pool through it.

---

  - `tests/distributed/test_aiter_rms_fallback.py` — Gemma prefill that misses 1-stage fused AR+RMS goes through regular all-reduce then `fused_add_rms_norm(..., gemma_norm=True)`, and never enters fused QR+RMSNorm
  - `tests/compile/passes/distributed/test_fusion_all_reduce.py` — Gemma variants of the AR+RMS fusion tests; fused graph matches the unfused Gemma residual path

Thanks Simon, you were right to question it. The earlier A/B wasn't clean: both arms already had #57547 - a tier 2 PR I'm planning to open after this one lands - applied rather than main. I re-ran it on a clean nightly with only the PRs under test and updated the description:

- On main alone this PR is perf-neutral, because main never sends large prefill through this fallback.
- With #57547, which does, the fused kernel replaces a norm done as separate fp32 kernels: about 0.09 ms vs 0.75 ms per call, 185 calls per 8k prefill chunk, so about 120 ms of a roughly 550 ms step. That is the −23% TTFT.
- main vs main + #57547 + this PR: −5 to −9% TTFT, +3 to +5% output throughput.

In other words, this PR is a protective layer preventing subsequent #57547 not becoming regressive. An alternative would be to merge this PR and #57547, but I'm slightly reluctant to do it in order to keep the PRs small enough. 

On your question: yes, the all-reduce is unchanged; only the norm after it changes.

Good catch — the ordering as written contradicted the comment immediately below it, so I've moved the Gemma block (73ec1cbe62).

Short answer: it doesn't change which pattern wins today, but only because of graph position.

`PatternMatcherPass.apply` collects the candidate anchor nodes for every registered pattern, walks them in reverse graph order, and only falls back to registration order when several patterns are anchored on the *same* node. The quant-fused patterns anchor on the quant node, which is strictly downstream of the norm, so they get tried before any AR+RMS-only pattern can claim the `all_reduce` — wherever they sit in the registration list.

There is deliberately no Gemma+quant variant: the fused AR+RMS+quant op has no `gemma_norm` mode, so a Gemma graph with a trailing quant keeps folding `(1 + weight)` outside the kernel, exactly as it does on main.

To pin this down, I parametrized `test_rocm_aiter_all_reduce_rmsnorm_group_quant_fp8_fusion_pass_replace` over Gemma norms. If a Gemma AR+RMS match ever did strand the trailing quant, the existing `check_before_ops(..., fully_replaced=True)` assertion would catch it.
