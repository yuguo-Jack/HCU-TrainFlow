# [Bugfix][Model][Rust Frontend] Qwen3_ASR: Handle ragged Qwen audio batches from Rust frontend

[Upstream PR](https://github.com/vllm-project/vllm/pull/60979) · state: open · merged: False

## Original PR description



## Overview


Fixes #60970. 
Fix an EngineCore crash when the Rust frontend batches Qwen3-ASR audio requests with different padded feature lengths. Normalize ragged audio features in Qwen3-ASR and the shared Qwen Omni input parser.
## Claims
- Accept ragged lists and tuples of per-audio feature tensors, remove padding, and concatenate valid frames along the time dimension.
- Preserve existing stacked and flat tensor handling, feature order, and dtype.
- Add regression tests for both parsers, including mixed lengths, padding, and mismatched feature/length counts.

## Details


### Root Cause
1. The multimodal registry declares `input_audio_features` as `FieldLayout::Batched`, so the Rust frontend emits one item per clip — a 2-D `[n_mels, padded_seq]` tensor, padded to the request's longest clip.
2. The model contract is `MultiModalFieldConfig.flat_from_sizes(..., dim=1)`: a single flat `[n_mels, total_seq]` tensor.
3. `_reduce_data` stacks only when all shapes are equal; unequal durations (or unequal intra-request padding) → `return batch` raw list.
4. The parser's guard only matches `torch.Tensor` with `dim() == 3`; the list falls through and dies in TensorSchema validation.


## Why this is not a duplicate
Following PR (before 2026.10.10) are related but none of them solved this problem.
- #50958 — canonical model-side fix for familiar bug of Gemma series model. Not involved rust frontend.
- #57146  — It addresses Python preprocessing parity but does not add ragged-list handling or change the Rust preprocessing path.

I tested this on an RTX 6000 Ada (sm_89) with `Qwen/Qwen3-ASR-1.7B`:
- vLLM: the 0.31.0 wheel plus this PR's two model files.
- Rust frontend: `vllm-rs` built from the v0.31.0 tag.
- Input: 16 distinct FLEURS test clips (8 en, 8 zh, about 5 s and 14 s).
- Requests: greedy, one pass sending clips one by one, then two passes sending all 16 at once.

HTTP 200 counts:

| | one by one | all 16 at once, x2 |
|---|---|---|
| Python frontend, 0.31.0 | 16/16 | 16/16, 16/16 |
| Python frontend, this PR | 16/16 | 16/16, 16/16 |
| Rust frontend, 0.31.0 | 16/16 | 0/16, then 0/16 (EngineCore dies in the first pass: `got torch.Size([3, 128, 462])`) |
| Rust frontend, this PR | 16/16 | 16/16, 16/16 |

With the PR, the concurrent passes give the same transcripts as the one-by-one pass, and both match the Python frontend: 16/16 identical in each comparison.

I also logged a hash of each clip's features after unpadding. Across 8 encoder calls the input was a ragged list, e.g. `[(128, 504), (128, 536), (128, 474), (128, 510)]`. Those calls covered 14 of the 16 clips, and every clip's features were bit-identical to the same clip sent alone. I didn't run Qwen2.5-Omni.

Two notes for anyone reproducing:
- As #60970 notes, repeated audio skips this code. If you reuse clips across rounds, give each request a fresh `uuid`. My first run passed on unpatched 0.31.0 for exactly this reason.
- The Rust frontend doesn't start from the official repo as-is (no `tokenizer.json`, nested `vocab_size`; filed as #61057). All four arms used a local copy with a converted `tokenizer.json` and `--hf-overrides '{"vocab_size": 151936}'`.
