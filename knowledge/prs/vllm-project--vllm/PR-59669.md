# [Feature][MoE] Add expert-capacity token dropping

[Upstream PR](https://github.com/vllm-project/vllm/pull/59669) · state: open · merged: False

## Original PR description

## Overview

This PR adds opt-in expert-capacity token dropping for modular MoE kernels.

The token-dropping pass runs before prepare/finalize. It sorts assignments by expert and weight, then drops the lowest-weight assignments beyond each expert’s capacity.

The compactor is a per-prepare/finalize layout adapter. For standard format, it removes fully dropped token rows before dispatch; for batched format, it slices padded expert-major payloads after dispatch. It records the original layout and restores or scatters outputs before combine.

- `FusedMoEConfig.expert_capacity` is disabled by default. When enabled, `_drop_tokens` keeps the highest-weight assignments per expert, preserves token/slot order for ties, and represents dropped assignments as `topk_ids == -1` with zero weights. A Triton fast path handles common CUDA shapes.
- Capacity is passed into prepare/finalize constructors and validated/propagated by `FusedMoEKernel`. Compactor ownership is centralized in `FusedMoEPrepareAndFinalizeModular`.
- Standard-format dispatch removes rows whose assignments were all dropped before dispatch and scatters them back after finalize. Batched-format dispatch compacts the received expert-major payload for supported NIXL-EP/DeepEP-LL paths and restores the communication layout before combine. The batched compactor preserves FP8 value/scale layouts for DeepGEMM and Humming experts.
- Expert workspaces use capacity while retaining dispatcher rank limits.
- Monolithic MoE kernels and LoRA configurations reject token dropping.

## Claims

- Expert capacity is opt-in and disabled by default.
- Token dropping retains the highest-weight assignments per expert while preserving stable ordering for tied weights.
- Supported standard- and batched-format paths reduce modular expert workspace allocations without repurposing dispatcher rank limits.
- The measured workspace savings do not imply lower total device memory because the allocator generally refills freed workspace with KV cache.

## Validation

- `pytest tests/kernels/moe/test_modular_kernel_token_dropping.py -v --tb=short`: **100 passed**.
- gsm8k evals with and without token dropping enabled.  See below.

## Details

The latest benchmarks used Qwen3-30B-A3B-FP8-block on GSM8K. All four result rows below were captured with CUDA graphs enabled.

| Format | Experts | Prepare/finalize | Variant | Accuracy | Eval seconds | Workspace/GPU | Workspace saving |
|---|---|---|---|---:|---:|---:|---:|
| Standard | Humming grouped | No-DP/EP | No dropping | 89.61% | 28.7 | 512 MiB | — |
| Standard | Humming grouped | No-DP/EP | Capacity 128 | 87.57% | 29.5 | 351 MiB | 161 MiB/GPU (31.4%) |
| Batched | DeepGEMM | NIXL-EP | No dropping | 90.52% | 18.7 | 176 MiB | — |
| Batched | DeepGEMM | NIXL-EP | Capacity 128 | 89.61% | 36.5 | 88 MiB | 88 MiB/GPU (50%) |

These are modular expert-workspace savings, not total-device-memory savings. Both capacity runs passed their configured GSM8K threshold.

These are single-run results. The current batched timing is slower with capacity 128. Standard row compaction is also disabled during CUDA-graph capture because its dynamic row selection is not capture-safe; the measured standard workspace reduction comes from capacity-aware workspace sizing.
