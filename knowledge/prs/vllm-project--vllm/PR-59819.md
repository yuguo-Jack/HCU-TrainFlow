# [LoRA] Add an API to read and update LoRA slot weights

[Upstream PR](https://github.com/vllm-project/vllm/pull/59819) · state: open · merged: False

## Original PR description

## Overview

Adds tensor-based read/update methods for loaded LoRA adapters, including dense and MoE layers. Worker extensions and weight-transfer callbacks can use the manager API instead of private slot tables and buffer attributes. Related to the adapter-only synchronization item in RFC #48297. Open-PR searches for that RFC and LoRA slot updates found no equivalent runtime slot read/update API; related work on adapter loading or layer execution is outside this change. The diff is limited to 11 files: LoRA managers/layers, existing LoRA tests, and `docs/features/lora.md`.

## Claims

- `get_adapter_slot(lora_id)` returns the active GPU slot or `None`.
- `get_adapter_slot_weights(lora_id, module_names=None)` returns views of the physical A/B buffers: rank-local, padded, and with scaling folded into B. Dense linear, embedding, logits, gated/non-gated MoE, shared-expert factors, and 3D MoE layouts are supported.
- `update_adapter_weights(lora_id, weights, update_cpu_cache=True)` accepts checkpoint-oriented tensors with full TP dimensions and the loaded rank. It validates every module before writing, retains omitted packed slices, applies EP expert slicing, and reuses each layer's existing `set_lora` layout/sharding. Updating the cached copy preserves weights across GPU-slot eviction. GPU-only replacement requires a pinned active adapter and complete slices. Aliased inputs are snapshotted before reset/copy.
- `WorkerLoRAManager` forwards these methods. No scheduler/model-runner changes or trainer-to-worker tensor transport are added.

## Details

**Why these primitives for ZO / ES.** A zeroth-order step can write a new perturbation before every probe forward. Repeated checkpoint I/O, CPU-cache copies, intermediate allocations and reset-then-copy work belong outside that hot loop. Pin the active adapter, acquire its local views once, then generate directions directly into those views or copy prepared GPU factors into them. This writes to the buffers the forward already reads, retaining their addresses for CUDA graphs. The general replacement API remains available when validation, layout conversion or eviction persistence is needed. This is an update primitive, not a claim about end-to-end training speed.

```python
class ProbeWriter:
    def prepare_probe(self, lora_id, module_names):
        manager = self.model_runner.lora_manager
        manager.pin_adapter(lora_id)
        weights = manager.get_adapter_slot_weights(lora_id, module_names)
        self.probe_b = [b for _, bs in weights.values() for b in bs]

    def zero_probe_b(self):
        with torch.inference_mode():
            torch._foreach_zero_(self.probe_b)
```

**MoE contract.** A factors have shape `(experts, rank, in)` and B factors `(experts, out, rank)`. Slice order is `w1/w2/w3` for gated layers, `w1/w2` for non-gated layers, and `w13/w2` for 3D layers. Shared factors keep an expert axis of one. Replacement accepts global EP tensors or this worker's local expert range; slot views expose actual TP/EP-local storage and must not be treated as full checkpoint tensors.

**Scope and tradeoffs.** Call from inside the worker, between forwards, ordered on its stream. Utility RPC carries small arguments; tensors come from the worker or an existing transfer channel. Retained views bypass replacement validation and affect only GPU storage: keep the adapter pinned, write all intended/padded entries, and synchronize any producer stream. Removal or eviction after unpinning invalidates the adapter/view association. The API does not quiesce concurrent requests. Prefix-cache entries are not invalidated; reset them after changing weights when affected requests share prefixes. An adapter removed from the CPU cache still reloads from its original checkpoint.

The implementation is confined to LoRA managers and layers. It reuses loading/sharding logic rather than adding another forward or transfer path. Documentation explains both persistent replacement and the direct-write ZO path.
