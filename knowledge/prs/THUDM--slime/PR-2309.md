# perf(rollout): reuse filtered prompt token ids

[Upstream PR](https://github.com/THUDM/slime/pull/2309) · state: open · merged: False

## Original PR description

## Summary

Max-length filtering already tokenizes every retained text prompt, but default rollout preparation encodes the same rendered prompt again. Reuse those IDs for stock training and evaluation, eliminating the second encoding pass.

The cache contains only immutable packed uint32 IDs (4 bytes per token). Deep-copied siblings share the payload and each materializes its own mutable token list on consumption. The cache is excluded from serialization and dataclass reconstruction. Multimodal outputs and custom rollout/generate/data-source contracts remain uncached.

Training is wired through the current `slime.data.data_source` API. Missing rollout configuration disables caching; existing tokens and multimodal processing retain their precedence.

Related to #1111.

## Validation

- 111 local CPU tests passed across filtering, Sample serialization/reconstruction, train/eval cache ownership, buffer/checkpoint behavior, fully async rollout, and plugin contracts.
- Direct CI-style filtering runner: 25 passed.
- Repository-pinned pre-commit checks passed.
- On the original 10,000-prompt in-memory BPE benchmark, second-pass `tokenizer.encode` calls dropped from 10,000 to 0. The immediate same-process comparison for filtering plus preparation was 2.65s versus 0.57s; packed payload size was 8.35 MiB. Timing is workload-dependent.
- The updated GitHub CPU/agent matrix also exercises distributed Ray/Straw fan-out against the current upstream data-source API.

- liuhao-labs · comment · 2026-08-24T00:39:33Z · [source](https://github.com/THUDM/slime/pull/2309#issuecomment-5389432691)

Thanks for the context. I measured the retained text-only path before opening this, because the benefit depends on dataset size and prompt length.

On the same local workload (10,000 retained prompts, 2,189,001 prompt token IDs, an in-memory ByteLevel BPE), the current path made one batched tokenization call during filtering plus 10,000 per-sample `encode()` calls during rollout preparation. With this change, the second count is zero.

The immediate same-process comparison was:

- current path: 2.652 s total (0.586 s filter + 2.066 s prepare)
- cached path: 0.571 s total (0.541 s filter + 0.030 s prepare)
- rollout preparation: 98.6% lower, total for the two stages: 78.5% lower

The retained cache payload was 8,756,004 bytes (8.35 MiB) as packed uint32 IDs. It is only created when max-length filtering has already tokenized the prompt, only for retained text prompts on the stock rollout path, and it is consumed before Ray transfer. Multimodal processor outputs and custom rollout/data-source paths remain uncached.

So this is not intended to add tokenization work when filtering is disabled; it only reuses work that has already happened. The exact speedup will vary with tokenizer and prompts, but the invariant improvement is one fewer encoding pass per retained text prompt.
