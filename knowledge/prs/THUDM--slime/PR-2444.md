# Support manual Megatron restarts with retained serving

[Upstream PR](https://github.com/THUDM/slime/pull/2444) · state: closed · merged: True

## Original PR description

## Summary

Allow a failed Megatron training job to restart on the same Ray cluster while retaining healthy SGLang engines, routers, and accepted rollout data. The new trainer can change its parallel layout and replay the batches after the last committed checkpoint without regenerating samples or repeating accepted reward postprocessing.

Replay uses Straw storage (`--rollout-data-transport straw`) or per-rollout debug dumps (`--save-debug-rollout-data` with `{rollout_id}` in the path). Internal serving retention does not require the legacy `--use-fault-tolerance` flag.

The PR also makes recovery ownership explicit, publishes each converted training batch once, fixes restored disk-delta weight updates, and bounds cleanup independently of normal training and storage operations.

## Changes

### Serving and training lifetimes

- Introduce a named, detached `ServingCluster` that owns routers, engines, placement groups, the queue controller, and the weight-update lock. `RolloutManager` borrows those resources and can be replaced independently.
- Fence live training drivers before accepting a successor. Register trainer actors with serving so they can be released even after manager failure.
- Retain serving and replay data after training failure; dispose the session after successful completion. Launchers preserve a running Ray cluster when resubmitting a job.
- Let the driver own attempt cleanup, including rollback when startup fails after attaching to serving. Give an unresponsive manager a bounded opportunity to pause, then release trainers directly through serving. Cleanup failures do not replace the original training exception.
- Dispose manager and serving resources independently, so a custom data source's cleanup error does not skip serving cleanup.

### Checkpoint and replay ownership

- Use queue receipts as the authority for accepted raw and converted batches. Represent conversion as an ordinary queue control task instead of maintaining a second batch-progress ledger.
- Keep the recovery journal responsible for the committed model boundary and the replay window. Reconcile accepted queue results after manager death or a lost RPC reply.
- Separate runtime training completion from durable checkpoint completion. Only a committed model/source checkpoint releases the associated replay pins.
- Bound scheduler progress to buffered and currently collected work; discard finished conversion references instead of retaining an ever-growing delivery history.
- Make checkpoint selection return a configuration copy and a restore plan. Pass checkpoint fields and the serving weight version through an explicit `TrainingResume`; keep long-lived data-source configuration separate from each trainer attempt.
- Preserve the existing journal field representation and all public custom function signatures and return conventions.

### Shared batch publication

- Convert and publish the global training batch once. Send each DP rank a selection over shared tensor records instead of serializing another payload per rank.
- Rebuild selections when training resumes with a different parallel layout. Keep R3/score-centering tensors lazy and reuse accepted converted data.
- Keep custom conversion and reward-postprocessing hooks at the original whole-batch boundary.
- Put asynchronous consumers on their owning data source, with its pause, restore, and close lifecycle, instead of using a module-global worker.

### Engine recovery and weight synchronization

- Bound engine reset and health-check RPCs, unregister failed engines, and terminate their serving children before replacing them.
- Send old weight-update-group reset requests to **all** serving groups before waiting. Prefill and decode can share an NCCL group; waiting for one side before notifying the other can deadlock healthy PD engines.
- On the first disk-delta update after trainer replacement or engine changes, publish the current restored weights as a full baseline. Keep weight versions above earlier publication attempts.
- Restore the DDP gradient-synchronization hook correctly across repeated rollouts with `overlap_grad_reduce`.

### Optimizer state and defaults

- Support recovery with `--use-stateless-adam --no-save-optim`. Save and restore the LR/WD scheduler alongside the model; require RNG state and validate the scheduler sidecar before accepting the checkpoint.
- Continue requiring optimizer state for ordinary Adam. Changes are confined to Slime's Megatron adapter; `/root/Megatron-LM` is unchanged.
- Set both `--rollout-health-check-timeout` and `--rollout-health-check-first-wait` to **600 seconds** by default.
- Add an independent `--rollout-cleanup-timeout`, default **60 seconds**, for exiting an attempt. It does not limit normal data reads, generation, training, or checkpoint writes.
- Update English and Chinese recovery documentation and retain the CPU/GPU recovery suites in the CI matrix.

## Validation

### Regression and fault tests

Lifecycle/configuration validation recorded for commit `8a6406bd`.

The lifecycle/configuration follow-up passed **443 distinct regression cases** across training recovery, argument validation, Straw transport, fully asynchronous/distributed rollout, optional Straw dependencies, engine control, and score centering. Repeated verification runs are not added to this count.

The **12-case real-Ray manager recovery suite** additionally covers:

- Manager death after raw acceptance, conversion acceptance, or recovery-journal persistence.
- Lost conversion replies with a surviving manager.
- Replay and repartitioning with online GC both enabled and disabled.
- Engine reset timeout while retaining healthy peers.
- A live manager that cannot pause, and direct trainer release by the serving owner.
- Joint prefill/decode reset through a barrier that requires both peers to participate.

Tests also check partial-startup rollback, cleanup error propagation, checkpoint selection without mutating requested paths, and unchanged args-based custom data-source construction.

### GPU recovery

Validation used a four-host cluster with **8 H100 GPUs per host** and shared JuiceFS storage.

The original recovery validation passed six GPU scenarios covering disk-delta updates, PD engine failure, object-store fully asynchronous rollout, ordinary Adam with overlapping gradient reduction, dense stateless Adam, and MoE stateless Adam with R3.

The lifecycle/configuration changes were also exercised with:

| Scenario | GPUs | Fault and restart | Checks |
| --- | ---: | --- | --- |
| Qwen2.5-0.5B, PD, stateless Adam | 4 | Real training OOM, retained manager, TP 1 → 2 / DP 2 → 1 | Healthy serving processes retained; checkpoint/scheduler restored; accepted samples replayed; subsequent training and saves complete |
| Qwen3-30B-A3B, R3, stateless Adam | 8 | Real training OOM plus manager loss, TP 1 → 2 / DP 4 → 2 | Serving retained; samples and routing data replayed; scheduler progress restored; finite gradients and completed training |

Large-MoE recovery uses stateless Adam; ordinary Adam recovery is covered by the dense-model scenarios.

### Batch-publication measurement

Measured Qwen3-30B-A3B on **32 H100s**: 16 training GPUs, 16 serving GPUs, configured serving concurrency 256, 256 samples per rollout, 1,024 generated tokens per sample, four rollouts, and R3 enabled. TP=2, EP=8, DP=8.

| Manager phase | Before | Shared-batch publication |
| --- | ---: | ---: |
| Whole-batch conversion | 0.00699 s | 0.00641 s |
| Global publication | Not timed separately | 1.92476 s |
| DP partition/publication | 3.09694 s | 0.09642 s |

These are phase means. The DP phase becomes about **32.1× faster** because it builds selections over one published batch. This is **not an end-to-end throughput speedup**; the revised global-publication cost is reported separately. R3 routes were nonempty and fully consumed during the measured training runs.

## Scope and limitations

- Recovery requires resubmitting the job to the same live Ray cluster. This PR does not introduce automatic job retries.
- Losing the serving owner or the whole Ray cluster requires cold startup from a committed checkpoint.
- Keep model, rollout settings, global batch size, session identity, and custom hook configuration unchanged when attaching to retained serving. Supported trainer parallelism and memory settings can change.
- Stateless Adam rebuilds FP32 master parameters from the saved model precision. Parallel-layout changes can also alter RNG behavior; bitwise-identical training after restart is not promised.
