# perf: fuse FP32 CUDA updates in StatelessAdam

[Upstream PR](https://github.com/THUDM/slime/pull/2461) · state: open · merged: False

## Original PR description

## Problem

`StatelessAdam.step()` launches several pointwise operations and allocates parameter-sized temporary tensors for every update, even though it does not retain Adam moments.

## Change

- Fuse the update into one Triton kernel per parameter for same-shape, contiguous FP32 CUDA parameters and gradients. Other inputs continue through the existing eager path.
- Preserve Adam/AdamW modes, bias correction, maximize, decoupled gradients, learning-rate changes, and empty optimizer state. Use explicit FMA and rounded division at the corresponding eager operation boundaries, and record the in-place mutation for autograd.
- Add single-GPU correctness and temporary-memory coverage, register it in the generated PR workflow, and include the kernel package in wheel installations.

The existing `--use-stateless-adam` configuration selects this path automatically when eligible; no new option is required.

## Validation

On one RTX 5090, Python 3.12.13, PyTorch 2.11.0+cu128, and Triton 3.6.0:

```text
PYTHONPATH=. python -m pytest tests/test_stateless_adam.py tests/test_stateless_adam_cuda.py -q
43 passed
```

Coverage includes reset-Adam parity, exact eager rounding with coupled-decay cancellation, unchanged gradients, non-contiguous and low-precision fallback, broadcast decoupled gradients, non-default CUDA streams, and autograd mutation tracking. The memory regression fails on the original implementation: a 16 MiB parameter update allocates 32 MiB of temporary tensors; the fused path stays below the 1 MiB threshold.

CPU-only execution passes 6 tests and skips 37 CUDA tests. A wheel built and installed into an isolated directory passes a real CUDA update and stale-graph check outside the source checkout. Black, isort, Ruff, workflow-generation consistency, and `git diff --check` pass.

## Benchmark

Baseline: `58b0878679de339ec7844b45d884a87955a134be`. Hardware/software: one RTX 5090, driver 580.178.04, CUDA 12.8, and the versions above.

Optimizer-only measurements use FP32 parameters and fixed gradients, AdamW with weight decay 0.1 and learning rate 1e-6. After warmup, alternate baseline/fused order over 7 rounds of 30 updates; report median synchronized wall time, including Python and launch overhead.

| Parameter layout | Original | Fused | Speedup |
| --- | ---: | ---: | ---: |
| One tensor with 32M elements | 1.038 ms | 0.256 ms | 4.06x |
| 256 tensors with 4096 elements each | 3.293 ms | 2.087 ms | 1.58x |
| Qwen3-0.6B: 310 tensors, 596,049,920 parameters | 12.406 ms | 4.605 ms | 2.69x |

For the Qwen layout, additional peak PyTorch tensor allocation during the optimizer step falls from 1,245,708,288 bytes (1.16 GiB) to zero after warmup. This excludes allocator-reserved memory, CUDA context memory, and compilation.

A Transformers Qwen3-0.6B forward/backward/update benchmark using Slime's optimizer reduces step time from **47.23 ms to 39.20 ms (17.0%)** and peak allocated GPU memory from **5.62 GiB to 5.04 GiB**. It uses FP32 parameters/gradients, BF16 autocast, SDPA, batch size 1, sequence length 256, fixed random tokens, learning rate 1e-5, and weight decay 0.1. Baseline/fused/fused/baseline runs each start from the same checkpoint and seed, with 10 warmup and 30 measured steps. The reported time is the median of the two per-run medians. All four 40-step loss curves match exactly in this configuration.

This is optimizer and model-step validation, not a complete Slime RL run or a task-quality result. Distributed Megatron, CPU offload, other GPUs, and other PyTorch/Triton versions were not exercised.

Prepared with Codex assistance; the results above were measured on the original and final implementations.
