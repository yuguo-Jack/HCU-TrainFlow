## Affected area

Python API or bindings; FE OSS kernels or CuTeDSL.

## Summary

Use the shared native binders for admitted SM90 FP16/BF16 dense and packed forward plans, through both graph and standalone execution. Each call still observes current buffers, validates storage and builds a fresh frame for the existing compiled pointer host.

SM90 needs more than an architecture-gate extension. Dense binding retains its covering-permutation layout predicate and fixed scheduler extents. THD binding retains fixed batch and 128-byte workspace alignment. Both use the host's natural-unit scale slot, including zero and negative specializations. Standalone packed Stats keeps its BHS-versus-TH1 disambiguation in metadata, including the ambiguous S=1 case, without constructing a tensor view.

The existing singleton-stride recorders now rebuild the native binder after replacing the recorded callable, so they continue to inspect the actual launch.

Stacked on #1371. The SM90 layer is seven files, 311 additions/45 deletions relative to that parent; the parent native-forward layers have their own reviews and validation.

## Why

SM90 still rebuilt Python operand facts and launch frames on every call after its pointer-host migration. Reusing the native dense/THD binders removes that repeated work while preserving Hopper-specific storage, scheduler and scale contracts. Graph execution keeps the same public API and current workspace/stream guards.

## Related issues

Continues the native binder work in #1291, #1361 and #1371. Physical stride and product probes cover the truncation class discussed in #1146.

## API and compatibility impact

No public API, capability-row, kernel, scheduling or dependency-floor change. SM90's existing graph envelope and standalone head-dimension support remain unchanged; CuTe DSL 4.7.0 is tested. Runtime validation does not fall back to a different executor. Per-call pointers, streams and storage observations remain outside plan caches.
