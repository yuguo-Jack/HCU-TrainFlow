# perf(recipe): Enable cuDNN GDN for GB300 Qwen3.5-VL 35B/397B GDN layers 

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6330) · state: closed · merged: True

## Original PR description

# What does this PR do ?
Select gdn_kernel_backend="transformer_engine" in the GB300 Qwen3.5-VL 35B-A3B and 397B-A17B perf recipes when Megatron-Core declares the field (NVIDIA/Megatron-LM#6645, re-landing as #7583). The FP8-CS and MXFP8 variants inherit it; the VR200 aliases built from these recipes keep FLA.

ConfigContainer.validate() warns, without changing the config, when the installed packages cannot reach cuDNN's fast GatedDeltaNet kernels: no Transformer Engine GatedDeltaNetAttention, cuDNN frontend missing or older than 1.29.0, or, on frontend 1.29+, a CuTe DSL that is not importable or older than 4.7.0 (the frontend then falls back to its slower cuTile engine).

Measured with MXFP8, one run per arm in the same batch: +9.6% at 397B-A17B on 64 GB300 and +12.0% / +19.4% at 35B-A3B on 16 GB300.

[P2] Warn about the documented Transformer Engine 2.19 + FP8 incompatibility

**Failure:** With TE 2.19, `HAVE_TE_GDN=True`, frontend 1.29.0, and importable CuTe DSL 4.8.0, the probe returns `[]` and this validator is silent even for the newly enabled FP8-CS/MXFP8 recipes. However, the new `qwen_vl/common.py:135–137` explicitly documents that TE 2.19 raises under their FP8 autocast. This precision is visible here: `runtime_config_update()` applies mixed precision before validation (`config.py:2084–2089`), and `Qwen3VLTransformerBlock.forward()` wraps these layers in `get_fp8_context()` (`transformer_block.py:727–755`). Other stack gaps also produce an install hint claiming `transformer-engine>=2.19` is sufficient. The missed warning follows directly from this source; the upstream exception was not executed in this review.

**Correction:** Extend `_validate_cudnn_gdn_stack()` to diagnose that known combination without changing the backend or disabling FP8 globally. A bounded suggested insertion after the probe is:

```python
te_version = (
    _installed_distribution_version("transformer-engine")
    if getattr(config.model, "fp8", None)
    else None
)
te219_fp8 = te_version is not None and _release_tuple(te_version)[:2] == (2, 19)
if te219_fp8:
    issues.append(
        f"transformer-engine {te_version} rejects GatedDeltaNet under FP8 autocast"
    )
te_floor = "2.20.2" if te219_fp8 else "2.19"
```

Use `transformer-engine>={te_floor}` in the existing install hint, and update the helper docstring's claim that validation cannot see the FP8 case. This intentionally diagnoses the documented 2.19 family rather than declaring every build below 2.20.2 broken: the repository pins a `2.20.0+131157b5` development build, whose upstream behavior could not be inspected. Verify the suggestion against the intended TE builds before adopting it.

**Preservation and acceptance:** Proposed `test_cudnn_gdn_warns_for_te219_fp8`: mock the probe to return `[]`, metadata to return `2.19.0`, and set the selected model backend to TE with `fp8="hybrid"` and separately `"e4m3"`; each must warn once, recommend 2.20.2+, and leave backend/precision unchanged. With identical packages but `fp8=None`, retain silence. With FP8 and TE `2.20.2` or the compatible pinned development build, retain silence. Retain the existing no-field/FLA/torch cases' assertion that the probe is never called, and the existing stack-gap assertions for frontend/DSL advice and the FLA override.
