# feat(training): dynamic context parallel on global-batch packing with a Qwen3.5-35B-A3B recipe

[Upstream PR](https://github.com/NVIDIA-NeMo/Megatron-Bridge/pull/6275) · state: closed · merged: True

## Original PR description

## What does this PR do ?

Adds **dynamic context parallelism** on top of global-batch online packing (#6127, split out per review), with a Qwen3.5-35B-A3B fine-tuning recipe. With `model.dynamic_context_parallel=True`, Megatron-Core's `default_dynamic_cp` scheduler runs every packed microbatch on a context-parallel group sized for its longest sequence, chosen from the `dp × cp` pool, instead of splitting every microbatch across the full static group.

**Depends on #6127.** This branch contains that PR's commit; review the top commit only.

**Validation (`training/config.py`)**
- `model.dynamic_context_parallel` makes the dataset switch select `default_dynamic_cp`; setting either model field without `dataset.enable_global_batch_packing` is rejected.
- Dynamic-CP rules: a power-of-two `dp × cp` pool of at least two ranks, a power-of-two `min_dynamic_context_parallel_size` within the pool, `dist.use_decentralized_pg=False`, and `pool × max_seqlen_per_dp_cp_rank` covering `seq_length`.
- The per-sequence alignment covers every group the pool can form: `2 × dp × cp`, and `dp × cp × tp` under sequence parallelism (review fix: the SP multiple previously ignored the DP factor and under-padded with TP above two and DP above one).
- The support probe requires the dynamic-CP arguments on the packed batch fetch and points at `./scripts/switch_mcore.sh dev` when they are missing.

**Glue and data**
- The packed batch fetch receives `dynamic_cp=True` only when dynamic CP is on; Megatron-Core returns a `PackedSeqParams` carrying the microbatch's CP group, which the glue binds before attention runs.
- `fold_alignment_padding` (GPT-SFT and `GPTDatasetConfig`) reports each sequence's alignment padding as part of the sequence. Set it when attention runs on FlashAttention under CP, for example head dimension 256 on Blackwell where Transformer Engine disables cuDNN fused attention for training: FlashAttention rejects THD bins with padding between sequences. It is exact for causal attention because the padding follows each sequence's last token and stays loss-masked. It also needs https://github.com/NVIDIA/Megatron-LM/pull/7417.

**Recipe, example, docs**
- `qwen35_text_35b_a3b_sft_8gpu_gb200_bf16_dynamic_cp_config`: Qwen3.5-35B-A3B SFT on CoderForge-Preview SWE-Rebench, TP1 PP1 CP4 EP8 on eight GB200 GPUs, 32K cap, 16 loader workers, full recompute (see Measured for why not selective).
- `examples/training_features/long_context/qwen35_35b_a3b_dynamic_cp.py` launches it, with a `--tiny-model` two-GPU smoke on a generated variable-length SFT file; the README shows measured results.
- New page `docs/training/dynamic-context-parallel.md` with its Fern mirror and navigation entries; `packed-sequences.md` stays global-batch-only.

Requires the Megatron-Core dev pin.

## Measured

**The recipe on GB200 (Bridge).** Eight GB200 GPUs in one NVL72 rack, NeMo 26.06.01, Megatron-Core dev pin + #7417, random initialization, the first 4,000 CoderForge SWE-Rebench trajectories, 12 steps with the first four dropped; throughput is Bridge's model TFLOP/s per GPU.

| Configuration | Median step | Median TFLOP/s per GPU | Peak allocated |
|---|---|---|---|
| Recipe: dynamic CP, full recompute, 16 loader workers | 88 s | 90 | 108 GB |
| Static CP4 (`dp_balanced`), otherwise identical | 83 s | 93 | 108 GB |
| Recipe with 2 loader workers | 254 s | 31 | 108 GB |
| Recipe with selective recompute (`moe_act`, `layernorm`) | 75 s over four steps, then NCCL out of memory | 106 | 163 GB |

GPT-SFT tokenizes each CoderForge trajectory lazily (about 9 s per sample) and the scheduler pulls a whole step's samples at once, so the default two loader workers left the GPUs waiting; the recipe now sets 16. Selective recompute is about 13% faster per step but reserves over 170 GB per GPU, and the next communicator dynamic CP creates for a new group size then fails to allocate; full recompute keeps the headroom. About nine in ten of these trajectories exceed the 32K cap, so nearly every sequence needs the full CP4 group and dynamic CP stays within noise of static CP4 on this data. To check whether a longer cap changes that, I also ran 128K with CP8 and 16K tokens per rank, which keeps the trajectories whole: dynamic CP and static CP8 again stayed within noise (median step 188 s against 177 s, 81 against 83 TFLOP/s, peak 121 against 139 GB over steps 5 to 10), so the recipe keeps the 32K cap.

**Dynamic vs static CP on variable-length streams (Megatron-LM's loop).** Same Megatron-Core scheduler, measured earlier with Megatron-LM's training loop (dev `0c59fc6eb` + the `pad_between_seqs` fix, `pytorch:26.07-py3`, FlashAttention-2, 60% optimizer CPU offload), Qwen3.5-35B-A3B on one GB200 node, TP1 PP1 CP4 EP4, full recompute, 10 iterations with the first 3 dropped:

| Stream | Cap / global batch | Static CP4 | Dynamic CP | Δ step time | Tokens eligible for CP1 / CP2 / CP4 |
|---|---|---|---|---|---|
| Mixed-length SFT (median ~3.7K, tail to the cap) | 49,152 / 512 | 187.4 ± 10.6 s, 21.1K tok/s | **169.8 ± 14.7 s, 23.3K tok/s** | **−9.4%** | 38% / 22% / 39% |
| Near-cap RL (36K–46K) | 49,152 / 256 | 526.9 ± 3.7 s | 531.2 ± 6.2 s | +0.8% (tie) | 0 / 0 / 100% |
| Long RL (38K–97K) | 99,840 / 128 | 381.9 ± 14.4 s | 385.4 ± 35.5 s | +0.9% (tie) | 0 / 11% / 89% |

Dynamic CP pays where static CP is required by memory and the stream has short sequences to run on smaller groups; when every sequence needs the full group it is a small scheduling overhead, which matches the CoderForge result above.
