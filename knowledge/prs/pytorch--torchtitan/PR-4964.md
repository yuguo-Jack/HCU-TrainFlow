# [not for land] use mxfp8 kernels from PyTorch core

[Upstream PR](https://github.com/pytorch/torchtitan/pull/4964) · state: open · merged: False

## Original PR description

Summary:

Hook up mxfp8 kernels from
https://github.com/pytorch/pytorch/pull/199022

Test Plan:

```bash
# mxfp8
NGPU=8 MODULE=torchtitan_recipes.tests.models.llama3 CONFIG=llama3_8b_mxfp8_100steps_8k ./run_train.sh
# mxfp8 with stateful SR for grads
NGPU=4 CUDA_VISIBLE_DEVICES=0,3,4,5 MODULE=torchtitan_recipes.tests.models.llama3 CONFIG=llama3_8b_mxfp8_grad_output_sr_100steps_8k ./run_train.sh
# mxfp8 with stateless SR for grads
NGPU=4 CUDA_VISIBLE_DEVICES=0,3,4,5 MODULE=torchtitan_recipes.tests.models.llama3 CONFIG=llama3_8b_mxfp8_stateless_sr_100steps_8k ./run_train.sh
```

Performance and numerics unchanged on short Llama 3 8B run: https://gist.github.com/vkuzo/15716af96a442941f2a32c774ea731b5

Stateful and stateless SR logs: https://gist.github.com/vkuzo/169a95912e6689c63f35ae7cdf2ec04f


Note that there is a slight peak memory regression, this is not specific to `quantize_tensor` and instead a combination of:
1. cutedsl internals of `cute.kernel` implementation holding a reference cycle including op output tensors
2. torchtitan disabling garbage collection
3. (1) being triggered after gc is disabled and before cuda graph capture

I verified that other cuteDSL ops in torch have the same behavior: https://gist.github.com/vkuzo/3442f362c7542271daade09102d5a681

Also, agent verified that before vs after are bitwise equivalent on individual op level.  We do not match bitwise e2e because torch.compile chooses a different reduction order on surrounding on new vs old, chasing this down is in progress.
