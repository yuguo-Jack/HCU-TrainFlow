# [rl] Build and pack training batches in their own process

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5284) · state: closed · merged: False

## Original PR description

**TLDR:** On a busy controller, the batcher waits on the GIL: one batch takes 3.6-4.1 s instead of 0.2 s (CPU benchmark). This PR moves the builder and the batcher into their own process (`BatcherActor`): 1.6-1.8 s under the same load.

**Problem**
1. **One GIL.** `_batcher_loop` builds training samples and packs microbatches inside the controller process.
2. **Busy loop.** On large runs, the controller's event loop holds that GIL most of the time, serving rollouts.
3. **Build blocks.** `build_from_group` runs on the event loop, so every rollout waits for it.
4. **Pack waits.** `add_training_samples` runs in `asyncio.to_thread` and, after each torch op, waits up to 5 ms (`sys.getswitchinterval()`) to get the GIL back.
5. **How much.** A batch is thousands of small torch ops: 0.2 s alone, 3.6-4.1 s next to a busy loop.
6. **At scale.** On a 10-node agentic run, the trainer idled 54% of each step: the batcher took 100-180 s per batch vs 80 s of forward/backward.

```text
before (controller process, one GIL)
  event loop thread:  serve rollouts, ..., build_from_group        <- holds the GIL most of the time
  to_thread worker:   add_training_samples                         <- every torch op: release, wait up to 5 ms

after
  controller:         await batcher.add_group.call_one(rollout_group=group)   <- pickle a group, unpickle a batch
  batcher process:    BatcherActor: build_from_group + add_training_samples   (its own GIL)
```

**Solution**
1. **Own GIL.** Build and pack in a separate process, as the router already does ("so routing does not contend with the training loop for the controller's GIL").
2. **`BatcherActor`** (`torchtitan/rl/distributed/actors/batcher.py`) owns the builder and the batcher; `add_group(rollout_group=...)` returns what `add_training_samples` returns.
3. **Wiring.** `setup_async` spawns it on a one-process mesh on the controller host; `_batcher_loop` awaits `add_group`.
4. **Step sync.** The trainer loop sends the step with `broadcast`, so it never waits behind a running `add_group`.
5. **Unchanged:** `Batcher`, `TrainingSampleBuilder`, `TrainerStepBatch`, the batch order and the one-batch queue.

**Results**

CPU benchmark, devserver CPU, torch 2.15 nightly: 8 groups x 8 rollouts x 8 turns -> 1 batch of 32 microbatches. A task on the asyncio loop burns CPU for <load> of every 10 ms. Wall time per batch, main -> this PR:

```text
loop idle        0.22 s    -> 0.35 s
loop 50% busy    0.40 s    -> 0.38 s
loop 90% busy    0.79 s    -> 0.46 s
loop 100% busy   3.6-4.1 s -> 1.6-1.8 s
```

- At 100%, ~1.3 s of what's left is the controller unpickling the returned batch (0.03 s on an idle loop). A TODO in `add_group` covers it.
- On an idle loop the actor costs 0.13 s more per batch, for pickling the groups and the batch.
- Same batch: the unit test checks that the actor's `TrainerStepBatch` equals the in-process one, every tensor exact.

You may ask:
- Why not a `ProcessPoolExecutor`? Its pipe moves the batch in 64 KB reads, each one a GIL handoff: 26 s at 100% load.
- Why not `sys.setswitchinterval(0.0005)`? It cuts the busy-loop time 4x (3.2 s -> 0.75 s), but it's process-wide: the event loop gets preempted 10x more often.
- Why not fewer torch ops in the packer? The cost is still ops x 5 ms, and it grows with the microbatch count.
- Why not move rollout serving out of the controller? It removes the load at its source, but it's a larger change; the batcher should stay off the controller's GIL either way.

NOTE:
- The 10-node run was on a branch whose `TrainingSample`s hold tensors, which packs with many more torch ops: 0.1 s -> 18 s under the same benchmark, vs main's 0.2 s -> 3.6-4.1 s. This PR has not run at scale.
- Sending a group pickles it on the event loop: 0.02 s for 8 rollouts x 8 turns, 0.04-0.07 s for 8 rollouts x 40 turns (each turn stores its full prompt). Main's on-loop build took 0.003 s and 0.02 s for those groups.
- The `training_sample_builder` and `batcher_pack` spans move to a new `rl_batcher` structured log; the controller logs `batcher_add_group` around the call.
- A bad batcher config (e.g. `num_tokens_per_microbatch_per_dp_rank` not a multiple of `max_context_length`) now fails at actor spawn: the run stops as "Interrupted", and the `ValueError` is in the batcher process's traceback.

**Follow up**
- [ ] Return refs the trainer pulls microbatches from, so batch bytes skip the controller (needs trainer ranks to pull their own microbatches).
- [ ] Send only the fields the builder reads, if group pickling shows up in `batcher_add_group`.
- [ ] Move rollout serving out of the controller process.

**Test plan**

- `pytest tests/rl/unit_tests/cpu`: all pass.
- 2 GPUs, Qwen3-0.6B alphabet sort (1 trainer GPU, 1 generator GPU), 5 steps, main vs this PR: both exit 0, reward main 0.52 -> 0.42, this PR 0.51 -> 0.38 (async runs, so rollouts differ). `rl_batcher` has 64 `training_sample_builder` and 64 `batcher_pack` spans, stamped with steps 1-5.
