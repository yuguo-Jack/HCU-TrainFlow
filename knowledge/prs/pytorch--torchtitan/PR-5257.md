# [rl][easy] vLLM priority scheduling: serve rollout groups in the order they started

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5257) · state: open · merged: False

## Original PR description

**TLDR:** vLLM now serves requests in the order their rollout groups started, instead of first-come-first-served: every turn of an older group is admitted first from the queue and preempted last. On main, a multi-turn rollout's next turn waits behind groups that started after it. Not measured yet; our multi-turn runs rarely queue requests, so for them this is headroom.

**Problem**
1. **Many groups.** In async RL, one generator serves many rollout groups at once, started under several policy versions.
2. **FCFS.** The generator hard-codes `scheduling_policy="fcfs"`, so vLLM admits queued requests in arrival order.
3. **Late turns wait.** A multi-turn rollout's next turn is a new request, so it queues behind the first turns of groups that started later.
4. **Repeat victims.** When the KV cache is full, FCFS preempts the request that entered the running set last, so an old request that just resumed is preempted again.
5. **When.** Single-turn math on GB300 kept 150-290 requests waiting per engine all night and had ~730 preemptions per engine-hour while filling up (watermark 0.03). Its arrivals already follow start order closely, so it mostly gains from point 4.
6. **Headroom.** Terminal-Bench and chess had 0 requests waiting in their first waves and at most 35 in chess's refill, so point 3 does not bite them today.

**Solution**
1. **Priority.** Pass each request's priority to vLLM and set `scheduling_policy="priority"`. Lower runs first.
2. **Priority = `group_id`.** Every request already carries it. Training group ids are dataloader indices, so they grow as groups start. Every rollout and turn of a group shares it.
3. **Validation.** Its group ids are negative (-1, -2, ...), so validation goes before training.
4. **Ties.** vLLM breaks ties by `arrival_time`. Rank 0 stamps it in `_decide_next_action` and broadcasts it on `EngineRequest`, so a TP rank whose clock jumps back cannot schedule a different batch.
5. **Unchanged.** `min_policy_version` still salts the prefix cache and measures policy age. No new config field.

```text
one generator, one policy version; requests in arrival order:
  g1 turn 1 (t=0)   g2 turn 1 (t=1)   g3 turn 1 (t=2)   g1 turn 2 (t=3)
priority = group_id: g1 = 1, g2 = 2, g3 = 3

vLLM waiting queue at t=3 (g1 turn 1 has finished), front first
before (fcfs):     g2 turn 1 | g3 turn 1 | g1 turn 2
after (priority):  g1 turn 2 | g2 turn 1 | g3 turn 1

preemption victim  before: the request that entered the running set last
                   after:  the youngest group's latest request
```

You may ask:
- Main says continuous batching requires FCFS. Why is priority safe? FCFS kept every TP rank admitting in the broadcast order. Priority order depends only on `priority` and `arrival_time`, both set by rank 0, so the ranks still agree (ties: see NOTE).
- Does a queued old request now evict running new ones? No. vLLM preempts only when a running request can't grow. Only the victim changes, so preemption counts can move either way.
- Why not the policy version, as this PR first did? Within one version it falls back to arrival order, so an old group's turn 5 still queues behind a new group's turn 1. Start order refines it: groups that started earlier, under older policies, have smaller ids.
- Why does validation go first? Its negative ids give that with no extra code. On main, validation runs only before and after training, so no training request waits behind it. Once validation runs beside training, it would delay training's next batch, and that change can pick validation's priority.
- Why not a config field to keep FCFS? No workload should serve newer groups first. The heap costs ~1.2 us per add + pop with 500 waiting, vs ~0.1 us for FCFS (CPU microbenchmark of vLLM's two request queues).

NOTE:
- **Resumes.** Replayed groups carry the oldest ids, so they now go first, and they are often slow stragglers: the groups in flight longest when the checkpoint was saved.
  - On two Terminal-Bench resumes (FCFS), the oldest 24 groups ended at 8,071 s and 6,622 s. The first batches (24 groups) formed at 1,910 s and 1,968 s, from younger groups.
  - In the first resume, the 94 oldest groups ran a median of 139 turns, against 33 for the other 50.
  - So start order may delay the first batch after a resume whenever vLLM queues or preempts (not measured). Watch the first step after a resume.
- Not measured: no RL A/B (policy age, preemptions, tok/s) and no GPU run.
- `time_to_first_token_ms` now starts at rank 0's stamp, so it also counts the decision broadcast and prompt rendering. On a DP replica on another host, it also includes the clock skew between hosts.
- Equal priority and arrival time fall back to vLLM's internal id: ours plus a random per-rank suffix. TP ranks still agree unless one request id is another plus `-...`, which our ids never are.

### Your question: set `arrival_time` in `generate` (L1283-1289) or in `_decide_next_action` (L1525)?

Both places are correct. `generate` is rank-0-only (`_rank0_check_engine_loop_running`), so either way the timestamp comes from rank 0's clock and is broadcast inside `EngineRequest`. The TP-agreement argument from the PR holds in both. Tie-breaking also comes out the same: `_engine_loop_queue` is FIFO and `_decide_next_action` stamps in drain order, so arrival order matches enqueue order either way. Only two things change:

1. **What `time_to_first_token_ms` measures.** vLLM's `first_token_latency` is counted from `arrival_time`. If you stamp in `generate`, TTFT also includes the time a request waits in the engine-loop queue before admission. That is up to one step burst (`max_engine_steps_between_decisions` steps). It also includes any weight pull that comes first, since a pull is applied before pending requests and they carry over to the next decision (L1509-1514). That is the latency the rollout actually sees. It can also make TTFT jump around pull boundaries. `queue_time_ms` (`scheduled_ts - queued_ts`, from vLLM's own timestamps) is unaffected, so you could still separate engine-loop wait from vLLM queueing.
2. **Code shape.** Stamping in `generate` lets `arrival_time` be an ordinary required init field instead of `field(init=False)` set later. The tests would pass it to the constructor rather than setting it by hand (`test_engine_loop.py:1054`, `test_generator.py:363`). The case for the current spot is that all admission metadata (`min_policy_version` plus `arrival_time`) gets set in one place.

**Recommendation:** I lean slightly toward your suggestion. "Arrival" naturally means when the caller asked. The field becomes a plain constructor argument, and the only downside is a TTFT definition change. If @felipemello1 keeps it in `_decide_next_action`, the code is fine. In that case, the `EngineRequest.arrival_time` docstring should say it's the *admission* time, so TTFT excludes engine-loop queue and pull wait. Either way, the PR's NOTE about the TTFT semantics change should match the final choice.

### Review of the PR

The change is small and correct. The reasoning in the description holds up when checked against the code.

**Verified**
- `add_request` is called in only one place in the loop (L1406), and `priority`/`arrival_time` are passed on every rank. `torchtitan/rl/generate.py:246` is a standalone script that keeps the default policy, so it's unaffected.
- Where `group_id` comes from:
  - Training: `controller.py:998`, the dataloader index.
  - Validation: `controller.py:726`, `-(i + 1)`.
  - Both match the docstring's "validation first" claim.
- Rank 0 stamps every pending request in the STEP branch, before routing (L1517-1525), including requests carried over from a decision that turned into a pull. So no follower can see an unset `arrival_time`. With `slots=True` and `init=False`, an unset value would raise `AttributeError` loudly instead of silently diverging, which is good.
- The new test pins the essential property: priority is `group_id`, not `min_policy_version`. It fails on the earlier version of the PR.

**Minor / worth a look**
1. **Externally chosen priority (verifiers).** In `examples/verifiers/generation_server.py:212`, `group_id` comes from client `sampling_params`, and it now also sets vLLM priority. A client that sends small or negative ids would jump ahead of everything else on that generator. This is probably fine for an example, but a line in that file's docstring that group_id now also controls scheduling would help.
2. **Resume stragglers.** The NOTE already flags that replayed groups go first. Consider logging it, e.g. watching `num_preemptions` and first-step latency on the first resume with this change, before calling it neutral. No code change needed.
3. **Comment wording (L1010-1011):** "Priority = `EngineRequest.group_id`" doesn't say what the priority orders. Something like `# vLLM admits lower priority first and preempts it last; priority = EngineRequest.group_id (see its docstring).` would stand on its own.
4. **Lint.** I couldn't run `pre-commit` here. The new TODO line at L1011 and the docstring lines at L1712 and L1725 look close to the line-length limit, so it's worth a quick `pre-commit run --all-files`.

No blocking issues. Your approval stands from my side; the `arrival_time` placement is a style/metric-semantics call, not a correctness one.
