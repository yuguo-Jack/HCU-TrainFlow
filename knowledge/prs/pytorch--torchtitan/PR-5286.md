# [rl] read each trainer rank's microbatches two ahead of training

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5286) · state: open · merged: False

## Original PR description

**TLDR:** Reads now overlap compute: each trainer rank reads its microbatches two ahead on a background thread, and the engine trains each one as it arrives. On H100 the loss is bitwise equal to the base at DP 1 and DP 2, and reads after a step's first microbatch wait ≤ 1.1 ms per step in total. Stacked on the PR where trainer ranks read their microbatches from Monarch RDMA buffers.

**Problem**
1. **With the previous PR, each rank reads its whole column before compute.**
2. **The reads are exposed:** est. ~0.15% of `forward_backward` at 38 B/token, ~2% at 614 B/token, up to ~25% for a fast trainer with a heavy payload and 16 TCP readers.
3. **The whole column sits in host memory.**
4. **The engine needs every microbatch before the first forward:** `TrainingEngine.forward_backward` preprocesses every group up front, so a stream would be drained before training starts.

**Solution**
1. **Commit 1, `TrainingEngine`:** without a CUDA graph or SDC replay, preprocess each group just before its forward (PP included). The device also holds one group's inputs at a time instead of the whole step.
2. **Commit 2, `MicrobatchStream`:** what `Trainer.forward_backward` now passes as `microbatch_groups`.
   - It reads this rank's column on a thread, two microbatches ahead, running each `async` read with `asyncio.run`; the engine only needs `len()` and one pass.
   - It copies the actor's context into the thread, so Monarch doesn't start a second client.
   - It cancels queued reads on an error, and a `wait_for_microbatch` span records read time training didn't hide.
3. **Unchanged:** the CUDA graph and SDC paths still preprocess up front (they drain the stream first: correct, no overlap).

```text
trainer rank:  read thread  | read 0 | read 1, read 2 | read 3  | ...
               main thread  | wait   | train 0        | train 1 | ...
```

**Results**

GPU, Qwen3-0.6B, H100, batch invariant, lockstep, 10 steps, one TP 1 generator. Measured before the previous PR dropped its by-value option, with the RDMA path on (the same code path as now); "main + commit 1" is upstream main plus this PR's engine commit, without the previous PR:
```text
                                          trainer DP 1 (2 GPUs)          trainer DP 2 (3 GPUs)
loss/mean, vs main + commit 1             bitwise equal at all 10 steps  bitwise equal at all 10 steps
forward_backward, main + commit 1         1.393 s                        0.909 s
forward_backward, previous PR             1.414 s                        0.910 s
forward_backward, this stack              1.399 s                        0.932 s
wait_for_microbatch, first read           2.3-3.1 ms per step            2.8-5.1 ms per step
wait_for_microbatch, later reads          0.4-1.1 ms per step in total   0.2-0.7 ms per step in total, per rank
```
4,096-token microbatches (0.16 MB each): at this size there is little to hide, and the forward_backward rows differ by run-to-run noise (the previous-PR row is a separate run). Prefetch pays with heavier per-token payloads (see NOTE).
With this PR included (the next two PRs' heads), trainer DP 2, 5 steps: `loss/mean` bitwise equal to main's DP 2 at every step, over TCP and over ibverbs.
CPU stress: 1,500 steps x 8 microbatches x 4 ranks of register, read and drop: every field matched, no hang.

You may ask:
- **Does commit 1 change pretraining?** Only eager runs without SDC: `disable_cuda_graphs=True` recipes and ROCm; the CUDA graph paths are unchanged. They now hold one group's inputs on the GPU instead of the step's (an RL step of 46 x 128K tokens: 229 MB -> 5 MB). Pretraining inputs are already pinned, so only varlen's host sync can add time there; Flux, DeepSeek-V3 and ROCm were not measured.
- **Why a Python thread if Rust moves the bytes?** A Monarch `Future` does nothing until someone calls `get()` or awaits it, and the actor's loop thread is busy in forward/backward.
- **Why read two ahead?** While the engine waits on microbatch i, reads i+1 and i+2 are queued, so a rank holds at most 4 microbatches on the host. Not tuned.

NOTE:
- **The lazy path costs ~4 ms per microbatch** (pageable inputs and varlen's host sync; +0.77% at 16K tokens, Qwen3-0.6B, H100). That's about what prefetch hides at 38 B/token; prefetch pays with heavy payloads and fast trainers. In a repro, pinned inputs plus `max_num_documents` removed it; pinned alone did not.
- **Metrics:** `trainer/tokens_per_second` and MFU include each step's first read, which is never hidden. The weight push returns after `forward_backward`, as on main (the previous PR let it finish during the reads).
- **Not tested:** multiple hosts; the RL GPU CI.

**Test plan**
- `pytest tests/rl/unit_tests/cpu tests/unit_tests/cpu/test_trainer.py tests/unit_tests/cpu/components/test_invalid_loss.py` (from the repo root, Monarch 0.7): 487 passed, 5 skipped; the 2 failures (`test_verifiers_terminal_bench.py`, a config mismatch) fail on main too.
- Engine: lazy preprocessing with and without SDC, and the PP path.
- `test_rdma_microbatch.py`: the stream yields in order and reads exactly two ahead (fails for a read-ahead of 0, 1 or 100); the read thread sees the caller's context; closing the stream cancels queued reads.
- GPU parity above.
