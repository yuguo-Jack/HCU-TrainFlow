# [rl] MoE router replay: train on the experts the generator chose

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5255) · state: open · merged: False

## Original PR description

**TLDR:** The trainer can now route each token to the experts the vLLM generator chose (rollout routing replay, R3). On Qwen3-30B-A3B DAPO math, the two routers disagree on 12.8% of (token, layer) top-8 sets. Replaying the generator's choice lowers the trainer-generator k3 KL ~6x and the mean |Δlogp| ~55% (first 3 steps, same config). Off by default; a measure-only mode logs the mismatch.

**Problem**
1. **Same weights, different experts.** The generator (vLLM) and the trainer run the same TorchTitan MoE code, but bf16 noise near the top-k boundary makes their routers pick different experts for some tokens.
2. **How often.** On Qwen3-30B-A3B, 12.8% of (token, layer) top-8 sets differ (1.9% of the chosen experts). The rate rises with depth: 0.1% at layer 0, a peak of 19% at layer 36, 12% at layer 47. It stays at 11-18% on every step of a 98-step run.
3. **Why it matters.** A token sent to a different expert gets a different logprob in the trainer, so the importance ratio `p_trainer / q_generator` moves for reasons unrelated to the policy update.
4. **Cost.** Per token, the k3 KL is 2.8e-4 and the mean |Δlogp| is 0.0074. The worst token per step is off by 2.0 nats on average (9.8 at worst).

**Solution**
1. **Replay the generator's routing.** The generator returns each token's expert ids, and each trainer router uses them instead of its own top-k. The gating weights still come from the trainer's own scores, so the router keeps its gradient.
2. **Generator.** `VLLMGenerator.Config.return_routed_experts`: a forward hook exposes every `TokenChoiceTopKRouter` to vLLM's routed-experts capture. `Completion.routed_expert_ids` is `uint8 [prompt + completion - 1, num_layers, top_k]`.
3. **Transport.** The ids ride like `generator_logprobs`: `RolloutTurn` -> `TrainingSample` -> the batcher's `model_kwargs["routed_expert_ids"]`, packed like `input_ids`.
4. **Trainer.** `Decoder.forward(routed_expert_ids=...)` gives layer `i` its `[:, i]` slice, the MoE shards it like the tokens, and one branch in `TokenChoiceTopKRouter.forward` swaps the ids. `Trainer.Config.replay_routed_experts=False` only measures.
5. **Metrics.** `moe_routing/set_mismatch_frac` (+ per layer), `moe_routing/expert_mismatch_frac`, `bit_wise/kl_k3/mean`, `bit_wise/logprob_diff_abs/mean`, `bit_wise/ratio_beyond_2x/mean`.
6. **Unchanged.** Both flags default to off, and without ids every forward is bitwise identical. All seven MoE families (Qwen3, Qwen3.5, gpt-oss, DeepSeek-V3, DeepSeek-V4, Kimi K2.7, Kimi K3) pass the ids to every router.

```text
vLLM generator                     controller                           trainer
router --hook--> vLLM capture      Completion.routed_expert_ids         model_kwargs["routed_expert_ids"]  [T, L, K]
                 (rows by KV slot)   [P+N-1, L, K] uint8                  Decoder: layer i gets [:, i]
                                     -> RolloutTurn -> TrainingSample     router: topk_ids := replayed ids
                                                                                  weights  := scores.gather(topk_ids)
```

**Results**

Full model. The rows differ only in `replay_routed_experts`; both runs use the same config, seed and prompt order.
```text
Qwen3-30B-A3B (48 layers, top-8 of 128), DAPO math, thinking off, on-policy, lr 1e-6, 8xH100
trainer: DP4 x EP4, bf16, SelectiveAC; generators: four TP1 vLLM engines, FULL CUDA graphs

steps 1-3                 replay off              replay on
k3 KL                     2.4e-4 - 3.2e-4    ->   4e-5 - 5e-5
mean |Δlogp|              0.0071 - 0.0085    ->   0.0030 - 0.0038
max |Δlogp|               1.04 - 1.35        ->   0.21 - 0.93
ratio beyond 2x           2e-5 - 3e-5        ->   0 - 4e-6

replay off, steps 3-98: sets differ 12.8%, k3 2.8e-4, mean |Δlogp| 0.0074, max |Δlogp| 2.0 (worst 9.8)
```

Depth trend, first 8 real layers of the same checkpoint, 5 steps per arm, on-policy:
```text
                          replay off              replay on
sets that differ          4.4% - 5.4%             (replayed)
k3 KL                     3.3e-3 - 4.0e-3    ->   2.3e-4 - 2.6e-4   (~15x lower)
mean |Δlogp|              0.045 - 0.048      ->   0.016 - 0.017     (-65%)
max |Δlogp|               0.65 - 0.98        ->   0.095 - 0.14      (~7x lower)
```

Correctness (1 GPU, Qwen3 debug MoE): replaying the trainer's own routing gives bitwise identical logits and gradients. With replayed random ids, FullAC, SelectiveAC and RegionAC give the same logits and gradients as no AC, bitwise. In all seven MoE families, every router uses the replayed ids.

Memory: vLLM keeps a 0.09 GB host buffer per generator for the ids. Trainer GPUs used ~81 GB (nvidia-smi) with replay on and off.

You may ask:
- Why a forward argument and not router state, like a global replay manager? Activation checkpointing re-runs the forward in backward and must read the same ids. A forward argument is saved with the inputs and sharded by CP like `input_ids`. State is read again later, and any forward in between shifts it silently.
- Why not replay the gate weights too? Then the router would get no gradient.
- Why not replay the trainer's own old-policy routing (R2)? TitanRL takes one optimizer step per batch and uses `generator_logprobs` as the old policy, so there is no earlier trainer forward to record.
- Why vLLM's capture and not our own buffer? vLLM stores rows by KV slot, so a prefix-cache hit returns the cached prompt's rows. Our own buffer would need prefix caching off.
- Why uint8? 384 B per token on Qwen3-30B-A3B (48 layers x 8 ids); int64 would be 3 KB.

NOTE:
- The results above were measured on an earlier main (`e3929368e`). After rebasing onto main `6f2225575`, the CPU tests below pass; the 1-GPU test passed on the previous rebase and was not re-run; the RL runs were not repeated.
- The full-model replay arm ran only 3 steps; the matched 100-step pair and the step-time cost (an arm with the feature off) are not measured yet.
- All runs are on-policy. With stale samples the logprob gap also contains policy drift, which replay cannot remove.
- vLLM's newest capture path needs Model Runner V2, and TitanRL forces V1 today (TODO in `generator.py`).
- Not run end to end: multi-turn RL (unit-tested), trainer TP or CP with replay (TP x EP is unit-tested; CP alignment was checked with a one-off script).

**Test plan**


update by claude: addressed the review in 34c5857e0, after merging main (c455f1c04).

**combine with previous sharding?** Done. `_maybe_shard_routed_branch_inputs_across_tp` now takes and returns the routed expert ids next to the padding mask, and the separate `_maybe_shard_routed_expert_ids_across_tp` is gone (-16 lines in `moe.py`; the Kimi K3 MoE uses the same call).

**docstring example?** Done. The batcher example now shows the row each input token gets: `model_kwargs["routed_expert_ids"] = [e10, e11, e20, e21, 0, 0, 0, 0]`.

**Verifiers rollouter?** Yes, agentic RL goes through it, so it's in this PR now.
- Verifiers already has a routed-experts protocol (the one prime-rl uses): the client sends `routed_experts_prompt_start` on a continued turn, the server returns `routed_experts = {data: base64, shape, start, dtype}`, and Verifiers keeps the rows per trace node.
- `GenerationServer` now returns that field from `Completion.routed_expert_ids`, and `VerifiersRollouter` gives each turn `branch.routed_experts[:end - 1]`, the same contract as the native rollouter. Replay no longer raises there.
- Verifiers DAPO math, Qwen3-30B-A3B cut to its first 2 layers, on-policy, 4 steps: k3 KL 3.3e-4 - 7.5e-4 -> 8e-5 - 9e-5 (~6x), max |Δlogp| 0.45 - 0.92 -> 0.08 - 0.10 (~7x), matching the native rollouter.
- Caveat, from Verifiers itself (prime-rl has it too): on a continued turn, the last token of the previous completion keeps a copy of the row before it, because Verifiers does not overwrite reused nodes with the next prefill's row. So 1 input per turn boundary replays its neighbor's experts (~0.15% of inputs for 30 turns in 20k tokens; none for single-turn tasks). It's a TODO next to the slice.

**stored with the KV cache?** Not inside the KV tensors, but at the same addresses.
- vLLM's scheduler keeps one CPU array with a `[num_layers, top_k]` row per KV slot (`block_id * block_size + offset`). Each step's GPU capture is copied there by the step's slot mapping, and a finished request gathers its rows by its block ids.
- So a prefix-cache hit returns the rows computed with that KV, and evicting a block overwrites both. For Qwen3-30B-A3B it is 0.09 GB of host memory per generator.
- vLLM main has since moved this to a store keyed by KV block hash, which needs Model Runner V2 (the TODO in `generator.py`).

**comm time?** Measured with the real microbatch grid of the 30B run (4 DP ranks x 8 microbatches x 10k tokens), sent to CPU actors the way the controller calls `trainer.forward_backward`, single host:
```text
                              grid per rank   whole grid to every rank   own column only
4 ranks x 8 mb, no ids        12.5 MB         44 - 53 ms                 20 - 22 ms
4 ranks x 8 mb, routed ids    138 MB          315 - 317 ms               75 - 85 ms
8 ranks x 4 mb, routed ids    138 MB          385 - 414 ms               63 - 72 ms
```
- +~270 ms per step at 4 ranks, ~1.5% of that run's 18 s forward_backward. It grows with the number of trainer ranks, since each rank receives the whole grid.
- Sending each rank only its column brings it to ~75 ms. That changes how every batch reaches the trainer (it also halves the no-ids call), so I kept it as the TODO, now with these numbers, for a follow-up PR.

Also from the main merge: FullAC now runs on torch_remat, so the router replay AC test no longer needs the checkpoint-wrapper name fixup; replay stays bitwise identical under FullAC, SelectiveAC and RegionAC.

Tests: `test_moe.py` + RL CPU tests (553 passed), Verifiers tests (15 passed), `test_router_replay.py` on 1 GPU (4 passed), pre-commit clean.
