# [rl] release a routing session when its rollout ends (2/5)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5217) · state: closed · merged: True

## Original PR description

**TLDR:** each `RolloutWorker` rollout now releases its routing session when it ends, so the sticky map holds only live sessions. `max_sessions` (262,144) stays as a guard for sessions nobody releases.

**Problem**
1. `StickySessionRoutingStrategy` pins each rollout's session to one generator, so its turns reuse that generator's prefix KV.
2. Nothing removes a finished session; the map is an LRU capped at `max_sessions` (262,144).
3. Past that many sessions, the LRU evicts live ones. Their next turn lands on another generator and re-prefills its whole context.
4. Real runs stay below the cap: a 35B chess self-play run peaks at 18,432 sessions (1,152 groups x 16). So this PR is prevention, plus the per-rollout release that holding session KV (5/5) needs.

**Solution**
1. Release a session when its rollout ends.
2. `RolloutWorker._run_single_rollout` calls a new `ReleaseSessionFn` after the rollout's last turn. The controller passes it per call, next to `generate_fn`.
3. `InterGeneratorRouter.release_session` calls the new `RoutingStrategy.release_session`; the sticky strategy drops the entry, the others ignore it.
4. `max_sessions` (262,144, ~35 MiB) is the last guard: the per-generator DP router, `VerifiersRollouter` (TODO) and failed releases still rely on it.

**Results**
```
CPU sim on the real router classes, 32 generators, multi-turn; old 4,096-entry LRU -> this PR.
Not rerun against main's 262,144 default, which is above all three sizes.
rollouts in flight   later turns moved       prefix hit
4,080                0.01% -> 0%             0.865 -> 0.865
6,144                8.7%  -> 0%             0.841 -> 0.863
9,216                20.7% -> 0%             0.732 -> 0.805
```

You may ask: why per rollout, when group end would be enough for the sticky map alone? Holding session KV (5/5) frees a session's held KV when its rollout ends, and a multi-turn group lasts as long as its slowest rollout (in chess, a few plies to 120), so finished siblings would keep their KV until then.

NOTE:
- Overrides of `Rollouter.run_group_rollouts`, `RolloutWorker.run_group` and `RolloutWorker._run_single_rollout` must accept `release_session_fn`.
- `VerifiersRollouter` does not release sessions yet (TODO in code); they age out through `max_sessions`, as on main.
- Rewrites `max_sessions`' docstring: main's says finished sessions age out through the LRU, which this PR makes untrue.

**Test plan**
`pytest tests/rl/unit_tests/cpu`: 433 passed, 5 skipped (main: 432 passed; the 2 `test_verifiers_terminal_bench.py` failures are on main too).
New: `test_sticky_session_release_drops_its_assignment`; `test_worker_executes_group_without_actor_mesh` checks one release per rollout.

```python
    generate_fn=generate_fn, release_session_fn=release_session_fn, ...
)
```
