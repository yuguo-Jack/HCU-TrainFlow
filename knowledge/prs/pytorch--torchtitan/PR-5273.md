# [rl] Store each turn's prompt as a delta on the previous turn (linear-size multi-turn rollouts) (1/2)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5273) · state: closed · merged: True

## Original PR description

**TLDR:** each `RolloutTurn` now stores only the prompt tokens that differ from the previous turn, not its full prompt, so a rollout grows linearly with turns instead of quadratically. On a synthetic 120-ply chess group, the token fields pickle to 17 MB instead of 236 MB and unpickle on the controller in 0.11 s instead of 1.83 s. Today's chess runs (~11 plies) unpickle in under 0.12 s per group, so for chess this is headroom; Terminal-Bench rollouts reach ~45 turns at ~95K-token contexts (not measured here). Packed training batches are bitwise identical.

**Problem**
1. **Every turn stores its full prompt.** `RolloutTurn.prompt_token_ids` is the whole conversation so far, so K turns hold sum(prompt_k) tokens: O(K^2).
2. **The group crosses a process boundary.** The rollout worker pickles each finished `RolloutGroup`, and the controller unpickles it on its event loop.
3. **Long games pay quadratically.** A chess player's prompt grows ~1.7k tokens per turn, so a 120-ply group holds 51.7M list entries where 2.7M would do.
4. **Cost:** at 120 plies, 236 MB to pickle and 1.83 s of the controller's event loop to unpickle, per group.

**Solution**
1. **One delta per turn.** `prompt_token_ids` becomes `prompt_prefix_len` + `prompt_delta_token_ids`, where `prompt == previous_turn_tokens[:prompt_prefix_len] + prompt_delta_token_ids`.
2. **`split_prompt(prompt, previous)` fills both** from the longest common prefix, so a rewritten history (e.g. thinking stripped) also stores only what changed. `TokenEnv` calls it, since it builds each prompt (`TokenEnvOutput.next_prompt_prefix_len`), so the rollout loop never handles tokens; the verifiers example calls it too.
3. **The builder rebuilds a new sample's prompt** from the last sample's `token_ids`, and opens samples exactly where it did before.
4. **Unchanged:** what the trainer receives, the generator calls, and `prompt_messages` (still full).

```text
turn  prompt (before: stored in full)   after: stored as (prompt_prefix_len, prompt_delta_token_ids)
0     [P]                               (0, [P])
1     [P, C0, E0]                       (len(P+C0), [E0])
2     [P, C0, E0, C1', E1]              (len(P+C0+E0), [C1', E1])    # thinking stripped from C1
```

**Results**
```
synthetic 16-rollout chess group, 1.1k-token completions, 600-token boards; token fields only; CPU (x86)
                                              before -> after
 60 plies: list entries / pickle / unpickle   13.6M / 63 MB / 0.46 s  ->  1.4M / 8.5 MB / 0.05 s
120 plies: list entries / pickle / unpickle   51.7M / 236 MB / 1.83 s ->  2.7M / 16.9 MB / 0.11 s
packed TrainingMicrobatch, 78 batches x 3 packings, 658 branch samples
(rewrites, resets, every turn rewritten, NaN logprobs):                    bitwise identical
```

You may ask:
- **Why not a message graph** like verifiers v1? Our rollouts are chains, so today it would only share the first prompt across siblings, under 1% of a 120-ply group. A TODO keeps it for turns that fork (subagents, tree search).
- **Why not store the full prompt only on a break?** Renderers that strip past thinking break the prefix every turn, which stays O(K^2). The longest common prefix keeps those linear too.

NOTE:
- With `log_tensors=True`, the recorder writes `prompt_prefix_len` + `prompt_delta_token_ids` instead of `prompt_token_ids`.
- `RolloutTurn.num_prompt_tokens` replaces `len(prompt_token_ids)` in the rollout metrics.
- `build_from_group` drops a rollout whose turn after the first has no completion (e.g. a request aborted before its first token) and counts it in `training_sample_builder/num_rollouts_dropped_empty_completion`. Before, `rollout_to_training_samples` raised and stopped the run.
- A rollouter that builds `RolloutTurn` by hand must call `split_prompt`. Otherwise the builder raises: a full prompt stored as the delta would silently open one sample per turn.

**Test plan**
- `pytest tests/rl/unit_tests/cpu` (verifiers 0.3.1 installed): 443 passed, 5 skipped, 2 failed. Main: 432 passed and the same 2 failed (`test_verifiers_terminal_bench.py` still reads the renamed `train_dataset`).
- New: `test_delta_prompts_rebuild_the_full_prompt_samples` (the real rollout worker and `TokenEnv` on 20 random multi-turn rollouts vs the full-prompt rule), `test_env_returns_each_next_prompt_as_a_delta`, `test_split_prompt`, `test_rewrite_that_keeps_a_prefix_branches_then_continues`, `test_prefix_that_is_not_the_longest_raises`, `test_verifiers_second_branch_stores_its_prompt_as_a_delta_on_the_first`.
- Bitwise check: the same random groups packed on main and on this branch.
- Same data as main, end to end: the real `TokenEnv` + `RolloutWorker` on 618 rollouts (18 edge cases: empty delta, strict prefix down to an empty prompt, retries, resets, env errors, truncation, abort, NaN logprobs, prompt too long) and `VerifiersRollouter.trace_to_rollout_turns` on 4,000 random message trees. Every rebuilt prompt, training sample, rollout metric and packed microbatch tensor is identical to main, with and without the stacked `TrainingSample`-tensor PR. A copy that splits against the prompt without the completion fails the same check.

### Review: delta prompts (1/2)

I found no correctness bugs. The builder and both rollouters agree on what "previous" means: the rollouter uses the previous turn's prompt + completion, and the builder uses `training_samples[-1].token_ids`. Those two are always equal, because every turn that isn't skipped is appended to the last sample. The "longest prefix" check catches a full prompt stored as the delta, and it only reads one token, so it's cheap. A few small points:

1. **`verifiers/rollouter.py:402-405`: element type of `token_ids`.** The old code used `list(token_ids[:absolute_start])`, and `completion_token_ids` still wraps its slice in `list(...)`. If `branch.token_ids` is ever a tuple (verifiers is an external lib), two things happen:
   - `split_prompt`'s fast path (`tuple[:n] == list`) is always `False`, so every turn takes the per-token Python loop.
   - `prompt_delta_token_ids` becomes a tuple, and `prev[:k] + delta` in the builder (`training_sample_builder.py:268-270`) raises `TypeError`.

   I couldn't check the verifiers source in this run. Either confirm it is always a `list`, or keep `list(...)`, e.g. `token_ids = list(branch.token_ids)` once per branch.
2. **`rollouter.py:470`: transient work per turn.** `previous_token_ids = prompt_token_ids + completion.token_ids`, plus the slice in `split_prompt`'s fast path, copy O(context) tokens every turn. Over a rollout that is still O(K^2) CPU work, though not stored memory. That's fine for now; a one-line note would stop someone from "optimizing" it later and thinking storage is still quadratic.
3. **The `split_prompt` contract is only enforced in the builder.** A rollouter that gets it wrong only fails at training-sample build time, away from the cause. That's acceptable. Optionally, add an `assert` (or the same check) in `split_prompt`'s callers' tests rather than at runtime; no change needed.
4. **`rollout_recorder.py:164-165`: format break.** The `log_tensors` JSONL schema changes (`prompt_token_ids` → `prompt_prefix_len` + `prompt_delta_token_ids`). Any offline tooling that reads these dumps will break silently. Consider a tiny `rebuild_prompts(turns)` helper next to `split_prompt` so readers don't each re-implement the replay; it would also make test assertions shorter.
5. **Nit, `types.py:164`.** The fast path also matches when `previous_token_ids == []`, so the first turn returns `(0, prompt[0:])`, which is a full copy. That's correct; just noting it is intentional.

The overall design looks good to me: longest common prefix over break-only, bitwise-identical packing, and the TODO for a graph representation. The rename of `train_dataset` in `test_verifiers_terminal_bench.py` is pre-existing on main and outside this PR.
