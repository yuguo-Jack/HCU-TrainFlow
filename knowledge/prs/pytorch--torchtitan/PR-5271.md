# [rl] RL model defaults in every run: fp32 lm_head, frozen MoE expert bias and router gate

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5271) · state: open · merged: False

## Original PR description

**TLDR:** Every RL recipe now gets fp32 lm_head logits, a frozen MoE router gate, no router aux loss, and a frozen expert bias where the model has one. `build_rl_model_configs` applies them to the trainer and generator model configs. A moving expert bias made the trainer-vs-vLLM logprob gap grow every step: 0.053 -> 0.157 in 30 steps at lr=0. With the bias frozen, the gap stays flat (0.054 -> 0.053).

**Problem**
1. **The bias moves.** An MoE layer with an expert bias moves `expert_bias_E` before each optimizer step. Today that covers:
   - the Kimi K3 recipes (quantile balancing);
   - any checkpoint that ships a bias (DeepSeek-V3, Kimi K2.7).

   Qwen3 MoE had one until the batch-wise aux loss replaced it.
2. **More routing flips each step.** The trainer and vLLM score experts with tiny numeric differences, so tokens near the top-k boundary pick different experts. The moving bias pushes experts onto that boundary: 3.2% -> 9.0% of tokens per layer route differently after 30 steps.
3. **The gap grows.** At lr=0 with bitwise-correct weight sync, the logprob abs mean grows 0.053 -> 0.157.
4. **The aux loss pushes toward uniform load.** 13 of the 16 MoE RL recipes build a batch-wise aux loss (coeff 1e-3). Its gradient reaches the router gate and the hidden states. NeMo-RL turns load balancing off for GRPO: "seq_aux_loss causes logprob error divergence for grpo".
5. **The router gate trains too,** at the policy lr. prime-rl and NeMo-RL freeze it in RL by default.
6. **fp32 logits are opt-in.** Each recipe has to remember `LMHeadFP32OutputConverter`.

**Solution**
1. `build_rl_model_configs`, which every RL recipe calls, applies the RL model changes to both model configs it returns.
2. Two keywords, each an opt-out:
   - `fp32_lm_head`: appends `LMHeadFP32OutputConverter` to `converters`, as the recipes did, so the lm_head becomes `HiMidLoLinear` (fp32 logits).
   - `freeze_moe_routing`: every MoE layer gets three changes:
     - `freeze_expert_bias=True`: the balancing hooks still zero their counts but skip the bias update;
     - `router.freeze_gate=True`: `requires_grad=False` on the gate, and on gpt-oss's gate bias. The Qwen3.5 shared-expert gate still trains;
     - `router.aux_loss=None`.
3. Recipes drop their 14 explicit `LMHeadFP32OutputConverter` lines and 3 wrapper appends. Muse Glimmer passes `fp32_lm_head=False`: its `SoftCappedLinear` can't be converted yet.
4. `LMHeadFP32OutputConverter` changes in two ways:
   - it skips a head that is already `HiMidLoLinear`, keeping its `backward_mode`;
   - it raises a clear `ValueError` on Linear subclasses, e.g. a soft-capped head.
5. Unchanged: pretraining, which doesn't call this function, and the controller, which doesn't touch the model. The new MoE fields default to False.

```text
recipe -> build_rl_model_configs(build_model_config, flavor, trainer_parallelism=..., generator_parallelism=...)
    trainer model config, generator model config, each:
        lm_head: Linear -> HiMidLoLinear              (fp32 logits)
        every MoE layer: freeze_expert_bias=True      (no-op without a bias)
        every router: freeze_gate=True, aux_loss=None
-> Trainer.Config(model=...), VLLMGenerator.Config(model=...)
```

You may ask:
- Why not `load_balance_coeff=None` in the recipes? Main already uses it for most models. But it deletes a checkpoint's bias (DeepSeek-V3, Kimi K2.7), and Kimi K3's quantile balancing keeps its bias anyway.
- Why turn off the batch-wise aux loss in RL? Its gradient still pushes the hidden states toward uniform load with the gate frozen. NeMo-RL also turns load balancing off for GRPO.
- Why in `build_rl_model_configs`, not in the controller at runtime? The printed config is then the run config, and users who build their own model configs aren't rewritten behind their back.
- Why not a separate `ModelConfigTransform`? This function would be its only caller.
- Why freeze the gate when verl, slime and AReaL train it? prime-rl and NeMo-RL freeze it by default, and with no aux loss and a frozen bias, nothing balances a trainable gate. A lower gate lr is the alternative (TODO in the code).

NOTE:
- A checkpoint saved before this PR keeps its drifted bias, now frozen. Start MoE runs fresh.
- A checkpoint saved with frozen routing can't resume with `freeze_moe_routing=False`: there is no optimizer state for the gates. The other direction works.
- A model config built without `build_rl_model_configs` doesn't get these defaults.
- Not run on this commit: GPU tests and an RL run with the gate frozen. The MXFP8 and dist_moe recipes need packages the CPU env lacks, so the recipe test skips those two by name.

- `test_model_defaults.py` has three parts:
  - it builds every RL recipe in the discovered recipe modules and checks both model configs: fp32 head except Muse Glimmer, every MoE layer and router frozen, no aux loss;
  - it runs one AdamW step per MoE family, frozen and not;
  - it checks the DeepSeek-V3 aux-loss removal.
- The recipe test fails if either default is flipped off.
- CI's Verifiers pass now also runs the recipe test, because the first pass skips the two Verifiers recipe modules (`verifiers` isn't installed yet).
