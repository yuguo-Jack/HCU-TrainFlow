# [rl] opt-in repin_load_ratio for sticky routing (4/5)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5219) · state: open · merged: False

## Original PR description

A pinned session never leaves its generator, so a slow generator (straggler node, throttled GPU) keeps all its sessions while the others idle.

```python
StickySessionRoutingStrategy.Config(repin_load_ratio=1.5)
```
A session moves to the fallback's choice once its generator holds more than 1.5x the mean in-flight load; the move re-prefills its context. Default `None` keeps today's behavior.

```
CPU sim on the real router classes, wall time vs sticky routing without the knob, one generator 2x slower:
  multi-turn, 4 generators:              -8.0%   (plain least-loaded: -10.9%)
  long-context agentic, 8 generators:    -4.9%
equal-speed fleets and low load:         -2.7% (agentic) .. +0.1%
```
Re-pins cost prefix hits: on an equal-speed agentic fleet 0.892 -> 0.864 (314 re-pins per run), at low-load multi-turn 0.879 -> 0.840.

You may ask: why not plain least-loaded, which is faster with a slow generator? It drops session affinity on every turn, so turns re-prefill on any fleet; the ratio moves only sessions on an overloaded generator.
You may ask: why one ratio, not `max(ratio * mean, mean + abs)`? The two-knob version was weaker in every sim case (slow multi-turn -5.0%, slow agentic 0%).

The change is small and correct for the case it targets. The main problem is pzhan9's: at low load, the ratio test also fires on very small imbalances. I'd fix that, or at least document it, before switching the knob on by default.

---

### 1. pzhan9's concern: yes, this happens, and the PR's own numbers show it

@tianyu-l asked whether it's likely, given that new sessions already go to `LeastLoaded`. It is. `LeastLoaded` balances sessions when they are placed, but it doesn't balance the in-flight load at the moment of a later turn. Turns finish at different times, so loads drift.

When this session's turn is routed, its previous turn has already released its load (`_release` runs in `finally`). The check is then only "pinned load > ratio * mean", with no absolute floor:

| loads (4 gens), pinned = gen0 | mean | 1.5 * mean | re-pin? |
|---|---|---|---|
| `[1, 0, 0, 0]` | 0.25 | 0.375 | **yes** |
| `[1, 1, 0, 0]` | 0.5 | 0.75 | **yes** |
| `[2, 1, 1, 0]` | 1.0 | 1.5 | **yes** |
| `[6, 2, 2, 2]` (docstring example) | 3 | 4.5 | yes |

When load is light, a single other in-flight request on the pinned generator is enough to move the session. That re-prefills its context even though no generator is close to saturated. The PR description measures exactly this: low-load multi-turn prefix hit rate drops 0.879 -> 0.840 for about 0.1% wall time. With 2+ generators and low concurrency, the knob mostly acts like plain least-loaded.

Two ways to address it:
- **Absolute floor, as pzhan9 suggests:** re-pin only if `load > ratio * mean and load >= min_repin_load`. This differs from the `max(ratio * mean, mean + abs)` variant the PR description rejects. That variant raises the bar at every load level; a floor only turns the check off when the generator is lightly loaded. The floor could reasonably be tied to vLLM `max_num_seqs` (pzhan9's suggestion). One caveat: `reserved_load` counts `estimated_cost` units, not sequences. They're the same today (`estimated_cost=1`, `inter_generator.py:288`), so the doc should say which unit it uses.
- **Keep one knob, but document it:** say in the `repin_load_ratio` docstring that at low absolute load, small imbalances trigger re-pins.

### 2. Default `1.5` instead of `None` (@tianyu-l): I'd keep `None` for now

- **Both routing layers are affected.** `StickySessionRoutingStrategy` is the default strategy for both `InterGeneratorRouter` (`inter_generator.py:81`) and `IntraGeneratorRouter` (`intra_generator.py:52`). Changing the default would also turn re-pinning on across DP ranks inside a generator. The PR's sims only cover the generator layer.
- **The benefit is only shown with a slow generator.** On equal-speed fleets the PR reports -2.7%..+0.1% wall time while prefix hit rate drops (agentic 0.892 -> 0.864, 314 re-pins per run). Turning it on by default would trade prefix-cache hits for little gain, which conflicts with "Protect battle-tested code paths" in CLAUDE.md.
- If a non-`None` default is wanted, I'd add the absolute floor from section 1 first and run sims on the intra-generator layer.

### 3. Validation in `__post_init__` (@tianyu-l): agree, but raise `ValueError`, not `assert`

This is a user-facing config field. CLAUDE.md says to use `ValueError` there, and it matches the existing `max_sessions` check right above. It's also needed for correctness: with `ratio < 1` and equal non-zero loads, `L > r * L` is always true, so every turn re-pins and stickiness is lost entirely.
```python
if self.repin_load_ratio is not None and self.repin_load_ratio <= 1:
    raise ValueError(f"repin_load_ratio must be > 1, got {self.repin_load_ratio}")
```
[Fix this ->](https://claude.ai/code?q=In%20torchtitan%2Frl%2Fdistributed%2Frouting%2Fstrategies.py%20on%20branch%20felipemello1%2Fsession-kv%2F4-repin-load-ratio%2C%20in%20StickySessionRoutingStrategy.Config.__post_init__%20raise%20ValueError%20if%20repin_load_ratio%20is%20not%20None%20and%20%3C%3D%201%2C%20and%20add%20a%20CPU%20unit%20test%20in%20tests%2Frl%2Funit_tests%2Fcpu%2Ftest_inter_generator_router.py&repo=pytorch/torchtitan)

### 4. Smaller points

- **`strategies.py:191`: wasted work.** `mean_load` is computed on every pinned request, even when `repin_load_ratio is None` (the default) and when the pinned candidate isn't in `candidates`. Check membership and `self._repin_load_ratio is not None` first, and compute the mean only after that:
  ```python
  if sticky_candidate is not None and any(h is sticky_candidate for h in candidates):
      if self._repin_load_ratio is None or not self._is_overloaded(sticky_candidate, candidates):
          ...
  ```
  It's O(#candidates), so this is about clarity more than speed.
- **The fallback decides where a session moves.** With `fallback_strategy=RoundRobin`, an overloaded session can land on another busy candidate, or back on the same one. That works as documented ("moves to the fallback's choice"). It may still be worth one line in the docstring saying the knob only makes sense with a load-aware fallback.
- **Interaction with drain mode.** `_route` waits on `pinned.serving` before `choose` (`inter_generator.py:184-186`). A session pinned to a slow generator therefore still waits for that generator's weight sync before it can be re-pinned. That's fine, since all generators drain together under `hot_swap=False`, but it's worth knowing when reading the sim numbers.
- **Tests.** `test_sticky_session_repins_off_an_overloaded_generator` checks the happy path and that the move sticks. Two cheap tests worth adding:
  - with `repin_load_ratio=None` and the same skewed loads, the session stays put;
  - the `ValueError` from section 3.

  A low-load case like `[1, 0]` would also record the behavior from section 1, whichever way it's decided.

### Summary
- Keep the default at `None`, or add an absolute floor before changing it; a default change also affects intra-generator DP routing.
- Add a `> 1` check that raises `ValueError`, not `assert`.
- pzhan9's low-load re-pin issue is real and visible in the PR's prefix-hit numbers. An absolute floor fixes it, and differs from the two-knob variant the PR rejects.
