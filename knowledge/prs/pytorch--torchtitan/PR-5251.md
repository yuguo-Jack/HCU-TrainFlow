# [rl] Fix generator OOM from weight sync spike

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5251) · state: open · merged: False

## Original PR description

## Summary

Today, vLLM sizes its KV cache based on the unsharded model weights and the peak activations. It does not take into account the sharded model weights used during weight sync, leading to OOM for larger models since the KV cache took up too much memory:

| | Memory subtracted from generator KV cache |
|---|---|
| main | unsharded + peak activations |
| Naive fix | unsharded + sharded + peak activations |
| **This PR** | unsharded + max(sharded, peak activations) |
| Actual RL training | unsharded + max(sharded, peak activations) |

In actual RL training, the unsharded params are always resident in memory, the sharded buffers appear only during weight sync, and activations appear only during forward, and the latter two never appear at the same time. This PR simulates this by resharding + unsharding during vLLM memory profiling, so vLLM is aware of the sharded buffers.

An alternative naive fix is to keep both sharded + unsharded buffers in memory during vLLM memory profiling. This fixes the OOM, but is overly pessimistic and leads to smaller KV caches than necessary.

## Test Plan

**Qwen3-30B-A3B** (DP=2, TP=2, EP=4, FSDP=2)
- For this workload, "Naive fix" and "This PR" are both fine because activations are small
- Baseline "main" allocated too much for KV cache and OOM'ed during weight sync due to unexpected sharded buffers

| | Main | Naive fix | This PR |
|---|---|---|---|
| **Model weights + ~1.9 GiB non-PyTorch** | 19.92 | 33.18 | 19.92 |
| **vLLM profiled transient peak** | 0.34 | 0.34 | 14.15 |
| **Subtracted from KV budget** | **20.27** | **33.53** | **34.07** |
| **KV cache memory** (160.52 - subtracted) | 140.25 GiB | 126.99 GiB | 126.44 GiB |
| **Result** | OOM | Runs successfully | Runs successfully |

**Qwen3.6-27B** (DP=1, TP=4, EP=1, FSDP=1)
- `num_prompts_per_train_step=32`
- `num_samples_per_prompt=32`
- `max_num_seqs=4096` (high concurrency)
- For this workload, "Naive fix" uses significantly smaller KV cache than "This PR", which is closer to actual RL training
- Baseline "main" did not OOM; the model is probably not big enough

| | Main | Naive fix | This PR |
|---|---|---|---|
| **Model weights + ~1.9 GiB non-PyTorch** | 14.95 | 27.11 | 14.93 |
| **vLLM profiled transient peak** | 18.09 | 18.09 | 18.09 |
| **Subtracted from KV budget** | **33.04** | **45.20** | **33.02** |
| **KV cache memory** (160.52 - subtracted) | 127.47 GiB | 115.31 GiB | 127.49 GiB |
| **Result** | Runs successfully | Runs successfully | Runs successfully |

- felipemello1 · comment · 2026-10-11T01:27:35Z · [source](https://github.com/pytorch/torchtitan/pull/5251#issuecomment-6104190356)

Message from claude: #5268 fixes the same OOM without shrinking the KV cache: it loads weights one FSDP module at a time, so a sync needs about one module extra instead of a second copy of the model. Reserving that copy at profiling costs a whole model of KV when the generator's FSDP degree is 1 (TP-only or 1-GPU generators). On one H100: Qwen3.5-9B TP1 KV cache 67.81 → 51.44 GiB, and Qwen3.5-35B-A3B TP1 fails to start (OOM in `profile_run`), while #5268 runs it with +1.6 GiB per sync. Only one of the two should land: with #5268, this hook would still reserve the full copy.
