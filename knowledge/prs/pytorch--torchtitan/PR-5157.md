# [moe][perf] Compile local token dispatch and combine as per-token gather-sums

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5157) · state: open · merged: False

## Original PR description

**TLDR:** under the `moe_dispatch_combine` region, MoE dispatch and combine become deterministic fp32 gather-sums: Kimi K3 16k step 219.95 -> 194.23 ms (-11.7%), peak 51.7 -> 40.9 GB.

**Problem**
1. **Dispatch.** Each token is copied into K expert-sorted rows.
2. **Dispatch backward.** aten's sort-based `index_put` accumulates the K row grads in bf16.
3. **Combine.** The `[T*K, D]` expert output is scaled by scores, then scatter-added back with the opaque `deterministic_scatter_add` custom op (bf16 accumulation).
4. **Cost.** At Kimi shapes (K=16, D=3584, T=16k): combine 13.49 ms, dispatch gather 3.50 ms, fwd+bwd.

**Solution**
1. **Every token owns exactly K rows.** So combine and the dispatch backward can each be a per-token gather-sum.
2. **New Functions.** `_GatherTokenRows` and `_CombineTokenRows` sum in fp32, in top-k order: deterministic.
3. **Row order.** Each token's rows come from the inverse of the expert sort (one scatter).
4. **Gate.** Eager keeps the old code behind `torch.compiler.is_compiling()`: the gather-sum is slower in eager.
5. **Unchanged.** One helper serves the Local, AllToAll and TorchAO (EP=1) dispatchers; enabled only in `KimiK3Model.Config`. DeepEP/HybridEP untouched.

```text
before:  y[T*K,D] * score --deterministic_scatter_add (bf16)--> out[T,D]
after:   out[t] = sum_k score[t,k] * y[row(t,k)]   (fp32, top-k order, one fused gather)
         bwd of dispatch and combine: gathers, no accumulation
```

**Results**
```text
Kimi K3 layers 50+51, 16k tokens, fwd+bwd wall, 1x GB300 (shared), on PR 1, median of clean processes
no AC          219.95 -> 194.23 ms  (-11.7%; 8.5% of the 304.6 ms upstream step)
SelectiveAC    257.7  -> 216.8  ms  (one clean process; a screen run gave 216.4)
peak             51.7 ->  40.9 GB

op level, K=16, D=3584, T=16k, bf16, fwd+bwd wall (measured one base earlier, same code)
combine          13.49 -> 1.30 ms  (ideal 0.85)
dispatch gather   3.50 -> 0.92 ms  (ideal 0.58)

correctness vs fp64, Kimi shapes, bf16 (more accurate, not bitwise)
combine output    5.2e-3 -> 1.7e-3
dispatch x grad   5.0e-3 -> 1.7e-3
score grad        7.9e-8 -> 7.7e-8
graphs: _local_reorder, _score_and_scatter_add: 1 per grad mode at fixed T; EP makes row count dynamic (+1 each)
```

You may ask:
- Why not compile combine as written? The scatter custom op stays opaque: 4.3 vs 1.3 ms op level.
- Why not let Inductor differentiate the gather? Its backward is an atomic scatter: nondeterministic, bf16.

NOTE:
- Reaches Kimi K3 now. Any model on Local/AllToAll/TorchAO dispatchers gets it by adding `moe_dispatch_combine` to its regions (DeepSeek-V3, DeepSeek-V4, Qwen3 MoE, Qwen3.5 MoE, GPT-OSS, transformers-backend MoE).
- Numerics change wherever this runs under `torch.compile`, including a user's block compile.
- Not tested: EP>1 at runtime (AllToAll/TorchAO type-checked by CPU EP tests only; combine input may be an AsyncCollectiveTensor), zero-token ranks, `use_deterministic_algorithms(True)` timing, other models' loss curves, H100.
- The DeepSeek-V3 stack carries a variant of this change; land one.

**Test plan**
`pytest tests/unit_tests/gpu/test_moe_dispatch_combine_compile.py` (eager and compiled, fp32 < 1e-5 and bf16 < 1e-2 vs fp64)
Existing `test_moe.py`, `test_expert_parallel.py`, `test_inference_moe.py` pass.
