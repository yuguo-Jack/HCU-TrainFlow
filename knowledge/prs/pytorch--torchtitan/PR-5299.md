# [rl] offload idle session KV to CPU (6/6)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5299) · state: open · merged: False

## Original PR description

**TLDR:** opt-in `VLLMGenerator.Config.kv_offload_gib` turns on vLLM's native CPU KV offload. A multi-turn session whose history was evicted from GPU reloads it instead of recomputing it: 23-26 ms vs 196 ms for an 8k history (Qwen3.5-4B-Base, 1 H100). Ended sessions are evicted first, so a 16 GiB CPU tier keeps a live 32k session that plain LRU loses (40 ms vs 883 ms). Tokens and logprobs are bitwise equal to a run without eviction. Works with TP and DP; DP x TP is untested.

**Problem**
1. A multi-turn rollout re-sends its whole history every turn. vLLM skips recomputing it only while it is still in the GPU prefix cache.
2. Between turns (env step, opponent move, tool call), other requests evict it. `hold_session_kv` (5/5) protects it, but when memory runs short it drops whole idle sessions, which then recompute.
3. Recompute grows with the history: 196 ms of time to first token (TTFT) for 8k tokens, 882 ms for 32k.
4. vLLM's native CPU offload would fix this, but here:
   - it refuses to start under `expandable_segments:True`, which `RL_ENV_DEFAULTS` sets for every RL process;
   - by default it stores prompt blocks only, so the previous turn's completion is never stored;
   - its LRU fills the CPU tier with finished rollouts, which push out live sessions;
   - with more than one GPU per generator it hangs: each rank runs its own vLLM scheduler, and a transfer counts as done only once every worker has finished it, but nothing merges the workers' finished transfers.

**Solution**
1. `kv_offload_gib` sets vLLM's `kv_offloading_size` with `offload_prompt_only=False` and its LRU eviction policy.
2. `train.py` launches generator procs with `expandable_segments:False` (the one allocator option it flips) and `PYTHONHASHSEED=0` when offload is on. Trainers are unchanged.
3. When a rollout ends, the router forwards its `release_session` to the generator it was pinned to whenever offload is on, not only with `hold_session_kv`. Group end (`release_groups`) releases the rest.
4. The ended sessions' CPU chunks are evicted first: `SessionKVHolder.release` moves them to the front of vLLM's LRU. Chunks a live session still uses keep their place: sessions past their first prefill, and requests still waiting for it (GRPO siblings share their prompt).
5. A session the free floor drops from GPU is not evicted first: its CPU copy is what it reloads. Without `hold_session_kv`, the holder only tracks sessions.
6. TP and DP (`_enable_multi_worker_kv_offload`):
   - with TP > 1, every engine step all-gathers the TP ranks' finished transfers before the scheduler reads them, and merges them with vLLM's `KVOutputAggregator`, as vLLM's multiprocess executor does;
   - the TP ranks' schedulers stay identical: request ids get a counter suffix instead of vLLM's random one, and procs share `PYTHONHASHSEED=0` (vLLM iterates sets), checked at init;
   - each step's gather also compares a scheduler fingerprint across ranks and raises if they differ;
   - each scheduler waits for its own TP group only (vLLM's world size also counts DP replicas, which have their own schedulers).
7. Off by default. `reset_kv_cache_on_weight_sync=True` with offload raises: vLLM cannot reset the prefix cache while a request waits on a CPU load (so `batch_invariant`, which needs the reset, does not work with offload).

**Results**
```
Qwen3.5-4B-Base, VLLMGenerator standalone, 1 H100, TP=1, FULL CUDA graphs, greedy.
4 sessions x 8k prompts -> churn of 2x the 124-block GPU pool -> turn 2 (7,920 reusable tokens):
  no eviction              7,920 cached   TTFT  16.4-16.6 ms
  offload off                  0 cached   TTFT 196-197 ms
  offload on (16 GiB)      7,920 cached   TTFT  22.9-25.9 ms
  offload on + hold        7,920 cached   TTFT  24.1-27.6 ms   (the free floor dropped all 4; reloaded from CPU)
  tokens and logprobs bitwise equal to no eviction; churn took 3.05 s with offload off, 3.07 s on

1 live 32k session, offload on, hold off, 16 GiB CPU tier, ~18 GB of churn stored after it,
each churn rollout released through InterGeneratorRouter:
  base branch (plain LRU)                       0 cached   TTFT 882 ms
  this PR, forward_session_releases forced off  0 cached   TTFT 883 ms
  this PR                                  32,736 cached   TTFT  40.5 ms   bitwise equal to no eviction (15.5 ms)

TP=2 (2 H100, 4B, this head), 4 x 8k two-turn with churn:
  hold off                     7,920 cached x4   TTFT 22.4-24.3 ms
  hold on                      7,920 cached x4   TTFT 20.4-22.2 ms
  hold on + pull               7,920 cached x4   TTFT 18.8-21.7 ms   (pull between turns; same weights:
                                                                      load_state_dict patched to a no-op)
  all bitwise equal to TP=2 no eviction; both ranks scheduled the same steps
TP=2 churn loop, 16 sessions x 12 turns, 8 GiB tier:
  Qwen3.5-4B           1,787 steps in sync, 939 CPU hits, the same CPU eviction order on both ranks
  Qwen3-0.6B           4,339 steps in sync (attention-only, 16-token blocks)
  per-step all-gather  +0.5% wall time (prototype: 30.19 vs 30.33 s with offload off, with and without it)
DP=2, Qwen3.5-35B-A3B-Base, EP=2 (vLLM's default all-to-all), CUDA graphs off, this head:
  7,392 cached x4, bitwise equal to DP=2 no eviction; TTFT 1.1-1.2 s vs 2.1-2.5 s recomputed
```
The 8k TP=1 numbers and a 3-step 2-GPU RL run (Qwen3.5-4B-Base, multi-turn alphabet sort: completes, generator proc on `expandable_segments:False`, trainer on `True`) were measured before the review fixes.

You may ask:
- Why merge every step, not once per engine-loop decision? Per decision delays a reload by up to 16 steps (190-260 ms on the 4B), about an 8k recompute; per step costs +0.5%.
- Why a counter suffix on request ids? vLLM reports finished loads by its internal id, whose random suffix differs per rank.
- Why `PYTHONHASHSEED=0`? Without it, the two ranks held the same CPU chunks in a different eviction order, so later evictions could differ.
- Why evict ended sessions first instead of not storing them? Often only the env knows after a turn that it was the last (chess: game over after the move).
- Why not `enable_cumem_allocator=True`? Our worker routes only weights through CuMem, so the KV cache would stay on expandable segments: it would only silence vLLM's check.

NOTE:
- DP x TP (4+ GPUs) is untested. EP was tested only with vLLM's default all-to-all, not DeepEP, whose buffers now live under `expandable_segments:False`.
- `expandable_segments:False` in generator procs may fragment memory for CUDA graph pools and DeepEP buffers; unmeasured. Launchers other than `train.py` must set both env values themselves (vLLM or our init check raises otherwise).
- Uses private vLLM state, pinned to the vLLM we run:
  - `LRUCachePolicy.evictable_chunks` and `connector_scheduler.manager._policy`;
  - the connector's `num_workers` and `_job_counter`;
  - `InputProcessor.assign_request_id`;
  - a wrapped `Scheduler.update_from_output`.
  Rerun the TP=2 two-turn replay after each vLLM bump.
- Weight sync: requests carry a per-version cache salt, so a new-version request can't hit old-version CPU chunks.
- `/dev/shm`: each rank's file is sized for all of a generator's workers (each fills only its own slot); with 2 workers per host keep ~2x `kv_offload_gib` free.
- Gaps: a sibling whose first request has not reached the generator yet does not protect the shared prompt, so those chunks can be evicted first. A chunk whose store finishes after the release keeps its LRU place (TODO).
- Releases rebuild the set of live sessions' block hashes: 0.6 ms for 250 Qwen3.5 sessions of 16k tokens, 23 ms with 16-token hash blocks (attention-only models). TODO: a refcount.
- CPU RAM is ~131 KB per token for Qwen3.5-4B; pinning 16 GiB added at most 5 s to init, 64 GiB 15-25 s (H100 host).
- Not measured: GB300 (reloads go over NVLink-C2C), Qwen3.5-35B-A3B under RL, RL throughput with offload under memory pressure.

**Test plan**
- `pytest tests/rl/unit_tests/cpu`: 467 passed, 5 skipped (base branch: 446 passed; the 2 `test_verifiers_terminal_bench.py` failures happen on both). Each new test fails with its fix reverted.
- New:
  - `test_session_kv_holder.py`: 6 tests on vLLM's real `CPUOffloadingManager`.
  - `test_generator.py`: offload with KV reset raises; negative size; engine args; and 6 tests of `_enable_multi_worker_kv_offload` with a scripted all-gather (a load finishes once every TP rank did, including an empty step that must still gather and leave vLLM's shared output alone; divergence raises; same request ids on every rank; TP=1 only sets the expected count; the `PYTHONHASHSEED` check; a missing `assign_request_id` raises).
  - `test_shutdown.py`: router `forward_session_releases`, launch env.
- `test_engine_loop.py`: its timeout goes 5 s -> 30 s (an upper bound only). A pull's `gc.collect()` takes ~0.7 s in the full suite's heap, and a busy host pushed two pull tests past 5 s once in ~31 full runs.
- GPU: the standalone replays above drive `VLLMGenerator` through `generate()` and the router's `release_session` (scripts not checked in).
