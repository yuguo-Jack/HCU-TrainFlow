# [rl] Extract the generator's engine loop into VLLMEngineLoop

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5190) · state: open · merged: False

## Original PR description

**For reviewers**: the real change is in [e531dc8](https://github.com/pytorch/torchtitan/pull/5190/commits/e531dc82b29d1b9de117d39f7fe1648b17c096b6). The first 3 commits are just adding unit tests and moving code.


**Why:** `VLLMGenerator` runs Monarch endpoints on the actor's event loop and the vLLM engine loop on a dedicated engine thread, sharing one `self`. Which thread may touch which state was only documented in a docstring.

**What:** `VLLMEngineLoop` owns the engine, the dispatcher, the policy version and the loop itself.
- Its methods run on the engine thread, except `start`, `started` and `close`, which control its lifetime from the actor thread.
- `VLLMGenerator` keeps its endpoints. It builds the engine, queue, dispatcher and gloo group at the same points in `__init__` as before, then hands them to the loop.
- The cache-salt pins and the prefetch buffers stay shared with `release_groups` and `prefetch_model_state_dict`, whose bodies are unchanged.

No behavior change.

**Reviewing:** go commit by commit.
- Commits 1–2 add tests.
- Commit 3 is a pure method reorder; `git diff --color-moved=dimmed-zebra` shows it as a block move.
- In commit 4 the loop method bodies are unchanged.

**Test plan:**
- New CPU tests: the endpoint's context reaches `open_result_channel`; `generate` and pull fail before `start_engine_loop`; a second start is a no-op. The RL CPU suite passes.
- Bitwise comparison against `main` (seed 42, batch-invariant):
  - `rl_grpo_0_6b_tp4_batch_invariant`: 0 of 74 metrics differ, including loss and grad_norm.
  - `rl_grpo_moe_debug_tp4_ep4_batch_invariant` (generator DP=2): identical except prefix-cache hit counts, which also vary between two runs of `main`.
- End to end: `rl_grpo_fsdp2_gen_tp2_compile` and `rl_grpo_moe_debug_tp4_ep4` reach step 5.
