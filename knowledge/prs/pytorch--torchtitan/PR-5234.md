# [rl] Name training-loop timings by what they measure (1/2)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5234) · state: open · merged: False

## Original PR description

**TLDR:** On a Qwen3.5-4B RL run (FSDP=4 trainer on H100s), `timing/weight_sync/trainer_push_model_state_dict` read ~150 s while the transfer took ~0.2 s and the training loop waited ~0 s for it. Nothing in the key said it is a start-to-done time that includes queueing. This PR renames the training-loop timings so each key says which kind of time it is. (1/2. The fix for the 150 s push is 2/2.)

**Problem**
1. The training loop times each phase with `MetricsTimer` under `timing/step/*`; the phases make up `timing/step/total`.
2. The weight push and pull run in the background. `WeightSyncManager` reports each one's start-to-done time under `timing/weight_sync/*`.
3. Start-to-done includes time the work sits behind other work: the push's data moves in a thread, but its call returns only after the next forward/backward on the trainer (fixed in 2/2).
4. The background time and the loop's wait for it had near-identical names (`trainer_push_model_state_dict` vs `blocking_trainer_push_model_state_dict`), so 150 s of start-to-done read like a 150 s push.
5. `perf/trainer/step_time_ratio/fwd_bwd` and `perf/trainer/tokens_per_second_fwd_bwd` also counted the optimizer, which includes checkpoint saves.

**Solution**
1. Each key says its kind:
   - `timing/step/<phase>`: the loop's own time in that phase; the phases make up `timing/step/total`.
   - `timing/step/wait_for_<x>`: how long the loop idled on background work x, i.e. the part of x the loop sees.
   - `timing/weight_sync/<x>_wall`: background work x from start to done. It runs beside the step and is not part of it.
2. One ratio per phase: `perf/trainer/step_time_ratio/<phase>` = `timing/step/<phase>` / `timing/step/total`.
3. Values do not change, except the two `fwd_bwd` perf keys, which are split (below).

```text
timing/step/blocking_trainer_push_model_state_dict    -> timing/step/wait_for_push         (loop wait)
timing/step/blocking_generator_pull_model_state_dict  -> timing/step/wait_for_pull         (loop wait: pull + slot release)
timing/weight_sync/trainer_push_model_state_dict      -> timing/weight_sync/push_wall      (background, start to done)
timing/weight_sync/generator_pull_model_state_dict    -> timing/weight_sync/pull_wall      (background, start to done)

perf/trainer/step_time_ratio/batch                    -> perf/trainer/step_time_ratio/wait_for_training_batch
perf/trainer/step_time_ratio/blocking_trainer_*       -> perf/trainer/step_time_ratio/wait_for_push
perf/trainer/step_time_ratio/blocking_generator_*     -> perf/trainer/step_time_ratio/wait_for_pull
perf/trainer/step_time_ratio/fwd_bwd                  -> perf/trainer/step_time_ratio/forward_backward
   (was forward/backward + optimizer)                    + perf/trainer/step_time_ratio/optimizer
perf/trainer/tokens_per_second_fwd_bwd                -> perf/trainer/tokens_per_second_forward_backward
   (was over forward/backward + optimizer)               (over forward/backward only)

trace spans blocking_trainer_push_model_state_dict, blocking_generator_pull_model_state_dict -> wait_for_push, wait_for_pull

unchanged: timing/step/{total, wait_for_training_batch, forward_backward, optimizer},
           perf/trainer/tokens_per_second_full_step, perf/trainer/step_time_ratio/unaccounted
```

You may ask:
- Why `wait_for_`? titan already names the batch wait `timing/step/wait_for_training_batch`.
- Why `push_wall` and not the push's work time? The controller times the `push_model_state_dict` call, so it includes any time the call waits on the trainer. It equals the push's work only when nothing else holds the trainer, which 2/2 makes true.
- Why change the `tokens_per_second` denominator? `optimizer` has its own ratio now, and checkpoint saves made the old number dip on save steps. Tokens over forward/backward + optimizer is no longer logged on the controller; `trainer/tokens_per_second` (trainer side, forward/backward through the optimizer update, no checkpoint save) still covers both.

NOTE: dashboards and scripts that read the old keys need the new names.
NOTE: the 150 s and 0.2 s are from a run on an older main.
NOTE: `timing/step/total` still excludes `sync_log_step` and the metrics log at the top and bottom of each iteration (unchanged).

**Test plan**
- `test_compute_perf_ratio_metrics_reads_flushed_means`: every phase ratio plus `unaccounted`.
- `test_weight_sync.py`: the existing push/pull tests, on the new keys.
- `pytest tests/rl/unit_tests/cpu -q`: 432 passed, 5 skipped, plus the same 2 Terminal-Bench failures as main (no new tests).
