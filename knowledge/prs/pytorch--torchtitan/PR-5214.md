# [transformers_modeling_backend] Initialize rotary inv_freq through HF's _init_weights

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5214) · state: open · merged: False

## Original PR description

Fixes #4783.

HF rotary modules compute `inv_freq` and `original_inv_freq` in `__init__`, so the backend's meta init + `to_empty()` leaves them uninitialized and RoPE silently rotates by garbage. The recompute loop in `init_states()` (from #3772) reads `module.rope_init_fn`, which Transformers 5.x no longer sets, so it has been a no-op since the pin moved to 5.x.

This adds a `RotaryEmbedding` branch to `_init_weights_patched` that delegates to HF's own `PreTrainedModel._init_weights`, captured at import before the backend patches it. HF's branch already handles every `rope_type` and both buffers, so the backend no longer re-derives HF's rope dispatch (the main point of the review on #4817). The dead loop is removed. `attention_scaling` is a float set in `__init__` and survives `to_empty()`, so nothing needs to reset it.

**Test:** `tests/test_rope_init.py` runs the real `Config -> build() on meta -> to_empty() -> init_states()` path for Llama default / llama3 / dynamic and Qwen3 yarn. It fills the rotary buffers with NaN before `init_states()` and compares against the rotary module constructed directly on CPU.
- fails 4/4 on main, passes with this change on transformers 5.9.0 (installed by the backend workflow), 5.10.1 (requirements pin) and 5.14.1
- `pre-commit` passes

The backend's unit tests weren't collected by any CI job (the CPU job ignores `torchtitan/experiments/**`), so this also runs `test_rope_init.py` in the backend's 8-GPU workflow. It's CPU-only and takes seconds.

I didn't run a GPU loss comparison; #3775 has the loss measurements for this failure mode.

Diagnosis by @Jiarwang77 in #4783 / #4817. Drafted with AI assistance (Claude); I reviewed and tested the change.

### Correctness

I traced the path below, and the fix holds up:

1. **Meta build.** `post_init` → `_initialize_weights_patched` (`model.py:899`). The meta-param early return only looks at `module.parameters()`. Rotary modules have no parameters, so they still reach `self._init_weights(module)` → the new branch → `_hf_init_weights`. On meta tensors this copy does nothing, so it is harmless.
2. **`init_states()`** (`model.py:1406`). `self.model.apply(selective_init)` calls the patched `_init_weights` directly. It does not go through `_initialize_weights`, so the `_is_hf_initialized` flag set in step 1 cannot block re-init. The tensors from `to_empty()` are new and carry no per-tensor `_is_hf_initialized` either, so HF's `init.copy_` really writes. ✅
3. **Removed loop.** In 5.x, `rope_init_fn` is no longer an instance attribute. That means `getattr(module, "rope_init_fn", None)` always returned `None` and the loop did nothing. Deleting it is the right call, as opposed to patching it up.
4. **`attention_scaling`.** It is a Python float computed from config in `__init__`, and `to_empty()` doesn't touch it. The same holds for the dynamic-rope state (`max_seq_len_cached`, `original_max_seq_len`). ✅
5. **Branch ordering.** None of the earlier branches (`nn.Embedding`, `*Norm`, `lm_head`, etc.) can match a `*RotaryEmbedding` class, so the new `elif` is reachable. ✅

### Suggestions (non-blocking)

**1. A rotary module could still skip init silently** (`model.py:1089-1094`).
HF's base `_init_weights` rotary branch is guarded by `hasattr(module, "original_inv_freq")`, and as I remember it, `"RotaryEmbedding"` in the class name. Suppose a future or less common architecture has a rotary module without `original_inv_freq`, or with per-layer-type buffers like `{layer_type}_inv_freq`. The delegate call would then do nothing, and we'd be back in the silent-garbage-RoPE state #4783 describes.

This is exactly the "invariant whose failure would otherwise be silent" case in CLAUDE.md. A cheap guard would help, for example:
```python
elif "RotaryEmbedding" in module.__class__.__name__:
    if not hasattr(module, "original_inv_freq"):
        raise ValueError(
            f"{module.__class__.__name__} has no original_inv_freq; HF's _init_weights "
            "will not recompute its inv_freq after meta init."
        )
    _hf_init_weights(self, module)
```
It's optional for Llama-like models today, but it would make the next regression loud.

**2. Capturing `_hf_init_weights` at import** (`model.py:45-47`).
This works because the patch is only applied inside a method, after import. It does depend on module import order, though. If `model.py` were ever reloaded (`importlib.reload`, some test harnesses), `_hf_init_weights` would capture the *patched* function. Rotary init would then recurse without end.

Stashing the original once makes this order-independent:
```python
_hf_init_weights = getattr(PreTrainedModel, "_titan_orig_init_weights", PreTrainedModel._init_weights)
PreTrainedModel._titan_orig_init_weights = _hf_init_weights
```
Very much a nit; feel free to skip.

**3. The test isn't run by CI.**
As you noted, the CPU job ignores `torchtitan/experiments/**`, and the backend workflow only runs the 8-GPU integration tests. The test is self-contained and CPU-only, so it would be worth wiring into the backend workflow. Bot accounts can't edit `.github/workflows`, so this has to come from you or a maintainer. Without that, this regression test won't protect against the next transformers bump.

**4. The transformers version differs between the PR and CI.**
The PR description says the current pin is 5.10.1. `.github/workflows/integration_test_8gpu_transformers_modeling_backend.yaml:87` installs `transformers==5.9.0`. You tested 5.9.0 as well, so there's no functional issue. The description could just be corrected so readers aren't misled.

**5. Numerics.**
Per CLAUDE.md, a computation change needs convergence evidence. This one changes training numerics for every meta-initialized run with the backend (from broken RoPE to correct RoPE). Pointing at #3775 is reasonable. A short before/after loss curve from the Llama 3 debug integration config would still make the PR self-contained.

### Test file

- Pre-filling with NaN before `init_states()` is a good idea: the test can't pass by accident on whatever memory `to_empty()` returned.
- Comparing against `type(rotary)(rotary.config)` built on CPU is a good choice. The expected value is independent of the code path under test.
- The cases cover default, llama3, dynamic (which needs `original_inv_freq`) and yarn. That's good coverage of the `rope_type` dispatch.
- Nit: `deterministic=False` in `load_hf_config` is fine for a CPU buffer check. A one-line comment saying it's irrelevant here would stop readers from wondering.

### Summary

The fix is correct and minimal. It hands rope buffer recomputation to HF instead of re-deriving it, and it deletes dead code. Main asks: optionally add a loud failure for rotary modules HF won't re-init, and get the new test into a CI job.

Thanks for the review. Going through the points:

1. **Raising when a rotary module has no `original_inv_freq`**: I didn't add this, because it breaks Gemma4. `Gemma4PreTrainedModel._init_weights` calls `super()._init_weights(module)` (the patched one) for every module before initializing its own per-layer-type `{layer_type}_inv_freq` buffers, so the guard fires on `Gemma4TextRotaryEmbedding`. Building a tiny Gemma4 through the backend with the guard fails with `ValueError: Gemma4TextRotaryEmbedding has no original_inv_freq`; with this PR, all four Gemma4 rotary buffers match a CPU-constructed module. In 5.10.1 the other rotary classes without `original_inv_freq` are vision/audio encoders the backend doesn't build.
2. **Import-time capture**: `_patch_hf_llama_like` only runs after import and nothing reloads `model.py`, so I kept the simple version rather than storing state on `PreTrainedModel`.
3. Added `test_rope_init.py` to the backend's 8-GPU workflow (CPU-only, takes seconds).
4. Fixed the description: requirements pin is 5.10.1, the workflow installs 5.9.0; the test passes on both (and 5.14.1).
5. **Numerics**: built a tiny Llama (llama3 rope) through `init_states()`, loaded the same weights into a normally constructed `LlamaForCausalLM`, and compared on the same batch. Logits are bit-identical with this PR (max diff 0); on main they differ (max diff 5.6e-4 at init, since an untrained model's attention is near-uniform). The training impact is the loss gap measured in #3775.

### New observations (all non-blocking)

1. **The Gemma4 case isn't tested.** The reason for not adding the guard (Gemma4's per-layer-type buffers get initialized correctly through `super()` -> patched -> HF base no-op -> Gemma4's own init) is only verified by hand. It is the same kind of silent no-op, though. With CPU offload, the trainer passes `buffer_device=cuda`, but the rotary buffers stay on whatever device `to_empty()` used. I'd leave it out of this PR and open a separate issue or add a TODO.
