# [rl] Build and pack training batches in their own process

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5291) · state: open · merged: False

## Original PR description

**TLDR:** On a busy controller the batcher waits on the GIL: one batch takes 3.7-5.4 s instead of 0.2 s (CPU benchmark). This PR moves the builder and the batcher into their own process (`BatcherActor`). Under the same load a batch takes 2.0-4.5 s returned by value (the default), and 0.61-0.70 s with the RDMA fast path on: the batcher then registers each batch as `RDMAMicrobatch`es and returns only those, trainer ranks read from its process, and the controller never touches the batch's bytes. Stacked on the trainer-pull PRs.

**Problem**
1. **One GIL.** `_batcher_loop` builds training samples and packs microbatches inside the controller process.
2. **Busy loop.** On large runs, the controller's event loop holds that GIL most of the time, serving rollouts.
3. **Build blocks.** `build_from_group` runs on the event loop, so every rollout waits for it.
4. **Pack waits.** `add_training_samples` runs in `asyncio.to_thread` and, after each torch op, waits up to 5 ms (`sys.getswitchinterval()`) to get the GIL back.
5. **How much.** A batch is thousands of small torch ops: 0.2 s alone, 3.7-5.4 s next to a busy loop.
6. **At scale.** On a 10-node agentic run, the trainer idled 54% of each step: the batcher took 100-180 s per batch vs 80 s of forward/backward.

```text
before (controller process, one GIL)
  event loop thread:  serve rollouts, ..., build_from_group        <- holds the GIL most of the time
  to_thread worker:   add_training_samples, then register (fast path) <- every torch op: release, wait up to 5 ms
```

**Solution**
1. **Own GIL.** Build and pack in a separate process, as the router already does.
2. **`BatcherActor`** (`torchtitan/rl/distributed/monarch_actors/batcher.py`) owns the builder and the batcher. `add_group(rollout_group=...)` returns a finished batch by value, or, with `rdma_fast_path_threshold` set, registers its microbatches as `RDMAMicrobatch`es, keeps the tensors, and returns those.
3. **Release (fast path).** After `forward_backward` (in a `finally`, so a failed step frees its batch too), the trainer loop calls `batcher.release_oldest_batch.broadcast()`, which drops the oldest batch's buffers. Not awaited, so it never waits behind an in-flight `add_group` (awaited, it waited p50 255 ms behind a pack); batches train in order through the one-batch queue.
4. **The controller no longer registers or drops** (removed from the trainer-pull PR's controller block).
5. **Wiring.** `setup_async` spawns the actor on a one-process mesh on the controller host; the step reaches it with `broadcast`, like the release.
6. **Unchanged:** `Batcher`, `TrainingSampleBuilder`, the batch order, the one-batch queue, and the trainer side (with the fast path it reads as before, now from the batcher's process).

```text
after (fast path on)
  controller:       await batcher.add_group.call_one(rollout_group=group)          <- pickle a group, unpickle RDMAMicrobatches
                    await trainer.forward_backward.call(packed.microbatches, ...)   <- RDMAMicrobatches
                    batcher.release_oldest_batch.broadcast()
  batcher process:  build_from_group + add_training_samples + register buffers (its own GIL; owns the tensors)
  trainer ranks:    read their columns from the batcher process over RDMA
```

**Results**

CPU benchmark, devserver CPU, torch 2.15 nightly, torchmonarch 0.6.0: 8 groups x 8 rollouts x 8 turns -> 1 batch of 32 microbatches, dp 4. A task on the controller's event loop burns CPU for <load> of every 10 ms. Wall time per batch:
```text
                 main (in the controller)   this PR, by value (default)   this PR, fast path
loop idle        0.23-0.25 s                not measured                  0.35-0.36 s
loop 50% busy    0.39-0.41 s                not measured                  0.36-0.45 s
loop 100% busy   3.7-5.4 s                  2.0-4.5 s                     0.61-0.70 s
```

- **Same batch:** the unit test spawns the actor with and without the fast path; both return the in-process builder + batcher's batches, every tensor exact (with the fast path, read from the test process as a trainer rank would).
- **On an idle loop** the fast path costs ~0.1 s more per batch, for pickling the groups and registering buffers.

You may ask:
- **Why not always return `RDMAMicrobatch`es?** The fast path is opt-in (previous PR). By value, the reply is the whole `[num_microbatches][dp_degree]` grid (~1.1 GB for a 29M-token step at 38 B/token, 9-18 GB with router replay and top-k logprobs), unpickled on the controller's busy loop: still faster than main at 100% load (2.0-4.5 s vs 3.7-5.4 s), but turn the fast path on for heavy payloads.
- **Why not a `ProcessPoolExecutor`?** Its pipe moves the batch in 64 KB reads, each one a GIL handoff: 26 s at 100% load.
- **Why `async` endpoints?** Monarch rejects an actor that mixes sync and async endpoints, and the release awaits the buffer drops. They stay plain `@endpoint`, so groups are processed one at a time, in arrival order.
- **Why FIFO release, not keyed by step?** The batcher doesn't know a batch's step when it packs it, and batches train in order. A lost broadcast only holds one extra batch; it never frees an unread one.
- **Why not `sys.setswitchinterval(0.0005)`?** It cuts the busy-loop time 4x (3.2 s -> 0.75 s), but it's process-wide: the event loop gets preempted 10x more often.
- **Why not fewer torch ops in the packer?** The cost is still ops x 5 ms, and it grows with the microbatch count.
- **Why not move rollout serving out of the controller?** It removes the load at its source, but it's a larger change; the batcher should stay off the controller's GIL either way.

NOTE:
- **The input side remains.** Sending a group pickles it on the event loop: 0.02 s for 8 rollouts x 8 turns, 0.04-0.07 s for 8 rollouts x 40 turns (each turn stores its full prompt). Main's on-loop build took 0.003 s and 0.02 s for those groups; router replay and top-k add per-token data.
- **Memory (fast path):** the batcher holds the batch being trained, the queued one, and one more if `_batcher_loop` is blocked on the queue: up to 3 at peak (~53 GB at 17.8 GB per batch with router replay), plus transient copies on the TCP fallback; the controller holds none. A released batch's memory goes back by the batcher's next call. By value, the controller holds the batch, as on main.
- **CUDA context:** the context that silences Monarch's per-buffer log moves from the controller into the batcher process, which now registers the buffers (~256 MiB on GPU 0, 0 `[RdmaXcel]` lines in the GPU run vs 152 before).
- **Needs Monarch ≥ 0.7:** its drop lock is reentrant, so the batcher keeps only the `RDMAMicrobatch`es. On 0.6 the fast path hangs within its first few steps.
- **Fast-path reads don't slow down while the batcher works** (CPU probe, 4 readers, 81.7 MB microbatches): 115 ms per microbatch idle vs 105-117 ms while the batcher spins, packs or registers. The owner side of a read needs neither its GIL nor its actor loop.
- **Spans:** `training_sample_builder` and `batcher_pack` move to a new `rl_batcher` structured log; the controller logs `batcher_add_group` around the call.
- **Config errors** (e.g. `num_tokens_per_microbatch_per_dp_rank` not a multiple of `max_context_length`) now fail at actor spawn, with the `ValueError` in the batcher process's traceback.
- **The 10-node run** was on a branch whose `TrainingSample`s hold tensors, which packs with many more torch ops: 0.1 s -> 18 s under the same benchmark, vs main's 0.2 s -> 3.6-4.1 s. This PR has not run at scale.
- **Not tested:** multiple hosts, the RL GPU CI.

Follow up:
- [ ] Send only the fields the builder reads, or let rollouts reach the batcher directly, if group pickling shows up in `batcher_add_group`.

**Test plan**
- `pytest tests/rl/unit_tests/cpu` (from the repo root, Monarch 0.7): 439 passed, 5 skipped; the 2 failures (`test_verifiers_terminal_bench.py`, a config mismatch) fail on main too.
- `tests/rl/unit_tests/cpu/test_batcher_actor.py`: spawns `BatcherActor` in its own process, with and without the fast path. 5 groups (one untrainable) make batches A and B; after releasing A, B still reads back to the in-process batch, every tensor exact (256-token microbatches: the int64 fields cross by ref, the token counts by value). By value, both batches match too. A builder error surfaces at `call_one`.
- GPU, Qwen3-0.6B, H100, trainer DP 1 (2 GPUs), Monarch 0.7, 5 steps through the batcher process: `loss/mean` bitwise equal with the fast path on (threshold 1024) and off, and equal to the earlier PR's by-value run.
