# [gpt_oss][perf] Add expert biases with a gather and a one-hot GEMM backward

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5192) · state: open · merged: False

## Original PR description

**Depends on:** nothing; these 2 PRs apply to main on their own. The shared MoE PRs add more for GPT-OSS: #5160 dispatch/combine -20%, #5163 router -1% (single-process runs, indicative), #5162 EP permutes -1.0 ms per MoE layer at EP2 (op level), #5164 int16 keys ~0. Turning them on in `GptOssModel.Config` is a one-line follow-up after they land.

**TLDR:** GPT-OSS's per-expert bias backward becomes one fp32 GEMM instead of a bf16 scatter-add: 16k step -9.7%, deterministic.

**Problem**
1. **Bias per expert.** Each GPT-OSS expert projection (w13, w2) adds its expert's bias to every routed row.
2. **Expanded in eager.** `repeat_interleave` copies the bias out to all R rows, then adds it.
3. **Scatter in backward.** Autograd sums the R row grads back into the bias with a bf16 scatter-add.
4. **Cost.** The scatter alone is 2.65 ms per 2 layers at 16k tokens.

**Solution**
1. **Gather, don't expand.** Each row reads its expert's bias by index (`add_grouped_bias`).
2. **Bias grad as a GEMM.** `one_hot[E+1, R] @ grad[R, O]`, accumulated in fp32: deterministic.
3. **Single path.** The new form is faster in eager too, so no gate.
4. **Region.** `grouped_expert_bias` fuses gather + add, enabled in `GptOssModel.Config`.
5. **Unchanged:** expert weights, routing and the dispatcher.

Region options:
- width marked static (w13 and w2 differ): one kernel per width instead of a symbolic one.
- `recompile_limit=16`: 6 graphs (2 widths x static/dynamic rows x grad mode).

```text
before:  bias[E,O] --repeat_interleave--> [R,O] --add-->   bwd: bf16 scatter_add over R rows
after:   bias[E,O] --gather(expert_id)--> add   (region)   bwd: one_hot[E+1,R] @ grad  (fp32)
```

**Results**
```text
one projection, 16 experts, R = 4T, fwd+bwd kernel time, GB300   (ideal = min bytes / bandwidth)
T=16k O=5760   1593 -> 615 us   (new form in eager 868, ideal ~319)
T=16k O=2880    947 -> 305 us   (ideal ~160)
T=4k  O=5760    313 -> 161 us
T=4k  O=2880    173 ->  85 us

GPT-OSS 20b layers 0-1, 16k tokens, fwd+bwd wall, GB300
1 process, on top of #5160's MoE dispatch/combine (indicative)
step   28.46 -> 25.70 ms  (-9.7%)
correctness: fp64 CPU test vs the repeat_interleave reference (fwd, input grad, bias grad,
             incl. an empty expert and padding rows), eager and compiled
graphs: grouped_expert_bias 6 (2 widths x static/dynamic rows x grad mode), limit 16
```

You may ask: why not let per-block compile handle it? Its scatter uses atomics: nondeterministic.
NOTE: not yet measured under CUDA graphs. Not tested: EP>1 with padded rows from TorchAO (only the padding-row test covers it), loss curve.

Rejected:
- gathering the bias with autograd's own backward: an `index_put`, slower
- QKVLinear's contiguous q/k copies before `cos_sin_rope`: ~0.35 ms (~1.4%); shared code kept as is for vLLM
- folding the w13 bias into `fused_binary_activation`: ~2%; needs an interface change in shared MoE code

Compile limits hit:
- Inductor lowers the gathered bias's backward to an atomic scatter-add: nondeterministic, so the bias grad is a one-hot GEMM instead (PR 1).

Left (out of scope): the sliding-window layer runs cuDNN attention (bwd 2.2 + fwd 0.7 ms at 16k) while the full layer runs FA4 (0.65 + 0.22 ms): ~2.1 ms (~9% of the step), a backend choice, not a region.

Not tested: TP=2 (the recipe's TP), multi-GPU EP, the vLLM generator path, GraphTrainer, CUDA graphs, flex backend, 120b, loss curves.

Stack: 1 of 2. Branch `felipemello1/lcp/gptoss-1-grouped-expert-bias`.
