# Resolve commits before checkout in loss_compare and checkpoint_compat_test

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5288) · state: closed · merged: True

## Original PR description

scripts/loss_compare.py and scripts/checkpoint_compat_test.py both check out the baseline commit before they look at the test commit. So anything that depends on the current checkout, like `.` or a relative ref such as `HEAD~1`, gets read after HEAD has already moved to the baseline.

In practice `loss_compare.py HEAD~1 HEAD` (or `main .`) trains the baseline code twice, the losses match exactly and `--assert-equal` passes without ever running the change. Same thing in checkpoint_compat_test.py, where the docstring's own example `HEAD~1 . --assert-equal` runs the resume step at HEAD~1, so loading an old checkpoint with the new code never actually gets tested.

The fix resolves both commits to SHAs up front, before the first checkout. When both sides are `.` nothing changes (no checkout, same as before, which is what CI uses). Uncommitted changes aren't affected either, since both scripts already refuse to switch commits with a dirty tree.

Added tests/unit_tests/cpu/scripts/test_loss_compare.py and test_checkpoint_compat_test.py. They build a small two-commit git repo in a temp dir, stub out the training run, and check which commit each step ran at. All 4 fail on main and pass with the fix, along with the other script tests. ufmt and flake8 are clean.

**Overall: LGTM.** The bug is real and the fix addresses its cause.

**The bug, as I read it**
- `loss_compare.py`: on main, `run_scenario` passes `args.test_commit` straight to `git checkout` *after* the baseline checkout has moved HEAD. That means `HEAD`, `HEAD~1`, `.` and similar refs are read against the wrong commit. `HEAD~1 HEAD` checks out HEAD~1 twice, and `old .` runs the test scenario at `old`. Both make `--assert-equal` pass without testing anything.
- `checkpoint_compat_test.py`: main already resolved real refs up front, but `"."` stayed as `"."` and `checkout(".")` does nothing. So with `HEAD~1 .` (the docstring example on line 26), Step 3 resumes at HEAD~1. That defeats the purpose of the script. Resolving `.` to the original HEAD SHA whenever the other side needs a checkout is the right fix.

**What I checked**
- When both sides are `.`, nothing changes. `needs_checkout` / `needs_git_checkout` are computed from the raw args and resolution happens only inside that branch. The CI path is untouched.
- Restoring the original state still works. The original branch name is captured from the raw HEAD before any checkout, and the `finally` block restores it even though the runs now use detached SHAs. Your tests assert that `main` is restored.
- A bad ref fails in `rev-parse` before the `try`, so no checkout has happened yet and there's nothing to restore. That's fine.
- The dirty-tree check still runs before any checkout, so resolving `.` to HEAD can't silently drop uncommitted changes.

**Nits (none blocking)**
1. **Bad refs give a less useful error in `loss_compare.py`.** `resolve_commit` uses `capture_output=True, check=True`. A typo'd ref now produces a bare `CalledProcessError` with git's stderr swallowed. Before, `git checkout` printed `pathspec 'foo' did not match`. Printing `result.stderr`, or exiting with a short message naming the arg, would keep the error readable. `checkpoint_compat_test.git_run` probably behaves the same way, so the same applies there.
2. **`resolve_commit` is now defined in both scripts.** Both already import from `scripts/_checkpoint_test_config.py`. That module name is about config, so moving it there is optional, but a single shared helper would follow the repo's reuse-over-duplication rule. Keeping two 5-line helpers is also defensible for standalone scripts.
3. **Shared test setup.** The two test files build the same two-commit temp repo in `setUp`. You could move that into a small shared helper in `tests/unit_tests/cpu/scripts/`. Optional.
4. **Pre-existing, out of scope.** In `loss_compare.py`, `create_seed_checkpoint` still runs at the original checkout, not at the baseline commit. That's probably intended (both scenarios share one seed), but if it isn't, a docstring note would help.

**Tests:** They exercise the real git checkout path and stub only the training and metric extraction, which is the right boundary. They also cover both the relative-ref (`HEAD~1 HEAD`) and the `.` cases for each script. Before merging, please confirm they pass in CI (`tests/unit_tests/cpu/scripts`), since I couldn't run them myself.
