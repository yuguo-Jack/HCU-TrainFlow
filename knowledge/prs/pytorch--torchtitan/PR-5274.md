# [rl] RolloutTurn and TrainingSample per-token fields as numpy arrays (2/2)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5274) · state: closed · merged: True

## Original PR description

**TLDR:** `RolloutTurn`'s and `TrainingSample`'s per-token fields become numpy arrays instead of Python lists. A chess group crosses Monarch from the rollout worker to the controller in 0.05 s instead of 0.33 s, the GC stops walking every token, building a group's samples takes 0.01 s instead of 0.21 s, and packing a batch takes 0.28 s instead of 6.88 s (16 synthetic 60-ply chess groups). Packed training batches are bitwise identical. Stacked on the delta-prompt PR.

**Problem**
1. **`RolloutTurn` and `TrainingSample` keep their per-token fields as Python lists:** `prompt_delta_token_ids`, `completion_token_ids` and `completion_logprobs`, then `token_ids`, `loss_mask`, `logprobs` and `advantage`.
2. **Every finished group crosses a process:** Monarch pickles it from the rollout worker to the controller, one Python int at a time.
3. **The controller holds them:** the batcher keeps a whole batch of samples until the last group arrives, and every full GC walks every entry. In a 35B chess self-play run, the controller's full GCs grew from 1.25 to 2.7 s per step as games grew from 8.5 to 11.3 plies.
4. **The pack converts all those lists** with `torch.tensor(list)` when the last group arrives, on the trainer's critical path.

**Solution**
1. **`RolloutTurn`: numpy** (`int32` tokens, `float32` logprobs). `split_prompt` and `TokenEnvOutput.next_prompt_delta_token_ids` return arrays; `RolloutWorker` and the Verifiers rollouter store completions with `np.asarray`.
2. **`TrainingSample`: numpy in the batcher's packed dtypes** (`int64`, `bool`, `float32`, `float32`).
3. **`rollout_to_training_samples` keeps its loop:** a private `_SampleInProgress` collects the turns' arrays and concatenates them once per field. A sample is finished when the next one opens.
4. **The pack concatenates each field once into its packed dtype** (`np.concatenate(..., dtype=...)`) and wraps it with `torch.from_numpy`, which shares the memory.
5. **The controller runs `build_from_group` in `asyncio.to_thread`,** like `add_training_samples` already is.
6. **Unchanged:** `TrainingMicrobatch`, the trainer, and the builder's filters and metrics.

**Results**
```
CPU, real RolloutTurn / TrainingSampleBuilder / Batcher, groups built as the default Rollouter builds them.
One group: 16 rollouts x 60 turns (120-ply chess)          before (lists)   after (numpy)
  pickle                                                     17.3 MB          11.3 MB
  Monarch flatten + unflatten                                0.33 s           0.05 s
  full GC added by 4 held groups                             +50 ms           +1 ms
  build_from_group                                           0.21 s           0.01 s
Terminal-Bench-shaped group (16 x 45 turns, ~94K context): pickle 13.1 -> 9.0 MB, Monarch 0.25 -> 0.03 s, build 0.20 -> 0.01 s

16 groups, main (lists everywhere) -> this PR                main             this PR
  60 plies: pack (the call that completes the batch)         6.88 s           0.28 s
  20 plies: pack                                             2.80 s           0.16 s
  60 plies: full-GC time added by 15 held groups of samples  0.081 s          ~0
  60 plies: build per group (now in a thread)                0.091 s          0.010 s
packed TrainingMicrobatch, 78 batches x 3 packings, 658 branch samples:        bitwise identical
```

You may ask:
- **Why numpy and not torch tensors?** Both stop the GC walk. But Monarch pickles each torch storage separately with `torch.save`, which is slow for the thousands of small per-turn arrays in a group. Numpy pickles as raw bytes. With host data in numpy, the only conversion to torch is the batcher's pack.
- **Why int32 tokens in `RolloutTurn`?** It halves the bytes crossing Monarch (vocabularies fit in 31 bits). The builder concatenates into `int64`, which is what the trainer uses.
- **Why not `gc.freeze()` per step?** It bounds the pauses, but it leaks any reference cycle that existed before the freeze, and it leaves the Monarch and pack costs.

NOTE:
- Code that builds `RolloutTurn` or `TrainingSample` by hand (custom rollouters, `rollout_to_training_samples` overrides) must pass numpy arrays. The repo has none outside the builders, the rollouters and the tests.
- `np.concatenate(dtype=...)` in the pack casts float64 logprobs to float32 (where `torch.cat` would promote the batch to float64), and raises on int or float to bool.
- `log_logprobs` writes float32 values: `-0.1` is written as `-0.10000000149011612`.

**Test plan**
- `pytest tests/rl/unit_tests/cpu` (verifiers 0.3.1 installed): 444 passed, 5 skipped. The same 2 `test_verifiers_terminal_bench.py` failures as main (they still read the renamed `train_dataset`).
- Same data as main, end to end: the real `TokenEnv` + `RolloutWorker` on 618 rollouts (18 edge cases) and `VerifiersRollouter.trace_to_rollout_turns` on 4,000 random message trees. Every rebuilt prompt, turn, training sample, rollout metric and packed microbatch tensor (with dtypes) is identical to main. Turns match the generator's inputs and outputs, and every packed segment matches its sample.
- Bitwise check: the same random groups packed on main and on this branch.

### Name for `_OpenSample` -> `_TrainingSampleInProgress`

It names the type it turns into (`TrainingSample`), and "in progress" says the sample is still being built while turns are appended. That is the "sample under construction / sample being built" meaning you asked for. The type's docstring also says who builds it now:

```diff
 @dataclass(kw_only=True, slots=True)
-class _OpenSample:
-    """A training_sample while turns are appended to it: per-token Python lists (cheap appends),
-    converted to tensors once by `to_training_sample`."""
+class _TrainingSampleInProgress:
+    """A training_sample still being built by `rollout_to_training_samples`, while turns are appended
+    to it: per-token Python lists (cheap appends), converted to tensors once by `to_training_sample`."""
@@
-        training_samples: list[_OpenSample] = []
+        training_samples: list[_TrainingSampleInProgress] = []
@@
-                    _OpenSample(
+                    _TrainingSampleInProgress(
```

Other names I considered: `_PartialTrainingSample` (could read as "a truncated sample") and `_TrainingSampleDraft`. `_SampleUnderConstruction` also works, but it drops the "Training" link to the output type.

### Review

Overall this looks correct and well scoped. I found no blocking issues. Notes, most important first:

**1. The dtype contract is only stated in comments (`types.py:96-103`, `batcher.py:667-702`).**
After 3fbb763 dropped the cast, `_pack_training_samples` sends each sample's tensor straight into `torch.cat` next to pads built with `_DTYPES[key]`. `torch.cat` promotes types instead of failing. So if a `rollout_to_training_samples` override returns float64 `logprobs` or int32 `token_ids`, the packed `TrainingMicrobatch` silently changes dtype: float64 `generator_logprobs`/`advantages` reach the loss. The old `torch.tensor(..., dtype=_DTYPES[key])` made that impossible. The PR says no such override exists in the repo, and this is the documented extension point, so a hard assert would be speculative. But the contract is easy to break silently. A cheap way to make it explicit: have `rollout_to_training_samples`'s docstring say "must return tensors in `long`/`bool`/`float32`/`float32`". Or check the dtype once in `build_from_group`, which is the user-overridable boundary, rather than in the pack.

**2. Empty pad tensors per sample (`batcher.py:689`).**
Without `per_sample_pad_multiple` (the default), `pad(key, 0)` still allocates five 0-length tensors per sample and doubles the `torch.cat` inputs. It's cheap next to the old cost, but guarding it is trivial:
```python
for key in keys:
    packed_fields[key].append(sample[key])
    if sample_len > unpadded_len:
        packed_fields[key].append(pad(key, sample_len - unpadded_len))
```

**3. `asyncio.to_thread(build_from_group, ...)` (`controller.py:1040`).**
I checked that this is safe. Only the single batcher loop calls `build_from_group`, so calls never overlap. The builder keeps no mutable state besides `config`. The `rollout_group` has already been taken out of the buffer, so nothing else is touching it. The new comment ("turning a group's samples into tensors walks every token") is accurate. As the PR notes, the per-group cost goes up (0.073 -> 0.195 s at 60 plies). That's fine because it's off the loop now. If it grows, the extra cost is mostly the `torch.tensor(list)` calls, and building each field with one `torch.tensor` over pre-sized lists already is the cheap path.

**4. The builder still aliases the previous sample's list (`training_sample_builder.py:247-249`).**
`prev_prompt_and_completion` is the previous sample's `token_ids` list itself, not a copy. That's still correct: the only read before the next mutation is the slice `[:prompt_prefix_len]`, which copies. Just noting it because the list/tensor split now makes the type of `prev_prompt_and_completion` depend on being inside `_TrainingSampleInProgress`.

**5. Tests.**
- `pytest.approx` on the `.tolist()` float comparisons is right, since values now go through float32.
- There's no test asserting the output dtypes of `rollout_to_training_samples` or of the packed microbatch. One line in `test_single_turn_packs_one_training_sample` would lock in the contract from point 1, e.g. `assert training_sample.logprobs.dtype == torch.float32`.
- A small `_pack_training_samples` test with `per_sample_pad_multiple` set would cover the new `torch.arange(sample_len) >= unpadded_len` padding-mask path. I didn't check whether `test_batcher.py` already covers it.

**6. Nits**
- `types.py:96`: `token_ids: torch.Tensor  # long` has both a trailing comment and a docstring. You could put the dtype in the docstring instead (`"""[L] long: packed prompt + ..."""`) to match how `TrainingMicrobatch` uses only `# [T]`.
- The controller TODO is now narrowed to `RolloutTurn`. Good, it matches what's still a list.
