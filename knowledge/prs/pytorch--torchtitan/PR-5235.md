# [rl] Reply to the weight push from its worker thread, so the pull overlaps forward/backward (2/2)

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5235) · state: open · merged: False

## Original PR description

**TLDR:** On main, the generators start pulling new weights only after the next forward/backward ends: the trainer's push replies from the actor's event loop, and forward/backward blocks that loop. This PR sends the push's reply from its worker thread right after the TorchStore put. The pull then also overlaps forward/backward, and the training loop stops waiting for it after the optimizer. On a local Qwen3-0.6B run, that wait dropped from 0.40-1.00 s to under 0.1 ms on each step whose batch was already waiting (3 of 19 steps; 0.5% of loop time on this generation-bound run). (2/2, stacked on 1/2, which renames the timing keys used here.)

**Problem**
1. After `optim_step` N, `WeightSyncManager.start_async_push_pull` starts push N -> pull N -> buffer-slot release in the background. When batch N+1 arrives, the loop sends `forward_backward` N+1 to the same trainer actor.
2. The push queues the GPU -> pinned-CPU copy on a side stream and runs the TorchStore put in a worker thread, so its bytes move during forward/backward N+1.
3. The trainer actor runs all its endpoints on one asyncio loop, and `forward_backward` never yields it. The push sent its reply from that loop, so the reply arrived only after forward/backward N+1 ended.
4. The pull starts on that reply, so the loop waits for it after optimizer N+1 (`timing/step/wait_for_pull`).
5. This happens whenever batch N+1 arrives before the push finishes. On the local run below, that was 3 of 19 steps, and the loop waited 0.40-1.00 s on each.

```text
main, batch N+1 arrives before push N finishes:
  loop:    | forward/backward N+1 ============= | optimizer N+1 | wait for pull N ~~~ |
  push N:  | copy + put, in a thread |    reply ^
  pull N:                                       | pull N ---------------------------- |

this PR:
  loop:    | forward/backward N+1 ============= | optimizer N+1 |
  push N:  | copy + put, in a thread ^ reply
  pull N:                            | pull N --------- |
```

**Solution**
1. The push replies from its worker thread as soon as the put finishes.
2. `TrainerActor.push_model_state_dict` becomes `@concurrent_endpoint(explicit_response_port=True)`. It passes `on_published=lambda: port.send(None)` to `Trainer.push_model_state_dict`, which calls it in the worker thread right after the put. `Trainer` stays independent of Monarch.
3. Errors: Monarch does not forward exceptions from explicit-port endpoints. The actor would fail, and the controller process would exit through Monarch's unhandled-fault hook. The endpoint forwards them with `port.exception(ActorError(e))`, so the controller still gets an `ActorError`, as on main.
4. Unchanged: the controller's order. The loop awaits the push before optimizer N+1 changes the weights, and the pull before push N+1 overwrites TorchStore's copy. New rollouts still start only after the generators hold the new weights.
5. Side effect: `timing/weight_sync/push_wall` becomes the push's own time (copy + put). On main it also included forward/backward N+1.

**Results**
```text
Qwen3-0.6B, trainer on 1 H100 + 1 generator on 1 H100, multi-turn debug env (12 turns),
4 prompts x 16 samples per step, TorchStore over TCP (no RDMA), 20 steps per run, steps 2-20.
1/2 (main's loop) -> this PR

steps whose batch arrived before the push finished     3 -> 3 (of 19)
  timing/step/wait_for_pull                            0.40-1.00 s -> < 0.1 ms
  timing/weight_sync/push_wall                         3.02-3.05 s -> 1.23-1.27 s
  pulls that started during forward/backward           0 -> 3
  timing/step/forward_backward                         3.01-3.04 s -> 3.02-3.36 s
loop time waiting on weight sync                       2.24 s (0.49% of 457 s) -> 0.00 s (of 369 s)
perf/trainer/step_time_ratio/wait_for_pull, mean       3.1% -> 0.0%
timing/step/wait_for_push, max                         0.9 ms -> 0.03 ms
timing/step/forward_backward, median over all steps    3.00 s -> 3.01 s
```
Correctness, same run:
```text
trainer/policy_version          1..20 in both; all 21 pulls (setup + one per step) completed in both
rollout/max_policy_version      trails the trainer by 1-3 versions -> 1-2 versions
bit_wise/logprob_diff/max       median 0.59 -> 0.60 (range 0.34-1.26 -> 0.29-1.51)
bit_wise/logprob_diff/mean      median -2.9e-4 -> -2.7e-4
```
- One overlapped forward/backward took 3.36 s, while a 2.57 s pull ran beside it. The other two took 3.05 and 3.02 s.
- Total loop time differs (457 vs 369 s) because of generation noise: the median batch wait is ~20 s. This PR does not cause that difference.
- One batch in this PR's run had max policy age 16: a group that started at version 0 finished at step 17. On 1/2 the peak was 9. Group age comes from generation time, and neither run caps it.

You may ask:
- Why not await the push before forward/backward (the previous version of this PR)? The loop would then wait for the rest of the push instead of the pull. On the run above, the push took longer than the pull (median 1.21 s vs 0.79 s), so that version would have been slower.
- Why not run `forward_backward` in a thread? It has the same payoff, but training compute would leave the actor's thread, and per-thread CUDA/NCCL state (current device and stream) would need review. This PR changes one endpoint.
- Why can a non-actor thread reply? A Monarch `Port` keeps its actor instance, and `send` pickles while holding the GIL, so any thread can call it.

NOTE: the reply from a non-actor thread relies on Monarch behavior that is not documented as a contract. The CPU test and the GPU run above check it on Monarch 0.6.0.
NOTE: the trainer-side `push_model_state_dict` trace span still ends when the actor loop is free, after forward/backward. The controller's `trainer_push_model_state_dict` span ends at the reply.

**Test plan**
- `test_trainer_actor_push_replies_during_forward_backward_and_forwards_errors` (new): a real Monarch actor on CPU, with the real endpoint adapter over a fake trainer whose `forward_backward` blocks the actor loop for 2 s.
  - The push's reply arrives before `forward_backward` returns. Fails on 1/2's adapter.
  - A failing push raises `ActorError` in the caller. Without the forwarding, the unhandled fault ends the pytest process.
- `test_push_model_state_dict_calls_on_published_in_worker_thread_after_put` (new).
