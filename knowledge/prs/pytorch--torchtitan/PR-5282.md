# Initialize CPU-offloaded EMA directly in pinned host storage

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5282) · state: closed · merged: True

## Original PR description

## Motivation

Initialize CPU-offloaded EMA copies directly in their final pinned host storage. `offload_to_cpu=True` currently constructs every parameter and selected-buffer shadow on the accelerator first, then converts the complete set to pinned CPU tensors. Multiple EMA decays amplify this initialization peak.

For `K` configured EMA copies and `B` bytes of tracked local parameters and buffers, the current path retains `K*B` bytes of accelerator shadows before offloading starts. The final EMA storage belongs on the CPU under the existing configuration. A model that fits with CPU-offloaded EMA can exhaust accelerator memory during EMA construction.

This follows the multi-copy interface added in #5074 and the direct pinned-storage approach used by #5107.

## Changes

- Pass the existing offload choice into the private `_EMAParamOptimizer` constructor for both parameters and selected buffers.
- Detach each source and use the existing `get_local_tensor` helper for its local shard. Allocate a separate pinned CPU tensor for every EMA key and copy directly into it.
- Keep the non-offloaded `detach().clone()` path unchanged.
- Remove the post-construction migration loop and its unused helper. Preserve the offload stream, event, scratch-pool, update, save, and load behavior. Update the two existing GPU-test docstrings that referenced the removed helper.

The copy uses the default blocking behavior, so each host shadow is readable when construction returns. Every EMA key retains independent storage; changing a live weight or another EMA copy leaves that shadow unchanged. Checkpoint keys, configured decays, half-life schedules, tracked-buffer selection, and dtypes keep their existing owners.

## Resource model

For dense local tensors, direct allocation removes the accumulated `K*B` accelerator clones. It also removes the pageable-CPU-to-pinned-CPU copy at initialization. Final pinned storage remains `K*B`, and initialization copies the source once per EMA key. No new configuration, dispatch threshold, or dependency is introduced.

Non-dense cross-device copies may use per-tensor contiguous staging inside PyTorch. The claim is removal of the accumulated EMA clones; the platform's copy temporaries retain their own layout-dependent cost. The update pipeline and checkpoint materialization keep their existing memory and transfer behavior.

**Verdict:** I didn't find any correctness problems, and the change is a clear win. With `offload_to_cpu=True`, the old path built K full accelerator clones (`t.detach().clone()` per key) before `_init_cpu_offload` moved them to the host. Initialization peak was K×B on GPU, and that doesn't match what the feature promises. The new path removes that peak and the second pageable-to-pinned copy, and the diff is smaller.

### What I checked

- **Placement and layout match the old behavior.** Old: `get_local_tensor(clone).cpu().pin_memory()`. New: `torch.empty_like(local, device="cpu", pin_memory=True).copy_(local)`. Both give a pinned local shard with `preserve_format` strides: a transposed source keeps its strides and a non-dense source becomes contiguous. Both use the same caching host allocator, so final pinned usage (including its power-of-two rounding) is the same. `_scratch_chunks` / `_foreach_copy_` already handle stride mismatch between scratch and `ema_param`, so nothing changes downstream.
- **The host shadow is ready when construction returns.** A blocking `copy_` into pinned memory syncs the stream, so the first `_update_offloaded` H2D can't race initialization.
- **Each EMA key gets its own storage.** One `empty_like` runs per key, so copies don't alias each other or the live param.
- **DTensor handling is unchanged.** `get_local_tensor(t.detach())` gives the same local shard as before. `_materialize_dtensor`, `state_dict`, `load_state_dict` and the cold-start reseed all still expect a plain pinned local tensor, and they get one.
- **The non-offload path is unchanged.**
- **No callsites are left behind.** `_pin_local` and `_init_cpu_offload` aren't referenced anywhere else, and `_EMAParamOptimizer` is private with only the two callers updated here. The keyword-only `offload_to_cpu` follows the repo's config rules.

### Suggestions (non-blocking)

1. **Keep the DTensor `pin_memory` TODO.** The deleted comment above `_pin_local` said *why* the shard is pinned on its own and rewrapped at save/load: `aten._pin_memory` is NYI for DTensor. It also noted the process-group/world-size caveat a native implementation would have to handle. That limitation still exists and is the reason `_materialize_dtensor` is needed, so please move the TODO next to the new allocation in `_EMAParamOptimizer.__init__` (or into the `_materialize_dtensor` docstring) rather than drop it. Per CLAUDE.md, TODOs should record known limitations.
   [Fix this →](https://claude.ai/code?q=In%20torchtitan%2Fcomponents%2Foptim%2Fema.py%20on%20branch%20contrib%2Fnew-ema-cpu-initialization%2C%20restore%20the%20removed%20TODO%20comment%20explaining%20that%20DTensor%20doesn%27t%20support%20pin_memory()%20(NYI%3A%20aten._pin_memory.default)%2C%20so%20only%20the%20local%20shard%20is%20pinned%20and%20rewrapped%20as%20a%20DTensor%20at%20save%2Fload%20time%20via%20_materialize_dtensor%2C%20including%20the%20process-group%20restore%20caveat.%20Place%20it%20above%20the%20offload_to_cpu%20branch%20in%20_EMAParamOptimizer.__init__.%20ASCII%20only.&repo=pytorch/torchtitan)

2. **Add a regression test for the property this PR is about.** The existing GPU tests already check `is_pinned()` and the values, so the behavior is covered. Nothing guards the memory claim, though: if someone brings back a `clone()` before offloading, every test still passes. A small case in `tests/unit_tests/gpu/test_ema.py` would catch that. It could build a plain CUDA module, call `torch.cuda.reset_peak_memory_stats()`, build `EMA.Config(decays=[0.9, 0.99, 0.999], offload_to_cpu=True)`, and assert `max_memory_allocated() - before` is about 0 for contiguous params. The PR description has the measurement; checking in a cheap version keeps it true.

3. **Docstring nit.** In `_materialize_dtensor`, the reflowed first sentence ("...matching ``p``'s own sharding for DCP at checkpoint save/load -- this is what DCP needs...") now reads a little awkwardly and leaves one long line. Consider: "Move the local shard onto the accelerator and rewrap it as a DTensor matching ``p``'s sharding, for the copy handed to DCP at checkpoint save/load."

4. **Optional optimization, not needed for this PR.** With K>1, each tensor goes through K separate blocking D2H copies. Doing one D2H and then K-1 pinned-to-pinned host copies would leave the device alone after the first copy. Your timings already show a large speedup, so this isn't worth the extra code unless initialization time on large K becomes an issue.
