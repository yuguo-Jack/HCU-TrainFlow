# Fix FFN depth-scaled initialization target

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5111) · state: closed · merged: True

## Original PR description

## Summary

Depth-scale only the FFN output projection (`w2`), while keeping the gate/up projections (`w1` and `w3`) on the regular initializer across the affected dense, shared-expert, and routed-expert paths.

The common FFN helpers now use `w13_param_init` and `w2_param_init`, which makes the initialization roles explicit and avoids carrying forward the old `w2w3_param_init` grouping.

This is an intentional change to initialization numerics for models that use depth-scaled output projections. It is not a regression introduced by the fused `w13` representation; the older unfused implementation also depth-scaled `w3`. Existing checkpoints are unaffected, as are models such as Qwen3 that already initialize these projections uniformly.

`depth_init` remains model-specific. GPT-OSS uses a separate initialization scheme and is intentionally left for a follow-up rather than changing its numerics in this PR.

## Changes

- Use the regular initializer for both logical `w13` projections (`w1` and `w3`).
- Apply the depth-scaled initializer only to `w2`.
- Rename the helper arguments to `w13_param_init` and `w2_param_init`.
- Fix the equivalent `w3_EFD` initialization in the affected routed-expert paths.
- Update the corresponding dense and shared-expert model configurations.
- Add regression coverage for the common helpers, a real Llama3 flavor, and routed experts.

## Validation

The new routed-expert regression cases pass on this branch and fail against the original base, covering the initialization behavior this PR changes.

Passing:
- formatting/lint checks
- CPU unit tests
- single-GPU unit tests
- eight focused routed-expert regression cases

Because this changes initialization for from-scratch training, dense and MoE convergence validation is still pending.

The change itself is correct. Every edited site now initializes the logical `w3` slice of `w13` (and `w3_EFD`) with the input-projection init, and keeps depth scaling on `w2`. I checked these paths:
- `w3_EFD` for routed experts in DeepSeek V3, DeepSeek V4, Kimi K2.7 and Qwen3.5
- dense FFNs in Llama3, DeepSeek V3/V4, Qwen3.5 and Muse Glimmer
- shared experts in DeepSeek V3/V4
- the hand-built fused paths in Qwen3.5 `_shared_experts_config` and DeepSeek V4 MTP

In DeepSeek V4 MTP and Qwen3.5, the `depth_init` local is still used for `w2`, so nothing is left dangling. Kimi K2.7 reuses `deepseek_v3.build_mla_moe_layers`, so its dense and shared FFNs are covered by the DSv3 edits. I'd still like to see the points below addressed before merge.

### 1. The PR description misstates where this behavior came from (please fix it)
The description says the fused `w13` refactor caused this. It didn't. The pre-fusion Llama3 `FeedForward.init_weights` did the same thing on purpose:
```python
nn.init.trunc_normal_(self.w1.weight, mean=0.0, std=0.02)
for linear in (self.w2, self.w3):
    nn.init.trunc_normal_(linear.weight, mean=0.0, std=init_std)
```
That is where the name `w2w3_param_init` comes from. This PR is not fixing a refactor regression. It changes the default init numerics for every depth-init model (Llama3, DSv3/V4, Kimi K2.7, Qwen3.5, Muse Glimmer). Training from scratch will diverge from current runs. Existing checkpoints are unaffected.

Under the repo's rules (Core Principle 5 and "Validating Numerics"), a computation change needs **loss convergence evidence on a representative dataset (e.g. C4)**. At minimum that means before/after curves for Llama3 8B or the debug model, plus one MoE model such as DSv3 16B. The PR currently lists only the CPU unit test and CI. Please add the convergence results and update the description so it says this is an intentional numerics change.

### 2. The optional override has no in-tree user of its default
After this PR, every in-tree caller that passes a depth-scaled `w2w3_param_init` also passes `w3_param_init=<linear init>`. The remaining callers pass the same dict for both arguments: Qwen3, Kimi K3, the HF backend `moe_replacement.py`, and the tests. So the default `w3_param_init = w2w3_param_init` fallback exists only to keep the old, now-unwanted behavior. That leaves two problems:
- `w2w3_param_init` is now misnamed, because in practice it only sets `w2`.
- Any new model that copies the old call pattern silently gets the old init.

A cleaner API, following Principle 3 (reuse over duplication) and the config rule against `None` defaults for required fields:
- Rename `w2w3_param_init` to `w2_param_init` (or `out_param_init`).
- Initialize both gate and up slices from `w1_param_init`. Add an explicit `w3_param_init` only if a real caller needs a different init.

This touches about 15 call sites, mostly in tests (`test_async_linear.py`, `test_tensor_parallel_feed_forward.py`, `test_fused_swiglu.py`, `test_lora.py`, `test_moe.py`, `test_tp_kv_heads_validation.py`), plus Qwen3, Kimi K3 and `moe_replacement.py`. It's mechanical, and it removes the trap instead of documenting around it.

### 3. GPT-OSS is still inconsistent (could be a follow-up)
`torchtitan/models/gpt_oss/flavors.py:149-161` applies `depth_scaled_std` to the whole routed-expert `w13`, both the gate and up slices. Under the rule this PR adopts (depth-scale only the projection that writes back into the residual stream), that is also wrong. If it's deliberately left out, please say so in the description or add a TODO. Principle 6 asks for all model variants to be audited.

### 4. Test coverage
- `test_make_ffn_config_uses_separate_w3_init` only tests the helper's plumbing. It doesn't catch the actual regression, which is a flavor config that depth-scales `w3`. A small CPU test would: build a debug Llama3 (or DSv3) config, check that `w13`'s two slices use the same `param_init` callables (or match in std), and check that `w2` uses the depth-scaled one.
- `make_shared_expert_ffn_config` has the same new code path and no test.
- I couldn't run `pytest tests/unit_tests/cpu/test_feed_forward.py` here because the command was blocked by permissions, so please confirm it passes locally.

### Nits
- `config_utils.py:276` and `:301`: if you keep the override, `w3_param_init = w3_param_init or w2w3_param_init` is simpler. Note that `or` also falls back on an empty dict `{}`, which is a falsy value.
- The new `make_ffn_config` docstring is good. `make_shared_expert_ffn_config` should explain `w1`/`w3`/`w2` the same way.

### Summary
The fix does what it says. Before merge, it needs convergence evidence because it changes init numerics for every depth-init model, and a more accurate description of where the old behavior came from. I'd also recommend renaming `w2w3_param_init` instead of adding an override that every caller sets anyway, and handling or noting GPT-OSS.
