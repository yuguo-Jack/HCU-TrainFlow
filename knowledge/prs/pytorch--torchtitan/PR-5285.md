# [rl] Add an opt-in RDMA fast path for trainer microbatches

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5285) · state: open · merged: False

## Original PR description

**TLDR:** Adds an opt-in RDMA fast path for trainer microbatches, `async_loop.rdma_fast_path_threshold`. With it set, tensors of at least that many bytes stay in the controller's memory as Monarch RDMA buffers, the trainer call carries `RDMAMicrobatch`es, and each rank reads only its own microbatches. Off by default: `None` sends the grid by value, exactly as on main. With it on, a 5.2 GB step at dp 2 x tp 2 drops from 9.1-11.1 s to 3.3-5.1 s end to end, reads included, and peak memory per rank from 15-18 GB to 2.6-3.1 GB (CPU Monarch, one host).

**Problem**
1. **One message per step.** The controller calls `trainer.forward_backward` with the step's whole `[num_microbatches][dp_degree]` grid of `TrainingMicrobatch`, by value.
2. **Every rank gets every column.** Each rank keeps only `row[dp_rank]`, so it unpickles dp_degree times the data it trains on, and needs ~3x the message in fresh host memory while it does.
3. **Small on main, not with extra per-token fields.** Main's fields are 38 B/token, ~1.1 GB per rank for a 29M-token step. Router replay plus top-32 logprobs make it 614 B/token: in one such run, the step-3 call took 93-100 s to reach the last trainer rank (17.8-19.9 GB to each of 4 ranks), and the job died on Monarch's 60 s proc-state timeout.

```text
before: controller --[pickled grid, all DP columns]--> every trainer rank
```

**Solution**
1. **Opt-in:** `AsyncLoopConfig.rdma_fast_path_threshold: int | None = None`. `None` keeps main's by-value path.
2. **`RDMAMicrobatch`** (new `torchtitan/rl/distributed/rdma_microbatch.py`):
   - `register(microbatch, min_bytes)` turns every tensor of at least `min_bytes`, `model_kwargs` included, into a Monarch `RDMABuffer`; smaller ones (the per-microbatch token counts, empty tensors) go in the message;
   - `read` copies them into fresh tensors with one RDMA action (`async`);
   - `drop` releases the buffers.
3. **`Trainer.forward_backward` reads its column only when it gets `RDMAMicrobatch`es,** on the actor loop, one microbatch at a time, under a `read_microbatches` span. Then it calls the engine with a plain list, as before.
4. **The controller registers in a thread, calls, then drops in a `finally`,** while the step's tensors are still alive.
5. **Unchanged:** with the threshold unset, everything. With it set: the batcher, the grid, the global token counts, the loss, the engine, `optim_step`, weight sync.

```text
after (threshold set):
  controller --[RDMAMicrobatches, ~0.8 MB per production step]--> every trainer rank
  trainer rank: read its column | train 0 | train 1 | ...
  controller: drop the RDMA buffers after the call returns (or fails)
```

**Results**

Data path per step, end to end: from the controller's packed batch to every rank holding its column, then drop. Main sends the grid by value; the fast path registers buffers and each rank reads its column (reads included). CPU Monarch, one host, TCP fallback, 4 rank processes, 131,072-token microbatches, real `TrainingMicrobatch`es; 614 B/token adds routed expert ids and top-32 logprobs in `model_kwargs`:
```text
                                     main (by value)   fast path        peak memory per rank
dp 2 x tp 2, 0.64 GB, 38 B/token     1.3 s             1.0 s            2.5 -> 0.2 GB
dp 2 x tp 2, 2.6 GB, 614 B/token     7.5 s             2.5 s            7.5 -> 1.3 GB
dp 2 x tp 2, 5.2 GB, 614 B/token     9.1-11.1 s        3.3-5.1 s        15-18 -> 2.6-3.1 GB
dp 4 x tp 1, 2.6 GB, 614 B/token     4.9 s             1.0 s            7.5 -> 0.7 GB
dp 1 x tp 4, 2.6 GB, 614 B/token     5.0 s             3.8 s            7.5 -> 2.4 GB
```
Medians of steps 2-5; ranges are separate runs (the 5.1 s run had a 1.8 s registration stall on a loaded devserver). At dp 1 every rank reads the whole step either way, and the fast path still wins: main pickles the grid, sends a copy to each rank, and every rank unpickles all of it.

GPU, Qwen3-0.6B, H100, batch invariant, lockstep, one TP 1 generator, trainer DP 1 (2 GPUs), 4,096-token microbatches, Monarch 0.7, this PR with the threshold unset vs 1024:
```text
loss/mean                 bitwise equal at all 5 steps
read_microbatches (on)    5.2-9.8 ms per step (56.8 ms at step 1: one-time RDMA setup)
```
The earlier push measured trainer DP 2 (3 GPUs) against main: bitwise equal over 10 steps, reads 5.6-9.1 ms per step per rank.

You may ask:
- **Why opt-in?** The fast path needs Monarch RDMA (or its TCP fallback), and splitting the call per DP replica would cut what each rank receives without RDMA. The fast path is for heavy per-token payloads.
- **What threshold?** 1024 moves only the token counts by value at every shape from 1,024 tokens up (10 -> 8 buffers per microbatch), so CI-sized microbatches still exercise RDMA.
- **Why not overlap the reads?** The next PR in this stack does. It needs `TrainingEngine` to preprocess one microbatch group at a time, which changes every eager run, so it ships separately.
- **Why not gather the reads?** Gathered reads share the controller's bandwidth, so each RDMA action lasts as long as the whole column, and each has its own 60 s timeout. It was 0-41% faster in my runs; one at a time keeps each action to one microbatch.
- **Why one buffer per tensor, not one packed buffer per microbatch or per column?** Packing costs a controller copy (0.3-0.8 s at 5.2 GB) and twice the step's memory there, and doesn't make registration cheaper. Packed reads tie per-tensor reads with ≤16 MiB TCP chunks, and are 1.3x slower at Monarch's default 64 MiB (`MONARCH_RDMA_MAX_CHUNK_SIZE_MB`; 16 MiB also makes per-tensor reads ~13% faster).
- **Why one `forward_backward` call per step, not one per microbatch?** The gradient-accumulation flags for the last microbatch live inside one engine call.
- **Why not TorchStore?** TitanRL's store only accepts the weight sync's planned keys; a second store needs the deprecated `ControllerStorageVolumes` and cleanup on both sides.
- **Why register in a thread?** ~0.3 s per production step (2,200 tensors) would block the controller's loop, which drives the rollouts. The next PRs in this stack move registration into the batcher's own process.

NOTE:
- **Monarch ibverbs:** works on Monarch 0.7 on our H100 RoCE devserver (5.1 GB/s in a CPU-memory probe, ~6x TCP); the results above use the TCP fallback. Where ibverbs fails, set `MONARCH_RDMA_DISABLE_IBVERBS=1` in every host's launch env; it also moves TorchStore's cross-host weight sync to TCP. The config docstring says so; there is no env default.
- **One host, TCP only.** Across hosts, main sends the whole grid to every rank over the network and the fast path sends each rank its column, so one host likely understates the gap (not measured).
- **CUDA context:** Monarch prints one `[RdmaXcel] No CUDA context` line per registered buffer in a process without a CUDA context (~31 per step in a 0.6B run). With the fast path on, the controller makes a CUDA context current on GPU 0 with the per-thread stack limit at 0: ~256 MiB on H100 (~520 MiB without the limit), plus ~100 MiB of host memory, and 0 lines. A TODO removes it once Monarch logs this once. On GPUs in exclusive-process mode, the controller and trainer rank 0 race for GPU 0; keep the fast path off there. Not measured on Blackwell.
- **Contention:** one controller actor serves the TCP fallback, so per-rank read speed falls as readers grow. Registering in a thread slows down a lot while the controller's event loop is busy (320 buffers: 19 s instead of 0.06 s with the loop held 100%, CPU).
- **Metrics:** with the fast path, `timing/step/forward_backward` includes registering, reading and dropping; tokens/s and MFU exclude the reads.
- **Not tested:** multiple hosts; the RL GPU CI with the fast path on.

Follow up:
- [ ] Overlap the reads with compute (next PR in this stack).
- [ ] Read once per DP replica and broadcast (TODO in `Trainer.forward_backward`).
- [ ] If Monarch keeps logging per buffer: the batcher writes each microbatch into one buffer (no copy).

**Test plan**
- `pytest tests/rl/unit_tests/cpu` (from the repo root, Monarch 0.7): 435 passed, 5 skipped; the 2 failures (`test_verifiers_terminal_bench.py`, a config mismatch) fail on main too.
- `test_rdma_microbatch.py`: every field round-trips with fake RDMA classes; every tensor of at least `min_bytes` becomes a ref (one in `model_kwargs`), and every smaller one, empty included, goes by value; `drop` releases every buffer.
- `test_trainer.py`: `forward_backward` trains a by-value grid as on main, and on `RDMAMicrobatch`es reads only its own column (the other rank's is never read).
- GPU parity above. CPU Monarch stress of the earlier push's register / async read / drop with a concurrent push: 500 steps x 8 microbatches x 4 ranks, every field matched, no hang.

Overall the design is sound. The call now carries refs, each rank reads only `row[dp_rank]`, the engine call doesn't change, and the drop-ordering trick for the Monarch 0.6 deadlock has a comment explaining it. The PR description is very thorough. Below are the issues I found, most important first. I didn't run the tests here: running Python needed approval in this environment.

---

### 1. Drop is skipped when the call raises (agree with @pzhan9)
`torchtitan/rl/controller.py:1126-1144`: when `forward_backward.call` raises, `ref.drop()` never runs, so the step's buffers leak. In practice the job is probably going down at that point, so the cost is small. Still, `try/finally` is the right shape:
```python
microbatch_refs = await asyncio.to_thread(...)
try:
    fwd_bwd_metrics = self._get_rank_0_value(await self.trainer.forward_backward.call(...))
finally:
    # Drop while `packed` still holds the tensors (Monarch 0.6 deadlock).
    await asyncio.gather(*(ref.drop() for row in microbatch_refs for ref in row))
```
`packed` stays alive through the `finally`, so the deadlock invariant still holds. On the success path, the NaN `break` already runs after the drop, so that path is fine.

### 2. Reads run one microbatch at a time, each with its own thread hop and RDMA action
`torchtitan/rl/trainer.py:273`: `[await asyncio.to_thread(ref.read) for ref in refs]` waits for each microbatch to finish before starting the next. That's one thread handoff and one `submit().get()` round trip per microbatch. Two ways to fix it:
- (a) Take @pzhan9's suggestion: make `read` async with `await action.submit()`, then `asyncio.gather(*(ref.read() for ref in refs))`. This also avoids blocking a worker thread on `.get()`.
- (b) Queue every read for the column into **one** `RDMAAction` and submit once.

(a) is the smaller change, and the next PR (prefetch) needs per-microbatch async reads anyway. One caveat from your own measurements: with the TCP fallback served by one controller actor, many concurrent reads per rank may not be faster than serial ones. Please check the `read_microbatches` span after the change.

### 3. Tiny tensors each get their own RDMA buffer
The batcher (`torchtitan/rl/components/batcher.py:718-733`) gives every microbatch 10 top-level tensors, and all of them get a buffer. Some are very small:
- `loss_token_counts` and `routing_token_counts` have `1 + num_mtp_layers` elements (from `torch.stack` in `get_mtp_token_counts`).
- `temperature` is a `full_like` of a constant.

Each costs ~0.15 ms to register, one GIL handoff, and one `[RdmaXcel] No CUDA context` log line, while carrying only a few bytes. A byte-size threshold in `register` (small tensors go by value, like empty tensors already do) is a cheap win. It also reduces the ~1.6K log lines per step.

On @pzhan9's `_runtime.py` comment: I see the threshold and `MONARCH_RDMA_DISABLE_IBVERBS` as **separate** concerns. The threshold is about per-buffer overhead. The env var is about the ibverbs transport failing on some fabrics, and a threshold can't replace it. Both could exist. If you add the threshold, `MicrobatchRef` is still an accurate name: it is still a ref to a microbatch, with some fields inlined.

### 4. The env default may not reach trainer procs on other hosts
`torchtitan/rl/_runtime.py:40-48`: `apply_env_defaults()` runs when `torchtitan.rl` is imported.
- **Single host:** spawned trainer procs inherit the controller's environment after `setdefault`, so this works.
- **Remote host meshes:** the actor proc has already imported `monarch` before it unpickles anything that imports `torchtitan.rl`, and it doesn't inherit the controller's environment. On those procs the new warning fires and the default may not apply.

The PR already lists multiple hosts as untested. I'd add a sentence to the `RL_ENV_DEFAULTS` comment saying multi-host launchers must export the variable themselves.

### 5. `read()` assumes CPU, and `register()` assumes contiguous tensors
- `queue_read` allocates with `torch.empty(shape, dtype=dtype)`, which is always CPU. That matches what the old unpickled path produced, so it's fine today. A short comment would help, since `_TensorRef` doesn't record the device.
- `tensor.view(-1)` in `_TensorRef.register` raises on non-contiguous tensors. That fails loudly rather than silently, which is good. As @pzhan9 asked, say in the comment that the batcher guarantees contiguity. On main every tensor comes from `torch.tensor(...)`, `full_like`, or `torch.stack`, so this holds.

### 6. Silent fallback for unknown containers in `model_kwargs`
`pytree.tree_map_only` only walks containers pytree knows (dict, list, tuple, namedtuple, registered dataclasses). Suppose a future `model_kwargs` value is a custom object holding tensors. Its tensors are treated as one opaque leaf and pickled by value, with no error and no warning, and the message grows back silently. Today `model_kwargs` is empty on main (nothing in `torchtitan/rl` fills it), so this isn't urgent. A docstring note on `MicrobatchRef.fields` would be enough for now.

### 7. Minor / nits
- `trainer.py:266-270`: I agree with @pzhan9 that the two TODOs could be shorter. The numbers (230 MB/s vs 1 GB/s, 0.15% / 2%) belong in the PR description. In code they will go stale.
- `test_microbatch_ref.py`: `assert len(tensor_refs) == 11` depends on the field count of `TrainingMicrobatch`. Counting `tree_leaves(ref.fields)` that are `_TensorRef` and comparing to the number of non-empty tensors in the input would survive adding a field.
- `test_microbatch_ref.py`: the fake `submit()` returns `SimpleNamespace(get=...)`. If you switch to `await action.submit()` (point 2), make the fake return an awaitable, or the test will stop exercising the real call shape.
- `test_trainer.py`: switching to `dp_rank = 1` plus `other_rank_ref.read.assert_not_called()` is a nice way to prove each rank reads only its own column. 👍

### Things that look correct
- Message shape: the controller still owns `packed` for the whole step, and the tensors outlive the buffers, so the deadlock comment is accurate.
- `_step_compute_start` is now set after the reads, so tokens/s and MFU exclude read time. That matches the description.
- 0-dim tensors: `view(-1)` gives shape `[1]` and `torch.empty(())` restores the 0-dim shape. Bool tensors: `view(torch.uint8)` works because the element sizes match.
- Every caller of `Trainer.forward_backward` has been updated: the controller is the only production caller, and the actor endpoint's type hint changed with it.

**Summary:** one real fix (`try/finally` around drop), one likely performance improvement (no serial thread hop per microbatch), and one small-tensor threshold that would cut both overhead and log spam. The rest are documentation and tests.
