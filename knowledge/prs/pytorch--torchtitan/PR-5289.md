# [data] Give each DatasetConcatConfig child its own seed

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5289) · state: closed · merged: True

## Original PR description

DatasetConcatConfig builds every child with the same iteration policy, so they all get the same seed. DatasetMixConfig already gives each child `seed + index` on purpose, but concat doesn't.

That matters for the repeat-a-dataset recipe in the data README, `datasets=(books_ds,) * 3 + ...`: each copy of books_ds makes exactly the same random processor draws row for row, so repeating it doesn't add any variety from random processors.

This seeds each concat child with `seed + index`, same as mix. The first child keeps the configured seed, and the global shuffle after concat still uses the original seed. It does change the random draws of later children, which is the point; children with deterministic processors produce the same rows as before. No in-tree recipe uses DatasetConcatConfig right now.

Added test_concat_children_draw_independent_processor_randomness to tests/unit_tests/cpu/components/data/test_grain_data.py: concat a child with itself using a random-offset processor and check the second copy's offsets differ while the first copy matches the child built on its own. It fails on main and passes with the fix, and the rest of the file passes (97 passed, 1 skipped). ufmt and flake8 are clean.

**Verdict:** The change is correct and small. It makes concat seed its children the same way mix already does. I found no blocking issues, only the small follow-ups below.

### Why it's correct

- When concat builds its children, it sets `shuffle=False`, `dp_rank=0` and `dp_world_size=1`. For a map-style child, that leaves `random_map(..., seed=policy.seed)` in `SingleDatasetConfig._build_map_dataset` (`dataset.py:144-147`) as the only place the seed is used. So before this PR, `(books_ds,) * 3` really did produce the same processor output for every copy, row for row.
- After the fix, child `i` uses `seed + i`, exactly like `DatasetMixConfig` (`dataset.py:245-249`). Child 0 keeps the configured seed. The shuffle after concatenation (`dataset.py:309-310`) still uses the original `dataset_iteration_policy.seed`, as the description says.
- `ConcatThenSplitPackingConfig` also reads `seed` (`packing.py:285`), but packing produces an iterable dataset, which concat rejects with `TypeError`. That path isn't affected.
- No in-tree recipe uses `DatasetConcatConfig` (it only appears in `__init__.py` and the README), so nothing that is already running changes.

### Suggestions (non-blocking)

1. **Say in the comment that seeds depend on child position.** The mix code says so explicitly (`# Inserting or reordering a child reseeds every later child.`). The new comment at `dataset.py:292-293` should say the same, because concat now has that property too: reordering `(books_ds, code_ds, math_ds)` changes the random draws of every child after the first change.

2. **Make the test check the exact `seed + index` rule.** Right now the test only checks that the second copy's offsets differ from the first's, which would also pass with any other way of picking a seed. One more line would lock in the rule and match the mix behavior:
   ```python
   assert second == list(
       child.build(context=CONTEXT, dataset_iteration_policy=dataset_iteration_policy(seed=8))
   )
   ```
   That makes the `[row["id"] for row in second]` assertion unnecessary.

3. **Update the README.** In the "Concatenate datasets" section of `torchtitan/components/data/README.md` (around line 363), a short note would tell users what to expect, for example: *"Each child gets seed `seed + index`, so repeated copies make independent random processor draws (for example, augmentation or random cropping)."*

4. **Seeds can repeat when configs are nested (already true for mix, just noting it).** Offsetting by `+ index` at each level means seeds can collide across levels. For example, in `DatasetMixConfig((concat(A, B), C))`, `B` gets `seed+1` and `C` also gets `seed+1`. This only matters if the *same* child shows up at two such positions, e.g. `concat(concat(A, A), A)` gives the two later copies of `A` the same seed (`seed+1`). The design was already like this and it's rare, so it's fine for this PR. A future fix could derive seeds by hashing `(parent_seed, index)` for both mix and concat. If you want to track it, a TODO is reasonable.

5. **Resuming a checkpoint across this change gives different samples.** A run that is resumed from a checkpoint saved before this change will see different processor output for children at index 1 and above, because `random_map` uses each row's index plus the seed. Since no in-tree recipe uses concat, this is only worth a sentence in the PR description, which already mostly covers it.

### Code style

- The comment is ASCII, the `enumerate` + `replace` pattern matches the mix code, and there are no unnecessary checks. 👍
- `dataset_iteration_policy.seed + index` in `replace(child_iteration_policy, ...)` is correct, since `child_iteration_policy` doesn't change `seed`. Writing `child_iteration_policy.seed + index` would read a bit more consistently, but it's a matter of taste.
