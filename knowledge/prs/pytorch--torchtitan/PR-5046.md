# [dist_moe] Add DistMoE for the vLLM generator inference path

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5046) · state: closed · merged: True

## Original PR description

Follow-up to #4541 (generator side). Lets a vLLM generator run Dist-MoE experts with `DistMoeRuntime.Config(inference=True)`, and routes padding rows to expert `-1` in both the trainer and the generator. Builds on the bounded per-call token counts from #5085 and needs a `dist_moe` that ignores `-1` routes.

## Why

- Dist-MoE experts refuse to run without a runtime, and vLLM constructs `VLLMModelWrapper` itself, so nothing builds one for a generator. `DistMoeRuntime` plans for training (PP activation slots, weight gradients); a generator runs no backward and no pipeline.
- Both roles feed Dist-MoE padding rows: vLLM pads each step (TP rounding, CUDA-graph capture size, DP equalization), and the RL batcher and pretraining packer pad microbatches. Dist-MoE cannot tell a padding row from a real one, so without a mask every padding row is dispatched, computed and combined like a real token.
- Every EP rank must pass Dist-MoE the same row count per call. Padding every inference call to the planned maximum made a decode step run as many rows as the largest step (measured in the previous revision: about 71 ms per decode step, against 20 to 23 ms when padding only to the EP-group maximum).

## What

- **Inference runtime.** `DistMoeRuntime.Config` gains `inference: bool = False`, passed to `dist_moe`, which then plans scratch only (no activation slots). The wrapper builds it after parallelize and before CUDA-graph capture, with `pp_schedule=None`, sized from vLLM's `max_num_batched_tokens`, and rejects a config without `inference=True`. Plumbed through `register_to_vllm` and the generator config as `dist_moe_runtime`.
- **Padding rows go nowhere.** `DistMoeRoutedExperts` sets expert ID `-1` and score `0` on rows marked in `padding_mask`, in training and inference. Dist-MoE never dispatches a `-1` route, so padding costs no communication or expert GEMM work and its output rows are zero. `MoE.forward`, and `KimiLatentMoE.forward` (which overrides it to wrap the experts in latent projections), hand their TP-sharded mask to experts that set `uses_padding_mask`.
  - Generator: the runner publishes the unpadded token count into a device scalar before vLLM pads the step (`_determine_batch_execution_and_padding`); the wrapper builds `padding_mask` from it inside `forward`, so CUDA-graph replay sees the current count.
  - Trainer: the existing `padding_mask` from the RL batcher or the pretraining packer already reaches every MoE block; training passes its microbatch row count unchanged (every EP rank runs the same shape).
  - With a Python-callback post-expert postprocess, `zero_out_padded_callback_inputs` is set so the callback never reads stale rows of `-1` routes.
- **Per-step call size in inference.** Each call carries the largest TP-local token count across vLLM DP replicas (`dp_metadata.num_tokens_across_dp_cpu`), padded with `-1` rows. Graph steps already share the capture size; eager steps do not. Without DP metadata and with DP > 1, calls pad to the planned maximum.
- **Fused postprocess in the generator (optional, can be removed).** The last commit, `[dist_moe] Use a module's fused postprocess in the generator`, lets an inference context take the postprocess module's `to_dist_moe_inference_postprocess(input_dtype)` when it defines one, and otherwise keeps `to_dist_moe_postprocess()`. A route-wise callable makes Dist-MoE execute eagerly, so a generator that captures CUDA graphs needs a fused `RMSNormPostprocess`; this lets a trainable post-expert norm keep its callable form in training (its gamma gets gradients) and use the fused form in the generator. No model in this repo defines the hook yet, so the commit can be dropped without affecting anything here.
- **Batch-invariant mode** (`debug.batch_invariant`). Two `dist_moe` choices depend on the call size: the post-expert top-k reduction uses another, equally correct, accumulation order at or below 128 rows, and the BF16 expert-GEMM schedule is picked from the call size. In batch-invariant mode, inference calls are raised above 128 rows and an inference context without an explicit preset uses `2cta2mma_bm512_bn256`, so a token's output does not depend on how many tokens share its step. Outside batch-invariant mode both keep the size-tuned defaults.

## RL integration test

Recipe `rl_grpo_moe_debug_dist_moe_tp2_ep4` (`torchtitan_recipes/tests/rl.py`): trainer FSDP=2 x TP=2 with EP=4 and one generator with vLLM DP=2 x TP=2 and EP=4 on the Qwen3 debug MoE model, generator `FULL_DECODE_ONLY` graphs, scratch factor equal to the EP size. The two generator replicas hold different token counts, so uneven per-step call sizes and padding run. The recipe applies `DistMoeTransform` through `apply_transforms`.

`build_b200_rl_test_list()` in `tests/rl/integration_tests/rl.py` is the B200 suite (`--test_suite b200`): the existing Kimi K3 KDA test (the `kda` suite stays for the H100 workflow) plus this test. `.github/workflows/integration_test_rl_b200.yaml` is one job: one environment that also installs `dist_moe`; one unit-test step (Kimi K3 bitwise parity plus the Dist-MoE unit tests, which the CPU workflow skips because it does not install `dist_moe`); one integration step running the `b200` suite, which still runs if the unit tests fail. Timeout 60 -> 90 minutes.

## Tested

- **RL with Dist-MoE in both the trainer and the generator, GB300.** GRPO on DAPO-Math with real weights of a large MoE model and the same padding and call-size logic: trainer FSDP 32 x TP 4 x EP 4 (128 GPUs, fp32 master weights, bf16 forward), generator vLLM DP 4 x TP 4 x EP 16 (16 GPUs, FULL CUDA graphs), on-policy so the logprob diff compares the two roles under the same weights. All 5 steps completed:

  | Step | 1 | 2 | 3 | 4 | 5 |
  |---|---|---|---|---|---|
  | logprob diff mean (trainer - generator) | -0.0013 | -0.0015 | -0.0014 | -0.0012 | -0.0012 |
  | logprob diff max | 1.02 | 3.07 | 1.92 | 1.73 | 1.23 |
  | reward mean | 0.875 | 0.609 | 0.828 | 0.969 | 0.859 |
  | grad norm | 0.0 | 8.06 | 0.35 | 0.63 | 1.71 |
  | train-batch padding | 60% | 10% | 18% | 30% | 48% |

  Step 1 had zero reward variance in every group, so its gradient is zero. The two roles run different Dist-MoE kernels, so the diff is small but not zero. No scratch overflow or non-finite values in either role.
- CPU: the new tests cover `-1` routing at the call size, training keeping its row count, callback zeroing, per-call size bounds, the batch-invariant floor and GEMM schedule, the wrapper's mask and per-step size from DP metadata, the runner hook, `MoE.forward` and `KimiLatentMoE.forward` handing the mask only to opt-in experts, the fused inference postprocess, and the recipe and suite. Rebased on `main` with #5085: `test_dist_moe.py`, `test_vllm_dist_moe_padding_mask.py`, `test_rl_dist_moe_recipe.py` and `test_moe.py` give 82 passed, 3 skipped; `test_dist_moe_671b_recipe_topology[deepseek_v3_671b_dist_moe_mxfp8-64-240]` fails identically on `main` in my environment (needs a `torchao` nightly). Generator tests also pass without `dist_moe` installed.
- pre-commit passes on the changed files.
- GB300 inference, real weights of a large MoE model, greedy decoding on AIME 2025, vLLM DP=4 x TP=4 x EP=16 with FULL CUDA graphs, one sequence per DP replica (4 prompts):
  - Default path (per-step call size, auto GEMM schedule): coherent, 3/4 correct. It first differs from the previous pad-to-maximum path (4/4) by about 1e-5 in logprob at the first decode step; the cause is the small-call reduction order above, not padding.
  - Batch-invariant settings (calls above 128 rows, fixed GEMM schedule): tokens and logprobs bitwise identical to the previous path under the same schedule on 4/4 prompts (up to 1823 tokens), 4/4 correct.
  - Reruns of the same code are bitwise identical. The standard all-to-all MoE backend gives the same answers but not identical tokens.
  - 30 prompts with FULL graphs (capture sizes up to 512, and up to 64), with calls raised above 128 rows: completed without errors.
