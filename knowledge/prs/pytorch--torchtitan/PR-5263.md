# [MoE] Opt-in shared-expert overlap with deferred DeepEP dispatch

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5263) · state: open · merged: False

## Original PR description

## Summary

Add opt-in overlap of shared-expert computation with DeepEP training dispatch.
`MoE.Config.overlap_shared_experts` defaults to `False`; no recipe enables it
automatically.

The existing compact training path waits for CPU counts inside dispatch,
before independent shared-expert work is submitted. Reuse DeepEP v2.5's
`defer_epilogue` API to allow:

`launch dispatch -> shared experts -> wait/materialize counts -> routed experts -> combine`

This is a scheduling feature, not a new communication kernel or count-prefetch
algorithm. It contains no private-model or two-batch logic.

## Implementation and compatibility

- Split dispatch into ordered launch/wait custom ops. Wait retains the dispatch
  autograd rule and explicit input edges; pending events use the handle-lifetime
  cleanup pattern.
- Add a callback seam to common token dispatch and routed experts. Other
  dispatchers run the callback synchronously; only DeepEP gets overlap.
  The no-callback path remains the default.
- Preserve the saved shared-expert add, TP transitions, remat policy and
  checkpoint parameter names.
- The deferred path requires DeepEP v2.5 `EPBuffer`. The default path retains
  the older `ElasticBuffer` import fallback. Custom MoE forward implementations
  (such as Kimi latent MoE) and Dist-MoE routed-expert replacements reject
  opt-in overlap instead of silently ignoring it.

Existing GPU fixtures only gain buffer-class selection for the two DeepEP APIs;
no new test cases are included. A separate small cleanup removes an unused
GraphPP test import that prevented all-files lint on the tested upstream base.

## Effective workloads and limitations

Intended for training with standard common `MoE` / `RoutedExperts`, independent
shared experts and DeepEP's compact layout. It can help when the shared branch
covers exposed dispatch/count-wait latency without excessive GPU contention.
It does not eliminate the CPU count wait or make compact training CUDA-graph
compatible.

There is no universal speedup: shared-FFN size, CPU launch cost, TP/AC policy and
GPU contention matter. Earlier shared outputs can also live longer.
Debug-model allocator measurements do not establish production memory usage.

Validation covers single-node BF16 EP8 training with SP and the TP/AC matrix
below. Whole-model compile, inference speedups, FP8, Dist-MoE, PP/CP and
multi-node overlap are not validated. Local model compile regions were
disabled; the official Flex kernel still compiled. Synthetic packed inputs
preserve document-causal attention, but do not establish dataset convergence
or full-size model performance.

## Exploratory performance on the new base

| AC / TP (EP8) | OFF median step ms | ON median step ms | OFF/ON - 1 |
| --- | ---: | ---: | ---: |
| FullAC / TP1 | 126.835 | 127.361 | -0.41% |
| SelectiveAC / TP1 | 131.077 | 126.011 | +4.02% |
| RegionAC, saved EP / TP1 | 126.391 | 125.893 | +0.40% |
| FullAC / TP2 | 180.224 | 178.501 | +0.97% |

One OFF/ON debug-model pair per configuration, not stable performance claims.
Statistic: median over steps 6-20 of each step's maximum wall time across
eight ranks. Full forward/backward and optimizer step are timed after a rank
barrier, with CUDA synchronization at each boundary. Repeated representative
workloads and traces are still needed for production-throughput claims.
