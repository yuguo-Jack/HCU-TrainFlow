# [rl] Send each trainer DP replica only its column of the grid

[Upstream PR](https://github.com/pytorch/torchtitan/pull/5309) · state: open · merged: False

## Original PR description

**NOTE: only relevant at very high DP; a draft until we train there.** Every trainer rank receives the step's `RDMAMicrobatch` handles for every DP column, and that grows with DP. This PR sends each DP replica only its column. CPU Monarch, one host, 4 rank processes, 46 microbatches per DP rank, routed expert ids and top-32 logprobs in `model_kwargs`:
```text
          handles per rank           call to 4 ranks
dp        whole grid -> column       whole grid -> column
2         0.45 MB -> 0.22 MB         41 ms -> 19 ms
8         1.8 MB  -> 0.22 MB         153 ms -> 16 ms
32        7.2 MB  -> 0.22 MB         946 ms -> 20 ms
64        14.4 MB -> 0.22 MB         1475 ms -> 22 ms
```
Summed over dp x tp 4 ranks, that is 3.7 GB -> 58 MB per step at dp 64 (computed, not measured).

**TLDR:** The controller called `trainer.forward_backward` on the whole trainer mesh with the step's `[num_microbatches][dp_degree]` grid of `RDMAMicrobatch` handles; each rank read only its column. Now each DP replica receives only its column, so what each rank receives stays flat as DP grows. Stacked on the trainer-pull PRs.

**Problem**
1. The batcher packs each step as a `[num_microbatches][dp_degree]` grid and registers it as `RDMAMicrobatch` handles (~5 KB each).
2. The controller calls `trainer.forward_backward` on the whole trainer mesh with the whole grid.
3. Every rank receives and unpickles every column's handles, then reads only its own column's bytes.
4. At dp 64 that is 14 MB per rank and ~1.5 s per call (table above); at dp 2 it is 0.45 MB.

```text
before: trainer[0..3].forward_backward(grid [M][2])   -> each of the 4 ranks receives M x 2 handles
```

**Solution**
1. The trainer lays its ranks out as `(dp, cp, tp)`, and RL rejects PP. So each DP replica is `cp * tp` consecutive ranks.
2. `Controller.setup_async` uses Monarch's `split` to cut the trainer mesh into one sub-mesh per DP replica, once.
3. It checks that layout once: each rank reports its DP rank through a new `get_dp_rank` endpoint, and setup raises if a replica's ranks don't all match.
4. `Controller._trainer_loop` sends one call per replica, each with its column, then awaits them together. It reads rank 0's metrics as before.
5. `Trainer.forward_backward` takes that column, `microbatches: [num_microbatches]`, instead of the grid.
6. Unchanged: the batcher, the grid, the global loss and routing token counts, the reads, and every other trainer call.

```text
after:  trainer[0, 1].forward_backward([row[0] for row in grid])  -> M handles each
        trainer[2, 3].forward_backward([row[1] for row in grid])  -> M handles each
```

**Results**

Handles: the table above (`len(cloudpickle.dumps(...))` of the grid vs one column; the call is a median of 5, endpoint returns `len()`). Handles here carry only TCP contexts; on ibverbs hosts and across hosts each one is larger, so these bytes are a lower bound.

GPU, Qwen3-0.6B, H100, batch invariant, lockstep, trainer DP 2 (3 GPUs), one TP 1 generator, Monarch 0.7, 5 steps, TCP: `loss/mean` bitwise equal to main's DP 2 run at every step.

CPU mesh check (the controller's actual setup and `_trainer_loop` code against real Monarch actor meshes, a fake trainer with the real DP-rank lines and a collective that spans replicas; run on an earlier version of this PR, with the same split and layout check):
- dp 2 x tp 2, dp 4, dp 1 x tp 4, dp 2 x cp 2, and HSDP 2 x 2 x 2 on a 2-level mesh: each rank got exactly its column every step, and rank 0's metrics came from global rank 0.
- With DP made the innermost dimension, the startup check raised.
- When one replica raised, the step raised within 20 ms and the batch release ran once.

You may ask:
- **Why not one call per rank?** Each column would be pickled `cp * tp` times on the controller's event loop.
- **Why slice by layout instead of asking each rank where it belongs?** A Monarch slice needs consecutive ranks anyway. The startup check turns a layout drift into an error instead of silently wrong gradients.
- **Does it make the controller cheaper?** No: pickling 64 columns costs the same as one grid (0.43 vs 0.42 s at dp 64). It cuts what each rank receives and unpickles.

NOTE:
- The `cp * tp` ranks of a replica still each receive the same column (the "read once per replica" TODO).
- The GPU run is DP 2 x TP 1, so each replica is one rank; the CPU mesh check covers replicas of several ranks.
- Not tested on more than one host.

**Test plan**
- `pytest tests/rl/unit_tests/cpu` (from the repo root, Monarch 0.7): 438 passed, 5 skipped; the 2 failures (`test_verifiers_terminal_bench.py`, a config mismatch) fail on main too.
- `test_trainer.py`: `forward_backward` trains a column of `RDMAMicrobatch`es through the read-ahead stream.
- GPU parity and the CPU mesh check above.
