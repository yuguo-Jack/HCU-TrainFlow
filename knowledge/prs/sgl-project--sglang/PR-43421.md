# [VLM][MM refactor 2/6] Initialize multimodal processors from a processor config

[Upstream PR](https://github.com/sgl-project/sglang/pull/43421) · state: open · merged: False

## Original PR description

## Motivation

`BaseMultimodalProcessor.__init__` reads its preprocessing and resource settings directly from
`get_mm()`, which exists only inside a running server. A host that only loads and preprocesses
media (for example a trainer) has no server args to read from.

## Modifications

- Add `MultimodalProcessorConfig` (`multimodal/processors/processor_config.py`), a frozen
  `msgspec.Struct` that carries the settings a processor reads once while it initializes: image
  processor backend, fast image processor flag, per-modality `mm_process_config`, processor /
  media IO / CPU worker counts, CPU worker start method, and the media URL domain allowlist and
  size limit.
- `BaseMultimodalProcessor` fills the config from `get_mm()` and initializes from it. The config
  is an input only; the processor keeps the same effective attributes as before
  (`image_processor_backend`, `image_config`, ...) and stores just the two values the CPU pool
  needs when it is (re)created.

Serving behavior is unchanged:
- The CPU worker start method is still `spawn` for `cuda_vmm` and `fork` otherwise; the config
  default (`spawn`) only applies to hosts that do not pass it.
- `SGLANG_CPU_WORKERS` is still read each time the CPU pool is created.
- Server args always provide a domain list and a size limit, so `configure_media_url_security`
  gets the same arguments as before.

## Tests

- Existing multimodal processor unit tests pass on every commit.
- `test_llava_processor_pool.py` builds the processor with `object.__new__`, so it now sets the
  two CPU pool attributes directly instead of `mm_feature_transport`.
