# [Refactor] Native NVFP4 prefill via FlashInfer kv_cache_sf: retire the FP8 dequant workspace (O(n^2) + OOM fix; tvm-ffi fake-Segfault note)

[Upstream PR](https://github.com/sgl-project/sglang/pull/43471) · state: open · merged: False

## Original PR description

## Summary

Routes **NVFP4 prefill attention on the FlashInfer backend through FlashInfer's native packed-FP4 paged prefill** (`kv_data_type=uint8` + `run(..., kv_cache_sf=(k_scales, v_scales))`), replacing the FP8 dequant-workspace route. The kernel dequantizes block-scaled FP4 tiles on the fly — the FP8 workspace disappears entirely from the prefill path.

This is the follow-up to #43239 (HiCache host-pool geometry, PR #43240). This PR attacks the other NVFP4 structural problem found in the same incident investigation.

## Problem

The `DEQUANT_WORKSPACE` prefill access makes `get_flashinfer_dequant_workspace_kv_buffer` **gather + dequantize the entire cached prefix into the FP8 workspace on every chunked-prefill chunk**:

- **Memory**: `dq_k/dq_v_buffer` are allocated per *pool row count* (not chunk size) — ~146 MiB fixed per TP rank at a 160K pool — and `compute_cell_size()` charges **1024 B/token** into the pool budget on top of that. The gather temporaries inside the dequant step scale with prefix length (bf16 intermediates for a ~45K-token prefix, per layer call).
- **Time**: re-dequantizing the whole prefix per chunk is quadratic in chunk count for long prompts.
- **Production impact**: a ~45K-token cold prefix OOM-killed the scheduler (CUDA OOM inside `dequantize_prev_kv`) on 2× RTX 5060 Ti (SM120) with a 160K-token pool.

## Changes

1. **`fp4_kv_cache_quant_method.py`** — the registry entry for NVFP4 prefill becomes `_native_fp4({"flashinfer", "trtllm_mha"})` (was `dequant_workspace` for flashinfer). `dequant_workspace_dtype()` returns `None` → dq buffers are never allocated → `compute_cell_size` drops from 10816 to **9792 B/token** (+10.5% same-budget pool capacity). Rollback: `SGLANG_NVFP4_NATIVE_PREFILL=0` restores the workspace route (registry is built from the env at import).

2. **`flashinfer_backend.py`**:
   - `prefill_uses_native_fp4` flag; `flashinfer_kv_cache_dtype` becomes `uint8` (the packed convention the run path expects). The decode tensor-core heuristic keeps receiving `float8_e4m3fn` so decode routing is unchanged.
   - `forward_extend` feeds `pool.get_raw_kv_buffer()` directly: packed `[rows, heads, head_dim//2]` uint8 KV + token-linear `[rows, heads, head_dim//16]` e4m3 block scales — on SM120 these *are* the pool's own tensors (zero copies; SM100's GenMHA-layout native buffers are unaffected and stay on the trtllm route).
   - Paged and ragged-merge call sites use `wrapper.run(..., kv_cache_sf=...)` with the pool's global FP32 scales as `k_scale`/`v_scale` (same pair `dequantize_prev_kv` uses; mirrors the trtllm_mha native decode route).
   - Split-KV is force-disabled for NVFP4 KV by FlashInfer's own `_nvfp4_kv_requires_disabled_split_kv` guard.

## The "fake Segfault" trap (why the call goes through `run()` + attribute injection)

`BatchPrefillWithPagedKVCacheWrapper.run()` does **not** accept `causal` / `sm_scale` / `logits_soft_cap`; the deprecated `forward()` shim injects them as wrapper attributes (`_causal`, `_sm_scale`, …) before calling `run()`. Passing them as kwargs to `run()` raises `TypeError` *inside the tvm-ffi call frame* — the C++ unwinder turns it into `abort()`, and tvm_ffi's crash handler prints a Rust-symbol "Segfault encountered" backtrace, swallows the real error, and prevents any core dump. This cost days of misdirected forensics (SIGSEGV is a red herring: no sanitizer, no gdb attach, no core will ever show a segfault because there is none). `_set_paged_forward_attrs()` mirrors the `forward()` contract exactly; the docstring documents the trap.

## Validation (Qwen3.8-27B-NVFP4 hybrid, TP2, SM120, HiCache kernel backend + NEXTN MTP)

All on the same machine/battery before vs after:

- **Byte-level**: native prefill vs the workspace route's own `nvfp4_kv_dequantize` primitive agree to bf16 output rounding (maxabs 0.0125); scattered token-slot page tables (page_size=1 radix semantics) gather payload and scale tensors identically (synthetic battery).
- **4× dual-session HiCache eviction/reload**: `accept_mean` = 3.00 ×15, 2.99 ×2, zero corruption.
- **3× 45K-token cold prefixes** (the exact OOM repro from 10/09): all survived, 13 s/round, **GPU memory flat to the MiB** across all rounds (workspace route: hundreds of MB transient per layer call).
- **10× 137K-resident turns at token usage 0.89–0.90** (above the 0.92 waterline the engine died near before): all green, accept 2.28–2.68.
- Boot headroom: pool-end `avail mem` improved ~0.3 GB/rank; the prefill transient that killed the previous config is structurally gone.

## Notes / scope

- Requires FlashInfer with the NVFP4 `kv_cache_sf` prefill support (present in 0.6.18; `_nvfp4_kv_requires_disabled_split_kv` and the uint8 packed convention are both there).
- Cross-attention asserts out of the native route (same as the workspace route did).
- `fp4_mx_block16` recipe untouched (it never used the workspace).
- Speculative verify/draft-extend routing to trtllm native decode is unchanged.

Related: #43239 / PR #43240 (HiCache host pool geometry — independent bug on the same deployment).
