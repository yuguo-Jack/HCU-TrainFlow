# [weight cache] Add disk-vs-daemon parity harness; fix persistence, zombie-PID liveness, and SM100 block-FP8 gating

[Upstream PR](https://github.com/sgl-project/sglang/pull/36156) · state: open · merged: False

## Original PR description

## Motivation

First roadmap item of #33522: a parity harness producing the required evidence for every `IPC_QUANT_ALLOWLIST` entry. Running it caught three real gaps, fixed here.

## Modifications

- **Harness**: `python -m sglang.srt.weight_cache.parity --model-path M --tp-size N` — per rank, diffs a disk-loaded model vs a daemon-served IPC-loaded model over names / shape / dtype / stride / kind / persistence / byte hash. Three sequential phases so two weight copies never coexist on a GPU. `--gsm8k N` adds a few-shot accuracy gate (disk-loaded vs daemon-loaded engine).
- **Fix**: daemon entries carry a `persistent` flag; the client no longer registers non-persistent buffers (rotary `cos_sin_cache`) as persistent.
- **Fix**: `_is_pid_alive` treats zombies as dead (containers without a PID-1 reaper). Two consumers: the rank-takeover path, and the engine-side liveness watchdog — this PR also routes the watchdog's private `_daemon_alive` copy through the shared helper, so a dead-but-unreaped daemon is detected on the engine side too.
- **Fix**: block-FP8 is rejected when DeepGEMM's UE8M0 scale repack is active (SM100+): the repack changes `weight_scale_inv` shape/dtype, which the meta-init client cannot reproduce. The error points at `SGLANG_ENABLE_JIT_DEEPGEMM=0`.
- **Fix**: MXFP4 routed experts (`model_config.is_fp4_experts`, #39762) bypassed the gate — mixed checkpoints do not mark expert layout in hf `quantization_config`. The gate now also takes `model_config` and rejects them before any load.

## Testing

B200: parity PASS for Qwen3-0.6B tp1/tp2 and Qwen3-0.6B-FP8 (block-wise, `SGLANG_ENABLE_JIT_DEEPGEMM=0`) tp1/tp2; without the flag FP8 fails fast at the gate. CPU unit tests (registered in `base-a-test-cpu`) and the existing `TestWeightCacheDaemonTP1Smoke` e2e pass. GSM8K gate on Qwen3-0.6B tp1: identical greedy outputs 20/20, equal accuracy.

**One review point.** `_deepgemm_ue8m0_active()` returns `True` from a bare `except Exception`, i.e. "unknown means unsafe". Fail-closed is the right default for a numerics gate, but the message it produces asserts a specific cause — *"requires the DeepGEMM UE8M0 scale repack to be disabled (SGLANG_ENABLE_JIT_DEEPGEMM=0 ...)"* — and if the failure were an unrelated import error, following that advice would not help and the real cause would be invisible. Logging the caught exception (or falling back to a platform check) would keep the fail-closed behaviour while making a misdiagnosis diagnosable.

Relatedly, `DEEPGEMM_SCALE_UE8M0` is a global signal: it says the repack is *possible* here, not that it ran for a given layer, so the gate may reject some configurations that would in fact round-trip. That is the safe direction and I would keep it, but saying "conservative" in the message would pre-empt the question.

**One coordination note.** The MXFP4 half of this PR overlaps two other open PRs — #39794 (`reject routed MXFP4 experts for IPC`, +63/-12) is a strict subset of the same fix, and #38306 takes the opposite approach by making MXFP4 *work* rather than rejecting it. I raised which direction should win on #33522, since it decides whether this PR keeps that hunk or drops it on rebase.

- awesome-pro · comment · 2026-09-30T20:31:13Z · [source](https://github.com/sgl-project/sglang/pull/36156#issuecomment-5919214071)

One more thing my review above missed, and it is an argument for landing this rather than folding it into #39794: **the zombie fix has two consumers, and only this PR reaches the second one.**

On `main`, `ipc_loader.py`'s `_start_daemon_liveness_watchdog` defines its own private `_daemon_alive(pid)` — a near-copy of `_is_pid_alive` that does `os.kill(pid, 0)` and returns `True` on success. This PR deletes that copy and routes the watchdog through `protocol._is_pid_alive`, so a daemon that dies without being reaped now reads as dead on the *engine side* as well as on the takeover path. Fixing `protocol._is_pid_alive` alone would leave the watchdog still reporting a zombie daemon as alive, which is the case the watchdog exists to catch.

Worth a line in the description, since it is not obvious from the file list that the liveness fix covers two call sites rather than one.
