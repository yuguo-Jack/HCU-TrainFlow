# [BugFix][DP] Prevent health checks from perturbing user request routing

[Upstream PR](https://github.com/sgl-project/sglang/pull/35721) · state: closed · merged: True

## Original PR description

## Motivation

Generation health checks (`HEALTH_CHECK_*`) are intentionally skipped by the scheduler while normal inference is already making progress. Under DP serving, however, the request passes through `DataParallelController` before that scheduler-side skip.

With `round_robin`, a generation health request can advance the same dispatch state used by user requests. For load-aware methods, it can also participate in the user load-budget refresh/update path. A health request that is later discarded can therefore still perturb user-request ownership across DP ranks.

The canonical runtime evidence now localizes the failure chain as:

```text
generation health request
  -> shared user LB state is mutated
  -> user dispatch across DP ranks becomes skewed
  -> per-rank effective batch diverges / running work inventory drops
  -> Input TPS collapses and TTFT tail inflates
```

DP Attention, long chunked prefill, and PrefillDelayer expose or amplify the resulting ownership skew; they are not the source of the health request mutating DPC routing state.

The root-cause investigation is tracked in #35241.

## Modifications

This PR isolates generation-health dispatch state from user load-balancing state in `DataParallelController`:

- Detect generation health requests before normal user LB dispatch.
- Use an independent round-robin counter for health requests.
- Do not refresh or mutate the user `DPBudget` for health-only dispatches.
- For batch generate, refresh the user load budget only when the batch contains a user request.
- Preserve explicit `routed_dp_rank` behavior.
- Preserve `FOLLOW_BOOTSTRAP_ROOM` semantics for PD/disaggregated serving, since that path uses request-specific routing rather than shared mutable user LB state.

This PR does **not** change DP Attention, PrefillDelayer, scheduler busy-health skip behavior, or the health endpoint semantics.

### Runtime reproduction

The validation matrix keeps the server/client workload fixed and varies only generation-health state and whether this DPC patch is applied. The relevant runtime knobs are:

```bash
# server-side topology / scheduler configuration
--tp 8 \
--dp 8 \
--enable-dp-attention \
--enable-prefill-delayer \
--moe-a2a-backend megamoe \
--chunked-prefill-size 65536 \
--load-balance-method round_robin

# generation-health control
SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION=1  # HEALTH ON
SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION=0  # HEALTH OFF
```

Workload shape:

```text
input length    = 60000
output length   = 1
max concurrency = 16
num prompts     = 160
seed            = 1
```

With DP Attention, `--chunked-prefill-size 65536` corresponds to an 8k effective chunk per DP rank. Each arm is run from a fresh server process; external `/health` polling remains enabled in all arms so `HEALTH OFF` isolates generation-health request creation rather than HTTP polling overhead.

The exact benchmark wrapper used for these B300 runs is environment-specific, so the PR records the model-independent server knobs, workload shape, and controlled variables needed to reproduce the failure family rather than claiming a portable one-command benchmark across environments.

### Signal interpretation

The expanded evidence also corrected two earlier intermediate-mechanism assumptions:

- `IDLE-while-EXTEND` was **0 across all 27 analyzed rounds**, including severe LOW cases, so it is not used as a required link in the canonical causal chain.
- `wait_timeout > 0` is **not** a LOW-state discriminator: patched HEALTH-ON runs remained GOOD with 12-24 timeouts. PrefillDelayer `mixed` / timeout activity is treated as downstream scheduler activity or an amplifier, not the root trigger.
- `fill%` and queue depth also overlap between GOOD and LOW rounds and are not state discriminators.

All canonical runs completed 160/160 requests with no fatal errors. The patch removes the user-ownership skew while preserving generation-health dispatch.

This is a scoped validation for the tested failure family; it is not intended to claim that generation health is the cause of every low-throughput state.

A separate 16k-effective-chunk follow-up with generation health ON also completed 4/4 GOOD after patching, supporting the same invariant across both tested chunk configurations.

## Limitations

- Runtime validation is scoped to the tested DeepSeek-V4-Pro, 8x B300, TP8/DP8 DP-Attention serving configuration; it does not establish the incidence rate of this failure across all models, hardware, or DP topologies.
- The controlled experiments establish that generation-health traffic mutating shared DPC user-routing state is causal for this reproduced failure family. Downstream scheduler symptoms such as PrefillDelayer timeouts, queue depth, or aggregate request-count skew are not individually necessary or sufficient failure indicators.
- The patch intentionally isolates routing state rather than redesigning the configured user load-balancing policy. Policy-specific performance differences remain outside the scope of this fix.

## Scope

The intended invariant is:

> Generation health traffic must not mutate the load-balancing state used by user requests when it is routed through DP serving.

This PR does not make round-robin load-aware and does not change the configured load-balancing policy.

Related: #35241

## Source-history check and extended runtime validation

I traced the bug back through the endpoint and dispatch history. This supports fixing the problem at the DPC dispatch boundary, rather than changing PrefillDelayer.

### Historical source

- Before [#8444](https://github.com/sgl-project/sglang/pull/8444), `GET /health` returned 200 without entering inference; only `/health_generate` created a `HEALTH_CHECK_*` request.
- [#8444](https://github.com/sgl-project/sglang/pull/8444) (commit [6f9baf1](https://github.com/sgl-project/sglang/commit/6f9baf100298636174188d845ee6d6493b29ca0c), 2025-08-03) merged the routes, so ordinary `/health` polling began creating generation requests.
- At that revision, every `TokenizedGenerateReqInput` was first dispatched through the configured `DataParallelController` load balancer. The health-specific busy skip happened later in `Scheduler.process_input_requests()`.
- Thus “ignored while busy” meant no model execution, but did **not** mean no mutation of user load-balancing state.
- [#13320](https://github.com/sgl-project/sglang/pull/13320) later added `SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION` with default `True`; [#13961](https://github.com/sgl-project/sglang/pull/13961) fixed its lookup but did not isolate dispatch state.

This history identifies the bug as an interaction between two individually reasonable behaviors:

```text
generation-based health semantics
+
normal DPC routing before the scheduler-side health skip
```

DP Attention, long chunked prefill, and PrefillDelayer expose/amplify the resulting ownership skew; they are not the source of the health request mutating RR state.

## Closed-loop benchmark interpretation

A small clarification on the runtime signals: the validation workload is fixed-concurrency **closed-loop**, so client refill is driven by request completion rather than by an independent offered QPS.

In the post-fix 60k/1 concurrency sweep, raw `perf.json` request throughput reaches ~1.57 req/s at C16 and stays essentially flat through C24/C32/C64, while median TTFT grows roughly with concurrency. This identifies C16 as the closed-loop saturation knee.

That benchmark model also explains why `avg_queue_req` does not need to spike in the pathological LOW state. When the routing bug lowers service capacity (~1.58 -> ~1.14 req/s in the canonical comparison), the client refill rate falls with completions, providing backpressure. Queue depth can therefore remain similar even while running width collapses and TTFT tail worsens.

This is only a signal-interpretation note; it does not change the PR's causal claim. The direct mechanism remains:

```text
generation health
  -> shared DPC user LB state mutation
  -> user dispatch skew
  -> per-rank running-batch divergence / work-supply loss
  -> TPS and TTFT degradation
```

The ~1.57 req/s saturation value is not a production SLO-capacity claim; that would require a separate fixed-rate/open-loop QPS sweep.

## Follow-up: `total_requests` does not replace health/user LB-state isolation

I ran a new control to test whether switching away from round-robin is sufficient to avoid the LOW state without this patch.

Environment was held fixed: v0.5.17 unpatched, generation health ON, TP8/DP8, DP Attention, DP LM Head, MegaMoE, PrefillDelayer, effective 8k/rank chunk, C16/N160, 60k input / 1 output. The only policy change was:

```text
--load-balance-method total_requests
```

Results:

| Run | Input TPS | median TTFT | p99 TTFT | HEALTH@DPC | Result |
|---|---:|---:|---:|---:|---|
| r01 | 94,511.6 | 10.30 s | 11.21 s | 52 | GOOD |
| r02 | 90,597.0 | 10.42 s | 14.43 s | 55 | LOW |
| r03 | 90,713.8 | 10.38 s | 14.44 s | 50 | LOW |
| r04 | 88,454.8 | 9.59 s | 18.07 s | 54 | LOW |

So this arm was only **1/4 GOOD**, with mean Input TPS **91.07k**. All 640/640 requests completed and there were no server fatals.

The useful part is that coarse request-count balance was often already good. For example, rank-local admission reconstruction for r02 was:

```text
[55, 55, 54, 54, 54, 54, 53, 53]  (432/432 observed)
```

while the run was still LOW at 90.6k TPS. r04 was similarly close to even at `[55, 53, 53, 55, 54, 55, 53, 53]` (431/432 observed) but was the slowest run at 88.5k TPS.

This refines the downstream mechanism: persistent **aggregate request-count skew is not required**. A better description is:

```text
generation health
  -> mutates shared user LB state / dispatch dynamics
  -> perturbs rank-local arrival/refill timing and work supply
  -> per-rank effective running/batch formation diverges
  -> TPS drops and TTFT tail inflates
```

`total_requests` can reduce coarse ownership imbalance, but in the unpatched path health requests still participate in the same user load-budget refresh/update machinery. It therefore acts, at best, as an unstable partial mitigation; it does not restore the invariant that health traffic must not mutate user-routing state.

One instrumentation caveat: the current DPC trace does not expose `selected_dp_rank` for the `total_requests` path, so the ownership vectors above are reconstructed from rank-local admission traces rather than direct DPC selected-rank counters. r02 is the cleanest example because all 432 observed user admissions were reconstructed.

I will treat a future patched + `total_requests` run only as a load-balancing policy/performance comparison; the correctness requirement addressed by this PR remains independent of the selected user LB policy.
