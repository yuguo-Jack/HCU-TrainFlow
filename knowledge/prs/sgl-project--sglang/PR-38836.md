# [Unified Memory] fix lazy Mamba buffer lifecycle

[Upstream PR](https://github.com/sgl-project/sglang/pull/38836) · state: closed · merged: False

## Original PR description

## Motivation

Unified Mamba request pools do not receive `enable_mamba_extra_buffer_lazy`, so the pool can allocate and clean up eager buffers while the scheduler performs lazy tracking. Once a track boundary replaces a released slot with `-1`, cleanup can pass that sentinel to the allocator. Streaming-session cleanup and accounting also treat every ping-pong buffer entry as an allocated slot.

## Modifications

- Forward `enable_mamba_extra_buffer_lazy` through both configurator paths, both unified Mamba factories, and `UnifiedHybridReqToTokenPool` to the parent pool. Make the parameter required at these unified-pool entry points so omissions fail at construction; update the existing tri-pool test fixture to pass it explicitly.
- Track ping-pong slot validity with a CPU bitmask on `ReqKvInfo`. Initialize it with the allocated slots, update it when slots are assigned or cleared, and reset it when the buffer is released or the request is retracted.
- Add `mamba_ping_pong_slots()` to select valid slots, optionally excluding a retained buffer position, using tensor slices instead of device-side boolean filtering. Use it in request cleanup so unallocated lazy slots are not freed.
- Use the same valid-slot selection for streaming-session Mamba accounting and cleanup, excluding unallocated entries from both the slot count and allocator frees.

## Validation

Previously run on the flag-propagation change:

- Existing CPU `test_unified_tri_pool.py` suite: **42 passed, 76 subtests passed**.
- Separate one-off checks covered MHA+Mamba, MLA+Mamba, and Full+SWA+Mamba: eager/lazy allocation, the lazy boundary handler, cleanup, and byte accounting passed in 12 cases. These checks were not added to the repository or CI.

These historical results do not validate the subsequent validity-mask and streaming-session changes. No new regression test cases are included in the current diff; the test-file change supplies the required lazy flag in the existing factory fixture.

## Accuracy and Performance

No model/server accuracy run or full scheduler finish/abort validation is recorded here. No lazy-versus-eager accuracy or throughput comparison under unified-pool memory pressure has been run. The cleanup change replaces device-side boolean filtering with CPU-mask-selected tensor slices; no performance measurements are claimed.

- ch-wan · COMMENTED · 2026-09-22T21:07:56Z · [source](https://github.com/sgl-project/sglang/pull/38836#pullrequestreview-5283334669)

**Severity:** 1 blocking, 2 major, 5 minor (4 below, 4 inline).
*Blocking = must fix before merge · Major = should fix in this PR · Minor = worth fixing, doesn't gate merge*

Forwarding the lazy flag into the unified factories is right: the factories are keyword-only, and PD disaggregation already rejects `extra_buffer_lazy`. The findings below are outside the diff, so they go here.

**[Blocking] Streaming sessions free the `-1` sentinel.** `StreamingSession._free_slot_mamba` (`python/sglang/srt/session/streaming_session.py:501`) frees the whole ping-pong buffer. The `!= -1` filter exists only in `free_mamba_cache`. With lazy mode on a unified pool, a session slot holds `[a, -1]` from its first request. On `release_session`, or when that request is aborted mid-processing, `mamba_allocator.free([a, -1])` reaches `MultiEndedAllocator._free_lazy`, whose docstring warns that a `-1` "would join the free list". `-1` gets appended to `free_virtual_ids` and `_free_phys_pages`, and `live_page_count` drops one too far. A later `alloc(1)` can hand out virtual id `-1`, and with eager compaction the stale-slot assertion fires instead. The sturdier fix is at the one place every caller goes through: drop `-1` in `UnifiedMambaSlotAllocator.free` (`unified_memory_pool.py:1002`), or assert on it there, rather than in each caller.

**[Major] Session-held mamba slots are over-counted.** `session_held_mamba_slots` (`streaming_session.py:489`) adds `mamba_ping_pong_track_buffer.numel()`, which counts the `-1` as a held slot. So the mamba accounting invariant (available + evictable + protected + session_held == total) over-counts by one for each idle session. The idle check then reports a mamba leak that isn't there, or hides a real one-slot leak. That is a warning in production and a `ValueError` under `SGLANG_ENABLE_STRICT_MEM_CHECK_DURING_IDLE`.

**[Minor] Host sync on every release.** Now that lazy mode is live on unified pools, `free_mamba_cache` (`memory_pool.py:1707`) runs `buf[buf != -1]`. That is a boolean mask with a data-dependent shape, so it forces a device sync on every request release, and the unified free path was written to avoid those. Masking the known 2-slot layout on the CPU, or filtering with a fixed-shape op inside the allocator, would avoid it.

**[Minor] The description is out of date.** Since merge `26b559579e`, main (#37507) provides the base `_schedulable_capacity_key` keyed on gate state, and this PR only adds the float override (see inline). The description still says the PR adds peer-hole credit to the memo key and rewires memo diagnostics. The validation it cites also ran on code that has since been replaced.

**Severity:** 0 blocking, 1 major, 2 minor (1 inline, 2 below). Two findings from the last review are still open.

The ping-pong validity mask resolves the last round's blocking and major findings. `StreamingSession` now frees and counts only valid slots, and `free_mamba_cache` no longer runs a data-dependent `buf[buf != -1]` on the device. The new free path matches the old semantics in every case: eager 2-slot, spec 1-slot, and lazy with or without a pending slot. Every write to the buffer goes through `_alloc_ping_pong_buffer` or `set_mamba_ping_pong_slot`, and neither `ReqKvInfo` reconstruction in the unified cache copies the buffer, so the mask can't drift from it. Dropping the defaults and deleting the float memo override also address those two threads.

**[Major] The description describes a different PR.** It still presents the capacity-memo key change (peer-hole credit, float pools, consolidating #38837), and it says three files match the union of two earlier diffs. This revision doesn't touch the capacity memo at all. It forwards the lazy flag, adds `mamba_ping_pong_track_buffer_mask`, and routes request and session cleanup through it. The validation section cites runs on code that no longer exists. Please rewrite the description for what the PR does now, and say why the memo change was dropped: main's base key already covers the gate inputs.

**[Minor] The remaining `.item()` checks for `-1` can read the mask.** Four places test a slot for `-1` with `.item()`:
- `mamba_lazy_prealloc_at_boundary` (`schedule_batch.py:3482`)
- `mamba_lazy_spec_prepare` (`schedule_batch.py:3520`)
- `_mamba_lazy_spec_update` (`batch_result_processor.py:1468`)
- `mamba_lazy_post_decode_at_boundary` (`batch_result_processor.py:1545`)

The buffer lives on the device, so each check is a device-to-host sync per request, and `mamba_lazy_spec_prepare` runs every spec step for requests in the tracking window. Testing `req.kv.mamba_ping_pong_track_buffer_mask >> other_idx & 1` instead removes those syncs. It also makes the mask the only record of which slots are live.

**Still open from the last review:**
- The accuracy and throughput A/B under memory pressure (`kv_cache_configurator.py:713`).
- A regression test. The session path needs one most: build a unified pool with `enable_mamba_extra_buffer_lazy=True`, hold a session slot through one request, release the session, and assert that no `-1` reaches the allocator's free list and that `session_held_mamba_slots` counts one ping-pong slot rather than two.
