# [ROCm][Perf] Qwen3.8 mono decode: two persistent FlyDSL launches per layer on MI355X

[Upstream PR](https://github.com/sgl-project/sglang/pull/43516) · state: open · merged: False

## Original PR description

## Motivation

This is a ROCm performance change for Qwen3.8 (`Qwen3_5MoeForCausalLM`) on MI355X: it runs each of the 92 decoder layers of a decode step of 8 rows or fewer as two persistent FlyDSL launches, ported from vllm-project/vllm#60833, instead of the dozen-odd kernel launches and two all-reduces per layer that make small decode steps launch- and sync-bound today, worth **-28% median TPOT (+38% output tok/s) at 8k/1k, concurrency 1** and -16% TPOT (+18.8% output tok/s) at concurrency 4 on one 8x MI355X node, TP8, no MTP. With NEXTN MTP, running only the second launch on the verify steps gives +18% output tok/s at concurrency 1 on `main`.

It is off by default; `SGLANG_QWEN3_5_MONO_DECODE=1` turns it on. Any step it does not cover (prefill, mixed, more than 8 rows, PP, or a non-TP8/non-gfx950 setup) keeps the existing path. With the flag unset, the default path changes only in `qwen3_5.py`, where the attention and GDN forwards now call `attention_core()` / `core()` and then `o_proj` / `out_proj`: the same ops in the same order.

**Stacked on #43481.** That PR adds the Kimi-K3 mono framework (`k3_mono_flydsl/common`, `stages/gemv.py`). The Qwen kernels import it as-is, so this PR does not carry a second copy. Only the commits after #43481 are new here; I will rebase once #43481 lands.

## Modifications

- `kernels/ops/moe/qwen3_5_mono_flydsl/`: the #60833 K1/K2 kernels at its head `6a1c13b2fc` and their layout module, with imports pointed at `k3_mono_flydsl`. One change: K1 also takes a bf16 SSM state. It widens the state to fp32 for the recurrence and rounds it on store, as the stock GDN kernel does; the dtype is part of the K1 build key.
  - K1 (`gdn_pre`, 69 GDN layers): residual add + input norm, `in_proj_qkvz` / `in_proj_ba`, conv1d, the gated delta rule and the gated norm, writing `out_proj`'s input.
  - K2 (`layer_post`, all 92 layers): `out_proj` / `o_proj` with an in-kernel TP all-reduce, residual + post norm, the 512-expert top-10 router, MXFP4 experts, the sigmoid-gated shared expert and the MoE all-reduce.
- `srt/layers/moe/qwen3_5_mono_decode.py`: binds the kernels to SGLang's state. It reads the GDN state from the hybrid backend's mamba pool (`mamba_cache_indices`, conv `(slots, dim, 3)`, SSM `(slots, HV, V, K)` fp32 or bf16). It passes #60833's per-width speed flags (`tuned()`) to both kernels. The weight-layout options of #60833 (fused shared expert, MXFP4 `o_proj` / `out_proj` / `in_proj_qkvz`, the output gate in K2) stay off, because SGLang loads those weights as bf16 and applies the gate in `attention_core()`. Pad rows (`-1`) and the reserved slot 0 are skipped in-kernel. It checks the weights once at the first decode step and logs the reason when it turns itself off.
- `models/qwen3_5.py`: `self_attention` is split so `attention_core()` returns `o_proj`'s input. The 23 full-attention layers keep SGLang's fused HIP front and attention, then run K2. The GDN layer's `forward` is split the same way: `core()` returns `out_proj`'s input. The text model's `forward` hands covered decode and target-verify steps to the mono path. The decode CUDA graph captures it at widths 1, 2, 4 and 8.
- `environ.py`: `SGLANG_QWEN3_5_MONO_DECODE`.
- Docs: the flag in `docs/references/environment_variables.mdx` and a tip in the AMD section of `cookbook/autoregressive/Qwen/Qwen3.8.mdx`.

Requirements, all checked at runtime: TP8, gfx950 and `--disable-shared-experts-fusion` (K2 runs the shared expert itself). Without speculative decoding, K1 also needs an fp32 or bf16 SSM state and no ReplaySSM ring. It also turns itself off on a GPU with fewer than 256 CUs (a partitioned GPU cannot keep all 256 spinning CTAs resident) and with HiCache or LMCache (their copy kernels on another stream can hold CUs those CTAs wait on). The launch argument checks raise `ValueError` instead of `assert`, so `python -O` keeps them; both changes follow the current #60833 head.

Known dependency on ROCm 10 images: the peer buffer uses aiter's `UncachedIpcHeap`, whose `load_hip_runtime()` opens `libamdhip64.so` by name. With `_rocm_sdk_devel/lib` on `LD_LIBRARY_PATH`, that maps devel's HIP runtime next to torch's core copy. This brings back the bug #39513 fixed: `vattn_asm` binds to the first `libamdhip64` in `/proc/self/maps`, which #39513 assumed is always torch's, and graph capture can fail with:

```
RuntimeError: vattn_asm: hipModuleLaunchKernel failed: 709 (context is destroyed)
```

It takes all of these:

- A ROCm 10 image with `_rocm_sdk_devel/lib` on `LD_LIBRARY_PATH`. `rocm720` and `rocm724` images map one runtime and are not affected.
- Mono decode on, so the peer buffer imports `UncachedIpcHeap`.
- `vattn_asm` in use: gfx950, the aiter backend, `--page-size 16`, head dim 256, and `SGLANG_ASM_VERIFY_ATTN` at its default of 1. Since #37465 it runs plain q_len 1 decode (`forward_decode` -> `unified_attention_3d_mtp_decode_func`) as well as MTP target verify and draft extend, so non-MTP runs hit it too. At other page sizes `vattn_asm` is not used.

It is intermittent: it failed two of three non-MTP server starts here, in the decode graph capture. [Rocm/aiter6398](https://github.com/ROCm/aiter/pull/6398) makes `load_hip_runtime()` bind to the copy already mapped; with that file mounted, no later start failed, MTP or not. `smallm_moe_gfx950` looks up HIP the same way, so it is exposed too, but I have not seen it fail. #43481 imports the same `peer_memory.py`, so it also maps the second runtime on ROCm 10.

## Accuracy Tests

GSM8K, 5-shot, all 1319 questions, `lm_eval` local-completions at concurrency 8. Flag on and flag off ran on the same image and node:

| | flexible-extract | strict-match |
| --- | --- | --- |
| SGLang, mono on (this PR) | 0.8506 +- 0.0098 | 0.8287 +- 0.0104 |
| SGLang, mono off (stock) | 0.8446 | 0.8302 |

Per-question exact McNemar test, mono on against off: flexible-extract 87 questions right only with mono and 79 only without (p = 0.59); strict-match 81 against 83 (p = 0.94). No difference. RULER `niah_single_2` at 128k with mono on: 0.992.

With MTP (K2 only on the verify steps, see below), GSM8K at concurrency 2 against the same MTP server with the flag off: flexible-extract 0.8582 against 0.8461, 85 questions right only with mono and 69 only without (p = 0.23); strict-match 0.8446 against 0.8370 (p = 0.47). No difference.

GPQA Diamond and RULER `niah_single_2` at concurrency 8 (every decode step in the mono range), flag on against off on the same server config:

| | flag off | flag on |
| --- | --- | --- |
| GPQA Diamond, thinking, temperature 1.0 (2 runs each) | 0.884, 0.924 (mean 0.904) | 0.894, 0.934 (mean 0.914) |
| NIAH 64k (500 questions) | 0.994, 0.996 (2 runs) | 0.996 |
| NIAH 128k (500 questions) | 0.996, 1.000 (2 runs) | 0.992 |

GPQA samples at temperature 1.0, and the two runs of one arm differ by 4 points, so the 1-point gap is noise. NIAH is greedy: paired per question, mono against each flag-off run gives p = 0.63 and 0.13 at 128k and p = 1.0 at 64k. The two flag-off runs also disagree on 2 to 5 questions between themselves. No difference.

Unit tests (`test/registered/amd/test_qwen3_5_mono_decode.py`, 1 GPU): every fp4 byte and e8m0 scale of SGLang's gfx950 expert layout is where K2 reads it. K1 runs at widths 1, 4 and 8 against SGLang's pool layout, writes the live rows, and leaves pad rows and other slots unchanged; each case runs with and without the speed flags and the outputs must be bitwise equal. With a bf16 state, K1 gives the same core output and conv state as with the widened fp32 state, and the fp32 run's new state rounded to bf16. They pass on MI355X both in the v0.5.21-based image and on `main` (the ROCm nightly of 2026-10-09 with this branch's files); the file has not run in CI yet.

### MTP

With speculative decoding on, K1 is off and K2 runs alone on the target-verify steps: GDN layers run SGLang's own input projection and core, then K2 runs `out_proj` and the MoE. K1 cannot run there because it has no per-draft-token state for the SSM rollback. Verify steps have batch x 4 rows (3 draft tokens), so only c1 (4 rows) and c2 (8 rows) are covered. The K1 requirements (the SSM state dtype, no ReplaySSM ring) do not apply then.

Same node, NEXTN with 3 draft tokens, FSE off in both arms, so the reference is the same server without the flag:

| Cell | Median TPOT off / on (ms) | Output tok/s off / on | Change |
| --- | --- | --- | --- |
| 8k/1k c1 | 3.77 / 3.21 | 244.5 / 283.3 | +15.9% |
| 8k/1k c2 | 4.56 / 4.39 | 400.2 / 413.0 | +3.2% |
| 8k/1k c4 (16 rows: stock path) | 6.05 / 6.01 | 608.5 / 606.7 | flat |
| 60k/600 c1 | 3.85 / 3.29 | 117.3 / 125.2 | +6.7% |

The accept length is the same in both arms (3.62-3.69). Stock MTP with FSE on gets 3.37 / 4.21 / 5.70 / 3.45 ms TPOT. Its accept length on this random dataset is 3.96-4.00, so its TPOT is not comparable per token. Per verify step (TPOT x accept length), K2 saves 14-15% at c1 and 4% at c2 against both.

The same A/B on `main` (the ROCm nightly of 2026-10-09 with this branch's files mounted in both arms, same node, accept length 3.62-3.69 in both):
