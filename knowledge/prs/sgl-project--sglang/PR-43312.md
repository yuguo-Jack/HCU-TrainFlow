# [XPU] Enable LongCat-Flash on Intel XPU; fix stale ngram skip mask in decode

[Upstream PR](https://github.com/sgl-project/sglang/pull/43312) · state: open · merged: False

## Original PR description

## Motivation

`meituan-longcat/LongCat-Flash-Lite-FP8` does not run on Intel XPU. It fails at three points in turn:

1. Model construction: `AssertionError: Torch not compiled with CUDA enabled`. `NgramEmbedding` creates a tensor with a hardcoded `device="cuda"`.
2. First forward: the four n-gram embedding ops are CUDA JIT kernels (`speculative/ngram_embedding.cuh`, built with nvcc), which XPU cannot build.
3. First decode: MLA weight-absorption calls `bmm_fp8` for the fp8 `w_kc` / `w_vc`. That is the flashinfer cuBLAS path, which is CUDA-only, so it fails on XPU with Level Zero error 40.

With those fixed, a full gsm8k run then hit an out-of-bounds device assert near the end. That one is a generic bug, not XPU-specific (see item 4 below).

**Depends on sgl-project/sgl-kernel-xpu#532**, which adds SYCL versions of the four n-gram embedding ops.

## Modifications

1. `layers/n_gram_embedding.py`: drop `device="cuda"` from `exclusive_oe_embedder_size_sums`. The model is built inside the loader's device context, so the tensor still lands on the GPU, the same as its siblings `oe_mods` / `oe_weights`, which never passed a device.
2. `kernels/ops/speculative/ngram_embedding.py`: when the tensors are on XPU, the four wrappers call `torch.ops.sgl_kernel.<op>` (from #532) instead of the CUDA JIT module. The CUDA path is unchanged.
3. `models/deepseek_common/attention_forward_methods/forward_mla.py`: in both fp8 `bmm_fp8` call sites of the absorb path, XPU takes the existing CPU fallback (upcast to bf16, `torch.bmm`). The condition changes from `_is_cpu` to `_is_cpu or _is_xpu`.
4. `model_runner_components/ngram_embedding_manager.py`: reset `batch.ne_skip_token_table_update` in `prepare_for_forward`.
   - The mask is set for an extend batch that contains a chunked request, but it is never cleared.
   - After the chunked request is filtered out, that batch can become the running decode batch and keeps the old, longer mask. Requests merged later then never get their tokens written to the n-gram table, and once the batch shrinks the gather goes out of bounds.
   - On CUDA, decode CUDA graphs hide this because replay uses a zeroed mask buffer. XPU decode is eager and hits it. CUDA with `--disable-cuda-graph` should take the same eager path (not tested).
   - The new unit test in `test_ngram_embedding_manager.py` fails before this change and passes after it.

Items 2 and 3 are gated on XPU. Item 1 does not change where the tensor is placed on CUDA. Item 4 only changes behaviour when a stale mask would otherwise have been used.

## Test

Serve on 8x Intel Arc Pro B60 (with sgl-kernel-xpu#532):

```
SGLANG_USE_SGL_XPU=1 sglang serve --model-path meituan-longcat/LongCat-Flash-Lite-FP8 --device xpu --tp-size 8 \
  --mem-fraction-static 0.65 --trust-remote-code --attention-backend intel_xpu --context-length 8192
```

The weights load as fp8 (12.06 GB per GPU). Full gsm8k with lm_eval (`local-chat-completions`, 5-shot, `--apply_chat_template --fewshot_as_multiturn`, 16 concurrent requests):

| Filter | exact_match |
| --- | --- |
| strict-match | 0.8552 ± 0.0097 |
| flexible-extract | 0.8635 ± 0.0095 |

All 1319 requests completed with no errors. For reference, the same eval on H200 gives 0.8324 strict-match. Decode throughput was about 148 tok/s at 12-16 running requests.

- `test/registered/unit/model_executor/model_runner_components/test_ngram_embedding_manager.py`: 4 passed (CPU).
- Before item 4, the same gsm8k run ended in a device assert (index out of bounds). Disabling the overlap scheduler did not help.
