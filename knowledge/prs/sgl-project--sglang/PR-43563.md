# [Fix] Account for captured inputs in DeepGEMM masked workspace budget

[Upstream PR](https://github.com/sgl-project/sglang/pull/43563) · state: open · merged: False

## Original PR description

## Motivation

DeepGEMM's automatic standard-layout policy can select a masked workspace that OOMs during prefill CUDA Graph capture. The estimate assumes the runner input is released after the gate/up GEMM, but capture makes `dispose_tensor` a no-op: the input and its scales remain live during activation and the down GEMM.

Reproduced on H200 with the default memory fraction, prefill chunk size, and graph settings:

| Model | TP | Failing prefill shape | Masked budget | Failing `down_output` allocation |
|---|---:|---:|---:|---:|
| Qwen3-30B-A3B-FP8 | 1 | 4608 | 3.15 GiB | 2.38 GiB, with 1.20 GiB free |
| Qwen3.5-122B-A10B-FP8 | 2 | 3072 | 5.37 GiB | 4.88 GiB, with 1.89 GiB free |

The 30B failure reproduces with a warm compilation cache. Minimal 30B reproduction: `python -m sglang.launch_server --model-path Qwen/Qwen3-30B-A3B-FP8 --tp-size 1 --moe-runner-backend deep_gemm`.

## Modifications

Include the retained input and scales in the activation/down-GEMM peak estimate. Use the same conservative bound during warmup and capture so layout selection stays consistent. Extend the existing layout-policy test with the two failing geometries and packed/unpacked scales; no new test files.

Explicit layout overrides and the budget fraction are unchanged. Automatic selection can switch to compact earlier on other models too: the existing 397B-shaped fixture now selects compact at 8K under its 42.5 GiB budget, while 4K remains masked. That can change performance near the selection boundary.

## Accuracy Tests

- Existing `test/registered/kernels/ops/moe/test_minimax_quant_scatter.py`: **53 passed** on GB300. The six parameterized policy cases fail against the original estimator.
- Both affected models complete startup, graph capture, serving benchmarks, and GSM8K with the fix on H200. Validation base: `e35f60b9`.
- GSM8K: 1,314 held-out cases, greedy, 2,048-token cap, identical case IDs/prompt hashes. Qwen3-30B fixed-auto scored **1215 / 1217** across two runs; forced-compact controls scored **1223 / 1221**. All requests stopped normally, with no errors. The reverse pair loses 13 and gains 9 cases; these results do not establish numerical equivalence.
- Qwen3.5-122B fixed-auto scored **1275**, versus **1277** with the default Triton MoE runner. Both have the same two length-capped cases, retained in scoring, and no request errors. Original DeepGEMM auto cannot supply an accuracy baseline because startup fails.

## Speed Tests and Profiling

Qwen3-30B, one H200, 320 requests, nominal 8K input / 1K output, concurrency 64. Saved prompts and actual token counts match across all four runs. Repeated in reverse order:

| Configuration | Output token/s, runs 1 / 2 | Median TPOT ms, runs 1 / 2 |
|---|---:|---:|
| Forced compact | 1852.52 / 1853.72 | 30.608 / 30.596 |
| Fixed auto | 2083.69 / 2083.45 | 26.780 / 26.779 |

Fixed auto retains masked decode while using compact for large prefills: about **12.4%** faster than the forced-compact workaround, with median TTFT around 4.04 seconds in both configurations. The default Triton runner remains faster at 2140.95 token/s; this fixes capture reliability rather than establishing a generally faster backend. Qwen3.5-122B also remains slower with DeepGEMM than with its default Triton runner.
