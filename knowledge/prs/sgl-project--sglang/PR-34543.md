# [AMD] [Bugfix] Stop registering oversized inputs in the AMD deterministic all-reduce

[Upstream PR](https://github.com/sgl-project/sglang/pull/34543) · state: open · merged: False

## Original PR description

## Motivation

On AMD GPUs, the deterministic all-reduce (turned on by `--enable-deterministic-inference`, `--rl-on-policy-target`, or `SGLANG_USE_1STAGE_ALLREDUCE=1`) breaks whenever a single all-reduce is larger than its 16 MiB working buffer. That is common: a normal-sized prefill on a large model is enough.

- **Wrong results.** The output is each GPU's own input instead of the sum across GPUs.
- **Eventual crash.** Every such call permanently uses up an entry in a fixed-size table. When the table is full the server dies with `RuntimeError: Rank data buffer is overflowed by 1`. In our benchmark runs this took about an hour, and the container still exited with code 0, so the run looked like it had finished normally.

## Modifications

- Large inputs are now reduced through the existing working buffer in buffer-sized pieces, instead of being registered on every call. All-reduce works element by element and the kernel always adds ranks in the same order, so results and determinism are unchanged.
- An input of exactly the buffer size now takes the normal path instead of the large-input one.
- New test: repeated large all-reduces against a deliberately small buffer, which reproduces the crash in seconds. The test harness also now fails when a worker process fails; before, those failures were ignored.

## Accuracy Tests

`test_amd_deterministic_custom_allreduce.py` on 2x MI355X, ROCm 7.2:

| case | before | after |
| --- | --- | --- |
| existing determinism tests | pass | pass |
| large input, one call | wrong result | correct |
| large input, repeated | crash after 4095 calls | correct, no growth |

## Speed Tests and Profiling

Inputs up to the buffer size, which covers every decode step and small prefills, take exactly the same path as before. Larger inputs now take one kernel launch per buffer-sized piece. The old path returned wrong results, so there is no correct baseline to regress against.
