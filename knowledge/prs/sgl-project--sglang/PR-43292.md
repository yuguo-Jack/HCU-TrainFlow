# [MLX] Sync decode KV to the pool once at release, clamped to the owned prefix

[Upstream PR](https://github.com/sgl-project/sglang/pull/43292) · state: closed · merged: True

## Original PR description

## Motivation

On the MLX backend with the radix cache on, a prefix hit can read KV that another request has overwritten. Fixes #42415.

Chained decode steps in the MLX overlap loop skip `prepare_for_decode` and allocate no pool slots, so a request owns the slots in its `req_to_token` row only for its first `owned_kv_len()` positions; beyond that, the row holds whatever an earlier owner left, often slots the radix tree still references. `_sync_decode_kv_to_pool` nevertheless wrote up to the MLX cache offset, which counts every decoded token, and did so in two places:

- `flush_all_decode_kv`, on every extend launch, for every running request;
- `remove_request`, after the scheduler had already released the row.

Both wrote decode KV into slots owned by the tree or by live requests.

Repro (Qwen3-0.6B-4bit, `--mlx-enable-sampling`, radix cache on): a ~720-token prompt is cached, a short prompt decodes 200 tokens, and the first prompt runs again. The first-token top-5 logprobs of the cached run are compared with the cold run:

| scenario | main + #43291 | this change | control (nothing in between) |
| --- | --- | --- | --- |
| finished request synced after release | top-5 tokens differ | max abs diff 0.0000 | max abs diff 0.0000 |
| running request flushed by an extend | top-5 tokens differ | max abs diff 0.0000 | max abs diff 0.0000 |

## Modifications

- `MlxModelRunner.release_request_row(req_id, owned_len)` syncs the request's decode KV up to `owned_len`, then forgets its row, so no later sync can write through it.
- `MlxTpModelWorker.prepare_for_kv_cache_release` calls it with `req.owned_kv_len()` right before `release_kv_cache`, while the request still owns its row; the tree then inserts exactly `[0, owned_kv_len)`.
- Remove `flush_all_decode_kv` and its call on every extend launch. Decode KV enters the tree only at release, which now syncs it.
- `process_batch_result_prefill` runs the same pre-release hook for a decode request that finishes inside a mixed batch.
- `MlxModelRunner.remove_request` no longer syncs, and its `sync_kv` argument is removed. The sync could only run after the row was released, as on retraction, where it wrote through a row the scheduler may have reassigned.

Two cases remain out of scope: decode tokens from chained steps are still not inserted into the tree, since they own no slots (#40046), and the opt-in fused RoPE and pool-scatter kernel (`SGLANG_MLX_USE_CUSTOM_ROPE`, off by default) writes through unowned entries in the same way. #42542 clamps the sync at release but keeps the per-extend flush, which still corrupts the second scenario above.

## Verification

- `test_decode_kv_release.py` (real `MlxModelRunner` and pool): after release, the owned decode slot holds KV and the slots behind stale row entries stay zero. `TestMixedBatchKvRelease`: the hook runs for a decode request finishing in a mixed batch and not for a prefill request. `test_retracted_request_writes_nothing`: dropping a decoded request's state without the release hook leaves foreign slots untouched. All three fail without the change.
- The repro above and the sequential repro in #42415: max abs diff 0.0000, the same as the control.
- `test/registered/unit/hardware_backend/mlx/` and `test_batch_result_processor_*.py` pass on Apple Silicon; `test_gpt_oss_mlx_correctness.py -k TestGptOssMlxCorrectness` (gpt-oss-20b, radix cache on): 4 passed.
- MLX CI on this stack's head: [unit tests](https://github.com/sgl-project/sglang/actions/runs/38001998841/job/114062157076) pass.
