# [DSpark] Fold draft sampling for DeepSeek-V4.1 heads under AUTO

[Upstream PR](https://github.com/sgl-project/sglang/pull/42987) · state: closed · merged: True

## Original PR description

## Motivation

`SGLANG_DSPARK_FOLDED_SAMPLING=AUTO` (the default) folds the draft sampling step into the draft CUDA graph when its static buffers fit in memory. One head type is excluded: any markov head with `supports_sharded_greedy` (DeepSeek-V4.1 under TP). For these heads AUTO always returns False, so every non-greedy batch runs the draft proposal eagerly.

This costs a lot at low concurrency. At TP4 c1 with temperature 1.0, median TPOT is 2.35 ms with AUTO and 1.51 ms with FORCE. The exception was meant to keep the compact sharded argmax for greedy batches, but in our measurements that only saves a few percent.

The exception also applies under DP attention with `--enable-dp-lm-head`. There the lm-head shard group has size 1, so the sharded argmax saves nothing, yet sampled batches still go eager.

## Modifications

- `_resolve_folded_sampling`: remove the `supports_sharded_greedy` exception. AUTO now decides on free memory alone for every DSpark head. When sampling is folded, greedy batches go through the general in-graph block sampler instead of the sharded argmax.
- The unit test now checks that AUTO folds when the buffers fit and stays eager when they don't, with and without a sharded-greedy head, and that FORCE always folds.

Capturing both the sharded-greedy graph and the folded-sampling graph would recover the greedy-only cost (1-4%, see below). That adds a second draft graph per batch size, so it is left out of this PR.

## Accuracy Tests

No change to the sampling math. FORCE mode already runs this exact path for V4.1. DeepSeek-V4.1-Flash on GB300 with `SGLANG_DSPARK_FOLDED_SAMPLING=2` (FORCE) scores 0.975 GSM8K strict-match.

## Speed Tests and Profiling

**Setup**
- Hardware and model: GB300, DeepSeek-V4.1-Flash (FP4), DSpark gamma 5.
- Workload: `sglang.benchmark.serving`, random 2048 in / 1024 out, range ratio 1, simulated acceptance length 3.51.
- Runs: 2 repetitions per point.
- Metric: median TPOT in ms, AUTO (before this PR) → FORCE (behavior after this PR). Lower is better.
- DP2 config: `--tp 2 --dp 2 --enable-dp-attention --enable-dp-lm-head`.

**Summary**
- Sampled traffic gains the most at low concurrency: TP4 c1 throughput rises about 49%. Under DP attention it gains 2-6% at every concurrency tested.
- Greedy traffic under TP pays 1-4% TPOT, mostly at TP4 c64-c256, which is the cost of dropping the sharded argmax. Under DP attention the sharded path is not faster, and usually we use DP at high concurrency, so greedy is neutral or better.
