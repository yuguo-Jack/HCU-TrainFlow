# [Bugfix] Let the GLM47 tool grammar follow always-thinking templates (GLM-5.3)

[Upstream PR](https://github.com/sgl-project/sglang/pull/42984) · state: open · merged: False

## Original PR description

## Motivation

Refs #41939 (the tool-bearing branch of that report; the "loops even with thinking on" reports there look like a separate cause).

With `--tool-call-parser glm47`, every request that carries non-strict tools gets the full-assistant EBNF. `_process_messages` builds that grammar from the client's raw `chat_template_kwargs.enable_thinking`:

```python
thinking_mode=True if enable_thinking is None else bool(enable_thinking)
```

GLM-5.3 templates ignore that kwarg: the generation prompt always ends with `<|assistant|><think>`, which is exactly why `template_detection` classifies them as `glm53_always_think` (`ReasoningToggleConfig(special_case="always")`). So a client that still sends `enable_thinking: false` (the GLM-4.5/4.7 habit, or a server-wide `--default-chat-template-kwargs`) gets a grammar with `thinking_block ::= ""` whose text rule excludes every special token, `</think>` included. The model is already inside the think block and the grammar never lets it out. `ReasonerGrammarBackend` passes `full_assistant_ebnf` through unwrapped, so nothing else allows the token either.

What that looks like on a production SGLang build (`c9a8fba99`, `zai-org/GLM-5.3-Flash`, `--reasoning-parser glm45 --tool-call-parser glm47`, 8×H200, one non-strict `add` tool, `temperature 0`):

| request | finish_reason | completion_tokens | `content` | `tool_calls` | `reasoning_content` |
|---|---|---|---|---|---|
| no `chat_template_kwargs` | `tool_calls` | 40 | empty | `add(a=2, b=2)` | 87 chars |
| `{"enable_thinking": false}` | `length` | 1024 (max) | empty | none | 4107 chars, ends in `I'll make the call. I'll make the call. …` |

## Modifications

- `serving_chat.py`: when the detected template always thinks (`reasoning_config.always_on`), build the glm47 grammar with thinking enabled regardless of `enable_thinking`. Toggle templates (GLM-4.5/4.7) keep the previous behaviour, and so does the no-reasoning-parser case for templates that honour the kwarg.
- Unlike #42761 (thanks @kflansburg for the earlier diagnosis), this keys off the template config rather than `--reasoning-parser`, so a GLM-5.3 deployment without a reasoning parser is covered too; the raw grammar is what gates `</think>` in both setups.

## Accuracy Tests

No model forward code changes. Two regression cases in `test/registered/unit/entrypoints/openai/test_serving_chat.py` drive the real `_process_messages` path and compile the returned EBNF with xgrammar:

- always-think template + `enable_thinking: false`, with `--reasoning-parser glm45` and with none: the grammar now accepts `…</think>answer` and `…</think><tool_call>add…</tool_call>`. Both subcases fail on `main`.
- toggle template + `enable_thinking: false`: the grammar still rejects a stray `</think>`.

Results (Python 3.12, CPU): on `main` the always-think case fails in both subtests (`SUBFAILED(reasoning_parser='glm45')`, `SUBFAILED(reasoning_parser=None)`); with the fix both cases pass, and the whole `test_serving_chat.py` passes (157 tests, 104 subtests).

Token-level check with the real `zai-org/GLM-5.3-Flash` tokenizer (same grammar builder as the server, `xgrammar.TokenizerInfo.from_huggingface`), after feeding a thinking prefix:

| grammar | `</think>` accepted after thinking text | `<tool_call>add…</tool_call>` accepted after `</think>` | turn can end |
|---|---|---|---|
| `main`: `thinking_block ::= ""` | no | no | no |
| this PR: `thinking_block ::= thinking_block_content "</think>"` | yes | yes | yes |

I could not restart a patched server on the production GPUs, so the post-fix evidence is the compiled-grammar check above rather than a live run; happy to add one if a reviewer can run it.
