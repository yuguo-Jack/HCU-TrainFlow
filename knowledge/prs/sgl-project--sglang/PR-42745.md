# [Fix] Cap SWA lock-walk pinning at one window in the Rust TreeCore

[Upstream PR](https://github.com/sgl-project/sglang/pull/42745) · state: open · merged: False

## Original PR description

Fixes the Rust TreeCore gap in #41579. Mirrors #41580's `_maybe_split_for_window_lock` in the native Rust TreeCore: a lock walk that reaches a long live-SWA ancestor now splits it to a page-aligned window tail (default-on `SGLANG_SWA_LOCK_WINDOW_ONLY`) instead of pinning it whole. #40283 is complementary rather than a replacement. Regression test: 7-token endpoint + 32-token live ancestor + 8-token window pins 8 tokens (was 39) and unlocks cleanly. 868 lib tests pass.

AI-assisted (code written with AI help).

Two small things:
1. `swa_lock_window_only()` doesn't parse the flag the way Python's `EnvBool` does. With `SGLANG_SWA_LOCK_WINDOW_ONLY=no` (or `n`) both tests above still pass here, so the Rust split stays on, while Python reads `no` as false and turns its split off; `off` disables it here but is an error in Python. `sglang-server`'s `utils/environ.rs::env_bool` already mirrors `EnvBool.parse`; matching it would switch both TreeCores with the same values.
2. It's read on every iteration of the walk; the Python reads it once before the loop (`window_only = not lock_host and envs.SGLANG_SWA_LOCK_WINDOW_ONLY.get()`). Hoisting it would match and saves a getenv per node.

@apex-mochen one more thing, found while rebasing #41580 onto today's `main` (`0b635266d4`). #42633 (merged 10-06) added buffer-mode HiCache backups. The buffer pipeline pins a node with `inc_lock_ref` when it launches the D2H copy, and that pin is itself a lock walk, so the window-only split fires on the node being written: its older part is no longer pinned until the ack, and the written keys no longer match the node. On the Python core, #42633's `test_buffer_only_writes_component_pools_independently` caught it with #41580's flag on, and #41580 now leaves a node whole while `buffer_backup_pending(node.id)` (pushed as `4dad756d38`).

The same happens on the Rust core with this PR, and CI won't show it: that test forces the Python core (it overrides a component). I ran its flow with the default components (insert one window + 1 page, back up the leaf through the buffer pipeline, drain), on GPU:

| | node split by the backup's pin | writes match the chain |
|---|---|---|
| Rust, `main` | 0 / 8 configurations | 8 / 8 |
| Rust, this PR at `7ba21bd` | 6 / 8 (all page sizes > 1; e.g. 384 → 128 tokens at page size 128) | 2 / 8 |
| Python, #41580 with the check | 0 / 8 | 8 / 8 |
| Python, #41580 without it | the same 6 / 8 | 2 / 8 |

The Rust core can't see the pipeline's pending set (`BufferModePipeline.inflight_backup_pools`, Python-side), so a guard needs that state passed down, e.g. the adapter marks a node when the pipeline enqueues it and clears it at the ack, and the split skips marked nodes, as the Python side does. A blunter option is to skip the split under `is_host_memory_buffer_only`. Your call; I'm happy to re-run this on whatever you push. As a test for the shared suite (it runs on both cores there):

- apex-mochen · comment · 2026-10-12T10:35:14Z · [source](https://github.com/sgl-project/sglang/pull/42745#issuecomment-6122538497)

Root cause of the platform failures found and fixed.

The `set_buffer_backup_pending` binding added for the buffer-mode feedback used the legacy `py.allow_threads` API, which does not exist on the pyo3 version the platform builds compile against — `main` has migrated every other binding in this file to `py.detach`. The rust extension failed to compile (E0599 at python_bindings.rs:1869), which cascaded into the AMD/NPU test failures (servers could not start).

Pushed `a0455a03` aligning the binding with the rest of the file (`py.detach(|| self.core().set_buffer_backup_pending(...))`). Same closure, same GIL-release semantics, no behavior change.

Platform rust-ext builds should compile again now. Could a maintainer trigger a CI rerun (or add the run-ci label)? Thanks @Jialin @alphabetc1.
