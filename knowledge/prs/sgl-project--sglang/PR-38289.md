# [NPU] Optimize DFlash2 prefix KV writes and draft block preparation

[Upstream PR](https://github.com/sgl-project/sglang/pull/38289) · state: open · merged: False

## Original PR description

## Motivation

DFlash2 support for Ascend NPU was introduced by #35629. Profiling and runtime benchmarks showed that the NPU execution path still contained avoidable per-step overhead:

1. Prefix-valid KV commits used dynamic-shape operations such as `nonzero` and `index_select`.
2. The DFlash2 draft block mask buffer was fully initialized on every draft step, although only the anchor token changes after allocation.

This PR optimizes these two paths for Ascend NPU while preserving the existing behavior on CUDA, ROCm, CPU, and other backends.

## Modifications

### Static-shape prefix-valid KV writes on NPU

Add an NPU-specific static-shape implementation of `set_kv_buffer_prefix_valid` in `NPUMHATokenToKVPool`.

Instead of dynamically packing valid KV rows, the implementation:

- keeps the original rectangular KV tensors;
- preserves valid KV destinations;
- redirects invalid suffix rows to reserved KV cache slot `0`;
- performs one static-shape KV cache write.

Slot `0` is already reserved by the NPU KV pool for padded or dummy writes and is not used as a valid token cache location.

The original paths remain available:

- `SGLANG_NPU_USE_STATIC_PREFIX_KV_CACHE_STORE=0` restores the previous dynamic fallback.
- When `SGLANG_NPU_USE_TRITON_PREFIX_KV_CACHE_STORE=1` is enabled, the existing Triton prefix-KV implementation is still used.

This optimization is implemented entirely in the NPU KV pool. It applies to NPU callers of `set_kv_buffer_prefix_valid`, currently including DFlash2 and DSpark, without changing non-NPU KV pools.

### Initialize the DFlash2 mask buffer once

Avoid filling the complete DFlash2 draft block with the mask token on every eager draft step.

When the draft block buffer is allocated or resized, its mask-token tail is initialized once. Subsequent steps only update the anchor token in column `0`.

The shared DFlash2 worker does not directly check the device type. Instead, `AscendAttnBackend` exposes an explicit capability flag, and other backends default to the original per-step initialization behavior.

The optimization can be disabled with:

```bash
export SGLANG_NPU_DFLASH_INIT_MASK_ONCE=0
```

### Hardware isolation

This PR does not add any `is_npu()` or `_is_npu` checks to shared DFlash2 code.

- The prefix-valid KV optimization is implemented in the NPU-specific memory pool.
- The mask-buffer optimization is enabled through an Ascend backend capability.
- CUDA, ROCm, CPU, and other attention backends retain their existing behavior.

### Tests

Add unit coverage for:

- redirecting invalid KV suffix rows to reserved slot `0`;
- equivalence between static and dynamic writes at valid KV locations;
- invalid input-shape validation;
- fallback to the original dynamic prefix-valid writer;
- one-time mask-buffer initialization;
- the original per-step mask initialization fallback.

## Accuracy Tests

This PR does not change DFlash2 proposal, sampling, acceptance, or target verification algorithms. The accuracy check only verifies that the NPU execution optimizations do not cause an accuracy regression; a multi-concurrency accuracy sweep is not required for this PR.

### GSM8K regression check

The same GSM8K evaluation setup was used for the DFlash2 accuracy check. The baseline accuracy is reused from the previous baseline measurement because this PR only changes the DFlash2 execution path.

| Configuration | Accuracy | Invalid | Requests |
|---|---:|---:|---:|
| Previous baseline | 0.836 | 0 | 128 |
| DFlash2 optimized | 0.836 | 0 | 128 |

DFlash2 optimized run details:

- `parallel=10`
- latency: `155.295 s`
- output throughput: `245.371 token/s`

The accuracy is unchanged and no invalid output was observed, so no accuracy regression was detected.

## Speed Tests and Profiling

### Environment

- Hardware: Ascend 910C
- Tensor parallelism: TP=2
- Target model: Qwen3.8-27B
- Target dtype: BF16
- Draft model: Qwen3.8-27B-DFlash2
- DFlash2 draft tokens: 4
- RadixCache: disabled
- Dataset: random
- Input length: 1024 tokens
- Output length: 100 tokens
- Length range ratio: 0
- Concurrency: 10
- Number of requests: 100
- Temperature: 0
- Ignore EOS: enabled

### Benchmark command

```bash
vllm bench serve \
  --backend openai-chat \
  --model /path/to/Qwen3.8-27B \
  --served-model-name /path/to/Qwen3.8-27B \
  --tokenizer /path/to/Qwen3.8-27B \
  --percentile-metrics ttft,tpot,itl,e2el \
  --dataset-name random \
  --max-concurrency 10 \
  --num-prompts 100 \
  --endpoint /v1/chat/completions \
  --base-url http://<server-url> \
  --seed 10959 \
  --ignore-eos \
  --temperature 0 \
  --random-input-len 1024 \
  --random-output-len 100 \
  --random-range-ratio 0 \
  --random-prefix-len 0
```

### Results

| Implementation | Output throughput | Relative performance |
|---|---:|---:|
| DFlash2 before this optimization | ~175 tok/s | 1.00x |
| DFlash2 with this PR | ~195 tok/s | ~1.11x |

The optimized implementation improves output throughput by approximately **11.4%**, from about **175 tok/s** to about **195 tok/s** under this workload.
