# fix(openai): omit absent tool_calls from chat responses

[Upstream PR](https://github.com/sgl-project/sglang/pull/43027) · state: open · merged: False

## Original PR description

## Motivation

DeepSeek's Chat Completions response schema defines [`tool_calls` as an optional array](https://api-docs.deepseek.com/api/create-chat-completion/), and its no-tool response example omits the field. When a model does not call a tool, SGLang instead serializes `tool_calls: null` in every non-streaming Chat Completions assistant message. Some streaming paths, including normal text emitted while a tool parser is active, have the same behavior.

The [DeepSeek Provider Verifier](https://github.com/smg-project/deepseek-provider-verifier/blob/161fee64de1a59eb21e2c19563f0d64347a1fc78/src/deepseek_provider_verifier/protocols/chat.py#L93-L97) exposed this difference by rejecting a present non-array value. OpenAI also defines `tool_calls` as optional, and its [no-tool response and streaming examples](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) omit the field. Omitting an absent optional field therefore aligns with DeepSeek's documented response shape while remaining OpenAI-compatible.

The [`/v1/chat/completions` endpoint](https://github.com/sgl-project/sglang/blob/7760d5264ac16b85392aefb1bf5c13ce38d9632e/python/sglang/srt/entrypoints/http_server.py#L1779-L1787) uses one `OpenAIServingChat` implementation for every served model. Its [non-streaming response builder](https://github.com/sgl-project/sglang/blob/7760d5264ac16b85392aefb1bf5c13ce38d9632e/python/sglang/srt/entrypoints/openai/serving_chat.py#L2419-L2464) initializes `tool_calls` to `None` and always constructs the shared [`ChatMessage`](https://github.com/sgl-project/sglang/blob/7760d5264ac16b85392aefb1bf5c13ce38d9632e/python/sglang/srt/entrypoints/openai/protocol.py#L1209-L1214). This makes the non-streaming behavior model-independent rather than specific to DeepSeek. SGLang's ordinary streaming fast path already omits absent tool calls; only Chat Completions paths that serialize `DeltaMessage` through `ChatCompletionResponseStreamChoice` need the same rule.

## Minimal Reproduction

Start an SGLang server with any chat model:

```bash
python -m sglang.launch_server \
  --model-path Qwen/Qwen2.5-0.5B-Instruct \
  --host 127.0.0.1 \
  --port 30000
```

Then issue a non-streaming request without tools:

```bash
curl -s http://127.0.0.1:30000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "Qwen/Qwen2.5-0.5B-Instruct",
    "messages": [{"role": "user", "content": "Reply with amber."}],
    "temperature": 0,
    "max_tokens": 4
  }' | jq '.choices[0].message'
```

Before this fix, the message includes:

```json
{
  "role": "assistant",
  "content": "amber",
  "tool_calls": null
}
```

After this fix, `tool_calls` is omitted. Requests that produce tool calls still return the existing array unchanged. Chat Completions streaming choices that use `DeltaMessage` follow the same presence rule; the ordinary streaming fast path already omits the field.

The observed verifier failure is non-streaming. The narrower streaming surface is covered separately by the focused unit test rather than claimed as a second end-to-end reproduction or an all-streaming-path failure.

## Modifications

- Omit `ChatMessage.tool_calls` when its value is `None`.
- Omit `delta.tool_calls` only when `DeltaMessage` is serialized inside a Chat Completions stream choice. `DeltaMessage` itself is unchanged because the transcription API also reuses it.
- Preserve actual tool-call arrays and explicitly supplied empty arrays.
- Add focused CPU coverage for absent, empty, and populated tool-call values in complete buffered and streaming Chat Completions JSON payloads.

This does not change prompting, tool parsers, constrained decoding, model output, finish reasons, or tool-call contents.

## Compatibility and Merge Danger

- **Door:** Two-way; reverting restores explicit `tool_calls: null` values.
- **Blast radius:** OpenAI-compatible Chat Completions only: all non-streaming messages without a tool-call list, independent of model, plus streaming choices that use the Pydantic response path. Transcription serialization is unchanged.
- **Intentional behavior change:** Raw JSON consumers see an omitted optional field instead of `null`.
- **Preserved behavior:** Populated tool-call arrays and explicitly supplied empty arrays serialize unchanged.
- **Compatibility basis:** DeepSeek documents an optional array and omits absent tool calls in its example; OpenAI also omits the optional field in its no-tool examples.
- **Canary:** Verify one no-tool buffered response, one no-tool stream, and one actual tool-call response.

A server-wide configurable policy for absent tools could be discussed separately. This PR intentionally limits itself to Chat Completions response serialization.
