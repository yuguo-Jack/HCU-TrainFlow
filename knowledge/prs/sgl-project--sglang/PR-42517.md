# [HiCache] Use attention-TP ownership for bounded CP file caches

[Upstream PR](https://github.com/sgl-project/sglang/pull/42517) · state: open · merged: False

## Original PR description

## Motivation

The bounded file backend elects the owner of rank-replicated KV from `storage_config.tp_rank`. Without attention DP, this is a global TP coordinate even under CP. CP shards already have distinct `_cp{rank}_{size}` filenames, but `LRUFileEvictor.reserve` still refuses new files on every global rank except zero.

CPU reproduction on main 35f3c96ff4: TP=8, CP=4, attention DP=1, two attention-TP replicas per CP shard. Generate real storage configs with the production controller method, then use the real file backend with a 64-byte cap. Global rank 2 is the leader of CP shard 1, yet its `set` is refused as a non-owner. The topology-only reproduction needs neither model weights nor CUDA.

## Modifications

- Append an optional `attn_tp_rank` to HiCacheStorageConfig, defaulting to None for compatibility with existing constructors.
- Populate it from the runtime's attention-TP rank.
- For rank-replicated caches, pass that replica-group rank to the file evictor's owner check. Keep `tp_rank`, `tp_size`, CP suffixes, storage keys and other backends unchanged. Legacy manually constructed configs fall back to their existing TP rank.
- Add CPU regressions using real rank derivation, real storage configuration generation, actual temporary files and byte-exact CPU tensor reads. Each CP leader can write its own file; non-leader replicas cannot create new files. Existing non-CP, DP+CP and non-replicated storage coordinates are covered.

### Relationship to #37149

#37149 fixes the controller's earlier `backup_skip` election. Its diff does not change the file evictor's ownership check, so with file eviction enabled its newly elected CP writers can still be refused at `reserve`. This PR fixes that separate backend admission check; it does **not** replace #37149 or claim full CP serving is fixed by this PR alone. Full controller-to-file CP backup requires the controller election fix as well. No changes to `backup_skip` here.

## Accuracy Tests

Python 3.12; PyTorch 2.13.0+cu130; CUDA hidden; normal project imports and isolated test dependencies.

- Before production fix, final scoped regressions: **1 failed, 2 passed, 3 subtests passed**, 34 deselected (22.61s). Failure is the real backend refusing the CP shard leader.
- After fix, full existing registered file-cache suite: **37 passed, 3 subtests passed**, 16 warnings (23.46s).

The controller is represented by a minimal attribute fixture; runtime context and process-group CP coordinates are injected. An uninitialized real MLATokenToKVPool instance supplies the production isinstance classification without allocating GPU KV memory. Actual rank formulas, configuration generation and file I/O run unchanged. No distributed collectives, GPU forward pass or complete model-serving validation was run.

## Speed Tests and Profiling

Not run; no TTFT/throughput or model-quality claim. This is owner admission correctness. The cap continues to apply per evictor/file namespace, not globally across all CP shard files.
