# fix(openai): return real HTTP status for pre-stream admission aborts

[Upstream PR](https://github.com/sgl-project/sglang/pull/28175) · state: open · merged: False

## Original PR description

## Motivation

When a streaming request is aborted with an explicit error `status_code` **before the first chunk is emitted** — e.g. an admission-time rejection like `"The request queue is full."` once `--max-running-requests` / `--max-queued-requests` is exceeded — the OpenAI serving layer emits the error as an in-band SSE chunk under an **already-committed HTTP 200**. Clients and reverse proxies that key on the HTTP status code see a `200` and cannot tell the request was actually rejected, so they cannot retry or route on a real `503`.

The kick-start `generator.__anext__()` in `_handle_streaming_request` already exists precisely to surface pre-200 validation failures as real HTTP errors, but it only catches `ValueError`. An abort delivered via a `finish_reason` carrying a `status_code` is **yielded as a chunk** rather than raised, so it slips past that guard and the 200 is committed.

## Modifications

- Add `StreamingAbortBeforeFirstChunk` in `serving_base.py`. It carries `message` / `err_type` / `status_code` and is intentionally **not** a `ValueError` subclass (which is already mapped to a default 400), so the real status code is preserved.
- In the chat and completions streaming generators, when an abort with an `HTTPStatus` `status_code` arrives while `stream_started is False`, **raise** `StreamingAbortBeforeFirstChunk` instead of yielding the SSE error chunk.
- `_handle_streaming_request` (chat & completions) catches it from the kick-start `__anext__()` and returns a real `create_error_response(message, err_type, status_code)` whose HTTP status matches the body.
- Behavior **after** streaming has started is unchanged: the 200 status line is already on the wire, so the existing in-band SSE error-chunk path is kept. Fully backwards compatible.

Files: `serving_base.py`, `serving_chat.py`, `serving_completions.py`.
