# [AMD][DeepSeek-V4.1] Fix server crash on prompt-logprob and hidden-state requests under decoder SWA bounded replay

[Upstream PR](https://github.com/sgl-project/sglang/pull/41448) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-decoder-swa-bounded-replay`, the layers after the last kv_source layer run only on the last 128 rows (`SWA_WINDOW`) of each prefill extend. Requests requiring prompt logprobs or full hidden-state capture (outside DSpark) need earlier rows, so the **server crashes** on such requests:

```
ValueError: decoder SWA bounded replay cannot return logprobs of prompt tokens; set logprob_start_len to the prompt length
ValueError: decoder SWA bounded replay cannot capture hidden states of all prompt tokens
```

The error is raised in the model forward, so one request brings down the server and all requests in flight. These requests trigger it:
- `/generate` with `return_logprob: true` and `logprob_start_len` below the prompt length;
- `/v1/completions` with `echo: true` and `logprobs`;
- `return_hidden_states: true` (full capture).

Normal generation and output-token logprobs are not affected. These requests are rare in chat serving but common in evaluation and scoring: loglikelihood benchmarks (for example MMLU or HellaSwag through lm-evaluation-harness), perplexity runs, prompt scoring in RL pipelines, and hidden-state extraction.

This request crashes a running DeepSeek-V4.1 server with replay on:

```bash
curl -s localhost:30000/generate -H 'Content-Type: application/json' -d '{
  "text": "Any prompt", "sampling_params": {"max_new_tokens": 8},
  "return_logprob": true, "logprob_start_len": 0}'
```

## Modifications

1. **Per-request tail length:** new `late_layer_tail_lens()`. A request that reads prompt rows gets its whole extend as the tail. Other requests keep the 128-row tail.
2. **Correct window floors:** `late_layer_tail_layout()` takes these lengths. Rows before the last 128 are floored at the tail start, because rows before the tail have no late-layer KV.
3. **CUDA and HIP backends:** both pass the new lengths.
4. **No false errors:** `_check_late_layer_tail_readers` raises only if the tail really misses needed rows. The logits path shifts the prompt-logprob start into the tail.
5. **Unit test:** `test_dsv4_late_layer_tail.py`.

## Accuracy Tests

DeepSeek-V4.1-Flash on MI355X, TP4, DSpark, SWA replay on.

| Request | main | This PR |
|---|---|---|
| Prompt logprobs from token 0 (3k prompt) | crashes | OK |
| Prompt logprobs after a 2k prefix-cache hit | crashes | OK |
| 20k prompt in two prefill chunks | crashes | OK |
| Normal and prompt-logprob requests in one batch | crashes | OK |

- **GSM8K:** 0.968 with replay on and this PR.
- **Prompt logprobs, replay on vs off:** the mean absolute difference is 0.07-0.15 per request. This is within the server's own noise: the same request sent twice differs by 0.06-0.16.
- **Full hidden-state capture:** covered by the unit test.

## Speed Tests and Profiling

Requests without prompt logprobs or full hidden-state capture run the same code as before. A prompt-logprob request runs its late layers on its whole extend, as without replay.

- RolaoDenthu · COMMENTED · 2026-10-09T22:42:40Z · [source](https://github.com/sgl-project/sglang/pull/41448#pullrequestreview-5476051040)

Thanks for working on this! But I can't think of a scenario that needs `--enable-decoder-swa-bounded-replay` on while returning prompt logprobs or full hidden states. Could you share the use case you have in mind?

If there isn't a specific one, I'd lean towards returning a 400 instead (as #42719 does), for two reasons:

1. This PR quietly turns the feature off for these requests: they get no speedup, requests in the same batch pay for the extra rows, and the user isn't told. A 400 suggesting a relaunch without the flag feels more explicit, and matches the cookbook ("refuses prompt logprobs by design").
2. It touches common code (`models/deepseek_v4.py`, `deepseek_v4_backend.py`, the shared metadata kernel)

@RolaoDenthu Thanks for the review! Fair points on the silent fallback and the shared code.

On the use case: it's not only a wrong request. A common case is running evals on a server started with the replay on(available in the cookbook). lm-eval-harness tasks like MMLU, HellaSwag and ARC score answers with prompt logprobs (`echo` + `logprobs`). Scoring jobs (perplexity, ranking, RL reference logprobs) need the same. And on a shared endpoint, any client can send such a request by mistake. Today, one of these requests crashes the whole server and drops every request in flight. The main goal of this PR is to stop that.

I'm fine with a 400 as well. If you think rejecting is the better fix, I'm happy to change this PR to do that. Since this PR was the first to report and fix this crash, it would be good to keep the fix here. Let me know what you prefer.
