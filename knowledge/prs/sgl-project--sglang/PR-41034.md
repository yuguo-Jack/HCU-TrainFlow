# [Bugfix] GigaChat3 streaming: stop leaking protocol markers, keep arguments valid

[Upstream PR](https://github.com/sgl-project/sglang/pull/41034) · state: open · merged: False

## Original PR description

## Motivation

`GigaChat3Detector.parse_streaming_increment` disagrees with `detect_and_parse`
in three ways, all reproducible on `main` by feeding one response in deltas of
different sizes. The non-streaming result is the reference for every case below.

**1. Protocol markers are printed as assistant text.** Content is derived from
the *delta* (`REGEX_CONTENT_PATTERN.search(delta_text)`), and when the delta holds
no complete marker the code falls back to `content = delta_text`. A marker that
straddles a delta boundary is therefore emitted verbatim:

```
input   : <|message_sep|>\n\nfunction call<|role_sep|>\n{"name": "manage_user_memory", ...}
streamed: "<|message_sep|>\n\nfunction call<|role_sep|>\n"     <- shown to the user
expected: ""
```

Reproduces at 1, 5 and 13 characters per delta, i.e. for most real framings; only
a delta large enough to contain the whole marker avoided it.

**2. The arguments can arrive as invalid JSON.** The end token is stripped only
when it is complete (`if cur_args.endswith("</s>")`), so an intermediate snapshot
that ends mid-token is emitted as an argument delta. No later delta can repair a
string the client has already concatenated, so the accumulated arguments stay
broken -- which is also why the detector logs its own
`Arguments overlap mismatch` warning:

```
streamed arguments: '{"action": "create", "id": "test"}}</s'   <- not JSON
expected          : '{"action": "create", "id": "test"}'
```

**3. A call completing inside one delta loses its arguments.** The parser sends
the tool name first and the arguments on a later call; there was no `finish()`
override, so with a single delta the client received the call with empty
arguments:

```
input   : <|function_call|>{"name": "manage_user_memory", "arguments": {...}}
streamed: [(0, "manage_user_memory", "")]      (at 145 chars per delta: no call at all)
expected: [(0, "manage_user_memory", '{"action": "create", "id": "preferences"}')]
```

All three are reachable whenever a call completes inside a single delta
(multi-token deltas from speculative decoding / MTP, `stream_interval > 1`) or
whenever a marker is split across deltas, which is the normal case for
character-level streaming.

## Modifications

`python/sglang/srt/function_call/gigachat3_detector.py` (+82/-9):

- **Content comes from the accumulated buffer**, like `detect_and_parse`, and only
  the part before the marker is emitted. A suffix that could still become a marker
  is held until it is decided, and the already-emitted length is tracked so text
  is sent exactly once.
- **A partial end token is held back** instead of being emitted as arguments, so
  the streamed argument string stays a prefix of the cleaned value.
- **`finish()`** drains pending state by re-running the parser with an empty delta
  until a round yields neither calls nor text, following the pattern
  `GigaChat35Detector.finish()` already uses. The empty-delta early return now
  also processes a non-empty buffer, which is what makes the drain possible.

`test/registered/unit/function_call/test_function_call_parser.py` (+99): three
cases in `TestGigaChat3Detector`, all three failing on `main`, parametrized over
chunk sizes 1, 5, 13, 16, 24, 32, 48 and whole-response.

**Reviewer note — why the drain sits in `finish()` and not in the base class.**

There is an open base-class fix for part of this defect class (#32167, "Fix streaming tool calls losing arguments when completed in the final delta"). It does not cover this detector, and the reason is worth recording before anyone has to ask:

- The shared flush path is `FunctionCallParser.parse_stream_end()` -> `detector.finish()`, and **both** streaming entrypoints call it (`serving_chat.py:3030`, `serving_responses.py:2399`). The flush that #32167 extends, `_check_for_unstreamed_tool_args`, exists only in `serving_chat.py` (defined at 3115, used at 945); `serving_responses.py` has no equivalent.
- `BaseFormatDetector.parse_streaming_increment` processes exactly **one** JSON object per call — there is no loop between the `bot_token` search and the Case 1 / Case 2 returns. A delta carrying several complete calls therefore leaves the rest buffered, and registering the single object that was parsed does not recover them; the drain here re-runs the parser until it yields nothing, which does.
- `GigaChat3Detector.parse_streaming_increment` is a fully custom state machine that never calls `super()`, so a base-class registration cannot reach it at all. This detector also differs in kind: the defects fixed here are protocol markers leaking into `content` and invalid-JSON argument tails (`...}}</s`), not only a lost final-delta call.

### Residual: the "arguments overlap mismatch" guard is kept, deliberately

The readiness pass flagged `gigachat3_detector.py:207-212` — the `else` branch that logs
`Arguments overlap mismatch` and returns an empty result — as a branch no input reaches.
Read against the code, it has no reachable input, and I am nevertheless keeping it, which
is a change from how the sibling residual in `qwen25_detector.py` was resolved.

Why it is unreachable: `cur_args` is `ARGS_REGEX.group(1).strip()` taken from the
*accumulated* buffer (`self._buffer += new_text`), and `ARGS_REGEX` is
`'"arguments"\s*:\s*(.*)'` with `re.DOTALL` — a greedy capture to the end of the buffer. The buffer only ever grows, so the
capture only ever extends; the two things that can shorten it are removing a trailing
`</s>` and dropping a trailing `}` when what remains still parses as JSON, and both remove
a suffix rather than mutating the middle. The prefix relation the guard tests therefore
holds by construction, and nine synthetic stream shapes in the earlier round failed to
break it, which is consistent.

Why keep it rather than delete it: the two options are not behaviourally symmetric, which
they were for the `qwen25` case. There the removed line simply never executed, so deleting
it changed nothing. Here, if the branch is ever reached and the guard is gone, control
falls through to `delta_args = cur_args[len(prev_args):]` on a string that is *not* an
extension of `prev_args` — sending the client a nonsense slice of the arguments instead of
a refused one. A cheap refusal plus a warning is the better failure mode for an invariant
this load-bearing, so the branch stays as a defensive assertion of the invariant.

The consequence to be honest about: it remains uncovered by the suite, so it reads as dead
code to a coverage report. Anyone who later wants it gone should first change the fallback
to something safe rather than removing the check outright.
