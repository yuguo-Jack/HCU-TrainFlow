# Prevent scheduler crashes when Mamba checkpoint slots run out

[Upstream PR](https://github.com/sgl-project/sglang/pull/37619) · state: open · merged: False

## Original PR description

## Motivation

Concurrent long prompts can crash the scheduler when an optional intermediate Mamba-state checkpoint needs a replacement slot and the unified cache has no free or evictable slot. The failure is `AssertionError: Can not alloc mamba cache`, rather than a request waiting for capacity.

This PR skips that unfinished-request checkpoint when the pool is exhausted. The request keeps its KV indices and continues without inserting a new checkpoint; successful checkpoint allocation behaves as before.

## Modifications

- Use a non-asserting allocation attempt for unfinished-request checkpoints and return through the existing zero-length cache-insertion path if eviction cannot supply a slot.
- Log the skipped checkpoint at most once per second, including free, evictable and total slots.
- Keep the asserting allocation contract for other callers. The legacy Mamba cache is unchanged.

## Accuracy Tests

2 CPU tests passed, covering exhausted allocation without state donation and successful allocation with the existing donation behavior. The exhausted case fails on unpatched main. The concurrent long-prompt GPU reproducer has not been rerun.

## Speed Tests and Profiling

The fallback runs only after allocation and eviction fail. No speed benchmark was run.

**Incident (2026-09-09 11:12 UTC)**

A single ~140k-token prompt was being chunk-prefilled with only 2 running requests (+1 queued). In one prefill step `mamba usage` jumped from 0.18 straight to 1.00 and the scheduler died:

```

    cl = comp.prepare_for_caching_req(
  File ".../mem_cache/unified_cache/components/mamba_component.py", in _alloc_mamba_slot
```

The container exited and was auto-restarted by the `always` restart policy (full service outage until reload).

**Why I believe this PR covers it**

- Crash site is identical to your fix's call sites: the chunk-boundary donate path in `prepare_for_caching_req` (`chunked=True`), allocation via `_alloc_mamba_slot`.
- Most notably, the pool saturated with only **2 running requests out of a cap of 12** and `evict_for_alloc` freed nothing — consistent with your note that slots can be "locked for a pending host backup" under the HiCache mamba tier, which is exactly the extra held-slot source our config introduces (hicache on, write_through). A ~140k prompt crossing the 64-token track grid repeatedly also matches your cold-95k-prompt starvation pattern.
