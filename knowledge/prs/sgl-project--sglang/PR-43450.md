# [Feature] Forward observer and deferred outputs for out-of-tree consumers

[Upstream PR](https://github.com/sgl-project/sglang/pull/43450) · state: open · merged: False

## Original PR description

## Motivation

Out-of-tree consumers sometimes need per-request forward outputs delivered somewhere other than the HTTP response. Example: SpecForge trains draft models from a target's prefill hidden states, written straight into a Mooncake store.

`SamplingObserver` plus auxiliary outputs (sgl-project/sglang#35747, sgl-project/sglang#39164) already give plugins one batched device-to-host copy and a per-request `consume` before streaming. Two pieces are missing:

1. A sampling observer only sees logits. There is no hook that sees the forward's other outputs (hidden states) together with the batch's requests.
2. `consume` is synchronous. A consumer that publishes asynchronously has no way to keep a finished request from responding before its data is durable. Without that, the client can receive a reference to data that is not stored yet.

Today SpecForge patches about 14 SGLang files for this. These two extension points let it ship as a plugin instead.

## Modifications

**`ModelRunner.forward_observer`** (`model_executor/forward_observer.py`)
- `ForwardObserver.after_forward(batch, forward_batch, logits_output, *, can_run_graph)` runs right after each target forward, on the forward stream, and may return a `DeviceAuxiliaryOutput`.
- The output is stored on `GenerationBatchResult.forward_auxiliary_output`.
- At copy time it is merged with the sampling observer's output via `append_auxiliary_output`, giving one composite copy. `consume` then runs before streaming as today. The non-overlap path copies when either output exists.
- Support matches the sampling observer: non-speculative, non-dLLM, single-PP target runners. Otherwise the setter raises.
- The docstring states the CUDA-graph aliasing rule from `DeviceAuxiliaryOutput`.

**`DeferredOutputSource`** (`managers/deferred_output.py`)
- A consumer sets `Req.defer_output` on a finished request, e.g. in `HostAuxiliaryOutput.consume`, and registers a source with `Scheduler.register_deferred_output_source`.
- The streamer skips held requests. It filters only once a source is registered.
- The scheduler polls sources at the start of `process_batch_result` and in `on_idle`, and streams released requests exactly once.
- `on_idle` yields the GIL while sources exist, like the HiCache and PD paths.
- Held requests don't count against `is_fully_idle()`. Under TP only the rank that streams outputs holds them, and idle-gated operations (`flush_cache`, `release_memory_occupation`, HiCache attach/detach) must see the same state on every rank. A held request has already released its KV cache, so a source must own the data it publishes.
- While a source holds requests, `on_idle` keeps polling instead of sleeping, because a release is not a socket event.
- Registration is rejected under PD disaggregation, whose prefill requests finish and stream from the transfer queues.
- The scheduler's source tuple is a class-level default read through `getattr`, so mixin-based callers of `Scheduler` methods keep working.

## Speed Tests and Profiling

Neither hook does anything unless a plugin installs it. Without one:
- the forward path reads one attribute per forward;
- the streamer reads one flag per `stream_output` call;
- the scheduler checks an empty tuple per iteration.

**`bench_serving` A/B, hooks off.**
- Setup: one GB300, Qwen3.8-27B (hybrid GDN), TP1, bf16, `--mem-fraction-static 0.85 --context-length 8192`, otherwise default flags, `random-ids` datasets.
- Arms: stock main `8c273d6813` vs. main + #43448, #43449 and this PR, with the SpecForge capture plugin installed but inactive.
- Both servers run side by side on two GPUs, and the GPUs are swapped between rounds.
- Each arm runs in its own fresh container. Runs alternate between arms: 3 repetitions × 2 rounds per workload.

| Workload | Metric | main | this stack | Δ | Δ round A / B |
|---|---|---|---|---|---|
| decode: 1024 in / 256 out, 512 prompts, concurrency 128 | output tok/s | 2872.5 ± 26.1 | 2866.4 ± 22.7 | -0.21% | +0.20% / -0.63% |
|  | mean TPOT (ms) | 27.75 ± 0.11 | 27.82 ± 0.11 | +0.23% | -0.22% / +0.69% |
|  | median ITL (ms) | 20.37 ± 0.03 | 20.37 ± 0.02 | +0.01% | -0.01% / +0.04% |
| prefill: 2048 in / 1 out, 256 prompts, concurrency 64 | req/s | 12.17 ± 0.05 | 12.16 ± 0.05 | -0.04% | +0.33% / -0.40% |
|  | mean TTFT (ms) | 4671.6 ± 50.2 | 4674.3 ± 49.4 | +0.06% | -0.26% / +0.38% |

Every difference is within run-to-run spread, and its sign is not consistent across the swapped rounds.

Methodology note: an earlier run gave this branch a container that had first served a hidden-state capture workload. That run showed −4% prefill and −2% decode, and the gap disappeared once both arms had fresh containers.
- The likely cause is Triton autotuning: FLA's GDN kernels mostly leave the token count out of their autotune keys, and `cache_results` persists the chosen config across server starts.
- So whichever workload first tunes a container decides the kernels for later runs.
- A/B comparisons on GDN models need fresh Triton caches for both arms.
