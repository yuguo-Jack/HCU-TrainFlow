# [Fix] GGUF: make the MMQ branch of fused_moe_gguf runnable

[Upstream PR](https://github.com/sgl-project/sglang/pull/43445) · state: open · merged: False

## Original PR description

## Motivation

`fused_moe_gguf` in `python/sglang/srt/layers/quantization/gguf.py` has three branches. The MMQ one (both expert weights in a standard or K-quant type, i.e. `MMQ_QUANT_TYPES`, and more than 64 tokens) cannot run on current main. Any GGUF MoE model with standard/K-quant experts hits it on the first prefill longer than 64 tokens. It fails in two places before any kernel is launched:

1. `BLOCK_SIZE = ggml_moe_get_block_size(qweight_type)` calls `torch.ops.sgl_kernel.ggml_moe_get_block_size.default(type)`. The schema is `ggml_moe_get_block_size(int type) -> int`, with no tensor argument, and the op is registered only for `torch::kCUDA` (`common_extension.cc`) / `torch::kMUSA` (`common_extension_musa.cc`). With no tensor the dispatcher has no key to route on:

   ```
   NotImplementedError: There were no tensor arguments to this function (e.g., you passed an empty list of Tensors), but no fallback function is registered for schema sgl_kernel::ggml_moe_get_block_size.  This usually means that this function requires a non-empty list of Tensors, or that you (the operator writer) forgot to register a fallback function.
   ```

2. `moe_align_block_size` is imported from `sgl_kernel`, which is the raw op wrapper `moe_align_block_size(topk_ids, num_experts, block_size, sorted_token_ids, experts_ids, num_tokens_post_pad, cumsum_buffer, ...)`. It expects the caller to allocate the outputs and returns nothing, so the three-argument call `moe_align_block_size(topk_ids, BLOCK_SIZE, E)` raises:

   ```
   TypeError: moe_align_block_size() missing 4 required positional arguments: 'sorted_token_ids', 'experts_ids', 'num_tokens_post_pad', and 'cumsum_buffer'
   ```

   (The positional order of `block_size` and `num_experts` is also swapped relative to the raw op.) The call matches the signature of sglang's own wrapper, `sglang.srt.layers.moe.fused_moe_triton.moe_align_block_size(topk_ids, block_size, num_experts)`, which allocates the buffers and returns `(sorted_ids, expert_ids, num_tokens_post_pad)`.

The open WIP PR #13451 touches both of these as part of a much larger GGUF MoE change (it re-registers the op without a dispatch key in `common_extension.cc`). This PR is only the narrow fix, and needs no sgl-kernel rebuild.

## Modifications

`python/sglang/srt/layers/quantization/gguf.py` only:

- `GGML_MOE_BLOCK_SIZE`: a Python table `{GGUF type: MOE_X_*}` for the ten types `ggml_moe_get_block_size` handles in `gguf_kernel.cu` (Q4_0, Q4_1, Q5_0, Q5_1, Q8_0, Q2_K..Q6_K). The values are the non-ROCm `MOE_X_*` defines in `quantization/gguf/moe.cuh`, which are 4 for every type. `moe.cuh` has 8 under `USE_ROCM`, but the GGUF ops are not registered in `common_extension_rocm.cc` (and `gguf.py` imports them only on CUDA and MUSA), so there is no ROCm entry. The MMQ branch looks the block size up there instead of calling the op.
- The MMQ branch uses sglang's `moe_align_block_size` wrapper (imported locally from `sglang.srt.layers.moe.fused_moe_triton`, as `mova.py` does). `moe_align_block_size` and `ggml_moe_get_block_size` are dropped from the `sgl_kernel` imports; nothing else in the file used them.
- The MMVQ branch (`ggml_moe_a8_vec`, used for <= 64 tokens and for i-quants) and the per-token fallback are unchanged. The sgl-kernel op itself is left as is.

The wrapper's outputs fit what `ggml_moe_a8` reads: sorted ids padded with `numel` (dropped by the kernel's `col_dst >= ncols_dst` check), expert ids per block of `BLOCK_SIZE` tokens, and `num_tokens_post_pad`. The same sorted ids feed both GEMMs, as before.

## Accuracy Tests

No existing test exercises this path: `python/sglang/kernels/aot/tests/test_gguf.py` imports `ggml_moe_get_block_size` but only tests dequant, MMVQ and MMQ for dense matmuls, and `test/registered/e2e/quantization/test_gguf.py` uses a dense model (Qwen2-1.5B Q4_K_M). I did not add a GPU test here.

To reproduce: serve any GGUF MoE model whose expert weights are a standard or K-quant type (e.g. a Qwen3-30B-A3B Q4_K_M or Q8_0 GGUF) on CUDA and send a prompt longer than 64 tokens. Before this patch the prefill raises the `NotImplementedError` above; with only the block size fixed it raises the `TypeError`.

With this change, the same code path (Q8_0 experts, `ggml_moe_a8` -> `silu_and_mul` -> `ggml_moe_a8` -> topk weights -> `moe_sum`, block size 4, sglang's alignment wrapper) has run the MoE of a 35K-token prompt prefill without error in a downstream tree based on an earlier sglang release.

Checked on CPU against the current sources: the table matches `ggml_moe_get_block_size`'s switch in `gguf_kernel.cu` case by case and the non-ROCm `MOE_X_*` values in `moe.cuh`; both error messages above were reproduced (the first with a tensor-less op registered only for CUDA in a CPU torch build, the second with the `sgl_kernel` `moe_align_block_size` signature).
