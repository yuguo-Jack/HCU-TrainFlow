# feat(kda): integrate FlashInfer prefill checkpoints

[Upstream PR](https://github.com/sgl-project/sglang/pull/41400) · state: closed · merged: True

## Original PR description

## Motivation

[FlashInfer #5021](https://github.com/flashinfer-ai/flashinfer/pull/5021) (0.7.0) adds indexed, floor-aligned checkpoints to CuTe DSL KDA prefill, which SGLang needs for radix prefix caching.

## Modifications

- Opt-in `--linear-attn-prefill-backend flashinfer` for BF16, 128-dim safe-gate KDA on SM100/SM103.
- Map FlashInfer checkpoints to radix-cache track rows (FP32 state pools, padded gate/beta); write only radix-tracked checkpoints.
- KDA models pass raw beta logits in every phase. Kernel adapters own activation, without backend-dependent model flags or model mutation during backend construction. FlashInfer tensor validation runs during warmup.
- Call `flashinfer.kda.recurrent_kda(..., backend="cute-dsl")` directly. FlashInfer owns scheduling and workspace allocation; SGLang maps radix-cache checkpoint destinations once per tracked batch. Invalid scheduler/checkpoint metadata raises an assertion.
- Reject incompatible checkpoint intervals, TBO, and full prefill CUDA graphs at setup. FlashInfer validates safe gates during warmup. BCG keeps linear attention eager; verify uses its separately configured backend.
- Retain Triton fallback for a packed prefill containing only one token, which FlashInfer's current packed-prefill API excludes.

This PR leaves dependency pins unchanged; the current tree already pins FlashInfer 0.7.0.post1.

## Speed Tests

These are historical measurements from the wrapper-based integration. The current direct API can read packed sequence offsets on the host to size its workspace and allocates that workspace within each call; performance and D2H behavior need remeasurement on the latest head.

Kimi K3 NVFP4 dummy weights, 8xGB300 TP8/DCP8, bs1, 131k in / 1k out, 95% prefix hit, A/B/A x10:

| Metric | Triton | FlashInfer |
| --- | ---: | ---: |
| Normal TTFT, median | 0.429 s | 0.411 s |
| Output throughput, median | 406.5 tok/s | 407.4 tok/s |
| KDA GPU time per layer (EXTEND trace) | 421 µs | 219 µs |
| KDA-associated D2H copies | 0 | 0 |

An intermittent ~6.7 s TTFT stall appears with both backends and is not attributed to KDA.

Kernel-only KDA prefill (checkpoints off), K3 shape on one TP8 rank (12 heads x 128), single GB300, bf16 in / fp32 state, median of 5 (ms). Backends that fall back to Triton at these lengths are omitted: `nvidia_kda` (needs >1 sequence), `flashkda` (caps at 2048 tokens/seq).

| Case | Triton | FlashInfer | ptx_kda | cutedsl |
| --- | ---: | ---: | ---: | ---: |
| 16k | 1.18 | 0.87 | 0.72 | 1.51 |
| 32k | 2.09 | 1.37 | 1.13 | 2.67 |
| 64k | 3.95 | 2.38 | 1.94 | 4.94 |
| 128k, one sequence | 7.76 | 4.36 | 3.65 | 9.61 |
| 128k as 8x16k chunks | 3.82 | 1.18 | 2.66 | 7.52 |

FlashInfer is 1.3-1.8x Triton on a single sequence and 3.2x on the 8x16k shape chunked prefill actually issues, where it batches the sequences into one kernel. `ptx_kda` is ~20% faster on a single sequence but 2.3x slower on that chunked shape; it is also not measured here with checkpoints on, which its own fallback note says routes tracked batches to Triton. `cutedsl` cannot serve K3 at all (no safe gate, no interior checkpoints).
