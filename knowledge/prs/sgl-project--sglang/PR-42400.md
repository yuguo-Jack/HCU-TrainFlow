# [Qwen4-Exp] Skip the PLE backing-file rewrite when the on-disk table already matches

[Upstream PR](https://github.com/sgl-project/sglang/pull/42400) · state: open · merged: False

## Original PR description

## Motivation

`--ple-offload-backend file` keeps the 47.7 GiB PLE table in a sparse file that is deliberately reused across restarts: `qwen4_exp_ple_table.py` only creates or truncates it when it is missing or the wrong size. The weight loader, however, still copies every row into that mapping on every boot, in `copy_ple_rows_to_tp_embedding`. Writing into a fresh sparse file is cheap; rewriting a file that is already populated is not.

#39126 flags the consequence in its own description, "populated files are rewritten on boot and can be much slower than fresh sparse files", and recommends deleting `ple_table_*.bin` before each boot. #37068 left automatic management out of scope. #40235 still carries the same caveat in the cookbook it edits. So the current guidance is to throw away 47.7 GiB and write it again on every restart.

On a single DGX Spark (GB10, 128 GB unified memory) that costs:

| | Fresh sparse file | Populated file, rewritten | Populated file, rewrite skipped |
|---|---:|---:|---:|
| load-weight end | 467.7 s (7.8 min) | ~3,200 s (53 min) | 423.4 s (7.1 min) |

The slow path is page-fault bound, not disk bound. It is a synchronous mmap write through 4 KiB faults, confirmed with the major-fault counts in `/proc/<pid>/stat`: the same filesystem sustains 1.1-5.1 GB/s under `dd`, 60-300x the effective PLE write rate.

## Modifications

Before copying a shard, sample random 4 KiB windows of the destination and of the source, and skip the `copy_()` when every sample is byte-identical.

- `_ple_shard_matches()` compares dtype and shape, then 32 sampled 4 KiB windows plus the first and last window, with a seed derived from the shard size. A shard of two windows or fewer is compared in full.
- `copy_ple_rows_to_tp_embedding()` skips the copy only on a match.
- One summary line after loading: `PLE table: N/M shards already on disk (R rows), K copied`.
- `SGLANG_QWEN4_PLE_FILE_REUSE` (default on) and `SGLANG_QWEN4_PLE_FILE_REUSE_WINDOWS` (default 32), declared in `sglang/srt/environ.py` beside the other `SGLANG_QWEN4_PLE_FILE_*` entries.
- `test/registered/unit/models/test_qwen4_exp_ple_reuse.py`: 10 CPU-only cases covering identical shards, a difference in the first and in the last sampled window, wholly different contents, shape and dtype mismatches, the empty shard, the environment switch, the full-compare path for shards of two windows or fewer, and that the verdict does not depend on global RNG state.

This is a content check, not a filename, mtime or size heuristic. A stale, truncated or wrong-revision file fails the sample and falls back to the normal copy, per shard, so the fast path cannot serve wrong weights. Nothing changes for the `pinned` backend, and nothing changes on a first boot, where the destination is zero-filled and every shard is copied as before.

Credit: this is a port of `ple_reuse.py` by Shantanu Goel (shantanugoel/qwen38-flash-next-sglang-dgx-spark, Apache-2.0), who diagnosed the problem and wrote the sampling approach. I opened an issue on his repository before submitting this, setting out exactly this attribution: https://github.com/shantanugoel/qwen38-flash-next-sglang-dgx-spark/issues/1 — the file-backed PLE approach itself traces back to hashd1ve/qwen38-flash-next-one-dgx-spark and #37068.

## Accuracy Tests

The skip cannot change what is loaded unless the sampled comparison returns a false positive. It compares dtype, shape and sampled bytes of the destination against the source the loader was about to write, so a stale, truncated or wrong-revision file fails the sample and that shard takes the normal copy. A first boot, where the destination is zero-filled, copies every shard as before.

Evidence from running this on a DGX Spark rather than from a dedicated A/B:

- On restarts the loader reports every shard as already present and copies none: `PLE table: 128/128 shards already on disk (320001536 rows), 0 copied`. A boot that reports a non-zero `copied` count is the signal that the file did not match, which is also how the 53-minute case is recognised.
- Servers booted this way have been used for the published evaluations on this checkpoint: JamC-QA (2,309 Japanese four-choice questions, 3-shot, exact match) at 64.57% with 0% parse failures, a 3-task vision suite at 100% parse rate on the structured-output tasks, and long Aider Polyglot runs. None of these show the degradation that serving a wrong n-gram table would produce.
- The added unit tests cover the comparison itself.

What I have not done: a bit-exact A/B of logprobs between a forced full copy (`SGLANG_QWEN4_PLE_FILE_REUSE=0`) and a skipped boot. The box is in use and that comparison costs a ~53-minute rewrite boot. I am happy to run it if you would like it before merging — say the word and I will post the numbers.

## Speed Tests and Profiling

Single DGX Spark (GB10, 128 GB unified memory), `--ple-offload-embedding --ple-offload-backend file`, TP1, `senfu/Qwen3.8-Flash-Next-NVFP4`, torch 2.13.0, FlashInfer 0.6.18.

Load-weight end, as in the table above: 467.7 s for a fresh sparse file, ~3,200 s rewriting a populated file, 423.4 s with the skip. The patch does not make the first boot faster; it keeps restarts out of the 53-minute case.

No inference hot-path change: the skip runs during weight loading only. The forward path, the gather kernel and the mapping are untouched.

- xin-osaka-u · comment · 2026-10-09T00:47:45Z · [source](https://github.com/sgl-project/sglang/pull/42400#issuecomment-6071960442)

TP=2 field report in support of this. Setup: 2× DGX Spark (GB10), TP=2 over RoCE, Qwen3.8-Flash-Next NVFP4, file backend, 25.6 GB of PLE file per rank.

We run a reuse scheme close to yours in production. A few findings may be useful for the TP>1 case and for the design:

1. **Per-rank halves work at TP=2 without any collective check.** Each rank's file holds only its own rows. In our run, rank 0 held rows `0–160000768` and rank 1 held `160000768–320001536`. Each rank checks its own half against the checkpoint shards.
2. **A writable shared mapping keeps dirtying pages after load.** Even with byte-identical content, the file's mtime kept advancing for hours, and we saw writeback of about 10 GB over 19 h. GPU pinning (GUP with write intent) marks the pages dirty. On reuse we map the file read-only (`r--s`). After that, mtime stopped changing and the extra writeback disappeared.
3. **Only trust a table that was completely written.** After the first full write we `msync` and `fsync`, then atomically write a sidecar fingerprint. The fingerprint covers the config and quant-config hashes, the PLE shard names, sizes and mtimes, shape, dtype, TP size and rank. If a later boot finds a matching sidecar, it maps the file read-only and samples windows against the checkpoint, much like your `_ple_shard_matches`. A boot that crashed mid-write leaves no sidecar, so the table gets rebuilt.

Measured on that setup, per node:

| | Rebuild (sparse file, full write) | Reuse |
|---|---:|---:|
| Boot to healthy | 514 s | 468 s |
| SSD written per boot | ~29 GB | ~2.7 GB (logs and JIT cache only) |

A full byte-for-byte compare against the checkpoint passed on all 64/64 shards on both ranks. Table hashes were identical before and after reuse, including after serving requests.

So +1 for skipping the copy. I'd also suggest considering a read-only mapping on the reuse path, and a completion marker written after fsync. Happy to share our patch if that helps.
