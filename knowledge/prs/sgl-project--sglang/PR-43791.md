# [DFlash] Decide the Domino candidate pool in one place and apply simulated acceptance inside the accept

[Upstream PR](https://github.com/sgl-project/sglang/pull/43791) · state: open · merged: False

## Original PR description

- `_domino_prefers_tp_candidate_pool` decides whether Domino uses the TP candidate pool; the draft graph and the eager rollout pass whether they run in a captured graph instead of each deciding on its own. The policy is unchanged: the graph uses the pool above batch size 1, eager above the 96 MiB full-logits threshold.
- `SGLANG_SIMULATE_ACC_LEN` is applied inside `_accept_block` through `apply_dflash_simulated_acceptance`, which now also materializes the target argmax the real-draft-token mode needs; the accept returns its final lengths and no longer returns `target_predict`.
- `SGLANG_SIMULATE_ACC_TOKEN_MODE` is checked once at worker init (`check_simulate_acc_token_mode`) instead of on every verify.

Behavior change: an invalid `SGLANG_SIMULATE_ACC_TOKEN_MODE` with `SGLANG_SIMULATE_ACC_LEN` on now fails at startup instead of at the first verify.

## Verification

- Simulated acceptance before and after: byte-identical outputs and RNG state over 320 cases (lengths, methods, token modes, seeds) for the move, and over 160 cases (with and without a precomputed target argmax) for the helper change.
- GB300: Domino kernel and unit tests, lilicorr, DFlash logits and overlap host-sync tests pass; Domino e2e at TP2 passes.
