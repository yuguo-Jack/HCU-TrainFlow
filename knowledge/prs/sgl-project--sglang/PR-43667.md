# [Diffusion] Speed up LTX-2 guidance and video output

[Upstream PR](https://github.com/sgl-project/sglang/pull/43667) · state: open · merged: False

## Original PR description

## Motivation

LTX-2's advanced CFG/STG/modality-guidance branches bypass the existing breakable CUDA graph runner. Video decoding also introduces avoidable channels-last layout copies and full-video CPU conversion work. This PR reduces those costs while preserving eager video and audio outputs.

## Modifications

- Route the existing advanced-guidance calls through the shared BCG runner and preserve guider/LoRA settings during synthetic warmup. Construct mixed perturbation masks on the device so capture does not copy from unpinned host memory.
- Let LTX's fixed-shape, single-GPU SDPA attention stay inside the captured region. Other attention backends, sequence-parallel paths and varlen metadata keep their existing eager breaks. Request-level backend overrides bypass graphs captured with the default backend.
- Extend the existing residual-gate kernel to read one `[B, 1, D]` gate row per batch. Noncontiguous AdaLN gate views copy only the small gate, without expanding it over tokens. FP16/BF16 product/add rounding is unchanged.
- Keep LTX VAE reflection padding in channels-last storage for ordinary CUDA Conv3d. Convert raw-frame output on the GPU in chunks of at most 64 MiB of FP32 data (or one frame), then complete the pinned CPU transfer before returning NumPy storage. Pinned allocation or CUDA conversion OOM falls back to CPU postprocessing. The generic NumPy thread-pool change has been removed.

Merged main through `11bfd868ac36` (#43656): preserve the shared bounded MP4 encoder, audio-first ordering on eligible requests, and encoder fallback. Successful MP4 encoding skips raw-frame materialization; only raw output/fallback calls the chunked postprocessor. No new test files remain: coverage lives in the existing LTX BCG, VAE, frame-output, and modulation suites.

SGLang uses eager + BCG, with torch.compile disabled. BCG still requires the existing enable flag; the VAE/output improvements apply without it.

## Accuracy Tests

- The existing LTX BCG, VAE layout, frame callback/output, video encoding, Wan streamed-encoding and modulation suites pass **1,089 tests / 58 subtests on GB300** at cleanup commit `5c377d8`. After the final fallback-buffer cleanup, the frame-output suite passes again at `dfd8189`: **19 tests / 15 subtests**.
- Coverage retains changed-input/mask replay, request backend fallback, advanced-guidance warmup, batched gates, reflection padding/cache, exact raw-frame conversion, output ownership and MP4/audio fallback ordering. Bounded-conversion and CUDA-conversion-OOM cases extend the existing frame-output suite. All five standalone test files from the initial PR have been consolidated or removed; the existing registered diffusion bridge discovers the retained cases.
- Full-model A-B-B-A regression at final head `dfd8189` against main `11bfd868ac36` checks **32 outputs across two prompts/seeds**. Raw video hashes after canonical RGB8 conversion and audio hashes match the eager controls; all saved MP4 files match byte for byte. Native SGLang execution, actual BCG capture, identical schedules and BF16 untiled decode settings are verified.
- A real CUDA allocator-cap probe uses BF16 `[1, 3, 121, 1024, 1536]` input with 512 MiB of headroom. The previous full-clip FP32 conversion raises CUDA OOM; the chunked path matches the CPU reference exactly with a 1,258,291,200-byte peak under the 1,679,818,752-byte cap. This is a controlled allocator-cap test, not a claim about a physically full production GPU.
- Pre-commit passes. [Targeted H100 CI for the final head](https://github.com/sgl-project/sglang/actions/runs/38147640089) is dispatched separately.

## Speed Tests and Profiling

### Regression after integrating #43656

Compare main `11bfd868ac36` with final head `dfd8189` on the same GB300 and PyTorch 2.14.1+cu130, using the pinned checkpoint and native BF16 recipe below. A-B-B-A uses four fresh processes. Each process runs two prompts/seeds with one warmup and one measurement per prompt in each output mode: 16 timed requests total. The SDK timer includes complete CPU output or complete MP4 writing; evidence hashing is outside the timer. BCG is enabled only for the candidate; torch.compile is disabled in both.

| Output mode | Main A / D median | Candidate B / C median | Paired latency reduction |
| --- | ---: | ---: | ---: |
| Raw CPU video/audio | 30.204 / 30.363 s | 26.595 / 26.578 s | 11.95% / 12.47% |
| Fully written MP4 | 29.673 / 29.657 s | 27.842 / 27.833 s | 6.17% / 6.15% |

The pooled medians improve by **11.97% for raw CPU output** and **6.16% for fully written MP4**. This is a small matched two-prompt regression, not a broad workload performance study. The saved-output comparison includes main's shared bounded encoder; it does not reuse the older baseline numbers below.

### Original benchmark and profiling evidence

The following table records the original implementation against `33d2ef175666`; it is not a benchmark against main after #43656. Updated-main validation is recorded above.

One GB300, resident BF16 weights, uncached text encoding, 1536×1024×121 output at 24 fps. Stage 1 uses 768×512×121 for 40 steps; stage 2 uses three refinement steps. Both frameworks use the same observed sigma schedules, BF16 VAE input and weights, untiled decoding and disabled autocast. CPU affinity is fixed to cores 8–15 on NUMA node 0.

Stage 1 uses video/audio CFG 3/7, STG 1, modality guidance 3, rescale 0.7 and STG block 29. Distilled LoRA strength is 0/1 across the two stages. A benchmark adapter selects these existing request-extra fields in both SGLang baseline and candidate, because the original LTX-2 sampling class does not expose the later per-modality fields.

Each fresh process has nine warmup requests and fifteen measured requests across three prompts/seeds. Run order is stock → candidate → Omni → Omni → candidate → stock. The metric ends when the native SDK returns complete CPU video frames and audio; file saving and evidence hashing are excluded.

| Mode | Repeat 1 median | Repeat 2 median |
| --- | ---: | ---: |
| SGLang eager baseline | 29.984 s | 29.864 s |
| SGLang eager + BCG candidate | **26.161 s** | **26.185 s** |
| vLLM-Omni + regional torch.compile | 26.221 s | 26.242 s |
| Latency reduction vs SGLang eager | 12.75% | 12.32% |
| Latency reduction vs Omni compile | 0.23% | 0.22% |

The cross-framework median advantage is small (about 0.22%); the repeatable within-SGLang improvement is the main performance result. This is a result for the measured workload, not a claim that every prompt or configuration outperforms Omni.

A separate profile confirms one real captured segment for each denoising stage, without signature misses. VAE GPU time falls from 1,048.8 ms to 529.2 ms, with copy-kernel time falling from 546.1 ms to 25.5 ms. Profiled runs are excluded from the latency table; those stage timings are not additive estimates of end-to-end gain.

Native peak reserved GPU memory decreases from 102,350 MiB to 99,222 MiB (−3.05 GiB) in a separate one-warmup/one-measurement diagnostic for the same workload. This diagnostic's latency is excluded from the table.

Omni compilation is verified on all 48 transformer blocks and with nonzero Dynamo graph counters. SGLang and Omni use their supported PyTorch environments, 2.14.1+cu130 and 2.13.0+cu130 respectively; the within-SGLang comparison isolates this PR's gain. Their native noise generators use different packed/unpacked layouts, so matching seeds do not imply cross-framework pixel equality. Exact-output validation compares the candidate against its SGLang baseline.

Revisions: SGLang baseline `33d2ef17566685f596b82512e8264456716527f7`; Omni `194b936637f4e7356cc998c2796c67d14d52d854`; Lightricks/LTX-2 checkpoint `dfcc2108383fe1aaa0584bdf55d368a4bdadd90c`.
