# [Fix] Stop at the earliest matching stop_str when several match

[Upstream PR](https://github.com/sgl-project/sglang/pull/42466) · state: open · merged: False

## Original PR description

## Motivation

When several stop_strs match within the same decode step, `_check_str_based_finish` records the first one in list order instead of the one that appears earliest in the output. `trim_matched_stop` then trims only that string, so an earlier stop string leaks into the response.

Example: `stop_strs=["END", "STOP"]` on output `"... STOP ... END"` records `matched="END"` and leaves `"STOP"` in the text.

## Modifications

- Collect every matched stop string in `_check_str_based_finish` (`schedule_batch.py`) and record the one with the earliest occurrence in the decoded text (ties keep list order; single-match behavior unchanged).
- This addresses the TODO in `DetokenizerManager.trim_matched_stop` about handling multiple matched stop strings.

## Accuracy Tests

New unit test `test/srt/test_multi_stop_str.py` (pure Python, CPU CI) covering single-match regression, earliest-match-wins under both list orders, no-match case, and `trim_matched_stop` end-to-end (trim and `no_stop_trim`).

## Speed Tests and Profiling

Not applicable — O(small constant) per decode step on the CPU-side finish check, off the GPU critical path.
