# [MM] Return owned output from ViT CUDA/NPU graph replays

[Upstream PR](https://github.com/sgl-project/sglang/pull/43315) · state: open · merged: False

## Original PR description

## Motivation

With `SGLANG_VIT_ENABLE_CUDA_GRAPH=1`, `ViTCudaGraphRunner.replay` and `ViTNpuGraphRunner.replay` return `block_output[graph_key]`, the captured graph's static output buffer, which the next replay of the same graph key overwrites. Qwen3-VL returns that buffer as its image and video embedding, and the multimodal scheduler keeps it past the next encode in two places. Both give wrong outputs on main:

1. **Embedding cache.** A single-item cache miss caches the buffer itself, because `MultiModalStaticCache.set` clones only slices that are smaller than their storage. A later image of the same size replays the same graph and rewrites the cached embedding, so the next cache hit for the first image returns the second image's features.
2. **Several multi-span requests in one prefill batch.** Video items are multi-span (frames are separated by timestamp tokens), so `_get_chunked_prefill_embedding` encodes them one request at a time and concatenates afterwards. Every request but the last is merged with a later request's rows.

Repro on Qwen3-VL-8B-Instruct on one GPU, with the cookbook flags plus `--chunked-prefill-size 16384`, greedy decoding:

| Scenario | ViT graph off, main | ViT graph on, main | ViT graph on, this PR |
| --- | --- | --- | --- |
| A red image, then a blue image of the same size, then the red image again behind a different text prefix: answer to the last request | Red | **blue** | Red |
| 8 concurrent videos of the same size in distinct solid colors, 4 rounds: correct colors | 32/32 | **16/32** | 32/32 |

## Modifications

- `replay` returns `out.clone()` unless it already reorders the output with `index_select` (Qwen2.5-VL), which allocates a new tensor.
- The InternVL and Kimi-K3 ViT graph runners pass their output through a projector before it reaches the scheduler, so they are not affected. The eager path is unchanged.
- The ViT CUDA graph doc notes that replay returns a copy.

## Accuracy Tests

MMMU validation (900 questions, `benchmark/mmmu/bench_sglang.py`, greedy). Each run used a fresh server with `--mem-fraction-static 0.5`; at the default, main runs out of memory capturing one graph per image shape on this dataset.

| | Run 1 | Run 2 | Run 3 | Mean |
| --- | --- | --- | --- | --- |
| ViT graph on, main | 0.567 | 0.558 | 0.547 | 0.557 |
| ViT graph on, this PR | 0.554 | 0.563 | 0.563 | 0.560 |
| ViT graph off, main | 0.580 | 0.579 | 0.580 | 0.580 |
| ViT graph off, this PR | 0.583 | 0.584 | 0.584 | 0.584 |

MMMU rarely re-hits a cached image of a repeated size, so the bug does not move its score beyond run-to-run noise. The gap of about 0.02 between ViT graph on and off is present on main as well and is not addressed here.

New unit tests `test_vit_graph_replay_output_survives_the_next_replay` (CUDA and NPU runners) replay one graph twice and check that the first result is intact. Both fail on main.

## Speed Tests and Profiling

The copy costs one write of the encoder output per replay, in ViT graph mode only. Peak allocation inside `embed_mm_inputs` on cache-miss chunks of five 1792x1792 images (15.7K tokens; Qwen3-VL-8B deepstack width 16384), measured in the server after graph capture: 1565 MiB on main, 1960 MiB with this PR. The follow-up #43316, which scatters chunk embeddings without per-batch copies, brings it back to 1565 MiB.

`bench_serving` with `--dataset-name image --image-count 4 --image-resolution 1080p --image-content random --random-input-len 128 --random-output-len 64 --num-prompts 256 --max-concurrency 16`, after a 32-prompt warmup, three fresh-server runs per arm. Mean TTFT (range) and request throughput:

| | main | This PR |
| --- | --- | --- |
| ViT graph on | 2288 ms (2193-2382), 3.30 req/s | 2136 ms (2032-2305), 3.39 req/s |
| ViT graph off | 2030 ms (2014-2057), 3.62 req/s | 2022 ms (1908-2102), 3.56 req/s |

The differences are within run-to-run variation.

Not run: NPU hardware. The NPU change is the same one-line change as CUDA and is covered by its unit test.
