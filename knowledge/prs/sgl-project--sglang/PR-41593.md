# [Scheduler] Refresh waiting requests' cached prefixes under FCFS-like policies with LRU eviction

[Upstream PR](https://github.com/sgl-project/sglang/pull/41593) · state: closed · merged: True

## Original PR description

## Motivation

Under the default `fcfs` policy (and `lof`, `random`, `routing_key`) a waiting request is invisible to radix-cache eviction. Its prefix was last matched when its previous turn ran; while it sits in the waiting queue nothing touches that prefix again until the admission loop in `get_new_batch_prefill` reaches it, and that loop stops at the first request the token budget cannot fit. Eviction is LRU on `TreeNode.last_access_time`, refreshed only by a prefix match, and only admitted requests hold `lock_ref`. So the request that is about to be scheduled is, to the LRU, a session idle since its last turn, and it becomes the eviction victim as soon as it has waited longer than the other live sessions have been away.

Once that happens the loop closes on itself: the request is admitted cold, needs the whole prompt recomputed instead of the new tokens, holds the batch for several chunks, and every request behind it waits longer, ages past the same threshold, and loses its own prefix. One cold prompt arriving at a rank whose cache is full turns into minutes of recomputation on that rank.

The condition is generic: a cache-agnostic policy, an LRU radix cache whose live working set is at or above the pool, and a waiting-queue tail of seconds. Multi-turn traffic with long cached prefixes is where all three meet. `lpm` does not show it only because `_compute_prefix_matches` happens to match every waiting request each round while sorting.

In internal testing of a disaggregated prefill serving multi-turn traffic with long cached prefixes, with the live working set at or above the radix pool, the cache hit rate at admission was flat for requests admitted quickly and fell with time spent in the waiting queue once a request had waited longer than the idle sessions had been away. Requests in the long-wait tail were admitted mostly cold, and a burst of cold admissions on a rank was usually followed by a storm of low hit rates on that rank. With the first version of this change the hit rate stayed flat across the wait distribution. The head commit is measured end to end below.

## Modifications

The refresh only changes eviction order, and only where that order can improve: every other configuration keeps the previous behavior exactly.

- `schedule_policy.py`: after the waiting queue is sorted, `calc_priority` calls `_refresh_waiting_prefixes`, which touches the cached prefix of the first `WAITING_PREFIX_REFRESH_MAX_QUEUE = 128` requests (the depth at which `lpm` already stops matching), tail to head, so the head carries the newest timestamp and eviction follows admission order. Refreshing after the sort makes this hold for `lof`, `random`, `routing_key` and priority scheduling too. It runs only when all of these hold, and is a no-op otherwise:
  - the active policy is cache-agnostic (`fcfs`, `lof`, `random`, `routing_key`, or `lpm`/`hrrn` after their fallback to FCFS above 128 waiting requests); cache-aware policies already refresh as they match;
  - `--radix-eviction-policy lru` (the default); other strategies rank by other keys, and `mru` would evict the refreshed prefixes first;
  - the cache shares prefixes (not `--disable-radix-cache`) and has no fast match path, and the worker is not a decode worker;
  - `SGLANG_ENABLE_WAITING_PREFIX_REFRESH` is on (default); `0` restores the previous behavior;
  - at least `WAITING_PREFIX_REFRESH_INTERVAL_S = 0.5` s have passed since the last refresh. A refresh only has to keep waiting prefixes newer than idle ones, so it need not run every round.
- `common.py`: `refresh_waiting_prefix(tree_cache, req)` builds the key with `_req_radix_key`, shared with `match_kv_cache`, so the refresh touches exactly the path admission will match.
- `base_prefix_cache.py`: `BasePrefixCache.refresh_device_prefix(key) -> None`, a no-op by default. It walks the tree and stamps it; with a host tier it also touches host-backed nodes, but it never allocates, loads, or enqueues lookups on a storage backend or external connector, as `match_prefix` may.
- `radix_cache.py`: `RadixCache.refresh_device_prefix` runs the key preparation of `match_prefix`, then `_match_prefix_helper` on the local tree. Subclasses such as `FlexKVRadixCache` and `PureSWARadixCache` inherit it, so their external lookups are never reached.
- `unified_radix_cache.py`: `UnifiedRadixCache.refresh_device_prefix` runs `tree_core.match_prefix` plus `_apply_cache_actions` for a possible boundary split, skipping the streaming-session shortcut, the cache-level finalizers and the external linker.
- `environ.py`: `SGLANG_ENABLE_WAITING_PREFIX_REFRESH = EnvBool(True)`.
- `test/registered/unit/mem_cache/test_fcfs_waiting_prefix_refresh.py` (CPU, `base-a-test-cpu`), on both `RadixCache` and `UnifiedRadixCache`: the head's prefix survives when eviction must take a waiting prefix; the head is still refreshed with a queue deeper than the bound; the refresh never calls `match_prefix`; it is skipped with the switch off and under `mru`, `fifo` and `lfu`; it is throttled; it follows the sorted order under `lof`. A `ChunkCache` is left alone.
- `test/manual/test_schedule_policy.py`: publish a runtime context in `setUp`, since `calc_priority` reads the disaggregation namespace.

Hit counts (`hit_count`, which LFU and SLRU read) are not touched by the refresh; a split during the walk is bookkeeping only.

Alternatives considered:

- Switching the affected deployments to `lpm` changes scheduling order and fairness to fix an eviction-order defect; `fcfs` is the default and stays the default here.
- Taking `lock_ref` on waiting requests' prefixes would protect them absolutely, but a deep queue could then pin more than the budget and stall admission; refreshing the timestamp keeps every page evictable when nothing else is left.
- A per-node "pending demand" key in the eviction strategy would make the order explicit for every policy and avoid the walks, but it touches every cache implementation; it is left as a follow-up if the walk cost matters.

## Speed Tests and Profiling

End to end on one H200 per arm, `meta-llama/Llama-3.1-8B-Instruct`, default server flags plus `--max-total-tokens` where noted to put the radix cache under pressure. The base is the merge base with main (54b551df8e); both arms ran at the same time with the same client seed. Multi-turn traffic is `benchmark/hicache/bench_multiturn.py --num-clients 128 --max-parallel 128 --request-length 1024 --output-length 128 --num-rounds 8 --request-rate 64 --ready-queue-policy fifo --disable-random-sample --disable-auto-run`, so every pending turn waits in the server queue.

**Issue**

This calls the general request-aware matcher, not an L1-only timestamp refresh. External-cache implementations give that call extra side effects. For example, FlexKV MP calls `lookup_kv` and stores a held task under the request handle on every scheduling round; the next lookup overwrites that entry without cancelling the previous task. FlexKV IP can allocate and load KV immediately. A waiting request can therefore leak lookup tasks or consume KV before admission.

**Fix**

Add a local-device-only refresh operation that cannot call storage/linker code, or skip this refresh for caches whose match has external side effects. Add a test asserting that FCFS refresh never calls the external connector.

**Issue**

This loop stamps the queue head first, so the head's prefix gets the oldest `last_access_time` of all waiting requests. `RadixCache` uses `time.monotonic()` and `UnifiedRadixCache` uses an increasing counter. When eviction must take a waiting prefix, LRU takes the head's prefix first, but the head is the next request FCFS admits.

**Example**

Queue `[A, B]` waits behind a chunked prefill, and no other evictable leaves remain. The next chunk's allocation evicts `A`'s prefix before `B`'s, so `A` is admitted cold.

**Fix**

Iterate `reversed(waiting_queue)` so the head is touched last. Add a CPU test with two waiting prefixes that evicts one leaf and checks that the head's prefix survives.
