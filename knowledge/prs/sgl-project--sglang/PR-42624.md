# [DSpark] Mask uncommitted slots before commit-inject cache lookups

[Upstream PR](https://github.com/sgl-project/sglang/pull/42624) · state: closed · merged: True

## Original PR description

## Motivation

`_commit_inject_layout_kernel` looks up `req_to_token` and then `full_to_swa_mapping` for **every** verify slot, and only afterwards replaces uncommitted slots (`col >= commit_len`, including graph-padding rows with `commit_len == 0`) with `-1`. The second lookup uses the first lookup's value as an address, so a stale or garbage `req_to_token` entry in a discarded slot is still dereferenced. Writing `-1` afterwards does not undo that read.

In practice this rarely goes out of bounds, because `req_to_token` is zero-initialized and stale entries are usually still valid locations. That is also why the existing parity test, whose random entries are all in range, never caught it.

## Modifications

- Triton kernel: compute `committed = mask & (c < commit_len)` first and use it as the load mask for both lookups (`other=0` and `other=-1`). Positions are still written for every slot.
- Torch reference (`build_commit_inject_layout`): stop going through `assign_extend_cache_locs_func` and index `req_to_token` directly. Uncommitted rows and columns are clamped to 0 with `torch.where`, so the result has a fixed shape (no data-dependent boolean indexing, no host sync), matching `build_unified_commit_inject_layout`.
- Test: in the existing `commit_len` edge case of `test_dspark_kernel_parity.py`, the uncommitted row's `req_to_token` entries are set to `1 << 40`, far beyond the mapping, and the case now also checks Triton/torch parity.

## Accuracy Tests

On B300 (CUDA 13.0, torch 2.13), running this branch:

- `test/registered/spec/dspark/test_dspark_kernel_parity.py`: 1 passed, 22 subtests passed. The commit-inject case also runs clean under `compute-sanitizer --tool memcheck` (0 errors). On unpatched `main`, the same test fails with `CUDA error: an illegal memory access`.
- Standalone poison driver (commit_lens 0 / 2 / full) under `compute-sanitizer --tool memcheck`:

| Kernel | memcheck | `swa_loc` |
|---|---|---|
| unpatched `main` | **8 errors** (`Invalid __global__ read`) | n/a |
| this PR | **0 errors** | `[-1]*7`, `[10, 11, -1, ...]`, `[10..16]` (as expected) |

- Earlier, on a downstream branch, the same masking gave GSM8K 1278/1319 vs a 1281/1319 baseline.

No throughput claim. The kernel now skips two loads for discarded slots.
