# fix(attention): dispatch hybrid-model full-attn layers by call form in FA backend

[Upstream PR](https://github.com/sgl-project/sglang/pull/42333) · state: open · merged: False

## Original PR description

## Description

Fixes #42012.

Glm5Next-style hybrid models interleave linear-attention (KDA) layers with full-attention layers whose `RadixAttention` calls arrive in **plain-MHA form**: `q/k/v` share the head count (verified live: `q=k=v=(T, 8, 256)`) and `q_rope` is absent, backed by a per-token **single-latent-head** KV pool (`(N, 1, 512)`).

The FlashAttention backend routes every call through the backend-level `use_mla` flag when the model family is MLA-enabled, so those MHA-form calls entered the absorbed-MLA path and carved a zero-width rope slice out of the latent cache:

```
RuntimeError: shape '[-1, 64, 8, 0]' is invalid for input of size ...
              page_size × tp_k_head_num × (head_dim − v_head_dim = 0 for NoPE)
```

crashing at the first decode CUDA-graph capture. The fix routes **by call form**: when `q_rope` is absent and `k` carries the same head count as `q`, take the standard MHA path regardless of `use_mla`. Absorbed-MLA calls keep `k` as a single latent head (or pass `q_rope`) and never match the predicate, so DeepSeek-style MLA behavior is unchanged. Applied at the three routing sites (forward_extend, its save path, forward_decode).

## Validation (end-to-end, same setup as the issue)

8x RTX PRO 6000 (SM120), GLM-5.3-Flash FP8 TP8, `--attention-backend fa4`, docker image built 2026-09-18 (v0.5.20-equivalent) with the identical change bind-mounted:

| | before | after |
|---|---|---|
| engine init | crash at first decode-graph capture (`shape '[-1, 64, 8, 0]'`) | healthy, capture passes |
| correctness | — | `17×19=323` + reasoning chain correct; generation clean |
| single-stream decode | — | 84.6 tok/s (3 runs stable) |
| ~3K-token prefill | — | ≈88 tok/s |

Triton on the same config measures 82.4 tok/s decode / ≈88 tok/s prefill, so the patched fa4 path is on par with the previously-only-working backend on this model; neither is the limiting factor for the hybrid model's overall throughput on SM120.

Two operational notes discovered along the way:
- FA4 CuTe rejects FP8 inputs below SM100 (`AssertionError: FP8 is only supported on SM100`), so on SM120 this checkpoint needs `--kv-cache-dtype bf16` to serve through fa4 — a separate kernel-support constraint, unchanged by this PR.
- With bf16 KV, `fa_k_descale`/`fa_v_descale` still get threaded and the CuTe interface rejects descale args for non-FP8 inputs (`q_descale/... only supported for FP8 inputs`). The v0.5.20 validation tree additionally guards the descale kwargs by cache dtype; I kept this PR minimal (routing fix only) but can fold that guard in if maintainers prefer it handled here.

## Test Plan

- Serve any Glm5Next checkpoint on SM120 with `--attention-backend fa4 --kv-cache-dtype bf16`: init/capture succeeds, output correct (validated above).
- DeepSeek-family MLA regressions: absorbed calls are structurally excluded from the new predicate (single-latent-head `k` or explicit `q_rope`); happy to run any standard MLA smoke the team uses.
