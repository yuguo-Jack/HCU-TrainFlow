# [GLM-5.3-Flash] Overlap prefill TP all-reduces across two microbatches

[Upstream PR](https://github.com/sgl-project/sglang/pull/43655) · state: open · merged: False

## Original PR description

## Motivation

On PCIe GPUs without NVLink, GLM-5.3-Flash prefill at TP4 spends much of its time in tensor-parallel all-reduces. In a profile of a 32K-token prompt (4x RTX PRO 6000 Blackwell Max-Q, FP8, TP4, 8192-token chunks), NCCL all-reduce was 45% of GPU time: 64 MB per call, 4.2 ms each. Prefill runs one request's chunk through each layer and then waits for that layer's all-reduce, so the GPUs compute nothing while it runs.

Splitting the chunk in two lets one half's all-reduce run while the other half computes. In an isolated test of a 4096-row MoE layer, an all-reduce running under the next half's MoE took a layer from 4.78 ms serially to 3.13 ms; the MoE alone took 2.61 ms.

## Modifications

- New `prefill_mbo` module, enabled with `SGLANG_PREFILL_MBO=1` (default off).
  - A single-request extend of at least `SGLANG_PREFILL_MBO_MIN_TOKENS` tokens (default 4096) is split at a 256-aligned absolute position into two child batches. The 256-token alignment keeps KV pages, k-pool groups and KDA chunks of both halves aligned.
  - Each child batch has its own attention backend instance and metadata. Mamba track fields go to the child that reaches the tracked length.
  - Each half's attention and FFN partial sums are all-reduced on a side stream, over a dedicated NCCL group created at startup on the TP ranks. The summed tensor is recorded on the side stream, so its memory is not reused before the all-reduce ends even if a forward is abandoned.
  - A batch whose mamba track mask lacks its CPU metadata is not split.
- The halves run layer by layer through the existing two-batch-overlap stage executor:
  - `operations_strategy` gives `Glm5NextDecoderLayer` an attention stage and an FFN stage per layer, only while a split prefill is active; other GLM-5-Next two-batch-overlap requests still raise `NotImplementedError`.
  - The split state is cleared in a `finally`, so a failed forward does not leave it active.
  - The executor records which microbatch is running.
  - It accepts batches without DP padding fields.
- mHC keeps `h_res` and `h_post` per microbatch, because the two halves interleave within a layer.
- Only models that implement `supports_prefill_mbo()` take part. GLM-5-Next does when all of these hold:
  - the model uses mHC;
  - PP is 1;
  - attention TP equals TP (no DP attention or attention CP) and decode context parallelism is off;
  - MoE EP is 1;
  - no auxiliary hidden states are captured (EAGLE3 or DFlash);
  - no DSA layer reuses another layer's top-k indices, which the stages do not carry between layers;
  - the model has MoE layers after its dense layers, which run through the stage executor.
- Draft workers, CUDA graph capture and batches with more than one request are never split.

## Accuracy Tests

Author runs on 4x RTX PRO 6000 Blackwell Max-Q (PCIe Gen4, no NVLink, 250 W). Model: `zai-org/GLM-5.3-Flash` FP8 at TP4/EP1 with FP8 KV, 8192-token chunks and EAGLE 3/1/4. Each comparison ran in the same session on the same machine.

- **Prompt logprobs.** Mean absolute per-token difference over 14.6K-token and 36.5K-token prompts:

  | Comparison | Mean absolute difference |
  |---|---|
  | Two baseline servers | 0.077-0.079 nats |
  | Overlap vs baseline | 0.084-0.090 nats |
  | Baseline at 4096-token vs 8192-token chunks | 0.085-0.094 nats |

  The overlap's difference from baseline is the same size as changing the chunk size.
- **Long-context GSM8K.** 100 questions, each behind its own ~11K-token document: 99/100 with the overlap, 97/100 without.
- **Retrieval.** A 6-digit code in a 600K-token prompt was found at depths of 5%, 50% and 95% (3/3).
- **Full GSM8K.** A release build with the overlap on scored 1,280/1,319 (temperature 0, final numeric answer extracted). The build without the overlap scored 1,278/1,319.
- **Unit tests.** `test_prefill_mbo.py` (CPU) covers:
  - the GLM-5-Next gate conditions, and the `enabled()` check (env, draft worker, model support);
  - split-point alignment and eligibility, including a refused split without CPU track metadata;
  - the GLM-5-Next stage list, and that it is refused when no split is active;
  - mHC coefficients across interleaved microbatches.

## Speed Tests and Profiling

Same setup as above. TTFT is measured from a single streamed request and covers cold prompts. Each side ran 3 repetitions in the same session; the first 8K request of each side, which was a warmup, is excluded.

| Prompt | Baseline | `SGLANG_PREFILL_MBO=1` |
|---|---|---|
| 8K | 8.36-8.45K tok/s | 10.65-10.68K tok/s |
| 32K | 8.57-8.59K tok/s | 10.58-10.69K tok/s |
| 128K | 8.41-8.43K tok/s | 10.17-10.20K tok/s |
| 1,040,434 tokens (1 run) | 135.4 s | 109.6 s |

Further results from the same setup:

- **Concurrent long prompts.** Wall time, all requests completing with 0 errors:
  - 16 concurrent 60K-token requests: 122.6 s → 100.9 s.
  - 8 concurrent 120K-token requests: 121.4 s → 102.4 s.
- **Images.** 8 concurrent requests with 24 large images each (fixed seed): 323.8 s → 285.5 s.
- **Unchanged.** Decode throughput (C1 74.3 target forwards/s, C4 37.0-37.3), the KV pool size and free memory after graph capture (3.51 GB per GPU) were the same with and without the overlap.

A later release build with the overlap on ran the same cold prompts, 5 requests per size. It measured 10.13-10.62K prompt tok/s at 8K-128K, which matches the A/B.

At TP2 with 4096-token chunks (same GPUs, a W4A16 checkpoint), the overlap was slower: 32K cold prefill measured 5.83K tok/s with it, against 6.07-6.18K without. Each half has only 2048 tokens there, and the two-rank all-reduce is cheaper. That is why this PR leaves the overlap off by default.

The measurements ran on main `3831e7e0` with unrelated local patches needed to serve this checkpoint on SM120. This branch is the same change rebased onto current main. After the measurements, it gained the model gate and the safeguards listed above: the side-stream `record_stream`, cleanup in a `finally`, the strategy restriction and the track-metadata check. Of these, only `record_stream` and a per-layer check that the declared sum group is the TP group run on the measured path. Both add host-side bookkeeping and no GPU work; this branch itself was not re-measured.
