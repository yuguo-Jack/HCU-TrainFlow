# [Refactor] Declare every model's stages from a shared function and drop the meta-device neighbour build

## Motivation

#43459 lets a model give `make_layers` its shared declaration function and keeps a transitional list of models that still had their pipeline neighbours built on the meta device. This PR gives every remaining model that declares stages such a function and removes the meta-device path.

## Modifications

- **Shared declaration functions, one commit per model or family**, each taking the rule that chose a declaration out of the built module and into a function of the config, the layer index, construction options known before the layer is built, and the fixed parallel topology; the layer declares itself with the same function:
  - LLaDA2, MiMo-V2, MiniMax-M2, MiniMax-M3, Mixtral, Nanbeige, SDAR, Spark 2.5, Step-3.5, xLLM, Sarvam MLA;
  - Apertus / Arcee, Bailing, dots3, Ernie 4.5 VL MoE, EXAONE MoE, GLM-4 MoE, GPT-OSS, Kimi Linear, Laguna;
  - the shared and special decoder layers: Llama, Qwen2 / Qwen3, the Qwen2-MoE family, DeepSeek-V2, GLM-4, Gemma 4, GraniteMoeHybrid, EXAONE 4.0, ZAYA1, DeciLM (where a model picks the layer class, the function lives on the class);
  - Kimi K3, GLM-5-Next, Qwen3.5 and Qwen4-exp, whose declarations had been read from built modules (K3's dense MLP group and latent MoE, Qwen4-exp's MLP type and PLE). The rules those modules are built with are now functions shared by the module and the declaration; K3's SP collective is settled once by the model before its layers are built and passed in. `AttnBankState.facts`, `MHCState.facts` and `GatedResidualState.facts` give what their reads and updates declare without the modules.
- **Read pipeline neighbours only from the shared declaration function.** The transitional list, `building_neighbour_layer` / `is_building_neighbour_layer`, the neighbour rebuild, and the resource skips it needed (MoE dispatcher, KT expert wrapper, MiniMax-M2's fused QK norm, Qwen4-exp's PLE offload) are removed: every layer a rank builds is a layer it runs. A model that declares stages under PP without a function fails at construction; every model that builds its layers with `make_layers` under PP has one.

Every moved rule is the expression it replaces, reading the config or the same server args instead of the built module.

## Compatibility

A model that declares stage boundaries and runs under pipeline parallelism must now give `make_layers` / `make_pp_layers` its shared declaration function (`stage_facts`); without one, construction fails with an error naming the model, instead of building the neighbouring layers on the meta device. Every in-tree model that builds its layers with `make_layers` under PP gives one; an out-of-tree model integration that declares stages needs to do the same (see the layer boundary developer guide). Models that do not declare stage boundaries, or that do not run under PP, are unaffected.

## Accuracy Tests

How the stack is checked:
- **Unit tests**: the 39 layer-boundary test files pass at the head of every PR in the stack, apart from the two AMD-only `test_aiter_allreduce_fusion_amd` cases that fail on NVIDIA on main too; the test files that changed most recently pass on every commit. The full `test/registered/unit` suite (926 files, one process per file) shows no failure on the stack's head that main does not have.
- **Plan comparison**: an out-of-tree harness binds every stage plan for seven stack shapes (decoder layers with and without an output transform, MHC, Nemotron-H patterns, Kimi K3, Qwen4-exp, NemotronNAS-style attention-only layers, single-stage appends) over 23 parallel configurations, four boundary reductions and one or two pipeline ranks (3,928 scenarios), and compares each bound plan leaf by leaf with the parent commit's.
- **GPU**: dummy weights are seeded per TP rank and scaled (0.05, norms 1.0), so that a sum taken twice or a mixture of rank partials changes the output; the default dummy weights give every rank the same shard and would hide both.
- GPU results below were measured on these commits as based on main `516fd1c1b5` unless marked as on the merge candidate; rebasing onto current main had no conflicts, and the CPU checks were run again after it.
- **On the merge candidate** (head of this stack against main `961bcf481d`, H200, asymmetric dummy weights unless noted): DeepSeek-V2-Lite input-scattered PP2 is bit-identical to PP1 (main crashes on it); Nemotron-H cut between a mixer and its FFN differs from PP1 only at the rounding level of the FFN-to-mixer cuts (main: 0.93 and 2.21); Llama, Qwen3-MoE, GPT-OSS and DeepSeek-V2-Lite are bit-identical to main at PP1 and PP2; GSM8K (real DeepSeek-V2-Lite weights, 250 questions, TP4 with attention DP2 and the dense FFN fully data-parallel) gives 0.360 at PP2, 0.364 at PP1 and 0.368 on main at PP1, medians of three runs whose run-to-run spread is 0.012–0.016. The last revision of the stack changed only comments, docstrings, an equivalent condition and explicitly set attributes after these runs; its bound plans are identical.

For this PR:
- Plan comparison before and after the migration: the 3,168 non-K3 scenarios and all 728 constructed Kimi K3 scenarios are identical.
- GPU A/B, before the migration against this PR's head, TP2 PP2, all bit-identical, and PP2 repeat runs bit-identical: Llama, Qwen3, Qwen2-MoE, Qwen3-MoE, Mixtral, GLM-4-MoE, DeepSeek-V2-Lite (with and without input-scattered attention), GPT-OSS, MiniMax-M2, Kimi Linear, Nemotron-H, Qwen3.5 (synthetic 4–8 layer configs, H200) and Kimi K3 (B200). No model failed the per-layer check against its function at startup.
- Kimi K3 on B300 with its tuned SP collective (TP4 and TP8, DeepEP, custom all-reduce, CUDA graph decode, attention-residual bank, `SGLANG_K3_SP_ATTN_RES` 0 and 1; GB300 tuning tables copied under the B300 device name): every rank reports the collective enabled and the tuned kernels accept the calls; the outputs are bit-identical to main and to main before Kimi K3 moved onto layer boundaries (666da4f56b with #42895 applied), and per-layer prefill inputs match in all compared layers. A deliberately doubled sum in the tuned path changes the outputs, so the comparison can see a wrong sum.
- Kimi K3 on B200 (synthetic 6-layer config, hidden 7168, attention-residual bank on; GB300 tuning tables copied under the B200 device name), comparing this stack, main and main before Kimi K3 moved onto layer boundaries:
  - Tuned SP collective, TP4, DeepEP, custom all-reduce, `SGLANG_K3_SP_ATTN_RES` 0 and 1: all runs fall in one bitwise cluster across the three trees, apart from one main run 1 bf16 ulp off at layer 1 whose repeats rejoin it; call counts of every tuned kernel match.
  - Decode context parallel, TP4 with attention DP2 and DCP2 (`a2a`, `fi_a2a`, `ag_rs`; DeepEP and the standard dispatcher), and DCP2 alone: bit-identical across the trees. DCP with prefill CP fails the same way on all three (`KimiK3LinearModel.forward()` does not take `input_embeds`).
  - Chunked prefill under PP (TP2 with PP2, 16-token chunks, at least two micro-batches in flight; cuts 3+3 and 4+2, `ar` and `rs`, decode graph on and off): bit-identical across the trees wherever it runs, and PP2 matches PP1 except with the decode graph on, where all three trees differ the same way. A 3+3 cut with the decode graph on, and dynamic chunking with PP2, fail identically on all three.
  - A deliberately doubled attention sum at layer 1 changes the outputs on every path.

## Speed Tests and Profiling

A pipeline rank no longer builds its neighbours' layers on the meta device at startup. No forward-path change.

Kimi K3 on B200 on the merge candidate against main (TP4, DeepEP, custom all-reduce, tuned SP collective, attention-residual bank, CUDA graph decode, three runs per tree): prefill of 4,096 tokens takes 23.4 ms against 23.7 ms (`SGLANG_K3_SP_ATTN_RES=0`) and 23.4 ms against 23.3 ms (`=1`); decode throughput at batch 1, 16 and 64 differs by less than the run-to-run spread; peak allocated (90.912 GiB per rank), steady-state memory and the KV pool size are identical.
