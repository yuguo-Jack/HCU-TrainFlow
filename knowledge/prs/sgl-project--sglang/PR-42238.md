# [Perf] Reduce multi-detokenizer router IPC sends

[Upstream PR](https://github.com/sgl-project/sglang/pull/42238) · state: closed · merged: True

## Original PR description

## Motivation

In a multi-tokenizer/multi-detokenizer deployment, `MultiDetokenizerRouter`
currently converts each scheduler output batch into one message per request.
Each request is serialized and sent separately, even when multiple requests in
the same scheduler batch have the same target detokenizer.

This creates serial Python and IPC overhead in the single router process. Under
sustained decode-only workloads, the output path can become a bottleneck,
causing the scheduler `Batchsize` to stay below the available CUDA Graph
capacity and form a deep sawtooth pattern. `#prealloc-req` can also remain
close to zero for extended periods.

This PR is related to #42217.

## Modifications

- Group requests from one `BaseBatchReq` by the existing target selected by
  `_pick(http_worker_ipc)`.
- Construct one `BatchTokenIDOutput`, `BatchStrOutput`, or
  `BatchEmbeddingOutput` sub-batch per target detokenizer.
- Preserve the original request order within each target group.
- Preserve each request's `http_worker_ipc` ownership value.
- Send each grouped sub-batch once to its target detokenizer.
- Do not merge requests across separate scheduler messages.
- Keep single-request, empty-batch, control-message, and broadcast-message
  behavior unchanged.
- Fall back to the existing per-request path when a payload cannot be sliced
  exactly.
- Construct all grouped sub-batches before the first grouped send, preventing
  partial grouped sends followed by duplicate fallback sends.
- Keep send-time exceptions propagating without resending the batch.

The change is limited to the following path:

Scheduler -> MultiDetokenizerRouter -> Detokenizer

It does not modify the Detokenizer -> TokenizerWorker path, HTTP worker
connection allocation, or `SO_REUSEPORT` behavior.

## Accuracy Tests

This change only changes the batching and IPC-send strategy between the
scheduler output path and detokenizer workers. It does not change token
sampling, decoding, routing decisions, or model computation.

No model accuracy test is required for this change.

## Speed Tests and Profiling

The optimization targets the number of serialization and IPC-send operations
performed by `MultiDetokenizerRouter`.

A controlled DSV4 decode-only A/B test on the multi-tokenizer/multi-detokenizer
topology showed the following observations:

- Client throughput: `33,035.76 -> 42,334.27 token/s`
- Total elapsed time: `2,402.25 s -> 1,874.60 s`
- Per-rank Batchsize p50: `187 -> 310`
- Per-rank average Batchsize: `186.73 -> 285.67`
- Scheduler-to-router p50 latency: `89.88 s -> 11.30 ms`
- Router CPU utilization p50: `127.5% -> 43.9%`
- Router sends per scheduler batch: approximately `180 -> 10.8`

These measurements were obtained from the earlier controlled test environment
and are included as diagnostic evidence for the bottleneck. They are not
claimed as universal gains for all workloads or hardware configurations.

Local unit tests cover:

- Mixed target ownership.
- Target grouping and per-target ordering.
- Preservation of `http_worker_ipcs`.
- Latest `msgspec.Struct` output fields.
- `BatchTokenIDOutput`, `BatchStrOutput`, and
  `BatchEmbeddingOutput` handling.
- Conservative fallback behavior.
- Send exception propagation.
- Pickle IPC enabled and disabled configurations.
