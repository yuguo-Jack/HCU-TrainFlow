# [Feature] Add --config-format alias for --model-config-parser (Mistral vLLM parity, part 1 of #28020)

[Upstream PR](https://github.com/sgl-project/sglang/pull/30141) · state: closed · merged: False

## Original PR description

## Summary

Adds `--config-format` as a vLLM-parity CLI alias for the existing `--model-config-parser`. Closes part 1 of #28020.

Motivated by #28020, which asks for the vLLM-style Mistral invocation

```bash
python3 -m sglang.launch_server \
  --model-path mistralai/Mistral-Small-4-119B-2603-NVFP4 \
  --config-format mistral \
  --load-format mistral \
  --tokenizer-mode mistral
```

to work verbatim on SGLang. The three flags map as follows on today's `main`:

| Flag from the vLLM invocation | Status on `main` |
| --- | --- |
| `--load-format mistral` | Works — `LoadFormat.MISTRAL` branch is wired in `python/sglang/srt/model_loader/loader.py`; auto-detected by `_is_mistral_native_format()` when the checkpoint ships `params.json` + `consolidated*.safetensors` and no `model-*.safetensors`. |
| `--config-format mistral` | Same feature exists under a different name: `--model-config-parser mistral`. Users copy-pasting the vLLM command hit an unknown-flag error. |
| `--tokenizer-mode mistral` | Choices are `["auto", "slow"]`. Not implemented — deferred, see below. |

This PR is the small, safe half — the CLI alias. `--tokenizer-mode mistral` needs a `mistral_common.tokens.tokenizers.mistral.MistralTokenizer` adapter into the `PreTrainedTokenizer` API, which is a separate change with its own review surface. Will open the follow-up under the same issue.

## Approach

`config_format: Optional[str]` on `ServerArgs`, default `None`. If set at parse time, `_handle_config_format()` (new) reconciles it into `model_config_parser` before the dummy-model short-circuit in `__post_init__` — so a conflict is caught even for dummy/none models — and before `_handle_load_format`, which relies on `model_config_parser` being finalized.

Reconciliation rules:

1. `config_format=None` → no-op. `model_config_parser` retains whatever was passed (default `"auto"`).
2. Input normalized: `.strip().lower()`. `--config-format="  Mistral  "` and `--config-format=MISTRAL` both become `mistral`.
3. Empty / whitespace-only after normalization → treated as not passed (no-op). Prevents `--config-format=""` from silently producing an unregistered parser name.
4. `config_format=X`, `model_config_parser="auto"` → `model_config_parser = X`.
5. `config_format=X`, `model_config_parser=Y` (both explicit, different, comparison case-insensitive) → `ValueError`. Explicit-conflict errors are more useful than a silent last-wins winner. `"auto"` is compared as a literal value on the `config_format` side — `--config-format=auto` together with an explicit `--model-config-parser=hf` also raises.
6. `config_format=X`, `model_config_parser=X` → accepted (no-op after propagation).
7. Side effect: `config_format="mistral"` + `load_format="auto"` → sets `load_format = "mistral"`. Mirrors vLLM's behavior — users who pass only `--config-format mistral` (as several Mistral docs pages show) still get Mistral weight loading. Explicit non-`auto` `load_format` values are respected.

`config_format` is a separate field rather than an `Arg(aliases=["--config-format"])` on `model_config_parser` specifically so passing both flags with conflicting values raises rather than silently letting whichever appears last on the command line win. Documented inline.

## Peripheral

`get_config()` in `utils/hf_transformers/config.py` raises a `ValueError` for `model_config_parser not in ("auto", "hf")` when the input is a GGUF file. Updated that error message to mention `--config-format` alongside `--model-config-parser`, so users who hit it via the alias recognize the flag name.

## Tests

`test/registered/unit/server_args/test_server_args.py` gains `TestConfigFormatAlias` with twelve cases covering every reconciliation state above, plus a regression test that confirms `_handle_config_format()` runs before the dummy-model short-circuit (so `ServerArgs(model_path="dummy", config_format="mistral", model_config_parser="hf")` still raises).

Tests follow the existing `SimpleNamespace` + `ServerArgs._handle_config_format(ns)` pattern to isolate the alias logic from `prepare_server_args` side effects — the alternative of driving reconciliation via `prepare_server_args` would need a real Mistral checkpoint on disk to exercise the "config_format=mistral" propagation path, since the Mistral config parser downstream would otherwise fail on a non-Mistral model.

Registered under `base-a-test-cpu` (unchanged from the file's existing `register_cpu_ci`).

## Alternatives considered

- **Rename `--model-config-parser` → `--config-format` with a deprecation shim.** Rejected: breaking, and `model_config_parser` is a more descriptive name for SGLang's plugin registry — the vLLM name is only useful as a copy-paste target.
- **Silently prefer one flag on conflict.** Rejected: hides misconfigurations. Erroring makes the intended value explicit at server boot.
- **`Arg(aliases=["--config-format"])` on the existing field.** Rejected: silent last-wins semantics on conflict, no way to distinguish "user passed both flags with matching values" from "user only passed one." Separate field lets the reconciler see both intents.
- **Ship `--tokenizer-mode mistral` in the same PR.** Rejected: the real work is adapting `mistral_common.MistralTokenizer` (or a similar direct load path) into `get_tokenizer()`, which is bigger than a CLI alias and worth its own review. Filed as follow-up.
