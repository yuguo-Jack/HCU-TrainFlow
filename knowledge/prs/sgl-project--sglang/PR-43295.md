# [MegaMoE][Kimi-K3] Implement the mxf4xmxf4 pre-dispatch branch in _forward_mega_experts

[Upstream PR](https://github.com/sgl-project/sglang/pull/43295) · state: open · merged: False

## Original PR description

## Motivation

`_mega_moe_mma_type()` already selects packed-fp4 (`mxf4xmxf4`) for mxfp4 quant, but `kimi_k3.py::_forward_mega_experts` only ships the fp8 pre-dispatch, so `--moe-a2a-backend megamoe` on an mxfp4 target cannot serve. This ports the mxf4 branch `mega_moe.py` already carries (same split, same buffer geometry the allocator produces: hidden/2 packed rows). Tracking issue with full findings: https://github.com/sgl-project/sglang/issues/43294

## Modifications

One file (+27/−10): in `_forward_mega_experts`, route `mma_type == "mxf4xmxf4"` through `deep_gemm.mega_moe_pre_dispatch` (which emits E2M1-packed activations) and keep the existing sglang JIT FP8 pre-dispatch for `fp8xfp4`; the else-branch preserves the original call byte-for-byte. `nvfp4xnvfp4` is unchanged/out of scope (K3 checkpoints are mxfp4; it was equally unreachable before this PR).

**Sequencing:** (a) safe to merge now — the new branch is inert on `fp8xfp4`, and `SymmBuffer.mma_type` + `mega_moe_pre_dispatch(..., mma_type=)` already exist in the pinned `sgl-deep-gemm==0.2.1.post1` wheel; (b) the mxf4 path activates once sgl-project/DeepGEMM#100 ships in an sgl-deep-gemm release and the pin is bumped (happy to file that bump); (c) until then an mxf4 attempt fails at DeepGEMM's explicit situ assert instead of today's opaque TensorMatcher error.
