## Original PR description

# [metrics] Export radix cache size gauges (entry count + total tokens)

## Motivation

There is no direct metric for "how much is currently in the cache" / "roughly how many
requests can it hold". Operators can see pool-level `kv_*` numbers, but not the radix
tree's own footprint (node count) or total cached tokens as a single value. This adds two
footprint gauges, aligned with #15699.

## Modifications

- `RadixCache.get_cache_stats() -> (entry_count, total_tokens)`:
  `total_tokens` from the incrementally-maintained `evictable_size_ + protected_size_`
  (O(1), exact device-resident tokens); `entry_count` from an O(n) traversal of
  non-evicted nodes.
- Two gauges on `RadixCacheMetricsCollector` (`multiprocess_mode="mostrecent"`):
  `sglang:cache_entry_count`, `sglang:cache_total_tokens`, plus `set_cache_size()`.
- The scheduler pushes them from the **throttled** metrics path
  (`SchedulerMetricsMixin._log_radix_cache_size`, called next to `_log_hicache_stats()`
  in both the prefill and decode stats reporters), guarded by `hasattr` + `try/except`
  so footprint reporting can never break the scheduler loop. The O(n) traversal only runs
  at the metrics-log cadence, never on the request hot path.

Files:
- `python/sglang/srt/mem_cache/radix_cache.py`
- `python/sglang/srt/observability/metrics_collector.py`
- `python/sglang/srt/observability/scheduler_metrics_mixin.py`

## Coverage / limitations

`get_cache_stats()` lives on `RadixCache` (inherited by `HiRadixCache` / `LMCRadixCache`).
Other tree caches without the method are a graceful no-op (the `hasattr` guard) and left
as follow-up.

## Test process (verified on a live deployment)

- Engine: `sglang` v0.5.12 (cu129), model **MiniMax-M2.7**, `tp=8/ep=8` on 8×GPU,
  `--enable-metrics --enable-hierarchical-cache`.
- Relaunched with `--max-total-tokens 40000` so the footprint numbers are easy to
  sanity-check against the pool size.
- Sent a batch of `/generate` requests to populate the radix tree, waited one
  metrics-push interval, then `curl localhost:30000/metrics`.
- Before the patch, `cache_entry_count` / `cache_total_tokens` did not exist in `/metrics`.

## Key logs / sample output (real, captured)

```
sglang:cache_entry_count{cache_type="HiRadixCache"}   69
sglang:cache_total_tokens{cache_type="HiRadixCache"}  38757
```

`cache_total_tokens` (38757) tracks the ~40000-token KV pool as it fills, and
`cache_entry_count` (69 nodes) lets you derive average prefix length / fragmentation
(`38757 / 69 ≈ 562 tokens/node`). Together with `rate(sglang:evicted_tokens_total[5m])`
this gives the effective cache horizon (capacity ÷ churn).

- chenkaiyue · comment · 2026-07-01T11:49:53Z · [source](https://github.com/sgl-project/sglang/pull/28508#discussion_r3505606218)

File: `python/sglang/srt/mem_cache/radix_cache.py` · line None

OK, you're right. The decode path is gated by decode_log_interval, but the prefill path calls this on every prefill batch, so the O(n) walk can add up on a large tree. Fixed in the latest commit:

entry_count_ is now maintained incrementally at the node create/delete sites (_split_node / _insert_helper / _delete_leaf in RadixCache, plus the HiRadixCache overrides _insert_helper / _insert_helper_host / _split_node / evict_host, and the extra insert path in LMCRadixCache). get_cache_stats() is now O(1) and no longer traverses the tree.

One deliberate semantics note: the old traversal skipped evicted nodes. For RadixCache this is identical; for HiRadixCache the incremental counter now reports the total number of tree nodes (including host-only/device-evicted nodes still resident in the tree), which I think matches the cache_entry_count intent better. The docstring reflects this.

Verified on a real serving image (sglang, tp deployment): a randomized reconciliation of the incremental counter against a fresh O(n) traversal matched at every step across 4000 ops × page_size 1/4/8, and the counter drains back to 0 after full eviction.
