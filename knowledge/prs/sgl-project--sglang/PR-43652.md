# [diffusion] Reject unservable LLaDA-Image edits at request validation

[Upstream PR](https://github.com/sgl-project/sglang/pull/43652) · state: open · merged: False

## Original PR description

## Motivation

Two kinds of LLaDA-Image edit requests pass request validation and are then refused inside the worker, so the client receives a 500 response with a bare Internal Server Error body while the server stays healthy. An edit at 1920x1920 fits the 32768-row sequence limit only if the caption is left out, and an edit with more than one source image is refused only after the text encoder has already run.

## Modifications

- Count the caption's 256 query tokens and one text token in the editing size bound, so the bound matches the check the DiT makes for short prompts. A 1920x1920 edit is now rejected while 1888x1888 is still admitted.
- Reject more than one source image for a single prompt when the sampling parameters are built. Prompt lists and prompt files keep pairing one image with each prompt for offline generation.
- Extend the existing validation test with the new size boundary and the two-image case.

## Validation

- The extended unit test fails before this change and passes with it, and the other LLaDA-Image config tests pass.
- Across every editing size on the 32-pixel grid, the sizes that are newly rejected are exactly those the DiT refuses for every prompt, and every size that stays admitted runs with the shortest prompt.
- On one GPU with LLaDA-Image-Turbo, the 1920x1920 edit and the two-image edit now return 400 with these messages instead of 500.
  - `LLaDA-Image editing at 1920x1920 needs at least 32977 sequence positions, above the model limit of 32768`
  - `LLaDA-Image editing takes exactly one source image, got 2`
- Edits at 1888x1888 and 1024x1024 and text to image requests still succeed, health stays 200 after every refusal, and 14 text to image and edit requests return byte-identical images before and after the change.

## Limits

A prompt long enough to push an otherwise admitted edit past the sequence limit is still refused inside the worker with a 500 response, because request validation does not tokenize the prompt.
