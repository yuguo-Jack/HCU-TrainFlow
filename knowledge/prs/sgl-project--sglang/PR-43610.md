# [Feature] Add optional fastapi-guard security middleware

[Upstream PR](https://github.com/sgl-project/sglang/pull/43610) · state: open · merged: False

## Original PR description

Closes #43609

## Motivation

The core HTTP server has auth (`--api-key`) but nothing at the request layer: no rate limiting, no IP controls, no payload screening. The gateway covers this for deployments that have one (and its docs note rate-limit state is per-worker, suggesting Redis for production), but bare-server deployments have nothing. This PR adds the opt-in middleware built on [fastapi-guard](https://github.com/Guard-Core/fastapi-guard), per the discussion in #43609.

## Modifications

- New `sglang/srt/entrypoints/guard_integration.py`: env-driven fastapi-guard wiring (`attach_guard(app)`, `_build_guard_config()`). The module imports without torch (same discipline as `srt/utils/auth.py`) so it stays unit-testable. Opt-in via `SGLANG_GUARD_ENABLED`; unset means no-op with zero imports and zero overhead. Enabled-but-not-installed fails loudly with the install command
- `environ.py`: flat `SGLANG_GUARD_*` family in the "HTTP server and health" section (`EnvBool`/`EnvInt`/`EnvStr`, mirroring the neighbors)
- `http_server.py`: one `attach_guard(app)` call right after the CORS/request-decompression block, following the `SGLANG_ENABLE_REQUEST_DECOMPRESSION` env-gated lazy-import precedent
- `python/pyproject.toml`: new `guard` extra (`fastapi-guard>=8.1.0,<9.0.0`) so the core dependency set doesn't grow
- When enabled: IP block/allow lists (CIDR), rate limiting with auto-ban, user-agent blocking, penetration-attempt detection, passive/log-only mode, IPInfo geo/cloud-provider blocking (via `SGLANG_GUARD_IPINFO_TOKEN`), Redis-backed shared counters and bans (`SGLANG_GUARD_REDIS_URL` - relevant under `--tokenizer-worker-num > 1`, where each worker is a separate process)
- Health, metrics and server-info paths are excluded from detection checks so orchestrators can probe; global IP lists still apply on them

## Accuracy Tests

Not applicable - the middleware does not touch model outputs, tokenization, or sampling paths.

## Speed Tests and Profiling

Not applicable when disabled (the default): the flag-gated branch imports nothing and attaches no middleware, so the hot path is unchanged. When enabled, the added overhead is the guard screening pass (IP-list lookup, rate-limit counter, pattern scan), which is O(request) small-constant work in Python and off the GPU path entirely; profiling on a serving workload would measure it alongside network noise. Happy to run the standard benchmark suite if maintainers want numbers for the enabled case.

## Test plan

- New `test/registered/unit/entrypoints/test_guard_middleware.py` (registered CPU test, `CustomTestCase` + `register_cpu_ci`, no GPU): disabled-by-default no-op, fail-loud without the package, blocked IP 403, rate-limit 200/200/429, passive mode never blocks, Redis-off default. Env state is snapshotted/restored per test; each scenario uses its own TEST-NET client IP because guard's rate-limit state is process-wide
- Module behavior validated against fastapi-guard 8.1.0 (blocked 403, 200/200/429, passive 200, defaults sanity)
- isort (7.0.0) + ruff (0.15.1, repo select list) + ruff-format clean; pre-commit isort hook satisfied
