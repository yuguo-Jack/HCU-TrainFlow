# [NPU] Avoid boolean index assignment in PyTorch top-k/top-p sampling

[Upstream PR](https://github.com/sgl-project/sglang/pull/43525) · state: open · merged: False

## Original PR description

## Motivation

With the PyTorch sampling backend on Ascend NPU, zeroing filtered probabilities through boolean indexing (`x[mask] = 0.0`) expands a dense mask into explicit indices (`NonZero` + `IndexPutV2`) and performs expensive indexed writes. `masked_fill_` applies the same dense mask directly (`MaskedFill`).

## Modifications

Replace the top-k, top-p, and min-p boolean index assignments in `top_k_top_p_min_p_sampling_from_probs_torch` with `masked_fill_`. The masks, operation order, and sampling parameters are unchanged; only these three assignments differ.

The function is shared by every device that uses the `pytorch` sampling backend, so the change is device-agnostic and semantics-preserving. The performance numbers below are measured on Ascend NPU only; CUDA performance was not tested.


## Accuracy Tests

- **NPU, function level:** 12 cases covering batch sizes 1/5/10, probabilities produced from FP32/BF16 logits, heterogeneous top-k/top-p values, and min-p enabled/disabled. With the NPU RNG reset to the same seed, sampled IDs, filtered weights, their token permutation, and selected weights match exactly between the two implementations.
- **NPU, micro-benchmark:** all nine cases (top-k alone, top-p alone, and both filters, at batch 1/5/10) produce exactly equal outputs.
- **CPU:** 200 random batches with random top-k/top-p/min-p values produce identical filtered weights between the two implementations.

Not tested: request-level seeded sampling, CUDA performance, 910B3/CANN 9.0.

## Speed Tests and Profiling

**Isolated micro-benchmark** (Ascend 910C, CANN 9.1, FP32 probabilities, vocabulary size 248,320, top_k=20, top_p=0.95). It compares `tensor[mask] = 0.0` with `tensor.masked_fill_(mask, 0.0)` on identical tensors and precomputed top-k/top-p masks, and needs only PyTorch and torch_npu:

| Batch | Boolean index assignment, both filters | `masked_fill_`, both filters |
| --- | ---: | ---: |
| 1 | 2.3930 ms | 0.0180 ms |
| 5 | 9.3492 ms | 0.0217 ms |
| 10 | 18.1574 ms | 0.0290 ms |

**End-to-end** (Ascend 910C, CANN/ATB 9.1, 40-layer Whittle-Next-26B-A3B W8A8 model, TP=1, vocabulary size 248,320):

| Workload | Before | After |
| --- | ---: | ---: |
| Fixed B=10, input=20, output=100: median streaming ITL | 60.6 ms | 31.9 ms |
| vLLM benchmark, concurrency=1: mean TPOT | 25.04 ms | 20.18 ms |
| vLLM benchmark, concurrency=5: mean TPOT | 47.80 ms | 33.79 ms |
| vLLM benchmark, concurrency=10: mean TPOT | 75.06 ms | 47.65 ms |

These end-to-end numbers come from a locally optimized model/runtime. They do not establish the same speedup for other models, devices, or an unmodified upstream server.

<details>
<summary>Micro-benchmark methodology</summary>

Each value is the median of three repeat measurements, with five warmup iterations and twenty timed iterations per method. Method order alternates between repeats. Timing uses synchronized wall time averaged over repeated writes on one NPU stream; allocation, mask construction, softmax, sorting, correctness checks, and profiler export are excluded. This measures assignment cost, not isolated single-call latency or full-sampler/model speedup. The top-k mask selects 99.992% of positions for zeroing; the synthetic top-p mask selects approximately 25.9%, which can differ from real model distributions.

A separate profile executes six writes per method and confirms six `NonZero` plus six `IndexPutV2` kernels for boolean indexing, versus six `MaskedFill` kernels for the replacement.

</details>

<details>
<summary>End-to-end benchmark setup and profile details</summary>

Serving benchmark: official vLLM v0.21.0 benchmark source, `openai-chat`, seed 10978, `ignore_eos`, random input/output means 20/100, and random range ratio 0.5 (input 10-30, output 50-150). Temperature is left unspecified, so the server uses model defaults: temperature=1, top_k=20, top_p=0.95. Request counts are 10/50/100 for concurrency 1/5/10. Before values average three runs; after values average two runs in opposite concurrency orders. All 320 after-patch requests succeeded, with output-token totals matching the original per-concurrency request lists.

Profiles: each contains exactly eight B=10 decode replays, with 2,594 compute tasks per replay and no prefill steps. Model graph execution span remains about 31 ms, while the mean replay start interval drops from 61.55 ms to 32.79 ms. The 16 dense-mask `NonZero`/`IndexPutV2` operations attributable to the two sampling filters disappear; small scheduler indexed writes remain. Profile export blocks the server, so profiled wall-clock request durations are excluded from the benchmark comparison.

</details>
