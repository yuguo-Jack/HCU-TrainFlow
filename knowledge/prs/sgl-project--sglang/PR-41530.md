## Motivation

Enable the existing PLE offload options on Ascend NPU for Qwen4-Exp / Qwen3.8-Flash-Next:

- `--ple-offload-embedding`
- `--ple-offload-backend pinned|file`
- `--ple-offload-dir` for the file backend

The CUDA gather path reads the host table through device-accessible pointers and uses CUDA streams. The NPU path needs explicit host row selection and device copies. It also needs to execute the lookup with fresh IDs on every decode graph replay; performing the host lookup only during capture would reuse stale rows.

## Modifications

- Add an NPU host gather path: copy lookup IDs to CPU, normalize them to int64 on the host, select this TP rank's rows, zero out non-local IDs, and copy BF16 rows through pinned staging into the device output buffer. Reuse the existing pinned/file storage and file prefetcher.
- Use `get_device_module()` for PLE prefetch streams and synchronization.
- Add `NPUHostOffloadGraph` to capture device graph segments around host lookups. Each replay alternates graph segments and fresh host callbacks, retains the input/output buffers, and preserves per-segment attention dispatch updates.
- Integrate segmented capture into `NPUCudaGraphBackend`. Detect host-offload modules on the first capture, when the model is available; preserve the ordinary graph path for models without host lookups.
- Keep PLE graph breaks on the capture stream by skipping side-stream prefetch during NPU capture. Reject unsupported raw capture, torch-compile, and graph memory-saver combinations explicitly.
- Add single-device and full-model manual tests for pinned/file gathers, shard boundaries, repeated and empty IDs, output buffer reuse, prefill-sized lookups, file persistence, changed-ID graph replay, and graph input updates.

## Accuracy Tests

**Test environment:** Ascend910 A3, TP8 using eight NPU dies, CANN 9.1.0, torch 2.10.0 / torch_npu 2.10.0.post6, and triton-ascend 3.2.2. Full-model tests used the BF16 Qwen3.8-Flash-Next checkpoint, Ascend attention, and `--mamba-ssm-dtype bfloat16`.

Validation was performed on integration checkout `d645e0819`, which includes this PR's head `c6497d039` and PR #37570.

The full-model validation also depends on the Qwen3.8-Flash-Next operators from [sgl-kernel-npu #807](https://github.com/sgl-project/sgl-kernel-npu/pull/807): QSA, PLE short convolution, and hyperconnection. The container's stock sgl-kernel-npu 2026.9.0 did not include `sgl_kernel_npu.qwen3_8_flash_next`, so we built and installed a local integration checkout. The tested kernel was `ed2daf6d`: the PR [sgl-kernel-npu #807](https://github.com/sgl-project/sgl-kernel-npu/pull/807) branch merged with upstream main via `e06de0a2`, plus a short-conv constexpr integer-arithmetic fix for triton-ascend 3.2.2. The results below refer to this tested kernel snapshot, not the current head of [sgl-kernel-npu #807](https://github.com/sgl-project/sgl-kernel-npu/pull/807).

Full-model manual serving tests used local harness adjustments for an independent port, the A3 BF16 SSM flag, and an EOS-aware check of the repetitive prefill prompt. That prompt returns first-token EOS with PLE both off and on, so the check requires output token IDs and a positive completion count instead of non-empty text. These harness adjustments are still uncommitted in the test checkout; the file-backend pass results reflect that setup.

## Speed Tests and Profiling

Measured PLE off/on on the same checkpoint, TP8 devices, attention backend, BF16 SSM state, and decode graph configuration. Requests used deterministic prompts, `temperature=0`, and `ignore_eos=true` to keep output lengths equal. Startup was excluded; the following rates use client wall-clock time.

| Workload | PLE off | PLE pinned on | On/off |
| --- | ---: | ---: | ---: |
| Single request: 512 output tokens, median of 3 trials | 25.263 tok/s | 25.130 tok/s | 0.9947 (-0.53%) |
| 8 concurrent requests: 1,024 output tokens each, median of 2 trials | 132.176 tok/s | 131.204 tok/s | 0.9926 (-0.74%) |

Individual batch trials ranged from 125.28–139.07 tok/s with PLE off and 124.98–137.43 tok/s with PLE on. Both modes used NPU decode graphs, with approximately 147 aggregate tok/s in steady decode logs. These short-context measurements show no material slowdown from enabling pinned PLE within the observed variation; very long contexts and file-backend throughput were not covered by this comparison.

A separate exploratory pinned-PLE graph/eager probe, using one warm-up and five 128-token trials, measured median throughput of **23.91 tok/s with decode graphs versus 3.85 tok/s eager**. On the real model, all eight TP ranks reported **2 graph segments around 1 host lookup**.

The full GPQA run generated 3,273,695 output tokens. Its eight-request decode batches typically sustained about 95–97 aggregate tok/s, so the long evaluation time is consistent with the generated token volume; this is not an off/on performance comparison.

Both off/on measurement files are complete. The performance runner reported a cleanup failure because its original 60-second exit check expired; a subsequent check confirmed that the test server, listener, and NPU processes had exited. The helper's wait was increased to 120 seconds afterward. No profiler trace was collected.
