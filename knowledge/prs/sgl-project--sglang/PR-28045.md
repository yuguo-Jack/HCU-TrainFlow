## Motivation

Building on [#21599](https://github.com/sgl-project/sglang/pull/21599) and [#24055](https://github.com/sgl-project/sglang/pull/24055), SGLang already has the core infrastructure for adaptive speculative decoding: `SpecRuntimeState` for atomic runtime switching, per-candidate CUDA graph / attention backend management, and batch-size-aware step activation.

However, the current default strategy (EMA + hysteresis) still has practical limitations, **especially when deployment conditions vary — quantized models, MoE architectures, non-NVIDIA hardware, or speculative algorithms like DFlash that change the draft/verify cost profile**:

- **Manual tuning**: rise/drop thresholds and dead zones must be hand-tuned and do not generalize well across hardware, models, or speculative algorithms.
- **No cost awareness**: decisions are driven only by historical accept length, without measuring the actual overhead of draft / verify / draft-extend under different batch sizes.
- **Load mismatch**: the same accept rate can imply different optimal steps when decode latency changes with batch size or hardware.

This PR adds a **throughput-aware** policy as an alternative strategy (`--speculative-adaptive-strategy=throughput_aware`). It:

1. **Profiles decode cost at startup** via real-path dummy runs (draft + verify + draft-extend), building a `(batch_size, num_steps) → latency` table on the actual hardware.
2. **Tracks per-position acceptance rates** at runtime with a sliding window (shared across batch sizes).
3. **Selects the step count** that maximizes `score(S) = E[tokens | S steps] / cost_ms(batch_size, S)`, combining observed acceptance with profiled cost.

This gives adaptive speculative decoding a more hardware- and load-aware decision path, while reusing the existing `AdaptiveController` runtime-state switching machinery from the prior PRs.

### Throughput-aware policy

In online serving, **throughput** is output tokens divided by end-to-end latency. In speculative decoding, we focus on **decode-step throughput**: how many tokens each decode batch produces per unit time.

One decode step with `k` draft tokens produces at least 1 token (from verify), plus extra tokens from accepted drafts. Its latency is roughly one decode batch:

```
cost(k, b) ≈ draft(k, b) + verify(k+1, b) + draft_extend(k, b)   (~ ITL)
```

So decode throughput for step count `k` at batch size `b` is:

```
throughput(k, b) ≈ E[tokens | k] / cost(k, b)
```

This is the **score** we optimize — for each batch, pick the `k` that maximizes it.

- **`E[tokens | k]`** — expected output tokens per decode step when drafting `k` tokens. Estimated at runtime from per-position acceptance rates: `E[tokens | k] = 1 + p[0] + p[1] + ... + p[k-1]`.

- **`cost(k, b)`** — latency of one decode step at batch size `b`. Measured at startup via real-path profiling (draft + verify + draft_extend) and stored in a `(batch_size, k)` cost table.

```bash
--speculative-adaptive --speculative-adaptive-strategy throughput_aware
```

### Example: Qwen3.5 + MTP

| Scenario | output throughput (tok/s) | mean ITL (ms) | avg accepted length (AL) |
|----------|---------------------------|---------------|--------------------------|
| baseline | 103.08 | 9.65 | 1 |
| speculative (fixed k) | 241.61 | 17.34 | 4.2 |

**Baseline (no speculation):** each step outputs 1 token and costs ~9.65 ms:
```
throughput ≈ 1 / 9.65 ms ≈ 0.10 tok/ms ≈ 103 tok/s
```

**Speculative decoding:** each step outputs ~4.2 tokens on average, but costs ~17.34 ms:
```
throughput ≈ 4.2 / 17.34 ms ≈ 0.24 tok/ms ≈ 242 tok/s
```

## Architecture

### Inheritance chain

```
BaseSpecWorker
└── EAGLEWorkerV2
    ├── adaptive_controller: AdaptiveController | ThroughputAwareAdaptiveController | None
    ├── build_adaptive_runtime_state()  → SpecRuntimeState
    └── apply_runtime_state()           → swaps draft/verify/extend backends + CUDA graphs

_SpecAdaptiveBase                          ← shared state registry + _activate()
├── AdaptiveController                     ← EMA decision (AdaptiveSpeculativeParams)
└── ThroughputAwareAdaptiveController      ← throughput decision
    ├── PositionAcceptanceTracker          (acceptance history)
    ├── BatchSizeCostTable                 (profiled ITL cost)
    └── run_profiling() → SpecProfilingSession
```

Both controllers share `_SpecAdaptiveBase` for runtime state switching; only the decision logic differs. `ThroughputAwareAdaptiveController` does **not** inherit `AdaptiveController`, so it does not pull in EMA params.

### Call chain

**Startup (cost table profiling)**

```
run_scheduler_process()
  └── scheduler.maybe_run_spec_startup_profiling()
        └── EAGLEWorkerV2.run_startup_spec_profiling(tree_cache)
              └── ThroughputAwareAdaptiveController.run_profiling(tree_cache)
                    ├── _build_profile_grid()          # (steps, bs) grid from cuda_graph_bs + config
                    ├── _activate(steps)               # switch STS before each profile point
                    └── SpecProfilingSession.measure() # prefill → warmup → timed decode
                          ├── _broadcast_float_from_rank0(avg_ms)  # sync cost across TP ranks
                          └── BatchSizeCostTable.set(bs, steps, avg_ms)
```

**Runtime (step selection)**

```
Scheduler event loop
  └── EAGLEWorkerV2.forward_batch_generation()          [decode path]
        └── activate_step_by_batch(batch_size)
              └── ThroughputAwareAdaptiveController.activate_step_by_batch()
                    ├── _should_reevaluate()?          # batch_count % update_interval == 0
                    │     └── _reevaluate_and_switch() # score candidates → update _current_steps
                    └── _activate(_current_steps)      # apply STS if needed
                          └── EAGLEWorkerV2.apply_runtime_state(SpecRuntimeState)

  └── EAGLEWorkerV2.on_verify_complete_cpu(accept_lengths, batch_size)
        └── ThroughputAwareAdaptiveController.on_verify_complete()
              └── PositionAcceptanceTracker.update()   # data collection only; no step switch here
```

Based on the review suggestions, I refactored the adaptive speculative decoding flow to share one controller across different strategies. The strategy is now selected from `--speculative-adaptive-config`, so the separate `speculative_adaptive_strategy` argument has been removed. `AdaptiveController.from_config()` creates either the existing EMA policy or `ThroughputAwarePolicy`, while `EAGLEWorkerV2` only provides the runtime-state build and apply operations.

`AdaptiveController` now owns the common lifecycle, including runtime-state initialization, step activation, verification feedback, and optional startup profiling. `ThroughputAwarePolicy` only handles acceptance tracking, profiling plans, cost-based scoring, and step selection. The EMA and throughput-aware policies also share `AdaptiveStepRouter` for batch-size routing, candidate-step lookup, and CUDA graph batch-size selection.

The current structure is:

```text
EAGLEWorkerV2
    -> AdaptiveController.from_config()
         -> AdaptiveSpeculativeParams (EMA)
         -> ThroughputAwarePolicy

AdaptiveController
    -> init/build/apply runtime states
    -> run startup profiling
    -> activate_step_by_batch()
    -> on_verify_complete()

AdaptiveStepRouter
    -> candidates_for_batch()
    -> cuda_graph_bs_for_step()

ThroughputAwarePolicy
    -> acceptance tracker
    -> profiling plan and cost table
    -> scoring and step selection
```

Catching general exceptions and silently returning `value` in a distributed collective operation (`dist.broadcast`) is highly risky. If one rank encounters an exception (e.g., due to device allocation or group retrieval issues) while other ranks do not, the non-failing ranks will enter the collective broadcast and hang indefinitely. It is safer to let the exception propagate so the system fails fast and cleanly, or use a more robust synchronization mechanism.

```python
def _broadcast_float_from_rank0(value: float) -> float:
    """Broadcast a float from TP rank 0 to all ranks; no-op when TP=1 or dist not active."""
    if not dist.is_initialized():
        return value
    from sglang.srt.distributed import (
        get_tensor_model_parallel_world_size,
        get_tp_group,
    )
    if get_tensor_model_parallel_world_size() <= 1:
        return value
    t = torch.tensor([value], dtype=torch.float64,
                     device=get_tp_group().device)
    dist.broadcast(t, src=0, group=get_tp_group().device_group)
    return float(t.item())
```

If any individual request fails to free (e.g., due to an exception in `kv_alloc.free` or `pool.free`), the loop will terminate prematurely, leaving the remaining requests in `reqs` unfreed. Wrapping the loop body in a `try...except` block ensures that all requests are attempted to be cleaned up, preventing potential memory leaks in the token/KV pool.

```suggestion
    def _teardown(self, reqs: List[Req]) -> None:
        pool = self._worker.req_to_token_pool
        kv_alloc = self._worker.token_to_kv_pool_allocator

        for req in reqs:
            if getattr(req, "req_pool_idx", None) is None:
                continue
            try:
                # free_mamba_cache needs req_pool_idx; call before pool.free().
                if (
                    getattr(req, "mamba_pool_idx", None) is not None
                    and hasattr(pool, "free_mamba_cache")
                ):
                    pool.free_mamba_cache(req)
                end = max(int(getattr(req, "kv_allocated_len", 0)), int(req.fill_len))
                kv_indices = pool.req_to_token[req.req_pool_idx, :end]
                kv_alloc.free(kv_indices)
                pool.free(req)
            except Exception as e:
                logger.error(f"Failed to free request {req.rid} during profiling teardown: {e}")
```

![medium](https://www.gstatic.com/codereviewagent/medium-priority.svg)

If `pn > p0` due to noise in the sliding window, `alpha` will be `> 1.0`, leading to an extrapolated rate that is even larger, potentially exceeding 1.0. Clamping the extrapolated rate to `[0.0, pn]` ensures that the acceptance rate is non-increasing and physically valid. Additionally, if `p0 <= 0`, returning `0.0` is safer than returning `None` because if we return `None`, `get_expected_tokens` will return `None` and we won't be able to score candidates.

```suggestion
    def _get_rate_or_extrapolate(
        self, k: int, known_rates: list[float]
    ) -> Optional[float]:
        """Window mean if available; else geometric extrapolation from known_rates."""
        real = self._best_rate(k)
        if real is not None:
            return real
        if not known_rates:
            return None
        if len(known_rates) == 1:
            return known_rates[0]
        # p[i] = p[0] * alpha^i  ⟹  alpha = (p[N-1] / p[0])^(1/(N-1))
        p0, pn = known_rates[0], known_rates[-1]
        if p0 <= 0:
            return 0.0
        alpha = (pn / p0) ** (1.0 / (len(known_rates) - 1))
        return max(0.0, min(pn, pn * alpha))
```
