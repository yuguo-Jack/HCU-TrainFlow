# Skip fully-masked KV tiles in sliding-window extend attention

[Upstream PR](https://github.com/sgl-project/sglang/pull/39769) · state: open · merged: False

## Original PR description

## Motivation

On a sliding-window layer, the stage-2 loop in `_fwd_kernel` sweeps the extend KV from 0:

```python
for start_n in range(0, extend_end, BLOCK_N):
```

The window mask inside that loop keeps `(q, kv)` only when `q <= kv + SLIDING_WINDOW_SIZE`, so every tile lying entirely below `cur_block_m * BLOCK_M - SLIDING_WINDOW_SIZE` is fully masked and contributes nothing.

Those tiles do not read K/V and do not run the dot — `SKIP_TILE` already guards that. What they still pay, once per tile, is the cost of establishing that they contribute nothing: building `final_mask` (the causal compare, the window compare, the `&`), and then the `[BLOCK_M, BLOCK_N]` cross-wave `tl.max` reduction that computes `SKIP_TILE` itself.

On a long extend with a small window that is the majority of the loop. At `extend_len = 8192` and `W = 127`, the last M block's floor sits at roughly `8192 - 127`, so almost every iteration is spent proving that the tile is empty.

## Modifications

Start the loop at the `BLOCK_N`-aligned tile that contains the window floor:

```python
extend_start = 0
if SLIDING_WINDOW_SIZE > 0:
    extend_start = (
        tl.maximum(cur_block_m * BLOCK_M - SLIDING_WINDOW_SIZE, 0) // BLOCK_N
    ) * BLOCK_N
for start_n in range(extend_start, extend_end, BLOCK_N):
```

The bound is derived from the mask predicate rather than estimated. The kernel returns early when `cur_block_m * BLOCK_M >= cur_seq_len_extend`, so `offs_m = 0` is always a live row and the smallest query index in the block is exactly `m0 = cur_block_m * BLOCK_M`. A skipped tile satisfies `start_n + BLOCK_N <= floor_aligned <= m0 - W`, hence its largest key index `start_n + BLOCK_N - 1 < m0 - W`, so the window mask is false for every one of its elements.

It is also tight at tile granularity: the preceding tile would need `floor_aligned >= m0 - W + 1` to hold a surviving element, which contradicts `floor_aligned <= m0 - W`. Nothing that can contribute is skipped, for any `BLOCK_M`/`BLOCK_N`.

`SLIDING_WINDOW_SIZE` is a `tl.constexpr`, so a full-attention layer loses the branch at trace time and its loop is unchanged. `extend_start` is a multiple of `BLOCK_N`, so `tl.multiple_of(start_n, BLOCK_N)` stays valid. A custom mask or the non-causal path only adds conjuncts, which narrow the mask further, so the bound remains sound there. Under the HIP compact grid `cur_block_m` is still the per-sequence tile index, so the derivation is unaffected.

## Accuracy Tests

**MI355X (gfx950), 256 CU, ROCm 7.2, torch 2.9.1, Triton 3.7.0.**

The existing SWA suite passes unchanged: `test/registered/attention/unittests/swa/test_triton.py` reports 6 passed, 1 skipped, 20 subtests passed.

Output is unchanged rather than merely close. Across 21 configurations (12 sliding-window, 4 full-attention, 5 bound-inert) at `B=32, H_Q=64, H_KV=8, D=128`, bf16, causal, `o_extend` is bitwise identical before and after. Each run hashes its inputs as well as its output, so the comparison is only accepted when the inputs provably matched: **21/21 inputs identical, 21/21 outputs bitwise identical.**

The second commit adds coverage for the bound itself. Every pre-existing SWA extend case keeps the extend length under `BLOCK_M`, so `cur_block_m` is always 0 and the loop always starts at tile 0, leaving this code path unexercised. The three new cases use extend lengths above `BLOCK_M` with windows below it -- no prefix, with prefix and a window that is not a tile multiple, and a window landing exactly on a tile boundary -- so some query tile starts past the window and the bound takes effect.

## Speed Tests

Minimum over 7 repetitions of `triton.testing.do_bench(warmup=100ms, rep=500ms, return_mode="median")`, one idle GPU. The baseline sweep was run twice, before and after the patched sweep; **maximum run-to-run drift was 0.23%**, so the deltas below are well outside noise.

Note on methodology: `benchmark/kernels/sliding_window_attention_triton/bench_triton_swa_kernel.py` does not run on current main — its `_run_triton` predates the required `k_scale`/`v_scale` parameters of `extend_attention_fwd`, and `sglang.benchmark.bench_utils` hard-imports `flashinfer`, which has no ROCm build. These numbers therefore come from a harness that reuses that file's `_build_batch` for input generation but calls `extend_attention_fwd` the way `triton_backend` does, including `extend_seq_lens_cpu` so the HIP compact ragged grid is exercised.

The gain tracks the fraction of the loop below the floor: it grows with sequence length and shrinks with the window, which is what the derivation predicts.

### End to end

`gemma-4-26B-A4B-it` (25 of 30 layers `sliding_attention`, window 1024, `head_dim` 256, so `BLOCK_M`=128 here), `sglang.bench_one_batch --attention-backend triton`, one MI355X. Prefill latency, minimum of 4 alternating runs per arm. Minimum rather than mean because one patched run hit a 1.3 s startup artifact at `bs=4, 2048`; across the other cells the run-to-run spread is 0.2–1.3% for the baseline.

| batch | input_len | before (s) | after (s) | delta |
|---|---|---|---|---|
| 1 | 16384 | 0.5173 | 0.4753 | **−8.1%** |
| 4 | 16384 | 1.9708 | 1.8210 | **−7.6%** |
| 1 | 8192 | 0.2041 | 0.1944 | −4.8% |
| 4 | 8192 | 0.7725 | 0.7381 | −4.5% |
| 1 | 2048 | 0.0501 | 0.0497 | −0.9% |
| 4 | 2048 | 0.1558 | 0.1557 | −0.1% |

This is whole-model prefill, MoE included, so the attention-only share of the win is larger than these numbers. The 2048 rows are near zero because `BLOCK_M`=128 against a 1024 window means the bound only starts firing at `cur_block_m >= 9`, i.e. past token 1152. A model with a tighter window, such as `gpt-oss` at 128, should gain considerably more; I have not measured that.

### Full-attention control

At `sliding_window_size = -1` the branch is constexpr-eliminated, so the two builds should be indistinguishable:

| N_CTX | before (ms) | after (ms) | delta |
|---|---|---|---|
| 1024 | 0.6566 | 0.6573 | +0.1% |
| 2048 | 2.4447 | 2.4423 | −0.1% |
| 4096 | 8.0970 | 8.0976 | +0.0% |
| 8192 | 22.8541 | 22.8669 | +0.1% |

Mean +0.02%, all within the 0.23% drift. Full-attention models and the global-attention layers of hybrid models are unaffected both by construction and by measurement.

### Cost where the bound never fires

A sliding-window layer whose every M block satisfies `m0 <= W`: `extend_start` always evaluates to 0 and the trip count is unchanged, yet the computation still runs. `_build_batch` draws extend lengths from `randint(1, N_CTX // 2)`, so `W >= N_CTX / 2` makes the bound inert; `max_len_extend <= W` was checked per configuration rather than assumed.

| N_CTX | window | max_len_extend | before (ms) | after (ms) | delta |
|---|---|---|---|---|---|
| 1024 | 1024 | 466 | 1.1208 | 1.1082 | −1.1% |
| 1024 | 2048 | 466 | 1.1167 | 1.1051 | −1.0% |
| 2048 | 2048 | 913 | 4.3497 | 4.2907 | −1.4% |
| 4096 | 4096 | 1884 | 14.8614 | 14.6661 | −1.3% |
| 8192 | 8192 | 4072 | 42.3522 | 41.9029 | −1.1% |

No configuration regresses. The small consistent gain is above drift but I do not have an explanation for it, so I am reporting it rather than claiming it.

The AMDGCN metadata does **not** show this as free on gfx950, at `N_CTX=8192, W=127`:

```
sgpr_count:       106 -> 106
vgpr_count:       204 -> 204
sgpr_spill_count:  76 ->  80
vgpr_spill_count:   0 ->   0
shared:         16384 -> 16384
```

Four more SGPR spills. It does not show up in any measurement above, but I would rather flag it than assert the bound is free.
