# [AMD] Keep the FP4 varctx schedule test off AITER's 2048-row compile

[Upstream PR](https://github.com/sgl-project/sglang/pull/41793) · state: open · merged: False

## Original PR description

## Motivation

The scheduled [PR Test (AMD) run 36568058787](https://github.com/sgl-project/sglang/actions/runs/36568058787) on `main` included #40546 and #41464. In it, `stage-b-test-1-gpu-small-amd-mi35x (rocm10, linux-mi35x-gpu-1)` passed 46 of 49 files, then hit the 30-minute `Run test` step timeout ([job log](https://github.com/sgl-project/sglang/actions/runs/36568058787/job/109404903720)).

Most of the overrun came from `test_fp4_indexer_hip.py`, which took 578s against an estimate of 60s. 551s of that was spent in one case, `test_decode_schedule_matches_aiter_varctx_schedule[1536]`. With 1536 rows, AITER's `compute_varctx_schedule` reference launches `_varctx_cta_info_kernel` with `BLOCK_B = next_power_of_2(1536) = 2048`. The kernel holds a `[256, 2048]` tile and unrolls a 32-step search over the 2048-row vector. On the ROCm 10 image that Triton compile is very slow. On the rocm720 and rocm724 lanes of [run 36606581500](https://github.com/sgl-project/sglang/actions/runs/36606581500), the whole file takes 40s.

## Modifications

`test_decode_schedule_matches_aiter_varctx_schedule` now uses 200 rows instead of 1536, and monkeypatches `_DECODE_ROW_BLOCK` from 1024 to 64 for the test. The test still covers what the large case was there for:
- The in-tree prep kernel carries prefix sums across four row blocks, and the last block is partial (200 = 3×64 + 8).
- `_decode_cta_count(200, 65536)` is 1024, so the cta_info kernel still spans four 256-slot programs.
- Every 7th row still has zero length.

AITER's reference tile drops to `[256, 256]`. The production code is unchanged.
