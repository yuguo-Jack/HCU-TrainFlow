# disaggregation: Support Intel XPU for staging-buffer KV transfer

[Upstream PR](https://github.com/sgl-project/sglang/pull/40861) · state: open · merged: False

## Original PR description

## Motivation

PD disaggregation with staging-buffer KV transfer assumes CUDA in several places along the Encoder/Prefill/Decode path. On Intel XPU these assumptions either fail immediately (`torch.cuda.*` calls on a build without CUDA) or silently skip required synchronization because it is gated on `is_cuda`.

This PR makes the staging-buffer path device-agnostic and enables it end to end on Intel XPU, verified on 3x Intel Arc Pro B60.

Two of the fixes are not XPU-specific:

- The encoder `/send` path synchronized only when `mm_embedding.is_cuda`. The sync is required on every accelerator because `transfer_sync` does not order against the device stream; without it, the transport can read a buffer before the device writes land.
- Staging initialization hard-coded `device = f"cuda:{gpu_id}"`, so a non-CUDA backend could silently allocate staging buffers on CUDA.

NIXL with staging was also broken on main for every device: `prefill.py` and `decode.py` pass `slot_layer_ids=` to `set_kv_buffer_tensors`, which NIXL did not accept, so manager init failed with `unexpected keyword argument 'slot_layer_ids'`.

## Modifications

**Device helpers (`srt/utils/common.py`)**

- Add `create_device_event` and `current_device_stream`, which resolve the device module from the given device instead of hard-coding `torch.cuda`.

**Staging buffers (`disaggregation/common/staging_buffer.py`)**

- Device-aware allocation for CUDA, XPU and NPU; any other device type raises with a hint to unset `SGLANG_DISAGG_STAGING_BUFFER`.
- An explicit index on the device string wins over `gpu_id` (with a warning on mismatch), so a caller passing `"xpu:3"` cannot allocate on a different device.
- Custom memory pools stay CUDA-only; XPU/NPU use the default caching allocator, and a custom pool passed on those devices is ignored with a warning.
- Triton staging kernels are restricted to CUDA. XPU `data_ptr()` values can set bit 63, which `torch.tensor(..., dtype=torch.int64)` rejects, and there is no Triton NPU backend; other supported accelerators take the torch gather/scatter path.
- Gather and scatter assert that the KV buffers and the staging buffer are on the same device, so a cross-device pair fails with a clear message instead of faulting inside a kernel.
- Allocation logs include `ptr_type=XPU-kernel-space` / `XPU-user-space` on XPU.

**Stream ordering**

- The gather orders against the calling thread's current stream (`StagingBuffer.producer_stream()`), resolved per call, instead of `torch.cuda.default_stream`. The current stream is thread-local, and transfer workers run on their own threads.
- The decode scatter waits on an event recorded on `schedule_stream` when the room is registered, right after pre-alloc writes its `req_to_token` row. Previously there was no ordering edge; XPU has no CUDA-style default-stream synchronization, and a dedicated CUDA stream does not implicitly sync with unrelated work either. Waiting on the stream itself would also queue each scatter behind any forward running there without overlap.
- The decode scatter stream is now created eagerly, and `release_room` drains it only when the room still has an in-flight scatter. The stream is shared by all rooms, so draining unconditionally would stall the scheduler thread behind unrelated rooms on the success path. The prefill gather stream stays lazy, since the decode-side allocator's buffer never gathers.

**Staging handler and transports (`common/staging_handler.py`, `mooncake/conn.py`, `nixl/conn.py`)**

- Use the runtime device module for Event and Stream creation. `DecodeStagingHandler` derives its device from the KV buffers and requires an indexed device.
- Thread the runtime `device_type` from `server_args.device` into staging initialization.
- NIXL: use `np.uint64` for staged transfer descriptors so high device pointers are not truncated or read as signed. `set_kv_buffer_tensors` accepts `slot_layer_ids` (see Motivation); NIXL staging is `pp_size == 1` only, so the value is stored but not read.

**DCP pack (`disaggregation/common/dcp_pack.py`)**

- `copy_mla_rows_into_pack` is Triton-only, so off CUDA `init_dcp_pack_buffers` returns no buffers and DCP transfers fall back to per-token RDMA.
- Order the gather against the staging buffer's producer stream instead of `torch.cuda.default_stream`, and enter it through the device-agnostic stream context.

**Encoder (`disaggregation/encoder/server.py`, `encoder/receiver.py`)**

- `TensorWrapper` copies from any non-CPU device, not only CUDA.
- `/send` synchronizes for every non-CPU accelerator instead of gating on `is_cuda`, and the embedding-cache paths synchronize through `current_device_stream`.
- The receiver's RDMA buffers and `EmbeddingPool` allocate on the runtime device type instead of `cuda:{gpu_id}`.

**Metadata buffers and QK normalization (`disaggregation/utils.py`, `models/utils.py`)**

- The `INTRA_NODE_NVLINK` metadata-buffer placement now also requires `is_cuda()`. The `use_mem_pool` context stays on `torch.cuda`, since `custom_mem_pool` is a `torch.cuda.MemPool`.
- `apply_qk_norm` enters `alt_stream` through the device-agnostic stream context.

**Docker (`docker/xpu.Dockerfile`)**

- Build the Mooncake transfer engine from a pinned upstream commit with icpx (`-DUSE_XPU=ON -DUSE_TENT=ON -DWITH_STORE=OFF`) and install `sglang-router`, which the PD tests launch between prefill and decode.

### Breaking changes for out-of-tree backends

- `init_staging_buffers`, `init_staging_allocator` and `init_dcp_pack_buffers` take a required keyword-only `device_type`. The old implicit `"cuda"` is intentionally gone, so omitting `device_type` fails loudly instead of allocating staging on the wrong accelerator.
- `gather_all_layers_to_staging` no longer takes `gpu_id`; the device comes from the KV buffers.
- `EmbeddingPool` takes keyword-only `device_type`, `gpu_id` and `size_bytes`.

### XPU end-to-end

The registered XPU PD tests run on Mooncake. Mooncake's XPU support lives in its TENT engine, so the test classes set `MC_USE_TENT=1` and `MOONCAKE_PROTOCOL=tcp` and need no RDMA NIC. They skip when `mooncake.engine` is not importable, so the nightly stays green on an image built before the Dockerfile step.

Verified on 3x Intel Arc Pro B60:

- `test/registered/xpu/test_disaggregation_staging_xpu.py` (prefill TP 1, decode TP 2, so KV goes through the staging path): 4 passed, on `nightly-xpu-4-gpu`.
  - staging buffer allocated on prefill and on decode, including the XPU kernel-space pointer format
  - single completion and deterministic output
  - concurrent requests matching serial output
  - multi-chunk long-sequence generation
- `test/registered/disaggregation/test_disaggregation_xpu.py`: 2 passed, on `nightly-xpu-2-gpu`.
- The same Mooncake tests pass against a transfer-engine-only install of upstream Mooncake built with the Dockerfile steps.

The concurrent-vs-serial case matters most: it exercises `enable_overlap` together with a radix-cache prefix hit, and compares against the serial answers at temperature 0, so KV corruption shows up as a token mismatch. It needs the dependency PR above.

The staging e2e test lives under the `xpu` vendor tree because the registered-test taxonomy rejects new paths outside the `<kind>/<subsystem>` layout, while vendor directories are exempt.

The NIXL variants are manual tests under `test/manual/kv_transfer/`: `test_disaggregation_nixl_xpu.py` (basic completion) and `test_disaggregation_staging_nixl_xpu.py` (staging). They mirror the registered scenarios and skip when nixl is not installed.

The staging decode server (TP 2) runs with `TORCHINDUCTOR_USE_STATIC_CUDA_LAUNCHER=0`. On torch 2.13.0+xpu, inductor's static Triton launcher segfaults in `load_kernel` on the compiled vocab-parallel embedding mask, which only runs at TP > 1. This is not PD-specific: a plain Qwen2.5-1.5B or Llama-3.1-8B server at TP 2 crashes the same way. Turning off only the static launcher keeps `torch.compile` on, unlike `TORCHDYNAMO_DISABLE=1`. Likely pytorch/pytorch#199511; the override can go once the XPU torch pin includes the fix.

## Performance


No CUDA-path performance regression is intended. The changes are mostly device selection and stream/event handling on initialization or correctness-critical paths.

- The gather resolves the current stream per call instead of using a fixed stream, measured at about 0.3% overhead on the affected path. The per-call lookup is intentional, because the current stream is thread-local and transfer workers run on separate threads.
- `release_room` now skips the scatter-stream drain for rooms with no in-flight scatter, which removes a scheduler-thread stall on the success path.
