# [DSA] Pass the batch size to the decode metadata kernels at runtime

[Upstream PR](https://github.com/sgl-project/sglang/pull/43627) · state: open · merged: False

## Original PR description

## Motivation

The three DSA metadata kernels (`_fused_dsa_decode_metadata_kernel`, `_fused_dsa_target_verify_metadata_kernel`, `_fused_dsa_draft_extend_metadata_kernel`) take the batch size as a `tl.constexpr`. They run outside CUDA graphs on every decode, verify and draft step, and the batch size changes whenever a request joins or finishes. So a server compiles each kernel again for every new batch size, up to `--max-running-requests` times, while it serves. Each compile stalls every request on the server.

The kernels use the batch size only in masks (`offs_b < bs`, `row < bs`, `out_row < expanded_size`) and as the bound of `tl.range` loops. None of these needs a compile-time value. `BLOCK_BS` and `BLOCK_EXPANDED` (powers of two) already set the tile shapes.

## Modifications

- `dsa_metadata.py`: `bs` is a runtime argument in the three kernels, and `expanded_size = bs * next_n` is a runtime value in the target-verify kernel. The launchers are unchanged. The kernels now compile once per `BLOCK_BS` / `BLOCK_EXPANDED` pair (Triton still specializes the integer on 1 and on multiples of 16).
- `test_dsa_metadata.py`: `test_decode_does_not_recompile_for_each_batch_size` runs the decode kernel for batch sizes 5, 6 and 7 (one `BLOCK_BS`) and checks that the second and third sizes add no compiled kernel.

## Accuracy Tests

The kernels compute the same values: only the compile-time status of `bs` changes. All existing tests of `test_dsa_metadata.py` compare each kernel with an eager reference with `rtol=0, atol=0`, and they pass with the change.

## Speed Tests and Profiling

On one B200 node, GLM-5.3-Flash (FP8, DSA k-pool, MTP), TP8, v0.5.20 with this change backported, empty Triton cache:

- Without the change, the first decode batch of each new size added about 0.5 s: rounds of 7 and 12 concurrent sampled requests (64 output tokens each) took 1.99 s and 1.91 s, and their repeats 1.45 s and 1.36 s. The repeats were still slow, because the batch size shrinks as requests finish and each smaller size compiles again.
- With the change and a start-up warmup of one batch size per `BLOCK_BS` bucket, the same rounds took 1.12 s and 1.36 s, the same as their repeats (1.07 s and 1.25 s).
- Steady-state decode did not change: time per verify step was 0.999x, 1.006x and 1.002x of the server without the change with 1, 4 and 16 requests in flight.

## Validation

```bash
python3 -m pytest test/registered/kernels/ops/attention/test_dsa_metadata.py
```

- On B200 (Triton 3.7.1), the test file was run against `main` and against this branch. On `main` the new test fails with `AssertionError: 3 != 1` (three compiled kernels for three batch sizes). With this change all 9 tests pass.
- `pre-commit run --files` passes for the two changed files.
