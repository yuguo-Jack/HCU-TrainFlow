# [unified-memory] Admit asymmetric K/V rows (MiMo-V2-Flash)

[Upstream PR](https://github.com/sgl-project/sglang/pull/43325) · state: open · merged: False

## Original PR description

**Stack:** #42930 → #43168 → #43169 → #43170 → #43171 → this PR. Merge it after those; until they land, its diff against main also shows their commits (the four fixes are each also open against main on their own). This PR's own changes are its top two commits, `a413f736e8` and `a46ae3f507` (7 files, +278/−107).

## Motivation

MiMo-V2-Flash has asymmetric K/V rows: 192-wide K heads and 128-wide V heads, on its full-attention and its sliding-window layers alike. `--enable-unified-memory` refuses any such model at boot ("does not yet admit asymmetric K/V rows"), so MiMo serves only on the default pool. That pool splits its memory between the two layer kinds at boot, and under long decodes it retracts requests while the other kind's memory still has room.

## Modifications

1. **Admit asymmetric K/V rows on the backends that carry `v_head_dim`** (`a413f736e8`). The token-major entry holds a K row and a narrower V row at their own offsets under one slot stride, so the pool-level refusal goes. What remains is a backend property: whether the kernel is told the V width at all. FlashInfer's `paged_kv_t` keeps separate K and V strides but one `head_dim` for both tiles, and sglang's MHA plan path never passes `head_dim_vo`; trtllm_mha refuses unequal QK/V dims. The MHA arm of the page-major allowlist therefore narrows to `ASYMMETRIC_KV_BACKENDS`: triton, fa3 and fa4, which pass `layer.v_head_dim` through. fa4 is the resolved default for an asymmetric-K/V model on SM100, so leaving it out would make such a model unbootable in its own default configuration; every run below is on SM90, where fa4 does not run. A fused draft with asymmetric rows follows the same rule (it fuses only when the target's and the draft's backends all carry `v_head_dim`), its region carries the draft's own `v_head_dim`, and the placement's row-alignment check covers the V row as well as the K row.
2. **Allocate SWA-family hosts with their real K/V geometry** (`a46ae3f507`). The two SWA-family unified factories (`_init_unified_swa_pools` for hybrid-SWA hosts, `_init_unified_mamba_swa_pools` for tri-pool hosts) derived the head geometry inline, and on GPU both hard-coded a symmetric shape (`v_head_dim = head_dim`, the window side equal to the full side). For MiMo that allocates 192-wide V rows on the sliding-window side while the boot solve prices 192 + 128: the allocated entry is 20% larger than the priced one, so the pool lands about 17% below the slot count the boot solve committed to. One `_UnifiedSWAHeadGeometry`, built from the model config (`v_head_dim`, `get_swa_num_kv_heads`, `swa_head_dim`, `swa_v_head_dim`), now feeds both factories and the fused-entry price, so the priced and the allocated entry cannot drift.

Tests (CPU): `TestUnifiedSWAHeadGeometry` builds the geometry from a 192/128 model config and fails before (no shared source, symmetric GPU path); its pricing case holds the fused price to the same geometry. The tri-pool test stubs gain the SWA head fields and `v_head_dim`.

## Accuracy Tests

The GSM8K runs used this stack's commits over main b130f8af02; the load tests and the Qwen comparison under Speed Tests ran over main 4b384df0c9. Neither rebase changed this PR's commits.

SM90, MiMo-V2-Flash, TP4, no speculation, radix cache, overlap scheduler, CUDA graphs on. Default pool against `--enable-unified-memory`. GSM8K, all 1314 test questions, 5-shot, greedy:

| attention backend | default pool | unified |
|---|---|---|
| triton | 0.839 | 0.852 |
| fa3 | 0.823 | 0.842 |

The unified pool lays MiMo out with its real 192/128 geometry on both layer kinds, at the entry size the boot solve prices.

The MiMo runs here used the head of the next PR in this stack, which changes what a speculative draft binds and leaves a run without a draft as it is in this PR.

GPU unit suite (unified-memory scope): all pass except the 2 cases of `test_swa_write_back_host_full_preserves_full_and_continues`, which force the Rust TreeCore that our test image does not build.

## Speed Tests and Profiling

The same MiMo configuration under two load tests: 100 requests of 512 input / 4096 output tokens at concurrency 128, and 192 requests that share a 4096-token system prompt, each with a 128-token question and 2048 output tokens, at concurrency 192. Every request completed on every server, and no server reported an error.

| attention backend | requests × input / output tokens | default pool req/s | unified req/s | change |
|---|---|---|---|---|
| triton | 100 × 512 / 4096 | 0.615 | 0.896 | +45.6% |
| triton | 192 × (4096 shared + 128) / 2048 | 0.867 | 1.259 | +45.2% |
| fa3 | 100 × 512 / 4096 | 0.611 | 0.874 | +43.2% |
| fa3 | 192 × (4096 shared + 128) / 2048 | 0.824 | 1.156 | +40.3% |

The gain is capacity: from the same memory, the unified pool lets either layer kind take the bytes the default pool splits between them at boot, so it retracts fewer requests.

A model this PR does not admit is unaffected: Qwen3.5-9B without speculation (200 requests of 2048 input / 512 output tokens at concurrency 64), run back to back on one host with and without this PR, keeps its unified-vs-default-pool req/s gap at −0.4% (fa3), −0.5% (triton) and −0.4% (trtllm_mha), against −0.3%, −0.2% and −0.5% without it. The default pool runs twice per configuration, and its two runs differ by at most 0.2%.
