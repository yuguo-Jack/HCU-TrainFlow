# [AMD] Set maxseq length limit for DSV4.1 BCG metadata buffers

## Motivation

<!-- Describe the purpose and goals of this pull request. -->

When running DSV4.1 with BCG on hip, every replay rebuilds the attention metadata based on the current batch's actual context length and swaps it into the graph. Each graph bucket keeps its latest copy. 

As a result:
- The metadata memory has no upper bound. Long-context, multi-turn workloads (e.g. agentx) may OOM.

  ```python
  mem = num_buckets * ctx_len
  ```
- Every replay allocates new metadata buffers of a different size.

Nv's DSV4.1 path avoids this by capping BCG at `cuda_graph_config.prefill.max_seq_len` (16k by default) and running longer contexts eager. Our previous DSV4 path also avoids it by keeping the metadata at a fixed size.

## Modifications

<!-- Detail the changes made in this pull request. -->

Only `deepseek_v4_backend_hip_radix.py` is changed:
- Reuse nv's `can_run_prefill_cuda_graph`: if the longest context in a batch exceeds `prefill.max_seq_len`, the batch runs eager instead of BCG.
- Add `_graph_metadata_max_seq_len()`: use `--cuda-graph-prefill-max-context` if set, otherwise `prefill.max_seq_len`.

Memory impact:
One shared prefix of length L, then 74 requests whose suffix lengths match each graph bucket. Numbers are VRAM growth since the server became ready.

| L | before | after | eager (BCG disabled) |
|---|---|---|---|
| 128k | +15.1 GiB | +8.3 GiB | +10.0 GiB |
| 256k | +27.4 GiB | +9.5 GiB | +10.0 GiB |
| 512k | OOM (+33.0 GiB) | +10.7 GiB | +12.1 GiB |
| ~1M | - | +14.7 GiB | +17.2 GiB |

## Speed Tests and Profiling

<!-- If this pull request impacts inference speed, provide benchmarking and profiling results. -->

From our experiments, BCG brings no speedup on long contexts, so running them eager costs nothing.
`bench_serving` random dataset, output 1024, num-prompts = 4 * concurrency.
- Up to 16k, both versions run BCG and the results are within noise.
- Above 16k, chunks run eager after this change, with no performance loss.
