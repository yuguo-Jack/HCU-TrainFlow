# [AITER] Give pa_decode_gluon a page table when the KV layout is SHUFFLE 5D

[Upstream PR](https://github.com/sgl-project/sglang/pull/43335) · state: open · merged: False

## Original PR description

## Motivation

With the SHUFFLE 5D KV layout (`SGLANG_AITER_KV_CACHE_LAYOUT=vectorized_5d`), a dense model without sliding-window attention decodes garbage on the AITER backend: GSM8K drops from 0.955 to 0.010 on Qwen3-14B-FP8, with no error.

`forward_decode_vectorized_5d` passes `forward_metadata.kv_indices` to `pa_decode_gluon` as its `block_tables`, a 2-D `(bs, max_num_blocks_per_seq)` table of page ids, and its docstring says the same ("Full-attn → `kv_indices` page table"). But the decode metadata only builds that table on the unified-attention branch:

```python
if not self.use_triton_unified_attention:
    # flat per-token kv_indices, addressed through kv_indptr
    create_flashinfer_kv_indices_triton[(bs,)](...)
else:
    # 2-D page table
    ...
```

`use_triton_unified_attention` is forced on for sliding-window models, which is why gpt-oss (the model the 5D path was added for in #27063) is unaffected. Every other model leaves it off by default, so `pa_decode_gluon` reads token ids as page ids with a row stride of 1. The eager path, the CUDA-graph page-table buffer and CUDA-graph capture/replay all make the same choice.

## Modifications

The decode metadata format and the decode kernel are separate choices, so this PR names the former explicitly:

```python
self.decode_uses_page_table = (
    self.use_triton_unified_attention or self.kv_cache_is_vectorized_5d
)
```

and uses it at the five sites that decide between the flat indices and the page table: the eager decode path (plain and speculative), the CUDA-graph page-table buffer allocation, and both checks in `_apply_cuda_graph_metadata` (shared by capture and replay).

`use_triton_unified_attention` itself is unchanged. The 5D layout already has dedicated KV-write, extend and decode branches, so the only things the flag still controls for it are the metadata format and the target-verify kernel choice (`_use_unified_verify`). Forcing the flag on would also switch the verify kernel, which is outside this fix. The NHD layout is unaffected: `decode_uses_page_table` equals `use_triton_unified_attention` there.

Tests: `test/registered/amd/test_aiter_vectorized_5d_decode.py` launches the CI default model (`meta-llama/Llama-3.1-8B-Instruct`, dense, no sliding window) with `SGLANG_USE_AITER=1`, the 5D layout and `--page-size 64`, and runs GSM8K. Registered in `stage-b-test-1-gpu-small-amd-mi35x`.

## Accuracy Tests

MI355X (gfx950, 256 CU), ROCm 7.2.0, torch 2.9.1, Triton 3.7.0. sglang `main` @ `c44a42e6d3` (no later changes to the touched files), `sgl-kernel` built from the same commit, AITER `e7d2453f` (the commit pinned in `docker/rocm.Dockerfile`).

Qwen3-14B-FP8, `SGLANG_USE_AITER=1`, `--page-size 64`, CUDA graph on, GSM8K 200 questions, 5-shot, greedy:

| Config | GSM8K | Output tok/s (warm) |
|---|---|---|
| `main`, NHD layout (reference) | 0.955 | 3594 |
| `main`, 5D layout | **0.010** | n/a (garbage output) |
| This PR, 5D layout | 0.945 / 0.940 | 3499 |
| `main`, 5D layout + `SGLANG_USE_AITER_UNIFIED_ATTN=1` | 0.945 / 0.955 | 3581 |

The last row already builds the page table on `main` (through the unified flag), so it is the existing reference for the fixed path. This PR matches it in accuracy and throughput; the three servers ran concurrently on separate GPUs, so the ~3% spread is within noise.

New test, same environment:

| Code | GSM8K | Result |
|---|---|---|
| `main` | 0.015 | fails (threshold 0.7) |
| This PR | 0.770 | passes in 204 s |

## Speed Tests and Profiling

No change on the NHD layout. On the 5D layout the fixed path builds the same page table as the unified-attention path; throughput is in the table above.
