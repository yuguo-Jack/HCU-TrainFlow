# [AMD] aiter unified attention: refresh the CUDA-graph page table at page_size 1

[Upstream PR](https://github.com/sgl-project/sglang/pull/41234) · state: closed · merged: False

## Original PR description

## Summary

Part of #41152.

With a single KV pool and the default `page_size` 1, `_apply_cuda_graph_metadata` builds the decode page indices but never copies them into `cuda_graph_page_table`. Only the SWA-pool branch and the `page_size > 1` branch do the copy. Unified attention then replays every CUDA-graph decode step against a stale page table and produces garbage from the second generated token on. Eager decode (`--disable-cuda-graph`) builds its own table and is unaffected.

`_transform_table_1_to_real` is a no-op at `page_size` 1, so the fix takes the existing copy branch for every page size.

Affected: any model on the aiter unified path with a single pool and `page_size` 1 under CUDA graphs. That includes Gemma 2/3, whose only aiter decode path is unified attention, and any model forced onto it with `SGLANG_USE_AITER_UNIFIED_ATTN=1`.

## Results (1× MI325X, TP1, default CUDA graphs)

8 fixed chat prompts, temperature 0, max 256 tokens, `SGLANG_USE_AITER_UNIFIED_ATTN=1`:

| model | main | this PR |
|---|---|---|
| Gemma 3 4B | every reply turns to garbage after the first token and runs to 256 tokens | matches triton: reply lengths 84/51/78/39/19/106 vs triton 84/52/78/39/19/106; "Count from 1 to 20" identical |
| Qwen3-8B | garbage (`<think>();++邾ETOELS =~GetInstance…`) | coherent |

GSM8K (lm_eval, temperature 0, strict / flexible):

| model | this PR | reference |
|---|---|---|
| Gemma 3 4B | 0.831 / 0.831 | triton 0.832 / 0.832 |
| Qwen3-8B | 0.930 / 0.935 | aiter default backend 0.935 / 0.939 |

On main, GSM8K does not finish on this path because generations never stop.

Three more models, same settings. On main each one answers "The" and then produces garbage until the 256-token limit (`The ( ( ( ( …` on Llama 3.1 8B, `The处罚 กลۆ paddock…` on Gemma 3 12B):

| model | reply lengths, this PR | reply lengths, reference | GSM8K this PR | GSM8K reference |
|---|---|---|---|---|
| Llama 3.1 8B | 91/76/86/64/8/21/105/256 | identical (aiter default backend) | 0.837 / 0.838 | 0.834 / 0.836 |
| Gemma 2 9B | 123/78/45/72/15/52/5/246 | 123/77/45/72/15/52/5/252 (triton) | 0.845 / 0.846 | 0.842 / 0.843 |
| Gemma 3 12B | 256/72/54/79/34/50/95/256 | identical (triton) | 0.933 / 0.933 | 0.933 / 0.932 |

`page_size` > 1 takes the same code path before and after this change. As a control, Qwen3-8B with `--page-size 16` gives the same replies on main and this PR, at the same throughput (1024 in / 512 out at concurrency 4: 580.0 vs 584.4 tok/s; 4096 / 512 at concurrency 32: 1582.7 vs 1609.6 tok/s).

Not fixed here: decode on the unified path is also slow at small batch and long context. Two running requests at about 5K tokens decode at about 11 tok/s on Gemma 3 4B, while triton runs one such request at about 83 tok/s. That is the throughput gap reported in #41152 and needs a separate look.
