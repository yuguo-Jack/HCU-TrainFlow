# [Bugfix] Propagate SwiGLU clamp to KT CPU experts

[Upstream PR](https://github.com/sgl-project/sglang/pull/43500) · state: open · merged: False

## Original PR description

## Motivation

`KTEPWrapperMethod.create_weights()` does not pass the layer's `swiglu_limit`
to `KTMoEWrapper`. The native wrapper therefore defaults to `0.0` (disabled),
even when the GPU runner and checkpoint require clamping. This omission is
still present on main at `3831e7e0918052be50ef38b3ff62154573e213d7`.

We found this while qualifying DeepSeek-V4.1-Flash with MXFP4 CPU expert offload
on dual EPYC 7443 (AVX2) and two RTX PRO 4500 Blackwell GPUs. The checkpoint's
`text_config.swiglu_limit` is 10.0; resident GPU experts use it, but the CPU
configuration silently received zero.

## Modifications

- Pass `layer.moe_runner_config.swiglu_limit or 0.0` to the native wrapper.
- Register five CPU-only unit tests covering limits 10 and 7, `None`, zero,
  and the non-owning TP rank. They exercise `create_weights` while replacing
  only the native constructor/GPU weight-creation boundaries; no checkpoint,
  GPU execution or installed `kt_kernel` is needed.
- Keep native backend validation in charge of rejecting unsupported nonzero
  clamp/method combinations instead of silently disabling model arithmetic.

This does not attempt to add support for other parameterized activations
(`swiglu_alpha`, `gemm1_alpha`, etc.).

## Accuracy Tests

- Executed the exact patched current-main `create_weights` function with the
  five new tests in our deployed image's dependency environment: **5/5 pass**.
  The standalone harness installed that function only in its own Python process;
  it did not alter the server or installed source files. This is not a full
  current-main dependency-stack or end-to-end run.
- Negative control removing only the new keyword: the two nonzero-clamp cases
  fail (`0.0 != 10.0`, `0.0 != 7.0`); the other three cases pass.
- Independent native AVX2 MXFP4 primitive, rerun on both NUMA pools:
  four identical routed tokens, one expert, hidden/intermediate size 128,
  group size 32, one active coordinate. Gate projection 96, up projection 24,
  and unit down projection produce **2304** with native limit 0 and **100**
  with native limit 10. This verifies that the existing native backend honors
  the setting when the caller supplies it.
- The equivalent fix was deployed on our pinned V4.1 integration
  (SGLang `1aa0e962b206102b7c439a4a0c4981cfec6e87bc` plus the community tree
  patch, KTransformers `95009ea6856c0799e517e93cb12be5e8494bc7ce`). Fresh tool
  calls, tool-result round trips and six fresh/cached/growing retrieval checks
  near 126K input tokens passed without diagnostic hooks.

The native primitive and the omitted configuration are the correctness evidence;
successful model requests do not prove this omission caused every earlier
behavioral failure. The integration also has a separate streamed-GPU clamp fix.

Local CI command in a configured SGLang development environment:

```sh
python test/registered/unit/layers/moe/test_kt_ep_wrapper.py
```

## Speed Tests and Profiling

On that pinned integration, three fixed-256-output runs after the fix had median
decode throughput **23.16 tok/s**, essentially unchanged from the preceding image.
Warmed fresh prefill was about **365 input tok/s** end-to-end. These are deployment
observations, not a benchmark of pristine current main or an isolated attribution
of every serving change to this one line.
