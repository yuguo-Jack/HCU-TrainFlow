# [AMD] DeepSeek-V4.1: opt-in mono decode launches on gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/43497) · state: open · merged: False

## Original PR description

## Motivation

In decode with few requests, each DeepSeek-V4.1-Flash layer runs many small kernels plus two all-reduces. Launch gaps and memory round trips then cost more than the math.

This PR adds persistent monokernels launches for decode on MI355X (gfx950):

- the **FFN launch**: the attention all-reduce, the mHC mix before the FFN, and the FFN / MoE block with the MoE all-reduce;
- the **attention launch**: the mHC mix before the attention and the attention front block, on layers without compressor or indexer.

Each block becomes one launch. The launch's workgroups stay on the GPU for the whole block and synchronize on the GPU between its steps, so the block has no launch gaps and fewer memory round trips. The goal is lower time per output token (TPOT) at small and medium batch.

No other PR is needed, with or without DSpark. The code runs as is on the ROCm 10-10 image `rocm/sgl-dev:v0.5.21-rocm724-mi35x-20261010` (SGLang 44bc478863, AITER e7d2453f, FlyDSL 0.3.4.1), which includes DSpark.

## Modifications

**Flags** (both off by default): `SGLANG_ROCM_MONO_DECODE=1` turns on the FFN launch. `SGLANG_ROCM_MONO_K1=1` adds the attention launch and needs the first flag.

**When the launches run.** In decode steps (one row per running request) and DSpark verify steps (block size + 1 rows per request) of 1 to 48 rows. In DeepSeek-V4.1-Flash the FFN launch runs on all 40 layers and the attention launch on 30 layers (27 in DSpark verify steps). Prefill, extend and mixed steps, steps of more than 48 rows, and DSpark's draft layers take the normal path.

**Startup checks.** If a flag is set and the deployment does not fit, the server stops at startup with a `ValueError` that says why. The launches need gfx950 with all compute units, TP 2 or 4 without attention data or expert parallelism, the DeepSeek-V4.1-Flash config with AITER's MXFP4 expert layout, FlyDSL, and no speculative decoding or DSpark with `SGLANG_RAGGED_VERIFY_MODE=static` (the default). The attention launch also needs the paged SWA KV cache, the V4 KV layout and the fused `wqkv_a` projection.

**Files.**

- New: the FlyDSL kernels in `deepseek_common/amd/dsv41_mono/` and the glue `deepseek_common/amd/dsv41_mono_decode.py`.
- Shared files: `deepseek_v4.py` +10 -1, `deepseek_v4_hip.py` +4, `deepseek_v4_fused_mhc.py` +37 -2, `environ.py` +3.
- Manual tests in `test/srt/amd/dsv41_mono/`: kernel, attention drift and race stress tests (GPU), and a CPU guard test.

**Memory.** The FFN launch keeps an FP8 copy of the shared expert: about 354 MB per GPU at TP4, computed from the checkpoint shapes. KV cache at TP4, mem fraction 0.87: 57,816,832 -> 57,040,896 tokens (-1.3%) without DSpark, and 54,858,240 -> 54,101,248 (-1.4%) with DSpark block 5.

**Limits.**

- Outputs are close to the normal path, not bitwise equal. The FFN launch uses the FP8 shared-expert copy (SGLang's fusion uses MXFP4). In the serving check, the query rel-L2 is at most 6.7e-4 (bound 1e-2, cos >= 0.9999) and the pre / post / comb mixes differ by at most 5.4e-7 (bound 1e-5). The drift test (17 widths, TP2 and TP4) measured a query rel-L2 of at most 2.26e-3 and mixes of at most 5.96e-7, within its bounds of 5e-3 and 1e-6. The attention launch's KV-cache records are bitwise equal.
- Mixed chunked prefill (`--enable-mixed-chunk`) is not tested; its mixed steps take the normal path. Serving and the race stress test ran only at TP4.
- The attention launch mirrors SGLang's kernels as compiled in the image. Re-run the drift test after SGLang, AITER, Triton or FlyDSL updates.

**How to run** (the recipe of the runs below):

```bash
SGLANG_USE_AITER=1 SGLANG_MOE_PADDING=1 AITER_FLYDSL_FORCE_REDUCE=0 AITER_BF16_FP8_MOE_BOUND=0 \
ROCM_QUICK_REDUCE_QUANTIZATION=INT4 SGLANG_DSV41_REASONING_EFFORT=75 \
SGLANG_OPT_HIP_OPUS_SPARSE_PREFILL=1 SGLANG_OPT_FP8_WO_A_GEMM=1 SGLANG_OPT_FUSE_MHC_POST_PRE=1 \
SGLANG_ROCM_MONO_DECODE=1 SGLANG_ROCM_MONO_K1=1 \
sglang serve --model-path deepseek-ai/DeepSeek-V4.1-Flash --trust-remote-code --tp 4 \
  --mem-fraction-static 0.87 --chunked-prefill-size 16384 --max-prefill-tokens 16384 --context-length 135168 \
  --cuda-graph-backend-prefill disabled --enable-decoder-swa-bounded-replay \
  --enforce-shared-experts-fusion --cuda-graph-max-bs-decode 256 --max-running-requests 256 \
  --reasoning-parser auto --tool-call-parser auto
# random-prompt and accuracy runs add: --disable-radix-cache
# DSpark adds: SGLANG_RAGGED_VERIFY_MODE=static (the default) --speculative-algorithm DSPARK --speculative-dspark-block-size 5
```

The kernels are adapted from vLLM's mono decode kernels and keep their license notices.

## Accuracy Tests

All tests ran on the 10-10 image, not on current main, with the same setups as the speed runs (see the note under Speed Tests). TP4, radix cache off. GSM8K, GPQA (thinking, 198 questions), NIAH single_2 at 64k and 128k.

| Setup | GSM8K | GPQA | NIAH 64k | NIAH 128k |
|---|---|---|---|---|
| Upstream, run 1 / 2 | 0.9718 / 0.9703 | 0.8687 / 0.8687 | 1.0 / 1.0 | 1.0 / 1.0 |
| Both launches, run 1 / 2 | 0.9734 / 0.9734 | 0.8434 / 0.8687 | 1.0 / 1.0 | 1.0 / 1.0 |
| DSpark | 0.9711 | 0.8586 | 1.0 | 1.0 |
| DSpark + both launches | 0.9711 | 0.8535 | 1.0 | 1.0 |

Gate, per run against the upstream mean: GSM8K within 1 point, GPQA within 5 points, NIAH = 1.0. All runs pass. The first mono GPQA run is 5 questions below upstream; the second equals it. DSpark accept length in these runs: 3.66 with the launches, 3.65 without (one run each).

Correctness checks:

- KV cache: 0 of 424,491,300 compared slots differ, and all 4,440 attention-launch record checks are within bounds (TP4 serving check).
- DSpark verify steps: 0 of 21,166,788 compared slots differ.
- Drift test (17 widths) and kernel test (10 widths): pass at TP2 and TP4.
- Race stress at TP4: 288,930 steps with both launches and 239,920 with the FFN launch only, 0 mismatches.
- The kernels in this PR give the same output digests as the earlier build used in the runs without DSpark (TP2 and TP4).
- CPU guard test: all cases pass (30 refusal cases, warm-up, 9 speculative, 63 step and 2 layer cases).

The mono experiments we ran for the speed, accuracy and profile runs also had #42498 and #42911 applied; this PR does not need them. The runs with DSpark used this PR's code. Thanks @rkarhila-amd good questions!

On the code location: AMD maintainers have been careful with PRs that touch common code, so I kept this self-contained on purpose. Apart from some minor changes in `environ.py` and `deepseek_v4.py`, it's all new code under `deepseek_common/amd/` plus tests, and it's off by default. It's the same layout vLLM merged in vllm-project/vllm#60397. The reusable part is already split out in `dsv41_mono/common/` (from ROCm/ATOM's `atom/mono`). When a second model's mono kernels come to SGLang, we can move it to a shared AMD folder in a small follow-up PR. vLLM is starting to do the same.

On other GPUs: this PR is gfx950 only and stops at startup with a clear error elsewhere, so gfx942 users see no change. gfx942 is possible but needs a port, and vLLM has a draft for it (vllm-project/vllm#60731). With 64 KB of LDS instead of 160 KB, it takes up to 42 rows instead of 48, runs at TP4 only and adds a few kernels. We can bring it over as a follow-up PR. For gfx1250, I'd wait: these kernels are built for fixed shapes and tuned per chip, so a small separate PR once the hardware and FlyDSL support are ready is cleaner.
