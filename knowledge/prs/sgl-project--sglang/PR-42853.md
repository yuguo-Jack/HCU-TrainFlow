# [DeepSeek-V4.1] Extend mHC mix-stats num_stages=1 to small Blackwell batches

[Upstream PR](https://github.com/sgl-project/sglang/pull/42853) · state: closed · merged: False

## Original PR description

## Motivation

Torch-profiler triage of DeepSeek-V4.1-Flash at main `730f1f3e5b` on 4x B200 (cookbook TP4+EP4 low-latency cell, DSPARK block 5) shows the mHC mix-stats pair (`_hc_mix_stats_partial_kernel` + `_hc_mix_reduce_sinkhorn_kernel`) is the single largest decode kernel family: ~32% of decode GPU time at bs=1, ~86 calls per spec iteration (one per hc sublayer, 40 layers x attn/ffn + MTP).

`_num_stages_for` enables `num_stages=1` only for `64 <= m <= 384`, so decode/verify row counts (M <= 8 at bs=1) fall through and launch the partial kernel with `num_stages=2`. At these sizes the extra pipeline stage only adds shared-memory footprint and scheduling overhead: the whole K loop is 4 x BLOCK_K=64 tiles per slice.

## Modification

Drop the lower bound of the `num_stages=1` window: `64 <= m <= 384` becomes `m <= 384` (Blackwell, K=20480 unchanged).

`num_stages` only reorders memory issue, not arithmetic, so the partials are bitwise unchanged — verified with `torch.equal` on `part_mix`/`part_sq` against `num_stages=2` for M in {1, 7, 8, 64, 128}. Batch invariance (K slicing, BLOCK_K, dot precision, BLOCK_M buckets) is untouched. (For the record: `num_warps` is *not* a bit-safe knob — the `tl.sum(x*x)` reduction tree changes with warp count — so it stays at 4.)

## Benchmarks

Kernel level, B200, K=20480 (hc_mult 4 x hidden 5120), CUDA-graph replay timings:

| M | pair before (us) | pair after (us) | partial alone |
|---|---|---|---|
| 1 | 19.4 | 10.1 | — |
| 7 | 22.2 | 13.2 (-41%) | 14.2 -> 5.0 |
| 8 | 22.7 | 13.6 | — |
| 64 | 54.9 | 20.6 (-62%) | — |

End to end, DeepSeek-V4.1-Flash on 4x B200 (TP4+EP4, `--speculative-algorithm DSPARK --speculative-dspark-block-size 5 --cuda-graph-max-bs-decode 64`), 256K-token prompt, bs=1, out 512, same-seed pairs:

| seed | decode before (tok/s) | decode after (tok/s) |
|---|---|---|
| 70 | 903 | 1138 (+26%) |
| 72 | 890 | 1038 (+17%) |

TTFT unchanged (4.87-4.88 s before and after): prefill row counts do not route through this backend (bf16x3/DeepGEMM paths), and 64 <= m <= 384 already had `num_stages=1`.
