# [Quant] compressed-tensors NVFP4 MoE: add Marlin (W4A16) path

[Upstream PR](https://github.com/sgl-project/sglang/pull/43431) · state: open · merged: False

## Original PR description

## Motivation

`ModelOptNvFp4FusedMoEMethod` can run NVFP4 MoE weights through the Marlin MoE runner (W4A16). It does this automatically on SM80-SM90 and on request on Blackwell (`--moe-runner-backend marlin`). `CompressedTensorsW4A4Nvfp4MoE`, which loads llm-compressor NVFP4 checkpoints such as the `RedHatAI/*-NVFP4` models, has no such path. It raises on anything older than Blackwell, and on Blackwell it always quantizes expert activations to e2m1 (W4A4).

The two cases where this matters:

- **SM80-SM90:** compressed-tensors NVFP4 MoE checkpoints now load and run (W4A16), as ModelOpt ones already do.
- **Blackwell, opt-in:** keeping BF16 activations removes most of the quantization error of these checkpoints, and it speeds up small-batch decode. On `RedHatAI/Qwen3.8-Flash-Next-NVFP4`, with BF16 dense layers, full-vocabulary KLD against the BF16 model over 45,610 positions fell from 0.0176 (W4A4, FlashInfer CUTLASS) to 0.0106 (W4A16, this path), and top-1 agreement rose from 0.961 to 0.971. That number comes from a downstream build on 0.5.21 with this scheme logic overlaid, not from this branch.

## Modifications

`compressed_tensors_w4a4_nvfp4_moe.py`:
- `__init__` selects Marlin the same way ModelOpt does: automatically for SM80-SM90 when the backend is `auto`, otherwise when `--moe-runner-backend marlin` is set. The Blackwell check only rejects configurations that would need FP4 activations.
- Marlin takes w13 as `[gate; up]`, so `load_up_proj_weight_first` is `False` on this path.
- `process_weights_after_loading` inverts the global scales as before, then calls `prepare_moe_nvfp4_layer_for_marlin`.
- `create_moe_runner` builds a `MoeRunnerBackend.MARLIN` runner. A new `get_marlin_quant_info` feeds it, and `apply_weights` returns early on this path.
- `get_min_capability` is 80. The SM100 requirement for FP4 activations is still enforced in `__init__`.

`marlin_utils_fp4.py`:
- `prepare_moe_nvfp4_layer_for_marlin` reads the group size from the weight and scale shapes instead of `layer.quant_config.group_size`, because the compressed-tensors config has no such field. The group-size-16 check is unchanged.

New test `test_compressed_tensors_nvfp4_moe_marlin_matches_dequant_reference` (`test/registered/kernels/ops/moe/test_moe_wna16_marlin.py`):
- It builds a compressed-tensors layer from random NVFP4 weights, with `[gate; up]` rows and the inverted global scale the format stores.
- It runs `process_weights_after_loading` and `fused_marlin_moe`, and compares the result with a float64 reference computed from the dequantized weights.
- Swapping gate and up, or leaving the global scale uninverted, makes it fail.

## Speed Tests and Profiling

Same server and model, `--mem-fraction-static 0.85`, `bench_serving --dataset-name random --random-range-ratio 1 --seed 1`:

| workload | default (W4A4) | Marlin (W4A16) |
|---|---|---|
| c=1, 1024 in / 256 out: output tok/s | 200.2 | 246.7 (+23%) |
| c=1: mean TPOT | 4.87 ms | 3.92 ms |
| c=32, 1024 in / 256 out: output tok/s | 1998.4 | 2060.6 (+3%) |
| c=1, 8192 in: mean TTFT | 156.0 ms | 196.1 ms (+26%) |

Prefill is slower because Marlin runs its large GEMMs on BF16 tensor cores, where CUTLASS uses FP4. That is why this path stays opt-in on Blackwell and the default does not change. Decode is faster because the experts are read once as 4-bit weights, with no activation quantization step.
