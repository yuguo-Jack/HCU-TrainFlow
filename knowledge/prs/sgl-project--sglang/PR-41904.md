# [AMD][DSV4] route bf16->fp32 GEMM to aiter's tuned FlyDSL kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/41904) · state: closed · merged: False

## Original PR description

## Motivation

On ROCm, `linear_bf16_fp32` (bf16 x bf16 -> fp32) runs `torch.mm(out_dtype=fp32)`, i.e. hipBLASLt. For the DeepSeek-V4 compressor `wkv_gate` (K=7168, N=1024 HCA / N=2560 fused CSA) that takes 11-16 us per call at decode sizes (M<=32), and a DSv4-Pro decode step makes 61 of these calls. ROCm/aiter#6005 makes the FlyDSL HGEMM fp32-accurate for fp32 output and adds tuned FlyDSL rows for these shapes (6-14 us).

## Modifications

- `kernels/ops/gemm/bf16_fp32.py`: on ROCm, `_linear_bf16_fp32_cublas` looks up aiter's tuned bf16 -> fp32 config for (M, N, K). If it is a FlyDSL row, it calls `aiter.tuned_gemm.tgemm.mm(x, w, otype=fp32)`. Otherwise it uses `torch.mm(out_dtype=fp32)` as before.
- Depends on ROCm/aiter#6005 for the fp32-accurate kernel and the DSv4 rows (M<=32 only; larger M stays on torch). Without it, none of the current callers' shapes has a FlyDSL fp32 row (the only ones on aiter main are N=6144, K=2048/3072), so everything stays on `torch.mm`. The same holds when aiter is not installed.

## Accuracy Tests

- DSv4 `wkv_gate` shapes (N=1024/2560, K=7168, M=1..112) vs fp64, 1x MI355X, image `lmsysorg/sglang-rocm:v0.5.20-rocm724-mi35x-20260927`:
  - stock aiter: never routed, output bitwise equal to `torch.mm`;
  - aiter + ROCm/aiter#6005: routed for M<=32, max rel err 2e-7..4e-7 (torch.mm 1e-7..5e-7); M>32 not routed, bitwise equal to `torch.mm`.
- `test/registered/kernels/ops/gemm/test_router_gemv_hip.py`: 2/2 pass, with and without ROCm/aiter#6005.
- DSv4-Pro TP8, DSpark (6 drafts), gsm8k 1319 questions, per boot: before 0.942 / 0.943, after 0.944 / 0.945.
