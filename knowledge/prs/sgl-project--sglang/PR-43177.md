# Overlap scheduler startup with the data parallel controller

[Upstream PR](https://github.com/sgl-project/sglang/pull/43177) · state: closed · merged: True

## Original PR description

## Motivation

With attention data parallelism, `Engine._launch_scheduler_processes` starts the data parallel controller process first, and the controller then spawns every scheduler process on the node. The schedulers only begin importing and initializing after the controller has finished its own setup (ZMQ sockets, worker port broadcast, dispatcher wiring), so the two startup phases run back to back instead of overlapping. On a multi-GPU node this adds the controller's whole setup time to the critical path of server startup.

## Modifications

- `engine.py`: when the DP controller is used, attention DP is enabled, and neither elastic EP nor EP join is in use, the launcher pre-spawns the per-rank scheduler processes itself, in parallel with the controller. Each child is started with `run_scheduler_process_with_init_pipe` and a duplex pipe; the controller receives the `(pid, pipe)` map as `prelaunched_schedulers`. In that mode the launcher already knows the scheduler PIDs, so it skips `SCHEDULER_PIDS_ARG`, and on follower nodes `block_until_scheduler_exits` runs a `SubprocessWatchdog` over the pre-spawned processes so that a scheduler crash still tears the node down.
- `data_parallel_controller.py`: `DataParallelController` accepts an optional `prelaunched_schedulers` map. `launch_tensor_parallel_group` keeps computing rank, GPU id, port args and display ranks exactly as before, but when a pre-spawned process exists for `(pp_rank, tp_rank)` it sends those arguments down the pipe instead of calling `mp.Process`. The new `run_scheduler_process_with_init_pipe` target blocks on that pipe, then runs the unchanged scheduler entrypoint with the same pipe for its ready reply, so the ready handshake is unchanged. `run_data_parallel_controller_process` reports the pre-spawned PIDs and, because it does not own those processes, waits on their pipes instead of joining them.
- Launches without attention DP, with elastic EP, or on EP joiners take the existing path and are unchanged. `RayDataParallelController` is unaffected: the new parameter is keyword-optional and defaults to `None`.
- `test_data_parallel_controller.py`: the bare `__new__` controller fixture in `test_controller_collects_all_scheduler_sources` sets `prelaunched_schedulers = None`, because `launch_tensor_parallel_group` now reads that attribute (the file's docstring asks for exactly this when a new attribute is read).
