# Skip the eager activation reserve in KV sizing on a capped Full prefill role

[Upstream PR](https://github.com/sgl-project/sglang/pull/43435) · state: closed · merged: True

## Original PR description

## Motivation

On a disaggregated prefill server with Full prefill CUDA graphs, the KV sizing of Mamba-style hybrid models charges the eager activation reserve (`pre_capture_activation_reserve_mb`, which grows with `chunked_prefill_size`) at two sites:

- the post-capture headroom floor in `compute_post_capture_kv_resize`, charged on top of the graph pool that already holds every captured bucket's activations;
- the configurator's pre-capture Mamba slack, which bounds the KV pool reservation that the post-capture resize clamps to.

That reserve sizes the working set of a prefill batch that runs eagerly. Once `--prefill-max-requests` is at or below the Full graph's request slots (`full_prefill_max_req`), every prefill batch replays a captured bucket, so the charge only shrinks the KV pool. At large chunk sizes the reserve exceeds the configured headroom (`(1 - mem_fraction_static) x pre-model-load memory`) by a wide margin, and even with the post-capture charge removed the pre-capture bound leaves part of the budget unused.

## Modifications

Both sites skip the activation reserve and keep the configured headroom when the role is capped, i.e. when all of these hold:

- `disaggregation_mode == "prefill"`;
- the prefill CUDA graph backend is `full`;
- `--max-mamba-cache-size` is set explicitly;
- `--prefill-max-requests` is set and at most `full_prefill_max_req`.

The explicit Mamba size is part of the condition because with an auto-sized Mamba cache the larger remaining memory would grow the physical Mamba pool instead of the KV bound. Every other configuration keeps the current sizing: no request cap, an auto-sized Mamba cache, breakable / tc_piecewise / disabled prefill graphs, the decode role, non-disaggregated servers, and non-Mamba models. No log line or flag is added.

The post-capture site reads the request slots after capture has clamped them to the request pool; the pre-capture site evaluates the same condition on the pre-clamp slot count. The clamp can only lower the slots, in which case the post-capture site keeps the reserve.

## Accuracy Tests

No numerics change: no kernel, bucket or batch composition is touched, only how much free memory the KV pool may claim on this role.
