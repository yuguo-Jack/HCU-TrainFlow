# [Unified Memory] Support mxfp8 KV cache on the unified memory pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/42396) · state: open · merged: False

## Original PR description

## Motivation

`--enable-unified-memory` with `--kv-cache-dtype mxfp8` passes every startup
check today but cannot work: the unified pool builds a plain
`UnifiedMHATokenToKVPool`, which has no scale buffers. The server boots, sizes
its pools, and dies on the first forward:

```
AttributeError: 'UnifiedMHATokenToKVPool' object has no attribute 'get_kv_scale_buffer'
```

mxfp8 is the only KV dtype that keeps a slot in two pieces — an fp8 payload and
a per-32-element UE8M0 exponent — while the unified pool's premise is one shared
byte buffer. This adds the missing half.

## Modification

A block-scaled sub-pool sets `scale_block_size` on its `MHASubPoolSpec`.
`UnifiedKVPool` allocates each layer's K/V scales as contiguous tensors in the
FA4 interleaved shape, outside the shared buffer, and shrinks that buffer by
`1/scale_block_size` per scaled sub-pool so the pair stays inside the caller's
byte budget. `UnifiedMHATokenToKVPoolMXFP8` binds them and inherits
`MHATokenToKVPoolMXFP8` for the scale read/write path, which already works in
the physical loc space this pool hands out. `move_kv_cache` relocates the
payload by page envelope and the scales per slot.

Two things a reviewer should check:

- **The scale tensors must span exactly the paged KV extent.** FA4 keeps only
  the scale tensor's base pointer and rebuilds its layout by tiling
  `BlockScaledBasicChunk` over `k_cache`'s shape, then indexes it with the raw
  page-table value. Nothing asserts the shape, so a mismatch is a silent
  out-of-bounds read.
- **The K/V views carry the fp8 dtype**, not the `uint8` storage alias the
  unified pool normally uses, because `store_cache` type-checks the destination
  buffer. Hence `MHASubPoolSpec.view_dtype()`.

`mxfp8` and `fp8_e4m3` resolve to the same `torch.dtype`, so the pool factory
takes the resolved dtype string rather than inferring it.

**Breaking change** (`MHATokenToKVPoolMXFP8Host`): the staged write-back gate no
longer requires the payload rows to be packed. The scales move through their own
staging over their own contiguous buffers, so only their own kernel eligibility
matters; conflating the two rejected every unified pool, whose token-major views
are slot-strided. Non-unified pools are unaffected — they already satisfied both
conditions.

## Accuracy Tests

`TestUnifiedMemoryMXFP8HiCacheBitExact` — Inkling `test` revision, FULL+SWA+MAMBA
tri-pool, unified memory + HiCache + mxfp8, deterministic inference, CUDA graphs
and both Inkling fused paths at their stock defaults: **`avg_kl_div=0.0`**. The
pre-existing `TestUnifiedHybridHiCacheBitExact` control also stays at `0.0`.

A batched-decode probe (9 x 512-token prompts, 128 decode tokens) returns 9/9
requests with no null logprobs, bit-identical to the same probe with mxfp8 but
without unified memory.

`test/registered/unit/mem_cache/`: 3020 passed, 1498 skipped, 3855 subtests, no
failures.

Unit coverage is one case for the path an e2e run does not reach:
`TestUnifiedMXFP8ScaleReload` drives device -> host -> device for the scales and
is negative-controlled (skipping the scale load-back turns it red). The three
remaining device-side behaviours — payload/scale round trip, scale page
placement, `move_kv_cache` — are left to the KL test, which was instrumented to
confirm it exercises all of them (`move_kv_cache` fires with 640 slots).

Run on 4x GB300 (SM 10.3).

**[bug]** `init_unified_mamba_pools` now calls `build_unified_mha_pool`, but its `MHASubPoolSpec` never sets `scale_block_size`, and `_init_unified_mamba_pools` never forwards `_unified_scale_block_size()`. `--enable-unified-memory --kv-cache-dtype mxfp8` on a hybrid-Mamba (non-SWA) model still builds a plain `UnifiedMHATokenToKVPool` and hits the same `get_kv_scale_buffer` AttributeError this PR claims to fix. SWA and tri-pool are wired; this third supported unified path is not.

**Suggestion:** Add `scale_block_size` to `init_unified_mamba_pools` (and the configurator call), mirror the tri-pool pattern of checking the bs=1 floor after the scale shrink (pass `bs1_floor_terms` into `UnifiedKVPool` rather than checking only the unshrunk budget), and add a unit smoke that `build_unified_mha_pool` returns `UnifiedMHATokenToKVPoolMXFP8` for that factory when `kv_cache_dtype_str == "mxfp8"`.

- ch-wan · comment · 2026-10-12T08:30:28Z · [source](https://github.com/sgl-project/sglang/pull/42396#discussion_r4246030535)

File: `python/sglang/srt/mem_cache/unified_memory_pool.py` · line 485

**[bug]** `UnifiedKVPool.__init__` now shrinks `total_bytes` by `scale_share` before reserving/allocating the shared payload buffer and sizing scale tensors. `finalize_backing` still treats `config.unified_memory_pool_bytes` as a raw payload size: it does not re-apply the shrink, does not resize scale buffers, and then republishes `_max_slots` from the unshrunk final budget. For post-capture SWA + mxfp8 (SWA is the only unified path that passes `post_capture_active`), that means (1) final capacity no longer matches an eager pool built at the same byte budget, and (2) the final backed payload plus the already-allocated scales can exceed the caller's budget. Tri-pool/Inkling is unaffected today because it never enables post-capture.

**Suggestion:** Apply the same `scale_share` shrink inside `finalize_backing` (and have `config_from_budget` / resize compare against the shrunk value), or document post-capture as unsupported with `scale_block_size` and reject that combination at boot. Prefer shrinking in one place so eager and post-capture stay bit-identical on capacities.

File: `python/sglang/srt/mem_cache/unified_memory_pool.py` · line 959

**[suggestion]** `UnifiedMHATokenToKVPoolMXFP8` forces `mxfp8_sf_interleaved = True` for any `page_size`, while the non-unified pool sets it from `page_size == 128` and keeps a flat scale layout otherwise. `scale_shape()` only requires `page_size % scale_block_size == 0`, so a non-128 page size still builds the interleaved tensor shape; the first `store_sf_interleaved` / host-pool check then fails later. Host already requires interleaved scales, and FA4 production is page_size=128-only.

**Suggestion:** Assert `page_size == 128` (or `page_size == MHATokenToKVPoolMXFP8` interleaved requirement) in `_create_buffers` / `scale_shape` so misconfiguration fails at pool construction rather than on the first store or HiCache attach.
