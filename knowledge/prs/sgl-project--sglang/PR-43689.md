# [sgl-router] Render Qwen3.8 (Max, 27B, Flash-Next) through sglang-processor

[Upstream PR](https://github.com/sgl-project/sglang/pull/43689) · state: open · merged: False

## Original PR description

> [!NOTE]
> **Stack 3/3**, merge in order: #43625 (GLM-5.3) → #43608 (Kimi-K3) → #43689 (Qwen3.8). This PR is based on #43608 (`kan/sgl-router-kimi-k3`), so its diff shows only the Qwen3.8 commit. The Jinja parity-test plumbing (`tests/parity.rs`, `generate_parity.py`, `normalize_tools`) now comes from #43625. After the PRs below merge it gets rebased onto `main`.

Adds Qwen3.8 to sglang-processor and serves it through sgl-router's processor path: Qwen3.8-Max (`Qwen/Qwen3.8-2.4T-A95B`), Qwen3.8-27B and Qwen3.8-Flash-Next.

## Modifications

- **Render:** `ChatFormatter::Qwen38` (`render/models/qwen38.rs`), picked in `from_tokenizer_config` by its template. SGLang renders Qwen3.8 with `apply_chat_template` (no encoding spec), so the processor builds the template context `_process_messages` and `_apply_jinja_template` build and renders it with Dynamo's Jinja formatter:
  - messages, tools and tool calls as the pydantic dumps give them (`Tool`'s null `defer_loading`, `FunctionResponse`'s null `arguments`);
  - content in the template's content format: Max's text-only template gets strings (text parts joined with spaces), the vision template of 27B and Flash-Next gets parts lists, which it concatenates;
  - kwargs over the request effort, then the server's default kwargs.

  Where Dynamo departs from Python, the processor fails rather than render differently, so hosts leave the chat to the engine: a later system turn (Dynamo demotes it, the template raises), media, a `chat_template` kwarg, text whose `trim` differs (U+001C..U+001F), and numbers serde_json prints unlike Python.
- **Router:** renders Qwen3.8 through the processor, so every text chat forwards `input_ids` (`AllText`). The processor does not port the `qwen3` and `qwen3_coder` parsers, so with the cookbook's parsers chats take the engine's OpenAI route; without parsers they are served through `/generate`.
- **Fixtures:** the parity generator renders through `_process_messages` with SGLang's `TemplateManager`, records a Jinja checkpoint's template, and takes per-case server default kwargs. That change now lands in #43625 (GLM-5.3), which this PR is stacked on.

## Checks

- **Render:** 131 cases per checkpoint match SGLang's prompt text and token ids at the pinned revisions (`Qwen/Qwen3.8-2.4T-A95B`, `Qwen/Qwen3.8-27B`, `Qwen/Qwen3.8-Flash-Next`); SGLang rejects 26 to 29 of them, and the processor rejects them too. 7 per checkpoint are `known_gap`s, each one a chat the processor leaves to the engine: media, the `chat_template` kwarg, separators at a trimmed edge, and exponent floats or huge integers.
- **Live:** each model on its cookbook recipe, plus `--log-requests-level 3` and `--served-model-name`. 27B uses the GB300 BF16 cell, since the page has no B300 cell. Flash-Next uses B300 FP8 low latency. Max uses B300 NVFP4 (`RadixArk/Qwen3.8-2.4T-A95B-NVFP4`). Each model ran 168 chats: the fixture cases, streaming, tool calls, sampling, logprobs, n=2, `json_object`, an image, and 11k to 34k-token prompts. Each chat went to the engine directly and then through the router.

  | Model | Engine | Identical `GenerateReqInput` | Router `input_ids` | via `/generate` | Identical responses |
  |---|---|---|---|---|---|
  | Qwen3.8-27B | `qwen3`/`qwen3_coder` parsers | 168 / 168 | 132 | 0 | 166 |
  | Qwen3.8-27B | no parsers, default kwargs `{"reasoning_effort":"low","preserve_thinking":false}` | 168 / 168 | 138 | 120 | 166 |
  | Qwen3.8-Flash-Next | `auto` parsers | 168 / 168 | 132 | 0 | 162 |
  | Qwen3.8-Flash-Next | no parsers, same default kwargs | 168 / 168 | 138 | 120 | 164 |
  | Qwen3.8-Max | `qwen3`/`qwen3_coder` parsers | 168 / 168 | 127 | 0 | 167 |
  | Qwen3.8-Max | no parsers, same default kwargs | 168 / 168 | 133 | 113 | 167 |

  The chats sent without router `input_ids` are the ones SGLang rejects (the engine returns the same 400), the 5 the processor leaves to the engine, and the image. The response differences are `sampling`, the image error (it embeds an object address), and Flash-Next's long prompts. Sent straight to the engine three times, each of these gives 2 or 3 different outputs, so they are engine nondeterminism.
- `cargo test`, `cargo clippy --all-targets -- -D warnings` and `cargo fmt --check` pass for `rust/` and `experimental/sgl-router`, as does `cargo check -p sglang-processor --no-default-features --features render,tokenizer`.
