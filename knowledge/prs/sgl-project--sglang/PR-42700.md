# [HiCache] Fix SWA over-admission of host load-backs that crashes the scheduler

[Upstream PR](https://github.com/sgl-project/sglang/pull/42700) · state: open · merged: False

## Original PR description

## Motivation

With HiCache on a hybrid sliding-window (SWA) model, prefill admission can accept a host load-back that the SWA pool cannot serve. `alloc_for_extend` then raises and the scheduler dies; every later request fails:

```
alloc_for_extend -> alloc_token_slots: RuntimeError: Out of memory. Try to lower your batch size.
Try to allocate 2318 tokens.
Available full tokens: 7949 (full_available_size=4137 + full_evictable_size_=3812)
Available swa: 2270 (available_size=2270 + component_evictable_size_=0)
```

`PrefillAdder.add_one_req` selects the request while only its device match (`req.last_node`) is pinned. After `init_load_back`, the request's sliding-window lock is anchored at `req.best_match_node`, and that window can cover device-resident SWA past `last_node`. Selection counted that SWA as evictable, and nothing charged it: `swa_host_hit_length` covers only the host-only part of the window.

`add_one_req` already pins `best_match_node` around `memory_budget.prepare_load_back(...)`. `SharedSWAPrefillBudget` (unified memory) implements that hook, but `SWAPrefillBudget`, used by the separate FULL/SWA pools and the Mamba tri-pool, inherits the base no-op. So on the default allocator nothing checks SWA with the window pinned.

Observed with Gemma-4-26B-A4B-it (window 1024) on one RTX 5090, at 28 concurrent multi-turn chat sessions, on a build of `main` from 2026-09-21 (a9871012ac). The admission path involved is unchanged on current `main`, and the unit test below reproduces the same accounting on it. The batch was a 2071-token chunk continuation plus a 247-token request whose prefix sat mostly on host (5286 FULL tokens, 1019 SWA tokens to load):

| step | SWA free | SWA evictable | SWA reserved by batch | remaining SWA |
|---|---|---|---|---|
| chunk admitted | 3131 | 508 | 2072 | 1567 |
| load-back selected (needs 1442) | 3131 | 508 | 2072 | 1567 |
| after `init_load_back` | 2112 | 158 | 2072 | 198 |
| after commit | 2112 | 158 | 2495 | -225 |

The load-back allocated the 1019 SWA tokens it was charged for and also locked 350 evictable device SWA tokens (two nodes above the host segment) that it was not charged for.

## Modifications

- `SWAPrefillBudget.prepare_load_back`: run the same SWA check `check_prefill` uses, now with `best_match_node` pinned, so the device SWA the load-back will lock is no longer counted as evictable. An over-committing load-back returns `NO_TOKEN` and is retried in a later round instead of crashing the scheduler.
- `SWAPrefillBudget._swa_fits`: the comparison (`<=` for per-request SWA rings, `<` otherwise), shared by `check_prefill` and `prepare_load_back`.
- FULL needs no re-check: selection already bills every token past the device match as a new allocation.
- Test `TestHiCacheLoadBackSWAWindow` in `test/registered/unit/managers/test_prefill_adder.py` replays the batch above against a tree whose SWA evictable size depends on which nodes are locked:
  - The over-committing load-back must not be admitted, the admitted batch must fit free + evictable SWA, and no lock may leak. This fails on `main`, where the load-back is admitted with 2318 tokens to allocate from 2270.
  - With enough SWA the same load-back is still admitted and leaves only its own locks.

This changes default behavior: an over-committing load-back now waits instead of crashing the scheduler. A load-back that fits is admitted exactly as before, so there is no option to turn it off.

Known limitation: the re-check runs with both admission pins held, the device-match pin on `last_node` and the load-back pin on `best_match_node`. After admission only the `best_match_node` window stays locked, so when the two windows do not overlap, the re-check also excludes up to one window that the request will release. With ordinary SWA pools that slack is negligible, but on a pool of about three windows or less a load-back can be refused every round even on an idle server, where `main` would admit it and run. The same applies to a request that cannot fit the SWA pool even when empty: `check_prefill` shrinks its chunk using the unpinned figure, and the re-check can refuse the shrunk chunk every round. `SharedSWAPrefillBudget.prepare_load_back` behaves the same way.

Two alternatives were considered:
- Run selection itself under the `best_match_node` pin, as the re-check does. This has the same double pin. It also counts FULL KV that is resident behind host-only SWA twice, since `total_tokens` already bills it.
- When the re-check refuses, fall back to recomputing the host part instead of waiting, through the existing `_select_prefill_admission(host_hit_length=0, ...)` path. That removes the stall, but under SWA pressure it trades a short wait for recomputing the whole host hit. I kept the smaller change; happy to switch if reviewers prefer the fallback.

Related: #42703 keeps a cached prompt reusable by a short re-match on SWA models; it came from the same Gemma-4 chat load. Independent of this PR.

## Speed Tests and Profiling

No reproduction on a public model: the crash depends on which SWA nodes the device match leaves behind, and a 15-minute load did not hit it on `main`. The unit test above is the reproduction. The same load checks that the re-check costs nothing when it does not fire.

Setup: `google/gemma-4-E4B-it` on one RTX 5090, `--enable-hierarchical-cache --hicache-size 8 --hicache-write-policy write_through --max-total-tokens 60000 --swa-full-tokens-ratio 0.35` (21K-token SWA pool). Load: 40 multi-turn sessions taking turns through 24 concurrent workers for 15 minutes, greedy `/generate` with `input_ids`. Each session starts from a 3000-token prompt and adds its 150-token reply and 200 new tokens per turn, resetting at 6000 tokens.
