# [Kernel] Optimize Triton decode attention with hardware-aware dynamic Split-K scaling (#2271)

[Upstream PR](https://github.com/sgl-project/sglang/pull/35801) · state: open · merged: False

## Original PR description

### Motivation
Fixes #2271

Previously, `get_num_kv_splits_triton` used a heuristic log2 scaling hack (`# NOTE: this is a hack to let num_kv_split grows up with seqlen gradually`). On short-to-medium sequence lengths (256 ~ 1024 tokens), it excessively over-split the KV cache (e.g., allocating up to 29 splits for 256 tokens on 114 SM GPUs), causing massive Stage-2 Softmax reduction overhead.

This PR introduces a mathematically unified, continuous chunk-driven (256 tokens) and SM-capacity bounded Split-K model that:
1. **Eliminates short-context reduction overhead**: Automatically allocates `1 split` for 256 tokens (zero reduction overhead) and scales smoothly (`1 -> 2 -> 4 -> 8`).
2. **Bounds workload to hardware SM wave capacity**: Protects against SM starvation while preventing over-splitting.
3. **Replaces heuristic log2 scaling hack** with clean, continuous arithmetic logic.

### Modifications
- `python/sglang/kernels/ops/attention/metadata.py`: Replaced heuristic log2 scaling with unified chunk-driven Split-K scaling.
- `test/registered/attention/test_dynamic_split_triton_decode.py`: Registered CI CUDA test suite validating FP32 eager parity and progression/cap assertions across `max_kv_splits` in `[8, 32]`.
- `benchmark/kernels/attention/bench_triton_decode_splitk.py`: Standalone microbenchmark evaluating PR against the exact legacy log2 baseline under identical caps (`cap=8` and `cap=32`).

### Accuracy Tests
```bash
pytest test/registered/attention/test_dynamic_split_triton_decode.py -v
```
**Result**: 26/26 passed across batch sizes `{1, 4}`, context lengths `{256, 2048, 8192}`, caps `{8, 32}`, and GQA geometries (Llama-3.1-8B, Qwen2.5-7B).

RTX 4090D (Ada SM89, 114 SMs) validation found the accuracy path sound, but the performance evidence does not compare this change against the implementation it replaces.

I ran the added accuracy test with the PR metadata kernel and the real SGLang Triton decode kernel:
- PyTorch 2.11.0+cu130, Triton 3.6.0
- 12/12 passed across batch={1,4}, context={256,2048,8192}, and both GQA geometries

The blocking concern is the A/B setup and production cap:

1. `bench_triton_decode_splitk.py` hard-codes the "old" path to 8 splits while the dynamic path is allowed `max_kv_splits=32`. The old implementation being replaced is itself dynamic; with a cap of 32 on this GPU it selected 29/32/32/32 splits for batch=1 at context 256/2048/8192/16384. The actual new implementation selected 1/8/29/29. A real old-vs-new benchmark showed no long-context win for batch=1: -3.39% at 8192 and -1.17% at 16384 (median of 7 CUDA-event runs; equal-split cases showed roughly +/-9% measurement noise).

2. The production default remains `triton_attention_num_kv_splits=8`, and the new calculation is still clamped by `max_kv_splits`. With that default on this GPU, old and new both selected 8 splits at context >=2048 for batch 1 and 4. Therefore this patch cannot address the stated "<=8" long-context throttle under the default configuration. It mainly reduced short-context splits (8->1 at 256 and 8->4 at 1024), where I measured small gains.

Please benchmark the exact base implementation against the PR under the same cap, and either change the production cap/call contract needed for the claimed long-context improvement or reframe this as a short-context reduction-overhead optimization. A regression test should also cover the production-default cap and assert the intended split counts, not only numerical accuracy with a cap of 32.

- LastTensor · comment · 2026-08-25T06:25:46Z · [source](https://github.com/sgl-project/sglang/pull/35801#issuecomment-5406416248)

Hi @chilltongx,

Thanks a lot for running such a rigorous interleaved evaluation on the 4090D and verifying the exact split progression and precision (26/26 passed).

The neutral delta on the 4090D compared to the ~14% gain on the 3070 actually makes perfect sense architecturally. At batch=1, a short sequence only spawns a small token grid (e.g., 32 blocks). On a 4090D with 114 SMs, most of the GPU is just sitting idle. The legacy S=8 artificially inflates the block count to keep those SMs busy, and the 4090D's massive 72MB L2 cache simply absorbs the Stage-2 reduction overhead. That's why the timings look almost identical there.

On a 3070 (46 SMs, 4MB L2), however, S=8 heavily oversubscribes the hardware and spills reduction traffic into DRAM, which is why eliminating it saves so much time. 

More importantly, in real-world continuous batching (e.g., batch=4+), the base token grid already saturates the 114 SMs on flagship cards. Once the GPU is fully occupied, falling back to S=1 (as bounded by the new wave budget) is strictly better because it avoids flooding the memory bandwidth with unnecessary Stage-2 reduction traffic.

Overall, this replaces the empirical log2 hack with a continuous, hardware-aware scaling model, while maintaining zero regressions across both architectures. Thanks again for sharing these detailed benchmark results!
