# [Fix] Keep request-pool row generations monotonic across clear()

[Upstream PR](https://github.com/sgl-project/sglang/pull/43439) · state: closed · merged: True

## Original PR description

## Motivation

`ReqToTokenPool.clear()` and `DecodeReqToTokenPool.clear()`, which run on `/flush_cache` and on a disaggregation role switch, reset `req_generation` to zero. Readers of that tensor detect row reuse by comparing a generation they stored against the live value. After a flush, the first request on a row gets generation 1 again, which is exactly what the row's previous request carried whenever the row served one request since the previous flush or startup (always the case when a client flushes between batches). The stored generation then still matches, and state kept for the previous request is attributed to the new one.

The speculative verify-budget planner is such a reader (`HostConfidenceBudgetPlanner.compute_budget` compares the relayed generation with the current one): with a flush between batches it can budget a request's first verify steps from the confidence of the row's previous request. Any future reader that keys per-row state on `req_generation` inherits the same hole.

## Modifications

- `ReqToTokenPool.clear()` and `DecodeReqToTokenPool.clear()` keep `req_generation` instead of zeroing it. `HybridMambaDecodeReqToTokenPool.clear()` already did. Generations only increase, so a stored generation never matches a later request on the same row.
- `test/registered/unit/disaggregation/test_decode_req_to_token_pool.py`: a parametrized CPU case over both pools allocates a row, clears the pool, re-allocates the same row and checks that its generation moved. Both cases fail before this change (`assert 1 != 1`).

No kernel, model or sampling change. Behaviour changes only for a request that reuses a row after a flush or role switch, and only for readers of `req_generation`; with none active this is a no-op.

## Accuracy Tests

Not applicable: the change is bookkeeping for generation readers only. Model outputs change only on the verify-budget path after a flush, where the budget now comes from the request's own confidence instead of the previous occupant's; verification itself is unchanged.

## Speed Tests and Profiling

Not applicable: one tensor zero-fill removed from a flush path.
