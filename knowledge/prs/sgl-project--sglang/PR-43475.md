# [Fix] Repair multimodal VMM lease cleanup and source-stream ordering

[Upstream PR](https://github.com/sgl-project/sglang/pull/43475) · state: closed · merged: True

## Original PR description

## Summary

Fix multimodal GPU transport lifetime bugs found while investigating #43402. Thanks to @StarDuster for the report and native-stack evidence.

- Release unconsumed features on queued aborts, early rejection, and peer reconstruction failure. Session aborts release the current turn's media without invalidating borrowed history or skipping KV cleanup.
- Keep publisher rollback alive across repeated asyncio cancellation.
- Acknowledge only the current consumer, not its peers; keep unused raw features available for later re-prefill. Match consumer slots to the routed attention-DP group.
- Poll VMM acknowledgements outside the allocator lock and recheck allocation identity before reclaiming. Disable incompatible IPC borrowing for VMM.
- Wait for the producing CUDA stream before VMM publication or CPU fallback, including across the asynchronous publisher's thread boundary.

No pool-size, default-backend, or fixed-HBM-budget change.

## Remaining investigation

This fixes the reproduced leak and stream-ordering defects, **not a proven fix for the reported CUDA-driver D2H hang**. A two-hour synthetic baseline soak on original `e8fb52c5` completed 454,724 dispatches (302,413 VMM / 152,311 CPU fallbacks), with all eight consumers passing, both node exits 0, and the full 1 GiB pool free at shutdown. The paired two-hour fixed-source soak at `193aa211` also completed: 453,447 dispatches (301,495 VMM / 151,952 CPU fallbacks), all eight consumers passed, both node and wrapper exits were 0, and the full 1 GiB pool was free at shutdown. Its independent preprocessing loop completed 2,095,671 iterations; maximum observed wrap duration was 0.4287 seconds. Both nodes' logs and exit markers were preserved and SHA-256 verified. Both explicitly synchronize the source stream to isolate the unresolved hang from the separately reproduced stream-ordering bug; this is not a performance comparison.

Neither version reproduced the production hang on driver 580.159.04. This synthetic workload does not replay customer traffic or load full Kimi-K3 weights; the reporter's driver 580.126.20 remains untested. Keep #43402 open for the separate hang investigation.
