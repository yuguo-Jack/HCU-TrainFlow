# [Fix] Mamba slot admission for the classic hybrid pool: gate the scheduler, never assert the engine

[Upstream PR](https://github.com/sgl-project/sglang/pull/43484) · state: open · merged: False

## Original PR description

## Description

**Symptom**: on hybrid-SSM models (Qwen3-Next / Qwen3.8 GDN family) with the classic `HybridReqToTokenPool` (i.e. **without** `--enable-unified-memory`), two concurrent long requests deterministically crash the scheduler:

```
AssertionError: Can not alloc mamba cache
  .../unified_cache/components/mamba.py:509: _alloc_mamba_slot
```

Repro on a 27B GDN model, `--max-mamba-cache-size 10` (auto-sized): fire two ~90K-token requests concurrently → dead. Two ~30K requests with `mamba_track_interval=64` → also dead. The assert kills every in-flight request on the engine; nothing else dies gracefully.

**Root cause**: the scheduler *does* have a mamba-slot admission ledger (`PrefillAdder.rem_mamba_slots`, `schedule_policy.py`), but it is gated on `isinstance(token_to_kv_pool_allocator, UnifiedMamba*Allocator)` — it only fires for the **unified memory pool**. With the classic hybrid pool, `mamba_allocator` is a separate free-list the ledger never sees, so admission checks nothing. Meanwhile each new mamba request really costs **3 slots** (`MAMBA_STATE_PER_REQ_PREFIX_CACHE`: 2 ping-pong + 1 running — the constant `alloc_req_slots` reserves with), plus one donated checkpoint per cache boundary. Two long requests ≈ 10+ slot demand against a 10-slot pool; the ledger admits both; the first donation with no evictable slot left asserts.

The gap is even acknowledged in-place: the FIXME in `_mamba_gap_budget_for_req` says *"if over-admission crashes under pressure, make this more conservative (e.g. multiply by `MAMBA_STATE_PER_REQ_PREFIX_CACHE`)"* — this PR does exactly that, for the pool shape where the ledger was dormant.

**Fix** (two files):

1. `schedule_policy.py` — extend the ledger to the classic pool: `rem_mamba_slots = pool.mamba_allocator.schedulable_available_size() + tree_cache.mamba_evictable_size()`, charge `MAMBA_STATE_PER_REQ_PREFIX_CACHE(_LAZY)` per newly-admitted request, and gate `budget_state()` on the *full* factor (`< _mamba_slots_per_req` instead of `<= 0`). The unified-pool path is untouched (`_mamba_slots_per_req = 1`, byte-for-byte upstream behavior). When the ledger says no, the request simply stays queued — the scheduler already handles `AddReqResult.NO_TOKEN` as "batch full".
2. `components/mamba.py` — the two `assert ... "Can not alloc mamba cache"` sites are **mid-request** paths (donation at chunk/track boundaries; COW of a matched state during `init_next_round_input`, which runs *before* the admission gate can help). A lost checkpoint should cost the donor a cache entry, not the engine every other request:
   - donate path: skip this donation (live slot untouched, re-donates next boundary) → `return 0`;
   - COW path: return `zero_match_result(...)` — the request gets no prefix reuse and recomputes, i.e. exactly a normal cache miss.
   Both log a `logger.warning` with the actionable knob (`--max-mamba-cache-size`).

**Why the assert can't be the backstop**: both sites run inside the scheduler's batching loop; raising there tears down the TP scheduler process and takes the whole engine down — every queued and in-flight request dies with it, on perfectly ordinary (if tight) workloads.

## Tests

On 2×RTX 5060 Ti 16GB (TP2), Qwen3.8-27B-NVFP4 + NEXTN MTP, HiCache kernel backend, `--max-mamba-cache-size 10`, `mamba_track_interval=64`:

- **Before**: 2 × ~90K-token cold concurrent requests → `AssertionError: Can not alloc mamba cache`, scheduler dead (deterministic; also reproduces at 2 × 30K).
- **After**: same battery returns both completions (60.9 s wall, engine alive, zero asserts in log).
- Regression suite unchanged: greedy probe exact; 4×dual-cycle accept-mean battery green (3.00/2.99); 10×turns HiCache battery green; 45K/100K/150K cold-prefill ladder green; single-stream decode 70–90 tok/s, accept 2.1–2.9.

## Also worth noting

`available_size()` on the classic `MambaSlotAllocator` is the exact free-list length (its `schedulable_available_size()` is documented as the same view for a static pool), so the ledger init reads honestly on both pool shapes.
