# [NVIDIA][MegaMoE] Fix the default spec decoding moe backend when the target model uses flashinfer megamoe

[Upstream PR](https://github.com/sgl-project/sglang/pull/40772) · state: open · merged: False

## Original PR description

## Summary

- Fixes an `illegal memory access` crash (sgl-project/sglang#40623) that occurs when `--moe-a2a-backend flashinfer_megamoe --moe-runner-backend flashinfer_megamoe` is combined with `--speculative-algorithm EAGLE` on a checkpoint whose MTP/NextN draft layer is unquantized (e.g. GLM-5.2-NVFP4, DeepSeek-NVFP4). The draft's MoE runner/a2a backend silently inherited the target's `flashinfer_megamoe`, so `StandardDispatcher.skip_local_expert_mapping` (`token_dispatcher/standard.py`) assumed the mega kernel's own global-expert-ID routing and skipped the EP global->local expert-id remap — but the unquantized draft layer actually falls back to the plain Triton MoE kernel, which needs that remap. Under EP (`ep_size > 1`) this feeds Triton out-of-range expert indices into EP-sharded local weight tensors, crashing `invoke_fused_moe_kernel`.
- `_speculative_moe_runner_default` (`arg_groups/overrides.py`) now falls back to `auto` instead of `flashinfer_megamoe` when defaulting the speculative runner backend from the target's backend; `initialize_moe_config()` (`layers/moe/utils.py`) applies the same default for both `speculative_a2a_backend` and `speculative_runner_backend` for call paths that construct the MoE flags directly (e.g. benchmark scripts) rather than through the full CLI resolution pipeline. `--speculative-moe-runner-backend` / `--speculative-moe-a2a-backend` still take precedence when set explicitly.
- Adds `GlmMoeDsaForCausalLM` (GLM-5.2/5.3-NVFP4) to `validate_flashinfer_megamoe_model`'s supported-architectures list, so megamoe is reachable for this family at all.

## Root cause

- `create_moe_dispatcher` (`layers/moe/fused_moe_triton/layer.py`) routes both `a2a_backend.is_none()` and `a2a_backend.is_flashinfer_megamoe()` to the same `StandardDispatcher` class.
- `StandardDispatcher.__init__` (`layers/moe/token_dispatcher/standard.py`) independently reads `get_moe_runner_backend()` to decide `skip_local_expert_mapping`; it skips the remap whenever the ACTIVE runner backend is `flashinfer_megamoe`, trusting the mega kernel to route by global expert ID internally.
- `UnquantizedFusedMoEMethod.create_moe_runner` (`layers/quantization/unquant.py`) has no `flashinfer_megamoe` branch, so an unquantized layer (the MTP/NextN draft) always falls through to the plain Triton runner regardless of the configured backend.
- Because `speculative_moe_runner_backend` defaulted to inheriting the target's `moe_runner_backend`, the draft's dispatcher believed it was running the mega kernel (skipping the remap) while its actual runner was Triton (which needs the remap) — global-space expert IDs then index into EP-sharded local weight tensors sized for only `num_experts / ep_size` experts.

## Repro

DEP4 on Blackwell:

​```bash

python -m sglang.launch_server \
  --model-path /path/to/glm-5.2-nvpf4 \
  --load-format dummy \
  --trust-remote-code \
  --tp-size 4 \
  --dp-size 4 \
  --enable-dp-attention \
  --moe-runner-backend flashinfer_megamoe \
  --moe-a2a-backend flashinfer_megamoe \
  --speculative-algorithm EAGLE \
  --speculative-num-steps 3 \
  --speculative-eagle-topk 1 \
  --speculative-num-draft-tokens 4 \
  --mem-fraction-static 0.7
​```

Before this fix: crashes during CUDA graph capture of the draft decode step with `RuntimeError: Triton Error [CUDA]: an illegal memory access was encountered` (`invoke_fused_moe_kernel`). `--speculative-moe-a2a-backend none --speculative-moe-runner-backend triton` is necessary to workaround. After this fix, `server_args` resolves `speculative_moe_runner_backend=auto` / `speculative_moe_a2a_backend=none`, the server starts cleanly, and `/generate` requests (and a gsm8k `bench_sglang.py` smoke run) complete without crashing.
