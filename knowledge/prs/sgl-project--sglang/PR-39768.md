# [PD][GLM-5.x] Improve PP prefill to DCP decode KV transfer

[Upstream PR](https://github.com/sgl-project/sglang/pull/39768) · state: open · merged: False

## Original PR description

Depends on #36990.

## Motivation

Inspired by PR #36990, this PR builds on it to improve DCP support for PD-disaggregated deployments. The main changes introduced in this PR are as follows:

- Extend the packed DCP transfer path introduced in #35762 to prevent oversized DCP1-to-DCP-N KV transfers from generating an excessive number of RDMA descriptors. When the complete transfer plan exceeds the reusable GPU pack buffer, the existing path falls back to fragmented transfers for interleaved source KV rows.
- Split oversized transfer plans into buffer-sized chunks and apply packing to each chunk, preserving large-block RDMA transfers through Mooncake.
- Synchronize pack-buffer reuse between chunks and add tests for oversized and partial-chunk transfers.

The target production topology is GLM-5.2 with PP8 prefill and single-node DCP2+DP4 decode over Mooncake. DCP2 shards each request's decode KV cache across two GPUs, enabling a single decode node to serve 1M-token contexts while retaining four DP replicas. On the tested long-input, high-concurrency workload, PP8 achieved higher end-to-end throughput than TP8.

## Server commands

Decode server, TP8+DP4+DCP2:

```bash
python3 -m sglang.launch_server \
  --model-path GLM-5.2-W4AFP8 \
  --quantization w4afp8 \
  --disable-shared-experts-fusion \
  --tp-size 8 \
  --dp-size 4 \
  --dcp-size 2 \
  --enable-dp-attention \
  --enable-dp-lm-head \
  --moe-dense-tp-size 1 \
  --disaggregation-mode decode \
  --attention-backend nsa \
  --dsa-prefill-backend flashmla_kv \
  --dsa-decode-backend flashmla_kv \
  --kv-cache-dtype fp8_e4m3 \
  --page-size 64 \
  --context-length 1048576 \
  --max-running-requests 128 \
  --cuda-graph-max-bs 32 \
  --mem-fraction-static 0.83 \
  --trust-remote-code
```

Prefill server, TP1+PP8+DCP1:

```bash
export SGLANG_PP_LAYER_PARTITION=10,10,10,10,10,10,10,8

python3 -m sglang.launch_server \
  --model-path GLM-5.2-FP8 \
  --tp-size 1 \
  --pp-size 8 \
  --dp-size 1 \
  --dcp-size 1 \
  --disaggregation-mode prefill \
  --attention-backend nsa \
  --dsa-prefill-backend flashmla_kv \
  --kv-cache-dtype fp8_e4m3 \
  --page-size 64 \
  --context-length 1048576 \
  --chunked-prefill-size 8192 \
  --max-running-requests 128 \
  --mem-fraction-static 0.82 \
  --trust-remote-code
```

## Performance

### Stability comparison with original #36990

| Workload | Original #36990 | Bounded packing |
| --- | --- | --- |
| TP8, 104K shared prefix, C1 | Transfer timeout | Completed |
| PP8, 100K shared prefix, C16 | KV waiting timeout | Completed |

This historical comparison records whether the oversized cached-prefix transfers complete; it is not a matched throughput benchmark.

### Ablation against #35762 whole-plan packing

The direct ablation keeps the same PP8 -> DCP2+DP4 topology, models, Mooncake transport, server limits, and 100K shared-prefix workload at concurrency 1. The workload generates 500 output tokens per request. The baseline uses whole-plan packing; the optimized version adds capacity-bounded packing and sender draining.

| Transfer strategy | Output tok/s | Mean TTFT | Mean TPOT |
| --- | ---: | ---: | ---: |
| Whole-plan packing | 24.35 | 9.748 s | 21.61 ms |
| Bounded packing | 42.84 | 0.701 s | 21.99 ms |
| Relative change | **+75.9%** | **-92.8%** | +1.7% |

The baseline is slower because oversized transfer plans fall back to many small RDMA descriptors for interleaved source KV rows, increasing KV handoff time and TTFT.

### PP8 versus TP8 prefill

All rows use bounded packing and DCP2+DP4 decode. The shared-prefix, GSM8K, and LongBench rows compare TP8 and PP8 on matched workload data. The cold-input rows were collected in separate completed runs with different server limits and are included as workload observations rather than a single-variable topology ablation. The shared-prefix rows use a 100K-token prefix and 500 output tokens per request. The cold-input rows use random 100K-token inputs, flush the prefix cache, and generate 500 output tokens per request. The GSM8K row submits all 1,314 evaluation prompts through the non-streaming completion API. The LongBench row uses the same 503 prompts for both topologies, submits all requests without a client-side concurrency cap, and sets `max-running-requests=128` on the services; its TTFT values therefore include client-side queuing.

| Workload | Client load | TP8 output tok/s | PP8 output tok/s | TP8 mean TTFT | PP8 mean TTFT | TP8 mean TPOT | PP8 mean TPOT |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 100K shared prefix | C1 | 42.18 | **42.30** | **0.498 s** | 0.756 s | 22.75 ms | **22.17 ms** |
| 100K shared prefix | C64 | **1342.78** | 1288.39 | **2.811 s** | 3.161 s | **40.05 ms** | 41.28 ms |
| 100K cold input | C1 | 24.08 | **32.60** | 9.715 s | **4.286 s** | **22.14 ms** | 22.15 ms |
| 100K cold input | C32 | 52.80 | **181.40** | 273.951 s | **71.460 s** | **21.85 ms** | 23.57 ms |
| GSM8K | all 1,314 | **2263.50** | 2229.57 | - | - | - | - |
| LongBench v2 | all 503 | 378.00 | **1092.81** | 2327.849 s | **594.390 s** | **31.15 ms** | 47.92 ms |

The updated transfer path supports both TP8 -> DCP2+DP4 and PP8 -> DCP2+DP4. Throughput depends on the workload: TP8 is 1.5% faster on the short-input GSM8K workload, while PP8 delivers 2.89x higher output throughput on the long-input LongBench workload.
