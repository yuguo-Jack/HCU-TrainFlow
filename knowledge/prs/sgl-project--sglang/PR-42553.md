# [ROCm] Eliminate HiCache migration stalls and use exact-size host allocations

[Upstream PR](https://github.com/sgl-project/sglang/pull/42553) · state: open · merged: False

## Original PR description

## Motivation

Add an opt-in, non-USERPTR allocation path for ROCm HiCache host pools to avoid page-migration-related GPU stalls. Request the pool's byte count directly from HIP rather than allocating through PyTorch's caching host allocator.

ROCm 7.2 enables USERPTR for the relevant paged-memory allocations when `HSA_USERPTR_FOR_PAGED_MEM` is unset; only `0` disables it ([default initialization](https://github.com/ROCm/rocm-systems/blob/rocm-7.2.0/projects/rocr-runtime/libhsakmt/src/fmm.c#L2810)). Its [host-allocation code](https://github.com/ROCm/rocm-systems/blob/rocm-7.2.0/projects/rocr-runtime/libhsakmt/src/fmm.c#L2091) selects between anonymous-memory USERPTR mappings and driver-managed GTT allocations.

Setting the variable alone does not change HiCache's existing `hipHostRegister` path. This PR switches eligible pools to `hipHostMalloc` without changing the ROCm default.

## Changes

The implementation is in [`pool_host/common.py`](https://github.com/jiejingzhangamd/sglang/blob/1a5d0287ec2c23fa4074f637ba92eb3ff9801322/python/sglang/srt/mem_cache/pool_host/common.py#L239).

- Use the new path only on ROCm, with pinned memory, the default `HostTensorAllocator`, and `HSA_USERPTR_FOR_PAGED_MEM=0`.
- Bind the already-loaded HIP runtime and request `numel * dtype.itemsize` bytes with `hipHostMalloc`.
- Expose the allocation as a tensor without copying. Free it after the last tensor/view reference is released; skip `cudaHostUnregister` for these pools.
- Report allocation failures with the GTT capacity reference and a suggestion to reduce `--hicache-size`; do not silently fall back to USERPTR.
- Leave custom allocators, unpinned allocations, non-ROCm platforms, and configurations without the opt-in unchanged.

The exact-size allocation change comes from [JohnQinAMD's commit `1a5d028`](https://github.com/JohnQinAMD/sglang-amd/commit/1a5d0287ec2c23fa4074f637ba92eb3ff9801322).

## Usage

Set this before starting SGLang, so it takes effect before HIP initialization:

```bash
export HSA_USERPTR_FOR_PAGED_MEM=0
```

The GTT path remains subject to driver allocation limits. `SGLANG_HUGEPAGE_SIZE` does not apply to this path; the allocator logs a warning if it is set.

[`test_hicache_host_register.py`](https://github.com/jiejingzhangamd/sglang/blob/1a5d0287ec2c23fa4074f637ba92eb3ff9801322/test/registered/unit/mem_cache/test_hicache_host_register.py#L72) covers exact allocation size, release after the last view, skipping host unregister, unchanged allocation paths, and allocation failure without fallback. ## Reproducing the migration stall

[`bench_host_memory_migration.py`](https://github.com/jiejingzhangamd/sglang/blob/b9ea0f359df5e7e9c352ca1f8a85f29e5dcf4f71/benchmark/hicache/bench_host_memory_migration.py) is included in this PR. This is a manual hardware test requiring two memory NUMA nodes, sufficient host/GTT memory, and permission to call `move_pages()`; it is not part of regular CI.

Run the two arms in separate processes on the same idle GPU:

```bash
export HSA_USERPTR_FOR_PAGED_MEM=0
python benchmark/hicache/bench_host_memory_migration.py --allocator registered --pool-gb 180
python benchmark/hicache/bench_host_memory_migration.py --allocator gtt --pool-gb 180
```

The registered arm calls the legacy mmap + host-register path; the GTT arm calls the patched allocator. Both use the same environment. Each iteration runs four 4096-by-4096 BF16 matrix multiplications, a 16 MiB host-to-device copy, and synchronization. A second thread attempts three 2 MiB migrations, with 1,000 GPU iterations after each attempt. The script checks page-migration status, copy correctness, CPU wall-clock latency, and `/sys/class/kfd/kfd/proc/<pid>/stats_<gpu>/evicted_ms`. For a container, `--kfd-pid` identifies the worker's host PID without requiring a shared PID namespace.

Measured on MI355X GPU0, `crsuse2-m2m-168`, using the PR checkout in the 0924 image above (Docker CPU quota: 8; memory limit: 256 GiB). Both arms exited successfully.

| Allocation | Maximum iteration time, trials 1 / 2 / 3 (ms) | Largest per-GPU KFD eviction delta per trial (ms) |
| --- | ---: | ---: |
| Registered USERPTR | 64162.856 / 64141.420 / 64152.832 | 64159 / 64140 / 64149 |
| Exact-size GTT | 0.796 / 0.891 / 0.792 | 0 / 0 / 0 |

The USERPTR arm moved all 512 pages on every attempt. The GTT arm returned `-EFAULT` for all 512 page-status entries each time, with zero eviction. Control median iteration times were 0.723 ms and 0.722 ms, respectively.

These are induced GPU-workload stalls, **not token latency or P90 interactivity**. The result establishes the migration/eviction behavior for this setup, not a general end-to-end speedup.

## Performance

A fresh same-node sequential A/B was run on MI355X node `crsuse2-m2m-059` (SPUR job `196589`). Both arms used `lmsysorg/sglang-rocm:v0.5.20-rocm720-mi35x-20260924`, GLM-5.2 MXFP4, TP4/EP4, MTP 5/6/1, concurrency 8, HiCache 180 GB per rank, random seed 42, and a configured 3,600-second AgentX profiling window. #### HiCache/AITER failure triage

I investigated the HiCache failure in more detail. The evidence strongly indicates that it is not caused by this PR:

- The crash happens during decode CUDA-graph capture while AITER is JIT-compiling `module_moe_ck2stages_b16_b16_preshuffle_off_b16_silu_no_mulWeightStage2`. Three parallel clang compilations fail with `malloc(): smallbin double linked list corrupted`, a segmentation fault, and `free(): invalid pointer`.
- This occurs before `build_kv_cache() -> init_hicache()`. The failed log never reaches the 200 GB HiCache host-pool allocation.
- The CI job does not set `HSA_USERPTR_FOR_PAGED_MEM=0`. Therefore the new `hipHostMalloc`/GTT branch added by this PR is not selected; the test retains the existing USERPTR allocation path.
- The [preceding scheduled-main shard](https://github.com/sgl-project/sglang/actions/runs/37395620023/job/112050816803) used the same ROCm image digest and AITER revision, built the same AITER module, allocated the HiCache pool, and passed. The [following scheduled-main shard](https://github.com/sgl-project/sglang/actions/runs/37553745648/job/112575126352) also passed.

I also ran `TestHiCacheMLA.test_mmlu` locally at PR head `c7453ec` on MI355X with the matching ROCm 10 image date and AITER revision, leaving `HSA_USERPTR_FOR_PAGED_MEM` unset as in CI. A fresh JIT build of the same AITER module completed in 48.1 seconds; CUDA-graph capture completed, the 200 GB HiCache host pool was allocated, and the server became healthy. The accuracy phase was then blocked only by an HTTP 429 while fetching the pinned MMLU archive. Separately, all 15 allocator unit tests pass locally.

The local run is not an exact gfx942 reproduction, but together with the execution order, inactive PR code path, and the two passing adjacent-main controls, it supports treating this as a transient ROCm clang/AITER JIT runner failure rather than a regression from #42553.

The MORI failure is also a one-off clang exit-code-139 during dependency installation; its [preceding-main shard passed](https://github.com/sgl-project/sglang/actions/runs/37395620023/job/112050816904), and it happens before the test suite can exercise this PR. The remaining gate failures are downstream consequences, not additional test failures.

Overall, the AMD CI evidence does not indicate a regression caused by this PR.
