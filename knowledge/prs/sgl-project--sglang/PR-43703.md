# [Perf] Autotune low-M BF16 GEMMs via FlashInfer CuTe DSL on Blackwell

[Upstream PR](https://github.com/sgl-project/sglang/pull/43703) · state: open · merged: False

## Original PR description

**Depends on #43494** (FlashInfer 0.7.1): merge after it lands. 0.7.1 includes flashinfer-ai/flashinfer#5705, which keeps saved `bf16_gemm` tactics usable on later boots. 0.7.0.post1 re-tunes on every boot.

## Motivation

Low-M BF16 decode GEMMs on Blackwell leave measurable performance on the table versus cuBLAS. So far that gap has been closed by hand-measured per-shape tables (`_BF16_SPLITK_TUNED_TACTICS`), which needs a new row for every model, weight shape and M. This PR lets FlashInfer pick the kernel per shape and M bucket instead.

FlashInfer's `mm_bf16(backend="cute-dsl")` autotunes over the direct, warp split-K and cluster split-K low-M kernels. sglang's existing FlashInfer autotune pass drives the tuning, so no per-model or per-shape code is needed.

## Modifications

- On by default when the BF16 GEMM backend is CuTe DSL (the default on Blackwell). Contiguous BF16 linears with M <= 16 (with or without a BF16 bias) go to `mm_bf16(pdl=True, backend="cute-dsl")`, in both `_bf16_gemm_dispatch_impl` and `apply_into`. `--disable-flashinfer-autotune` turns it off.
- Tuning: inside the FlashInfer autotune context, a larger M (the autotune dummy forward) profiles the M <= 16 buckets on a 16-row slice of each linear. `should_run_flashinfer_autotune` now also fires when this path is active.
- First boot tunes each unique BF16 weight shape once; later boots load the cache.
- Removes what the autotuned path makes unreachable: the 60 M <= 16 rows of `_BF16_SPLITK_TUNED_TACTICS`, the direct-kernel branch, and the Qwen4-Exp precompile hook. The 8 GB300 rows at M = 24/32 stay. Net diff: +70/-113.

Kernel level (cold-L2 graph replay, B300, FlashInfer 0.7.1), on the 60 removed hand-table cells (GB300 TP16 and Qwen4-Exp shapes, M <= 16):

|---|---:|
| hand-tuned table | 1.71x |

The autotuned pick is faster than cuBLAS on all 60 cells, and faster than the hand tactic overall (1.04x geomean). It is slower than the hand tactic by more than 5% in 14 cells; the worst is (16, 512, 8192) at 0.74x. These cells were already served by the autotuned path before the rows were removed. The cause is FlashInfer's tuner timing (see Known limitations).

On Qwen3-VL-4B's own shapes, M = 1..16: gate_up 19456x2560 1.09→0.98x, qkv 6144x2560 1.11–1.33x, down 2560x9728 1.22–1.37x vs cuBLAS.

## Known limitations

- FlashInfer's BF16 cute-dsl tuner measures every small GEMM at about a 10 us floor, so fast candidates tie, and it sometimes picks a slower tactic than one in its own candidate set: 14/60 hand-table cells, and gate_up at M=16 (0.98x cuBLAS) and M=32 (0.78x). This is why M > 16 is not routed. It is unchanged in 0.7.1 and will be reported upstream.
- With `--disable-flashinfer-autotune`, the removed M <= 16 hand rows no longer apply, and those shapes use TGV/cuBLAS.
