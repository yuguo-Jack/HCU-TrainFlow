# fix: Rotary embeddings on XPU, UnifiedRadixCache default, Transformers-backend remote-code fallback, and tokenizer pad() compat shim

[Upstream PR](https://github.com/sgl-project/sglang/pull/41213) · state: open · merged: False

## Original PR description

## Motivation

Five independent, unrelated-but-small fixes found:

1. Partial rotary embeddings crash on XPU's fallback kernel path.
2. `UnifiedRadixCache.dec_lock_ref` missing a default argument, crashing the scheduler.
3. Transformers-backend fallback (`--model-impl transformers`) failing to load/serve remote-code models with legacy tied-weights conventions or wrapper classes (found via `YannQi/R-4B`).
4. A silent accuracy bug in the OpenAI-compatible chat-completions content formatter, affecting any model whose chat template expects structured ("openai"-format) content but receives a plain string.
5. Custom remote-code tokenizers with a stale `_pad()` override crashing on every request once `padding_side` started being forwarded (found via `zai-org/chatglm2-6b`).

## Modifications

### 1. `RotaryEmbedding.forward_xpu()` partial rotary embeddings (`python/sglang/srt/layers/rotary_embedding/base.py`)

The fallback-kernel branch (used when `head_size` is not in `[128, 256, 512]`) calls `torch.ops.sgl_kernel.rotary_embedding(...)` without slicing to `rotary_dim` first. That compiled kernel asserts `rotary_dim == head_size` internally and raises `RuntimeError: Rotary dim doesn't match query head_size` for any model with partial rotary embeddings (`rotary_dim < head_size`) on XPU, e.g. `adept/persimmon-8b-chat`, `microsoft/phi-2`, `stabilityai/stablelm-2-1_6b`, `stabilityai/stablelm-3b-4e1t`, `stabilityai/stablelm-zephyr-3b`. Independent of `--attention-backend`, since rotary embedding dispatch is keyed on device type (`is_xpu()`).

Fix: add an `elif self.head_size != self.rotary_dim` branch that falls back to `forward_native()`, mirroring the existing pattern where `forward_cpu`/`forward_npu` already fall back to `forward_native` for their own unsupported cases.

### 2. `UnifiedRadixCache.dec_lock_ref` missing default (`python/sglang/srt/mem_cache/unified_radix_cache.py`)

`BasePrefixCache.dec_lock_ref` declares `params: Optional[DecLockRefParams] = None`, but `UnifiedRadixCache`'s override (introduced in #36848) dropped the default, requiring `params` positionally. `schedule_policy.py`'s `_lock_node` calls `self.tree_cache.dec_lock_ref(last_node)` with no `params` whenever the acquire receipt's `to_dec_params()` returns `None`, even though `is_tree_cache()` is `True` for `UnifiedRadixCache`. This crashes with `TypeError: UnifiedRadixCache.dec_lock_ref() missing 1 required positional argument: 'params'`.

Fix: restore the default, matching the abstract interface and every other concrete `dec_lock_ref` implementation. Backend-agnostic -- reproduced on Intel XPU, but the code path has no device-specific branching.

### 3. Transformers-backend fallback: legacy tied-weights + wrapped-model remote code (`python/sglang/srt/models/transformers.py`, `python/sglang/srt/utils/hf_transformers_patches.py`, `python/sglang/srt/parser/jinja_template_utils.py`)

Four fixes for models routed through the Transformers-backend fallback (`TransformersBase`), found while debugging `YannQi/R-4B`:

- `PreTrainedModel.get_expanded_tied_weights_keys()` (transformers 5.17.0) assumes `_tied_weights_keys` is a `{target: source}` dict. Remote model code that still declares it as a list (pre-v5 convention, e.g. `YannQi/R-4B`'s `modeling_r.py`) crashes with `AttributeError: 'list' object has no attribute 'keys'`. Patched to convert a list-style mapping into the expected dict by resolving the source path from `get_input_embeddings()`. That call is itself guarded: some remote-code classes with this same list-style convention never override `get_input_embeddings()` either, so a failure there is caught and the mapping is left untouched -- the model still fails to load, but with the original, well-understood `AttributeError` instead of a different, confusing exception raised from inside this patch.
- Some remote-code repos map `AutoModel` to the same class as `AutoModelForCausalLM` / `AutoModelForImageTextToText` -- a full `*ForConditionalGeneration` wrapper with its own `.model` backbone and `.lm_head` -- rather than a bare backbone class (again, `YannQi/R-4B`). That adds an extra `model.` nesting level relative to the checkpoint's flat weight names, and `_run_hf_backbone()` would call the wrapper's full forward (returning logits, not hidden states) instead of the backbone's. `TransformersBase.__init__` now detects and unwraps this redundant wrapper.
- `R-4B`'s checkpoint ships `vision_tower` weights under a `model.vision_tower.vision_model.*` prefix (the unwrap above makes `self.model` the bare backbone, so the checkpoint's own `model.` prefix on top of the already-flattened `vision_tower.vision_model.*` convention needs remapping too). The existing `vision_tower.vision_model.` -> `model.vision_tower.` remap only covered the un-prefixed variant; added the `model.`-prefixed one.
- `R-4B`'s `vision_config.torch_dtype` is `float32`, independent of the top-level dtype used to serve the model. `TransformersBase._init_parameters()` materializes meta-device params via `torch.empty_like(param.data, ...)`, which preserves each param's own (possibly stale) dtype. Modules rebuilt by `recursive_replace()` (Linear/RMSNorm) get the uniform engine dtype, but untouched modules (vision tower's Conv2d/LayerNorm/Embedding) kept the divergent `float32`, causing `RuntimeError: mat1 and mat2 must have the same dtype, but got Float and Half` on the first mixed op. Now forces every floating-point param to the engine's `torch.get_default_dtype()` instead.
Plus one fix in the OpenAI-compatible chat-completions layer found while validating accuracy end-to-end on the same model:

- In `process_content_for_template_format()` (`jinja_template_utils.py`, used by all OpenAI-compatible chat completions, not just the Transformers backend): sglang already detects whether a model's chat template expects `"string"` or `"openai"` (structured list) content, but when a caller sends plain-string `content` against an `"openai"`-format template, the function passed it through unchanged instead of wrapping it into `[{"type": "text", "text": ...}]`. `R-4B`'s own `chat_template.jinja` iterates `message['content']` expecting a list, so a plain string renders as empty content -- the model gets no question text, silently, no error. This affects any model whose template is classified `"openai"`-format when a caller sends legacy-style string content, not just R-4B.

### 4. Tokenizer `_pad()` compat shim for stale custom signatures (`python/sglang/srt/utils/patch_tokenizer.py`)

transformers 5.x's `PreTrainedTokenizerBase.pad()` now always forwards `padding_side` down to `_pad()`. Custom remote-code tokenizers with a stale, fixed `_pad()` signature (no `padding_side` param, no `**kwargs` catch-all -- e.g. `zai-org/chatglm2-6b`'s `ChatGLMTokenizer`, unchanged for years) crash with:

```
TypeError: ChatGLMTokenizer._pad() got an unexpected keyword argument 'padding_side'
```

on every single generation request, regardless of memory/backend settings.

Fix: detects the mismatch structurally via `inspect.signature` (not a name/class check), so any other custom tokenizer with the same stale signature is covered too, and wraps `_pad()` to drop the `padding_side` kwarg before delegating to the original implementation (which already reads `self.padding_side` directly, so behavior is unchanged).

## Accuracy Tests

All five fixes were validated end-to-end on real Intel XPU hardware (docker `lmsysorg/sglang:v0.5.20-xpu`), not just reasoned about statically:

- **Rotary fix**: 20-example accuracy smoke checks (server + client, real GPU) for `adept/persimmon-8b-chat` (intel_xpu backend, gsm8k), `microsoft/phi-2` (triton backend, gsm8k), `stabilityai/stablelm-3b-4e1t` (triton backend, hellaswag), `stabilityai/stablelm-zephyr-3b` (triton backend, gsm8k) -- all previously crashed with `RuntimeError: Rotary dim doesn't match query head_size`, all now serve and produce results.
- **Radix cache fix**: reproduced the crash on `lmsysorg/sglang:v0.5.20-xpu` running `docvqa_val`/`gsm8k` evals (e.g. `HuggingFaceTB/SmolVLM2-2.2B-Instruct`, `CohereLabs/aya-vision-8b`); with the fix overlaid, a 20-example `docvqa_val` run against `HuggingFaceTB/SmolVLM2-2.2B-Instruct` completes successfully (accuracy 0.4831, no crash).
- **Transformers-backend + chat-template fixes**: `YannQi/R-4B`, `--model-impl transformers --trust-remote-code`, task `gsm8k`: server now starts, loads weights, and serves correctly (all four crashes are gone); produces real (non-zero) accuracy using the model's own unmodified `chat_template.jinja` -- no `--chat-template` override needed.
- **Tokenizer `_pad()` shim**: confirmed on real Intel XPU hardware against `zai-org/chatglm2-6b`: the `TypeError` no longer occurs and generation requests proceed past tokenization/padding.
