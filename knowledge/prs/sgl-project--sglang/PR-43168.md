# [SWA] Keep a whole window behind the page an insert can end on

[Upstream PR](https://github.com/sgl-project/sglang/pull/43168) · state: open · merged: False

## Original PR description

## Motivation

`free_swa_out_of_window_slots` keeps `max(window, page)` tokens behind `pre_len` and floors the frontier to a page. When the window is not a whole number of pages, that can leave less than a window between the frontier and `page_floor(pre_len)`. gpt-oss runs a 127-token window (`sliding_window - 1`); at page size 64, a decode eviction at `pre_len = 63 mod 64` leaves only 64 tokens there, and with the default 128-token eviction interval and one token per step, every decode eviction lands on that residue.

`page_floor(pre_len)` is where an EAGLE request's insert ends when the next verify finishes it with one token, since a bigram key spans one token less than the request owns. The new leaf then holds 64 live SWA tokens against a 127-token window, the match after the insert rejects it, and `cache_protected_len` stays at the previous prefix. The release then frees `[cache_protected_len, owned)`, including the pages the insert just gave the tree, which the tree frees again when it evicts them. Since #41520 folded the finished insert into `checkpoint()`, gpt-oss EAGLE3 at page size 64 leaks and double-frees KV, on the default pool and on `--enable-unified-memory` alike, and on every attention backend; some runs hit an illegal memory access.

## Modifications

`mem_cache/common.py`: the retained span is now `max(window, page)` rounded up to whole pages, so the frontier stays a full window below `page_floor(pre_len)`. Page-aligned windows and page size 1 keep the old frontier; an unaligned window keeps at most one more SWA page per request.

Test (`test_unified_radix_cache_unittest.py`, CPU): `TestSWAWindowUnderBigramKey` runs a 7-token window at page size 4, the same misalignment. In `test_finish_after_decode_eviction_frees_only_the_requests_pages`, a request decodes, evicts at `pre_len` 23 and finishes at 24; before this change the full pool counts 8 tokens twice (`264 != 256`), after it every page is either free or held by the tree.

## Accuracy Tests

SM90, TP1, gpt-oss-20b with EAGLE3 on triton, page size 64, radix cache, overlap scheduler, `--mem-fraction-static 0.55`. GSM8K, all 1314 test questions, 5-shot, greedy. Every server ran with the per-step pool checks and the allocator invariants on (`SGLANG_ENABLE_STRICT_MEM_CHECK_DURING_BUSY=1 SGLANG_CHECK_KV_PAGE_INVARIANTS=1 SGLANG_INVARIANT_CHECK=1`), which stop a server at the step that leaks or frees a page twice. Baseline: the default pool, run twice. Unified: `--enable-unified-memory` with lazy compaction (the default) and eager compaction (`SGLANG_DISABLE_LAZY_COMPACTION=1`), on a poisoned pool (`SGLANG_DEBUG_POISON_POOL=1`).

| CUDA graphs | baseline / baseline repeat / unified eager / unified lazy | accept length |
|---|---|---|
| off | 0.520 / 0.544 / 0.572 / 0.524 | 1.27-1.28 |
| on | 0.521 / 0.535 / 0.530 / 0.543 | 1.27-1.28 |

Every server answered all 1314 questions with no leak, double free, invariant violation or illegal memory access. Without this change the same configuration leaked and double-freed KV on every arm, the default pool's included. gpt-oss-20b's GSM8K score moves by several points between identical runs (the two baseline runs above differ by up to 2.4).

GPU unit suite (unified-memory scope, including this test file, which is CUDA-registered): all pass except the 2 cases of `test_swa_write_back_host_full_preserves_full_and_continues`, which force the Rust TreeCore that our test image does not build.

## Speed Tests and Profiling

Not measured: the change keeps at most one more SWA page per request, and only for a window that is not a whole number of pages.
