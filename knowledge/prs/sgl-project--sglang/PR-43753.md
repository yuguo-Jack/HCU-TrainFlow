# [Fix] Gemma 4 vision pooler: mask padding patches and scale in float32

[Upstream PR](https://github.com/sgl-project/sglang/pull/43753) · state: open · merged: False

## Original PR description

## Motivation

`Gemma4VisionPooler` and `Gemma4VisionEncoder`, which `Gemma4ForConditionalGeneration` uses for images and video frames, differ from transformers' Gemma 4 vision model in two places:

1. **Padding patches leak into the first image token.** The processor pads each image to 2520 patches unless its patch grid fills them exactly. That leaves 216 padding patches for a square image, 180 for 3:2, 144 for 16:9 and 0 for 960x672. Padding positions are clamped to (0, 0), so without masking every padding patch is averaged into pooled token 0.
   - transformers zeroes them before pooling, and has since its first Gemma 4 commit (huggingface/transformers#45192).
   - `mask_pad_before_pool` was added for DiffusionGemma in #34061, which passes `True`. EmbeddingGemma2 (#42782) ships its own pooler, and it masks too.
   - Only the generative Gemma 4 path still uses the unmasked default.
2. **float16 overflow.** The pooler pools and scales by `sqrt(hidden_size)` (about 33.9) in the working dtype, and the encoder standardizes in it. Pooled values above 65504 / 33.9, about 1930, overflow in float16 before `std_bias` can cancel them. So image requests return NaN logits in float16, whether set with `--dtype float16` or by a checkpoint config. One example is the AWQ checkpoint from #43342, once #43616 lets it load. With the radix cache on, requests that reuse the chat prefix cached by such a prefill fail too (see #43616). transformers fixed the same overflow in huggingface/transformers#46277: it scales and standardizes in float32, then casts back. Its pooling was already float32.

To isolate the pooler, I fed transformers' vision-encoder output for stock `google/gemma-4-31B-it` (A100 80GB) through SGLang's actual `Gemma4VisionEncoder`, with only the patch embedder and transformer stubbed out.
- **With this change:** the bf16 image embeddings after `embed_vision` are bitwise identical to transformers' for all 7 test images.
- **Before it:** token 0 of every padded image had a cosine similarity of only 0.17 to 0.51 with transformers' (max abs diff up to 12). The unpadded image differed by bf16 rounding alone (max 0.125).

## Modifications

`python/sglang/srt/models/gemma4_vision.py`:
- `mask_pad_before_pool` now defaults to `True` in `Gemma4VisionPooler` and `Gemma4VisionEncoder`. I kept the argument so DiffusionGemma's call site is unchanged; since `False` only reproduces the bug, it could be removed in a follow-up.
- `_avg_pool_by_positions` pools in float32 and casts back. The pooler then scales in float32 and returns float32, and `Gemma4VisionEncoder.forward` standardizes before casting to the working dtype. This follows transformers' `Gemma4VisionPooler` and `Gemma4VisionModel.forward`.
- Effect on the other models that use these classes:
  - **DiffusionGemma** already masked, but it gets the float32 steps too. Its bf16 image embeddings move by bf16 rounding (up to 0.125 on the test images) to match transformers', and float16 no longer overflows.
  - **EmbeddingGemma2** replaces the pooler with its own, which returns the working dtype, so its output does not change.

`test/registered/unit/models/test_gemma4_vision.py` (CPU, `base-a-test-cpu`) runs the real `Gemma4VisionEncoder.__init__` and `forward`, with pass-through stubs for the patch embedder and the transformer. Each case fails on main:
- **Padding:** padding patches must not change any pooled token. On main, token 0 is off by 400 (the padding value, 100, times sqrt(16)).
- **float16:** inputs whose scaled values exceed 65504 must give finite, exact float16 tokens. On main, every one of them is inf.
- **bfloat16 rounding:** each bfloat16 pooled token must be its patches' mean rounded once. On main, bfloat16 pooling weights (1/9 rounds to 0.1113) round this test's mean up a step.

## Accuracy Tests

Setup:
- Stock `google/gemma-4-31B-it` on 1x A100 80GB.
- SGLang 0.5.21 with and without this PR's `gemma4_vision.py`; the original file is identical on main.
- Offline `Engine`, greedy decoding.

Results:
- **bfloat16, the checkpoint's dtype** (radix cache off, so every prompt gets a fresh prefill):
  - Test set: 7 synthetic images, 13 prompts. 6 images have a small object or text in the top-left corner, the region pooled into token 0, and get a question about it. All 7 get a one-sentence description.
  - Corner answers are correct with and without this PR: "Green", "Q7", "The sun is in the top left corner and it is yellow.", "Purple", "Green".
  - Descriptions differ in wording for 4 of the 6 padded images (e.g. "A red triangle..." vs "A large red triangle..."), and all are correct.
  - The unpadded control gives the same text.
- **float16, with the radix cache on:** the image request goes first, then a text request, then the image again.
  - Without this PR, all three return NaN logprobs and `<pad>`.
  - With it, both image requests return the same description as bfloat16 ("The image features a red square on the left and a blue circle on the right against a white background."), and the text answer is correct.

## Speed Tests and Profiling

Pool, scale and standardize for one 2520-patch image (bf16, A100, CUDA events, median of 15 x 200 calls) takes 0.55 ms without this PR and 0.71 ms with it. For scale, one transformers bf16 vision-encoder forward on the same image takes 78 ms.
