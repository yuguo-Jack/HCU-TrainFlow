# [CustomAllReduceV2] Replace threshold heuristics with ordered dispatch tables

[Upstream PR](https://github.com/sgl-project/sglang/pull/43296) · state: open · merged: False

## Original PR description

## Motivation

Reviewing #42811 raised that the CustomAllReduceV2 dispatch has become hard to follow. Each new algorithm adds another positional threshold to `Heuristic`, another branch to the `if`-chain in `_pick_config`, and another clipping rule. An algorithm is disabled by setting two thresholds equal. This PR swaps that for a lookup table, with no change in behavior under default sizing, so #42811 can add `2shot_push` as one constant plus table rows.

## Modifications

- Each `(arch, world_size)` lists plain `(max_bytes, ALGO)` rows for graph mode and eager mode. The first row with `nbytes <= max_bytes` wins. Past the last row, the call falls back to NCCL.
  ```python
  4: config(4, graph=((2.25 * MB, PUSH1), (128 * MB, PULL2)),
               eager=((3 * MB, PUSH1), (32 * MB, PULL2))),
  8: config(8, graph=((512 * KB, PUSH1), (8 * MB - 1, PULL2), (128 * MB, MC), (128 * MB, PULL2)), ...),
  ```
- `PUSH1 / PULL1 / PULL2 / MC` are `(AllReduceAlgo, use_multicast)` pairs. A multicast range that used to have a floor becomes a preceding `PULL2` row (`8 * MB - 1`; sizes are always multiples of 16 B).
- `MC` rows are dropped once at init when the group has no multicast, which resolves each table to the `(world_size, can_use_multicast)` case the review asked for.
- `_pick_config` is one loop. It checks each row against its workspace capacity (push or pull) instead of clipping the tables ahead of time.
- The forced-size env vars and `uncap_pull_thresholds()` add a row bounded only by the workspace: `(inf, PUSH1)` at the head, `(inf, PULL2)` at the tail.
- `use_graph` is derived in one place, `can_use_graph and not algo.is_push() and not use_multicast`, and the override path uses the same rule.
- Removed: `Heuristic`, `Range`, `_pack_heuristic`, every `clip()`, and the local pick-result `AllReduceConfig`. `eager` defaults to `graph` when the two are identical.
- A trailing `PULL2` row stays even where an earlier row covers it, for example SM107 world 2. It still sizes the pull plane, and the fused collectives borrow that plane's semaphores.

## Accuracy Tests

An equivalence check (a script, not committed) loads `main`'s config module and this one and compares the old picker with the new one. It covers:
- all four config sets (SM90, SM100, SM107, and the unknown-arch default) and every world size in each;
- graph and eager mode, with and without multicast;
- sizes at every threshold ±32 B, plus the 1–256 MB edges;
- 20 sizing scenarios:
  - five `max_size` values, with and without `uncap_pull_thresholds()`;
  - push-only fused instances, and test-style explicit sizes;
  - forced pull and forced push sizes.

Results:
- **Default sizing: identical.** In total, 83,372 picks were checked.
- **Workspace sizes** (push slot, pull buffer, `num_mc_blocks`) are identical in all 20 scenarios.
- **All remaining differences** fall into two explained classes, both from the old clip-then-compare scheme and both needing non-default sizes:
  1. **A forced push size below the tuned 1shot crossover**, or a forced pull workspace larger than the push workspace (`SGLANG_FORCE_CUSTOM_ALL_REDUCE_V2_{PUSH,PULL}_SIZE_KB`, which nothing in the repo sets). The old code fell into a `1shot_pull` the tuning had turned off (equal thresholds). The table falls through to the next tuned row.
  2. **`SGLANG_CUSTOM_ALL_REDUCE_V2_MAX_SIZE_KB` set below a multicast floor** (SM90 world 6, SM100 world 8, graph mode). The old `Range.clip` shrank the multicast range to the single size equal to the workspace. That one size now takes non-multicast `2shot_pull` (8 picks).
