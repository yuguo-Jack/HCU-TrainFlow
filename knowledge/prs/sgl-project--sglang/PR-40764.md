# [DSA][DSv4.1] Add opt-in LiteTopK decode top-k for SM100

[Upstream PR](https://github.com/sgl-project/sglang/pull/40764) · state: open · merged: False

## Original PR description

@DarkSharpness could you take a look when you have a chance? The speed tables are below.

## Motivation

DSA models (GLM-5 family, DeepSeek-V3.2) and DeepSeek-V4.1's ratio-1/2 index layers run a lightweight indexer before sparse attention: a paged MQA kernel scores every KV position of each decode / verify token, and a top-k (2048 for DSA, 512 for V4.1) picks the positions attention reads. The default path writes the dense scores and then runs a separate top-k whose first pass over the scores only builds a coarse histogram.

With sgl-project/DeepGEMM#94 the scoring kernel counts that histogram while it writes the scores. LiteTopK reads it, finds the bin holding the k-th score and scans the scores once: scores above that bin are selected outright and the bin's own scores are ranked exactly. **The selection is exact over the producer's scores** (ties go to the lower physical slot). A histogram that disagrees with the scores, or a crossing bin larger than the candidate buffer, falls back to an exact radix select of the whole row, so the result never depends on the histogram being right.

This PR covers both the DSA and the DeepSeek-V4.1 decode top-k and replaces #42351.

## Modifications

- `kernels/jit/csrc/litetopk_decode/select.cuh`: one templated selector with two configurations, FP32 top-2048 on 64-slot pages (DSA) and BF16 top-512 on 128-slot pages (V4.1). One launch covers all rows: rows of up to 10240 (FP32) / 16384 (BF16) scores are selected by one CTA from registers, longer rows are split across CTAs. The histogram and the scratch return to zero after every call, so CUDA graph replays need no reset kernel. PDL is on.
- `kernels/ops/attention/litetopk_decode.py`: storage / plan and `select(scores, lengths, table, out=...)`, which writes physical KV slots (`-1` padded); runtime detection of SM100 and of a DeepGEMM with the histogram producers.
- `srt/layers/attention/litetopk_decode.py`: one set of selector buffers per process, a plan per row count, grown only outside CUDA graph capture.
- Serving, opt-in with `SGLANG_OPT_LITETOPK_DECODE=1` (default off):
  - DSA (`dsa/dsa_indexer.py`, `dsa_backend.py`): decode and target verify with up to 4 tokens per request. The producer gets the histogram, and LiteTopK replaces the fused paged top-k transform with the same output. When LiteTopK serves verify, the producer gets each verify token's causal length.
  - DeepSeek-V4.1 (`dsv4/v41_indexer/{litetopk,full_topk,sparse_table}.py`, `deepseek_v4_backend.py`, `dsv4/metadata.py`): FullTopK and SparseTable decode / verify with 1-6 tokens per request use DeepGEMM's BF16 producer with the histogram; its schedule is rebuilt once per forward inside the graph; candidate block maxima accept BF16 scores (`block_amax.cuh`, `candidate_blocks.py`). Exactness is relative to the BF16 scores: BF16 rounding can change the selection relative to the default FP32 scores.
  - Other GPUs, prefill, other geometries and a DeepGEMM without the histogram APIs keep the default path.

## Accuracy

- `test/registered/kernels/ops/attention/test_litetopk_decode.py` (B200, **31/31**): both configurations against an exact (score, lower slot) reference: every launch shape, verify rows sharing a page-table row, rows up to 1M scores, ties / signed zeros / infinities, stale histograms and candidate overflow (exact fallback), CUDA graph replay, scratch back at rest. With DeepGEMM#94: the FP32 producer chain, and the V4.1 FullTopK / SparseTable routes captured in a CUDA graph and replayed with new lengths, request runs and pages.
- `test/registered/unit/layers/attention/test_litetopk_decode.py` (CPU, **14/14**): flag off leaves the DeepGEMM calls unchanged, unsupported calls keep the default top-k, histogram wiring, causal verify lengths, CUDA graph buffer rules.
- Serving on truncated models (real weights, 1x B200): GLM-5.2 (8 layers + MTP) is exact on 17,408 decode rows and 4,848 MTP verify rows; DeepSeek-V4.1 (6 layers) is exact on 1,024 rows against the top-512 of the same BF16 scores. In the same GLM runs, the default `topk_transform_paged_v2` missed part of the exact top-2048 on 0.5 % of the rows (all with 33K+ keys); this reproduces offline on the captured scores.

## Speed (kernel level)

Indexer scores + top-k selection of one layer per decode / verify step on B200 (148 SMs). **SGLang** = DeepGEMM `fp8_fp4_paged_mqa_logits` (FP32 logits, no histogram) + `topk_transform_paged_v2`. **LiteTopK** = the producer with the histogram (FP32 `fp8_fp4_paged_mqa_logits(..., histogram=)` for GLM-5.2, BF16 `fp4_paged_mqa_logits_bf16(..., histogram=)` for V4.1) + this selector. Both return physical KV slots; PDL is on for every kernel.

Cold method: a 1 GiB buffer is zeroed before every call (outside the timed span); CUPTI measures each chain from its first kernel start to its last kernel end; the arms run in randomized order inside each block and each cell is the median; an A/A arm (the selector compiled a second time) bounds the noise. Every cell is checked before and after timing: values equal `torch.topk`, LiteTopK's slots equal the (score desc, lower slot) oracle, histogram and scratch are back to zero. Only GPUs without other processes are used. Speedup = SGLang / LiteTopK (> 1 = LiteTopK faster).

### GLM-5.2 (DSA), FP32 top-2048, layers 0 and 38

Inputs: a real GLM-5.2 1M-token decode capture (indexer q / weights / FP8 KV of layers 0 and 38); every request reads its own KV pages; token j of a request sees L + j keys (next_n = 1..4). 48 (B, L) pairs × 4 next_n = 192 cells per layer; cells marked * exceed one rank's KV pool (B x (L + next_n) > 1,550,400 tokens) and are included to cover larger batches. The SM clock samples read 1965 MHz in 380 of the 384 cells; in four large cells (B = 128 x 64K, B = 8 x 512K) some samples dropped to 1785-1942 MHz (SW power cap).
