# [dLLM] Size decode graph buffers by the separate-context request cap

[Upstream PR](https://github.com/sgl-project/sglang/pull/41680) · state: closed · merged: False

## Original PR description

## Motivation

The cookbook launch command for DiffusionGemma (`docs/cookbook/autoregressive/Google/DiffusionGemma.mdx`) OOMs on a single H200 while capturing the decode CUDA graph:

```
Capture target decode CUDA graph begin. backend=full, num_tokens_per_req=1, bs=[1, 2, 4, ..., 256], avail mem=21.73 GB
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 64.00 GiB.
  File ".../runner/decode_cuda_graph_runner.py", in __init__
    next_token_logits_buffer=self.model_runner.graph_shared_output.get_logits_buffer(
```

The shared logits buffer is sized by `ModelRunner.max_decode_logits_rows()` as `max(get_batch_sizes_to_capture(...)) * decode_num_tokens_per_req()`. For a separate-context dLLM (`Gemma4Renoise`), that is 256 (uncapped bs) x 256 (canvas) rows x 262,144 vocab x fp32 = 64 GiB.

`DecodeCudaGraphRunner` does cap its capture bs to the dLLM `max_running_requests` (default 1), but only on its own list, after `get_batch_sizes_to_capture` returns. The shared buffer, `BaseRunner._widest_decode_rows()`, the elastic graph config, the post-warmup `compile_bs` recompute, and the capture log line all call `get_batch_sizes_to_capture` directly and never see the cap. The runner itself only ever asks for 1 x 256 rows.

Workaround until this lands: `--cuda-graph-max-bs-decode 4 --max-running-requests 4`.

## Modifications

- Move the separate-context dLLM clamp from `DecodeCudaGraphRunner.__init__` into `get_batch_sizes_to_capture`, so every consumer derives the same bs list the runner captures. The clamp logic itself is unchanged; non-separate-context dLLMs (LLaDA2, SDAR) and AR models are unaffected.
- The decode capture log line now uses `decode_num_tokens_per_req()` for non-speculative runners, so dLLM logs show the real `num_tokens_per_req` and capped bs, instead of `num_tokens_per_req=1, bs=[1, ..., 256]`.
- Add CPU unit tests: a separate-context dLLM's `max_decode_logits_rows()` is `min(max_running_requests, max(capture_bs)) * block_size`, and other dLLMs keep the full range.

- javey-q · comment · 2026-09-29T17:40:13Z · [source](https://github.com/sgl-project/sglang/pull/41680#issuecomment-5895457701)

Hi @rwang5203 , a question about the decode capture cap from #34061.

When --max-running-requests is not passed, a dLLM server has two different limits. DllmConfig.max_running_requests defaults to 1, while the global max_running_requests is auto-estimated at 2048 to 4096. get_batch_sizes_to_capture only clamps to the global one, so decode graphs are prepared for bs up to 256, even though the dLLM scheduler never runs more than one request. #34061 caps capture_bs for separate-context algorithms inside DecodeCudaGraphRunner. This PR moves that cap into get_batch_sizes_to_capture, so the shared logits buffer is sized to match. That fixes the 64 GiB OOM with the DiffusionGemma cookbook command.

The other dLLMs have the same mismatch. I launched LLaDA2.0-mini on 1 x H200 without --max-running-requests. On main, startup fails while capturing bs=256 (256 x 32 query rows overflow the flashinfer workspace). With the cap applied to all dLLMs, it captures only bs=[1], frees about 4.8 GB, and serves normally. Greedy outputs are identical to main run with --max-running-requests 1. This is not a regression; it stays hidden because the LLaDA cookbook and tests always pass --max-running-requests or --cuda-graph-max-bs-decode.

1. Was limiting the cap to requires_separate_context_encoding intentional, or does some non-separate-context path need decode graphs above DllmConfig.max_running_requests?
2. If not, are you OK with applying the cap to all dLLM algorithms in this PR? The change is dropping that condition in get_batch_sizes_to_capture and updating the unit test.

Thanks!
