# [HiCache] Isolate Mooncake KV objects by kv_cache_dtype via tenant_id

## Motivation

HiCache Mooncake keys previously ignored `--kv-cache-dtype`. Two servers sharing one Mooncake store with the same model but different dtypes (for example `bfloat16` then `fp8_e4m3`) produced identical object keys, so the second run could silently reuse cache bytes in the wrong format.

This change namespaces Mooncake objects by KV cache dtype using Mooncake `tenant_id`. Key-prefix concatenation via `extra_backend_tag` is not used for dtype isolation.

**Mooncake version:** `tenant_id` was added to `MooncakeDistributedStore.setup()` in **mooncake-transfer-engine 0.3.12**. Older packages fail at startup with an upgrade hint: `pip install -U 'mooncake-transfer-engine>=0.3.12'`.

## Modifications

- Carry the resolved logical device-pool dtype in `HiCacheStorageConfig`. Normalize it once; FP8 formats remain distinct even when their buffers use `uint8`, and hybrid host-pool facades do not need a `dtype` attribute.
- Compose the Mooncake tenant in one place: `default` + `bfloat16` becomes `dtype_bfloat16`; `tenant-a` + `float8_e4m3fn` becomes `tenant-a_dtype_float8_e4m3fn`. Object keys and the existing model/backend prefixes are unchanged.
- Share setup compatibility handling between KV and embedding stores. Unsupported SSD options retain the existing fallback; an unsupported `tenant_id` fails with an upgrade hint instead of dropping isolation.
- Document the master-side multi-tenant/quota prerequisites and the matching tenant needed by an external standalone client.
- Simplify CPU regressions to focused mocks, covering logical FP8 dtype propagation, tenant composition, key prefixes, compatibility failures, and SSD fallback. Preserve current main's per-rank SSD directories.

Tenant isolation requires the Mooncake master to enable `--enable_multi_tenants=true` and register the composed tenants in its quota policy. Otherwise Mooncake uses the default namespace and does not enforce dtype isolation.
