# [KV Cache] Amortize L1 eviction under sustained pressure

[Upstream PR](https://github.com/sgl-project/sglang/pull/41690) · state: open · merged: False

## Original PR description

## Motivation

When the device (L1) KV pool remains saturated, the allocator currently evicts only the exact token shortfall required by each allocation. Under sustained prefill traffic, this produces many small eviction cycles.

Each cycle synchronously rebuilds and scans the radix-cache eviction heap on the scheduler thread. Once `kv_available_tokens` reaches zero, repeated eviction work stalls the scheduler, introduces pipeline backpressure, and causes a persistent throughput drop even though allocations continue to succeed.

The effect is especially severe for short-input workloads: short requests create allocation and radix-cache activity more frequently while providing less GPU computation over which to amortize the synchronous CPU work.

With an approximately 55-million-token L1 KV pool:

- Sustained 4K input: throughput dropped from approximately 3.62M to 1.90M input tokens/min after saturation (`-47.5%`).
- Sustained 32K input: throughput dropped from approximately 3.82M to 3.63M input tokens/min after saturation (`-5.0%`).

The paged free-list optimization in #37146 reduces release-side metadata overhead, but it does not reduce the number of radix-cache eviction cycles. Profiling shows that the remaining bottleneck is repeated synchronous eviction-heap work.

## Modifications

- Add the opt-in environment variable `SGLANG_OPT_KV_CACHE_EVICTION_HEADROOM_TOKENS`.
- When an allocation first encounters pressure, evict the current shortfall plus a bounded reserve.
- Cap the optional reserve by the number of currently evictable tokens, so headroom cannot turn an otherwise satisfiable allocation into a failure.
- Apply headroom independently to Full KV and SWA KV.
- Preserve no-pressure behavior: no additional eviction occurs while the allocation already fits.
- Keep the default at `0`, preserving exact-shortfall eviction for existing deployments.
- Cover standard, SWA, and unified Full/SWA allocators with CPU unit tests.
- Document the parameter in the environment-variable reference and radix-eviction guide.

This changes eviction batch size, not cache replacement ordering. Reclaimed slots return to the ordinary free pool and remain available to subsequent allocations; they are not permanently reserved.

### Configuration

Set the variable before launching each server process whose L1 KV cache should use batched eviction:

```bash
SGLANG_OPT_KV_CACHE_EVICTION_HEADROOM_TOKENS=131072 \
python3 -m sglang.launch_server --model-path MODEL_PATH
```

The value is measured in logical KV token slots, not bytes or pages:

```text
target = shortfall + min(headroom, max(0, evictable_tokens - shortfall))
```

- `0` (default): retain exact-shortfall eviction.
- Positive value: add at most that many evictable token slots when pressure begins.
- Negative value: treated as `0`.
- Full KV and SWA KV calculate their pressure and bounded headroom independently.
- The setting affects L1 device KV eviction only; HiCache/L2 eviction is outside this PR.

For the tested 55-million-token pool, `131072` is about `0.24%` of capacity and `524288` is about `0.95%`. These are workload-specific test points rather than universal defaults. A practical starting point is a small fraction of L1 capacity, followed by validation under sustained saturation.

## Accuracy Tests

This change does not modify model weights, KV contents, page mappings, attention kernels, PD transfer protocols, or replacement ordering. The default is `0`, so existing deployments retain the current behavior unless the optimization is explicitly enabled. Model computation and output accuracy are unchanged.

Added CPU tests cover:

- Default and negative-value exact-shortfall behavior.
- Bounded headroom and evictable-token capping.
- No-pressure behavior.
- Standard L1 KV allocation.
- Independent Full KV/SWA KV handling.
- Unified Full/SWA allocation.

## Speed Tests and Profiling

### End-to-end saturation test

Environment:

- DeepSeek V4 Pro with PD-disaggregated serving.
- Prefill deployed on two 8xH200 nodes (16 GPUs total).
- PP8/CP2.
- L1 KV pool capacity: approximately 55 million tokens.
- Sustained prefill traffic.
- Optimized runs used `SGLANG_OPT_KV_CACHE_EVICTION_HEADROOM_TOKENS=524288` (approximately `0.95%` of L1 capacity).

| Input length | Exact-shortfall eviction | 524,288-token headroom |
| --- | --- | --- |
| 4K | After saturation, throughput fell from approximately 3.62M to 1.90M input tokens/min (`-47.5%`). | The post-saturation throughput cliff disappeared; throughput remained close to its pre-saturation level. |
| 32K | After saturation, throughput fell from approximately 3.82M to 3.63M input tokens/min (`-5.0%`). | Throughput remained stable after saturation. |

The 4K result shows that exact-shortfall eviction is not merely a small steady-state cost: repeated synchronous eviction can consume enough scheduler time to reduce throughput by nearly half. Bounded headroom removes this saturation cliff in the tested short- and long-input workloads.

### Detailed 32K profiling

This separate profiling run used a smaller `131072`-token headroom (approximately `0.24%` of L1 capacity) to quantify eviction behavior.

| Metric | Exact-shortfall eviction | 131,072-token headroom | Change |
| --- | ---: | ---: | ---: |
| Throughput before pressure | 64,624 token/s | 64,614 token/s | -0.02% |
| Throughput under pressure | 61,008 token/s | 63,634 token/s | +4.31% |
| Throughput loss after saturation | 5.60% | 1.52% | 72.9% reduction |
| Eviction frequency | 7.45/s | 0.45/s | -93.9% |
| Eviction wall-time share | 2.36% | 0.86% | -63.5% |
| Maximum eviction latency | 337.97 ms | 198.71 ms | -41.2% |
| Allocation failures | 0 | 0 | unchanged |

The optimization leaves pre-pressure throughput unchanged while reducing eviction frequency by `93.9%`. Under sustained pressure, throughput improves by `4.31%`, and saturation-related throughput loss decreases from `5.60%` to `1.52%`.
