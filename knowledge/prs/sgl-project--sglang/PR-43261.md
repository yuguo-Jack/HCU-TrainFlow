# [diffusion] map the merged LoRA cache read-only

[Upstream PR](https://github.com/sgl-project/sglang/pull/43261) · state: open · merged: False

## Original PR description

## Motivation

`safetensors.torch.load_file` maps a file through `UntypedStorage.from_file(shared=False)` — a private, writable mapping. On a shared CPU/GPU pool that permission costs memory, which `runtime/loader/readonly_safetensors.py` already documents for the checkpoint path:

> when the device copies from such a mapping the driver pins the pages with write intent, the kernel breaks copy-on-write, and every page copied becomes anonymous memory — 1 GiB copied in 1 GiB of unreclaimable RAM, at a fraction of the bandwidth.

That loader was added for the ordinary checkpoint mapping, but the LoRA merge cache still reads through `safetensors_load_file` at both of its read sites. A merged adapter is written once by `save_file` + `os.replace` and is immutable afterwards, so it never needs the write permission — yet every co-resident instance that reads it currently pays for a private copy.

## Modifications

Both read sites use the existing `load_safetensors_readonly`, and the now-unused `safetensors_load_file` import is dropped. No API, dependency, or configuration change.

## Accuracy Tests

Not applicable in the usual sense: the bytes returned are identical, only the mapping permission changes. Sanity check performed — two co-resident instances reading the same merge-cache key return identical tensors, and a request through the merged adapter is unaffected.

## Speed Tests and Profiling

No speed claim. This is a host-memory change only.

MiniMax-H3 fl2va, one RTX PRO 6000 (SM120), `--layerwise-offload-components dit,text_encoder,image_encoder`, merge cache ~62 GiB:

| | Pss |
|---|---|
| instance A alone | 167.11 GiB |
| instance A after B joined (same merge-cache key) | **145.81 GiB** |

≈42.6 GiB of the cache stops being a private copy per instance.
