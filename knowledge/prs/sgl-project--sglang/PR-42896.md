## Motivation

MLP sync pads each rank's extend batch to a multiple of attention TP (`input_ids`, `positions`, `out_cache_loc`), while the attention metadata still covers only the real tokens. The prefill CUDA graph path already runs attention on the real rows. In eager mode, though, the backends got the padded queries:

- flashinfer's paged and ragged prefill and flashinfer MLA's ragged path reject them. Qwen3-30B-A3B with DeepEP at TP 2 fails as soon as prefill runs eager, as it does by default under pipeline parallelism:
  ```
  q.shape[0] (6) does not match qo_indptr[-1] (5)
  ```
- The other backends compute only the rows their metadata covers and leave the rest of the output uninitialized.

## Modifications

- `RadixAttention` does in eager what the prefill graph path does:
  - it runs the backend on the real rows, with the cache locations and positions narrowed for the call;
  - it allocates the padded output up front, with the graph branch's allocation (`_new_attention_output`, now shared). A backend that writes into `forward_batch._attn_output` (flashattention, triton, aiter, trtllm_mha's NVFP4 output) fills the real rows in place; another backend's output is copied in. Only the padded tail is zeroed. A backend that returns more than its output (its LSE, or a sparse indexer's output beside it) returns a tuple, which is padded as it comes, so no output is allocated for that call.
- K and V go with the queries unless the caller gives them an extent of their own, the layer is a cross-attention (K and V are the encoder's), or they have a different row count. K and V that hold a cached prefix declare their extent: the chunked-prefix chunks did, and DeepSeek's one-shot MHA, whose K and V cover every token of the sequences, now does too, so they are never taken for padded rows when their row count happens to equal the padded query count.
- The other per-row inputs are narrowed with the rows they belong to:
  - `rel_bias`, `aux_tensors`, the q/k/v descales and the mxfp8 deferred norm/RoPE inputs, from the list the graph path's extra-kwargs route already narrows (`_PER_ROW_EXTRA_KWARGS`, now shared);
  - `k_rope` and the k/v descales follow K and V; a sparse indexer's `idx_q` follows the queries and its `idx_k` / `idx_v` the keys, as the prefill graph's sparse attention already narrows them (MiniMax's backend trimmed them itself only while it received the padded queries).
- The FA4 wrappers (`flash_attn_varlen_func` and `flash_attn_with_kvcache` in `flash_attention_v4.py`) pass `out=` on to the kernel. They dropped it, so FA4 allocated a second output that was then copied in; the output the prefill graph path preallocates now reaches FA4 too. Where the wrapper pads MLA query heads, or the kernel is a released flash-attn-4 build without `out=`, the result is still a new tensor.
- trtllm_mha's FMHA-v2 prefill (SM90 and SM120) also writes into the output it is given, as its other prefill kernel already did, so the padded call and the prefill graph path no longer copy a second output in.
- DeepSeek's born-FP8 query for DSA's `flashmla_sparse_q8` prefill (`SGLANG_ENABLE_DSA_Q8KV8_BORN_FP8_Q`) is prepared for every row but handed to the backend for the rows its attention call takes: the stash records the real rows of a padded extend (`padded_extend_real_tokens`, the same test the narrowing uses), which the backend reads as a prefix of the rows written.
- Target verify, which plans its padded rows itself, is left as it is.
- The real count comes from `global_num_token_non_padded_cpu`, which every batch carries.
- Kimi K3 trimmed its own attention to the real rows for the same reason, counting them from `extend_seq_lens_cpu`, which GPU-only batches leave unset. That trim is removed, together with:
  - the padded o_proj output it kept for the SP collectives;
  - the trimmed `out_cache_loc` it left on the batch.
- `test_radix_attention_padded_extend.py` covers:
  - only padded extend batches are narrowed;
  - the backend sees the real rows and the tail is zero;
  - keys with their own extent or row count, or a cross-attention's, are left whole, also when they are as long as the padded queries (a cached prefix, or encoder rows);
  - the per-row inputs follow the rows they belong to, a sparse indexer's too (each index output shaped by the query rows);
  - the output is written in place or copied, with `_attn_output` restored afterwards.

## Accuracy Tests

- Qwen3-30B-A3B, DeepEP, TP 2, deterministic inference (flashinfer), eager prefill, on B200: crashes on `main`, both with and without PP 2; runs with this change.
- `trtllm_mha` in eager prefill, which ran on the padded batch before: identical before and after.
- The output buffer handling and the per-row narrowing change no value. Qwen3-30B-A3B, DeepEP, TP 2, deterministic inference, eager prefill, 24 prompts of uneven length (every process takes the padded path 51–351 times): with the backend's own output copied in (flashinfer) or written in place (triton and fa4 on B200, fa3 on H200), input and output logprobs are bit-identical to narrowing Q, K and V alone.
- FA4 output reuse, counted at the FA4 kernel call (Qwen3-30B-A3B, DeepEP, TP 2, deterministic inference, B200), two launches per tree:
  - eager prefill: all 381 padded attention calls per process now hand the preallocated output to FA4 and get it back (none before). A padded attention call's peak memory drops from 609 KiB to 309 KiB, one real-row output (75 rows × 2048 × 2 bytes);
  - prefill CUDA graph: the 6,465 FA4 calls that have a preallocated output now write into it (none before);
  - input and output logprobs are bit-identical to before in both modes.
  - the same on an HGX B300 (SM103): the same counts and peak memory, and bit-identical logprobs in both modes.
- DeepSeek one-shot MHA over a cached prefix on a padded extend (a 4-layer DeepSeek-V3 config with dummy weights, DeepEP TP 4, flashinfer, eager prefill, `SGLANG_CHUNKED_PREFIX_CACHE_THRESHOLD=1`, B300): a 3-token cached prefix and 9 new tokens padded to 12, so K and V have as many rows as the padded queries. Without the declared extent, K and V were cut to 9 rows on every MLA layer and the greedy tokens changed; with it, the output is bit-identical to the same request without the prefix cache, in two launches.
- MiniMax-M3's sparse attention (its released config cut to 6 layers, index values on in two of the five sparse layers, dummy weights), TP 4 × DP 2 attention, eager prefill, on B300. Narrowing q, K and V without the indexer's inputs fails in `store_kv_index`, whose `idx_k` keeps the padded rows. With them narrowed, every padded call hands the backend the real rows for q, `idx_q` and `idx_v`, and the index output comes back on those rows. Sending the 24 prompts one at a time, so that each launch runs the same batches (9 of the 24 prefills padded), the greedy tokens match `main` on all 24 prompts. The logprobs differ from `main`'s by at most 0.0073; `main` differs from its own second launch by 0.0068.
- trtllm_mha's FMHA-v2 on H200 (Qwen3-30B-A3B, DeepEP TP 2, eager prefill, requests one at a time): all 192 padded attention calls per process now hand FMHA-v2 the preallocated output and get it back (none before), saving one real-row output per call; input and output logprobs are bit-identical to before.
- DSA's born-FP8 query (`SGLANG_ENABLE_DSA_Q8KV8_BORN_FP8_Q=1`, `flashmla_sparse_q8` prefill, FP8 KV cache) on H200: a DeepSeek-V3.2 config cut to 4 layers with bf16 dummy weights, TP 4 × DP 2 attention, eager prefill, 12 long prompts sent one at a time. On the padded prefill, every layer's stash records the real rows the attention call reads; stashing every written row instead fails the backend's check (`q8kv8 born-fp8 q stash mismatch: stashed (num_tokens=2082, layer_id=0) but consuming (num_tokens=2081, layer_id=0)`). Input and output logprobs are bit-identical to `main`, to the same run with the born-FP8 query off, and across two launches.
- Inkling-Small-NVFP4 with FA4's sheared relative bias, TP 4 × DP 2 attention, eager prefill on B200: narrowing Q, K and V alone fails FA4's `assert rel_bias.shape == (total_q, num_head, rel_extent)` on all four ranks; with the per-row inputs narrowed too it serves. (Inkling's output under DP attention is wrong on `main` as well, GSM8K 0.03, so that configuration has no accuracy to compare; at TP 4 this PR and `main` both score 0.74 with identical answers on the first questions.)
- Kimi K3 (synthetic, DeepEP TP 2, eager prefill, 5-token prompt padded to 6 rows), its own trim against this narrowing, per layer and per rank:
  - with the attention-residual bank: real and padded rows identical;
  - standard residual path: identical, except one launch of the trimmed tree that also differs from the trimmed tree's own second launch.
- H200 (fa3, deterministic inference), Qwen3-30B-A3B GSM8K at the top of this stack, against `main`: TP 4, TP 4 × DP 2 attention, TP 2 × PP 2, TP 4 × EP 4 DeepEP, and TP 4 × DP 4 attention × EP 4 DeepEP all give the same accuracy (0.915–0.930) and 200/200 identical answers.

## Speed Tests and Profiling

Not applicable: unpadded batches are unchanged; a padded eager batch now runs the backend on its real rows only, and FA4 writes into the output buffer it is given instead of allocating another.

Memory, on B300 (Qwen3-30B-A3B's config with dummy weights, DeepEP TP 2, eager prefill, deterministic inference):
- A padded attention call's own peak, 127 real of 128 rows × 2048: triton, which writes in place, 528,384 bytes, the padded output; flashinfer, whose output is copied in, 1,044,480 bytes, the padded output plus its real-row output, released at the end of the call. FA4 writes in place too (above).
- The whole run's peak allocated and reserved memory per rank is identical to `main`'s to the byte with triton and with FA4.
