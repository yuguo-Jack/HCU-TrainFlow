# Fix overflow in legacy and v1 DSA top-k selectors

[Upstream PR](https://github.com/sgl-project/sglang/pull/37625) · state: open · merged: False

## Original PR description

## Motivation

Legacy DSA top-k selection can drop candidates when a coarse radix bin reaches its fixed buffer capacity, selecting lower-scoring tokens before full scores are compared. This patch covers the DeepSeek-V4 JIT v1, legacy CUDA AOT and DeepSeek-V4 AOT selectors. KPool JIT already rescans overflowing bins on main (#39273), so its kernel is unchanged here and only gains regression coverage.

## Modifications

Keep normal-bin selection. For a coarse bin larger than the stash, find the exact FP32 cutoff one key byte per row scan; each scan also emits the scores the previous byte placed strictly above the cutoff, and the last scan emits the remaining ones and the cutoff ties (six scans of the row including the coarse histogram, down from seven). Preserve page mapping, `-1` padding and synchronization around shared-memory reuse. The JIT header takes its CUDA/HIP types from `sgl_kernel/utils.cuh`. Retain the additive ROCm tests. Co-authored with Benjamin Oldenburg (@bold84).

Add a CUDA test for `topk_transform_paged` (JIT v1) covering threshold bins on both sides of the 8192-entry stash, strictly higher values ahead of an oversized bin, cutoff ties, clusters that separate only in one of the lower three FP32 key bytes, runtime `topk` values, short rows, score rows padded past their lengths, a noncontiguous score view, and both raw and page-mapped outputs. Add KPool regressions at its 4096-entry stash for oversized and exact-capacity bins, cutoff ties, clusters that separate in the lower three key bytes, padded rows and page-table expansion, registered for CUDA and AMD.

The v2 changes are removed from this PR so the legacy/v1 fix can be reviewed and merged independently. I will submit the v2 changes in a separate PR.

## Accuracy Tests

On RTX PRO 6000 Blackwell (SM120), a combined build passed 12 KPool JIT tests/38 subtests and 7 focused legacy CUDA AOT cases, including oversized coarse bins. One ROCm-only case was skipped. Those results predate the rebase onto main's KPool implementation.

On RTX PRO 6000 Blackwell (SM120), torch 2.14.1+cu130, Triton 3.8.0, at this branch, `test_topk_v1.py` passed (15 tests) and `test_dsa_kpool_topk_transform.py` passed against main's KPool kernel (12 tests, 38 subtests). Against main's unpatched `topk_v1.cuh`, 9 of the 15 v1 tests fail (the overflow cases). The AOT header was compiled for sm_120 in a standalone harness and matched a CPU reference on random rows, single-bin rows above the stash, and strictly higher values plus cutoff ties. The AOT test matrix and ROCm tests have not been run.

## Speed Tests and Profiling

Rows whose coarse threshold bin exceeds the stash take six row scans; other rows are unchanged. No speed benchmark was run.

- Wendy-Hamlet · comment · 2026-09-26T07:55:24Z · [source](https://github.com/sgl-project/sglang/pull/37625#issuecomment-5844417451)

Real-model data point for the legacy (v1) part, since it just got a review: we hit this truncation on DeepSeek-V4-Flash with real long prompts, not only synthetic inputs.

**Where.** On `c9ceab34cf` (2026-07-06), DSV4 prefill with raw indices went through `topk_transform_512` in `topk_v1.cuh`. Its threshold-bin candidates go into a shared-memory buffer of `SMEM_INPUT_SIZE = 8192`; anything past `pos < SMEM_INPUT_SIZE` is dropped, and which ones are dropped depends on `atomicAdd` order. The same code is still on `main` (`3ed56a341b`). There, the default DSV4 prefill path now uses v2 after #39648, so this concerns `SGLANG_OPT_USE_TOPK_V2=0` and releases that predate #39648.

**How often it triggers.** We captured the indexer scores (fp16) for 22 prompts of about 128K tokens (RULER vt / cwe / qa_1 and InfiniteBench longbook_choice_eng), on all 21 CSA layers and 1,536 rows per prompt, for 569,856 (row, layer) pairs in total. Replaying stage 1 bit-exactly from those scores:
- 448 pairs had a threshold bin larger than 8192 while slots were still open. The largest bin held 28,050 candidates.
- All 448 are in the 4 RULER `vt` prompts (variable tracking, highly repetitive text), mostly at L8 with some at L4 and L30.
- The other 18 prompts peak at 5,391 candidates, so they never truncate.

**Whether the selection is actually wrong.** We counted a row as wrong when a non-selected candidate scores strictly higher than the lowest selected one (fp16 rounding is monotone, so this proves the top-k is inexact):
- 444 of the 448 truncated rows are wrong; per prompt, the median number of misplaced candidates per row ranges from 4 to 241.
- Rows that were not truncated have 0 wrong selections (all window rows of the 4 vt prompts, plus one cwe and one longbook prompt).

**On GPU (H100, that tree's kernel, 50 repeats).**
- Synthetic inputs with an oversized bin: 64/64 rows are inexact, and in a few rows the selected set also changes between repeats.
- Replaying real vt score rows: every truncated row is inexact (L4 21, L8 76, L30 5 rows).

So on real DSV4 inputs the legacy path is exact whenever it does not truncate, and truncation happens only on repetitive long inputs, where it nearly always returns a wrong set. We have not measured the end-to-end quality impact.
