# Report the OpenAI layer's env vars in /server_info

[Upstream PR](https://github.com/sgl-project/sglang/pull/43300) · state: open · merged: False

## Original PR description

`experimental/sgl-router` renders, tokenizes and parses chats on the engine's behalf, then serves them through `/generate`. To match the engine exactly, it needs the engine's OpenAI-layer configuration. Server args are visible in `/server_info`, but several env vars the OpenAI layer reads are not:
- `SGLANG_DEFAULT_THINKING`, `SGLANG_DSV4_REASONING_EFFORT` and `SGLANG_DSV41_REASONING_EFFORT` change the rendered prompt;
- `SGLANG_FORWARD_UNKNOWN_TOOLS` and `SGLANG_TOOL_STRICT_LEVEL` change tool parsing and constraints.

Today the router reads these from its own environment, so a router and engine configured differently produce different prompts, with no way to detect it. This PR makes the engine's values visible; a follow-up router PR adopts them and warns when the router's own configuration differs.

## Modifications

- `build_server_info` (shared by HTTP `/server_info` and the native gRPC metadata) adds an `openai_env` block. It holds each env var listed in `OPENAI_LAYER_ENVS`, resolved through `envs`, so defaults are filled in:

  ```json
  "openai_env": {
    "SGLANG_DEFAULT_THINKING": false,
    "SGLANG_DSV4_REASONING_EFFORT": "",
    "SGLANG_DSV41_REASONING_EFFORT": null,
    "SGLANG_INKLING_DEFAULT_REASONING_EFFORT": null,
    "SGLANG_FORWARD_UNKNOWN_TOOLS": false,
    "SGLANG_TOOL_STRICT_LEVEL": 0,
    "SGLANG_ENABLE_REQUEST_HEADER_OVERRIDES": false
  }
  ```

- `TestServerInfoOpenAiEnvField`:
  - checks the block reports overridden values;
  - scans `entrypoints/openai`, `function_call` and `parser` for `envs.SGLANG_*` reads, and fails if one is missing from `OPENAI_LAYER_ENVS`. A new env var in the OpenAI layer therefore can't silently go unreported.
