# [HiCache] Expose the Mooncake L3 object-key layout for external KV routers

## Motivation
SGLang HiCache stores one logical page as several per-pool Mooncake objects, keyed as `{key_prefix}_{page_hash}{suffix}`. An external KV-aware router that wants to score L3 hits must rebuild exactly these keys, but the suffix depends on the model's pool layout, the parallelism layout, and the resolved `--page-size`, so deriving it outside the engine is fragile and breaks silently whenever the naming changes. Mooncake already models per-pool hit policies internally (`PoolHitPolicy`: ALL_PAGES / TRAILING_PAGES); this PR surfaces the same information to external consumers.

This is the engine-side producer for the Dynamo KV router change (ai-dynamo/dynamo#14720), which consumes this layout to reconstruct the object keys.

<!-- Describe the purpose and goals of this pull request. -->

## Modifications

- New engine endpoint `GET /get_hicache_l3_cache_layout`, following the existing `GetInternalStateReq` tokenizer→scheduler round-trip. Returns the per-pool layout: key suffixes, hit policy, trailing-page window, the key prefix, and the rank that produced it. Returns `"enabled": false` (with a debug log naming the reason) when hierarchical caching is disabled or the L3 backend is not Mooncake.
- The layout is assembled by `MooncakeStore.describe_l3_object_layout`, which reuses `_get_hybrid_page_component_keys` — the same key-building code the store writes objects with — so the reported naming cannot drift from the stored keys.
- CPU-only unit tests in `test/registered/hicache/test_hicache_l3_object_layout.py` (registered under `base-a-test-cpu`), and a section in `docs/docs/advanced_features/hicache_design.mdx`.

Two scoping decisions, happy to revisit:
- The endpoint mirrors `/model_info` (no auth); can add `AuthLevel.ADMIN_OPTIONAL` to match the adjacent `/hicache/storage-backend` if preferred.
- Suffixes are rank-independent for single-PP MLA models; with `pp_size > 1` or an MHA layout they embed the rank. The response reports `pp_rank`/`pp_size` so a consumer can check whether one response covers the whole deployment.
