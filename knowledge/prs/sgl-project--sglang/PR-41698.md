## Original PR description

# [AMD] Fuse AITER DSA decode RoPE and KV-cache preparation

**Depends on:** #39083 and #41697

## Motivation

The ROCm MLA path already has a fused operation that applies RoPE, concatenates
the absorbed query, and writes the KV cache. DSA decode using the AITER backend
did not select that path, so it applied RoPE separately before entering the
attention core.

## Modifications

- Recognize AITER DSA decode on ROCm gfx950 as eligible for fused RoPE and
  KV-cache preparation.
- Defer RoPE from the prepare phase to the existing fused operation in the
  attention core.
- Preserve the existing behavior for other architectures and DSA backends.
- Keep AITER DSA on the already-absorbed query path rather than enabling the
  separate fused absorb optimization.

## Accuracy Tests

All five registered fusion-gate tests pass. They verify that AITER DSA decode
selects fused RoPE/cache preparation without enabling fused query absorption.

On MI355X TP4, parent and candidate produced exact matching text and exact
matching retokenized output for fixed-seed 60k-input/600-output greedy
generation.

## Speed Tests and Profiling

Hardware: AMD MI355X, TP4, `amd/GLM-5.2-MXFP4`, FP8 KV cache, and eight matched
serving points from 8k to 120k input.

- Output throughput improved by 16.95–70.01%.
- Mean TPOT improved by 12.94–40.95%.
- Mean TTFT improved by 37.72–45.74%.

This PR shows improvement over #41697 but also over Triton backend

## Reproduction

Launch the candidate on MI355X:

```bash
SGLANG_USE_AITER=1 python3 -m sglang.launch_server \
  --model amd/GLM-5.2-MXFP4 \
  --tp 4 \
  --trust-remote-code \
  --attention-backend dsa \
  --dsa-prefill-backend aiter \
  --dsa-decode-backend aiter \
  --dsa-topk-backend sgl-kernel \
  --kv-cache-dtype fp8_e4m3 \
  --page-size 64 \
  --enforce-shared-experts-fusion \
  --cuda-graph-max-bs-decode 256 \
  --disable-radix-cache \
  --chunked-prefill-size 32768 \
  --max-prefill-tokens 32768
```

For the matched control, change only `--dsa-decode-backend` from `aiter` to
`triton`. After an unrecorded 60k-input/8-output warmup at concurrency 4 and
seed 0, run:

- 1,024 input / 1,024 output, concurrency 128, seed 11, 384 prompts;
- 60,000 input / 600 output, concurrency 4, seed 15, 32 prompts.

- Jacob0226 · comment · 2026-10-08T02:30:24Z · [source](https://github.com/sgl-project/sglang/pull/41698#discussion_r4214004317)

File: `python/sglang/srt/models/deepseek_common/attention_forward_methods/forward_mla_rocm.py` · line 1108

With `--kv-cache-dtype fp8_e4m3`, this sends AITER DSA decode through `_fused_rope_cat_and_cache`, which returns FP8 `q_cat`. `_forward_aiter` then passes `q_scale=None` and allocates `o` with `q.new_empty`, so `o` is FP8 too. On pinned AITER `e7d2453f` this aborts in `mla_decode_stage1_asm_fwd` ("fp8 Q requires q_scale and kv_scale"). With a unit `q_scale` it aborts in `kn_mla_reduce_v1` instead (no FP8 output). I reproduced both on MI355X with the same calls. Suggest keeping BF16 q for AITER DSA in `q_out_dtype`, like the existing `current_attention_backend == "aiter"` case.

MI355X, H=16, topk=2048, bs=4, FP8 KV, persistent metadata, same `mla_decode_fwd` call as `_forward_aiter`; error vs fp32 reference:

| Case | Kernel | Result |
|---|---|---|
| Parent: q BF16, o BF16 | `mla_a16w8_qh16_..._ps` | OK, cos 0.999998, mean abs err 3.5e-5 |
| **This PR**: q FP8, `q_scale=None`, o FP8 | — | **abort**: `fp8 Q requires q_scale and kv_scale` |
| q FP8, `q_scale=None`, o BF16 | — | same abort |
| q FP8, `q_scale=1`, o FP8 | `mla_a8w8_qh16_..._ps` | **abort**: `kn_mla_reduce_v1 doesn't support output type fp8` |
| q FP8, `q_scale=1`, o BF16 | `mla_a8w8_qh16_..._ps` | runs, cos 0.999565, mean abs err 5.7e-4 (~16x parent) |
