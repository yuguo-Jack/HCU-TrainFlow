# Serve decision model checkpoints natively on /v1/decisions, /v1/jev, and /v1/systemone

[Upstream PR](https://github.com/sgl-project/sglang/pull/41712) · state: open · merged: False

## Original PR description

## What

Serve **decision model checkpoints** — models trained to answer typed questions (`choice` / `score` / `noul`) about a state in a single prefill, reading the next-token distribution at trained answer-marker positions — natively in sglang. The first supported family is [Intern-Decision](https://github.com/internlm/Intern-Decision) (internlm, 0.8B/2B/4B, Qwen3.5 backbone, public on HF); the family abstraction exists so further Jev-class checkpoints can register their own prompt source later.

Stacked on #41724 (positional-readout requests must stay out of chunked prefill).

This builds directly on the decisions core from #40992 / #41208 rather than adding a parallel serving path: **`OpenAIServingDecisions` now owns every decision request**. Generic bodies keep the existing per-question label scoring untouched; Jev/System-One-shaped bodies are dispatched to the trained prompt source of the detected decision-model family:

- `POST /v1/decisions` — generic `input` bodies → the existing handler (unchanged); `state`/Jev bodies → the trained source.
- `POST /v1/jev` and `POST /v1/systemone` — the Jev / TypeSafe System One wire contract the rest of this ecosystem speaks (Kev, JevK5, jevbench): `jev-latest` / `jev-preview` accepted as model aliases, choice/score confidence uses the TypeSafe reference formulas (the existing helpers in `systemone/serving.py`, imported as-is).
- `x-typesafe-request-id` echoed or generated on every response (success, 400/404, 422) via a small ASGI middleware scoped to the three routes.

## How

- Dispatch is a first-class concept in the decisions core: `serving_decisions.py` defines `DecisionPromptSource` (`name`, `request_model`, `detect`, `handle`). The existing generic per-question flow is the default/fallback source (appended last, detects any checkpoint; its rendering/label/scoring code is untouched); the trained source is exported as an immutable `PROMPT_SOURCES` tuple from `decision/serving.py` and composed into both handlers at startup; the generic System One path participates as a source of the systemone handler. No per-request `isinstance` special cases, no lazy imports — the dependency direction is one-way (`decision.serving → systemone.serving → openai.serving_decisions`), and `/v1/systemone` validates its body through the resolved native source's request model rather than branching on the checkpoint.
- `entrypoints/decision/`: the Jev wire protocol models (`JevRequest`/`JevAnswer`/`JevResponse`…), the family contract (`families/base.py`: `detect`, `answer_symbols`, `validate`, `compile`), image admission/normalization, the request-id middleware, and the trained prompt source. `families/intern.py` is the first family — detection by the checkpoint's `<decision>` added token and a line-for-line port of the official prompt compiler.
- The seam is source-level dispatch, not the per-question encode: the trained protocol answers all fields from **one prefill** at N marker positions and cannot be expressed as N per-question prompts. The trained source shares the core's server refusals (`_validate_server` runs first) and scores its prefill through a new `TokenizerManagerScoreMixin.score_readouts`, which sits beside `score_prompts` and reuses its logprob extraction/conversion (`max_new_tokens=0`, `token_indices_to_pool` at marker−1, candidate-id softmax; `temperature` as the official `softmax(log p / T)`, argmax-preserving, with a guard refusing numerically destructive T that would flip the argmax).
- **Images**: official HTTP shapes — upload objects `{"type": "image/png", "data": "<base64>"}` and data-URL strings — with the official admission limits (8 images, 12 MiB/image, 32 MiB aggregate, 16 MP, static only), normalized to the official pixel representation (EXIF transpose + RGB) before preprocessing; marker positions are resolved **after** multimodal expansion in the tokenizer manager.
- Refusals: prompts longer than `--chunked-prefill-size` after expansion (400), image admission/limit violations (422 with field location), numerically destructive temperatures that would change the argmax (422, matching the official `scale_probabilities` guard), speculative decoding, any `--chat-template`, `--allow-auto-truncate`, unknown `model` (404). `x-typesafe-request-id` is emitted on 2xx/4xx/5xx including auth rejections.

## Tests

- `test_serving_decisions.py` (the existing suite from #40992) runs **unmodified** and passes.
- `test_serving_decision_models.py`: golden compiler output generated from the official repo, reserved-marker rejection, limits, route dispatch both ways, readout positions/order, TypeSafe answer shapes incl. both confidence formulas as literals, temperature, aliases, image compile + post-expansion marker resolution, refusal branches, route tests incl. the request-id middleware. All CPU-registered; affected suites pass locally.

## e2e (1x H200, BF16, vs official HF backend; together with #41724)

- Text, Typed Decision suite (400 rows / 2000 decisions): **0.8B 77.60%** vs official 77.35%; **4B 80.50%** vs official 80.55%. Native readout vs `/generate` + top-64 route: ≤ 3.3e-8. Post-review-fix equivalence: max |Δp| = 0.0 across synthetic/typed-subset/image/generic traffic vs the pre-fix head.
- Images, synthetic pixel-answerable cases: argmax agreement with the official backend **8/8** for both sizes; prompt token counts match the official processor exactly. EXIF orientation-6 uploads now produce the official pixel representation (Δp = 0.0 vs pre-rotated).
- v1↔v2 equivalence smoke (this refactor): bit-identical answers and token counts across synthetic, typed-subset, image, and generic-body traffic; 32/32 concurrent image requests succeed.

## Limitations

- Prompts must fit one prefill chunk after image expansion (default 8192 tokens).
- The official service's thinking handoff and its `request_id` / `timing` response fields are not served.
- Jev answers intentionally do not carry `label_mass` / `x_label_mass` (the trained readout softmaxes over candidate ids only), and the two request schemas (`JevRequest` vs generic `DecisionRequest`) stay separate.
- 2B checkpoint not verified.
