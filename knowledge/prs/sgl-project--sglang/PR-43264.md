# [Fix] Preserve GLM4 comma argument text instead of Python tuples

[Upstream PR](https://github.com/sgl-project/sglang/pull/43264) · state: open · merged: False

## Original PR description

## Motivation

`parse_arguments("1,000", "number")` currently accepts Python's implicit tuple `(1, 0)`. A GLM-4 tool call then exposes `{"n": [1, 0]}` rather than retaining the original argument text.

Fixes #43147.

## Modifications

Convert tuple results to lists for explicit array schemas. For numeric or untyped arguments, reject tuple results and continue through the existing string fallback. Add regressions for comma expressions, tuple literals, and the serialized GLM-4 tool-call arguments.

- Shreyasg13 · comment · 2026-10-09T03:06:43Z · [source](https://github.com/sgl-project/sglang/pull/43264#issuecomment-6073421536)

Thanks for picking this up! One small behaviour note: before this change, an array-typed argument written with a bare comma (e.g. `<arg_value>1, 2</arg_value>` for `{"type": "array"}`) came out as `[1, 2]`, since `json.dumps` turned the tuple into a list. With the tuple rejected unconditionally it now becomes the string `"1, 2"`. Keeping the list when `arg_type == "array"` would avoid that:

```python
if not isinstance(parsed_value, tuple):
    return parsed_value, True
if arg_type == "array":
    return list(parsed_value), True
```

FYI, `glm47_moe_detector.py` (GLM-4.7/5) has its own copy of `parse_arguments` with the same bug. I've opened #43270 for that file only, so the two PRs don't overlap.
