# [Perf] GGUF: llama.cpp's int8 tensor-core MMQ behind ggml_mul_mat_a8

[Upstream PR](https://github.com/sgl-project/sglang/pull/43650) · state: open · merged: False

## Original PR description

## Motivation

On CUDA, `ggml_mul_mat_a8` is the dp4a MMQ that vLLM copied from llama.cpp in 2024 (b2899). Since then llama.cpp's MMQ has moved to int8 tensor-core `mma` instructions, stream-k scheduling and kernels for the i-quants. At prefill sizes, SGLang's GGUF linear layers are now **8-15x slower** than llama.cpp on the same GPU. The i-quants (IQ2_*, IQ3_*, IQ4_*, IQ1_S) have no MMQ at all here: they dequantize the whole weight to bf16 on every call.

Low-bit GGUF releases of large MoE models are now common: IQ2/IQ3/IQ4 experts, with Q4_K/Q6_K dense layers. This PR replaces the CUDA implementation behind `ggml_mul_mat_a8` with llama.cpp's current MMQ and extends MMQ to all GGUF weight types except IQ1_M.

All numbers below are from an RTX 5070 Ti (sm_120) with bf16 activations. The table is ms per call, for an 11008 x 4096 weight streamed from DRAM, timed as 20 calls in a CUDA graph:

| type | M | main (dp4a MMQ, or dequant for IQ) | **this PR** | dequant + bf16 GEMM | llama.cpp (test-backend-ops) |
|---|---|---|---|---|---|
| Q4_K | 256 / 4096 / 16384 | 2.41 / 38.4 / 154 | **0.193 / 3.10 / 13.9** | 0.380 / 4.02 / 15.5 | 0.182 / 2.82 / 12.8 |
| Q6_K | 256 / 4096 / 16384 | 3.11 / 49.4 / 198 | **0.261 / 3.88 / 17.1** | 0.393 / 4.03 / 15.5 | 0.256 / 3.60 / 15.9 |
| Q8_0 | 256 / 4096 | 2.38 / 37.9 | **0.207 / 2.90** | 0.423 / 4.07 | 0.205 / 2.64 |
| Q2_K | 256 / 4096 | 1.48 / 24.1 | **0.314 / 4.68** | 0.371 / 4.01 | 0.305 / 4.38 |
| IQ4_XS | 16 / 256 / 4096 | dequant: 0.246 / 0.382 / 4.02 | **0.039 / 0.173 / 2.85** | (same as main) | 0.030 / 0.167 / 2.59 |
| IQ3_S | 16 / 256 / 4096 | dequant: 0.245 / 0.385 / 4.03 | **0.052 / 0.189 / 3.10** | (same as main) | 0.041 / 0.182 / 2.83 |

## Modifications

### Vendored llama.cpp
`python/sglang/kernels/aot/csrc/quantization/gguf/llama_mmq/ggml/` holds llama.cpp commit `23b0202a189c44a54625aadcb37a946dd1d6278d`, verbatim; the one change to it is kept as a patch file applied at build time (see *bf16 / fp16 output* below):
- MMQ headers and template instances, `mma.cuh`, `vecdotq.cuh`, `quantize.cuh`, `common.cuh`, `ggml-common.h`, and the ggml headers they include
- 45 files, about 18.5K lines, **unmodified**
- `SHA256SUMS` and the upstream LICENSE (MIT) sit next to them, and `THIRDPARTYNOTICES.txt` carries the notice

The shim and entry points around them:
- **`llama_mmq/ggml_shim.cu`** (139 lines) supplies what the vendored code links against:
  - `ggml_cuda_info()`, built from `cudaDeviceProp`
  - a pool backed by `c10::cuda::CUDACachingAllocator` (`raw_alloc_with_stream`), which is safe under graph capture
  - errors as `std::runtime_error`
- **`llama_mmq/mmq_dense.cu`** (198 lines) is the 2D path of llama.cpp's `ggml_cuda_mul_mat_q`: tile selection, `GGML_PREC_Q8` and `mul_mat_q_case<type>`.
- **`llama_mmq/quantize_mmq_q8_1.cu`** (197 lines) is llama.cpp's `quantize_mmq_q8_1`, templated to read fp32/fp16/bf16 directly, so bf16 activations need no conversion pass.
  - Block sums are taken over the quantized values, as in #43636.
  - The file carries an MIT attribution.
- **`llama_mmq/sgl_llama_mmq.h`** is the boundary between torch and ggml; neither header includes the other.

### bf16 / fp16 output (second commit)
llama.cpp's MMQ writes fp32; SGLang's activations are bf16. Instead of an fp32 output plus a cast (an extra round trip over the output and an fp32 temporary of M x N, e.g. 721 MB at M = 16384 for an 11008-row weight), the kernel writes X's dtype directly:
- `llama_mmq/patches/0001-mmq-dst-type.patch` (+61 lines in `mmq.cuh`) adds a runtime destination type to `mmq_args` (no extra template instances). CMake copies the vendored `ggml/` into the build tree and applies the patch there, so the tree in the repository stays verbatim (`sha256sum -c ggml/SHA256SUMS` passes) and a re-vendor that no longer applies fails loudly.
- Stream-k: a block that finishes a tile another block started would round twice if its partial sums went through the half-precision output, so partial sums stay fp32 in the fixup buffer and are rounded once.
- Results are bit-identical to the fp32 result rounded to bf16 / fp16 (912 cases: all 18 types x 2 shapes x M = 2..2050, and 5 types x 2 large shapes up to M = 16384).

### `gguf_kernel.cu`
- `ggml_mul_mat_a8` keeps its schema and output dtype.
- On CUDA it calls the new MMQ, which writes X's dtype directly (see above).
- MUSA keeps the dp4a kernel (`#ifdef USE_MUSA`).
- An unsupported type now raises (`TORCH_CHECK`). The old kernel silently returned an uninitialized tensor for i-quants.

### `python/sglang/srt/layers/quantization/gguf.py`
- `MMQ_QUANT_TYPES` on CUDA covers all standard, K and i-quant types except IQ1_M (Q8_1 is an activation format). MUSA keeps standard + K.
- `MOE_MMQ_QUANT_TYPES` (standard + K) gates `fused_moe_gguf`'s MMQ branch, because the MoE kernel is still the dp4a one (see Follow-ups).
- `fused_mul_mat_gguf`: for CUDA MMQ types, MMVQ is used for a single token only.
  - I measured 10 types x 4 shapes. MMVQ wins only at M=1 (by up to 1.8x); MMQ is faster from M=2. At M=16, MMVQ is 2.5-11x slower.
  - The old cutoffs (2/6, and 8/16 for i-quants) were tuned against the dp4a MMQ and the dequant path.
- **Padding.** llama.cpp's MMQ reads each weight row in steps of 256 values. When K % 512 != 0 it reads past the last row, which is why ggml pads its tensors to a multiple of 512 values (`MATRIX_ROW_PADDING`). This PR pads the same way, with zeros:
  - Unmerged weights are padded once at load.
  - Merged QKV and gate/up shards keep main's layout; `_gguf_mmq_shard` passes a shard as a view when the bytes after it suffice, and otherwise makes the one per-forward copy main already makes, into a buffer that ends with the zero padding. That is never more copies than main, and the same number when K % 512 == 0.
  - The op itself still pads an unpadded weight with a per-call copy (warning once), so other callers stay correct.

### Build (`CMakeLists.txt`)
- An OBJECT library `sgl_llama_mmq` with its own include path is linked into both common_ops libraries. No ggml symbols are exported.
- It is compiled for **sm_80, sm_90, sm_100f and sm_120a**. The sm_80 SASS runs on 8.x, and all 8.x share the same Ampere tile config.
- Objects total about 35.7 MB with `--compress-mode=size` (33.9 MB before the bf16 / fp16 output, +2.3 MB), and take about 80 s with 32 jobs.
- The bf16 / fp16 output patch is applied by CMake to a copy of the vendored tree in the build directory, so `patch` must be available at configure time.
- `.pre-commit-config.yaml` excludes the vendored directory, because codespell flags an upstream spelling.

## Accuracy Tests

`python/sglang/kernels/aot/tests/test_gguf.py` gains the following MMQ coverage:
- **All sample types**, including the i-quants, at 7, 8, 9, 65, 128, 129 and 2050 tokens.
- **Synthetic weights for 18 types**:
  - rows = 1000 with K = 2304, which hits the fallback tiles and the tail
  - 1024 x 2048
  - bf16, fp16 and fp32 activations
  - padded vs unpadded weights, which must be bit-identical
  - strided X
- M = 16384 for three types.
- Unsupported types must raise.
- CUDA graph capture and replay.

Relative L2 against gguf-py's dequantization is 5.3e-3 to 6.1e-3 for every type, which is the q8_1 activation rounding. **235 tests pass** on the first commit and **273** with the second (38 more for the bf16 / fp16 output: bit-exactness against the fp32 result rounded, stream-k fixup shapes, CUDA graph replay), both in a standalone build of the kernels and in the real CMake-built `common_ops` (sm90 library) loaded through `torch.ops`. compute-sanitizer memcheck over the 18 types reports no errors.

Not run: MUSA (not built), and execution on sm_80/90/100 (compile-checked only; execution was on sm_120).

## Speed Tests and Profiling

See the table above (first commit, fp32 output plus cast). Writing bf16 directly (second commit) removes the cast. 11008 x 4096, bf16, ms, first commit -> second commit:

| type | M = 4096 | M = 16384 |
|---|---|---|
| Q4_K | 3.123 -> 2.840 (-9.1%) | 14.075 -> 12.712 (-9.7%) |
| Q6_K | 3.926 -> 3.552 (-9.5%) | 17.372 -> 15.507 (-10.7%) |
| IQ4_XS | 2.884 -> 2.599 (-9.9%) | 12.858 -> 11.447 (-11.0%) |

With this, the port is within a few percent of llama.cpp itself (e.g. Q4_K at M = 16384: 12.71 vs 12.8 ms).

## Dependencies

This branch is stacked on **#43636** (its first two commits: the IQ3_S codebook and the q8_1 block sums). Without #43636 the new IQ3_S tests would fail on main's IQ3_S tables.

This PR does not change the merged-shard layout, which **#43430** handles separately. If #43430 lands first, the padding moves to the end of its flat buffer, a few lines.

## Follow-ups (planned, not in this PR)

1. **MoE with the same MMQ (MUL_MAT_ID).** On main today the GGUF MoE path is slow, and at prefill sizes it breaks. Each row is one MoE layer, in ms at 256 / 1024 / 2560 / 8192 tokens (64 experts, 8 per token, hidden 2560):

   | layer | `fused_moe_gguf` today | llama.cpp MMQ (gate + up + down) |
   |---|---|---|
   | IQ3_S gate/up + IQ4_NL down (I 640) | 8.23 / 33.1 / 82.8 / crashes ("invalid argument") | 0.83 / 1.51 / 3.42 / 10.4 |
   | Q4_K (I 768) | 2.62 / 9.85 / 24.6 / 78.4 (with #43445; main fails above 64 tokens) | 0.93 / 1.67 / 3.68 / 11.4 |
   | Q6_K (I 768) | 3.50 / 13.3 / 33.1 / 106 | 1.17 / 2.05 / 4.43 / 13.4 |

   The plan:
   - A new op `ggml_moe_mmq(X, W, topk_ids, type, row)` that uses llama.cpp's `mm_ids_helper` to route tokens to experts without a host sync.
   - The scatter quantizer, so each token is quantized once for all its top-k.
   - Rewire `fused_moe_gguf` onto it, and drop `moe_align_block_size` for GGUF.
   - About 180 more vendored lines (`mmid.cu`) plus about 300 of entry and dispatch, with MoE tests (there are none today).
2. **Binary size.** If 34 MB per library is too much, the options are:
   - drop sm_80
   - restrict the tile widths to {8, 16, 32, 64, 128}, about 3x smaller but up to 2x wasted compute for 33-127 tokens
   - move the kernels to the JIT path under `python/sglang/kernels/jit`
3. **Q2_K, Q3_K, Q6_K, IQ2_XS and IQ2_S at large M.** These are slower than the other types, and Q2_K / Q6_K / IQ2_S are slower than dequant + bf16 GEMM at large M (Q2_K 18.7 vs 15.5 ms at M = 16384). The same holds in llama.cpp's own kernels: all five carry one scale per 16 values, so the mma path issues two `m16n8k16` per 32 values where the other types issue one `m16n8k32`, and on sm_120 a k16 mma costs the same tensor time as a k32 (measured 49.7 G mma/s for both). For Q2_K and Q3_K the scale can be folded into the int8 weights exactly, which on our side made them 17-28% faster with llama.cpp's tests passing; for Q6_K and IQ2 the product does not fit int8. Such a change belongs in llama.cpp itself, and the vendored copy would pick it up on the next resync. A per-type switch to the dequant path (as in #43626) is possible meanwhile if wanted.
