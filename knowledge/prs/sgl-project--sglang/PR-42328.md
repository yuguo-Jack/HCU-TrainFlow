# fix(function_call): stream DeepSeek V3 tool arguments that arrive with the name

[Upstream PR](https://github.com/sgl-project/sglang/pull/42328) · state: open · merged: False

## Original PR description

## Motivation

Fixes #42327.

With `--tool-call-parser deepseekv3`, a streamed chat completion returns `"arguments": "{}"` for a tool call whose closing ```` ``` ```` fence and `<｜tool▁call▁end｜><｜tool▁calls▁end｜>` arrive in the same, final stream event, while the non-streaming path returns the full arguments. That is the usual shape of the last event with MTP/EAGLE speculative decoding (the DeepSeek-V3/R1 cookbook deployment) or `--stream-interval > 1`.

`DeepSeekV3Detector` only matches a call once its closing fence has arrived, so the first match already holds the complete arguments, but the branch that sends the tool name returned without them and deferred them to the next increment. With no next increment, the serving layer's `_check_for_unstreamed_tool_args` filled in `"{}"`.

## Modifications

- `deepseekv3_detector.py`: after sending the tool name, continue into the existing argument handling in the same pass instead of returning, as `glm4_moe_detector.py` already does. `_last_arguments` is empty at that point, so the full arguments are emitted once, and the completion bookkeeping runs as before.
- `test_function_call_parser.py`: a regression case in `TestDeepSeekV3Detector` with two calls, each with its closing fence and end tokens in one increment, the last of them in the final increment. It fails on `main` and passes with the fix.

## Accuracy Tests

Not applicable: parser-only change; no model output, kernel or forward code is touched. Through `OpenAIServingChat._generate_chat_stream` with a mocked engine, the bundled final event now streams `{"city": "Paris", "unit": "celsius"}` instead of `{}`; token-by-token events are unchanged.

Not applicable: no change to inference.

- adenzhou1350 · comment · 2026-10-10T20:08:56Z · [source](https://github.com/sgl-project/sglang/pull/42328#issuecomment-6101689484)

Thanks for fixing the same-increment argument loss. I independently checked this head (`4581069`) and #42464 (`72cbf05`): single-call delivery and separately drained two-call controls work with both fixes.

One additional case from #31915 remains: two complete calls in one increment select the **second** name/arguments, while removing the **first** call from the buffer. This may be better handled as a follow-up rather than expanding this PR.

```python
import json
from sglang.srt.entrypoints.openai.protocol import Tool
from sglang.srt.function_call.deepseekv3_detector import DeepSeekV3Detector

tools = [Tool(type="function", function={
    "name": name, "parameters": {"type": "object"}
}) for name in ("get_weather", "get_time")]

def call(name, city):
    return ("<｜tool▁call▁begin｜>function<｜tool▁sep｜>" + name
            + "\n```json\n" + json.dumps({"location": city})
            + "\n```<｜tool▁call▁end｜>")

text = ("<｜tool▁calls▁begin｜>" + call("get_weather", "Tokyo")
        + call("get_time", "Paris") + "<｜tool▁calls▁end｜>")
d = DeepSeekV3Detector()
print([c.model_dump() for c in d.parse_streaming_increment(text, tools).calls])
print([c.model_dump() for c in d.finish(tools).calls])
print([c.model_dump() for c in DeepSeekV3Detector().detect_and_parse(text, tools).calls])
```

On both PR heads, the first print contains only `get_time` / Paris (name and argument deltas at index 0); `finish()` emits nothing. Non-streaming returns `get_weather` / Tokyo followed by `get_time` / Paris. Adding empty increments instead duplicates `get_time`, so it does not recover the missing call. Reversing the call order similarly loses the first call.

Scope: Linux CPython 3.12 CPU checks against the complete unchanged detector and its actual Tool/base/JSON-helper modules, bypassing only heavyweight package initializers; not a server/model or official CI run. Current main `234ccba` has the same detector bytes and also loses the first call. No competing PR opened.
