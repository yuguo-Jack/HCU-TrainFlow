# [DSv4.1] Bound prefill indexer score tiles by a memory budget

[Upstream PR](https://github.com/sgl-project/sglang/pull/43376) · state: open · merged: False

## Original PR description

## Motivation

The DeepSeek-V4.1 ratio-1/2 index layers score every prefill row against the whole compressed context with DeepGEMM `fp8_fp4_mqa_logits`, in row tiles (`score_tiles` / `flat_index_logits_tiles`). Each tile is `rows x max compressed context` fp32, allocated by DeepGEMM outside every pool sized by `--mem-fraction-static`. Two things made these tiles a long-context OOM:

1. The tile budget was a fixed 2 GiB (`_DEEP_GEMM_SCORE_BUDGET_BYTES`), whatever memory was actually free. At a 485K-token context a ratio-1 row is 1.85 MiB, so a chunk above 1104 rows scores in 2 GiB tiles.
2. The budget counted only the logits. While a tile is alive the dense-blocks publisher also allocates a bool causal mask, and `select_candidate_block_ids` padded an unaligned context (`F.pad`) into a full fp32 copy of the tile, so at 485K a 2 GiB tile peaked at about 4.2 GiB. The sparse-table publisher kept the previous tile and its block keys alive while the next tile was allocated.

Observed on 4x RTX PRO 6000 Blackwell (SM120, about 95 GiB each), TP4, `--mem-fraction-static 0.85`, chunked prefill 8192: a conversation with about 485K cached tokens grew by prefill chunks of a few hundred to a few thousand tokens. Each chunk allocated 1.0 to 2.0 GiB per tile in `_publish_prefill_blocks -> score_tiles -> fp8_fp4_mqa_logits`, the caching allocator logged repeated OOM retries of 1.0 to 2.1 GiB, and the scheduler died with `CUDA out of memory` (2.00 GiB requested, 1.98 GiB free, 83.5 GiB allocated by PyTorch).

Related: #40967.

## Modifications

- `scoring.prefill_score_budget_bytes`: the minimum of the static budget, `SGLANG_DSA_MQA_LOGITS_FREE_MEM_FRACTION` of current free memory, and 2 GiB, so a tile is never larger than before. It returns 2 GiB without a device query when the forward is below `MQA_LOGITS_STATIC_SKIP_ELEMS`, and the static budget (capped at 2 GiB) without a free-memory query under graph capture.
- `DeepseekV4AttnBackend` reads it once per eager prefill forward, on the first low-ratio layer and only when the DeepGEMM prefill scorers run, keeps it on `DSV4Metadata.low_ratio_score_budget_bytes`, shares it with the late-layer tail metadata, and passes it through `PrefillInputs.score_budget_bytes` to `DeepGEMMPrefillData`. Graph-replay copies clear it.
- `flat_index_logits_rows_per_tile` / `flat_index_logits_tiles` / `score_tiles` take the caller's scratch as bytes a row and bytes a tile. A tile takes all rows when their aligned allocation (rows aligned to the kernel's row group `128 // heads`, row stride aligned to 256 fp32) plus that scratch fits the budget; otherwise it takes row-group multiples, with one row group as the floor.
- Dense-blocks publisher: scores block-aligned (`width_align = lcm(4, block_size)`) and passes `logits[rows, :ceil(lc / block_size) * block_size]` to `select_candidate_block_ids`, so it no longer pads a copy; the publisher masks padding columns to `-inf` before block selection. It declares the mask, block maxima and block top-k as row scratch and one request's int64 index vector as tile scratch. The dense-blocks consumer declares `topk_among_blocks`'s candidate gather, masks and picks as row scratch.
- Sparse-table publisher: drops each tile and its block keys before the next tile is scored, and declares the block keys as row scratch.

The budget covers a score tile and declared scratch, subject to the minimum row-group allocation. Free memory can change later in the forward.

## Accuracy Tests

New CPU test `test/registered/unit/layers/test_dsv41_prefill_score_tiles.py` replaces DeepGEMM and the ragged top-k with exact references and covers allocation alignment and scratch, tiled selection parity, tile lifetimes, and per-forward budget propagation and clearing.

GPU test additions in `test/registered/kernels/ops/attention/test_dense_prefill_indexer.py` (SM100 and SM120), at a 485,123-entry compressed context:
- With 2048 query rows, tiles under a 256 MiB budget return bitwise the same scores as one untiled call within each row's valid window.
- With 2048 query rows, publish, consume and the full top-k select positions with the same scores (exact ties may resolve to different positions) and the same blocks at a 256 MiB budget as in one tile, and the published blocks match the pad-based reference.
- With 12 query rows at one-row-group tiles, the measured requested peak bytes past each path's outputs stay within the logits allocation plus declared scratch and a 1 KiB allowance (consumer at top-k 512 and 16).
- `test_score_memory_is_bounded` now holds an unaligned 65535 context to the same 3 GiB as the aligned one.

On RTX PRO 6000 Blackwell (SM120), `python -m pytest test/registered/kernels/ops/attention/test_dense_prefill_indexer.py`: the three tests above that run on SM120 pass in each of 8 consecutive runs (`test_tiles_score_bitwise_like_one_tile`, `test_selection_matches_one_tile`, `test_tile_scratch_within_declared_bytes`); the five SM100-only tests, including `test_score_memory_is_bounded`, were skipped. `test/registered/unit/layers/test_dsv41_prefill_score_tiles.py`: 13 passed.

## Speed Tests and Profiling

Prefill throughput on DeepSeek-V4.1-Flash, 4x RTX PRO 6000 Blackwell, TP4, median of three repetitions per prompt length, with this change vs the same build without it: 10,086 / 12,628 / 12,851 vs 10,092 / 12,640 / 12,958 tok/s at 8K / 32K / 128K prompts. At the default 2 GiB cap with ample free memory, tiles are smaller than before because the scratch now counts against the budget (at a 485K context, ratio 1, 32 index heads, candidate block size 8 and 2048 candidate blocks: 704 publisher rows per tile instead of 1104). With 1.98 GiB free and the default free-memory fraction 0.2, the budget is 0.40 GiB and the same configuration takes 136 publisher rows per tile.
