# [diffusion] perf: replay hot Triton launches from Rust

[Upstream PR](https://github.com/sgl-project/sglang/pull/39878) · state: open · merged: False

## Original PR description

> **Draft.** The mechanism is measured and bit-exact, but coverage is three call
> sites out of the ~1191 small launches a Z-Image step makes. Opening it early
> for a read on the approach and on where the crate belongs.

## Motivation

At low resolution a diffusion step is not a few large kernels, it is a long tail of small ones. Profiling Z-Image-Turbo at 512x512, 4 steps on one H200:

| | |
|---|---|
| kernels | 2108 |
| mean kernel | **26.6 us** |
| GPU busy | 36.9% |
| **GPU idle** | **63.1%** |
| idle behind each kernel | **45.5 us** |

76% of those kernels run under 20 us and together account for 15% of the busy time. The device is finished long before Python and the Triton launcher can describe the next launch.

This is regime-specific, and the regime is set by kernel size rather than by parallelism. The same engine on MiniMax-H3 at 768p across 8 GPUs, Ulysses8, eager, idles **0.3%** — kernels there average 482.8 us. Sharding the sequence does not change that: it divides the work per kernel's *sequence*, not the kernel's absolute size.

## Modifications

`rust/sglang-launch`, a PyO3 extension holding `LaunchChain`: record a launch as (function, grid, block, arguments), then replay it through `cuLaunchKernel`. Kept out of the root workspace exactly as `sglang-radix-tree` is, and for the
same reason — PyO3 0.22 cannot share a dependency graph with the workspace's native `links = "python"` crates.

Python side, `fast_launch.CachedLaunch` keys recordings by signature (shape, stride, dtype, eps — not addresses). First call of a signature runs the ordinary Triton path and records; later calls rebind pointers and replay.

Three entry points adopt it: `rmsnorm_scale`, `rmsnorm_tanh_residual`, `zimage_qk_rmsnorm_native`. No model definition changes.

Unlike the breakable-graph path a recording survives a shape change: a new signature records a new entry rather than forcing a recapture. That matters for models whose sequence length depends on the prompt — MiniMax-H3 stays eager in its validated deployment precisely because prompt-dependent packed boundaries miss a captured signature.

## Accuracy Tests

Bit-exact, which is the point: the same kernel runs with the same grid and
arguments in the same order, so only host latency changes.

- Call site: `torch.equal(triton_result, replayed_result)` is True, max abs
  difference 0.
- End to end: same prompt and seed generated with the extension importable and
  not, PNG sha256 identical (`34aab947d442b26c3cf8c793728f21e5...`).

This is what `torch.compile` cannot offer here — it is a measured comparator on
this codebase, not a lossless baseline.

## Speed Tests and Profiling

Z-Image-Turbo, 1x H200, 512x512, 4 steps, eager, no compile, no breakable graph:

| entry points hooked | window | GPU idle | per step |
|---|---|---|---|
| none (baseline) | 167.31 ms | 63.1% | 131.3 ms |
| 1 | 163.76 ms | 62.2% | 127.2 ms |
| **3** | **129.74 ms** | **51.6%** | **107.7 ms** |

**1.29x end to end, step -18.0%, idle 63.1% -> 51.6%.**

Two results worth recording separately.

**The cut has to be deeper than the launcher.** At a single call site,
replacing only the Triton launcher was worth 1.36x (27.15 -> 19.93 us).
Short-circuiting sglang's own per-call validation and stride derivation as well
took it to 2.33x (27.27 -> 11.73 us). Half the cost was bookkeeping *around*
the launch, not the launch.

**Gain tracks coverage, linearly.** One entry point moved the step 2.1%; three
moved it 18%. The remaining ~890 small launches per step are ATen elementwise
rather than Triton and need a different hook.

## Open questions for review

1. **Build integration.** The crate is registered in `extension-manifests` but
   nothing builds or ships it yet; `fast_launch.available()` returns False and
   every call takes the existing path. How should it be wired — alongside
   `sglang-radix-tree`, or behind an extra?
2. **Coverage.** Worth extending to the ATen elementwise launches, or is a
   Triton-only hook the right boundary?
3. **Signature cache growth.** One entry per (shape, stride, dtype, eps). Fine
   for fixed-resolution serving; a bound may be wanted for arbitrary shapes.
