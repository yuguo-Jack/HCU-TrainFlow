# [QSA] Defer FP8 KV widening in sparse chunk-prefill kernels

[Upstream PR](https://github.com/sgl-project/sglang/pull/41461) · state: open · merged: False

## Original PR description

## Summary

This PR optimizes the QSA sparse chunk-prefill operand pipeline for FP8 E4M3 KV cache in `Qwen3.8-Flash-Next-FP8`.

The optimized path:

- Dynamically quantizes each query-head row to FP8 E4M3.
- Keeps Q/K/V and softmax-probability operands in FP8 until the Triton dot boundary.
- Avoids explicit full-tile K/V widening in the kernel source.
- Preserves FP32 accumulation and BF16 output.
- Uses `BLOCK_N=32`, which is required by the tested Triton FP8 dot lowering and improves tile efficiency.


## Motivation

The existing sparse chunk-prefill kernel widens FP8 K/V tiles to the query dtype before both dot operations.

Nsight Compute shows that the target H20 kernel is not DRAM-bound. The measured improvement comes from shortening the lifetime of widened operands, reducing conversion and MIO pressure, and improving Tensor-pipe utilization. It does not rely on an H20-specific native FP8 MMA instruction.

## Runtime dispatch

The FP8 operand pipeline is selected only when all of the following conditions are satisfied:

- the device matches a validated tuning profile, currently NVIDIA H20;
- K/V cache dtype is FP8 E4M3;
- head dimension is 256;
- GQA group size is between 1 and 12;
- sparse top-k is at least 1024;
- the average query length is at least 4096 tokens per request.

All other configurations retain the existing BF16-widening path.

## Implementation

The BF16 query is dynamically scaled per head row before conversion to E4M3:

```python
q_absmax = tl.max(tl.abs(q_values), axis=1)
q_scale = tl.where(q_absmax > 0, q_absmax / 448.0, 1.0)
q_values_fp8 = (q_values / q_scale[:, None]).to(tl.float8e4nv)
```

The QK result is restored with the row-wise scale:

```python
scores = tl.dot(q_values_fp8, keys) * q_scale[:, None]
```

The optimized pipeline is:

```text
BF16 Q
-> row-wise E4M3 quantization
FP8 E4M3 K/V cache
-> FP8 Q/K operands at the QK dot boundary
-> FP32 score accumulation
-> online softmax
-> FP8 probability/V operands at the PV dot boundary
-> FP32 output accumulation
-> BF16 output
```

This is an FP8 operand-lifetime optimization, not a native FP8 MMA implementation. With the tested Triton 3.7.1 toolchain, the final PTX still lowers the dot operations to FP16 MMA instructions. The benefit comes from avoiding source-level full-tile widening and allowing conversions to be scheduled closer to the MMA operation.


## Performance

All serving and primary kernel results were measured on NVIDIA H20 with FP8 E4M3 K/V.

### Shape generalization

| GQA group size | Top-k 1025 speedup | Top-k 2051 speedup |
|---:|---:|---:|
| 1 | 1.47x | 1.50x |
| 3 | 1.46x | 1.49x |
| 6 | 1.45x | 1.50x |
| 8 | 1.44x | 1.49x |
| 12 | 1.41x | 1.46x |

Group sizes 2 and 4 were also validated and showed comparable results. The optimization is not tied to one tensor-parallel shape or to the exact Qwen3.8 top-k value of 2051.

### Kernel

Primary benchmark shape:

```text
24 query heads
2 KV heads
head dimension 256
GQA group size 12
top-k 2051
```

| Case | Baseline | Candidate | Latency reduction |
|---|---:|---:|---:|
| 8K contiguous | 6.318 ms | 4.275 ms | 32.34% |
| 8K fragmented | 6.312 ms | 4.268 ms | 32.38% |
| 32K contiguous | 6.363 ms | 4.298 ms | 32.45% |
| 32K fragmented | 6.349 ms | 4.308 ms | 32.15% |

### Ablation

A separate ablation used the Qwen3.8 TP4 local shape on two idle H20 GPUs:

```text
Q/KV heads: 6/1
Query length: 4096
KV length: 8192
Head dimension: 256
Top-k: 2051
```

| Path | Latency range | Speedup vs BF16 BN16 | Max abs error |
|---|---:|---:|---:|
| BF16 widening, BLOCK_N=16 | 3.107-3.132 ms | 1.00x | 0 |
| BF16 widening, BLOCK_N=32 | 2.818-2.840 ms | 1.102-1.103x | 0.000977 |
| FP8 operands, BLOCK_N=32 | 2.130-2.147 ms | 1.4585-1.4587x | 0.015137 |

At the same `BLOCK_N=32`, the FP8 operand path is approximately 1.32x faster than explicit BF16 widening. This shows that the gain is not explained by tile-size tuning alone.

`FP8 + BLOCK_N=16` is not a valid configuration in the tested Triton 3.7.1 toolchain because the FP8 PV dot reduction dimension must be at least 32.

### End-to-end prefill

Serving configuration:

```text
Model: Qwen3.8-Flash-Next-FP8
TP4 / EP4
Local Q/KV heads: 6/1
GQA group size: 6
chunked-prefill-size=8192
max-prefill-tokens=16384
kv-cache-dtype=fp8_e4m3
attention-backend=fa3
```

| Input length | Throughput improvement | TTFT reduction |
|---:|---:|---:|
| 8K | +0.35% | -0.33% |
| 32K | +3.48% | 3.41% |
| 64K | +4.32% | 4.15% |
| 128K | +4.84% | 5.07% |
| 256K | +3.94% | 4.10% |
| 512K | +2.35% | 2.37% |

The 8K TTFT result is effectively flat and does not show an end-to-end latency benefit at that length.

## Tests

The focused tests verify:

1. Workload eligibility is independent of device selection.
2. Only devices with validated tuning profiles automatically select the FP8 path.
3. Unsupported dtypes and shapes retain the existing path.
4. The FP8 operand path matches the BF16-dot path across the tested GQA group sizes and top-k values.
