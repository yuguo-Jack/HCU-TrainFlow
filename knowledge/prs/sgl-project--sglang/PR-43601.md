# [diffusion] torch.compile: skip inductor's saved multi-kernel pick (Z-Image warm starts crash or hang)

[Upstream PR](https://github.com/sgl-project/sglang/pull/43601) · state: closed · merged: True

## Original PR description

## Motivation

Since #35755, Z-Image compiles with `multi_kernel_hints`. With `--enable-torch-compile`, every server start after the first fails: the first start fills the inductor FX-graph cache, and each later start hits it.

| Z-Image-Turbo, 1x GB300, `sglang generate --enable-torch-compile true`, fresh cache root | Result |
|---|---|
| 1st start (cold cache) | OK, 112 s wall |
| 2nd start (warm cache) | **fails**: `BackendCompilerFailed: TypeError: 'NoneType' object does not support the context manager protocol` (4x) |
| 2nd start, `TORCHINDUCTOR_FX_GRAPH_CACHE=0` | OK, 89 s wall (recompiles) |
| 2nd and 3rd start with this PR | OK, 54 s / 51 s wall |

With TP the failure becomes a hang. Only the rank that hits the cache raises and abandons the request. Its peer keeps waiting in the custom all-reduce, and its next `cuModuleLoadData` blocks behind the spinning kernel:

```
Z-Image-Turbo, 2x GB300, --tp-size 2 --enable-torch-compile true, warm cache
TP0  idle in recv_reqs -> broadcast            (warmup request failed: backend='inductor' raised)
TP1  cuModuleLoadData <- triton _init_handles   (100% CPU for 10+ min; GPU1 at 100%)
```

Cause (torch 2.13, triton 3.7). On a cache hit, the loaded module builds `SizeHintMultiKernelCall` at import time, and its constructor reads the saved pick (`MultiKernelCall.load_cache`). That hashes every sub-kernel through `k.fn.cache_key` (`with self._hash_lock`). The sub-kernels come back from the compile workers with `_hash_lock = None` (`CachingAutotuner.prepare_for_pickle`), and they are not restored until `async_compile.wait()` runs later in the same module.

## Modifications

`apply_inductor_config` sets `TORCHINDUCTOR_DISABLE_MULTI_KERNEL_CACHE=1` (via `setdefault`) whenever a model sets `multi_kernel_hints`. Inductor then skips `load_cache`, and each process re-picks during warmup. The FX-graph and autotune caches are unaffected.

## Accuracy Tests

The output is bit-identical to an unpatched warm start that recompiles (`TORCHINDUCTOR_FX_GRAPH_CACHE=0`): md5 `0d6093d6…` for that start and for both patched starts.

## Speed Tests and Profiling

No change at run time. `SizeHintMultiKernelCall.run` picks a sub-kernel per input shape (`_select_kernel_by_shape`, cached in memory) and overwrites `picked_kernel` on every call, so the saved pick never decides anything for these kernels. Skipping `load_cache` only removes the crash. Startup with a warm cache: 54 s / 51 s, against 112 s cold and 89 s recompiling with the FX-graph cache off.
