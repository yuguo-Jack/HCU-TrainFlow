# [KDA] Fix prefill-graph track copies with a bf16 SSM pool

[Upstream PR](https://github.com/sgl-project/sglang/pull/43657) · state: open · merged: False

## Original PR description

## Motivation

With `--mamba-ssm-dtype bfloat16`, the KDA SSM pool is bf16. `_kda_track_ssm_kernel` (#41105) loads the pool dtype in its mode-1 branch and the fp32 chunk-boundary snapshot in its mode-2 branch, then stores the result. Triton rejects a variable whose type differs between the branches of a runtime `if`, so the kernel fails to compile on a bf16 pool. On GLM-5.3-Flash with breakable prefill CUDA graphs, which capture the KDA extend, this fails server startup during prefill graph capture.

## Modifications

- Cast the fp32 snapshot to the pool dtype inside the mode-2 branch, so both branches produce the pool dtype. An fp32 pool is unaffected: the cast is then a no-op.
- Add `test_kda_prefill_graph_track.py`. It runs `kda_track_ssm_state` on fp32 and bf16 pools with mode 0, 1 and 2 rows, and compares the pool exactly with a torch reference.

## Accuracy Tests

On an RTX PRO 6000 Blackwell (SM120) with Triton 3.8.0, the new test passes (2 tests). Without the kernel change, the bf16 case fails to compile.

A GLM-5.3-Flash FP8 TP4 server with `--mamba-ssm-dtype bfloat16` and `--cuda-graph-backend-prefill breakable` failed at startup without this change. With it, the server started and served.
