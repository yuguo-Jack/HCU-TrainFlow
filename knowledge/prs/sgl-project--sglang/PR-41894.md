# [Diffusion] FLUX 3 video VAE: fused QKV norm + RoPE, cached RoPE tables

[Upstream PR](https://github.com/sgl-project/sglang/pull/41894) · state: open · merged: False

## Original PR description

## Motivation

Every attention layer of the FLUX 3 video VAE prepares Q/K/V with eager ops: unbind the packed projection, apply two affine-free RMSNorms, then rebuild the 3-D RoPE tables and apply rotate-half. Encoding one 544x736 frame launches about 2200 kernels. On RTX 5090 that encode is launch-bound (17.7 ms of wall time for 9.3 ms of GPU work). Observation encoding runs on every FLUX 3 Action request, so the cost shows up on the one-step `sd` variants.

## Modifications

- **`flux3_video_qknorm_rope`** (`kernels/ops/diffusion/rope/flux3_video_qknorm_rope_triton.py`): one Triton launch reads packed BF16 QKV and writes RMSNorm + rotate-half Q/K plus a contiguous V. The RMSNorm follows ATen's vectorized reduction for head dim 64 and keeps the BF16 rounding boundary before the RoPE products.
- **`Natten3D`**: uses that kernel when QK norm, head dim 64, and batch 1 all apply. The first call is compared with eager under `BitExactFusionGate`. A mismatch or an error disables the kernel and stays on the eager path.
- **`RotaryPositionEmbedding3D`**: memoizes cos/sin per grid and time origin. The fused and eager paths share the tables.

## Accuracy

No accuracy change. The kernel is bit-exact against eager `nn.RMSNorm` (affine-free, `eps=1e-5`) plus rotate-half, not a lower-precision approximation.

- `test_flux3_video_qknorm_rope.py` checks `torch.equal` on several shapes, and checks that `Natten3D` matches its eager prep and reuses the RoPE cache.
- The VAE latent of a frame is bit-identical to main.
- Actions on 4 frames of the public Cosmos3-DROID episode 0 are identical to main for `base` and `sd-fp8r`.
- If the first call is not bit-exact, the gate keeps the eager outputs and does not use the kernel again.

## Speed

Setup: one RTX 5090, NATTEN VAE. `bench_flux3_action` is OpenPI WebSocket, 10 warmup + 50 requests, median `server_timing.infer_ms`.

Video VAE `encode_frame` (544x736):

| | main | This PR | Change |
|---|---:|---:|---:|
| Eager wall time | 17.7 ms | 12.2 ms | -31.1% |
| Kernel launches | 2220 | 840 | -62.2% |
| Kernel time | 9.3 ms | 7.5 ms | -19.4% |
| With the FLUX 3 Action CUDA graph PR | 9.5 ms | 7.6 ms | -20.0% |

End to end:

| Variant | main | This PR | Change |
|---|---:|---:|---:|
| base | 1139 ms | 1137 ms | -0.2% |
| sd | 181 ms | 174 ms | -3.9% |
| sd-fp8r | 159 ms | 155 ms | -2.5% |

The observation stage drops by about 5 ms per request (`sd`: 25.5 ms to 19.4 ms). On `base` the 50-step denoise hides that. On `sd` / `sd-fp8r` it is a few percent of the request.
