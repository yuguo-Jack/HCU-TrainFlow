# Warm up real serving paths before the first user request

[Upstream PR](https://github.com/sgl-project/sglang/pull/37541) · state: open · merged: False

## Original PR description

## Motivation

A server can report ready before it has compiled the kernels needed for ordinary sampled chats, larger prompt batches or images. The first matching user request then pays the compilation or device-load cost. The general warmup does not cover all of these request shapes.

This PR adds an opt-in startup warmup that exercises those serving paths before readiness. An author-observed GLM-5.3-Flash deployment spent about 75 seconds compiling FlashInfer sampling during its first sampled chat; that observation motivates the sampling phase, but no GPU receipt for this PR revision is attached.

## Modifications

`--warmups serving_coverage` sends and fully consumes requests through the tokenizer manager: concurrent cohorts, cold prompts crossing prefill-chunk boundaries, short and natural-text prompts, a completed cache seed followed by replay and concurrent prefix reuse, non-greedy sampling variants, concurrent decode waves at power-of-two sizes up to the running-request limit, and a generated image when a compatible processor is available. Natural text exercises speculative decoding shapes that random token IDs may not reach.

Token-ID requests respect the configured prompt/decode budget and vocabulary bounds. DP requests are routed to each rank in bounded windows; disaggregated requests receive distinct bootstrap rooms. Text and image inputs are not token-count-clamped. Phase failures are logged and later phases continue, so this is warmup coverage, not a readiness correctness gate. No scheduler, model-forward or kernel implementation changes.

The decode-batches phase reads `effective_max_running_requests_per_dp` from the schedulers' internal state and, on each DP rank, submits waves of concurrent requests at every power of two below that limit and at the limit itself (a limit of 12 gives waves of 1, 2, 4, 8 and 12). The replies arrive in completion order and do not identify their DP rank, so when ranks report different limits every rank uses the smallest; if none is reported, the configured `max_running_requests` applies. Requests ask for 16 to 256 prompt token IDs and 16 decode tokens with `ignore_eos`, and alternate greedy and sampled (temperature 1.0) within each wave. Like the other phases, both lengths are clamped to the prompt and decode budget, so a small context gets shorter prompts and fewer than 16 decode tokens. On a prefill disaggregation server the scheduler sets `max_new_tokens` to 1, so this phase exercises prefill batches there, not decode. The aim is to load batch-size-specialized kernels that run outside CUDA graphs (allocation, speculative verify, sampling) before serving, but the phase is best effort: it submits N concurrent requests, and the scheduler may still batch them differently, for example with mixed chunked prefill or `prefill_max_requests=1`, where early requests can finish before the last ones are admitted. The phase does not verify the decode batch sizes that actually ran. It is not capped at the 8-request cohort size; a rank runs at most ceil(log2(limit)) + 1 waves and fewer than 3 x limit requests.

The warmup only runs where it can exercise the path it targets:

- Non-generative (embedding or reward) models skip the warmup entirely, since its requests decode multiple tokens.
- Under prefill or decode disaggregation the cached-prefix phase is skipped with a log line, because warmup requests use the fake bootstrap host, which disables prefix cache insertion, so the seed could never be reused.
- A sampling variant the server rejects at admission (for example `min_p` and penalties under UNO speculative decoding) is logged and left out of the concurrent sampling cohort; the supported variants still run. Among the sequential per-variant requests, only a rejection of every variant fails the phase; a failure in the concurrent cohort still fails the phase.
- With more than one DP window, a failure on one rank no longer stops later windows from being warmed; the first failure is reported after all windows have run.
- With `--enable-encoder-swa-bounded-replay`, which makes the tokenizer manager reject every multimodal request, the image phase is skipped with a log line instead of sending a request that fails with a traceback; a unit test enables the flag and checks that no image request is sent (it fails without the change).

## Accuracy Tests

`test/registered/unit/entrypoints/test_serving_coverage_warmup.py` covers phase ordering, concurrent cohorts, prompt lengths, sampling, image eligibility, DP routing, budgets and failures, plus regressions for non-generative models, the disaggregated cached-prefix skip, a rejected sampling variant, all variants rejected, a failing DP rank followed by later windows, and the decode-batches phase (wave sizes, alternating temperatures and request bounds, equal limits filling every rank, the smallest limit for every rank when ranks report different limits in either reply order or when some report none, the `max_running_requests` fallback when no limit is reported, unique disaggregation bootstrap rooms, and no decode-batches requests for non-generative models). The tests use a fake tokenizer manager that records requests, so no server, model or GPU is involved; they check the requests the warmup sends, not how a scheduler batches them.

The file was run unmodified with pytest on macOS, in a CPU-only environment (Python 3.12, torch 2.14.1 CPU build) with the source tree on `PYTHONPATH`: `python -m pytest -q test/registered/unit/entrypoints/test_serving_coverage_warmup.py`. Results:

- This branch: 47 passed, 7 subtests passed.
- This branch merged with current main: 47 passed, 7 subtests passed.
- The same test file with the first revision of this PR's `warmup.py`: 17 failed, 34 passed, 3 subtests passed. All 14 test methods added since that revision fail there (the disaggregation and reply-order tests in both of their subtests), as does the phase-order test, which now expects the decode-batches phase.

The full unit suite, GPU warmup coverage and startup time have not been run or measured.
