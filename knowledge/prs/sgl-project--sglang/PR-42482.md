# [HiCache] Preserve ownership of pending file write reservations

[Upstream PR](https://github.com/sgl-project/sglang/pull/42482) · state: open · merged: False

## Original PR description

## Motivation

Concurrent writes of the same key can invalidate each other's `LRUFileEvictor` reservation. A controlled interleaving on main `1e490772e5` leaves **192 bytes of committed `.bin` payloads under a 128-byte configured cap**, while the evictor accounts for only the competing write.

The pending-write set has one entry per key, but `reserve` currently admits a second writer for that key. Its `commit` clears the first writer's protection; its `abort` instead removes the first writer's reservation entirely. Another write can then evict/admit against that incomplete accounting. The original writer subsequently publishes an untracked file.

## Modifications

- Under the existing reservation lock, reject a key that already has a pending writer before eviction or accounting changes.
- Document this refusal in the existing `reserve` contract. `HiCacheFile.set` already returns `False` for refused reservations and only calls `abort` if its own reservation succeeded, so no caller changes or waiting locks are required.
- Extend the existing registered LRU unit suite with real temporary files, CPU tensors, and an event-controlled writer paused immediately before `os.replace`. Cover both a duplicate commit and an injected duplicate publication failure on the old implementation, then verify capacity, tensor contents, temporary-file cleanup, and successful eviction/retry after the original completes.

This fixes reservation ownership within one evictor instance. It does not introduce cross-process locking, bound temporary-file filesystem allocation, or change the unbounded-storage path. A concurrent duplicate backup can return `False`; it can retry after the original finishes rather than claiming completion while that write is still pending.
