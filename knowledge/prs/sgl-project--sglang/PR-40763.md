# Enabling DWDP Support for Intel XPU

[Upstream PR](https://github.com/sgl-project/sglang/pull/40763) · state: open · merged: False

## Original PR description

Enables DWDP (MoE distributed weight data parallelism, issue #22084, merged as #29778) on Intel XPU. The CUDA VMM calls move behind a `VmmBackend` seam and a Level Zero implementation is added; DWDP on CUDA goes through the same seam.

**Verified on Intel XPU only**, 8x Arc Pro B60: gpt-oss-20b GSM8K 0.910 at dwdp=2 against 0.890 for the TP control arm, and Qwen3-30B-A3B decodes at dwdp=4. Every CUDA registration here is unverified -- a CUDA maintainer should start with `test/registered/unit/test_dwdp_weight_prefetch.py`, which pins peer prefetch byte-exactly without a model.

Worth a reviewer's attention:

- `_validate_local_shard_rows` is a new hard failure when shared-experts fusion is on; `handle_dwdp` does not yet force `disable_shared_experts_fusion=True`.
- `align_up` / `align_down` left `cuda_vmm_utils`' surface for `vmm_common`.
- Two Level Zero loaders coexist in the process, torch's and ours; `SGLANG_XPU_ZE_LOADER_SO_PATH` overrides the search path where the default loader predates 1.28.
- The new CUDA model-test lanes add roughly 2400s to `extra-b`. Say the word and they ship `disabled=`.

Follow-ups, not in this PR: round-robin expert slicing from #22084; generalizing `SimpleEvalGSM8KXPUMixin` (8 files use it); `test_utils.py` raises `IndexError` if `CUDA_VISIBLE_DEVICES` is set to the empty string.

L0 Spec has documented a limitation, which may be applicable in this scenario where allocation from L0 is used later in SYCL kernels.

"The application must only use the memory allocation on the context for which it was created."
Ref: https://oneapi-src.github.io/level-zero-spec/level-zero/latest/core/api/apis/virtual_mem.html#zevirtualmemreserve

A small op returning sycl::get_native<sycl::backend::ext_oneapi_level_zero>(queue.get_context()) would give torch's own Level Zero context instead of a private one. It may help avoid the DEVICE_LOST error and remapping workaround.

``` c++
// src/sycl/ze_native.cpp
#include <sycl/sycl.hpp>
#include <sycl/ext/oneapi/backend/level_zero.hpp>
#include "Utils.h"

int64_t ze_context_handle() {
  auto ctx = dpcppGetCurrentQueue().get_context();
  return reinterpret_cast<int64_t>(
      sycl::get_native<sycl::backend::ext_oneapi_level_zero>(ctx));
}
// register as torch.ops.sgl_kernel.ze_context_handle
```
