# [AMD] Run DSA prefill under breakable CUDA graphs on HIP

[Upstream PR](https://github.com/sgl-project/sglang/pull/43642) · state: open · merged: False

## Original PR description

## Motivation

`--cuda-graph-backend-prefill breakable` cannot run DSA prefill on ROCm. With the flag set, GLM-5 / DeepSeek-V3.2 on MI355X hit `AssertionError: Internal error: in-graph DSA prefill must go through the graph DSA split-op dispatch`, for two reasons:

- `is_graph_dsa_split_op_surface` is CUDA-only, so the indexer never takes the split op inside the graph.
- `pcg_dsa_indexer_prefill_split` asserts CUDA, imports the Triton `act_quant`, and cannot receive the `(x, x_s[, x_bf16])` tuple that the ROCm fused RMSNorm + quant produces.

Separately, on non-CUDA platforms the runner sends every extend with a prefix to eager whenever MHA companion layers exist, but DSA sets `use_mha=False` inside piecewise and breakable graphs, so the companion never runs there.

## Modifications

- Allow the split-op surface on HIP.
- In the split op, pick the tilelang `act_quant` on HIP (same rule as `forward_cuda`), take the quantized tuple as separate tensors, and use the AITER fused FP8 Q/K writer when it is active, sliced to the unpadded token count.
- Size `topk_result` from the activation's row count so tuple inputs work.
- Skip the prefix veto when the attention backend is DSA.
- Add a test: a breakable prefill with a nonzero prefix on a non-CUDA platform with DSA must not be vetoed. It fails without the runner change.

CUDA paths are unchanged. ROCm only reaches this with the breakable flag; the default prefill graph backend there is unchanged.

## Accuracy Tests

GLM-5.3 MXFP4, first 4 layers with real weights, TP1 on MI355X, breakable graph vs eager in the same process. The graph replays for prefixes 0 and 4096 (`can_run_graph:prefix:True`, the split op and fused writer run inside the graph). Logits are finite, and the max abs difference from eager is 0.43-0.64, against 0.03-0.61 between two eager runs. Argmax matches in all 6 graph cases. A seventh case (3000 new tokens) is above the capture size and runs eager on both sides; its argmax still differs, which is eager run-to-run noise.

GSM8K, GLM-5.3 MXFP4 TP4/EP4 on the 0.5.21 image: 0.9735 with this change and the flag, 0.9750 stock (SE ~0.004).

## Speed Tests and Profiling

Same 4-layer model, `model_runner.forward` for one extend, median ms:

| new tokens | prefix 0: eager / graph | prefix 32768: eager / graph |
|---|---|---|
| 16 | 5.82 / 2.46 | 7.22 / 3.42 |
| 128 | 5.75 / 3.16 | 7.09 / 4.13 |
| 512 | 5.92 / 4.18 | 7.02 / 5.28 |
| 1024 | 6.04 / 6.28 | 8.43 / 8.12 |
| 2048 | 7.34 / 10.66 | 13.97 / 13.65 |

Small extends gain the most. A 2048-token extend with no prefix is 45% slower in the graph, so a lower `--cuda-graph-max-bs-prefill` (for example 1024) may suit workloads with long cold prompts.

GLM-5.3 MXFP4 TP4/EP4 agentic replay (CONC 10, 1 h, 0.5.21 image), with this change and `--cuda-graph-backend-prefill breakable --cuda-graph-max-bs-prefill 2048` vs stock: P50 interactivity 112.26 vs 109.49 (+2.5%, 95% CI [+0.2, +5.0]), TTFT P50 441 vs 459 ms. An earlier version of this change measured +8.75% P50 at TP8/EP1 CONC 4 on 0.5.20.
