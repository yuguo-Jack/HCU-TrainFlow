# MLA decode-side KV broadcast: one rank pulls over the network, relays over NVLink

[Upstream PR](https://github.com/sgl-project/sglang/pull/37950) · state: open · merged: False

## Original PR description

## Motivation

In a Prefill CP → Decode TP attention configuration for MLA models, during KV transfer, prefill CP rank 0 sends the full KV cache to each decode TP rank. For Prefill CP8 → Decode TP8, this means 8 redundant inter-node transfers of the same KV data.

<img width="500" alt="kv_broadcast_before@2x" src="https://github.com/user-attachments/assets/b958aada-47e1-4fd7-b385-270a57e4c0b6" />

For short-context workloads this overhead is acceptable, but as context length grows, *e.g.* beyond 50K, **KV transfer latency dominates TTFT**, making this redundancy increasingly costly.

This PR minimizes inter-node transfer by having prefill CP0 send the KV cache once to decode TP0 over the network, then letting TP0 broadcast it to TP1–TP7 via the faster intra-node network (NVLink). This trades a single inter-node transfer and one broadcast operation for eight redundant inter-node transfers.

<img width="500" alt="kv_broadcast_after@2x" src="https://github.com/user-attachments/assets/d873137b-fe7e-47cf-b619-07da2797b789" />

This feature is controlled by `SGLANG_ENABLE_DISAGG_MLA_DECODE_KV_BROADCAST` (off by default).

## Modifications

1. **KV manager.** `DecodePreallocQueue` resolves the relay decision and passes it down as `kv_args.enable_decode_kv_broadcast`. Only attn TP rank 0 pulls; the other receivers omit `kv_indices` and set a `kv_relayed_by_peer` frame, so the sender skips their KV/state but still delivers aux data and status.

2. **Broadcast in the scheduler phase, after popping the transfer.** `DecodeTransferQueue.pop_transferred()` relays the indices of reqs polling `Success`. `Success` comes out of a MIN all-reduce, so every rank broadcasts the same set.

3. **Relay through a staging buffer** (`decode_kv_broadcast.py`, new). `DecodeKVBroadcaster` gathers the scattered rows into a packed staging buffer, broadcasts it, and scatters it back on the peers. `SGLANG_DISAGG_MLA_DECODE_KV_BROADCAST_CHUNK_MIB` (default 32 MiB) bounds the buffer.

## Test environment
- GPU: MI300X
- Model: GLM-5.2-FP8
- PD disaggregation with Prefill CP8 and Decode TP8
- Before -> `SGLANG_ENABLE_DISAGG_MLA_DECODE_KV_BROADCAST = 0`
- After -> `SGLANG_ENABLE_DISAGG_MLA_DECODE_KV_BROADCAST = 1`

## Performance Tests
Benchmark tests were done using sglang bench_serving with generated-shared-prefix multi-turn workloads.
- gsp-system-prompt-len 80000
- gsp-question-len 1300
- gsp-output-len 300
- gsp-num-turns 15

This is to reflect typical agentic workloads with the following characteristics.
- large prefix length
- small tool-call results
- smaller generations

@Fridge003
Thanks a lot for your comment. This PR provides an optimization exclusively for MLA models, where the KV cache is fully replicated across all GPUs in the same attention TP group.

I believe similar, interesting optimization opportunities exist for GQA models as well. Recent GQA models, including some Qwen 3.5 variants, have very few KV heads (e.g., 2), bringing them closer to MLA than conventional MHA in terms of KV cache replication at larger TP sizes. 

For example, a Qwen 3.5 model with 2 KV heads running with attention TP8 replicates each KV head across 4 GPUs, resulting in 4 copies of the full-attention KV cache across 8 GPUs. During KV transfer, this can lead to redundant transfers over the relatively slow inter-node network, similar to the MLA case addressed in this PR.

Extending this optimization to GQA, however, would require broader changes to account for KV-head ownership and replication across subsets of TP ranks. This goes beyond the scope of the current PR, but I’d like to explore incorporating it in future work.

> Have you considered `SGLANG_DISAGGREGATION_ALL_CP_RANKS_TRANSFER` as a solution?

@ShangmingCai 

Thank you for your comment.

Yes, I tested it, and it improves performance, but with a caveat. 
**We still transfer the same KV cache to each decode TP rank over the inter-node network - eight copies in our configuration.**

Reducing the total transfer volume matters for several reasons:
- InfiniBand (IB) network shared with other applications in the cluster
- Bursty nature of KV transfer with large volumes (e.g. ~50 GB aggregate inter-node traffic for 100000 tokens with GLM-5.2-FP8, including eight copies)
- Fan-in situation of `ALL_CP_RANKS_TRANSFER` which can create receiver-side contention or incast congestion
- Possibility of exacerbating the congestion by multiple sglang instances doing the same thing, whose effect is not yet verified and hard to test in a production cluster

This PR reduces inter-node traffic by transferring one copy of the KV cache and then broadcasting it within the decode node.

Here are the measurements on GLM-5.2-FP8 serving on MI300X, with Prefill CP8 and Decode TP8.
- SGLang v0.5.18 with the Mooncake transfer backend
- Number of cached tokens : 99968
- Number of uncached tokens: < 50

| Condition | TTFT (sec) | Inter-node KV transfer time (sec) |
| --- | --- | --- |
| `ALL_CP_RANKS_TRANSFER=0` (baseline) | 1.5 | 1.3 |
| `ALL_CP_RANKS_TRANSFER=1` | 0.984 | 0.819 |
| This PR | 0.435 | 0.160 |

We see a ~34% decrease of TTFT when using `ALL_CP_RANKS_TRANSFER=1`. However, KV transfer still accounts for most of TTFT, as in the baseline.

I should note that we have four NDR NICs (400 Gbit/s each) per node. Despite having four NICs, enabling all CP ranks reduces the measured transfer time from 1.3 s to 0.819 s, a 1.59x speedup in this setup.

Eight NDR NICs per node may improve transfer parallelism, but they do not eliminate the replicated inter-node traffic.

With this PR applied, you see a ~71% decrease of TTFT relative to the baseline, and a ~56% reduction relative to `ALL_CP_RANKS_TRANSFER=1`.

The inter-node transfer time reported for this PR excludes decode-side broadcast, so this column alone does not represent the full cost of KV transfer. Nevertheless, the end-to-end benchmarks in the PR description show substantially lower TTFT, lower TPOT, and higher throughput.

So, I believe that this PR is a good opt-in feature for further optimization of KV transfer.
