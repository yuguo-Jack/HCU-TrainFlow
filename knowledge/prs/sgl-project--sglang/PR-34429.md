# [Kernel] Add SM120 per-tensor FP8 GEMM for small-M (#33632)

[Upstream PR](https://github.com/sgl-project/sglang/pull/34429) · state: open · merged: False

## Original PR description

<!-- Thank you for your contribution! Please follow these guidelines to enhance your pull request. If anything is unclear, submit your PR and reach out to maintainers for assistance. Join our Slack community at https://slack.sglang.io to discuss further. -->

## Motivation
Fixes [#33632](https://github.com/sgl-project/sglang/issues/33632).

On SM120, ModelOpt per-tensor FP8 linears currently go through `flashinfer.bmm_fp8(..., backend="cublas")`. For the attention-group shapes from `nvidia/Qwen3.6-27B-NVFP4` at TP=1 and small M (MTP, `M < 64`), a dedicated in-tree CUTLASS dense GEMM is faster than cuBLAS on a useful subset of those shapes. This PR adds that kernel and routes only the profitable shapes to it.
<!-- Describe the purpose and goals of this pull request. -->

## Modifications
- Add an SM120 JIT per-tensor FP8 scaled GEMM (`fp8_pertensor_scaled_mm`) under `sglang.kernels` with two Pingpong tiles (`64x128x64` for `M < 24`, `64x64x128` otherwise) and a fused dual-scale epilogue. 
- Route profitable shapes through the new kernel in `apply_fp8_linear_bmm_flashinfer` / `flashinfer_bmm_fp8`; otherwise keep
cuBLAS.
- `is_profitable`:
    - wide N (`N > 8192`): `M >= 16`
    - narrow N: `M >= 24` (do not route `M < 24`; GEMM-only CUPTI sweep shows cuBLAS ahead by ~9–11% there)
- Add correctness test, production dispatch test, and a registered benchmark using `bench_gpu_time_with_cupti` with CUDA graph on and cold L2, matching the issue measurement requirement.

## SM120 re-run on CUDA 13.0: two one-line blockers, then the routing rule does not match the measurements

Tested the branch on a second SM120 box, independently of the author's environment.

Hardware / stack: one RTX PRO 5000 72GB Blackwell (SM120), sglang 0.5.20, torch 2.13.0+cu130, nvcc 13.0 (V13.0.88), driver 580.126.09, flashinfer 0.6.18. The serving process was stopped so the CUPTI sweep owned the GPU.

### Blocker 1 — the new module cannot be imported

`python/sglang/kernels/ops/gemm/fp8_pertensor_gemm.py:7`:

```python
from sglang.kernel_api_logging import debug_kernel_api
```

On 0.5.20 that module lives at `sglang/kernels/kernel_api_logging.py`, and `python/sglang/kernel_api_logging.py` does not exist at this PR's base commit (`6220f45d8e9a`), on `main`, or in 0.5.20. Verified directly:

```text
>>> import sglang.kernel_api_logging
ModuleNotFoundError: No module named 'sglang.kernel_api_logging'
```

The consequence is worse than a broken import in a test file, because of how the dispatch hook is written in `fp8_utils.py`:

```python
@lru_cache(maxsize=1)
def _fp8_pertensor_backend():
    if not is_sm120_supported():
        return None
    if envs.SGLANG_DISABLE_SM120_FP8_PERTENSOR_GEMM.get():
        return None
    from sglang.kernels.ops.gemm import fp8_pertensor_gemm as pertensor
    return pertensor if pertensor.is_available() else None
```

`is_available()` has a `try/except` around the *JIT build*, but the module-level import above is not guarded, so on an SM120 box `flashinfer_bmm_fp8` raises `ModuleNotFoundError` on the first per-tensor FP8 linear instead of falling back to cuBLAS. The escape hatch `SGLANG_DISABLE_SM120_FP8_PERTENSOR_GEMM=1` is the only way out, and it is not a default. Suggest either fixing the import path or wrapping that `from ... import` in the same `try`.

### Blocker 2 — the kernel does not compile

```text
fp8_pertensor/fp8_pertensor_scaled_mm_sm120.cuh(165): error: identifier "alloc_workspace_tensor" is undefined
```

`alloc_workspace_tensor` is declared in `sgl_kernel/ffi.h`, inside `namespace host::ffi`:

```cpp
inline Tensor alloc_workspace_tensor(size_t required_bytes, DLDevice device) { ... }
```

The `.cuh` includes `sgl_kernel/tensor.h`, `utils.h`, `runtime.cuh`, `utils.cuh` and does `using namespace host;` — `host::ffi` is not brought in, so the unqualified call does not resolve. Same declaration site at the PR's base and on `main`, so this is not a 0.5.20 drift. Fix used for the measurements below: qualify the call as `host::ffi::alloc_workspace_tensor(...)`.

### After those two lines: it builds and runs

- JIT flags resolved by the tree itself are `-gencode=arch=compute_120f,code=sm_120f` (`get_jit_cuda_arch()` gives `ArchInfo(major=12, minor=0, suffix='f')`), and `CUTLASS_ARCH_MMA_SM120_SUPPORTED` is satisfied — so no `sm_120a` is needed for this kernel, which is worth recording because it is a recurring SM120 question.
- Cold JIT compile: 32.8 s; warm cache load: 0.01 s. Below the 300 s scheduler watchdog, so first-start JIT is not a risk here.
- Correctness against `bmm_fp8(..., backend="cublas")` over all 21 swept shapes: agrees within bf16 rounding, worst `max_rel = 0.0086`, but not bit-exact — 6 of 21 agree exactly, and they are precisely `M=48` and `M=60` at all three N; the other 15 differ by 1-2 bf16 ulp. Worth stating in the test docstring if the tolerance is intentional, since a bit-exact assertion would fail on most of the grid.

Three things follow.

1. Under the shipped `m <= 64`, 3 shapes here are clear regressions (up to 1.56x) and they are exactly the narrow-N small-M points the description says to exclude.
2. Under the *documented* rule the `N=16384, M=48/60` pair is still routed and still loses (1.14x). That rule has no upper-M bound; on the author's box those same two points measured 0.99 and 1.00. So the M~48 boundary is not stable between boxes and probably should not be routed at all.
3. Absolute cuBLAS times differ by roughly 2x between the two environments (e.g. `N=5120, M=24`: 54.91 µs reported vs 28.64 µs here). The profit table is therefore tracking the NVJET/cuBLAS build in the container, not just the kernel. Any fixed `is_profitable` heuristic will silently go stale when the base image CUDA/cuBLAS changes — a runtime autotune over the 3-4 candidate tiles, or a version-keyed table, would age better than either rule.

### Scope of this data

GEMM-only, as in the issue methodology. No end-to-end number from us: this box serves a BF16 checkpoint, so no per-tensor FP8 linear is on its path at all, and an E2E delta would have to come from an NVFP4 deployment.

Aware that @b8zhong already concluded on E2E grounds that the PR is not needed, so this is not an argument to merge. The parts worth keeping regardless of that decision are the two blockers above — anyone checking out this branch on CUDA 13 will hit them on the first request — and point 3, since the same routing idea may reappear for other SM120 shapes.

> Hardware / stack: one RTX PRO 5000 72GB Blackwell (SM120), sglang 0.5.20, torch 2.13.0+cu130, nvcc 13.0 (V13.0.88), driver 580.126.09, flashinfer 0.6.18. The serving process was stopped so the CUPTI sweep owned the GPU.
> 
> ### Blocker 1 — the new module cannot be imported
> `python/sglang/kernels/ops/gemm/fp8_pertensor_gemm.py:7`:
> 
> ```python
> from sglang.kernel_api_logging import debug_kernel_api
> ```
> 
> On 0.5.20 that module lives at `sglang/kernels/kernel_api_logging.py`, and `python/sglang/kernel_api_logging.py` does not exist at this PR's base commit (`6220f45d8e9a`), on `main`, or in 0.5.20. Verified directly:
> 
> ```
> >>> import sglang.kernel_api_logging
> ModuleNotFoundError: No module named 'sglang.kernel_api_logging'
> ```
> 
> The consequence is worse than a broken import in a test file, because of how the dispatch hook is written in `fp8_utils.py`:
> 
> ```python
> @lru_cache(maxsize=1)
> def _fp8_pertensor_backend():
>     if not is_sm120_supported():
>         return None
>     if envs.SGLANG_DISABLE_SM120_FP8_PERTENSOR_GEMM.get():
>         return None
>     from sglang.kernels.ops.gemm import fp8_pertensor_gemm as pertensor
>     return pertensor if pertensor.is_available() else None
> ```
> 
> `is_available()` has a `try/except` around the _JIT build_, but the module-level import above is not guarded, so on an SM120 box `flashinfer_bmm_fp8` raises `ModuleNotFoundError` on the first per-tensor FP8 linear instead of falling back to cuBLAS. The escape hatch `SGLANG_DISABLE_SM120_FP8_PERTENSOR_GEMM=1` is the only way out, and it is not a default. Suggest either fixing the import path or wrapping that `from ... import` in the same `try`.
> 
> ### Blocker 2 — the kernel does not compile
> ```
> fp8_pertensor/fp8_pertensor_scaled_mm_sm120.cuh(165): error: identifier "alloc_workspace_tensor" is undefined
> ```
> 
> `alloc_workspace_tensor` is declared in `sgl_kernel/ffi.h`, inside `namespace host::ffi`:
> 
> ```c++
> inline Tensor alloc_workspace_tensor(size_t required_bytes, DLDevice device) { ... }
> ```
> 
> The `.cuh` includes `sgl_kernel/tensor.h`, `utils.h`, `runtime.cuh`, `utils.cuh` and does `using namespace host;` — `host::ffi` is not brought in, so the unqualified call does not resolve. Same declaration site at the PR's base and on `main`, so this is not a 0.5.20 drift. Fix used for the measurements below: qualify the call as `host::ffi::alloc_workspace_tensor(...)`.
> 
> ### After those two lines: it builds and runs
> * JIT flags resolved by the tree itself are `-gencode=arch=compute_120f,code=sm_120f` (`get_jit_cuda_arch()` gives `ArchInfo(major=12, minor=0, suffix='f')`), and `CUTLASS_ARCH_MMA_SM120_SUPPORTED` is satisfied — so no `sm_120a` is needed for this kernel, which is worth recording because it is a recurring SM120 question.
> * Cold JIT compile: 32.8 s; warm cache load: 0.01 s. Below the 300 s scheduler watchdog, so first-start JIT is not a risk here.
> * Correctness against `bmm_fp8(..., backend="cublas")` over all 21 swept shapes: agrees within bf16 rounding, worst `max_rel = 0.0086`, but not bit-exact — 6 of 21 agree exactly, and they are precisely `M=48` and `M=60` at all three N; the other 15 differ by 1-2 bf16 ulp. Worth stating in the test docstring if the tolerance is intentional, since a bit-exact assertion would fail on most of the grid.
>
