# [MoE] Enable deferred finalize for NVFP4 on the routed TRT-LLM runner

[Upstream PR](https://github.com/sgl-project/sglang/pull/42654) · state: open · merged: False

## Original PR description

## Motivation

This PR covers the NVFP4 case of #39299.

- Deferred finalize means the MoE kernel skips its last step, the weighted sum over the selected experts. A later fused kernel then does that step together with the shared-expert add.
- Today NVFP4 experts on the `flashinfer_trtllm_routed` runner can never use it. The hybrid FP8 + NVFP4 DeepSeek V4 / V4.1 checkpoints always use this runner, because the routing options built into the kernel (`RoutingMethodType`) cannot describe their routing.
- The routed FlashInfer op already accepts `do_finalize=False`, and the MXFP4 method uses it (#38798). The NVFP4 routed path was never connected to it. Three places block it:

1. `FusedMoE.supports_deferred_finalize` requires `is_flashinfer_trtllm()`, which is false for the routed backend.
2. `DeepseekV2MoE` only defers when the top-k output format is `BYPASSED`. The routed runner receives regular top-k ids and weights.
3. `fused_experts_none_to_flashinfer_trtllm_fp4` only sets `defer_finalize` when `use_routed_topk` is false, and the routed call always passes `do_finalize=True`.

wenchen76 is working in the same direction in wenchen76/sglang#1.

## Modifications

- `FusedMoE`: new flag `supports_routed_deferred_finalize`. It is true for `ModelOptNvFp4FusedMoEMethod` on `flashinfer_trtllm_routed`, when there is no A2A backend and the routed scaling factor is already folded into the top-k weights. `supports_deferred_finalize` is not changed, so the CuTe DSL layer-boundary fusion, Kimi and Qwen paths behave as before.
- `DeepseekV2MoE`: picks the flag by top-k format. `BYPASSED` uses the old flag. Regular top-k uses the new one.
- `fused_experts_none_to_flashinfer_trtllm_fp4`: the routed call now passes `do_finalize=not defer_finalize` and wraps the result with `_make_deferred_finalize_output`, the same way the MXFP4 method does.
- Workaround: the deferred routed call still passes a `[T, hidden]` output buffer, although the kernel does not write to it in deferred mode. FlashInfer's autotune cache key includes the output shape. With `output=None` the lookup misses the tuned entry, the expert GEMMs run with a fallback tactic, and each call is 9 to 14% slower. I filed this as flashinfer-ai/flashinfer#6077 with a standalone repro. The buffer can be removed once that is fixed.
- `SGLANG_ENABLE_MOE_DEFERRED_FINALIZE=0` turns the new behavior off.
- `test_deepseek_v4_amd_tp4.py`: the MoE stub gets the new attribute.

Since #42245, the V4 block asks the MoE for deferred output whenever the fused mHC kernel can be used. With this PR the NVFP4 routed runner can return it. So NVFP4 now uses the single fused kernel that does the finalize, the shared-expert add and the all-reduce, and no other condition has to change.

## Accuracy Tests

**Kernel level.** I compute the same MoE output in two ways and compare them:

- the routed op with the finalize inside the op, followed by the shared add
- the routed op with deferred finalize, followed by `moe_finalize_fuse_shared`

The weights are synthetic NVFP4 weights with the V4.1-Flash expert shapes (hidden 5120, intermediate 2304, 384 experts, top-6). There are 28 cases: T in {1, 2, 8, 33, 96, 192, 384}, with all experts local and with an EP slice of 96 local experts, and with per-tensor and per-token activation scales.

## Speed Tests and Profiling

4x B300, FlashInfer 0.7.0.post1. The baseline is the same code with `SGLANG_ENABLE_MOE_DEFERRED_FINALIZE=0`.

```bash
CUDA_VISIBLE_DEVICES=4,5,6,7 SGLANG_SPEC_TP_SYNC=rng SGLANG_RAGGED_VERIFY_MODE=static \
SGLANG_SIMULATE_ACC_LEN=5.4 SGLANG_SIMULATE_ACC_METHOD=match-expected \
sglang serve --trust-remote-code --model-path nvidia/DeepSeek-V4.1-Flash-NVFP4 \
  --tp 4 --ep-size 4 --host 0.0.0.0 --port 31500 \
  --reasoning-parser auto --tool-call-parser auto --mem-fraction-static 0.8 \
  --speculative-algorithm DSPARK --speculative-dspark-block-size 5 --cuda-graph-max-bs-decode 64
```

```bash
aiperf profile -m nvidia/DeepSeek-V4.1-Flash-NVFP4 --url http://127.0.0.1:31500 \
  --endpoint-type chat --streaming --use-server-token-count \
  --concurrency 8 --request-count 48 --warmup-request-count 8 \
  --isl 8192 --isl-stddev 0 --osl 1024 --osl-stddev 0 \
  --extra-inputs '{"ignore_eos": true, "min_tokens": 1024, "temperature": 1.0, "top_p": 0.95}'
```

ITL p50 in ms. This is the branch after merging main `abed685de1`, which includes #42245. Each column is one server launch. Two launches of the same build differ by up to 2.2% per cell.

| concurrency | deferred finalize off | this PR | delta |
|---|---|---|---|
| 1 | 1.005 | 1.004 | -0.1% |
| 4 | 1.529 | 1.455 | -4.8% |
| 8 | 2.042 | 1.945 | -4.7% |

GSM8K on the merged branch is 0.984 (500 questions, same command as above).

Before #42245, the same change was within noise (-0.3% to -1.1%, with 4 launches of main and 2 of the PR). Deferring alone only removes the finalize step, which is about 1.5% of GPU time (#39299). The gain now comes from the fused kernel also doing the all-reduce.

## Follow-ups

1. MXFP8 experts on the routed runner (`Fp8MoEMethod` with `use_mxfp8`, the RL rollout path from #28676). It needs the same change in `fused_experts_none_to_flashinfer_trtllm_fp8`, limited to `use_mxfp8`. The kernel-level comparison passes at V4.1-Flash shapes (worst max abs diff / max abs ref is 4.9e-3). It still needs an end-to-end run on an MXFP8 checkpoint before I open it.
2. The MXFP4 method should pass the output buffer on every deferred call. Today it only does so for 96 < T <= 384, so smaller batches hit the same autotune miss. On V4.1-Flash MXFP4 this moved ITL p50 from 1.020 to 1.002 ms at concurrency 1, with no change at concurrency 2 to 8.
3. Remove both dummy buffers once flashinfer-ai/flashinfer#6077 is fixed.
