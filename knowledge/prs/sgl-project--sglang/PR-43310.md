# [Fix] Accept pack-quantized (WNA16) lm_head in should_apply_lm_head_quant_method so DFLASH does not crash

[Upstream PR](https://github.com/sgl-project/sglang/pull/43310) · state: open · merged: False

## Original PR description

## Motivation

With a compressed-tensors `pack-quantized` int4 checkpoint whose `lm_head` is quantized (a `config_groups` entry with `targets: [lm_head]`), the target model serves normally but DFLASH exits on the first request:

```
File ".../srt/models/dflash.py", line 124, in candidate_topk
RuntimeError: DFlash candidate top-k requires a dense FP16/BF16/FP32 target lm_head or a supported lm_head.quant_method.
```

Startup already hints at it: `DFLASH draft greedy head kept eager (reason=unsupported quantized lm_head).`

`should_apply_lm_head_quant_method` (`layers/logits_processor.py`) decides whether the target logits path and the DFLASH candidate selector call `quant_method.apply`. It required `hasattr(lm_head, "weight")`, but the method owns its parameter layout: the WNA16 (Marlin) linear method stores its codes in `weight_packed`, GGUF in `qweight`. So the helper returned `False` for a head whose `apply` works, `dflash_worker_v2.py` kept the draft head eager, and `models/dflash.py::candidate_topk` raised.

Reproduced on v0.5.21 and current `main` with Qwen3.8-27B W4A16 (int4 group-128 head, `lm_head` added to the config group and removed from `ignore`) + `incoai/Qwen3.8-27B-DFlash2` on one RTX 4090.

## Modifications

- `should_apply_lm_head_quant_method`: gate on the method only (`None`, no callable `apply`, or a known unquantized method → `False`). The `weight` reads stay where they are needed, in the ModelOpt stale-method layout checks, which return `False` for a head without `weight`.
- `LogitsProcessor._compute_lm_head`: require `weight` before taking the helper's branch, so heads without `weight` (GGUF, packed codes) keep the existing fp32-aware `apply` path. The target logits path is unchanged for every head.
- Only the live definition is touched. The file also carries a dead copy of this helper and of `_has_lm_head_runtime_attrs` near the top, pasted back by the Qwen3.8 rebase (#35758) above the originals from #27906 / #34158; Python keeps the later definitions. Removing it is a behavior-free deletion I can send as a separate PR if wanted.

Behavior change, intended: a head without `weight` paired with a non-ModelOpt quantized method is now admitted by the DFLASH selector (previously refused, then crashed). The compressed-tensors WNA16 case has been run end to end; GGUF / GPTQ / AWQ heads take the same path but were not exercised. DSPARK is unaffected (its worker requires `lm_head.weight` before this helper is reached).

Tests:
- `test/registered/unit/spec/test_dflash_logits.py`: `test_selector_projects_a_pack_quantized_target_lm_head` — a `weight_packed` head through `DFlash2DraftModel.compute_candidates`. Fails on `main` with the `RuntimeError` above.
- `test/registered/unit/layers/quantization/test_compressed_tensors_lm_head.py`: `TestShouldApplyLmHeadQuantMethod` — a packed head is applied, an `UnquantizedLinearMethod` is still refused, and a stale ModelOpt method on a packed head is refused.

## Accuracy Tests

- After the fix the selector is captured: `DFLASH selector decode folded into the draft cuda graph (sampling_enabled=True)`.
- Local serving with the int4 head: 40-task tool-call test, 0 failures; DFlash2 acceptance length 4.06 vs 4.11 with the bf16 head (within noise); 128K positions compared position-by-position against the bf16 head: top-1 agreement 98.25% — the head quantization itself, not this change.
- The two CPU test files above and `test_modelopt_loader.py`'s lm_head guard cases pass locally; no public checkpoint with a pack-quantized head is available for an e2e CI case.

No hot-path change beyond the fix itself; not separately benchmarked.
