# [PD] Send prefill KV chunks as soon as the batch result copy completes

[Upstream PR](https://github.com/sgl-project/sglang/pull/43811) · state: open · merged: False

## Original PR description

# [PD] Send prefill KV chunks as soon as the batch result copy completes

## Motivation

With the overlap scheduler, a prefill batch's KV transfer is only started when its result is processed in `process_batch_result_disagg_prefill`, which runs after the *next* batch has been launched. In addition, `send_kv_chunk` runs on the schedule stream behind the WAR barrier of the next forward. As a result the KV transfer of batch N starts roughly one full batch duration after batch N finished on the GPU.

On a prefill-saturated 1P1D setup we measured a median delay of 0.08-4.4 s between "batch GPU done" and "KV transfer enqueued". This delay scales with batch duration and adds directly to TTFT.

## Modifications

Adds an opt-in path, `SGLANG_DISAGG_PREFILL_EARLY_SEND_KV=1` (default off), in which a dedicated worker thread (`EarlyKVChunkSender`) sends a batch's KV chunks as soon as the batch's `copy_done` event completes. The worker uses its own CUDA stream, so it does not wait for the next forward.

- **Per-request ownership** (`KVSendOwner`: `NONE` / `EARLY` / `SCHEDULER`, stored on `Req`).
  - Ownership is fixed when the request's first batch result is submitted. An eligible request is owned by the worker for its whole lifetime: all middle chunks, the last chunk, and appending the first token.
  - All other requests stay on the existing scheduler path, and the scheduler skips sends for `EARLY` requests.
  - Each request's KV is therefore always sent by exactly one sender, in order.
  - A request is eligible when it has a bootstrap room, has finished bootstrapping, has no output yet, and does not need logprobs, a sampling mask, or grammar. Those features need the scheduler-side result processing before the last chunk.
- **Delayed sampling** (grammar / `SGLANG_ENABLE_DELAY_SAMPLE`): `copy_done` is only recorded after `launch_batch_sample_if_needed`, so submission happens after that call in that case.
- **KV lifetime and aborts.**
  - Paths that release an `EARLY` request's KV hold `EarlyKVChunkSender.lock` via `early_kv_send_lock(req)`, so the worker never reads freed KV pages. These paths are `_retire_aborted_prefill_result`, `handle_inflight_transfer_failure`, and `process_pending_chunked_abort`.
  - The worker skips requests that were aborted or whose KV was already released.
  - When an `EARLY` request is aborted after the worker may have started sending, the scheduler aborts its sender (`KVPoll.Failed`) and lets it drain through the inflight queue instead of retiring it directly.
  - A failed middle-chunk send aborts the sender and skips the request's remaining chunks.
- **`handle_inflight_transfer_failure`** now keeps an existing `FINISH_ABORT` reason instead of always overwriting it with `FINISH_LENGTH(0)`. Without this, a client abort that surfaces as a transfer failure is reported as a normal length finish. **Behavior change:** this also applies with the flag off.
- **Lifecycle:** the worker is stopped in `teardown_disaggregation` (PD role switch). `optimistic_release_and_requeue` resets ownership.
- **Support matrix.** When enabled with an unsupported configuration, the flag is ignored with a warning and the scheduler path is used.
  - Requires: CUDA, the overlap scheduler, and the Mooncake backend.
  - Not supported with: staging buffer, KV checksum, speculative decoding, the `prefill_complete` decode allocation policy, unified memory, or models that transfer extra state (`state_types`, e.g. Mamba / SWA / DSA).
- **Cached-prefix early send** (`maybe_send_cached_prefix_chunk`) is skipped for `EARLY` requests.
- **Docs:** the new variable is added to the Mooncake prefill configuration table in `pd_disaggregation.mdx`.
- **Tests:**
  - New unit tests in `test/registered/unit/disaggregation/test_prefill_early_send.py`: support matrix, ownership, submit, worker send / abort / failure handling.
  - New e2e test `test/registered/disaggregation/test_disaggregation_early_send_kv.py`: GSM8K accuracy, greedy consistency between sequential and concurrent requests, and mixed logprob / regex requests. The prefill server runs with `--enable-deterministic-inference` so the consistency check is not affected by batch-dependent numerics (without it, concurrent vs sequential first tokens also differ with the flag OFF).
  - Existing test fakes (`test_prefill_abort_result_cleanup.py`, `test_auxiliary_output.py`) get the new `kv_send_owner` field.

## Accuracy Tests

1P1D, TP4 each, Mooncake RDMA, same server code with the flag OFF vs ON.

GSM8K, `few_shot_gsm8k`, 500 questions, 5-shot:

| | Accuracy | Invalid |
|---|---|---|
| OFF | 0.898 | 0.000 |
| ON | 0.908 | 0.000 |

Output consistency, from an earlier prototype of this change (same copy-done trigger):

- **Greedy, sequential (30 prompts):** 30/30 identical outputs between ON and OFF.
- **Concurrent (200 prompts):** ON vs OFF differs in about 33% of outputs. This matches the OFF-vs-OFF control (69/200 differ) and the ON-vs-ON control (70/200 differ), so the differences come from batch-dependent numerics, not from the change.
- **Regex and logprob requests (which stay on the scheduler path):** regex 20/20 full match and logprobs 20/20 present in both modes.

## Speed Tests and Profiling

**Setup.**
- 1P1D, TP4 each (H20), Mooncake RDMA, `--page-size 16`, radix cache on, chunked prefill off.
- Workload: `bench_serving --dataset-name generated-shared-prefix`, 200 prompts, input 1024 / output 100. "Prefix" is the shared system-prompt fraction of the input.
- Each cell is the mean of 2 runs with identical seeds in both modes, and the cache is flushed before every run.
- All 24 runs completed 200/200 requests with no errors. With ON, every request was sent by the early sender.
