# [AMD] Resolving bug in per batch size graph capture due to multiple capture runs per batch size

[Upstream PR](https://github.com/sgl-project/sglang/pull/39840) · state: closed · merged: True

## Original PR description

## Motivation

Per-batch-size CUDA-graph capture traces (`SGLANG_GRAPH_BATCH_CAPTURE`) assume
exactly **one** capture per batch size. That assumption was broken on **16 Aug
2026** by #31324 ([AMD][GLM5] dense k-only fast path), which made DSA models
capture **two** decode graphs per batch size (`dense` + `sparse`). #38993 later
generalized this to `AttentionGraphVariants`, but the trace bookkeeping was
never updated.

The capture loop walks `bs × lora variant × attention variant` and each
combination drives its own profiler cycle, while `on_trace_ready` indexed a flat
list of batch sizes. With DSA the cursor advances twice per batch size, so it:

1. **mislabels every trace** — the `dense` and `sparse` traces for bs=64 are
   written as `bs_64` and `bs_56`; and
2. **crashes the server** once the list runs out, halfway through capture:

```
File ".../runner/decode_cuda_graph_runner.py", line 786, in on_trace_ready
    bs = self._profile_bs_list[self._profile_bs_idx]
IndexError: list index out of range
```

Repro: GLM-5.2-FP8 (`GlmMoeDsaForCausalLM`), TP=8, MI300X,
`--enable-profile-cuda-graph` + `SGLANG_GRAPH_BATCH_CAPTURE=1`. The server dies
during `init_cuda_graphs` and never becomes ready. `UnoDecodeCudaGraphRunner`
hits the same bug via `record_nolora_graph` (two LoRA variants), independent of
ROCm.

## Modifications

Replace the positional cursor with the identity of the capture being recorded:

- `_profile_bs_list` / `_profile_bs_idx` → `_profile_trace_tag`, set by
  `_capture_one_stream` before each capture and read by `on_trace_ready`.
  No indexing, so the profiling path can no longer raise.
- New `_set_profile_trace_tag(bs, stream_idx, variant_label, attention_variant)`
  appends only the parts that vary, so **single-variant models keep the existing
  `bs_<n>` filenames byte-for-byte**. DSA models gain a suffix:

```
DecodeCudaGraphRunner_bs_64_dense_rank0.json.gz
DecodeCudaGraphRunner_bs_64_sparse_rank0.json.gz
```

The tag is set in the shared loop rather than in `capture_one_shape`, because
five subclasses override that method (`FrozenKVMTP` discards the variant args
outright) while all of them inherit the loop.

## Tests

Unit (`test/registered/unit/model_executor/runner/test_decode_cuda_graph_runner.py`,
CPU): dual dense/sparse naming, `bs_<n>` back-compat, tag composition, and a
regression case asserting more flushes than batch sizes no longer raises.

| Model | Before | After |
| --- | --- | --- |
| GLM-5.2-FP8 (DSA) | crash at bs 7 of 12 | 192 traces (12 bs × dense/sparse × 8 ranks) |
| GLM-5.2-FP8 + MTP | crash | 736 traces; target split dense/sparse, both EAGLE draft runners unchanged |
| DeepSeek-R1-0528 | 160 traces | 160 traces, **filenames unchanged** |
| Qwen3-VL-30B-A3B-FP8 | 96 traces | 96 traces, **filenames unchanged** |

The MTP run confirms scope: only the DSA target runner gains suffixes, while
`EAGLEDraftCudaGraphRunner` / `EAGLEDraftExtendCudaGraphRunner` keep `bs_<n>`.

- haishuok0525 · comment · 2026-09-22T09:46:35Z · [source](https://github.com/sgl-project/sglang/pull/39840#issuecomment-5774388756)

Closing #39093 in favor of this one — same root cause and same fix strategy,
and your matrix is wider than mine. The MTP run in particular confirms
something I never verified, that the suffix stays scoped to the DSA target
runner while both EAGLE draft runners keep `bs_<n>`.

Five things #39093 covered that I do not see here, ranked. The last two are
minor, and #3 is defensive rather than a live defect.

**1. The downstream effect of the rename is not stated**

The table correctly says filenames are unchanged for DeepSeek-R1-0528 and
Qwen3-VL. For DSA models they do change, and any consumer that keys traces on
`bs_<n>` will collapse the new pair rather than see two graphs.

I measured this on a trace consumer that groups capture shards by a `bs_\d+`
match: after the fix it saw 8 files on disk and returned 4 shards, silently
dropping every sparse variant, because `bs_11_dense` and `bs_11_sparse` both
reduce to `bs_11`. That is the correct consequence of the fix and not a defect
in it, but one line in the description would tell tooling owners to go look.

**2. No test asserts uniqueness across the lora × attention product**

`test_dual_attention_variants_name_both_traces` varies attention only, and
`test_appends_attention_lora_and_stream` asserts a single composed string.
Nothing asserts that the full product is collision-free, which is exactly the
multiplication that broke here — and per your own motivation section,
`UnoDecodeCudaGraphRunner` reaches the bug through the lora axis alone.

#39093 has [`test_variant_graphs_get_one_trace_each`](https://github.com/haishuok0525/sglang/blob/a8e9b77c7c3e359d43bfccc51786f891b964eb11/test/registered/unit/model_executor/runner/test_decode_cuda_graph_runner.py#L235-L269),
which drives 2 bs × {lora, nolora} × {dense, sparse} = 8 flushes and asserts
both the ordered export list and `len(set(exported)) == len(exported)`. Worth
lifting across.

**3. `on_trace_ready` has no guard for an unset tag**

```python
tag = self._profile_trace_tag
trace_file = os.path.join(trace_dir, f"{runner_name}_{tag}_rank{rank}.json.gz")
```

With `tag` still `None` this writes a file literally named
`..._None_rank0.json.gz`, and `test_primes_empty_trace_tag` establishes that
`None` is the initial state.

To be explicit: I do not believe this is reachable today. `capture_one` issues
exactly three `step()` calls per capture against `wait=2, active=1`, so the tag
is always set before the flush, and as you note all five subclasses override
`capture_one_shape` while inheriting the loop. It matters for the case your
comment already anticipates from the other direction — a future subclass that
overrides `_capture_one_stream` instead would never set the tag, and every
trace would land silently under the same `_None_` name instead of failing
loudly. #39093 [returns without exporting](https://github.com/haishuok0525/sglang/blob/a8e9b77c7c3e359d43bfccc51786f891b964eb11/python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py#L775-L779)
in that case, with a test [here](https://github.com/haishuok0525/sglang/blob/a8e9b77c7c3e359d43bfccc51786f891b964eb11/test/registered/unit/model_executor/runner/test_decode_cuda_graph_runner.py#L299-L306).
Two lines, take it or leave it.

**4. The mislabeling claim can be made checkable**

The motivation says the dense and sparse traces for bs=64 are written as
`bs_64` and `bs_56`. That is right, but as written a reader has to take it on
faith, since filenames are the very thing under suspicion.

It can be shown without trusting them. Each trace carries a `ProfilerStep#k`
marker, and given the three `step()` calls per capture, flush *j* lands at
`ProfilerStep#(3j+2)` — which fixes which flush wrote which file independently
of its name. The `cuda_runtime` launch count then fingerprints the graph, since
sparse launches more kernels than dense. The resulting pre-fix ledger is in
#39092: on `amd/GLM-5.2-MXFP4` TP8, `bs_7` held bs=11 sparse, `bs_5` held bs=7
dense, `bs_3` held bs=7 sparse, and only `bs_11` was right, by luck.

One caveat if you reuse the method: counting `kernel` events does not work
here, because capture records launches into the graph instead of executing
them, so a capture trace holds only a couple of kernel events regardless of
graph size. The launch count is what discriminates.

**5. Nit: `stream{idx}` breaks the separator convention**

Parts are joined on `_`, but the stream part is `f"stream{stream_idx}"`,
producing `bs_8_sparse_nolora_stream1`. Since the leading segment is `bs_8`,
the same stem mixes `key_value` and `keyvalue` forms, and a parser needs
`bs_(\d+)` alongside `stream(\d+)`. `stream_{idx}` keeps the two symmetric.

Also worth having this PR close #39092, so the repro and the ledger above stay
attached to the fix.
