# [AMD] Keep MiniMax decode-score tile at 128 tokens off gfx950

[Upstream PR](https://github.com/sgl-project/sglang/pull/42772) · state: closed · merged: True

## Original PR description

## What

On ROCm, `_decode_score_kernel` now uses the 512-token `BLOCK_SIZE_N` tile for batches of 4 or fewer only on gfx950. Other archs use 128, which is what every ROCm arch already uses for larger batches.

## Why

The ROCm heuristic was tuned on gfx950, which has 160 KB of LDS. A 512-token bf16 K tile needs 128 KB, and gfx942 (MI300X/MI325X) has only 64 KB, so `flash_decode_with_topk_idx` fails to load there at batch ≤ 4:

```
triton.runtime.errors.OutOfResources: out of resource: shared memory, Required: 131072, Hardware limit: 65536
```

`amd/test_minimax_indexer_cp.py` (added in #41488) is the first MI300 test to reach this path. It has failed in `stage-b-test-1-gpu-small-amd` part 7 since it landed, e.g. https://github.com/sgl-project/sglang/actions/runs/37395620023/job/112050816832

## Test plan

- [x] Compiled `_decode_score_kernel` for a gfx942 target with Triton 3.8.0, using the test's batch=1, 8K-context bf16 inputs. LDS was 131072 bytes with the 512 tile (same as CI) and 32768 bytes with the 128 tile.
- [x] On MI355X (gfx950), `test_minimax_indexer_cp.py` passes unchanged (512 tile). It also passes with the arch check forced to non-gfx950 (128 tile), so the selected top-k IDs match across both tile sizes.
- [x] On MI300 (gfx942) in `stage-b-test-1-gpu-small-amd` part 7: [passed](https://github.com/sgl-project/sglang/actions/runs/37481699749/job/112346794455) (`Ran 1 test in 20.070s / OK`), so the indexer-CP kernels are now exercised on gfx942.
- [x] Control: the same partition on a branch without this change still fails with `OutOfResources: shared memory, Required: 131072, Hardware limit: 65536` ([run](https://github.com/sgl-project/sglang/actions/runs/37478665740/job/112347556006)) — the 131072 figure matches the gfx942 compile measured above.
