# [HiCache] Keep unified memory off the direct page_first_direct copies

[Upstream PR](https://github.com/sgl-project/sglang/pull/43333) · state: open · merged: False

## Original PR description

## Motivation

With `--enable-unified-memory`, each layer's device KV rows are strided: a unified-pool entry holds every layer's K and V for one token (#40326). The direct `page_first_direct` copies (`transfer_kv_all_layer_direct_lf_pf` / `transfer_kv_per_layer_direct_pf_lf`) still copy a page as one contiguous `page_size * row_stride` span. On Inkling that is 8x the page's real size, so:

- a backup writes past its host page into the neighbouring host pages;
- a load-back rewrites the row's other layers and the next rows on the device;
- when the overrun crosses an allocation end, the copy fails with `cudaMemcpyBatchAsync failed ... error=invalid argument` and the scheduler dies.

`page_first_direct` forces the direct io backend, and storage backends such as Mooncake resolve to it, so this is reachable from ordinary HiCache flags.

## Modifications

- `resolve_unified_memory_layout_io`: with unified memory, a `page_first_direct` layout resolves to `page_first` with the kernel io backend, whose JIT kernels address rows by stride. It runs after the storage-layout step, which can itself pick `page_first_direct`.
- `MHATokenToKVPoolHost` / `MLATokenToKVPoolHost`: the direct `page_first_direct` copies call `_require_packed_device_rows`, so strided rows fail loudly instead of corrupting memory.

## Tests

- `test_server_args.py::TestHiCacheArgs`: two cases, unified memory with `page_first_direct`, and with Mooncake + direct + `layer_first`.
- `test_hicache_strided_device_rows.py`: the direct `page_first_direct` backup and load on strided rows raise `NotImplementedError`. Host pools now call `destroy()` on cleanup, so a later pool in the same process does not hit `cudaHostRegister` error 712 on a reused address.

On H200, all three new assertions fail on main and pass with this PR. Inkling with unified memory, a 0.35 GB pool and `--hicache-mem-layout page_first_direct` crashes on main within seconds; with this PR it resolves to `page_first`/kernel and serves. The surrounding host-pool unit suites match main; `test_kvcacheio_asymmetric.py::test_asymmetric_mha_kernel_page_first_roundtrip` fails on main too.

Not shown: a wrong-output reproduction. The HiCache KL test with unified memory did not load anything back from host, so it cannot see the corruption.
