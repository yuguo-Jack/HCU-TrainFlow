# [DSA] Q8KV8 FP8 Sparse Prefill on GLM-5.3-Flash with BF16 KV Cache

[Upstream PR](https://github.com/sgl-project/sglang/pull/41790) · state: open · merged: False

## Original PR description

> Part of the SM90 Q8KV8 FP8 sparse-attention roadmap #25746.
> Throughout, **q8** = `--dsa-prefill-backend flashmla_sparse_q8` and **base** = `--dsa-prefill-backend tilelang`. Both configurations run the same bf16 KV cache and the same `--dsa-decode-backend tilelang`; only the prefill backend differs.

**One-line summary:** `flashmla_sparse_q8` now serves GLM-5.3-Flash on Hopper (SM90): per DSA layer the sparse prefill is 1.53-1.72x faster than tilelang, which on a prefill-dominated workload is +11.16% to +12.44% total token throughput at 3.5k-120k input and 8.37% to 10.97% lower single-request TTFT at 8k-120k at TP4/EP4 (+5.82% to +12.06% and 6.06% to 11.28% lower at TP8/EP8), with no gsm8k few-shot count (1319 questions each) where q8 scores lower than base.

## TL;DR

- **Before this PR, GLM-5.3-Flash could not use `flashmla_sparse_q8` at all.** Launching with it on H200 failed at backend construction (fp8-KV-only guard); relaxing that alone still fails on the KPool tail guard, the 2051-wide KPool top-k (kernel needs a multiple of 128), and zero-length RoPE in the Triton q-prep kernel.
- **Per DSA layer (single H200, real backend code paths; 11 of this model's 45 layers are DSA):** at TP4's 16 local heads, q8 sparse prefill is **1.53-1.72x faster** than tilelang across 8k-131k context (1.53-1.72x at TP8's 8 local heads; 1.79-1.98x at 64 local heads).
- **End to end** on a **prefill-dominated** workload (random dataset, 3.5k-120k input, **1-token outputs**), with the same server flags at both sizes: at **TP4/EP4**, total token throughput is **+11.16% to +12.44%** and single-request **TTFT is 8.37% to 10.97% lower at 8k-120k**; at **TP8/EP8** the same rows give **+5.82% to +12.06%** and **6.06% to 11.28% lower**. At 3.5k the TTFT difference is small and varies between runs, so it is not claimed.
- **Accuracy:** gsm8k at four few-shot counts (5-120 shots, all 1319 questions at every count): **no shot count where q8 scores lower than base** after subtracting the server-to-server offset measured at 5 shots, where both run the identical dense path. LongBench-v2 (336 questions, every request on the sparse prefill path): **−0.003**, against a single-run noise of about ±0.027.
- **Cost:** this PR adds one int32 buffer per attention backend (one per GPU here) to pad the 2051-wide top-k to the 2176 the kernel needs, at most `--chunked-prefill-size` rows (71.3 MB at 8192); no new flags or environment variables.

## Motivation

On Hopper, GLM-5.3-Flash (`Glm5NextForConditionalGeneration`) runs with a bf16 KV cache (`--kv-cache-dtype auto` resolves to bfloat16 on SM90), so its DSA prefill computes in BF16. On SM90, FP8 doubles the peak tensor-core throughput of BF16 and halves the bytes moved per operand; that is why this series added an FP8 sparse prefill, `--dsa-prefill-backend flashmla_sparse_q8`, for DeepSeek-V3.2 (#30514) and extended it to GLM-5.2 (#31888).

That backend could not run on GLM-5.3-Flash at all, because three properties of the model each block it:

1. **bf16 KV cache.** The q8 backend accepted only an `fp8_e4m3` KV cache, but this model is served from a bf16 cache on Hopper.
2. **NoPE MLA** (`qk_rope_head_dim=0`). The fused fp8 q-prep Triton kernel builds `tl.arange(0, ROPE)` and fails to compile at ROPE=0, as does the KV concat-cast kernel behind the opt-in `SGLANG_ENABLE_DSA_Q8KV8_KV_CAT_FUSION`.
3. **KPool top-k** (`index_kpool=4`). The KPool indexer appends up to `index_kpool - 1` tail tokens to every top-k row, so rows are `index_topk + index_kpool - 1 = 2051` wide, but the kernel walks top-k in pairs of 64-wide blocks and needs `topk % 128 == 0`, and the KPool tail guard did not admit q8.

## Modifications

None of the three needs a change to the SM90 attention kernel: `d_qk=512` is already one of its two supported widths (512 and 576), `d_v=512` and `h_kv=1` match, and padding the local heads to 64 (from 16 at TP4 or 8 at TP8) already satisfies its contract. The fixes sit around the kernel:

1. **bf16 KV cache** (`dsa_backend.py`, `dequant_k_cache.py`). The q8 kernel only needs q and KV in fp8 at call time, so the validator now accepts a bf16 pool, q8 extend batches take the RAGGED top-k transform whatever the pool dtype, and prefix rows are gathered by slot and cast to fp8 per call (`gather_cast_kv_fp8_pad_paged`: on NoPE rows one vectorized Triton kernel that also zeroes the pad band, otherwise the existing MLA gather; bit-identical to the non-prefix cast). This mirrors an existing path in the opposite direction: `flashmla_sparse` already dequantizes an fp8 cache to bf16 on a prefix hit (`dequantize_k_cache_paged`).
2. **NoPE MLA** (`cache_ops.py`, `dequant_k_cache.py`). Both Triton kernels skip the rope segment behind a static `if ROPE > 0:`, so output with ROPE>0 is byte-identical to before.
3. **KPool top-k** (`dsa_backend.py`, `dsa_backend_kpool.py`). Top-k is padded with -1 to 2176 (output-invariant), and the KPool tail guard admits q8 prefill over a bf16 pool; an fp8 pool keeps the guard, since gathering packed fp8 rows through KPool tail columns is untested.

Also included:

- **Guards** (`dsa_backend.py`). At launch, q8 prefill rejects `--enable-mixed-chunk`, HiSparse, an fp8 dtype whose pool is not stored packed, and (not supported yet) an fp8 pool on a NoPE model; these previously failed mid-forward. At run time, a non-RAGGED q8 batch that carries top-k indices raises instead of silently running the bf16 kernel.
- **Memory.** The q8 kernel needs a top-k width that is a multiple of 128, so the 2051-wide KPool top-k is padded with -1 to 2176 (fix 3 above). tilelang pads the same rows to 2112 (a multiple of its 64-column blocks) with a new tensor on every DSA layer call; this PR instead keeps the padded ids in one `(rows, 2176)` int32 buffer per attention backend that runs q8 prefill (one per GPU here), at most `--chunked-prefill-size` rows (71.3 MB at 8192). It is filled with -1 once and reused across DSA layers and forward passes; each call copies in only the 2051 real columns.
- **Docs** (separate commits). The GLM-5.3-Flash docs page (`GLM-5.3-Flash.mdx` and its config) gains a Hopper `BF16 + Q8 sparse prefill` option, listed after `BF16 + TileLang` so the Hopper default does not change, with its own empty benchmark entries so it does not show the BF16 + TileLang numbers; `attention_backend.mdx` drops the stale `requires --kv-cache-dtype fp8_e4m3`.
- **Unchanged.** The SM90 kernel and its wrapper; fp8-KV behaviour for DeepSeek-V3.2 / GLM-5.2 apart from the launch-time checks above; DeepSeek-V4; every other DSA prefill and decode backend.

## Usage

```bash
sglang serve --model-path zai-org/GLM-5.3-Flash --tp-size 8 --ep-size 8 \
  --moe-a2a-backend megamoe --moe-runner-backend deep_gemm --kv-cache-dtype bfloat16 \
  --dsa-prefill-backend flashmla_sparse_q8 --dsa-decode-backend tilelang \
  --mem-fraction-static 0.70 --disable-overlap-schedule --disable-shared-experts-fusion \
  --max-running-requests 32 --max-prefill-tokens 8192 --chunked-prefill-size 8192 \
  --context-length 131072 --cuda-graph-backend-prefill disabled
```

Opt-in only: without `--dsa-prefill-backend flashmla_sparse_q8`, no default and no other backend changes.

**Hardware scope.** SM90 only (the kernel is SM90-gated).

**Short prefills.** Batches whose longest KV length is at most `SGLANG_DSA_PREFILL_DENSE_ATTN_KV_LEN_THRESHOLD` (2048 by default) can take the dense MHA path instead, where both backends are identical. The decision is made per batch and has further conditions (for example, the batch's total KV length must fit the MHA chunk capacity), so under concurrency short requests can still reach the sparse path.

### Performance Benchmark

**Per DSA layer** (single H200; times only the sparse prefill attention call, through the real backend code paths with synthetic indices and values; `do_bench` median per call; q8 time includes top-k padding, fp8 q-prep and the bf16 prefix gather-cast; speedup = tilelang / q8, higher = this PR better; ms columns at 16 heads; the 32k and 64k kv_len rows are omitted and fall in between):

| s_q | kv_len | tilelang (ms) | q8 (ms) | speedup, 16 heads (TP4) | 8 heads (TP8) | 64 heads |
|---|---|---|---|---|---|---|
| 4096 | 8192 | 3.07 | 1.79 | 1.72x | 1.72x | 1.98x |
| 4096 | 131072 | 3.06 | 2.00 | 1.53x | 1.53x | 1.79x |
| 8192 | 8192 | 5.99 | 3.48 | 1.72x | 1.72x | 1.98x |
| 8192 | 131072 | 6.01 | 3.87 | 1.55x | 1.55x | 1.79x |

All columns come from one run on this PR's final code with the software listed in Setup. q8 pads the local heads to 64 and tilelang pads them to 16, so 8 and 16 heads cost the same in each backend; at 64 heads (all of the model's heads on one GPU) tilelang's work grows while q8's does not. Only 11 of the model's 45 layers are DSA (the other 34 are KDA linear-attention layers, which this PR does not touch), so the end-to-end gain is much smaller than the per-layer gain.

**End to end** (improvement of q8 over tilelang, + = this PR better; for TTFT, the percentage by which it is lower):

| input | throughput, TP4/EP4 | throughput, TP8/EP8 | TTFT, TP4/EP4 | TTFT, TP8/EP8 |
|---|---|---|---|---|
| 3.5k | +11.70% | +5.82% | +0.86% | +1.91% |
| 8k | +12.07% | +8.33% | +9.31% | +6.06% |
| 16k | +12.18% | +10.88% | +9.60% | +7.63% |
| 32k | +12.44% | +11.21% | +10.17% | +8.94% |
| 64k | +11.16% | +12.06% | +10.97% | +11.28% |
| 120k | +11.24% | +11.65% | +8.37% | +10.92% |

Spread across repetitions (1σ): throughput ±0.07-1.18 percentage points at TP4/EP4, and at TP8/EP8 ±0.32-1.42 from 8k up and ±3.15 at 3.5k; TTFT at 8k-120k ±0.23-0.49 at TP4/EP4 up to 64k, ±3.40 at 120k, and ±0.26-2.78 at TP8/EP8. Three entries (TP8/EP8 throughput at 3.5k, TP4/EP4 throughput at 32k and TTFT at 120k) include one repetition well away from the other three; with the median of the repetitions instead of the mean, the ranges are +11.12% to +12.21% (TP4/EP4) and +4.60% to +12.03% (TP8/EP8) for throughput, and 9.34% to 10.90% and 6.64% to 11.10% lower TTFT at 8k-120k. At 3.5k the TTFT difference is small (+0.86% ±3.27 at TP4/EP4, +1.91% ±1.47 at TP8/EP8) and varies between runs, so the TTFT claim covers 8k-120k only.

| 8k | 31,531 → 35,355 | 39,888 → 43,172 | 274.5 → 248.5 | 226 → 211 |

Divided by GPU count, TP4/EP4's q8 throughput is 1.60-1.68x TP8/EP8's, while TP8/EP8's q8 single-request TTFT is 15-20% lower from 8k up. Two TP4/EP4 servers were not run side by side on 8 GPUs, and TP8/EP8's larger KV capacity matters more with longer outputs.

**Where the time goes** (TP8/EP8, torch profiler, kernel time per GPU, averaged over the 8 GPUs and taking the median over server sessions, on a short separate test with 16,000-token requests rather than the benchmark rows): the sparse MLA prefill is 30.7% of tilelang's total kernel time, and this PR's kernel runs it 1.72x faster (256.1 → 149.0 ms), which alone cuts the total by 12.8%. The q8 preparation it adds (top-k padding, fp8 q-prep and the bf16 prefix gather-cast, 3.6 ms) costs 0.4%, the tensor concatenation that only the tilelang path runs (8.6 ms) saves 1.0%, and the fused MoE kernel (`deep_gemm` mega-MoE, which also carries the expert-parallel exchange) grows by 2.8% (190.1 → 213.5 ms). The total kernel time falls 10.6% (834.4 → 745.8 ms).

### Correctness and Accuracy Tests

The accuracy runs used TP4 without expert parallelism (flags under Setup) and an earlier revision of this PR's code. This PR's later changes (where the padded top-k ids are stored, message text, launch-time checks, a pad-buffer width check that is a no-op at this model's top-k width, and the vectorized gather with bit-identical output) do not touch the numerics.

**gsm8k** (all 1319 test questions at every shot count, few-shot examples from the train split, temperature 0, completion API, 2 repetitions; σ is the spread across them):

| K (shots) | ~context | base mean (sigma) | q8 mean (sigma) | raw delta | delta vs control |
|---|---|---|---|---|---|
| 5 | 0.8k | 0.9223 (0.0016) | 0.9166 (0.0011) | -0.0057 | *control* |
| 20 | 3.3k | 0.8537 (0.0096) | 0.8575 (0.0032) | +0.0038 | +0.0095 |
| 60 | 10k | 0.6740 (0.0161) | 0.6820 (0.0038) | +0.0080 | +0.0136 |
| 120 | 20k | 0.3082 (0.0059) | 0.3048 (0.0086) | -0.0034 | +0.0023 |

K=5 stays below the 2048-token dense threshold, where both configurations take the identical MHA path, so its −0.0057 is a pure server-to-server offset; the last column subtracts it. No shot count shows q8 scoring lower than base. The largest difference, q8 0.0136 higher at K=60, varies widely between the two repetitions (+0.0224 and +0.0049), so no gain is claimed. Both configurations score lower at longer contexts (0.92 at K=5, 0.31 at K=120), partly because of the completion API (on a separate base server with the same flags, K=120 scores 0.566 with the chat API and 0.324 with the completion API), so only the differences are claimed.

**Kernel engagement and numerics.** A profiler capture on the LongBench-v2 q8 server shows 132 q8 kernel calls. For gsm8k, a separate profiled run at 4k and 16k context on an earlier commit shows 44 in q8 and none in base; the sweep itself was not profiled. q and KV are cast to fp8_e4m3 with scalar-1.0 scales; the largest magnitude seen in real GLM-5.3-Flash prefills is 13.9 (q; KV at most 5.2), 32x below the ±448 limit, so no rescaling is needed.

**LongBench-v2**, where every prompt is longer than 2,048 tokens, so every request takes the sparse prefill path (thinking on, temperature 0.6, top-p 0.95, max-tokens 16,384, the 2,300-147,000-token subset selected with GLM-5.3-Flash's tokenizer, 336 questions, exact letter match; 2 repetitions):

| statistic | base | q8 | delta |
|---|---|---|---|
| score (max-tokens 16,384) | 0.601 (σ 0.004) | 0.598 (σ 0.025) | **−0.003** |
| answered by both, same repetition | 0.714 | 0.714 | **+0.000** |
| truncated (no answer emitted) | 15.0% | 14.7% | — |

No way of scoring shows a difference beyond about ±0.027, the binomial standard error of one run's score at 336 questions (−0.002 on the 255 questions answered in all four runs). About 15% of responses reach the 16,384-token cap while still reasoning and count as wrong in both configurations, so the claim is the difference, not the absolute score.

## Tests

- `test/registered/unit/layers/attention/test_dsa_q8kv8_bf16_prefill_routing.py` (CPU, 24 cases): which top-k layout each prefill backend, KV dtype and batch type gets; which configurations q8 accepts and which it rejects at launch; the top-k padding and its buffer reuse; and the KPool tail guard for bf16 and fp8 pools.
- `test/registered/kernels/ops/attention/test_q8kv8_dsa_nope_bf16_prefill.py` (1 GPU, 16 cases): the fp8 q-prep, KV cast and bf16 prefix gather kernels, with and without a rope part, match a plain torch cast byte for byte; and the q8 path on this model's shape (NoPE, bf16 pool, 2051-wide top-k) gives the same output with and without a cached prefix, is unaffected by the padding, and matches a torch reference.
- The existing `test_sparse_mla_q8kv8_prefill_sm90.py` and `test_q8kv8_sparse_prefill_backend.py` are unchanged and pass.

## Future work

- **FP8 KV cache.** Our next step is to connect q8 prefill to an fp8 KV cache for this model, so the prefill reads fp8 KV rows directly instead of casting bf16 rows (about half the bytes per row); we expect this to improve end-to-end performance further.
