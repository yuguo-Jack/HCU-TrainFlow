# [DeepSeek-V4.1] Use num_stages=1 for the hc_mix stats partial kernel

[Upstream PR](https://github.com/sgl-project/sglang/pull/43070) · state: closed · merged: True

## Original PR description

> (auto generated by Claude)

## Motivation

In low-latency DeepSeek-V4.1 decode, `_hc_mix_stats_partial_kernel` runs on the mHC stats side stream next to the MoE sublayer. On a 4x B300 bs1 profile (DSpark verify, M=6), it takes 14.3 us next to attention but 36.5 us next to the MoE GEMMs. The MoE post then waits on it for a median of 8.1 us per layer, about 6% of the forward.

The kernel used `num_stages=2` for every M except 64..384 on Blackwell. With 2 stages the tf32x3 loop is a long serial chain per warp, so it is slow on its own and any kernel sharing the SM stretches it further.

## Modifications

Use `num_stages=1` for the partial kernel on CUDA at every M, and drop `_num_stages_for`. AMD keeps 2.

## Accuracy

`num_stages` only changes the order in which memory is issued, not the arithmetic. Outputs of stages 1/2/3 are bitwise identical for M in 1..200 on both B300 and H200. A row computed alone also matches the same row inside a batch, so batch invariance is unchanged.

## Benchmark

Partial kernel time in us, K=20480, standalone:

| M | B300 s2 -> s1 | H200 s2 -> s1 |
|---|---|---|
| 1-8 | 13.6 -> 4.6 | 14.9 -> 5.6 |
| 18-48 | 25.9 -> 6.4 | 28.3 -> 7.6 |
| 52-60 | 49.9 -> 11.2 | 42-54 -> 13.8 |
| 512 | 224 -> 56 | 266 -> 56 |
| 4096 | 1206 -> 525 | 1383 -> 576 |

s3 and s4 are slower than s2 at every M. With an SM-occupying kernel running on another stream (M=1-8), s2 goes to 36 us on B300 and 39 us on H200, while s1 stays at 6-7.5 us.
