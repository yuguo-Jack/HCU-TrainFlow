# [AMD] Enable the gfx950 fused DSA indexer for block-FP8 wq_b/wk

[Upstream PR](https://github.com/sgl-project/sglang/pull/43643) · state: open · merged: False

## Original PR description

## Motivation

The gfx950 fused DSA indexer (#38583) only accepts bf16 `wq_b`, `wk` and `weights_proj`, and only plain bf16 hidden states. GLM-5.3 checkpoints ship block-FP8 `wq_b`/`wk` and run the gfx95 fused RMSNorm + quant, which hands the indexer an `(fp8, scale, bf16)` tuple, so GLM-5.3 never takes the fused path on MI355X.

## Modifications

- Accept `wq_b`/`wk` when both are bf16 or both are block-FP8 (`weights_proj` stays bf16).
- With FP8 weights, node 1 runs the layers' own GEMMs (the same ones the standard path runs) instead of the merged bf16 GEMV. Node 2 reads `k` and `weights` through their row stride, so the GEMM outputs are not copied into the workspace.
- Accept the `(fp8, scale, bf16)` hidden-state tuple: the bf16 GEMV takes `x[2]` and the FP8 GEMMs take the tuple.
- Add a test that checks the FP8 node 1 against the packed bf16 layout: `q_fp8`, head gate, index-K cache bytes and sorted top-k must be equal, rows 1/6/24/48. It fails on main. A CPU-side test covers the weight-dtype gate, including mixed bf16/FP8 pairs.

bf16 checkpoints keep the existing path.

## Accuracy Tests

Top-k overlap on GLM-5.3 MXFP4 layers 0 and 38, real indexer weights, decode rows 1/8/48 and verify rows 6/12/24/48, contexts 4k-200k:

| comparison | overlap |
|---|---|
| fused vs the stock chain with the same index-K format | 99.80% |
| stock vs stock, two runs | 99.82% |
| fused vs stock with the AITER fused writer | 94.75% |
| stock chain vs stock with the AITER fused writer | 94.75% |

On main, GLM-5.3 runs the AITER fused writer, which stores the index K without the Hadamard rotation that the non-fused chain and the fused kernels apply. That rotation accounts for the 5% gap, and the two stock paths already differ by the same amount. Against the chain with the same format, the fused kernels match to run-to-run level.

GSM8K (GLM-5.3 MXFP4 TP4/EP4, 0.5.21 image): 0.9735 with this change, 0.9750 stock (SE ~0.004).

## Speed Tests and Profiling

`Indexer.forward_cuda`, layer 0, real weights, CUDA graph replay, median time per layer vs stock (stock is 37-362 us across these cases):

| context | decode 1 row | decode 8 | decode 48 | verify 6 rows | verify 24 | verify 48 |
|---|---|---|---|---|---|---|
| 4k | -9% | +1% | +25% | -6% | +3% | +17% |
| 16k | -17% | -15% | +10% | -18% | -14% | +4% |
| 64k | -22% | -26% | -13% | -32% | -31% | -30% |
| 200k | -14% | -22% | -11% | -35% | -40% | -42% |

Long contexts gain 11-42%. Short contexts with many rows are slower, as with the bf16 path. Like #38583, enabling the fused path turns the AITER fused writer off for the layer, so batches above 48 rows and prefill run the stock chain without that writer.

GLM-5.3 MXFP4 TP4/EP4 agentic replay (CONC 10, 1 h, 0.5.21 image) vs stock: P50 interactivity 116.90 vs 109.49 (+6.8%, 95% CI [+3.9, +9.4]). Per-request decode speed at a fixed number of running requests goes from 221/181/157/141 to 229/187/168/155 tok/s at bs 1/2/3/4.

This merges cleanly with #34394, but #34394 merges `wk`/`weights_proj` on ROCm only while the AITER fused writer stays on, and this PR turns that writer off for GLM-5.3, so whichever lands second needs to reconcile the two.
