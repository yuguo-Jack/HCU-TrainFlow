# MoonEP style expert duplication for MoE load balancing

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/7450) · state: open · merged: False

## Original PR description

## Summary

This PR adds MoonEP virtual-expert load balancing over HybridEP (`--moe-virtual-expert-load-balance`).


Requirements and limitations (no FSDP, variable sequence lengths, capacity factor, expert bias, sinkhorn, partial MoE CUDA-graph scopes, or FC1 offload) are documented in the [MoE README](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/README.md#virtual-expert-load-balancing).

## Architecture

Each rank exposes 2·L runtime experts to HybridEP: its L native experts plus L virtual slots. HybridEP itself is unmodified. It receives the planner's runtime expert IDs and a fixed worst-case capacity ([load_balancer:L805-812](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_load_balancer.py#L805-L812)).

The new code is the kernels in `virtual_expert_triton.py`, the runtime in `virtual_expert_load_balancer.py`, and glue in the dispatcher, router, experts, TE, GTP, and config (see [Per-file changes](#per-file-changes)).

## Load balancer design

[`virtual_expert_load_balancer.py`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_load_balancer.py#L1-L965) is the runtime between the kernels and Megatron.

- **On the first forward**, it creates a shared symmetric-memory workspace used across every iteration:
  - one weight arena and one grad arena per expert layout, exposed as virtual-slot weights. All layers with the same layout share the same arenas, so the slots hold one layer's replicas at a time and each layer's forward and backward push refills them;
  - the slots are bound into TE's grouped GEMM alongside the natives but kept invisible to DDP, the optimizer, and checkpointing;
  - pointer tables that fix every weight and grad address from then on.
- **On each iteration**, it:
  - plans the layer's routes and pushes the selected weights into peer slots on side streams;
  - lets HybridEP and TE run over natives plus slots;
  - in the backward, pushes again, reduces the slot gradients back into the owners' native `main_grad` (or GTP's wgrad scratch), and hands the result to DDP or GTP;
  - has the compute stream wait on events at the points listed in the Integration table.
- **With GTP**, it reaches GTP through TE's `DistributedWeight` interface rather than by special-casing GTP inside TE.

### Structures

- [`VirtualExpertLoadBalancer`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_load_balancer.py#L587-L965): the mixin the dispatcher inherits, so the HybridEP transport itself stays untouched. Each slot is exposed as a weight whose gradient buffer is a view of the grad arena, which is what the kernels push into and reduce from.
- [`_VirtualExperts`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_load_balancer.py#L448-L561): one layer's view of that workspace. With expert GTP the native weights are gathered per forward and the wgrads reduce-scattered, so this class implements TE's `DistributedWeight` interface to obtain the gathered weights before the push and to delay the reduce-scatter until the slot gradients have arrived.
- [`VirtualExpertPlan`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_load_balancer.py#L71-L85): one forward's plan (runtime IDs and which experts to copy) and its in-flight state. It is kept until that forward's backward finishes, so interleaved microbatches and repeated MTP forwards each keep their own.
- [`_VirtualExpertHook`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_load_balancer.py#L567-L580): the identity autograd function that triggers the backward steps (see Integration). It passes its tensor through unchanged and runs a load-balancer method when the gradient reaches it.

## Kernel design

The three kernels are designed to run fast and to overlap with HybridEP and expert compute on side streams:

- **No host syncs**
  - The CPU never waits on the GPU, because all sizes are static and the plan stays on the device. This keeps launches asynchronous and makes the kernels CUDA-graph capturable.
- **Deterministic**
  - The planner breaks ties with a fixed rule and keeps route order within each expert, so every rank computes the same plan.
  - The grad reduce sums in a fixed order and rounds once, so results are bitwise reproducible.
- **Small, fixed grids**
  - All kernels use at most 32 SMs, leaving the rest for the overlapped attention and shared-expert compute.
- **Static shapes and pointers**
  - Pointer tables are built once and checked on every later pass.

All three kernels are single cooperative launches in `virtual_expert_triton.py`.

For the two transport kernels, regular NCCL isn't sufficient because the plan lives on the device:

- send/recv needs each peer and byte count on the host, which would force a device-to-host sync per layer;
- a dense all-to-all or reduce-scatter over every expert slot would avoid that sync but move up to EP× more data.

Instead, both kernels read `experts_to_copy` on the device and access the peers' symmetric memory directly.

### Planner ([`_plan_virtual_expert_routes_kernel`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L135-L425))

The planner runs the MoonEP algorithm on the router output. Its inputs are the router's top-k expert IDs `[T, topk]` (int32/int64), the token alignment from `get_align_size_for_quantization` (256, because MoonEP requires TE grouped tensors), and a [planner workspace](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L453-L498) holding the symmetric histogram window and scratch space.

It produces two tensors:

- the MoonEP-adjusted routing map: runtime expert IDs `[T, topk]` int16 that HybridEP dispatches to;
- `experts_to_copy` `[EP, L]` int32: the experts each rank must copy into its slots ([triton:L501-550](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L501-L550)).

Everything runs in a single 32-block launch, in this order:

1. **Local histogram** ([triton:L193-202](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L193-L202)): each block counts the routes in a contiguous range of tokens. The block's row is kept so that route order can be recovered in step 7.
2. **Cross-rank exchange** ([triton:L205-231](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L205-L231)): each rank writes its histogram into every peer's symmetric-memory window, followed by one rendezvous. After this, every rank holds every rank's histogram.
3. **Global expert load** ([triton:L237-277](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L237-L277)): sum the histograms to get the global route count of each expert, and from that the total load of each rank. Each expert's count is rounded up to the alignment once, so placement works in aligned blocks ([triton:L254-256](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L254-L256)).
4. **Pair senders with receivers** ([triton:L293-311](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L293-L311)): repeatedly pair the most-loaded rank with the emptiest one. The receiver takes its whole deficit from that single sender, which guarantees L slots are always enough.
5. **Split each sender's quota across its experts** ([triton:L312-345](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L312-L345)): the largest remaining expert fills the largest remaining quota. This gives the cumulative route boundaries for each destination.
6. **Assign slots** ([triton:L349-367](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L349-L367)): each receiver puts its incoming experts into slots 0..L−1 and writes `experts_to_copy`.
7. **Remap routes** ([triton:L371-424](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L371-L424)): compute stable per-expert ordinals from earlier blocks' histograms plus an in-tile sort ([triton:L393-407](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L393-L407)). A binary search over the boundaries then picks each route's destination and runtime ID ([triton:L410-424](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L410-L424)). Routes for the same expert keep their order.

### Weight push ([`_virtual_expert_weight_push_kernel`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L708-L769))

This kernel copies local expert weights into the virtual slots of peer GPUs in the expert-parallel group, following the planner's `experts_to_copy` ([launcher](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L949-L1001)). It runs before the forward expert GEMMs and again before the backward ones, because the slots are shared across layers and get overwritten in between.

- **Who sends what:** each owner picks out the entries of `experts_to_copy` that name its own experts, so it sends only the experts some peer actually needs ([triton:L743-748](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L743-L748)).
- **Work split:** each expert copy is cut into segments and spread across the blocks. Blocks working at the same time are given different destination peers, so the transfer uses every NVLink at once instead of queuing on one ([triton:L672-682](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L672-L682)).
- **Copy path:** the weights are read locally and written into the peer's arena as raw bytes, so BF16 and MXFP8 (data and scales) are copied unchanged ([triton:L684-704](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L684-L704)).
- **Barrier:** one on exit, so every slot is filled before any rank starts its expert GEMMs ([triton:L769](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L769)).

### Grad reduce ([`_virtual_expert_grad_reduce_kernel`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L785-L899))

After the backward GEMMs, each virtual slot holds a partial gradient for an expert that belongs to another rank. This kernel brings those partials home: each owner reads the slot gradients from every peer that hosted one of its experts and adds them into its own expert gradient ([launcher](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L1004-L1055)). It runs twice per layer, once for FC2 right after FC2's weight-gradient GEMM and once for FC1 after dispatch backward, so each can overlap the rest of the backward ([load_balancer:L915-936](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_load_balancer.py#L915-L936)).

- **Who reads from whom:** the planner's `experts_to_copy` tells each owner which peers hold copies of its experts, so only those slots are read ([triton:L839-849](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L839-L849)).
- **Peer reads:** one TMA descriptor covers every peer's grad arena ([triton:L855-862](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L855-L862)). This works because symmetric memory places all peers' arenas at the same stride, which the host checks once ([load_balancer:L178-187](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_load_balancer.py#L178-L187)).
- **Accumulation:** for each tile, the owner's own gradient and the peer partials are summed in FP32 in a fixed order and written once ([triton:L873-898](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L873-L898)). The result is bitwise identical from run to run, which a NCCL reduce-scatter would not guarantee.
- **Barriers:** one on entry, so every peer has finished writing its slot gradients, and one on exit, so every owner has finished reading and the slots can be reused ([triton:L863](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L863), [triton:L899](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L899)).

### Synchronization primitives

We create synchronization primitives to order symmetric-memory reads and writes across ranks, since no NCCL collective does this for us.

- **[`_grid_sync`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L99-L112)**: a self-resetting grid barrier. Block 0 flips a tag bit and each block waits for the flip, so no reset is needed between launches.
- **[`_rendezvous`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L581-L607)**: one int32 flag per ordered rank pair in the symmetric signal pad ([triton:L553-578](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L553-L578)). A release-flip to every peer is followed by an acquire-consume from every peer. The flags reset themselves.
- **[`_cross_rank_barrier`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L610-L638)**: a grid sync, then a block-0 rendezvous, then another grid sync and a proxy fence so later TMA reads see the peer writes.
  - In the push, the exit barrier means the slots are filled before anyone computes.
  - In the reduce, the entry barrier means every peer's wgrad is written, and the exit barrier means the slots can be reused.
- **[Timeouts](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L67-L96)**: every wait polls `globaltimer` and traps after ~100 s, even with `TRITON_DEBUG=0`. This turns a hang into a CUDA error. The planner's device asserts only fire with `TRITON_DEBUG=1`.

## Integration of MoonEP with the MoE layer

MoonEP launches three kernels per layer on side streams, each of which has to run at a specific point in the forward or backward:

- **Planner**: runs after the router and must finish before dispatch.
- **Weight push**: runs once before the forward expert GEMMs and again before the backward expert GEMMs, because the slots are shared and get overwritten between passes.
- **Gradient reduction**: runs after each FC's wgrad GEMM and must finish before the gradients are handed to DDP or GTP.

The forward calls these kernels directly. In the backward, they are triggered by identity [`_VirtualExpertHook`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_load_balancer.py#L567-L580)s placed on four forward tensors (the layer input, the dispatch input, the combine input, and the layer output), plus a forward pre-hook on FC1 and FC2's `wgrad_store`. The input hook takes the real parameters as extra inputs ([`wrap_layer_input`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_load_balancer.py#L816-L823)), and this is the only autograd edge back to them.

## Per-file changes

Each entry says why the file had to change, then what changed.

### `megatron/core/transformer/moe/virtual_expert_triton.py` (new)

**Why:** the planner, weight push, and gradient reduce need custom kernels; see [Kernel design](#kernel-design).

**What changed:** new file.
- [`VirtualExpertPlannerWorkspace`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L453-L498) owns the histogram window and scratch space the planner writes into. Compiled planner launches are cached per shape so later layers don't pay the Triton dispatch cost ([cache key](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L519-L549)).
- Kernel launches go through [`_launch_with_descriptor_allocator`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/virtual_expert_triton.py#L938-L946), which scopes Triton's descriptor allocator to the launch. This is why Triton 3.5 or newer is required.

### `megatron/core/transformer/moe/virtual_expert_load_balancer.py` (new)

**Why:** something has to connect the kernels to autograd, streams, and parameter storage; see [Load balancer design](#load-balancer-design).

**What changed:** new file. It is a mixin, so the HybridEP transport is left untouched and the virtual slots never become optimizer or checkpoint state.

### `megatron/core/transformer/moe/token_dispatcher.py`

**Why:** MoonEP has to plug into the flex dispatcher, and HybridEP has to accept a capacity that the planner computed rather than one derived from a capacity factor.

**What changed:**
- A new HybridEP subclass, [`_VirtualExpertHybridEPManager`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/token_dispatcher.py#L1328-L1405), is selected when the flag is on. It builds HybridEP with 2L local experts, starts the planner in [`setup_metadata`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/token_dispatcher.py#L1352-L1368), and in [`dispatch`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/token_dispatcher.py#L1370-L1390) hands HybridEP the runtime IDs and the matching probabilities.
- `_HybridEPManager.dispatch` takes a new optional [`rank_capacity`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/token_dispatcher.py#L1228-L1243) argument. Without it, behavior is unchanged. This is the one change to shared HybridEP code.
- Two no-op hooks, [`wrap_layer_input` and `finalize_layer_output`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/token_dispatcher.py#L220-L226), are added to the dispatcher base class so the MoE layer can call them unconditionally.

### `megatron/core/transformer/moe/router.py`

**Why:** the planner takes compact `[T, topk]` expert IDs. Building a `[T, E]` routing map and then compressing it would cost an extra kernel per layer.

**What changed:**
- With MoonEP on, the router returns compact int64 IDs and matching probabilities for every routing mode: top-k, hash, and quantile ([routing](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/router.py#L997-L1045)).
- [`_dense_route_indices_dtype`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/router.py#L486-L513) is restructured and now called for every routing mode. For the other backends it also excludes hash and sinkhorn, which preserves their previous behavior.

### `megatron/core/transformer/moe/experts.py`

**Why:** TE's grouped GEMM has to run over the natives plus the slots, but the slots must not be registered parameters. The FC2 gradient reduce also needs a trigger right after the FC2 weight-gradient GEMM so it can overlap FC1's backward.

**What changed:**
- [`bind_virtual_experts`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/experts.py#L439-L455) installs the slot weights as `weight{L..2L-1}` with `object.__setattr__`, which is how TE sees them while DDP and checkpointing don't.
- [`_VirtualExpertFC2WgradStore`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/experts.py#L237-L261) is installed as FC2's `wgrad_store`. TE then hands it the weight-gradient GEMM, which it runs immediately before starting the reduce.

### `megatron/core/transformer/moe/moe_layer.py`

**Why:** the load balancer needs a hook on the layer input and output, and the shared experts need to run while the planner is in flight.

**What changed:**
- The layer binds the experts to the manager ([here](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/moe_layer.py#L387-L389)) and wraps the layer input ([here](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/moe_layer.py#L523)) and output ([here](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/moe_layer.py#L694)).
- With MoonEP on, the shared experts run after preprocess instead of before the router ([flag](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/moe_layer.py#L207-L214), [reorder](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/transformer/moe/moe_layer.py#L740-L752)).

### `megatron/core/extensions/transformer_engine.py`

**Why:** `TEGroupedLinear` needs extra GEMM slots for the virtual experts, without changing initialization or the checkpoint layout.

**What changed:**
- `TEGroupedLinear` builds `num_gemms + num_virtual_experts` GEMMs ([here](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/extensions/transformer_engine.py#L2707)).
- [`reset_parameters`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/extensions/transformer_engine.py#L2899-L2906) unregisters the slot weights before init, so no RNG is consumed for them and init matches a non-MoonEP model.
- `sharded_state_dict` covers only the owned GEMMs, so checkpoints are interchangeable ([here](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/extensions/transformer_engine.py#L3010-L3032)).
- `is_first_microbatch` is forced to `None` whenever slots exist, because slot contents change between microbatches ([here](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/extensions/transformer_engine.py#L2916-L2921)).

### `megatron/core/tensor_parallel/generalized_tensor_parallelism.py`, `gtp_cuda_graphs.py`

**Why:** with expert GTP, the push needs the gathered weights before TE consumes them, and the gradient reduce needs weight-gradient buffers that stay at a fixed address until the delayed reduce-scatter.

**What changed:**
- [`peek_group_for_{forward,backward}`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/tensor_parallel/generalized_tensor_parallelism.py#L2507-L2518) returns the gathered buffers without consuming them, issuing the all-gather itself if none is in flight ([`_peek_gathered_weight`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/tensor_parallel/generalized_tensor_parallelism.py#L1719-L1761)). To support this, the consume path no longer checks `next_w`/`prev_w is not None` ([fwd](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/tensor_parallel/generalized_tensor_parallelism.py#L1821-L1823), [bwd](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/tensor_parallel/generalized_tensor_parallelism.py#L1878-L1880)). This affects every GTP user, not just MoonEP.
- [`get_wgrad_tensor(persistent=True)`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/tensor_parallel/generalized_tensor_parallelism.py#L1996-L2015) returns a buffer from a fixed ring per domain ([`_bind_eager_wgrad_ring_slot`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/tensor_parallel/generalized_tensor_parallelism.py#L336-L360)), sized by the new `eager_wgrad_ring_size` knob. Before a buffer is reused, it waits for the previous reduce-scatter ([`_EagerWgradRingSlot`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/tensor_parallel/generalized_tensor_parallelism.py#L320-L333)).
- The ring helpers are factored out so the graph and eager rings share them ([`allocate_wgrad_ring`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/tensor_parallel/gtp_cuda_graphs.py#L248-L262)). [`wgrad_ring_key`](https://github.com/NVIDIA/Megatron-LM/blob/b25838d02c5ba0067b930e76540cc8de7f3d03a2/megatron/core/tensor_parallel/gtp_cuda_graphs.py#L236-L245) now includes `chain_id`, so FC1 and FC2 get separate graph rings.
