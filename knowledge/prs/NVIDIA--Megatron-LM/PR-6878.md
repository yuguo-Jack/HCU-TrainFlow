[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/6878) · state: closed · merged: True

## Original PR description

- [x] I, the PR author, have personally reviewed every line of this PR.

  # What does this PR do?

  Bounds transient memory used by the generic ReFIT executor by executing
  deterministic, parameter-aligned batches. Existing uncapped execution remains
  the default.

  ## Details

  - Adds the optional `execution_batch_bytes` setting to the ReFIT APIs and
    exposes it through `--refit-execution-batch-bytes`.
  - Assigns globally consistent batch IDs from the shared metadata roster.
  - Keeps every slice and replica of a logical parameter in the same batch so
    MXFP8 destinations are quantized only after the complete parameter arrives.
  - Releases sender-side BF16 dequantization buffers and receiver-side staging
    buffers between batches without adding a device-wide synchronization after
    every batch.
  - Adds the required CUDA stream ordering before reusing MXFP8 dequantization
    storage across batches.
  - Makes multiple `CopyService.run()` calls explicitly opt-in:
    - NCCL, Gloo, and NVSHMEM support batched execution.
    - NIXL preserves its stable model-wide registration behavior.
    - NCCL M2N continues to use its native whole-plan execution path.
  - Uses the smallest configured non-`None` limit across participating ranks.
    The limit is soft because a single complete parameter may exceed it.
  - Preserves backward compatibility: when the setting is unset, execution uses
    one model-wide submission exactly as before, and third-party copy services
    retain the previous single-run behavior.

  ## Validation

  - `140 passed, 32 skipped` in the CPU-safe resharding and argument suites.
    Skips require CUDA, Blackwell MXFP8, FlashInfer, NVSHMEM, or NCCL4Py.
  - `BASE_REF=main CHECK_ONLY=true SKIP_DOCS=false bash tools/autoformat.sh`

Light review — one substantive finding, plus a test-coverage note.

**Cross-batch reuse of the side-stream dequant buffers is unordered**

`megatron/core/resharding/execution.py:123-130` — the BF16 dequant tensors are allocated *inside* `torch.cuda.stream(prefetch_stream)`, so the caching allocator associates those blocks with `prefetch_stream`'s pool. They are consumed on the **default** stream (the `[op.my_slice]` / `.contiguous()` slicing, and the backend's `isend`), then freed by `sendable_cache.clear()` at `execution.py:208`, right after `service.run()`.

Pre-PR this was harmless: there was exactly one dequant round per `execute_reshard_plan`, and the next one came after a full `torch.cuda.synchronize()`. Now the batch loop reuses the same `prefetch_stream` across batches with **no synchronize between batches** (the sync moved to after the loop, `execution.py:323`). So in batch N+1 the allocator can hand a just-freed block back to `prefetch_stream` and `dequantize_fp8_tensor` starts writing it while batch N's default-stream reads are still in flight — the slice copy, and the NCCL/Gloo send, since `req.wait()` only stream-orders and does not host-block. That is a silent wrong-weights race on MXFP8 sources rather than a crash.

Either fix works. Order the side stream behind the previous batch:

```python
    if mxfp8_param_names:
        assert prefetch_stream is not None
        prefetch_stream.wait_stream(torch.cuda.current_stream())
        with torch.cuda.stream(prefetch_stream):
            for param_name in mxfp8_param_names:
                sendable_cache[param_name] = _ensure_sendable(src_params[param_name])
                event = torch.cuda.Event()
                event.record()
                sendable_events[param_name] = event
```

or keep the streams independent and tell the allocator about the consumer:

```python
        with torch.cuda.stream(prefetch_stream):
            for param_name in mxfp8_param_names:
                sendable = _ensure_sendable(src_params[param_name])
                sendable.record_stream(torch.cuda.default_stream())
                sendable_cache[param_name] = sendable
                ...
```

**Test coverage**

`TestExecutionBatches` covers the batch split, the `supports_incremental_runs=False` opt-out, and the split-parameter rejection — good. What is not covered is the case the PR exists for: an **MXFP8 source or destination spanning more than one batch**. `test_nccl_m2n_copy_service.py` already builds real `MXFP8Tensor`s, so a plan with two MXFP8 params at `batch_id` 0 and 1, asserting bit-correct destination values, would exercise the per-batch dequant / accumulate / `quantize_` lifecycle — and would be the natural regression test for the race above.

Nothing else blocking. The planner-side batch IDs are derived from the same global roster on every rank, so the lockstep `run()` count holds for the collective backends (NVSHMEM's `schedule()`), and NCCL-M2N is unaffected since it takes the native `execute_plan` path.

- claude[bot] · comment · 2026-08-26T21:17:07Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/6878#issuecomment-5431223962)

Light review — the batching design is sound (globally-deterministic batch IDs replayed from the shared roster, no extra collective, per-param atomicity enforced by `_validate_execution_batches`, and the opt-in `supports_multiple_runs_per_plan` flag keeping NIXL/M2N on their stable paths). Three things worth a look, none blocking.

**1. `nccl_m2n` receives the un-reduced local limit, so heterogeneous values hard-fail**

`build_local_reshard_plan` min-reduces `execution_batch_bytes` across ranks (`planner.py:844-846`), but `get_or_create_service` passes the caller local value straight into the service (`refit.py:151`):

    service = NCCLM2NCopyService(group=group, max_group_bytes=execution_batch_bytes)

`NCCLM2NCopyService._get_topology` then requires exact cross-rank equality, raising `NCCL M2N max_group_bytes must match on every rank, got [...]`.

M2N is non-collocated by construction (source ranks then destination ranks, typically separate launchers), which is exactly the case where per-rank values can differ. So a config the planner deliberately harmonizes will instead crash in the M2N topology check on the first `execute_plan`. Options: min-reduce before constructing the service, or state explicitly in the `swap_model_weights` / `get_or_create_service` docstrings that the smallest-wins rule applies only to generic execution and that `nccl_m2n` requires the identical value on every rank.

**2. No end-to-end test of a multi-batch plan against an MXFP8 destination**

The stated motivation is "Keeps every slice and replica of a logical parameter in the same batch so MXFP8 destinations are quantized only after the complete parameter arrives." The new coverage tests that invariant only indirectly:

- `TestExecutionBatches` uses plain float32 params, so `pending_quantized` is never populated and the per-batch `quantize_()` finalization is never exercised.
- `test_mxfp8_prefetch_waits_for_previous_batch_consumers` mocks `is_mxfp8tensor`, `_ensure_sendable`, streams and events, so it asserts ordering only — no real quantized data.
- `test_rejects_destination_parameter_split_across_batches` covers the validator, not the MXFP8 path in the executor.

A value-checking test in `tests/unit_tests/resharding/test_mxfp8_refit.py` — real MXFP8 destination params, `num_batches=2` with one param per batch and multiple slices per param, asserting the refit weights match `MXFP8Tensor.from_bf16(src)` exactly as `test_multi_slice_assembly` does — would pin down the property the PR is built around and catch a regression where a batch boundary lands mid-parameter.

**3. `execution_batch_bytes` is not documented in the module README**

`megatron/core/resharding/README.md` only picks up the two cache-key rows. The new knob does not appear in Quick Start, Copy Service Backends, or MXFP8 Transform, so a reader of the module doc has no way to discover it or learn which backends honor it. A short subsection under Copy Service Backends would cover it, along the lines of:

    Bounding transient execution memory
    -----------------------------------
    `execution_batch_bytes` (CLI: `--refit-execution-batch-bytes`) caps the
    transient staging a rank allocates during one `CopyService.run()`. The limit
    is soft: a single complete logical parameter is never split, so one parameter
    may exceed it. Every slice and replica of a parameter stays in one batch, so
    MXFP8 destinations are quantized only once the full parameter has arrived.

    `nccl`, `gloo`, and `nvshmem` execute the batches. `nixl` keeps one
    model-wide submission because its receive address map must stay stable
    across refits, and `nccl_m2n` uses the value as its native
    grouped-submission limit instead. Ranks agree on the smallest configured
    non-`None` value; `None` everywhere preserves the previous single
    model-wide submission.
