# [Dev] Support paged stash with device-initiated GroupedTensor experts

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/6845) · state: open · merged: False

## Original PR description

## Summary

- Enable paged stash for the non-op-fuser `TEGroupedMLP` GroupedTensor path.
- Mark dynamic saved tensors explicitly through the MCore Transformer Engine adapter.
- Allow HybridEP static-budget paged stash with `moe_use_grouped_tensor=True` without requiring the TE op fuser.
- Preserve the paged-stash marker across fused SwiGLU/QuickGeGLU view and FP8-cast operations, and restrict this path to those supported fused activations.
- Exclude selective-recompute-managed FC2 inputs from paged-stash ownership using the existing `CheckpointWithoutOutput` storage-level marker, which survives TE reshape/split views.

## Review follow-up

Commit `16c115625` refreshes the branch onto current `dev` and addresses the strict-review comments:

- Replace the tensor-object recompute marker with `is_checkpoint_without_output_tensor()`, and add a reshape/split view regression test.
- Drive packed-bias operand marking directly from `config.moe_paged_stash`, so selective-recompute `detach()` does not silently disable it.
- Share the paged-stash scope setup and fused-activation marker propagation helpers.
- Route grouped-tensor marker detection through the Transformer Engine adapter and ignore `None` values when marking optional tensors.

## Strict review summary

**Findings: CRITICAL: 1, IMPORTANT: 1, SUGGESTION: 3**

Scope reviewed: the paged-stash saved-tensor hook, the new `_unfused_forward` split in `TEGroupedMLP`, marker propagation through the fused SwiGLU/QuickGeGLU boundaries, the TE adapter shim, and the new `__post_init__` validation. The `forward`/`_unfused_forward` split itself is a faithful move — the pre-compute padding, `tokens_per_expert` dtype/device normalization, and `quantization_unpadding` all retain their original ordering, and the paged-stash scope is placed to match `_fused_forward` exactly (context wraps compute; unpadding stays outside; `group_commit` after). The FP32 accumulation contract in `_apply_packed_bias` is unchanged, and the author's reasoning about which multiply operands autograd actually saves is correct.

### Most impactful

**1. CRITICAL — the selective-recompute ownership fix does not fire (`paged_stash.py:930-934`).** `_RECOMPUTE_MANAGED_TENSOR_ATTR` is a per-tensor-object Python attribute, but TE `GroupedLinear` reshapes and splits its input before `save_for_backward`, and those views carry a fresh `TensorImpl` with no Python attributes. So `on_save_for_backward` sees an unmarked tensor and paged-stashes the activation anyway — the exact double-ownership between `CheckpointWithoutOutput` (`resize_(0)` + `share_storage` rebind) and the paged stash that the commit set out to eliminate. This repo already documents the hazard and already solves it storage-level: see `tensor_parallel/random.py:64-66` ("the storage-level marker is visible through aliases/views") and `random.py:1146-1149`, which names *"TE GroupedLinear's `inp.reshape()` + `torch.split()` saved for backward"* as the motivating case. `is_checkpoint_without_output_tensor()` is already set unconditionally on every checkpoint output (`random.py:1093-1094`) and is already used for the identical question by `fine_grained_activation_offload.py:993` — swapping to it removes the new attribute, the new marker function, its export, and the `experts.py:945-946` call site. Note `test_recompute_managed_tensor_bypasses_paged_stash_save_hook` passes the marked object directly, so it cannot detect this; a `reshape()` in that test would.

**2. IMPORTANT — the packed-bias marking is dead under the config its own test uses (`experts.py:316-322`).** `paged_stash_marked` is inferred from `permuted_probs`, but with `activation_recompute` on, `bias_act_func` receives args routed through `detach_variable` (`random.py:778`) and therefore marks a *detached copy*; the object `_apply_bias` later sees is unmarked, as is the FC2 output. `TestPagedStashingGroupedTensor::test_forward_backward_without_op_fuser` sets `recompute_modules=["moe_act"]`, so both new `mark_grouped_tensor` calls are unreachable there. Impact is a silently lost memory saving (and a stash footprint that varies with an unrelated recompute setting), not wrong numerics — but it leaves the added marking untested. `self.config.moe_paged_stash` already answers this unambiguously; prefer threading it in over sniffing a TE attribute on an operand.

### Suggestions
- Extract the 19-line paged-stash scope block duplicated verbatim between `_fused_forward:771-789` and `forward:1028-1046`; the two `avg_num_tokens` estimates must stay in agreement for buffer sizing.
- `_propagate_paged_stash_marker` is byte-identical in `fused_bias_swiglu.py` and `fused_bias_geglu.py`, and its `hasattr(source, "grouped_tensor_scale_inv")` probe hardcodes a TE-internal attribute name in four places while the *write* goes through the TE adapter. An `is_grouped_tensor_marked()` predicate in the same adapter would keep one place aware of TE's naming.
- `_mark_paged_stash_tensors(*tensors: Optional[torch.Tensor])` advertises `None` but forwards straight into TE, which will not accept it; `bias_act_func` already guards `permuted_probs is not None` at line 879.

### One additional observation (no inline comment — outside the diff)
`on_save_for_backward` derives `hidden_size = tensor.numel() // self.max_num_tokens` (`paged_stash.py:950`) with no divisibility assertion. That was low-risk when only TE-internal `[max_num_tokens, H]` buffers were marked, but this PR extends marking to MCore-side tensors (`flat_probs` at `hidden_size=1`, `bias_per_token`, and fused-activation views produced by `input.view(-1, ori_shape[-1])`, which is shared with the 3-D dense-MLP call sites in `mlp.py`). A wrong `hidden_size` there is not an error — it silently mis-sizes the stash extents. Worth an `assert tensor.numel() % self.max_num_tokens == 0` at that parallelism boundary.

### Risk assessment

**Medium-high.** Backward compatibility is clean: the new validation only tightens a combination that previously produced a silent no-op stash, no defaults or checkpoint keys move, and the op-fuser path is untouched. Performance is fine — the added work is `hasattr` probes and marker sets, no new syncs, and `_apply_packed_bias` keeps its `output_size=` sync avoidance. The risk is concentrated in finding 1: if the recompute-managed guard is inert as analyzed, `--moe-paged-stash` combined with `--recompute-granularity selective --recompute-modules moe_act` on this new path can produce silently wrong expert gradients, and the PR's own validation (paged-stash-on capture iteration vs. paged-stash-on steady iteration) would not distinguish that from correct. Please either move the marker to storage level or add a view-level regression test plus a paged-stash-**off** reference comparison in `test_forward_backward_without_op_fuser` before this lands.

Also worth noting for the record: per the PR description the end-to-end grouped-tensor case is dependency-gated in CI (the image predates TE #3224), and the 32-GPU ON/OFF parity run was performed on the #6828 stack rather than this head — so at merge time neither the new path nor the ownership fix has CI coverage on this branch.

**[CRITICAL Correctness]** The recompute-managed marker is a **per-tensor-object Python attribute**, but the tensor autograd actually saves is not the object that was marked, so this guard will not fire for the case it is meant to protect.

`mark_paged_stash_recompute_managed(bias_act_output)` (`experts.py:946`) sets the attribute on the `CheckpointWithoutOutput` output object. `bias_act_output` is then handed to `TEGroupedLinear`, and TE's `GroupedLinear` reshapes/splits its input before `save_for_backward`. `reshape`/`view`/`split`/`detach` all produce a new `TensorImpl` and **do not carry Python attributes**, so by the time `on_save_for_backward` inspects the tensor, `getattr(tensor, _RECOMPUTE_MANAGED_TENSOR_ATTR, False)` is `False` and the activation gets paged-stashed anyway — the exact double-ownership the PR is fixing.

This repo already documents this precise hazard. From `megatron/core/tensor_parallel/random.py:1146-1149`:

> ALL views / reshapes that reference output's StorageImpl see the data (e.g. **TE GroupedLinear's `inp.reshape()` + `torch.split()` saved for backward**)

and that is why the analogous offload guard is **storage**-level, not tensor-level (`random.py:64-66`):

> Set on the output StorageImpl wrapper used by `CheckpointWithoutOutput`. The storage-level marker is visible through aliases/views of the output tensor.

**Why it matters:** the guard silently no-ops. Paged stashing takes ownership of a storage that `CheckpointWithoutOutput` will `resize_(0)` and later rebind via `share_storage`, so the backward pass reads whichever of the two writers landed last — silently wrong expert gradients, only under `recompute_granularity='selective'` + `moe_act`. The new `TestPagedStashingGroupedTensor::test_forward_backward_without_op_fuser` compares paged-stash-on against a *previous paged-stash-on capture iteration*, not against paged-stash-off, so a consistent-but-wrong gradient would still pass it.

**Suggested fix:** drop the new attribute and marker entirely and reuse the existing storage-level predicate, which `CheckpointWithoutOutput.checkpoint()` already sets unconditionally on every output (`random.py:1093-1094`) — no call site change needed in `experts.py`:

```python
from megatron.core.tensor_parallel.random import is_checkpoint_without_output_tensor

    def on_save_for_backward(self, tensor: torch.Tensor) -> Any:
        # CheckpointWithoutOutput intentionally releases the storage of its output after the
        # following module has saved it, then restores that same StorageImpl during backward
        # recomputation. Paged stashing must not take ownership of such a tensor in between.
        # The check is storage-level because TE GroupedLinear saves reshaped/split views of
        # the activation output, and Python attributes do not survive those views.
        if is_checkpoint_without_output_tensor(tensor):
            return tensor
```

This also removes `_RECOMPUTE_MANAGED_TENSOR_ATTR`, `mark_paged_stash_recompute_managed`, its export, the `if self.config.moe_paged_stash:` block at `experts.py:945-946`, and matches how `fine_grained_activation_offload.py:993` already solves the identical ownership question.

If the tensor-level marker is intentional because TE re-marks the reshaped view itself, please add a test that asserts the guard fires on a `reshape()` of the marked tensor — `test_recompute_managed_tensor_bypasses_paged_stash_save_hook` passes the marked object directly and therefore cannot catch this.
