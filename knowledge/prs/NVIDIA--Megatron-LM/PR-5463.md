# feat(recompute): add mamba to recompute_modules

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/5463) · state: open · merged: False

## Original PR description

- [ ] I, the PR author, have personally reviewed every line of this PR.

## What

Add `mamba` as a selective activation-recompute target. With `--recompute-granularity selective --recompute-modules '[mamba]'`, `MambaLayer` checkpoints the mixer (convolution plus selective SSM/SSD compute) instead of retaining its activations.

## Why

In Mamba-hybrid models the mixer activations can be a material part of long-sequence memory. Megatron already lets selective recompute target attention, MLP, MoE, and several GDN components, but not Mamba, leaving full-layer recompute as the only way to trade compute for this activation memory.

## Implementation

- Add `mamba` to the `recompute_modules` validation and documentation.
- Warn when `mamba` is selected with `moe_shortcut_connection`: shortcut MoE uses two-stage mixer execution and does not enter this checkpoint path.
- Use `tensor_parallel.checkpoint` for BF16/FP16/FP32.
- Use Transformer Engine checkpointing for FP8/FP4 so recomputation does not update amax/scaling history twice.
- Preserve `inference_context` and `packed_seq_params` through both paths.
- Keep eval and inference on the direct mixer path.
- Bypass activation checkpointing during local CUDA-graph warmup/capture, matching the existing tensor-parallel checkpoint contract and avoiding TE checkpoint's `.grad()` incompatibility.

The option is default-off and does not change existing runs unless `mamba` is explicitly selected.

## Tests

The focused suite retains the 12 routing/bypass cases and adds three shortcut-MoE warning cases. Six new tests build a real `HybridModel` with `MambaMixer`, compare recompute-off versus selective logits and all parameter gradients, and verify that the mixer runs again during backward. The matrix covers TP1, TP2, TP2 with sequence parallelism, and both memory-efficient and explicit Mamba paths. The mixer and checkpoint functions are not mocked in these model tests.

On the preceding head `6f88cf61288a`, NVIDIA CI passed the focused suite and H100 integration jobs; the SSM bucket passed 387 tests with 9 skips. Those results do not cover the new tests.

For the October 5 review update, Black, isort, Ruff, Pylint, `py_compile`, and `git diff --check` pass. The repository formatter script exits successfully; its non-blocking mypy step still reports missing dependencies/stubs and an existing `normalization` override type error. The local macOS pytest attempt stopped during normal Core import because Triton is unavailable; no test cases ran. Linux CPU and CUDA validation of the new cases remain pending, and CI needs authorization for the updated head.

An earlier 8×B200 run covered packed BF16 and FP8 training plus local Mamba CUDA-graph capture/replay. At sequence length 16K (CP1/DP8), selective and full FP8 recompute both completed without NaNs or OOMs and differed by about `1e-5` relative loss. A 20-step BF16 selective/full comparison had a maximum absolute difference of `2.37e-3`; repeating selective with the same seed produced `2.24e-3` run-to-run variation, so the cross-mode difference was within the measured baseline nondeterminism.

At the 24K BF16 boundary with the same model/topology, no recompute OOMed before completing its first step, while selective Mamba recompute completed both steps without NaNs (`10.58632 → 10.09310`) with rank-0 peak allocated memory of 96.13 GiB and 102.09 GiB. At 32K both modes OOMed before a complete step. Because the failed baseline has no common completed step, this is capacity evidence rather than a like-for-like percentage-memory comparison.

The intended CP8 matrix could not run because this environment did not expose a compatible deterministic attention backend, so these results are explicitly CP1/DP8 rather than CP8. Raw numbers and the CUDA-graph baseline comparison are in the PR discussion.

The one gap is fp8/fp4, where fp8-scaling correctness is at risk. As the PR notes, it is still a draft pending convergence/loss-parity and peak-memory validation vs full recompute — that validation should include an fp8 run to exercise the path above.

- claude · comment · 2026-07-06T21:31:08Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/5463#discussion_r3532161121)

File: `megatron/core/ssm/mamba_layer.py` · line None

**[IMPORTANT Implementation]** This recompute path unconditionally uses `tensor_parallel.checkpoint`, but the Mamba mixer runs fp8/fp4 GEMMs — `in_proj`/`out_proj` are `TELayerNormColumnParallelLinear`/`TERowParallelLinear`, and `mamba_mixer.py:227` has an explicit fp8 assertion. The established selective-recompute pattern in `transformer_layer.py:824-842` branches on fp8:

```python
if self.config.fp8 or self.config.fp4:
    from megatron.core.extensions.transformer_engine import te_checkpoint
    mlp_output_with_bias = te_checkpoint(apply_module(self.mlp), False,
        tensor_parallel.random.get_cuda_rng_tracker, self.pg_collection.tp, ...)
else:
    mlp_output_with_bias = tensor_parallel.checkpoint(...)
```

**Why it matters:** the plain `CheckpointFunction` (random.py:614-621) re-runs the forward under `torch.enable_grad()` in backward with no fp8-recompute context. TE's `te_checkpoint` sets the `activation_recompute` phase so the fp8 amax history / delayed-scaling factors are not updated a second time during recompute. Without it, fp8 mamba training will double-update amax and silently corrupt fp8 scaling, degrading convergence — while looking fine at bf16.

**Fix:** mirror the transformer-layer branch and route through `te_checkpoint` (passing `self.mixer`'s pg_collection TP group) when `self.config.fp8 or self.config.fp4`. Note the mixer is constructed with its own `pg_collection`, so you'll need the TP group available on the layer/mixer.
