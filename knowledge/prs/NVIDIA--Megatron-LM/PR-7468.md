# Fix stale weight decay after OptimizerParamScheduler.load_state_dict

## Original PR description

# What does this PR do?

Fixes a resume bug in `OptimizerParamScheduler.load_state_dict`. The method called `self.step(increment=num_steps)` before it restored `start_wd`, `end_wd`, `wd_incr_steps` and `wd_incr_style` from the checkpoint. `step()` writes both `lr` and `weight_decay` into every param group, so right after a resume the param groups held the learning rate from the checkpoint schedule but the weight decay from the constructor arguments. The scheduler object itself ended up with the right values, only the param groups were stale.

This matters because `train_step` in `megatron/training/training.py` calls `optimizer.step()` before `opt_param_scheduler.step()`, so the first optimizer step after a resume ran with the wrong weight decay. Every later step is fine because the next scheduler step rewrites the param groups. The bug only shows up when `--use-checkpoint-opt_param-scheduler` is set and the weight decay arguments differ from the ones stored in the checkpoint. With matching arguments the two schedules agree and nothing is visible.

The fix moves the `num_iters` / `num_steps` lookup and the `step()` call to the end of `load_state_dict`, after every value has been restored. Legacy checkpoints that only carry the old learning rate keys still load the same way. No other behaviour changes.

The change touches two files.

- `megatron/core/optimizer_param_scheduler.py` moves the `step()` call to the end of `load_state_dict`, adds a two line comment saying why, and adds the blank line after the module docstring that black 26.3.0 requires. That blank line is the only formatting change. black already fails on this file on main without it, so the formatter run for this PR could not pass otherwise.
- `tests/unit_tests/test_optimizer_param_scheduler.py` adds `test_load_state_dict_applies_checkpoint_weight_decay`. It loads a checkpoint whose weight decay schedule differs from the constructor and checks that the param group holds the checkpoint value and that lr and weight decay agree with the scheduler. On main the param group holds 0.05 while the scheduler reports 0.2, so the test fails there.
