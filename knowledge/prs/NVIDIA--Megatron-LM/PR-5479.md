# [main] Refactor Muon FP8 gather and preserve Adam sharding in both layouts

[Upstream PR](https://github.com/NVIDIA/Megatron-LM/pull/5479) · state: open · merged: False

## Original PR description

Main already supports FP8 parameter gather, including the initialization and synchronization fixes from #6754. This PR refactors Muon FP8 staging and makes Adam sharding independent of the Muon layout. The branch is rebased onto main `e30d863a6`.

## Scope

Both layouts reuse main's existing `ChainedOptimizer(LayerWise(Muon), DistributedOptimizer(Adam))` construction:

| Parameter owner | Compact layout | Padded layout |
| --- | --- | --- |
| Muon | Whole-parameter ownership, unpadded buffers, all-reduce gradients | Existing shard-aligned layout and reduce-scatter |
| Adam | Standard DistOpt sharding and reduce-scatter | Standard DistOpt sharding and reduce-scatter |

Only compact Muon buffers receive a private `dataclasses.replace(ddp_config, use_distributed_optimizer=False)` configuration. Adam retains `True`; the shared configuration is not changed to disable DistOpt. Training wrappers and direct core DDP construction use the same layout functions.

One `uses_grad_buffer_for_fp8_param_gather(param, ddp_config)` predicate defines staging independently of layout and tensor-parallel sharding:

| Parameter | Gradient-buffer reuse |
| --- | --- |
| Gather disabled, or high-precision parameter | Never |
| Plain/grouped MXFP8, either optimizer owner | Existing `--reuse-grad-buf-for-mxfp8-param-ag` flag |
| Muon blockwise FP8 | BF16 staging |
| Adam blockwise FP8 | Never; native FP8 DistOpt gather in both layouts |

No reuse flag is added, renamed or deprecated. Compact Muon transport supports plain MXFP8 and blockwise tensors; existing explicit errors cover generic Float8Tensor, NVFP4 and GroupedTensor. Grouped-MXFP8 eligibility in the general predicate does not imply compact Muon transport support. The compact MXFP8 opt-in guard does not restrict ordinary BF16 parameters.

The refactor keeps TE publication/quantization separate from transport staging, handles owner and non-owner publication after gather, and retains main's relocated-parameter copyback. GDP uses the existing `ensure_params_ready` helper before direct convolution-weight reads or CP weight slicing. Explicit refresh waits for pending gather; `zero_grad_buffer()` remains identical to main.

Checkpoint production methods and the optimizer-chain implementation are unchanged. The existing expert-Adam assertion is retained. Moving compact Adam to DistOpt changes optimizer ownership relative to main's compact path; validation covers new checkpoints saved and resumed with the same layout and topology, not migration from the old compact optimizer container.

### Attribution against main

On GB200, padded MXFP8 was rerun on main `e30d863a6` and PR `238b019b9`, with gather OFF and ON separately: **main → PR has zero loss, grad-norm and LR difference at every one of 200 steps for either flag setting**. Main itself reproduces the same OFF/ON differences shown above.

Initial masters match exactly. Both versions move the same two BF16 router parameters between owners when FP8 changes the padded buffer grouping; Adam shard ranges stay identical. At step 2, every prepared gradient shard has identical bytes across OFF/ON, but the norm differs by one FP32 ULP. This supports sensitivity to the existing norm summation order with clipping. One router gradient hash already differs at step 1; its numerical magnitude was not decoded, so norm rounding is not claimed as the sole origin of all differences.

The diagnostic reads tensors only at initialization and before clipping in the first three steps. Its current-PR trajectories also match the original ordinary E2E trajectories exactly for all 200 steps. This main baseline covers **MXFP8 padded only**; blockwise's similar layout mechanism is a code-based inference, not a separately executed main/blockwise comparison.

- Wohox · comment · 2026-08-17T10:13:03Z · [source](https://github.com/NVIDIA/Megatron-LM/pull/5479#discussion_r3795496498)

File: `megatron/core/optimizer/optimizer_config.py` · line None

Here, `layout` means the mapping of each parameter into the contiguous DDP buffer: its start/end indices, bucket assignment, and the padding and shard boundaries used by that buffer.

For LayerWise-managed parameters, the padded layout places every whole parameter inside one DP shard, aligns parameter starts, and pads the shards to the same size. The compact layout instead uses the normal no-padding DDP ordering and keeps whole-parameter ownership in the LayerWise optimizer’s ping-pong assignment.

The layout always determines the grad-buffer placement. It also determines the param-buffer placement when that buffer uses DistributedOptimizer; compact non-DistOpt LayerWise buffers do not allocate a DDP param buffer.
