# fix(optimizer): align mixed-dtype parameter indices with shard order

# What does this PR do?

Fix distributed optimizer parameter/state lookup for optimizer groups that contain both FP32 and FP16/BF16 model parameters.

Previously, the parameter index map was built in gradient-buffer traversal order, before main-parameter construction reordered the optimizer parameters. This change collects each group's local parameters, constructs the main parameter shards, then builds the index map once using the final optimizer order: FP32 shards followed by FP16/BF16-derived shards. Checkpoint reads and writes therefore use the actual optimizer parameter order.

### Example of the previous behavior

Consider one optimizer group containing BF16 parameter A and FP32 parameter B, with the BF16 buffer visited first:

| | Slot 0 | Slot 1 |
| --- | --- | --- |
| Original parameter index map | A | B |
| Actual optimizer parameter group | B's FP32 shard | A's FP32 master shard |

Previously, looking up A's main parameter and Adam state selected slot 0 and returned B's tensors. Different shard sizes can cause a checkpoint shape error; equal sizes can silently associate the wrong parameter and optimizer state. The corrected map assigns B to slot 0 and A to slot 1.

## Validation

- Added a distributed regression test covering both mixed-dtype registration orders and homogeneous dtype controls, with ordinary and precision-aware Adam (FP32 master weights).
- The test checks initial parameter association, serialized DP-zero checkpoint restore, and exact agreement of the next optimizer update with an uninterrupted run.
- Before the fix, the BF16-first regression fails on both ranks in both Adam modes: the lookup returns a shard with the wrong shape.
- Both test functions carry `launch_on_gb200`, enabling all 10 cases in the existing GB200 unit-test suite (4 GPUs). Marker selection was checked; GB200 execution is pending CI.
- Added two concrete mHC cases using a real small `HybridModel`, production `mark_keep_in_fp32` markers, `Float16Module`, DDP, and ordinary/precision-aware Adam. They assert that mHC parameters remain FP32, surrounding weights are BF16, and BF16-first buffers feed a mixed optimizer group.
- These are optimizer unit tests with controlled gradients and no mocks, model forward/backward, or training loop. They check direct parameter/state association, serialized DP-zero checkpoint restore, and exact agreement of the next optimizer update.
- Without the fix, both mHC cases fail on both GPU ranks with wrong-shard shapes (for example, 2,048 elements returned instead of 16,384). With the fix, all 10 cases pass on both ranks using `nvcr.io/nvidian/nemo:26.08.rc9`.
