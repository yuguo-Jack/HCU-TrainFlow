# feat(ppo): make loss aggregation configurable

[Upstream PR](https://github.com/areal-project/AReaL/pull/1546) · state: closed · merged: True

## Original PR description

## Description

Make policy-gradient loss aggregation configurable while keeping the default
token-mean behavior and response-level optimizer schedule.

| `actor.loss_aggregation` | Objective |
| --- | --- |
| `token_mean` (default) | Mean over valid response tokens |
| `seq_mean` | Mean of per-response token means |
| `prompt_mean` | Mean of per-prompt-group token means |
| `constant` | Masked token-loss sum / (`n_active_responses` × `L`) |

Each mode implements a bound `PolicyGradientReduction` protocol. Loss preparation
owns original denominator data and optimizer-step constants; PPO, SAPO, and CISPO
only pass their token losses and numerator masks to the reduction. Engines keep
their existing loss/weight callbacks.

For `prompt_mean`, preparation computes full-group token weights before the
unchanged response-level split. Groups can span optimizer steps and microbatches.
With G active groups across data-parallel ranks and K actual steps, each step
uses a fixed G/K denominator. At fixed parameters and masks, averaging the step
objectives and gradients recovers the full-batch prompt mean. Accumulation and
objective metrics use each microbatch's share of the step's real responses so optimizer steps contribute equally. Megatron's per-token path
keeps original token counts for MTP/MoE normalization and compensates the main
objective separately, preserving fractional reduction weights. Reward-model
batches without token masks retain their existing callback-defined counts.
Real steps with no valid tokens remain in the schedule; transport dummies have
zero weight, and globally empty updates are rejected.

Rejection sampling and M2PO narrow the numerator while preserving original
normalization. Both multi-teacher and legacy single-teacher distillation use the
original token denominator; legacy teacher numerators retain their post-M2PO,
pre-rejection masks. M2PO's existing selector remains microbatch-dependent.
Non-token aggregation with distillation or tree training is rejected.

`actor_loss/avg` reports the composed objective. The token-level PG diagnostic is
available as `actor_loss_token_mean/avg` and its min/max.

The knobs, and what we found:

Token aggregation (+3.9 pts). There are three natural ways to aggregate the policy loss over a batch:
Equally over every token (token_mean, one global token pool, which is how token-level loss is implemented in most open frameworks; Dr. GRPO [14] is the equal-token variant that normalizes by a constant)
Equally over every sequence (sequence_mean, as in original GRPO [15])

Loss Aggregation We evaluate three strategies for aggregating the RL loss: (a) Sample average where each
rollout contributes equally (as in GRPO, Appendix A.2). (b) Prompt average where each prompt contributes
equally (as in DAPO, Appendix A.2). (c) Token average where all token losses in the batch are averaged
directly, without intermediate grouping. The comparison results are shown in Appendix A.9 (Figure 14a). We
find prompt-average achieves the highest asymptotic performance and therefore use this choice for ScaleRL.

- EazyReal · comment · 2026-09-23T23:18:54Z · [source](https://github.com/areal-project/AReaL/pull/1546#discussion_r4088250860)

File: `areal/trainer/ppo/actor.py` · line None

The current revision keeps the original response-level optimizer partitions and step count. Preparation now owns the normalization state, and PPO/SAPO/CISPO receive a bound reduction rather than prompt-specific arguments.

I'd like your preference on one remaining design choice: should the engine keep accepting a local loss plus a weight, or accept an additive numerator with explicit step normalization? Both options keep the per-mode reduction protocol and the same objective and schedule.

For example, take one GPU and one optimizer step:

| Microbatch | Responses and token losses | Prompt's mean loss |
| --- | --- | --- |
| MB1 | Prompt A: `[2, 4]`, `[6, 8]` | `20/4 = 5` |
| MB2 | Prompt B: `[10, 14]` | `24/2 = 12` |

Each prompt should contribute equally, so the target is `(5 + 12) / 2 = 8.5`.

**A — keep the current engine contract, as implemented here.** The engine takes a weighted mean of callback results. The current prompt reduction uses each microbatch's share of the step's responses as its engine weight: `2/3` for MB1 and `1/3` for MB2.

To preserve the desired contributions of `5/2` and `12/2`, the reduction first divides them by those weights:

```text
MB1 returns: loss = (5/2) / (2/3) = 3.75, weight = 2/3
MB2 returns: loss = (12/2) / (1/3) = 18,  weight = 1/3

Engine: (3.75 * 2/3 + 18 * 1/3) / (2/3 + 1/3) = 8.5
```

This fits the existing callbacks, but the reduction has to undo the weighting that the engine will apply.

**B — make the numerator and step denominator explicit.** The callbacks return `5` and `12`, and the step provides denominator `2`:

```python
LossObjective(
    numerator_fn=...,
    normalization=GlobalDenominator(2),
)
```

The engine backpropagates `5/2` and `12/2`, accumulating gradients before one optimizer step. If MB1 is split again, its numerators become `1.5` and `3.5`; the same denominator gives `(1.5 + 3.5 + 12) / 2 = 8.5`. A preserves this result too, through its weight compensation.

The normalization contract would distinguish a measured denominator (`SumDenominator(measure)`, for token/sequence/pair means) from an already-global one (`GlobalDenominator(value)`, for prompt mean). Measured counts are collected after packing, before numerator filtering, and reduced over DP without counting CP replicas twice.

For prompts spanning optimizer steps, both options retain full-group coefficients and the current fixed denominator: global active group count divided by actual optimizer-step count. Neither changes the schedule.

B would keep computation inside the training worker, resolve the denominator once per step, and preserve backend scaling and Megatron's auxiliary-loss normalization. It doesn't require retaining every microbatch's graph or adding a denominator all-reduce per microbatch. Its cost is migrating the train/eval contract and normalization/metrics across all three engines and the SFT/critic/DPO/RW callers.

I prefer B as the longer-term interface, while A keeps this PR scoped. Would you prefer keeping A here and considering B separately, or taking the core API change in this PR?
