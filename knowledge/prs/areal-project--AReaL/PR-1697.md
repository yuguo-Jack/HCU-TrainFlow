# perf: reduce VLM CPU broadcast and microbatch memory overhead

[Upstream PR](https://github.com/areal-project/AReaL/pull/1697) · state: closed · merged: True

## Original PR description

## Description

Reduce duplicated CPU tensor transfers and image-buffer residency in the VLM training path.

### Background

Shared rollout image tensors can still be broadcast repeatedly from a data-parallel head to other model-parallel ranks, creating separate receiver buffers for the same source tensor. In addition, Megatron previously concatenated image tensors for every microbatch during batch preparation, retaining all concatenated CPU image buffers while the schedule consumed microbatches one at a time.

This PR builds on the existing tensor-reference reuse and CPU microbatch streaming paths. It addresses these remaining CPU-side copies without changing image preprocessing, logical image ordering, batch partitioning, or loss normalization.

### Optimizations

1. **Preserve tensor aliases during CPU broadcasts.** Send each repeated tensor object once per broadcast payload and encode subsequent occurrences as references. Receivers reuse the corresponding tensor buffer. Both the v1 RPC path and v2 training workers opt in only for CPU-staged methods on vision engines, and the source selects the new protocol only when the payload contains nonempty multimodal tensors. Text-only payloads retain the existing wire format and receiver-buffer behavior.
2. **Assemble vision inputs immediately before each Megatron microbatch runs.** Keep reusable per-sample CPU image tensors in the microbatch sources, then concatenate the current microbatch just before device staging. Remove stale top-level vision fields that the concatenation would overwrite, and keep vision payloads off the loss/bookkeeping side. Shallow-copying the dictionaries before extraction preserves sources for repeated forward calls and virtual-pipeline consumers.

The expected benefits are fewer duplicate CPU broadcasts/receiver allocations for shared images and less CPU memory occupied by eagerly concatenated image batches. This PR does not claim measured GPU-memory or throughput improvements.

### Added files

- `tests/scripts/check_multimodal_memory_minimal.sh`: CPU/Gloo regression-check entry point for broadcast aliases, v1/v2 worker gating, microbatch preparation, and existing CPU streaming contracts.
- `tests/scripts/check_multimodal_memory_e2e.sh`: target-hardware entry point for distributed VLM forward and training checks, configured through `VLM_MODEL_PATH` and `BACKEND`.
- `tests/scripts/multimodal_memory.md`: instructions, supported-path boundaries, and the distinction between data-contract checks and hardware performance validation.

### Modified files

- `areal/utils/data.py`: detect nonempty multimodal tensor payloads and add the source-selected alias-preserving broadcast protocol.
- `areal/infra/rpc/guard/engine_blueprint.py`: scope the broadcast opt-in to CPU-staged vision-engine RPC calls.
- `areal/v2/training_service/worker/app.py`: enable the same CPU-staged vision-engine broadcast opt-in for v2.
- `areal/engine/megatron_engine.py`: defer vision concatenation until microbatch consumption and release overwritten batched fields during preparation.
- `areal/engine/megatron_utils/packed_context_parallel.py`: reuse existing vision extraction on copied microbatch dictionaries.
- `tests/test_broadcast_tensor_container.py`: cover real CPU/Gloo collectives, absent receiver inputs, repeated tensors, distinct views, and text-only protocol isolation.
- `tests/infra/rpc/test_engine_validation.py`: cover the vision-engine/CPU-staging opt-in boundary.
- `tests/v2/training_service/test_worker_unit.py`: cover missing/false/true vision capability and unstaged-method protocol isolation.
- `tests/test_megatron_engine_vlm.py`: cover lazy/eager tensor equivalence, reusable sources, stale-field handling, and text/empty-image staging.
- `tests/test_megatron_engine_vlm_distributed.py`: register a two-GPU tensor-parallel regression test.
- `tests/torchrun/run_megatron_engine_vlm_distributed.py`: add a memory-isolation scenario covering alias broadcast, repeated image forward, text-only forward, and an optimizer update.

### Scope and limitations

- Alias reuse is based on tensor object identity within one broadcast call, not image-content deduplication. Distinct tensor views remain distinct. Once enabled for a mixed multimodal payload, alias preservation applies to repeated tensors throughout that payload.
- The broadcast opt-in is wired into both v1 RPC and v2 training workers. Megatron lazy vision assembly already lives in the shared training engine and applies to both versions.
- For repeated images from separate v2 rollout sessions, #1711 preserves shared references through export, worker localization, and advantage computation. This PR reuses those shared objects during model-parallel broadcast; it does not deduplicate distinct objects by content. When trajectory dumping is enabled, #1709 prevents the dump path from materializing image references. Lazy image assembly can reduce eager CPU buffers independently of repeated-image reuse.
- No FSDP/Archon engine changes, inference-server changes, new configuration fields, or dependency changes are included. Existing VLM context-parallel support restrictions remain unchanged.
- Original CPU image sources remain available for the microbatch-list lifetime. Autograd and pipeline execution may retain GPU inputs until backward; the change does not guarantee single-microbatch GPU residency.
- Virtual-pipeline consumers can repeat CPU concatenation. Its throughput trade-off and actual memory savings require target-hardware measurement.
