# PR information

`swift sft`, `swift rlhf` and the other commands run the real entry point (or torchrun) in a child process with [`subprocess.run(args)`](https://github.com/modelscope/ms-swift/blob/409170095f24b45b8945715341504d99b70a2bc0/swift/cli/main.py#L100), and the CLI leaves signals alone. Two things follow:

- **SIGTERM sent to the `swift` process never reaches the child.** The CLI exits (or, as PID 1 in a container, ignores the signal), and the trainer keeps running until it is SIGKILLed along with the container, without a checkpoint. Kubernetes (Job deletion, preemption, eviction), `docker stop`, supervisord and `kill <pid>` all signal that one PID. We hit this running training as Kubernetes Jobs with a callback that saves on SIGTERM.
- **Ctrl-C kills the child 0.25 s later.** The terminal sends SIGINT to the whole foreground process group, so the child gets it too. But `subprocess.run` answers the CLI's `KeyboardInterrupt` with `process.kill()` after a 0.25 s wait. With `NPROC_PER_NODE` the child is torchrun, killed while it is shutting its workers down.

As a result, handlers in ms-swift that expect these signals are skipped or cut short:
- [`ShutdownManager`](https://github.com/modelscope/ms-swift/blob/409170095f24b45b8945715341504d99b70a2bc0/swift/utils/shutdown_manager.py#L9) (SIGTERM, SIGINT), behind `--callbacks graceful_exit`;
- the web UI's [`register_clean_hook`](https://github.com/modelscope/ms-swift/blob/409170095f24b45b8945715341504d99b70a2bc0/swift/ui/llm_infer/llm_infer.py#L302-L310) (SIGINT, SIGTERM → `clean_deployment`);
- the `swift rollout` server's [shutdown](https://github.com/modelscope/ms-swift/blob/409170095f24b45b8945715341504d99b70a2bc0/swift/pipelines/infer/rollout.py#L824-L830), which uvicorn runs on SIGINT or SIGTERM and which waits up to 10 s for each vLLM worker to exit.

This PR replaces `subprocess.run` with a small `run_command` that:
- forwards SIGTERM to the child;
- ignores SIGINT in the CLI while the child runs, since the child already gets it from the terminal (forwarding it would deliver it twice);
- returns 128 + N for a child killed by signal N, as a shell reports it, instead of the 256 − N that `sys.exit(-N)` gives (241 for SIGTERM);
- installs the handlers only from the main thread, and restores them afterwards.

With `NPROC_PER_NODE`, the forwarded SIGTERM goes to torchrun. torchrun passes it on to the workers and kills any that are still running after 30 s, which recent PyTorch lets you change with `TORCH_ELASTIC_SHUTDOWN_TIMEOUT`. This PR doesn't change that.

Replacing the CLI with `os.execv` would be simpler. However, the web UI finds its running tasks by the `swift <command>` command line ([`runtime.py`](https://github.com/modelscope/ms-swift/blob/409170095f24b45b8945715341504d99b70a2bc0/swift/ui/llm_infer/runtime.py#L139-L145)) and stops them through that process's children, so the `swift` process has to stay.

## Experiment results

The new `tests/utils/test_cli_signals.py` starts `cli_main` in its own session, with a stand-in child that logs the signals it handles, and then sends the signals. The same harness on `main` (`40917009`) and on this branch:

| case | `main` | this PR |
|---|---|---|
| SIGTERM to the `swift` PID; the child saves on SIGTERM | The CLI is killed by the signal. The child never sees it and keeps running. | The child handles it and exits 0. The CLI exits 0. |
| SIGTERM to the `swift` PID; the child has no handler | The CLI is killed by the signal. The child keeps running. | The child is terminated. The CLI exits 143. |
| Ctrl-C (SIGINT to the process group); the child takes 1 s to finish | The child is SIGKILLed mid-handler. The CLI dies of the `KeyboardInterrupt`. | The child finishes. The CLI exits 0. |

The three tests fail on `main` and pass on this branch, on Linux (`python:3.12-slim`) and on macOS. `tests/utils/test_cli_config_args.py` still passes, and `pre-commit` is clean on the changed files.
