# fix: keep BCO running statistics unchanged during evaluation

# PR information

I found that evaluating `bco_pair` updates the same `RunningMoments` used for training. `prediction_step()` already passes `train_eval='eval'`, but that flag does not reach `dpo_loss()`. As a result, validation rewards change the baseline used by the next training batch, even though evaluation does not update model weights.

This change passes the existing flag through the loss loop and updates BCO statistics only during training. Evaluation reads the training baseline without modifying `mean`, `count`, `var`, or `std`. The default remains `'train'` for existing direct callers, and the flag also reaches BCO in weighted loss combinations.

The patch is limited to one production file (+5/-2 lines).

## Experiment results

Validation used PyTorch 2.12.1+cu130, Transformers 5.5.0, and TRL 0.29.1, with a local two-layer Qwen3 model and the actual Swift `DPOTrainer.train()` / `evaluate()` paths:

- Ran 36 configurations on each of the original and patched implementations: CPU FP32/FP64 and CUDA FP32/BF16 autocast; BCO, weighted BCO + sigmoid, and sigmoid; evaluation disabled or using 1/4 batches. Each run performed five optimizer steps with gradient accumulation of two, including epoch transitions.
- On the patched implementation, inserting evaluation left training losses, every optimizer-step gradient, final parameters, and running statistics exactly equal to the no-evaluation control. Standalone evaluation also preserved all running statistics and model parameters.
- All 12 no-evaluation configurations matched the original implementation exactly, including gradients and final parameters. The original implementation changed subsequent gradients in all 16 BCO/mixed-loss configurations with evaluation enabled.
- `pre-commit run --all-files`: passed.
- Existing `test_rlhf_loss.py` and `test_dpo_precompute.py`: the original and patched trees both reported 14 passed, 66 subtests passed, and the same 3 failures. These are the padded/padding-free logits-to-keep test and its CPU/CUDA integration subtests: `_PaddingFreeDPOStub.args` lacks `tuner_backend`, causing an `AttributeError` in `prepare_logits_to_keep()` before the loss is reached. No new failures were introduced.

These checks establish behavior for the tested configurations; they are not a claim about convergence or model-quality improvements.
