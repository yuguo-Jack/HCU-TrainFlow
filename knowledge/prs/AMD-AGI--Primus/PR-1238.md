# perf(mi355x): run the DSv2-Lite and Qwen3-30B-A3B FP8 recipes on Primus-Turbo GEMMs

[Upstream PR](https://github.com/AMD-AGI/Primus/pull/1238) · state: open · merged: False

## Original PR description

## Why
Both recipes keep their dense FP8 GEMMs (and Qwen3 its experts) on Transformer Engine, and neither trains on MI355X:
- DSv2-Lite FP8: TE's hipBLASLt wgrad GEMM returns `HIPBLAS_STATUS_INTERNAL_ERROR` in the first backward, or the first forward loss is NaN.
- Qwen3-30B-A3B FP8: delayed scaling + legacy grouped GEMM hits an HSA memory aperture violation in iteration 3.

## What
- `use_turbo_gemm: true` and `use_turbo_grouped_gemm: true` in both recipes.
- Qwen3: `fp8_recipe: tensorwise` (Turbo GEMMs reject `delayed`), legacy grouped GEMM dropped.
- DSv2-Lite: `turbo_gemm_backend: "fp8:triton"`. Turbo's default FP8 tensorwise backend is hipBLASLt, which fails the same way on this model's backward GEMMs; Triton was faster than CK here (10.44 vs 10.71 s/iter).

## Results (MI355X, 1 node, 50 iters, mock data, Turbo 53099da3 / #539)
| recipe | s/iter | tokens/s/GPU | notes |
|---|---|---|---|
| Qwen3-30B-A3B FP8 | 8.76 | 29.9k | BF16 recipe on the same node: 9.36 s/iter, 28.0k |
| DSv2-Lite FP8 | 10.47 | 43.8k | loss 11.86 -> 0.51 by iter 50, no NaN or skipped iters |

Both recipes also ran 10 iterations exactly as committed; the resolved Megatron arguments match the 50-iteration runs.
