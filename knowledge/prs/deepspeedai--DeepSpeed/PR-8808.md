# fix(fp_quantizer): rename local shadowing template param for CUDA 13+ nvcc

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8808) · state: open · merged: False

## Original PR description

## What does this PR do?

nvcc 13.x (CUDA 13+) rejects redeclaring a template parameter name as a local variable inside the function body. `apply_dequantization()` and `apply_selective_dequantization()` in `csrc/fp_quantizer/fp_quantize_impl.cu` both declare a local `constexpr int q_exponent_bits` that shadows the template parameter `int q_exponent_bits`, so building `fp_quantizer_op` on CUDA 13+ fails with:

```
csrc/fp_quantizer/fp_quantize_impl.cu(234): error: template parameter "q_exponent_bits" may not be redeclared in this scope
csrc/fp_quantizer/fp_quantize_impl.cu(413): error: template parameter "q_exponent_bits" may not be redeclared in this scope
2 errors detected in the compilation of "csrc/fp_quantizer/fp_quantize_impl.cu".
```

CUDA 12.x compilers accept the shadowing, which is why upstream CI has not caught it.

## Why is this PR needed?

PyTorch >= 2.12 headers require C++20, and DeepSpeed's `nvcc_args()` now passes `-std=c++20` on CUDA 12.5+/13+. On a CUDA 13 + recent torch stack (e.g. CUDA 13.4 / torch 2.14) the fp_quantizer kernel no longer compiles at all, breaking `op_builder` / `python setup.py install` / `python -m build` when `DS_BUILD_FP_QUANTIZER=1`.

## Design

Rename the two shadowing locals to `new_qeb`. The template parameter name is kept because it is part of the kernel signature and referenced by call sites (including the `clip<...>` template arguments).

Behavior is unchanged: the local always equals `total_q_bits - mantisa_bits - 1` (e.g. 3+2=6), which differs from the template default (4) anyway — the existing line 233/412 `quantized_bits = q_mantisa_bits + q_exponent_bits + 1` already implicitly relied on the shadowed value.

## Testing

- Reproduced the failure with the pre-fix file on CUDA 13.4 + torch 2.14.1 (`-std=c++20`): 2 errors, build fails.
- With the fix, the file compiles cleanly (0 errors) under the same toolchain.
- Full wheel build succeeds: `python -m build --wheel --no-isolation --config-setting="--build-option=build_ext"` on an A100 (sm_80/86/89/120) host, CUDA 13.4, Python 3.12, torch 2.14.1.

Hardware: 2x NVIDIA A100-SXM4-80GB (sm_80) host, compile targets sm_80/86/89/120.

- bheu · comment · 2026-10-12T10:16:13Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8808#discussion_r4246886830)

File: `csrc/fp_quantizer/fp_quantize_impl.cu` · line 234

This P1 does not apply — I traced the full call chain and verified the shadowing is intentional and correct.

**How `q_exponent_bits` actually gets bound in this PR**

`apply_dequantization` / `apply_selective_dequantization` are only reached via:

```cpp
// csrc/fp_quantizer/fp_quantize_impl.cu (DEQUANT_SWITCH, applied to both kernels)
#define DEQUANT_SWITCH(q_bits)                                                    \
    switch (q_bits) {                                                            \
    case 8: /* E4M3 */                                                            \
        apply_dequantization<T, mantisa_bits, 3, 4>...                            \
    case 6: /* E3M2 */                                                            \
        apply_dequantization<T, mantisa_bits, 2, 3>...                            \
    ...
```

which is invoked as:

```cpp
DEQUANT_SWITCH(q_mantisa_bits * q_exponent_bits)   // q_mantisa_bits, q_exponent_bits are the
                                                   // SOURCE quantization format's bit widths,
                                                   // passed in from deepspeed/ops/fp_quantizer/quantize.py
```

So the template `q_exponent_bits` is **always** the source quantization format's exponent width (4 for E4M3, 3 for E3M2, ...), never the destination dtype's width. It is not a free parameter — there is no call site that binds it to 8 for a BF16 destination.

**Why the local re-derivation is correct for the destination**

Inside the kernel, `q_buf`/`q_buf1` are the *destination-format* packed values (shifted by `mantisa_bits`, i.e. 7 for BF16, then repacked into `uint16_t`). The masks that read them therefore need the destination-format bit widths:

```cpp
constexpr uint16_t _exponent_mask = ((1 << new_qeb) - 1) << q_mantisa_bits;
constexpr uint16_t _sign_mask = 1U << (q_mantisa_bits + new_qeb);
```

where `new_qeb == total_q_bits - mantisa_bits - 1 == 16 - 7 - 1 == 8` for a BF16 destination. Using the *source* `q_exponent_bits` (4) there instead would mask only 4 bits of a field that actually occupies 8 — the subsequent re-biasing (`dst_exponent - bias_q + bias_dst`, where `bias_q` is derived from the *source* format) and repacking into `dst_data[j]` with `<< (mantisa_bits - q_mantisa_bits)` shifts would then operate on a truncated/misplaced exponent field. That matches the existing (pre-PR) behavior exactly: on every CUDA version that compiles this code today (CUDA <=12, where the shadow is legal C++), the local variable was always the value in use, and the FP8-GEMM tests (`tests/unit/ops/fp_quantizer/test_fp8_gemm.py`) pass upstream with that behavior.

**Net effect of the PR**

- CUDA <=12: identical generated code to today (local variable was always shadowing; nothing changes).
- CUDA 13+: compiles at all (currently a hard error). Generated code is bit-for-bit the same as the CUDA <=12 behavior above, since `constexpr` folding of `total_q_bits - mantisa_bits - 1` yields the same value the shadowed local always had.

So this is a pure build-fix, not a behavior change, and the "mis-sized `quantized_bits`" concern would actually introduce a behavior change relative to every release shipped so far. Happy to add a short comment to the code documenting why `new_qeb` must track the destination format (not the source `q_exponent_bits`) so this doesn't have to be re-derived next time — let me know if you'd like that added to this PR.
