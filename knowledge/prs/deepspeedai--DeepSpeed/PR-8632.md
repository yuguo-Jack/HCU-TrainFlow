# Harden ZeRO-1/2 offload gradient storage lifetime and stream ordering

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8632) · state: closed · merged: True

## Original PR description

## Summary

Harden gradient storage lifetime and stream ordering for ZeRO-1/2 with optimizer offload (`cpu` or `nvme`). These protections are always on for offload and have no configuration options. They address ownership and synchronization risks found while debugging NaNs under CPU offload.

## Changes

- **Oversized-gradient ownership:** gradients larger than `reduce_bucket_size` are cloned into independent storage before reduction. Reduction and the D2H offload copy then read the clone.
- **Producer readiness:** every bucket producer records an event, including oversized gradients. Reduction waits on all of them, with or without `overlap_comm`.
- **Bucket reuse:** a contiguous IPG buffer records a reuse event when its consumer finishes, and later producers wait on it before writing into that buffer again.
- **Stream lifetimes:** gradient tensors are `record_stream`'d on the streams that consume them.
- **Offload copy ordering:** successive CPU-gradient writes are ordered across streams. Pending offload copies are waited on before CPU accumulator reloads, `step()`, `reset_cpu_buffers`, checkpoint loading (legacy and universal), and `destroy()`.
- The existing `overlap_comm` barrier (compute stream waits on the reduction stream) is kept. The new events only add ordering on top of it.

## Scope

- **Covered:** ZeRO-1 and ZeRO-2 with `offload_optimizer` set to `cpu` or `nvme`. Both stages use the same `reduce_independent_p_g_buckets_and_remove_grads` → `copy_grads_in_partition` D2H path, and offload already forces `contiguous_gradients`. Pipeline parallelism and DeepCompile are not excluded.
- **Not covered:** ZenFlow, which overrides reduction and offload copies with its own ordering. A warning is logged when ZenFlow is combined with offload.
- **Unchanged:** non-offloaded paths and ZeRO-3. Reduction thresholds, communication dtypes, and accumulation semantics are also unchanged.

## Cost

Oversized gradients add one gradient-sized allocation and copy. Event tracking adds synchronization overhead and can extend storage lifetimes.

## Tests

`tests/unit/v1/zero/test_zero2_gradient_safety.py`:
- Unit tests for oversized-copy independence, producer and reuse waits, cross-stream CPU write ordering, the pageable-accumulator wait (default path, no accumulation flag), and waits before step, reset, and checkpoint load.
- A constructor matrix covering stage, contiguous, and offload device (cpu, nvme, none).
- Two-rank training against an independent full-batch reference: ZeRO-1/2, with and without offload, `overlap_comm`, and `contiguous_gradients=false`.
- A CUDA stream-handoff test for oversized producers.

Ran locally (macOS, CPU accelerator, 2 ranks): 35 passed, 2 skipped (the CUDA-only tests). A multi-GPU NCCL run of offload + overlap is still pending.

- sfc-gh-truwase · comment · 2026-10-01T14:05:40Z · [source](https://github.com/deepspeedai/DeepSpeed/pull/8632#issuecomment-5933116598)

The 10 `modal-torch-latest` failures are one issue, and it is in the test harness rather than the offload code.

`_record_gradient_stream` (`stage_1_and_2.py`) calls `tensor.record_stream(stream)` whenever offload safety is on and `resolves_data_dependency()` is `False`. `make_optimizer` in `test_zero2_gradient_safety.py` builds the parameter, its gradient, and the IPG buffer on **CPU** while using the real `get_accelerator()`. On CUDA that returns `False`, so `record_stream` runs on a CPU tensor, which `aten` does not implement. On a CPU/MPS accelerator it returns `True` and the call is skipped, which is why this was green locally. That also explains why only the `cpu_offload=True` parametrizations fail.

No production path is affected: every tensor reaching the three call sites is accelerator-resident (`get_gradient_for_reduction` returns the bit16 `param.grad`; the IPG buffers and `temp_grad_buffer_for_gpu_offload` are allocated on `current_device_name()`). The two-rank offload test in the same file passed on the GPU runner.

Fix is in the test: default `make_optimizer(device=...)` to `get_accelerator().device_name()` (keep the fp32 master partition on CPU, as it already is) and allocate `original` in `test_oversized_copy_is_independent_and_preserves_routing` on `param.device`. That matches real offload layout and actually exercises `record_stream` on GPU runners. Reproduced all 10 failures on a CPU box by flipping `resolves_data_dependency()` to `False`; with that harness change the suite stays green there.

One side note: in `async_inplace_copy_grad_to_fp32_buffer_from_gpu`, when a dtype conversion happens the recorded tensor is `grad_accum`, not the converted `src_tensor` the copy actually reads. Safe today (same stream), but imprecise.
