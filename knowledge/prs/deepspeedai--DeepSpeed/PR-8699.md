# Keep the buffers a model names for fp32 in fp32 under ZeRO-3

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8699) · state: closed · merged: True

## Original PR description

# Keep the buffers a model names for fp32 in fp32 under ZeRO-3 (`data_types.keep_in_fp32_modules`)

## Summary

Hugging Face transformers models list the tensors that must stay in fp32 in `_keep_in_fp32_modules_strict`
(and `_keep_in_fp32_modules` for fp16). transformers honors these lists when it loads a model by itself.
Under ZeRO-3 the lists are lost, so, for example, the MoE routing bias `e_score_correction_bias` of
DeepSeek-V3, GLM-4.5 and GLM-5 trains in bf16. bf16 cannot tell its values apart, so tokens are routed to
different experts than the model was trained with.

This PR adds `data_types.keep_in_fp32_modules` (default `"auto"`: use the model's own lists) and keeps the
listed **buffers** in fp32. Listed parameters are left to a follow-up PR, because ZeRO-3 needs to hold
partitions of two dtypes for them.

## Why the lists are lost

1. `deepspeed.zero.Init` converts every floating tensor created inside the context to the training dtype,
   buffers included, even ones created with an explicit `dtype=torch.float32`
   (`deepspeed/runtime/zero/partition_parameters.py:262-270`, `zero_wrapper_for_fp_tensor_constructor`).
2. transformers' ZeRO-3 loader then copies the checkpoint into those tensors in place
   (`transformers/integrations/deepspeed.py`, `_load_state_dict_into_zero3_model`: `buf.copy_(state_dict[k])`).
   It never reads the dtype plan it built from the lists, so the fp32 values are rounded to bf16.
3. Without ZeRO-3 the engine already keeps buffers in their loaded dtype (#8066), unless `buffer_dtype` is set,
   in which case it casts the listed buffers as well.

## How much it matters

The routing bias values sit close together at a large magnitude, where bf16 values are far apart
(checkpoint values, bf16 rounding computed per layer):

| model | experts | distinct bias values per layer, fp32 -> bf16 (median layer) | expert pairs whose order flips or ties |
|---|---|---|---|
| GLM-5.2 | 256 | 214 -> 7 | 45.9% |
| GLM-4.7-Flash | 64 | 32 -> 4 | 64.0% |
| DeepSeek-V4-Flash | 256 | 254 -> 6 | 64.8% |
| DeepSeek-V3.2 | 256 | 50 -> 50 | 0% (values near 0, rounding is small) |

13 transformers models list `e_score_correction_bias`: axk1, axk2, deepseek_v3, deepseek_v32, dots1, exaone_moe,
glm4_moe, glm4v_moe, glm4_moe_lite, glm_moe_dsa, hy_v3, mimo_v2_flash, solar_open.

Measured on GLM-4.7-Flash (47 layers, real weights, book text, 1 node x 8 H200, ZeRO-3, bf16):

| | bias as ZeRO-3 leaves it (bf16) | bias in fp32 (this PR) |
|---|---|---|
| distinct values, layer 1 | 3 | 23 (all of the checkpoint's) |
| loss at step 1, before any update, mean over 8 ranks | 7.1479 | 6.5999 |
| tokens routed to a different expert set (mean over 46 MoE layers) | 34.7% | 0 |

The same forward comparison without DeepSpeed (one GPU, transformers only, 320 sequences of 4096 tokens) gives
+0.52 to +0.60 nats from rounding the bias. After training starts, the difference in our 40-step runs was within
run-to-run noise; we did not test longer runs.

## What this PR changes

| file | change |
|---|---|
| `deepspeed/runtime/keep_in_fp32.py` (new) | read the model's lists (or the configured patterns), match names the way transformers does, convert buffers |
| `deepspeed/runtime/config.py`, `constants.py` | `data_types.keep_in_fp32_modules`: `"auto"` (default), a list of name patterns, or `[]`; validated |
| `deepspeed/runtime/zero/partition_parameters.py` | `zero.Init` converts the listed buffers back to fp32 when a module's `__init__` finishes, i.e. before a checkpoint is loaded into them; also for `zero.Init(module=...)` |
| `deepspeed/runtime/engine.py` | the mixed-precision cast skips listed buffers when `buffer_dtype` is set, and upcasts a listed buffer that arrives in a lower precision |
| `docs/_pages/config-json.md` | documents the key |

Name matching follows transformers (`core_model_loading.build_glob_alternation` then `re.search`): `*` stands for
any characters and a pattern may match anywhere in the full name. With `"auto"`, the lists are read from each
module that carries them; for a transformers model that is the `PreTrainedModel`, whose `post_init` has merged
its submodels' lists by the time `zero.Init` sees it.

Behavior change: with the default `"auto"`, listed buffers are now fp32 under ZeRO-3. The cost is the buffers'
size, a few hundred floats per layer for the routing bias. `"keep_in_fp32_modules": []` restores the old behavior.

## Tests

New `tests/unit/v1/half_precision/test_keep_in_fp32_modules.py`:

* name matching: `"auto"` under bf16 and fp16, explicit patterns with `*`, `[]` and fp32 training select nothing,
  invalid settings are rejected;
* ZeRO-3 `zero.Init` (2 ranks): a value loaded after the build is kept exactly in fp32; with `[]` it is rounded as
  before; other buffers are unchanged; the buffer stays exact through `deepspeed.initialize` and training steps;
* engine without `zero.Init`, ZeRO stages 0 and 3: `buffer_dtype` does not cast listed buffers; a listed buffer
  that arrives in bf16 is upcast; `[]` keeps the old behavior.

Run on 1 node x 8 NVIDIA H200, torch 2.8.0+cu126, transformers 5.15.1, on this branch (master c9e1b4d25 + this PR):

Hi @pengdurice,
Thank you for fixing this critical issue! The overall change looks good, but I found an issue we should address before merging.

In "auto" mode, `keep_in_fp32_pattern()` reads the FP32 declarations only from the module passed to it. If that module is a wrapper and only its child model defines those declarations, the function misses them and returns `None`. As a result, the child model’s listed buffers can remain in BF16 instead of being kept in FP32.

I opened to a [PR](https://github.com/pengdurice/DeepSpeed/pull/3) with a possible fix in case it's helpful. Feel free to use it directly or just as a reference for your own fix—whatever works best for you.
