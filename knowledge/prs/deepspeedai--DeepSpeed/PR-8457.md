# [AutoSP] Aggregate the causal LM loss and gradients over the SP group

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8457) · state: open · merged: False

## Original PR description

Aggregates the AutoSP causal-LM loss and gradients over the sequence-parallel group, so training matches the full sequence.

This PR now covers only loss and gradient aggregation. Label alignment for a causal shift *inside* the model (tohtana's `sp_compile.py` comment) moves to a follow-up draft PR. Until that lands, labels must be shifted on the full sequence before `prepare_autosp_inputs()`.

## Problem
AutoSP sharded the labels, and each rank computed a mean loss over only its own shard. This caused three problems:
- Every shard was weighted equally, even when the shards held different numbers of non-ignored tokens.
- A shard with only ignored tokens produced NaN.
- Gradients were not summed over SP ranks.
  - Implicit path (only `sequence_parallel_size` set): the engine sees no SP group and averages gradients over every rank.
  - Explicit mesh (`data_parallel_size` or `mesh_param`): `groups._get_sequence_data_parallel_group()` fell back to the DP-only mesh dimension, while the engine still divided by `dp / sp`, so SP contributions were never summed. This also affects Ulysses with `mesh_param`.

## Fix
- **New custom op `autosp::aggregate_loss`.** Each `F.cross_entropy` on the labels is summed per shard in FP32. The op all-reduces the loss sum and the number of non-ignored tokens over the SP group, and every rank gets the full-sequence loss. Both `mean` and `sum` reductions work. In backward the gradient is scaled only by `1 / total_valid` for `mean`, with no `sp_size` factor.
- **`groups`: summed SP gradients with a mesh.** With a `(data_parallel, sequence_parallel)` mesh and no `mpu`, the sequence-data-parallel group is the whole world. The engine then sums gradients over SP ranks and averages over DP ranks, which is the Ulysses convention.
- **`deepspeed.initialize`: one convention for both paths.** When the `autosp` pass is enabled with only `sequence_parallel_size`, it creates that mesh, so the implicit and explicit paths behave the same.
- **New check when the engine compiles AutoSP.** It raises if the SP size of an `mpu` or mesh differs from AutoSP's `sequence_parallel_size`.
- **Clear errors for unsupported loss arguments.** Class-weighted cross entropy and `reduction="none"` raise.

## Tests
`TestAutoSPCausalLoss` runs with world_size=4 (sp=2, dp=2). The two shards hold different numbers of valid tokens. Over 2 SGD steps, it checks the loss and the updated parameters against single-device training on the full sequences, with gradient clipping off. Cases:
- ZeRO 0 and 1, with `mean` and `sum` reductions, and keyword arguments
- an all-ignored shard
- an explicit mesh via `data_parallel_size`
- an SP-size mismatch, which must raise

`TestAutoSPHalfPrecisionLoss` covers the FP16 shard-sum overflow. The attention-mask gradient tests were updated to the summed-gradient convention.

Hardware: 8× Intel Arc Pro B70 (XPU), torch 2.14.0.dev+xpu, transformers 5.17. All AutoSP tests pass except two groups that fail identically on master in this environment:
- `TestAutoSPCompile`: dynamo fails tracing `accelerator.synchronize()`.
- `TestAutoSPEngineBackward`: the XPU op build needs C++20 (#8803).

This shape-based search still misses the conventional `logits[..., :-1, :]` / `labels[..., 1:]` pattern. The shifted target has length `S-1`, so the search walks back to the raw labels and inserts sharding before the shift, losing cross-boundary pairs such as `C → D` in `A B C | D E F`. This is an existing limitation that remains after the current fix.

I'm not sure what the most rubust and general approach would be. One approach is to use the semantics of the operations to determine where sharding is safe, rather than shape equality alone? Delaying label sharding might help, but the logits slice also needs to remove only the final position of the full sequence.

Do you see a good way to handle this pattern?

Thanks, you were right: with `data_parallel_size`/`mesh_param` the sequence-data-parallel group fell back to the DP-only mesh dimension, so SP contributions were never summed (this also affected Ulysses with `mesh_param`). Fixed in fe3853512 by making the engine own the SP reduction instead of compensating in the loss op:
- `groups._get_sequence_data_parallel_group()` returns the whole (DP×SP) world when a mesh is set and there is no `mpu`, so the engine sums over SP and averages over DP.
- `deepspeed.initialize` creates the same mesh when the `autosp` pass is enabled with only `sequence_parallel_size`, so implicit and explicit paths follow one convention.
- `autosp::aggregate_loss` no longer multiplies by `sp_size`.
- Compiling AutoSP raises if an `mpu`/mesh SP size differs from `sequence_parallel_size`.

`TestAutoSPCausalLoss` now also runs with an explicit `data_parallel_size` mesh (ZeRO 0 mean, ZeRO 1 sum) against the single-device full-sequence reference, plus the mismatch case.
