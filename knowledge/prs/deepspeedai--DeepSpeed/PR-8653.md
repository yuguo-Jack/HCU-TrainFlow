# Add an opt-in chunked causal-LM loss that keeps no full-vocabulary FP32 tensor

[Upstream PR](https://github.com/deepspeedai/DeepSpeed/pull/8653) · state: closed · merged: True

## Original PR description

## Summary

Adds an opt-in replacement for Hugging Face's `ForCausalLMLoss` that computes the same FP32 cross entropy without materializing any FP32 `[tokens, vocab]` tensor.

`ForCausalLMLoss` upcasts the whole logits tensor to FP32 and calls `cross_entropy`, which saves an FP32 log-softmax for backward; backward then allocates two more FP32 `[tokens, vocab]` tensors. At 8,192 tokens with Qwen3's 151,936-token vocabulary each is 4.98 GB, and all three are alive when backward starts.

`install_chunked_causal_lm_loss(model)` sets the model's `loss_function` to `ChunkedCausalLMLoss`:

- Forward saves only the given logits and one FP32 log-sum-exp per token. Backward recomputes the softmax and writes the gradient directly in the logits' dtype, which is the dtype the stock path casts its FP32 gradient to.
- On CUDA a Triton kernel does each pass in one read of the logits; a PyTorch backend does the same arithmetic in blocks of rows and runs anywhere. `backend="auto"` picks Triton when it can run, and naming a backend that cannot run raises instead of substituting.
- It only replaces the stock `ForCausalLMLoss` and refuses any other `loss_function`. Nothing changes unless it is installed.

## Semantics

As in `ForCausalLMLoss`:

- labels are shifted by one position, padding with `ignore_index`, unless `shift_labels` is given;
- class-index targets must be `torch.long`; floating-point, boolean and other non-long targets are rejected rather than silently converted. When `shift_labels` is supplied, only those actual targets are checked; unused `labels` retain the stock loss's behavior;
- rows whose target is `ignore_index` get zero loss and zero gradient;
- without `num_items_in_batch` the loss is the mean over non-ignored tokens (NaN if every token is ignored); with it, the sum divided by `num_items_in_batch`;
- the loss is FP32 and the gradient has the logits' dtype. FP32 gradients match; BF16/FP16 gradients can differ by one representable step where the FP32 evaluation order lands on a rounding boundary.

Beyond that:

- `block_rows` must be a positive integer or `None` for automatic sizing. Constructor, installer and direct calls reject invalid values before a backend runs, including when the selected backend would not use row blocking;
- targets may be strided;
- an out-of-range target fails through a device-side assert, as `cross_entropy` does, without adding a host synchronization;
- the range assertion uses the existing `required_torch_version` helper to call Torch 2.0's one-argument API and supply the message only on Torch 2.1+;
- a non-writable stock `loss_function` produces an actionable installer error, including property setters raising `AttributeError` or `TypeError`;
- backward with `create_graph=True` raises, because the gradient is computed outside autograd and a second derivative would otherwise be silently missing.

## Results (NVIDIA H100 80GB HBM3)

**Operator speed.** Loss forward plus backward alone at 8192 × 151936 BF16 logits, median of 40 alternating iterations:

| loss | time |
| --- | --- |
| `ForCausalLMLoss` | 20.82 ms |
| chunked, Triton | 2.76 ms |
| chunked, PyTorch | 35.23 ms |

**Memory, end to end.** AutoEP training of Qwen3-30B-A3B (48 layers, sequence length 8192, EP16 on 16 GPUs, BF16, ZeRO stage 1, reentrant activation checkpointing), four mirrored repeats per arm that differ only in the loss. Both arms also use the opt-in fused row weighting (#8644) and fused RMSNorm (#8645).

| | stock | chunked (Triton) |
| --- | --- | --- |
| peak allocated | 62.224 GB | 54.439 GB |
| peak reserved | 70.477 GB | 57.481 GB |

In the stock arm, the three FP32 `[tokens, vocab]` tensors account for 14.9 GB of the memory live at the peak.

**Step time, end to end.** In the same runs, the median step is 1763.6 ms stock and 1752.8 ms chunked (−0.6%, 95% interval [−6.0%, +2.9%]). The ~18 ms the operator saves is about 1% of the step, below what this comparison resolves, so no end-to-end speedup is claimed.

**Training loss.** Step 0 is identical. Over 24 steps the largest cross-arm difference is 0.0098, within the 0.0078–0.0124 spread between repeats of the same arm. This is a short-run check, not a convergence result.

These operator and end-to-end numbers were measured at the "Compute the chunked causal-LM loss with Triton on CUDA" commit. For the contiguous, in-range targets used there, the later commits add a no-op `.contiguous()`, a device-side range check of the targets, and a grad-mode check in backward.

The input-validation follow-up adds only API guards and compatibility handling. Triton kernels and both autograd implementations are byte-identical to the previously validated head. Existing memory/performance evidence is reused; no large-vocabulary allocation test or full E2E was rerun for this follow-up, and the historical timings are not new measurements of the added guards.

## Tests

`tests/unit/v1/runtime/test_chunked_cross_entropy.py`: the original 28 cases plus input/installer/compatibility regressions (50 cases total):

- loss and gradient against the stock `ForCausalLMLoss` for BF16, FP16 and FP32 on both backends, across Triton tile boundaries;
- `num_items_in_batch`, a given `shift_labels`, ignored rows (zero gradient) and all-ignored (NaN), matching the stock loss;
- a strided target on both backends; an out-of-range target raising on CPU, and failing the Triton backend in a subprocess instead of reading another row;
- `create_graph=True` raising on both backends, and a named backend that cannot run raising;
- no FP32 tensor larger than one value per row saved for backward;
- a small Hugging Face causal LM giving the same loss and parameter gradients with the installed loss, and a non-stock loss being refused;
- at the real shape (8192 × 151936 BF16), gradients 99.9% bit-identical and within one step, and a backward peak lower by more than two FP32 logits copies.
- zero, negative and fractional row blocks; non-long actual targets through direct CE, the causal-LM wrapper and installed HF models; supplied `shift_labels` overriding unused floating/absent labels; non-writable loss properties leaving the stock function unchanged; Torch 2.0's one-argument assertion contract; and fresh collection followed by a real fork and CUDA allocation.

Results:

- Current follow-up on NVIDIA H100 80GB HBM3, torch 2.10/CUDA 13.0, Triton 3.6.0 and transformers 5.12.0: plain pytest and `pytest --forked` each passed **49 cases, 0 skipped**. Only the previously validated large-vocabulary allocator case was deselected. Both runs retain the original loss/gradient tolerances.

Prior collection code with the fixed runtime independently reproduces the CUDA bad-fork error; the final import/fork/allocation regression passes in both test modes.
- The Torch 2.0 assertion branch is exercised against its documented one-argument collaborator signature under the current runtime, not claimed as a separate Torch 2.0 hardware qualification.
- 1× NVIDIA H100 80GB HBM3, torch 2.10 (CUDA 13.0), Triton 3.6.0, transformers 5.12.0: 28 passed, 0 skipped. The same tests against the runtime without the `create_graph` guard: 27 passed, and the Triton `create_graph` case failed because the second derivative was silently dropped.
- CPU, torch 2.14: 16 passed and 12 skipped (CUDA-only), with transformers 5.17 and with 4.51.3.
- `pre-commit run --files` on the changed files: passed.

## Not covered

- Label smoothing, soft labels, class weights, distributed or vocabulary-parallel cross entropy, and loss functions other than the stock `ForCausalLMLoss`.
- Second derivatives through the loss, which raise.
- Models other than the ones above (a small Llama in the unit tests, Qwen3-30B-A3B end to end), and long-run convergence.
