# 热点上限、融合与实现迭代

用于优化模式的计算算子工作线；仅分析模式交付同样的评估与待测方案，不启动实验。初步对齐融合粒度后继续本流程，不能以“已有融合实现”作为优化完成条件。

## 0. 进入计算算子工作线

先根据完整步和多 rank 证据判断是否存在显著空泡、通信暴露或提交等待。确有系统瓶颈时先处理对应关键路径，独立的算子分析可以并行；计算占主导时，将计算算子队列作为优化主线。用户明确收束系统调查时记录范围决定与遗留比例，不能把“停止调查”写成“空泡消失”。

原则是**谁占比大，先分析并优化谁**；每次修改后按新证据重新判断，不把阶段名或预选候选固定成主线：

| 端到端主要问题 | 下一步 |
| --- | --- |
| 空泡/提交/同步暴露最大 | 先追数据、CPU提交、同步与调度。GPU空白本身不能区分这些原因。 |
| 通信占比最大，未达同条件独立预期 | 检查现场配方、链路/库/消息与rank到达，再做有界修正。 |
| 通信已符合预期，仍有大量固有开销 | 重点检查可重叠的依赖、bucket/chunk/prefetch及通算融合；验证整步收益和计算/显存代价，不反复只测带宽。 |
| rank/专家/流水线负载不均 | 查并行切分、路由、microbatch、调度；可借鉴官方/AMD/华为/百度相关引擎实现，固定语义后验证。 |
| 计算占比最大 | 按下面的真实计算算子占比逐个分析上限和优化；无需优化的逐项说明依据。 |

通信驻留包含等待时不能直接当纯通信性能；不同区间重叠时先建立可信归因。未消除的系统问题保持可见，但无需等它全部解决才开始独立计算分析。

**先排序和裁决，再派发实现。** 不能因为某项容易写、已有 benchmark、成员熟悉或已开始编码就优先它。第一轮至少初查所有高占比项，完成下面的排序表后，才能决定下一项实现/硬件实验；纯源码和可达性调查可以先进行。初步融合、上限评估、同形状对照彼此提供证据，不代表任一工作线完成就可以跳过排序。

## 1. 先确定覆盖与优先级

固定完整稳态步、rank、前向/反向/优化器阶段和墙钟分母，建立累计覆盖端到端至少 90% 的热点集合。保留通信、CPU/等待和未归因区间；异步重叠按区间并集或有证据的归因处理，不能累加 CPU 包装、GPU 子 kernel 和并发 rank 的时长。无法完成关键路径归因时同时报告原始服务时间、并集覆盖和归因缺口，不编造可删除的时间。

从该集合中取出非通信算子，包括 copy、转换、清零、规约及混合通算 kernel 的计算部分。先按端到端贡献排序，再结合有依据的剩余空间、关键路径影响、数值风险和实现成本确定实施次序；跳过更高占比算子要写理由。每项保留：

| 内容 | 必须回答 |
| --- | --- |
| 调用契约 | 哪个固定源码/dispatch、shape、dtype、stride、次数、phase、alias/in-place、累积与保存状态？ |
| 贡献 | 哪个 rank、多少完整步、服务时间及端到端占比？重叠或等待能否分离？ |
| 上限模型 | FLOPs、字节量、延迟/依赖约束分别来自哪里？哪些流量仍未知？ |
| 当前效率 | 同口径当前时间、模型/独立差异、合理可达参考及其适用条件？ |
| 优化候选 | 复用、融合、省遍历、调 kernel 或改底层库，预计能减少什么？ |
| 结论 | 已尝试的改动、正确性/性能原件、最佳版本、剩余空间、继续或停止原因？ |

“覆盖 90% 的非通信 GPU 时间”不能替代上面的端到端覆盖；不能靠删掉通信和空白区间提高覆盖率。新 profile 或融合改变热点后重新排序，保留与初始基线的对应关系。

### 两层排序与选择裁决

1. 先按真实逻辑 op/调用链聚合贡献，再在其中按 phase、shape、dtype、实现拆开。大类名称如 `gemm_bmm` 不能直接作为开发任务，也不能把同一个逻辑算子拆成许多小 kernel 后低估它的总占比；嵌套 wrapper 和子 kernel 不重复计算。
2. 对高占比项初查已有实现、独立对照、可达参考与瓶颈。尚不知道上限的高占比项应优先补模型或做针对性 profiling，不能因为“不好分析”直接移到队尾。明确近上限、没有有意义的可消除开销，或已有具体阻塞处置时，才有依据转向后续项。
3. 分开记录**分析优先级**和**实现优先级**。分析先补高贡献/高不确定性；实施先做证据支持的整步收益较大者。估算 `调用数 × max(当前时间 − 参考时间, 0)` 只提供条件性服务时间空间；重叠/关键路径未知时不能把该值当实际整步收益。比较区间与不确定性，不用没有依据的精确评分制造排序。
4. 下一项候选必须写明：为什么先于更高占比项、预计消除哪些工作、证据缺什么、哪种结果会让它停止或降级。尚不能判断时先完成相应调查，不因候选已写了一半继续投入。

工作区/看板按以下列维护真实队列，owner 由实际独立工作决定，不为每行机械起 Agent：

| 排名 | 逻辑 op / phase / 实现 | 同口径贡献与分母 | 瓶颈证据与上限/未知 | 可兑现空间及限制 | 下一动作 / owner | 跳过更高项的理由 | 状态与原件 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 按实际证据填写 | 关联具体调用与源码 | 服务时间、并集/归因占比、rank、窗口 | 计算/访存/依赖/提交与匹配参考 | 区间或未知；不把理论差全当收益 | 补分析、复用、融合、HIP迭代等 | 无则写无；未知不能冒充近峰 | 未分析/待实测/迭代/保留/受阻 |

主控在启动新 kernel 实现或昂贵实验前审阅这张表；完成一个候选后更新其结果和下一项选择。该裁决通过既有 flow 候选/独立 review 和看板记录，不另建一套与其脱节的调度器。

## 2. 建立可解释的上限

对计算/带宽受限候选，可用 `max(FLOPs / matched_compute_rate, bytes / matched_bandwidth)` 形成理想时间下界，再加入启动、规约、同步、依赖、占用和实际访存路径的限制。峰值必须匹配 gfx、精度、指令类型与 shape；小 GEMV/点积、除法/开方、规约不能套用大 GEMM 的矩阵峰值。

分别记录硬件理论值、经核验的同类实测参考和本次观测。简单 copy 带宽、不同访问模式的最佳值仅作参考，不能直接称为某融合算子的可达上限。逻辑字节量与 PMC 测得的实际流量分别列出；混合瓶颈或参考条件不足时给区间/假设，效率未知就保留未知。不能把低效的当前独立测试自身定义为上限。

融合后重新计算工作量：少读写的中间量、仍需写回的梯度/状态、saved tensors、额外重算和寄存器压力。某个 kernel 消失不代表它的全部时间从整步消失，也不能把多项重叠收益直接相加。

## 数值失败时核对实际执行序列

候选与参考的数学公式相同，不保证编译后浮点结果相同。严格检查失败时，先保存最小失败输入、参数/状态、未更新区间和原始差异；区分索引/alias/越界、标量精度、FMA收缩、运算重结合及除法/开方实现。确认实际加载的库、设备函数、dtype/索引类型和目标 gfx，必要时沿 HIP Skill 检查原库与候选的真实 ISA；源码行号或编译选项名称不能代替实际二进制。

能从 ISA 建立具体假设时，用小范围可复现计算验证差异，再只修改该计算顺序或舍入边界。保留既定精度契约：要求逐位一致就继续逐位检查，允许误差则沿原先有依据的门槛；不能为了接受候选临时放宽容差，也不无依据地要求所有优化逐位一致。参考输出、高精度 oracle、padding/alias/梯度和多步状态各自验证，不让一种检查代替其余。未通过数值门槛不进入收益比较，不修改模型 dispatch。明确失败或无稳定收益的迭代也应保留为停止/回退证据。

## 3. 融合后仍需迭代

1. 沿生产者—消费者追代码与实际 trace，检查能否减少中间 tensor、全量遍历、launch 或同步；对齐 NV 融合接口/精度只是起点。先查 HCU TE、Flash-Train、Primus Turbo 和当前引擎已有实现，证明候选真正命中。
2. 首个候选完成局部正确性及干净计时后，更新其上限与瓶颈。若离有依据的可达水平仍显著偏远，继续优化，不能因“比 eager 快”就关闭。
3. Triton/编译后实现遇到向量化、布局、寄存器、同步或代码生成限制，且有显著可兑现空间时，进入 HIP 实现路线：缺基线用 `$hygon-hip-baseline-generator`，随后用 `$hygon-hip-kernel-optimizer`；仍适合 Triton 的用 `$hygon-triton-kernel-optimizer`。用相同输入/数值契约验证 HIP 候选，不默认 HIP 一定更快，也不静默收窄支持范围。
4. 每轮采用“测量 → 瓶颈假设 → 具体改动 → 局部验证 → 配对性能 → 机制复核”。瓶颈不清、收益停滞或明显低效时必须使用适用性能工具；XProf/XCompute 与 hipprof 的参数、指标公式和产物分别使用。ISA/资源检查辅助解释，不能代替实际 profiling。
5. 检查输出、输入/参数梯度、optimizer 状态和写回副作用；特别关注 FP32/BF16 舍入顺序、FMA、全局 norm/clip、溢出与跳步、alias、padding 和多 stream。不能为融合跨越未完成的跨 rank 规约，或改变 loss/优化器语义。超出候选支持范围须在部分修改数据之前回退。
6. 候选回接模型后核验实际 dispatch、额外显存和 profiler-off 重复收益，重新分析剩余空间。每轮做受影响的局部回归；稳定阶段统一验 loss，不逐小改动频繁长训。已验且未受影响的底层基线直接引用。

按真实实现选择处理方式：数学库 GEMM 先确认性能异常或明显低于合理可达上限；确需调优时按 [数学库日志与调优交接](math-library-tuning.md) 提取实际库日志打印的完整 bench 命令、库版本与性能依据，shape 分析表不能替代 tune 输入；rocBLAS 可按匹配教程 tune，hipBLASLt/grouped GEMM 等整理工单给用户协调数学库优化，不因占比高就默认重写 GEMM。attention/规约/逐元素等先核对已有库的接口与数值路径，适用就复用并复评效率，不适用或明显低效再进行有根据的融合/重写。工单不是完成优化：保留待处理状态、预计影响与当前可用实现，独立项继续推进。

不同算子可以并行开发和分析；共享设备上的计时串行。集成多个候选后复验组合，不能把独立收益相加。具体 shape/临时补丁留私有工作区。

## 4. 优化停止与阶段推进

尽可能逼近当前条件下有依据的可达水平，不预设所有算子都必须达到同一个峰值百分比，也不无限盲目扫参。逐项给出以下一种有证据的处置：

- **达到目标或接近可达水平**：报告匹配参考、剩余空间和为什么进一步收益有限。
- **多轮无稳定收益**：列出有机制依据的尝试、profile/ISA 原件、噪声与回退；保留最佳版本，解释限制来自何处。
- **数值/生命周期或资源约束**：说明不能消除的依赖、显存代价或数值失败；不能降低正确性要求来换速度。
- **仍有显著空间但受阻**：说明缺少的库/编译能力、环境、证据或专家决策，登记当前 flow 问题并汇报；标记未完成，不能当作“已优化到极致”。预算耗尽也属于待处理边界，而非性能达标。

主控在推进前检查高优先级算子的处置、未覆盖项、最佳候选和阶段数值结果。独立的容错验证可并行推进；它不代表优化阶段已验收。用户明确收束某条工作线时记录范围调整，不把该决定写成技术上的近峰结论。

新通用训练 HIP 算子在 HCU 现有库均无适用实现时，默认交付 **HCU Flash-Train**；扩展 TE 已有算子/优化器交 HCU TE，Primus Turbo 自有能力交其 HCU 仓。训练引擎保留必要调用、配置与集成测试。按任务约定完成整个工作流后再整合主仓/提交 PR；参见 [工程联动](hcu-library-integration.md)。
