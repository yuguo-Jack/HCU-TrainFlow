# 从性能证据到下一轮优化

用于 `analyze` 的分析交付，以及 `optimize/full` 的实验安排、候选验收和停滞处理。沿用当前 flow、BOARD 和 experience，不另建调度器；只分析模式不启动采集或实验。本页补充证据如何驱动决策，具体上限与实现交给 [算子迭代](operator-ceiling-iteration.md)，通信交给 [通信优化](communication-optimization.md)。方法来源及 HCU 差异见项目 `docs/practices/performance-methods.md`。

## 1. 先判断证据是否仍适用

保留三个对象：**初始正确性/性能基线、已验收最佳组合、当前试验候选**。初始数值 oracle 不随候选滚动；性能既与当前最佳比较增量，也与初始基线比较累计净收益。若数据、训练目标、配方或环境发生实质改变，显式建立新比较 context，旧结果只能作参考。

从官方 Wiki、HCU 大库和符合收录规则的本仓经验中找最近配方，逐项核对模型语义、硬件、拓扑、精度、分支、依赖和场景。近似匹配只生成候选；每放宽一个条件记录差异，不能继承其性能数字或验收状态。优先复用已部署 HCU 脚本，再考虑有证据的局部调整、补丁移植、依赖适配和独立重编。

| 改变/事件 | 必须重看的证据 | 可复用的部分 |
|---|---|---|
| TP/PP/CP/EP、微批、累积、序列长度/packing、重算、优化器或精度变化 | 实际 rank 组、phase/shape 分布、容量和完整步热点；语义变化另立比较条件 | 未受影响的独立算子数值资格 |
| graph/compile、融合、backend、调用接口或数据布局变化 | 实际 dispatch、调用次数、输入/输出契约、稳态 trace 与源码映射 | 原始 oracle、未变依赖的构建证据 |
| 单 kernel 的 tile/流水线/寄存器变化 | 本 kernel 的当前计时、资源和瓶颈证据；集成后的短窗口 | 调用契约不变且无漂移的其他算子证据 |
| 多个候选累积、明显收益/回退、热点转移或持续异常 | 当前最佳组合的完整步与多 rank 分布，重排优化优先级 | 原始结果仍保存，但注明属于哪个快照 |
| 仅注释/文档修改或完全相同运行条件的断点接续 | 先核对源/制品/配方/输入身份与测量条件 | 可引用一致的已有证据，不机械重跑 |

不设置“一定要涨到 5% 才刷新”之类通用阈值；结构变化即使总步时相近，也可能让旧归因失效。一次采集失败记录原因、工具和缺项，有界重试后换适用采集方式或升级；旧 trace 不冒充当前候选。需要细查 kernel 瓶颈时，缺少 profiler 不能把猜测写成已确认。

## 2. 分开采集映射、稳态时间和计数器

- **调用映射**：必要时用短窗口 CPU stack、shape 或 eager/graph-off 调试运行定位 Python → dispatcher → 底层源码。它会改变开销和融合，不能把这里的时间搬到正式图执行。
- **正式稳态剖面**：使用任务真实 graph/compile、并行和 overlap；逐 trace 核对完整 CPU step、实际步数、rank、事件非空、输出新鲜度和丢失记录。不同 rank/phase 保持同口径，不能从旧目录碰巧找到文件就认定本次成功。
- **针对性计数器/指令分析**：仅对已选高价值问题使用匹配 gfx/工具版本的 XProf/XCompute 或 DTK hipprof。replay 可能改变并发、缓存和通信依赖；尤其 collective 不单独重放到等待 peer。看 HCU 手册和现场帮助决定模式，采样的 CU/SE 和范围明确保留。
- **正式性能计时**：关闭 profiler、trace hook、debug 同步与密集日志，按预先约定的重复/配对方案测量。诊断采集不是加速数字来源。

映射 trace 与正式 trace 通过 source/dispatch、shape/dtype/layout、phase、graph 特化和调用序列对应。签名重复、融合改变或关联不唯一时标为候选映射，继续读源码/做定向标注；不能按 kernel 名或相邻顺序强行一对一。TrainFlow 的归因导入只接受同一原 trace/窗口的映射；跨运行映射是人工查证线索，不能伪造 event/hash 导入。

## 3. 用三张互相关联的表形成优化计划

不要求复制三份原始大表：在现有报告/BOARD 维护关键行，链接 TraceLens 原件和 operator key。

| 表 | 每条候选必须说明 |
|---|---|
| 热点—源码—上限 | 逻辑 op、phase、rank/shape 分布、真实 backend/源码；服务时间、端到端分母、覆盖/未知；工作量/参考、效率与可改善空间 |
| 依赖—重叠机会 | producer → consumer → join、哪个 rank 暴露尾部；输入何时就绪、wait/event/collective 协议；共享 CU/HBM/NIC 与显存代价；为什么可能缩短整步 |
| 融合—契约机会 | 原调用链与已有融合、适用 guard；可省的 launch/中间量/遍历，以及新增计算、转换和 buffer；fwd/bwd、saved tensor、alias/RNG/数值边界；复用目标或实现 owner |

邻近 kernel、同名 op 或 stream 重叠只提供候选线索。重叠部分可能拖慢另一关键任务；“已隐藏”不能只由区间相交证明。合成层级显示泳道不代表真实执行 stream。图重放减少提交开销，融合减少中间量/调用，算子调优改善设备执行，三者须分别说明消除的成本。

**训练重点**：前向、输入梯度、权重梯度、优化器、重算和通信尾部各自看实际负载。对动态 shape/MoE 记录频次与 token/专家负载分布，至少区分主耗时桶、最慢/不均衡桶和支持边界；不要只优化一个容易测的 shape。多个小 kernel 若属于高贡献逻辑链，可作为融合候选整体评估。统一 kernel 名不能掩盖多个特化或不同 backward 调用。

## 4. 把上限空间转成可证伪的实验

先按端到端贡献分析最高项，再决定实现顺序。若某部分确在串行关键路径，占步时比例 `f`、局部加速 `s`，条件性整步加速为 `1 / ((1-f)+f/s)`；纯服务时间占比或等分重叠归因不能直接代入。没有因果证据就给乐观空间、限制和未知，不把估计当承诺，也不把多个候选的预计收益相加。

每轮在既有候选记录中写清：

1. 观察到了什么、支持/反证是什么；预计改动哪个瓶颈或依赖。
2. 只改哪一类变量；若多个变量形成必要组合，分别保留整体比较和能做的消融，不把组合收益归给某一个开关。
3. 最少什么证据能证明方向有效；结果怎样会否定它；设备时间/编译预算与停止点。
4. 当前最佳与候选的快照、制品、实际 dispatch、局部数值、内存和 profiler-off 配对原件。
5. 观察是否符合预测；保留、回退、补证据还是换方向，及下一项优先级。

小算子检查完整 API 的分配、清零、layout 转换、Python/C++ 包装、同步和 graph replay 开销。只计设备 kernel 不能证明整个 op 变快。消除清零前证明所有可读位置每次都被写入；复用 buffer 要检查多 stream、重入、graph、backward 和异步消费生命周期。不能为了训练性能移除 autograd 或依赖正确性检查。

## 5. 接受候选与组合的条件

- 先证明候选在预期 **phase/shape/rank** 生效，再花时间正式测量。源码存在、环境变量已设、调优表加载或 kernel 编译成功均不是命中证据；同时检查未支持条件下的安全 fallback。
- 局部正确性面对固定 oracle，包含实际输入/梯度/更新状态；组合后仍对初始数值基线验证，防止每轮小偏差累积。优化器算法、cast、累积、mask 和重算 RNG 不因优化改变。
- 计时比较至少遵守 CLI 所需的三组匹配重复；实际重复数、预热、配对顺序、稳定性门槛由站点噪声和期望收益确定。必要时 A/B/A 检查漂移；同一进程的多次迭代不等于多个独立实验。不得以 min/max 不重叠自动宣称统计显著，也不照搬 0.5% 通用门槛。
- 不能分辨的微小收益保存为**待组合验证候选**，不替换已验收最佳。只有契约兼容、无已确认数值/内存/性能回退的项才考虑组合；组合对当前最佳及初始基线测量，失败做有界拆分/消融。不能以若干不确定结果相加报收益。
- 保留每个重要 shape/阶段的退化和最紧 rank 显存，不用一个 geomean 或平均吞吐隐藏尾部、长序列、保存/恢复峰值。支持范围变化明确告知；阶段稳定后统一验 loss，长训质量另按任务目标验收。

`iteration-kept` 是局部迭代筛选，允许约定的回退幅度，不是统计增益证明或生产验收。未设稳定性标准时结果明确 `not-specified`；有实际优化决策前补足测量协议。分析器输出只辅助审查，主控依据原件和独立复核接受集成。

## 6. 无进展时换机制，不能无限扫参数

有实测改进且机制成立时，沿同一假设做有界细化；多轮无稳定收益、重复编译/数值失败、没有可执行改动，或预测与实测持续背离时，回到最佳版本复核 profile 和假设。分别判断：证据过期、测量噪声、实现/依赖受限、当前策略不适用，还是已接近可达水平。

换方向可以是调整调用/布局/算法组织、复用另一个已验证后端、改善资源分配/重叠，或交数学库调优；应由新证据驱动，不为了“多样性”固定切换语言或增加 Agent。旧失败记录仅对其版本和条件有效，新编译器/调用契约变化时可说明新依据后重试。

退出前核对高贡献项处置、未解释空泡/通信、≥90% 覆盖缺口、当前最佳和阶段数值。尚有明显空间但缺证据/能力/预算时登记阻塞并汇报，不能把平台期、预算耗尽或别人的速度数字称为 HCU 硬件极限。只把符合知识架构要求的可复用经验和最终里程碑写共享 Wiki；逐轮假设、失败和临时补丁留私有任务档案。
