# 引擎原生能力调优与实现迭代

用于预训练、SFT、RL 和 Torch 原生训练的分析优化阶段。开始时先系统检查**当前训练/推理引擎已有的优化能力及其配置**，与并行切分、显存预算同等对待；在编写新实现前，优先验证适用的已有机制。参数不仅是数值，也包括后端选择、模块替换、调度策略和功能开关。

“全面检查”指覆盖当前任务相关的能力类别，不是枚举所有参数或穷举组合。先复用适配阶段的有效配方、基线与既有 profile；必要时短时采样，按主要瓶颈和预期整步收益选择少量实验。已有可信热点可直接推进，不等全表填完。仅分析模式完成查证、排序与建议，不擅自改参数、应用 PR 或启动实验。

选项与 PR 的比较服从项目[双线方法](../../../docs/practices/engine-delivery-tracks.md)选定的执行基点：稳定线维护已验 release/插件组合；快速线先验证指定 commit 的原生能力，有预算再迁移高价值 HCU 独有优化或候选 PR，与必要适配 patch 分层交付。该可选范围仅指额外机制移植；端到端分析、调参、热点处置和原有精度验收两条线相同。查到新机制不自动切换基线。

## 1. 查清有哪些能力，以及当前到底用上了什么

先复用适配阶段已核验的配方；需要补查时，通过 HCU-Knowledge 查匹配模型、硬件和版本的 Train Cookbook 配方/脚本，结合所选 HCU 仓启动脚本与现场环境脚本还原配置。通信环境变量尤其要核对加载/覆盖顺序及各 rank 的实际值，不拼接不同版本或站点的变量组合。再从实际启动链、模型配置和执行分支出发，沿以下路径核对相关候选：

```text
启动参数 / 配置文件 / 环境变量 / 默认值及覆盖顺序
    → 配置解析与实际各角色、rank 的有效值
    → 特性条件检查、模块选择与 backend dispatch
    → 实际加载的库 / 编译产物 / kernel / 调度路径
```

参数被解析、设置日志出现或源码含有实现，都不证明实际生效。检查模型/shape/dtype、训练或推理阶段、硬件、并行布局、依赖版本和编译选项限制，以及自动选择、静默 fallback、被 launcher 覆盖等情况。默认已启用且命中预期路径的能力也要识别，避免把它重复当成新增优化。

| 候选来源 | 需要确认的状态与证据 |
| --- | --- |
| 当前 HCU 分支和现场配方 | 以实际部署的版本、调用者和脚本为准，查 HCU 特有优化及与官方同名参数的差异；通过 HCU-Knowledge 查证，必要时读对应源码 |
| 官方已合入机制 | 分清 merged、released、当前执行版本可用；读匹配版本的教程、配置解析、调用链和测试，不能照搬最新文档的开关 |
| 官方开发分支或审核中的 PR | 固定 PR/提交、基线、review 与依赖；它是实验性候选，可能需移植代码，不能写成已支持参数。适用且有价值时按任务范围隔离验证，不直接替换运行中的分支 |
| 其他引擎的实现 | 按项目[优化参考表](../../../docs/optimization-reference-map.md)联查 DeepSpeed、TorchTitan、Primus、MindSpeed、LoongForge 等，借鉴机制及触发条件；其配置名、默认值和平台实现不能直接套用 |

本地资料不足时用 Wiki 搜索联查官方教程、PR 描述/review、最终源码与实际依赖版本；HCU 实现查大知识库及当前分支。仅因资料更新，不自动升级训练依赖或更新 HCU 大知识库。

## 2. 按能力类别检查，不只看并行与显存

下表是检查方向，**不声明所有引擎/HCU 版本均支持这些功能，也不要求每类都试验**。不适用项简记原因即可；实际参数名和值从当前代码、帮助和配方取得。

| 类别 | 原生机制和可调因素举例 | 重点核对 |
| --- | --- | --- |
| 并行与容量 | TP/PP/DP/CP/EP/SP、微批/累积、流水调度、重算、状态分片/offload | 最重 rank 峰值与余量、通信/空泡、shape；沿用完整模型容量判断，不为调参随意改模型 |
| 算子与模块后端 | Attention/MoE/优化器后端、融合、布局、权重/中间状态缓存、低精度实现 | 真正命中的前后向和更新路径、依赖库、数值/缓存生命周期；不靠改优化器算法或降低精度标准换速度 |
| 执行与编译 | compile 范围、图捕获/重放、特化与缓存、host/设备调度 | 编译与预热单列，断图/重编译、动态形状、捕获兼容性；graph 与融合的收益分别解释 |
| 通信与计算协同 | 梯度/参数同步、overlap、bucket/chunk、预取、异步完成与队列设置 | 暴露尾部、同步协议、竞争和额外 buffer；`GPU_MAX_HW_QUEUES` 等以目标 runtime 和实测为准 |
| 输入、保存与状态管理 | worker/预取/packing、数据搬运、异步保存和卸载 | 有效 token、mask、数据顺序、恢复一致性及周期性停顿；不能删掉必要保存来美化吞吐 |
| RL 的推理与训推协同 | 推理 batch/调度、KV/cache、后端/图模式、sleep/唤醒、权重传输、角色资源分配 | 同时查训练与推理引擎的原生配置；看完整 RL 迭代和等待，不以生成 tokens/s 代替总体收益；保持 policy version、采样/更新比、logprob 和样本时效契约 |

参数之间可能互斥或依赖：融合后端影响图捕获与临时内存，重算影响通信可隐藏窗口，微批改变算子 shape，推理缓存影响训练可用显存。把必要组合与互斥关系先写清，再安排实验；不要独立打开全部“优化开关”后猜收益来源。

MoE 的专家计算检查是否经过 TE grouped GEMM，以及能否复用 hipBLASLt 的 grouped GEMM 后端。具体开关、默认行为和支持条件按实际引擎/TE/数学库版本查询 HCU-Knowledge 并核对消费者源码，不把历史环境变量当作所有版本的必设项。适用时验证实际分派、前后向数值及整步收益；已命中仍有性能缺口，再按[数学库调优](math-library-tuning.md)提取真实分组复现交接，不直接重写已有能力。

卷积等 MIOpen 热点还要核对 layout、Find/benchmark、workspace 与缓存是否适配当前 HCU 调用路径：按[数学库调优](math-library-tuning.md)先比较已有选优能力，再决定 size 交接。搜索预热与正式运行分开；框架开关、HCU Find 模式和 AMD 同名参数不默认等价。rocBLAS 的自动选优结果同样回到真实引擎 backend 与配置命中验证，不能把独立工具的收益直接计入整步。

## 3. 在现有看板维护候选与处置

使用当前 BOARD/DETAILS 和实验记录，不另建必填数据库或要求每个开关单独审核。每项有价值候选保留以下最少信息，原件可链接复用：

- **机制与来源**：对应瓶颈、教程/PR/源码、版本、merged/open/HCU-specific 状态。
- **实际配置与路径**：默认/当前有效值、候选差异，消费者及当前 backend；启用条件、依赖/互斥项。
- **实验和验收**：预期整步改善及代价、最小可证伪实验、局部数值与显存检查、无 profiler 对照、回退方法。
- **结果与下一步**：已启用且有效、可试验、被覆盖/回退、依赖缺口、当前不适用，或已验证保留/回退；引用实际命中证据和测量，不把“尚未验证”写成不支持。

按主要端到端瓶颈及可兑现收益安排优先级；同等收益下优先低成本、已支持的原生机制。原生选项不能解决当前主要问题时，可直接进入相应实现优化；不为完成清单先试低收益参数。独立方向可并行分析/实施，共享 GPU、NIC 或存储上的性能测量按隔离条件安排，组合回到共同基线验证。

## 4. 调参与后续实现相互反馈

```text
固定基线 + 当前能力/有效配置 + 稳态瓶颈证据
    → 优先验证适用的原生优化项（含必要组合）
    → 核对命中、局部正确性、显存和整步收益
        ├─ 有收益：保留最佳组合，重排剩余瓶颈
        ├─ 无收益/退化：解释条件与竞争，回退或换方向
        └─ 有价值但缺能力：追引擎调用 → 底层依赖/接口缺口
             → 复用已有 HCU 能力，必要时移植/实现/优化
             → 回到原参数/后端选择与相关组合重新验证
    → 稳定阶段统一验 loss；按任务目标决定继续或交付
```

依赖缺口按预期收益排序。阻塞一个选项不等于阻塞所有调参：继续检查能独立推进的候选；不提前补齐全部底层库，也不在有明显缺口时只写“参数无效”就结束。

例如，某融合选项在官方实现依赖特定 TE/cuDNN 路径，而当前 HCU 因条件检查回退。先确认原调用链、fwd/bwd、saved tensor、cast/累积和数值要求，再按[库联动与修改归属](hcu-library-integration.md)查已有 HCU 实现。可复用就接入；确需新实现或补性能时，分别衔接 HIP baseline、HIP optimizer 或 Triton optimizer Skill。完成局部与模型集成验证后，**重新检查该选项是否命中，并回调受影响的 compile/graph、overlap、微批和显存设置**；原来不可用或无收益的组合可能已改变。这个例子不代表所有融合均依赖这两个库，归属仍由实际消费者决定。

候选 PR 或底层实现改变调用、融合粒度、rank 分组、shape、精度或资源竞争时，按[证据刷新规则](evidence-driven-loop.md)补采受影响 profile、重排热点与上限；旧证据保留身份，不冒充新组合结果。新后端显著改善当前热点后，不再机械优化已经退出主要占比的旧实现。

## 5. 验证、停止与后续维护

每次尝试先做必要的配置/dispatch 与局部数值检查，再进行匹配条件的短时筛选。可保留候选按既有[证据闭环](evidence-driven-loop.md)和[验证指南](validation-diagnostics.md)做正式无 profiler 对照、组合验证与必要消融；同一假设的连续试参不逐次 RLCR，也不逐次长时验 loss。

冻结的初始数值基线、模型结构、优化器、有效全局 batch/token 和质量标准不因调参降低。改变精度策略、采样/数据语义或学习配方时，先确认属于任务允许的优化范围并单列对照条件，不能作为等价配置静默替换。稳定阶段统一验 loss；只看平均吞吐不够，还要看最慢 rank、显存余量、尾部以及保存恢复受影响范围。

原生调优后达到目标，可以不开发新 kernel，但仍需完成当前模式的热点解释、高贡献项/≥90% 覆盖与质量验收，给出停止依据；显著未解释空间、被阻塞选项和未验组合如实交接。共享 Wiki 只提炼可复用经验或最终里程碑，逐次参数实验留任务档案。

引擎、底层库、HCU 配方或相关 PR 状态变化后，更新 Skill 时联动核对参数默认值/覆盖链、条件检查、后端选择、依赖及数值边界，修订失效的用法与关联入口；运行任务只重评受影响候选，不重复完整调参、不自动升级执行环境。
