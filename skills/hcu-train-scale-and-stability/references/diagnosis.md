# 训练故障诊断与恢复验收

用于所有阶段的异常调查，也可由本 Skill 独立执行 `diagnose`。先按症状读对应分支；不把全文所有检查都跑一遍。这里补充排障方法，不扩大当前任务的执行、重启或节点管理权限。项目级证据、命令回执和中间结论留在任务 workspace。

本指南依据 [HCU 与官方证据入口](evidence-sources.md) 整理。文档/源码核对、离线场景复核、现场复现与修复验收分别记录；这些方法尚未覆盖真实 HCU 的全部故障类型。既有有界恢复实验的范围见项目 `docs/capabilities.md`。

## 1. 接手异常：先确定是哪一次任务出了什么问题

1. 固定 task/context、attempt、源快照、镜像/实际库、节点与 rank→PID→设备映射、时区与时钟偏差。PID 还要配启动时间、容器/作业身份，避免读到重启后的同号进程。
2. 记录最后正常 step、首次异常、后续超时与恢复动作；保存异常前后的全部必需成员日志。先核实日志是否完整、轮转、缓冲或混入旧 attempt，再比较时间。最先报错的 rank 是调查入口，不一定是根因。
3. 确认训练是仍在运行、已退出、正在恢复，还是观察链路失联。用调度/容器状态、进程身份、设备与真实 step 交叉核实；SSH 超时、日志静止或一次心跳各自都不充分。
4. 沿当前部署协议确认恢复负责人、已执行动作和下一截止时间。既有容错可按原规则处置；Agent 不启动第二个恢复器，也不为采证无限拖延既定恢复。尽可能在日志/现场被替换前保存有界证据，不能保存的项标缺失。
5. 给出初始分流、最多几个有依据的假设和下一项最能区分假设的检查。先只读，再做已授权的局部可逆实验；会暂停进程的 attach、信号、注入、重启或节点状态修改要符合现场处置范围。必要权限缺失时说明具体入口，其他只读调查继续。

### 最小事件记录

| 项目 | 必须能回答的问题 |
|---|---|
| 身份和范围 | 哪个模型/配方/数据版本、context/attempt、哪些 rank/节点、什么阶段？ |
| 时间线 | 最后正常、首个异常、其他 rank 的反应、容错动作、当前状态分别何时？ |
| 条件 | gfx/DTK/驱动、实际加载库及构建、并行组、shape/dtype、关键非敏感环境？ |
| 证据与缺口 | 日志/栈/指标/转储原件在哪里，哪些成员缺失，采集是否改变时序？ |
| 假设与查证 | 支持/反证各是什么，查过哪些 KB 页面/PR/源码版本，下一检查如何区分？ |
| 处置与验收 | 唯一 owner、预算/截止、回退、重启/隔离范围、怎样证明恢复有效？ |

在现有 BOARD/report/experience 中记录，不另造平行任务状态机。未确认原因可交付诊断报告；不能写成修复完成。

### 1.1 每轮必须缩小假设，不能只增加日志

维护少量当前假设：支持证据、反证/未覆盖条件、下一项区分实验、成本/副作用、停止点。一次检查后更新“已排除/仍可能/新增”，并说明排除范围。例如某两节点固定消息单测通过，只排除了该条件下的可复现链路失败，不能排除模型异步顺序或其他 NIC。没有新信息的同一命令不要无限重试；命令超时先核实原采集是否仍运行。

先保存**能够重放的失败条件**：失败前可用 checkpoint、数据 manifest/游标、样本/shape、随机状态、优化器/低精度状态、phase、并行组和加载制品；只保存故障末尾日志通常不够。不得为取证从头复制全部训练数据。间歇性并发问题还需保留队列/stream/调用顺序和失败频率，不能因单进程单样本不复现就否认故障。

重放在授权的隔离资源进行，逐步缩小且保持必要依赖；重放失败记录缺少什么。线上无法重现时可先做有界被动观察和源码排查，不把“先重放”变成停止所有调查的硬门槛。仅从可信任务来源读取可执行的 checkpoint/pickle，采用引擎支持的安全加载方式；不为复现关闭通用安全检查。

采集产物为空或权限失败时，检查目标身份、namespace、工具实际支持、输出目录/写盘结束和选择过滤器。日志、栈、设备转储、计数器是不同证据；降级明确缺了什么，不能将“工具 exit0”或“没有检测报告”变为正常结论。遇到需暂停/重启的工具，遵守该任务已确定的处置边界。

### 1.2 版本回归与节点问题的区分实验

- 有已知好/坏版本时，冻结相同数据、硬件与配方；先确认好/坏可重现，再在独立 checkout 有界二分。每个点记录子模块、依赖和构建身份；不能构建或缺依赖是 `skip/unknown`，不是 good。间歇失败预先约定重复/观察窗口，二分结果是引入范围，仍需读差异验证根因。
- 疑似硬件/网络时，在调度许可与唯一容错 owner 下，用已知健康基准做“同负载/绑定换节点”“同节点换绑定/链路”的最小交叉矩阵。记录源/目的、NIC、rail、方向、消息、设备和负载；共同交换机、存储或配置可能解释多个失败，不能自动给所有节点贴故障标签。
- 保留失败矩阵和状态增量，区分偶发与稳定复现。卸载驱动、重置卡、清缓存、移除 taint、终止进程不作为自动诊断动作；确需执行按部署授权和恢复协议处理。修改后复验原失败条件及邻近边界，再判断能否重入。

## 2. 选择症状路线

| 首要现象 | 首先排除 | 进入 |
|---|---|---|
| 初始化卡住、collective 超时、训练不走 step | 成员没启动/已退出、数据或保存阻塞、观察源错误 | §3 |
| 段错误、abort、VMFault、设备断言 | 主机 core 与设备转储混淆、异步错误滞后、符号不匹配 | §4 |
| OOM、RSS/显存持续增长、突然 SIGKILL | cgroup/主机 OOM、真实容量峰值、缓存平台期 | §5 |
| NaN/Inf、loss 或梯度异常、恢复后偏离 | 数据/配方/状态不同、首个错误已传播 | §6 |
| 步时退化、周期性慢、扩卡收益不足 | 测量不同比、错误重试、节点/存储慢、负载不均 | §7 |
| checkpoint 失败、反复重启、健康但未恢复 | 存储/元数据、控制链未完成、观察对象仍是旧 attempt | §8 |

故障可以跨路线。例如一个 rank 被主机 OOM 杀掉，其余 rank 的 RCCL 超时是后果，先调查退出者，再核对通信是否有独立问题。

## 3. 卡住和分布式超时

### 3.1 从成员和阶段定位

- **启动前/初始化：** 核对所有成员是否进入相同入口、world size/rank/local rank、rendezvous 地址/端口、设备可见性、工作目录与激活链。核对启动器退出与导入异常；不要先无限延长超时。
- **取数据/CPU 等待：** 比较各 rank 的数据游标、样本/序列长度、worker 状态、CPU/内存压力和存储读错误。检查数据路径是否各节点指向相同内容；同名路径或文件大小相同不证明版本一致。保留数据 manifest、分片/样本 ID 和必要校验，避免全量 dump 数据。
- **前后向/更新：** 取得同一时间窗口的重复 Python/native 栈、最近正常算子、设备活动和 stream/event 依赖。重复栈是否有进展，比一张停在同步函数的栈更有判断价值。
- **保存/评估：** 查 writer、异步上传、barrier、只有部分 rank 进入保存/评估等路径，转 §8；不要把等待 I/O 自动归为通信库故障。

先复用现场 Cluster Manager `stack-analyzer` 和已安装采集入口，核对其版本、PID namespace、rank 映射与采集权限。若使用 py-spy/pstack/调试器，先读实际帮助并评估 attach 停顿；没有预装 Python 信号处理器时，不发送猜测的 dump 信号。

### 3.2 复核通信契约

1. 对照**真实 process group**和其成员，核对 collective 顺序、类型、dtype、count、root、split sizes 以及 async work 的 wait/stream 依赖。PP send/recv 检查匹配的 peer、tag/顺序；all-to-all 检查发送与接收矩阵，不要求所有 rank 的数据形状相同。
2. 使用同一 communicator 和同一轮次的日志比较。地址形式的 communicator 指针只在本进程内有意义；global/local rank 映射必须一致，不能把所有进程的 opCount 直接混算。
3. 只有日志覆盖完整、初始化映射明确且格式被正确解析时，才能认为“某 rank 少下发”。日志截断、过滤或 graph 相关计数差异须先排除。零利用率和等待中的通信 kernel 只是线索。
4. 若某 rank 未到调用点，回查其前序数据、算子、异常/退出及控制流。HCU 知识库有数据不一致造成 collective 参数不同的案例；不能通过调通信性能变量修复此类契约错误。
5. 所有成员正确下发仍不推进，才结合实际加载的 RCCL/插件/runtime、拓扑/传输、proxy 进度与设备状态缩小到实现层；必要时阅读当前 HCU 分支的 enqueue、transport、proxy 及调用方源码。

还要区分 host API 返回、通信设备工作完成、消费 stream 的依赖建立、watchdog 观察到完成四个时刻。异步 `Work.wait` 可能只插入设备依赖，不能据返回或单个 event 推断全组成功。graph 的监控 event 与消费 join event 可能用途不同；先查现场 TorchComms/PyTorch 后端，不删除依赖来“修复”卡住，也不假定所有超时从 Python 调用时开始计时。HCU 查 `torchcomms-async-functional-watchdog` 与 `pytorch-memory-stream-graph-lifecycle`。

诊断复现可在确认版本支持后使用 `NCCL_DEBUG=INFO`、`NCCL_DEBUG_SUBSYS=INIT,COLL`、按 host/PID 区分的 `NCCL_DEBUG_FILE`；还需按 attempt 分目录。HCU RCCL 使用 NCCL 风格变量，不代表 NV 工具都可用。PyTorch 的 `TORCH_DISTRIBUTED_DEBUG`、flight recorder 等先核对当前 HCU 构建；`monitored_barrier` 的官方支持范围是 Gloo，若用它需在可修改的复现程序中由相同成员按相同顺序创建并使用诊断组，不能对挂住进程临时“插入 barrier”。这些都是诊断开销，不用于报性能收益。

### 3.3 复现与隔离

按证据选择一个区分实验：相同通信契约的 rccl-test/最小程序、相同节点换绑定、固定绑定换节点、或关闭一个可疑 graph/overlap 路径。保持消息/dtype/组/拓扑可比，预先核对峰值内存及资源占用。基础通信通过不能排除训练中的异步顺序、生命周期和并发问题；新复现仍保留引发问题的依赖。节点异常判断需交叉对照，不能因所有失败组合共享一个节点就不查它们共同的 NIC/交换机/存储路径。

## 4. 崩溃、core 和设备错误

1. 先辨识异常类型与退出来源：Python 异常、主机 signal/core、cgroup/调度终止、HIP 异步错误、HSA/驱动故障。记录最早错误及相邻调用，而不是只看 launcher 最后打印的失败。
2. **主机 core：** 核对 core 是否生成/完整、core_pattern 或系统转储服务、任务进程资源限制；读取现有配置，避免为一次调查修改全机设置。使用对应可执行文件、共享库、build ID 和调试符号；普通主机 core 不保证包含 GPU 状态。
3. **HCU 设备转储：** 查询当前 DTK 手册和 `hipprof --help`；确认现场 runtime 支持时，才在有界复现中配置 `HSA_ENABLE_COREDUMP` 等能力。内存快照额外评估空间与落盘时间，存到任务授权位置。`HSA_COREDUMP_SAVE_DIR` 在旧材料有缺陷记录，不直接从旧示例抄到新环境。
4. DTK 26.10 文档包含 `hipprof --input-core <core_0>`，历史版本曾废弃后恢复该接口。只对匹配格式的异构转储使用；看 fault_info、queue、kernel/code object、参数和地址，不把它当所有 ELF core 的解析器。设备调试优先查询现场 `hipgdb`/对应手册，不能默认 AMD rocgdb 与 HCU 工具互换。
5. VMFault 可由越界、失效地址、异步释放/跨流生命周期、设备断言等触发；核对实际 kernel、参数有效区间、布局/别名、同步和源代码断言。某个 HCU 通信实现的 assertion trap 也可能表现为 VMFault；错误标签或栈落在库内不能单独归责。
6. 缩小到保留失败条件的输入与调用链，必要时在独立调试构建中补符号、校验或同步定位。同步/debug/-O0 改变时间与代码形态；问题消失仅是线索，修复要回到正常优化构建复验。

禁止把旧手册中的 `kill -34` 当作通用只读采集命令：只有确认当前 runtime 安装了对应处理器、目标身份和部署授权后才可考虑；错误信号可能终止进程。保存和公开 core/环境转储前检查凭据、模型与数据内容，完整原件保留在受控任务档案。

## 5. 内存、显存和资源泄漏

### 5.1 先分清耗尽的资源

| 层次 | 观察项 | 判断与下一步 |
|---|---|---|
| 主机/容器 | 各进程 RSS/PSS、cgroup 实际限额与 memory.events 增量、内核/调度原因、pinned memory、共享内存 | exit137/SIGKILL 不自动等于显存 OOM；核对事件发生的 cgroup、时间和受害进程 |
| PyTorch allocator | allocated/reserved/peak、分配失败记录、碎片/图池、实际 allocator backend | reserved-allocated 不是泄漏量；缓存平台期、活动张量和待释放事件分别看 |
| runtime/第三方库 | 设备总占用、其他进程、TE/通信/workspace、自定义 allocator、stream/event 数 | PyTorch snapshot 看不全库外分配；先确认口径再追分配/释放配对 |
| 训练状态 | 初始化、fwd/bwd、optimizer、all-gather/offload、保存/恢复的逐 rank 峰值 | 单稳态步能放下不代表初始化/保存/恢复能放下；最紧 rank 和必要余量主导容量 |

Linux 下先由目标 PID 的 `/proc/<pid>/cgroup` 与实际挂载确定路径和 cgroup 版本，不能假设宿主和容器视图一致。权限受限就登记缺口。v2 的 memory.events 可能含子组累计，使用前后增量并结合合适层级；v1 则按其接口读取。

### 5.2 做随 step 和阶段的生命周期对照

固定输入/形状，分别记录预热、稳态、保存/评估、恢复周期；画 allocated、reserved、设备总量、RSS 与 step 的曲线。检查 Python tensor 容器与 hook、retain_graph、异步写盘/offload、数据 worker/prefetch、graph/recompile 缓存和通信 buffer 的所有者与释放时机。动态形状需要按形状分组或单独固定复现，不能把新增 shape 的缓存增长直接归为泄漏。

- 活跃量持续增长：追对象引用、保存的张量、未完成异步 work，保留分配栈和生命周期。
- 活跃量平稳但 reserved 增长：看段/碎片、graph 私有池、跨流事件与缓存平台期，再判断是否泄漏。
- allocator 平稳但设备总量增长：核对其他进程和库外分配；Torch snapshot 无发现不能排除。
- host 增长：区分 worker 数据复制、pinned 队列、统计缓存、异步 checkpoint 和真正引用泄漏。

按当前 HCU PyTorch 支持情况使用 memory summary/snapshot/history，限制记录窗口和数据量；私有 API 先核对签名。必要时查 DTK `hipprof --memory-usage`（趋势）或 `--leak-check`（栈与分配信息）。先读现场帮助，选一个进程或最小复现，并考虑 hook/LD_PRELOAD、正常退出生成报告、未拦截接口和采集自身开销；没有报告不算没有泄漏。与 XProf/XCompute 性能采集分开，不混合命令或输出格式。

`empty_cache`、缩 batch 或强制周期重启只能作为诊断/缓解手段，不能自动称根因修复。修复后关闭诊断，覆盖原增长窗口、保存/恢复周期和最坏 shape，观察峰值与斜率；短跑尚不足就保留长稳待验证项。

## 6. 数值异常与训练质量

先固定同一数据/模型/优化器/RNG/并行布局与候选快照；参考项目 `docs/training-state-validation.md`。NaN/Inf、梯度消失或阶段 loss 偏离必须转入排障，不能以吞吐提升放行。

沿输入/tokenizer/mask/labels → 首个前向差异 → loss 归一化 → backward/梯度归约 → clipping/unscale → optimizer 更新定位第一处分歧。先检查数据和配方一致性，再逐层缩小；关注混合参数组、低精度缩放状态、溢出跳步和累积边界。首个被发现的坏张量还要沿通信或异步边回溯生产者。

按需复用 HCU hcuprobe/dcu_probe、TE dump 或引擎现有比对入口。核对当前源码的调用方法和 hook 覆盖，先采相同少量 step/rank/算子，读取输出/梯度/更新前后张量，必要时扩至完整相关通信组。异步 dump 应保存当时的内容；缺 rank、空匹配、同名模块错配或没采到 backward 都是 incomplete。不要通过放宽容差、替换优化器或改变训练目标掩盖偏差。

RL 另对齐 policy/权重版本、rollout 样本及数据年龄、logprob/reward、训练/推理精度与权重传输完成状态。发现错误先停住该候选推进；修复后局部回归，再于稳定阶段做同初态 loss 对照，无需每次调查都长时训练。

### RL 阶段阻塞和恢复的补查

按当前引擎的实际 driver/worker 链区分 rollout、reward/评估、logprob/advantage、actor/critic 更新、权重同步与保存；有的算法没有 critic，不按固定角色表判断缺成员。检查队列背压、worker 退出、样本数/长度差异与数据年龄，不能因为训练卡利用率低就先重写计算 kernel。

共卡或 offload 模式下分别核对训练状态、推理 weights、KV cache 的驻留与 sleep/wake 顺序；同步峰值 OOM 不等于稳态 batch 放不下。发送调用返回、backend 完成、replica 已加载新版本和下一批使用新权重是不同证据。step 标签一致也不能单独证明参数一致；LoRA 还查 base/adapter 同步关系。

权重传输不是持久化 checkpoint。恢复时查 actor/可选 critic、优化器、driver/global step、dataloader/队列状态，以及异步保存完成标记；缺少数据游标要说明可能重复/跳过样本。结合 HCU 大库 `verl-ppo-grpo-worker-chain`、`verl-weight-sync-checkpoint-lifecycle` 和相应 slime/AReaL 官方 Wiki，按现场子模块与传输 backend 追代码。固定小窗口验证恢复后首批 rollout 和更新链，不把该验证扩称完整 RL 收敛。

## 7. 性能持续退化与扩展效率

先按项目 `docs/environment-discovery.md` 第 6 节排除测量口径、诊断开销、错误重试与环境差异，再看实际最慢 rank/关键路径。核对频率/温度/功耗、CPU quota/亲和、数据与存储吞吐、NIC 路径、并行负载、周期 checkpoint/评估和重编译。健康管理值不支持某项时标未知，不用另一型号阈值补齐。

相同条件下单测也退化，优先环境/库/链路；单测正常但模型内慢，转性能 Skill 比较重叠竞争、调度和暴露尾部。`GPU_MAX_HW_QUEUES` 只能在匹配 runtime、固定配方和单变量对照下验证，不作为所有卡住或变慢的通用修复。主动测试必须避开其他任务负载；单测通过也不代表模型运行正常。

持续显著差距经基本有界尝试仍未解决，按项目 `docs/collaboration.md` 向用户报告可信预期、当前差距、已试结果、推荐下一步与需要的专家/权限。不要无限加 Agent 或重复无新证据的实验。

## 8. 保存恢复、容错失效与节点重入

1. **存储：** 先查容量、inode、quota、挂载/权限及读写错误，区分磁盘满、元数据/网络阻塞和写入进程退出。大型写盘探测本身可能扰动训练，不自动压满共享存储。
2. **checkpoint：** 确认 writer/finalization 完成、manifest/分片/metadata 一致、完整性与加载版本匹配；未结束写入的目录不能当恢复点。检查模型 keys、优化器、RNG、scheduler 与数据位置，按项目 `docs/training-state-validation.md` 做恢复对照，不能仅以 load exit0 判断完整。
3. **控制链：** 逐项核对异常被检测 → 事件被消费 → 原作业停止 → 必需成员实际退出 → 节点处置 → 新资源就绪 → 新 attempt 启动 → 加载恢复点 → 真正继续 step。每一段保存身份、回执和截止；失败落在哪段就调查哪段，不能只看“restart sent”。
4. **责任与边界：** Cluster Manager 的裸机/Slurm/MPI、Docker 候选和 K8s operator 是不同入口，阅读已部署分支/PR，不照搬另一部署的命令。确认重试预算、退避和重复失败的人工介入点；无效恢复不能无限循环。
5. **节点重入：** 保留故障证据，在授权隔离池中复核设备、网络及任务相关负载，必要时与已确认健康节点交叉测试。K8s Ready、单次 check 返回0、已发送告警均不够；核对结构化结果/缺项。解除黑名单/taint 由当前恢复协议决定，不能删除其他管理者状态。
6. **观察与告警：** 对照新 attempt 的真实进度、全部成员、watcher、独立 sentinel 与日志轮转/存储。outbox、桥接消费、飞书送达、Agent 接手、问题解除是不同状态。训练恢复后 watcher 仍失联时保留监控故障，不能只关闭训练异常。

## 9. 收尾：恢复不等于根因已经解决

分开记录根因置信度（已确认/候选/未知）、临时缓解、修复状态和验证范围。关闭训练故障需要全部必需成员与正确 attempt、健康资源、有效恢复状态、连续进度、数值/吞吐/显存符合约定，并观察超过原故障窗口或明确待长稳验证；观察器和告警链路分别验收。只分析任务可在形成可操作诊断后交付，不擅自进行恢复。

修复涉及源码/库/参数时回到对应阶段做受影响回归，保留失败输入和测试；只有实验性 workaround 时明确代价、回退及后续 owner。已有通过的无关算子资格测试不重复跑。完整任务仍沿固定执行基线完成后整合交付，不因排障切到另一主仓丢掉比较依据。

最终报告应能让下一位 Agent 或专家直接继续：症状与范围、时间线、最强证据、已排除项、查过的资料及适用性、复现命令、结果/缺口、下一步与资源/权限、回退和验收。只有可跨任务复用的环境经验及最终模型总结按项目知识规则入共享 Wiki；零碎过程留任务档案。
