# Project instructions

- Default file mutations to the current task workspace and verified local/remote/container mappings. Read `docs/workspace-boundaries.md` before the first write or a mapping/exception change; preserve this scope when delegating or entering a standalone mode. External reads remain available. Record necessary external write paths, impact and existing authorization; ask only for missing authorization, not again for already approved work. Never treat cwd, root access or a workspace path as permission for broad deletion. Authorized Wiki/Skill/project maintenance uses its declared checkout/install targets.

- Keep only official material, transferable environment knowledge, and final model-optimization milestone summaries/data in `knowledge/`. Intermediate candidates, one-off debugging and measurement logs stay in the task workspace/board. Apply the curation rules in `docs/knowledge-architecture.md` before adding shared pages. Never commit credentials, private keys or access tokens. External Cookbook publication rules are separate.
- Preserve one coordinator entry plus three stage Skills and two Wiki Skills. Analysis-only, environment-only and diagnosis-only are valid independent requests.
- For model adaptation, inspect applicable scripts/configs in the selected HCU repository and the user's actual deployment first. Reuse compatible HCU launch recipes; use NVIDIA upstream to check model/training semantics. Verify branch, dependencies and effective environment instead of copying NVIDIA launch commands or platform-specific variables.
- Do not refresh HCU-Knowledge as a side effect of this project's search or maintenance.
- Do not duplicate HCU repository Wikis here. Official projects live under knowledge/projects/<project>/knowledgebase/{upstream,local}; HCU repository knowledge is queried through HCU-Knowledge. Maintain external routes and affected workflow contracts in knowledge/catalog/external-knowledge.json. Keep transferable tool/site experience under the existing curation rules; preserve page IDs and update path aliases when reorganizing.
- Attach full tasks to the persistent flow review protocol. A review never substitutes for executed training evidence. Collect human guidance every 300 seconds by default; check collected guidance before new experiments and transitions. Explicit refresh can collect immediately.
- Decompose useful parallel work by dependencies, evidence inputs and independent edit scope. Claim/bind actual Agent sessions, exchange durable questions/findings, and accept results before downstream use. Shared hardware measurements and coupled edits require serialization or verified isolation; native Agent delegation still follows the host's authorization.
- Assess full-model capacity before reducing layers: use a matching HCU Train Simulator/model estimate, available healthy devices, worst-rank memory/headroom and a real short-run calibration. Prefer the full configuration when feasible. Surplus isolated resources may host independent full-model experiments with shared baselines, explicit Agent scopes, timely peer results and common-instance integration validation. See docs/practices/capacity-and-parallel-experiments.md.
- Generate operator analysis/optimization assignments from the actual model/profile, not a fixed roster of operator names. Independent operators may analyze and optimize concurrently; each can proceed when its own dependencies are met without waiting for every operator's analysis. Revisit decomposition after new profiling evidence.
- Treat source acquisition, content review, local tests and real hardware validation as different states. Never turn missing evidence, skipped tests, fallback dispatch or empty output into a pass.
- Use the initial numerical baseline and stage-level loss checks. Preserve wall-clock denominators, overlap accounting, actual rank groups and shape-specific models.
- A remote execution timeout or controller failure can leave the process running. Reconcile the original operation before retrying. Existing site recovery remains the single recovery owner.
- When upstream files change, review related overviews, topics, cases, Skills and command/parser contracts together.
- Write detailed optimization cases only for substantial or high-value optimizations, preferably extending an existing case for the same mechanism. Maintain minor changes in the relevant pages, PR summaries and evidence without case quotas; still explain important correctness/accuracy/recovery impacts. Follow docs/wiki-authoring-standard.md for full, incremental and task-driven updates.
- Keep generic guidance in docs; keep development tracking in task_plan.md, findings.md and progress.md.
- Keep project release numbers out of workflow diagrams and diagram-generation prompts. Maintain release numbers in README, package metadata and CHANGELOG instead; retain actual hardware/tool versions where they define applicability.
- Skills and workflow steps must describe transferable decisions, methods and validation contracts. Keep task-specific shapes, addresses, patches, temporary workarounds and experiment sequences in workspace configuration/adapters. Promote a lesson only after identifying its general trigger, applicability, verification and fallback; do not turn one model's workaround into a default or mandatory step.
- Validate changes with the relevant tests and `python scripts/validate_knowledge.py`. Real HCU/site limitations must remain explicit.
- After reviewed changes to this project, synchronize an existing selected local installation with `python scripts/sync_local_install.py --target <actual-skills-directory>` and verify with `--check`. This applies to docs, Wiki, Skills, scripts and package changes, not only Skill edits. Read `docs/integrations.md` for dependency changes or first setup. Do not fetch/update HCU-Knowledge or silently replace another checkout binding. Report failures and reload/new-session requirements; never claim installed updates solely from a Git commit.
- Keep mode-specific reading routes in `docs/skill-reading-map.md` and validate them with `python scripts/check_skill_resources.py`. Shared docs resolve from the project binding; installed references resolve from their own Skill.
