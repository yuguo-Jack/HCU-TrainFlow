# 改动审查与交付

仅交付也按[工作空间写入边界](workspace-boundaries.md)确认开发 checkout 与输出范围。用户指定已有仓库可直接登记为本次修改目标，不为迁就目录结构搬动它；不要修改参考缓存、清理其他 worktree 或覆盖无关的未提交改动。

本页是三个阶段共用的交付规范。主控可直接接受“这些修改已完成，只做对比、整理并提 PR”，读取本页和改动所属阶段的相关契约即可。成果仍由所属阶段负责，不增加独立 Skill 或训练阶段。

## 1. 确定本次范围

- 明确只审查、整理补丁、创建 PR，还是还需处理 CI/review；沿用用户已有授权。创建 PR 不等于授权合并。
- 保存收到的源码/patch、工作树差异、基点和已有验证，尊重用户未提交修改，不 reset/clean 或覆盖。多个来源分别记录，避免把无法解释的差异一起提交。
- 已有 TrainFlow 任务则引用其 workspace、候选和证据；独立交付可用普通任务计划、审查记录和报告，不必创建训练 TaskSpec 或调用 `flow-start`。不得伪造 environment、baseline、performance、stage-quality 等报告来满足无关门槛。
- 快速线的 example/patch 是成果形式，不是跳过性能分析、调参、算子优化、精度与约定规模/长稳验证的交付捷径。核对原任务的验收范围与结果，缺失部分保持待办，不能用补丁重放检查替代。
- 原完整训练任务有未完成目标时保持其真实状态。单独交付一个 patch 不将整项训练任务标为 completed，也不扩大为新一轮适配、调优或长训。

## 2. 核对来源、目标与改动

1. 读取目标仓 `AGENTS.md`、贡献指南、PR 模板、CI 和测试。先按[双线方法](practices/engine-delivery-tracks.md)确认稳定插件/发布交付或快速模型 example/patch 交付；用户指定基点和目标优先，不用“活跃分支”覆盖 release 锁或客户 commit。查 HCU 实现仍核对实际适用分支，公开/内部仓选择与可发布内容分别判断。
2. 获取当前目标/源分支，记录完整 SHA、merge-base 和 fork/upstream 关系。审查 PR 实际显示的 diff，同时核对原补丁与最终补丁，防止带入无关提交或漏掉新文件。快速线分清**模型源码基点/patch**与**承载 example 的目标仓/PR diff**，二者可能不是同一个仓；按双线方法验证干净基点重放、子模块/依赖及验收快照一致，不把 example 仓的 merge-base 当作模型补丁基点。
3. 查找上游相同问题、相关 PR 和等价实现，追当前调用者、测试及依赖分支。仅标题相似不算等价；已覆盖的改动可缩减或退役，保留理由。必要时查询局部 Wiki、HCU-Knowledge 或匹配底层源码；普通交付不更新大知识库。
4. 按问题与调用链组织改动，检查公开接口、默认行为、错误路径、并发/异步与资源生命周期；算法、精度或 checkpoint 相关变化核对对应语义。用户原有修改超出本次范围的，明确保留位置，不擅自一并重写。
5. 确需 rebase/cherry-pick 或冲突处理时在独立开发树操作，保留原始基点。目标仓可能是训练引擎、HCU TE、Flash-Train、Primus Turbo、数学/通信库或容错工具；按责任归属交付。涉及多个仓时说明接口依赖、提交顺序和兼容窗口。开发树不能占用 HCU-Knowledge 的缓存。

## 3. 用改动影响决定验证

先把已有证据绑定到实际源码 SHA/补丁、依赖、配置和测试条件，再决定哪些可复用。目标分支整合或冲突处理改变了相关实现时，补受影响的回归，不能把移植前结果原样声明为移植后通过。

| 改动范围 | 应核对的验证 |
| --- | --- |
| 文档、配置或启动脚本 | 格式/链接/解析、实际生效参数与可复现命令；有设备副作用的脚本测试仍要资源准入 |
| 引擎逻辑、图编译、并行/通信集成 | 调用是否命中、相关单测/集成、同步与状态生命周期；性能或数值主张须有对应证据 |
| 算子或底层库 | 目标构建/加载、适用 shape/dtype/layout、前后向/累积语义及正确性；主张加速才给同条件性能对照 |
| 优化器、精度、训练状态或 checkpoint | 相关状态和数值对照，按影响决定是否需要阶段 loss/恢复回归；不机械长训 |
| 容错、监测或恢复 | 超时/断线/重复事件/退出状态、唯一恢复负责人及幂等；合成测试与真实站点演练分开说明 |

无法访问硬件或原环境时完成可做的代码审查/CPU 检查，写出未验证项、影响及建议验证命令。实质验证缺失时按目标仓规范创建 draft PR 或保持阻塞；已有适用证据充足时不因本次只是交付就额外要求整套训练。不得在仅有代码推断时宣称性能、loss 或稳定性已经通过。

## 4. 整理与提交 PR

- 按目标仓风格组织集中、可审查的提交，区分必要修复与无关重构。保存源码引用、构建/测试命令、关键结果和回退方法。
- PR 先说明具体问题及最终行为，再写实现依据、适用/失败条件、验证与限制；按模板提供兼容性、性能/精度口径和关联 issue/PR。不要用任务聊天记录代替技术说明。
- 确认最终 diff 只含授权内容；凭据、完整私有日志/数据和临时缓存不能误入外部仓。对内部实现向公开目标的移植检查实际发布范围，未获授权时保留可审查补丁并明确所缺授权，不因可读源码就默认可公开。
- 提交前复核当前目标分支。目标已移动时判断影响，必要时更新候选并重验相关项；不自动 force-push 用户或共享分支。远端已有本人这项任务的 PR 时继续维护，避免重复创建。
- 提交后核实远端 head SHA、base 分支和实际文件差异，检查 CI 状态；CI 尚在运行、权限受限或测试失败时如实报告。后续 CI/review 按本次约定继续处理；不擅自合并 PR。宿主支持时把创建/更新的 PR 附到当前任务。

## 5. 交付回执

至少给出路线、目标仓/分支/example、源提交与补丁身份、PR 链接或补丁位置、改动摘要、已运行/复用的验证、未验证项及当前 CI/review 状态。快速线交付明确必要/可选 patch 顺序、库依赖、重放结果和 Cookbook 入口；稳定发布承接后按双线方法核对替代范围，再退役临时差异。区分代码已整理、PR 已提交、CI 通过、已合入和实际部署，不互相替代。

成果符合共享知识收录条件时调用 `$hcu-trainflow-wiki-skill-update`，按 [知识归属与维护时机](knowledge-architecture.md#任务中的维护时机) 更新精选总结与既有 Cookbook/PR 状态；普通零散 PR 不自动进入 Wiki。直接交付没有 flow 提醒，由负责阶段在原计划中记录本次筛选结果，不补造训练总结。交付 TrainFlow 自身修改还需按 [本机同步](integrations.md#skills账号与升级) 更新本地安装，并报告结果。
