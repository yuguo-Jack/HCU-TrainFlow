# 节点健康检查与训练筛机

环境适配和扩 DP 域共用这一流程。优先复用当前 ClusterManager 的环境检查、NHC、节点池与筛机能力；每次换站点或镜像，重新确认入口和副作用。健康检查不能代替任务占用检查，也不能代替真实计算与通信测量。

## 发现实际工具

先区分执行层：批量控制端、计算节点宿主、训练容器。用 `command -v` / `type -a`、限定目录查找和匹配版本源码确认入口，再读帮助；未知脚本不要假设 `--help` 一定无副作用。

- 用户所说的“run nhc”在部分 ClusterManager 版本中实际调用 `run_nhc`，它是站点提供的命令，不能假定包含在训练镜像或 ClusterManager wheel 中。
- 批量执行工具通常是 ClusterShell 的 `clush`。先核对实际可执行文件、SSH 路径和版本，不把口述拼写或旧脚本参数直接执行。
- 控制端能找到 `clush`，不代表计算节点能找到 `run_nhc`；宿主能执行，也不代表容器有同一设备视图、驱动接口和权限。
- 记录实际入口、脚本/配置哈希、版本、检查项、依赖、退出码与结果格式。缺失时查 HCU-Knowledge、当前仓库和现场部署目录；确实需要站点包或权限时反馈缺口，继续其他可独立完成的检查。

## 小范围验证后再批量

1. 从用户授权节点集合与实际分配中生成私有 hostfile，去重、确认名称解析，禁止沿用仓库示例名单。多 Agent 共用同一资源准入协议。
2. 先对一个目标做只读连通性与身份检查，再测试批量回显的逐节点结果。跨跳板的 SSH 路由必须实际验证；本机免密不等于容器内 MPI/SSH 可用。
3. 阅读 `run_nhc` 及其配置，确认是否仅采集、是否分配 GPU/执行负载、是否改调度状态。需要主动负载的检查先获得新鲜空闲证据；检查运行中的任务时只使用已确认不干扰训练的项目。
4. 在一台获准节点执行有界 NHC，保留原始 stdout/stderr、时间和结果；确认解析器适配真实输出后才批量。fanout、超时按当前节点数和控制端能力设置，不照搬示例中的大并发值。
5. 批量结果按节点区分 `pass`、`fail`、`unknown`。SSH 超时、命令缺失、空输出、结果缺节点或格式变化均为未知；不能当健康、不能仅凭批量进程返回 0 将全节点放行。

## 组合验收与动态节点池

NHC、`hcu-envcheck`、训练筛机分别保留证据和覆盖范围：

| 检查 | 作用 | 后续动作 |
| --- | --- | --- |
| NHC / 静态环境 | 驱动、链路、卡数、错误状态等当前健康信息 | 失败定位；未知补证据 |
| GEMM / HBM / RCCL / 专用通信测试 | 当前 dtype、shape、拓扑和软件的数据路径 | 与匹配条件的性能参考比较 |
| 代表性训练筛机 | 当前模型和并行配置下的稳定性、吞吐、资源压力 | 形成可用池与待复核池，再扩 DP |

筛机先固定已验证的模型、并行拓扑和基线，逐组测量。允许缩层或用户授权的维度代理时记录限制；代理通过不证明完整模型峰值显存或长训稳定性。恢复完整参数后，再按实际显存余量选择并行配置并扩 DP。

横向/纵向分组测试的交集只能提供可疑节点线索：有失败组但没有交集时，不能把全部节点记为健康。保留未归因的组级问题，复测链路、节点配对和共享网络干扰；不能仅信任脚本生成的 `healthy_nodes` 文件。

节点池保留节点身份、检查时间、证据、状态变化、当前占用及重入条件。外部任务开始使用资源时停止新派发；本任务 lease 不代表站点独占。健康修复后的节点需要重新检查，旧通过记录不自动恢复有效。

## 与容错衔接

部署时明确唯一恢复负责人，先核对当前 ClusterManager 的停止、换节点和重启实现。某些版本会按通用 `python` 关键字停止进程，不能在共享节点上原样接管；须先限制到实际作业 ID、容器或经验证的本任务进程身份，并做有界恢复演练。

训练失败、NHC 不可达、观察器失联是不同事件。Agent 汇总训练日志、NHC 原始结果、节点池、checkpoint 和重启记录；避免观察器与容错工具重复重启。保留未知状态并上报实际缺口，详见 [运行与恢复](operations.md) 和 [真实训练观测](training-observation.md)。

当前工具升级后复核入口、输出解析与停止范围；把通用修订提交到独立开发 checkout，真实节点与报告只放私有工作区。
