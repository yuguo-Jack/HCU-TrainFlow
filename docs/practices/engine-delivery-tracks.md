# 训练引擎的稳定发布与快速适配

适用于 Megatron-LM/Core、Bridge，以及其他预训练、SFT、RL 引擎；RL 同时固定训练、推理和权重同步依赖。两条线可以维护在同一仓库，通过分支、发布清单和模型 example 分开管理，不需要新增 Skill 或调度阶段。

稳定线限制维护范围、保证已声明的组合；快速线跟随明确的新模型与源码需求，避免等待 release。两者共享 HCU 算子/通信能力、数值与实测验收方法，**不能把快速适配理解为降低正确性、精度或交付可复现性**。本页规定方法，不代表所有 HCU 引擎已实现同一种插件接口或已有这两条发布线。

## 1. 先选路线，再选版本和交付目标

| | 稳定插件形式 | 快速适配优化 |
| --- | --- | --- |
| 源码基线 | 明确的官方 release/tag 及其解析出的提交；匹配已发布的 HCU 插件、库与环境 | 用户指定或经确认的官方/客户仓**精确 commit**，可能是 Bridge、Megatron 或其他引擎；不自动换成最新 HEAD |
| 支持范围 | 只承诺经过验证的模型 example、精度、规模和部署组合；不为追新模型频繁抬升基线 | 面向指定模型与任务范围适配；稳定线不支持、指定 commit 或所需机制未发布时使用 |
| HCU 能力 | 优先用引擎的扩展入口、后端或模块替换接入 HCU 库；承接已验证的 HCU 独有优化 | 先完成 HCU 适配、实际融合/执行路径对齐，用好该基线可用的原生优化项；有预算再移植高价值 HCU 独有机制或未合入 PR |
| 交付 | 固定版本的稳定插件/发布配方、支持矩阵和对应模型 example；变更按维护仓规范交付 | 对应模型 example 下的启动配方、源码/依赖锁、可重放的 `git diff` patch、验证与限制；补丁包可通过该 example 所在仓的 PR 交付 |
| 后续 | 维护 release 分支、必要修复与回归；新发布推进须单独验收 | 按需求定向更新补丁；稳定线满足替代条件后迁移 example 并退役临时补丁 |

用户指定基线/路线优先。没有指定时，已有稳定发布覆盖模型及任务要求则优先稳定线；缺支持则走快速线，**不为了让稳定线支持所有新模型而强行回移整套上游代码**。“活跃分支优先”用于寻找适用的实现和依赖，不覆盖发布锁或用户指定 commit；提交时间较新也不自动比已验证 release 更合适。

在现有任务计划/DETAILS 中记录路线、模型范围、执行基点、HCU 依赖、example 归属、交付方式和验证目标即可，不新增必填 CLI 字段。只有环境检查时无需替用户选训练路线。查看最新源码用于查证，不自动改变运行任务的依赖。

## 2. 稳定插件线：稳定来自明确的组合与验证

插件优先承接设备后端、算子/通信接入和 HCU 独有能力，尽量减少对上游核心的侵入；必要的核心兼容补丁单独记录并随匹配 release 验证。不能因称为“插件”就宣称任意上游版本可用，也不要求所有引擎使用同一种注册接口。

发布配方固定官方基点、插件版本/提交、DTK/PyTorch、HCU TE/算子/通信库及相关子模块。已支持的模型才放入稳定支持清单；候选或未验 example 放快速线并注明状态，不能混入稳定保证。HCU 独有优化说明开关、适用条件、收益与回退，沿原有局部回归和稳定阶段 loss 验证，不无条件全开。

两条线共仓时，沿目标仓规范组织 release 分支、实验/模型工作分支及 example 路径；稳定发布清单和默认测试入口须明确区分，快速线新增材料不自动成为稳定发行的一部分。

## 3. 快速线：围绕固定 commit 交付可重放方案

1. **保留输入。** 记录官方/客户仓 URL、完整 SHA、子模块、依赖和客户原始 patch/脏工作树。开发用独立 checkout，不修改知识库缓存。客户原有改动与本次 HCU 适配分别标识，不能覆盖或混成无法解释的总 diff。
2. **核对模型与 HCU 接入。** 以指定基点的模型定义、训练脚本和数值语义为准，复用适用的 HCU 现场配方。逐项追实际算子、通信 op、动态加载与依赖；设备相关实现必须接入匹配的 HCU 库，不能只改启动参数就称完成适配。沿用 TE 接口时使用匹配的 **HCU TE**，核对前后向、数值、版本与实际 dispatch；接口可用就不机械改调用，有缺失仍按依赖缺口处理。兼容 API 名称不等于使用了 NV 实现，不按 `cuda` 字符串机械改写。
3. **对齐实际融合与执行路径。** 以同基点/配方的 NVIDIA 调用链为参考，检查前后向融合、通信/计算流程和数值边界。优先接入已有 HCU 能力，缺失时按[库联动](../../skills/hcu-train-analyze-and-optimize/references/hcu-library-integration.md)补实现或提交具体需求；不能用未说明的拆散回退冒充已对齐。无 NV 环境可读源码与使用可信数值参考，但不声明完成了 NV 实测对比。暂用回退须说明代价与未完成项，取得范围调整后才能按受限目标验收。
4. **先利用现有优化项。** 按[原生能力调优](../../skills/hcu-train-analyze-and-optimize/references/native-engine-tuning.md)检查当前 commit 的有效配置和依赖，按实际瓶颈试验；“官方有优化参数”不代表全开或最新文档里的参数当前可用。能力缺口和优化需求尽早向对应引擎/库 owner 提出，附消费者基点、接口、实际 shape/类型、瓶颈与验证要求。
5. **有预算再深化。** 迁移 HCU 独有优化、官方未合入 PR 或其他引擎机制时，固定来源/review 状态和依赖，按收益选择；与必要适配补丁分层，说明顺序、冲突、回退及数值影响，不为借用一个优化项而盲目搬入整套稳定插件或候选 PR。复用现有迭代与阶段 loss 门槛。
6. **从干净基点复现交付。** 完成约定范围的验证后，在对应模型 example 保存最终 patch 和配方；应用补丁后的源码应与实际验收快照一致，再补必要的构建/加载检查。快速线可据此交付，不要求先合入 HCU 稳定引擎或改成 release 基线。

example 的示意结构如下，实际名称沿目标仓规范；这是**交付目标工程**中的目录，不是在 TrainFlow `examples/` 存放每个客户的训练实现：

```text
examples/<model>/<recipe>/
  README.md             # 稳定/快速路线、模型与资源、安装运行、验收范围、限制与回退
  sources.md            # 精确基点、客户原有补丁、子模块/依赖、补丁顺序与摘要哈希
  patches/              # 必要 HCU 适配；可选优化分开，可关联其他库的固定 PR/提交
  configs/              # 实际有效的模型/训练/推理配置
  scripts/              # 参数化构建、应用补丁与启动入口，按项目规范组织
```

导出 `git diff` 时检查已提交、已暂存、未暂存及新增文件，明确相对哪个基点；保留文件模式与必要的受版本管理二进制资源变更，不能因未跟踪而漏掉新实现；编译产物、日志、权重和数据集不混入源码补丁。子模块内修改要另附子仓补丁/固定提交，只有父仓 gitlink 不足以重现。客户基线若有未提交改动，分别保留原始差异和本次增量及应用顺序。依赖已发布产物或其他库 PR 记录准确版本/哈希，不把共享环境的安装变化藏在步骤之外。源码/客户补丁的可发布范围按[交付规范](../change-delivery.md)处理；无需改源码时明确记“无源码 patch”，不制造空补丁。

先做干净基点上的补丁应用检查，再核对重放后的源码/依赖与验收快照；缺源码、冲突、漏文件或实际版本不符则交付未完成。仅 patch 能应用不证明训练通过，原有环境、局部数值、阶段 loss 和任务规模边界仍独立保留。

## 4. Cookbook 与经验记录必须指向正确路线

Cookbook/模型 example 明确：**推荐路线、精确官方/HCU 版本、适用模型与资源、HCU 依赖、运行命令、必要/可选 patch 顺序、验证范围、限制和回退**。稳定与快速方案分别给入口，不能共用一个无版本的“最新命令”，也不能把快速方案的成绩写成稳定发布已经支持。

在任务开始/交付、相关 HCU release 发布以及项目例行维护时复核入口、补丁适用性和支持矩阵，记最后核对时间、维护负责人及下一次复核时机；沿既有维护周期执行，无定时服务时不宣称已后台自动更新。当前 Cookbook 维护属于任务授权才提交对应变更，否则保留具体待办。本次流程维护不自动更新任何外部 Cookbook 或 HCU 大知识库。

最终模型总结记录所用路线、完整基点/依赖、最终补丁身份及 example/Cookbook/PR 链接，后续迁移补充替代关系。完整补丁交付在所属工程，HCU 仓知识通过 HCU-Knowledge 查询，不在 TrainFlow 重建另一套 HCU 仓 Wiki。

## 5. 稳定线接管后退役临时补丁

“支持同名模型”只是复核触发条件。实际替代还要满足当前任务需要的结构/精度/功能、HCU 库与环境，复核质量、性能/显存和必要的保存恢复能力；有客户指定 commit、仍在使用的方案或稳定线尚未承接的独有优化时，不能直接删除。

条件满足后，把推荐 example/Cookbook 指向经过验证的稳定版本，再从活跃快速目录退役已被替代的临时适配 patch；逐项核对可选优化，未替代部分保留必要差异或向正确库/插件交付。保留原方案可追溯的 Git 提交/tag、基点与替代说明，不改写 Git 历史，也不删除运行任务的源码、证据或恢复点。迁移训练依赖仍在任务约定窗口执行，不能因发布新 release 就热替换长训环境。

两条线均沿[执行基线规则](execution-baseline.md)完成自身范围验证；只有任务明确包含主仓整合才安排对应回归，不再把“所有快速方案必须合入 HCU 主仓”作为交付前置条件。
