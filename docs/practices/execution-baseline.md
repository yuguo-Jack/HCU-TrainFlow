# 执行基线与最终交付目标

开始时记录执行仓/基点/工作分支/补丁/依赖，以及独立的最终目标仓/分支。HCU主仓已经支持模型时可以直接从它起步；否则选适合当前模型的功能分支或用户patch。固定基线仍允许侵入式优化，但每个候选有不可变快照、实际运行配置和回退。

完整任务顺序：适配 → 系统与算子优化 → 稳定阶段loss → 扩DP和容错/持续监测 → 整理改动 → 目标主仓整合与差异回归。查最新源码寻找机制不等于迁移整套引擎。没有实际阻塞或用户要求时，不因分支更新/交付目标不同中途重做适配。独立适配、优化或诊断按自己的已授权范围验收交付，不强制增加扩容/长训；仅分析不擅自实施候选。

## 复用哪些验证

| 改变的层 | 通常需要补的证据 | 可以保留的证据 |
| --- | --- | --- |
| 原样复用已测底层算子 | 当前模型dispatch与接口命中 | 相同实现/ABI/shape/dtype/契约的独立数值测试 |
| 梯度生命周期、累积/清零、hook或DDP路径 | 对应多微批/跨step及分布式集成 | 不受影响的独立数学参考 |
| 微批、并行、重算或overlap | 同有效batch/精度的性能、显存、样本消费和阶段loss | 未变的底层函数资格，原数据/初始基线 |
| 引擎主仓整合 | 实际调用、数值与性能受影响项，必要的checkpoint/恢复 | 经源码差异确认仍适用的底层测试和历史经验 |

跨分支性能或loss成绩不能直接视为新分支通过；也不能以“换了分支”为由重跑全部独立资格。先写差异和测试复用表，再执行补证。局部候选需要局部回归，较长loss验收在稳定阶段进行，不把反复资格测试当作优化推进。

## 必须中途改变基线时

说明阻塞、局部修复备选、迁移收益/成本、受影响机制与回归范围。既有授权范围内处理；超出既定范围先给用户具体选择。保留旧最好候选和未解决问题，正式切换更新比较上下文、观察器与任务计划，不让旧证据自动为新实现放行。

执行与交付的具体步骤见 [工作流](../workflows.md) 和 adapt Skill 的 [基线规则](../../skills/hcu-train-environment-check-and-adapt/references/workflow.md#适配工作树与最终交付)。
