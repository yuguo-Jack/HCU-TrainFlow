# 源码快照与传输

本地编辑和远端执行通过固定源码快照衔接。快照 ID 同时绑定选中文件的路径、SHA-256、字节数和执行位；Git HEAD 是来源线索，不能代替工作区实际内容。原始代码、压缩包和远端目录留在任务的私有工作区。

## 标准流程

```bash
# 在独立开发 checkout 暂停编辑，显式选择要运行的源码和配置。
hcu-trainflow --workspace PRIVATE source-snapshot CHECKOUT src scripts configs
hcu-trainflow --workspace PRIVATE source-bundle SNAPSHOT_ID PRIVATE/source.zip

# 使用现场已授权的 SSH/传输工具复制这个压缩包；保持主机校验。
# 以下命令在远端对应的 TrainFlow Python 环境执行。
hcu-trainflow --workspace REMOTE_PRIVATE source-receive REMOTE_PRIVATE/source.zip NEW_DESTINATION
```

以当前 `--help` 为准。部署使用新目录，不能覆盖正在运行的源码。训练启动记录应引用返回的 `snapshot_id`、远端目录以及运行时/镜像版本。`verified: true` 仅表示传输内容通过完整性校验，不代表代码已经编译、训练、性能或 loss 验证通过。

源码捕获按文件完成；它不是文件系统级跨文件事务。协调者应在生成快照期间暂停同一 checkout 的修改。程序会拒绝单文件读取期间可检测的大小、修改时间或 inode 变化。原有未提交修改会按实际字节进入快照，不应只依据 HEAD 声称与上游完全相同。

## 完整性与路径

- 每个内容对象先写临时文件、flush/fsync，再原子替换。读取对象时再次校验哈希与已登记大小。
- 快照和接收使用流式 `Store.put_many`。所有对象写入成功后，在一个 SQLite 事务中批量登记。不会为几千个源码文件各做一次数据库提交；对象文件的独立落盘保障仍然保留。
- 打包和展开通过 `Store.iter_artifacts` 复用一个读取连接，逐文件校验、处理，只在内存中保留当前文件与清单元数据。
- 接收检查清单 ID、完整文件集合、逐文件大小/哈希、重复压缩包成员、重复 JSON 键、压缩包声明的解压总大小及符号链接类型。
- 文件路径必须是明确的相对 POSIX 路径。绝对路径、反斜杠、盘符/ADS 冒号、空路径段、`.`/`..` 别名和文件与父目录冲突均拒绝。Windows 还拒绝大小写冲突和设备保留名。`trainflow-snapshot.json` 是发布回执的保留路径，源码不可占用。
- `.git`、`.private`、`.work`、`__pycache__` 和名称以 `.env` 开头的文件继续排除。普通生成文件不会自动全部排除；必须按任务显式选择合适范围，并检查快照内容。

## 执行位与 Windows

Windows 的 `stat` 执行位不能代表 Linux shell 脚本的执行权限。Windows 捕获已跟踪文件时读取 Git index 的 `100755`/`100644` 模式，并在文件记录中保留 `executable_source`。Linux 捕获以实际工作区 POSIX 执行位为准，保留尚未提交的 chmod 修改。

Windows 上未跟踪文件没有可靠的 POSIX 执行位来源，默认按非可执行文件记录。可以显式用 `python script.py` / `bash launch.sh` 启动；需要直接执行时，先在开发仓登记文件并设置 Git 模式，例如：

```bash
git add scripts/launch.sh
git update-index --chmod=+x scripts/launch.sh
```

Windows 的 Git 符号链接占位文件不会被误当普通源码发送。仓内相对链接按下面的规则解引用；越界依赖仍须明确处理。含未解决 merge stage 的选中文件同样拒绝。

选中范围包含已检出的子模块或嵌套 Git 仓时，分别读取其自身 index。外层 index 的 gitlink 不能说明子仓内的执行位与符号链接；即使只选择子仓中的一个文件，也要按其所属仓解析。无法读取已存在的 Git 元数据时停止快照；不会拉取缺失子模块，也不会打包 `.git`。

失效的 `.git` 链接必须先拒绝，防止 Git 向上发现父仓而返回错误的模式表。Windows 选择路径也须使用实际目录项大小写，不能以文件系统宽松匹配替代 Git 索引中的准确路径。

## 仓内相对链接

Windows `core.symlinks=false` 可能把 Git 的 `120000` 链接检出成一个只包含目标路径的普通文本文件。直接发送这个文件会把脚本变成路径字符串、把目录入口变成文本。快照识别 Git index 和真实文件系统符号链接，并执行受限解析：

1. 只接受仓库内部的相对 POSIX 目标。拒绝绝对路径、盘符、越界、缺失目标、循环和过深的链接链；Windows junction 仍须显式处理。
2. 按路径分量依次解析。`link/..` 中的 `..` 基于链接实际目标，不预先用字符串归一化改变含义。
3. 文件链接复制其最终目标内容；目录链接递归复制其目标文件，在原链接入口下保留相同相对目录结构。不忽略整个链接，也不要求接收端具有创建 Windows 符号链接的权限。
4. 清单 `resolved_links` 保存原链接路径、目标文本及其哈希、最终仓内源路径、目标类型和原始表示形式。解引用文件另有 `source_path`，可追到实际源文件。链接指向排除的私有材料路径时拒绝。
5. 对象批量登记前重新核对链接解析，检测已变化的目标。跨文件修改仍需协调者暂停编辑，不能依靠这一检查替代源码冻结。

接收端物化的是普通文件。此模式保留固定源码内容，不保留 symlink/inode 身份、运行时可写别名或空目录语义。若程序依赖这些行为，应将其列为明确的部署依赖，不能把内容解引用声称为原始文件系统完全等价。

## 中断与重试

压缩包先写 `NAME.zip.partial`，关闭 ZIP 并 fsync 后才重命名为最终包。展开先写 `DESTINATION.partial`，逐文件验证和写入清单回执后才重命名为最终目录。因此，中途异常不能把目标目录或包标成已验证完成。

若 `.partial` 已存在，程序停止并要求检查，避免重试覆盖现场。确认没有相关进程运行、已保留必要故障证据后，可以选择新的目标目录继续，或由操作者明确处理旧半成品。

对象写完但批量登记尚未提交时，异常可能留下未登记的内容对象。它们不会成为成功快照；相同输入重试会重新校验并复用这些字节。失败不会自动删除可能用于排障的文件，也不会自动重启远端训练。

首次接收仍须写入全部源码及其对象，并执行文件落盘；批量登记减少数据库往返，不能消除共享存储自身的元数据、带宽与 fsync 成本。实际速度要在现场测量，不能把本地单元测试时间当作远端传输性能。

## 原生扩展与运行缓存

传输完整性不意味着训练期间源码不会变化。有些框架在初始化时执行 `make -C 源码目录`，把数据集扩展等 `.so` 写在 Python 包旁。启动适配应单独检查这类行为：固定源码保持只读职责，编译、数据集索引和 Python 字节码等生成物放在任务私有的实验输出目录。

需要保留原生构建语义时，可采用窄范围构建适配：复制未修改的源码和构建文件到缓存，以源码哈希、当前 Python ABI、头文件、编译器及显式参数形成构建标识；由全局 rank 0 构建并原子发布成功回执，其他 rank 有界等待并校验产物。保留框架原有同步步骤；rank 0 崩溃或超时时应明确失败，不能只凭文件存在继续运行。

扩展导入路径同样属于验证内容。仅添加缓存路径不能排除之前已经加载的旧模块，也不能覆盖 `from ... import ...` 提前捕获的旧函数。适配应在框架导入之前建立精确的扩展选择，拒绝未知来源的已加载模块，不改写其它包的搜索规则。构建后核对完整源码树未变化、各 rank 的实际扩展来源与哈希，并记录构建日志及回执。缓存路径逃逸、ABI不一致、编译失败或损坏的回执都不能退回源码目录里的旧产物。

这些规则需要在对应框架的适配代码和真实环境中落实；TrainFlow 的源码接收器本身不会自动拦截框架运行时的文件写入。
