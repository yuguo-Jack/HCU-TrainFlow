# 环境发现与逐项验收

先找到当前环境真正提供的工具，再组合检查；不要把某台机器的工具路径、网卡名或历史阈值复制为默认配置。环境记录留在任务私有工作区，通用流程保存在本工程。

## 1. 明确执行位置

分别记录本机、跳转节点、计算节点宿主和容器的职责、Python 版本、软件入口、挂载及权限。跳转节点能 SSH 不代表能运行最新版检查器；容器中有 DTK 也不代表宿主安装了相同 DTK。优先复用已有运行环境，缺依赖时先定位对应执行层，不直接修改系统安装。

现场连接若依赖跳转节点持有第二跳凭据，使用 [远程执行](remote-execution.md) 的显式连接模式。只在用户允许的私有目录部署检查代码和记录。源码在本地修改，通过 [固定源码快照](source-transfer.md) 同步；检查脚本本身同样固定提交与内容。

## 2. 发现已有能力

1. 阅读当前 Cluster Manager 对应子工程、`run_nhc`、check 脚本和环境自带启动脚本。区分独立环境检查、Slurm 作业容错、K8s 控制器、栈分析等功能，不能用整个仓库名称代替具体入口。
2. 用限定深度的目录检查优先发现镜像 `/opt` 下的 DTK、驱动管理工具、通信测试、数学库测试及激活脚本；再核对 PATH、包元数据和 `--help`。`/opt` 是优先检索位置，不是唯一允许位置；路径存在不代表接口或运行依赖正常。
3. 记录命令所在层、实际路径、版本/提交、所需设备和环境变量、输出格式、退出码含义、是否执行主动负载。不能只按文件名猜测用途。
4. 对找不到的能力，先查 HCU-Knowledge、当前工程代码和安装指南；使用与本镜像版本兼容的现有测试。不要因旧脚本中不存在某路径就宣布硬件不支持。

### 先还原现场启动和激活链

环境检查和单测也要复用现场配方，不能只在模型适配时才读启动脚本。先从用户提供的命令、部署说明、已有 launcher 和明确的共享目录入口追踪环境脚本及其 `source` 链；限定范围发现，找不到时记录具体缺口。DTK 自带激活脚本只建立其中一层环境，现场脚本还可能设置通信 traffic class、端口/GID、网络选择、QP、库搜索路径等。按原配方的加载顺序检查覆盖关系，读取脚本内容和调用的文件；不能仅凭文件名执行未知的安装、清理或系统修改。

在选择调优变量之前，固定当前现场配方的路径、内容哈希/版本、执行层和实际加载顺序，核对每个节点/rank 生效的必要非敏感参数、最终 argv 与加载的库。不要全量打印环境中的凭据。SSH、MPI、容器和调度器各自的环境传递须实际验证；在控制端加载脚本不等于所有 rank 都继承。比较自建测试和用户实测时，列出两者的 host/rank 映射、launcher、二进制、消息范围及工具默认值差异。只改变安全执行所必需的连接或资源设置时也要说明，不能称为完全相同的命令。

用户给出已知可工作的现场命令时，在授权和资源准入范围内优先复现这套完整配方，再做受控差异定位。整套配方带来收益只能证明配置组合有效，不能直接归因到某一个开关；之后才有依据地拆分对照。保留“现场配方基线”和“自行选定的调优候选”的区别，不把缺失现场激活脚本的结果称为该环境默认性能。

注意 Python import 也可能初始化 GPU 或查询设备属性。导入训练框架/TE 等库的检查应按实际副作用进行资源准入；不要把“只执行 Python 导入”自动归类为无设备访问。

## 3. 被动检查与主动检查分开

| 层次 | 主要内容 | 放行依据 |
| --- | --- | --- |
| 身份与挂载 | 节点、镜像摘要、目录映射、共享盘可见性、工具版本 | 真实输出与限定目录读写验证 |
| 占用与预约 | 调度分配、宿主设备持有者、多次利用率/显存观测 | 新鲜且覆盖完整的占用证据；见 occupancy-check |
| 静态健康 | 卡数/型号/架构、驱动、链路状态、网络路由、资源限制 | 与分配清单和现场配置一致；未知项保留 |
| 基础计算 | 小规模正确性、指定 dtype/shape GEMM、HBM 测试 | 可复现输入、明确字节/运算数口径、有效参考 |
| 机内通信 | 拓扑、P2P、实际消息量的 RCCL 正确性与带宽 | 匹配设备集和通信类型的证据 |
| 机间通信 | 实际 NIC/GID/协议、RCCL、适用的 DeepEP 等测试 | 匹配节点、链路、dtype、token/hidden/expert shape 与分发模式 |

仅在当前步骤所需资源和能力已确认时运行有界诊断。例如单卡组件正确性不代表机间通信已通过。全环境报告必须列出所有未覆盖设备/能力；不能为了推进全流程把诊断成功写成完整环境放行。

测量前重新准入；共用设备、网络、共享盘压力域不能因分给不同 Agent 就同时做干扰性基准。发现他人占用时保留待测项并等待或换到获准的空闲资源。

宿主 `fuser /dev/kfd /dev/dri/renderD*` 返回空不能证明无人使用。容器内设备文件可能与宿主有不同的文件系统和 inode，实际字符设备 major/minor 却相同。公用 `collect_node_occupancy.py` 按 `/proc/*/fd` 的 `st_rdev` 匹配设备，同时保留读取失败和身份缺口；不得用一次 `fuser` 的 exit 1 代替进程覆盖完整。硬件利用率非零却没有可归属进程时，将进程覆盖标为未确认，显存/利用率证据继续参与阻止准入。驱动保留显存应与进程分配分别解释，不能把所有非零显存都称为泄漏。

节点迁移后重新核对 PCI/NUMA、KFD/render 对应、网卡/GID、控制路由和容器设备视图；不复制上一组节点的 GPU ordinal 或拓扑文件。相同镜像 tag 可能指向不同 image ID，应固定 digest/ID 并比较实际加载的 DTK、RCCL、TE、DeepEP 等关键二进制哈希。版本字符串相同或部分库字节相同只能证明所查范围一致，不能证明整个镜像等价；比较结果记录到任务环境快照。

## 4. 检查失败先定位层次

- **入口失败**：区分命令不存在、Python/语法版本不兼容、激活脚本未加载和动态库缺失。查看 stderr；退出码 127 并不总是文件不存在。对已安装二进制可检查依赖解析，优先使用当前进程的明确激活方式，避免修改全局系统配置。
- **远端激活失效**：控制端的环境变量不会自动进入 SSH 远端。检查器的 `remote-python` 若要求一个可执行路径，就提供任务目录内审核过的包装器，不将 shell 前缀塞进路径字段。
- **协议假设错误**：RDMA 设备出现在 `/sys/class/infiniband` 不代表链路一定是原生 InfiniBand。核对 link layer、实际 netdev/bond、速率、GID 类型、路由和工具支持的模式；不能把接口名含 `bond` 的设备一律排除。
- **解析误判**：保留原始输出、工具版本和字段边界。例如 `prio-tc` 与 `reco-prio-tc` 是不同字段；存在 numeric 输出选项时优先使用，并保留未知值。修复 parser 需覆盖真实 fixture 和边界情形，不能只修改最终报告。
- **配置含义不明确**：RoCE 的 PFC/ETS/DSCP 需要结合实际训练流量优先级及交换机策略判断。某些普通业务优先级未开 PFC，不足以证明训练链路有故障；也不能据此擅自打开全部 PFC 或猜一个 traffic class。

错误消除后重跑受影响的检查，保留前后证据和修复范围。工具缺陷、测试方法不适用、真正的设备故障分别登记，不混成一个 pass/fail。

## 5. 性能预期与专用库验收

参考值需记录来源时间、硬件/链路、软件版本、计算或通信口径、shape、dtype、预热和重复次数。硬件标称值、历史同类环境数据、当前实测三者分开。条件不匹配的历史值仅用于解释差距，不能当硬性通过线。默认脚本中的节点数、目标规模或 NIC 也是待核对输入。

检查 DeepEP 等专用通信库时，先读其测试 launcher：有的入口会自行 spawn 多个本地进程，外层再按 GPU 数启动会重复扩增进程。分别说明正确性、吞吐模式、消息量、单机/跨机、环境变量和二进制来源；Python 文件相同不等于已证明扩展二进制来自同一提交。

训练后端资格同样需要实际路径证据。例如启用 TE 的分组 GEMM 开关时，核对已安装版本的源码、已有 HCU 模型配方、空 expert/全空输入处理，以及前向、输入梯度和权重梯度。测试开关生效、结果正确、性能符合预期是三项独立证据。

环境矩阵、工具修订和未确定的性能预期进入私有经验库；需要修订上游检查器时使用独立开发 checkout，准备通用复现与测试。后续镜像/工具更新应重验受影响条目，而非沿用旧的通过标记。

## 6. 性能不及预期时的排查顺序

环境验收、模型优化和扩容/故障诊断共用以下闭环。**发现有依据的性能差距后，必须完成基本排查和授权范围内的有界尝试；只列差距或写“条件不全”不是处理完成。** 只分析模式保持原权限，交付已查证结论和待执行实验；不能将未执行写成已排除。

先区分判定与调查：

| 情况 | 验收结论 | 处理 |
| --- | --- | --- |
| 当前条件与已冻结参考一致，实测低于有依据的最低线 | `fail` | 排查并复测，不能降阈值使其通过 |
| 原文支持明显差距，但软件、拓扑或测试条件尚有缺项 | `incomplete`，记录 provisional discrepancy | 保留已知差距，先补可比性；不能因条件未知自动忽略 |
| 缺正文、方法/单位不可比或根本未采集 | `incomplete`，evidence gap | 补原件/测量，不先计算一个看似精确的比例 |

“明显”由原件、当前可比部分、重复分布和工程机理说明，不设通用的达标百分比。历史最好值、硬件标称和当前现场结果各自标明身份；现场结果不能自己充当性能正常的证明。已有检查退出 0 或达到旧最低线，仍有未处理的可信差距时，要填写 `performance_discrepancy`，使 `environment-check` 保持未完成；字段和输出见 [环境验收契约](contracts.md#环境验收)。

### 查证、尝试和复验

1. **复核原件和测量口径。** 从 `reference-query` / `experience-search` 追到原表、日志与测试实现。核对源日期/版本、标称或实测、HT/LL/collective 类型、dtype/shape、实际数据量、单向/双向/聚合带宽、GB/GiB、计时区间、同步、预热/重复和最慢 rank；API wall time、kernel 时间、RDMA payload 不互换。先修解析/单位问题，不改变原始材料。
2. **确认实际运行配置与环境链路。** 先按第 2 节还原现场启动/激活链，核对自建测试是否漏掉现场脚本或改变加载顺序，再保留所有参与节点/rank 的真实 argv、必要非敏感环境变量、镜像/驱动/runtime、所加载库路径和二进制哈希。重新确认资源空闲与共享压力域，再按下表定位。配置文件里的值、环境变量被设置，都不能单独证明实际数据路径生效。
3. **查 HCU 知识与匹配实现。** 有 HCU 机制、工具或版本疑问时主动使用 `$hcu-knowledge-search`，必要时读飞书原文及当前安装库对应分支、提交、测试和 launcher。官方/较新主仓可作机制参考，不能冒充当前二进制来源；不更新大知识库。记录查到的触发条件、假设和可以验证它的观测。
4. **做最小有界对照。** 在已授权、重新准入的空闲资源内，自主执行可逆、任务局部的基本尝试，不为普通诊断反复索要确认。每次改变一个有依据的变量，冻结预算、超时/停止条件、原配置和回退；通常用 A（原配置）→B（候选）→A（恢复）检查漂移和可逆性。先复现小规模，再扩大覆盖；基线、数据、shape、rank、其它变量保持可比。没有安全可执行的变量时，说明已排除项及具体阻碍并升级，不能虚构一次“尝试”。
5. **验证正确性和作用路径。** 比较前先验证结果及实际 backend/transport/kernel；用日志、计数器增量、profile 或版本源码证明改动作用到了目标路径。开关被接受、通信正确、带宽提高、模型整步受益是不同证据。记录所有 rank、重复分布、共享干扰、显存/CPU 代价及超时/错误；调试/profiler 开销不能混入正式对照。A/B/A 的短诊断不能替代 `iteration-check` 所需的匹配重复和阶段 loss。
6. **保留有效改动或回退。** 无收益、作用未确认、正确性失败或新增回归时恢复 A 并核对实际恢复。有效候选保留固定源/配置与受影响单测，进入所属阶段的局部回归、profiler-off 测量和必要的阶段 loss。不能将降低校验覆盖、变更消息量或缩模型带来的时间下降冒充同条件优化。
7. **未解决则明确请求用户决定。** 基本排查和有界尝试后仍有可信显著差距，或预算耗尽、反复无收益、数值异常、无访问权限、必须改站点配置时，按 [问题升级与用户决定](collaboration.md#问题升级与用户决定) 提交证据简报，说明为什么此时需要用户或现场专家介入，并给出具体选择及推荐。创建当前 flow 的阻塞问题、更新看板并在会话中报告，不能只写“待处理/建议后续验证”后结束。等待真实答复期间停止扩展同一问题的参数搜索及受其影响的放行；仍保留 `fail/incomplete`，无关阅读与分析可按现有规则继续。用户已经给出下一步命令或决定时直接依其范围处理，不再重复提问。答复决定下一步工作，不能把“已上报”或“用户选择继续”当作环境通过。

无需把所有层次都做成固定压测清单，按证据选择相关项，并说明未适用或未覆盖的部分：

| 层次 | 先查什么 | 避免的误判 |
| --- | --- | --- |
| 测量与占用 | dtype/shape、真实 backend、预热/重复、最慢 rank、其他任务和资源隔离 | 把 compile/初始化/保存混入稳态吞吐，或把退出码 0 当性能达标 |
| GPU/驱动 | 实际卡型、频率/功耗/温度、PCIe/NUMA、驱动/runtime 版本、P2P、当前 HCU XDP 功能状态 | 将系统网络 eBPF/XDP 与 HCU 驱动的 XDP 功能混为一谈；配置存在不代表数据路径生效 |
| NIC/机间链路 | 物理 NIC/端口→netdev/slave→bond→HCA/GID 的实际映射、链路速率与 rail 数、实际传输后端、GPU-NIC 亲和、错误/重传/丢包计数增量 | 把逻辑 HCA/bond 数当物理网卡数；控制通道走 TCP 就认定数据通道走 TCP；把 bond 聚合速率直接当单次消息可达带宽 |
| 交换机/网络策略 | 测试流量的 TC/DSCP 与 PFC/ECN 映射、拥塞/端口计数和多 rail 路径 | 无权限或缺策略时仍声称交换机检查通过；普通业务优先级未启用 PFC 就报训练故障 |
| 共享存储/CPU | 数据等待、文件数量、metadata 延迟、读写吞吐、CPU 利用和 NUMA、缓存冷暖状态 | 把保存大量小对象的耗时归为 GPU 慢；测试过程中更改共享盘或他人数据 |

HCU XDP 检查需读取匹配驱动版本文档及当前只读接口；例如某些 HYCU 版本提供模块参数 `xdp_size`，具体数值含义以该版本为准。同时核对当前库源码与实际 transport 日志/计数器，区分驱动能力、运行时启用状态与此轮测试是否使用该路径。不要把示例值当成全环境默认，也不要为诊断自动重新加载驱动、修改网卡/交换机或系统限额。GEMM/HBM、P2P、RCCL、DeepEP/SHMEM 等分别查其相关路径，不限于某一个通信库。

保留测试前后的计数器、原始日志和对照条件。共有网络/存储在测试期间受其他业务干扰时标明不可比较；本工作区的 lease 只能协调遵守同一协议的任务，不能证明外部资源已独占。优先提出有证据的最小复现与下一项实验，需要现场管理权限或影响他人的改动交由用户协调。

### 沿用现有报告和协作循环

在私有 `findings.md` / `progress.md` 及 `experience-record` 的 diagnosis 记录中保留原始证据、假设、A/B/A、正确性、作用路径、回退/保留和未解项。主控沿用 `team-plan` / `flow-next` 派发和复核，不另建独立状态机；相关成员共享同一窗口、条件和资源域。

`environment-check` 是纯判定，不自行访问机器、查知识库或做实验。`follow_up` 列出后续义务，由当前 Agent 执行或明确受阻原因。字段校验也不能证明推理正确；review 必须读原件和实际执行证据。解决差距后保留旧失败报告，以新观测重新判定，并经原有 flow/阶段验收关闭问题；仅删除 discrepancy、写 resolved 或改摘要不是解决。确因参考不适用而撤销比较时，记录原文依据和复核结论；剩余参考仍不足时保持 incomplete。

## 7. 修复与交付

修复检查器、训练引擎或底层库时，记录来源分支、原始失败、最小修改、单测、真实环境、数值/性能变化及尚未覆盖的配置。提交前核对最新上游，相关更新合入开发分支后重跑受影响的复现和回归；不能直接把较早镜像的验证当作最新分支验收。公开 PR 只包含可公开代码、方法和获准数据，现场标识及原始报告留在私有证据库。
