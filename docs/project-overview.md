# HCU-TrainFlow 工程介绍

## 从一个模型和一套环境，到可验证、可持续运行的训练任务

HCU-TrainFlow 是面向 HCU 的大模型训练适配与优化工作流。它把环境验收、模型适配、性能优化、扩 DP 域和长时训练守护组织成一条有证据、有反馈、可恢复的工作路径，由本地主控 Agent 统筹推进。

适用范围包括预训练、SFT、RL，也包括以 Torch 原生框架为主的视频生成、VLA、世界模型等训练。用户可以委托完整任务，也可以仅做环境检查、模型适配、性能分析、优化或故障诊断；独立任务按自身目标交付。

本文介绍 **0.5.0** 的整体方法和各环节如何衔接。它描述的是工作流应如何执行；已经验证的环境、模型范围及尚未完成的生产验证，见[能力与验证边界](capabilities.md)。

## 1. 如何接手一个新任务

安装后，可以直接向支持 Skill 的 Agent 提出：

> `$hcu-trainflow` 在这套环境上适配并优化这个模型，然后进行扩容验证和持续训练。模型与环境入口如下，已有脚本、数据和资源范围如下……

通常需要确认模型及官方来源、训练类型、环境访问方式、可用资源、数据或权重位置、已有代码和目标。Agent 会从现有脚本、环境和文档中查明能够自行确认的信息；访问权限、模型语义、资源边界或实验目标存在实质缺口时，再提出具体问题。

任务开始时确定三类约束：

- **模型与质量目标**：到底训练哪个模型、使用什么优化器和数据语义，允许哪些缩减，如何判断正确性与阶段 loss。
- **执行与资源范围**：可用节点、卡、调度分配、容器、写入目录、实验预算，以及故障后允许采取的动作。
- **完成条件**：只需报告瓶颈，还是要完成优化、扩容、恢复验证和一段持续训练；哪些条件需要用户或专家决定。

主控随后建立计划、证据记录和看板。接续已有任务时，先核对当前配置、已完成工作和远端实际作业；遇到超时或断线，先确认原进程是否仍在运行，再决定接续或重试。

### 本地与远端如何分工

本地负责代码修改、分析、任务协同和文档；远端负责实际编译、训练、性能采集与调试。SSH + Docker、裸机或 Conda、Slurm、K8s 等通过各自的执行适配衔接，具体环境分别验收。

目录用途保持清楚：

| 位置 | 保存内容 |
| --- | --- |
| TrainFlow 工程 | 通用流程、Skill、工具、官方 Wiki 与精选共享知识 |
| 每个任务的独立 workspace | 开发 checkout、用户 patch、实验配置、完整日志、trace、结果、看板 |
| 远端任务目录 | 对应任务的固定源码快照、构建产物、运行与采集输出 |
| HCU-Knowledge 的源码缓存 | 查证知识使用的参考源码，不承担开发或提交 PR 的工作树 |

每次重要实验关联源码快照、依赖、构建和实际配置，避免本地改过、远端没同步，或多个候选混用构建产物。具体接手清单见 [Agent 接手与阶段交接指南](agent-playbook.md)。

## 2. 三个阶段，共用一套证据与反馈机制

| 阶段 | 要解决的问题 | 主要产出 |
| --- | --- | --- |
| 环境验收与模型适配 | 环境是否可信、模型是否准确、当前资源能否运行 | 环境与硬件基线、适用启动配方、容量评估、初始数值基线 |
| 性能分析与优化 | 时间和显存花在哪里，哪些改动有可靠收益 | 端到端分析、热点优先级、算子上限评估、已验证候选与阶段质量结论 |
| 扩 DP 域与持续容错 | 扩规模后是否有效率，训练能否持续推进并可靠恢复 | 扩展效率、健康节点池、恢复证据、持续观测与交接记录 |

三个阶段可以回流：扩容出现新瓶颈会返回优化，模型或环境变化会重新检查受影响的基线。每轮按“实施 → 测量 → 独立复核 → 修正或推进”执行。独立复核检查结论与证据是否一致，程序同时检查阶段所需证据；两者都不能代替真实运行。

完整分支、并行关系和验收门槛见[工作流全景图](workflow-map.md)。

## 3. 环境验收：先建立可信的测量条件

### 3.1 先发现现场，再选择命令

检查实际主机、容器和调度环境，记录 DTK、编译器、PyTorch、关键计算与通信库、网卡、设备拓扑和共享存储。优先寻找现场的 Cluster Manager、`run_nhc`、检查脚本和 DTK 工具，并核对当前版本的帮助、源码及适用条件。

启动配方也属于环境：DTK 激活脚本、站点环境脚本的执行顺序，容器内外变量、各 rank 生效值，以及实际加载的库路径，都需要核实。已有经过验证的 HCU 配方优先复现。

缺少工具或权限的检查保持“未完成”，并记录可替代手段与覆盖缺口。运行主动测试前先核对调度授权、节点与设备占用；观察到空闲还需要确认使用权限，不抢占他人的训练资源。

### 3.2 检查的不只是“能运行”

按任务需要逐步验证：

- 节点、设备健康和实际可用资源；
- GEMM 计算性能、HBM 访存带宽；
- 机内互联和机间通信，包括实际使用的集合通信及其正确性；
- 网卡与通信链路、加载库、进程映射，以及存储和数据读取条件。

预期值必须有来源与条件：硬件标称、相同配置的历史实测、当前参考实现、尚未确定的预期要分开记录。不能拿明显异常的当前测量当作正常上限。

同时建立后续算子建模所需的硬件资料：HCU 型号、gfx、有效计算资源、显存和缓存、频率与功耗条件、不同精度下的计算能力、可用带宽。标称值与现场可达值分列，不确定项保留。

### 3.3 不符合预期时怎么做

先排查测试口径、单位、消息规模、设备映射、环境变量、库路径和实际通信路径，查询 HCU-Knowledge，必要时阅读对应分支源码。条件允许时做有界、可回退的对照实验。

基本排查后仍有可信差距，提交包含“预期、实测、已排除原因、剩余假设、建议动作”的问题，交由用户决定需要的专家或环境支持。受影响的验收保持未完成，无关的阅读与分析仍可继续。

详见[环境发现与偏差排查](environment-discovery.md)、[健康检查与筛机](cluster-health-and-screening.md)和[通信配方核对](practices/communication-recipe.md)。

## 4. 模型适配：保持真实训练语义

### 4.1 选择源码和启动配方

核对适用的官方实现、模型支持分支或 PR、HCU 工程和用户 patch。等价的 HCU 开源仓与内部仓之间优先选择适用的公开实现；公开仓明显滞后时检查内部活跃实现。分支选择还要看模型支持、依赖和功能，不能只看默认分支或最后提交日期。

HCU 的环境与启动脚本决定实际部署方式；官方模型和训练代码用于核对训练语义。需要确认模型构建入口、层数、隐藏维度、注意力和专家结构、位置编码、归一化、数据与 tokenizer、mask、loss、精度、优化器、参数组和学习率等。模型使用 Muon 或混合优化器时，必须检查实际分发，不能用另一个优化器代替后宣称适配成功。

执行基线与最终交付目标分别记录。适合模型的 HCU 主仓可以直接作为起点；使用功能分支或用户 patch 时，完整任务先在该基线上完成优化、阶段质量、扩容与容错验证，再整合目标主仓，避免中途更换整个引擎干扰归因。独立阶段按其授权范围完成交付。见[执行基线与交付顺序](practices/execution-baseline.md)。

### 4.2 先判断完整模型能否放下

结合适用的 HCU Train Sim、模型结构和当前健康资源估算容量，再用短跑校准。预算覆盖参数、梯度、优化器状态、激活、重算、通信缓冲、临时空间，以及初始化和保存时的峰值；关注最吃显存的 rank 和运行余量。

资源够就用完整模型；确实不够时优先只缩 layer，保留其他模型语义。维度、专家数等变化需要明确授权并单独标明代理范围。代理可以验证部分方法与流程，不能代表原完整模型的性能或收敛。详见[容量评估与并行实验](practices/capacity-and-parallel-experiments.md)和[代理模型契约](proxy-contract.md)。

### 4.3 建立初始基线

跑通前向、反向、梯度更新、数据处理和 checkpoint，确认实际调用了目标实现。记录源码、模型配置、优化器、数据和随机状态。具备 NVIDIA 环境时可以增加对照；没有时采用适用的参考实现和本地数值证据，说明比较覆盖范围。

后续候选始终保留这份初始数值基线，避免经过多轮小幅变化后丢失质量参照。

## 5. 性能优化：按主要瓶颈推进

### 5.1 先看并行切分、显存和实际吞吐

结合卡数、拓扑和模型评估 TP、PP、DP、CP、EP、SP，以及微批、梯度累积、重算、状态切分和 overlap。显存“刚好放下”不等于适合运行，还要为临时分配、通信和波动保留余量。

配置比较说明有效 batch、token 数、模型和精度是否一致。有效 batch 或学习语义变化时，单独解释可比性。`GPU_MAX_HW_QUEUES` 等变量按目标 runtime、实际配置和测量调整，不采用脱离环境的统一数值。

### 5.2 抓有代表性的端到端 profile

先取得稳定阶段的无 profiler 性能基线，再采集 CPU、GPU、通信及必要的显存证据。每个实际存在的非单例并行组至少选择两个有代表性的 rank；TraceLens 完整 collective 报告还要求当前任务 `0..N-1` 全部 rank 的文件和真实进程组上下文。代表性采样不能冒充完整集合通信报告。

利用 TraceLens 和工作流上下文关联真实 step、rank、算子、shape、前后向与优化器阶段。预热、编译、冷启动和 profiler 开销分别说明。CPU 活动长可能包含等待；GPU 空泡和通信耗时也需要结合依赖、慢 rank 与时间线判断，不能只凭一个比例定因。

### 5.3 谁占主要时间，先处理谁

| 主要现象 | 优先调查与优化方向 |
| --- | --- |
| 大量空泡、GPU 等待 | 数据流水、host 调度、同步点、流水线、CPU 阻塞 |
| 通信单测就明显异常 | 环境、链路、库版本、进程映射和实际实现 |
| 通信符合单测预期但暴露时间长 | overlap、bucket/chunk、调度、预取、通算融合及资源竞争 |
| rank 或专家负载不均 | 并行布局、流水调度、路由、通信与框架实现 |
| 计算算子占主导 | 按真实贡献排序，逐项分析瓶颈、上限和实现空间 |
| 显存压力、漂移或 OOM | 生命周期、缓存、碎片、临时峰值、状态切分、重算或泄露 |

这些方向会相互影响。通信隐藏可能挤占计算资源，融合可能增加寄存器或显存压力，因此看整步净收益，并在主要瓶颈变化后重新排序。

Torch 原生训练在同一流程中加强输入流水、autograd、DDP/FSDP、`compile`、断图、重编译及前后向图分析。RL 还需拆开训练、rollout、推理、权重同步和样本流转，核对策略版本、logprob、reward 与样本时效。

机制参考包括官方教程、开发分支和 PR，也包括 AMD Primus 系列、华为 MindSpeed/MindSpeed-LLM、百度 LoongForge 的适用实现。先查清适用条件和依赖，再在 HCU 上验证。见[性能分析](profiling.md)、[Torch 专项](../skills/hcu-train-optimize/references/torch-native-training.md)和[通信专项](../skills/hcu-train-optimize/references/communication-optimization.md)。

## 6. 算子优化：同形状对照、上限建模与迭代实现

这是计算瓶颈的主要处理路径。工作流先按真实逻辑算子聚合贡献，再细分 shape、dtype、layout、前后向阶段和实际实现，形成优先级列表。

### 6.1 明确覆盖口径

累计覆盖 **≥90% 端到端时间的热点集合**中，非通信算子逐项评估上限与效率。记录端到端墙钟分母、空泡、重叠和未归因时间；不能只在非通信 GPU 时间里凑够 90%，也不能把多个 rank 或重叠区间直接相加。

纯通信单独评估暴露时间、带宽、负载和 overlap；通算混合算子的计算部分仍需建模。空泡或未知项占比很大时，先解决归因缺口。

### 6.2 两条分析线可以并行

**同形状单测对照**：从模型提取实际 shape、dtype、stride、布局和调用路径，分别测计算、通信或 copy，保持工作量与环境条件可比。若独立运行快、放入模型后慢，重点调查资源竞争、依赖、时钟、缓存和调度。

**上限建模与实现优化**：根据真实工作量、数据搬运、精度、硬件和算法评估可达性能。简化 Roofline 可以用下式建立时间下界：

```text
时间下界 ≈ max(计算量 / 匹配精度的可达算力,
              必要数据量 / 对应存储层级的可达带宽,
              必要延迟约束)
```

这只是条件模型。还要考虑缓存命中、归约与同步、特殊指令、并行度和实际数据流，区分理论峰值与现场可达上限。报告给出假设、当前效率、剩余空间和可信度，不能用一个粗略 Roofline 数字作最终结论。

不同算子的分析和优化也可并行。每个任务具备自己的输入和测量条件就可推进，无需等待所有算子评估完成；共享 GPU、网卡或存储带宽的性能实验则需要排队或证明隔离。

### 6.3 先复用，再按实现类型深入

优先检查 HCU TE、Flash-Train、Primus Turbo、注意力与数学库等已有能力。对齐参考融合粒度时同时核对接口、前后向、保存的中间量、累加精度和转换位置。

- **缺少可信 HIP 基线**：用 `hygon-hip-baseline-generator` 建立数值与布局契约、初版实现和测试，再交给 HIP 优化。
- **已有 HIP/C++ 实现**：用 `hygon-hip-kernel-optimizer` 做建模、profile、ISA 查证和迭代回归。
- **已有 Triton 实现**：用 `hygon-triton-kernel-optimizer` 分析生成代码、配置与访存，推进对应优化。

初步融合后若仍明显低于可达性能，应继续查瓶颈，必要时转向 HIP 实现。遇到优化瓶颈要使用性能工具；DTK hipprof 与 XProf/XCompute 分别按实际功能和版本使用，结合目标架构核实指令证据。

GEMM 确有性能缺口时，从 rocBLAS/hipBLASLt 的日志提取可复现的 **完整 bench 命令**，保留布局、精度、转置、batch、步长等条件。rocBLAS 可依适用教程做有界 tune；hipBLASLt/grouped GEMM 整理实际 tune 需求交给用户协调，不能只交一个框架 shape。

通信按瓶颈联动 HCU RCCL、rocSHMEM、DeepEP、UCCL、UltraEP、MoonEP 等。必要时追到对应分支的底层源码，隔离修改与重编，并验证加载路径、正确性、单测和整步收益。成果根据原实现归属进入相应仓；新增训练融合实现按 TE、Flash-Train、Primus Turbo 等的职责与规范选择目标。

### 6.4 每个重点算子都要有处理结论

记录模型内耗时、独立耗时、当前效率、剩余空间、尝试结果和下一步。停止原因可以是接近可达上限、收益不稳定、资源或接口受限、质量风险、预算耗尽或需要专家支持；原因必须有证据。做出一个融合版本，并不自动表示该热点已完成优化。

详细方法与交接表见[热点排序、上限评估与算子迭代](../skills/hcu-train-optimize/references/operator-ceiling-iteration.md)和[底层库联动](practices/hcu-library-routing.md)。

## 7. 正确性与 loss：逐轮局部验证，稳定阶段严格对照

每个候选先验证真实分发、前后向、梯度或参数更新及多种相关 shape，再做重复的无 profiler 性能测试，同时观察显存与资源代价。保存当前最佳可信版本；合并多个优化后重新测量整步收益，不能把独立提升相加。

形成稳定阶段后，再做较长窗口的质量比较。基线和候选必须从相同的模型与优化器状态、随机状态、数据游标和配方出发，并使用预先确定的比较窗口与容差。从训练前一段取基线、再从进展后的状态取候选，不能自动视为有效 A/B。

`stage-quality` 的推进要求保留 `quality_inputs` 中的 contract、baseline、candidate，重算数值结果并核对冻结初态、配方、上下文与候选身份。只有历史 `pass` 标签、缺少比较输入的旧记录，不能据此推进新阶段。

局部正确性、阶段 loss 和长时收敛是不同结论。阶段通过不宣称完整模型收敛；数值退化时停止推进并定位原因。详见[数值与训练状态验证](training-state-validation.md)。

## 8. 多 Agent：围绕实际任务协作

主控按依赖、证据输入、代码范围和资源安排分工。例如，模型配方查证与环境资料核对可以并行；同形状复测与上限分析可以并行；互不耦合的高占比算子可以各自迭代。资源充裕时，也可用隔离的完整模型实例验证不同方向，共用基线和质量契约。

Agent 名单从当前模型与热点生成，不固定为某几个算子。每个任务有负责人、验收条件、实际会话和输出；相关 Agent 能提问、交流发现、汇报阻塞，下游使用经过验收的结果。共享测量、耦合修改、集成和阶段 loss 由主控协调。

独立复核检查目标、代码差异、原始证据及历史问题，不以实施者换名自审替代。简单单线问题直接处理，只有确实能并行或需要独立判断时才增加 Agent。见[多 Agent 协同](multi-agent.md)与[持续实施、复核和修正](collaboration.md)。

## 9. 扩 DP 域：把优化后的配置推向目标规模

完整模型是任务目标时，如果前面使用了代理配置，先恢复目标结构，重新评估容量并验证可行的模型并行布局；若已经是完整配置，无需重复“恢复”。用户明确只验证缩减模型时，可扩该配置的 DP，并保留原完整模型的验证缺口。

结合 Cluster Manager 等现有工具筛机，复核健康池和疑似节点的交叉测试。随后逐级扩 DP 域，检查显存、通信、吞吐与扩展效率，并说明是保持总工作量还是增加全局 batch。改变有效 batch 或学习配方时需要相应质量依据。

扩容出现新的慢 rank、负载不均或通信瓶颈时，返回优化阶段处理。保存与恢复同样属于验收：确认完整训练状态、存储预算、保存完成、旧进程退出，以及恢复后的优化器、随机状态、数据游标和实际训练进展。

故障恢复以现场既有容错为唯一恢复负责人。Agent 收集证据、定位问题和准备修复，实际隔离、终止或重启遵循部署时确定的授权。受控故障验证需要看到“发现故障 → 处理旧进程 → 重启加载 → 持续推进”的实际链路。见[长训运行与恢复](operations.md)。

## 10. 长时训练：同时关注训练和守护本身

训练启动后，按部署持续观察：

- step、token 和数据消费是否推进；
- loss、梯度、溢出与吞吐是否符合当前阶段预期；
- 各 rank、节点、进程和设备是否存活，显存与主机内存是否漂移；
- checkpoint 是否真实完成，恢复是否超过时限；
- 观察器及其独立健康检查是否仍有效。

日志和曲线保留单位、采样条件、缺失值与运行 attempt。图表用于发现趋势，数值缺失不能填成正常或零。卡住、core dump、内存/显存泄露等问题按证据收集、调用栈、版本和加载库核对、源码定位、最小复现与回归的路径处理。

本地主控休眠或离线时，已部署并验收的远端守护和既有容错继续工作。本机恢复后重放事件、去重并核对实际作业，再接续分析。通知已产生、通知已送达、Agent 已接单、问题已解决分别记录；自动唤醒依赖实际部署的 bridge 和宿主能力，不能由一份配置推断已经可用。

详见[训练观察](training-observation.md)、[分布式观察](distributed-observation.md)和[训练图表](training-dashboard.md)。

### 故障调查如何推进

任何阶段出现异常，都先固定任务/attempt 和首个错误时间线，区分训练本身、成员退出与观察链路故障，再按卡住、设备崩溃、内存增长、数值偏差、性能退化或保存恢复分流。查 HCU 大知识库的适用案例；不足时继续读在线 PR、官方资料和实际加载库的对应源码，用有界实验区分假设。修复后分别验证训练状态、连续进度、数值/显存、全部成员与监控链路，未覆盖的长稳场景明确保留。详见 [诊断指南](../skills/hcu-train-scale-and-stability/references/diagnosis.md)。

## 11. 人的指导如何进入流程

任务目录中的 `BOARD.md` 展示可直接指导工作的技术信息，包括环境预期与实测、模型与并行配置、profile 结论、热点上限和效率、优化方法与结果、阶段 loss、扩容、故障和持续训练状态。完整日志与证据通过链接展开。

用户在 `GUIDANCE.md` 写指导，在 `QUESTIONS.md` 提问。默认每 **5 分钟**采集文件变化，主控在新实验和阶段推进前检查已采集意见，并记录处理结果；会话中的即时指导照常处理，也可显式刷新。这个周期是交互文件采集周期，远端训练健康检查按站点另行配置。

正常步骤在授权内自主推进。明确权限缺口、模型语义不明、可信性能差距、质量异常、平台期或恢复超时，需要向用户提供具体证据、建议和待决事项，而非只显示一个“正在优化”的状态。

## 12. 知识、更新和最终交付

### 知识贯穿三个阶段

HCU-Knowledge 是完整安装的必需组成。遇到 HCU 问题，按工程、错误、符号、gfx/DTK、shape 和机制查询，并核对当前源码。TrainFlow 自带 Wiki 提供官方训练引擎与生态资料、可复用环境知识和模型最终优化总结。

官方资料覆盖 Megatron 生态及相关 TE、cuDNN Frontend 等底层依赖，也服务于其他训练与 RL 引擎。本地答案不足时，主动搜索线上已收录或未收录的 PR，阅读描述、review、讨论和最终 diff，再追到固定提交源码、调用者和测试。

局部官方 Wiki 可以按需频繁更新，并复核相关 Skill、命令、解析器是否过时；正在运行的任务仍固定自身依赖，更新知识不会自动升级训练环境。HCU 大知识库独立维护，普通查询与训练任务不附带更新。

### 哪些经验随工程保留

| 内容 | 归属 |
| --- | --- |
| 官方资料、专题、PR 与源码关联 | 工程官方 Wiki |
| 有适用条件和证据的通用站点经验 | `knowledge/sites/` |
| 数值验收明确的模型最终优化里程碑与关键数据 | `knowledge/experiments/` |
| 中间候选、零散排查、逐次调参和完整原件 | 当前任务 workspace 与看板 |
| 通用方法、流程与交接规则 | 工程 docs / Skills |

新任务可以复用既有经验，但仍核对硬件、版本、配置和测量条件。外部 Cookbook 的最佳实践另按目标工程规范处理，并保留草稿、PR 与后续状态关联。见[知识架构](knowledge-architecture.md)和[Wiki 检索与更新](wiki.md)。

### 交付什么

根据任务范围，交付可复现的源码和配置、启动与测试方法、环境与性能结论、质量证据、回退办法、恢复与监测说明，以及未解决限制。需要修改上游时，按正确目标仓的规范准备集中、可复核的 PR；整合版本重新验证。

完整流程的完成意味着约定范围内的模型、性能、质量、扩容和持续运行条件都有对应结论。只分析或诊断的任务，则交付已查明的问题、证据和下一步，不额外要求训练到全流程终点。
