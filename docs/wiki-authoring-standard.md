# Wiki 工程组织规范

所有登记官方工程按同一组内容维度整理。不同工程可以有不同页数，但不能用一篇简介、目录清单或大批原文代替核心实现的解释。已深入的工程保留细节，薄弱工程补足相同类型的问题和证据。

## 内容维度

| 维度 | 必须让读者找到的内容 |
| --- | --- |
| 定位与边界 | 解决什么问题、在训练链路的职责、上游/HCU/第三方区别 |
| 工程目录 | 目录/关键文件 → 职责 → 从什么问题进入，继续到实际函数或类 |
| 安装与依赖 | 构建入口、版本/子模块、可选扩展、运行环境与实际加载确认 |
| 运行与测试 | 官方 recipe/配置入口、启动与分层单测、关键参数、成功判据 |
| 模型与数据契约 | 支持入口、模型参数、数据/mask/batch、精度及状态所有权 |
| 调用链 | 从配置/入口到核心实现、底层依赖和对应测试；不只罗列函数 |
| 性能与内存 | 至少两项有源码依据的机制，解释触发、收益来源、代价和限制 |
| 数值、诊断与恢复 | 典型症状的定位路径、数值/分布式状态、恢复与回退条件 |
| 版本、PR 与更新 | 当前固定证据、发布/roadmap/特性 PR 入口、更新需联动哪些页 |

图执行库的“模型与数据”解释 tensor/layout/autograd 契约；工具的“运行与测试”解释输入格式和分析/诊断验收。确实不适用的维度注明职责边界并链接消费者，不套写不存在的训练循环。源码阅读、上游测试描述与 HCU 实测分别标记。

## 页面与证据

- 总览作为工程入口，链接运行指南、机制专题、案例、官方文档和 PR。保留既有路径和 ID，避免更新后旧查询入口失效。
- 机制专题写清 **问题 → 配置/调用链 → 实现位置 → 适用条件 → 验证 → 限制/回退**。关联到实际文件、符号和完整固定提交；对重要 PR 同时读描述、review、最终代码与测试。
- 案例使用相同证据标准，不要求将所有 PR 写成案例。引用上游性能数字时保留设备、输入、版本和测量范围；没有实测不填估计收益。
- 原文、PR 与全仓路径保存在原来源层。作者正文解释机制和选择，不粘贴整篇文档，也不通过通用模板重复凑篇幅。

## 更新与均衡检查

`knowledge/coverage.json` 登记各工程的来源、入口、内容维度与机制专题；[覆盖导航](../knowledge/COVERAGE.md)便于横向浏览。维护时先检查薄弱维度，再按当前变化修订相关总览、专题、案例和工作流。新增来源必须登记角色和阅读入口，不能只注册下载。

`python scripts/check_wiki_coverage.py` 检查登记来源、页面与维度引用是否齐全，`validate_knowledge.py` 核对固定证据。它们不判断文字是否准确：Agent 仍须阅读正文与代码、运行代表性查询，并明确未覆盖模型、backend、历史 PR 或现场验证范围。统一标准不是“所有实现均已精读”的声明。

父工程的固定子仓另登记时，用 `parent_gitlink` 指明父来源和路径，子来源 `ref`/基线对应父树中的完整提交。覆盖检查会报告父 gitlink 漂移；更新先核对父工程调用，再推进子来源和关联专题，不拿子仓最新 HEAD 偷换父工程实际依赖。

更新采集和复核继续走 [Wiki 协议](wiki.md)。Release/roadmap 的存在与查证结果单独记录，完整目录不表示自动收录所有网页或历史讨论。工具/方法来源保留其用途，不因为其不是训练引擎就漏掉更新或硬套模型专题。
