# Wiki 工程组织规范

lite 使用发现优先的维护方式：先保留可靠的官方路由、版本边界、已有知识和实际引用证据；普通 PR 通过联搜找到原页。正文、代码和必要讨论按问题读取，不要求离线镜像所有评论、review 或 PR 历史。新增来源不附带逐仓报告、统一维度或案例数量配额。

## 内容维度

下表是形成深入解释时可选择的阅读方向。按来源角色、实际问题和变化影响使用，不要求每仓逐项填表；已有详细知识继续保留。

| 阅读方向 | 需要解释时核对的内容 |
| --- | --- |
| 定位与边界 | 解决什么问题、在训练链路的职责、上游/HCU/第三方区别 |
| 工程目录 | 目录/关键文件 → 职责 → 从什么问题进入，继续到实际函数或类 |
| 安装与依赖 | 构建入口、版本/子模块、可选扩展、运行环境与实际加载确认 |
| 运行与测试 | 官方 recipe/配置入口、启动与分层单测、关键参数、成功判据 |
| 模型与数据契约 | 支持入口、模型参数、数据/mask/batch、精度及状态所有权 |
| 调用链 | 从配置/入口到核心实现、底层依赖和对应测试；不只罗列函数 |
| 性能与内存 | 与问题相关的机制，解释触发、收益来源、代价和限制 |
| 数值、诊断与恢复 | 典型症状的定位路径、数值/分布式状态、恢复与回退条件 |
| 版本、PR 与更新 | 当前固定证据、发布/roadmap/特性 PR 入口、更新需联动哪些页 |

图执行库可重点解释 tensor/layout/autograd 契约；工具可重点解释输入格式和分析/诊断验收。只写实际适用的内容，不为满足模板套写训练循环。源码阅读、上游测试描述与 HCU 实测分别标记。

## 页面与证据

- 已有工程以 `knowledge/projects/<project>/README.md` 导航，`knowledgebase/upstream` 保留选定官方资料，`knowledgebase/local` 放深入解释。新增发现来源先登记官方路由即可；有值得沉淀的内容时再扩展作者页。路径调整同步引用与迁移映射，保持页面 ID 稳定。
- 机制专题写清 **问题 → 配置/调用链 → 实现位置 → 适用条件 → 验证 → 限制/回退**。关联实际文件、符号和完整固定提交；需要解释重要 PR 时读取描述、最终代码与测试，存在设计歧义时再查相关讨论。
- 案例使用相同证据标准，不要求将所有 PR 写成案例。引用上游性能数字时保留设备、输入、版本和测量范围；没有实测不填估计收益。
- 已引用原件和选定 PR 保存在来源层，普通 PR 保留在线发现入口。退役的历史副本沿固定 Git 基线按需读取，不为保留历史再建立一份全量镜像。作者正文解释机制和选择，不粘贴整篇文档，也不通过模板凑篇幅。

上述内容维度适用于局部官方工程；HCU 仓库知识归 HCU-Knowledge，不在 TrainFlow 再建平行 Wiki。HCU 工具的流程接口和适用边界留本仓 docs，通用使用经验按规范进 sites；联查与受影响用法登记 `catalog/external-knowledge.json`。Release/roadmap 保留官方入口与必要版本解释，不要求单独归档发布页 JSON。

## 更新时如何选择案例

资料维护和任务中经验提炼都先判断变化是否影响现有用法，以及是否值得形成长期知识；重构请求本身不触发全库资料刷新：

- **重大或高价值优化项整理详细案例**：算法/融合、并行调度与通信重叠、访存或状态生命周期等实质改进，能解释重要瓶颈且有复用价值。先读实际代码、描述和测试，必要时查讨论；优先完善同一机制的已有案例。
- **小修改按影响维护**：常规修复、局部参数/接口调整、版本兼容和文档维护，仅修订受影响章节和必要证据；未影响现有知识的普通提交保持在线入口，不逐条生成摘要。影响已有案例就修订，不为每个 PR 或每轮维护另写案例。
- **深度按影响确定**：不按 diff 行数、统一加速比或案例数量判定；重要精度、正确性或恢复变化即使代码很少，也要充分说明并联动复核。没有重大优化项可以不新增案例；内容维度齐全不意味着各仓案例数相同或每次新增机制页。
- **缺证据保留缺口**：重大优化项暂缺实现、测试或性能依据时，在已有维护记录中注明待补入口；已确认机制与未验证收益分开，不造数据、不把来源宣称改成自己的实测。

来源登记不等于承诺镜像其全部正文、讨论或每条后续变更。实际使用影响仍须联动相关页面、Skill 与版本证据；无关内容无需重写总结。通用环境经验和最终模型总结按 [知识归属](knowledge-architecture.md) 筛选，不把中间改动扩写成共享大案例。

## 更新与均衡检查

`knowledge/coverage.json` 的 schema 2 / `discovery-first` 登记各来源组的角色、来源 ID、已有入口、可选深入阅读链接和限制；[覆盖导航](../knowledge/COVERAGE.md)保留现有专题。新增来源有真实官方路由即可，不强制先写工程报告。维护按实际变化和消费者依赖判断影响，不逐仓重复完整阅读与总结。旧 profile 的维度检查保留用于旧 checkout，不是 lite 的新增义务。

新增来源或改变材料保留方式时，同步[第三方工程与来源说明](../THIRD_PARTY_NOTICES.md)；保留的上游文档、PR 等材料继续记录原始归属，并核对[知识材料声明与许可副本](../thirdparty/KNOWLEDGE-NOTICES.md)，不能把来源层原文表述为 TrainFlow 原创内容。已有来源推进版本时，也按该页维护规则核对 LICENSE/NOTICE、文档目录或文件专用许可及官网声明；分别记录副本来源、核对基线和未确认项，不能用仓库许可替代网页材料的适用声明。

`python scripts/check_wiki_coverage.py` 检查来源分组、角色、路由、已有页面链接与父锁；不检查九维、机制或案例数量配额。`validate_knowledge.py` 核对当前保留的固定证据。程序不判断文字是否准确：形成结论仍需阅读相关正文与代码、运行代表性查询，并说明未覆盖模型、backend、历史 PR 或现场验证范围。

父工程的固定子仓另登记时，用 `parent_gitlink` 指明父来源和路径，子来源 `ref`/基线对应父树中的完整提交。覆盖检查会报告父 gitlink 漂移；更新先核对父工程调用，再推进子来源和关联专题，不拿子仓最新 HEAD 偷换父工程实际依赖。

更新采集和复核继续走 [Wiki 协议](wiki.md)。Release/roadmap 的存在与查证结果单独记录，完整目录不表示自动收录所有网页或历史讨论。工具/方法来源保留其用途，不因为其不是训练引擎就漏掉更新或硬套模型专题。
