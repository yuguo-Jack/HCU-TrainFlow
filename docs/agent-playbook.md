# 主控接手与阶段交接

这是 `$hcu-trainflow` 在新任务、换 Agent 或中断恢复时的阅读入口。它把阶段决策串起来；具体工具和参数以对应 Skill、当前 CLI 帮助及实际部署源码为准。Agent 负责实施，CLI 保存状态并检查契约。不要把“读完流程”或“生成报告”当作已执行训练。

## 1. 先恢复事实，再选择动作

1. **定位**：确认项目 checkout、版本、私有 workspace、Task ID 和当前模式。新任务从用户的环境、模型和目标生成 TaskSpec；已有任务先读 `task-show`、`flow-next`、BOARD/DETAILS 和三个计划文件，不能另建同名任务来绕过旧阻塞。
2. **核对任务边界**：完整训练还是仅环境检查、适配、分析、优化、诊断或运行；完整模型还是获准的代理配置；本轮的性能、质量、规模和监测完成条件是什么。沿用会话授权，只询问会实质影响下一动作的缺项。
3. **核对现场与在途工作**：已运行的 operation/attempt、活跃 Agent、资源、最近观测时间和未处理事件。遇到 `reconcile` 先确认原操作；旧日志中的成功和上次看到空卡都不代表现在的状态。先查进程/调度/设备占用，再考虑任何可能触卡的探针。
4. **接收指导**：读取已采集的用户指导、问题和相关 Agent 消息，明确应用范围。文件默认每 300 秒采集，会话的新指导即时留存；正常已授权工作持续推进，不把每步都变为确认。
5. **检查依赖**：完整安装含 HCU-Knowledge、三个算子 Skill 和 TraceLens。确认搜索目录/索引与工具的实际可用性；对需要的在线资料做真实权限请求检查。缺在线权限不等于离线搜索失效。普通任务不更新 HCU-Knowledge。
6. **写清本轮决定**：在现有计划和 BOARD 中说明当前主要问题、证据、下一步及停止条件，然后只加载当前阶段 Skill 与所需参考。无需每轮通读整个 Wiki 或启动固定团队。

若 `flow-next` 仍要求环境/基线报告，但看板已经记录了大量算子或恢复实验，应先核对状态差异：哪些是探索，哪些已验收，哪些报告属于旧 context。补齐真实交接；不要改看板冒充推进，也不要因为状态停在早期就把已验证的独立实验全部重做。

### 最小接手信息

以下信息使用已有 TaskSpec、看板和原始证据保存，不另建重复数据库：

| 信息 | 接手时必须能回答 |
| --- | --- |
| 目标与范围 | 用户要什么；模型/代理差异；本轮哪些事项已明确停止或延期 |
| 代码与运行身份 | 执行基线、用户 patch、具体候选、最终交付仓；节点/容器/调度 allocation、镜像与依赖身份 |
| 数值与比较条件 | 初始状态、优化器参数组、数据/tokenizer/mask、随机状态、精度、有效 batch、容差依据 |
| 资源与恢复 | 哪些资源获准且当前空闲；哪个现场工具拥有恢复权；谁在运行或等待 |
| 当前结论 | 最大端到端瓶颈、最佳已验收候选、未完成热点/风险及原件入口 |
| 下一步 | 当前 `flow-next` 动作、最小有价值实验、预期产物、停止/回退与专家介入条件 |

## 2. 三个阶段各交什么，什么时候进入下一阶段

| 阶段 | 主要判断和工作 | 交接证据 | 不应提前做的事 |
| --- | --- | --- | --- |
| 环境与适配 | 复原 HCU/现场启动链；验收硬件、GEMM、访存和互联；核对官方模型语义；容量预估并短跑校准，能放下就全参，否则优先只缩 layer | 当前环境报告、配方与依赖身份、模型差异、初始数值基线、未覆盖项 | 未查现场配方就照搬 NV 命令；未知预期当 pass；为跑通静默换优化器或缩维 |
| 分析与优化 | 并行切分和显存权衡；稳定多 rank profile；按最大瓶颈推进系统、通信或计算；真实热点建模、复用/融合/实现迭代 | 热点及墙钟分母、逐项模型与处置、实际 dispatch、局部回归、profiler-off 对照、阶段 loss、最佳候选与回退 | 先挑易写的算子；初步融合即结束；仅凭优化器小例子宣称模型收益；把最近候选当最佳 |
| 扩 DP 与容错 | 选定完整配置或明确代理范围；健康池筛选、逐级扩 DP；保存/加载/续训；单一恢复负责人、全部成员及观察器健康 | 每级配置/环境/规模验收、实际恢复和进展、监测/告警/接续验证范围、最终完成或交接条件 | 启动即结束；只看一个 rank；观察器心跳代替训练进展；Agent 与现场工具同时重启 |

程序状态与证据门槛：

```text
prepared --environment--> environment_checked --baseline--> baseline_validated
         --baseline--> profiling --analysis--> optimizing
         --stage-quality + performance--> scale_ready
         --environment + stage-quality + scale--> training --completion--> completed
```

每个箭头仍要经过候选提交、独立复核和程序检查；`flow-next` 返回的 `required_reports` 是当前模式的实际要求。优化阶段的 `iterate` 只保留局部候选，不代替阶段 loss。`stage-quality` 必须按质量契约登记可重算的 `quality_inputs`，包含固定初态和配方；旧窗口比较的 pass 不授予新阶段晋级。跨阶段可以并行准备资料、源码和独立验证，但相关 gate 未通过就不能把整阶段称为通过。

### 门槛未通过时，允许的有界诊断

环境差距、未知硬件参数或缺少依赖时，仍可在已授权资源上做用于解决该问题的短实验，或并行开展不依赖缺项的源码分析。保持原 fail/incomplete 与具体未覆盖项，记录诊断范围和证据；不得为了试验把门槛改成 pass。若用户明确调整本轮为代理验证/局部分析，记录真实指导、更新比较范围和计划，重新检查受影响证据；完整模型目标的缺口继续保留。

仅检查/分析/诊断可以交付失败或不充分的结论，并按本模式完成；这不授予训练准入。执行模式与目标不得由 Agent 为方便自行缩减。完整任务的未解决问题应升级、等待所需输入或有据修复，不能以“流程已走过”结束。

## 3. 优化每轮的选择顺序

1. **先判断数据是否能支持结论**：同一候选、窗口、rank 组、phase、精度和真实调用；warmup/编译/保存与稳态分开，profile 的时间不当无 profiler 基准。空泡需要继续区分数据、host 提交、同步/依赖及采样缺口。
2. **按端到端主要占比决策**：空泡最大先解原因；通信最大先区分异常、固有链路开销及负载不均。异常走环境/库/数据路径排查，正常固有开销再考虑 overlap、调度、通算融合。计算最大按逻辑 op 占比排序，高占比上限未知者先建模。显存余量贯穿所有选择。
3. **并行做必要的两类证据**：冻结调用后，同 shape 独立实测与上限建模可同时开展；不同热点可各自进入实现。实际 GPU/NIC/共享盘测量只有资源真正隔离才并行。独立任务的结果通过验收后再用于组合决策。
4. **模型能复算**：累计 ≥90% 端到端热点集合里的非通信算子，说明 FLOPs、流量层级、延迟约束、匹配的硬件/可达参考及当前效率。纯通信另列，含计算的融合通信仍建模；保留空泡/未归因部分。复制带宽或方形 GEMM 峰值不是所有算子的可达性能。理论空间不是整步可兑现收益。
5. **实施依据充分才写代码**：先查当前 HCU 库和对应分支。缺 HIP 正确基线走 baseline Skill，再交 HIP optimizer；已有 HIP/Triton 分别进入对应优化 Skill。遇到瓶颈必须使用实际 profiler/ISA/计数器证据。数学库确有性能缺口再提取原生日志里的完整 bench 命令交 tune，不能只报框架 shape。
6. **局部正确才比较速度**：实际 dispatch、前后向/参数更新、多形状回归；按预先约定的无 profiler 测量协议重复。数值失败先定位精度/顺序/状态，不能放宽门槛换通过。初步融合仍远低于合理上限就继续优化，或有据说明限制与下一步。
7. **组合后重新归因**：多个独立收益不能相加。回接模型后确认加载候选，检查通信竞争、显存、shape/热点变化，再在稳定里程碑验 loss。布局、数据、初态或验证契约改变时重新冻结适用范围，不能沿用失配证据。

停止一个方向应属于以下之一：达到目标；已接近有依据的可达水平；受控重复无稳定收益；当前证据或依赖不足；到达预算/数值风险边界。前两项可以保留实现，后几项记录原因和未兑现空间，必要时升级专家。均不等同于整任务自动完成。

## 4. 证据怎样复用，什么变化需要重验

| 变化 | 处理 |
| --- | --- |
| 仅改说明或读取相同原件 | 复用已核验结论，不重复占卡 |
| kernel 实现/launch 改变 | 新候选局部数值、实际 dispatch、多 shape 和无 profiler 对照；稳态集成后阶段 loss |
| 并行布局、MB/累积、overlap/队列改变 | 有效 batch/训练语义、最重 rank 显存、通信/shape/profile 和受影响数值；重新排序 |
| 环境、模型/数据、初始基线或质量契约改变 | `task-context` + `flow-replan`；旧证据仅作参考，核对新观察 Store/peer/sentinel 的交接 |
| 上游源码/工具命令变化 | 读匹配分支 diff/help，复核调用、库加载、解析器与 Skill；先在隔离候选中验证，不替换运行中的依赖 |
| 只有文档更新、线上 PR 搜索 | 私有留存或局部 Wiki 维护；不自动刷新 HCU 大知识库，也不把未合入 PR 当现场已有能力 |

报告绑定当前 `candidate_snapshot`。复用以前的环境或基线证据时，说明哪些依赖没变、原件 ID 和适用依据；不能只替换哈希字段。失败/被拒候选和最佳版本都留存，清理只处理已登记可重建缓存。

## 5. 多 Agent、看板与长训的接续

- 默认一个主控。存在输入明确、相互独立且有收益的任务才委派；同一问题不用重复派三个人。动态拆分源码/算子/分析范围，并提供 Skill、oracle、profile、允许路径、资源和验收。有关联的 Agent 主动共享证据，主控验收兼容结果。
- BOARD 直接展示环境预期与实测、配置/显存、瓶颈证据、热点上限与余量、实验结果、恢复/训练趋势和缺口。细节和原件链接在同一工作区；记录不是重新做一次实验。
- 每次启动或接续训练都核对全部必需成员、真实输出进度的 rank、观察器/sentinel、唯一恢复 owner、保存点与告警路由。通知送达、Agent 唤醒、训练恢复分别验收；没有配置桥接时说明恢复本机后人工打开任务的接续方式。
- 主控离线时远端观察和既有容错独立运行。回来先同步事件并核销原 attempt；不能看到超时就换 ID 重跑。进度/吞吐异常的调查先保存运行现场，主动压测在隔离空闲资源或获准维护窗口进行。
- 有意结束本轮工作时，要有最终停止状态或明确运行交接：作业/恢复/观察由谁负责、下一事件如何通知、未完成项在哪里。不要为了写最终答复关闭用户要求持续运行的训练。

## 6. 收尾与阅读路由

成果由负责阶段交付，不增加交付 Skill。功能分支/用户 patch 先完成选定工作流，再整合到活跃 HCU 出口并回归；不要为追主仓在中途换实验基线。共享 Wiki 只收官方资料、通用环境经验和最终模型优化里程碑；中间尝试留 workspace。外部 PR/Cookbook 遵循其仓库规范与授权。
